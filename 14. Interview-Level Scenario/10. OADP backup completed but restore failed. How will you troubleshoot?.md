# OADP Backup Completed but Restore Failed — Interview-Level Troubleshooting Scenario

**Role level:** Advanced OpenShift Administrator / Platform Engineer with 10+ years experience  
**Technology focus:** Red Hat OpenShift, OADP, Velero, CSI snapshots, Data Mover, Kopia/Restic, object storage, RBAC, SCC, admission webhooks, PV/PVC restore, namespace restore

---

## 1. Interview Scenario

**Question:**

> OADP backup completed successfully, but the restore failed. How will you troubleshoot?

**Senior-level answer:**

I would not assume that a completed backup means every application component is restorable. In OADP, a backup can complete while the restore fails because of restore-time conditions: missing CRDs, unavailable storage classes, PVC binding issues, snapshot restore problems, admission webhook failures, SCC/RBAC restrictions, existing conflicting resources, namespace mapping issues, image registry problems, or application-specific post-restore hooks.

My troubleshooting approach is structured:

1. Confirm the restore phase and exact failure messages.
2. Compare backup contents with restore scope.
3. Check OADP, Velero, node-agent, and plugin health.
4. Validate BackupStorageLocation and VolumeSnapshotLocation.
5. Investigate PVC/PV restore and CSI snapshot/data mover behavior.
6. Check namespace, CRD, API version, and resource conflicts.
7. Check admission webhooks, SCC, RBAC, quotas, limits, and NetworkPolicies.
8. Validate restored application objects and logs.
9. Decide whether to retry restore, restore selectively, restore into a new namespace, or fix cluster prerequisites first.

---

## 2. Important Concept: Backup Completed Does Not Guarantee Restore Success

A backup may show `Completed`, but restore can still fail because restore is a separate operation with different dependencies.

### Backup depends on:

- Velero/OADP pod health
- Object storage access
- Backup CR configuration
- Snapshot or filesystem backup availability
- Namespace and resource selection
- Backup plugin behavior

### Restore depends on:

- Target cluster API compatibility
- Target namespace state
- CRDs/operators existing before custom resources are restored
- StorageClass availability
- CSI driver availability
- VolumeSnapshotClass availability
- SCC/RBAC permissions
- Admission webhook availability
- Existing object conflicts
- PVC binding behavior
- Node-agent/Kopia/Restic restore health
- Application-specific startup dependencies

So my first statement in an interview would be:

> A completed OADP backup confirms that Velero stored the selected backup data, but restore can fail if the target cluster does not satisfy the same API, storage, security, and dependency requirements required to recreate the workload.

## 4. Confirm Backup Actually Contains Required Resources

A common mistake is assuming the backup included everything. I verify what was backed up.

```bash
oc get backup -n openshift-adp
oc get backup <backup-name> -n openshift-adp -o yaml
velero backup describe <backup-name> --details
velero backup logs <backup-name>
```

Check:

- Was the correct namespace included?
- Were labels used incorrectly?
- Were cluster-scoped resources excluded?
- Were PVCs included?
- Were PVs restored using snapshot or filesystem backup?
- Were CRDs included or excluded?
- Were resources excluded with `excludedResources`?
- Was `snapshotVolumes` enabled or disabled?
- Was `defaultVolumesToFsBackup` used?
- Did backup finish with warnings?

Example:

```bash
velero backup describe app-backup --details
```

Look for:

```text
Phase: Completed
Warnings: <number>
Errors: <number>
Namespaces: app-prod
Resources: pods, services, routes, deployments, pvc, secrets, configmaps
Velero-Native Snapshots: true/false
CSI Snapshots: true/false
Pod Volume Backups: completed/failed
```

Interview statement:

> I always compare the restore failure with the original backup content. Restore cannot recover resources that were never selected, were excluded, or failed during backup with warnings.

## 5. Check Restore CR Specification

Inspect the restore object:

```bash
oc get restore <restore-name> -n openshift-adp -o yaml
```

Key fields:

```yaml
spec:
  backupName: app-backup
  includedNamespaces:
  - app-prod
  excludedResources:
  - nodes
  - events
  restorePVs: true
  namespaceMapping:
    app-prod: app-restore
```

Check for mistakes:

- Wrong `backupName`
- Wrong namespace mapping
- `restorePVs: false` when persistent data is expected
- Excluding required resources
- Including resources that should not be restored
- Trying to restore cluster resources without required permissions
- Restore into existing namespace with resource conflicts

Correct sample Restore CR:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: app-restore-001
  namespace: openshift-adp
spec:
  backupName: app-backup-001
  includedNamespaces:
  - app-prod
  excludedResources:
  - nodes
  - events
  - events.events.k8s.io
  - backups.velero.io
  - restores.velero.io
  - resticrepositories.velero.io
  restorePVs: true
```

Restore to a different namespace:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: app-restore-to-new-ns
  namespace: openshift-adp
spec:
  backupName: app-backup-001
  namespaceMapping:
    app-prod: app-restore
  restorePVs: true
```

## 7. Check BackupStorageLocation

Restore needs to read the backup metadata and artifacts from object storage.

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
oc describe backupstoragelocations.velero.io -n openshift-adp
```

Expected:

```text
PHASE: Available
```

If BSL is unavailable:

```bash
oc get secret -n openshift-adp
oc describe secret cloud-credentials -n openshift-adp
oc logs deploy/velero -n openshift-adp | grep -i backupstoragelocation
oc logs deploy/velero -n openshift-adp | grep -i s3
```

Check:

- Bucket exists
- Prefix is correct
- Region is correct
- Endpoint URL is correct
- Credentials are correct
- CA certificate is trusted
- S3-compatible provider requires special config
- Network/DNS from cluster to object storage works
- Proxy/noProxy is correct
- Object lock/versioning/WORM bucket compatibility

Example BSL check:

```bash
oc get bsl -n openshift-adp -o yaml
```

Look for:

```yaml
status:
  phase: Available
  lastValidationTime: ...
```

If restore error says backup not found:

```bash
velero backup get
velero backup describe <backup-name>
```

Possible causes:

- Backup expired due to TTL
- Backup object deleted from bucket
- Wrong BSL selected
- Wrong bucket prefix
- Restore running on different cluster with no access to source bucket
- Credentials cannot list/read objects

## 8. Check VolumeSnapshotLocation and CSI Snapshot Readiness

If the backup used CSI snapshots, restore needs the target cluster to support snapshot restore.

```bash
oc get volumesnapshotlocation.velero.io -n openshift-adp
oc describe volumesnapshotlocation.velero.io -n openshift-adp
```

Check VolumeSnapshot CRDs:

```bash
oc get crd | grep volumesnapshot
```

Expected CRDs:

```text
volumesnapshotclasses.snapshot.storage.k8s.io
volumesnapshotcontents.snapshot.storage.k8s.io
volumesnapshots.snapshot.storage.k8s.io
```

Check snapshot classes:

```bash
oc get volumesnapshotclass
oc describe volumesnapshotclass <snapshot-class-name>
```

Check CSI driver:

```bash
oc get csidriver
oc get pods -A | grep -i csi
oc get storageclass
```

Common CSI restore problems:

- No `VolumeSnapshotClass`
- Snapshot class missing deletion policy
- Snapshot driver name mismatch
- Target cluster does not have same CSI driver
- Restoring to a different cloud/region/storage backend
- PVC requested size does not match expected restore size
- Snapshot content cannot be found
- Snapshot API unavailable
- CSI provisioner/snapshotter pods unhealthy

Useful checks:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
oc describe volumesnapshot -n <namespace> <snapshot-name>
oc describe volumesnapshotcontent <snapshotcontent-name>
```

Interview statement:

> If backup completed with CSI snapshots but restore fails at PVC creation, I verify VolumeSnapshotClass, CSI driver, StorageClass, and whether the target cluster can provision a PVC from the restored snapshot.

## 9. Check PVC and PV Restore Failures

Most OADP restore failures in production are related to persistent data.

Check restored namespace:

```bash
oc get pvc -n <namespace>
oc describe pvc -n <namespace> <pvc-name>
oc get pv
oc describe pv <pv-name>
```

Check events:

```bash
oc get events -n <namespace> --sort-by='.lastTimestamp'
```

Common PVC symptoms:

```text
Pending
Lost
FailedBinding
ProvisioningFailed
waiting for first consumer
volume snapshot not ready
storageclass not found
requested storage greater than snapshot size
access mode not supported
```

Check StorageClass:

```bash
oc get sc
oc describe sc <storageclass-name>
```

Important fields:

```yaml
provisioner: openshift-storage.rbd.csi.ceph.com
volumeBindingMode: Immediate
allowVolumeExpansion: true
reclaimPolicy: Delete
```

If target cluster does not have the same StorageClass:

```bash
oc patch pvc <pvc-name> -n <namespace> -p '{"spec":{"storageClassName":"new-storageclass"}}'
```

However, PVC storageClass is often immutable after creation. Better options:

- Restore into a clean namespace after preparing correct StorageClass.
- Use Velero restore resource modifier if supported in your OADP version.
- Pre-create compatible StorageClass with same name.
- Restore resources without PVCs first, then restore data separately.

Check PVC capacity mismatch:

```bash
oc get pvc -n <namespace> -o custom-columns=NAME:.metadata.name,REQ:.spec.resources.requests.storage,STATUS:.status.phase,SC:.spec.storageClassName
```

If backup-time PVC was 20Gi and restore spec requests 10Gi, restore can fail. The requested size should not be smaller than the backed-up volume size.

## 10. Check Filesystem Backup / Kopia / Restic Restore

If OADP used filesystem backup instead of snapshots, restore depends on node-agent and Kopia/Restic repository.

Check pod volume backups and restores:

```bash
oc get podvolumebackups -n openshift-adp
oc get podvolumerestores -n openshift-adp
oc describe podvolumerestore -n openshift-adp <pvr-name>
```

Check DataUpload/DataDownload if Data Mover is used:

```bash
oc get datauploads -n openshift-adp
oc get datadownloads -n openshift-adp
oc describe datadownload -n openshift-adp <datadownload-name>
```

Check repository objects:

```bash
oc get backuprepositories -n openshift-adp
oc describe backuprepository -n openshift-adp <repo-name>
```

Common filesystem restore errors:

- Node-agent not scheduled on the node
- Repository locked
- Repository unavailable
- Object storage read failure
- Permission denied inside restored volume
- Pod not created for restore hook
- Kopia/Restic timeout
- PVC not bound before restore starts
- NetworkPolicy blocking access
- Large volume restore timing out

Logs:

```bash
oc logs -n openshift-adp daemonset/node-agent
oc logs -n openshift-adp deploy/velero
```

Search for:

```bash
oc logs -n openshift-adp deploy/velero | egrep -i "podvolumerestore|kopia|restic|error|failed|timeout|permission"
```

## 11. Check Namespace Conflicts

Restore can fail if resources already exist in the target namespace.

```bash
oc get ns <namespace>
oc get all -n <namespace>
oc get pvc,secret,cm,route,ingress -n <namespace>
```

Common errors:

```text
resource already exists
cannot patch immutable field
field is immutable
object has been modified
already exists and is different
```

Senior approach:

- Do not blindly delete production namespace.
- Restore into a temporary namespace first.
- Use namespace mapping for validation.
- Compare restored resources before cutover.

Example restore into clean namespace:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-app-prod-to-test
  namespace: openshift-adp
spec:
  backupName: app-prod-backup
  namespaceMapping:
    app-prod: app-prod-restore-test
  restorePVs: true
```

## 12. Check Missing CRDs and Operators

If the backup contains custom resources, the target cluster must have the CRDs installed before restore.

Examples:

- Argo CD `Application`
- ServiceMesh `VirtualService`
- Cert-manager `Certificate`
- PrometheusRule
- Kafka CRs
- OpenShift Pipelines CRs
- OpenShift GitOps CRs
- ODF/NooBaa CRs

Check failed restore logs:

```bash
velero restore logs <restore-name> | grep -i "no matches for kind"
```

Example error:

```text
no matches for kind "Application" in version "argoproj.io/v1alpha1"
```

Check CRDs:

```bash
oc get crd | grep -i argoproj
oc get crd | grep -i kafka
oc get crd | grep -i cert
```

Fix:

1. Install the required operator on the target cluster.
2. Confirm CRDs exist.
3. Re-run restore.

Commands:

```bash
oc get packagemanifest -n openshift-marketplace | grep -i <operator>
oc get csv -A | grep -i <operator>
oc get crd | grep -i <api-group>
```

Interview statement:

> For CR-based applications, I restore prerequisites first: operators and CRDs, then restore custom resources. Velero cannot restore a custom resource if the target API server does not know that kind.

## 13. Check API Version Compatibility

Restore may fail when moving backups between different OpenShift/Kubernetes versions.

Check source and target versions:

```bash
oc version
oc get clusterversion
```

Check failed APIs in logs:

```bash
velero restore logs <restore-name> | egrep -i "no matches|deprecated|unable to recognize|not found|unsupported"
```

Examples:

```text
no matches for kind "DeploymentConfig" in version ...
unable to recognize "": no matches for kind ...
```

Fix options:

- Install required CRDs/operators.
- Convert manifests to supported API versions.
- Use restore resource modifiers if supported.
- Restore to same/similar OpenShift version where possible.
- Exclude problematic resources and recreate them with GitOps.

## 14. Check Admission Webhooks

Admission webhooks can block restore because restored objects are admitted through the Kubernetes API server.

Check webhooks:

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
```

Look in restore logs:

```bash
velero restore logs <restore-name> | grep -i webhook
```

Common errors:

```text
failed calling webhook
connection refused
service not found
context deadline exceeded
x509 certificate signed by unknown authority
```

Check webhook services:

```bash
oc get svc -A | grep -i webhook
oc get endpoints -A | grep -i webhook
oc get pods -A | grep -i webhook
```

Fix options:

- Bring the webhook backend pod/service up.
- Temporarily change `failurePolicy: Ignore` only after risk review.
- Exclude webhook configurations during restore.
- Restore operator/webhook dependencies first.

Example high-risk temporary patch:

```bash
oc patch validatingwebhookconfiguration <name> \
  --type='json' \
  -p='[{"op":"replace","path":"/webhooks/0/failurePolicy","value":"Ignore"}]'
```

Production warning:

> Do not casually disable admission webhooks in production. Document the risk, time-box the change, and revert after restore.

## 15. Check SCC and ServiceAccount Issues

OpenShift SCC can prevent restored pods from starting even when restore phase is partially successful.

Check pods:

```bash
oc get pods -n <namespace>
oc describe pod -n <namespace> <pod-name>
```

Look for:

```text
Error creating: pods forbidden: unable to validate against any security context constraint
container has runAsNonRoot and image will run as root
privileged containers are not allowed
hostPath volumes are not allowed
```

Check service accounts:

```bash
oc get sa -n <namespace>
oc get rolebinding -n <namespace>
oc get clusterrolebinding | grep <serviceaccount>
```

Check SCC assignment:

```bash
oc adm policy who-can use scc anyuid
oc adm policy who-can use scc privileged
```

Fix example:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

For privileged workloads:

```bash
oc adm policy add-scc-to-user privileged -z <serviceaccount> -n <namespace>
```

Production advice:

- Prefer least privilege SCC.
- Do not assign `privileged` unless required.
- Compare SCC assignments from source cluster.

## 16. Check RBAC Restore Issues

Restore may fail if Velero lacks permission to create certain resources.

Check Velero service account:

```bash
oc get sa -n openshift-adp
oc describe sa velero -n openshift-adp
oc get clusterrolebinding | grep -i velero
```

Can Velero create resources?

```bash
oc auth can-i create deployments --as=system:serviceaccount:openshift-adp:velero -n <namespace>
oc auth can-i create persistentvolumeclaims --as=system:serviceaccount:openshift-adp:velero -n <namespace>
oc auth can-i create routes.route.openshift.io --as=system:serviceaccount:openshift-adp:velero -n <namespace>
oc auth can-i create securitycontextconstraints.security.openshift.io --as=system:serviceaccount:openshift-adp:velero
```

Look for errors:

```bash
velero restore logs <restore-name> | grep -i forbidden
```

Example:

```text
User "system:serviceaccount:openshift-adp:velero" cannot create resource "routes" in API group "route.openshift.io"
```

Fix:

- Validate OADP operator installed correctly.
- Reconcile DPA.
- Check ClusterRole/ClusterRoleBinding for Velero.
- Avoid manually reducing Velero permissions unless you fully understand restore impact.

## 17. Check ResourceQuota and LimitRange

Restored pods/PVCs can fail if target namespace quota blocks object creation.

```bash
oc get quota -n <namespace>
oc describe quota -n <namespace>
oc get limitrange -n <namespace>
oc describe limitrange -n <namespace>
```

Common errors:

```text
exceeded quota
must specify limits.cpu
must specify requests.memory
persistentvolumeclaims is forbidden: exceeded quota
```

Fix:

- Temporarily adjust quota.
- Restore to clean namespace with correct quota.
- Restore objects first, then apply production quota.

## 18. Check Image Restore and ImageStream Issues

OADP can back up internal images depending on configuration and plugin support. Restore can fail or apps can fail to start if image references are unavailable.

Check pods:

```bash
oc get pods -n <namespace>
oc describe pod -n <namespace> <pod-name>
```

Look for:

```text
ImagePullBackOff
ErrImagePull
unauthorized: authentication required
manifest unknown
```

Check image streams:

```bash
oc get imagestream -n <namespace>
oc describe imagestream -n <namespace> <imagestream-name>
```

Check pull secrets:

```bash
oc get secret -n <namespace>
oc get sa default -n <namespace> -o yaml
oc get sa <serviceaccount> -n <namespace> -o yaml
```

Fix:

- Restore image pull secrets.
- Re-link pull secret to service account.
- Import image stream.
- Mirror image to target registry.
- Use ImageContentSourcePolicy / ImageDigestMirrorSet / ImageTagMirrorSet if disconnected.

Example:

```bash
oc secrets link default <pull-secret-name> --for=pull -n <namespace>
oc import-image <imagestream>:<tag> -n <namespace> --confirm
```

## 19. Check Routes, Services, and DNS

Restore might complete partially, but the application is unreachable.

```bash
oc get route,svc,endpoints -n <namespace>
oc describe route -n <namespace> <route-name>
oc get ingresscontroller -n openshift-ingress-operator
oc get pods -n openshift-ingress
```

Common route restore issues:

- Host already claimed by another route
- TLS secret missing
- Service selector mismatch
- Pods not ready
- NetworkPolicy blocks traffic
- IngressController unavailable

Check route admission:

```bash
oc get route <route-name> -n <namespace> -o yaml
```

Look for:

```yaml
status:
  ingress:
  - conditions:
    - type: Admitted
      status: "True"
```

If `Admitted=False`, describe route.

## 20. Check NetworkPolicies

Restore can bring back NetworkPolicies before dependencies are ready, causing app communication problems.

```bash
oc get networkpolicy -n <namespace>
oc describe networkpolicy -n <namespace> <policy-name>
```

Check pod connectivity:

```bash
oc rsh -n <namespace> <pod-name>
curl -v http://<service>:<port>
nslookup <service>
```

Common issues:

- DNS egress blocked
- App-to-database traffic blocked
- Namespace selector changed
- Pod labels not restored as expected
- Default deny policy restored before allow policies

## 21. Check Restore Hooks

Restore hooks can fail and mark restore as failed or partially failed.

Check restore details:

```bash
velero restore describe <restore-name> --details
velero restore logs <restore-name> | grep -i hook
```

Common hook issues:

- Container name mismatch
- Command not found
- Permission denied
- Application pod not running
- Timeout
- Hook runs before dependency is ready

Example errors:

```text
restore hook failed
container not found
command terminated with exit code 1
```

Fix:

- Correct hook command.
- Increase timeout.
- Remove hook and run manual post-restore steps.
- Restore dependencies first.

## 22. Check DeploymentConfig-Specific Behavior

OpenShift `DeploymentConfig` workloads may require additional cleanup after restore, especially with volumes and restore hooks.

Check DCs:

```bash
oc get dc -n <namespace>
oc describe dc -n <namespace> <dc-name>
oc get pods -n <namespace> --show-labels
```

Common issues:

- DC scaled down during restore
- Standalone restored pods remain
- Post-restore hook pod not removed
- DC controller creates replacement pods

Fix:

```bash
oc scale dc/<dc-name> --replicas=0 -n <namespace>
oc delete pod <standalone-restored-pod> -n <namespace>
oc scale dc/<dc-name> --replicas=<desired> -n <namespace>
```

## 23. Check Cluster-Scoped Resources

Some resources are cluster-scoped and can create restore conflicts.

Examples:

- ClusterRole
- ClusterRoleBinding
- CRD
- SCC
- PV
- StorageClass
- Namespace
- Webhook configurations
- APIService

Check restore logs:

```bash
velero restore logs <restore-name> | egrep -i "clusterrole|clusterrolebinding|crd|scc|storageclass|namespace|already exists|forbidden"
```

Best practice:

- Restore application namespaced resources first.
- Recreate cluster-scoped platform resources through GitOps or platform automation.
- Avoid restoring entire cluster state with OADP. OADP is designed primarily for application-level protection, not etcd/platform disaster recovery.

```bash

oc get pvc -n <namespace>
```

```text

Failed
Terminating
```

## 26. Check Scheduling and Node-Level Problems

Restored pods may remain Pending.

```bash
oc get pods -n <namespace> -o wide
oc describe pod -n <namespace> <pod-name>
oc get nodes
oc describe node <node-name>
```

Common scheduling causes:

- Node selector points to missing node label
- Taints not tolerated
- Requested CPU/memory unavailable
- PVC uses WaitForFirstConsumer and cannot bind
- Topology constraints cannot be satisfied
- Zone/region mismatch
- Local PV node affinity mismatch

Check node selectors:

```bash
oc get ns <namespace> -o yaml | grep -i node-selector -A3
oc get deploy <deploy-name> -n <namespace> -o yaml | grep -i nodeSelector -A5
```

Check topology:

OADP restores Kubernetes objects and data, but application correctness depends on runtime dependencies.

Check:

- Database restored before app starts
- Secrets restored correctly
- ConfigMaps restored correctly
- External endpoints still valid
- Certificates not expired
- Service DNS names unchanged
- Route hostnames valid
- OAuth/client secrets valid
- Database users/passwords match restored data
- Message queues restored consistently

Commands:

## 28. Troubleshooting by Error Pattern

### Error: Backup not found

Check:

```bash
velero backup get
oc get backup -n openshift-adp
oc get bsl -n openshift-adp
```

Likely causes:

- Backup expired due to TTL
- Object deleted from bucket
- Wrong bucket/prefix
- Wrong credentials
- Restore cluster points to different BSL

Fix:

- Correct BSL config.
- Re-sync backup location.
- Confirm object exists in bucket.

---

### Error: Restore failed with `forbidden`

Check:

```bash
velero restore logs <restore-name> | grep -i forbidden
oc auth can-i create <resource> --as=system:serviceaccount:openshift-adp:velero -n <namespace>
```

Likely causes:

- Velero RBAC missing
- OADP install incomplete
- Restricted cluster policy
- SCC denied pod creation

Fix:

- Repair OADP operator/DPA.
- Restore Velero ClusterRoleBinding.
- Assign required SCC to application service account, not blindly to all accounts.

---

### Error: `no matches for kind`

Check:

```bash
velero restore logs <restore-name> | grep -i "no matches for kind"
oc get crd | grep -i <kind-or-group>
```

Likely causes:

- CRD missing
- Operator not installed
- API version mismatch

Fix:

- Install operator/CRD first.
- Retry restore.

---

### Error: PVC stuck Pending

Check:

```bash
oc describe pvc -n <namespace> <pvc-name>
oc get sc
oc get volumesnapshotclass
oc get events -n <namespace> --sort-by='.lastTimestamp'
```

Likely causes:

- StorageClass missing
- CSI driver missing
- Snapshot restore unsupported
- WaitForFirstConsumer scheduling issue
- Access mode unsupported
- Capacity mismatch

Fix:

- Prepare StorageClass and CSI driver.
- Restore to compatible storage backend.
- Adjust restore strategy.

---

### Error: Webhook blocked restore

Check:

```bash
velero restore logs <restore-name> | grep -i webhook
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
```

Likely causes:

- Webhook service missing
- Webhook certificate expired
- Operator not running
- failurePolicy Fail blocks API request

Fix:

- Restore/install webhook backend first.
- Temporarily set failurePolicy Ignore if approved.
- Exclude problematic webhook configs.

---

### Error: Pods restored but app not running

Check:

```bash
oc get pods -n <namespace>
oc describe pod -n <namespace> <pod-name>
oc logs -n <namespace> <pod-name>
```

Likely causes:

- ImagePullBackOff
- Secret missing
- SCC denied
- ConfigMap missing
- PVC not mounted
- App dependency unavailable

Fix:

- Fix pod-level issue first.
- Validate app config and dependencies.

```bash

  --from-backup app-backup \
```


Restore only config objects:

```bash
  --from-backup app-backup \
```

```bash
  --from-backup app-backup \
```

Restore without PVs:

```bash
velero restore create restore-no-pv \
  --from-backup app-backup \
```


## 33. Enterprise-Level Root Cause Categories

| Category | Example Failure | Validation Command | Fix |
|---|---|---|---|
| Backup artifact | Backup missing/expired | `velero backup get` | Correct BSL / recover backup |
| Object storage | Cannot read S3 | `oc describe bsl` | Fix credentials, endpoint, CA, network |
| Restore CR | Wrong scope | `oc get restore -o yaml` | Correct restore spec |
| CRD/API | `no matches for kind` | `oc get crd` | Install operator/CRD first |
| PVC | Pending PVC | `oc describe pvc` | Fix SC/CSI/snapshot |
| Snapshot | Snapshot class missing | `oc get volumesnapshotclass` | Create correct class |
| Filesystem backup | Kopia/Restic fail | `oc get podvolumerestores` | Fix node-agent/repo/object storage |
| Webhook | Admission blocked | `oc get validatingwebhookconfiguration` | Fix webhook backend/cert |
| SCC | Pod forbidden | `oc describe pod` | Assign correct SCC |
| RBAC | Velero forbidden | `oc auth can-i` | Repair ClusterRoleBinding |
| Quota | Exceeded quota | `oc describe quota` | Adjust quota |
| Existing resources | Already exists | restore logs | Restore to clean namespace |
| App dependency | Pod CrashLoop | `oc logs` | Fix app config/data/secrets |

## 34. Production Best Practices

### 1. Always test restore, not only backup

A backup strategy is incomplete until restore is tested.

Recommended schedule:

- Daily backup status check
- Weekly namespace restore test
- Monthly DR restore test
- Quarterly full application recovery exercise

### 2. Use GitOps with OADP

Best enterprise model:

- GitOps restores application manifests.
- OADP restores persistent data and selected runtime objects.
- Operators are installed before restoring custom resources.

### 3. Restore in dependency order

Recommended order:

1. Operators and CRDs
2. Namespaces
3. ServiceAccounts, RBAC, SCC bindings
4. Secrets and ConfigMaps
5. PVCs and data
6. Services
7. Workloads
8. Routes/Ingress
9. NetworkPolicies
10. Application validation

### 4. Avoid restoring unnecessary cluster-scoped resources

Do not restore cluster platform state blindly.

Avoid unless required:

- Nodes
- Events
- Operator namespaces
- ClusterOperators
- MachineConfigPools
- Core platform objects
- etcd content through OADP

### 5. Keep source and target storage compatible

Before restore, confirm:

- Same or compatible StorageClass
- Same CSI driver or supported migration path
- Snapshot restore support
- Correct VolumeSnapshotClass
- Object storage access
- Region/zone compatibility

### 6. Capture evidence before retry

Before deleting or retrying:

```bash
velero restore describe <restore-name> --details > restore-describe.txt
velero restore logs <restore-name> > restore-logs.txt
oc get restore <restore-name> -n openshift-adp -o yaml > restore.yaml
oc get events -A --sort-by='.lastTimestamp' > events.txt
```

## 36. Example Interview Answer

If I had to answer this in an interview, I would say:

> First, I will verify the restore phase using `oc get restore -n openshift-adp` and `velero restore describe --details`. Then I will check `velero restore logs` to identify whether the failure is related to API resources, storage, PVC restore, webhooks, RBAC, SCC, or application hooks.  
>
> Since the backup completed, I will still validate the backup contents using `velero backup describe --details` because the backup may have completed with warnings or may not include required namespaces, PVCs, CRDs, or labels.  
>
> Next, I will check OADP component health: DPA status, Velero deployment, node-agent daemonset, BackupStorageLocation, and VolumeSnapshotLocation. If BSL is unavailable, restore cannot read backup objects. If CSI snapshot or filesystem backup is involved, I will check VolumeSnapshotClass, CSI driver, PodVolumeRestore, DataDownload, and PVC events.  
>
> If restore logs show `no matches for kind`, I will install the missing operator or CRD before retrying. If logs show webhook errors, I will verify webhook backend services and certificates. If logs show forbidden errors, I will check Velero RBAC and application SCC. If PVCs are Pending, I will check StorageClass, snapshot class, volume binding mode, topology, and capacity mismatch.  
>
> I prefer restoring first into a clean temporary namespace using namespace mapping. Once I validate pods, PVCs, routes, services, and application data, I plan the production cutover. I also collect restore logs, Velero logs, DPA YAML, BSL/VSL YAML, PVC events, and must-gather if escalation is required.

## 38. Final Senior-Level Summary

When OADP backup is completed but restore fails, I troubleshoot from the restore CR outward:

1. Read restore phase, details, and logs.
2. Validate backup contents and warnings.
3. Confirm OADP/DPA/Velero/node-agent health.
4. Validate BSL and object storage access.
5. Validate VSL, CSI snapshots, StorageClass, and PVC binding.
6. Check filesystem backup restore objects such as PodVolumeRestore and DataDownload.
7. Check CRDs, operators, API versions, and cluster-scoped dependencies.
8. Check admission webhooks, SCC, RBAC, quotas, and existing resource conflicts.
9. Validate restored application pods, routes, services, secrets, and logs.
10. Retry restore only after fixing the actual dependency.

The professional approach is not to rerun restore blindly. I isolate the failed restore layer, fix the missing prerequisite, restore into a clean namespace when possible, and validate application functionality before production cutover.
