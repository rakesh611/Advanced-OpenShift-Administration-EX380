# Node is NotReady after MachineConfig Change — Interview-Level Recovery Scenario for Advanced OpenShift Administration

## Scenario

You are working as a senior OpenShift administrator in a production OpenShift 4.x cluster. A new `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig`, `ImageDigestMirrorSet`, kernel argument change, CRI-O change, systemd drop-in, NetworkManager change, or registry configuration change was recently applied. After the Machine Config Operator started rolling out the rendered configuration, one or more nodes moved to:

```bash
NotReady
NotReady,SchedulingDisabled
Ready,SchedulingDisabled
```

The related MachineConfigPool may show:

```bash
UPDATED   UPDATING   DEGRADED
False     True       True
```

or:

```bash
MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
3              2                   2                     1
```

The interviewer asks:

> Node is NotReady after MachineConfig change. How will you recover?

As a 10-year experienced OpenShift administrator, the correct answer is not simply "reboot the node." You must protect workload availability, understand MCO behavior, isolate the broken change, recover node access, roll back safely, and verify cluster health.

---

## 1. Senior-Level Short Answer

If a node becomes `NotReady` after a MachineConfig change, I first stop further damage by pausing the affected MachineConfigPool or reducing rollout impact, then identify whether the issue is node health, kubelet, CRI-O, network, filesystem, certificate, OS boot, or MCO configuration drift. I check the MCP, rendered config, MCD logs, node events, kubelet logs, CRI-O logs, and recent MachineConfig changes. If the node is reachable, I use `oc debug node/<node>` and `chroot /host` or SSH/core access to repair the OS-level issue. If the MachineConfig itself is bad, I remove or correct the offending MachineConfig and let MCO generate a new rendered config. If the node cannot recover, I replace it through Machine API or bare-metal recovery, depending on platform. For control-plane nodes, I proceed very carefully because etcd quorum and API availability are at risk.

---

## 2. What Happens Internally When MachineConfig Changes

The Machine Config Operator manages operating-system-level configuration for OpenShift nodes. It can apply changes such as:

- Kubelet configuration
- CRI-O configuration
- Systemd units
- Kernel arguments
- Registries configuration
- Files under supported paths such as `/etc` and `/var`
- SSH key changes for the `core` user
- RHCOS OS updates
- NetworkManager-related configuration

When a new MachineConfig is applied:

1. The Machine Config Controller renders a new `rendered-<pool>-xxxxx` config.
2. The affected MachineConfigPool starts updating.
3. The Machine Config Daemon on each node detects the desired config.
4. The node is cordoned.
5. Workloads are drained where applicable.
6. The config is applied.
7. The node may reboot.
8. Kubelet, CRI-O, networking, and node services come back.
9. The node reports Ready.
10. MCO marks the node updated.

If the change breaks kubelet, CRI-O, networking, boot, DNS, certificates, SELinux labels, systemd, kernel args, or the node's ability to contact the API server, the node can remain `NotReady`.

## 3. Typical Causes of NotReady After MachineConfig

### 3.1 Bad KubeletConfig

Examples:

- Invalid kubelet setting
- Wrong `systemReserved`
- Wrong `kubeReserved`
- Invalid eviction thresholds
- CPU/memory reservations too aggressive
- Unsupported kubelet field
- Bad TLS/security profile

Impact:

```bash
systemctl status kubelet
journalctl -u kubelet
```

may show kubelet failing to start or unable to register the node.

---

### 3.2 Bad CRI-O or ContainerRuntimeConfig

Examples:

- Invalid registries configuration
- Bad runtime configuration
- Broken proxy/no_proxy settings
- Incorrect pause image or mirror
- Invalid insecure registry configuration
- Wrong container runtime drop-in

Impact:

```bash
systemctl status crio
journalctl -u crio
crictl info
```

may show CRI-O down. If CRI-O is down, kubelet cannot run pods correctly and node readiness may fail.

---

### 3.3 NetworkManager or Host Network Misconfiguration

Examples:

- Bad DNS
- Wrong default route
- Broken interface configuration
- Bad MTU
- Invalid bond/VLAN config
- Wrong static IP
- Incorrect proxy or no_proxy values
- Broken API server connectivity

Impact:

```bash
ping <api-vip>
curl -k https://api.<cluster-domain>:6443/readyz
nmcli con show
ip route
resolvectl status
```

The node may boot but cannot reach the API server.

---

### 3.4 Kernel Argument Breakage

Examples:

- Invalid kernel argument
- Wrong hugepage configuration
- Boot parameter incompatible with hardware
- FIPS-related mismatch
- Real-time kernel misuse
- Driver/module conflict

Impact:

The node may fail to boot, boot slowly, or kubelet may fail after boot.

---

### 3.5 Bad Systemd Unit or Drop-In

Examples:

- Invalid unit syntax
- Drop-in changes kubelet service incorrectly
- Dependency loop
- Service start failure
- Wrong permissions

Impact:

```bash
systemctl --failed
systemctl status kubelet crio NetworkManager
journalctl -xb
```

---

### 3.6 Configuration Drift

If a file managed by MachineConfig is manually changed on the node, the Machine Config Daemon detects drift. The node or pool may become degraded. A degraded node can still be online, but MCO will not continue updates until the drift is fixed.

Common examples:

- Manual edit to `/etc/kubernetes/kubelet.conf`
- Manual edit to `/etc/containers/registries.conf`
- Manual edit to a systemd drop-in delivered by MCO
- Manual permission change on a managed file
- Manually modified file content no longer matches expected rendered config

---

### 3.7 Drain Failure or PDB Blocking

Sometimes the MachineConfig change itself is not bad. The rollout gets stuck because the node cannot drain.

Common causes:

- PodDisruptionBudget blocks eviction
- Static pods
- DaemonSets
- Local storage pods
- Pods with finalizers
- Long termination grace period
- Stateful workload without available replicas

In this case the node may show `SchedulingDisabled`, and MCP may show `UPDATING=True`.

---

### 3.8 Disk Pressure or Filesystem Issue

MachineConfig application may fail if the node has:

- Full root filesystem
- Full `/var`
- Read-only filesystem
- Overlay storage issue
- Corrupted ostree deployment
- Failed rpm-ostree transaction

Check:

```bash
df -h
df -ih
ostree admin status
rpm-ostree status
journalctl -u machine-config-daemon
```

## 4. First Rule: Stop Further Damage

If one node is already down after a new MachineConfig, do not allow the change to continue rolling across the entire pool until you understand the failure.

### Check MCP Status

```bash
oc get mcp
oc describe mcp worker
oc describe mcp master
```

Expected problematic output:

```bash
Name:         worker
Updated:      False
Updating:     True
Degraded:     True
Message:      Node worker-1 is reporting: "unexpected on-disk state validating against rendered-worker-xxxxx"
```

### Pause the Affected Pool

For worker pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

For master pool:

```bash
oc patch mcp master --type=merge -p '{"spec":{"paused":true}}'
```

Important:

- Pausing prevents further MachineConfig application.
- It does not automatically fix already broken nodes.
- Use it to contain blast radius.
- Be very careful pausing the `master` pool for long periods because upgrades and config reconciliation may remain pending.

## 11. Recovery Decision Tree

## Case A: Node is NotReady Because Kubelet Is Down

### Symptoms

```bash
systemctl status kubelet
```

shows failed.

Logs may show:

```text
failed to run Kubelet
invalid configuration
failed to load Kubelet config file
unknown field
failed to start ContainerManager
```

### Recovery

1. Identify the bad `KubeletConfig`.

```bash
oc get kubeletconfig
oc describe kubeletconfig <name>
```

2. Correct or delete the bad object.

```bash
oc edit kubeletconfig <name>
```

or:

```bash
oc delete kubeletconfig <name>
```

3. Wait for new rendered config.

```bash
oc get mcp worker -w
```

4. If node is stuck and kubelet cannot recover, use console/debug to inspect generated kubelet config.

```bash
cat /etc/kubernetes/kubelet.conf
ls -l /etc/kubernetes/kubelet.conf
journalctl -u kubelet -b
```

5. Restart kubelet only after fixing root cause.

```bash
systemctl restart kubelet
systemctl status kubelet
```

### Interview Point

Do not directly edit kubelet config permanently on the node unless it is an emergency temporary repair. The real fix must be in the OpenShift API object that generated the MachineConfig.

---

## Case B: Node is NotReady Because CRI-O Is Down

### Symptoms

```bash
systemctl status crio
journalctl -u crio -b
```

Errors may include:

```text
error parsing registries.conf
invalid TOML
failed to load runtime config
container runtime is down
```

### Recovery

1. Check recent `ContainerRuntimeConfig`, mirror, or registry changes.

```bash
oc get containerruntimeconfig
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get imagecontentsourcepolicy
```

2. Validate `/etc/containers/registries.conf` on the node.

```bash
cat /etc/containers/registries.conf
```

3. Fix or remove the bad object.

```bash
oc edit containerruntimeconfig <name>
```

or:

```bash
oc delete containerruntimeconfig <name>
```

4. Restart CRI-O after fixing the file/config.

```bash
systemctl restart crio
systemctl status crio
```

5. Restart kubelet if needed.

```bash
systemctl restart kubelet
```

6. Watch node readiness.

```bash
oc get node <node-name> -w
```

---

## Case C: Node is NotReady Because Network Is Broken

### Symptoms

- Node boots but cannot reach API.
- Kubelet logs show node lease update failures.
- DNS lookup fails.
- API VIP unreachable.
- NetworkUnavailable condition is True.

### Checks

```bash
ip addr
ip route
nmcli con show
nmcli dev status
cat /etc/resolv.conf
curl -k https://api.<cluster-domain>:6443/readyz
journalctl -u NetworkManager -b
```

### Recovery

1. Identify whether MachineConfig modified network files.
2. Revert or correct the bad MachineConfig.
3. If the node cannot contact API, use console to restore networking manually enough for MCO to reconcile.

Example temporary recovery:

```bash
nmcli con reload
nmcli con up <connection-name>
ip route add default via <gateway>
echo "nameserver <dns-ip>" > /etc/resolv.conf
```

4. Once API connectivity returns, allow MCO to apply the corrected config.

### Interview Point

A network-related MachineConfig can isolate the node from the API server. In that case, cluster-side changes alone may not fix the node because the node cannot receive them. You may need out-of-band console access.

---

## Case D: Node is Degraded Because of Configuration Drift

### Symptoms

MCP message:

```text
unexpected on-disk state validating against rendered-worker-xxxxx
content mismatch for file "/etc/..."
```

Node annotation:

```bash
machineconfiguration.openshift.io/state=Degraded
machineconfiguration.openshift.io/reason=content mismatch for file ...
```

### Recovery

1. Identify the mismatched file from MCD logs or node annotation.

```bash
oc get node <node-name> -o yaml | grep -A5 machineconfiguration
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

2. Check whether the mismatch was caused by manual editing or another operator.

3. Restore file content, permissions, ownership, or SELinux context to match the rendered config.

4. If the MachineConfig is wrong, fix the MachineConfig instead of forcing the node.

5. Restart MCD or reboot only if needed.

```bash
systemctl restart machine-config-daemon
```

or:

```bash
reboot
```

### Important

Do not blindly delete files from the node. A managed file mismatch may indicate a real configuration problem. Understand the expected content first.

---

## Case E: Node is Stuck During Drain

### Symptoms

MCP is updating but not degraded. Node is:

```bash
Ready,SchedulingDisabled
```

MCD logs show drain failure.

### Checks

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data --dry-run=server
oc get pdb -A
oc get pods -A -o wide | grep <node-name>
```

### Recovery

1. Identify the pod blocking drain.
2. Check PDB.

```bash
oc get pdb -A
oc describe pdb -n <namespace> <pdb-name>
```

3. Scale workload safely or temporarily adjust PDB.

```bash
oc scale deploy/<name> -n <namespace> --replicas=<n>
```

4. Do not force delete production stateful pods unless approved and data safety is understood.

5. Once drain can complete, unpause MCP if it was paused.

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

---

## Case F: Node Cannot Boot After Kernel Argument or OS Change

### Symptoms

- Node missing from API
- Console shows boot failure
- Kernel panic
- Emergency mode
- Boot loop

### Recovery

1. Use console/iDRAC/iLO/cloud serial console.
2. Select previous OSTree deployment from bootloader if available.
3. Boot into previous working deployment.
4. Remove or correct bad MachineConfig from cluster.
5. Reboot node into corrected desired state.
6. If unrecoverable, replace the machine.

Useful commands from rescue/console:

```bash
rpm-ostree status
ostree admin status
journalctl -xb
```

### If Machine API Platform

For worker node replacement:

```bash
oc get machines -n openshift-machine-api
oc delete machine -n openshift-machine-api <machine-name>
```

The MachineSet should create a replacement machine.

### Bare Metal / UPI

You may need to:

- Reprovision node
- Reboot from live ISO/rescue
- Fix boot config
- Rejoin node
- Replace host manually
- Approve CSRs if needed

```bash
oc get csr
oc adm certificate approve <csr-name>
```

## Case G: Control Plane Node NotReady After MachineConfig

This is high-risk.

### First Check etcd Quorum

```bash
oc get nodes
oc get co etcd kube-apiserver authentication machine-config
oc -n openshift-etcd get pods -o wide
```

If API is available:

```bash
oc rsh -n openshift-etcd etcd-master-0
etcdctl endpoint health
etcdctl endpoint status -w table
```

Depending on OpenShift version and container environment, `etcdctl` may already have required environment variables in the etcd pod.

### Rules

- Do not reboot multiple control-plane nodes at once.
- Do not delete master machines casually.
- Maintain etcd quorum.
- Pause master MCP if needed.
- Recover one node at a time.
- If quorum is lost, follow official etcd disaster recovery procedure.

### Recovery

1. Pause master MCP.

```bash
oc patch mcp master --type=merge -p '{"spec":{"paused":true}}'
```

2. Identify the failed master.
3. Use console/SSH/debug.
4. Fix kubelet/CRI-O/network/boot issue.
5. Ensure static pods return:

```bash
crictl ps | grep -E 'kube-apiserver|etcd|kube-controller|kube-scheduler'
```

6. Confirm node Ready.
7. Unpause master MCP only when safe.

```bash
oc patch mcp master --type=merge -p '{"spec":{"paused":false}}'
```

## 12. How to Roll Back a Bad MachineConfig Safely

### Important Concept

You normally do not roll back by editing the rendered MachineConfig directly. Rendered MachineConfigs are generated by MCO. You roll back by removing or correcting the source MachineConfig, KubeletConfig, ContainerRuntimeConfig, or related API object.

### Step 1: Find Source Config

```bash
oc get mc
oc get kubeletconfig
oc get containerruntimeconfig
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get imagecontentsourcepolicy
```

### Step 2: Back Up the Bad Object

```bash
oc get mc <bad-mc> -o yaml > bad-mc-backup.yaml
```

or:

```bash
oc get kubeletconfig <bad-kc> -o yaml > bad-kubeletconfig-backup.yaml
```

### Step 3: Delete or Fix It

```bash
oc delete mc <bad-mc>
```

or:

```bash
oc edit mc <bad-mc>
```

For KubeletConfig:

```bash
oc delete kubeletconfig <bad-kc>
```

For ContainerRuntimeConfig:

```bash
oc delete containerruntimeconfig <bad-crc>
```

### Step 4: Wait for New Rendered Config

```bash
oc get mcp worker -w
```

### Step 5: Unpause Pool

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

### Step 6: Watch Rollout

```bash
oc get mcp
oc get nodes
oc get pods -n openshift-machine-config-operator -o wide
```

## 13. Forcing Node Annotation — Only as Last Resort

In some extreme break-glass situations, administrators may consider modifying node annotations to move a node back to a previous known rendered config. This is risky and should not be the normal approach.

Before considering annotation changes:

- Confirm with Red Hat support for production.
- Confirm the old rendered config exists.
- Confirm the node's on-disk state actually matches the config you are forcing.
- Understand that incorrect annotation manipulation can worsen drift or block future MCO updates.

Preferred approach:

1. Fix/delete the source bad MachineConfig.
2. Let MCO render a corrected config.
3. Recover the node service/network.
4. Let MCD reconcile normally.

## 15. Example Interview Scenario 1: Bad Registries Config Breaks CRI-O

### Problem

A new ImageDigestMirrorSet or MachineConfig changed registry settings. After reboot, one worker is `NotReady`.

### Investigation

```bash
oc get nodes
oc get mcp
oc describe mcp worker
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Node logs:

```bash
oc debug node/worker-1
chroot /host
systemctl status crio
journalctl -u crio -b
```

Error:

```text
error parsing /etc/containers/registries.conf
```

### Recovery

```bash
oc get imagedigestmirrorset
oc get imagecontentsourcepolicy
oc get containerruntimeconfig
```

Fix/delete bad object:

```bash
oc edit imagedigestmirrorset <name>
```

or:


## 19. What Not To Do

Avoid these mistakes:

```text
Do not reboot all nodes at once.
Do not unpause the pool before identifying the bad config.
Do not delete master machines casually.
Do not force delete production stateful pods without data impact analysis.
Do not manually edit MCO-managed files as a permanent fix.
Do not edit rendered MachineConfigs directly.
Do not ignore etcd quorum when master nodes are involved.
Do not assume NotReady means hardware failure.
Do not replace nodes before checking if a simple config rollback fixes the issue.
Do not continue cluster upgrade while MCO/MCP is degraded.
```

## 20. Production Change-Control Recovery Plan

For production, I would follow this structure:

### 20.1 Declare Incident

- Open incident bridge.
- Freeze further node-level changes.
- Identify affected pool and node count.
- Check workload impact.
- Notify application owners if workload disruption exists.

### 20.2 Contain

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":true}}'
```

### 20.3 Diagnose

- Check MCP
- Check MCO/MCD logs
- Check node annotations
- Check kubelet/CRI-O/network/systemd/disk
- Identify exact bad source object

### 20.4 Recover

- Fix or remove bad config
- Restore node services
- Replace node only if unrecoverable
- Recover one node at a time

### 20.5 Validate

```bash
oc get nodes
oc get mcp
oc get co
oc adm top nodes
oc get pods -A | grep -v Running | grep -v Completed
```

### 20.6 Prevent Recurrence

- Test MachineConfig in non-prod
- Use canary MachineConfigPool
- Keep `maxUnavailable` conservative
- Avoid direct node edits
- Validate generated config
- Use GitOps review for MachineConfig changes
- Document rollback steps before rollout

## 21. Canary Strategy for Future MachineConfig Changes

A senior administrator should not apply risky MachineConfig directly to all workers.

### Create a Canary Pool

Label one worker:

```bash
oc label node worker-1 node-role.kubernetes.io/worker-canary=
```

Create a custom MachineConfigPool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-canary
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - worker-canary
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-canary: ""
  maxUnavailable: 1
```

Target canary-specific MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-canary-test
  labels:
    machineconfiguration.openshift.io/role: worker-canary
spec:
  config:
    ignition:
      version: 3.4.0
```

Validate the change on one node before applying to the whole worker pool.

## 24. Sample Final Interview Answer

If a node becomes `NotReady` after a MachineConfig change, I treat it as a controlled production incident. First, I check `oc get nodes`, `oc get mcp`, and `oc describe co machine-config` to confirm whether the MachineConfigPool is updating or degraded. If the issue started after a new MachineConfig, I pause the affected pool using `oc patch mcp <pool> --type=merge -p '{"spec":{"paused":true}}'` so the broken change does not continue rolling to more nodes.

Then I inspect the failed node's MachineConfig annotations: `currentConfig`, `desiredConfig`, `state`, and `reason`. This tells me whether the node is applying a new rendered config, stuck between old and new config, or degraded because of drift. I check the MCD logs from `openshift-machine-config-operator` and then access the node using `oc debug node/<node>` with `chroot /host`, or via SSH/console if the node cannot run debug pods.

On the node I check `systemctl --failed`, `systemctl status kubelet crio NetworkManager`, `journalctl -u kubelet`, `journalctl -u crio`, network routes, DNS, disk space, and `rpm-ostree status`. Based on the failure, I identify whether the root cause is a bad KubeletConfig, CRI-O/registry change, NetworkManager change, kernel argument, systemd drop-in, disk issue, boot failure, or configuration drift.

If the MachineConfig is bad, I do not edit the rendered MachineConfig directly. I fix or delete the source object such as the custom MachineConfig, KubeletConfig, ContainerRuntimeConfig, or image mirror object. After the corrected rendered config is generated, I restore node services if needed, restart kubelet/CRI-O only when appropriate, or reboot the node one at a time. For a worker node that cannot be recovered, I replace it through Machine API or platform tooling. For a master node, I first protect etcd quorum and recover one control-plane node at a time.

Finally, I unpause the MCP, monitor `oc get mcp -w`, confirm all nodes return `Ready`, verify cluster operators are healthy, and check application pods. For prevention, I recommend testing MachineConfig changes on a canary MachineConfigPool, using GitOps review, keeping `maxUnavailable` conservative, and avoiding manual edits to MCO-managed files.
