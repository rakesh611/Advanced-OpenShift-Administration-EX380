# Argo CD Sync Failed Due to RBAC — Interview-Level Scenario for Advanced OpenShift Administration

## 1. Interview Question

**Question:**  
`Argo CD sync failed due to RBAC. How will you fix it?`

**Expected senior-level answer:**  
I will not blindly give cluster-admin to Argo CD. First, I will identify *which RBAC layer is denying the action*. In OpenShift GitOps / Argo CD, sync failure due to RBAC can happen at different layers:

1. **OpenShift/Kubernetes RBAC** — Argo CD application controller service account does not have permission to create, update, patch, delete, or watch the target resource.
2. **Argo CD internal RBAC** — the logged-in Argo CD user or group does not have permission to sync the application.
3. **Argo CD AppProject restriction** — the project does not allow the destination namespace, destination cluster, source repository, or resource kind.
4. **OpenShift security controls** — SCC, namespace ownership, cluster-scoped resource restrictions, operator-managed resources, or admission policy blocks the operation.

I will check the error message, identify the denied verb/resource/API group/namespace, verify the Argo CD controller service account permission using `oc auth can-i`, then fix the minimum required Role/ClusterRole and RoleBinding/ClusterRoleBinding. If the issue is Argo CD user RBAC or AppProject restriction, I will update `argocd-rbac-cm` or the `AppProject` policy accordingly. Finally, I will re-sync, validate events/logs, and commit the RBAC fix to Git so the solution remains GitOps-compliant.

---

## 2. Real Production Scenario

You are managing OpenShift GitOps in a production OpenShift cluster. A developer reports that an application is visible in Argo CD, but sync fails.

Example error in Argo CD UI:

```text
SyncFailed: one or more objects failed to apply
roles.rbac.authorization.k8s.io is forbidden:
User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller"
cannot create resource "roles" in API group "rbac.authorization.k8s.io" in the namespace "payments-dev"
```

Another possible error:

```text
permission denied: applications, sync, payments/payments-api, sub: rakesh, iat: ...
```

Another possible error:

```text
resource ServiceAccount is not permitted in project payments-project
```

These errors look similar to a junior engineer, but they are not the same problem. A senior OpenShift administrator must identify the exact RBAC boundary that failed.

## 3. Key Concept: Argo CD Has Two Different RBAC Worlds

### 3.1 OpenShift/Kubernetes RBAC

This controls what Argo CD can do inside the OpenShift cluster.

Example:

```text
Can Argo CD create Deployment in namespace payments-dev?
Can Argo CD patch Route in namespace payments-dev?
Can Argo CD create ClusterRole at cluster scope?
Can Argo CD manage SecurityContextConstraints?
```

This is controlled by:

```text
Role
ClusterRole
RoleBinding
ClusterRoleBinding
ServiceAccount
```

For OpenShift GitOps, the important service account is usually:

```text
system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Depending on your Argo CD instance name and namespace, the service account can be different, for example:

```text
system:serviceaccount:<argocd-namespace>:<argocd-instance>-argocd-application-controller
```

### 3.2 Argo CD Internal RBAC

This controls what a user can do inside Argo CD itself.

Example:

```text
Can user rakesh sync application payments-api?
Can group openshift-gitops-admins delete applications?
Can developer view logs?
Can team lead override sync?
```

This is controlled by Argo CD RBAC policy, commonly in:

```text
argocd-rbac-cm
```

or by the OpenShift GitOps Operator-managed ArgoCD custom resource.

### 3.3 AppProject Restrictions

Argo CD AppProject is another important control layer.

It can restrict:

```text
Allowed source repositories
Allowed destination clusters
Allowed destination namespaces
Allowed cluster-scoped resources
Allowed namespace-scoped resources
Denied resources
Project-level roles
```

Even when Kubernetes RBAC is correct, AppProject can still block sync.

---

## 4. First Rule in Production

Do **not** immediately run:

```bash
oc adm policy add-cluster-role-to-user cluster-admin \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

This may fix the issue temporarily, but it creates a serious security risk.

A senior administrator should follow least privilege:

```text
Give Argo CD only the permissions needed for that application, namespace, and resource type.
```

Cluster-admin should be used only for platform-level GitOps where Argo CD intentionally manages cluster configuration, and even then it should be approved, documented, and separated from application GitOps.

## Step 2: Read the Exact Error Message

This is the most important step.

### Error Type A: Kubernetes/OpenShift RBAC Denial

Example:

```text
User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller"
cannot create resource "roles" in API group "rbac.authorization.k8s.io"
in the namespace "payments-dev"
```

Meaning:

```text
The Argo CD application controller service account lacks Kubernetes/OpenShift RBAC permission.
```

### Error Type B: Argo CD Internal RBAC Denial

Example:

```text
permission denied: applications, sync, payments/payments-api
```

Meaning:

```text
The logged-in Argo CD user or group is not allowed to sync this application.
```

### Error Type C: AppProject Restriction

Example:

```text
application destination server/namespace is not permitted in project
```

Meaning:

```text
The AppProject does not allow this destination cluster or namespace.
```

### Error Type D: Resource Kind Not Allowed

Example:

```text
resource ClusterRole is not permitted in project
```

Meaning:

```text
AppProject blocks this resource kind, especially cluster-scoped resources.
```

## Step 5: Reproduce the Permission Check with `oc auth can-i`

This is the most important OpenShift command for RBAC troubleshooting.

Syntax:

```bash
oc auth can-i <verb> <resource> \
  --as=system:serviceaccount:<argocd-namespace>:<argocd-controller-sa> \
  -n <target-namespace>
```

Example error said Argo CD cannot create Role in `payments-dev`.

Check:

```bash
oc auth can-i create roles.rbac.authorization.k8s.io \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

Expected failing output:

```text
no
```

Check Deployment permission:

```bash
oc auth can-i create deployments.apps \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

Check Route permission:

```bash
oc auth can-i create routes.route.openshift.io \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

Check Service permission:

```bash
oc auth can-i create services \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

Check Secret permission:

```bash
oc auth can-i create secrets \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

For cluster-scoped resources:

```bash
oc auth can-i create clusterroles.rbac.authorization.k8s.io \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

No namespace is used for cluster-scoped resources.

## 6. Fix Pattern 1: Namespace-Scoped Application RBAC

If Argo CD manages normal application resources inside one namespace, create a Role and RoleBinding in the target namespace.

### Example: Application Needs Deployment, Service, Route, ConfigMap, Secret

Create file:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: argocd-app-deployer
  namespace: payments-dev
rules:
  - apiGroups: [""]
    resources:
      - services
      - configmaps
      - secrets
      - serviceaccounts
      - persistentvolumeclaims
    verbs:
      - get
      - list
      - watch
      - create
      - update
      - patch
      - delete
  - apiGroups: ["apps"]
    resources:
      - deployments
      - replicasets
      - statefulsets
      - daemonsets
    verbs:
      - get
      - list
      - watch
      - create
      - update
      - patch
      - delete
  - apiGroups: ["route.openshift.io"]
    resources:
      - routes
    verbs:
      - get
      - list
      - watch
      - create
      - update
      - patch
      - delete
  - apiGroups: ["networking.k8s.io"]
    resources:
      - ingresses
      - networkpolicies
    verbs:
      - get
      - list
      - watch
      - create
      - update
      - patch
      - delete
```

Create RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: argocd-app-deployer-binding
  namespace: payments-dev
subjects:
  - kind: ServiceAccount
    name: openshift-gitops-argocd-application-controller
    namespace: openshift-gitops
roleRef:
  kind: Role
  name: argocd-app-deployer
  apiGroup: rbac.authorization.k8s.io
```

Apply:

```bash
oc apply -f argocd-app-deployer-role.yaml
oc apply -f argocd-app-deployer-rolebinding.yaml
```

Validate:

```bash
oc auth can-i create deployments.apps \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

Expected:

```text
yes
```

```yaml
      - delete
```

```bash
oc auth can-i create roles.rbac.authorization.k8s.io \
```


## 8. Fix Pattern 3: Argo CD Needs to Manage OpenShift-Specific Resources

OpenShift applications commonly use resources that are not present in vanilla Kubernetes.

Examples:

```text
Route
BuildConfig
ImageStream
DeploymentConfig
Template
```

Add permissions as required.

```yaml
  - apiGroups: ["route.openshift.io"]
    resources:
      - routes
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

  - apiGroups: ["build.openshift.io"]
    resources:
      - buildconfigs
      - builds
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

  - apiGroups: ["image.openshift.io"]
    resources:
      - imagestreams
      - imagestreamtags
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

  - apiGroups: ["apps.openshift.io"]
    resources:
      - deploymentconfigs
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

  - apiGroups: ["template.openshift.io"]
    resources:
      - templates
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
```

Validate each required resource:

```bash
oc auth can-i create routes.route.openshift.io \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

## 9. Fix Pattern 4: Cluster-Scoped Resource Denied

If Argo CD sync fails on resources such as:

```text
Namespace
ClusterRole
ClusterRoleBinding
CustomResourceDefinition
SecurityContextConstraints
StorageClass
OperatorGroup
Subscription
```

then namespace Role is not enough.

These require ClusterRole and ClusterRoleBinding.

Example error:

```text
User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller"
cannot create resource "clusterroles" in API group "rbac.authorization.k8s.io" at the cluster scope
```

### Minimal ClusterRole Example for ClusterRole Management

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: argocd-cluster-rbac-manager
rules:
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources:
      - clusterroles
      - clusterrolebindings
    verbs:
      - get
      - list
      - watch
      - create
      - update
      - patch
      - delete
```

ClusterRoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: argocd-cluster-rbac-manager-binding
subjects:
  - kind: ServiceAccount
    name: openshift-gitops-argocd-application-controller
    namespace: openshift-gitops
roleRef:
  kind: ClusterRole
  name: argocd-cluster-rbac-manager
  apiGroup: rbac.authorization.k8s.io
```

Validate:

```bash
oc auth can-i create clusterroles.rbac.authorization.k8s.io \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Expected:

```text
yes
```

### Senior-Level Warning

Do not mix platform-level GitOps and application-level GitOps without governance.

Recommended design:

```text
Application Argo CD instance:
  - Manages app namespaces only
  - Uses namespace-scoped RBAC
  - Does not manage cluster-wide objects

Platform Argo CD instance:
  - Manages cluster configuration
  - Can manage selected cluster-scoped resources
  - Restricted to platform admin team
  - Strong audit and approval process
```

## 10. Fix Pattern 5: User Cannot Click Sync in Argo CD UI

If the error says:

```text
permission denied: applications, sync
```

this is usually Argo CD internal RBAC, not Kubernetes RBAC.

Check Argo CD RBAC ConfigMap:

```bash
oc get cm argocd-rbac-cm -n openshift-gitops -o yaml
```

Example policy:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: openshift-gitops
data:
  policy.default: role:readonly
  policy.csv: |
    p, role:dev-sync, applications, get, payments/*, allow
    p, role:dev-sync, applications, sync, payments/*, allow
    p, role:dev-sync, applications, action/*, payments/*, allow
    g, payments-dev-team, role:dev-sync
  scopes: '[groups]'
```

Explanation:

```text
p = permission policy
g = group or user mapping
role:dev-sync = custom Argo CD role
applications = Argo CD resource
sync = action
payments/* = project/application scope
allow = permission
```

If the application is in project `payments` and app name is `payments-api`, then:

```text
payments/payments-api
```

matches:

```text
payments/*
```

After updating RBAC ConfigMap, restart Argo CD server if required:

```bash
oc rollout restart deployment/openshift-gitops-server -n openshift-gitops
```

Validate by logging out and logging in again to Argo CD UI.

## 11. Fix Pattern 6: AppProject Blocks Sync

Check the AppProject:

```bash
oc get appproject -n openshift-gitops
oc get appproject payments -n openshift-gitops -o yaml
```

Example restricted AppProject:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://git.example.com/payments/*
  destinations:
    - namespace: payments-dev
      server: https://kubernetes.default.svc
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ""
      kind: Service
    - group: route.openshift.io
      kind: Route
```

If your Git repo includes ConfigMap, Secret, Role, or RoleBinding, but AppProject only allows Deployment, Service, and Route, sync can fail.

Fix by adding allowed resources:

```yaml
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ""
      kind: Service
    - group: ""
      kind: ConfigMap
    - group: ""
      kind: Secret
    - group: ""
      kind: ServiceAccount
    - group: route.openshift.io
      kind: Route
    - group: rbac.authorization.k8s.io
      kind: Role
    - group: rbac.authorization.k8s.io
      kind: RoleBinding
```

If cluster-scoped resource is needed:

```yaml
  clusterResourceWhitelist:
    - group: rbac.authorization.k8s.io
      kind: ClusterRole
    - group: rbac.authorization.k8s.io
      kind: ClusterRoleBinding
```

But use this carefully.

## 12. Fix Pattern 7: Namespace Destination Not Allowed

Error:

```text
application destination namespace payments-dev is not permitted in project payments
```

Check Application:

```bash
oc get application payments-api -n openshift-gitops -o yaml
```

Look at:

```yaml
spec:
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
  project: payments
```

Check AppProject destinations:

```bash
oc get appproject payments -n openshift-gitops -o yaml
```

Fix:

```yaml
spec:
  destinations:
    - namespace: payments-dev
      server: https://kubernetes.default.svc
```

For multiple namespaces:

```yaml
spec:
  destinations:
    - namespace: payments-dev
      server: https://kubernetes.default.svc
    - namespace: payments-test
      server: https://kubernetes.default.svc
    - namespace: payments-prod
      server: https://kubernetes.default.svc
```

Avoid broad wildcard unless required:

```yaml
namespace: '*'
```

Wildcard is easy, but risky in enterprise environments.

Error:

```text
repository not permitted in project
```

Check Application source:

```yaml
spec:
  source:
    repoURL: https://git.example.com/payments/payments-api.git
```

Check AppProject:

```yaml
spec:
  sourceRepos:
    - https://git.example.com/platform/*
```

Fix:

```yaml
spec:
  sourceRepos:
    - https://git.example.com/payments/*
```

or more strictly:

```yaml
spec:
  sourceRepos:
    - https://git.example.com/payments/payments-api.git
```

Senior-level recommendation:

```text
Use exact repository URLs for production projects where possible.
Use wildcard only for controlled group-level repositories.
```

## 14. Fix Pattern 9: Sync Fails Due to SCC or OpenShift Admission

Sometimes the message looks like RBAC, but the real issue is OpenShift SecurityContextConstraints.

Example:

```text
pods is forbidden: unable to validate against any security context constraint
```

This is not Argo CD RBAC. It means the application service account cannot run with the requested security context.

Check pod events:

```bash
oc get events -n payments-dev --sort-by=.lastTimestamp
```

Check service account:

```bash
oc get deploy payments-api -n payments-dev -o jsonpath='{.spec.template.spec.serviceAccountName}'
```

Check SCC access:

```bash
oc adm policy who-can use scc restricted-v2
```

Do not give privileged SCC blindly.

If required and approved:

```bash
oc adm policy add-scc-to-user nonroot-v2 \
  -z payments-api-sa \
  -n payments-dev
```

For privileged workloads, get security approval before using:

```bash
oc adm policy add-scc-to-user privileged \
  -z payments-api-sa \
  -n payments-dev
```

Senior answer:

```text
I separate Argo CD controller permission from workload runtime permission. Argo CD may have permission to create the Deployment, but the pod may still fail because the workload service account is not allowed by SCC.
```

## 15. Fix Pattern 10: Resource Already Exists But Owned by Another Manager

Sometimes Argo CD has permission, but sync fails due to ownership or immutable field issues.

Examples:

```text
resource already exists
field is immutable
managedFields conflict
cannot patch resource
```

Check resource owner:

```bash
oc get deployment payments-api -n payments-dev -o yaml
```

Look for:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/tracking-id:
```

Also check labels:

```yaml
app.kubernetes.io/instance:
```

Fix options:

```text
1. Import existing resource into Argo CD ownership.
2. Delete and recreate if downtime is acceptable.
3. Use replace sync option carefully.
4. Correct immutable fields in Git.
5. Avoid manually managing GitOps-owned resources.
```

Example sync option:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Replace=true
```

Use carefully because replace can delete and recreate resources.

## 17. Enterprise GitOps RBAC Design

For a 10-year experienced OpenShift administrator, the answer should include design maturity.

### Recommended Model

```text
openshift-gitops namespace
  Argo CD instance for application teams

team-a-dev namespace
team-a-test namespace
team-a-prod namespace

Argo CD controller gets namespace-level RoleBindings only for approved namespaces.
```

### Example Namespace-Level Binding

```bash
oc adm policy add-role-to-user edit \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-dev
```

This is quick but broad.

Better approach:

```text
Create custom Role with only required resources and verbs.
```

### Avoid This for Normal Application GitOps

```bash
oc adm policy add-cluster-role-to-user cluster-admin \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

### Better Separation

```text
Argo CD Instance 1: platform-gitops
  - Manages cluster operators, namespaces, quotas, policies
  - Controlled by platform team
  - Can have selected cluster-scoped permissions

Argo CD Instance 2: app-gitops
  - Manages application manifests only
  - Namespace-scoped permissions
  - Used by development teams
```

## 19. Common Root Causes and Fixes

| Symptom | Likely Cause | Fix |
|---|---|---|
| `cannot create deployments.apps` | Argo CD controller lacks namespace RBAC | Add Role/RoleBinding in target namespace |
| `cannot create routes.route.openshift.io` | Missing OpenShift Route permission | Add route.openshift.io permission |
| `cannot create roles.rbac.authorization.k8s.io` | Git contains Role/RoleBinding but Argo CD cannot manage RBAC | Add RBAC API group permission in namespace |
| `cannot create clusterroles` | Cluster-scoped RBAC missing | Add ClusterRole/ClusterRoleBinding only if approved |
| `permission denied: applications, sync` | Argo CD user lacks internal sync permission | Update `argocd-rbac-cm` or ArgoCD CR RBAC |
| `destination namespace not permitted` | AppProject destination restriction | Update AppProject destinations |
| `repository not permitted` | AppProject sourceRepos restriction | Update sourceRepos |
| `resource not permitted in project` | AppProject whitelist/blacklist issue | Update resource whitelist |
| `unable to validate against SCC` | Workload service account SCC issue | Fix SCC for workload SA, not Argo CD controller |
| `field is immutable` | Existing resource conflict | Correct Git manifest or replace resource carefully |

## 20. Interview Answer Structure

A strong interview answer should be structured like this:

```text
First, I will identify whether the RBAC failure is from Kubernetes/OpenShift RBAC, Argo CD internal RBAC, or AppProject restriction.

I will check the Application status and controller logs to find the exact forbidden verb, resource, API group, namespace, and identity.

If the error shows the Argo CD application-controller service account cannot create or patch a resource, I will validate using oc auth can-i with --as. Then I will create a least-privilege Role and RoleBinding in the target namespace, or ClusterRole/ClusterRoleBinding only for approved cluster-scoped resources.

If the error is permission denied while a user clicks Sync, I will check Argo CD internal RBAC in argocd-rbac-cm and map the correct user/group to a role that can sync that project/application.

If the error says destination, source repository, or resource is not permitted, I will fix the AppProject configuration.

After applying the fix, I will re-run oc auth can-i, re-sync the application, check events and Argo CD health, and commit the RBAC change to Git.

I will avoid giving cluster-admin unless this is a controlled platform GitOps instance with documented approval.
```

## 22. Production Best Practices

1. **Use least privilege**  
   Do not assign cluster-admin to application Argo CD.

2. **Separate platform GitOps and application GitOps**  
   Platform GitOps may need cluster-scoped permissions. Application GitOps should mostly be namespace-scoped.

3. **Use AppProjects for boundaries**  
   Restrict source repositories, destination namespaces, and allowed resource kinds.

4. **Keep RBAC in Git**  
   Do not manually patch production RBAC without committing it back to Git.

5. **Validate with `oc auth can-i` before re-sync**  
   This saves time and proves the permission is fixed.

6. **Audit who can sync production apps**  
   Argo CD internal RBAC should allow only approved users/groups to sync production.

7. **Avoid wildcard AppProject permissions in production**  
   Avoid `namespace: '*'`, `sourceRepos: ['*']`, or unrestricted resource whitelist unless justified.

8. **Review SCC separately**  
   Argo CD RBAC and workload runtime SCC are different problems.

9. **Use OpenShift groups**  
   Map enterprise LDAP/OIDC groups to Argo CD roles.

10. **Check logs and events**  
   Argo CD UI gives summary, but controller logs and OpenShift events provide root cause.

## 23. Senior-Level Summary

When Argo CD sync fails due to RBAC in OpenShift, I troubleshoot in layers. First, I check whether the denial is coming from Kubernetes/OpenShift RBAC, Argo CD internal RBAC, or AppProject restrictions. If the Argo CD application controller service account is denied by the Kubernetes API, I verify the exact permission using `oc auth can-i --as`. Then I create the minimum required Role/RoleBinding or ClusterRole/ClusterRoleBinding depending on whether the resource is namespace-scoped or cluster-scoped.

If the user is denied while clicking Sync in Argo CD, I fix Argo CD RBAC policy, not Kubernetes RBAC. If the AppProject blocks the destination, source repository, or resource kind, I update the AppProject. After the fix, I validate the permission, re-sync the app, check application health, and store the RBAC manifest in Git.

The most important production principle is least privilege. I should not give cluster-admin to Argo CD unless it is a dedicated platform GitOps instance with clear approval and governance.
