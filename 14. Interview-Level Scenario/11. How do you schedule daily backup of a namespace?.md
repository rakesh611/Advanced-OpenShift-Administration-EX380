# How Do You Schedule Daily Backup of a Namespace?

## Advanced OpenShift Administration — Interview-Level Scenario

**Scenario:**  
You are working as a senior OpenShift administrator in a production environment. A business-critical application runs in a namespace called `finance-prod`. The application has Kubernetes/OpenShift objects such as Deployments, Services, Routes, ConfigMaps, Secrets, ServiceAccounts, RoleBindings, PVCs, and application data stored on persistent volumes. The business asks you to schedule an automated daily backup of this namespace so that the application can be restored after accidental deletion, bad deployment, ransomware impact, storage failure, or disaster recovery testing.

As a 10-year experienced OpenShift administrator, I would not answer this only as “create a cron job.” In OpenShift, the enterprise-grade and supported approach is to use **OADP — OpenShift API for Data Protection**, which is based on **Velero**. OADP provides Backup, Restore, Schedule, BackupStorageLocation, and VolumeSnapshotLocation APIs. Red Hat documentation describes OADP as a way to protect applications, application-related cluster resources, persistent volumes, internal images, and VMs, but it is not a replacement for etcd disaster recovery or OpenShift Operator backup.  

References used for this guide: Red Hat OpenShift backup and restore documentation and Velero resource filtering documentation.  
- Red Hat OpenShift 4.19 Backup and Restore documentation: https://docs.redhat.com/en/documentation/openshift_container_platform/4.19/html-single/backup_and_restore/index  
- OKD/OADP Schedule CR documentation: https://docs.okd.io/latest/backup_and_restore/application_backup_and_restore/backing_up_and_restoring/oadp-scheduling-backups-doc.html  
- Velero resource filtering documentation: https://velero.io/docs/main/resource-filtering/

## 1. Interview Answer — Short Summary

To schedule a daily backup of a namespace in OpenShift, I would use **OADP Operator**, which installs and manages **Velero**. First, I would ensure that OADP is installed, the `DataProtectionApplication` is in `Ready` state, and object storage is configured through `BackupStorageLocation`. For persistent volumes, I would verify whether the storage class supports CSI snapshots or whether file-system backup is required. Then I would create a Velero/OADP `Schedule` custom resource that runs daily using a cron expression and includes only the target namespace. After creating the schedule, I would validate that backups are created daily, check Velero logs and backup status, test restore in a separate namespace or test cluster, and monitor backup health using alerts.

Example high-level flow:

```bash
oc get dpa -n openshift-adp
oc get backupstoragelocation -n openshift-adp
oc get volumesnapshotclass
oc apply -f finance-prod-daily-backup-schedule.yaml
oc get schedule -n openshift-adp
oc get backup -n openshift-adp
```

## 2. Why I Use OADP Instead of Manual YAML Export

A junior admin may say:

```bash
oc get all -n finance-prod -o yaml > backup.yaml
```

That is not sufficient for production backup.

Problems with manual export:

- It does not reliably capture all namespace-scoped resources.
- It may miss Secrets, ConfigMaps, PVCs, Routes, RoleBindings, ServiceAccounts, NetworkPolicies, custom resources, and operator-managed objects.
- It does not protect persistent volume data.
- It is not automated unless wrapped manually.
- It does not provide a proper restore workflow.
- It does not handle object storage, retention, backup expiration, labels, snapshots, restore mapping, or DR testing.
- It may include cluster-generated fields that create restore conflicts.

In enterprise OpenShift, I use OADP/Velero because it provides:

- Kubernetes-native Backup and Restore CRs.
- Scheduled backups.
- Namespace filtering.
- Resource filtering.
- Persistent volume backup support through CSI snapshots or file-system backup.
- Backup storage integration with S3-compatible object storage.
- Restore workflow with namespace mapping.
- Operational visibility through CR status and Velero logs.

## 3. Components Involved

### 3.1 OADP Operator

The OADP Operator is installed from OperatorHub. It manages the data protection components in OpenShift.

Typical namespace:

```bash
openshift-adp
```

Check operator pods:

```bash
oc get pods -n openshift-adp
```

Expected components may include:

```text
openshift-adp-controller-manager
velero
node-agent / restic / kopia related pods depending on version and configuration
```

---

### 3.2 DataProtectionApplication CR

The `DataProtectionApplication` resource defines the Velero/OADP configuration, plugins, backup locations, snapshot locations, and node-agent/file-system backup settings.

Check DPA:

```bash
oc get dpa -n openshift-adp
oc describe dpa <dpa-name> -n openshift-adp
```

Example:

```bash
oc get dpa -n openshift-adp
```

Expected:

```text
NAME              AGE
velero-sample     10d
```

Check status:

```bash
oc get dpa velero-sample -n openshift-adp -o yaml
```

Important condition:

```yaml
status:
  conditions:
  - type: Reconciled
    status: "True"
```

In many environments, documentation says the DPA should be in a ready/reconciled state before scheduling backups.

---

### 3.3 BackupStorageLocation

The `BackupStorageLocation` points Velero/OADP to object storage such as AWS S3, Azure Blob, Google Cloud Storage, NooBaa, Ceph RGW, MinIO, or another S3-compatible backend.

Check:

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation <bsl-name> -n openshift-adp
```

Expected phase:

```text
Available
```

If BSL is unavailable, scheduled backups may fail.

Common causes:

- Wrong bucket name.
- Wrong S3 endpoint.
- Invalid access key or secret key.
- TLS certificate issue.
- Network policy/firewall blocking object storage.
- Incorrect region.
- Object storage credentials secret missing.
- Proxy misconfiguration.

---

### 3.4 VolumeSnapshotLocation

If the namespace has PVCs and the storage platform supports CSI snapshots, I configure `VolumeSnapshotLocation` and ensure the correct `VolumeSnapshotClass` exists.

Check snapshot classes:

```bash
oc get volumesnapshotclass
```

Check volume snapshot CRDs:

```bash
oc get crd | grep snapshot
```

If CSI snapshots are not available, I use file-system backup through the OADP node agent, depending on the environment and OADP version.

## 5. Daily Namespace Backup Using Schedule CR

OADP/Velero supports a `Schedule` CR. This is the Kubernetes-native way to schedule recurring backups.

A daily backup can be scheduled using a cron expression:

```text
0 1 * * *
```

This means every day at 01:00.

> Important: The actual timezone handling depends on the Velero controller environment. In production, I always confirm the controller timezone and document the business backup window clearly. Many clusters run controllers in UTC, so 01:00 UTC may not equal 01:00 local time.

---

## 6. Example: Daily Backup of `finance-prod` Namespace

Create a file:

```bash
vi finance-prod-daily-backup-schedule.yaml
```

Content:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: finance-prod-daily-backup
  namespace: openshift-adp
  labels:
    app.kubernetes.io/name: finance-prod
    backup-type: daily
    managed-by: oadp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
    - finance-prod
    storageLocation: default
    ttl: 168h0m0s
```

Apply:

```bash
oc apply -f finance-prod-daily-backup-schedule.yaml
```

Verify:

```bash
oc get schedule -n openshift-adp
oc describe schedule finance-prod-daily-backup -n openshift-adp
```

Expected:

```text
NAME                         STATUS    SCHEDULE    LASTBACKUP
finance-prod-daily-backup    Enabled   0 1 * * *   <timestamp>
```

---

## 7. YAML Explanation

```yaml
apiVersion: velero.io/v1
kind: Schedule
```

This creates a Velero/OADP Schedule object.

```yaml
metadata:
  name: finance-prod-daily-backup
  namespace: openshift-adp
```

The schedule is created in the OADP namespace, commonly `openshift-adp`.

```yaml
spec:
  schedule: "0 1 * * *"
```

Runs daily at 01:00.

```yaml
template:
  includedNamespaces:
  - finance-prod
```

Only backs up the `finance-prod` namespace.

```yaml
storageLocation: default
```

Uses the configured BackupStorageLocation named `default`.

```yaml
ttl: 168h0m0s
```

Keeps each backup for 168 hours, which is 7 days.

For production, retention must match business and compliance requirements. Examples:

- Daily backup retention: 7 days.
- Weekly backup retention: 4 to 8 weeks.
- Monthly backup retention: 6 to 12 months.
- Compliance retention: as per organization policy.

## 8. Backup With Persistent Volume Snapshots

If the application uses PVCs and the storage supports CSI snapshots, I include snapshot configuration.

Example:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: finance-prod-daily-backup
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
    - finance-prod
    storageLocation: default
    snapshotVolumes: true
    ttl: 168h0m0s
```

Apply:

```bash
oc apply -f finance-prod-daily-backup-schedule.yaml
```

Check backup after scheduled run:

```bash
oc get backup -n openshift-adp
oc describe backup <backup-name> -n openshift-adp
```

Check snapshots:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

## 9. Backup With File-System Backup Instead of CSI Snapshot

If CSI snapshot support is unavailable, I may use file-system backup. In Velero/OADP, this is commonly handled by node-agent/Kopia or Restic depending on the version and configuration.

A common approach is to set file-system backup behavior through the DPA and annotate pods or use default file-system backup settings if configured.

Example pod annotation style used in Velero environments:

```bash
oc annotate pod <pod-name> -n finance-prod backup.velero.io/backup-volumes=<volume-name>
```

However, in production I avoid manual pod-only annotations where possible because pods are recreated. I prefer adding the annotation to the controller template, such as Deployment, StatefulSet, or DeploymentConfig.

Example Deployment patch:

```bash
oc patch deployment finance-api -n finance-prod --type merge -p '
{
  "spec": {
    "template": {
      "metadata": {
        "annotations": {
          "backup.velero.io/backup-volumes": "data"
        }
      }
    }
  }
}'
```

Then confirm new pods contain the annotation:

```bash
oc get pod -n finance-prod -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.annotations.backup\.velero\.io/backup-volumes}{"\n"}{end}'
```

Important interview point:

> For stateless applications, backing up Kubernetes objects may be enough. For stateful applications, I must protect PVC data using CSI snapshots or file-system backup. Otherwise, restore will recreate the application objects but not the actual application data.

## 10. Schedule With Resource Filtering

Sometimes I do not want to back up everything in the namespace. For example, I may exclude temporary pods, jobs, events, or specific resources.

Velero supports filtering by namespace, resource type, labels, and other selectors.

Example: include namespace and exclude events:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: finance-prod-daily-backup
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
    - finance-prod
    excludedResources:
    - events
    storageLocation: default
    snapshotVolumes: true
    ttl: 168h0m0s
```

Example: backup only resources with a label:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: finance-prod-daily-backup
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
    - finance-prod
    labelSelector:
      matchLabels:
        backup: required
    storageLocation: default
    snapshotVolumes: true
    ttl: 168h0m0s
```

Then label important resources:

```bash
oc label deployment finance-api -n finance-prod backup=required
oc label service finance-api -n finance-prod backup=required
oc label route finance-api -n finance-prod backup=required
```

In most production namespace-level backups, I start with the full namespace backup and use exclusions carefully. Over-filtering can create incomplete restores.

## 11. Creating an Immediate Backup From the Schedule

After creating a schedule, I do not wait until tomorrow to know whether it works. I create a manual backup from the schedule for validation.

Using Velero CLI if available:

```bash
velero backup create finance-prod-manual-test \
  --from-schedule finance-prod-daily-backup \
  -n openshift-adp
```

Using OpenShift CR directly:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: finance-prod-manual-test
  namespace: openshift-adp
spec:
  includedNamespaces:
  - finance-prod
  storageLocation: default
  snapshotVolumes: true
  ttl: 168h0m0s
```

Apply:

```bash
oc apply -f finance-prod-manual-test-backup.yaml
```

Check:

```bash
oc get backup -n openshift-adp
oc describe backup finance-prod-manual-test -n openshift-adp
```

Expected phase:

```text
Completed
```

Possible phases:

```text
New
InProgress
Completed
PartiallyFailed
Failed
Deleting
```

If phase is `PartiallyFailed` or `Failed`, check warnings and errors.

## 13. Restore Testing — Most Important Production Step

A backup is not valid until restore is tested.

I always perform restore validation in one of these ways:

1. Restore into a different namespace in the same non-production cluster.
2. Restore into a DR cluster.
3. Restore into an isolated test namespace with namespace mapping.

Example restore to a different namespace:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-finance-prod-test
  namespace: openshift-adp
spec:
  backupName: finance-prod-manual-test
  namespaceMapping:
    finance-prod: finance-prod-restore-test
```

Apply:

```bash
oc apply -f restore-finance-prod-test.yaml
```

Check restore:

```bash
oc get restore -n openshift-adp
oc describe restore restore-finance-prod-test -n openshift-adp
```

Check restored namespace:

```bash
oc get all -n finance-prod-restore-test
oc get pvc -n finance-prod-restore-test
oc get route -n finance-prod-restore-test
oc get secret -n finance-prod-restore-test
oc get configmap -n finance-prod-restore-test
```

Application validation:

```bash
oc get pods -n finance-prod-restore-test
oc logs deployment/<deployment-name> -n finance-prod-restore-test
oc get route -n finance-prod-restore-test
curl -k https://<restored-route-url>/health
```

For database workloads, I validate data consistency at the application/database level, not only Kubernetes resource restoration.

## 14. Important Real-World Considerations

### 14.1 Application Consistency

For databases such as PostgreSQL, MySQL, MongoDB, Redis, or Elasticsearch, crash-consistent storage snapshots may not always be enough.

I consider:

- Pre-backup hooks to freeze or flush data.
- Post-backup hooks to unfreeze.
- Database-native backup tools.
- Operator-supported backup mechanism.
- Quiescing application writes.
- Maintenance window.
- Consistency group snapshots if storage supports them.

Example Velero hook concept:

```yaml
metadata:
  annotations:
    pre.hook.backup.velero.io/command: '["/bin/sh", "-c", "pg_dumpall > /backup/prebackup.sql"]'
```

In interviews, I clearly say:

> For stateful workloads, I do not blindly trust Kubernetes object backup. I validate whether the application needs logical backup, snapshot backup, or both.

---

### 14.2 Backup Window

I schedule the backup during low business traffic.

Example:

```text
Daily at 01:00 during off-peak hours
```

I also ensure backups do not overlap. OADP documentation recommends leaving enough time for a backup to complete before the next backup starts. If a namespace backup usually takes 30 minutes, I do not schedule it every 30 minutes.

---

### 14.3 Retention Policy

Retention should be business-driven.

Example strategy:

```text
Daily backup: retain 7 days
Weekly backup: retain 4 weeks
Monthly backup: retain 12 months
```

Daily schedule:

```yaml
ttl: 168h0m0s
```

Weekly schedule:

```yaml
schedule: "0 2 * * 0"
ttl: 672h0m0s
```

Monthly schedule:

```yaml
schedule: "0 3 1 * *"
ttl: 8760h0m0s
```

---

### 14.4 Security of Backup Data

Backup storage can contain sensitive data because it may include:

- Secrets.
- ConfigMaps.
- TLS certificates.
- Routes.
- Application manifests.
- PVC data.
- Database data.

Security controls:

- Use encrypted object storage.
- Restrict bucket access.
- Use least-privilege IAM/service account.
- Rotate credentials.
- Enable object lock/versioning if required.
- Audit backup access.
- Secure backup credentials in OpenShift Secrets.
- Avoid sharing backup bucket credentials with application teams unless required.
- Consider separate buckets per environment.

---

### 14.5 Namespace Backup Is Not Full Cluster Backup

A namespace backup protects namespace-scoped application resources.

It may not protect:

- etcd disaster recovery.
- Full cluster control plane state.
- Cluster operators.
- Cluster-wide resources unless included.
- Node configuration.
- MachineConfigPool state.
- OpenShift installation assets.
- External databases.
- External object stores.
- External secrets managers.

For full cluster disaster recovery, OpenShift etcd backup is a separate process.

Example etcd backup command is usually executed from a control plane node using cluster-backup scripts, depending on OpenShift version and procedure. I keep etcd backup separate from OADP application backup.

## 15. Full Production Example

Below is a practical production-style schedule for a namespace called `finance-prod`.

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: finance-prod-daily-backup
  namespace: openshift-adp
  labels:
    app.kubernetes.io/name: finance-prod
    app.kubernetes.io/component: backup
    backup-tier: gold
    environment: production

  schedule: "0 1 * * *"
  template:
    includedNamespaces:
    - finance-prod
    excludedResources:
    - events
    storageLocation: default
    snapshotVolumes: true
    ttl: 168h0m0s
```

Apply:

```bash
oc apply -f finance-prod-daily-backup-schedule.yaml
```

Verify:

```bash
oc get schedule finance-prod-daily-backup -n openshift-adp
oc describe schedule finance-prod-daily-backup -n openshift-adp
```

```bash

  - finance-prod
```

## 16. Troubleshooting Daily Backup Failures

### 16.1 Schedule Created But No Backup Is Running

Check schedule:

```bash
oc describe schedule finance-prod-daily-backup -n openshift-adp
```

Check Velero logs:

```bash
oc logs deployment/velero -n openshift-adp | grep finance-prod-daily-backup
```

Possible causes:

- Invalid cron expression.
- Velero pod not running.
- Schedule is paused.
- OADP DPA not reconciled.
- Controller timezone misunderstanding.

Check paused status:

```bash
oc get schedule finance-prod-daily-backup -n openshift-adp -o yaml | grep paused
```

If paused:

```bash
oc patch schedule finance-prod-daily-backup -n openshift-adp --type merge -p '{"spec":{"paused":false}}'
```

---

### 16.2 Backup Fails With Object Storage Error

Commands:

```bash
oc describe backupstoragelocation default -n openshift-adp
oc logs deployment/velero -n openshift-adp | egrep -i "s3|bucket|access|denied|credential|timeout|tls|x509"
```

Possible causes:

- Wrong object storage endpoint.
- Bucket does not exist.
- Credentials invalid.
- Secret missing.
- CA certificate issue.
- Proxy issue.
- Firewall issue.
- DNS resolution issue.

Fix example:

```bash
oc get secret -n openshift-adp
oc describe secret cloud-credentials -n openshift-adp
```

Do not print secret values in production logs or screenshots.

---

### 16.3 Backup Completed With Warnings

Check:

```bash
oc describe backup <backup-name> -n openshift-adp
```

Common warnings:

- Some resources skipped.
- Some CRDs not found.
- Snapshot not taken.
- Volume backup failed.
- Resource conflict.
- Permission denied for specific resources.

A `Completed` backup with warnings is not always safe. I review warnings and decide whether the backup is acceptable.

---

### 16.4 PVC Data Not Restored

Check whether PVC was backed up:

```bash
oc describe backup <backup-name> -n openshift-adp | egrep -i "snapshot|volume|pvc|warning|error"
```

Check snapshots:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

Check storage class and snapshot class:

```bash
oc get pvc -n finance-prod
oc get sc
oc get volumesnapshotclass
```

Possible causes:

- Storage driver does not support CSI snapshots.
- No VolumeSnapshotClass.
- Snapshot class missing required labels/driver.
- `snapshotVolumes` disabled.
- File-system backup not enabled.
- Pod volume annotation missing.
- Node-agent not running on nodes.
- PVC was dynamically provisioned differently during restore.

---

### 16.5 Restore Fails Due to Existing Resources

If restoring into the same namespace, resources may already exist.

Better approach:

- Restore into a clean namespace.
- Use namespace mapping.
- Delete broken resources carefully before restoring.
- Avoid overwriting production without a restore plan.

Check restore errors:

```bash
oc describe restore <restore-name> -n openshift-adp
oc logs deployment/velero -n openshift-adp | grep <restore-name>
```

---

### 16.6 Secrets Restored But Application Still Fails

Check:

```bash
oc get secret -n finance-prod-restore-test
oc describe pod <pod-name> -n finance-prod-restore-test
oc logs <pod-name> -n finance-prod-restore-test
```

Possible causes:

- External dependency not restored.
- Route hostname conflict.
- ImagePullSecret invalid in target cluster.
- ServiceAccount token behavior differs in newer Kubernetes/OpenShift versions.
- External database endpoint inaccessible.
- NetworkPolicy blocking traffic.
- Storage restore incomplete.

## 17. Monitoring and Alerting

For production, I do not rely on manual checking.

I configure monitoring for:

- Backup failure.
- Backup partially failed.
- No successful backup in last 24 hours.
- BackupStorageLocation unavailable.
- Velero pod crashlooping.
- Node-agent pod failures.
- Snapshot failures.
- Object storage access failures.

Useful commands:

```bash
oc get backup -n openshift-adp
oc get schedule -n openshift-adp
oc get backupstoragelocation -n openshift-adp
oc get pods -n openshift-adp
```

In mature environments, I integrate backup status with Prometheus, Alertmanager, email, Slack, ServiceNow, or enterprise monitoring tools.

| PVC | Snapshot or file-system backup configured |
| Retention | TTL matches policy |
| Security | Object storage encrypted and access controlled |
| Restore | Restore tested successfully |
| Monitoring | Backup failure alerts configured |
| Documentation | RTO/RPO documented |
| Ownership | App owner and platform owner agreed |

## 19. RTO and RPO Explanation

### RPO — Recovery Point Objective

If backup runs daily at 01:00, the maximum possible data loss can be close to 24 hours, unless the application has separate database replication or more frequent backups.

Example:

```text
Daily backup RPO ≈ 24 hours
```

### RTO — Recovery Time Objective

RTO depends on:

- Size of Kubernetes resources.
- Size of PVC data.
- Object storage speed.
- Storage snapshot restore speed.
- Image availability.
- External dependencies.
- DNS and route changes.
- Manual approval process.

Example:

```text
Small stateless namespace restore: minutes
Large stateful namespace restore: tens of minutes to hours
```

Interview statement:

> I always align backup frequency and restore testing with RPO/RTO. A daily backup may satisfy some applications, but critical databases may require more frequent database-level backup or replication.

## 20. Common Interview Follow-Up Questions

### Q1. Does OADP backup etcd?

No. OADP is mainly for application backup and restore. OpenShift etcd backup is a separate cluster-level disaster recovery activity.

### Q2. Can I back up only one namespace?

Yes. Use `includedNamespaces` in the Backup or Schedule template.

### Q3. Can I back up multiple namespaces?

Yes.

```yaml
includedNamespaces:
- finance-prod
- payment-prod
- reporting-prod
```

### Q4. Can I exclude a namespace?

Yes, Velero supports namespace and resource filtering. However, for a namespace-specific backup, I usually use `includedNamespaces`.

### Q5. How do you protect PVC data?

Use CSI snapshots if the storage provider supports them. Otherwise, configure file-system backup using OADP node-agent/Kopia/Restic depending on OADP version and platform configuration.

### Q6. How do you confirm backup is valid?

A backup is valid only after successful restore testing. I restore to a test namespace or DR cluster and validate application functionality.

### Q7. What happens if the namespace has routes?

Routes are backed up as OpenShift resources. During restore to a different namespace or cluster, route hostnames may conflict. I review route hostnames and may modify them for restore testing.

### Q8. Are Secrets backed up?

Yes, namespace Secrets can be included. That is why backup storage must be secured and encrypted.

### Q9. Can I schedule daily, weekly, and monthly backups?

Yes. Create separate Schedule CRs with different cron expressions and TTL values.

Example:

```yaml
schedule: "0 1 * * *"     # daily
schedule: "0 2 * * 0"     # weekly Sunday
schedule: "0 3 1 * *"     # monthly first day
```

### Q10. What if the backup takes longer than expected?

I review backup duration, PVC size, object storage performance, network latency, snapshot performance, and schedule overlap. I adjust the backup window or split workloads if required.

## 21. Senior-Level Interview Answer

If asked in an interview, I would answer like this:

> To schedule a daily backup of a namespace in OpenShift, I would use OADP, which provides Velero-based Backup, Restore, and Schedule APIs. First, I would verify that the OADP Operator is installed, the DataProtectionApplication is reconciled, and the BackupStorageLocation is available. Then I would check whether the namespace has PVCs and whether the storage class supports CSI snapshots. If snapshots are not available, I would configure file-system backup using the OADP node agent.
>
> After validation, I would create a `Schedule` CR in the `openshift-adp` namespace with a daily cron expression such as `0 1 * * *`, and I would specify `includedNamespaces: [finance-prod]`. I would also define retention using `ttl`, configure `storageLocation`, and enable volume snapshots if required. After creating the schedule, I would not assume it is working. I would trigger a manual backup from the same template, check the backup phase, review Velero logs, verify object storage, and perform a restore test into a separate namespace.
>
> In production, I would also define RPO/RTO, secure backup storage, monitor backup failures, prevent backup overlap, test restores regularly, and document the runbook. For stateful applications, I would ensure application-consistent backups using database-native backup, hooks, or storage-level consistency depending on the workload.

## 23. Final Production Recommendation

For a production OpenShift namespace, my recommended daily backup design is:

- Use OADP Operator with Velero.
- Store backups in secure S3-compatible object storage.
- Use `Schedule` CR for daily automation.
- Use `includedNamespaces` to target the namespace.
- Use CSI snapshots for PVCs where supported.
- Use file-system backup where snapshots are unavailable.
- Set backup TTL according to retention policy.
- Create separate schedules for daily, weekly, and monthly backups if required.
- Monitor backup health.
- Regularly test restore.
- Document RPO, RTO, ownership, and restore procedure.

The key senior-level point is: **scheduling the backup is easy; proving that the backup can be restored successfully is the real production responsibility.**
