# How do you restore an application with PVC data?

## Interview-Level Scenario for Advanced OpenShift Administration

**Role expectation:** Senior OpenShift Administrator / Platform Engineer with 10+ years of production experience  
**Focus area:** Application backup and restore, OADP, Velero, PVC/PV recovery, storage validation, application consistency, and post-restore troubleshooting

---

## 1. Interview Question

**Question:**  
How do you restore an application with PVC data in OpenShift?

**Senior-level answer:**  
I do not restore only Kubernetes YAML objects and assume the application is recovered. For a real production restore, I restore the complete application state, which includes namespace-scoped Kubernetes objects, secrets, config maps, service accounts, routes, deployments/statefulsets, PVCs, PV data, security context constraints impact, storage classes, and application-level consistency.

In OpenShift, I normally use **OADP**, which is Red Hat's OpenShift API for Data Protection and is based on Velero. OADP can back up and restore Kubernetes resources and persistent volume data by using storage snapshots or file system backup mechanisms such as Kopia or Restic depending on the storage backend and configuration. Red Hat documentation states that OADP backs up and restores Kubernetes resources, internal images, and PVs by using snapshots or file-system backup methods such as Restic/Kopia depending on the environment.  

References used while preparing this guide:

- Red Hat OpenShift Backup and Restore documentation: OADP backs up/restores namespace resources and PVs using snapshots or file-system backup.  
  Source: https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/backup_and_restore/index
- Velero documentation: Velero supports Kubernetes resource backup/restore and persistent volume backup using snapshots or file-system backup.  
  Source: https://velero.io/docs/main/file-system-backup/
- Velero restore reference: restore behavior, restore command, restore phases, and object restore process.  
  Source: https://velero.io/docs/main/restore-reference/

## 2. Production Scenario

Assume I have an OpenShift application running in namespace:

```bash
project: payments-prod
```

The application has:

```text
Deployment/StatefulSet  : payments-api, payments-db
PVCs                    : payments-db-data, payments-upload-data
StorageClass            : ocs-storagecluster-ceph-rbd or gp3-csi or nfs-client
Routes                  : payments.apps.example.com
Secrets                 : db-secret, app-secret, pull-secret
ConfigMaps              : app-config
ServiceAccounts         : payments-sa
NetworkPolicies         : allow-payments-ingress
```

A disaster occurred:

- Namespace was deleted accidentally, or
- PVC data was corrupted, or
- Cluster migration is required, or
- Application needs to be restored to another cluster, or
- A failed release damaged the database volume.

My target is:

```text
Restore application objects + restore PVC data + validate application functionality.
```

## 3. Important Concept: Application Restore Is More Than `oc apply`

A junior admin may think restore means:

```bash
oc apply -f deployment.yaml
```

That is not enough.

A real application restore requires:

| Component | Why It Matters |
|---|---|
| Namespace/project | Application objects live inside namespace |
| Deployments/StatefulSets | Recreate application workload |
| Services/Routes | Restore access path |
| ConfigMaps/Secrets | Restore runtime configuration and credentials |
| PVCs | Recreate storage claims |
| PV data | Restore actual application data |
| ServiceAccounts/RBAC | Allow pods to run with correct permissions |
| SCC impact | OpenShift-specific security may block restored pods |
| ImageStreams/internal images | Required if application uses OpenShift image streams |
| NetworkPolicies | Required for traffic flow |
| StorageClass | Required for dynamic PVC provisioning |
| VolumeSnapshotClass | Required if snapshot restore is used |
| Application consistency | Database/application data must not be crash-inconsistent |

In an interview, I would clearly say:

> Restoring PVC YAML without restoring the volume data does not restore the application state. The PVC only requests storage; the real business data is inside the PV or snapshot/file-system backup.

## 4. Restore Methods for PVC Data

There are mainly three restore patterns in OpenShift/OADP.

---

### 4.1 Snapshot-Based Restore

This is used when the storage backend supports CSI snapshots or cloud-provider snapshots.

Examples:

- OpenShift Data Foundation / Ceph RBD with snapshot support
- AWS EBS CSI
- Azure Disk CSI
- Google Persistent Disk CSI
- VMware vSphere CSI, depending on configuration

In this method:

```text
Backup captures Kubernetes objects + VolumeSnapshot/CSI snapshot metadata.
Restore recreates PVC from snapshot or restores PV data using snapshot mechanism.
```

Advantages:

- Fast backup and restore
- Efficient for large volumes
- Storage-native capability
- Better for production databases when coordinated properly

Limitations:

- Requires storage backend snapshot support
- Requires correct VolumeSnapshotClass
- Cross-cluster restore may need compatible storage backend
- Snapshot location must survive source-cluster failure
- Some snapshots are crash-consistent unless application quiescing is implemented

---

### 4.2 File System Backup Restore using Kopia or Restic

This is used when snapshots are unavailable or not suitable.

Common examples:

- NFS volumes
- Local storage
- Storage without CSI snapshot support
- Cross-storage migration
- Migration between different clusters/storage providers

In this method:

```text
Velero/OADP node agent reads data from mounted pod volumes and uploads the file-level data to object storage.
During restore, data is copied back into the newly provisioned PVC.
```

Advantages:

- Works with non-snapshot storage
- Useful for migration across storage classes
- Can restore to a different cluster/storage backend

Limitations:

- Slower for large volumes
- Needs node-agent/Kopia/Restic configuration
- Requires pods using the PVC to exist at backup time
- Performance depends on object storage, network, and volume size
- Some special file systems or databases may require application-level backup for consistency

---

### 4.3 Application-Native Restore

For databases and stateful systems, the best practice may be to use application-native backup and restore.

Examples:

| Application | Native Restore Method |
|---|---|
| PostgreSQL | pg_dump, pg_basebackup, WAL restore, operator backup |
| MySQL/MariaDB | mysqldump, Percona XtraBackup |
| MongoDB | mongodump/mongorestore, Ops Manager backup |
| Elasticsearch | snapshot repository restore |
| Kafka | MirrorMaker/replication/rebuild from topics |
| GitLab | GitLab backup/restore command |

For mission-critical databases, I prefer:

```text
OADP restore for Kubernetes objects + application-native database restore for logical consistency.
```

Why?

Because PVC snapshot/file backup may be crash-consistent but not always application-consistent unless the database was quiesced, frozen, or backed up using database-aware tooling.

## 5. Pre-Restore Checklist

Before restoring, I validate the environment carefully.

---

### 5.1 Confirm Restore Target

I first identify whether restore is going to:

```text
Same namespace in same cluster
Different namespace in same cluster
Different cluster
Different storage class
Different OpenShift version
DR cluster
```

Commands:

```bash
oc whoami
oc cluster-info
oc get clusterversion
oc get nodes
oc get co
```

Check cluster health:

```bash
oc get co
oc get nodes
oc get mcp
oc get pods -A | egrep -i 'CrashLoop|Error|Pending|ImagePull|Terminating'
```

I do not start a production restore on an unhealthy cluster unless it is an emergency DR restore.

---

### 5.2 Confirm OADP/Velero Health

```bash
oc get pods -n openshift-adp
oc get dpa -n openshift-adp
oc get backupstoragelocation -n openshift-adp
oc get volumesnapshotlocation -n openshift-adp
```

Expected:

```text
Velero pod Running
node-agent pods Running, if Kopia/Restic file-system backup is used
BackupStorageLocation Available
VolumeSnapshotLocation configured, if snapshot restore is used
```

Detailed check:

```bash
oc describe dpa -n openshift-adp
oc logs deploy/velero -n openshift-adp
oc get backupstoragelocation -n openshift-adp -o yaml
```

If `BackupStorageLocation` is unavailable, restore will fail or backup metadata may not be readable.

---

### 5.3 Confirm Backup Exists

```bash
oc get backup -n openshift-adp
velero backup get
```

Describe backup:

```bash
velero backup describe payments-prod-backup-2026-07-03 --details
```

Check backup logs:

```bash
velero backup logs payments-prod-backup-2026-07-03
```

I verify:

```text
Backup phase: Completed
Namespace included: payments-prod
PVCs included: yes
PV backup method: snapshot or filesystem backup
Errors: 0 or understood
Warnings: reviewed
Volume backups completed
```

For file-system backup, check pod volume backups:

```bash
oc get podvolumebackup -n openshift-adp
oc describe podvolumebackup -n openshift-adp
```

For restore later, check pod volume restores:

```bash
oc get podvolumerestore -n openshift-adp
```

For snapshot-based backup, check:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
oc get volumesnapshotclass
```

---

### 5.4 Confirm StorageClass Exists on Target

```bash
oc get storageclass
```

Check original PVC storage class:

```bash
oc get pvc -n payments-prod -o wide
oc get pvc -n payments-prod -o yaml | grep -i storageClassName
```

On target cluster, the storage class must exist or be mapped.

Example issue:

```text
Source cluster storageClass: ocs-storagecluster-ceph-rbd
Target cluster storageClass: ocs-external-storagecluster-ceph-rbd
```

If restore expects old storage class and target does not have it, PVC may stay Pending.

---

### 5.5 Confirm Namespace State

If restoring to same namespace, I check whether objects already exist:

```bash
oc get all -n payments-prod
oc get pvc -n payments-prod
oc get route,secret,cm,sa,role,rolebinding -n payments-prod
```

Important decision:

```text
Do I restore into a clean namespace?
Do I delete existing broken objects?
Do I restore with namespace mapping?
Do I restore only PVC data?
Do I restore both app and data?
```

For production, I prefer restoring into a clean namespace first when possible:

```bash
payments-prod-restore
```

Then validate before switching traffic.

## 6. Backup Example Before Disaster

A restore can only be successful if the backup was created correctly.

Example namespace backup:

```bash
velero backup create payments-prod-backup-2026-07-03 \
  --include-namespaces payments-prod \
  --wait
```

With snapshot volumes:

```bash
velero backup create payments-prod-snapshot-backup \
  --include-namespaces payments-prod \
  --snapshot-volumes \
  --wait
```

With file-system backup:

```bash
velero backup create payments-prod-fsb-backup \
  --include-namespaces payments-prod \
  --default-volumes-to-fs-backup \
  --wait
```

For selected pod volumes using annotation:

```bash
oc annotate pod payments-db-0 \
  backup.velero.io/backup-volumes=database-data \
  -n payments-prod
```

Then backup:

```bash
velero backup create payments-prod-db-fsb \
  --include-namespaces payments-prod \
  --wait
```

Senior point:

> I always confirm backup content before trusting it. A completed backup without PVC data is not a complete application backup.

## 8. Restore Flow: Restore to Different Namespace

Sometimes I do not want to overwrite production immediately. I restore to a validation namespace.

Source namespace:

```text
payments-prod
```

Target namespace:

```text
payments-prod-restore
```

Command:

```bash
velero restore create payments-prod-restore-test \
  --from-backup payments-prod-backup-2026-07-03 \
  --namespace-mappings payments-prod:payments-prod-restore \
  --wait
```

Validate:

```bash
oc get all -n payments-prod-restore
oc get pvc -n payments-prod-restore
oc get pods -n payments-prod-restore
```

Important points:

- Routes may conflict if same host is restored.
- Secrets may point to production database endpoints.
- ConfigMaps may contain old namespace/service names.
- NetworkPolicies may need namespaceSelector changes.
- External DNS or route host may need modification.
- Applications with hardcoded namespace names may fail.

If the route conflicts, I patch it:

```bash
oc patch route payments \
  -n payments-prod-restore \
  --type='merge' \
  -p '{"spec":{"host":"payments-restore.apps.example.com"}}'
```

## 10. PVC Restore Deep Dive

---

### 10.1 What Happens During PVC Restore?

For PVC restore, the following happens conceptually:

```text
1. Velero restores namespace-scoped PVC object.
2. Storage provisioner dynamically creates a new PV.
3. If snapshot restore is used, the new volume is created from snapshot.
4. If file-system backup is used, Velero node-agent restores files into the volume.
5. Pods are created or resumed.
6. Application mounts restored PVC.
```

The PVC object alone is not the data. Data recovery depends on whether snapshot or FSB was correctly configured and completed.

## 11. Application Consistency

This is one of the most important senior-level points.

PVC restore may be:

```text
Crash-consistent
Application-consistent
Transaction-consistent
```

### 11.1 Crash-Consistent Restore

This is like pulling the power from a server and starting it again from disk state. Many databases can recover using WAL/journals, but it is not always ideal.

### 11.2 Application-Consistent Restore

Application is quiesced before backup:

```text
Stop writes
Flush buffers
Freeze filesystem or database
Take backup/snapshot
Resume writes
```

Examples:

```bash
# Scale app down before backup if downtime is acceptable
oc scale deploy/payments-api --replicas=0 -n payments-prod
oc scale sts/payments-db --replicas=0 -n payments-prod

velero backup create payments-prod-consistent-backup \
  --include-namespaces payments-prod \
  --snapshot-volumes \
  --wait

oc scale sts/payments-db --replicas=1 -n payments-prod
oc scale deploy/payments-api --replicas=3 -n payments-prod
```

For databases, better approach:

```text
Take database-native backup + OADP backup for Kubernetes objects.
```

### 11.3 Interview Statement

> For stateless apps, OADP restore is usually straightforward. For stateful apps with databases, I always confirm whether the backup is crash-consistent or application-consistent. For critical workloads, I use database-native backup integrated with OADP object restore.

## 12. Restore Order

A clean restore usually follows this order:

```text
1. Validate target cluster health
2. Validate OADP health
3. Validate backup availability and backup content
4. Install required operators/CRDs first, if needed
5. Ensure StorageClass and VolumeSnapshotClass exist
6. Restore namespace and Kubernetes resources
7. Restore PVC/PV data
8. Validate PVC binding
9. Validate pod startup
10. Validate logs, routes, services, secrets, config
11. Validate application data
12. Perform smoke test
13. Switch traffic if restoring to DR/temporary namespace
14. Monitor application after restore
```

## 13. Selective Restore

Sometimes I do not restore everything. For example, I may restore only PVC and StatefulSet resources, or exclude routes to avoid conflict.

Restore only selected resources:

```bash
velero restore create payments-pvc-only-restore \
  --from-backup payments-prod-backup-2026-07-03 \
  --include-resources persistentvolumeclaims,persistentvolumes \
  --wait
```

Exclude routes:

```bash
velero restore create payments-no-route-restore \
  --from-backup payments-prod-backup-2026-07-03 \
  --exclude-resources routes.route.openshift.io \
  --wait
```

Restore selected namespace with mapping:

```bash
velero restore create payments-restore-test \
  --from-backup payments-prod-backup-2026-07-03 \
  --namespace-mappings payments-prod:payments-restore \
  --wait
```

## 14. Handling Existing Resources

If resources already exist, Velero usually does not overwrite everything blindly. Existing objects can cause restore warnings or skipped resources.

I check restore logs:

```bash
velero restore logs payments-prod-restore-2026-07-03 | less
```

Common messages:

```text
resource already exists
PVC already exists
route host already claimed
storageclass not found
failed to restore pod volume
forbidden SCC/securityContext issue
```

In production, I decide whether to:

```text
Delete broken namespace and restore cleanly
Restore to a new namespace
Delete only selected conflicting objects
Patch restored resources
Use namespace mapping
Use resource filtering
```

Example clean namespace approach:

```bash
oc delete project payments-prod
oc get ns payments-prod

velero restore create payments-prod-clean-restore \
  --from-backup payments-prod-backup-2026-07-03 \
  --wait
```

Be careful: deleting a namespace may delete PVCs and PVs depending on reclaim policy and storage backend.

## 16. Common Restore Failures and Troubleshooting

---

### 16.1 PVC Stuck in Pending

Symptoms:

```bash
oc get pvc -n payments-prod
```

```text
payments-db-data   Pending
```

Check:

```bash
oc describe pvc payments-db-data -n payments-prod
oc get storageclass
oc get events -n payments-prod --sort-by=.metadata.creationTimestamp
```

Common causes:

| Cause | Fix |
|---|---|
| StorageClass missing | Create same StorageClass or map/patch PVC |
| CSI driver not installed | Install/configure storage operator |
| Insufficient storage | Expand backend capacity |
| Access mode unsupported | Use correct RWX/RWO storage class |
| VolumeSnapshotClass missing | Create correct snapshot class |
| Zone/region mismatch | Restore to matching topology or patch constraints |

---

### 16.2 Pod Stuck in ContainerCreating

Check:

```bash
oc describe pod <pod-name> -n payments-prod
```

Common messages:

```text
Unable to attach or mount volumes
MountVolume.MountDevice failed
permission denied
volume not found
multi-attach error
```

Troubleshooting:

```bash
oc get pvc -n payments-prod
oc describe pvc <pvc-name> -n payments-prod
oc describe pv <pv-name>
oc get nodes
oc get events -n payments-prod
```

For CSI logs:

```bash
oc get pods -n openshift-cluster-csi-drivers
oc logs <csi-controller-pod> -n openshift-cluster-csi-drivers
```

For ODF:

```bash
oc get pods -n openshift-storage
oc logs <rook-ceph-operator-pod> -n openshift-storage
```

---

### 16.3 Restore Completed but Data Missing

This is a serious issue.

Check whether backup included PVC data:

```bash
velero backup describe payments-prod-backup-2026-07-03 --details
velero backup logs payments-prod-backup-2026-07-03
```

Check file-system backup objects:

```bash
oc get podvolumebackup -n openshift-adp
oc get podvolumerestore -n openshift-adp
```

Check snapshot objects:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

Possible causes:

```text
Backup captured PVC object but not PV data
Application pod was not running during FSB backup
Required backup annotation missing
node-agent was not enabled
Snapshot failed silently with warning
Wrong backup selected
Restore created empty PVC using StorageClass
Application writes data to different mount path than expected
SubPath issue
Init container overwrote restored data
Application reformatted/reinitialized empty database
```

Senior-level action:

```text
I compare restore logs, backup details, PodVolumeBackup/Restore status, snapshot status, and application mount path. Then I verify whether the restored PVC contains expected files before starting the application fully.
```

---

### 16.4 Pods Running but Application Fails

Check logs:


### 16.5 Route Restore Conflict

Symptoms:


Check:

```bash

```

### 16.6 SCC / Permission Issues After Restore

OpenShift uses SCCs. A restored app may fail if service account permissions are missing.

Check pod events:

```bash

```

Check service account:


```bash

```

Senior note:

## 19. Data Protection Design Best Practices

A strong answer should also explain how I design backup/restore before failure.

---

### 19.1 Backup Storage Must Be Off-Cluster

Do not keep the only backup inside the same cluster storage.

Bad design:

```text
Backup bucket on same failed cluster storage
```

Good design:

```text
S3-compatible object storage outside cluster
Cloud object bucket
ODF MCG replicated externally
Dedicated backup object store
```

---

### 19.2 Test Restore Regularly

A backup that is never restored is only an assumption.

I schedule restore drills:

```text
Daily/weekly backup validation
Monthly restore test
Quarterly DR drill
Application owner sign-off
RTO/RPO measurement
```

---

### 19.3 Match Backup Method to Workload

| Workload | Recommended Backup Method |
|---|---|
| Stateless app | OADP object restore |
| App with uploaded files | OADP + PVC snapshot/FSB |
| Database | DB-native backup + OADP object backup |
| NFS-backed app | OADP FSB with Kopia/Restic |
| Large block volume | CSI snapshot/data movement |
| Cross-cluster migration | FSB or data movement depending on storage |

---

### 19.4 Define RPO and RTO

Example:

```text
RPO: Maximum acceptable data loss
RTO: Maximum acceptable restore time
```

For example:

```text
Payments application:
RPO = 15 minutes
RTO = 1 hour
```

This means backup frequency and restore architecture must support that target.

## 20. Interview-Level Answer Structure

In an interview, I would answer like this:

```text
First, I confirm the backup type and whether it contains PVC data. In OpenShift I normally use OADP/Velero. I check the Backup object, backup logs, BackupStorageLocation, VolumeSnapshotLocation, and whether the volume was backed up using CSI snapshot or file-system backup with Kopia/Restic.

Before restore, I validate the target cluster, storage classes, snapshot classes, OADP health, required operators, CRDs, SCC/RBAC, and namespace state. Then I create a Velero restore from the backup, preferably into a temporary namespace first using namespace mapping. After restore, I verify PVC binding, PV creation, PodVolumeRestore or VolumeSnapshot status, pod startup, application logs, routes, services, secrets, and finally the actual business data inside the application.

For stateful databases, I do not rely blindly on crash-consistent PVC restore. I check whether the backup was application-consistent. For critical databases, I combine OADP for Kubernetes objects with database-native backups for data consistency.

If PVC remains Pending, I troubleshoot StorageClass, CSI driver, VolumeSnapshotClass, capacity, access mode, and events. If pods are running but data is missing, I check whether PV data was included in backup, PodVolumeBackup/Restore status, Velero logs, node-agent logs, snapshot status, and application mount paths.
```

## 22. Final Senior-Level Conclusion

Restoring an application with PVC data in OpenShift requires a controlled and validated process. I first confirm that the backup actually contains the persistent volume data, then verify OADP/Velero health, backup storage, snapshot or file-system backup configuration, storage classes, and target namespace conditions. I perform the restore, preferably into a temporary namespace first, and then validate PVC binding, PV creation, pod startup, data presence, application health, routes, services, secrets, and business-level functionality.

For production databases, I also evaluate consistency. A PVC restore may recover files, but the application may still need database recovery or native restore. My final goal is not only to see pods in Running state; my final goal is to prove that the restored application is usable, consistent, secure, reachable, and meets the required RTO/RPO.
