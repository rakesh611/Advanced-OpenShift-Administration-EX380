# MachineConfigPool Is Degraded — Senior OpenShift Troubleshooting Flow

## Interview-Level Scenario

**Question:** `MachineConfigPool is degraded. What is your troubleshooting flow?`

**Expected level:** Advanced OpenShift Administration, production troubleshooting, 10+ years infrastructure experience.

---

## 1. Short Interview Answer

If a `MachineConfigPool` is degraded, I treat it as a node operating-system reconciliation issue handled by the Machine Config Operator. I first identify which pool is degraded, how many nodes are impacted, and whether the cluster is in the middle of an upgrade or machine configuration rollout. Then I inspect the MCP status, MCO operator status, rendered MachineConfig, affected nodes, Machine Config Daemon logs, node annotations, events, and host-level services such as `kubelet`, `crio`, `ostree`, and `rpm-ostree`.

My troubleshooting flow is:

1. Confirm MCP state and impact.
2. Identify degraded pool and degraded node.
3. Read MCP condition messages carefully.
4. Check Machine Config Operator and Machine Config Daemon pods.
5. Compare current, desired, and rendered MachineConfig.
6. Check node annotations and MCD logs.
7. Identify whether the issue is configuration drift, failed file write, failed service restart, rpm-ostree issue, reboot failure, drain failure, certificate/network/DNS issue, or bad MachineConfig.
8. Pause further rollout if necessary.
9. Fix the actual root cause, not just the symptom.
10. Resume rollout and verify that `UPDATED=True`, `UPDATING=False`, and `DEGRADED=False`.

In production, I avoid deleting MCPs or force-modifying rendered MachineConfigs. I preserve evidence first, pause rollout if more nodes could be affected, and recover node by node.

## 2. Background: What Is MachineConfigPool?

A `MachineConfigPool` groups nodes that receive the same operating-system-level configuration. Common pools are:

```bash
master
worker
infra
custom pools such as gpu, storage, logging, router, etc.
```

The Machine Config Operator manages operating-system-level configuration for OpenShift nodes, including parts of:

- systemd configuration
- CRI-O configuration
- kubelet configuration
- kernel arguments
- files written under the host filesystem
- registries configuration
- SSH keys
- node-level OS changes
- RHCOS updates during cluster upgrades

The main components are:

| Component | Purpose |
|---|---|
| `MachineConfigOperator` | Top-level operator controlling machine configuration lifecycle |
| `MachineConfigController` | Generates rendered machine configs and tracks pool state |
| `MachineConfigDaemon` | Runs on each node and applies the desired config |
| `MachineConfigPool` | Logical grouping of nodes that receive the same config |
| `MachineConfig` | Declarative OS-level configuration object |
| `Rendered MachineConfig` | Final merged config generated from multiple MachineConfigs |

A degraded MCP means at least one node in that pool failed to apply or validate the desired machine configuration.

---

## 3. What Does MCP Degraded Mean?

A degraded MCP usually means one or more nodes in the pool are marked degraded by the Machine Config Daemon. The node may still be `Ready`, but it cannot successfully reconcile to the desired machine configuration.

Important point for interviews:

> A degraded node can still run workloads, but it cannot be safely updated by the MCO until the degradation is fixed.

This is especially critical during cluster upgrades because OpenShift upgrades often wait for all MCPs to become healthy.

Typical MCP states:

```bash
oc get mcp
```

Example output:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
master   rendered-master-aaaa                               True      False      False      3              3                   3                     0
worker   rendered-worker-bbbb                               False     True       True       6              5                   4                     1
```

Here the `worker` pool is not fully updated and has one degraded machine.

## 4. Production Mindset Before Troubleshooting

Before running commands blindly, I ask:

1. Is this happening during an OpenShift upgrade?
2. Was a new `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig`, or `ImageContentSourcePolicy` recently applied?
3. Is only one node degraded or the entire pool?
4. Is this master, worker, infra, or custom pool?
5. Is the cluster still scheduling workloads safely?
6. Did any administrator manually change files on the node?
7. Is the node reachable by SSH/debug?
8. Are drains/reboots stuck?
9. Is the degraded condition caused by config drift or failed config application?
10. Do we need to pause the MCP to prevent further rollout?

In a large production cluster, if a bad MachineConfig is rolling out to more nodes, I pause the MCP immediately after collecting minimal evidence.

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

This does not fix the degraded node, but it prevents the pool from continuing the rollout to additional nodes.

```text

   |

   |

   |

```

## 6. Step 1: Check MCP Status

```bash
oc get mcp
```

Detailed view:

```bash
oc describe mcp worker
```

YAML view:

```bash
oc get mcp worker -o yaml
```

Useful JSONPath commands:

```bash
oc get mcp worker -o jsonpath='{.status.conditions}' | jq
```

```bash
oc get mcp worker -o jsonpath='{.status.degradedMachineCount}{"\n"}'
```

```bash
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
```

Check these fields:

| Field | Meaning |
|---|---|
| `UPDATED` | Pool nodes have desired config |
| `UPDATING` | Pool is applying new config |
| `DEGRADED` | One or more nodes failed reconciliation |
| `MACHINECOUNT` | Total nodes in pool |
| `READYMACHINECOUNT` | Ready nodes in pool |
| `UPDATEDMACHINECOUNT` | Nodes already on desired config |
| `DEGRADEDMACHINECOUNT` | Nodes marked degraded |
| `status.configuration.name` | Desired rendered config |

Interview explanation:

> I do not start with SSH. I start from the Kubernetes API because MCP status usually tells me whether this is a pool-wide issue, single-node issue, bad MachineConfig, or rollout issue.

## 8. Step 3: Identify the Degraded Node

Check nodes:

```bash
oc get nodes
```

Show node MachineConfig annotations:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,ROLE:.metadata.labels."node-role\.kubernetes\.io/worker",STATE:.metadata.annotations."machineconfiguration\.openshift\.io/state",CURRENT:.metadata.annotations."machineconfiguration\.openshift\.io/currentConfig",DESIRED:.metadata.annotations."machineconfiguration\.openshift\.io/desiredConfig",REASON:.metadata.annotations."machineconfiguration\.openshift\.io/reason"
```

For a specific node:

```bash
NODE=worker-1.example.com
oc get node $NODE -o yaml | grep -A10 -B5 machineconfiguration.openshift.io
```

Important annotations:

| Annotation | Meaning |
|---|---|
| `machineconfiguration.openshift.io/currentConfig` | Config currently applied on node |
| `machineconfiguration.openshift.io/desiredConfig` | Config node is trying to apply |
| `machineconfiguration.openshift.io/state` | Node MCO state such as `Done`, `Working`, `Degraded` |
| `machineconfiguration.openshift.io/reason` | Human-readable reason for degradation |

Example degraded annotations:

```yaml
machineconfiguration.openshift.io/currentConfig: rendered-worker-old
machineconfiguration.openshift.io/desiredConfig: rendered-worker-new
machineconfiguration.openshift.io/state: Degraded
machineconfiguration.openshift.io/reason: 'unexpected on-disk state validating against rendered-worker-new: content mismatch for file /etc/containers/registries.conf'
```

This usually points to configuration drift.

## 9. Step 4: Check Machine Config Daemon Pods

The MCD runs as a daemonset in `openshift-machine-config-operator`.

```bash
oc get pods -n openshift-machine-config-operator -o wide
```

Find the MCD pod running on the degraded node:

```bash
NODE=worker-1.example.com
oc get pod -n openshift-machine-config-operator -o wide | grep $NODE
```

Check logs:

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide | awk '/worker-1.example.com/ && /machine-config-daemon/ {print $1}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=200
```

Previous logs if pod restarted:

```bash
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --previous --tail=200
```

Follow logs during remediation:

```bash
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon -f
```

Common log patterns:

```text
content mismatch for file
unexpected on-disk state
failed to update OS to quay.io/openshift-release-dev/ocp-v4.0-art-dev
failed to drain node
failed to reboot
failed to start kubelet
error running rpm-ostree
error decoding Ignition config
file exists and has different mode
```

## 12. Step 7: Check Whether Rollout Is Stuck Due to Drain Failure

MCO drains a node before applying certain changes and rebooting. If workloads cannot be evicted, the MCP may stay updating or become degraded.

Check node cordon/drain state:

```bash
oc get nodes
```

Check pods on the affected node:

```bash
NODE=worker-1.example.com
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
```

Look for pods blocking drain:

```bash
oc get pdb -A
```

```bash
oc describe pdb -A
```

Typical causes:

- PodDisruptionBudget too strict
- static pods
- daemonset behavior misunderstood
- pods with local storage
- terminating pods stuck
- finalizers blocking deletion
- workload replicas too low

Example:

```text
Cannot evict pod as it would violate the pod's disruption budget
```

Fix:

- scale application replicas properly
- temporarily adjust PDB if approved
- remove stuck finalizers only after careful validation
- manually drain only when safe

```bash
oc adm drain worker-1.example.com --ignore-daemonsets --delete-emptydir-data --timeout=10m
```

Use manual drain carefully. Do not force-delete business-critical pods without application owner approval.

## 13. Step 8: Check for Configuration Drift

Configuration drift means the node filesystem has changed outside MCO control. For example, someone manually edited:

```text
/etc/containers/registries.conf
/etc/kubernetes/kubelet.conf
/etc/crio/crio.conf
/etc/ssh/sshd_config
/etc/sysctl.d/*.conf
/etc/systemd/system/*.service
```

MCD validates expected content against actual on-disk content. If it detects unexpected changes, it marks the node degraded.

Example message:

```text
unexpected on-disk state validating against rendered-worker-xxxxx: content mismatch for file /etc/containers/registries.conf
```

Check node reason:

```bash
oc get node worker-1.example.com -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Use debug shell:

```bash
oc debug node/worker-1.example.com
chroot /host
```

Check file:

```bash
ls -l /etc/containers/registries.conf
cat /etc/containers/registries.conf
```

Compare with MachineConfig desired content. MachineConfig file contents are often base64 encoded:

```bash
oc get mc rendered-worker-xxxxx -o yaml
```

Decode example:

```bash
echo '<base64-content>' | base64 -d
```

Recovery options:

1. If manual change is wrong, revert the file to match MachineConfig.
2. If manual change is required, convert it into a supported MachineConfig.
3. If the MachineConfig is wrong, correct or remove the bad MachineConfig.
4. Let MCD revalidate and reconcile.

Do not keep manual host changes outside MCO in production.

## 14. Step 9: Check Bad MachineConfig Syntax or Unsafe File Content

A custom MachineConfig can degrade a pool if it has:

- invalid Ignition syntax
- wrong file path
- wrong file mode
- wrong ownership
- invalid systemd unit
- invalid CRI-O configuration
- invalid registry configuration
- invalid kubelet configuration
- wrong base64 encoded content
- conflicting MachineConfigs writing the same file
- kernel arguments unsupported by the node

Check MachineConfig:

```bash
oc get mc 99-worker-custom -o yaml
```

Check for file sections:

```yaml
spec:
  config:
    ignition:
      version: 3.2.0
    storage:
      files:
      - path: /etc/example.conf
        mode: 0644
        contents:
          source: data:text/plain;charset=utf-8;base64,...
```

Common mistake:

```yaml
mode: 644
```

Correct form should be decimal representation expected by Ignition/OpenShift examples, often:

```yaml
mode: 420
```

Because `0644` octal equals `420` decimal.

Another common mistake is malformed systemd unit content:

```bash
systemd-analyze verify /etc/systemd/system/custom.service
```

Recovery:

```bash
oc delete mc 99-worker-bad-config
```

or fix and apply corrected config:

```bash
oc apply -f corrected-machineconfig.yaml
```

Then monitor:

```bash
oc get mcp worker -w
```

## 15. Step 10: Check rpm-ostree / OS Update Failure

During upgrades, the MCD may use `rpm-ostree` to apply OS image changes. Failure here can degrade MCP.

Access node:

```bash
oc debug node/worker-1.example.com
chroot /host
```

Check:

```bash
rpm-ostree status
journalctl -u rpm-ostreed --no-pager -n 100
journalctl -u machine-config-daemon-firstboot --no-pager -n 100
```

Look for:

- failed OS pivot
- unavailable release image
- image pull failure
- proxy issue
- registry certificate issue
- disk full
- ostree deployment issue

Check disk:

```bash
df -h
findmnt
lsblk
```

Check image pull/proxy/certs:

```bash
cat /etc/containers/registries.conf
cat /etc/containers/policy.json
ls -l /etc/pki/ca-trust/source/anchors/
```

Possible fixes:

- fix proxy configuration
- fix mirror registry configuration
- fix custom CA bundle
- free disk space
- restore registry access
- correct ImageDigestMirrorSet/ImageContentSourcePolicy
- retry node update

## 16. Step 11: Check Kubelet and CRI-O

MCO changes can restart kubelet and CRI-O. If either service fails, node may become NotReady and MCP may degrade.

```bash
oc debug node/worker-1.example.com
chroot /host
```

Check services:

```bash
systemctl status kubelet --no-pager
systemctl status crio --no-pager
journalctl -u kubelet --no-pager -n 100
journalctl -u crio --no-pager -n 100
```

Common root causes:

- invalid CRI-O config
- invalid registry config
- invalid proxy settings
- bad kubelet config
- certificate issue
- missing filesystem path
- DNS issue
- node cannot reach API server

Check kubelet config:

```bash
cat /etc/kubernetes/kubelet.conf
cat /etc/kubernetes/kubelet-ca.crt
```

Check API connectivity:

```bash
curl -k https://api.<cluster-domain>:6443/readyz
```

Check DNS:

```bash
cat /etc/resolv.conf
nslookup api.<cluster-domain>
```

## 17. Step 12: Check Node Reboot Issues

Some MachineConfig changes require reboot. MCP can get stuck if node does not reboot or does not return healthy.

Check node annotations:

```bash
oc get node worker-1.example.com -o yaml | grep -i reboot -A5 -B5
```

From node:

```bash
oc debug node/worker-1.example.com
chroot /host
uptime
last reboot
journalctl -b -1 --no-pager -n 100
journalctl -b --no-pager -u kubelet -n 100
```

Possible causes:

- node hung during shutdown
- hypervisor issue
- cloud provider issue
- BIOS/firmware issue
- encrypted disk unlock issue
- filesystem corruption
- node returns with old boot deployment

Recovery:

- reboot from OS if safe
- reboot from cloud/hypervisor console
- validate node returns Ready
- validate currentConfig equals desiredConfig

```bash
oc adm cordon worker-1.example.com
oc debug node/worker-1.example.com
chroot /host
systemctl reboot
```

Use out-of-band console if SSH/debug is unavailable.

## 18. Step 13: Check Disk, Filesystem, and Permissions

MachineConfig application can fail if the node cannot write files.

```bash
oc debug node/worker-1.example.com
chroot /host
```

Check disk:

```bash
df -h
df -ih
lsblk
mount | grep ' / '
```

Check read-only filesystem:

```bash
touch /etc/test-write && rm -f /etc/test-write
```

Check SELinux denials:

```bash
ausearch -m AVC -ts recent
journalctl --no-pager | grep -i denied
```

Common issues:

- `/var` full
- inode exhaustion
- filesystem read-only
- bad permissions
- SELinux denial due to custom file placement
- immutable OS expectations violated

Fix disk pressure before retrying MCO reconciliation.

## 19. Step 14: Check Custom MCP Selector Problems

Custom MCPs are common in advanced clusters, for example:

```bash
infra
router
storage
gpu
logging
```

Check MCP selector:

```bash
oc get mcp infra -o yaml
```

Check node labels:

```bash
oc get nodes --show-labels
```

Common mistakes:

- node selected by two custom pools accidentally
- MachineConfig label does not match expected pool
- node role label missing
- custom pool created but no matching nodes
- infra node also receiving worker config unexpectedly

Example custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Check MachineConfig labels:

```bash
oc get mc --show-labels
```

MachineConfig intended for infra should have something like:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

If labels are wrong, the wrong pool may receive the wrong config.

```bash

```

On node:

```bash

chroot /host
cat /etc/containers/registries.conf

```

Symptoms:

```text
x509: certificate signed by unknown authority

no route to host
proxyconnect tcp
manifest unknown
unauthorized: authentication required
```

Fix depends on root cause:

- correct CA bundle
- fix proxy noProxy list
- fix mirror registry route/DNS
- fix pull secret
- fix disconnected registry mapping

## 21. Step 16: Pause and Resume MCP Safely

Pause worker pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

Resume:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Important:

- Pausing prevents new changes from rolling out.
- Pausing does not automatically fix degraded nodes.
- Do not leave MCP paused permanently without change control documentation.
- During upgrade, paused MCPs can block upgrade completion.

## 22. Step 17: Recover from Common Scenarios

### Scenario A: Configuration Drift

Symptom:

```text
content mismatch for file /etc/containers/registries.conf
```

Flow:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
oc debug node/<node>
chroot /host
cat /etc/containers/registries.conf
```

Fix:

- revert file to MCO expected content, or
- create proper MachineConfig for required change, or
- remove unsupported manual change

After fix:

```bash
oc delete pod -n openshift-machine-config-operator <mcd-pod>
oc get mcp worker -w
```

Deleting the MCD pod only restarts reconciliation. It is not the root fix.

---

### Scenario B: Bad MachineConfig Applied

Symptom:

```text
failed to apply machine config
failed to write file
failed to restart service
```

Flow:

```bash
oc get mc --sort-by=.metadata.creationTimestamp
oc describe mcp worker
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Fix:

```bash
oc delete mc 99-worker-bad-config
```

or:

```bash
oc apply -f corrected-machineconfig.yaml
```

Monitor:

```bash
oc get mcp worker -w
```

---

### Scenario C: Drain Blocked by PDB

Symptom:

```text
Cannot evict pod as it would violate the pod's disruption budget
```

Flow:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node>
oc get pdb -A
oc describe pdb -n <namespace> <pdb-name>
```

Fix:

- increase app replicas
- temporarily relax PDB after approval
- reschedule workload
- retry drain/reconciliation

---

### Scenario D: Node Not Returning After Reboot

Symptom:

```text
node unreachable
node not ready
currentConfig != desiredConfig
```

Flow:

```bash
oc get node <node>
oc describe node <node>
```

From console/debug:

```bash
journalctl -b -u kubelet --no-pager -n 100
journalctl -b -u crio --no-pager -n 100
rpm-ostree status
```

Fix:

- restore kubelet/CRI-O
- fix node networking
- reboot again if necessary
- replace node if unrecoverable

---

### Scenario E: Disk Full

Symptom:

```text
no space left on device
failed to write file
rpm-ostree cleanup failed
```

Flow:

```bash
df -h
df -ih
journalctl --disk-usage
du -sh /var/*
```

Safe cleanup examples:

```bash
journalctl --vacuum-time=7d
crictl images
crictl rmi --prune
rpm-ostree cleanup -m
```

Use cleanup carefully. Do not delete random directories under `/var/lib/kubelet`, `/var/lib/containers`, or `/ostree` without understanding impact.

## 24. What I Avoid Doing

In a real production cluster, I avoid:

```text
Deleting rendered MachineConfigs randomly
Deleting MCP objects
Force rebooting all nodes at once
Manually editing RHCOS files without converting changes to MachineConfig
Ignoring PDB impact
Deleting application pods without owner approval
Leaving MCP paused without tracking
Assuming node Ready means MCP healthy
Running random cleanup under /var/lib/kubelet or /ostree
```

Rendered MachineConfigs are generated objects. Manually editing them is not a proper fix.

## 25. Interview-Level Troubleshooting Script

A strong interview answer can be given like this:

> First I check `oc get mcp` to identify which pool is degraded and whether it is still updating. Then I describe the degraded MCP and check the condition message. Next, I identify the degraded node using node annotations such as `machineconfiguration.openshift.io/state`, `currentConfig`, `desiredConfig`, and `reason`. After that I check the Machine Config Operator status and logs from the Machine Config Daemon pod running on the affected node.
>
> If the reason says `unexpected on-disk state` or `content mismatch`, I treat it as configuration drift and compare the actual file on the host with the desired rendered MachineConfig. If a recent custom MachineConfig caused the issue, I validate the YAML, file mode, systemd unit, CRI-O config, kubelet config, registry config, and kernel arguments. If the issue is drain-related, I check PDBs and pods on the node. If it is reboot or OS update related, I check `rpm-ostree`, `kubelet`, `crio`, disk, registry, proxy, and certificate trust.
>
> In production, if a bad config is still rolling out, I pause the MCP to protect other nodes. Then I fix the root cause, resume the MCP, and watch until `UPDATED=True`, `UPDATING=False`, and `DEGRADED=False`. I also document the RCA because MCP degradation can block OpenShift upgrades.

## 27. Root Cause Matrix

| Symptom | Likely Cause | Where to Check | Fix |
|---|---|---|---|
| `content mismatch` | Manual host change / config drift | Node annotation, MCD logs, host file | Revert file or create proper MachineConfig |
| `failed to write file` | Bad MachineConfig, permission, disk full | MCD logs, `df -h`, MC YAML | Fix MC or disk issue |
| `failed to drain node` | PDB or stuck pod | Events, PDB, pods on node | Fix replicas/PDB/stuck pods |
| `rpm-ostree` error | OS pivot/update issue | `rpm-ostree status`, journal | Fix registry/proxy/disk/ostree issue |
| Node NotReady after update | kubelet/CRI-O/network issue | systemctl, journalctl | Fix service config/network |
| `x509` error | Registry or CA trust issue | MCD logs, node certs, image config | Fix CA bundle/mirror config |
| Pool stuck updating | Node cannot reboot/drain/apply | MCP, node annotation | Fix node-level blocker |
| Custom pool degraded | selector/label mismatch | MCP YAML, node labels, MC labels | Correct labels/selectors |

## 30. Best Practices to Prevent MCP Degradation

1. Never manually edit MCO-managed files on RHCOS nodes.
2. Manage OS-level changes through MachineConfig only.
3. Test MachineConfig in non-production first.
4. Use GitOps for MachineConfig changes.
5. Roll out custom pools in small batches when possible.
6. Keep proper PDB and workload replica design.
7. Monitor MCP and MCO conditions.
8. Avoid applying multiple risky MachineConfigs together.
9. Validate registry, proxy, and CA changes carefully.
10. Document every manual node-level emergency change.

## 31. Final Senior-Level Answer

A degraded `MachineConfigPool` means one or more nodes failed MCO reconciliation. I troubleshoot it from the pool level down to the node level. I first check `oc get mcp`, `oc describe mcp <pool>`, and `oc get co machine-config`. Then I identify the degraded node by checking node annotations for `state`, `currentConfig`, `desiredConfig`, and `reason`. After that I inspect the Machine Config Daemon pod logs on the affected node.

If the error is configuration drift, I compare the on-disk file with the rendered MachineConfig and either revert the manual change or convert it into a proper MachineConfig. If the issue is a bad custom MachineConfig, I correct or remove it. If the rollout is blocked by drain, reboot, CRI-O, kubelet, rpm-ostree, disk, proxy, registry, or certificate issues, I troubleshoot that subsystem directly.

In production, I pause the MCP if the bad change is still rolling out, fix the root cause, resume the MCP, and verify the pool returns to `UPDATED=True`, `UPDATING=False`, and `DEGRADED=False`. I also check ClusterVersion because degraded MCP commonly blocks OpenShift upgrades.
