# How do you design infra nodes for logging, router, and registry?

## Interview-Level Scenario for Advanced OpenShift Administration

**Role expectation:** Senior OpenShift Administrator / OpenShift Platform Engineer with around 10 years of production infrastructure experience.

**Scenario:**

An enterprise is running Red Hat OpenShift for multiple business-critical applications. Application teams are complaining that application workloads are affected whenever logging, ingress router, or image registry workloads consume high CPU, memory, storage I/O, or network bandwidth. The platform team asks you to design dedicated **infrastructure nodes** for OpenShift platform components such as:

- OpenShift Ingress Router
- OpenShift Image Registry
- OpenShift Logging stack
- Monitoring or other platform services if required

The interviewer asks:

> **How do you design infra nodes for logging, router, and registry?**

---

## 1. Interview Answer — High-Level Summary

In a production OpenShift cluster, I design infra nodes as a dedicated worker-node pool for platform workloads. The goal is to isolate infrastructure services such as router, registry, logging, and monitoring from application workloads. I normally create at least three infra nodes across failure domains or availability zones, label them with `node-role.kubernetes.io/infra=`, taint them to prevent normal application pods from landing there, and then configure each OpenShift component with proper `nodeSelector`, `tolerations`, resource requests, limits, storage, and anti-affinity.

For router workloads, I focus on high network throughput, HA, and external load-balancer integration. For registry workloads, I focus on persistent object storage, availability, and image pull/push performance. For logging workloads, I focus heavily on disk I/O, memory, CPU, retention, index/storage sizing, and separating collectors from storage/backend components.

I also validate the design using `oc get nodes`, `oc adm top nodes`, pod placement checks, cluster operator health, metrics, alerts, and failure testing such as draining one infra node to confirm that router, registry, and logging remain available.

---

## 2. What are infra nodes in OpenShift?

Infra nodes are OpenShift worker nodes dedicated to running cluster infrastructure workloads instead of business application workloads.

Common infra workloads include:

- Ingress router pods
- Internal image registry pods
- Monitoring stack components
- Logging stack components
- GitOps or ACM components, depending on enterprise design
- Service mesh control plane components, if separated
- Quay registry components, if deployed inside the cluster

Red Hat documents that infrastructure machine sets can be used to host only infrastructure components such as the default router, integrated image registry, and monitoring components. These nodes are not counted toward the same worker subscription calculation in applicable Red Hat subscription models, but the exact entitlement treatment should always be verified with the customer’s Red Hat subscription agreement.

Reference:

- Red Hat OpenShift documentation: creating infrastructure machine sets
- Red Hat OpenShift documentation: scheduling with node selectors, taints, and tolerations
- Red Hat OpenShift Logging documentation: scheduling logging resources

## 3. Why do we need infra nodes?

In production, router, registry, and logging are not small side components. They can create major pressure on the cluster.

### 3.1 Router pressure

Router pods handle external application traffic. If router pods compete with application pods on the same nodes, heavy ingress traffic can cause:

- CPU pressure
- Network saturation
- Packet drops
- Increased latency
- TLS termination overhead
- Application route instability

### 3.2 Registry pressure

The image registry handles image pushes and pulls. During deployments, upgrades, CI/CD pipelines, and node scaling, the registry can create:

- Network pressure
- Storage I/O pressure
- Object storage traffic
- Temporary image pull delays
- Deployment rollout delays

### 3.3 Logging pressure

Logging is often the heaviest infra workload. It can consume:

- High disk I/O
- High memory
- High CPU
- High network bandwidth
- Storage capacity
- Backend indexing capacity

If application logs suddenly increase, logging pods can affect application workloads unless they are isolated.

### 3.4 Operational separation

Infra nodes also provide operational advantages:

- Easier troubleshooting
- Better capacity planning
- Clear ownership between platform and application workloads
- Easier maintenance windows
- Reduced noisy-neighbor impact
- Better compliance and audit separation

---

## 4. Core design principles

When I design infra nodes, I follow these principles:

| Principle | Explanation |
|---|---|
| Isolation | Platform workloads should not compete with business workloads. |
| High availability | Minimum three infra nodes for production. |
| Failure-domain spread | Infra nodes should be distributed across zones/racks where possible. |
| Taints and tolerations | Prevent normal workloads from landing on infra nodes. |
| Node selectors | Explicitly place router, registry, and logging on infra nodes. |
| Sizing by workload | Router, registry, and logging have different CPU, memory, disk, and network needs. |
| Storage planning | Registry and logging require serious storage design. |
| Monitoring | Infra node utilization must be continuously monitored. |
| Upgrade safety | Infra nodes should be compatible with MachineConfigPool and cluster upgrades. |
| Drain testing | Validate that infra services survive node maintenance. |

## 5. Recommended infra node topology

### 5.1 Small production cluster

For a basic production cluster:

```text
3 control plane nodes
3 worker nodes
3 infra nodes
```

Example:

```text
master-0
master-1
master-2

worker-0
worker-1
worker-2

infra-0
infra-1
infra-2
```

### 5.2 Multi-zone production cluster

For an HA enterprise cluster:

```text
Availability Zone A: infra-0
Availability Zone B: infra-1
Availability Zone C: infra-2
```

This protects against a single zone failure.

### 5.3 Large production cluster

For larger clusters, I may separate infra workloads further:

```text
infra-router-0/1/2
infra-registry-0/1/2
infra-logging-0/1/2
infra-monitoring-0/1/2
```

This is useful when logging volume is high or router traffic is very heavy.

---

## 6. Minimum node count recommendation

For production, I do not design only one or two infra nodes.

Minimum recommended design:

```text
3 infra nodes
```

Reason:

- Router needs HA.
- Registry needs availability.
- Logging backend often needs quorum or replica distribution.
- Node drain should not break infrastructure services.
- Red Hat documentation highlights the importance of having at least three nodes available when rebooting nodes that host critical infrastructure components such as router, registry, and monitoring pods.

For non-production, two infra nodes may be acceptable, but I would clearly document the risk.

## 7. Infra node labeling strategy

Infra nodes should be labeled clearly.

### 7.1 Standard infra role label

```bash
oc label node infra-0.example.com node-role.kubernetes.io/infra=
oc label node infra-1.example.com node-role.kubernetes.io/infra=
oc label node infra-2.example.com node-role.kubernetes.io/infra=
```

Check labels:

```bash
oc get nodes -l node-role.kubernetes.io/infra=
```

Expected output:

```text
NAME                  STATUS   ROLES    AGE   VERSION
infra-0.example.com   Ready    infra    10d   v1.xx.x
infra-1.example.com   Ready    infra    10d   v1.xx.x
infra-2.example.com   Ready    infra    10d   v1.xx.x
```

### 7.2 Additional workload-specific labels

For advanced separation, I may use additional labels:

```bash
oc label node infra-0.example.com infra-role=router
oc label node infra-1.example.com infra-role=registry
oc label node infra-2.example.com infra-role=logging
```

But in most environments, I prefer a common infra pool first:

```yaml
node-role.kubernetes.io/infra: ""
```

Then I use resource sizing, anti-affinity, and replicas to balance workloads.

## 8. Infra node tainting strategy

Label alone is not enough. If I only label infra nodes, normal application workloads may still land there unless project-level default node selectors or scheduling policies prevent it.

So I normally taint infra nodes:

```bash
oc adm taint nodes infra-0.example.com node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes infra-1.example.com node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes infra-2.example.com node-role.kubernetes.io/infra=:NoSchedule
```

Check taints:

```bash
oc describe node infra-0.example.com | grep -i taints -A2
```

Expected:

```text
Taints: node-role.kubernetes.io/infra:NoSchedule
```

### Important point

If I taint infra nodes, every infrastructure workload that must run there needs a matching toleration.

Example toleration:

```yaml
tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Exists
    effect: NoSchedule
```

### Why taints are important

Taints make infra nodes reject ordinary application pods unless those pods tolerate the taint. This is the real isolation mechanism.

---

## 9. Worker node protection strategy

I also ensure application workloads prefer or require worker nodes.

Standard worker label:

```bash
oc get nodes -l node-role.kubernetes.io/worker=
```

Application namespaces can use node selectors or GitOps policies to ensure workloads run on workers only.

Example namespace annotation:

```bash
oc annotate namespace app-prod openshift.io/node-selector='node-role.kubernetes.io/worker=' --overwrite
```

This prevents accidental placement of business apps onto infra nodes.

## 10. MachineSet design for infra nodes

In IPI-based OpenShift clusters, I prefer using dedicated infrastructure MachineSets rather than manually converting random workers.

### 10.1 Why MachineSet-based infra nodes are better

MachineSets provide:

- Repeatable node creation
- Auto-replacement if a node fails
- Consistent labels
- Consistent taints
- Easier scaling
- Better GitOps control
- Zone-aware infrastructure pools

### 10.2 Example infra MachineSet concept

A MachineSet should include infra labels and taints in the machine template.

Example conceptual snippet:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: cluster01-infra-us-east-1a
  namespace: openshift-machine-api
spec:
  replicas: 1
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-cluster: cluster01
      machine.openshift.io/cluster-api-machineset: cluster01-infra-us-east-1a
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-cluster: cluster01
        machine.openshift.io/cluster-api-machineset: cluster01-infra-us-east-1a
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
      taints:
        - key: node-role.kubernetes.io/infra
          value: ""
          effect: NoSchedule
      providerSpec:
        value:
          # Cloud-specific provider configuration goes here
```

In real projects, I copy an existing worker MachineSet and modify:

- Name
- Labels
- Taints
- Instance type
- Availability zone
- Disk size
- Replicas

### 10.3 Three MachineSets across zones

Example:

```text
cluster01-infra-zone-a replicas: 1
cluster01-infra-zone-b replicas: 1
cluster01-infra-zone-c replicas: 1
```

This gives three infra nodes across three zones.

## 11. MachineConfigPool for infra nodes

If infra nodes need separate OS-level tuning, I create a separate MachineConfigPool.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

This allows infra-specific MachineConfig tuning if needed.

Use cases:

- Custom sysctl tuning
- Log storage mount tuning
- Kernel parameters
- CRI-O tuning
- Registry/cache tuning
- Huge network workload tuning

However, I avoid unnecessary custom MachineConfigs because they increase upgrade and reboot complexity.

## 12. Designing router placement on infra nodes

The OpenShift router is managed by the Ingress Operator.

Default namespace:

```text
openshift-ingress
```

Default deployment:

```text
router-default
```

Check current router pods:

```bash
oc get pods -n openshift-ingress -o wide
```

### 12.1 Configure router node placement

Edit the default IngressController:

```bash
oc edit ingresscontroller default -n openshift-ingress-operator
```

Example configuration:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  replicas: 3
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

### 12.2 Verify router placement

```bash
oc get pods -n openshift-ingress -o wide
```

Expected:

```text
NAME                              READY   STATUS    NODE
router-default-xxxxx              1/1     Running   infra-0.example.com
router-default-yyyyy              1/1     Running   infra-1.example.com
router-default-zzzzz              1/1     Running   infra-2.example.com
```

### 12.3 Router sizing considerations

For router nodes, I consider:

- Number of routes
- TLS termination volume
- Requests per second
- Concurrent connections
- WebSocket traffic
- Large file uploads
- External load balancer health checks
- East-west and north-south network traffic
- Network interface bandwidth

### 12.4 Router HA design

Recommended:

```yaml
spec:
  replicas: 3
```

If there are three infra nodes, I want one router pod per infra node where possible.

### 12.5 Router anti-affinity

The Ingress Operator usually manages placement, but from a design point of view I want router replicas spread across infra nodes. I verify this manually:

```bash
oc get pods -n openshift-ingress -o wide
```

If multiple router pods land on the same infra node, I check:

```bash
oc describe pod <router-pod> -n openshift-ingress
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get nodes --show-labels
```

### 12.6 Router interview statement

I would say:

> I place router pods on infra nodes using the IngressController `nodePlacement` field. I run at least three replicas in production and spread infra nodes across zones. Since router is network-sensitive, I size infra nodes for CPU and network throughput, not only memory. I also validate external load-balancer health checks, route availability, and failover by draining one infra node.

## 13. Designing image registry placement on infra nodes

The OpenShift image registry is managed by the Cluster Image Registry Operator.

Namespace:

```text
openshift-image-registry
```

Check registry pods:

```bash
oc get pods -n openshift-image-registry -o wide
```

Check registry operator config:

```bash
oc get configs.imageregistry.operator.openshift.io cluster -o yaml
```

### 13.1 Configure registry node selector and toleration

Patch the registry configuration:

```bash
oc patch configs.imageregistry.operator.openshift.io cluster --type=merge -p '{
  "spec": {
    "nodeSelector": {
      "node-role.kubernetes.io/infra": ""
    },
    "tolerations": [
      {
        "key": "node-role.kubernetes.io/infra",
        "operator": "Exists",
        "effect": "NoSchedule"
      }
    ]
  }
}'
```

Verify:

```bash
oc get pods -n openshift-image-registry -o wide
```

### 13.2 Registry replica design

For production:

```bash
oc patch configs.imageregistry.operator.openshift.io cluster --type=merge -p '{"spec":{"replicas":3}}'
```

Then verify:

```bash
oc get deployment image-registry -n openshift-image-registry
oc get pods -n openshift-image-registry -o wide
```

### 13.3 Registry storage design

Registry storage should not be treated casually.

Preferred production options:

- Cloud object storage such as S3, Azure Blob, GCS, or compatible object storage
- OpenShift Data Foundation object storage
- External enterprise object storage

Avoid for production unless specifically justified:

- Ephemeral storage
- Single-node local storage
- Non-HA NFS without proper support and performance validation

### 13.4 Registry resource considerations

For registry, I check:

- Image push/pull frequency
- CI/CD pipeline concurrency
- Number of nodes pulling images during rollout
- Image size
- Pruning policy
- Storage backend latency
- Network throughput
- TLS and route exposure if registry is exposed externally

### 13.5 Registry interview statement

I would say:

> I schedule the integrated image registry onto infra nodes using the Image Registry Operator configuration. I configure multiple replicas and use highly available object storage. I avoid local single-node registry storage in production because registry availability directly affects image pulls, deployments, builds, and cluster recovery.

## 14. Designing logging placement on infra nodes

Logging requires special attention because it is not just one pod. It normally has collectors and backend components.

Depending on OpenShift version and logging stack, components may include:

- Collector: Vector or Fluentd
- Log storage/backend: LokiStack or Elasticsearch in older deployments
- Visualization: OpenShift console plugin, Kibana in older stacks, or Grafana integration
- Gateway or query frontend components

### 14.1 Important logging design point

Log collectors are usually DaemonSets and often run on many or all nodes because they need to collect logs from workloads running across the cluster.

So I do not blindly move every logging component only to infra nodes.

Correct design:

| Logging component | Placement approach |
|---|---|
| Collector DaemonSet | Usually runs on all workload nodes or selected node groups. |
| Logging backend | Place on infra/logging nodes. |
| Query/frontend/gateway | Place on infra nodes. |
| Visualization components | Place on infra nodes. |

### 14.2 OpenShift Logging scheduling options

OpenShift Logging supports scheduling resources using:

- Node selectors
- Taints and tolerations
- Affinity and anti-affinity

This is important when designing logging infra nodes.

### 14.3 LokiStack example placement

Example conceptual LokiStack configuration:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  size: 1x.extra-small
  storage:
    schemas:
      - version: v13
        effectiveDate: "2024-04-01"
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: gp3-csi
  tenants:
    mode: openshift-logging
  template:
    compactor:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Exists
          effect: NoSchedule
    distributor:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Exists
          effect: NoSchedule
    ingester:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Exists
          effect: NoSchedule
    querier:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Exists
          effect: NoSchedule
    queryFrontend:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Exists
          effect: NoSchedule
```

Actual fields can vary by OpenShift Logging and Loki Operator version, so I always verify with:

```bash
oc explain lokistack.spec.template
oc get crd lokistacks.loki.grafana.com -o yaml
```

### 14.4 ClusterLogging example placement

For older or operator-managed logging resources, the `ClusterLogging` custom resource may support node selector and toleration placement depending on version.

Example concept:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogging
metadata:
  name: instance
  namespace: openshift-logging
spec:
  managementState: Managed
  collection:
    type: vector
  logStore:
    type: lokistack
    lokistack:
      name: logging-loki
  visualization:
    type: ocp-console
```

For exact placement fields, I check the installed CRD:

```bash
oc explain clusterlogging.spec
oc explain clusterlogging.spec.collection
oc explain clusterlogging.spec.visualization
```

### 14.5 Logging sizing considerations

Logging sizing depends on:

- Logs generated per day
- Retention requirement
- Number of namespaces
- Number of pods
- Application log verbosity
- Audit log collection
- Infrastructure log collection
- Query frequency
- Index/chunk storage model
- Compression ratio
- Peak ingestion rate
- Storage backend performance

### 14.6 Logging storage calculation example

Example:

```text
Daily log volume: 300 GB/day
Retention: 14 days
Compression estimate: 50%
Replication/overhead: 1.5x
```

Approximate storage:

```text
300 GB x 14 days = 4200 GB raw
4200 GB x 0.5 compression = 2100 GB
2100 GB x 1.5 overhead = 3150 GB
```

So I would plan around:

```text
3.5 TB or more usable storage
```

I would also add growth buffer:

```text
Final planned capacity: 4 TB to 5 TB usable
```

### 14.7 Logging node design

For heavy logging, I may create dedicated logging infra nodes:

```text
infra-logging-0
infra-logging-1
infra-logging-2
```

Labels:

```bash
oc label node infra-logging-0.example.com node-role.kubernetes.io/infra=
oc label node infra-logging-0.example.com infra.openshift.io/logging=true
```

Taint:

```bash
oc adm taint node infra-logging-0.example.com infra.openshift.io/logging=true:NoSchedule
```

Then logging backend pods must tolerate:

```yaml
tolerations:
  - key: infra.openshift.io/logging
    operator: Equal
    value: "true"
    effect: NoSchedule
```

This gives stronger isolation than a shared infra pool.

### 14.8 Logging interview statement

I would say:

> For logging, I do not simply say ‘move logging to infra nodes’. I first separate collectors from backend components. Collectors usually run as DaemonSets on nodes where logs are generated, while Loki or Elasticsearch backend, query, gateway, and visualization components are placed on infra or dedicated logging nodes. I size logging nodes based on daily ingest, retention, query load, and storage I/O.

## 15. Combined design for router, registry, and logging

### 15.1 Shared infra pool design

This is common for medium environments.

```text
infra-0: router + registry + logging backend
infra-1: router + registry + logging backend
infra-2: router + registry + logging backend
```

Pros:

- Simple
- Cost-effective
- Easy to manage
- Good for moderate traffic

Cons:

- Logging can affect router and registry if under-sized
- Scaling one infra function means scaling all infra capacity

### 15.2 Dedicated infra pool design

For large environments:

```text
router-infra nodes:   3 nodes
registry-infra nodes: 3 nodes
logging-infra nodes:  3 nodes
```

Pros:

- Strong isolation
- Better performance predictability
- Easier capacity planning
- Logging cannot impact ingress

Cons:

- Higher cost
- More nodes to patch and monitor
- More MachineSets and labels to manage

### 15.3 My practical recommendation

For most production clusters, I start with:

```text
3 shared infra nodes
```

Then I separate logging if:

- Log volume is high
- Disk I/O is high
- Logging queries are heavy
- Retention is long
- Router latency is affected
- Registry image pulls become slow

## 16. Example sizing approach

### 16.1 Small production

```text
Infra nodes: 3
CPU per node: 8 vCPU
Memory per node: 32 GB
Disk: 120 GB OS + storage as required
Network: 10 Gbps preferred
```

Suitable for:

- Moderate route traffic
- Moderate registry usage
- External object storage
- Light to medium logging

### 16.2 Medium production

```text
Infra nodes: 3
CPU per node: 16 vCPU
Memory per node: 64 GB
Disk: 120 GB OS + fast storage for logging if needed
Network: 10 Gbps or better
```

Suitable for:

- Multiple application teams
- CI/CD usage
- Medium logging
- Higher route count

### 16.3 Large production

```text
Router infra:   3 nodes, 8-16 vCPU, 32-64 GB RAM, high network
Registry infra: 3 nodes, 8-16 vCPU, 32-64 GB RAM, object storage
Logging infra:  3+ nodes, 16-32 vCPU, 64-128 GB RAM, high IOPS storage
```

Suitable for:

- Enterprise multi-tenant clusters
- High logging ingestion
- Heavy route traffic
- Strict performance isolation

### 16.4 Important sizing warning

There is no universal sizing. I always collect:

```bash
oc adm top nodes
oc adm top pods -A
oc get --raw /api/v1/nodes/<node-name>/proxy/stats/summary
```

And review Prometheus metrics for:

- CPU usage
- Memory working set
- Network transmit/receive
- Disk I/O
- Filesystem usage
- Pod restarts
- Throttling
- Ingress request rate
- Registry HTTP metrics
- Logging ingestion metrics

## 17. Resource requests and limits

Scheduling infra pods to infra nodes is not enough. I also check resource requests and limits.

### 17.1 Why requests matter

Requests help the scheduler reserve resources.

If router, registry, and logging have no meaningful requests, the scheduler may overpack infra nodes.

### 17.2 Why limits must be used carefully

Limits can prevent runaway usage, but very tight CPU limits can cause throttling.

For router and logging, CPU throttling can directly affect:

- Request latency
- Log ingestion delay
- Query timeout
- Image pull/push performance

### 17.3 Check pod resources

```bash
oc get pods -n openshift-ingress -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{.spec.containers[*].resources}{"\n\n"}{end}'

oc get pods -n openshift-image-registry -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{.spec.containers[*].resources}{"\n\n"}{end}'

oc get pods -n openshift-logging -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{.spec.containers[*].resources}{"\n\n"}{end}'
```

## 18. Storage design

### 18.1 Router storage

Router pods usually do not require persistent storage, but they require:

- Stable scheduling
- Network performance
- HA replicas
- Load balancer integration

### 18.2 Registry storage

Registry requires durable storage.

Production options:

```text
Object storage > HA shared storage > single-node local storage
```

I prefer object storage.

### 18.3 Logging storage

Logging backend storage needs:

- High write throughput
- High read/query performance
- Retention capacity
- Backup or replication strategy
- Lifecycle management

For Loki, object storage is commonly used for log chunks. For Elasticsearch-based logging, fast block storage is critical.

---

## 19. Network design

Infra nodes must have reliable and high-performance networking.

### 19.1 Router network

Router nodes need:

- Load balancer connectivity
- External DNS integration
- Firewall rules
- TLS termination capacity
- North-south traffic bandwidth

### 19.2 Registry network

Registry nodes need:

- Fast internal cluster connectivity
- Object storage connectivity
- CI/CD pipeline access
- Image pull/push capacity

### 19.3 Logging network

Logging nodes need:

- Log collector traffic from worker nodes
- Backend storage traffic
- Query traffic
- Possible external SIEM forwarding

---

## 20. Security design

Infra nodes are sensitive because they host platform services.

Security controls:

- Restrict SSH access
- Use bastion/jump host
- Enable audit logging
- Use least-privilege RBAC
- Restrict who can edit Operators and infra placement
- Use NetworkPolicy where applicable
- Protect registry credentials
- Secure object storage credentials
- Secure logging backend access
- Use TLS for external integrations

## 21. Monitoring and alerting

I monitor infra nodes separately.

### 21.1 Node-level checks

```bash
oc adm top nodes
oc describe node <infra-node>
oc get nodes -l node-role.kubernetes.io/infra=
```

Watch for:

- MemoryPressure
- DiskPressure
- PIDPressure
- Network saturation
- Filesystem full
- Kubelet issues
- CRI-O issues

### 21.2 Pod-level checks

```bash
oc adm top pods -n openshift-ingress
oc adm top pods -n openshift-image-registry
oc adm top pods -n openshift-logging
```

### 21.3 Cluster operator checks

```bash
oc get co
oc describe co ingress
oc describe co image-registry
oc get clusteroperator logging
```

## 24. Common mistakes

### Mistake 1: Only labeling nodes but not tainting them

This does not fully protect infra nodes from application workloads.

### Mistake 2: Tainting infra nodes without adding tolerations

Result: router, registry, or logging pods may remain Pending.

Troubleshoot:

```bash
oc describe pod <pod-name> -n <namespace>
```

Look for:

```text
node(s) had untolerated taint
```

### Mistake 3: Running only one router replica

This creates a single point of failure.

### Mistake 4: Using weak storage for registry

Registry storage failure can break image pulls and deployments.

### Mistake 5: Treating logging as a small workload

Logging can become one of the largest consumers of storage and I/O.

### Mistake 6: Putting all infra components on under-sized nodes

Router latency, registry slowness, and logging delay may all appear together.

### Mistake 7: Not testing node drain

A design that has not been drain-tested is not production-validated.

## 25. Troubleshooting scenarios

### 25.1 Router pods are Pending after moving to infra nodes

Check:

```bash
oc describe pod <router-pod> -n openshift-ingress
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get nodes -l node-role.kubernetes.io/infra=
oc describe node <infra-node> | grep -i taints -A2
```

Likely causes:

- Missing infra label
- Missing toleration
- Wrong node selector
- Insufficient CPU or memory
- Infra nodes NotReady

### 25.2 Registry pods are not moving to infra nodes

Check:

```bash
oc get configs.imageregistry.operator.openshift.io cluster -o yaml
oc get pods -n openshift-image-registry -o wide
oc describe pod <registry-pod> -n openshift-image-registry
```

Likely causes:

- Operator config not patched correctly
- Deployment not rolled out yet
- Missing toleration
- Wrong node selector

Restart rollout if needed:

```bash
oc rollout restart deployment/image-registry -n openshift-image-registry
```

### 25.3 Logging backend is Pending

Check:

```bash
oc get pods -n openshift-logging -o wide
oc describe pod <logging-pod> -n openshift-logging
oc get pvc -n openshift-logging
oc get sc
```

Likely causes:

- StorageClass issue
- PVC Pending
- Missing toleration
- Wrong node selector
- Insufficient CPU/memory
- Zone mismatch between pod and volume

### 25.4 Application pods are running on infra nodes

Check:

```bash
oc get pods -A -o wide | grep infra
```

Fix:

- Add taints to infra nodes
- Add namespace node selectors for application namespaces
- Review workload tolerations
- Review GitOps templates

## 27. Real interview-style answer

If I am answering in an interview, I would say:

> I design infra nodes as a dedicated, highly available node pool for OpenShift platform components. First, I create at least three infra nodes across availability zones using dedicated MachineSets. I label them with `node-role.kubernetes.io/infra=` and taint them with `node-role.kubernetes.io/infra=:NoSchedule` so normal application pods cannot run there.
>
> Then I move the router using the IngressController `nodePlacement` configuration with node selector and toleration. I usually run three router replicas and validate external load balancer health and route failover.
>
> For the image registry, I configure the Image Registry Operator with infra node selector and toleration, run multiple replicas, and use highly available object storage. I do not depend on single-node local storage for production registry.
>
> For logging, I separate collectors from backend components. Collectors may need to run on all nodes because they collect logs from application nodes, but logging backend components like Loki ingesters, queriers, distributors, compactors, gateways, or Elasticsearch nodes should run on infra or dedicated logging nodes. I size logging based on daily log volume, retention, query load, and storage I/O.
>
> Finally, I validate the design using pod placement checks, cluster operator health, metrics, alerts, and drain testing. A good infra-node design must survive one infra node failure without breaking routes, registry, or logging.

## 29. Key points to remember for interviews

- Infra nodes are for platform workloads, not application workloads.
- Use both labels and taints.
- Labels attract selected workloads; taints repel unwanted workloads.
- Router is network-sensitive.
- Registry is storage and availability-sensitive.
- Logging is CPU, memory, storage, and I/O-sensitive.
- Minimum three infra nodes are recommended for production HA.
- Use MachineSets for repeatable infra node creation.
- Use node selectors and tolerations in Operators.
- Collectors may still run on worker nodes; logging backend should run on infra/logging nodes.
- Always validate by draining one infra node.
- Monitor infra nodes separately.

## 30. Final conclusion

A mature infra-node design in OpenShift is not just about adding three extra workers. It is about creating a controlled platform workload layer. Router, registry, and logging are critical services, and if they are not isolated properly, they can impact application performance and cluster stability.

My design approach is:

```text
Create dedicated infra MachineSets
Label infra nodes
Taint infra nodes
Configure router placement
Configure registry placement
Configure logging backend placement
Size nodes based on workload
Use HA storage
Monitor continuously
Test failover with node drain
```

This is the kind of answer expected from an experienced OpenShift administrator because it covers architecture, implementation, operations, troubleshooting, and production validation.
