# OpenShift Login Failed After LDAP Integration — Interview-Level Troubleshooting Scenario

> **Role level:** Advanced OpenShift Administrator / Senior Platform Engineer  
> **Experience expectation:** 10+ years Linux, Kubernetes, OpenShift, Identity Provider, LDAP, TLS, RBAC, and production troubleshooting  
> **Scenario type:** Real production incident + interview explanation  

---

## 1. Scenario Statement

You integrated an enterprise LDAP server with OpenShift OAuth. After applying the LDAP identity provider configuration, users are unable to log in to the OpenShift web console or CLI.

Example symptoms:

```bash
oc login -u rakesh
Authentication required for https://api.ocp.example.com:6443 (openshift)
Username: rakesh
Password:
Login failed (401 Unauthorized)
```

Or from the console:

```text
Invalid login or password
```

Or after LDAP configuration:

```text
The configured identity provider is not shown on the login page
```

Or OAuth operator becomes degraded:

```bash
oc get co authentication
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED
authentication   4.x.x     False       True          True
```

As a senior OpenShift administrator, the goal is not to randomly edit OAuth YAML. The correct approach is to isolate whether the issue is in:

1. OpenShift OAuth configuration
2. Secret or ConfigMap reference
3. LDAP URL/search filter/base DN
4. Bind DN or bind password
5. LDAP user attribute mapping
6. TLS/CA certificate trust
7. Network/DNS/firewall connectivity
8. OAuth pod rollout/operator issue
9. User and identity mapping conflict
10. RBAC access after successful authentication

## 2. How OpenShift LDAP Login Works Internally

Before troubleshooting, explain the flow clearly in an interview.

```text
User / oc CLI / Web Console
        |
        v
OpenShift OAuth Server
        |
        v
OAuth Custom Resource: oauth/cluster
        |
        v
LDAP Identity Provider Configuration
        |
        v
LDAP Server Search + Bind
        |
        v
LDAP user attributes mapped to OpenShift identity
        |
        v
OpenShift User + Identity object created or reused
        |
        v
Token issued
        |
        v
User accesses API according to RBAC
```

Important point:

Authentication and authorization are different.

| Area | Meaning |
|---|---|
| Authentication | Can the user prove identity using LDAP username/password? |
| Identity mapping | Can OpenShift map LDAP result to an OpenShift identity/user? |
| Authorization | After login, does the user have RBAC permission? |

A user may authenticate successfully but still see permission errors such as:

```text
Error from server (Forbidden): users "rakesh" cannot list projects
```

That is not an LDAP login failure. That is RBAC.

## 3. First Rule: Keep Break-Glass Access

Never troubleshoot LDAP login by relying only on LDAP users. Before changing OAuth, ensure you still have emergency access.

Check current user:

```bash
oc whoami
```

Check whether `kubeadmin` still works:

```bash
oc login -u kubeadmin -p '<password>' https://api.ocp.example.com:6443
```

If your organization disabled `kubeadmin`, ensure at least one existing cluster-admin user still has a valid token/session.

Check cluster-admin bindings:

```bash
oc get clusterrolebinding -o wide | grep cluster-admin
```

Interview point:

> I never make identity-provider changes without a validated break-glass account because a wrong LDAP configuration can lock out administrators.

## 5. Inspect OAuth Configuration

OpenShift LDAP identity provider is configured in the cluster-wide OAuth custom resource.

```bash
oc get oauth cluster -o yaml
```

Focus on:

```yaml
spec:
  identityProviders:
  - name: ldap-provider
    mappingMethod: claim
    type: LDAP
    ldap:
      url: ldaps://ldap.example.com:636/ou=People,dc=example,dc=com?uid
      bindDN: cn=openshift-bind,ou=ServiceAccounts,dc=example,dc=com
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
      attributes:
        id:
        - uid
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
```

Validate these items:

| Field | What to verify |
|---|---|
| `name` | Unique identity provider name; do not keep changing it casually |
| `type` | Must be `LDAP` |
| `mappingMethod` | Usually `claim`; avoid conflict unless you understand identity mapping |
| `ldap.url` | Correct scheme, host, port, base DN, attribute, and filter |
| `bindDN` | Correct service-account DN |
| `bindPassword.name` | Secret exists in `openshift-config` namespace |
| `ca.name` | ConfigMap exists in `openshift-config` namespace if using custom CA |
| `attributes.id` | Stable unique LDAP attribute |
| `attributes.preferredUsername` | Username shown/used in OpenShift |

## 6. Validate Secret Reference

The LDAP bind password must be stored in a Secret in the `openshift-config` namespace.

Check secret:

```bash
oc get secret ldap-bind-password -n openshift-config
```

Check expected key:

```bash
oc get secret ldap-bind-password -n openshift-config -o jsonpath='{.data}'
```

The key must normally be:

```text
bindPassword
```

Decode and verify only from a secure admin terminal:

```bash
oc get secret ldap-bind-password -n openshift-config \
  -o jsonpath='{.data.bindPassword}' | base64 -d; echo
```

Recreate if wrong:

```bash
oc delete secret ldap-bind-password -n openshift-config

oc create secret generic ldap-bind-password \
  --from-literal=bindPassword='CorrectPasswordHere' \
  -n openshift-config
```

Common mistakes:

| Mistake | Result |
|---|---|
| Secret created in wrong namespace | Identity provider ignored or OAuth degraded |
| Key named `password` instead of `bindPassword` | OAuth cannot read bind password |
| Wrong bind password | LDAP invalid credentials |
| Password contains shell-special characters and was not quoted | Wrong secret value stored |

Interview point:

> In OpenShift 4, the Secret referenced by the OAuth LDAP provider must be in `openshift-config`, and the expected key is `bindPassword`.

## 7. Validate CA ConfigMap for LDAPS or StartTLS

If LDAP uses a private CA, OpenShift must trust that CA.

Check ConfigMap:

```bash
oc get configmap ldap-ca -n openshift-config -o yaml
```

Expected key:

```yaml
data:
  ca.crt: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

If missing or wrong, recreate:

```bash
oc delete configmap ldap-ca -n openshift-config

oc create configmap ldap-ca \
  --from-file=ca.crt=/path/to/ldap-ca.crt \
  -n openshift-config
```

Check certificate:

```bash
openssl x509 -in /path/to/ldap-ca.crt -noout -subject -issuer -dates
```

Test LDAP TLS from an admin host:

```bash
openssl s_client -connect ldap.example.com:636 -showcerts -CAfile /path/to/ldap-ca.crt
```

Look for:

```text
Verify return code: 0 (ok)
```

Common TLS errors:

| Error | Meaning | Fix |
|---|---|---|
| `x509: certificate signed by unknown authority` | CA not trusted | Create correct `ca.crt` ConfigMap |
| `certificate has expired` | LDAP server certificate expired | Renew LDAP certificate |
| `certificate is valid for ldap01, not ldap.example.com` | SAN/CN mismatch | Use correct LDAP hostname or reissue cert |
| `unknown ca` | Wrong CA chain | Use full issuing CA chain |

Important:

For production, prefer `ldaps://` or StartTLS. Avoid insecure LDAP unless explicitly accepted by security architecture.

## 8. Validate LDAP Server Connectivity from Cluster Network

A login failure can be caused by network/firewall/DNS issues, not LDAP configuration.

Check DNS from a debug pod:

```bash
oc run ldap-debug -n default --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi \
  -- bash
```

Inside pod:

```bash
dnf install -y openldap-clients bind-utils nc openssl

nslookup ldap.example.com
nc -vz ldap.example.com 389
nc -vz ldap.example.com 636
```

If `nc` fails:

```text
Ncat: Connection timed out
```

Check:

1. Firewall between OpenShift nodes and LDAP server
2. Security groups / ACLs
3. DNS resolution
4. Proxy rules
5. Routing
6. LDAP server listener ports

From OpenShift node:

```bash
oc debug node/<node-name>
chroot /host
getent hosts ldap.example.com
nc -vz ldap.example.com 636
```

Why node-level test matters:

The OAuth pods run on cluster nodes. LDAP must be reachable from where OAuth pods are scheduled, not only from your laptop.

## 9. Validate LDAP Bind Manually

Use `ldapsearch` to test the same bind DN, same password, same base DN, and same user attribute used by OpenShift.

For LDAPS:

```bash
LDAPTLS_CACERT=/path/to/ldap-ca.crt ldapsearch -x \
  -H ldaps://ldap.example.com:636 \
  -D "cn=openshift-bind,ou=ServiceAccounts,dc=example,dc=com" \
  -W \
  -b "ou=People,dc=example,dc=com" \
  "(uid=rakesh)" uid cn mail
```

For LDAP with StartTLS:

```bash
LDAPTLS_CACERT=/path/to/ldap-ca.crt ldapsearch -x -ZZ \
  -H ldap://ldap.example.com:389 \
  -D "cn=openshift-bind,ou=ServiceAccounts,dc=example,dc=com" \
  -W \
  -b "ou=People,dc=example,dc=com" \
  "(uid=rakesh)" uid cn mail
```

Expected result:

```text
# rakesh, People, example.com
dn: uid=rakesh,ou=People,dc=example,dc=com
uid: rakesh
cn: Rakesh Kumar Jha
mail: rakesh@example.com
```

If no result:

```text
# numEntries: 0
```

Then OpenShift will also fail because the user cannot be found.

Common LDAP search errors:

| LDAP Error | Meaning | Fix |
|---|---|---|
| `Invalid credentials (49)` | Wrong bind DN or password | Correct Secret or bind DN |
| `No such object (32)` | Wrong base DN | Correct LDAP URL base DN |
| `Invalid DN syntax (34)` | DN format issue | Fix bindDN/baseDN escaping |
| `Insufficient access (50)` | Bind user cannot search directory | Grant LDAP read permission |
| `Can't contact LDAP server` | Network/TLS/DNS problem | Fix connectivity or certificate |

## 10. Understand OpenShift LDAP URL Format

OpenShift LDAP URL is not just hostname. It includes the search base and attribute.

General format:

```text
ldap://host:port/baseDN?attribute?scope?filter
ldaps://host:port/baseDN?attribute?scope?filter
```

Example:

```yaml
url: ldaps://ldap.example.com:636/ou=People,dc=example,dc=com?uid
```

Meaning:

| Part | Meaning |
|---|---|
| `ldaps://ldap.example.com:636` | LDAP server endpoint |
| `ou=People,dc=example,dc=com` | Search base DN |
| `uid` | Attribute used to search username |

If users log in with email address:

```yaml
url: ldaps://ldap.example.com:636/ou=People,dc=example,dc=com?mail
```

If users log in with sAMAccountName in Active Directory:

```yaml
url: ldaps://ad.example.com:636/DC=example,DC=com?sAMAccountName
```

With filter:

```yaml
url: ldaps://ad.example.com:636/DC=example,DC=com?sAMAccountName?sub?(objectClass=user)
```

Active Directory example:

```yaml
ldap:
  url: ldaps://ad.example.com:636/DC=example,DC=com?sAMAccountName?sub?(memberOf=CN=OpenShift-Users,OU=Groups,DC=example,DC=com)
```

Common mistake:

```yaml
url: ldaps://ldap.example.com:636
```

This is incomplete because it does not define where and how to search users.

## 11. Validate Attribute Mapping

OpenShift needs LDAP attributes to create identity and user records.

Example:

```yaml
attributes:
  id:
  - uid
  email:
  - mail
  name:
  - cn
  preferredUsername:
  - uid
```

Check that LDAP actually returns those attributes:

```bash
ldapsearch -x -H ldaps://ldap.example.com:636 \
  -D "cn=openshift-bind,ou=ServiceAccounts,dc=example,dc=com" \
  -W \
  -b "ou=People,dc=example,dc=com" \
  "(uid=rakesh)" uid cn mail entryUUID
```

For 389 Directory Server / OpenLDAP, common attributes:

```text
uid
cn
mail
entryUUID
```

For Active Directory, common attributes:

```text
sAMAccountName
cn
mail
objectGUID
userPrincipalName
```

Senior recommendation:

| Mapping | Recommendation |
|---|---|
| `id` | Use a stable unique value like `entryUUID`, `objectGUID`, or `uid` if stable |
| `preferredUsername` | Use human login name like `uid` or `sAMAccountName` |
| `email` | Use `mail` |
| `name` | Use `cn` or `displayName` |

Risk:

If `preferredUsername` changes, the visible OpenShift username can change. If `id` changes, OpenShift may treat the same person as a different identity.

## 12. Check Identity Provider Is Actually Honored

If OAuth references a missing Secret or ConfigMap, the identity provider might not be honored.

Check login page providers:

```bash
oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}'
```

Open in browser:

```text
https://oauth-openshift.apps.<cluster-domain>/oauth/authorize
```

Also check OAuth logs:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300 | egrep -i "ldap|provider|secret|configmap|x509|bind|error"
```

If provider is missing from console login page, check:

```bash
oc get oauth cluster -o yaml
oc get secret -n openshift-config
oc get configmap -n openshift-config
oc describe co authentication
```

Likely causes:

1. Wrong namespace for Secret/ConfigMap
2. Wrong key name
3. Invalid CA bundle
4. Invalid YAML structure
5. OAuth operator has not rolled out new config yet

## 13. Force OAuth Rollout Only After Config Validation

Normally, the authentication operator rolls out OAuth pods automatically after OAuth config changes.

Check rollout:

```bash
oc get pods -n openshift-authentication -w
```

Check deployment:

```bash
oc rollout status deployment/oauth-openshift -n openshift-authentication
```

If config is correct but pods are stale, restart OAuth deployment carefully:

```bash
oc rollout restart deployment/oauth-openshift -n openshift-authentication
oc rollout status deployment/oauth-openshift -n openshift-authentication
```

Do not restart OAuth blindly. First validate the configuration.

## 14. Test CLI Login Correctly

Use provider username format expected by LDAP URL.

If LDAP URL uses `uid`:

```bash
oc login https://api.ocp.example.com:6443 -u rakesh
```

If LDAP URL uses `mail`:

```bash
oc login https://api.ocp.example.com:6443 -u rakesh@example.com
```

If using Active Directory `sAMAccountName`:

```bash
oc login https://api.ocp.example.com:6443 -u rakesh
```

Run with verbose logging:

```bash
oc login https://api.ocp.example.com:6443 -u rakesh --loglevel=8
```

Useful observation:

`oc login` does not directly bind to LDAP. It talks to OpenShift OAuth. OAuth talks to LDAP.

## 15. Check User and Identity Objects

After successful LDAP authentication, OpenShift creates User and Identity objects.

Check users:

```bash
oc get users
```

Check identities:

```bash
oc get identities
```

Example:

```text
ldap-provider:rakesh
```

Inspect:

```bash
oc get identity ldap-provider:rakesh -o yaml
oc get user rakesh -o yaml
```

Possible issue:

```text
username already exists and is mapped to another identity
```

This can happen if:

1. User previously logged in using HTPasswd
2. Same username exists from another identity provider
3. Mapping method is `claim` and identity conflict exists
4. Provider name changed and created a new identity prefix

Check mapping:

```bash
oc get user rakesh -o yaml
```

Look for:

```yaml
identities:
- ldap-provider:rakesh
```

If wrong identity mapping exists, fix carefully.

Example delete old identity only after confirmation:

```bash
oc delete identity old-provider:rakesh
```

Do not delete users/identities randomly in production. Confirm impact, audit, and backup YAML first:

```bash
oc get user rakesh -o yaml > user-rakesh-backup.yaml
oc get identity old-provider:rakesh -o yaml > identity-rakesh-backup.yaml
```

## 16. Understand Mapping Methods

OpenShift identity providers support mapping behavior that controls how external identities map to OpenShift users.

Common mapping methods:

| Method | Meaning | Use case |
|---|---|---|
| `claim` | Provision user with claimed username if not already mapped | Common default choice |
| `lookup` | Only allow login if identity already exists | Strict pre-provisioned environments |
| `generate` | Generate unique username if conflict exists | Avoid username conflicts |
| `add` | Add identity to existing user if username exists | Migration scenarios; use carefully |

Example:

```yaml
mappingMethod: claim
```

Senior interview point:

> If the LDAP bind is successful but login still fails, I check identity mapping conflicts. The problem may not be LDAP at all; it may be OpenShift user/identity association.

## 17. Check RBAC After Login

If login succeeds but user cannot see projects, it is an authorization issue.

Check current user:

```bash
oc whoami
```

Check permissions:

```bash
oc auth can-i get pods
oc auth can-i list projects
oc auth can-i create pods -n dev
```

Grant project access:

```bash
oc adm policy add-role-to-user view rakesh -n dev
```

Grant admin to namespace:

```bash
oc adm policy add-role-to-user admin rakesh -n dev
```

Grant cluster-admin only if approved:

```bash
oc adm policy add-cluster-role-to-user cluster-admin rakesh
```

Check group-based RBAC:

```bash
oc get groups
oc describe group openshift-admins
```

Important:

LDAP authentication does not automatically sync LDAP groups unless LDAP group sync is configured separately.

## 18. LDAP Group Sync Is Separate From LDAP Login

A common interview trap:

> “I integrated LDAP, but my LDAP groups are not visible in OpenShift.”

LDAP login and LDAP group sync are different.

LDAP identity provider authenticates users.
LDAP group sync imports LDAP group membership into OpenShift Group objects.

Check groups:

```bash
oc get groups
```

Sync groups example:

```bash
oc adm groups sync --sync-config=ldap-group-sync.yaml --confirm
```

Then bind group to role:

```bash
oc adm policy add-cluster-role-to-group cluster-admin openshift-admins
```

Or namespace admin:

```bash
oc adm policy add-role-to-group admin dev-team -n dev
```

## 19. Common Root Causes and Fixes

| Symptom | Likely Cause | Troubleshooting Command | Fix |
|---|---|---|---|
| Provider not visible on login page | OAuth config invalid | `oc describe co authentication` | Fix OAuth YAML |
| OAuth degraded | Missing Secret/ConfigMap | `oc logs deploy/oauth-openshift` | Create correct resources in `openshift-config` |
| `Invalid credentials` | Wrong bind DN/password or user password | `ldapsearch -D ... -W` | Fix Secret or user credentials |
| `No such object` | Wrong base DN | `ldapsearch -b ...` | Correct LDAP URL base DN |
| User not found | Wrong search attribute/filter | `ldapsearch "(uid=user)"` | Use correct attribute/filter |
| x509 unknown authority | Missing/wrong CA | `openssl s_client` | Create CA ConfigMap with `ca.crt` |
| Connection timeout | Firewall/network | `nc -vz ldap 636` | Open firewall/routing |
| Login works but no projects | RBAC missing | `oc auth can-i` | Add role binding |
| Same user conflict | Identity mapping conflict | `oc get user/identity` | Fix mapping or remove stale identity |
| Works from laptop but not OpenShift | Cluster network cannot reach LDAP | Debug pod/node test | Fix network path from nodes |

## 21. Example Correct LDAP OAuth YAML

### 389 Directory Server / OpenLDAP Example

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: ldap-provider
    mappingMethod: claim
    type: LDAP
    ldap:
      url: ldaps://ldap.example.com:636/ou=People,dc=example,dc=com?uid
      bindDN: cn=openshift-bind,ou=ServiceAccounts,dc=example,dc=com
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
      attributes:
        id:
        - uid
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
```

Create Secret:

```bash
oc create secret generic ldap-bind-password \
  --from-literal=bindPassword='BindPasswordHere' \
  -n openshift-config
```

Create CA ConfigMap:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/root/ldap-ca.crt \
  -n openshift-config
```

Apply OAuth:

```bash
oc apply -f oauth-ldap.yaml
```

Watch rollout:

```bash
oc get co authentication -w
oc get pods -n openshift-authentication -w
```

## 22. Active Directory Example

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: ad-provider
    mappingMethod: claim
    type: LDAP
    ldap:
      url: ldaps://ad01.example.com:636/DC=example,DC=com?sAMAccountName?sub?(objectClass=user)
      bindDN: CN=openshift-bind,OU=Service Accounts,DC=example,DC=com
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
      attributes:
        id:
        - objectGUID
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - sAMAccountName
```

Active Directory troubleshooting notes:

1. Use `sAMAccountName` for short usernames.
2. Use `userPrincipalName` if users log in as email-style usernames.
3. Base DN should usually start at the domain root if users are spread across multiple OUs.
4. If filtering by group membership, confirm nested group behavior. LDAP filters may not behave like AD UI group membership.
5. `objectGUID` may require special handling because it is binary; many environments use another stable ID attribute depending on OpenShift compatibility and LDAP output behavior.

## 23. Safe Rollback Plan

Before changing OAuth:

```bash
oc get oauth cluster -o yaml > oauth-cluster-backup.yaml
```

Rollback:

```bash
oc apply -f oauth-cluster-backup.yaml
```

If LDAP provider caused full login issue, temporarily configure HTPasswd as emergency identity provider:

```bash
htpasswd -c -B -b users.htpasswd emergency-admin 'StrongPasswordHere'

oc create secret generic emergency-htpasswd \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config
```

Patch OAuth with HTPasswd provider carefully, then grant cluster-admin:

```bash
oc adm policy add-cluster-role-to-user cluster-admin emergency-admin
```

Important:

Do not permanently keep weak emergency accounts. Rotate/remove after incident.

## 24. Interview Answer Structure

When asked:

> “OpenShift login failed after LDAP integration. How will you troubleshoot?”

A strong senior-level answer:

```text
First, I confirm whether the issue is authentication, identity mapping, or RBAC.
I keep break-glass access using kubeadmin or an existing cluster-admin session.
Then I check the authentication cluster operator, OAuth pods, and OAuth server logs.
I inspect oauth/cluster to validate the LDAP provider configuration, including URL, bindDN,
bindPassword secret, CA ConfigMap, and attribute mapping.

Next, I test LDAP connectivity from inside the OpenShift network, not just from my laptop,
because OAuth pods must reach LDAP. I use debug pods or node debug to test DNS, TCP port 389/636,
TLS handshake, and ldapsearch with the same bind DN and search base used in OAuth.

If bind/search works manually, I check OpenShift identity mapping: users, identities, mappingMethod,
and username conflicts from previous identity providers. If login succeeds but the user cannot access
resources, I treat it as RBAC and verify with oc auth can-i.

Finally, I apply the minimal fix, monitor authentication operator rollout, verify CLI and console login,
and document root cause and rollback.
```

## 25. Senior-Level Deep-Dive Points

### 25.1 Do not confuse LDAP login with LDAP group sync

LDAP login validates credentials. LDAP group sync imports groups. Group-based RBAC needs group sync or manual OpenShift groups.

### 25.2 Test from where the workload runs

Testing LDAP from your laptop is not enough. OAuth pods run inside OpenShift. Test from a pod or node.

### 25.3 Secret and ConfigMap namespace matters

OAuth provider references for LDAP bind password and CA must be in `openshift-config`.

### 25.4 TLS is a common production failure

Enterprise LDAP usually uses private CA certificates. The correct CA bundle must be provided with key `ca.crt`.

### 25.5 Identity conflicts are common during migration

If users previously logged in through HTPasswd, GitHub, OIDC, or another LDAP provider name, identity mapping conflicts may happen.

### 25.6 RBAC is separate

Successful login only proves identity. It does not grant project access.

## 26. Sample Incident RCA

### Incident

Users could not log in to OpenShift after LDAP identity provider integration.

### Impact

Developers were unable to access the OpenShift console and CLI using LDAP credentials.

### Detection

Authentication operator became degraded and console login returned invalid credentials.

### Root Cause

The LDAP bind password Secret was created in the `default` namespace instead of `openshift-config`. OAuth could not read the referenced Secret, so the LDAP identity provider was not initialized correctly.

### Resolution

Created the Secret in the correct namespace with key `bindPassword`, verified OAuth rollout, and tested LDAP login successfully.

### Corrective Actions

1. Add pre-change validation checklist for OAuth identity providers.
2. Store known-good OAuth YAML in Git.
3. Add break-glass account validation before identity-provider changes.
4. Document LDAP test commands.
5. Monitor authentication operator degradation alerts.

nslookup ldap.example.com
nc -vz ldap.example.com 636

oc get identities
