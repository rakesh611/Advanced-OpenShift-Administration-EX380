# LDAP Group Sync Is Failing — Interview-Level Troubleshooting and Fix Guide for Advanced OpenShift Administration

## 1. Interview Scenario

**Question:**

> LDAP group sync is failing. How will you fix it?

**Expected senior-level answer:**

As an Advanced OpenShift Administrator, I will not directly change RBAC or recreate groups blindly. I will first identify whether the failure is happening at the LDAP connectivity layer, TLS/certificate layer, bind/search permission layer, LDAP query/schema mapping layer, OpenShift group object layer, or automation layer such as CronJob/Secret/ConfigMap/ServiceAccount. Then I will run a controlled dry-run sync, validate the LDAP search output outside OpenShift, correct the `LDAPSyncConfig`, verify group/user attributes, test with a whitelist, apply with `--confirm`, and finally validate RBAC impact.

OpenShift LDAP group sync is separate from LDAP login authentication. A user may authenticate successfully through the LDAP identity provider, but group sync can still fail because group sync uses its own config file, bind DN, CA file, search base, schema mapping, and query attributes.

---

## 2. Core Concept: What LDAP Group Sync Does

OpenShift uses internal `Group` objects for RBAC. LDAP group sync imports or updates LDAP group membership into OpenShift groups so that administrators can assign roles to groups instead of individual users.

Example:

```bash
oc adm policy add-role-to-group edit developers -n app-dev
```

If LDAP group sync works, users from the LDAP/AD group `developers` automatically become members of the OpenShift group `developers`, and RBAC applies through group membership.

OpenShift supports LDAP group sync using three common schemas:

1. **RFC2307**
   - Common in OpenLDAP, 389 Directory Server, FreeIPA-style Unix LDAP layouts.
   - Group entries usually contain member attributes.
   - Example group object: `posixGroup`, `groupOfNames`, `groupOfUniqueNames`.

2. **Active Directory**
   - User objects usually contain `memberOf` attributes.
   - Common attributes: `sAMAccountName`, `mail`, `userPrincipalName`, `distinguishedName`.

3. **Augmented Active Directory**
   - Uses both group query and user query.
   - Useful when you need group naming from group objects and membership from user-side `memberOf`.

## 3. Important Interview Point

A very common mistake is assuming that LDAP authentication and LDAP group sync are the same.

They are not.

| Area | LDAP Authentication | LDAP Group Sync |
|---|---|---|
| Purpose | User login to OpenShift | Import LDAP groups into OpenShift groups |
| Object managed | OAuth identity provider | OpenShift `Group` objects |
| Command | `oc edit oauth cluster` | `oc adm groups sync` |
| Config location | OAuth CR and Secret/ConfigMap | LDAP sync YAML, Secret, ConfigMap, CronJob |
| Failure symptom | `oc login` fails | User logs in but has no expected project access |
| Common cause | Bind/login mapping issue | Wrong group query, CA, member attribute, whitelist, RBAC |

So in an interview, I would say:

> First I separate login failure from group sync failure. If the user cannot log in, I troubleshoot OAuth LDAP identity provider. If the user can log in but project access is missing, I troubleshoot LDAP group sync and RBAC mapping.

## 4. Typical Production Symptoms

LDAP group sync failure can appear in multiple ways:

```text
error: LDAP Result Code 49 "Invalid Credentials"
error: LDAP Result Code 32 "No Such Object"
error: LDAP Result Code 10 "Referral"
x509: certificate signed by unknown authority
ldap: cannot StartTLS
searching for groups failed
no groups matched the provided query
unable to find user by DN
synced group is empty
OpenShift group exists but members are missing
user exists in LDAP but cannot access project
CronJob completed but group membership did not update
```

From an admin perspective, I divide the symptoms into two categories:

1. **Command-level failure**
   - `oc adm groups sync` exits with error.
   - Usually connectivity, TLS, bind, baseDN, schema, or permission issue.

2. **Logical sync failure**
   - Command completes but groups are empty or incorrect.
   - Usually wrong attributes, user name mismatch, group UID mismatch, whitelist mismatch, nested group limitation, or RBAC not bound to synced group name.

## 5. First Checks on the OpenShift Side

### 5.1 Confirm Current Cluster Login and Privileges

LDAP group sync requires cluster-admin level permissions.

```bash
oc whoami
oc auth can-i create groups.user.openshift.io --all-namespaces
oc auth can-i update groups.user.openshift.io --all-namespaces
oc auth can-i get groups.user.openshift.io --all-namespaces
```

Expected:

```text
yes
yes
yes
```

If not, use a cluster-admin user:

```bash
oc login -u kubeadmin -p '<password>' https://api.<cluster>:6443
```

or verify the current user has cluster-admin:

```bash
oc adm policy who-can create groups.user.openshift.io
oc get clusterrolebinding cluster-admin -o yaml
```

### 5.2 Check Existing OpenShift Groups

```bash
oc get groups
oc get group developers -o yaml
oc describe group developers
```

Look for:

```yaml
users:
- rakesh@example.com
- amit@example.com
```

If the group exists but users are missing, the sync is reaching group objects but failing membership resolution.

If the group does not exist, the group query or whitelist may not match LDAP.

## 6. Reproduce the Failure Manually

I always reproduce manually before touching production automation.

```bash
oc adm groups sync --sync-config=ldap-sync.yaml
```

Important: without `--confirm`, this is a dry run. It shows what would be changed but does not modify OpenShift groups.

If dry-run output is correct, apply it:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

For safer testing, use a whitelist:

```bash
cat > whitelist.txt <<EOF
