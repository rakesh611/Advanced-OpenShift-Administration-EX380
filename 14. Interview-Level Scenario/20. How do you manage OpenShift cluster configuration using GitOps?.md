# How do you manage OpenShift cluster configuration using GitOps?

## Interview-Level Scenario for Advanced OpenShift Administration

**Experience level:** Senior / 10+ years  
**Technology focus:** OpenShift, Red Hat OpenShift GitOps, Argo CD, Kubernetes manifests, Kustomize, Helm, Operators, RBAC, cluster configuration lifecycle  
**Scenario type:** Enterprise platform administration, Day-2 operations, auditability, drift control, multi-cluster governance

---

## 1. Interview question

**Question:**  
How do you manage OpenShift cluster configuration using GitOps?

**What the interviewer expects:**  
The interviewer is not only asking how to deploy an application with Argo CD. They want to know whether you can manage **cluster-level OpenShift configuration** in a controlled, repeatable, auditable, and production-safe way using Git as the source of truth.

A strong answer should cover:

- GitOps principles.
- OpenShift GitOps Operator and Argo CD architecture.
- Repository structure for cluster configuration.
- Bootstrap model.
- Managing namespaces, RBAC, Operators, MachineConfig, monitoring, logging, ingress, storage, certificates, quotas, and network policies.
- Sync policies, drift detection, self-healing, pruning, and manual approval.
- Secret management.
- Promotion between dev, test, stage, and production clusters.
- Multi-cluster strategy.
- Security and access control.
- Troubleshooting failed syncs and OutOfSync states.
- Real production risks.

## 2. Short interview answer

In OpenShift, I manage cluster configuration using GitOps by keeping the desired cluster state in Git and using Red Hat OpenShift GitOps, which is based on Argo CD, to continuously reconcile that desired state into the cluster.

I normally install the OpenShift GitOps Operator first, create a controlled Argo CD instance, connect it to a secured Git repository, and then define Argo CD `Application` or `ApplicationSet` resources for cluster configuration. The Git repository contains declarative YAML, Kustomize overlays, Helm values, Operator subscriptions, namespaces, RBAC, NetworkPolicies, ResourceQuotas, LimitRanges, MachineConfigs, monitoring configuration, logging configuration, ingress configuration, and other Day-2 platform settings.

For production, I do not allow everyone to change the cluster directly using `oc apply`. Changes go through Git pull requests, code review, validation, policy checks, and then Argo CD applies the approved configuration. Argo CD continuously detects drift between Git and the live cluster. Depending on the risk level, I use automatic sync with self-heal for low-risk configuration and manual sync for high-risk cluster components such as MachineConfig, cluster-wide Operators, ingress, storage, or authentication.

This approach gives auditability, repeatability, rollback capability, environment consistency, and better compliance because Git becomes the source of truth instead of manual cluster changes.

## 3. Detailed senior-level explanation

GitOps is a cluster management approach where Git stores the desired state of the platform, and a controller inside the cluster continuously reconciles the actual state to match Git.

In OpenShift, the common enterprise implementation is **Red Hat OpenShift GitOps**, which provides a supported Argo CD-based GitOps engine. Argo CD watches a Git repository and compares the desired manifests in Git with the live Kubernetes/OpenShift resources in the cluster. If there is a difference, Argo CD marks the application as `OutOfSync`. Based on the configured policy, it can either wait for manual approval or automatically sync the changes.

For cluster configuration, GitOps is used not just for applications, but for platform administration tasks such as:

- Project and namespace creation.
- RBAC and service accounts.
- Operator installation.
- Operator configuration.
- IngressController configuration.
- Image registry configuration.
- Monitoring configuration.
- Logging configuration.
- Network policies.
- SecurityContextConstraints usage through RBAC.
- ResourceQuota and LimitRange configuration.
- StorageClass-related defaults.
- MachineConfig and node tuning.
- Cluster-wide certificates.
- External secrets integration.
- Compliance and policy configuration.

The main goal is to reduce manual changes and make cluster state reproducible.

## 4. Why GitOps is important for OpenShift cluster configuration

In a small lab, an administrator may run commands manually:

```bash
oc create namespace finance
oc adm policy add-role-to-group edit finance-devs -n finance
oc apply -f networkpolicy.yaml
```

This works for testing, but it becomes risky in production because:

- Manual changes are hard to audit.
- Different clusters become inconsistent.
- Rollback is difficult.
- There is no mandatory peer review.
- Documentation becomes outdated.
- Troubleshooting becomes harder because no one knows who changed what.
- Disaster recovery becomes slower because configuration is not fully reproducible.

With GitOps, the same configuration is stored in Git:

```text
clusters/prod/namespaces/finance/namespace.yaml
clusters/prod/namespaces/finance/rbac.yaml
clusters/prod/namespaces/finance/networkpolicy.yaml
```

Any change requires a commit and pull request. The Git history shows:

- Who changed the configuration.
- What was changed.
- When it was changed.
- Why it was changed, if commit messages and pull requests are properly written.

This is extremely valuable for regulated enterprise environments.

## 5. Basic GitOps architecture in OpenShift

A typical OpenShift GitOps architecture looks like this:

```text
Developer / Platform Engineer
        |
        | 1. Raises Pull Request
        v
Git Repository
        |
        | 2. Argo CD watches Git repository
        v
OpenShift GitOps / Argo CD
        |
        | 3. Compares Git desired state with cluster live state
        v
OpenShift Cluster
        |
        | 4. Applies, reconciles, detects drift
        v
Cluster Configuration
```

Main components:

| Component | Purpose |
|---|---|
| Git repository | Source of truth for desired configuration |
| OpenShift GitOps Operator | Installs and manages Argo CD on OpenShift |
| Argo CD | Reconciliation engine |
| Application | Defines what Git path should be synced to which cluster/namespace |
| ApplicationSet | Generates multiple Applications dynamically, useful for multi-cluster or multi-environment setup |
| Kustomize / Helm | Template and overlay management |
| Secrets tool | Manages sensitive values securely |
| CI pipeline | Validates YAML, policies, and security before merge |

## 6. Installing OpenShift GitOps Operator

In production, I usually install the OpenShift GitOps Operator using OperatorHub or GitOps itself during bootstrap.

Manual installation example:

```bash
oc create namespace openshift-gitops-operator
```

Create an OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  upgradeStrategy: Default
```

Create a Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  channel: latest
  installPlanApproval: Manual
  name: openshift-gitops-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Apply it:

```bash
oc apply -f operatorgroup.yaml
oc apply -f subscription.yaml
```

Check installation:

```bash
oc get pods -n openshift-gitops
oc get csv -n openshift-gitops-operator
oc get route -n openshift-gitops
```

By default, the operator creates an Argo CD instance in the `openshift-gitops` namespace.

## 7. Bootstrap strategy

A senior administrator should explain the bootstrap problem clearly.

GitOps needs Argo CD to apply manifests, but Argo CD itself must first be installed somehow. This is called the bootstrap phase.

Common bootstrap approaches:

### Approach 1: Manual bootstrap

Install OpenShift GitOps Operator manually once, then let Argo CD manage everything else.

Good for:

- Small environments.
- Labs.
- Initial proof of concept.

Risk:

- Initial installation is not fully GitOps-managed.

### Approach 2: Scripted bootstrap

Use a controlled script to install the GitOps operator and root application.

Example:

```bash
#!/bin/bash
set -e

oc apply -f bootstrap/openshift-gitops-operator/
oc apply -f bootstrap/root-application.yaml
```

Good for:

- Repeatable cluster creation.
- DR rebuild.
- Multi-cluster onboarding.

### Approach 3: Advanced bootstrap with ACM / Hive / ZTP

For large enterprises, cluster provisioning and GitOps bootstrap can be automated using tools such as Advanced Cluster Management, Hive, Assisted Installer, or Zero Touch Provisioning.

Good for:

- Multi-cluster platform teams.
- Edge clusters.
- Telco environments.
- Large hybrid-cloud estates.

## 9. App-of-apps pattern

For cluster configuration, I often use the **app-of-apps** pattern.

In this model, one root Argo CD Application manages multiple child Applications.

Example root application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-config-root
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: 'https://git.example.com/platform/openshift-platform-gitops.git'
    targetRevision: main
    path: clusters/prod/root
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: false
      selfHeal: true
    syncOptions:
      - CreateNamespace=false
```

The root path contains child Applications:

```text
clusters/prod/root/
├── operators-app.yaml
├── namespaces-app.yaml
├── rbac-app.yaml
├── monitoring-app.yaml
├── logging-app.yaml
├── ingress-app.yaml
└── security-app.yaml
```

Example child application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prod-namespaces
  namespace: openshift-gitops
spec:
  project: cluster-config
  source:
    repoURL: 'https://git.example.com/platform/openshift-platform-gitops.git'
    targetRevision: main
    path: clusters/prod/namespaces
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=false
```

The benefit is that one root Application can bootstrap the entire cluster configuration.

## 10. ApplicationSet pattern for multiple clusters

For multiple clusters, I prefer `ApplicationSet` instead of creating each Argo CD Application manually.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-config-appset
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - cluster: dev
            url: https://api.dev.example.com:6443
            path: clusters/dev
          - cluster: stage
            url: https://api.stage.example.com:6443
            path: clusters/stage
          - cluster: prod
            url: https://api.prod.example.com:6443
            path: clusters/prod
  template:
    metadata:
      name: '{{cluster}}-cluster-config'
    spec:
      project: cluster-config
      source:
        repoURL: 'https://git.example.com/platform/openshift-platform-gitops.git'
        targetRevision: main
        path: '{{path}}'
      destination:
        server: '{{url}}'
        namespace: default
      syncPolicy:
        automated:
          prune: false
          selfHeal: true
```

This is useful when managing many clusters with similar baseline configuration.

## 11. Managing namespaces using GitOps

Namespace creation is one of the most common GitOps use cases.

Example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: finance-prod
  labels:
    environment: prod
    owner: finance
    cost-center: cc-fin-001
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

For OpenShift, you can also create a Project:

```yaml
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: finance-prod
  labels:
    environment: prod
    owner: finance
```

I usually manage namespace metadata carefully because labels are used by:

- NetworkPolicy selectors.
- Monitoring selectors.
- Cost management tools.
- Compliance scans.
- Tenant ownership.
- Automation.

## 12. Managing RBAC using GitOps

RBAC should be controlled through Git because it directly affects security.

Example RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: finance-devs-edit
  namespace: finance-prod
subjects:
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: finance-devs
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: edit
```

Example view-only access:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: finance-auditors-view
  namespace: finance-prod
subjects:
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: finance-auditors
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: view
```

Senior-level best practices:

- Avoid giving `cluster-admin` through Git unless absolutely required.
- Prefer group-based access, not user-based access.
- Keep emergency access separate from normal GitOps RBAC.
- Use pull request approval for any RBAC change.
- Review RBAC changes during security audits.

## 13. Managing ResourceQuota and LimitRange

Resource governance should be GitOps-managed to avoid noisy-neighbor problems.

Example ResourceQuota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: finance-prod-quota
  namespace: finance-prod
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 80Gi
    limits.cpu: "40"
    limits.memory: 160Gi
    pods: "100"
    persistentvolumeclaims: "20"
```

Example LimitRange:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: finance-prod-limits
  namespace: finance-prod
spec:
  limits:
    - type: Container
      default:
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "2"
        memory: "4Gi"
      min:
        cpu: "50m"
        memory: "64Mi"
```

This ensures every namespace has predictable resource boundaries.

## 14. Managing NetworkPolicy using GitOps

Network policies are critical for workload isolation.

Example default deny policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: finance-prod
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

Allow same namespace communication:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: finance-prod
spec:
  podSelector: {}
  ingress:
    - from:
        - podSelector: {}
  policyTypes:
    - Ingress
```

Allow ingress from OpenShift router namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-router-ingress
  namespace: finance-prod
spec:
  podSelector:
    matchLabels:
      app: finance-web
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              policy-group.network.openshift.io/ingress: ""
  policyTypes:
    - Ingress
```

In interviews, explain that you do not apply default deny blindly in production without understanding DNS, monitoring, logging, service mesh, ingress, and external dependencies.

## 15. Managing Operators using GitOps

Operators are installed through OLM resources:

- `Namespace`
- `OperatorGroup`
- `Subscription`
- Custom Resource after the operator is ready

Example Namespace:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-logging
```

Example OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-logging
  namespace: openshift-logging
spec:
  targetNamespaces:
    - openshift-logging
```

Example Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: cluster-logging
  namespace: openshift-logging
spec:
  channel: stable
  installPlanApproval: Manual
  name: cluster-logging
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Important senior point:

Do not apply the operator Custom Resource before the CRD exists. For example, do not apply `ClusterLogging` before the logging operator is installed and CRDs are available.

To solve this, use:

- Separate Argo CD Applications.
- Sync waves.
- Manual sync for operator upgrades.
- Health checks.
- PreSync checks if required.

## 16. Sync waves for ordering

Argo CD sync waves help control resource order.

Example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-logging
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-logging
  namespace: openshift-logging
  annotations:
    argocd.argoproj.io/sync-wave: "1"
spec:
  targetNamespaces:
    - openshift-logging
```

Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: cluster-logging
  namespace: openshift-logging
  annotations:
    argocd.argoproj.io/sync-wave: "2"
spec:
  channel: stable
  installPlanApproval: Manual
  name: cluster-logging
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Custom Resource:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogging
metadata:
  name: instance
  namespace: openshift-logging
  annotations:
    argocd.argoproj.io/sync-wave: "3"
spec:
  managementState: Managed
```

Even with sync waves, operator CRDs may take time to become available. For critical Operators, I prefer separate Applications and controlled sync phases.

## 17. Managing OpenShift monitoring configuration

User workload monitoring can be enabled through GitOps.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

User workload monitoring configuration:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      retention: 15d
      volumeClaimTemplate:
        spec:
          storageClassName: ocs-storagecluster-ceph-rbd
          resources:
            requests:
              storage: 100Gi
```

PrometheusRule example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: finance-alerts
  namespace: finance-prod
spec:
  groups:
    - name: finance.rules
      rules:
        - alert: FinanceAppHighErrorRate
          expr: rate(http_requests_total{namespace="finance-prod",status=~"5.."}[5m]) > 0.05
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: Finance application high error rate
```

Monitoring configuration is sensitive because a bad change can affect alerting and observability. I usually require review from the platform monitoring team.

## 18. Managing OpenShift logging configuration

Logging can also be managed declaratively.

Typical GitOps-managed logging objects include:

- Logging Operator Subscription.
- ClusterLogForwarder.
- Output secrets.
- LokiStack or external SIEM configuration.
- Namespace log forwarding rules.

Example `ClusterLogForwarder` concept:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  outputs:
    - name: external-siem
      type: syslog
      syslog:
        url: tls://siem.example.com:6514
      secret:
        name: siem-tls-secret
  pipelines:
    - name: app-logs-to-siem
      inputRefs:
        - application
      outputRefs:
        - external-siem
```

Important:

- Do not store SIEM credentials directly in Git.
- Store only secret references in Git.
- Use External Secrets, Sealed Secrets, SOPS, Vault, or another approved secret management method.

## 19. Managing ingress and router configuration

IngressController configuration can be GitOps-managed.

Example:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  replicas: 3
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

This is useful when routers must run only on infra nodes.

Production caution:

- Router changes can impact application traffic.
- Certificate changes can break TLS.
- Replica or placement changes can affect availability.
- Use maintenance windows for high-risk ingress changes.

## 21. Managing MachineConfig using GitOps

MachineConfig can be managed using GitOps, but it is high-risk.

Example MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: 99-worker-custom-sysctl
spec:
  config:
    ignition:
      version: 3.2.0
    storage:
      files:
        - path: /etc/sysctl.d/99-custom.conf
          mode: 0644
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8;base64,bmV0LmlwdjQuaXBfZm9yd2FyZCA9IDEK
```

Senior-level warning:

MachineConfig changes can reboot nodes. A wrong MachineConfig can degrade the MachineConfigPool and impact workloads. For this reason:

- I do not enable blind auto-sync for critical MachineConfigs in production.
- I test MachineConfig changes in dev or staging first.
- I check MCP status before and after sync.
- I respect PodDisruptionBudgets.
- I perform risky changes during maintenance windows.

Check MCP:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
```

## 22. Managing node tuning using GitOps

Node tuning can be handled with the Node Tuning Operator.

Example Tuned profile:

```yaml
apiVersion: tuned.openshift.io/v1
kind: Tuned
metadata:
  name: custom-worker-tuning
  namespace: openshift-cluster-node-tuning-operator
spec:
  profile:
    - name: custom-worker-profile
      data: |
        [main]
        summary=Custom worker tuning
        include=openshift-node

        [sysctl]
        net.core.somaxconn=4096
  recommend:
    - match:
        - label: node-role.kubernetes.io/worker
      priority: 20
      profile: custom-worker-profile
```

This is safer than random node-level manual tuning because configuration is declarative and auditable.

## 23. Managing authentication configuration

OAuth configuration can be GitOps-managed, but it must be handled carefully because a bad change can block user login.

Example concept:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
    - name: corporate-ldap
      mappingMethod: claim
      type: LDAP
      ldap:
        attributes:
          id:
            - dn
          email:
            - mail
          name:
            - cn
          preferredUsername:
            - uid
        bindDN: uid=openshift,ou=serviceaccounts,dc=example,dc=com
        bindPassword:
          name: ldap-bind-password
        insecure: false
        url: ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid
```

Best practices:

- Do not commit bind passwords into Git.
- Keep break-glass kubeadmin or emergency access plan where applicable.
- Test OAuth changes in non-production first.
- Apply authentication changes manually or with gated sync in production.
- Monitor authentication ClusterOperator after change.

Commands:

```bash
oc get co authentication
oc describe oauth cluster
oc logs -n openshift-authentication deploy/oauth-openshift
```

## 24. Secret management in GitOps

Secrets are one of the most important GitOps topics.

Never store plain-text secrets in Git.

Bad example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-password
stringData:
  password: MyPlainTextPassword
```

Better approaches:

### Option 1: External Secrets Operator

Git stores only the reference:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-secret
  namespace: finance-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: db-secret
  data:
    - secretKey: password
      remoteRef:
        key: finance/prod/db
        property: password
```

Actual secret remains in Vault, AWS Secrets Manager, Azure Key Vault, or another backend.

### Option 2: Sealed Secrets

Git stores encrypted secret manifests that only the cluster can decrypt.

### Option 3: SOPS

Secrets are encrypted in Git and decrypted during deployment using approved keys.

### Option 4: Vault integration

Applications or operators retrieve secrets directly from Vault.

Senior answer:

I choose the secret strategy based on enterprise security standards. My preference is usually External Secrets with Vault or cloud-native secret manager because secret rotation is easier and secrets are not permanently tied to one cluster.

## 25. Sync policy design

Not every configuration should use the same sync policy.

Example automated sync:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
    - CreateNamespace=false
```

Meaning:

| Option | Meaning |
|---|---|
| automated | Argo CD syncs automatically when Git changes |
| prune | Deletes live resources removed from Git |
| selfHeal | Reverts manual drift in the cluster |
| CreateNamespace | Allows Argo CD to create destination namespace |

My production policy:

| Configuration type | Sync recommendation |
|---|---|
| Namespace labels | Auto-sync allowed |
| ResourceQuota / LimitRange | Auto-sync with review |
| RBAC | Auto-sync only after PR approval |
| NetworkPolicy | Manual or controlled auto-sync |
| Monitoring rules | Auto-sync after validation |
| Operator Subscription | Manual approval for production |
| MachineConfig | Manual sync / maintenance window |
| OAuth | Manual sync / emergency rollback plan |
| IngressController | Manual sync for production |
| Logging forwarding | Controlled sync |

## 26. Drift detection and self-healing

One major benefit of GitOps is drift detection.

Example scenario:

An administrator manually changes a namespace quota:

```bash
oc edit resourcequota finance-prod-quota -n finance-prod
```

Argo CD detects that the live object no longer matches Git and marks it `OutOfSync`.

If self-heal is enabled, Argo CD reverts the change automatically.

If self-heal is disabled, Argo CD shows the difference and waits for manual sync.

Commands:

```bash
argocd app list
argocd app get prod-namespaces
argocd app diff prod-namespaces
argocd app sync prod-namespaces
```

Using `oc`:

```bash
oc get applications -n openshift-gitops
oc describe application prod-namespaces -n openshift-gitops
```

## 27. Handling cluster-scoped resources

OpenShift cluster configuration often includes cluster-scoped resources such as:

- ClusterRole
- ClusterRoleBinding
- MachineConfig
- IngressController
- OAuth
- Image registry config
- Scheduler config
- APIServer config
- Proxy config
- ClusterVersion
- CustomResourceDefinitions

Argo CD needs permission to manage these resources.

In OpenShift, the default Argo CD instance may not have permission for all cluster-scoped resources unless configured.

You may need to grant appropriate permissions:

```bash
oc adm policy add-cluster-role-to-user cluster-admin \
  -z openshift-gitops-argocd-application-controller \
  -n openshift-gitops
```

However, this is powerful and should be carefully controlled.

Production recommendation:

- Use dedicated Argo CD Projects.
- Restrict repositories.
- Restrict destinations.
- Restrict resource kinds.
- Use separate Argo CD instances or projects for application teams and platform teams.
- Do not give broad cluster-admin to team-managed Argo CD instances.

## 36. Handling generated or operator-mutated fields

Many Kubernetes/OpenShift resources are mutated by controllers. This can create false OutOfSync status.

Examples:

- Defaulted fields added by API server.
- Status fields.
- Operator-managed annotations.
- CA bundle injection.
- Webhook mutations.
- Automatically generated secrets.

Solutions:

- Do not store status fields in Git.
- Use `.spec` only where possible.
- Use Argo CD ignore differences for specific fields.
- Avoid managing resources that are fully operator-owned.

Example ignoreDifferences:

```yaml
spec:
  ignoreDifferences:
    - group: admissionregistration.k8s.io
      kind: MutatingWebhookConfiguration
      jsonPointers:
        - /webhooks/0/clientConfig/caBundle
```

Use ignore differences carefully. Do not hide real drift.

## 37. Common OutOfSync causes

| Cause | Explanation | Fix |
|---|---|---|
| Manual cluster edit | Someone changed live resource | Revert manually or let Argo self-heal |
| API defaulting | Cluster added default fields | Use clean YAML or ignore differences |
| Operator mutation | Operator changed fields | Do not manage operator-owned fields |
| Missing CRD | CR applied before operator installed | Fix ordering or split Applications |
| RBAC denied | Argo CD lacks permission | Grant required access carefully |
| Invalid YAML | Manifest syntax or schema issue | Validate in CI |
| Namespace missing | Destination namespace does not exist | Create namespace first or enable CreateNamespace |
| Prune disabled | Deleted Git resource remains live | Enable prune where safe |
| Helm render difference | Dynamic template value changed | Pin values and chart versions |

## 41. Rollback strategy

Rollback in GitOps means reverting Git to a previous known good state.

Example:

```bash
git revert <bad_commit_id>
git push origin main
```

Argo CD detects the change and syncs the previous configuration.

For application deployment rollback:

```bash
argocd app rollback my-app <history-id>
```

For cluster configuration, I prefer Git revert because it keeps the audit trail clear.

Caution:

Rollback is not always simple for:

- CRD version changes.
- Operator upgrades.
- Storage changes.
- MachineConfig changes.
- OAuth changes.
- Database/schema changes.

For these, rollback must be planned before production rollout.

## 46. Example interview scenario answer

**Interviewer:** How do you manage OpenShift cluster configuration using GitOps?

**Answer:**

In my OpenShift environments, I use GitOps to manage cluster configuration by treating Git as the source of truth and using Red Hat OpenShift GitOps, which is based on Argo CD, as the reconciliation engine. All cluster configuration such as namespaces, RBAC, quotas, network policies, operator subscriptions, monitoring rules, logging configuration, ingress configuration, and selected cluster-scoped resources are stored as declarative manifests in Git.

I normally start with a bootstrap process. First, I install the OpenShift GitOps Operator and create a root Argo CD Application. That root application points to the platform Git repository and creates child applications for different configuration areas such as operators, namespaces, RBAC, monitoring, logging, ingress, and security. This is usually implemented using the app-of-apps pattern or ApplicationSet if I am managing multiple clusters.

For repository design, I separate base configuration from environment overlays. For example, common namespace templates, RBAC templates, network policies, and quotas stay in a base folder, while dev, stage, and prod have their own overlays. This allows us to keep environments consistent while still allowing production-specific differences.

For production safety, I do not use the same sync policy everywhere. Low-risk resources such as namespace labels or standard quotas may use automated sync and self-healing. High-risk resources such as MachineConfig, OAuth, ingress, storage, or operator upgrades are usually manually synced after approval and during a maintenance window. I also avoid automatic prune for critical cluster-scoped resources because accidental deletion can be dangerous.

All changes go through pull requests, code review, CI validation, and policy checks. We validate YAML, Kustomize builds, Helm templates, and security policies before merging. For sensitive data, I never store plain-text secrets in Git. I use External Secrets, Vault, Sealed Secrets, or SOPS depending on the enterprise standard.

Argo CD continuously compares the live cluster state with Git. If someone manually changes a resource using `oc edit`, Argo CD detects drift and marks the application OutOfSync. If self-heal is enabled, it automatically restores the Git-defined state. Otherwise, the platform team reviews the difference and syncs manually.

For troubleshooting, I check the Argo CD Application status, sync error, repo-server logs, application-controller logs, RBAC permissions, missing CRDs, OpenShift events, Operator status, and ClusterOperator health. Most GitOps failures are caused by invalid manifests, missing namespaces, RBAC denial, CRDs not existing yet, operator timing issues, or resources being mutated by another controller.

This approach gives strong auditability, repeatability, rollback, compliance, and consistency across clusters. It also reduces manual configuration drift and makes disaster recovery easier because the cluster configuration can be rebuilt from Git.

## 50. Final senior-level conclusion

Managing OpenShift cluster configuration using GitOps means moving from manual administration to a declarative, audited, and automated operating model. Git stores the desired state, Argo CD continuously compares and reconciles the live cluster, and every change goes through review and validation.

For a senior OpenShift administrator, the most important point is not simply installing Argo CD. The real skill is designing a safe GitOps operating model for production: repository structure, bootstrap strategy, sync policy, RBAC boundaries, secret management, promotion workflow, rollback strategy, multi-cluster support, and troubleshooting process.

In production, I use GitOps for consistency and auditability, but I still classify changes by risk. Low-risk configuration can be auto-synced. High-risk cluster configuration should be manually approved, tested in lower environments, and applied during controlled windows.

That is the difference between basic GitOps usage and enterprise-grade OpenShift GitOps administration.
