# Interview Scenario: Application Should Run Only on Infra Nodes — How Will You Configure It?

## 1. Interview-Level Answer

If an application should run **only on infra nodes** in OpenShift, I will configure pod placement using a combination of:

1. **Node labels** to identify infra nodes.
2. **Node taints** to prevent normal workloads from landing on infra nodes.
3. **Pod tolerations** so only approved workloads can tolerate the infra-node taint.
4. **nodeSelector or nodeAffinity** in the application Deployment/DeploymentConfig so the application is scheduled only on infra nodes.
5. Optional **namespace-level node selector** if all workloads in one namespace must run on infra nodes.
6. Validation using `oc get pods -o wide`, `oc describe pod`, `oc describe node`, and scheduler events.

A senior OpenShift administrator should not rely only on `nodeSelector`. `nodeSelector` attracts the target application to infra nodes, but it does not stop other workloads from also using infra nodes. For proper isolation, infra nodes should normally be **labeled and tainted**, and only selected applications should have matching **nodeSelector/nodeAffinity + toleration**.

---

## 2. Why This Question Is Asked in Interviews

This question checks whether you understand **OpenShift workload placement** beyond basic deployment.

The interviewer wants to know whether you can:

- Separate application workloads from infrastructure workloads.
- Use labels, taints, tolerations, node selectors, and node affinity correctly.
- Understand infra-node subscription and architecture considerations.
- Avoid accidentally scheduling business workloads on nodes reserved for routers, registry, monitoring, logging, or other platform services.
- Troubleshoot Pending pods caused by placement constraints.
- Explain production-grade design, not just one command.

## 3. What Are Infra Nodes in OpenShift?

In OpenShift, **infra nodes** are worker-type nodes dedicated to infrastructure workloads such as:

- Ingress/router pods
- Internal image registry
- Monitoring stack
- Logging stack
- Service mesh control plane components
- GitOps or platform management components
- Other shared platform services

Infra nodes are still Kubernetes/OpenShift nodes. They are not control-plane nodes. They are usually workers with special labels and sometimes separate MachineConfigPool or MachineSet configuration.

Typical infra node label:

```bash
node-role.kubernetes.io/infra=
```

Example node list:

```bash
oc get nodes
```

Example output:

```text
NAME            STATUS   ROLES          AGE   VERSION
master-0        Ready    master         40d   v1.xx.x
master-1        Ready    master         40d   v1.xx.x
master-2        Ready    master         40d   v1.xx.x
worker-0        Ready    worker         40d   v1.xx.x
worker-1        Ready    worker         40d   v1.xx.x
infra-0         Ready    infra,worker   40d   v1.xx.x
infra-1         Ready    infra,worker   40d   v1.xx.x
infra-2         Ready    infra,worker   40d   v1.xx.x
```

In many environments, infra nodes may still show both `worker` and `infra` roles. That is common because they are worker-class machines but logically dedicated for infrastructure workloads.

## 4. Core Scheduling Concepts

### 4.1 Node Label

A label is a key-value marker on a node.

Example:

```bash
oc label node infra-0 node-role.kubernetes.io/infra=
oc label node infra-1 node-role.kubernetes.io/infra=
oc label node infra-2 node-role.kubernetes.io/infra=
```

Check labels:

```bash
oc get nodes --show-labels
```

Filter infra nodes:

```bash
oc get nodes -l node-role.kubernetes.io/infra=
```

### 4.2 nodeSelector

`nodeSelector` tells the scheduler that the pod can run only on nodes with matching labels.

Example:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

This ensures the pod is scheduled only on nodes labeled as infra.

### 4.3 Taint

A taint is applied on a node to repel pods that do not have a matching toleration.

Example:

```bash
oc adm taint nodes infra-0 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes infra-1 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes infra-2 node-role.kubernetes.io/infra=:NoSchedule
```

This means normal pods cannot be scheduled on infra nodes unless they tolerate this taint.

### 4.4 Toleration

A toleration is added to a pod specification so the pod can run on a tainted node.

Example:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### 4.5 Node Affinity

Node affinity is a more advanced and expressive version of `nodeSelector`.

Example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node-role.kubernetes.io/infra
          operator: Exists
```

For production, I prefer **required node affinity** when rules are complex, and `nodeSelector` when the rule is simple.

## 5. Production-Grade Configuration Strategy

To make an application run **only on infra nodes**, I use this model:

```text
Application Pod
   |
   |-- nodeSelector / required nodeAffinity
   |       -> attracts pod only to infra nodes
   |
   |-- toleration
           -> allows pod to tolerate infra node taint

Infra Node
   |
   |-- label: node-role.kubernetes.io/infra=
   |       -> identifies node as infra
   |
   |-- taint: node-role.kubernetes.io/infra=:NoSchedule
           -> prevents unwanted workloads
```

This gives two-way control:

- `nodeSelector` or `nodeAffinity` says: **this application must go to infra nodes**.
- `taint` says: **normal applications must not come to infra nodes**.
- `toleration` says: **this approved application is allowed to run there**.

## 6. Step-by-Step Implementation

## Step 1: Identify Existing Infra Nodes

```bash
oc get nodes
```

Check infra labels:

```bash
oc get nodes -l node-role.kubernetes.io/infra=
```

Check all node roles:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,ROLES:.metadata.labels
```

Better readable command:

```bash
oc get nodes --show-labels | grep infra
```

If no infra nodes exist, you need to create or label them.

---

## Step 2: Label Worker Nodes as Infra Nodes

Example:

```bash
oc label node worker-3 node-role.kubernetes.io/infra=
oc label node worker-4 node-role.kubernetes.io/infra=
oc label node worker-5 node-role.kubernetes.io/infra=
```

Verify:

```bash
oc get nodes -l node-role.kubernetes.io/infra=
```

Expected output:

```text
NAME       STATUS   ROLES          AGE   VERSION
worker-3   Ready    infra,worker   30d   v1.xx.x
worker-4   Ready    infra,worker   30d   v1.xx.x
worker-5   Ready    infra,worker   30d   v1.xx.x
```

Important production note:

Do not randomly convert normal worker nodes to infra nodes without checking workload capacity, autoscaling, router replicas, monitoring requirements, logging requirements, and business application impact.

---

## Step 3: Taint Infra Nodes

Apply taint:

```bash
oc adm taint nodes worker-3 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes worker-4 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes worker-5 node-role.kubernetes.io/infra=:NoSchedule
```

Verify taints:

```bash
oc describe node worker-3 | grep -i taints -A2
```

Expected output:

```text
Taints: node-role.kubernetes.io/infra:NoSchedule
```

Or use JSONPath:

```bash
oc get node worker-3 -o jsonpath='{.spec.taints}'
```

### Why Taint Is Important

Without taint, other normal workloads may also land on infra nodes if scheduler finds resources available.

`nodeSelector` only controls the selected application. It does not protect infra nodes from other pods. Taint protects infra nodes cluster-wide.

---

## Step 4: Add nodeSelector and Toleration to Application Deployment

Example application Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-infra-app
  namespace: app-infra-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-infra-app
  template:
    metadata:
      labels:
        app: my-infra-app
    spec:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
      containers:
      - name: my-infra-app
        image: registry.access.redhat.com/ubi9/ubi:latest
        command: ["/bin/sh", "-c", "while true; do echo running-on-infra-node; sleep 30; done"]
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 512Mi
```

Apply it:

```bash
oc new-project app-infra-demo
oc apply -f my-infra-app.yaml
```

Verify:

```bash
oc get pods -n app-infra-demo -o wide
```

Expected output:

```text
NAME                            READY   STATUS    NODE
my-infra-app-xxxxxx-abcde       1/1     Running   worker-3
my-infra-app-xxxxxx-fghij       1/1     Running   worker-4
my-infra-app-xxxxxx-klmno       1/1     Running   worker-5
```

Confirm these nodes are infra nodes:

```bash
oc get node worker-3 --show-labels | grep node-role.kubernetes.io/infra
```

## 7. Using Node Affinity Instead of nodeSelector

For simple placement, `nodeSelector` is enough. For enterprise-grade configuration, I often prefer `nodeAffinity` because it is more expressive.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-infra-app
  namespace: app-infra-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-infra-app
  template:
    metadata:
      labels:
        app: my-infra-app
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: node-role.kubernetes.io/infra
                operator: Exists
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
      containers:
      - name: my-infra-app
        image: registry.access.redhat.com/ubi9/ubi:latest
        command: ["/bin/sh", "-c", "while true; do echo running-on-infra-node; sleep 30; done"]
```

### nodeSelector vs Node Affinity

| Feature | nodeSelector | Node Affinity |
|---|---|---|
| Simplicity | Very simple | More complex |
| Operators | Exact match only | Exists, In, NotIn, DoesNotExist |
| Multiple conditions | Limited | Strong support |
| Preferred rules | No | Yes |
| Production flexibility | Basic | Better |

For the interview, I would say:

> For a simple infra placement requirement, I can use `nodeSelector`. For a more flexible production design, I prefer `requiredDuringSchedulingIgnoredDuringExecution` node affinity with tolerations.

## 8. Namespace-Level Node Selector Option

If every pod in a namespace must run only on infra nodes, we can configure the namespace annotation:

```bash
oc annotate namespace app-infra-demo \
  openshift.io/node-selector='node-role.kubernetes.io/infra='
```

Check annotation:

```bash
oc get namespace app-infra-demo -o yaml | grep -A5 node-selector
```

Then add tolerations to workloads because infra nodes are tainted.

Example pod spec still needs:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### Important Warning

Namespace node selector only handles node selection. It does not automatically add tolerations to pods.

So if infra nodes are tainted and pods do not have tolerations, pods will remain Pending.

## 10. Patching an Existing Deployment

If the application already exists, patch it.

### Add nodeSelector

```bash
oc patch deployment my-infra-app -n app-infra-demo --type=merge -p '
{
  "spec": {
    "template": {
      "spec": {
        "nodeSelector": {
          "node-role.kubernetes.io/infra": ""
        }
      }
    }
  }
}'
```

### Add toleration

```bash
oc patch deployment my-infra-app -n app-infra-demo --type=json -p '
[
  {
    "op": "add",
    "path": "/spec/template/spec/tolerations",
    "value": [
      {
        "key": "node-role.kubernetes.io/infra",
        "operator": "Exists",
        "effect": "NoSchedule"
      }
    ]
  }
]'
```

Restart rollout if needed:

```bash
oc rollout restart deployment/my-infra-app -n app-infra-demo
```

Watch rollout:

```bash
oc rollout status deployment/my-infra-app -n app-infra-demo
```

Verify pod node placement:

```bash
oc get pods -n app-infra-demo -o wide
```

## 13. How Scheduler Makes the Decision

When a pod is created, the scheduler checks:

1. Is the node Ready?
2. Does the node have enough CPU and memory?
3. Does the node match pod `nodeSelector` or `nodeAffinity`?
4. Does the pod tolerate the node taints?
5. Are there topology spread constraints?
6. Are there pod affinity or anti-affinity rules?
7. Are there resource quotas or admission policies blocking the pod?
8. Are PVC topology constraints satisfied?

For this case:

```text
Pod requires node-role.kubernetes.io/infra
        +
Pod tolerates infra NoSchedule taint
        +
Infra node has enough resources
        =
Pod gets scheduled on infra node
```

If any of these conditions fail, the pod remains Pending.

## 14. Troubleshooting: Pod Is Pending

### 14.1 Check Pod Events

```bash
oc describe pod <pod-name> -n app-infra-demo
```

Common event:

```text
0/6 nodes are available: 3 node(s) didn't match Pod's node affinity/selector, 3 node(s) had untolerated taint {node-role.kubernetes.io/infra: }.
```

Meaning:

- Pod selector may be wrong.
- Pod toleration may be missing.
- Infra node taint key may not match toleration key.

### 14.2 Check Node Labels

```bash
oc get nodes --show-labels | grep infra
```

Or:

```bash
oc get node worker-3 -o jsonpath='{.metadata.labels}'
```

Problem example:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: "true"
```

But node label is:

```text
node-role.kubernetes.io/infra=
```

This will not match.

Correct:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

### 14.3 Check Node Taints

```bash
oc describe node worker-3 | grep -i taints -A2
```

If taint is:

```text
node-role.kubernetes.io/infra:NoSchedule
```

Then toleration should be:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### 14.4 Check Node Resources

```bash
oc describe node worker-3
```

Look at:

```text
Allocated resources:
  CPU Requests
  Memory Requests
```

If infra nodes are full, pod stays Pending even if labels and tolerations are correct.

### 14.5 Check Namespace Node Selector

```bash
oc get namespace app-infra-demo -o yaml | grep -A3 node-selector
```

If the namespace has a conflicting node selector, pod may not schedule.

Example conflict:

Namespace selector:

```text
openshift.io/node-selector: env=prod
```

Pod selector:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

If no node has both labels, pod remains Pending.

### 14.6 Check Cluster-Wide Default Node Selector

```bash
oc get scheduler cluster -o yaml
```

Look for:

```yaml
spec:
  defaultNodeSelector: ...
```

A cluster-wide default node selector can conflict with pod or namespace placement.

### 14.7 Check PVC Zone or Storage Constraints

If the pod uses PVC, storage topology can affect scheduling.

Commands:

```bash
oc get pvc -n app-infra-demo
oc describe pvc <pvc-name> -n app-infra-demo
oc get pv
oc describe pv <pv-name>
```

Possible issue:

- Pod must run on infra nodes in zone A.
- PVC is bound to storage in zone B.
- Scheduler cannot place the pod.

### 14.8 Check SCC or Admission Issues

If the pod is not even created correctly:

```bash
oc get events -n app-infra-demo --sort-by=.lastTimestamp
oc describe deployment my-infra-app -n app-infra-demo
```

SCC issues usually show as create/admission failures, not only scheduling failures.

## 15. Common Mistakes

### Mistake 1: Only Using Toleration

Wrong:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

Why wrong?

This allows the pod to run on infra nodes, but it does not force the pod to run only on infra nodes. The pod may still run on worker nodes.

Correct:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### Mistake 2: Only Using nodeSelector

Wrong:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

Why incomplete?

If infra nodes are tainted, the pod cannot schedule without toleration.

Correct:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### Mistake 3: Wrong Label Value

Wrong:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: "true"
```

Correct when label has empty value:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

### Mistake 4: Taint Key and Toleration Key Mismatch

Node taint:

```text
infra=reserved:NoSchedule
```

Pod toleration:

```yaml
- key: node-role.kubernetes.io/infra
```

This does not match.

### Mistake 5: Running Business Apps on Infra Nodes Without Approval

Infra nodes are usually reserved for platform workloads. Running user applications on infra nodes may violate design, support, or subscription assumptions.

## 16. Interview Answer: Short Version

In an interview, I would answer like this:

> First, I will confirm which nodes are infra nodes by checking the `node-role.kubernetes.io/infra` label. If required, I will label selected worker nodes as infra nodes. Then I will taint infra nodes with `NoSchedule` so normal workloads cannot run there. For the application, I will configure `nodeSelector` or required `nodeAffinity` to select only infra nodes, and add a matching toleration so the pod can tolerate the infra-node taint. After deployment, I will verify with `oc get pods -o wide`, `oc describe pod`, and `oc describe node`. If the pod is Pending, I will check node labels, taints, tolerations, node resources, namespace node selector, cluster default node selector, and storage topology constraints.

---

## 17. Interview Answer: Senior-Level Version

A 10-year-experience answer should sound like this:

> I would not simply patch the deployment blindly. First, I would validate the cluster architecture: whether infra nodes already exist, whether they are dedicated through MachineSet or manually labeled workers, whether they are tainted, and whether they have enough capacity. Then I would use a two-layer placement model. The infra nodes would have the label `node-role.kubernetes.io/infra=` and a `NoSchedule` taint. The application pod template would have either `nodeSelector` or required node affinity for the infra label, plus a matching toleration for the infra taint. This ensures the workload is both attracted to infra nodes and allowed to run there, while other workloads are repelled. I would implement this through GitOps or YAML, not manual one-time changes, and validate scheduling using pod events and node labels. I would also check for namespace-level selectors, default scheduler selectors, resource pressure, PVC zone binding, and anti-affinity rules if the pod remains Pending.

## 21. GitOps-Friendly Kustomize Patch

In production, placement should be controlled through GitOps.

Example patch file:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-infra-app
  namespace: app-infra-demo
spec:
  template:
    spec:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

`kustomization.yaml`:

```yaml
resources:
- deployment.yaml

patchesStrategicMerge:
- infra-placement-patch.yaml
```

## 23. Operator-Based Application Placement

If the application is managed by an Operator, do not directly edit generated deployments unless the Operator supports it.

Instead, check the Custom Resource.

Example pattern:

```yaml
apiVersion: example.com/v1
kind: MyApp
metadata:
  name: myapp
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Exists
    effect: NoSchedule
```

If the Operator does not support placement fields, options are:

- Check Operator documentation.
- Use supported custom resource fields.
- Use subscription/operator group placement where applicable.
- Avoid unsupported manual patching because the Operator may revert changes.

## 24. Infra Nodes and OpenShift Platform Components

Many OpenShift platform components support node placement, for example:

- Ingress Controller
- Image Registry
- Monitoring
- Logging
- Service Mesh


## 25. Security and Governance Considerations

Running an application only on infra nodes is not only a scheduler task. In enterprise environments, I would also check:

- Who approved application placement on infra nodes?
- Is this a platform application or business application?
- Will it consume infra capacity required by routers, registry, monitoring, or logging?
- Is there a quota and limit range in the namespace?
- Are there PodDisruptionBudgets?
- Are there topology spread constraints?
- Is monitoring configured?
- Is the app part of disaster recovery planning?
- Is this configured through GitOps?
- Will cluster autoscaler handle infra nodes separately?

## 27. High Availability Considerations

If the application must run only on infra nodes, ensure enough infra nodes exist.

Recommended:

- Minimum 3 infra nodes for production HA.
- Spread replicas across nodes.
- Use PodDisruptionBudget.
- Avoid single infra node dependency.
- Consider topology spread constraints.

Example topology spread:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: infra-only-app
```

Full pod spec section:

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Exists
    effect: NoSchedule
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: infra-only-app
```

## 33. Troubleshooting Matrix

| Symptom | Possible Cause | Fix |
|---|---|---|
| Pod Pending | Missing toleration | Add toleration matching infra taint |
| Pod Pending | Wrong nodeSelector value | Use correct infra label key/value |
| Pod on worker node | Only toleration used, no selector | Add nodeSelector or required node affinity |
| Other apps on infra nodes | Infra nodes not tainted | Add `NoSchedule` taint |
| Pod Pending | Infra nodes full | Add capacity or reduce requests |
| Pod Pending | Namespace selector conflict | Fix namespace annotation |
| Pod Pending | PVC zone mismatch | Check PV topology and storage class |
| Operator reverts changes | Manual patch unsupported | Configure placement in custom resource |
| DaemonSet runs everywhere | Missing nodeSelector | Add nodeSelector to DaemonSet pod template |

## 34. Best Practices

1. Use **labels** to identify infra nodes.
2. Use **taints** to protect infra nodes from general workloads.
3. Use **nodeSelector or required node affinity** to force selected workloads onto infra nodes.
4. Use **tolerations** only for approved workloads.
5. Define placement in GitOps manifests.
6. Avoid manual patching in production unless it is emergency remediation.
7. Validate with pod events and node-level configuration.
8. Do not run business workloads on infra nodes unless architecture and licensing policies allow it.
9. Use requests and limits to protect infra capacity.
10. Use PDB and topology spread constraints for HA.

## 35. Final Interview Summary

To configure an application to run only on infra nodes in OpenShift, I would label the target nodes as infra, taint them with `NoSchedule`, and configure the application pod template with a matching `nodeSelector` or required node affinity plus a matching toleration. The selector ensures the application is scheduled only on infra nodes, and the toleration allows it to run on tainted infra nodes. I would verify using `oc get pods -o wide`, `oc describe pod`, and `oc describe node`. If scheduling fails, I would check labels, taints, tolerations, namespace selectors, cluster default scheduler selectors, node capacity, storage topology, and Operator-managed placement settings.
