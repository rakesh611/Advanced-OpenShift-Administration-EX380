# Argo CD App is OutOfSync — What Does It Mean?

## Interview-Level Scenario for Advanced OpenShift Administration

**Target Role:** Senior OpenShift / Platform / GitOps Administrator  
**Experience Level:** 10+ Years  
**Technology Stack:** Red Hat OpenShift, OpenShift GitOps, Argo CD, Kubernetes, Helm, Kustomize, Git, RBAC, Operators

---

## 1. Short Interview Answer

When an **Argo CD Application shows `OutOfSync`**, it means the **live state running in the OpenShift cluster does not match the desired state stored in Git or the configured source repository**.

In GitOps, Git is treated as the source of truth. Argo CD continuously compares:

- **Desired state:** YAML, Helm chart, or Kustomize manifests stored in Git
- **Live state:** Actual Kubernetes/OpenShift resources currently present in the cluster

If there is any difference between these two states, Argo CD marks the application as **OutOfSync**.

This does **not always mean the application is down**. It only means there is configuration drift or a difference between Git and the cluster. The application may still be healthy and serving traffic, but it is no longer exactly matching the Git-defined desired state.

---

## 2. Real Interview Scenario

### Scenario

You are working as a senior OpenShift administrator. Your organization uses **OpenShift GitOps based on Argo CD** to deploy applications into production namespaces.

A developer reports:

> “My Argo CD application is showing `OutOfSync`. The pods are running, but Argo CD says the application is not synced. What does this mean, and how will you troubleshoot it?”

As a senior administrator, you should not simply click **Sync** immediately. You must first understand:

- What resource is different?
- Was the drift expected or accidental?
- Did someone manually change the resource in the cluster?
- Did an operator mutate the resource?
- Did a Helm/Kustomize template change?
- Is this a harmless metadata difference or a real production risk?
- Will syncing overwrite a live manual fix?

## 3. What Argo CD Sync Status Means

Argo CD maintains two important statuses for an application:

1. **Sync Status**
2. **Health Status**

These two are different.

---

## 4. Sync Status vs Health Status

### 4.1 Sync Status

Sync status tells whether the live cluster state matches the desired Git state.

Common sync statuses are:

| Sync Status | Meaning |
|---|---|
| `Synced` | Live state matches Git desired state |
| `OutOfSync` | Live state differs from Git desired state |
| `Unknown` | Argo CD cannot determine the state due to an error |

---

### 4.2 Health Status

Health status tells whether the application resources are operational.

Common health statuses are:

| Health Status | Meaning |
|---|---|
| `Healthy` | Application appears operational |
| `Progressing` | Resources are still rolling out |
| `Degraded` | One or more resources have a problem |
| `Suspended` | Resource is intentionally paused |
| `Missing` | Expected resource is missing |
| `Unknown` | Health cannot be evaluated |

---

## 5. Important Point for Interview

An application can be:

```text
OutOfSync + Healthy
```

This means:

- The app is running successfully
- Pods may be healthy
- Services may be reachable
- Routes may be working
- But the live configuration does not match Git

Example:

Someone manually changed the number of replicas from `3` to `5` using `oc scale`.

The application is healthy because pods are running, but it is OutOfSync because Git still says replicas should be `3`.

---

## 6. GitOps Concept Behind OutOfSync

In a GitOps model:

```text
Git Repository = Desired State
OpenShift Cluster = Live State
Argo CD = Reconciliation Engine
```

Argo CD continuously performs comparison:

```text
Desired State in Git  <---- compare ---->  Live State in Cluster
```

If both match:

```text
Application = Synced
```

If both differ:

```text
Application = OutOfSync
```

## 7. Common Causes of OutOfSync in OpenShift

There are many reasons why an Argo CD application becomes OutOfSync.

---

## 8. Cause 1: Manual Change in the Cluster

This is one of the most common reasons.

Example:

```bash
oc scale deployment frontend --replicas=5 -n app-prod
```

But Git contains:

```yaml
spec:
  replicas: 3
```

Argo CD detects that the live deployment has 5 replicas, while Git expects 3.

Result:

```text
Application Status: OutOfSync
```

### Interview Explanation

Manual changes break the GitOps principle because the cluster is no longer controlled only by Git. In production, manual changes should either be reverted or backported into Git after proper approval.

---

## 9. Cause 2: Resource Missing from the Cluster

A resource defined in Git may be missing from OpenShift.

Example:

Git contains:

```yaml
kind: ConfigMap
metadata:
  name: app-config
  namespace: app-prod
```

But someone deleted it:

```bash
oc delete configmap app-config -n app-prod
```

Argo CD detects that the desired ConfigMap exists in Git but not in the cluster.

Result:

```text
OutOfSync
```

The resource may show as:

```text
Missing
```

---

## 10. Cause 3: Extra Resource Exists in the Cluster

Sometimes a resource exists in OpenShift but is no longer present in Git.

Example:

A Secret or ConfigMap was removed from Git, but it still exists in the cluster.

Argo CD may show the resource as:

```text
OutOfSync / Requires pruning
```

This usually means the resource should be deleted if it is no longer part of the desired state.

However, deletion must be handled carefully, especially for:

- PVCs
- Secrets
- Routes
- Operator-managed resources
- StatefulSet data
- Database-related resources

---

## 11. Cause 4: Git Commit Changed but Application Not Synced Yet

If a developer commits a manifest change to Git, Argo CD detects the new desired state.

Example:

Git changed from:

```yaml
image: quay.io/company/payment:v1
```

To:

```yaml
image: quay.io/company/payment:v2
```

But the cluster is still running:

```yaml
image: quay.io/company/payment:v1
```

Result:

```text
OutOfSync
```

This is expected behavior when auto-sync is disabled.

---

## 12. Cause 5: Auto-Sync Disabled

If Argo CD is configured for manual sync, it will detect changes but not apply them automatically.

Example:

```yaml
syncPolicy: {}
```

or no automated sync policy is configured.

In this case, Argo CD only reports drift:

```text
OutOfSync
```

An administrator or developer must manually sync the application.

---

## 13. Cause 6: Operator or Controller Mutates the Resource

In OpenShift, many resources are modified by controllers or Operators after creation.

Examples:

- OpenShift Routes may receive generated status fields
- Deployments get defaulted values
- Operators may inject labels or annotations
- ServiceAccounts may get secrets or image pull secrets
- SecurityContextConstraints may influence pods
- HorizontalPodAutoscaler modifies replica counts indirectly
- OpenShift build/image controllers may update image references

Sometimes these automatic modifications create a diff between Git and the live object.

### Example

Git defines:

```yaml
spec:
  replicas: 3
```

HPA changes the live deployment to:

```yaml
spec:
  replicas: 6
```

Argo CD may show OutOfSync if it compares the replica field directly.

### Senior-Level Explanation

Not all drift is caused by humans. Some drift is caused by valid Kubernetes/OpenShift controllers. In that case, we may need to configure Argo CD `ignoreDifferences` for specific fields instead of forcing sync continuously.

---

## 14. Cause 7: Helm Chart Rendered Output Changed

If Argo CD deploys using Helm, it compares the rendered manifests, not just the raw chart files.

OutOfSync may occur because of:

- Changed values file
- Updated chart version
- Changed dependency chart
- Random values generated by templates
- Incorrect Helm release values
- Environment-specific override mismatch

Example:

```yaml
replicaCount: 2
```

changed to:

```yaml
replicaCount: 4
```

Argo CD renders a different Deployment manifest and marks the app OutOfSync.

---

## 15. Cause 8: Kustomize Overlay Difference

In OpenShift GitOps, teams often use Kustomize overlays:

```text
base/
overlays/dev/
overlays/test/
overlays/prod/
```

If Argo CD is pointing to the wrong overlay path, the desired state may not match the environment.

Example:

Production app accidentally points to:

```text
overlays/dev
```

instead of:

```text
overlays/prod
```

Result:

```text
OutOfSync or incorrect deployment configuration
```

---

## 16. Cause 9: Image Tag Drift

OutOfSync may happen when image tags are changed manually or updated outside Git.

Example:

Git contains:

```yaml
image: quay.io/company/backend:1.0.0
```

Live cluster has:

```yaml
image: quay.io/company/backend:1.0.1
```

This can happen due to:

- Manual `oc set image`
- External image updater
- CI/CD pipeline directly patching the cluster
- OpenShift ImageStream triggers

### Senior-Level Recommendation

In a strict GitOps environment, CI should update Git, not directly patch the OpenShift cluster.

Correct model:

```text
CI builds image -> CI updates Git image tag -> Argo CD syncs cluster
```

Incorrect model:

```text
CI builds image -> CI directly patches deployment in cluster
```

---

## 17. Cause 10: Namespace or RBAC Resource Drift

OutOfSync may also happen for cluster-scoped or namespace-scoped security resources.

Examples:

- Role
- RoleBinding
- ClusterRole
- ClusterRoleBinding
- ServiceAccount
- SecurityContextConstraints usage
- NetworkPolicy
- ResourceQuota
- LimitRange

Manual changes to RBAC are very common during troubleshooting.

Example:

```bash
oc adm policy add-role-to-user edit user1 -n app-prod
```

If that RoleBinding is not defined in Git, Argo CD may detect extra live RBAC configuration.

---

## 18. Cause 11: Resource Hook or Job Behavior

Argo CD supports hooks such as:

- PreSync
- Sync
- PostSync
- SyncFail
- PostDelete

Jobs created by hooks may complete and remain in the cluster. If hook deletion policies are not configured properly, Argo CD may show unexpected diffs.

Example annotation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
```

Without proper cleanup, completed hook jobs may remain and create confusion.

---

## 19. Cause 12: Secrets Managed Outside Git

Many organizations do not store raw Secrets in Git. Instead they use:

- External Secrets Operator
- Sealed Secrets
- HashiCorp Vault
- OpenShift Secrets created by automation
- CSI Secret Store driver

If Argo CD expects a Secret but another controller manages it, the live object may differ from Git.

This can cause OutOfSync due to:

- Data hash differences
- Auto-generated secret values
- Controller-added annotations
- OwnerReferences
- Refresh timestamps

### Senior-Level Note

Never blindly sync or prune secrets in production without understanding the ownership model.

---

## 20. Cause 13: PVC and Stateful Application Differences

Stateful applications can create OutOfSync conditions involving:

- PersistentVolumeClaim
- StatefulSet
- VolumeClaimTemplates
- StorageClass
- AccessModes
- Requested storage size

Example:

Git says:

```yaml
resources:
  requests:
    storage: 10Gi
```

Live PVC was expanded to:

```yaml
resources:
  requests:
    storage: 20Gi
```

Argo CD may show OutOfSync.

### Important Production Warning

PVC changes are sensitive. Do not force sync or prune PVCs without understanding application data impact.

---

## 21. Cause 14: Compare Options or Ignore Differences Not Configured

Some fields should not be compared because they are expected to change.

Examples:

- `status`
- `metadata.managedFields`
- HPA-controlled replicas
- Operator-generated annotations
- Certificate rotation timestamps
- Mutating webhook injected fields

Argo CD supports ignoring specific differences using `ignoreDifferences`.

Example:

```yaml
spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
    - /spec/replicas
```

This tells Argo CD not to mark the app OutOfSync only because the Deployment replica count differs.

Use this carefully. Do not hide important configuration drift.

## 22. Initial Troubleshooting Approach

As a senior OpenShift administrator, I would follow a structured troubleshooting flow.

---

## 23. Step 1: Check Application Status

```bash
oc get applications -n openshift-gitops
```

or if the application is in a custom Argo CD namespace:

```bash
oc get applications -n <argocd-namespace>
```

Example:

```bash
oc get applications -n openshift-gitops
```

Output:

```text
NAME              SYNC STATUS   HEALTH STATUS
payment-app       OutOfSync     Healthy
```

This tells us:

- App is OutOfSync
- App health is still Healthy
- Issue is likely configuration drift, not necessarily runtime failure

---

## 24. Step 2: Describe the Argo CD Application

```bash
oc describe application payment-app -n openshift-gitops
```

Check:

- Source repository URL
- Target revision
- Path or chart
- Destination namespace
- Sync policy
- Sync errors
- Resource status
- Events

Important fields:

```yaml
spec:
  source:
    repoURL:
    targetRevision:
    path:
  destination:
    server:
    namespace:
  syncPolicy:
```

---

## 25. Step 3: Use Argo CD CLI to Check App Details

If Argo CD CLI is available:

```bash
argocd app get payment-app
```

This shows:

- Sync status
- Health status
- Git revision
- Resources
- Which resource is OutOfSync
- Missing or extra resources

Example output:

```text
Name:               payment-app
Project:            default
Server:             https://kubernetes.default.svc
Namespace:          payment-prod

SyncWindow:         Sync Allowed

Sync Status:        OutOfSync from main
Health Status:      Healthy
```

## 26. Step 4: Identify Which Resource is OutOfSync

```bash
argocd app diff payment-app
```

This is one of the most important commands.

It shows the exact difference between:

- Git desired manifest
- Live OpenShift resource

Example:

```diff
- replicas: 3
+ replicas: 5
```

This means Git wants 3 replicas, but the cluster currently has 5.

---

## 27. Step 5: Check Application Resources

```bash
argocd app resources payment-app
```

Example output:

```text
GROUP        KIND        NAMESPACE      NAME            STATUS     HEALTH
apps         Deployment  payment-prod   payment-api     OutOfSync  Healthy
             Service     payment-prod   payment-api     Synced     Healthy
route.openshift.io Route payment-prod   payment-api     Synced     Healthy
```

Here, only the Deployment is OutOfSync.

## 28. Step 6: Check the Live Resource in OpenShift

```bash
oc get deployment payment-api -n payment-prod -o yaml
```

Check the live object carefully:

```bash
oc get deployment payment-api -n payment-prod -o yaml | less
```

Look for:

- replicas
- image
- environment variables
- labels
- annotations
- resources requests/limits
- nodeSelector
- tolerations
- affinity
- serviceAccountName
- securityContext
- volumes
- volumeMounts

## 29. Step 7: Compare with Git Manifest

Check the Git repository:

```bash
git clone https://git.example.com/platform/payment.git
cd payment
```

Check the application path:

```bash
cat overlays/prod/deployment.yaml
```

or render Kustomize:

```bash
kubectl kustomize overlays/prod
```

For Helm:

```bash
helm template payment ./chart -f values-prod.yaml
```

Compare rendered output with the live resource.

## 30. Step 8: Check Whether Someone Manually Changed the Resource

Check resource events:

```bash
oc describe deployment payment-api -n payment-prod
```

Check annotations:

```bash
oc get deployment payment-api -n payment-prod -o jsonpath='{.metadata.annotations}'
```

Check managed fields:

```bash
oc get deployment payment-api -n payment-prod -o yaml | grep -A20 managedFields
```

Managed fields may show which manager modified the resource:

- `argocd-controller`
- `oc`
- `kubectl`
- `openshift-controller-manager`
- `horizontal-pod-autoscaler`
- `operator`
- `helm`

This helps identify whether drift was caused by Argo CD, a user, or another controller.

---

## 31. Step 9: Check Argo CD Application Controller Logs

In OpenShift GitOps, Argo CD components usually run in the `openshift-gitops` namespace.

```bash
oc get pods -n openshift-gitops
```

Check controller logs:

```bash
oc logs deployment/openshift-gitops-application-controller -n openshift-gitops
```

If the deployment name differs:

```bash
oc get deploy -n openshift-gitops
```

Then:

```bash
oc logs deploy/<argocd-application-controller-deployment> -n openshift-gitops
```

Look for:

- comparison errors
- manifest generation errors
- RBAC permission errors
- Git authentication errors
- resource tracking issues
- cache errors
- diff normalization errors

---

## 32. Step 10: Check Repository Connectivity

Sometimes OutOfSync or Unknown status may happen because Argo CD cannot properly access the Git repository.

Check repositories:

```bash
argocd repo list
```

Check repo connection:

```bash
argocd repo get https://git.example.com/platform/payment.git
```

In OpenShift:

```bash
oc get secrets -n openshift-gitops
```

Repository credentials are usually stored as secrets.

Check for:

- expired token
- wrong SSH key
- wrong branch
- Git server certificate issue
- network/proxy issue
- repository moved or renamed

---

## 33. Step 11: Check Manifest Generation Errors

For Helm or Kustomize apps, Argo CD may fail to render manifests correctly.

Common errors:

- invalid YAML
- missing values file
- Helm dependency issue
- Kustomize patch failure
- wrong path
- wrong branch
- missing CRD
- plugin error

Command:

```bash
argocd app get payment-app
```

Look for messages such as:

```text
ComparisonError
Manifest generation error
```

For Kustomize locally:

```bash
kubectl kustomize overlays/prod
```

For Helm locally:

```bash
helm dependency build ./chart
helm template payment ./chart -f values-prod.yaml
```

---

## 34. Step 12: Check Argo CD Project Permissions

An Argo CD Application belongs to an AppProject.

Check:

```bash
oc get appproject -n openshift-gitops
```

Describe project:

```bash
oc describe appproject <project-name> -n openshift-gitops
```

Important fields:

```yaml
spec:
  sourceRepos:
  destinations:
  clusterResourceWhitelist:
  namespaceResourceWhitelist:
```

If AppProject restrictions prevent Argo CD from managing certain resources, sync or comparison may fail.

---

## 35. Step 13: Check RBAC Permission of Argo CD

Argo CD needs permission to read and apply resources in destination namespaces.

Check service account:

```bash
oc get sa -n openshift-gitops
```

Common controller service account:

```text
openshift-gitops-argocd-application-controller
```

Check permissions:

```bash
oc auth can-i get deployments \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payment-prod
```

Check apply/update permission:

```bash
oc auth can-i patch deployments \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payment-prod
```

Check create permission:

```bash
oc auth can-i create routes \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payment-prod
```

If Argo CD cannot read or patch resources, it may show sync errors or fail to reconcile.

---

## 36. Step 14: Check Resource Tracking Method

Argo CD tracks resources using labels or annotations.

Common tracking label:

```yaml
app.kubernetes.io/instance: payment-app
```

If labels are manually changed or overwritten, Argo CD may lose ownership tracking.

Check resource labels:

```bash
oc get deployment payment-api -n payment-prod --show-labels
```

Check application instance label:

```bash
oc get all -n payment-prod -l app.kubernetes.io/instance=payment-app
```

If resource tracking labels are removed, Argo CD may think resources are missing or orphaned.

---

## 37. Step 15: Check Sync Policy

Check if auto-sync is enabled:

```bash
oc get application payment-app -n openshift-gitops -o yaml
```

Look for:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

Meaning:

| Option | Meaning |
|---|---|
| `automated` | Argo CD automatically syncs Git changes |
| `prune` | Deletes resources removed from Git |
| `selfHeal` | Reverts manual cluster drift automatically |

---

## 38. Auto-Sync Behavior

If auto-sync is enabled:

```yaml
syncPolicy:
  automated: {}
```

Argo CD automatically applies Git changes.

If self-heal is enabled:

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

Argo CD automatically corrects manual changes in the cluster.

Example:

If someone changes replicas from 3 to 5 manually, Argo CD changes it back to 3.

---

## 39. Manual Sync Behavior

If auto-sync is disabled, Argo CD only detects differences.

Example:

```text
Git changed -> Argo CD detects change -> App becomes OutOfSync -> Admin manually syncs
```

Manual sync command:

```bash
argocd app sync payment-app
```

Or using OpenShift console:

```text
OpenShift Console -> GitOps -> Application -> Sync
```

---

## 40. Should We Immediately Click Sync?

No. In production, do not blindly sync.

Before syncing, confirm:

- What changed?
- Why did it change?
- Is Git correct?
- Is live cluster correct?
- Will sync restart pods?
- Will sync reduce replicas?
- Will sync delete resources?
- Will sync overwrite emergency fixes?
- Will prune delete PVCs or Secrets?

---

## 41. Production-Safe Decision Flow

Use this decision flow:

```text
Application OutOfSync
        |
        v
Check Argo CD diff
        |
        v
Identify resource and field difference
        |
        v
Is Git correct?
   |              |
  Yes             No
   |              |
Sync app       Update Git first
   |              |
Validate       Let Argo CD sync after Git correction
```

## 42. Example 1: Manual Replica Change

### Problem

App is OutOfSync.

Diff:

```diff
- replicas: 3
+ replicas: 5
```

### Meaning

Git expects 3 replicas. Cluster has 5 replicas.

### Investigation

```bash
argocd app diff payment-app
oc get deployment payment-api -n payment-prod -o yaml
oc describe deployment payment-api -n payment-prod
```

### Decision

If 5 replicas were added temporarily during high traffic, update Git if the change should stay.

If 5 replicas were accidental, sync from Git:

```bash
argocd app sync payment-app
```

---

## 43. Example 2: Image Changed Manually

### Problem

Diff:

```diff
- image: quay.io/company/payment:v1.2.0
+ image: quay.io/company/payment:v1.2.1
```

### Meaning

Cluster is running a different image than Git.

### Possible Cause

Someone ran:

```bash
oc set image deployment/payment-api payment-api=quay.io/company/payment:v1.2.1 -n payment-prod
```

### Correct Remediation

If `v1.2.1` is approved, update Git:

```yaml
image: quay.io/company/payment:v1.2.1
```

Then commit and let Argo CD sync.

If it is not approved, sync app to revert to Git:

```bash
argocd app sync payment-app
```

---

## 44. Example 3: ConfigMap Deleted Manually

### Problem

Argo CD shows ConfigMap as Missing.

```text
ConfigMap app-config Missing OutOfSync
```

### Meaning

Git contains the ConfigMap, but it does not exist in OpenShift.

### Remediation

Sync the app:

```bash
argocd app sync payment-app
```

Validate:

```bash
oc get configmap app-config -n payment-prod
oc rollout status deployment/payment-api -n payment-prod
```

---

## 45. Example 4: Resource Removed from Git but Still Exists in Cluster

### Problem

Argo CD shows resource requires pruning.

```text
Service old-api OutOfSync requires pruning
```

### Meaning

Resource exists in the cluster but is no longer present in Git.

### Remediation

If the resource is truly obsolete:

```bash
argocd app sync payment-app --prune
```

But before pruning, verify impact:

```bash
oc get svc old-api -n payment-prod
oc get endpoints old-api -n payment-prod
oc get route -n payment-prod
```

Do not prune blindly in production.

---

## 46. Example 5: HPA Causing Replica Drift

### Problem

Git says replicas should be 2. HPA scales to 8.

Argo CD shows OutOfSync on Deployment replicas.

### Meaning

HPA is expected to control replicas. Argo CD should not fight with HPA.

### Better Solution

Configure ignore difference for replicas:

```yaml
spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
    - /spec/replicas
```

This prevents Argo CD from continuously marking replica changes as drift.

---

## 47. Example 6: Operator-Managed Resource Drift

### Problem

An Operator updates annotations or spec fields after Argo CD applies a resource.

### Meaning

The Operator is reconciling the resource according to its own logic.

### Troubleshooting

```bash
oc get <resource> <name> -n <namespace> -o yaml
oc describe <resource> <name> -n <namespace>
oc logs deploy/<operator-controller> -n <operator-namespace>
```

### Remediation

Possible options:

- Accept Operator-managed fields
- Add `ignoreDifferences`
- Move ownership fully to Operator
- Avoid managing generated child resources directly through Argo CD

## 50. Understanding Diff Output

Example diff:

```diff
===== apps/Deployment payment-prod/payment-api ======
@@ -10,7 +10,7 @@
 spec:
-  replicas: 3
+  replicas: 5
```

Interpretation:

- `-` usually represents desired Git state
- `+` usually represents live cluster state
- Git expects 3 replicas
- Cluster currently has 5 replicas

Always carefully confirm the direction of diff in your CLI output and UI before taking action.

## 51. Argo CD Sync Options

Argo CD supports sync options to control behavior.

Example:

```yaml
syncPolicy:
  syncOptions:
  - CreateNamespace=true
  - PruneLast=true
  - ApplyOutOfSyncOnly=true
```

Common sync options:

| Sync Option | Meaning |
|---|---|
| `CreateNamespace=true` | Create destination namespace automatically |
| `PruneLast=true` | Delete pruned resources after applying others |
| `ApplyOutOfSyncOnly=true` | Apply only resources that are OutOfSync |
| `Validate=false` | Skip kubectl validation |
| `ServerSideApply=true` | Use server-side apply |
| `Replace=true` | Replace resource instead of patching |

Use sync options carefully in production.

## 52. Prune in Argo CD

Prune means Argo CD deletes live resources that are no longer defined in Git.

Example:

Git removed:

```yaml
kind: Service
metadata:
  name: old-api
```

But OpenShift still has:

```bash
oc get svc old-api -n payment-prod
```

Argo CD may show it as requiring pruning.

To prune:

```bash
argocd app sync payment-app --prune
```

### Production Warning

Prune can delete important resources. Be very careful with:

- PVCs
- Secrets
- ConfigMaps
- Routes
- Services
- ServiceAccounts
- RBAC
- CRDs
- Operator custom resources

---

## 53. Self-Heal in Argo CD

Self-heal means Argo CD automatically corrects manual drift in the cluster.

Example:

Git:

```yaml
replicas: 3
```

User manually changes:

```bash
oc scale deployment payment-api --replicas=5 -n payment-prod
```

With self-heal enabled, Argo CD changes it back to 3.

Example configuration:

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

### Senior-Level View

Self-heal is useful for enforcing GitOps discipline, but in production it must be combined with change management. Emergency changes should be backported into Git or they will be reverted.

---

## 54. Automated Sync with Prune and Self-Heal

Example:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
  - ApplyOutOfSyncOnly=true
```

Meaning:

- Git changes are automatically applied
- Manual drift is automatically corrected
- Resources removed from Git are deleted
- Only OutOfSync resources are applied

This is powerful but should be enabled only after proper governance.

## 58. OutOfSync Due to RBAC Denial

Example error:

```text
deployments.apps is forbidden: User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller" cannot patch resource "deployments" in namespace "payment-prod"
```

### Meaning

Argo CD does not have enough permission in the target namespace.

### Fix

Grant appropriate role:

```bash
oc adm policy add-role-to-user edit \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payment-prod
```

For production, use least privilege RBAC instead of broad permissions whenever possible.

---

## 59. OutOfSync Due to Missing CRD

If Git contains a custom resource but the CRD is not installed, sync may fail.

Example:

```text
no matches for kind "ExternalSecret" in version "external-secrets.io/v1beta1"
```

### Meaning

The CustomResourceDefinition for `ExternalSecret` is not available in the cluster.

### Troubleshooting

```bash
oc get crd | grep externalsecret
oc api-resources | grep -i external
```

### Fix

Install the required Operator or CRD before syncing the application.

---

## 60. OutOfSync Due to Admission Webhook Mutation

Admission webhooks may mutate resources during creation or update.

Examples:

- service mesh sidecar injection
- security context mutation
- policy engine mutation
- certificate injection
- image policy webhook

This can cause live resources to differ from Git.

### Fix Options

- Accept the mutation and configure ignore differences
- Store mutated configuration in Git if appropriate
- Adjust webhook policy
- Disable injection for selected namespaces if required

---

## 61. OutOfSync Due to Resource Quota or LimitRange Defaults

OpenShift namespaces may have LimitRange that injects default CPU and memory requests/limits.

Example:

Git does not define resources:

```yaml
resources: {}
```

LimitRange injects:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 256Mi
```

This may create differences depending on the resource and comparison behavior.

### Best Practice

Define resource requests and limits explicitly in Git for production workloads.

---

## 62. OutOfSync Due to Generated Fields

Kubernetes adds many generated fields:

- `resourceVersion`
- `uid`
- `creationTimestamp`
- `managedFields`
- `status`

Normally Argo CD ignores many of these fields. But some custom resources may include generated spec fields that need explicit ignore rules.

---

## 63. How to Configure Ignore Differences

Example for Deployment replicas:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-app
  namespace: openshift-gitops
spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
    - /spec/replicas
```

Example for an annotation:

```yaml
spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jqPathExpressions:
    - .metadata.annotations."operator.example.com/last-updated"
```

### Important Warning

Do not use ignore rules to hide real configuration problems. Use them only for fields that are intentionally managed by another controller.

## 64. OutOfSync and Sync Waves

Argo CD supports sync waves to control order of resource deployment.

Example:

```yaml
metadata:

    argocd.argoproj.io/sync-wave: "0"
```

Resources with lower wave numbers are applied first.

Common order:

```text
Namespace -> RBAC -> ConfigMap/Secret -> Service -> Deployment -> Route
```

If dependencies are not ordered correctly, sync may fail or remain partially OutOfSync.

## 67. Hard Refresh vs Normal Refresh

### Normal Refresh

```bash
argocd app get payment-app --refresh
```

Refreshes application state.

### Hard Refresh

```bash
argocd app get payment-app --hard-refresh
```

Clears manifest cache and forces Argo CD to regenerate manifests from source.

Use hard refresh when:

- Helm dependency changed
- Kustomize output changed unexpectedly
- Git cache seems stale
- Argo CD UI shows old diff
- Repo server cache issue is suspected

## 70. Production Remediation Options

Depending on the cause, remediation may be different.

| Cause | Remediation |
|---|---|
| Git changed, cluster not updated | Sync application |
| Manual cluster change is wrong | Sync from Git to revert |
| Manual cluster change is valid | Commit the change to Git |
| HPA changed replicas | Configure ignore difference for replicas |
| Operator changed generated field | Configure ignore difference or change ownership model |
| Resource removed from Git | Sync with prune after impact review |
| Argo CD lacks permissions | Fix RBAC |
| Manifest generation error | Fix Helm/Kustomize/YAML |
| Git credentials issue | Fix repo secret/token/SSH key |
| Missing CRD | Install required Operator/CRD first |

### Issue

```text
Application: payment-app
Sync Status: OutOfSync
Health Status: Healthy
Namespace: payment-prod
```


Diff:

```diff
- image: quay.io/company/payment:v1.5.0
+ image: quay.io/company/payment:v1.5.1-hotfix
```

### Step 3: Check Live Deployment

```bash
oc get deployment payment-api -n payment-prod -o yaml | grep image
```

Output:

```text
image: quay.io/company/payment:v1.5.1-hotfix
```

### Step 4: Check History


### Step 5: Check Who Changed It

```bash
oc get deployment payment-api -n payment-prod -o yaml | grep -A30 managedFields
```

Found manager:

```text
manager: oc
```

A production hotfix was applied manually using `oc set image`, but Git was not updated.

### Correct Fix

If hotfix is approved:

1. Update Git image tag to `v1.5.1-hotfix`
2. Create pull request
3. Get approval
4. Merge PR
5. Let Argo CD sync

If hotfix is not approved:

```bash
argocd app sync payment-app
```

This reverts the cluster to Git state.

## 74. What Not to Do

Avoid these mistakes:

```text
Do not blindly click Sync in production.
Do not prune resources without impact analysis.
Do not ignore all differences globally.
Do not manually patch GitOps-managed resources repeatedly.
Do not allow CI/CD pipelines to bypass GitOps.
Do not store unencrypted sensitive secrets directly in Git.
Do not disable self-heal without understanding governance impact.
Do not manage Operator-generated child resources directly unless required.
```

## 75. Best Practices to Prevent OutOfSync Issues

### 75.1 Enforce Git as Source of Truth

All changes should go through Git pull requests.

Correct workflow:

```text
Developer -> Git PR -> Review -> Merge -> Argo CD Sync -> OpenShift
```

---

### 75.2 Avoid Manual Production Changes

Manual changes should be limited to emergency cases.

If manual change is made:

- Document it
- Raise incident/change record
- Backport the change to Git
- Reconcile Argo CD

---

### 75.3 Use Auto-Sync Carefully

For lower environments:

```yaml
automated:
  prune: true
  selfHeal: true
```

For production, choose based on governance:

- Manual sync with approval
- Auto-sync with sync windows
- Auto-sync without prune
- Self-heal enabled only after maturity

---

### 75.4 Configure Sync Windows

Sync windows help control when apps can sync.

Example use cases:

- Allow sync during maintenance window
- Deny sync during business hours
- Freeze production during release blackout

---

### 75.5 Use Ignore Differences Properly

Ignore only fields managed by other controllers.

Good examples:

- HPA-managed replicas
- Operator-generated timestamps
- Certificate rotation fields

Bad examples:

- container image
- environment variables
- security context
- RBAC permissions
- network policy rules

---

### 75.6 Separate App Ownership Clearly

Do not let multiple tools control the same field.

Bad model:

```text
Argo CD controls replicas
HPA controls replicas
Manual admin controls replicas
CI pipeline controls replicas
```

Good model:

```text
Git controls baseline deployment
HPA controls runtime scaling
Argo CD ignores HPA-managed replica drift
```

---

### 75.7 Use AppProject Boundaries

Use AppProjects to restrict:

- allowed repositories
- allowed namespaces
- allowed clusters
- allowed resource kinds

This improves security and governance.

---

### 75.8 Use Separate Applications for Platform and Workloads

Separate GitOps apps for:

- namespaces
- RBAC
- quotas
- operators
- monitoring
- application workloads
- secrets integration

This reduces blast radius and makes OutOfSync troubleshooting easier.

## 85. Final Interview-Level Summary

`OutOfSync` in Argo CD means the OpenShift cluster does not match the desired state stored in Git.

It can happen because of:

- Git changes not yet applied
- manual cluster changes
- missing resources
- extra resources requiring prune
- Helm or Kustomize rendering changes
- HPA changes
- Operator mutations
- admission webhook mutations
- RBAC problems
- repository or manifest generation issues
- resource tracking problems

A senior OpenShift administrator should not blindly sync. The correct approach is to identify the exact diff, understand ownership of the changed field, assess production impact, and then choose the correct remediation:

```text
If Git is correct      -> Sync application
If live change is valid -> Update Git
If controller owns field -> Configure ignoreDifferences
If resource is obsolete -> Prune after impact review
If Argo CD lacks access -> Fix RBAC
If manifest is broken   -> Fix Git/Helm/Kustomize
```

In enterprise OpenShift administration, Argo CD OutOfSync is not only a deployment status. It is a signal of drift, governance, compliance, and operational control.

> Argo CD `OutOfSync` means the live OpenShift resources differ from the Git-defined desired state; I would inspect the exact diff, identify whether the drift is manual, Git-driven, controller-driven, or permission-related, and then safely reconcile by syncing, updating Git, configuring ignore rules, or fixing RBAC without blindly overwriting production changes.
