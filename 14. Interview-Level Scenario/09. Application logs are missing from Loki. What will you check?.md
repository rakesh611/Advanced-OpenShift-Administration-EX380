# Application Logs Are Missing from Loki — Interview-Level Troubleshooting Scenario

**Role level:** Advanced OpenShift Administrator / Senior OpenShift Platform Engineer  
**Experience expectation:** 10+ years Linux, Kubernetes, OpenShift, observability, production operations  
**Scenario:** Application teams report that application logs are not visible in Loki / OpenShift Console / Grafana, but pods are running.

---

## 1. How I Would Answer in an Interview

If application logs are missing from Loki, I do not start directly with Loki queries. I first isolate where the log flow is broken.

In OpenShift Logging, the normal flow is:

```text
Application Container stdout/stderr
        ↓
Node container log files under /var/log/pods and /var/log/containers
        ↓
Collector DaemonSet, usually Vector in newer OpenShift Logging
        ↓
ClusterLogForwarder pipeline
        ↓
Loki Gateway / Distributor / Ingester
        ↓
Object storage / Loki chunks and index
        ↓
Query frontend / Querier / OpenShift Console / Grafana
```

So I troubleshoot in layers:

1. Confirm the application is really writing logs to stdout/stderr.
2. Confirm logs exist on the node.
3. Confirm logging operators and collector pods are healthy.
4. Check `ClusterLogForwarder` pipelines and whether `application` input is selected.
5. Check collector errors, RBAC, service account permissions, TLS, proxy, DNS, and endpoint reachability.
6. Check LokiStack health, tenants, storage, retention, object storage, rate limits, and ingestion errors.
7. Check query-side issues: wrong tenant, wrong labels, wrong namespace, time range, RBAC, console plugin, or Grafana datasource.
8. Fix the exact broken layer and validate end-to-end ingestion.

A senior engineer should not say only, “restart Loki.” Missing logs can be caused by wrong pipeline configuration, collector not running on a node, namespace excluded by filters, application writing to files instead of stdout, tenant mismatch, storage failure, rate limiting, RBAC, or query mistakes.

## 2. Important OpenShift Logging Concepts

OpenShift Logging with Loki usually contains these major components:

| Component | Purpose |
|---|---|
| **Red Hat OpenShift Logging Operator** | Manages log collection and forwarding configuration. |
| **Loki Operator** | Manages `LokiStack` and Loki components. |
| **ClusterLogForwarder** | Defines which logs are collected, processed, and forwarded. |
| **Collector DaemonSet** | Runs on nodes and collects logs, commonly Vector in newer versions. |
| **LokiStack** | Stores logs and exposes query APIs through Loki gateway. |
| **Object Storage** | Backend for Loki chunks and indexes, for example S3, Azure Blob, GCS, ODF, or MinIO. |
| **OpenShift Console / Observability UI / Grafana** | Query and visualization layer. |

Red Hat documentation describes LokiStack as the log store for application, infrastructure, and audit logs, and ClusterLogForwarder as the resource used to select log sources and forward them through pipelines to outputs.

## 3. First Clarifying Questions I Would Ask

In a real interview, I would ask a few targeted questions before jumping into commands:

```text
1. Are only application logs missing, or are infrastructure and audit logs also missing?
2. Are logs missing for all namespaces or only one namespace/application?
3. Did it start after an upgrade, logging operator change, LokiStack change, or ClusterLogForwarder update?
4. Are logs missing in OpenShift Console only, or also missing when querying Loki directly?
5. Are application pods writing logs to stdout/stderr or to files inside the container?
6. Which OpenShift Logging version is used? Logging 5.x or Logging 6.x?
7. Is the collector Vector or Fluentd?
8. Is LokiStack using object storage, ODF, MinIO, S3, or another backend?
9. Are there any recent namespace labels, NetworkPolicy, proxy, certificate, or RBAC changes?
```

These questions help me separate ingestion problems from query, UI, RBAC, and application logging-pattern problems.

## 4. Confirm the Problem Scope

### 4.1 Check if the Application Is Producing Logs

First, confirm the pod itself is generating logs.

```bash
oc -n <app-namespace> get pods
oc -n <app-namespace> logs <pod-name> --tail=50
```

For multi-container pods:

```bash
oc -n <app-namespace> logs <pod-name> -c <container-name> --tail=50
```

For previous crashed container logs:

```bash
oc -n <app-namespace> logs <pod-name> -c <container-name> --previous --tail=100
```

If `oc logs` shows nothing, Loki cannot ingest anything unless the application writes to stdout/stderr. In Kubernetes/OpenShift, container logs normally come from stdout and stderr. If an application writes only to `/var/log/app.log` inside the container, the default OpenShift collector will not automatically collect that file.

### 4.2 Check Whether the Issue Is Namespace-Specific

```bash
oc logs -n <namespace-a> deploy/<deployment-a> --tail=20
oc logs -n <namespace-b> deploy/<deployment-b> --tail=20
```

Then query Loki or the console for both namespaces.

If only one namespace is missing, suspect:

- Namespace not included in `ClusterLogForwarder` input selector.
- Label-based filter excludes namespace.
- RBAC prevents user from seeing logs.
- Application writes no stdout/stderr.
- Collector pod missing on the node where that workload runs.
- NetworkPolicy or node-level problem affecting a subset of nodes.

If all application logs are missing but infrastructure logs exist, suspect:

- `application` input missing from pipeline.
- Application tenant query issue.
- `ClusterLogForwarder` misconfiguration.
- Collector unable to read application logs.
- Loki ingestion rejected for application tenant.

If all log types are missing, suspect:

- Collector DaemonSet failure.
- LokiStack failure.
- Object storage failure.
- Gateway/distributor/ingester failure.
- Global network/proxy/TLS issue.

## 6. Check LokiStack Health

### 6.1 List LokiStack Resources

```bash
oc get lokistack -A
```

Describe the LokiStack:

```bash
oc -n openshift-logging describe lokistack <lokistack-name>
oc -n openshift-logging get lokistack <lokistack-name> -o yaml
```

Check status conditions:

```bash
oc -n openshift-logging get lokistack <lokistack-name> -o jsonpath='{.status.conditions}' | jq
```

Look for conditions such as:

```text
Ready
Degraded
Pending
Failed
```

### 6.2 Check Loki Pods

Depending on the deployment mode, LokiStack may run components such as:

```text
compactor
querier
query-frontend
distributor
ingester
gateway
index-gateway
ruler
```

Command:

```bash
oc -n openshift-logging get pods -l app.kubernetes.io/part-of=lokistack
oc -n openshift-logging get pods | egrep 'loki|gateway|querier|ingester|distributor|compactor|index'
```

Check restarts:

```bash
oc -n openshift-logging get pods -o wide
oc -n openshift-logging get pods --sort-by=.status.containerStatuses[0].restartCount
```

Describe failing pods:

```bash
oc -n openshift-logging describe pod <loki-pod>
```

Check logs:

```bash
oc -n openshift-logging logs <loki-pod> --all-containers --tail=200
```

For previous crash:

```bash
oc -n openshift-logging logs <loki-pod> --all-containers --previous --tail=200
```

### 6.3 Common LokiStack Failure Indicators

Search for these in Loki pod logs:

```bash
oc -n openshift-logging logs <pod> --all-containers | egrep -i 'error|warn|denied|timeout|throttle|rate|limit|object|s3|bucket|forbidden|unauthorized|certificate|x509|dns|refused|deadline|ingester|chunk|index'
```

Common issues:

| Error Pattern | Meaning |
|---|---|
| `x509: certificate signed by unknown authority` | TLS trust issue. |
| `AccessDenied` / `Forbidden` | Object storage credential or IAM policy issue. |
| `NoSuchBucket` | Wrong bucket name or bucket missing. |
| `timeout` / `i/o timeout` | Network, proxy, DNS, object storage reachability issue. |
| `too many outstanding requests` | Query pressure or rate limiting. |
| `rate limit exceeded` | Loki ingestion or query limit reached. |
| `no space left on device` | Local disk or PVC issue. |
| `context deadline exceeded` | Backend, network, DNS, or overloaded component. |

## 7. Check Collector Health

### 7.1 Identify Collector DaemonSet

```bash
oc -n openshift-logging get ds
oc -n openshift-logging get pods -o wide | egrep 'collector|vector|fluentd'
```

For Vector-based logging:

```bash
oc -n openshift-logging get ds collector -o wide
```

For older Fluentd-based logging:

```bash
oc -n openshift-logging get ds | grep fluentd
```

### 7.2 Confirm Collector Runs on Every Required Node

```bash
oc get nodes -o wide
oc -n openshift-logging get pods -o wide | egrep 'collector|vector|fluentd'
```

Compare application pod node:

```bash
oc -n <app-namespace> get pod <pod-name> -o wide
```

If the application pod is on `worker-3`, but the collector pod on `worker-3` is missing, pending, crashlooping, or not ready, logs from that node may be missing.

### 7.3 Check Collector Pod Logs

```bash
oc -n openshift-logging logs <collector-pod> --all-containers --tail=300
```

Search for problems:

```bash
oc -n openshift-logging logs <collector-pod> --all-containers | egrep -i 'error|warn|loki|forbidden|unauthorized|x509|tls|timeout|connection|refused|dropped|parse|rate|backpressure|buffer|permission|denied|read|file|kubernetes'
```

Important collector-side symptoms:

| Symptom | Possible Cause |
|---|---|
| Collector pod CrashLoopBackOff | Bad config, resource pressure, image issue, SCC issue. |
| `permission denied` reading logs | SecurityContext/SCC/hostPath issue. |
| `x509` errors | Collector does not trust Loki gateway certificate. |
| `401` / `403` | Token, RBAC, tenant auth, or service account issue. |
| `connection refused` | Loki gateway/distributor service unavailable. |
| `no route to host` | NetworkPolicy, SDN/OVN issue, node networking issue. |
| `buffer full` / `backpressure` | Loki slow/unavailable or collector resource pressure. |
| `dropped events` | Filter, parse error, transform, or output failure. |

### 7.4 Check Collector Events

```bash
oc -n openshift-logging describe pod <collector-pod>
oc -n openshift-logging get events --sort-by=.lastTimestamp | tail -50
```

Look for:

```text
FailedMount
FailedCreatePodSandBox
ImagePullBackOff
OOMKilled
Evicted
NodePressure
Readiness probe failed
Liveness probe failed
```

## 8. Check ClusterLogForwarder Configuration

This is one of the most common root causes.

### 8.1 List ClusterLogForwarders

```bash
oc get clusterlogforwarder -A
```

Depending on OpenShift Logging version, the `ClusterLogForwarder` may be cluster-scoped or namespace-scoped.

Get full YAML:

```bash
oc -n openshift-logging get clusterlogforwarder <name> -o yaml
```

### 8.2 Check Inputs

A pipeline must include application logs. Look for something like:

```yaml
spec:
  pipelines:
  - name: application-logs
    inputRefs:
    - application
    outputRefs:
    - default
```

If the pipeline only has infrastructure or audit, application logs will not be forwarded.

Bad example:

```yaml
spec:
  pipelines:
  - name: infra-only
    inputRefs:
    - infrastructure
    outputRefs:
    - default
```

Correct example:

```yaml
spec:
  pipelines:
  - name: app-to-loki
    inputRefs:
    - application
    outputRefs:
    - default
```

### 8.3 Check Namespace Selectors

Some configurations include only selected namespaces.

Example:

```yaml
spec:
  inputs:
  - name: selected-apps
    application:
      namespaces:
      - payments
      - orders
```

If the missing application runs in `claims`, it will not be collected.

Check namespace:

```bash
oc get ns <app-namespace> --show-labels
```

If label selectors are used:

```yaml
application:
  selector:
    matchLabels:
      logging: enabled
```

Then validate:

```bash
oc get ns --show-labels | grep <app-namespace>
```

Fix by labeling namespace if that is the intended design:

```bash
oc label namespace <app-namespace> logging=enabled
```

Or update `ClusterLogForwarder` to include the namespace.

### 8.4 Check Filters

Filters can drop logs silently from the user perspective.

Look for filters such as:

```yaml
filters:
- name: drop-debug
  type: drop
```

or pipelines referencing filters:

```yaml
pipelines:
- name: app-pipeline
  inputRefs:
  - application
  filterRefs:
  - drop-noisy-namespaces
  outputRefs:
  - default
```

Check whether the application namespace, labels, container, or severity is being dropped.

### 8.5 Check Output References

Confirm the pipeline output points to the correct Loki output.

```yaml
outputs:
- name: default
  type: lokiStack
  lokiStack:
    target:
      name: logging-loki
      namespace: openshift-logging
```

Common mistakes:

- Wrong `LokiStack` name.
- Wrong namespace.
- Output removed but pipeline still references it.
- Pipeline references `default`, but no default output exists.
- Secret referenced by output is missing.
- TLS config wrong.

Check CLF conditions:

```bash
oc -n openshift-logging get clusterlogforwarder <name> -o jsonpath='{.status.conditions}' | jq
oc -n openshift-logging describe clusterlogforwarder <name>
```

Look for:

```text
Ready=False
ValidationFailure
OutputError
PipelineError
CollectorDeadEnd
```

## 9. Check RBAC and Tenant Access

Logs may be ingested into Loki, but the user may not be allowed to see them.

### 9.1 Test with Cluster Admin

As cluster-admin, query the same namespace. If cluster-admin sees logs but developer does not, ingestion is fine and the issue is RBAC/query authorization.

```bash
oc auth can-i get pods/log -n <app-namespace> --as=<user>
oc auth can-i view logs -n <app-namespace> --as=<user>
```

Also check project access:

```bash
oc adm policy who-can get pods/log -n <app-namespace>
oc get rolebinding -n <app-namespace>
oc get clusterrolebinding | grep <user-or-group>
```

Grant appropriate access if required:

```bash
oc adm policy add-role-to-user view <user> -n <app-namespace>
```

Or group-based:

```bash
oc adm policy add-role-to-group view <group-name> -n <app-namespace>
```

### 9.2 Understand Loki Tenants

OpenShift Logging commonly separates logs by tenant/log type such as:

```text
application
infrastructure
audit
```

If you query the wrong tenant, logs may appear missing.

Application logs must be queried under the application tenant/context, not infrastructure or audit.

## 10. Check Query Problems

Many “missing logs” incidents are query mistakes.

### 10.1 Check Time Range

Validate the query time range:

```text
Last 5 minutes
Last 30 minutes
Last 1 hour
Last 24 hours
```

If the application did not generate recent logs, a short query window will show nothing.

Generate a test log:

```bash
oc -n <app-namespace> exec deploy/<deployment-name> -- sh -c 'echo test-log-$(date)'
```

If `exec` is not possible, restart a pod or trigger a request to the application.

### 10.2 Use Correct Labels

Depending on collector and Loki label mapping, labels may include:

```text
namespace_name
kubernetes_namespace_name
pod
pod_name
kubernetes_pod_name
container
container_name
log_type
```

Try broader queries first.

Example LogQL-style queries:

```logql
{namespace_name="myapp"}
```

```logql
{namespace_name="myapp", pod_name=~"api-.*"}
```

```logql
{namespace_name="myapp"} |= "ERROR"
```

If labels changed after an upgrade, old dashboards may query old labels and return empty results.

### 10.3 Query Without Too Many Filters

Bad query:

```logql
{namespace_name="payments", pod_name="payments-api-7f8d9", container_name="app"} |= "TransactionFailed"
```

Better first test:

```logql
{namespace_name="payments"}
```

Then narrow it down.

## 11. Check Application Logging Behavior

### 11.1 Application Writes to File Instead of stdout/stderr

Check inside the pod:

```bash
oc -n <app-namespace> rsh <pod-name>
ls -l /var/log
find / -name '*.log' 2>/dev/null | head
```

If logs are inside the container file system only, default OpenShift logging will not collect them automatically.

Preferred fix:

- Configure application to write logs to stdout/stderr.
- For Java apps, configure console appender.
- For Nginx, symlink access/error logs to stdout/stderr.
- For custom apps, use container-native logging.

Example container-native pattern:

```text
Application → stdout/stderr → kubelet/container runtime → collector → Loki
```

Avoid relying on application-local log files unless you have a supported sidecar or custom collector design.

### 11.2 Application Produces Very Large Lines

Large log lines may be dropped or truncated depending on collector and Loki limits.

Check collector logs for:

```text
line too long
max line size
payload too large
entry too far behind
entry too far ahead
```

Fix options:

- Reduce application log line size.
- Avoid dumping huge JSON payloads or stack traces as one line.
- Tune collector/Loki limits only after impact analysis.

### 11.3 Application Timestamps Are Wrong

If application logs contain timestamps too far in the past or future, Loki may reject them or queries may not show them in expected windows.

Check node time:

```bash
oc debug node/<node-name>
chroot /host timedatectl
```

Check chrony:

```bash
chroot /host chronyc tracking
chroot /host chronyc sources -v
```

Fix NTP/time sync if needed.

## 12. Check Node-Level Log Files

If `oc logs` works, kubelet/container runtime logs should exist on the node.

Find node where pod runs:

```bash
oc -n <app-namespace> get pod <pod-name> -o wide
```

Debug node:

```bash
oc debug node/<node-name>
chroot /host
```

Check logs:

```bash
ls -l /var/log/pods/<app-namespace>_*
ls -l /var/log/containers/*<pod-name>*
```

Tail the container log:

```bash
tail -100 /var/log/containers/*<pod-name>*
```

If logs exist on node but not in Loki, collector/forwarding/Loki ingestion is the issue.

If logs do not exist on node, application/container runtime/kubelet logging is the issue.

## 13. Check Collector Configuration Generated by Operator

The operator generates collector configuration from `ClusterLogForwarder` and related resources.

Find collector config ConfigMap or Secret:

```bash
oc -n openshift-logging get cm | egrep 'collector|vector|fluentd'
oc -n openshift-logging get secret | egrep 'collector|vector|fluentd'
```

For Vector:

```bash
oc -n openshift-logging get cm collector -o yaml
```

Or inspect inside collector pod:

```bash
oc -n openshift-logging rsh <collector-pod>
ls -R /etc/vector* /etc/collector* 2>/dev/null
```

Check whether sources include application logs and sinks point to Loki.

Do not manually edit generated collector config. Fix the source custom resources such as `ClusterLogForwarder`.

## 14. Check Network Connectivity from Collector to Loki

### 14.1 Check Services

```bash
oc -n openshift-logging get svc | egrep 'loki|gateway|distributor|querier'
oc -n openshift-logging get endpoints | egrep 'loki|gateway|distributor|querier'
```

If service has no endpoints, backend pods are not ready.

### 14.2 Test DNS and Connectivity from Collector

```bash
oc -n openshift-logging rsh <collector-pod>
```

Inside pod:

```bash
getent hosts <loki-service-name>
curl -vk https://<loki-gateway-service>:8080/ready
curl -vk https://<loki-gateway-service>:8080/metrics
```

Actual ports and service names depend on your LokiStack version and generated services.

Common failures:

| Failure | Cause |
|---|---|
| DNS resolution fails | CoreDNS/DNS Operator issue. |
| Connection refused | Loki gateway unavailable. |
| TLS handshake failure | CA/certificate mismatch. |
| 401/403 | Auth token or RBAC issue. |
| Timeout | NetworkPolicy, routing, proxy, SDN issue. |

### 14.3 Check NetworkPolicy

```bash
oc -n openshift-logging get networkpolicy
oc -n openshift-logging describe networkpolicy <policy-name>
```

A restrictive NetworkPolicy may block collector to Loki gateway/distributor traffic.

## 15. Check Proxy and Certificate Issues

In enterprise OpenShift environments, cluster-wide proxy and custom CA issues are common.

### 15.1 Check Cluster Proxy

```bash
oc get proxy cluster -o yaml
```

Check:

```yaml
spec:
  httpProxy:
  httpsProxy:
  noProxy:
  trustedCA:
```

If Loki object storage or external endpoints are accessed through proxy, verify proxy rules.

If internal services are accidentally going through proxy, add required domains/CIDRs to `noProxy`.

### 15.2 Check Trusted CA

```bash
oc get configmap -n openshift-config
oc get proxy cluster -o jsonpath='{.spec.trustedCA.name}'
```

Collector and Loki may need correct CA bundles for internal/external TLS endpoints.

Search logs for:

```text
x509: certificate signed by unknown authority
certificate has expired
certificate is not valid for any names
```

## 16. Check Object Storage Backend

Loki depends heavily on object storage for chunks and indexes.

### 16.1 Check Storage Secret

```bash
oc -n openshift-logging get secret
oc -n openshift-logging get lokistack <lokistack-name> -o yaml | grep -A20 storage
```

Verify:

- Bucket name.
- Endpoint URL.
- Region.
- Access key.
- Secret key.
- CA certificate.
- TLS settings.
- IAM permissions.

### 16.2 Common Object Storage Problems

| Problem | Effect |
|---|---|
| Wrong credentials | Ingestion/query failures. |
| Bucket missing | Loki cannot write chunks. |
| Wrong region | Signature or endpoint errors. |
| Expired credentials | Sudden log loss after working earlier. |
| TLS CA mismatch | x509 errors. |
| Object storage latency | Backpressure, timeouts, delayed queries. |
| Bucket policy changed | 403/AccessDenied. |

### 16.3 Check Loki Logs for Storage Errors

```bash
oc -n openshift-logging logs <loki-pod> --all-containers | egrep -i 's3|bucket|object|storage|accessdenied|forbidden|signature|timeout|x509|chunk|index'
```

If storage is failing, fix storage first. Restarting collectors will not solve a broken object store.

## 17. Check Resource Pressure and Scaling

### 17.1 Collector Resource Pressure

```bash
oc -n openshift-logging top pods
oc -n openshift-logging describe pod <collector-pod>
```

Check for:

```text
OOMKilled
CPU throttling
Evicted
MemoryPressure
DiskPressure
```

Node pressure:

```bash
oc describe node <node-name>
oc adm top node
```

If collector is OOMKilled, logs may be dropped during restart/backpressure.

### 17.2 Loki Resource Pressure

```bash
oc -n openshift-logging top pods | egrep 'loki|gateway|ingester|querier|distributor'
oc -n openshift-logging describe pod <loki-pod>
```

Check PVCs if applicable:

```bash
oc -n openshift-logging get pvc
oc -n openshift-logging describe pvc <pvc-name>
```

Check pod events:

```bash
oc -n openshift-logging get events --sort-by=.lastTimestamp | tail -100
```

### 17.3 Log Volume Spike

If logs disappeared after traffic spike, check:

- Application log volume increased.
- Error loop generated massive logs.
- Loki ingestion limits hit.
- Collector buffers filled.
- Object storage latency increased.
- LokiStack size too small.

Possible remediation:

- Reduce noisy logs at application level.
- Add filters carefully.
- Increase LokiStack size/profile if supported.
- Tune resource requests/limits.
- Scale components according to supported operator configuration.

## 18. Check Retention and Compaction

Logs may not be missing; they may have expired.

Check LokiStack retention configuration:

```bash
oc -n openshift-logging get lokistack <lokistack-name> -o yaml | grep -A30 retention
```

If retention is short, older logs will be deleted.

Validate:

```text
Are users searching for logs older than retention period?
Did retention policy recently change?
Is compactor running correctly?
```

Check compactor logs:

```bash
oc -n openshift-logging logs <compactor-pod> --all-containers --tail=200
```

## 19. Check OpenShift Console / Grafana Integration

If logs exist in Loki but not in the UI, focus on query frontend, console plugin, datasource, and RBAC.

### 19.1 Check Console

```bash
oc get co console
oc -n openshift-console get pods
oc -n openshift-console logs deploy/console --tail=200
```

### 19.2 Check Observability UI / Plugin

Depending on version:

```bash
oc get pods -A | egrep -i 'observability|logging|plugin|console'
```

Check plugin resources if used.

### 19.3 Check Grafana Datasource

If using Grafana:

- Verify Loki datasource URL.
- Verify tenant header.
- Verify bearer token or auth proxy config.
- Verify TLS CA.
- Verify time range.
- Verify label names.

Common Grafana issue:

```text
Grafana datasource queries wrong tenant or old label names after logging upgrade.
```

## 20. Check Version and Upgrade Compatibility

If the issue started after upgrade, compare:

```bash
oc version
oc get clusterversion
oc get csv -A | egrep -i 'logging|loki|observability'
oc get clusterlogforwarder -A -o yaml
oc get lokistack -A -o yaml
```

Important upgrade-related checks:

- Logging 5.x to 6.x architectural changes.
- Fluentd to Vector migration.
- Deprecated fields in `ClusterLogForwarder`.
- Changed label names in Loki queries.
- Changed console/observability plugin behavior.
- Operator channel mismatch.
- LokiStack CRD version changes.
- Existing dashboards still using old labels.

Never assume old YAML works unchanged after major logging upgrades.

## 21. Decision Tree: Where Is the Break?

```text
START
 |
 |-- Does oc logs show application logs?
 |       |-- NO  → Application logging problem. Check stdout/stderr, app config, container.
 |       |-- YES → Continue.
 |
 |-- Do node log files exist under /var/log/containers?
 |       |-- NO  → Kubelet/container runtime/node issue.
 |       |-- YES → Continue.
 |
 |-- Is collector pod running on the same node?
 |       |-- NO  → Collector DaemonSet scheduling/node/SCC/resource issue.
 |       |-- YES → Continue.
 |
 |-- Collector logs show forwarding errors?
 |       |-- YES → Fix Loki endpoint/TLS/RBAC/network/backpressure.
 |       |-- NO  → Continue.
 |
 |-- ClusterLogForwarder includes application input and correct namespace?
 |       |-- NO  → Fix CLF pipeline/input/filter/output.
 |       |-- YES → Continue.
 |
 |-- LokiStack healthy and storage working?
 |       |-- NO  → Fix Loki/object storage/resources.
 |       |-- YES → Continue.
 |
 |-- Cluster-admin can see logs but user cannot?
 |       |-- YES → RBAC/tenant/query authorization issue.
 |       |-- NO  → Continue.
 |
 |-- Direct Loki query works but UI does not?
 |       |-- YES → Console/Grafana datasource/plugin/query issue.
 |       |-- NO  → Deep-dive Loki ingestion/query labels/limits.
```

## 22. Practical Command Flow

This is the command flow I would use during a production incident.

### Step 1: Confirm Application Logs Exist

```bash
APP_NS=<namespace>
APP_POD=<pod-name>

oc -n $APP_NS get pod $APP_POD -o wide
oc -n $APP_NS logs $APP_POD --tail=50
```

### Step 2: Identify Node

```bash
NODE=$(oc -n $APP_NS get pod $APP_POD -o jsonpath='{.spec.nodeName}')
echo $NODE
```

### Step 3: Check Collector on Same Node

```bash
oc -n openshift-logging get pods -o wide | egrep "collector|vector|fluentd|$NODE"
```

### Step 4: Check Collector Logs

```bash
COLLECTOR_POD=$(oc -n openshift-logging get pods -o wide | grep $NODE | egrep 'collector|vector|fluentd' | awk '{print $1}' | head -1)
echo $COLLECTOR_POD

oc -n openshift-logging logs $COLLECTOR_POD --all-containers --tail=300
```

### Step 5: Check CLF

```bash
oc get clusterlogforwarder -A
oc -n openshift-logging get clusterlogforwarder <name> -o yaml
oc -n openshift-logging describe clusterlogforwarder <name>
```

### Step 6: Check LokiStack

```bash
oc get lokistack -A
oc -n openshift-logging get lokistack <name> -o yaml
oc -n openshift-logging describe lokistack <name>
```

### Step 7: Check Loki Pods

```bash
oc -n openshift-logging get pods | egrep 'loki|gateway|ingester|distributor|querier|compactor|index'
oc -n openshift-logging logs <loki-pod> --all-containers --tail=200
```

### Step 8: Check Services and Endpoints

```bash
oc -n openshift-logging get svc | egrep 'loki|gateway|distributor|querier'
oc -n openshift-logging get endpoints | egrep 'loki|gateway|distributor|querier'
```

### Step 9: Check RBAC

```bash
oc auth can-i get pods/log -n $APP_NS --as=<user>
oc adm policy who-can get pods/log -n $APP_NS
```

### Step 10: Generate a Test Log

```bash
oc -n $APP_NS exec $APP_POD -- sh -c 'echo loki-test-log-$(date)'
oc -n $APP_NS logs $APP_POD --tail=20
```

Then query Loki for the namespace and recent time window.

## 23. Common Root Causes and Fixes

### Root Cause 1: Application Does Not Write to stdout/stderr

**Symptoms:**

```text
oc logs shows nothing or very little.
Application team says logs exist inside /var/log/app/app.log.
Loki has no logs.
```

**Fix:**

Configure application logging to console/stdout.

For example:

- Java: use ConsoleAppender.
- Spring Boot: configure console logging.
- Nginx: link logs to stdout/stderr.
- Node.js/Python/Go: write logs to stdout/stderr.

**Interview statement:**

```text
In Kubernetes, stdout/stderr is the standard logging path. If the app writes only to an internal file, the OpenShift collector will not automatically collect it unless we design a custom supported forwarding pattern.
```

---

### Root Cause 2: ClusterLogForwarder Does Not Include Application Input

**Symptoms:**

```text
Infrastructure logs visible.
Application logs missing.
Collector is healthy.
LokiStack is healthy.
```

**Bad config:**

```yaml
pipelines:
- name: infra
  inputRefs:
  - infrastructure
  outputRefs:
  - default
```

**Fix:**

```yaml
pipelines:
- name: application
  inputRefs:
  - application
  outputRefs:
  - default
```

Apply:

```bash
oc apply -f clusterlogforwarder.yaml
```

Validate:

```bash
oc -n openshift-logging describe clusterlogforwarder <name>
oc -n openshift-logging get pods | grep collector
```

---

### Root Cause 3: Namespace Not Selected by CLF Input

**Symptoms:**

```text
Only one project/application is missing.
Other namespaces are visible.
```

**Fix options:**

Add namespace explicitly:

```yaml
inputs:
- name: selected-apps
  application:
    namespaces:
    - payments
    - claims
```

Or label namespace if selector-based:

```bash
oc label namespace claims logging=enabled
```

---

### Root Cause 4: Collector Not Running on Application Node

**Symptoms:**

```text
Logs missing only for pods on one node.
Collector DaemonSet pod missing or failing on that node.
```

**Check:**

```bash
oc -n <app-ns> get pod <pod> -o wide
oc -n openshift-logging get pods -o wide | grep <node>
```

**Fix:**

Investigate collector scheduling:

```bash
oc -n openshift-logging describe ds collector
oc -n openshift-logging describe pod <collector-pod>
oc describe node <node>
```

Resolve taints, tolerations, resource pressure, image pull, SCC, or node health.

---

### Root Cause 5: Collector Cannot Reach Loki

**Symptoms:**

```text
Collector logs show connection refused, timeout, x509, 401, 403.
```

**Check:**

```bash
oc -n openshift-logging logs <collector-pod> --all-containers | egrep -i 'loki|error|timeout|x509|forbidden|unauthorized|refused'
oc -n openshift-logging get svc,endpoints | egrep 'loki|gateway'
```

**Fix depends on error:**

| Error | Fix |
|---|---|
| x509 | Fix CA bundle / certificate configuration. |
| 401/403 | Fix token/RBAC/tenant auth. |
| timeout | Fix NetworkPolicy, DNS, proxy, or service route. |
| refused | Fix Loki gateway/distributor readiness. |

---

### Root Cause 6: Loki Object Storage Failure

**Symptoms:**

```text
Loki pods show S3/bucket/object storage errors.
Collectors may show backpressure.
Queries return partial/no results.
```

**Check:**

```bash
oc -n openshift-logging logs <loki-pod> --all-containers | egrep -i 's3|bucket|storage|accessdenied|forbidden|signature|timeout|x509'
oc -n openshift-logging get lokistack <name> -o yaml
```

**Fix:**

- Correct storage secret.
- Restore bucket permissions.
- Fix endpoint/region.
- Fix CA certificate.
- Fix network path to object storage.

---

### Root Cause 7: User Has No Permission to View Logs

**Symptoms:**

```text
Cluster-admin can see logs.
Developer cannot see logs.
```

**Check:**

```bash
oc auth can-i get pods/log -n <namespace> --as=<user>
oc adm policy who-can get pods/log -n <namespace>
```

**Fix:**

```bash
oc adm policy add-role-to-user view <user> -n <namespace>
```

Or use group-based RBAC.

---

### Root Cause 8: Wrong Loki Query or Labels

**Symptoms:**

```text
Logs are present, but dashboard shows empty.
Manual broader query works.
```

**Fix:**

Use broad query first:

```logql
{namespace_name="payments"}
```

Then narrow down:

```logql
{namespace_name="payments", pod_name=~"payments-api-.*"}
```

Update dashboard labels after logging upgrade if label names changed.

---

### Root Cause 9: Logs Expired Due to Retention

**Symptoms:**

```text
Recent logs visible.
Older logs missing.
Users search beyond retention period.
```

**Check:**

```bash
oc -n openshift-logging get lokistack <name> -o yaml | grep -A30 retention
```

**Fix:**

Adjust retention according to compliance and storage capacity.

---

### Root Cause 10: Loki Ingestion Rate Limit or Payload Limit

**Symptoms:**

```text
Collector logs show dropped events, retries, rate limit, payload too large.
Application has high log volume.
```

**Fix:**

- Reduce noisy application logs.
- Add controlled filters.
- Increase supported LokiStack sizing.
- Tune resource limits after capacity review.
- Avoid huge single-line logs.

## 24. Example End-to-End Troubleshooting Case

### Situation

Application team says:

```text
Our payments-api logs are missing from Loki after yesterday's deployment.
Pods are running and users can access the application.
```

### Investigation

Check pod logs:

```bash
oc -n payments get pods
oc -n payments logs deploy/payments-api --tail=50
```

Result:

```text
Logs are visible with oc logs.
```

Check node:

```bash
oc -n payments get pod <pod-name> -o wide
```

Result:

```text
Pod is running on worker-5.
```

Check collector on worker-5:

```bash
oc -n openshift-logging get pods -o wide | grep worker-5
```

Result:

```text
Collector is running.
```

Check collector logs:

```bash
oc -n openshift-logging logs <collector-pod-on-worker-5> --all-containers --tail=300
```

Result:

```text
No forwarding errors.
```

Check CLF:

```bash
oc -n openshift-logging get clusterlogforwarder instance -o yaml
```

Found:

```yaml
inputs:
- name: prod-apps
  application:
    selector:
      matchLabels:
        logging: enabled
pipelines:
- name: prod-apps-to-loki
  inputRefs:
  - prod-apps
  outputRefs:
  - default
```

Check namespace labels:

```bash
oc get ns payments --show-labels
```

Found:

```text
payments   env=prod
```

Namespace is missing `logging=enabled`.

### Root Cause

The `payments` namespace was not selected by the `ClusterLogForwarder` application input because the namespace label `logging=enabled` was missing.

### Fix

```bash
oc label namespace payments logging=enabled
```

### Validation

Generate test log:

```bash
oc -n payments exec deploy/payments-api -- sh -c 'echo loki-test-payment-$(date)'
oc -n payments logs deploy/payments-api --tail=20
```

Query Loki:

```logql
{namespace_name="payments"} |= "loki-test-payment"
```

### Final RCA Statement

```text
Application logs were not missing due to Loki failure. The ClusterLogForwarder was configured to collect application logs only from namespaces labeled logging=enabled. The payments namespace did not have that label after namespace recreation. Adding the correct label restored log ingestion.
```

## 26. Preventive Controls

### 26.1 Monitoring Alerts

Create alerts for:

- Collector pod not ready.
- Collector restart count high.
- Collector dropped events.
- Loki distributor ingestion failures.
- Loki ingester errors.
- Loki gateway 5xx responses.
- Object storage errors.
- LokiStack degraded.
- CLF not ready.

### 26.2 GitOps for Logging Configuration

Manage these through GitOps:

```text
ClusterLogForwarder
LokiStack
Namespace logging labels
NetworkPolicy
RBAC
Object storage secret references
Console/Grafana datasource configuration
```

Benefits:

- Prevent accidental pipeline removal.
- Track changes causing log loss.
- Roll back bad logging configuration.
- Enforce consistent namespace onboarding.

### 26.3 Namespace Onboarding Standard

For every production namespace:

```bash
oc label namespace <namespace> logging=enabled env=prod owner=<team>
```

Or maintain explicit namespace list in CLF if that is your enterprise standard.

### 26.4 Application Logging Standard

Application teams should follow:

```text
1. Write logs to stdout/stderr.
2. Use structured JSON logging where possible.
3. Avoid huge single-line payloads.
4. Include trace_id/request_id/correlation_id.
5. Do not log secrets, tokens, passwords, Aadhaar/PAN, or sensitive data.
6. Use proper log levels.
7. Avoid debug logging in production unless temporarily enabled.
```

## 27. Interview-Level Explanation of Why This Happens

Application logs can be missing from Loki even when Loki itself is healthy because OpenShift Logging is a pipeline-based system. The data must pass through multiple layers:

```text
Application → container runtime → node log file → collector → CLF pipeline → Loki ingestion → object storage → query frontend → UI/RBAC
```

A break at any layer can create the same user-facing symptom: “logs are missing.”

A junior admin may only check Loki pods. A senior OpenShift admin checks the complete log path and separates:

```text
Generation problem
Collection problem
Forwarding problem
Ingestion problem
Storage problem
Query problem
Authorization problem
Visualization problem
```

This approach avoids random restarts and leads to a precise root cause.

---

## 28. Strong Interview Answer

```text
If application logs are missing from Loki, I first verify whether the application is producing logs using oc logs. If oc logs is empty, the problem is application logging, usually the app writing to a file instead of stdout/stderr.

If oc logs works, I identify the node and check whether the logging collector DaemonSet is running on that node. Then I inspect collector logs for forwarding, TLS, RBAC, DNS, network, backpressure, or dropped-event errors.

Next, I validate ClusterLogForwarder. I check whether the pipeline includes the application input, whether the namespace is selected, whether filters are dropping logs, and whether the output points to the correct LokiStack.

Then I check LokiStack health, Loki gateway/distributor/ingester/querier pods, services, endpoints, and object storage errors. If Loki ingestion is healthy, I check query-side issues such as wrong tenant, wrong labels, short time range, Grafana datasource misconfiguration, console plugin issue, or user RBAC.

I validate by generating a test log from the application and querying Loki with a broad namespace-level query. Finally, I document the exact broken layer and implement preventive monitoring and GitOps controls so the issue does not repeat.
```

## 31. Key Takeaways

- Missing logs do not always mean Loki is down.
- Always verify application log generation first.
- `oc logs` is the first checkpoint.
- Collector must run on the same node as the workload.
- `ClusterLogForwarder` is a frequent root cause.
- Namespace selectors and filters can silently exclude logs.
- Loki may ingest logs correctly while RBAC or query labels hide them.
- Object storage issues can break Loki ingestion and queries.
- Validate with a fresh test log and a broad query.
- Use GitOps and alerts to prevent recurrence.
