# Prometheus Target Is Down — Interview-Level Investigation Guide for Advanced OpenShift Administration

## Scenario

**Interview question:**  
`Prometheus target is down. How will you investigate?`

**Expected senior-level answer:**  
As a senior OpenShift administrator, I will not directly restart Prometheus or the application. A Prometheus target being down means Prometheus is unable to scrape the configured metrics endpoint. The issue can be in the application, Service, Endpoints/EndpointSlice, ServiceMonitor/PodMonitor, NetworkPolicy, TLS, authentication, RBAC, namespace labels, user-workload monitoring configuration, DNS, proxy, or the monitoring stack itself.

My approach is to first identify **which Prometheus instance** is scraping the target, then verify the target error, then follow the path from Prometheus to ServiceMonitor/PodMonitor to Service to Endpoint to Pod to metrics port.

---

## 1. First Clarify the Scope

Before troubleshooting, I confirm whether the target belongs to:

1. **Platform monitoring**
   - Namespace: `openshift-monitoring`
   - Prometheus pods:
     - `prometheus-k8s-0`
     - `prometheus-k8s-1`
   - Used for cluster operators, kubelet, API server, etcd, router, machine config, cluster components.

2. **User workload monitoring**
   - Namespace: `openshift-user-workload-monitoring`
   - Prometheus pods:
     - `prometheus-user-workload-0`
     - `prometheus-user-workload-1`
   - Used for application/project metrics configured through `ServiceMonitor`, `PodMonitor`, `PrometheusRule`, etc.

This distinction is important because the troubleshooting namespace, Prometheus instance, RBAC, ServiceMonitor selectors, and configuration files are different.

---

## 2. High-Level Troubleshooting Flow

My investigation flow is:

```text
Alert / Console Target Down
        |
        v
Identify Prometheus instance and target error
        |
        v
Check Prometheus UI / Observe > Targets
        |
        v
Check ServiceMonitor or PodMonitor
        |
        v
Check Service selector and Endpoints/EndpointSlice
        |
        v
Check Pod readiness, labels, port, metrics path
        |
        v
Test scrape URL from inside cluster
        |
        v
Check TLS/authentication/network policy/DNS/proxy
        |
        v
Check Prometheus Operator and Prometheus logs
        |
        v
Fix root cause and validate target becomes UP
```

## 3. Check Target Status from OpenShift Console

In OpenShift console:

```text
Administrator Perspective
Observe
Targets
```

I filter by:

- Namespace
- Job name
- Target URL
- Status: `Down`

Then I open the target details and check the error message.

Common target errors:

| Error | Meaning |
|---|---|
| `context deadline exceeded` | Network issue, endpoint slow, timeout, NetworkPolicy, app overloaded |
| `connection refused` | Pod is not listening on the metrics port |
| `no route to host` | Network path problem, CNI, node issue, NetworkPolicy |
| `server returned HTTP status 404` | Wrong metrics path |
| `server returned HTTP status 401/403` | Authentication or authorization issue |
| `x509: certificate signed by unknown authority` | TLS CA trust issue |
| `certificate is valid for X, not Y` | TLS SAN mismatch |
| `unsupported protocol scheme` | Wrong scheme: `http` vs `https` |
| `EOF` | Endpoint closed connection, TLS mismatch, app crash, proxy issue |

## 5. Check Whether User Workload Monitoring Is Enabled

If the down target belongs to an application namespace, I first confirm user workload monitoring is enabled.

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config -o yaml
```

Expected configuration:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

If `enableUserWorkload: true` is missing, user-defined project monitoring will not work properly.

Check user workload monitoring pods:

```bash
oc -n openshift-user-workload-monitoring get pods
```

Expected pods:

```text
prometheus-user-workload-0
prometheus-user-workload-1
prometheus-operator
thanos-ruler-user-workload-0
thanos-ruler-user-workload-1
```

Check cluster operators:

```bash
oc get co monitoring
oc get co
```

If monitoring operator is degraded, I troubleshoot the monitoring stack before blaming the application.

## 6. Identify the ServiceMonitor or PodMonitor

Most application targets are discovered through `ServiceMonitor` or `PodMonitor`.

List ServiceMonitors:

```bash
oc get servicemonitor -A
```

List PodMonitors:

```bash
oc get podmonitor -A
```

For a specific namespace:

```bash
oc -n <namespace> get servicemonitor
oc -n <namespace> get podmonitor
```

Describe the ServiceMonitor:

```bash
oc -n <namespace> describe servicemonitor <servicemonitor-name>
oc -n <namespace> get servicemonitor <servicemonitor-name> -o yaml
```

Important fields to check:

```yaml
spec:
  selector:
    matchLabels:
      app: myapp
  namespaceSelector:
    matchNames:
    - my-namespace
  endpoints:
  - port: metrics
    path: /metrics
    scheme: http
    interval: 30s
```

## 7. Validate ServiceMonitor Selector

A very common root cause is a label mismatch between `ServiceMonitor` and `Service`.

Check ServiceMonitor selector:

```bash
oc -n <namespace> get servicemonitor <name> -o jsonpath='{.spec.selector.matchLabels}'
```

Check Services and labels:

```bash
oc -n <namespace> get svc --show-labels
```

Example problem:

```yaml
ServiceMonitor selector:
  app: frontend
```

But Service has:

```yaml
labels:
  app: frontend-v2
```

In this case Prometheus may not discover the service, or it may discover the wrong target.

Fix example:

```bash
oc -n <namespace> label svc <service-name> app=frontend --overwrite
```

Or update the `ServiceMonitor` selector to match the actual service label.

---

## 8. Validate Service Port Name

Prometheus Operator uses the **Service port name**, not always the numeric container port.

ServiceMonitor example:

```yaml
endpoints:
- port: metrics
```

The Service must have a port named `metrics`:

```yaml
apiVersion: v1
kind: Service
spec:
  ports:
  - name: metrics
    port: 8080
    targetPort: 8080
```

Check Service:

```bash
oc -n <namespace> get svc <service-name> -o yaml
```

If the ServiceMonitor references:

```yaml
port: metrics
```

But the Service has:

```yaml
ports:
- name: http
```

Then the target may not be generated correctly.

Fix example:

```bash
oc -n <namespace> patch svc <service-name> --type='json' \
  -p='[{"op":"replace","path":"/spec/ports/0/name","value":"metrics"}]'
```

Better approach in production: update GitOps manifest and let Argo CD/RHACM apply it.

---

## 9. Validate Service Endpoints

Even if the ServiceMonitor is correct, Prometheus cannot scrape if the Service has no endpoints.

Check Service:

```bash
oc -n <namespace> get svc <service-name> -o wide
```

Check Endpoints:

```bash
oc -n <namespace> get endpoints <service-name> -o yaml
```

Check EndpointSlice:

```bash
oc -n <namespace> get endpointslice -l kubernetes.io/service-name=<service-name> -o yaml
```

If endpoints are empty:

```yaml
subsets: []
```

Then the issue is usually one of these:

- Service selector does not match Pod labels
- Pods are not Ready
- Pods are failing readiness probe
- Pods are in CrashLoopBackOff
- Pods are not running on expected nodes
- Deployment has zero replicas

Check Service selector:

```bash
oc -n <namespace> get svc <service-name> -o jsonpath='{.spec.selector}'
```

Check Pod labels:

```bash
oc -n <namespace> get pods --show-labels
```

Example mismatch:

```yaml
Service selector:
  app: payment
```

But Pods have:

```yaml
labels:
  app: payment-api
```

Fix the Service selector or Pod labels.

## 10. Check Pod Health

Check pods:

```bash
oc -n <namespace> get pods -o wide
```

Describe the pod:

```bash
oc -n <namespace> describe pod <pod-name>
```

Check events:

```bash
oc -n <namespace> get events --sort-by=.lastTimestamp
```

Check logs:

```bash
oc -n <namespace> logs <pod-name>
```

For multi-container pod:

```bash
oc -n <namespace> logs <pod-name> -c <container-name>
```

Check previous crashed container logs:

```bash
oc -n <namespace> logs <pod-name> -c <container-name> --previous
```

Important things to verify:

- Is the pod `Running`?
- Is the pod `Ready`?
- Is metrics endpoint exposed?
- Is the metrics container running?
- Is the metrics port open?
- Is the app binding on `0.0.0.0` or only `127.0.0.1`?
- Is the app overloaded?
- Is the metrics endpoint slow?

## 11. Check Whether Metrics Port Is Listening

Use `oc rsh` if available:

```bash
oc -n <namespace> rsh <pod-name>
```

Inside the pod:

```bash
ss -lntp
```

Or:

```bash
netstat -lntp
```

Check metrics endpoint locally:

```bash
curl -v http://localhost:<metrics-port>/metrics
```

If the app binds only to localhost, Prometheus scraping via Pod IP or Service IP will fail.

Example bad application configuration:

```text
metrics bind address = 127.0.0.1:9090
```

Better:

```text
metrics bind address = 0.0.0.0:9090
```

## 12. Test the Metrics Endpoint from Inside the Cluster

Create a temporary debug pod:

```bash
oc -n <namespace> run curl-test --rm -it --image=curlimages/curl -- sh
```

Test Service DNS:

```bash
curl -v http://<service-name>.<namespace>.svc:<port>/metrics
```

Test ClusterIP:

```bash
curl -v http://<cluster-ip>:<port>/metrics
```

Test Pod IP directly:

```bash
curl -v http://<pod-ip>:<metrics-port>/metrics
```

Interpretation:

| Test Result | Meaning |
|---|---|
| Pod IP works, Service fails | Service selector/port/endpoint problem |
| Service works, Prometheus fails | Prometheus config, auth, TLS, network policy, namespace selection |
| Both fail | Application/pod/port/network issue |
| DNS fails only | CoreDNS/DNS policy issue |
| Curl times out | NetworkPolicy, CNI, endpoint hang, firewall-like issue |
| 401/403 | Authentication/authorization required |
| 404 | Wrong path |

## 13. Check NetworkPolicy

NetworkPolicy is a very common reason for Prometheus targets going down in restricted namespaces.

Check policies:

```bash
oc -n <namespace> get networkpolicy
oc -n <namespace> describe networkpolicy <policy-name>
```

Prometheus pods usually run in:

```text
openshift-monitoring
openshift-user-workload-monitoring
```

If the application namespace has default deny ingress, allow ingress from the monitoring namespace.

Example NetworkPolicy allowing user workload Prometheus:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-prometheus-scrape
  namespace: myapp
spec:
  podSelector:
    matchLabels:
      app: myapp
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-user-workload-monitoring
    ports:
    - protocol: TCP
      port: 8080
```

For platform Prometheus:

```yaml
namespaceSelector:
  matchLabels:
    kubernetes.io/metadata.name: openshift-monitoring
```

After applying policy:

```bash
oc apply -f allow-prometheus-scrape.yaml
```

Validate:

```bash
oc -n <namespace> get networkpolicy allow-prometheus-scrape -o yaml
```

## 14. Check TLS Configuration

If the endpoint uses HTTPS, verify the `ServiceMonitor` configuration.

Example:

```yaml
endpoints:
- port: metrics
  scheme: https
  path: /metrics
  tlsConfig:
    insecureSkipVerify: false
    ca:
      secret:
        name: metrics-ca
        key: ca.crt
```

Common TLS issues:

| Error | Root Cause |
|---|---|
| `x509: certificate signed by unknown authority` | Prometheus does not trust endpoint CA |
| `certificate is valid for X, not Y` | Certificate SAN mismatch |
| `server gave HTTP response to HTTPS client` | ServiceMonitor uses `https`, endpoint is `http` |
| `client sent an HTTP request to an HTTPS server` | ServiceMonitor uses `http`, endpoint is `https` |

Check certificate:

```bash
openssl s_client -connect <service-name>.<namespace>.svc:<port> -showcerts
```

From a debug pod:

```bash
curl -vk https://<service-name>.<namespace>.svc:<port>/metrics
```

Temporary test only:

```yaml
tlsConfig:
  insecureSkipVerify: true
```

Production recommendation: do not permanently use `insecureSkipVerify: true`. Fix CA trust or certificate SAN properly.

## 15. Check Authentication and Authorization

Some applications protect `/metrics` using bearer token, basic auth, OAuth proxy, or mTLS.

If Prometheus error shows:

```text
server returned HTTP status 401 Unauthorized
```

or:

```text
server returned HTTP status 403 Forbidden
```

Then check whether metrics require authentication.

ServiceMonitor bearer token example:

```yaml
endpoints:
- port: metrics
  path: /metrics
  bearerTokenSecret:
    name: metrics-token
    key: token
```

Basic auth example:

```yaml
endpoints:
- port: metrics
  basicAuth:
    username:
      name: metrics-basic-auth
      key: username
    password:
      name: metrics-basic-auth
      key: password
```

Check secret exists:

```bash
oc -n <namespace> get secret metrics-token
oc -n <namespace> get secret metrics-basic-auth
```

Check ServiceAccount permissions if metrics endpoint uses Kubernetes authorization.

```bash
oc -n <namespace> get role,rolebinding
oc auth can-i get pods --as=system:serviceaccount:<namespace>:<serviceaccount>
```

## 16. Check Namespace Selection

A ServiceMonitor may exist but Prometheus may not select it due to namespace selection rules.

Check ServiceMonitor namespace:

```bash
oc get servicemonitor -A | grep <name>
```

Check namespace labels:

```bash
oc get ns <namespace> --show-labels
```

Check ServiceMonitor namespace selector:

```bash
oc -n <namespace> get servicemonitor <name> -o yaml
```

If using cross-namespace monitoring, verify:

```yaml
namespaceSelector:
  matchNames:
  - myapp
```

or:

```yaml
namespaceSelector:
  any: true
```

In production, avoid broad `any: true` unless governance allows it.

For user workload monitoring:


For platform monitoring:

```bash
oc -n openshift-monitoring get pods
```

Look for:

- ServiceMonitor rejected
- invalid endpoint port
- permission issue
- YAML schema problem
- secret not found
- TLS secret missing
- selector mismatch
- namespace not allowed

If required, temporarily enable debug logging for Prometheus Operator, then revert after troubleshooting.

## 19. Check Generated Prometheus Configuration

Prometheus Operator generates Prometheus configuration from ServiceMonitor/PodMonitor resources.

Check Prometheus configuration secret.

Platform monitoring:

```bash
oc -n openshift-monitoring get secret | grep prometheus-k8s
```

User workload monitoring:

```bash
oc -n openshift-user-workload-monitoring get secret | grep prometheus-user-workload
```

Extract configuration if needed:

```bash
oc -n openshift-user-workload-monitoring get secret prometheus-user-workload -o jsonpath='{.data.prometheus\.yaml\.gz}' | base64 -d | gunzip > prometheus.yaml
```

Search for job:

```bash
grep -n "<job-name>" prometheus.yaml
```

This confirms whether Prometheus Operator actually generated a scrape job.

## 20. Check Resource Pressure on Prometheus

Sometimes targets are down because Prometheus itself is unhealthy or overloaded.

Check pods:

```bash
oc -n openshift-monitoring get pods -o wide
oc -n openshift-user-workload-monitoring get pods -o wide
```

Check resource usage:

```bash
oc adm top pods -n openshift-monitoring
oc adm top pods -n openshift-user-workload-monitoring
```

Check PVC:

```bash
oc -n openshift-monitoring get pvc
oc -n openshift-user-workload-monitoring get pvc
```

Check events:

```bash
oc -n openshift-monitoring get events --sort-by=.lastTimestamp
oc -n openshift-user-workload-monitoring get events --sort-by=.lastTimestamp
```

Problems to look for:

- Prometheus pod restarting
- OOMKilled
- PVC full
- node disk pressure
- node memory pressure
- WAL corruption
- high cardinality metrics
- scrape timeout due to too many targets
- Prometheus configuration reload failure

## 21. Check Scrape Timeout and Metrics Cardinality

If the error is timeout:

```text
context deadline exceeded
```

Check whether the metrics endpoint is slow:

```bash
time curl -s http://<service>.<namespace>.svc:<port>/metrics > /tmp/metrics.out
```

Check size:

```bash
wc -l /tmp/metrics.out
```

Large metrics output may cause scrape timeout or high memory usage.

ServiceMonitor tuning example:

```yaml
endpoints:
- port: metrics
  interval: 30s
  scrapeTimeout: 10s
  path: /metrics
```

Do not blindly increase timeout. First check why metrics are slow:

- Too many labels
- High-cardinality labels like `request_id`, `user_id`, `session_id`
- Application is overloaded
- Metrics endpoint computes expensive data live
- Database dependency inside metrics endpoint

## 22. Check Relabeling and Metric Limits

ServiceMonitor may have relabeling rules that drop targets unintentionally.

Check:

```bash
oc -n <namespace> get servicemonitor <name> -o yaml
```

Look for:

```yaml
relabelings:
metricRelabelings:
sampleLimit:
targetLimit:
labelLimit:
labelNameLengthLimit:
labelValueLengthLimit:
```

Bad relabeling can drop all targets.

Example risky configuration:

```yaml
relabelings:
- action: drop
  regex: .*
  sourceLabels:
  - __meta_kubernetes_pod_name
```

This would drop every pod target.

## 23. Check Route/Ingress Misunderstanding

Prometheus usually scrapes internal Kubernetes Services or Pods directly, not the external OpenShift Route.

Bad assumption:

```text
Application route works, so Prometheus should work.
```

That is not always true.

A route may work while ServiceMonitor fails because:

- ServiceMonitor points to wrong service port
- Route terminates TLS but internal service is HTTP
- NetworkPolicy allows router namespace but blocks Prometheus namespace
- Route uses public hostname but Prometheus scrapes cluster service DNS
- Metrics endpoint is not exposed on the same service as application traffic

Always test internal service URL:

```bash
curl -v http://<service>.<namespace>.svc:<port>/metrics
```

## 24. Check DNS Resolution

From debug pod:

```bash
nslookup <service-name>.<namespace>.svc
```

Or:

```bash
dig <service-name>.<namespace>.svc.cluster.local
```

If DNS fails:

```bash
oc -n openshift-dns get pods
oc -n openshift-dns logs -l dns.operator.openshift.io/daemonset-dns=default
oc get co dns
```

DNS issue is less common for one target but possible if namespace, service, or cluster DNS is broken.

## 25. Check Node-Level or CNI Issues

If only targets on a specific node are down:

```bash
oc get pods -A -o wide | grep <node-name>
oc get node <node-name>
oc describe node <node-name>
```

Check node conditions:

- `Ready`
- `MemoryPressure`
- `DiskPressure`
- `PIDPressure`
- `NetworkUnavailable`

Check CNI pods:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc get pods -n openshift-sdn -o wide
```

Depending on cluster networking, one of these namespaces is relevant.

Check cluster network operator:

```bash
oc get co network
```

If Prometheus cannot reach pods on a specific node, investigate CNI, node firewall, kube-proxy equivalent, OVN-Kubernetes, MTU, and node health.

## 26. Common Root Causes and Fixes

| Root Cause | How to Detect | Fix |
|---|---|---|
| ServiceMonitor selector mismatch | Service labels do not match ServiceMonitor selector | Fix labels or selector |
| Service port name mismatch | ServiceMonitor references `port: metrics`, Service has no `metrics` port | Rename/add Service port |
| No endpoints | `oc get endpoints` empty | Fix Service selector or Pod readiness |
| Pod not exposing metrics | Curl to Pod IP fails | Fix app metrics config |
| Wrong metrics path | HTTP 404 | Correct `path: /metrics` or app path |
| HTTP/HTTPS mismatch | TLS/EOF/protocol error | Correct `scheme` |
| TLS CA issue | x509 unknown authority | Add CA secret or fix cert |
| Auth required | HTTP 401/403 | Configure bearer token/basic auth/mTLS |
| NetworkPolicy blocks scrape | Curl timeout from Prometheus/debug pod | Allow monitoring namespace ingress |
| Prometheus overloaded | Prometheus restarts, high CPU/memory | Tune resources, reduce cardinality |
| User workload monitoring disabled | No user workload Prometheus | Enable `enableUserWorkload: true` |
| Prometheus Operator issue | Operator logs show rejection | Fix ServiceMonitor/PodMonitor YAML |
| Endpoint slow | `context deadline exceeded` | Optimize metrics endpoint/cardinality |
| Wrong namespace selection | ServiceMonitor cannot see namespace | Fix `namespaceSelector` |
| Secret missing | Operator/Prometheus logs show secret error | Create/fix secret reference |

## 27. Example End-to-End Investigation

Assume alert says:

```text
TargetDown
job="myapp/myapp-service/0"
namespace="myapp"
service="myapp-service"
endpoint="metrics"
```

### Step 1: Check target in Prometheus

```bash
oc -n openshift-user-workload-monitoring port-forward pod/prometheus-user-workload-0 9090:9090
```

Open:

```text
http://localhost:9090/targets
```

Error:

```text
server returned HTTP status 404 Not Found
```

### Step 2: Check ServiceMonitor

```bash
oc -n myapp get servicemonitor myapp -o yaml
```

Found:

```yaml
endpoints:
- port: metrics
  path: /metrics
```

### Step 3: Test endpoint

```bash
oc -n myapp run curl-test --rm -it --image=curlimages/curl -- sh
curl -v http://myapp-service.myapp.svc:8080/metrics
```

Result:

```text
404 Not Found
```

Try application-specific path:

```bash
curl -v http://myapp-service.myapp.svc:8080/actuator/prometheus
```

Result:

```text
200 OK
```

### Step 4: Fix ServiceMonitor

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp
  namespace: myapp
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    path: /actuator/prometheus
    interval: 30s
```

Apply:

```bash
oc apply -f servicemonitor.yaml
```

### Step 5: Validate

```bash
oc -n openshift-user-workload-monitoring port-forward pod/prometheus-user-workload-0 9090:9090
```

Check:

```text
http://localhost:9090/targets
```

Target should become:

```text
UP
```

Query:

```promql
up{namespace="myapp", service="myapp-service"}
```

Expected:

```text
1
```

## 28. Important PromQL Queries During Investigation

Check target status:

```promql
up
```

Specific namespace:

```promql
up{namespace="myapp"}
```

Specific job:

```promql
up{job=~".*myapp.*"}
```

Targets down:

```promql
up == 0
```

Scrape duration:

```promql
scrape_duration_seconds{namespace="myapp"}
```

Scrape samples:

```promql
scrape_samples_scraped{namespace="myapp"}
```

Scrape series added:

```promql
scrape_series_added{namespace="myapp"}
```

Check if Prometheus is missing target completely:

```promql
count by (job, namespace, service) (up{namespace="myapp"})
```

## 29. What I Would Say in an Interview

If asked directly, I would answer like this:

> First I identify whether the down target is scraped by platform Prometheus in `openshift-monitoring` or user workload Prometheus in `openshift-user-workload-monitoring`. Then I check the target in the OpenShift console under Observe > Targets or directly from Prometheus `/targets` page using port-forward. I focus on the last scrape error because it tells whether the issue is timeout, connection refused, 401, 403, 404, TLS, DNS, or network related.
>
> After that I validate the discovery chain. For application monitoring, I check the `ServiceMonitor` or `PodMonitor`, its selector, namespace selector, endpoint port name, path, scheme, TLS, and authentication configuration. Then I verify the Service labels, Service port, Endpoints or EndpointSlice, Pod labels, Pod readiness, and whether the metrics port is actually listening.
>
> I test the metrics endpoint from inside the cluster using a temporary curl pod, first through Service DNS, then ClusterIP, then Pod IP. If Pod IP works but Service fails, I check Service selector and endpoints. If Service works but Prometheus fails, I check NetworkPolicy, authentication, TLS, Prometheus Operator logs, and generated Prometheus configuration. If the endpoint times out, I check NetworkPolicy, CNI, scrape timeout, application performance, and high-cardinality metrics.
>
> I avoid restarting Prometheus blindly. I fix the actual root cause, then validate with Prometheus targets page and PromQL query `up{namespace="..."}` returning `1`.

## 30. Production Best Practices

1. Manage ServiceMonitor, PodMonitor, and PrometheusRule through GitOps.
2. Use consistent labels across Deployment, Service, and ServiceMonitor.
3. Always name the metrics Service port clearly, for example `metrics`.
4. Keep `/metrics` lightweight and fast.
5. Avoid high-cardinality labels such as user ID, session ID, request ID, token ID, or dynamic URL path.
6. Do not expose sensitive data in metrics.
7. Use TLS properly; avoid permanent `insecureSkipVerify`.
8. If metrics require auth, configure Prometheus credentials through Kubernetes Secrets.
9. Add NetworkPolicy rules to allow scraping from monitoring namespaces.
10. Monitor Prometheus resource usage, PVC usage, scrape duration, and sample ingestion rate.
11. Keep application metrics endpoint independent of database-heavy live queries.
12. Use alerts for target down, scrape duration, scrape sample count, Prometheus TSDB issues, and Prometheus restarts.
13. Document ownership of each ServiceMonitor and alert rule.
14. Use namespace-level governance for user workload monitoring.
15. Validate monitoring configuration after every deployment.

## 32. Final Senior-Level Summary

A Prometheus target down issue is not one single problem. It is a scrape-path investigation. I check the target error first, then validate discovery, ServiceMonitor/PodMonitor, Service, Endpoints, Pod, metrics port, path, scheme, TLS, authentication, NetworkPolicy, and Prometheus health.

The most common real-world causes are:

- ServiceMonitor selector mismatch
- Service port name mismatch
- Empty endpoints
- Pod not ready
- Wrong `/metrics` path
- HTTP/HTTPS mismatch
- TLS CA or SAN issue
- Authentication missing
- NetworkPolicy blocking Prometheus
- Metrics endpoint timeout
- Prometheus resource pressure

A 10-year experienced OpenShift administrator should show structured thinking, avoid blind restarts, use Prometheus `/targets` and `up` query, test from inside the cluster, and fix the exact root cause through controlled configuration changes.
