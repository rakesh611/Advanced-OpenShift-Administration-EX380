# ClusterOperator `authentication` is Degraded — Interview-Level Troubleshooting Flow for Advanced OpenShift Administration

## Scenario

You are working as a senior OpenShift administrator in a production environment. During a health check, upgrade precheck, or incident call, you see that the `authentication` ClusterOperator is degraded.

```bash
oc get co authentication
```

Example output:

```text
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
authentication   4.x.x     True        False         True       20m     OAuthServerRouteEndpointAccessibleControllerAvailable: ...
```

The interviewer asks:

> **ClusterOperator authentication is degraded. What will you check?**

A 10-year-experience answer should not start with random pod deletion. It should follow a structured flow: identify the exact degraded condition, check OAuth operator and OAuth server health, validate routes, ingress, certificates, API connectivity, identity provider configuration, secrets, network, DNS, proxy, and recent changes.

---

## 1. First Principle: What Does the Authentication Operator Manage?

In OpenShift 4, the `authentication` ClusterOperator represents the health of the cluster authentication stack. It mainly involves:

- Cluster Authentication Operator
- Internal OAuth server
- OAuth route: `oauth-openshift`
- Identity provider integration such as LDAP, HTPasswd, GitHub, OIDC, Keystone, request header, etc.
- OAuth server certificates and trusted CA bundles
- OAuth client/token flow
- Interaction with kube-apiserver and ingress/router

The OpenShift internal OAuth server is responsible for authenticating users and issuing OAuth access tokens that are used to access the OpenShift API. If this layer is degraded, users might face login issues through CLI or console.

Important impact:

- `oc login` may fail.
- Web console login may fail.
- OAuth redirects may fail.
- Existing tokens may continue working for some time, but new logins may fail.
- Cluster upgrades may be blocked because ClusterOperators must normally be healthy.

---

## 2. Senior-Level Troubleshooting Mindset

I troubleshoot this in layers:

1. **Read exact ClusterOperator condition** — do not guess.
2. **Check authentication operator pods** in `openshift-authentication-operator`.
3. **Check OAuth server pods** in `openshift-authentication`.
4. **Check OAuth route and router/ingress path**.
5. **Check certificates and trusted CA bundle**.
6. **Check identity provider configuration** in `oauth.config.openshift.io/cluster`.
7. **Check secrets/configmaps referenced by OAuth**.
8. **Check kube-apiserver connectivity from OAuth pods**.
9. **Check DNS, routes, ingress, proxy, firewall, and network policies**.
10. **Check recent changes** such as certificate replacement, LDAP/OIDC change, proxy change, ingress change, upgrade, node issue, or image pull issue.

The most important command is:

```bash
oc describe co authentication
```

The `MESSAGE` and `REASON` fields tell where to go next.

---

## 3. Immediate Health Check Commands

### 3.1 Check all ClusterOperators

```bash
oc get co
```

Look for related degraded operators:

```bash
oc get co authentication console ingress kube-apiserver openshift-apiserver network dns
```

Why?

Authentication often depends on ingress, DNS, kube-apiserver, and certificates. If `ingress` or `kube-apiserver` is degraded, authentication may be a symptom, not the root cause.

---

### 3.2 Describe the authentication ClusterOperator

```bash
oc describe co authentication
```

Or get only conditions:

```bash
oc get co authentication -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

Common condition examples:

```text
Available=True
Progressing=False
Degraded=True
Upgradeable=True/False
```

Common degraded reasons/messages:

```text
OAuthServerDeploymentDegraded
OAuthServerRouteEndpointAccessibleControllerAvailable
OAuthRouteCheckEndpointAccessibleControllerDegraded
RouterCertsDegraded
OAuthServerConfigObservationDegraded
OAuthServerServiceEndpointAccessibleControllerAvailable
APIServerDeploymentDegraded
```

Interview point:

> I always classify the problem based on the degraded reason. If the message says route endpoint inaccessible, I check ingress/router/DNS/TLS. If it says deployment degraded, I check OAuth pods, images, config, node scheduling, and logs. If it says config observation degraded, I check OAuth CR, IDP secrets, and configmaps.


```bash

```

```bash

```

Look for:

```text
failed to sync OAuth server
secret not found
configmap not found
x509 certificate signed by unknown authority
route not reachable
failed to GET route
context deadline exceeded
connection refused

```

If the operator itself is crashlooping, check:

```bash
oc get events -n openshift-authentication-operator --sort-by=.lastTimestamp

```

Possible causes:

- Image pull issue
- Node scheduling issue
- API connectivity issue
- Operator config issue
- Certificate trust issue

## 6. Check OAuth Server Pods

The OAuth server runs in `openshift-authentication`.

```bash
oc get pods -n openshift-authentication -o wide
```

Expected pods usually look like:

```text
oauth-openshift-xxxxx
```

Check deployment:

```bash
oc get deploy -n openshift-authentication
oc describe deploy oauth-openshift -n openshift-authentication
```

Check replicas:

```bash
oc get deploy oauth-openshift -n openshift-authentication -o wide
oc get rs -n openshift-authentication
```

Check pods:

```bash
oc describe pod -n openshift-authentication <oauth-pod>
oc logs -n openshift-authentication <oauth-pod>
oc logs -n openshift-authentication <oauth-pod> --previous
```

Look for pod states:

```text
Running but not Ready
CrashLoopBackOff
ImagePullBackOff
CreateContainerConfigError
Pending
Evicted
ContainerCreating
```

### 6.1 If OAuth pods are CrashLoopBackOff

Check logs:

```bash
oc logs -n openshift-authentication <oauth-pod> --previous
```

Common causes:

- Invalid OAuth configuration
- Invalid IDP secret
- Bad LDAP bind DN/password
- Bad OIDC issuer URL or CA bundle
- Bad certificate chain
- Missing configmap or secret
- OAuth template syntax error
- Kube-apiserver connectivity issue

Check events:

```bash
oc get events -n openshift-authentication --sort-by=.lastTimestamp
```

### 6.2 If OAuth pods are Pending

Check scheduling:

```bash
oc describe pod -n openshift-authentication <oauth-pod>
oc get nodes
oc describe node <node-name>
```

Look for:

```text
Insufficient cpu
Insufficient memory
node(s) had taint that the pod didn't tolerate
node not ready
volume mount issue
```

Authentication is a control-plane critical component. If master/control-plane nodes are unhealthy, OAuth server availability can be affected.

## 7. Check OAuth Service and Endpoints

```bash
oc get svc -n openshift-authentication

```

Expected:

- Endpoints point to ready OAuth pod IPs.

If service exists but endpoints are empty:

```bash

oc describe svc oauth-openshift -n openshift-authentication
```

Possible causes:

- OAuth pods are not ready.
- Service selector mismatch.
- Pod readiness probe failing.
- Deployment rollout incomplete.

## 8. Check OAuth Route

The OAuth login endpoint is exposed through a route.

```bash
oc get route -n openshift-authentication
oc get route oauth-openshift -n openshift-authentication -o yaml
```

Expected route host usually looks like:

```text
oauth-openshift.apps.<cluster-domain>
```

Check route details:

```bash
oc describe route oauth-openshift -n openshift-authentication
```

Check whether the route has admitted status:

```bash
oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.status.ingress[*].conditions[*]}'
```

If route is not admitted:

```bash
oc get co ingress
oc describe co ingress
oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller default -n openshift-ingress-operator
oc get pods -n openshift-ingress -o wide
```

Possible causes:

- Ingress operator degraded
- Router pods down
- Router certificate issue
- Wildcard DNS broken
- Load balancer not forwarding 80/443
- Network/firewall blocking router
- Route admission issue

---

## 9. Test OAuth Route Connectivity

From your admin machine:

```bash
curl -k -I https://oauth-openshift.apps.<cluster-domain>
```

Better test:

```bash
curl -k -v https://oauth-openshift.apps.<cluster-domain>/healthz
```

Also test metadata endpoint:

```bash
curl -k -v https://oauth-openshift.apps.<cluster-domain>/.well-known/oauth-authorization-server
```

Expected:

- DNS resolves.
- TCP 443 connects.
- TLS handshake succeeds.
- HTTP response is returned.

If you get:

```text
Could not resolve host
```

Check DNS.

If you get:

```text
Connection timed out
Connection refused
```

Check load balancer/router/firewall.

If you get:

```text
x509: certificate signed by unknown authority
certificate has expired
certificate is valid for X, not Y
```

Check router/default ingress certificate and OAuth serving certificate.

## 10. Check DNS for OAuth Route

```bash
dig oauth-openshift.apps.<cluster-domain>
nslookup oauth-openshift.apps.<cluster-domain>
```

Also check wildcard apps domain:

```bash
dig '*.apps.<cluster-domain>'
```

Expected:

- OAuth route resolves to the ingress VIP/load balancer/router IP.

For bare metal or lab clusters, check:

```bash
cat /etc/hosts
nmcli dev show | grep DNS
```

In production, verify enterprise DNS or load balancer records.

If DNS is broken, users cannot access OAuth route, and authentication operator can report route endpoint inaccessible.

Authentication depends heavily on the default ingress route.

```bash
oc get co ingress
oc describe co ingress
```

Check ingress controller:

```bash
oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller default -n openshift-ingress-operator
```

Check router pods:

```bash
oc get pods -n openshift-ingress -o wide
oc describe pod -n openshift-ingress <router-pod>
oc logs -n openshift-ingress <router-pod>
```

Check router service:

```bash
oc get svc -n openshift-ingress
oc describe svc router-default -n openshift-ingress
```

In bare metal or UPI environments, check the external load balancer:

```bash
curl -k https://console-openshift-console.apps.<cluster-domain>
curl -k https://oauth-openshift.apps.<cluster-domain>
```

Possible issues:

- Router pods not running
- Router not admitted route
- Ingress canary failures
- HAProxy/F5/NGINX load balancer misconfiguration
- Firewall blocking 443
- Incorrect wildcard DNS
- Router certificate expired or wrong SAN

## 12. Check Certificates

Authentication degradation is often certificate-related.

### 12.1 Check OAuth route certificate from outside

```bash
openssl s_client -connect oauth-openshift.apps.<cluster-domain>:443 -servername oauth-openshift.apps.<cluster-domain> -showcerts </dev/null
```

Check:

```text
subject
issuer
notBefore
notAfter
SAN
Verify return code
```

### 12.2 Check ingress default certificate

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

Look for:

```yaml
spec:
  defaultCertificate:
    name: <secret-name>
```

Then check secret:

```bash
oc get secret -n openshift-ingress <secret-name> -o yaml
```

Decode certificate:

```bash
oc get secret -n openshift-ingress <secret-name> -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -text
```

### 12.3 Check OAuth serving cert configmap

```bash
oc get configmap oauth-serving-cert -n openshift-config-managed -o yaml
```

The Authentication Operator publishes OAuth serving certificate data into this configmap. If the router certificate or CA bundle is wrong, OAuth route validation can fail.

### 12.4 Common certificate problems

- Expired ingress/router certificate
- Incomplete certificate chain
- Wrong SAN for `*.apps.<cluster-domain>`
- Custom CA not included in trusted CA bundle
- Router serving wrong certificate
- OAuth route certificate mismatch
- Certificate secret updated incorrectly

Fix approach:

- Restore correct router/default ingress certificate.
- Include full chain: server certificate + intermediate CA.
- Validate SAN includes wildcard apps domain.
- Ensure secret type and key names are correct: `tls.crt`, `tls.key`.
- Let operators reconcile.

## 13. Check OAuth Configuration

OAuth cluster configuration:

```bash
oc get oauth cluster -o yaml
oc describe oauth cluster
```

Important areas:

```yaml
spec:
  identityProviders:
  - name: ldap
    type: LDAP
    ldap:
      url: ldap://...
      bindDN: ...
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
```

Check for:

- YAML syntax issue
- Wrong provider type
- Missing required fields
- Secret name typo
- ConfigMap name typo
- Wrong LDAP URL
- Wrong OIDC issuer URL
- Invalid CA reference
- Invalid mapping method
- Bad custom login template
- Recent OAuth edit

Useful command:

```bash
oc explain oauth.spec.identityProviders
```

If recent change caused degradation, inspect history from GitOps, audit logs, or cluster events.

## 14. Check IDP Secrets and ConfigMaps

List referenced secrets/configmaps:

```bash
oc get oauth cluster -o yaml
```

Then check them in `openshift-config` namespace:

```bash
oc get secret -n openshift-config
oc get configmap -n openshift-config
```

For LDAP bind password:

```bash
oc get secret ldap-bind-password -n openshift-config -o yaml
```

For LDAP/OIDC CA:

```bash
oc get configmap ldap-ca -n openshift-config -o yaml
```

Common mistake:

```text
OAuth references secret name ldap-secret, but actual secret is ldap-bind-secret.
```

Another common mistake:

```text
CA configmap key must normally be ca.crt, but user created a different key name.
```

Check events:

```bash
oc get events -n openshift-authentication --sort-by=.lastTimestamp
oc get events -n openshift-config --sort-by=.lastTimestamp
```

## 15. LDAP-Specific Checks

If LDAP is configured, verify:

```bash
oc get oauth cluster -o yaml
```

Check LDAP URL format:

```text
ldap://ldap.example.com:389/ou=users,dc=example,dc=com?uid
ldaps://ldap.example.com:636/ou=users,dc=example,dc=com?uid
```

Test LDAP reachability from a debug pod or OAuth pod if tools are available:

```bash
oc debug node/<node-name>
```

Or create temporary test pod:

```bash
oc run ldap-test -n openshift-authentication --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside pod:

```bash
curl -v ldap://ldap.example.com:389
```

If ldap utilities are available:

```bash
ldapsearch -x -H ldap://ldap.example.com:389 -D '<bindDN>' -W -b '<baseDN>' '(uid=testuser)'
```

Check:

- LDAP server reachable from cluster nodes/pods
- Port 389/636 open
- Bind DN correct
- Bind password correct
- Base DN correct
- Attribute mapping correct
- CA trusted for LDAPS
- LDAP certificate not expired
- Firewall allows traffic from cluster nodes

Important interview line:

> If only LDAP users cannot login but kubeadmin or another IDP works, the OAuth server may be available but the identity provider configuration is broken. If the authentication ClusterOperator itself is degraded, I still check whether bad IDP configuration is causing OAuth server rollout failure.

## 16. OIDC-Specific Checks

For OIDC, check:

```bash
oc get oauth cluster -o yaml
```

Validate:

- `issuer` URL is correct
- OIDC discovery endpoint is reachable
- Client ID is correct
- Client secret exists
- CA bundle is correct
- Redirect URI configured in identity provider is correct

Test from outside:

```bash
curl -k https://<oidc-issuer>/.well-known/openid-configuration
```

Test from inside cluster:

```bash
oc run oidc-test -n openshift-authentication --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -kv https://<oidc-issuer>/.well-known/openid-configuration
```

Common OIDC issues:

- Corporate proxy blocks OIDC issuer
- TLS CA missing
- Issuer URL mismatch
- Client secret rotated but OpenShift secret not updated
- Redirect URI mismatch
- OIDC provider outage

## 17. Check kube-apiserver Connectivity from OAuth Pods

OAuth server must talk to the API server.

Check kube-apiserver ClusterOperator:

```bash
oc get co kube-apiserver
oc describe co kube-apiserver
```

Check kube-apiserver pods:

```bash
oc get pods -n openshift-kube-apiserver -o wide
oc logs -n openshift-kube-apiserver <kube-apiserver-pod> -c kube-apiserver
```

From OAuth pod:

```bash
oc rsh -n openshift-authentication <oauth-pod>
```

Inside pod:

```bash
curl -kv https://kubernetes.default.svc
curl -kv https://openshift.default.svc
curl -kv https://api.<cluster-domain>:6443/.well-known/oauth-authorization-server
```

If using cluster-wide proxy, check whether proxy/noProxy is correct:

```bash
oc get proxy cluster -o yaml
```

Common API connectivity problems:

- kube-apiserver degraded
- service network issue
- DNS issue inside cluster
- proxy misconfiguration
- noProxy missing `.cluster.local`, service CIDR, pod CIDR, API VIP, or internal domains
- network plugin issue



## 20. Check Proxy Configuration

In proxy-enabled clusters:

```bash
oc get proxy cluster -o yaml
```

Check:

```yaml
spec:
  httpProxy:
  httpsProxy:
  noProxy:
```

Important `noProxy` should include internal ranges/domains such as:

- `.cluster.local`
- `.svc`
- service CIDR
- pod CIDR
- machine CIDR
- API VIP
- Ingress VIP
- internal DNS domains
- LDAP/OIDC internal domains if required

Symptoms of proxy issues:

```text
context deadline exceeded
proxyconnect tcp: dial tcp ...
x509 unknown authority
connection refused
```

A bad proxy config can break OAuth-to-API or OAuth-to-IDP communication.

## 25. Troubleshooting Based on Common Degraded Messages

### 25.1 `OAuthServerDeploymentDegraded`

Meaning:

The OAuth server deployment is unhealthy. Pods may be unavailable, not ready, crashlooping, or rollout is stuck.

Check:

```bash
oc get deploy oauth-openshift -n openshift-authentication
oc get pods -n openshift-authentication -o wide
oc describe pod -n openshift-authentication <oauth-pod>
oc logs -n openshift-authentication <oauth-pod> --previous
oc get events -n openshift-authentication --sort-by=.lastTimestamp
```

Likely causes:

- Invalid OAuth config
- Missing secret/configmap
- Bad certificate
- Image pull issue
- Node resource/scheduling issue
- API connectivity failure

Fix:

- Correct config/secret/cert.
- Restore missing resources.
- Fix node or image pull issue.
- Let operator reconcile.

---

### 25.2 `OAuthServerRouteEndpointAccessibleControllerAvailable` or `OAuthRouteCheckEndpointAccessibleControllerDegraded`

Meaning:

The operator cannot successfully access the OAuth route endpoint.

Check:

```bash
oc get route oauth-openshift -n openshift-authentication -o yaml
oc describe route oauth-openshift -n openshift-authentication
curl -k -v https://oauth-openshift.apps.<cluster-domain>/healthz
oc get co ingress
oc get pods -n openshift-ingress -o wide
oc logs -n openshift-ingress <router-pod>
```

Likely causes:

- DNS issue
- Router/ingress issue
- Load balancer issue
- Firewall blocking 443
- TLS certificate problem
- OAuth service endpoints empty

Fix:

- Restore wildcard DNS.
- Fix ingress/router pods.
- Fix LB/firewall.
- Fix OAuth service endpoints.
- Fix router certificate.

---

### 25.3 `RouterCertsDegraded`

Meaning:

Authentication operator is not happy with the certificate chain presented by the router for OAuth route.

Check:

```bash
openssl s_client -connect oauth-openshift.apps.<cluster-domain>:443 -servername oauth-openshift.apps.<cluster-domain> -showcerts </dev/null
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get secret -n openshift-ingress <router-cert-secret> -o yaml
oc get configmap oauth-serving-cert -n openshift-config-managed -o yaml
```

Likely causes:

- Expired cert
- Wrong wildcard cert
- Missing intermediate CA
- Secret mounted with wrong data
- Router not reloaded

Fix:

- Replace ingress certificate with valid full-chain cert.
- Confirm SAN and expiry.
- Wait for operator reconciliation.

---

### 25.4 `OAuthServerConfigObservationDegraded`

Meaning:

Authentication operator cannot correctly observe or process OAuth configuration.

Check:

```bash
oc get oauth cluster -o yaml
oc describe oauth cluster
oc logs -n openshift-authentication-operator deploy/authentication-operator
oc get secret -n openshift-config
oc get configmap -n openshift-config
```

Likely causes:

- Invalid OAuth CR
- Missing referenced secret
- Missing referenced CA configmap
- Invalid login template
- Unsupported or malformed IDP config

Fix:

- Correct OAuth CR.
- Restore referenced secrets/configmaps.
- Validate IDP configuration.

---

### 25.5 `OAuthServerServiceEndpointAccessibleControllerAvailable`

Meaning:

OAuth service endpoint is not accessible internally.

Check:

```bash
oc get svc oauth-openshift -n openshift-authentication
oc get ep oauth-openshift -n openshift-authentication
oc get pods -n openshift-authentication -o wide
oc rsh -n openshift-authentication <oauth-pod>
```

Likely causes:

- OAuth pods not ready
- Endpoints empty
- Service selector issue
- Network plugin problem
- Pod readiness failing

Fix:

- Fix OAuth pod readiness.
- Fix network issue.
- Allow operator to recreate managed objects if corrupted.

---

## 26. Safe Recovery Actions

### 26.1 Let operators reconcile after fixing root cause

After correcting the issue:

```bash
oc get co authentication -w
```

Watch pods:

```bash
oc get pods -n openshift-authentication -w
```

### 26.2 Restart OAuth pods only after identifying cause

Sometimes, after fixing certificate/config issues, recycling pods helps pick up changes:

```bash
oc delete pod -n openshift-authentication -l app=oauth-openshift
```

But in an interview, say clearly:

> I do not start with deleting pods. I first read the degraded reason and logs. Pod deletion is only a reconciliation trigger after root cause is corrected.

### 26.3 Do not manually patch operator-managed deployment casually

Avoid:

```bash
oc edit deploy oauth-openshift -n openshift-authentication
```

Reason:

The deployment is managed by the Authentication Operator. Manual changes may be overwritten and can make troubleshooting harder.

## 27. Example End-to-End Troubleshooting Flow

### Step 1: Confirm condition

```bash
oc get co authentication
oc describe co authentication
```

Observed:

```text
Degraded=True
Reason=OAuthServerRouteEndpointAccessibleControllerAvailable
Message=failed to GET route: x509: certificate signed by unknown authority
```

### Step 2: Check route

```bash
oc get route oauth-openshift -n openshift-authentication
curl -kv https://oauth-openshift.apps.prod.example.com/healthz
```

Observed:

```text
certificate signed by unknown authority
```

### Step 3: Check ingress certificate

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get secret -n openshift-ingress router-certs-default -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -issuer -subject -dates
```

Observed:

```text
Certificate expired yesterday
```

### Step 4: Replace certificate correctly

Create/update valid full-chain certificate secret:

```bash
oc create secret tls router-certs-default \
  --cert=fullchain.crt \
  --key=tls.key \
  -n openshift-ingress \
  --dry-run=client -o yaml | oc apply -f -
```

### Step 5: Wait and validate

```bash
oc get pods -n openshift-ingress -w
oc get co ingress authentication -w
curl -kv https://oauth-openshift.apps.prod.example.com/healthz
oc login https://api.prod.example.com:6443
```

Expected:

```text
authentication Available=True Progressing=False Degraded=False
```

## 28. Interview Answer — Short Version

If asked in an interview, I would answer:

```text
First, I will not assume it is an LDAP or OAuth issue directly. I will describe the authentication ClusterOperator and read the exact Degraded reason and message. Then I will check both namespaces: openshift-authentication-operator for the operator logs, and openshift-authentication for the OAuth server deployment and pods.

If OAuth pods are degraded, I will check pod status, events, readiness, logs, image pull, node scheduling, and referenced secrets/configmaps. If the condition says route endpoint is not accessible, I will check the oauth-openshift route, router pods, ingress operator, wildcard DNS, load balancer, firewall, and route certificate. If the error is x509 or RouterCertsDegraded, I will validate the router certificate chain, SAN, expiry, oauth-serving-cert configmap, and custom CA bundle.

Then I will validate the OAuth/cluster configuration, especially identityProviders, LDAP/OIDC settings, referenced secrets, CA configmaps, bind credentials, issuer URL, and proxy/noProxy configuration. I will also verify kube-apiserver, DNS, and network operators because authentication depends on API and ingress availability.

After fixing the root cause, I will let the operator reconcile, watch OAuth pods and ClusterOperator status, and finally validate with curl to the OAuth route and oc login. I will avoid manually editing operator-managed deployments unless directed by official support.
```

## 30. Common Root Causes Table

| Symptom | Likely Root Cause | What to Check |
|---|---|---|
| OAuth pods CrashLoopBackOff | Bad OAuth config, bad IDP config, missing secret, cert error | OAuth pod logs, operator logs, OAuth CR |
| Route endpoint inaccessible | DNS, ingress, router, LB, firewall | OAuth route, ingress operator, router pods, curl |
| x509 error | Bad router cert, missing CA, expired cert | openssl, ingress secret, oauth-serving-cert |
| OAuth service endpoint unavailable | Pods not ready or endpoints empty | svc/ep, pods, readiness probes |
| Login fails only for LDAP users | LDAP config or LDAP server issue | LDAP URL, bind secret, CA, ldapsearch |
| Login fails only for OIDC users | OIDC issuer/client/CA/redirect issue | OIDC discovery URL, client secret, CA |
| Authentication and console degraded | OAuth route or ingress problem | ingress, route, console route, OAuth route |
| Authentication and kube-apiserver degraded | API connectivity or control plane issue | kube-apiserver logs, nodes, etcd |
| Degraded after proxy change | Wrong noProxy | proxy/cluster, pod-to-API connectivity |
| Degraded after cert replacement | Wrong cert chain/SAN/secret | router certificate and CA bundle |

## 32. What I Would Avoid

Avoid these mistakes:

- Deleting OAuth pods without checking degraded reason.
- Assuming LDAP is the issue without checking route/ingress/certs.
- Editing `oauth-openshift` deployment manually.
- Ignoring related degraded operators like ingress, DNS, kube-apiserver, and network.
- Replacing certificates without full chain.
- Forgetting that OAuth references secrets/configmaps in `openshift-config`.
- Testing only from laptop, not from inside cluster.
- Ignoring proxy/noProxy in enterprise environments.
- Continuing upgrade while authentication is degraded.

## 33. Final Senior-Level Summary

When `ClusterOperator authentication` is degraded, I treat it as a platform-level incident because it can affect CLI login, console login, OAuth token issuance, and cluster upgrade health.

My first action is always:

```bash
oc describe co authentication
```

Then I follow the condition message. If it points to deployment, I check OAuth pods and operator logs. If it points to route endpoint, I check route, ingress, DNS, LB, firewall, and TLS. If it points to certificates, I validate router cert chain and OAuth serving cert. If it points to configuration, I inspect OAuth CR, IDP secrets, configmaps, LDAP/OIDC configuration, and proxy settings.

A good OpenShift administrator does not troubleshoot authentication in isolation. Authentication depends on API server, ingress, DNS, network, certificates, identity providers, secrets, and proxy. The correct approach is layered, evidence-based, and reversible.
