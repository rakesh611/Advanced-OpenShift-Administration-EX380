# Interview-Level Scenario: Pod is Pending Even Though Nodes are Ready — What Will You Check?

## 1. Scenario

You are working as an Advanced OpenShift Administrator in a production OpenShift cluster.

A developer reports:

> "My application pod is stuck in `Pending`. All worker nodes are showing `Ready`. Why is the pod not starting?"

At first glance, this looks confusing because node health is good:

```bash
oc get nodes
```

Example output:

```text
NAME             STATUS   ROLES    AGE   VERSION
worker-1         Ready    worker   120d  v1.29.x
worker-2         Ready    worker   120d  v1.29.x
worker-3         Ready    worker   120d  v1.29.x
```

But the pod is still pending:

```bash
oc get pods -n payments
```

Example output:

```text
NAME                         READY   STATUS    RESTARTS   AGE
payment-api-7c9d88c9f-8jkl2  0/1     Pending   0          12m
```

As a 10-year experienced OpenShift administrator, you should not immediately assume a node problem. A pod can remain `Pending` even when all nodes are `Ready` because `Ready` only means the node is healthy enough to accept workloads. It does not mean the pod satisfies all scheduling, resource, policy, storage, quota, security, topology, or admission requirements.

---

## 2. Senior-Level Interview Answer

If a pod is `Pending` while nodes are `Ready`, I first determine whether the pod is pending because it has not been scheduled, or because it was scheduled but cannot start due to another dependency such as image pull, volume attach, init container, admission, or sandbox creation.

My first command is always:

```bash
oc describe pod <pod-name> -n <namespace>
```

Then I check the `Events` section. The event message normally tells the exact scheduling blocker, for example:

```text
0/3 nodes are available: 3 Insufficient cpu.
0/3 nodes are available: 1 node(s) had untolerated taint, 2 node(s) didn't match Pod's node affinity/selector.
pod has unbound immediate PersistentVolumeClaims.
exceeded quota: compute-resources.
```

After that, I validate resources, quota, LimitRange, node selectors, taints, tolerations, affinity, PVC binding, storage class, pod priority, topology spread constraints, MachineConfig/node conditions, and scheduler/operator health.

In OpenShift, I also check project-level annotations, Security Context Constraints, namespace quota, cluster resource quota, image pull secrets, and whether the workload is restricted by deployment configuration or operator-managed constraints.

---

## 3. Important Concept: `Node Ready` Does Not Guarantee Pod Scheduling

A node can be `Ready`, but the scheduler can still reject it for a specific pod.

A node may be healthy, but not eligible for a pod due to:

- Insufficient requested CPU or memory
- Node selector mismatch
- Node affinity mismatch
- Pod anti-affinity conflict
- Taints not tolerated by the pod
- ResourceQuota or ClusterResourceQuota limits
- LimitRange defaulting or validation issues
- PVC not bound
- StorageClass missing or unavailable
- Volume node affinity conflict
- Topology spread constraint conflict
- PodSecurity/SCC/admission issue
- Namespace default node selector
- Scheduler profile or scheduler issue
- Priority/preemption limitations
- Host port conflict
- Requested GPU, hugepages, SR-IOV, or special device unavailable
- Pull secret or image policy issue after scheduling

The scheduler evaluates more than node readiness. It checks whether the pod can legally and practically run on one of the nodes.

## 4. First Check: Pod Events

### Command

```bash
oc describe pod <pod-name> -n <namespace>
```

Example:

```bash
oc describe pod payment-api-7c9d88c9f-8jkl2 -n payments
```

### Focus Area

Look at:

```text
Events:
```

Example event:

```text
Warning  FailedScheduling  default-scheduler  0/3 nodes are available: 3 Insufficient memory.
```

This immediately tells us the scheduler cannot find a suitable node because the pod's memory request cannot be satisfied.

### Senior-Level Explanation

In Kubernetes and OpenShift scheduling, the scheduler uses the pod's `resources.requests`, not current actual usage, to decide whether a node has enough allocatable capacity.

For example, a node may show free memory from Linux tools, but Kubernetes may already have that memory reserved by pod requests.

Check the pod request:

```bash
oc get pod <pod-name> -n <namespace> -o jsonpath='{.spec.containers[*].resources}' | jq
```

Or:

```bash
oc describe pod <pod-name> -n <namespace>
```

Check node allocatable capacity:

```bash
oc describe node <node-name>
```

Look for:

```text
Capacity:
Allocatable:
Allocated resources:
```

Example:

```text
Allocated resources:
  Resource           Requests      Limits
  cpu                3900m (97%)   6000m (150%)
  memory             15Gi (94%)    25Gi (156%)
```

Even if the node is `Ready`, the scheduler may reject the pod if requested CPU/memory does not fit.

## 5. Check Resource Requests and Limits

### Command

```bash
oc get pod <pod-name> -n <namespace> -o yaml | grep -A20 resources:
```

Better:

```bash
oc get pod <pod-name> -n <namespace> -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{.resources}{"\n"}{end}'
```

### Example Problem

```yaml
resources:
  requests:
    cpu: "4"
    memory: 16Gi
  limits:
    cpu: "8"
    memory: 32Gi
```

If the largest worker node only has 8 CPU and 16 Gi memory total, and existing workloads already reserve resources, this pod may never schedule.

### Fix

Reduce requests or add capacity:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: 512Mi
  limits:
    cpu: "1"
    memory: 1Gi
```

Then redeploy:

```bash
oc rollout restart deployment/payment-api -n payments
```

### Interview Point

A senior admin should say:

> I check requests first, not limits. Scheduling is based mainly on requests. Limits affect runtime enforcement, but requests reserve schedulable capacity.

## 6. Check Namespace ResourceQuota

A pod can remain pending or fail admission if the namespace quota is exhausted.

### Commands

```bash
oc get quota -n <namespace>
oc describe quota -n <namespace>
```

Example:

```bash
oc describe quota -n payments
```

Example output:

```text
Resource                 Used     Hard
requests.cpu             8        8
requests.memory          16Gi     16Gi
pods                     20       20
```

### Meaning

The namespace has already consumed its quota. New pods cannot be admitted or scheduled if they would exceed the quota.

### Fix Options

Option 1: Increase quota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: payments-quota
  namespace: payments
spec:
  hard:
    requests.cpu: "12"
    requests.memory: 24Gi
    limits.cpu: "24"
    limits.memory: 48Gi
    pods: "40"
```

Apply:

```bash
oc apply -f quota.yaml
```

Option 2: Reduce replicas or resource requests:

```bash
oc scale deployment/payment-api --replicas=2 -n payments
```

Option 3: Clean unused workloads:

```bash
oc get all -n payments
```

## 7. Check ClusterResourceQuota

In OpenShift, there may be a `ClusterResourceQuota` applied across multiple projects.

### Commands

```bash
oc get clusterresourcequota
oc describe clusterresourcequota <name>
```

Also check project selection:

```bash
oc get clusterresourcequota <name> -o yaml
```

### Why This Matters

A namespace quota may look fine, but a cluster-level quota across multiple namespaces can still block the workload.

Example:

```text
exceeded quota: team-a-global-quota, requested: requests.cpu=2, used: requests.cpu=20, limited: requests.cpu=20
```

### Fix

Increase the cluster quota or reduce resource consumption in one of the selected namespaces.

## 8. Check LimitRange

A `LimitRange` can apply default requests and limits automatically. Sometimes the user does not define resources, but OpenShift injects defaults that make the pod too large to schedule.

### Commands

```bash
oc get limitrange -n <namespace>
oc describe limitrange -n <namespace>
```

Example:

```bash
oc describe limitrange -n payments
```

Example output:

```text
Type       Resource  Min  Max  Default Request  Default Limit
Container  memory    1Gi  4Gi  2Gi              4Gi
Container  cpu       1    4    1                2
```

### Problem

The application YAML may not show resources, but `LimitRange` defaults may inject:

```yaml
requests:
  cpu: "1"
  memory: 2Gi
```

If the deployment has many replicas, scheduling may fail due to inflated default requests.

### Fix

Set explicit realistic requests in the deployment:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

## 9. Check Node Selector

A pod may be restricted to nodes with a specific label.

### Commands

```bash
oc get pod <pod-name> -n <namespace> -o yaml | grep -A10 nodeSelector
oc get nodes --show-labels
```

Example pod spec:

```yaml
nodeSelector:
  workload: payment
```

But nodes may not have that label:

```bash
oc get nodes -l workload=payment
```

If no nodes are returned, the pod cannot schedule.

### Fix Option 1: Label the Correct Node

```bash
oc label node worker-2 workload=payment
```

### Fix Option 2: Remove or Correct Node Selector

```bash
oc patch deployment/payment-api -n payments --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
```

### OpenShift-Specific Check: Project Node Selector

OpenShift projects can have default node selectors through namespace annotations.

```bash
oc get namespace payments -o yaml | grep -i node-selector -A3
```

Check:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: workload=payment
```

If this annotation exists, all pods in that namespace may inherit node placement restrictions.

### Fix

Update the namespace annotation:

```bash
oc annotate namespace payments openshift.io/node-selector- --overwrite
```

Or set a valid selector:

```bash
oc annotate namespace payments openshift.io/node-selector='workload=payment' --overwrite
```

## 10. Check Node Affinity

Node affinity is more expressive than node selector. It may require specific node labels.

### Command

```bash
oc get pod <pod-name> -n <namespace> -o yaml | grep -A50 affinity
```

Example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node-role.kubernetes.io/infra
          operator: Exists
```

This pod can only run on infra nodes. If no infra nodes are available or schedulable, the pod stays pending.

### Check Matching Nodes

```bash
oc get nodes -l node-role.kubernetes.io/infra
```

### Fix

Either label the correct nodes:

```bash
oc label node worker-3 node-role.kubernetes.io/infra=
```

Or change the pod/deployment affinity rules.

---

## 11. Check Pod Affinity and Anti-Affinity

Pod anti-affinity can block scheduling when replicas are not allowed to run together on the same node or topology zone.

### Command

```bash
oc get deployment <deployment-name> -n <namespace> -o yaml | grep -A80 affinity
```

Example:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values:
          - payment-api
      topologyKey: kubernetes.io/hostname
```

### Problem

If the deployment has 5 replicas but only 3 worker nodes, and hard anti-affinity requires one pod per hostname, only 3 replicas can schedule. The remaining 2 stay pending.

### Fix

Change hard anti-affinity to preferred anti-affinity:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values:
          - payment-api
      topologyKey: kubernetes.io/hostname
```

Or add more worker nodes.

## 12. Check Taints and Tolerations

A node can be `Ready` but tainted. The scheduler will not place pods on tainted nodes unless the pod has matching tolerations.

### Commands

```bash
oc describe node <node-name> | grep -i taints -A5
```

Or:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

Example:

```text
Taints: node-role.kubernetes.io/infra:NoSchedule
```

### Pod Event Example

```text
0/3 nodes are available: 3 node(s) had untolerated taint {node-role.kubernetes.io/infra: }.
```

### Fix Option 1: Add Toleration

```yaml
tolerations:
- key: "node-role.kubernetes.io/infra"
  operator: "Exists"
  effect: "NoSchedule"
```

### Fix Option 2: Remove Taint

Only do this if it matches cluster design:

```bash
oc adm taint nodes worker-1 node-role.kubernetes.io/infra:NoSchedule-
```

### Senior-Level Note

Do not blindly remove taints from infra, master/control-plane, storage, GPU, or dedicated nodes. Understand why the taint exists.

## 13. Check PVC Binding

A pod can be pending because its PersistentVolumeClaim is not bound.

### Pod Event Example

```text
pod has unbound immediate PersistentVolumeClaims
```

### Commands

```bash
oc get pvc -n <namespace>
oc describe pvc <pvc-name> -n <namespace>
oc get pv
oc get storageclass
```

Example:

```bash
oc get pvc -n payments
```

Output:

```text
NAME           STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
payment-data   Pending                                      fast-block
```

### Common Causes

- StorageClass does not exist
- Dynamic provisioner is not working
- No matching PV exists
- Requested size is too large
- Access mode mismatch
- Volume mode mismatch
- Storage backend issue
- CSI driver issue
- Immediate binding with topology conflict

### Check StorageClass

```bash
oc get storageclass
oc describe storageclass fast-block
```

### Check CSI Pods

```bash
oc get pods -A | grep -i csi
```

### Fix Examples

Create a valid StorageClass, fix the CSI driver, create a matching PV, or update the PVC to use the correct storage class.

Example PVC correction:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: payment-data
  namespace: payments
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: thin-csi
  resources:
    requests:
      storage: 10Gi
```

## 14. Check Volume Node Affinity Conflict

A PVC may be bound, but the volume may only be attachable to nodes in a certain zone or topology.

### Event Example

```text
0/3 nodes are available: 3 node(s) had volume node affinity conflict.
```

### Commands

```bash
oc get pvc <pvc-name> -n <namespace> -o wide
oc get pv <pv-name> -o yaml
```

Look for:

```yaml
nodeAffinity:
  required:
    nodeSelectorTerms:
```

### Meaning

The PV is tied to a zone, rack, host, or topology where the pod is not allowed to run.

### Fix

- Adjust pod node affinity to match volume topology
- Recreate PVC with a suitable StorageClass
- Use `WaitForFirstConsumer` volume binding mode for topology-aware provisioning
- Avoid manually binding PVs to incompatible zones

---

## 15. Check HostPort Conflict

If the pod requests a `hostPort`, only one pod using that port can run on each node.

### Command

```bash
oc get pod <pod-name> -n <namespace> -o yaml | grep -A5 hostPort
```

Example:

```yaml
ports:
- containerPort: 8080
  hostPort: 8080
```

### Event Example

```text
0/3 nodes are available: 3 node(s) didn't have free ports for the requested pod ports.
```

### Fix

Avoid `hostPort` unless absolutely required. Use Service and Route instead:

```bash
oc expose deployment/payment-api --port=8080 -n payments
oc expose service/payment-api -n payments
```

## 16. Check Topology Spread Constraints

Topology spread constraints can prevent scheduling if the cluster cannot satisfy distribution rules.

### Command

```bash
oc get deployment <deployment-name> -n <namespace> -o yaml | grep -A50 topologySpreadConstraints
```

Example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: payment-api
```

### Problem

If nodes do not have proper zone labels, or only one zone has capacity, the scheduler may block the pod.

### Check Node Labels

```bash
oc get nodes --show-labels | grep topology.kubernetes.io/zone
```

### Fix

- Add correct topology labels
- Change `DoNotSchedule` to `ScheduleAnyway` if acceptable
- Add capacity in required zones
- Correct the label selector

## 17. Check Special Resources: GPU, HugePages, SR-IOV, Device Plugins

Pods that request extended resources can be pending even when CPU and memory are available.

### Example GPU Request

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

### Example HugePages Request

```yaml
resources:
  requests:
    hugepages-1Gi: 2Gi
```

### Commands

```bash
oc describe node <node-name> | grep -A20 Capacity
oc describe node <node-name> | grep -A20 Allocatable
```

Check device plugin pods:

```bash
oc get pods -A | grep -E 'gpu|sriov|device|plugin'
```

### Fix

- Install/fix device plugin operator
- Label and configure nodes correctly
- Allocate the special hardware to worker nodes
- Reduce resource request
- Ensure MachineConfig and kernel parameters are correct for hugepages or SR-IOV

## 18. Check Scheduler Health

If many unrelated pods are pending across namespaces, check scheduler health.

### Commands

```bash
oc get clusteroperator scheduler
oc describe clusteroperator scheduler
oc get pods -n openshift-kube-scheduler
oc logs -n openshift-kube-scheduler -l app=openshift-kube-scheduler --tail=100
```

### Also Check Cluster Operators

```bash
oc get co
```

Look for degraded operators:

```text
scheduler                  True    False   False
kube-apiserver             True    False   False
machine-config             True    False   False
```

### Senior-Level Interpretation

If only one pod is pending, it is usually a pod-specific constraint.

If many pods across namespaces are pending, suspect a cluster-wide issue such as scheduler, API server, admission, MachineConfig, storage provisioner, or infrastructure capacity.

## 19. Check MachineConfig and Node Conditions

A node can show `Ready`, but still have pressure or scheduling issues.

### Commands

```bash
oc describe node <node-name>
```

Check conditions:

```text
MemoryPressure
DiskPressure
PIDPressure
NetworkUnavailable
Ready
```

Check schedulability:

```bash
oc get nodes
oc describe node <node-name> | grep -i Unschedulable
```

Check cordoned nodes:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,STATUS:.status.conditions[-1].type,SCHEDULABLE:.spec.unschedulable
```

If a node is cordoned:

```text
SchedulingDisabled
```

### Fix

Uncordon only after confirming the node is safe:

```bash
oc adm uncordon <node-name>
```

## 20. Check Image Pull and Admission Issues

Usually image pull problems show as `ImagePullBackOff` or `ErrImagePull`, not pure `Pending`. However, during early pod creation, some image or admission issues may appear in events.

### Commands

```bash
oc describe pod <pod-name> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Check image pull secret:

```bash
oc get sa -n <namespace>
oc describe sa default -n <namespace>
oc get secret -n <namespace>
```

Link pull secret:

```bash
oc secrets link default <pull-secret-name> --for=pull -n <namespace>
```

## 21. Check Security Context Constraints and Admission

In OpenShift, SCC issues often cause pod creation failure or container startup failure. Some cases appear during admission rather than scheduling.

### Commands

```bash
oc describe pod <pod-name> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Check service account:

```bash
oc get pod <pod-name> -n <namespace> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

Check SCC access:

```bash
oc adm policy who-can use scc restricted-v2
oc adm policy who-can use scc anyuid
```

### Example SCC Error

```text
unable to validate against any security context constraint
```

### Fix

Grant the least privileged SCC required by the workload:

```bash
oc adm policy add-scc-to-user anyuid -z <service-account> -n <namespace>
```

For production, avoid `anyuid` unless truly required. Prefer fixing the image to run as non-root and use `restricted-v2`.

## 22. Check Deployment, ReplicaSet, and Owner Chain

Sometimes the pending pod is created by a deployment, operator, job, cronjob, or statefulset. Fixing only the pod is useless because the controller will recreate it.

### Commands


Check ReplicaSet:

```bash
oc get rs -n <namespace>

```

Check Deployment:


For StatefulSet:

```bash

```

For Operator-managed workloads:

```bash
oc get csv -n <namespace>
oc get subscription -n <namespace>
```

## 24. Practical Troubleshooting Flow

Use this order in real production troubleshooting:

```text
1. Confirm pod state
2. Describe pod and read events
3. Check if pod is scheduled to a node
4. Check resource requests vs node allocatable
5. Check quota and LimitRange
6. Check nodeSelector and project node selector
7. Check node affinity and pod anti-affinity
8. Check taints and tolerations
9. Check PVC and StorageClass
10. Check volume node affinity
11. Check topology spread constraints
12. Check hostPort conflicts
13. Check special resources such as GPU, hugepages, SR-IOV
14. Check SCC/admission events
15. Check scheduler and cluster operators if issue is widespread
```

## 26. Common Event Messages and Meaning

| Event Message | Meaning | Fix |
|---|---|---|
| `Insufficient cpu` | Pod CPU request cannot fit | Reduce request or add nodes |
| `Insufficient memory` | Pod memory request cannot fit | Reduce request or add nodes |
| `had untolerated taint` | Node has taint pod cannot tolerate | Add toleration or use other node |
| `didn't match Pod's node affinity/selector` | Label/affinity mismatch | Fix labels, nodeSelector, or affinity |
| `pod has unbound immediate PersistentVolumeClaims` | PVC is pending | Fix StorageClass/PV/CSI |
| `volume node affinity conflict` | PV topology does not match node | Fix topology, storage, or affinity |
| `didn't have free ports for requested pod ports` | hostPort conflict | Remove hostPort or reduce replicas |
| `exceeded quota` | Namespace or cluster quota exhausted | Increase quota or reduce usage |
| `max node group size reached` | Autoscaler cannot add nodes | Increase autoscaler/max machines |
| `preemption is not helpful` | Scheduler cannot evict lower-priority pods to fit | Change constraints or add capacity |

## 27. Real Interview Scenario Walkthrough

### Problem

Developer says:

```text
payment-api pod is Pending. Nodes are Ready. Please fix urgently.
```

### Step 1: Check Pod

```bash
oc get pod -n payments -o wide
```

Output:

```text
NAME                         READY   STATUS    NODE
payment-api-7c9d88c9f-8jkl2  0/1     Pending   <none>
```

`NODE` is `<none>`, so the pod has not been scheduled yet.

### Step 2: Describe Pod

```bash
oc describe pod payment-api-7c9d88c9f-8jkl2 -n payments
```

Event:

```text
0/3 nodes are available: 2 Insufficient memory, 1 node(s) had untolerated taint.
```

### Step 3: Check Resource Request

```bash
oc get deployment payment-api -n payments -o yaml | grep -A10 resources:
```

Output:

```yaml
resources:
  requests:
    cpu: "2"
    memory: 8Gi
  limits:
    cpu: "4"
    memory: 16Gi
```

### Step 4: Check Node Allocated Resources

```bash
oc describe node worker-1
oc describe node worker-2
oc describe node worker-3
```

Output:

```text
worker-1: memory requests 92%
worker-2: memory requests 95%
worker-3: taint dedicated=infra:NoSchedule
```

### Step 5: Root Cause

The pod is pending because:

1. Two worker nodes do not have enough allocatable memory based on existing requests.
2. The third node is tainted for infra workloads and the pod does not tolerate that taint.

### Step 6: Fix

For immediate recovery, reduce memory request if application sizing allows:

```bash
oc set resources deployment/payment-api \
  --requests=cpu=500m,memory=1Gi \
  --limits=cpu=1,memory=2Gi \
  -n payments
```

Then monitor rollout:

```bash
oc rollout status deployment/payment-api -n payments
oc get pods -n payments -o wide
```

For permanent fix:

- Review actual usage from Prometheus/Grafana
- Right-size requests and limits
- Add worker node capacity if demand is valid
- Keep infra taints intact unless app is intended to run there
- Apply namespace quota strategy
- Define LimitRange defaults properly

## 28. What Not To Do

Do not troubleshoot randomly.

Avoid these mistakes:

```text
Wrong: Nodes are Ready, so delete the pod.
Wrong: Restart kubelet immediately.
Wrong: Remove all taints from all nodes.
Wrong: Increase limits without checking requests.
Wrong: Blame CNI before checking pod events.
Wrong: Ignore PVC status.
Wrong: Change SCC to privileged without evidence.
```

A senior administrator starts from events and validates the scheduler decision path.

## 29. Production Root Cause Categories

### Category 1: Capacity Issue

Symptoms:

```text
Insufficient cpu
Insufficient memory
Insufficient ephemeral-storage
```

Checks:

```bash
oc describe node
oc adm top nodes
oc adm top pods -A
```

Fix:

- Right-size requests
- Scale down unused workloads
- Add worker nodes
- Tune quotas

### Category 2: Placement Issue

Symptoms:

```text
node(s) didn't match node selector
node(s) didn't match node affinity
node(s) had untolerated taint
```

Fix:

- Correct labels
- Correct node selectors
- Correct affinity
- Add tolerations only where appropriate

### Category 3: Storage Issue

Symptoms:

```text
pod has unbound immediate PersistentVolumeClaims
volume node affinity conflict
```

Fix:

- Fix StorageClass
- Fix CSI driver
- Create matching PV
- Correct topology

### Category 4: Policy Issue

Symptoms:

```text
exceeded quota
failed quota
forbidden by admission
unable to validate against security context constraint
```

Fix:

- Adjust quota
- Adjust LimitRange
- Fix SCC/service account
- Fix admission policy

### Category 5: Cluster-Wide Control Plane Issue

Symptoms:

```text
Many pods pending across namespaces
Scheduler degraded
API/admission delays
CSI provisioner down
```

Fix:

- Check cluster operators
- Check scheduler logs
- Check API server health
- Check storage operator
- Check MachineConfigPool

## 30. Advanced Checks for 10-Year Experience

### Check Scheduler Queue and Logs

```bash
oc logs -n openshift-kube-scheduler -l app=openshift-kube-scheduler --tail=200
```

Look for:

```text
FailedScheduling
Preemption is not helpful
node affinity conflict
```

### Check Cluster Autoscaler or Machine Autoscaler

If cluster autoscaling is enabled:

```bash
oc get clusterautoscaler -A
oc get machineautoscaler -A
oc get machines -n openshift-machine-api
oc get machinesets -n openshift-machine-api
```

Pending pods may remain pending if autoscaler cannot add capacity due to max replicas, cloud quota, machine API issue, or unavailable instance type.

### Check MachineConfigPool

```bash
oc get mcp
oc describe mcp worker
```

If workers are updating or degraded, available scheduling capacity may be reduced.

### Check Pod Priority and Preemption

```bash
oc get priorityclass
oc get pod <pod-name> -n <namespace> -o yaml | grep priority -A5
```

If preemption is not helpful, it means even evicting lower-priority pods cannot satisfy all constraints.

### Check Ephemeral Storage

```bash
oc describe node <node-name> | grep -i ephemeral -A5
oc describe pod <pod-name> -n <namespace> | grep -i ephemeral -A5
```

Event:

```text
Insufficient ephemeral-storage
```

Fix by cleaning node disk, reducing requests, or adding capacity.

## 31. Final Interview Answer

A strong interview answer would be:

> If a pod is Pending while all nodes are Ready, I first check whether the pod has been assigned to a node. If `NODE` is `<none>`, it is a scheduling issue. I run `oc describe pod` and read the Events section because the scheduler normally gives the exact reason. Then I check resource requests versus node allocatable, namespace ResourceQuota, ClusterResourceQuota, LimitRange defaults, nodeSelector, OpenShift project node selector, node affinity, pod anti-affinity, taints and tolerations, PVC binding, StorageClass, volume node affinity, topology spread constraints, hostPort conflicts, special resources such as GPU or hugepages, and scheduler health. If the issue affects only one workload, I focus on pod-specific constraints. If many pods are pending across namespaces, I check scheduler, cluster operators, CSI/storage, MachineConfigPool, and cluster capacity. I avoid deleting pods blindly because the controller will recreate the same broken spec. I fix the root cause in the owning Deployment, StatefulSet, Operator CR, quota, node labels, storage, or capacity layer.
