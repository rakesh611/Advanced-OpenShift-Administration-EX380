## 1. Why TLS Certificates Matter in OpenShift

TLS certificates in OpenShift are not just about making browser warnings disappear. They are part of the trust fabric of the platform. They secure communication between users, applications, routers, operators, kubelets, the API server, etcd, monitoring components, webhooks, image registries, and external systems.

In an enterprise OpenShift cluster, certificates answer these operational questions:

- Is the client really talking to the OpenShift API server?
- Is the browser really talking to the application route and not a man-in-the-middle?
- Can the router trust the backend service certificate in a re-encrypt route?
- Can an admission webhook be trusted by the Kubernetes API server?
- Can platform components trust a corporate proxy that intercepts TLS?
- Can kubelet safely communicate with the API server?
- Are etcd peer and client connections encrypted and authenticated?
- Can workloads use internal TLS without every team manually building a PKI process?

A senior administrator must understand both sides of TLS:

1. **Identity**: A certificate proves the identity of a server, client, service, node, or component.
2. **Trust**: A client trusts that identity only if it trusts the issuing CA chain.

Most certificate problems in OpenShift are not caused by TLS itself. They are caused by one of the following:

- Wrong SAN on the certificate.
- Wrong certificate chain order.
- Missing intermediate CA.
- Private key does not match the certificate.
- Certificate stored in the wrong namespace.
- Certificate secret referenced by the wrong object.
- IngressController patched but router not using expected certificate.
- Internal components do not trust the CA that signed a custom ingress or API certificate.
- Service CA bundle injected into the wrong place or overwritten unexpectedly.
- CSR pending for kubelet serving certificates.
- Corporate proxy CA not added to OpenShift trusted CA bundle.
- Expired certificate or CA.
- Manual CA rotation without planning pod restarts.

## 2. TLS Fundamentals for Senior OpenShift Administrators

### 2.1 TLS Objects You Must Know

| Object | Meaning | OpenShift Example |
|---|---|---|
| Private key | Secret key used by server/client to prove identity | `tls.key` in a Kubernetes TLS secret |
| Public certificate | Public identity document signed by a CA | `tls.crt` in a TLS secret |
| CA certificate | Certificate used to sign and validate other certificates | Service CA, ingress CA, corporate proxy CA |
| Intermediate CA | CA between root and leaf certificate | Enterprise PKI chain |
| Root CA | Top-level trust anchor | Public CA root or corporate root CA |
| Certificate chain | Leaf + intermediates + optional root | Required for API/ingress named certs |
| SAN | Subject Alternative Name; modern hostname identity | `*.apps.cluster.example.com`, `api.cluster.example.com` |
| Key usage | Declares allowed certificate use | server auth, client auth |
| SNI | Server Name Indication; TLS client tells server which name it wants | API named certs, router default certs |
| Trust bundle | A group of trusted CA certificates | `ca-bundle.crt` config map |

### 2.2 Certificate Chain Order

For OpenShift API and ingress custom certificates, chain order matters:

```text
-----BEGIN CERTIFICATE-----
leaf/server/wildcard certificate
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
intermediate CA certificate
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
root CA certificate, if included
-----END CERTIFICATE-----
```

The private key must match the first certificate in the chain.

Validate this before importing:

```bash
openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

The hashes must match.

Check SAN:

```bash
openssl x509 -in tls.crt -noout -text | grep -A2 "Subject Alternative Name"
```

For an OpenShift ingress wildcard certificate, expect something like:

```text
DNS:*.apps.ocp4.example.com
```

For an API named certificate, expect something like:

```text
DNS:api.ocp4.example.com
```

### 2.3 CN Is Not Enough

Older administrators often check only the certificate CN. Modern TLS validation requires SAN. The CN can be present, but clients validate the hostname against the SAN extension.

Bad certificate example:

```text
Subject: CN=*.apps.ocp4.example.com
SAN: missing
```

Good certificate example:

```text
Subject: CN=*.apps.ocp4.example.com
SAN: DNS:*.apps.ocp4.example.com
```

### 2.4 TLS Serving Certificate vs Client Certificate

OpenShift uses both serving and client certificates.

| Certificate Type | Purpose | Example |
|---|---|---|
| Serving certificate | Server proves identity to client | API server, router, service, webhook |
| Client certificate | Client proves identity to server | kubelet client cert, etcd client cert |
| CA certificate | Used to verify certificates | service-ca, etcd-signer, corporate CA |

When troubleshooting, first identify which side is failing:

- Server failed to present a valid certificate.
- Client does not trust the server's CA.
- Client certificate is expired or rejected.
- Server requires client auth but client did not present a valid certificate.

## 3. OpenShift Certificate Architecture

OpenShift is a Kubernetes distribution, but it adds Operators that own and reconcile many certificate assets. That changes how administrators should work. In OpenShift, you generally do not edit static files directly on masters or workers. You modify cluster APIs, secrets, config maps, and custom resources, then Operators reconcile the state.

### 3.1 Major Certificate Domains

| Domain | Main Component | Typical Namespace | Managed By |
|---|---|---|---|
| API server external serving cert | Kubernetes API server | `openshift-config`, `openshift-kube-apiserver` | User for named cert, Operator for rollout |
| Default ingress wildcard cert | IngressController/router | `openshift-ingress`, `openshift-ingress-operator` | User for custom default cert |
| Route-specific certs | Route object | Application namespace | Application/admin owner |
| Internal service certs | service-ca | App namespace + `openshift-service-ca` | service-ca Operator |
| Node/kubelet certs | kubelet/API communication | node filesystem, operator namespaces | System-managed |
| etcd certs | etcd peer/client/server/metrics | `openshift-etcd`, `openshift-kube-apiserver` | etcd Operator/system |
| Proxy trust bundle | Cluster-wide egress trust | `openshift-config`, `openshift-config-managed` | User provides CA, platform distributes |
| OLM/webhook/APIService certs | OLM and installed Operators | `openshift-operator-lifecycle-manager`, operator namespaces | OLM/system or user depending case |
| Monitoring/logging certs | Prometheus/logging services | `openshift-monitoring`, `openshift-logging` | System-managed |
| cert-manager app certs | Workload certificates | User namespaces | cert-manager Operator + issuers |

### 3.2 High-Level Traffic Map

```text
External user/browser
        |
        | TLS to route host, e.g. app.apps.cluster.example.com
        v
OpenShift router / IngressController
        |
        | HTTP, TLS passthrough, or TLS re-encrypt
        v
Application Service / Pod

oc CLI / automation
        |
        | TLS to api.cluster.example.com:6443
        v
Kubernetes API server
        |
        | mTLS / internal certs
        v
etcd, kubelet, aggregated APIs, admission webhooks
```

### 3.3 The Senior Admin Principle

For every OpenShift certificate task, answer these four questions before touching the cluster:

1. **Who presents the certificate?**
2. **Who validates the certificate?**
3. **Which CA signs the certificate?**
4. **Where must the CA be trusted?**

Example: default ingress custom certificate.

- Presenter: router pod.
- Validator: browser, curl, oc console callback, OAuth, console, registry, external clients.
- Signing CA: public CA or corporate CA.
- Trust location: external clients already trust public CA; internal components might need CA added through cluster-wide trusted CA.

## 4. Certificate Ownership: System-Managed vs User-Managed

### 4.1 System-Managed Certificates

System-managed certificates are created and rotated by OpenShift Operators. Do not manually replace them unless documentation explicitly gives a supported procedure.

Examples:

- Service CA certificates.
- Kubelet/node certificates.
- Bootstrap certificate lifecycle.
- etcd peer/client/server certificates.
- Control plane component certificates.
- Monitoring service certificates.
- Many OLM-generated certificates.

System-managed does not mean you ignore them. It means you monitor them and use supported APIs/procedures when intervention is required.

### 4.2 User-Managed Certificates

User-managed certificates require your operational process for lifecycle, renewal, storage, and rotation.

Examples:

- API server named certificates.
- Custom default ingress wildcard certificate.
- Route-specific edge/re-encrypt certificates.
- Corporate proxy trust CA bundle.
- Custom MachineConfig trust anchors.
- cert-manager issuers and certificates for application workloads.

### 4.3 Rule of Thumb

If the certificate belongs to OpenShift infrastructure internals, assume the Operator owns it. If the certificate is for external client trust, corporate PKI, or application-specific TLS identity, assume the user/admin owns it.

## 5. API Server TLS Certificates

The OpenShift API is normally reached at:

```text
https://api.<cluster_name>.<base_domain>:6443
```

Example:

```text
https://api.ocp4.example.com:6443
```

The API server certificate is critical because every `oc`, `kubectl`, GitOps controller, CI system, monitoring integration, and external automation uses it.

### 5.1 Default API Certificate

By default, the API server uses an internal OpenShift cluster CA. Internal cluster clients trust it, but external clients might not. That is why many enterprises add a named API certificate signed by a public or enterprise CA.

### 5.2 Named API Certificate Concept

OpenShift supports named certificates for the API server. The API server selects a certificate based on the hostname requested by the client, using TLS SNI.

This is useful when:

- The cluster API is behind an enterprise load balancer.
- Corporate automation requires a certificate issued by internal PKI.
- Security policy disallows self-signed or cluster-internal CA certificates for external API access.
- You want `oc login https://api.company.com:6443` to validate cleanly without `--insecure-skip-tls-verify`.

### 5.3 Important Warning: Do Not Replace `api-int`

Do not configure a named certificate for:

```text
api-int.<cluster_name>.<base_domain>
```

That endpoint is used internally by nodes and control plane components. Providing a named cert for the internal load balancer can degrade the cluster.

### 5.4 API Certificate Prerequisites

Prepare:

- Certificate for the exact FQDN.
- Unencrypted private key.
- SAN containing the API FQDN.
- Correct chain order: API certificate first, then intermediate certificates, then root if required.
- Secret in `openshift-config` namespace.

### 5.5 Add an API Server Named Certificate

Create the secret:

```bash
oc create secret tls api-custom-cert \
  --cert=/path/to/api-chain.crt \
  --key=/path/to/api.key \
  -n openshift-config
```

Patch `apiserver/cluster`:

```bash
oc patch apiserver cluster --type=merge -p '
{
  "spec": {
    "servingCerts": {
      "namedCertificates": [
        {
          "names": ["api.ocp4.example.com"],
          "servingCertificate": {
            "name": "api-custom-cert"
          }
        }
      ]
    }
  }
}'
```

Watch rollout:

```bash
oc get clusteroperators kube-apiserver
oc get pods -n openshift-kube-apiserver -l app=openshift-kube-apiserver -w
```

Adding a named API certificate for the first time triggers a new kube-apiserver revision. Node reboots are not required.

### 5.6 Renew an Existing API Named Certificate

If the secret name remains the same, replace the secret contents:

```bash
oc create secret tls api-custom-cert \
  --cert=/path/to/new-api-chain.crt \
  --key=/path/to/new-api.key \
  -n openshift-config \
  --dry-run=client -o yaml | oc replace -f -
```

Check operator state:

```bash
oc get clusteroperators kube-apiserver
```

For an existing named certificate renewal, API server pods can hot-reload the updated certificate asset without rolling a new revision, provided only the secret content changes and the API server configuration structure is not changed.

### 5.7 Verify API Certificate from Outside

```bash
openssl s_client -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com \
  -showcerts </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
```

Check SAN:

```bash
openssl s_client -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -text | grep -A2 "Subject Alternative Name"
```

Validate using curl:

```bash
curl -v https://api.ocp4.example.com:6443/version
```

Expected: no x509 trust error if your client trusts the CA.

### 5.8 Common API Certificate Problems

#### Problem: `x509: certificate signed by unknown authority`

Cause:

- Client does not trust the CA.
- Missing intermediate certificate.
- Corporate CA not installed on the client.

Fix:

- Provide full chain in `tls.crt`.
- Install corporate root/intermediate CA on client trust store.
- Avoid `--insecure-skip-tls-verify` except for emergency diagnostics.

#### Problem: `x509: certificate is valid for X, not Y`

Cause:

- SAN does not include the API hostname used by the client.
- Client connecting to load balancer alias not present in SAN.

Fix:

- Reissue certificate with all required API FQDNs.
- Patch named certificate names accordingly.

#### Problem: Cluster degraded after API cert change

Cause possibilities:

- Accidentally configured certificate for `api-int`.
- Secret missing key/cert.
- Invalid chain or mismatched key.
- API server config patch malformed.

Diagnostics:

```bash
oc get co kube-apiserver
oc describe co kube-apiserver
oc get apiserver cluster -o yaml
oc get secret api-custom-cert -n openshift-config -o yaml
```

## 6. Ingress and Default Wildcard Certificates

OpenShift routes are normally exposed under:

```text
*.apps.<cluster_name>.<base_domain>
```

Example:

```text
*.apps.ocp4.example.com
```

The router/IngressController uses a default certificate for secured routes that do not specify their own certificate.

### 6.1 Default Ingress Certificate

By default, the Ingress Operator creates an internal CA and issues a wildcard certificate for the `.apps` subdomain. The web console and CLI-related route flows also use this certificate.

The default operator-generated certificate is useful for installation and internal bootstrap, but in production you should use a custom default certificate signed by a public or enterprise CA.

### 6.2 Why Replace the Default Wildcard Certificate?

Replace it when:

- External users access applications via browser.
- Security policy requires trusted public or corporate CA.
- You want to remove browser/curl warnings.
- You expose the OpenShift console through the default apps domain.
- OAuth callback routes must work cleanly for enterprise users.
- External integrations call route endpoints.

### 6.3 Ingress Certificate Requirements

You need:

- Wildcard certificate for `*.apps.<cluster>.<domain>`.
- Unencrypted private key.
- SAN containing the wildcard DNS name.
- Full chain in PEM format.
- Root CA in separate PEM file when updating cluster trust.
- Certificate secret in `openshift-ingress` namespace.
- IngressController patch in `openshift-ingress-operator` namespace.

### 6.4 Replace the Default Ingress Certificate

Create a ConfigMap with the root CA if needed:

```bash
oc create configmap custom-ca \
  --from-file=ca-bundle.crt=/path/to/root-ca.crt \
  -n openshift-config
```

Update cluster trusted CA:

```bash
oc patch proxy/cluster \
  --type=merge \
  --patch='{"spec":{"trustedCA":{"name":"custom-ca"}}}'
```

Create wildcard certificate secret:

```bash
oc create secret tls apps-wildcard-cert \
  --cert=/path/to/apps-chain.crt \
  --key=/path/to/apps.key \
  -n openshift-ingress
```

Patch the default IngressController:

```bash
oc patch ingresscontroller.operator default \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"apps-wildcard-cert"}}}' \
  -n openshift-ingress-operator
```

Check router rollout/state:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get pods -n openshift-ingress
oc get co ingress
```

### 6.5 Renewal Behavior

For default ingress certificate renewal, do not change the secret name unless you intentionally want to repoint the IngressController. Replace the secret content under the same name:

```bash
oc create secret tls apps-wildcard-cert \
  --cert=/path/to/new-apps-chain.crt \
  --key=/path/to/new-apps.key \
  -n openshift-ingress \
  --dry-run=client -o yaml | oc replace -f -
```

The kubelet propagates secret updates to mounted volumes, and the router can detect file changes and hot-reload the certificate/key pair. Updating secret contents does not require a router deployment rolling update.

### 6.6 Verify Default Ingress Certificate

Use a real route hostname:

```bash
openssl s_client -connect console-openshift-console.apps.ocp4.example.com:443 \
  -servername console-openshift-console.apps.ocp4.example.com \
  -showcerts </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
```

Check SAN:

```bash
openssl s_client -connect console-openshift-console.apps.ocp4.example.com:443 \
  -servername console-openshift-console.apps.ocp4.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -text | grep -A2 "Subject Alternative Name"
```

Check route:

```bash
curl -Iv https://console-openshift-console.apps.ocp4.example.com
```

### 6.7 Ingress Certificate Secrets and Locations

| Item | Namespace | Purpose |
|---|---|---|
| `apps-wildcard-cert` | `openshift-ingress` | User-provided default wildcard cert |
| `router-certs-<name>` | `openshift-ingress` | Operator-generated router default cert |
| `router-ca` | `openshift-ingress-operator` | Operator-generated signing CA for default certs |
| `metrics-tls` | `openshift-ingress-operator` | Ingress Operator metrics service cert |
| `router-metrics-certs-<name>` | `openshift-ingress` | IngressController metrics cert |

### 6.8 Production Warning

Do not rely on operator-generated default ingress certificates for production external traffic. They are placeholders until a custom default certificate is configured.

## 7. Route TLS Termination: Edge, Passthrough, and Re-encrypt

OpenShift routes expose services through the router. TLS termination controls where encrypted traffic is decrypted.

### 7.1 Route TLS Modes

| Mode | TLS Between Client and Router | TLS Between Router and Pod | Certificate Location | Use Case |
|---|---:|---:|---|---|
| Edge | Yes | No | Route/router | Simple HTTPS termination at router |
| Passthrough | Yes | Yes, untouched | Application pod | App owns TLS end-to-end |
| Re-encrypt | Yes | Yes | Route cert + backend cert | Enterprise end-to-end encryption with router inspection |

### 7.2 Edge Route

The router terminates TLS and forwards plain HTTP to the backend service.

Create edge route with custom cert:

```bash
oc create route edge frontend \
  --service=frontend \
  --hostname=www.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --ca-cert=ca.crt
```

Use edge when:

- Backend app speaks HTTP only.
- You want simple TLS offload at router.
- Internal cluster traffic risk is acceptable or controlled.

Avoid edge when:

- Compliance requires encryption all the way to the pod.
- Sensitive traffic should not be plaintext between router and service.

### 7.3 Passthrough Route

The router does not terminate TLS. It passes encrypted traffic to the backend. The backend application presents the certificate.

```bash
oc create route passthrough route-passthrough-secured \
  --service=frontend \
  --port=8443
```

Use passthrough when:

- Application must own TLS completely.
- Client certificate authentication is handled by the application.
- Router should not inspect HTTP headers.

Limitations:

- Router cannot modify HTTP headers because it cannot decrypt traffic.
- Some L7 features are not available.
- Certificate lives in application, not route.

### 7.4 Re-encrypt Route

Router terminates client TLS, then opens a new TLS connection to backend.

```bash
oc create route reencrypt frontend \
  --service=frontend \
  --hostname=www.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --ca-cert=ca.crt \
  --dest-ca-cert=destca.crt
```

`dest-ca-cert` is important. It tells the router which CA to trust for the backend service certificate.

Use re-encrypt when:

- You need end-to-end encryption.
- Router should still make routing decisions at HTTP level.
- Backend service uses a service serving certificate or app certificate.

### 7.5 Route Certificate vs Default Ingress Certificate

A route-specific certificate overrides the default IngressController certificate for that route host. If a route does not specify a certificate, the router uses the IngressController default certificate.

### 7.6 Re-encrypt with Service Serving Certificate

Typical pattern:

1. Annotate backend service to generate service serving certificate.
2. Mount generated secret into backend pod.
3. Inject service CA bundle into a config map or extract it.
4. Use service CA as route `dest-ca-cert`.
5. Create re-encrypt route.

Example backend service cert:

```bash
oc annotate service backend \
  service.beta.openshift.io/serving-cert-secret-name=backend-tls
```

Extract service CA from injected config map or secret source, then:

```bash
oc create route reencrypt backend \
  --service=backend \
  --hostname=backend.apps.ocp4.example.com \
  --dest-ca-cert=service-ca.crt
```

## 8. Service Serving Certificates and Service CA

The OpenShift service-ca Operator gives internal services an easy way to get TLS serving certificates without integrating every team with an external PKI.

### 8.1 What Service Serving Certificates Are For

Service serving certificates provide automatic TLS encryption for service-to-service communication inside the cluster.

They are best for:

- Internal APIs.
- Operator webhooks.
- Metrics endpoints.
- Re-encrypt route backends.
- Middleware that requires TLS.
- Internal service clients that can trust the OpenShift service CA.

They are not intended for public internet-facing certificates.

### 8.2 Generate a Service Certificate

Annotate a service:

```bash
oc annotate service myservice \
  service.beta.openshift.io/serving-cert-secret-name=myservice-tls \
  -n mynamespace
```

OpenShift creates a TLS secret in the same namespace:

```bash
oc get secret myservice-tls -n mynamespace
```

The secret contains:

```text
tls.crt
tls.key
```

Mount it into the pod:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myservice
  namespace: mynamespace
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myservice
  template:
    metadata:
      labels:
        app: myservice
    spec:
      containers:
      - name: myservice
        image: example/myservice:latest
        ports:
        - containerPort: 8443
        volumeMounts:
        - name: tls
          mountPath: /etc/tls/private
          readOnly: true
      volumes:
      - name: tls
        secret:
          secretName: myservice-tls
```

### 8.3 Service Certificate Validity

The generated certificate is valid only for the internal service DNS name:

```text
<service>.<namespace>.svc
```

For example:

```text
myservice.mynamespace.svc
```

For a headless service, a wildcard subject might be generated:

```text
*.myservice.mynamespace.svc
```

Important security point: do not use service CA for cases where the client must differentiate individual pods behind a headless service. A wildcard service certificate can let one pod impersonate another pod identity under that service DNS pattern.

### 8.4 Inject Service CA Bundle into a ConfigMap

Create an empty config map:

```bash
oc create configmap service-ca-bundle -n mynamespace
```

Annotate it:

```bash
oc annotate configmap service-ca-bundle \
  service.beta.openshift.io/inject-cabundle=true \
  -n mynamespace
```

Check injection:

```bash
oc get configmap service-ca-bundle -n mynamespace -o yaml
```

You should see:

```yaml
data:
  service-ca.crt: |
    -----BEGIN CERTIFICATE-----
    ...
```

Important: when you add the injection annotation, the service-ca Operator can overwrite existing data in that config map. Use a dedicated config map only for the CA bundle.

### 8.5 Inject CA into APIService, CRD, and Webhooks

For aggregated APIs:

```bash
oc annotate apiservice v1alpha1.example.com \
  service.beta.openshift.io/inject-cabundle=true
```

For CRD conversion webhooks:

```bash
oc annotate crd widgets.example.com \
  service.beta.openshift.io/inject-cabundle=true
```

For mutating webhooks:

```bash
oc annotate mutatingwebhookconfiguration my-mutating-webhook \
  service.beta.openshift.io/inject-cabundle=true
```

For validating webhooks:

```bash
oc annotate validatingwebhookconfiguration my-validating-webhook \
  service.beta.openshift.io/inject-cabundle=true
```

Warning: for webhook configurations, the injected service CA bundle applies to all webhooks in that object. Do not use this annotation when different webhooks in the same configuration require different CA bundles.

### 8.6 Rotate a Service Serving Certificate

Find the generated secret:

```bash
oc describe service myservice -n mynamespace | grep serving-cert-secret-name
```

Delete the secret:

```bash
oc delete secret myservice-tls -n mynamespace
```

The service-ca Operator recreates it.

Check age:

```bash
oc get secret myservice-tls -n mynamespace
```

Restart workload if the application does not hot-reload the mounted certificate:

```bash
oc rollout restart deployment/myservice -n mynamespace
```

### 8.7 Service CA Rotation

The service CA is valid for 26 months and automatically refreshes when less than 13 months of validity remain. Service serving certificates are automatically replaced near expiration.

Manual service CA rotation is disruptive because trust with the previous service CA is not maintained in the same way. If you delete the service CA signing key, pods might need restart to use certificates issued by the new CA.

Check current service CA expiration:

```bash
oc get secrets/signing-key -n openshift-service-ca \
  -o template='{{index .data "tls.crt"}}' \
  | base64 --decode \
  | openssl x509 -noout -enddate
```

Manual rotation:

```bash
oc delete secret/signing-key -n openshift-service-ca
```

Then restart affected pods in a controlled manner, not blindly in production unless you have a maintenance window.

## 9. CA Bundles, Proxy Trust, and Node Trust Stores

TLS is not only about certificates presented by OpenShift. OpenShift also needs to trust external certificates, especially in enterprise networks with proxies, private registries, internal Git servers, artifact repositories, and security appliances.

### 9.1 Cluster-Wide Trusted CA Bundle

The cluster-wide proxy object can reference a ConfigMap containing custom trusted CAs.

Create the ConfigMap:

```bash
oc create configmap custom-ca \
  --from-file=ca-bundle.crt=/path/to/company-ca-bundle.crt \
  -n openshift-config
```

Patch cluster proxy:

```bash
oc patch proxy/cluster \
  --type=merge \
  --patch='{"spec":{"trustedCA":{"name":"custom-ca"}}}'
```

The key must be:

```text
ca-bundle.crt
```

### 9.2 What Happens Internally

OpenShift merges the user-provided CA bundle with the RHCOS trust bundle and distributes it to platform components that make egress HTTPS calls.

Examples of consumers:

- Image registry operator.
- Cluster operators that call external services.
- Components using the cluster-wide proxy.
- Some workloads or operators that mount injected trust bundles.

### 9.3 Impact of Updating Trusted CA

If you update only the trusted CA, the Machine Config Operator updates the node trust bundle and restarts critical services such as kubelet and CRI-O. Nodes can briefly become `NotReady` while services restart. A node reboot is not normally required for a trusted CA-only update.

If you change other proxy-related parameters, such as `noProxy`, node reboots can occur depending on the MachineConfig changes.

### 9.4 Install-Time Trust Bundle

During cluster installation, use `additionalTrustBundle` in `install-config.yaml` when the cluster needs to trust a proxy or corporate CA from day one.

Example:

```yaml
proxy:
  httpProxy: http://proxy.example.com:8080
  httpsProxy: http://proxy.example.com:8080
  noProxy: .example.com,10.0.0.0/8
additionalTrustBundle: |
  -----BEGIN CERTIFICATE-----
  ...company CA...
  -----END CERTIFICATE-----
```

### 9.5 Node-Level Trust with MachineConfig

For node-level trust anchors, create a MachineConfig that writes the CA certificate under:

```text
/etc/pki/ca-trust/source/anchors/
```

Example outline:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-worker-company-ca
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/pki/ca-trust/source/anchors/company-ca.crt
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,<base64_encoded_ca_certificate>
```

After MCO applies it, `update-ca-trust` and service restarts happen. Validate MachineConfigPool status:

```bash
oc get mcp
oc describe mcp worker
```

### 9.6 Common Trust Bundle Mistakes

- ConfigMap key is not `ca-bundle.crt`.
- Namespace is not `openshift-config`.
- Bundle contains leaf/server certificates instead of CA certificates.
- Missing intermediate CA.
- Corporate TLS interception proxy signs traffic with a CA not trusted by OpenShift.
- Application pods expect system trust but do not mount the updated bundle.
- Java workloads use their own JVM truststore and ignore RHEL trust bundle.

## 10. Node, Kubelet, Bootstrap, and CSR Certificates

Node certificates secure communication between kubelet and the Kubernetes API server.

### 10.1 Bootstrap Certificate

When a node first joins the cluster, kubelet uses a bootstrap kubeconfig certificate to authenticate enough to request real kubelet certificates through CertificateSigningRequests.

The bootstrap certificate is long-lived. The kubelet-managed certificate is valid for one year and rotates automatically around the 80% point of its lifetime.

### 10.2 Kubelet Client and Serving Certificates

| Certificate | Purpose |
|---|---|
| Kubelet client certificate | Kubelet authenticates to API server |
| Kubelet serving certificate | API server connects to kubelet for logs, exec, port-forward, metrics |

If kubelet serving cert is missing or invalid, commands such as these can fail:

```bash
oc logs podname
oc exec -it podname -- /bin/bash
oc rsh podname
```

### 10.3 CSR Approval

Check CSRs:

```bash
oc get csr
```

Describe a CSR:

```bash
oc describe csr <csr-name>
```

Approve a valid CSR:

```bash
oc adm certificate approve <csr-name>
```

Deny invalid CSR:

```bash
oc adm certificate deny <csr-name>
```

Approve all pending CSRs only after verifying they are legitimate:

```bash
oc get csr -o name | xargs -r oc adm certificate approve
```

A safer view of pending CSRs:

```bash
oc get csr --no-headers | awk '$NF == "Pending" {print $1}'
```

Then approve intentionally:

```bash
oc adm certificate approve csr-xxxxx
```

### 10.4 UPI and Non-Machine API Clusters

On platforms without full Machine API integration, kubelet serving CSRs might require manual or custom approval automation. If serving CSRs are not approved, node might become Ready but `oc logs`, `oc exec`, and `oc rsh` can fail because the API server cannot securely connect to kubelet.

### 10.5 Node Certificate Rotation

Node certificates are system-managed. In current OpenShift documentation, kubelet-related node certificates are automatically rotated, and the kubelet CA certificate can be manually renewed by annotating the `kube-apiserver-to-kubelet-signer` secret when needed.

Manual kubelet CA renewal:

```bash
oc annotate -n openshift-kube-apiserver-operator \
  secret kube-apiserver-to-kubelet-signer \
  auth.openshift.io/certificate-not-after-
```

### 10.6 Troubleshooting Kubelet Certificate Issues

Check nodes:

```bash
oc get nodes
oc describe node <node>
```

Check CSRs:

```bash
oc get csr
```

Check kubelet logs from node debug:

```bash
oc debug node/<node>
chroot /host
journalctl -u kubelet -b --no-pager | tail -200
```

Common symptoms:

```text
error dialing backend
x509: certificate is valid for ..., not ...
certificate signed by unknown authority
remote error: tls: bad certificate
```

## 11. etcd and Control Plane Certificates

etcd is the data store for the cluster. Its certificates protect peer, server, client, and metrics communication.

### 11.1 etcd Certificate Types

| Type | Purpose |
|---|---|
| Peer certificate | TLS between etcd members |
| Server certificate | etcd server authenticates to clients |
| Client certificate | API server/client authenticates to etcd |
| Metrics certificate | Secures etcd metrics access |
| Signer CA | Signs etcd certificates |

etcd certificates are signed by `etcd-signer`. Current OpenShift documentation states CA certificates are valid for 10 years, and peer/client/server certificates are valid for three years. These are system-managed and automatically rotated.

### 11.2 Manual etcd Certificate Rotation

Use manual rotation only for documented cases such as expiration alerts, private key compromise, or directed maintenance.

Backup signer:

```bash
oc get secret -n openshift-etcd etcd-signer -o yaml > signer_backup_secret.yaml
```

Delete signer to trigger rotation:

```bash
oc delete secret -n openshift-etcd etcd-signer
```

Wait for etcd stability:

```bash
oc wait --for=condition=Progressing=False --timeout=15m clusteroperator/etcd
```

After a signer rotation, remove unused CA bundle entries if required:

```bash
oc delete configmap -n openshift-etcd etcd-ca-bundle
oc adm wait-for-stable-cluster --minimum-stable-period 2m
```

For metrics signer rotation, use:

```text
etcd-metric-signer
etcd-metrics-ca-bundle
```

instead of:

```text
etcd-signer
etcd-ca-bundle
```

### 11.3 Control Plane Certificates

Control plane certificates live in namespaces such as:

```text
openshift-config-managed
openshift-kube-apiserver
openshift-kube-apiserver-operator
openshift-kube-controller-manager
openshift-kube-controller-manager-operator
openshift-kube-scheduler
```

They are system-managed and automatically rotated. If control plane certificates expire, use Red Hat documented recovery procedures. Do not manually edit static pod manifests or secrets without a supported procedure.

### 11.4 Practical etcd Certificate Troubleshooting

Check etcd operator:

```bash
oc get co etcd
oc describe co etcd
```

Check etcd pods:

```bash
oc get pods -n openshift-etcd
```

Check static pod logs:

```bash
oc logs -n openshift-etcd etcd-<master-node-name> -c etcd
```

Check signer secret:

```bash
oc get secret -n openshift-etcd etcd-signer -o yaml
```

Check certificate expiration:

```bash
oc get secret -n openshift-etcd etcd-signer \
  -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -dates
```

## 12. OLM, Webhooks, Aggregated APIs, Monitoring, and Logging Certificates

### 12.1 OLM Certificates

Operator Lifecycle Manager manages certificates for many OLM components and for Operators that include webhooks or API services in their CSV.

Components include:

```text
olm-operator
catalog-operator
packageserver
marketplace-operator
```

Certificates in `openshift-operator-lifecycle-manager` are generally system-managed.

Important proxy note: OLM does not automatically update the certificates of Operators it manages in proxy environments. Those certificates might need user management through subscription config.

### 12.2 Admission Webhook TLS

Admission webhooks require TLS because the Kubernetes API server calls the webhook endpoint. The API server must trust the webhook serving certificate.

Common pattern:

1. Webhook service gets service serving certificate.
2. Webhook pod mounts generated TLS secret.
3. `MutatingWebhookConfiguration` or `ValidatingWebhookConfiguration` receives CA bundle injection.
4. API server validates webhook TLS.

If the CA bundle is wrong, the API server fails webhook calls with x509 errors. Depending on failure policy, this can block object creation cluster-wide.

Critical production advice:

- Use `failurePolicy: Ignore` only when safe.
- Avoid deploying broken admission webhooks cluster-wide.
- Verify TLS before enabling strict failure policies.
- Keep webhook certificate rotation tested.

### 12.3 Aggregated APIs

Aggregated APIs use APIService objects. The Kubernetes API server connects to the backing service and must trust its serving certificate.

Inject service CA:

```bash
oc annotate apiservice <api_service_name> \
  service.beta.openshift.io/inject-cabundle=true
```

If broken, symptoms can include:

```bash
oc get apiservice
```

showing unavailable API services.

### 12.4 Monitoring and Logging Certificates

Monitoring components secure traffic with service CA certificates. Certificates present in `openshift-monitoring` or `openshift-logging` namespaces are generally system-managed and rotated automatically.

Troubleshoot monitoring TLS issues:

```bash
oc get pods -n openshift-monitoring
oc get secrets -n openshift-monitoring | grep tls
oc get servicemonitor -A
oc get co monitoring
```

## 13. cert-manager Operator for Red Hat OpenShift

The cert-manager Operator for Red Hat OpenShift provides supported certificate lifecycle management for applications. It integrates external CAs and supports provisioning, renewal, and retirement of workload certificates.

### 13.1 When to Use cert-manager

Use cert-manager when:

- Application teams need self-service certificates.
- You need ACME automation.
- You need integration with external PKI.
- You want automatic certificate renewal.
- You need GitOps-managed certificates.
- You need per-namespace or per-application certificate issuance.

### 13.2 When Not to Use cert-manager

Do not use cert-manager to replace OpenShift internal system-managed certificates unless Red Hat documentation explicitly supports that integration.

Do not install both:

- Red Hat cert-manager Operator, and
- community cert-manager Operator

in the same cluster at the same time.

### 13.3 Common Issuer Types

| Issuer | Purpose |
|---|---|
| SelfSigned | Bootstrap/testing; not ideal for production |
| CA | Internal enterprise CA integration |
| ACME | Let's Encrypt or ACME-compatible CA |
| Vault | HashiCorp Vault PKI integration |
| Venafi | Enterprise PKI management |
| Google CAS | Google Certificate Authority Service |

### 13.4 Example CA Issuer Pattern

Create CA secret:

```bash
oc create secret tls internal-ca-keypair \
  --cert=ca.crt \
  --key=ca.key \
  -n cert-demo
```

Create issuer:

```yaml
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: internal-ca
  namespace: cert-demo
spec:
  ca:
    secretName: internal-ca-keypair
```

Request certificate:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: app-cert
  namespace: cert-demo
spec:
  secretName: app-cert-tls
  dnsNames:
  - app.cert-demo.svc
  issuerRef:
    name: internal-ca
    kind: Issuer
  usages:
  - digital signature
  - key encipherment
  - server auth
```

Check status:

```bash
oc get certificate -n cert-demo
oc describe certificate app-cert -n cert-demo
oc get certificaterequest -n cert-demo
```

### 13.5 cert-manager and Ingress Default Certificate Renewal

If cert-manager manages the secret used by the IngressController default certificate, keep the same secret name. The router can hot-reload updated certificate data from the mounted secret.

## 14. Certificate Validation and Troubleshooting Commands

### 14.1 Inspect a Local Certificate File

```bash
openssl x509 -in tls.crt -noout -subject -issuer -dates
openssl x509 -in tls.crt -noout -text | less
openssl x509 -in tls.crt -noout -fingerprint -sha256
```

### 14.2 Check SAN

```bash
openssl x509 -in tls.crt -noout -text | grep -A2 "Subject Alternative Name"
```

### 14.3 Verify Key Matches Certificate

```bash
openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

### 14.4 Verify Remote Certificate

```bash
openssl s_client -connect host.example.com:443 \
  -servername host.example.com \
  -showcerts </dev/null
```

### 14.5 Extract Certificate from a Secret

```bash
oc get secret my-tls-secret -n myns \
  -o jsonpath='{.data.tls\.crt}' | base64 -d > tls.crt
```

Extract key:

```bash
oc get secret my-tls-secret -n myns \
  -o jsonpath='{.data.tls\.key}' | base64 -d > tls.key
```

Check expiration directly:

```bash
oc get secret my-tls-secret -n myns \
  -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -dates
```

### 14.6 Find TLS Secrets Across Cluster

```bash
oc get secret -A --field-selector type=kubernetes.io/tls
```

If field selector does not work for type in your environment, use:

```bash
oc get secret -A -o json \
  | jq -r '.items[] | select(.type=="kubernetes.io/tls") | [.metadata.namespace,.metadata.name] | @tsv'
```

### 14.7 Check Certificates Expiring Soon

Example script:

```bash
#!/usr/bin/env bash
set -euo pipefail

DAYS=30
NOW=$(date +%s)
LIMIT=$(( NOW + DAYS*24*60*60 ))

oc get secret -A -o json | jq -r '
  .items[]
  | select(.type=="kubernetes.io/tls")
  | [.metadata.namespace, .metadata.name, .data["tls.crt"]]
  | @tsv
' | while IFS=$'\t' read -r ns name cert; do
  enddate=$(echo "$cert" | base64 -d 2>/dev/null | openssl x509 -noout -enddate 2>/dev/null | cut -d= -f2 || true)
  [ -z "$enddate" ] && continue
  endsec=$(date -d "$enddate" +%s 2>/dev/null || true)
  [ -z "$endsec" ] && continue
  if [ "$endsec" -le "$LIMIT" ]; then
    echo "$ns/$name expires on $enddate"
  fi
done
```

On macOS, replace `date -d` with GNU date or run from a Linux admin host.

### 14.8 Check Cluster Operators

```bash
oc get co
oc describe co kube-apiserver
oc describe co ingress
oc describe co authentication
oc describe co console
oc describe co etcd
```

### 14.9 Check Events

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
```

### 14.10 Debug from a Pod

Run a UBI debug pod:

```bash
oc run tls-debug -it --rm \
  --image=registry.access.redhat.com/ubi9/ubi \
  --restart=Never \
  -- bash
```

## 15. Common Failure Scenarios and Fixes

### Scenario 1: Browser Shows Insecure Warning for OpenShift Console

Likely cause:

- Default ingress cert is self-signed/operator-generated.
- Custom default cert not configured.
- CA is internal and not trusted by browser.

Fix:

- Issue wildcard certificate for `*.apps.<cluster>.<domain>`.
- Create TLS secret in `openshift-ingress`.
- Patch IngressController default certificate.
- Add CA to cluster trust if internal components need it.

### Scenario 2: `curl` to Route Fails with Unknown Authority

```text
SSL certificate problem: unable to get local issuer certificate
```

Likely cause:

- Missing intermediate CA in route/default certificate chain.
- Client does not trust corporate root.

Fix:

- Rebuild certificate chain with leaf first, intermediates next.
- Use `openssl s_client -showcerts` to inspect served chain.

### Scenario 3: Re-encrypt Route Returns 503

Likely cause:

- Router cannot connect to backend service.
- Backend service certificate is not trusted by router.
- `dest-ca-cert` missing or wrong.
- Backend expects SNI/hostname not matching service certificate.
- Service endpoints missing.

Diagnostics:

```bash
oc get route <route> -o yaml
oc get svc,endpoints -n <ns>
oc logs -n openshift-ingress deploy/router-default
```

Fix:

- Provide correct `dest-ca-cert`.
- Verify backend certificate SAN.
- Confirm service endpoints and targetPort.
- Test backend from debug pod.

### Scenario 4: API Server Named Certificate Not Used

Likely cause:

- Client connects using hostname not listed in `names`.
- SNI mismatch.
- DNS/load balancer points elsewhere.
- Patch not applied or operator rollout incomplete.

Diagnostics:

```bash
oc get apiserver cluster -o yaml
oc get secret -n openshift-config api-custom-cert -o yaml
openssl s_client -connect api.ocp4.example.com:6443 -servername api.ocp4.example.com
```

Fix:

- Add correct FQDN to `namedCertificates.names`.
- Reissue cert with correct SAN.
- Wait for kube-apiserver operator availability.

### Scenario 5: `oc logs` / `oc exec` Fails on One Node

Likely cause:

- Kubelet serving certificate CSR pending or invalid.
- Node certificate hostname mismatch.

Diagnostics:

```bash
oc get csr
oc describe node <node>
oc debug node/<node>
chroot /host
journalctl -u kubelet -b --no-pager | tail -200
```

Fix:

- Validate and approve legitimate kubelet serving CSR.
- Check node hostname and DNS.

### Scenario 6: Webhook Blocks All Deployments with x509 Error

Likely cause:

- Webhook serving cert expired.
- `caBundle` does not match webhook serving CA.
- service-ca injection missing or overwritten.

Diagnostics:

```bash
oc get validatingwebhookconfiguration <name> -o yaml
oc get mutatingwebhookconfiguration <name> -o yaml
oc get apiservice
oc get secret -n <webhook-ns>
```

Fix:

- Recreate serving certificate.
- Reinject service CA bundle.
- Restart webhook deployment.
- Temporarily patch failure policy only if needed and approved.

### Scenario 7: Pulling from Private Registry Fails with x509 Error

Likely cause:

- Registry CA not trusted by nodes/CRI-O.
- CA bundle not added to cluster trust.
- Image registry trust configured incorrectly.

Diagnostics:

```bash
oc describe pod <pod>
oc get events -n <ns>
oc get proxy/cluster -o yaml
oc get mcp
```

Fix:

- Add registry CA to trusted bundle.
- Use image registry additional trust config if required.
- Wait for MCO to apply and CRI-O restart.

### Scenario 8: Service CA ConfigMap Data Disappeared

Likely cause:

- ConfigMap annotated with `service.beta.openshift.io/inject-cabundle=true`.
- service-ca Operator overwrote data.

Fix:

- Use a dedicated config map only for service CA injection.
- Store application config separately.

## 16. Production Best Practices

### 16.1 Certificate Inventory

Maintain a certificate inventory with:

- Certificate purpose.
- Namespace and secret/config map name.
- Owning team.
- Issuing CA.
- Expiration date.
- Renewal method.
- Rotation test date.
- Rollback plan.

Example:

| Certificate | Secret/Object | Namespace | Owner | Expiry | Renewal |
|---|---|---|---|---|---|
| Default apps wildcard | `apps-wildcard-cert` | `openshift-ingress` | Platform | 2027-05-10 | cert-manager / PKI |
| API named cert | `api-custom-cert` | `openshift-config` | Platform | 2027-05-10 | PKI + secret replace |
| Internal service cert | `backend-tls` | `payments` | App team | auto | service-ca |

### 16.2 Never Use Insecure Flags Permanently

Avoid making this normal:

```bash
oc login --insecure-skip-tls-verify=true
curl -k https://...
```

Use those only for emergency diagnosis. Permanent insecure TLS hides real security and configuration problems.

### 16.3 Keep Secret Names Stable During Renewal

For API named cert and default ingress cert, prefer replacing secret content while keeping the same secret name. This reduces unnecessary configuration changes and allows hot-reload behavior where supported.

### 16.4 Separate Identity and Trust Tasks

Do not confuse:

- Installing a certificate that a server presents.
- Installing a CA that clients trust.

Example: replacing default ingress certificate does not automatically make every internal component trust a new private CA. Add the CA bundle through supported trust mechanisms.

### 16.5 Validate Before Applying

Before applying certs:

```bash
openssl x509 -in tls.crt -noout -subject -issuer -dates
openssl x509 -in tls.crt -noout -text | grep -A2 "Subject Alternative Name"
openssl verify -CAfile ca-bundle.crt tls.crt
```

Check key match:

```bash
openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

### 16.6 Use Maintenance Windows for Risky Rotations

High-risk operations:

- Manual service CA rotation.
- etcd signer rotation.
- API certificate structure changes.
- Cluster-wide proxy/noProxy changes.
- MachineConfig trust changes across all workers.

Plan:

- Backup current objects.
- Validate new certificates.
- Apply in low-traffic window.
- Watch cluster operators.
- Test critical flows.
- Keep rollback artifacts ready.

### 16.7 Protect Private Keys

Private keys should be handled like passwords:

- Store in secure secrets manager or PKI workflow.
- Restrict access to admin hosts.
- Avoid committing to Git.
- Avoid pasting into tickets/chat.
- Use sealed secrets/external secrets if GitOps is required.
- Rotate immediately if leaked.

### 16.8 Prefer Automation

Use automation for:

- Expiration scanning.
- cert-manager certificate renewal.
- Alerting at 30/60/90 days.
- GitOps-managed certificate references.
- Policy checks for SAN/issuer/key length.

## 17. Real-World Operational Runbooks

### Runbook A: Replace Default Ingress Wildcard Certificate

1. Confirm target apps domain:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o jsonpath='{.status.domain}{"\n"}'
```

2. Validate certificate SAN:

```bash
openssl x509 -in apps-chain.crt -noout -text | grep -A2 "Subject Alternative Name"
```

3. Validate key match:

```bash
openssl x509 -noout -modulus -in apps-chain.crt | openssl md5
openssl rsa  -noout -modulus -in apps.key | openssl md5
```

4. Backup current IngressController:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml > ingresscontroller-default-backup.yaml
```

5. Create/update secret:

```bash
oc create secret tls apps-wildcard-cert \
  --cert=apps-chain.crt \
  --key=apps.key \
  -n openshift-ingress \
  --dry-run=client -o yaml | oc apply -f -
```

6. Patch IngressController:

```bash
oc patch ingresscontroller.operator default \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"apps-wildcard-cert"}}}' \
  -n openshift-ingress-operator
```

7. Validate:

```bash
oc get co ingress
curl -Iv https://console-openshift-console.apps.ocp4.example.com
openssl s_client -connect console-openshift-console.apps.ocp4.example.com:443 \
  -servername console-openshift-console.apps.ocp4.example.com </dev/null
```

8. Rollback if needed:

```bash
oc apply -f ingresscontroller-default-backup.yaml
```

### Runbook B: Add API Server Named Certificate

1. Validate cert:

```bash
openssl x509 -in api-chain.crt -noout -subject -issuer -dates
openssl x509 -in api-chain.crt -noout -text | grep -A2 "Subject Alternative Name"
```

2. Backup API server config:

```bash
oc get apiserver cluster -o yaml > apiserver-cluster-backup.yaml
```

3. Create secret:

```bash
oc create secret tls api-custom-cert \
  --cert=api-chain.crt \
  --key=api.key \
  -n openshift-config
```

4. Patch API server:

```bash
oc patch apiserver cluster --type=merge -p '
{"spec":{"servingCerts":{"namedCertificates":[{"names":["api.ocp4.example.com"],"servingCertificate":{"name":"api-custom-cert"}}]}}}'
```

5. Watch:

```bash
watch 'oc get co kube-apiserver'
```

6. Validate:

```bash
curl -v https://api.ocp4.example.com:6443/version
```

### Runbook C: Renew Existing API Named Certificate

1. Validate new cert/key.
2. Replace secret content under same name:

```bash
oc create secret tls api-custom-cert \
  --cert=new-api-chain.crt \
  --key=new-api.key \
  -n openshift-config \
  --dry-run=client -o yaml | oc replace -f -
```

3. Confirm operator does not start unexpected rollout:

```bash
oc get co kube-apiserver
```

4. Validate remote certificate:

```bash
openssl s_client -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

### Runbook D: Create Internal TLS for a Service

1. Annotate service:

```bash
oc annotate service backend \
  service.beta.openshift.io/serving-cert-secret-name=backend-tls \
  -n app-prod
```

2. Verify secret:

```bash
oc get secret backend-tls -n app-prod
```

3. Mount secret into backend deployment.
4. Inject service CA into config map:

```bash
oc create configmap service-ca-bundle -n app-prod
oc annotate configmap service-ca-bundle \
  service.beta.openshift.io/inject-cabundle=true \
  -n app-prod
```

5. Mount CA bundle into client deployment.
6. Test from client pod:

```bash
curl --cacert /path/service-ca.crt https://backend.app-prod.svc:8443/healthz
```

### Runbook E: Troubleshoot x509 on Re-encrypt Route

1. Check route:

```bash
oc get route backend -n app-prod -o yaml
```

2. Check backend service endpoints:

```bash
oc get svc,endpoints -n app-prod
```

3. Check router logs:

```bash
oc logs -n openshift-ingress deploy/router-default --tail=200
```

4. Verify backend cert:

```bash
oc rsh -n app-prod deploy/backend
openssl s_client -connect localhost:8443 -showcerts </dev/null
```

5. Ensure route `destinationCACertificate` trusts backend certificate issuer.

## 18. Interview and Exam-Focused Notes

### 18.1 Must-Know Concepts

- API certificate and ingress wildcard certificate are different.
- API custom named certificate secret goes in `openshift-config`.
- Default ingress certificate secret goes in `openshift-ingress`.
- IngressController object lives in `openshift-ingress-operator`.
- Service serving certs are created by annotating a Service.
- Service CA bundle injection uses `service.beta.openshift.io/inject-cabundle=true`.
- Re-encrypt route requires router to trust backend cert using destination CA.
- Passthrough route does not store cert/key on route.
- Edge route terminates TLS at router and sends plain traffic to backend.
- Do not configure named API certificate for `api-int`.
- CN alone is not enough; SAN is required.
- Private keys must be unencrypted for OpenShift TLS secrets.
- System-managed certs should not be manually replaced casually.
- CSRs affect node onboarding and kubelet serving operations.

### 18.2 Common Exam-Style Tasks

#### Task: Create secure edge route with provided cert

```bash
oc create route edge myapp \
  --service=myapp \
  --hostname=myapp.apps.ocp4.example.com \
  --cert=tls.crt \
  --key=tls.key
```

#### Task: Create re-encrypt route with destination CA

```bash
oc create route reencrypt myapp \
  --service=myapp \
  --hostname=myapp.apps.ocp4.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --dest-ca-cert=destca.crt
```

#### Task: Generate self-signed test certificate

```bash
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout tls.key \
  -out tls.crt \
  -days 365 \
  -subj "/CN=myapp.apps.ocp4.example.com" \
  -addext "subjectAltName=DNS:myapp.apps.ocp4.example.com"
```

#### Task: Create TLS secret

```bash
oc create secret tls myapp-tls \
  --cert=tls.crt \
  --key=tls.key \
  -n myproject
```

#### Task: Check route certificate

```bash
openssl s_client -connect myapp.apps.ocp4.example.com:443 \
  -servername myapp.apps.ocp4.example.com </dev/null
```

#### Task: Approve pending CSR

```bash
oc get csr
oc adm certificate approve <csr-name>
```

### 18.3 Tricky Points

- If `curl -k` works but normal `curl` fails, the application is reachable but trust is broken.
- If `nc -zv host 443` works but `curl` fails, TCP is reachable but TLS/application layer might be broken.
- If route returns 503, check service endpoints before blaming certificates.
- If re-encrypt route fails, check `dest-ca-cert`.
- If API named certificate patch causes degradation, verify you did not touch `api-int`.
- If pod cannot start after mounting injected service CA ConfigMap, the key might not exist yet unless optional mount is used.

## Final Senior-Admin Summary

TLS certificates in OpenShift are a platform-wide trust system, not isolated files. A strong administrator understands which certificate is presented, who trusts it, which Operator owns it, and how rotation happens.

The most important practical split is this:

- **API certificate:** secures `api.<cluster>.<domain>:6443`; custom named certificate lives in `openshift-config` and is referenced by `apiserver/cluster`.
- **Default ingress certificate:** secures `*.apps.<cluster>.<domain>` routes; custom wildcard secret lives in `openshift-ingress` and is referenced by the `IngressController` in `openshift-ingress-operator`.
- **Route certificate:** secures one route; can be edge, passthrough, or re-encrypt.
- **Service serving certificate:** secures internal service DNS; generated by service-ca from service annotation.
- **Trust bundle:** makes OpenShift components trust external or corporate CAs; managed through `proxy/cluster` and ConfigMaps.
- **Node/control plane/etcd certificates:** usually system-managed; intervene only with supported procedures.

In production, the best certificate strategy is boring: inventory every user-managed certificate, automate renewal, validate chain/SAN/key before applying, keep secret names stable, monitor expiration, and never normalize insecure TLS bypasses.
