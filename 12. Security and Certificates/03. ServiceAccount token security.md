## 1. Executive Summary

A **ServiceAccount token** is a bearer credential that allows a pod, job, controller, operator, CI/CD tool, or external automation to authenticate to the OpenShift/Kubernetes API as a non-human identity.

From a security point of view, a ServiceAccount token must be treated like a password, SSH private key, or API key:

- Whoever has the token can authenticate as that ServiceAccount.
- The token is not tied to a human login session.
- Its effective power is controlled mainly by RBAC bindings and admission controls.
- If the ServiceAccount has excessive permissions, token theft becomes privilege escalation.
- If the token is mounted unnecessarily into pods, any application vulnerability can become API access.

Modern Kubernetes/OpenShift moved from old **Secret-based long-lived tokens** to **TokenRequest-based projected tokens**. Projected tokens are safer because they can be time-bound, audience-bound, mounted by kubelet, and rotated automatically.

For OpenShift administrators, the main objective is simple:

> Give every workload only the ServiceAccount token it actually needs, only for the audience it needs, only for the lifetime it needs, and only with the RBAC permissions it needs.

## 2. Why ServiceAccount Token Security Matters

In a production OpenShift cluster, ServiceAccount tokens are used by:

- Application pods calling the Kubernetes API.
- Operators reconciling custom resources.
- Build pods pushing images.
- Deployment controllers managing rollout objects.
- Monitoring tools scraping cluster state.
- GitOps tools such as Argo CD or Tekton tasks.
- External automation scripts.
- Backup, security, and inventory agents.

A compromised ServiceAccount token can allow an attacker to:

- List pods, services, routes, config maps, and secrets.
- Create privileged pods if RBAC and SCC permissions allow it.
- Modify deployments or inject malicious containers.
- Read application credentials from Secrets.
- Create additional tokens for other ServiceAccounts if `serviceaccounts/token` is allowed.
- Pivot across namespaces if broad ClusterRoleBindings exist.
- Damage availability by deleting pods, deployments, PVCs, routes, or config.

The risk depends on three things:

1. **Token exposure** — is the token mounted or stored somewhere unsafe?
2. **Token lifetime** — is it short-lived or long-lived?
3. **Authorization scope** — what can the token do after authentication?

## 3. ServiceAccount Identity Model

A ServiceAccount is a namespaced Kubernetes identity.

Example:

```text
Namespace: payments
ServiceAccount: invoice-reader
Authenticated username:
  system:serviceaccount:payments:invoice-reader
```

Every ServiceAccount is automatically a member of these groups:

```text
system:serviceaccounts
system:serviceaccounts:<namespace>
```

For the example above:

```text
system:serviceaccounts
system:serviceaccounts:payments
```

This matters because RBAC can bind permissions to:

- A single ServiceAccount.
- All ServiceAccounts in a namespace.
- All ServiceAccounts cluster-wide.

### Single ServiceAccount binding

```bash
oc adm policy add-role-to-user view \
  system:serviceaccount:payments:invoice-reader \
  -n payments
```

### Namespace ServiceAccount group binding

```bash
oc adm policy add-role-to-group view \
  system:serviceaccounts:payments \
  -n payments
```

This grants the role to **all ServiceAccounts in the payments namespace**. Use this carefully.

### Cluster-wide ServiceAccount group binding

```bash
oc adm policy add-cluster-role-to-group view system:serviceaccounts
```

This is usually dangerous because it grants permissions to every ServiceAccount in every namespace.

## 4. Token Authentication Flow

When a pod uses a ServiceAccount token to call the API server, the flow is:

1. Pod reads token from the mounted service account token path.
2. Application sends the token as a bearer token:

```http
Authorization: Bearer <token>
```

3. Kubernetes API server validates the token signature, issuer, audience, and expiry.
4. The request is authenticated as:

```text
system:serviceaccount:<namespace>:<serviceaccount>
```

5. RBAC authorizer checks whether that identity can perform the requested verb on the requested resource.
6. Admission controllers, SCC / Pod Security Admission, validating webhooks, and OpenShift-specific policies may further allow or deny the request.

Authentication answers:

> Who are you?

Authorization answers:

> What are you allowed to do?

A valid token with no RBAC permissions is authenticated but mostly useless. A valid token with `cluster-admin` is extremely powerful.

## 5. ServiceAccount Tokens and Certificates

ServiceAccount token security is closely related to certificate and signing trust.

A modern ServiceAccount token is a signed JWT. It normally contains claims such as:

```json
{
  "iss": "https://kubernetes.default.svc",
  "sub": "system:serviceaccount:payments:invoice-reader",
  "aud": ["https://kubernetes.default.svc"],
  "exp": 1760000000,
  "iat": 1759996400,
  "kubernetes.io": {
    "namespace": "payments",
    "serviceaccount": {
      "name": "invoice-reader",
      "uid": "..."
    },
    "pod": {
      "name": "invoice-api-abc123",
      "uid": "..."
    }
  }
}
```

Important certificate/security pieces:

| Component | Purpose |
|---|---|
| ServiceAccount signing key | Signs ServiceAccount JWTs. |
| API server verification key | Verifies token signatures during authentication. |
| `iss` claim | Identifies the issuer of the token. |
| `aud` claim | Identifies the intended recipient / audience. |
| `exp` claim | Controls token expiry. |
| `ca.crt` mounted in pod | Allows in-cluster clients to verify API server TLS. |
| `namespace` file mounted in pod | Allows clients to discover current namespace. |

Inside a pod, the standard mounted files are normally under:

```text
/var/run/secrets/kubernetes.io/serviceaccount/token
/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
/var/run/secrets/kubernetes.io/serviceaccount/namespace
```

In modern Kubernetes/OpenShift, the pod often has a projected volume named similar to:

```text
kube-api-access-xxxxx
```

That projected volume combines:

- ServiceAccount token.
- Kubernetes root CA bundle.
- Downward API namespace file.

### Why audience matters

A token with audience `https://kubernetes.default.svc` should be accepted by the Kubernetes API server, but an external system such as Vault, cloud IAM, or custom identity broker should require its own audience, for example:

```yaml
audience: vault
```

If an external service accepts a Kubernetes API audience token without audience validation, a stolen in-cluster API token may be reusable against that external service. That is poor relying-party validation.

### Why issuer matters

The issuer tells external systems where the token came from. In OpenShift, `spec.serviceAccountIssuer` can be configured in the cluster `Authentication` object when a custom issuer is required for external validation.

Example:

```bash
oc edit authentications cluster
```

```yaml
spec:
  serviceAccountIssuer: https://issuer.example.com
```

Do not change this casually. Changing the issuer affects how relying parties validate bound tokens. Plan it as a cluster security change, not as an application tweak.

## 6. OpenShift Default ServiceAccounts

OpenShift creates default ServiceAccounts in projects and for platform components.

Common project ServiceAccounts:

| ServiceAccount | Purpose |
|---|---|
| `default` | Used by pods that do not explicitly set `serviceAccountName`. |
| `builder` | Used by build pods when Build capability is enabled. |
| `deployer` | Used by deployment pods when DeploymentConfig capability is enabled. |

Security point:

> Never allow business workloads to run with the default ServiceAccount unless that is an intentional decision.

A better pattern is:

```bash
oc create sa invoice-api -n payments
```

Then set it explicitly in the Deployment:

```yaml
spec:
  template:
    spec:
      serviceAccountName: invoice-api
```

This makes RBAC review, auditing, and incident response much easier.

## 7. Modern Bound ServiceAccount Tokens

A **bound ServiceAccount token** is safer than a legacy Secret token because it can be:

- **Time-bound** — expires after a defined duration.
- **Audience-bound** — valid only for a specific recipient.
- **Object-bound** — associated with a pod or other object.
- **Projected** — mounted through a projected volume instead of stored as a normal Secret.
- **Rotated** — kubelet refreshes it as it approaches expiration.

### Example: projected token for a pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: vault-client
  namespace: payments
spec:
  serviceAccountName: invoice-api
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: registry.access.redhat.com/ubi9/ubi-minimal
      command: ["sleep", "3600"]
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: vault-token
          mountPath: /var/run/secrets/tokens
          readOnly: true
  volumes:
    - name: vault-token
      projected:
        sources:
          - serviceAccountToken:
              path: vault-token
              audience: vault
              expirationSeconds: 3600
```

Notice two important design choices:

1. `automountServiceAccountToken: false` disables the default Kubernetes API token mount.
2. A custom projected token is mounted only for the `vault` audience.

This prevents the application from automatically receiving a generic API token if it only needs a token for Vault or another external service.

### Token rotation behavior

Applications must not read the token once at startup and keep it forever in memory. They should reload the token file because kubelet can rotate projected tokens.

Bad pattern:

```text
Application reads token during startup and stores it forever.
```

Good pattern:

```text
Application reads token before each authentication exchange or watches the token file for rotation.
```

## 8. Legacy Long-Lived ServiceAccount Token Secrets

Older Kubernetes/OpenShift versions created long-lived token Secrets automatically for ServiceAccounts.

Legacy token Secret type:

```yaml
type: kubernetes.io/service-account-token
```

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: legacy-token
  namespace: payments
  annotations:
    kubernetes.io/service-account.name: invoice-api
type: kubernetes.io/service-account-token
```

Security problems with long-lived token Secrets:

- They are stored as API objects.
- They can be read by users or workloads with `get secrets` permission.
- They are often copied into CI/CD systems and forgotten.
- They may not expire.
- They survive pod restarts.
- They are difficult to inventory after years of cluster upgrades.

### OpenShift 4.16+ behavior

Starting with OpenShift 4.16, long-lived ServiceAccount API token Secrets are no longer automatically created for each ServiceAccount. However, clusters upgraded from older releases can still contain old long-lived token Secrets, and those existing tokens may continue to function.

This means a production audit must check both:

1. Current ServiceAccount token projection behavior.
2. Old token Secrets left behind from upgrades.

### Find legacy ServiceAccount token Secrets

```bash
oc get secrets -A \
  --field-selector type=kubernetes.io/service-account-token
```

Show details:

```bash
oc get secret -n <namespace> <secret-name> -o yaml
```

Check whether it is tied to a ServiceAccount:

```bash
oc get secret -n <namespace> <secret-name> \
  -o jsonpath='{.metadata.annotations.kubernetes\.io/service-account\.name}{"\n"}'
```

### Remove unused legacy token Secrets

```bash
oc delete secret -n <namespace> <secret-name>
```

Before deleting, confirm:

- It is not used by an external integration.
- No automation depends on it.
- A replacement short-lived token or OIDC/IAM integration exists.
- You have a rollback plan for production systems.

## 9. Token Mounting Behavior

When a pod is created, the ServiceAccount admission controller normally:

1. Sets `.spec.serviceAccountName: default` if no ServiceAccount is specified.
2. Verifies that the ServiceAccount exists.
3. Mounts a projected token volume unless automount is disabled.
4. Adds image pull secrets from the ServiceAccount if the pod does not already define them.

Check pod ServiceAccount:

```bash
oc get pod <pod> -n <namespace> \
  -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

Check mounted token volume:

```bash
oc get pod <pod> -n <namespace> -o yaml | grep -A20 kube-api-access
```

From inside the pod:

```bash
oc rsh -n <namespace> <pod>
ls -l /var/run/secrets/kubernetes.io/serviceaccount/
cat /var/run/secrets/kubernetes.io/serviceaccount/namespace
```

Check whether a token exists:

```bash
test -f /var/run/secrets/kubernetes.io/serviceaccount/token && echo "token mounted" || echo "no token"
```

## 10. Disable Unnecessary Token Automounting

Many application pods do not need Kubernetes API access. For those pods, disable token automounting.

### Disable at ServiceAccount level

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web-frontend
  namespace: payments
automountServiceAccountToken: false
```

Apply:

```bash
oc apply -f sa-web-frontend.yaml
```

### Disable at pod level

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-frontend
  namespace: payments
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-frontend
  template:
    metadata:
      labels:
        app: web-frontend
    spec:
      serviceAccountName: web-frontend
      automountServiceAccountToken: false
      containers:
        - name: web
          image: registry.access.redhat.com/ubi9/httpd-24
```

Pod-level setting overrides ServiceAccount-level behavior.

### Verify token is not mounted

```bash
oc exec -n payments deploy/web-frontend -- \
  sh -c 'ls -l /var/run/secrets/kubernetes.io/serviceaccount/ || true'
```

Expected result:

```text
No such file or directory
```

or no token file present.

### Production recommendation

Use this default posture:

| Workload type | Token automount |
|---|---|
| Static web application | Disabled |
| API app with no Kubernetes API calls | Disabled |
| App calling Kubernetes API | Enabled only on dedicated ServiceAccount |
| Operator/controller | Enabled with least privilege |
| External identity exchange | Use projected audience-bound token |
| CI/CD automation | Prefer short-lived `oc create token`; avoid stored Secrets |

## 11. RBAC Hardening for ServiceAccounts

A ServiceAccount token is only as dangerous as the RBAC attached to it.

### Check what a ServiceAccount can do

```bash
oc auth can-i --list \
  --as=system:serviceaccount:payments:invoice-api \
  -n payments
```

Check a specific action:

```bash
oc auth can-i get secrets \
  --as=system:serviceaccount:payments:invoice-api \
  -n payments
```

```bash
oc auth can-i create pods \
  --as=system:serviceaccount:payments:invoice-api \
  -n payments
```

```bash
oc auth can-i create serviceaccounts/token \
  --as=system:serviceaccount:payments:invoice-api \
  -n payments
```

### Good Role example: read only ConfigMaps

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: config-reader
  namespace: payments
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]
```

Bind it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: invoice-api-config-reader
  namespace: payments
subjects:
  - kind: ServiceAccount
    name: invoice-api
    namespace: payments
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: config-reader
```

Apply:

```bash
oc apply -f role-config-reader.yaml
oc apply -f rb-invoice-api-config-reader.yaml
```

### Avoid broad roles

Avoid binding these unless truly required:

```text
cluster-admin
admin
edit
self-provisioner
system:masters
```

The `edit` role can be more dangerous than many admins expect because the ability to modify workload objects can often be used to mount secrets, run new containers, or change application behavior.

### Prefer namespace RoleBinding over ClusterRoleBinding

Better:

```bash
oc adm policy add-role-to-user view \
  system:serviceaccount:payments:invoice-api \
  -n payments
```

Riskier:

```bash
oc adm policy add-cluster-role-to-user view \
  system:serviceaccount:payments:invoice-api
```

The second command grants cluster-wide visibility.

## 12. Dangerous Permissions Related to Tokens

The following permissions are high-risk for ServiceAccounts and users.

### `get/list/watch secrets`

If a subject can read Secrets, it may read credentials, TLS keys, pull secrets, legacy ServiceAccount tokens, database passwords, and application tokens.

Check:

```bash
oc auth can-i get secrets \
  --as=system:serviceaccount:<ns>:<sa> \
  -n <ns>
```

### `create serviceaccounts/token`

This allows creation of tokens for existing ServiceAccounts through the TokenRequest API.

Check:

```bash
oc auth can-i create serviceaccounts/token \
  --as=<user-or-sa> \
  -n <namespace>
```

This permission should be granted only to trusted automation or controllers that genuinely need it.

### `impersonate users/groups/serviceaccounts`

Impersonation can become direct privilege escalation.

Check:

```bash
oc auth can-i impersonate serviceaccounts \
  --as=<user-or-sa>
```

### `create pods` with permissive SCC

If a ServiceAccount can create pods and use a privileged SCC, it may be able to access host resources.

Check SCC usage:

```bash
oc adm policy who-can use scc privileged
oc adm policy who-can use scc anyuid
```

### `bind` and `escalate` RBAC verbs

These verbs allow subjects to bind or escalate privileges beyond what they currently hold.

Check:

```bash
oc auth can-i bind clusterroles \
  --as=<user-or-sa>

oc auth can-i escalate clusterroles \
  --as=<user-or-sa>
```

## 13. Image Pull Secrets vs API Tokens

OpenShift uses ServiceAccounts for both:

1. API authentication.
2. Image pull secret association.

Do not confuse them.

| Item | Purpose | Consumed by |
|---|---|---|
| ServiceAccount API token | Authenticates to Kubernetes/OpenShift API | Application process / client library |
| Image pull secret | Authenticates to image registry | Kubelet / CRI-O |
| `ca.crt` | Verifies API server TLS | Application process / client library |

Check ServiceAccount image pull secrets:

```bash
oc describe sa <sa-name> -n <namespace>
```

Add a pull secret to a ServiceAccount:

```bash
oc secrets link <sa-name> <pull-secret-name> \
  --for=pull \
  -n <namespace>
```

Security note:

> Image pull secrets are still sensitive, but they are not the same as ServiceAccount API tokens. A compromised pull secret usually gives registry access; a compromised API token gives Kubernetes API access according to RBAC.

## 14. External Integrations and `oc create token`

Use `oc create token` to create a short-lived token for a ServiceAccount.

```bash
oc create sa monitoring-bot -n observability
```

Create a token:

```bash
oc create token monitoring-bot -n observability
```

With duration:

```bash
oc create token monitoring-bot \
  -n observability \
  --duration=1h
```

Use in an external script:

```bash
TOKEN=$(oc create token monitoring-bot -n observability --duration=1h)
API=https://api.ocp4.example.com:6443

curl -k \
  -H "Authorization: Bearer ${TOKEN}" \
  ${API}/api/v1/namespaces/observability/pods
```

Better with CA verification:

```bash
curl --cacert kube-apiserver-ca.crt \
  -H "Authorization: Bearer ${TOKEN}" \
  https://api.ocp4.example.com:6443/api
```

Do not store this token permanently in Git, Jenkins credentials, shell history, Ansible inventory, ticket comments, or chat messages.

### Safer external automation pattern

1. Create a dedicated ServiceAccount.
2. Bind minimal RBAC.
3. Generate short-lived token during job execution.
4. Avoid storing token at rest.
5. Rotate or recreate automation identity if compromised.
6. Monitor audit logs for that ServiceAccount identity.

## 15. Projected Token for External Systems

For external systems such as Vault, cloud IAM, or a custom identity broker, use an audience-specific projected token.

Example deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vault-client
  namespace: payments
spec:
  replicas: 1
  selector:
    matchLabels:
      app: vault-client
  template:
    metadata:
      labels:
        app: vault-client
    spec:
      serviceAccountName: vault-client
      automountServiceAccountToken: false
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi-minimal
          command: ["sleep", "3600"]
          volumeMounts:
            - name: vault-token
              mountPath: /var/run/secrets/tokens
              readOnly: true
      volumes:
        - name: vault-token
          projected:
            sources:
              - serviceAccountToken:
                  path: vault-token
                  audience: vault
                  expirationSeconds: 3600
```

Inside the pod:

```bash
cat /var/run/secrets/tokens/vault-token
```

The external service must verify:

- JWT signature.
- `iss` claim.
- `aud` claim.
- `exp` claim.
- ServiceAccount subject.
- Namespace and ServiceAccount mapping to an allowed role.

Do not let external systems accept any token from any ServiceAccount. Map exact ServiceAccount identities to exact external roles.

Example mapping concept:

```text
system:serviceaccount:payments:vault-client
  -> vault role: payments-readonly
```

Do not use:

```text
system:serviceaccounts
  -> vault role: admin
```

## 16. TokenReview and Token Validation

The Kubernetes `TokenReview` API lets a trusted caller ask the API server whether a token is valid and who it authenticates as.

Example:

```bash
TOKEN=$(oc create token invoice-api -n payments --duration=10m)

cat <<EOF | oc create -f -
apiVersion: authentication.k8s.io/v1
kind: TokenReview
spec:
  token: "${TOKEN}"
EOF
```

Example response shape:

```yaml
apiVersion: authentication.k8s.io/v1
kind: TokenReview
status:
  authenticated: true
  user:
    username: system:serviceaccount:payments:invoice-api
    groups:
      - system:serviceaccounts
      - system:serviceaccounts:payments
```

Security note:

> TokenReview access should not be granted broadly. It allows validation of bearer credentials and may support external authentication flows.

## 17. Audit and Detection

### Find pods running with default ServiceAccount

```bash
oc get pods -A \
  -o jsonpath='{range .items[?(@.spec.serviceAccountName=="default")]}{.metadata.namespace}{"\t"}{.metadata.name}{"\n"}{end}'
```

### Find pods with automount not explicitly disabled

```bash
oc get pods -A -o json | jq -r '
  .items[] |
  select(.spec.automountServiceAccountToken != false) |
  [.metadata.namespace, .metadata.name, (.spec.serviceAccountName // "default")] |
  @tsv
'
```

### Find ServiceAccounts with automount disabled

```bash
oc get sa -A -o json | jq -r '
  .items[] |
  select(.automountServiceAccountToken == false) |
  [.metadata.namespace, .metadata.name] |
  @tsv
'
```

### Find legacy ServiceAccount token Secrets

```bash
oc get secrets -A \
  --field-selector type=kubernetes.io/service-account-token
```

### Find who can read Secrets in a namespace

```bash
oc adm policy who-can get secrets -n payments
```

### Find who can create ServiceAccount tokens

```bash
oc adm policy who-can create serviceaccounts/token -n payments
```

### Find ClusterRoleBindings for ServiceAccounts

```bash
oc get clusterrolebinding -o json | jq -r '
  .items[] as $crb |
  ($crb.subjects // [])[]? |
  select(.kind=="ServiceAccount") |
  [$crb.metadata.name, .namespace, .name, $crb.roleRef.kind, $crb.roleRef.name] |
  @tsv
'
```

### Find RoleBindings for ServiceAccounts

```bash
oc get rolebinding -A -o json | jq -r '
  .items[] as $rb |
  ($rb.subjects // [])[]? |
  select(.kind=="ServiceAccount") |
  [$rb.metadata.namespace, $rb.metadata.name, .namespace, .name, $rb.roleRef.kind, $rb.roleRef.name] |
  @tsv
'
```

### Audit log identities

In OpenShift audit logs, ServiceAccount activity appears as:

```text
system:serviceaccount:<namespace>:<serviceaccount>
```

Useful search patterns:

```bash
system:serviceaccount:payments:invoice-api
serviceaccounts/token
secrets
create pods
patch deployments
```

Look especially for:

- ServiceAccount creating unexpected pods.
- ServiceAccount reading Secrets.
- ServiceAccount creating tokens.
- ServiceAccount modifying RBAC.
- ServiceAccount making API calls from unusual source IPs.
- Default ServiceAccount performing non-trivial API actions.

## 18. Incident Response: Suspected Token Leak

If a ServiceAccount token is leaked, handle it like a credential compromise.

### Step 1: Identify the ServiceAccount

Decode token payload without verifying signature:

```bash
TOKEN='<paste-token-here>'
python3 - <<'PY'
import os, json, base64
jwt=os.environ.get('TOKEN','')
parts=jwt.split('.')
if len(parts) < 2:
    raise SystemExit('Not a JWT')
payload=parts[1] + '=' * (-len(parts[1]) % 4)
print(json.dumps(json.loads(base64.urlsafe_b64decode(payload)), indent=2))
PY
```

Run with environment variable:

```bash
TOKEN="$TOKEN" python3 decode-jwt.py
```

Look for:

```text
sub: system:serviceaccount:<namespace>:<serviceaccount>
aud
exp
kubernetes.io.namespace
kubernetes.io.serviceaccount.name
```

### Step 2: Check permissions

```bash
oc auth can-i --list \
  --as=system:serviceaccount:<namespace>:<serviceaccount> \
  -n <namespace>
```

Check cluster-wide exposure:

```bash
oc auth can-i --list \
  --as=system:serviceaccount:<namespace>:<serviceaccount> \
  -A
```

### Step 3: Determine token type

Projected pod-bound token:

- Delete the pod to invalidate pod-bound token.
- Restart Deployment/StatefulSet/DaemonSet workload.

```bash
oc delete pod <pod> -n <namespace>
```

Long-lived Secret token:

- Delete the Secret.
- Replace dependent automation with short-lived token flow.

```bash
oc delete secret <secret-name> -n <namespace>
```

Unknown token:

- Assume compromise until proven otherwise.
- Rotate the ServiceAccount usage path.
- Review audit logs.

### Step 4: Remove unnecessary RBAC

```bash
oc get rolebinding,clusterrolebinding -A -o yaml | grep -B5 -A10 '<serviceaccount-name>'
```

Then delete or patch excessive bindings.

### Step 5: Review audit logs

Search for:

```text
system:serviceaccount:<namespace>:<serviceaccount>
```

Focus on actions after suspected leak time.

### Step 6: Recreate workload with hardened settings

- Dedicated ServiceAccount.
- Minimal Role.
- `automountServiceAccountToken: false` unless required.
- Projected token with custom audience if external identity is needed.
- No broad Secret access.
- No privileged SCC unless absolutely required.


### Common error: `Forbidden`

Example:

```text
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:payments:invoice-api" cannot list resource "pods" in API group "" in the namespace "payments"
```

Meaning:

- Token is valid.
- Authentication worked.
- RBAC denied the action.

Fix:

```bash
oc adm policy add-role-to-user view \
  system:serviceaccount:payments:invoice-api \
  -n payments
```

Or create a narrower custom Role.

### Common error: `Unauthorized`

Meaning possibilities:

- Token expired.
- Token malformed.
- Token signed by unknown key.
- Wrong API server.
- Wrong issuer.
- Audience mismatch.

Check token expiry and audience.

### Common error: token file missing

Possible causes:

- `automountServiceAccountToken: false` set at pod level.
- `automountServiceAccountToken: false` set at ServiceAccount level.
- Custom volume path used.
- Container does not include shell tools to inspect path.

Check:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.automountServiceAccountToken}{"\n"}'
oc get sa <sa> -n <ns> -o jsonpath='{.automountServiceAccountToken}{"\n"}'
```

## 20. Production Hardening Checklist

### Workload identity

- [ ] Every workload has a dedicated ServiceAccount.
- [ ] No important workload runs with the `default` ServiceAccount.
- [ ] ServiceAccount names match workload purpose.
- [ ] ServiceAccounts are namespaced by application/team boundary.

### Token mounting

- [ ] `automountServiceAccountToken: false` is used for workloads that do not call the API.
- [ ] External identity integrations use projected audience-bound tokens.
- [ ] Applications reload projected tokens after rotation.
- [ ] Token files are mounted read-only.

### RBAC

- [ ] No application ServiceAccount has `cluster-admin`.
- [ ] Avoid broad `edit` unless required.
- [ ] Prefer custom Roles over built-in broad roles.
- [ ] Avoid ClusterRoleBinding when RoleBinding is enough.
- [ ] No broad binding to `system:serviceaccounts`.
- [ ] `get/list/watch secrets` is tightly controlled.
- [ ] `create serviceaccounts/token` is tightly controlled.
- [ ] `impersonate`, `bind`, and `escalate` are restricted.

### Legacy tokens

- [ ] Legacy `kubernetes.io/service-account-token` Secrets are inventoried.
- [ ] Unused long-lived tokens are deleted.
- [ ] External jobs use short-lived tokens or OIDC federation.
- [ ] Upgraded clusters are checked for old functional token Secrets.

### Certificates and trust

- [ ] API clients verify API server TLS using CA bundle.
- [ ] External systems validate token issuer and audience.
- [ ] Custom `serviceAccountIssuer` changes are planned and documented.
- [ ] Token validation relies on trusted issuer keys, not blind JWT decoding.

### Audit and monitoring

- [ ] Audit logs are searchable by ServiceAccount identity.
- [ ] Alert on ServiceAccounts reading Secrets unexpectedly.
- [ ] Alert on ServiceAccounts creating tokens unexpectedly.
- [ ] Alert on ServiceAccounts creating privileged pods.
- [ ] Review ClusterRoleBindings referencing ServiceAccounts.

## 21. Common Interview / Real-World Questions

### Q1. What is the difference between a user token and a ServiceAccount token?

A user token represents a human identity authenticated through OAuth/identity provider. A ServiceAccount token represents a workload identity such as a pod, operator, controller, or automation script. ServiceAccount tokens authenticate as `system:serviceaccount:<namespace>:<name>`.

### Q2. Why are legacy ServiceAccount token Secrets risky?

They can be long-lived, stored as Secret API objects, copied outside the cluster, and read by anyone with Secret read access. If the associated ServiceAccount has powerful RBAC, the token becomes a powerful reusable credential.

### Q3. What is a bound ServiceAccount token?

It is a ServiceAccount token with boundaries such as expiration, audience, and object binding. It is commonly delivered through a projected volume and rotated by kubelet.

### Q4. What is the benefit of `automountServiceAccountToken: false`?

It prevents Kubernetes from automatically injecting an API credential into a pod. This reduces blast radius if the application process is compromised.

### Q5. Does disabling token automount break image pulling?

No. API token automount and image pull secrets are separate concepts. Image pull secrets are used by kubelet to pull images. The ServiceAccount API token is used by the application process to authenticate to the Kubernetes API.

### Q6. How do you check what a ServiceAccount can do?

```bash
oc auth can-i --list \
  --as=system:serviceaccount:<namespace>:<serviceaccount> \
  -n <namespace>
```

### Q7. What permission allows a user to create ServiceAccount tokens?

The `create` verb on the `serviceaccounts/token` subresource.

### Q8. What is the difference between `Forbidden` and `Unauthorized`?

`Unauthorized` usually means authentication failed: invalid, expired, malformed, or unacceptable token. `Forbidden` means authentication succeeded, but authorization denied the action.

### Q9. Why is audience validation important?

Without audience validation, a token intended for the Kubernetes API might be accepted by another service. That allows token replay across systems.

### Q10. What is the safest way to give an external CI job OpenShift API access?

Use a dedicated ServiceAccount with minimal RBAC and generate a short-lived token at job runtime. Avoid storing long-lived token Secrets in CI credential stores unless there is no alternative and the risk is formally accepted.

## 22. Quick Lab

### Objective

Create a secure ServiceAccount pattern for an application that does **not** need Kubernetes API access, and a second application that needs read-only pod access.

### Part A: Application with no API access

```bash
oc new-project sa-token-lab
oc create sa no-api-app
```

Patch ServiceAccount:

```bash
oc patch sa no-api-app \
  -n sa-token-lab \
  -p '{"automountServiceAccountToken": false}'
```

Create deployment:

```bash
oc create deployment no-api-app \
  --image=registry.access.redhat.com/ubi9/ubi-minimal \
  -n sa-token-lab \
  -- sleep 3600

oc set serviceaccount deployment/no-api-app no-api-app -n sa-token-lab
```

Restart rollout:

```bash
oc rollout restart deployment/no-api-app -n sa-token-lab
oc rollout status deployment/no-api-app -n sa-token-lab
```

Verify no token:

```bash
POD=$(oc get pod -n sa-token-lab -l app=no-api-app -o jsonpath='{.items[0].metadata.name}')
oc exec -n sa-token-lab $POD -- \
  sh -c 'ls /var/run/secrets/kubernetes.io/serviceaccount/token 2>/dev/null || echo no-token-mounted'
```

Expected:

```text
no-token-mounted
```

### Part B: Application with read-only API access

```bash
oc create sa pod-reader -n sa-token-lab
```

Create Role:

```bash
cat <<EOF | oc apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: sa-token-lab
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
EOF
```

Create RoleBinding:

```bash
cat <<EOF | oc apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader
  namespace: sa-token-lab
subjects:
  - kind: ServiceAccount
    name: pod-reader
    namespace: sa-token-lab
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
EOF
```

Verify RBAC:

```bash
oc auth can-i list pods \
  --as=system:serviceaccount:sa-token-lab:pod-reader \
  -n sa-token-lab

oc auth can-i get secrets \
  --as=system:serviceaccount:sa-token-lab:pod-reader \
  -n sa-token-lab
```

Expected:

```text
yes
no
```

Create deployment:

```bash
oc create deployment pod-reader \
  --image=registry.access.redhat.com/ubi9/ubi-minimal \
  -n sa-token-lab \
  -- sleep 3600

oc set serviceaccount deployment/pod-reader pod-reader -n sa-token-lab
oc rollout restart deployment/pod-reader -n sa-token-lab
```

Test API call from inside pod:

```bash
POD=$(oc get pod -n sa-token-lab -l app=pod-reader -o jsonpath='{.items[0].metadata.name}')

oc exec -n sa-token-lab $POD -- sh -c '
TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
CA=/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
curl --cacert $CA \
  -H "Authorization: Bearer $TOKEN" \
  https://kubernetes.default.svc/api/v1/namespaces/sa-token-lab/pods
'
```

Cleanup:

```bash
oc delete project sa-token-lab
```

## Final Takeaway

ServiceAccount token security is not only about the token file. It is the combined security of:

```text
ServiceAccount identity
+ token lifetime
+ token audience
+ token mount behavior
+ RBAC
+ SCC / admission controls
+ Secret access
+ audit visibility
+ certificate and issuer trust
```

For advanced OpenShift administration, the best practice is:

> Use dedicated ServiceAccounts, disable token automount by default, prefer short-lived bound tokens, remove legacy long-lived token Secrets, restrict token creation and Secret access, and continuously audit RBAC bindings for workload identities.
