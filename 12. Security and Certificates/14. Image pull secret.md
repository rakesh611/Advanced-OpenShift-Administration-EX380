# Image Pull Secret in OpenShift: Security and Certificates Deep Dive

**Audience:** Advanced OpenShift Administrators / Platform Engineers  
**Experience level:** 10+ years Linux, Kubernetes, OpenShift, DevOps, SRE  
**Scope:** OpenShift Container Platform 4.x, with notes aligned to OpenShift 4.20 behavior  
**Theme:** Security and Certificates

---

## 1. Executive Summary

An **image pull secret** is a Kubernetes/OpenShift `Secret` used by the kubelet/CRI-O runtime to authenticate to a container image registry before pulling a container image. In OpenShift, image pull secrets sit at the intersection of:

- **Authentication**: Can the node/runtime authenticate to the registry?
- **Authorization**: Is that identity allowed to pull the requested repository/tag/digest?
- **TLS trust**: Does the node trust the registry certificate chain?
- **OpenShift internal registry access**: Can a service account in one project pull images from another project?
- **Cluster lifecycle**: Can operators, payload images, builds, and workloads pull required images reliably?
- **Secret governance**: Are credentials scoped, rotated, audited, and protected?

A senior OpenShift administrator must understand that an image pull failure is rarely only a “secret issue.” It can be caused by incorrect credentials, missing service account linkage, wrong namespace, missing `system:image-puller` RBAC, private registry policy, short-name resolution, mirror configuration, disconnected registry misconfiguration, custom CA trust issues, expired certificates, registry route certificates, proxy settings, network policy, DNS, or registry-side repository permissions.

The most important mental model:

> **Image pull secret solves registry authentication. It does not solve registry TLS trust.**

For private registries with custom/self-signed certificates, you usually need **both**:

1. A valid image pull secret for registry authentication.
2. A trusted CA configuration through OpenShift image configuration so cluster nodes and builds trust the registry certificate.

## 2. What Is an Image Pull Secret?

An image pull secret stores registry credentials in a Kubernetes Secret object. It is usually of type:

```yaml
type: kubernetes.io/dockerconfigjson
```

or legacy:

```yaml
type: kubernetes.io/dockercfg
```

The modern and preferred format is `kubernetes.io/dockerconfigjson`, which stores a Docker-compatible JSON authentication file in the `.dockerconfigjson` key.

Basic structure:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-registry-pull-secret
  namespace: app-prod
type: kubernetes.io/dockerconfigjson
data:
  .dockerconfigjson: <base64-encoded-json>
```

Decoded `.dockerconfigjson` example:

```json
{
  "auths": {
    "registry.example.com": {
      "username": "robot-prod-app",
      "password": "REDACTED",
      "auth": "BASE64(username:password)",
      "email": "unused@example.com"
    }
  }
}
```

Important notes:

- Base64 is **encoding**, not encryption.
- Anyone with permission to read the Secret can decode the registry credential.
- The Secret must exist in the same namespace as the Pod that references it.
- The kubelet uses the secret during image pull; the application container does not need to mount it.
- A pull secret is not automatically visible across namespaces.
- Pull secret names are referenced from either the Pod spec or the ServiceAccount spec.

## 3. OpenShift-Specific Image Pull Secret Behavior

OpenShift adds platform-specific behavior on top of Kubernetes.

### 3.1 Automatically Generated Internal Registry Pull Secrets

OpenShift automatically creates an image pull secret for each service account when the integrated image registry is enabled. This secret integrates the internal OpenShift registry with OpenShift authentication and authorization.

Example service account:

```bash
oc describe sa default -n myproject
```

Typical output:

```text
Name:                default
Namespace:           myproject
Annotations:         openshift.io/internal-registry-pull-secret-ref: default-dockercfg-abcd1
Image pull secrets:  default-dockercfg-abcd1
Mountable secrets:   default-dockercfg-abcd1
Tokens:              <none>
Events:              <none>
```

In recent OpenShift 4.x versions, the auto-generated image pull secret remains important, but long-lived service account API token secrets are no longer created by default for new service accounts starting in OpenShift 4.16. That means administrators should not confuse internal registry pull secrets with old service account token secrets.

### 3.2 Namespace Creation Race Condition

When a namespace or service account is newly created, OpenShift may need a short time to provision the automatic internal registry pull secret. If a Pod is created immediately before the service account is fully populated with its internal registry pull secret, the Pod can fail to access the internal OpenShift registry.

Operationally, this matters in automation and exams:

```bash
oc new-project demo
oc get sa default -o yaml
oc get secret | grep dockercfg
```

Before deploying a workload that pulls from the internal registry, verify that the service account has an image pull secret.

### 3.3 Internal Registry Pull Access Is Controlled by RBAC

For the internal OpenShift image registry, registry authentication is tied to OpenShift RBAC.

A service account in one namespace cannot automatically pull images from another namespace. You must grant the consuming service account permission to pull images from the source project.

Example:

```bash
# Allow default service account in project-a to pull images from project-b
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:project-a:default \
  -n project-b
```

Verification:

```bash
oc policy who-can get imagestreams/layers -n project-b
```

Common exam/practical scenario:

```bash
# Image built in project build-ns
# App deployed in project runtime-ns
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:runtime-ns:default \
  -n build-ns
```

Without this RBAC, the image pull may fail even if the service account has an internal registry pull secret.

## 4. Image Pull Secret Authentication Flow

When a Pod is created, the image pull flow is roughly:

1. User creates a Deployment/Pod/BuildConfig.
2. Scheduler assigns the Pod to a node.
3. Kubelet on that node receives the Pod spec.
4. Kubelet asks CRI-O to pull the image.
5. CRI-O resolves the registry and image reference.
6. CRI-O checks credentials from applicable image pull secrets.
7. CRI-O establishes TLS connection to registry.
8. Registry validates credentials and authorization.
9. Registry returns image manifest and layers.
10. CRI-O stores layers locally.
11. Kubelet starts the container.

Credentials may come from:

- `spec.imagePullSecrets` in the Pod.
- `imagePullSecrets` attached to the ServiceAccount used by the Pod.
- Cluster-level/global pull secret for certain platform/node image pull scenarios.
- Node-level runtime configuration in special cases.

TLS trust may come from:

- Public CA trust already present on RHCOS nodes.
- OpenShift `image.config.openshift.io/cluster` `additionalTrustedCA` configuration.
- Registry marked as insecure, which should be avoided except for lab or controlled internal cases.

## 5. Main Types of Pull Secrets in OpenShift

## 5.1 Workload-Level Pull Secret

Used by an application Pod or Deployment to pull from a private external registry.

Example:

```bash
oc create secret docker-registry quay-prod-pull \
  --docker-server=quay.io \
  --docker-username='<robot-account>' \
  --docker-password='<token>' \
  --docker-email='unused@example.com' \
  -n app-prod
```

Then link it to the ServiceAccount:

```bash
oc secrets link default quay-prod-pull --for=pull -n app-prod
```

Or reference it directly in workload YAML:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: private-app
  namespace: app-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: private-app
  template:
    metadata:
      labels:
        app: private-app
    spec:
      imagePullSecrets:
      - name: quay-prod-pull
      containers:
      - name: app
        image: quay.io/myorg/private-app:v1.2.3
```

### ServiceAccount Link vs Direct Pod Reference

| Method | Where configured | Best use case | Operational impact |
|---|---|---|---|
| `oc secrets link sa secret --for=pull` | ServiceAccount | Namespace-wide default behavior | All Pods using that SA inherit the pull secret |
| `spec.imagePullSecrets` | Pod template | GitOps/Helm/ArgoCD explicit config | Only that workload uses the secret |
| Global pull secret | `openshift-config/pull-secret` | Cluster-level image access, payload, operators, mirrors | Affects nodes and cluster lifecycle |

Senior admin guidance:

- Use **ServiceAccount linkage** for standard namespace-level app patterns.
- Use **direct workload reference** for GitOps clarity, multi-tenant isolation, or application-specific registry credentials.
- Use **global pull secret** only for cluster-level requirements or registries needed broadly by nodes/operators.

## 5.2 Automatically Generated ServiceAccount Internal Registry Pull Secret

OpenShift creates secrets such as:

```text
default-dockercfg-xxxxx
builder-dockercfg-xxxxx
deployer-dockercfg-xxxxx
```

These are not your external registry credentials. They are used so service accounts can authenticate to OpenShift’s internal registry.

Check them:

```bash
oc get sa default -n myproject -o yaml
oc get secret -n myproject | grep dockercfg
```

Do not manually edit these generated secrets unless you know exactly what you are doing. If they are missing and the internal registry is enabled, investigate service account controller behavior, image registry operator state, and namespace/service account provisioning.

## 5.3 Global Cluster Pull Secret

The global pull secret is stored in:

```text
namespace: openshift-config
secret: pull-secret
key: .dockerconfigjson
```

Check:

```bash
oc get secret pull-secret -n openshift-config -o yaml
```

Extract decoded content:

```bash
oc get secret/pull-secret -n openshift-config \
  --template='{{index .data ".dockerconfigjson" | base64decode}}' | jq .
```

Use cases:

- Cluster installation authentication to Red Hat registries.
- Pulling OpenShift payload/operator images.
- Disconnected/mirrored registry environments.
- Adding credentials for a registry required cluster-wide.
- Supporting short-name pulls from authenticated registries in specific runtime configurations.

Update pattern:

```bash
oc get secret/pull-secret -n openshift-config \
  --template='{{index .data ".dockerconfigjson" | base64decode}}' \
  > pull-secret.json

oc registry login \
  --registry='registry.example.com' \
  --auth-basic='robot-user:REDACTED' \
  --to=pull-secret.json

oc set data secret/pull-secret -n openshift-config \
  --from-file=.dockerconfigjson=pull-secret.json
```

Important production warning:

- Updating the global pull secret can trigger cluster-wide node reconciliation behavior.
- Plan during a maintenance window if the environment is sensitive.
- Always back up the existing pull secret before changing it.
- Validate JSON before applying it.
- Keep `registry.redhat.io`, `quay.io`, payload mirror, and internal registry requirements intact.

Backup:

```bash
oc get secret pull-secret -n openshift-config -o yaml \
  > backup-pull-secret-$(date +%F).yaml
```

Validate JSON:

```bash
jq . pull-secret.json >/dev/null
```

## 5.4 Build Pull Secret

Builds may need credentials to pull a base image or push/pull from external registries.

Example for a `BuildConfig` source strategy:

```yaml
apiVersion: build.openshift.io/v1
kind: BuildConfig
metadata:
  name: secure-build
  namespace: build-demo
spec:
  source:
    git:
      uri: https://git.example.com/app.git
  strategy:
    sourceStrategy:
      from:
        kind: DockerImage
        name: registry.example.com/base-images/java-17:latest
      pullSecret:
        name: registry-pull
  output:
    to:
      kind: ImageStreamTag
      name: secure-build:latest
```

For builds, distinguish:

- Source repository secret.
- Pull secret for builder/base image.
- Push secret for external output registry.
- CA trust bundle for registry TLS.

A build can fail at any one of these stages with similar-looking authentication or certificate errors.

## 6. Image Pull Secret and Certificates: Critical Difference

Image pull secrets answer:

> “Who are you to the registry?”

Certificates and CA bundles answer:

> “Can the cluster trust that this registry endpoint is really who it claims to be?”

These are different layers.

### 6.1 Authentication Failure Example

Symptoms:

```text
Failed to pull image "registry.example.com/app:v1":
unauthorized: authentication required
```

Likely cause:

- Missing pull secret.
- Wrong username/password/token.
- Secret not linked to correct service account.
- Secret in wrong namespace.
- Registry account lacks repository pull permission.
- Wrong registry hostname in `.dockerconfigjson`.

### 6.2 TLS Trust Failure Example

Symptoms:

```text
x509: certificate signed by unknown authority
```

Likely cause:

- Registry uses private CA or self-signed certificate.
- CA not configured in OpenShift image trust.
- Wrong certificate chain installed on registry.
- Registry route uses cert signed by internal/non-public CA.

Fixing the pull secret will not fix this. You must configure registry CA trust.

### 6.3 Certificate Name Mismatch Example

Symptoms:

```text
x509: certificate is valid for registry.internal.local, not registry.example.com
```

Likely cause:

- Workload image references `registry.example.com`, but certificate SAN/CN covers a different DNS name.
- Route hostname differs from certificate hostname.
- Mirror registry certificate does not include the exact host used in image pull spec.

Fix:

- Reissue registry certificate with correct SAN.
- Use image pull spec matching the certificate SAN.
- Avoid relying on CN only; modern TLS validation depends on SAN.

### 6.4 Insecure Registry Is Not a Security Fix

Marking a registry as insecure disables or weakens TLS validation for that registry. This can make lab pulls work but is risky in production.

Use insecure registries only when:

- It is a temporary lab or break-glass action.
- The network is isolated and risk is understood.
- The long-term fix is to deploy a proper certificate and configure `additionalTrustedCA`.

Production best practice:

- Use HTTPS registries.
- Use proper CA-signed certificates.
- Add private CAs to OpenShift trust.
- Avoid `insecureRegistries` wherever possible.

## 7. Configuring Registry CA Trust in OpenShift

For a private registry using an internal CA, configure a ConfigMap in `openshift-config` and reference it in `image.config.openshift.io/cluster`.

### 7.1 ConfigMap Key Format

Registry without port:

```yaml
data:
  registry.example.com: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

Registry with port `registry.example.com:5000`:

```yaml
data:
  registry.example.com..5000: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

Important:

- Replace `:` with `..` in ConfigMap key names.
- Use PEM-encoded CA certificate, not usually the leaf/server certificate.
- The key must match the registry hostname used in the image pull spec.

### 7.2 Create Registry CA ConfigMap

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.example.com=ca.crt
```

For registry with port:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.example.com..5000=ca.crt
```

### 7.3 Patch Cluster Image Configuration

```bash
oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Verify:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get co machine-config
oc get mcp
```

On a node:

```bash
oc debug node/<node-name>
chroot /host
ls -R /etc/docker/certs.d/
ls -R /etc/containers/certs.d/
```

Depending on OpenShift version and implementation details, trust material may be rendered into node container trust paths by the Machine Config Operator.

## 8. Creating Image Pull Secrets

## 8.1 Create from Username and Token

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=robot-app-prod \
  --docker-password='REDACTED_TOKEN' \
  --docker-email=unused@example.com \
  -n app-prod
```

Verify:

```bash
oc get secret regcred -n app-prod -o jsonpath='{.type}{"\n"}'
oc get secret regcred -n app-prod -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

### Security warning

This command may expose credentials in:

- Shell history.
- Terminal scrollback.
- Audit logs depending on environment.
- CI/CD job logs.

Safer production options:

- Use `--from-file=.dockerconfigjson=...` with a pre-created file.
- Use CI secret masking.
- Use External Secrets Operator or Vault-backed flows.
- Use short-lived robot tokens where supported.

---

## 8.2 Create from Docker Config

After `docker login`:

```bash
oc create secret generic regcred \
  --from-file=.dockerconfigjson=${HOME}/.docker/config.json \
  --type=kubernetes.io/dockerconfigjson \
  -n app-prod
```

After `podman login`, auth file may be:

```text
${XDG_RUNTIME_DIR}/containers/auth.json
${HOME}/.config/containers/auth.json
```

OpenShift supports creating secrets from Podman auth JSON as well:

```bash
oc create secret generic podman-regcred \
  --from-file=${HOME}/.config/containers/auth.json \
  --type=kubernetes.io/podmanconfigjson \
  -n app-prod
```

However, for Kubernetes-native workload `imagePullSecrets`, `kubernetes.io/dockerconfigjson` is the safest portable default.

## 8.3 Create Declaratively for GitOps

Never commit real credentials to Git.

Use a placeholder pattern:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: regcred
  namespace: app-prod
type: kubernetes.io/dockerconfigjson
stringData:
  .dockerconfigjson: |
    {
      "auths": {
        "registry.example.com": {
          "username": "robot-prod",
          "password": "REPLACE_ME",
          "auth": "REPLACE_ME"
        }
      }
    }
```

Better GitOps production options:

- SealedSecrets.
- External Secrets Operator.
- Vault agent/operator.
- SOPS with age/KMS.
- Argo CD Vault Plugin.
- Red Hat Advanced Cluster Management policy injection.

## 9. Attaching Pull Secrets to Workloads

## 9.1 Link Secret to ServiceAccount

```bash
oc secrets link default regcred --for=pull -n app-prod
```

Verify:

```bash
oc get sa default -n app-prod -o yaml
```

Expected:

```yaml
imagePullSecrets:
- name: default-dockercfg-abcde
- name: regcred
```

Test:

```bash
oc run pulltest \
  --image=registry.example.com/private/app:v1 \
  --restart=Never \
  -n app-prod

oc get pod pulltest -n app-prod
oc describe pod pulltest -n app-prod
```

## 9.2 Use a Custom ServiceAccount

```bash
oc create sa app-runner -n app-prod
oc secrets link app-runner regcred --for=pull -n app-prod
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: private-app
  namespace: app-prod
spec:
  replicas: 1
  selector:
    matchLabels:
      app: private-app
  template:
    metadata:
      labels:
        app: private-app
    spec:
      serviceAccountName: app-runner
      containers:
      - name: app
        image: registry.example.com/private/app:v1
```

Verify actual Pod service account:

```bash
oc get pod -n app-prod -l app=private-app \
  -o jsonpath='{range .items[*]}{.metadata.name}{" SA="}{.spec.serviceAccountName}{" pullSecrets="}{.spec.imagePullSecrets}{"\n"}{end}'
```

Remember: if the Deployment uses `serviceAccountName: app-runner`, linking the secret to `default` will not help.

## 9.3 Direct Pod Template Reference

```yaml
spec:
  template:
    spec:
      imagePullSecrets:
      - name: regcred
      containers:
      - name: app
        image: registry.example.com/private/app:v1
```

This is explicit and GitOps-friendly.

But you must duplicate it across workloads unless you use Helm/Kustomize/common templates.

## 10. Image Pull Secrets and OpenShift Internal Registry

Internal registry service name:

```text
image-registry.openshift-image-registry.svc:5000
```

Common internal image pull format:

```text
image-registry.openshift-image-registry.svc:5000/<namespace>/<imagestream>:<tag>
```

Example:

```yaml
image: image-registry.openshift-image-registry.svc:5000/build-ns/myapp:latest
```

Required access:

- Service account must have an internal registry pull secret.
- Service account must have RBAC permission to pull the image from the source namespace.

Grant cross-project pull:

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:runtime-ns:default \
  -n build-ns
```

Troubleshoot:

```bash
oc get is -n build-ns
oc describe is myapp -n build-ns
oc get sa default -n runtime-ns -o yaml
oc policy who-can get imagestreams/layers -n build-ns
oc describe pod <pod> -n runtime-ns
```

Common failure:

```text
unauthorized: authentication required
```

or:

```text
denied: requested access to the resource is denied
```

If using the internal registry across namespaces, always check RBAC before recreating pull secrets.

## 11. Image Pull Secrets, Service Accounts, and RBAC

Image pull secrets are attached to service accounts, but they do not grant Kubernetes API permissions. RBAC still controls what the service account can do inside the cluster.

Example:

```bash
oc create sa app-sa -n app-prod
oc secrets link app-sa regcred --for=pull -n app-prod
```

This only allows image pull authentication. It does not allow the Pod to list secrets, create pods, read configmaps, or pull images from another OpenShift project.

For internal registry cross-project image pulls, RBAC must be granted in the image source namespace:

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:app-prod:app-sa \
  -n image-source-project
```

For API access, separate roles are needed:

```bash
oc adm policy add-role-to-user view \
  system:serviceaccount:app-prod:app-sa \
  -n app-prod
```

Do not over-grant cluster roles just to fix an image pull issue.

## 12. Image Pull Secret and SCC/Pod Security

Image pull secrets have no direct relationship with SCC. However, in real troubleshooting, image pull issues and SCC issues often appear sequentially.

Example flow:

1. Pod fails with `ImagePullBackOff` because pull secret is missing.
2. You fix pull secret.
3. Image pulls successfully.
4. Pod now fails admission because it needs `anyuid` or restricted-v2 compatible settings.

Do not confuse the stages:

| Stage | Component | Common error |
|---|---|---|
| Admission | API server/SCC | `would violate PodSecurity` / SCC denied |
| Pull | kubelet/CRI-O | `ImagePullBackOff`, `ErrImagePull` |
| Start | runtime | permission denied, executable missing |
| Runtime | application | crash loop, config error |

Pull secret fixes image pull only.

## 13. Cluster-Wide Registry Policy and Pull Secrets

OpenShift image configuration can control allowed, blocked, insecure, and search registries.

Resource:

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Important fields:

```yaml
spec:
  additionalTrustedCA:
    name: registry-cas
  registrySources:
    allowedRegistries:
    - registry.redhat.io
    - quay.io
    - image-registry.openshift-image-registry.svc:5000
    - registry.example.com
    blockedRegistries:
    - bad-registry.example.com
    insecureRegistries:
    - lab-registry.example.com:5000
  containerRuntimeSearchRegistries:
  - registry.example.com
```

Advanced warning:

If you define `allowedRegistries`, any registry not explicitly listed can be blocked. This includes registries needed by cluster payloads, operators, and internal workloads. Always include required registries such as:

- `registry.redhat.io`
- `quay.io`
- Internal OpenShift registry hostname
- Disconnected mirror registry
- Any corporate registry required by operators/workloads

Troubleshooting check:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get mcp
oc get co machine-config
```

On node:

```bash
oc debug node/<node>
chroot /host
cat /etc/containers/registries.conf
cat /etc/containers/policy.json
```

A valid pull secret cannot pull from a registry blocked by cluster image policy.

## 14. Short Image Names and Pull Secrets

Short image names are image references without a fully qualified registry hostname, for example:

```text
ubi9/ubi
```

instead of:

```text
registry.access.redhat.com/ubi9/ubi
```

In production OpenShift:

- Prefer fully qualified image references.
- Avoid short names for public registries requiring authentication.
- Short names can expose credentials to multiple searched registries if configured incorrectly.
- Short-name search registries are runtime-level behavior and might not apply to builds and image streams.

Good:

```yaml
image: registry.redhat.io/ubi9/ubi:latest
```

Risky:

```yaml
image: ubi9/ubi:latest
```

Best practice for production:

- Use fully qualified registry hostnames.
- Pin by digest for critical workloads.
- Use signature policy/admission control where required.
- Avoid ambiguous image resolution.

## 15. Disconnected and Mirrored Registry Environments

In disconnected OpenShift, image pull secrets become critical because the cluster must pull from internal mirrors rather than public registries.

Key components:

- Global pull secret with mirror registry credentials.
- Mirror configuration using IDMS/ITMS or older ICSP depending on version/environment.
- Registry CA trust for internal mirror registry.
- Correct allowed registry list.
- Operator catalogs mirrored internally.
- Release payload mirrored internally.

Common failure after installation:

```text
Failed to pull image quay.io/openshift-release-dev/ocp-v4.0-art-dev@sha256:...
```

This might indicate:

- Mirror configuration missing or incorrect.
- Pull secret missing mirror credentials.
- Mirror registry CA not trusted.
- Mirror registry not reachable from nodes.
- Allowed registry policy blocks the mirror or source.

Checklist:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get imagedigestmirrorsets
oc get imagetagmirrorsets
oc get imagecontentsourcepolicy
oc get secret pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
oc get mcp
```

Node-level debug:

```bash
oc debug node/<node>
chroot /host
crictl pull registry.example.com/openshift/release@sha256:<digest>
```

## 16. Registry Authentication Methods and Credential Design

Prefer robot/service accounts over human usernames.

| Registry | Recommended credential style |
|---|---|
| Red Hat registry | Registry service account token for production |
| Quay | Robot account token scoped to org/repo |
| Harbor | Robot account with project/repository scope |
| Nexus/Artifactory | Service account/token with pull-only permissions |
| AWS ECR | Token/credential helper integration or automation-managed secret |
| Azure ACR | Service principal/managed identity depending platform |
| GCP Artifact Registry | Service account JSON/key or workload identity pattern |

Security principles:

- Use pull-only credentials for runtime workloads.
- Separate build push credentials from runtime pull credentials.
- Separate dev/stage/prod registry credentials.
- Avoid shared admin registry accounts.
- Rotate credentials regularly.
- Scope robot accounts to required repositories.
- Revoke credentials when teams/apps are decommissioned.

## 17. Secret Protection in OpenShift

Image pull secrets are Kubernetes Secrets. They require strong governance.

### 17.1 RBAC Protection

Check who can read secrets:

```bash
oc policy who-can get secrets -n app-prod
oc policy who-can list secrets -n app-prod
```

Be careful with roles:

- `view` generally should not allow secret reading.
- `edit` may allow meaningful modification of workloads and access paths.
- `admin` can manage namespace resources, including secrets.
- `cluster-admin` can read everything.

Do not grant namespace `admin` casually in production namespaces that contain registry credentials.

### 17.2 Encryption at Rest

Enable and verify Kubernetes secret encryption at rest as part of cluster hardening.

Check cluster config according to your OpenShift version and security policy. Secrets stored in etcd should be encrypted in regulated environments.

### 17.3 GitOps Secret Handling

Never commit plain `.dockerconfigjson` secrets to Git.

Acceptable approaches:

- SealedSecrets.
- SOPS-encrypted YAML.
- External Secrets Operator.
- Vault integration.
- Argo CD with secret plugin.
- Pipeline-injected runtime secret.

### 17.4 Audit and Rotation

Rotation plan:

1. Create new registry token.
2. Update or create new OpenShift secret.
3. Link new secret to ServiceAccount or update workload reference.
4. Roll out deployments if needed.
5. Verify new Pods pull successfully.
6. Revoke old registry token.
7. Remove old Secret.

Safe rotation with new secret name:

```bash
oc create secret docker-registry regcred-v2 \
  --docker-server=registry.example.com \
  --docker-username=robot-app-prod \
  --docker-password='NEW_TOKEN' \
  --docker-email=unused@example.com \
  -n app-prod

oc secrets link app-sa regcred-v2 --for=pull -n app-prod
oc rollout restart deploy/private-app -n app-prod
oc rollout status deploy/private-app -n app-prod
```

After validation:

```bash
oc secrets unlink app-sa regcred-v1 --for=pull -n app-prod
oc delete secret regcred-v1 -n app-prod
```

## 21. Troubleshooting Methodology

When a Pod has `ImagePullBackOff`, do not guess. Follow the layers.

### 21.1 First Look

```bash
oc get pod <pod> -n <ns>
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp | tail -50
```

Look for exact message:

```text
ErrImagePull
ImagePullBackOff
unauthorized: authentication required
x509: certificate signed by unknown authority
manifest unknown
repository does not exist
Name or service not known
connection refused
i/o timeout
not found
```

### 21.2 Confirm Image Reference

```bash
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.containers[*]}{.image}{"\n"}{end}'
```

Check:

- Correct registry hostname?
- Correct port?
- Correct repository path?
- Correct tag?
- Should it use digest instead?
- Does image exist?

### 21.3 Confirm Pod ServiceAccount

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

If empty, it uses `default`.

### 21.4 Confirm Pull Secrets on Pod

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.imagePullSecrets}{"\n"}'
```

### 21.5 Confirm Pull Secrets on ServiceAccount

```bash
SA=$(oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}')
oc get sa ${SA:-default} -n <ns> -o yaml
```

### 21.6 Confirm Secret Exists in Same Namespace

```bash
oc get secret <secret-name> -n <ns>
oc get secret <secret-name> -n <ns> -o jsonpath='{.type}{"\n"}'
```

Expected:

```text
kubernetes.io/dockerconfigjson
```

### 21.7 Decode Secret

```bash
oc get secret <secret-name> -n <ns> \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Check:

- Registry key exactly matches image registry host and port.
- Username/token are current.
- `auth` value corresponds to username/password if present.
- No malformed JSON.

### 21.8 Test Credentials Outside Cluster

From an admin workstation:

```bash
podman login registry.example.com
podman pull registry.example.com/private/app:v1
```

If workstation fails too, problem is registry credentials, repository permission, image name, or registry certificate.

### 21.9 Test From Node

```bash
oc debug node/<node-name>
chroot /host
crictl pull registry.example.com/private/app:v1
```

If node fails with x509, solve CA trust.

If node fails with DNS/network, solve network path.

If node fails with unauthorized, solve credentials or registry-side permission.

### 21.10 Check Registry Policy

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Look for:

```yaml
registrySources:
  allowedRegistries:
  blockedRegistries:
  insecureRegistries:
additionalTrustedCA:
containerRuntimeSearchRegistries:
```

### 21.11 Check Machine Config Rollout

```bash
oc get mcp
oc describe mcp worker
oc get co machine-config
```

If CA or registry policy changes are not applied to nodes, image pulls may continue failing.

## 22. Error Message Mapping

| Error | Most likely cause | What to check |
|---|---|---|
| `unauthorized: authentication required` | Missing/wrong credentials | Secret, SA linkage, registry token |
| `denied: requested access to the resource is denied` | Credential valid but lacks repo permission | Registry ACL, Quay robot permission, Harbor project role |
| `pull access denied` | Repo private, missing permission, wrong repo | Image path, registry ACL |
| `manifest unknown` | Tag/digest missing | Registry image tags, digest |
| `x509: certificate signed by unknown authority` | Registry CA not trusted | `additionalTrustedCA`, CA chain |
| `certificate is valid for X, not Y` | Hostname/SAN mismatch | Registry cert SAN and image pull hostname |
| `no such host` | DNS issue | Node DNS, CoreDNS, `/etc/resolv.conf` |
| `connection refused` | Registry port/service down | Registry service, firewall, route, load balancer |
| `i/o timeout` | Network/firewall/proxy | Egress firewall, proxy, routing |
| `toomanyrequests` | Rate limit | Registry limits, mirror/cache |
| `server gave HTTP response to HTTPS client` | Registry is HTTP/insecure | Use HTTPS or configure insecure registry |
| `blocked by policy` | OpenShift registry policy | `image.config.openshift.io/cluster` |

## 24. Common Real-World Scenarios

## 24.1 Secret Created but Pod Still Fails

Likely causes:

- Secret not linked to the Pod’s actual service account.
- Pod uses `serviceAccountName: custom-sa`, but secret linked to `default`.
- Secret is in a different namespace.
- Deployment needs restart to create new Pods.
- Existing failed Pod still uses old spec.

Fix:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
oc secrets link <actual-sa> <secret> --for=pull -n <ns>
oc rollout restart deploy/<deploy> -n <ns>
```

## 24.2 Pull Secret Has Wrong Registry Key

Image:

```text
registry.example.com:8443/team/app:v1
```

Secret auth key:

```json
"registry.example.com": {...}
```

This may fail because the image uses `registry.example.com:8443`, but the secret contains `registry.example.com`.

Fix:

Create secret with exact server:

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.example.com:8443 \
  --docker-username=robot \
  --docker-password='TOKEN' \
  --docker-email=unused@example.com \
  -n app-prod
```

## 24.3 Secret Linked but Registry Says Denied

Credential may authenticate but lack repository permission.

Example:

```text
denied: requested access to the resource is denied
```

Fix at registry side:

- Add robot account to repository/project.
- Grant pull role.
- Verify repository path.
- Verify image tag/digest exists.

## 24.4 x509 Unknown Authority After Secret Fix

This proves auth progressed enough to attempt TLS but trust failed.

Fix:

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=registry.example.com=ca.crt

oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Then wait for machine config rollout.

## 24.5 Build Pull Works but Runtime Pod Pull Fails

Possible causes:

- Build strategy has `pullSecret`, but runtime service account does not.
- Build ran in one namespace; app runs in another.
- Internal ImageStream access not granted with `system:image-puller`.
- Runtime nodes do not trust registry CA.

## 24.6 Runtime Pull Works but ImageStream Import Fails

Possible causes:

- Credentials exist in application namespace but not in `openshift` namespace for image stream import needs.
- Registry CA trust not configured for import controller/build.
- `allowedRegistriesForImport` blocks import.

Check:

```bash
oc import-image myimage:latest --from=registry.example.com/team/app:latest --confirm -n app-prod
oc describe is myimage -n app-prod
oc get image.config.openshift.io/cluster -o yaml
```

## 24.7 Operator Install Fails Due to Image Pull

Possible causes:

- Operator catalog references external registry not in disconnected mirror.
- Global pull secret missing credentials.
- Registry CA trust missing.
- ImageContentSourcePolicy/IDMS wrong.
- Cluster-wide allowed registry policy blocks catalog/image registry.

Check:

```bash
oc get pods -n openshift-marketplace
oc get pods -A | grep -i catalog
oc get subscription -A
oc get installplan -A
oc describe pod <catalog-pod> -n openshift-marketplace
```

## 25. Production Best Practices

## 25.1 Use Fully Qualified Image References

Good:

```text
registry.example.com/platform/app@sha256:<digest>
```

Less ideal:

```text
registry.example.com/platform/app:latest
```

Risky:

```text
app:latest
```

Use digest pinning for high-control production workloads, especially regulated systems.

## 25.2 Separate Credentials by Environment

Do not use one global robot account for everything.

Example:

| Environment | Robot account | Scope |
|---|---|---|
| dev | `robot-dev-pull` | dev repos only |
| stage | `robot-stage-pull` | stage repos only |
| prod | `robot-prod-pull` | prod repos only |
| cluster | `robot-cluster-pull` | operators/platform images only |

## 25.3 Use Pull-Only Runtime Credentials

Runtime Pods normally need only pull permission.

Build pipelines may need push permission, but that should be a different credential.

## 25.4 Avoid Human Credentials

Human credentials break when:

- User leaves company.
- Password rotates.
- MFA changes.
- Account is disabled.
- Personal access token expires unexpectedly.

Use robot/service accounts.

## 25.5 Rotate Secrets Safely

Do not update all secrets blindly during business hours.

Safe sequence:

1. Create new token.
2. Create new Secret.
3. Link new Secret.
4. Restart small canary workload.
5. Validate.
6. Roll out broadly.
7. Remove old Secret.
8. Revoke old registry token.

## 25.6 Monitor Pull Failures

Alert on:

- `ImagePullBackOff`
- `ErrImagePull`
- catalog/operator image pull failures
- registry certificate expiry
- mirror registry availability
- machine config pool degraded after registry policy changes

Prometheus query idea:

```promql
kube_pod_container_status_waiting_reason{reason=~"ImagePullBackOff|ErrImagePull"}
```

## 25.7 Keep Registry Certificates Healthy

Track expiry:

```bash
echo | openssl s_client -connect registry.example.com:443 -servername registry.example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

Check SAN:

```bash
echo | openssl s_client -connect registry.example.com:443 -servername registry.example.com 2>/dev/null \
  | openssl x509 -noout -text | grep -A1 'Subject Alternative Name'
```

## 25.8 Document Ownership

Every pull secret should have clear metadata:

```yaml
metadata:
  labels:
    security.openshift.io/secret-purpose: image-pull
    app.kubernetes.io/managed-by: argocd
    owner: platform-team
  annotations:
    security.openshift.io/registry: registry.example.com
    security.openshift.io/rotation-policy: quarterly
    security.openshift.io/contact: platform-team@example.com
```

## 26. Security Anti-Patterns

Avoid these:

1. Using a cluster-admin registry token for all namespaces.
2. Storing `.dockerconfigjson` in plain Git.
3. Sharing one pull secret across dev, test, and prod.
4. Granting namespace admin just to let someone update a pull secret.
5. Using `insecureRegistries` for production instead of fixing CA trust.
6. Pulling images by short names from public registries.
7. Using human credentials in global pull secret.
8. Never rotating robot tokens.
9. Giving runtime Pods push access.
10. Assuming `ImagePullBackOff` is always caused by missing secret.
11. Forgetting cross-project `system:image-puller` for internal registry.
12. Updating global pull secret without backup.
13. Defining `allowedRegistries` and forgetting `registry.redhat.io`, `quay.io`, or internal registry.
14. Using `latest` for production critical workloads.
15. Ignoring registry certificate expiry monitoring.

## 27. Exam and Interview Perspective

For Advanced OpenShift Administration, expect questions like:

### Q1. What is the difference between a pull secret and a TLS secret?

A pull secret stores registry authentication credentials. A TLS secret stores certificates/keys, usually for serving TLS. Pull secret does not establish trust in a private registry CA. Registry CA trust is configured separately, often through `image.config.openshift.io/cluster` `additionalTrustedCA`.

### Q2. Pod uses private image and fails with `unauthorized`. What do you check?

Check:

```bash
oc describe pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}'
oc get sa <sa> -n <ns> -o yaml
oc get secret <pull-secret> -n <ns> -o jsonpath='{.type}'
oc get secret <pull-secret> -n <ns> -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Then verify registry-side repository permission.

### Q3. Pod fails with `x509: certificate signed by unknown authority`. Should you recreate pull secret?

No. Configure registry CA trust. Recreating the pull secret does not fix TLS trust.

### Q4. How do you allow project A to pull internal registry image from project B?

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:project-a:default \
  -n project-b
```

### Q5. What is the global pull secret?

The global pull secret is `pull-secret` in the `openshift-config` namespace. It stores cluster-level registry credentials used for OpenShift cluster image access and can be updated when adding new cluster-level registries or mirror registry credentials.

### Q6. Why should `allowedRegistries` be configured carefully?

Because once an allowlist is defined, registries not listed may be blocked. If required registries such as Red Hat, Quay, internal registry, or mirror registry are omitted, cluster components and workloads can fail to pull images.

## 29. Production Checklist

Before marking image pull secret configuration as production-ready, verify:

- [ ] Pull secret exists in the correct namespace.
- [ ] Secret type is `kubernetes.io/dockerconfigjson`.
- [ ] `.dockerconfigjson` is valid JSON.
- [ ] Registry hostname and port match the image pull spec exactly.
- [ ] Secret is linked to the correct ServiceAccount or referenced in workload spec.
- [ ] Workload uses the expected `serviceAccountName`.
- [ ] Registry account has pull-only permission for required repository.
- [ ] Human credentials are not used.
- [ ] Secret is not stored in plain Git.
- [ ] Rotation owner and schedule are defined.
- [ ] Private registry CA is trusted through OpenShift image configuration.
- [ ] Registry certificate SAN matches pull hostname.
- [ ] Registry certificate expiry is monitored.
- [ ] Cluster image registry policy does not block the registry.
- [ ] Disconnected mirror config is correct, if applicable.
- [ ] Cross-project internal pulls have `system:image-puller` RBAC.
- [ ] Existing workloads were rolled out or recreated after secret changes.
- [ ] Pull failures are monitored via events/metrics.

## 30. Key Takeaways

1. Image pull secrets are registry authentication objects, not certificate trust objects.
2. In OpenShift, service accounts automatically get internal-registry pull secrets when the integrated registry is enabled.
3. For external private registries, create a `kubernetes.io/dockerconfigjson` secret and link it to the correct service account or reference it in workload YAML.
4. Secret namespace must match Pod namespace.
5. For internal registry cross-project pulls, grant `system:image-puller` from the source project to the target service account.
6. For private registry certificates, configure `additionalTrustedCA` in `image.config.openshift.io/cluster`.
7. The global pull secret is powerful and should be modified carefully with backup and validation.
8. `ImagePullBackOff` is a symptom, not a root cause. Always read Pod events and node runtime logs.
9. Avoid insecure registries in production; fix CA trust instead.
10. Use robot accounts, least privilege, rotation, and GitOps-safe secret management.
