# LDAP Certificate Trust in OpenShift Security and Certificates

**Audience:** Advanced OpenShift Administration / OpenShift admin with ~10 years Linux, DevOps, and platform operations experience  
**Scope:** Red Hat OpenShift Container Platform 4.x LDAP identity provider trust, LDAP group sync trust, LDAPS, StartTLS, custom CA bundles, troubleshooting, and production practices  
**Last reviewed:** 2026-07-03  

---

## 1. What is LDAP certificate trust?

**LDAP certificate trust** means OpenShift trusts the TLS certificate presented by an LDAP server when OpenShift connects to that LDAP server for authentication or group synchronization.

In OpenShift, LDAP is usually used in two places:

1. **LDAP identity provider**
   - Users log in to OpenShift with LDAP credentials.
   - The OpenShift OAuth server connects to the LDAP server.
   - OpenShift searches for the user entry and then performs a simple bind using the user DN and password.

2. **LDAP group sync**
   - OpenShift synchronizes LDAP groups into OpenShift `Group` objects.
   - A cluster admin, scheduled job, or CronJob runs `oc adm groups sync`.
   - The sync process connects to LDAP and reads group/user membership.

LDAP certificate trust protects the connection between OpenShift and LDAP from:

- credential snooping,
- man-in-the-middle attacks,
- fake LDAP servers,
- unauthorized interception of bind DN credentials,
- unauthorized interception of end-user passwords during authentication.

A 10-year experienced admin should treat LDAP trust as part of the cluster authentication control plane, not as a simple certificate upload task.

---

## 2. Where LDAP certificate trust fits in OpenShift authentication

A common authentication flow looks like this:

```text
User / oc login / Web Console
        |
        v
OpenShift OAuth server
        |
        |  TLS connection to LDAP
        v
LDAP / Active Directory / FreeIPA / RHDS
```

Important point:

The user's browser or `oc` client does **not** connect directly to LDAP. The OpenShift OAuth server connects to LDAP on behalf of the login flow.

Therefore, the LDAP CA certificate must be trusted by the OpenShift component that performs the LDAP request. For an OpenShift LDAP identity provider, the CA bundle is referenced from the cluster OAuth configuration through a `ConfigMap` in the `openshift-config` namespace.

---

## 3. Why certificate trust is required

When OpenShift connects to LDAP over TLS, the LDAP server sends its server certificate. OpenShift validates that certificate using a trusted CA bundle.

OpenShift checks, directly or indirectly through the TLS stack:

- whether the server certificate is signed by a trusted CA,
- whether the certificate chain is valid,
- whether the certificate is currently valid and not expired,
- whether the certificate is being used for the correct server hostname,
- whether the certificate is usable for TLS server authentication,
- whether the connection mode matches the configured security mode.

If the LDAP server uses a public CA certificate, OpenShift might already trust it through system root CAs. In enterprise environments, LDAP commonly uses an internal CA, Active Directory Certificate Services, FreeIPA CA, or corporate PKI. In that case, OpenShift must be explicitly given the LDAP CA bundle.

## 4. LDAP, LDAPS, and StartTLS in OpenShift

OpenShift LDAP integration commonly uses one of these modes:

| Mode | URL scheme | Port | TLS behavior | Production use |
|---|---:|---:|---|---|
| Plain LDAP | `ldap://` | 389 | No TLS if `insecure: true` | Avoid |
| LDAP + StartTLS | `ldap://` | 389 | Starts as LDAP, upgrades to TLS when `insecure: false` | Acceptable if LDAP server supports StartTLS |
| LDAPS | `ldaps://` | 636 | TLS from the beginning | Common production choice |

For the OpenShift LDAP identity provider:

- `insecure: false` enables secure behavior.
- With `ldaps://`, OpenShift connects using TLS.
- With `ldap://` and `insecure: false`, OpenShift upgrades the connection with StartTLS.
- `insecure: true` means no TLS connection is made.
- `ldaps://` must not be used with `insecure: true`.

Production recommendation:

```yaml
insecure: false
```

Use `insecure: true` only for temporary lab validation, never for production authentication.

## 5. LDAP identity provider CA trust model

For an LDAP identity provider, OpenShift uses a `ConfigMap` to store the CA bundle.

Key rules:

- The `ConfigMap` must be in the `openshift-config` namespace.
- The CA bundle key must be named exactly `ca.crt`.
- The OAuth resource references only the `ConfigMap` name.
- The `ca` reference is used only when `insecure: false`.
- If the `ca` field is omitted, OpenShift uses default system-trusted roots.
- If the referenced ConfigMap or key is missing, invalid, or malformed, the identity provider can be ignored/not honored by OpenShift.

Example object relationship:

```text
OAuth cluster object
  spec.identityProviders[].ldap.ca.name: ldap-ca

ConfigMap
  namespace: openshift-config
  name: ldap-ca
  data:
    ca.crt: |
      -----BEGIN CERTIFICATE-----
      ... corporate root/intermediate CA ...
      -----END CERTIFICATE-----
```

## 6. What should be inside the LDAP CA bundle?

The LDAP CA bundle should contain the CA certificates needed to validate the LDAP server certificate chain.

Usually it contains:

- the corporate root CA, and/or
- one or more intermediate CA certificates.

Usually it should **not** contain:

- the LDAP server private key,
- the bind password,
- unrelated application certificates,
- expired CA certificates unless required during a temporary rotation overlap,
- random public CA bundles copied from hosts without review.

A good CA bundle looks like this:

```text
-----BEGIN CERTIFICATE-----
Intermediate CA certificate
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
Root CA certificate
-----END CERTIFICATE-----
```

The order normally does not matter for a trust bundle, but many admins keep intermediate first and root second for readability.

## 7. LDAP server certificate requirements

The LDAP server certificate should satisfy these requirements:

1. **Valid SAN**
   - The hostname in the OpenShift LDAP URL must match a DNS name in the certificate Subject Alternative Name.
   - Do not rely on only the legacy Common Name field.

2. **Correct key usage**
   - The certificate should be valid for TLS server authentication.

3. **Complete chain**
   - The LDAP server should present the server certificate and required intermediates.
   - OpenShift should trust the root/intermediate CA bundle.

4. **Not expired**
   - Check both server certificate and CA certificates.

5. **Correct hostname strategy**
   - If you use `ldaps://ldap.example.com:636`, the certificate must be valid for `ldap.example.com`.
   - If you use an LDAP load balancer, the certificate must be valid for the load balancer DNS name.
   - If you point OpenShift at individual domain controllers, each domain controller certificate must be valid for its own FQDN.

6. **Compatible TLS settings**
   - The LDAP server must support TLS versions and ciphers compatible with the OpenShift cluster security profile.

## 8. Collecting and validating the LDAP certificate chain

### 8.1 Check LDAPS on port 636

```bash
LDAP_HOST="ldap.example.com"
LDAP_PORT="636"

openssl s_client \
  -connect ${LDAP_HOST}:${LDAP_PORT} \
  -servername ${LDAP_HOST} \
  -showcerts \
  </dev/null
```

Look for:

```text
Verify return code: 0 (ok)
```

If the return code is not `0`, collect the CA chain and validate manually.

### 8.2 Check StartTLS on port 389

```bash
LDAP_HOST="ldap.example.com"
LDAP_PORT="389"

openssl s_client \
  -connect ${LDAP_HOST}:${LDAP_PORT} \
  -starttls ldap \
  -servername ${LDAP_HOST} \
  -showcerts \
  </dev/null
```

This validates the TLS handshake after LDAP StartTLS negotiation.

### 8.3 Extract the server certificate for inspection

```bash
LDAP_HOST="ldap.example.com"

openssl s_client \
  -connect ${LDAP_HOST}:636 \
  -servername ${LDAP_HOST} \
  -showcerts \
  </dev/null 2>/dev/null \
| awk '/BEGIN CERTIFICATE/,/END CERTIFICATE/ {print}' > ldap-server-chain.pem
```

Inspect the first certificate:

```bash
openssl x509 -in ldap-server-chain.pem -noout -subject -issuer -dates -ext subjectAltName
```

### 8.4 Validate with your CA bundle

```bash
openssl verify -CAfile ldap-ca-bundle.pem ldap-server-chain.pem
```

For a live connection:

```bash
openssl s_client \
  -connect ldap.example.com:636 \
  -servername ldap.example.com \
  -CAfile ldap-ca-bundle.pem \
  -verify_return_error \
  </dev/null
```

Expected result:

```text
Verify return code: 0 (ok)
```

## 9. Creating the LDAP CA ConfigMap for OAuth

Assume your CA bundle is saved as:

```bash
ldap-ca-bundle.pem
```

Create or update the ConfigMap:

```bash
oc -n openshift-config create configmap ldap-ca \
  --from-file=ca.crt=ldap-ca-bundle.pem \
  --dry-run=client -o yaml | oc apply -f -
```

Verify:

```bash
oc -n openshift-config get configmap ldap-ca -o yaml
```

Confirm the key is exactly:

```yaml
data:
  ca.crt: |
    -----BEGIN CERTIFICATE-----
```

Common mistake:

```yaml
data:
  ldap-ca-bundle.pem: |
```

This is wrong for the LDAP identity provider because OpenShift expects `ca.crt`.

## 10. Creating the LDAP bind password Secret

If your LDAP directory requires authenticated search, create a secret for the bind password.

```bash
oc -n openshift-config create secret generic ldap-bind-secret \
  --from-literal=bindPassword='REPLACE_WITH_BIND_PASSWORD' \
  --dry-run=client -o yaml | oc apply -f -
```

Verify the object exists:

```bash
oc -n openshift-config get secret ldap-bind-secret
```

Important:

- The secret key must be `bindPassword`.
- Do not store the bind password in a ConfigMap.
- Use a least-privilege LDAP service account for the bind DN.
- The account should be read-only and scoped to required search bases where possible.

## 11. LDAP identity provider example using LDAPS

Create a file named `oauth-ldap.yaml`:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: ldap-provider
    mappingMethod: claim
    type: LDAP
    ldap:
      url: "ldaps://ldap.example.com:636/ou=users,dc=example,dc=com?uid?sub?(objectClass=person)"
      bindDN: "cn=openshift-bind,ou=service-accounts,dc=example,dc=com"
      bindPassword:
        name: ldap-bind-secret
      ca:
        name: ldap-ca
      insecure: false
      attributes:
        id:
        - dn
        preferredUsername:
        - uid
        name:
        - cn
        email:
        - mail
```

Apply it:

```bash
oc apply -f oauth-ldap.yaml
```

Important production note:

If your cluster already has identity providers, do not blindly overwrite the OAuth object. Always back up and merge carefully.

```bash
oc get oauth cluster -o yaml > oauth-cluster-backup.yaml
```

Then edit the existing object:

```bash
oc edit oauth cluster
```

## 14. What happens after applying OAuth LDAP config?

After you update the `OAuth` object:

1. The OpenShift Authentication Operator observes the change.
2. The OAuth server configuration is reconciled.
3. OAuth pods in `openshift-authentication` roll out/reload as needed.
4. New login attempts use the new identity provider configuration.

Useful checks:

```bash
oc get co authentication
oc -n openshift-authentication get pods
oc -n openshift-authentication rollout status deployment/oauth-openshift
```

Check OAuth logs:

```bash
oc -n openshift-authentication logs deployment/oauth-openshift \
  -c oauth-openshift --tail=200 | egrep -i 'ldap|x509|certificate|tls|bind|error'
```

Test login:

```bash
oc login -u alice
oc whoami
```

## 15. LDAP URL deep dive

OpenShift LDAP identity provider URLs follow this structure:

```text
ldap://host:port/basedn?attribute?scope?filter
ldaps://host:port/basedn?attribute?scope?filter
```

Example:

```text
ldaps://ldap.example.com:636/ou=users,dc=example,dc=com?uid?sub?(objectClass=person)
```

Breakdown:

| Part | Meaning |
|---|---|
| `ldaps` | Secure LDAP over TLS |
| `ldap.example.com:636` | LDAP server and port |
| `ou=users,dc=example,dc=com` | Base DN for user search |
| `uid` | Attribute matched against login username |
| `sub` | Search subtree under the base DN |
| `(objectClass=person)` | Additional LDAP filter |

When a user logs in as `alice`, OpenShift effectively searches using a combined filter similar to:

```text
(&(objectClass=person)(uid=alice))
```

If exactly one user entry is found, OpenShift attempts a simple bind as that user's DN with the password provided during login.

## 16. Certificate trust for LDAP group sync

LDAP group sync is separate from the LDAP identity provider, but it often uses the same LDAP server, bind secret, and CA bundle.

For group sync, the CA is usually referenced as a **file path** in the LDAP sync config, not as `ca.name`.

Example `sync.yaml`:

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ldap.example.com:636
insecure: false
bindDN: cn=openshift-bind,ou=service-accounts,dc=example,dc=com
bindPassword:
  file: "/etc/secrets/bindPassword"
ca: /etc/ldap-ca/ca.crt
rfc2307:
  groupsQuery:
    baseDN: "ou=groups,dc=example,dc=com"
    scope: sub
    filter: "(objectClass=groupOfNames)"
    derefAliases: never
    pageSize: 0
  groupUIDAttribute: dn
  groupNameAttributes:
  - cn
  groupMembershipAttributes:
  - member
  usersQuery:
    baseDN: "ou=users,dc=example,dc=com"
    scope: sub
    derefAliases: never
    pageSize: 0
  userUIDAttribute: dn
  userNameAttributes:
  - uid
  tolerateMemberNotFoundErrors: false
  tolerateMemberOutOfScopeErrors: false
```

If you run group sync as a CronJob in a separate namespace such as `ldap-sync`, you must copy or recreate the LDAP CA ConfigMap and bind secret in that namespace, then mount them into the job.

Example:

```bash
oc new-project ldap-sync

oc get configmap ldap-ca -n openshift-config -o yaml \
| sed 's/namespace: openshift-config/namespace: ldap-sync/' \
| oc apply -f -

oc get secret ldap-bind-secret -n openshift-config -o yaml \
| sed 's/namespace: openshift-config/namespace: ldap-sync/' \
| oc apply -f -
```

Better production method:

- manage these objects through GitOps,
- avoid ad-hoc `sed` in automation,
- use External Secrets, Sealed Secrets, or another approved secret-management pattern for the bind password.

## 17. CronJob example for LDAP group sync with CA trust

Example `ldap-sync-configmap.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
data:
  sync.yaml: |
    kind: LDAPSyncConfig
    apiVersion: v1
    url: ldaps://ldap.example.com:636
    insecure: false
    bindDN: cn=openshift-bind,ou=service-accounts,dc=example,dc=com
    bindPassword:
      file: "/etc/secrets/bindPassword"
    ca: /etc/ldap-ca/ca.crt
    rfc2307:
      groupsQuery:
        baseDN: "ou=groups,dc=example,dc=com"
        scope: sub
        filter: "(objectClass=groupOfNames)"
        derefAliases: never
        pageSize: 0
      groupUIDAttribute: dn
      groupNameAttributes: [ cn ]
      groupMembershipAttributes: [ member ]
      usersQuery:
        baseDN: "ou=users,dc=example,dc=com"
        scope: sub
        derefAliases: never
        pageSize: 0
      userUIDAttribute: dn
      userNameAttributes: [ uid ]
      tolerateMemberNotFoundErrors: false
      tolerateMemberOutOfScopeErrors: false
```

Example `ldap-sync-cronjob.yaml`:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
spec:
  schedule: "*/30 * * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 0
      template:
        spec:
          serviceAccountName: ldap-group-syncer
          restartPolicy: Never
          containers:
          - name: ldap-group-sync
            image: registry.redhat.io/openshift4/ose-cli:latest
            command:
            - /bin/bash
            - -c
            - oc adm groups sync --sync-config=/etc/config/sync.yaml --confirm
            volumeMounts:
            - name: ldap-sync-volume
              mountPath: /etc/config
            - name: ldap-bind-password
              mountPath: /etc/secrets
            - name: ldap-ca
              mountPath: /etc/ldap-ca
          volumes:
          - name: ldap-sync-volume
            configMap:
              name: ldap-group-syncer
          - name: ldap-bind-password
            secret:
              secretName: ldap-bind-secret
          - name: ldap-ca
            configMap:
              name: ldap-ca
```

## 18. Validating connectivity from inside the cluster

Testing from your laptop is useful, but OpenShift OAuth pods must reach LDAP from inside the cluster network.

Create a temporary debug pod:

```bash
oc new-project ldap-debug

oc run ldap-client \
  -n ldap-debug \
  --image=registry.access.redhat.com/ubi9/ubi \
  --restart=Never \
  -- sleep 3600

oc rsh -n ldap-debug ldap-client
```

Inside the pod, test DNS and TCP:

```bash
getent hosts ldap.example.com
```

If tools are available:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com </dev/null
```

Some minimal images do not include `openssl`, `nc`, or `ldapsearch`. In restricted environments, use an approved troubleshooting image that contains network tools, or use `oc debug node/<node>` carefully if node-level testing is required.

Clean up:

```bash
oc delete project ldap-debug
```

## 19. Common errors and fixes

| Symptom | Likely cause | Check | Fix |
|---|---|---|---|
| `x509: certificate signed by unknown authority` | LDAP CA not trusted | `oc get cm ldap-ca -n openshift-config -o yaml` | Add correct CA bundle under `ca.crt` |
| `certificate is valid for X, not Y` | LDAP URL hostname does not match certificate SAN | `openssl x509 -noout -ext subjectAltName` | Use correct FQDN or reissue certificate with correct SAN |
| LDAP IdP not visible / login option missing | Invalid OAuth IdP config or missing ConfigMap key | `oc describe co authentication`; OAuth logs | Fix `ca.crt`, secret, YAML structure |
| `ldaps://` fails with insecure error | `insecure: true` with LDAPS | `oc get oauth cluster -o yaml` | Set `insecure: false` |
| `ldap://` fails after setting `insecure: false` | LDAP server does not support StartTLS | `openssl s_client -starttls ldap` | Use LDAPS or enable StartTLS |
| Bind fails | Wrong bind DN/password or account locked | LDAP server logs; OAuth logs | Fix secret, unlock account, verify DN |
| Search returns zero users | Wrong base DN, scope, attribute, or filter | `ldapsearch` with same base/filter | Fix LDAP URL |
| Search returns more than one user | Non-unique login attribute | OAuth logs; LDAP search | Use unique attribute, usually `uid`, `sAMAccountName`, `userPrincipalName`, or email depending on directory |
| Works from laptop, fails in OpenShift | Network path blocked from cluster | test from debug pod/node | Fix firewall, routing, proxy, DNS, NetworkPolicy/egress controls |
| Group sync fails but login works | Group sync namespace lacks CA or secret | Check mounted files in CronJob pod | Copy/recreate ConfigMap and Secret in group sync namespace |
| Certificate suddenly fails after LDAP maintenance | LDAP server cert rotated to new CA | `openssl s_client -showcerts` | Add new issuing/root CA to ConfigMap before rotation |

## 20. Troubleshooting workflow for experienced admins

Follow this order during incidents:

### Step 1: Confirm OAuth operator health

```bash
oc get co authentication
oc get co openshift-apiserver
oc get co kube-apiserver
```

### Step 2: Confirm OAuth configuration

```bash
oc get oauth cluster -o yaml
```

Check:

- `type: LDAP`
- `ldap.url`
- `ldap.ca.name`
- `ldap.insecure`
- `ldap.bindDN`
- `ldap.bindPassword.name`
- `ldap.attributes`

### Step 3: Confirm CA ConfigMap

```bash
oc -n openshift-config get configmap ldap-ca -o yaml
```

Check:

- namespace is `openshift-config`,
- key is `ca.crt`,
- PEM blocks are valid,
- bundle contains the required CA chain.

### Step 4: Confirm bind Secret

```bash
oc -n openshift-config get secret ldap-bind-secret -o jsonpath='{.data.bindPassword}' | base64 -d; echo
```

Be careful: this prints the password. Use only in a secure admin session.

### Step 5: Check OAuth pod rollout

```bash
oc -n openshift-authentication get pods
oc -n openshift-authentication rollout status deployment/oauth-openshift
```

### Step 6: Check OAuth logs

```bash
oc -n openshift-authentication logs deployment/oauth-openshift \
  -c oauth-openshift --tail=300 \
| egrep -i 'ldap|x509|tls|certificate|bind|search|error'
```

### Step 7: Validate LDAP TLS outside and inside the cluster

Outside:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com -CAfile ldap-ca-bundle.pem </dev/null
```

Inside cluster:

```bash
oc run ldap-test -n ldap-debug --image=registry.access.redhat.com/ubi9/ubi --restart=Never -- sleep 3600
oc rsh -n ldap-debug ldap-test
```

### Step 8: Test login

```bash
oc login -u alice
oc whoami
```

## 21. CA rotation strategy

LDAP CA rotation must be planned because failed LDAP trust can block user login.

Recommended safe rotation pattern:

### Phase 1: Add new CA before server rotation

Create a combined bundle:

```bash
cat old-ldap-ca.pem new-ldap-ca.pem > ldap-ca-bundle.pem
```

Update ConfigMap:

```bash
oc -n openshift-config create configmap ldap-ca \
  --from-file=ca.crt=ldap-ca-bundle.pem \
  --dry-run=client -o yaml | oc apply -f -
```

Watch OAuth rollout/health:

```bash
oc get co authentication
oc -n openshift-authentication get pods
```

### Phase 2: Rotate LDAP server certificate

LDAP team rotates the LDAP server certificate to the new issuing CA.

Validate:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com -showcerts </dev/null
```

Test OpenShift login:

```bash
oc login -u testuser
```

### Phase 3: Remove old CA after safe period

After all LDAP endpoints use the new chain:

```bash
cp new-ldap-ca.pem ldap-ca-bundle.pem

oc -n openshift-config create configmap ldap-ca \
  --from-file=ca.crt=ldap-ca-bundle.pem \
  --dry-run=client -o yaml | oc apply -f -
```

Repeat the same for group sync namespaces if they use copied CA ConfigMaps.

## 22. Active Directory-specific notes

In Active Directory environments:

- LDAPS commonly uses port `636`.
- Global Catalog over SSL commonly uses port `3269`, but OpenShift LDAP identity provider usage depends on your search design.
- StartTLS can be available on port `389` if enabled and certificates are correctly configured.
- Domain controller certificates are often issued by AD CS.
- The certificate SAN should include the domain controller FQDN or the load-balanced LDAP FQDN.
- If using a load balancer in front of multiple DCs, the LDAPS certificate presented by the load balancer must match the LDAP URL hostname.
- Use a dedicated bind account with read-only permissions.
- For login attribute, many AD environments use `sAMAccountName`, `userPrincipalName`, or `mail` instead of `uid`.

Example AD-style LDAP URL:

```text
ldaps://ad.example.com:636/DC=example,DC=com?sAMAccountName?sub?(objectClass=user)
```

Example attributes:

```yaml
attributes:
  id:
  - dn
  preferredUsername:
  - sAMAccountName
  name:
  - cn
  email:
  - mail
```

## 23. FreeIPA / Red Hat Directory Server notes

In FreeIPA or Red Hat Directory Server environments:

- LDAP over TLS is commonly available through LDAPS or StartTLS.
- User login attributes are often `uid`.
- Email is usually `mail`.
- Display name can be `cn`.
- CA may be a FreeIPA CA or corporate PKI CA.

Example URL:

```text
ldaps://ipa.example.com:636/cn=users,cn=accounts,dc=example,dc=com?uid?sub?(objectClass=person)
```

## 24. Production security best practices

### 24.1 Do not use insecure LDAP

Avoid:

```yaml
insecure: true
```

This disables TLS and can expose user credentials and bind credentials.

### 24.2 Use least-privilege bind DN

The bind DN should:

- be a dedicated service account,
- have read-only permissions,
- be limited to required OUs if possible,
- have a strong rotated password,
- be monitored for lockout and failed bind attempts.

### 24.3 Protect the bind password

- Store bind password in a Kubernetes `Secret`, not a ConfigMap.
- Restrict RBAC access to `openshift-config` and any LDAP sync namespace.
- Avoid printing decoded secrets in shared terminals.
- Rotate periodically.

### 24.4 Monitor certificate expiry

Monitor:

- LDAP server certificate expiry,
- intermediate CA expiry,
- root CA expiry,
- Authentication Operator health,
- OAuth pod restart or rollout failures,
- LDAP bind failure spikes.

Useful command:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com </dev/null 2>/dev/null \
| openssl x509 -noout -dates -subject -issuer
```

### 24.5 Use stable DNS names

Prefer:

```text
ldaps://ldap.example.com:636
```

Avoid hardcoding individual IP addresses unless unavoidable, because certificates are validated against DNS names, not IPs, unless the certificate contains an IP SAN.

### 24.6 Keep identity provider name stable

The identity provider name is part of the OpenShift identity naming model. Changing it can create new identities for the same LDAP users.

For example:

```yaml
name: ldap-provider
```

Changing this later should be treated as an identity migration activity.

## 26. Disaster recovery considerations

LDAP certificate misconfiguration can lock out normal users.

Before changing LDAP trust:

1. Confirm break-glass access exists.
2. Keep `kubeadmin` or another emergency admin path until LDAP is verified.
3. Back up OAuth object.
4. Back up CA ConfigMap and bind secret metadata.
5. Have LDAP server certificate chain ready.
6. Test from inside the cluster.

Backup commands:

```bash
mkdir -p auth-backup

oc get oauth cluster -o yaml > auth-backup/oauth-cluster.yaml
oc -n openshift-config get configmap ldap-ca -o yaml > auth-backup/ldap-ca.yaml
oc -n openshift-config get secret ldap-bind-secret -o yaml > auth-backup/ldap-bind-secret.yaml
```

Rollback:

```bash
oc apply -f auth-backup/oauth-cluster.yaml
oc apply -f auth-backup/ldap-ca.yaml
```

Be careful restoring old secrets from files; ensure the secret data is still valid and protected.

## 27. Exam and interview notes

Remember these points for OpenShift admin exams and interviews:

- LDAP IdP CA trust uses a ConfigMap in `openshift-config`.
- The key must be `ca.crt`.
- OAuth LDAP config references `ca.name`, not a file path.
- LDAP group sync config commonly references CA by file path, such as `/etc/ldap-ca/ca.crt`.
- For OAuth LDAP IdP, `bindPassword` secret key must be `bindPassword`.
- `ldaps://` uses TLS.
- `ldap://` with `insecure: false` uses StartTLS.
- `insecure: true` disables TLS and cannot be used with `ldaps://`.
- Missing or invalid CA ConfigMap can cause the identity provider not to be honored.
- Certificate SAN must match the LDAP URL hostname.
- Always test OAuth login after changes.
- Always check `oc get co authentication` and OAuth logs when troubleshooting.

## 30. Final mental model

Think of LDAP certificate trust in OpenShift like this:

```text
LDAP server certificate
        |
        | signed by
        v
Corporate LDAP CA / Intermediate CA
        |
        | stored as ca.crt
        v
ConfigMap in openshift-config
        |
        | referenced by ldap.ca.name
        v
OAuth cluster configuration
        |
        | used by OAuth server
        v
Secure LDAP authentication
```

If authentication fails, ask these questions in order:

1. Can OpenShift reach the LDAP hostname and port?
2. Does the LDAP server present the expected certificate?
3. Does the certificate SAN match the LDAP URL hostname?
4. Does the CA bundle in `openshift-config` trust that certificate?
5. Is the key named exactly `ca.crt`?
6. Is `insecure: false` set correctly?
7. Is the LDAP bind DN/password correct?
8. Does the LDAP URL search return exactly one user?
9. Did OAuth pods roll out/reload successfully?
10. What do OAuth logs say?

That is the practical senior-admin approach to LDAP certificate trust in OpenShift.
