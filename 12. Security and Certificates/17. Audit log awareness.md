# Audit Log Awareness in OpenShift Security and Certificates

**Audience:** Advanced OpenShift Administration / DO380-style operations  
**Experience level:** Written for administrators with around 10 years of Linux, Kubernetes, DevOps, and platform operations experience  
**Scope:** OpenShift Container Platform 4.x, API-server audit logs, security investigation, certificate-related change awareness, forwarding, retention, and troubleshooting  
**Primary tools:** `oc`, `oc adm node-logs`, `jq`, `oc adm must-gather`, OpenShift Logging / `ClusterLogForwarder`

---

## 1. What “Audit Log Awareness” Means

Audit log awareness means you understand how to answer security and operational questions from OpenShift audit records:

- Who performed an action?
- What API object was touched?
- Which namespace was affected?
- Which user, group, service account, or component made the request?
- Was the request allowed or denied?
- Was it authentication-related, authorization-related, or normal controller activity?
- Did someone change RBAC, SCC, OAuth, routes, certificates, secrets, API server configuration, or ingress configuration?
- Is the audit trail reliable enough for troubleshooting, compliance, and incident response?

In OpenShift, audit logs are not just “logs.” They are the cluster’s security timeline for API activity. They help reconstruct what happened when someone deletes a project, patches a `Secret`, creates a `ClusterRoleBinding`, changes an `APIServer` certificate setting, updates an OAuth identity provider, or accesses sensitive resources.

A senior OpenShift administrator must know that audit logs are generated mainly at the API server layer. They record API requests handled by OpenShift and Kubernetes API servers. This is different from:

- Application logs
- Pod container logs
- Node system logs
- Journal logs
- Kubernetes `Event` objects
- Operator controller logs
- Ingress/router access logs
- Network flow logs

Audit logs tell you about API intent and API results. They do not automatically tell you everything that happened inside a container, inside an application, or on the network.

## 2. Why Audit Logs Matter in Security and Certificates

In the Security and Certificates domain, audit logs are important because most security-sensitive OpenShift changes are API operations.

Examples:

| Security area | Typical API object | Why audit logs matter |
|---|---|---|
| RBAC | `RoleBinding`, `ClusterRoleBinding`, `Role`, `ClusterRole` | Identify who granted access or escalated privileges |
| SCC | `SecurityContextConstraints` | Detect changes that allow privileged, hostPath, hostNetwork, or anyuid execution |
| Secrets | `Secret` | Track reads/writes of sensitive material at metadata level |
| Certificates | `Secret`, `ConfigMap`, `APIServer`, `IngressController`, `Route`, `OAuth` | Detect certificate rotation, replacement, or trust bundle changes |
| OAuth / Identity | `OAuth`, `Secret`, `ConfigMap`, identity/user resources | Investigate login failures and identity provider changes |
| Routes / TLS | `Route`, router certificates, ingress secrets | Detect external exposure or TLS cert changes |
| NetworkPolicy | `NetworkPolicy` | Identify who changed connectivity rules |
| Project security | `Namespace`, `Project`, `ResourceQuota`, `LimitRange` | Investigate tenant isolation issues |
| ServiceAccount | `ServiceAccount`, `Secret`, token-related resources | Track automation identity behavior |
| API server | `APIServer`, `Authentication`, `Proxy`, `Scheduler`, `ControllerManager` | Detect cluster-wide configuration changes |

For certificate operations specifically, audit logs help you answer questions such as:

- Who updated the default ingress certificate secret?
- Who patched the API server named certificate configuration?
- Who changed the trusted CA bundle ConfigMap?
- Who modified an OAuth identity provider secret?
- Who created or replaced a route with custom TLS?
- Who accessed a TLS secret?
- Was a certificate secret changed by a human, GitOps controller, cert-manager, External Secrets Operator, or another automation?

## 3. Audit Logs vs Events vs Normal Logs

### 3.1 Audit logs

Audit logs are API request records. They are generated when clients interact with API servers.

Typical clients:

- Human users using `oc`
- Web console users
- Operators
- Controllers
- Kubelets
- Schedulers
- CI/CD systems
- GitOps controllers
- Monitoring components
- External automation
- Service accounts

Audit logs are best for:

- Security investigation
- Compliance evidence
- “Who did what?” analysis
- RBAC decision visibility
- API request tracing
- Change timeline reconstruction

### 3.2 Kubernetes Events

Kubernetes `Event` objects describe cluster activity and resource lifecycle messages.

Examples:

```bash
oc get events -A --sort-by=.lastTimestamp
oc describe pod mypod -n myns
```

Events are best for:

- Pod scheduling failures
- Image pull failures
- PVC binding issues
- Probe failures
- Deployment rollout problems

Events are not a reliable long-term security audit source. They are short-lived and operational.

### 3.3 Pod logs

Pod logs show application/container output.

Examples:

```bash
oc logs deploy/myapp -n myns
oc logs pod/mypod -c mycontainer -n myns
```

Pod logs are best for:

- Application errors
- Startup failures
- Runtime debugging
- App-level authentication or transaction logs

They do not reliably prove who changed OpenShift resources.

### 3.4 Operator logs

Operator logs explain controller reconciliation behavior.

Examples:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift
oc logs -n openshift-apiserver deploy/apiserver
oc logs -n openshift-ingress-operator deploy/ingress-operator
```

Operator logs are useful when audit logs show that a resource changed, but you need to understand how the operator reacted.

## 4. Where Audit Logs Exist in OpenShift

OpenShift has multiple API-related components that can produce audit logs. The important ones are:

| Component | Typical path with `oc adm node-logs` | Purpose |
|---|---|---|
| OpenShift API server | `openshift-apiserver/` | OpenShift-specific APIs such as projects, routes, users, groups, templates, OAuth-related resources |
| Kubernetes API server | `kube-apiserver/` | Core Kubernetes APIs such as pods, secrets, configmaps, RBAC, namespaces, deployments |
| OpenShift OAuth API server | `oauth-apiserver/` | OAuth API resources |
| OpenShift OAuth server | `oauth-server/` | Login and OAuth server activity |

Audit logs are available per control plane node. In a three-master cluster, you can have audit logs from each control plane node.

The practical implication: when investigating an incident, do not check only one master unless you know which API server handled the request. Use `--role=master` to list logs across all control plane nodes.

## 6. Understanding an Audit Log Event

A typical audit log line is JSON. Each line is one audit event.

Example simplified event:

```json
{
  "kind": "Event",
  "apiVersion": "audit.k8s.io/v1",
  "level": "Metadata",
  "auditID": "cfce8a0b-b5f5-4365-8c9f-79c1227d10f9",
  "stage": "ResponseComplete",
  "requestURI": "/api/v1/namespaces/demo/secrets/db-password",
  "verb": "get",
  "user": {
    "username": "system:serviceaccount:demo:app-sa",
    "groups": [
      "system:serviceaccounts",
      "system:serviceaccounts:demo",
      "system:authenticated"
    ]
  },
  "sourceIPs": ["10.128.2.15"],
  "userAgent": "my-controller/v1.0",
  "objectRef": {
    "resource": "secrets",
    "namespace": "demo",
    "name": "db-password",
    "apiVersion": "v1"
  },
  "responseStatus": {
    "code": 200
  },
  "requestReceivedTimestamp": "2026-07-03T10:00:00.000000Z",
  "stageTimestamp": "2026-07-03T10:00:00.010000Z",
  "annotations": {
    "authorization.k8s.io/decision": "allow",
    "authorization.k8s.io/reason": "RBAC: allowed by RoleBinding..."
  }
}
```

### 6.1 Important fields

| Field | Meaning | Practical use |
|---|---|---|
| `level` | Audit level used for this event | Shows whether metadata or body was logged |
| `auditID` | Unique ID for a request | Correlates multiple stages of same request |
| `stage` | Request processing stage | Usually `ResponseComplete` is most useful |
| `requestURI` | Full API path | Useful when `objectRef` is missing or incomplete |
| `verb` | API action such as `get`, `list`, `create`, `update`, `patch`, `delete` | Separates read vs write activity |
| `user.username` | User or service account identity | Main “who did it?” field |
| `user.groups` | Groups of the requester | Useful for RBAC context |
| `sourceIPs` | Source IPs observed by API server | Useful for tracing client location |
| `userAgent` | Client program | Identifies `oc`, controller, browser, operator, GitOps, CI/CD |
| `objectRef` | Target API object | Main “what was touched?” field |
| `responseStatus.code` | HTTP response code | `200`, `201`, `403`, `404`, etc. |
| `requestReceivedTimestamp` | Time request reached API server | Timeline reconstruction |
| `annotations.authorization.k8s.io/decision` | RBAC allow/deny decision | Authorization analysis |
| `annotations.authorization.k8s.io/reason` | Why RBAC allowed/denied | Shows role or binding reason |

### 6.2 Important HTTP response codes

| Code | Meaning | Investigation note |
|---|---|---|
| `200` | OK | Successful read/update depending on verb |
| `201` | Created | Resource created |
| `202` | Accepted | Often async delete accepted |
| `302` | Redirect | Common in OAuth/login flow |
| `400` | Bad request | Invalid API request |
| `401` | Unauthorized | Authentication failed or missing |
| `403` | Forbidden | Authenticated but not authorized |
| `404` | Not found | Object does not exist or path incorrect |
| `409` | Conflict | Resource version conflict |
| `422` | Unprocessable entity | Validation/admission failure |
| `500` | Server error | API server/internal issue |

## 7. Request Stages in Audit Logs

Kubernetes audit events can be emitted at different stages of request handling.

Common stages:

| Stage | Meaning |
|---|---|
| `RequestReceived` | API server received the request |
| `ResponseStarted` | Response headers sent, usually for long-running requests |
| `ResponseComplete` | Request completed normally |
| `Panic` | Request caused a panic |

For most administration investigations, filter on:

```jq
select(.stage == "ResponseComplete")
```

Why? Because `ResponseComplete` usually includes the final response code and authorization result.

Example:

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.stage == "ResponseComplete")'
```

## 8. Audit Levels and OpenShift Audit Profiles

OpenShift provides predefined audit policy profiles. These control how much information is logged for API requests.

### 8.1 Common audit levels

| Level | Meaning |
|---|---|
| `None` | Do not log matching events |
| `Metadata` | Log request metadata but not request or response body |
| `Request` | Log metadata and request body |
| `RequestResponse` | Log metadata, request body, and response body where applicable |

In OpenShift administration, you normally work with OpenShift audit profiles rather than manually editing low-level Kubernetes audit policy files.

### 8.2 OpenShift predefined audit profiles

| Profile | Behavior | Operational use |
|---|---|---|
| `Default` | Logs metadata for read and write requests. Does not log request bodies except specific OAuth token requests. | Normal production baseline |
| `WriteRequestBodies` | Logs metadata for all requests and request bodies for write operations such as `create`, `update`, `patch`, `delete`, `deletecollection`. | Temporary deep troubleshooting of write changes |
| `AllRequestBodies` | Logs metadata and request bodies for read and write requests such as `get`, `list`, `create`, `update`, `patch`. | Very heavy; use with strong justification |
| `None` | Disables audit logging for requests. Custom rules are ignored. | Avoid except exceptional cases with documented risk approval |

Important senior-admin point:

> More audit detail increases CPU, memory, disk I/O, storage volume, forwarding load, and analysis complexity.

Do not casually switch a production cluster to `AllRequestBodies`. Use it only when required, for a controlled duration, and with storage/forwarding capacity reviewed.

### 8.3 Sensitive resource handling

Sensitive resources such as `Secret`, `Route`, and `OAuthClient` are not logged beyond metadata level in OpenShift audit profiles. This protects sensitive values from being written into audit logs.

Practical meaning:

- Audit logs can show that a secret was read, created, updated, patched, or deleted.
- They should not be treated as a safe way to view secret contents.
- Do not expect certificate private key material, tokens, or password values to appear in audit logs.
- If secret values appear due to some external application logging, that is a separate security issue.

## 9. Checking the Current Audit Profile

### 9.1 View the APIServer resource

```bash
oc get apiserver cluster -o yaml
```

### 9.2 Extract the audit profile only

```bash
oc get apiserver cluster -o jsonpath='{.spec.audit.profile}{"\n"}'
```

If nothing is explicitly shown, the cluster is normally using the default behavior.

### 9.3 Show audit config with `yq`

```bash
oc get apiserver cluster -o yaml | yq '.spec.audit'
```

## 10. Changing the Audit Profile

### 10.1 Edit interactively

```bash
oc edit apiserver cluster
```

Example:

```yaml
spec:
  audit:
    profile: WriteRequestBodies
```

### 10.2 Patch to `WriteRequestBodies`

```bash
oc patch apiserver cluster --type=merge \
  -p '{"spec":{"audit":{"profile":"WriteRequestBodies"}}}'
```

### 10.3 Patch back to `Default`

```bash
oc patch apiserver cluster --type=merge \
  -p '{"spec":{"audit":{"profile":"Default"}}}'
```

### 10.4 Patch to `None` — not recommended

```bash
oc patch apiserver cluster --type=merge \
  -p '{"spec":{"audit":{"profile":"None"}}}'
```

Do not use `None` in production unless your organization has explicitly accepted the security, compliance, and support risk.

### 10.5 Watch cluster operators after change

```bash
oc get co
oc get co kube-apiserver openshift-apiserver authentication
```

Changing audit policy can cause API-related operators to roll out configuration changes. Watch for degraded/progressing states.

```bash
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-apiserver -o wide
oc get pods -n openshift-authentication -o wide
```

## 11. Practical `jq` Filters for Audit Logs

Install `jq` on your workstation or use a debug/admin host where it is available.

### 11.1 Filter by username

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.user.username == "bob")'
```

### 11.2 Filter by service account

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.user.username == "system:serviceaccount:demo:app-sa")'
```

### 11.3 Filter by namespace

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.namespace == "demo")'
```

### 11.4 Filter by resource type

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.resource == "secrets")'
```

### 11.5 Filter by verb

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.verb == "delete")'
```

### 11.6 Filter writes only

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.verb | IN("create","update","patch","delete","deletecollection"))'
```

### 11.7 Filter denied requests

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.annotations["authorization.k8s.io/decision"] == "forbid")'
```

### 11.8 Filter HTTP 403

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.responseStatus.code == 403)'
```

### 11.9 Filter failed authentication / OAuth login errors

```bash
oc adm node-logs master-0.example.com --path=oauth-server/audit.log \
| jq 'select(.annotations["authentication.openshift.io/decision"] == "error")'
```

### 11.10 Filter by user agent

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.userAgent | test("oc/|kubectl/"))'
```

### 11.11 Display compact useful fields

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq -r '
  [
    .requestReceivedTimestamp,
    .verb,
    .user.username,
    .objectRef.namespace,
    .objectRef.resource,
    .objectRef.name,
    .responseStatus.code,
    .annotations["authorization.k8s.io/decision"],
    .userAgent
  ] | @tsv'
```

### 11.12 Filter role binding and cluster role binding changes

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    (.objectRef.resource == "rolebindings" or .objectRef.resource == "clusterrolebindings")
    and (.verb | IN("create","update","patch","delete"))
  )'
```

### 11.13 Filter SCC changes

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "securitycontextconstraints"
    and (.verb | IN("create","update","patch","delete"))
  )'
```

### 11.14 Filter secret access

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "secrets"
    and (.verb | IN("get","list","watch","create","update","patch","delete"))
  )'
```

### 11.15 Filter certificate-related secret changes

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "secrets"
    and (.objectRef.name | test("tls|cert|ca|certificate|router|ingress|oauth"; "i"))
    and (.verb | IN("create","update","patch","delete"))
  )'
```

### 11.16 Filter API server certificate config changes

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "apiservers"
    and .objectRef.name == "cluster"
    and (.verb | IN("update","patch"))
  )'
```

### 11.17 Filter ingress controller changes

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "ingresscontrollers"
    and (.verb | IN("create","update","patch","delete"))
  )'
```

### 11.18 Filter route TLS changes

Routes are OpenShift API objects, so check the OpenShift API server audit log:

```bash
oc adm node-logs master-0.example.com --path=openshift-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "routes"
    and (.verb | IN("create","update","patch","delete"))
  )'
```

### 11.19 Filter OAuth config changes

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "oauths"
    and .objectRef.name == "cluster"
    and (.verb | IN("update","patch"))
  )'
```

### 11.20 Filter anonymous activity

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.user.username == "system:anonymous")'
```

### 11.21 Filter impersonation usage

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.impersonatedUser != null)'
```

### 11.22 Filter delete collection operations

`deletecollection` can be dangerous because it may delete many objects.

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.verb == "deletecollection")'
```

## 12. Investigation Playbooks

### 12.1 Who deleted a namespace/project?

Check Kubernetes API server:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "namespaces"
    and .verb == "delete"
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    name: .objectRef.name,
    code: .responseStatus.code,
    sourceIPs: .sourceIPs,
    userAgent: .userAgent
  }'
```

Also check OpenShift API server for project-related resources:

```bash
oc adm node-logs --role=master --path=openshift-apiserver/audit.log \
| jq 'select(
    (.objectRef.resource == "projects" or .requestURI | test("/apis/project.openshift.io"))
    and .verb == "delete"
  )'
```

### 12.2 Who deleted a deployment?

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "deployments"
    and .objectRef.namespace == "demo"
    and .verb == "delete"
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    namespace: .objectRef.namespace,
    deployment: .objectRef.name,
    code: .responseStatus.code,
    reason: .annotations["authorization.k8s.io/reason"],
    userAgent: .userAgent
  }'
```

### 12.3 Who granted cluster-admin?

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "clusterrolebindings"
    and (.verb | IN("create","update","patch"))
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    binding: .objectRef.name,
    code: .responseStatus.code,
    userAgent: .userAgent
  }'
```

With `WriteRequestBodies`, you might see request body details for non-sensitive resources, which can help identify the exact subject and roleRef. With `Default`, you usually identify the binding name and then inspect current or historical Git/SIEM records.

### 12.4 Who changed SCC permissions?

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "securitycontextconstraints"
    and (.verb | IN("update","patch","create","delete"))
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    scc: .objectRef.name,
    verb: .verb,
    code: .responseStatus.code
  }'
```

Also check RBAC bindings that grant SCC use indirectly:

```bash
oc get clusterrole | grep -i scc
oc get clusterrolebinding | grep -i scc
```

### 12.5 Who accessed a secret?

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "secrets"
    and .objectRef.namespace == "demo"
    and .objectRef.name == "db-password"
    and (.verb | IN("get","list","watch"))
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    verb: .verb,
    secret: .objectRef.name,
    code: .responseStatus.code,
    sourceIPs: .sourceIPs,
    userAgent: .userAgent
  }'
```

Important interpretation:

- A `get` on a secret is direct read access.
- A `list` on secrets can expose many secrets.
- A `watch` on secrets is also sensitive.
- Normal controllers may read secrets as part of platform operations.
- A workload using a mounted secret might not generate repeated API `get` events every time the app reads the file inside the container.

### 12.6 Who changed an API certificate secret?

For API named certificates, the certificate data is usually stored in a secret and referenced by cluster configuration.

Search secret changes:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "secrets"
    and (.objectRef.name | test("api|cert|tls|ca"; "i"))
    and (.verb | IN("create","update","patch","delete"))
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    namespace: .objectRef.namespace,
    secret: .objectRef.name,
    verb: .verb,
    code: .responseStatus.code,
    userAgent: .userAgent
  }'
```

Search APIServer config changes:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "apiservers"
    and .objectRef.name == "cluster"
    and (.verb | IN("update","patch"))
  )'
```

### 12.7 Who changed the default ingress certificate?

Default ingress certificate changes usually involve:

- A secret in `openshift-ingress`
- The `IngressController` resource in `openshift-ingress-operator`

Check secret changes:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.namespace == "openshift-ingress"
    and .objectRef.resource == "secrets"
    and (.verb | IN("create","update","patch","delete"))
  )'
```

Check ingress controller changes:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "ingresscontrollers"
    and (.verb | IN("update","patch"))
  )'
```

Then inspect current state:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get secret -n openshift-ingress
```

### 12.8 Who changed OAuth / identity provider configuration?

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "oauths"
    and .objectRef.name == "cluster"
    and (.verb | IN("update","patch"))
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    verb: .verb,
    code: .responseStatus.code,
    userAgent: .userAgent
  }'
```

Also check related secrets and configmaps:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    (.objectRef.namespace == "openshift-config" or .objectRef.namespace == "openshift-authentication")
    and (.objectRef.resource == "secrets" or .objectRef.resource == "configmaps")
    and (.verb | IN("create","update","patch","delete"))
  )'
```

### 12.9 Who created a route with custom TLS?

Route objects are OpenShift API objects:

```bash
oc adm node-logs --role=master --path=openshift-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "routes"
    and (.verb | IN("create","update","patch"))
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    namespace: .objectRef.namespace,
    route: .objectRef.name,
    code: .responseStatus.code,
    userAgent: .userAgent
  }'
```

Then inspect route TLS configuration:

```bash
oc get route <route_name> -n <namespace> -o yaml
```

### 12.10 Who changed NetworkPolicy?

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.resource == "networkpolicies"
    and (.verb | IN("create","update","patch","delete"))
  ) | {
    time: .requestReceivedTimestamp,
    user: .user.username,
    namespace: .objectRef.namespace,
    policy: .objectRef.name,
    verb: .verb,
    code: .responseStatus.code
  }'
```

### 12.11 Who used `kubeadmin`?

OAuth login attempts:

```bash
oc adm node-logs --role=master --path=oauth-server/audit.log \
| jq 'select(
    .annotations["authentication.openshift.io/username"] == "kubeadmin"
  )'
```

API usage:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(.user.username == "kube:admin" or .user.username == "kubeadmin")'
```

In many clusters, `kubeadmin` should be removed or tightly controlled after identity providers and admin users are configured.

## 14. Audit Log Forwarding and Retention Strategy

Node-local audit logs are useful for immediate troubleshooting, but production security operations should not rely only on local node log files.

A mature production approach:

1. Collect audit logs from control plane nodes.
2. Forward audit logs to a centralized logging or SIEM platform.
3. Protect forwarded logs from tampering.
4. Apply retention according to compliance requirements.
5. Restrict access to audit logs because they contain sensitive metadata.
6. Alert on suspicious patterns.
7. Test that audit forwarding still works after upgrades.

OpenShift Logging can collect and forward audit logs using `ClusterLogForwarder`, depending on the Logging Operator version and configuration.

### 14.1 Common destination types

Audit logs may be forwarded to:

- LokiStack
- Splunk
- Elasticsearch / OpenSearch
- Kafka
- Syslog receiver
- Cloud SIEM
- Enterprise log lake
- Security analytics platform

### 14.2 Example conceptual `ClusterLogForwarder`

The exact API version and fields can differ between OpenShift Logging releases. Treat this as a conceptual example and verify against your installed Logging Operator version.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: audit-forwarder
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
    - name: audit-input
      type: audit
  outputs:
    - name: external-siem
      type: syslog
      syslog:
        url: tls://siem.example.com:6514
  pipelines:
    - name: audit-to-siem
      inputRefs:
        - audit-input
      outputRefs:
        - external-siem
```

### 14.3 Required RBAC concept

The log collector service account needs permissions to collect the relevant log types. For audit logs, expect a role such as `collect-audit-logs` depending on Logging Operator version.

Example style:

```bash
oc create sa collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z collector -n openshift-logging
```

Also grant infrastructure/application collection roles if the same collector handles those log streams.

### 14.4 Security requirements for audit forwarding

For audit logs, require:

- TLS encryption in transit
- Authentication to log destination
- Restricted read access
- Immutable or tamper-evident storage where possible
- Time synchronization across nodes
- Retention policy
- Backup policy
- Monitoring for pipeline failure
- Alerting on sudden volume drop
- Alerting on collector crash loops
- Alerting on destination connection failure

## 15. Performance and Capacity Considerations

Audit logging has overhead. The more you log, the greater the cost.

### 15.1 Main overhead sources

| Source | Impact |
|---|---|
| Request body logging | More CPU/memory on API servers |
| High API QPS | More audit events |
| Verbose profiles | More disk I/O |
| Forwarding audit logs | More network and collector CPU |
| SIEM parsing | More indexing cost |
| Long retention | More storage cost |

### 15.2 High-volume sources

Expect high audit volume from:

- Controllers
- Operators
- Kubelets
- Monitoring stack
- GitOps controllers
- CI/CD pipelines
- Service mesh controllers
- Autoscalers
- Security scanners
- Backup tools
- Admission webhooks
- Workloads using dynamic Kubernetes API clients

### 15.3 Production recommendations

Use `Default` for normal production unless a stronger requirement exists.

Use `WriteRequestBodies` temporarily when:

- You are troubleshooting unauthorized or unexpected writes.
- You need more detail for an incident.
- The target resources are not sensitive resources limited to metadata.
- You have enough disk and forwarding capacity.

Avoid `AllRequestBodies` unless:

- There is a specific security/compliance requirement.
- You have tested the performance impact.
- You have approval from platform/security leadership.
- You have a rollback plan.

Avoid `None`.

## 16. Common Mistakes

### Mistake 1: Checking only one master node

In HA clusters, any control plane node may handle the request.

Better:

```bash
oc adm node-logs --role=master --path=kube-apiserver/
```

Then search across all relevant logs.

### Mistake 2: Looking only at `kube-apiserver`

Routes, projects, users, groups, and some OpenShift-specific resources can appear in `openshift-apiserver`.

Check both when unsure:

```bash
oc adm node-logs --role=master --path=kube-apiserver/
oc adm node-logs --role=master --path=openshift-apiserver/
```

### Mistake 3: Confusing `403` and `401`

- `401 Unauthorized` usually means authentication failed or credentials are missing.
- `403 Forbidden` usually means authentication succeeded but authorization denied.

### Mistake 4: Assuming audit logs contain secret values

OpenShift protects sensitive resources from body-level logging beyond metadata in the standard profiles.

### Mistake 5: Forgetting service accounts

Many important actions are performed by service accounts, not human users.

Example usernames:

```text
system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
system:serviceaccount:openshift-monitoring:prometheus-k8s
system:serviceaccount:myproject:pipeline
```

### Mistake 6: Ignoring `userAgent`

The `user.username` tells you the identity. The `userAgent` often tells you the tool.

Examples:

- `oc/...`
- `kubectl/...`
- `argocd-application-controller`
- `openshift-controller-manager`
- `cluster-version-operator`
- `Mozilla/...` for browser/web console/OAuth flow

### Mistake 7: Not correlating with GitOps

If Argo CD or another GitOps controller changed a resource, the audit user may be the GitOps service account. You must then check Git history, Argo CD application history, and repo commits to identify the human source.

### Mistake 8: Not preserving evidence

For incidents, immediately collect:

```bash
oc adm must-gather -- /usr/bin/gather_audit_logs
```

Then archive the resulting directory:

```bash
tar cvaf audit-must-gather-$(date +%F-%H%M).tar.gz must-gather.local.*
```

## 18. Building a Cluster-Wide Audit Search Script

For repeated investigations, use a small shell script.

```bash
#!/usr/bin/env bash
set -euo pipefail

PATH_NAME="${1:-kube-apiserver/audit.log}"
JQ_FILTER="${2:-.}"

for node in $(oc get nodes -l node-role.kubernetes.io/master= -o name | cut -d/ -f2); do
  echo "### NODE: $node PATH: $PATH_NAME" >&2
  oc adm node-logs "$node" --path="$PATH_NAME" \
  | jq -c "$JQ_FILTER" \
  | sed "s/^/{\"node\":\"$node\",\"event\":/" \
  | sed 's/$/}/'
done
```

Example usage:

```bash
./audit-search.sh kube-apiserver/audit.log \
'select(.objectRef.resource=="clusterrolebindings" and (.verb=="create" or .verb=="patch"))'
```

Note: This script is intentionally simple. For production use, prefer centralized forwarding and search.

## 19. Security Alert Ideas

A mature OpenShift platform should alert on high-risk audit patterns.

### 19.1 RBAC escalation

Alert when:

- `clusterrolebindings` are created/updated/patched
- `cluster-admin` is granted
- Users are added to privileged groups
- Bindings are changed in sensitive namespaces

### 19.2 SCC privilege expansion

Alert when:

- SCCs are changed
- `privileged` SCC use is granted
- `anyuid`, `hostmount-anyuid`, or custom powerful SCCs are granted unexpectedly

### 19.3 Secret access anomalies

Alert when:

- A human user lists many secrets
- A service account reads secrets outside normal namespace
- Secret access occurs from unexpected source IP
- Secret read volume spikes

### 19.4 Certificate material changes

Alert when:

- TLS secrets are created/updated/deleted in `openshift-ingress`
- Secrets in `openshift-config` change
- `APIServer` named certificates change
- `IngressController` default certificate changes
- OAuth CA bundle changes
- Proxy trusted CA changes

### 19.5 Authentication anomalies

Alert when:

- Repeated failed OAuth login attempts occur
- `kubeadmin` is used
- `system:anonymous` performs unusual requests
- New identity provider configuration is applied

### 19.6 Destructive operations

Alert when:

- Namespaces are deleted
- `deletecollection` is used
- CRDs are deleted
- StorageClasses/PVs/PVCs are deleted
- NetworkPolicies are deleted

## 20. Audit Logs and RBAC Troubleshooting

Audit logs are excellent for RBAC troubleshooting because they show allow/deny decisions and reasons.

### 20.1 User says: “I cannot create project”

Check:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .user.username == "john"
    and .responseStatus.code == 403
  ) | {
    time: .requestReceivedTimestamp,
    verb: .verb,
    uri: .requestURI,
    resource: .objectRef.resource,
    reason: .annotations["authorization.k8s.io/reason"]
  }'
```

Also verify:

```bash
oc auth can-i create projects --as=john
oc auth can-i create namespaces --as=john
```

### 20.2 User says: “I cannot access a namespace”

```bash
oc auth can-i get pods -n demo --as=harry
oc get rolebinding -n demo
oc get clusterrolebinding | grep harry
```

Audit denied events:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(.user.username == "harry" and .responseStatus.code == 403)'
```

### 20.3 ServiceAccount cannot run privileged workload

Audit logs might show forbidden actions, but SCC admission failures are often easier to see in pod events and descriptions:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
oc auth can-i use scc/anyuid --as=system:serviceaccount:<namespace>:<sa>
```

Still check audit logs for SCC binding changes:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.resource=="clusterrolebindings" and (.verb | IN("create","patch","update")))'
```

## 21. Audit Logs and NetworkPolicy Troubleshooting

NetworkPolicy behavior is not directly proven by API audit logs. Audit logs show who created, changed, or deleted a `NetworkPolicy`.

They do not prove packet-level allow/deny.

For NetworkPolicy issues:

1. Use audit logs to see who changed policies.
2. Use `oc get networkpolicy -n <ns> -o yaml`.
3. Check pod labels and namespace labels.
4. Test traffic using a debug pod.
5. Check network observability/flow logs if available.

Audit filter:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.resource=="networkpolicies" and (.verb | IN("create","update","patch","delete")))'
```

## 22. Audit Logs and Image Pull Secrets

Audit logs can show:

- Secret creation/update/delete
- ServiceAccount patching
- Pod creation referencing image pull secrets
- Deployment changes that introduce a private image

Useful filters:

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    (.objectRef.resource == "secrets" and (.objectRef.name | test("pull|docker|registry|image"; "i")))
    or (.objectRef.resource == "serviceaccounts")
    or (.objectRef.resource == "pods" and .verb == "create")
  )'
```

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

## 23. Audit Logs and Secret Management

Audit awareness for secrets should answer:

- Who created the secret?
- Who updated it?
- Who deleted it?
- Who read it?
- Was it read by a human or service account?
- Was it accessed from an unexpected IP?
- Was it listed across a namespace?
- Was it copied to another namespace?
- Did a GitOps or External Secrets controller manage it?

Filters:

```bash
# Secret writes
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.resource=="secrets" and (.verb | IN("create","update","patch","delete")))'

# Secret reads
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.resource=="secrets" and (.verb | IN("get","list","watch")))'
```

Interpretation warning:

- A secret mounted into a pod is consumed by kubelet and projected into the container filesystem.
- Application reads from the mounted file do not create new API audit events.
- API audit tells you API access, not every in-container read.

## 25. Advanced Correlation Approach

Senior administrators rarely rely on a single log line. Use correlation.

### 25.1 Correlate by time

Audit log:

```text
2026-07-03T10:00:01Z user patched deployment
```

Then check:

```bash
oc rollout history deploy/myapp -n demo
oc get events -n demo --sort-by=.lastTimestamp
oc logs deploy/myapp -n demo --since=30m
```

### 25.2 Correlate by `auditID`

If multiple stages exist for the same request:

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(.auditID == "cfce8a0b-b5f5-4365-8c9f-79c1227d10f9")'
```

### 25.3 Correlate by service account

If the actor is a GitOps controller:

```text
system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Then check:

```bash
oc get applications -n openshift-gitops
oc describe application <app> -n openshift-gitops
```

Also check Git commit history.

### 25.4 Correlate by source IP

Source IP can identify:

- Bastion host
- CI runner
- Admin workstation
- Internal pod IP
- OAuth proxy/router path
- NAT/load balancer path

But be careful: source IP may be affected by proxies, load balancers, and network design.

## 26. Audit Logging in Incident Response

### 26.1 Immediate response checklist

When suspicious activity is reported:

```bash
# 1. Preserve audit logs
oc adm must-gather -- /usr/bin/gather_audit_logs

# 2. Collect cluster state
oc adm must-gather

# 3. Capture suspicious resources
oc get clusterrolebinding -o yaml > clusterrolebindings-$(date +%F-%H%M).yaml
oc get rolebinding -A -o yaml > rolebindings-$(date +%F-%H%M).yaml
oc get scc -o yaml > scc-$(date +%F-%H%M).yaml
oc get secret -A > secret-list-$(date +%F-%H%M).txt
oc get oauth cluster -o yaml > oauth-cluster-$(date +%F-%H%M).yaml
```

### 26.2 Investigation questions

Ask:

1. What was changed?
2. Who changed it?
3. Was it allowed or denied?
4. Was it a human, service account, controller, or external system?
5. Which client/userAgent was used?
6. Which source IP was used?
7. Did the same actor perform other actions?
8. Did it touch secrets, RBAC, SCC, OAuth, routes, certificates, or network policies?
9. Was the action expected by GitOps, CI/CD, or an operator?
10. Do we need to rotate credentials or certificates?

### 26.3 Common containment actions

Depending on evidence:

```bash
# Disable suspicious user access by removing role bindings
oc delete clusterrolebinding <binding>

# Remove namespace role binding
oc delete rolebinding <binding> -n <namespace>

# Rotate a secret
oc delete secret <secret> -n <namespace>
oc create secret generic <secret> ...

# Remove suspicious route
oc delete route <route> -n <namespace>

# Restore network policy
oc apply -f known-good-networkpolicy.yaml

# Revert OAuth config from known-good YAML
oc apply -f oauth-known-good.yaml
```

Do not destroy evidence before collecting it.

## 27. Compliance and Governance

Audit logs support compliance evidence, but only if they are:

- Enabled
- Collected centrally
- Protected
- Time-synchronized
- Retained long enough
- Searchable
- Access-controlled
- Tested

### 27.1 Minimum governance controls

| Control | Recommendation |
|---|---|
| Time sync | Ensure NTP/chrony is healthy on nodes and log platforms |
| Retention | Match legal/compliance requirements |
| Access | Restrict audit log access to platform/security admins |
| Integrity | Forward to tamper-resistant storage |
| Encryption | Use TLS for forwarding |
| Monitoring | Alert on collector or pipeline failure |
| Change control | Record audit profile changes |
| Review | Periodically review high-risk audit events |

### 27.2 Audit profile change governance

Any change to the audit profile should include:

- Reason
- Requested by
- Approved by
- Start time
- End time or rollback plan
- Expected impact
- Storage capacity check
- SIEM capacity check
- Final rollback confirmation

Example change record:

```text
Change: Temporarily set APIServer audit profile to WriteRequestBodies
Reason: Investigate unexpected RBAC changes
Window: 2026-07-03 22:00 to 23:00 IST
Approval: Security Lead + Platform Lead
Rollback: Patch profile back to Default
Validation: oc get apiserver cluster -o jsonpath='{.spec.audit.profile}'
```

For Advanced OpenShift Administration or real-world interviews, you should be comfortable with the following.

### 28.1 Must-know commands

```bash
oc adm node-logs --role=master --path=kube-apiserver/
oc adm node-logs --role=master --path=openshift-apiserver/
oc adm node-logs --role=master --path=oauth-apiserver/

```

### 28.2 Must-know investigation filters

```bash
# Denied requests
jq 'select(.responseStatus.code == 403)'

# Writes
jq 'select(.verb | IN("create","update","patch","delete","deletecollection"))'

# Secret access
jq 'select(.objectRef.resource == "secrets")'

# RBAC changes
jq 'select(.objectRef.resource == "rolebindings" or .objectRef.resource == "clusterrolebindings")'

# OAuth login errors
jq 'select(.annotations["authentication.openshift.io/decision"] == "error")'

# One user
jq 'select(.user.username == "bob")'
```

### 28.3 Interview answer: What are OpenShift audit logs?

OpenShift audit logs are API server records that capture security-relevant API activity, including the user or service account, verb, target object, namespace, source IP, user agent, response code, and authorization decision. They help administrators investigate who performed a change, whether access was allowed or denied, and what sensitive resources such as secrets, RBAC bindings, SCCs, routes, OAuth configuration, or certificate-related objects were touched.

### 28.4 Interview answer: Where do you check audit logs?

Use `oc adm node-logs` against control plane nodes. Check `kube-apiserver/audit.log` for Kubernetes resources, `openshift-apiserver/audit.log` for OpenShift-specific resources, `oauth-apiserver/audit.log` for OAuth API resources, and `oauth-server/audit.log` for login/OAuth server activity.

### 28.5 Interview answer: How do you collect audit logs for support?

Run:

```bash
oc adm must-gather -- /usr/bin/gather_audit_logs
```

Then compress and securely share the generated must-gather directory.

### 28.6 Interview answer: What is the difference between `Default` and `WriteRequestBodies`?

`Default` logs metadata for read and write requests and is suitable for normal production use. `WriteRequestBodies` adds request body logging for write operations, which can help troubleshoot changes but increases CPU, memory, disk I/O, storage, and forwarding overhead. Sensitive resources remain metadata-only.

## 30. Troubleshooting Audit Log Problems

### 30.1 `oc adm node-logs` permission denied

You likely need cluster-admin or sufficient node log access.

Check:

```bash
oc whoami
oc auth can-i get nodes/log
```

### 30.2 Audit logs not found

Check paths:

```bash
oc adm node-logs --role=master --path=/
oc adm node-logs --role=master --path=kube-apiserver/
oc adm node-logs --role=master --path=openshift-apiserver/
```

Also confirm control plane node role label:

```bash
oc get nodes --show-labels | grep master
```

### 30.3 Too much data

Filter by:

- Time window
- Node
- API server path
- Namespace
- User
- Verb
- Resource
- Response code

Example:

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq 'select(
    .requestReceivedTimestamp >= "2026-07-03T10:00:00Z"
    and .requestReceivedTimestamp <= "2026-07-03T11:00:00Z"
    and .objectRef.namespace == "demo"
  )'
```

### 30.4 `jq` parse errors

Audit log lines should be JSON, but shell wrapping, partial lines, or non-JSON messages can break parsing.

Try:

```bash
oc adm node-logs master-0.example.com --path=kube-apiserver/audit.log \
| jq -R 'fromjson? | select(. != null)'
```

### 30.5 Cannot find the user action

Possible reasons:

- You checked wrong API server log.
- You checked wrong control plane node.
- The log rotated out.
- The action was performed by a controller/service account, not the human.
- The action happened through GitOps automation.
- The object was changed by an operator reconciliation.
- You filtered only successful requests but the action failed.
- You searched for `update` but the action used `patch`.
- You searched Kubernetes API logs for OpenShift-specific resources.
- The timestamp is in UTC, not local time.

## 31. Timezone Awareness

Audit timestamps are commonly in UTC, for example:

```text
2026-07-03T10:00:00.000000Z
```

India Standard Time is UTC+05:30.

Example conversion:

```text
10:00 UTC = 15:30 IST
```

When investigating incidents, always document both:

```text
Audit timestamp: 2026-07-03T10:00:00Z
Local IST time: 2026-07-03 15:30 IST
```

This prevents confusion during handover with security teams, application teams, and management.

### 32.4 Find audit events

```bash
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
| jq 'select(
    .objectRef.namespace == "audit-demo"
```

Expected result:

- `create` event for secret creation
- `patch` event for metadata update
- `get` event for secret read

You should not expect secret value exposure in audit logs.

## 35. Senior Admin Mental Model

When something security-related happens in OpenShift, think in layers:

```text
Human / Automation
        |
        v
CLI / Console / GitOps / Operator / CI-CD
        |
        v
OpenShift OAuth / Kubernetes Authentication
        |
        v
RBAC Authorization / Admission / SCC / Validating Webhooks
        |
        v
API Server persists desired state in etcd
        |
        v
Operators / Controllers reconcile actual state
        |
        v
Pods / Routes / Certificates / Secrets / NetworkPolicy change
```

Audit logs mainly observe the API server layer. They are strongest for:

- Identity
- Authorization
- API request
- Target object
- Result code
- Timing

They are weaker for:

- In-container behavior
- Packet-level networking
- Application transaction details
- Human intent behind automation
- Full object diffs under `Default` profile
- Long-term retention unless forwarded

A good OpenShift administrator combines audit logs with:

- `oc get` current state
- `oc describe`
- Kubernetes events
- Operator logs
- GitOps history
- CI/CD logs
- SIEM searches
- Certificate inspection with `openssl`
- RBAC checks using `oc auth can-i`

## 36. Quick Command Reference

```bash
# List logs
oc adm node-logs --role=master --path=kube-apiserver/
oc adm node-logs --role=master --path=openshift-apiserver/
oc adm node-logs --role=master --path=oauth-apiserver/
oc adm node-logs --role=master --path=oauth-server/

# View logs
oc adm node-logs <node> --path=kube-apiserver/audit.log
oc adm node-logs <node> --path=openshift-apiserver/audit.log
oc adm node-logs <node> --path=oauth-server/audit.log

# Current audit profile
oc get apiserver cluster -o jsonpath='{.spec.audit.profile}{"\n"}'

# Change audit profile
oc patch apiserver cluster --type=merge -p '{"spec":{"audit":{"profile":"WriteRequestBodies"}}}'
oc patch apiserver cluster --type=merge -p '{"spec":{"audit":{"profile":"Default"}}}'

# Must-gather audit logs
oc adm must-gather -- /usr/bin/gather_audit_logs

# Denied requests
oc adm node-logs <node> --path=kube-apiserver/audit.log | jq 'select(.responseStatus.code == 403)'

# Writes only
oc adm node-logs <node> --path=kube-apiserver/audit.log | jq 'select(.verb | IN("create","update","patch","delete","deletecollection"))'

# Secret access
oc adm node-logs <node> --path=kube-apiserver/audit.log | jq 'select(.objectRef.resource=="secrets")'

# RBAC changes
oc adm node-logs <node> --path=kube-apiserver/audit.log | jq 'select(.objectRef.resource=="clusterrolebindings" or .objectRef.resource=="rolebindings")'

# OAuth login errors
oc adm node-logs <node> --path=oauth-server/audit.log | jq 'select(.annotations["authentication.openshift.io/decision"]=="error")'
```

## 37. Final Summary

Audit log awareness is a core skill for advanced OpenShift administration. It connects security, certificates, identity, RBAC, SCC, OAuth, routes, secrets, and compliance into one investigation workflow.

Remember these key points:

1. Audit logs record API server activity.
2. Check the correct API server log: `kube-apiserver`, `openshift-apiserver`, `oauth-apiserver`, or `oauth-server`.
3. Audit logs are per control plane node.
4. Use `oc adm node-logs` for direct viewing.
5. Use `jq` for practical filtering.
6. Use `oc adm must-gather -- /usr/bin/gather_audit_logs` for support/investigation collection.
7. The `Default` profile is normal production baseline.
8. `WriteRequestBodies` and `AllRequestBodies` increase detail but also overhead.
9. Sensitive resources remain metadata-only.
10. Forward audit logs to centralized, protected storage for real production readiness.
11. Correlate audit logs with events, operator logs, GitOps, CI/CD, and current cluster state.
12. For certificates, watch secrets, configmaps, routes, ingress controllers, OAuth, APIServer, Proxy, and trust bundle resources.

A 10-year experienced OpenShift administrator does not just know where logs are. They know how to convert audit logs into answers, evidence, remediation, and prevention.
