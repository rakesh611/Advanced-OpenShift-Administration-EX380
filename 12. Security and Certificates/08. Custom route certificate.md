# Custom Route Certificate in OpenShift

**Area:** Security and Certificates  
**Audience:** Advanced OpenShift Administration / 10+ years Linux, Kubernetes, OpenShift experience  
**Platform focus:** OpenShift Container Platform 4.x  
**Last reviewed:** 2026-07-03

---

## 1. What is a Custom Route Certificate?

A **custom route certificate** is a TLS certificate explicitly configured for a specific OpenShift `Route` so that clients connecting to that route see an application-specific certificate instead of the Ingress Controller default certificate.

In OpenShift, external application traffic normally enters through the **Ingress Controller**, commonly implemented by the OpenShift router. A `Route` maps an external hostname, such as:

```text
https://app1.apps.ocp4.example.com
```

to an internal Kubernetes `Service`, which then forwards traffic to application pods.

A custom route certificate controls the certificate presented to the external client for that specific route host.

Example use cases:

- `https://payments.example.com` must use a public CA certificate issued for `payments.example.com`.
- A regulated application must use an enterprise PKI certificate instead of the cluster wildcard certificate.
- A third-party vendor requires a certificate chain from a specific CA.
- Multiple applications share the cluster but require separate certificates, ownership, lifecycle, and renewal windows.
- A route uses a hostname outside the default `*.apps.<cluster>.<base-domain>` wildcard domain.

---

## 2. Why Custom Route Certificates Matter

In production OpenShift administration, custom route certificates are not just a developer convenience. They affect security, compliance, external trust, traffic flow, and incident response.

A senior administrator should understand them because:

1. **External users trust certificates, not Kubernetes objects.**
   If the presented certificate is expired, mismatched, incomplete, or untrusted, the application appears down even if pods are healthy.

2. **Certificate placement changes the security model.**
   A certificate embedded directly in a `Route` behaves differently from a certificate stored in a Kubernetes `Secret` and referenced through newer route APIs.

3. **TLS termination mode changes where encryption ends.**
   Edge, re-encrypt, and passthrough routes have very different trust boundaries.

4. **Route certificates are often owned by different teams.**
   The app team may own the hostname, the PKI team may issue certificates, the platform team may operate routers, and the security team may enforce policy.

5. **Incorrect certificate chain handling causes real outages.**
   A route can work in `curl -k` but fail for browsers, Java clients, automation tools, or external health checks.

## 3. Key Terms

| Term | Meaning |
|---|---|
| `Route` | OpenShift API object that exposes a service externally. |
| `Ingress Controller` | OpenShift component that admits and serves routes. The router pods run in `openshift-ingress`. |
| Router | The runtime data-plane component, commonly HAProxy-based, that serves route traffic. |
| Edge termination | TLS terminates at the router. Router sends plain HTTP to the backend service. |
| Re-encrypt termination | TLS terminates at the router, then the router opens a new TLS connection to the backend. |
| Passthrough termination | Router does not decrypt TLS. TLS goes directly to the backend pod. |
| `certificate` | Public server certificate presented to the client. |
| `key` | Private key corresponding to the certificate. Must be protected. |
| `caCertificate` | CA chain sent to client to complete trust path. Used for route frontend certificate chain. |
| `destinationCACertificate` | CA used by the router to validate the backend service certificate in re-encrypt mode. |
| SAN | Subject Alternative Name. Modern clients validate hostname using SAN, not only CN. |
| SNI | Server Name Indication. TLS extension that lets the router choose the certificate based on requested hostname. |
| HSTS | HTTP Strict Transport Security. Browser policy forcing HTTPS for a host. |

## 4. Custom Route Certificate vs Default Ingress Certificate

Do not confuse these two designs.

### 4.1 Default Ingress Certificate

The **default ingress certificate** is used by an Ingress Controller for secured routes that do not specify their own certificate.

Typical default route host:

```text
myapp-myproject.apps.ocp4.example.com
```

If the route has TLS termination but no route-specific certificate, the router serves the Ingress Controller default certificate.

This is cluster-level or ingresscontroller-level configuration.

Common admin command pattern:

```bash
oc create secret tls apps-wildcard-tls \
  --cert=wildcard.apps.ocp4.example.com.crt \
  --key=wildcard.apps.ocp4.example.com.key \
  -n openshift-ingress

oc patch ingresscontroller.operator/default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"apps-wildcard-tls"}}}'
```

### 4.2 Custom Route Certificate

A **custom route certificate** is specific to one `Route`.

Example:

```text
payments.example.com
```

The certificate can be configured directly in the route TLS fields or, on newer OpenShift versions, referenced through `.spec.tls.externalCertificate`.

This is application-level or namespace-level configuration.

## 5. TLS Termination Types and Certificate Placement

OpenShift routes support three main secure termination modes.

| Termination | Where client TLS terminates | Backend connection | Certificate on Route? | Typical use |
|---|---|---|---|---|
| `edge` | Router | Plain HTTP | Yes, unless default cert is used | Common web apps where router handles TLS. |
| `reencrypt` | Router, then new TLS to pod/service | HTTPS/TLS | Yes + destination CA | Security-sensitive apps needing encrypted backend traffic. |
| `passthrough` | Backend pod | Same TLS stream | No | App needs full TLS control, client cert auth, custom TLS stack, gRPC, strict end-to-end. |

## 6. Edge Route with a Custom Certificate

### 6.1 Traffic Flow

```text
Client --HTTPS--> OpenShift Router --HTTP--> Service --HTTP--> Pod
```

In edge termination:

- The router presents the custom certificate to the client.
- The router decrypts traffic.
- The router forwards unencrypted HTTP to the backend service.
- The application pod does not need to run TLS.

### 6.2 When to Use Edge Termination

Use edge termination when:

- The application listens only on HTTP.
- TLS policy is centralized at the router.
- You want simple certificate management.
- Backend network is trusted enough for plain HTTP.
- You need HTTP-level routing, redirects, cookies, or headers at the router.

Avoid edge termination when:

- Compliance requires encryption from client to pod.
- Backend traffic crosses untrusted zones.
- The application requires client certificate authentication directly.
- The application must inspect TLS session properties itself.

### 6.3 Create an Edge Route with Custom Certificate

Assume:

```text
Namespace: finance
Service: payments
Hostname: payments.example.com
Certificate: tls.crt
Private key: tls.key
CA chain: ca.crt
```

Command:

```bash
oc -n finance create route edge payments \
  --service=payments \
  --hostname=payments.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --ca-cert=ca.crt \
  --insecure-policy=Redirect
```

Verify:

```bash
oc -n finance get route payments
oc -n finance get route payments -o yaml
```

Expected route TLS section:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments
  namespace: finance
spec:
  host: payments.example.com
  to:
    kind: Service
    name: payments
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
    certificate: |-
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----
    key: |-
      -----BEGIN PRIVATE KEY-----
      ...
      -----END PRIVATE KEY-----
    caCertificate: |-
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----
```

### 6.4 Security Note: Inline Private Key

In the classic route model, the private key is embedded in the `Route` object under:

```yaml
spec:
  tls:
    key: ...
```

This is operationally simple but sensitive.

Senior-admin considerations:

- Restrict who can `get`, `list`, or `watch` routes in sensitive namespaces.
- Avoid giving broad route read access to non-admin users if route private keys are embedded.
- Consider using `.spec.tls.externalCertificate` where available so the certificate/key live in a Kubernetes TLS secret instead of inline route fields.
- Enable and validate etcd encryption for secrets and sensitive resources according to your organization policy.
- Audit who can export namespace YAMLs.

## 7. Re-encrypt Route with a Custom Certificate

### 7.1 Traffic Flow

```text
Client --HTTPS--> OpenShift Router --HTTPS--> Service --HTTPS--> Pod
```

In re-encrypt termination:

- The router presents the route certificate to the client.
- The router decrypts the incoming TLS session.
- The router creates a second TLS connection to the backend service.
- The backend application must serve HTTPS/TLS.
- The router must trust the backend certificate.

### 7.2 Why Destination CA is Required

For re-encrypt routes, the router validates the backend service certificate. It needs a CA certificate to trust the backend certificate. This is configured as:

```yaml
destinationCACertificate: |-
  -----BEGIN CERTIFICATE-----
  ...
  -----END CERTIFICATE-----
```

This is different from `caCertificate`.

| Field | Purpose |
|---|---|
| `certificate` | Frontend certificate served to external clients. |
| `key` | Private key for the frontend certificate. |
| `caCertificate` | CA/intermediate chain for external clients. |
| `destinationCACertificate` | CA used by router to verify backend pod/service certificate. |

### 7.3 When to Use Re-encrypt

Use re-encrypt when:

- You need TLS from client to router and router to pod.
- You still want OpenShift router features such as HTTP header processing, route policies, HSTS, and redirects.
- You need backend encryption but do not require the backend to receive the original client TLS session.
- You use internal service certificates or app-specific backend certificates.

Avoid re-encrypt when:

- The application must perform end-to-end TLS without router decryption.
- Client certificate authentication must happen inside the pod using the original TLS session.
- You cannot maintain backend certificate trust properly.

### 7.4 Create a Re-encrypt Route with Custom Certificate

Assume:

```text
Namespace: finance
Service: payments-https
Hostname: payments.example.com
Frontend cert: tls.crt
Frontend key: tls.key
Frontend CA chain: ca.crt
Backend CA: destca.crt
```

Command:

```bash
oc -n finance create route reencrypt payments \
  --service=payments-https \
  --hostname=payments.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --ca-cert=ca.crt \
  --dest-ca-cert=destca.crt \
  --insecure-policy=Redirect
```

Verify route:

```bash
oc -n finance get route payments -o yaml
```

Expected TLS section:

```yaml
tls:
  termination: reencrypt
  insecureEdgeTerminationPolicy: Redirect
  certificate: |-
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
  key: |-
    -----BEGIN PRIVATE KEY-----
    ...
    -----END PRIVATE KEY-----
  caCertificate: |-
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
  destinationCACertificate: |-
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

### 7.5 Backend Certificate Requirements

For re-encrypt to work reliably:

- The pod must listen on HTTPS/TLS.
- The service target port must point to the TLS-enabled container port.
- The backend certificate must be signed by the CA placed in `destinationCACertificate`.
- The backend certificate hostname/SAN must match what the router expects, depending on router validation behavior and configuration.
- The backend application must not require TLS features incompatible with router re-encryption.

### 7.6 Common Re-encrypt Failure Pattern

Symptom:

```text
curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL
HTTP 503 from router
```

Common causes:

- Backend pod is serving HTTP, not HTTPS.
- Service `targetPort` points to the wrong container port.
- `destinationCACertificate` does not match backend certificate signer.
- Backend certificate expired.
- Backend application only accepts a specific SNI that router is not using.
- NetworkPolicy blocks router-to-pod traffic.
- Endpoints are empty or not ready.

Troubleshooting commands:

```bash
oc -n finance get route payments -o yaml
oc -n finance get svc payments-https -o yaml
oc -n finance get endpoints payments-https -o wide
oc -n finance get pods -o wide
oc -n finance logs deploy/payments
```

Test backend TLS from inside cluster:

```bash
oc -n finance run tls-test --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
curl -vk https://payments-https.finance.svc.cluster.local:8443
openssl s_client -connect payments-https.finance.svc.cluster.local:8443 -showcerts
```

## 8. Passthrough Route and Why It Has No Route Certificate

### 8.1 Traffic Flow

```text
Client --HTTPS----------------------------------> Pod
                  Router passes encrypted TCP stream
```

In passthrough mode:

- The router does not decrypt TLS.
- The router uses SNI to select the route.
- The backend pod presents the certificate to the client.
- The route does not contain `certificate`, `key`, or `caCertificate`.
- Path-based routing is not available because the router cannot read HTTP paths inside encrypted traffic.

### 8.2 Create Passthrough Route

```bash
oc -n finance create route passthrough payments \
  --service=payments-https \
  --port=https \
  --hostname=payments.example.com
```

Expected route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments
  namespace: finance
spec:
  host: payments.example.com
  port:
    targetPort: https
  tls:
    termination: passthrough
    insecureEdgeTerminationPolicy: None
  to:
    kind: Service
    name: payments-https
```

### 8.3 When to Use Passthrough

Use passthrough when:

- The application must terminate TLS itself.
- The application performs mutual TLS with client certificates.
- You need exact end-to-end TLS with no router decryption.
- The application protocol is TLS-based but not standard HTTP after decryption.
- The application requires TLS settings controlled only by the app team.

Avoid passthrough when:

- You need path-based routing.
- You need router-level HTTP redirects or header manipulation.
- You need HSTS configured by route annotations.
- You need the router to inspect HTTP traffic.

## 9. Certificate Files Required

### 9.1 Frontend Certificate and Key

A route custom certificate normally needs:

```text
tls.crt  -> server certificate for route host
tls.key  -> private key for server certificate
ca.crt   -> intermediate/root CA chain, if required
```

The certificate must match the route host.

For example, if the route is:

```text
payments.example.com
```

Then the certificate SAN should include:

```text
DNS:payments.example.com
```

For wildcard:

```text
DNS:*.example.com
```

But remember:

```text
*.example.com matches payments.example.com
*.example.com does not match api.payments.example.com
```

### 9.2 Private Key Must Not Be Encrypted

OpenShift route certificates require an unencrypted private key.

If a key has a passphrase, remove it before importing:

```bash
openssl rsa \
  -in password_protected_tls.key \
  -out tls.key
```

Protect the resulting key carefully.

### 9.3 Certificate Chain Order

A common production-safe chain order in `tls.crt` or route `certificate`/`caCertificate` handling is:

```text
Server certificate
Intermediate CA 1
Intermediate CA 2
Root CA, if your policy/tooling requires it
```

Many public CAs recommend not serving the root CA because clients already have it, but internal enterprise environments often include full chain material for consistency.

Practical advice:

- Always include required intermediate CAs.
- Avoid missing intermediates; browsers may sometimes recover, but automation tools often fail.
- Validate with `openssl s_client -showcerts` from outside the cluster.

## 10. Generate a Test Certificate for Lab Use

For production, use a real CA or enterprise PKI. For lab practice, create a self-signed cert.

```bash
cat > route-cert.cnf <<'EOF_CERT'
[ req ]
default_bits       = 2048
prompt             = no
default_md         = sha256
req_extensions     = req_ext
distinguished_name = dn

[ dn ]
C  = IN
ST = Delhi
L  = New Delhi
O  = ExampleOrg
OU = Platform
CN = payments.example.com

[ req_ext ]
subjectAltName = @alt_names

[ alt_names ]
DNS.1 = payments.example.com
EOF_CERT

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout tls.key \
  -out tls.crt \
  -config route-cert.cnf \
  -extensions req_ext
```

Inspect:

```bash
openssl x509 -in tls.crt -noout -text | grep -A2 "Subject Alternative Name"
openssl x509 -in tls.crt -noout -subject -issuer -dates
```

Create route:

```bash
oc -n finance create route edge payments \
  --service=payments \
  --hostname=payments.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --insecure-policy=Redirect
```

Test:

```bash
curl -vk https://payments.example.com
```

Because it is self-signed, `curl` without `-k` will fail unless the CA is trusted by the client.

## 11. Using `externalCertificate` for Route Certificates

Newer OpenShift versions support referencing externally managed certificates through:

```yaml
spec:
  tls:
    externalCertificate:
      name: myapp-tls
```

This allows the router to use a Kubernetes TLS secret instead of embedding certificate and key directly in the `Route` object.

### 11.1 Benefits

- Keeps private key in a Kubernetes `Secret` instead of inline route spec.
- Works better with certificate automation tools.
- Reduces manual YAML edits during renewal.
- Helps the router serve renewed certificates after secret content changes.
- Separates route configuration from certificate material.

### 11.2 Create TLS Secret

```bash
oc -n finance create secret tls payments-tls \
  --cert=tls.crt \
  --key=tls.key
```

### 11.3 Allow Router to Read the Secret

The OpenShift router service account must be able to read the secret.

```bash
oc -n finance create role payments-tls-reader \
  --verb=get,list,watch \
  --resource=secrets \
  --resource-name=payments-tls

oc -n finance create rolebinding payments-tls-reader-binding \
  --role=payments-tls-reader \
  --serviceaccount=openshift-ingress:router
```

### 11.4 Route YAML Using External Certificate

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments
  namespace: finance
spec:
  host: payments.example.com
  to:
    kind: Service
    name: payments
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
    externalCertificate:
      name: payments-tls
```

Apply:

```bash
oc apply -f payments-route.yaml
```

### 11.5 Important Limitation

When using:

```yaml
spec.tls.externalCertificate
```

do not also set:

```yaml
spec.tls.certificate
spec.tls.key
```

Use either inline route certificate fields or external certificate reference, not both.

## 12. Certificate Automation with cert-manager Operator

In mature OpenShift environments, manual certificate replacement does not scale. Use an automated lifecycle tool such as the **cert-manager Operator for Red Hat OpenShift** when available and supported for your environment.

Typical automation model:

```text
Issuer / ClusterIssuer -> Certificate -> Secret -> Route externalCertificate
```

Example conceptual flow:

1. PKI admin configures an issuer.
2. App or platform team creates a `Certificate` resource.
3. cert-manager obtains or renews the certificate.
4. cert-manager stores certificate and key in a Kubernetes TLS secret.
5. Route references the TLS secret through `externalCertificate`.
6. Router hot-reloads or detects updated certificate material.

Example `Certificate` object:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: payments-cert
  namespace: finance
spec:
  secretName: payments-tls
  dnsNames:
  - payments.example.com
  issuerRef:
    name: enterprise-ca-issuer
    kind: ClusterIssuer
```

Route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments
  namespace: finance
spec:
  host: payments.example.com
  to:
    kind: Service
    name: payments
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
    externalCertificate:
      name: payments-tls
```

Senior-admin guidance:

- Prefer automation for internet-facing and compliance-sensitive apps.
- Avoid manual renewal windows where possible.
- Monitor expiration at least 30, 14, and 7 days before expiry.
- Keep issuer permissions tightly controlled.
- Confirm router service account permissions for referenced secrets.
- Validate renewal without changing the secret name when possible.

## 13. Ingress Object to Route Translation

OpenShift can create a `Route` from a Kubernetes `Ingress` object.

Because Kubernetes `Ingress` does not have a native OpenShift route termination field, OpenShift uses annotations such as:

```yaml
route.openshift.io/termination: "reencrypt"
route.openshift.io/destination-ca-certificate-secret: secret-ca-cert
```

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: payments
  namespace: finance
  annotations:
    route.openshift.io/termination: "reencrypt"
    route.openshift.io/destination-ca-certificate-secret: payments-dest-ca
spec:
  rules:
  - host: payments.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: payments-https
            port:
              number: 8443
  tls:
  - hosts:
    - payments.example.com
    secretName: payments-tls
```

Admin note:

- This pattern is useful when teams deploy generic Kubernetes manifests.
- Route-specific controls still matter.
- Validate generated routes with `oc get route -o yaml`.

## 14. DNS Requirements

A custom route certificate only solves TLS identity. DNS must still point clients to the router.

For a hostname:

```text
payments.example.com
```

DNS must resolve to the OpenShift router endpoint, usually:

- Load balancer VIP
- Cloud load balancer hostname
- Router node IPs
- External DNS CNAME to `*.apps` load balancer

Check DNS:

```bash
dig payments.example.com
nslookup payments.example.com
```

Check OpenShift route admission:

```bash
oc -n finance get route payments -o jsonpath='{.status.ingress[*].conditions[*]}' | jq
```

Check router canonical hostname:

```bash
oc -n finance get route payments -o yaml | grep -A20 status:
```

Common DNS/certificate mismatch:

```text
Route host: payments.example.com
Certificate SAN: payments.apps.ocp4.example.com
Result: browser certificate name mismatch
```

## 15. Insecure Edge Termination Policy

For edge and re-encrypt routes, OpenShift supports `insecureEdgeTerminationPolicy`.

Values:

| Value | Meaning |
|---|---|
| `Redirect` | Redirect HTTP to HTTPS. Recommended for most web apps. |
| `None` | Do not allow insecure traffic. |
| Empty/omitted | Behavior depends on route/router defaults; avoid ambiguity in production. |

Example:

```yaml
tls:
  termination: edge
  insecureEdgeTerminationPolicy: Redirect
```

CLI:

```bash
oc -n finance create route edge payments \
  --service=payments \
  --hostname=payments.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --insecure-policy=Redirect
```

Best practice:

- Use `Redirect` for browser apps unless strict policy requires no HTTP listener.
- Use HSTS after confirming HTTPS is stable.
- Do not enable HSTS with long max-age until rollback is understood.

## 16. HSTS with Custom Route Certificates

HSTS tells browsers to always use HTTPS for a host.

Example route annotation:

```bash
oc -n finance annotate route payments \
  haproxy.router.openshift.io/hsts_header='max-age=31536000;includeSubDomains;preload'
```

Safer rollout:

```bash
oc -n finance annotate route payments \
  haproxy.router.openshift.io/hsts_header='max-age=300'
```

Then gradually increase.

Important:

- HSTS is meaningful for edge and re-encrypt routes.
- It is not useful for passthrough because the router does not inject HTTP headers.
- Be careful with `includeSubDomains`; it can affect many hosts.
- Be very careful with `preload`; browser preload lists are hard to undo quickly.

### 17.1 Verify Route Object

```bash
oc -n finance get route payments
oc -n finance describe route payments
oc -n finance get route payments -o yaml
```

### 17.2 Verify Certificate Presented Externally

```bash
openssl s_client \
  -connect payments.example.com:443 \
  -servername payments.example.com \
  -showcerts </dev/null
```

```bash
openssl s_client \
  -connect payments.example.com:443 \
  -servername payments.example.com </dev/null 2>/dev/null \

```

### 17.3 Verify HTTP Response

```bash
curl -v https://payments.example.com
curl -vk https://payments.example.com
curl -I https://payments.example.com
```

Use `-k` only for troubleshooting, never as final proof.

```bash
openssl x509 -in tls.crt -noout -text | grep -A2 "Subject Alternative Name"
```

### 17.5 Verify Service Endpoints

```bash

oc -n finance get endpoints payments -o wide
oc -n finance get pods -l app=payments -o wide
```


```bash

```

## 18. Updating or Rotating a Custom Route Certificate

### 18.1 Inline Certificate Rotation

If certificate and key are embedded in the route:

```bash
oc -n finance delete route payments

oc -n finance create route edge payments \
  --service=payments \
  --hostname=payments.example.com \
  --cert=new-tls.crt \
  --key=new-tls.key \
  --ca-cert=new-ca.crt \
  --insecure-policy=Redirect
```

Better approach: patch route from YAML.

Export current route:

```bash
oc -n finance get route payments -o yaml > payments-route.yaml
```

Edit:

```yaml
spec:
  tls:
    certificate: |-
      NEW CERT
    key: |-
      NEW KEY
    caCertificate: |-
      NEW CA CHAIN
```

Apply:

```bash
oc apply -f payments-route.yaml
```

### 18.2 External Certificate Secret Rotation

If using `externalCertificate`:

```bash
oc -n finance create secret tls payments-tls-new \
  --cert=new-tls.crt \
  --key=new-tls.key \
  --dry-run=client -o yaml | oc apply -f -
```

If secret name stays the same:

```bash
oc -n finance create secret tls payments-tls \
  --cert=new-tls.crt \
  --key=new-tls.key \
  --dry-run=client -o yaml | oc apply -f -
```

Then verify:

```bash
sleep 5
openssl s_client -connect payments.example.com:443 \
  -servername payments.example.com </dev/null 2>/dev/null \
| openssl x509 -noout -subject -issuer -dates
```

Best practice:

- Keep the secret name stable for automation.
- Do not rotate by creating many new secret names unless your route references are also updated.
- Test renewal in lower environment.
- Monitor router logs during production rotations.

## 19. Troubleshooting Matrix

| Symptom | Likely cause | Check | Fix |
|---|---|---|---|
| Browser says certificate name mismatch | Route host not present in SAN | `openssl x509 -text` | Reissue cert with correct SAN. |
| Browser says certificate untrusted | Missing intermediate or private CA not trusted | `openssl s_client -showcerts` | Add proper chain or trust CA on client. |
| Browser says expired certificate | Cert expired | `openssl x509 -dates` | Renew and update route/secret. |
| `curl -k` works but normal `curl` fails | Trust or chain issue | Compare with and without `-k` | Fix CA chain/trust. |
| HTTP works but HTTPS fails | Route not secured or wrong termination | `oc get route -o yaml` | Configure TLS section. |
| HTTPS returns 503 | No endpoints or backend TLS failure | `oc get endpoints`, router logs | Fix service selector/backend cert. |
| Re-encrypt route fails | Missing/wrong `destinationCACertificate` | Route YAML, backend cert | Add correct backend CA. |
| Passthrough route path not working | Passthrough cannot inspect HTTP path | Route YAML | Use edge/reencrypt for path routing. |
| Cert update not visible | Router not reloaded yet or wrong route/secret | `openssl s_client`, router logs | Wait briefly, confirm route references. |
| Route not admitted | Host conflict or router shard mismatch | Route status | Fix host/shard/labels. |
| Wrong cert served | SNI not sent or host mismatch | `openssl s_client -servername` | Use correct hostname/SNI. |

## 20. Deep Troubleshooting Workflow

### Step 1: Confirm the Client Sees the Issue

```bash
curl -v https://payments.example.com
```

Capture:

- DNS resolution
- TLS handshake
- Certificate subject/issuer
- HTTP status
- Redirect behavior

### Step 2: Confirm SNI Certificate

```bash
openssl s_client \
  -connect payments.example.com:443 \
  -servername payments.example.com \
  -showcerts </dev/null
```

Without SNI, router may return a default certificate:

```bash
openssl s_client \
  -connect payments.example.com:443 \
  -showcerts </dev/null
```

If results differ, SNI is involved.

### Step 3: Validate Route YAML

```bash
oc -n finance get route payments -o yaml
```

Check:

```yaml
spec:
  host:
  port:
  to:
  tls:
    termination:
    certificate:
    key:
    caCertificate:
    destinationCACertificate:
    externalCertificate:
```

### Step 4: Validate Service and Endpoints

```bash
oc -n finance get svc payments -o yaml
oc -n finance get endpoints payments -o wide
oc -n finance get pods -o wide
```

No endpoints means route cannot forward to pods.

### Step 5: Validate Backend Protocol

For edge route:

```bash
# Backend should usually respond over HTTP
curl -v http://<pod-ip>:<port>
```

For re-encrypt route:

```bash
# Backend should respond over HTTPS
curl -vk https://<pod-ip>:<port>
```

From a debug pod:

```bash
oc -n finance run debug --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
```

### Step 6: Check Router Logs

```bash
oc -n openshift-ingress logs deploy/router-default -c router --tail=200
```

If multiple routers or shards exist:

```bash
oc -n openshift-ingress get deploy
oc -n openshift-ingress-operator get ingresscontroller -A
```

### Step 7: Check Route Admission

```bash
oc -n finance get route payments -o json | jq '.status.ingress'
```

Look for:

```text
Admitted: True
Reason: Admitted
```

If not admitted, check host conflicts and router selectors.

## 21. RBAC and Security Governance

### 21.1 Why RBAC Matters

Custom route certificates may contain private keys. If route TLS fields are inline, users who can read the route YAML may read the private key.

Control permissions carefully:

```bash
oc policy who-can get routes -n finance
oc policy who-can list routes -n finance
oc policy who-can get secrets -n finance
```

### 21.2 Recommended Governance

- Platform team owns Ingress Controller default certificates.
- Application team owns application-specific route requests.
- PKI/security team owns certificate issuance policy.
- Use separate namespaces for sensitive apps.
- Use `externalCertificate` where supported.
- Restrict direct private key handling.
- Audit certificate expiry and ownership.
- Do not store private keys in Git.
- Use sealed/encrypted secret workflows if using GitOps.

### 21.3 GitOps Warning

Do not commit this to Git:

```yaml
spec:
  tls:
    key: |-
      -----BEGIN PRIVATE KEY-----
```

Prefer one of these:

- cert-manager-generated secret
- External Secrets Operator
- Sealed Secrets
- Vault integration
- SOPS-encrypted manifests
- OpenShift GitOps with approved secret management pattern

## 22. Multi-Router and Sharding Considerations

OpenShift can have multiple Ingress Controllers.

Examples:

- `default` router for normal apps
- `external` router for internet-facing apps
- `internal` router for private apps
- dedicated router for PCI workloads

Route placement can be controlled by:

- namespace selectors
- route selectors
- route labels
- ingresscontroller domain

Check routers:

```bash
oc -n openshift-ingress-operator get ingresscontroller
oc -n openshift-ingress-operator get ingresscontroller default -o yaml
```

Check route labels:

```bash
oc -n finance get route payments --show-labels
```

If the wrong router serves the route, the wrong certificate may appear or the route may not be admitted.

## 24. Common Interview and Real-World Questions

### Q1. What is the difference between `caCertificate` and `destinationCACertificate`?

`caCertificate` helps complete the frontend certificate chain that external clients use to trust the route certificate.

`destinationCACertificate` is used only in re-encrypt routes so the router can trust the backend service certificate.

### Q2. Why does passthrough route not require `tls.crt` and `tls.key`?

Because the router does not terminate TLS. The backend pod presents the certificate directly to the client.

### Q3. Why is my route showing the default wildcard certificate instead of my custom certificate?

Possible causes:

- Route TLS fields were not configured.
- Wrong route hostname is being tested.
- Client did not send SNI.
- Route not admitted by router.
- You configured default ingress certificate, not route-specific certificate.
- `externalCertificate` secret is missing or router lacks RBAC to read it.

### Q4. Can one route use multiple certificates?

Normally one route host uses one serving certificate. Use SAN/wildcard certificates for multiple names, or create separate routes for separate hostnames.

### Q5. Can I use a wildcard certificate for a custom route?

Yes, if the wildcard matches the route hostname.

Example:

```text
*.example.com -> payments.example.com    valid
*.example.com -> api.payments.example.com not valid
```

### Q6. Why does `curl -k` work but browser fails?

`curl -k` skips certificate verification. Browser failure usually means certificate name mismatch, missing chain, expired certificate, or untrusted CA.

### Q7. What happens if the certificate expires?

The router may continue presenting the expired certificate until you update the route/secret. Clients that validate certificates will reject the connection.

### Q8. Should I use edge or re-encrypt?

Use edge for simple web apps where backend HTTP is acceptable. Use re-encrypt when traffic must remain encrypted from router to pod but you still need router HTTP features.

### Q9. Should I use passthrough?

Use passthrough when the application must own TLS completely, especially for mutual TLS or protocols where the router must not decrypt traffic.

## 26. Senior Admin Mental Model

Think of custom route certificates in four layers:

```text
1. DNS layer
   Does the hostname resolve to the OpenShift router?

2. Route admission layer
   Is the route accepted by the correct Ingress Controller?

3. TLS frontend layer
   Does the router present the right certificate for the requested SNI host?

4. Backend delivery layer
   Does the router reach the service and pod using the expected protocol?
```

For edge:

```text
Frontend TLS is important; backend is HTTP.
```

For re-encrypt:

```text
Frontend TLS and backend TLS are both important.
```

For passthrough:

```text
The backend certificate is the certificate the client sees.
```

This mental model helps solve most production incidents quickly.

## 27. Advanced Best Practices

1. **Prefer public CA certificates for public apps.**
   Avoid asking users to trust internal CAs unless the app is internal.

2. **Use enterprise PKI for internal apps.**
   Ensure managed endpoints trust the enterprise root CA.

3. **Automate certificate lifecycle.**
   Manual renewals fail during holidays, outages, and team transitions.

4. **Monitor certificate expiry externally.**
   Internal Kubernetes state may look fine while public clients see an expired cert.

5. **Use SNI-aware testing.**
   Always include `-servername` with `openssl s_client`.

6. **Do not use `curl -k` as proof of health.**
   It hides trust failures.

7. **Avoid inline private keys where possible.**
   Use secret-backed certificate references when supported.

8. **Document certificate ownership.**
   Every production route should have an owner, CA source, renewal process, and escalation path.

9. **Separate internet and internal routers.**
   Use IngressController sharding for security zones.

10. **Test renewal before expiry.**
    A renewal that changes SANs, chain, key type, or issuer can break clients.

## 30. Final Summary

A custom route certificate is a route-specific TLS identity presented to clients for an OpenShift application hostname. The most important administration decision is the TLS termination mode:

- Use **edge** when the router terminates TLS and backend HTTP is acceptable.
- Use **re-encrypt** when both external and internal legs must use TLS.
- Use **passthrough** when the backend application must own TLS completely.

For advanced administration, always validate DNS, route admission, SNI behavior, certificate SAN, certificate chain, private key handling, backend protocol, and renewal ownership. Most production incidents come from one of these areas, not from the `Route` object alone.
