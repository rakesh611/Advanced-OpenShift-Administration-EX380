## 1. Executive Summary

RBAC, or Role-Based Access Control, is the authorization framework that decides whether an authenticated identity can perform a specific action against an OpenShift API resource.

In practical OpenShift administration, RBAC answers questions like:

- Can user `bob` view pods in project `apollo`?
- Can group `dev-team` create deployments in namespace `payments-dev`?
- Can service account `backup-sa` list persistent volume claims across all projects?
- Can a CI/CD pipeline update routes but not read secrets?
- Can an application pod use a privileged or `anyuid` SCC?
- Can a developer create projects by self-provisioning?

RBAC is not only a security feature; it is also an operational control plane. A good RBAC model determines how safely teams can use a shared OpenShift platform without accidentally damaging other teams, exposing secrets, escalating privileges, or breaking cluster components.

A senior administrator should think of RBAC as a combination of:

```text
Identity + Action + Scope + Binding = Authorization Decision
```

Where:

- **Identity** = user, group, or service account
- **Action** = verb such as `get`, `list`, `create`, `update`, `delete`, `watch`, `patch`, `use`, `bind`, `escalate`, `impersonate`
- **Scope** = project/namespace or cluster-wide
- **Binding** = relationship between identity and role

RBAC is additive. There is no native deny rule in Kubernetes/OpenShift RBAC. If any applicable role grants the action, the action is allowed. If no rule matches, the action is denied by default.

## 2. Where RBAC Fits in OpenShift Security

OpenShift security is layered. RBAC is one layer, but it must be understood with the other layers.

```text
Client / User / Pod
        |
        v
Authentication: Who are you?
        |
        v
Authorization / RBAC: What are you allowed to do?
        |
        v
Admission Controllers: Is this request acceptable?
        |
        v
SCC / PSA / Quotas / Policies / Operators
        |
        v
etcd state change or workload execution
```

### Key security layers

| Layer | Main Question | Examples |
|---|---|---|
| TLS / certificates | Is the API endpoint trusted and encrypted? | API server certificate, ingress certificate, kubelet client certs |
| Authentication | Who is making the request? | OAuth, LDAP, HTPasswd, OIDC, kubeconfig, service account token |
| RBAC authorization | Is the identity allowed to do this action? | Role, ClusterRole, RoleBinding, ClusterRoleBinding |
| Admission | Is the object valid and safe? | SCC, Pod Security Admission, quotas, image policy, validating/mutating webhooks |
| Runtime security | Can the process escape or abuse node resources? | SELinux, seccomp, Linux capabilities, cgroups, CRI-O |
| Network security | Can workloads talk to each other? | NetworkPolicy, EgressFirewall, service mesh policy |

RBAC controls API permissions. It does not directly control pod Linux privileges. For example, a user may be allowed by RBAC to create pods, but SCC admission can still reject a pod that requests host networking, root UID, hostPath, or privileged mode.

## 3. Authentication vs Authorization vs Admission

### Authentication

Authentication confirms identity.

Examples:

```bash
oc login -u bob -p redhat https://api.ocp4.example.com:6443
oc whoami
oc whoami --show-token
```

Authentication sources can include:

- HTPasswd identity provider
- LDAP identity provider
- OpenID Connect / external OIDC
- OAuth access token
- kubeconfig client certificate
- service account token

Authentication answers:

```text
This request is from user bob.
This request is from group developers.
This request is from service account system:serviceaccount:ci:deploy-bot.
```

### Authorization

Authorization decides whether that identity is allowed to perform an API action.

Example:

```bash
oc auth can-i create deployments -n apollo --as=bob
```

Authorization answers:

```text
Can bob create deployments in project apollo?
```

### Admission

Admission checks whether the requested object should be accepted after authorization succeeds.

Example:

```bash
oc run test --image=registry.access.redhat.com/ubi9/ubi --privileged=true
```

RBAC may allow pod creation, but SCC admission may reject the pod because the service account is not allowed to use a privileged SCC.

This distinction is critical during troubleshooting:

| Error Type | Meaning |
|---|---|
| `Unauthorized` | Authentication failed |
| `Forbidden` | Authentication succeeded, RBAC denied action |
| `would violate PodSecurity` / `unable to validate against any security context constraint` | RBAC may have allowed pod creation, but admission rejected workload security context |
| `quota exceeded` | RBAC allowed the request, but ResourceQuota admission blocked it |

## 4. RBAC Mental Model

Think of RBAC as four objects:

```text
Role / ClusterRole = What actions are allowed?
RoleBinding / ClusterRoleBinding = Who gets those permissions?
```

### Namespaced example

```text
User bob
  -> RoleBinding in namespace apollo
      -> ClusterRole view
          -> get/list/watch pods, services, deployments, etc.
```

Bob can view resources only in the `apollo` namespace.

### Cluster-wide example

```text
User alice
  -> ClusterRoleBinding
      -> ClusterRole cluster-admin
          -> all verbs on all resources across the cluster
```

Alice can perform cluster administrator actions everywhere.

### Service account example

```text
Pod runs as service account deploy-bot in namespace ci
  -> RoleBinding in namespace payments-prod
      -> Role deployer-limited
          -> patch deployments and update imagestreamtags
```

The pod can perform only those API operations in the target namespace.

## 5. Core RBAC API Objects

Kubernetes and OpenShift RBAC use four primary API objects:

| Object | Scope | Purpose |
|---|---|---|
| `Role` | Namespace/project | Defines permissions inside one namespace |
| `ClusterRole` | Cluster | Defines reusable permissions, cluster-scoped permissions, or namespaced permissions reusable across namespaces |
| `RoleBinding` | Namespace/project | Grants a Role or ClusterRole to subjects inside one namespace |
| `ClusterRoleBinding` | Cluster | Grants a ClusterRole to subjects cluster-wide |

### 5.1 Role

A `Role` is namespaced. It grants permissions only in the namespace where it exists.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: apollo
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
```

Use `Role` when:

- The permission is unique to one namespace.
- You do not want reusable cluster-level policy.
- You want very tight local control.

### 5.2 ClusterRole

A `ClusterRole` is not namespaced. It can describe:

1. Cluster-scoped resources, such as nodes, persistent volumes, namespaces, clusterroles.
2. Namespaced resources, such as pods or services, for reuse in multiple namespaces.
3. Non-resource URLs such as `/healthz`.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: namespace-pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
```

This does not grant anything by itself. It must be bound using `RoleBinding` or `ClusterRoleBinding`.

### 5.3 RoleBinding

A `RoleBinding` grants permissions within a namespace.

It can reference:

- A `Role` in the same namespace
- A `ClusterRole`

Example binding a ClusterRole locally:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bob-view
  namespace: apollo
subjects:
- kind: User
  apiGroup: rbac.authorization.k8s.io
  name: bob
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: view
```

This is a best-practice pattern: reuse built-in `ClusterRole` definitions but bind them only inside specific projects.

### 5.4 ClusterRoleBinding

A `ClusterRoleBinding` grants a `ClusterRole` cluster-wide.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: alice-cluster-admin
subjects:
- kind: User
  apiGroup: rbac.authorization.k8s.io
  name: alice
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: cluster-admin
```

Use `ClusterRoleBinding` carefully. It is one of the highest-risk RBAC objects in a production OpenShift cluster.

## 6. OpenShift-Specific RBAC Concepts

OpenShift builds on Kubernetes RBAC and adds platform-specific operational patterns.

### 6.1 Project vs Namespace

A Kubernetes namespace is a scope for namespaced resources.

An OpenShift project is a namespace with additional OpenShift annotations and project-management behavior. For day-to-day administration, many commands use project terminology:

```bash
oc new-project apollo
oc project apollo
oc get projects
oc get namespaces
```

A project is the main security boundary for regular application teams.

### 6.2 `oc adm policy`

OpenShift provides administrator-friendly commands for RBAC management:

```bash
oc adm policy add-role-to-user view bob -n apollo
oc adm policy add-role-to-group edit developers -n apollo
oc adm policy add-cluster-role-to-user cluster-admin alice
oc adm policy remove-cluster-role-from-group self-provisioner system:authenticated:oauth
oc adm policy who-can create pods -n apollo
```

These are wrappers around RBAC resources.

### 6.3 Default project service accounts

Each project commonly includes default service accounts such as:

- `default`
- `builder`
- `deployer`

A mature OpenShift admin should avoid using the `default` service account for privileged application behavior. Create application-specific service accounts and bind only the needed permissions.

### 6.4 SCC access through RBAC

OpenShift SCCs can be granted through RBAC using the `use` verb against the SCC resource.

Common shortcut:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n app-project
```

This allows service account `app-sa` in project `app-project` to use the `anyuid` SCC.

## 7. Default OpenShift Cluster Roles

OpenShift ships with default roles that administrators can bind cluster-wide or locally. Do not manually edit default system roles unless you fully understand the upgrade and reconciliation impact.

| Role | Practical Meaning | Typical Scope |
|---|---|---|
| `cluster-admin` | Superuser. Can perform any action on any resource. | ClusterRoleBinding for platform admins only |
| `admin` | Project administrator. Can manage most project resources. | RoleBinding inside a project |
| `edit` | Can modify most application resources but not RBAC roles/bindings. | RoleBinding for developers/operators |
| `view` | Read-only access to most project resources. | RoleBinding for auditors/support/read-only users |
| `cluster-reader` | Read access to most cluster objects, no modification. | ClusterRoleBinding for read-only platform observers |
| `cluster-status` | Basic cluster status information. | Limited operational visibility |
| `basic-user` | Basic information about projects and users. | General authenticated user role |
| `self-provisioner` | Allows users to create their own projects. | Usually bound to authenticated users by default, often removed in enterprise clusters |

### Important: local `cluster-admin` is not the same as cluster-wide `cluster-admin`

This is a common confusion.

```bash
oc adm policy add-role-to-user cluster-admin bob -n apollo
```

This gives Bob powerful permissions in only the `apollo` namespace. It does not make Bob a real cluster administrator.

Real cluster admin:

```bash
oc adm policy add-cluster-role-to-user cluster-admin bob
```

### Do not manually modify default roles

Default roles may be maintained by the platform. Direct modification can cause cluster instability, unpredictable behavior after upgrades, or reconciliation overwrites. Create custom roles instead.

## 8. Users, Groups, and Service Accounts

RBAC subjects can be:

| Subject Kind | Example | Usage |
|---|---|---|
| User | `bob` | Human user from identity provider |
| Group | `dev-team` | Team-based access |
| ServiceAccount | `system:serviceaccount:ci:deploy-bot` | Workload, CI/CD, operator, automation |

### 8.1 User

Example:

```yaml
subjects:
- kind: User
  apiGroup: rbac.authorization.k8s.io
  name: bob
```

Human users should normally get access through groups, not direct user bindings, except for break-glass or one-off temporary access.

### 8.2 Group

Example:

```yaml
subjects:
- kind: Group
  apiGroup: rbac.authorization.k8s.io
  name: developers
```

Group-based RBAC is easier to audit and maintain.

Typical enterprise mapping:

| Identity Provider Group | OpenShift Group | Role |
|---|---|---|
| LDAP `ocp-platform-admins` | `platform-admins` | `cluster-admin` |
| LDAP `payments-dev` | `payments-dev` | `edit` in dev project |
| LDAP `payments-readonly` | `payments-readonly` | `view` in prod project |
| LDAP `security-auditors` | `security-auditors` | `cluster-reader` |

### 8.3 ServiceAccount

Service accounts are used by pods and automation.

Full service account username format:

```text
system:serviceaccount:<namespace>:<service-account-name>
```

Example:

```text
system:serviceaccount:ci:deploy-bot
```

Every service account is also part of these groups:

```text
system:serviceaccounts
system:serviceaccounts:<namespace>
```

Do not grant broad privileges to `system:serviceaccounts` unless you intentionally want all service accounts in the cluster to receive that permission.

### 8.4 Service account best practice

Bad pattern:

```bash
oc adm policy add-cluster-role-to-group cluster-admin system:serviceaccounts
```

This effectively gives every service account cluster admin permissions and is a critical security failure.

Better pattern:

```bash
oc create sa deploy-bot -n ci
oc adm policy add-role-to-user edit system:serviceaccount:ci:deploy-bot -n app-dev
```

Best pattern:

Create a narrow custom role and bind it only where needed.

## 9. Verbs, Resources, API Groups, Subresources, and Resource Names

RBAC rules are built from verbs and resources.

### 9.1 Common verbs

| Verb | Meaning |
|---|---|
| `get` | Read one object by name |
| `list` | List multiple objects |
| `watch` | Stream object changes |
| `create` | Create new objects |
| `update` | Replace an existing object |
| `patch` | Partially modify an object |
| `delete` | Delete one object |
| `deletecollection` | Delete multiple objects |
| `use` | Use a special resource such as SCC |
| `bind` | Bind a role that contains permissions the user may not already have |
| `escalate` | Create/update roles with permissions beyond the user's own permissions |
| `impersonate` | Act as another user/group/service account |

### 9.2 Core API group

Core resources use an empty API group:

```yaml
apiGroups: [""]
resources: ["pods", "services", "configmaps"]
```

### 9.3 Named API groups

Examples:

```yaml
apiGroups: ["apps"]
resources: ["deployments", "replicasets", "statefulsets"]
```

```yaml
apiGroups: ["route.openshift.io"]
resources: ["routes"]
```

```yaml
apiGroups: ["image.openshift.io"]
resources: ["imagestreams", "imagestreamtags"]
```

```yaml
apiGroups: ["security.openshift.io"]
resources: ["securitycontextconstraints"]
verbs: ["use"]
```

### 9.4 Subresources

Subresources matter a lot in security.

Examples:

| Subresource | Why It Matters |
|---|---|
| `pods/log` | Allows reading container logs |
| `pods/exec` | Allows executing commands inside containers |
| `pods/portforward` | Allows port-forwarding to pods |
| `pods/proxy` | Allows proxying to pods |
| `deployments/scale` | Allows scaling deployments |
| `pods/status` | Allows status updates |

Example:

```yaml
rules:
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list"]
```

### 9.5 Resource names

`resourceNames` restricts a rule to named objects.

Example: allow updating only one config map:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: update-app-config-only
  namespace: app-prod
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  resourceNames: ["app-config"]
  verbs: ["get", "update", "patch"]
```

Important limitation: `resourceNames` does not work well with `list` and `watch`, because list/watch are not against a single named object in the same way.

## 10. Local RBAC vs Cluster RBAC

### Local RBAC

Local RBAC applies inside one namespace/project.

```bash
oc adm policy add-role-to-user view bob -n apollo
```

This creates or updates a RoleBinding in project `apollo`.

Bob can view project `apollo`, not the whole cluster.

### Cluster RBAC

Cluster RBAC applies cluster-wide.

```bash
oc adm policy add-cluster-role-to-user cluster-reader auditor
```

This creates or updates a ClusterRoleBinding.

The user receives the role across the cluster.

### Decision table

| Requirement | Correct Binding |
|---|---|
| User can view one project | RoleBinding to `view` in that project |
| User can edit one project | RoleBinding to `edit` in that project |
| User can administer one project | RoleBinding to `admin` in that project |
| User can read all namespaces | ClusterRoleBinding to `cluster-reader` or carefully selected custom ClusterRole |
| User can administer entire cluster | ClusterRoleBinding to `cluster-admin` |
| Pipeline can update one deployment | RoleBinding to custom Role in that namespace |
| Operator watches resources across all namespaces | ClusterRoleBinding to custom ClusterRole |

## 11. RoleBinding to ClusterRole: The Most Important Production Pattern

In production, you often bind a ClusterRole locally.

Example:

```bash
oc adm policy add-role-to-user view bob -n payments-prod
```

Behind the scenes:

```text
RoleBinding in payments-prod
  -> references ClusterRole view
  -> subject bob
```

This gives Bob `view` only in `payments-prod`.

Why this is useful:

- Reuse standard OpenShift role definitions.
- Avoid copy-pasting Roles in every namespace.
- Keep project-level access scoped.
- Avoid unnecessary ClusterRoleBindings.

Bad alternative:

```bash
oc adm policy add-cluster-role-to-user view bob
```

This gives Bob view access across all namespaces.

## 12. RBAC Evaluation Flow

When a request arrives, OpenShift evaluates authorization roughly like this:

```text
1. Identify user and groups.
2. Identify requested action: verb + resource + namespace + resource name.
3. Find all ClusterRoleBindings matching the user/groups/service account.
4. Find all RoleBindings in the target namespace matching the user/groups/service account.
5. Collect all referenced Role and ClusterRole rules.
6. Check whether any rule matches the request.
7. If yes, allow.
8. If no, deny by default.
```

Example request:

```bash
oc get pods -n apollo --as=bob
```

Authorization engine checks:

```text
Identity: bob
Groups: groups assigned to bob
Verb: get/list
Resource: pods
Namespace: apollo
Bindings: ClusterRoleBindings + RoleBindings in apollo
Decision: allowed or forbidden
```

RBAC has no native deny rule. To remove access, you must remove the binding or remove the permission from the role.

## 13. Least Privilege RBAC Design

Least privilege means granting only the minimum permissions needed for the task.

### 13.1 Start with the question

Before creating RBAC, ask:

```text
Who needs access?
What exact action do they need?
Which namespace?
For how long?
Do they need write access or only read access?
Do they need secrets?
Do they need pod exec?
Do they need SCC access?
Can this be group-based instead of user-based?
```

### 13.2 Prefer groups for humans

Better:

```bash
oc adm policy add-role-to-group edit payments-dev -n payments-dev
```

Worse:

```bash
oc adm policy add-role-to-user edit alice -n payments-dev
oc adm policy add-role-to-user edit bob -n payments-dev
oc adm policy add-role-to-user edit charlie -n payments-dev
```

### 13.3 Prefer service-account-specific bindings for workloads

Better:

```bash
oc create sa backup-reader -n backup
oc adm policy add-role-to-user pvc-reader system:serviceaccount:backup:backup-reader -n app-prod
```

Worse:

```bash
oc adm policy add-role-to-group view system:serviceaccounts -n app-prod
```

### 13.4 Avoid broad wildcard rules

High-risk:

```yaml
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["*"]
```

This is effectively cluster-admin-like behavior when bound broadly.

### 13.5 Avoid unnecessary secret access

Reading secrets can enable privilege escalation. Many service account tokens and credentials are stored or projected as secret-like material. Treat `get/list/watch secrets` as sensitive.

### 13.6 Avoid unnecessary pod exec

`pods/exec` enables command execution inside running containers. This can expose application credentials, mounted tokens, database passwords, and internal network access.

## 14. RBAC and Secrets Security

Secrets are not ordinary read-only data.

A user who can read secrets in a namespace may be able to:

- Read application credentials.
- Read registry credentials.
- Access database passwords.
- Steal service account tokens if long-lived token secrets exist.
- Impersonate workload behavior indirectly.

### 14.1 `view` role and secrets

The Kubernetes/OpenShift `view` role is intentionally designed to avoid secret read access. Read-only is not always harmless if it includes secrets.

### 14.2 `edit` role and secrets

The `edit` role can be powerful. A user with edit permissions may be able to create pods that run as service accounts in the namespace or access application secret data through workload changes. For production namespaces, treat `edit` as high trust.

### 14.3 Safe pattern for support users

Support users often need logs and pod status, not secrets.

Create a custom support role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: support-readonly-no-secrets
  namespace: app-prod
rules:
- apiGroups: [""]
  resources: ["pods", "services", "endpoints", "events", "configmaps"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list"]
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets", "statefulsets", "daemonsets"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["route.openshift.io"]
  resources: ["routes"]
  verbs: ["get", "list", "watch"]
```

Bind it:

```bash
oc adm policy add-role-to-group support-readonly-no-secrets app-support -n app-prod
```

## 15. RBAC and Pod Execution Security

Pod-related subresources are security-sensitive.

### 15.1 `pods/exec`

Allows:

```bash
oc exec -n app-prod deploy/api -- /bin/bash
```

Risks:

- Read mounted service account token.
- Read mounted secrets/configs.
- Access internal services from inside the pod network.
- Modify temporary application state.
- Trigger commands that were not intended for the user.

### 15.2 `pods/log`

Allows:

```bash
oc logs -n app-prod deploy/api
```

Risks:

- Logs may contain tokens, passwords, connection strings, customer data, or stack traces.

### 15.3 `pods/portforward`

Allows:

```bash
oc port-forward -n app-prod svc/database 5432:5432
```

Risks:

- Bypasses normal ingress path.
- Can expose internal-only services to a user workstation.
- May bypass network-level assumptions if not controlled.

### 15.4 Safe operational model

| Need | Suggested Permission |
|---|---|
| View pod status | `get/list/watch pods` |
| Read logs | `get pods/log` |
| Restart deployment | `patch deployments` or `rollout restart` with controlled permissions |
| Exec into prod pod | Break-glass only, audited, time-bound |
| Port-forward to database | Avoid unless explicitly approved and audited |

## 16. RBAC and SecurityContextConstraints

OpenShift SCCs control pod security context permissions. RBAC controls who or which service account can use an SCC.

### 16.1 SCC examples

Common SCCs include:

| SCC | Meaning |
|---|---|
| `restricted-v2` | Default restricted workload posture in newer OpenShift releases |
| `nonroot-v2` | Allows non-root workloads with modern restrictions |
| `anyuid` | Allows containers to run as any UID |
| `hostnetwork` / `hostnetwork-v2` | Allows host networking/ports |
| `hostmount-anyuid` | Allows hostPath-style host file access and any UID; very sensitive |
| `privileged` | Allows privileged workloads; extremely sensitive |

### 16.2 Granting SCC access

Common command:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n app-project
```

Equivalent idea:

```text
Give service account app-sa permission to use SCC anyuid.
```

### 16.3 Avoid granting SCC to users directly

Prefer granting SCC to service accounts, not human users.

Better:

```bash
oc create sa mysql-sa -n database
oc adm policy add-scc-to-user anyuid -z mysql-sa -n database
oc set serviceaccount deployment/mysql mysql-sa -n database
```

Riskier:

```bash
oc adm policy add-scc-to-user anyuid bob
```

Granting SCC to a human can let them create workloads with that SCC in multiple places depending on binding scope and context.

### 16.4 SCC and RBAC troubleshooting

Symptom:

```text
Error creating: pods "app-..." is forbidden: unable to validate against any security context constraint
```

Check service account:

```bash
oc get deploy app -n app-project -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

Check SCC access:

```bash
oc adm policy who-can use scc anyuid
oc auth can-i use scc/anyuid --as=system:serviceaccount:app-project:app-sa
```

Grant only if justified:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n app-project
```

## 17. RBAC and Service Account Tokens

Service accounts authenticate workloads to the OpenShift API.

### 17.1 Why service account RBAC matters

If a pod is compromised, the attacker may attempt to use the pod's service account token.

Check inside a pod:

```bash
ls /var/run/secrets/kubernetes.io/serviceaccount/
```

Common files:

```text
ca.crt
namespace
token
```

Depending on platform version and token projection behavior, tokens may be bounded and time-limited rather than old long-lived secret-based tokens.

### 17.2 Best practices

- Create one service account per application or automation workflow.
- Bind narrow roles to that service account.
- Avoid using the `default` service account for privileged tasks.
- Avoid broad role grants to `system:serviceaccounts`.
- Rotate/delete old long-lived service account token secrets if they exist and are not needed.
- Prefer bound, audience-specific, time-bound service account tokens when integrating with cloud IAM or external systems.

### 17.3 Disable automount where possible

If an application does not need to talk to the Kubernetes/OpenShift API, disable token automount.

At service account level:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: app-prod
automountServiceAccountToken: false
```

At pod level:

```yaml
spec:
  automountServiceAccountToken: false
```

## 18. RBAC and Certificates / OAuth / Identity Providers

Because this topic sits under Security and Certificates, it is important to connect RBAC with authentication and certificate trust.

### 18.1 Certificate trust secures the API connection

When you run:

```bash
oc login https://api.ocp4.example.com:6443
```

TLS certificates protect the connection and help the client verify the API server identity.

If certificates are wrong or untrusted, users may see TLS errors before RBAC is even evaluated.

### 18.2 OAuth authenticates users

OpenShift users commonly authenticate through OAuth backed by an identity provider:

- HTPasswd
- LDAP
- OIDC
- GitHub/GitLab/Google depending on configuration

After login, OpenShift issues an OAuth token. That token identifies the user and groups. RBAC then evaluates permissions.

### 18.3 Identity provider groups drive RBAC

A production-grade design should avoid local one-off bindings and instead map enterprise identity groups to OpenShift groups.

Example:

```bash
oc adm groups new payments-dev alice bob charlie
oc adm policy add-role-to-group edit payments-dev -n payments-dev
oc adm policy add-role-to-group view payments-dev -n payments-prod
```

In LDAP-integrated environments, use LDAP group sync or identity mapping processes so RBAC follows corporate joiner/mover/leaver workflows.

### 18.4 kubeconfig client certificate identity

Some kubeconfigs authenticate with certificates. The certificate subject can map to a Kubernetes/OpenShift username and groups. Once authenticated, the same RBAC engine decides permissions.

### 18.5 Break-glass access

For production clusters, maintain a secure break-glass process:

- Small number of emergency cluster admins.
- MFA or secure vault process.
- Audit trail.
- Time-bound access if possible.
- Remove unused `kubeadmin` after creating named cluster administrators.

## 21. Advanced Patterns

### 21.1 ClusterRole aggregation

ClusterRole aggregation lets you extend default user-facing roles such as `admin`, `edit`, and `view` for custom resources.

Example: allow `view` users to read a custom resource called `widgets`.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: aggregate-widgets-view
  labels:
    rbac.authorization.k8s.io/aggregate-to-view: "true"
rules:
- apiGroups: ["apps.example.com"]
  resources: ["widgets"]
  verbs: ["get", "list", "watch"]
```

Use this for CRDs where standard OpenShift roles should automatically include custom resource permissions.

Do not use aggregation casually. It changes permissions for all subjects using the aggregated role.

### 21.2 Delegated project administration

A platform team may grant project admins local `admin` but not cluster-admin.

```bash
oc adm policy add-role-to-group admin app-admins -n app-dev
```

This allows team-level control inside one namespace without granting cluster-wide control.

### 21.3 Namespace onboarding template

For enterprise onboarding, create a repeatable RBAC template:

```text
<app>-dev-admins      -> admin in <app>-dev
<app>-dev-developers  -> edit in <app>-dev
<app>-prod-readers    -> view in <app>-prod
<app>-prod-ops        -> custom ops role in <app>-prod
ci:deploy-bot         -> custom deploy role in dev/test/prod as needed
```

### 21.4 Separate human and automation access

Humans:

```text
LDAP/OIDC group -> OpenShift group -> RoleBinding
```

Automation:

```text
ServiceAccount -> narrow RoleBinding -> namespace-specific permissions
```

Avoid using human user tokens in CI/CD systems.

### 21.5 Time-bound elevated access

OpenShift RBAC does not natively expire RoleBindings. For time-bound access, use:

- External IAM workflow.
- GitOps pull request with automated removal.
- Ticket-based automation.
- Periodic audit job.
- Temporary group membership in identity provider.

## 22. Common Misconfigurations

### 22.1 Accidentally using ClusterRoleBinding

Bad:

```bash
oc adm policy add-cluster-role-to-user edit bob
```

This grants Bob edit-like permissions across all projects.

Better:

```bash
oc adm policy add-role-to-user edit bob -n apollo
```

### 22.2 Granting `cluster-admin` for application troubleshooting

Bad:

```bash
oc adm policy add-cluster-role-to-user cluster-admin appuser
```

Better:

```bash
oc adm policy add-role-to-user view appuser -n app-prod
oc adm policy add-role-to-user support-readonly-no-secrets appuser -n app-prod
```

### 22.3 Binding to the wrong namespace

Command:

```bash
oc adm policy add-role-to-user view bob
```

If `-n` is omitted, it uses the current project. Always specify `-n` in production change commands.

Better:

```bash
oc adm policy add-role-to-user view bob -n app-prod
```

### 22.4 Granting SCC to wrong service account

If deployment runs as `default`, but you granted SCC to `app-sa`, the pod still fails.

Check:

```bash
oc get deploy app -n app-prod -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

Set service account:

```bash
oc set serviceaccount deployment/app app-sa -n app-prod
```

### 22.5 Assuming `view` can read secrets

It normally cannot. If a support team needs one specific secret, create a very explicit role for that secret only, and document why.

### 22.6 Granting `pods/exec` widely

`pods/exec` is command execution. Treat it like SSH into an application container.

### 22.7 Editing default `system:` ClusterRoles

Do not manually edit system roles. Create custom roles.

### 22.8 Granting to all service accounts

Bad:

```bash
oc adm policy add-cluster-role-to-group view system:serviceaccounts
```

This grants access to every service account in the cluster.

## 23. Troubleshooting RBAC

### 23.1 Error: Forbidden

Example:

```text
Error from server (Forbidden): pods is forbidden: User "bob" cannot list resource "pods" in API group "" in the namespace "apollo"
```

Interpretation:

```text
User: bob
Verb: list
Resource: pods
API group: core
Namespace: apollo
Decision: denied
```

Check:

```bash
oc auth can-i list pods -n apollo --as=bob
oc get rolebinding -n apollo -o wide
oc describe rolebinding -n apollo
oc adm policy who-can list pods -n apollo
```

Fix:

```bash
oc adm policy add-role-to-user view bob -n apollo
```

### 23.2 User can login but sees no projects

Check:

```bash
oc whoami
oc get projects
oc auth can-i get projects
oc adm policy who-can get projects
```

Likely causes:

- User has no RoleBinding in any project.
- Self-provisioner has been removed.
- Identity provider authentication works, but group mapping is missing.

### 23.3 User cannot create projects

Check:

```bash
oc auth can-i create projectrequests --as=bob
oc describe clusterrolebinding self-provisioners
```

Restore self-provisioning if policy allows:

```bash
oc adm policy add-cluster-role-to-group self-provisioner system:authenticated:oauth
```

Disable if enterprise policy requires central project creation:

```bash
oc adm policy remove-cluster-role-from-group self-provisioner system:authenticated:oauth
```

### 23.4 Service account cannot list pods

Check:

```bash
oc auth can-i list pods -n app-prod --as=system:serviceaccount:ci:deploy-bot
oc get rolebinding -n app-prod -o yaml | grep -A5 -B5 deploy-bot
```

Fix:

```bash
oc adm policy add-role-to-user view system:serviceaccount:ci:deploy-bot -n app-prod
```

Or use a custom role.

### 23.5 Pod fails because of SCC

Error:

```text
unable to validate against any security context constraint
```

Check:

```bash
oc get pod <pod> -n <ns> -o yaml | grep -i serviceAccount
oc adm policy who-can use scc anyuid
oc auth can-i use scc/anyuid --as=system:serviceaccount:<ns>:<sa>
```

Fix only after validating the workload requirement:

```bash
oc adm policy add-scc-to-user anyuid -z <sa> -n <ns>
```

### 23.6 Role exists but binding fails

Common issue: using RoleBinding to reference a Role in another namespace. RoleBinding can reference:

- A Role in the same namespace
- A ClusterRole

It cannot reference a Role from a different namespace.

### 23.7 `oc auth can-i` says yes, but action still fails

RBAC is only one layer. Check:

- Admission controllers
- ResourceQuota
- LimitRange
- SCC / Pod Security Admission
- Operator webhook validation
- NetworkPolicy for runtime traffic
- Image pull secrets
- StorageClass / PVC issues

## 24. Auditing and Compliance Checklist

### 24.1 Cluster admin audit

```bash
oc get clusterrolebinding -o json | jq -r '
  .items[] |
  select(.roleRef.name=="cluster-admin") |
  .metadata.name as $binding |
  .subjects[]? |
  [$binding, .kind, .name, (.namespace // "-")] | @tsv'
```

Questions:

- Who has cluster-admin?
- Is every entry justified?
- Are there direct user bindings that should be group-based?
- Are break-glass accounts documented?

### 24.2 Secret access audit

```bash
oc adm policy who-can get secrets --all-namespaces
oc adm policy who-can list secrets --all-namespaces
```

Questions:

- Which groups can read secrets?
- Do support users need this?
- Do CI/CD service accounts have broader secret access than required?

### 24.3 Pod exec audit

```bash
oc adm policy who-can create pods/exec --all-namespaces
oc adm policy who-can get pods/exec --all-namespaces
```

Questions:

- Who can exec into production pods?
- Is exec access break-glass only?
- Are audit logs reviewed?

### 24.4 SCC audit

```bash
oc adm policy who-can use scc privileged
oc adm policy who-can use scc anyuid
oc adm policy who-can use scc hostmount-anyuid
oc adm policy who-can use scc hostnetwork
```

Questions:

- Which service accounts can use privileged SCCs?
- Are SCC grants namespace-scoped?
- Are default SCCs modified? They should not be.

### 24.5 Wildcard audit

```bash
oc get clusterrole -o yaml | grep -B5 -A10 'verbs:.*\*'
oc get clusterrole -o yaml | grep -B5 -A10 'resources:.*\*'
```

Questions:

- Are wildcard roles custom-created?
- Who are they bound to?
- Are they temporary or permanent?

### 24.6 Service account audit

```bash
oc get rolebinding,clusterrolebinding -A -o yaml | grep -B5 -A10 'ServiceAccount'
```

Questions:

- Does every automation service account have a narrow purpose?
- Are any service accounts bound to cluster-admin?
- Are any bindings to `system:serviceaccounts` too broad?

## 25. Real-World Scenarios

### Scenario 1: Developer needs edit access in dev but read-only in prod

Requirement:

```text
Group payments-devs should edit payments-dev, but only view payments-prod.
```

Commands:

```bash
oc adm policy add-role-to-group edit payments-devs -n payments-dev
oc adm policy add-role-to-group view payments-devs -n payments-prod
```

Verify:

```bash
oc auth can-i create deployment -n payments-dev --as=alice
oc auth can-i create deployment -n payments-prod --as=alice
oc auth can-i get pods -n payments-prod --as=alice
```

Expected:

```text
create deployment in payments-dev: yes
create deployment in payments-prod: no
get pods in payments-prod: yes
```

### Scenario 2: User qwerty must not create projects

Remove self-provisioner from authenticated users:

```bash
oc adm policy remove-cluster-role-from-group self-provisioner system:authenticated:oauth
```

Verify:

```bash
oc auth can-i create projectrequests --as=qwerty
```

Expected:

```text
no
```

### Scenario 3: Service account needs anyuid for MySQL image

Some database images need a fixed UID or root-like behavior. Prefer non-root-compatible images first. If business requirement remains:

```bash
oc new-project database
oc create sa mysql-sa -n database
oc adm policy add-scc-to-user anyuid -z mysql-sa -n database
oc set serviceaccount deployment/mysql mysql-sa -n database
```

Verify:

```bash
oc auth can-i use scc/anyuid --as=system:serviceaccount:database:mysql-sa
oc get deploy mysql -n database -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

### Scenario 4: Support team needs logs but not secrets

Apply support role from [20.1](#201-read-only-support-role-without-secrets), then:

```bash
oc adm policy add-role-to-group support-readonly-no-secrets support-team -n app-prod
```

Verify:

```bash
oc auth can-i get pods/log -n app-prod --as=support-user
oc auth can-i get secrets -n app-prod --as=support-user
```

Expected:

```text
get pods/log: yes
get secrets: no
```

### Scenario 5: CI/CD can deploy only one namespace

Create service account:

```bash
oc create sa deploy-bot -n ci
```

Apply `cicd-deployer` role in target namespace and RoleBinding to service account.

Verify:

```bash
oc auth can-i patch deployments -n payments-dev --as=system:serviceaccount:ci:deploy-bot
oc auth can-i patch deployments -n payments-prod --as=system:serviceaccount:ci:deploy-bot
```

Expected depends on where you created the RoleBinding.

## 26. Interview / Exam Notes

### 26.1 Must-know commands

```bash
oc auth can-i <verb> <resource> -n <namespace>
oc auth can-i <verb> <resource> -n <namespace> --as=<user>
oc adm policy who-can <verb> <resource> -n <namespace>
oc adm policy add-role-to-user <role> <user> -n <namespace>
oc adm policy add-role-to-group <role> <group> -n <namespace>
oc adm policy add-cluster-role-to-user <role> <user>
oc adm policy remove-cluster-role-from-user <role> <user>
oc adm policy add-scc-to-user <scc> -z <serviceaccount> -n <namespace>
```

### 26.2 Common exam traps

| Trap | Correct Thinking |
|---|---|
| Forgetting `-n` | Always specify namespace explicitly |
| Using ClusterRoleBinding instead of RoleBinding | ClusterRoleBinding is cluster-wide |
| Granting SCC to wrong service account | Check deployment `serviceAccountName` |
| Assuming authentication problem when error is Forbidden | Forbidden usually means RBAC authorization failure |
| Assuming RBAC can fix SCC errors | SCC is admission, not normal RBAC resource access only |
| Giving `edit` when only logs are needed | Create custom log-reader role |
| Testing as yourself instead of target user | Use `--as=<user>` |
| Using `view` and expecting secret access | `view` normally does not allow reading secrets |

### 26.3 Fast answer patterns

Task: Give Bob view access to project `apollo`.

```bash
oc adm policy add-role-to-user view bob -n apollo
oc auth can-i get pods -n apollo --as=bob
```

Task: Give group `site-users` edit access to project `test`.

```bash
oc adm policy add-role-to-group edit site-users -n test
oc auth can-i create deployments -n test --as=<member-user>
```

Task: Prevent qwerty from creating projects.

```bash
oc adm policy remove-cluster-role-from-user self-provisioner qwerty
# If self-provisioner is granted to the authenticated group, remove it from that group:
oc adm policy remove-cluster-role-from-group self-provisioner system:authenticated:oauth
```

Task: Allow service account `project1-sa` to run anyuid in namespace `qed`.

```bash
oc adm policy add-scc-to-user anyuid -z project1-sa -n qed
oc auth can-i use scc/anyuid --as=system:serviceaccount:qed:project1-sa
```

## 27. Quick Revision Sheet

```text
RBAC = Authorization, not authentication.
Authentication says who you are.
RBAC says what you can do.
Admission decides whether the object is acceptable.
```

```text
Role = namespaced rules.
ClusterRole = cluster-level reusable rules.
RoleBinding = namespace-scoped grant.
ClusterRoleBinding = cluster-wide grant.
```

```text
RoleBinding can bind Role or ClusterRole.
ClusterRoleBinding can bind only ClusterRole.
```

```text
No deny rules.
Permissions are additive.
No matching rule = denied by default.
```

```text
Use groups for humans.
Use dedicated service accounts for workloads.
Avoid broad ClusterRoleBindings.
Avoid wildcard rules.
Avoid secret access unless required.
Treat pods/exec as privileged operational access.
Grant SCC to service accounts, not human users, whenever possible.
```

```bash
# Check permission
oc auth can-i create pods -n app --as=bob

# Find who can do something
oc adm policy who-can get secrets -n app

# Local access
oc adm policy add-role-to-user view bob -n app

# Cluster access
oc adm policy add-cluster-role-to-user cluster-reader auditor

# SCC access
oc adm policy add-scc-to-user anyuid -z app-sa -n app
```
