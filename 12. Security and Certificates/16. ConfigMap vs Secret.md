# ConfigMap vs Secret in OpenShift Security and Certificates

**Audience:** Advanced OpenShift administrators, SREs, DevOps engineers, platform engineers  
**Experience level:** 10+ years Linux / Kubernetes / OpenShift operations  
**Scope:** OpenShift Container Platform 4.x, Kubernetes-native ConfigMaps and Secrets, security, certificates, RBAC, etcd encryption, troubleshooting, and production patterns

---

## 1. Executive Summary

In OpenShift, **ConfigMap** and **Secret** are both Kubernetes API objects used to externalize data from container images and workload manifests. They look similar because both can be consumed as environment variables, command-line arguments, or mounted files. However, they have very different operational and security intent.

A **ConfigMap** is for **non-sensitive configuration**:

- application properties
- feature flags
- endpoint names
- non-secret CA bundles
- application tuning values
- nginx/httpd config files
- Java properties
- logging configuration

A **Secret** is for **sensitive material**:

- passwords
- API tokens
- OAuth client secrets
- SSH private keys
- TLS private keys
- image registry credentials
- database credentials
- service account tokens

The most important point for senior administrators is this:

> A Kubernetes Secret is **not automatically a vault**. Secret values are base64-encoded in manifests and API responses. Base64 is encoding, not encryption. Real protection depends on RBAC, namespace isolation, OpenShift etcd encryption, workload isolation, node security, audit controls, and preferably external secret management for high-value credentials.

In OpenShift certificate administration, you will see both objects used together:

- the **TLS private key and certificate** are stored in a **Secret**
- the **trusted CA bundle** is commonly distributed through a **ConfigMap**
- the **service serving certificate** generated by OpenShift is stored in a **Secret**
- the **service CA bundle** can be injected into a **ConfigMap**

## 2. Quick Comparison Table

| Area | ConfigMap | Secret |
|---|---|---|
| Purpose | Non-sensitive configuration | Sensitive data |
| Typical examples | app config, feature flags, CA bundle, log level | password, token, TLS key, registry auth |
| API kind | `ConfigMap` | `Secret` |
| Namespace scoped | Yes | Yes |
| Stored in etcd | Yes | Yes |
| Default encryption in etcd | Not encrypted unless OpenShift etcd encryption is enabled | Not encrypted unless OpenShift etcd encryption is enabled |
| Manifest value format | Plain strings in `data`, base64 in `binaryData` | base64 in `data`, plain input accepted in `stringData` |
| Confidentiality | No | Better handling than ConfigMap, but still requires security controls |
| Volume mount support | Yes | Yes |
| Environment variable support | Yes | Yes |
| Auto-update when mounted as volume | Eventually yes, except `subPath` | Eventually yes, except `subPath` |
| Auto-update when used as env var | No, pod restart required | No, pod restart required |
| Common OpenShift certificate use | CA bundle distribution | TLS certificate and private key storage |
| Size guidance | Do not use for large data; object data limit is 1 MiB | Individual Secret limit is 1 MiB |
| RBAC risk | Usually lower, but can leak internal config | High. `get/list/watch secrets` can expose credentials |
| GitOps storage | Can usually be stored in Git if non-sensitive | Do not store raw Secret values in Git; use SOPS, Sealed Secrets, External Secrets, Vault, etc. |

---

## 3. Why OpenShift Uses ConfigMaps and Secrets

Containers should be immutable and portable. A container image should not be rebuilt every time an endpoint, feature flag, password, certificate, or environment-specific setting changes.

OpenShift uses ConfigMaps and Secrets to separate:

```text
Container image       = application binary/runtime
Deployment manifest   = desired runtime state
ConfigMap             = non-sensitive runtime config
Secret                = sensitive runtime config
```

This improves:

- portability across dev, test, staging, and production
- separation of duties between app teams and platform/security teams
- safer image promotion
- GitOps workflows
- certificate and credential rotation
- cluster-wide policy enforcement

A 10-year admin should not treat these as simple key-value stores only. They are part of the platform security boundary.

## 4. ConfigMap Deep Dive

### 4.1 What Is a ConfigMap?

A ConfigMap is a namespaced Kubernetes API object that stores configuration data as key-value pairs. It is intended for data that does **not** require confidentiality.

Example ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: production
data:
  APP_MODE: "prod"
  LOG_LEVEL: "info"
  DATABASE_HOST: "mysql.production.svc.cluster.local"
  nginx.conf: |
    server {
      listen 8080;
      location /healthz {
        return 200 'ok';
      }
    }
```

A ConfigMap has two primary data fields:

```yaml
data:        # UTF-8 string values
binaryData:  # base64-encoded binary values
```

Use ConfigMaps for configuration that can be safely shown to developers, operators, CI/CD logs, Git repositories, and support bundles.

### 4.2 What Should Go in a ConfigMap?

Good ConfigMap data:

```text
LOG_LEVEL=debug
FEATURE_X_ENABLED=true
APP_THEME=dark
DATABASE_HOST=mysql.prod.svc.cluster.local
CACHE_TTL_SECONDS=300
TRUSTED_CA_PATH=/etc/pki/ca-trust/source/anchors/internal-ca.crt
```

Bad ConfigMap data:

```text
DATABASE_PASSWORD=redhat123
PRIVATE_KEY=-----BEGIN PRIVATE KEY-----
AWS_SECRET_ACCESS_KEY=...
TOKEN=...
```

If compromise of the value can give access to a system, account, database, registry, API, or private key, use a Secret or an external secret manager.

### 4.3 Create ConfigMap with `oc`

From literals:

```bash
oc create configmap app-config \
  --from-literal=APP_MODE=prod \
  --from-literal=LOG_LEVEL=info \
  -n production
```

From a file:

```bash
oc create configmap nginx-config \
  --from-file=nginx.conf \
  -n production
```

From an environment file:

```bash
cat > app.env <<'EOF_ENV'
APP_MODE=prod
LOG_LEVEL=info
FEATURE_LOGIN=true
EOF_ENV

oc create configmap app-config --from-env-file=app.env -n production
```

Export as YAML:

```bash
oc get configmap app-config -n production -o yaml
```

### 4.4 Consume ConfigMap as Environment Variables

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: frontend
        image: registry.ocp4.example.com:8443/apps/frontend:v1
        envFrom:
        - configMapRef:
            name: app-config
```

Or use a specific key:

```yaml
env:
- name: LOG_LEVEL
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: LOG_LEVEL
```

Important behavior:

> If a ConfigMap is consumed as an environment variable, updates to the ConfigMap are **not** automatically reflected in the running container. You must restart or roll out pods.

Common command:

```bash
oc rollout restart deployment/frontend -n production
```

### 4.5 Consume ConfigMap as Mounted Files

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: registry.access.redhat.com/ubi9/nginx-120
        volumeMounts:
        - name: nginx-config
          mountPath: /etc/nginx/conf.d
          readOnly: true
      volumes:
      - name: nginx-config
        configMap:
          name: nginx-config
```

Each key in the ConfigMap becomes a file under the mount path.

Example:

```text
ConfigMap key: nginx.conf
Mounted path: /etc/nginx/conf.d/nginx.conf
```

Important behavior:

- Volume-mounted ConfigMap updates are eventually reflected in the pod.
- The application may still need to reload its configuration.
- If mounted with `subPath`, updates are not automatically reflected.

### 4.6 ConfigMap Size and Design Limit

ConfigMaps are not for large files, binaries, or application packages. Use a PVC, object storage, image layer, or external config service for large data.

Practical guidance:

- keep ConfigMaps small
- split unrelated config into multiple ConfigMaps
- avoid using ConfigMaps as a database
- avoid frequently changing high-cardinality ConfigMaps at scale
- use immutable ConfigMaps for release-versioned configuration

### 4.7 Immutable ConfigMap

An immutable ConfigMap cannot be edited after creation. You must delete and recreate it, usually with a new name.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v1
  namespace: production
data:
  LOG_LEVEL: "info"
immutable: true
```

Recommended production pattern:

```text
app-config-v1
app-config-v2
app-config-v3
```

Update Deployment to reference the new ConfigMap name and roll out the workload.

This is safer than editing a shared ConfigMap used by many pods.

## 5. Secret Deep Dive

### 5.1 What Is a Secret?

A Secret is a namespaced Kubernetes API object intended to store a small amount of sensitive data.

Example Secret using `stringData`:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: production
type: Opaque
stringData:
  username: appuser
  password: SuperSecretPassword123
```

After creation, the API stores values under `data` as base64-encoded strings:

```yaml
data:
  username: YXBwdXNlcg==
  password: U3VwZXJTZWNyZXRQYXNzd29yZDEyMw==
```

Important:

> Base64 is not encryption. Anyone who can read the Secret can decode it.

Decode example:

```bash
oc get secret db-credentials -n production \
  -o jsonpath='{.data.password}' | base64 -d; echo
```

### 5.2 Create Secret with `oc`

From literals:

```bash
oc create secret generic db-credentials \
  --from-literal=username=appuser \
  --from-literal=password='SuperSecretPassword123' \
  -n production
```

From files:

```bash
oc create secret generic ssh-key-secret \
  --from-file=ssh-privatekey=/home/user/.ssh/id_rsa \
  --type=kubernetes.io/ssh-auth \
  -n production
```

TLS Secret:

```bash
oc create secret tls app-tls \
  --cert=tls.crt \
  --key=tls.key \
  -n production
```

Docker registry Secret:

```bash
oc create secret docker-registry private-registry-auth \
  --docker-server=registry.example.com \
  --docker-username=myuser \
  --docker-password='mypassword' \
  --docker-email=admin@example.com \
  -n production
```

Link image pull secret to ServiceAccount:

```bash
oc secrets link default private-registry-auth --for=pull -n production
```

### 5.3 Common Secret Types

| Secret type | Purpose |
|---|---|
| `Opaque` | Generic key-value sensitive data |
| `kubernetes.io/tls` | TLS certificate and private key, usually `tls.crt` and `tls.key` |
| `kubernetes.io/dockerconfigjson` | Image registry authentication |
| `kubernetes.io/dockercfg` | Older Docker config format |
| `kubernetes.io/basic-auth` | Basic authentication username/password convention |
| `kubernetes.io/ssh-auth` | SSH private key convention |
| `kubernetes.io/service-account-token` | Legacy long-lived ServiceAccount token Secret |
| `bootstrap.kubernetes.io/token` | Node/bootstrap token use cases |

For modern Kubernetes/OpenShift, avoid manually creating long-lived service account token Secrets unless there is a strong reason. Prefer short-lived projected tokens where possible.

### 5.4 Consume Secret as Environment Variables

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: backend
        image: registry.ocp4.example.com:8443/apps/backend:v1
        env:
        - name: DB_USERNAME
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: username
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: password
```

Operational caution:

- Environment variables are easy for applications to consume.
- But they can be exposed in debugging output, crash dumps, process inspection, accidental logs, or application diagnostics.
- They do not update in a running container when the Secret changes.

For highly sensitive values, prefer mounted files with strict file permissions and application reload logic.

### 5.5 Consume Secret as Mounted Files

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: backend
        image: registry.ocp4.example.com:8443/apps/backend:v1
        volumeMounts:
        - name: db-secret
          mountPath: /etc/secrets/db
          readOnly: true
      volumes:
      - name: db-secret
        secret:
          secretName: db-credentials
          defaultMode: 0400
```

Inside the container:

```bash
ls -l /etc/secrets/db
cat /etc/secrets/db/username
cat /etc/secrets/db/password
```

Mounted Secret update behavior:

- Kubernetes/OpenShift eventually updates projected Secret volume content.
- Applications may need to reload files.
- `subPath` mounts do not receive automatic updates.
- Environment variable usage requires pod restart.

### 5.6 Secret Size Limit

Individual Secrets are limited to 1 MiB. Do not store large certificates chains, binary bundles, keystores, dumps, or application artifacts in Secrets.

Better alternatives:

- external secret manager
- CSI Secret Store driver
- PVC with controlled access
- image layer for non-sensitive files
- object storage
- compressed artifact repository

### 5.7 Immutable Secret

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials-v1
  namespace: production
type: Opaque
stringData:
  username: appuser
  password: SuperSecretPassword123
immutable: true
```

Once immutable, it cannot be changed. You must create a new Secret and update workloads.

Production rotation pattern:

```text
db-credentials-v1 -> db-credentials-v2 -> db-credentials-v3
```

Then update Deployment reference and roll pods.

## 6. Security Reality: Secret Is Not Enough

### 6.1 Base64 Is Not Encryption

A Secret manifest often looks safe because the values are base64-encoded:

```yaml
data:
  password: cmVkaGF0MTIz
```

But decode is trivial:

```bash
echo 'cmVkaGF0MTIz' | base64 -d; echo
```

Output:

```text
redhat123
```

Therefore:

- Do not commit raw Kubernetes Secret YAML to Git.
- Do not paste Secret YAML in tickets, chats, or logs.
- Do not assume `oc get secret -o yaml` is safe.
- Do not grant `get/list/watch secrets` casually.

### 6.2 API Access Is the Main Secret Boundary

The biggest risk is not only etcd. It is API access.

Any user, group, or service account with these permissions can expose Secrets:

```text
get secrets
list secrets
watch secrets
create pods / deployments that mount secrets
update workloads to reference secrets
impersonate service accounts
exec into pods that already have mounted secrets
```

Important senior-admin rule:

> If a subject can create a pod in a namespace, it may be able to read Secrets in that namespace indirectly by mounting them into that pod.

Therefore, RBAC for Secrets must be designed together with workload creation permissions.

### 6.3 Dangerous Roles

Be careful with broad roles:

```bash
oc adm policy add-role-to-user edit alice -n production
oc adm policy add-role-to-user admin bob -n production
oc adm policy add-cluster-role-to-user cluster-admin charlie
```

The `edit` role can be dangerous for Secret isolation because users who can create or modify pods/deployments may indirectly access secrets available in that namespace.

For strict security, create custom roles.

Example read-only role for ConfigMaps only:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: configmap-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "watch"]
```

Bind it:

```bash
oc create rolebinding alice-configmap-reader \
  --role=configmap-reader \
  --user=alice \
  -n production
```

Example Secret reader for one service account only:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: specific-secret-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["db-credentials"]
  verbs: ["get"]
```

Bind to service account:

```bash
oc create rolebinding backend-secret-reader \
  --role=specific-secret-reader \
  --serviceaccount=production:backend-sa \
  -n production
```

### 6.4 Namespace Boundary

ConfigMaps and Secrets are namespace-scoped.

A pod in namespace `app1` cannot directly mount a Secret from namespace `app2`.

Bad design:

```text
One shared namespace for many teams and apps
```

Better design:

```text
namespace per application / team / environment
separate secrets per workload
separate service accounts per workload
least-privilege RBAC
```

Example:

```bash
oc new-project payment-prod
oc new-project inventory-prod
oc new-project frontend-prod
```

Do not put all production applications in one namespace unless you accept shared trust.

## 7. OpenShift etcd Encryption

### 7.1 What etcd Encryption Protects

OpenShift stores API objects in etcd. By default, etcd data is not encrypted in OpenShift Container Platform. You can enable etcd encryption to protect sensitive API resource values if an etcd backup or disk is exposed.

OpenShift etcd encryption can encrypt:

- Secrets
- ConfigMaps
- Routes
- OAuth access tokens
- OAuth authorize tokens

Important limitation:

> etcd encryption encrypts values, not object keys. Resource type, namespace, and object name remain visible.

Example: this may still be visible even when values are encrypted:

```text
namespace: production
kind: Secret
name: payment-gateway-prod-api-key
```

So do not reveal sensitive data in object names.

Bad names:

```text
mysql-root-password-redhat123
prod-aws-secret-key-akia...
payment-api-key-live
```

Better names:

```text
db-credentials
cloud-credentials
payment-gateway-credentials
```

### 7.2 Enable etcd Encryption in OpenShift

Check current setting:

```bash
oc get apiserver cluster -o yaml | grep -A5 encryption
```

Enable AES-GCM encryption:

```bash
oc edit apiserver cluster
```

Set:

```yaml
spec:
  encryption:
    type: aesgcm
```

Alternative patch:

```bash
oc patch apiserver cluster --type=merge -p '{"spec":{"encryption":{"type":"aesgcm"}}}'
```

Verify status:

```bash
oc get apiserver cluster -o jsonpath='{.spec.encryption.type}{"\n"}'

oc get kubeapiserver cluster -o yaml | grep -i encrypted -A5 -B5
oc get openshiftapiserver cluster -o yaml | grep -i encrypted -A5 -B5
```

Operational warnings:

- Initial encryption can take time depending on etcd size.
- Do not take etcd backups until the initial encryption process has completed.
- If encryption is enabled, backup material that contains encryption keys must be protected separately.
- Restoring encrypted etcd requires the matching encryption keys.

### 7.3 Why etcd Encryption Does Not Replace RBAC

etcd encryption protects data at rest. It does not protect data from authorized API reads.

If a user can run:

```bash
oc get secret db-credentials -n production -o yaml
```

then etcd encryption does not help, because the API server decrypts the data before returning it.

Defense layers:

```text
RBAC least privilege
+ namespace isolation
+ workload identity separation
+ etcd encryption
+ audit logs
+ node hardening
+ external secret management
+ GitOps secret encryption
```

## 8. ConfigMap vs Secret in Certificate Administration

This is where many OpenShift admins get confused.

### 8.1 Certificate Data Types

| Data | Sensitive? | Object |
|---|---:|---|
| TLS private key | Yes | Secret |
| TLS public certificate | Usually not secret, but paired with private key | Secret when used with key |
| CA bundle / root CA certificate | Usually not secret | ConfigMap |
| Route custom certificate and key | Yes | Secret or Route spec fields depending workflow |
| Service serving certificate private key | Yes | Secret generated by OpenShift |
| Trusted CA bundle for apps | No | ConfigMap |
| LDAP bind password | Yes | Secret |
| OAuth client secret | Yes | Secret |
| Registry pull credentials | Yes | Secret |

### 8.2 TLS Secret

Create a TLS Secret:

```bash
oc create secret tls backend-tls \
  --cert=backend.crt \
  --key=backend.key \
  -n production
```

YAML structure:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: backend-tls
  namespace: production
type: kubernetes.io/tls
data:
  tls.crt: <base64-cert>
  tls.key: <base64-key>
```

The `tls.key` is highly sensitive. Treat this Secret as privileged.

### 8.3 Mount TLS Secret into Pod

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: backend
        image: registry.ocp4.example.com:8443/apps/backend:v1
        volumeMounts:
        - name: tls
          mountPath: /etc/tls/private
          readOnly: true
      volumes:
      - name: tls
        secret:
          secretName: backend-tls
          defaultMode: 0400
```

Expected files:

```text
/etc/tls/private/tls.crt
/etc/tls/private/tls.key
```

### 8.4 Service Serving Certificate Secret in OpenShift

OpenShift can generate a serving certificate for a Service using the service CA operator.

Annotate the Service:

```bash
oc annotate service backend \
  service.beta.openshift.io/serving-cert-secret-name=backend-serving-cert \
  -n production
```

OpenShift creates a Secret:

```bash
oc get secret backend-serving-cert -n production
```

Expected keys:

```text
tls.crt
tls.key
```

Mount the generated Secret into the workload:

```yaml
volumes:
- name: serving-cert
  secret:
    secretName: backend-serving-cert

containers:
- name: backend
  volumeMounts:
  - name: serving-cert
    mountPath: /etc/tls/private
    readOnly: true
```

### 8.5 Service CA Bundle ConfigMap

To allow clients to trust service-serving certificates, inject the OpenShift service CA bundle into a ConfigMap.

Create ConfigMap:

```bash
oc create configmap service-ca-bundle -n production
```

Annotate it:

```bash
oc annotate configmap service-ca-bundle \
  service.beta.openshift.io/inject-cabundle=true \
  -n production
```

OpenShift injects:

```yaml
data:
  service-ca.crt: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

Important warning:

> When the service CA bundle is injected into a ConfigMap, OpenShift can replace/delete existing data in that ConfigMap. Use a dedicated ConfigMap only for the injected CA bundle.

### 8.6 Trusted CA Bundle Pattern

Common pattern:

```text
Server pod:
  mounts Secret with tls.crt + tls.key

Client pod:
  mounts ConfigMap with service-ca.crt or ca-bundle.crt
```

Server Deployment:

```yaml
volumes:
- name: server-tls
  secret:
    secretName: backend-serving-cert
```

Client Deployment:

```yaml
volumes:
- name: service-ca
  configMap:
    name: service-ca-bundle
    items:
    - key: service-ca.crt
      path: service-ca.crt
```

Client mount:

```yaml
volumeMounts:
- name: service-ca
  mountPath: /etc/pki/service-ca
  readOnly: true
```

## 9. Operational Update Behavior

### 9.1 Environment Variables

ConfigMap or Secret used as env var:

```yaml
envFrom:
- configMapRef:
    name: app-config
- secretRef:
    name: db-credentials
```

Update behavior:

```text
ConfigMap changed -> running env var does not change
Secret changed    -> running env var does not change
Pod restart       -> new value appears
```

Commands:

```bash
oc set env deployment/backend --from=secret/db-credentials -n production
oc rollout restart deployment/backend -n production
oc rollout status deployment/backend -n production
```

### 9.2 Volume Mounts

ConfigMap or Secret used as volume:

```yaml
volumes:
- name: config
  configMap:
    name: app-config
- name: secret
  secret:
    secretName: db-credentials
```

Update behavior:

```text
ConfigMap changed -> projected volume eventually updates
Secret changed    -> projected volume eventually updates
Application       -> may need reload/restart to re-read file
```

### 9.3 `subPath` Caveat

This pattern does not auto-update:

```yaml
volumeMounts:
- name: config
  mountPath: /etc/app/application.properties
  subPath: application.properties
```

Reason: `subPath` creates a bind mount to a specific file path at container start. Updates to the projected volume are not reflected into that bind mount.

Production advice:

- Avoid `subPath` for rotating Secrets/certificates.
- Mount the full directory when you expect updates.
- Use checksum annotations or rollout restart when config changes.

### 9.4 Application Reload

Even if the mounted file updates, your app may not reload it.

Common approaches:

1. Roll pods on config change.
2. App watches file changes and reloads.
3. Sidecar watches config and sends SIGHUP.
4. Operator reconciles Deployment when ConfigMap/Secret hash changes.
5. GitOps pipeline updates checksum annotation.

Example checksum annotation:

```yaml
template:
  metadata:
    annotations:
      configmap.revision/app-config: "2026-07-03-001"
      secret.revision/db-credentials: "2026-07-03-001"
```

Any change to pod template annotation triggers a rollout.

## 10. OpenShift RBAC and Secret Access

### 10.1 Check Who Can Read Secrets

```bash
oc policy who-can get secrets -n production
oc policy who-can list secrets -n production
oc policy who-can create pods -n production
oc policy who-can update deployments -n production
```

Do not check only `get secrets`. Check workload permissions too.

### 10.2 Can Current User Read Secret?

```bash
oc auth can-i get secret/db-credentials -n production
oc auth can-i list secrets -n production
oc auth can-i create pods -n production
oc auth can-i update deployment/backend -n production
```

As another user:

```bash
oc auth can-i get secret/db-credentials -n production --as=alice
oc auth can-i create pods -n production --as=alice
```

As service account:

```bash
oc auth can-i get secret/db-credentials \
  -n production \
  --as=system:serviceaccount:production:backend-sa
```

### 10.3 Least Privilege Design

Bad:

```bash
oc adm policy add-role-to-user admin app-team -n production
```

Better:

```text
Developers: view logs, view deployments, trigger rollout
CI/CD SA: update specific deployment, read specific configmaps, not list all secrets
Runtime SA: no API secret-read needed unless app calls API directly
Platform admins: break-glass access with audit
```

### 10.4 Why `list` and `watch` Are Dangerous

This is dangerous:

```yaml
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["list", "watch"]
```

It can expose every Secret in the namespace.

Prefer:

```yaml
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["specific-secret"]
  verbs: ["get"]
```

But remember: `resourceNames` cannot restrict `list/watch` safely in the same way as `get`.

## 11. ServiceAccounts, Image Pull Secrets, and Runtime Secrets

### 11.1 ServiceAccount Image Pull Secret

Image pull secret is used by kubelet to pull images.

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.ocp4.example.com:8443 \
  --docker-username=developer \
  --docker-password='redhat' \
  --docker-email=dev@example.com \
  -n demo

oc secrets link default regcred --for=pull -n demo
```

Check:

```bash
oc get sa default -n demo -o yaml
```

Expected:

```yaml
imagePullSecrets:
- name: regcred
```

### 11.2 Runtime Secret Mount

Runtime secret is used by the containerized application.

```yaml
volumes:
- name: db-credentials
  secret:
    secretName: db-credentials
```

Do not confuse:

| Secret use | Consumer |
|---|---|
| `imagePullSecrets` | kubelet/node pulling image |
| mounted Secret | application container |
| env Secret | application container |
| service account token | pod identity/API access |
| TLS Secret | router, app, ingress, webhook, or service |

### 11.3 Avoid Default ServiceAccount Abuse

Do not run every app with `default` ServiceAccount in production.

Create dedicated SA:

```bash
oc create sa backend-sa -n production
```

Use it:

```yaml
spec:
  serviceAccountName: backend-sa
```

Then bind only required access.

## 12. ConfigMap and Secret with GitOps

### 12.1 ConfigMap in Git

Usually acceptable if non-sensitive:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: production
data:
  LOG_LEVEL: "info"
  FEATURE_X: "true"
```

But still avoid putting internal secrets in names or values.

### 12.2 Secret in Git

Bad:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
data:
  password: cmVkaGF0MTIz
```

This is equivalent to storing the password in Git.

Better options:

| Pattern | Description |
|---|---|
| External Secrets Operator | Sync secrets from Vault, AWS Secrets Manager, Azure Key Vault, etc. |
| Sealed Secrets | Store encrypted Secret manifest that only cluster controller can decrypt |
| SOPS + KMS/GPG/Age | Encrypt YAML values in Git |
| Argo CD Vault Plugin | Inject secrets during sync from external secret store |
| HashiCorp Vault Agent/CSI | Mount or inject secrets dynamically |

### 12.3 GitOps Rotation Pattern

For ConfigMap:

```text
Change ConfigMap -> commit -> Argo CD sync -> rollout trigger -> pods restart
```

For Secret:

```text
Rotate in external manager -> controller syncs Kubernetes Secret -> workload reload/restart
```

Do not manually edit Secrets in production if GitOps owns the namespace, unless you understand reconciliation behavior.

## 13. Advanced Production Patterns

### 13.1 Versioned ConfigMaps

```text
app-config-20260703-001
app-config-20260703-002
```

Deployment references exact version:

```yaml
volumes:
- name: app-config
  configMap:
    name: app-config-20260703-002
```

Advantages:

- rollback is easy
- immutable behavior
- no surprise shared updates
- GitOps-friendly

### 13.2 Versioned Secrets

```text
db-credentials-v1
db-credentials-v2
```

Rotation sequence:

1. Create `db-credentials-v2`.
2. Update app to use v2.
3. Roll pods.
4. Verify app connection.
5. Revoke old DB credential.
6. Delete `db-credentials-v1`.

### 13.3 Dual Credential Rotation

For databases that support multiple users/passwords:

```text
Old secret active -> create new credential -> deploy app with new secret -> verify -> revoke old credential
```

This avoids downtime.

### 13.4 Certificate Rotation

TLS Secret rotation checklist:

```bash
# Check certificate expiry
oc get secret backend-tls -n production -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject -issuer -dates

# Create new TLS secret
oc create secret tls backend-tls-v2 --cert=new.crt --key=new.key -n production

# Update deployment to mount backend-tls-v2
oc set volume deployment/backend --remove --name=tls -n production
oc set volume deployment/backend --add --name=tls --type=secret --secret-name=backend-tls-v2 --mount-path=/etc/tls/private --read-only -n production

# Verify rollout
oc rollout status deployment/backend -n production
```

### 13.5 Separate Secret per Application

Bad:

```text
namespace: production
secret: all-prod-passwords
```

Better:

```text
payment-db-credentials
payment-api-token
inventory-db-credentials
frontend-oauth-client-secret
```

Benefits:

- smaller blast radius
- easier rotation
- clearer ownership
- better audit
- cleaner RBAC

### 13.6 Avoid Shared ConfigMap for Critical Apps

Bad:

```text
one global app-config used by 40 deployments
```

A small edit can break many workloads.

Better:

```text
frontend-config
backend-config
worker-config
payment-config
```

Or versioned immutable ConfigMaps per release.

## 14. Troubleshooting ConfigMap Issues

### 14.1 Pod Fails Because ConfigMap Missing

Symptoms:

```bash
oc get pods -n production
oc describe pod <pod> -n production
```

Events:

```text
configmap "app-config" not found
```

Fix:

```bash
oc get configmap app-config -n production
oc create configmap app-config --from-literal=LOG_LEVEL=info -n production
oc delete pod <pod> -n production
```

### 14.2 Key Missing

Event:

```text
couldn't find key LOG_LEVEL in ConfigMap production/app-config
```

Check:

```bash
oc get cm app-config -n production -o yaml
```

Patch:

```bash
oc patch cm app-config -n production --type=merge -p '{"data":{"LOG_LEVEL":"info"}}'
```

Restart if env var:

```bash
oc rollout restart deployment/backend -n production
```

### 14.3 Env Var Not Updated

Check inside pod:

```bash
oc rsh deployment/backend -n production
printenv | grep LOG_LEVEL
```

If ConfigMap changed but env var is old, restart pods:

```bash
oc rollout restart deployment/backend -n production
```

### 14.4 Mounted File Not Updated

Check if using `subPath`:

```bash
oc get deployment backend -n production -o yaml | grep -A5 subPath
```

If `subPath` exists, automatic update will not happen. Restart pod or redesign mount.

### 14.5 App Did Not Reload

Check file content:

```bash
oc rsh deployment/backend -n production
cat /etc/app/config/application.properties
```

If file is updated but app behavior did not change, the application did not reload configuration. Restart app/pod or implement reload.

## 15. Troubleshooting Secret Issues

### 15.1 Secret Missing

Event:

```text
secret "db-credentials" not found
```

Check:

```bash
oc get secret db-credentials -n production
oc describe pod <pod> -n production
```

Fix:

```bash
oc create secret generic db-credentials \
  --from-literal=username=appuser \
  --from-literal=password='SuperSecretPassword123' \
  -n production
```

### 15.2 Wrong Key Name

Event:

```text
couldn't find key password in Secret production/db-credentials
```

Inspect keys without printing values:

```bash
oc get secret db-credentials -n production -o jsonpath='{.data}' | jq 'keys'
```

Or:

```bash
oc get secret db-credentials -n production -o go-template='{{range $k,$v := .data}}{{printf "%s\n" $k}}{{end}}'
```

### 15.3 Decode Secret Value

```bash
oc get secret db-credentials -n production \
  -o jsonpath='{.data.password}' | base64 -d; echo
```

Use only in secure terminal sessions. Avoid copying output to tickets or chat.

### 15.4 ImagePullBackOff Due to Registry Secret

Symptoms:

```text
ErrImagePull
ImagePullBackOff
unauthorized: authentication required
```

Check pod:

```bash
oc describe pod <pod> -n production
```

Check ServiceAccount:

```bash
oc get sa default -n production -o yaml
```

Link pull secret:

```bash
oc secrets link default private-registry-auth --for=pull -n production
```

Restart pod:

```bash
oc delete pod <pod> -n production
```

### 15.5 TLS Secret Invalid

Check Secret type and keys:

```bash
oc get secret backend-tls -n production -o jsonpath='{.type}{"\n"}'
oc get secret backend-tls -n production -o go-template='{{range $k,$v := .data}}{{printf "%s\n" $k}}{{end}}'
```

Expected:

```text
kubernetes.io/tls
tls.crt
tls.key
```

Check certificate:

```bash
oc get secret backend-tls -n production -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject -issuer -dates
```

Check private key matches certificate:

```bash
oc get secret backend-tls -n production -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/tls.crt
oc get secret backend-tls -n production -o jsonpath='{.data.tls\.key}' | base64 -d > /tmp/tls.key

openssl x509 -noout -modulus -in /tmp/tls.crt | openssl md5
openssl rsa  -noout -modulus -in /tmp/tls.key | openssl md5
```

The MD5 hashes should match for RSA certificates.

### 15.6 Secret Updated but App Still Uses Old Password

Possible causes:

| Cause | Fix |
|---|---|
| Secret consumed as env var | Restart pods |
| Secret mounted using `subPath` | Restart pods or remove `subPath` |
| App caches credential | Reload app or restart pods |
| External DB password not actually changed | Verify external system |
| GitOps reverted Secret | Check Argo CD / controller sync |
| Secret name changed but Deployment still references old name | Inspect Deployment YAML |

Commands:

```bash
oc get deployment backend -n production -o yaml | grep -A10 -B5 secret
oc rollout restart deployment/backend -n production
oc rollout status deployment/backend -n production
```

## 16. Security Hardening Checklist

### 16.1 ConfigMap Hardening

- Do not store passwords, tokens, or private keys in ConfigMaps.
- Use dedicated ConfigMaps per app/component.
- Use immutable ConfigMaps for release-stable configuration.
- Avoid large ConfigMaps.
- Avoid sensitive data in ConfigMap names.
- Review ConfigMaps in support bundles before sharing externally.
- Use GitOps validation to reject sensitive key names like `PASSWORD`, `TOKEN`, `SECRET`, `PRIVATE_KEY` in ConfigMaps.

### 16.2 Secret Hardening

- Enable OpenShift etcd encryption.
- Restrict `get/list/watch secrets` with RBAC.
- Avoid broad `edit/admin` for untrusted users in sensitive namespaces.
- Use separate namespaces for separate trust zones.
- Use separate ServiceAccounts per workload.
- Use separate Secrets per application.
- Avoid storing raw Secrets in Git.
- Prefer external secret managers for production.
- Rotate credentials regularly.
- Avoid long-lived ServiceAccount token Secrets.
- Avoid printing Secret values in logs.
- Avoid mounting Secrets into containers that do not need them.
- Avoid privileged pods in namespaces with high-value Secrets.
- Use audit logs to detect Secret reads.

### 16.3 Certificate Hardening

- Store private keys only in Secrets.
- Store CA bundles in ConfigMaps when public/non-sensitive.
- Use dedicated ConfigMap for service CA injection.
- Monitor certificate expiry.
- Automate certificate rotation.
- Restart/reload apps after certificate Secret rotation if needed.
- Avoid `subPath` for mounted certificates that must rotate.
- Protect route wildcard certificates and ingress certificates as highly sensitive.

## 17. Admission and Policy Controls

Senior platform teams often enforce rules using admission controllers, Gatekeeper, Kyverno, or OpenShift policy mechanisms.

Example policies to enforce:

```text
Reject ConfigMaps containing keys matching PASSWORD|TOKEN|SECRET|PRIVATE_KEY
Reject Secrets without owner labels
Reject Secrets in GitOps namespaces unless encrypted workflow is used
Require immutable: true for ConfigMaps in production
Require dedicated serviceAccountName, not default
Deny privileged pods in namespaces containing high-value secrets
Deny pods mounting all-in-one shared secrets
Require certificate expiry annotation
```

Example labels:

```yaml
metadata:
  labels:
    app.kubernetes.io/name: payment-api
    app.kubernetes.io/part-of: payment-platform
    security.openshift.io/data-classification: confidential
    owner: platform-security
```

Example annotations:

```yaml
metadata:
  annotations:
    rotation.openshift.io/owner: platform-security
    rotation.openshift.io/interval: 90d
    rotation.openshift.io/last-rotated: "2026-07-03"
```

## 18. Auditing and Investigation

### 18.1 What to Investigate

When a Secret is suspected to be exposed, check:

```text
Who can get/list/watch secrets?
Who recently accessed the Secret?
Who can create pods in the namespace?
Which pods mount the Secret?
Which service accounts are used?
Was the Secret printed in logs?
Was the Secret committed to Git?
Was the Secret included in must-gather/support bundle?
Was the etcd backup exposed?
Was a privileged pod running on the same node?
```

### 18.2 Find Pods Mounting a Secret

```bash
SECRET_NAME=db-credentials
NAMESPACE=production

oc get pods -n "$NAMESPACE" -o json | jq -r \
  --arg SECRET "$SECRET_NAME" \
  '.items[] | select(.spec.volumes[]? | .secret?.secretName == $SECRET) | .metadata.name'
```

Find Deployments referencing a Secret:

```bash
oc get deploy -n production -o yaml | grep -B5 -A10 'secretName: db-credentials'
oc get deploy -n production -o yaml | grep -B5 -A10 'secretKeyRef:'
```

### 18.3 Find ConfigMaps Mounted by Pods

```bash
CONFIGMAP_NAME=app-config
NAMESPACE=production

oc get pods -n "$NAMESPACE" -o json | jq -r \
  --arg CM "$CONFIGMAP_NAME" \
  '.items[] | select(.spec.volumes[]? | .configMap?.name == $CM) | .metadata.name'
```

### 18.4 Check Secret RBAC Exposure

```bash
oc policy who-can get secrets -n production
oc policy who-can list secrets -n production
oc policy who-can watch secrets -n production
oc policy who-can create pods -n production
oc policy who-can update deployments -n production
```

## 19. Backup and Restore Considerations

### 19.1 etcd Backup

OpenShift etcd backup can contain ConfigMaps, Secrets, Routes, OAuth tokens, and encryption keys depending on configuration.

Protect:

```text
snapshot_<timestamp>.db
static_kuberesources_<timestamp>.tar.gz
```

If etcd encryption is enabled, the static Kubernetes resources archive can contain encryption keys required for restore. Store it securely and separately according to your backup policy.

### 19.2 Application Backup

Application backup tools such as OADP/Velero may back up Kubernetes objects including ConfigMaps and Secrets.

Checklist:

- Are Secrets included in backups?
- Are backups encrypted?
- Who can restore into another cluster?
- Are restored Secrets valid in the target environment?
- Are cloud credentials rotated after restore testing?
- Are TLS certificates still valid after restore?

### 19.3 Restore Risk

Restoring old Secrets can reintroduce old credentials.

After restore:

```text
Rotate DB passwords
Rotate API tokens
Rotate registry credentials
Rotate OAuth client secrets
Validate TLS certificate expiry
Validate service account tokens
```

## 20. Common Misconceptions

### Misconception 1: “Secret is encrypted because it is base64.”

False. Base64 is reversible encoding.

### Misconception 2: “ConfigMap is safe because it has no password.”

Not always. ConfigMaps can reveal internal service names, endpoints, feature flags, or security architecture. They are lower sensitivity than Secrets, not always public.

### Misconception 3: “etcd encryption means developers cannot see Secrets.”

False. If RBAC allows API access, the API server returns decrypted Secret data.

### Misconception 4: “Secret update instantly changes the app.”

Not if consumed as env var. Volume projection updates eventually, but the app may need reload.

### Misconception 5: “Namespace isolation means any user in a namespace can safely be admin.”

Not if the namespace contains high-value Secrets. Namespace admin can usually expose Secrets indirectly through workloads.

### Misconception 6: “CA certificate must be Secret.”

Usually no. CA public certificates are normally not confidential and are commonly distributed by ConfigMap. Private keys must be Secrets.

## 22. Exam and Interview Notes

### 22.1 When to Use ConfigMap

Use ConfigMap when:

```text
Data is not secret
Data configures app behavior
Data can be versioned in Git
Data can be seen by app operators
Data is a public CA bundle
```

### 22.2 When to Use Secret

Use Secret when:

```text
Data authenticates to something
Data authorizes access
Data includes private key material
Data includes password/token/API key
Data compromise causes security incident
```

## 23. Real-World Architecture Recommendation

For production OpenShift:

```text
1. Store non-sensitive app config in versioned immutable ConfigMaps.
2. Store sensitive data in Secrets only when Kubernetes-native storage is acceptable.
3. Use external secret management for high-value credentials.
4. Enable OpenShift etcd encryption.
5. Keep Secrets out of raw Git.
6. Use separate ServiceAccounts per workload.
7. Minimize RBAC access to Secrets.
8. Use namespace isolation for trust boundaries.
9. Avoid subPath for rotating Secret/ConfigMap mounts.
10. Automate rollout/reload after config, credential, or certificate changes.
11. Audit Secret access and workload creation permissions.
12. Protect etcd backups and Kubernetes resource backups.
```

Recommended model:

```text
Git repository:
  Deployment YAML
  Service YAML
  Route YAML
  ConfigMap YAML for non-sensitive values
  Encrypted Secret reference / ExternalSecret YAML

OpenShift cluster:
  ConfigMap for runtime config
  Secret synced from external manager
  ServiceAccount per app
  RBAC least privilege
  etcd encryption enabled
  audit enabled
```

## 24. Final Decision Matrix

Ask these questions:

### Question 1: Is the value sensitive?

```text
Yes -> Secret or external secret manager
No  -> ConfigMap
```

### Question 2: Is it a private key, password, token, or credential?

```text
Yes -> Secret/external secret manager
No  -> continue
```

### Question 3: Is it a CA certificate or public certificate only?

```text
CA/public cert only -> ConfigMap is usually fine
Private key included -> Secret
```

### Question 4: Does the app need automatic update without pod restart?

```text
Use mounted volume, avoid subPath, implement app reload
```

### Question 5: Will this be stored in Git?

```text
ConfigMap -> usually yes if non-sensitive
Secret -> only encrypted/sealed/external reference
```

### Question 6: Does a user with namespace access need to see it?

```text
If no, restrict RBAC and reconsider namespace design
```

## 25. One-Line Summary

**ConfigMap is for configuration; Secret is for sensitive data; neither is secure by naming alone. In OpenShift, real security comes from correct object choice plus RBAC, namespace isolation, etcd encryption, safe GitOps, node hardening, audit, and proper certificate/credential rotation.**
