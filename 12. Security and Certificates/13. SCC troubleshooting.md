## 1. Executive Summary

Security Context Constraints, usually called **SCCs**, are one of the most important OpenShift-specific security controls. In Kubernetes, a pod may define a `securityContext`, request Linux capabilities, ask to run as root, mount host paths, use host networking, or run privileged. In OpenShift, SCC admission decides whether that pod is allowed to enter the cluster and whether some missing security values should be defaulted.

For an experienced administrator, SCC troubleshooting is not simply running:

```bash
oc adm policy add-scc-to-user anyuid -z default -n myproject
```

That command may fix the symptom, but it can also weaken security for every pod using the `default` service account in that namespace. A senior OpenShift administrator must identify:

- Which service account created the pod.
- Which SCCs that service account is allowed to use.
- Which security field violates the SCC.
- Whether the workload truly needs more privileges.
- Whether the better fix is image hardening, YAML cleanup, service account isolation, a custom SCC, or a narrow RBAC binding.
- Whether Pod Security Admission is also warning, auditing, or enforcing a policy.

The correct mindset is:

> **Do not grant a stronger SCC until you understand exactly which Linux security feature the workload is requesting and why.**

## 2. What SCC Troubleshooting Really Means

SCC troubleshooting means diagnosing why OpenShift admission rejects, mutates, or restricts a pod because of security settings.

Typical failure areas include:

- Pod tries to run as UID `0`.
- Pod sets a fixed UID outside the project UID range.
- Pod requests `privileged: true`.
- Pod requests Linux capabilities not allowed by the selected SCC.
- Pod uses `hostNetwork`, `hostPID`, `hostIPC`, or `hostPort`.
- Pod mounts `hostPath`.
- Pod requests an SELinux label not allowed by the namespace.
- Pod sets an invalid `fsGroup` or supplemental group.
- Pod uses a Helm chart security context copied from upstream Kubernetes that is not OpenShift-compatible.
- Operator-created pods use a service account that lacks SCC permissions.
- The namespace has Pod Security Admission labels that create warnings or rejections independent of SCC.

SCC troubleshooting has two sides:

1. **Admission troubleshooting**  
   The pod does not get created, or ReplicaSet/Deployment events show `forbidden`, `unable to validate against any security context constraint`, or `would violate PodSecurity`.

2. **Runtime troubleshooting**  
   The pod is admitted but fails at runtime because of permissions, file ownership, SELinux, read-only filesystem, or missing Linux capabilities.

A common mistake is to treat both as the same. They are not. SCC admission happens before the pod starts. Runtime permission failures happen after the pod is scheduled and containers execute.

## 3. Why SCC Matters in Security and Certificates

SCC is not a certificate object. It does not issue TLS certificates, rotate ingress certificates, or manage CA bundles. However, SCC belongs in the broader **Security and Certificates** skill area because certificates are often consumed by workloads through Kubernetes Secrets, projected volumes, ConfigMaps, CSI drivers, or host-mounted trust stores.

Examples:

- A pod mounting a TLS Secret generally does **not** need a privileged SCC.
- A pod mounting `/etc/pki/ca-trust` from the host through `hostPath` likely needs a host-mount-capable SCC and should be questioned.
- A workload that wants to update system CA trust inside the container may fail because it runs as a random non-root UID.
- A certificate sidecar may fail if it expects to write to a root-owned path.
- A legacy Java app may fail if it expects to import certs into a root-owned JVM truststore at startup.
- A service mesh, certificate injector, CSI driver, or security agent may need elevated SCC permissions because it interacts with node-level resources.

A senior OpenShift administrator should first ask:

> Is this really an SCC problem, or is the image designed incorrectly for OpenShift's restricted security model?

For certificate-related workloads, the best production answer is often:

- Mount certificates as Secret volumes.
- Mount CA bundles as ConfigMap volumes.
- Write to an application-owned directory, not a system path.
- Build the image to run as non-root.
- Avoid hostPath unless the workload is a trusted node-level agent.

## 4. Core Concepts

### 4.1 What is an SCC?

A Security Context Constraint is a cluster-scoped OpenShift API object:

```yaml
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata:
  name: restricted-v2
```

An SCC controls what a pod can request in its security context. It can allow or deny:

- Privileged containers.
- Host networking.
- Host ports.
- Host PID namespace.
- Host IPC namespace.
- HostPath volumes.
- Linux capabilities.
- UID strategy.
- SELinux strategy.
- fsGroup strategy.
- Supplemental group strategy.
- Allowed volume types.
- Seccomp profiles.
- Privilege escalation.
- Read-only root filesystem rules.

SCC admission also defaults some values. For example, under `restricted-v2`, a pod that does not specify `runAsUser` may be assigned a UID from the namespace UID range.

### 4.2 SCC is Admission Control, Not Runtime Enforcement Alone

SCC works during admission. The API server evaluates the pod specification and decides whether the pod can be admitted. After admission, Linux kernel features, CRI-O, SELinux, seccomp, namespaces, cgroups, and container runtime behavior enforce the result at runtime.

This is why SCC troubleshooting often starts from events:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc describe deploy/<deployment> -n <namespace>
oc describe rs/<replicaset> -n <namespace>
oc describe pod/<pod> -n <namespace>
```

If the pod was never created, look at Deployment/ReplicaSet events. If the pod was created but crashed, look at pod events, logs, and container status.

### 4.3 The Service Account Is Usually the Key

Pods almost always run through a service account. If a workload does not specify one, it uses the `default` service account in that namespace.

Check the service account:

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

For a Deployment:

```bash
oc get deploy <deployment> -n <namespace> -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

If this prints nothing, Kubernetes defaults it to:

```text
default
```

In production, do not grant strong SCCs to `default` unless there is a very deliberate reason. Create a dedicated service account.

## 5. SCC vs Kubernetes SecurityContext vs Pod Security Admission

### 5.1 Kubernetes `securityContext`

The pod or container `securityContext` is what the workload requests.

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: registry.example.com/app:v1
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
```

The application author controls this YAML.

### 5.2 OpenShift SCC

SCC says whether the requested security context is allowed. It may also default some missing fields.

Example:

```bash
oc get scc restricted-v2 -o yaml
```

### 5.3 Pod Security Admission

Pod Security Admission, or PSA, is Kubernetes-native policy based on profiles:

- `privileged`
- `baseline`
- `restricted`

In OpenShift 4.x, SCC and PSA can both matter. SCC may mutate and validate the pod. PSA may also validate the pod against namespace labels.

Important distinction:

- SCC is OpenShift-specific and service-account-aware.
- PSA is Kubernetes-native and namespace-label-driven.
- SCC and PSA are independent controllers.

This means a pod can pass SCC but still produce PSA warnings, or an SCC grant can cause namespace PSA warning/audit label synchronization behavior.

### 5.4 RBAC

RBAC controls who can `use` an SCC.

Example:

```bash
oc auth can-i use scc/anyuid \
  --as=system:serviceaccount:myproject:app-sa \
  -n myproject
```

RBAC also protects against privilege escalation. A normal project admin usually cannot grant SCC use permissions unless they already have rights to do so.

## 6. SCC Admission Flow

When a pod creation request reaches OpenShift, the SCC admission logic follows a process similar to this:

1. Identify the user or controller creating the pod.
2. Identify the pod service account.
3. Build the list of SCCs the user or service account can use.
4. Sort SCCs by priority, restrictiveness, and name.
5. Try to apply each SCC to the pod.
6. Default missing values where strategy allows defaulting.
7. Validate requested security settings.
8. Admit the pod with an `openshift.io/scc` annotation if one SCC matches.
9. Reject the pod if no SCC matches.

After admission, you can see the selected SCC:

```bash
oc get pod <pod> -n <namespace> \
  -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

Example output:

```text
restricted-v2
```

If the pod was rejected, it will not have this annotation because it was never created.

## 7. Default SCCs and Their Risk Levels

OpenShift includes several default SCCs. Names can vary slightly by release, Operators, or components installed, but the common ones are:

| SCC | Typical Use | Risk Level | Notes |
|---|---|---:|---|
| `restricted-v2` | Default secure workload model | Low | Most normal apps should run here. Drops all capabilities, requires non-root-style behavior, uses runtime default seccomp. |
| `restricted` | Older restricted model | Low | Present for compatibility. Prefer `restricted-v2` where available. |
| `nonroot-v2` | Allows non-root workloads with more flexibility than restricted | Low/Medium | Useful when image needs a non-root UID but not necessarily namespace-assigned UID behavior. |
| `nonroot` | Older non-root SCC | Low/Medium | Compatibility. |
| `anyuid` | Allows arbitrary UID, including root | Medium/High | Common for legacy images. Use only with dedicated service accounts. |
| `hostnetwork` | Allows host networking/ports | High | Needed for some network agents, ingress-style components, or diagnostics. |
| `hostaccess` | Host namespace access with constraints | High | Trusted workloads only. |
| `hostmount-anyuid` | HostPath plus arbitrary UID | Very High | Dangerous; host filesystem access can break node isolation. |
| `hostmount-anyuid-v2` | Newer host mount variant in recent OCP | Very High | Added to address SELinux behavior around host paths in recent OCP releases. |
| `privileged` | Full privileged/host access | Critical | Use only for trusted cluster administration, node agents, CSI/CNI/security components. |

A practical rule:

> Use `restricted-v2` unless the workload proves that it needs exactly one additional permission. Then grant only that permission to only that service account.

## 8. How SCC Selection Works

SCC selection often surprises administrators.

### 8.1 Priority Matters

SCCs have a `priority` field. Higher priority SCCs are tried before lower priority SCCs.

Check priority:

```bash
oc get scc -o custom-columns=NAME:.metadata.name,PRIORITY:.priority,RUNAS:.runAsUser.type,PRIV:.allowPrivilegedContainer
```

Do not raise priority on default SCCs. It can cause unexpected cluster-wide behavior and instability.

### 8.2 More Than One SCC Can Match

A service account may be able to use multiple SCCs. For example:

```text
restricted-v2
anyuid
custom-app-scc
```

OpenShift chooses the first matching SCC after sorting. This means adding a new SCC can unintentionally change which SCC is selected.

### 8.3 Pod Annotation Shows the Winner

After admission:

```bash
oc get pod <pod> -n <namespace> \
  -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

This is one of the fastest ways to confirm the actual SCC used.

### 8.4 Required SCC Annotation Can Pin Behavior

A workload can require a specific SCC with:

```yaml
metadata:
  annotations:
    openshift.io/required-scc: custom-app-scc
```

Use this carefully. If the service account cannot use that SCC, pod admission fails.

## 9. Service Accounts and SCC Binding

### 9.1 Create a Dedicated Service Account

Production-safe pattern:

```bash
oc create sa app-sa -n myproject
```

Patch Deployment:

```bash
oc patch deploy myapp -n myproject \
  --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"app-sa"}}}}'
```

### 9.2 Grant an Existing SCC to a Service Account

Common command:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n myproject
```

Equivalent fully qualified subject:

```bash
oc adm policy add-scc-to-user anyuid \
  system:serviceaccount:myproject:app-sa
```

### 9.3 Verify Access

```bash
oc auth can-i use scc/anyuid \
  --as=system:serviceaccount:myproject:app-sa \
  -n myproject
```

```bash
oc adm policy who-can use scc anyuid
```

Important limitation: RBAC checks and direct SCC `users` / `groups` fields are not always shown by the same command. Always check both when investigating legacy clusters or hand-edited SCCs:

```bash
oc describe scc anyuid
oc adm policy who-can use scc anyuid
```

### 9.4 Remove SCC Access

```bash
oc adm policy remove-scc-from-user anyuid -z app-sa -n myproject
```

Or remove the RoleBinding / ClusterRoleBinding if access was granted through RBAC.

## 10. Fast Troubleshooting Method

Use this method during production incidents.

### Step 1: Confirm Whether the Pod Exists

```bash
oc get pods -n <namespace>
```

If the pod does not exist, inspect controller events:

```bash
oc describe deploy/<deployment> -n <namespace>
oc describe rs -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

If the pod exists but fails, inspect pod details:

```bash
oc describe pod/<pod> -n <namespace>
oc logs <pod> -n <namespace> --all-containers
```

### Step 2: Identify the Service Account

For a running or failed pod:

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

For a deployment:

```bash
oc get deploy <deployment> -n <namespace> -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

### Step 3: Check Selected SCC

If pod exists:

```bash
oc get pod <pod> -n <namespace> \
  -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

### Step 4: Check Requested Security Context

```bash
oc get deploy <deployment> -n <namespace> -o yaml | sed -n '/securityContext:/,+30p'
```

Better:

```bash
oc get deploy <deployment> -n <namespace> -o jsonpath='{.spec.template.spec.securityContext}{"\n"}'
oc get deploy <deployment> -n <namespace> -o jsonpath='{.spec.template.spec.containers[*].securityContext}{"\n"}'
```

### Step 5: Check Namespace UID/GID Ranges

```bash
oc get ns <namespace> -o yaml | egrep 'openshift.io/sa.scc.uid-range|openshift.io/sa.scc.mcs|openshift.io/sa.scc.supplemental-groups'
```

### Step 6: Check SCC Permissions

```bash
SA=app-sa
NS=myproject

oc auth can-i use scc/restricted-v2 --as=system:serviceaccount:${NS}:${SA} -n ${NS}
oc auth can-i use scc/anyuid       --as=system:serviceaccount:${NS}:${SA} -n ${NS}
oc auth can-i use scc/privileged   --as=system:serviceaccount:${NS}:${SA} -n ${NS}
```

### Step 7: Fix the Smallest Thing

Prefer fixes in this order:

1. Remove unnecessary securityContext fields from Helm/YAML.
2. Make the image run as arbitrary non-root UID.
3. Change writable paths to `/tmp`, `/var/lib/app`, or a mounted volume owned by the runtime user.
4. Add `runAsNonRoot`, drop capabilities, and set `allowPrivilegeEscalation: false`.
5. Use a dedicated service account.
6. Grant the narrowest suitable SCC.
7. Create a custom SCC only if built-in SCCs are too broad or too narrow.
8. Use `privileged` only for trusted infrastructure workloads.

## 11. Common SCC Error Messages

### 11.1 `unable to validate against any security context constraint`

Example:

```text
Error creating: pods "app-xxxxx" is forbidden: unable to validate against any security context constraint:
[provider restricted-v2: .containers[0].runAsUser: Invalid value: 0: must be in the ranges: [1000670000, 1000679999]]
```

Meaning:

- OpenShift tried SCCs available to the user/service account.
- None of them allowed the requested security context.
- The bracketed messages show why each SCC failed.

Troubleshooting:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc describe rs/<replicaset> -n <namespace>
oc get deploy <deployment> -n <namespace> -o yaml | grep -n "runAsUser\|privileged\|hostNetwork\|capabilities" -C 3
```

### 11.2 `must be in the ranges`

Example:

```text
runAsUser: Invalid value: 1000: must be in the ranges: [1000780000, 1000789999]
```

Meaning:

- The pod requested a fixed UID.
- `restricted-v2` expects a UID from the namespace allocated range.

Fix options:

- Remove fixed `runAsUser` if not required.
- Rebuild the image to run with arbitrary UID.
- Use `anyuid` only if the application truly requires a fixed UID.
- Create a custom SCC with a controlled UID range if required by enterprise policy.

### 11.3 `privileged containers are not allowed`

Example:

```text
.securityContext.privileged: Invalid value: true: Privileged containers are not allowed
```

Meaning:

- The container requested `privileged: true`.
- The service account cannot use an SCC that allows privileged containers.

Fix options:

- Remove `privileged: true`.
- Identify the actual kernel feature required.
- Use a narrower capability if possible.
- Grant `privileged` only to a dedicated service account for trusted infrastructure workloads.

### 11.4 `hostPath volumes are not allowed`

Meaning:

- The pod tries to mount a node filesystem path.
- Restricted SCCs usually do not allow `hostPath`.

Fix options:

- Use ConfigMap, Secret, PVC, CSI, or projected volume instead.
- If node-level access is required, use a DaemonSet with a dedicated service account and a host mount SCC.

### 11.5 `allowPrivilegeEscalation` Rejected

Example:

```text
.allowPrivilegeEscalation: Invalid value: true: Allowing privilege escalation is not allowed
```

Meaning:

- The container requested or defaulted to privilege escalation.
- Newer restricted policies expect `allowPrivilegeEscalation: false` or unset depending on SCC behavior.

Fix:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
```

### 11.6 Pod Security Admission Warning

Example:

```text
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false
```

Meaning:

- This may be PSA warning/audit/enforce, not necessarily SCC.
- SCC and PSA are separate controls.

Check namespace labels:

```bash
oc get ns <namespace> --show-labels | tr ',' '\n' | grep pod-security
```

## 12. Troubleshooting Root / AnyUID Issues

### 12.1 Symptom

A Deployment fails with:

```text
runAsUser: Invalid value: 0: must be in the ranges
```

or the container runs but the application fails with:

```text
permission denied
cannot write /var/lib/app
cannot create /opt/app/logs
```

### 12.2 Diagnosis

Inspect image and YAML:

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -n "runAsUser\|runAsNonRoot\|securityContext" -C 4
```

Check the Dockerfile if available:

```Dockerfile
USER 0
```

or:

```Dockerfile
USER appuser
```

A fixed non-root user can still fail under `restricted-v2` if the UID is outside the namespace range.

### 12.3 Best Fix: Make Image Arbitrary UID Compatible

OpenShift-friendly image design:

```Dockerfile
FROM registry.access.redhat.com/ubi9/ubi-minimal

RUN mkdir -p /opt/app /var/lib/app /var/log/app \
    && chgrp -R 0 /opt/app /var/lib/app /var/log/app \
    && chmod -R g=u /opt/app /var/lib/app /var/log/app

WORKDIR /opt/app
COPY app /opt/app/

USER 1001
CMD ["/opt/app/app"]
```

Even better, avoid fixed UID assumptions and make directories group-writable by group `0`.

### 12.4 Operational Fix: Grant `anyuid`

Use only when needed:

```bash
oc create sa legacy-app-sa -n legacy
oc adm policy add-scc-to-user anyuid -z legacy-app-sa -n legacy
oc patch deploy legacy-app -n legacy \
  --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"legacy-app-sa"}}}}'
```

Verify:

```bash
oc rollout restart deploy/legacy-app -n legacy
oc get pod -n legacy
oc get pod <pod> -n legacy -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

Expected:

```text
anyuid
```

### 12.5 Senior Admin Warning

Do not grant `anyuid` to all service accounts in a namespace unless the namespace is dedicated and risk accepted.

Avoid:

```bash
oc adm policy add-scc-to-user anyuid -z default -n production
```

Better:

```bash
oc create sa app-anyuid -n production
oc adm policy add-scc-to-user anyuid -z app-anyuid -n production
```

## 13. Troubleshooting UID Range Issues

### 13.1 How OpenShift UID Ranges Work

OpenShift assigns UID ranges per namespace through annotations such as:

```text
openshift.io/sa.scc.uid-range
```

Example:

```bash
oc get ns myproject -o jsonpath='{.metadata.annotations.openshift\.io/sa\.scc\.uid-range}{"\n"}'
```

Example output:

```text
1000670000/10000
```

This means the namespace has a range beginning at `1000670000` with length `10000`.

A pod under `restricted-v2` should not assume it can run as UID `1000`, `1001`, or `0`.

### 13.2 Common Bad YAML

```yaml
securityContext:
  runAsUser: 1000
```

This may work in upstream Kubernetes but fail in OpenShift restricted namespaces.

### 13.3 Preferred Fix

Remove the fixed UID:

```yaml
securityContext:
  runAsNonRoot: true
```

Container-level:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
```

Let OpenShift assign the UID.

### 13.4 Runtime Check

Inside a pod:

```bash
oc rsh -n myproject <pod> id
```

Example:

```text
uid=1000670000 gid=0(root) groups=0(root),1000670000
```

This surprises many admins: UID is random high number, but group may include `0`. That is why image directories should often be writable by group `0`.

## 14. Troubleshooting SELinux and MCS Issues

### 14.1 SCC and SELinux

OpenShift uses SELinux strongly. A namespace usually gets an MCS label. SCC strategies can require a pod to run with the namespace-assigned SELinux level.

Check namespace MCS:

```bash
oc get ns <namespace> -o jsonpath='{.metadata.annotations.openshift\.io/sa\.scc\.mcs}{"\n"}'
```

Example:

```text
s0:c27,c4
```

Check running pod SELinux options:

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.spec.securityContext.seLinuxOptions}{"\n"}'
```

### 14.2 Symptom

Pod admitted, but cannot access mounted content:

```text
permission denied
```

Node logs may show AVC denial:

```bash
oc debug node/<node>
chroot /host
ausearch -m avc -ts recent
journalctl -t setroubleshoot --since "1 hour ago"
```

### 14.3 Common Cause

Using `hostPath` or host-mounted directories with labels that are not accessible to the container MCS label.

### 14.4 Fix Options

- Avoid hostPath.
- Use PVC, Secret, ConfigMap, projected volume, or CSI driver.
- For node-level agents, use appropriate host mount SCC and SELinux-aware design.
- Do not randomly relabel host system paths.

### 14.5 Senior Admin Note

If an app needs a certificate or CA bundle, do not mount host `/etc/pki` by default. Use a ConfigMap or Secret:

```bash
oc create configmap custom-ca --from-file=ca.crt=./ca.crt -n myproject
```

Mount it:

```yaml
volumes:
- name: custom-ca
  configMap:
    name: custom-ca
containers:
- name: app
  volumeMounts:
  - name: custom-ca
    mountPath: /etc/pki/ca-trust/source/anchors/custom-ca.crt
    subPath: ca.crt
    readOnly: true
```

But remember: writing to `/etc/pki/ca-trust` at runtime may still require root. A better pattern is to configure the app to read trust from an app-specific path.

## 15. Troubleshooting fsGroup and Supplemental Group Issues

### 15.1 Symptom

Pod starts but cannot write to a mounted PVC:

```text
permission denied: /data
```

or pod admission fails:

```text
fsGroup: Invalid value: 1000: must be in the ranges
```

### 15.2 Diagnosis

Check pod security context:

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -n "fsGroup\|supplementalGroups" -C 4
```

Check namespace supplemental groups:

```bash
oc get ns <namespace> -o jsonpath='{.metadata.annotations.openshift\.io/sa\.scc\.supplemental-groups}{"\n"}'
```

If missing, OpenShift may fall back to UID range behavior depending on SCC strategy.

### 15.3 Best Fix

For most OpenShift-compatible apps, avoid hardcoding:

```yaml
fsGroup: 1000
```

Instead, allow OpenShift and the storage provider to manage ownership, or configure storage permissions correctly.

### 15.4 Storage Provider Reality

Not all storage behaves the same:

- Block storage may support ownership changes.
- NFS with root squash may behave differently.
- CSI drivers may or may not honor fsGroup as expected.
- Some workloads require init containers to prepare permissions, but init containers also run under SCC restrictions.

### 15.5 Troubleshooting Commands

```bash
oc describe pod <pod> -n <namespace>
oc rsh <pod> -n <namespace> id
oc rsh <pod> -n <namespace> ls -ld /data
oc get pvc -n <namespace>
oc describe pvc <pvc> -n <namespace>
```

If using NFS, check export options and server-side ownership. SCC may not be the root cause.

## 16. Troubleshooting Capabilities

### 16.1 What Are Linux Capabilities?

Linux capabilities split root privileges into smaller units. Examples:

- `NET_BIND_SERVICE` allows binding to ports below 1024.
- `NET_ADMIN` allows advanced network administration.
- `SYS_ADMIN` is extremely broad and dangerous.
- `CHOWN` allows ownership changes.
- `DAC_OVERRIDE` bypasses file permission checks.

### 16.2 Common Error

```text
capability may not be added
```

or:

```text
.capabilities.add: Invalid value: "NET_ADMIN"
```

### 16.3 Diagnose Requested Capabilities

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -n "capabilities" -A 10
```

Example bad YAML:

```yaml
securityContext:
  capabilities:
    add:
    - NET_ADMIN
```

### 16.4 Fix Strategy

Ask what the app actually needs.

For binding to port 80, do not grant `NET_ADMIN`. Options:

1. Change the app to listen on port 8080 and expose Service port 80.
2. Add only `NET_BIND_SERVICE` if policy allows.
3. Use Route/Ingress/Service to handle low external ports.

Recommended app design:

```yaml
ports:
- containerPort: 8080
```

Service:

```yaml
ports:
- name: http
  port: 80
  targetPort: 8080
```

### 16.5 Custom SCC for One Capability

If absolutely needed:

```yaml
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata:
  name: app-netbind-scc
allowPrivilegedContainer: false
allowPrivilegeEscalation: false
requiredDropCapabilities:
- ALL
allowedCapabilities:
- NET_BIND_SERVICE
runAsUser:
  type: MustRunAsRange
seLinuxContext:
  type: MustRunAs
fsGroup:
  type: MustRunAs
supplementalGroups:
  type: RunAsAny
seccompProfiles:
- runtime/default
volumes:
- configMap
- downwardAPI
- emptyDir
- persistentVolumeClaim
- projected
- secret
readOnlyRootFilesystem: false
```

Then bind through RBAC or `oc adm policy` to a dedicated service account.

## 17. Troubleshooting Privileged Containers

### 17.1 Symptom

```text
privileged containers are not allowed
```

### 17.2 Diagnose

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -n "privileged" -C 4
```

### 17.3 Common Sources

- Security agents.
- Node monitoring agents.
- CSI drivers.
- CNI components.
- Backup agents.
- Legacy Docker-in-Docker workloads.
- CI/CD build pods needing nested container runtime behavior.

### 17.4 Do Not Use Privileged for Normal Applications

Normal web apps, APIs, databases, queues, and Java services should almost never need `privileged`.

### 17.5 Grant Privileged Safely

```bash
oc create ns infra-agent
oc create sa node-agent-sa -n infra-agent
oc adm policy add-scc-to-user privileged -z node-agent-sa -n infra-agent
```

Patch DaemonSet:

```bash
oc patch ds node-agent -n infra-agent \
  --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"node-agent-sa"}}}}'
```

Verify selected SCC:

```bash
oc get pod -n infra-agent -l app=node-agent \
  -o jsonpath='{range .items[*]}{.metadata.name}{" => "}{.metadata.annotations.openshift\.io/scc}{"\n"}{end}'
```

### 17.6 Risk

A privileged container can often access host devices, host namespaces, and sensitive node resources. Treat it as close to node-level trust.

## 18. Troubleshooting HostPath, HostNetwork, HostPID, and HostIPC

### 18.1 HostPath

Bad for normal apps:

```yaml
volumes:
- name: host-certs
  hostPath:
    path: /etc/pki/ca-trust
```

Better:

```yaml
volumes:
- name: ca-bundle
  configMap:
    name: trusted-ca-bundle
```

HostPath may be acceptable for:

- CSI node plugins.
- Log collectors.
- Node agents.
- Hardware device plugins.
- Security scanners.

### 18.2 HostNetwork

Symptom:

```text
Host network is not allowed to be used
```

Check YAML:

```bash
oc get ds <daemonset> -n <namespace> -o yaml | grep -n "hostNetwork\|dnsPolicy\|hostPort" -C 3
```

If using `hostNetwork: true`, DNS policy often needs:

```yaml
dnsPolicy: ClusterFirstWithHostNet
```

### 18.3 HostPort

HostPort binds a container port directly on the node. It creates scheduling and port conflict issues.

Prefer:

- Service
- Route
- Ingress
- NodePort only when appropriate
- LoadBalancer service where supported

### 18.4 HostPID and HostIPC

Usually only for node-level debugging, monitoring, security, or infrastructure components.

If a normal application requests these, challenge the requirement.

## 19. Troubleshooting Volume and Certificate Mount Issues

### 19.1 Secret Volumes Are Allowed Under Restricted SCCs

TLS certificates are commonly stored in Secrets:

```bash
oc create secret tls app-tls \
  --cert=tls.crt \
  --key=tls.key \
  -n myproject
```

Mount:

```yaml
volumes:
- name: tls
  secret:
    secretName: app-tls
containers:
- name: app
  volumeMounts:
  - name: tls
    mountPath: /etc/tls/private
    readOnly: true
```

This normally does not require `anyuid`, `hostmount-anyuid`, or `privileged`.

### 19.2 ConfigMap CA Bundles

```bash
oc create configmap app-ca \
  --from-file=ca-bundle.crt=./ca-bundle.crt \
  -n myproject
```

Mount:

```yaml
volumes:
- name: app-ca
  configMap:
    name: app-ca
containers:
- name: app
  volumeMounts:
  - name: app-ca
    mountPath: /etc/app/certs
    readOnly: true
```

### 19.3 Projected Service Account Token and CA

Many workloads use projected volumes:

```yaml
volumes:
- name: kube-api-access
  projected:
    sources:
    - serviceAccountToken:
        expirationSeconds: 3600
        path: token
    - configMap:
        name: kube-root-ca.crt
        items:
        - key: ca.crt
          path: ca.crt
```

Projected volumes are normally compatible with restricted SCCs.

### 19.4 Problem: App Wants to Write to a Mounted Secret

Secrets and ConfigMaps are read-only. The error may look like permissions, but the root cause is volume type.

Bad app behavior:

```text
cannot write /etc/tls/private/tls.crt
```

Fix:

- Copy certs to an `emptyDir` in an init container if mutation is required.
- Configure app to read certs from mounted path without modifying them.
- Rebuild image to not import certs into root-owned truststore at startup.

Example with `emptyDir`:

```yaml
volumes:
- name: tls-src
  secret:
    secretName: app-tls
- name: tls-work
  emptyDir: {}
initContainers:
- name: prepare-certs
  image: registry.access.redhat.com/ubi9/ubi-minimal
  command: ["sh", "-c", "cp /src/* /work/ && chmod 0440 /work/*"]
  volumeMounts:
  - name: tls-src
    mountPath: /src
    readOnly: true
  - name: tls-work
    mountPath: /work
containers:
- name: app
  volumeMounts:
  - name: tls-work
    mountPath: /etc/app/tls
```

### 19.5 Problem: App Wants to Update OS Trust Store

This often fails because the container runs as non-root.

Bad pattern:

```bash
update-ca-trust
```

Better patterns:

- Build CA into image during CI.
- Use Java `-Djavax.net.ssl.trustStore=/etc/app/certs/truststore.jks`.
- Use app-level CA path.
- Use ConfigMap-mounted CA bundle.

## 20. Troubleshooting Helm and Operator Deployments

### 20.1 Helm Charts Commonly Break on OpenShift

Upstream charts may include:

```yaml
securityContext:
  runAsUser: 1000
  fsGroup: 1000
containerSecurityContext:
  allowPrivilegeEscalation: true
  privileged: false
```

Even if `privileged: false` is harmless, `runAsUser: 1000` or `fsGroup: 1000` can break OpenShift restricted SCC.

### 20.2 Helm Fix Pattern

Search values:

```bash
helm show values <chart> | grep -n "securityContext\|runAsUser\|fsGroup\|privileged" -C 3
```

Override values:

```yaml
podSecurityContext:
  enabled: false
containerSecurityContext:
  enabled: true
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
  runAsNonRoot: true
```

Depending on the chart, exact values differ.

### 20.3 Operator Workloads

Operators often create service accounts and roles automatically. If an operator-managed pod fails due to SCC:

```bash
oc get sa -n <operator-namespace>
oc get deploy,ds,statefulset -n <operator-namespace>
oc get events -n <operator-namespace> --sort-by=.lastTimestamp
```

Check ClusterServiceVersion:

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv> -n <operator-namespace>
```

Do not randomly patch operator-managed objects. The operator may revert your changes. Instead:

- Check Operator documentation.
- Check Subscription/CSV requirements.
- Check whether the Operator installed required SCCs.
- Check whether the target namespace has correct OperatorGroup.
- Check if SCC is expected to be granted by the Operator's RBAC.

## 21. SCC and Pod Security Admission Warnings

### 21.1 Symptom

You apply a deployment and get:

```text
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false
```

But the pod may still run.

### 21.2 Meaning

This is often PSA `warn` or `audit`, not SCC rejection.

Check namespace labels:

```bash
oc get ns <namespace> -o yaml | grep pod-security -n
```

Example:

```yaml
pod-security.kubernetes.io/warn: restricted
pod-security.kubernetes.io/audit: restricted
```

### 21.3 Fix the Workload YAML

A restricted-compatible container security context commonly looks like:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
```

In OpenShift, be careful with fixed `runAsUser`. `runAsNonRoot: true` is usually safer than `runAsUser: 1000`.

### 21.4 Do Not Silence Warnings Blindly

Do not change namespace PSA labels simply to hide warnings unless there is a platform policy decision.

## 22. Creating a Custom SCC Safely

### 22.1 When to Create a Custom SCC

Create a custom SCC when:

- Built-in `restricted-v2` is too restrictive.
- Built-in `anyuid` is too broad.
- You need one specific capability.
- You need hostPath for one trusted DaemonSet.
- You need a controlled UID/GID strategy.
- You need to pin behavior and avoid default SCC changes.

Do not create a custom SCC just because one pod failed. First understand the exact violation.

### 22.2 Minimal Custom SCC Example: Any UID but No Host Access

```yaml
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata:
  name: custom-anyuid-nohost
allowPrivilegedContainer: false
allowPrivilegeEscalation: false
allowedCapabilities: []
requiredDropCapabilities:
- ALL
runAsUser:
  type: RunAsAny
seLinuxContext:
  type: MustRunAs
fsGroup:
  type: RunAsAny
supplementalGroups:
  type: RunAsAny
readOnlyRootFilesystem: false
seccompProfiles:
- runtime/default
volumes:
- configMap
- downwardAPI
- emptyDir
- persistentVolumeClaim
- projected
- secret
allowHostDirVolumePlugin: false
allowHostIPC: false
allowHostNetwork: false
allowHostPID: false
allowHostPorts: false
```

Apply:

```bash
oc apply -f custom-anyuid-nohost.yaml
```

Create RBAC role scoped to namespace:

```bash
oc create role use-custom-anyuid-nohost \
  --verb=use \
  --resource=scc \
  --resource-name=custom-anyuid-nohost \
  -n myproject
```

Bind to service account:

```bash
oc adm policy add-role-to-user use-custom-anyuid-nohost \
  system:serviceaccount:myproject:legacy-sa \
  -n myproject
```

Verify:

```bash
oc auth can-i use scc/custom-anyuid-nohost \
  --as=system:serviceaccount:myproject:legacy-sa \
  -n myproject
```

### 22.3 Avoid Direct Users/Groups in Custom SCC Where Possible

SCC has `users` and `groups` fields, but RBAC is usually cleaner and easier to audit.

Prefer:

- Role / RoleBinding for namespace-scoped access.
- ClusterRole / ClusterRoleBinding only when cluster-wide access is required.

### 22.4 Custom SCC Review Checklist

Before applying custom SCC:

- Does it allow hostPath?
- Does it allow privileged?
- Does it allow hostNetwork?
- Does it allow all capabilities?
- Does it allow `RunAsAny` unnecessarily?
- Does it allow all volumes with `*`?
- Is `allowPrivilegeEscalation` false where possible?
- Are all capabilities dropped by default?
- Is `seccompProfiles` restricted to `runtime/default` where possible?
- Is it bound only to the required service account?

## 23. Using Required SCC Annotation

### 23.1 Purpose

If a service account can use multiple SCCs, OpenShift may choose a different SCC than expected. You can pin a workload to a required SCC:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    metadata:
      annotations:
        openshift.io/required-scc: custom-anyuid-nohost
    spec:
      serviceAccountName: legacy-sa
      containers:
      - name: app
        image: registry.example.com/app:v1
```

### 23.2 Verification

```bash
oc get pod <pod> -n myproject \
  -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

Expected:

```text
custom-anyuid-nohost
```

### 23.3 Failure Mode

If the service account cannot use the required SCC, pod admission fails.

Check:

```bash
oc auth can-i use scc/custom-anyuid-nohost \
  --as=system:serviceaccount:myproject:legacy-sa \
  -n myproject
```

## 25. Real-World Troubleshooting Scenarios

### Scenario 1: Legacy Nginx Image Runs as Root

#### Problem

Deployment fails:

```text
runAsUser: Invalid value: 0: must be in the ranges
```

#### Investigation

```bash
oc describe rs -n web
oc get deploy nginx -n web -o yaml | grep -n "runAsUser" -C 3
```

YAML:

```yaml
securityContext:
  runAsUser: 0
```

#### Best Fix

Use an OpenShift-compatible image that listens on 8080 and supports arbitrary UID.

#### Temporary Fix

```bash
oc create sa nginx-anyuid -n web
oc adm policy add-scc-to-user anyuid -z nginx-anyuid -n web
oc patch deploy nginx -n web --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"nginx-anyuid"}}}}'
oc rollout restart deploy/nginx -n web
```

Verify:

```bash
oc get pod -n web -l app=nginx \
  -o jsonpath='{range .items[*]}{.metadata.name}{" => "}{.metadata.annotations.openshift\.io/scc}{"\n"}{end}'
```

---

### Scenario 2: Helm Chart Hardcodes `runAsUser: 1001`

#### Problem

Chart works in upstream Kubernetes but fails in OpenShift.

#### Error

```text
runAsUser: Invalid value: 1001: must be in the ranges
```

#### Fix

In Helm values, disable fixed UID:

```yaml
podSecurityContext:
  enabled: false
containerSecurityContext:
  enabled: true
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
```

Apply:

```bash
helm upgrade --install app ./chart -n app -f values-openshift.yaml
```

---

### Scenario 3: App Cannot Read Mounted TLS Cert

#### Problem

Pod runs but app fails:

```text
permission denied: /etc/tls/private/tls.key
```

#### Investigation

```bash
oc rsh <pod> -n app id
oc rsh <pod> -n app ls -l /etc/tls/private
oc get pod <pod> -n app -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

#### Possible Causes

- App expects cert owned by a specific UID.
- App tries to modify the key file.
- File mode is too restrictive for runtime UID.
- App config points to wrong path.

#### Fix Options

- Configure app to read Secret-mounted files directly.
- Use `defaultMode` on Secret volume if appropriate.
- Copy cert to an `emptyDir` with correct permissions in init container.
- Avoid granting `anyuid` unless the app truly requires root.

Example:

```yaml
volumes:
- name: tls
  secret:
    secretName: app-tls
    defaultMode: 0440
```

---

### Scenario 4: Log Collector Needs HostPath

#### Problem

DaemonSet fails:

```text
hostPath volumes are not allowed
```

#### Investigation

```bash
oc get ds log-agent -n logging -o yaml | grep -n "hostPath" -C 5
```

#### Decision

A node log collector may legitimately need hostPath access.

#### Fix

Use a dedicated namespace and service account:

```bash
oc create ns logging-agents
oc create sa log-agent-sa -n logging-agents
oc adm policy add-scc-to-user hostmount-anyuid -z log-agent-sa -n logging-agents
```

For recent OCP versions where SELinux host path behavior requires it, evaluate `hostmount-anyuid-v2` if available and recommended for that workload.

Patch DaemonSet:

```bash
oc patch ds log-agent -n logging-agents --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"log-agent-sa"}}}}'
```

#### Senior Admin Note

Do not use host mount SCCs for application logs. Use stdout/stderr and cluster logging.

---

### Scenario 5: PodSecurity Warning After SCC Grant

#### Problem

After granting `anyuid`, namespace starts showing PSA warnings.

#### Explanation

SCC and PSA are independent. The service account may now have access to a stronger SCC, and namespace PSA label synchronization may adjust warning/audit labels based on SCC permissions.

#### Troubleshooting

```bash
oc get ns app -o yaml | grep pod-security -n
oc adm policy who-can use scc anyuid
```

#### Fix

- Use a dedicated service account.
- Limit SCC grant to one namespace and one workload.
- Make workload restricted-compatible if possible.
- Do not manually edit PSA labels unless platform policy requires it.

---

### Scenario 6: Init Container Fails Because Main Container SCC Assumption Is Wrong

#### Problem

Deployment has an init container that runs `chown` on a PVC:

```yaml
initContainers:
- name: fix-permissions
  image: ubi9
  command: ["sh", "-c", "chown -R 1000:1000 /data"]
```

It fails under restricted SCC.

#### Why

The init container is part of the same pod and must satisfy the same SCC. If it needs root or `CHOWN`, restricted SCC may block it or runtime may deny operation.

#### Fix Options

- Avoid chown at startup.
- Fix storage permissions outside the pod.
- Use fsGroup if storage supports it.
- Use CSI driver features.
- Grant a narrow SCC only if operationally justified.

---

### Scenario 7: Database Image Requires Fixed UID

#### Problem

Vendor database image expects UID `1001` and writable `/bitnami`.

#### Fix Options

1. Use vendor OpenShift-compatible image/settings.
2. Override chart securityContext to avoid fixed UID if image supports it.
3. Grant `anyuid` to a dedicated service account if vendor requires fixed UID.
4. Use a custom SCC with allowed UID range if policy needs tighter control.

#### Example

```bash
oc create sa db-sa -n db
oc adm policy add-scc-to-user anyuid -z db-sa -n db
```

StatefulSet:

```yaml
spec:
  template:
    spec:
      serviceAccountName: db-sa
```

## 26. Security Hardening Best Practices

### 26.1 Use Dedicated Service Accounts

Bad:

```bash
oc adm policy add-scc-to-user anyuid -z default -n prod
```

Good:

```bash
oc create sa payment-api-sa -n prod
oc adm policy add-scc-to-user anyuid -z payment-api-sa -n prod
```

### 26.2 Keep SCC Grants Narrow

Grant to:

- One service account.
- One namespace.
- One workload.

Avoid cluster-wide SCC grants unless required by platform components.

### 26.3 Do Not Modify Default SCCs

Do not edit:

- `restricted-v2`
- `restricted`
- `anyuid`
- `privileged`
- `hostnetwork`
- `hostmount-anyuid`

Create a custom SCC instead.

### 26.4 Avoid `privileged`

Before privileged, check whether the workload really only needs:

- A single capability.
- A PVC.
- A ConfigMap/Secret.
- A Service/Route instead of hostPort.
- A non-root image fix.

### 26.5 Build OpenShift-Compatible Images

Image guidelines:

- Do not require root.
- Do not require fixed UID.
- Make writable directories group-writable by group `0`.
- Avoid writing into `/etc`, `/usr`, `/opt` unless ownership is prepared.
- Listen on high ports like `8080`.
- Store runtime data on PVC or application-owned paths.
- Support read-only root filesystem where possible.

### 26.6 Drop Capabilities

Recommended:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
```

Add only the exact capability required.

### 26.7 Use RuntimeDefault Seccomp

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

### 26.8 Treat HostPath as Node-Level Access

HostPath can expose:

- Node filesystem.
- Kubelet data.
- CRI-O storage.
- Certificates.
- Logs.
- Host sockets.

Only trusted DaemonSets should use it.

## 29. Interview and Exam Notes

### 29.1 One-Line Definition

SCC is an OpenShift admission control mechanism that determines which security settings a pod is allowed to use and may default certain security context values based on the selected SCC.

### 29.2 Most Important Troubleshooting Command

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### 29.3 Most Important Verification Command

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

### 29.4 Common Exam-Style Fix

If a pod must run with any UID:

```bash
oc create sa app-sa -n app
oc adm policy add-scc-to-user anyuid -z app-sa -n app
oc set serviceaccount deploy/app app-sa -n app
```

If `oc set serviceaccount` is unavailable or unclear:

```bash
oc patch deploy app -n app --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"app-sa"}}}}'
```

### 29.5 Common Real-World Answer

Do not immediately grant `anyuid`. First remove hardcoded `runAsUser`, make the image arbitrary-UID-compatible, use a dedicated service account, and grant the narrowest SCC only if required.

### 29.6 Difference Between `anyuid` and `privileged`

- `anyuid` allows running as arbitrary UID, including root, but does not automatically allow host access or privileged containers.
- `privileged` allows the broadest access and should be treated as node-level trust.

### 29.7 SCC Troubleshooting Mental Model

```text
Who is running the pod?        -> serviceAccountName
What does the pod request?     -> securityContext, volumes, host settings
What is it allowed to use?     -> SCC RBAC/use permissions
What SCC actually admitted it? -> openshift.io/scc annotation
What failed after admission?   -> logs, id, file modes, SELinux, storage
```

## Final Senior Admin Takeaway

SCC troubleshooting is not about making pods run at any cost. It is about finding the exact security boundary the workload is crossing and deciding whether to fix the workload, fix the image, fix the chart, fix the service account, or grant a narrowly scoped SCC.

The safest production pattern is:

```text
restricted-v2 by default
+ arbitrary UID-compatible images
+ dedicated service accounts
+ narrow SCC grants
+ no default SCC modification
+ no privileged unless infrastructure-grade trust is required
```
