## 1. What is an Ingress certificate?

An **Ingress certificate** in OpenShift is the TLS certificate presented by the OpenShift router, normally HAProxy-based, when external clients connect to application routes under the cluster application domain.

For example, when a user opens:

```text
https://console-openshift-console.apps.ocp4.example.com
https://myapp-dev.apps.ocp4.example.com
https://api-frontend-prod.apps.ocp4.example.com
```

The certificate presented to the browser is normally either:

1. the **default certificate** configured on the `IngressController`, usually a wildcard certificate for `*.apps.ocp4.example.com`; or
2. a **route-specific certificate** embedded in a secured `Route` object; or
3. a certificate served directly by the backend pod in case of passthrough TLS.

In simple language:

> The Ingress certificate is the public-facing TLS identity of applications exposed through OpenShift routes.

In production, this certificate is important because it affects:

- browser trust for the web console and application routes;
- CLI access to console-related OAuth endpoints;
- external API consumers calling services through routes;
- compliance scans;
- security posture of application ingress;
- certificate expiry risk;
- user confidence and audit readiness.

## 2. OpenShift Ingress architecture

OpenShift uses the **Ingress Operator** to manage IngressControllers. An IngressController creates and manages router pods that receive external HTTP and HTTPS traffic and forward it to Kubernetes services behind OpenShift Routes.

### Key components

| Component | Namespace | Purpose |
|---|---:|---|
| `IngressController` custom resource | `openshift-ingress-operator` | Desired configuration for router/Ingress behavior |
| Ingress Operator | `openshift-ingress-operator` | Reconciles IngressController configuration |
| Router pods | `openshift-ingress` | HAProxy-based data-plane pods that terminate or pass TLS traffic |
| Router service | `openshift-ingress` | Exposes router pods internally and/or through load balancer/node ports/host network |
| Default router certificate secret | `openshift-ingress` | Stores certificate/key used by router |
| `Route` resources | Application namespaces | Define hostnames, services, and TLS termination behavior |

Typical default objects:

```bash
oc get ingresscontroller -n openshift-ingress-operator
oc get pods -n openshift-ingress
oc get svc -n openshift-ingress
oc get secret -n openshift-ingress | grep router
```

Expected default IngressController:

```text
NAME      AGE
/default  ...
```

Router pods usually look like:

```text
router-default-xxxxx
router-default-yyyyy
```

### High-level flow

```text
External Client
     |
     | HTTPS request to app.apps.ocp4.example.com
     v
External Load Balancer / DNS / NodePort / HostNetwork
     |
     v
OpenShift Router Pod - HAProxy
     |
     | Route lookup by Host header / SNI
     v
Kubernetes Service
     |
     v
Application Pod
```

The Ingress certificate is presented at the router layer unless the route uses passthrough termination.

## 3. Certificate types related to Ingress

OpenShift has multiple certificate areas. Do not confuse them.

| Certificate area | Used by | Example |
|---|---|---|
| API server certificate | `oc`, Kubernetes API, automation tools | `https://api.ocp4.example.com:6443` |
| Ingress default certificate | Routes without their own cert | `*.apps.ocp4.example.com` |
| Route-specific certificate | One application route | `www.example.com` |
| Service serving certificate | Internal service-to-service TLS | `service.namespace.svc` |
| Router metrics certificate | Metrics endpoint for router | `router-metrics-certs-default` |
| OAuth/console route certificate | Usually uses default Ingress cert unless route-specific | `console-openshift-console.apps...` |

The **Ingress certificate** discussed here is primarily the default route-serving certificate for the `IngressController`.

## 4. Default Ingress certificate behavior

By default, OpenShift creates an internal CA and issues a wildcard certificate for the cluster apps domain. This certificate is used for applications under the `.apps` subdomain when routes do not provide their own certificate.

For example, if the apps domain is:

```text
apps.ocp4.example.com
```

OpenShift-generated default certificate is normally valid for something like:

```text
*.apps.ocp4.example.com
```

The default certificate affects:

- default secured routes;
- the OpenShift web console route;
- OAuth login flows exposed through routes;
- any route that relies on the IngressController default certificate.

### Where OpenShift stores generated Ingress certificate material

Common generated secrets:

| Secret | Namespace | Purpose |
|---|---:|---|
| `router-ca` | `openshift-ingress-operator` | Ingress Operator signing CA for generated router certificates |
| `router-certs-default` | `openshift-ingress` | Generated default certificate for the default IngressController |
| `router-metrics-certs-default` | `openshift-ingress` | Metrics certificate generated by service-ca |

Check them:

```bash
oc get secret router-ca -n openshift-ingress-operator
oc get secret router-certs-default -n openshift-ingress
oc get secret router-metrics-certs-default -n openshift-ingress
```

The exact name contains the IngressController name. For a non-default IngressController named `external`, the generated secret can be similar to:

```text
router-certs-external
router-metrics-certs-external
```

## 5. Why the default certificate is not production-grade

OpenShift-generated default Ingress certificates are useful immediately after installation because the cluster can expose routes without waiting for enterprise PKI integration. However, for production, they are normally not enough.

Main reasons:

1. **It is not trusted by external clients by default.**
   Browsers, external systems, monitoring tools, partner APIs, and users may see certificate warnings unless the generated CA is imported into their trust stores.

2. **It is intended as a placeholder.**
   The default generated certificate is mainly for bootstrap and internal convenience.

3. **It creates operational expiry risk.**
   If no one tracks the generated certificate validity, routes can suddenly start failing with expiry errors.

4. **Compliance teams usually require CA-issued certificates.**
   Public-facing or enterprise-facing systems normally require a certificate issued by a public CA or enterprise private CA.

5. **Browser and API consumers expect SAN-based trust.**
   Modern TLS validation depends on `subjectAltName`, not just the common name.

Best production pattern:

```text
Use a CA-issued wildcard certificate for *.apps.<cluster-domain>
and configure it as the IngressController defaultCertificate.
```

## 6. Ingress certificate vs API certificate vs route certificate

This distinction is extremely important in real operations.

### 6.1 API certificate

Used for:

```text
https://api.ocp4.example.com:6443
```

Managed through API server certificate configuration, not IngressController default certificate.

Common symptom if API certificate is bad:

```text
oc login https://api.ocp4.example.com:6443
error: x509: certificate signed by unknown authority
```

### 6.2 Ingress default certificate

Used for:

```text
https://console-openshift-console.apps.ocp4.example.com
https://myapp.apps.ocp4.example.com
```

Configured on:

```text
IngressController/default in openshift-ingress-operator
```

Secret stored in:

```text
openshift-ingress
```

### 6.3 Route-specific certificate

Used only for a particular route, for example:

```text
https://payment.example.com
```

Stored inside the route spec:

```yaml
spec:
  tls:
    termination: edge
    certificate: |-
      -----BEGIN CERTIFICATE-----
    key: |-
      -----BEGIN PRIVATE KEY-----
```

A route-specific certificate overrides the default Ingress certificate for that route host.

## 7. TLS request flow through the OpenShift router

When a client connects using HTTPS, several things happen.

### 7.1 With default certificate

```text
Client connects to myapp.apps.ocp4.example.com:443
       |
       | TLS ClientHello with SNI: myapp.apps.ocp4.example.com
       v
OpenShift router selects certificate
       |
       | No route-specific certificate found
       v
Router presents default Ingress certificate
       |
       v
TLS handshake completes if client trusts cert and hostname matches SAN
       |
       v
Router forwards traffic to backend service/pod
```

### 7.2 With route-specific certificate

```text
Client connects to www.example.com:443
       |
       | SNI: www.example.com
       v
Router finds route with custom TLS certificate
       |
       v
Router presents certificate embedded in that route
       |
       v
Traffic is forwarded according to route termination mode
```

### 7.3 With passthrough route

```text
Client connects to secure-db-ui.apps.ocp4.example.com:443
       |
       | SNI used by router for routing decision
       v
Router does not terminate TLS
       |
       v
Encrypted TLS stream goes to backend pod
       |
       v
Backend application presents its own certificate
```

In passthrough mode, the Ingress default certificate is not the certificate the client validates for the application session.

## 8. IngressController `defaultCertificate`

The key setting is:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  defaultCertificate:
    name: custom-certs-default
```

Important points:

- `spec.defaultCertificate.name` refers to a Kubernetes TLS secret.
- The secret must exist in the `openshift-ingress` namespace.
- The secret must contain `tls.crt` and `tls.key`.
- The certificate is served for secured routes that do not specify their own certificate.
- If `defaultCertificate` is not configured, the Ingress Operator generates and uses a default wildcard certificate.

### Why the secret is in `openshift-ingress`, not `openshift-ingress-operator`

The IngressController CR lives in:

```text
openshift-ingress-operator
```

But router pods run in:

```text
openshift-ingress
```

The router pods need to mount the serving certificate secret at runtime. Therefore, the TLS secret must be created in `openshift-ingress`.

## 9. Certificate requirements

A production Ingress certificate should meet these requirements.

### 9.1 Hostname/SAN requirement

For an apps domain:

```text
apps.ocp4.example.com
```

The certificate should include:

```text
DNS:*.apps.ocp4.example.com
```

Optionally include the base apps domain if you expose anything directly at that name:

```text
DNS:apps.ocp4.example.com
DNS:*.apps.ocp4.example.com
```

For most OpenShift routes, the wildcard is the critical SAN.

### 9.2 Wildcard limitations

A wildcard certificate for:

```text
*.apps.ocp4.example.com
```

matches:

```text
myapp.apps.ocp4.example.com
console-openshift-console.apps.ocp4.example.com
oauth-openshift.apps.ocp4.example.com
```

But it does **not** match deeper names like:

```text
api.prod.apps.ocp4.example.com
blue.api.apps.ocp4.example.com
```

For deeper hostnames, you need a certificate that includes the correct SAN, such as:

```text
*.prod.apps.ocp4.example.com
```

or a route-specific certificate.

### 9.3 Key usage and extended key usage

Typical expected certificate properties:

```text
Key Usage: Digital Signature, Key Encipherment
Extended Key Usage: TLS Web Server Authentication
Basic Constraints: CA:FALSE
```

For ECDSA certificates, key usage may differ slightly depending on CA policy.

### 9.4 PEM format

OpenShift expects PEM-encoded certificate and key files:

```text
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

```text
-----BEGIN PRIVATE KEY-----
...
-----END PRIVATE KEY-----
```

or:

```text
-----BEGIN RSA PRIVATE KEY-----
...
-----END RSA PRIVATE KEY-----
```

### 9.5 Private key must not be password protected

Password-protected private keys are not suitable for router pods because the router cannot interactively unlock the key during startup.

Remove passphrase if required:

```bash
openssl rsa -in password_protected_tls.key -out tls.key
```

### 9.6 Certificate and key must match

Verify RSA key match:

```bash
openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

Both hashes must match.

For non-RSA keys, use public key comparison:

```bash
openssl x509 -in tls.crt -pubkey -noout > cert.pub
openssl pkey -in tls.key -pubout > key.pub
diff cert.pub key.pub
```

No output from `diff` means the public keys match.

## 10. Certificate chain basics

A TLS certificate chain normally contains:

```text
Server certificate
Intermediate CA certificate(s)
Root CA certificate
```

For `tls.crt`, the recommended order is:

```text
-----BEGIN CERTIFICATE-----
# Server certificate for *.apps.ocp4.example.com
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
# Intermediate CA certificate
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
# Optional additional intermediate
-----END CERTIFICATE-----
```

Usually, do **not** include the root CA unless your organization requires it. Clients normally already trust the root CA. But including the root is often tolerated by clients; still, many PKI teams prefer server + intermediate chain only.

### Why chain order matters

If the router serves only the leaf certificate without intermediate CA certificates, clients may fail with:

```text
unable to get local issuer certificate
certificate verify failed
```

This often happens when admins receive multiple files from the CA and upload only the server certificate.

Correct approach:

```bash
cat wildcard.apps.ocp4.example.com.crt intermediate-ca.crt > tls.crt
cp wildcard.apps.ocp4.example.com.key tls.key
```

Validate:

```bash
openssl verify -CAfile ca-chain.crt tls.crt
```

## 11. Inspect current Ingress certificate configuration

### 11.1 Check IngressController

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

Look for:

```yaml
spec:
  defaultCertificate:
    name: custom-certs-default
```

If `spec.defaultCertificate` is missing, OpenShift is using the generated default certificate.

### 11.2 Check router pods

```bash
oc get pods -n openshift-ingress -o wide
```

Example:

```text
router-default-6c9d4c8b4b-abcde   1/1 Running
router-default-6c9d4c8b4b-fghij   1/1 Running
```

### 11.3 Check router deployment

```bash
oc get deployment router-default -n openshift-ingress -o yaml
```

You can inspect volumes and mounts to understand which certificate secret is mounted.

### 11.4 Check generated/default secret

```bash
oc get secret -n openshift-ingress | grep router-certs
```

### 11.5 Decode current certificate from secret

```bash
oc get secret router-certs-default -n openshift-ingress \
  -o jsonpath='{.data.tls\.crt}' | base64 -d | \
  openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

For a custom secret:

```bash
oc get secret custom-certs-default -n openshift-ingress \
  -o jsonpath='{.data.tls\.crt}' | base64 -d | \
  openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### 11.6 Check live certificate served externally

```bash
openssl s_client \
  -connect console-openshift-console.apps.ocp4.example.com:443 \
  -servername console-openshift-console.apps.ocp4.example.com \
  -showcerts </dev/null
```

Useful filtered command:

```bash
openssl s_client \
  -connect console-openshift-console.apps.ocp4.example.com:443 \
  -servername console-openshift-console.apps.ocp4.example.com \
  </dev/null 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

## 12. Replace the default Ingress certificate

This is the most common production activity.

### 12.1 Pre-checks

Confirm the apps domain:

```bash
oc get ingresscontroller default -n openshift-ingress-operator \
  -o jsonpath='{.status.domain}{"\n"}'
```

Example output:

```text
apps.ocp4.example.com
```

Confirm certificate SAN:

```bash
openssl x509 -in tls.crt -noout -subject -issuer -dates -ext subjectAltName
```

Expected SAN:

```text
DNS:*.apps.ocp4.example.com
```

Confirm key matches certificate:

```bash
openssl x509 -in tls.crt -pubkey -noout > cert.pub
openssl pkey -in tls.key -pubout > key.pub
diff cert.pub key.pub
```

Confirm certificate is not expired:

```bash
openssl x509 -in tls.crt -noout -enddate
```

### 12.2 Create TLS secret in `openshift-ingress`

```bash
oc create secret tls custom-certs-default \
  --cert=tls.crt \
  --key=tls.key \
  -n openshift-ingress
```

Validate secret:

```bash
oc get secret custom-certs-default -n openshift-ingress -o yaml
```

Expected keys:

```yaml
data:
  tls.crt: ...
  tls.key: ...
type: kubernetes.io/tls
```

### 12.3 Patch the IngressController

```bash
oc patch ingresscontroller.operator default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"custom-certs-default"}}}'
```

Alternative YAML:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  defaultCertificate:
    name: custom-certs-default
```

Apply:

```bash
oc apply -f ingresscontroller-default-cert.yaml
```

### 12.4 Watch rollout

Changing the default certificate causes the router deployment to roll out.

```bash
oc rollout status deployment/router-default -n openshift-ingress
```

Check pods:

```bash
oc get pods -n openshift-ingress -w
```

Check Ingress Operator status:

```bash
oc get co ingress
oc describe co ingress
```

Check authentication because OAuth/console routes rely on Ingress:

```bash
oc get co authentication
oc describe co authentication
```

## 13. Verify the custom Ingress certificate

### 13.1 Verify from outside the cluster

```bash
HOST=console-openshift-console.apps.ocp4.example.com

openssl s_client \
  -connect ${HOST}:443 \
  -servername ${HOST} \
  </dev/null 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

Expected:

```text
subject=... CN = *.apps.ocp4.example.com
issuer=... Your Public CA or Enterprise CA
notAfter=...
X509v3 Subject Alternative Name:
    DNS:*.apps.ocp4.example.com
```

### 13.2 Verify with curl

```bash
curl -Iv https://console-openshift-console.apps.ocp4.example.com
```

Good signs:

```text
SSL certificate verify ok.
HTTP/2 200
```

or depending on endpoint:

```text
HTTP/1.1 200 OK
HTTP/1.1 302 Found
```

### 13.3 Verify a normal app route

```bash
oc get route -A | head
```

Pick a route under the apps domain:

```bash
curl -Iv https://myapp-dev.apps.ocp4.example.com
```

### 13.4 Verify browser trust

Open:

```text
https://console-openshift-console.apps.ocp4.example.com
```

Certificate should show as trusted and issued by your expected CA.

### 13.5 Verify router logs

```bash
oc logs -n openshift-ingress deployment/router-default --tail=100
```

Look for certificate load or HAProxy errors.

## 14. Rotate or renew the Ingress certificate

Certificate renewal is a planned operational task. Do not wait for expiry.

### 14.1 Recommended renewal window

For production:

- Start renewal at least 30 days before expiry.
- For strict enterprises, start 45–60 days before expiry.
- Maintain a rollback copy of old certificate and key until new certificate is verified.
- Test in non-production first.

### 14.2 Check expiry

From secret:

```bash
oc get secret custom-certs-default -n openshift-ingress \
  -o jsonpath='{.data.tls\.crt}' | base64 -d | \
  openssl x509 -noout -enddate
```

From live endpoint:

```bash
HOST=console-openshift-console.apps.ocp4.example.com
openssl s_client -connect ${HOST}:443 -servername ${HOST} </dev/null 2>/dev/null | \
  openssl x509 -noout -enddate
```

### 14.3 Renew by replacing the secret

Method 1: delete and recreate the secret.

```bash
oc delete secret custom-certs-default -n openshift-ingress

oc create secret tls custom-certs-default \
  --cert=new-tls.crt \
  --key=new-tls.key \
  -n openshift-ingress
```

Then trigger or wait for reconciliation:

```bash
oc rollout status deployment/router-default -n openshift-ingress
```

If rollout does not happen automatically in your version/environment, restart router deployment carefully:

```bash
oc rollout restart deployment/router-default -n openshift-ingress
oc rollout status deployment/router-default -n openshift-ingress
```

Method 2: create a new secret name and patch IngressController.

```bash
oc create secret tls custom-certs-default-2026 \
  --cert=new-tls.crt \
  --key=new-tls.key \
  -n openshift-ingress

oc patch ingresscontroller.operator default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"custom-certs-default-2026"}}}'
```

This method is cleaner because rollback is simple:

```bash
oc patch ingresscontroller.operator default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"custom-certs-default"}}}'
```

### 14.4 Production rotation checklist

Before change:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml > before-ingresscontroller.yaml
oc get secret custom-certs-default -n openshift-ingress -o yaml > before-custom-certs-default.yaml
oc get co ingress authentication
```

During change:

```bash
oc get pods -n openshift-ingress -w
oc rollout status deployment/router-default -n openshift-ingress
```

After change:

```bash
curl -Iv https://console-openshift-console.apps.ocp4.example.com
oc get co ingress authentication
```

## 15. Rollback to the OpenShift-generated certificate

If you must remove the custom default certificate and go back to the generated certificate:

```bash
oc patch ingresscontroller.operator default \
  -n openshift-ingress-operator \
  --type=json \
  -p='[{"op":"remove","path":"/spec/defaultCertificate"}]'
```

Then monitor:

```bash
oc rollout status deployment/router-default -n openshift-ingress
oc get co ingress authentication
```

Important:

- This may restore an untrusted/self-signed certificate.
- Browsers and external clients may show warnings again.
- Use rollback only as emergency recovery or for lab/testing.

## 16. Route-level TLS certificates

The default Ingress certificate is not the only way to serve TLS. Each secure route can have its own certificate.

### When to use route-specific certificates

Use a route-level certificate when:

- the route host is outside the default apps wildcard domain;
- the application uses a vanity domain like `www.company.com`;
- a business unit owns its own certificate;
- you need different certificate lifecycle per application;
- you need a certificate with specific SANs;
- you are exposing an application through a custom domain not covered by `*.apps.ocp4.example.com`.

Example:

```text
Default Ingress cert: *.apps.ocp4.example.com
Application route: payment.company.com
```

The wildcard certificate does not cover `payment.company.com`, so configure a route-specific certificate.

### Edge route with custom certificate

```bash
oc create route edge payment \
  --service=payment-svc \
  --hostname=payment.company.com \
  --cert=payment.crt \
  --key=payment.key \
  --ca-cert=payment-ca-chain.crt \
  -n payment-prod
```

### Inspect route certificate

```bash
oc get route payment -n payment-prod -o yaml
```

You will see:

```yaml
spec:
  host: payment.company.com
  tls:
    termination: edge
    certificate: |-
      -----BEGIN CERTIFICATE-----
    key: |-
      -----BEGIN PRIVATE KEY-----
    caCertificate: |-
      -----BEGIN CERTIFICATE-----
```

### Security note

Route TLS private keys are stored in the route object. Control RBAC carefully because anyone who can read that route YAML can potentially read the private key.

For this reason, many enterprises prefer:

- default wildcard Ingress certificate for standard apps domain routes;
- strict RBAC around namespaces using custom route certificates;
- external secrets management or automation for certificate lifecycle;
- GitOps secret encryption if route manifests contain TLS material.

## 17. Edge, re-encrypt, and passthrough TLS

OpenShift Routes support multiple TLS termination modes.

### 17.1 Edge termination

In edge termination, TLS terminates at the router.

```text
Client --HTTPS--> Router --HTTP--> Pod
```

Characteristics:

- Router presents certificate to client.
- Router decrypts traffic.
- Router forwards plain HTTP to backend service.
- Simple and common for internal cluster networks.
- Not end-to-end encrypted from router to pod.

Command:

```bash
oc create route edge myapp \
  --service=myapp-svc \
  --hostname=myapp.apps.ocp4.example.com
```

If no `--cert` and `--key` are provided, the route uses the default Ingress certificate.

### 17.2 Edge termination with route-specific certificate

```bash
oc create route edge myapp \
  --service=myapp-svc \
  --hostname=www.example.com \
  --cert=tls.crt \
  --key=tls.key \
  --ca-cert=ca.crt
```

### 17.3 Re-encrypt termination

In re-encrypt termination, TLS terminates at the router, then the router creates a new TLS connection to the backend pod.

```text
Client --HTTPS--> Router --HTTPS--> Pod
```

Characteristics:

- Router presents external certificate to client.
- Router decrypts and inspects HTTP routing information.
- Router re-encrypts traffic to backend.
- Backend pod/service must serve TLS.
- Requires destination CA trust for backend certificate verification.

Command:

```bash
oc create route reencrypt myapp \
  --service=myapp-svc \
  --hostname=myapp.apps.ocp4.example.com \
  --dest-ca-cert=backend-ca.crt
```

With route-specific external cert:

```bash
oc create route reencrypt myapp \
  --service=myapp-svc \
  --hostname=www.example.com \
  --cert=frontend.crt \
  --key=frontend.key \
  --ca-cert=frontend-chain.crt \
  --dest-ca-cert=backend-ca.crt
```

### 17.4 Passthrough termination

In passthrough termination, the router does not terminate TLS.

```text
Client --HTTPS---------------> Pod
          Router passes stream
```

Characteristics:

- Router uses SNI to select backend route.
- Router does not present the Ingress default certificate for the application session.
- Backend application presents its own certificate.
- Useful for mutual TLS because TLS is end-to-end between client and application.
- Router cannot inspect HTTP headers because traffic remains encrypted.

Command:

```bash
oc create route passthrough myapp \
  --service=myapp-svc \
  --hostname=secure.apps.ocp4.example.com
```

### 17.5 Choosing a TLS termination mode

| Requirement | Recommended mode |
|---|---|
| Simple HTTPS exposure | Edge |
| HTTPS from client to router and router to pod | Re-encrypt |
| Backend app owns TLS completely | Passthrough |
| Mutual TLS between client and app | Passthrough |
| Router must inspect HTTP headers/cookies | Edge or re-encrypt |
| App uses custom external domain | Edge/re-encrypt with route-specific cert, or default cert if SAN matches |

## 18. Multiple IngressControllers and sharding

Production clusters may have more than one IngressController, for example:

- public router;
- private/internal router;
- DMZ router;
- app-team-specific router;
- PCI router;
- dedicated router for high-throughput workloads.

Each IngressController can have its own:

- domain;
- default certificate;
- namespace selector;
- route selector;
- replicas;
- endpoint publishing strategy;
- node placement;
- TLS security profile.

Example:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: internal
  namespace: openshift-ingress-operator
spec:
  domain: internal.apps.ocp4.example.com
  defaultCertificate:
    name: internal-apps-cert
  namespaceSelector:
    matchLabels:
      router: internal
```

Secret:

```bash
oc create secret tls internal-apps-cert \
  --cert=internal-tls.crt \
  --key=internal-tls.key \
  -n openshift-ingress
```

Certificate SAN:

```text
*.internal.apps.ocp4.example.com
```

### Sharding impact on certificates

If you have multiple domains, you need certificates for each domain.

| IngressController | Domain | Certificate SAN |
|---|---|---|
| `default` | `apps.ocp4.example.com` | `*.apps.ocp4.example.com` |
| `internal` | `internal.apps.ocp4.example.com` | `*.internal.apps.ocp4.example.com` |
| `pci` | `pci.apps.ocp4.example.com` | `*.pci.apps.ocp4.example.com` |

Do not assume one wildcard covers all subdomains.

`*.apps.ocp4.example.com` does **not** cover:

```text
myapp.internal.apps.ocp4.example.com
```

## 19. TLS security profiles for Ingress

The Ingress certificate proves identity. The TLS security profile controls protocol and cipher behavior.

These are related but different:

| Item | Controls |
|---|---|
| Certificate | Identity, SAN, issuer, validity, trust |
| TLS security profile | TLS versions and cipher suites |

### Configure TLS security profile

```bash
oc edit ingresscontroller default -n openshift-ingress-operator
```

Example:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  tlsSecurityProfile:
    type: Intermediate
    intermediate: {}
```

Custom example:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  tlsSecurityProfile:
    type: Custom
    custom:
      minTLSVersion: VersionTLS12
      ciphers:
        - ECDHE-ECDSA-AES128-GCM-SHA256
        - ECDHE-RSA-AES128-GCM-SHA256
        - ECDHE-ECDSA-AES256-GCM-SHA384
        - ECDHE-RSA-AES256-GCM-SHA384
```

Verify:

```bash
oc describe ingresscontroller default -n openshift-ingress-operator
```

Look for:

```text
Spec:
  Tls Security Profile:
Status:
  Tls Profile:
```

### Practical guidance

- Use `Intermediate` for broad compatibility in most enterprises.
- Use `Modern` only if all clients support modern TLS requirements and your OpenShift version supports it as expected.
- Use `Custom` only when required by compliance and after testing.
- Do not blindly disable older protocols without checking legacy clients, monitoring probes, API consumers, and partner integrations.

## 20. Private CA and enterprise trust considerations

Many enterprises use internal PKI rather than public CA certificates.

### 20.1 External clients must trust the issuing CA

If the Ingress certificate is signed by an internal CA, every external client must trust that CA.

Examples:

- user laptops;
- jump servers;
- CI/CD runners;
- monitoring systems;
- API gateways;
- third-party integrations;
- synthetic monitoring tools;
- load balancer health-check clients.

If they do not trust the CA, they may report:

```text
x509: certificate signed by unknown authority
SSL certificate problem: unable to get local issuer certificate
```

### 20.2 Cluster trust vs client trust

Configuring the OpenShift cluster trust bundle helps pods and cluster components trust external CAs. It does not automatically make every user laptop or browser trust your internal CA.

There are two separate trust problems:

```text
Client -> OpenShift route trust
Pod/OpenShift component -> External service trust
```

Ingress certificate replacement mainly solves:

```text
External client -> OpenShift route
```

### 20.3 When to update cluster-wide trusted CA

You may need custom CA bundle configuration when:

- pods call external HTTPS endpoints signed by private CA;
- OpenShift components pull images from registries using private CA;
- builds need to access internal Git servers using private CA;
- re-encrypt routes use backend certificates signed by internal service CA or private CA;
- internal automation calls OpenShift routes and validates certificates.

## 21. Ingress certificate and OAuth/web console behavior

The OpenShift console and OAuth endpoints are exposed using routes under the apps domain.

Examples:

```text
console-openshift-console.apps.ocp4.example.com
oauth-openshift.apps.ocp4.example.com
```

Therefore, replacing the default Ingress certificate affects console login and OAuth browser flows.

After changing Ingress certificate, always check:

```bash
oc get co authentication
oc get co console
oc get co ingress
```

Also test:

```bash
curl -Iv https://console-openshift-console.apps.ocp4.example.com
curl -Iv https://oauth-openshift.apps.ocp4.example.com
```

Common symptoms after a bad certificate change:

| Symptom | Likely cause |
|---|---|
| Browser warning on console | CA not trusted or SAN mismatch |
| OAuth login fails | OAuth route certificate/trust issue |
| `authentication` ClusterOperator degraded | OAuth endpoint unavailable or certificate problem |
| `curl` shows wrong issuer | Router still serving old certificate or wrong IngressController selected |
| Console route gives TLS error | Secret chain incomplete or wrong certificate |

## 22. Ingress certificate and image registry routes

If the internal OpenShift image registry is exposed using a route, its external HTTPS behavior may rely on the default Ingress certificate unless a custom route certificate is configured for the registry route.

Typical exposed registry route:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --patch '{"spec":{"defaultRoute":true}}' \
  --type=merge
```

Get route:

```bash
oc get route default-route -n openshift-image-registry
```

If the registry route is under:

```text
default-route-openshift-image-registry.apps.ocp4.example.com
```

then a wildcard Ingress certificate for:

```text
*.apps.ocp4.example.com
```

will normally cover it.

Without a trusted certificate, external `podman login` or image push/pull operations may require insecure flags or fail certificate verification. In production, avoid `--tls-verify=false` as a permanent solution.

## 23. Operational runbook

### 23.1 Standard change plan

1. Identify apps domain.
2. Generate CSR with correct SAN.
3. Get certificate from CA.
4. Build full certificate chain.
5. Validate certificate, key, SAN, expiry, and chain.
6. Create new TLS secret in `openshift-ingress`.
7. Patch IngressController `defaultCertificate`.
8. Watch router rollout.
9. Verify console, OAuth, and sample app routes.
10. Monitor ClusterOperators.
11. Keep rollback secret until validation is complete.

### 23.2 CSR generation example

Create OpenSSL config:

```ini
[ req ]
default_bits       = 2048
prompt             = no
default_md         = sha256
req_extensions     = req_ext
distinguished_name = dn

[ dn ]
C  = IN
ST = Delhi
L  = New Delhi
O  = Example Corp
OU = Platform Engineering
CN = *.apps.ocp4.example.com

[ req_ext ]
subjectAltName = @alt_names

[ alt_names ]
DNS.1 = *.apps.ocp4.example.com
DNS.2 = apps.ocp4.example.com
```

Generate key and CSR:

```bash
openssl req -new \
  -newkey rsa:2048 \
  -nodes \
  -keyout tls.key \
  -out ingress-wildcard.csr \
  -config ingress-wildcard.cnf
```

Inspect CSR:

```bash
openssl req -in ingress-wildcard.csr -noout -text | grep -A2 "Subject Alternative Name"
```

Submit the CSR to public CA or enterprise PKI.

### 23.3 Prepare final files from CA output

Example CA files:

```text
wildcard_apps_ocp4_example_com.crt
intermediate_ca.crt
root_ca.crt
tls.key
```

Build `tls.crt`:

```bash
cat wildcard_apps_ocp4_example_com.crt intermediate_ca.crt > tls.crt
```

Validate:

```bash
openssl x509 -in tls.crt -noout -subject -issuer -dates -ext subjectAltName
openssl verify -CAfile <(cat intermediate_ca.crt root_ca.crt) wildcard_apps_ocp4_example_com.crt
```

### 23.4 Apply

```bash
oc create secret tls custom-certs-default-2026 \
  --cert=tls.crt \
  --key=tls.key \
  -n openshift-ingress

oc patch ingresscontroller.operator default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"custom-certs-default-2026"}}}'

oc rollout status deployment/router-default -n openshift-ingress
```

### 23.5 Post-check

```bash
oc get co ingress authentication console

HOST=console-openshift-console.apps.ocp4.example.com
openssl s_client -connect ${HOST}:443 -servername ${HOST} </dev/null 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates -ext subjectAltName

curl -Iv https://${HOST}
```

## 24. Troubleshooting guide

### Problem 1: Browser says certificate is not trusted

Symptoms:

```text
NET::ERR_CERT_AUTHORITY_INVALID
x509: certificate signed by unknown authority
```

Likely causes:

- certificate signed by private CA not trusted by client;
- missing intermediate CA in `tls.crt`;
- client trust store not updated;
- wrong certificate served by router;
- TLS interception/proxy replacing certificates.

Checks:

```bash
openssl s_client -connect myapp.apps.ocp4.example.com:443 \
  -servername myapp.apps.ocp4.example.com -showcerts </dev/null
```

Fix:

- use public CA certificate; or
- distribute enterprise root/intermediate CA to clients; and
- include intermediate chain in `tls.crt`.

---

### Problem 2: Hostname mismatch

Symptoms:

```text
certificate is valid for *.apps.ocp4.example.com, not api.prod.apps.ocp4.example.com
```

Cause:

Wildcard does not cover multiple DNS label levels.

Fix:

- use hostname directly under apps domain; or
- create route-specific certificate; or
- use another IngressController domain and matching wildcard; or
- issue a certificate with required SANs.

---

### Problem 3: Router still serves old certificate

Checks:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get secret -n openshift-ingress custom-certs-default -o yaml
oc rollout status deployment/router-default -n openshift-ingress
oc get pods -n openshift-ingress
```

Possible causes:

- IngressController patch not applied;
- secret created in wrong namespace;
- wrong secret name referenced;
- router rollout not completed;
- DNS points to different cluster/router;
- request is hitting another IngressController shard;
- external load balancer is terminating TLS before OpenShift.

Fix:

```bash
oc patch ingresscontroller.operator default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"custom-certs-default"}}}'

oc rollout restart deployment/router-default -n openshift-ingress
```

Use rollout restart only after confirming the Operator did not already roll out naturally.

---

### Problem 4: Secret has wrong keys

Symptoms:

Router fails to load certificate or Ingress Operator reports degraded.

Check:

```bash
oc get secret custom-certs-default -n openshift-ingress -o jsonpath='{.type}{"\n"}'
oc get secret custom-certs-default -n openshift-ingress -o jsonpath='{.data}'
```

Expected:

```text
kubernetes.io/tls
```

Expected keys:

```text
tls.crt
tls.key
```

Fix:

```bash
oc delete secret custom-certs-default -n openshift-ingress
oc create secret tls custom-certs-default --cert=tls.crt --key=tls.key -n openshift-ingress
```

---

### Problem 5: Certificate and key do not match

Symptoms:

Router pod fails, HAProxy complains, or TLS handshake fails.

Check:

```bash
openssl x509 -in tls.crt -pubkey -noout > cert.pub
openssl pkey -in tls.key -pubout > key.pub
diff cert.pub key.pub
```

Fix:

- locate correct key used to generate CSR;
- reissue certificate if key is lost;
- never guess certificate/key pairs in production.

---

### Problem 6: Ingress ClusterOperator degraded

Check:

```bash
oc get co ingress
oc describe co ingress
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc logs -n openshift-ingress-operator deployment/ingress-operator --tail=200
```

Possible causes:

- bad certificate secret;
- missing secret;
- invalid IngressController configuration;
- router deployment cannot roll out;
- node scheduling issue;
- load balancer issue;
- DNS issue.

---

### Problem 7: Authentication ClusterOperator degraded after Ingress certificate change

Check:

```bash
oc get co authentication
oc describe co authentication
oc get route -n openshift-authentication
oc get route -n openshift-console
curl -Iv https://oauth-openshift.apps.ocp4.example.com
```

Possible causes:

- OAuth route not reachable;
- certificate chain not trusted;
- wrong wildcard SAN;
- router not serving new cert correctly;
- external DNS/load balancer points to wrong place.

Fix:

- fix Ingress certificate first;
- verify OAuth route;
- then wait for authentication operator to recover.

---

### Problem 8: `curl` works with `-k` but fails without `-k`

Example:

```bash
curl -k https://myapp.apps.ocp4.example.com
```

works, but:

```bash
curl https://myapp.apps.ocp4.example.com
```

fails.

Meaning:

- TCP connectivity and routing are probably okay;
- TLS trust or hostname validation is failing.

Check:

```bash
curl -Iv https://myapp.apps.ocp4.example.com
```

Fix the certificate trust, SAN, or chain issue. Do not use `-k` as a production solution.

---

### Problem 9: Route-specific certificate not used

Possible causes:

- route is not secured;
- route TLS section missing;
- host mismatch;
- passthrough route behavior misunderstood;
- request SNI missing or wrong;
- another route owns same host;
- route admitted by different IngressController.

Checks:

```bash
oc get route myapp -n myns -o yaml
oc describe route myapp -n myns
openssl s_client -connect myhost.example.com:443 -servername myhost.example.com </dev/null
```

---

### Problem 10: External load balancer is serving a different certificate

In some environments, TLS is terminated before traffic reaches OpenShift.

Flow may be:

```text
Client --HTTPS--> External LB --HTTP/HTTPS--> OpenShift router
```

If external LB terminates TLS, changing the OpenShift Ingress certificate might not change what the client sees.

Check:

- load balancer listener configuration;
- certificate bound to LB frontend;
- whether LB uses TCP passthrough or HTTPS termination;
- whether OpenShift router receives encrypted traffic.

For OpenShift route TLS to be visible to clients, the external LB should usually use TCP passthrough for port 443.

## 25. Security best practices

### 25.1 Use trusted CA-issued wildcard certificates

For production, use a certificate issued by:

- a public CA, for internet-facing apps; or
- enterprise internal CA, for private/internal apps.

### 25.2 Use SAN, not only CN

Modern TLS clients validate SAN. Ensure the certificate has:

```text
DNS:*.apps.ocp4.example.com
```

### 25.3 Store private keys securely

Private keys should be:

- generated on a secure admin host or HSM-backed process;
- accessible only to platform/security admins;
- never committed to plain Git;
- rotated if exposed;
- transferred securely.

### 25.4 Use separate certificates for separate trust zones

Example:

| Zone | Domain | Certificate |
|---|---|---|
| Public apps | `*.apps.ocp4.example.com` | Public CA |
| Internal apps | `*.internal.apps.ocp4.example.com` | Enterprise CA |
| PCI apps | `*.pci.apps.ocp4.example.com` | PCI-controlled CA |

### 25.5 Monitor expiry

Create monitoring for:

- secret certificate expiry;
- live route certificate expiry;
- route-specific certificates;
- API server certificates;
- service serving certificates where relevant.

Useful script pattern:

```bash
for host in \
  console-openshift-console.apps.ocp4.example.com \
  oauth-openshift.apps.ocp4.example.com \
  myapp.apps.ocp4.example.com; do
  echo "===== $host ====="
  echo | openssl s_client -connect ${host}:443 -servername ${host} 2>/dev/null | \
    openssl x509 -noout -subject -issuer -enddate
done
```

### 25.6 Avoid permanent insecure client flags

Avoid permanent use of:

```bash
curl -k
podman --tls-verify=false
```

These hide certificate problems rather than fixing them.

### 25.7 Apply least privilege RBAC

Restrict access to:

```text
openshift-ingress secrets
IngressController resources
routes with embedded certificates
```

Users who can read private key material can impersonate the route endpoint.

### 25.8 Keep documented rollback

Before certificate change:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml > ingresscontroller-before.yaml
oc get secret -n openshift-ingress custom-certs-default -o yaml > cert-secret-before.yaml
```

### 25.9 Validate from multiple networks

Test from:

- bastion host;
- admin laptop;
- monitoring network;
- application consumer network;
- external internet if public;
- inside cluster if internal clients use routes.

## 26. Interview and real-world scenario questions

### Q1. Where do you configure the default Ingress certificate?

On the `IngressController` custom resource in `openshift-ingress-operator`, using:

```yaml
spec:
  defaultCertificate:
    name: <secret-name>
```

The referenced TLS secret must be in `openshift-ingress`.

### Q2. What happens if a route has its own certificate?

The route-specific certificate is served for that route host instead of the IngressController default certificate, for edge or re-encrypt routes.

### Q3. Why does `*.apps.example.com` not match `api.prod.apps.example.com`?

A wildcard certificate covers only one DNS label. `*.apps.example.com` covers `api.apps.example.com`, not `api.prod.apps.example.com`.

### Q4. Why did console login break after replacing the Ingress certificate?

Because console and OAuth are exposed through routes under the apps domain. A bad default Ingress certificate can break browser trust or OAuth route health.

### Q5. Which namespace stores the custom default Ingress certificate secret?

`openshift-ingress`.

### Q6. Which namespace stores the IngressController CR?

`openshift-ingress-operator`.

### Q7. Does replacing Ingress certificate change the Kubernetes API certificate?

No. API server certificates are separate from Ingress route certificates.

### Q8. Does passthrough route use the default Ingress certificate?

No. The backend application presents its own certificate. The router passes encrypted traffic through.

### Q9. What is the safest renewal strategy?

Create a new secret with a versioned name, patch the IngressController to point to it, verify, and keep the old secret for rollback until validation is complete.

### Q10. What is the most common mistake during replacement?

Creating the TLS secret in the wrong namespace, using an incomplete chain, or using a certificate without the correct SAN.

```text
Correct wildcard SAN
+ complete certificate chain
+ TLS secret in openshift-ingress
+ IngressController defaultCertificate reference
+ rollout verification
+ expiry monitoring
+ documented rollback
```
