## 1. Executive Summary

In OpenShift, the **API certificate** normally means the **TLS serving certificate presented by the Kubernetes API server** when clients connect to the API endpoint, usually:

```text
https://api.<cluster_name>.<base_domain>:6443
```

This certificate protects the most important control-plane entry point in the cluster. Every `oc`, `kubectl`, Operator, controller, CI/CD tool, automation script, and service account that talks to the API depends on this trust relationship.

At a practical level, the API certificate answers one question:

> “When a client connects to the OpenShift API endpoint, how does the client know it is really talking to the genuine OpenShift API server and not a fake endpoint?”

The API certificate provides:

- **Encryption** of API traffic over TLS.
- **Server identity validation** for `api.<cluster>.<domain>`.
- **Protection from man-in-the-middle attacks**.
- **Trust integration** with enterprise/public Certificate Authorities when configured.
- **Clean browser/CLI trust** for users and automation outside the cluster.

By default, OpenShift uses an **internal cluster CA** to issue the API server certificate. For production, many organizations add a **custom API server named certificate** signed by an enterprise CA or public CA so that external clients trust the API endpoint without manually importing the internal OpenShift CA.

## 2. What Is an API Certificate?

An API certificate is an **X.509 TLS server certificate** used by the OpenShift Kubernetes API server to serve HTTPS traffic on port `6443`.

When you run:

```bash
oc login https://api.ocp4.example.com:6443
```

or:

```bash
kubectl get nodes --server=https://api.ocp4.example.com:6443
```

the client connects over TLS. During the TLS handshake, the API server presents a certificate. The client checks whether:

1. The certificate is valid for the DNS name used by the client.
2. The certificate is not expired.
3. The certificate chain leads to a trusted CA.
4. The certificate is acceptable for server authentication.
5. The private key used by the server matches the public key in the certificate.

If validation fails, you commonly see errors such as:

```text
x509: certificate signed by unknown authority
```

```text
x509: certificate is valid for api.ocp4.example.com, not api.newdomain.example.com
```

```text
x509: certificate has expired or is not yet valid
```

The API certificate is not the same as a user token, OAuth token, kubeconfig client certificate, ingress certificate, route certificate, service serving certificate, or etcd certificate. It is specifically the **server-side TLS identity** for the API endpoint.

## 3. Where the API Certificate Fits in OpenShift Architecture

A simplified API access path looks like this:

```text
Admin laptop / Automation / Operator / CI tool
        |
        | HTTPS 6443
        v
External Load Balancer / VIP
        |
        v
Control plane node
        |
        v
kube-apiserver static pod
        |
        v
Authentication -> Authorization -> Admission -> etcd
```

The API certificate is presented by the API server side of this path. The certificate is normally observed by clients at the public API endpoint:

```text
api.<cluster_name>.<base_domain>:6443
```

In many clusters, traffic first hits a load balancer. The load balancer usually passes TCP traffic through to the control-plane nodes for port `6443`. In that model, TLS termination happens at the Kubernetes API server, not at the external load balancer.

Some organizations use more complex patterns, such as reverse proxies, private endpoints, split DNS, or dedicated management networks. In those cases, a named API server certificate can be configured for the exact FQDN used by the client.

## 4. API Serving Certificate vs API Client Certificate

The phrase “API certificate” can be confusing because there are two major certificate directions:

| Type | Used by | Purpose | Example |
|---|---|---|---|
| API **serving** certificate | API server | Proves the API server identity to clients | `api.ocp4.example.com` certificate |
| API **client** certificate | Client/user/component | Authenticates a client to the API server | kubelet client cert, admin kubeconfig cert |

### 4.1 API Serving Certificate

This is the main topic of this note. It is presented by the API server to clients.

Example validation command:

```bash
echo | openssl s_client \
  -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### 4.2 API Client Certificate

A client certificate is used when a client authenticates to the API server using mTLS-style client certificate authentication.

Examples include:

- Kubelet client certificates.
- Controller certificates.
- Certificates generated through Kubernetes CertificateSigningRequest objects.
- Legacy or special-purpose admin kubeconfigs.

Modern OpenShift administrators mostly use OAuth tokens with `oc login`, but client certificates still exist inside the control plane and node lifecycle.

### 4.3 Do Not Mix These Concepts

If the client says:

```text
certificate signed by unknown authority
```

that usually means the client does not trust the **API serving certificate** chain.

If the API server says:

```text
Unauthorized
```

or:

```text
You must be logged in to the server
```

that usually means the user token/client certificate authentication failed.

TLS trust failure happens **before** OpenShift authentication and RBAC. Authentication/RBAC failure happens **after** TLS is established.

## 5. Default OpenShift API Certificate Behavior

During installation, OpenShift creates internal certificate authorities and operator-managed certificates. The default API server certificate is issued by an internal OpenShift cluster CA.

This default design works well for cluster-managed components because the cluster distributes the needed CA information internally. However, generic external clients, browsers, enterprise monitoring tools, and automation systems might not trust that internal CA unless the CA is explicitly installed or embedded into the client configuration.

For production, common approaches are:

1. Keep the default internal API certificate and distribute the CA to trusted clients.
2. Add a custom API server named certificate signed by an enterprise CA.
3. Add a custom API server named certificate signed by a public CA, where policy allows.
4. Use cert-manager Operator for Red Hat OpenShift to automate issuing and renewal.

The preferred enterprise design is usually option 2 or option 4.

## 6. Important API Endpoints and Names

OpenShift commonly uses these names:

| Endpoint | Typical form | Purpose | Custom named certificate? |
|---|---|---|---|
| Public/API endpoint | `api.<cluster>.<base_domain>` | Used by admins, CLI, external automation | Yes, common |
| Internal API endpoint | `api-int.<cluster>.<base_domain>` | Used internally by nodes/control plane | **No, avoid** |
| Kubernetes service DNS | `kubernetes.default.svc` | In-cluster service endpoint | Managed internally |
| Console route | `console-openshift-console.apps.<cluster>.<base_domain>` | Web console access | Ingress/route certificate, not API certificate |
| OAuth route | Often under `.apps` domain | User login flow | OAuth/ingress certificate path, not the same as API serving cert in standard OCP |

### Critical Warning About `api-int`

Do **not** configure a named API certificate for:

```text
api-int.<cluster_name>.<base_domain>
```

The internal API endpoint is used by workers/control-plane components. Replacing or misconfiguring trust for this internal endpoint can degrade the cluster. Treat `api-int` as an internal platform endpoint managed by OpenShift.

## 7. OpenShift Resources Involved

The main OpenShift resource is:

```bash
oc get apiserver cluster -o yaml
```

This is the cluster-scoped `APIServer` configuration object:

```yaml
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  servingCerts:
    namedCertificates:
    - names:
      - api.ocp4.example.com
      servingCertificate:
        name: api-custom-cert
```

The certificate and private key are stored in a Kubernetes TLS secret in:

```text
namespace: openshift-config
type: kubernetes.io/tls
keys:
  tls.crt
  tls.key
```

Example:

```bash
oc get secret api-custom-cert -n openshift-config -o yaml
```

Other important objects/components:

| Component | Purpose |
|---|---|
| `apiserver/cluster` | User-facing API server certificate configuration |
| `openshift-config` namespace | Location for the user-provided TLS secret |
| `kube-apiserver-operator` | Reconciles API server static pod revisions |
| `openshift-kube-apiserver` namespace | Runs kube-apiserver static pod mirror objects/log visibility |
| `clusteroperator/kube-apiserver` | Shows API operator health/progressing/degraded status |
| `clusteroperator/authentication` | Useful when login/token flows are affected |
| `clusteroperator/openshift-apiserver` | Useful for OpenShift API extension health |

## 8. TLS Handshake Flow for `oc login`

When you run:

```bash
oc login https://api.ocp4.example.com:6443
```

the flow is:

```text
1. Client resolves api.ocp4.example.com by DNS.
2. Client connects to port 6443.
3. Client sends TLS ClientHello with SNI = api.ocp4.example.com.
4. API server chooses the certificate matching that name.
5. API server presents the certificate chain.
6. Client validates:
   - SAN contains api.ocp4.example.com
   - Certificate is time-valid
   - Chain leads to trusted CA
   - Usage supports server authentication
7. TLS session is established.
8. oc performs authentication flow.
9. API server validates token/client identity.
10. RBAC decides allowed actions.
```

This order is important. If certificate trust fails, OpenShift authentication never starts.

## 9. Subject Alternative Name, Common Name, and SNI

Modern TLS clients validate the DNS name using the **Subject Alternative Name** extension, not only the Common Name.

A good certificate must include:

```text
DNS:api.ocp4.example.com
```

inside SAN.

Example check:

```bash
openssl x509 -in fullchain.pem -noout -text | grep -A2 "Subject Alternative Name"
```

Expected output:

```text
X509v3 Subject Alternative Name:
    DNS:api.ocp4.example.com
```

### SNI Selection

SNI means **Server Name Indication**. A client sends the requested hostname during TLS negotiation. OpenShift can serve different named certificates depending on the FQDN requested by the client.

Example:

```yaml
spec:
  servingCerts:
    namedCertificates:
    - names:
      - api.ocp4.example.com
      servingCertificate:
        name: api-prod-cert
    - names:
      - api.dr.ocp4.example.com
      servingCertificate:
        name: api-dr-cert
```

Rules to remember:

- Exact names are preferred over wildcard names.
- Explicit names in `spec.servingCerts.namedCertificates[].names` are preferred over names extracted from the certificate.
- If no named certificate matches, the default API serving certificate is used.
- Always test with `-servername` in `openssl s_client`; otherwise you might not test SNI correctly.

## 10. Certificate Chain Requirements

For an API server named certificate, the certificate file should normally contain the full chain in this order:

```text
1. Leaf/server certificate for api.<cluster>.<base_domain>
2. Intermediate CA certificate(s)
3. Root CA certificate, if required by your organization/process
```

Example:

```bash
cat api-server.crt intermediate-ca.crt root-ca.crt > fullchain.pem
```

Private key file:

```text
api-server.key
```

The private key must be unencrypted for Kubernetes TLS secret use.

Create TLS secret:

```bash
oc create secret tls api-custom-cert \
  --cert=fullchain.pem \
  --key=api-server.key \
  -n openshift-config
```

### Common Chain Mistakes

| Mistake | Symptom |
|---|---|
| Leaf certificate missing | API server cannot serve expected certificate |
| Wrong order | Some clients fail chain validation |
| Intermediate missing | Works on some laptops, fails on minimal containers/automation |
| SAN missing | `certificate is valid for X, not Y` |
| Key does not match cert | Secret accepted but API operator may fail to use it |
| Encrypted private key | API server cannot load key |
| Wrong namespace | API server cannot reference the secret |
| Secret not `kubernetes.io/tls` | API server cannot consume it as expected |

## 11. Adding a Custom API Server Named Certificate

### 11.1 Preconditions

Before making changes, confirm:

```bash
oc whoami
oc get clusterversion
oc get clusteroperators
oc get nodes
oc get apiserver cluster -o yaml
```

You need:

- `cluster-admin` access.
- Correct FQDN, usually `api.<cluster>.<base_domain>`.
- Valid DNS record pointing to the API load balancer/VIP.
- Certificate with SAN for the API FQDN.
- Full certificate chain in PEM format.
- Unencrypted private key.
- Planned maintenance/change window for production.

### 11.2 Inspect Current API Certificate

From your workstation:

```bash
API_FQDN=api.ocp4.example.com

openssl s_client \
  -connect ${API_FQDN}:6443 \
  -servername ${API_FQDN} \
  -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

Check current `apiserver/cluster` config:

```bash
oc get apiserver cluster -o yaml
```

### 11.3 Create the TLS Secret

```bash
oc create secret tls api-custom-cert \
  --cert=/path/to/fullchain.pem \
  --key=/path/to/api-server.key \
  -n openshift-config
```

Verify:

```bash
oc get secret api-custom-cert -n openshift-config
oc get secret api-custom-cert -n openshift-config -o jsonpath='{.type}{"\n"}'
```

Expected:

```text
kubernetes.io/tls
```

Inspect the stored certificate:

```bash
oc get secret api-custom-cert -n openshift-config \
  -o jsonpath='{.data.tls\.crt}' \
  | base64 -d \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### 11.4 Patch the API Server Configuration

```bash
oc patch apiserver cluster --type=merge -p '
{
  "spec": {
    "servingCerts": {
      "namedCertificates": [
        {
          "names": ["api.ocp4.example.com"],
          "servingCertificate": {
            "name": "api-custom-cert"
          }
        }
      ]
    }
  }
}'
```

### 11.5 Watch the Rollout

Adding a named certificate for the first time causes the `kube-apiserver-operator` to roll out a new API server pod revision. Node reboots are not required.

Watch status:

```bash
watch 'oc get clusteroperators kube-apiserver authentication openshift-apiserver'
```

Or:

```bash
oc get co kube-apiserver
oc describe co kube-apiserver
```

Check pods:

```bash
oc get pods -n openshift-kube-apiserver -o wide
```

Do not repeatedly patch the object while the API server is progressing. Wait until:

```text
AVAILABLE=True
PROGRESSING=False
DEGRADED=False
```

### 11.6 Validate From Outside the Cluster

```bash
API_FQDN=api.ocp4.example.com

echo | openssl s_client \
  -connect ${API_FQDN}:6443 \
  -servername ${API_FQDN} 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

Then run:

```bash
oc login https://${API_FQDN}:6443
oc whoami
oc get nodes
```

If a browser or automation tool previously showed a trust warning, retest from a clean environment that trusts the issuing CA.

## 12. Updating or Renewing an Existing API Certificate

Renewal is different from first-time configuration.

If the API server already references a TLS secret, and you only update the certificate/key data inside the **same secret name**, the API server pods can dynamically detect and reload the updated assets. A new kube-apiserver revision is normally not required for simple secret data replacement.

### 12.1 Replace Existing Secret Data

```bash
oc create secret tls api-custom-cert \
  --cert=/path/to/new-fullchain.pem \
  --key=/path/to/new-api-server.key \
  -n openshift-config \
  --dry-run=client -o yaml | oc replace -f -
```

### 12.2 Verify No Unnecessary Rollout

```bash
oc get co kube-apiserver
oc get apiserver cluster -o yaml
```

Confirm the served certificate:

```bash
API_FQDN=api.ocp4.example.com

echo | openssl s_client \
  -connect ${API_FQDN}:6443 \
  -servername ${API_FQDN} 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -serial -fingerprint -sha256
```

### 12.3 CA Change Warning

If the renewed certificate is signed by a different root CA or intermediate chain, some clients may fail even though the API server is healthy.

Typical affected clients:

- Java applications with static truststores.
- Jenkins agents.
- GitLab runners.
- Monitoring systems.
- Custom controllers.
- Long-running pods using cached CA bundles.
- Older automation hosts with outdated CA trust.

Fix options:

- Update OS trust store on clients.
- Update application truststore.
- Recreate kubeconfig with correct `certificate-authority-data`.
- Restart long-running workloads that do not hot-reload trust bundles.

## 13. Using cert-manager for API Certificates

For production lifecycle management, the **cert-manager Operator for Red Hat OpenShift** can issue and renew API server certificates.

High-level flow:

```text
Issuer / ClusterIssuer
        |
        v
Certificate object in openshift-config
        |
        v
TLS secret generated by cert-manager
        |
        v
apiserver/cluster references that secret as named certificate
        |
        v
kube-apiserver serves certificate for API FQDN
```

Example `Certificate` object:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: api-server-cert
  namespace: openshift-config
spec:
  isCA: false
  commonName: api.ocp4.example.com
  secretName: api-custom-cert
  dnsNames:
  - api.ocp4.example.com
  issuerRef:
    name: enterprise-ca-issuer
    kind: Issuer
```

Then reference the generated secret:

```bash
oc patch apiserver cluster --type=merge -p '
{
  "spec": {
    "servingCerts": {
      "namedCertificates": [
        {
          "names": ["api.ocp4.example.com"],
          "servingCertificate": {
            "name": "api-custom-cert"
          }
        }
      ]
    }
  }
}'
```

Production note:

- Validate cert-manager version compatibility with your OpenShift release.
- Do not run Red Hat cert-manager Operator and community cert-manager Operator together unless Red Hat documentation explicitly supports your design.
- Ensure issuer credentials are protected.
- Monitor Certificate `Ready` status.
- Test renewal before expiry.

## 14. Verification Commands

### 14.1 Check API Server Configuration

```bash
oc get apiserver cluster -o yaml
```

Only named certificates:

```bash
oc get apiserver cluster \
  -o jsonpath='{.spec.servingCerts.namedCertificates}{"\n"}'
```

### 14.2 Check TLS Secret

```bash
oc get secret -n openshift-config api-custom-cert
oc describe secret -n openshift-config api-custom-cert
```

Decode certificate:

```bash
oc get secret -n openshift-config api-custom-cert \
  -o jsonpath='{.data.tls\.crt}' \
  | base64 -d \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

Check private key and certificate match:

```bash
openssl x509 -noout -modulus -in fullchain.pem | openssl md5
openssl rsa  -noout -modulus -in api-server.key | openssl md5
```

The hashes must match.

For ECDSA keys, use public key comparison:

```bash
openssl x509 -in fullchain.pem -pubkey -noout | openssl sha256
openssl pkey -in api-server.key -pubout | openssl sha256
```

### 14.3 Check Served Certificate

```bash
API_FQDN=api.ocp4.example.com

echo | openssl s_client \
  -connect ${API_FQDN}:6443 \
  -servername ${API_FQDN} \
  -showcerts 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### 14.4 Check Trust Chain

Save served chain:

```bash
openssl s_client \
  -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com \
  -showcerts </dev/null > api-chain.txt 2>/dev/null
```

Extract and verify against CA bundle:

```bash
openssl verify -CAfile enterprise-ca-bundle.pem fullchain.pem
```

### 14.5 Check Cluster Operators

```bash
oc get clusteroperators
oc get co kube-apiserver authentication openshift-apiserver
oc describe co kube-apiserver
```

### 14.6 Check API Server Pods

```bash
oc get pods -n openshift-kube-apiserver -o wide
```

Logs:

```bash
oc logs -n openshift-kube-apiserver <kube-apiserver-pod-name> -c kube-apiserver
```

If labels differ by version, first list pods and containers:

```bash
oc get pods -n openshift-kube-apiserver
oc get pod -n openshift-kube-apiserver <pod-name> -o jsonpath='{.spec.containers[*].name}{"\n"}'
```

## 15. Troubleshooting Scenarios

### Scenario 1: `x509: certificate signed by unknown authority`

#### Meaning

The client does not trust the CA that signed the API server certificate.

#### Common Causes

- API server uses internal OpenShift CA and client does not have that CA.
- Enterprise CA root/intermediate missing from client truststore.
- New cert was signed by a different CA after renewal.
- Kubeconfig has old or wrong `certificate-authority-data`.
- Automation container image has minimal CA bundle.

#### Checks

```bash
oc config view --raw --minify
```

```bash
openssl s_client \
  -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com \
  -showcerts </dev/null
```

#### Fix

- Install the CA into the client OS trust store.
- Update kubeconfig CA data.
- Provide `--certificate-authority=/path/to/ca.crt` for controlled testing.
- Do **not** use `--insecure-skip-tls-verify=true` in production automation.

---

### Scenario 2: `certificate is valid for X, not Y`

#### Meaning

The certificate SAN does not include the hostname used by the client.

#### Example

Client connects to:

```text
api-new.ocp4.example.com
```

Certificate only contains:

```text
DNS:api.ocp4.example.com
```

#### Fix

Issue a new certificate containing all required DNS names:

```text
DNS:api.ocp4.example.com
DNS:api-new.ocp4.example.com
```

Patch `apiserver/cluster` if using a new secret/name.

---

### Scenario 3: Custom Cert Added but Old Cert Still Served

#### Possible Causes

- Client did not send SNI.
- Wrong FQDN in `names` list.
- Secret is invalid.
- API server rollout not complete.
- DNS points to a different cluster or stale load balancer.
- You tested `api-int` or another endpoint.

#### Checks

Always test with `-servername`:

```bash
openssl s_client \
  -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

Check configuration:

```bash
oc get apiserver cluster -o yaml
oc get secret -n openshift-config api-custom-cert -o yaml
oc get co kube-apiserver
```

---

### Scenario 4: `kube-apiserver` ClusterOperator Becomes Degraded

#### Possible Causes

- Bad secret reference.
- Secret does not exist in `openshift-config`.
- Secret has wrong keys.
- Certificate/key mismatch.
- Private key encrypted.
- Wrong chain format.
- Named certificate configured for `api-int`.

#### Checks

```bash
oc describe co kube-apiserver
oc get apiserver cluster -o yaml
oc get secret -n openshift-config
oc get pods -n openshift-kube-apiserver
```

#### Fix

If the API is still accessible, rollback the patch or correct the secret.

---

### Scenario 5: Internal Apps Fail After Certificate Renewal

#### Meaning

The API is healthy, but client pods do not trust the new CA chain.

#### Common Causes

- Renewed certificate uses a new root CA.
- Long-running pods use cached CA bundles.
- Java truststore was not updated.
- Custom controller uses pinned CA.

#### Fix

- Update trust bundle.
- Restart affected workloads.
- Regenerate kubeconfigs.
- Avoid changing root CA during routine renewal unless planned.

---

### Scenario 6: `oc login` Works With `--insecure-skip-tls-verify` Only

#### Meaning

Network and API reachability are okay. TLS trust is broken.

#### Fix Properly

Do not leave insecure mode enabled. Fix trust:

```bash
oc login https://api.ocp4.example.com:6443 \
  --certificate-authority=/path/to/ca-bundle.crt
```

or install the CA into OS trust.

---

### Scenario 7: API Certificate Expired

#### Impact

Clients that validate TLS will fail. Cluster components may also show degraded status depending on which certificate expired and which endpoint is affected.

#### Immediate Checks

```bash
API_FQDN=api.ocp4.example.com

echo | openssl s_client \
  -connect ${API_FQDN}:6443 \
  -servername ${API_FQDN} 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

If API is still reachable with an admin kubeconfig, replace the named certificate secret immediately.

If the control plane has broader internal certificate expiry and API is not functional, follow Red Hat’s expired control-plane certificate recovery procedures or engage Red Hat Support. Avoid manually editing static pod manifests unless explicitly guided by supported recovery documentation.

## 16. Security Best Practices

### 16.1 Use Enterprise/Public CA for External API FQDN

For production, the API endpoint should be trusted by:

- Admin workstations.
- Bastion hosts.
- CI/CD systems.
- Monitoring tools.
- GitOps controllers.
- Automation platforms.
- Security scanners.

Use a certificate signed by a CA already trusted by these systems.

### 16.2 Never Configure Named Certificate for `api-int`

This is one of the most important OpenShift certificate rules.

Do not configure:

```text
api-int.<cluster>.<base_domain>
```

as a named API certificate.

### 16.3 Protect Private Keys

A Kubernetes secret is base64-encoded, not automatically “secure” by itself. Protect API certificate private keys by:

- Limiting RBAC access to `openshift-config` secrets.
- Enabling etcd encryption for sensitive resources where required.
- Avoiding secret export into tickets, chat, or Git.
- Using sealed/external secret tooling only if approved.
- Auditing secret access.

### 16.4 Avoid Wildcard API Certificates Unless Required

A wildcard such as:

```text
*.ocp4.example.com
```

may work technically, but it expands blast radius. Prefer a specific SAN:

```text
api.ocp4.example.com
```

### 16.5 Keep Certificate Lifetime Reasonable

Balance security and operational risk:

- Short lifetime improves security but requires strong automation.
- Long lifetime reduces renewal events but increases key exposure risk.
- For manual operations, maintain a renewal calendar well before expiry.
- For automated cert-manager flows, monitor renewal health.

### 16.6 Do Not Use Insecure Skip TLS Verify in Automation

This is bad:

```bash
oc login --insecure-skip-tls-verify=true
```

Use only for emergency diagnosis, never as a permanent fix.

### 16.7 Separate Ingress and API Certificate Management

Ingress certificates secure application routes under `.apps`. API certificates secure the API endpoint on `:6443`. They are configured differently:

| Certificate | Endpoint | Config object | Namespace |
|---|---|---|---|
| API certificate | `api.<cluster>.<domain>:6443` | `apiserver/cluster` | `openshift-config` |
| Default ingress certificate | `*.apps.<cluster>.<domain>` routes | `ingresscontroller/default` | `openshift-ingress-operator` |
| Service serving certificate | Internal service DNS | Service annotations / service-ca | Application namespace |

## 17. Production Change Plan

Use this as a real L3 change checklist.

### 17.1 Before Change

```bash
mkdir -p ~/api-cert-change-$(date +%F)
cd ~/api-cert-change-$(date +%F)

oc get clusterversion -o yaml > clusterversion.before.yaml
oc get co -o wide > clusteroperators.before.txt
oc get apiserver cluster -o yaml > apiserver.cluster.before.yaml
oc get nodes -o wide > nodes.before.txt
```

Back up current named certificate secret if one exists:

```bash
oc get secret -n openshift-config api-custom-cert -o yaml > api-custom-cert.before.yaml
```

Validate new certificate locally:

```bash
openssl x509 -in fullchain.pem -noout -subject -issuer -dates -ext subjectAltName
openssl verify -CAfile enterprise-ca-bundle.pem fullchain.pem
```

Check key match:

```bash
openssl x509 -noout -modulus -in fullchain.pem | openssl md5
openssl rsa  -noout -modulus -in api-server.key | openssl md5
```

### 17.2 During Change

Create or replace secret:

```bash
oc create secret tls api-custom-cert \
  --cert=fullchain.pem \
  --key=api-server.key \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

Patch `apiserver/cluster` if this is a new named certificate:

```bash
oc patch apiserver cluster --type=merge -p '
{
  "spec": {
    "servingCerts": {
      "namedCertificates": [
        {
          "names": ["api.ocp4.example.com"],
          "servingCertificate": {
            "name": "api-custom-cert"
          }
        }
      ]
    }
  }
}'
```

Watch status:

```bash
watch 'oc get co kube-apiserver authentication openshift-apiserver'
```

### 17.3 After Change

```bash
oc get co -o wide > clusteroperators.after.txt
oc get apiserver cluster -o yaml > apiserver.cluster.after.yaml
```

External validation:

```bash
API_FQDN=api.ocp4.example.com

echo | openssl s_client \
  -connect ${API_FQDN}:6443 \
  -servername ${API_FQDN} 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -fingerprint -sha256 -ext subjectAltName
```

Functional validation:

```bash
oc login https://api.ocp4.example.com:6443
oc whoami
oc get nodes
oc get projects
```

Automation validation:

- Jenkins/GitLab runner can connect.
- Argo CD/GitOps can connect.
- Monitoring can scrape/query API as expected.
- External scripts using kubeconfig still work.
- Browser trust warning is gone if browser access is relevant.

## 18. Rollback Plan

### 18.1 If You Replaced Only Secret Data

Restore previous secret from backup:

```bash
oc replace -f api-custom-cert.before.yaml
```

Then verify served certificate again.

### 18.2 If You Added a New Named Certificate

Remove or modify the `namedCertificates` entry.

Example: remove all named certificates and fall back to operator-managed default serving certificate:

```bash
oc patch apiserver cluster --type=json \
  -p='[{"op":"remove","path":"/spec/servingCerts/namedCertificates"}]'
```

If the path does not exist or JSON patch fails, edit carefully:

```bash
oc edit apiserver cluster
```

Then watch:

```bash
watch 'oc get co kube-apiserver authentication openshift-apiserver'
```

### 18.3 If API Access Is Broken

Use an already-authenticated admin shell or bastion if available.

If no API access is possible:

- Check whether the issue is only client trust. Try from a host with correct CA trust.
- Try the internal/admin kubeconfig if available and still valid.
- Avoid unsupported manual static pod changes.
- Follow Red Hat recovery documentation or open a support case.

## 19. Monitoring and Alerting

### 19.1 What to Monitor

Monitor:

- Certificate expiry date.
- Certificate issuer/chain changes.
- `kube-apiserver` ClusterOperator status.
- Authentication operator status.
- Failed API client TLS errors.
- cert-manager `Certificate` readiness if using cert-manager.
- Automation login failures after renewal.

### 19.2 Simple External Expiry Check

```bash
API_FQDN=api.ocp4.example.com

echo | openssl s_client \
  -connect ${API_FQDN}:6443 \
  -servername ${API_FQDN} 2>/dev/null \
  | openssl x509 -noout -enddate
```

Output:

```text
notAfter=Aug 15 12:00:00 2026 GMT
```

### 19.3 Prometheus Blackbox Style Check

For enterprise monitoring, a blackbox TLS probe can check:

- TCP connectivity to `:6443`.
- TLS handshake success.
- Certificate expiry threshold.
- Correct SAN.
- Correct issuer.

Alert examples:

```text
API certificate expires in < 30 days
API certificate expires in < 14 days
API certificate chain changed unexpectedly
API TLS probe failed
kube-apiserver ClusterOperator degraded
```

### 19.4 Operational Calendar

For manually managed certificates:

- Renew at least 30–45 days before expiry.
- For critical production clusters, start 60–90 days before expiry.
- Validate CA chain in non-prod first.
- Update client trust before switching root/intermediate CA.

## 20. Interview and Exam Notes

### 20.1 One-Line Answer

An OpenShift API certificate is the TLS serving certificate used by the Kubernetes API server on `api.<cluster>.<domain>:6443` to encrypt traffic and prove the API server identity to clients.

### 20.2 Key Objects to Remember

```bash
oc get apiserver cluster -o yaml
oc create secret tls <secret> --cert=<cert> --key=<key> -n openshift-config
oc patch apiserver cluster --type=merge -p '<json>'
oc get co kube-apiserver
```

### 20.3 Must-Remember Rules

- The custom API certificate secret must be in `openshift-config`.
- The secret must contain `tls.crt` and `tls.key`.
- The certificate must include SAN for the API FQDN.
- The certificate chain should be leaf first, then intermediate(s), then root if required.
- The key must be unencrypted.
- Do not configure a named certificate for `api-int.<cluster>.<base_domain>`.
- First-time named certificate addition triggers kube-apiserver rollout.
- Renewing an existing referenced secret can be hot-reloaded without a new revision.
- Changing the root CA can break clients that do not reload truststores.
- API certificate is not ingress certificate.

### 20.4 Common Exam-Style Task

**Task:** Configure a trusted certificate for the OpenShift API endpoint `api.ocp4.example.com`.

Expected workflow:

```bash
oc create secret tls api-cert \
  --cert=/home/admin/api-fullchain.crt \
  --key=/home/admin/api.key \
  -n openshift-config

oc patch apiserver cluster --type=merge -p '
{
  "spec": {
    "servingCerts": {
      "namedCertificates": [
        {
          "names": ["api.ocp4.example.com"],
          "servingCertificate": {
            "name": "api-cert"
          }
        }
      ]
    }
  }
}'

oc get co kube-apiserver
```

Verify:

```bash
openssl s_client -connect api.ocp4.example.com:6443 \
  -servername api.ocp4.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

## Final Practical Advice

For a 10-year experienced OpenShift administrator, API certificate handling is not just a certificate replacement task. It is a control-plane trust operation. Always think in five layers:

```text
DNS -> Load Balancer -> TLS Certificate -> Client Trust -> OpenShift Authentication/RBAC
```

Most failures happen because engineers fix only one layer and ignore the others.

Before any API certificate change, confirm DNS, SAN, chain, key match, secret namespace, `apiserver/cluster` config, kube-apiserver operator health, and client trust. After the change, validate using both `openssl` and real clients such as `oc`, CI/CD, GitOps, and monitoring systems.
