# Trusted CA Bundle in OpenShift

**Area:** Security and Certificates  
**Level:** Advanced OpenShift Administration / 10+ Years Experience  
**Format:** Single Markdown guide  
**Focus:** Cluster trust, custom PKI, proxy trust, image registry trust, service CA bundle injection, operational troubleshooting, and production hardening.

---

## 1. Executive Summary

A **Trusted CA bundle** in OpenShift is the collection of Certificate Authority certificates that OpenShift components, nodes, Operators, and selected workloads use to verify TLS certificates presented by remote services.

In simple words:

> A trusted CA bundle tells OpenShift: “Certificates signed by these CAs are trusted.”

This is critical in enterprise environments because OpenShift often communicates with services that use certificates signed by private or internal Certificate Authorities, such as:

- Corporate HTTPS proxy
- Internal image registry
- Internal Git server
- LDAP or IdP endpoint
- Internal artifact repository
- Private API gateway
- Internal monitoring endpoint
- Custom ingress wildcard certificate
- Admission webhook service
- Operator-managed service
- Disconnected mirror registry

Without the correct CA bundle, OpenShift may reject TLS connections with errors such as:

```text
x509: certificate signed by unknown authority
certificate verify failed
unable to get local issuer certificate
ImagePullBackOff
ErrImagePull
OAuth provider connection failure
operator degraded: unable to verify server certificate
```

A senior OpenShift administrator must understand that OpenShift has **multiple trust planes**, not just one certificate store. A common mistake is adding a CA in one place and expecting every component and workload to trust it automatically. In reality, trust depends on the consumer:

| Consumer | Correct trust mechanism |
|---|---|
| Cluster components making outbound HTTPS calls | `proxy/cluster.spec.trustedCA` |
| Pods that need OpenShift cluster-wide trusted CA bundle | ConfigMap label `config.openshift.io/inject-trusted-cabundle=true` |
| Pods that need OpenShift service serving CA | ConfigMap annotation `service.beta.openshift.io/inject-cabundle=true` |
| Image pulls from private registry | `image.config.openshift.io/cluster.spec.additionalTrustedCA` |
| Builds pulling from registry | Image additional trusted CA / build trusted CA path |
| Webhooks secured by service CA | Service CA injection into APIService / CRD / webhook configs |
| Nodes / CRI-O trust | Usually through MCO-controlled cluster trust or image registry trust |
| Application language runtimes | Sometimes need explicit trust store handling inside the container |

## 2. Why Trusted CA Bundle Matters

TLS provides confidentiality, integrity, and server identity verification. The trusted CA bundle is the root of identity verification. When OpenShift connects to an HTTPS endpoint, it does not only check encryption. It also checks whether the server certificate chains back to a trusted CA.

Example:

```text
OpenShift component ---> https://registry.example.com
                          presents server certificate
                          signed by Corp-Root-CA

OpenShift checks:
1. Is certificate currently valid?
2. Does hostname match certificate SAN/CN?
3. Is chain complete?
4. Is issuing CA trusted?
5. Is algorithm acceptable?
6. Is certificate usable for server authentication?
```

If `Corp-Root-CA` is not trusted by the component, the connection fails even if the network path, DNS, port, and credentials are correct.

### Real production impact

A missing trusted CA can break:

- Cluster installation behind enterprise proxy
- Cluster upgrades in disconnected environments
- Image pulls from mirror registries
- Operator installation from private catalogs
- OAuth login using LDAP/HTPasswd/OIDC/SAML endpoints
- GitOps controllers pulling repositories over HTTPS
- Tekton pipelines cloning source code
- Webhook admission calls
- Monitoring scrape over TLS
- Console access to custom secured routes
- Registry pull-through behavior
- Cluster version operator access to update payloads

## 3. Certificate Chain Refresher

A TLS certificate is normally validated through a chain:

```text
Server Certificate
  signed by Intermediate CA
    signed by Root CA
      trusted by client trust store
```

### Root CA

A Root CA is self-signed and must be explicitly trusted by the client. If a private enterprise Root CA signs internal certificates, OpenShift must be configured to trust that Root CA.

### Intermediate CA

Intermediate CAs are issued by the Root CA. They usually sign server certificates. Clients may need the intermediate certificate either from the server chain or from the trust bundle, depending on how the server is configured.

### Server certificate

The server certificate is presented by an endpoint such as:

```text
registry.example.com
ldap.example.com
git.example.com
api.internal.example.com
```

For server verification, the client checks hostname match against the Subject Alternative Name field. Modern TLS validation depends on SAN, not only Common Name.

### Important rule

Do not add random server certificates into the cluster-wide CA bundle unless you intentionally want to trust that exact issuing path. The proper object to trust is normally the **root CA** or **intermediate CA**, not a leaf server certificate.

## 4. Trusted CA Bundle vs Certificate vs Secret

These terms are often confused.

| Item | Purpose | Usually stored as |
|---|---|---|
| CA certificate | Public certificate used to verify other certificates | ConfigMap |
| Server certificate | Certificate presented by a server | Secret |
| Private key | Secret key paired with server certificate | Secret |
| CA bundle | One or more CA certificates | ConfigMap |
| Trust store | Local location where a client reads trusted CAs | File path or OS trust database |
| Serving cert | Certificate used by a service, router, API, webhook | Secret |

### CA bundle is public, private key is secret

A CA certificate is not secret. It can be stored in a ConfigMap.

A private key is secret. It must be stored in a Secret and protected with RBAC.

Correct pattern:

```yaml
# CA certificate bundle
kind: ConfigMap
metadata:
  name: custom-ca-bundle
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

```yaml
# TLS serving certificate and private key
kind: Secret
type: kubernetes.io/tls
metadata:
  name: app-tls
data:
  tls.crt: ...
  tls.key: ...
```

## 5. OpenShift Trust Planes

OpenShift uses several CA trust mechanisms. Understanding the separation is the key to advanced administration.

### 5.1 RHCOS system trust bundle

Each Red Hat CoreOS node has an operating system trust bundle inherited from RHEL/RHCOS. This contains well-known public CA certificates.

Typical location inside a RHEL/RHCOS-style system:

```text
/etc/pki/tls/certs/ca-bundle.crt
/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

This trust bundle is used by many host-level tools and libraries.

### 5.2 Cluster-wide proxy trusted CA

The `Proxy` object controls cluster-wide proxy settings and trusted CAs for cluster components that make outbound HTTPS calls.

Resource:

```text
proxy.config.openshift.io/cluster
```

Important field:

```yaml
spec:
  trustedCA:
    name: custom-ca-bundle
```

The referenced ConfigMap must exist in:

```text
openshift-config
```

The ConfigMap must contain:

```text
data.ca-bundle.crt
```

This trust bundle is merged with the base RHCOS trust bundle to produce a cluster-wide trusted bundle.

### 5.3 Trusted CA bundle injection for workloads and Operators

OpenShift can inject the merged trusted CA bundle into an empty ConfigMap when the ConfigMap has this label:

```yaml
metadata:
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
```

The injected ConfigMap gets a key:

```text
ca-bundle.crt
```

A pod can mount that ConfigMap and use it as a trust bundle.

### 5.4 Service CA bundle injection

OpenShift has a Service CA Operator that signs certificates for internal services. Pods and API extension objects can trust these service certificates by using this annotation:

```yaml
metadata:
  annotations:
    service.beta.openshift.io/inject-cabundle: "true"
```

For ConfigMaps, the injected key is:

```text
service-ca.crt
```

This is different from the cluster-wide trusted CA bundle.

### 5.5 Image registry additional trusted CA

Image pulls use a separate image registry trust mechanism:

```text
image.config.openshift.io/cluster
```

Important field:

```yaml
spec:
  additionalTrustedCA:
    name: registry-config
```

The ConfigMap must exist in:

```text
openshift-config
```

The key format is special:

```yaml
data:
  registry.example.com: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
  registry-with-port.example.com..5000: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

If the registry uses a port such as `registry.example.com:5000`, replace `:` with `..` in the ConfigMap key:

```text
registry.example.com..5000
```

### 5.6 Ingress custom certificate trust

When the default ingress certificate is replaced with a custom wildcard certificate, internal cluster components such as OAuth, console, and registry may need to trust the CA that signed that certificate. That is commonly handled through cluster proxy trusted CA configuration.

### 5.7 Application runtime trust

Even after OpenShift injects a CA bundle into a pod, the application must actually use that bundle. Some applications use the OS CA path; others use language-specific trust stores:

| Runtime | Trust consideration |
|---|---|
| RHEL/UBI curl, Python requests using system OpenSSL | Usually can use mounted OS bundle if path is correct |
| Java | Often needs Java `cacerts` or `javax.net.ssl.trustStore` |
| Node.js | May need `NODE_EXTRA_CA_CERTS` |
| Go | Usually uses system trust depending on build/base image |
| Distroless/scratch | May not include CA bundle by default |
| Alpine | Uses different CA path from RHEL/UBI |

Check current proxy/trusted CA settings:

```bash

```

```yaml

  name: cluster
```

## 7. Installation-Time Trusted CA: `additionalTrustBundle`

For a new cluster, you can add a custom CA during installation with `install-config.yaml`.

Example:

```yaml
apiVersion: v1
baseDomain: example.com
metadata:
  name: ocp4
additionalTrustBundle: |
  -----BEGIN CERTIFICATE-----
  MIID...
  -----END CERTIFICATE-----
```

This is used when the cluster must trust an internal CA from the beginning, for example:

- Installation through HTTPS proxy
- Pulling release images from a mirror registry
- Internal CA for disconnected installation
- Corporate TLS interception

The installer uses this certificate to create a `user-ca-bundle` ConfigMap in `openshift-config`.

### Senior admin note

If the cluster needs private PKI during bootstrap, configure it at installation time. Adding the CA after the cluster is installed may be too late if bootstrap or release image pulls already depend on that CA.

## 8. Adding a Custom CA to a Running Cluster

### 8.1 Prepare CA certificate

Assume your internal CA file is:

```text
corp-root-ca.crt
```

Verify it is PEM encoded:

```bash
openssl x509 -in corp-root-ca.crt -noout -subject -issuer -dates -fingerprint -sha256
```

Expected PEM format:

```text
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

### 8.2 Create ConfigMap in `openshift-config`

```bash
oc create configmap custom-ca-bundle \
  --from-file=ca-bundle.crt=corp-root-ca.crt \
  -n openshift-config
```

Or declarative YAML:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: custom-ca-bundle
  namespace: openshift-config
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

Apply:

```bash
oc apply -f custom-ca-bundle.yaml
```

### 8.3 Patch the cluster Proxy object

```bash
oc patch proxy/cluster --type=merge \
  --patch='{"spec":{"trustedCA":{"name":"custom-ca-bundle"}}}'
```

### 8.4 Watch cluster operators

Changing cluster-wide trust can trigger node updates and rolling reboots because the Machine Config Operator distributes trust-related changes to nodes.

Monitor:

```bash
oc get co
oc get mcp
oc get nodes
watch 'oc get mcp && oc get nodes'
```

Check MCO progress:

```bash
oc describe mcp master
oc describe mcp worker
oc get machineconfigpool -o wide
```

### 8.5 Verify generated trusted bundle

```bash
oc get configmap trusted-ca-bundle -n openshift-config -o yaml
```

Extract and inspect:

```bash
oc get cm trusted-ca-bundle -n openshift-config \
  -o jsonpath='{.data.ca-bundle\.crt}' > /tmp/cluster-ca-bundle.crt

grep -n "BEGIN CERTIFICATE" /tmp/cluster-ca-bundle.crt
openssl crl2pkcs7 -nocrl -certfile /tmp/cluster-ca-bundle.crt | \
  openssl pkcs7 -print_certs -noout | grep -E "subject=|issuer="
```

### 8.6 Verify on a node

```bash
NODE=$(oc get nodes -o name | head -1)
oc debug $NODE
chroot /host
trust list | grep -i "corp"
openssl verify -CAfile /etc/pki/tls/certs/ca-bundle.crt server.crt
exit
exit
```

### 8.7 Verify from a workload

Create injected ConfigMap:

```bash
oc create namespace ca-test
cat <<'EOF_CM' | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-trusted-ca
  namespace: ca-test
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
data: {}
EOF_CM
```

Check injection:

```bash
oc get cm app-trusted-ca -n ca-test -o yaml
```

Run test pod:

```bash
cat <<'EOF_POD' | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: ca-test
  namespace: ca-test
spec:
  restartPolicy: Never
  containers:
  - name: test
    image: registry.access.redhat.com/ubi9/ubi:latest
    command: ["/bin/bash", "-c", "sleep 3600"]
    volumeMounts:
    - name: trusted-ca
      mountPath: /etc/pki/ca-trust/extracted/pem
      readOnly: true
  volumes:
  - name: trusted-ca
    configMap:
      name: app-trusted-ca
      items:
      - key: ca-bundle.crt
        path: tls-ca-bundle.pem
EOF_POD
```

Test:

```bash
oc exec -n ca-test ca-test -- \
  curl -v https://internal-service.example.com
```

## 9. Trusted CA Injection for Applications

Cluster components may trust the CA after `proxy/cluster.spec.trustedCA`, but normal application pods do not automatically inherit every cluster trust change in a useful runtime path. For workloads, use trusted CA bundle injection.

### 9.1 Create injectable ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: trusted-ca
  namespace: app-prod
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
data: {}
```

Apply:

```bash
oc apply -f trusted-ca.yaml
```

OpenShift populates:

```text
ca-bundle.crt
```

### 9.2 Mount into a Deployment

For RHEL/UBI-based images, common mount target:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
  namespace: app-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app
  template:
    metadata:
      labels:
        app: app
    spec:
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi:latest
        command: ["/bin/bash", "-c", "sleep 3600"]
        volumeMounts:
        - name: trusted-ca
          mountPath: /etc/pki/ca-trust/extracted/pem
          readOnly: true
      volumes:
      - name: trusted-ca
        configMap:
          name: trusted-ca
          items:
          - key: ca-bundle.crt
            path: tls-ca-bundle.pem
```

### 9.3 Path expectations

Red Hat examples mount the injected `ca-bundle.crt` as:

```text
/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

This works well for RHEL/UBI-style containers that use the system OpenSSL trust path.

### 9.4 Java application example

Java often uses a separate trust store. Options:

#### Option A: Import CA into Java cacerts at image build time

```Dockerfile
FROM registry.access.redhat.com/ubi9/openjdk-17
COPY corp-root-ca.crt /tmp/corp-root-ca.crt
RUN keytool -importcert -noprompt \
    -alias corp-root-ca \
    -file /tmp/corp-root-ca.crt \
    -keystore $JAVA_HOME/lib/security/cacerts \
    -storepass changeit
```

#### Option B: Mount trust bundle and configure JVM

```yaml
env:
- name: JAVA_TOOL_OPTIONS
  value: "-Djavax.net.ssl.trustStore=/truststore/custom-truststore.jks -Djavax.net.ssl.trustStorePassword=changeit"
```

In production, build a truststore during image build or init container execution.

### 9.5 Node.js example

```yaml
env:
- name: NODE_EXTRA_CA_CERTS
  value: /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

### 9.6 Python requests example

```yaml
env:
- name: REQUESTS_CA_BUNDLE
  value: /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
- name: SSL_CERT_FILE
  value: /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

## 10. Service CA Bundle vs Trusted CA Bundle

This is a common interview and troubleshooting topic.

### 10.1 Trusted CA bundle

Label:

```text
config.openshift.io/inject-trusted-cabundle=true
```

Injected key:

```text
ca-bundle.crt
```

Owner/operator:

```text
Cluster Network Operator
```

Purpose:

```text
Trust external/custom CAs merged with cluster system trust.
```

Use cases:

- Pod needs to call internal corporate HTTPS endpoint
- Operator needs to trust custom external service
- Application needs cluster-wide custom CA bundle

### 10.2 Service CA bundle

Annotation:

```text
service.beta.openshift.io/inject-cabundle=true
```

Injected key:

```text
service-ca.crt
```

Owner/operator:

```text
OpenShift Service CA Operator
```

Purpose:

```text
Trust certificates generated by OpenShift service serving certificate signer.
```

Use cases:

- Pod calls another OpenShift Service using service serving cert
- APIService uses service-ca signed serving certificate
- ValidatingWebhookConfiguration trusts webhook service
- MutatingWebhookConfiguration trusts webhook service
- CRD conversion webhook trusts service-ca cert

### 10.3 Never mix both on the same ConfigMap

Do not use both of these on one ConfigMap:

```yaml
labels:
  config.openshift.io/inject-trusted-cabundle: "true"
annotations:
  service.beta.openshift.io/inject-cabundle: "true"
```

Reason:

- Trusted CA injection takes ownership of the ConfigMap data and uses `ca-bundle.crt`.
- Service CA injection takes ownership of the ConfigMap data and uses `service-ca.crt`.
- Both controllers may delete or replace data.
- Use two separate ConfigMaps.

Correct pattern:

```text
trusted-ca-bundle ConfigMap  -> label  -> ca-bundle.crt
service-ca-bundle ConfigMap  -> annotation -> service-ca.crt
```

## 11. Service Serving Certificates and Service CA

OpenShift can issue a serving certificate for a Service by annotation.

### 11.1 Request service serving certificate

```bash
oc annotate service my-api \
  service.beta.openshift.io/serving-cert-secret-name=my-api-tls \
  -n app-prod
```

OpenShift creates Secret:

```bash
oc get secret my-api-tls -n app-prod
```

Secret keys:

```text
tls.crt
tls.key
```

### 11.2 Mount service certificate into pod

```yaml
volumes:
- name: service-cert
  secret:
    secretName: my-api-tls
containers:
- name: app
  volumeMounts:
  - name: service-cert
    mountPath: /etc/tls/private
    readOnly: true
```

### 11.3 Client pod trusts the service CA

Create ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: service-ca
  namespace: app-prod
  annotations:
    service.beta.openshift.io/inject-cabundle: "true"
data: {}
```

Mount key:

```text
service-ca.crt
```

Then client can verify:

```bash
curl --cacert /var/run/configmaps/service-ca/service-ca.crt \
  https://my-api.app-prod.svc:8443/healthz
```

### 11.4 Webhook CA injection

For admission webhooks using service-ca signed certs:

```bash
oc annotate validatingwebhookconfiguration my-webhook \
  service.beta.openshift.io/inject-cabundle=true
```

For mutating webhook:

```bash
oc annotate mutatingwebhookconfiguration my-webhook \
  service.beta.openshift.io/inject-cabundle=true
```

For APIService:

```bash
oc annotate apiservice v1alpha1.example.com \
  service.beta.openshift.io/inject-cabundle=true
```

For CRD conversion webhook:

```bash
oc annotate crd widgets.example.com \
  service.beta.openshift.io/inject-cabundle=true
```

## 12. Image Registry Additional Trusted CA

A very common OpenShift production issue is image pull failure from a registry using an internal CA.

### 12.1 Symptoms

```text
Failed to pull image "registry.example.com/app:v1":
rpc error: code = Unknown desc = pinging container registry registry.example.com:
Get "https://registry.example.com/v2/": x509: certificate signed by unknown authority
```

Pod events:

```bash
oc describe pod <pod> -n <ns>
```

Node CRI-O logs:

```bash
oc debug node/<node>
chroot /host
journalctl -u crio --since "30 min ago"
```

### 12.2 Create registry CA ConfigMap

For registry without port:

```bash
oc create configmap registry-config \
  --from-file=registry.example.com=registry-ca.crt \
  -n openshift-config
```

For registry with port `registry.ocp4.example.com:8443`, the key must replace `:` with `..`:

```bash
oc create configmap registry-config \
  --from-file=registry.ocp4.example.com..8443=registry-ca.crt \
  -n openshift-config
```

YAML:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: registry-config
  namespace: openshift-config
data:
  registry.ocp4.example.com..8443: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

### 12.3 Configure image cluster resource

```bash
oc patch image.config.openshift.io/cluster --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-config"}}}'
```

Verify:

```bash
oc get image.config.openshift.io/cluster -o yaml
```

### 12.4 Watch MCO and nodes

```bash
oc get mcp
oc get nodes
oc describe mcp worker
```

### 12.5 Verify from node

```bash
oc debug node/<node-name>
chroot /host
ls -l /etc/containers/certs.d/
find /etc/containers/certs.d -maxdepth 2 -type f -print
podman login registry.ocp4.example.com:8443
podman pull registry.ocp4.example.com:8443/project/image:tag
```

### 12.6 Difference between registry CA and proxy trusted CA

| Problem | Fix |
|---|---|
| Cluster component cannot call HTTPS endpoint | `proxy/cluster.spec.trustedCA` |
| Pod cannot pull image from registry | `image.config.openshift.io/cluster.spec.additionalTrustedCA` |
| Application inside pod cannot call HTTPS endpoint | Inject trusted CA ConfigMap and configure app runtime |
| Webhook CA bundle missing | Service CA injection or custom webhook `caBundle` |

## 13. Trusted CA and Cluster-Wide Proxy

Enterprise clusters often run behind an HTTP/HTTPS proxy. Some proxies perform TLS interception and re-sign server certificates using a corporate CA.

### 13.1 Example proxy object

```yaml
apiVersion: config.openshift.io/v1
kind: Proxy
metadata:
  name: cluster
spec:
  httpProxy: http://proxy.corp.example.com:8080
  httpsProxy: http://proxy.corp.example.com:8080
  noProxy: .cluster.local,.svc,10.128.0.0/14,172.30.0.0/16
  trustedCA:
    name: custom-ca-bundle
```

### 13.2 Common proxy CA issues

| Symptom | Possible reason |
|---|---|
| Operators degraded | Proxy CA not trusted |
| ClusterVersion cannot retrieve updates | Proxy blocks or re-signs TLS |

## 14. Custom Ingress Certificate and Trust

When you replace the default ingress certificate with a custom wildcard certificate, clients outside the cluster must trust the public or corporate CA that signed the wildcard cert.

Example secret:

```bash
oc create secret tls apps-wildcard-tls \
  --cert=wildcard.apps.ocp4.example.com.crt \
  --key=wildcard.apps.ocp4.example.com.key \
  -n openshift-ingress
```

Patch IngressController:

```bash
oc patch ingresscontroller.operator default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"apps-wildcard-tls"}}}'
```

If internal cluster components must trust routes using that certificate, add the signing CA to the cluster trusted CA bundle through `proxy/cluster.spec.trustedCA`.

Verify route certificate:

```bash
openssl s_client -connect console-openshift-console.apps.ocp4.example.com:443 \
  -servername console-openshift-console.apps.ocp4.example.com \
  -showcerts </dev/null
```

Check certificate chain:

```bash
openssl verify -CAfile corp-root-ca.crt wildcard.apps.ocp4.example.com.crt
```

## 18. Troubleshooting Decision Tree

### 18.1 Error: `x509: certificate signed by unknown authority`

Ask first: who is the TLS client?

```text
Is the client a cluster operator/component?
  -> Configure proxy/cluster.spec.trustedCA

Is the client CRI-O pulling an image?
  -> Configure image.config.openshift.io/cluster.spec.additionalTrustedCA

Is the client an application inside a pod?
  -> Inject trusted CA ConfigMap and configure the application runtime

Is the client Kubernetes API server calling a webhook?
  -> Inject service CA into webhook config or set caBundle correctly

Is the client an external browser/user?
  -> Install CA in user/client trust store or use publicly trusted certificate
```

### 18.2 Error after adding CA: still failing

Check:

```bash
oc get proxy/cluster -o yaml
oc get cm custom-ca-bundle -n openshift-config -o yaml
oc get cm trusted-ca-bundle -n openshift-config -o yaml
oc get mcp
oc get co
```

Possible causes:

- Wrong ConfigMap namespace
- Wrong ConfigMap key; must be `ca-bundle.crt`
- CA certificate not PEM encoded
- Added leaf certificate instead of CA certificate
- Missing intermediate CA
- Server certificate SAN does not match hostname
- Application does not use mounted trust path
- Pod was not restarted after ConfigMap update
- MCO rollout not complete
- Registry key used `host:port` instead of `host..port`
- Proxy `noProxy` misconfigured
- Multiple CAs needed, but only one included

### 18.3 Error: ConfigMap data disappeared

If you add injection label or annotation, OpenShift controllers may delete existing data and own the ConfigMap.

Trusted CA injection:

```yaml
labels:
  config.openshift.io/inject-trusted-cabundle: "true"
```

Service CA injection:

```yaml
annotations:
  service.beta.openshift.io/inject-cabundle: "true"
```

Do not store application config in an injected CA ConfigMap.

### 18.4 Error: Pod cannot start because ConfigMap key missing

If the pod references a key before injection completes, startup may fail.

Example:

```text
configmap references non-existent config key: ca-bundle.crt
```

Fix options:

- Create injected ConfigMap first.
- Wait until key appears.
- Roll out workload after injection.
- Use `optional: true` only if application can handle missing trust bundle temporarily.

### 18.5 ImagePullBackOff from internal registry

Check events:

```bash
oc describe pod <pod> -n <ns>
```

Check image config:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get cm registry-config -n openshift-config -o yaml
```

Check port key:

```text
registry.example.com:5000     wrong as ConfigMap key
registry.example.com..5000    correct as ConfigMap key
```

Check node files:

```bash
oc debug node/<node>
chroot /host
find /etc/containers/certs.d -maxdepth 2 -type f -print
journalctl -u crio --since "30 min ago"
```

### 18.6 OAuth degraded after certificate change

Check:

```bash
oc get co authentication
oc describe co authentication
oc logs -n openshift-authentication deploy/oauth-openshift
oc get oauth cluster -o yaml
```

Common causes:

- LDAP CA missing
- OIDC issuer CA missing
- Ingress default certificate changed but CA not trusted by internal components
- OAuth pods need rollout
- Incorrect CA ConfigMap name in OAuth spec

## 19. Production Change Procedure

### 19.1 Before change

Collect current state:

```bash
mkdir -p ca-change-backup
oc get proxy/cluster -o yaml > ca-change-backup/proxy-cluster.yaml
oc get image.config.openshift.io/cluster -o yaml > ca-change-backup/image-cluster.yaml
oc get cm -n openshift-config > ca-change-backup/openshift-config-cm-list.txt
oc get co > ca-change-backup/co-before.txt
oc get mcp > ca-change-backup/mcp-before.txt
```

Validate CA:

```bash
openssl x509 -in new-ca.crt -noout -subject -issuer -dates -fingerprint -sha256
openssl x509 -in new-ca.crt -noout -text | grep -A2 "Basic Constraints"
```

A CA should normally show:

```text
CA:TRUE
```

### 19.2 Apply change

```bash
oc create configmap custom-ca-bundle \
  --from-file=ca-bundle.crt=new-ca.crt \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -

oc patch proxy/cluster --type=merge \
  --patch='{"spec":{"trustedCA":{"name":"custom-ca-bundle"}}}'
```

### 19.3 Monitor

```bash
watch 'oc get co; echo; oc get mcp; echo; oc get nodes'
```

### 19.4 Verify

```bash
oc get cm trusted-ca-bundle -n openshift-config \
  -o jsonpath='{.data.ca-bundle\.crt}' > /tmp/cluster-ca-bundle.crt

grep -c "BEGIN CERTIFICATE" /tmp/cluster-ca-bundle.crt
openssl crl2pkcs7 -nocrl -certfile /tmp/cluster-ca-bundle.crt | \
  openssl pkcs7 -print_certs -noout | grep -i "subject=.*corp"
```

### 19.5 Rollout dependent workloads

ConfigMap updates do not always cause applications to reload trust. Roll out workloads that mount the bundle:

```bash
oc rollout restart deployment/app -n app-prod
oc rollout status deployment/app -n app-prod
```

### 19.6 Backout

If the change breaks cluster components:

```bash
oc apply -f ca-change-backup/proxy-cluster.yaml
```

Or remove trusted CA reference:

```bash
oc patch proxy/cluster --type=json \
  -p='[{"op":"remove","path":"/spec/trustedCA"}]'
```

Monitor MCO and ClusterOperators.

## 20. Security Best Practices

### 20.1 Trust minimum required CA

Do not add an entire enterprise CA hierarchy if only one intermediate is needed. Trusting too broadly increases blast radius.

### 20.2 Prefer CA certificates, not server certificates

Trust the issuing CA, not the leaf certificate, unless a special pinned-trust design is intentionally used.

### 20.3 Validate Basic Constraints

```bash
openssl x509 -in ca.crt -noout -text | grep -A2 "Basic Constraints"
```

Expected:

```text
X509v3 Basic Constraints: critical
    CA:TRUE
```

### 20.4 Track expiration

```bash
openssl x509 -in ca.crt -noout -enddate
```

For all certificates in a bundle:

```bash
awk 'BEGIN {n=0} /BEGIN CERTIFICATE/ {n++} {print > "/tmp/ca-" n ".crt"}' bundle.crt
for f in /tmp/ca-*.crt; do
  echo "$f"
  openssl x509 -in "$f" -noout -subject -enddate
 done
```

### 20.5 Use GitOps for CA configuration

Manage these objects declaratively:

```text
openshift-config/custom-ca-bundle ConfigMap
proxy.config.openshift.io/cluster
image.config.openshift.io/cluster
namespace-level injected ConfigMaps
application volume mounts/env vars
```

### 20.6 Separate duties

- PKI team owns CA issuance and rotation.
- OpenShift platform team owns cluster trust configuration.
- Application team owns runtime trust usage.
- Security team approves trust scope.

### 20.7 Avoid insecure registries

Do not solve CA errors by making registries insecure unless it is temporary lab work. In production, fix CA trust.

Bad production workaround:

```yaml
spec:
  registrySources:
    insecureRegistries:
    - registry.example.com
```

Better:

```yaml
spec:
  additionalTrustedCA:
    name: registry-config
```

### 20.8 Document CA fingerprint

Record:

```text
Subject
Issuer
Serial
SHA256 fingerprint
Expiration
Owner
Purpose
Change ticket
Rollback plan
```

## 21. Rotation Strategy

CA rotation is high-impact because trust is foundational.

### 21.1 Safe rotation pattern

Use overlap:

```text
Phase 1: Trust old CA + new CA
Phase 2: Reissue server certificates with new CA
Phase 3: Verify all clients work
Phase 4: Remove old CA after all old certs expire or are replaced
```

### 21.2 Bundle with multiple CAs

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: custom-ca-bundle
  namespace: openshift-config
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    OLD_CA
    -----END CERTIFICATE-----
    -----BEGIN CERTIFICATE-----
    NEW_CA
    -----END CERTIFICATE-----
```

### 21.3 Rotation checklist

```text
[ ] Identify all endpoints using old CA
[ ] Add new CA to trusted bundle
[ ] Wait for MCO rollout
[ ] Restart workloads that mount CA
[ ] Reissue server certificates
[ ] Verify image pulls, OAuth, Operators, webhooks, apps
[ ] Monitor x509 errors
[ ] Remove old CA after safe window
[ ] Archive evidence
```

## 23. Common Mistakes

### Mistake 1: Adding registry CA to proxy trustedCA only

Symptom:

```text
Operators work, but image pulls fail.
```

Reason:

Image pull trust uses `image.config.openshift.io/cluster.spec.additionalTrustedCA`.

### Mistake 2: Adding CA to image config only

Symptom:

```text
Image pulls work, but operators or apps fail calling HTTPS endpoint.
```

Reason:

Registry trust does not automatically configure all cluster component or application trust.

### Mistake 3: Wrong ConfigMap key

For proxy trusted CA:

```text
ca-bundle.crt
```

For service CA injection:

```text
service-ca.crt
```

For registry additionalTrustedCA:

```text
registry hostname as key
host..port when port is used
```

### Mistake 4: Trusting a leaf cert

A leaf certificate can expire or rotate frequently. Trust the CA that signs it.

### Mistake 5: Forgetting application runtime trust

Mounting a bundle is not enough if the application does not read it.

### Mistake 6: Not planning for MCO reboot

Changing cluster-wide trust can trigger MCP updates and node reboots. Plan a maintenance window for production.

### Mistake 7: Putting application config in injected ConfigMap

Injected ConfigMaps are controller-owned. Data may be deleted.

### Mistake 8: Same ConfigMap for trusted CA and service CA

Use separate ConfigMaps.

### Mistake 9: Not including intermediate CA

Some servers do not send the complete chain. Include necessary intermediates or fix the server chain.

### Mistake 10: Hostname mismatch

CA trust does not fix SAN mismatch.

Example error:

```text
certificate is valid for registry.internal, not registry.example.com
```

Fix certificate SAN or use the correct hostname.

## 24. Interview-Level Questions and Answers

### Q1. What is a trusted CA bundle in OpenShift?

A trusted CA bundle is a collection of CA certificates used by OpenShift components, nodes, Operators, or workloads to verify TLS certificates. It allows OpenShift to trust certificates signed by private or enterprise CAs.

### Q2. Which object configures cluster-wide custom CA trust for OpenShift components?

`proxy.config.openshift.io/cluster`, specifically:

```yaml
spec:
  trustedCA:
    name: custom-ca-bundle
```

The referenced ConfigMap must be in `openshift-config` and must contain `ca-bundle.crt`.

### Q3. Does `proxy/cluster.spec.trustedCA` automatically fix image pull x509 errors?

Not always. Image registry trust is configured through:

```yaml
image.config.openshift.io/cluster:
  spec:
    additionalTrustedCA:
      name: registry-config
```

### Q4. What is the difference between `config.openshift.io/inject-trusted-cabundle` and `service.beta.openshift.io/inject-cabundle`?

`config.openshift.io/inject-trusted-cabundle=true` injects the cluster trusted CA bundle into a ConfigMap key named `ca-bundle.crt`.

`service.beta.openshift.io/inject-cabundle=true` injects the OpenShift service CA bundle into a ConfigMap key named `service-ca.crt`, or into API/webhook CA bundle fields.

### Q5. Why should you not use both injection markers on the same ConfigMap?

Both controllers own and replace ConfigMap data. Combining them can delete data or cause unpredictable results. Use separate ConfigMaps.

### Q6. What happens after patching `proxy/cluster.spec.trustedCA`?

OpenShift updates the cluster trust bundle. The Machine Config Operator may roll out changes to nodes, which can involve draining and rebooting nodes.

### Q7. What is the registry ConfigMap key for `registry.example.com:5000`?

```text
registry.example.com..5000
```

The colon is replaced with two dots.

### Q8. If a pod still gets x509 errors after CA injection, what do you check?

- ConfigMap injection completed
- Pod mounts correct key and path
- Application runtime uses that path
- Pod restarted after bundle update
- Server chain and SAN are correct
- Correct CA was added
- Intermediate CA is present

### Q9. What is the purpose of service CA?

The OpenShift service CA signs serving certificates for Services and injects the CA bundle into clients, APIService, CRD conversion webhooks, and admission webhook configurations so Kubernetes/OpenShift clients can verify service-serving certificates.

### Q10. How do you verify the cluster-wide trusted CA bundle?

```bash
oc get configmap trusted-ca-bundle -n openshift-config -o yaml
```

Inspect `data.ca-bundle.crt`.

## 26. Practical Troubleshooting Scenarios

### Scenario A: `oc import-image` fails with unknown authority

Likely cause:

```text
External registry CA not configured in image additionalTrustedCA.
```

Fix:

```bash
oc create configmap registry-config \
  --from-file=registry.example.com=registry-ca.crt \
  -n openshift-config

oc patch image.config.openshift.io/cluster --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-config"}}}'
```

### Scenario B: Console degraded after custom ingress cert

Likely cause:

```text
Cluster components do not trust the CA that signed the custom ingress certificate.
```

Fix:

```bash
oc create configmap ingress-ca \
  --from-file=ca-bundle.crt=ingress-signing-ca.crt \
  -n openshift-config

oc patch proxy/cluster --type=merge \
  -p '{"spec":{"trustedCA":{"name":"ingress-ca"}}}'
```

### Scenario C: App pod cannot call internal HTTPS API

Likely cause:

```text
App container does not trust internal corporate CA.
```

Fix:

1. Add CA to cluster trusted bundle if it should be shared cluster-wide.
2. Create injected ConfigMap in app namespace.
3. Mount it to correct trust path.
4. Configure application runtime if needed.
5. Restart deployment.

### Scenario D: Admission webhook timeout with certificate error

Likely cause:

```text
Webhook clientConfig.caBundle missing or incorrect.
```

Fix if service-ca signed:

```bash
oc annotate validatingwebhookconfiguration <name> \
  service.beta.openshift.io/inject-cabundle=true
```

If custom CA signed, set the correct `clientConfig.caBundle` manually or through the managing Operator.

```bash
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-config"}}}'

# Watch MCO
oc get mcp
oc describe mcp worker

# Check cluster operators
oc get co

# Debug node
oc debug node/<node>
chroot /host

# Test certificate chain
openssl s_client -connect <host>:443 -servername <host> -showcerts </dev/null

# Inspect certificate
openssl x509 -in ca.crt -noout -subject -issuer -dates -fingerprint -sha256

# Check CA:TRUE
openssl x509 -in ca.crt -noout -text | grep -A2 "Basic Constraints"
```

## 28. Senior Admin Mental Model

When you see a certificate error, do not immediately add the CA everywhere. Identify the exact TLS client.

```text
TLS client determines where trust must be configured.
```

Examples:

```text
CRI-O pulling image
  -> image.config.openshift.io additionalTrustedCA

Authentication operator calling LDAP/OIDC
  -> OAuth IdP CA config and/or cluster trustedCA depending on design

Console/auth/registry operator calling custom route
  -> proxy/cluster trustedCA

Application calling internal API
  -> Inject CA into pod and configure runtime

Kubernetes API server calling webhook
  -> webhook caBundle or service-ca injection

External browser calling route
  -> User machine/browser trust store
```

This mental model prevents over-trusting, avoids unnecessary cluster changes, and reduces downtime.

## 30. Final Key Points

- Trusted CA bundle is about **who OpenShift trusts** for TLS verification.
- Cluster-wide trust for OpenShift components is configured through `proxy/cluster.spec.trustedCA`.
- The ConfigMap for cluster-wide custom CA must be in `openshift-config` and use key `ca-bundle.crt`.
- The generated merged bundle can be checked with `oc get cm trusted-ca-bundle -n openshift-config -o yaml`.
- Workloads need explicit CA injection and runtime configuration.
- Service CA bundle is separate from cluster trusted CA bundle.
- Image registry trust is separate and configured through `image.config.openshift.io/cluster.spec.additionalTrustedCA`.
- For registry keys with ports, replace `:` with `..`.
- CA changes can trigger MCO rollout and node reboots.
- Never mix trusted CA injection and service CA injection in the same ConfigMap.
- Always identify the TLS client before choosing the trust mechanism.
