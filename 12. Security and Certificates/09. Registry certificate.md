# Registry Certificate in OpenShift Security and Certificates

**Audience:** Advanced OpenShift Administration / DO380-level administrator with real production experience  
**Focus:** Registry TLS certificates, registry trust, internal image registry route certificates, external/private registry CA bundles, disconnected registry certificates, troubleshooting, rotation, and production best practices  
**Platform context:** OpenShift Container Platform 4.x / Kubernetes / CRI-O / RHCOS

---

## 1. What is a Registry Certificate?

A **registry certificate** is the TLS certificate used when a client communicates with a container image registry over HTTPS.

In OpenShift, registry certificates matter whenever one of these components talks to an image registry:

- A **worker node** pulls an image for a Pod.
- A **control plane component** imports image metadata into an ImageStream.
- A **BuildConfig**, build Pod, Buildah, S2I, or pipeline pulls a builder/base image.
- A **user workstation** uses `podman`, `docker`, `skopeo`, `oc image`, or `oc adm release mirror`.
- The **OpenShift internal image registry** is exposed with a route and used from outside the cluster.
- A **disconnected/mirror registry** serves OpenShift release images, Operator catalogs, application images, or base images.

A registry certificate proves the identity of the registry endpoint and encrypts traffic between the client and registry.

Example registry endpoints:

```text
registry.redhat.io
quay.io
registry.ocp4.example.com:8443
mirror.example.com:5000
image-registry.openshift-image-registry.svc:5000
default-route-openshift-image-registry.apps.ocp4.example.com
```

When an image pull fails with an error like the following, the issue is often certificate trust:

```text
x509: certificate signed by unknown authority
```

or:

```text
certificate is valid for registry.example.com, not registry.example.com:5000
```

or:

```text
tls: failed to verify certificate
```

## 2. Registry Certificate vs Registry Credential

A senior administrator must separate **TLS trust** from **authentication**.

| Area | Purpose | OpenShift Object / Location | Common Error |
|---|---|---|---|
| Registry certificate | Proves registry identity and encrypts HTTPS | Registry server TLS certificate, CA bundle in `image.config.openshift.io/cluster` | `x509: certificate signed by unknown authority` |
| Registry credential | Authenticates user/service account to pull or push | Pull secret, global pull secret, project pull secret | `unauthorized: authentication required` |
| Registry authorization | Decides whether identity can pull/push image | Registry RBAC, OpenShift `system:image-puller`, repository permissions | `denied`, `forbidden`, `unauthorized` |
| Registry mirror config | Redirects pulls from source registry to mirror | `ImageDigestMirrorSet`, `ImageTagMirrorSet`, older `ImageContentSourcePolicy` | Pulling from wrong source or fallback failure |

Do not fix every registry issue by adding `--tls-verify=false`. That hides the real TLS problem and creates a security exception.

## 3. Registry TLS Flow in OpenShift

### 3.1 External registry image pull flow

When a Pod uses an image like:

```yaml
image: registry.example.com:5000/team/app:v1
```

OpenShift image pull flow is roughly:

```text
Pod scheduled
  -> kubelet on selected node requests image
  -> CRI-O uses containers/image libraries
  -> node connects to registry.example.com:5000 over HTTPS
  -> registry presents TLS certificate
  -> node validates certificate chain against trusted CA bundle
  -> node authenticates with pull secret if registry requires login
  -> image layers are pulled
  -> container starts
```

If the registry certificate is signed by a public CA already trusted by RHCOS, no extra OpenShift trust configuration is normally required.

If the registry uses a **private CA**, **self-signed certificate**, or **corporate TLS inspection CA**, OpenShift nodes must trust that CA.

### 3.2 Build flow

For OpenShift builds:

```text
BuildConfig / Build
  -> build pod starts
  -> pulls builder image or base image
  -> may push output image to internal or external registry
  -> registry TLS is validated
```

A build can fail even when normal application Pods are fine if:

- The builder image is imported from a private registry.
- The build strategy talks to a registry directly.
- The build output is pushed to a registry with an untrusted certificate.
- The service account lacks pull/push credentials.

### 3.3 ImageStream import flow

ImageStream import is handled by OpenShift components, not by your application Pod directly.

Example:

```bash
oc import-image app:latest \
  --from=registry.example.com:5000/team/app:latest \
  --confirm
```

If the registry CA is not trusted, import can fail with certificate verification errors.

### 3.4 Internal OpenShift registry flow

OpenShift has an internal integrated registry managed by the **Image Registry Operator**.

Internal service name:

```text
image-registry.openshift-image-registry.svc:5000
```

Common in-cluster pull format:

```text
image-registry.openshift-image-registry.svc:5000/<namespace>/<image>:<tag>
```

When the registry is accessed inside the cluster, OpenShift components and service accounts normally handle trust and authentication automatically.

External access requires exposing the registry through a route.

## 4. Main OpenShift Objects Related to Registry Certificates

### 4.1 `configs.imageregistry.operator.openshift.io/cluster`

This is the main configuration resource for the **OpenShift internal image registry**.

Check it:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Important fields:

```yaml
spec:
  managementState: Managed
  defaultRoute: true
  routes:
  - name: public-routes
    hostname: myregistry.example.com
    secretName: public-route-tls
```

This object controls:

- Whether the internal registry is managed, unmanaged, or removed.
- Registry storage backend.
- Registry route exposure.
- Custom route hostname and route TLS secret.
- Replica count and deployment settings.

Use this object when you want to expose the **OpenShift internal registry** with a default or custom route.

### 4.2 `image.config.openshift.io/cluster`

This is the cluster-wide image configuration resource.

Check it:

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Important field:

```yaml
spec:
  additionalTrustedCA:
    name: registry-cas
```

This tells OpenShift which ConfigMap contains extra CA certificates that must be trusted when the cluster accesses image registries.

Use this object when OpenShift must pull from or push to an **external registry** whose certificate is signed by a private CA.

### 4.3 Registry CA ConfigMap in `openshift-config`

The additional registry CA ConfigMap must be created in:

```text
openshift-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: registry-cas
  namespace: openshift-config
data:
  registry.example.com: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
  registry.example.com..5000: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

Important naming rule:

- For registry without port, key is the hostname:

```text
registry.example.com
```

- For registry with port, replace `:` with `..`:

```text
registry.example.com..5000
```

So this registry:

```text
registry.example.com:5000
```

must be represented in the ConfigMap as:

```yaml
registry.example.com..5000: |
```

This is one of the most common mistakes in exams and production.

### 4.4 Pull secret in `openshift-config`

The global pull secret lives here:

```text
namespace: openshift-config
secret: pull-secret
key: .dockerconfigjson
```

Check it:

```bash
oc get secret pull-secret -n openshift-config -o yaml
```

Use it for global registry credentials, not CA certificates.

### 4.5 Project-level pull secret

For a namespace-specific private registry credential:

```bash
oc create secret docker-registry my-regcred \
  --docker-server=registry.example.com:5000 \
  --docker-username=myuser \
  --docker-password='mypassword' \
  --docker-email=unused \
  -n myproject

oc secrets link default my-regcred --for=pull -n myproject
```

This solves authentication, not TLS trust.

### 4.6 `proxy.config.openshift.io/cluster` trusted CA

Cluster proxy trusted CA is different from registry-specific CA trust.

Proxy trust is used when platform components make egress HTTPS calls through a corporate proxy or TLS-inspecting proxy.

Example:

```yaml
spec:
  trustedCA:
    name: user-ca-bundle
```

Use proxy trusted CA when the proxy re-signs outbound TLS connections.

Use `image.config.openshift.io/cluster.spec.additionalTrustedCA` when the image registry itself uses a private CA.

In some corporate environments, you need both.

## 5. Types of Registry Certificate Scenarios

## 5.1 Public registry with public CA

Example:

```text
registry.redhat.io
quay.io
docker.io
```

Usually no additional CA is required because the CA is already trusted by the node OS trust store.

You still need authentication for registries like `registry.redhat.io`.

## 5.2 Private registry with internal corporate CA

Example:

```text
registry.corp.example.com:5000
```

The registry certificate is signed by an enterprise CA.

Required actions:

1. Get the **CA certificate**, not only the registry leaf certificate.
2. Create ConfigMap in `openshift-config`.
3. Patch `image.config.openshift.io/cluster`.
4. Add pull secret if authentication is required.
5. Test with Pod, ImageStream import, and node-level pull.

## 5.3 Private registry with self-signed certificate

A self-signed leaf certificate can work, but a better production design is:

```text
Root CA -> Intermediate CA -> Registry server certificate
```

For labs, self-signed may be acceptable.

For production, prefer a proper private PKI chain.

## 5.4 Disconnected mirror registry

Disconnected clusters commonly use a mirror registry like:

```text
registry.ocp4.example.com:8443
```

It stores:

- OpenShift release payload images.
- Operator catalog images.
- Operator bundle images.
- Red Hat base images.
- Application images.

Certificate trust must be correct before installation and after installation.

During installation, the registry CA is commonly added through `additionalTrustBundle` in `install-config.yaml`.

After installation, registry CA trust is commonly managed through `image.config.openshift.io/cluster.spec.additionalTrustedCA`.

## 5.5 Internal OpenShift registry exposed by default route

The internal registry is not exposed externally by default in modern OpenShift 4.

Expose it:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --patch '{"spec":{"defaultRoute":true}}' \
  --type=merge
```

Get route:

```bash
oc get route default-route -n openshift-image-registry
```

The default route normally uses the Ingress Controller certificate.

If your workstation does not trust the router certificate, `podman login` can fail with an x509 error.

## 5.6 Internal OpenShift registry exposed with custom corporate certificate

Use a custom route hostname and a TLS secret:

```bash
oc create secret tls public-route-tls \
  -n openshift-image-registry \
  --cert=/path/to/tls.crt \
  --key=/path/to/tls.key
```

Then configure:

```yaml
spec:
  routes:
  - name: public-routes
    hostname: registry.apps.ocp4.example.com
    secretName: public-route-tls
```

## 6. Certificate Requirements for Registry TLS

A correct registry server certificate should include:

### 6.1 Subject Alternative Name

Modern TLS validation uses SAN, not only CN.

Example SAN:

```text
DNS:registry.example.com
DNS:registry.ocp4.example.com
IP:10.10.10.50
```

For a registry endpoint:

```text
registry.example.com:5000
```

The certificate SAN should contain:

```text
DNS:registry.example.com
```

The port is not part of the certificate SAN.

### 6.2 Correct certificate chain

The registry should present:

```text
server certificate
intermediate certificate(s)
```

The client trust store should contain:

```text
root CA certificate
optional intermediate CA certificate if required
```

In many environments, putting the full CA chain in the OpenShift ConfigMap is safer:

```text
-----BEGIN CERTIFICATE-----
Intermediate CA
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
Root CA
-----END CERTIFICATE-----
```

Do not put the private key in a CA ConfigMap.

### 6.3 Key usage and extended key usage

The registry server certificate should be valid for server TLS.

Typical X.509 requirements:

```text
Key Usage: Digital Signature, Key Encipherment
Extended Key Usage: TLS Web Server Authentication
```

### 6.4 Valid date range

Check certificate expiry:

```bash
openssl x509 -in tls.crt -noout -dates
```

Example output:

```text
notBefore=Jul  1 00:00:00 2026 GMT
notAfter=Jul  1 23:59:59 2027 GMT
```

### 6.5 Hostname must match exactly

If OpenShift pulls from:

```text
registry.ocp4.example.com:8443
```

but the certificate is issued only for:

```text
mirror.ocp4.example.com
```

it fails.

Either update the certificate SAN or change the image references and mirror configuration to use the certified hostname.

## 7. Configure OpenShift to Trust an External Registry CA

Scenario:

```text
Registry URL: registry.ocp4.example.com:8443
CA file: /root/registry-ca.crt
```

### 7.1 Validate the certificate from your admin host

```bash
openssl s_client \
  -connect registry.ocp4.example.com:8443 \
  -servername registry.ocp4.example.com \
  -showcerts </dev/null
```

Useful checks:

```bash
openssl s_client \
  -connect registry.ocp4.example.com:8443 \
  -servername registry.ocp4.example.com \
  -CAfile /root/registry-ca.crt </dev/null
```

Successful validation should show:

```text
Verify return code: 0 (ok)
```

### 7.2 Create ConfigMap with registry CA

For registry with port `8443`, the ConfigMap key must use `..8443`.

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.ocp4.example.com..8443=/root/registry-ca.crt
```

Check:

```bash
oc get configmap registry-cas -n openshift-config -o yaml
```

Expected:

```yaml
data:
  registry.ocp4.example.com..8443: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

### 7.3 Patch image config

```bash
oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Verify:

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Expected:

```yaml
spec:
  additionalTrustedCA:
    name: registry-cas
```

### 7.4 Wait for cluster propagation

Check cluster operators:

```bash
oc get co
```

Check Machine Config Operator:

```bash
oc get co machine-config
oc get mcp
```

Check nodes:

```bash
oc get nodes
```

Depending on the OpenShift version and what changed, some image configuration changes can be applied without reboot, while other image/mirror changes can involve Machine Config Operator reconciliation. Always verify cluster operator and machine config pool state before testing critical workloads.

### 7.5 Test with an image pull

Create a temporary test namespace:

```bash
oc new-project registry-cert-test
```

If registry requires credentials:

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.ocp4.example.com:8443 \
  --docker-username=myuser \
  --docker-password='mypassword' \
  --docker-email=unused

oc secrets link default regcred --for=pull
```

Create test Pod:

```bash
oc run test-pull \
  --image=registry.ocp4.example.com:8443/myproject/myimage:latest \
  --restart=Never \
  --command -- sleep 3600
```

Check:

```bash
oc describe pod test-pull
oc get events --sort-by=.lastTimestamp
```

Common successful state:

```text
Successfully pulled image
Created container
Started container
```

Common certificate failure:

```text
x509: certificate signed by unknown authority
```

Common auth failure:

```text
unauthorized: authentication required
```

## 8. Configure Multiple Registry CAs

You can store multiple registry CA entries in one ConfigMap.

Example:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry1.example.com=/root/registry1-ca.crt \
  --from-file=registry2.example.com..5000=/root/registry2-ca.crt \
  --from-file=registry3.example.com..8443=/root/registry3-ca.crt
```

Patch once:

```bash
oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

If you need to add a new CA later:

```bash
oc create configmap registry-cas-new \
  -n openshift-config \
  --from-file=registry1.example.com=/root/registry1-ca.crt \
  --from-file=registry2.example.com..5000=/root/registry2-ca.crt \
  --from-file=registry3.example.com..8443=/root/registry3-ca.crt \
  --from-file=newregistry.example.com..9443=/root/newregistry-ca.crt \
  --dry-run=client -o yaml | oc apply -f -
```

The key point: do not accidentally replace the ConfigMap with only the new CA and remove existing registry CA entries.

## 9. Expose the OpenShift Internal Registry

### 9.1 Check registry operator status

```bash
oc get co image-registry
oc get pods -n openshift-image-registry
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

If `managementState` is `Removed`, the registry is not running.

Common on bare metal, vSphere, Nutanix, or other platforms where storage is not automatically configured:

```yaml
spec:
  managementState: Removed
```

You must configure storage and set it to `Managed` before using the internal registry.

### 9.2 Expose default route

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --patch '{"spec":{"defaultRoute":true}}' \
  --type=merge
```

Check route:

```bash
oc get route default-route -n openshift-image-registry
```

Get hostname:

```bash
HOST=$(oc get route default-route \
  -n openshift-image-registry \
  --template='{{ .spec.host }}')

echo $HOST
```

### 9.3 Trust the route certificate on admin workstation

Extract the router/default ingress certificate:

```bash
oc extract secret/$(oc get ingresscontroller default \
  -n openshift-ingress-operator \
  -o jsonpath='{.spec.defaultCertificate.name}') \
  -n openshift-ingress \
  --confirm
```

In many clusters, if no custom default cert is set, the default is:

```text
router-certs-default
```

Alternative:

```bash
oc extract secret/router-certs-default \
  -n openshift-ingress \
  --confirm
```

Trust it on RHEL/Fedora admin host:

```bash
sudo cp tls.crt /etc/pki/ca-trust/source/anchors/openshift-registry-route.crt
sudo update-ca-trust extract
```

Then login:

```bash
podman login -u $(oc whoami) -p $(oc whoami -t) $HOST
```

For quick lab-only validation:

```bash
podman login -u $(oc whoami) -p $(oc whoami -t) --tls-verify=false $HOST
```

Do not use `--tls-verify=false` as a permanent production approach.

### 9.4 Push an image to internal registry

Example:

```bash
oc new-project demo-registry

podman pull registry.access.redhat.com/ubi9/ubi-minimal:latest
podman tag registry.access.redhat.com/ubi9/ubi-minimal:latest \
  $HOST/demo-registry/ubi-minimal:latest

podman push $HOST/demo-registry/ubi-minimal:latest
```

Verify ImageStream:

```bash
oc get is -n demo-registry
oc describe is ubi-minimal -n demo-registry
```

## 10. Expose Internal Registry with a Custom Certificate

Production often requires a corporate DNS name:

```text
registry.apps.ocp4.example.com
```

### 10.1 Certificate SAN requirement

Certificate should include:

```text
DNS:registry.apps.ocp4.example.com
```

### 10.2 Create TLS secret

```bash
oc create secret tls public-route-tls \
  -n openshift-image-registry \
  --cert=/root/registry-route.crt \
  --key=/root/registry-route.key
```

### 10.3 Configure registry route

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type=merge \
  -p '{
    "spec": {
      "routes": [
        {
          "name": "public-routes",
          "hostname": "registry.apps.ocp4.example.com",
          "secretName": "public-route-tls"
        }
      ]
    }
  }'
```

Check:

```bash
oc get route -n openshift-image-registry
oc describe route public-routes -n openshift-image-registry
```

Login:

```bash
podman login -u $(oc whoami) -p $(oc whoami -t) registry.apps.ocp4.example.com
```

### 10.4 Important route behavior

If you do not specify `secretName`, the registry route uses the default Ingress Controller certificate.

If you specify `secretName`, the secret must exist in:

```text
openshift-image-registry
```

not in:

```text
openshift-ingress
openshift-config
default
```

## 11. Registry CA During Disconnected Installation

In disconnected OpenShift, registry certificate trust is critical before the cluster even exists.

Typical mirror registry:

```text
registry.ocp4.example.com:8443
```

Typical install-config snippet:

```yaml
additionalTrustBundle: |
  -----BEGIN CERTIFICATE-----
  <REGISTRY_CA_CERT>
  -----END CERTIFICATE-----
imageContentSources:
- mirrors:
  - registry.ocp4.example.com:8443/ocp4/openshift4
  source: quay.io/openshift-release-dev/ocp-release
- mirrors:
  - registry.ocp4.example.com:8443/ocp4/openshift4
  source: quay.io/openshift-release-dev/ocp-v4.0-art-dev
```

Modern disconnected environments may use `ImageDigestMirrorSet` or `ImageTagMirrorSet` after installation.

Post-install, confirm:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get imageDigestMirrorSet
oc get imageTagMirrorSet
oc get mcp
```

If the mirror registry certificate expires after installation, cluster upgrades, Operator installs, and node image pulls can fail.

## 12. Registry Certificate and Machine Config Operator

The Machine Config Operator can distribute node-level configuration for image registry trust and mirror settings.

Things to monitor after registry CA or mirror configuration changes:

```bash
oc get mcp
oc describe mcp worker
oc describe mcp master
oc get nodes
oc get co machine-config
```

Important signs:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
```

If MCO is degraded, image pulls may behave differently across nodes.

Check per-node debug:

```bash
oc debug node/<node-name>
chroot /host
```

Inside debug shell, inspect container registry trust paths if needed:

```bash
ls -l /etc/containers/certs.d/
ls -l /etc/pki/ca-trust/source/anchors/
cat /etc/containers/registries.conf
```

Exact file placement can vary by OpenShift release and MachineConfig rendering, so prefer supported OpenShift APIs over manually editing node files.

Do not manually copy registry CA files to nodes as a permanent fix. Manual changes will drift and can be overwritten.

## 13. Registry Certificate Troubleshooting Methodology

A 10-year administrator should troubleshoot in layers.

## 13.1 Identify the failing component

Ask: who is failing?

| Failure Location | Command | Likely Area |
|---|---|---|
| Pod image pull | `oc describe pod`, events | node trust, pull secret, registry auth |
| Build | `oc logs build/<build-name>` | build pull/push trust, build SA secret |
| ImageStream import | `oc import-image`, `oc describe is` | image config trust, registry availability |
| Podman from laptop | `podman login/pull` | workstation trust, route cert |
| Cluster upgrade | `oc adm upgrade`, CVO logs | release mirror trust, global pull secret |
| Operator install | CatalogSource Pod logs | mirror/catalog registry trust/auth |

## 13.2 Read the exact error

### Certificate trust error

```text
x509: certificate signed by unknown authority
```

Meaning:

- Registry certificate chain is not trusted.
- CA missing from OpenShift registry trust ConfigMap.
- Wrong ConfigMap key format.
- Registry is presenting incomplete chain.
- Corporate TLS proxy CA missing.

### Hostname mismatch

```text
x509: certificate is valid for mirror.example.com, not registry.example.com
```

Meaning:

- SAN does not match the registry hostname used by image reference.
- DNS alias not included in cert.
- Pull is going to unexpected mirror/source.

### Expired certificate

```text
x509: certificate has expired or is not yet valid
```

Meaning:

- Certificate expired.
- Node time is wrong.
- New certificate not installed on registry.
- OpenShift still trusts old CA chain but registry changed to a new CA.

### Authentication failure

```text
unauthorized: authentication required
```

Meaning:

- TLS succeeded; auth failed.
- Pull secret missing or wrong.
- Service account not linked to pull secret.
- Global pull secret missing mirror registry credentials.

### Authorization failure

```text
denied: requested access to the resource is denied
```

Meaning:

- Auth succeeded, but identity does not have permission.
- For internal registry across namespaces, bind `system:image-puller`.

### Registry unavailable

```text
dial tcp: lookup registry.example.com: no such host
connect: connection refused
i/o timeout
```

Meaning:

- DNS, routing, firewall, proxy, or registry service issue.
- Not primarily certificate trust.

## 14. Practical Troubleshooting Commands

### 14.1 Check image config

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Expected:

```yaml
spec:
  additionalTrustedCA:
    name: registry-cas
```

### 14.2 Check CA ConfigMap

```bash
oc get cm registry-cas -n openshift-config -o yaml
```

Verify key format:

```text
registry.example.com
registry.example.com..5000
registry.ocp4.example.com..8443
```

Wrong:

```text
registry.example.com:5000
```

Correct:

```text
registry.example.com..5000
```

### 14.3 Check MachineConfigPool

```bash
oc get mcp
oc describe mcp worker
```

### 14.4 Check node-level image pull

```bash
oc debug node/<worker-node>
chroot /host
crictl pull registry.example.com:5000/team/app:latest
```

If `crictl` is not available or not appropriate in your environment, test through a Pod and inspect kubelet/CRI-O logs.

```bash
oc adm node-logs <node-name> -u crio
```

```bash
journalctl -u crio -b
```

```bash
oc adm node-logs <node-name> -u kubelet
```

or:

```bash
journalctl -u kubelet -b
```

### 14.10 Verify CA file locally

```bash
echo | openssl s_client \
  -connect registry.example.com:5000 \
  -servername registry.example.com \
  -CAfile registry-ca.crt
```

Look for:

```text
Verify return code: 0 (ok)
```

## 15. Certificate Rotation for External Registry CA

Certificate rotation must be planned. Do not wait until the day of expiry.

## 15.1 Rotation patterns

### Same CA, new registry server certificate

If registry certificate is renewed under the same CA, OpenShift trust usually does not need to change.

Actions:

1. Install new server certificate on registry.
2. Restart/reload registry service.
3. Verify with `openssl s_client`.
4. Test image pulls.

### New intermediate CA

If the registry starts using a new intermediate CA:

1. Add new intermediate/root CA to OpenShift registry CA ConfigMap.
2. Keep old CA during transition.
3. Patch/apply ConfigMap.
4. Wait for propagation.
5. Rotate registry server certificate.
6. Remove old CA only after all clients no longer need it.

### New root CA

If root CA changes:

1. Add both old and new roots to CA bundle.
2. Wait for OpenShift propagation.
3. Rotate registry certificate.
4. Verify all workloads.
5. Remove old root after safe period.

## 15.2 Safe update example

Export existing ConfigMap:

```bash
oc get cm registry-cas -n openshift-config -o yaml > registry-cas-backup.yaml
```

Create updated ConfigMap manifest with both old and new CA:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: registry-cas
  namespace: openshift-config
data:
  registry.example.com..5000: |
    -----BEGIN CERTIFICATE-----
    OLD_OR_EXISTING_CA
    -----END CERTIFICATE-----
    -----BEGIN CERTIFICATE-----
    NEW_CA
    -----END CERTIFICATE-----
```

Apply:

```bash
oc apply -f registry-cas-updated.yaml
```

Monitor:

```bash
oc get co
oc get mcp
```

Test:

```bash
oc delete pod test-pull --ignore-not-found
oc run test-pull \
  --image=registry.example.com:5000/team/app:latest \
  --restart=Never --command -- sleep 3600
```

## 16. Registry Certificate and Image Mirroring

In disconnected or controlled environments, image mirror configuration and certificate trust must align.

Example `ImageDigestMirrorSet`:

```yaml
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: redhat-release-mirror
spec:
  imageDigestMirrors:
  - source: quay.io/openshift-release-dev/ocp-release
    mirrors:
    - registry.ocp4.example.com:8443/ocp4/openshift4
    mirrorSourcePolicy: NeverContactSource
```

If the mirror is:

```text
registry.ocp4.example.com:8443
```

then the CA ConfigMap key must be:

```yaml
registry.ocp4.example.com..8443: |
```

If you configure mirrors but forget registry CA trust, the cluster knows where to pull from but does not trust the HTTPS endpoint.

If you configure CA trust but forget mirror policy, the cluster trusts the mirror but may still pull from public registries.

If you configure both but forget global pull secret credentials, TLS succeeds but authentication fails.

## 17. Registry Certificate vs Ingress Certificate

The internal registry route is a Route served by the OpenShift Ingress Controller.

That means registry external TLS can come from:

1. The default Ingress wildcard certificate.
2. A custom route-specific certificate configured through the Image Registry Operator route settings.

Default ingress wildcard certificate example:

```text
*.apps.ocp4.example.com
```

Internal registry route example:

```text
default-route-openshift-image-registry.apps.ocp4.example.com
```

If the default wildcard covers the route hostname, the route can use that certificate.

If you want a cleaner registry hostname:

```text
registry.ocp4.example.com
```

then use a custom route and custom certificate.

## 18. Registry Certificate vs Service CA Certificate

OpenShift has a Service CA Operator that can issue serving certificates for Kubernetes Services.

This is different from registry route certificate trust.

Service CA use case:

```yaml
metadata:
  annotations:
    service.beta.openshift.io/serving-cert-secret-name: my-service-cert
```

This is usually for in-cluster service-to-service TLS.

The internal image registry has its own managed behavior. Do not confuse:

- service serving certificates,
- ingress/router certificates,
- external registry CA bundles,
- API server certificates,
- OAuth certificates,
- proxy trusted CA bundles.

## 19. Registry Certificate and RBAC for Internal Registry

When pulling images from the internal registry across projects, TLS might be fine but authorization can fail.

Example:

```text
project-a wants to pull image from project-b
```

Grant pull permission:

```bash
oc policy add-role-to-user \
  system:image-puller \
  system:serviceaccount:project-a:default \
  -n project-b
```

For all service accounts in project-a:

```bash
oc policy add-role-to-group \
  system:image-puller \
  system:serviceaccounts:project-a \
  -n project-b
```

This solves authorization, not certificate trust.

## 20. Common Real-World Issues and Fixes

## 20.1 Wrong ConfigMap key for port-based registry

Problem:

```yaml
data:
  registry.example.com:5000: |
```

This is wrong.

Fix:

```yaml
data:
  registry.example.com..5000: |
```

## 20.2 Added leaf certificate instead of CA

Problem:

The ConfigMap contains the server certificate only.

Fix:

Use the CA certificate that signed the registry certificate. Include intermediate CA if needed.

## 20.3 Certificate SAN mismatch

Problem:

Image uses:

```text
registry.example.com:5000
```

Certificate SAN contains:

```text
DNS:mirror.example.com
```

Fix options:

- Reissue certificate with `DNS:registry.example.com`.
- Change image references/mirror config to use `mirror.example.com`.

## 20.4 DNS points to load balancer but certificate points to backend

Problem:

Client connects to:

```text
registry.company.com
```

but registry presents certificate for:

```text
registry-node01.company.com
```

Fix:

Install load balancer hostname certificate on TLS termination point, or configure passthrough correctly.

## 20.5 Internal registry route login fails from laptop

Problem:

```text
x509: certificate signed by unknown authority
```

Fix:

Trust the route certificate on the laptop/admin host, or use a publicly/corporately trusted ingress certificate.

## 20.6 Pod fails but `podman pull` works on admin host

Problem:

Admin host trusts the CA, but OpenShift nodes do not.

Fix:

Add CA through OpenShift `image.config.openshift.io/cluster.spec.additionalTrustedCA`.

## 20.7 `podman pull` works on one node but not another

Possible causes:

- MachineConfigPool not fully updated.
- Node not rebooted/reconciled if required.
- Manual CA changes on one node only.
- Node has stale CRI-O state.

Check:

```bash
oc get mcp
oc get nodes
oc describe node <node>
oc adm node-logs <node> -u crio
```

## 20.8 Build fails but deployment works

Possible causes:

- Build uses different source/builder image.
- Build service account lacks pull secret.
- Build output registry certificate untrusted.
- Build strategy directly contacts registry.

Check:

```bash
oc logs build/<build-name>
oc describe build/<build-name>
oc get sa builder -o yaml
```

## 20.9 ImageStream import fails with certificate error

Check:

```bash
oc import-image test:latest \
  --from=registry.example.com:5000/team/app:latest \
  --confirm

oc describe is test
```

Fix registry CA trust through image config.

## 20.10 Using `--insecure` permanently

Temporary lab command:

```bash
oc import-image app:latest \
  --from=registry.example.com:5000/team/app:latest \
  --confirm \
  --insecure
```

Production fix:

- Correct TLS certificate.
- Correct CA ConfigMap.
- Correct registry hostname.

## 21. Security Best Practices

### 21.1 Do not disable TLS verification in production

Avoid permanent use of:

```text
--tls-verify=false
--insecure
insecureRegistries
```

These allow man-in-the-middle attacks and image substitution.

### 21.2 Use private enterprise CA correctly

Recommended chain:

```text
Enterprise Root CA
  -> Enterprise Intermediate CA
    -> Registry server certificate
```

OpenShift trust should usually include the root and any required intermediate CA certificates.

### 21.3 Use short-lived server certificates and planned rotation

Registry server certificate validity of 1 year is common.

CA validity is longer, but CA expiry must still be tracked.

### 21.4 Monitor certificate expiry

Use monitoring or scheduled checks:

```bash
echo | openssl s_client -connect registry.example.com:5000 -servername registry.example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

### 21.5 Use image signatures and digest pinning for high-security environments

TLS protects the connection, but it does not prove image provenance by itself.

For stronger supply-chain security, combine registry TLS with:

- Image digest references.
- Signature verification.
- Admission policy.
- Red Hat Advanced Cluster Security or equivalent controls.
- Trusted build pipelines.
- SBOM and vulnerability scanning.

### 21.6 Limit global pull secret exposure

Global pull secret applies cluster-wide.

For application-only registries, project-level pull secrets are safer.

For mirrored release/Operator content, global pull secret may be required.

### 21.7 Keep registry DNS stable

Avoid changing registry hostnames frequently. Certificates, mirror policies, pull secrets, and image references are hostname-sensitive.

## 22. Exam-Oriented Notes for Advanced OpenShift Administration

For exam or real troubleshooting, remember this mental map:

```text
External registry CA trust
  -> ConfigMap in openshift-config
  -> image.config.openshift.io/cluster.spec.additionalTrustedCA

Internal registry external route TLS
  -> configs.imageregistry.operator.openshift.io/cluster
  -> spec.defaultRoute or spec.routes
  -> TLS secret in openshift-image-registry if custom route cert

Registry authentication
  -> pull-secret in openshift-config for global
  -> docker-registry secret + oc secrets link for namespace

Internal registry cross-project pull
  -> system:image-puller RBAC

Corporate proxy CA
  -> proxy.config.openshift.io/cluster.spec.trustedCA
```

The most likely mistakes:

1. Using `registry.example.com:5000` instead of `registry.example.com..5000` as ConfigMap key.
2. Adding credentials but forgetting certificate trust.
3. Adding certificate trust but forgetting credentials.
4. Trusting the CA on the admin workstation but not in OpenShift.
5. Exposing internal registry but not trusting the router certificate on the client.
6. Using the wrong namespace for TLS secret.
7. Confusing Ingress certificate, API certificate, Service CA, proxy CA, and registry CA.
8. Forgetting that ImageStream imports and build pulls can fail separately from runtime Pod pulls.

## 23. Complete Production Workflow: External Private Registry

Scenario:

```text
Registry: registry.corp.example.com:5000
CA file: corp-registry-ca.crt
Registry user: ocp-puller
Namespace: payments
Image: registry.corp.example.com:5000/payments/api:v2
```

### Step 1: Verify registry TLS externally

```bash
openssl s_client \
  -connect registry.corp.example.com:5000 \
  -servername registry.corp.example.com \
  -CAfile corp-registry-ca.crt </dev/null
```

Expected:

```text
Verify return code: 0 (ok)
```

### Step 2: Add CA to OpenShift

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.corp.example.com..5000=corp-registry-ca.crt \
  --dry-run=client -o yaml | oc apply -f -
```

### Step 3: Patch image config

```bash
oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

### Step 4: Monitor propagation

```bash
oc get co
oc get mcp
```

### Step 5: Create namespace pull secret

```bash
oc new-project payments

oc create secret docker-registry corp-regcred \
  --docker-server=registry.corp.example.com:5000 \
  --docker-username=ocp-puller \
  --docker-password='REDACTED' \
  --docker-email=unused \
  -n payments

oc secrets link default corp-regcred --for=pull -n payments
```

### Step 6: Test Pod pull

```bash
oc run api-test \
  -n payments \
  --image=registry.corp.example.com:5000/payments/api:v2 \
  --restart=Never \
  --command -- sleep 3600

oc describe pod api-test -n payments
```

### Step 7: Deploy application

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: payments
spec:
  replicas: 2
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      containers:
      - name: api
        image: registry.corp.example.com:5000/payments/api:v2
        ports:
        - containerPort: 8080
```

## 25. Decision Tree

Use this quick decision tree during incidents.

```text
Image pull failed?
|
+-- Error says x509 / certificate / unknown authority?
|   |
|   +-- External registry?
|   |   -> Check registry cert SAN and chain
|   |   -> Add CA in openshift-config ConfigMap
|   |   -> Patch image.config.openshift.io/cluster
|   |
|   +-- Internal registry route from laptop?
|       -> Trust router/custom route CA on laptop
|       -> Or configure trusted route certificate
|
+-- Error says unauthorized/authentication required?
|   -> Fix pull secret / global pull secret / service account link
|
+-- Error says denied/forbidden?
|   -> Fix registry-side authorization or system:image-puller RBAC
|
+-- Error says DNS/timeout/connection refused?
    -> Fix DNS, network, firewall, proxy, route, service, registry availability
```

## 27. Interview-Level Explanation

A registry certificate in OpenShift is not just the certificate installed on a registry server. It is part of a complete image trust path. When a Pod, build, ImageStream import, Operator catalog, or cluster upgrade pulls an image, the node or OpenShift component must validate the registry TLS certificate chain. If the registry is signed by a private CA, that CA must be distributed to the cluster using the supported image configuration API, normally a ConfigMap in `openshift-config` referenced by `image.config.openshift.io/cluster.spec.additionalTrustedCA`. For the internal OpenShift registry, certificates are usually handled by the Ingress route when the registry is exposed externally. A default route uses the default ingress certificate, while a custom route can use a TLS secret in `openshift-image-registry`. Registry certificate trust must be handled separately from pull secrets and RBAC. TLS trust answers “am I talking securely to the real registry?”, while pull secrets answer “who am I?”, and RBAC or registry permissions answer “am I allowed to pull or push this image?”

## 28. Production Checklist

Before calling registry certificate configuration complete, verify:

- [ ] Registry DNS name matches certificate SAN.
- [ ] Registry presents full certificate chain.
- [ ] CA certificate is PEM encoded.
- [ ] ConfigMap exists in `openshift-config`.
- [ ] ConfigMap key uses `hostname` or `hostname..port` format.
- [ ] `image.config.openshift.io/cluster.spec.additionalTrustedCA` references correct ConfigMap.
- [ ] MachineConfigPools and ClusterOperators are healthy.
- [ ] Pull secret exists where needed.
- [ ] Service account is linked to pull secret where needed.
- [ ] Internal registry cross-project access uses `system:image-puller` where needed.
- [ ] Internal registry custom route TLS secret is in `openshift-image-registry`.
- [ ] External admin hosts trust route CA if using `podman login` externally.
- [ ] Certificate expiry is monitored.
- [ ] CA rotation process is documented.
- [ ] No permanent `--tls-verify=false` workaround remains.
