## 1. Executive Summary

In OpenShift, **Secret management** is the discipline of securely creating, storing, distributing, rotating, auditing, and deleting sensitive values used by workloads and cluster components. These values include passwords, API tokens, TLS private keys, registry credentials, SSH keys, OAuth client secrets, database credentials, webhook certificates, and service account credentials.

A senior OpenShift administrator must understand that a Kubernetes/OpenShift `Secret` is **not automatically safe just because it is named Secret**. It is a Kubernetes API object. Its values are base64-encoded in manifests, persisted in etcd, exposed through the API to authorized users/controllers, delivered to nodes by kubelet, and mounted or injected into containers. Security comes from a combination of:

- Correct RBAC.
- Namespace isolation.
- Least-privilege service accounts.
- Etcd encryption at rest.
- Secure workload design.
- External secret stores where required.
- Rotation automation.
- Audit logging.
- GitOps-safe workflows.
- Avoiding secret leakage in images, logs, events, shell history, CI/CD output, and support bundles.

In production OpenShift, Secret management is not only an application concern. It affects:

- Cluster installation pull secret.
- Internal and external registry authentication.
- Route TLS termination.
- Service serving certificates.
- Operators.
- BuildConfigs.
- ImageStreams.
- OAuth identity providers.
- Webhook configurations.
- Cloud provider credentials.
- Service account tokens.
- Application runtime configuration.

A good OpenShift admin treats Secrets as **high-value security assets**, not as simple configuration files.

## 2. What a Secret Is in OpenShift

A Secret is a namespaced Kubernetes API resource used to store sensitive data. In OpenShift, the same Kubernetes Secret model is used, with additional OpenShift integrations around service accounts, internal registry authentication, build secrets, routes, operators, and service serving certificates.

Basic structure:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-db-secret
  namespace: prod
  labels:
    app.kubernetes.io/name: payments
    security.example.com/classification: confidential
type: Opaque
stringData:
  username: payments_user
  password: change-me-in-real-life
```

After admission, `stringData` is converted into base64-encoded entries under `data`:

```yaml
data:
  username: cGF5bWVudHNfdXNlcg==
  password: Y2hhbmdlLW1lLWluLXJlYWwtbGlmZQ==
```

### Key concept: base64 is not encryption

Base64 encoding only converts binary/text into a transport-safe representation. Anyone who can read the Secret object can decode it:

```bash
oc get secret app-db-secret -n prod -o jsonpath='{.data.password}' | base64 -d; echo
```

Therefore, the protection boundary is **API authorization and storage encryption**, not base64.

### Secret vs ConfigMap

| Feature | Secret | ConfigMap |
|---|---|---|
| Intended use | Sensitive data | Non-sensitive configuration |
| Base64 `data` | Yes | Usually plain text |
| Access should be restricted | Strongly yes | Usually less strict |
| Etcd encryption target | Yes, when etcd encryption enabled | Also encrypted in OpenShift when etcd encryption enabled |
| Example | DB password, TLS key | App mode, log level, feature flag |

Do not store passwords in ConfigMaps. Do not store non-sensitive tuning flags in Secrets just to hide poor design.

## 3. Secret Threat Model

A 10-year-experienced administrator thinks in terms of attack paths, not just YAML syntax.

### Main attack paths

1. **API read access**
   - A user, group, service account, or controller has `get`, `list`, or `watch` access to Secrets.
   - `list` and `watch` are especially dangerous because they expose all Secrets in a namespace.

2. **Indirect pod creation access**
   - A user who can create Pods, Deployments, Jobs, or CronJobs in a namespace might be able to mount or reference Secrets in that namespace.
   - This means `create pods` can become indirect Secret-read capability.

3. **Compromised service account**
   - Workload token is stolen.
   - Token has excessive permissions.
   - Attacker reads Secrets through API or deploys a pod to mount Secrets.

4. **Node compromise**
   - Kubelet receives Secret material for pods scheduled on that node.
   - A privileged host-level compromise can expose mounted Secret volumes and container environment variables.

5. **Secret in environment variables**
   - Env vars can leak through crash dumps, debug endpoints, application logs, `/proc`, support tools, or shell output.

6. **Secret in Git**
   - Plain Kubernetes manifests with base64 `data` are committed to Git.
   - Base64 is decoded easily.

7. **Secret in CI/CD logs**
   - Pipeline prints `oc set env`, `helm template`, `kubectl describe`, or debug output.

8. **Secret in container image**
   - Secret accidentally copied into image during Dockerfile/Containerfile build.
   - Image pushed to internal or external registry.

9. **Secret in backup or support bundle**
   - etcd backup or must-gather contains sensitive resources.
   - Backup encryption and access control are weak.

10. **Weak rotation process**
    - Secret compromised but not rotated.
    - Application still uses old credential.
    - Long-lived service account tokens remain active.

### Senior-admin principle

Never ask only: “Can this pod run?”  
Ask: **“Who can read, mount, copy, list, watch, rotate, delete, back up, or impersonate the identity that can access this Secret?”**

## 4. Secret Lifecycle Inside the Cluster

A Secret moves through several layers:

```text
Admin / GitOps / External Secret Store
        |
        v
OpenShift API Server admission
        |
        v
etcd storage
        |
        v
API watch / controller / kubelet
        |
        v
Node memory and pod volume/env injection
        |
        v
Application process
```

### Lifecycle stages

1. **Creation**
   - Created by `oc create secret`, YAML manifest, Helm chart, Operator, External Secrets Operator, cert-manager, service-ca operator, or cluster operator.

2. **Admission**
   - API server validates schema and type-specific requirements.
   - `stringData` is converted into `data`.

3. **Persistence**
   - Stored in etcd.
   - If etcd encryption is enabled, Secret values are encrypted.
   - Object metadata such as names and namespaces are still visible.

4. **Distribution**
   - Kubelet receives the Secret only when a pod on that node references it.
   - Controllers may also watch Secrets if their RBAC allows it.

5. **Consumption**
   - Mounted as files.
   - Injected as environment variables.
   - Used as image pull credentials.
   - Used by routes, builds, operators, webhooks, and service accounts.

6. **Rotation**
   - Secret data changes.
   - Pods may or may not automatically reload it depending on how the Secret is consumed.

7. **Deletion**
   - Removing the Secret can break running workloads, new pod scheduling, image pulls, routes, builds, or operators.

## 5. Secret Types

Kubernetes and OpenShift support several built-in Secret types. Type matters because some controllers expect specific keys.

### 5.1 Opaque

Default arbitrary key-value Secret.

```yaml
type: Opaque
stringData:
  username: admin
  password: redhat
```

Use for:

- Application credentials.
- Database passwords.
- API keys.
- Small config values that are sensitive.

### 5.2 kubernetes.io/tls

Used for TLS certificate and private key pairs.

Required keys:

- `tls.crt`
- `tls.key`

Command:

```bash
oc create secret tls app-tls \
  --cert=tls.crt \
  --key=tls.key \
  -n prod
```

Validate before creating:

```bash
openssl x509 -in tls.crt -noout -subject -issuer -dates
openssl rsa -in tls.key -check -noout
openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

If the modulus values do not match, the certificate and key do not belong together.

### 5.3 kubernetes.io/dockerconfigjson

Used as image pull credentials.

Expected key:

- `.dockerconfigjson`

Command:

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=myuser \
  --docker-password='mypassword' \
  --docker-email=admin@example.com \
  -n prod
```

OpenShift commonly uses this for private registry authentication and for linking image pull secrets to service accounts.

### 5.4 kubernetes.io/dockercfg

Legacy Docker config Secret type. Prefer `kubernetes.io/dockerconfigjson` for modern usage.

### 5.5 kubernetes.io/basic-auth

Expected keys:

- `username`
- `password`

Useful for Git source clone secrets, simple HTTP basic credentials, and some automation integrations.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: git-basic-auth
  namespace: build-demo
type: kubernetes.io/basic-auth
stringData:
  username: gituser
  password: git-token-or-password
```

### 5.6 kubernetes.io/ssh-auth

Expected key:

- `ssh-privatekey`

Useful for private Git repository access from builds.

```bash
oc create secret generic git-ssh \
  --type=kubernetes.io/ssh-auth \
  --from-file=ssh-privatekey=$HOME/.ssh/id_rsa \
  -n build-demo
```

Also provide host trust separately, often through a ConfigMap containing `known_hosts`. SSH private key alone does not protect against man-in-the-middle attacks.

### 5.7 kubernetes.io/service-account-token

This is the legacy long-lived service account token Secret type.

Modern Kubernetes and OpenShift prefer short-lived, automatically rotated bound service account tokens through the TokenRequest API and projected volumes. In OpenShift 4.16 and later, a long-lived service account API token Secret is no longer automatically generated for every new service account. Existing long-lived token Secrets from older clusters can continue to function after upgrade until removed.

Avoid manually creating long-lived service account token Secrets unless a legacy integration absolutely requires it and the risk is accepted.

### 5.8 bootstrap.kubernetes.io/token

Used for node/bootstrap scenarios. Application teams should almost never create this manually in OpenShift.

### 5.9 Operator-specific Secrets

Operators often create or require Secrets with expected key names. Examples:

- Database operator admin password Secret.
- cert-manager generated TLS Secret.
- External Secrets Operator generated target Secret.
- OAuth identity provider bind password Secret.
- Cloud credential Secrets.

Always check the Operator CRD documentation before editing or deleting these Secrets manually.

## 6. Creating Secrets Correctly

### 6.1 Create from literals

```bash
oc create secret generic db-secret \
  --from-literal=username=appuser \
  --from-literal=password='S3cureP@ssw0rd' \
  -n prod
```

Risk: this can expose the password in shell history or process listings. Prefer files, stdin-safe tooling, external stores, or CI/CD secret variables with masked logs.

### 6.2 Create from files

```bash
printf '%s' 'S3cureP@ssw0rd' > password.txt
oc create secret generic db-secret \
  --from-file=password=password.txt \
  -n prod
shred -u password.txt 2>/dev/null || rm -f password.txt
```

### 6.3 Create from env file

```bash
cat > db.env <<'EOF_ENV'
DB_USERNAME=appuser
DB_PASSWORD=S3cureP@ssw0rd
EOF_ENV

oc create secret generic db-secret --from-env-file=db.env -n prod
rm -f db.env
```

### 6.4 Create declaratively with `stringData`

For manual examples, `stringData` is easier to read:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: payment-api-secret
  namespace: prod
type: Opaque
stringData:
  API_TOKEN: replace-from-secure-source
```

Apply:

```bash
oc apply -f payment-api-secret.yaml
```

Do not commit this file to Git with real values.

### 6.5 Generate a manifest without creating immediately

```bash
oc create secret generic db-secret \
  --from-literal=username=appuser \
  --from-literal=password='S3cureP@ssw0rd' \
  -n prod \
  --dry-run=client -o yaml
```

Useful for learning and testing, but do not paste real output with real values into Git or tickets.

### 6.6 Mark a Secret immutable

For Secrets that should not change accidentally:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-license
  namespace: prod
type: Opaque
immutable: true
stringData:
  license.key: example
```

Benefits:

- Prevents accidental updates.
- Can reduce API server/kubelet watch load for large-scale clusters.

Trade-off:

- To rotate, create a new Secret name and update workloads to reference it.

### 6.7 Naming standards

Use names that communicate ownership and purpose without revealing secret values:

Good:

```text
payments-db-credentials
router-wildcard-tls
gitlab-source-clone
quay-pull-secret
```

Bad:

```text
root-password-redhat123
prod-bank-api-token-real
admin-secret-do-not-delete
```

Object names are not encrypted even when etcd encryption is enabled. Avoid leaking sensitive details in Secret names.

## 7. Consuming Secrets in Workloads

### 7.1 As environment variables

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments
  namespace: prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: payments
  template:
    metadata:
      labels:
        app: payments
    spec:
      containers:
      - name: app
        image: registry.example.com/payments:1.0
        env:
        - name: DB_USERNAME
          valueFrom:
            secretKeyRef:
              name: payments-db-credentials
              key: username
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: payments-db-credentials
              key: password
```

Pros:

- Simple.
- Many applications support env-based configuration.

Cons:

- Secret values are fixed for the lifetime of the container process.
- App restart is required for update.
- Environment variables can leak through debugging, crash dumps, support tools, or accidental log output.

### 7.2 As all environment variables with `envFrom`

```yaml
        envFrom:
        - secretRef:
            name: payments-db-credentials
```

Risk:

- All keys become environment variables.
- Easy to accidentally expose more than needed.

Senior recommendation: use explicit `secretKeyRef` for high-value Secrets.

### 7.3 As mounted files

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments
  namespace: prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: payments
  template:
    metadata:
      labels:
        app: payments
    spec:
      containers:
      - name: app
        image: registry.example.com/payments:1.0
        volumeMounts:
        - name: db-secret
          mountPath: /etc/secrets/db
          readOnly: true
      volumes:
      - name: db-secret
        secret:
          secretName: payments-db-credentials
          defaultMode: 0400
```

Inside the pod:

```bash
ls -l /etc/secrets/db
cat /etc/secrets/db/username
cat /etc/secrets/db/password
```

Pros:

- Better for certificates, keys, and files.
- Secret volume contents can be updated by kubelet after Secret changes.
- Applications can reload files if designed to do so.

Cons:

- Application must know file path.
- Some runtimes do not auto-reload.
- `subPath` mounts do not receive updates automatically in the same way as normal Secret volume mounts.

### 7.4 Mount only selected keys

```yaml
      volumes:
      - name: tls-secret
        secret:
          secretName: app-tls
          items:
          - key: tls.crt
            path: server.crt
          - key: tls.key
            path: server.key
            mode: 0400
```

This reduces accidental exposure when a Secret contains multiple keys.

### 7.5 File permissions and OpenShift restricted SCC

OpenShift commonly runs containers with randomized UIDs under restricted SCC. If your application expects to read files as a specific UID or group, check:

```bash
oc rsh deploy/payments id
oc rsh deploy/payments ls -l /etc/secrets/db
```

Patterns:

- Use `defaultMode: 0400` or `0440` depending on app user/group.
- Avoid running as root just to read a Secret.
- Prefer application images that support arbitrary UID.
- Use group-readable files only when required.

Example with `defaultMode: 0440`:

```yaml
      volumes:
      - name: db-secret
        secret:
          secretName: payments-db-credentials
          defaultMode: 0440
```

### 7.6 Avoid printing Secrets during debug

Unsafe:

```bash
oc rsh deploy/payments env
oc describe pod payments-xxx
oc logs deploy/payments | grep PASSWORD
```

Safer:

```bash
oc get pod payments-xxx -o jsonpath='{.spec.containers[*].env[*].name}'
oc exec deploy/payments -- test -f /etc/secrets/db/password
```

The goal is to verify presence, not expose value.

## 8. RBAC and Access Control for Secrets

RBAC is the main control plane boundary for Secret access.

### 8.1 Check who can read Secrets

As current user:

```bash
oc auth can-i get secrets -n prod
oc auth can-i list secrets -n prod
oc auth can-i watch secrets -n prod
```

As another user:

```bash
oc auth can-i get secrets -n prod --as alice
oc auth can-i list secrets -n prod --as bob
```

As a service account:

```bash
oc auth can-i get secrets -n prod \
  --as system:serviceaccount:prod:payments-sa
```

### 8.2 Dangerous permissions

These are high risk:

```yaml
resources: ["secrets"]
verbs: ["get", "list", "watch"]
```

Especially dangerous at cluster scope:

```yaml
kind: ClusterRole
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["*"]
```

### 8.3 Least-privilege Role for one Secret

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-specific-db-secret
  namespace: prod
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames:
  - payments-db-credentials
  verbs:
  - get
```

Bind to a service account:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payments-sa-read-specific-db-secret
  namespace: prod
subjects:
- kind: ServiceAccount
  name: payments-sa
  namespace: prod
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: read-specific-db-secret
```

Important: `resourceNames` works with `get`, `update`, `patch`, and `delete`, but not with unrestricted `list`/`watch` in the same way. Avoid `list`/`watch` for Secrets unless truly required.

### 8.4 Built-in roles and Secrets

Be careful with broad roles:

- `admin` in a namespace can usually manage most namespaced resources and can indirectly access Secrets.
- `edit` can modify workloads and might indirectly consume Secrets by creating pods.
- `view` is intentionally safer and should not grant Secret read access in a typical Kubernetes/OpenShift model.

In production, do not assume that giving `edit` is harmless. A user with workload creation privileges can potentially create a pod that mounts a Secret already present in the namespace.

### 8.5 Namespace isolation is not optional

If multiple teams share one namespace, they often share Secret exposure risk. Better model:

```text
team-a-dev
team-a-test
team-a-prod
team-b-dev
team-b-test
team-b-prod
```

Secrets should not be shared across teams by copying manually. Use controlled automation or external secret store policies.

## 9. Service Accounts and Secret Access

A service account is the identity your pod uses when talking to the OpenShift API.

```yaml
spec:
  serviceAccountName: payments-sa
```

Create:

```bash
oc create sa payments-sa -n prod
```

Patch deployment:

```bash
oc set serviceaccount deploy/payments payments-sa -n prod
```

### 9.1 Service account token behavior

Modern OpenShift uses short-lived bound service account tokens for workloads. In OpenShift 4.16 and later, OpenShift no longer automatically creates a long-lived API token Secret for every new service account. Existing long-lived token Secrets from upgraded clusters can still exist and should be reviewed.

Check long-lived service account token Secrets:

```bash
oc get secrets -A --field-selector type=kubernetes.io/service-account-token
```

Investigate a Secret:

```bash
oc get secret <token-secret> -n <ns> -o yaml
```

If a legacy token is no longer needed, remove it carefully after confirming no external automation depends on it.

### 9.2 Disable automatic token mounting when not needed

For pods that do not need Kubernetes API access:

```yaml
spec:
  automountServiceAccountToken: false
```

Or on the service account:

```bash
oc patch sa payments-sa -n prod -p '{"automountServiceAccountToken": false}'
```

This reduces token exposure from compromised containers.

### 9.3 Projected bound service account token

For applications that need a specific audience and short lifetime:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: token-demo
  namespace: prod
spec:
  serviceAccountName: payments-sa
  containers:
  - name: app
    image: registry.access.redhat.com/ubi9/ubi-minimal
    command: ["sleep", "3600"]
    volumeMounts:
    - name: api-token
      mountPath: /var/run/secrets/tokens
      readOnly: true
  volumes:
  - name: api-token
    projected:
      sources:
      - serviceAccountToken:
          path: token
          audience: openshift
          expirationSeconds: 3600
```

### 9.4 Service account and image pull Secrets

A pod's service account can have image pull secrets:

```bash
oc secrets link payments-sa regcred --for=pull -n prod
oc get sa payments-sa -n prod -o yaml
```

This is different from allowing a pod to mount a Secret as a volume.

## 10. Image Pull Secret Management

Image pull secrets allow kubelet/CRI-O to authenticate to a private registry before starting containers.

### 10.1 Create a registry pull Secret

```bash
oc create secret docker-registry quay-pull \
  --docker-server=quay.io \
  --docker-username='<username>' \
  --docker-password='<token>' \
  --docker-email='admin@example.com' \
  -n prod
```

### 10.2 Link to the default service account

```bash
oc secrets link default quay-pull --for=pull -n prod
```

### 10.3 Link to a custom service account

```bash
oc create sa app-sa -n prod
oc secrets link app-sa quay-pull --for=pull -n prod
oc set serviceaccount deploy/payments app-sa -n prod
```

### 10.4 Define directly in workload YAML

```yaml
spec:
  imagePullSecrets:
  - name: quay-pull
```

Senior recommendation: prefer linking to the service account for many workloads in the same namespace, and use workload-level `imagePullSecrets` only for exceptions.

### 10.5 OpenShift internal registry integration

OpenShift automatically creates image pull secrets for service accounts to integrate the internal image registry with cluster authentication and authorization, if the integrated registry capability is enabled. If the image registry capability is disabled, these secrets might not be generated.

Check service account pull secrets:

```bash
oc get sa default -n prod -o jsonpath='{.imagePullSecrets}' | jq .
oc get sa default -n prod -o yaml
```

### 10.6 Global cluster pull secret

The cluster-level pull secret is used by OpenShift components and cluster operators to pull platform images.

Inspect secret location:

```bash
oc get secret pull-secret -n openshift-config -o yaml
```

Extract:

```bash
oc extract secret/pull-secret -n openshift-config --to=/tmp/pull-secret --confirm
```

Never edit casually. Mistakes can degrade cluster operators. Use official procedures for adding registries or rotating credentials.

### 10.7 Troubleshooting image pull failures

Symptoms:

```text
ErrImagePull
ImagePullBackOff
unauthorized: authentication required
manifest unknown
x509: certificate signed by unknown authority
```

Commands:

```bash
oc describe pod <pod> -n prod
oc get events -n prod --sort-by=.lastTimestamp
oc get sa <sa> -n prod -o yaml
oc get secret <pull-secret> -n prod -o jsonpath='{.type}'; echo
oc get secret <pull-secret> -n prod -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Common causes:

| Symptom | Likely cause | Fix |
|---|---|---|
| `unauthorized` | Bad username/token | Recreate pull Secret |
| `secret not found` | Wrong namespace | Create Secret in workload namespace |
| `x509 unknown authority` | Registry CA not trusted by nodes | Configure cluster image registry trust / additional trust bundle |
| `manifest unknown` | Image tag does not exist | Correct image reference |
| Works with `podman pull` but not pod | Secret not linked to pod's service account | `oc secrets link <sa> <secret> --for=pull` |

## 11. TLS and Certificate Secret Management

TLS Secrets are central to OpenShift security and certificate administration.

### 11.1 Create TLS Secret

```bash
oc create secret tls app-tls \
  --cert=fullchain.crt \
  --key=private.key \
  -n prod
```

### 11.2 Validate TLS Secret

```bash
oc get secret app-tls -n prod -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/tls.crt
oc get secret app-tls -n prod -o jsonpath='{.data.tls\.key}' | base64 -d > /tmp/tls.key

openssl x509 -in /tmp/tls.crt -noout -subject -issuer -dates
openssl x509 -in /tmp/tls.crt -noout -text | grep -A2 'Subject Alternative Name'
openssl rsa -in /tmp/tls.key -check -noout
```

### 11.3 Use TLS Secret in a Route

Edge termination:

```bash
oc create route edge payments \
  --service=payments \
  --hostname=payments.apps.example.com \
  --cert=fullchain.crt \
  --key=private.key \
  -n prod
```

Declarative route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments
  namespace: prod
spec:
  host: payments.apps.example.com
  to:
    kind: Service
    name: payments
  tls:
    termination: edge
    certificate: |
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----
    key: |
      -----BEGIN PRIVATE KEY-----
      ...
      -----END PRIVATE KEY-----
```

OpenShift Routes store TLS material directly in the Route object, not always as a separate Kubernetes Secret. That means Route TLS data is also sensitive and must be protected. When OpenShift etcd encryption is enabled, Routes are included among encrypted resources.

### 11.4 Re-encrypt route

Use re-encrypt when router terminates external TLS and then creates a second TLS connection to the backend service.

```bash
oc create route reencrypt payments \
  --service=payments \
  --hostname=payments.apps.example.com \
  --cert=router.crt \
  --key=router.key \
  --dest-ca-cert=backend-ca.crt \
  -n prod
```

### 11.5 Passthrough route

Use passthrough when the backend pod terminates TLS:

```bash
oc create route passthrough payments \
  --service=payments \
  --hostname=payments.apps.example.com \
  -n prod
```

The backend pod needs its own TLS certificate, normally mounted from a Secret or generated through service serving certificates/cert-manager.

### 11.6 TLS rotation pattern

Recommended pattern:

1. Create new Secret name, for example `payments-tls-2026q3`.
2. Validate certificate, SAN, chain, and key.
3. Patch workload or ingress/route reference.
4. Roll out application/router if required.
5. Verify externally with `openssl s_client` and curl.
6. Keep old Secret briefly for rollback.
7. Delete old Secret after successful validation.

Do not overwrite high-risk TLS Secrets without a rollback path.

## 12. OpenShift Service Serving Certificate Secrets

OpenShift includes a Service CA Operator that can generate serving certificates for services. This is useful for internal service-to-service TLS and webhooks.

### 12.1 Generate a service serving certificate

Annotate a Service:

```bash
oc annotate service payments \
  service.beta.openshift.io/serving-cert-secret-name=payments-serving-cert \
  -n prod
```

OpenShift creates a Secret named `payments-serving-cert` with:

- `tls.crt`
- `tls.key`

Check:

```bash
oc get secret payments-serving-cert -n prod
oc get secret payments-serving-cert -n prod -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject -issuer -dates
```

Mount it into the pod:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments
  namespace: prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: payments
  template:
    metadata:
      labels:
        app: payments
    spec:
      containers:
      - name: app
        image: registry.example.com/payments:1.0
        volumeMounts:
        - name: serving-cert
          mountPath: /etc/tls/private
          readOnly: true
      volumes:
      - name: serving-cert
        secret:
          secretName: payments-serving-cert
          defaultMode: 0400
```

### 12.2 Inject service CA bundle into a ConfigMap

Create ConfigMap:

```bash
oc create configmap service-ca -n prod
```

Annotate:

```bash
oc annotate configmap service-ca \
  service.beta.openshift.io/inject-cabundle=true \
  -n prod
```

The Service CA Operator injects the CA certificate under `service-ca.crt`.

Important: when this annotation is added, existing data in the ConfigMap can be removed. Use a dedicated ConfigMap for the service CA bundle.

Mount CA bundle:

```yaml
      volumeMounts:
      - name: service-ca
        mountPath: /etc/pki/service-ca
        readOnly: true
      volumes:
      - name: service-ca
        configMap:
          name: service-ca
```

### 12.3 Rotate service serving certificate manually

OpenShift can recreate the generated Secret:

```bash
oc delete secret payments-serving-cert -n prod
```

The operator recreates it because the Service annotation still requests it.

Then restart/reload pods if the application does not automatically reload cert files:

```bash
oc rollout restart deploy/payments -n prod
```

### 12.4 When not to use service serving certs

Do not use Service CA certs for:

- Public internet certificates.
- External client trust.
- Certificates requiring public CA validation.
- Cases where every individual pod needs a unique identity and cannot share a service-level certificate.

For more advanced certificate lifecycle, use cert-manager Operator, enterprise PKI, service mesh mTLS, SPIFFE/SPIRE-based workload identity, or an external CA workflow.

## 13. Secret Encryption at Rest in etcd

OpenShift stores API objects in etcd. Without etcd encryption, Secret values are only base64 encoded in storage. OpenShift supports enabling etcd encryption to provide another layer of protection if an etcd backup or disk is exposed.

### 13.1 What gets encrypted

When etcd encryption is enabled in OpenShift, sensitive resource values include:

- Secrets.
- ConfigMaps.
- Routes.
- OAuth access tokens.
- OAuth authorize tokens.

Important: encryption protects **values**, not all metadata. Resource type, namespace, and object name are not encrypted. Therefore, do not put sensitive values into names or labels.

### 13.2 Supported encryption types

OpenShift supports:

- `aesgcm`
- `aescbc`
- `identity` for no encryption

OpenShift documentation notes that encryption keys rotate automatically and historical keys are retained to support decrypting older data/backups.

### 13.3 Enable etcd encryption

Edit the cluster APIServer object:

```bash
oc edit apiserver
```

Set:

```yaml
spec:
  encryption:
    type: aesgcm
```

Alternative:

```yaml
spec:
  encryption:
    type: aescbc
```

### 13.4 Verify encryption completion

OpenShift API server resources:

```bash
oc get openshiftapiserver -o=jsonpath='{range .items[0].status.conditions[?(@.type=="Encrypted")]}{.reason}{"\n"}{.message}{"\n"}'
```

Kubernetes API server resources:

```bash
oc get kubeapiserver -o=jsonpath='{range .items[0].status.conditions[?(@.type=="Encrypted")]}{.reason}{"\n"}{.message}{"\n"}'
```

OAuth API server resources:

```bash
oc get authentication.operator.openshift.io -o=jsonpath='{range .items[0].status.conditions[?(@.type=="Encrypted")]}{.reason}{"\n"}{.message}{"\n"}'
```

Expected successful reason:

```text
EncryptionCompleted
```

### 13.5 Backup warning

Do not take a production etcd backup during initial encryption or decryption if you can avoid it. A backup taken mid-process can be partially encrypted. Also, when encryption is enabled, the static Kubernetes resources archive associated with an etcd backup contains encryption keys required for restore. Protect that file separately and strictly.

### 13.6 What etcd encryption does not solve

Etcd encryption does not protect against:

- A user with `get secrets` API access.
- A compromised pod that has the Secret mounted.
- A compromised node.
- Secret values printed in logs.
- Secrets committed to Git.
- Secrets stored in container images.
- Over-permissive CI/CD credentials.

Think of etcd encryption as one control, not the complete solution.

## 14. External Secret Management Patterns

Enterprise OpenShift environments often avoid storing source-of-truth secrets directly in Kubernetes. Instead, they use an external system and synchronize or mount secrets into the cluster.

### 14.1 Why external secret stores are used

Benefits:

- Centralized control.
- Strong audit trail.
- Rotation automation.
- Fine-grained access policy.
- Separation of duties.
- Multi-cluster consistency.
- Compliance alignment.

Common stores:

- HashiCorp Vault.
- AWS Secrets Manager.
- Azure Key Vault.
- Google Secret Manager.
- IBM Cloud Secrets Manager.
- AWS Systems Manager Parameter Store.
- CyberArk / enterprise PAM solutions.

### 14.2 External Secrets Operator for Red Hat OpenShift

The Red Hat External Secrets Operator integrates external secret management systems with OpenShift by fetching external values and creating/updating native Kubernetes Secrets in the cluster.

High-level flow:

```text
External Secret Store
        |
        | provider auth
        v
External Secrets Operator
        |
        | reconciles ExternalSecret CR
        v
Kubernetes Secret in namespace
        |
        v
Application pod consumes native Secret
```

Example conceptual resources:

```yaml
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: team-vault
  namespace: prod
spec:
  provider:
    vault:
      server: https://vault.example.com
      path: secret
      version: v2
      auth:
        kubernetes:
          mountPath: kubernetes
          role: payments-prod
          serviceAccountRef:
            name: external-secrets-sa
```

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: payments-db
  namespace: prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: team-vault
    kind: SecretStore
  target:
    name: payments-db-credentials
    creationPolicy: Owner
  data:
  - secretKey: username
    remoteRef:
      key: payments/prod/db
      property: username
  - secretKey: password
    remoteRef:
      key: payments/prod/db
      property: password
```

The exact API versions and provider configuration can vary by Operator version. Always confirm against the installed CRDs:

```bash
oc api-resources | grep -i external
oc explain externalsecret.spec
oc explain secretstore.spec
```

### 14.3 Secrets Store CSI Driver pattern

The CSI pattern mounts secrets from an external store directly into pods as volumes. Depending on configuration, it may or may not create a Kubernetes Secret.

High-level flow:

```text
External Secret Store
        |
        v
Secrets Store CSI Driver
        |
        v
Pod volume mount
```

Use when:

- You want to avoid persisting certain secret values as Kubernetes Secret objects.
- Application can read files from mounted paths.
- External store availability and node plugin behavior are well understood.

Trade-offs:

- More moving parts on nodes.
- App must read from files.
- Debugging involves CSI driver, provider plugin, node identity, and external store policy.

### 14.4 Vault Agent sidecar/injector pattern

A sidecar or init container authenticates to Vault and writes secrets to a shared memory-backed volume.

Benefits:

- Dynamic secrets.
- Lease renewal.
- Tight integration with Vault.

Risks:

- Sidecar complexity.
- Token handling.
- App reload behavior.
- Namespace tenancy and Vault role mapping.

### 14.5 Choosing the right model

| Pattern | Secret exists as Kubernetes Secret? | Best for | Main risk |
|---|---:|---|---|
| Native Kubernetes Secret | Yes | Simple apps, lab, basic deployments | Weak rotation / Git leakage |
| External Secrets Operator | Yes, synced | Enterprise central source of truth | Kubernetes Secret still exists |
| Secrets Store CSI | Optional | File-based consumption, avoid API Secret persistence | Node/plugin complexity |
| Vault Agent | No native Secret required | Dynamic secrets, Vault-heavy shops | Sidecar/app complexity |
| cert-manager | Yes, generated TLS Secret | Certificate automation | Issuer/RBAC mistakes |

## 15. GitOps-Safe Secret Management

GitOps and Secrets need special care. A common anti-pattern is committing this:

```yaml
data:
  password: cmVkaGF0MTIz
```

That is not secure. It is just base64.

### 15.1 Never commit real Secrets in plain Kubernetes manifests

Bad:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: prod-db
type: Opaque
data:
  password: UHJvZFJlYWxQYXNzd29yZA==
```

Anyone with repo access can decode it.

### 15.2 GitOps-safe options

1. **External Secrets Operator**
   - Git stores `ExternalSecret` references only.
   - Secret value lives in external store.

2. **Sealed Secrets**
   - Git stores encrypted Secret sealed for a cluster/controller key.
   - Controller decrypts into native Secret.

3. **SOPS with KMS/GPG/Age**
   - Git stores encrypted YAML.
   - Argo CD plugin, pipeline, or controller decrypts.

4. **Helm values from CI/CD secret variables**
   - Avoid rendering secret values into logs.
   - Use masked/protected variables.

5. **Argo CD Vault Plugin / similar**
   - Git stores placeholders.
   - Deployment time resolves values from Vault or cloud store.

### 15.3 Argo CD and Secret risk

Argo CD often needs broad read access to desired state. If Argo CD can sync Secrets into many namespaces, protect:

- Argo CD admin access.
- Repository credentials.
- Project permissions.
- Cluster credentials.
- ApplicationSet generators.
- Sync windows and approval policies.

A compromised GitOps controller can become a cluster-wide secret distribution mechanism.

### 15.4 Safe repo pattern

```text
apps/
  payments/
    base/
      deployment.yaml
      service.yaml
      externalsecret.yaml
    overlays/
      dev/
      test/
      prod/
```

The repository contains:

```yaml
kind: ExternalSecret
spec:
  data:
  - secretKey: password
    remoteRef:
      key: payments/prod/db
      property: password
```

The repository does **not** contain the actual password.

## 16. Rotation Strategy

Secret rotation is the controlled replacement of a credential without outage or with minimal outage.

### 16.1 Rotation types

| Type | Example | Restart needed? |
|---|---|---|
| Static password update | DB password | Usually yes |
| TLS certificate renewal | Route/backend cert | Sometimes |
| Registry token rotation | Pull secret token | New pulls affected |
| Service account token | Bound token | Automatic |
| External dynamic credential | Vault DB credential | App-dependent |

### 16.2 Golden rotation process

1. **Inventory**
   - Find all consumers.
   - Find all places the Secret value exists.

2. **Create new credential in source system**
   - New DB user/password, new API token, new certificate.

3. **Create/update Secret**
   - Prefer new Secret name for high-risk changes.

4. **Update application reference**
   - Patch Deployment, Helm values, ExternalSecret target, or Route.

5. **Rollout restart or reload**
   - Required for env var-based consumption.
   - File-based consumers may reload automatically only if app supports it.

6. **Verify**
   - App health.
   - Logs.
   - Synthetic transaction.
   - External TLS validation.

7. **Revoke old credential**
   - Do not leave old password active forever.

8. **Delete old Secret**
   - After rollback window.

### 16.3 Rotation for env var Secrets

When a Secret used as env vars changes, existing pods do not update their environment. Restart pods:

```bash
oc rollout restart deploy/payments -n prod
oc rollout status deploy/payments -n prod
```

### 16.4 Rotation for mounted Secret files

Mounted Secret volumes can update after kubelet syncs the new content, but:

- App must reload file.
- `subPath` mounts will not update normally.
- Some apps read files only at startup.

Check file timestamp inside pod:

```bash
oc exec deploy/payments -n prod -- ls -l /etc/secrets/db
```

If the app does not reload:

```bash
oc rollout restart deploy/payments -n prod
```

### 16.5 Immutable Secret rotation

Use new names:

```text
payments-db-credentials-v1
payments-db-credentials-v2
payments-db-credentials-v3
```

Patch deployment:

```bash
oc set volume deploy/payments \
  --remove --name=db-secret -n prod

oc set volume deploy/payments \
  --add --name=db-secret \
  --type=secret --secret-name=payments-db-credentials-v2 \
  --mount-path=/etc/secrets/db \
  -n prod
```

### 16.6 TLS rotation with overlap

For TLS, avoid rotating at the last minute. Use this schedule:

- T-30 days: alert.
- T-14 days: renew certificate.
- T-7 days: deploy.
- T-1 day: verify no old cert remains.

Check expiration:

```bash
oc get secret app-tls -n prod -o jsonpath='{.data.tls\.crt}' \
  | base64 -d \
  | openssl x509 -noout -enddate
```

Find TLS Secrets expiring soon:

```bash
for ns in $(oc get ns -o jsonpath='{.items[*].metadata.name}'); do
  for s in $(oc get secret -n "$ns" --field-selector type=kubernetes.io/tls -o jsonpath='{.items[*].metadata.name}' 2>/dev/null); do
    echo "--- $ns/$s"
    oc get secret "$s" -n "$ns" -o jsonpath='{.data.tls\.crt}' \
      | base64 -d 2>/dev/null \
      | openssl x509 -noout -subject -enddate 2>/dev/null
  done
done
```

## 17. Backup, Restore, and DR Considerations

Secrets are part of the Kubernetes API state. Therefore, backup and restore operations are security-sensitive.

### 17.1 Etcd backup sensitivity

An etcd backup can contain:

- Secrets.
- ConfigMaps.
- Route TLS material.
- OAuth tokens.
- Operator credentials.
- Service account token Secrets from old clusters.

If etcd encryption is enabled, backup restore also requires encryption key material from the static Kubernetes resources archive. Protect backup files and encryption key archives with strict access controls.

### 17.2 Backup handling rules

- Encrypt backups at rest.
- Store backups in restricted bucket/storage.
- Separate duties between backup operators and cluster administrators where possible.
- Log access to backup storage.
- Test restore in secure environment.
- Never share etcd backups in support cases unless explicitly required and approved.

### 17.3 Application-level backup

For application backups, do not assume Kubernetes Secret backup is enough. A DB password Secret does not back up database data. A TLS Secret does not back up application state.

### 17.4 Restore risks

Restoring old Secrets can reintroduce:

- Old passwords.
- Expired certificates.
- Revoked tokens.
- Old image pull credentials.
- Old OAuth client secrets.

After restoring a cluster, perform a credential review and rotate high-risk Secrets.

## 18. Auditing and Compliance

### 18.1 What to audit

Audit these events:

- Secret create/update/delete.
- Secret get/list/watch.
- Role/ClusterRole changes that grant Secret access.
- RoleBinding/ClusterRoleBinding changes.
- Service account token creation.
- ExternalSecret/SecretStore changes.
- Route TLS changes.
- Image pull secret changes.

### 18.2 Commands for review

List Secrets across namespaces:

```bash
oc get secrets -A
```

Find large Secrets:

```bash
oc get secrets -A -o json \
  | jq -r '.items[] | [.metadata.namespace, .metadata.name, .type, ((.data // {}) | tostring | length)] | @tsv' \
  | sort -k4 -n
```

Find who can read Secrets in a namespace:

```bash
oc get rolebindings,clusterrolebindings -A -o wide | grep -i secret
```

Better RBAC inspection often requires reviewing roles:

```bash
oc get role -A -o yaml | less
oc get clusterrole -o yaml | less
```

Check direct permission:

```bash
oc auth can-i get secrets -n prod --as jane
oc auth can-i create pods -n prod --as jane
```

Remember: `create pods` may allow indirect Secret access by mounting Secrets.

### 18.3 Secret classification labels

A useful convention:

```yaml
metadata:
  labels:
    security.example.com/classification: restricted
    security.example.com/owner: payments
    security.example.com/rotation: quarterly
```

Do not put secret values in labels or annotations. Labels and annotations are often visible in logs, UIs, metrics, inventory tools, and audit output.

### 18.4 Compliance questions to answer

For production environments, you should be able to answer:

- Which Secrets are older than 90/180/365 days?
- Which Secrets are not owned by any team?
- Which Secrets contain TLS certs expiring within 30 days?
- Which service accounts can read Secrets?
- Which users have namespace admin/edit access?
- Is etcd encryption enabled?
- Are long-lived service account token Secrets still present?
- Are image pull secrets using personal user credentials instead of robot/service accounts?
- Are any Secrets present in Git history?

## 19. SCC, Pod Security, and Secret Exposure

Security Context Constraints do not directly grant Secret API access, but they affect what a pod can do after it receives a Secret.

### 19.1 Why SCC matters for Secrets

If a pod can run privileged, mount host paths, or run as root with broad capabilities, then a container compromise is more severe. It might access host paths, other workload data, node-level credentials, or service account tokens.

### 19.2 Risky SCC combinations

High-risk patterns:

- `privileged` SCC plus mounted Secrets.
- HostPath access plus application credentials.
- `hostNetwork: true` plus sensitive tokens.
- Root containers with unnecessary Linux capabilities.
- Shared namespace with broad `edit` access.

### 19.3 Safer baseline

- Use restricted/restricted-v2 where possible.
- Do not grant `anyuid` just to read Secret files.
- Disable service account token auto-mount when app does not use API.
- Use read-only root filesystem where possible.
- Mount Secrets read-only.
- Avoid mounting all Secrets into a generic debug/admin pod.

Example:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop:
    - ALL
```

Container images must support these settings.

## 20. Common Production Failure Scenarios

### Scenario 1: Pod fails because Secret is missing

Error:

```text
secret "db-secret" not found
```

Fix:

```bash
oc get secret db-secret -n prod
oc get deploy payments -n prod -o yaml | grep -A5 -B5 db-secret
oc create secret generic db-secret --from-literal=password='...' -n prod
```

### Scenario 2: Wrong namespace

Secret exists in `dev`, pod runs in `prod`.

Secrets are namespace-scoped. You cannot directly mount a Secret from another namespace.

Fix:

- Create/sync the Secret into the correct namespace.
- Use External Secrets Operator with namespace-specific policy.
- Avoid manual copy without ownership and rotation plan.

### Scenario 3: Secret key name mismatch

Deployment expects `DB_PASSWORD`; Secret contains `password`.

Check:

```bash
oc get secret db-secret -n prod -o jsonpath='{.data}' | jq keys
oc get deploy payments -n prod -o yaml | grep -A10 secretKeyRef
```

Fix Secret key or deployment reference.

### Scenario 4: Updated Secret but app still uses old value

Cause:

- Secret consumed as env var.
- App reads file only at startup.

Fix:

```bash
oc rollout restart deploy/payments -n prod
```

### Scenario 5: ImagePullBackOff after token rotation

Cause:

- Pull Secret recreated but not linked to service account.
- Wrong registry server key in `.dockerconfigjson`.
- Registry CA not trusted.

Fix:

```bash
oc get sa app-sa -n prod -o yaml
oc secrets link app-sa quay-pull --for=pull -n prod
oc describe pod <pod> -n prod
```

### Scenario 6: TLS route serves old certificate

Cause:

- Route not updated.
- Router not reloaded yet.
- Wrong hostname/SNI tested.
- Intermediate chain missing.

Check:

```bash
oc get route payments -n prod -o yaml
openssl s_client -connect payments.apps.example.com:443 -servername payments.apps.example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
```

### Scenario 7: Service serving certificate not generated

Cause:

- Annotation on wrong object.
- Service name wrong.
- Service CA Operator degraded.
- Namespace issue.

Check:

```bash
oc describe svc payments -n prod
oc get secret payments-serving-cert -n prod
oc get co service-ca
oc get pods -n openshift-service-ca-operator
```

### Scenario 8: ExternalSecret not syncing

Check:

```bash
oc get externalsecret -n prod
oc describe externalsecret payments-db -n prod
oc get secretstore -n prod
oc describe secretstore team-vault -n prod
oc logs -n openshift-operators deploy/external-secrets-operator
```

Common causes:

- Provider auth failure.
- Wrong remote key/property.
- RBAC denied.
- Network/proxy issue.
- TLS trust issue to external store.

## 21. Troubleshooting Playbooks

### 21.1 Pod cannot start due to Secret

```bash
NS=prod
POD=<pod-name>

oc describe pod "$POD" -n "$NS"
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -50
```

Look for:

```text
MountVolume.SetUp failed for volume
secret not found
couldn't find key
ImagePullBackOff
```

Verify references:

```bash
oc get pod "$POD" -n "$NS" -o yaml | grep -A20 -B10 -i secret
```

Verify Secret:

```bash
oc get secret -n "$NS"
oc get secret <secret-name> -n "$NS" -o yaml
```

### 21.2 Workload has wrong Secret value

Do not print the value unless absolutely necessary.

Check key exists:

```bash
oc get secret db-secret -n prod -o json | jq '.data | keys'
```

Check deployment reference:

```bash
oc get deploy payments -n prod -o yaml | grep -A20 -B10 secretKeyRef
```

Restart if env var based:

```bash
oc rollout restart deploy/payments -n prod
oc rollout status deploy/payments -n prod
```

### 21.3 TLS Secret mismatch

```bash
oc get secret app-tls -n prod -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/app.crt
oc get secret app-tls -n prod -o jsonpath='{.data.tls\.key}' | base64 -d > /tmp/app.key

openssl x509 -noout -modulus -in /tmp/app.crt | openssl md5
openssl rsa  -noout -modulus -in /tmp/app.key | openssl md5
```

If hashes differ, recreate the TLS Secret with matching key/cert.

### 21.4 Secret volume permission issue

Inside pod:

```bash
oc rsh deploy/payments
id
ls -l /etc/secrets/db
cat /etc/secrets/db/username
```

If permission denied:

- Check `defaultMode`.
- Check app UID.
- Check SCC constraints.
- Avoid using `anyuid` as first fix.
- Prefer image compatibility with arbitrary UID and correct file permissions.

### 21.5 Who changed a Secret?

Use audit logs if configured and retained. Also check object metadata:

```bash
oc get secret db-secret -n prod -o yaml
```

Look at:

- `metadata.creationTimestamp`
- `metadata.managedFields`
- labels/annotations from GitOps tools

For GitOps-managed Secrets, check Argo CD app history or pipeline logs. Be careful that pipeline logs might include secret values if masking is misconfigured.

### 21.6 Find workloads using a Secret

Quick grep method:

```bash
NS=prod
SECRET=db-secret

for r in deploy deploymentconfig statefulset daemonset job cronjob; do
  oc get $r -n "$NS" -o yaml 2>/dev/null | grep -B20 -A20 "$SECRET" && echo "Found in $r"
done
```

Better JSON/JQ approaches can be built for your environment, but the grep method is practical during incidents.

- [ ] Enforce audit log retention suitable for compliance.
- [ ] Use trusted CA bundles for private registries and external secret stores.

### Namespace-level

- [ ] Separate teams/environments into different namespaces.
- [ ] Avoid shared prod namespace for many teams.
- [ ] Do not grant broad `admin`/`edit` unnecessarily.
- [ ] Review who can `create pods` and `create deployments`.
- [ ] Label Secrets with owner and rotation policy.
- [ ] Avoid secret values in names, labels, annotations.
- [ ] Use dedicated service accounts per application.

### Workload-level

- [ ] Disable service account token auto-mount when unused.
- [ ] Mount only required Secret keys.
- [ ] Prefer file mounts for TLS/private keys.
- [ ] Avoid `envFrom` for large/high-value Secrets.
- [ ] Avoid privileged/anyuid for secret-consuming workloads.
- [ ] Use read-only mounts.
- [ ] Ensure application does not log Secret values.
- [ ] Restart/reload workloads after rotation.

### GitOps/CI/CD

- [ ] Never commit real Secret values in plain YAML.
- [ ] Use External Secrets Operator, SOPS, Sealed Secrets, or approved equivalent.
- [ ] Mask CI/CD variables.
- [ ] Do not print rendered Secret manifests in logs.
- [ ] Restrict repository and Argo CD project access.
- [ ] Rotate credentials after accidental exposure.

### Certificate-specific

- [ ] Track TLS Secret expiration.
- [ ] Validate cert/key match.
- [ ] Include full certificate chain where required.
- [ ] Rotate before expiry.
- [ ] Use service serving certs for internal services where appropriate.
- [ ] Use public/enterprise CA certs for external routes.

## 23. Real-World Administration Scenarios

### Scenario A: Secure database password for production app

Goal: app reads DB credentials securely and supports rotation.

Recommended design:

- Store source-of-truth in Vault or cloud secret manager.
- Use External Secrets Operator to create `payments-db-credentials` in namespace `payments-prod`.
- Mount as files, not env vars, if app supports reload.
- Use dedicated service account `payments-sa`.
- Disable automount service account token if API access is not needed.
- Give no direct Secret read access to developers in prod.
- Use GitOps to deploy `ExternalSecret`, not real password.

YAML shape:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments
  namespace: payments-prod
spec:
  template:
    spec:
      serviceAccountName: payments-sa
      automountServiceAccountToken: false
      containers:
      - name: app
        image: registry.example.com/payments:2.1
        volumeMounts:
        - name: db-creds
          mountPath: /etc/payments/db
          readOnly: true
      volumes:
      - name: db-creds
        secret:
          secretName: payments-db-credentials
          items:
          - key: username
            path: username
          - key: password
            path: password
          defaultMode: 0400
```

1. Identify Secret and consumers.

```bash

```

2. Revoke external credential first if possible.
3. Create replacement credential.
4. Update Secret or create new Secret.
5. Restart/reload workloads.
6. Confirm application health.
7. Search logs/pipelines/Git for exposed value.
8. Review RBAC and audit logs.
9. Remove old credential and old Secret.
10. Document incident and preventive control.

## 24. Interview and Exam-Style Questions

### Q1. Is a Kubernetes Secret encrypted by default?

Not necessarily. In manifests/API output, data is base64 encoded, not encrypted. In OpenShift, enable etcd encryption to encrypt Secret values at rest. RBAC is still required because API-authorized users can read decoded values.

### Q2. Why is `create pods` dangerous in a namespace with Secrets?

A user who can create a pod can often create a pod that mounts an existing Secret in that namespace. Therefore, even without direct `get secrets`, pod creation can become indirect Secret access.

### Q3. Difference between `--for=pull` and `--for=mount` in `oc secrets link`?

- `--for=pull`: allows service account to use Secret as image pull credentials.
- `--for=mount`: historically allowed service account pods to mount a Secret. In modern Kubernetes/OpenShift, mounting is primarily governed by pod spec and RBAC/admission model, but understanding this distinction is important for OpenShift administration and legacy behavior.

### Q4. Why did my pod not pick up the new Secret value?

If the Secret was consumed as environment variables, existing pods keep the old environment until restarted. If mounted as files, kubelet can update the volume, but the application must reload the file and `subPath` mounts are problematic for updates.

### Q5. What is the best way to store production Secrets in GitOps?

Do not store real Secret values in plain YAML. Use External Secrets Operator, SOPS, Sealed Secrets, Argo CD Vault Plugin, or another approved encrypted/external-store workflow.

### Q6. What OpenShift feature can generate internal service certificates?

The OpenShift Service CA Operator can generate service serving certificate Secrets when a Service is annotated with `service.beta.openshift.io/serving-cert-secret-name=<secret-name>`.

### Q7. What happens when etcd encryption is enabled?

OpenShift encrypts values for sensitive resources such as Secrets, ConfigMaps, Routes, OAuth access tokens, and OAuth authorize tokens. Resource names, namespaces, and types remain visible. Encryption status must be verified after enabling.

### Q8. How do you troubleshoot `ImagePullBackOff` caused by private registry auth?

Check pod events, service account `imagePullSecrets`, pull Secret type and decoded `.dockerconfigjson`, registry hostname, token validity, image tag existence, and node trust for registry CA.

### Q9. How do you rotate an immutable Secret?

Create a new Secret with a new name, update workload references, roll out the workload, validate, and then delete the old Secret after rollback window.

### Q10. Why should service account token automount be disabled?

If a pod does not need Kubernetes API access, disabling automount reduces the impact of container compromise because the attacker cannot steal an unnecessary in-cluster API token from the pod filesystem.

## 25. Command Cheat Sheet

### Create generic Secret

```bash
oc create secret generic app-secret \
  --from-literal=username=appuser \
  --from-literal=password='S3cret' \
  -n prod
```

### Create TLS Secret

```bash
oc create secret tls app-tls --cert=tls.crt --key=tls.key -n prod
```

### Create image pull Secret

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=user \
  --docker-password=token \
  --docker-email=admin@example.com \
  -n prod
```

### Link image pull Secret to service account

```bash
oc secrets link default regcred --for=pull -n prod
```

### Decode Secret value

```bash
oc get secret app-secret -n prod -o jsonpath='{.data.password}' | base64 -d; echo
```

### List Secret keys without values

```bash
oc get secret app-secret -n prod -o json | jq '.data | keys'
```

### Check Secret type

```bash
oc get secret app-secret -n prod -o jsonpath='{.type}'; echo
```

### Find all TLS Secrets

```bash
oc get secret -A --field-selector type=kubernetes.io/tls
```

### Check TLS cert expiry

```bash
oc get secret app-tls -n prod -o jsonpath='{.data.tls\.crt}' \
  | base64 -d \
  | openssl x509 -noout -subject -issuer -dates
```

### Generate service serving cert

```bash
oc annotate service app \
  service.beta.openshift.io/serving-cert-secret-name=app-serving-cert \
  -n prod
```

### Inject service CA bundle

```bash

  service.beta.openshift.io/inject-cabundle=true \
  -n prod
```

```bash

```

### Disable service account token automount on deployment

```bash
oc patch deploy app -n prod --type merge \
  -p '{"spec":{"template":{"spec":{"automountServiceAccountToken":false}}}}'
```

### Enable etcd encryption

```bash
oc edit apiserver
```

Set:

```yaml
spec:
  encryption:
    type: aesgcm
```

```bash
oc get kubeapiserver -o=jsonpath='{range .items[0].status.conditions[?(@.type=="Encrypted")]}{.reason}{"\n"}{.message}{"\n"}'
```

### Restart deployment after Secret change

```bash
oc rollout restart deploy/app -n prod
oc rollout status deploy/app -n prod
```

### Find service account token Secrets

```bash
oc get secrets -A --field-selector type=kubernetes.io/service-account-token
```

### Troubleshoot pod events

```bash
oc describe pod <pod> -n prod
oc get events -n prod --sort-by=.lastTimestamp | tail -50
```

## Final Senior-Admin Notes

Secret management is not a one-command task. It is an operational security practice. In a mature OpenShift platform, you should be able to prove:

- Where every production Secret comes from.
- Who owns it.
- Who can read or indirectly consume it.
- How it is rotated.
- Whether it is backed up securely.
- Whether it is present in Git, logs, images, or support bundles.
- Whether applications restart or reload safely after rotation.
- Whether expired certificates and stale tokens are detected before outage.

For Advanced OpenShift Administration, the target skill is not only creating a Secret. The target skill is designing and operating a Secret lifecycle that survives audits, incidents, application releases, certificate expirations, registry token changes, cluster upgrades, and disaster recovery.
