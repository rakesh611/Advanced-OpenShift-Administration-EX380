# API Server Metrics in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift Administrators / Platform Engineers with ~10 years Linux, Kubernetes, DevOps, and operations experience  
**Scope:** OpenShift Container Platform 4.x platform monitoring, Prometheus/Thanos queries, API server SLOs, troubleshooting, alerting, and operational runbooks  
**Last updated:** 2026-07-03

---

## 1. Executive summary

In OpenShift, the API server is the main control-plane entry point. Every `oc`, `kubectl`, controller, Operator, scheduler, kubelet, CI/CD tool, GitOps controller, admission webhook, and custom application client ultimately depends on API server responsiveness.

API server metrics tell you whether the cluster control plane is healthy from four operational angles:

1. **Traffic**: How many requests are coming to the API server?
2. **Errors**: Are requests failing with `5xx`, authorization errors, authentication errors, webhook rejections, or throttling?
3. **Latency**: How long do API requests take at p50, p90, p95, and p99?
4. **Saturation**: Is the API server overloaded because of inflight request limits, API Priority and Fairness queues, long-running watches, etcd latency, webhook delay, or client storms?

For a senior OpenShift administrator, API server metrics are not just dashboard numbers. They are evidence for decisions such as:

- Is the cluster API available enough for production workloads?
- Is etcd causing API latency?
- Is a bad Operator flooding the API?
- Are admission webhooks slowing deployments?
- Are users or automation using deprecated APIs before an OpenShift upgrade?
- Are API Priority and Fairness queues protecting the platform or throttling important traffic?
- Is the issue in OpenShift, Kubernetes API machinery, etcd, network, authentication, authorization, or an external webhook?

## 2. What “API server” means in OpenShift

In vanilla Kubernetes, the central API component is `kube-apiserver`. In OpenShift, the control-plane API surface includes Kubernetes APIs plus OpenShift-specific APIs and authentication components.

Common API-related OpenShift components include:

| Component | Typical namespace | Purpose |
|---|---|---|
| Kubernetes API server | `openshift-kube-apiserver` | Handles Kubernetes API objects such as pods, services, deployments, secrets, RBAC, CRDs, and aggregated APIs. |
| OpenShift API server | `openshift-apiserver` | Handles OpenShift API groups such as routes, builds, deploymentconfigs, image streams, projects, templates, and OpenShift-specific authorization APIs. |
| OAuth/API authentication components | `openshift-authentication`, `openshift-oauth-apiserver` or version-dependent namespaces | Handles OpenShift OAuth login flows, identity provider integration, token review, and related auth APIs. |
| API server Operators | `openshift-kube-apiserver-operator`, `openshift-apiserver-operator`, etc. | Manage the lifecycle, rollout, certificates, configuration, and health of API server components. |
| etcd | `openshift-etcd` | Backing datastore for Kubernetes API state. API latency and etcd latency are tightly related. |

> Namespace and pod names can vary slightly by OpenShift version and topology. Always confirm with `oc get pods -A | grep -i apiserver` and `oc get co`.

Useful health checks:

```bash
oc get co kube-apiserver openshift-apiserver authentication etcd
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-apiserver -o wide
oc get pods -n openshift-authentication -o wide
oc get pods -n openshift-etcd -o wide
```

## 3. Where API server metrics fit in the OpenShift monitoring stack

OpenShift includes a preconfigured platform monitoring stack for core components. The stack is managed by the Cluster Monitoring Operator and includes Prometheus, Prometheus Operator, Thanos Querier, Alertmanager, Telemeter Client, and platform scrape targets.

High-level flow:

```text
API server /metrics endpoints
        |
        v
ServiceMonitor / scrape configuration managed by platform monitoring
        |
        v
Prometheus in openshift-monitoring
        |
        v
Thanos Querier for query federation and deduplication
        |
        v
OpenShift web console Observe > Metrics / Alerts / Dashboards
        |
        v
Alertmanager routes notifications
```

Important operational points:

- API server metrics are **platform metrics**, not application metrics.
- They are normally scraped by platform Prometheus in `openshift-monitoring`.
- Query them from the OpenShift console, Thanos Querier, or Prometheus API.
- Do not create your own duplicate scrape of the API server unless Red Hat support or a specific architecture requires it. Duplicate scraping can increase load and produce inconsistent dashboards.

## 4. How to access API server metrics

### 4.1 From OpenShift web console

Go to:

```text
Observe -> Metrics
```

Example PromQL:

```promql
sum(rate(apiserver_request_total[5m]))
```

For cluster administrators, the web console is usually the easiest place to validate queries quickly.

### 4.2 From CLI using Thanos Querier route

```bash
THANOS_HOST=$(oc -n openshift-monitoring get route thanos-querier -o jsonpath='{.spec.host}')
TOKEN=$(oc whoami -t)

curl -G -k \
  -H "Authorization: Bearer ${TOKEN}" \
  --data-urlencode 'query=sum(rate(apiserver_request_total[5m]))' \
  "https://${THANOS_HOST}/api/v1/query"
```

For range queries:

```bash
curl -G -k \
  -H "Authorization: Bearer ${TOKEN}" \
  --data-urlencode 'query=sum(rate(apiserver_request_total[5m]))' \
  --data-urlencode 'start=2026-07-03T00:00:00Z' \
  --data-urlencode 'end=2026-07-03T01:00:00Z' \
  --data-urlencode 'step=30s' \
  "https://${THANOS_HOST}/api/v1/query_range"
```

### 4.3 Direct raw API server metrics

As a cluster administrator, you can test whether the API server exposes metrics:

```bash
oc get --raw /metrics | grep '^apiserver_request_total' | head
oc get --raw /metrics | grep '^apiserver_request_duration_seconds_bucket' | head
```

This is good for confirming metric existence, but for real operational analysis use Prometheus/Thanos because they provide history, rate calculations, histograms, and alerting.

### 4.4 Validate monitoring targets

```bash
oc -n openshift-monitoring get pods
oc -n openshift-monitoring get prometheus
oc -n openshift-monitoring get servicemonitor,podmonitor | grep -i apiserver
```

If API server metrics are missing from Prometheus, investigate:

```bash
oc -n openshift-monitoring get pods | egrep 'prometheus|thanos|cluster-monitoring-operator'
oc -n openshift-monitoring logs deploy/cluster-monitoring-operator --tail=100
```

## 5. Key labels used by API server metrics

Most API server metrics are high-dimensional. Understanding labels is mandatory before writing production PromQL.

| Label | Meaning | Example |
|---|---|---|
| `verb` | API operation | `GET`, `LIST`, `WATCH`, `POST`, `PUT`, `PATCH`, `DELETE` |
| `resource` | Kubernetes/OpenShift resource | `pods`, `secrets`, `deployments`, `routes`, `customresourcedefinitions` |
| `subresource` | Subresource endpoint | `status`, `scale`, `log`, `exec` |
| `group` | API group | `apps`, `route.openshift.io`, `rbac.authorization.k8s.io` |
| `version` | API version | `v1`, `v1beta1` |
| `scope` | Resource scope | `cluster`, `namespace` |
| `code` | HTTP response code | `200`, `201`, `403`, `404`, `429`, `500` |
| `component` | API server component identity | often `apiserver` or version-specific value |
| `instance` | Scrape target instance | API server pod or endpoint |
| `job` | Prometheus scrape job | often contains `apiserver` |
| `dry_run` | Whether request was dry-run | empty or `All` |

### Cardinality warning

Avoid dashboards that group by too many labels at once. This is dangerous:

```promql
sum by (verb, resource, group, version, subresource, code, instance, component) (
  rate(apiserver_request_total[5m])
)
```

Better for first-level triage:

```promql
sum by (verb, resource, code) (
  rate(apiserver_request_total[5m])
)
```

For top offenders:

```promql
topk(20,
  sum by (verb, resource, code) (
    rate(apiserver_request_total[5m])
  )
)
```

## 6. Metric family 1: API request volume

### Metric

```text
apiserver_request_total
```

This counter tracks API server requests broken down by labels such as `verb`, `group`, `version`, `resource`, `subresource`, `scope`, `component`, `dry_run`, and HTTP `code`.

### What it tells you

- Overall API traffic level.
- Which resources are generating the most API load.
- Whether traffic is read-heavy or write-heavy.
- Whether a particular controller, Operator, or automation is creating request storms.
- Whether errors are concentrated on one resource, verb, or API group.

### Basic request rate

```promql
sum(rate(apiserver_request_total[5m]))
```

### Request rate by verb

```promql
sum by (verb) (
  rate(apiserver_request_total[5m])
)
```

### Request rate by resource

```promql
topk(20,
  sum by (resource) (
    rate(apiserver_request_total{resource!=""}[5m])
  )
)
```

### Request rate by verb and resource

```promql
topk(30,
  sum by (verb, resource) (
    rate(apiserver_request_total{resource!=""}[5m])
  )
)
```

### Error rate by HTTP code

```promql
sum by (code) (
  rate(apiserver_request_total{code=~"4..|5.."}[5m])
)
```

### 5xx error percentage

```promql
100 *
sum(rate(apiserver_request_total{code=~"5.."}[5m]))
/
sum(rate(apiserver_request_total[5m]))
```

### 429 throttling / rejection rate

```promql
sum by (verb, resource) (
  rate(apiserver_request_total{code="429"}[5m])
)
```

### Advanced interpretation

| Pattern | Meaning | First action |
|---|---|---|
| High `LIST` on many resources | Controllers repeatedly listing instead of watching efficiently | Identify client via audit logs and controller logs. |
| High `WATCH` | Many controllers, dashboards, CLI watches, or GitOps tools | Check long-running requests and watch metrics. |
| High `POST/PATCH/PUT` | Heavy writes, HPA/controller churn, GitOps sync storm, Operator loop | Identify resource and namespace, then client. |
| Many `403` | RBAC/authz denial pattern | Check user/service account permissions and automation config. |
| Many `404` | Broken clients calling missing resources/endpoints | Check client version, API migration, old CRDs. |
| Many `429` | API Priority and Fairness or inflight request pressure | Check APF queue and rejection metrics. |
| Many `5xx` | API server, etcd, webhook, aggregator, or internal server failure | Correlate with logs and etcd metrics. |

## 7. Metric family 2: API request latency

### Metric

```text
apiserver_request_duration_seconds_bucket
apiserver_request_duration_seconds_sum
apiserver_request_duration_seconds_count
```

This is a Prometheus histogram. Use `histogram_quantile()` to calculate percentiles.

### Cluster-wide p99 latency

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(apiserver_request_duration_seconds_bucket[5m])
  )
)
```

### p99 latency by verb

```promql
histogram_quantile(
  0.99,
  sum by (le, verb) (
    rate(apiserver_request_duration_seconds_bucket[5m])
  )
)
```

### p99 latency by resource and verb

```promql
topk(20,
  histogram_quantile(
    0.99,
    sum by (le, verb, resource) (
      rate(apiserver_request_duration_seconds_bucket{resource!=""}[5m])
    )
  )
)
```

### Read latency, excluding WATCH

`WATCH` requests are long-running by design. Do not mix them with normal `GET`/`LIST` latency when building dashboards.

```promql
histogram_quantile(
  0.99,
  sum by (le, verb, resource) (
    rate(apiserver_request_duration_seconds_bucket{verb=~"GET|LIST",resource!=""}[5m])
  )
)
```

### Write latency

```promql
histogram_quantile(
  0.99,
  sum by (le, verb, resource) (
    rate(apiserver_request_duration_seconds_bucket{verb=~"POST|PUT|PATCH|DELETE",resource!=""}[5m])
  )
)
```

### Advanced interpretation

API request latency includes time spent in request handling paths such as authentication, authorization, admission, API machinery, storage interaction, and response processing. It does not automatically prove that etcd is slow. You must correlate it with etcd, admission, APF, and control-plane node metrics.

| Latency pattern | Likely cause |
|---|---|
| High write latency for many resources | etcd storage latency, admission webhook delay, API server saturation |
| High latency only for one resource | CRD conversion webhook, aggregated API, bad Operator, large object size |
| High `LIST` latency | Large resource count, cache issue, expensive list selectors, many namespaces |
| High `WATCH` duration | Expected for long-running watches; evaluate watch count/events instead |
| High latency plus high 429 | API Priority and Fairness or inflight request limits |
| High latency plus high webhook metrics | Admission webhook is slow or unhealthy |

## 8. Metric family 3: Inflight and long-running requests

### Inflight requests

```text
apiserver_current_inflight_requests
```

This gauge shows currently used inflight request capacity by request kind.

```promql
sum by (request_kind) (
  apiserver_current_inflight_requests
)
```

High inflight requests mean the API server is actively processing many requests. If inflight remains high and latency increases, the API server may be saturated.

### Long-running requests

```text
apiserver_longrunning_requests
```

This tracks active long-running requests, often watches, logs, exec, port-forward, and similar streaming operations.

```promql
sum by (verb, resource, subresource) (
  apiserver_longrunning_requests
)
```

Watch-specific:

```promql
sum by (resource) (
  apiserver_longrunning_requests{verb="WATCH"}
)
```

### Why this matters

A cluster with many Operators, GitOps controllers, dashboards, and automation tools can have many watches. Watches are normal, but uncontrolled watch storms can increase API server memory, network traffic, and APF pressure.

## 9. Metric family 4: API Priority and Fairness metrics

API Priority and Fairness, usually called **APF**, classifies API requests into flow schemas and priority levels. It protects important system traffic from noisy clients and overload.

### Important APF metrics

```text
apiserver_flowcontrol_current_executing_requests
apiserver_flowcontrol_current_executing_seats
apiserver_flowcontrol_current_inqueue_requests
apiserver_flowcontrol_dispatched_requests_total
apiserver_flowcontrol_rejected_requests_total
apiserver_flowcontrol_request_wait_duration_seconds_bucket
apiserver_flowcontrol_nominal_limit_seats
```

### Current queued requests

```promql
sum by (priority_level, flow_schema) (
  apiserver_flowcontrol_current_inqueue_requests
)
```

### Rejected requests

```promql
sum by (priority_level, flow_schema, reason) (
  rate(apiserver_flowcontrol_rejected_requests_total[5m])
)
```

### APF p99 queue wait

```promql
histogram_quantile(
  0.99,
  sum by (le, priority_level, flow_schema) (
    rate(apiserver_flowcontrol_request_wait_duration_seconds_bucket[5m])
  )
)
```

### Seat usage

```promql
sum by (priority_level, flow_schema) (
  apiserver_flowcontrol_current_executing_seats
)
```

### Operational meaning

| APF signal | Meaning |
|---|---|
| Queue length grows | Requests are waiting before execution. |
| Queue wait p99 grows | Clients experience API delay even before normal API processing. |
| Rejections increase | APF is protecting the server by rejecting or timing out traffic. |
| One flow schema dominates | A specific client class or workload category is noisy. |
| System priority impacted | Critical control-plane traffic might be affected; investigate immediately. |

### Senior admin guidance

Do not immediately tune APF objects when you see queues. First identify the client and traffic pattern. APF tuning without understanding the workload can make the cluster less stable.

Recommended order:

1. Check whether latency and errors are actually user-impacting.
2. Identify top resources and verbs from `apiserver_request_total`.
3. Check APF flow schema and priority level.
4. Use audit logs or controller logs to identify client/user/service account.
5. Fix noisy client behavior before changing flow-control configuration.

## 10. Metric family 5: Admission controller and webhook metrics

Admission happens after authentication and authorization but before the object is persisted. OpenShift and Kubernetes use admission for validation, mutation, policy enforcement, image policy, security, quotas, SCC/Pod Security, webhooks, and many Operator integrations.

### Admission duration

```text
apiserver_admission_controller_admission_duration_seconds_bucket
apiserver_admission_webhook_admission_duration_seconds_bucket
```

### p99 admission webhook latency

```promql
histogram_quantile(
  0.99,
  sum by (le, name, type) (
    rate(apiserver_admission_webhook_admission_duration_seconds_bucket[5m])
  )
)
```

### Admission webhook request rate

```promql
sum by (name, type, operation, code, rejected) (
  rate(apiserver_admission_webhook_request_total[5m])
)
```

### Admission webhook rejection rate

```promql
sum by (name, type, operation, error_type, rejection_code) (
  rate(apiserver_admission_webhook_rejection_count[5m])
)
```

### Troubleshooting slow webhooks

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc describe validatingwebhookconfiguration <name>
oc describe mutatingwebhookconfiguration <name>
```

Check webhook service and endpoints:

```bash
oc get svc,endpoints -A | grep -i <webhook-service-name>
oc get pods -n <webhook-namespace> -o wide
oc logs -n <webhook-namespace> deploy/<webhook-deployment> --tail=200
```

### Common webhook failure causes

| Problem | Symptom |
|---|---|
| Webhook pod down | Create/update/delete requests fail or hang depending on `failurePolicy`. |
| No endpoints behind webhook service | API calls timeout or fail. |
| TLS certificate mismatch | API server cannot call webhook. |
| Webhook too slow | High admission latency and deployment delay. |
| Webhook rejects objects | Increase in rejection metrics and user-facing apply failures. |
| Bad webhook scope | Webhook intercepts too many resources/namespaces. |

## 11. Metric family 6: Authentication and authorization metrics

Authentication and authorization metrics help distinguish API server performance problems from identity/RBAC issues.

### Authentication attempts

```text
authentication_attempts
authentication_duration_seconds_bucket
```

Failed authentication rate:

```promql
sum by (result) (
  rate(authentication_attempts{result!="success"}[5m])
)
```

Authentication latency:

```promql
histogram_quantile(
  0.99,
  sum by (le, result) (
    rate(authentication_duration_seconds_bucket[5m])
  )
)
```

### Authorization attempts

```text
authorization_attempts_total
authorization_duration_seconds_bucket
```

Authorization denial/error rate:

```promql
sum by (result) (
  rate(authorization_attempts_total{result=~"denied|error"}[5m])
)
```

Authorization latency:

```promql
histogram_quantile(
  0.99,
  sum by (le, result) (
    rate(authorization_duration_seconds_bucket[5m])
  )
)
```

### Authenticated users metric

```text
authenticated_user_requests
```

This counter is useful but can be high-cardinality because it has a `username` label.

Top authenticated users by API request rate:

```promql
topk(20,
  sum by (username) (
    rate(authenticated_user_requests[5m])
  )
)
```

Use it carefully. It is excellent during incident triage, but avoid long-term dashboards that create huge user-level cardinality unless you have reviewed storage and privacy implications.

## 12. Metric family 7: Deprecated API usage

Deprecated APIs matter heavily during OpenShift upgrades. A cluster might be healthy today but fail upgrade readiness if workloads still depend on APIs removed in the target Kubernetes/OpenShift version.

### Metrics

```text
apiserver_requested_deprecated_apis
```

Query:

```promql
apiserver_requested_deprecated_apis
```

Group by removed release:

```promql
sum by (removed_release, group, version, resource, subresource) (
  apiserver_requested_deprecated_apis
)
```

### OpenShift APIRequestCount

OpenShift also provides `APIRequestCount` resources that help administrators identify API usage over time.

```bash
oc get apirequestcounts
oc get apirequestcounts <name> -o yaml
```

Find APIs with recent requests:

```bash
oc get apirequestcounts -o json \
  | jq -r '.items[] | select(.status.requestCount > 0) | .metadata.name'
```

### Upgrade runbook

1. Query deprecated API metrics.
2. Review `APIRequestCount` objects.
3. Identify workload, client, user agent, or namespace if available.
4. Update manifests, Helm charts, Operators, GitOps repos, and CI/CD templates.
5. Re-run checks for several days to ensure the deprecated API is no longer requested.
6. Only then proceed with upgrade acknowledgement when required.

## 13. Metric family 8: Watch metrics

Watches are essential to Kubernetes. Controllers watch objects and react to changes. But watch storms can hurt the API server.

Useful metrics include:

```text
apiserver_watch_events_total
apiserver_watch_events_sizes_bucket
apiserver_watch_cache_events_total
apiserver_watch_cache_initializations_total
apiserver_longrunning_requests
```

Watch event rate by resource:

```promql
sum by (group, version, resource) (
  rate(apiserver_watch_events_total[5m])
)
```

Long-running watches:

```promql
sum by (resource, group, version) (
  apiserver_longrunning_requests{verb="WATCH"}
)
```

### Watch storm indicators

- Sudden increase in `apiserver_longrunning_requests{verb="WATCH"}`.
- Sudden increase in `apiserver_watch_events_total` for one resource.
- API server CPU/network increases.
- Controllers reconnect repeatedly.
- Many clients list-then-watch in tight loops.
- Prometheus shows high `LIST` followed by high `WATCH` rates.

## 14. Correlating API server metrics with etcd

API server request latency often depends on etcd. Writes, resource versions, object lists, compaction, and watch cache behavior are tied to etcd health.

Useful etcd metrics:

```text
etcd_request_duration_seconds_bucket
etcd_disk_backend_commit_duration_seconds_bucket
etcd_disk_wal_fsync_duration_seconds_bucket
etcd_server_leader_changes_seen_total
etcd_server_has_leader
etcd_mvcc_db_total_size_in_bytes
```

### etcd p99 request latency

```promql
histogram_quantile(
  0.99,
  sum by (le, operation, type) (
    rate(etcd_request_duration_seconds_bucket[5m])
  )
)
```

### WAL fsync p99

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
  )
)
```

### Backend commit p99

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(etcd_disk_backend_commit_duration_seconds_bucket[5m])
  )
)
```

### Leader changes

```promql
sum(rate(etcd_server_leader_changes_seen_total[15m]))
```

### Interpretation

| API symptom | etcd correlation | Meaning |
|---|---|---|
| Write latency high + etcd fsync high | Storage backend slow | Check disk latency, IOPS, control-plane node health. |
| API errors + no etcd leader | etcd quorum/leader problem | Control-plane incident. Prioritize etcd recovery. |
| LIST latency high + etcd request latency high | Expensive reads/storage pressure | Check object counts and etcd health. |
| API latency high but etcd normal | Admission, APF, CPU, network, auth, aggregator, or webhook issue | Continue outside etcd path. |

## 15. API server SLO thinking

A practical API server SLO should measure real platform usability, not just pod health.

### Recommended golden signals

| Signal | Example metric/query |
|---|---|
| Availability | `up{job=~".*apiserver.*"}` and successful request ratio |
| Latency | `apiserver_request_duration_seconds_bucket` p95/p99 |
| Errors | `apiserver_request_total{code=~"5.."}` and selected `4xx` classes |
| Saturation | inflight requests, APF queues/rejections, CPU/memory, etcd latency |

### Example internal SLOs

These are examples. Adjust based on cluster size, workload type, OpenShift version, support guidance, and business requirements.

| SLO | Example target |
|---|---|
| API success ratio | `>= 99.9%` non-5xx over 30 days |
| Read p99 latency | `< 1s` for normal `GET/LIST` excluding `WATCH` |
| Write p99 latency | `< 2s-5s` depending on admission/webhook complexity |
| APF rejection rate | Near zero for critical/system traffic |
| API server target availability | All expected API server targets up |
| Deprecated API usage | Zero for APIs removed in target upgrade release |

### Success ratio query

```promql
100 *
(
  1 -
  sum(rate(apiserver_request_total{code=~"5.."}[5m]))
  /
  sum(rate(apiserver_request_total[5m]))
)
```

### Read p99 excluding WATCH

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(apiserver_request_duration_seconds_bucket{verb=~"GET|LIST"}[5m])
  )
)
```

### Write p99

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(apiserver_request_duration_seconds_bucket{verb=~"POST|PUT|PATCH|DELETE"}[5m])
  )
)
```

## 16. Dashboard design for API server metrics

A strong API server dashboard should have these panels:

### Panel 1: API server target health

```promql
up{job=~".*apiserver.*"}
```

### Panel 2: Total request rate

```promql
sum(rate(apiserver_request_total[5m]))
```

### Panel 3: Request rate by verb

```promql
sum by (verb) (rate(apiserver_request_total[5m]))
```

### Panel 4: Top resources by request rate

```promql
topk(20, sum by (resource) (rate(apiserver_request_total{resource!=""}[5m])))
```

### Panel 5: Error rate by code

```promql
sum by (code) (rate(apiserver_request_total{code=~"4..|5.."}[5m]))
```

### Panel 6: p99 latency read/write

Read:

```promql
histogram_quantile(0.99, sum by (le) (rate(apiserver_request_duration_seconds_bucket{verb=~"GET|LIST"}[5m])))
```

Write:

```promql
histogram_quantile(0.99, sum by (le) (rate(apiserver_request_duration_seconds_bucket{verb=~"POST|PUT|PATCH|DELETE"}[5m])))
```

### Panel 7: APF queues and rejections

```promql
sum by (priority_level) (apiserver_flowcontrol_current_inqueue_requests)
```

```promql
sum by (priority_level, reason) (rate(apiserver_flowcontrol_rejected_requests_total[5m]))
```

### Panel 8: Admission webhook latency


## 17. Alert examples

Before applying custom alerts, verify the supported alerting CRD in your OpenShift version:

```bash
oc api-resources | grep -E 'AlertingRule|PrometheusRule'
```

Some OpenShift versions support `AlertingRule` for platform alerting, while `PrometheusRule` is also widely used in Prometheus Operator based installations. Use your organization’s supported pattern.

### 17.1 AlertingRule example

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertingRule
metadata:
  name: api-server-slo-alerts
  namespace: openshift-monitoring
spec:
  groups:
  - name: api-server-slo.rules
    rules:
    - alert: APIHigh5xxErrorRate
      expr: |
        100 * sum(rate(apiserver_request_total{code=~"5.."}[5m]))
        /
        sum(rate(apiserver_request_total[5m])) > 1
      for: 10m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "API server 5xx error rate is above 1%"
        description: "The API server is returning elevated 5xx errors for more than 10 minutes. Check API server, etcd, webhooks, and control-plane node health."

    - alert: APIHighWriteLatencyP99
      expr: |
        histogram_quantile(
          0.99,
          sum by (le) (
            rate(apiserver_request_duration_seconds_bucket{verb=~"POST|PUT|PATCH|DELETE"}[5m])
          )
        ) > 5
      for: 15m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "API server write p99 latency is high"
        description: "Write request p99 latency is above 5 seconds. Correlate with etcd latency, admission webhooks, and APF queues."

    - alert: APIFlowControlRejections
      expr: |
        sum(rate(apiserver_flowcontrol_rejected_requests_total[5m])) > 0
      for: 10m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "API Priority and Fairness is rejecting requests"
        description: "APF rejected requests are non-zero. Identify priority_level, flow_schema, client, and request pattern."
```

### 17.2 PrometheusRule example

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-server-slo-alerts
  namespace: openshift-monitoring
  labels:
    prometheus: k8s
    role: alert-rules
spec:
  groups:
  - name: api-server-slo.rules
    rules:
    - alert: APIHighReadLatencyP99
      expr: |
        histogram_quantile(
          0.99,
          sum by (le) (
            rate(apiserver_request_duration_seconds_bucket{verb=~"GET|LIST"}[5m])
          )
        ) > 1
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "API server read p99 latency is high"
        description: "Read request p99 latency is above 1 second. Check top resources, etcd, API server CPU, and APF queues."
```

> Thresholds are examples. Production thresholds must be tuned with baseline data.



### Step 6: Emergency consideration

Changing or deleting webhooks can affect security and compliance. Before any emergency bypass, understand:

- `failurePolicy: Fail` means API requests fail if the webhook is unreachable.
- `failurePolicy: Ignore` means requests can continue if the webhook fails.
- Disabling a security webhook might allow non-compliant objects.
- In production, document the incident and restore policy after recovery.

## 19. Common false positives and mistakes

### Mistake 1: Treating WATCH latency as bad latency

`WATCH` requests are long-running. Exclude them from normal latency SLO dashboards.

Bad:

```promql
histogram_quantile(0.99, sum by (le) (rate(apiserver_request_duration_seconds_bucket[5m])))
```

Better:

```promql
histogram_quantile(0.99, sum by (le) (rate(apiserver_request_duration_seconds_bucket{verb!="WATCH"}[5m])))
```

### Mistake 2: Looking only at average latency

Average latency hides tail latency. Always check p95 and p99.

### Mistake 3: Ignoring resource and verb labels

Cluster-wide latency does not tell you whether the problem is `GET pods`, `PATCH deployments`, `LIST secrets`, or a CRD conversion issue.

### Mistake 4: Assuming every 4xx is a platform problem

Many `403` and `404` responses are client or RBAC issues, not API server outages.

### Mistake 5: Changing APF configuration too early

If APF is queueing, first find the noisy client. APF might be protecting the cluster correctly.

### Mistake 6: Ignoring admission webhooks

Slow admission webhooks are a common cause of create/update latency. Always check webhook metrics when write latency is high.

### Mistake 7: Ignoring etcd storage latency

If etcd fsync or request latency is high, API server write latency will often follow.

### Mistake 8: High-cardinality dashboards

Avoid permanent dashboards grouped by `username`, `instance`, `group`, `version`, `resource`, `subresource`, `code`, and `verb` all at once.

## 20. Practical senior-admin checklist

Use this checklist during any API server incident.

```text
[ ] Are all API server targets up?
[ ] Are kube-apiserver, openshift-apiserver, authentication, and etcd ClusterOperators Available=True?
[ ] Is request traffic higher than baseline?
[ ] Which verb/resource is highest?
[ ] Are 5xx errors present?
[ ] Are 429 errors or APF rejections present?
[ ] Is p99 latency high for reads, writes, or both?
[ ] Is WATCH traffic separated from normal request latency?
[ ] Are admission webhooks slow or rejecting requests?
[ ] Is etcd request/WAL/backend latency high?
[ ] Did a new Operator, webhook, GitOps sync, CI/CD job, or upgrade start recently?
[ ] Is a single user/service account generating abnormal request volume?
[ ] Are deprecated APIs in use before upgrade?
[ ] Are control-plane nodes CPU, memory, disk, and network healthy?
[ ] Are certificates, routes, or aggregated APIs failing?
[ ] Is must-gather needed for Red Hat support?
```

## 22. Exam/interview-style explanation

If asked in an interview, explain API server metrics like this:

> API server metrics in OpenShift are platform control-plane metrics scraped by the default monitoring stack. They show request rate, latency, error codes, inflight requests, APF queueing, admission webhook behavior, authentication and authorization activity, watch behavior, and deprecated API usage. I use `apiserver_request_total` for traffic and error rate, `apiserver_request_duration_seconds_bucket` for p95/p99 latency, `apiserver_current_inflight_requests` and APF metrics for saturation, admission webhook metrics for create/update delays, and etcd metrics for storage correlation. I never judge API health from pod status alone; I combine PromQL, ClusterOperator status, API server logs, etcd metrics, audit logs, and recent platform changes.

## 23. Real production scenarios

### Scenario 1: GitOps sync storm

Symptoms:

- Sudden increase in `PATCH` and `APPLY` style traffic.
- High request rate for deployments, configmaps, secrets, routes, or CRDs.
- APF queue grows.
- API server latency increases.

Actions:

- Check Argo CD/OpenShift GitOps sync frequency.
- Look for repeated OutOfSync/SelfHeal loops.
- Check invalid manifests causing continuous reconciliation.
- Reduce sync waves/concurrency if needed.

### Scenario 2: Bad Operator reconcile loop

Symptoms:

- One service account dominates `authenticated_user_requests`.
- High `GET/LIST/PATCH` for one CRD.
- Operator logs show repeated reconcile errors.

Actions:

- Identify service account and namespace.
- Inspect Operator logs.
- Fix CR status update loop, invalid permissions, missing dependency, or bad CR spec.

### Scenario 3: Slow validating webhook

Symptoms:

- `POST`/`PATCH` latency high.
- Webhook admission p99 high for one webhook.
- Deployments hang or fail.

Actions:

- Check webhook pods/endpoints.
- Check TLS and service DNS.
- Check webhook timeout and failure policy.
- Scale or fix webhook backend.

### Scenario 4: etcd disk latency

Symptoms:

- Write latency high across many resources.
- etcd WAL fsync/backend commit p99 high.
- Control-plane nodes show disk latency.

Actions:

- Check storage backend and IOPS.
- Check etcd pod/node health.
- Avoid disruptive operations until etcd stabilizes.
- Gather must-gather and involve Red Hat support if persistent.

### Scenario 5: Deprecated API before upgrade

Symptoms:

- `apiserver_requested_deprecated_apis` non-zero.
- `APIRequestCount` shows removed API usage.
- Upgrade path blocked or warning shown.

Actions:

- Identify clients and manifests.
- Update API versions.
- Replace old Operators/Helm charts.
- Observe for multiple days.

## 24. Recommended operational baseline

For each production cluster, capture a baseline during normal business periods:

| Baseline item | Why |
|---|---|
| Average and peak API request rate | Detect traffic storms. |
| Top 20 resources by request rate | Know normal noisy resources. |
| Read/write p95 and p99 latency | Define realistic alert thresholds. |
| 5xx and 429 normal rate | Detect abnormal failures. |
| APF queue wait and rejection rate | Understand saturation behavior. |
| Admission webhook p99 | Identify risky webhooks before incidents. |
| etcd WAL/backend p99 | Detect storage degradation early. |
| Deprecated API usage | Avoid upgrade surprises. |
| Top API users/service accounts | Identify noisy automation early. |

Store baseline screenshots or query outputs before major changes:

- OpenShift upgrades.
- New Operators.
- New admission webhooks.
- GitOps rollout.
- Major CI/CD onboarding.
- Large namespace/project onboarding.
- Control-plane node or storage changes.

## 26. Final takeaway

For advanced OpenShift administration, API server metrics are one of the most important control-plane observability areas. A healthy API server means the platform can schedule, reconcile, deploy, scale, authenticate, authorize, and recover. A degraded API server means the entire cluster feels slow or broken even if worker-node workloads are still running.

The senior approach is:

```text
Measure traffic -> measure errors -> measure latency -> measure saturation -> correlate with etcd/admission/APF/auth -> identify client/resource -> fix root cause
```

Do not stop at `oc get co`. Combine metrics, logs, events, audit data, and recent change history. That is the difference between basic monitoring and advanced OpenShift operations.
