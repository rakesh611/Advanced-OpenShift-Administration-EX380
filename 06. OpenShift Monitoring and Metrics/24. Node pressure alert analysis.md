## 1. Executive Summary

A **Node Pressure alert** means the node is approaching or has crossed a resource safety boundary. The kubelet is trying to protect the node from total resource starvation. In OpenShift, this normally appears through Kubernetes node conditions such as:

- `MemoryPressure=True`
- `DiskPressure=True`
- `PIDPressure=True`

When pressure exists, the scheduler can stop placing new pods on that node through automatic taints, and the kubelet can start reclaiming resources. If reclaim is not enough, kubelet can evict pods.

The important senior-admin mindset is this:

> A node pressure alert is not only a capacity alert. It is a scheduling, eviction, workload reliability, and node stability incident.

A junior admin often checks only `oc adm top node`. A senior admin correlates:

- node condition
- taint
- kubelet eviction signal
- events
- Prometheus metrics
- pod QoS and requests
- recent deployments
- CRI-O/image/log usage
- system-reserved sizing
- MachineConfigPool status
- node role: worker, infra, master/control-plane, ODF, logging, GPU, etc.

## 2. What “Node Pressure” Means

In Kubernetes and OpenShift, **pressure** means kubelet has detected that a critical node-local resource is below a safe threshold.

Typical resources involved:

| Pressure condition | Resource problem | Common production meaning |
|---|---|---|
| `MemoryPressure` | Available node memory is low | Workloads or system daemons are consuming too much memory; pods might be evicted or OOM killed. |
| `DiskPressure` | Filesystem space or inode availability is low | Logs, images, writable layers, `emptyDir`, dead containers, or inode exhaustion are threatening node stability. |
| `PIDPressure` | Available process IDs are low | Too many processes/threads are running; new processes or containers might fail to start. |

OpenShift also has metrics for CPU saturation, CPU throttling, and Linux Pressure Stall Information (PSI), but Kubernetes does **not** normally expose a `CPUPressure=True` node condition in the same way as memory, disk, and PID pressure.

## 3. Pressure Conditions vs Alerts vs Taints

These three are related but different.

### 3.1 Node condition

A node condition is status written on the Kubernetes `Node` object by kubelet.

Example:

```bash
oc get node worker-1 -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

Possible output:

```text
MemoryPressure=False reason=KubeletHasSufficientMemory message=kubelet has sufficient memory available
DiskPressure=True reason=KubeletHasDiskPressure message=kubelet has disk pressure
PIDPressure=False reason=KubeletHasSufficientPID message=kubelet has sufficient PID available
Ready=True reason=KubeletReady message=kubelet is posting ready status
```

Important: a node can be `Ready=True` and still have `DiskPressure=True` or `MemoryPressure=True`.

### 3.2 Alert

An alert is generated by Prometheus/Thanos based on metrics.

Common metric behind pressure alerts:

```promql
kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"} == 1
```

The exact alert name depends on OpenShift version and the rule set shipped with the monitoring stack. You might see names such as:

- `KubeNodePressure`
- `KubeNodeDiskPressure`
- `KubeNodeMemoryPressure`
- `KubeNodePIDPressure`
- a custom company-specific node pressure alert

Always confirm the actual alerting rule in your cluster:

```bash
oc -n openshift-monitoring get prometheusrule -o yaml | grep -n "KubeNode\|Pressure\|DiskPressure\|MemoryPressure\|PIDPressure" -C 5
```

Or from the web console:

```text
Administrator perspective -> Observe -> Alerting -> Alerting Rules
```

### 3.3 Taint

When pressure conditions are active, Kubernetes/OpenShift can map them to taints. These taints stop new pods from being scheduled on the unhealthy node unless pods tolerate them.

Typical automatic taints:

```text
node.kubernetes.io/memory-pressure
node.kubernetes.io/disk-pressure
node.kubernetes.io/pid-pressure
```

Check taints:

```bash
oc get node worker-1 -o jsonpath='{range .spec.taints[*]}{.key}{"="}{.value}{":"}{.effect}{"\n"}{end}'
```

If `DiskPressure=True`, the node may show:

```text
node.kubernetes.io/disk-pressure=:NoSchedule
```

This means new pods will not be scheduled there unless they tolerate the taint.

## 4. How OpenShift Monitoring Detects Node Pressure

OpenShift Monitoring includes several components relevant to this topic:

| Component | Role |
|---|---|
| `prometheus-k8s` | Scrapes platform metrics in `openshift-monitoring`. |
| `thanos-querier` | Provides a query layer across Prometheus instances. |
| `kube-state-metrics` | Exposes Kubernetes object state, including node conditions and taints. |
| `node-exporter` | Exposes host-level Linux metrics such as memory, filesystem, CPU, load, network. |
| `kubelet` / cAdvisor metrics | Expose container, volume, pod, runtime, and eviction-relevant metrics. |
| `Alertmanager` | Groups, routes, silences, and sends alerts. |

A node pressure alert usually starts from this chain:

```text
Node resource shortage
        ↓
kubelet observes eviction signal
        ↓
kubelet sets Node condition=True
        ↓
kube-state-metrics exposes kube_node_status_condition
        ↓
Prometheus evaluates alert rule
        ↓
Alertmanager sends notification
        ↓
Admin investigates node + workload + runtime + filesystem
```

A simplified Prometheus rule often looks like:

```yaml
expr: kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"} == 1
for: 10m
labels:
  severity: warning
annotations:
  summary: Node {{ $labels.node }} is under {{ $labels.condition }}
```

Production rules often add labels such as `cluster`, `node`, `condition`, `severity`, `namespace`, `prometheus`, `service`, or `job`.

## 5. Kubelet Eviction Model

Node pressure is tightly connected to kubelet eviction.

The kubelet continuously monitors node-local resources. If eviction thresholds are crossed, kubelet first tries node-level reclaim. If reclaim does not bring the node below threshold, kubelet starts evicting pods.

### 5.1 Eviction signals

Important Linux eviction signals include:

| Signal | Meaning |
|---|---|
| `memory.available` | Available memory calculated by kubelet, not simply `free -m`. |
| `nodefs.available` | Free space on node filesystem, commonly root filesystem or `/var` layout. |
| `nodefs.inodesFree` | Free inodes on node filesystem. |
| `imagefs.available` | Free space on container runtime image filesystem, if separate. |
| `imagefs.inodesFree` | Free inodes on image filesystem. |
| `containerfs.available` | Free space on container writable-layer filesystem, if split from imagefs. |
| `containerfs.inodesFree` | Free inodes on container writable-layer filesystem. |
| `pid.available` | Available process IDs. |

### 5.2 Condition mapping

Kubelet maps eviction signals to node conditions:

| Node condition | Trigger signals |
|---|---|
| `MemoryPressure` | `memory.available` |
| `DiskPressure` | `nodefs.available`, `nodefs.inodesFree`, `imagefs.available`, `imagefs.inodesFree`, `containerfs.available`, `containerfs.inodesFree` |
| `PIDPressure` | `pid.available` |

### 5.3 Node-pressure eviction is not graceful application maintenance

During node-pressure eviction:

- kubelet can mark selected pods as `Failed`
- PodDisruptionBudget is not treated the same as API-initiated eviction
- hard eviction thresholds can cause immediate termination
- workload controllers such as Deployment/StatefulSet later create replacement pods
- replacement pods might schedule to another healthy node if capacity exists

This matters because a node pressure incident can become an application availability incident even when the Kubernetes control plane remains healthy.

## 6. Node Pressure Types

### 6.1 MemoryPressure

`MemoryPressure=True` means kubelet believes available memory has crossed an eviction threshold.

Common reasons:

- workload memory leak
- too many pods on node
- missing or unrealistic memory requests
- BestEffort pods consuming memory
- Burstable pods exceeding requests
- system daemons consuming more memory than reserved
- CRI-O/kubelet/system slice pressure
- ODF/logging/monitoring workloads placed on undersized nodes
- memory fragmentation or page cache behavior misunderstood by admins

Important senior-level point:

> `oc adm top node` shows usage, but kubelet eviction uses its own `memory.available` calculation. Do not rely only on `free -m` or top output.

### 6.2 DiskPressure

`DiskPressure=True` means disk space or inode availability crossed an eviction threshold.

Common reasons:

- container logs growing rapidly
- application writes large data to container writable layer
- `emptyDir` usage without limits
- image pull storms
- unused images not garbage collected fast enough
- dead containers/pods accumulating
- `/var/log` or journald growth
- inode exhaustion from many small files
- separate `imagefs` or `nodefs` pressure
- local storage workloads wrongly using node filesystem
- monitoring/logging agents buffering large queues

Important senior-level point:

> Disk pressure can be caused by inode exhaustion even when `df -h` looks fine. Always check `df -ih`.

### 6.3 PIDPressure

`PIDPressure=True` means process/thread availability is low.

Common reasons:

- application fork bomb
- JVM/thread pool explosion
- sidecars creating excessive processes
- many pods with high process count
- stuck process creation loops
- node `podPidsLimit` too high for density
- too many pods per node

Important senior-level point:

> PID pressure is often not visible in CPU or memory dashboards at first. Check process/thread counts directly.

## 7. Production Impact Analysis

When an alert fires, do not ask only “which node is full?” Ask these production-impact questions:

### 7.1 Which node role is affected?

```bash
oc get node <node> --show-labels
```

Impact differs by role:

| Node type | Risk |
|---|---|
| Worker node | Application pods might be evicted or blocked from scheduling. |
| Infra node | Router, registry, monitoring, logging, ingress availability can be affected. |
| Control plane node | API server, scheduler, controller-manager, etcd static pods can be affected. Higher severity. |
| ODF/storage node | Storage I/O, Ceph pods, PV availability, and data-plane stability can be affected. |
| Logging/monitoring node | Observability pipeline might degrade; alerts might become noisy or delayed. |

### 7.2 Is this isolated or cluster-wide?

```bash
oc get nodes
oc get nodes -o custom-columns=NAME:.metadata.name,READY:.status.conditions[-1].status,TAINTS:.spec.taints
```

PromQL:

```promql
sum by (condition) (kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"})
```

One node usually indicates local workload/runtime/filesystem issue. Many nodes at once usually indicates:

- bad rollout
- logging storm
- image pull storm
- cluster capacity issue
- wrong MachineConfig/KubeletConfig
- common base image behavior
- monitoring/logging/sidecar issue
- infrastructure/storage outage

### 7.3 Are pods already evicted?

```bash
oc get pods -A --field-selector=status.phase=Failed -o wide | grep -i Evicted
```

### 7.4 Is scheduling blocked?

```bash
oc describe node <node> | egrep -A5 -i "Taints|Conditions|Allocated resources|Events"
```

Look for:

```text
Taints: node.kubernetes.io/disk-pressure:NoSchedule
```

### 7.5 Is the alert flapping?

PromQL:

```promql
changes(kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure"}[2h])
```

Frequent changes indicate oscillation around thresholds. That usually means the node is close to the edge and will repeatedly evict or block scheduling.

## 8. Immediate Triage Workflow

Use this workflow during an incident.

### Step 1: Identify alert labels

From Alertmanager or OpenShift Alerting UI, capture:

- `alertname`
- `cluster`
- `node`
- `condition`
- `severity`
- `startsAt`
- `for` duration
- `runbook_url`, if present

### Step 2: Confirm node condition

```bash
NODE=<node-name>
oc get node "$NODE"
oc describe node "$NODE"
```

Focused condition output:

```bash
oc get node "$NODE" -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" lastTransition="}{.lastTransitionTime}{" message="}{.message}{"\n"}{end}'
```

### Step 3: Confirm pressure taint

```bash
oc get node "$NODE" -o jsonpath='{range .spec.taints[*]}{.key}{":"}{.effect}{"\n"}{end}'
```

### Step 4: Check top-level resource usage

```bash
oc adm top node "$NODE"
oc adm top pods -A --sort-by=memory | head -30
oc adm top pods -A --sort-by=cpu | head -30
```

### Step 5: List pods on the node

```bash
oc get pods -A --field-selector spec.nodeName="$NODE" -o wide
```

With requests/limits view:

```bash
oc describe node "$NODE" | sed -n '/Allocated resources:/,/Events:/p'
```

### Step 6: Check node events

```bash
oc get events -A --sort-by=.lastTimestamp | grep "$NODE" | tail -50
```

Or:

```bash
oc describe node "$NODE" | sed -n '/Events:/,$p'
```

### Step 7: Enter node debug shell

```bash
oc debug node/"$NODE"
chroot /host
```

Then collect:

```bash
df -hT
df -ih
free -h
cat /proc/meminfo | head -40
journalctl -u kubelet --since "-2 hours" | egrep -i "pressure|evict|eviction|imagegc|garbage|memory|disk|inode|pid|oom" | tail -200
journalctl -u crio --since "-2 hours" | egrep -i "error|warn|no space|image|overlay|oom|pid" | tail -200
```

### Step 8: Decide immediate containment

Possible actions:

- cordon node to stop new scheduling
- scale down or restart offender workload
- clean safe logs/images if disk pressure
- add capacity
- drain node if safe
- create temporary alert silence if remediation is already in progress

Do **not** blindly reboot the node until you know whether it hosts critical pods, control plane static pods, ODF, router, registry, or only one replica of a workload.

## 9. Command-Line Investigation Runbook

### 9.1 Set variables

```bash
NODE=<node-name>
```

### 9.2 Cluster health snapshot

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes -o wide
```

If `MachineConfigPool` is updating or degraded, node pressure might be related to reboot, kubelet config rollout, image pull, or node replacement activity.

### 9.3 Node condition and taints

```bash
oc describe node "$NODE"

oc get node "$NODE" -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.lastTransitionTime}{"\t"}{.message}{"\n"}{end}'

oc get node "$NODE" -o jsonpath='{range .spec.taints[*]}{.key}{"\t"}{.value}{"\t"}{.effect}{"\n"}{end}'
```

### 9.4 Pods running on the node

```bash
oc get pods -A --field-selector spec.nodeName="$NODE" -o wide
```

Find high-memory pods:

```bash
oc adm top pods -A --sort-by=memory | head -30
```

Find high-CPU pods:

```bash
oc adm top pods -A --sort-by=cpu | head -30
```

Find failed/evicted pods:

```bash
oc get pods -A --field-selector=status.phase=Failed -o wide | egrep -i "Evicted|$NODE"
```

### 9.5 Events

```bash
oc get events -A --sort-by=.lastTimestamp | egrep -i "$NODE|Evicted|Preempt|FailedScheduling|DiskPressure|MemoryPressure|PIDPressure|insufficient|no space|out of"
```

### 9.6 Kubelet logs from OpenShift

```bash
oc adm node-logs "$NODE" -u kubelet --since=2h | egrep -i "pressure|evict|eviction|threshold|imagegc|garbage|memory|disk|inode|pid|oom" | tail -200
```

CRI-O logs:

```bash
oc adm node-logs "$NODE" -u crio --since=2h | egrep -i "error|warn|no space|overlay|image|oom|pid|failed" | tail -200
```

### 9.7 Node filesystem from debug shell

```bash
oc debug node/"$NODE"
chroot /host

df -hT
df -ih
mount | egrep '/var|/sysroot|containers|kubelet'
lsblk
```

Large directories:

```bash
du -xhd1 /var 2>/dev/null | sort -h
du -xhd1 /var/lib 2>/dev/null | sort -h
du -xhd1 /var/lib/kubelet 2>/dev/null | sort -h
du -xhd1 /var/lib/containers 2>/dev/null | sort -h
du -xhd1 /var/log 2>/dev/null | sort -h
```

Large files:

```bash
find /var -xdev -type f -size +500M -ls 2>/dev/null | sort -k7 -n | tail -50
```

Inode-heavy directories:

```bash
find /var -xdev -type d -print 2>/dev/null | while read d; do c=$(find "$d" -maxdepth 1 -xdev 2>/dev/null | wc -l); echo "$c $d"; done | sort -nr | head -30
```

### 9.8 Runtime data

Inside node debug chroot:

```bash
crictl ps -a | head -50
crictl images | head -50
crictl stats
```

Do not remove runtime data blindly. In emergency disk-pressure cases, you may consider pruning unused images only after validating impact and change-control policy:

```bash
crictl rmi --prune
```

Prefer fixing the cause and tuning kubelet image garbage collection rather than repeatedly doing manual cleanup.

## 10. PromQL Investigation Library

Run these from:

```text
OpenShift web console -> Observe -> Metrics
```

or through Thanos/Prometheus API if you have access.

### 10.1 Which nodes are under pressure?

```promql
kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"} == 1
```

### 10.2 Count pressure nodes by condition

```promql
sum by (condition) (
  kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"}
)
```

### 10.3 Pressure flapping in last 2 hours

```promql
changes(kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure"}[2h])
```

### 10.4 Node taints created by pressure

```promql
kube_node_spec_taint{key=~"node.kubernetes.io/(memory-pressure|disk-pressure|pid-pressure)"}
```

### 10.5 Node memory utilization

```promql
100 * (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes))
```

Per node:

```promql
100 * (1 - (node_memory_MemAvailable_bytes{instance=~".*"} / node_memory_MemTotal_bytes{instance=~".*"}))
```

### 10.6 Top pods by memory working set

```promql
topk(20,
  sum by (namespace, pod) (
    container_memory_working_set_bytes{container!="",pod!=""}
  )
)
```

### 10.7 CRI-O OOM kills

OpenShift node metrics dashboard includes CRI-O OOM-kill style queries. A useful starting point is:

```promql
topk(20,
  sum by (name) (
    increase(container_runtime_crio_containers_oom_count_total[1d])
  )
)
```

Metric labels can vary by OpenShift version. If `name` is not useful, inspect available labels in the Metrics UI.

### 10.8 Node filesystem usage

Root filesystem usage:

```promql
100 * (1 - (
  node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs|overlay"}
  /
  node_filesystem_size_bytes{mountpoint="/",fstype!~"tmpfs|overlay"}
))
```

All filesystems by node/mount:

```promql
100 * (1 - (
  node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}
  /
  node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}
))
```

### 10.9 Inode usage

```promql
100 * (1 - (
  node_filesystem_files_free{fstype!~"tmpfs|overlay"}
  /
  node_filesystem_files{fstype!~"tmpfs|overlay"}
))
```

### 10.10 Container writable layer / filesystem usage

```promql
topk(20,
  sum by (namespace, pod, container) (
    container_fs_usage_bytes{container!="",pod!=""}
  )
)
```

### 10.11 PVC usage is not the same as node disk pressure

PVC usage can cause application problems, but PVC usage usually does not directly equal node filesystem pressure unless local storage or host paths are involved.

PVC query:

```promql
100 * kubelet_volume_stats_used_bytes / kubelet_volume_stats_capacity_bytes
```

Use it to distinguish PVC-full from node-root-filesystem-full.

### 10.12 PID/process usage, if exposed

Some clusters expose container process metrics:

```promql
topk(20,
  sum by (namespace, pod, container) (
    container_processes{container!="",pod!=""}
  )
)
```

If this metric is unavailable, investigate from the node with `ps -eLf`.

### 10.13 CPU throttling is not NodePressure, but it helps explain symptoms

```promql
topk(20,
  sum by (namespace, pod, container) (
    rate(container_cpu_cfs_throttled_periods_total{container!="",pod!=""}[5m])
  )
  /
  sum by (namespace, pod, container) (
    rate(container_cpu_cfs_periods_total{container!="",pod!=""}[5m])
  )
)
```

High throttling does not set `CPUPressure=True`, but it can cause latency, probes failing, slow image unpacking, slow log processing, and cascading workload instability.

### 10.14 PSI metrics discovery

If Linux PSI is enabled, discover pressure-related metrics:

```promql
{__name__=~".*pressure.*"}
```

Or inspect `/proc/pressure` from a node debug shell:

```bash
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

## 11. Memory Pressure Deep Dive

### 11.1 Symptoms

You might see:

```text
MemoryPressure=True
node.kubernetes.io/memory-pressure:NoSchedule
The node was low on resource: memory
Evicted
OOMKilled
FailedScheduling: node(s) had untolerated taint {node.kubernetes.io/memory-pressure: }
```

### 11.2 First checks

```bash
NODE=<node>

oc adm top node "$NODE"
oc adm top pods -A --sort-by=memory | head -30
oc describe node "$NODE" | sed -n '/Allocated resources:/,/Events:/p'
oc get pods -A --field-selector spec.nodeName="$NODE" -o wide
```

### 11.3 Check pod requests and limits

A common root cause is that pods are scheduled because requests are low, but real usage is much higher.

```bash
oc get pods -A --field-selector spec.nodeName="$NODE" -o json \
  | jq -r '.items[] | [.metadata.namespace,.metadata.name, (.spec.containers[]? | .name + " reqMem=" + ((.resources.requests.memory // "none")|tostring) + " limMem=" + ((.resources.limits.memory // "none")|tostring))] | @tsv'
```

If `jq` is unavailable, use:

```bash
oc describe node "$NODE" | sed -n '/Non-terminated Pods:/,/Allocated resources:/p'
```

### 11.4 Understand QoS classes

Kubernetes classifies pods as:

| QoS class | Memory behavior |
|---|---|
| `Guaranteed` | Every container has memory request and limit, and request equals limit. Usually last to evict. |
| `Burstable` | Has some requests/limits, but not fully equal. Can be evicted if usage exceeds request. |
| `BestEffort` | No requests/limits. Usually first risk under pressure. |

Check QoS:

```bash
oc get pods -A --field-selector spec.nodeName="$NODE" -o custom-columns=NS:.metadata.namespace,POD:.metadata.name,QOS:.status.qosClass,NODE:.spec.nodeName
```

### 11.5 Node-level memory checks

```bash
oc debug node/"$NODE"
chroot /host

free -h
cat /proc/meminfo | egrep 'MemTotal|MemFree|MemAvailable|Buffers|Cached|Swap|Active|Inactive|Slab|SReclaimable|SUnreclaim'
ps -eo pid,ppid,comm,%mem,rss,args --sort=-rss | head -30
systemd-cgtop
```

### 11.6 Kubelet and CRI-O memory issues

Check logs:

```bash
journalctl -u kubelet --since "-2 hours" | egrep -i "memory|evict|threshold|oom|pressure" | tail -200
journalctl -u crio --since "-2 hours" | egrep -i "memory|oom|error|warn" | tail -200
```

Check system slice pressure:

```bash
systemctl status kubelet crio
systemd-cgtop
```

### 11.7 Common memory-pressure causes

| Cause | Evidence | Fix |
|---|---|---|
| App memory leak | One pod memory climbs steadily | Fix app, restart temporarily, add proper limits. |
| Missing requests | Many pods have no memory requests | Enforce LimitRange/ResourceQuota, set requests. |
| Overcommit | Allocated requests close to allocatable, usage higher | Add nodes or increase node size. |
| System daemons under-reserved | `system.slice` high, kubelet/CRI-O memory high | Review `systemReserved`, node sizing, OpenShift version guidance. |
| Logging/monitoring heavy | Fluent/log collector/prometheus high memory | Tune log volume, retention, resource limits. |
| Too many pods per node | High pod density | Reduce `maxPods`, add nodes, tune workload spread. |

### 11.8 Senior-level remediation

Immediate:

```bash
oc adm cordon "$NODE"
```

Find offender:

```bash
oc adm top pods -A --sort-by=memory | head -30
```

Scale or restart safely:

```bash
oc -n <ns> rollout restart deploy/<deploy>
# or
oc -n <ns> scale deploy/<deploy> --replicas=<lower-number>
```

Long-term:

- set realistic memory requests and limits
- enforce namespace `LimitRange`
- use `ResourceQuota`
- use HPA based on CPU/memory/custom metrics where suitable
- use topology spread constraints to avoid hot nodes
- size infra/monitoring/ODF nodes separately
- review `systemReserved`
- reduce pod density if necessary

## 12. Disk Pressure Deep Dive

### 12.1 Symptoms

You might see:

```text
DiskPressure=True
node.kubernetes.io/disk-pressure:NoSchedule
The node was low on resource: ephemeral-storage
failed to garbage collect required amount of images
no space left on device
write /var/lib/containers/storage/overlay: no space left on device
FailedScheduling: node(s) had untolerated taint {node.kubernetes.io/disk-pressure: }
```

### 12.2 Disk pressure can be bytes or inodes

Always check both:

```bash
oc debug node/"$NODE"
chroot /host

df -hT
df -ih
```

`df -h` might show free GB while `df -ih` shows inode exhaustion.

### 12.3 Identify whether root, `/var`, kubelet, or container storage is affected

```bash
mount | egrep '/var|containers|kubelet|sysroot'
lsblk
findmnt
```

Large directories:

```bash
du -xhd1 /var 2>/dev/null | sort -h
du -xhd1 /var/lib 2>/dev/null | sort -h
du -xhd1 /var/lib/kubelet 2>/dev/null | sort -h
du -xhd1 /var/lib/containers 2>/dev/null | sort -h
du -xhd1 /var/log 2>/dev/null | sort -h
```

### 12.4 Check logs

Container stdout/stderr logs are a common source.

```bash
du -xhd1 /var/log 2>/dev/null | sort -h
find /var/log -xdev -type f -size +500M -ls 2>/dev/null | sort -k7 -n | tail -50
journalctl --disk-usage
```

Pod logs under kubelet:

```bash
du -xhd1 /var/log/pods 2>/dev/null | sort -h | tail -30
find /var/log/pods -xdev -type f -size +500M -ls 2>/dev/null | sort -k7 -n | tail -50
```

### 12.5 Check container runtime storage

```bash
du -xhd1 /var/lib/containers/storage 2>/dev/null | sort -h
crictl images | head -50
crictl ps -a | head -50
```

Image cache growth usually appears under:

```text
/var/lib/containers/storage
```

Pod volumes and `emptyDir` often appear under:

```text
/var/lib/kubelet/pods/<pod-uid>/volumes/
```

### 12.6 Identify pod-level ephemeral storage usage

PromQL:

```promql
topk(20,
  sum by (namespace, pod, container) (
    container_fs_usage_bytes{container!="",pod!=""}
  )
)
```

CLI approximation from node:

```bash
du -xhd2 /var/lib/kubelet/pods 2>/dev/null | sort -h | tail -50
```

Map pod UID to pod:

```bash
oc get pods -A -o custom-columns=NS:.metadata.namespace,POD:.metadata.name,UID:.metadata.uid,NODE:.spec.nodeName | grep <pod-uid>
```

### 12.7 Inode exhaustion investigation

```bash
df -ih
find /var -xdev -type d -print 2>/dev/null | while read d; do c=$(find "$d" -maxdepth 1 -xdev 2>/dev/null | wc -l); echo "$c $d"; done | sort -nr | head -50
```

Common inode-heavy offenders:

- application cache directories
- millions of tiny temp files
- log shippers buffering small files
- build tools writing node_modules-like trees
- CI/CD jobs using `emptyDir`
- Git checkout workspaces

### 12.8 Deleted-but-open files

Sometimes `du` and `df` disagree. A process might hold a deleted file open.

If `lsof` is available:

```bash
lsof +L1
```

On minimal RHCOS, `lsof` might not be present. Use process investigation and service restart carefully when `df` remains high after file deletion.

### 12.9 Disk-pressure remediation

Immediate safe options:

- cordon the node
- stop or scale down the offender workload
- delete unnecessary failed pods
- reduce log storm
- allow kubelet image GC to reclaim unused images
- prune unused runtime images only during emergency and with caution
- expand node disk or replace node with larger root/var disk

Commands:

```bash
oc adm cordon "$NODE"
```

Find evicted/failed pods:

```bash
oc get pods -A --field-selector=status.phase=Failed -o wide | grep "$NODE"
```

Delete old evicted pods only if you are sure they are not needed for evidence:

```bash
oc get pods -A --field-selector=status.phase=Failed -o name | xargs -r -n1 oc delete
```

Be careful: the above command across all namespaces is aggressive. In production, filter namespace, age, and reason.

### 12.10 Long-term disk fixes

- set `ephemeral-storage` requests and limits
- set `emptyDir.sizeLimit`
- fix applications that write large data to container filesystem
- move persistent data to PVCs
- tune app log level
- implement log sampling/rate-limiting
- verify container log rotation
- tune image garbage collection thresholds
- use separate, larger disks for `/var` or container storage where design allows
- keep node image cache under control
- prevent build workloads from running on general application nodes

Example container resource policy:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 256Mi
    ephemeral-storage: 512Mi
  limits:
    cpu: 500m
    memory: 512Mi
    ephemeral-storage: 1Gi
```

Example `emptyDir` limit:

```yaml
volumes:
- name: cache
  emptyDir:
    sizeLimit: 1Gi
```

## 13. PID Pressure Deep Dive

### 13.1 Symptoms

You might see:

```text
PIDPressure=True
node.kubernetes.io/pid-pressure:NoSchedule
fork: Resource temporarily unavailable
cannot allocate memory
failed to create container process
runtime create failed
```

PID pressure is usually caused by too many processes or threads.

### 13.2 Node checks

```bash
oc debug node/"$NODE"
chroot /host

cat /proc/sys/kernel/pid_max
cat /proc/sys/kernel/threads-max
ps -eLf | wc -l
ps -eLf -o pid,ppid,nlwp,comm,args --sort=-nlwp | head -30
```

Count processes per user:

```bash
ps -eLo user | sort | uniq -c | sort -nr | head
```

Count threads by command:

```bash
ps -eLf -o comm= | sort | uniq -c | sort -nr | head -30
```

### 13.3 Pod-level clues

```bash
oc get pods -A --field-selector spec.nodeName="$NODE" -o wide
oc adm top pods -A --sort-by=cpu | head -30
```

High process count might not mean high CPU. A sleeping thread explosion can cause PID pressure while CPU appears moderate.

### 13.4 Common PID-pressure causes

| Cause | Evidence | Fix |
|---|---|---|
| Fork bomb | Huge number of similar processes | Kill/restart offending pod, fix app. |
| Thread leak | One app has thousands of threads | Tune thread pools, patch app. |
| Too many sidecars | Many pods each run several processes | Reduce sidecars, reduce density. |
| CI workload | Build/test jobs spawn many short-lived processes | Isolate CI nodes, set limits. |
| Wrong pod density | High `maxPods`, high process count | Reduce density, add nodes. |

### 13.5 Long-term PID fixes

- define sane application thread pool limits
- isolate build/CI workloads
- reduce pods per node where necessary
- configure pod PID limits if appropriate
- use `LimitRange`/policy for resource governance
- monitor process count trends

## 14. CPU Pressure, CPU Saturation, and PSI

Kubernetes node conditions include memory, disk, and PID pressure, but not a standard `CPUPressure=True` condition.

However, CPU starvation can still cause serious symptoms:

- API latency
- kubelet heartbeats delayed
- probes failing
- workload latency
- image pull/unpack slow
- log agents falling behind
- Prometheus scrape timeout
- CRI-O operations delayed

### 14.1 CPU saturation checks

```bash
oc adm top node "$NODE"
oc adm top pods -A --sort-by=cpu | head -30
```

Node debug:

```bash
oc debug node/"$NODE"
chroot /host

uptime
mpstat -P ALL 1 5  # if available
pidstat 1 5        # if available
top
```

### 14.2 CPU throttling PromQL

```promql
topk(20,
  sum by (namespace, pod, container) (
    rate(container_cpu_cfs_throttled_periods_total{container!="",pod!=""}[5m])
  )
  /
  sum by (namespace, pod, container) (
    rate(container_cpu_cfs_periods_total{container!="",pod!=""}[5m])
  )
)
```

### 14.3 PSI in OpenShift

Linux Pressure Stall Information (PSI) can expose how much time tasks are stalled waiting for CPU, memory, or I/O.

OpenShift can enable PSI with a `MachineConfig` kernel argument:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: 99-worker-enable-psi
spec:
  kernelArguments:
    - psi=1
```

Verify on a node:

```bash
oc debug node/<node>
chroot /host
cat /proc/cmdline | grep psi=1
ls /proc/pressure/
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

Example PSI output:

```text
some avg10=0.91 avg60=1.05 avg300=1.28 total=61523749
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

Interpretation:

- `some`: at least some tasks were stalled
- `full`: all non-idle tasks were stalled

Use PSI carefully in very large clusters because additional metrics can increase Prometheus memory usage.

## 15. Evicted Pod Analysis

### 15.1 Find evicted pods

```bash
oc get pods -A --field-selector=status.phase=Failed -o wide | grep -i Evicted
```

Describe one pod:

```bash
oc -n <namespace> describe pod <pod-name>
```

Look for messages like:

```text
Status: Failed
Reason: Evicted
Message: The node was low on resource: ephemeral-storage.
```

or:

```text
Message: The node was low on resource: memory.
```

### 15.2 Why the selected pod was evicted

Kubelet generally considers:

1. Whether pod usage exceeds requests
2. Pod priority
3. Usage relative to requests

A BestEffort pod or Burstable pod exceeding request is usually at higher risk than a properly sized Guaranteed pod.

For disk/inode/PID pressure, eviction ranking can be less intuitive because inodes and PIDs do not have normal pod resource requests like memory and CPU.

### 15.3 Eviction does not always mean app bug

Possible reasons:

- app bug or leak
- bad request/limit sizing
- node under-sized
- noisy neighbor
- system daemons under-reserved
- log storm from another pod
- image garbage collection delay
- inode exhaustion
- runtime issue

Always compare the evicted pod with other pods on the same node.

## 16. Root Cause Patterns

### 16.1 Pattern: One pod causes node memory pressure

Evidence:

```bash
oc adm top pods -A --sort-by=memory | head
```

One pod dominates memory.

Likely cause:

- memory leak
- query/job processing too much data
- cache not bounded
- wrong JVM heap
- missing limit

Fix:

- restart temporarily
- set request/limit
- tune heap/cache
- add HPA/workload sharding
- investigate application metrics

### 16.2 Pattern: Many small pods cause pressure

Evidence:

- no single offender
- high pod count on node
- allocated resources high
- high system overhead

Fix:

- reduce pod density
- add nodes
- adjust scheduler spread
- review DaemonSet overhead
- review `maxPods`
- review system reservations

### 16.3 Pattern: Disk pressure after deployment

Evidence:

- new version logs heavily
- image size much larger
- app writes to `/tmp`, `/cache`, or working directory
- `container_fs_usage_bytes` rising

Fix:

- rollback
- lower log level
- set `emptyDir.sizeLimit`
- move data to PVC
- set ephemeral storage limits

### 16.4 Pattern: Disk pressure from image cache

Evidence:

- `/var/lib/containers/storage` huge
- many unused images
- recent image pull storm
- kubelet image GC messages

Fix:

- allow image GC
- tune image GC thresholds
- avoid frequent unique image tags for every rollout on small disks
- use larger node disks
- reduce unnecessary pull policy `Always` where not needed

### 16.5 Pattern: Disk pressure from logs

Evidence:

- `/var/log/pods` or journald huge
- app logs repeated errors
- log collector lagging

Fix:

- fix noisy app
- reduce log level
- configure app-side log rotation if writing files
- rely on stdout/stderr but avoid unbounded error loops
- tune cluster logging pipeline capacity

### 16.6 Pattern: PID pressure from thread leak

Evidence:

```bash
ps -eLf -o pid,ppid,nlwp,comm,args --sort=-nlwp | head
```

One process has extremely high `NLWP`.

Fix:

- restart pod temporarily
- tune thread pools
- fix code
- set process/thread limits where possible
- isolate workload

### 16.7 Pattern: Control plane node pressure

Evidence:

- master/control-plane node affected
- static pods might restart
- API latency or etcd warnings

Fix:

- treat as high severity
- avoid aggressive drain unless documented and safe
- inspect static pod logs
- collect must-gather
- check etcd/API/operator health
- open vendor support case if persistent

Commands:

```bash
oc get co
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-apiserver -o wide
oc adm node-logs <master-node> -u kubelet --since=2h
```

## 17. Remediation Playbooks

### 17.1 Generic immediate containment

```bash
NODE=<node>

oc adm cordon "$NODE"
```

Cordon is safe in most incidents because it stops new pods from landing on the node but does not kill running pods.

Drain only when safe:

```bash
oc adm drain "$NODE" --ignore-daemonsets --delete-emptydir-data
```

Be careful with:

- control plane nodes
- infra nodes hosting routers/registry/monitoring/logging
- ODF/storage nodes
- stateful workloads
- pods without replicas
- PodDisruptionBudgets
- local data

### 17.2 Memory pressure remediation

Immediate:

```bash
oc adm top pods -A --sort-by=memory | head -30
oc -n <ns> rollout restart deploy/<deploy>
oc -n <ns> scale deploy/<deploy> --replicas=<safe-number>
```

Permanent:

- define memory requests/limits
- avoid BestEffort pods
- tune JVM heap: `-Xms`, `-Xmx`, container-aware memory
- use HPA/VPA carefully
- add nodes or larger node flavor
- separate infra and workload nodes
- tune `systemReserved`

### 17.3 Disk pressure remediation

Immediate:

```bash
oc debug node/"$NODE"
chroot /host

df -hT
df -ih
du -xhd1 /var /var/lib /var/lib/kubelet /var/lib/containers /var/log 2>/dev/null | sort -h
```

If application logs are exploding, fix the application or reduce log level. If unused images are the issue, prefer kubelet image GC. Emergency manual image cleanup:

```bash
crictl rmi --prune
```

Permanent:

- set ephemeral storage requests/limits
- set `emptyDir.sizeLimit`
- tune image GC thresholds
- expand root/var disk
- isolate build workloads
- fix log storms

### 17.4 PID pressure remediation

Immediate:

```bash
oc debug node/"$NODE"

ps -eLf | wc -l
ps -eLf -o pid,ppid,nlwp,comm,args --sort=-nlwp | head -30
```

If one pod is responsible, restart or scale it safely.

Permanent:

- fix thread/process leak
- tune thread pools
- reduce pod density
- isolate CI/build workloads
- configure pod PID limits if appropriate for your platform version

### 17.5 Add capacity

For machine API clusters:


## 18. KubeletConfig, Garbage Collection, and Reservations

### 18.1 Why KubeletConfig matters

OpenShift uses kubelet settings for:

- eviction thresholds
- image garbage collection
- container garbage collection
- system reserved resources
- pod density related behavior

Do not edit kubelet config directly on RHCOS nodes. Use OpenShift-supported APIs such as `KubeletConfig` through the Machine Config Operator.

### 18.2 Image garbage collection

OpenShift image garbage collection removes images not referenced by running pods. Important variables include:

| Setting | Meaning |
|---|---|
| `imageMinimumGCAge` | Minimum age before unused image can be removed. |
| `imageGCHighThresholdPercent` | Disk usage percentage that triggers image GC. |
| `imageGCLowThresholdPercent` | Target usage percentage image GC tries to reach. |

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-gc-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    imageMinimumGCAge: 5m
    imageGCHighThresholdPercent: 80
    imageGCLowThresholdPercent: 75
```

### 18.3 Eviction thresholds example

Example only. Test before production.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-eviction-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    evictionSoft:
      memory.available: "500Mi"
      nodefs.available: "10%"
      nodefs.inodesFree: "5%"
      imagefs.available: "15%"
      imagefs.inodesFree: "10%"
    evictionSoftGracePeriod:
      memory.available: "1m30s"
      nodefs.available: "1m30s"
      nodefs.inodesFree: "1m30s"
      imagefs.available: "1m30s"
      imagefs.inodesFree: "1m30s"
    evictionHard:
      memory.available: "200Mi"
      nodefs.available: "5%"
      nodefs.inodesFree: "4%"
      imagefs.available: "10%"
      imagefs.inodesFree: "5%"
    evictionPressureTransitionPeriod: 3m
```

Important production notes:

- OpenShift supports only one `KubeletConfig` per MachineConfigPool.
- Changing kubelet config can roll nodes through the Machine Config Operator.
- Test in non-production first.
- For `evictionHard`, specify all relevant parameters; partial configuration can cause unexpected garbage collection behavior.
- Understand whether `nodefs`, `imagefs`, and `containerfs` are separate or the same filesystem.

### 18.4 System reserved resources

OpenShift reserves CPU and memory for node/system components such as kubelet, CRI-O, `sshd`, and NetworkManager.

If system daemons use more than reserved, user pods might be evicted even if their own resource behavior looks reasonable.

Check allocation:

```bash
oc describe node "$NODE" | sed -n '/Capacity:/,/System Info:/p'
```

On node:

```bash
oc debug node/"$NODE"
chroot /host
cat /etc/node-sizing.env
```

Manual example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: set-worker-allocatable
spec:
  autoSizingReserved: false
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    systemReserved:
      cpu: 1000m
      memory: 4Gi
      ephemeral-storage: 50Mi
```

Use manual reservation only with proper sizing analysis. Reserving too much reduces workload capacity. Reserving too little risks node instability.

## 20. Custom Alerting Examples

Do not directly modify Red Hat managed alerting rules in `openshift-monitoring`. For production, use the supported alerting API available in your OpenShift version and your organization’s GitOps process.

Check available APIs:

```bash
oc api-resources | egrep -i 'prometheusrule|alertingrule'
oc explain prometheusrule
oc explain alertingrule
```

### 20.1 Lab-style PrometheusRule example

Use this as a learning example. Adjust namespace/API according to your OpenShift version and monitoring policy.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: node-pressure-custom-rules
  namespace: openshift-monitoring
spec:
  groups:
  - name: node-pressure.custom
    rules:
    - alert: CustomNodePressure
      expr: kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"} == 1
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "Node {{ $labels.node }} is under {{ $labels.condition }}"
        description: "Kubelet has reported {{ $labels.condition }} on node {{ $labels.node }} for more than 10 minutes. Check node conditions, taints, events, kubelet logs, filesystem, memory, and process usage."
```

### 20.2 Disk usage early-warning alert

```yaml
- alert: CustomNodeRootFilesystemHighUsage
  expr: |
    100 * (1 - (
      node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs|overlay"}
      /
      node_filesystem_size_bytes{mountpoint="/",fstype!~"tmpfs|overlay"}
    )) > 85
  for: 15m
  labels:
    severity: warning
  annotations:
    summary: "Node root filesystem usage high on {{ $labels.instance }}"
    description: "Root filesystem usage is above 85% for 15 minutes. Investigate /var/log, /var/lib/kubelet, and /var/lib/containers before DiskPressure occurs."
```

### 20.3 Inode early-warning alert

```yaml
- alert: CustomNodeFilesystemInodesLow
  expr: |
    100 * (
      node_filesystem_files_free{fstype!~"tmpfs|overlay"}
      /
      node_filesystem_files{fstype!~"tmpfs|overlay"}
    ) < 10
  for: 15m
  labels:
    severity: warning
  annotations:
    summary: "Node filesystem inode availability low on {{ $labels.instance }}"
    description: "Free inode percentage is below 10%. Check for many small files under /var/log, /var/lib/kubelet, and application cache directories."
```

## 21. Prevention Strategy

### 21.1 Enforce requests and limits

Use `LimitRange` for defaults:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-compute-limits
  namespace: app-namespace
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 256Mi
      ephemeral-storage: 512Mi
    default:
      cpu: 500m
      memory: 512Mi
      ephemeral-storage: 1Gi
```

Use `ResourceQuota`:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: namespace-quota
  namespace: app-namespace
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    requests.ephemeral-storage: 20Gi
    limits.ephemeral-storage: 40Gi
    pods: "50"
```

### 21.2 Avoid BestEffort workloads

BestEffort pods are easy to schedule and easy to evict. In production OpenShift clusters, most workloads should have at least memory and CPU requests.

### 21.3 Set ephemeral storage policy

For workloads that write temporary files:

```yaml
resources:
  requests:
    ephemeral-storage: 512Mi
  limits:
    ephemeral-storage: 2Gi
```

And:

```yaml
emptyDir:
  sizeLimit: 1Gi
```

### 21.4 Use node role separation

Do not mix heavy application workloads with:

- routers
- registry
- monitoring
- logging
- ODF/Ceph
- build workloads
- CI runners
- GPU workloads

Use labels, taints, tolerations, node selectors, affinity, and dedicated MachineConfigPools.

### 21.5 Spread workloads

Use topology spread constraints:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: ScheduleAnyway
  labelSelector:
    matchLabels:
      app: myapp
```

This prevents a single hot node from accumulating too many replicas of the same application.

### 21.6 Watch early-warning dashboards

Track:

- memory available
- memory working set by namespace/pod
- OOM kills
- filesystem usage
- inode usage
- container filesystem usage
- evicted pods
- pressure condition changes
- kubelet and CRI-O resource usage
- system reserved usage
- pod density per node

### 21.7 Capacity planning signals

A node pool needs capacity work when:

- pressure conditions appear repeatedly
- node filesystem stays above 80–85%
- inode free stays below 15–20%
- system-reserved usage approaches reservation
- pod density is consistently high
- evictions appear during normal traffic
- pressure happens during every deployment or log spike

## 22. Advanced Troubleshooting Scenarios

### Scenario 1: `DiskPressure=True`, but `df -h` shows enough free space

Likely causes:

- inode exhaustion
- pressure is on separate `imagefs` or `containerfs`
- deleted-but-open files
- kubelet saw threshold earlier and condition is waiting for transition period
- filesystem metrics differ between mounts

Check:

```bash
df -ih
findmnt
du -xhd1 /var/lib/containers /var/lib/kubelet /var/log 2>/dev/null | sort -h
journalctl -u kubelet --since "-2 hours" | egrep -i "imagefs|nodefs|containerfs|inode|eviction|pressure"
```

### Scenario 2: `MemoryPressure=True`, but `oc adm top node` looks normal

Likely causes:

- condition recently changed and has not transitioned back
- kubelet memory.available calculation differs from simple tools
- system daemons consumed reserved memory
- short memory spike already caused eviction
- page cache/inactive file interpretation confusion

Check:

```bash
oc describe node "$NODE"
cat /proc/meminfo
journalctl -u kubelet --since "-2 hours" | egrep -i "memory|evict|threshold|pressure|oom"
```

### Scenario 3: Repeated evictions from one namespace

Likely causes:

- namespace lacks LimitRange
- application writes temp files without limit
- memory requests too low
- batch jobs too dense

Check:

```bash
oc get limitrange,resourcequota -n <namespace>
oc adm top pods -n <namespace> --sort-by=memory
oc get pods -n <namespace> -o custom-columns=POD:.metadata.name,QOS:.status.qosClass,NODE:.spec.nodeName
```

### Scenario 4: Node pressure after MachineConfig rollout

Likely causes:

- node reboot/image pull storm
- kubelet config changed
- disk cache rebuilt
- MCO stuck or degraded
- multiple nodes updating, reducing capacity

Check:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
oc get co machine-config
```

### Scenario 5: Infra node under pressure

Impact can include:

- ingress route instability
- registry pull/push failures
- monitoring scrape gaps
- log pipeline backpressure

Check infra pods:

```bash
oc get pods -A -o wide | grep "$NODE"
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-monitoring -o wide
oc get pods -n openshift-image-registry -o wide
```

## 23. Interview and Real-World Questions

### Q1. What is the difference between `DiskPressure` and a PVC being full?

`DiskPressure` is node-local filesystem or inode pressure observed by kubelet. A PVC being full is storage volume capacity exhaustion for an application. PVC fullness can break the app, but it does not always create node `DiskPressure` unless the PVC is backed by local node storage or the workload writes heavily to node-local paths.

### Q2. Why can a node be `Ready` but still under pressure?

`Ready=True` means kubelet is healthy enough to report status and the node is generally operational. Pressure conditions are separate status fields. A node can be operational but still unsuitable for more pods because memory/disk/PID thresholds are crossed.

### Q3. What happens when `DiskPressure=True`?

Kubelet reports `DiskPressure=True`, Kubernetes can apply `node.kubernetes.io/disk-pressure` taint, scheduler avoids the node, kubelet tries to reclaim dead containers/images depending on filesystem layout, and if pressure persists, pods can be evicted.

### Q4. Which pods are evicted first under memory pressure?

Pods exceeding requests are at higher risk, especially lower-priority BestEffort/Burstable pods. Guaranteed pods are generally safer, but not absolutely protected if system stability requires eviction and no better candidates exist.

### Q5. Does PodDisruptionBudget protect pods from node-pressure eviction?

Not in the same way as API-initiated voluntary eviction. Node-pressure eviction is kubelet-driven to protect node health.

### Q6. Why should you check `df -ih`?

Because inode exhaustion can cause `DiskPressure` even when there is enough disk space in GB.

### Q7. Why is manual deletion under `/var/lib/containers` dangerous?

CRI-O and kubelet manage runtime state. Manual deletion can corrupt runtime metadata or break running containers. Use supported runtime tools and kubelet garbage collection behavior.

### Q8. How do you prevent disk pressure from app temp files?

Use `emptyDir.sizeLimit`, ephemeral-storage requests/limits, move persistent data to PVCs, and fix application cleanup behavior.

### Q9. What is the first safe action in most node pressure incidents?

Cordon the node:

```bash
oc adm cordon <node>
```

It stops new scheduling without killing running pods.

### Q10. Why can node pressure alerts flap?

Resource usage might hover around eviction thresholds. Kubelet uses an eviction pressure transition period to reduce oscillation, but repeated spikes can still cause alert flapping.

## 24. Quick Cheat Sheet

### Confirm pressure

```bash
NODE=<node>
oc get node "$NODE"
oc describe node "$NODE"
oc get node "$NODE" -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" "}{.reason}{" "}{.lastTransitionTime}{"\n"}{end}'
```

### Check taints

```bash
oc get node "$NODE" -o jsonpath='{range .spec.taints[*]}{.key}{":"}{.effect}{"\n"}{end}'
```

### List pods on node

```bash
oc get pods -A --field-selector spec.nodeName="$NODE" -o wide
```

### Top pods

```bash
oc adm top pods -A --sort-by=memory | head -30
oc adm top pods -A --sort-by=cpu | head -30
```

### Evicted pods

```bash
oc get pods -A --field-selector=status.phase=Failed -o wide | grep -i Evicted
```

### Kubelet logs

```bash
oc adm node-logs "$NODE" -u kubelet --since=2h | egrep -i "pressure|evict|threshold|memory|disk|inode|pid|oom" | tail -200
```

### Node debug

```bash
oc debug node/"$NODE"
chroot /host
```

### Disk

```bash
df -hT
df -ih
du -xhd1 /var /var/lib/kubelet /var/lib/containers /var/log 2>/dev/null | sort -h
```

### Memory

```bash
free -h
cat /proc/meminfo | head -40
ps -eo pid,ppid,comm,%mem,rss,args --sort=-rss | head -30
```

### PID

```bash
cat /proc/sys/kernel/pid_max
cat /proc/sys/kernel/threads-max
ps -eLf | wc -l
ps -eLf -o pid,ppid,nlwp,comm,args --sort=-nlwp | head -30
```

### PromQL: pressure nodes

```promql
kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"} == 1
```

### PromQL: filesystem usage

```promql
100 * (1 - (node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}))
```

### PromQL: inode usage

```promql
100 * (1 - (node_filesystem_files_free{fstype!~"tmpfs|overlay"} / node_filesystem_files{fstype!~"tmpfs|overlay"}))
```

### PromQL: top pod memory

```promql
topk(20, sum by (namespace,pod) (container_memory_working_set_bytes{container!="",pod!=""}))
```

## Final Senior Admin Takeaway

When a node pressure alert fires, treat it as a **node stability incident**. The alert is only the first signal. Your job is to map:

```text
Alert -> Node condition -> Kubelet eviction signal -> Resource consumer -> Workload behavior -> Permanent control
```

The best OpenShift administrators do not only clear the alert. They prevent the next one by fixing workload requests, ephemeral storage limits, image/log lifecycle, node reservations, node pool sizing, and scheduling design.
