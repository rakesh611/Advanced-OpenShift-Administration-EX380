## 1. What alert routing means

In OpenShift, **alert routing** means deciding **where an alert notification should go, when it should be sent, how it should be grouped, and whether it should be repeated, suppressed, muted, or escalated**.

Alert routing is handled primarily by **Alertmanager**. Prometheus or Thanos Ruler evaluates alerting rules. When an alerting expression becomes true for the configured duration, the alert becomes firing and is sent to Alertmanager. Alertmanager then applies routing logic and sends notifications to receivers such as PagerDuty, Slack, Microsoft Teams, webhook endpoints, email systems, ticketing systems, or a central enterprise alerting platform.

A simple alerting flow looks like this:

```text
Metric scraped by Prometheus
        |
        v
PromQL alert rule evaluates to true
        |
        v
Alert becomes pending, then firing
        |
        v
Alert is sent to Alertmanager
        |
        v
Alertmanager route tree evaluates labels
        |
        v
Alert is grouped, inhibited, muted, or routed
        |
        v
Notification is sent to receiver
```

For a senior administrator, alert routing is not only a YAML configuration topic. It is a production operations design topic. A good routing design answers questions such as:

- Which team owns this alert?
- Is it urgent enough to page someone?
- Should it create a ticket instead of waking up an engineer?
- Should platform alerts and application alerts go to different teams?
- Should alerts be grouped by cluster, namespace, service, node, or alert name?
- Should alerts be muted during maintenance windows?
- Should child alerts be suppressed when a parent infrastructure outage is already firing?
- How do we prevent alert fatigue?
- How do we prove that the alert pipeline itself is working?

## 2. OpenShift monitoring architecture for alert routing

OpenShift includes an integrated monitoring stack. The exact component versions and deployment details can vary by OpenShift release, but the core architecture is consistent.

### 2.1 Platform monitoring

Platform monitoring is deployed mainly in the `openshift-monitoring` namespace. It monitors cluster components such as:

- Kubernetes API server
- OpenShift API server
- kubelet
- scheduler
- controller manager
- etcd
- cluster operators
- nodes
- ingress
- networking
- storage operators
- monitoring stack itself

Important platform monitoring components include:

```text
openshift-monitoring
├── prometheus-k8s
├── alertmanager-main
├── thanos-querier
├── cluster-monitoring-operator
├── kube-state-metrics
├── node-exporter
├── openshift-state-metrics
└── telemetry / adapters / supporting components
```

### 2.2 User workload monitoring

User workload monitoring is used for application or tenant workloads. It is commonly deployed in the `openshift-user-workload-monitoring` namespace after it is enabled by a cluster administrator.

Important user workload monitoring components include:

```text
openshift-user-workload-monitoring
├── prometheus-user-workload
├── thanos-ruler-user-workload
├── alertmanager-user-workload   # optional/separate depending on configuration
└── user-workload monitoring config resources
```

In user workload monitoring, **Prometheus scrapes metrics**, while **Thanos Ruler evaluates alerting and recording rules** for user workloads in many OpenShift versions/configurations. This distinction matters because alert labels and external labels might be attached by different components depending on whether you are dealing with metrics or rules.

### 2.3 Alertmanager’s role

Alertmanager is responsible for:

- Receiving alerts from Prometheus or Thanos Ruler
- Deduplicating repeated alert events
- Grouping related alerts into fewer notifications
- Matching alerts against routes
- Sending notifications to receivers
- Applying inhibition rules
- Respecting silences
- Repeating unresolved notifications based on timing settings

Alertmanager does **not** scrape metrics and does **not** decide whether a PromQL expression is true. That is done by Prometheus or Thanos Ruler. Alertmanager starts its work after an alert is already generated.

## 3. Alert lifecycle: metric to notification

A full alert lifecycle in OpenShift normally follows this path:

```text
1. Target exposes metrics
2. Prometheus scrapes metrics
3. Alerting rule evaluates PromQL expression
4. Alert enters pending state if expression is true
5. Alert becomes firing after 'for' duration
6. Alert is sent to Alertmanager
7. Alertmanager checks silences
8. Alertmanager checks inhibition rules
9. Alertmanager evaluates routing tree
10. Alertmanager groups alert with related alerts
11. Alertmanager sends notification to receiver
12. Alert remains firing or becomes resolved
13. Alertmanager sends resolved notification if enabled by receiver
```

Example alert rule:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: app-alerts
  namespace: payments
spec:
  groups:
  - name: payments.rules
    rules:
    - alert: PaymentsHighErrorRate
      expr: |
        sum(rate(http_requests_total{namespace="payments",status=~"5.."}[5m]))
        /
        sum(rate(http_requests_total{namespace="payments"}[5m])) > 0.05
      for: 10m
      labels:
        severity: critical
        team: payments
        service: checkout
      annotations:
        summary: "Payments service high 5xx error rate"
        description: "More than 5% of payments requests are failing for 10 minutes."
```

The rule defines **when the alert fires**. The Alertmanager route defines **where the alert goes**.

Example routing logic:

```yaml
route:
  receiver: default
  routes:
  - matchers:
    - severity="critical"
    - team="payments"
    receiver: payments-pagerduty
  - matchers:
    - severity="warning"
    - team="payments"
    receiver: payments-ticket-webhook
```

## 4. Alert routing vs alert rules vs silencing vs inhibition

These concepts are often confused.

| Concept | Main question | Config location | Example |
|---|---|---|---|
| Alert rule | When should an alert fire? | `PrometheusRule` | CPU usage > 90% for 10m |
| Alert routing | Where should the alert notification go? | Alertmanager config or `AlertmanagerConfig` | Critical alerts go to PagerDuty |
| Receiver | How is the notification delivered? | Alertmanager receiver config | Slack webhook, email SMTP, PagerDuty key |
| Silence | Should matching alerts be muted temporarily? | Alertmanager UI/API | Mute node alerts during patching |
| Inhibition | Should lower-level alerts be suppressed when a higher-level alert is firing? | Alertmanager config | Suppress pod alerts when node is down |
| Grouping | Which alerts should be batched together? | Alertmanager route config | Group by `cluster`, `namespace`, `alertname` |

### 4.1 Alert rule example

```yaml
- alert: NodeFilesystemAlmostFull
  expr: node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.10
  for: 15m
  labels:
    severity: warning
    team: platform
```

This says: **fire the alert** when filesystem free space is below 10% for 15 minutes.

### 4.2 Alert route example

```yaml
route:
  receiver: default
  routes:
  - matchers:
    - team="platform"
    - severity="warning"
    receiver: platform-ticketing
```

This says: **send the alert notification** to the platform ticketing receiver.

### 4.3 Silence example

A silence might mute:

```text
alertname="NodeFilesystemAlmostFull", node="worker-1.example.com"
```

for a planned disk maintenance window.

### 4.4 Inhibition example

If `NodeDown` is firing for a node, you might inhibit pod-level alerts from that same node so that one node outage does not generate hundreds of application alerts.

## 6. Platform alert routing

Platform alerts are cluster-level alerts generated for OpenShift and Kubernetes infrastructure.

Examples:

- `KubeAPIDown`
- `KubeControllerManagerDown`
- `KubeSchedulerDown`
- `EtcdMembersDown`
- `ClusterOperatorDown`
- `NodeNotReady`
- `KubePodCrashLooping`
- `TargetDown`
- `Watchdog`

### 6.1 Default behavior

After installation, firing alerts are visible in the OpenShift web console Alerting UI. However, external notifications are not configured by default. This means alerts can fire but no email, Slack, PagerDuty, Teams, or webhook notification will be sent until routing and receivers are configured.

### 6.2 Configuration method

For default platform alerts, you typically configure Alertmanager by editing the `alertmanager-main` secret in the `openshift-monitoring` namespace.

Extract current configuration:

```bash
oc -n openshift-monitoring get secret alertmanager-main \
  --template='{{ index .data "alertmanager.yaml" }}' \
  | base64 --decode > alertmanager.yaml
```

Edit the file:

```bash
vi alertmanager.yaml
```

Apply updated configuration:

```bash
oc -n openshift-monitoring create secret generic alertmanager-main \
  --from-file=alertmanager.yaml \
  --dry-run=client -o yaml \
  | oc -n openshift-monitoring replace secret --filename=-
```

Check pods and reload behavior:

```bash
oc get pods -n openshift-monitoring -l alertmanager=main
oc logs -n openshift-monitoring alertmanager-main-0 -c alertmanager --tail=100
```

### 6.3 Default route example

A simplified platform Alertmanager configuration often looks like this:

```yaml
global:
  resolve_timeout: 5m
  http_config:
    proxy_from_environment: true

route:
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  receiver: default
  routes:
  - matchers:
    - "alertname=Watchdog"
    repeat_interval: 2m
    receiver: watchdog

receivers:
- name: default
- name: watchdog
```

Important points:

- `default` is usually a catch-all receiver.
- `Watchdog` is special and should normally be routed to a heartbeat receiver.
- The root route should match all alerts.
- Child routes match specific labels.
- Routes are evaluated in order.
- If no child route matches, the alert falls back to the current route receiver.

### 6.4 Platform alert routing design

A mature platform routing design usually separates:

| Alert type | Receiver | Response |
|---|---|---|
| Critical control plane alert | PagerDuty / on-call | Immediate page |
| Node warning | Ticketing webhook | Investigate during business hours |
| Storage full critical | Storage on-call | Immediate escalation |
| Ingress degraded | Network/platform on-call | Page or urgent ticket |
| Watchdog | Heartbeat receiver | Alert if heartbeat stops |
| Informational alerts | Low-priority channel or no notification | Observe only |

Example route strategy:

```yaml
route:
  receiver: default-drop
  group_by: ['cluster', 'namespace', 'alertname']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
  - matchers:
    - alertname="Watchdog"
    receiver: watchdog-heartbeat
    repeat_interval: 2m

  - matchers:
    - severity="critical"
    - openshift_io_alert_source="platform"
    receiver: platform-pagerduty
    group_wait: 15s
    repeat_interval: 30m

  - matchers:
    - severity="warning"
    - openshift_io_alert_source="platform"
    receiver: platform-ticketing
    repeat_interval: 12h

  - matchers:
    - severity="info"
    receiver: default-drop
```

## 7. User workload alert routing

User workload alert routing is for application teams and tenant namespaces.

Examples:

- Payments API high error rate
- Frontend latency high
- Kafka consumer lag
- Application pod crash looping
- Database connection pool exhausted
- Business transaction failures
- Certificate expiry for app-owned endpoints

### 7.1 Two major models

OpenShift supports two common models for user-defined alert routing:

```text
Model A: Use default platform Alertmanager for user workload alerts
Model B: Use a separate Alertmanager instance dedicated to user workload alerts
```

### 7.2 Model A: platform Alertmanager also handles user alerts

In this model:

```text
User workload alerts --> default platform Alertmanager --> receivers
```

Advantages:

- One central Alertmanager
- Easier central governance
- Easier central auditing
- Consistent receiver handling

Disadvantages:

- User workload routing mistakes can affect shared Alertmanager configuration if not scoped properly
- Platform and application alerts can mix if route labels are not designed well
- Requires careful separation by labels such as `openshift_io_alert_source`, `namespace`, `team`, and `severity`

### 7.3 Model B: separate user workload Alertmanager

In this model:

```text
User workload alerts --> alertmanager-user-workload --> app/team receivers
Platform alerts       --> alertmanager-main          --> platform receivers
```

Advantages:

- Strong separation between platform and application alerting
- User workload alert routing can evolve independently
- Reduces risk of application alert noise affecting platform on-call

Disadvantages:

- More components to monitor
- More configuration to manage
- Separate secrets and routing policies

### 7.4 `AlertmanagerConfig` resource

For user-defined projects, `AlertmanagerConfig` lets application teams configure project-scoped alert routing.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
metadata:
  name: payments-alert-routing
  namespace: payments
spec:
  route:
    receiver: payments-default
    groupBy: ['alertname', 'service']
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 2h
    routes:
    - matchers:
      - name: severity
        value: critical
      receiver: payments-pager
      repeatInterval: 30m
    - matchers:
      - name: severity
        value: warning
      receiver: payments-slack
      repeatInterval: 4h
  receivers:
  - name: payments-default
    webhookConfigs:
    - url: https://alerts.example.com/payments/default
  - name: payments-pager
    webhookConfigs:
    - url: https://alerts.example.com/payments/pager
  - name: payments-slack
    webhookConfigs:
    - url: https://alerts.example.com/payments/slack
```

Important limitations:

- User-defined alert routing is namespace-scoped.
- An `AlertmanagerConfig` in namespace `payments` applies to alerting rules in that same namespace.
- If a namespace is excluded from user workload monitoring, its `AlertmanagerConfig` stops contributing to Alertmanager configuration.
- Users need appropriate RBAC, commonly the `alert-routing-edit` role for the project.

### 7.5 Granting access for application teams

Example:

```bash
oc adm policy add-role-to-user alert-routing-edit alice -n payments
```

Verify:

```bash
oc auth can-i create alertmanagerconfigs.monitoring.coreos.com -n payments --as alice
oc auth can-i update alertmanagerconfigs.monitoring.coreos.com -n payments --as alice
```

## 8. Alertmanager routing tree deep dive

Alertmanager routing is based on a tree.

A route tree has:

```text
Root route
├── Child route 1
├── Child route 2
│   ├── Nested route 2.1
│   └── Nested route 2.2
└── Child route 3
```

Every alert enters at the root route. The root route must be a catch-all route and normally should not have matchers. Alertmanager then evaluates child routes based on label matchers.

### 8.1 Root route

Example:

```yaml
route:
  receiver: default
  group_by: ['cluster', 'namespace', 'alertname']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
  - matchers:
    - severity="critical"
    receiver: pagerduty
  - matchers:
    - severity="warning"
    receiver: slack
```

The root route defines defaults inherited by child routes unless child routes override them.

### 8.2 Child routes

Child routes select alerts by labels.

Example:

```yaml
routes:
- matchers:
  - team="platform"
  receiver: platform-slack

- matchers:
  - team="database"
  receiver: database-pagerduty
```

### 8.3 Nested routes

Nested routes are useful when you first match by team, then severity.

```yaml
route:
  receiver: default
  group_by: ['cluster', 'namespace', 'alertname']
  routes:
  - matchers:
    - team="payments"
    receiver: payments-default
    routes:
    - matchers:
      - severity="critical"
      receiver: payments-pagerduty
    - matchers:
      - severity="warning"
      receiver: payments-slack
```

This means:

```text
If team=payments and severity=critical -> payments-pagerduty
If team=payments and severity=warning  -> payments-slack
If team=payments and no child matches  -> payments-default
If team is not payments               -> continue checking sibling routes or root default
```

### 8.4 `continue` behavior

By default, when an alert matches a child route, Alertmanager stops checking sibling routes. This is equivalent to:

```yaml
continue: false
```

Use `continue: true` when the same alert must go to multiple receiver paths.

Example:

```yaml
routes:
- matchers:
  - severity="critical"
  receiver: noc-dashboard-webhook
  continue: true

- matchers:
  - severity="critical"
  - team="platform"
  receiver: platform-pagerduty
```

This sends all critical alerts to a NOC dashboard and also allows matching a later team-specific PagerDuty route.

Use `continue: true` carefully. It can create duplicate notifications if teams do not understand the route tree.

## 9. Route matching strategy

Alert routing depends heavily on labels.

Common alert labels:

```text
alertname
severity
namespace
pod
container
job
service
endpoint
instance
node
team
component
cluster
openshift_io_alert_source
```

### 9.1 Equality matcher

```yaml
matchers:
- severity="critical"
```

Matches only alerts where:

```text
severity == critical
```

### 9.2 Negative matcher

```yaml
matchers:
- severity!="critical"
```

Matches alerts where severity is not critical.

### 9.3 Regex matcher

```yaml
matchers:
- namespace=~"prod-.*"
```

Matches namespaces beginning with `prod-`.

### 9.4 Negative regex matcher

```yaml
matchers:
- namespace!~"dev-.*|test-.*"
```

Matches alerts not from dev or test namespaces.

### 9.5 Multi-label match

```yaml
matchers:
- severity="critical"
- team="database"
- environment="prod"
```

All matchers must match.

### 9.6 Matcher order and route order

Matchers inside a route are logical AND. Route order matters among sibling routes.

Bad order:

```yaml
routes:
- matchers:
  - severity="critical"
  receiver: general-critical

- matchers:
  - severity="critical"
  - team="database"
  receiver: database-critical
```

In this case, a database critical alert may match `general-critical` first and never reach `database-critical`, unless `continue: true` is used.

Better order:

```yaml
routes:
- matchers:
  - severity="critical"
  - team="database"
  receiver: database-critical

- matchers:
  - severity="critical"
  receiver: general-critical
```

Specific routes should normally come before generic routes.

## 10. Receivers and notification integrations

A receiver is a named notification destination.

Example:

```yaml
receivers:
- name: platform-pagerduty
  pagerduty_configs:
  - routing_key: <pagerduty-routing-key>

- name: platform-email
  email_configs:
  - to: ocp-platform@example.com
    from: alertmanager@example.com
    smarthost: smtp.example.com:587
    auth_username: alertmanager@example.com
    auth_password_file: /etc/alertmanager/secrets/smtp-auth/password

- name: platform-webhook
  webhook_configs:
  - url: https://alerts.example.com/api/openshift
```

### 10.1 Common receiver types in OpenShift operations

| Receiver | Use case |
|---|---|
| PagerDuty | Critical incident paging |
| Slack | Team collaboration and warning alerts |
| Microsoft Teams | Enterprise team notifications |
| Email | Low-frequency admin alerts or reports |
| Webhook | Ticket creation, ITSM, ServiceNow, custom automation |
| Heartbeat receiver | Watchdog monitoring |

### 10.2 Receiver naming convention

Use clear names:

```text
platform-pager-critical
platform-ticket-warning
network-pager-critical
storage-pager-critical
payments-slack-warning
payments-pager-critical
watchdog-heartbeat
blackhole
```

Avoid names like:

```text
default2
receiver1
slacktest
newpd
```

Good names make route trees easy to audit during incidents.

## 11. Grouping, timing, and repeat behavior

Alertmanager grouping and timing are crucial for reducing alert noise.

### 11.1 `group_by`

`group_by` defines which labels are used to batch alerts into one notification.

Example:

```yaml
group_by: ['cluster', 'namespace', 'alertname']
```

This groups alerts with the same cluster, namespace, and alert name.

Common patterns:

| Pattern | Example | Impact |
|---|---|---|
| Cluster-level grouping | `['cluster', 'alertname']` | Good for platform alerts |
| Namespace grouping | `['cluster', 'namespace', 'alertname']` | Good for app teams |
| Service grouping | `['cluster', 'namespace', 'service', 'alertname']` | Good for microservices |
| No grouping | `['...']` | Usually noisy; avoid unless upstream system groups |

### 11.2 `group_wait`

`group_wait` is how long Alertmanager waits before sending the first notification for a new alert group.

Example:

```yaml
group_wait: 30s
```

Practical meaning:

- Short value: faster notification, but group might be incomplete.
- Long value: better grouping, but slower alerting.

Recommended starting points:

```text
Critical paging: 10s to 30s
Warning/ticketing: 1m to 5m
Noisy application alerts: 2m to 5m
```

### 11.3 `group_interval`

`group_interval` defines how long Alertmanager waits before sending another notification about new or resolved alerts in the same group.

Example:

```yaml
group_interval: 5m
```

If new alerts join an existing group, Alertmanager waits until the next group interval to notify.

### 11.4 `repeat_interval`

`repeat_interval` defines how often Alertmanager repeats notifications for alerts that are still firing.

Example:

```yaml
repeat_interval: 4h
```

Practical values:

| Alert class | Suggested repeat interval |
|---|---|
| Critical page | 30m to 1h |
| Warning ticket | 6h to 24h |
| Info | No notification or 24h |
| Watchdog | 1m to 5m depending on heartbeat provider |

### 11.5 Timing inheritance

Child routes inherit timing settings from parent routes unless they override them.

Example:

```yaml
route:
  receiver: default
  group_wait: 1m
  group_interval: 10m
  repeat_interval: 4h
  routes:
  - matchers:
    - severity="critical"
    receiver: pagerduty
    group_wait: 15s
    repeat_interval: 30m
```

Critical alerts override `group_wait` and `repeat_interval`, but inherit `group_interval` unless changed.

## 12. Severity, team, namespace, and source-based routing

A scalable alert routing design depends on consistent labels.

### 12.1 Recommended labels

For custom application alerts, enforce labels like:

```yaml
labels:
  severity: critical
  team: payments
  service: checkout
  environment: prod
  runbook_url: https://runbooks.example.com/payments/high-error-rate
```

Important routing labels:

| Label | Purpose |
|---|---|
| `severity` | Decide page vs ticket vs chat |
| `team` | Decide owner |
| `namespace` | Tenant/project context |
| `service` | Application service owner |
| `environment` | Prod vs non-prod |
| `cluster` | Multi-cluster context |
| `openshift_io_alert_source` | Platform vs user-defined source separation |

### 12.2 Severity-based design

Common severity model:

| Severity | Meaning | Receiver |
|---|---|---|
| `critical` | User impact, outage, data risk, urgent SLO burn | PagerDuty/on-call |
| `warning` | Degraded, approaching limit, needs action soon | Slack/ticket |
| `info` | Awareness only | Dashboard/low-priority channel/no notification |
| `none` or missing | Poor hygiene | Route to audit/noise channel |

### 12.3 Platform vs user-defined source

In many OpenShift configurations, platform alerts have the label:

```text
openshift_io_alert_source="platform"
```

You can use this to separate platform and user-defined alerts when both are handled by the same Alertmanager.

Example:

```yaml
routes:
- matchers:
  - openshift_io_alert_source="platform"
  - severity="critical"
  receiver: platform-pagerduty

- matchers:
  - openshift_io_alert_source!="platform"
  - severity="critical"
  receiver: application-critical-router
```

### 12.4 Namespace-based routing

Example:

```yaml
routes:
- matchers:
  - namespace=~"prod-payments|prod-billing"
  receiver: finance-apps-oncall

- matchers:
  - namespace=~"prod-platform-.*"
  receiver: platform-oncall
```

### 12.5 Team-based routing

Example:

```yaml
routes:
- matchers:
  - team="payments"
  receiver: payments-default
  routes:
  - matchers:
    - severity="critical"
    receiver: payments-pager
  - matchers:
    - severity="warning"
    receiver: payments-slack
```

This is cleaner than relying only on namespace names.

## 13. Watchdog alert and alerting health checks

`Watchdog` is a special alert that is designed to fire continuously. It is used to verify that the alerting pipeline is alive.

The idea:

```text
Watchdog should always fire
        |
        v
Alertmanager should repeatedly send it
        |
        v
External heartbeat receiver should expect it
        |
        v
If heartbeat stops, alert the platform team
```

### 13.1 Why Watchdog matters

Without Watchdog, you might not know that alert delivery is broken until a real outage happens and no one is notified.

Watchdog validates:

- Prometheus or Thanos Ruler sending alerts
- Alertmanager receiving alerts
- Route matching
- Receiver configuration
- Network egress to receiver
- Authentication to receiver
- External incident management system health

### 13.2 Example Watchdog route

```yaml
route:
  receiver: default
  routes:
  - matchers:
    - alertname="Watchdog"
    receiver: watchdog-heartbeat
    repeat_interval: 2m

receivers:
- name: watchdog-heartbeat
  webhook_configs:
  - url: https://heartbeat.example.com/openshift/prod-cluster-1
```

### 13.3 Do not silence Watchdog casually

During maintenance, avoid silencing Watchdog unless you know exactly what the external heartbeat system expects. Silencing Watchdog might create a false alert that alerting is broken.

## 14. Secrets, proxy, TLS, and secure receiver authentication

Production alert receivers commonly require authentication.

Examples:

- PagerDuty routing key
- Slack webhook URL
- Teams webhook URL
- SMTP password
- Webhook bearer token
- Client certificate
- Private CA bundle

### 14.1 Do not hard-code secrets when avoidable

Bad:

```yaml
receivers:
- name: webhook
  webhook_configs:
  - url: https://alerts.example.com/api?token=plain-text-secret
```

Better:

```yaml
receivers:
- name: webhook
  webhook_configs:
  - url: https://alerts.example.com/api
    http_config:
      authorization:
        credentials_file: /etc/alertmanager/secrets/alert-webhook-token/token
```

### 14.2 Mounting secrets for platform Alertmanager

Create secret:

```bash
oc -n openshift-monitoring create secret generic alert-webhook-token \
  --from-literal=token='REDACTED_TOKEN_VALUE'
```

Configure Alertmanager to mount it through `cluster-monitoring-config`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    alertmanagerMain:
      secrets:
      - alert-webhook-token
```

The secret is mounted in Alertmanager pods under:

```text
/etc/alertmanager/secrets/<secret_name>/
```

### 14.3 Proxy configuration

If your OpenShift cluster uses a cluster-wide HTTP/HTTPS proxy, receiver traffic may need to use that proxy.

Global option:

```yaml
global:
  http_config:
    proxy_from_environment: true
```

Receiver-specific option:

```yaml
receivers:
- name: external-webhook
  webhook_configs:
  - url: https://alerts.example.com/api
    http_config:
      proxy_from_environment: true
```

### 14.4 TLS and private CA

For receivers using internal certificates, mount a CA secret and use `tls_config`.

Example:

```yaml
receivers:
- name: secure-webhook
  webhook_configs:
  - url: https://alerts.internal.example.com/api
    http_config:
      tls_config:
        ca_file: /etc/alertmanager/secrets/internal-ca/ca.crt
      authorization:
        credentials_file: /etc/alertmanager/secrets/alert-token/token
```

### 14.5 Common secure delivery mistakes

| Mistake | Symptom |
|---|---|
| Secret not mounted | Alertmanager log says file not found |
| Wrong file path | Receiver authentication fails |
| Wrong CA | x509 unknown authority |
| Proxy missing | Connection timeout |
| Proxy used for internal URL incorrectly | Internal receiver unreachable |
| Expired webhook token | 401/403 from receiver |
| SMTP TLS mismatch | Email send failure |

## 15. External Alertmanager integration

Some enterprises centralize alerting outside individual clusters.

Example architecture:

```text
Cluster A Prometheus/Thanos Ruler ----\
Cluster B Prometheus/Thanos Ruler ----- > Central Alertmanager / Enterprise AIOps
Cluster C Prometheus/Thanos Ruler ----/
```

Reasons to use external Alertmanager:

- Centralized multi-cluster alert routing
- Common enterprise escalation policy
- Central governance of receivers
- Integration with global NOC
- Unified silencing and inhibition

Trade-offs:

- Network dependency between clusters and central Alertmanager
- Larger blast radius if central Alertmanager fails
- Requires careful cluster labeling
- Multi-tenant security concerns
- More complex troubleshooting

### 15.1 External labels are critical

When alerts from many clusters go to one Alertmanager, add labels such as:

```yaml
externalLabels:
  cluster: prod-ocp-east
  region: apac
  environment: prod
```

Without `cluster`, alerts from multiple clusters can be deduplicated incorrectly or routed ambiguously.

### 15.2 User workload external Alertmanager example

Example style for user workload monitoring config:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    thanosRuler:
      additionalAlertmanagerConfigs:
      - scheme: https
        pathPrefix: /
        timeout: "30s"
        apiVersion: v1
        bearerToken:
          name: alertmanager-bearer-token
          key: token
        tlsConfig:
          ca:
            name: alertmanager-tls
            key: ca.crt
        staticConfigs:
        - central-alertmanager.example.com
```

## 16. High availability and deduplication concepts

Alertmanager usually runs as a clustered HA set. In OpenShift, this is managed by operators.

### 16.1 Why HA matters

Alerting is part of the reliability control plane. If Alertmanager is down during an outage, alerts might be visible in Prometheus but no external notifications are sent.

HA provides:

- Multiple Alertmanager pods
- Replicated notification state
- Deduplication between replicas
- Better tolerance for pod/node failures

### 16.2 Deduplication

Prometheus and Thanos Ruler can send the same alert repeatedly. Alertmanager deduplicates notifications based on alert labels and internal fingerprinting. Grouping and repeat intervals then determine notification behavior.

### 16.3 Multi-cluster caution

If multiple clusters send alerts to a central Alertmanager, always include unique labels such as:

```text
cluster
region
environment
```

Otherwise, two alerts with identical labels from different clusters can look like the same alert.

## 17. Production routing design patterns

### 17.1 Pattern 1: Platform critical page, warning ticket

```yaml
route:
  receiver: blackhole
  group_by: ['cluster', 'namespace', 'alertname']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
  - matchers:
    - alertname="Watchdog"
    receiver: watchdog
    repeat_interval: 2m

  - matchers:
    - openshift_io_alert_source="platform"
    - severity="critical"
    receiver: platform-pagerduty
    group_wait: 15s
    repeat_interval: 30m

  - matchers:
    - openshift_io_alert_source="platform"
    - severity="warning"
    receiver: platform-ticketing
    repeat_interval: 12h
```

### 17.2 Pattern 2: Team-first application routing

```yaml
route:
  receiver: app-default
  group_by: ['cluster', 'namespace', 'team', 'alertname']
  routes:
  - matchers:
    - team="payments"
    receiver: payments-default
    routes:
    - matchers:
      - severity="critical"
      receiver: payments-pagerduty
    - matchers:
      - severity="warning"
      receiver: payments-slack

  - matchers:
    - team="orders"
    receiver: orders-default
    routes:
    - matchers:
      - severity="critical"
      receiver: orders-pagerduty
    - matchers:
      - severity="warning"
      receiver: orders-slack
```

### 17.3 Pattern 3: Environment-aware routing

```yaml
routes:
- matchers:
  - environment="prod"
  - severity="critical"
  receiver: prod-pagerduty

- matchers:
  - environment="stage"
  - severity="critical"
  receiver: stage-slack

- matchers:
  - environment=~"dev|test"
  receiver: nonprod-alerts
```

### 17.4 Pattern 4: NOC plus owner route

Use `continue: true` to send a critical alert to a central NOC and also to the owning team.

```yaml
routes:
- matchers:
  - severity="critical"
  receiver: noc-dashboard
  continue: true

- matchers:
  - severity="critical"
  - team="platform"
  receiver: platform-pagerduty

- matchers:
  - severity="critical"
  - team="database"
  receiver: database-pagerduty
```

### 17.5 Pattern 5: Blackhole default receiver

A blackhole receiver prevents accidental delivery of noisy unmatched alerts.

```yaml
route:
  receiver: blackhole

receivers:
- name: blackhole
```

Use this carefully. A safer initial deployment might route unmatched alerts to an audit Slack channel so you can discover missing labels.

```yaml
receivers:
- name: unmatched-alert-audit
  slack_configs:
  - api_url_file: /etc/alertmanager/secrets/slack-webhook/url
    channel: '#alert-routing-audit'
```

## 20. Troubleshooting alert routing

### 20.1 Alert is visible in console but no notification is sent

Possible causes:

- No receiver configured
- Alert matches a blackhole/default receiver
- Route matcher does not match alert labels
- Alert is silenced
- Alert is inhibited
- Receiver authentication failed
- Network/proxy issue to external receiver
- Alertmanager config failed to reload
- Alert resolved before `group_wait` completed

Checks:

```bash
oc get secret alertmanager-main -n openshift-monitoring -o yaml
oc logs -n openshift-monitoring alertmanager-main-0 -c alertmanager --tail=200
oc get alertmanagerconfig -A
```

Check alert labels in the UI. Routing mistakes are often label mistakes.

### 20.2 Critical alert goes to warning channel

Likely causes:

- Route order is wrong
- Generic route appears before specific route
- `continue` missing or incorrectly used
- Alert has wrong `severity` label
- Alert rule labels were overwritten

Fix:

- Put specific routes before generic routes.
- Verify alert labels from Alerting UI.
- Use exact matchers for critical route.

### 20.3 Team does not receive application alerts

Likely causes:

- `AlertmanagerConfig` is in wrong namespace
- User workload monitoring not enabled
- Alert routing for user-defined projects not enabled
- User lacks `alert-routing-edit`
- Alert rule is not in same namespace as `AlertmanagerConfig`
- Namespace excluded from user workload monitoring
- Receiver URL invalid

Commands:

```bash
oc get alertmanagerconfig -n <namespace>
oc describe alertmanagerconfig -n <namespace>
oc get prometheusrule -n <namespace>
oc auth can-i create alertmanagerconfigs.monitoring.coreos.com -n <namespace> --as <user>
```

### 20.4 Alertmanager pods crash or config not applied

Likely causes:

- Invalid YAML
- Invalid Alertmanager schema
- Bad indentation
- Receiver references a missing secret file
- Route references a receiver name that does not exist
- Duplicate receiver names

Commands:

```bash
oc logs -n openshift-monitoring alertmanager-main-0 -c alertmanager --tail=300
oc get events -n openshift-monitoring --sort-by=.lastTimestamp
```

### 20.5 Notifications repeat too frequently

Likely causes:

- `repeat_interval` too short
- Alert flapping
- Group labels too granular
- Receiver creates new incident every repeat
- External incident tool dedup key misconfigured

Fix:

- Increase `repeat_interval`.
- Improve alert rule stability with `for` duration.
- Use better grouping labels.
- Configure receiver-side deduplication.

### 20.6 Notifications are delayed

Likely causes:

- `group_wait` too long
- `group_interval` too long
- Alert remains pending due to rule `for` duration
- Alertmanager delivery retries due to receiver failures
- Network/proxy/TLS timeouts

Understand full delay:

```text
Total delay roughly = Prometheus evaluation interval + alert 'for' duration + group_wait + receiver delivery time
```

### 20.7 Watchdog not received by external heartbeat system

Likely causes:

- Watchdog route missing
- Watchdog receiver URL wrong
- Proxy missing
- External heartbeat expects different interval
- Watchdog silenced
- Alertmanager not sending due to config error

Check:

```bash
oc logs -n openshift-monitoring alertmanager-main-0 -c alertmanager | grep -i watchdog
```

### 20.8 User workload AlertmanagerConfig not included

Likely causes:

- Alert routing not enabled for user-defined projects
- `AlertmanagerConfig` CRD version mismatch
- Namespace is excluded from user-defined monitoring
- RBAC problem
- Invalid object rejected by admission

Check:

```bash
oc get alertmanagerconfig -A
oc describe alertmanagerconfig <name> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### 20.9 Receiver returns HTTP 401/403

Likely causes:

- Wrong token
- Expired token
- Secret mounted incorrectly
- `authorization` type wrong
- Webhook endpoint changed

Check Alertmanager logs:

```bash
oc logs -n openshift-monitoring alertmanager-main-0 -c alertmanager --tail=200 | egrep -i '401|403|notify|error'
```

### 20.10 TLS x509 error

Likely causes:

- Missing CA
- Wrong CA file path
- Certificate SAN mismatch
- Intercepting proxy certificate not trusted

Fix:

- Mount correct CA secret.
- Configure `tls_config.ca_file`.
- Validate receiver certificate chain.

## 21. Security and RBAC considerations

### 21.1 Keep platform routing cluster-admin controlled

Platform alert routing affects critical cluster operations. Only trusted platform administrators should edit `alertmanager-main`.

### 21.2 Delegate user workload routing carefully

Application teams can be allowed to manage their own `AlertmanagerConfig` only in their namespace.

Example:

```bash
oc adm policy add-role-to-user alert-routing-edit app-team-user -n app-namespace
```

Avoid giving application teams broad access to `openshift-monitoring` or `openshift-user-workload-monitoring` unless necessary.

### 21.3 Protect receiver credentials

Receiver credentials can page people, create tickets, or trigger automation. Treat them as production secrets.

Recommendations:

- Store tokens in Kubernetes Secrets.
- Restrict secret read access.
- Rotate tokens periodically.
- Avoid committing tokens to Git.
- Avoid exposing tokens in route URLs.
- Use external secrets integration if available.

### 21.4 GitOps considerations

If you manage alert routing with GitOps:

- Store non-secret YAML in Git.
- Store secrets in sealed/encrypted secret tooling.
- Use pull requests for routing changes.
- Validate configuration before merge.
- Require approvals for paging policy changes.
- Keep platform and app routing in separate directories.

Suggested repo layout:

```text
monitoring/
├── platform-alertmanager/
│   ├── alertmanager.yaml
│   ├── receivers.yaml
│   └── README.md
├── user-workload-routing/
│   ├── payments-alertmanagerconfig.yaml
│   ├── orders-alertmanagerconfig.yaml
│   └── shipping-alertmanagerconfig.yaml
└── secrets/
    └── sealed-secrets/
```

## 22. Common interview and real-world questions

### Q1. What is alert routing in OpenShift?

Alert routing is the process by which Alertmanager sends firing alerts to the correct receiver based on labels, route tree configuration, grouping, timing, silences, and inhibition rules.

### Q2. Where do you configure platform alert routing?

For default platform alerts, configure the `alertmanager-main` secret in the `openshift-monitoring` namespace, or use the OpenShift web console for supported receiver settings.

### Q3. Where do you configure user workload alert routing?

For user-defined projects, application teams can use `AlertmanagerConfig` objects in their namespace when user-defined alert routing is enabled. If a separate user workload Alertmanager is enabled, cluster administrators can also edit the `alertmanager-user-workload` secret in `openshift-user-workload-monitoring`.

### Q4. What is the difference between `PrometheusRule` and `AlertmanagerConfig`?

`PrometheusRule` defines alerting conditions. `AlertmanagerConfig` defines where matching alerts should be sent for a namespace-scoped user workload.

### Q5. Why did my alert not send notification even though it is firing?

Common reasons include missing receiver, matcher mismatch, silence, inhibition, invalid route order, receiver authentication failure, network/proxy issue, config reload failure, or alert resolving before `group_wait` completes.

### Q6. What is `group_wait`?

`group_wait` is how long Alertmanager waits before sending the first notification for a new alert group. It allows related alerts and inhibiting alerts to arrive before notification.

### Q7. What is `repeat_interval`?

`repeat_interval` controls how often unresolved alerts are repeated to the receiver.

### Q8. What is the purpose of Watchdog?

Watchdog is a continuously firing alert used to verify that the alert pipeline is functioning. An external heartbeat system should alert you if it stops receiving Watchdog notifications.

### Q9. What is `continue: true` used for?

It allows an alert that matched one child route to continue evaluating later sibling routes. It is useful when one alert must go to multiple destinations, such as a NOC dashboard and a team on-call route.

### Q10. How do you separate platform alerts from application alerts?

Use separate Alertmanager instances where possible, or use labels such as `openshift_io_alert_source="platform"`, `namespace`, `team`, and `severity` to route platform and user workload alerts to different receivers.

## 23. Best practices checklist

### 23.1 Routing design

- [ ] Use clear ownership labels such as `team`, `service`, and `environment`.
- [ ] Use consistent severity values.
- [ ] Route `critical` alerts to paging only when human action is urgent.
- [ ] Route `warning` alerts to ticketing or team chat.
- [ ] Avoid paging on symptoms that automatically recover.
- [ ] Keep specific routes before generic routes.
- [ ] Use `continue: true` only when duplicate delivery is intentional.
- [ ] Keep a catch-all receiver for unmatched alerts during early rollout.
- [ ] Route Watchdog to a heartbeat receiver.

### 23.2 Noise reduction

- [ ] Use meaningful `group_by` labels.
- [ ] Avoid grouping by too many high-cardinality labels.
- [ ] Tune `group_wait`, `group_interval`, and `repeat_interval` by severity.
- [ ] Use inhibition for parent-child outage relationships.
- [ ] Use silences for planned maintenance.
- [ ] Review noisy alerts weekly.

### 23.3 Security

- [ ] Store credentials in Secrets.
- [ ] Mount secrets into Alertmanager instead of hard-coding tokens.
- [ ] Limit access to `openshift-monitoring`.
- [ ] Delegate `AlertmanagerConfig` permissions per namespace.
- [ ] Rotate receiver tokens.
- [ ] Use TLS and CA validation for internal webhooks.

### 23.4 Operations

- [ ] Keep alert routing in Git.
- [ ] Validate YAML before applying.
- [ ] Test receiver connectivity from inside the cluster.
- [ ] Monitor Alertmanager pods and logs.
- [ ] Test Watchdog after routing changes.
- [ ] Document escalation policy and runbooks.

## Final senior-admin summary

Alert routing in OpenShift is the operational bridge between **alert detection** and **incident response**. Prometheus and Thanos Ruler decide when alerts fire. Alertmanager decides where notifications go, how they are grouped, how often they repeat, and whether they are muted or suppressed.

For platform alerts, treat `alertmanager-main` as production-critical cluster configuration. For application alerts, prefer namespace-scoped `AlertmanagerConfig` when user-defined alert routing is enabled. Build routing around stable labels: `severity`, `team`, `namespace`, `service`, `environment`, and `cluster`. Always route Watchdog. Always test receivers. Always control noise before it becomes alert fatigue.

A good OpenShift administrator does not just configure Alertmanager. A good OpenShift administrator designs an alerting system that helps the right team take the right action at the right time.
