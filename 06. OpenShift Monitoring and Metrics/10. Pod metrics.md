## 1. What pod metrics mean in OpenShift

A **pod metric** is a time-series measurement that describes the runtime behavior, resource consumption, lifecycle state, or application-level performance of a Kubernetes/OpenShift pod or its containers.

In OpenShift, pod metrics answer questions such as:

- Which pod is consuming the most CPU?
- Which container is getting CPU throttled?
- Which pod is close to its memory limit?
- Which pods are restarting frequently?
- Which namespace is consuming the most requested CPU or memory?
- Which deployment has pods stuck in `Pending`, `CrashLoopBackOff`, or `ImagePullBackOff`?
- Which pods receive or transmit the most network traffic?
- Which application pods expose custom business metrics?
- Which pods are good candidates for right-sizing requests and limits?
- Why did HPA scale or not scale a workload?

For a senior administrator, pod metrics should not be treated as simple graphs. They are operational evidence. They help you connect application symptoms to infrastructure causes.

Example:

```text
Symptom: Application latency increased.
Possible pod metric evidence:
- CPU usage high but CPU request too low.
- CPU throttling high because CPU limit is too strict.
- Memory working set close to memory limit.
- Pod restarts increased after rollout.
- Network receive/transmit changed suddenly.
- Application request duration histogram p95/p99 increased.
```

## 2. Where pod metrics come from

Pod metrics in OpenShift normally come from four major sources.

### 2.1 Kubelet and cAdvisor metrics

The kubelet runs on every node. It exposes runtime/container metrics, many of which are backed by cAdvisor. These metrics describe actual container resource usage.

Common examples:

```promql
container_cpu_usage_seconds_total
container_cpu_cfs_throttled_seconds_total
container_memory_working_set_bytes
container_memory_rss
container_network_receive_bytes_total
container_network_transmit_bytes_total
container_fs_usage_bytes
```

Use these when you want **actual runtime usage**.

### 2.2 kube-state-metrics

`kube-state-metrics` exposes Kubernetes object state as metrics. These metrics describe desired state, configuration, ownership, pod status, requests, limits, labels, and restart counters.

Common examples:

```promql
kube_pod_info
kube_pod_status_phase
kube_pod_container_status_restarts_total
kube_pod_container_resource_requests
kube_pod_container_resource_limits
kube_pod_owner
kube_pod_labels
kube_pod_container_status_waiting_reason
kube_pod_container_status_terminated_reason
```

Use these when you want **Kubernetes API object state**, not actual usage.

### 2.3 Application metrics

Application metrics are exposed by your workload, usually on `/metrics`, and collected using `ServiceMonitor` or `PodMonitor` when user workload monitoring is enabled.

Examples:

```promql
http_requests_total
http_request_duration_seconds_bucket
jvm_memory_used_bytes
process_cpu_seconds_total
nodejs_eventloop_lag_seconds
nginx_ingress_controller_requests
```

Use these when you want **application behavior**, such as request rate, latency, error rate, queue depth, or business KPIs.

### 2.4 OpenShift platform and operator metrics

Some pod-related behavior is visible through platform operators and OpenShift-specific metrics. These can include cluster operators, ingress, image registry, build/deployment, machine config, network, and storage metrics.

Use these when pod symptoms are caused by platform components.

## 3. OpenShift monitoring architecture for pod metrics

OpenShift includes a built-in monitoring stack managed by the **Cluster Monitoring Operator**.

### 3.1 Core platform monitoring

The default monitoring stack runs mainly in:

```bash
openshift-monitoring
```

Typical components include:

```text
Cluster Monitoring Operator
Prometheus
Alertmanager
Thanos Querier
kube-state-metrics
node-exporter
openshift-state-metrics
Prometheus Operator
```

Core platform monitoring collects metrics for OpenShift control plane and platform components.

### 3.2 User workload monitoring

User workload monitoring is optional and allows cluster users to monitor their own projects without deploying a separate Prometheus stack.

It runs in:

```bash
openshift-user-workload-monitoring
```

Typical components include:

```text
prometheus-user-workload
thanos-ruler-user-workload
prometheus-operator
optional user-workload Alertmanager
```

Enable it with:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get pods
```

Expected components:

```text
prometheus-operator-*
prometheus-user-workload-0
prometheus-user-workload-1
thanos-ruler-user-workload-0
thanos-ruler-user-workload-1
```

### 3.3 Query path

A typical query path looks like this:

```text
User / Admin
  -> OpenShift Web Console Observe -> Metrics
  -> Thanos Querier
  -> Prometheus platform and/or user workload Prometheus
  -> Metrics stored in TSDB
```

For API access:

```bash
THANOS_HOST=$(oc get route -n openshift-monitoring thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/query?query=up"
```

### 3.4 Data flow for pod metrics

```text
Pod/Container runtime
  -> kubelet/cAdvisor on node
  -> Prometheus scrape
  -> Prometheus TSDB
  -> Thanos Querier
  -> OpenShift Observe UI / API / alerts

Kubernetes API pod object
  -> kube-state-metrics
  -> Prometheus scrape
  -> Prometheus TSDB
  -> queries and alerts

Application /metrics endpoint
  -> ServiceMonitor or PodMonitor
  -> user workload Prometheus
  -> Thanos Querier
  -> dashboards and alerts
```

## 4. Pod metric categories

For production troubleshooting, classify pod metrics into these categories.

| Category | Main question | Example metric |
|---|---|---|
| CPU usage | How much CPU is the pod using? | `container_cpu_usage_seconds_total` |
| CPU throttling | Is CPU limit restricting the container? | `container_cpu_cfs_throttled_seconds_total` |
| Memory usage | How much active memory is used? | `container_memory_working_set_bytes` |
| OOM / restarts | Is container restarting due to memory or crashes? | `kube_pod_container_status_restarts_total` |
| Network traffic | How much traffic enters/leaves pod? | `container_network_receive_bytes_total` |
| Filesystem | How much writable layer/ephemeral storage is used? | `container_fs_usage_bytes` |
| Object state | What is the pod phase/state? | `kube_pod_status_phase` |
| Requests/limits | What resources are reserved or capped? | `kube_pod_container_resource_requests` |
| Ownership | Which deployment/statefulset owns the pod? | `kube_pod_owner` |
| App metrics | What is app behavior? | `http_requests_total`, histograms |

## 5. CPU pod metrics

### 5.1 Key CPU concepts

In Kubernetes/OpenShift, CPU is measured in cores.

```text
1 CPU core  = 1000 millicores
500m        = 0.5 CPU core
100m        = 0.1 CPU core
```

A container can use CPU above its request if node CPU is available, unless CPU limits or cgroup quotas restrict it.

### 5.2 CPU usage metric

Main metric:

```promql
container_cpu_usage_seconds_total
```

This is a counter. It continuously increases with CPU seconds consumed. You must use `rate()` or `irate()` to convert it into CPU cores.

Pod CPU usage by pod:

```promql
sum by (namespace, pod) (
  rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])
)
```

CPU usage by container:

```promql
sum by (namespace, pod, container) (
  rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])
)
```

Top 10 CPU consuming pods:

```promql
topk(10,
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])
  )
)
```

### 5.3 CPU usage as percentage of request

This is useful for right-sizing.

```promql
100 *
sum by (namespace, pod) (
  rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])
)
/
sum by (namespace, pod) (
  kube_pod_container_resource_requests{resource="cpu", unit="core"}
)
```

Interpretation:

```text
< 30% for many days  -> possible over-requesting
70-90% sustained     -> request may be realistic
> 100% sustained     -> pod uses more CPU than requested; possible noisy-neighbor risk
```

### 5.4 CPU usage as percentage of limit

```promql
100 *
sum by (namespace, pod) (
  rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])
)
/
sum by (namespace, pod) (
  kube_pod_container_resource_limits{resource="cpu", unit="core"}
)
```

Important: CPU limit is not just an accounting value. It can create CFS throttling.

### 5.5 CPU throttling

Main metric:

```promql
container_cpu_cfs_throttled_seconds_total
```

CPU throttling means the container wanted to run but was throttled because it hit its CPU quota.

CPU throttling time by pod:

```promql
sum by (namespace, pod) (
  rate(container_cpu_cfs_throttled_seconds_total{container!="", pod!=""}[5m])
)
```

Throttling ratio:

```promql
100 *
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_throttled_periods_total{container!="", pod!=""}[5m])
)
/
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_periods_total{container!="", pod!=""}[5m])
)
```

Interpretation:

```text
0-5%       usually acceptable
5-20%      investigate if latency-sensitive
>20%       likely performance issue if app is CPU-bound
```

A pod can show low average CPU but still have throttling if CPU bursts are restricted by a low CPU limit.

### 5.6 CPU troubleshooting logic

```text
High latency + high CPU usage + low throttling:
  App needs more CPU or more replicas.

High latency + moderate CPU usage + high throttling:
  CPU limit is too low or app is bursty.

High CPU usage + low request:
  Scheduler underestimates pod needs; node can become overcommitted.

High CPU request + low usage:
  Capacity wasted; cluster autoscaler may scale unnecessarily.
```

## 6. Memory pod metrics

### 6.1 Memory concepts

Memory is less forgiving than CPU. CPU throttling slows a container. Memory limit violation can kill a container with OOM.

Important memory terms:

| Term | Meaning |
|---|---|
| RSS | Resident Set Size, physical memory used by process pages |
| Working set | Memory actively used and not easily reclaimable |
| Cache | Page cache; may be reclaimable |
| Limit | Hard cgroup memory limit |
| Request | Scheduling reservation |
| OOMKilled | Container killed after exceeding memory limit or node memory pressure |

### 6.2 Main memory metric

```promql
container_memory_working_set_bytes
```

Current pod memory working set:

```promql
sum by (namespace, pod) (
  container_memory_working_set_bytes{container!="", pod!=""}
)
```

Top 10 memory pods:

```promql
topk(10,
  sum by (namespace, pod) (
    container_memory_working_set_bytes{container!="", pod!=""}
  )
)
```

### 6.3 Memory percentage of request

```promql
100 *
sum by (namespace, pod) (
  container_memory_working_set_bytes{container!="", pod!=""}
)
/
sum by (namespace, pod) (
  kube_pod_container_resource_requests{resource="memory", unit="byte"}
)
```

### 6.4 Memory percentage of limit

```promql
100 *
sum by (namespace, pod) (
  container_memory_working_set_bytes{container!="", pod!=""}
)
/
sum by (namespace, pod) (
  kube_pod_container_resource_limits{resource="memory", unit="byte"}
)
```

Alert threshold usually starts around 85-90% of limit, but tune based on workload behavior.

### 6.5 Detect OOMKilled containers

```promql
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}
```

Recent OOMKilled in last 30 minutes:

```promql
max_over_time(kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}[30m]) == 1
```

Restarts by container:

```promql
increase(kube_pod_container_status_restarts_total[15m]) > 0
```

### 6.6 Memory troubleshooting logic

```text
Memory working set near limit + restarts + OOMKilled:
  Increase memory limit or fix memory leak.

Memory working set above request but below limit:
  Pod is using more memory than scheduled reservation; node pressure risk.

Memory usage slowly grows over hours/days:
  Possible leak, cache growth, JVM heap issue, or connection/session accumulation.

Memory spikes during traffic peaks:
  Check concurrency, request body size, cache, thread pools, JVM/native memory.
```

### 6.7 JVM memory note

For Java pods, container memory includes heap, metaspace, thread stacks, direct buffers, native memory, and page cache. Do not set JVM `-Xmx` equal to container memory limit. Leave headroom.

Typical pattern:

```text
container memory limit: 2Gi
JVM max heap:           1.3Gi to 1.5Gi
headroom:               metaspace, threads, direct buffers, native, GC overhead
```

## 7. Network pod metrics

### 7.1 Main network metrics

Common container network metrics:

```promql
container_network_receive_bytes_total
container_network_transmit_bytes_total
container_network_receive_packets_total
container_network_transmit_packets_total
container_network_receive_errors_total
container_network_transmit_errors_total
container_network_receive_packets_dropped_total
container_network_transmit_packets_dropped_total
```

### 7.2 Pod receive bandwidth

```promql
sum by (namespace, pod) (
  rate(container_network_receive_bytes_total{pod!=""}[5m])
)
```

### 7.3 Pod transmit bandwidth

```promql
sum by (namespace, pod) (
  rate(container_network_transmit_bytes_total{pod!=""}[5m])
)
```

### 7.4 Top network consumers

```promql
topk(10,
  sum by (namespace, pod) (
    rate(container_network_receive_bytes_total{pod!=""}[5m])
    +
    rate(container_network_transmit_bytes_total{pod!=""}[5m])
  )
)
```

### 7.5 Packet drops

```promql
sum by (namespace, pod) (
  rate(container_network_receive_packets_dropped_total{pod!=""}[5m])
  +
  rate(container_network_transmit_packets_dropped_total{pod!=""}[5m])
)
```

### 7.6 Network troubleshooting logic

```text
High network transmit from one pod:
  Check logs export, backup jobs, replication, ingress/egress spikes.

High receive traffic + high CPU:
  Request processing load; check app request rate and latency.

Packet drops/errors:
  Check node pressure, CNI, MTU, NetworkPolicy, route/ingress, NIC saturation.

One pod receives no traffic:
  Check Service selector, endpoints, readiness probe, route, and NetworkPolicy.
```

For deeper network troubleshooting, pod metrics should be combined with:

```bash
oc get svc,endpoints,endpointslice -n <namespace>
oc get networkpolicy -n <namespace>
oc describe pod <pod> -n <namespace>
oc logs <pod> -n <namespace>
```

## 8. Filesystem and ephemeral storage pod metrics

### 8.1 Why filesystem metrics matter

Pods can fail because of ephemeral storage exhaustion even when CPU and memory look fine.

Common causes:

- Application writes too much to `/tmp`
- Logs grow inside container filesystem
- Cache files are not cleaned
- EmptyDir volume grows unexpectedly
- Build or CI workloads create large temporary files
- Image layers or writable layer become large

### 8.2 Common filesystem metrics

```promql
container_fs_usage_bytes
container_fs_limit_bytes
container_fs_reads_bytes_total
container_fs_writes_bytes_total
container_fs_reads_total
container_fs_writes_total
```

### 8.3 Pod filesystem usage

```promql
sum by (namespace, pod) (
  container_fs_usage_bytes{container!="", pod!=""}
)
```

### 8.4 Filesystem usage percentage

```promql
100 *
sum by (namespace, pod) (
  container_fs_usage_bytes{container!="", pod!=""}
)
/
sum by (namespace, pod) (
  container_fs_limit_bytes{container!="", pod!=""}
)
```

### 8.5 Write throughput

```promql
sum by (namespace, pod) (
  rate(container_fs_writes_bytes_total{container!="", pod!=""}[5m])
)
```

### 8.6 Ephemeral storage requests and limits

Kubernetes supports ephemeral storage requests and limits. If used, inspect them with:

```promql
kube_pod_container_resource_requests{resource="ephemeral_storage"}
kube_pod_container_resource_limits{resource="ephemeral_storage"}
```

Cluster availability of these metrics can vary. Always verify with the Thanos metadata API or Metrics UI autocomplete.

## 9. Pod lifecycle and health metrics

Runtime usage metrics tell you resource behavior. State metrics tell you Kubernetes behavior.

### 9.1 Pod phase

```promql
kube_pod_status_phase
```

Pods not running:

```promql
kube_pod_status_phase{phase!="Running", phase!="Succeeded"} == 1
```

Pending pods:

```promql
kube_pod_status_phase{phase="Pending"} == 1
```

Failed pods:

```promql
kube_pod_status_phase{phase="Failed"} == 1
```

### 9.2 Waiting reasons

```promql
kube_pod_container_status_waiting_reason
```

Important reasons:

```text
CrashLoopBackOff
ImagePullBackOff
ErrImagePull
CreateContainerConfigError
CreateContainerError
ContainerCreating
```

Query:

```promql
kube_pod_container_status_waiting_reason{reason=~"CrashLoopBackOff|ImagePullBackOff|ErrImagePull|CreateContainerConfigError"} == 1
```

### 9.3 Restarts

```promql
increase(kube_pod_container_status_restarts_total[15m]) > 0
```

Top restart containers over 1 hour:

```promql
topk(10,
  sum by (namespace, pod, container) (
    increase(kube_pod_container_status_restarts_total[1h])
  )
)
```

### 9.4 Readiness and availability

Useful signals:

```promql
kube_pod_status_ready
kube_pod_container_status_ready
kube_pod_status_scheduled
```

Pods not ready:

```promql
kube_pod_status_ready{condition="true"} == 0
```

Containers not ready:

```promql
kube_pod_container_status_ready == 0
```

### 9.5 Pod owner mapping

Pod names change during rollouts. For operational dashboards, aggregate by workload owner where possible.

```promql
kube_pod_owner
```

Example idea:

```text
Pod -> ReplicaSet -> Deployment
Pod -> StatefulSet
Pod -> DaemonSet
Pod -> Job/CronJob
```

In production dashboards, group by `namespace`, `owner_kind`, and `owner_name` when possible, not only by pod name.

## 10. Requests, limits, QoS, and saturation metrics

### 10.1 Requests vs limits

| Field | Meaning |
|---|---|
| Request | Guaranteed scheduling reservation used by scheduler |
| Limit | Maximum resource usage allowed by cgroup |
| CPU request | Used for scheduling and HPA utilization calculation |
| CPU limit | Can cause throttling |
| Memory request | Used for scheduling and eviction priority |
| Memory limit | Can cause OOMKilled |

### 10.2 Resource request metrics

```promql
kube_pod_container_resource_requests
```

CPU requested by namespace:

```promql
sum by (namespace) (
  kube_pod_container_resource_requests{resource="cpu", unit="core"}
)
```

Memory requested by namespace:

```promql
sum by (namespace) (
  kube_pod_container_resource_requests{resource="memory", unit="byte"}
)
```

### 10.3 Resource limit metrics

```promql
kube_pod_container_resource_limits
```

CPU limits by namespace:

```promql
sum by (namespace) (
  kube_pod_container_resource_limits{resource="cpu", unit="core"}
)
```

Memory limits by namespace:

```promql
sum by (namespace) (
  kube_pod_container_resource_limits{resource="memory", unit="byte"}
)
```

### 10.4 Pods without requests

CPU request missing:

```promql
sum by (namespace, pod, container) (
  kube_pod_container_info{container!=""}
)
unless
sum by (namespace, pod, container) (
  kube_pod_container_resource_requests{resource="cpu"}
)
```

Memory request missing:

```promql
sum by (namespace, pod, container) (
  kube_pod_container_info{container!=""}
)
unless
sum by (namespace, pod, container) (
  kube_pod_container_resource_requests{resource="memory"}
)
```

### 10.5 QoS class

Kubernetes QoS classes:

| QoS | Condition | Operational impact |
|---|---|---|
| Guaranteed | CPU and memory request equals limit for every container | Highest eviction priority protection |
| Burstable | At least one request/limit set but not Guaranteed | Normal enterprise default |
| BestEffort | No CPU/memory requests or limits | First eviction candidate |

Metric often available:

```promql
kube_pod_status_qos_class
```

BestEffort pods:

```promql
kube_pod_status_qos_class{qos_class="BestEffort"} == 1
```

### 10.6 Saturation signals

A pod is saturated when it wants more of a resource than it can effectively obtain.

| Resource | Saturation signal |
|---|---|
| CPU | throttling, high run queue, high CPU vs request/limit |
| Memory | near memory limit, OOMKilled, node memory pressure |
| Network | packet drops/errors, high bandwidth, latency |
| Disk | high write rate, ephemeral storage near limit |
| App | queue depth, high latency, thread pool saturation |

## 11. Application pod metrics

Infrastructure metrics tell you whether the container is healthy. Application metrics tell you whether the service is useful.

### 11.1 Golden signals

Use these four signals for application pods:

| Signal | Metric examples |
|---|---|
| Latency | `http_request_duration_seconds_bucket` |
| Traffic | `http_requests_total` |
| Errors | `http_requests_total{status=~"5.."}` |
| Saturation | queue depth, worker usage, DB pool usage |

### 11.2 Request rate

```promql
sum by (namespace, pod) (
  rate(http_requests_total[5m])
)
```

### 11.3 Error rate percentage

```promql
100 *
sum by (namespace, pod) (
  rate(http_requests_total{status=~"5.."}[5m])
)
/
sum by (namespace, pod) (
  rate(http_requests_total[5m])
)
```

### 11.4 p95 latency from histogram

```promql
histogram_quantile(0.95,
  sum by (le, namespace, pod) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
```

### 11.5 Application metrics design rules

Good label examples:

```text
method="GET"
route="/api/orders/{id}"
status="200"
service="orders"
```

Bad label examples:

```text
user_id="123456"
request_id="8f14e45fceea167a5a36dedd4bea2543"
email="user@example.com"
raw_url="/api/orders/987654?token=..."
```

Avoid unbounded labels. High-cardinality labels can overload Prometheus, increase disk usage, and slow queries.

## 12. ServiceMonitor and PodMonitor for pod metrics

### 12.1 ServiceMonitor

Use `ServiceMonitor` when your app exposes metrics through a Kubernetes Service.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: webapp-monitor
  namespace: app-prod
spec:
  selector:
    matchLabels:
      app: webapp
  endpoints:
    - port: metrics
      path: /metrics
      interval: 30s
      scheme: http
```

The Service must have a named port:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: webapp
  namespace: app-prod
  labels:
    app: webapp
spec:
  selector:
    app: webapp
  ports:
    - name: http
      port: 8080
      targetPort: 8080
    - name: metrics
      port: 9090
      targetPort: 9090
```

### 12.2 PodMonitor

Use `PodMonitor` when scraping pods directly is better than scraping through a Service.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: worker-pod-monitor
  namespace: app-prod
spec:
  selector:
    matchLabels:
      app: worker
  podMetricsEndpoints:
```

## 15. Dashboards for pod metrics

A production pod dashboard should not only show CPU and memory. It should answer an incident question within 30 seconds.

### 15.1 Recommended dashboard sections

1. **Overview**
   - Running pods
   - Pending pods
   - Failed pods
   - Not ready pods
   - Restart count

2. **CPU**
   - CPU usage by pod/container
   - CPU usage vs request
   - CPU usage vs limit
   - CPU throttling ratio

3. **Memory**
   - Working set by pod/container
   - Memory vs request
   - Memory vs limit
   - OOMKilled events

4. **Network**
   - Receive bytes/sec
   - Transmit bytes/sec
   - Packet drops/errors

5. **Filesystem**
   - Writable layer usage
   - Write throughput
   - Ephemeral storage usage

6. **Lifecycle**
   - CrashLoopBackOff
   - ImagePullBackOff
   - ContainerCreating
   - Pending by reason

7. **Application**
   - Request rate
   - Error rate
   - p95/p99 latency
   - Queue depth

8. **Capacity and right-sizing**
   - Request vs actual usage
   - Limit vs actual usage
   - Top over-requested workloads
   - Top under-requested workloads

### 15.2 Dashboard design principle

For administrators, dashboards should be arranged from symptom to root cause:

```text
Availability -> Restarts -> Resource saturation -> Kubernetes state -> Application metrics -> Infrastructure dependencies
```

Do not build dashboards that only show pretty graphs. Build dashboards that reduce mean time to recovery.

## 16. Alerting on pod metrics

### 16.1 PrometheusRule example: high restart rate

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pod-health-rules
  namespace: app-prod
spec:
  groups:
    - name: pod-health.rules
      rules:
        - alert: PodContainerRestartingFrequently
          expr: |
            sum by (namespace, pod, container) (
              increase(kube_pod_container_status_restarts_total[15m])
            ) > 3
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "Container restarting frequently"
            description: "{{ $labels.namespace }}/{{ $labels.pod }}/{{ $labels.container }} restarted more than 3 times in 15 minutes."
```

### 16.2 Alert: pod memory near limit

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pod-memory-rules
  namespace: app-prod
spec:
  groups:
    - name: pod-memory.rules
      rules:
        - alert: PodMemoryNearLimit
          expr: |
            100 *
            sum by (namespace, pod) (
              container_memory_working_set_bytes{container!="", pod!=""}
            )
            /
            sum by (namespace, pod) (
              kube_pod_container_resource_limits{resource="memory", unit="byte"}
            ) > 90
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: "Pod memory near limit"
            description: "{{ $labels.namespace }}/{{ $labels.pod }} memory working set is above 90% of limit for 10 minutes."
```

### 16.3 Alert: CPU throttling high

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pod-cpu-rules
  namespace: app-prod
spec:
  groups:
    - name: pod-cpu.rules
      rules:
        - alert: PodCPUThrottlingHigh
          expr: |
            100 *
            sum by (namespace, pod, container) (
              rate(container_cpu_cfs_throttled_periods_total{container!="", pod!=""}[5m])
            )
            /
            sum by (namespace, pod, container) (
              rate(container_cpu_cfs_periods_total{container!="", pod!=""}[5m])
            ) > 20
          for: 15m
          labels:
            severity: warning
          annotations:
            summary: "High CPU throttling"
            description: "{{ $labels.namespace }}/{{ $labels.pod }}/{{ $labels.container }} CPU throttling is above 20%."
```

### 16.4 Alert quality rules

Good alerts are:

- Actionable
- Linked to user impact or high risk
- Stable enough to avoid noise
- Annotated with namespace, pod, container, and runbook
- Tuned by environment

Avoid alerting on every short CPU spike. Alert on sustained saturation, restarts, OOM, unready pods, and error/latency symptoms.

## 17. HPA, KEDA, and pod metrics

### 17.1 HPA and pod metrics

Horizontal Pod Autoscaler uses metrics to scale replicas. For common CPU/memory HPA, requests matter.

Example HPA:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: webapp-hpa
  namespace: app-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: webapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

Important:

```text
CPU utilization percentage is calculated against CPU request, not CPU limit.
If CPU request is missing, CPU-based HPA will not behave correctly.
```

Check HPA:

```bash

oc describe hpa <hpa-name> -n <namespace>
```

Check CPU usage:

```promql

  rate(container_cpu_usage_seconds_total{namespace="app-prod", container!="", pod!=""}[5m])

```

Check CPU requests:

```promql

  kube_pod_container_resource_requests{namespace="app-prod", resource="cpu", unit="core"}

```

Check if pods are throttled:

### 17.3 KEDA / Custom Metrics Autoscaler

OpenShift Custom Metrics Autoscaler is based on KEDA and can scale workloads using sources beyond simple CPU and memory, including Prometheus and external systems.

Example Prometheus ScaledObject:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: webapp-prometheus-scaler
  namespace: app-prod
spec:
  scaleTargetRef:
    name: webapp
  minReplicaCount: 1
  maxReplicaCount: 10
  triggers:
    - type: prometheus
      metadata:
        serverAddress: https://thanos-querier-openshift-monitoring.apps.example.com
        metricName: http_requests_per_second
        threshold: "100"
        query: |
          sum(rate(http_requests_total{namespace="app-prod", app="webapp"}[2m]))
```

Do not configure KEDA `ScaledObject` and a normal HPA on the same workload unless the product documentation explicitly supports your pattern. Competing scalers can fight each other.

| Symptom | Likely cause | Fix |
|---|---|---|

| HPA has unknown metrics | Missing requests or metrics API issue | Check HPA describe and metrics |

## 19. Cardinality, retention, and performance impact

### 19.1 What cardinality means

In Prometheus, each unique combination of metric name and labels creates a time series.

Example:

```text
http_requests_total{method="GET", route="/api/orders", status="200"}
http_requests_total{method="POST", route="/api/orders", status="201"}
```

These are two time series.

If you add `user_id`, `request_id`, or raw URL as labels, cardinality can explode.

### 19.2 Why pod labels can create high cardinality

Pod names are often unique and short-lived:

```text
webapp-7d9c6f8b9f-abcde
webapp-7d9c6f8b9f-pqrst
```

Dashboards grouped by pod are useful for incidents, but long-term reporting should prefer workload-level grouping.

### 19.3 Detect high scrape samples

```promql
topk(10,
  max by(namespace, job) (
    topk by(namespace, job) (1, scrape_samples_post_metric_relabeling)
  )
)
```

### 19.4 Detect series churn

```promql
topk(10,
  sum by(namespace, job) (
    sum_over_time(scrape_series_added[1h])
  )
)
```

### 19.5 Best practices

- Do not use request IDs, user IDs, session IDs, emails, IPs, or unbounded URLs as labels.
- Use route templates, not raw URLs.
- Keep scrape intervals reasonable.
- Use recording rules for expensive repeated queries.
- Use namespace filters in dashboards.
- Aggregate before joining large metric sets.
- Use `topk()` for exploratory troubleshooting.
- Keep alert expressions efficient.

## 21. Advanced admin best practices

### 21.1 Requests and limits

- Always define CPU and memory requests for production pods.
- Avoid setting very low CPU limits for latency-sensitive apps.
- Use memory limits carefully; memory limit breach kills containers.
- Right-size using p95 or p99 over a representative period.
- Consider different profiles for day/night or batch/online workloads.

### 21.2 Metric design

- Standardize metric names and labels across teams.
- Use base units: seconds, bytes, cores.
- Keep labels bounded.
- Expose build/version info as info metrics, but do not overuse changing labels.
- Instrument application errors and latency, not only resource usage.

### 21.3 Dashboard governance

- Create namespace/workload dashboards for app teams.
- Create cluster-wide pod health dashboards for platform team.
- Keep expensive long-range queries out of default dashboard load.
- Use recording rules for repeated expensive calculations.

### 21.4 Alert governance

- Alert on symptoms first: errors, latency, unavailability.
- Alert on causes when they require platform action: OOMKilled, throttling, pending pods.
- Add runbook URLs.
- Route namespace/team alerts to the owning team.
- Avoid duplicate alerts from every pod replica unless necessary.

### 21.5 Security and RBAC

- Do not give cluster-admin only for metrics access.
- Use project-scoped monitoring roles.
- Do not expose monitoring APIs publicly without authentication.
- Use bearer token authentication for Thanos Querier API access.
- Treat metrics as sensitive: labels can leak URLs, tenant names, or internal topology.

### 21.6 Multi-tenancy

In shared OpenShift clusters:

```text
Platform team:
  Owns cluster monitoring, capacity, CMO configuration, global alerting.

Application teams:
  Own ServiceMonitor/PodMonitor, app metrics, app alerts, dashboards.

Security team:
  Reviews sensitive metric labels and access control.

SRE team:
  Owns SLO metrics, burn-rate alerts, incident runbooks.
```

```text
8. Prometheus Operator logs show no errors
```

### 22.6 Difference between usage, request, and limit

```text
Usage  = actual consumed resource from runtime metrics.
Request = scheduler reservation and HPA utilization denominator.
Limit = cgroup maximum; CPU limit throttles, memory limit can kill.
```

### 22.7 Why `rate()` is needed for CPU

`container_cpu_usage_seconds_total` is a counter, so raw values only increase. `rate(metric[5m])` converts it into CPU cores consumed per second.

### 22.8 Why high cardinality is dangerous

Every unique label combination creates a unique time series. Unbounded labels like request ID, user ID, and raw URL can create millions of series, causing high memory, high disk usage, and slow queries.

## Final senior-admin takeaway

For advanced OpenShift administration, pod metrics are not just for dashboards. They are the bridge between Kubernetes scheduling, Linux cgroups, application behavior, autoscaling decisions, and incident response.

A strong OpenShift administrator should be able to:

- Separate runtime usage metrics from Kubernetes object-state metrics.
- Explain CPU usage, CPU request, CPU limit, and CPU throttling clearly.
- Explain memory working set, memory limits, and OOMKilled behavior.
- Build PromQL for pod usage, restarts, readiness, network, and storage.
- Configure ServiceMonitor and PodMonitor correctly.
- Troubleshoot missing metrics using targets, labels, endpoints, and operator logs.
- Design alerts that are actionable and not noisy.
- Prevent high-cardinality metrics from damaging Prometheus performance.
- Use pod metrics for right-sizing, HPA troubleshooting, capacity planning, and production RCA.
