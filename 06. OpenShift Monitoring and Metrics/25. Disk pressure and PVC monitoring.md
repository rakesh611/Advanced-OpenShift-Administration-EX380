# Disk Pressure and PVC Monitoring in OpenShift

**Area:** OpenShift Monitoring and Metrics  
**Level:** Advanced OpenShift Administration / Senior Platform Engineer / SRE  
**Target experience:** ~10 years Linux, Kubernetes, OpenShift, DevOps, production operations  
**Applies to:** OpenShift Container Platform 4.x, validated against current OpenShift 4.20 monitoring concepts as of July 2026

---

## 1. Objective

Disk pressure and PVC monitoring are two different but closely related operational areas in OpenShift:

1. **Node disk pressure monitoring** protects the cluster from local node filesystem exhaustion. It focuses on node root disk, container image storage, container runtime storage, pod logs, `emptyDir`, local ephemeral storage, CSI staging paths, inode exhaustion, and kubelet eviction behavior.
2. **PVC monitoring** protects stateful applications from persistent volume exhaustion. It focuses on actual PVC usage, requested capacity, available bytes, inodes, PVC phase, binding state, storage class behavior, expansion support, and storage backend health.

A senior OpenShift administrator must understand both layers because a storage incident usually looks like an application issue first:

- Pods stuck in `ContainerCreating`
- Pods evicted with `DiskPressure`
- StatefulSet replicas failing to start
- Database pods running but unable to write
- Prometheus or Elasticsearch/Loki pods crash-looping because their PVC is full
- Image pulls failing because node image storage is full
- PVC stuck in `Pending`, `FileSystemResizePending`, or `Terminating`
- Application logs showing `No space left on device`
- Node showing `Ready,SchedulingDisabled` or tainted with disk pressure

This guide explains the concepts, metrics, PromQL, alerting, troubleshooting, remediation, and production runbooks for **Disk Pressure and PVC Monitoring** in OpenShift.

## 2. High-Level Architecture

OpenShift monitoring is built around Prometheus-based collection and querying.

At a high level:

```text
+-----------------------+      +-------------------------+
| kubelet / cAdvisor    | ---> | Prometheus platform     |
| node volume stats     |      | openshift-monitoring    |
+-----------------------+      +-------------------------+
                                      |
+-----------------------+             |
| node-exporter         | ------------+
| node filesystem stats |
+-----------------------+             |
                                      v
+-----------------------+      +-------------------------+
| kube-state-metrics    | ---> | Thanos Querier          |
| PVC object state      |      | Observe -> Metrics      |
+-----------------------+      +-------------------------+
                                      |
                                      v
                              +-------------------------+
                              | Alerts / Dashboards     |
                              | Alertmanager            |
                              +-------------------------+
```

Important collectors and components:

| Component | What it gives you | Disk/PVC relevance |
|---|---|---|
| `node-exporter` | Host-level Linux metrics | Node filesystem size, available bytes, inode availability, disk I/O |
| `kubelet` | Node and pod runtime metrics | PVC volume usage through `kubelet_volume_stats_*`, eviction signals |
| `kube-state-metrics` | Kubernetes object state as metrics | PVC phase, requested size, deletion timestamp, storage class, PV binding |
| `openshift-state-metrics` | OpenShift-specific object metrics | OpenShift resource visibility beyond upstream Kubernetes |
| Prometheus | Scraping, TSDB, alert rule evaluation | Stores disk/PVC time series and evaluates rules |
| Thanos Querier | Query aggregation | Web console Observe -> Metrics queries platform and user workload metrics |
| Alertmanager | Alert routing, grouping, silencing | Sends disk/PVC alerts to email, Slack, PagerDuty, webhook, etc. |

OpenShift includes a preconfigured monitoring stack for core platform components, and administrators can enable user workload monitoring for application projects. Platform metrics are normally queried through the OpenShift console under **Observe -> Metrics** or through the Thanos Querier API.

## 3. Disk Pressure vs PVC Full: Do Not Confuse Them

### 3.1 Node disk pressure

Node disk pressure means the **node local filesystem** is under pressure. This does not always mean a PVC is full.

Common node local paths involved:

```text
/var/lib/kubelet
/var/lib/containers
/var/log
/var/log/pods
/var/log/containers
/var/lib/containers/storage
/var/lib/kubelet/pods
/var/lib/kubelet/plugins
/var/lib/kubelet/plugins/kubernetes.io/csi
/var/lib/kubelet/pods/<pod-uid>/volumes
/var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir
```

Typical causes:

- Container images consuming image filesystem space
- Container logs not rotating correctly
- Application writing huge data into container writable layer
- `emptyDir` used without size limit
- Large debug dumps, heap dumps, thread dumps, backup files inside pod filesystem
- Orphaned pod directories
- Container runtime storage growth
- CSI mount/staging artifacts
- Local PV usage
- Inode exhaustion due to millions of small files
- Monitoring stack TSDB growth if persistent storage is not sized properly
- Image registry storage issues

### 3.2 PVC full

PVC full means a **persistent volume mounted by a pod** is running out of capacity or inodes.

Typical causes:

- Database data directory growth
- WAL/archive logs not purged
- Backup files stored on same PVC
- Prometheus TSDB retention too high for PVC size
- Elasticsearch/Loki/Quay/registry storage growth
- Application cache growth
- Many small files causing inode exhaustion
- No log/data lifecycle policy
- PVC not expanded before hitting critical threshold
- Storage backend capacity exhausted

### 3.3 Why it matters

| Symptom | Likely layer | Example |
|---|---|---|
| Pod evicted with `DiskPressure` | Node disk | Kubelet evicts pod due to `nodefs.available` or `imagefs.available` threshold |
| Pod logs show `No space left on device` | PVC or container layer | Need to check mount path and `df -h` inside pod |
| PVC usage > 90% | PVC | Application data volume nearly full |
| Node root `/` > 90% | Node disk | `/var/lib/containers` or `/var/log` growing |
| PVC `Pending` | Storage provisioning | StorageClass/provisioner/backend issue |
| PVC `Terminating` forever | Kubernetes finalizer/mount/reference issue | Pod still using PVC or finalizer stuck |
| Image pull fails due to no space | Node imagefs | Image cache or container runtime storage full |
| `emptyDir` fills node | Node ephemeral storage | App writes to `/tmp`, `/cache`, or default container filesystem |

## 4. Kubernetes and OpenShift Disk Pressure Internals

### 4.1 Node condition

A node reports conditions such as:

```bash
oc get nodes
oc describe node <node-name>
oc get node <node-name> -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

Relevant node condition:

```text
DiskPressure=True
```

When the node reports disk pressure, Kubernetes/OpenShift can add a taint:

```text
node.kubernetes.io/disk-pressure:NoSchedule
```

Effect:

- New pods without matching toleration are not scheduled on that node.
- Existing pods can be evicted depending on pressure and kubelet policy.
- DaemonSets often tolerate many node-pressure taints, so they might remain running.

Check taints:

```bash
oc describe node <node-name> | grep -i -A5 Taints
oc get node <node-name> -o jsonpath='{.spec.taints}' | jq
```

### 4.2 Eviction signals

Kubelet uses eviction signals to decide whether the node is under pressure.

Key disk-related signals:

| Signal | Meaning |
|---|---|
| `nodefs.available` | Available bytes on node root filesystem |
| `nodefs.inodesFree` | Free inodes on node root filesystem |
| `imagefs.available` | Available bytes on image filesystem |
| `imagefs.inodesFree` | Free inodes on image filesystem |
| `containerfs.available` | Available bytes on container filesystem, where supported |
| `containerfs.inodesFree` | Free inodes on container filesystem, where supported |

In OpenShift, kubelet settings are managed through `KubeletConfig` custom resources and applied by the Machine Config Operator to selected MachineConfigPools.

Example structure:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-disk-eviction-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    evictionSoft:
      nodefs.available: "10%"
      nodefs.inodesFree: "5%"
      imagefs.available: "15%"
      imagefs.inodesFree: "10%"
      memory.available: "500Mi"
    evictionSoftGracePeriod:
      nodefs.available: "1m30s"
      nodefs.inodesFree: "1m30s"
      imagefs.available: "1m30s"
      imagefs.inodesFree: "1m30s"
      memory.available: "1m30s"
    evictionHard:
      nodefs.available: "5%"
      nodefs.inodesFree: "4%"
      imagefs.available: "10%"
      imagefs.inodesFree: "5%"
      memory.available: "200Mi"
    evictionPressureTransitionPeriod: 3m
    imageMinimumGCAge: 5m
    imageGCHighThresholdPercent: 80
    imageGCLowThresholdPercent: 75
```

Important production notes:

- Do not casually tune eviction thresholds without capacity data.
- Changing kubelet settings can roll/reconfigure nodes through MachineConfigPool updates.
- Always verify MachineConfigPool health after applying KubeletConfig:

```bash
oc get mcp
oc describe mcp worker
```

### 4.3 Soft vs hard eviction

| Type | Behavior |
|---|---|
| Soft eviction | Threshold must remain true for a grace period before eviction |
| Hard eviction | Immediate action without grace period |

Hard eviction is dangerous when thresholds are too aggressive because pods can be killed quickly.

### 4.4 Image garbage collection

Kubelet can remove unused images when image storage crosses configured thresholds.

Common GC settings:

| Setting | Meaning |
|---|---|
| `imageGCHighThresholdPercent` | Disk usage percentage that triggers image garbage collection |
| `imageGCLowThresholdPercent` | Target usage after garbage collection |
| `imageMinimumGCAge` | Minimum age before an unused image can be removed |

Example:

```text
High threshold: 85%
Low threshold: 80%
```

This means garbage collection starts around 85% usage and attempts to reduce usage to around 80%.

## 5. PVC Monitoring Internals

### 5.1 PVC lifecycle

PVC phases:

| Phase | Meaning |
|---|---|
| `Pending` | Claim is not bound to a PV yet |
| `Bound` | Claim is bound to a PV |
| `Lost` | Bound PV is missing or unavailable |

Check PVCs:

```bash
oc get pvc -A
oc get pvc -n <namespace>
oc describe pvc <pvc-name> -n <namespace>
oc get pv
oc describe pv <pv-name>
```

### 5.2 PVC usage metrics are not the same as PVC requested size

PVC object request:

```text
kube_persistentvolumeclaim_resource_requests_storage_bytes
```

Actual PVC capacity and usage from kubelet:

```text
kubelet_volume_stats_capacity_bytes
kubelet_volume_stats_used_bytes
kubelet_volume_stats_available_bytes
```

The requested size is what the user asked for. Actual capacity/usage comes from kubelet volume stats and depends on mounted filesystem visibility.

### 5.3 Why PVC usage metrics can be missing

PVC usage metrics can be missing or incomplete when:

- PVC is not mounted by any running pod.
- Storage plugin/CSI driver does not expose stats correctly.
- Volume mode is `Block`; filesystem stats may not apply the same way.
- Kubelet cannot collect volume stats for that volume type.
- The PVC is mounted on a node that Prometheus cannot scrape.
- Metrics are relabeled/dropped by platform policy.
- The application uses object storage or external DB, not a filesystem PVC.

Always verify with both Prometheus and inside the pod:

```bash
oc rsh -n <namespace> <pod-name>
df -hT
df -ih
```

For block volumes, use storage/backend monitoring and application-level metrics rather than filesystem-only assumptions.

## 6. Key Metrics for Disk Pressure and PVC Monitoring

### 6.1 Node condition and taint metrics

| Metric | Purpose |
|---|---|
| `kube_node_status_condition{condition="DiskPressure",status="true"}` | Detect nodes reporting DiskPressure |
| `kube_node_spec_taint{key="node.kubernetes.io/disk-pressure"}` | Detect disk-pressure taint |
| `kube_node_status_condition{condition="Ready",status="true"}` | Confirm node readiness |

Example:

```promql
kube_node_status_condition{condition="DiskPressure",status="true"} == 1
```

### 6.2 Node filesystem metrics

| Metric | Purpose |
|---|---|
| `node_filesystem_size_bytes` | Filesystem total size |
| `node_filesystem_avail_bytes` | Available bytes for non-root users |
| `node_filesystem_free_bytes` | Free bytes including root-reserved blocks |
| `node_filesystem_files` | Total inodes |
| `node_filesystem_files_free` | Free inodes |
| `node_filesystem_readonly` | Filesystem read-only state |

Root filesystem usage percentage:

```promql
100 * (
  1 - (
    node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs|overlay|squashfs"}
    /
    node_filesystem_size_bytes{mountpoint="/",fstype!~"tmpfs|overlay|squashfs"}
  )
)
```

Filesystem inode usage percentage:

```promql
100 * (
  1 - (
    node_filesystem_files_free{fstype!~"tmpfs|overlay|squashfs"}
    /
    node_filesystem_files{fstype!~"tmpfs|overlay|squashfs"}
  )
)
```

### 6.3 Disk I/O metrics

| Metric | Purpose |
|---|---|
| `node_disk_read_bytes_total` | Disk read throughput counter |
| `node_disk_written_bytes_total` | Disk write throughput counter |
| `node_disk_reads_completed_total` | Completed read operations |
| `node_disk_writes_completed_total` | Completed write operations |
| `node_disk_io_time_seconds_total` | Time disk spent doing I/O |
| `node_disk_io_time_weighted_seconds_total` | Weighted I/O time; useful for saturation indicators |

Write throughput by device:

```promql
rate(node_disk_written_bytes_total{device!~"loop.*|ram.*"}[5m])
```

Read throughput by device:

```promql
rate(node_disk_read_bytes_total{device!~"loop.*|ram.*"}[5m])
```

Disk utilization approximation:

```promql
100 * rate(node_disk_io_time_seconds_total{device!~"loop.*|ram.*"}[5m])
```

### 6.4 PVC volume metrics from kubelet

| Metric | Purpose |
|---|---|
| `kubelet_volume_stats_capacity_bytes` | PVC filesystem capacity |
| `kubelet_volume_stats_used_bytes` | PVC used bytes |
| `kubelet_volume_stats_available_bytes` | PVC available bytes |
| `kubelet_volume_stats_inodes` | PVC total inodes |
| `kubelet_volume_stats_inodes_used` | PVC used inodes |
| `kubelet_volume_stats_inodes_free` | PVC free inodes |
| `kubelet_volume_stats_health_status_abnormal` | Volume health abnormal flag, where supported |

PVC usage percentage:

```promql
100 * (
  kubelet_volume_stats_used_bytes
  /
  kubelet_volume_stats_capacity_bytes
)
```

PVC free percentage:

```promql
100 * (
  kubelet_volume_stats_available_bytes
  /
  kubelet_volume_stats_capacity_bytes
)
```

PVC inode usage percentage:

```promql
100 * (
  kubelet_volume_stats_inodes_used
  /
  kubelet_volume_stats_inodes
)
```

Top 10 PVCs by usage percentage:

```promql
topk(10,
  100 * (
    kubelet_volume_stats_used_bytes
    /
    kubelet_volume_stats_capacity_bytes
  )
)
```

Top 10 PVCs by used bytes:

```promql
topk(10,
  kubelet_volume_stats_used_bytes
)
```

### 6.5 PVC object state metrics from kube-state-metrics

| Metric | Purpose |
|---|---|
| `kube_persistentvolumeclaim_info` | PVC metadata such as storage class, volume name, volume mode |
| `kube_persistentvolumeclaim_status_phase` | PVC phase: Pending, Bound, Lost |
| `kube_persistentvolumeclaim_resource_requests_storage_bytes` | Requested storage size |
| `kube_persistentvolumeclaim_deletion_timestamp` | PVC deletion timestamp, useful for Terminating detection |
| `kube_persistentvolumeclaim_status_condition` | PVC conditions, where available |

Pending PVCs:

```promql
kube_persistentvolumeclaim_status_phase{phase="Pending"} == 1
```

Lost PVCs:

```promql
kube_persistentvolumeclaim_status_phase{phase="Lost"} == 1
```

PVCs blocked in terminating state:

```promql
kube_persistentvolumeclaim_deletion_timestamp
* on(namespace, persistentvolumeclaim) group_left()
  (kube_persistentvolumeclaim_status_phase{phase="Bound"} == 1)
> 0
```

## 7. How to Access Metrics in OpenShift

### 7.1 Web console

Go to:

```text
Observe -> Metrics
```

Run PromQL directly.

Useful first checks:

```promql
kube_node_status_condition{condition="DiskPressure",status="true"}
```

```promql
topk(10, 100 * kubelet_volume_stats_used_bytes / kubelet_volume_stats_capacity_bytes)
```

```promql
topk(10, 100 * (1 - node_filesystem_avail_bytes / node_filesystem_size_bytes))
```

### 7.2 Thanos Querier API

Get Thanos route:

```bash
THANOS_ROUTE=$(oc get routes -n openshift-monitoring thanos-querier -o jsonpath='{.status.ingress[0].host}')
echo $THANOS_ROUTE
```

Query metric metadata:

```bash
curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_ROUTE}/api/v1/metadata" | jq
```

Run instant query:

```bash
curl -k -G -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=kube_node_status_condition{condition="DiskPressure",status="true"}' \
  "https://${THANOS_ROUTE}/api/v1/query" | jq
```

Run PVC usage query:

```bash
curl -k -G -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=100 * kubelet_volume_stats_used_bytes / kubelet_volume_stats_capacity_bytes' \
  "https://${THANOS_ROUTE}/api/v1/query" | jq
```

### 7.3 Check available metrics before building alerts

Do this before writing final alert rules:

```bash
curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_ROUTE}/api/v1/metadata" \
  | jq '.data | keys[]' | grep -E 'kubelet_volume|node_filesystem|kube_persistentvolumeclaim|DiskPressure'
```

In the console, you can also type part of the metric name in Observe -> Metrics and check if it autocompletes.

## 8. Essential PromQL Cookbook

### 8.1 Nodes currently under disk pressure

```promql
kube_node_status_condition{condition="DiskPressure",status="true"} == 1
```

### 8.2 Nodes with disk-pressure taint

```promql
kube_node_spec_taint{key="node.kubernetes.io/disk-pressure"} == 1
```

### 8.3 Root filesystem usage per node

```promql
100 * (
  1 - (
    node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs|overlay|squashfs"}
    /
    node_filesystem_size_bytes{mountpoint="/",fstype!~"tmpfs|overlay|squashfs"}
  )
)
```

### 8.4 Filesystems above 85% usage

```promql
100 * (
  1 - (
    node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}
    /
    node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"}
  )
) > 85
```

### 8.5 Inodes above 85% usage

```promql
100 * (
  1 - (
    node_filesystem_files_free{fstype!~"tmpfs|overlay|squashfs"}
    /
    node_filesystem_files{fstype!~"tmpfs|overlay|squashfs"}
  )
) > 85
```

### 8.6 PVC usage percentage by namespace and claim

```promql
100 * (
  kubelet_volume_stats_used_bytes
  /
  kubelet_volume_stats_capacity_bytes
)
```

### 8.7 PVCs above 80% usage

```promql
100 * (
  kubelet_volume_stats_used_bytes
  /
  kubelet_volume_stats_capacity_bytes
) > 80
```

### 8.8 PVCs above 90% usage

```promql
100 * (
  kubelet_volume_stats_used_bytes
  /
  kubelet_volume_stats_capacity_bytes
) > 90
```

### 8.9 PVCs with less than 10 GiB available

```promql
kubelet_volume_stats_available_bytes < 10 * 1024 * 1024 * 1024
```

### 8.10 PVCs that might fill in 24 hours

```promql
predict_linear(kubelet_volume_stats_available_bytes[6h], 24 * 3600) < 0
```

Use this carefully. It works best for mostly linear growth such as logs or time-series data. It can be noisy for batch workloads.

### 8.11 PVC write growth rate

```promql
rate(kubelet_volume_stats_used_bytes[1h])
```

For dashboards, convert to GiB/day:

```promql
rate(kubelet_volume_stats_used_bytes[1h]) * 86400 / 1024 / 1024 / 1024
```

### 8.12 Estimated days to full

```promql
kubelet_volume_stats_available_bytes
/
clamp_min(rate(kubelet_volume_stats_used_bytes[6h]), 1)
/ 86400
```

This gives an approximate number of days until full. Use with caution because workloads can grow non-linearly.

### 8.13 PVC inode usage above 80%

```promql
100 * (
  kubelet_volume_stats_inodes_used
  /
  kubelet_volume_stats_inodes
) > 80
```

### 8.14 Abnormal PVC health

```promql
kubelet_volume_stats_health_status_abnormal == 1
```

### 8.15 Pending PVCs for more than 10 minutes

Use as alert expression with `for: 10m`:

```promql
kube_persistentvolumeclaim_status_phase{phase="Pending"} == 1
```

### 8.16 Bound PVCs with no kubelet usage metrics

This can identify PVCs that are bound but not mounted or not exposing stats:

```promql
kube_persistentvolumeclaim_status_phase{phase="Bound"} == 1
unless on(namespace, persistentvolumeclaim)
kubelet_volume_stats_capacity_bytes
```

Interpretation:

- It might be normal if no pod is using the PVC.
- It might be a monitoring gap if the PVC is mounted but metrics are absent.

## 9. Production Alert Rules

OpenShift 4.19+ supports `AlertingRule` for cluster administrators to create custom platform alerts from platform monitoring metrics. For user workload projects, use `PrometheusRule` in the application namespace when user workload monitoring is enabled and the user has the required monitoring RBAC.

### 9.1 Platform alerting with `AlertingRule`

Use this when you want cluster-level alerts based on platform metrics such as node filesystem and PVC metrics available in the platform monitoring stack.

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertingRule
metadata:
  name: disk-pressure-pvc-platform-alerts
spec:
  groups:
  - name: disk-pressure-pvc.rules
    interval: 30s
    rules:
    - alert: NodeDiskPressureActive
      expr: kube_node_status_condition{condition="DiskPressure",status="true"} == 1
      for: 5m
      labels:
        severity: critical
        team: platform
      annotations:
        summary: "Node {{ $labels.node }} is reporting DiskPressure"
        description: "The node has DiskPressure=True for more than 5 minutes. Check nodefs/imagefs usage, logs, image cache, emptyDir, and inode availability."

    - alert: NodeFilesystemAlmostFull
      expr: |
        100 * (
          1 - (
            node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}
            /
            node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"}
          )
        ) > 85
      for: 15m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "Node filesystem usage high on {{ $labels.instance }} {{ $labels.mountpoint }}"
        description: "Filesystem {{ $labels.mountpoint }} on {{ $labels.instance }} is above 85% usage for 15 minutes."

    - alert: NodeFilesystemCritical
      expr: |
        100 * (
          1 - (
            node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}
            /
            node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"}
          )
        ) > 92
      for: 5m
      labels:
        severity: critical
        team: platform
      annotations:
        summary: "Node filesystem critically full on {{ $labels.instance }} {{ $labels.mountpoint }}"
        description: "Filesystem {{ $labels.mountpoint }} on {{ $labels.instance }} is above 92%. Evictions or workload failures may occur."

    - alert: NodeFilesystemInodesLow
      expr: |
        100 * (
          1 - (
            node_filesystem_files_free{fstype!~"tmpfs|overlay|squashfs"}
            /
            node_filesystem_files{fstype!~"tmpfs|overlay|squashfs"}
          )
        ) > 85
      for: 15m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "Node filesystem inode usage high on {{ $labels.instance }} {{ $labels.mountpoint }}"
        description: "Inode usage is above 85%. Many small files can trigger DiskPressure even when bytes are available."

    - alert: PVCUsageHigh
      expr: |
        100 * (
          kubelet_volume_stats_used_bytes
          /
          kubelet_volume_stats_capacity_bytes
        ) > 80
      for: 30m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} usage is above 80%"
        description: "PVC usage has crossed 80%. Check application growth, retention, cleanup, and expansion options."

    - alert: PVCUsageCritical
      expr: |
        100 * (
          kubelet_volume_stats_used_bytes
          /
          kubelet_volume_stats_capacity_bytes
        ) > 90
      for: 10m
      labels:
        severity: critical
        team: platform
      annotations:
        summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} usage is above 90%"
        description: "PVC is critically full. Application writes may fail. Expand PVC or clean data safely."

    - alert: PVCFillingSoon
      expr: |
        predict_linear(kubelet_volume_stats_available_bytes[6h], 24 * 3600) < 0
      for: 30m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} may fill within 24 hours"
        description: "Based on recent growth, this PVC may reach zero available bytes within 24 hours. Validate growth trend before acting."

    - alert: PVCInodesRunningOut
      expr: |
        100 * (
          kubelet_volume_stats_inodes_used
          /
          kubelet_volume_stats_inodes
        ) > 85
      for: 15m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} inode usage is high"
        description: "PVC inode usage is above 85%. Many small files can cause ENOSPC even when bytes are available."

    - alert: PVCPending
      expr: kube_persistentvolumeclaim_status_phase{phase="Pending"} == 1
      for: 10m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} is Pending"
        description: "PVC has been Pending for more than 10 minutes. Check StorageClass, provisioner, quotas, topology, and backend capacity."

    - alert: PVCBlockedInTerminatingState
      expr: |
        kube_persistentvolumeclaim_deletion_timestamp
        * on(namespace, persistentvolumeclaim) group_left()
          (kube_persistentvolumeclaim_status_phase{phase="Bound"} == 1)
        > 0
      for: 5m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} is blocked in Terminating"
        description: "PVC deletion timestamp is set while the PVC remains Bound. Check pods, finalizers, VolumeAttachment, and CSI driver status."
```

Apply:

```bash
oc apply -f disk-pressure-pvc-platform-alerts.yaml
oc get alertingrule
```

Check in console:

```text
Observe -> Alerting -> Alerting rules
```

## 11. Troubleshooting Runbook: Node DiskPressure

### 11.1 Confirm the condition

```bash
oc get nodes
oc describe node <node-name>
oc get node <node-name> -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

Look for:

```text
DiskPressure=True
KubeletHasDiskPressure
node.kubernetes.io/disk-pressure
```

### 11.2 Check alerts and metrics

```promql
kube_node_status_condition{condition="DiskPressure",status="true"} == 1
```

```promql
100 * (1 - node_filesystem_avail_bytes / node_filesystem_size_bytes)
```

```promql
100 * (1 - node_filesystem_files_free / node_filesystem_files)
```

### 11.3 Debug node filesystem usage

Use `oc debug node`:

```bash
oc debug node/<node-name>
chroot /host
```

Inside the debug shell:

```bash
df -hT
df -ih
lsblk
mount | column -t
```

Check large directories:

```bash
du -xh --max-depth=1 /var | sort -h
du -xh --max-depth=1 /var/lib | sort -h
du -xh --max-depth=1 /var/lib/containers | sort -h
du -xh --max-depth=1 /var/log | sort -h
du -xh --max-depth=1 /var/lib/kubelet | sort -h
```

Find large files:

```bash
find /var -xdev -type f -size +1G -printf '%s %p\n' | sort -n | tail -20
```

Find too many small files:

```bash
find /var -xdev -type f | awk -F/ '{print "/"$2"/"$3"/"$4}' | sort | uniq -c | sort -n | tail -20
```

Check deleted-but-open files:

```bash
lsof +L1
```

This is important when `df` shows full but `du` does not. A process may still hold deleted files open.

### 11.4 Check container runtime storage

On CRI-O based OpenShift nodes:

```bash
crictl images
crictl ps -a
crictl stats
```

Check container storage:

```bash
du -xh --max-depth=1 /var/lib/containers/storage | sort -h
```

Do not manually delete random files inside container runtime storage unless directed by Red Hat support or you fully understand the impact. Prefer kubelet/container runtime GC and safe cleanup.

### 11.5 Check pod logs

```bash
du -xh --max-depth=2 /var/log/pods | sort -h | tail -50
du -xh --max-depth=2 /var/log/containers | sort -h | tail -50
```

Find largest pod log files:

```bash
find /var/log/pods -type f -name '*.log' -printf '%s %p\n' | sort -n | tail -30
```

Map pod UID to pod:

```bash
oc get pod -A -o wide | grep <pod-uid-or-name-fragment>
```

### 11.6 Check `emptyDir` abuse

`emptyDir` consumes node local storage unless backed by memory.

Find pod volumes:

```bash
oc get pod -A -o json | jq -r '
  .items[] |
  select(.spec.volumes[]? | has("emptyDir")) |
  [.metadata.namespace, .metadata.name] | @tsv'
```

Check kubelet pod volume directories:

```bash
du -xh --max-depth=5 /var/lib/kubelet/pods | sort -h | tail -50
```

Best practice for `emptyDir`:

```yaml
volumes:
- name: cache
  emptyDir:
    sizeLimit: 2Gi
```

Also set pod/container ephemeral storage requests and limits:

```yaml
resources:
  requests:
    ephemeral-storage: "1Gi"
  limits:
    ephemeral-storage: "2Gi"
```

### 11.7 Immediate remediation

Safe actions:

```bash
oc adm cordon <node-name>
```

Then investigate.

If workloads need to move:

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
```

Be careful:

- `--delete-emptydir-data` deletes `emptyDir` data.
- Do not drain control plane nodes unless you understand quorum and platform impact.
- Do not drain storage nodes blindly, especially ODF/Ceph nodes.

Other remediation options:

- Reduce noisy logging.
- Delete or rotate large application logs safely.
- Remove unused debug/backup dumps.
- Scale down or restart process holding deleted files open.
- Increase node root/container filesystem size.
- Tune image garbage collection thresholds.
- Add ephemeral storage limits.
- Move heavy local-cache workloads to PVC or object storage.
- Rebuild workload with proper log retention.

After remediation:

```bash
oc adm uncordon <node-name>
oc get nodes
oc describe node <node-name> | grep -i DiskPressure -A5
```

## 12. Troubleshooting Runbook: PVC Full

### 12.1 Identify high PVCs

PromQL:

```promql
topk(20, 100 * kubelet_volume_stats_used_bytes / kubelet_volume_stats_capacity_bytes)
```

CLI:

```bash
oc get pvc -A
```

For a namespace:

```bash
oc get pvc -n <namespace>
oc describe pvc <pvc-name> -n <namespace>
```

### 12.2 Find pod using the PVC

```bash
oc get pod -n <namespace> -o json | jq -r \
  --arg pvc "<pvc-name>" '
  .items[] |
  select(.spec.volumes[]? | .persistentVolumeClaim.claimName == $pvc) |
  .metadata.name'
```

Or manually:

```bash
oc describe pod <pod-name> -n <namespace> | grep -A5 -B5 <pvc-name>
```

### 12.3 Verify inside the pod

```bash
oc rsh -n <namespace> <pod-name>
df -hT
df -ih
mount | grep <mount-path>
du -xh --max-depth=1 <mount-path> | sort -h
```

Find large files:

```bash
find <mount-path> -xdev -type f -size +500M -printf '%s %p\n' | sort -n | tail -30
```

Find many small files:

```bash
find <mount-path> -xdev -type f | awk -F/ '{print "/"$2"/"$3"/"$4}' | sort | uniq -c | sort -n | tail -30
```

### 12.4 Decide cleanup vs expansion

Use this decision table:

| Situation | Best action |
|---|---|
| Temporary logs/backups on PVC | Clean safely and fix lifecycle policy |
| Database/WAL expected growth | Expand PVC and tune DB retention |
| Prometheus TSDB full | Increase PVC or reduce retention/remote write |
| Inode exhaustion | Remove small files or recreate filesystem with better inode density if needed |
| StorageClass supports expansion | Expand PVC online/offline depending on driver |
| StorageClass does not support expansion | Migrate data to larger PVC or create new volume |
| Backend pool full | Expand backend storage first; PVC expansion may fail |

### 12.5 Check StorageClass expansion support

```bash
oc get storageclass
oc get storageclass <storageclass-name> -o yaml | grep -i allowVolumeExpansion
```

Expected:

```yaml
allowVolumeExpansion: true
```

If missing or false, confirm support with your CSI/storage vendor before changing it.

### 12.6 Expand PVC

Example: increase from `20Gi` to `50Gi`.

```bash
oc patch pvc <pvc-name> -n <namespace> \
  -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'
```

Watch:

```bash
oc get pvc <pvc-name> -n <namespace> -w
oc describe pvc <pvc-name> -n <namespace>
```

Check pod:

```bash
oc rsh -n <namespace> <pod-name> df -hT
```

Important:

- Shrinking PVs/PVCs is not supported.
- Some CSI drivers support online filesystem expansion.
- Some require pod restart/remount.
- Some require backend-side operations.
- Always confirm storage backend health before expansion.

### 12.7 If PVC is stuck in `FileSystemResizePending`

Check:

```bash
oc describe pvc <pvc-name> -n <namespace>
oc get pod -n <namespace> -o wide
```

Common fix:

- Restart the pod using the PVC if the driver requires remount for filesystem resize.
- For StatefulSet:

```bash
oc rollout restart statefulset/<name> -n <namespace>
```

Be careful with databases. Follow application-specific graceful restart procedures.

## 16. OpenShift Monitoring Stack Storage Itself

The monitoring stack can itself become a storage consumer.

Critical components:

| Component | Storage concern |
|---|---|
| Prometheus platform | TSDB size, retention, PVC capacity |
| Alertmanager | Silences and notification state |
| Thanos Ruler | Rule evaluation data |
| User workload Prometheus | Application metrics cardinality and retention |

Production recommendation:

- Use persistent storage for Prometheus, Alertmanager, and Thanos Ruler in production.
- Size PVCs based on scrape interval, target count, label cardinality, retention, and remote write usage.
- Monitor Prometheus PVCs like any other PVC.
- Avoid unbounded labels in application metrics.

### 16.1 Check monitoring PVCs

```bash
oc get pvc -n openshift-monitoring
oc get pvc -n openshift-user-workload-monitoring
```

### 16.2 Prometheus storage risk indicators

PromQL examples:

```promql
topk(20, 100 * kubelet_volume_stats_used_bytes{namespace="openshift-monitoring"} / kubelet_volume_stats_capacity_bytes{namespace="openshift-monitoring"})
```

```promql
prometheus_tsdb_head_series
```

```promql
rate(prometheus_tsdb_head_samples_appended_total[5m])
```

High cardinality can fill Prometheus PVC rapidly.

### 16.3 Reduce monitoring storage pressure

Options:

- Reduce retention time.
- Increase PVC size.
- Use remote write for long-term storage.
- Drop unnecessary metrics carefully.
- Fix high-cardinality application labels.
- Avoid per-request, per-user, per-session labels.
- Tune scrape intervals for noisy workloads.

## 17. Capacity Planning

### 17.1 Node disk capacity planning

For worker nodes, plan space for:

- RHCOS root filesystem
- Container runtime storage
- Image cache
- Pod logs
- Kubelet pod directories
- CSI mount/staging paths
- `emptyDir`
- Debug artifacts
- Local PVs, if used
- Upgrade overhead

Senior admin baseline:

| Area | Guideline |
|---|---|
| Root/container filesystem usage | Alert at 80-85%, critical at 90-92% |
| Inode usage | Alert at 80-85% |
| Image GC | Keep enough headroom for deployment bursts |
| Logs | Enforce rotation and logging pipeline health |
| `emptyDir` | Use `sizeLimit` and ephemeral-storage limits |
| Node upgrade | Keep extra space for pivot/update operations |

### 17.2 PVC capacity planning

For each PVC-owning application, know:

- Owner/team
- Workload type
- StorageClass
- Access mode
- Volume mode
- Current size
- Growth GiB/day
- Retention policy
- Backup policy
- Expansion support
- RTO/RPO
- Maintenance window

PVC capacity formula:

```text
Required PVC Size = Current Used + (Daily Growth * Retention Days) + Safety Buffer
```

Example:

```text
Current used: 120 GiB
Growth: 5 GiB/day
Retention: 30 days
Safety buffer: 25%
Required = 120 + (5 * 30) = 270 GiB
With 25% buffer = 337.5 GiB
Choose 350 GiB or 400 GiB
```

### 17.3 Prometheus PVC sizing considerations

Prometheus storage depends on:

```text
number_of_series * scrape_frequency * retention * bytes_per_sample
```

Risk multipliers:

- Too many pods/services/endpoints
- High-cardinality labels
- Short scrape interval
- Long retention
- Many histograms
- User workload metrics without label discipline

## 18. Common Production Scenarios

### Scenario 1: Node DiskPressure because application writes to container layer

Symptoms:

```text
Pod evicted
Node DiskPressure=True
PVC usage normal
/var/lib/containers grows fast
```

Diagnosis:

```bash
oc debug node/<node>
chroot /host
du -xh --max-depth=1 /var/lib/containers/storage | sort -h
```

Application check:

```bash
oc describe pod <pod> -n <ns>
oc logs <pod> -n <ns> --previous
```

Fix:

- Mount a PVC for data path.
- Configure app to write logs to stdout only.
- Set ephemeral-storage requests/limits.
- Set `emptyDir.sizeLimit` if using cache.

### Scenario 2: PVC full for database

Symptoms:

```text
Database errors: No space left on device
PVC > 95%
Pod still Running but app unhealthy
```

Fix path:

1. Confirm mount path with `df -h` inside pod.
2. Check database logs and WAL/archive growth.
3. Take backup/snapshot if required.
4. Expand PVC if supported.
5. Restart/remount if filesystem resize pending.
6. Fix retention/autovacuum/WAL cleanup.

### Scenario 3: Inodes exhausted but `df -h` shows free space

Symptoms:

```text
df -h shows 40% used
df -ih shows 100% inode usage
App cannot create files
```

Fix:

```bash
df -ih
find <mount> -xdev -type f | wc -l
find <mount> -xdev -type f | awk -F/ '{print "/"$2"/"$3"/"$4}' | sort | uniq -c | sort -n | tail
```

Remediation:

- Delete/compact small files safely.
- Change application file layout.
- Use object storage for many tiny objects.
- Recreate filesystem with more inodes if storage backend allows.

### Scenario 4: PVC Pending due to `WaitForFirstConsumer`

Symptoms:

```text
PVC Pending
Event: waiting for first consumer
No pod yet
```

This is normal for topology-aware storage. Create the pod and scheduler/provisioner will select appropriate zone/node topology.

Check:

```bash
oc describe sc <sc>
oc describe pvc <pvc> -n <ns>
oc get pod -n <ns>
```

### Scenario 5: Monitoring Prometheus PVC filling fast

Symptoms:

```text
Prometheus PVC grows rapidly
High prometheus_tsdb_head_series
Many user workload targets
```

Fix:

- Identify high-cardinality jobs.
- Review application labels.
- Reduce retention or increase storage.
- Configure remote write if needed.
- Tune scrape intervals.
- Remove unnecessary ServiceMonitors/PodMonitors.

## 20. Prevention Best Practices

### 20.1 For platform administrators

- Monitor node root, image, container, and inode usage.
- Alert before DiskPressure, not only after it happens.
- Use `KubeletConfig` carefully and consistently across MachineConfigPools.
- Keep node filesystem sizing aligned with workload density.
- Enforce log rotation and centralized logging.
- Set ephemeral-storage requests/limits in tenant policies.
- Use LimitRanges to default ephemeral-storage requests/limits where appropriate.
- Review high-write workloads before onboarding.
- Keep storage backend dashboards separate from PVC dashboards.
- Monitor CSI controller/node plugin health.
- Treat inode exhaustion as a first-class alert.

### 20.2 For application teams

- Do not write persistent data to container writable layer.
- Use PVC for durable data.
- Use object storage for unbounded file/object growth.
- Configure retention for logs, backups, WAL, cache, temporary exports.
- Add app-level storage metrics where possible.
- Provide expected growth rate during production onboarding.
- Use `emptyDir.sizeLimit` for cache/temp directories.
- Do not store backups on the same PVC as primary data.
- Test PVC expansion in lower environments.

### 20.3 For SRE/on-call

- Use runbooks linked in alert annotations.
- Route warning alerts to ticket queue; critical to pager.
- Suppress noisy trend alerts for batch PVCs if predictable.
- Alert on time-to-full, not only percentage.
- Maintain owner labels for namespaces and workloads.
- Keep storage dashboards visible during deployments and migrations.

## 24. Interview / Real-World Explanation

If asked, “How do you monitor disk pressure and PVC usage in OpenShift?” answer like this:

> I separate node-local disk pressure from persistent volume capacity. For node disk pressure, I monitor `DiskPressure` node conditions, disk-pressure taints, node filesystem usage, inode usage, and kubelet eviction behavior. I check `nodefs` and `imagefs` pressure sources such as `/var/lib/containers`, `/var/log`, `/var/lib/kubelet`, pod logs, image cache, and `emptyDir`. For PVC monitoring, I use `kubelet_volume_stats_used_bytes`, `available_bytes`, `capacity_bytes`, and inode metrics for actual mounted volume usage, and `kube_persistentvolumeclaim_*` metrics for object state such as Pending, Bound, Lost, storage class, requested size, and Terminating detection. I build alerts for node DiskPressure, filesystem/inode thresholds, PVC 80/90 percent usage, PVC filling prediction, Pending PVCs, and abnormal volume health. During troubleshooting I correlate Prometheus metrics with `oc describe node`, `oc describe pvc`, pod-to-PVC mapping, `df -hT`, `df -ih`, events, CSI pods, and storage backend dashboards.

## 25. Common Mistakes

| Mistake | Why it is bad | Correct approach |
|---|---|---|
| Monitoring only PVC percentage | Misses node DiskPressure and inode exhaustion | Monitor node, PVC, inode, and backend metrics |
| Ignoring inodes | Apps can fail with free bytes available | Alert on inode usage |
| Assuming PVC request equals usage | Request is not actual used capacity | Use kubelet volume stats |
| Expanding PVC without checking backend | Expansion can fail if backend full | Check CSI/storage backend first |
| Removing finalizers blindly | Can corrupt or leak storage resources | Confirm no pod/attachment/storage operation first |
| Manually deleting CRI-O files | Can break runtime state | Use safe cleanup and GC mechanisms |
| No `emptyDir` limits | Apps can fill node disk | Use `emptyDir.sizeLimit` and ephemeral-storage limits |
| No owner labels | Alerts cannot be routed well | Label namespaces/apps with owner/team/service |
| No growth prediction | Teams react too late | Add `predict_linear` or growth-rate alerts |
| Treating all PVCs equally | Batch workloads create noisy alerts | Tune alert thresholds by workload class |

## 29. Final Senior Admin Takeaway

For production OpenShift operations, disk pressure and PVC monitoring must be handled as a combined reliability practice:

```text
Node disk monitoring protects the platform.
PVC monitoring protects stateful applications.
Storage backend monitoring protects the storage system.
Alerting and runbooks connect all three into operations.
```

A strong OpenShift administrator does not wait for `DiskPressure=True` or `No space left on device`. They monitor trends, inodes, growth rate, PVC state, storage backend health, and workload behavior before applications fail.
