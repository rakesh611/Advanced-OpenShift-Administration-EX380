## 1. What Are Application Metrics?

**Application metrics** are measurements emitted by an application to describe its behavior, health, traffic, latency, errors, throughput, saturation, business events, and internal runtime state.

In OpenShift, application metrics are normally exposed by the application on an HTTP endpoint, commonly:

```text
/metrics
```

Prometheus scrapes that endpoint at regular intervals and stores the time-series data. OpenShift then allows administrators and developers to query, visualize, alert on, and optionally forward those metrics.

Example metrics exposed by an application:

```text
http_requests_total{method="GET",code="200",handler="/api/orders"} 12450
http_request_duration_seconds_bucket{le="0.5",handler="/api/orders"} 9800
process_resident_memory_bytes 82497536
jvm_threads_current 52
app_build_info{version="1.4.2",commit="9f3a1c"} 1
orders_created_total{payment_type="upi"} 450
```

These are different from Kubernetes or OpenShift platform metrics. Application metrics come from the workload itself or from a sidecar/exporter attached to the workload.

## 2. Why Application Metrics Matter for OpenShift Administrators

A senior OpenShift administrator is not only responsible for cluster health. In production, platform teams must also provide an observability foundation for applications running on the cluster.

Application metrics help answer questions like:

- Is the application healthy from a business and technical point of view?
- Is traffic increasing or decreasing?
- Is latency affecting users?
- Are 5xx errors increasing after a deployment?
- Is a particular route, API, tenant, or dependency causing failures?
- Is the workload under-provisioned or over-provisioned?
- Should the application scale horizontally?
- Did a canary or blue-green deployment introduce a regression?
- Are SLIs and SLOs being met?

For advanced administration, application metrics connect multiple OpenShift topics:

```text
Monitoring + RBAC + Networking + Service discovery + TLS + Operators + Alerting + Autoscaling + GitOps
```

## 3. Platform Metrics vs Application Metrics

| Area | Platform Metrics | Application Metrics |
|---|---|---|
| Source | OpenShift/Kubernetes components | User applications, exporters, sidecars |
| Namespace scope | `openshift-*`, `kube-*`, platform namespaces | User/application namespaces |
| Examples | API server latency, etcd metrics, node CPU, kubelet metrics | HTTP request rate, application latency, business counters |
| Managed by | Cluster Monitoring Operator | User workload monitoring stack |
| Prometheus instance | Platform Prometheus | User workload Prometheus |
| Primary users | Cluster admins, SREs | App teams, DevOps, SREs, platform admins |
| Scrape config object | Internal platform config | `ServiceMonitor`, `PodMonitor` |
| Alert rules | Platform rules | User-defined `PrometheusRule` |

Important distinction:

- **Cluster monitoring** watches OpenShift itself.
- **User workload monitoring** watches applications running in user-defined projects.

A production platform should avoid mixing custom application monitoring into platform namespaces.

## 4. OpenShift Application Metrics Architecture

High-level architecture:

```text
Application Pod
  |
  | exposes /metrics
  v
Service or Pod endpoint
  |
  | selected by ServiceMonitor or PodMonitor
  v
Prometheus Operator in openshift-user-workload-monitoring
  |
  | generates scrape config
  v
Prometheus user-workload
  |
  | stores scraped samples
  v
Thanos Querier
  |
  | provides unified query layer
  v
OpenShift Web Console Observe -> Metrics / Dashboards
  |
  v
Alerts, dashboards, SLOs, remote write, autoscaling integrations
```

Main components:

| Component | Namespace | Purpose |
|---|---|---|
| `cluster-monitoring-operator` | `openshift-monitoring` | Reconciles supported monitoring stack configuration |
| `prometheus-k8s` | `openshift-monitoring` | Scrapes platform metrics |
| `thanos-querier` | `openshift-monitoring` | Query layer for metrics |
| `prometheus-operator` | `openshift-user-workload-monitoring` | Watches `ServiceMonitor`, `PodMonitor`, `PrometheusRule` for user workloads |
| `prometheus-user-workload` | `openshift-user-workload-monitoring` | Scrapes user/application metrics |
| `thanos-ruler-user-workload` | `openshift-user-workload-monitoring` | Evaluates user-defined recording and alerting rules |
| Optional user workload Alertmanager | `openshift-user-workload-monitoring` | Dedicated alert routing for user-defined alerts |

## 5. User Workload Monitoring Concept

User workload monitoring is the supported OpenShift mechanism for collecting metrics from user-defined projects.

Instead of installing a separate unsupported Prometheus stack for every team, OpenShift provides a managed monitoring stack for user applications.

Key points:

- It is enabled by cluster administrators.
- It deploys user workload monitoring components in `openshift-user-workload-monitoring`.
- Application teams define what to scrape by using `ServiceMonitor` or `PodMonitor`.
- Alerting rules are defined with `PrometheusRule`.
- Developers can be given project-scoped permissions.
- The platform remains operator-managed and supportable.

Important support note:

Do not manually modify monitoring stack resources in `openshift-monitoring` or `openshift-user-workload-monitoring`. The Cluster Monitoring Operator reconciles them back to the supported state.

## 6. End-to-End Application Metrics Flow

A complete production flow looks like this:

```text
1. Developer instruments application with Prometheus client library.
2. Application exposes metrics endpoint, usually /metrics.
3. Deployment runs pod in user namespace.
4. Service exposes the metrics port with a named port.
5. ServiceMonitor selects the Service by label.
6. Prometheus Operator detects the ServiceMonitor.
7. Prometheus user-workload starts scraping the endpoint.
8. Metrics become queryable through Thanos Querier and OpenShift Observe UI.
9. PrometheusRule evaluates alerts or recording rules.
10. Alertmanager routes alerts to email, Slack, webhook, PagerDuty, etc.
11. Optional remoteWrite sends metrics to long-term storage.
```

## 7. Enable User Workload Monitoring

### 7.1 Create or Edit `cluster-monitoring-config`

User workload monitoring is enabled from the `openshift-monitoring` namespace:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Apply it:

```bash
oc apply -f cluster-monitoring-config.yaml
```

Or edit directly:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Add:

```yaml
data:
  config.yaml: |
    enableUserWorkload: true
```

### 7.2 Verify User Workload Monitoring Pods

```bash
oc -n openshift-user-workload-monitoring get pods
```

Expected components:

```text
prometheus-operator-xxxxx
prometheus-user-workload-0
prometheus-user-workload-1
thanos-ruler-user-workload-0
thanos-ruler-user-workload-1
```

Depending on configuration, you might also see user workload Alertmanager pods.

### 7.3 Check ConfigMap

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config -o yaml
oc -n openshift-user-workload-monitoring get configmap user-workload-monitoring-config -o yaml
```

When user workload monitoring is enabled, OpenShift creates or uses:

```text
openshift-user-workload-monitoring/user-workload-monitoring-config
```

## 8. Required RBAC and Roles

Application metrics are multi-tenant. OpenShift allows project-level permissions instead of giving all developers cluster-admin access.

Important roles:

| Role | Purpose |
|---|---|
| `monitoring-edit` | Create/edit/delete `ServiceMonitor`, `PodMonitor`, and `PrometheusRule` in a user project |
| `monitoring-rules-edit` | Create/edit/delete `PrometheusRule` only |
| `monitoring-rules-view` | View `PrometheusRule` resources |
| `pod-metrics-reader` | Access Thanos API endpoints for user-defined projects |
| `alert-routing-edit` | Create/edit/delete `AlertmanagerConfig` for user-defined alert routing |
| `user-workload-monitoring-config-edit` | Edit the user workload monitoring stack config in `openshift-user-workload-monitoring` |

Grant monitoring edit to a developer for one namespace:

```bash
oc adm policy add-cluster-role-to-user monitoring-edit alice -n payments
```

Grant alert routing edit for one namespace:

```bash
oc -n payments adm policy add-role-to-user alert-routing-edit alice
```

Grant user workload monitoring config edit:

```bash
oc -n openshift-user-workload-monitoring adm policy add-role-to-user \
  user-workload-monitoring-config-edit alice \
  --role-namespace openshift-user-workload-monitoring
```

Check permissions:

```bash
oc auth can-i create servicemonitors.monitoring.coreos.com -n payments --as alice
oc auth can-i create podmonitors.monitoring.coreos.com -n payments --as alice
oc auth can-i create prometheusrules.monitoring.coreos.com -n payments --as alice
```

## 9. Application Instrumentation Basics

Application instrumentation means adding code or an exporter so the application exposes metrics in Prometheus format.

Common approaches:

| Application Type | Common Instrumentation Method |
|---|---|
| Java / Spring Boot | Micrometer + Actuator Prometheus endpoint |
| Node.js | `prom-client` |
| Python | `prometheus_client` |
| Go | `prometheus/client_golang` |
| NGINX | NGINX exporter or ingress/router metrics |
| MySQL / PostgreSQL | Exporter sidecar or separate exporter deployment |
| JVM apps | JMX exporter |
| Custom binary | Prometheus client library |

A metrics endpoint should be:

- Lightweight
- Fast to respond
- Stable across releases
- Authenticated if sensitive
- Low-cardinality
- Exposed only inside the cluster unless intentionally public

Example endpoint:

```bash
curl http://my-app:8080/metrics
```

Example output:

```text
# HELP http_requests_total Total HTTP requests.
# TYPE http_requests_total counter
http_requests_total{method="GET",code="200"} 1027
http_requests_total{method="POST",code="500"} 3

# HELP app_active_sessions Current active sessions.
# TYPE app_active_sessions gauge
app_active_sessions 42
```

## 10. Prometheus Metric Types

### 10.1 Counter

A counter only increases. It resets only when the process restarts.

Use for:

- Request count
- Error count
- Jobs completed
- Messages consumed
- Orders created

Example:

```text
http_requests_total{method="GET",code="200"} 1000
```

Query rate:

```promql
rate(http_requests_total[5m])
```

### 10.2 Gauge

A gauge can go up or down.

Use for:

- Current memory usage
- Active sessions
- Queue depth
- Current connections
- In-flight requests

Example:

```text
app_active_sessions 42
```

### 10.3 Histogram

A histogram samples observations into buckets.

Use for:

- Request duration
- Database query duration
- Queue processing time
- API latency percentiles

Example:

```text
http_request_duration_seconds_bucket{le="0.1"} 100
http_request_duration_seconds_bucket{le="0.5"} 400
http_request_duration_seconds_bucket{le="1"} 480
http_request_duration_seconds_bucket{le="+Inf"} 500
http_request_duration_seconds_sum 95
http_request_duration_seconds_count 500
```

Calculate p95 latency:

```promql
histogram_quantile(
  0.95,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m]))
)
```

### 10.4 Summary

A summary calculates quantiles on the client side.

Use carefully because summaries are harder to aggregate across replicas.

For most OpenShift multi-pod workloads, prefer histograms over summaries for request latency.

## 11. Metric Naming and Labeling Standards

### 11.1 Good Metric Names

Use clear names with units:

```text
http_requests_total
http_request_duration_seconds
queue_depth
process_cpu_seconds_total
database_query_duration_seconds
```

Recommended suffixes:

| Suffix | Meaning |
|---|---|
| `_total` | Counter |
| `_seconds` | Duration |
| `_bytes` | Size |
| `_ratio` | Ratio |
| `_info` | Static build/version info |

### 11.2 Good Labels

Good labels have a small, bounded set of values:

```text
method="GET"
code="200"
route="/api/orders"
namespace="payments"
service="checkout"
version="v1"
```

### 11.3 Bad Labels

Avoid unbounded labels:

```text
user_id="123456"
customer_id="987654"
email="user@example.com"
request_id="1f4ac77c-..."
session_id="..."
full_url="/orders/123456/items/987654"
```

These create high cardinality and can overload Prometheus.

### 11.4 Correct Route Labeling

Bad:

```text
path="/api/orders/123456"
```

Good:

```text
route="/api/orders/{order_id}"
```

### 11.5 Cardinality Formula

Cardinality grows by label combinations:

```text
series = metric_name x label_value_1 x label_value_2 x label_value_3 ...
```

Example:

```text
100 routes x 5 status codes x 4 methods x 20 pods = 40,000 series
```

Add one bad label:

```text
40,000 series x 1,000,000 customer_id values = disaster
```

## 12. Expose an Application Metrics Endpoint

Example application deployment and service:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api

    metadata:
      labels:
        app: checkout-api
    spec:
      containers:

        - name: web
          containerPort: 8080

          containerPort: 8080

kind: Service
metadata:
  name: checkout-api
```

## 13. ServiceMonitor Deep Dive

A `ServiceMonitor` tells the Prometheus Operator how to scrape metrics from a Kubernetes/OpenShift Service.

### 13.1 Basic ServiceMonitor

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: checkout-api-monitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: checkout-api
  endpoints:
  - port: web
    path: /metrics
    interval: 30s
    scheme: http
```

Apply:

```bash
oc apply -f checkout-api-servicemonitor.yaml
```

Verify:

```bash
oc -n payments get servicemonitor
oc -n payments describe servicemonitor checkout-api-monitor
```

### 13.2 Important ServiceMonitor Details

#### The `port` Field Uses Service Port Name

This is a common exam and production mistake.

If the Service is:

```yaml
ports:
- name: web
  port: 8080
  targetPort: 8080
```

The ServiceMonitor must use:

```yaml
endpoints:
- port: web
```

Not:

```yaml
endpoints:
- port: 8080
```

#### Selector Matches Service Labels, Not Pod Labels Directly

ServiceMonitor selector checks the **Service metadata labels**:

```yaml
spec:
  selector:
    matchLabels:
      app: checkout-api
```

So this label must exist on the Service:

```yaml
metadata:
  labels:
    app: checkout-api
```

#### Namespace Scope

For user-defined projects, a `ServiceMonitor` in a user namespace discovers services in the same namespace. Do not depend on cross-namespace scraping from a user namespace.

#### Scrape Path

Default path is commonly `/metrics`, but define it explicitly for clarity:

```yaml
path: /metrics
```

#### Scrape Interval

```yaml
interval: 30s
```

Choose a reasonable interval:

| Environment | Suggested Interval |
|---|---|
| Dev/test | 30s to 60s |
| Production normal services | 15s to 60s |
| High-cardinality heavy services | 60s or higher |
| Critical SLO APIs | 15s to 30s |

Avoid scraping every few seconds unless there is a strong reason.

### 13.3 ServiceMonitor with Relabeling

Example: keep only targets with specific labels.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: checkout-api-monitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: checkout-api
  endpoints:
  - port: web
    path: /metrics
    interval: 30s
    relabelings:
    - sourceLabels: [__meta_kubernetes_pod_label_version]
      targetLabel: app_version
```

### 13.4 ServiceMonitor with Metric Relabeling

Use metric relabeling to drop noisy metrics after scrape but before ingestion.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: checkout-api-monitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: checkout-api
  endpoints:
  - port: web
    path: /metrics
    interval: 30s
    metricRelabelings:
    - sourceLabels: [__name__]
      regex: 'debug_.*'
      action: drop
```

Use this carefully. Dropping metrics can hide useful troubleshooting data.

### 13.5 ServiceMonitor with TLS

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: secure-api-monitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: secure-api
  endpoints:
  - port: metrics
    path: /metrics
    scheme: https
    interval: 30s
    tlsConfig:
      ca:
        secret:
          name: metrics-ca
          key: ca.crt
      serverName: secure-api.payments.svc
```

### 13.6 ServiceMonitor with Bearer Token

Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: metrics-bearer-auth
  namespace: payments
stringData:
  token: REPLACE_WITH_TOKEN
```

ServiceMonitor:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: checkout-api-monitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: checkout-api
  endpoints:
  - port: web
    path: /metrics
    authorization:
      credentials:
        name: metrics-bearer-auth
        key: token
```

Do not use `bearerTokenFile` for user workload `ServiceMonitor` authentication. Use Secret-based credentials.

## 14. PodMonitor Deep Dive

A `PodMonitor` scrapes pods directly without requiring a Service.

Basic example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: checkout-api-podmonitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: checkout-api
  podMetricsEndpoints:
  - port: web
    path: /metrics
    interval: 30s
```

Use `PodMonitor` when:

- There is no Service.
- You need to scrape sidecars directly.
- You are monitoring batch-like or internal pods.
- The Service abstraction hides the actual metrics endpoints you need.

Be careful:

- PodMonitor selects pods directly.
- If pod labels are too broad, Prometheus might scrape too many targets.
- For stable application services, `ServiceMonitor` is often cleaner.

## 15. ServiceMonitor vs PodMonitor

| Feature | ServiceMonitor | PodMonitor |
|---|---|---|
| Scrapes | Services/endpoints | Pods directly |
| Requires Service | Yes | No |
| Selector matches | Service labels | Pod labels |
| Best for | Normal applications exposed by Service | Sidecars, pods without Service, custom scraping |
| Common production choice | Yes | Sometimes |
| Common mistake | Port name mismatch | Pod label too broad |

Rule of thumb:

```text
If the app has a stable Service, use ServiceMonitor.
If the metrics endpoint exists only on pods or sidecars, use PodMonitor.
```

## 16. Securing Application Metrics

Application metrics may expose sensitive details:

- Internal endpoint names
- Business volume
- Tenant names
- Error patterns
- Build versions
- Dependency names
- JVM/runtime internals

### 16.1 Network Exposure

Do not expose `/metrics` publicly unless required.

Prefer:

```text
ClusterIP Service + ServiceMonitor
```

Avoid:

```text
Public Route directly exposing /metrics
```

### 16.2 Use NetworkPolicy

Example: only allow traffic from monitoring namespace to metrics port.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-monitoring-to-metrics
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: checkout-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-user-workload-monitoring
    ports:
    - protocol: TCP
      port: 8080
```

Note: confirm namespace labels in your cluster before relying on them.

### 16.3 TLS for Metrics

Use HTTPS for sensitive metrics endpoints.

```yaml
scheme: https
tlsConfig:
  ca:
    secret:
      name: metrics-ca
      key: ca.crt
```

### 16.4 Authentication

Use Secret-based bearer token, basic auth, OAuth2, or TLS client authentication where appropriate.

### 16.5 RBAC for Viewing Metrics

Do not give all teams cluster-wide metrics access. Use project-scoped roles.

## 17. Query Application Metrics

### 17.1 OpenShift Web Console

Go to:

```text
Observe -> Metrics
```

Developers with permission can query metrics for their selected project. Cluster administrators can query across projects.

Example query:

```promql
up{namespace="payments"}
```

### 17.2 Query Thanos Querier from CLI

Get Thanos Querier route:

```bash
THANOS_HOST=$(oc get route -n openshift-monitoring thanos-querier -o jsonpath='{.status.ingress[0].host}')
```

Get token:

```bash
TOKEN=$(oc whoami -t)
```

Query metadata:

```bash
curl -k -H "Authorization: Bearer ${TOKEN}" \
  "https://${THANOS_HOST}/api/v1/metadata"
```

Query a metric:

```bash
curl -k -G -H "Authorization: Bearer ${TOKEN}" \
  "https://${THANOS_HOST}/api/v1/query" \
  --data-urlencode 'query=up{namespace="payments"}'
```

Range query:

```bash
curl -k -G -H "Authorization: Bearer ${TOKEN}" \
  "https://${THANOS_HOST}/api/v1/query_range" \
  --data-urlencode 'query=rate(http_requests_total{namespace="payments"}[5m])' \
  --data-urlencode 'start=2026-07-03T00:00:00Z' \
  --data-urlencode 'end=2026-07-03T01:00:00Z' \
  --data-urlencode 'step=30s'
```

## 18. Useful PromQL for Application Metrics

### 18.1 Is My Target Being Scraped?

```promql
up{namespace="payments"}
```

`1` means target is up.  
`0` means scrape target is discovered but failing.

### 18.2 Request Rate

```promql
sum by (route) (
  rate(http_requests_total{namespace="payments"}[5m])
)
```

### 18.3 Error Rate

```promql
sum(rate(http_requests_total{namespace="payments",code=~"5.."}[5m]))
/
sum(rate(http_requests_total{namespace="payments"}[5m]))
```

### 18.4 Error Rate by Route

```promql
sum by (route) (rate(http_requests_total{namespace="payments",code=~"5.."}[5m]))
/
sum by (route) (rate(http_requests_total{namespace="payments"}[5m]))
```

### 18.5 p95 Latency by Route

```promql
histogram_quantile(
  0.95,
  sum by (le, route) (
    rate(http_request_duration_seconds_bucket{namespace="payments"}[5m])
  )
)
```

### 18.6 p99 Latency

```promql
histogram_quantile(
```

## 19. Application Alerting with PrometheusRule

A `PrometheusRule` defines alerting and recording rules for user workloads.

### 19.1 High Error Rate Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: checkout-api-alerts
  namespace: payments
spec:
  groups:
  - name: checkout-api.rules
    rules:
    - alert: CheckoutAPIHighErrorRate
      expr: |
        sum(rate(http_requests_total{namespace="payments",app="checkout-api",code=~"5.."}[5m]))
        /
        sum(rate(http_requests_total{namespace="payments",app="checkout-api"}[5m]))
        > 0.05
      for: 10m
      labels:
        severity: warning
        team: payments
      annotations:
        summary: "Checkout API high 5xx error rate"
        description: "Checkout API 5xx error rate is above 5% for more than 10 minutes."
```

### 19.2 High p95 Latency Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: checkout-api-latency-alerts
  namespace: payments
spec:
  groups:
  - name: checkout-api.latency
    rules:
    - alert: CheckoutAPIHighP95Latency
      expr: |
        histogram_quantile(
          0.95,
          sum by (le) (
            rate(http_request_duration_seconds_bucket{namespace="payments",app="checkout-api"}[5m])
          )
        ) > 1
      for: 10m
      labels:
        severity: critical
        team: payments
      annotations:
        summary: "Checkout API p95 latency is high"
        description: "p95 latency is above 1 second for more than 10 minutes."
```

### 19.3 Target Down Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: checkout-api-target-alerts
  namespace: payments
spec:
  groups:
  - name: checkout-api.target
    rules:
    - alert: CheckoutAPIMetricsTargetDown
      expr: up{namespace="payments",service="checkout-api"} == 0
      for: 5m
      labels:
        severity: warning
        team: payments
      annotations:
        summary: "Checkout API metrics target is down"
        description: "Prometheus cannot scrape checkout-api metrics for more than 5 minutes."
```

### 19.4 Recording Rule for Error Rate

Recording rules precompute expensive queries.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: checkout-api-recording-rules
  namespace: payments
spec:
  groups:
  - name: checkout-api.recording
    rules:
    - record: namespace_app:http_5xx_error_rate:ratio5m
      expr: |
        sum by (namespace, app) (rate(http_requests_total{code=~"5.."}[5m]))
        /
        sum by (namespace, app) (rate(http_requests_total[5m]))
```

Then query:

```promql
namespace_app:http_5xx_error_rate:ratio5m{namespace="payments",app="checkout-api"}
```

## 20. Dashboards and Visualization

Application dashboards should be designed around service health, not only infrastructure graphs.

A useful application dashboard includes:

| Panel | PromQL Example |
|---|---|
| Request rate | `sum(rate(http_requests_total[5m]))` |
| Error rate | `sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))` |
| p95 latency | `histogram_quantile(0.95, sum by(le)(rate(http_request_duration_seconds_bucket[5m])))` |
| Saturation | CPU, memory, queue depth, connection pool usage |
| Pod health | Restarts, ready replicas, unavailable replicas |
| Dependency health | DB latency, external API failures |
| Business metric | Orders, payments, logins, messages processed |

Dashboard design principle:

```text
Start with user impact, then drill down into application internals, then infrastructure.
```

Suggested golden signals:

1. **Traffic**: request rate, messages consumed, transactions per second.
2. **Errors**: 4xx/5xx, failed jobs, dependency errors.
3. **Latency**: p50, p95, p99.
4. **Saturation**: CPU, memory, queue depth, thread pool usage, connection pool usage.

## 21. Application Metrics and Autoscaling

Application metrics can be used for autoscaling when CPU/memory are not enough.

Examples:

- Scale workers based on queue length.
- Scale API pods based on requests per second.
- Scale consumers based on Kafka lag.
- Scale jobs based on pending work items.

In OpenShift, custom/external metric-based scaling is commonly handled with the **Custom Metrics Autoscaler Operator** based on KEDA.

Example scaling signals:

```text
queue_depth
kafka_consumer_lag
http_requests_per_second
pending_jobs
rabbitmq_queue_messages
```

Important production rule:

Do not autoscale directly on noisy metrics without smoothing.

Prefer:

```promql
avg_over_time(queue_depth[5m])
```

or KEDA scaler cooldown/stabilization settings.

## 22. Retention, Storage, and Remote Write

### 22.1 User Workload Prometheus Retention

Retention for user workload Prometheus can be configured in:

```text
openshift-user-workload-monitoring/user-workload-monitoring-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      retention: 24h
      retentionSize: 10GB
```

Apply/edit:

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

### 22.2 Thanos Ruler Retention

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    thanosRuler:
      retention: 10d
```

### 22.3 Remote Write

Remote write sends ingested metrics to external systems for long-term retention and centralized observability.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      remoteWrite:
      - url: "https://remote-write-endpoint.example.com"
        writeRelabelConfigs:
        - sourceLabels: [__name__, namespace]
          regex: '(http_requests_total|http_request_duration_seconds_.*);payments'
          action: keep
```

Use remote write carefully:

- Use HTTPS.
- Use authentication.
- Use relabeling to avoid sending unnecessary data.
- Monitor queue failures and remote write lag.
- Confirm the receiver is sized for your metrics volume.

## 23. Cardinality and Performance Management

High cardinality is one of the biggest production risks in Prometheus-based monitoring.

### 23.1 What Causes High Cardinality?

Bad labels:

```text
user_id
session_id
transaction_id
request_id
email
ip_address
full_url
customer_id
container_id
```

High-cardinality patterns:

```text
http_requests_total{path="/orders/100001"}
http_requests_total{path="/orders/100002"}
http_requests_total{path="/orders/100003"}
```

Better:

```text
http_requests_total{route="/orders/{order_id}"}
```

### 23.2 Symptoms of High Cardinality

- Prometheus disk usage grows quickly.
- Query latency increases.
- Metrics UI times out.
- Prometheus pod memory increases.
- `KubePersistentVolumeFillingUp` alert fires.
- Scrape samples are very high for one namespace/job.

### 23.3 Find Heavy Jobs

```promql
topk(10, max by(namespace, job) (
  topk by(namespace, job) (1, scrape_samples_post_metric_relabeling)
))
```

### 23.4 Find Series Churn

```promql
topk(10, sum by(namespace, job) (
  sum_over_time(scrape_series_added[1h])
))
```

### 23.5 TSDB Status API

```bash
HOST=$(oc -n openshift-monitoring get route prometheus-k8s -o jsonpath='{.status.ingress[].host}')
TOKEN=$(oc whoami -t)

curl -H "Authorization: Bearer $TOKEN" -k \
  "https://$HOST/api/v1/status/tsdb"
```

### 23.6 Cardinality Controls

Use these controls:

- Educate developers on metric labels.
- Review application metrics before production onboarding.
- Drop noisy metrics with `metricRelabelings` only when justified.
- Increase scrape interval for noisy targets.
- Enforce sample limits if required.
- Use recording rules for expensive PromQL.
- Remote write only required metrics.

## 24. Multi-Tenant Monitoring Design

In enterprise OpenShift clusters, many teams share one platform. Application metrics must be designed with tenancy boundaries.

### 24.1 Namespace Ownership

Each team owns metrics in its own namespace:

```text
payments
orders
inventory
billing
platform-tools
```

Each team can have:

```text
ServiceMonitor
PodMonitor
PrometheusRule
AlertmanagerConfig
```

### 24.2 Project-Scoped Permissions

Give teams `monitoring-edit` only in their namespaces:

```bash
oc adm policy add-cluster-role-to-user monitoring-edit payments-devops -n payments
```

### 24.3 Exclude a Namespace from User Monitoring

To exclude a project:

```bash
oc label namespace my-project 'openshift.io/user-monitoring=false'
```

Remove exclusion:

```bash
oc label namespace my-project 'openshift.io/user-monitoring-'
```

### 24.4 Avoid Platform Namespaces

Do not create application `ServiceMonitor`, `PodMonitor`, or `PrometheusRule` objects in:

```text
openshift-*
kube-*
default
```

Use user-defined namespaces.

### 24.5 Governance Model

Recommended governance:

| Control | Owner |
|---|---|
| Enable user workload monitoring | Cluster admin |
| Configure retention/remote write | Platform/SRE team |
| Define application ServiceMonitor | App team or platform team |
| Define alert rules | App team with SRE review |
| Alert routing | App team, approved by platform |
| Cardinality review | Platform/SRE |
| Dashboard ownership | App team |

## 25. Troubleshooting Application Metrics

### 25.1 Problem: Metrics Not Visible in Observe UI

Checklist:

```bash
oc -n openshift-user-workload-monitoring get pods
oc -n payments get servicemonitor,podmonitor,prometheusrule
oc -n payments get svc
oc -n payments get endpoints
oc -n payments get pods --show-labels
```

Check namespace exclusion:

```bash
oc get namespace payments --show-labels | grep 'openshift.io/user-monitoring=false'
```

Check ServiceMonitor labels:

```bash
oc -n payments get servicemonitor checkout-api-monitor --show-labels
```

Check Service labels:

```bash
oc -n payments get service checkout-api --show-labels
```

Common cause:

```text
ServiceMonitor selector does not match Service metadata.labels.
```

### 25.2 Problem: ServiceMonitor Exists but No Targets

Check ServiceMonitor:

```bash
oc -n payments get servicemonitor checkout-api-monitor -o yaml
```

Check Service:

```bash
oc -n payments get svc checkout-api -o yaml
```

Verify:

- ServiceMonitor namespace is correct.
- Service has matching labels.
- Service port name matches `endpoints[].port`.
- Service has endpoints.
- Pods are ready.
- Application exposes `/metrics`.

### 25.3 Problem: Port Name Mismatch

Service:

```yaml
ports:
- name: http
  port: 8080
```

Wrong ServiceMonitor:

```yaml
endpoints:
- port: web
```

Correct:

```yaml
endpoints:
- port: http
```

### 25.4 Problem: Service Has No Endpoints

```bash
oc -n payments get endpoints checkout-api
```

If empty:

```bash
oc -n payments get svc checkout-api -o yaml
oc -n payments get pods --show-labels
```

Service selector must match pod labels:

```yaml
spec:
  selector:
    app: checkout-api
```

Pod must have:

```yaml
metadata:
  labels:
    app: checkout-api
```

### 25.5 Problem: `/metrics` Endpoint Fails

Test inside namespace:

```bash
oc -n payments run curl-test --rm -it --image=curlimages/curl --restart=Never -- \
  curl -v http://checkout-api:8080/metrics
```

Check pod logs:

```bash
oc -n payments logs deploy/checkout-api
```

Check application port:

```bash
oc -n payments get pod -l app=checkout-api -o yaml | grep -A5 ports
```

### 25.6 Problem: Target Down Due to TLS

Symptoms:

```text
x509: certificate signed by unknown authority
server name mismatch
connection refused
```

Fix:

- Use correct `scheme: https`.
- Provide CA Secret in `tlsConfig`.
- Configure `serverName` correctly.
- Confirm certificate CN/SAN matches service DNS.

### 25.7 Problem: NetworkPolicy Blocks Scrape

Check policies:

```bash
oc -n payments get networkpolicy
oc -n payments describe networkpolicy allow-monitoring-to-metrics
```

Temporary test:

```bash
oc -n payments run test --rm -it --image=curlimages/curl --restart=Never -- \
  curl http://checkout-api:8080/metrics
```

If Prometheus cannot scrape but in-namespace curl works, check ingress policy from monitoring namespace.

### 25.8 Problem: High Disk Usage in Prometheus

Check high scrape samples:

```promql
topk(10, max by(namespace, job) (
  topk by(namespace, job) (1, scrape_samples_post_metric_relabeling)
))
```

Check churn:

```promql
topk(10, sum by(namespace, job) (
  sum_over_time(scrape_series_added[1h])
))
```

Fix:

- Remove unbounded labels.
- Drop unnecessary metrics.
- Increase scrape interval.
- Reduce histogram bucket count.
- Configure retention and retention size.
- Review remote write filters.

### 25.9 Problem: PrometheusRule Not Firing

Check rule exists:

```bash
oc -n payments get prometheusrule
oc -n payments describe prometheusrule checkout-api-alerts
```

Check expression manually in Observe -> Metrics.

Check labels:

```bash
oc -n payments get prometheusrule checkout-api-alerts -o yaml
```

Common issues:

- Wrong metric name.
- Wrong namespace label.
- Expression returns empty vector.
- `for:` duration not satisfied.
- Alert exists but route/receiver not configured.

### 25.10 Problem: Developer Cannot Create ServiceMonitor

Check permission:

```bash
oc auth can-i create servicemonitors.monitoring.coreos.com -n payments --as alice
```

Grant:

```bash
oc adm policy add-cluster-role-to-user monitoring-edit alice -n payments
```

## 26. Production Best Practices

### 26.1 Platform Best Practices

- Enable user workload monitoring instead of installing separate Prometheus instances.
- Keep monitoring stack operator-managed.
- Configure persistent storage and retention based on workload volume.
- Use project-scoped RBAC.
- Enforce naming and labeling standards.
- Review high-cardinality metrics before production release.
- Use remote write for long-term retention when required.
- Keep application monitoring resources out of `openshift-*` and `kube-*` namespaces.

### 26.2 Application Team Best Practices

- Expose `/metrics` on an internal port.
- Use histograms for latency.
- Use counters for requests and errors.
- Use bounded labels only.
- Define SLIs before alerts.
- Use alerts based on user impact.
- Provide dashboards with traffic, errors, latency, and saturation.
- Test metrics during CI/CD or pre-production.

### 26.3 Alerting Best Practices

Bad alert:

```text
CPU above 80% for 1 minute
```

Better alert:

```text
p95 latency above SLO and error rate above threshold for 10 minutes
```

Good alert properties:

- Actionable
- User-impacting
- Has clear ownership
- Has runbook link
- Has severity
- Avoids flapping

Example annotation pattern:

```yaml
annotations:
  summary: "Checkout API error rate is high"
  description: "5xx error rate is above 5% for 10 minutes in namespace payments."
  runbook_url: "https://internal.example.com/runbooks/checkout-api-high-error-rate"
```

### 26.4 Scrape Interval Best Practices

Avoid setting aggressive scrape intervals for every app.

Recommended default:

```yaml
interval: 30s
```

For high-volume applications:

```yaml
interval: 60s
```

For critical SLO services:

```yaml
interval: 15s
```

### 26.5 Histogram Bucket Best Practices

Bad: too many buckets for every route.

Good: buckets aligned to SLO.

Example for HTTP latency:

```text
0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10
```

If your SLO is 500 ms, ensure buckets around:

```text
0.25, 0.5, 1
```

## 28. Interview and Real-World Scenario Notes

### Scenario 1: Developer Says Metrics Are Not Showing

Senior admin approach:

```text
1. Confirm user workload monitoring is enabled.
2. Confirm prometheus-user-workload pods are running.
3. Confirm namespace is not excluded.
4. Confirm ServiceMonitor exists in the same namespace.
5. Confirm ServiceMonitor selector matches Service labels.
6. Confirm Service port name matches ServiceMonitor endpoint port.
7. Confirm Service has endpoints.
8. Curl /metrics from inside the cluster.
9. Check TLS/auth/network policy.
10. Query up{namespace="..."}.
11. Check Prometheus Operator logs if needed.
```

### Scenario 2: Prometheus Disk Is Filling Fast

Likely causes:

- High-cardinality labels.
- Too many histogram buckets.
- Very short scrape interval.
- Too many pods/targets.
- No retention size limit.
- Unnecessary debug metrics.

Admin response:

```text
1. Identify high sample jobs.
2. Identify series churn.
3. Review app labels.
4. Drop or fix bad metrics.
5. Increase scrape interval.
6. Configure retention/retentionSize.
7. Consider remote write for long-term retention.
```

### Scenario 3: Alerts Are Not Reaching Team

Check:

```text
1. Is PrometheusRule valid?
2. Does the expression return data?
3. Has the for: duration elapsed?
4. Is alert routing enabled for user-defined projects?
5. Is AlertmanagerConfig configured?
6. Does the user have alert-routing-edit role?
7. Are receiver credentials correct?
```

### Scenario 4: Team Wants Cross-Namespace Scraping

Best answer:

```text
For user workload monitoring, keep ServiceMonitor/PodMonitor resources namespace-scoped.
Create monitoring resources in each application namespace or use a platform-managed pattern approved by cluster administrators.
Do not depend on unsupported cross-namespace scraping behavior in user projects.
```

### Scenario 5: Team Wants to Install Its Own Prometheus Operator

Best answer:

```text
Use OpenShift user workload monitoring first. Installing custom Prometheus instances managed by a separate Prometheus Operator is not the supported default path for OpenShift monitoring and can create operational/support problems. If a separate stack is required, validate support boundaries and ownership clearly.
```

# Final Summary

Application metrics in OpenShift are collected through the supported **user workload monitoring** stack. The application exposes `/metrics`; a `ServiceMonitor` or `PodMonitor` defines how Prometheus scrapes it; `prometheus-user-workload` stores it; Thanos Querier makes it queryable; and `PrometheusRule` plus Alertmanager provide alerting.

For a senior OpenShift administrator, the most important skills are:

- Enable and verify user workload monitoring.
- Understand `ServiceMonitor`, `PodMonitor`, and `PrometheusRule` deeply.
- Troubleshoot label, port, endpoint, TLS, RBAC, and NetworkPolicy issues.
- Control metric cardinality before it damages Prometheus performance.
- Design project-scoped, secure, multi-tenant monitoring.
- Use PromQL to build dashboards, alerts, and SLO views.
- Keep the monitoring stack operator-managed and supportable.
