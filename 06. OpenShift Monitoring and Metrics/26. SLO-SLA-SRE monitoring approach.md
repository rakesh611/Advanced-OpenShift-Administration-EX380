## 1. Executive Summary

A mature OpenShift monitoring approach should not only ask:

> “Is the pod running?”

It should ask:

> “Are users receiving the service at the reliability level we promised?”

That is the purpose of **SLO/SLA/SRE monitoring**.

Traditional monitoring focuses on infrastructure symptoms: CPU high, memory high, pod restart, disk full, node not ready, target down. These are still important, but they do not directly tell whether the customer journey is healthy.

SRE-style monitoring starts from **user-visible reliability**:

- Can users reach the service?
- Are requests succeeding?
- Is latency within acceptable limits?
- Is the API behaving correctly?
- Is the platform stable enough for workloads?
- Is error budget being consumed too fast?
- Should we page someone, create a ticket, pause releases, or continue normally?

In OpenShift, the practical implementation uses:

- **Prometheus** for metric collection and PromQL query evaluation.
- **Thanos Querier** for querying platform and user workload metrics through a unified interface.
- **Thanos Ruler** for user workload rule evaluation in the user workload monitoring stack.
- **Alertmanager** for routing, grouping, silencing, and inhibiting alerts.
- **ServiceMonitor / PodMonitor** for scraping application metrics.
- **PrometheusRule** for recording rules and alerting rules.
- **OpenShift Console Observe pages** for metrics, dashboards, alerts, silences, and alerting rules.
- **GitOps** for version-controlling SLO rules, dashboards, AlertmanagerConfig, and runbook links.

A 10-year experienced OpenShift administrator should design monitoring around four layers:

| Layer | Purpose | Example |
|---|---|---|
| Business reliability | SLA/SLO compliance | 99.9% checkout availability |
| User journey | SLIs | request success ratio, p95 latency |
| Application/platform symptoms | Early diagnosis | 5xx rate, pod restarts, queue depth |
| Infrastructure saturation | Capacity and prevention | CPU, memory, disk, PVC, network, API latency |

The best production pattern is:

1. Define critical user journeys.
2. Define SLIs for those journeys.
3. Set SLO targets and rolling windows.
4. Calculate error budget.
5. Convert raw metrics into recording rules.
6. Alert on **error budget burn rate**, not random thresholds only.
7. Route alerts based on user impact.
8. Link every alert to a runbook.
9. Review SLO reports monthly.
10. Use error budget to control release velocity and reliability work.

## 2. SLA, SLO, SLI, SRE, Error Budget: Exact Meaning

### 2.1 SRE

**SRE** means Site Reliability Engineering. It is an engineering discipline that applies software engineering, automation, observability, and operational discipline to run reliable systems.

An SRE team does not only restart pods or clear alerts. A mature SRE team owns:

- Reliability targets.
- Automation.
- Incident response.
- Error budget policy.
- Postmortems.
- Capacity planning.
- Production readiness reviews.
- Change risk management.
- Monitoring quality.
- Runbooks.
- Toil reduction.

In OpenShift, SRE work usually includes:

- Cluster health monitoring.
- API server performance.
- etcd stability.
- Ingress/router reliability.
- Node pressure management.
- PVC/storage availability.
- Application SLO monitoring.
- Alert routing and noise reduction.
- Platform upgrade reliability.
- Operator health.
- Tenant monitoring enablement.

### 2.2 SLA

**SLA** means Service Level Agreement.

It is usually a contractual or business commitment between a provider and a customer.

Example:

> The production application will be available 99.9% per calendar month, excluding approved maintenance windows.

SLA failure can have business impact:

- Penalty.
- Service credit.
- Escalation.
- Customer dissatisfaction.
- Compliance issue.
- Management review.

SLA should be fewer in number, business-friendly, and measurable.

### 2.3 SLO

**SLO** means Service Level Objective.

It is an internal reliability target used by engineering and operations teams.

Example:

> 99.95% of checkout API requests should return successful responses within 500 ms over a rolling 30-day window.

SLO is stricter and more operational than SLA. Usually, SLO should be equal to or stronger than SLA.

Example:

| Business SLA | Internal SLO |
|---|---|
| 99.9% monthly availability | 99.95% rolling 30-day availability |
| Response time under 2 seconds | p95 latency under 800 ms |
| Support response in 30 min | page within 5 min for severe burn-rate alert |

### 2.4 SLI

**SLI** means Service Level Indicator.

It is the actual metric used to measure service behavior.

Example SLIs:

- Availability SLI: successful requests / total requests.
- Latency SLI: percentage of requests under threshold.
- Error SLI: failed requests / total requests.
- Durability SLI: successful writes / total writes.
- Freshness SLI: events processed within expected time / total events.
- Control plane SLI: successful API requests / total API requests.

A good SLI must be:

- User-impact based.
- Measurable from metrics/logs/traces/probes.
- Hard to fake.
- Stable over time.
- Owned by a service/team.
- Linked to an SLO.

### 2.5 Error Budget

**Error budget** is the allowed unreliability.

Formula:

```text
Error budget = 1 - SLO target
```

For a 99.9% SLO:

```text
Error budget = 1 - 0.999 = 0.001 = 0.1%
```

Meaning:

- 99.9% service must be good.
- 0.1% can be bad.
- That 0.1% is your allowed error budget.

For a 30-day month:

| SLO | Allowed downtime/error budget over 30 days |
|---|---:|
| 99.0% | ~7h 12m |
| 99.5% | ~3h 36m |
| 99.9% | ~43m 12s |
| 99.95% | ~21m 36s |
| 99.99% | ~4m 19s |

Error budget is powerful because it converts reliability into a decision-making tool.

If the service is within budget:

- Continue feature releases.
- Accept controlled risk.
- Improve reliability gradually.

If budget is burning fast:

- Page on-call.
- Stop risky deployments.
- Roll back recent change.
- Prioritize reliability bug fixes.
- Increase capacity.
- Create incident/postmortem.

## 3. Why Traditional Monitoring Is Not Enough

### 3.1 Traditional OpenShift Monitoring

Traditional monitoring checks things like:

```bash
oc get nodes
oc get pods -A
oc get co
oc get mcp
oc get pvc -A
oc adm top nodes
oc adm top pods -A
```

Typical alerts:

- NodeNotReady
- PodCrashLooping
- KubePersistentVolumeFillingUp
- TargetDown
- Watchdog
- HighCPUUsage
- HighMemoryUsage
- DiskPressure
- APIServerDown

These alerts are important, but many do not directly represent customer pain.

Example:

- A pod restarted once, but traffic was served by other replicas. No user impact.
- CPU is 90%, but latency is fine. No page required.
- One Prometheus target is down, but it is a non-production canary app. Ticket, not page.
- API p99 latency is high for failed/rare requests, but normal user path is healthy.

### 3.2 SRE-Style Monitoring

SRE monitoring reduces noise by prioritizing user impact.

Instead of alerting only on symptoms:

```text
CPU > 90%
```

Alert on impact:

```text
Checkout success ratio is below SLO and error budget is burning fast.
```

Then use CPU, memory, node, PVC, API latency, and logs as diagnostic signals.

### 3.3 Alerting Rule Maturity

| Maturity | Alert Type | Example | Problem |
|---|---|---|---|
| Level 1 | Resource threshold | CPU > 90% | Often noisy |
| Level 2 | Component health | Pod restarts > 5 | Better but not user focused |
| Level 3 | Service symptom | 5xx > 5% | Good, but threshold may be arbitrary |
| Level 4 | SLO burn rate | 2% budget burned in 1 hour | Best for paging |
| Level 5 | Error budget policy | auto-freeze release on budget breach | Mature SRE governance |

A 10-year OpenShift administrator should know all levels but design paging around Level 4 and Level 5.

## 4. OpenShift Monitoring Stack Mapping to SRE

OpenShift includes a managed monitoring stack based on Prometheus and related components.

### 4.1 Main Components

| Component | Namespace | Role in SRE Monitoring |
|---|---|---|
| Cluster Monitoring Operator | `openshift-monitoring` | Deploys and manages monitoring stack components |
| Prometheus Operator | `openshift-monitoring`, `openshift-user-workload-monitoring` | Watches ServiceMonitor, PodMonitor, PrometheusRule resources |
| Prometheus | Platform and user workload stack | Scrapes metrics and evaluates rules |
| Thanos Querier | `openshift-monitoring` | Unified query interface for platform and user workload metrics |
| Thanos Ruler | `openshift-user-workload-monitoring` | Evaluates user workload rules and alerts |
| Alertmanager | Platform and optional user workload | Routes, groups, silences, inhibits alerts |
| kube-state-metrics | Platform stack | Exposes Kubernetes object state metrics |
| openshift-state-metrics | Platform stack | Exposes OpenShift-specific object metrics |
| node-exporter | Every node | Exposes node OS/kernel/hardware metrics |
| Metrics Server | Platform stack | Exposes resource metrics through `metrics.k8s.io` |
| monitoring-plugin | Console | Provides Observe pages in OpenShift web console |

### 4.2 How SLO Monitoring Flows

```text
Application exposes /metrics
        |
        v
ServiceMonitor or PodMonitor selects endpoint
        |
        v
Prometheus scrapes metrics
        |
        v
PrometheusRule records SLI ratios and burn rates
        |
        v
Alertmanager receives firing alerts
        |
        v
Alertmanager routes page/ticket notifications
        |
        v
SRE responds using runbook and dashboard
        |
        v
Postmortem updates SLO, alert, dashboard, automation
```

### 4.3 HA Behavior

In multi-node OpenShift clusters, key monitoring components run in high availability mode. Prometheus, Alertmanager, Thanos Ruler, Thanos Querier, Metrics Server, and the monitoring plugin are replicated across pods where applicable. For production, stateful components such as Prometheus, Alertmanager, and Thanos Ruler should use persistent storage.

Operational point:

```bash
oc -n openshift-monitoring get pods
oc -n openshift-user-workload-monitoring get pods
oc -n openshift-monitoring get pvc
oc -n openshift-user-workload-monitoring get pvc
```

Do not manually edit monitoring stack resources owned by OpenShift operators. Use supported ConfigMap and CR-based configuration patterns.

## 5. Platform vs User Workload Monitoring

OpenShift monitoring is split into two areas.

### 5.1 Platform Monitoring

Platform monitoring covers core cluster components.

Namespace:

```text
openshift-monitoring
```

Examples:

- API server
- etcd
- scheduler
- controller manager
- kubelet
- CoreDNS
- ingress/router
- image registry
- Cluster Operators
- Machine Config Operator
- node-exporter
- kube-state-metrics
- openshift-state-metrics

Platform monitoring is managed by OpenShift and should not be customized by creating arbitrary ServiceMonitor, PodMonitor, or PrometheusRule resources inside `openshift-*` or `kube-*` namespaces unless the specific configuration is supported.

### 5.2 User Workload Monitoring

User workload monitoring covers application namespaces.

Namespace:

```text
openshift-user-workload-monitoring
```

It allows application teams to monitor their own workloads using:

- ServiceMonitor
- PodMonitor
- PrometheusRule
- AlertmanagerConfig
- custom dashboards in console-supported patterns

Enable user workload monitoring:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Apply or edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get pods
```

Expected components:

```text
prometheus-operator
prometheus-user-workload
thanos-ruler-user-workload
alertmanager-user-workload   # if enabled/configured
```

### 5.3 Project Exclusion

A namespace can be excluded from user workload monitoring using a label such as:

```bash
oc label namespace myapp openshift.io/user-monitoring=false
```

If application metrics are missing, always check namespace labels:

```bash
oc get ns myapp --show-labels
```

### 5.4 Monitoring Roles

Common OpenShift monitoring roles:

| Role | Purpose |
|---|---|
| `monitoring-rules-view` | View PrometheusRule CRs, alerts, silences in project |
| `monitoring-rules-edit` | Create/update/delete PrometheusRule CRs |
| `monitoring-edit` | Manage PrometheusRule, ServiceMonitor, and PodMonitor resources |
| `alert-routing-edit` | Manage AlertmanagerConfig CRs |
| `user-workload-monitoring-config-edit` | Edit user workload monitoring ConfigMap |

Example:

```bash
oc -n myapp adm policy add-role-to-user monitoring-edit alice
oc -n myapp adm policy add-role-to-user alert-routing-edit alice
```

## 6. SRE Monitoring Design Method

A production-grade SLO monitoring design should follow a strict method.

### Step 1: Identify the Service

Example:

```text
Service: payment-api
Namespace: prod-payments
Owner: payments-platform-team
Criticality: Tier-1
Customer journey: checkout payment authorization
```

### Step 2: Identify User Journeys

Examples:

- User login.
- Product search.
- Cart checkout.
- Payment authorization.
- Order creation.
- Report download.
- API token creation.
- File upload.

Do not start with pods. Start with user actions.

### Step 3: Define Good and Bad Events

For HTTP service:

```text
Good event:
HTTP request returns 2xx or expected 3xx within 500 ms.

Bad event:
HTTP request returns 5xx, timeout, or latency above 500 ms.
```

For async queue service:

```text
Good event:
Message processed successfully within 2 minutes.

Bad event:
Message failed, dead-lettered, or processed after 2 minutes.
```

For OpenShift API:

```text
Good event:
API request succeeds and completes under defined latency bucket.

Bad event:
API request fails with server error or exceeds latency objective.
```

### Step 4: Define SLIs

Example:

```text
Availability SLI = successful_requests / total_requests
Latency SLI = requests_under_500ms / total_requests
Error SLI = failed_requests / total_requests
```

### Step 5: Define SLO

Example:

```text
99.9% of checkout API requests must be successful over rolling 30 days.
99.5% of checkout API requests must complete within 500 ms over rolling 30 days.
```

### Step 6: Choose Metrics

Application metrics:

```text
http_requests_total
http_request_duration_seconds_bucket
```

OpenShift/platform metrics:

```text
apiserver_request_total
apiserver_request_duration_seconds_bucket
haproxy_backend_http_responses_total
kube_pod_status_phase
kube_node_status_condition
kube_persistentvolumeclaim_resource_requests_storage_bytes
container_cpu_usage_seconds_total
container_memory_working_set_bytes
```

Metric names can vary by OpenShift version, component, and exporter. Always confirm with Metrics UI or Prometheus/Thanos query.

### Step 7: Create Recording Rules

Recording rules simplify dashboards and alerts.

Instead of repeating this everywhere:

```promql
sum(rate(http_requests_total{namespace="prod-payments", app="payment-api", code=~"5.."}[5m]))
/
sum(rate(http_requests_total{namespace="prod-payments", app="payment-api"}[5m]))
```

Create a recorded metric:

```text
slo:payment_api:error_ratio_rate5m
```

### Step 8: Alert on Burn Rate

Alert when the service is consuming error budget too fast.

Example:

```text
Page: 2% budget burned in 1 hour.
Page: 5% budget burned in 6 hours.
Ticket: 10% budget burned in 3 days.
```

### Step 9: Attach Runbook

Every alert must include:

- What failed.
- User impact.
- PromQL query.
- Dashboard link.
- First 5 commands.
- Escalation path.
- Rollback instruction.

### Step 10: Review Monthly

SRE monitoring is not “set and forget.” Review:

- SLO compliance.
- Alert noise.
- False positives.
- Missed incidents.
- Top error-budget consumers.
- Release correlation.
- Capacity trends.
- Runbook quality.

## 7. Selecting SLIs for OpenShift Services

### 7.1 HTTP Request Availability SLI

Best for APIs and web applications.

```text
SLI = good HTTP requests / total HTTP requests
```

Good requests normally include:

- 2xx
- expected 3xx
- sometimes selected 4xx if caused by user/client behavior

Bad requests normally include:

- 5xx
- timeout
- connection reset
- failed dependency response

PromQL example:

```promql
1 - (
  sum(rate(http_requests_total{namespace="prod", app="checkout", code=~"5.."}[5m]))
  /
  sum(rate(http_requests_total{namespace="prod", app="checkout"}[5m]))
)
```

### 7.2 HTTP Latency SLI

Best for user-facing APIs.

```text
SLI = requests under latency threshold / total requests
```

For histogram bucket metric:

```promql
sum(rate(http_request_duration_seconds_bucket{namespace="prod", app="checkout", le="0.5"}[5m]))
/
sum(rate(http_request_duration_seconds_count{namespace="prod", app="checkout"}[5m]))
```

This measures the percentage of requests under 500 ms.

For p95 latency:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_request_duration_seconds_bucket{namespace="prod", app="checkout"}[5m])
  )
)
```

Use bucket-ratio SLI for SLO compliance and percentile for dashboard visibility. Percentiles are excellent for troubleshooting, but SLO math is often easier and more accurate with good/total event ratios.

### 7.3 Availability SLI from Blackbox Probe

For external route availability:

```text
SLI = successful probes / total probes
```

Example metrics if Blackbox Exporter or synthetic probing is used:

```promql
avg_over_time(probe_success{route="checkout"}[5m])
```

OpenShift monitoring support policies may restrict certain Probe CRD usage in the managed stack. In production, validate the supported method before deploying synthetic probes.

### 7.4 Queue Processing SLI

For asynchronous services:

```text
SLI = messages processed within target time / total messages
```

Example:

```promql
sum(rate(queue_messages_processed_total{status="success"}[5m]))
/
sum(rate(queue_messages_received_total[5m]))
```

Latency/freshness:

```promql
histogram_quantile(
  0.95,
  sum by (le) (rate(message_processing_duration_seconds_bucket[5m]))
)
```

### 7.5 Kubernetes Job/CronJob SLI

For scheduled workloads:

```text
SLI = successful scheduled executions / expected scheduled executions
```

Useful metrics:

```text
kube_job_status_succeeded
kube_job_status_failed
kube_cronjob_next_schedule_time
kube_job_status_start_time
kube_job_status_completion_time
```

Example idea:

```promql
sum(increase(kube_job_status_succeeded{namespace="batch-prod"}[1d]))
/
(
  sum(increase(kube_job_status_succeeded{namespace="batch-prod"}[1d]))
  +
  sum(increase(kube_job_status_failed{namespace="batch-prod"}[1d]))
)
```

### 7.6 Storage SLI

For persistent applications:

```text
SLI = successful storage operations / total storage operations
```

Application-level storage SLIs are better than only PVC capacity metrics.

Useful platform symptoms:

- PVC pending.
- PVC almost full.
- PV not bound.
- CSI provisioner errors.
- Volume attach/mount failures.
- High disk latency.
- Node filesystem pressure.

### 7.7 Control Plane SLI

For OpenShift platform team:

```text
SLI = successful API server requests / total API server requests
```

Example:

```promql
1 - (
  sum(rate(apiserver_request_total{code=~"5.."}[5m]))
  /
  sum(rate(apiserver_request_total[5m]))
)
```

Latency:

```promql
histogram_quantile(
  0.99,
  sum by (le, verb, resource) (
    rate(apiserver_request_duration_seconds_bucket[5m])
  )
)
```

## 8. SLO Target and Error Budget Design

### 8.1 Common SLO Windows

| Window | Use Case |
|---|---|
| 7 days | Fast-moving internal service |
| 28 days | Weekly cycle neutral; common SRE practice |
| 30 days | Business monthly reporting |
| Calendar month | SLA/legal reporting |
| Quarter | Executive reliability trend |

For engineering, rolling windows are usually better than calendar windows because they avoid end-of-month reset behavior.

### 8.2 Choosing SLO Target

Avoid copying 99.99% blindly. Higher reliability costs more.

Ask:

- What does the customer need?
- What is the business impact of downtime?
- What is the current historical reliability?
- What can the architecture support?
- What is the dependency reliability?
- What is the cost of improvement?

### 8.3 Example SLO Targets

| Service Type | Possible SLO |
|---|---|
| Public login API | 99.95% availability, p95 < 500 ms |
| Internal reporting service | 99.5% availability, p95 < 3 sec |
| Payment authorization | 99.99% availability, p95 < 700 ms |
| Admin dashboard | 99.0% availability, p95 < 2 sec |
| Batch job | 99% daily completion success |
| OpenShift API | 99.95% API availability, p99 latency target by verb/resource |

### 8.4 Error Budget Calculation

Formula:

```text
Error budget percentage = 100% - SLO percentage
```

For 99.9%:

```text
Error budget = 0.1%
```

For request-based SLO:

```text
Allowed bad requests = total requests × error budget
```

Example:

```text
Total requests in 30 days = 100,000,000
SLO = 99.9%
Error budget = 0.1%
Allowed bad requests = 100,000,000 × 0.001 = 100,000
```

### 8.5 Time-Based vs Request-Based SLO

| Type | Formula | Best For |
|---|---|---|
| Time-based | good minutes / total minutes | external uptime, blackbox probes |
| Request-based | good requests / total requests | APIs, web services |
| Event-based | good events / total events | queues, jobs, streams |

Request-based SLO is usually better for high-traffic APIs because it reflects actual user impact.

### 8.6 Dependency-Aware SLO Design

If your service depends on:

- OpenShift API
- Ingress router
- Database
- Object storage
- Message broker
- External payment gateway
- DNS
- LDAP/OAuth

Then your real reliability cannot exceed dependency reliability unless you build retries, caching, fallback, queueing, circuit breakers, or multi-region architecture.

Example:

```text
payment-api depends on payment-gateway SLA 99.9%.
payment-api cannot realistically promise 99.99% successful authorization unless it has fallback or queue-based delayed authorization.
```

## 9. SLA Design and Operational Translation

SLA is business language. SLO is engineering language. SLI is metric language.

### 9.1 Example Translation

Business SLA:

```text
Application will be available 99.9% monthly.
```

Engineering SLO:

```text
99.95% of route probes and 99.9% of user requests must succeed over rolling 30 days.
```

Metric SLI:

```promql
1 - (
  sum(rate(http_requests_total{code=~"5.."}[30d]))
  /
  sum(rate(http_requests_total[30d]))
)
```

Alert:

```text
Page when the service burns 2% of monthly error budget in 1 hour or 5% in 6 hours.
```

Runbook:

```text
Check route, router pods, app pods, endpoints, recent rollout, DB dependency, node pressure, PVC, and logs.
```

### 9.2 SLA Exclusions

SLA document should define exclusions carefully:

- Scheduled maintenance.
- Customer-caused failures.
- Force majeure.
- Unsupported client behavior.
- Third-party provider failure.
- Security isolation event.
- DNS provider outage.
- External network failure.

Engineering should still monitor excluded events, but business SLA calculation may exclude them.

### 9.3 SLA Reporting

Monthly SLA report should include:

- Total time window.
- Excluded maintenance.
- Incident list.
- Availability percentage.
- Error budget consumed.
- Top causes.
- Corrective actions.
- SLA met/missed.

Example report fields:

```text
Service: checkout-api
Month: June 2026
SLA: 99.9%
Measured availability: 99.94%
Allowed downtime: 43m 12s
Actual downtime: 25m 10s
SLA status: Met
Error budget consumed: 58%
```

## 10. Golden Signals, RED, USE, and OpenShift Metrics

### 10.1 Four Golden Signals

Google SRE popularized four golden signals:

| Signal | Meaning | OpenShift Example |
|---|---|---|
| Latency | Time taken to serve request | p95/p99 HTTP latency |
| Traffic | Demand on service | requests/sec, router connections |
| Errors | Failed requests | 5xx, timeouts, failed jobs |
| Saturation | How full resource is | CPU, memory, disk, queue depth |

### 10.2 RED Method

RED is excellent for request-driven services.

| RED | Meaning | Metric |
|---|---|---|
| Rate | Requests per second | `rate(http_requests_total[5m])` |
| Errors | Error rate/ratio | `rate(http_requests_total{code=~"5.."}[5m])` |
| Duration | Request latency | `histogram_quantile()` |

### 10.3 USE Method

USE is excellent for infrastructure.

| USE | Meaning | Node/PVC Example |
|---|---|---|
| Utilization | How busy resource is | CPU usage, memory working set |
| Saturation | Queued work or pressure | load average, disk IO queue, throttling |
| Errors | Resource errors | disk errors, network drops, mount failures |

### 10.4 Mapping to OpenShift

| Area | Golden Signal | Example Metrics |
|---|---|---|
| Application | Rate | `http_requests_total` |
| Application | Errors | `http_requests_total{code=~"5.."}` |
| Application | Duration | `http_request_duration_seconds_bucket` |
| Application | Saturation | queue depth, worker pool, DB pool |
| Node | Utilization | `container_cpu_usage_seconds_total`, node CPU metrics |
| Node | Saturation | CPU throttling, memory pressure, disk pressure |
| PVC | Saturation | filesystem available bytes, PVC capacity |
| API server | Latency | `apiserver_request_duration_seconds_bucket` |
| API server | Errors | `apiserver_request_total{code=~"5.."}` |
| Router | Errors | HAProxy 5xx metrics |
| etcd | Latency | etcd disk fsync / request duration metrics |

## 13. Control Plane SLOs

### 13.1 API Server Availability

Metric:

```text
apiserver_request_total
```

Availability SLI:

```promql
1 - (
  sum(rate(apiserver_request_total{code=~"5.."}[5m]))
  /
  sum(rate(apiserver_request_total[5m]))
)
```

Filter noisy dimensions when needed:

```promql
1 - (
  sum(rate(apiserver_request_total{code=~"5..", verb!="WATCH"}[5m]))
  /
  sum(rate(apiserver_request_total{verb!="WATCH"}[5m]))
)
```

Why exclude `WATCH` sometimes?

- Watch requests are long-running.
- They behave differently than normal API calls.
- For user-facing API latency and success, separate watch and non-watch traffic.

### 13.2 API Latency

```promql
histogram_quantile(
  0.99,

    rate(apiserver_request_duration_seconds_bucket{verb!="WATCH"}[5m])
  )
)
```

By resource:

```promql
histogram_quantile(
  0.99,
  sum by (le, resource, verb) (
    rate(apiserver_request_duration_seconds_bucket{verb!="WATCH"}[5m])
  )
)
```

## 18. PromQL Foundation for SLO Monitoring

### 18.1 Counters and Rate

Counters increase over time. Use `rate()` for per-second rate.

```promql
rate(http_requests_total[5m])
```

Use `increase()` for count over a window.

```promql
increase(http_requests_total[1h])
```

### 18.2 Error Ratio

```promql
bad_events / total_events
```

Example:

```promql
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))
```

### 18.3 Availability

```promql
1 - error_ratio
```

Example:

```promql
1 - (
  sum(rate(http_requests_total{code=~"5.."}[5m]))
  /
  sum(rate(http_requests_total[5m]))
)
```

### 18.4 Histogram Quantile

Classic histogram p95:

```promql
histogram_quantile(
  0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m]))
)
```

Grouped by route:

```promql
histogram_quantile(
  0.95,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m]))
)
```

### 18.5 Good Events Under Latency Threshold

```promql
sum(rate(http_request_duration_seconds_bucket{le="0.5"}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```

This is very useful for latency SLOs.

### 18.6 Avoid Divide-by-Zero

For low traffic services:

```promql
(
  sum(rate(http_requests_total{code=~"5.."}[5m]))
  /
  clamp_min(sum(rate(http_requests_total[5m])), 1)
)
```

But be careful. `clamp_min()` can hide low-traffic reality. For low-traffic services, synthetic probes or longer windows may be better.

### 18.7 Aggregation Best Practices

Bad:

```promql
avg(rate(http_requests_total[5m]))
```

Better:

```promql
sum(rate(http_requests_total[5m]))
```

For ratios, aggregate numerator and denominator separately, then divide:

```promql
sum(rate(errors_total[5m])) / sum(rate(requests_total[5m]))
```

Do not average ratios across pods unless you intentionally want pod-weighted behavior.

- Easier troubleshooting.
- Reduced query load.
- Standard metric names.

### 19.2 Naming Convention

Good naming pattern:



## 20. Burn Rate Alerting

Burn-rate alerting is one of the most important SRE monitoring concepts.

### 20.1 Burn Rate Formula

```text
Burn rate = observed error ratio / allowed error ratio
```

For 99.9% SLO:

```text
Allowed error ratio = 0.001
```

If current error ratio is 0.006:

```text
Burn rate = 0.006 / 0.001 = 6
```

Meaning:

> The service is consuming error budget 6 times faster than allowed.

### 20.2 Time to Exhaust Budget

For a 30-day SLO window:

```text
Time to exhaust = 30 days / burn rate
```

| Burn Rate | Time to Exhaust 30-Day Budget |
|---:|---:|
| 1x | 30 days |
| 2x | 15 days |
| 6x | 5 days |
| 14.4x | ~2.08 days |
| 36x | ~20 hours |
| 100x | ~7.2 hours |
| 1000x | ~43 minutes |

### 20.3 Multi-Window Multi-Burn-Rate Alerting

Single-window alerts are weak.

Short window only:

- Fast detection.
- High false positives.

Long window only:

- Low noise.
- Slow detection.

Multi-window approach combines both.

Common SRE starting points:

| Budget Consumption | Window | Burn Rate | Notification |
|---:|---:|---:|---|
| 2% | 1 hour | 14.4x | Page |
| 5% | 6 hours | 6x | Page |
| 10% | 3 days | 1x | Ticket |

For better precision, many teams pair long and short windows:

| Alert | Long Window | Short Window | Burn Rate | Severity |
|---|---:|---:|---:|---|
| Fast burn | 1h | 5m | 14.4x | critical/page |
| Slow burn | 6h | 30m | 6x | critical/page or high |
| Ticket burn | 3d | 6h | 1x | warning/ticket |

### 20.4 For 99.9% SLO

Allowed error ratio:

```text
0.001
```

Fast burn threshold:

```text
14.4 × 0.001 = 0.0144 = 1.44% error ratio
```

Slow burn threshold:

```text
6 × 0.001 = 0.006 = 0.6% error ratio
```

Ticket threshold:

```text
1 × 0.001 = 0.001 = 0.1% error ratio
```

### 20.5 Why This Is Better Than “5xx > 5%”

Random threshold:

```text
5xx > 5% for 5 minutes
```

Problems:

- It ignores SLO target.
- It ignores error budget.
- It treats all services similarly.
- It may page too late for strict SLOs.
- It may page too often for loose SLOs.

Burn-rate alert:

```text
Error ratio > burn_rate × allowed_error_ratio
```

Benefits:

- Tied to business reliability.
- Works across SLO targets.
- Supports severity mapping.
- Reduces noise.
- Helps release decisions.

## 21. PrometheusRule Example: Multi-Window Burn-Rate Alert

This example uses:

```text
Service: checkout-api
Namespace: prod-checkout
SLO: 99.9% request success over 30 days
Allowed error ratio: 0.001
```

### 21.1 Full Rule

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: checkout-api-slo-alerts
  namespace: prod-checkout
  labels:
    app: checkout-api
    slo: checkout-availability
spec:
  groups:
  - name: checkout-api.slo.alerts
    rules:
    - alert: CheckoutAPIErrorBudgetFastBurn
      expr: |
        (
          slo:checkout_api:errors:ratio_rate1h > (14.4 * 0.001)
          and
          slo:checkout_api:errors:ratio_rate5m > (14.4 * 0.001)
        )
      for: 2m
      labels:
        severity: critical
        team: checkout-sre
        service: checkout-api
        slo: availability
        notification: page
      annotations:
        summary: "Checkout API is burning error budget very fast"
        description: |
          checkout-api is consuming more than 2% of its 30-day error budget in 1 hour.
          SLO: 99.9% availability. Check 5xx rate, recent deployments, router/backend errors, pod readiness, DB dependency, node pressure, and PVC/storage issues.
        runbook_url: "https://runbooks.example.com/openshift/checkout-api-error-budget-fast-burn"
        dashboard_url: "https://console-openshift-console.apps.example.com/monitoring/dashboards/checkout-api-slo"

    - alert: CheckoutAPIErrorBudgetSlowBurn
      expr: |
        (
          slo:checkout_api:errors:ratio_rate6h > (6 * 0.001)
          and
          slo:checkout_api:errors:ratio_rate30m > (6 * 0.001)
        )
      for: 15m
      labels:
        severity: critical
        team: checkout-sre
        service: checkout-api
        slo: availability
        notification: page
      annotations:
        summary: "Checkout API is steadily burning error budget"
        description: |
          checkout-api is consuming more than 5% of its 30-day error budget in 6 hours.
          Investigate sustained 5xx, degraded dependency, resource saturation, rollout problems, and router/backend instability.
        runbook_url: "https://runbooks.example.com/openshift/checkout-api-error-budget-slow-burn"

    - alert: CheckoutAPIErrorBudgetTicketBurn
      expr: |
        (
          slo:checkout_api:errors:ratio_rate3d > (1 * 0.001)
          and
          slo:checkout_api:errors:ratio_rate6h > (1 * 0.001)
        )
      for: 1h
      labels:
        severity: warning
        team: checkout-sre
        service: checkout-api
        slo: availability
        notification: ticket
      annotations:
        summary: "Checkout API is slowly consuming error budget"
        description: |
          checkout-api has sustained error budget consumption. This may not require paging, but it requires investigation and reliability work.
        runbook_url: "https://runbooks.example.com/openshift/checkout-api-error-budget-ticket-burn"
```

### 21.2 Why Use `and` Between Long and Short Window?

Example:

```promql
slo:checkout_api:errors:ratio_rate1h > threshold
and
slo:checkout_api:errors:ratio_rate5m > threshold
```

This reduces false positives:

- Long window confirms sustained impact.
- Short window confirms issue is still happening.

Without the short window, alert may fire after issue already ended.

### 21.3 Apply and Verify

```bash

oc apply -f checkout-api-slo-alerts.yaml
oc -n prod-checkout get prometheusrule
```

Check alerts in console:

```text

Observe -> Alerting -> Alerts
```

Or query:

```promql

```

## 22. ServiceMonitor and PodMonitor Design

### 22.1 ServiceMonitor

Use ServiceMonitor when the app has a Service.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    path: /metrics
    interval: 30s
```

Important:

- The Service must have matching labels.
- The port name in ServiceMonitor must match the Service port name, not only container port.
- In user-defined namespaces, ServiceMonitor discovers services in the same namespace.
- Scrape interval should not be too aggressive.
- Avoid scraping unstable high-cardinality metrics.

### 22.2 PodMonitor

Use PodMonitor when there is no Service or when scraping pods directly is required.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: myapp-pods
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  podMetricsEndpoints:
  - port: metrics
    path: /metrics
    interval: 30s
```

### 22.3 ServiceMonitor Troubleshooting

Check resources:

```bash
oc -n myapp-prod get servicemonitor
oc -n myapp-prod describe servicemonitor myapp
oc -n myapp-prod get svc --show-labels
oc -n myapp-prod get endpoints myapp
oc -n myapp-prod get pods --show-labels
```

Check application metrics endpoint:

```bash
oc -n myapp-prod port-forward svc/myapp 9090:9090
curl http://localhost:9090/metrics
```

Check if Prometheus target is up:

```promql
up{namespace="myapp-prod"}
```

Common mistakes:

| Problem | Fix |
|---|---|
| ServiceMonitor selector does not match Service labels | Correct labels |
| Wrong port name | Use Service port name |
| App does not expose `/metrics` | Fix app instrumentation |
| Namespace excluded from monitoring | Remove exclusion label |
| User lacks RBAC | Bind `monitoring-edit` |
| Metrics endpoint requires auth | Configure supported auth in ServiceMonitor |
| High cardinality | Remove dangerous labels |

## 23. Alertmanager Routing for SRE Operations

Alertmanager handles:

- Deduplication.
- Grouping.
- Routing.
- Silencing.
- Inhibition.
- Notification dispatch.

### 23.1 Alert Labels Matter

Every alert should have good labels:

```yaml
labels:
  severity: critical
  team: checkout-sre
  service: checkout-api
  namespace: prod-checkout
  slo: availability
  notification: page
```

Labels are used for routing.

### 23.2 Alert Annotations Matter

Annotations are for humans:

```yaml
annotations:
  summary: "Checkout API error budget fast burn"
  description: "User-facing checkout errors are burning budget quickly."
  runbook_url: "https://runbooks.example.com/checkout-fast-burn"
  dashboard_url: "https://console.../dashboard"
```

### 23.3 Routing Strategy

| Severity | Destination | Example |
|---|---|---|
| critical | Pager/phone/SMS | Fast burn, outage |
| warning | Ticket/Slack/email | Slow burn, capacity risk |
| info | Dashboard only | Low-impact signal |

### 23.4 AlertmanagerConfig Example

For user-defined alert routing:

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
metadata:
  name: checkout-routing
  namespace: prod-checkout
spec:
  route:
    groupBy: ['alertname', 'service']
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 4h
    receiver: checkout-sre-default
    routes:
    - matchers:
      - name: severity
        value: critical
      receiver: checkout-sre-page
    - matchers:
      - name: severity
        value: warning
      receiver: checkout-sre-ticket
  receivers:
  - name: checkout-sre-default
  - name: checkout-sre-page
    webhookConfigs:
    - url: https://alert-webhook.example.com/page/checkout
  - name: checkout-sre-ticket
    webhookConfigs:
    - url: https://alert-webhook.example.com/ticket/checkout
```

### 23.5 Inhibition Example

If a cluster-wide router outage fires, you may inhibit hundreds of app route alerts.

Concept:

```text
When IngressOperatorDown is firing,
inhibit downstream AppRouteUnavailable alerts.
```

This reduces alert storm during major incidents.

### 23.6 Silencing Rules

Silence only when:

- Maintenance is approved.
- Incident is already known and tracked.
- Alert is noisy and being fixed.
- Temporary suppression is justified.

Do not silence by broad matchers such as:

```text
severity=critical
```

Prefer narrow silences:

```text
alertname=CheckoutAPIErrorBudgetSlowBurn
namespace=prod-checkout
service=checkout-api
```

## 24. Dashboards for SLO/SLA/SRE Monitoring

Dashboards are for investigation and reporting. Alerts are for action.

### 24.1 SLO Dashboard Panels

A good SLO dashboard has:

1. Current SLO compliance.
2. Error budget remaining.
3. Burn rate current.
4. Request rate.
5. Error rate by status code.
6. Latency p50/p95/p99.
7. Latency good-event ratio.
8. Recent deployments.
9. Pod health.
10. Node placement.
11. Dependency status.
12. Alert history.

### 24.2 Example Dashboard Queries

Availability 30d:

```promql
1 - (
  sum(rate(http_requests_total{namespace="prod-checkout", app="checkout-api", code=~"5.."}[30d]))
  /
  sum(rate(http_requests_total{namespace="prod-checkout", app="checkout-api"}[30d]))
)
```

Error budget remaining:

```promql
1 - (
  (
    sum(rate(http_requests_total{namespace="prod-checkout", app="checkout-api", code=~"5.."}[30d]))
    /
    sum(rate(http_requests_total{namespace="prod-checkout", app="checkout-api"}[30d]))
  )
  /
  0.001
)
```

Burn rate 1h:

```promql
slo:checkout_api:errors:ratio_rate1h / 0.001
```

Request rate:

```promql
sum(rate(http_requests_total{namespace="prod-checkout", app="checkout-api"}[5m]))
```

p95 latency:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_request_duration_seconds_bucket{namespace="prod-checkout", app="checkout-api"}[5m])
  )
)
```

Pod restarts:

```promql
increase(kube_pod_container_status_restarts_total{namespace="prod-checkout"}[1h])
```

### 24.3 Dashboard Anti-Patterns

Avoid:

- 100 panels no one understands.
- CPU-only dashboard for user-facing service.
- No SLO panel.
- No error budget panel.
- No deployment marker.
- No owner/team label.
- No runbook links.
- High-cardinality route/user panels.
- p99 without request volume context.

## 26. Error Budget Policy

SLO without policy is only a graph.

### 26.1 Example Error Budget Policy

| Budget Consumed | Action |
|---:|---|
| 0–25% | Normal development and releases |
| 25–50% | Review top reliability risks |
| 50–75% | Prioritize reliability fixes, increase review for risky changes |
| 75–90% | Freeze non-critical releases, reliability work mandatory |
| 90–100% | Stop feature releases, executive/customer communication if needed |
| >100% | SLA/SLO breach review, postmortem, corrective action plan |

### 26.2 Release Decision

Example:

```text
If error budget remaining < 25%, only emergency fixes and reliability improvements are allowed.
```

### 26.3 Incident Trigger

```text
If a page-level burn-rate alert fires, create an incident.
If error budget consumed > 5% in 24 hours, require postmortem.
If SLO breach occurs, require leadership review.
```

### 26.4 Error Budget and Change Management

Integrate with GitOps/CI/CD:

- Check SLO status before production deployment.
- Block risky deployment if budget is nearly exhausted.
- Require approval for deploy during active burn alert.
- Auto-create ticket when budget crosses 75% consumed.

Example pseudo-policy:

```text
IF service=checkout-api AND error_budget_remaining < 20%
THEN block non-emergency Argo CD sync to prod-checkout.
```

## 27. Incident Response Model

### 27.1 Severity Based on SLO Impact

| Severity | SLO Impact | Example |
|---|---|---|
| Sev1 | Major user impact, fast burn | Checkout unavailable |
| Sev2 | Partial impact, slow burn | Elevated errors sustained |
| Sev3 | No immediate user impact but budget risk | Gradual latency degradation |
| Sev4 | Informational | Non-prod issue |

### 27.2 First 10 Minutes of Response

1. Acknowledge alert.
2. Open SLO dashboard.
3. Confirm user impact.
4. Identify recent change.
5. Check app pods and endpoints.
6. Check route/router errors.
7. Check dependencies.
8. Check node pressure/PVC.
9. Mitigate first, root-cause second.
10. Communicate status.

### 27.3 OpenShift Commands During Incident

```bash
# Overall cluster health
oc get co
oc get nodes
oc get mcp

# Application health
oc -n prod-checkout get deploy,rs,po,svc,route,endpoints
oc -n prod-checkout get events --sort-by=.lastTimestamp | tail -50
oc -n prod-checkout logs deploy/checkout-api --since=15m

# Rollout

# Resource pressure
oc adm top nodes
oc adm top pods -A

# Router
oc -n openshift-ingress get pods -o wide
oc -n openshift-ingress logs deploy/router-default --since=15m

# Storage
oc -n prod-checkout get pvc
oc -n prod-checkout describe pvc <pvc>
```

### 27.4 Mitigation Examples

| Issue | Fast Mitigation |
|---|---|
| Bad deployment | Rollback deployment |
| Pod overload | Scale replicas / tune HPA |
| Node pressure | Evacuate workload, add capacity |
| PVC full | Expand PVC, cleanup data/logs |
| Router overload | Scale router, check LB |
| DB latency | Failover, tune pool, reduce traffic |
| Dependency outage | Enable fallback/circuit breaker |

## 28. Postmortem and Continuous Improvement

### 28.1 Postmortem Goals

Postmortem should not blame people. It should improve the system.

A good postmortem identifies:

- What happened.
- User impact.
- Timeline.
- Detection gap.
- Mitigation.
- Root causes.
- Contributing factors.
- What went well.
- What went poorly.
- Action items.

### 28.2 SLO-Focused Postmortem Questions

- Which SLO was impacted?
- How much error budget was consumed?
- Did burn-rate alert fire correctly?
- Was the alert too late, too early, or noisy?
- Did dashboard show the right data?
- Did runbook help?
- Was there an automation gap?
- Should the SLO be changed?
- Should the app expose better metrics?
- Should deployment policy change?

### 28.3 Action Item Examples

| Problem | Action |
|---|---|
| Alert fired late | Add fast burn alert |
| Alert noisy | Add long+short window condition |
| No metric for dependency | Add dependency metrics |
| Manual rollback slow | Automate rollback procedure |
| PVC filled repeatedly | Add capacity forecast and cleanup job |
| Node pressure recurring | Adjust requests/limits and add nodes |
| Poor dashboard | Add SLO and dependency panels |

## 31. Advanced Troubleshooting

### 31.1 User Metrics Not Showing

Checklist:

```bash
oc -n openshift-user-workload-monitoring get pods
oc get ns <namespace> --show-labels
oc -n <namespace> get servicemonitor,podmonitor
oc -n <namespace> get svc --show-labels
oc -n <namespace> get endpoints
oc -n <namespace> get pods --show-labels
```

PromQL:

```promql
up{namespace="<namespace>"}
```

Common issue:

```text
ServiceMonitor selector does not match Service labels.
```

### 31.2 PrometheusRule Not Working

```bash
oc -n <namespace> get prometheusrule
oc -n <namespace> describe prometheusrule <name>
oc -n openshift-user-workload-monitoring logs deploy/prometheus-operator
```

Check rule in console:

```text
Observe -> Alerting -> Alerting rules
```

Common problems:

- YAML indentation error.
- PromQL syntax error.
- Missing metric.
- Wrong namespace label.
- Division by zero.
- Rule not selected due to RBAC/namespace issue.

### 31.3 Alert Not Routing

```bash
oc -n <namespace> get alertmanagerconfig
oc -n <namespace> describe alertmanagerconfig <name>
oc -n openshift-user-workload-monitoring get secret
```

Check labels on alert:

```promql
ALERTS{alertstate="firing"}
```

Common problems:

- Alert labels do not match route matchers.
- Receiver secret/webhook wrong.
- AlertmanagerConfig not allowed by namespace/RBAC.
- Silence active.
- Inhibition rule suppressing alert.
- Alert is pending, not firing.

### 31.4 Alert Firing but No Real Impact

Possible reasons:

- Threshold too sensitive.
- Low traffic service with 1 failed request.
- Bad SLI definition.
- Synthetic endpoint failing but user path healthy.
- Alert lacks long+short window condition.
- Metric includes client-side 4xx errors as bad events.

Fix:

- Improve SLI.
- Use minimum traffic guard.
- Use multi-window burn rate.
- Separate page vs ticket.
- Tune runbook.

Traffic guard example:

```promql
(
  slo:checkout_api:errors:ratio_rate5m > (14.4 * 0.001)
)
and
(
  sum(rate(http_requests_total{namespace="prod-checkout", app="checkout-api"}[5m])) > 10
)
```

### 31.5 Alert Did Not Fire During Incident

Possible reasons:

- Missing metric.
- Wrong label filter.
- Alert threshold too high.
- SLO query excluded failing path.
- Prometheus target down.
- Recording rule evaluation failed.
- Alert routed to wrong receiver.
- Service failed before emitting metrics.

Fix:

- Add blackbox/synthetic probe.
- Add dependency metrics.
- Test alert rules.
- Review incident timeline.
- Add low-traffic handling.

### 31.6 High Cardinality Problem

Symptoms:

- Prometheus memory high.
- Slow queries.
- Target scrape errors.
- Too many time series.
- OOM/restart of Prometheus.

Dangerous labels:

```text
request_id
user_id
session_id
email
full_url
ip
uuid
transaction_id
```

Troubleshooting:

```promql
count by (__name__)({__name__=~".+"})
```

Top series by metric:

```promql
topk(20, count by (__name__)({__name__=~".+"}))
```

Fix:

- Drop bad labels in app instrumentation.
- Use route templates instead of raw URLs.
- Reduce scrape targets.
- Reduce unnecessary buckets.
- Use recording rules.

### 31.7 Low Traffic Service SLO Problem

If a service has 10 requests/hour, one failed request causes 10% error ratio.

Solutions:

- Use longer windows.
- Use synthetic probes.
- Use ticket instead of page for low volume.
- Use minimum traffic condition.
- Combine request SLO with availability probe.

Example:

```promql
(
  error_ratio > threshold
)
and
(
  sum(rate(http_requests_total[30m])) > 1
)
```

### 31.8 Missing Metrics After Deployment

Check:

```bash
oc -n <ns> get pods
oc -n <ns> get svc
oc -n <ns> get endpoints
oc -n <ns> describe servicemonitor <name>
oc -n <ns> logs deploy/<app> --since=10m
```

Common causes:

- Metrics port renamed.
- `/metrics` path changed.
- App no longer exposes metrics.
- Service labels changed.
- NetworkPolicy blocks scrape traffic.
- TLS/auth changed.

## 33. Interview and Real-Time Scenario Questions

### Q1. What is the difference between SLA, SLO, and SLI?

**Answer:**

- SLA is a contractual/business agreement.
- SLO is an internal reliability target.
- SLI is the actual metric used to measure the target.

Example:

```text
SLA: 99.9% monthly availability.
SLO: 99.95% successful requests over rolling 30 days.
SLI: successful HTTP requests / total HTTP requests.
```

### Q2. Why should we alert on burn rate instead of CPU?

CPU is a symptom. Burn rate measures how quickly the service is consuming allowed unreliability. A CPU alert may fire without user impact, while a burn-rate alert is tied to SLO and business reliability.

### Q3. Your app has 99.9% SLO. Error ratio is 0.6%. What is burn rate?

Allowed error ratio:

```text
1 - 0.999 = 0.001
```

Burn rate:

```text
0.006 / 0.001 = 6x
```

The service is burning budget 6 times faster than allowed.

### Q4. What is multi-window burn-rate alerting?

It combines long and short windows to improve detection and reduce false positives.

Example:

```promql
error_ratio_1h > threshold and error_ratio_5m > threshold
```

Long window confirms sustained issue. Short window confirms issue is still active.

### Q5. ServiceMonitor created but metrics not visible. What do you check?

```bash
oc -n <ns> get servicemonitor
oc -n <ns> describe servicemonitor <name>
oc -n <ns> get svc --show-labels
oc -n <ns> get endpoints
oc -n <ns> get pods --show-labels
oc get ns <ns> --show-labels
```

Then query:

```promql
up{namespace="<ns>"}
```

### Q6. How do you design SLO for low-traffic service?

Use longer windows, synthetic probes, minimum traffic guards, and ticket-based alerts. Avoid paging for one failed request when traffic is very low.

### Q7. What labels are required for production alerts?

At minimum:

```text
severity
team
service
namespace
slo
notification
```

### Q8. What is error budget policy?

It defines actions based on error budget consumption, such as normal release, reliability review, release freeze, or postmortem.

### Q9. What is the difference between RED and USE?

RED is for request services: Rate, Errors, Duration.  
USE is for resources: Utilization, Saturation, Errors.

### Q10. What is a good OpenShift platform SLO?

Example:

```text
99.95% of non-watch Kubernetes API requests should succeed over rolling 30 days.
99% of API requests should complete below defined latency threshold.
```

## Final Notes for Advanced OpenShift Administrators

A strong OpenShift SRE monitoring approach is not measured by the number of alerts. It is measured by how quickly and accurately the team detects real user impact, protects error budget, restores service, and improves the platform after incidents.

For production clusters, your target should be:

```text
Every Tier-1 service has:
- documented SLA/SLO/SLI
- ServiceMonitor or PodMonitor
- recording rules
- burn-rate alerts
- Alertmanager route
- dashboard
- runbook
- owner
- error budget policy
- monthly review
```

That is the difference between basic monitoring and mature SRE-driven OpenShift operations.
