## 1. What is User Workload Monitoring?

**User Workload Monitoring (UWM)** is the OpenShift-supported mechanism for collecting, storing, querying, and alerting on metrics from **user-defined projects**, meaning normal application namespaces created for business workloads.

In simple terms:

- **Platform monitoring** watches OpenShift itself: API server, kubelet, scheduler, router, nodes, cluster operators, etc.
- **User workload monitoring** watches your applications: Java apps, NGINX apps, databases, APIs, custom exporters, business services, and namespace-level workload metrics.

UWM lets application teams expose metrics from their own workloads and lets OpenShift collect those metrics using the built-in monitoring stack instead of requiring every team to install a separate Prometheus stack.

A senior OpenShift administrator should view UWM as a **controlled multi-tenant Prometheus service** provided by the platform team.

### Key idea

User workload monitoring is not normally implemented by installing your own Prometheus Operator from OperatorHub. In supported OpenShift, the built-in monitoring stack is managed by the **Cluster Monitoring Operator (CMO)**. Application teams integrate with it through supported Custom Resources such as:

- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`
- `AlertmanagerConfig`

### What UWM monitors

When enabled, UWM can collect metrics from:

- `/metrics` endpoints exposed by application services
- Pods exposing Prometheus-compatible metrics
- Application exporters
- Custom business metrics
- Namespace-local alerting and recording rules

### What UWM does not mean

UWM does **not** mean:

- Every developer gets admin access to the cluster Prometheus.
- Every project can scrape every other project by default.
- You should deploy random Prometheus CRs using an OLM-installed Prometheus Operator.
- UWM is a replacement for log aggregation or tracing.
- UWM automatically scrapes every pod just because it has annotations.

UWM is intentionally opinionated and controlled because monitoring itself can become a high-resource, high-cardinality, multi-tenant risk.

## 2. Why OpenShift separates platform monitoring and user workload monitoring

OpenShift separates monitoring into two logical areas for operational safety.

### Platform monitoring

Platform monitoring is for Red Hat OpenShift components and cluster health. It runs primarily in:

```bash
openshift-monitoring
```

It monitors:

- Kubernetes API server
- OpenShift API server
- Cluster Operators
- Kubelet
- Node exporter
- Router / Ingress
- Storage and networking components
- Control plane health
- Cluster-level alerts

This area is critical for cluster availability. If application teams can accidentally overload platform Prometheus, they can impact cluster observability.

### User workload monitoring

User workload monitoring is for non-platform application namespaces. It runs primarily in:

```bash
openshift-user-workload-monitoring
```

It monitors:

- Application metrics
- Custom exporters
- User project `PrometheusRule` objects
- User-defined alert routing

This separation gives you:

| Benefit | Explanation |
|---|---|
| Isolation | Application metrics do not directly pollute platform Prometheus. |
| Governance | Platform admins control who can define monitors, rules, and alert routes. |
| Scalability | User workload Prometheus can be tuned independently. |
| Security | Users get namespace-scoped access instead of cluster-wide monitoring control. |
| Supportability | CMO manages a supported configuration surface. |

### Senior-admin perspective

In a production OpenShift platform, application monitoring is a platform service. You must balance:

- Developer self-service
- Cluster stability
- Resource consumption
- Alert quality
- Compliance
- Data retention
- Long-term storage
- Multi-team ownership

UWM is the OpenShift-native way to strike that balance.

## 3. High-level architecture

At a high level, UWM looks like this:

```text
Application Pod
   |
   | exposes /metrics
   v
Service / Pod endpoint
   |
   | selected by ServiceMonitor or PodMonitor
   v
Prometheus Operator
   |
   | generates scrape configuration
   v
Prometheus User Workload
   |
   | stores metrics in local TSDB / PVC
   | sends optional remoteWrite
   v
Thanos Querier / Console / API
   |
   | users query metrics by RBAC
   v
Thanos Ruler
   |
   | evaluates user PrometheusRule objects
   v
Alertmanager
   |
   | routes notifications
   v
Email / Slack / Webhook / PagerDuty / External receiver
```

### Main architectural principle

Application teams do not usually configure scrape jobs directly inside Prometheus. They create Kubernetes-style CRDs such as `ServiceMonitor` or `PodMonitor`. The Prometheus Operator watches these CRDs and converts them into Prometheus scrape configuration.

This gives OpenShift a Kubernetes-native monitoring model.

## 4. Important namespaces and components

### 4.1 `openshift-monitoring`

This namespace contains the default platform monitoring stack.

Common components include:

| Component | Purpose |
|---|---|
| `cluster-monitoring-operator` | Reconciles the OpenShift monitoring stack. |
| `prometheus-k8s` | Scrapes platform and cluster metrics. |
| `alertmanager-main` | Handles platform alerts and optionally user-defined alert routing. |
| `thanos-querier` | Provides a unified query layer. |
| `kube-state-metrics` | Exposes Kubernetes object state metrics. |
| `node-exporter` | Exposes node-level OS metrics. |
| `openshift-state-metrics` | Exposes OpenShift-specific object metrics. |
| `monitoring-plugin` / console integration | Enables Observe dashboards and metrics UI. |

### 4.2 `openshift-user-workload-monitoring`

This namespace contains the components responsible for user-defined project monitoring.

Common components include:

| Component | Purpose |
|---|---|
| `prometheus-operator` | Watches `ServiceMonitor`, `PodMonitor`, `PrometheusRule`, and related CRDs for user workloads. |
| `prometheus-user-workload` | Scrapes and stores metrics from user-defined projects. |
| `thanos-ruler-user-workload` | Evaluates alerting and recording rules for user-defined projects. |
| `alertmanager-user-workload` | Optional dedicated Alertmanager for user-defined alerts. |

After enablement, you normally see pods similar to:

```bash
oc -n openshift-user-workload-monitoring get pods
```

Example style output:

```text
NAME                                  READY   STATUS    RESTARTS   AGE
prometheus-operator-xxxxx             2/2     Running   0          3h
prometheus-user-workload-0            4/4     Running   0          3h
prometheus-user-workload-1            4/4     Running   0          3h
thanos-ruler-user-workload-0          3/3     Running   0          3h
thanos-ruler-user-workload-1          3/3     Running   0          3h
```

### 4.3 User application namespaces

Example namespaces:

```bash
myapp-dev
myapp-qa
myapp-prod
payments-prod
inventory-prod
```

Inside these namespaces, application teams can create:

- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`
- `AlertmanagerConfig` if alert routing is enabled

They can do this only if RBAC permits it.

## 5. Data flow: from application metric to dashboard or alert

### Step 1: Application exposes metrics

A Prometheus-compatible app exposes metrics on an HTTP endpoint, commonly:

```text
/metrics
```

Example metrics:

```text
http_requests_total{method="GET",code="200"} 12039
http_request_duration_seconds_bucket{le="0.5"} 9843
process_cpu_seconds_total 223.41
jvm_memory_used_bytes{area="heap"} 123456789
```

### Step 2: Kubernetes Service selects the app pods

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
  namespace: myapp-prod
  labels:
    app: myapp
spec:
  selector:
    app: myapp
  ports:
  - name: metrics
    port: 8080
    targetPort: 8080
```

The port name is important because the `ServiceMonitor` normally references the named port.

### Step 3: ServiceMonitor tells Prometheus what to scrape

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    path: /metrics
    interval: 30s
    scheme: http
```

### Step 4: Prometheus Operator generates scrape config

The user workload Prometheus Operator watches the `ServiceMonitor` and updates Prometheus configuration safely.

### Step 5: Prometheus scrapes and stores metrics

The `prometheus-user-workload` pods scrape the target and store time-series data.

### Step 6: Users query through OpenShift Observe UI or API

Users can query metrics only according to their RBAC permissions. For example, a developer with project access can view their project’s metrics in the console.

### Step 7: Thanos Ruler evaluates rules

If the project defines `PrometheusRule` objects, Thanos Ruler evaluates them and produces alerts or recording rule output.

### Step 8: Alertmanager routes alerts

Depending on cluster configuration, user-defined alerts can route through:

- the main platform Alertmanager, or
- a dedicated user workload Alertmanager

## 6. Supported configuration model

OpenShift monitoring is managed by the Cluster Monitoring Operator. You configure it with supported ConfigMaps, not by manually editing generated StatefulSets, Deployments, Secrets, or Prometheus internals.

### 6.1 Main ConfigMaps

| ConfigMap | Namespace | Purpose |
|---|---|---|
| `cluster-monitoring-config` | `openshift-monitoring` | Configures platform monitoring and enables UWM. |
| `user-workload-monitoring-config` | `openshift-user-workload-monitoring` | Configures UWM components: Prometheus, Prometheus Operator, Thanos Ruler, optional Alertmanager. |

### 6.2 Golden rule

Do not manually edit CMO-managed workloads such as:

- `statefulset/prometheus-user-workload`
- `statefulset/thanos-ruler-user-workload`
- generated Prometheus secrets
- generated services
- generated scrape config secrets

Your change will either be reverted or put the stack into an unsupported state.

### 6.3 Supported UWM configuration keys

Inside `user-workload-monitoring-config`, common top-level keys are:

```yaml
prometheus:
  # Prometheus user workload settings

prometheusOperator:
  # User workload Prometheus Operator settings

thanosRuler:
  # User workload rule evaluation settings

alertmanager:
  # Dedicated user workload Alertmanager settings
```

## 7. Enable user workload monitoring

### 7.1 Prerequisites

You need:

- `cluster-admin` access
- `oc` CLI access
- Existing `cluster-monitoring-config` ConfigMap, or permission to create it
- No unsupported custom Prometheus CRs managed by an OLM-installed Prometheus Operator

### 7.2 Check current state

```bash
oc get cm cluster-monitoring-config -n openshift-monitoring -o yaml
```

If it does not exist:

```bash
oc create configmap cluster-monitoring-config -n openshift-monitoring
```

### 7.3 Enable UWM

Edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Set:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

### 7.4 Patch method

You can also patch it:

```bash
oc -n openshift-monitoring patch configmap cluster-monitoring-config \
  --type merge \
  -p '{"data":{"config.yaml":"enableUserWorkload: true\n"}}'
```

Be careful: this patch replaces the full `config.yaml` value. In production, first export and merge safely:

```bash
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml > cluster-monitoring-config.backup.yaml
```

### 7.5 What happens after enabling

OpenShift creates or reconciles UWM components in:

```bash
openshift-user-workload-monitoring
```

You should see:

- Prometheus Operator for UWM
- Prometheus user workload pods
- Thanos Ruler user workload pods
- `user-workload-monitoring-config` ConfigMap

## 9. RBAC model for user workload monitoring

UWM is multi-tenant. RBAC is critical.

### 9.1 Important roles and cluster roles

| Role / ClusterRole | Scope | What it allows |
|---|---|---|
| `user-workload-monitoring-config-edit` | `openshift-user-workload-monitoring` namespace role | Edit the UWM stack configuration ConfigMap. Usually platform admins only. |
| `monitoring-rules-view` | Bind with RoleBinding in user namespace | View `PrometheusRule` resources and alerts/silences for the project. |
| `monitoring-rules-edit` | Bind with RoleBinding in user namespace | Create, update, delete `PrometheusRule`; manage alerts/silences. |
| `monitoring-edit` | Bind with RoleBinding in user namespace | Includes rule editing plus create/update/delete `ServiceMonitor` and `PodMonitor`. |
| `alert-routing-edit` | Bind with RoleBinding in user namespace | Create/update/delete `AlertmanagerConfig`. |
| `pod-metrics-reader` | Bind with RoleBinding in user namespace | Access Thanos API endpoints for user project metrics. |
| `monitoring-alertmanager-api-reader` | `openshift-user-workload-monitoring` namespace role | Read access to dedicated user Alertmanager API if enabled. |
| `monitoring-alertmanager-api-writer` | `openshift-user-workload-monitoring` namespace role | Read/write access to dedicated user Alertmanager API if enabled. |

### 9.2 Grant a developer permission to create ServiceMonitor and PrometheusRule

```bash
oc adm policy add-cluster-role-to-user monitoring-edit alice -n myapp-prod
```

This creates a namespace-scoped binding. The user does not get cluster-wide monitoring admin.

### 9.3 Grant only alert rule editing

```bash
oc adm policy add-cluster-role-to-user monitoring-rules-edit alice -n myapp-prod
```

### 9.4 Grant alert routing edit permission

```bash
oc -n myapp-prod adm policy add-role-to-user alert-routing-edit alice
```

or:

```bash
oc adm policy add-cluster-role-to-user alert-routing-edit alice -n myapp-prod
```

### 9.5 Grant UWM stack configuration permission

Use this carefully. This is for platform team members, not normal app developers.

```bash
oc -n openshift-user-workload-monitoring adm policy add-role-to-user \
  user-workload-monitoring-config-edit platform-admin1 \
  --role-namespace openshift-user-workload-monitoring
```

### 9.6 Verify bindings

```bash
oc get rolebinding -n myapp-prod
oc describe rolebinding <binding-name> -n myapp-prod
```

Check what a user can do:

```bash
oc auth can-i create servicemonitors.monitoring.coreos.com -n myapp-prod --as alice
oc auth can-i create podmonitors.monitoring.coreos.com -n myapp-prod --as alice
oc auth can-i create prometheusrules.monitoring.coreos.com -n myapp-prod --as alice
oc auth can-i create alertmanagerconfigs.monitoring.coreos.com -n myapp-prod --as alice
```

## 10. ServiceMonitor and PodMonitor deep dive

### 10.1 ServiceMonitor

A `ServiceMonitor` tells Prometheus how to scrape endpoints discovered through Kubernetes `Service` objects.

Use `ServiceMonitor` when:

- Your application has a stable Kubernetes Service.
- You want to scrape via service labels.
- The metrics endpoint is exposed through a named service port.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    path: /metrics
    interval: 30s
    scrapeTimeout: 10s
    scheme: http
```

### 10.2 Important ServiceMonitor fields

| Field | Meaning |
|---|---|
| `metadata.namespace` | Namespace where the monitor object is created. |
| `spec.selector.matchLabels` | Selects Service objects by label. |
| `spec.endpoints[].port` | Name of the Service port, not necessarily the numeric port. |
| `spec.endpoints[].path` | Metrics path, commonly `/metrics`. |
| `spec.endpoints[].interval` | Scrape interval. |
| `spec.endpoints[].scrapeTimeout` | Timeout per scrape. Must be lower than or equal to interval. |
| `spec.endpoints[].scheme` | `http` or `https`. |
| `spec.endpoints[].tlsConfig` | TLS settings for HTTPS endpoints. |
| `spec.endpoints[].basicAuth` | Basic auth secret reference. |
| `spec.endpoints[].authorization` | Bearer token authorization reference. |
| `spec.endpoints[].relabelings` | Target relabeling before scrape. |
| `spec.endpoints[].metricRelabelings` | Metric relabeling after scrape, before ingest. |

### 10.3 Namespace limitation

A user-defined `ServiceMonitor` can discover Services only in the same namespace. In user workload monitoring, do not design cross-namespace scraping as a normal tenant workflow. Keep monitors with the workloads they monitor.

Good:

```text
myapp-prod ServiceMonitor -> myapp-prod Service
```

Bad:

```text
team-a ServiceMonitor -> team-b Service
```

### 10.4 Common ServiceMonitor mistake: selector mismatch

Service:

```yaml
metadata:
  labels:
    app: backend
```

Wrong ServiceMonitor:

```yaml
selector:
  matchLabels:
    app: myapp
```

Fix:

```yaml
selector:
  matchLabels:
    app: backend
```

### 10.5 Common ServiceMonitor mistake: wrong port name

Service:

```yaml
ports:
- name: web
  port: 8080
```

Wrong:

```yaml
endpoints:
- port: metrics
```

Fix:

```yaml
endpoints:
- port: web
```

### 10.6 PodMonitor

A `PodMonitor` tells Prometheus to scrape pods directly without requiring a Service.

Use `PodMonitor` when:

- You do not have a Service.
- You want to scrape sidecar metrics directly.
- You have a daemon-like workload where pod labels are enough.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: myapp-pod-monitor
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  podMetricsEndpoints:
  - port: metrics
    path: /metrics
    interval: 30s
```

### 10.7 ServiceMonitor vs PodMonitor

| Requirement | Use |
|---|---|
| Stable service abstraction exists | `ServiceMonitor` |
| Direct pod scraping needed | `PodMonitor` |
| Metrics exposed through Service port | `ServiceMonitor` |
| Metrics exposed only on pod port | `PodMonitor` |
| Standard app deployment | `ServiceMonitor` |
| Advanced/sidecar/daemon pattern | `PodMonitor` |

### 10.8 Authentication for metrics endpoints

If metrics endpoint requires authentication, use secrets referenced by the monitor object.

#### Basic auth example

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: myapp-metrics-basic-auth
  namespace: myapp-prod
stringData:
  username: metrics-user
  password: change-me
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    path: /metrics
    basicAuth:
      username:
        name: myapp-metrics-basic-auth
        key: username
      password:
        name: myapp-metrics-basic-auth
        key: password
```

#### Bearer token example

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: myapp-metrics-token
  namespace: myapp-prod
stringData:
  token: eyJhbGciOi...
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    authorization:
      type: Bearer
      credentials:
        name: myapp-metrics-token
        key: token
```

Do not use `bearerTokenFile` for user monitor bearer-token configuration; use a Secret reference.

### 10.9 TLS scrape example

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp-prod
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    scheme: https
    path: /metrics
    tlsConfig:
      serverName: myapp.myapp-prod.svc
      ca:
        secret:
          name: myapp-metrics-ca
          key: ca.crt
```

For production, prefer proper CA verification over `insecureSkipVerify: true`.

## 11. PrometheusRule, alerting rules, and recording rules

### 11.1 What is PrometheusRule?

A `PrometheusRule` defines:

- Alerting rules
- Recording rules

In UWM, user-defined rules are evaluated by **Thanos Ruler** for user-defined projects.

### 11.2 Alerting rule example

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: myapp-alerts
  namespace: myapp-prod
spec:
  groups:
  - name: myapp.availability
    rules:
    - alert: MyAppHigh5xxRate
      expr: |
        sum(rate(http_requests_total{namespace="myapp-prod",code=~"5.."}[5m]))
        /
        sum(rate(http_requests_total{namespace="myapp-prod"}[5m]))
        > 0.05
      for: 10m
      labels:
        severity: warning
        team: app-team
      annotations:
        summary: "High 5xx error rate for myapp"
        description: "More than 5% of requests are returning 5xx for 10 minutes."
```

### 11.3 Recording rule example

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: myapp-recording-rules
  namespace: myapp-prod
spec:
  groups:
  - name: myapp.recording
    rules:
    - record: namespace:myapp:http_requests:rate5m
      expr: |
        sum by (namespace, route, method, code) (
          rate(http_requests_total{namespace="myapp-prod"}[5m])
        )
```

### 11.4 Why use recording rules?

Recording rules precompute expensive PromQL queries. This helps when:

- Dashboards repeatedly run the same query.
- Alert expressions are expensive.
- You need stable SLI/SLO metrics.
- You want to reduce query pressure on Prometheus / Thanos.

### 11.5 Rule design best practices

Use these practices in production:

- Always include useful labels: `severity`, `team`, `service`, `runbook_url` if possible.
- Use `for:` to avoid alert flapping.
- Avoid alerting on raw instant spikes unless it is truly critical.
- Prefer ratios over absolute counts for request error rates.
- Avoid high-cardinality labels in alert grouping.
- Ensure alerts include actionable descriptions.
- Create runbooks for critical alerts.

### 11.6 Namespace label enforcement

In multi-tenant UWM, rules are normally constrained so that users cannot easily create broad cluster-wide alerting rules from their namespace. OpenShift supports namespace-label enforcement behavior to reduce cross-project visibility risks.

Platform admins can configure exceptions using `namespacesWithoutLabelEnforcement`, but this should be used carefully for trusted platform or shared observability namespaces.

## 12. Alert routing with AlertmanagerConfig

### 12.1 Two supported approaches

OpenShift can route user-defined alerts in two main ways:

1. Through the **main platform Alertmanager**
2. Through a **dedicated user workload Alertmanager**

### 12.2 Enable user alert routing through platform Alertmanager

Edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Add:

```yaml
data:
  config.yaml: |
    enableUserWorkload: true
    alertmanagerMain:
      enableUserAlertmanagerConfig: true
```

This allows user-defined `AlertmanagerConfig` objects to be used with the main platform Alertmanager.

### 12.3 Enable a dedicated Alertmanager for user workloads

Edit:

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Add:

```yaml
data:
  config.yaml: |
    alertmanager:
      enabled: true
      enableAlertmanagerConfig: true
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get alertmanager
oc -n openshift-user-workload-monitoring get pods | grep alertmanager
```

### 12.4 When to use dedicated user workload Alertmanager

Use a dedicated user workload Alertmanager when:

- You want clean separation between platform alerts and application alerts.
- Application alert volume is high.
- You want different receivers, templates, or notification ownership.
- You want to reduce operational risk to platform alerting.

Use platform Alertmanager when:

- You want central alert management.
- Alert volume is small.
- Your platform team owns all alert routing.

### 12.5 Grant permission to configure alert routing

## 14. Persistent storage and retention planning

### 14.1 Why persistent storage matters

For production, persistent storage is strongly recommended because it protects metrics and alerting state from pod restarts and rescheduling.

Without PVCs:

- Prometheus data can be lost on pod recreation.
- Alertmanager silences can disappear.
- Thanos Ruler local state can be lost.

### 14.2 Components that need storage

| Component | Storage reason |
|---|---|
| Prometheus user workload | Time-series database, WAL, blocks. |
| Thanos Ruler | Rule evaluation data. |
| Alertmanager user workload | Notification state, silences, deduplication state. |

### 14.3 Prometheus PVC example

```yaml
data:
  config.yaml: |
    prometheus:
      volumeClaimTemplate:
        spec:
          storageClassName: fast-block
          resources:
            requests:
              storage: 100Gi
```

### 14.4 Thanos Ruler PVC example

```yaml
data:
  config.yaml: |
    thanosRuler:
      volumeClaimTemplate:
        spec:
          storageClassName: fast-block
          resources:
            requests:
              storage: 20Gi
```

### 14.5 Alertmanager PVC example

```yaml
data:
  config.yaml: |
    alertmanager:
      enabled: true
      volumeClaimTemplate:
        spec:
          storageClassName: fast-block
          resources:
            requests:
              storage: 5Gi
```

### 14.6 Storage type guidance

Use a storage class that provides:

- Reliable block storage
- Good IOPS
- POSIX-compliant filesystem
- Expandable volumes if possible
- Stable performance during compaction and WAL writes

Avoid raw block mode for Prometheus. Prometheus expects a filesystem. Be careful with NFS unless your implementation is fully POSIX compliant and performance-tested.

### 14.7 Retention configuration

Prometheus retention has two controls:

```yaml
prometheus:
  retention: 7d
  retentionSize: 80GB
```

| Parameter | Meaning |
|---|---|
| `retention` | How long data is retained. |
| `retentionSize` | Maximum disk space used by data blocks and WAL. |

### 14.8 Thanos Ruler retention

```yaml
thanosRuler:
  retention: 7d
```

### 14.9 Capacity planning formula

A rough estimate:

```text
storage ≈ samples_per_second × bytes_per_sample × retention_seconds × overhead_factor
```

Where:

- `samples_per_second` depends on number of targets, metrics per target, and scrape interval.
- `bytes_per_sample` varies due to compression and label cardinality.
- `overhead_factor` accounts for WAL, compaction, metadata, head block, and safety margin.

Practical admin approach:

1. Start with safe storage.
2. Monitor ingestion and disk growth.
3. Tune scrape intervals and cardinality.
4. Add remote write for long-term storage if required.
5. Avoid treating local Prometheus as your infinite archive.

### 14.10 Metrics to watch for storage

Useful PromQL ideas:

```promql
prometheus_tsdb_head_series
rate(prometheus_tsdb_head_samples_appended_total[5m])
prometheus_tsdb_wal_corruptions_total
prometheus_tsdb_compactions_total
kubelet_volume_stats_available_bytes{namespace="openshift-user-workload-monitoring"}
kubelet_volume_stats_used_bytes{namespace="openshift-user-workload-monitoring"}
```

## 15. Performance, scale, and cardinality control

### 15.1 The biggest risk: cardinality explosion

Cardinality means the number of unique time series.

A metric like this is safe:

```text
http_requests_total{method="GET",code="200"}
```

This can be dangerous:

```text
http_requests_total{method="GET",code="200",user_id="123456",request_id="a8f...",session_id="xyz"}
```

High-cardinality labels cause:

- High Prometheus memory usage
- High disk usage
- Slow queries
- Expensive remote write
- Possible scraping failures
- Monitoring stack instability

### 15.2 Labels to avoid

Avoid unbounded labels such as:

- `user_id`
- `email`
- `session_id`
- `request_id`
- `trace_id`
- `uuid`
- `ip_address` in high-volume systems
- raw URL path with IDs, such as `/orders/123456/items/987`

Use normalized route labels instead:

```text
/orders/{order_id}/items/{item_id}
```

### 15.3 Enforced sample and label limits

Example:

```yaml
data:
  config.yaml: |
    prometheus:
      enforcedSampleLimit: 50000
      enforcedLabelLimit: 500
      enforcedLabelNameLengthLimit: 100
      enforcedLabelValueLengthLimit: 1000
      scrapeInterval: 30s
      evaluationInterval: 30s
```

These settings control the blast radius of badly instrumented applications.

### 15.4 Important behavior

If a scrape exceeds enforced sample or label limits, Prometheus stops ingesting additional data for that target scrape. This protects the monitoring system but can cause missing metrics.

### 15.5 Scrape interval strategy

| Workload type | Suggested interval |
|---|---|
| Critical low-latency app | 15s-30s |
| Normal business app | 30s-60s |
| Batch app | 60s-120s |
| Heavy exporter | 60s+ |
| High-cardinality exporter | Tune carefully; reduce labels first. |

Do not set every application to `5s`. You will overload the monitoring stack.

### 15.6 Query performance guidance

Avoid dashboard queries like:

```promql
{namespace="myapp-prod"}
```

Prefer targeted queries:

```promql
sum by (route, code) (rate(http_requests_total{namespace="myapp-prod"}[5m]))
```

Use recording rules for expensive repeated queries.

## 16. Remote write and long-term metrics strategy

### 16.1 What remote write does

Remote write sends samples from Prometheus to an external remote-write-compatible endpoint for long-term storage or centralized analytics.

Common destinations include:

- Thanos Receive
- Cortex
- Mimir
- VictoriaMetrics
- Managed Prometheus services
- Enterprise observability platforms

### 16.2 Why use remote write

Use it when:

- You need long retention, such as 90 days, 1 year, or 13 months.
- You need cross-cluster observability.
- You need compliance retention.
- You want centralized dashboards across clusters.
- You do not want large local Prometheus disks.

### 16.3 Remote write configuration example

```yaml
data:
  config.yaml: |
    prometheus:
      remoteWrite:
      - url: https://remote-write.example.com/api/v1/write
        authorization:
          type: Bearer
          credentials:
            name: remote-write-token
            key: token
```

Create the secret in:

```bash
openshift-user-workload-monitoring
```

Example:

```bash
oc -n openshift-user-workload-monitoring create secret generic remote-write-token \
  --from-literal=token='REPLACE_ME'
```

### 16.4 Add cluster ID label for remote write

```yaml
data:
  config.yaml: |
    prometheus:
      remoteWrite:
      - url: https://remote-write.example.com/api/v1/write
        writeRelabelConfigs:
        - sourceLabels:
          - __tmp_openshift_cluster_id__
          targetLabel: cluster_id
          action: replace
```

### 16.5 Filter what you remote write

Do not send everything blindly if cost is a concern.

Example keep only selected metrics:

```yaml
data:
  config.yaml: |
    prometheus:
      remoteWrite:
      - url: https://remote-write.example.com/api/v1/write
        writeRelabelConfigs:
        - sourceLabels: [__name__]
          regex: 'http_requests_total|http_request_duration_seconds_bucket|jvm_.*'
          action: keep
```

### 16.6 Security for remote write

Production requirements:

- Use HTTPS.
- Use authentication.
- Store credentials in Secrets.
- Avoid `insecureSkipVerify` unless temporarily troubleshooting.
- Apply egress NetworkPolicies if your cluster uses them.
- Monitor remote write queue failures.

## 17. Security considerations

### 17.1 UWM is a multi-tenant security boundary

Metrics can leak sensitive information if poorly designed. Application teams must not expose:

- Customer email addresses
- User IDs if considered sensitive
- Access tokens
- Session IDs
- Payment details
- Internal secret values
- Raw query strings with credentials

### 17.2 Metrics endpoint protection

For internal cluster metrics endpoints, many teams keep metrics accessible only inside the cluster. If metrics expose sensitive operational data, secure them with:

- NetworkPolicy
- TLS
- Authentication
- Service mesh policy if applicable
- Namespace RBAC controls

### 17.3 RBAC principle

Give only the minimum required role:

| User need | Suggested role |
|---|---|
| View metrics only | Project access + `pod-metrics-reader` when API access is needed |
| Manage alert rules | `monitoring-rules-edit` |
| Create ServiceMonitor/PodMonitor | `monitoring-edit` |
| Configure alert routing | `alert-routing-edit` |
| Configure UWM stack | `user-workload-monitoring-config-edit` only for platform admins |

### 17.4 Avoid direct Prometheus access bypassing OpenShift auth

Do not expose user workload Prometheus externally using custom routes unless you have a strong reason and security review. Prefer OpenShift Console / Thanos Query API protected by OpenShift authentication and RBAC.

### 17.5 Alertmanager secrets

If using webhook credentials, API tokens, or receiver credentials:

- Store them as Secrets.
- Keep them in the correct namespace.
- Rotate them periodically.
- Avoid writing secrets into Git repositories.
- Use Sealed Secrets / External Secrets / Vault integration if GitOps is used.

## 18. Multi-tenant governance model

For a mature OpenShift platform, define an observability contract with application teams.

### 18.1 Platform team owns

- Enabling UWM
- UWM capacity and scaling
- Storage class selection
- Retention policy
- Remote write integration
- Default limits and guardrails
- RBAC templates
- Cluster-level dashboards
- Monitoring SLOs
- Alertmanager architecture

### 18.2 Application team owns

- Instrumenting code
- Exposing `/metrics`
- Creating ServiceMonitor/PodMonitor
- Creating application alert rules
- Defining runbooks
- Alert receiver ownership
- Reducing noisy alerts
- Fixing high-cardinality metrics

### 18.3 Recommended platform policies

Define standards such as:

```text
1. Every production service must expose /metrics.
2. Every production ServiceMonitor must use interval >= 30s unless approved.
3. Alerts must include severity, team, service, and runbook_url labels.
4. High-cardinality labels such as user_id, request_id, and session_id are prohibited.
5. Application teams own their own AlertmanagerConfig where permitted.
6. Platform team can disable or restrict monitors that threaten cluster stability.
```

### 18.4 GitOps model

For enterprise use, store monitoring resources in Git:

```text
apps/
  myapp/
    base/
      deployment.yaml
      service.yaml
      servicemonitor.yaml
      prometheusrule.yaml
    overlays/
      dev/
      prod/
```

Use Argo CD or OpenShift GitOps to manage:

- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`
- `AlertmanagerConfig`
- namespace RBAC

Do not let every team manually create monitoring objects in production without review.

### 20.1 UWM pods not created

Check:

```bash
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml
```

Confirm:

```yaml
enableUserWorkload: true
```


Check logs:

```bash
oc -n openshift-monitoring logs deploy/cluster-monitoring-operator
```

Likely causes:

- Invalid YAML in `cluster-monitoring-config`
- Unsupported field in config
- CMO degraded
- Custom unsupported Prometheus CRs present
- Insufficient resources

### 20.2 UWM pods pending

Check:

```bash
oc -n openshift-user-workload-monitoring get pods
oc -n openshift-user-workload-monitoring describe pod <pod>
```

Look for:

- PVC pending
- Node selector mismatch
- Taints without tolerations
- Insufficient CPU/memory
- Topology spread too strict

Check PVC:

```bash
oc -n openshift-user-workload-monitoring get pvc
oc -n openshift-user-workload-monitoring describe pvc <pvc>
```

### 20.3 ServiceMonitor created but target not scraped

Check ServiceMonitor:

```bash
oc -n myapp-prod get servicemonitor
oc -n myapp-prod describe servicemonitor myapp-monitor
```

Check Service labels:

```bash
oc -n myapp-prod get svc --show-labels
```

Check service port names:

```bash
oc -n myapp-prod get svc myapp -o yaml
```

Check endpoints:

```bash
oc -n myapp-prod get endpoints myapp -o yaml
oc -n myapp-prod get endpointslice -l kubernetes.io/service-name=myapp
```

Common causes:

- ServiceMonitor selector does not match Service labels.
- Service port name is wrong.
- Service has no endpoints because pod labels do not match service selector.
- Metrics endpoint path is wrong.
- Application is not actually serving metrics.
- NetworkPolicy blocks traffic.
- TLS/auth settings are wrong.

### 20.4 Test metrics endpoint from inside cluster

Use a debug pod:

```bash
oc -n myapp-prod run curl-test --rm -it --image=curlimages/curl -- sh
```

Inside:

```bash
curl -v http://myapp.myapp-prod.svc:8080/metrics
```

If curl image is not allowed, use UBI and install tools only in a lab environment if repos are available, or use an approved internal troubleshooting image.

### 20.5 PrometheusRule not firing

Check rule object:

```bash
oc -n myapp-prod get prometheusrule
oc -n myapp-prod describe prometheusrule myapp-alerts
```

Check syntax by querying expression manually in Observe → Metrics.

Common causes:

- Metric name wrong.
- Label filter wrong.
- Rule namespace mismatch.
- `for:` duration has not elapsed.
- Data missing because scrape target is down.
- Alert severity labels missing but route expects them.

### 20.6 Alert fires but notification not received

Check:

```bash
oc -n myapp-prod get alertmanagerconfig
oc -n myapp-prod describe alertmanagerconfig myapp-routing
```

Check whether alert routing is enabled:

```bash
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml
oc -n openshift-user-workload-monitoring get cm user-workload-monitoring-config -o yaml
```

Check Alertmanager pods:

```bash
oc -n openshift-monitoring get pods | grep alertmanager
oc -n openshift-user-workload-monitoring get pods | grep alertmanager
```

Common causes:

- `alert-routing-edit` missing.
- Alert routing not enabled.
- Wrong API version for `AlertmanagerConfig`.
- Receiver URL blocked by egress policy/proxy.
- Route matcher does not match alert labels.
- Secret missing or in wrong namespace.

```bash

```

Check ConfigMap YAML:


- Bad indentation
- Unsupported field
- Duplicate YAML key
- Wrong type, for example string instead of boolean
- Invalid resource quantity


- Reduce retention.
- Set `retentionSize`.
- Increase PVC if storage class supports expansion.
- Reduce scrape frequency.
- Drop high-cardinality metrics.
- Add remote write for long-term retention.

## 21. Common mistakes and fixes

| Mistake | Symptom | Fix |
|---|---|---|
| UWM not enabled | No `prometheus-user-workload` pods | Set `enableUserWorkload: true`. |
| Wrong namespace | Monitor created in different namespace than app | Create monitor in same app namespace. |
| Service label mismatch | Target not discovered | Match ServiceMonitor selector with Service labels. |
| Wrong port name | Target missing or scrape error | Use Service port name, not random name. |
| Metrics path wrong | HTTP 404 scrape error | Set correct `path`, usually `/metrics`. |
| App not exposing metrics | `connection refused` or empty metrics | Fix app/exporter. |
| NetworkPolicy blocks scrape | Timeout | Allow traffic from UWM/monitoring components as required. |
| Bad TLS config | x509 errors | Use correct CA/serverName. |
| Secret in wrong namespace | Auth failure | Put Secret in same namespace expected by monitor/config. |
| High-cardinality labels | Prometheus memory/disk growth | Remove unbounded labels, relabel/drop metrics. |
| Too-short scrape interval | High CPU/network | Increase interval. |
| Alert route not enabled | Alert visible but no notification | Enable user alert routing. |
| Missing RBAC | User cannot create monitors/rules | Bind `monitoring-edit` or required role. |
| Invalid ConfigMap YAML | Monitoring operator degraded | Fix YAML and unsupported fields. |

## 23. Interview and real-world scenario questions

### Q1. What is the difference between platform monitoring and user workload monitoring?

Platform monitoring observes the OpenShift cluster itself and runs in `openshift-monitoring`. User workload monitoring observes application workloads in user-defined projects and runs in `openshift-user-workload-monitoring`.

### Q2. How do you enable UWM?

Set `enableUserWorkload: true` in `openshift-monitoring/cluster-monitoring-config` under `data.config.yaml`, then verify UWM pods in `openshift-user-workload-monitoring`.

### Q3. Which component scrapes user application metrics?

`prometheus-user-workload` scrapes user application metrics based on `ServiceMonitor` and `PodMonitor` resources.

### Q4. Which component evaluates user-defined alerting rules?

`thanos-ruler-user-workload` evaluates user-defined `PrometheusRule` resources.

### Q5. Can a ServiceMonitor in one user namespace scrape a Service in another namespace?

In normal UWM behavior, a `ServiceMonitor` in a user-defined namespace should discover Services in the same namespace. Design tenant monitoring so monitor objects live with the workload.

### Q6. What role allows a user to create ServiceMonitor and PodMonitor?

`monitoring-edit`, bound in the target namespace.

### Q7. What is the biggest operational risk in UWM?

High-cardinality metrics and excessive scrape volume. These can increase Prometheus memory, CPU, disk usage, query latency, and remote write cost.

### Q8. When would you use remote write?

Use remote write for long-term retention, cross-cluster observability, compliance, or centralized metrics platforms.

### Q9. How do you separate platform alerts from app alerts?

Enable a dedicated user workload Alertmanager, or configure routing rules so platform and user alerts go to different receivers.

### Q10. What should you check if a ServiceMonitor is not working?

Check monitor namespace, Service labels, Service port names, Endpoints, metrics path, application availability, auth/TLS settings, NetworkPolicy, and Prometheus target status.

## Final senior-admin summary

User Workload Monitoring is a core OpenShift observability feature that lets application teams monitor their own projects without deploying unsupported or duplicate Prometheus stacks. For a senior administrator, the most important skills are not only enabling it, but operating it safely:

- Enable it through `cluster-monitoring-config`.
- Configure it through `user-workload-monitoring-config`.
- Delegate access through namespace-scoped RBAC.
- Use `ServiceMonitor` and `PodMonitor` for scrape discovery.
- Use `PrometheusRule` for app alerting and recording rules.
- Use `AlertmanagerConfig` only after alert routing is enabled.
- Control storage, retention, resource requests, scrape limits, and cardinality.
- Treat UWM as a multi-tenant platform service with clear governance.

In production, UWM success depends on discipline: good metrics design, controlled cardinality, clear ownership, tested alert routing, and continuous monitoring of the monitoring stack itself.
