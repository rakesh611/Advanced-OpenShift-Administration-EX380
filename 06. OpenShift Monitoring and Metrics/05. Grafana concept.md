# Grafana Concept in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift Administration / 10+ years Linux, DevOps, Kubernetes, OpenShift experience  
**Focus area:** OpenShift Monitoring and Metrics  
**Last verified:** 2026-07-03  
**Primary OpenShift context:** OpenShift Container Platform 4.x, especially modern 4.19-style observability architecture

---

## 1. Executive Summary

Grafana is a **visualization and analytics layer** used to build dashboards from metrics, logs, and traces. In an OpenShift monitoring environment, Grafana is normally not the component that collects metrics. Metrics are collected by **Prometheus**, exposed through **exporters**, aggregated or federated through **Thanos Querier**, and alert notifications are handled by **Alertmanager**. Grafana sits above these systems and turns raw time-series data into operational dashboards.

In older OpenShift 4 releases, OpenShift shipped a Grafana instance with the default monitoring stack. That bundled Grafana was generally **read-only** and focused on Kubernetes and cluster-monitoring dashboards. In newer OpenShift releases, the supported day-to-day dashboard experience is mainly through the OpenShift web console under **Observe → Dashboards**, while the core monitoring stack is managed by the **Cluster Monitoring Operator (CMO)** and includes components such as Prometheus, Alertmanager, Thanos Querier, Telemeter Client, and metric targets.

For an advanced administrator, the key point is this:

> Grafana is not the monitoring stack itself. Grafana is the dashboard and visualization front end. In OpenShift, the supported metric backend is the Prometheus-based CMO-managed stack, and custom Grafana usage should be treated as an additional visualization layer connected to Prometheus or Thanos APIs.

## 2. Why Grafana Matters for an OpenShift Administrator

Grafana matters because OpenShift administrators need more than raw metrics. They need fast answers to operational questions:

- Is the cluster healthy?
- Which node is under pressure?
- Which namespace is consuming the most CPU or memory?
- Are pods restarting because of application failure, OOMKill, image pull failure, or node instability?
- Is etcd latency increasing?
- Is API server request latency normal?
- Is Prometheus itself overloaded?
- Which workload is creating high-cardinality metrics?
- Is user workload monitoring scraping application metrics correctly?
- Are dashboards slow because PromQL is expensive or because Prometheus/Thanos is under pressure?

Grafana helps by combining metrics into visual views such as time-series graphs, gauges, tables, heatmaps, single-stat panels, bar charts, and alert panels.

However, in OpenShift administration, you must clearly separate these responsibilities:

| Layer | Component | Responsibility |
|---|---|---|
| Metric producer | Application, kubelet, node-exporter, kube-state-metrics, operators | Exposes metrics, usually on `/metrics` |
| Scraping and storage | Prometheus | Scrapes targets and stores time-series data |
| Rule evaluation | Prometheus / Thanos Ruler | Evaluates recording and alerting rules |
| Alert routing | Alertmanager | Groups, silences, routes notifications |
| Aggregated query layer | Thanos Querier | Gives a unified query API across platform and user workload metrics |
| Visualization | Grafana / OpenShift Console Dashboards | Shows dashboards and visual analysis |

## 3. Modern OpenShift Monitoring Architecture

OpenShift includes a preconfigured monitoring stack. The stack is deployed by default and managed by the **Cluster Monitoring Operator**. Modern OpenShift observability documentation describes monitoring as part of a broader observability platform that includes monitoring, logging, distributed tracing, OpenTelemetry, network observability, and power monitoring.

At a high level:

```text
Applications / Platform components
        |
        | expose /metrics
        v
ServiceMonitor / PodMonitor / built-in scrape configs
        |
        v
Prometheus Operator
        |
        v
Prometheus instances
        |
        +--> Alertmanager for alerts
        |
        +--> Thanos sidecar / Thanos Querier for aggregated queries
        |
        v
OpenShift Console Observe UI / Grafana / external consumers
```

### 3.1 Core OpenShift monitoring namespace

Core platform monitoring components run mainly in:

```bash
openshift-monitoring
```

Common resources:

```bash
oc get pods -n openshift-monitoring
oc get routes -n openshift-monitoring
oc get cm -n openshift-monitoring
oc get prometheus -n openshift-monitoring
oc get alertmanager -n openshift-monitoring
oc get servicemonitor -n openshift-monitoring
oc get prometheusrule -n openshift-monitoring
```

Typical components include:

- `cluster-monitoring-operator`
- `prometheus-k8s`
- `prometheus-operator`
- `alertmanager-main`
- `thanos-querier`
- `kube-state-metrics`
- `node-exporter`
- `openshift-state-metrics`
- `telemeter-client`

### 3.2 User workload monitoring namespace

When user-defined workload monitoring is enabled, user workload components run mainly in:


Common resources:

```bash
oc get pods -n openshift-user-workload-monitoring
```

- `thanos-ruler-user-workload-0`
- `thanos-ruler-user-workload-1`

## 4. Grafana’s Role in OpenShift

Grafana performs four major roles:

1. **Visualization**  
   Converts PromQL query results into graphs, tables, gauges, and dashboards.

2. **Exploration**  
   Lets administrators explore metrics interactively before formalizing dashboards.

3. **Operational dashboards**  
   Provides reusable dashboards for platform, application, SRE, capacity, and troubleshooting views.

4. **Optional alerting**  
   Grafana can evaluate alerts against data sources, but in OpenShift, the native and supported alerting path is normally **PrometheusRule → Alertmanager**.

Important clarification:

```text
Grafana does not scrape OpenShift metrics by itself.
Grafana does not replace Prometheus.
Grafana does not replace Alertmanager in the supported OpenShift monitoring stack.
Grafana queries Prometheus-compatible APIs and visualizes the result.
```

## 5. OpenShift Version Behavior: Legacy Bundled Grafana vs Modern Console Dashboards

### 5.1 Older OpenShift behavior

In earlier OpenShift 4 versions, OpenShift exposed a Grafana UI in the `openshift-monitoring` namespace. This Grafana instance was useful for viewing predefined dashboards, but it had important limitations:

- The bundled Grafana instance and dashboards were read-only.
- It focused on Kubernetes and `cluster-monitoring` metrics.
- Third-party UI access was deprecated in some releases.
- Custom dashboards in the built-in Grafana were not the right long-term design.

### 5.2 Modern OpenShift behavior

In newer OpenShift releases, the preferred supported UI is the OpenShift web console:

```text
Observe → Dashboards
Observe → Metrics
Observe → Alerts
Observe → Targets
```

The current platform monitoring stack is CMO-managed. Grafana is not the primary supported dashboard surface for platform monitoring in the same way it was in older releases. If an organization wants Grafana, it usually deploys a separate Grafana instance and connects it to Prometheus or Thanos as a data source.

### 5.3 Practical admin guidance

For real production clusters:

- Use **Observe → Dashboards** first for supported platform dashboards.
- Use **Observe → Metrics** for quick PromQL investigation.
- Use **PrometheusRule** and **Alertmanager** for supported OpenShift alerting.
- Deploy separate Grafana only when you need custom visualization, cross-system dashboards, business/service dashboards, multi-cluster dashboards, or external integrations.
- Do not modify CMO-managed monitoring stack objects directly unless Red Hat documentation says the field is supported through `cluster-monitoring-config` or `user-workload-monitoring-config`.

## 7. Key Grafana Concepts

### 7.1 Data source

A Grafana data source is a backend system that Grafana queries. In OpenShift monitoring, common data sources are:

- Prometheus
- Thanos Querier
- Loki, if using logs
- Tempo or Jaeger-like tracing systems, if using tracing
- Elasticsearch/OpenSearch, in some legacy logging designs
- PostgreSQL/MySQL for business dashboards

For OpenShift metrics, the most important data source type is **Prometheus**, because Thanos Querier also exposes a Prometheus-compatible API.

Example data source URL pattern:

```text
https://thanos-querier-openshift-monitoring.apps.<cluster-domain>
```

or inside the cluster:

```text
https://thanos-querier.openshift-monitoring.svc:9091
```

The exact service port and route depend on the OpenShift version and configuration.

### 7.2 Dashboard

A dashboard is a collection of panels designed to answer a particular operational question.

Examples:

- Cluster overview dashboard
- Node health dashboard
- Namespace resource usage dashboard
- Application SLO dashboard
- API server performance dashboard
- etcd health dashboard
- Prometheus health dashboard
- Storage dashboard
- Network performance dashboard

### 7.3 Panel

A panel is one visualization block inside a dashboard.

Common Grafana panel types:

| Panel type | Use case |
|---|---|
| Time series | CPU, memory, request rate, latency over time |
| Stat | Current value, e.g. Ready nodes |
| Gauge | Utilization percentage |
| Bar gauge | Per-node or per-namespace comparison |
| Table | Pod restart list, PVC list, alert list |
| Heatmap | Latency buckets or distribution analysis |
| Logs | If connected to Loki or logging backend |

### 7.4 Query

For Prometheus and Thanos, Grafana uses **PromQL**.

Example:

```promql
sum(rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])) by (namespace)
```

This query shows CPU usage rate grouped by namespace.

### 7.5 Variables

Variables make dashboards reusable.

Example variables:

| Variable | Purpose |
|---|---|
| `$cluster` | Select cluster in multi-cluster Grafana |
| `$namespace` | Select OpenShift namespace/project |
| `$workload` | Select deployment, statefulset, or app |
| `$pod` | Select pod |
| `$node` | Select worker/master node |
| `$container` | Select container |
| `$interval` | Dynamic query interval |

Example variable query:

```promql
label_values(kube_namespace_status_phase, namespace)
```

Example usage:

```promql
sum(rate(container_cpu_usage_seconds_total{namespace="$namespace", container!=""}[5m])) by (pod)
```

### 7.6 Transformations

Grafana transformations reshape data after query execution. Use them carefully.

Examples:

- Rename fields
- Join data from multiple queries
- Calculate derived fields
- Convert labels into columns
- Filter series by value

Advanced admin advice:

> Prefer correct PromQL first. Use Grafana transformations for display shaping, not for heavy computation that belongs in PromQL or recording rules.

### 7.7 Annotations

Annotations mark events on graphs.

Useful OpenShift annotation examples:

- Deployment rollout time
- Application release time
- Node reboot
- Incident window
- Cluster upgrade start/end
- MachineConfig rollout
- etcd leader change

Annotations help answer: “Did the metric change after a release or cluster operation?”

### 7.8 Alerting

Grafana has its own alerting system. But in OpenShift, the supported native alerting model is usually:

```text
PrometheusRule → Prometheus/Thanos Ruler → Alertmanager → Receiver
```

Use Grafana alerting when:

- You are running an independent Grafana stack.
- You need dashboards and alerts across non-OpenShift data sources.
- Your organization standardizes on Grafana Alerting.

Use OpenShift monitoring alerting when:

- The alert is platform-related.
- The metric is from OpenShift platform or user workload monitoring.
- You need supportable Kubernetes-native alert definitions.
- You want alerts visible in the OpenShift console.

## 8. Grafana vs OpenShift Console Dashboards

| Feature | OpenShift Console Dashboards | Grafana |
|---|---|---|
| Supported by OpenShift platform | Yes | Separate deployment depends on installation method |
| Default platform dashboards | Yes | Older releases had bundled read-only Grafana; modern clusters usually use console dashboards |
| Custom dashboard flexibility | Moderate | Very high |
| Multi-data-source dashboards | Limited | Strong |
| PromQL support | Yes, in metrics UI and dashboards | Yes |
| GitOps dashboard provisioning | Possible with console dashboard ConfigMaps in some contexts; varies by component | Strong with dashboard JSON/provisioning |
| User experience | Integrated with OpenShift RBAC and console | Separate UI and auth model |
| Best use | Platform operations | Custom SRE/application/business dashboards |

## 9. Grafana Data Source Design for OpenShift

### 9.1 Option 1: Query Thanos Querier

This is usually the best approach for a custom Grafana instance because Thanos Querier provides a unified query interface.

Advantages:

- Can aggregate platform and user workload metrics depending on access and configuration.
- Provides a Prometheus-compatible query API.
- Avoids pointing dashboards directly to individual Prometheus replicas.
- Better for HA Prometheus environments.

Example test:

```bash
HOST=$(oc -n openshift-monitoring get route thanos-querier -o jsonpath='{.spec.host}')
TOKEN=$(oc whoami -t)

curl -k \
  -H "Authorization: Bearer ${TOKEN}" \
  "https://${HOST}/api/v1/query?query=up"
```

If this returns JSON with `status: success`, the API is reachable.

### 9.2 Option 2: Query platform Prometheus directly

Example route:

```bash
oc -n openshift-monitoring get route prometheus-k8s
```

This can work, but it is less ideal for long-term dashboard design because:

- Prometheus may run as multiple replicas.
- You might need to handle deduplication or replica differences.
- Platform Prometheus is focused on core platform monitoring.
- User workload metrics might be in a separate Prometheus.

### 9.3 Option 3: Query user workload Prometheus

Useful if Grafana should only visualize application metrics.

Namespace:

```bash
openshift-user-workload-monitoring
```

Check pods:

```bash
oc get pods -n openshift-user-workload-monitoring
```

### 9.4 Recommended production pattern

For most enterprise clusters:

```text
Grafana → Thanos Querier → Prometheus platform + user workload metrics
```

For strict tenant isolation:

```text
Team Grafana → restricted service account/token → only allowed metrics/projects
```

## 10. Authentication and Authorization

### 10.1 OpenShift OAuth

Older bundled monitoring UIs used OpenShift login through OAuth proxy. For custom Grafana, common approaches include:

- OpenShift OAuth integration
- OIDC integration with corporate identity provider
- LDAP integration
- SSO through Keycloak/Red Hat SSO
- Basic auth only for lab/test environments

For production, avoid local-only Grafana users unless required by policy.

### 10.2 Bearer token to query OpenShift monitoring APIs

A Grafana Prometheus data source can authenticate using a bearer token.

Common approaches:

- A dedicated service account token mounted into the Grafana pod
- An externally managed token stored in a Kubernetes Secret
- OAuth/OIDC user flow, depending on deployment model

Example service account:

```bash
oc create ns grafana-monitoring
oc -n grafana-monitoring create sa grafana-reader
```

Grant read permission to monitoring data, depending on your policy:

```bash
oc adm policy add-cluster-role-to-user cluster-monitoring-view \
  -z grafana-reader \
  -n grafana-monitoring
```

Then create or use a projected token. In newer Kubernetes/OpenShift versions, prefer the TokenRequest API instead of relying on old long-lived service account token Secrets.

Example short-lived token test:

```bash
TOKEN=$(oc -n grafana-monitoring create token grafana-reader)
HOST=$(oc -n openshift-monitoring get route thanos-querier -o jsonpath='{.spec.host}')

curl -k \
  -H "Authorization: Bearer ${TOKEN}" \
  "https://${HOST}/api/v1/query?query=up"
```

### 10.3 RBAC principles

Do not give Grafana `cluster-admin`.

Use least privilege:

| Requirement | Permission direction |
|---|---|
| View cluster metrics | `cluster-monitoring-view` or equivalent approved role |
| View project metrics only | Namespace-scoped monitoring roles where possible |
| Create ServiceMonitor/PodMonitor | `monitoring-edit` in target namespace |
| Edit PrometheusRule | `monitoring-rules-edit` |
| View PrometheusRule | `monitoring-rules-view` |
| Configure user workload monitoring stack | `user-workload-monitoring-config-edit` in `openshift-user-workload-monitoring` |

## 11. Enabling User Workload Monitoring

User workload monitoring lets application teams expose metrics and have OpenShift scrape them without deploying a separate Prometheus stack.

### 11.1 Enable user workload monitoring

Create or edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Verify:

```bash
oc get pods -n openshift-user-workload-monitoring
```

Expected components include:

```text
prometheus-user-workload-0
prometheus-user-workload-1
prometheus-operator
thanos-ruler-user-workload-0
thanos-ruler-user-workload-1
```

### 11.2 Application ServiceMonitor example

Assume app namespace:

```bash
oc new-project app-demo
```

Deployment exposes metrics on port `web` or `metrics`.

Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: demo-app
  namespace: app-demo
  labels:
    app: demo-app
spec:
  selector:
    app: demo-app
  ports:
  - name: metrics
    port: 8080
    targetPort: 8080
```

ServiceMonitor:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: demo-app
  namespace: app-demo
spec:
  selector:
    matchLabels:
      app: demo-app
  endpoints:
  - port: metrics
    path: /metrics
    interval: 30s
```

Check if target appears:

```bash
oc -n app-demo get servicemonitor
oc -n openshift-user-workload-monitoring logs deploy/prometheus-operator
```

In OpenShift Console:

```text
Observe → Targets
Observe → Metrics
```

Example query:

```promql
up{namespace="app-demo"}
```

## 12. OpenShift Metrics You Should Know for Grafana Dashboards

### 12.1 CPU usage by namespace

```promql
sum(rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])) by (namespace)
```

### 12.2 CPU usage by pod in a namespace

```promql
sum(rate(container_cpu_usage_seconds_total{namespace="$namespace", container!="", pod!=""}[5m])) by (pod)
```

### 12.3 Memory working set by namespace

```promql
sum(container_memory_working_set_bytes{container!="",pod!=""}) by (namespace)
```

### 12.4 Memory working set by pod

```promql
sum(container_memory_working_set_bytes{namespace="$namespace", container!="", pod!=""}) by (pod)
```

### 12.5 Pod restart count

```promql
sum(increase(kube_pod_container_status_restarts_total{namespace="$namespace"}[1h])) by (pod, container)
```

### 12.6 Pods not ready

```promql
sum(kube_pod_status_ready{namespace="$namespace", condition="false"}) by (pod)
```

### 12.7 Node CPU utilization percentage

```promql
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

### 12.8 Node memory available percentage

```promql
(node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100
```

### 12.9 Filesystem usage percentage

```promql
100 * (1 - (node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}))
```

### 12.10 API server request rate

```promql
sum(rate(apiserver_request_total[5m])) by (verb, resource, code)
```

### 12.11 API server latency p99

```promql
histogram_quantile(0.99, sum(rate(apiserver_request_duration_seconds_bucket[5m])) by (le, verb, resource))
```

### 12.12 etcd disk sync latency p99

```promql
histogram_quantile(0.99, sum(rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) by (le, instance))
```

### 12.13 Prometheus target health

```promql
up == 0
```

### 12.14 High-cardinality hint

```promql
topk(20, count by (__name__)({__name__=~".+"}))
```

Use with care. Expensive broad queries can affect Prometheus/Thanos performance.

## 13. Dashboard Design for Experienced Administrators

A good Grafana dashboard is not a random collection of graphs. It should answer a specific operational question.

### 13.1 Cluster overview dashboard

Purpose: “Is my OpenShift cluster healthy?”

Recommended panels:

- Cluster version
- Node count by role and readiness
- Control plane health
- API server request rate and latency
- etcd leader and latency
- Cluster operators degraded/progressing/available
- CPU/memory utilization by node
- Top namespaces by CPU
- Top namespaces by memory
- Firing alerts count by severity
- Prometheus target down count

### 13.2 Node health dashboard

Purpose: “Which node is unhealthy or overloaded?”

Panels:

- CPU utilization by node
- Load average by node
- Memory available by node
- Disk pressure and filesystem usage
- Network receive/transmit errors
- Kubelet running pod count
- Container runtime errors
- Node condition table
- Top pods on selected node

### 13.3 Namespace/application dashboard

Purpose: “Is this application healthy?”

Panels:

- Pod readiness
- Deployment replica availability
- CPU by pod
- Memory by pod
- Restart count
- HTTP request rate
- Error rate
- Latency p50/p95/p99
- Saturation against CPU/memory requests and limits
- PVC usage if application is stateful

### 13.4 SRE dashboard: RED method

RED means:

- **Rate**: requests per second
- **Errors**: failed requests per second or percentage
- **Duration**: request latency

Useful for services and APIs.

Example request rate:

```promql
sum(rate(http_requests_total{namespace="$namespace", app="$app"}[5m]))
```

Error percentage:

```promql
100 * (
  sum(rate(http_requests_total{namespace="$namespace", app="$app", status=~"5.."}[5m]))
  /
  sum(rate(http_requests_total{namespace="$namespace", app="$app"}[5m]))
)
```

Latency p95:

```promql
histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket{namespace="$namespace", app="$app"}[5m])) by (le)
)
```

### 13.5 Infrastructure dashboard: USE method

USE means:

- **Utilization**: how busy the resource is
- **Saturation**: how much work is queued
- **Errors**: error events

Useful for nodes, storage, network, and control plane components.

### 14.3 Grant read access

```bash
oc adm policy add-cluster-role-to-user cluster-monitoring-view \
```

```bash
TOKEN=$(oc -n grafana-monitoring create token grafana-reader)

  -H "Authorization: Bearer ${TOKEN}" \
```

### 14.5 Grafana Prometheus data source settings

In Grafana:

```text
Data source type: Prometheus
URL: https://<thanos-route-host>
Access: Server/proxy

HTTP header: Authorization: Bearer <token>
```

For production, do not hard-code tokens manually into UI fields if your organization requires GitOps or secret rotation. Store credentials in Kubernetes Secrets or external secret management tools.

## 15. Deploying Grafana on OpenShift

There are multiple ways to deploy Grafana:

1. Operator-based deployment from OperatorHub
2. Helm chart
3. Plain Kubernetes Deployment/StatefulSet
4. External enterprise Grafana outside OpenShift
5. Managed Grafana service

### 15.1 Operator-based deployment

Advantages:

- Kubernetes-native lifecycle
- Easier CR-based management
- Can integrate dashboard and data source CRs if supported by chosen Operator

Cautions:

- Community operators may not be Red Hat supported.
- CRDs and schemas differ between Operators.
- Always check supportability before using in production.

### 15.2 Helm-based deployment

Advantages:

- Common in GitOps workflows
- Easy values-based customization
- Works with Argo CD

Cautions:

- Review SecurityContextConstraints compatibility.
- Do not run privileged unnecessarily.
- Ensure persistent storage and backup strategy.

### 15.3 Plain Deployment example skeleton

This is a conceptual example. Adjust image, storage, security context, and configuration for your environment.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: grafana
  namespace: grafana-monitoring
spec:
  replicas: 1
  selector:
    matchLabels:
      app: grafana
  template:
    metadata:
      labels:
        app: grafana
    spec:
      serviceAccountName: grafana-reader
      containers:
      - name: grafana
        image: grafana/grafana:latest
        ports:
        - name: http
          containerPort: 3000
        env:
        - name: GF_SECURITY_ADMIN_USER
          valueFrom:
            secretKeyRef:
              name: grafana-admin
              key: username
        - name: GF_SECURITY_ADMIN_PASSWORD
          valueFrom:
            secretKeyRef:
              name: grafana-admin
              key: password
        volumeMounts:
        - name: grafana-storage
          mountPath: /var/lib/grafana
      volumes:
      - name: grafana-storage
        persistentVolumeClaim:
          claimName: grafana-storage
```

Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: grafana
  namespace: grafana-monitoring
spec:
  selector:
    app: grafana
  ports:
  - name: http
    port: 3000
    targetPort: 3000
```

Route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: grafana
  namespace: grafana-monitoring
spec:
  to:
    kind: Service
    name: grafana
  port:
    targetPort: http
  tls:
    termination: edge
```

Important: `grafana/grafana:latest` is not a production-pinned image strategy. Pin an approved version or digest.

## 17. Security Best Practices

### 17.1 Do not expose Grafana without authentication

Grafana should always require authentication.

Production options:

- OpenShift OAuth
- Corporate OIDC/SAML
- LDAP
- Reverse proxy with SSO
- Grafana Enterprise authentication integrations

### 17.2 Use least-privilege data source credentials

Bad practice:

```text
Grafana uses kubeadmin token or cluster-admin token
```

Good practice:

```text
Grafana uses dedicated service account with read-only monitoring permission
```

### 17.3 Secure TLS

Avoid long-term `tlsSkipVerify: true`.

Better:

- Mount OpenShift router CA or cluster CA into Grafana.
- Configure data source TLS CA certificate.
- Use trusted enterprise certificates.

### 17.4 Protect secrets

Store tokens and admin passwords in:

- Kubernetes Secrets
- External Secrets Operator
- Vault
- Sealed Secrets
- SOPS + GitOps

Never commit plaintext tokens to Git.

### 17.5 NetworkPolicy

Restrict Grafana egress to only required services:

- Thanos Querier
- Prometheus API, if used
- OIDC/LDAP/SSO endpoints
- Notification endpoints, if Grafana Alerting is used

Example concept:

```text
Grafana namespace egress:
  allow -> openshift-monitoring/thanos-querier
  allow -> corporate identity provider
  deny -> everything else
```

### 17.6 Multi-tenancy

Grafana itself is not automatically OpenShift project-aware unless configured that way.

Risk:

- A user may see metrics from namespaces they should not see.

Mitigation:

- Use separate Grafana organizations or folders.
- Use team-based permissions.
- Use separate data sources with scoped credentials.
- Use query variables carefully.
- Use OpenShift RBAC and service accounts appropriately.

## 18. Performance and Scale Considerations

### 18.1 Query cost matters

A Grafana dashboard can overload Prometheus or Thanos if it contains many expensive queries and a low refresh interval.

Bad pattern:

```promql
{__name__=~".*"}
```

Bad pattern:

```promql
sum by (pod, container, image, id, name, instance, namespace) (rate(container_cpu_usage_seconds_total[1m]))
```

Better:

```promql
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m]))
```

### 18.2 Avoid unnecessary high cardinality

High-cardinality labels include:

- `pod` when pods are short-lived
- `container_id`
- `image_id`
- `request_id`
- `user_id`
- `session_id`
- dynamic URL paths

Never expose application metrics with labels such as:

```text
user_id
transaction_id
uuid
email
full_url_with_id
```

### 18.3 Use recording rules

For expensive queries that dashboards use often, create recording rules.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: namespace-cpu-recording
  namespace: app-demo
spec:
  groups:
  - name: namespace.cpu.rules
    rules:
    - record: namespace:container_cpu_usage_seconds_total:sum_rate5m
      expr: |
        sum(rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])) by (namespace)
```

Then dashboard query becomes:

```promql
namespace:container_cpu_usage_seconds_total:sum_rate5m
```

### 18.4 Dashboard refresh interval

Recommended refresh intervals:

| Dashboard type | Refresh interval |
|---|---|
| Incident live view | 15s to 30s, temporarily |
| Normal operations | 1m to 5m |
| Capacity planning | 15m to 1h |
| Executive dashboards | 5m to 30m |

Do not set every dashboard to refresh every 5 seconds.

### 18.5 Time range

Large time ranges increase query cost.

Examples:

- Troubleshooting: last 15m, 30m, 1h
- Incident review: last 6h, 24h
- Capacity: last 7d, 15d, 30d

Remember Prometheus retention may limit how far back you can query unless remote storage or long-term storage is configured.

## 19. Troubleshooting Grafana with OpenShift Metrics

### 19.1 Dashboard shows “No data”

Possible causes:

| Cause | Check |
|---|---|
| Wrong time range | Change to last 1h or 6h |
| Wrong namespace variable | Verify variable value exists |
| Wrong label selector | Run query in OpenShift Observe → Metrics |
| Metrics not scraped | Check Observe → Targets |
| ServiceMonitor label mismatch | Check Service labels and ServiceMonitor selector |
| User workload monitoring disabled | Check `enableUserWorkload: true` |
| RBAC denies metric access | Test API with Grafana token |
| Data source URL wrong | Test `/api/v1/query?query=up` |
| TLS issue | Verify CA or route certificate |

### 19.2 Grafana data source returns 401 Unauthorized

Check token:

```bash
oc whoami --show-token
oc -n grafana-monitoring create token grafana-reader
```

Test:

```bash
curl -k -H "Authorization: Bearer ${TOKEN}" \
  "https://${THANOS_HOST}/api/v1/query?query=up"
```

If user token works but service account token does not, check RBAC.

### 19.3 Grafana data source returns 403 Forbidden

Likely RBAC issue.

Check bindings:

```bash
oc get clusterrolebinding | grep grafana
oc auth can-i get namespaces --as=system:serviceaccount:grafana-monitoring:grafana-reader
```

Grant appropriate role:

```bash
oc adm policy add-cluster-role-to-user cluster-monitoring-view \
  -z grafana-reader \
  -n grafana-monitoring
```

### 19.4 Grafana data source cannot connect

Check route:

```bash
oc -n openshift-monitoring get route thanos-querier
```

Check DNS:

```bash
nslookup ${THANOS_HOST}
```

Check connectivity from Grafana pod:

```bash
oc -n grafana-monitoring rsh deploy/grafana
curl -k https://${THANOS_HOST}/-/ready
```

If `curl` is unavailable, use a debug pod:

```bash
oc -n grafana-monitoring run curl-test --rm -it --image=curlimages/curl -- sh
```

### 19.5 ServiceMonitor exists but target not scraped

Check labels:

```bash
oc -n app-demo get svc --show-labels
oc -n app-demo get servicemonitor demo-app -o yaml
```

The ServiceMonitor selector must match the Service labels.

Check endpoint port name:

```yaml
endpoints:
- port: metrics
```

The value `metrics` must match the Service port name:

```yaml
ports:
- name: metrics
```

### 19.6 Query works in Prometheus but not in Grafana

Possible causes:

- Different data source
- Different time range
- Grafana variable interpolation issue
- Grafana is querying Thanos with different labels
- Dashboard uses `$namespace` but variable is empty
- Query uses regex but variable is not configured for multi-value

Debug by copying the final interpolated query from Grafana Query Inspector.

### 19.7 Dashboard is slow

Check:

- Number of panels
- Number of queries per panel
- Query time range
- Refresh interval
- Use of regex matchers
- Use of high-cardinality labels
- Thanos Querier CPU/memory
- Prometheus query duration metrics

Useful metrics:

```promql
prometheus_engine_query_duration_seconds
prometheus_engine_queries
thanos_query_concurrent_gate_queries_max
```

## 20. Advanced PromQL Patterns for Grafana

### 20.1 Top CPU namespaces

```promql
topk(10, sum(rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])) by (namespace))
```

### 20.2 Top memory namespaces

```promql
topk(10, sum(container_memory_working_set_bytes{container!="",pod!=""}) by (namespace))
```

### 20.3 CPU usage vs requests

```promql
sum(rate(container_cpu_usage_seconds_total{namespace="$namespace", container!="", pod!=""}[5m])) by (pod)
/
sum(kube_pod_container_resource_requests{namespace="$namespace", resource="cpu"}) by (pod)
```

### 20.4 Memory usage vs limits

```promql
sum(container_memory_working_set_bytes{namespace="$namespace", container!="", pod!=""}) by (pod)
/
sum(kube_pod_container_resource_limits{namespace="$namespace", resource="memory"}) by (pod)
```

### 20.5 Deployment availability

```promql
kube_deployment_status_replicas_available{namespace="$namespace"}
/
kube_deployment_spec_replicas{namespace="$namespace"}
```

### 20.6 PVC usage percentage

```promql
100 * kubelet_volume_stats_used_bytes{namespace="$namespace"}
/
kubelet_volume_stats_capacity_bytes{namespace="$namespace"}
```

### 20.7 OOMKilled count

```promql
sum(increase(kube_pod_container_status_restarts_total{namespace="$namespace"}[1h])) by (pod, container)
```

Combine with container last terminated reason:

```promql
kube_pod_container_status_last_terminated_reason{namespace="$namespace", reason="OOMKilled"}
```

### 20.8 HTTP 5xx rate

```promql
sum(rate(http_requests_total{namespace="$namespace", status=~"5.."}[5m])) by (app)
```

### 20.9 Error percentage

```promql
100 * sum(rate(http_requests_total{namespace="$namespace", status=~"5.."}[5m])) by (app)
/
sum(rate(http_requests_total{namespace="$namespace"}[5m])) by (app)
```

### 20.10 Latency histogram p99

```promql
histogram_quantile(
  0.99,
  sum(rate(http_request_duration_seconds_bucket{namespace="$namespace"}[5m])) by (le, app)
)
```

## 21. Grafana Dashboard Anti-Patterns

### 21.1 Too many panels

A dashboard with 80 panels is usually not a dashboard. It is a performance problem.

Better:

- Overview dashboard
- Drill-down dashboard
- Application dashboard
- Node dashboard
- Storage dashboard

### 21.2 No operational question

Bad dashboard title:

```text
Kubernetes Metrics
```

Better:

```text
OpenShift Cluster Health Overview
```

Best:

```text
Can the platform accept production traffic right now?
```

### 21.3 Graphs without thresholds

A CPU graph without context is weak.

Better:

- Show CPU usage
- Show CPU requests
- Show CPU limits
- Show saturation percentage
- Show threshold markers

### 21.4 Using rate window too small

Bad:

```promql
rate(http_requests_total[30s])
```

Better:

```promql
rate(http_requests_total[5m])
```

Use shorter windows only for high-volume services and incident views.

### 21.5 Hard-coded namespaces

Bad:

```promql
sum(rate(container_cpu_usage_seconds_total{namespace="prod-a"}[5m]))
```

Better:

```promql
sum(rate(container_cpu_usage_seconds_total{namespace="$namespace"}[5m]))
```

## 22. Grafana and Alerting in OpenShift

### 22.1 OpenShift-native alerting path

```text
PrometheusRule CR
     ↓
Prometheus / Thanos Ruler
     ↓
Alertmanager
     ↓
Email / Slack / PagerDuty / Webhook / Ops tool
```

### 22.2 Grafana alerting path

```text
Grafana alert rule
     ↓
Grafana evaluator
     ↓
Grafana contact point / notification policy
     ↓
Email / Slack / PagerDuty / Webhook
```

### 22.3 Which one to use?

Use OpenShift-native alerting for:

- Node down
- Pod crashloop
- Prometheus target down
- Cluster operator degraded
- API server latency
- etcd issues
- Application metrics scraped by user workload monitoring

Use Grafana alerting for:

- Cross-data-source alerts
- Business dashboards using SQL + metrics
- External service views
- Non-OpenShift dashboards

Advanced recommendation:

> Keep platform alerts in OpenShift-native PrometheusRule resources. Use Grafana alerting only when the alert depends on Grafana-specific multi-source logic or enterprise dashboard workflows.

## 26. Real-World Troubleshooting Scenarios

### Scenario 1: Application dashboard empty after ServiceMonitor creation

Symptoms:

- Grafana dashboard shows “No data”.
- Query `up{namespace="app-demo"}` returns nothing.

Checks:

```bash
oc -n app-demo get svc --show-labels
oc -n app-demo get servicemonitor -o yaml
oc -n app-demo get endpoints demo-app
```

Likely root causes:

- ServiceMonitor selector does not match Service labels.
- Service port name differs from ServiceMonitor endpoint `port` value.
- User workload monitoring is not enabled.
- App does not expose `/metrics`.
- Namespace/team lacks permission to create monitoring resources.

Fix:

- Correct Service labels or ServiceMonitor selector.
- Correct endpoint port name.
- Verify `/metrics` from inside cluster.

### Scenario 2: Grafana can access route but gets 403

Symptoms:

```json
{"status":"error","errorType":"forbidden"}
```

Checks:

```bash
oc auth can-i get namespaces --as=system:serviceaccount:grafana-monitoring:grafana-reader
oc get clusterrolebinding | grep grafana
```

Fix:

```bash
oc adm policy add-cluster-role-to-user cluster-monitoring-view \
  -z grafana-reader \
  -n grafana-monitoring
```

### Scenario 3: Dashboard slow after adding namespace variable

Symptoms:

- Dashboard loads in 30 seconds.
- Thanos Querier CPU increases.
- Browser panel requests time out.

Likely causes:

- Variable query scans too many series.
- Panels use regex matchers with multi-value variables.
- Too many panels refresh every 10 seconds.

Better variable query:

```promql
label_values(kube_namespace_status_phase, namespace)
```

Avoid broad query:

```promql
label_values({__name__=~".*"}, namespace)
```

### Scenario 4: CPU graph shows inflated usage

Cause:

- Query includes infrastructure pause containers or empty container labels.

Better query:

```promql
sum(rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])) by (namespace)
```

### Scenario 5: Memory graph does not match `oc adm top pods`

Possible causes:

- Different metric source or calculation.
- `working_set` vs RSS vs usage bytes.
- Different time range.
- Grafana query aggregation differs from `oc adm top`.

Useful metrics:

```promql
container_memory_working_set_bytes
container_memory_rss
container_memory_usage_bytes
```

For dashboards, `container_memory_working_set_bytes` is often more useful for operational memory pressure views.

## 29. Grafana Interview and Senior Admin Questions

### Q1. Is Grafana a replacement for Prometheus?

No. Grafana visualizes data from Prometheus or other data sources. Prometheus collects, stores, and queries metrics. Grafana queries Prometheus-compatible APIs and displays results.

### Q2. What is the best data source for Grafana in OpenShift?

Usually Thanos Querier, because it provides a unified Prometheus-compatible query endpoint for OpenShift monitoring data. Direct Prometheus access can work but is less ideal in HA or multi-source environments.

### Q3. Why should you avoid using cluster-admin tokens in Grafana?

Because Grafana only needs read access to metrics. A cluster-admin token creates unnecessary risk. Use a dedicated service account with least privilege.

### Q4. Why does a Grafana dashboard show no data while pods are running?

Running pods do not guarantee metrics are scraped. Check `/metrics`, Service labels, ServiceMonitor selectors, endpoint port names, user workload monitoring status, RBAC, and query labels.

### Q5. What is high cardinality and why is it dangerous?

High cardinality means too many unique time series due to labels with many unique values. It increases memory, storage, and query cost in Prometheus/Thanos. Labels like request ID, user ID, transaction ID, and dynamic URL path are dangerous.

### Q6. Should OpenShift platform alerts be created in Grafana?

Usually no. Use PrometheusRule and Alertmanager for OpenShift-native platform alerts. Grafana alerting is useful for custom multi-data-source or external dashboards.

### Q7. What is the difference between dashboard variables and PromQL labels?

Labels are part of metric data. Variables are Grafana placeholders that let users select label values dynamically and reuse dashboards across namespaces, pods, nodes, or clusters.

### Q8. Why should expensive dashboard queries become recording rules?

Recording rules precompute expensive PromQL expressions. This reduces dashboard load time and decreases repeated query pressure on Prometheus/Thanos.

## 31. Senior-Level Operational Advice

1. **Use OpenShift’s supported monitoring stack as the source of truth.**  
   Do not replace it just because Grafana dashboards look nicer.

2. **Treat Grafana as a read path, not a control path.**  
   Grafana should visualize and help diagnose. It should not become the only place where platform health is understood.

3. **Review PromQL like production code.**  
   A badly written query can overload Thanos/Prometheus.

4. **Separate dashboard types.**  
   Incident dashboards, capacity dashboards, executive dashboards, and deep troubleshooting dashboards should not be the same dashboard.

5. **Design dashboards around decisions.**  
   A good panel should help an admin decide what to do next.

6. **Respect multi-tenancy.**  
   OpenShift projects are security boundaries. Grafana dashboard variables can accidentally expose cross-namespace information if credentials are too broad.

7. **Use recording rules for repeated expensive calculations.**  
   This is essential in large clusters.

8. **Do not ignore Grafana itself.**  
   Monitor Grafana CPU, memory, disk, login failures, dashboard load latency, and data source errors.

- Avoid high-cardinality labels.

## 34. Final Mental Model

Think of OpenShift monitoring like this:

```text
Prometheus = metric database and rule engine
Alertmanager = alert routing and notification engine
Thanos Querier = global/aggregated query gateway
OpenShift Observe UI = supported platform dashboard and metrics UI
Grafana = optional powerful custom visualization layer
```

For advanced administration:

```text
Do not ask: “How do I install Grafana?” first.
Ask: “What operational question do I need to answer, which metric source is authoritative, and how do I visualize it without breaking supportability, security, or performance?”
```
