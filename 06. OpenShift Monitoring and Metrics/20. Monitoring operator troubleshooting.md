# Monitoring Operator Troubleshooting in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift Administration / DO380-style operations  
**Experience level:** Senior administrator, SRE, platform engineer, 10+ years Linux/Kubernetes/OpenShift background  
**Primary focus:** Cluster Monitoring Operator (CMO), Prometheus Operator, Prometheus, Alertmanager, Thanos Querier, Metrics Server, user workload monitoring, and real production troubleshooting workflows  
**OpenShift version context:** OpenShift Container Platform 4.x, with references aligned to Red Hat OpenShift 4.19 monitoring documentation

---

## 1. What “Monitoring Operator troubleshooting” means in OpenShift

In OpenShift, monitoring is not normally installed manually like a standalone Prometheus stack. It is delivered as a managed platform capability. The key operator is the **Cluster Monitoring Operator (CMO)**, which is responsible for deploying, managing, and reconciling the monitoring stack.

When we say **Monitoring Operator troubleshooting**, we are usually troubleshooting one or more of these layers:

1. **Cluster Operator status**
   - `clusteroperator/monitoring`
   - Conditions: `Available`, `Progressing`, `Degraded`, `Upgradeable`

2. **Cluster Monitoring Operator pod**
   - Namespace: `openshift-monitoring`
   - Deployment: `cluster-monitoring-operator`

3. **Generated monitoring resources**
   - Prometheus Operator
   - Prometheus StatefulSets
   - Alertmanager StatefulSets
   - Thanos Querier
   - Telemeter Client
   - kube-state-metrics
   - openshift-state-metrics
   - node-exporter
   - Metrics Server
   - monitoring-plugin

4. **User workload monitoring components**
   - Namespace: `openshift-user-workload-monitoring`
   - Prometheus Operator
   - `prometheus-user-workload`
   - `thanos-ruler-user-workload`
   - Optional user workload Alertmanager

5. **Configuration layer**
   - `openshift-monitoring/cluster-monitoring-config`
   - `openshift-user-workload-monitoring/user-workload-monitoring-config`
   - Alertmanager secrets
   - ServiceMonitor, PodMonitor, PrometheusRule, AlertmanagerConfig objects

6. **Data path layer**
   - Scraping targets
   - PromQL query path
   - Thanos Querier API
   - Web console Observe pages
   - Alert evaluation and routing

A senior administrator should not troubleshoot only by restarting pods. The correct method is to identify which reconciliation layer is broken: **CVO → CMO → Prometheus Operator → generated workloads → scrape targets → query/alerting path**.

## 2. Monitoring stack architecture from an operator troubleshooting point of view

### 2.1 Control-plane ownership model

```text
Cluster Version Operator (CVO)
        |
        v
Cluster Monitoring Operator (CMO)
        |
        +--> Prometheus Operator in openshift-monitoring
        |       |
        |       +--> Prometheus k8s StatefulSet
        |       +--> Alertmanager main StatefulSet
        |       +--> ServiceMonitors / PrometheusRules generated for platform components
        |
        +--> Thanos Querier
        +--> Telemeter Client
        +--> kube-state-metrics
        +--> openshift-state-metrics
        +--> node-exporter DaemonSet
        +--> Metrics Server
        +--> monitoring-plugin
        |
        +--> Optional user workload monitoring stack
                |
                +--> openshift-user-workload-monitoring namespace
                +--> Prometheus user workload
                +--> Thanos Ruler user workload
                +--> Optional user workload Alertmanager
```

Important production point:

- The **CVO manages the CMO**.
- The **CMO manages most monitoring stack resources**.
- The **Prometheus Operator manages Prometheus and Alertmanager custom resources**.
- Manual edits to generated monitoring Deployments, StatefulSets, DaemonSets, Services, Secrets, and ConfigMaps are usually overwritten by reconciliation.

### 2.2 Core namespaces

| Namespace | Purpose |
|---|---|
| `openshift-monitoring` | Core platform monitoring stack |
| `openshift-user-workload-monitoring` | User-defined project monitoring stack |
| `openshift-config-managed` | Some generated managed configuration resources |
| `openshift-config` | Global cluster config objects can affect monitoring indirectly |
| `openshift-console` | Console Observe UI depends on monitoring APIs |

### 2.3 Main components and what failure looks like

| Component | Typical resource | Main symptom when broken |
|---|---|---|
| CMO | Deployment | `clusteroperator/monitoring` degraded or progressing |
| Prometheus Operator | Deployment | Prometheus/Alertmanager CRs not reconciled |
| Prometheus k8s | StatefulSet | Metrics missing, alerts not evaluated, PVC full |
| Alertmanager main | StatefulSet | Alerts firing but notifications not delivered |
| Thanos Querier | Deployment/Route | Console metrics queries fail |
| node-exporter | DaemonSet | Node metrics missing |
| kube-state-metrics | Deployment | Kubernetes object state metrics missing |
| openshift-state-metrics | Deployment | OpenShift-specific metrics missing |
| Metrics Server | Deployment / APIService | `oc adm top` or HPA resource metrics fail |
| Telemeter Client | Deployment | Remote health telemetry problems |
| monitoring-plugin | Console plugin | Observe pages broken or unavailable |

## 3. Support boundary: what not to edit manually

A common senior-level mistake is to “quick-fix” a generated resource. It may work for a few minutes, then the operator reverts it.

### 3.1 Do not manually edit these for permanent changes

Avoid direct permanent edits to:

```text
openshift-monitoring deployments
openshift-monitoring statefulsets
openshift-monitoring daemonsets
openshift-monitoring services
openshift-monitoring prometheus CRs
openshift-monitoring alertmanager CRs
openshift-monitoring generated configmaps
openshift-monitoring generated secrets
openshift-user-workload-monitoring generated resources
```

The correct supported configuration path is through:

```text
openshift-monitoring/cluster-monitoring-config
openshift-user-workload-monitoring/user-workload-monitoring-config
supported monitoring API objects in user namespaces
supported Alertmanager secret modification procedure when applicable
```

### 3.2 Unsupported patterns that cause unstable monitoring

Avoid these in production:

```text
Creating custom Prometheus CRs managed by an external Prometheus Operator
Installing another Prometheus Operator for user workload monitoring integration
Creating ServiceMonitor/PodMonitor/PrometheusRule in openshift-* or kube-* namespaces
Deploying user applications into openshift-* or kube-* namespaces
Adding openshift.io/cluster-monitoring=true label to custom namespaces
Manually changing resources generated by CMO
Setting CVO overrides for monitoring operators except for temporary Red Hat-guided debugging
```

### 3.3 Why this matters

CMO reconciliation is not a bug. It is the intended design.

If you patch a generated StatefulSet directly:

```bash
oc -n openshift-monitoring patch statefulset prometheus-k8s --type=merge -p '{...}'
```

CMO or Prometheus Operator may reset it back to the expected state. The right place is usually:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

or:

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

## 4. First 10-minute production triage

When monitoring is degraded, do not start with random pod deletion. Use this order.

### 4.1 Check cluster operator status

```bash
oc get clusteroperators
oc get co monitoring
oc describe co monitoring
oc get co monitoring -o yaml
```

Look for:

```text
Available=False
Progressing=True
Degraded=True
Upgradeable=False
```

Useful JSONPath view:

```bash
oc get co monitoring -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

Interpretation:

| Condition | Meaning |
|---|---|
| `Available=True` | Monitoring operator is generally functional |
| `Available=False` | Required monitoring components are not available |
| `Progressing=True` | CMO is applying or reconciling changes |
| `Degraded=True` | CMO detected a configuration or component failure |
| `Upgradeable=False` | Monitoring issue might block cluster upgrade |

### 4.2 Check monitoring namespace health

```bash
oc -n openshift-monitoring get pods -o wide
oc -n openshift-monitoring get deploy,ds,sts
oc -n openshift-monitoring get events --sort-by=.lastTimestamp
```

For user workload monitoring:

```bash
oc -n openshift-user-workload-monitoring get pods -o wide
oc -n openshift-user-workload-monitoring get deploy,sts
oc -n openshift-user-workload-monitoring get events --sort-by=.lastTimestamp
```

### 4.3 Check the CMO pod and logs

```bash
oc -n openshift-monitoring get deploy cluster-monitoring-operator
oc -n openshift-monitoring get pod -l app.kubernetes.io/name=cluster-monitoring-operator
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --since=1h
```

If the pod restarted:

```bash
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --previous
```

Search common errors:

```bash
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --since=2h | egrep -i 'error|degraded|invalid|failed|reconcile|unsupported|yaml|permission|forbidden|denied'
```

### 4.4 Check configuration ConfigMaps

```bash
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml
oc -n openshift-monitoring extract cm/cluster-monitoring-config --keys=config.yaml --to=-
```

For user workload monitoring:

```bash
oc -n openshift-user-workload-monitoring get cm user-workload-monitoring-config -o yaml
oc -n openshift-user-workload-monitoring extract cm/user-workload-monitoring-config --keys=config.yaml --to=-
```

### 4.5 Snapshot before changing anything

```bash
mkdir -p ~/monitoring-debug-$(date +%F-%H%M)
cd ~/monitoring-debug-$(date +%F-%H%M)

oc get co monitoring -o yaml > co-monitoring.yaml
oc -n openshift-monitoring get all -o wide > openshift-monitoring-all.txt
oc -n openshift-monitoring get events --sort-by=.lastTimestamp > openshift-monitoring-events.txt
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml > cluster-monitoring-config.yaml 2>/dev/null || true
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --since=2h > cmo.log 2>&1 || true
```

For a serious production incident, collect a must-gather before making risky changes:

```bash
oc adm must-gather
```

## 5. Understanding CMO reconciliation

### 5.1 Normal reconciliation behavior

CMO continuously checks whether the monitoring stack matches the desired state. If configuration changes are made through supported ConfigMaps, CMO reconciles the stack. If unsupported changes are made directly to generated objects, CMO usually resets them.

Expected examples:

```text
You edit cluster-monitoring-config
CMO detects config change
CMO updates generated resources
Prometheus/Alertmanager/Thanos pods might restart
clusteroperator/monitoring may show Progressing=True temporarily
```

### 5.2 Abnormal reconciliation behavior

Symptoms:

```text
clusteroperator/monitoring Degraded=True
CMO logs contain repeated reconcile errors
Generated resources not updated
Monitoring pods stuck in old configuration
Prometheus Operator not creating StatefulSets
```

Common causes:

```text
Invalid YAML in config.yaml
Unsupported field in config.yaml
Wrong type for a field
Node selector points to no schedulable nodes
Tolerations missing for tainted nodes
PVC cannot bind
Storage class deleted or unavailable
Image pull failure in disconnected cluster
Resource pressure prevents pods from starting
Webhook or admission issue
RBAC or SCC issue due to unsupported modification
CVO override set to unmanaged
```

## 7. Troubleshooting `clusteroperator/monitoring Degraded=True`

### 7.1 Fast workflow

```bash
oc get co monitoring
oc describe co monitoring
oc get co monitoring -o jsonpath='{range .status.conditions[*]}{.type}{" "}{.status}{" "}{.reason}{" "}{.message}{"\n"}{end}'
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --since=2h
oc -n openshift-monitoring get events --sort-by=.lastTimestamp
```

### 7.2 Most common root causes

| Symptom in condition/log | Likely cause | Fix direction |
|---|---|---|
| `invalid configuration` | Bad `config.yaml` | Fix ConfigMap YAML |
| `unsupported field` | Field not supported by current version | Remove unsupported field |
| `cannot unmarshal` | Wrong value type | Correct boolean/string/map/list type |
| `no nodes available` | Bad nodeSelector/tolerations | Fix scheduling config |
| `persistentvolumeclaim pending` | Storage class/PV issue | Fix PVC/storage |
| `forbidden` | RBAC was changed manually | Restore supported RBAC/resources |
| `context deadline exceeded` | API or dependent component slow/unreachable | Check API, network, resource pressure |
| `admission webhook` | Prometheus Operator webhook problem | Check webhook pod/certs/APIService |

### 7.3 Example: invalid YAML in cluster-monitoring-config

Bad example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      retention: 15d
       resources:
        requests:
          cpu: 500m
```

The indentation before `resources` is wrong. CMO can stop reconciling and mark monitoring degraded.

Check:

```bash
oc -n openshift-monitoring extract cm/cluster-monitoring-config --keys=config.yaml --to=-
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --since=30m | egrep -i 'yaml|unmarshal|invalid|degraded'
```

Fix:

```bash
oc -n openshift-monitoring edit cm cluster-monitoring-config
```

Correct example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      retention: 15d
      resources:
        requests:
          cpu: 500m
          memory: 2Gi
```

Verify:

```bash
oc get co monitoring
oc -n openshift-monitoring get pods
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --since=10m
```

## 8. Troubleshooting CMO pod issues

### 8.1 CMO pod not running

Check:

```bash
oc -n openshift-monitoring get deploy cluster-monitoring-operator -o wide
oc -n openshift-monitoring get rs -l app.kubernetes.io/name=cluster-monitoring-operator
oc -n openshift-monitoring get pods -l app.kubernetes.io/name=cluster-monitoring-operator -o wide
oc -n openshift-monitoring describe pod -l app.kubernetes.io/name=cluster-monitoring-operator
```

Common causes:

```text
ImagePullBackOff
CrashLoopBackOff
Node resource pressure
PodSecurity/SCC/RBAC modification
CVO override or payload issue
Admission webhook issue
```

### 8.2 ImagePullBackOff in disconnected environment

Check:

```bash
oc -n openshift-monitoring describe pod <cmo-pod>
oc get imagecontentsourcepolicy
oc get imagecontentsourcepolicy -o yaml
oc get mcp
oc get nodes
```

Look for:

```text
Failed to pull image
x509 certificate signed by unknown authority
manifest unknown
unauthorized
connection refused
```

Fix direction:

- Verify cluster-wide pull secret.
- Verify mirror registry configuration.
- Verify trusted CA bundle.
- Verify MachineConfigPool rolled out after image policy change.
- Avoid manually changing image fields on generated resources.

### 8.3 CMO CrashLoopBackOff

Check:

```bash
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --previous
oc -n openshift-monitoring describe pod -l app.kubernetes.io/name=cluster-monitoring-operator
oc -n openshift-monitoring get events --sort-by=.lastTimestamp
```

Look for:

```text
panic
OOMKilled
permission denied
failed to load configuration
failed to create client
```

Fix direction:

| Cause | Action |
|---|---|
| Bad config | Revert/fix `cluster-monitoring-config` |
| OOMKilled | Check node pressure and operator resource state |
| RBAC broken | Compare generated RBAC with healthy cluster / restore from release payload with Red Hat guidance |
| CVO override | Remove unsupported override |

## 9. Troubleshooting Prometheus Operator issues

CMO deploys Prometheus Operator, and Prometheus Operator manages Prometheus and Alertmanager custom resources.

### 9.1 Check Prometheus Operator

```bash
oc -n openshift-monitoring get deploy prometheus-operator
oc -n openshift-monitoring get pods -l app.kubernetes.io/name=prometheus-operator
oc -n openshift-monitoring logs deployment/prometheus-operator --since=1h
```

For user workload monitoring:

```bash
oc -n openshift-user-workload-monitoring get deploy prometheus-operator
oc -n openshift-user-workload-monitoring logs deployment/prometheus-operator --since=1h
```

### 9.2 Symptoms

```text
Prometheus StatefulSet not created
Alertmanager StatefulSet not created
ServiceMonitor exists but target not discovered
PrometheusRule rejected
Admission webhook errors
Prometheus config reload failing
```

### 9.3 Check Prometheus custom resources

```bash
oc -n openshift-monitoring get prometheus -o yaml
oc -n openshift-monitoring describe prometheus k8s
oc -n openshift-monitoring get alertmanager -o yaml
oc -n openshift-monitoring describe alertmanager main
```

For user workload:

```bash
oc -n openshift-user-workload-monitoring get prometheus -o yaml
oc -n openshift-user-workload-monitoring describe prometheus user-workload
oc -n openshift-user-workload-monitoring get thanosruler -o yaml
```

### 9.4 Admission webhook issue

Prometheus Operator has admission webhooks for validating some monitoring resources. If the webhook is unavailable or certificates are wrong, creation or update of monitoring CRs might fail.

Check:

```bash
oc get validatingwebhookconfiguration | grep -i prometheus
oc get mutatingwebhookconfiguration | grep -i prometheus
oc -n openshift-monitoring get pods | grep prometheus-operator
oc -n openshift-monitoring get svc | grep prometheus-operator
oc -n openshift-monitoring logs deployment/prometheus-operator --since=1h | egrep -i 'webhook|admission|certificate|tls|x509'
```

Symptoms:

```text
failed calling webhook
service not found
x509: certificate signed by unknown authority
context deadline exceeded
```

Fix direction:

- Ensure Prometheus Operator pod and service are running.
- Check CMO logs for webhook reconciliation failures.
- Do not manually edit webhook CA bundles unless directed by Red Hat.
- If only the pod is unhealthy, fix the pod root cause first.

## 10. Troubleshooting Prometheus pods

### 10.1 Check Prometheus StatefulSet

```bash
oc -n openshift-monitoring get sts prometheus-k8s
oc -n openshift-monitoring get pods -l app.kubernetes.io/name=prometheus -o wide
oc -n openshift-monitoring describe sts prometheus-k8s
```

Check containers:

```bash
oc -n openshift-monitoring get pod prometheus-k8s-0 -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{end}'
```

Typical containers include:

```text
prometheus
config-reloader
thanos-sidecar
kube-rbac-proxy
```

### 10.2 Prometheus pod Pending

Check:

```bash
oc -n openshift-monitoring describe pod prometheus-k8s-0
oc -n openshift-monitoring get pvc
oc get nodes
oc describe node <node>
```

Common reasons:

```text
PVC Pending
Insufficient CPU
Insufficient memory
Node selector mismatch
Taints not tolerated
Pod anti-affinity/topology constraints cannot be satisfied
```

Fix direction:

| Cause | Fix |
|---|---|
| PVC pending | Fix StorageClass/PV/provisioner |
| No matching nodeSelector | Correct `prometheusK8s.nodeSelector` |
| Tainted nodes | Add supported tolerations or change placement |
| Insufficient resources | Increase nodes or adjust supported resource requests |
| Topology spread unsatisfied | Adjust topology settings or cluster capacity |

### 10.3 Prometheus pod CrashLoopBackOff

Check:

```bash
oc -n openshift-monitoring describe pod prometheus-k8s-0
oc -n openshift-monitoring logs prometheus-k8s-0 -c prometheus --since=1h
oc -n openshift-monitoring logs prometheus-k8s-0 -c prometheus --previous
oc -n openshift-monitoring logs prometheus-k8s-0 -c config-reloader --since=1h
oc -n openshift-monitoring logs prometheus-k8s-0 -c thanos-sidecar --since=1h
```

Common log patterns:

```text
opening storage failed
WAL corruption
no space left on device
permission denied
error loading config
rule manager failed
out of memory
```

### 10.4 Prometheus PVC full

Check PVC:

```bash
oc -n openshift-monitoring get pvc
oc -n openshift-monitoring describe pvc prometheus-k8s-db-prometheus-k8s-0
```

Check Prometheus disk metrics:

```promql
kubelet_volume_stats_used_bytes{namespace="openshift-monitoring"}
kubelet_volume_stats_capacity_bytes{namespace="openshift-monitoring"}
```

Check series count:

```promql
prometheus_tsdb_head_series
prometheus_tsdb_symbol_table_size_bytes
prometheus_tsdb_storage_blocks_bytes
scrape_samples_post_metric_relabeling
scrape_samples_scraped
```

Emergency actions:

1. Identify high-cardinality source.
2. Reduce scrape volume or relabel labels where supported.
3. Increase PVC size if storage supports expansion.
4. Reduce retention time or retention size.
5. Avoid deleting Prometheus PVC unless data loss is acceptable and approved.

Example supported configuration for retention:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      retention: 15d
      retentionSize: 80GB
```

Verify after change:

```bash
oc get co monitoring
oc -n openshift-monitoring rollout status sts/prometheus-k8s
```

### 10.5 Prometheus high memory or OOMKilled

Check:

```bash
oc -n openshift-monitoring describe pod prometheus-k8s-0 | egrep -i 'oom|killed|reason|exit'
oc adm top pod -n openshift-monitoring
```

Useful PromQL:

```promql
process_resident_memory_bytes{namespace="openshift-monitoring",pod=~"prometheus-k8s.*"}
prometheus_tsdb_head_series
prometheus_tsdb_head_chunks
scrape_samples_post_metric_relabeling
```

Root causes:

```text
High-cardinality metrics
Too many targets
Too many samples per scrape
Large rules
Expensive queries
Remote write backlog
Node exporter collectors enabled without capacity planning
```

Mitigation:

- Fix metric cardinality at application/source.
- Apply supported sample limits for user workload monitoring.
- Increase Prometheus resources through supported config.
- Review ServiceMonitor/PodMonitor intervals.
- Avoid unbounded labels like `user_id`, `session_id`, `request_id`, `pod_uid`, `container_id` in application metrics.

## 11. Troubleshooting user workload monitoring

User workload monitoring allows teams to scrape metrics from their own namespaces using ServiceMonitor, PodMonitor, and PrometheusRule objects.

### 11.1 Verify user workload monitoring is enabled

```bash
oc -n openshift-monitoring extract cm/cluster-monitoring-config --keys=config.yaml --to=-
```

Expected:

```yaml
enableUserWorkload: true
```

If missing, enable it:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Apply:

```bash
oc apply -f cluster-monitoring-config.yaml
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get pods
oc -n openshift-user-workload-monitoring get prometheus
oc -n openshift-user-workload-monitoring get thanosruler
```

### 11.2 ServiceMonitor exists but metrics are missing

Workflow:

```bash
oc -n <app-namespace> get servicemonitor
oc -n <app-namespace> describe servicemonitor <name>
oc -n <app-namespace> get svc --show-labels
oc -n <app-namespace> get endpoints <service-name>
oc -n <app-namespace> get pod --show-labels
```

Check these items carefully:

| Check | Command | Expected |
|---|---|---|
| Service labels | `oc get svc --show-labels` | Match ServiceMonitor selector |
| Service port name | `oc get svc -o yaml` | Match `endpoints[].port` |
| Endpoint exists | `oc get endpoints` | Has pod IP and port |
| Pod readiness | `oc get pod` | Pod Ready |
| Metrics path | `curl` from debug pod | Returns Prometheus text format |
| RBAC | RoleBinding | User has monitoring role if needed |

Example ServiceMonitor:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: demo-app
  namespace: demo
spec:
  selector:
    matchLabels:
      app: demo-app
  endpoints:
    - port: metrics
      path: /metrics
      interval: 30s
```

Matching Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: demo-app
  namespace: demo
  labels:
    app: demo-app
spec:
  selector:
    app: demo-app
  ports:
    - name: metrics
      port: 8080
      targetPort: 8080
```

Common mistake:

```yaml
endpoints:
  - port: 8080
```

`port` in ServiceMonitor is the **service port name**, not the numeric container port. It should be:

```yaml
endpoints:
  - port: metrics
```

## 16. Troubleshooting high-cardinality metrics

High-cardinality metrics are one of the most common production causes of Prometheus performance problems.

### 16.1 What cardinality means

Each unique combination of metric name and labels creates a time series.

Bad example:

```text
http_request_duration_seconds{user_id="100001",session_id="abc",path="/api/order/98439843"}
```

Better example:

```text
http_request_duration_seconds{handler="/api/order/:id",method="GET",status="200"}
```

Avoid labels such as:

```text
user_id
customer_id
session_id
request_id
trace_id
pod_uid
container_id
email
ip_address
full_url
error_message
```

### 16.2 Detect high cardinality

PromQL:

```promql
topk(20, count by (__name__)({__name__=~".+"}))
topk(20, count by (job)({__name__=~".+"}))
topk(20, scrape_samples_post_metric_relabeling)
prometheus_tsdb_head_series
```

Series by namespace:

```promql
topk(20, count by (namespace)({__name__=~".+"}))
```

Series by job:

```promql
topk(20, count by (job)({__name__=~".+"}))
```

### 16.3 Operational fixes

| Fix | Where |
|---|---|
| Remove bad labels | Application instrumentation |
| Rename dynamic paths | Application metrics library |
| Reduce scrape frequency | ServiceMonitor/PodMonitor |
| Set sample limits | User workload monitoring config |
| Disable unnecessary collectors | Supported CMO config |
| Increase Prometheus resources | Supported CMO config |
| Increase PVC size | Supported CMO config/storage |

Example user workload sample control:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      enforcedSampleLimit: 50000
      scrapeInterval: 30s
      evaluationInterval: 30s
```

Always validate supported field names against your exact OpenShift version before applying.

        |-- Check kubelet/node connectivity

## 29. Common mistakes and senior-level corrections

| Mistake | Why it is wrong | Correct action |
|---|---|---|
| Editing `prometheus-k8s` StatefulSet directly | Operator overwrites it | Use `cluster-monitoring-config` |
| Installing custom Prometheus Operator | Unsupported conflict with platform monitoring | Use built-in user workload monitoring |
| Creating ServiceMonitor in `openshift-*` | Reserved namespaces | Create in user namespace |
| Using numeric port in ServiceMonitor | ServiceMonitor expects service port name | Use named service port |
| Ignoring PVC growth | Prometheus eventually fails | Track cardinality and retention |
| Deleting Prometheus PVC quickly | Causes metrics data loss | Resize/reduce retention first |
| Treating pod restart during cert rotation as outage | Rotation can restart pods normally | Confirm recovery before action |
| Leaving CVO override unmanaged | Can block upgrade and reconciliation | Remove override after debugging |
| Only checking Prometheus when Observe UI fails | UI query path uses Thanos/console/plugin/RBAC too | Test Thanos API directly |
| Giving cluster-admin to developers for monitoring | Over-permission | Use monitoring roles per namespace |

## 31. Safe remediation principles

### 31.1 Always preserve evidence first

Before major changes:

```bash
oc adm must-gather
oc get co monitoring -o yaml > co-monitoring.yaml
oc -n openshift-monitoring get all -o yaml > openshift-monitoring-all.yaml
oc -n openshift-monitoring get events --sort-by=.lastTimestamp > events.txt
oc -n openshift-monitoring logs deployment/cluster-monitoring-operator --since=2h > cmo.log
```

### 31.2 Prefer configuration correction over pod deletion

Use pod deletion only after fixing root cause or to accelerate restart of a stuck component.

Example safe restart after config/cert issue:

```bash
oc -n openshift-monitoring delete pod prometheus-k8s-0
```

But do not use this as the first solution if the pod is failing due to storage, invalid configuration, or scheduling.

### 31.3 Do not fight reconciliation

If an operator keeps reverting your change, your change is probably being made at the wrong layer.

Ask:

```text
Is this resource generated by CMO?
Is this field supported in cluster-monitoring-config?
Is this user workload config instead of platform config?
Is this a CVO-managed operator?
```

## 35. Interview and exam-style key points

For Advanced OpenShift Administration, remember these points:

1. **CMO is the central operator for OpenShift monitoring.**
2. **CVO deploys and manages the CMO lifecycle.**
3. **Supported monitoring configuration is done through ConfigMaps, not direct workload edits.**
4. **`cluster-monitoring-config` controls core platform monitoring.**
5. **`user-workload-monitoring-config` controls user workload monitoring components.**
6. **Invalid `config.yaml` can make monitoring degraded.**
7. **Prometheus storage issues are often caused by high cardinality.**
8. **ServiceMonitor uses service port name, not numeric target port.**
9. **Thanos Querier is the central query layer for console metrics.**
10. **Metrics Server backs `metrics.k8s.io`, `oc adm top`, and resource metrics usage.**
11. **Alert firing and alert notification are different troubleshooting paths.**
12. **Manual edits to generated resources are reverted by reconciliation.**
13. **CVO unmanaged overrides can block upgrades and should not remain in production.**
14. **Must-gather should be collected before destructive remediation.**

## 37. Final production mindset

Monitoring is a dependency for troubleshooting everything else. When monitoring itself fails, treat it like a platform outage:

```text
Stabilize the operator.
Recover the query path.
Recover alerting.
Recover long-term storage.
Prevent recurrence through supported configuration and cardinality control.
```

The best OpenShift administrators do not fight operators. They understand the reconciliation chain and fix the desired state at the correct layer.
