# Controller Manager Metrics in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift administrators, SREs, platform engineers, and Red Hat OpenShift exam/practice learners  
**Level:** Deep-dive / 10+ years operations style  
**Scope:** OpenShift Container Platform 4.x, Kubernetes controller manager, OpenShift controller manager, Prometheus/Thanos metrics, alerting, troubleshooting, and Day-2 operations  
**File purpose:** A single Markdown reference you can use as a study note, production runbook, and dashboard/alert design guide.

---

## 1. Executive Summary

In OpenShift, **Controller Manager metrics** show how well the cluster control loops are reconciling the desired state of the cluster into actual state.

A controller manager is not one controller. It is a process that runs many controllers. Each controller watches Kubernetes or OpenShift API objects, places work into queues, processes that work, and writes changes back through the API server. When controller manager metrics are unhealthy, the cluster might still look "up", but reconciliation becomes slow or broken. That means Deployments might not scale correctly, Jobs might not create Pods on time, Services might not update EndpointSlices, Nodes might not be marked unhealthy correctly, PVC/PV state might lag, and garbage collection might not clean deleted resources.

For an experienced administrator, controller manager metrics answer questions like:

- Is the active controller manager leader healthy?
- Are controllers keeping up with cluster object churn?
- Are controller workqueues backing up?
- Are controllers stuck processing a resource?
- Is the controller manager throttled by the API server?
- Are HPA, Job, CronJob, Node, PV/PVC, EndpointSlice, or garbage collector controllers delayed?
- Is a symptom caused by the controller manager, kube-apiserver, etcd, the scheduler, kubelet, or an application misconfiguration?
- Is reconciliation slow cluster-wide or isolated to one controller?

In production, controller manager metrics are important because Kubernetes is an eventually consistent system. The API object might be accepted immediately, but the controller still needs to reconcile it. Metrics tell you whether that reconciliation machinery is healthy.

## 2. What "Controller Manager" Means in OpenShift

OpenShift has more than one controller-manager-style component. When someone says **Controller Manager metrics**, clarify which component they mean.

### 2.1 Kubernetes Controller Manager

The **Kubernetes Controller Manager**, usually called `kube-controller-manager`, runs core Kubernetes controllers. Examples include:

| Controller area | What it does |
|---|---|
| Node controller | Watches Node health and reacts to unreachable/unready Nodes. |
| Replication / ReplicaSet related control loops | Helps maintain desired replica state through workload controllers. |
| Job controller | Creates and tracks Pods for Jobs. |
| CronJob controller | Creates Jobs at scheduled times. |
| EndpointSlice controller | Maintains EndpointSlices for Services. |
| HPA controller | Reconciles HorizontalPodAutoscaler objects. |
| PV/PVC binder/protection related controllers | Tracks and reconciles persistent volume lifecycle. |
| Namespace controller | Finalizes namespace deletion. |
| Garbage collector | Cleans dependent objects based on owner references. |
| ServiceAccount token/root CA publisher controllers | Maintains service account and namespace trust data. |

In OpenShift, the Kubernetes Controller Manager is managed by the **Kubernetes Controller Manager Operator** and is part of the managed control plane.

Common namespaces:

```bash
oc get pods -n openshift-kube-controller-manager
oc get pods -n openshift-kube-controller-manager-operator
```

Useful cluster operators:

```bash
oc get co kube-controller-manager
oc describe co kube-controller-manager
```

### 2.2 OpenShift Controller Manager

The **OpenShift Controller Manager** handles OpenShift-specific control loops. It watches OpenShift objects such as Projects, Routes, and Templates and uses the API to enforce desired state.

Common namespaces:

```bash
oc get pods -n openshift-controller-manager
oc get pods -n openshift-controller-manager-operator
```

Useful cluster operators:

```bash
oc get co openshift-controller-manager
oc describe co openshift-controller-manager
```

### 2.3 Cloud Controller Manager

On cloud or external-platform installations, the **Cloud Controller Manager** can manage cloud-provider-specific loops such as load balancer, route, and node cloud integration. Not every cluster exposes the same metrics because platform type and installed capabilities vary.

Useful discovery:

```bash
oc get co | grep -i controller
oc get pods -A | grep -i cloud-controller
oc get servicemonitor -A | grep -i controller
```

### 2.4 Operator Metrics vs Operand Metrics

Do not confuse these two:

| Metric source | Meaning |
|---|---|
| Controller manager operand metrics | Metrics from the actual `kube-controller-manager` or OpenShift controller manager process. These show control-loop health. |
| Controller manager operator metrics | Metrics from the Operator that manages the controller manager static pods/configuration/revisions. These show management health, not every controller reconciliation detail. |

Example:

```bash
oc get pods -n openshift-kube-controller-manager
oc get pods -n openshift-kube-controller-manager-operator
```

The first namespace is closer to the running control-plane component. The second is the Operator managing it.

## 3. Where Controller Manager Metrics Fit in OpenShift Monitoring

OpenShift includes a preconfigured platform monitoring stack in the `openshift-monitoring` namespace. It uses Prometheus, Alertmanager, Thanos Querier, Prometheus Operator, Cluster Monitoring Operator, kube-state-metrics, openshift-state-metrics, node-exporter, and related components.

Controller manager metrics are part of **core platform monitoring**. They are scraped by the platform Prometheus stack and queried through the OpenShift web console Observe section or Thanos Querier.

High-level flow:

```text
kube-controller-manager / openshift-controller-manager
        |
        | exposes /metrics
        v
Service + ServiceMonitor / PodMonitor managed by OpenShift components
        |
        v
Prometheus in openshift-monitoring
        |
        v
Rules / alerts / recording rules
        |
        +--> Alertmanager
        |
        +--> Thanos Querier / OpenShift Console Observe Metrics
```

Key discovery commands:

```bash
# Platform monitoring pods
oc get pods -n openshift-monitoring

# Controller manager namespaces
oc get pods -n openshift-kube-controller-manager
oc get pods -n openshift-controller-manager

# Metrics targets
oc get servicemonitor -A | grep -i controller
oc get podmonitor -A | grep -i controller

# Platform Prometheus rules
oc get prometheusrule -A | grep -i controller
oc get prometheusrule -A | grep -i kube
```

From the web console:

```text
Observe -> Metrics
Observe -> Targets
Observe -> Alerting
Observe -> Dashboards
```

## 4. Why Controller Manager Metrics Matter

Kubernetes works through reconciliation. A user or automation writes desired state into the API. Controllers watch that state and move actual state toward it.

Example:

```text
User creates Deployment replicas=5
        |
        v
kube-apiserver stores object
        |
        v
Deployment/ReplicaSet controllers observe desired state
        |
        v
Pods are created
        |
        v
Scheduler assigns Pods to Nodes
        |
        v
Kubelet starts containers
```

If a controller manager is unhealthy:

- API calls might still succeed.
- `oc get deployment` might show the desired spec.
- But actual Pods, Jobs, EndpointSlices, PVC state, or HPA changes might lag.
- Users report "OpenShift is slow" even when the API is reachable.

Controller manager metrics help separate:

| Symptom | Possible metric area |
|---|---|
| Deployment does not create expected Pods | Workqueue backlog, API errors, controller leader issue |
| CronJob starts late | `cronjob_controller_job_creation_skew_duration_seconds` |
| HPA not scaling | HPA controller reconciliation/metric computation metrics |
| Service endpoints stale | EndpointSlice controller metrics |
| PVCs stuck | PV/PVC collector metrics plus storage operator/CSI metrics |
| Nodes marked NotReady late or evictions delayed | Node controller metrics |
| Namespace stuck terminating | Garbage collector / namespace controller backlog |
| Cluster upgrades stuck | Control-plane operator conditions plus controller manager availability |

## 5. Controller Manager HA and Leader Election

In an HA OpenShift cluster, controller manager pods run on control-plane nodes. Usually only one instance actively leads a given controller lease at a time, while others are hot standbys.

Important idea:

```text
Multiple replicas exist for HA.
Only the elected leader actively processes many controllers.
Metrics can be exposed by all replicas.
For controller behavior, identify the active leader.
```

Useful metric:

```promql
leader_election_master_status
```

Meaning:

- `1` means the reporting instance is the leader/master for the named lease.
- `0` means it is a standby.
- Group by `name` to avoid confusing multiple leader leases.

PromQL examples:

```promql
sum by (name) (
  leader_election_master_status{job=~".*controller-manager.*"}
)
```

Expected result:

```text
For each leader election name, usually exactly 1 active leader.
```

Find active instance:

```promql
leader_election_master_status{job=~".*kube-controller-manager.*"} == 1
```

Potential problems:

| Observation | Meaning |
|---|---|
| No leader | Controller loops might not run. Severe issue. |
| More than one leader for same lease | Split-brain risk or metrics label mismatch; investigate immediately. |
| Frequent leader changes | Possible API server latency, etcd latency, control-plane node instability, resource pressure, network issue, certificate issue. |
| Leader exists but queues grow | Leader is alive but not keeping up. |

Leader election should be correlated with:

```promql
rate(leader_election_slowpath_total{job=~".*controller-manager.*"}[5m])
```

A rising slowpath rate can indicate lease renewal delay, API server latency, etcd delay, or control-plane resource pressure.

## 6. Important Metric Categories

Controller manager metrics fall into several operational categories.

### 6.1 Target/Scrape Health Metrics

These are Prometheus-level metrics that tell you whether Prometheus can scrape the target.

| Metric | What it tells you |
|---|---|
| `up` | Whether the target was scraped successfully. |
| `scrape_duration_seconds` | How long the scrape took. |
| `scrape_samples_scraped` | Number of samples scraped. |
| `scrape_samples_post_metric_relabeling` | Number of samples kept after relabeling. |
| `scrape_series_added` | New series added; useful for cardinality spikes. |

PromQL:

```promql
up{job=~".*controller-manager.*"}
```

Controller manager targets down:

```promql
up{job=~".*controller-manager.*"} == 0
```

Scrape latency:

```promql
max by (job, instance) (
  scrape_duration_seconds{job=~".*controller-manager.*"}
)
```

Operational meaning:

- If `up=0`, do not immediately assume the controller manager is down. It might be a metrics TLS/RBAC/service endpoint issue.
- Correlate with pod health and cluster operator conditions.

Commands:

```bash
oc get co kube-controller-manager openshift-controller-manager
oc get pods -n openshift-kube-controller-manager -o wide
oc get pods -n openshift-controller-manager -o wide
oc get svc,endpoints,endpointslice -A | grep -i controller
oc get servicemonitor -A | grep -i controller
```

### 6.2 Process and Runtime Metrics

Controller managers are Go processes. Runtime metrics help detect resource pressure, memory leaks, CPU saturation, and goroutine growth.

Common process/runtime metrics:

| Metric | Use |
|---|---|
| `process_cpu_seconds_total` | CPU consumed by the process. Use `rate()` for CPU cores. |
| `process_resident_memory_bytes` | Resident memory. |
| `go_goroutines` | Number of goroutines. Growth can indicate stuck watches, leaks, or high concurrency. |
| `go_memstats_alloc_bytes` | Go heap allocation. |
| `go_memstats_heap_inuse_bytes` | Heap in use. |
| `go_gc_duration_seconds` | Go GC duration summary/histogram depending on version. |
| `process_open_fds` | Open file descriptors. |
| `process_max_fds` | FD limit. |

PromQL:

```promql
rate(process_cpu_seconds_total{job=~".*controller-manager.*"}[5m])
```

```promql
process_resident_memory_bytes{job=~".*controller-manager.*"}
```

```promql
go_goroutines{job=~".*controller-manager.*"}
```

Memory trend:

```promql
max_over_time(process_resident_memory_bytes{job=~".*controller-manager.*"}[6h])
```

FD usage percentage:

```promql
100 *
process_open_fds{job=~".*controller-manager.*"}
/
process_max_fds{job=~".*controller-manager.*"}
```

Interpretation:

| Pattern | Possible cause |
|---|---|
| CPU high + queues growing | Controller cannot process workload fast enough or API calls are slow. |
| Memory steadily increasing | Possible leak, high object count, high watch cache/informer pressure. |
| Goroutines steadily increasing | Stuck clients, watches, or long-running handlers. |
| Open FDs near max | Connection leak or abnormal client behavior. |

### 6.3 Workqueue Metrics

Workqueue metrics are among the most important controller manager metrics.

A Kubernetes controller usually works like this:

```text
Watch event from API
        |
        v
Add key to workqueue
        |
        v
Worker pops item from queue
        |
        v
Reconcile object
        |
        v
Success -> done
Failure -> retry with rate limiting
```

Key metrics:

| Metric | Type | Meaning |
|---|---:|---|
| `workqueue_depth` | Gauge | Current number of items waiting in a queue. |
| `workqueue_adds_total` | Counter | Total items added to queue. |
| `workqueue_queue_duration_seconds` | Histogram | How long items wait before processing. |
| `workqueue_work_duration_seconds` | Histogram | How long item processing takes. |
| `workqueue_retries_total` | Counter | Retry count. |
| `workqueue_unfinished_work_seconds` | Gauge | In-progress work not yet observed as completed. Large/rising values can indicate stuck workers. |
| `workqueue_longest_running_processor_seconds` | Gauge | Longest currently running queue processor. |

#### 6.3.1 Top Backlogged Controller Queues

```promql
topk(10,
  max by (name) (
    workqueue_depth{job=~".*controller-manager.*"}
  )
)
```

Interpretation:

| Result | Meaning |
|---|---|
| Depth near 0 | Controller is keeping up. |
| Spiky depth but returns to 0 | Normal during bursts. |
| Sustained high depth | Controller lag. Investigate API latency, object churn, errors, or specific controller issues. |
| One queue high | Specific controller or resource type issue. |
| Many queues high | API server/etcd/control-plane-wide pressure likely. |

#### 6.3.2 Queue Waiting Latency p99

```promql
histogram_quantile(
  0.99,
  sum by (le, name) (
    rate(workqueue_queue_duration_seconds_bucket{job=~".*controller-manager.*"}[5m])
  )
)
```

Interpretation:

- High queue wait means items sit in the queue before workers pick them up.
- If queue wait is high but work duration is low, workers might be insufficient or event rate is high.
- If queue wait and work duration are both high, processing itself is slow.

#### 6.3.3 Work Processing Latency p99

```promql
histogram_quantile(
  0.99,
  sum by (le, name) (
    rate(workqueue_work_duration_seconds_bucket{job=~".*controller-manager.*"}[5m])
  )
)
```

Interpretation:

| Pattern | Likely cause |
|---|---|
| Work duration high for one controller | Reconcile operation is slow for that controller. |
| Work duration high for many controllers | API server, etcd, network, or global control-plane pressure. |
| Work duration high + API client errors | API calls are slow/failing. |
| Work duration high + no API issue | Controller-specific logic or object scale issue. |

#### 6.3.4 Workqueue Retries

```promql
topk(10,
  sum by (name) (
    rate(workqueue_retries_total{job=~".*controller-manager.*"}[5m])
  )
)
```

Interpretation:

- Retries mean reconcile attempts failed and were requeued.
- Small retry bursts can be normal during object churn.
- Persistent retries mean the controller cannot complete desired-state changes.

#### 6.3.5 Stuck Work

```promql
max by (name) (
  workqueue_unfinished_work_seconds{job=~".*controller-manager.*"}
)
```

```promql
max by (name) (
  workqueue_longest_running_processor_seconds{job=~".*controller-manager.*"}
)
```

Interpretation:

- `unfinished_work_seconds` rising continuously is dangerous.
- `longest_running_processor_seconds` growing for a specific queue can indicate a stuck reconcile worker.

Practical alert expression:

```promql
max by (name) (
  workqueue_longest_running_processor_seconds{job=~".*controller-manager.*"}
) > 300
```

Use as warning first. Tune based on your environment.

### 6.4 API Client Metrics

The controller manager is a heavy API client. It watches, lists, creates, updates, patches, and deletes objects via `kube-apiserver`.

Important metrics:

| Metric | Meaning |
|---|---|
| `rest_client_requests_total` | Number of HTTP requests by code, method, and host. |
| `rest_client_request_duration_seconds` | Request latency by host and verb. |
| `rest_client_request_retries_total` | Number of client request retries. |
| `rest_client_rate_limiter_duration_seconds` | Client-side throttling/wait time. |
| `rest_client_request_size_bytes` | Request size. |
| `rest_client_response_size_bytes` | Response size. |
| `rest_client_dns_resolution_duration_seconds` | DNS lookup latency. |

#### 6.4.1 API Error Rate from Controller Manager

```promql
sum by (job, code, method) (
  rate(rest_client_requests_total{
    job=~".*controller-manager.*",
    code=~"5..|429"
  }[5m])
)
```

Interpretation:

| Code | Meaning |
|---|---|
| `429` | API Priority and Fairness or client throttling pressure. |
| `500/503/504` | API server/backend problem, overload, or transient failure. |
| `403` | RBAC/authorization issue, unusual for built-in control-plane controllers. |
| `404/409` | Can occur in normal races, but high rates can indicate churn or conflict storms. |

#### 6.4.2 API Request Latency p99

```promql
histogram_quantile(
  0.99,
  sum by (le, host, verb) (
    rate(rest_client_request_duration_seconds_bucket{
      job=~".*controller-manager.*"
    }[5m])
  )
)
```

Interpretation:

- High GET/LIST/WATCH latency can delay informer updates.
- High PATCH/UPDATE latency can delay reconciliation.
- High latency plus queue backlog usually points to API server/etcd pressure or API Priority and Fairness throttling.

#### 6.4.3 Client Rate Limiter Delay

```promql
histogram_quantile(
  0.99,
  sum by (le, host, verb) (
    rate(rest_client_rate_limiter_duration_seconds_bucket{
      job=~".*controller-manager.*"
    }[5m])
  )
)
```

Interpretation:

- If controller manager client-side limiter delay is high, controllers are waiting before sending API calls.
- This can happen during high churn, object storms, upgrades, or API pressure.

#### 6.4.4 Request Retries

```promql
sum by (code, host, verb) (
  rate(rest_client_request_retries_total{job=~".*controller-manager.*"}[5m])
)
```

Interpretation:

- Retries are not automatically bad.
- Persistent retry rate with queue growth means reconciliation is degraded.

### 6.5 Informer Metrics

Controllers use informers to watch and cache API objects. Informer lag or queueing means controllers might be acting on stale data or not receiving changes quickly.

Common informer metrics can include:

| Metric | Meaning |
|---|---|
| `informer_processing_latency_seconds` | Time to process events after popping from informer queue. |
| `informer_queued_items` | Current number of informer queue items. |

PromQL:

```promql
topk(10,
  max by (group, resource, name) (
    informer_queued_items{job=~".*controller-manager.*"}
  )
)
```

```promql
histogram_quantile(
  0.99,
  sum by (le, group, resource, name) (
    rate(informer_processing_latency_seconds_bucket{
      job=~".*controller-manager.*"
    }[5m])
  )
)
```

Interpretation:

| Pattern | Meaning |
|---|---|
| Informer queue high for one resource | A specific object type has event pressure or slow processing. |
| Informer latency high across many resources | API watch/cache/control-plane-wide issue. |
| Informer queue high + workqueue high | Event ingestion and reconciliation are both lagging. |

### 7.1 HPA Controller Metrics

HPA-related metrics help debug autoscaling behavior.

Important metrics:

| Metric | Meaning |
|---|---|
| `horizontal_pod_autoscaler_controller_num_horizontal_pod_autoscalers` | Current number of HPA objects controlled. |
| `horizontal_pod_autoscaler_controller_desired_replicas` | Desired replica count calculated by HPA. |
| `horizontal_pod_autoscaler_controller_reconciliations_total` | HPA reconciliation count by action and error. |
| `horizontal_pod_autoscaler_controller_reconciliation_duration_seconds` | Reconciliation duration. |
| `horizontal_pod_autoscaler_controller_metric_computation_total` | Metric computation count by action/error/metric type. |
| `horizontal_pod_autoscaler_controller_metric_computation_duration_seconds` | Metric computation duration. |

Desired replicas:

```promql
horizontal_pod_autoscaler_controller_desired_replicas
```

HPA reconciliation errors:

```promql
sum by (action, error) (
  rate(horizontal_pod_autoscaler_controller_reconciliations_total{
    error!="none"
  }[5m])
)
```

HPA metric computation errors:

```promql
sum by (metric_type, action, error) (
  rate(horizontal_pod_autoscaler_controller_metric_computation_total{
    error!="none"
  }[5m])
)
```

HPA reconciliation p99:

```promql
histogram_quantile(
  0.99,
  sum by (le, action, error) (
    rate(horizontal_pod_autoscaler_controller_reconciliation_duration_seconds_bucket[5m])
  )
)
```

Operational diagnosis:

| Symptom | Check |
|---|---|
| HPA not scaling | HPA controller errors, Metrics Server availability, target metrics, resource requests. |
| HPA desired replicas correct but Pods not created | Workload controller/ReplicaSet/scheduler issue. |
| HPA desired replicas not changing | HPA metric computation issue or scaling stabilization window. |
| HPA flapping | Application load pattern, metric noise, HPA behavior policy, missing requests. |

Commands:

```bash
oc get hpa -A
oc describe hpa -n <namespace> <hpa-name>
oc adm top pods -n <namespace>
oc get --raw /apis/metrics.k8s.io/v1beta1/nodes | head
```

### 7.2 CronJob Controller Metrics

CronJob metrics help identify schedule-to-Job creation delay.

Important metric:

```promql
cronjob_controller_job_creation_skew_duration_seconds
```

Meaning:

```text
Time between when a CronJob is scheduled to run and when the corresponding Job is created.
```

p99 skew:

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(cronjob_controller_job_creation_skew_duration_seconds_bucket[5m])
  )
)
```

Operational interpretation:

| Skew | Meaning |
|---|---|
| Low skew | CronJob controller is timely. |
| High skew during upgrade | Temporary control-plane pressure may delay Jobs. |
| Persistent high skew | Controller backlog, API server latency, CronJob object scale issue, or time synchronization issue. |

Commands:

```bash
oc get cronjob -A
oc get job -A --sort-by=.metadata.creationTimestamp
oc describe cronjob -n <namespace> <cronjob-name>
```

Related checks:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc get pods -n <namespace> -l job-name=<job-name>
```

### 7.4 EndpointSlice Controller Metrics

EndpointSlice metrics are critical for Service traffic correctness. If EndpointSlices are stale, Services might route to wrong or missing backends.

Important metrics:

| Metric | Meaning |
|---|---|
| `endpoint_slice_controller_changes` | Number of EndpointSlice changes by operation. |
| `endpoint_slice_controller_syncs` | Number of EndpointSlice syncs by result. |
| `endpoint_slice_controller_desired_endpoint_slices` | Desired number of EndpointSlices. |
| `endpoint_slice_controller_num_endpoint_slices` | Current number of EndpointSlices. |
| `endpoint_slice_controller_endpoints_desired` | Desired endpoints. |
| `endpoint_slice_controller_endpoints_added_per_sync` | Endpoints added per sync. |
| `endpoint_slice_controller_endpoints_removed_per_sync` | Endpoints removed per sync. |
| `endpoint_slice_controller_endpointslices_changed_per_sync` | EndpointSlices changed per sync. |

EndpointSlice sync errors:

```promql
sum by (result) (
  rate(endpoint_slice_controller_syncs{result!="success"}[5m])
)
```

EndpointSlice churn:

```promql
sum by (operation) (
  rate(endpoint_slice_controller_changes[5m])
)
```

Desired vs actual EndpointSlices:

```promql
endpoint_slice_controller_desired_endpoint_slices
```

```promql
endpoint_slice_controller_num_endpoint_slices
```

Operational diagnosis:

| Symptom | Check |
|---|---|
| Service has no endpoints | Labels/selectors, Pods Ready, EndpointSlice controller sync, NetworkPolicy not relevant for object creation. |

## 10. Alerting Strategy

A mature alerting strategy should page on user-impacting control-plane degradation, not every short-lived spike.

### 10.1 Alert Severity Model

| Severity | Meaning | Example |
|---|---|---|
| Critical | Cluster reconciliation likely broken or severely degraded. | No controller manager leader, target down, workqueues stuck for long time. |
| Warning | Degradation developing; investigate during business hours or before it becomes outage. | Queue depth high, API 429s, CronJob skew high. |
| Info | Useful for dashboards or upgrade observation. | Temporary queue spikes during operator rollouts. |

### 10.2 Avoid Bad Alerts

Do not page on:

- One short workqueue spike.
- A single retry burst.
- Alpha metrics without version validation.
- Raw queue depth without considering event rate.
- Standby controller manager instance metrics that look idle.

Better approach:

- Alert when queue depth + queue latency + retries are all abnormal.
- Alert when no active leader exists.
- Alert when target down persists.
- Alert when controller manager API errors persist.
- Alert on user-facing symptoms: HPA not reconciling, CronJobs delayed, EndpointSlices sync failing, Node controller lag.

## 11. Example PrometheusRule

> Use this as a starting point. In OpenShift, platform alert rules are managed components. For custom user workload alerting, use supported user workload monitoring. Do not modify managed platform rules directly unless following Red Hat-supported configuration paths.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: controller-manager-custom-alerts
  namespace: openshift-user-workload-monitoring
spec:
  groups:
  - name: controller-manager.rules
    rules:
    - alert: ControllerManagerTargetDown
      expr: |
        up{job=~".*controller-manager.*"} == 0
      for: 10m
      labels:
        severity: critical
      annotations:
        summary: "Controller manager metrics target is down"
        description: "Prometheus cannot scrape {{ $labels.job }} on {{ $labels.instance }} for 10 minutes."

    - alert: ControllerManagerNoLeader
      expr: |
        sum by (name) (
          leader_election_master_status{job=~".*controller-manager.*"}
        ) < 1
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "No controller manager leader"
        description: "No active leader for controller manager lease {{ $labels.name }}."

    - alert: ControllerManagerMultipleLeaders
      expr: |
        sum by (name) (
          leader_election_master_status{job=~".*controller-manager.*"}
        ) > 1
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "Multiple controller manager leaders"
        description: "More than one active leader exists for lease {{ $labels.name }}."

    - alert: ControllerManagerWorkqueueBacklog
      expr: |
        max by (name) (
          workqueue_depth{job=~".*controller-manager.*"}
        ) > 100
        and
        histogram_quantile(
          0.95,
          sum by (le, name) (
            rate(workqueue_queue_duration_seconds_bucket{job=~".*controller-manager.*"}[5m])
          )
        ) > 30
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "Controller manager workqueue backlog"
        description: "Queue {{ $labels.name }} has sustained backlog and high wait latency."

    - alert: ControllerManagerWorkqueueStuck
      expr: |
        max by (name) (
          workqueue_longest_running_processor_seconds{job=~".*controller-manager.*"}
        ) > 600
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "Controller manager workqueue processor stuck"
        description: "Queue {{ $labels.name }} has a processor running longer than 10 minutes."

    - alert: ControllerManagerApiErrors
      expr: |
        sum by (job, code, method) (
          rate(rest_client_requests_total{
            job=~".*controller-manager.*",
            code=~"429|5.."
          }[5m])
        ) > 1
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "Controller manager API client errors"
        description: "{{ $labels.job }} is receiving API code {{ $labels.code }} for method {{ $labels.method }}."

    - alert: CronJobControllerHighCreationSkew
      expr: |
        histogram_quantile(
          0.99,
          sum by (le) (
            rate(cronjob_controller_job_creation_skew_duration_seconds_bucket[10m])
          )
        ) > 300
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "CronJob controller creation skew is high"
        description: "CronJobs are being converted to Jobs more than 5 minutes late at p99."

    - alert: EndpointSliceControllerSyncErrors
      expr: |
        sum by (result) (
          rate(endpoint_slice_controller_syncs{result!="success"}[5m])
        ) > 0
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "EndpointSlice controller sync errors"
        description: "EndpointSlice controller is reporting failed syncs."
```

Notes:

- `openshift-user-workload-monitoring` examples require user workload monitoring to be enabled.
- Built-in platform Prometheus access and custom rule support depend on cluster configuration and version.
- Use recording rules for expensive queries in large clusters.
- Tune thresholds for your cluster size and normal churn.

## 14. Troubleshooting Runbooks

### 14.1 Runbook: Controller Manager Target Down

Symptom:

```promql
up{job=~".*controller-manager.*"} == 0
```

Step 1: Check cluster operators.

```bash
oc get co kube-controller-manager openshift-controller-manager
oc describe co kube-controller-manager
oc describe co openshift-controller-manager
```

Step 2: Check pods.

```bash
oc get pods -n openshift-kube-controller-manager -o wide
oc get pods -n openshift-controller-manager -o wide
```

Step 3: Check endpoints and ServiceMonitor.

```bash
oc get svc,endpoints,endpointslice -n openshift-kube-controller-manager
oc get svc,endpoints,endpointslice -n openshift-controller-manager
oc get servicemonitor -A | grep -i controller
```

Step 4: Check monitoring stack health.

```bash
oc get pods -n openshift-monitoring
oc get co monitoring
oc describe co monitoring
```

Step 5: Check recent events.

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Possible root causes:

| Cause | Confirmation |
|---|---|
| Controller manager pod down | Pod not running/restarting. |
| Metrics endpoint TLS issue | Target down but pod healthy; check ServiceMonitor/endpoints/certs. |
| Prometheus issue | Multiple targets down, Prometheus pods unhealthy. |
| Operator rollout | Recent control-plane revision rollout; check operator logs/events. |
| Network/DNS issue | Metrics service unreachable from monitoring namespace. |

---

### 14.2 Runbook: No Active Leader

Symptom:

```promql
sum by (name) (
  leader_election_master_status{job=~".*controller-manager.*"}
) < 1
```

Step 1: Confirm pods.

```bash
oc get pods -n openshift-kube-controller-manager -o wide
oc get pods -n openshift-controller-manager -o wide
```

Step 2: Check logs of controller manager and operator.

```bash
oc logs -n openshift-kube-controller-manager <pod-name> --tail=200

```

Step 3: Check API server health.


### 14.3 Runbook: Workqueue Backlog

Symptom:

```promql
topk(10, max by (name) (workqueue_depth{job=~".*controller-manager.*"}))
```

High sustained values.

Step 1: Identify queue name.

```promql
topk(10,
  max by (name) (
    workqueue_depth{job=~".*controller-manager.*"}
  )
)
```

Step 2: Check queue wait and work duration.

```promql
histogram_quantile(
  0.99,
  sum by (le, name) (
    rate(workqueue_queue_duration_seconds_bucket{job=~".*controller-manager.*"}[5m])
  )
)
```

```promql
histogram_quantile(
  0.99,
  sum by (le, name) (
    rate(workqueue_work_duration_seconds_bucket{job=~".*controller-manager.*"}[5m])
  )
)
```

Step 3: Check retries.

```promql
sum by (name) (
  rate(workqueue_retries_total{job=~".*controller-manager.*"}[5m])
)
```

Step 4: Check API errors/latency.

```promql
sum by (code, method) (
  rate(rest_client_requests_total{job=~".*controller-manager.*", code=~"429|5.."}[5m])
)
```

Step 5: Map queue to resource.

Examples:

| Queue name contains | Investigate |
|---|---|
| `horizontalpodautoscaler` | HPAs, metrics API, Metrics Server. |
| `cronjob` | CronJobs, Jobs, API latency, time sync. |
| `job` | Job objects, quotas, SCC/admission, Pod creation. |
| `endpoint` / `endpointslice` | Services, Pod labels/readiness, endpoint churn. |
| `node` | Nodes, kubelet heartbeat, MCO, network. |
| `persistentvolume` / `pvc` | StorageClass, CSI, PV/PVC events. |
| `garbage` | Finalizers, owner references, API discovery. |
| `namespace` | Namespace finalization, APIService health. |

Step 6: Inspect relevant objects.

```bash
oc get events -A --sort-by=.lastTimestamp | tail -200
oc get pods -A | grep -E 'Pending|Error|CrashLoopBackOff|Terminating'
```

Decision tree:

```text
High queue depth?
  |
  +-- Queue wait high, work duration normal
  |       -> Event rate too high or worker concurrency insufficient.
  |
  +-- Queue wait high, work duration high
  |       -> Processing slow. Check API latency, retries, specific controller.
  |
  +-- Retries high
  |       -> Controller failing to reconcile. Check events/logs/API errors.
  |
  +-- API 429/5xx high
          -> API server/etcd/APF/control-plane issue.
```

## 15. Correlation with API Server, Etcd, Scheduler, and Kubelet

Controller manager metrics rarely stand alone. Always correlate.

### 15.1 Correlate with API Server

Controller manager sends requests to API server. If API server is slow, controllers lag.

Useful API server metrics:

```promql
histogram_quantile(
  0.99,
  sum by (le, verb, resource) (
    rate(apiserver_request_duration_seconds_bucket[5m])
  )
)
```

```promql
sum by (code, verb, resource) (
  rate(apiserver_request_total{code=~"429|5.."}[5m])
)
```

```promql
apiserver_current_inflight_requests
```

Look for:

- High API request latency.
- 429 responses.
- High inflight requests.
- Admission webhook latency.
- APF queueing.

### 15.2 Correlate with Etcd

If etcd is slow, API writes/reads slow, leader election renewals slow, and controller queues grow.

Useful etcd metrics:

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
  )
)
```

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(etcd_disk_backend_commit_duration_seconds_bucket[5m])
  )
)
```

```promql
rate(etcd_server_leader_changes_seen_total[5m])
```

Look for:

- Disk latency.
- Leader changes.
- Database size pressure.
- Network latency between control-plane nodes.

### 15.3 Correlate with Scheduler

If controller manager creates Pods but Pods remain Pending, the scheduler might be the next bottleneck.

Useful scheduler checks:

```bash
oc get pods -A | grep Pending
oc describe pod -n <namespace> <pod>
```

Metrics:

```promql
scheduler_pending_pods
```

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(scheduler_pod_scheduling_sli_duration_seconds_bucket[5m])
  )
)
```

### 15.4 Correlate with Kubelet

If controllers and scheduler did their jobs but containers are not running, check kubelet/CRI-O/node.

Commands:

```bash
oc describe pod -n <namespace> <pod>
oc adm top node <node>
oc debug node/<node>
```

Node-level metrics and events are usually more useful here than controller manager metrics.

## 17. Version and Stability Considerations

Kubernetes metrics have stability levels:

| Stability | Operational guidance |
|---|---|
| Stable | Safer for alerts and long-term dashboards. |
| Beta | Usually acceptable for dashboards and some warning alerts, but validate after upgrades. |
| Alpha | Use carefully. Names, labels, or semantics can change. Avoid critical paging unless no alternative exists. |

Controller manager metrics include a mix of stable, beta, and alpha metrics.

Practical advice:

1. Build critical alerts around stable/beta generic signals:
   - `up`
   - leader election
   - workqueue depth/latency/retries
   - API client errors
2. Use alpha controller-specific metrics for dashboards and diagnosis.
3. Review alert rules after OpenShift upgrades.
4. Use `count by (__name__)` before and after upgrades to detect metric disappearance.
5. Avoid overfitting dashboards to a single Kubernetes minor version.

Metric discovery before upgrade:

```promql
count by (__name__) (
  {job=~".*controller-manager.*"}
)
```

Save results before and after upgrade and compare.

## 18. Capacity and Scale Considerations

Controller manager pressure increases with:

- Number of Namespaces.
- Number of Pods.
- Number of Services and EndpointSlices.
- Number of HPAs.
- Number of Jobs/CronJobs.
- Number of PVs/PVCs.
- API object churn.
- Operators creating/updating many resources.
- Large deployments with rapid rollouts.
- CI/CD systems applying manifests frequently.
- GitOps sync storms.
- Admission webhooks adding latency to creates/updates.
- API Priority and Fairness contention.
- Etcd disk/network latency.

Watch these together:

```promql
topk(10, max by (name) (workqueue_depth{job=~".*controller-manager.*"}))
```

```promql
sum by (code, method) (
```

If many controllers are delayed during high churn, reduce object churn before increasing platform size:

- Stagger GitOps sync waves.
- Avoid mass namespace/project deletion during peak hours.
- Avoid creating thousands of Jobs at once.

- Tune HPA behavior to avoid rapid oscillations.
- Keep admission webhooks fast and highly available.
- Fix controllers/operators that constantly patch objects.
- Avoid label selectors that select too many Pods unintentionally.
- Keep etcd healthy and storage latency low.

## 19. Common Production Scenarios

### 19.1 GitOps Sync Storm

Symptoms:

- Many objects updated in short time.
- Workqueue depth spikes.
- API 429s increase.
- Operators reconcile repeatedly.
- EndpointSlice and workload controllers churn.

Metrics:

```promql
topk(10, max by (name) (workqueue_depth{job=~".*controller-manager.*"}))
```

```promql
sum by (code, method) (rate(rest_client_requests_total{job=~".*controller-manager.*"}[5m]))
```

Mitigation:

- Stagger Argo CD sync waves.
- Reduce auto-sync frequency.
- Use resource exclusions where appropriate.
- Avoid unnecessary field churn.
- Fix applications that constantly mutate desired state.
- Observe API Priority and Fairness.

### 19.2 Bad CronJob Design

Symptoms:

- Hundreds/thousands of Jobs created.
- Jobs overlap.
- CronJob skew increases.
- Job controller queue grows.

Mitigation:

- Set `concurrencyPolicy`.
- Set `successfulJobsHistoryLimit` and `failedJobsHistoryLimit`.
- Use `startingDeadlineSeconds`.
- Avoid every-minute schedules for heavy tasks.
- Spread schedules.

### 19.3 Endpoint Churn from Flapping Pods

Symptoms:

- EndpointSlice changes high.
- Service traffic unstable.
- Pods repeatedly fail readiness.

Mitigation:

- Fix readiness probe.
- Add startup probe.
- Slow rollout.
- Fix application crash loop.
- Validate Service selectors.

### 19.4 Storage Provisioning Delay

Symptoms:

- PVC pending.
- PV collector unbound counts rise.
- Pods pending with volume binding messages.

Mitigation:

- Check CSI controller.
- Check StorageClass.
- Check topology.
- Check storage backend capacity.
- Check volume attach limits.

### 19.5 Etcd Latency Impact

Symptoms:

- Leader election slowpath increases.
- API request duration increases.
- Workqueue latency increases across many queues.
- Cluster operator degradation.

Mitigation:

- Check etcd health.
- Check disk latency.
- Check control-plane node pressure.
- Reduce API churn.
- Engage Red Hat support for persistent etcd latency.

## 20. Best Practices for Advanced Administrators

### 20.1 Do

- Use OpenShift-managed monitoring instead of deploying a separate Prometheus for platform components.
- Observe controller manager metrics during upgrades, GitOps syncs, node outages, and storage incidents.
- Alert on sustained symptoms, not one-off spikes.
- Use leader election metrics to identify active controllers.
- Use workqueue metrics as the primary reconciliation health signal.
- Correlate with API server and etcd before blaming a controller.
- Keep control-plane nodes healthy and not overloaded.
- Use `oc adm must-gather` before restarting or changing anything.
- Validate metric names after OpenShift upgrades.
- Use recording rules for expensive dashboard queries.
- Keep admission webhooks highly available and low-latency.
- Keep CronJob and Job object churn under control.
- Stagger high-volume automation.

### 20.2 Do Not

- Do not manually edit static pod manifests on control-plane nodes in OpenShift.
- Do not disable or modify managed platform monitoring components outside supported paths.
- Do not page on alpha metrics without verifying stability across your OpenShift version.
- Do not assume `up=1` means controllers are healthy; queues may still be stuck.
- Do not assume API reachable means reconciliation is healthy.
- Do not remove finalizers unless you understand the side effects.
- Do not run mass deletions or namespace cleanup during peak hours without observing controller manager backlog.
- Do not ignore `429` responses from controller manager clients; they show API pressure or flow-control contention.

## 24. Interview-Ready Explanation

A strong senior-level answer:

> Controller manager metrics show the health of Kubernetes and OpenShift reconciliation loops. In OpenShift, the platform Prometheus stack scrapes the Kubernetes controller manager, OpenShift controller manager, and their operators as managed platform targets. The most important metrics are leader election status, workqueue depth, queue latency, work duration, retry rate, stuck work, and API client latency/errors. If users say resources are not changing after `oc apply`, I check whether the controller manager has a leader, whether the relevant queue is backed up, whether the controller is retrying, and whether API server/etcd latency is causing the delay. For specific symptoms, I check controller-specific metrics such as HPA reconciliation errors, CronJob creation skew, EndpointSlice sync errors, Node controller health duration, PV/PVC collector counts, and garbage collector errors. I never troubleshoot these metrics in isolation; I correlate with cluster operators, kube-apiserver, etcd, scheduler, kubelet, events, and affected objects.

```text
|     +-- Yes
|

|     |
|     +-- No -> Check pods, ServiceMonitor, monitoring, TLS/RBAC
|     +-- Yes
|
+-- Is there an active leader?
|     |
|     +-- No -> Control-plane critical; check API/etcd/leases/certs
|     +-- Yes
|
+-- Is relevant workqueue backlogged?
|     |
|     +-- Yes -> Check queue latency, work duration, retries
|     +-- No
|
+-- Are API client errors/latency high?
|     |
|     +-- Yes -> Check kube-apiserver/etcd/APF/admission webhooks
|     +-- No
|
+-- Is controller-specific metric bad?
|     |
|     +-- HPA -> Metrics API/resource requests/quota
|     +-- CronJob -> skew/schedule/deadline/concurrency/time
|     +-- EndpointSlice -> selectors/readiness/churn
|     +-- PV/PVC -> storageclass/CSI/topology/finalizers
|     +-- Node -> kubelet heartbeat/network/taints
|     +-- GC/Namespace -> finalizers/APIService/discovery
|
+-- If all controller metrics look normal
      -> Problem likely in scheduler, kubelet, admission, application, storage, or networking layer
```

## 27. Final Notes

Controller manager metrics are not just "monitoring data". They are the visibility layer into the reconciliation engine of OpenShift.

For senior OpenShift administration, always think in this sequence:

```text
desired state -> API storage -> controller queue -> reconcile -> API write -> next component
```

When that chain breaks, controller manager metrics tell you where to look.

The most valuable production habit is to correlate:

```text
workqueue metrics
+ API client metrics
+ leader election
+ cluster operator status
+ kube-apiserver/etcd health
+ affected object events
```

That combination quickly separates application misconfiguration from real platform control-plane degradation.
