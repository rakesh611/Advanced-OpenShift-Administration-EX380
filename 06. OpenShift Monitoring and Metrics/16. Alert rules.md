## 1. What alert rules mean in OpenShift

An **alert rule** is a Prometheus rule that continuously evaluates a PromQL expression. When the expression returns one or more time series for long enough, Prometheus or Thanos Ruler marks the alert as active and eventually sends it to Alertmanager.

In OpenShift, alert rules are not just YAML snippets. They are part of a full operational chain:

```text
Metrics target
  -> scrape by Prometheus
  -> time series stored locally / queried through Thanos Querier
  -> alert rule evaluated
  -> alert instance becomes pending or firing
  -> Alertmanager receives alert
  -> grouping, routing, inhibition, silence applied
  -> receiver sends notification
  -> human or automation responds using runbook
```

A senior OpenShift administrator must understand the difference between:

| Term | Meaning |
|---|---|
| Alerting rule | The rule definition: name, PromQL expression, `for`, labels, annotations. |
| Alert instance | A concrete alert produced for a specific label set. One rule can produce many alert instances. |
| Pending alert | Expression is true, but the `for` duration has not completed. |
| Firing alert | Expression is true and has remained true for the configured duration. |
| Resolved alert | Expression no longer matches; Alertmanager receives resolution if configured. |
| Silence | Alertmanager object that suppresses notifications for matching alerts. It does not stop rule evaluation. |
| Inhibition | Alertmanager rule that suppresses lower-level alerts when a higher-level alert is firing. |
| Receiver | Notification target such as email, webhook, PagerDuty, Slack-compatible webhook, ServiceNow integration, or custom automation. |

### Why alert rules are critical

Alert rules are the bridge between metrics and action. Dashboards are useful when someone is looking. Alert rules are useful when nobody is looking. In production, alert rules must answer these questions:

1. **Is there customer or platform impact?**
2. **Who owns the issue?**
3. **How urgent is it?**
4. **What should the responder do first?**
5. **Can the alert be trusted?**

Bad alerting causes either missed outages or alert fatigue. Advanced administration is about designing alert rules that are accurate, actionable, scoped, and maintainable.

## 2. OpenShift monitoring architecture for alerting

OpenShift includes a built-in monitoring stack based on Prometheus, Alertmanager, the Prometheus Operator, kube-state-metrics, node-exporter, OpenShift-specific exporters, and Thanos components.

At a high level:

```text
openshift-monitoring namespace
  - Cluster Monitoring Operator
  - Prometheus Operator
  - Prometheus for platform metrics
  - Alertmanager main
  - Thanos Querier
  - kube-state-metrics
  - node-exporter
  - platform ServiceMonitors / PodMonitors / rules

openshift-user-workload-monitoring namespace
  - Prometheus Operator for user workloads
  - Prometheus for user-defined projects
  - Thanos Ruler for user workload rules
  - optional user-workload Alertmanager
```

### Platform monitoring

Platform monitoring handles OpenShift control plane and core cluster components. Examples:

- Kubernetes API server
- etcd
- kubelet
- scheduler
- controller manager
- ingress/router
- cluster operators
- machine config pools
- storage operators
- nodes
- default OpenShift platform alerts

Platform alerts are normally viewed and managed by cluster administrators.

### User workload monitoring

User workload monitoring monitors application namespaces created by users or teams. It allows app teams to define their own ServiceMonitor, PodMonitor, PrometheusRule, and AlertmanagerConfig resources without deploying their own unsupported Prometheus stack.

Examples:

- Application error rate
- Application latency
- Pod restart rate
- PVC usage in an app namespace
- Queue backlog
- Business transaction failures
- SLO burn rate

### The practical split

| Area | Platform monitoring | User workload monitoring |
|---|---|---|
| Primary namespace | `openshift-monitoring` | `openshift-user-workload-monitoring` plus user namespaces |
| Rule CRD for custom alerts | `AlertingRule` | `PrometheusRule` |
| Primary operator | Cluster Monitoring Operator | User workload monitoring stack |
| Scope | Core OpenShift metrics | Application and user project metrics |
| Typical owner | Platform team | App team / namespace owner |
| Routing | Platform Alertmanager | Platform Alertmanager or dedicated user-workload Alertmanager |

## 3. Alert rule lifecycle

Prometheus evaluates alert rules periodically. Each evaluation creates zero or more alert instances based on the returned vector.

### State transitions

```text
Inactive
  expression false or no matching series

Pending
  expression true but `for` duration not completed

Firing
  expression true for the full `for` duration

Resolved
  expression becomes false after firing
```

### Example

```yaml
- alert: PodRestartingFrequently
  expr: increase(kube_pod_container_status_restarts_total{namespace="prod"}[15m]) > 3
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "Pod {{ $labels.pod }} is restarting frequently"
```

This alert does not fire immediately when the expression first becomes true. It enters `Pending`. It fires only if the expression remains true for 10 minutes.

### Important behavior

- `for` reduces flapping.
- The alert identity is based on the final label set of the alert instance.
- Changing labels can create new alert instances.
- Every matching time series can produce a separate alert instance.
- A rule with unbounded labels can create alert storms.
- A silence stops notifications, not evaluation.
- A rule can be valid YAML but operationally bad PromQL.

## 4. Platform alert rules vs user workload alert rules

This is one of the most important OpenShift-specific topics.

### Platform alert rules

Platform alert rules are about the OpenShift cluster itself. OpenShift ships many default platform alerting rules. As a cluster administrator, you can customize platform alerting by:

1. Modifying how existing platform alerts are labeled or handled before reaching Alertmanager.
2. Adding new platform alert rules based on core platform metrics.

For new custom platform rules, OpenShift uses:

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertingRule
metadata:
  namespace: openshift-monitoring
```

A platform `AlertingRule` must be created in `openshift-monitoring`. It is intended for cluster administrators.

### User workload alert rules

User workload alert rules are about applications and tenant workloads. These use the Prometheus Operator CRD:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  namespace: <application-namespace>
```

User workload rules require user workload monitoring to be enabled.

### Simple decision table

| Requirement | Use |
|---|---|
| Alert on application metric in `payments` namespace | `PrometheusRule` in `payments` |
| Alert on PVC usage in app namespace | `PrometheusRule` in app namespace |
| Alert on etcd leader changes | Platform `AlertingRule` in `openshift-monitoring` |
| Alert on API server latency | Platform `AlertingRule` in `openshift-monitoring` |
| Modify severity label of an existing platform alert | `AlertRelabelConfig` in `openshift-monitoring` |
| Send app alerts to app team's receiver | `AlertmanagerConfig` in app namespace, after routing is enabled |
| Cross-project user workload security rule | `PrometheusRule` in approved namespace configured with `namespacesWithoutLabelEnforcement` |

## 5. Important CRDs and objects

### 5.1 `PrometheusRule`

Used for user workload alerting and recording rules.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
```

Common fields:

```yaml
spec:
  groups:
  - name: group-name
    rules:
    - alert: AlertName
      expr: <promql>
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: ...
        description: ...
```

Use cases:

- Application alerts
- Namespace-level workload alerts
- User workload recording rules
- Cross-project user workload rules when explicitly configured

### 5.2 `AlertingRule`

OpenShift-specific resource for platform monitoring alerts.

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertingRule
metadata:
  namespace: openshift-monitoring
```

Use cases:

- Add cluster-level alerts based on platform metrics.
- Create custom platform alerts without modifying operator-owned resources.

### 5.3 `AlertRelabelConfig`

OpenShift-specific mechanism to modify platform alert labels before Alertmanager routing. Useful when you want to:

- Change severity for an existing platform alert.
- Add routing labels such as `team`, `service`, or `environment`.
- Drop or keep selected alerts before they reach Alertmanager.

Example use case:

```text
Default alert: KubeNodeNotReady severity=warning
Organization wants: severity=critical when production cluster
```

Do not casually drop default platform alerts. Dropping alerts can hide real incidents.

### 5.4 `AlertmanagerConfig`

Used for user-defined alert routing when enabled.

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
```

Use cases:

- Route application alerts to a team-specific webhook.
- Configure receiver grouping for a namespace.
- Allow developers to manage notification routes for their own projects.

### 5.5 `ServiceMonitor` and `PodMonitor`

Alert rules are useless if metrics are not scraped. ServiceMonitor and PodMonitor define how user workload Prometheus scrapes application metrics.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
```

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
```

Typical chain:

```text
Application exposes /metrics
  -> Service selects pods
  -> ServiceMonitor selects Service
  -> Prometheus scrapes target
  -> PrometheusRule evaluates metrics
  -> Alertmanager routes alert
```

## 6. RBAC model for alert rules

OpenShift monitoring is multi-tenant. Do not give every developer cluster-wide monitoring power.

### Important roles

| Role | Purpose |
|---|---|
| `monitoring-rules-view` | Read `PrometheusRule` CRs for user-defined projects. |
| `monitoring-rules-edit` | Create, modify, and delete `PrometheusRule` CRs in a user project. |
| `monitoring-edit` | Includes rule editing plus ServiceMonitor and PodMonitor management. |
| `alert-routing-edit` | Create, update, and delete `AlertmanagerConfig` CRs in a user project. |
| `pod-metrics-reader` | Access pod metrics through Thanos API endpoints for user-defined projects. |
| `cluster-monitoring-view` | View cluster monitoring data. |
| `monitoring-alertmanager-edit` | Create and manage silences. |
| `user-workload-monitoring-config-edit` | Edit the user workload monitoring stack config map. Highly privileged. |

### Grant a user permission to create PrometheusRule in one namespace

```bash
oc adm policy add-cluster-role-to-user monitoring-rules-edit alice -n payments
```

### Grant a user permission to create ServiceMonitor and PrometheusRule

```bash
oc adm policy add-cluster-role-to-user monitoring-edit alice -n payments
```

### Grant a user permission to create AlertmanagerConfig

```bash
oc -n payments adm policy add-role-to-user alert-routing-edit alice
```

### Check permissions

```bash
oc auth can-i create prometheusrules.monitoring.coreos.com -n payments --as alice
oc auth can-i create alertmanagerconfigs.monitoring.coreos.com -n payments --as alice
oc auth can-i create servicemonitors.monitoring.coreos.com -n payments --as alice
```

### Senior admin rule

Bind monitoring roles at the namespace level unless there is a strong platform reason to do otherwise. Alert rules can create high-cardinality queries and noisy notifications, so rule authoring is operationally sensitive.

## 7. Enable user workload monitoring

User workload monitoring is required for application namespaces to use supported OpenShift monitoring.

### 7.1 Enable user workload monitoring

Create or edit the `cluster-monitoring-config` ConfigMap:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Add:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Verify pods:

```bash
oc get pods -n openshift-user-workload-monitoring
```

Expected components can include:

```text
prometheus-operator-*
prometheus-user-workload-*
thanos-ruler-user-workload-*
```

### 7.2 Create or edit user workload config

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      retention: 24h
    thanosRuler:
      logLevel: info
```

Be careful: some configuration changes redeploy monitoring pods. In single-node clusters, this can temporarily interrupt monitoring.

### 7.3 Exclude a namespace from user workload monitoring

```bash
oc label namespace test-lab 'openshift.io/user-monitoring=false'
```

This is useful for noisy test namespaces, but remember: if a namespace is excluded, alerting and routing resources in that namespace no longer participate in user workload monitoring.

## 8. Writing user workload alert rules with PrometheusRule

### 8.1 Minimal working PrometheusRule

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: app-basic-alerts
  namespace: payments
spec:
  groups:
  - name: payments.basic.rules
    rules:
    - alert: PaymentsAppDown
      expr: up{namespace="payments", job="payments-api"} == 0
      for: 5m
      labels:
        severity: critical
        team: payments
      annotations:
        summary: "Payments API target is down"
        description: "Prometheus has not been able to scrape payments-api for 5 minutes."
        runbook_url: "https://runbooks.example.com/payments/app-down"
```

Apply:

```bash
oc apply -f app-basic-alerts.yaml
```

List:

```bash
oc -n payments get prometheusrule
oc -n payments get prometheusrule app-basic-alerts -o yaml
```

### 8.2 Anatomy of a rule

```yaml
- alert: HighErrorRate
  expr: |
    sum(rate(http_requests_total{namespace="payments", code=~"5.."}[5m]))
    /
    sum(rate(http_requests_total{namespace="payments"}[5m]))
    > 0.05
  for: 10m
  labels:
    severity: critical
    team: payments
    service: payments-api
  annotations:
    summary: "High 5xx error rate in payments-api"
    description: "5xx error ratio is above 5% for 10 minutes. Current value: {{ $value }}"
    runbook_url: "https://runbooks.example.com/payments/high-error-rate"
```

| Field | Purpose |
|---|---|
| `alert` | Alert name. Use PascalCase and stable naming. |
| `expr` | PromQL condition. If it returns a vector, alert becomes active. |
| `for` | How long the condition must remain true before firing. |
| `labels` | Routing, grouping, ownership, severity. Keep them stable and low-cardinality. |
| `annotations` | Human-readable context. Safe place for descriptions, dashboard links, runbooks. |

### 8.3 Naming conventions

Good alert names:

```text
PaymentsHighErrorRate
PaymentsHighLatency
NamespacePVCFillingSoon
PodRestartingFrequently
ApplicationTargetDown
```

Poor alert names:

```text
alert1
CPUHigh
Problem
Restart
CriticalIssue
```

A good alert name tells you the affected domain and symptom.

### 8.4 Good group names

```yaml
spec:
  groups:
  - name: payments.slo.rules
  - name: payments.capacity.rules
  - name: payments.availability.rules
```

Avoid one huge group containing unrelated rules. Group names should help you troubleshoot rule evaluation.

## 9. Writing platform alert rules with AlertingRule

Use `AlertingRule` when you want a custom alert based on platform metrics from the OpenShift platform monitoring stack.

### 9.1 Minimal platform AlertingRule

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertingRule
metadata:
  name: custom-platform-rules
  namespace: openshift-monitoring
spec:
  groups:
  - name: custom.platform.rules
    rules:
    - alert: CustomAPIServerHighLatency
      expr: |
        histogram_quantile(
          0.99,
          sum by (le, resource, verb) (
            rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|CONNECT"}[5m])
          )
        ) > 1
      for: 10m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "Kubernetes API server high p99 latency"
        description: "API server p99 request latency is above 1 second for 10 minutes."
        runbook_url: "https://runbooks.example.com/platform/api-latency"
```

Apply:

```bash
oc apply -f custom-platform-rules.yaml
```

Verify:

```bash
oc -n openshift-monitoring get alertingrule
oc -n openshift-monitoring get alertingrule custom-platform-rules -o yaml
```

### 9.2 Platform rule guidelines

1. Do not duplicate existing default platform alerts unless you intentionally customize them.
2. If you create a custom rule similar to an existing default alert, silence or relabel the original carefully to avoid conflicting notifications.
3. Always include a severity and message.
4. Put platform rules only in `openshift-monitoring`.
5. Review rule impact because platform Prometheus is critical infrastructure.

## 10. Modifying platform alert behavior with AlertRelabelConfig

`AlertRelabelConfig` is used to modify alert labels before alerts reach Alertmanager.

### 10.1 Example: add a team label to platform alerts

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertRelabelConfig
metadata:
  name: add-platform-team-label
  namespace: openshift-monitoring
spec:
  configs:
  - sourceLabels: [alertname]
    regex: "Kube.*|ClusterOperator.*|Node.*"
    targetLabel: team
    replacement: platform
    action: Replace
```

Apply:

```bash
oc apply -f add-platform-team-label.yaml
```

### 10.2 Example: change severity for one alert

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertRelabelConfig
metadata:
  name: node-not-ready-critical
  namespace: openshift-monitoring
spec:
  configs:
  - sourceLabels: [alertname]
    regex: "KubeNodeNotReady"
    targetLabel: severity
    replacement: critical
    action: Replace
```

### 10.3 Caution

Relabeling is powerful. It affects notifications downstream. A bad relabel rule can break routing or hide important alerts. Always test in a non-production cluster or apply narrowly with exact matchers.

## 11. Cross-project alert rules

By default, user workload `PrometheusRule` objects are namespace-scoped. OpenShift enforces namespace scoping so that a rule in one tenant namespace does not freely evaluate data for other namespaces.

In some advanced cases, platform teams need cross-project user workload alerting, for example:

- Validate namespace security labels across all app projects.
- Detect app namespaces without required limits or quotas.
- Create shared SRE rules for all production namespaces.

OpenShift supports cross-project user workload rules through `namespacesWithoutLabelEnforcement` in the `user-workload-monitoring-config` ConfigMap.

### 11.1 Configure a namespace for cross-project rules

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    namespacesWithoutLabelEnforcement:
    - platform-observability
```

Then create cross-project rules in `platform-observability`.

### 11.2 Example cross-project rule

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: namespace-policy-alerts
  namespace: platform-observability
spec:
  groups:
  - name: namespace.policy.rules
    rules:
    - alert: NamespaceMissingResourceQuota
      expr: |
        kube_namespace_status_phase{phase="Active", namespace!~"openshift.*|kube.*|default"}
        unless on(namespace)
        kube_resourcequota_created
      for: 30m
      labels:
        severity: warning
        team: platform
      annotations:
        summary: "Namespace {{ $labels.namespace }} has no ResourceQuota"
        description: "Active user namespace {{ $labels.namespace }} does not appear to have a ResourceQuota."
```

### 11.3 Governance

Cross-project rules should be owned by the platform team. They can easily produce many alert instances or leak tenant context through notifications.

## 12. Alert routing and notification flow

Alert rules only create alerts. Alertmanager routes alerts to humans or systems.

### 12.1 Default flow

```text
Prometheus / Thanos Ruler
  -> Alertmanager
  -> route tree
  -> receiver
  -> notification
```

### 12.2 User workload routing options

For user-defined projects, cluster administrators can choose:

1. Use the default platform Alertmanager instance.
2. Enable a separate Alertmanager instance dedicated to user workload alerts.

### 12.3 Enable platform Alertmanager for user-defined routing

Edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Add:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    alertmanagerMain:
      enableUserAlertmanagerConfig: true
```

### 12.4 Enable dedicated user workload Alertmanager

Edit:

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Add:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    alertmanager:
      enabled: true
      enableAlertmanagerConfig: true
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get alertmanager
oc -n openshift-user-workload-monitoring get pods | grep alertmanager
```

### 12.5 Example AlertmanagerConfig for a namespace

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
metadata:
  name: payments-routing
  namespace: payments
spec:
  route:
    receiver: payments-webhook
    groupBy:
    - alertname
    - namespace
    - severity
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 4h
  receivers:
  - name: payments-webhook
    webhookConfigs:
    - url: https://alerts.example.com/webhook/payments
```

Apply:

```bash
oc apply -f payments-alertmanagerconfig.yaml
```

### 12.6 Routing limitations to remember

- User-defined alert routing is scoped to the namespace where the `AlertmanagerConfig` is defined.
- A routing config in namespace `payments` applies to alerts from `PrometheusRule` resources in `payments`.
- If a namespace is excluded from user workload monitoring, its AlertmanagerConfig no longer participates.
- App teams need the `alert-routing-edit` role to create or update AlertmanagerConfig resources.

## 13. PromQL patterns for OpenShift alert rules

### 13.1 Counter rate

Counters increase over time and reset on restart. Use `rate()` or `increase()`.

```promql
rate(http_requests_total[5m])
```

For alerting on request rate or error ratio, use `rate()`:

```promql
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))
> 0.05
```

### 13.2 Gauge threshold

Gauges go up and down. Use direct comparison.

```promql
kube_deployment_status_replicas_unavailable{namespace="payments"} > 0
```

### 13.3 Ratio alert

Always aggregate numerator and denominator consistently.

Good:

```promql
sum by (namespace, app) (rate(http_requests_total{code=~"5.."}[5m]))
/
sum by (namespace, app) (rate(http_requests_total[5m]))
> 0.05
```

Bad:

```promql
rate(http_requests_total{code=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
```

The bad version can produce label mismatch or noisy per-instance alerts.

### 13.4 Absent metrics

Use `absent()` or `absent_over_time()` when the problem is missing telemetry.

```promql
absent(up{namespace="payments", job="payments-api"})
```

This catches missing target series. For production, tune carefully so you do not alert during intentional scale-to-zero.

### 13.5 Predictive capacity

Use `predict_linear()` for gauges such as available filesystem bytes.

```promql
predict_linear(kubelet_volume_stats_available_bytes{namespace="payments"}[6h], 4 * 3600) < 0
```

This predicts whether available bytes will reach zero within four hours based on the previous six hours.

### 13.6 Histogram latency

For classic Prometheus histograms:

```promql
histogram_quantile(
  0.99,
  sum by (le, namespace, app) (
    rate(http_request_duration_seconds_bucket{namespace="payments"}[5m])
  )
) > 1
```

Common mistakes:

- Forgetting `le` in the `sum by` clause.
- Calculating quantiles per pod instead of service level.
- Alerting on p99 for very low-traffic services without minimum traffic guard.

### 13.7 Minimum traffic guard

Avoid ratio alerts on tiny traffic.

```promql
(
  sum(rate(http_requests_total{namespace="payments", code=~"5.."}[5m]))
  /
  sum(rate(http_requests_total{namespace="payments"}[5m]))
) > 0.05
and
sum(rate(http_requests_total{namespace="payments"}[5m])) > 1
```

### 13.8 Join with metadata

Use joins carefully.

```promql
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{container!="", image!=""}[5m]))
/
sum by (namespace, pod) (kube_pod_container_resource_requests{resource="cpu", unit="core"})
> 0.9
```

Be careful when joining labels from kube-state-metrics. Incorrect joins can multiply series.

### 13.9 Avoid high-cardinality alerts

High-cardinality labels in alerts cause alert storms.

Risky labels:

- `pod`
- `container`
- `instance`
- `endpoint`
- `path`
- `method` if too granular
- `user_id`
- `request_id`
- `uri`
- dynamically generated labels

Prefer service-level aggregation for paging alerts:

```promql
sum by (namespace, app) (...)
```

Use pod-level alerts for warning/ticket workflows, not paging, unless the pod is a singleton critical component.

## 15. SLO and burn-rate alerting

Advanced alerting should focus on user impact. SLO burn-rate alerting is one of the best methods for production services.

### 15.1 Basic concept

Assume:

- SLO: 99.9% successful requests over 30 days
- Error budget: 0.1%
- Bad events: 5xx responses
- Total events: all HTTP responses

Error ratio:

```promql
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))
```

Burn rate:

```text
current error ratio / allowed error ratio
```

For 99.9% SLO, allowed error ratio is 0.001.

If current error ratio is 0.02, burn rate is:

```text
0.02 / 0.001 = 20x
```

At 20x, you burn a 30-day error budget in about 1.5 days.

### 15.2 Multi-window burn rate pattern

Use two windows to avoid false positives:

- Short window: detects fast incidents.
- Long window: confirms sustained impact.

Example critical page:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: payments-slo-alerts
  namespace: payments
spec:
  groups:
  - name: payments.slo.rules
    rules:
    - alert: PaymentsAPIFastBurn
      expr: |
        (
          sum(rate(http_requests_total{namespace="payments", app="payments-api", code=~"5.."}[5m]))
          /
          sum(rate(http_requests_total{namespace="payments", app="payments-api"}[5m]))
        ) > (14.4 * 0.001)
        and
        (
          sum(rate(http_requests_total{namespace="payments", app="payments-api", code=~"5.."}[1h]))
          /
          sum(rate(http_requests_total{namespace="payments", app="payments-api"}[1h]))
        ) > (14.4 * 0.001)
      for: 2m
      labels:
        severity: critical
        team: payments
        service: payments-api
        slo: availability
      annotations:
        summary: "Payments API is burning error budget quickly"
        description: "Error budget burn rate is above 14.4x over 5m and 1h windows."
        runbook_url: "https://runbooks.example.com/payments/slo-fast-burn"
```

### 15.3 Slow burn warning

```yaml
- alert: PaymentsAPISlowBurn
  expr: |
    (
      sum(rate(http_requests_total{namespace="payments", app="payments-api", code=~"5.."}[30m]))
      /
      sum(rate(http_requests_total{namespace="payments", app="payments-api"}[30m]))
    ) > (6 * 0.001)
    and
    (
      sum(rate(http_requests_total{namespace="payments", app="payments-api", code=~"5.."}[6h]))
      /
      sum(rate(http_requests_total{namespace="payments", app="payments-api"}[6h]))
    ) > (6 * 0.001)
  for: 15m
  labels:
    severity: warning
    team: payments
    service: payments-api
    slo: availability
  annotations:
    summary: "Payments API is slowly burning error budget"
    description: "Error budget burn rate is above 6x over 30m and 6h windows."
```

### 15.4 Why SLO alerts are better than simple threshold alerts

Simple threshold:

```text
5xx rate > 5%
```

SLO burn-rate:

```text
User-impacting errors are consuming error budget too quickly.
```

SLO alerts are easier to defend in incident reviews because they connect directly to customer impact.

## 16. Recording rules and alert performance

Alert expressions can become expensive. Use recording rules to precompute repeated calculations.

### 16.1 Example recording rule

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: payments-recording-rules
  namespace: payments
spec:
  groups:
  - name: payments.recording.rules
    rules:
    - record: namespace_app:http_requests:rate5m
      expr: |
        sum by (namespace, app) (
          rate(http_requests_total{namespace="payments"}[5m])
        )
    - record: namespace_app:http_5xx_requests:rate5m
      expr: |
        sum by (namespace, app) (
          rate(http_requests_total{namespace="payments", code=~"5.."}[5m])
        )
```

Then alert rule:

```yaml
- alert: PaymentsHighErrorRate
  expr: |
    namespace_app:http_5xx_requests:rate5m{namespace="payments", app="payments-api"}
    /
    namespace_app:http_requests:rate5m{namespace="payments", app="payments-api"}
    > 0.05
  for: 10m
  labels:
    severity: critical
```

### 16.2 When to use recording rules

Use recording rules when:

- Multiple alerts reuse the same heavy PromQL.
- Dashboard and alert use the same service-level indicator.
- Query joins are expensive.
- You want stable SLI names.
- You need consistent aggregation.

Avoid recording rules when:

- Query is simple.
- Metric is rarely used.
- You are still experimenting.
- Recording rule name is unclear.

### 16.3 Naming recording rules

Good:

```text
namespace_app:http_requests:rate5m
namespace_app:http_5xx_requests:rate5m
namespace_app:http_error_ratio:ratio5m
```

Pattern:

```text
<level>:<metric>:<operation>
```

## 17. Labels, annotations, severity, ownership, and runbooks

### 17.1 Labels are for machines

Labels are used for:

- Routing
- Grouping
- Deduplication
- Inhibition
- Ownership
- Severity
- Environment

Example:

```yaml
labels:
  severity: critical
  team: payments
  service: payments-api
  environment: production
  alert_type: symptom
```

Keep labels stable. Do not put dynamic values in labels unless you intentionally want separate alert instances.

### 17.2 Annotations are for humans

Annotations are used for:

- Summary
- Description
- Runbook URL
- Dashboard URL
- Query URL
- Impact explanation
- First troubleshooting steps

Example:

```yaml
annotations:
  summary: "Payments API error rate is high"
  description: "5xx ratio is above 5% for 10 minutes. Current value: {{ $value }}"
  runbook_url: "https://runbooks.example.com/payments/high-error-rate"
  dashboard_url: "https://grafana.example.com/d/payments-api"
```

### 17.3 Severity model

Use severity consistently.

| Severity | Meaning | Notification style |
|---|---|---|
| `critical` | Immediate human action required; user or platform impact likely. | Page/on-call. |
| `warning` | Action needed but not urgent; degradation, risk, capacity. | Ticket/chat. |
| `info` | Awareness; no immediate action. | Dashboard/event feed. |

Avoid making every alert `critical`. If everything pages, nothing pages.

### 17.4 Required annotation standard

For production, every alert should include:

```yaml
annotations:
  summary: "Short human title"
  description: "What happened, impact, important labels, current value"
  runbook_url: "https://..."
```

Recommended additional annotations:

```yaml
  dashboard_url: "https://..."
  logs_url: "https://..."
  owner: "payments-team"
```

Do not put secrets, tokens, customer personal data, or sensitive payloads in annotations.

## 18. Noise reduction and alert quality engineering

### 18.1 Alert only on actionable conditions

Bad alert:

```text
CPU usage above 70% for one pod
```

Better alert:

```text
Service latency SLO burn rate is high
```

CPU can be a diagnostic metric. It is not always a user-impacting symptom.

### 18.2 Prefer symptoms over causes

Cause alerts:

- Pod restarted
- Node disk pressure
- CPU throttling
- GC high

Symptom alerts:

- API unavailable
- Error budget burning
- Request latency high
- Data not being processed

You still need cause alerts, but page primarily on symptoms.

### 18.3 Use `for` durations

Examples:

| Alert type | Suggested `for` |
|---|---:|
| API target down | 3m-5m |
| Error rate critical | 5m-10m |
| Latency warning | 10m-15m |
| PVC high usage | 15m-30m |
| Predictive disk fill | 30m |
| Node not ready | 5m-10m |

Do not use `for: 0m` for noisy metrics unless the condition is extremely reliable and high impact.

### 18.4 Add minimum traffic guards

Ratio alerts can lie when traffic is tiny. Add a traffic threshold:

```promql
error_ratio > 0.05
and
request_rate > 1
```

### 18.5 Avoid alerting on every pod

Pod-level alerts can create storms during rollouts. Prefer deployment/service-level alerts for paging.

Better:

```promql
sum by (namespace, deployment) (kube_deployment_status_replicas_unavailable) > 0
```

Instead of alerting on every unavailable pod.

### 18.6 Inhibition examples

If the node is down, suppress pod alerts on that node.

Conceptually:

```text
NodeNotReady firing
  inhibits
PodNotReady alerts on same node
```

This is Alertmanager configuration, not PrometheusRule configuration.

### 18.7 Silence rules during maintenance

Use silences for planned maintenance, but avoid long-term silences that hide real issues.

Good silence comment:

```text
CHG-12345: planned router replacement in dc1, 22:00-23:00 IST
```

Bad silence comment:

```text
noise
```

For Kubernetes CRDs, you might maintain a test-friendly generated rule file in CI.

### 20.5 Unit testing alert rules

Prometheus supports unit tests for rules. Example concept:

`rules.yaml`:

```yaml
groups:
- name: example.rules
  rules:
  - alert: HighErrorRate
    expr: job:http_error_ratio:ratio5m > 0.05
    for: 10m
    labels:
      severity: critical
```

`test.yaml`:

```yaml
rule_files:
- rules.yaml

evaluation_interval: 1m

tests:
- interval: 1m
  input_series:
  - series: 'job:http_error_ratio:ratio5m{job="api"}'
    values: '0.10x20'
  alert_rule_test:
  - eval_time: 15m
    alertname: HighErrorRate
    exp_alerts:
    - exp_labels:
        severity: critical
        job: api
```

Run:

```bash
promtool test rules test.yaml
```

### 20.6 Live fire test

For non-production testing:

```yaml
- alert: AlwaysFiringTestAlert
  expr: vector(1)
  for: 1m
  labels:
    severity: warning
    team: platform
  annotations:
    summary: "Test alert"
```

Remove it immediately after testing:

```bash
oc -n payments delete prometheusrule test-alert
```

Do not leave permanent `vector(1)` test alerts in production.

## 22. Troubleshooting alert rules

### Problem 1: PrometheusRule created but alert rule does not appear

Possible causes:

- User workload monitoring is not enabled.
- Rule is in a namespace excluded from monitoring.
- RBAC allowed object creation but monitoring stack ignores namespace due to configuration.
- PrometheusRule has invalid schema or invalid PromQL.
- Thanos Ruler or user workload Prometheus is unhealthy.
- Rule is valid but source filter in UI is set to Platform only.

Checks:

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config -o yaml | grep enableUserWorkload -A2
oc get namespace payments --show-labels
oc -n payments get prometheusrule payments-alerts -o yaml
oc get pods -n openshift-user-workload-monitoring
oc logs -n openshift-user-workload-monitoring deploy/prometheus-operator
```

Console:

```text
Observe -> Alerting -> Alerting rules -> filter source User
```

---

### Problem 2: Alert stuck in Pending

Cause:

- Expression is true intermittently but not long enough for `for` duration.
- Metric scrapes are missing.
- Threshold is too aggressive.

Check the graph over time:

```promql
<your expression>
```

Fix:

- Adjust `for` duration.
- Use longer range window.
- Smooth noisy signal.
- Alert on service-level aggregation instead of pod-level signal.

---

### Problem 3: Alert fires but no notification is sent

Possible causes:

- AlertmanagerConfig not enabled.
- User lacks `alert-routing-edit` or config not applied.
- Route matcher does not match alert labels.
- Alert is silenced.
- Alert is inhibited by another alert.
- Receiver endpoint is unreachable.
- Proxy/TLS configuration problem.
- Namespace is excluded from user workload monitoring.

Checks:

```bash
oc get alertmanagerconfig -A
oc -n payments get alertmanagerconfig payments-routing -o yaml
oc get pods -n openshift-monitoring | grep alertmanager
oc get pods -n openshift-user-workload-monitoring | grep alertmanager
```

Console:

```text
Observe -> Alerting -> Silences
Observe -> Alerting -> Alerts -> alert details
```

---

### Problem 4: Too many alerts fire during rollout

Common cause:

- Rule alerts per pod/container/instance.
- No rollout-aware condition.
- `for` duration too short.

Fixes:

- Aggregate by deployment or app.
- Use `for: 10m` or more.
- Alert on unavailable replicas sustained over time.
- Suppress warning alerts during planned deployment windows if needed.

Bad:

```promql
kube_pod_status_ready{condition="false"} == 1
```

Better:

```promql
kube_deployment_status_replicas_unavailable{namespace="payments"} > 0
```

---

### Problem 5: Rule causes high Prometheus CPU

Possible causes:

- Regex over high-cardinality labels.
- Joins multiplying series.
- No namespace or app filter.
- Expensive histogram query across all namespaces.
- High-frequency evaluation interval.

Fixes:

- Add namespace/app filters.
- Pre-aggregate using recording rules.
- Reduce labels in `sum by`.
- Avoid regex when exact match works.
- Test expression cardinality before rollout.

Useful check:

```promql
count(<your expression>)
```

If `count()` returns thousands of series, be careful.

---

### Problem 6: Alert expression returns no data

Possible causes:

- Metric name wrong.
- Label name/value wrong.
- ServiceMonitor not selecting Service.
- Service not selecting pods.
- Metrics endpoint path or port wrong.
- App does not expose metrics.
- Namespace label enforcement removes cross-namespace data.

Checks:

```bash
oc -n payments get servicemonitor -o yaml
oc -n payments get svc --show-labels
oc -n payments get endpoints
oc -n payments get pods --show-labels
```

PromQL discovery:

```promql
{namespace="payments"}
```

Then narrow down:

```promql
up{namespace="payments"}
```

---

### Problem 7: Alert label routing does not work

Cause:

- Alert does not have expected label.
- AlertRelabelConfig changed or removed label.
- Alertmanager route matcher uses wrong label name or value.
- Namespace routing scope mismatch.

Check labels in alert details from console or Alertmanager UI. Confirm final labels after relabeling, not only labels in PrometheusRule.

---

### Problem 8: Duplicate notifications

Possible causes:

- Same rule deployed twice.
- Same alert name in multiple PrometheusRule objects with same labels.
- Cross-project rule duplicates namespace-local rule.
- Alertmanager grouping insufficient.
- Two receivers match the same alert.

Fixes:

- Search all rules:

```bash
oc get prometheusrule -A -o yaml | grep -n "alert: PaymentsHighErrorRate"
oc -n openshift-monitoring get alertingrule -o yaml | grep -n "alert:"
```

- Add clear ownership labels.
- Improve route tree and grouping.
- Remove duplicate rule definitions.

## 23. Security and multi-tenancy considerations

### 23.1 Alert rules can leak data

Annotations and labels can be sent to external systems. Do not include:

- Secrets
- Tokens
- Passwords
- Customer personal data
- Full request payloads
- Internal credentials
- Sensitive environment values

### 23.2 Namespace isolation

User workload monitoring is designed to respect project boundaries. Avoid disabling namespace label enforcement except for controlled platform namespaces.

### 23.3 RBAC least privilege

Do not give app teams cluster-admin just to create alert rules.

Use:

```bash
oc adm policy add-cluster-role-to-user monitoring-rules-edit <user> -n <namespace>
```

Only grant `monitoring-edit` if the user also needs ServiceMonitor/PodMonitor management.

Only grant `alert-routing-edit` if the user should manage notification routing.

### 23.4 Receiver security

For webhook receivers:

- Use HTTPS.
- Validate certificates.
- Use network policies where possible.
- Avoid embedding secrets directly in visible YAML.
- Store sensitive receiver configs in supported secrets where applicable.
- Ensure egress to external receiver is allowed.

### 23.5 Change control

Platform alert changes should go through review because they can:

- Hide default cluster alerts.
- Page the wrong team.
- Overload monitoring.
- Break incident response workflows.

## 24. Performance and cardinality considerations

### 24.1 Cardinality basics

A time series is uniquely identified by metric name and labels.

Example:

```text
http_requests_total{namespace="payments", pod="api-1", method="GET", path="/api/v1/order/123"}
```

If `path` includes IDs, cardinality explodes.

Alert rules evaluating high-cardinality metrics can:

- Increase Prometheus CPU.
- Increase memory usage.
- Slow queries.
- Generate many alert instances.
- Overwhelm Alertmanager and humans.

### 24.2 Avoid unbounded labels

Do not alert by:

- user ID
- request ID
- raw URL path with IDs
- session ID
- pod UID
- container ID
- dynamic exception message

### 24.3 Aggregate early

Better:

```promql
sum by (namespace, app) (rate(http_requests_total[5m]))
```

Worse:

```promql
rate(http_requests_total[5m])
```

The second may return one series for every pod, path, method, status code, and instance.

### 24.4 Use recording rules for expensive calculations

If a histogram quantile or join is used by multiple alerts and dashboards, precompute service-level series.

### 24.5 Test with count

Before deploying an alert:

```promql
count(<expression>)
```

If count is high, review labels and aggregation.

### 24.6 Alert evaluation cost checklist

- Does the query scan all namespaces?
- Does it use regex on high-cardinality labels?
- Does it join many-to-many?
- Does it include `pod`, `container`, `instance`, `path` unnecessarily?
- Does it evaluate histograms across all workloads?
- Is the rule group too large?
- Can a recording rule reduce repeated work?

## 25. Common interview and real-world questions

### Q1. What is the difference between PrometheusRule and AlertingRule in OpenShift?

`PrometheusRule` is the Prometheus Operator CRD used mainly for user workload alerting and recording rules in user-defined projects. `AlertingRule` is an OpenShift-specific CRD used by cluster administrators to create supported custom alerts based on platform monitoring metrics in `openshift-monitoring`.

### Q2. Why does my PrometheusRule not show in the console?

Check whether user workload monitoring is enabled, the namespace is not excluded, the rule is valid, the UI source filter includes User, and the user has permission to view monitoring rules.

### Q3. What does the `for` field do?

It requires the alert expression to remain true for a specified duration before the alert fires. Before that, the alert is pending.

### Q4. Difference between labels and annotations?

Labels are used for routing, grouping, deduplication, severity, and ownership. Annotations are used for human-readable context such as summary, description, runbook, and dashboard links.

### Q5. How do you reduce alert noise?

Use symptom-based alerts, SLO burn-rate alerts, suitable `for` durations, minimum traffic guards, aggregation, Alertmanager grouping, silences for maintenance, and inhibition for dependent failures.

### Q6. How do you route app team alerts to a team receiver?

Enable alert routing for user-defined projects, grant `alert-routing-edit`, and create an `AlertmanagerConfig` in the same namespace as the app PrometheusRule.

### Q7. Can developers create alerts for their projects?

Yes, if user workload monitoring is enabled and they have roles such as `monitoring-rules-edit` for their namespace. For scraping configuration, they might need `monitoring-edit`.

### Q8. How do you alert on app 5xx errors?

Use a ratio of 5xx request rate over total request rate, aggregate at service level, and add a minimum traffic guard.

```promql
(
  sum(rate(http_requests_total{namespace="payments", code=~"5.."}[5m]))
  /
  sum(rate(http_requests_total{namespace="payments"}[5m]))
) > 0.05
and
sum(rate(http_requests_total{namespace="payments"}[5m])) > 1
```

### Q9. Why should you avoid alerting by pod?

Pod names change, rollouts create churn, and per-pod alerts can create storms. Service or deployment-level alerts are usually better for paging.

### Q10. How do you test alert rules before production?

Validate YAML with server-side dry run, test PromQL in Observe → Metrics, use `promtool check rules` for extracted rule files, and use `promtool test rules` for unit tests.

### Q11. What is Alertmanager inhibition?

Inhibition suppresses notifications for lower-level alerts when a higher-level related alert is firing. Example: suppress pod alerts when the node is down.

### Q12. What is a silence?

A silence suppresses notifications for matching alerts for a specified time. It does not disable rule evaluation.

### Q13. What causes alert storms?

High-cardinality labels, pod-level rules, missing aggregation, duplicate rules, bad Alertmanager grouping, or widespread dependency failures without inhibition.

### Q14. What is a cross-project alert rule?

A rule defined in a configured namespace where namespace label enforcement is disabled, allowing the rule to evaluate across multiple user-defined projects. Use only for controlled platform use cases.

### Q15. How do you modify severity of a default platform alert?

Use `AlertRelabelConfig` in `openshift-monitoring` to replace the `severity` label for matching platform alerts. Review carefully before applying.

## Final senior-admin advice

Do not treat alert rules as simple threshold YAML. Treat them as production code. A good OpenShift alert rule has a stable owner, clear impact, correct severity, tested PromQL, low-cardinality labels, a runbook, and a routing path that reaches the right team. The goal is not to create many alerts. The goal is to create trusted alerts that trigger fast, correct action.
