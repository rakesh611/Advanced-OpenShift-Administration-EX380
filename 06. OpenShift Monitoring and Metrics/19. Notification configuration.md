# OpenShift Monitoring and Metrics: Notification Configuration Deep Dive

**Audience:** Advanced OpenShift Administrators, SREs, Platform Engineers  
**Experience level:** 10+ years Linux / Kubernetes / OpenShift administration  
**Scope:** OpenShift 4.x monitoring stack, aligned with OpenShift / Monitoring Stack for Red Hat OpenShift 4.20 concepts  
**Focus topic:** Notification configuration using Alertmanager, receivers, routes, secrets, user workload alert routing, and operational troubleshooting

---

## 1. What is notification configuration in OpenShift monitoring?

In OpenShift, **notification configuration** means configuring how alerts generated by the monitoring stack are delivered to people or external systems.

A monitoring alert is not useful only because it fires. It becomes operationally useful when it reaches the correct team, at the correct urgency, with enough context, without creating unnecessary noise.

In practical terms, notification configuration answers these questions:

| Question | Example |
|---|---|
| Which alerts should notify someone? | Only `critical` platform alerts should page L1/L2 immediately. |
| Where should alerts go? | Slack, Microsoft Teams, PagerDuty, email, webhook, ticketing system. |
| Who owns the alert? | Platform team, application team, storage team, security team. |
| How often should it repeat? | Every 30 minutes for critical, every 12 hours for warnings. |
| Should resolved alerts be sent? | Yes for PagerDuty, maybe no for noisy Slack channels. |
| How should alerts be grouped? | Group by `cluster`, `namespace`, `alertname`, `severity`. |
| What should be suppressed? | Suppress pod alerts when the whole node is down. |
| How should user application alerts be isolated? | Use `AlertmanagerConfig` per namespace or dedicated user workload Alertmanager. |

OpenShift uses **Prometheus** and **Thanos Ruler** to evaluate rules and send alerts to **Alertmanager**. Alertmanager then performs grouping, de-duplication, routing, silencing, inhibition, and notification delivery.

## 2. High-level alert notification flow

```text
Metrics scraped from cluster/applications
        |
        v
Prometheus / Thanos Ruler evaluates alerting rules
        |
        v
Alert enters pending state if rule condition is true
        |
        v
Alert becomes firing after the rule's `for:` duration
        |
        v
Alertmanager receives firing alert
        |
        +--> De-duplicates repeated alerts
        +--> Groups related alerts
        +--> Applies silences
        +--> Applies inhibition rules
        +--> Matches routing tree
        +--> Sends notification to receiver
                 |
                 +--> PagerDuty
                 +--> Slack
                 +--> Microsoft Teams
                 +--> Email / SMTP
                 +--> Generic webhook
                 +--> Ticketing / ITSM integration
```

Important distinction:

```text
Prometheus / Thanos Ruler decides: "Is something wrong?"
Alertmanager decides: "Who should be notified, how, and when?"
```

## 3. OpenShift monitoring notification components

### 3.1 Core platform monitoring

Core platform monitoring is installed by default in the `openshift-monitoring` namespace.

Main components involved in notification configuration:

| Component | Namespace | Role |
|---|---|---|
| Cluster Monitoring Operator | `openshift-monitoring` | Manages platform monitoring components. |
| Prometheus Operator | `openshift-monitoring` | Manages Prometheus and Alertmanager objects. |
| Prometheus | `openshift-monitoring` | Scrapes platform metrics and evaluates platform alerting rules. |
| Alertmanager | `openshift-monitoring` | Sends platform alert notifications to external receivers. |
| Thanos Querier | `openshift-monitoring` | Query layer for platform and user metrics. |

Platform Alertmanager configuration is stored mainly in:

```text
Namespace: openshift-monitoring
Secret:    alertmanager-main
Key:       alertmanager.yaml
```

You typically configure platform notifications by editing the `alertmanager-main` secret or using the OpenShift web console.

---

### 3.2 User workload monitoring

User workload monitoring is optional and runs in:

```text
openshift-user-workload-monitoring
```

Main components:

| Component | Namespace | Role |
|---|---|---|
| Prometheus Operator | `openshift-user-workload-monitoring` | Manages user workload monitoring CRs. |
| Prometheus user workload | `openshift-user-workload-monitoring` | Scrapes user application metrics. |
| Thanos Ruler | `openshift-user-workload-monitoring` | Evaluates user workload alerting and recording rules. |
| Alertmanager user workload | `openshift-user-workload-monitoring` | Optional dedicated Alertmanager for user-defined alerts. |

User-defined alerts can be routed in two major ways:

1. Through the **main platform Alertmanager**: `alertmanager-main` in `openshift-monitoring`.
2. Through a **dedicated user workload Alertmanager**: `alertmanager-user-workload` in `openshift-user-workload-monitoring`.

For normal multi-team OpenShift clusters, the cleanest approach is usually:

```text
Platform alerts       -> platform SRE receiver
Application alerts    -> app/team-owned receiver by namespace
Security alerts       -> security receiver
Storage alerts        -> storage receiver
Network alerts        -> network/platform receiver
Watchdog alert        -> external dead man's switch receiver
```

## 4. Why notification configuration is not enabled by default

OpenShift shows firing alerts in the web console by default, but external notification delivery is not automatically configured after installation.

That is intentional because OpenShift does not know your organization's escalation model, SMTP details, Slack webhooks, PagerDuty services, Microsoft Teams channels, proxy requirements, or secret management process.

As an advanced administrator, after cluster installation you should treat Alertmanager receiver configuration as a mandatory post-installation hardening step.

A freshly installed production cluster without external Alertmanager receivers has a major operational gap:

```text
Alerts may be firing, but nobody outside the console is notified.
```

## 5. Supported notification receiver types

OpenShift Alertmanager supports multiple receivers. The common enterprise receiver types are:

| Receiver type | Typical use case |
|---|---|
| PagerDuty | Critical paging and on-call escalation. |
| Webhook | Integration with ITSM, ticketing, automation, custom relay, EventBridge, ServiceNow gateway, etc. |
| Email | Non-urgent notifications, compliance mailbox, shared operations mailbox. |
| Slack | Team notification channels and collaboration. |
| Microsoft Teams | Enterprise collaboration channel notification. |

Upstream Alertmanager supports many more integrations depending on the bundled Alertmanager version, but in OpenShift you should always confirm the supported version and configuration schema for your OpenShift release.

```bash

```

```bash
oc -n openshift-monitoring get secret alertmanager-main \
```


```bash
oc exec alertmanager-main-0 -n openshift-monitoring -- \
  amtool config routes show --alertmanager.url http://localhost:9093
```

### 6.2 User-defined alert routing with `AlertmanagerConfig`

For application teams, OpenShift supports namespace-scoped alert routing using:

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
```

This allows developers or app teams with the `alert-routing-edit` role to define routing and receivers for their own project without editing the global platform Alertmanager secret.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
metadata:
  name: payments-alert-routing
  namespace: payments-prod
spec:
  route:
    receiver: payments-webhook
    groupBy: [namespace, alertname, severity]
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 4h
    routes:
    - receiver: payments-critical-webhook
      matchers:
      - name: severity
        value: critical
        matchType: =
  receivers:
  - name: payments-webhook
    webhookConfigs:
    - url: https://alert-router.example.com/teams/payments-warning
      sendResolved: true
  - name: payments-critical-webhook
    webhookConfigs:
    - url: https://alert-router.example.com/teams/payments-critical
      sendResolved: true
```

Apply it:

```bash
oc apply -f payments-alert-routing.yaml
```

Key point:

```text
AlertmanagerConfig routing is namespace-scoped.
An AlertmanagerConfig in namespace `payments-prod` applies only to alerts from that namespace.
```

## 7. Alertmanager configuration structure

A normal Alertmanager configuration contains these major sections:

```yaml
global:
  resolve_timeout: 5m

route:
  receiver: default
  group_by: [cluster, namespace, alertname]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  routes: []

receivers:
- name: default

inhibit_rules: []

time_intervals: []

templates: []
```

### 7.1 `global`

The `global` section defines defaults used by receivers.

Common examples:

```yaml
global:
  resolve_timeout: 5m
  smtp_smarthost: smtp.example.com:587
  smtp_from: alertmanager@example.com
  smtp_auth_username: alertmanager@example.com
  smtp_auth_password_file: /etc/alertmanager/secrets/smtp-auth/password
  slack_api_url_file: /etc/alertmanager/secrets/slack-webhook/url
  http_config:
    proxy_from_environment: true
```

Use `*_file` options wherever possible so that secrets are read from mounted Kubernetes Secrets instead of being embedded directly into `alertmanager.yaml`.

---

### 7.2 `route`

The `route` section defines the routing tree. Every alert enters at the top-level route. Child routes decide where the alert goes based on labels.

Example:

```yaml
route:
  receiver: default
  group_by: [cluster_id, namespace, alertname, severity]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  routes:
  - matchers:
    - 'alertname="Watchdog"'
    receiver: watchdog
    repeat_interval: 2m

  - matchers:
    - 'severity="critical"'
    receiver: platform-pagerduty
    repeat_interval: 30m

  - matchers:
    - 'severity="warning"'
    receiver: platform-slack
    repeat_interval: 12h
```

Route matching is label-based. Common alert labels include:

| Label | Meaning |
|---|---|
| `alertname` | Name of the alert. |
| `severity` | Alert importance such as `warning`, `critical`, `info`. |
| `namespace` | Namespace related to the alert. |
| `pod` | Pod related to the alert. |
| `node` | Node related to the alert. |
| `service` | Service/application label. |
| `team` | Ownership label if added in alert rule. |
| `openshift_io_alert_source` | Useful for separating platform and user-defined alerts when using shared Alertmanager. |

---

### 7.3 `receivers`

Receivers are named destinations.

Example:

```yaml
receivers:
- name: default

- name: platform-slack
  slack_configs:
  - channel: '#ocp-platform-alerts'
    send_resolved: true
    title: '[{{ .Status | toUpper }}] {{ .CommonLabels.alertname }}'
    text: >-
      Cluster: {{ .CommonLabels.cluster_id }}
      Severity: {{ .CommonLabels.severity }}
      Namespace: {{ .CommonLabels.namespace }}
      Summary: {{ .CommonAnnotations.summary }}

- name: platform-pagerduty
  pagerduty_configs:
  - routing_key_file: /etc/alertmanager/secrets/pagerduty-platform/routing-key
    send_resolved: true
    severity: '{{ .CommonLabels.severity }}'

- name: platform-email
  email_configs:
  - to: openshift-platform@example.com
    from: alertmanager@example.com
    smarthost: smtp.example.com:587
    auth_username: alertmanager@example.com
    auth_password_file: /etc/alertmanager/secrets/smtp-auth/password
    send_resolved: true
```

---

### 7.4 `inhibit_rules`

Inhibition suppresses lower-level alerts when a higher-level alert is already firing.

Example scenario:

```text
NodeNotReady is firing.
Many PodNotReady alerts from the same node also fire.
```

Without inhibition, your team receives many duplicate symptoms. With inhibition, you notify on the root-level condition and mute dependent symptoms.

Example:

```yaml
inhibit_rules:
- source_matchers:
  - 'alertname="NodeNotReady"'
  - 'severity="critical"'
  target_matchers:
  - 'severity="warning"'
  equal:
  - node
```

Meaning:

```text
If a critical NodeNotReady alert exists for node X,
then mute warning alerts that also have node X.
```

Do not overuse inhibition. Bad inhibition rules can hide real incidents.

---

### 7.5 `time_intervals`

Time intervals allow routes to be active or muted at specific times.

Example: warnings to Slack only during business hours in India.

```yaml
time_intervals:
- name: india-business-hours
  time_intervals:
  - times:
    - start_time: '09:00'
      end_time: '18:00'
    weekdays: ['monday:friday']
    location: 'Asia/Kolkata'

route:
  receiver: default
  routes:
  - matchers:
    - 'severity="warning"'
    receiver: platform-slack
    active_time_intervals:
    - india-business-hours
```

For production platform alerts, avoid muting critical infrastructure alerts based only on office hours. Use on-call escalation instead.

## 8. Key timing parameters

### 8.1 `group_wait`

How long Alertmanager waits before sending the first notification for a new group.

Example:

```yaml
group_wait: 30s
```

Operational impact:

- Too low: faster notifications but more noise.
- Too high: fewer duplicate messages but slower incident awareness.

Recommended starting point:

```yaml
group_wait: 30s
```

For very critical paging routes:

```yaml
group_wait: 10s
```

---

### 8.2 `group_interval`

How long Alertmanager waits before sending another notification about new alerts in an already-notified group.

Example:

```yaml
group_interval: 5m
```

If a node outage creates many alerts, Alertmanager sends the first grouped notification, then waits `group_interval` before sending updates about new alerts in the same group.

Recommended starting point:

```yaml
group_interval: 5m
```

---

### 8.3 `repeat_interval`

How long Alertmanager waits before repeating a notification for an alert that is still firing.

Example:

```yaml
repeat_interval: 12h
```

Good production pattern:

| Alert type | Repeat interval |
|---|---:|
| Critical platform alert | `30m` to `2h` |
| Warning platform alert | `6h` to `24h` |
| Watchdog | `1m` to `5m` |
| Application warning | `4h` to `24h` |
| Informational alert | Usually no external notification |

## 9. Watchdog alert and dead man's switch

OpenShift monitoring includes a `Watchdog` alert that fires continuously.

This is intentional.

The Watchdog alert is used to verify that the whole alert notification pipeline is alive:

```text
Prometheus rule evaluation -> Alertmanager -> receiver -> external notification service
```

Recommended pattern:

```yaml
route:
  receiver: default
  routes:
  - matchers:
    - 'alertname="Watchdog"'
    receiver: watchdog
    repeat_interval: 2m

receivers:
- name: watchdog
  webhook_configs:
  - url_file: /etc/alertmanager/secrets/deadmanssnitch/url
    send_resolved: true
```

Your external receiver should notify you when it **stops receiving** the Watchdog alert.

Do not remove Watchdog routing in production. If you do not use an external dead man's switch, at least route it to a low-noise health-check webhook.

## 11. Enabling user-defined alert routing with the platform Alertmanager

This allows application teams to create `AlertmanagerConfig` resources in their namespaces, while notifications are still delivered by the main platform Alertmanager.


```bash
  -n payments-prod --as rakesh
```


## 12. Enabling a dedicated user workload Alertmanager

In larger clusters, use a separate Alertmanager for user-defined projects to isolate application alert volume from platform alerting.

Edit:

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Add:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    alertmanager:
      enabled: true
      enableAlertmanagerConfig: true
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get alertmanager
oc -n openshift-user-workload-monitoring get pods | grep alertmanager
```

Expected:

```text
alertmanager-user-workload-0
alertmanager-user-workload-1
```

When to use a dedicated user workload Alertmanager:

| Scenario | Recommendation |
|---|---|
| Small cluster, few teams | Use platform Alertmanager with `AlertmanagerConfig`. |
| Many teams and many app alerts | Dedicated user workload Alertmanager. |
| Strong platform/app separation required | Dedicated user workload Alertmanager. |
| Central NOC owns all alerts | Platform Alertmanager may be enough. |
| App teams own their routing fully | Dedicated user workload Alertmanager is cleaner. |

## 13. Platform notification configuration example: Slack + PagerDuty + Watchdog

Create secrets first.

### 13.1 Create Slack webhook secret

```bash
oc -n openshift-monitoring create secret generic slack-platform-webhook \
  --from-literal=url='https://hooks.slack.com/services/REPLACE/REPLACE/REPLACE'
```

### 13.2 Create PagerDuty routing key secret

```bash
oc -n openshift-monitoring create secret generic pagerduty-platform \
  --from-literal=routing-key='REPLACE_WITH_PAGERDUTY_ROUTING_KEY'
```

### 13.3 Mount secrets into Alertmanager

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Add:

```yaml
apiVersion: v1

  name: cluster-monitoring-config
  namespace: openshift-monitoring

  config.yaml: |
    alertmanagerMain:
      secrets:
      - slack-platform-webhook
```

```text
/etc/alertmanager/secrets/slack-platform-webhook/url
/etc/alertmanager/secrets/pagerduty-platform/routing-key
```

```bash
oc -n openshift-monitoring get secret alertmanager-main \

cp alertmanager.yaml alertmanager.yaml.$(date +%F-%H%M%S).bak
```

```yaml
global:
  resolve_timeout: 5m
  http_config:
    proxy_from_environment: true

route:
  receiver: default
  group_by: [cluster_id, namespace, alertname, severity]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  routes:
  - matchers:
    - 'alertname="Watchdog"'
    receiver: watchdog
    repeat_interval: 2m

  - matchers:
    - 'severity="critical"'
    receiver: platform-pagerduty
    group_wait: 10s
    repeat_interval: 30m

  - matchers:
    - 'severity="warning"'
    receiver: platform-slack
    repeat_interval: 12h

receivers:
- name: default

- name: watchdog
  webhook_configs:
  - url: https://deadmansswitch.example.com/openshift-platform-watchdog
    send_resolved: true

- name: platform-pagerduty
  pagerduty_configs:
  - routing_key_file: /etc/alertmanager/secrets/pagerduty-platform/routing-key
    send_resolved: true
    severity: '{{ .CommonLabels.severity }}'
    description: '{{ .CommonLabels.alertname }} on {{ .CommonLabels.cluster_id }}'
    details:
      cluster: '{{ .CommonLabels.cluster_id }}'
      namespace: '{{ .CommonLabels.namespace }}'
      alertname: '{{ .CommonLabels.alertname }}'
      severity: '{{ .CommonLabels.severity }}'
      summary: '{{ .CommonAnnotations.summary }}'

- name: platform-slack
  slack_configs:
  - api_url_file: /etc/alertmanager/secrets/slack-platform-webhook/url

    send_resolved: true
```


## 14. Email notification configuration

Email requires an external SMTP server.

Create SMTP password secret:

```bash
oc -n openshift-monitoring create secret generic smtp-auth \
  --from-literal=password='REPLACE_WITH_SMTP_PASSWORD'
```

Mount it:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    alertmanagerMain:
      secrets:
      - smtp-auth
```

Receiver example:

```yaml
global:
  smtp_smarthost: smtp.example.com:587
  smtp_from: alertmanager@example.com
  smtp_hello: alertmanager.example.com
  smtp_auth_username: alertmanager@example.com
  smtp_auth_password_file: /etc/alertmanager/secrets/smtp-auth/password
  smtp_require_tls: true

route:
  receiver: platform-email
  group_by: [cluster_id, namespace, alertname]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h

receivers:
- name: platform-email
  email_configs:
  - to: openshift-platform@example.com
    send_resolved: true
    headers:
      subject: '[{{ .Status | toUpper }}] {{ .CommonLabels.alertname }} - {{ .CommonLabels.severity }}'
    html: |-
      <b>Cluster:</b> {{ .CommonLabels.cluster_id }}<br>
      <b>Alert:</b> {{ .CommonLabels.alertname }}<br>
      <b>Severity:</b> {{ .CommonLabels.severity }}<br>
      <b>Namespace:</b> {{ .CommonLabels.namespace }}<br>
      <b>Summary:</b> {{ .CommonAnnotations.summary }}<br>
```

Common email issues:

| Symptom | Likely cause |
|---|---|
| No email received | SMTP firewall or relay denied. |
| Authentication failed | Wrong username/password or unsupported auth method. |
| TLS error | CA trust or SMTP STARTTLS issue. |
| Repeated send failures | Smarthost unavailable or DNS issue. |
| Email accepted but not delivered | Mail gateway spam/security rule. |

## 15. Webhook notification configuration

Webhook is the most flexible receiver. Use it for:

- ServiceNow
- Jira
- Custom alert router
- Event-driven automation
- ITSM integration
- Incident enrichment pipeline
- ChatOps bridge
- NOC dashboard

Example:

```yaml
route:
  receiver: noc-webhook
  group_by: [cluster_id, namespace, alertname, severity]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

receivers:
- name: noc-webhook
  webhook_configs:
  - url: https://alerts.example.com/api/v1/openshift
    send_resolved: true
    http_config:
      proxy_from_environment: true
```

Webhook payload includes alert labels, annotations, status, group labels, common labels, receiver, and external URL.

Good webhook gateway behavior:

- Validate payload signature or source IP.
- Return 2xx quickly.
- Queue downstream processing asynchronously.
- Deduplicate using fingerprint or group key.
- Enrich with runbook links.
- Forward critical incidents to paging system.
- Forward warnings to ticket or chat.

Bad webhook behavior:

- Takes more than the Alertmanager timeout.
- Returns 500 for transient downstream errors.
- Has no idempotency.
- Creates duplicate tickets for same alert group.
- Drops resolved notifications.

## 16. Microsoft Teams notification configuration

OpenShift 4.20 documentation lists Microsoft Teams as a supported external notification receiver type. Exact receiver syntax can vary depending on the Alertmanager version included with your OpenShift release.

Before configuring Teams directly, confirm supported fields:

```bash
oc -n openshift-monitoring exec alertmanager-main-0 -c alertmanager -- \
  alertmanager --version
```

Then check supported Alertmanager configuration schema for that version.

Common enterprise pattern:

```text
Alertmanager -> generic webhook receiver -> internal alert router -> Microsoft Teams
```

This gives more control over formatting, retries, proxy, authentication, and Teams workflow changes.

If your Alertmanager version supports direct Teams receiver configuration, keep Teams receivers separate by team and severity:

```text
platform-critical-teams
platform-warning-teams
app-payments-teams
app-security-teams
```

Do not send every alert to a single Teams channel. It becomes noise very quickly.

## 17. User application alert + notification example

### 17.1 Application alert rule

Create a namespace:

```bash
oc new-project payments-prod
```

Create a `PrometheusRule`:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: payments-alert-rules
  namespace: payments-prod
spec:
  groups:
  - name: payments.rules
    rules:
    - alert: PaymentsHighErrorRate
      expr: |
        (
          sum(rate(http_requests_total{namespace="payments-prod",code=~"5.."}[5m]))
          /
          sum(rate(http_requests_total{namespace="payments-prod"}[5m]))
        ) > 0.05
      for: 10m
      labels:
        severity: critical
        team: payments
        service: payments-api
      annotations:
        summary: "Payments API 5xx error rate is above 5%"
        description: "Payments API has high server-side error rate for more than 10 minutes."
        runbook_url: "https://runbooks.example.com/payments/high-error-rate"
```

Apply:

```bash
oc apply -f payments-alert-rules.yaml
```

### 17.2 Team-owned routing

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
metadata:
  name: payments-routing
  namespace: payments-prod
spec:
  route:
    receiver: payments-warning
    groupBy: [namespace, alertname, severity, service]
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 4h
    routes:
    - receiver: payments-critical
      matchers:
      - name: severity
        value: critical
        matchType: =
      repeatInterval: 30m
  receivers:
  - name: payments-warning
    webhookConfigs:
    - url: https://alerts.example.com/team/payments/warning
      sendResolved: true
  - name: payments-critical
    webhookConfigs:
    - url: https://alerts.example.com/team/payments/critical
      sendResolved: true
```

Apply:

```bash
oc apply -f payments-routing.yaml
```

Verify:

```bash
oc -n payments-prod get prometheusrule
oc -n payments-prod get alertmanagerconfig
oc -n payments-prod describe alertmanagerconfig payments-routing
```

## 18. Separating platform alerts and user-defined alerts in shared Alertmanager

When platform alerts and user-defined alerts share `alertmanager-main`, use labels to route them differently.

OpenShift adds the `openshift_io_alert_source="platform"` label to platform alerts.

Example routing pattern:

```yaml
route:
  receiver: default
  group_by: [cluster_id, namespace, alertname, severity]
  routes:
  - matchers:
    - 'openshift_io_alert_source="platform"'
    receiver: platform-sre

  - matchers:
    - 'openshift_io_alert_source!="platform"'
    receiver: user-workload-default
```

Use this when:

```text
Same Alertmanager handles both OpenShift platform alerts and application alerts.
```

Do not rely only on `namespace` to detect platform alerts. Some user alerts may come from namespaces with names that look platform-like, and some platform alerts may not map cleanly to an application namespace.

## 19. Alert routing design patterns for production

### 19.1 Severity-based routing

```yaml
routes:
- matchers:
  - 'severity="critical"'
  receiver: pagerduty-critical
- matchers:
  - 'severity="warning"'
  receiver: slack-warning
- matchers:
  - 'severity="info"'
  receiver: null-receiver
```

Use this as the base layer, but do not stop there. Severity alone is not ownership.

---

### 19.2 Team-based routing

```yaml
routes:
- matchers:
  - 'team="platform"'
  receiver: platform-team
- matchers:
  - 'team="storage"'
  receiver: storage-team
- matchers:
  - 'team="network"'
  receiver: network-team
```

Best for mature organizations where alert rules include ownership labels.

---

### 19.3 Namespace-based routing

```yaml
routes:
- matchers:
  - 'namespace=~"payments-.*"'
  receiver: payments-team
- matchers:
  - 'namespace=~"identity-.*"'
  receiver: identity-team
```

Useful when app ownership maps cleanly to namespaces.

---

### 19.4 Service-based routing

```yaml
routes:
- matchers:
  - 'service="api-gateway"'
  receiver: api-platform-team
- matchers:
  - 'service="mysql"'
  receiver: database-team
```

Good when several teams share namespaces but own different services.

---

### 19.5 Maintenance-window routing

Use `time_intervals` for planned low-priority noise, but prefer silences for actual maintenance.

```yaml
time_intervals:
- name: weekend-muted
  time_intervals:
  - weekdays: ['saturday', 'sunday']
    location: 'Asia/Kolkata'

route:
  receiver: default
  routes:
  - matchers:
    - 'severity="info"'
    receiver: null-receiver
    mute_time_intervals:
    - weekend-muted
```

Critical alerts should normally not be muted automatically during weekends.

## 20. Null receiver pattern

A null receiver intentionally drops notifications.

```yaml
receivers:
- name: null-receiver
```

Example use:

```yaml
routes:
- matchers:
  - 'severity="info"'
  receiver: null-receiver
```

Use carefully. Do not silently drop alerts that should be fixed at the rule level.

Good use cases:

- Informational alerts visible in console but not external notification.
- Test alerts.
- Known noisy alert while waiting for permanent rule correction.

Bad use cases:

- Hiding production incidents.
- Avoiding ownership decisions.
- Masking poor alert rule quality.

## 22. Secrets and secure credentials

Never store real credentials directly in Git or plain `alertmanager.yaml`.

Use Kubernetes Secrets and mount them into Alertmanager.

### 22.1 Platform Alertmanager secret mounting

Create secret:

```bash
oc -n openshift-monitoring create secret generic alert-webhook-token \
  --from-literal=token='REPLACE_TOKEN'
```

```yaml
apiVersion: v1

  name: cluster-monitoring-config
  namespace: openshift-monitoring

  config.yaml: |
    alertmanagerMain:
      secrets:
```

Use in Alertmanager:

```yaml
receivers:
- name: secure-webhook
  webhook_configs:
  - url: https://alerts.example.com/api/v1/openshift

        type: Bearer
```

## 23. Proxy configuration

Many enterprise OpenShift clusters use cluster-wide proxies. Notification receivers might need outbound internet access through that proxy.

Alertmanager supports:

```yaml
global:
  http_config:
    proxy_from_environment: true
```

Or per receiver:

```yaml
receivers:
- name: external-webhook
  webhook_configs:
  - url: https://alerts.example.com/openshift
    http_config:
      proxy_from_environment: true
```

Troubleshooting proxy issues:

```bash
oc -n openshift-monitoring exec alertmanager-main-0 -c alertmanager -- env | grep -i proxy
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager | grep -i proxy
```

Common symptoms:

| Symptom | Cause |
|---|---|
| `connection refused` | Receiver or proxy not reachable. |
| `i/o timeout` | Firewall, proxy, DNS, or route issue. |
| `x509: certificate signed by unknown authority` | Private CA not trusted. |
| HTTP 407 | Proxy authentication required. |
| HTTP 403 | Receiver rejected source or token. |

## 24. External Alertmanager integration

Some organizations centralize alerting across multiple clusters.

Pattern:

```text
Cluster A Prometheus -> Local Alertmanager and/or External Alertmanager
Cluster B Prometheus -> Local Alertmanager and/or External Alertmanager
Cluster C Prometheus -> Local Alertmanager and/or External Alertmanager
```

Core platform external Alertmanager configuration is added under `prometheusK8s.additionalAlertmanagerConfigs`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      additionalAlertmanagerConfigs:
      - scheme: https
        pathPrefix: /
        timeout: "30s"
        apiVersion: v1
        bearerToken:
          name: alertmanager-bearer-token
          key: token
        tlsConfig:
          key:
            name: alertmanager-tls
            key: tls.key
          cert:
            name: alertmanager-tls
            key: tls.crt
          ca:
            name: alertmanager-tls
            key: tls.ca
        staticConfigs:
        - external-alertmanager1.example.com
        - external-alertmanager2.example.com
```

User workload external Alertmanager can be configured under either `prometheus` or `thanosRuler` in `user-workload-monitoring-config`.

Example for Thanos Ruler:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    thanosRuler:
      additionalAlertmanagerConfigs:
      - scheme: https
        pathPrefix: /
        timeout: "30s"
        apiVersion: v1
        bearerToken:
          name: alertmanager-bearer-token
          key: token
        staticConfigs:
        - central-alertmanager.example.com
```

Advanced guidance:

- Keep local Alertmanager enabled unless you have a mature central alerting design.
- Add external labels such as environment, region, and cluster identifier.
- Ensure all clusters use unique labels for cluster identity.
- Test failure modes when central Alertmanager is unavailable.
- Avoid duplicate notifications if both local and external Alertmanager send to the same receiver.

## 25. External labels for better notifications

External labels add metadata to alerts.

Example:

```yaml
apiVersion: v1

    prometheusK8s:
```

```text

Cluster: ocp-prod-delhi-01
Region: india-north
Environment: prod
Severity: critical
```

## 26. Change management process for production Alertmanager

For production clusters, never directly edit notification configuration without backup and validation.

Recommended workflow:

```bash
# 1. Backup current config
oc -n openshift-monitoring get secret alertmanager-main \
  --template='{{ index .data "alertmanager.yaml" }}' | base64 --decode \
  > alertmanager.yaml.$(date +%F-%H%M%S).bak

# 2. Extract working copy
cp alertmanager.yaml.$(date +%F-%H%M%S).bak alertmanager.yaml

# 3. Edit configuration
vi alertmanager.yaml

# 4. Validate locally if amtool is available
amtool check-config alertmanager.yaml

# 5. Apply
oc -n openshift-monitoring create secret generic alertmanager-main \
  --from-file=alertmanager.yaml \
  --dry-run=client -o yaml | \
  oc -n openshift-monitoring replace -f -

# 6. Verify route tree
oc exec alertmanager-main-0 -n openshift-monitoring -- \
  amtool config routes show --alertmanager.url http://localhost:9093

# 7. Check logs
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=100
```

Better GitOps approach:

```text
Git repo -> encrypted secrets -> CI validation -> Argo CD sync -> OpenShift monitoring config
```

Use Sealed Secrets, External Secrets Operator, Vault, or your approved secret management tool for sensitive values.

## 28. Troubleshooting notification configuration

### 28.1 Alert is firing in console but no external notification

Check:

```bash
oc -n openshift-monitoring get secret alertmanager-main
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=200
oc exec alertmanager-main-0 -n openshift-monitoring -- \
  amtool config routes show --alertmanager.url http://localhost:9093
```

Possible causes:

| Cause | Fix |
|---|---|
| Alert does not match route | Check labels and matchers. |
| Receiver name mismatch | Ensure route receiver exists in `receivers`. |
| Alert is silenced | Check Alertmanager silences. |
| Alert is inhibited | Check `inhibit_rules`. |
| Receiver URL blocked | Check firewall/proxy/DNS. |
| Invalid secret path | Verify secret mounted under `/etc/alertmanager/secrets`. |
| Config rejected | Check Alertmanager logs. |
| `send_resolved` expected but disabled | Set `send_resolved: true`. |

---

### 28.2 Alertmanager config not applied

Check operator and pod status:

```bash
oc -n openshift-monitoring get pods
oc -n openshift-monitoring get secret alertmanager-main -o yaml
oc -n openshift-monitoring logs deploy/cluster-monitoring-operator --tail=200
```

Check Alertmanager logs:

```bash
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=200
```

Look for:

```text
Loading configuration file failed
invalid YAML
unknown field
receiver not found
secret not mounted
```

---

### 28.3 User `AlertmanagerConfig` not working

Check prerequisites:

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config -o yaml
oc -n openshift-user-workload-monitoring get configmap user-workload-monitoring-config -o yaml
oc -n payments-prod get alertmanagerconfig
oc -n payments-prod describe alertmanagerconfig payments-routing
```

Check RBAC:

```bash
oc auth can-i create alertmanagerconfig.monitoring.coreos.com \
  -n payments-prod --as <user>
```

Check namespace scoping:

```text
AlertmanagerConfig and PrometheusRule must be in the same namespace for namespace-scoped user-defined routing.
```

Check that user workload monitoring is enabled:

```bash
oc -n openshift-user-workload-monitoring get pods
```

---

### 28.4 Slack notifications not arriving

Checklist:

```bash
oc -n openshift-monitoring exec alertmanager-main-0 -c alertmanager -- \
  cat /etc/alertmanager/secrets/slack-platform-webhook/url
```

Do not print real secrets in shared terminals or recorded sessions.

Check:

- Webhook URL is correct.
- Slack app/webhook is active.
- Receiver uses `api_url` or `api_url_file` correctly.
- Channel exists and webhook has permission.
- Proxy allows outbound HTTPS.
- Alert matches Slack route.
- Alert is not silenced or inhibited.

---

### 28.5 PagerDuty incidents not created

Check:

- Routing key is correct.
- PagerDuty integration type matches Alertmanager integration.
- Alert severity route is matching.
- PagerDuty service is not in maintenance/suppressed state.
- `send_resolved` behavior matches expectation.
- Alertmanager logs show successful sends.

Useful command:

```bash
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager | grep -i pager
```

### 28.6 Email not sent

Check network:

```bash
oc -n openshift-monitoring debug pod/alertmanager-main-0 -- chroot /host bash
```

Or use an allowed troubleshooting pod with network tools.

Check from inside a test pod:

```bash
oc run smtp-test -n openshift-monitoring --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Then test DNS and TCP connectivity if tools are available:

```bash

```

Common problem in minimal images: `nc` or `telnet` may not be installed. Use `curl -v telnet://host:port`, install tools in a debug image if allowed, or use a purpose-built network troubleshooting image approved by your organization.

## 29. Important best practices

### 29.1 Do not page on symptoms if root cause alert exists

Bad:

```text
Page for every PodRestarting, PodNotReady, ContainerOOMKilled, DeploymentUnavailable.
```

Better:

```text
Page only when customer impact or platform risk is clear.
Use warnings for symptoms and inhibition for dependent alerts.
```

---

### 29.2 Every alert should have an owner

Add labels:

```yaml
labels:
  severity: critical
  team: platform
  service: ingress
```

Without ownership labels, routing becomes fragile and manual.

---

### 29.3 Every actionable alert should have a runbook

Add:

```yaml
annotations:
  runbook_url: https://runbooks.example.com/openshift/router-down
```

A notification without a runbook often becomes a human escalation loop.

---

### 29.4 Keep platform and app alert ownership separate

Platform team owns:

- API server availability
- etcd health
- node readiness
- ingress/router health
- storage operators
- monitoring stack health
- cluster operators
- authentication/oauth
- machine config rollout

Application teams own:

- App latency
- App error rate
- App business metrics
- Queue depth
- App-specific SLO burn alerts
- Namespace resource exhaustion

---

### 29.5 Use different receivers for warning and critical

Bad:

```text
All alerts -> one Slack channel
```

Better:

```text
critical -> PagerDuty / on-call
warning  -> Slack / Teams / ticket
info     -> console only or low-noise channel
```

---

### 29.6 Avoid alert fatigue

Alert fatigue happens when operators receive too many non-actionable alerts.

Fix by:

- Improving alert rules.
- Increasing `for:` durations.
- Grouping alerts properly.
- Adding inhibition rules.
- Routing by ownership.
- Dropping informational notifications.
- Using silences for planned maintenance.
- Creating runbooks.
- Reviewing noisy alerts every sprint/month.

## 30. Production-ready routing example

```yaml
global:
  resolve_timeout: 5m
  http_config:
    proxy_from_environment: true

route:
  receiver: default
  group_by: [cluster_id, namespace, alertname, severity]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  routes:
  - matchers:
    - 'alertname="Watchdog"'
    receiver: watchdog
    repeat_interval: 2m

  - matchers:
    - 'openshift_io_alert_source="platform"'
    receiver: platform-default
    routes:
    - matchers:
      - 'severity="critical"'
      receiver: platform-critical
      group_wait: 10s
      repeat_interval: 30m
    - matchers:
      - 'severity="warning"'
      receiver: platform-warning
      repeat_interval: 12h

  - matchers:
    - 'openshift_io_alert_source!="platform"'
    receiver: user-workload-default
    routes:
    - matchers:
      - 'severity="critical"'
      receiver: app-critical
      repeat_interval: 1h
    - matchers:
      - 'severity="warning"'
      receiver: app-warning
      repeat_interval: 12h

receivers:
- name: default

- name: watchdog
  webhook_configs:
  - url: https://deadmansswitch.example.com/openshift/watchdog
    send_resolved: true

- name: platform-default
  slack_configs:
  - api_url_file: /etc/alertmanager/secrets/slack-platform-webhook/url
    channel: '#ocp-platform-alerts'
    send_resolved: true

- name: platform-critical
  pagerduty_configs:
  - routing_key_file: /etc/alertmanager/secrets/pagerduty-platform/routing-key
    send_resolved: true
    severity: critical

- name: platform-warning
  slack_configs:
  - api_url_file: /etc/alertmanager/secrets/slack-platform-webhook/url
    channel: '#ocp-platform-warnings'
    send_resolved: true

- name: user-workload-default
  webhook_configs:
  - url: https://alerts.example.com/app/default
    send_resolved: true

- name: app-critical
  webhook_configs:
  - url: https://alerts.example.com/app/critical
    send_resolved: true

- name: app-warning
  webhook_configs:
  - url: https://alerts.example.com/app/warning
    send_resolved: true

inhibit_rules:
- source_matchers:
  - 'alertname="NodeNotReady"'
  - 'severity="critical"'
  target_matchers:
  - 'severity="warning"'
  equal:
  - node
```

## 32. Common interview / real-world questions

### Q1. Why is my alert visible in OpenShift console but not sent to Slack?

Because console visibility and external notification delivery are separate. The alert can be firing in Prometheus/Alertmanager, but no route may match it, the receiver may not be configured, the Slack webhook may be invalid, the alert may be silenced/inhibited, or outbound network/proxy may be blocking delivery.

### Q2. Where is platform Alertmanager configuration stored?

```text
openshift-monitoring / secret / alertmanager-main / alertmanager.yaml
```

### Q3. How do application teams configure their own routing?

Enable user workload monitoring and user-defined alert routing, grant `alert-routing-edit` in the project, then let them create `AlertmanagerConfig` resources.

### Q4. What is the difference between silence and inhibition?

A **silence** is manually or automatically created for a matcher and time range, usually for maintenance.  
An **inhibition rule** is permanent logic that suppresses target alerts when a source alert is firing.

### Q5. What is the safest way to store webhook tokens?

Use Kubernetes Secrets mounted into Alertmanager and reference them with `*_file` or appropriate `credentials_file` fields. Do not commit real tokens in YAML.

### Q6. Why should Watchdog fire continuously?

Because it verifies that the alert pipeline is alive. External dead man's switch systems alert you when Watchdog stops arriving.

### Q7. Should user app alerts go to platform on-call?

Usually no. Platform on-call should own platform health. Application teams should own app-level SLO, error rate, latency, and business alerts. Shared NOC visibility is fine, but ownership must be clear.

```bash
# Grant alert routing edit permission
oc -n <namespace> adm policy add-role-to-user alert-routing-edit <user>

# Check user permission
oc auth can-i create alertmanagerconfig.monitoring.coreos.com -n <namespace> --as <user>

# List AlertmanagerConfig resources
oc get alertmanagerconfig -A
```

## 34. Summary

Notification configuration is one of the most important Day-2 responsibilities in OpenShift monitoring.

For a production-grade OpenShift environment, you should design notification configuration around:

- Clear platform vs application alert ownership.
- Correct receiver types for urgency.
- Secure secret handling.
- Strong routing labels.
- Watchdog-based pipeline monitoring.
- Inhibition for dependency noise reduction.
- Namespace-scoped `AlertmanagerConfig` for app teams.
- Dedicated user workload Alertmanager where separation is required.
- GitOps-controlled, validated, and reviewed configuration changes.

The goal is not to send more alerts. The goal is to send the **right alert** to the **right team** at the **right time** with enough context to resolve the issue quickly.
