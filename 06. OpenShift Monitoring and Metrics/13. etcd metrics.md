## 1. Executive Summary

In OpenShift, **etcd is the source of truth for the Kubernetes control plane**. Every object state that the API server persists, such as Pods, Deployments, Secrets, ConfigMaps, Routes, RBAC objects, Nodes, Operators, and CRDs, ultimately depends on etcd health.

For an experienced administrator, etcd metrics are not just "another monitoring topic". They are the fastest way to understand whether the cluster control plane is healthy, overloaded, unstable, disk-bound, network-bound, or approaching a dangerous state such as quorum loss or backend quota pressure.

The most important etcd metrics for OpenShift operations are:

| Area | Key Metrics | What They Tell You |
|---|---|---|
| Leadership | `etcd_server_has_leader`, `etcd_server_is_leader`, `etcd_server_leader_changes_seen_total` | Whether the cluster has stable quorum and leadership |
| Disk WAL latency | `etcd_disk_wal_fsync_duration_seconds_bucket` | How long Raft WAL fsync takes; high values directly affect control plane stability |
| Backend commit latency | `etcd_disk_backend_commit_duration_seconds_bucket` | How long backend database commits take |
| Peer network latency | `etcd_network_peer_round_trip_time_seconds_bucket` | How fast members replicate requests between each other |
| Proposal health | `etcd_server_proposals_pending`, `etcd_server_proposals_failed_total`, `etcd_server_proposals_committed_total`, `etcd_server_proposals_applied_total` | Whether Raft proposals are flowing or stuck |
| Database size | `etcd_mvcc_db_total_size_in_bytes`, `etcd_mvcc_db_total_size_in_use_in_bytes`, `etcd_server_quota_backend_bytes` | Whether etcd is growing, fragmented, or near quota |
| Availability target | `up{job="etcd"}` and OpenShift ClusterOperator metrics | Whether Prometheus can scrape etcd and whether the etcd operator reports healthy |

A practical senior-admin rule:

> If the OpenShift API feels slow, new pods are stuck, routes are delayed, Operators are degraded, or authentication looks random, check etcd leader changes, WAL fsync p99, backend commit p99, peer RTT p99, and proposal pending count before chasing application-level symptoms.

## 2. Why etcd Metrics Matter in OpenShift

### 2.1 etcd is the control plane database

OpenShift inherits Kubernetes' control-plane model. The API server is the front door, but etcd is the persistent key-value store behind it. The API server validates requests, admission controllers mutate or deny them, and then object state is persisted to etcd.

Examples of objects stored in etcd:

- Namespace and project objects
- Deployments, ReplicaSets, Pods, Services, Routes, Ingresses
- ConfigMaps and Secrets
- RBAC objects: Roles, RoleBindings, ClusterRoles, ClusterRoleBindings
- Operator custom resources
- MachineConfig and ClusterVersion state
- Node lease and status-related state
- CRDs and custom resource instances

When etcd is slow, OpenShift does not usually fail in one obvious place. Instead, you see distributed symptoms:

- `oc get pods` is slow or times out.
- New pods stay Pending longer than expected.
- Operators become `Progressing=True` or `Degraded=True`.
- The console loads slowly.
- Authentication and OAuth operations feel delayed.
- Webhooks time out.
- Controllers repeatedly retry reconciliation.
- API server request latency increases.
- Cluster upgrade prechecks or payload rollout may become unstable.

### 2.2 etcd is sensitive to disk and network

etcd uses the Raft consensus algorithm. For a write to be committed, it must be written to the leader's log and replicated to a majority of members. That means etcd performance is strongly tied to:

- WAL fsync latency
- Backend commit latency
- Peer network round-trip time
- Control-plane node CPU saturation
- Control-plane node memory pressure
- Database size and fragmentation
- Stability of the leader election process

For production OpenShift, etcd should run on low-latency SSD or NVMe-backed storage, not slow network storage or disks shared with noisy workloads.

## 3. OpenShift etcd Architecture Refresher

### 3.1 Default topology

A standard highly available OpenShift cluster normally has three control-plane nodes. Each control-plane node runs an etcd member as a static pod in the `openshift-etcd` namespace.

Typical layout:

```text
control-plane-0  -> etcd member 0
control-plane-1  -> etcd member 1
control-plane-2  -> etcd member 2
```

The majority quorum for a 3-member etcd cluster is 2. This means:

- 1 member can fail and the cluster can still operate.
- 2 members down means quorum loss.
- During quorum loss, etcd cannot commit writes.
- If etcd cannot commit writes, the Kubernetes API server cannot reliably persist state changes.

### 3.2 etcd static pods

In OpenShift 4.x, many control-plane components run as static pods managed by operators and rendered pod manifests on the control-plane nodes.

For etcd:

```bash
oc -n openshift-etcd get pods -l k8s-app=etcd -o wide
```

Typical output pattern:

```text
NAME                                      READY   STATUS    NODE
etcd-master-0.example.com                 3/3     Running   master-0.example.com
etcd-master-1.example.com                 3/3     Running   master-1.example.com
etcd-master-2.example.com                 3/3     Running   master-2.example.com
```

A production admin should know that `READY 3/3` usually means the etcd pod has multiple containers, commonly including the main etcd process and helper containers such as etcdctl or metric-serving components depending on version.

### 3.3 etcd operator

OpenShift includes the etcd Cluster Operator. It manages etcd lifecycle, certificates, scaling behavior for supported platforms, health checks, and maintenance-related behavior.

Check operator condition:

```bash
oc get clusteroperator etcd
oc describe clusteroperator etcd
```

Important conditions:

- `Available=True`
- `Progressing=False`
- `Degraded=False`

If `etcd` ClusterOperator is degraded, do not treat it as a normal application issue. It is control-plane critical.

### 3.4 Raft leadership model

At any point, one etcd member is the leader and the others are followers.

The leader:

- Handles incoming write proposals.
- Appends entries to its Raft WAL.
- Replicates log entries to followers.
- Commits once a majority confirms.

Followers:

- Receive replicated entries.
- Apply committed entries.
- Can become leader if the existing leader fails or heartbeats are missed.

Leadership changes are normal during maintenance, node reboot, upgrade, or certificate rotation. Frequent leadership changes during normal workload are not normal and usually indicate disk latency, network latency, CPU pressure, or member instability.

## 4. How OpenShift Collects etcd Metrics

OpenShift includes a preconfigured platform monitoring stack. It monitors core platform targets, including etcd, through Prometheus-compatible metrics. The core monitoring stack runs mainly in the `openshift-monitoring` namespace.

Key monitoring components:

| Component | Role |
|---|---|
| Cluster Monitoring Operator | Manages platform monitoring components |
| Prometheus Operator | Manages Prometheus and Alertmanager resources |
| Prometheus | Scrapes and stores platform metrics |
| Alertmanager | Handles alert notifications and silences |
| Thanos Querier | Provides an aggregated query interface |
| monitoring-plugin | Provides Observe pages in the web console |
| node-exporter | Provides node-level metrics used for correlation |

OpenShift's platform Prometheus scrapes etcd metrics and makes them available through:

- Web console dashboards
- Observe -> Metrics
- Prometheus API through Thanos Querier
- Built-in alerting rules
- Custom supplemental platform rules, where allowed by cluster policy

### 4.1 etcd metrics are ephemeral counters and gauges

etcd exposes Prometheus metrics for real-time monitoring and debugging. Metrics are not persisted by etcd itself. If an etcd member restarts, its local counters reset. This is why PromQL should use functions such as `rate()`, `increase()`, and `resets()` carefully.

Example:

```promql
increase(etcd_server_leader_changes_seen_total[1h])
```

This is better than reading the raw counter value because the raw value depends on process lifetime.

## 5. Where to View etcd Metrics

### 5.1 OpenShift web console dashboard

Path:

```text
Administrator Perspective -> Observe -> Dashboards -> etcd
```

Use this for quick visual checks:

- Peer round-trip time
- Leader changes
- WAL fsync latency
- Backend commit latency
- Database size
- Proposal state
- etcd pod health

The etcd dashboard is especially useful during:

- Upgrades
- Control-plane node reboot
- Certificate rotation
- Network maintenance
- Storage migration
- Suspected API slowness

### 5.2 Observe -> Metrics

Path:

```text
Administrator Perspective -> Observe -> Metrics
```

Use this when you want direct PromQL queries.

Example query:

```promql
histogram_quantile(
  0.99,
  sum by (pod, le) (
    rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
  )
)
```

### 5.3 CLI through Thanos Querier

For automation, you can query the OpenShift metrics API. The exact token and route access model can vary by version and permissions, but the common pattern is:

```bash
THANOS_QUERIER_HOST=$(oc get route thanos-querier -n openshift-monitoring -o jsonpath='{.spec.host}')
TOKEN=$(oc whoami -t)

query='histogram_quantile(0.99, sum by (pod, le) (rate(etcd_network_peer_round_trip_time_seconds_bucket[5m])))'
encoded_query=$(printf "%s" "$query" | jq -sRr @uri)

curl -sk \
  -H "Authorization: Bearer ${TOKEN}" \
  "https://${THANOS_QUERIER_HOST}/api/v1/query?query=${encoded_query}" | jq .
```

If your RBAC does not allow querying platform metrics, use a `cluster-admin` account or grant appropriate monitoring view permissions according to your organization's policy.

## 6. Metric Naming and Labeling Basics

### 6.1 Common metric suffixes

| Suffix | Meaning | PromQL Function Usually Used |
|---|---|---|
| `_total` | Counter that increases until process restart | `rate()`, `increase()` |
| `_seconds_bucket` | Histogram bucket | `histogram_quantile()` with `rate()` |
| `_seconds_sum` | Histogram sum | Average calculation |
| `_seconds_count` | Histogram count | Average calculation |
| `_bytes` | Gauge for current bytes | Direct value or ratio |
| `_in_bytes` | Gauge for current bytes | Direct value or ratio |

### 6.2 Histogram pattern

Many important etcd latency metrics are histograms. Do not read the bucket metric directly unless you understand histogram math.

Correct p99 pattern:

```promql
histogram_quantile(
  0.99,
  sum by (pod, le) (
    rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
  )
)
```

Correct average pattern:

```promql
sum by (pod) (rate(etcd_disk_wal_fsync_duration_seconds_sum[5m]))
/
sum by (pod) (rate(etcd_disk_wal_fsync_duration_seconds_count[5m]))
```

For senior operations, p95/p99 is usually more useful than average because short spikes in etcd latency can cause leader-election instability and API timeouts.

### 6.3 Label differences between clusters

Labels can differ across OpenShift versions and managed platforms. You may see labels such as:

- `job="etcd"`
- `namespace="openshift-etcd"`
- `pod="etcd-<node>"`
- `instance="<ip>:<port>"`
- `endpoint="metrics"`
- `To="<peer-id>"` for peer metrics
- `grpc_method`, `grpc_service`, `grpc_type` for gRPC metrics

When a query returns no data, first remove restrictive labels:

```promql
etcd_disk_wal_fsync_duration_seconds_bucket
```

Then inspect available labels and gradually add filters.

## 7. Golden Signals for etcd

For OpenShift etcd, the practical golden signals are:

1. **Availability** - Are all members up and scrapeable? Does etcd have a leader?
2. **Latency** - How long do WAL fsync, backend commits, and peer replication take?
3. **Traffic / load** - How many requests, proposals, watches, and client operations are flowing?
4. **Errors / saturation** - Are proposals pending or failing? Is the database near quota? Are leader changes frequent?

A senior admin should not watch only `up`. A cluster can have `up=1` for all etcd members while p99 WAL fsync is poor enough to cause API slowness.

## 8. Critical etcd Metric Categories

## 8.1 Availability and scrape health

### `up{job="etcd"}`

Shows whether Prometheus can scrape the etcd target.

```promql
up{job="etcd"}
```

Interpretation:

| Value | Meaning |
|---|---|
| `1` | Target scrape succeeded |
| `0` | Target scrape failed |

Important: `up=1` does not mean etcd is healthy. It only means Prometheus can scrape the target.

Useful aggregate:

```promql
sum(up{job="etcd"})
```

Expected in a normal 3-node HA cluster: `3`.

---

## 8.2 Leader and quorum metrics

### `etcd_server_has_leader`

Shows whether a member currently sees a leader.

```promql
etcd_server_has_leader
```

Interpretation:

| Value | Meaning |
|---|---|
| `1` | Member sees a leader |
| `0` | Member does not see a leader |

If any member reports no leader briefly during maintenance, observe. If multiple members report no leader, treat it as control-plane critical.

### `etcd_server_is_leader`

Shows which member is the leader.

```promql
etcd_server_is_leader
```

Expected:

- Exactly one member should have `1`.
- Other members should have `0`.

Useful query:

```promql
sum(etcd_server_is_leader)
```

Expected value: `1`.

### `etcd_server_leader_changes_seen_total`

Counts leader changes seen by a member since the process started.

```promql
increase(etcd_server_leader_changes_seen_total[1h])
```

Interpretation:

| Result | Meaning |
|---|---|
| `0` | Stable leadership |
| `1` during maintenance | Usually acceptable |
| Repeated increases | Investigate disk, network, CPU, restarts, and node pressure |

Frequent leader changes are one of the strongest signs of etcd instability.

---

## 8.3 Disk WAL fsync latency

### `etcd_disk_wal_fsync_duration_seconds_bucket`

Reports WAL fsync latency. This is one of the most important etcd metrics in OpenShift.

p99 query:

```promql
histogram_quantile(
  0.99,
  sum by (pod, le) (
    rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
  )
)
```

Why it matters:

- etcd must persist Raft metadata to the WAL.
- Slow fsync can delay heartbeats and proposal commits.
- Slow fsync can trigger request timeouts and temporary leader loss.
- OpenShift API writes can become slow or fail.

Common causes of high WAL fsync:

- Slow disks
- Network-attached storage
- Noisy neighbor I/O on control-plane nodes
- Snapshot or backup I/O pressure
- Hypervisor storage latency
- Cloud volume burst credit exhaustion
- RAID controller write cache issues
- Filesystem or kernel-level I/O stalls

Senior admin action:

- Check p99, not average.
- Compare all members.
- Identify whether one member is worse or all are worse.
- Correlate with node disk metrics and storage backend events.

---

## 8.4 Backend commit latency

### `etcd_disk_backend_commit_duration_seconds_bucket`

Reports backend database commit latency.

p99 query:

```promql
histogram_quantile(
  0.99,
  sum by (pod, le) (
    rate(etcd_disk_backend_commit_duration_seconds_bucket[5m])
  )
)
```

Why it matters:

- Backend commit latency affects how quickly etcd persists MVCC database changes.
- High commit latency can increase API request latency.
- It may rise during compaction, defragmentation, snapshot, or storage saturation.

Interpretation:

| Pattern | Likely Meaning |
|---|---|
| WAL high, backend normal | WAL path or fsync-sensitive issue |
| Backend high, WAL normal | DB commit/compaction/fragmentation/storage pressure |
| Both high | General storage latency or node I/O saturation |
| One member high | Node-specific storage/hypervisor problem |
| All members high | Shared storage backend or cluster-wide I/O issue |

---

## 8.5 Peer network latency

### `etcd_network_peer_round_trip_time_seconds_bucket`

Reports round-trip time between etcd peers.

p99 query:

```promql
histogram_quantile(
  0.99,
  sum by (pod, To, le) (
    rate(etcd_network_peer_round_trip_time_seconds_bucket[5m])
  )
)
```

Why it matters:

- etcd writes require replication to a majority.
- High peer RTT delays commits.
- High peer RTT and jitter can cause missed heartbeats.
- Missed heartbeats can cause leader elections.

Important distinction:

> etcd peer round-trip time is not the same as simple ICMP ping latency. It reflects etcd-level peer communication and replication behavior.

Common causes:

- Control-plane nodes spread across high-latency zones
- Network jitter
- MTU mismatch
- Packet loss
- Firewall inspection
- Congested overlay or underlay network
- Hypervisor host networking pressure
- Stretched cluster without meeting latency requirements

## 8.6 Proposal metrics

### `etcd_server_proposals_committed_total`

Counts committed Raft proposals.

```promql
rate(etcd_server_proposals_committed_total[5m])
```

This roughly indicates write activity.

### `etcd_server_proposals_applied_total`

Counts applied proposals.

```promql
rate(etcd_server_proposals_applied_total[5m])
```

Committed and applied should generally move together.

### Committed vs applied lag

```promql
etcd_server_proposals_committed_total - etcd_server_proposals_applied_total
```

A growing gap indicates etcd is committing faster than it can apply.

### `etcd_server_proposals_pending`

Shows pending proposals.

```promql
max by (pod) (etcd_server_proposals_pending)
```

Interpretation:

| Pattern | Meaning |
|---|---|
| Near 0 | Healthy |
| Short spikes | Possible during bursts |
| Sustained > 0 | etcd cannot keep up; investigate disk/network/API write load |

### `etcd_server_proposals_failed_total`

Counts failed proposals.

```promql
increase(etcd_server_proposals_failed_total[15m])
```

Any sustained increase is serious.

## 8.7 Database size and quota metrics

### `etcd_mvcc_db_total_size_in_bytes`

Physical allocated size of the backend database.

```promql
etcd_mvcc_db_total_size_in_bytes
```

### `etcd_mvcc_db_total_size_in_use_in_bytes`

Logical in-use size of the backend database.

```promql
etcd_mvcc_db_total_size_in_use_in_bytes
```

### `etcd_server_quota_backend_bytes`

Configured backend quota.

```promql
etcd_server_quota_backend_bytes
```

### Quota usage percent

```promql
100 * etcd_mvcc_db_total_size_in_bytes / etcd_server_quota_backend_bytes
```

### Fragmentation percent

```promql
100 *
(
  etcd_mvcc_db_total_size_in_bytes - etcd_mvcc_db_total_size_in_use_in_bytes
)
/
etcd_mvcc_db_total_size_in_bytes
```

### Freeable MB by defrag

```promql
(
  etcd_mvcc_db_total_size_in_bytes - etcd_mvcc_db_total_size_in_use_in_bytes
) / 1024 / 1024
```

Why it matters:

- Large DB size increases snapshot, restore, sync, and defrag time.
- Large fragmentation can cause wasted disk usage.
- Near-quota etcd may reject writes, which breaks API persistence.
- Big databases make recovery from network partitions slower.

## 8.8 Client gRPC and request metrics

Depending on OpenShift and etcd version, you may see gRPC metrics such as:

```promql
grpc_server_handled_total
grpc_server_handling_seconds_bucket
```

Useful query pattern:

```promql
rate(grpc_server_handled_total{job="etcd"}[5m])
```

Latency example:

```promql
histogram_quantile(
  0.99,
  sum by (grpc_service, grpc_method, le) (
    rate(grpc_server_handling_seconds_bucket{job="etcd"}[5m])
  )
)
```

These help identify whether operations like range, put, transaction, lease, or watch are expensive.

## 10. Thresholds and Practical SLO Guidance

Thresholds depend on workload, cluster size, topology, OpenShift version, and storage/network backend. Use the following as practical production guidance.

### 10.1 Critical Red Hat-aligned checks

| Metric | Target / Warning Guidance |
|---|---|
| p99 WAL fsync | Keep under 10 ms for healthy etcd disk performance validation |
| p99 peer round-trip time | Keep under 50 ms |
| Leader changes | Should be rare outside maintenance |
| Proposals pending | Should usually be 0 or short-lived |
| Proposal failures | Should not increase continuously |
| Database quota usage | Investigate before it becomes high; urgent near quota |
| Fragmentation | OpenShift can auto-defrag, but large DB + fragmentation increases latency impact |

### 10.2 Practical operating bands

#### WAL fsync p99

| p99 Value | Interpretation |
|---|---|
| `< 10 ms` | Good production target |
| `10-25 ms` | Watch; may be acceptable only for light clusters but not ideal |
| `25-100 ms` | Investigate storage latency and API slowness |
| `> 100 ms` | High risk of control-plane instability |

#### Peer RTT p99

| p99 Value | Interpretation |
|---|---|
| `< 20 ms` | Good |
| `20-50 ms` | Watch carefully |
| `> 50 ms` | Does not meet recommended OpenShift target |
| `> 100 ms` | Serious risk of missed heartbeats and elections |

#### Leader changes

| Pattern | Interpretation |
|---|---|
| `0 per day` | Very stable |
| `1 during maintenance` | Usually acceptable |
| `Multiple per hour` | Serious instability |
| `Repeated bursts` | Investigate disk/network/node restarts immediately |

#### Proposal pending

| Pattern | Interpretation |
|---|---|
| `0` | Healthy |
| Short burst then back to `0` | Normal during load spike |
| Sustained non-zero | etcd cannot keep up |
| Increasing with API latency | Control-plane bottleneck likely |

## 11. Alerting Strategy for Production

OpenShift ships platform alerting rules. Do not duplicate every built-in alert unless you have a specific operational need. For senior administration, create supplemental alerts only when they improve detection, routing, or context.

### 11.1 Alert levels

Use three levels:

| Severity | Use For | Example |
|---|---|---|
| Critical | Control plane may be unavailable or writes may fail | No leader, quorum risk, etcd member down |
| Warning | Degradation that can become outage | WAL p99 high, peer RTT high, database quota rising |
| Info | Useful operational signal | One leader change during maintenance window |

### 11.2 Avoid noisy alerts

Bad alert:

```promql
etcd_disk_wal_fsync_duration_seconds_bucket > 0
```

This is meaningless because histogram buckets are cumulative counters.

Good alert:

```promql
histogram_quantile(
  0.99,
  sum by (pod, le) (
    rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
  )
) > 0.01
```

### 11.3 Use `for:` duration

etcd can spike briefly. Alert on sustained bad states.

Example:

```yaml
for: 10m
```

Use shorter duration for hard failures such as no leader.

### 11.4 Alert with context

Good annotations should tell the on-call engineer:

- Which pod/member is impacted
- Which metric breached
- What the probable root causes are
- What dashboard/runbook to open
- What not to do during a control-plane incident

## 12. Sample PrometheusRule for Supplemental etcd Alerts

> Note: Platform alert rule management can be restricted by OpenShift version, RBAC, and cluster policy. Test in a non-production cluster and follow your organization's support model. Do not remove or modify built-in Red Hat platform rules without a valid reason.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: supplemental-etcd-sre-rules
  namespace: openshift-monitoring
  labels:
    prometheus: k8s
    role: alert-rules
spec:
  groups:
  - name: supplemental-etcd.rules
    rules:
    - alert: SupplementalEtcdNoLeader
      expr: min(etcd_server_has_leader) == 0
      for: 2m
      labels:
        severity: critical
        component: etcd
      annotations:
        summary: "At least one etcd member does not see a leader"
        description: >-
          One or more etcd members report no leader for more than 2 minutes.
          Check etcd pods, control-plane node health, network latency, WAL fsync latency,
          and recent leader changes.

    - alert: SupplementalEtcdFrequentLeaderChanges
      expr: sum(increase(etcd_server_leader_changes_seen_total[30m])) > 3
      for: 5m
      labels:
        severity: warning
        component: etcd
      annotations:
        summary: "Frequent etcd leader changes detected"
        description: >-
          etcd leader changed more than 3 times in 30 minutes.
          This often points to disk latency, peer network latency, member restarts,
          CPU starvation, or node pressure.

    - alert: SupplementalEtcdHighWalFsyncP99
      expr: |
        histogram_quantile(
          0.99,
          sum by (pod, le) (
            rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
          )
        ) > 0.01
      for: 10m
      labels:
        severity: warning
        component: etcd
      annotations:
        summary: "High etcd WAL fsync p99 latency"
        description: >-
          etcd WAL fsync p99 latency is above 10 ms for more than 10 minutes on pod {{ $labels.pod }}.
          Investigate disk latency, noisy workloads on control-plane nodes, storage backend health,
          snapshots, backups, or hypervisor storage contention.

    - alert: SupplementalEtcdHighPeerRTTP99
      expr: |
        histogram_quantile(
          0.99,
          sum by (pod, To, le) (
            rate(etcd_network_peer_round_trip_time_seconds_bucket[5m])
          )
        ) > 0.05
      for: 10m
      labels:
        severity: warning
        component: etcd
      annotations:
        summary: "High etcd peer round-trip p99 latency"
        description: >-
          etcd peer RTT p99 is above 50 ms for more than 10 minutes.
          Investigate control-plane network latency, packet loss, MTU mismatch,
          stretched cluster topology, and underlay network congestion.

    - alert: SupplementalEtcdProposalFailures
      expr: sum(increase(etcd_server_proposals_failed_total[15m])) > 0
      for: 5m
      labels:
        severity: critical
        component: etcd
      annotations:
        summary: "etcd proposal failures detected"
        description: >-
          etcd proposals failed in the last 15 minutes. This can indicate quorum,
          storage, or network problems affecting writes to the control-plane datastore.

    - alert: SupplementalEtcdDatabaseQuotaHigh
      expr: |
        100 * etcd_mvcc_db_total_size_in_bytes / etcd_server_quota_backend_bytes > 70
      for: 15m
      labels:
        severity: warning
        component: etcd
      annotations:
        summary: "etcd database quota usage is high"
        description: >-
          etcd database physical size is above 70% of backend quota for more than 15 minutes.
          Check database growth, event churn, CRD object count, fragmentation, and built-in alerts.
```

## 15. Capacity, Database Size, Fragmentation, and Defrag

### 15.1 Why database size matters

Large etcd databases increase:

- Backup time
- Restore time
- Snapshot size
- Defragmentation time
- Member resynchronization time
- Memory requirements
- API cache pressure
- Impact of network partitions

OpenShift database size is driven by the number and churn rate of Kubernetes objects. You cannot fully control it directly, because Operators and workloads create and update objects continuously.

### 15.2 Physical size vs in-use size

Physical size:

```promql
etcd_mvcc_db_total_size_in_bytes
```

Logical in-use size:

```promql
etcd_mvcc_db_total_size_in_use_in_bytes
```

Difference:

```promql
etcd_mvcc_db_total_size_in_bytes - etcd_mvcc_db_total_size_in_use_in_bytes
```

This difference is storage that may be reclaimable by defragmentation.

### 15.3 Fragmentation

Fragmentation percent:

```promql
100 *
(
  etcd_mvcc_db_total_size_in_bytes - etcd_mvcc_db_total_size_in_use_in_bytes
)
/
etcd_mvcc_db_total_size_in_bytes
```

OpenShift can automatically run etcd defragmentation one member at a time when fragmentation reaches a threshold. However, defrag is blocking for the member being defragmented, so large databases and slow disks increase the impact.

### 15.4 Manual defrag caution

Manual defrag is not a casual operation. It blocks the target member while defragmentation runs.

Before manual defrag:

1. Confirm that an alert or Red Hat guidance indicates manual defrag.
2. Check database size and freeable MB.
3. Check WAL and backend latency.
4. Check leader and member health.
5. Take or verify a recent etcd backup.
6. Defrag followers first and leader last.
7. Wait between members.
8. Monitor API and etcd dashboards during the operation.

### 15.5 Example manual defrag flow

List etcd pods:

```bash
oc -n openshift-etcd get pods -l k8s-app=etcd -o wide
```

Find leader:

```bash
oc rsh -n openshift-etcd <etcd-pod> etcdctl endpoint status --cluster -w table
```

Defrag one member from inside the pod:

```bash
oc rsh -n openshift-etcd <etcd-pod>
unset ETCDCTL_ENDPOINTS
etcdctl --command-timeout=30s --endpoints=https://localhost:2379 defrag
```

Verify reduced DB size:

```bash
etcdctl endpoint status --cluster -w table
```

Again: do not run defrag on all members at the same time.

## 16. Disk and Network Validation for etcd

## 16.1 Disk requirements mindset

etcd is not high-throughput like a database storing application data, but it is latency-sensitive. A small amount of slow synchronous disk I/O can destabilize etcd because Raft depends on durable log writes.

Important practices:

- Use SSD at minimum.
- Prefer NVMe for production.
- Use dedicated etcd drives where possible.
- Avoid network filesystems such as NFS.
- Avoid NAS/SAN patterns that introduce unpredictable latency unless explicitly supported and validated.
- Avoid running I/O-heavy workloads on control-plane nodes.
- Benchmark before production and after infrastructure changes.

### 16.2 Red Hat etcd performance test container

Example pattern:

```bash
sudo podman run --volume /var/lib/etcd:/var/lib/etcd:Z quay.io/cloud-bulldozer/etcd-perf
```

The test checks whether disk fsync performance is suitable for etcd. For production validation, compare p99 fsync against the target used by Red Hat guidance.

### 16.3 Network validation

For peer communication, simple ping is not enough. You need to consider:

- RTT
- Jitter
- Packet loss
- MTU consistency
- Control-plane node placement
- Firewall path
- SDN/underlay congestion

Useful host checks:

```bash
oc debug node/<control-plane-node>
chroot /host
ip addr
ip route
ip link show
nmcli device status
journalctl -b -u NetworkManager --no-pager
```

For advanced network validation, use approved tools such as iPerf in a controlled maintenance/testing window.

## 20. Interview and Exam-Oriented Notes

### 20.1 What is etcd in OpenShift?

etcd is the consistent distributed key-value store used by Kubernetes and OpenShift to persist cluster state. It stores API objects and is critical for control-plane availability.

### 20.2 Which etcd metrics are most important?

- `etcd_server_has_leader`
- `etcd_server_leader_changes_seen_total`
- `etcd_disk_wal_fsync_duration_seconds_bucket`
- `etcd_disk_backend_commit_duration_seconds_bucket`
- `etcd_network_peer_round_trip_time_seconds_bucket`
- `etcd_server_proposals_pending`
- `etcd_server_proposals_failed_total`
- `etcd_mvcc_db_total_size_in_bytes`
- `etcd_mvcc_db_total_size_in_use_in_bytes`
- `etcd_server_quota_backend_bytes`

### 20.3 Why is WAL fsync important?

Because etcd uses Raft and must persist log entries. Slow fsync delays commits and heartbeats, which can cause API slowness, request timeouts, and leader changes.

### 20.4 Why is peer RTT important?

Because writes must replicate between etcd members. High peer RTT delays consensus and can cause missed heartbeats or elections.

### 20.5 What is a leader change?

A leader change happens when etcd elects a new leader. Some leader changes during maintenance are normal, but frequent leader changes indicate instability.

### 20.6 How do you check etcd metrics in OpenShift?

- Web console: `Observe -> Dashboards -> etcd`
- Web console: `Observe -> Metrics`
- CLI: query Thanos Querier API
- Built-in platform alerts

### 20.7 What happens if etcd loses quorum?

The cluster cannot commit writes. API server operations that require persistence fail or hang. Recovery depends on member health and may require replacing unhealthy members or, as last resort, restoring etcd from backup.

### 20.8 Why should etcd backup be taken regularly?

Because etcd contains the cluster state. A valid etcd snapshot and static pod resources are required for disaster recovery scenarios such as quorum loss or critical accidental deletion.

## 21. Best Practices Checklist

### Monitoring

- [ ] Monitor etcd dashboard daily in production.
- [ ] Alert on no leader and member down.
- [ ] Alert on frequent leader changes.
- [ ] Track p99 WAL fsync latency.
- [ ] Track p99 backend commit latency.
- [ ] Track p99 peer RTT.
- [ ] Track proposal pending and failed proposals.
- [ ] Track database size and quota usage.
- [ ] Track fragmentation and freeable database size.
- [ ] Correlate etcd latency with API server latency.

### Storage

- [ ] Use SSD minimum, NVMe preferred.
- [ ] Avoid NFS and slow network filesystems for etcd.
- [ ] Avoid noisy I/O workloads on control-plane nodes.
- [ ] Validate disk performance with fio/etcd-perf.
- [ ] Monitor storage backend latency, not only node CPU/memory.

### Network

- [ ] Keep control-plane nodes on low-latency network paths.
- [ ] Validate peer RTT and jitter.
- [ ] Avoid unsupported stretched control-plane designs.
- [ ] Check MTU consistency.
- [ ] Watch packet loss and firewall inspection paths.

### Operations

- [ ] Take etcd backup before upgrades and risky control-plane maintenance.
- [ ] Store backup outside the cluster securely.
- [ ] Do not reboot multiple control-plane nodes at the same time.
- [ ] Do not manually defrag all members at once.
- [ ] Defrag followers before leader if manual defrag is required.
- [ ] Collect must-gather before destructive recovery where possible.
- [ ] Treat etcd alerts as platform-critical.

### Capacity

- [ ] Watch object count and event churn.
- [ ] Limit CI/CD namespace and job churn.
- [ ] Tune CronJob and Job history limits.
- [ ] Avoid large ConfigMaps and Secrets.
- [ ] Review noisy custom controllers and Operators.
