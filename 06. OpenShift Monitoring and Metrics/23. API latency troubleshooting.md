# API Latency Troubleshooting in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift Administrators / SREs with production experience  
**Focus:** OpenShift 4.x control plane API latency diagnosis using metrics, logs, events, `oc`, PromQL, etcd checks, and safe mitigation  
**Skill level:** 10-year Linux / Kubernetes / OpenShift administration depth  

---

## 1. What API Latency Means in OpenShift

API latency is the time taken by the OpenShift/Kubernetes API layer to receive, authenticate, authorize, admit, persist, and return a response for an API request.

In real operations, API latency is not just “`oc get pods` is slow.” It can mean:

- `oc` commands take several seconds or time out.
- Web console pages load slowly or show partial data.
- Operators become `Degraded`, `Progressing`, or slow to reconcile.
- Deployments, routes, secrets, config maps, PVCs, and CRDs take longer to create or update.
- Admission webhooks time out.
- GitOps or CI/CD tools flood the API server.
- HPA, scheduler, controllers, or OLM react slowly.
- etcd commit, fsync, leader election, or peer latency affects the complete control plane.

API latency is a **control-plane symptom**. The root cause can be in the API server, etcd, admission webhooks, API Priority and Fairness, a noisy client, DNS, network, control-plane node pressure, aggregated APIs, or bad custom controllers.

## 2. OpenShift API Request Path

A normal request flows like this:

```text
oc / console / controller / operator / GitOps / app client
        |
        v
API load balancer / api.<cluster>:6443
        |
        v
kube-apiserver pod on control-plane node
        |
        +--> authentication
        +--> authorization / RBAC / SCC checks
        +--> admission chain
        |       +--> mutating admission plugins
        |       +--> validating admission plugins
        |       +--> external admission webhooks
        |
        +--> API Priority and Fairness queueing
        |
        +--> storage layer
                |
                v
               etcd quorum
```

OpenShift also has OpenShift-specific API components, for example:

```text
openshift-kube-apiserver      -> Kubernetes API server integration
openshift-apiserver           -> OpenShift API groups
openshift-oauth-apiserver     -> OAuth API serving
openshift-authentication      -> authentication components
openshift-etcd                -> etcd static pods
openshift-monitoring          -> Prometheus, Alertmanager, Thanos Querier
```

When troubleshooting, separate these layers:

| Layer | Typical problem | Symptom |
|---|---|---|
| Client side | Slow DNS, proxy, VPN, old token, huge `oc get -A` | One user/tool affected |
| API load balancer | One master unreachable, TLS issue, VIP issue | Intermittent API timeouts |
| kube-apiserver | CPU/memory saturation, bad revision, log errors | All users affected |
| Admission | Slow or failing webhook | Writes slow, creates/updates fail |
| API Priority and Fairness | Queueing/rejection | `429`, long wait duration, controller delays |
| etcd | Disk/network/quorum latency | Cluster-wide API slowness, writes slow |
| Aggregated API | Broken APIService or extension API | Discovery slow, console/CLI slow |
| Noisy client | CI/CD, GitOps, custom controller loop | High request rate for one verb/resource |

## 3. Important API Latency Metrics

The most important metric for Kubernetes API latency is:

```promql
apiserver_request_duration_seconds_bucket
```

It is a histogram. You normally use `histogram_quantile()` to calculate p50, p95, or p99 latency.

The corresponding non-bucket metric might exist when native histograms are enabled:

```promql
apiserver_request_duration_seconds
```

However, in most OpenShift Prometheus queries you will still commonly use the classic histogram bucket form:

```promql
apiserver_request_duration_seconds_bucket
```

Common labels:

| Label | Meaning |
|---|---|
| `verb` | API operation such as `GET`, `LIST`, `WATCH`, `POST`, `PUT`, `PATCH`, `DELETE` |
| `resource` | Resource such as `pods`, `secrets`, `configmaps`, `nodes`, `deployments` |
| `group` | API group such as `apps`, `route.openshift.io`, `operators.coreos.com` |
| `version` | API version such as `v1`, `v1alpha1`, `v1beta1` |
| `subresource` | Subresource such as `status`, `scale`, `log`, `exec` |
| `scope` | `cluster`, `namespace`, or similar scope value |
| `component` | API serving component label, depending on version and scrape target |
| `le` | Histogram bucket boundary |

Other key metrics:

```promql
apiserver_request_total
apiserver_current_inflight_requests
apiserver_longrunning_requests
apiserver_admission_webhook_admission_duration_seconds_bucket
apiserver_admission_controller_admission_duration_seconds_bucket
apiserver_flowcontrol_request_wait_duration_seconds_bucket
apiserver_flowcontrol_current_inqueue_requests
apiserver_flowcontrol_rejected_requests_total
etcd_request_duration_seconds_bucket
etcd_request_errors_total
etcd_disk_wal_fsync_duration_seconds_bucket
etcd_disk_backend_commit_duration_seconds_bucket
etcd_network_peer_round_trip_time_seconds_bucket
etcd_server_leader_changes_seen_total
apiserver_storage_objects
process_cpu_seconds_total
process_resident_memory_bytes
container_cpu_usage_seconds_total
container_memory_working_set_bytes
```

> Note: Metric availability and labels can change by OpenShift/Kubernetes version. Always verify labels in your cluster before building a permanent alert or dashboard.

## 4. How to Access Metrics

### 4.1 From OpenShift Web Console

Use:

```text
Observe -> Metrics
```

As a cluster administrator, you can query platform metrics. For developer/user workload metrics, project-level permissions and user workload monitoring configuration matter.

### 4.2 From CLI Using Thanos Querier

```bash
TOKEN=$(oc whoami -t)
HOST=$(oc -n openshift-monitoring get route thanos-querier -o jsonpath='{.status.ingress[0].host}')

curl -k -H "Authorization: Bearer ${TOKEN}" \
  "https://${HOST}/api/v1/query" \
  --data-urlencode 'query=up'
```

For a range query:

```bash
curl -k -H "Authorization: Bearer ${TOKEN}" \
  "https://${HOST}/api/v1/query_range" \
  --data-urlencode 'query=sum(rate(apiserver_request_total[5m]))' \
  --data-urlencode 'start=2026-07-03T06:00:00Z' \
  --data-urlencode 'end=2026-07-03T07:00:00Z' \
  --data-urlencode 'step=30s'
```

### 4.3 Inspect Available Metric Labels

Before assuming labels:

```bash
curl -k -H "Authorization: Bearer ${TOKEN}" \
  "https://${HOST}/api/v1/series" \
  --data-urlencode 'match[]=apiserver_request_duration_seconds_bucket' | jq '.data[0:5]'
```

Or from the console, run:

```promql
count by (__name__) ({__name__=~"apiserver_.*"})
```

Check label combinations:

```promql
count by (job, namespace, service, endpoint, component) (apiserver_request_duration_seconds_bucket)
```

## 5. Golden PromQL Queries for API Latency

### 5.1 Overall API Server p99 Latency

```promql
histogram_quantile(
  0.99,
  sum by (le) (
    rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])
  )
)
```

Use this to answer: **Is API latency high cluster-wide?**

### 5.2 p95 API Latency

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])
  )
)
```

p95 is useful for operational dashboards. p99 is better for incident triage because it shows tail latency.

### 5.3 Latency by Verb

```promql
histogram_quantile(
  0.99,
  sum by (le, verb) (
    rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])
  )
)
```

Interpretation:

| Verb | Meaning | Common root cause |
|---|---|---|
| `GET` | Single object reads | API server CPU, authn/authz, network |
| `LIST` | List many objects | Large object count, bad controller, huge namespace |
| `WATCH` | Long-running watch | Many controllers/watchers, disconnected clients |
| `POST` | Create | Admission webhooks, etcd writes, quota, API validation |
| `PUT`/`PATCH` | Update | Admission, status updates, controller churn, etcd |
| `DELETE` | Delete | Finalizers, garbage collection, admission |

### 5.4 Latency by Resource

```promql
histogram_quantile(
  0.99,
  sum by (le, group, resource, subresource, verb) (
    rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])
  )
)
```

Sort mentally or graph only top offenders. If this query returns too much data, narrow it:

```promql
histogram_quantile(
  0.99,
  sum by (le, resource, verb) (
    rate(apiserver_request_duration_seconds_bucket{resource=~"pods|secrets|configmaps|leases|events",verb!~"WATCH|WATCHLIST|CONNECT"}[5m])
  )
)
```

### 5.5 API Request Rate

```promql
sum by (verb, group, resource, subresource) (
  rate(apiserver_request_total[5m])
)
```

High latency with low request rate often points to etcd, webhook, or node pressure. High latency with high request rate often points to client flood, controller loop, API saturation, or APF queueing.

### 5.6 API Error Rate

```promql
sum by (code, verb, resource) (
  rate(apiserver_request_total{code=~"4..|5.."}[5m])
)
```

Focus on:

| Code | Meaning |
|---|---|
| `429` | Too many requests / throttling / APF rejection |
| `500` | API server internal error |
| `503` | API service unavailable / control-plane issue |
| `504` | Timeout, often upstream/backend path |

### 5.7 5xx Error Percentage

```promql
100 *
sum(rate(apiserver_request_total{code=~"5.."}[5m]))
/
sum(rate(apiserver_request_total[5m]))
```

### 5.8 429 Throttling / Rejection Rate

```promql
sum by (verb, resource) (
  rate(apiserver_request_total{code="429"}[5m])
)
```

If this is high, inspect API Priority and Fairness metrics.

### 5.9 Inflight Requests

```promql
sum by (request_kind) (apiserver_current_inflight_requests)
```

High inflight requests can mean the API server is saturated, blocked by storage, blocked by admission, or serving expensive list/watch workloads.

### 5.10 Long-running Requests

```promql
sum by (verb, group, resource, subresource) (apiserver_longrunning_requests)
```

WATCH requests are expected to be long-running. Unexpected long-running non-watch requests need investigation.

## 6. API Priority and Fairness Troubleshooting

API Priority and Fairness, often called APF, protects the API server by classifying requests into flow schemas and priority levels. When there is heavy load, requests can wait in queues or be rejected.

### 6.1 APF Queue Wait p99

```promql
histogram_quantile(
  0.99,
  sum by (le, priority_level, flow_schema) (
    rate(apiserver_flowcontrol_request_wait_duration_seconds_bucket[5m])
  )
)
```

If queue wait is high, latency is happening before actual execution.

### 6.2 Current APF Queued Requests

```promql
sum by (priority_level, flow_schema) (
  apiserver_flowcontrol_current_inqueue_requests
)
```

### 6.3 APF Rejections

```promql
sum by (priority_level, flow_schema, reason) (
  rate(apiserver_flowcontrol_rejected_requests_total[5m])
)
```

### 6.4 Current Executing Seats

```promql
sum by (priority_level, flow_schema) (
  apiserver_flowcontrol_current_executing_seats
)
```

### 6.5 Inspect APF Objects

```bash
oc get prioritylevelconfiguration
oc get flowschema
oc describe prioritylevelconfiguration <name>
oc describe flowschema <name>
```

### 6.6 How to Interpret APF Symptoms

| Observation | Meaning | Next action |
|---|---|---|
| High APF wait, high request rate | API server is protecting itself from overload | Find noisy client/resource |
| High APF rejects with `429` | Requests are being rejected | Reduce client QPS, fix controller loop |
| One flow schema dominates | One class of clients is noisy | Inspect audit logs and client identities |
| System priority affected | Serious cluster-wide pressure | Check etcd, control-plane node pressure, and operator health |

Do not casually tune APF in production. First find the source of load. APF tuning without understanding the abusive workload can hide the real problem and make failure modes worse.

## 7. Admission Webhook Latency Troubleshooting

Admission webhooks are a very common cause of slow creates and updates.

Examples:

- Security scanners
- Policy engines
- Service mesh injectors
- Custom validation controllers
- OLM/operator webhooks
- Image policy webhooks
- Mutating webhooks that inject sidecars or labels

### 7.1 Webhook p99 Latency

```promql
histogram_quantile(
  0.99,
  sum by (le, name, type, operation, rejected) (
    rate(apiserver_admission_webhook_admission_duration_seconds_bucket[5m])
  )
)
```

### 7.2 Admission Controller Latency

```promql
histogram_quantile(
  0.99,
  sum by (le, name, operation, type, rejected) (
    rate(apiserver_admission_controller_admission_duration_seconds_bucket[5m])
  )
)
```

### 7.3 List Webhook Configurations

```bash
oc get validatingwebhookconfigurations
oc get mutatingwebhookconfigurations
```

Detailed output:

```bash
oc get validatingwebhookconfigurations,mutatingwebhookconfigurations -o json \
| jq -r '
  .items[] as $cfg |
  $cfg.webhooks[]? |
  [
    $cfg.kind,
    $cfg.metadata.name,
    .name,
    (.clientConfig.service.namespace // "external"),
    (.clientConfig.service.name // .clientConfig.url // "unknown"),
    (.timeoutSeconds // "default"),
    (.failurePolicy // "default"),
    ((.rules // []) | length)
  ] | @tsv'
```

### 7.4 Check Webhook Service Health

```bash
oc get svc,endpoints,endpointslices -A | grep -i <webhook-name-or-service>
oc get pods -A | grep -i <webhook-name>
oc logs -n <namespace> deploy/<webhook-deployment> --since=30m
```

### 7.5 Webhook Failure Patterns

| Pattern | Symptom | Fix |
|---|---|---|
| Webhook pod down | Create/update hangs then fails | Restore webhook pod/service |
| Service has no endpoints | API calls time out | Fix selector, pod readiness, namespace |
| Webhook TLS expired | Admission errors in API logs | Rotate certs/redeploy webhook |
| Webhook has high latency | POST/PATCH/PUT slow | Scale/fix webhook app/backend |
| Webhook calls external service | Latency depends on external network | Avoid external blocking calls |
| `failurePolicy: Fail` with unreliable webhook | Writes blocked | Fix webhook or temporarily change policy after risk review |
| Broad rules matching all resources | Cluster-wide slowness | Narrow webhook rules and namespace selectors |

### 7.6 Emergency Webhook Mitigation

For production incidents:

1. Confirm which webhook is slow or failing.
2. Check whether it is business/security critical.
3. Scale or fix webhook backend first.
4. If it is blocking the cluster, consider temporarily narrowing rules, reducing timeout, or changing `failurePolicy`, but document the risk.
5. Restore secure policy after the incident.

Never delete webhook configurations blindly. Some operators recreate them, and deleting policy/security webhooks can create compliance exposure.

## 8. etcd Latency and API Slowness

etcd is the backing store for Kubernetes and OpenShift control-plane state. If etcd is slow, API writes become slow. If etcd loses quorum or has leader changes, the API server can become unstable.

### 8.1 etcd API Storage Request Latency from kube-apiserver

```promql
histogram_quantile(
  0.99,
  sum by (le, operation, group, resource) (
    rate(etcd_request_duration_seconds_bucket[5m])
  )
)
```

This metric is exposed from kube-apiserver and shows API server storage operation latency by operation/resource.

### 8.2 etcd Request Errors

```promql
sum by (operation, group, resource) (
  rate(etcd_request_errors_total[5m])
)
```

### 8.3 etcd WAL fsync p99

```promql
histogram_quantile(
  0.99,
  sum by (le, instance) (
    rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
  )
)
```

High WAL fsync latency means etcd disk writes are slow. This is one of the most important etcd signals.

### 8.4 etcd Backend Commit p99

```promql
histogram_quantile(
  0.99,
  sum by (le, instance) (
    rate(etcd_disk_backend_commit_duration_seconds_bucket[5m])
  )
)
```

### 8.5 etcd Peer RTT p99

```promql
histogram_quantile(
  0.99,
  sum by (le, instance, To) (
    rate(etcd_network_peer_round_trip_time_seconds_bucket[5m])
  )
)
```

If the label is not `To` in your cluster, inspect available labels:

```promql
count by (__name__, instance) (etcd_network_peer_round_trip_time_seconds_bucket)
```

or query series labels through Thanos.

### 8.6 etcd Leader Changes

```promql
increase(etcd_server_leader_changes_seen_total[15m])
```

Leader changes during the incident window are a strong signal of etcd instability.

### 8.7 Check etcd Cluster Operator

```bash
oc get co etcd
oc describe co etcd
oc get pods -n openshift-etcd -l app=etcd -o wide
oc get events -n openshift-etcd --sort-by=.lastTimestamp | tail -50
```

### 8.8 Check etcd Endpoint Health

```bash
oc get pods -n openshift-etcd -l app=etcd

# Pick one etcd pod, then run:
oc -n openshift-etcd exec -it <etcd-pod> -- etcdctl endpoint health -w table
oc -n openshift-etcd exec -it <etcd-pod> -- etcdctl endpoint status -w table
```

### 8.9 etcd Database Size and Object Count

Top stored API resources:

```promql
topk(20, apiserver_storage_objects)
```

Watch object count trend:

```promql
max_over_time(apiserver_storage_objects[6h])
```

If one resource has exploded, find the owner:

```bash
oc get <resource> -A --no-headers | wc -l
oc get events -A --field-selector type=Warning | tail -100
```

Common object growth causes:

- Too many Events.
- Failed Jobs/CronJobs not cleaned up.
- Operators creating many CRs.
- GitOps continuously recreating resources.
- Finalizers blocking deletes.
- EndpointSlice churn due to unstable pods.
- Lease churn from many controllers.

## 9. Control-plane Node Pressure Checks

API latency can be caused by control-plane node pressure even when etcd is healthy.

### 9.1 Cluster Operators

```bash
oc get co
oc get co kube-apiserver openshift-apiserver authentication etcd monitoring
oc describe co kube-apiserver
oc describe co openshift-apiserver
oc describe co authentication
oc describe co etcd
```

### 9.2 Control-plane Nodes

```bash
oc get nodes -l node-role.kubernetes.io/master -o wide
oc describe node <master-node>
oc adm top nodes
```

Look for:

- `MemoryPressure`
- `DiskPressure`
- `PIDPressure`
- High CPU usage
- Disk latency
- kubelet instability
- Node NotReady events
- Container runtime issues

### 9.3 API Server Pods

```bash
oc -n openshift-kube-apiserver get pods -o wide
oc -n openshift-apiserver get pods -o wide
oc -n openshift-oauth-apiserver get pods -o wide
```

Check restarts:

```bash
oc -n openshift-kube-apiserver get pods \
  -o custom-columns=NAME:.metadata.name,READY:.status.containerStatuses[*].ready,RESTARTS:.status.containerStatuses[*].restartCount,NODE:.spec.nodeName
```

### 9.4 API Server CPU Usage

```promql
sum by (pod, container) (
  rate(container_cpu_usage_seconds_total{namespace="openshift-kube-apiserver", container!=""}[5m])
)
```

### 9.5 API Server Memory Usage

```promql
container_memory_working_set_bytes{namespace="openshift-kube-apiserver", container!=""}
```

### 9.6 Process-level Signals

```promql
rate(process_cpu_seconds_total{namespace="openshift-kube-apiserver"}[5m])
process_resident_memory_bytes{namespace="openshift-kube-apiserver"}
go_goroutines{namespace="openshift-kube-apiserver"}
```

Labels can differ, so first inspect available series:

```promql
count by (job, namespace, pod, instance) (process_cpu_seconds_total)
```

## 10. Client-side and Noisy-client Investigation

Not every “API latency” complaint is caused by the cluster. First determine whether it affects:

- One user
- One bastion/workstation
- One namespace
- One tool such as Argo CD/Jenkins/Tekton
- One operator
- All users and controllers

### 10.1 Compare From Multiple Locations

```bash
time oc whoami
time oc get --raw=/readyz
time oc get ns >/dev/null
time oc get pods -A --request-timeout=20s >/dev/null
```

From the same host:

```bash
curl -k https://api.<cluster-name>.<domain>:6443/readyz
```

Authenticated readyz:

```bash
oc get --raw='/readyz?verbose'
oc get --raw='/livez?verbose'
```

### 10.2 Use `oc` Verbose Logs

```bash
oc --v=8 get pods -n openshift-monitoring
```

Look for:

- DNS resolution delay
- TLS handshake delay
- HTTP round-trip delay
- Proxy delay
- Token refresh issue
- Repeated retries

### 10.3 Watch for Bad Client Behavior

Bad clients commonly do:

- `oc get pods -A` every second.
- Full cluster `LIST` repeatedly instead of `WATCH`.
- No client-side caching.
- Too many parallel CI/CD jobs.
- Custom controller loops due to reconcile errors.
- GitOps sync loop due to immutable field or drift.
- Controllers updating `status` too frequently.

Metrics help identify the resource/verb. Audit logs help identify the user-agent/user.

### 10.4 Request Rate by Verb and Resource

```promql
topk(20,
  sum by (verb, group, resource, subresource) (
    rate(apiserver_request_total[5m])
  )
)
```

### 10.5 LIST Request Rate

```promql
sum by (group, resource, scope) (
  rate(apiserver_request_total{verb="LIST"}[5m])
)
```

High `LIST` volume is a classic sign of inefficient clients or controllers.

### 10.6 Write Request Rate

```promql
sum by (verb, group, resource, subresource) (
  rate(apiserver_request_total{verb=~"POST|PUT|PATCH|DELETE"}[5m])
)
```

High writes put pressure on admission and etcd.

## 11. Audit Logs for API Latency

Metrics tell you **what** is slow. Audit logs often tell you **who** is causing it.

OpenShift audit log locations can vary by component and version, but kube-apiserver audit logs are commonly available from control-plane nodes under kube-apiserver log paths.

### 11.1 List Master Nodes

```bash
oc get nodes -l node-role.kubernetes.io/master
```

### 11.2 Inspect API Audit Logs from Node Logs

Example pattern:

```bash
oc adm node-logs <master-node> --path=kube-apiserver/audit.log | tail -100
```

If the exact path differs, inspect available paths:

```bash
oc adm node-logs <master-node> --path=/
```

### 11.3 Find High-volume Users or User Agents

If audit logs are JSON:

```bash
oc adm node-logs <master-node> --path=kube-apiserver/audit.log \
| jq -r '[.user.username, .userAgent, .verb, .objectRef.resource, .responseStatus.code] | @tsv' \
| sort | uniq -c | sort -nr | head -30
```

### 11.4 Find Slow Requests in Audit Logs

Some audit configurations include timestamps and stages. You can compare `requestReceivedTimestamp` and `stageTimestamp`:

```bash
oc adm node-logs <master-node> --path=kube-apiserver/audit.log \
| jq -r '
  select(.requestReceivedTimestamp and .stageTimestamp) |
  [.requestReceivedTimestamp, .stageTimestamp, .verb, .objectRef.resource, .user.username, .userAgent, .responseStatus.code] | @tsv'
```

If audit retention is short, collect logs immediately during incidents.

## 12. Aggregated API and APIService Problems

A broken aggregated API can make discovery slow and affect console/CLI behavior.

Check APIService status:

```bash
oc get apiservice
oc get apiservice | grep -v True
```

Describe unhealthy services:

```bash
oc describe apiservice <name>
```

Check the backing service:

```bash
oc get svc,endpoints,endpointslices -A | grep <service-name>
oc get pods -n <namespace> -o wide
```

Typical issues:

- Backing service has no endpoints.
- TLS serving certificate mismatch.
- APIService points to old service/namespace.
- Extension API server is overloaded.
- Operator owning the APIService is degraded.

API discovery commands that become slow:

```bash
oc api-resources
oc get --raw /apis
oc get --raw /api
```

If these are slow but simple resource gets are normal, suspect aggregated API discovery.

## 13. Network and Load Balancer Checks

API latency can be caused by load balancer or control-plane network problems.

### 13.1 Check API VIP and Endpoints

```bash
oc get endpoints kubernetes -n default -o wide
oc get endpointslices -n default -l kubernetes.io/service-name=kubernetes -o wide
```

### 13.2 Check API Server Pods by Node

```bash
oc -n openshift-kube-apiserver get pods -o wide
```

If only one API server instance has high latency, check its node, network, kubelet, and API pod logs.

### 13.3 Per-instance Latency

```promql
histogram_quantile(
  0.99,
  sum by (le, instance) (
    rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])
  )
)
```

Interpretation:

| Pattern | Likely cause |
|---|---|
| One instance slow | One master node, pod, network path, or LB target issue |
| All instances slow | etcd, admission, cluster-wide load, network/storage |
| Random spikes per instance | LB health, node pressure, GC, CPU throttling |

### 13.4 Check API Connectivity

From admin host:

```bash
time curl -k https://api.<cluster-domain>:6443/readyz
```

From inside cluster:

```bash
oc run api-test --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -k https://kubernetes.default.svc/readyz
```

If `curl` from inside is fast but outside is slow, suspect DNS, proxy, firewall, VPN, route to API VIP, or external load balancer.

## 15. API Latency Root-cause Decision Tree

Use this decision tree during incidents.

```text
1. Is API latency real for multiple clients?
   |
   +-- No -> client workstation, DNS, VPN, token, proxy, local network
   |
   +-- Yes
       |
       v
2. Is p99 apiserver_request_duration_seconds high?
   |
   +-- No -> maybe console/browser/client-side issue, aggregated API discovery, network path
   |
   +-- Yes
       |
       v
3. Is only one API server instance slow?
   |
   +-- Yes -> inspect that master node, kubelet, API pod, LB target
   |
   +-- No
       |
       v
4. Is etcd latency high or leader changing?
   |
   +-- Yes -> etcd disk/network/quorum/object growth investigation
   |
   +-- No
       |
       v
5. Is admission webhook latency high?
   |
   +-- Yes -> fix webhook service/backend/cert/rules/timeout
   |
   +-- No
       |
       v
6. Is APF queue wait or rejection high?
   |
   +-- Yes -> identify noisy client/resource, reduce QPS, fix loop
   |
   +-- No
       |
       v
7. Is LIST/write request rate abnormal?
   |
   +-- Yes -> audit logs, noisy controller/GitOps/CI/CD
   |
   +-- No
       |
       v
8. Are APIService/discovery calls slow?
   |
   +-- Yes -> unhealthy aggregated API or extension server
   |
   +-- No -> inspect logs, node pressure, DNS/network, recent changes
```

## 16. Practical Incident Runbook

### Phase 1: Confirm the Blast Radius

```bash
date
oc whoami
oc get clusterversion
oc get co

time oc get ns >/dev/null
time oc get pods -A --request-timeout=20s >/dev/null
time oc get --raw='/readyz?verbose' >/tmp/readyz.txt
cat /tmp/readyz.txt
```

Questions:

- Is the API slow for all users or one client?
- Are writes slow, reads slow, or both?
- Are only console pages slow?
- Did it start after an upgrade, operator install, GitOps sync, certificate rotation, or node event?

### Phase 2: Check Overall API Latency

Run:

```promql
histogram_quantile(0.99, sum by (le) (rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])))
```

### Phase 5: Check Admission


```bash

```

### Phase 6: Check APF

### Phase 8: Check Control-plane Nodes and Pods

```bash

```

For webhook backend:

```bash

```

### Phase 10: Mitigate Safely

Depending on confirmed root cause:

| Root cause | Safe mitigation |
|---|---|
| Noisy CI/CD or GitOps | Pause sync/job, reduce parallelism, fix loop |
| Bad custom controller | Scale down controller, fix reconcile error |
| Slow webhook | Restore endpoints, scale backend, fix cert, narrow scope |
| etcd disk latency | Remove competing I/O, check storage backend, engage platform/storage team |
| etcd leader changes | Check control-plane network, disk, node health, engage Red Hat support if severe |
| One bad master | Remove from LB temporarily only if approved, inspect node/pod health |
| APIService broken | Fix backing service/certs/operator |
| Too many objects | Clean old Jobs/Events/CRs, fix retention/finalizers |
| APF rejects | Reduce client QPS, fix abusive client before tuning APF |

## 17. Common Real-world Scenarios

### Scenario 1: `oc get pods -A` is Slow, But Creates Are Normal

Likely causes:

- Large pod count.
- Slow `LIST pods` operation.
- Inefficient client repeatedly listing all namespaces.
- API server CPU pressure.

Queries:

```promql
histogram_quantile(0.99, sum by (le, resource, verb) (rate(apiserver_request_duration_seconds_bucket{verb="LIST",resource="pods"}[5m])))
```

```promql
sum(rate(apiserver_request_total{verb="LIST",resource="pods"}[5m]))
```

Actions:

- Identify clients using audit logs.
- Reduce full-cluster polling.
- Use informers/watchers instead of repeated LIST.
- Avoid scripts that call `oc get pods -A` every few seconds.

### Scenario 2: Pod Creation is Slow

Likely causes:

- Admission webhook latency.
- Quota/LimitRange evaluation pressure.
- Image policy webhook.
- etcd write latency.
- Scheduler is fine but API write path is slow.

Queries:

```promql
histogram_quantile(0.99, sum by (le, name, operation, type) (rate(apiserver_admission_webhook_admission_duration_seconds_bucket{operation="CREATE"}[5m])))
```

```promql
histogram_quantile(0.99, sum by (le, operation, resource) (rate(etcd_request_duration_seconds_bucket{operation=~"create|put|update"}[5m])))
```

Actions:

- Check webhook services/endpoints.
- Check policy engines.
- Check etcd fsync/backend commit latency.
- Check quota usage and namespace object count.

### Scenario 3: API Returns 429

Likely causes:

- APF queue saturation.
- Too many requests from one client class.
- Controller or CI/CD flood.

Queries:

```promql
sum by (priority_level, flow_schema, reason) (rate(apiserver_flowcontrol_rejected_requests_total[5m]))
```

```promql
sum by (verb, resource) (rate(apiserver_request_total{code="429"}[5m]))
```

Actions:

- Identify noisy client.
- Reduce QPS/burst settings.
- Stop runaway automation.
- Avoid immediately tuning APF.

### Scenario 4: API Latency Spikes During Deployment Waves

Likely causes:

- GitOps sync waves creating many objects.
- Tekton/Jenkins creating many pods/jobs/secrets.
- Webhook backend not scaled.
- etcd write pressure.

Queries:

```promql
sum by (verb, resource) (rate(apiserver_request_total{verb=~"POST|PUT|PATCH|DELETE"}[5m]))
```

```promql
histogram_quantile(0.99, sum by (le, instance) (rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])))
```

Actions:

- Stagger deployment waves.
- Reduce GitOps parallelism.
- Tune CI/CD concurrency.
- Scale webhook backends.
- Clean old Jobs and completed Pods.

### Scenario 5: Console is Slow, `oc get pods` is Fine

Likely causes:

- Console backend issue.
- OAuth/authentication latency.
- Aggregated API discovery issue.
- Browser/network path.
- Monitoring plugin/dashboard query load.

Checks:

```bash
oc get co console authentication openshift-apiserver kube-apiserver
oc get apiservice | grep -v True
oc logs -n openshift-console deploy/console --since=30m
```

PromQL:

```promql
histogram_quantile(0.99, sum by (le, resource, verb) (rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])))
```

If API metrics are normal, focus on console/authentication rather than etcd.

## 19. Alerting Rules for API Latency

### 19.1 API p99 Latency Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-latency-rules
  namespace: openshift-monitoring
spec:
  groups:
  - name: api-latency.rules
    rules:
    - alert: HighKubeAPIServerLatencyP99
      expr: |
        histogram_quantile(
          0.99,
          sum by (le) (
            rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|WATCHLIST|CONNECT"}[5m])
          )
        ) > 1
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "Kubernetes API server p99 latency is high"
        description: "API server p99 latency is above 1 second for more than 10 minutes. Check API request rate, APF, admission webhooks, etcd latency, and control-plane node pressure."
```

### 19.2 Admission Webhook Latency Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: admission-latency-rules
  namespace: openshift-monitoring
spec:
  groups:
  - name: admission-latency.rules
    rules:
    - alert: HighAdmissionWebhookLatencyP99
      expr: |
        histogram_quantile(
          0.99,
          sum by (le, name) (
            rate(apiserver_admission_webhook_admission_duration_seconds_bucket[5m])
          )
        ) > 2
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "Admission webhook p99 latency is high"
        description: "Webhook {{ $labels.name }} has high p99 admission latency. Check webhook service endpoints, pod health, TLS, timeoutSeconds, and backend performance."
```

### 19.3 APF Rejection Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: apf-rejection-rules
  namespace: openshift-monitoring
spec:
  groups:
  - name: apf-rejection.rules
    rules:
    - alert: APIServerFlowControlRejectingRequests
      expr: |
        sum(rate(apiserver_flowcontrol_rejected_requests_total[5m])) > 0
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "API Priority and Fairness is rejecting requests"
        description: "APF is rejecting requests. Check priority_level, flow_schema, 429 rates, request volume, and noisy clients."
```

### 19.4 etcd WAL fsync Latency Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: etcd-latency-rules
  namespace: openshift-monitoring
spec:
  groups:
  - name: etcd-latency.rules
    rules:
    - alert: HighEtcdWALFsyncLatencyP99
      expr: |
        histogram_quantile(
          0.99,
          sum by (le, instance) (
            rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])

      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "etcd WAL fsync p99 latency is high"

```

> In production, align thresholds with your platform SLOs and Red Hat support guidance. Avoid copying thresholds blindly from another cluster.

## 20. Safe Remediation Guidelines

### 20.1 Safe First Actions

- Pause runaway CI/CD pipelines.
- Pause Argo CD automated sync for the offending app.
- Scale down a bad custom controller after confirming ownership.
- Restore unhealthy webhook pods/services.
- Fix webhook endpoints and certificates.
- Reduce webhook scope with namespace/object selectors.
- Clean up excessive Jobs, Events, and obsolete CRs.
- Remove accidental scripts polling the API.
- Check control-plane node disk, CPU, memory, and network.
- Collect must-gather before making destructive changes.

### 20.2 Risky Actions Requiring Strong Justification

- Deleting webhook configurations.
- Editing APF priority levels in production.
- Restarting all API server pods at once.
- Changing etcd timers.
- Manually editing static pod manifests.
- Removing control-plane nodes from load balancer without a rollback plan.
- Deleting CRDs with active custom resources.
- Removing finalizers broadly.

### 20.3 Never Do This During an Incident

- Do not run heavy all-metrics federation repeatedly.
- Do not query Prometheus with unbounded high-cardinality queries every few seconds.
- Do not run `oc get <resource> -A -o yaml` repeatedly on large clusters.
- Do not delete etcd data manually.
- Do not defragment or modify etcd without understanding OpenShift procedures.
- Do not assume web console slowness always means etcd is bad.

## 22. Performance Prevention Best Practices

### 22.1 For Cluster Admins

- Keep OpenShift updated within supported lifecycle.
- Monitor API p95/p99 as an SLO.
- Monitor etcd disk and peer latency continuously.
- Avoid running heavy workloads on control-plane nodes.
- Use fast local SSD/NVMe-backed etcd storage where applicable.
- Keep control-plane network stable and low-latency.
- Watch object growth trends.
- Regularly review unhealthy APIService objects.
- Validate webhooks during upgrades.
- Keep monitoring retention and capacity healthy.

### 22.2 For Platform Engineering Teams

- Set CI/CD concurrency limits.
- Avoid full-cluster polling.
- Use watches/informers correctly.
- Cache API discovery results where possible.
- Stagger GitOps sync waves.
- Use cleanup policies for Jobs, Pods, and temporary namespaces.
- Keep CRDs and operators efficient.
- Test webhooks under load.
- Set reasonable webhook `timeoutSeconds`.
- Avoid external network calls inside admission webhooks.

### 22.3 For Developers

- Avoid scripts that call `oc get -A` repeatedly.
- Avoid creating thousands of ConfigMaps/Secrets unnecessarily.
- Set TTL for completed Jobs where appropriate.
- Use labels/selectors to limit API queries.
- Avoid rapid status update loops in custom controllers.

## 25. Interview / Senior-admin Explanation

When explaining API latency troubleshooting as a senior OpenShift administrator, say:

> I first confirm whether latency is client-side or cluster-wide. Then I check API p99 latency from `apiserver_request_duration_seconds_bucket`, break it down by verb, resource, and API server instance, and correlate it with request rate and error codes. If writes are slow, I check admission webhook latency and etcd request latency. If there are 429 errors or queueing, I inspect API Priority and Fairness metrics. If all API servers are slow and etcd WAL fsync, backend commit, peer RTT, or leader changes are abnormal, I treat it as an etcd/control-plane infrastructure issue. If only one API server instance is slow, I inspect that master node, kubelet, API pod logs, and load balancer path. I use audit logs to identify noisy clients, especially repeated LIST calls, GitOps loops, CI/CD bursts, or bad custom controllers. I avoid unsafe control-plane changes and apply targeted mitigation: pause the noisy workload, fix webhooks, restore etcd health, or engage Red Hat support with must-gather and Prometheus evidence.

## 27. Final Summary

API latency troubleshooting in OpenShift is a correlation exercise:

```text
Latency symptom
  -> API p99 by verb/resource/instance
  -> request rate and errors
  -> APF queue/rejection
  -> admission webhook latency
  -> etcd request/disk/network latency
  -> control-plane node pressure
  -> audit logs for noisy clients
  -> safe mitigation
```

For production incidents, the fastest path is usually:

1. Confirm blast radius.
2. Check API p99.
3. Break down by verb/resource/instance.
4. Check request rate and 429/5xx.
5. Check admission webhooks.
6. Check APF queueing.
7. Check etcd latency and leader changes.
8. Identify noisy clients through audit logs.
9. Mitigate only the confirmed root cause.
10. Collect must-gather and evidence for support or RCA.
