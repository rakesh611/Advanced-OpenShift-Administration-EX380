## 1. What Alertmanager Solves

Prometheus is excellent at scraping metrics, storing time series, evaluating PromQL, and generating alerts from `PrometheusRule` resources. Prometheus should not be responsible for every downstream operational workflow such as paging, Slack routing, maintenance muting, notification grouping, or incident escalation. That responsibility belongs to **Alertmanager**.

Alertmanager is the alert notification processing layer. It receives firing and resolved alerts from Prometheus or Thanos Ruler, then decides:

- Should this alert notify anyone?
- Should it be grouped with related alerts?
- Should it be suppressed because a higher-level alert is already firing?
- Should it be muted because a maintenance silence exists?
- Which team owns it?
- Which receiver should get it?
- How often should repeat notifications be sent?
- Should a resolved notification be sent?

In OpenShift, Alertmanager is not normally installed manually. It is part of the managed monitoring stack. The Cluster Monitoring Operator and Prometheus Operator manage the Alertmanager deployment, configuration reloads, certificates, service discovery, and integration with the OpenShift web console.

### Simple mental model

```text
Metrics target
   ↓
Prometheus / Thanos Ruler evaluates alerting rule
   ↓
Alert becomes Pending
   ↓
Alert becomes Firing after for: duration
   ↓
Alert sent to Alertmanager
   ↓
Alertmanager groups, deduplicates, silences, inhibits, routes
   ↓
Receiver: PagerDuty / Slack / Email / Webhook / Microsoft Teams / Opsgenie / ticketing
```

### Alertmanager in one line

**Prometheus decides that something is wrong; Alertmanager decides who should know, when, how often, and whether they should be notified at all.**

## 2. OpenShift Monitoring Architecture Context

OpenShift monitoring is operator-managed. This matters because a senior administrator must know which objects can be safely configured and which objects are reconciled by operators.

### Main operators

| Component | Role |
|---|---|
| Cluster Version Operator, CVO | Deploys and manages cluster operators, including the Cluster Monitoring Operator. |
| Cluster Monitoring Operator, CMO | Owns the OpenShift monitoring stack lifecycle. Deploys and manages Prometheus, Alertmanager, Thanos Querier, Telemeter Client, metrics targets, and monitoring configuration. |
| Prometheus Operator | Creates and manages Prometheus, Alertmanager, Thanos Ruler, `ServiceMonitor`, `PodMonitor`, `PrometheusRule`, and related custom resources. |

### Default platform monitoring namespace

```text
openshift-monitoring
```

Typical platform monitoring resources include:

```bash
oc -n openshift-monitoring get pods
oc -n openshift-monitoring get prometheus
oc -n openshift-monitoring get alertmanager
oc -n openshift-monitoring get prometheusrule
oc -n openshift-monitoring get secret alertmanager-main
oc -n openshift-monitoring get configmap cluster-monitoring-config
```

Common platform components:

```text
prometheus-k8s
alertmanager-main
thanos-querier
cluster-monitoring-operator
prometheus-operator
kube-state-metrics
openshift-state-metrics
node-exporter
telemeter-client
monitoring-plugin
```

### User workload monitoring namespace

When user workload monitoring is enabled, OpenShift creates a separate namespace:

```text
openshift-user-workload-monitoring
```

Typical user workload monitoring resources include:

```bash
oc -n openshift-user-workload-monitoring get pods
oc -n openshift-user-workload-monitoring get prometheus
oc -n openshift-user-workload-monitoring get thanosruler
oc -n openshift-user-workload-monitoring get alertmanager
oc -n openshift-user-workload-monitoring get configmap user-workload-monitoring-config
```

Common user workload components:

```text
prometheus-user-workload
thanos-ruler-user-workload
prometheus-operator
alertmanager-user-workload    # optional, only if dedicated user workload Alertmanager is enabled
```

### Important administration principle

Do not manually edit operator-generated StatefulSets, Deployments, Services, or pods for monitoring components. They are reconciled. Use supported configuration surfaces:

- `cluster-monitoring-config` in `openshift-monitoring`
- `user-workload-monitoring-config` in `openshift-user-workload-monitoring`
- `alertmanager-main` secret for platform Alertmanager routing
- `alertmanager-user-workload` secret for dedicated user workload Alertmanager routing
- `AlertmanagerConfig` custom resources for namespace-scoped user alert routing
- OpenShift web console alerting configuration pages

## 3. Alert Flow End-to-End

### Platform alert flow

```text
OpenShift platform components
   ↓ metrics scraped by
Prometheus k8s in openshift-monitoring
   ↓ alert rules evaluated by
Prometheus k8s
   ↓ alerts sent to
Alertmanager main in openshift-monitoring
   ↓ routes to
Platform receivers: NOC, SRE, PagerDuty, Slack, email, webhook
```

### User workload alert flow

There are two common models.

#### Model A: User alerts routed through platform Alertmanager

```text
Application namespace
   ↓ metrics scraped by
prometheus-user-workload
   ↓ alert rules evaluated by
Thanos Ruler user-workload or prometheus-user-workload depending on configuration
   ↓ alerts sent to
alertmanager-main in openshift-monitoring
   ↓ routes separate platform and user alerts using labels
```

#### Model B: User alerts routed through dedicated user workload Alertmanager

```text
Application namespace
   ↓ metrics scraped by
prometheus-user-workload
   ↓ alert rules evaluated by
Thanos Ruler user-workload or prometheus-user-workload
   ↓ alerts sent to
alertmanager-user-workload in openshift-user-workload-monitoring
   ↓ routes to application team receivers
```

### Alert state lifecycle

| State | Meaning |
|---|---|
| Inactive | The PromQL expression is false. |
| Pending | The expression is true, but the `for:` duration has not completed. |
| Firing | The expression has remained true for the full `for:` duration. Alert is sent to Alertmanager. |
| Resolved | The expression becomes false. Alertmanager can send resolved notifications if receiver supports and enables them. |

Example rule:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: example-app-rules
  namespace: app-prod
spec:
  groups:
  - name: app-prod.availability
    rules:
    - alert: AppHighErrorRate
      expr: |
        sum(rate(http_requests_total{namespace="app-prod",code=~"5.."}[5m]))
        /
        sum(rate(http_requests_total{namespace="app-prod"}[5m]))
        > 0.05
      for: 10m
      labels:
        severity: critical
        team: app-platform
        service: frontend
      annotations:
        summary: "High HTTP 5xx error rate for frontend"
        description: "Frontend 5xx ratio is above 5% for more than 10 minutes."
```

Prometheus or Thanos Ruler evaluates this rule. Alertmanager does not evaluate the PromQL. Alertmanager only receives the generated alert with labels and annotations.

## 4. Core Alertmanager Concepts

Alertmanager has several core functions. For advanced OpenShift administration, you must understand each one separately.

### 4.1 Grouping

Grouping combines related alerts into one notification.

Example:

```text
100 pods fail readiness after a node/network issue.
Without grouping: 100 notifications.
With grouping by cluster, namespace, and alertname: 1 notification containing 100 alert instances.
```

Typical grouping labels:

```yaml
group_by:
- cluster
- namespace
- alertname
```

Bad grouping example:

```yaml
group_by:
- pod
- instance
- container
```

This often creates too many groups and notification storms.

### 4.2 Deduplication

Alertmanager deduplicates repeated alerts. Prometheus continues sending active alerts to Alertmanager, but Alertmanager does not notify every time it receives the same alert fingerprint.

The alert fingerprint is based on labels. If labels change frequently, Alertmanager treats the alert as a new alert.

Bad alert labels:

```yaml
labels:
  severity: warning
  timestamp: "{{ $value }}"
```

Do not put changing values in labels. Put dynamic data in annotations.

Good alert structure:

```yaml
labels:
  severity: warning
  team: app-platform
annotations:
  current_value: "{{ $value }}"
```

### 4.3 Routing

Routing decides which receiver should get an alert. Routing is label-based.

Example:

```yaml
route:
  receiver: default
  routes:
  - matchers:
    - severity="critical"
    receiver: pagerduty-critical
  - matchers:
    - team="database"
    receiver: database-slack
```

### 4.4 Receivers

Receivers define destination systems. Examples:

- PagerDuty
- Slack
- Email
- Webhook
- Microsoft Teams
- Opsgenie
- Jira or ticketing webhook
- Internal event bus
- Custom incident automation API

### 4.5 Silences

A silence mutes notifications for matching alerts during a defined time window.

Use case:

```text
You are patching worker nodes from 22:00 to 23:00.
Create a silence for node maintenance alerts during that period.
```

Silence does not stop rule evaluation. The alert still fires; Alertmanager simply does not notify receivers for matching alerts.

### 4.6 Inhibition

Inhibition suppresses lower-level alerts when a higher-level alert is firing.

Example:

```text
NodeDown is firing.
Do not send PodNotReady, KubeletDown, ContainerRestarting, and EndpointUnavailable alerts for the same node.
```

### 4.7 Templates

Templates customize notification text. Alertmanager uses Go templating. Templates can format alert summaries, add runbook links, display labels, and build receiver-specific messages.

### 4.8 High availability

Alertmanager supports HA clustering. Multiple replicas exchange notification state to prevent duplicate notifications and preserve silence/notification state.

In OpenShift, HA behavior is managed by the monitoring operators. As an administrator, you verify pods, configuration, peer connectivity, and service health rather than manually starting Alertmanager with custom flags.

## 6. Platform Alerts vs User-Defined Alerts

OpenShift separates two alert ownership models.

### Platform alerts

Platform alerts are generated by OpenShift and Kubernetes control plane or infrastructure components:

- API server
- etcd
- kubelet
- node exporter
- cluster operators
- machine config
- ingress
- image registry
- monitoring stack itself
- storage operators
- network operators

Platform alerts are owned by cluster administrators, SRE, platform engineering, or NOC teams.

### User-defined alerts

User-defined alerts are created by application teams in non-OpenShift namespaces using `PrometheusRule` resources.

Examples:

- Application latency high
- API error rate high
- Queue backlog high
- Database connection pool exhausted
- Business transaction failure rate high
- Custom service health failure

### Why separation matters

If all alerts go to one receiver, nobody owns them. OpenShift administrators should design alert routing so that:

- Cluster-critical platform alerts page platform/on-call teams.
- Application alerts go to application owners.
- Warning alerts usually go to Slack/email/ticketing.
- Critical alerts go to paging systems.
- Watchdog alerts verify notification pipeline health.

### `openshift_io_alert_source` label

OpenShift can add a source label to distinguish platform and user-defined alerts when routing through the platform Alertmanager.

Common routing pattern:

```yaml
routes:
- matchers:
  - openshift_io_alert_source="platform"
  receiver: platform-team
- matchers:
  - openshift_io_alert_source!="platform"
  receiver: app-team-default
```

Use this only when platform and user-defined alerts share the same Alertmanager. If you enable a separate dedicated user workload Alertmanager, this separation is handled by using different Alertmanager instances.

## 7. Alertmanager Configuration Model

Alertmanager configuration is YAML. In OpenShift, there are two different configuration styles you will encounter.

### 7.1 Native Alertmanager YAML

This is used in secrets such as:

```text
openshift-monitoring/alertmanager-main
openshift-user-workload-monitoring/alertmanager-user-workload
```

Native Alertmanager YAML uses snake_case keys:

```yaml
global:
  resolve_timeout: 5m
route:
  receiver: default
  group_by:
  - alertname
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
receivers:
- name: default
```

### 7.2 `AlertmanagerConfig` custom resource YAML

This is a Kubernetes custom resource used for namespace-scoped user-defined alert routing.

It uses camelCase keys:

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
metadata:
  name: app-routing
  namespace: app-prod
spec:
  route:
    receiver: app-webhook
    groupBy:
    - namespace
    - alertname
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 4h
  receivers:
  - name: app-webhook
    webhookConfigs:
    - url: https://example.org/alert-webhook
```

### 7.3 Important difference

| Native Alertmanager secret | AlertmanagerConfig CR |
|---|---|
| `group_by` | `groupBy` |
| `group_wait` | `groupWait` |
| `group_interval` | `groupInterval` |
| `repeat_interval` | `repeatInterval` |
| `webhook_configs` | `webhookConfigs` |
| `pagerduty_configs` | `pagerDutyConfigs` |
| `slack_configs` | `slackConfigs` |

A common administrator mistake is copying native Alertmanager YAML into an `AlertmanagerConfig` CR without converting key names.

## 8. Routing Tree Deep Dive

Alertmanager routes are a tree. Every alert enters at the root route. The root route must have a default receiver.

### Basic route

```yaml
route:
  receiver: default
receivers:
- name: default
```

This is valid but not useful. It catches everything and does not differentiate severity, team, service, or source.

### Production-style route

```yaml
route:
  receiver: default
  group_by:
  - cluster
  - namespace
  - alertname
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
  - matchers:
    - alertname="Watchdog"
    receiver: watchdog
    repeat_interval: 2m

  - matchers:
    - openshift_io_alert_source="platform"
    - severity="critical"
    receiver: platform-critical-pager

  - matchers:
    - openshift_io_alert_source="platform"
    - severity="warning"
    receiver: platform-warning-slack

  - matchers:
    - openshift_io_alert_source!="platform"
    - severity="critical"
    receiver: app-critical-default

  - matchers:
    - openshift_io_alert_source!="platform"
    receiver: app-warning-default
```

### How Alertmanager chooses a route

The alert enters the root route. Alertmanager evaluates child routes. If a child route matches, the alert is sent to that child receiver. By default, once a matching child route is found, sibling routes are not evaluated unless `continue: true` is set.

### `continue: true`

Use `continue: true` when the same alert should go to multiple receivers.

Example:

```yaml
routes:
- matchers:
  - severity="critical"
  receiver: pagerduty
  continue: true
- matchers:
  - severity="critical"
  receiver: critical-slack
```

This sends critical alerts to PagerDuty and Slack.

Use carefully. Overuse creates duplicate notifications.

### Matcher syntax

Common matchers:

```yaml
matchers:
- severity="critical"
- namespace="app-prod"
- team=~"database|platform"
- alertname!="Watchdog"
- openshift_io_alert_source!="platform"
```

Recommended style for newer Alertmanager compatibility:

```yaml
matchers:
- 'severity="critical"'
- 'team=~"platform|database"'
```

Keep matcher values quoted, especially for empty strings and regular expressions.

### Route by severity

```yaml
routes:
- matchers:
  - severity="critical"
  receiver: pagerduty-critical
- matchers:
  - severity="warning"
  receiver: slack-warning
- matchers:
  - severity="info"
  receiver: null
```

### Route by team

```yaml
routes:
- matchers:
  - team="network"
  receiver: network-team
- matchers:
  - team="database"
  receiver: database-team
- matchers:
  - team="platform"
  receiver: platform-team
```

### Route by namespace

```yaml
routes:
- matchers:
  - namespace=~"prod-.*"
  receiver: production-oncall
- matchers:
  - namespace=~"dev-.*|test-.*"
  receiver: nonprod-slack
```

### Null receiver pattern

A receiver with no configs acts like a sink.

```yaml
receivers:
- name: null
```

Use this for intentionally dropping low-value notifications. Do not use it to hide unresolved production problems.

## 9. Receivers and Notification Integrations

Alertmanager supports many receivers. In OpenShift, the commonly configured receiver types are:

- PagerDuty
- Webhook
- Email
- Slack
- Microsoft Teams

Other upstream integrations may also be available depending on the Alertmanager version shipped with your OpenShift version.

### 9.1 Webhook receiver

Webhook is the most flexible integration. Many enterprises route Alertmanager notifications to an internal webhook that creates incidents, tickets, chats, or automation.

```yaml
receivers:
- name: platform-webhook
  webhook_configs:
  - url: https://alerts.example.com/api/v1/alertmanager
    send_resolved: true
    max_alerts: 0
```

Webhook payload includes status, receiver, group labels, common labels, annotations, external URL, and alert list.

### 9.2 Slack receiver

```yaml
receivers:
- name: platform-slack
  slack_configs:
  - api_url: https://hooks.slack.com/services/REDACTED/REDACTED/REDACTED
    channel: '#ocp-alerts'
    send_resolved: true
    title: '{{ .CommonLabels.alertname }}'
    text: >-
      {{ range .Alerts }}
      *Severity:* {{ .Labels.severity }}
      *Namespace:* {{ .Labels.namespace }}
      *Summary:* {{ .Annotations.summary }}
      {{ end }}
```

In production, avoid plain-text webhook URLs in Git. Use mounted secrets when supported.

### 9.3 PagerDuty receiver

```yaml
receivers:
- name: platform-critical-pager
  pagerduty_configs:
  - routing_key: REDACTED
    send_resolved: true
    severity: '{{ .CommonLabels.severity }}'
    description: '{{ .CommonAnnotations.summary }}'
```

For production, prefer reading integration keys from mounted secret files where supported by your Alertmanager version.

### 9.4 Email receiver

```yaml
receivers:
- name: platform-email
  email_configs:
  - to: ocp-admins@example.com
    from: alertmanager@example.com
    smarthost: smtp.example.com:587
    auth_username: alertmanager@example.com
    auth_password: REDACTED
    send_resolved: true
```

Email is useful for warnings and daily operational visibility. It is usually not reliable enough for critical production paging unless tied to an escalation workflow.

### 9.5 Microsoft Teams receiver

OpenShift documentation lists Microsoft Teams as a supported receiver type for alert notifications. The exact upstream key depends on the Alertmanager version, such as `msteams_configs` or `msteamsv2_configs`. Always validate with the Alertmanager configuration reference for your OpenShift monitoring component version.

### 9.6 Receiver design principle

Do not design receivers by technology only. Design them by ownership and urgency.

Bad receiver design:

```text
one-slack-channel-for-everything
```

Better receiver design:

```text
platform-critical-pager
platform-warning-slack
network-critical-pager
database-critical-pager
app-team-a-warning-slack
watchdog-deadman
```

## 10. Silences

A silence prevents notifications for alerts that match a set of labels during a defined time window.

### Important properties

- Silences are time-bound.
- Silences are matcher-based.
- Silences do not stop alert rules from firing.
- Silences do not change alert state in Prometheus.
- Silences only affect notifications.
- Silences should include a clear author and comment.

### Good silence use cases

- Planned node maintenance
- Cluster upgrade window
- Storage migration
- Known application deployment outage
- Temporary suppression during incident mitigation

### Bad silence use cases

- Permanently hiding noisy alerts
- Suppressing all alerts for an entire cluster without incident approval
- Muting critical etcd or API server alerts because they are inconvenient
- Silencing by broad regex such as `namespace=~".*"` without strict duration

### Silence examples with `amtool`

Depending on authentication and access method, `amtool` may require port-forwarding or a route with token/certificate access.

Create a two-hour silence for one namespace:

```bash
amtool silence add \
  alertname=KubePodCrashLooping \
  namespace=app-prod \
  --duration=2h \
  --author="rakesh" \
  --comment="Planned app-prod deployment maintenance"
```

List silences:

```bash
amtool silence query
```

Expire a silence:

```bash
amtool silence expire <silence-id>
```

### OpenShift console method

In OpenShift web console:

```text
Observe → Alerting → Alerts → select alert → Silence alert
```

Required roles depend on whether the user is managing platform alerts or project/user-defined alerts.

## 11. Inhibition Rules

Inhibition suppresses notifications for target alerts when source alerts are already firing.

### Example scenario

If a node is down, many pod alerts on that node may fire. You usually want the node-level alert, not 200 pod-level pages.

### Example inhibition rule

```yaml
inhibit_rules:
- source_matchers:
  - alertname="KubeNodeNotReady"
  - severity="critical"
  target_matchers:
  - severity=~"warning|critical"
  equal:
  - cluster
  - node
```

Meaning:

```text
If KubeNodeNotReady critical is firing for node X,
suppress warning/critical target alerts that have the same cluster and node labels.
```

### Another common inhibition pattern

Suppress warning alerts when critical alerts for the same alert and namespace are firing:

```yaml
inhibit_rules:
- source_matchers:
  - severity="critical"
  target_matchers:
  - severity="warning"
  equal:
  - cluster
  - namespace
  - alertname
```

### Inhibition best practices

- Use `equal` labels carefully.
- Inhibit lower-level symptoms, not unrelated alerts.
- Never inhibit the root-cause alert.
- Document the reason for each inhibition rule.
- Test inhibition with controlled alerts before production rollout.

## 12. Grouping, Deduplication, and Timing

Alertmanager timing controls are critical for reducing noise.

### Key timing fields

| Field | Meaning |
|---|---|
| `group_wait` | How long to wait before sending first notification for a new group. Allows related alerts to arrive and be batched. |
| `group_interval` | How long to wait before sending an update for an existing group when new alerts join the group. |
| `repeat_interval` | Minimum time before repeating a notification for still-firing alerts. |

### Common baseline

```yaml
route:
  group_by:
  - cluster
  - namespace
  - alertname
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
```

### Critical alert tuning

For critical platform alerts:

```yaml
routes:
- matchers:
  - severity="critical"
  receiver: platform-critical-pager
  group_wait: 15s
  group_interval: 2m
  repeat_interval: 1h
```

### Warning alert tuning

For warning alerts:

```yaml
routes:
- matchers:
  - severity="warning"
  receiver: platform-warning-slack
  group_wait: 2m
  group_interval: 10m
  repeat_interval: 12h
```

### Watchdog tuning

Watchdog is different. It is intentionally always firing. Its receiver should confirm that notifications are still flowing.

```yaml
routes:
- matchers:
  - alertname="Watchdog"
  receiver: watchdog
  repeat_interval: 2m
```

The external receiver should alert you if it stops receiving Watchdog notifications.

### Label stability and deduplication

Alertmanager deduplication depends on stable labels.

Avoid labels such as:

```yaml
labels:
  value: "{{ $value }}"
  current_time: "{{ now }}"
  random_id: "{{ $labels.pod }}-{{ $value }}"
```

Use annotations for dynamic values:

```yaml
annotations:
  current_value: "{{ $value }}"
```

## 13. High Availability Behavior

OpenShift deploys Alertmanager as an operator-managed workload. The exact replica count and deployment details can vary by OpenShift version and configuration, so always inspect the running cluster.

```bash
oc -n openshift-monitoring get alertmanager
oc -n openshift-monitoring get statefulset alertmanager-main -o wide
oc -n openshift-monitoring get pods -l alertmanager=main -o wide
```

### How Alertmanager HA works conceptually

Multiple Alertmanager replicas form a cluster. They exchange alert notification state and silence state. This reduces duplicate notifications and avoids losing alerting capability when one pod fails.

### What HA does not mean

Alertmanager HA does not mean:

- Every receiver will never see duplicates.
- Bad routing configuration is automatically fixed.
- Receiver outages are solved.
- Alerts are permanently stored like metrics.
- Long-term audit history is guaranteed.

### Why Prometheus should target all Alertmanager replicas

In upstream Prometheus architecture, Prometheus should know about all Alertmanager replicas rather than relying on a generic load balancer that hides them. The Prometheus Operator handles this service discovery in OpenShift-managed monitoring.

### HA checks

```bash
oc -n openshift-monitoring get pods | grep alertmanager
oc -n openshift-monitoring describe pod alertmanager-main-0
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager
oc -n openshift-monitoring logs alertmanager-main-0 -c config-reloader
oc -n openshift-monitoring get events --sort-by=.lastTimestamp | tail -50
```

Check for:

- Peer connection errors
- Configuration reload failures
- Secret mount errors
- Certificate rotation events
- Pod restarts
- NetworkPolicy or proxy egress issues
- Receiver HTTP errors

## 14. Secrets, TLS, Proxy, and Secure Receiver Authentication

Alertmanager often needs credentials to talk to external systems. Examples:

- Slack webhook URL
- PagerDuty routing key
- SMTP password
- Webhook bearer token
- Client TLS certificate
- Private CA bundle
- Proxy credentials

### 14.1 Platform Alertmanager secrets

Create a secret in `openshift-monitoring`:

```bash
oc -n openshift-monitoring create secret generic pagerduty-routing-key \
  --from-literal=routing_key='REDACTED'
```

Mount it into platform Alertmanager by adding it to `cluster-monitoring-config`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    alertmanagerMain:
      secrets:
      - pagerduty-routing-key
```

After mounting, the file path inside the Alertmanager container is typically:

```text
/etc/alertmanager/secrets/pagerduty-routing-key/routing_key
```

Use file-based configuration where supported:

```yaml
receivers:
- name: platform-critical-pager
  pagerduty_configs:
  - routing_key_file: /etc/alertmanager/secrets/pagerduty-routing-key/routing_key
```

### 14.2 User workload Alertmanager secrets

For a dedicated user workload Alertmanager, create the secret in `openshift-user-workload-monitoring`:

```bash
oc -n openshift-user-workload-monitoring create secret generic slack-webhook \
  --from-literal=url='REDACTED'
```

Mount it through `user-workload-monitoring-config`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    alertmanager:
      secrets:
      - slack-webhook
```

Then reference the mounted file:

```yaml
receivers:
- name: app-slack
  slack_configs:
  - api_url_file: /etc/alertmanager/secrets/slack-webhook/url
    channel: '#app-alerts'
```

### 14.3 Proxy configuration

If your cluster uses an HTTP/HTTPS proxy and Alertmanager must send notifications externally, configure receiver HTTP settings to use environment proxy variables.

Example:

```yaml
global:
  http_config:
    proxy_from_environment: true
```

Or per receiver:

```yaml
receivers:
- name: platform-webhook
  webhook_configs:
  - url: https://alerts.example.com/api
    http_config:
      proxy_from_environment: true
```

### 14.4 Private CA certificate

If the receiver uses a private CA, mount the CA certificate as a secret and reference it from `tls_config` or receiver `http_config`.

Example concept:

```yaml
receivers:
- name: internal-webhook
  webhook_configs:
  - url: https://alert-gateway.corp.example.com/api/v1/events
    http_config:
      tls_config:
        ca_file: /etc/alertmanager/secrets/internal-ca/ca.crt
```

Validate exact field support against your shipped Alertmanager version.

```bash

```

### 15.3 Example platform routing configuration

This is a training-quality example. Customize receivers and secrets for your environment.

```yaml
global:
  resolve_timeout: 5m
  http_config:
    proxy_from_environment: true

route:
  receiver: default
  group_by:
  - cluster
  - namespace
  - alertname
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
  - matchers:
    - alertname="Watchdog"
    receiver: watchdog
    repeat_interval: 2m

  - matchers:
    - openshift_io_alert_source="platform"
    - severity="critical"
    receiver: platform-critical-pager

  - matchers:
    - openshift_io_alert_source="platform"
    - severity="warning"
    receiver: platform-warning-slack

  - matchers:
    - openshift_io_alert_source!="platform"
    - severity="critical"
    receiver: app-critical-default

  - matchers:
    - openshift_io_alert_source!="platform"
    receiver: app-warning-default

receivers:
- name: default

- name: watchdog
  webhook_configs:
  - url_file: /etc/alertmanager/secrets/watchdog-webhook/url
    send_resolved: false

- name: platform-critical-pager
  pagerduty_configs:
  - routing_key_file: /etc/alertmanager/secrets/pagerduty-routing-key/routing_key
    send_resolved: true

- name: platform-warning-slack
  slack_configs:
  - api_url_file: /etc/alertmanager/secrets/slack-webhook/url
    channel: '#ocp-platform-alerts'
    send_resolved: true

- name: app-critical-default
  webhook_configs:
  - url: https://alert-router.example.com/app-critical
    send_resolved: true

- name: app-warning-default
  webhook_configs:
  - url: https://alert-router.example.com/app-warning
    send_resolved: true

inhibit_rules:
- source_matchers:
  - severity="critical"
  target_matchers:
  - severity="warning"
  equal:
  - cluster
  - namespace
  - alertname
```

User workload alerting is important in OpenShift because platform administrators should not become the only team capable of routing application alerts.

### 16.1 Enable user workload monitoring

Create or edit `cluster-monitoring-config`:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Add:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get pods
```

Expected components include:

```text
prometheus-operator
prometheus-user-workload-0
prometheus-user-workload-1
thanos-ruler-user-workload-0
thanos-ruler-user-workload-1
```

### 16.2 Enable user-defined alert routing with default platform Alertmanager

This model allows user-defined routes through the platform Alertmanager.

Example configuration pattern:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
    alertmanagerMain:
      enableUserAlertmanagerConfig: true
```

> Field names can differ across OpenShift versions. Verify with your version documentation and `oc explain` where available.

### 16.3 Enable dedicated user workload Alertmanager

For stronger separation, enable an Alertmanager instance dedicated to user workloads.

Edit:

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Example configuration pattern:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    alertmanager:
      enabled: true
      enableAlertmanagerConfig: true
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get alertmanager
oc -n openshift-user-workload-monitoring get pods | grep alertmanager
```

### 16.4 Grant permission to configure alert routing

Application owners need `alert-routing-edit` in their namespace.

```bash
oc -n app-prod adm policy add-role-to-user alert-routing-edit rakesh
```

Verify:

```bash
oc auth can-i create alertmanagerconfigs.monitoring.coreos.com -n app-prod --as rakesh
oc auth can-i update alertmanagerconfigs.monitoring.coreos.com -n app-prod --as rakesh
```

### 16.5 Create namespace-scoped `AlertmanagerConfig`

Example:

```yaml
apiVersion: monitoring.coreos.com/v1beta1
kind: AlertmanagerConfig
metadata:
  name: app-prod-routing
  namespace: app-prod
spec:
  route:
    receiver: app-prod-webhook
    groupBy:
    - namespace
    - alertname
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 4h
    routes:
    - matchers:
      - name: severity
        value: critical
        matchType: =
      receiver: app-prod-critical
  receivers:
  - name: app-prod-webhook
    webhookConfigs:
    - url: https://alert-router.example.com/app-prod-warning
      sendResolved: true
  - name: app-prod-critical
    webhookConfigs:
    - url: https://alert-router.example.com/app-prod-critical
      sendResolved: true
```

Apply:

```bash
oc apply -f app-prod-alertmanagerconfig.yaml
```

Verify:

```bash
oc -n app-prod get alertmanagerconfig
oc -n app-prod describe alertmanagerconfig app-prod-routing
```

### 16.6 Namespace scope limitation

A user-defined `AlertmanagerConfig` is scoped to the namespace where it is created. A route in namespace `app-prod` applies to alerting rules in `app-prod`; it does not become a global cluster route.

This is by design. It prevents one application team from hijacking alert routing for another team.

## 17. Using External Alertmanager Instances

Large enterprises sometimes centralize alerting across clusters. Instead of each OpenShift cluster owning final notification routing, each cluster forwards alerts to an external Alertmanager or central alert gateway.

### Use cases

- Multi-cluster alert consolidation
- Centralized NOC/SOC integration
- Shared incident automation
- Global routing policies
- Standardized compliance and audit workflows

### Configure platform Prometheus to send to external Alertmanager

Edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      additionalAlertmanagerConfigs:
      - scheme: https
        pathPrefix: /
        timeout: "30s"
        apiVersion: v2
        staticConfigs:
        - external-alertmanager1.example.com:9093
        - external-alertmanager2.example.com:9093
```

If authentication is required, configure bearer token or TLS references according to supported fields for your OpenShift version.

### Disable local platform Alertmanager

Only do this if you have a tested external alerting path.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    alertmanagerMain:
      enabled: false
```

### Production warning

Before disabling local Alertmanager, verify:

- External Alertmanager is reachable from Prometheus pods.
- TLS trust is correct.
- Authentication is correct.
- Watchdog reaches external receiver.
- Critical alert test reaches on-call channel.
- Upgrade and maintenance ownership is clear.
- NetworkPolicy/firewall/proxy permits egress.

## 20. Troubleshooting Playbook

### Problem 1: Alert is firing in console but no notification received

Check whether alert exists in Alertmanager:

```bash
oc -n openshift-monitoring get pods | grep alertmanager
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=200
```

Check route matchers:

```bash
oc -n openshift-monitoring get secret alertmanager-main \
  --template='{{ index .data "alertmanager.yaml" }}' | base64 --decode > /tmp/alertmanager.yaml

grep -n "receiver\|matchers\|severity\|team\|namespace" /tmp/alertmanager.yaml
```

Check alert labels in console or Prometheus:

```promql
ALERTS{alertstate="firing"}
```

Most common causes:

- Alert labels do not match route matchers.
- Alert is silenced.
- Alert is inhibited.
- Receiver config is wrong.
- Secret path is wrong.
- External receiver is unreachable.
- Proxy or CA is not configured.
- `send_resolved` expectation is wrong.
- `repeat_interval` is long, so repeated notification has not occurred yet.

### Problem 2: Alertmanager configuration not loading

Check logs:

```bash
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=200
oc -n openshift-monitoring logs alertmanager-main-0 -c config-reloader --tail=200
```

Validate config:

```bash
amtool check-config alertmanager.yaml
```

Common causes:

- YAML indentation error
- Wrong key name, for example `groupBy` in native Alertmanager YAML
- Invalid matcher syntax
- Receiver referenced in route but not defined
- Secret file path does not exist
- Unsupported receiver field for shipped Alertmanager version

### Problem 3: User `AlertmanagerConfig` not working

Check prerequisites:

```bash
oc get alertmanagerconfig -A
oc -n app-prod get alertmanagerconfig
oc auth can-i create alertmanagerconfigs.monitoring.coreos.com -n app-prod --as <user>
oc -n openshift-user-workload-monitoring get pods
```

Check whether user workload monitoring is enabled:

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config -o yaml
```

Check whether alert routing is enabled for user-defined projects.

Common causes:

- User workload monitoring not enabled.
- Alert routing for user-defined projects not enabled.
- User lacks `alert-routing-edit`.
- `AlertmanagerConfig` created in wrong namespace.
- Alert rule is in namespace `app-prod`, but `AlertmanagerConfig` is in namespace `monitoring`.
- CR uses native Alertmanager snake_case keys instead of camelCase.
- Namespace is excluded from user workload monitoring.

### Problem 4: Too many notifications

Check route grouping:

```yaml
group_by:
- cluster
- namespace
- alertname
```

Avoid grouping by high-cardinality labels:

```yaml
# Avoid unless intentional
group_by:
- pod
- container
- endpoint
- instance
```

Check rule labels:

```bash
oc get prometheusrule -A -o yaml | grep -n "labels:" -A10
```

Common causes:

- Dynamic values in labels.
- `repeat_interval` too short.
- `group_by` too specific.
- No inhibition rules.
- Alert rules lack `for:` duration.
- Same alert generated by multiple rule groups with different labels.

### Problem 5: Alerts are delayed

Check:

- Prometheus rule `for:` duration
- Alertmanager `group_wait`
- Alertmanager `group_interval`
- Receiver retry behavior
- Network/proxy latency
- Receiver rate limits

Example:

```text
Prometheus rule for: 10m
Alertmanager group_wait: 2m
Receiver API delay: 30s
Total first notification delay can be about 12m30s.
```

### Problem 6: Notifications duplicate

Common causes:

- Multiple Alertmanager instances not clustered correctly.
- Prometheus sending to multiple independent external Alertmanagers.
- `continue: true` sends to multiple receivers intentionally.
- Same alert exists with different labels due to label instability.
- External receiver dedup key is not stable.

Check labels:

```promql
ALERTS{alertname="YourAlert"}
```

Check Alertmanager HA logs:

```bash
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager | grep -i peer
oc -n openshift-monitoring logs alertmanager-main-1 -c alertmanager | grep -i peer
```

### Problem 7: Receiver authentication fails

Check logs:

```bash
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=300 | grep -iE "error|failed|401|403|tls|x509|timeout"
```

Check secret mount:

```bash
oc -n openshift-monitoring exec alertmanager-main-0 -c alertmanager -- \
  ls -l /etc/alertmanager/secrets/
```

Check file exists:

```bash
oc -n openshift-monitoring exec alertmanager-main-0 -c alertmanager -- \
  find /etc/alertmanager/secrets -maxdepth 3 -type f -print
```

Common causes:

- Secret created in wrong namespace.
- Secret not listed in `alertmanagerMain.secrets` or `alertmanager.secrets`.
- Wrong key name inside secret.
- Wrong file path in Alertmanager YAML.
- Receiver token expired.
- Private CA not configured.
- Proxy required but not configured.

## 21. Production Design Best Practices

### 21.1 Define alert ownership labels

Every custom alert should include ownership labels:

```yaml
labels:
  severity: critical
  team: payments
  service: checkout
  environment: prod
```

### 21.2 Use severity consistently

Recommended severity model:

| Severity | Meaning | Receiver |
|---|---|---|
| critical | Immediate user/business/platform impact or high risk | Pager/on-call |
| warning | Degraded, capacity trend, retryable issue | Slack/ticket/email |
| info | Informational; usually no page | Dashboard/ticket/null |

### 21.3 Use runbook annotations

```yaml
annotations:
  summary: "API server error budget burn high"
  description: "API server is consuming error budget too quickly."
  runbook_url: "https://runbooks.example.com/openshift/api-server-error-budget"
```

A critical alert without a runbook causes slow incident response.

### 21.4 Avoid alerting on symptoms without root-cause control

Bad:

```text
Page on every pod restart.
```

Better:

```text
Warn on restart trend.
Page only when service SLO, availability, or customer impact crosses threshold.
```

### 21.5 Configure Watchdog

Watchdog should always fire and be sent to a dead-man receiver. The external system should alert when Watchdog stops arriving.

This detects:

- Alertmanager outage
- Receiver connectivity issue
- Broken routing config
- Proxy/TLS problem
- Notification provider failure

### 21.6 Separate platform and application alert ownership

Do not make platform admins the default owner of all application alerts. Use user-defined alert routing where possible.

### 21.7 Validate before applying

Always:

```bash
amtool check-config alertmanager.yaml
```

For newer matcher compatibility:

```bash
amtool check-config alertmanager.yaml --enable-feature="utf8-strict-mode"
```

### 21.8 Do not put secrets in plaintext Git

Use sealed/encrypted/external secrets.

### 21.9 Prefer file-based secret references

Where supported:

```yaml
routing_key_file: /etc/alertmanager/secrets/pagerduty-routing-key/routing_key
api_url_file: /etc/alertmanager/secrets/slack-webhook/url
url_file: /etc/alertmanager/secrets/webhook-url/url
```

### 21.10 Keep `repeat_interval` sane

Bad:

```yaml
repeat_interval: 5m
```

This can spam on-call during long incidents.

Better:

```yaml
repeat_interval: 1h    # critical
repeat_interval: 12h   # warning
```

### 21.11 Do not silence permanently

A permanent silence means alert debt. Fix the rule, route, threshold, ownership, or underlying issue.

### 21.12 Use inhibition carefully

Good inhibition reduces noise. Bad inhibition hides real incidents.

### 21.13 Design for receiver failure

Ask:

- What happens if Slack is down?
- What happens if PagerDuty API fails?
- What happens if SMTP is blocked?
- What happens if proxy certificate changes?
- What happens if external Alertmanager is down?

### 21.14 Test after cluster upgrades

After OpenShift upgrades:

```bash

oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=100
amtool check-config alertmanager.yaml
```

## 22. Common Mistakes

### Mistake 1: Editing generated pods or StatefulSets

Wrong:

```bash
oc -n openshift-monitoring edit statefulset alertmanager-main
```

The operator will reconcile it.

Correct:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
oc -n openshift-monitoring edit secret alertmanager-main
```

### Mistake 2: Using wrong YAML style

Wrong native Alertmanager YAML:

```yaml
route:
  groupBy:
  - alertname
```

Correct native Alertmanager YAML:

```yaml
route:
  group_by:
  - alertname
```

Correct `AlertmanagerConfig` CR:

```yaml
spec:
  route:
    groupBy:
    - alertname
```

### Mistake 3: No default receiver

Wrong:

```yaml
route:
  routes:
  - matchers:
    - severity="critical"
    receiver: pagerduty
```

Correct:

```yaml
route:
  receiver: default
  routes:
  - matchers:
    - severity="critical"
    receiver: pagerduty
receivers:
- name: default
- name: pagerduty
```

### Mistake 4: Receiver referenced but not defined

Wrong:

```yaml
route:
  receiver: platform-critical
receivers:
- name: default
```

Correct:

```yaml
route:
  receiver: platform-critical
receivers:
- name: platform-critical
```

### Mistake 5: Secret in wrong namespace

Platform Alertmanager secrets must be in:

```text
openshift-monitoring
```

Dedicated user workload Alertmanager secrets must be in:

```text
openshift-user-workload-monitoring
```

Application namespace secrets used by `AlertmanagerConfig` must match the CRD schema and RBAC model.

### Mistake 6: Alert labels do not match routes

Route expects:

```yaml
matchers:
- team="database"
```

But alert has:

```yaml
labels:
  app_team: database
```

No match. No expected receiver.

### Mistake 7: Too broad silences

Dangerous:

```text
severity=critical
```

Safer:

```text
alertname=KubeNodeNotReady
node=worker-1.example.com
```

### Mistake 8: No Watchdog receiver

Without Watchdog/dead-man monitoring, you may not know the notification pipeline is broken.

## 23. Interview and Real-World Scenario Questions

### Q1. What is Alertmanager in OpenShift?

Alertmanager is the notification handling component of the OpenShift monitoring stack. Prometheus or Thanos Ruler evaluates alerting rules and sends firing/resolved alerts to Alertmanager. Alertmanager groups, deduplicates, silences, inhibits, and routes alerts to external receivers such as PagerDuty, Slack, email, webhook, or Microsoft Teams.

### Q2. Difference between Prometheus alerting rule and Alertmanager route?

A Prometheus alerting rule defines the condition for an alert using PromQL. Alertmanager route defines where that alert notification goes after the alert fires.

### Q3. What happens if Alertmanager is down?

Prometheus can still scrape metrics and evaluate rules, but notifications might not be delivered. Depending on HA configuration, another Alertmanager replica may continue processing. If all Alertmanager replicas are unavailable, alert notifications are impacted.

### Q4. What is a silence?

A silence is a time-bound matcher-based mute. Alerts still fire, but matching notifications are not sent while the silence is active.

### Q5. What is inhibition?

Inhibition suppresses notifications for target alerts when a source alert is firing. For example, if a node is down, suppress pod-level alerts from that node.

### Q6. How do you separate platform and application alerts?

Use different routes, labels, receivers, and optionally separate Alertmanager instances. If both alert sources share `alertmanager-main`, route using labels such as `openshift_io_alert_source="platform"` and `openshift_io_alert_source!="platform"`. For stronger separation, enable dedicated user workload Alertmanager.

### Q7. How do developers configure their own alert routing?

After user workload monitoring and user-defined alert routing are enabled, grant users the `alert-routing-edit` role in their namespace. They can then create `AlertmanagerConfig` resources in that namespace.

### Q8. What is the difference between `alertmanager-main` and `alertmanager-user-workload`?

`alertmanager-main` is the platform Alertmanager in `openshift-monitoring`. `alertmanager-user-workload` is an optional dedicated Alertmanager for user-defined project alerts in `openshift-user-workload-monitoring`.

### Q9. Why is grouping important?

Grouping prevents alert storms by combining related alert instances into one notification. Without grouping, a single outage can generate hundreds of pages.

### Q10. How do you validate Alertmanager configuration?

Use:

```bash
amtool check-config alertmanager.yaml
```

Then apply the config and check Alertmanager plus config-reloader logs.

## Final Senior Admin Summary

Alertmanager is one of the most important day-2 OpenShift operations components because it converts raw alert firing events into controlled operational notifications. A good OpenShift administrator does not only check whether alerts are firing. A senior administrator checks whether alerts are owned, routed, grouped, deduplicated, silenced only when appropriate, inhibited correctly, secured with proper secrets, tested with Watchdog, and validated after every monitoring or cluster change.

For production OpenShift, the goal is not “send all alerts.” The goal is **send the right alert, to the right team, with the right urgency, at the right time, with enough context to fix the problem quickly.**
