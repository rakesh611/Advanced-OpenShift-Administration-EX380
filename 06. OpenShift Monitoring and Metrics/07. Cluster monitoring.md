## 1. What Cluster Monitoring Means

In OpenShift, **cluster monitoring** means the built-in monitoring system that collects metrics, evaluates rules, fires alerts, and provides dashboards for the health and performance of the OpenShift platform itself.

It monitors core platform components such as:

- Kubernetes API server
- OpenShift API server
- etcd
- nodes
- kubelet
- CRI-O/container runtime metrics
- ingress/router
- image registry
- cluster operators
- machine config and node state
- persistent volume and storage health indicators
- networking-related metrics
- Prometheus and Alertmanager health
- workload resource usage from the cluster point of view

A senior OpenShift administrator should not treat cluster monitoring as only a UI feature. It is an operational subsystem with its own controllers, custom resources, scrape targets, storage, RBAC, certificates, resource needs, and failure modes.

In production, cluster monitoring answers questions like:

- Is the cluster healthy?
- Which node is overloaded?
- Is etcd latency increasing?
- Is the API server returning errors?
- Are pods being killed due to memory pressure?
- Are persistent volumes filling up?
- Is Prometheus itself failing to scrape targets?
- Are platform alerts reaching the right teams?
- Is monitoring using too much CPU, memory, or disk?

## 2. The OpenShift Monitoring Mental Model

Think of OpenShift monitoring as a layered system:

```text
Applications / Platform Components
        |
        | expose /metrics endpoints
        v
ServiceMonitor / PodMonitor / built-in scrape configuration
        |
        v
Prometheus scrapes metrics and evaluates rules
        |
        +--> Local TSDB storage
        |
        +--> Alertmanager for alerts
        |
        +--> Remote write for external long-term storage, if configured
        |
        v
Thanos Querier provides unified query access
        |
        v
OpenShift Web Console Observe UI / PromQL API / Dashboards
```

For core platform monitoring, Red Hat provides most scrape configuration and rules automatically. You configure the supported parts through the **Cluster Monitoring Operator** rather than editing generated resources directly.

## 3. Core Architecture

OpenShift cluster monitoring is based on the Prometheus ecosystem. The main components are:

| Component | Main Role |
|---|---|
| Cluster Monitoring Operator | Deploys and manages the monitoring stack. |
| Prometheus Operator | Manages Prometheus and Alertmanager custom resources. |
| Prometheus | Scrapes metrics, stores time-series data, evaluates recording and alerting rules. |
| Alertmanager | Deduplicates, groups, inhibits, silences, and routes alerts. |
| Thanos Querier | Provides a single query layer across platform and user workload metrics. |
| Telemeter Client | Sends selected telemetry/health data to Red Hat for connected clusters. |
| kube-state-metrics | Converts Kubernetes object state into metrics. |
| openshift-state-metrics | Adds OpenShift-specific object metrics. |
| node-exporter | Exposes node-level Linux metrics from every node. |
| Metrics Server | Provides resource metrics through `metrics.k8s.io` for tools and APIs. |
| monitoring-plugin | Provides monitoring pages in the OpenShift web console Observe section. |

## 4. Core vs User Workload Monitoring

OpenShift separates monitoring into two areas.

### 4.1 Core Platform Monitoring

Core platform monitoring is installed by default in the `openshift-monitoring` namespace.

It monitors:

- OpenShift system components
- Kubernetes control plane components
- nodes
- cluster operators
- platform services
- platform alerting rules

You configure it with:

```text
Namespace: openshift-monitoring
ConfigMap: cluster-monitoring-config
```

### 4.2 User Workload Monitoring

User workload monitoring is optional and is used to monitor services and pods in user-defined projects.

It runs in:

```text
Namespace: openshift-user-workload-monitoring
ConfigMap: user-workload-monitoring-config
```

It enables developers and project administrators to use resources like:

- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`
- `AlertmanagerConfig`

### 4.3 Why the Separation Matters

The separation protects core platform monitoring from noisy or poorly designed application metrics.

A senior administrator should understand this boundary:

- Do not overload platform Prometheus with custom application metrics.
- Use user workload monitoring for application-specific scraping.
- Keep platform alert rules focused on cluster health.
- Avoid giving developers broad access to `openshift-monitoring`.
- Use RBAC to delegate only the required monitoring permissions.

## 6. Metrics Collection Flow

### 6.1 Platform Metrics Flow

```text
Platform component exposes /metrics
        |
Prometheus scrape config discovers endpoint
        |
Prometheus scrapes metrics periodically
        |
Metrics stored in Prometheus TSDB
        |
Rules evaluated
        |
Alerts sent to Alertmanager
        |
Dashboards and API query through Thanos Querier
```

### 6.2 Example: Node CPU Metric Flow

1. `node-exporter` runs on every node.
2. It exposes Linux node metrics.
3. Platform Prometheus scrapes `node-exporter`.
4. Prometheus stores metrics such as `node_cpu_seconds_total`.
5. Dashboards and alerts query CPU saturation.
6. Thanos Querier exposes query results to the console/API.

### 6.3 Example: Kubernetes Object State Flow

1. `kube-state-metrics` watches Kubernetes API objects.
2. It converts object state into metrics.
3. Prometheus scrapes those metrics.
4. Administrators query deployment, pod, PVC, node, and quota state.

Example metrics:

```text
kube_pod_status_phase
kube_deployment_status_replicas_available
kube_node_status_condition
kube_persistentvolumeclaim_status_phase
```

## 7. Cluster Monitoring Operator

The **Cluster Monitoring Operator**, often shortened to **CMO**, is the main management point for OpenShift monitoring.

It manages:

- platform Prometheus
- Alertmanager
- Thanos Querier
- Telemeter Client
- metrics targets
- monitoring plugin resources
- configuration reconciliation

### 7.1 Check Cluster Monitoring Operator Health

```bash
oc get co monitoring
oc describe co monitoring
```

Check pods:

```bash
oc -n openshift-monitoring get pods
oc -n openshift-monitoring logs deploy/cluster-monitoring-operator
```

Check recent events:

```bash
oc -n openshift-monitoring get events --sort-by=.lastTimestamp | tail -50
```

### 7.2 Important Operator Behavior

CMO is a reconciler. If you manually edit generated objects, CMO can overwrite your changes.

Do not manually patch these unless Red Hat support instructs you:

- generated Prometheus StatefulSets
- generated Alertmanager StatefulSets
- generated scrape configs
- generated service accounts
- generated cluster roles
- generated secrets managed by the stack

Use supported configuration through:

```text
openshift-monitoring/cluster-monitoring-config
openshift-user-workload-monitoring/user-workload-monitoring-config
```

### 7.3 Common CMO Failure Causes

- invalid YAML in `cluster-monitoring-config`
- unsupported configuration field
- invalid node selector or impossible scheduling constraints
- missing storage class
- PVC cannot bind
- insufficient CPU/memory on selected nodes
- taints without matching tolerations
- certificate or API access issue
- failing Prometheus Operator

## 8. Prometheus in Cluster Monitoring

Prometheus is the core metrics engine.

It performs three major jobs:

1. Scrapes metrics from targets.
2. Stores time-series data locally.
3. Evaluates rules and sends alerts to Alertmanager.

### 8.1 Prometheus StatefulSet

Platform Prometheus usually runs as:

```bash
oc -n openshift-monitoring get statefulset prometheus-k8s
oc -n openshift-monitoring get pods -l app.kubernetes.io/name=prometheus
```

Typical pods:

```text
prometheus-k8s-0
prometheus-k8s-1
```

### 8.2 Check Prometheus Custom Resource

```bash
oc -n openshift-monitoring get prometheus
oc -n openshift-monitoring describe prometheus k8s
```

### 8.3 Check Prometheus Logs

```bash
oc -n openshift-monitoring logs prometheus-k8s-0 -c prometheus --tail=100
oc -n openshift-monitoring logs prometheus-k8s-1 -c prometheus --tail=100
```

### 8.4 Prometheus Storage Concepts

Prometheus stores data in a time-series database. Important storage directories include:

```text
/prometheus
/prometheus/wal
/prometheus/chunks_head
```

Operationally, Prometheus disk growth is driven by:

- number of scrape targets
- scrape interval
- number of metrics per target
- label cardinality
- retention time
- retention size
- recording rules
- remote write queue pressure

### 8.5 Cardinality Is a Production Risk

High cardinality means too many unique label combinations.

Bad metric example:

```text
http_request_duration_seconds{user_id="123456",session_id="abcdef",path="/cart/987654"}
```

Better metric design:

```text
http_request_duration_seconds{route="/cart/:id",method="GET",code="200"}
```

High-cardinality labels can increase:

- Prometheus memory usage
- CPU usage
- query latency
- disk usage
- WAL growth
- remote write backlog
- outage risk during restarts

## 9. Alertmanager in Cluster Monitoring

Alertmanager receives alerts from Prometheus and handles:

- grouping
- deduplication
- inhibition
- silencing
- routing
- notification delivery

Typical pods:

```bash
oc -n openshift-monitoring get pods -l app.kubernetes.io/name=alertmanager
```

### 9.1 Check Alertmanager Status

```bash
oc -n openshift-monitoring get alertmanager
oc -n openshift-monitoring describe alertmanager main
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=100
```

### 9.2 Alert Lifecycle

```text
Prometheus rule expression becomes true
        |
Optional 'for' duration is satisfied
        |
Alert enters firing state
        |
Prometheus sends alert to Alertmanager
        |
Alertmanager groups/deduplicates/inhibits/silences
        |
Alertmanager routes notification to receiver
```

### 9.3 Alerts, Alerting Rules, and Silences

| Object | Meaning |
|---|---|
| Alerting rule | The rule definition and PromQL expression. |
| Pending alert | Condition is true but `for` duration is not complete. |
| Firing alert | Condition is true and `for` duration has passed. |
| Silence | Temporary muting of notifications for matching labels. |
| Inhibition | Suppresses lower-level alerts when a higher-level alert is firing. |

### 9.4 Production Alert Routing

For production, avoid sending every platform alert directly to a single mailbox. Design routes by severity and ownership.

Example policy:

| Severity | Route |
|---|---|
| `critical` | PagerDuty/Opsgenie/on-call paging. |
| `warning` | ITSM ticket or team channel. |
| `info` | Dashboard only or low-priority channel. |

## 10. Thanos Querier

Thanos Querier provides a unified query interface.

In OpenShift, it is important because it can aggregate and deduplicate metrics across:

- platform Prometheus
- user workload Prometheus, if enabled

### 10.1 Get Thanos Querier Route

```bash
THANOS_ROUTE=$(oc -n openshift-monitoring get route thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

echo $THANOS_ROUTE
```

### 10.2 Query Metrics Through Thanos API

```bash
curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_ROUTE}/api/v1/query?query=up"
```

### 10.3 List Metric Metadata

```bash
curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_ROUTE}/api/v1/metadata"
```

### 10.4 Common Thanos Issues

| Symptom | Possible Cause |
|---|---|
| Query timeout | Heavy PromQL, too much data, high cardinality. |
| Missing metrics | Prometheus target down or RBAC restriction. |
| Duplicate series | Replica deduplication or label issue. |
| 401/403 | Missing token or insufficient monitoring role. |
| Route unavailable | Route, router, OAuth proxy, or pod issue. |

## 13. RBAC and Security

Monitoring data can expose sensitive operational information, so access is controlled by RBAC.

### 13.1 Common Monitoring Roles

| Role | Purpose |
|---|---|
| `cluster-monitoring-metrics-api` | Access to Thanos Querier API endpoints and related monitoring APIs. |
| `cluster-monitoring-view` | Broader view access, including federation-style access depending on binding. |
| `monitoring-alertmanager-view` | View Alertmanager API and silences. |
| `monitoring-alertmanager-edit` | Manage Alertmanager API and silences. |
| `cluster-monitoring-operator-alert-customization` | Manage platform `AlertingRule` and `AlertRelabelConfig` resources. |
| `user-workload-monitoring-config-edit` | Edit user workload monitoring configuration. |
| `alert-routing-edit` | Configure alert routing for user-defined projects. |

### 13.2 Grant Access to Monitoring API for a User

Example:

```bash
oc adm policy add-role-to-user cluster-monitoring-metrics-api rakesh \
  -n openshift-monitoring \
  --role-namespace openshift-monitoring
```

### 13.3 Grant Alertmanager Edit Access

```bash
oc adm policy add-role-to-user monitoring-alertmanager-edit rakesh \
  -n openshift-monitoring \
  --role-namespace openshift-monitoring
```

### 13.4 Security Best Practices

- Use least privilege.
- Avoid giving developers access to `openshift-monitoring` unless necessary.
- Use user workload monitoring for app teams.
- Do not expose Prometheus or Alertmanager directly without OpenShift OAuth protection.
- Rotate webhook credentials used by Alertmanager.
- Store receiver secrets in Kubernetes secrets.
- Avoid putting tokens or webhook URLs in plain ConfigMaps.

## 15. Persistent Storage, Retention, and Capacity Planning

### 15.1 Why Persistent Storage Is Important

Without persistent storage, Prometheus and Alertmanager data can be lost when pods restart or are recreated.

Persistent storage helps retain:

- Prometheus historical metrics
- Alertmanager silences
- Alertmanager notification state

For production HA clusters, persistent storage for Prometheus and Alertmanager is strongly recommended.

### 15.2 Storage Prerequisites

Use a storage class appropriate for StatefulSets.

Important storage guidance:

- Use filesystem volumes, not raw block volumes.
- Ensure the filesystem is POSIX-compliant.
- Avoid unsupported or unreliable NFS implementations.
- Size storage based on scrape volume and retention.
- Monitor Prometheus PVC usage.

### 15.3 Example: Configure Prometheus and Alertmanager PVCs

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      volumeClaimTemplate:
        spec:
          storageClassName: <storage_class_name>
          resources:
            requests:
              storage: 200Gi
    alertmanagerMain:
      volumeClaimTemplate:
        spec:
          storageClassName: <storage_class_name>
          resources:
            requests:
              storage: 20Gi
```

### 15.4 Configure Prometheus Retention

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      retention: 15d
      retentionSize: 100GB
```

### 15.5 Capacity Planning Formula

A rough planning model:

```text
Daily data ~= samples_per_second * bytes_per_sample * 86400
```

Where:

```text
samples_per_second = number_of_targets * metrics_per_target / scrape_interval_seconds
```

Prometheus storage varies by compression, labels, churn, WAL, and compaction behavior. Always measure in the real cluster.

Useful PromQL:

```promql
sum(rate(prometheus_tsdb_head_samples_appended_total[5m]))
```

```promql
prometheus_tsdb_head_series
```

```promql
prometheus_tsdb_storage_blocks_bytes
```

```promql
prometheus_tsdb_wal_storage_size_bytes
```

### 15.6 Check Prometheus PVCs

```bash
oc -n openshift-monitoring get pvc
oc -n openshift-monitoring describe pvc prometheus-k8s-db-prometheus-k8s-0
```

Check filesystem usage inside the pod:

```bash
oc -n openshift-monitoring exec prometheus-k8s-0 -c prometheus -- df -h /prometheus
```

## 16. Performance, Scale, and High Availability

### 16.1 HA Behavior

In multi-node clusters, Prometheus and Alertmanager commonly run multiple replicas.

Benefits:

- scrape availability
- alert evaluation resilience
- notification deduplication
- reduced single-pod failure impact

But HA does not remove the need for proper storage, CPU, memory, and node placement.

### 16.2 Node Placement

You can move monitoring components to selected nodes with node selectors.

Example: label infra nodes.

```bash
oc label node <node_name> node-role.kubernetes.io/infra=
oc label node <node_name> monitoring=enabled
```

Example ConfigMap snippet:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      nodeSelector:
        monitoring: enabled
    alertmanagerMain:
      nodeSelector:
        monitoring: enabled
    thanosQuerier:
      nodeSelector:
        monitoring: enabled
```

### 16.3 Tolerations

If monitoring nodes are tainted, configure tolerations.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      tolerations:
      - key: "dedicated"
        operator: "Equal"
        value: "monitoring"
        effect: "NoSchedule"
```

### 16.4 Resource Requests and Limits

Configure resources for monitoring components when clusters are large or monitoring is resource constrained.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      resources:
        requests:
          cpu: 1000m
          memory: 8Gi
        limits:
          cpu: 4000m
          memory: 16Gi
    thanosQuerier:
      resources:
        requests:
          cpu: 500m
          memory: 1Gi
        limits:
          cpu: 2000m
          memory: 4Gi
```

### 16.5 Metrics Collection Profile

OpenShift supports metrics collection profiles to reduce resource usage.

Conceptually:

| Profile | Behavior |
|---|---|
| `full` | Collects the default full set of platform metrics. |
| `minimal` | Collects metrics required for alerts, recording rules, telemetry, and console dashboards. |

Use minimal mode carefully. It can reduce resource usage but might remove metrics that administrators rely on for ad hoc troubleshooting.

### 16.6 Topology Spread

In multi-zone clusters, use topology spread constraints to improve resilience by spreading monitoring pods across zones.

Before applying placement rules, confirm nodes can satisfy all constraints:

```bash
oc get nodes -L topology.kubernetes.io/zone,monitoring
oc -n openshift-monitoring describe pod prometheus-k8s-0 | grep -A20 -i events
```

## 17. Remote Write and Long-Term Metrics

Local Prometheus storage is not always enough for enterprise requirements.

Use remote write when you need:

- long-term retention
- central metrics lake
- multi-cluster observability
- compliance retention
- external analytics
- global dashboards

### 17.1 Remote Write Flow

```text
Prometheus local scrape
        |
Local TSDB retention
        |
remote_write queue
        |
External compatible endpoint
        |
Long-term query/storage platform
```

### 17.2 Example Remote Write Configuration

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      remoteWrite:
      - url: "https://remote-write-endpoint.example.com/api/v1/write"
        name: central-observability
        authorization:
          type: Bearer
          credentials:
            name: remote-write-token
            key: token
```

Secret example:

```bash
oc -n openshift-monitoring create secret generic remote-write-token \
  --from-literal=token='<token_value>'
```

### 17.3 Cluster ID Labels

For multi-cluster environments, add labels that identify the source cluster.

Examples:

```text
cluster_id="prod-delhi-01"
environment="prod"
region="in-north"
customer="internal-platform"
```

This makes external queries easier:

```promql
sum by (cluster_id) (up)
```

### 17.4 Remote Write Troubleshooting

Check metrics:

```promql
prometheus_remote_storage_samples_pending
```

```promql
rate(prometheus_remote_storage_failed_samples_total[5m])
```

```promql
rate(prometheus_remote_storage_samples_retried_total[5m])
```

Common causes of remote write issues:

- authentication failure
- TLS certificate mismatch
- proxy/firewall issue
- receiver unavailable
- queue too small
- high cardinality
- network latency
- endpoint rate limiting

## 19. Platform Alerting Deep Dive

### 19.1 Platform Alerts

OpenShift ships with many default platform alerts. They are designed to detect symptoms such as:

- API server failures
- etcd issues
- node readiness problems
- image registry issues
- Prometheus scrape failures
- PV filling up
- cluster operator degradation
- machine config update issues
- pod crash loops
- certificate expiry

### 19.2 Alert Severity

Common severities:

| Severity | Meaning |
|---|---|
| `critical` | Immediate human action required. |
| `warning` | Needs attention but not necessarily immediate paging. |
| `info` | Informational. |

### 19.3 Create a Core Platform AlertingRule

For core platform metrics, use the OpenShift-specific `AlertingRule` resource in `openshift-monitoring`.

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertingRule
metadata:
  name: example-platform-alert
  namespace: openshift-monitoring
spec:
  groups:
  - name: example-platform.rules
    rules:
    - alert: ExamplePlatformAlert
      expr: vector(1)
      for: 1m
      labels:
        severity: warning
      annotations:
        message: "Example platform alert for testing."
```

Apply:

```bash
oc apply -f example-platform-alert.yaml
```

Check:

```bash
oc -n openshift-monitoring get alertingrule
oc -n openshift-monitoring describe alertingrule example-platform-alert
```

### 19.4 Modify or Drop Platform Alert Labels

Use `AlertRelabelConfig` when supported by your version and requirement. This is useful for modifying alert labels before routing.

Example concept:

```yaml
apiVersion: monitoring.openshift.io/v1
kind: AlertRelabelConfig
metadata:
  name: example-alert-relabel
  namespace: openshift-monitoring
spec:
  configs:
  - sourceLabels: [alertname]
    regex: Watchdog
    targetLabel: severity
    replacement: critical
    action: Replace
```

Use this carefully. If you modify default platform alert behavior, document the reason and ensure it does not hide critical Red Hat support signals.

### 19.5 Alerting Rule Quality Checklist

Good alerts are symptom-based.

A good alert has:

- clear name
- useful severity
- `for` duration to avoid flapping
- actionable message
- runbook URL or troubleshooting hint
- owner label, if used by your routing
- low noise
- clear user impact

Bad alerts:

- fire on every small cause
- duplicate existing platform alerts
- lack severity
- lack message
- fire without action
- use expensive PromQL
- depend on unstable labels

Even though this note focuses on cluster monitoring, an advanced administrator must know how user workload monitoring interacts with it.

### 20.1 Enable User Workload Monitoring

```yaml
apiVersion: v1

  name: cluster-monitoring-config
  namespace: openshift-monitoring

  config.yaml: |

```

Apply:

```bash
oc apply -f cluster-monitoring-config.yaml
```

Verify:

```bash
oc -n openshift-user-workload-monitoring get pods
```

Expected pods might include:

```text
prometheus-operator-xxxxx
prometheus-user-workload-0
prometheus-user-workload-1
thanos-ruler-user-workload-0
```

### 20.2 User Workload ConfigMap

```bash
oc -n openshift-user-workload-monitoring get configmap user-workload-monitoring-config
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

### 20.3 Example ServiceMonitor

Your service must have a named port.

Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
  namespace: app-prod
  labels:
    app: myapp
spec:
  selector:
    app: myapp
  ports:
  - name: web
    port: 8080
    targetPort: 8080
```

ServiceMonitor:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp
  namespace: app-prod
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: web
    path: /metrics
    interval: 30s
```

### 20.4 Example PrometheusRule for Application Alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: myapp-alerts
  namespace: app-prod
spec:
  groups:
  - name: myapp.rules
    rules:
    - alert: MyAppHighErrorRate
      expr: |
        sum(rate(http_requests_total{namespace="app-prod",code=~"5.."}[5m]))
        /
        sum(rate(http_requests_total{namespace="app-prod"}[5m])) > 0.05
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "MyApp high 5xx error rate"
        description: "More than 5% HTTP requests are failing for 10 minutes."
```

### 20.5 Common User Workload Mistakes

| Mistake | Result |
|---|---|
| Service port has no name | ServiceMonitor does not match endpoint correctly. |
| Wrong label selector | Target never appears. |
| Metrics endpoint path wrong | Target down or 404. |
| App does not expose `/metrics` | No useful data. |
| NetworkPolicy blocks scrape | Target down. |
| App metric labels include user/session IDs | Cardinality explosion. |
| User lacks RBAC | Cannot view metrics or alerts. |

```promql
<alert_expression>
```

```bash
oc -n openshift-monitoring get alertingrule
oc -n <app_namespace> get prometheusrule
```

Check if alert is pending:

```text
Observe -> Alerting -> Alerting rules
```

Check common causes:

- expression is false
- `for` duration not completed
- wrong namespace label
- user workload monitoring not enabled
- rule in wrong namespace
- rule rejected by validation
- metrics missing
- alert silenced
- Alertmanager route not configured

### 21.5 Runbook: Monitoring Operator Degraded

```bash
oc get co monitoring
```

- YAML parse errors
- unsupported config field
- failed rollout
- unavailable pods
- pending PVC
- scheduling failure
- certificate errors
- image pull errors

### 21.6 Runbook: Metrics UI Slow or Timing Out

1. Try narrower time range.
2. Hide graph and inspect table first.
3. Avoid regex-heavy queries over all metrics.
4. Avoid unbounded selectors like `{__name__!=""}` in production.
5. Check Thanos Querier CPU/memory.
6. Check Prometheus CPU/memory.
7. Check high cardinality.
8. Check API server load if UI itself is slow.

## 22. Troubleshooting Cluster Monitoring

### 22.1 Prometheus Pod CrashLoopBackOff

Check:

```bash
oc -n openshift-monitoring describe pod prometheus-k8s-0
oc -n openshift-monitoring logs prometheus-k8s-0 -c prometheus --previous
```

Possible causes:

- OOMKilled
- corrupt TSDB block
- disk full
- permission issue
- bad configuration generated from invalid ConfigMap
- PVC attach/mount issue
- node pressure

Remediation:

- increase memory
- check PVC usage
- move to larger node
- reduce cardinality
- reduce retention
- contact Red Hat support before deleting TSDB data in production

### 22.2 Prometheus OOMKilled

Check:

```bash
oc -n openshift-monitoring describe pod prometheus-k8s-0 | grep -i -A5 oom
```

Useful metrics:

```promql
process_resident_memory_bytes{job=~"prometheus.*"}
```

```promql
prometheus_tsdb_head_series
```

Fix options:

- increase memory requests/limits
- reduce metric cardinality
- use minimal collection profile if suitable
- review user workload monitoring targets
- reduce scrape frequency for user workloads
- split app metrics responsibly

### 22.3 Prometheus PVC Pending

```bash
oc -n openshift-monitoring get pvc
oc -n openshift-monitoring describe pvc <pvc_name>
oc get sc
```

Common causes:

- invalid storage class
- insufficient storage capacity
- topology conflict
- `WaitForFirstConsumer` scheduling issue
- node selector prevents pod scheduling in storage-compatible zone

### 22.4 Alertmanager Not Sending Notifications

Check:

```bash
oc -n openshift-monitoring logs alertmanager-main-0 -c alertmanager --tail=200
```

Check route/receiver configuration:

```bash
oc -n openshift-monitoring get secret | grep alertmanager
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml
```

Common causes:

- webhook URL incorrect
- proxy blocks outbound traffic
- TLS validation failure
- secret key name mismatch
- route does not match alert labels
- alert is inhibited
- alert is silenced
- receiver service unavailable

### 22.5 Thanos Query Fails with 401 or 403

Check token:

```bash
oc whoami
oc whoami -t
```

Check role binding:

```bash
oc get rolebinding -n openshift-monitoring | grep monitoring
oc describe rolebinding -n openshift-monitoring <rolebinding_name>
```

Grant access if required:

```bash
oc adm policy add-role-to-user cluster-monitoring-metrics-api <user> \
  -n openshift-monitoring \
  --role-namespace openshift-monitoring
```

### 22.6 Missing Metrics After Upgrade

Possible causes:

- metric renamed or removed
- dashboard query changed
- minimal metrics collection profile enabled
- target no longer scraped
- RBAC view changed
- user workload monitoring disabled
- ServiceMonitor label no longer matches

Actions:

```bash
oc get clusterversion
```

## 23. Best Practices and Anti-Patterns

### 23.1 Best Practices

- Keep cluster monitoring configuration minimal and documented.
- Use supported `cluster-monitoring-config` fields only.
- Configure persistent storage for production.
- Monitor Prometheus disk, memory, series count, and scrape failures.
- Use user workload monitoring for application metrics.
- Keep application metrics low-cardinality.
- Define actionable alerts, not noisy alerts.
- Add runbooks to alerts.
- Use severity consistently.
- Use RBAC with least privilege.
- Test Alertmanager receivers.
- Use remote write for long-term retention.
- Size monitoring nodes properly.
- Keep monitoring components spread across nodes/zones.
- Review monitoring health after OpenShift upgrades.

### 23.2 Anti-Patterns

- Editing generated Prometheus StatefulSets directly.
- Creating your own unmanaged Prometheus for platform metrics without a strong reason.
- Scraping every pod blindly.
- Using labels like `user_id`, `session_id`, `request_id`, or raw URL path in metrics.
- Setting retention very high without storage planning.
- Ignoring `KubePersistentVolumeFillingUp` alerts.
- Silencing alerts permanently instead of fixing the cause.
- Giving all developers access to platform monitoring namespace.
- Sending all alerts to email only.
- Using heavy PromQL queries in dashboards with wide time ranges.

## 24. Interview and Exam-Style Questions

### Q1. What is Cluster Monitoring Operator?

It is the OpenShift operator that deploys, manages, and reconciles the built-in monitoring stack. It manages platform Prometheus, Alertmanager, Thanos Querier, Telemeter Client, and related monitoring targets. Administrators configure supported behavior with ConfigMaps instead of manually editing generated resources.

### Q2. Which namespace contains core platform monitoring?

```text
openshift-monitoring
```

### Q3. Which ConfigMap configures core monitoring?

```text
openshift-monitoring/cluster-monitoring-config
```

### Q4. Which namespace contains user workload monitoring?

```text
openshift-user-workload-monitoring
```

### Q5. How do you check monitoring operator health?

```bash
oc get co monitoring
oc describe co monitoring
oc -n openshift-monitoring get pods
```

### Q6. How do you query metrics from CLI?

```bash
THANOS_ROUTE=$(oc -n openshift-monitoring get route thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_ROUTE}/api/v1/query?query=up"
```

### Q7. What is the difference between Prometheus and Thanos Querier?

Prometheus scrapes, stores, and evaluates metrics. Thanos Querier provides a query layer that can aggregate and deduplicate metrics from platform and user workload monitoring.

### Q8. Why should Prometheus use persistent storage?

To avoid losing metrics data during pod restarts or recreation. Alertmanager persistent storage also helps preserve silences and notification state.

### Q9. What causes Prometheus high memory usage?

Common causes include too many active series, high-cardinality labels, many scrape targets, low scrape intervals, heavy queries, and large rule evaluations.

### Q10. What should you do if a ServiceMonitor target is down?

Check service labels, service endpoints, port name, `/metrics` path, scheme, TLS/authentication, NetworkPolicy, pod readiness, and the Targets UI error.

### Q11. Why is high cardinality dangerous?

It increases the number of unique time series, which increases Prometheus memory, CPU, disk usage, query latency, WAL size, and remote write load.

### Q12. How do you create custom platform alert rules?

Use the `AlertingRule` resource in the `openshift-monitoring` namespace.

### Q13. How do you create custom application alerts?

Use `PrometheusRule` in the user project after user workload monitoring is enabled.

### Q14. What is a silence?

A silence temporarily prevents notifications for matching alerts. It does not fix the alert condition and should not be used as a permanent solution.

### Q15. How do you check down scrape targets with PromQL?

```promql
up == 0
```

Cluster monitoring is not just Prometheus running in OpenShift. It is a managed, self-reconciling observability subsystem controlled by the Cluster Monitoring Operator. A strong OpenShift administrator must know how metrics are scraped, how alerts are evaluated and routed, how Thanos exposes queries, how storage and retention affect reliability, how RBAC controls access, and how to troubleshoot the monitoring stack itself.

For real production work, focus on these five skills:

1. Quickly prove whether monitoring itself is healthy.
2. Identify missing metrics or down targets.
3. Control Prometheus disk, memory, and cardinality growth.
4. Configure actionable alerting with proper routing.
5. Keep custom workload metrics separated from core platform monitoring.
