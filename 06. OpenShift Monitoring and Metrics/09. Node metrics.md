# Node Metrics in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift Administrator / Platform Engineer with ~10 years of Linux, Kubernetes, and OpenShift experience  
**Scope:** OpenShift Container Platform 4.x monitoring, with notes aligned to current Red Hat OpenShift 4.20 monitoring behavior  
**Goal:** Understand node metrics deeply enough to troubleshoot production incidents, design dashboards, tune capacity, and explain the data path in interviews or advanced administration exams.

---

## 1. What are node metrics?

Node metrics are time-series measurements that describe the health, capacity, utilization, saturation, and errors of each OpenShift node. A node can be a control plane node, worker node, infrastructure node, storage node, GPU node, or special workload node. In OpenShift, node metrics are not only about CPU and memory. They include:

- CPU usage, CPU idle, CPU wait, CPU steal, and load average
- Memory total, available, used, cache, buffers, slab, swap, and pressure symptoms
- Filesystem usage, inode usage, read-only filesystems, and mount-level capacity
- Disk I/O throughput, I/O time, queue/saturation symptoms, read/write operations
- Network throughput, packet errors, packet drops, link state, and interface status
- Node readiness, node pressure conditions, schedulability, taints, labels, capacity, and allocatable resources
- Kubelet, CRI-O, container runtime, pod density, and container resource consumption that affect the node
- Hardware or kernel-level signals exposed by Linux and node exporter

For an experienced administrator, node metrics answer questions like:

- Which node is becoming overloaded?
- Is high CPU caused by application containers, system daemons, kubelet, CRI-O, or kernel wait?
- Is memory usage real pressure or only Linux page cache?
- Is a node under `DiskPressure`, inode exhaustion, or image garbage collection pressure?
- Are pods failing because of insufficient allocatable resources, taints, or node conditions?
- Is network throughput normal, or are drops/errors increasing?
- Is the monitoring stack itself scraping node metrics correctly?
- Is the cluster sized correctly for upgrades, failures, and peak workload?

Node metrics are the foundation of node SRE work because a Kubernetes cluster can look healthy at the API layer while a worker node is already suffering from CPU saturation, memory pressure, disk pressure, PID pressure, or I/O bottlenecks.

## 2. OpenShift monitoring architecture for node metrics

OpenShift includes a default platform monitoring stack in the `openshift-monitoring` namespace. This stack is installed and managed by cluster Operators. It is designed to monitor core platform components and cluster infrastructure.

### 2.1 Main components involved

| Component | Namespace | Role for node metrics |
|---|---:|---|
| Cluster Monitoring Operator | `openshift-monitoring` | Deploys and reconciles core monitoring components. Do not manually modify generated resources unless documented. |
| Prometheus / `prometheus-k8s` | `openshift-monitoring` | Scrapes platform targets and stores time-series data. |
| Thanos Querier | `openshift-monitoring` | Provides a unified query layer across Prometheus replicas and user workload monitoring where enabled. |
| node-exporter | `openshift-monitoring` | Runs on every node and exposes Linux host metrics. |
| kubelet / cAdvisor endpoints | Node-local kubelet endpoint | Exposes pod/container resource usage and kubelet metrics. |
| kube-state-metrics | `openshift-monitoring` | Exposes Kubernetes object state such as node conditions, capacity, allocatable, pod requests, and pod ownership. |
| openshift-state-metrics | `openshift-monitoring` | Adds OpenShift-specific object metrics. |
| Metrics Server | `openshift-monitoring` in current versions | Provides `metrics.k8s.io` resource metrics used by commands such as `oc adm top` and Kubernetes resource APIs. |
| Alertmanager | `openshift-monitoring` | Receives firing alerts from Prometheus and routes notifications. |
| Web console Observe pages | Console plugin | Lets administrators query metrics, inspect targets, view dashboards, and review alerts. |

### 2.2 Data flow

A simplified node metric flow is:

```text
Linux kernel / procfs / sysfs
        |
        v
node-exporter DaemonSet on every node
        |
        v
Prometheus scrape via ServiceMonitor/PodMonitor generated by OpenShift monitoring
        |
        v
Prometheus time-series database
        |
        v
Thanos Querier / Console Observe -> Metrics / Dashboards / Alerts
```

Container and pod usage follows a parallel path:

```text
CRI-O + cgroups + kubelet/cAdvisor
        |
        v
kubelet metrics endpoints
        |
        v
Prometheus scrape and/or Metrics Server resource API
        |
        v
PromQL, dashboards, alerts, oc adm top, HPA resource metrics
```

Kubernetes object state follows another path:

```text
Kubernetes API objects
        |
        v
kube-state-metrics / openshift-state-metrics
        |
        v
Prometheus
        |
        v
PromQL joins with node/pod/container usage metrics
```

### 2.3 Important OpenShift version note

In modern OpenShift versions, Metrics Server provides the Kubernetes resource metrics API. That API is used for quick CPU/memory views such as `oc adm top nodes` and by Kubernetes consumers of `metrics.k8s.io`. Prometheus and Thanos remain the deeper monitoring/query path for historical analysis, alerting, dashboards, and advanced PromQL.

Practical meaning:

- `oc adm top nodes` is useful for quick current CPU/memory usage.
- PromQL is required for deep historical analysis, capacity planning, filesystem trends, disk I/O, network errors, pressure correlation, and alert rules.
- `oc adm top` output and Prometheus queries can differ slightly because they may come from different collection paths, windows, and aggregation logic.

## 3. Difference between node metrics, pod metrics, and cluster state metrics

A common advanced-admin mistake is mixing three different types of data.

### 3.1 Node exporter metrics

These are host OS metrics. They usually start with `node_`.

Examples:

```promql
node_cpu_seconds_total
node_memory_MemAvailable_bytes
node_filesystem_avail_bytes
node_disk_read_bytes_total
node_network_receive_bytes_total
node_load1
node_uname_info
```

These answer: **What is happening on the Linux node?**

### 3.2 Kubelet / cAdvisor container metrics

These usually start with `container_` or kubelet-related prefixes.

Examples:

```promql
container_cpu_usage_seconds_total
container_memory_working_set_bytes
container_fs_usage_bytes
container_network_receive_bytes_total
kubelet_running_pods
kubelet_running_containers
```

These answer: **Which pods/containers are consuming resources on the node?**

### 3.3 kube-state-metrics node object metrics

These usually start with `kube_node_`, `kube_pod_`, `kube_pod_container_`, etc.

Examples:

```promql
kube_node_status_condition
kube_node_status_capacity
kube_node_status_allocatable
kube_node_spec_unschedulable
kube_pod_container_resource_requests
kube_pod_info
```

These answer: **What does the Kubernetes API think about node state, capacity, allocatable resources, schedulability, and requested resources?**

### 3.4 Why this matters

| Question | Best metric source |
|---|---|
| Is the node CPU busy? | `node_cpu_seconds_total` |
| Which pod is using CPU on that node? | `container_cpu_usage_seconds_total` |
| Is the node Ready? | `kube_node_status_condition` |
| Is the node schedulable? | `kube_node_spec_unschedulable` |
| How much CPU is allocatable? | `kube_node_status_allocatable` |
| Are pods over-requested? | `kube_pod_container_resource_requests` + allocatable |
| Is filesystem usage growing? | `node_filesystem_*` |
| Are network errors increasing? | `node_network_*_errs_total`, `node_network_*_drop_total` |
| Is the target being scraped? | `up{job=...}` and Observe -> Targets |

## 4. How to access node metrics

### 4.1 Quick CLI view

```bash
oc adm top nodes
```

Example output:

```text
NAME                         CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
worker-0.example.com         650m         16%    4280Mi          55%
worker-1.example.com         1200m        30%    6110Mi          72%
worker-2.example.com         90m          2%     3000Mi          38%
```

For a specific node:

```bash
oc adm top node <node-name>
```

Filter by node label:

```bash
oc adm top node --selector='node-role.kubernetes.io/worker='
```

Remember: `oc adm top` is a quick snapshot, not a complete node observability solution.

### 4.2 View node objects and conditions

```bash
oc get nodes
oc get nodes -o wide
oc describe node <node-name>
```

Useful JSONPath examples:

```bash
# Show node conditions
oc get node <node-name> -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\n"}{end}'

# Show capacity and allocatable
oc get node <node-name> -o jsonpath='{.status.capacity}{"\n"}{.status.allocatable}{"\n"}'
```

### 4.3 Web console

Use:

```text
Observe -> Metrics
Observe -> Dashboards
Observe -> Targets
Observe -> Alerting
```

Important console locations:

- **Observe -> Metrics**: Run PromQL queries.
- **Observe -> Dashboards**: View built-in node, Kubernetes compute, network, and USE-method dashboards.
- **Observe -> Targets**: Check scrape target health, last scrape, scrape duration, and endpoint URL.
- **Observe -> Alerting**: Review firing and pending alerts.

### 4.4 Query through Thanos Querier route

Get the Thanos route:

```bash
THANOS_HOST=$(oc get route -n openshift-monitoring thanos-querier -o jsonpath='{.status.ingress[0].host}')
echo $THANOS_HOST
```

List metric metadata:

```bash
curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/metadata" | jq .
```

Run an instant query:

```bash
curl -k -G -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/query" \
  --data-urlencode 'query=up'
```

Run a node CPU query:

```bash
curl -k -G -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/query" \
  --data-urlencode 'query=100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))'
```

### 4.5 Inspect monitoring pods and targets

```bash
oc get pods -n openshift-monitoring
oc get ds -n openshift-monitoring | grep -i node
oc get svc -n openshift-monitoring | grep -i node
oc get servicemonitor -n openshift-monitoring | grep -i node
```

To inspect scrape target health in PromQL:

```promql
up
```

For node exporter targets specifically, the job label can vary slightly by version. Discover it first:

```promql
label_values(up, job)
```

Then filter:

```promql
up{job=~".*node-exporter.*"}
```

## 5. PromQL basics for node administrators

### 5.1 Instant vector vs range vector

Instant value:

```promql
node_load1
```

Range vector over five minutes:

```promql
node_cpu_seconds_total[5m]
```

Rate over five minutes:

```promql
rate(node_cpu_seconds_total[5m])
```

### 5.2 Counters vs gauges

| Type | Meaning | Example | Query style |
|---|---|---|---|
| Counter | Always increases until process restart | `node_network_receive_bytes_total` | Use `rate()` or `increase()` |
| Gauge | Can go up or down | `node_memory_MemAvailable_bytes` | Use directly or with arithmetic |
| Histogram | Bucketed latency/size data | Some kubelet/apiserver metrics | Use `histogram_quantile()` |

For counters, never alert on the raw value directly. Use `rate()` or `increase()`.

Bad:

```promql
node_network_receive_bytes_total > 1000000000
```

Good:

```promql
rate(node_network_receive_bytes_total[5m]) > 100000000
```

### 5.3 Label awareness

Node metrics commonly include labels such as:

```text
instance
job
node
device
mountpoint
fstype
cpu
mode
namespace
pod
container
```

The exact label set can vary by metric and version. Always inspect the actual labels in your cluster:

```promql
node_cpu_seconds_total
```

or from CLI:

```bash
curl -k -G -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/series" \
  --data-urlencode 'match[]=node_cpu_seconds_total'
```

## 6. CPU metrics

### 6.1 Important CPU metrics

| Metric | Meaning |
|---|---|
| `node_cpu_seconds_total` | CPU seconds spent in each mode per CPU core. This is the primary CPU metric from node exporter. |
| `node_load1`, `node_load5`, `node_load15` | Linux load average over 1, 5, and 15 minutes. |
| `container_cpu_usage_seconds_total` | Container CPU usage, useful for identifying workload consumers. |
| `kube_node_status_capacity{resource="cpu"}` | Total CPU capacity known to Kubernetes. |
| `kube_node_status_allocatable{resource="cpu"}` | CPU available for pods after kube/system reservations. |
| `kube_pod_container_resource_requests{resource="cpu"}` | CPU requested by scheduled containers. |

### 6.2 CPU modes you must understand

`node_cpu_seconds_total` has a `mode` label. Common modes:

| Mode | Meaning | Production interpretation |
|---|---|---|
| `idle` | CPU idle time | High idle means CPU is available. |
| `user` | User-space process time | Application or non-kernel process work. |
| `system` | Kernel time | Networking, filesystem, kernel, container runtime overhead. |
| `iowait` | Waiting for I/O | Often storage or network-backed storage bottleneck. Do not call it normal CPU usage. |
| `irq` / `softirq` | Interrupt processing | High values can indicate network/storage interrupt pressure. |
| `steal` | Hypervisor steal time | Virtualized node not getting CPU from host/hypervisor. Important on public cloud or nested virtualization. |
| `nice` | User processes with adjusted priority | Usually less important unless someone changed priorities. |

### 6.3 CPU utilization percentage per node

```promql
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
```

This shows non-idle CPU percentage per node.

Alternative with explicit core count:

```promql
100 *
sum by (instance) (rate(node_cpu_seconds_total{mode!="idle"}[5m]))
/
count by (instance) (node_cpu_seconds_total{mode="idle"})
```

### 6.4 CPU usage by mode

```promql
100 * avg by (instance, mode) (rate(node_cpu_seconds_total[5m]))
```

Use this when a node is hot. It tells you whether the heat is user CPU, system CPU, iowait, steal, or interrupt pressure.

### 6.5 CPU cores consumed per node

```promql
sum by (instance) (rate(node_cpu_seconds_total{mode!="idle"}[5m]))
```

If a node has 8 cores and this query returns `6`, it is consuming roughly 6 cores.

### 6.6 CPU iowait percentage

```promql
100 * avg by (instance) (rate(node_cpu_seconds_total{mode="iowait"}[5m]))
```

Interpretation:

- Low CPU utilization + high iowait = workload is blocked on disk/storage.
- High CPU utilization + low iowait = CPU-bound workload.
- High system/softirq = kernel/network/storage overhead.
- High steal = cloud/hypervisor contention.

### 6.7 Load average normalized by CPU cores

```promql
node_load1 / count by (instance) (node_cpu_seconds_total{mode="idle"})
```

Interpretation:

| Normalized load | Meaning |
|---:|---|
| `< 0.7` | Generally comfortable. |
| `0.7 - 1.0` | Busy but usually acceptable. |
| `> 1.0` | More runnable or waiting tasks than CPU cores; inspect CPU and I/O. |
| `> 2.0` | Serious saturation or blocked tasks; investigate urgently. |

Load average includes runnable tasks and tasks waiting for uninterruptible I/O. That is why a node can have high load but not high CPU percentage.

### 6.8 Find top CPU-consuming pods by node

```promql
sum by (node, namespace, pod) (
  rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])
)
```

Top pods on one node:

```promql
topk(10,
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="", pod!="", node="<node-name>"}[5m])
  )
)
```

If your metric does not have a `node` label, join with `kube_pod_info`:

```promql
topk(10,
  sum by (node, namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])
    * on (namespace, pod) group_left(node)
    kube_pod_info
  )
)
```

### 6.9 CPU requested vs allocatable

```promql
100 *
sum by (node) (kube_pod_container_resource_requests{resource="cpu", unit="core"})
/
on (node)
kube_node_status_allocatable{resource="cpu", unit="core"}
```

Use this for scheduling pressure. A node can have low actual CPU usage but high requested CPU. Kubernetes schedules based on requests, not actual usage.

### 6.10 CPU troubleshooting workflow

When a node shows high CPU:

1. Check non-idle CPU percentage.
2. Break down CPU by mode.
3. Check top consuming pods.
4. Check system pods such as SDN/OVN, kubelet, CRI-O, monitoring, logging, storage agents.
5. Check whether workload has CPU requests/limits.
6. Check throttling if application latency is high.
7. Check iowait and disk I/O before blaming CPU.
8. For virtualized platforms, check `steal`.

Useful commands:

```bash
oc adm top node <node-name>
oc adm top pods -A --sort-by=cpu
oc get pods -A --field-selector spec.nodeName=<node-name>
oc describe node <node-name>
oc debug node/<node-name>
```

Inside node debug shell:

```bash
chroot /host
top
ps aux --sort=-%cpu | head
pidstat 1 5   # if available
crictl ps
crictl stats
```

Use node debug carefully. Prefer `oc` and PromQL first.

## 7. Memory metrics

### 7.1 Important memory metrics

| Metric | Meaning |
|---|---|
| `node_memory_MemTotal_bytes` | Total memory on the node. |
| `node_memory_MemAvailable_bytes` | Best Linux estimate of memory available without swapping or major reclaim. Use this instead of naive free memory. |
| `node_memory_MemFree_bytes` | Completely free memory. Often low on healthy Linux systems because cache is used. |
| `node_memory_Cached_bytes` | Page cache. Can often be reclaimed. |
| `node_memory_Buffers_bytes` | Kernel buffers. |
| `node_memory_Slab_bytes` | Kernel slab memory. High slab may indicate kernel object pressure. |
| `container_memory_working_set_bytes` | Container memory actively used and less easily reclaimable. |
| `kube_node_status_condition{condition="MemoryPressure"}` | Kubernetes node memory pressure condition. |
| `kube_node_status_capacity{resource="memory"}` | Total memory known to Kubernetes. |
| `kube_node_status_allocatable{resource="memory"}` | Memory available to pods after reservation. |

### 7.2 Correct node memory utilization

Use `MemAvailable`, not `MemFree`:

```promql
100 * (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes))
```

Available memory in GiB:

```promql
node_memory_MemAvailable_bytes / 1024 / 1024 / 1024
```

### 7.3 Why `free memory` is misleading

Linux uses unused memory for page cache. This is good. A node with low `MemFree` can still be healthy if `MemAvailable` is high. Use:

```promql
node_memory_MemAvailable_bytes
```

not:

```promql
node_memory_MemFree_bytes
```

for operational decisions.

### 7.4 Node memory pressure condition

```promql
kube_node_status_condition{condition="MemoryPressure", status="true"} == 1
```

If this fires, the kubelet has detected memory pressure. Kubernetes may start evicting pods based on eviction thresholds and QoS.

### 7.5 Memory consumed by pods per node

```promql
sum by (node) (
  container_memory_working_set_bytes{container!="", pod!=""}
)
```

Memory usage as percentage of allocatable:

```promql
100 *
sum by (node) (container_memory_working_set_bytes{container!="", pod!=""})
/
on (node)
kube_node_status_allocatable{resource="memory", unit="byte"}
```

Top memory pods on a node:

```promql
topk(10,
  sum by (namespace, pod) (
    container_memory_working_set_bytes{container!="", pod!="", node="<node-name>"}
  )
)
```

### 7.6 Requested memory vs allocatable memory

```promql
100 *
sum by (node) (kube_pod_container_resource_requests{resource="memory", unit="byte"})
/
on (node)
kube_node_status_allocatable{resource="memory", unit="byte"}
```

If this is above 100%, pods may still run because Kubernetes allows overcommit based on requests and limits, but scheduling new pods can become difficult.

### 7.7 Memory limits vs actual usage

```promql
sum by (namespace, pod) (container_memory_working_set_bytes{container!="", pod!=""})
/
sum by (namespace, pod) (kube_pod_container_resource_limits{resource="memory", unit="byte"})
```

Use this to identify pods close to memory limit. Pods exceeding memory limits can be OOMKilled.

### 7.8 OOMKilled detection

```promql
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

Recent OOMKilled containers:

```promql
increase(kube_pod_container_status_restarts_total[30m]) > 0
and on (namespace, pod, container)
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

### 7.9 Memory troubleshooting workflow

When memory is high:

1. Check `MemAvailable`, not only memory percentage.
2. Check node `MemoryPressure` condition.
3. Find top memory pods on the node.
4. Compare pod usage with requests and limits.
5. Check for OOMKilled events.
6. Check kubelet/CRI-O/system daemon memory.
7. Check kernel slab and page cache.
8. Check workload changes, deployment rollouts, and pod density.
9. Check whether `system-reserved` and `kube-reserved` are appropriate.

Useful commands:

```bash
oc adm top node <node-name>
oc adm top pods -A --sort-by=memory
oc describe node <node-name>
oc get events -A --sort-by=.lastTimestamp | grep -Ei 'oom|evict|memory'
oc get pods -A --field-selector spec.nodeName=<node-name>
```

Inside node debug:

```bash
oc debug node/<node-name>
chroot /host
free -h
cat /proc/meminfo
ps aux --sort=-%mem | head
crictl stats
journalctl -u kubelet --since "1 hour ago" | grep -Ei 'evict|memory|oom'
```

### 7.10 Node reserved resources

OpenShift reserves CPU and memory for system components such as kubelet and CRI-O. This affects `allocatable`. Capacity is what the node physically has. Allocatable is what Kubernetes can schedule for pods.

Check:

```bash
oc describe node <node-name> | egrep -A8 'Capacity|Allocatable'
```

PromQL:

```promql
kube_node_status_capacity{resource="memory", unit="byte"}
kube_node_status_allocatable{resource="memory", unit="byte"}
```

A production cluster should not run all node memory as allocatable to pods. Kubelet, CRI-O, SDN, storage, logging, monitoring, and OS processes need guaranteed headroom.

## 8. Filesystem and disk capacity metrics

### 8.1 Important filesystem metrics

| Metric | Meaning |
|---|---|
| `node_filesystem_size_bytes` | Total filesystem size. |
| `node_filesystem_avail_bytes` | Available bytes to non-root users. Usually best for alerting. |
| `node_filesystem_free_bytes` | Free bytes including root-reserved blocks. |
| `node_filesystem_files` | Total inodes. |
| `node_filesystem_files_free` | Free inodes. |
| `node_filesystem_readonly` | Whether filesystem is read-only. |
| `container_fs_usage_bytes` | Container filesystem usage. |
| `kube_node_status_condition{condition="DiskPressure"}` | Kubernetes node disk pressure condition. |

### 8.2 Node root filesystem usage

```promql
100 * (1 - (
  node_filesystem_avail_bytes{mountpoint="/", fstype!~"tmpfs|overlay"}
  /
  node_filesystem_size_bytes{mountpoint="/", fstype!~"tmpfs|overlay"}
))
```

### 8.3 All important node filesystems

```promql
100 * (1 - (
  node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}
  /
  node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"}
))
```

Filter noisy pseudo filesystems. Common exclusions:

```promql
fstype!~"tmpfs|overlay|squashfs|ramfs|devtmpfs"
```

You might also exclude Kubernetes pod mounts depending on your dashboard:

```promql
mountpoint!~"/var/lib/kubelet/pods/.+"
```

### 8.4 Filesystem available GiB

```promql
node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"} / 1024 / 1024 / 1024
```

### 8.5 Predict filesystem exhaustion

Filesystem likely to fill within 24 hours based on last 6 hours:

```promql
predict_linear(
  node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs", mountpoint="/"}[6h],
  24 * 3600
) < 0
```

This is useful for proactive alerts, but it assumes the recent trend continues.

### 8.6 Inode usage

```promql
100 * (1 - (
  node_filesystem_files_free{fstype!~"tmpfs|overlay|squashfs"}
  /
  node_filesystem_files{fstype!~"tmpfs|overlay|squashfs"}
))
```

Inode exhaustion can break nodes even when bytes are still available. It is common with excessive small files, container logs, temporary files, or broken applications writing many files.

### 8.7 DiskPressure condition

```promql
kube_node_status_condition{condition="DiskPressure", status="true"} == 1
```

DiskPressure can involve root filesystem, image filesystem, container writable layer usage, logs, or ephemeral storage pressure.

### 8.8 Container filesystem usage by pod

```promql
topk(10,
  sum by (namespace, pod) (container_fs_usage_bytes{container!="", pod!=""})
)
```

If a node is filling because of containers, inspect pods on that node:

```bash
oc get pods -A --field-selector spec.nodeName=<node-name>
oc adm top pods -A --sort-by=memory
```

### 8.9 Log and image pressure locations

On RHCOS/OpenShift nodes, important locations include:

```text
/var/lib/kubelet
/var/lib/containers
/var/log
/var/log/pods
/var/log/containers
```

Do not randomly delete files from node paths in production. Understand whether kubelet garbage collection, image pruning, log rotation, or workload behavior is the root cause.

### 8.10 Disk capacity troubleshooting workflow

1. Check `DiskPressure` condition.
2. Check filesystem usage and inode usage.
3. Identify which mountpoint is filling.
4. Check container logs and image storage.
5. Check whether a workload is writing to ephemeral storage.
6. Check pods without ephemeral storage requests/limits.
7. Check image garbage collection and kubelet logs.
8. Check storage operator pods if using local storage/ODF.
9. Drain and remediate only if pressure risks pod eviction or node instability.

Commands:

```bash
oc describe node <node-name>
oc get events -A --sort-by=.lastTimestamp | grep -Ei 'disk|evict|image|ephemeral'
oc debug node/<node-name>
chroot /host
df -hT
df -ih
du -xhd1 /var | sort -h
journalctl -u kubelet --since "2 hours ago" | grep -Ei 'disk|evict|image|gc|ephemeral'
```

## 9. Disk I/O metrics

Disk capacity and disk I/O are different. A node can have enough free disk but still be slow because I/O is saturated.

### 9.1 Important disk I/O metrics

| Metric | Meaning |
|---|---|
| `node_disk_read_bytes_total` | Total bytes read from block device. |
| `node_disk_written_bytes_total` | Total bytes written to block device. |
| `node_disk_reads_completed_total` | Completed read operations. |
| `node_disk_writes_completed_total` | Completed write operations. |
| `node_disk_read_time_seconds_total` | Total time spent by reads. |
| `node_disk_write_time_seconds_total` | Total time spent by writes. |
| `node_disk_io_time_seconds_total` | Time spent doing I/O. Approximate utilization signal. |
| `node_disk_io_time_weighted_seconds_total` | Weighted time doing I/O; useful for queue/saturation analysis. |

Exclude loop and RAM devices:

```promql
device!~"loop.*|ram.*|dm-.*"
```

Whether to exclude `dm-*` depends on your storage stack. On RHCOS, device mapper paths can represent real underlying storage, LUKS, or logical volumes. For dashboard clarity, inspect actual devices first:

```bash
oc debug node/<node-name>
chroot /host
lsblk
```

### 9.2 Disk read/write throughput

Read MB/s:

```promql
rate(node_disk_read_bytes_total{device!~"loop.*|ram.*"}[5m]) / 1024 / 1024
```

Write MB/s:

```promql
rate(node_disk_written_bytes_total{device!~"loop.*|ram.*"}[5m]) / 1024 / 1024
```

### 9.3 Disk IOPS

Read IOPS:

```promql
rate(node_disk_reads_completed_total{device!~"loop.*|ram.*"}[5m])
```

Write IOPS:

```promql
rate(node_disk_writes_completed_total{device!~"loop.*|ram.*"}[5m])
```

### 9.4 Approximate disk utilization

```promql
100 * rate(node_disk_io_time_seconds_total{device!~"loop.*|ram.*"}[5m])
```

Interpretation:

- Near 100% for a sustained period suggests the disk is busy.
- On modern multi-queue devices, this value must be interpreted carefully. Use it as a saturation hint, not the only proof.
- Always correlate with I/O latency, application symptoms, and storage backend metrics.

### 9.5 Average read/write latency approximation

Average read seconds per operation:

```promql
rate(node_disk_read_time_seconds_total{device!~"loop.*|ram.*"}[5m])
/
rate(node_disk_reads_completed_total{device!~"loop.*|ram.*"}[5m])
```

Average write seconds per operation:

```promql
rate(node_disk_write_time_seconds_total{device!~"loop.*|ram.*"}[5m])
/
rate(node_disk_writes_completed_total{device!~"loop.*|ram.*"}[5m])
```

Convert to milliseconds:

```promql
1000 *
rate(node_disk_write_time_seconds_total{device!~"loop.*|ram.*"}[5m])
/
rate(node_disk_writes_completed_total{device!~"loop.*|ram.*"}[5m])
```

### 9.6 Disk I/O troubleshooting workflow

1. Check if CPU `iowait` is high.
2. Check read/write throughput.
3. Check IOPS.
4. Check approximate disk utilization.
5. Check average read/write latency.
6. Identify pods on the node causing disk activity.
7. Check storage classes, PVs, CSI drivers, ODF/local storage health.
8. Check logs for container runtime and kubelet delays.
9. If using cloud disks, compare against cloud provider IOPS/throughput limits.

Commands:

```bash
oc debug node/<node-name>
chroot /host
iostat -xz 1 5   # if sysstat is available
lsblk
journalctl -u kubelet --since "1 hour ago"
journalctl -u crio --since "1 hour ago"
```

### 10.1 Important network metrics

| `node_network_receive_bytes_total` | Bytes received by interface. |
| `node_network_transmit_bytes_total` | Bytes transmitted by interface. |
| `node_network_receive_packets_total` | Packets received. |

### 10.2 Interface filtering

Node network metrics include many virtual interfaces:

```text
lo
veth*
ovn-*
br-*
genev_sys_*
patch-*
```

A practical physical/primary interface filter might be:

```promql
device!~"lo|veth.*|br.*|ovn.*|genev_sys.*|patch.*"
```

Do not blindly use this in every cluster. Interface names depend on platform, CNI, SR-IOV, bonding, VLANs, and NIC naming.

### 10.3 Network receive/transmit throughput

Receive MB/s:

```promql
rate(node_network_receive_bytes_total{device!~"lo|veth.*|br.*|ovn.*|genev_sys.*|patch.*"}[5m]) / 1024 / 1024
```

Transmit MB/s:

```promql
rate(node_network_transmit_bytes_total{device!~"lo|veth.*|br.*|ovn.*|genev_sys.*|patch.*"}[5m]) / 1024 / 1024
```

### 10.4 Network packet errors

Receive errors:

```promql
rate(node_network_receive_errs_total{device!~"lo|veth.*"}[5m])
```

Transmit errors:

```promql
rate(node_network_transmit_errs_total{device!~"lo|veth.*"}[5m])
```

### 10.5 Packet drops

Receive drops:

```promql
rate(node_network_receive_drop_total{device!~"lo|veth.*"}[5m])
```

Transmit drops:

```promql
rate(node_network_transmit_drop_total{device!~"lo|veth.*"}[5m])
```

### 10.6 Network unavailable node condition

```promql
kube_node_status_condition{condition="NetworkUnavailable", status="true"} == 1
```

This condition indicates the node network is not correctly configured from the Kubernetes/OpenShift perspective.

### 10.7 Network troubleshooting workflow

1. Check node condition `NetworkUnavailable`.
2. Check primary interface throughput.
3. Check drops and errors.
4. Check whether drops are on physical NIC, bond, VLAN, OVN bridge, veth, or pod interface.
5. Check CNI/OVN pods on the affected node.
6. Check MTU mismatch, physical switch issues, NIC errors, bond degradation, or cloud ENI limits.
7. Check whether workload traffic is east-west, ingress, storage, registry, or control-plane traffic.
8. Use Network Observability Operator for flow-level troubleshooting where available.

Commands:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc get pods -A --field-selector spec.nodeName=<node-name>
oc debug node/<node-name>
chroot /host
ip -s link
ip addr
ip route
nmcli dev status
etstat -s  # if available
journalctl -u NetworkManager --since "1 hour ago"
```

For advanced packet-level checks, use approved operational tooling and change controls. Do not run disruptive packet captures on busy production nodes without clear scope.

## 11. Node readiness, pressure, and schedulability metrics

### 11.1 Node Ready condition

```promql
kube_node_status_condition{condition="Ready", status="true"}
```

Nodes not ready:

```promql
kube_node_status_condition{condition="Ready", status!="true"} == 1
```

Better practical alert-style query:

```promql
kube_node_status_condition{condition="Ready", status="true"} == 0
```

### 11.2 Node pressure conditions

```promql
kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure|NetworkUnavailable", status="true"} == 1
```

These conditions are important because they affect scheduling and eviction behavior.

| Condition | Meaning |
|---|---|
| `MemoryPressure` | Node memory is low. Kubelet may evict pods. |
| `DiskPressure` | Node disk or ephemeral storage is low. Kubelet may evict pods. |
| `PIDPressure` | Too many processes. New process creation can fail. |
| `NetworkUnavailable` | Node network is not correctly configured. |
| `Ready=false/unknown` | Node is unhealthy or not reporting correctly. |

### 11.3 Schedulability

Unschedulable nodes:

```promql
kube_node_spec_unschedulable == 1
```

CLI:

```bash
oc get nodes
oc describe node <node-name> | grep -i -A5 'Taints'
```

A node can be `Ready` but `SchedulingDisabled` because it is cordoned. That is operationally normal during maintenance but should be tracked.

### 11.4 Taints and dedicated nodes

Metrics alone do not always explain scheduling failures. Check:

```bash
oc describe node <node-name> | sed -n '/Taints:/,/Unschedulable:/p'
oc get nodes --show-labels
```

Common OpenShift node roles:

```text
node-role.kubernetes.io/master
node-role.kubernetes.io/control-plane
node-role.kubernetes.io/worker
node-role.kubernetes.io/infra
```

Workload placement issues often involve:

- Taints without matching tolerations
- Node selector mismatch
- Required node affinity mismatch
- Pod anti-affinity conflicts
- Insufficient allocatable CPU/memory
- Topology spread constraints
- PDB/drain interactions

## 12. Capacity and allocatable metrics

### 12.1 Capacity vs allocatable

Capacity is the total resource detected on the node. Allocatable is the resource available for pods after reservations.

PromQL:

Practical queries:

```promql
kube_node_status_capacity{resource="cpu", unit="core"}
kube_node_status_allocatable{resource="cpu", unit="core"}
kube_node_status_capacity{resource="memory", unit="byte"}
kube_node_status_allocatable{resource="memory", unit="byte"}
```

Cluster allocatable CPU:

```promql
sum(kube_node_status_allocatable{resource="cpu", unit="core"})
```

Cluster allocatable memory GiB:

```promql
sum(kube_node_status_allocatable{resource="memory", unit="byte"}) / 1024 / 1024 / 1024
```

### 12.2 Requested CPU and memory

CPU requested per node:

```promql
sum by (node) (kube_pod_container_resource_requests{resource="cpu", unit="core"})
```

Memory requested per node:

```promql
sum by (node) (kube_pod_container_resource_requests{resource="memory", unit="byte"})
```

CPU request saturation:

```promql
100 *
sum by (node) (kube_pod_container_resource_requests{resource="cpu", unit="core"})
/
on (node)
kube_node_status_allocatable{resource="cpu", unit="core"}
```

Memory request saturation:

```promql
100 *
sum by (node) (kube_pod_container_resource_requests{resource="memory", unit="byte"})
/
on (node)
kube_node_status_allocatable{resource="memory", unit="byte"}
```

### 12.3 Actual usage vs requested usage

CPU actual/request ratio:

```promql
sum by (node) (rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m]))
/
sum by (node) (kube_pod_container_resource_requests{resource="cpu", unit="core"})
```

Memory actual/request ratio:

```promql
sum by (node) (container_memory_working_set_bytes{container!="", pod!=""})
/
sum by (node) (kube_pod_container_resource_requests{resource="memory", unit="byte"})
```

Interpretation:

| Actual/request pattern | Meaning |
|---|---|
| Actual much lower than request | Over-requesting; wasted scheduling capacity. |
| Actual near request | Good request sizing if stable. |
| Actual much higher than request | Under-requesting; risk of noisy-neighbor behavior and eviction. |
| Limit much lower than actual need | CPU throttling or OOMKilled risk. |

### 12.4 Pod density per node

```promql
count by (node) (kube_pod_info)
```

Running pods only:

```promql
count by (node) (kube_pod_status_phase{phase="Running"} == 1)
```

Pods per node should be evaluated with CPU, memory, network, storage, process IDs, and platform maximums. High pod density increases kubelet, CRI-O, CNI, logging, and monitoring overhead.

## 13. PID and process metrics

### 13.1 Why PID metrics matter

A node can have enough CPU and memory but still fail to start containers if process IDs are exhausted. OpenShift exposes `PIDPressure` as a node condition.

### 13.2 PID pressure condition

```promql
kube_node_status_condition{condition="PIDPressure", status="true"} == 1
```

### 13.3 Process count metrics

Depending on node exporter version and enabled collectors, these might be available:

```promql
node_processes_pids
node_processes_max_processes
```

PID usage percentage:

```promql
100 * node_processes_pids / node_processes_max_processes
```

### 13.4 Troubleshooting PID pressure

Commands:

```bash
oc describe node <node-name>
oc debug node/<node-name>
chroot /host
ps -eLf | wc -l
cat /proc/sys/kernel/pid_max
ps -eo pid,ppid,comm,nlwp --sort=-nlwp | head
journalctl -u kubelet --since "1 hour ago" | grep -i pid
```

Common causes:

- Application spawning too many processes/threads
- Fork bomb or runaway process
- High pod density with high process count per pod
- Misconfigured `podPidsLimit`
- System daemons stuck in failure loop

## 15. Built-in dashboards and the USE method

OpenShift provides monitoring dashboards in the web console. For node performance, dashboards often follow the USE method:

```text
U = Utilization
S = Saturation
E = Errors
```

### 15.1 Applying USE to nodes

| Resource | Utilization | Saturation | Errors |
|---|---|---|---|
| CPU | CPU busy percentage | Run queue/load per core | CPU steal, throttling symptoms |
| Memory | Memory used / available | Memory pressure, reclaim, swap symptoms | OOMKilled, evictions |
| Disk capacity | Filesystem used | Predicted full, inode pressure | Read-only FS, DiskPressure |
| Disk I/O | Read/write throughput | I/O time, latency, queue | I/O errors, device resets |
| Network | RX/TX throughput | Interface saturation, queue drops | Packet errors/drops, link down |
| PID/process | PID usage | PIDPressure | Process creation failures |

### 15.2 Good node dashboard panels

A production node dashboard should include:

- Node Ready/NotReady state
- Node pressure conditions
- CPU usage by mode
- CPU usage by top pods
- Memory available percentage and GiB
- Memory usage by top pods
- Filesystem usage and inode usage by mountpoint
- Disk I/O throughput and utilization
- Network throughput by interface
- Network drops/errors
- Pod count per node
- Requested CPU/memory vs allocatable
- `up` status for node-exporter and kubelet targets
- Maintenance state: cordoned/unschedulable nodes

Avoid dashboards that only show average cluster CPU and memory. Averages hide hot nodes.

## 16. Alerting strategy for node metrics

### 16.1 Alert design principles

Good node alerts are:

- Symptom-based when possible
- Persistent for several minutes to avoid noise
- Labeled with node, severity, and runbook link
- Actionable by on-call engineers
- Correlated with node conditions and workload impact

Bad alerts:

- Alerting on raw counters
- Alerting on `MemFree` instead of `MemAvailable`
- Alerting on short one-minute spikes without impact
- Alerting on cluster averages instead of per-node failures
- Alerting on expected maintenance without silences

### 16.2 Example alert ideas

| Alert | PromQL idea | Severity |
|---|---|---|
| Node exporter down | `up{job=~".*node-exporter.*"} == 0` | warning/critical depending duration |
| Node not ready | `kube_node_status_condition{condition="Ready",status="true"} == 0` | critical |
| Memory pressure | `kube_node_status_condition{condition="MemoryPressure",status="true"} == 1` | critical |
| Disk pressure | `kube_node_status_condition{condition="DiskPressure",status="true"} == 1` | critical |
| PID pressure | `kube_node_status_condition{condition="PIDPressure",status="true"} == 1` | critical |
| Filesystem almost full | filesystem usage > 85/90/95% | warning/critical |
| Inodes almost exhausted | inode usage > 85/90/95% | warning/critical |
| High CPU | CPU > 85% for 15m | warning |
| High iowait | iowait > 20% for 10m | warning |
| Network drops/errors | drops/errors rate > baseline | warning |
| Node unschedulable too long | `kube_node_spec_unschedulable == 1` for unexpected duration | warning |

### 16.3 Sample PrometheusRule for custom environments

For user workload monitoring, custom rules are normally created in user-defined namespaces with monitoring enabled. For core platform alerts, follow Red Hat-supported mechanisms and do not edit generated rules directly.

Example pattern:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: node-custom-rules
  namespace: my-monitoring-project
spec:
  groups:
  - name: custom-node.rules
    rules:
    - alert: CustomNodeHighCPU
      expr: |
        100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))) > 85
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "High CPU usage on node {{ $labels.instance }}"
        description: "Node CPU usage is above 85% for 15 minutes. Check CPU by mode and top pods."
```

Before deploying custom rules:

```bash
promtool check rules node-custom-rules.yaml
oc apply -f node-custom-rules.yaml
```

In OpenShift, always align custom alerting with your platform monitoring model, RBAC, namespace selection, and support policy.

## 17. Metrics collection profile and retention impact

### 17.1 Full vs minimal metrics collection

OpenShift monitoring supports metrics collection profiles. A full profile collects the default broad metric set. A minimal profile collects only metrics needed for platform alerts, recording rules, telemetry, and console dashboards.

Operational impact:

- Full profile is best for deep troubleshooting and platform engineering.
- Minimal profile reduces Prometheus CPU/memory/storage usage.
- Some ad-hoc node PromQL queries may not work in minimal mode.
- Before blaming missing metrics, check whether the cluster uses a minimal collection profile.

### 17.2 Prometheus retention

Prometheus retention controls how long local time-series data is kept. Default core platform retention is commonly 15 days in OpenShift documentation examples. Production clusters often need more or less depending on:

- Compliance requirements
- Incident review window
- Capacity planning needs
- Storage cost
- Number of nodes and pods
- Number of scraped metrics and scrape interval
- Cardinality

### 17.3 Cardinality warning

Node metrics can become expensive when labels explode. Watch out for:

- Too many pod/container labels in joins
- Per-device, per-interface, per-mountpoint metrics on many nodes
- High pod churn
- Custom exporters exposing unbounded labels
- Excessive dashboards using expensive wide queries

Cardinality affects Prometheus memory, disk, query latency, and retention.

Useful checks:

```promql
count({__name__=~"node_.*"})
count by (__name__) ({__name__=~"node_.*"})
topk(20, count by (__name__) ({__name__=~"node_.*"}))
```

## 18. Advanced troubleshooting runbooks

## 18.1 Runbook: node CPU high

Symptoms:

- `oc adm top nodes` shows high CPU.
- Node dashboard shows CPU above 85%.
- Application latency increases.
- Kubelet or CRI-O may become slow.

PromQL:

```promql
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
100 * avg by (instance, mode) (rate(node_cpu_seconds_total[5m]))
topk(10, sum by (node, namespace, pod) (rate(container_cpu_usage_seconds_total{container!="", pod!=""}[5m])))
```

CLI:

```bash
oc adm top nodes
oc adm top pods -A --sort-by=cpu
oc get pods -A --field-selector spec.nodeName=<node-name>
oc describe node <node-name>
```

Decision tree:

- High `user` CPU: application workload issue or expected high usage.
- High `system`: kernel/CNI/storage/runtime overhead.
- High `iowait`: storage bottleneck.
- High `steal`: virtualization/cloud contention.
- High `softirq`: possible network packet processing pressure.

Actions:

- Scale workload horizontally if application CPU-bound.
- Correct CPU requests/limits.
- Move noisy workload to dedicated nodes.
- Investigate storage/network if iowait/softirq is high.
- Add worker capacity if sustained workload is legitimate.
- Check cluster autoscaler/machine autoscaler if applicable.

---

## 18.2 Runbook: node memory pressure

Symptoms:

- Node condition `MemoryPressure=True`.
- Pods evicted.
- Containers OOMKilled.
- Kubelet logs show eviction messages.

PromQL:

```promql
100 * (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes))
kube_node_status_condition{condition="MemoryPressure",status="true"}
topk(10, sum by (node, namespace, pod) (container_memory_working_set_bytes{container!="", pod!=""}))
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

CLI:

```bash
oc adm top pods -A --sort-by=memory
oc describe node <node-name>
oc get events -A --sort-by=.lastTimestamp | grep -Ei 'evict|oom|memory'
```

Actions:

- Identify top memory pods.
- Validate requests and limits.
- Fix memory leaks.
- Reduce pod density on node.
- Move memory-heavy workloads to larger/dedicated nodes.
- Tune reserved resources via supported KubeletConfig if needed.
- Add nodes or larger node types for sustained demand.

---

## 18.3 Runbook: node disk pressure

Symptoms:

- `DiskPressure=True`.
- Pods evicted due to ephemeral storage.
- Image pulls fail.
- Container runtime errors.
- Node logs or container logs fill disk.

PromQL:

```promql
kube_node_status_condition{condition="DiskPressure",status="true"}
100 * (1 - node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"})
100 * (1 - node_filesystem_files_free{fstype!~"tmpfs|overlay|squashfs"} / node_filesystem_files{fstype!~"tmpfs|overlay|squashfs"})
topk(10, sum by (namespace, pod) (container_fs_usage_bytes{container!="", pod!=""}))
```

CLI:

```bash
oc describe node <node-name>
oc get events -A --sort-by=.lastTimestamp | grep -Ei 'disk|ephemeral|evict|image'
oc debug node/<node-name>
chroot /host
df -hT
df -ih
du -xhd1 /var | sort -h
```

Actions:

- Identify filling mountpoint.
- Fix noisy log-writing workload.
- Set ephemeral storage requests/limits.
- Tune log retention through supported mechanisms.
- Check image garbage collection.
- Increase disk size if persistent trend is valid.
- Drain node only if needed and safe.

---

## 18.4 Runbook: node NotReady

Symptoms:

- `oc get nodes` shows `NotReady`.
- Workloads unavailable on that node.
- Prometheus target down.
- Kubelet heartbeat missing.

PromQL:

```promql
kube_node_status_condition{condition="Ready",status="true"} == 0
up{job=~".*node-exporter.*"} == 0
```

CLI:

```bash
oc get nodes -o wide
oc describe node <node-name>
oc get events -A --sort-by=.lastTimestamp | tail -100
oc adm node-logs <node-name> -u kubelet
```

Investigate:

- Kubelet down or unhealthy
- CRI-O failure
- Node network issue
- Disk full
- Memory pressure
- Certificate issue
- MachineConfig update/reboot
- Cloud/bare-metal host issue
- CNI/OVN issue

Actions:

- Check cluster operators.
- Check MachineConfigPool state.
- Check node logs.
- If a planned update/reboot is in progress, verify progress.
- If unplanned, isolate the node, protect workloads, and remediate host/runtime/network issue.

---

## 18.5 Runbook: node exporter target down but node is Ready

Symptoms:

- Node Ready in Kubernetes.
- `up{job=~".*node-exporter.*"} == 0`.
- Missing node metrics for one node.

Checks:

```bash
oc get pods -n openshift-monitoring -o wide | grep -i node-exporter
oc describe pod -n openshift-monitoring <node-exporter-pod>
oc logs -n openshift-monitoring <node-exporter-pod>
oc get servicemonitor -n openshift-monitoring | grep -i node
oc get endpoints -n openshift-monitoring | grep -i node
```

Possible causes:

- node-exporter pod failed on that node
- NetworkPolicy or SDN issue affecting scrape
- Prometheus cannot reach target
- Certificate/authentication issue
- Node under heavy load causing scrape timeout
- Monitoring stack degraded

Actions:

- Restarting CMO-managed pods manually is usually not the first fix.
- Check CMO and Prometheus Operator status.
- Check node resource pressure.
- Check Observe -> Targets error message.
- Use supported OpenShift monitoring procedures.

## 19. Correlating node metrics with scheduling failures

When pods are Pending, node metrics help explain why.

### 19.1 Check Pending pods

```bash
oc get pods -A --field-selector=status.phase=Pending
oc describe pod -n <namespace> <pod-name>
```

### 19.2 Common scheduler messages

| Scheduler message | Node metric or state to check |
|---|---|
| Insufficient cpu | `kube_node_status_allocatable`, CPU requests per node |
| Insufficient memory | `kube_node_status_allocatable`, memory requests per node |
| node(s) had untolerated taint | Node taints, workload tolerations |
| node(s) didn't match node selector | Node labels, pod nodeSelector |
| node(s) didn't match Pod's node affinity | Node labels and affinity rules |
| node(s) had volume node affinity conflict | PV zone/topology labels |
| Too many pods | Pod density, kubelet max pods |
| node(s) had disk pressure | `DiskPressure` condition |
| node(s) had memory pressure | `MemoryPressure` condition |

### 19.3 Useful PromQL for scheduling capacity

Available allocatable CPU per node:

```promql
kube_node_status_allocatable{resource="cpu", unit="core"}
-
sum by (node) (kube_pod_container_resource_requests{resource="cpu", unit="core"})
```

Available allocatable memory per node:

```promql
(
kube_node_status_allocatable{resource="memory", unit="byte"}
-
sum by (node) (kube_pod_container_resource_requests{resource="memory", unit="byte"})
) / 1024 / 1024 / 1024
```

Unschedulable nodes:

```promql
kube_node_spec_unschedulable == 1
```

Nodes with pressure:

```promql
kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure", status="true"} == 1
```

## 20. Node metrics during OpenShift upgrades

During OpenShift upgrades, node metrics are critical because nodes are cordoned, drained, rebooted, and returned to service. Watch:

- Control plane CPU and memory headroom
- Worker node drain duration
- MachineConfigPool update progress
- Node Ready state
- Node exporter target availability
- Workload rescheduling impact
- PDB-blocked drains
- Storage detach/attach delays
- Kubelet and CRI-O errors after reboot

Commands:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc adm upgrade status
```

PromQL:

```promql
kube_node_status_condition{condition="Ready",status="true"}
kube_node_spec_unschedulable
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
100 * (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes))
```

Best practice: keep enough CPU/memory headroom so remaining nodes can handle workload while one or more nodes are unavailable for maintenance.

## 22. Common mistakes and production lessons

### 22.1 Mistake: using cluster averages

Cluster average CPU can be 40% while one node is at 95%. Always inspect per-node metrics.

Bad:

```promql
avg(100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))))
```

Better:

```promql
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
```

### 22.2 Mistake: alerting on `MemFree`

Linux intentionally uses memory for cache. Use `MemAvailable`.

### 22.3 Mistake: ignoring iowait

High load with low CPU is often I/O wait. Check disk latency and storage backend.

### 22.4 Mistake: ignoring inode usage

Filesystem bytes can be fine while inodes are exhausted.

### 22.5 Mistake: treating `oc adm top` as historical truth

`oc adm top` is a snapshot. Use Prometheus/Thanos for historical analysis.

### 22.6 Mistake: modifying generated monitoring resources

OpenShift monitoring resources are reconciled by Operators. Configure only supported settings such as documented ConfigMaps and supported CRDs.

### 22.7 Mistake: not filtering virtual interfaces and filesystems

Unfiltered dashboards often show `lo`, `veth`, `tmpfs`, `overlay`, pod mounts, and other noisy series.

### 22.8 Mistake: missing workload context

Node metrics show symptoms. You still need deployment, event, pod, log, and change history context.

## 24. PromQL cheat sheet

### 24.1 CPU

```promql
# CPU utilization percentage per node
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))

# CPU by mode
100 * avg by (instance, mode) (rate(node_cpu_seconds_total[5m]))

# iowait percentage
100 * avg by (instance) (rate(node_cpu_seconds_total{mode="iowait"}[5m]))

# load per core
node_load1 / count by (instance) (node_cpu_seconds_total{mode="idle"})
```

### 24.2 Memory

```promql
# Node memory used percentage using MemAvailable
100 * (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes))

# Available memory GiB
node_memory_MemAvailable_bytes / 1024 / 1024 / 1024

# Top pod memory usage
sum by (node, namespace, pod) (container_memory_working_set_bytes{container!="", pod!=""})
```

### 24.3 Filesystem

```promql
# Filesystem usage percentage
100 * (1 - node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"})

# Inode usage percentage
100 * (1 - node_filesystem_files_free{fstype!~"tmpfs|overlay|squashfs"} / node_filesystem_files{fstype!~"tmpfs|overlay|squashfs"})

# Predict root filesystem full in 24h
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 24 * 3600) < 0
```

### 24.4 Disk I/O

```promql
# Read MB/s
rate(node_disk_read_bytes_total{device!~"loop.*|ram.*"}[5m]) / 1024 / 1024

# Write MB/s
rate(node_disk_written_bytes_total{device!~"loop.*|ram.*"}[5m]) / 1024 / 1024

# Approx disk utilization percentage
100 * rate(node_disk_io_time_seconds_total{device!~"loop.*|ram.*"}[5m])

# Average write latency in ms
1000 * rate(node_disk_write_time_seconds_total{device!~"loop.*|ram.*"}[5m]) / rate(node_disk_writes_completed_total{device!~"loop.*|ram.*"}[5m])
```

### 24.5 Network

```promql
# Receive MB/s
rate(node_network_receive_bytes_total{device!~"lo|veth.*|br.*|ovn.*|genev_sys.*|patch.*"}[5m]) / 1024 / 1024

# Transmit MB/s
rate(node_network_transmit_bytes_total{device!~"lo|veth.*|br.*|ovn.*|genev_sys.*|patch.*"}[5m]) / 1024 / 1024

# Receive errors
rate(node_network_receive_errs_total{device!~"lo|veth.*"}[5m])

# Transmit drops
rate(node_network_transmit_drop_total{device!~"lo|veth.*"}[5m])
```

### 24.6 Node conditions

```promql
# Node not ready
kube_node_status_condition{condition="Ready", status="true"} == 0

# Any pressure condition
kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure|NetworkUnavailable", status="true"} == 1

# Unschedulable nodes
kube_node_spec_unschedulable == 1
```

### 24.7 Requests vs allocatable

```promql
# CPU request percentage per node
100 * sum by (node) (kube_pod_container_resource_requests{resource="cpu", unit="core"}) / on (node) kube_node_status_allocatable{resource="cpu", unit="core"}

# Memory request percentage per node
100 * sum by (node) (kube_pod_container_resource_requests{resource="memory", unit="byte"}) / on (node) kube_node_status_allocatable{resource="memory", unit="byte"}
```

## 25. Interview/exam-style explanation

If asked to explain node metrics in OpenShift:

> Node metrics in OpenShift are collected mainly through node-exporter, kubelet/cAdvisor, Metrics Server, kube-state-metrics, and OpenShift state metrics. Node exporter runs as a DaemonSet on every node and exposes Linux host metrics such as CPU, memory, disk, filesystem, network, load, and process metrics. Kubelet and cAdvisor expose pod and container resource usage. kube-state-metrics exposes Kubernetes object state such as node readiness, pressure conditions, capacity, allocatable resources, and pod resource requests. Prometheus scrapes these metrics as part of the OpenShift monitoring stack, stores them as time series, and Thanos Querier provides a unified query endpoint for dashboards, alerts, and PromQL. Metrics Server provides the Kubernetes resource metrics API used by quick commands such as `oc adm top nodes`. For troubleshooting, I correlate node exporter metrics with kube-state-metrics and container metrics to determine whether a problem is host-level, workload-level, scheduling-level, or monitoring-pipeline-level.

A senior answer should also mention:

- Use `MemAvailable`, not `MemFree`.
- CPU must be broken down by mode: user, system, iowait, steal, softirq.
- Disk pressure includes bytes, inodes, container logs, image filesystem, and ephemeral storage.
- Network dashboards must filter virtual interfaces carefully.
- Scheduling decisions use requests and allocatable resources, not actual usage.
- Node conditions are Kubernetes state, while node exporter metrics are Linux host measurements.
- `oc adm top` is a quick view, while PromQL is needed for historical and deep analysis.
- OpenShift monitoring components are Operator-managed; configure supported settings only.

## 26. Production checklist for node metrics

Use this checklist for a real cluster review.

### 26.1 Monitoring health

- [ ] `ClusterOperator/monitoring` is Available and not Degraded.
- [ ] Prometheus pods are running.
- [ ] Thanos Querier route works.
- [ ] node-exporter DaemonSet has one pod per node.
- [ ] `up{job=~".*node-exporter.*"}` is `1` for all nodes.
- [ ] Observe -> Targets has no unexpected down targets.
- [ ] Alertmanager receivers are configured.

### 26.2 Node health

- [ ] All nodes are Ready.
- [ ] No unexpected cordoned nodes.
- [ ] No `MemoryPressure`, `DiskPressure`, `PIDPressure`, or `NetworkUnavailable`.
- [ ] CPU has enough headroom.
- [ ] Memory has enough `MemAvailable`.
- [ ] Root and container storage filesystems have enough free space and inodes.
- [ ] Network errors and drops are near zero or within known baseline.
- [ ] Disk I/O latency is within acceptable range.

### 26.3 Capacity

- [ ] Requests are not heavily overcommitted beyond policy.
- [ ] Actual usage is not consistently near allocatable.
- [ ] Control plane and infra nodes have enough headroom for upgrades and failures.
- [ ] Pod density per node is within design limits.
- [ ] Dedicated node pools have dedicated dashboards.

### 26.4 Alerting

- [ ] NodeNotReady alert exists.
- [ ] MemoryPressure/DiskPressure/PIDPressure alerts exist.
- [ ] Filesystem and inode predictive alerts exist.
- [ ] Node exporter target down alert exists.
- [ ] Alerts include severity, node label, and runbook link.
- [ ] Maintenance silencing process exists.

## 28. Final summary

Node metrics in OpenShift are not just numbers on a dashboard. They are the operational language of cluster health. A 10-year-level administrator should know the complete path from Linux kernel counters to node-exporter, kubelet/cAdvisor, kube-state-metrics, Prometheus, Thanos, dashboards, alerts, and `oc adm top`. The best troubleshooting comes from correlating host-level metrics, container-level metrics, and Kubernetes object-state metrics.

For production work, always ask:

1. Is the node healthy from Kubernetes point of view?
2. Is the Linux host saturated on CPU, memory, disk, network, or PIDs?
3. Which pods or system components are causing the pressure?
4. Is the monitoring data complete and being scraped correctly?
5. Is the issue temporary, workload-driven, infrastructure-driven, or capacity/design-driven?
6. What alert, dashboard, or capacity rule should prevent the same issue next time?
