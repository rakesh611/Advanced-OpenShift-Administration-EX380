## 1. Executive Summary

Scheduler metrics tell you whether OpenShift can place new pods onto nodes quickly, correctly, and consistently. In a healthy cluster, the scheduler consumes pending pods from its queues, filters and scores candidate nodes, binds pods, and keeps end-to-end scheduling latency low. When the scheduler or the cluster placement conditions are unhealthy, you normally see one or more of these symptoms:

- Pods remain in `Pending` state.
- `scheduler_pending_pods` grows, especially `queue="unschedulable"` or `queue="backoff"`.
- `scheduler_schedule_attempts_total{result="unschedulable"}` increases.
- `scheduler_schedule_attempts_total{result="error"}` increases.
- Scheduler latency histograms show elevated p95/p99 values.
- Plugin-level metrics point to expensive or blocking scheduling phases such as node affinity, taints/tolerations, inter-pod affinity, topology spread, volume binding, or resource fit.

For an experienced administrator, scheduler metrics are not only about checking whether `kube-scheduler` is up. They help answer deeper questions:

- Is the problem the scheduler itself, or are pods unschedulable because the cluster has no valid placement?
- Is scheduling slow due to cluster scale, expensive affinity rules, topology spread, or volume binding?
- Are workloads being packed or spread as expected after changing the OpenShift scheduler profile?
- Are node pools, taints, labels, MachineSets, and storage classes aligned with application placement rules?
- Is pending pod growth a capacity issue, an RBAC/admission issue, or a placement policy issue?

## 2. What the Scheduler Does in OpenShift

The default OpenShift scheduler is based on the Kubernetes scheduler. It watches for newly created pods that do not yet have a node assignment and decides which node should run each pod. It does not run the workload itself. It creates a binding between the pod and a selected node. After binding, the kubelet on that node starts handling pod execution.

At a high level, scheduling has these phases:

1. **Queueing**
   - A new pod enters the scheduler queue.
   - Pods might be active, delayed by backoff, marked unschedulable, or gated.

2. **Filtering**
   - The scheduler removes nodes that cannot run the pod.
   - Examples: insufficient CPU/memory, missing node labels, unmatched taints, volume constraints, pod anti-affinity conflicts, topology spread violations.

3. **Scoring**
   - Candidate nodes are ranked.
   - Scoring behavior depends on scheduler profile and enabled plugins.

4. **Reserve / Permit / Pre-bind**
   - The scheduler reserves resources logically and runs extension points.
   - Some plugins can wait or reject.

5. **Binding**
   - The scheduler sends a binding request to the API server.
   - After this, the pod has `spec.nodeName` set.

6. **Post-scheduling observation**
   - The pod might still fail later due to image pulls, CNI setup, CSI attach/mount, SCC/runtime constraints, or container startup. These are not pure scheduler placement failures, but they can be confused with scheduling problems.

### OpenShift scheduler components

In OpenShift, scheduler operation is controlled by cluster operators and cluster configuration. Typical objects and namespaces you inspect are:

```bash
oc get co kube-scheduler
oc get scheduler cluster -o yaml
oc get pods -n openshift-kube-scheduler -o wide
oc get pods -n openshift-kube-scheduler-operator -o wide
```

Common control points:

- `ClusterOperator/kube-scheduler` tells you whether the scheduler operator is available, progressing, degraded, or upgrade-blocking.
- `Scheduler/cluster` under `config.openshift.io/v1` controls cluster-level scheduler settings such as scheduler profile.
- `openshift-kube-scheduler` normally contains scheduler static pods and related revision/installer/pruner resources.
- `openshift-kube-scheduler-operator` normally contains the operator that manages scheduler lifecycle.

Do not manually edit scheduler static pod manifests or generated config unless directed by Red Hat support. Use supported OpenShift configuration APIs.

## 3. Where Scheduler Metrics Come From

The scheduler exports metrics from its `/metrics` endpoint in Prometheus format. OpenShift platform monitoring scrapes scheduler metrics as part of the default platform monitoring stack.

Scheduler metrics can be divided into these categories:

| Category | Purpose | Example metrics |
|---|---|---|
| Availability | Is the scheduler target scrapeable? | `up`, `target_info` |
| Queue pressure | Are pods waiting to be scheduled? | `scheduler_pending_pods`, `scheduler_queue_incoming_pods_total` |
| Scheduling outcomes | Are attempts succeeding, failing, or unschedulable? | `scheduler_schedule_attempts_total` |
| Scheduling latency | How long scheduling takes | `scheduler_scheduling_attempt_duration_seconds`, `scheduler_pod_scheduling_sli_duration_seconds` |
| Retry behavior | How many attempts are required before success? | `scheduler_pod_scheduling_attempts` |
| Preemption | Is the scheduler trying to evict lower-priority pods to place higher-priority pods? | `scheduler_preemption_attempts_total`, `scheduler_preemption_victims` |
| Framework/plugin latency | Which scheduling extension point or plugin is expensive? | `scheduler_framework_extension_point_duration_seconds`, `scheduler_plugin_execution_duration_seconds` |
| Internal scheduler/cache | Scheduler internals and work queues | `scheduler_cache_size`, `scheduler_goroutines`, `workqueue_*` |
| Go/process runtime | Runtime health of the process | `go_*`, `process_*` metrics, depending on version and scrape config |

## 4. How OpenShift Monitors Scheduler Metrics

OpenShift includes a preconfigured, preinstalled, self-updating monitoring stack. The platform monitoring stack monitors core platform components, including the Kubernetes scheduler. The important components for scheduler metric access are:

- **Cluster Monitoring Operator (CMO)**: Manages the platform monitoring stack.
- **Prometheus Operator**: Creates and manages platform Prometheus instances.
- **Prometheus**: Scrapes scheduler metrics and stores time series.
- **Thanos Querier**: Provides a query layer over platform and user workload metrics.
- **Alertmanager**: Handles alert delivery.
- **Web console Observe section**: Lets admins query metrics, inspect alerts, and review dashboards.

### Access paths

You usually query scheduler metrics by one of these methods:

1. **OpenShift web console**
   - Administrator perspective → Observe → Metrics
   - Run PromQL such as:

```promql
scheduler_pending_pods
```

2. **Thanos Querier route with bearer token**

```bash
THANOS_HOST=$(oc -n openshift-monitoring get route thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

curl -k -G \
  -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/query" \
  --data-urlencode 'query=scheduler_pending_pods'
```

3. **Prometheus UI inside cluster**
   - Usually accessed through OpenShift console integrations or secured routes.
   - Direct access depends on cluster configuration and permissions.

### Verify metric availability

Before writing alerts, list metric metadata:

```bash
THANOS_HOST=$(oc -n openshift-monitoring get route thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

curl -k \
  -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/metadata" \
  | jq '.data | keys[] | select(test("^scheduler_"))'
```

Or check a single metric:

```bash
curl -k -G \
  -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_HOST}/api/v1/query" \
  --data-urlencode 'query=count(scheduler_schedule_attempts_total)'
```

## 5. Scheduler Metrics Mental Model

For troubleshooting, think in this order:

```text
Can Prometheus scrape the scheduler?
        ↓
Are pods entering scheduler queues?
        ↓
Are queues draining normally?
        ↓
Are scheduling attempts successful, unschedulable, or erroring?
        ↓
Is latency high globally or only for a plugin/extension point?
        ↓
Do pod events explain the placement constraint?
        ↓
Is this capacity, policy, storage, node health, or scheduler health?
```

### The most important scheduler signals

For day-2 OpenShift operations, these are the scheduler metrics you should know first:

| Metric | What it tells you |
|---|---|
| `scheduler_pending_pods` | Current pending scheduler queue depth by queue type |
| `scheduler_queue_incoming_pods_total` | Rate of pods entering scheduler queues |
| `scheduler_schedule_attempts_total` | Attempt count by result: scheduled, unschedulable, or error |
| `scheduler_scheduling_attempt_duration_seconds` | Per-attempt scheduling latency including algorithm and binding |
| `scheduler_pod_scheduling_sli_duration_seconds` | End-to-end scheduling SLI latency from queue entry through scheduling; can involve multiple attempts |
| `scheduler_pod_scheduling_attempts` | Attempts needed to schedule a pod |
| `scheduler_framework_extension_point_duration_seconds` | Latency by scheduling framework extension point |
| `scheduler_plugin_execution_duration_seconds` | Plugin-level execution latency; alpha in Kubernetes metrics reference |
| `scheduler_unschedulable_pods` | Unschedulable pods broken down by plugin; alpha in Kubernetes metrics reference |
| `scheduler_preemption_attempts_total` | Number of preemption attempts |
| `scheduler_preemption_victims` | Number of selected victims during preemption |

## 6. Core Scheduler Metric Families

### 6.1 `scheduler_pending_pods`

**Type:** Gauge  
**Purpose:** Number of pending pods by scheduler queue type.

Important `queue` label values:

| Queue | Meaning | Operational interpretation |
|---|---|---|
| `active` | Pods actively waiting to be scheduled | Short spikes are normal. Sustained growth means scheduler cannot keep up or pods are repeatedly cycling. |
| `backoff` | Pods waiting for retry backoff | Often caused by repeated scheduling failures. Check events and unschedulable reasons. |
| `unschedulable` | Scheduler already attempted scheduling and failed | Usually placement/capacity/policy issue, not necessarily scheduler process failure. |
| `gated` | Pods blocked by scheduling gates and not yet attempted | Intentional if using pod scheduling readiness/gates. Unexpected growth means something never removes gates. |

PromQL:

```promql
sum by (queue) (scheduler_pending_pods)
```

Interpretation:

- `active` temporarily high after a large rollout is expected.
- `unschedulable` high for many minutes means pods cannot fit existing cluster constraints.
- `backoff` high means repeated failed attempts.
- `gated` high means pods are intentionally not eligible yet, or gates are stuck.

### 6.2 `scheduler_queue_incoming_pods_total`

**Type:** Counter  
**Purpose:** Number of pods added to scheduling queues by event and queue type.

PromQL:

```promql
sum by (event, queue) (rate(scheduler_queue_incoming_pods_total[5m]))
```

Use this metric to understand scheduler workload volume. It is especially useful during deployments, autoscaling events, node drains, or cluster upgrades.

### 6.3 `scheduler_schedule_attempts_total`

**Type:** Counter  
**Purpose:** Number of attempts to schedule pods by result.

Common `result` values:

| Result | Meaning | Action |
|---|---|---|
| `scheduled` | Attempt successfully placed a pod | Healthy signal if latency is acceptable. |
| `unschedulable` | No node met constraints | Inspect pod events, resources, node labels, taints, PVCs, topology spread, affinity. |
| `error` | Internal scheduler error | Investigate scheduler logs, API server health, RBAC/cert/config problems, operator status. |

PromQL:

```promql
sum by (result) (rate(scheduler_schedule_attempts_total[5m]))
```

Error ratio:

```promql
sum(rate(scheduler_schedule_attempts_total{result="error"}[5m]))
/
sum(rate(scheduler_schedule_attempts_total[5m]))
```

Unschedulable ratio:

```promql
sum(rate(scheduler_schedule_attempts_total{result="unschedulable"}[5m]))
/
sum(rate(scheduler_schedule_attempts_total[5m]))
```

### 6.4 `scheduler_scheduling_attempt_duration_seconds`

**Type:** Histogram  
**Purpose:** Scheduling attempt latency in seconds. It includes scheduling algorithm and binding for a single scheduling attempt.

PromQL p99:

```promql
histogram_quantile(
  0.99,
  sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m]))
)
```

By result:

```promql
histogram_quantile(
  0.99,
  sum by (le, result) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m]))
)
```

Interpretation:

- High p99 with `result="scheduled"`: scheduling succeeds but slowly.
- High p99 with `result="unschedulable"`: scheduler spends time evaluating impossible placements.
- High p99 with high `active` queue: scheduler throughput is insufficient for incoming workload.
- High p99 but low queue: occasional expensive pods, often affinity/topology/storage-related.

### 6.5 `scheduler_pod_scheduling_sli_duration_seconds`

**Type:** Histogram  
**Purpose:** End-to-end pod scheduling SLI latency from queue entry to scheduling, possibly involving multiple attempts.

PromQL p95:

```promql
histogram_quantile(
  0.95,
  sum by (le) (rate(scheduler_pod_scheduling_sli_duration_seconds_bucket[5m]))
)
```

PromQL p99:

```promql
histogram_quantile(
  0.99,
  sum by (le) (rate(scheduler_pod_scheduling_sli_duration_seconds_bucket[5m]))
)
```

This metric is better for user-impact view because it measures the overall scheduling experience for pods, not only one attempt.

### 6.6 `scheduler_pod_scheduling_attempts`

**Type:** Histogram  
**Purpose:** Number of attempts required to successfully schedule a pod.

Average attempts:

```promql
sum(rate(scheduler_pod_scheduling_attempts_sum[5m]))
/
sum(rate(scheduler_pod_scheduling_attempts_count[5m]))
```

High values indicate that pods often require retries before successful placement. Typical reasons include:

- transient node readiness changes,
- delayed PVC binding,
- cluster autoscaler adding nodes,
- pods waiting for gates or quota-related changes,
- workload placement rules that become satisfiable only after other pods move or finish.

### 6.7 `scheduler_framework_extension_point_duration_seconds`

**Type:** Histogram  
**Purpose:** Latency for running all plugins at a specific scheduler framework extension point.

Useful labels include:

- `extension_point`
- `profile`
- `status`

PromQL:

```promql
histogram_quantile(
  0.99,
  sum by (le, extension_point, status) (
    rate(scheduler_framework_extension_point_duration_seconds_bucket[5m])
  )
)
```

Important extension points:

| Extension point | What it means |
|---|---|
| `PreFilter` | Plugin preparation before filtering nodes |
| `Filter` | Node eligibility checks |
| `PostFilter` | Runs after filtering, often related to preemption when no node fits |
| `PreScore` | Preparation before scoring |
| `Score` | Ranking candidate nodes |
| `Reserve` | Temporary reservation of resources |
| `Permit` | Approval/wait phase before binding |
| `PreBind` | Actions before binding, often volume-related |
| `Bind` | Binding pod to node |
| `PostBind` | Actions after bind |

### 6.8 `scheduler_plugin_execution_duration_seconds`

**Type:** Histogram  
**Stability:** Alpha in Kubernetes metrics reference  
**Purpose:** Duration for a specific scheduler plugin at a specific extension point.

PromQL:

```promql
histogram_quantile(
  0.99,
  sum by (le, extension_point, plugin, status) (
    rate(scheduler_plugin_execution_duration_seconds_bucket[5m])
  )
)
```

Use this for deep diagnostics, but avoid hard dependency in long-term alerts unless you verify metric stability for your OpenShift version.

Common plugin names you might see:

| Plugin | Typical issue it reveals |
|---|---|
| `NodeResourcesFit` | Insufficient CPU, memory, pod count, ephemeral storage, extended resources |
| `NodeAffinity` | Required node affinity or node selector mismatch |
| `TaintToleration` | Pod does not tolerate node taints |
| `InterPodAffinity` | Expensive or impossible pod affinity/anti-affinity rules |
| `PodTopologySpread` | Topology spread constraints cannot be satisfied |
| `VolumeBinding` | PVC/PV/StorageClass/zone binding issue |
| `NodePorts` | Host port or node port conflict |
| `NodeUnschedulable` | Nodes cordoned or unschedulable |
| `PodFitsHostPorts` / host-port plugin variants | Host port conflict depending on Kubernetes version |

### 6.9 `scheduler_unschedulable_pods`

**Type:** Gauge  
**Stability:** Alpha in Kubernetes metrics reference  
**Purpose:** Number of unschedulable pods by plugin.

PromQL:

```promql
sum by (plugin, profile) (scheduler_unschedulable_pods)
```

This can quickly show whether unschedulability is dominated by `NodeResourcesFit`, `TaintToleration`, `NodeAffinity`, `VolumeBinding`, or other plugins.

Important: a pod can be counted under multiple plugins because more than one condition can make it unschedulable.

### 6.10 Preemption metrics

#### `scheduler_preemption_attempts_total`

**Type:** Counter  
**Purpose:** Total preemption attempts.

```promql
rate(scheduler_preemption_attempts_total[5m])
```

#### `scheduler_preemption_victims`

**Type:** Histogram  
**Purpose:** Number of selected preemption victims.

```promql
histogram_quantile(
  0.95,
  sum by (le) (rate(scheduler_preemption_victims_bucket[5m]))
)
```

High preemption means priority-based scheduling is actively trying to make room for high-priority pods. This can be legitimate for critical workloads, but sustained preemption usually indicates resource pressure or poorly designed priority classes.

### 6.11 Internal scheduler metrics

These metrics are useful for deep support and scale troubleshooting.

| Metric | Meaning |
|---|---|
| `scheduler_cache_size` | Number of nodes, pods, and assumed pods in scheduler cache; alpha in Kubernetes metrics reference |
| `scheduler_goroutines` | Number of scheduler goroutines by operation; alpha |
| `scheduler_inflight_events` | Events currently tracked in scheduling queue; alpha |
| `scheduler_pending_async_api_calls` | API calls pending in async queue; alpha |
| `workqueue_depth` | Current workqueue depth for controller-style queues |
| `workqueue_queue_duration_seconds` | Time items spend waiting in workqueue |
| `workqueue_work_duration_seconds` | Time to process workqueue item |
| `workqueue_unfinished_work_seconds` | Work in progress; high/rising value can indicate stuck processing |

## 7. Important Labels and Cardinality Considerations

### Common scheduler labels

| Label | Meaning |
|---|---|
| `queue` | Queue type such as active, backoff, unschedulable, gated |
| `result` | Scheduling result such as scheduled, unschedulable, error |
| `profile` | Scheduler profile name |
| `extension_point` | Scheduler framework stage |
| `plugin` | Scheduling plugin name |
| `status` | Plugin or extension point status |
| `event` | Queue event type |
| `instance` | Scrape target instance |
| `job` | Prometheus job name |
| `namespace` | Namespace of target, usually scheduler namespace for platform component |
| `pod` | Scheduler pod name, depending on scrape labels |

### Cardinality rules for production dashboards

Avoid dashboards that blindly group by too many labels. Good dashboards should aggregate by operational dimensions first:

Good:

```promql
sum by (queue) (scheduler_pending_pods)
```

Good:

```promql
sum by (result) (rate(scheduler_schedule_attempts_total[5m]))
```

Use carefully:

```promql
histogram_quantile(
  0.99,
  sum by (le, extension_point, plugin, status) (
    rate(scheduler_plugin_execution_duration_seconds_bucket[5m])
  )
)
```

This plugin-level query is valuable during incident investigation, but can be heavy on large clusters. Use it in drill-down panels, not always-on overview panels.

## 8. PromQL Cookbook for Scheduler Metrics

### 8.1 Is the scheduler target up?

```promql
up{job=~".*scheduler.*"}
```

If target labels differ in your cluster, discover them:

```promql
count by (job, namespace, service, endpoint) ({__name__=~"scheduler_.*"})
```

### 8.2 Pending pods by scheduler queue

```promql
sum by (queue) (scheduler_pending_pods)
```

### 8.3 Unschedulable pending pods

```promql
sum(scheduler_pending_pods{queue="unschedulable"})
```

### 8.4 Active queue pressure

```promql
sum(scheduler_pending_pods{queue="active"})
```

### 8.5 Backoff queue pressure

```promql
sum(scheduler_pending_pods{queue="backoff"})
```

### 8.6 Scheduling attempts by result




### 8.13 End-to-end scheduling SLI p99


### 8.14 Average attempts per scheduled pod

```promql

/
sum(rate(scheduler_pod_scheduling_attempts_count[5m]))
```

### 8.15 Queue incoming pod rate by queue and event

```promql

```

### 8.16 Preemption attempt rate

```promql
rate(scheduler_preemption_attempts_total[5m])
```

### 8.17 p99 scheduler framework extension point latency

```promql
histogram_quantile(
  0.99,
  sum by (le, extension_point, status) (
    rate(scheduler_framework_extension_point_duration_seconds_bucket[5m])
  )
)
```

### 8.18 p99 plugin execution latency

```promql
histogram_quantile(
  0.99,
  sum by (le, extension_point, plugin, status) (
    rate(scheduler_plugin_execution_duration_seconds_bucket[5m])
  )
)
```

### 8.19 Unschedulable pods by plugin

```promql
sum by (plugin) (scheduler_unschedulable_pods)
```

### 8.20 Workqueue depth related to scheduler

```promql
sum by (name) (workqueue_depth{job=~".*scheduler.*"})
```

### 8.21 Scheduler cache size

```promql
sum by (type) (scheduler_cache_size)
```

### 8.22 Detect sustained unschedulable pressure

```promql
sum(scheduler_pending_pods{queue="unschedulable"}) > 0
```

For alerting, combine with `for: 10m` or `for: 15m`.

### 8.23 Detect scheduler unable to keep up

```promql
sum(scheduler_pending_pods{queue="active"}) > 20
and
histogram_quantile(
  0.99,
  sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m]))
) > 1
```

Tune thresholds to your cluster scale.

## 9. Admin CLI Commands

### 9.1 Check scheduler ClusterOperator

```bash
oc get co kube-scheduler
oc describe co kube-scheduler
```

Look for:

- `Available=True`
- `Progressing=False`
- `Degraded=False`
- version consistency during upgrades

### 9.2 Check scheduler pods

```bash
oc get pods -n openshift-kube-scheduler -o wide
oc get pods -n openshift-kube-scheduler-operator -o wide
```

### 9.3 Check scheduler config

```bash
oc get scheduler cluster -o yaml
```

Get only the active profile:

```bash
oc get scheduler cluster -o jsonpath='{.spec.profile}{"\n"}'
```

### 9.4 Check pending pods cluster-wide

```bash
oc get pods -A --field-selector=status.phase=Pending -o wide
```

### 9.5 Describe a pending pod

```bash
oc describe pod -n <namespace> <pod-name>
```

Look at the `Events` section. Scheduler failure messages often say things like:

```text
0/6 nodes are available: 3 Insufficient cpu, 2 node(s) had untolerated taint, 1 node(s) didn't match Pod's node affinity/selector.
```

### 9.6 Check recent events

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp | tail -50
```

### 9.7 Inspect nodes and scheduling conditions

```bash
oc get nodes
oc get nodes -o wide
oc describe node <node-name>
```

Useful checks:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,UNSCHEDULABLE:.spec.unschedulable,TAINTS:.spec.taints
oc adm top nodes
oc adm top pods -A --sort-by=cpu
oc adm top pods -A --sort-by=memory
```

### 9.8 Check node labels relevant to placement

```bash
oc get nodes --show-labels
oc get node <node-name> -o jsonpath='{.metadata.labels}' | jq
```

### 9.9 Check taints

## 10. Troubleshooting with Scheduler Metrics

### Scenario 1: Many pods are Pending

Symptoms:

```promql
sum(scheduler_pending_pods) > 0
```

Start with queue breakdown:

```promql
sum by (queue) (scheduler_pending_pods)
```

#### If `active` is high

Likely possibilities:

- Large rollout, scale-up, or many jobs created at once.
- Scheduler throughput is temporarily behind incoming pod rate.
- API server latency or binding latency is high.
- Scheduler process is resource constrained.

Check:

```promql
sum by (queue, event) (rate(scheduler_queue_incoming_pods_total[5m]))
```

```promql
histogram_quantile(
  0.99,
  sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m]))
)
```

CLI:

```bash
oc get pods -A --field-selector=status.phase=Pending -o wide
oc describe co kube-scheduler
oc get pods -n openshift-kube-scheduler -o wide
```

#### If `unschedulable` is high

The scheduler is working, but cluster placement constraints are not satisfiable.

Check:

```promql
sum by (result) (rate(scheduler_schedule_attempts_total[5m]))
```

If available:

```promql
sum by (plugin) (scheduler_unschedulable_pods)
```

Then inspect pod events:

```bash
oc describe pod -n <namespace> <pod-name>
```

Typical root causes:

- insufficient CPU/memory,
- node selector mismatch,
- required node affinity mismatch,
- untolerated taints,
- pod anti-affinity too strict,
- topology spread impossible,
- PVC/PV not available or wrong zone,
- node cordoned,
- max pods per node reached,
- extended resources such as GPUs unavailable.

#### If `backoff` is high

Pods are repeatedly failing scheduling and waiting before retry.

Check:

```promql
sum(scheduler_pending_pods{queue="backoff"})
```

Also check retry attempts:

```promql
sum(rate(scheduler_pod_scheduling_attempts_sum[5m]))
/
sum(rate(scheduler_pod_scheduling_attempts_count[5m]))
```

If average attempts are high, inspect the top pending pod classes and their events.

#### If `gated` is high

Pods are blocked by scheduling gates. This is expected only if your platform/app uses pod scheduling readiness.

Check:

```bash
oc get pods -A -o json | jq -r '
  .items[]
  | select(.spec.schedulingGates != null)
  | [.metadata.namespace, .metadata.name, (.spec.schedulingGates | tostring)]
  | @tsv'
```

If gates are not removed, investigate the controller responsible for removing them.

---

### Scenario 2: Scheduler is up, but scheduling latency is high

PromQL:

```promql
histogram_quantile(
  0.99,
  sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m]))
)
```

If p99 is high, break it down:

```promql
histogram_quantile(
  0.99,
  sum by (le, result) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m]))
)
```

Then inspect extension points:

```promql
histogram_quantile(
  0.99,
  sum by (le, extension_point, status) (
    rate(scheduler_framework_extension_point_duration_seconds_bucket[5m])
  )
)
```

If plugin metrics are available:

```promql
histogram_quantile(
  0.99,
  sum by (le, extension_point, plugin, status) (
    rate(scheduler_plugin_execution_duration_seconds_bucket[5m])
  )
)
```

Interpretation:

| High latency area | Common cause |
|---|---|
| `Filter` | Many nodes, expensive constraints, resource fit checks, taints, node affinity |
| `Score` | Expensive scoring plugins, topology spread, inter-pod affinity |
| `PostFilter` | Preemption calculation when no nodes fit |
| `PreBind` | Volume binding or CSI-related pre-bind logic |
| `Bind` | API server latency or binding API errors |
| Plugin `InterPodAffinity` | Complex pod affinity/anti-affinity, broad selectors, many pods/namespaces |
| Plugin `PodTopologySpread` | Strict spread constraints across topology keys |
| Plugin `VolumeBinding` | Storage topology, PV availability, delayed binding |

CLI checks:

```bash
oc get pods -A --field-selector=status.phase=Pending
oc get events -A --sort-by=.lastTimestamp | tail -100
oc adm top nodes
oc get nodes
oc get pvc -A
```

### Scenario 3: `result="error"` increases

This is more serious than unschedulable. `unschedulable` usually means no node fits. `error` means the scheduler hit an internal problem or failed an operation.

PromQL:

```promql
sum(rate(scheduler_schedule_attempts_total{result="error"}[5m]))
```

Check scheduler operator:

```bash
oc describe co kube-scheduler
oc get pods -n openshift-kube-scheduler -o wide
oc get pods -n openshift-kube-scheduler-operator -o wide
```

Check logs:

```bash

oc logs -n openshift-kube-scheduler-operator <operator-pod-name> --tail=200
```

Also check API server health:

```bash
oc get co kube-apiserver openshift-apiserver etcd
oc get --raw='/readyz?verbose'
```

Possible causes:

- API server errors or timeouts.
- Scheduler config problem after unsupported/manual changes.
- Certificate or authentication problem.
- Operator rollout/revision problem.
- Version skew or upgrade problem.
- Rare scheduler bug.

### Scenario 7: Unschedulable due to pod affinity or anti-affinity

```text

```

```promql

```


Common causes:

- Required anti-affinity across too small a topology.
- Broad selectors matching too many pods.
- Namespace selectors too broad.
- Not enough zones/nodes to satisfy required spreading.

Fix options:

- Replace required anti-affinity with preferred anti-affinity when possible.
- Use `topologySpreadConstraints` where more appropriate.
- Make label selectors more specific.
- Add nodes/zones if strict rules are mandatory.

### Scenario 9: Unschedulable due to PVC or volume binding

```text
pod has unbound immediate PersistentVolumeClaims
```

```text

```


- `Immediate`: PVC binding happens immediately, before scheduling.

Fix options:

- Ensure StorageClass supports target zone/node topology.
- Ensure PV node affinity matches available nodes.
- Ensure CSI driver is healthy.
- Ensure PVC access mode is compatible with workload replicas.
- For local PV/topology-aware storage, check node labels and PV node affinity.

- Sustained preemption means high-priority pods frequently cannot fit without evicting lower-priority pods.

- Review PriorityClass design.
- Reserve capacity for critical workloads.
- Use dedicated nodes for system or critical applications.
- Avoid assigning high priority broadly.

## 11. Scheduler Profiles and Metric Interpretation

OpenShift supports scheduler profiles that influence pod distribution across nodes. The commonly referenced profiles are:

| Profile | Behavior | Metric expectation |
|---|---|---|
| `LowNodeUtilization` | Spreads pods more evenly; default behavior | More balanced node usage; scoring may be more active |
| `HighNodeUtilization` | Packs pods onto fewer nodes | Higher node utilization on selected nodes; possible risk if a packed node fails |
| `NoScoring` | Disables score plugins for low-latency scheduling | Lower scheduling latency may be observed; placement quality can be reduced |

Check current profile:

```bash
oc get scheduler cluster -o jsonpath='{.spec.profile}{"\n"}'
```

Change profile only after testing and platform review:

```bash
oc patch scheduler cluster --type=merge -p '{"spec":{"profile":"HighNodeUtilization"}}'
```

### Metrics to compare before and after profile changes

Before changing scheduler profile, capture baseline:

```promql
histogram_quantile(0.99, sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m])))
```

```promql
sum by (result) (rate(scheduler_schedule_attempts_total[5m]))
```

```promql
sum by (queue) (scheduler_pending_pods)
```

```promql
sum by (node) (kube_pod_info)
```

```promql
sum by (node) (kube_pod_container_resource_requests{resource="cpu"})
```

```promql
sum by (node) (kube_pod_container_resource_requests{resource="memory"})
```

After changing profile, compare:

- p95/p99 scheduling latency,
- active/backoff/unschedulable queue depth,
- node resource request distribution,
- pod distribution per node,
- application availability during node failures,
- autoscaler behavior.

### Important production guidance

- `NoScoring` can reduce scheduling cycle time, but it can also reduce quality of placement.
- `HighNodeUtilization` can improve packing and cost efficiency, but increases blast radius if a heavily packed node fails.
- Scheduler profile is a cluster-level behavior. Do not change it casually for one noisy application.
- For one workload, prefer pod-level placement controls such as affinity, tolerations, topology spread, or node selectors.

## 12. Capacity Planning with Scheduler Metrics

Scheduler metrics help identify whether the cluster has enough usable capacity, not just raw CPU/memory.

### 12.1 Raw capacity versus schedulable capacity

Raw capacity says:

```text
The cluster has CPU and memory.
```

Schedulable capacity says:

```text
The cluster has CPU and memory on nodes that match this workload's labels, taints, topology, storage, and policies.
```

A cluster can have 50% free CPU overall and still fail to schedule a pod because:

- the right node pool is full,
- required zone has no capacity,
- nodes with GPUs are full,
- nodes are tainted and pod lacks toleration,
- PVC is bound to a zone with no available compute,
- pod anti-affinity requires more nodes than exist.

### 12.2 Useful planning queries

Pending pods:

```promql
sum by (queue) (scheduler_pending_pods)
```

Unschedulable attempt percentage:

```promql
100 *
sum(rate(scheduler_schedule_attempts_total{result="unschedulable"}[30m]))
/
sum(rate(scheduler_schedule_attempts_total[30m]))
```

Scheduling p99 trend:

```promql
histogram_quantile(
  0.99,
  sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[30m]))
)
```

Node CPU requested:

```promql
sum by (node) (kube_pod_container_resource_requests{resource="cpu"})
```

Node memory requested:

```promql
sum by (node) (kube_pod_container_resource_requests{resource="memory"})
```

Pods per node:

```promql
count by (node) (kube_pod_info)
```

Node allocatable CPU:

```promql
kube_node_status_allocatable{resource="cpu"}
```

Node allocatable memory:

```promql
kube_node_status_allocatable{resource="memory"}
```

### 12.3 Capacity planning checklist

Use scheduler metrics with these checks:

- Are unschedulable attempts increasing over days/weeks?
- Are p95/p99 scheduling latencies trending upward?
- Are pending pods concentrated in a namespace, node pool, zone, or workload type?
- Are new workloads using strict affinity/anti-affinity?
- Are MachineAutoscaler and ClusterAutoscaler reacting quickly enough?
- Are LimitRanges creating default requests that are too high?
- Are quotas causing teams to under-request or over-request resources?
- Are storage topology and compute topology aligned?
- Are dedicated node pools sized for workload peaks?

## 13. Alerting Examples

OpenShift platform metric alerts should be implemented through the supported platform alerting mechanism for your OpenShift version. In modern OpenShift monitoring documentation, platform alerts based on default platform metrics are created with `AlertingRule` in the `openshift-monitoring` namespace. Verify support and feature status in your exact OpenShift version.

### 13.1 Scheduler target down

```yaml
apiVersion: monitoring.openshift.io/v1alpha1
kind: AlertingRule
metadata:
  name: scheduler-health-alerts
  namespace: openshift-monitoring
spec:
  groups:
  - name: scheduler-health.rules
    rules:
    - alert: OpenShiftSchedulerTargetDown
      expr: absent(up{job=~".*scheduler.*"} == 1)
      for: 5m
      labels:
        severity: critical
      annotations:
        message: "OpenShift scheduler metrics target is not being scraped. Check kube-scheduler pods, service monitor/target status, and ClusterOperator kube-scheduler."
```

Adjust the `job` selector after checking your cluster labels:

```promql
count by (job, namespace, service, endpoint) ({__name__=~"scheduler_.*"})
```

### 13.2 Sustained unschedulable pods

```yaml
apiVersion: monitoring.openshift.io/v1alpha1
kind: AlertingRule
metadata:
  name: scheduler-unschedulable-alerts
  namespace: openshift-monitoring
spec:
  groups:
  - name: scheduler-unschedulable.rules
    rules:
    - alert: OpenShiftSchedulerUnschedulablePods
      expr: sum(scheduler_pending_pods{queue="unschedulable"}) > 0
      for: 15m
      labels:
        severity: warning
      annotations:
        message: "Pods have remained unschedulable for more than 15 minutes. Inspect pending pod events, node capacity, labels, taints, topology spread, affinity, and PVC binding."
```

### 13.3 Scheduler internal errors

```yaml
apiVersion: monitoring.openshift.io/v1alpha1
kind: AlertingRule
metadata:
  name: scheduler-error-alerts
  namespace: openshift-monitoring
spec:
  groups:
  - name: scheduler-errors.rules
    rules:
    - alert: OpenShiftSchedulerHighErrorRate
      expr: |
        sum(rate(scheduler_schedule_attempts_total{result="error"}[5m])) > 0
      for: 10m
      labels:
        severity: critical
      annotations:
        message: "Scheduler scheduling attempts are returning internal errors. Check scheduler logs, API server health, and kube-scheduler ClusterOperator status."
```

### 13.4 High scheduler p99 latency

```yaml
apiVersion: monitoring.openshift.io/v1alpha1
kind: AlertingRule
metadata:
  name: scheduler-latency-alerts
  namespace: openshift-monitoring
spec:
  groups:
  - name: scheduler-latency.rules
    rules:
    - alert: OpenShiftSchedulerHighP99Latency
      expr: |
        histogram_quantile(
          0.99,
          sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m]))
        ) > 1
      for: 15m
      labels:
        severity: warning
      annotations:
        message: "Scheduler p99 attempt latency is above 1 second for more than 15 minutes. Check queue depth, extension point latency, plugin latency, API server latency, and workload placement rules."
```

Threshold guidance:

- Small clusters often schedule pods very quickly. A 1-second p99 can be high.
- Very large or busy clusters might need a higher threshold.
- Always baseline your cluster before setting final alert thresholds.

## 15. Production Runbooks

### Runbook A: `OpenShiftSchedulerUnschedulablePods`

**Trigger:**

```promql
sum(scheduler_pending_pods{queue="unschedulable"}) > 0 for 15m
```

**Goal:** Determine why pods cannot be placed.

Steps:

1. List pending pods:

```bash
oc get pods -A --field-selector=status.phase=Pending -o wide
```

2. Pick one representative pod per namespace/workload:

```bash
oc describe pod -n <namespace> <pod-name>
```

3. Categorize event reason:

| Event text | Category |
|---|---|
| `Insufficient cpu` / `Insufficient memory` | Capacity/request sizing |
| `untolerated taint` | Taints/tolerations |
| `didn't match Pod's node affinity/selector` | Labels/affinity |
| `didn't match pod anti-affinity rules` | Affinity/anti-affinity |
| `volume node affinity conflict` | Storage topology |
| `unbound immediate PersistentVolumeClaims` | PVC/PV/StorageClass |
| `node(s) were unschedulable` | Cordoned/drained nodes |

4. Confirm with metrics:

```promql
sum by (result) (rate(scheduler_schedule_attempts_total[5m]))
```

If available:

```promql
sum by (plugin) (scheduler_unschedulable_pods)
```

5. Apply fix:

- Scale node pool.
- Correct requests/limits.
- Add missing toleration.
- Correct node labels/selectors.
- Relax hard affinity/spread rules.
- Fix PVC/storage class.
- Uncordon node if appropriate.

6. Verify:

```bash
oc get pods -A --field-selector=status.phase=Pending
```

```promql
sum by (queue) (scheduler_pending_pods)
```

---

### Runbook B: `OpenShiftSchedulerHighP99Latency`

**Trigger:** p99 scheduler latency above baseline for 15 minutes.

Steps:

1. Confirm latency:

```promql
histogram_quantile(0.99, sum by (le) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m])))
```

2. Check queue depth:

```promql
sum by (queue) (scheduler_pending_pods)
```

3. Check incoming pod rate:

```promql
sum by (queue, event) (rate(scheduler_queue_incoming_pods_total[5m]))
```

4. Break latency down by result:

```promql
histogram_quantile(0.99, sum by (le, result) (rate(scheduler_scheduling_attempt_duration_seconds_bucket[5m])))
```

5. Break latency down by framework extension point:

```promql
histogram_quantile(0.99, sum by (le, extension_point, status) (rate(scheduler_framework_extension_point_duration_seconds_bucket[5m])))
```

6. If plugin metrics exist, find expensive plugin:

```promql
histogram_quantile(0.99, sum by (le, extension_point, plugin, status) (rate(scheduler_plugin_execution_duration_seconds_bucket[5m])))
```

7. Investigate corresponding workload patterns:

```bash
oc get pods -A --field-selector=status.phase=Pending
oc get deploy,statefulset,job,cronjob -A
oc get events -A --sort-by=.lastTimestamp | tail -100
```

8. Fix based on root cause:

- Large rollout: stagger rollout, tune deployment surge, review autoscaler.
- Affinity cost: narrow selectors or relax required rules.
- Topology spread: check topology labels and constraints.
- Volume binding: inspect CSI/storage class/PV topology.
- API bind latency: inspect kube-apiserver and etcd metrics.

### Runbook C: `OpenShiftSchedulerHighErrorRate`

**Trigger:** `result="error"` scheduling attempts continue.

Steps:

## 16. Common Mistakes

### Mistake 1: Treating all pending pods as scheduler failure

Not every `Pending` pod means scheduler is broken. Many pending pods are caused by valid placement constraints. Always check pod events.

### Mistake 2: Looking only at CPU/memory usage

Scheduling uses **requests**, not current usage, for CPU/memory fit. A node might look idle in `oc adm top nodes`, but be full from a request-allocation perspective.

Check requested resources, not only usage:

```promql
sum by (node) (kube_pod_container_resource_requests{resource="cpu"})
```

### Mistake 3: Ignoring taints and dedicated node pools

A node can have free resources but still be invalid because of taints. Dedicated pools need matching tolerations and selectors/affinity.

### Mistake 4: Using hard anti-affinity everywhere

Required anti-affinity can make workloads impossible to place after scaling. Prefer soft rules unless strict separation is required.

### Mistake 5: Creating alerts on alpha metrics without checking stability

Plugin-level metrics are powerful but can be alpha. Use stable metrics for critical alerts when possible, and use alpha metrics for dashboards and incident drill-down after verifying your cluster version.

### Mistake 6: Directly modifying scheduler-managed resources

Do not edit static pod manifests or generated scheduler config directly. Use supported OpenShift objects such as `Scheduler/cluster`.

### Mistake 7: Ignoring storage topology

PVC and PV topology can make a pod unschedulable even when compute resources are available.

### Mistake 8: Assuming `HighNodeUtilization` is always better

Packing can improve infrastructure efficiency, but it can increase blast radius during node failure and create hot spots.

## 17. Interview and Real-World Scenarios

### Scenario A

**Question:** Pods are pending. `scheduler_pending_pods{queue="unschedulable"}` is high. What do you do?

**Answer:**

1. Confirm attempts by result:

```promql
sum by (result) (rate(scheduler_schedule_attempts_total[5m]))
```

2. List pending pods:

```bash
oc get pods -A --field-selector=status.phase=Pending
```

3. Describe representative pods:

```bash
oc describe pod -n <ns> <pod>
```

4. Match event reason to root cause: resource fit, taints, affinity, PVC, topology spread, cordoned nodes.

5. Fix the specific constraint. Do not restart scheduler blindly.

### Scenario B

**Question:** Scheduler p99 latency is high, but pods eventually schedule. What is likely?

**Answer:**

The scheduler is functioning but spending more time per attempt. Check extension point and plugin latency. Common causes are expensive affinity/anti-affinity, topology spread, high cluster scale, volume binding, or API server latency during bind.

### Scenario C

**Question:** What is the difference between `scheduler_scheduling_attempt_duration_seconds` and `scheduler_pod_scheduling_sli_duration_seconds`?

**Answer:**

`scheduler_scheduling_attempt_duration_seconds` measures one scheduling attempt, including scheduling algorithm and binding. `scheduler_pod_scheduling_sli_duration_seconds` measures end-to-end pod scheduling latency from queue entry and can include multiple attempts. The SLI metric better represents pod scheduling user experience.

### Scenario D

**Question:** `scheduler_schedule_attempts_total{result="error"}` is increasing. Is this a capacity problem?

**Answer:**

Not usually. Capacity problems normally show `result="unschedulable"`. `result="error"` indicates internal scheduler/API/config/operation errors. Check scheduler logs, `ClusterOperator/kube-scheduler`, API server health, and recent upgrades/config changes.

### Scenario E

**Question:** You changed scheduler profile to `NoScoring`; what metrics do you compare?

**Answer:**

Compare p95/p99 scheduler latency, attempts by result, pending queue depth, pod distribution across nodes, resource request distribution, and application behavior during node failures. `NoScoring` can lower latency but may reduce placement quality.

## Final Notes for a 10-Year OpenShift Administrator

A junior admin often checks only this:

```bash
oc get pods -A | grep Pending
```

A senior OpenShift admin correlates:

- scheduler queue pressure,
- attempt result distribution,
- p95/p99 scheduler latency,
- plugin/extension point latency,
- pod events,
- node labels and taints,
- resource requests versus allocatable,
- PVC and storage topology,
- scheduler profile,
- API server and etcd health,
- rollout/autoscaler activity.

The scheduler is rarely the only problem. Scheduler metrics show where the placement system is blocked. The real fix is often in workload specification, node pool design, storage topology, resource requests, or cluster capacity.
