# Prometheus in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift Administration / senior Linux, Kubernetes, and OpenShift administrators  
**Depth level:** 10+ years production operations mindset  
**Focus:** Prometheus inside the OpenShift monitoring stack, not a generic standalone Prometheus installation  
**OpenShift scope:** OpenShift 4.x concepts, with notes aligned to current Red Hat Monitoring Stack documentation

---

## 1. Executive Summary

Prometheus is the metrics collection, time-series storage, query, and alert rule evaluation engine used by the OpenShift monitoring stack. In OpenShift, you normally do **not** install and manually manage Prometheus like a standalone binary. Instead, OpenShift deploys and manages Prometheus through the **Cluster Monitoring Operator** and **Prometheus Operator**.

For an experienced OpenShift administrator, Prometheus knowledge is not only about writing PromQL. You must understand:

- Which Prometheus instance handles platform metrics.
- Which Prometheus instance handles user workload metrics.
- How `ServiceMonitor`, `PodMonitor`, and `PrometheusRule` objects are reconciled.
- How metrics move from application endpoint to Prometheus to Thanos Querier to the web console.
- How Alertmanager receives alerts from Prometheus or Thanos Ruler.
- How storage, retention, cardinality, and scrape limits affect cluster stability.
- Which changes are supported and which changes will be reverted by the monitoring operators.

In production OpenShift, Prometheus is a platform component. Treat it like etcd, ingress, or authentication: configure it only through supported OpenShift mechanisms.

## 2. What Prometheus Is

Prometheus is an open source monitoring and alerting toolkit designed for cloud-native systems. It collects metrics from configured targets over HTTP, stores the metrics as time series, allows powerful querying through **PromQL**, and evaluates alerting and recording rules.

Prometheus is built around a **pull model**:

```text
Prometheus ---> HTTP GET /metrics ---> Target application/exporter
```

A target exposes a metrics endpoint, commonly `/metrics`. Prometheus periodically scrapes that endpoint, parses metrics, stores samples, and evaluates rules.

A metric sample is identified by:

```text
metric_name{label_key="label_value", another_label="value"} value timestamp
```

Example:

```text
http_requests_total{namespace="payments",pod="api-7d8f9",method="GET",code="200"} 18391
```

This model is powerful, but it can become dangerous when labels have too many unique values. For example, labels such as `user_id`, `request_id`, `session_id`, or `customer_id` can create massive time-series cardinality.

## 3. Why Prometheus Matters in OpenShift

OpenShift uses Prometheus to understand the health of:

- Kubernetes API server
- etcd
- kubelet
- nodes
- operators
- machine config pools
- ingress/router
- image registry
- network components
- storage components
- core platform services
- optionally, user workloads

Prometheus is also used for:

- Alerting
- Dashboards
- SLO and availability checks
- Capacity planning
- Troubleshooting performance issues
- Root cause analysis
- Detecting degraded cluster operators
- Understanding pod, node, and namespace resource behavior

For an advanced administrator, Prometheus becomes the main source of truth for answering questions such as:

- Why did this node become NotReady?
- Why is the API server slow?
- Is etcd latency increasing?
- Which namespace is consuming CPU?
- Which workload is generating too many metrics?
- Why is Prometheus using too much disk?
- Why did an alert fire?
- Is application traffic failing or only health checks failing?

## 4. OpenShift Monitoring Stack Architecture

OpenShift installs a preconfigured monitoring stack for core platform monitoring. The default platform monitoring components are installed in the `openshift-monitoring` namespace.

High-level architecture:

```text
                         OpenShift Web Console
                              Observe UI
                                  |
                                  v
                            Thanos Querier
                                  |
            +---------------------+----------------------+
            |                                            |
            v                                            v
   Platform Prometheus                         User Workload Prometheus
   namespace: openshift-monitoring             namespace: openshift-user-workload-monitoring
            |                                            |
            v                                            v
   Platform metrics targets                    User app ServiceMonitor/PodMonitor targets
            |                                            |
            v                                            v
       Alertmanager                              Thanos Ruler / Alertmanager
```

Core components:

| Component | Namespace | Purpose |
|---|---|---|
| Cluster Monitoring Operator | `openshift-monitoring` | Deploys and manages monitoring stack components |
| Prometheus Operator | `openshift-monitoring` and user workload namespace | Creates and manages Prometheus, Alertmanager, rules, and scrape configuration |
| Prometheus | `openshift-monitoring` | Stores and evaluates platform metrics |
| Prometheus for user workloads | `openshift-user-workload-monitoring` | Stores and scrapes user-defined project metrics |
| Thanos Querier | `openshift-monitoring` | Provides a unified query layer across platform and user workload metrics |
| Thanos Ruler | `openshift-user-workload-monitoring` | Evaluates user workload rules and alerts |
| Alertmanager | `openshift-monitoring` and optionally user workload namespace | Receives alerts and routes notifications |
| node-exporter | usually daemonset-managed | Exposes node OS-level metrics |
| kube-state-metrics | `openshift-monitoring` | Converts Kubernetes object state into metrics |
| openshift-state-metrics | `openshift-monitoring` | Exposes OpenShift-specific object metrics |
| Metrics Server | platform component | Provides `metrics.k8s.io` metrics used by Kubernetes APIs such as HPA |

Important distinction:

```text
Prometheus = metrics database and rule engine
Alertmanager = alert routing, grouping, inhibition, silence, notifications
Thanos Querier = query aggregation layer
Thanos Ruler = rule evaluation for user workload monitoring
```

## 5. Core Platform Monitoring vs User Workload Monitoring

OpenShift separates monitoring into two major areas.

### 5.1 Core Platform Monitoring

Core platform monitoring is installed by default in:

```text
openshift-monitoring
```

It monitors Red Hat provided and platform components. This is where you find platform Prometheus pods, Alertmanager, Thanos Querier, node-exporter, kube-state-metrics, openshift-state-metrics, and related components.

Typical objects:

```bash
oc get pods -n openshift-monitoring
oc get prometheus -n openshift-monitoring
oc get alertmanager -n openshift-monitoring
oc get servicemonitor -n openshift-monitoring
oc get prometheusrule -n openshift-monitoring
```

Typical Prometheus pods:

```text
prometheus-k8s-0
prometheus-k8s-1
```

You should not manually edit resources owned by the monitoring stack. The operators reconcile them back to the supported state.

### 5.2 User Workload Monitoring

User workload monitoring is optional and is enabled by a cluster administrator. It creates additional components in:

```text
openshift-user-workload-monitoring
```

It allows application teams and project administrators to define monitoring for their own namespaces using objects such as:

- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`
- `AlertmanagerConfig`

Typical commands:

```bash
oc get pods -n openshift-user-workload-monitoring
oc get prometheus -n openshift-user-workload-monitoring
oc get thanosruler -n openshift-user-workload-monitoring
oc get alertmanager -n openshift-user-workload-monitoring
```

Typical user workload Prometheus pods:

```text
prometheus-user-workload-0
prometheus-user-workload-1
```

## 6. Operators Involved

### 6.1 Cluster Monitoring Operator

The **Cluster Monitoring Operator**, commonly called CMO, is the main OpenShift operator responsible for the monitoring stack. It is managed by the Cluster Version Operator.

It manages:

- Prometheus
- Alertmanager
- Thanos Querier
- Telemeter Client
- Metrics targets
- Monitoring configuration
- Certificates and internal TLS rotation
- Monitoring component lifecycle during upgrades

Check status:

```bash
oc get co monitoring
oc describe co monitoring
oc get deployment cluster-monitoring-operator -n openshift-monitoring
oc logs deployment/cluster-monitoring-operator -n openshift-monitoring
```

A healthy cluster should normally show:

```text
AVAILABLE=True
PROGRESSING=False
DEGRADED=False
```

### 6.2 Prometheus Operator

The Prometheus Operator converts high-level Kubernetes custom resources into Prometheus configuration.

It watches resources such as:

- `Prometheus`
- `Alertmanager`
- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`
- `AlertmanagerConfig`

The Prometheus Operator automatically generates scrape configurations based on Kubernetes labels and selectors. That means OpenShift administrators generally do not edit `prometheus.yml` manually.

Check CRDs:

```bash
oc get crd | egrep 'servicemonitor|podmonitor|prometheusrule|alertmanagerconfig|prometheus'
```

Check operator pods:

```bash
oc get pods -n openshift-monitoring | grep prometheus-operator
oc logs -n openshift-monitoring deployment/prometheus-operator
```

For user workload monitoring:

```bash
oc get pods -n openshift-user-workload-monitoring
oc logs -n openshift-user-workload-monitoring deployment/prometheus-operator
```

## 7. Supported Configuration Model

The most important senior-admin rule:

> Do not directly edit the generated Prometheus, Alertmanager, StatefulSet, Secret, ServiceMonitor, or PrometheusRule objects in OpenShift monitoring namespaces unless Red Hat documentation explicitly tells you to do it.

Supported configuration is performed through ConfigMaps:

### Core platform monitoring ConfigMap

```text
Namespace: openshift-monitoring
Name:      cluster-monitoring-config
Key:       data.config.yaml
```

Edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

### User workload monitoring ConfigMap

```text
Namespace: openshift-user-workload-monitoring
Name:      user-workload-monitoring-config
Key:       data.config.yaml
```

Edit:

```bash
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Create if missing:

```bash
oc create configmap cluster-monitoring-config \
  -n openshift-monitoring \
  --from-literal=config.yaml=""
```

```bash
oc create configmap user-workload-monitoring-config \
  -n openshift-user-workload-monitoring \
  --from-literal=config.yaml=""
```

If YAML is invalid or unsupported fields are used, CMO can stop reconciling and mark the monitoring operator degraded.

## 8. Enabling User Workload Monitoring

To enable monitoring for user-defined projects:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Apply:

```bash
oc apply -f cluster-monitoring-config.yaml
```

Verify:

```bash
oc get pods -n openshift-user-workload-monitoring
oc get prometheus -n openshift-user-workload-monitoring
oc get thanosruler -n openshift-user-workload-monitoring
```

Expected components include Prometheus Operator, Prometheus user workload pods, Thanos Ruler, and related services.

Grant project users permission to create monitoring objects:

```bash
oc adm policy add-cluster-role-to-user monitoring-edit <user> -n <namespace>
oc adm policy add-cluster-role-to-user monitoring-rules-edit <user> -n <namespace>
oc adm policy add-cluster-role-to-user monitoring-rules-view <user> -n <namespace>
```

For alert routing:

```bash
oc -n <namespace> adm policy add-role-to-user alert-routing-edit <user>
```

Role names can vary by version and configuration. Always verify available roles:

```bash
oc get clusterrole | grep -i monitoring
oc get clusterrole | grep -i alert
```

## 9. Prometheus Data Model

Prometheus stores data as time series.

A time series is uniquely identified by:

```text
metric name + complete label set
```

Example:

```text
container_cpu_usage_seconds_total{
  namespace="backend",
  pod="api-7d89cc5c8f-lp2bq",
  container="api",
  cpu="0"
}
```

If any label value changes, a new time series is created.

### 9.1 Metric Types

Prometheus supports common metric patterns:

| Type | Meaning | Example |
|---|---|---|
| Counter | Always increases except reset | `http_requests_total` |
| Gauge | Can go up or down | `memory_usage_bytes` |
| Histogram | Bucketed distribution | `http_request_duration_seconds_bucket` |
| Summary | Client-side quantiles | `request_latency_seconds` |

### 9.2 Labels

Labels are dimensions.

Good labels:

```text
namespace
pod
container
method
code
route
service
```

Dangerous labels:

```text
user_id
request_id
session_id
transaction_id
email
ip_address
uuid
```

Dangerous labels create cardinality explosion.

### 9.3 Cardinality Formula

If a metric has labels with the following possible values:

```text
namespace = 20
pod       = 500
method    = 5
code      = 8
route     = 100
```

Maximum possible series:

```text
20 * 500 * 5 * 8 * 100 = 40,000,000 series
```

This is why senior OpenShift admins care deeply about metric label design.

## 10. How Scraping Works in OpenShift

OpenShift does not expect you to manually write Prometheus scrape configuration. Instead, you create monitor resources.

### 10.1 ServiceMonitor

A `ServiceMonitor` tells Prometheus how to scrape a Kubernetes `Service`.

Flow:

```text
Application Pod exposes /metrics
        |
        v
Kubernetes Service selects Pod
        |
        v
ServiceMonitor selects Service
        |
        v
Prometheus Operator generates scrape config
        |
        v
Prometheus scrapes endpoint
```

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: api-service-monitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: payments-api
  endpoints:
  - port: metrics
    path: /metrics
    interval: 30s
    scheme: http
```

Service must have matching label and named port:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payments-api
  namespace: payments
  labels:
    app: payments-api
spec:
  selector:
    app: payments-api
  ports:
  - name: metrics
    port: 8080
    targetPort: 8080
```

Important: In user-defined namespaces, a `ServiceMonitor` can discover services only in the same namespace. Do not depend on `namespaceSelector` for cross-namespace service discovery in normal user workload monitoring.

### 10.2 PodMonitor

A `PodMonitor` allows Prometheus to scrape pods directly, without requiring a Service.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: api-pod-monitor
  namespace: payments
spec:
  selector:
    matchLabels:
      app: payments-api
  podMetricsEndpoints:
  - port: metrics
    path: /metrics
    interval: 30s
```

Use `PodMonitor` when:

- You do not need a stable Service abstraction.
- Each pod exposes metrics directly.
- The workload is not naturally fronted by a Service.

Use `ServiceMonitor` when:

- You already expose a Service.
- You want Service-level discovery.
- You want cleaner app-team ownership.

## 12. PromQL for OpenShift Administrators

PromQL is the query language used by Prometheus.

### 12.1 Basic Query

```promql
up
```

Meaning: target scrape health. `1` means target is up, `0` means down.

Filter by namespace:

```promql
up{namespace="openshift-monitoring"}
```

### 12.2 CPU Usage by Namespace

```promql
sum by (namespace) (
  rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])
)
```

### 12.3 Memory Usage by Namespace

```promql
sum by (namespace) (
  container_memory_working_set_bytes{container!="",pod!=""}
)
```

### 12.4 Pod Restart Count

```promql
sum by (namespace, pod) (
  kube_pod_container_status_restarts_total
)
```

### 12.5 Recent Pod Restart Increase

```promql
sum by (namespace, pod) (
  increase(kube_pod_container_status_restarts_total[15m])
)
```

### 12.6 Node CPU Usage

```promql
100 - (
  avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100
)
```

### 12.7 Node Memory Usage Percentage

```promql
100 * (
  1 - (
    node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
  )
)
```

### 12.8 Node Filesystem Usage

```promql
100 * (
  1 - node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}
      / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}
)
```

### 12.9 API Server Request Rate

```promql
sum by (verb, resource) (
  rate(apiserver_request_total[5m])
)
```

### 12.10 API Server Error Rate

```promql
sum by (code) (
  rate(apiserver_request_total{code=~"5.."}[5m])
)
```

### 12.11 etcd fsync Latency

```promql
histogram_quantile(
  0.99,
  rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])
)
```

### 12.12 Ingress Router 5xx Rate

```promql
sum by (namespace, route) (
  rate(haproxy_backend_http_responses_total{code="5xx"}[5m])
)
```

### 12.13 Scrape Samples by Job

```promql
topk(10,
  max by (namespace, job) (
    scrape_samples_post_metric_relabeling
  )
)
```

### 12.14 Series Churn

```promql
topk(10,
  sum by (namespace, job) (
    sum_over_time(scrape_series_added[1h])
  )
)
```

Use this query when Prometheus disk, memory, or CPU usage is increasing unexpectedly.

## 13. Recording Rules and Alerting Rules

Prometheus supports two important rule types.

### 13.1 Recording Rules

Recording rules precompute expensive queries and store the result as a new metric.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-recording-rules
  namespace: payments
spec:
  groups:
  - name: api.recording.rules
    interval: 30s
    rules:
    - record: namespace:api_cpu_usage:rate5m
      expr: |
        sum by (namespace) (
          rate(container_cpu_usage_seconds_total{namespace="payments",container!=""}[5m])
        )
```

Use recording rules for:

- Dashboards that repeatedly run expensive queries.
- SLO calculations.
- Aggregated cluster or namespace metrics.
- Queries involving large numbers of pods or containers.

### 13.2 Alerting Rules

Alerting rules define conditions that generate alerts.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-alert-rules
  namespace: payments
spec:
  groups:
  - name: api.alert.rules
    rules:
    - alert: PaymentsApiHighErrorRate
      expr: |
        sum(rate(http_requests_total{namespace="payments",code=~"5.."}[5m]))
        /
        sum(rate(http_requests_total{namespace="payments"}[5m]))
        > 0.05
      for: 10m
      labels:
        severity: warning
        team: payments
      annotations:
        summary: "Payments API has high 5xx error rate"
        description: "5xx error rate is above 5% for 10 minutes."
```

Key fields:

| Field | Meaning |
|---|---|
| `alert` | Alert name |
| `expr` | PromQL condition |
| `for` | Required duration before firing |
| `labels` | Routing and classification labels |
| `annotations` | Human-readable context |

### 13.3 Good Alert Design

A good alert should be:

- Actionable
- Owned by a team
- Not too noisy
- Connected to user impact or platform risk
- Suppressed during maintenance if needed
- Routed to the right receiver

Bad alert:

```text
CPU > 80% for 1 minute
```

Better alert:

```text
API p99 latency above SLO and error rate above threshold for 10 minutes
```

## 14. Alertmanager Relationship

Prometheus evaluates alert rules. Alertmanager handles what happens after an alert fires.

Alertmanager provides:

- Grouping
- Routing
- Silencing
- Inhibition
- Deduplication
- Notification delivery

Common receivers:

- Email
- Slack-compatible webhook
- PagerDuty
- Webhook
- Opsgenie
- ServiceNow integration via webhook

OpenShift web console path:

```text
Observe -> Alerting
```

Alert lifecycle:

```text
Inactive -> Pending -> Firing -> Resolved
```

The `for` field controls pending duration. Example:

```yaml
for: 10m
```

This means the expression must remain true continuously for 10 minutes before the alert becomes firing.

## 15. Storage and Retention

Prometheus uses a local time-series database called TSDB.

Data path inside Prometheus containers is commonly under:

```text
/prometheus
```

Important TSDB concepts:

- Head block stores recent samples in memory.
- Write-ahead log, or WAL, protects recent samples from crash loss.
- Compacted blocks store historical data.
- Retention can be time-based and size-based.
- High cardinality increases memory, CPU, WAL, and disk usage.

### 15.1 Default Retention

Common OpenShift defaults:

| Monitoring area | Default retention |
|---|---|
| Core platform monitoring | 15 days |
| User workload monitoring | 24 hours |

Always verify in your version and cluster configuration.

### 15.2 User Workload Retention Configuration

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      retention: 7d
      retentionSize: 50GB
```

Apply:

```bash
oc apply -f user-workload-monitoring-config.yaml
```

### 15.3 Persistent Storage for User Workload Prometheus

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      volumeClaimTemplate:
        spec:
          storageClassName: fast-ssd
          resources:
            requests:
              storage: 100Gi
```

### 15.4 Persistent Storage Warnings

Production guidance:

- Use persistent storage for production monitoring.
- Use filesystem volume mode, not raw block.
- Use POSIX-compliant storage.
- Ensure enough IOPS for heavy scrape loads.
- Avoid slow or unreliable NFS implementations unless explicitly validated.
- Monitor PVC usage.
- Changing storage configuration can recreate StatefulSets and cause temporary monitoring outage.

Check PVCs:

```bash
oc get pvc -n openshift-monitoring
oc get pvc -n openshift-user-workload-monitoring
```

Check Prometheus disk usage from metrics:

```promql
prometheus_tsdb_storage_blocks_bytes
prometheus_tsdb_head_series
prometheus_tsdb_wal_segment_current
```

## 16. Performance, Scale, and Cardinality Control

Prometheus performance depends heavily on:

- Number of targets
- Scrape interval
- Number of samples per scrape
- Number of active series
- Query complexity
- Recording rule count
- Alerting rule count
- WAL write rate
- Disk I/O performance
- Label cardinality

### 16.1 Dangerous Symptoms

Prometheus is under pressure when you see:

- Prometheus pod restarting
- High memory usage
- High CPU usage
- PVC filling quickly
- Query timeouts in console
- `KubePersistentVolumeFillingUp` alerts
- Targets frequently showing `Down`
- Scrape duration close to scrape timeout
- High `scrape_samples_post_metric_relabeling`
- Fast increase in `prometheus_tsdb_head_series`

### 16.2 User Workload Limits

Example configuration:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      enforcedSampleLimit: 50000
      enforcedLabelLimit: 500
      enforcedLabelNameLengthLimit: 50
      enforcedLabelValueLengthLimit: 600
      scrapeInterval: 30s
      evaluationInterval: 30s
```

Meaning:

| Setting | Purpose |
|---|---|
| `enforcedSampleLimit` | Maximum samples accepted per target scrape |
| `enforcedLabelLimit` | Maximum labels per sample |
| `enforcedLabelNameLengthLimit` | Maximum label name length |
| `enforcedLabelValueLengthLimit` | Maximum label value length |
| `scrapeInterval` | Default scrape interval |
| `evaluationInterval` | Rule evaluation interval |

Warning: If a target exceeds enforced limits, Prometheus stops ingesting additional samples for that scrape.

### 16.3 Find Heavy Targets

```promql
topk(20,
  max by (namespace, job, service) (
    scrape_samples_post_metric_relabeling
  )
)
```

### 16.4 Find Series Churn

```promql
topk(20,
  sum by (namespace, job) (
    sum_over_time(scrape_series_added[1h])
  )
)
```

### 16.5 Find Active Series

```promql
prometheus_tsdb_head_series
```

### 16.6 Find Query Pressure

```promql
rate(prometheus_engine_query_duration_seconds_count[5m])
```

## 17. Security and RBAC

OpenShift monitoring is multi-tenant aware. Access to metrics is controlled by OpenShift RBAC.

### 17.1 Administrator Access

Cluster admins can view platform and user workload metrics.

```bash
oc adm policy add-cluster-role-to-user cluster-admin <user>
```

### 17.2 Developer Access

Project users can view metrics for projects they have access to.

## 18. Remote Write and Long-Term Storage

Prometheus local storage is not intended to be your only long-term metrics warehouse for months or years of data. For longer retention, use remote write to an external compatible endpoint such as Thanos Receive, Cortex, Mimir, or another supported endpoint.

Remote write does not change local retention. It sends ingested samples to an external system.

Example user workload remote write:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      remoteWrite:
      - url: "https://remote-write.example.com/api/v1/write"
        writeRelabelConfigs:
        - sourceLabels: [__name__, namespace]
          regex: '(http_requests_total|http_request_duration_seconds_bucket);payments'
          action: keep
```

Add a cluster ID label for multi-cluster observability:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      remoteWrite:
      - url: "https://remote-write.example.com/api/v1/write"
        writeRelabelConfigs:
        - sourceLabels:
          - __tmp_openshift_cluster_id__
          targetLabel: cluster_id
          action: replace
```

Best practices:

- Use HTTPS.
- Use authentication.
- Use write relabeling to avoid sending unnecessary metrics.
- Add cluster labels for multi-cluster correlation.
- Monitor remote write queue metrics.
- Do not assume remote write failure affects local Prometheus ingestion unless queues and resources are exhausted.

Remote write health metrics:

```promql
prometheus_remote_storage_samples_pending
prometheus_remote_storage_samples_failed_total
prometheus_remote_storage_samples_retried_total
prometheus_remote_storage_shards
prometheus_remote_storage_highest_timestamp_in_seconds
```

## 20. Troubleshooting Prometheus in OpenShift

### 20.1 First-Level Health Check

```bash
oc get co monitoring
oc describe co monitoring
oc get pods -n openshift-monitoring
oc get pods -n openshift-user-workload-monitoring
```

Look for:

```text
CrashLoopBackOff
Pending
ImagePullBackOff
OOMKilled
Evicted
ContainerCreating
```

### 20.2 Check CMO Logs

```bash
oc logs -n openshift-monitoring deployment/cluster-monitoring-operator
```

Common problems:

- Invalid `cluster-monitoring-config` YAML
- Unsupported fields
- Missing storage class
- Insufficient resources
- PVC binding failure
- Node selector mismatch
- Taint without toleration

### 20.3 Check Prometheus Operator Logs

```bash
oc logs -n openshift-monitoring deployment/prometheus-operator
oc logs -n openshift-user-workload-monitoring deployment/prometheus-operator
```

Common problems:

- Invalid `ServiceMonitor`
- Invalid `PrometheusRule`
- Rejected authentication field
- Missing secret referenced by monitor
- Invalid port name

### 20.4 Target Not Appearing

Checklist:

```bash
oc get servicemonitor -n <namespace>
oc describe servicemonitor <name> -n <namespace>
oc get svc -n <namespace> --show-labels
oc get endpoints -n <namespace> <service-name>
oc get pods -n <namespace> --show-labels
```

Most common causes:

- User workload monitoring not enabled.
- `ServiceMonitor` label selector does not match Service label.
- Service selector does not match Pod label.
- Service port name does not match `ServiceMonitor.spec.endpoints[].port`.
- App does not expose `/metrics`.
- App requires auth but `ServiceMonitor` has no auth config.
- `ServiceMonitor` created in wrong namespace.
- User does not have required monitoring role.

### 20.5 Target Appears But Is Down

Check target manually:

```bash
oc -n <namespace> run debug-curl --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -v http://<service>.<namespace>.svc:<port>/metrics
```

Check endpoint:

```bash
oc get endpoints <service> -n <namespace>
oc describe svc <service> -n <namespace>
```

Common causes:

- Wrong port
- Wrong path
- TLS mismatch
- Authentication missing
- NetworkPolicy blocking traffic
- Application not listening
- Endpoint has no ready addresses

### 20.6 Prometheus Disk Filling

Check PVC:

```bash
oc get pvc -n openshift-monitoring
oc get pvc -n openshift-user-workload-monitoring
```

Find heavy targets:

```promql
topk(10,
  max by(namespace, job) (
    scrape_samples_post_metric_relabeling
  )
)
```

Find churn:

```promql
topk(10,
  sum by(namespace, job) (
    sum_over_time(scrape_series_added[1h])
  )
)
```

Fix options:

- Remove high-cardinality labels from applications.
- Increase retention size carefully.
- Increase PVC size.
- Increase Prometheus memory and CPU resources.
- Increase scrape interval for noisy targets.
- Use enforced sample and label limits.
- Use remote write for long-term retention.
- Add recording rules to reduce expensive dashboard queries.

### 20.7 Prometheus OOMKilled

Check:

```bash
oc describe pod prometheus-k8s-0 -n openshift-monitoring
oc describe pod prometheus-user-workload-0 -n openshift-user-workload-monitoring
```

Look for:

```text
Last State: Terminated
Reason: OOMKilled
Exit Code: 137
```

PromQL checks:

```promql
prometheus_tsdb_head_series
process_resident_memory_bytes{job=~"prometheus.*"}
rate(prometheus_tsdb_head_samples_appended_total[5m])
```

Fix:

- Reduce cardinality.
- Increase memory request and limit through supported ConfigMap.
- Increase scrape interval.
- Limit samples per scrape.
- Investigate new application metrics.

### 20.8 Invalid PrometheusRule

Check:

```bash
oc describe prometheusrule <name> -n <namespace>
oc logs -n openshift-user-workload-monitoring deployment/prometheus-operator
```

Common causes:

- Bad PromQL syntax.
- Missing quotes in YAML.
- Duplicate rule names.
- Invalid label names.
- Query returns no namespace label where namespace enforcement is expected.

Validate PromQL in web console before committing rules.

### 20.9 Console Metrics Empty

Check:

```bash
oc get route -n openshift-monitoring thanos-querier
oc get pods -n openshift-monitoring | grep thanos
oc logs -n openshift-monitoring deployment/thanos-querier
oc get oauthclient | grep thanos
```

Also verify user permissions:

```bash
oc auth can-i get pods -n <namespace>
oc auth can-i get prometheusrules.monitoring.coreos.com -n <namespace>
```

## 22. Scheduling Monitoring Components

You can move user workload monitoring components to specific nodes by using node selectors and tolerations.

### 22.1 Node Selector Example

Taint node:


```yaml
apiVersion: v1

  namespace: openshift-user-workload-monitoring

        operator: Equal
        value: reserved
        effect: NoSchedule
```

```bash
oc describe pod -n openshift-user-workload-monitoring <pod-name>
```

Look for scheduler events.

## 23. NetworkPolicy Considerations

If a user namespace uses restrictive NetworkPolicy, Prometheus scraping can fail.

You must allow ingress to the metrics port from the monitoring namespace/pods.

Example concept:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-monitoring-scrape
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: payments-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-user-workload-monitoring
    ports:
    - protocol: TCP
      port: 8080
```

Exact labels can differ. Verify namespace labels:

```bash
oc get ns openshift-user-workload-monitoring --show-labels
```

Test from debug pod if necessary.

## 25. Common Production Scenarios

### Scenario 1: Application Team Says Metrics Are Missing

Steps:

```bash
oc get servicemonitor -n app-ns
oc get svc -n app-ns --show-labels
oc get endpoints -n app-ns
oc get pods -n app-ns --show-labels
```

Check:

- Is user workload monitoring enabled?
- Does ServiceMonitor selector match Service labels?
- Does Service selector match Pod labels?
- Does Service port have a name?
- Does ServiceMonitor endpoint use the same port name?
- Is `/metrics` reachable?
- Is NetworkPolicy blocking scraping?

### Scenario 2: Prometheus PVC Filling Fast

Immediate actions:

```promql
topk(10, max by(namespace, job) (scrape_samples_post_metric_relabeling))
topk(10, sum by(namespace, job) (sum_over_time(scrape_series_added[1h])))
prometheus_tsdb_head_series
```

Admin decision:

- If caused by bad metric labels, ask app team to fix instrumentation.
- If legitimate growth, increase PVC and resources.
- If long-term retention needed, configure remote write.

### Scenario 3: Alert Is Firing But Team Says No Issue

Check:

```promql
ALERTS{alertname="<alert-name>"}
```

Review:

- Expression
- `for` duration
- Labels
- Severity
- Runbook URL
- Recent deployment changes
- Whether alert uses symptoms or causes

Bad alerts are often caused by generic thresholds without workload context.

### Scenario 4: Console Metrics Query Is Slow

Check:

- Query range too large
- Query scans too many series
- Missing recording rules
- High cardinality labels
- Dashboard refresh interval too aggressive
- Prometheus CPU/memory pressure

Optimize with recording rules:

```yaml
- record: namespace:container_cpu_usage_seconds_total:rate5m
  expr: sum by (namespace) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))
```

## 26. Best Practices for Senior OpenShift Administrators

### Platform Configuration

- Use only supported ConfigMap fields.
- Never manually edit generated monitoring stack resources.
- Keep monitoring operator healthy before troubleshooting user workloads.
- Track monitoring changes through GitOps.
- Validate YAML before applying.

### Application Metrics

- Expose `/metrics` on a named port.
- Use bounded label values.
- Avoid user IDs, UUIDs, request IDs, and timestamps as labels.
- Keep scrape payloads small.
- Add application-level SLO metrics.
- Provide runbook annotations in alerts.

### PromQL

- Use `rate()` for counters.
- Use `increase()` for event count over a window.
- Use `sum by (...)` to aggregate intentionally.
- Avoid unbounded regex on high-cardinality labels.
- Avoid dashboard queries over very large time ranges.
- Use recording rules for expensive queries.

### Storage

- Use persistent storage in production.
- Size PVCs based on ingestion rate and retention.
- Monitor `prometheus_tsdb_head_series`.
- Use remote write for long-term retention.
- Do not use slow storage for heavy Prometheus workloads.

### Alerting

- Alert on user impact and platform risk.
- Add severity, team, service, and runbook labels.
- Use `for` to avoid flapping.
- Keep warning and critical thresholds separate.
- Regularly remove stale alerts.

## 27. Unsupported or Risky Practices

Avoid these in production OpenShift:

- Editing generated Prometheus StatefulSets directly.
- Editing generated Prometheus config Secrets directly.
- Creating custom Prometheus CRs as a replacement for OpenShift monitoring.
- Creating extra `ServiceMonitor`, `PodMonitor`, or `PrometheusRule` objects in reserved `openshift-*` or `kube-*` namespaces unless documentation explicitly allows it.
- Deploying user workloads into `openshift-*` or `kube-*` namespaces.
- Adding `openshift.io/cluster-monitoring: "true"` label manually to namespaces.
- Using unbounded metric labels.
- Using non-POSIX storage for Prometheus TSDB.
- Relying only on local Prometheus retention for long-term compliance requirements.

## 28. Interview and Real-World Talking Points

### Q1. What is the role of Prometheus in OpenShift?

Prometheus is the core time-series metrics database and rule evaluation engine used by OpenShift monitoring. It scrapes platform and user workload targets, stores metrics locally, evaluates rules, and sends alerts to Alertmanager. In OpenShift, Prometheus is operator-managed and configured through supported monitoring ConfigMaps and custom resources.

### Q2. Difference between Prometheus and Thanos Querier?

Prometheus stores and evaluates metrics. Thanos Querier provides a unified query API across multiple Prometheus-compatible stores, including platform and user workload Prometheus instances. The OpenShift console queries through Thanos Querier for a unified metrics view.

### Q3. Difference between ServiceMonitor and PodMonitor?

`ServiceMonitor` scrapes endpoints discovered through a Kubernetes Service. `PodMonitor` scrapes pods directly. `ServiceMonitor` is preferred when the workload already has a stable Service abstraction.

### Q4. Why is Prometheus using too much disk?

Usually due to high ingestion rate, too many targets, short scrape interval, high-cardinality labels, or series churn. Use queries such as `scrape_samples_post_metric_relabeling`, `scrape_series_added`, and `prometheus_tsdb_head_series` to identify the source.

### Q5. How do you enable user workload monitoring?

Set `enableUserWorkload: true` in `cluster-monitoring-config` in the `openshift-monitoring` namespace. Then verify components in `openshift-user-workload-monitoring`.

### Q6. How do you add application metrics?

The app exposes `/metrics`; create a Service with a named port; create a `ServiceMonitor` in the same namespace selecting the Service labels; query `up{namespace="..."}` or app metrics in the console.

### Q7. What should you avoid when configuring OpenShift monitoring?

Avoid direct modification of operator-managed resources. Use supported ConfigMap fields and CRDs only. Avoid creating monitoring resources in reserved namespaces unless explicitly supported.

## 30. Mental Model for Troubleshooting

Use this sequence:

```text
1. Is monitoring operator healthy?
2. Is user workload monitoring enabled, if needed?
3. Is the monitor object present?
4. Does the monitor selector match the Service or Pod labels?
5. Does the Service have endpoints?
6. Does the Service port name match the monitor port?
7. Is /metrics reachable?
8. Is authentication required?
9. Is NetworkPolicy blocking traffic?

11. Does PromQL return data?
12. Are alerts/rules valid?

```

This order avoids guessing and isolates whether the problem is discovery, connectivity, authentication, ingestion, query, or alerting.
