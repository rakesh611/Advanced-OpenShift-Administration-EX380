## 1. Purpose of High CPU/Memory Pod Analysis

High CPU or high memory pod analysis is the process of identifying which pod, container, namespace, workload, or node is consuming abnormal compute resources and determining whether the consumption is expected, misconfigured, caused by application behavior, or caused by platform pressure.

In OpenShift, this analysis is not limited to running `oc adm top pods`. A senior administrator must combine:

- Real-time usage from the Metrics API.
- Historical metrics from Prometheus/Thanos.
- Pod specifications such as requests, limits, QoS class, node placement, probes, and environment variables.
- Events such as `OOMKilled`, `Evicted`, `BackOff`, `FailedScheduling`, and `NodeHasInsufficientMemory`.
- Workload behavior from Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, Operators, and sidecars.
- Application telemetry such as request rate, latency, JVM heap, Go heap, database connections, queue depth, garbage collection, and thread counts.

A senior OpenShift admin does not simply ask, “Which pod is high?” The correct question is:

> Is this resource usage expected for the workload, aligned with its requests and limits, sustainable on the node, and safe for the cluster SLO?

## 2. Senior-Level Troubleshooting Mindset

When a pod shows high CPU or memory, avoid jumping directly to scaling or restarting. Use a layered approach.

### 2.1 First classify the problem

Ask these questions first:

| Question | Why it matters |
|---|---|
| Is the issue CPU, memory, or both? | CPU and memory fail differently. CPU is throttled; memory can kill the container. |
| Is usage high compared to request, limit, node capacity, or historical baseline? | A pod using 800Mi may be normal if its request is 1Gi, but dangerous if its limit is 900Mi. |
| Is this one pod, all replicas, one namespace, or one node? | Determines whether the issue is application-specific, release-specific, node-specific, or cluster-wide. |
| Did it start after a deployment, config change, traffic spike, or node change? | Correlation often reveals root cause faster than raw metrics. |
| Is the pod being throttled or killed? | High usage alone is not always an incident; throttling and OOM are stronger signals. |
| Is autoscaling configured and working? | Missing requests or bad metrics can prevent HPA from scaling. |
| Are limits too low, requests too low, or application behavior abnormal? | Remediation differs. |

### 2.2 Separate symptoms from causes

Common symptoms:

- Pod CPU usage is high.
- Pod memory usage is near limit.
- Pod restarts frequently.
- Pod is `OOMKilled`.
- Pod latency increased.
- Node is under `MemoryPressure`.
- HPA is not scaling.
- CPU throttling is high.

Common causes:

- Legitimate traffic increase.
- Bad resource requests or limits.
- CPU limit too low causing throttling.
- Memory leak.
- JVM heap misconfigured for container limits.
- Sidecar consuming unexpected resources.
- Infinite loop or hot code path.
- Excessive logging.
- Too many pods on one node.
- DaemonSet overhead not considered.
- CronJob or batch workload burst.
- Poor scheduling due to affinity, taints, tolerations, or topology constraints.
- Application dependency degradation causing retries and CPU spikes.

### 2.3 Decide incident severity

Use this decision table:

| Condition | Severity guidance |
|---|---|
| CPU high but no throttling, no latency, no saturation | Observe and baseline. |
| CPU high and throttling > 20% for sustained time | Investigate limits and app performance. |
| Memory high but stable below limit | Baseline and tune requests. |
| Memory increasing continuously toward limit | Memory leak investigation. |
| OOMKilled restarts | Incident for production workload. |
| Node MemoryPressure with evictions | Cluster/node capacity incident. |
| HPA cannot scale because requests are missing | Configuration incident. |
| Single replica critical pod saturated | Availability risk. |

## 3. OpenShift Monitoring Data Sources

OpenShift provides multiple ways to analyze CPU and memory. Each source has different purpose and accuracy.

### 3.1 `oc adm top`

`oc adm top nodes` and `oc adm top pods` give quick current usage.

Use it for:

- Fast triage.
- Current pod/node usage.
- Identifying obvious hot pods.
- Comparing current usage with Prometheus history.

Limitations:

- It is point-in-time or near-real-time.
- It does not show historical trend.
- It does not directly explain why usage is high.
- It does not show CPU throttling.
- It does not show request/limit ratio by default.

Examples:

```bash
oc adm top nodes
oc adm top pods -A
oc adm top pods -n myapp
oc adm top pod mypod -n myapp --containers
oc adm top pods -A --containers
```

### 3.2 OpenShift monitoring stack

OpenShift monitoring is based on Prometheus and related components. For cluster admins, the Observe/Metrics area and Thanos Querier allow querying platform and user workload metrics, depending on permissions and configuration.

Typical namespaces:

```bash
openshift-monitoring
openshift-user-workload-monitoring
```

Useful components:

| Component | Purpose |
|---|---|
| Prometheus | Scrapes and stores time-series metrics. |
| Thanos Querier | Query layer for metrics across Prometheus instances. |
| Alertmanager | Handles alerts, routing, grouping, silencing. |
| kube-state-metrics | Exposes Kubernetes object state such as requests, limits, restarts, pod status. |
| node-exporter | Exposes node OS metrics. |
| kubelet/cAdvisor metrics | Container CPU, memory, filesystem, and network metrics. |
| Metrics API | Used by `oc adm top`/`kubectl top` and autoscaling resource metrics. |

### 3.3 Prometheus metrics commonly used

| Area | Metrics |
|---|---|
| Container CPU usage | `container_cpu_usage_seconds_total` |
| CPU throttling | `container_cpu_cfs_throttled_periods_total`, `container_cpu_cfs_periods_total`, `container_cpu_cfs_throttled_seconds_total` |
| Container memory | `container_memory_working_set_bytes`, `container_memory_usage_bytes`, `container_memory_rss`, `container_memory_cache` |
| Requests/limits | `kube_pod_container_resource_requests`, `kube_pod_container_resource_limits` |
| Restarts | `kube_pod_container_status_restarts_total` |
| Termination reason | `kube_pod_container_status_last_terminated_reason` |
| Pod owner | `kube_pod_owner` |
| Node conditions | `kube_node_status_condition` |
| Node CPU | `node_cpu_seconds_total` |
| Node memory | `node_memory_MemAvailable_bytes`, `node_memory_MemTotal_bytes` |

> Metric names and labels can vary slightly by OpenShift/Kubernetes version and monitoring stack version. Always verify metric availability in the Metrics UI before building production alerts.

## 4. CPU and Memory Concepts You Must Understand

### 4.1 CPU in Kubernetes/OpenShift

CPU is measured in cores.

Examples:

| Value | Meaning |
|---|---|
| `1` | 1 CPU core |
| `500m` | 0.5 CPU core |
| `100m` | 0.1 CPU core |
| `250m` | 0.25 CPU core |

Important CPU behavior:

- CPU request affects scheduling and HPA utilization calculation.
- CPU limit controls maximum CPU time using Linux CFS quota.
- CPU is compressible. If a container wants more CPU than its limit, it is throttled, not killed.
- High CPU usage is not automatically bad. High CPU plus latency, throttling, failed readiness, or node saturation is more serious.

### 4.2 Memory in Kubernetes/OpenShift

Memory is measured in bytes, MiB, GiB, etc.

Important memory behavior:

- Memory request affects scheduling.
- Memory limit is enforced by the container runtime/cgroup.
- Memory is non-compressible from Kubernetes scheduling perspective.
- If a container exceeds its memory limit, it can be terminated with `OOMKilled`.
- If the node is under memory pressure, kubelet can evict pods based on QoS and eviction rules.

### 4.3 CPU high vs memory high

| Resource | Failure behavior | Typical symptom | Main remediation |
|---|---|---|---|
| CPU | Throttling, latency, slow response | High CPU, high throttling, HPA scaling | Tune CPU limit/request, scale out, optimize code |
| Memory | OOM kill or eviction | Restarts, OOMKilled, MemoryPressure | Fix leak, tune heap/cache, increase limit, reduce pod density |

### 4.4 Request vs limit

| Field | Used for | Enforced? |
|---|---|---|
| CPU request | Scheduling and HPA percentage calculation | No hard runtime cap |
| CPU limit | Runtime maximum CPU quota | Yes, via CFS quota |
| Memory request | Scheduling and QoS | No hard runtime cap |
| Memory limit | Runtime max memory | Yes, can cause OOMKilled |

### 4.5 QoS classes

Pods are assigned a Quality of Service class based on CPU and memory requests/limits.

| QoS | Condition | Eviction priority |
|---|---|---|
| Guaranteed | Every container has CPU and memory request equal to limit | Last to evict |
| Burstable | At least one request/limit set, but not all equal | Middle |
| BestEffort | No CPU/memory requests or limits | First to evict |

Check QoS:

```bash
oc get pod mypod -n myns -o jsonpath='{.status.qosClass}{"\n"}'
```

## 5. Fast Triage Workflow

Use this when an alert fires or someone reports slowness.

### 5.1 Identify the scope

```bash
oc adm top pods -A --sort-by=cpu
oc adm top pods -A --sort-by=memory
oc adm top nodes
```

If `--sort-by` is not supported in your `oc` version, use shell sorting:

```bash
oc adm top pods -A | sort -k3 -hr | head
oc adm top pods -A | sort -k4 -hr | head
```

### 5.2 Narrow to namespace

```bash
NS=myapp
oc adm top pods -n $NS
oc get pods -n $NS -o wide
oc get deploy,sts,ds,job,cronjob -n $NS
```

### 5.3 Check container-level usage

```bash
POD=mypod
oc adm top pod $POD -n $NS --containers
```

This is critical for multi-container pods. Frequently the main application is blamed while the sidecar, proxy, log collector, or exporter is consuming resources.

### 5.4 Check pod status, restarts, events

```bash
oc get pod $POD -n $NS -o wide
oc describe pod $POD -n $NS
oc get events -n $NS --sort-by='.lastTimestamp' | tail -50
```

Look for:

- `OOMKilled`
- `Evicted`
- `BackOff`
- `Unhealthy`
- `Readiness probe failed`
- `Liveness probe failed`
- `FailedScheduling`
- `NodeHasInsufficientMemory`
- `Preempting`

### 5.5 Check previous logs after restart

```bash
oc logs $POD -n $NS --all-containers --previous
oc logs $POD -n $NS -c app --previous
```

### 5.6 Check requests and limits

```bash
oc get pod $POD -n $NS -o jsonpath='{range .spec.containers[*]}{.name}{"\nrequests: "}{.resources.requests}{"\nlimits: "}{.resources.limits}{"\n\n"}{end}'
```

### 5.7 Check owning workload

```bash
oc get pod $POD -n $NS -o jsonpath='{.metadata.ownerReferences[*].kind}{"/"}{.metadata.ownerReferences[*].name}{"\n"}'
```

Then inspect the workload:

```bash
oc describe deploy <deployment> -n $NS
oc describe sts <statefulset> -n $NS
oc describe ds <daemonset> -n $NS
```

## 6. CLI-Based Analysis with `oc`

### 6.1 Top CPU pods across cluster

```bash
oc adm top pods -A --containers
```

Alternative with sorting:

```bash
oc adm top pods -A --containers | sort -k4 -hr | head -30
```

Depending on output columns, CPU and memory column positions may differ. Confirm column order first.

### 6.2 Top memory pods across cluster

```bash
oc adm top pods -A --containers | sort -k5 -hr | head -30
```

### 6.3 Top pods in one namespace

```bash
NS=payments
oc adm top pods -n $NS --containers
```

### 6.4 Node usage

```bash
oc adm top nodes
```

Interpretation:

| Column | Meaning |
|---|---|
| `CPU(cores)` | Current CPU usage in cores/millicores |
| `CPU%` | Percentage of node allocatable/capacity depending on implementation |
| `MEMORY(bytes)` | Current memory usage |
| `MEMORY%` | Percentage memory usage |

### 6.5 Pods on a hot node

```bash
NODE=worker-0.example.com
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
oc adm top pods -A --containers | grep "$NODE"
```

`oc adm top pods` normally does not print node name. Use `oc get pods -A -o wide` to correlate pod to node.

Better:

```bash
oc get pods -A --field-selector spec.nodeName=$NODE \
  -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,STATUS:.status.phase,RESTARTS:.status.containerStatuses[*].restartCount,NODE:.spec.nodeName'
```

### 6.6 Raw Metrics API for one pod

```bash
NS=payments
POD=api-abc123
oc get --raw "/apis/metrics.k8s.io/v1beta1/namespaces/$NS/pods/$POD" | jq
```

This is useful when `oc adm top` output looks suspicious or you want container-level values from the Metrics API.

### 6.7 Inspect pod resources with JSONPath

```bash
oc get pod $POD -n $NS -o jsonpath='{range .spec.containers[*]}Container: {.name}{"\n"}Requests: {.resources.requests}{"\n"}Limits: {.resources.limits}{"\n\n"}{end}'
```

### 6.8 Detect OOMKilled containers

```bash
oc get pods -A -o json | jq -r '
  .items[] as $pod |
  $pod.status.containerStatuses[]? |
  select(.lastState.terminated.reason == "OOMKilled") |
  [$pod.metadata.namespace, $pod.metadata.name, .name, .restartCount] | @tsv
'
```

### 6.9 Restart count overview

```bash
oc get pods -A \
  -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,STATUS:.status.phase,RESTARTS:.status.containerStatuses[*].restartCount,NODE:.spec.nodeName' \
  | sort -k4 -nr | head -30
```

### 6.10 Debug node-level pressure

```bash
NODE=worker-0.example.com
oc describe node $NODE
```

Look for:

- `MemoryPressure`
- `DiskPressure`
- `PIDPressure`
- Allocated resources
- Non-terminated pods
- Events
- Capacity and allocatable

For deeper node troubleshooting:

```bash
oc debug node/$NODE
chroot /host
free -h
uptime
ps aux --sort=-%cpu | head
ps aux --sort=-%mem | head
crictl ps
crictl stats
journalctl -u kubelet --since "1 hour ago"
```

Use node debug carefully in production and follow your organization’s break-glass process.

## 7. PromQL-Based CPU Analysis

PromQL gives historical and aggregated analysis that `oc adm top` cannot provide.

### 7.1 Current CPU usage by pod

```promql
topk(20,
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])
  )
)
```

Result interpretation:

| Value | Meaning |
|---|---|
| `0.1` | 100m CPU |
| `0.5` | 500m CPU |
| `1` | 1 CPU core |
| `2` | 2 CPU cores |

### 7.2 CPU usage by container

```promql
topk(30,
  sum by (namespace, pod, container) (
    rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])
  )
)
```

Use this for multi-container pods.

### 7.3 CPU usage in one namespace

```promql
topk(20,
  sum by (pod) (
    rate(container_cpu_usage_seconds_total{namespace="payments", container!="", container!="POD"}[5m])
  )
)
```

### 7.4 CPU usage by namespace

```promql
topk(20,
  sum by (namespace) (
    rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])
  )
)
```

This is useful when the cluster is hot and you need to identify the noisy namespace.

### 7.5 CPU usage as percentage of request

```promql
100 *
sum by (namespace, pod, container) (
  rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])
)
/
sum by (namespace, pod, container) (
  kube_pod_container_resource_requests{resource="cpu", unit="core"}
)
```

Interpretation:

| Result | Meaning |
|---|---|
| `50` | Using 50% of requested CPU |
| `100` | Using exactly requested CPU |
| `200` | Using 2x requested CPU |
| `500` | Using 5x requested CPU |

A pod can use more than its CPU request if node CPU is available and no CPU limit blocks it.

### 7.6 CPU usage as percentage of limit

```promql
100 *
sum by (namespace, pod, container) (
  rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])
)
/
sum by (namespace, pod, container) (
  kube_pod_container_resource_limits{resource="cpu", unit="core"}
)
```

If this is near 100% and throttling is high, the CPU limit is probably too low or the workload needs more replicas.

### 7.7 CPU trend over time

```promql
sum by (namespace, pod) (
  rate(container_cpu_usage_seconds_total{namespace="payments", container!="", container!="POD"}[5m])
)
```

Graph this over 1h, 6h, 24h, and 7d.

Questions to answer:

- Is the spike sudden or gradual?
- Did it start after deployment?
- Does it follow traffic pattern?
- Is it only during batch windows?
- Is it one replica or all replicas?

### 7.8 CPU by workload owner

Metric joins vary by label availability, but a common pattern is to use `kube_pod_owner` to map pods to controllers.

Example concept:

```promql
sum by (namespace, owner_name, owner_kind) (
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])
  )
  * on (namespace, pod) group_left(owner_name, owner_kind)
  kube_pod_owner
)
```

Use this when pods have random ReplicaSet suffixes and you need owner-level aggregation.

### 7.9 Detect CPU spike compared to past baseline

```promql
sum by (namespace, pod) (
  rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])
)
/
clamp_min(
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m] offset 1d)
  ),
  0.001
)
```

Interpretation:

| Value | Meaning |
|---|---|
| `1` | Same as yesterday at same time |
| `2` | 2x yesterday |
| `5` | 5x yesterday |

This helps separate normal peak traffic from abnormal spike.

## 8. PromQL-Based Memory Analysis

Memory analysis is different from CPU because memory does not use `rate()` for current usage. Memory metrics are gauges.

### 8.1 Current memory working set by pod

```promql
topk(20,
  sum by (namespace, pod) (
    container_memory_working_set_bytes{container!="", container!="POD"}
  )
)
```

`container_memory_working_set_bytes` is often the best first metric because it approximates memory actively used and less easily reclaimable than cache.

### 8.2 Memory by container

```promql
topk(30,
  sum by (namespace, pod, container) (
    container_memory_working_set_bytes{container!="", container!="POD"}
  )
)
```

### 8.3 Memory usage in MiB

```promql
sum by (namespace, pod, container) (
  container_memory_working_set_bytes{namespace="payments", container!="", container!="POD"}
) / 1024 / 1024
```

### 8.4 Memory as percentage of request

```promql
100 *
sum by (namespace, pod, container) (
  container_memory_working_set_bytes{container!="", container!="POD"}
)
/
sum by (namespace, pod, container) (
  kube_pod_container_resource_requests{resource="memory", unit="byte"}
)
```

If usage is consistently far above request, the scheduler may pack too many similar pods on a node, increasing MemoryPressure risk.

### 8.5 Memory as percentage of limit

```promql
100 *
sum by (namespace, pod, container) (
  container_memory_working_set_bytes{container!="", container!="POD"}
)
/
sum by (namespace, pod, container) (
  kube_pod_container_resource_limits{resource="memory", unit="byte"}
)
```

Interpretation:

| Result | Meaning |
|---|---|
| `< 60%` | Usually safe, depends on workload |
| `60-80%` | Watch trend |
| `80-90%` | Risk zone |
| `> 90%` | High OOM risk |
| `> 100%` | Metric/label issue or limit missing/mismatch; verify |

### 8.6 Memory growth over time

```promql
sum by (namespace, pod) (
  container_memory_working_set_bytes{namespace="payments", container!="", container!="POD"}
)
```

Graph over multiple windows:

- 30 minutes: immediate incident.
- 6 hours: deployment or traffic pattern.
- 24 hours: daily pattern.
- 7 days: leak or baseline shift.

### 8.7 Memory leak suspicion

A simple signal:

```promql
sum by (namespace, pod) (
  container_memory_working_set_bytes{container!="", container!="POD"}
)
-
sum by (namespace, pod) (
  container_memory_working_set_bytes{container!="", container!="POD"} offset 1h
)
```

A more advanced predictive query:

```promql
predict_linear(
  sum by (namespace, pod) (
    container_memory_working_set_bytes{namespace="payments", container!="", container!="POD"}
  )[1h:],
  3600
)
```

Use prediction carefully. Memory usage can be non-linear because of GC, cache eviction, batch processing, and traffic changes.

### 8.8 OOMKilled detection

```promql
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

### 8.9 Restart increase

```promql
increase(kube_pod_container_status_restarts_total{namespace="payments"}[1h]) > 0
```

### 8.10 Memory RSS vs cache

```promql
sum by (namespace, pod, container) (
  container_memory_rss{namespace="payments", container!="", container!="POD"}
)
```

```promql
sum by (namespace, pod, container) (
  container_memory_cache{namespace="payments", container!="", container!="POD"}
)
```

Interpretation:

| Metric | Use |
|---|---|
| `working_set` | First-line memory pressure metric |
| `rss` | Anonymous resident memory; useful for leaks |
| `cache` | File/page cache; may be reclaimable |
| `usage` | Broader cgroup memory usage; can include cache |

## 9. Container-Level Drill Down

Many production pods have multiple containers:

- Main application container.
- Service mesh sidecar.
- Logging sidecar.
- Metrics exporter.
- Init containers.
- Config reloader.
- OAuth proxy.
- Database proxy.

Always identify which container is hot.

### 9.1 CLI

```bash
oc adm top pod $POD -n $NS --containers
```

### 9.2 PromQL

```promql
sum by (namespace, pod, container) (
  rate(container_cpu_usage_seconds_total{namespace="payments", pod="api-abc123", container!="", container!="POD"}[5m])
)
```

```promql
sum by (namespace, pod, container) (
  container_memory_working_set_bytes{namespace="payments", pod="api-abc123", container!="", container!="POD"}
)
```

### 9.3 Container-specific logs

```bash
oc logs $POD -n $NS -c app
oc logs $POD -n $NS -c istio-proxy
oc logs $POD -n $NS -c oauth-proxy
oc logs $POD -n $NS -c metrics-exporter
```

### 9.4 Init containers

Init containers can consume high resources during startup, but they do not run continuously.

Check:

```bash
oc get pod $POD -n $NS -o jsonpath='{range .status.initContainerStatuses[*]}{.name}{"\t"}{.state}{"\n"}{end}'
```

If startup is slow or failing, init containers may be repeatedly consuming CPU/memory.

## 10. Requests, Limits, and QoS Analysis

Requests and limits are often the root cause of bad resource behavior.

### 10.1 View requests and limits

```bash
oc get pod $POD -n $NS -o jsonpath='{range .spec.containers[*]}{.name}{"\n  requests: "}{.resources.requests}{"\n  limits: "}{.resources.limits}{"\n"}{end}'
```

### 10.2 View QoS class

```bash
oc get pod $POD -n $NS -o jsonpath='{.status.qosClass}{"\n"}'
```

### 10.3 Common bad patterns

| Pattern | Symptom | Risk |
|---|---|---|
| No requests, no limits | BestEffort pods | First to evict, unpredictable scheduling |
| CPU limit too low | High throttling, latency | App appears slow despite available node CPU |
| Memory limit too low | OOMKilled | Restart loops, downtime |
| Memory request too low | Overpacking | Node MemoryPressure, eviction |
| Request equals huge limit without need | Wasted cluster capacity | Low utilization, scheduling failures |
| HPA without CPU request | HPA percentage calculation broken | HPA may not behave correctly |
| Java heap larger than container limit | OOMKilled | JVM/native memory exceeds cgroup |

### 10.4 CPU request/limit strategy

For most services:

- Set CPU request near normal steady-state usage or slightly above p50/p60.
- Avoid setting CPU limit too aggressively for latency-sensitive applications.
- Use HPA based on CPU/request, request rate, queue depth, or custom metrics.
- For batch jobs, use realistic CPU limits to avoid starving other workloads.

### 10.5 Memory request/limit strategy

For memory:

- Set request based on normal steady-state plus buffer.
- Set limit based on safe upper bound.
- Keep enough gap for spikes, GC, native memory, sidecars, and file cache.
- For JVM, configure heap relative to container limit.
- For Go/Python/Node.js, validate runtime memory behavior under load.

### 10.6 QoS tuning examples

#### Guaranteed pod

Use when eviction tolerance is very low and sizing is well known.

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "1Gi"
  limits:
    cpu: "500m"
    memory: "1Gi"
```

#### Burstable pod

Common for most apps.

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

#### BestEffort pod

Avoid for production.

```yaml
resources: {}
```

## 11. CPU Throttling Analysis

CPU throttling is one of the most misunderstood Kubernetes performance problems.

A pod may show CPU usage below limit but still suffer throttling because CPU quota is enforced over time periods. Bursty workloads can be throttled even when average CPU usage looks acceptable.

### 11.1 CPU throttling ratio

```promql
100 *
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_throttled_periods_total{container!="", container!="POD"}[5m])
)
/
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_periods_total{container!="", container!="POD"}[5m])
)
```

Interpretation:

| Throttling ratio | Meaning |
|---|---|
| `< 5%` | Usually acceptable |
| `5-20%` | Watch, possible performance impact |
| `20-50%` | Likely performance problem |
| `> 50%` | Severe CPU quota pressure |

### 11.2 CPU throttled seconds

```promql
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_throttled_seconds_total{container!="", container!="POD"}[5m])
)
```

### 11.3 CPU usage vs throttling

Use both queries together:

```promql
sum by (namespace, pod, container) (
  rate(container_cpu_usage_seconds_total{namespace="payments", container!="", container!="POD"}[5m])
)
```

```promql
100 *
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_throttled_periods_total{namespace="payments", container!="", container!="POD"}[5m])
)
/
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_periods_total{namespace="payments", container!="", container!="POD"}[5m])
)
```

### 11.4 Root causes of throttling

| Cause | Evidence | Fix |
|---|---|---|
| CPU limit too low | Throttling high, usage near limit | Increase/remove CPU limit after risk review |
| Traffic spike | CPU and request rate increased | Scale horizontally, tune HPA |
| Bad code path | CPU high after release | Roll back or fix code |
| Too few replicas | All replicas saturated | Increase replicas/HPA max |
| Sidecar overhead | Sidecar CPU high | Tune sidecar resources/config |
| Node CPU pressure | Many pods high on same node | Reschedule, rebalance, scale nodes |

### 11.5 Senior recommendation on CPU limits

For latency-sensitive workloads, many platform teams avoid tight CPU limits because limits can introduce throttling and latency. They still set CPU requests for scheduling and HPA. This decision must be aligned with cluster governance, multi-tenancy policy, and workload criticality.

Practical approach:

- Always set CPU requests.
- Use CPU limits for untrusted, batch, or noisy workloads.
- Avoid overly tight CPU limits for latency-sensitive services.
- Monitor throttling, not just CPU usage.

## 12. OOMKilled and Memory Pressure Analysis

Memory incidents are usually more dangerous than CPU incidents because memory exhaustion can terminate containers.

### 12.1 Detect OOMKilled from CLI

```bash
oc describe pod $POD -n $NS
```

Look for:

```text
Last State: Terminated
Reason: OOMKilled
Exit Code: 137
```

Also check events:

```bash
oc get events -n $NS --sort-by='.lastTimestamp' | grep -i -E 'oom|kill|evict|memory'
```

### 12.2 Detect OOMKilled from PromQL

```promql
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

### 12.3 Restart increase due to OOM

```promql
increase(kube_pod_container_status_restarts_total[30m]) > 0
```

Correlate with termination reason.

### 12.4 Why memory OOM happens

Common causes:

- Memory limit lower than application requirement.
- JVM max heap too high or not container-aware.
- Native memory leak.
- File upload/download buffering.
- Large cache without size bound.
- Too many threads.
- Large batch query/result set.
- Sidecar memory growth.
- Application traffic spike.
- Wrong memory unit, for example using `400m` instead of `400Mi`.

### 12.5 Memory limit vs working set

If working set is close to memory limit, OOM risk is high.

```promql
100 *
sum by (namespace, pod, container) (
  container_memory_working_set_bytes{container!="", container!="POD"}
)
/
sum by (namespace, pod, container) (
  kube_pod_container_resource_limits{resource="memory", unit="byte"}
)
```

### 12.6 Memory leak pattern

A memory leak often shows:

- Memory grows steadily over time.
- Memory does not drop after traffic decreases.
- Pod eventually restarts with OOMKilled.
- New pod starts low, then repeats the same growth pattern.

PromQL to compare now vs 1 hour ago:

```promql
sum by (namespace, pod) (
  container_memory_working_set_bytes{namespace="payments", container!="", container!="POD"}
)
-
sum by (namespace, pod) (
  container_memory_working_set_bytes{namespace="payments", container!="", container!="POD"} offset 1h
)
```

### 12.7 Node MemoryPressure

```bash
oc describe node $NODE | grep -A5 -i Conditions
```

PromQL:

```promql
kube_node_status_condition{condition="MemoryPressure", status="true"} == 1
```

If node memory pressure exists, pods may be evicted even if they are not exceeding their own limits.

### 12.8 Evicted pods

```bash
oc get pods -A --field-selector=status.phase=Failed | grep -i Evicted
```

More detailed:

```bash
oc get pods -A -o json | jq -r '
  .items[] |
  select(.status.reason == "Evicted") |
  [.metadata.namespace, .metadata.name, .status.message] | @tsv
'
```

### 12.9 Memory unit mistake

Kubernetes memory units are important.

| Value | Meaning |
|---|---|
| `400Mi` | 400 mebibytes |
| `400M` | 400 megabytes |
| `400m` | 0.4 bytes, usually a mistake |

Never use lowercase `m` for memory.

## 13. Node-Level Correlation

A high pod can be the victim or the cause. Always check node context.

### 13.1 Find pod node

```bash
oc get pod $POD -n $NS -o wide
```

### 13.2 Check node usage

```bash
oc adm top node $NODE
oc describe node $NODE
```

### 13.3 Pods on the same node

```bash
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
```

### 13.4 Node CPU usage from PromQL

```promql
100 - (
  avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  ) * 100
)
```

### 13.5 Node memory available percentage

```promql
100 *
node_memory_MemAvailable_bytes
/
node_memory_MemTotal_bytes
```

Low available memory plus MemoryPressure events indicates node-level risk.

### 13.6 Allocated resources from node description

```bash
oc describe node $NODE
```

Look at:

```text
Allocated resources:
  Resource           Requests      Limits
  cpu                ...           ...
  memory             ...           ...
```

Important distinction:

| Metric | Meaning |
|---|---|
| Usage | Actual current consumption |
| Request allocation | Scheduling reservation |
| Limit allocation | Maximum potential consumption |

A node can have low actual usage but high requested allocation, causing scheduling failures. A node can also have modest requests but high actual usage if pods are under-requested.

## 14. Workload Controller Analysis

After identifying a hot pod, inspect its controller.

### 14.1 Deployment

```bash
oc describe deploy <name> -n $NS
oc get deploy <name> -n $NS -o yaml
oc rollout history deploy/<name> -n $NS
```

Check:

- Recent rollout.
- Image tag/digest.
- Replica count.
- Strategy.
- Resource requests and limits.
- HPA association.
- Environment variables.
- ConfigMaps and Secrets.
- Probes.

### 14.2 StatefulSet

```bash
oc describe sts <name> -n $NS
oc get pvc -n $NS
```

For StatefulSets, high memory/CPU may be tied to:

- One shard/partition hotter than others.
- Persistent volume latency.
- Leader pod doing more work.
- Compaction, replication, or index rebuild.

### 14.3 DaemonSet

```bash
oc describe ds <name> -n $NS
```

DaemonSet resource issues are cluster-wide risks because they run on every matching node.

Examples:

- Log collectors.
- Security agents.
- CSI drivers.
- Network plugins.
- Monitoring agents.

A DaemonSet with underestimated memory requests can push every node toward pressure.

### 14.4 Job/CronJob

```bash
oc get jobs,cronjobs -n $NS
oc describe job <job> -n $NS
oc describe cronjob <cronjob> -n $NS
```

Batch jobs often create predictable CPU/memory spikes. Check:

- Schedule.
- Concurrency policy.
- Parallelism.
- Completions.
- Backoff limit.
- Resource limits.
- Missed jobs after outage.

### 14.5 Operator-managed workload

If a pod is managed by an Operator, do not directly edit the Deployment unless you know the reconciliation model.

Check:

```bash
oc get csv -A
oc get operators -A
oc get subscription -A
oc get installplan -A
```

Find the owning custom resource and update resources there if supported.

## 15. Application-Level Root Cause Patterns

### 15.1 Traffic spike

Evidence:

- All replicas show similar CPU increase.
- Request rate increased.
- HPA may be scaling.
- No single pod is abnormal.

Fix:

- Scale replicas.
- Increase HPA max.
- Tune CPU requests.
- Add caching.
- Rate-limit abusive clients.

### 15.2 Bad deployment or code regression

Evidence:

- CPU/memory increased immediately after rollout.
- New image only affected.
- Rollback fixes issue.

Commands:

```bash
oc rollout history deploy/api -n payments
oc rollout undo deploy/api -n payments
```

Fix:

- Roll back.
- Compare image versions.
- Review application changes.
- Run profiling.

### 15.3 CPU-bound loop

Evidence:

- One pod/container CPU near limit.
- Logs may show repeated errors/retries.
- Request rate may not justify CPU usage.

Fix:

- Inspect logs.
- Capture profile if app supports it.
- Check retry loops and dependency failures.

### 15.4 Memory leak

Evidence:

- Memory grows over time.
- OOMKilled after predictable duration.
- Restart resets memory.
- Pattern repeats.

Fix:

- Capture heap dump/profile.
- Set safe limit as temporary mitigation.
- Fix leak.
- Tune cache and connection pools.

### 15.5 JVM memory issue

Evidence:

- Java app OOMKilled.
- Container limit lower than heap plus native memory.
- GC logs show pressure.

Checks:

```bash
oc exec $POD -n $NS -- java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|InitialHeapSize|MaxRAMPercentage'
```

Fix:

- Set `-XX:MaxRAMPercentage` appropriately.
- Leave headroom for metaspace, threads, direct buffers, native memory, sidecars.
- Do not set heap equal to container memory limit.

Example:

```yaml
env:
- name: JAVA_TOOL_OPTIONS
  value: "-XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=40 -XX:+ExitOnOutOfMemoryError"
```

### 15.6 Go memory issue

Evidence:

- Go service memory grows with load.
- GC not returning memory quickly.

Fix ideas:

- Use `GOMEMLIMIT` for modern Go versions.
- Capture pprof heap.
- Tune caches and buffers.

Example:

```yaml
env:
- name: GOMEMLIMIT
  value: "700MiB"
```

### 15.7 Python/Node.js memory issue

Common causes:

- Large objects retained in memory.
- Unbounded queues.
- Large JSON processing.
- Memory-heavy dependencies.
- Too many worker processes.

Fix:

- Limit worker count.
- Stream large payloads.
- Use profiling.
- Tune runtime-specific memory flags.

### 15.8 Sidecar overhead

Evidence:

- `oc adm top pod --containers` shows sidecar hot.
- Application container is normal.

Fix:

- Tune sidecar resources.
- Adjust logging level.
- Reduce mesh telemetry volume.
- Check proxy configuration.

### 15.9 Excessive logging

Evidence:

- CPU high in app or log collector.
- Disk/network IO high.
- Logs repeat errors rapidly.

Fix:

- Reduce log level.
- Fix noisy error loop.
- Rate-limit logs.
- Tune log collector resources.

### 15.10 Dependency failure causing retries

Evidence:

- CPU high after DB/API/cache failure.
- Logs show retries/timeouts.
- Request rate to dependency increases.

Fix:

- Add backoff and circuit breaker.
- Reduce retry storm.
- Fix dependency.
- Scale dependency.

## 17. Alerting Rules for High CPU and Memory

### 17.1 CPU usage over request

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pod-resource-alerts
  namespace: payments
spec:
  groups:
  - name: pod-resource.rules
    rules:
    - alert: PodHighCPUOverRequest
      expr: |
        100 *
        sum by (namespace, pod) (
          rate(container_cpu_usage_seconds_total{namespace="payments", container!="", container!="POD"}[5m])
        )
        /
        sum by (namespace, pod) (
          kube_pod_container_resource_requests{namespace="payments", resource="cpu", unit="core"}
        ) > 200
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "Pod CPU usage is above 200% of request"
        description: "Pod {{ $labels.namespace }}/{{ $labels.pod }} is using more than 2x requested CPU for 15 minutes."
```

### 17.2 CPU throttling alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pod-cpu-throttling-alerts
  namespace: payments
spec:
  groups:
  - name: pod-cpu-throttling.rules
    rules:
    - alert: PodHighCPUThrottling
      expr: |
        100 *
        sum by (namespace, pod, container) (
          rate(container_cpu_cfs_throttled_periods_total{namespace="payments", container!="", container!="POD"}[5m])
        )
        /
        sum by (namespace, pod, container) (
          rate(container_cpu_cfs_periods_total{namespace="payments", container!="", container!="POD"}[5m])
        ) > 25
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "High CPU throttling detected"
        description: "Container {{ $labels.container }} in pod {{ $labels.namespace }}/{{ $labels.pod }} has CPU throttling above 25%."
```

### 17.3 Memory near limit

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pod-memory-alerts
  namespace: payments
spec:
  groups:
  - name: pod-memory.rules
    rules:
    - alert: PodMemoryNearLimit
      expr: |
        100 *
        sum by (namespace, pod, container) (
          container_memory_working_set_bytes{namespace="payments", container!="", container!="POD"}
        )
        /
        sum by (namespace, pod, container) (
          kube_pod_container_resource_limits{namespace="payments", resource="memory", unit="byte"}
        ) > 90
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "Pod memory is near limit"
        description: "Container {{ $labels.container }} in pod {{ $labels.namespace }}/{{ $labels.pod }} is above 90% memory limit."
```

### 17.4 OOMKilled alert

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pod-oom-alerts
  namespace: payments
spec:
  groups:
  - name: pod-oom.rules
    rules:
    - alert: PodOOMKilled
      expr: |
        kube_pod_container_status_last_terminated_reason{namespace="payments", reason="OOMKilled"} == 1
      for: 0m
      labels:
        severity: critical
      annotations:
        summary: "Pod container was OOMKilled"
        description: "Container {{ $labels.container }} in pod {{ $labels.namespace }}/{{ $labels.pod }} was terminated because of OOMKilled."
```

### 17.5 Alert design guidance

Good alerts should:

- Alert on symptoms that require action.
- Use `for:` to avoid noise.
- Include namespace, pod, container, and runbook link.
- Avoid alerting only on raw CPU high unless it maps to impact.
- Alert on throttling, memory near limit, OOMKilled, restart loops, and node pressure.

Bad alerts:

- `CPU > 80%` without context.
- `Memory > 80%` for every container regardless of limit.
- Alerting on short spikes.
- Alerting on every BestEffort pod in dev namespaces.

## 18. Remediation Patterns

### 18.1 Immediate mitigations

| Problem | Immediate mitigation |
|---|---|
| One pod CPU saturated | Scale deployment, increase HPA max, investigate logs |
| CPU throttling | Raise/remove CPU limit, scale out |
| Memory near limit | Increase limit temporarily, restart only if safe, capture diagnostics first |
| OOMKilled loop | Increase memory limit, roll back release, reduce load |
| Node MemoryPressure | Drain/cordon if needed, move workloads, add nodes |
| Batch job spike | Reduce parallelism, add schedule windows, set concurrency policy |

### 18.2 Scale deployment manually

```bash
oc scale deploy/api -n payments --replicas=5
```

### 18.3 Patch resource requests/limits

```bash
oc set resources deploy/api -n payments \
  --requests=cpu=500m,memory=512Mi \
  --limits=cpu=2,memory=1Gi
```

### 18.4 Restart workload

Use restart only as a mitigation, not root cause resolution.

```bash
oc rollout restart deploy/api -n payments
```

### 18.5 Roll back bad deployment

```bash
oc rollout history deploy/api -n payments
oc rollout undo deploy/api -n payments
```

### 18.6 Cordon and drain hot node

```bash
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data
```

Use carefully. Draining can disrupt workloads if PodDisruptionBudgets, storage, or replica counts are not ready.

### 18.7 Add HPA

```bash
oc autoscale deploy/api -n payments --min=3 --max=10 --cpu-percent=70
```

Remember: CPU-based HPA requires CPU requests.

### 18.8 Fix resource governance

Use namespace-level defaults:

- `LimitRange`
- `ResourceQuota`
- Admission policies
- GitOps validation
- CI policy checks

## 19. Production Runbooks

### 19.1 Runbook A: Alert says pod CPU is high

1. Identify pod/container.

```bash
oc adm top pod $POD -n $NS --containers
```

2. Check current pod status.

```bash
oc get pod $POD -n $NS -o wide
oc describe pod $POD -n $NS
```

3. Check CPU trend in PromQL.

```promql
sum by (container) (
  rate(container_cpu_usage_seconds_total{namespace="$NS", pod="$POD", container!="", container!="POD"}[5m])
)
```

4. Check throttling.

```promql
100 *
sum by (container) (
  rate(container_cpu_cfs_throttled_periods_total{namespace="$NS", pod="$POD", container!="", container!="POD"}[5m])
)
/
sum by (container) (
  rate(container_cpu_cfs_periods_total{namespace="$NS", pod="$POD", container!="", container!="POD"}[5m])
)
```

5. Check requests/limits.

```bash
oc get pod $POD -n $NS -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{.resources}{"\n\n"}{end}'
```

6. Check rollout.

```bash
oc rollout history deploy/<deploy> -n $NS
```

7. Decide action:

- Traffic spike: scale out.
- Throttling: raise CPU limit or remove tight limit after approval.
- Bad release: rollback.
- One bad pod: restart only after capturing logs/profiles.

### 19.2 Runbook B: Pod memory is near limit

1. Check current memory by container.

```bash
oc adm top pod $POD -n $NS --containers
```

2. Check limits.

```bash
oc get pod $POD -n $NS -o jsonpath='{range .spec.containers[*]}{.name}{"\nlimits: "}{.resources.limits}{"\nrequests: "}{.resources.requests}{"\n\n"}{end}'
```

3. Query memory percentage of limit.

```promql
100 *
sum by (container) (
  container_memory_working_set_bytes{namespace="$NS", pod="$POD", container!="", container!="POD"}
)
/
sum by (container) (
  kube_pod_container_resource_limits{namespace="$NS", pod="$POD", resource="memory", unit="byte"}
)
```

4. Check trend over 6h/24h.

5. Check OOMKilled/restarts.

```bash
oc describe pod $POD -n $NS | grep -i -A5 -B5 oom
oc logs $POD -n $NS --previous --all-containers
```

6. Decide action:

- Steady but near limit: resize resources.
- Growing trend: investigate leak.
- OOM loop: increase memory temporarily or rollback.
- Sidecar issue: tune sidecar.

### 19.3 Runbook C: Pod OOMKilled

1. Confirm OOMKilled.

```bash
oc describe pod $POD -n $NS
```

2. Check previous logs.

```bash
oc logs $POD -n $NS -c <container> --previous
```

3. Check memory limit and runtime config.

```bash
oc get pod $POD -n $NS -o yaml | grep -A20 resources:
```

4. Check historical memory before OOM.

```promql
container_memory_working_set_bytes{namespace="$NS", pod="$POD", container="<container>"}
```

5. Identify if it is leak, spike, or limit misconfiguration.

6. Mitigate:

- Increase limit if safe.
- Roll back if release-related.
- Reduce traffic.
- Fix app memory behavior.

### 19.4 Runbook D: Node MemoryPressure

1. Find affected nodes.

```bash
oc get nodes
oc describe node $NODE
```

2. Confirm MemoryPressure:

```promql
kube_node_status_condition{condition="MemoryPressure", status="true"} == 1
```

3. List pods on node.

```bash
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
```

4. Identify top memory consumers.

```bash
oc adm top pods -A --containers
```

5. Check allocatable and requested resources.

```bash
oc describe node $NODE
```

6. Mitigate:

- Remove/scale noisy workload.
- Add nodes.
- Drain node if unstable.
- Fix under-requested pods.
- Review DaemonSet overhead.

### 19.5 Runbook E: HPA not scaling while CPU is high

1. Check HPA.

```bash
oc get hpa -n $NS
oc describe hpa <hpa> -n $NS
```

2. Check CPU requests.

```bash
oc get deploy <deploy> -n $NS -o jsonpath='{range .spec.template.spec.containers[*]}{.name}{" "}{.resources.requests.cpu}{"\n"}{end}'
```

3. Check metrics availability.

```bash
oc adm top pods -n $NS
```

4. Check HPA target.

5. Check max replicas.

6. Fix:

- Add CPU requests.
- Increase max replicas.
- Fix metrics pipeline.
- Consider custom metrics if CPU is not the correct signal.

## 22. Common Mistakes

### 22.1 Using only `oc adm top`

`oc adm top` is useful but incomplete. It does not show history, throttling, OOM reason trends, or request/limit ratios.

### 22.2 Looking only at pod-level usage

Always check container-level usage. Sidecars often hide the real consumer.

### 22.3 Confusing CPU request with CPU limit

CPU request is not a cap. A container can use more CPU than requested if available.

### 22.4 Ignoring CPU throttling

A pod can show average CPU below limit while still being throttled during bursts.

### 22.5 Setting memory limit equal to observed average usage

Memory needs headroom. Average memory is not enough for GC, spikes, buffers, and native memory.

### 22.6 Using memory HPA blindly

Memory HPA is only useful when per-pod memory decreases as replicas increase. It does not fix memory leaks.

### 22.7 Restarting without collecting diagnostics

Restarting clears evidence. Before restart, collect:

- Logs.
- Previous logs.
- Pod YAML.
- Events.
- Metrics screenshot/query.
- Heap/profile if available.

### 22.8 Forgetting namespace quotas

Increasing pod limits may fail if namespace `ResourceQuota` blocks the new values.

Check:

```bash
oc describe quota -n $NS
```

### 22.9 Editing Operator-managed resources directly

Operators may revert your changes. Update the owning custom resource instead.

### 22.10 Ignoring node placement

If all hot pods land on one node due to affinity or topology rules, scaling replicas may not help.

## 23. Interview and Real-World Scenario Questions

### Q1. A pod is using 900m CPU. Is that bad?

Not enough information. Compare it with CPU request, CPU limit, throttling, latency, HPA status, number of replicas, node CPU pressure, and historical baseline.

### Q2. A pod has CPU request 200m and is using 800m. Will Kubernetes kill it?

No. CPU request is not a runtime cap. If no CPU limit prevents it and node CPU is available, it can use more than request. It may affect other workloads if under-requested.

### Q3. A pod exceeds CPU limit. What happens?

It is throttled. CPU is compressible; the container is not killed because of CPU limit violation.

### Q4. A pod exceeds memory limit. What happens?

The container can be terminated with `OOMKilled`. Memory is not handled like CPU throttling.

### Q5. Why does HPA not scale a CPU-heavy pod?

Common causes:

- CPU request missing.
- Metrics API unavailable.
- HPA max replicas reached.
- Wrong scale target.
- Pods not ready.
- CPU utilization does not exceed target based on request.

### Q6. Why is CPU throttling high even though average CPU looks low?

CFS quota is enforced over scheduling periods. Bursty workloads can be throttled within short windows even when 5-minute average CPU is below the limit.

### Q7. How do you identify memory leak using OpenShift metrics?

Graph `container_memory_working_set_bytes` over time. A leak often grows steadily, does not drop after traffic decreases, and resets after pod restart. Correlate with restarts and OOMKilled events.

### Q8. Should we remove CPU limits?

Not universally. For trusted latency-sensitive workloads, avoiding tight CPU limits may reduce throttling. For multi-tenant, untrusted, or batch workloads, limits can protect the cluster. Always follow platform policy.

### Q9. What is the difference between `container_memory_usage_bytes` and `container_memory_working_set_bytes`?

`usage_bytes` is broader cgroup memory usage and may include reclaimable cache. `working_set_bytes` is usually more useful for active memory pressure analysis because it excludes some easily reclaimable memory.

### Q10. What is the first command you run during CPU/memory incident?

A practical first sequence:

```bash
oc adm top nodes
oc adm top pods -A --containers
oc get events -A --sort-by='.lastTimestamp' | tail -50
```

Then narrow by namespace, pod, container, node, and workload owner.

100 * sum by (namespace, pod, container) (rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])) / sum by (namespace, pod, container) (kube_pod_container_resource_requests{resource="cpu", unit="core"})

# CPU percentage of limit
100 * sum by (namespace, pod, container) (rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m])) / sum by (namespace, pod, container) (kube_pod_container_resource_limits{resource="cpu", unit="core"})

# CPU throttling percentage
100 * sum by (namespace, pod, container) (rate(container_cpu_cfs_throttled_periods_total{container!="", container!="POD"}[5m])) / sum by (namespace, pod, container) (rate(container_cpu_cfs_periods_total{container!="", container!="POD"}[5m]))

# Memory percentage of request
100 * sum by (namespace, pod, container) (container_memory_working_set_bytes{container!="", container!="POD"}) / sum by (namespace, pod, container) (kube_pod_container_resource_requests{resource="memory", unit="byte"})

# Memory percentage of limit
100 * sum by (namespace, pod, container) (container_memory_working_set_bytes{container!="", container!="POD"}) / sum by (namespace, pod, container) (kube_pod_container_resource_limits{resource="memory", unit="byte"})

# OOMKilled
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1

# Restart increase
increase(kube_pod_container_status_restarts_total[1h]) > 0

# Node MemoryPressure
kube_node_status_condition{condition="MemoryPressure", status="true"} == 1

# Node CPU usage percentage
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# Node memory available percentage
100 * node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
