## 1. What “Prometheus target down” means

In Prometheus terminology, a scrapeable endpoint is an **instance**, and a group of similar instances is a **job**. During every scrape, Prometheus records special internal scrape metrics such as:

- `up{job="...", instance="..."}`
- `scrape_duration_seconds`
- `scrape_samples_scraped`
- `scrape_samples_post_metric_relabeling`

The most important one for target availability is:

```promql
up{job="<job-name>", instance="<target>"}
```

Meaning:

```text
up == 1  -> Prometheus successfully scraped the endpoint.
up == 0  -> Prometheus attempted the scrape but it failed.
absent(up{...}) -> Prometheus is not discovering that target at all, or labels changed.
```

A **target down** condition does **not always mean the application is down**. It means Prometheus could not successfully collect metrics from the endpoint. The application might still serve user traffic correctly while its metrics endpoint is broken, protected, too slow, mislabeled, or unreachable from the Prometheus pod.

### Senior-admin interpretation

When a target is down, classify it first into one of two categories:

| Category | Meaning | Typical root cause |
|---|---|---|
| Discovery failure | Target does not appear in Prometheus targets | ServiceMonitor/PodMonitor not selected, namespace not monitored, label mismatch, missing service endpoints |
| Scrape failure | Target appears but status is `Down` | Connection refused, timeout, TLS failure, HTTP 401/403/404/500, invalid metrics format, sample limit |

This classification saves time. Do not start by changing Prometheus configuration randomly. First identify whether Prometheus discovered the target.

## 2. OpenShift monitoring architecture recap

OpenShift includes a built-in monitoring stack based on Prometheus and related components. In a standard OpenShift 4.x cluster, the monitoring stack is managed by Operators, not by manual edits to Prometheus StatefulSets or generated configuration.

### Core namespaces

| Namespace | Purpose |
|---|---|
| `openshift-monitoring` | Platform monitoring stack for OpenShift and Kubernetes components |
| `openshift-user-workload-monitoring` | Optional user workload monitoring stack for application namespaces |

### Important components

| Component | Namespace | Role |
|---|---|---|
| Cluster Monitoring Operator | `openshift-monitoring` | Manages the supported OpenShift monitoring stack configuration |
| Prometheus Operator | `openshift-monitoring` | Creates and manages platform Prometheus and Alertmanager resources |
| Prometheus | `openshift-monitoring` | Scrapes platform targets and evaluates platform rules |
| Thanos Querier | `openshift-monitoring` | Aggregates/deduplicates metrics from platform and user workload Prometheus instances |
| Alertmanager | `openshift-monitoring` | Handles alerts from Prometheus |
| Prometheus Operator | `openshift-user-workload-monitoring` | Manages user workload Prometheus and Thanos Ruler |
| Prometheus user workload | `openshift-user-workload-monitoring` | Scrapes user-defined project targets |
| Thanos Ruler user workload | `openshift-user-workload-monitoring` | Evaluates user-defined rules |

### Why this matters for troubleshooting

If a platform target is down, investigate `openshift-monitoring` first. If an application target is down, investigate `openshift-user-workload-monitoring` and the application namespace.

Wrong namespace = wrong investigation.

## 3. Platform monitoring vs user workload monitoring

### Platform monitoring

Platform monitoring is enabled by default and monitors OpenShift core components such as:

- Kubernetes API server
- OpenShift API server
- etcd
- CoreDNS
- kubelets
- scheduler
- controller manager
- HAProxy/router
- image registry
- OLM
- node-exporter
- kube-state-metrics
- openshift-state-metrics

Platform monitoring resources live mostly in `openshift-monitoring` and other `openshift-*` namespaces.

### User workload monitoring

User workload monitoring is optional. It allows monitoring of application services and pods in user-defined projects using:

- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`

To enable it, a cluster administrator sets:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Verify:

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config -o yaml
oc -n openshift-user-workload-monitoring get pods
```

Expected important pods:

```text
prometheus-operator-xxxxx
prometheus-user-workload-0
prometheus-user-workload-1
thanos-ruler-user-workload-0
thanos-ruler-user-workload-1
```

If user workload monitoring is not enabled, application `ServiceMonitor` and `PodMonitor` resources will not produce usable metrics in the OpenShift monitoring stack.

## 4. How Prometheus discovers targets in OpenShift

Prometheus does not usually scrape arbitrary pods automatically. In OpenShift monitoring, target discovery normally follows this chain:

```text
ServiceMonitor
    -> selects Service by labels
        -> Service selects Pods by labels
            -> Service exposes named port
                -> Prometheus scrapes /metrics on that endpoint
```

For `PodMonitor`:

```text
PodMonitor
    -> selects Pods by labels
        -> Pod exposes named/container port
            -> Prometheus scrapes /metrics directly on pod IP
```

### ServiceMonitor chain

```text
ServiceMonitor.spec.selector.matchLabels
        must match
Service.metadata.labels

Service.spec.selector
        must match
Pod.metadata.labels

ServiceMonitor.spec.endpoints[].port
        must match
Service.spec.ports[].name

ServiceMonitor.spec.endpoints[].path
        must match
application metrics path

ServiceMonitor.spec.endpoints[].scheme
        must match HTTP/HTTPS behavior
```

### Very common mistake

Administrators often match `ServiceMonitor.spec.selector` against pod labels. That is wrong for `ServiceMonitor`.

`ServiceMonitor.spec.selector` selects **Service labels**, not pod labels.

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
```

This requires the **Service** to have:

```yaml
metadata:
  labels:
    app: myapp
```

It is not enough for only the pod to have `app: myapp`.

## 5. Fast triage checklist

Use this first when a target is down.

```bash
# 1. Identify namespace, job, instance, ServiceMonitor/PodMonitor from UI or PromQL.
oc get servicemonitor,podmonitor -A | grep -i '<name-or-app>'

# 2. Check whether target is visible in Observe -> Targets.
# Filter by Status=Down and Source=User or Platform.

# 3. Check user workload monitoring if it is an app target.
oc -n openshift-user-workload-monitoring get pods
oc -n openshift-user-workload-monitoring get prometheus

# 4. Check the ServiceMonitor/PodMonitor object.
oc -n <app-ns> get servicemonitor <sm-name> -o yaml
oc -n <app-ns> describe servicemonitor <sm-name>

# 5. Check service labels and ports.
oc -n <app-ns> get svc <svc-name> --show-labels
oc -n <app-ns> get svc <svc-name> -o yaml

# 6. Check endpoints or endpoint slices.
oc -n <app-ns> get endpoints <svc-name> -o wide
oc -n <app-ns> get endpointslice -l kubernetes.io/service-name=<svc-name> -o wide

# 7. Check pods and labels.
oc -n <app-ns> get pods --show-labels
oc -n <app-ns> describe pod <pod-name>

# 8. Test metrics endpoint from inside the cluster.
oc -n <app-ns> run curl-test --rm -it --restart=Never --image=curlimages/curl -- \
  curl -sv http://<service-name>.<app-ns>.svc:<port>/metrics

# 9. Check Prometheus Operator logs.
oc -n openshift-user-workload-monitoring logs deploy/prometheus-operator -c prometheus-operator --tail=200

# 10. Query up metric.
oc get route -n openshift-monitoring thanos-querier -o jsonpath='{.status.ingress[0].host}{"\n"}'
```

## 6. Common symptoms and what they usually mean

| Symptom in target details | Most likely meaning | First check |
|---|---|---|
| `context deadline exceeded` | Endpoint reachable but scrape did not finish before timeout, or network path stalls | `curl -m`, app latency, NetworkPolicy, exporter performance |
| `connection refused` | Nothing is listening on the target IP:port | Service port, targetPort, container port, app process |
| `no route to host` | Network path broken | node/pod networking, NetworkPolicy, endpoints |
| `server returned HTTP status 404` | Wrong metrics path | `path: /metrics` vs `/actuator/prometheus` |
| `server returned HTTP status 401` | Authentication required but not configured or token invalid | ServiceMonitor auth config and Secret |
| `server returned HTTP status 403` | Authenticated but not authorized | RBAC/token permission/exporter authorization |
| `x509: certificate signed by unknown authority` | Prometheus does not trust target certificate CA | `tlsConfig.ca`, service CA config map |
| `x509: certificate is valid for X, not Y` | TLS server name/SNI mismatch | `tlsConfig.serverName` |
| `unsupported protocol scheme` | Wrong scheme value | `scheme: http` or `https` |
| `INVALID is not a valid start token` | Endpoint returns HTML/JSON/log text, not Prometheus format | `curl /metrics` output |
| `sample limit exceeded` | Target exposes more samples than allowed | sample limit, metric cardinality |
| Target absent from UI | Discovery problem, not scrape problem | ServiceMonitor selection, namespace, labels |

## 7. Golden troubleshooting flow

### Phase 1: Identify the failing target

From the OpenShift web console:

```text
Observe -> Targets -> filter Status: Down
```

Capture:

```text
Target URL:
Namespace:
Source: Platform/User
ServiceMonitor or PodMonitor:
Job label:
Instance label:
Last scrape:
Scrape duration:
Error message:
```

From PromQL:

```promql
up == 0
```

Show labels:

```promql
up{namespace="<namespace>"} == 0
```

### Phase 2: Decide if it is discovery or scrape failure

If the target is visible and `up == 0`, it is a scrape failure.

If the target is not visible, check discovery:

```bash
oc -n <ns> get servicemonitor,podmonitor
oc -n <ns> get svc --show-labels
oc -n <ns> get endpoints,endpointslice
```

### Phase 3: Validate Kubernetes object chain

For `ServiceMonitor`:

```text
ServiceMonitor selector -> Service label -> Service selector -> Pod label -> Endpoint -> Port name -> Path -> Scheme -> Auth/TLS
```

For `PodMonitor`:

```text
PodMonitor selector -> Pod label -> Pod port -> Path -> Scheme -> Auth/TLS
```

### Phase 4: Test from the same network zone

Testing from your laptop is not enough. Prometheus scrapes from inside the cluster. Use an in-cluster debug pod.

```bash
oc -n <app-ns> run curl-test --rm -it --restart=Never --image=curlimages/curl -- sh

curl -sv http://<svc>.<app-ns>.svc:<port>/metrics
curl -skv https://<svc>.<app-ns>.svc:<port>/metrics
```

### Phase 5: Check Operator logs if discovery is suspicious

```bash
oc -n openshift-user-workload-monitoring logs deploy/prometheus-operator -c prometheus-operator --tail=300
```

Look for:

```text
skipping servicemonitor
failed to generate config
secret not found
field not supported
bearerTokenFile prohibited
```

### Phase 6: Fix the smallest incorrect object

Do not restart the whole monitoring stack unless required. Most target-down issues are fixed by correcting:

- Service labels
- Service selector
- Service port name
- ServiceMonitor endpoint port name
- metrics path
- scheme
- TLS config
- auth Secret
- NetworkPolicy
- exporter process

## 9. ServiceMonitor troubleshooting

A `ServiceMonitor` tells Prometheus how to scrape a Kubernetes Service.

### Correct minimal ServiceMonitor

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    path: /metrics
    scheme: http
    interval: 30s
    scrapeTimeout: 10s
```

Matching Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-metrics
  namespace: myapp
  labels:
    app: myapp
spec:
  selector:
    app: myapp
  ports:
  - name: metrics
    port: 8080
    targetPort: 8080
```

Matching pod labels:

```yaml
metadata:
  labels:
    app: myapp
```

### ServiceMonitor failure points

| Failure point | Check | Fix |
|---|---|---|
| ServiceMonitor not created | `oc get sm -n <ns>` | Create it in the user namespace |
| Wrong selector | `spec.selector.matchLabels` | Match Service labels |
| Wrong namespace | `metadata.namespace` | Put it in same user namespace as Service |
| Wrong endpoint port | `spec.endpoints[].port` | Use Service port **name**, not number |
| Service has no label | `oc get svc --show-labels` | Add matching label to Service |
| Service has no endpoints | `oc get endpoints` | Fix Service selector/pod readiness |
| Wrong path | target error 404 | Set `path: /metrics` or correct custom path |
| Wrong scheme | TLS/HTTP protocol error | Set `scheme: http` or `https` correctly |
| Bad auth | 401/403 | Configure `authorization`, `basicAuth`, or OAuth2 |
| Bad TLS | x509 error | Configure `tlsConfig` correctly |

### Important OpenShift behavior

In user-defined namespaces, a `ServiceMonitor` can discover services in the same namespace. Do not rely on cross-namespace discovery with `namespaceSelector` for normal user workload monitoring. Keep the `ServiceMonitor` and Service together unless your platform policy explicitly supports another design.

### Debug selector mismatch

Print ServiceMonitor selector:

```bash
oc -n $NS get sm $SM -o jsonpath='{.spec.selector.matchLabels}{"\n"}'
```

Print all Service labels:

```bash
oc -n $NS get svc --show-labels
```

Find matching Services manually:

```bash
oc -n $NS get svc -l app=myapp
```

If this returns nothing, Prometheus cannot discover the Service from that ServiceMonitor.

### Debug endpoint port mismatch

ServiceMonitor:

```yaml
spec:
  endpoints:
  - port: web
```

Service must have:

```yaml
spec:
  ports:
  - name: web
```

If Service has only:

```yaml
ports:
- port: 8080
  targetPort: 8080
```

then fix it:

```yaml
ports:
- name: web
  port: 8080
  targetPort: 8080
```

or update ServiceMonitor:

```yaml
endpoints:
- port: metrics
```

The value is a port **name**, not usually a numeric port.

## 10. PodMonitor troubleshooting

A `PodMonitor` lets Prometheus scrape pods directly without a Service.

### Correct minimal PodMonitor

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: myapp-podmonitor
  namespace: myapp
spec:
  selector:
    matchLabels:
      app: myapp
  podMetricsEndpoints:
  - port: metrics
    path: /metrics
    scheme: http
    interval: 30s
```

Pod container port:

```yaml
containers:
- name: app
  ports:
  - name: metrics
    containerPort: 8080
```

### When to use PodMonitor

Use `PodMonitor` when:

- The app has no stable Service for metrics.
- You intentionally want to scrape each pod directly.
- You are monitoring sidecars or exporters attached to pods.

Use `ServiceMonitor` when:

- Metrics are exposed through a Service.
- You want a stable Service abstraction.
- You want the usual Kubernetes Service selector chain.

### PodMonitor failure points

| Failure point | Check | Fix |
|---|---|---|
| Pod labels do not match | `oc get pods --show-labels` | Fix `spec.selector.matchLabels` |
| Wrong port name | pod `containerPort.name` | Use correct named pod port |
| Pod not running | `oc get pods` | Fix app/deployment |
| Pod not ready and filtered | pod readiness state | Fix readiness/app health |
| Wrong path/scheme | curl test | Correct endpoint config |

## 11. Service, endpoint, and pod label troubleshooting

A large percentage of OpenShift target-down incidents are not Prometheus problems. They are Kubernetes object-chain problems.

### Service label vs Service selector

Do not confuse these:

```yaml
metadata:
  labels:
    app: myapp        # selected by ServiceMonitor
spec:
  selector:
    app: myapp        # selects Pods
```

`ServiceMonitor` selects the Service using `metadata.labels`.  
`Service` selects pods using `spec.selector`.

### Check ServiceMonitor -> Service match

```bash
oc -n $NS get sm $SM -o yaml | yq '.spec.selector.matchLabels'
oc -n $NS get svc --show-labels
oc -n $NS get svc -l app=myapp
```

### Check Service -> Pod match

```bash
oc -n $NS get svc $SVC -o jsonpath='{.spec.selector}{"\n"}'
oc -n $NS get pods --show-labels
oc -n $NS get pods -l app=myapp
```

### Check endpoint population

```bash
oc -n $NS get endpoints $SVC -o wide
```

Good output:

```text
NAME            ENDPOINTS           AGE
myapp-metrics   10.128.2.15:8080    10m
```

Bad output:

```text
NAME            ENDPOINTS   AGE
myapp-metrics   <none>      10m
```

If endpoints are empty:

1. Service selector does not match pod labels.
2. Pods are not Ready.
3. Pods are terminating.
4. Target port is wrong or not exposed as expected.

### EndpointSlice check

Modern Kubernetes clusters use EndpointSlices heavily.

```bash
oc -n $NS get endpointslice -l kubernetes.io/service-name=$SVC -o wide
oc -n $NS describe endpointslice -l kubernetes.io/service-name=$SVC
```

## 12. Port, path, and scheme troubleshooting

### Port troubleshooting

Prometheus Operator expects named ports in ServiceMonitor/PodMonitor endpoint configuration.

Service:

```yaml
ports:
- name: metrics
  port: 8080
  targetPort: http-metrics
```

Deployment:

```yaml
ports:
- name: http-metrics
  containerPort: 8080
```

ServiceMonitor:

```yaml
endpoints:
- port: metrics
```

Check:

```bash
oc -n $NS get svc $SVC -o yaml | yq '.spec.ports'
oc -n $NS get deploy $APP -o yaml | yq '.spec.template.spec.containers[].ports'
oc -n $NS get sm $SM -o yaml | yq '.spec.endpoints'
```

### Path troubleshooting

Default Prometheus metrics path is often:

```text
/metrics
```

But common app paths include:

```text
/actuator/prometheus       # Spring Boot Micrometer
/q/metrics                 # Quarkus
/metrics                   # most exporters
/stats/prometheus          # some proxies/controllers
```

Symptoms:

```text
server returned HTTP status 404 Not Found
server returned HTTP status 301/302 redirect
expected a valid start token, got "<"
```

Test:

```bash
curl -sv http://$SVC.$NS.svc:8080/metrics | head
curl -sv http://$SVC.$NS.svc:8080/actuator/prometheus | head
```

Fix:

```yaml
endpoints:
- port: metrics
  path: /actuator/prometheus
```

### Scheme troubleshooting

HTTP endpoint:

```yaml
scheme: http
```

HTTPS endpoint:

```yaml
scheme: https
```

Symptoms of wrong scheme:

| Config | Actual endpoint | Error |
|---|---|---|
| `http` | HTTPS | connection reset, malformed HTTP response |
| `https` | HTTP | TLS handshake error |

Test both:

```bash
curl -sv  http://$SVC.$NS.svc:8080/metrics
curl -skv https://$SVC.$NS.svc:8443/metrics
```

## 13. TLS and certificate troubleshooting

TLS problems are common for operator metrics endpoints because many operators expose metrics on HTTPS with service-serving certificates.

### Common TLS errors

```text
x509: certificate signed by unknown authority
x509: certificate is valid for <name-a>, not <name-b>
remote error: tls: bad certificate
server gave HTTP response to HTTPS client
```

### Correct ServiceMonitor with OpenShift service CA

Many OpenShift services use the service CA bundle from:

```text
openshift-service-ca.crt
```

Example:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: my-operator-monitor
  namespace: my-operator-ns
spec:
  selector:
    matchLabels:
      app: my-operator
  endpoints:
  - port: metrics
    scheme: https
    path: /metrics
    tlsConfig:
      ca:
        configMap:
          name: openshift-service-ca.crt
          key: service-ca.crt
      serverName: my-operator-metrics.my-operator-ns.svc.cluster.local
```

### Temporary unsafe test only

For testing only:

```yaml
tlsConfig:
  insecureSkipVerify: true
```

Do not use this as a production habit. Correct CA and `serverName` are better.

### Debug TLS from curl

```bash
oc -n $NS run curl-test --rm -it --restart=Never --image=curlimages/curl -- sh

curl -vk https://$SVC.$NS.svc:8443/metrics
```

Check certificate names:

```bash
openssl s_client -connect $SVC.$NS.svc:8443 -servername $SVC.$NS.svc.cluster.local -showcerts </dev/null
```

Inside a debug pod, `openssl` might not be installed. Use a UBI pod if needed:

```bash
oc -n $NS run ubi-debug --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Install tools only if your environment allows it:

```bash
microdnf install -y openssl curl
```

### TLS root-cause mapping

| Error | Cause | Fix |
|---|---|---|
| unknown authority | Missing CA trust | Add `tlsConfig.ca` |
| cert valid for different name | SNI/serverName mismatch | Add `tlsConfig.serverName` matching cert SAN |
| HTTP response to HTTPS client | Service is HTTP, monitor uses HTTPS | Set `scheme: http` |
| TLS handshake timeout | app slow/network/policy | Check connectivity and app |

## 14. Authentication and authorization troubleshooting

Some metrics endpoints require authentication. In OpenShift, operator metrics endpoints commonly require a bearer token.

### Bearer token example

Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-metrics-token
  namespace: myapp
stringData:
  token: <token-value>
```

ServiceMonitor:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: myapp-monitor
  namespace: myapp
spec:
  selector:
    matchLabels:
      app: myapp
  endpoints:
  - port: metrics
    path: /metrics
    scheme: https
    authorization:
      type: Bearer
      credentials:
        name: my-metrics-token
        key: token
```

### Basic auth example

Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-basic-auth
  namespace: myapp
stringData:
  username: admin
  password: redhat
```

ServiceMonitor:

```yaml
endpoints:
- port: metrics
  basicAuth:
    username:
      name: my-basic-auth
      key: username
    password:
      name: my-basic-auth
      key: password
```

### Do not use bearerTokenFile

In OpenShift user workload monitoring, using `bearerTokenFile` can cause the ServiceMonitor to be rejected by the Prometheus Operator. Use `authorization.credentials` with a Secret instead.

### 401 vs 403

| HTTP status | Meaning | Fix |
|---|---|---|
| 401 Unauthorized | Missing/invalid authentication | Configure correct token/basic/OAuth |
| 403 Forbidden | Authentication accepted but lacks permission | Fix RBAC/exporter authorization |

### Debug auth manually

```bash
TOKEN=$(oc -n $NS get secret my-metrics-token -o jsonpath='{.data.token}' | base64 -d)

oc -n $NS run curl-test --rm -it --restart=Never --image=curlimages/curl -- \
  curl -skv -H "Authorization: Bearer $TOKEN" https://$SVC.$NS.svc:8443/metrics
```

If curl succeeds with token but Prometheus fails, check:

- Secret name
- Secret namespace
- key name
- ServiceMonitor endpoint auth stanza
- Prometheus Operator logs

## 15. NetworkPolicy and connectivity troubleshooting

A target can be perfectly configured but unreachable because of NetworkPolicy.

### Important concept

Prometheus user workload pods run in:

```text
openshift-user-workload-monitoring
```

If your application namespace has default-deny ingress policies, it must allow ingress from the Prometheus pods or from the monitoring namespace.

### Check policies

```bash
oc -n $NS get networkpolicy
oc -n $NS describe networkpolicy <policy-name>
```

### Check Prometheus pod labels

```bash
oc -n openshift-user-workload-monitoring get pods --show-labels
```

### Example allow policy

Adjust labels according to your cluster.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-user-workload-prometheus-to-metrics
  namespace: myapp
spec:
  podSelector:
    matchLabels:
      app: myapp
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-user-workload-monitoring
    ports:
    - protocol: TCP
      port: 8080
```

### Connectivity test from Prometheus namespace

Run debug pod in the Prometheus namespace if policy allows:

```bash
oc -n openshift-user-workload-monitoring run curl-test --rm -it --restart=Never --image=curlimages/curl -- \
  curl -sv http://$SVC.$NS.svc:8080/metrics
```

If this fails but the same curl from the application namespace succeeds, NetworkPolicy is very likely.

### DNS test

```bash
oc -n openshift-user-workload-monitoring run dns-test --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

getent hosts myapp-metrics.myapp.svc
curl -sv http://myapp-metrics.myapp.svc:8080/metrics
```

## 16. Timeout and slow scrape troubleshooting

### Symptom

```text
context deadline exceeded
net/http: request canceled while waiting for connection
Client.Timeout exceeded while awaiting headers
```

### Meaning

Prometheus attempted to scrape but did not receive a complete response before `scrapeTimeout`.

### Check scrape duration

```promql
scrape_duration_seconds{namespace="myapp"}
```

Compare with configured timeout. If scrape duration approaches timeout, the exporter is too slow or the response is too large.

### Check sample count

```promql
scrape_samples_scraped{namespace="myapp"}
```

A sudden increase can indicate high cardinality or too many metrics.

### Curl with timing

```bash
oc -n openshift-user-workload-monitoring run curl-test --rm -it --restart=Never --image=curlimages/curl -- \
  curl -s -w '\nDNS:%{time_namelookup} Connect:%{time_connect} TLS:%{time_appconnect} TTFB:%{time_starttransfer} Total:%{time_total}\n' \
  -o /tmp/metrics.out http://$SVC.$NS.svc:8080/metrics
```

### Count response size and lines

```bash
wc -l /tmp/metrics.out
wc -c /tmp/metrics.out
```

### Fix options

| Cause | Fix |
|---|---|
| Exporter slow due to expensive collection | Optimize exporter, reduce collectors, cache metrics |
| Too many samples | Reduce metrics/cardinality, apply limits carefully |
| Network latency | Check CNI, NetworkPolicy, node pressure |
| Too short timeout | Increase `scrapeTimeout` but keep it lower than interval |
| App CPU throttling | Increase resources or tune app |

Example:

```yaml
endpoints:
- port: metrics
  interval: 30s
  scrapeTimeout: 10s
```

Do not set `scrapeTimeout` equal to or greater than `interval`.

## 17. Metric format, sample limit, and cardinality troubleshooting

### Invalid metric format

Prometheus expects text exposition format or OpenMetrics format. If the endpoint returns HTML, JSON, login page, proxy error, or logs, scrape fails.

Test:

```bash
curl -sv http://$SVC.$NS.svc:8080/metrics | head -50
```

Good output:

```text
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",code="200"} 123
```

Bad output:

```html
<html>
  <title>Login</title>
```

or:

```json
{"status":"ok"}
```

### High cardinality

High cardinality happens when labels have too many unique values, for example:

```text
user_id
session_id
request_id
customer_id
pod_uid
container_id
url_full_path
```

Bad metric:

```text
http_request_duration_seconds{user_id="92736281",request_id="abc-123",path="/api/order/923762"} 0.2
```

Better metric:

```text
http_request_duration_seconds{method="GET",route="/api/order/{id}",status="200"} 0.2
```

### Check sample count

```promql
topk(20, scrape_samples_scraped)
```

By namespace:

```promql
topk(20, sum by (namespace, job) (scrape_samples_scraped))
```

### Check series count by job

```promql
topk(20, count by (job) ({__name__=~".+"}))
```

### Limits can make scrapes fail

Prometheus supports scrape limits such as sample, label, label name length, label value length, and target limits. If a target exceeds enforced limits, the scrape can be marked failed. Do not blindly raise limits. First identify whether the exporter is producing uncontrolled metrics.

## 22. TargetDown alert investigation runbook

### Alert meaning

`TargetDown` usually means one or more Prometheus targets have been down for a configured time window. The alert labels typically include namespace, service, job, or endpoint labels depending on the target.

```text
alertname:
```


Record the exact error message.


## 23. Real production scenarios

### Scenario 1: Target absent because Service label is missing

**Symptom:** ServiceMonitor exists but no target appears.

```bash
oc -n payments get sm payments-monitor -o yaml
oc -n payments get svc --show-labels
```

ServiceMonitor:

```yaml
selector:
  matchLabels:
    app: payments
```

Service:

```yaml
metadata:
  labels:
    component: api
```

**Fix:** Add matching label to Service.

```bash
oc -n payments label svc payments-metrics app=payments
```

Verify:

```bash
oc -n payments get svc -l app=payments
```

### Scenario 2: Target down with connection refused

**Symptom:** Target appears but error says connection refused.

Check Service:

```bash
oc -n payments get svc payments-metrics -o yaml
```

Service points to targetPort `9090`, but application listens on `8080`.

**Fix:** Correct Service targetPort.

```yaml
ports:
- name: metrics
  port: 8080
  targetPort: 8080
```

### Scenario 3: Target down with 404

**Symptom:** Error `server returned HTTP status 404`.

Curl:

```bash
curl -sv http://payments-metrics.payments.svc:8080/metrics
```

App exposes Spring Boot metrics at:

```text
/actuator/prometheus
```

**Fix:**

```yaml
endpoints:
- port: metrics
  path: /actuator/prometheus
```

### Scenario 4: Target down with x509 unknown authority

**Symptom:** HTTPS metrics endpoint uses service CA certificate.

**Fix:** Configure CA bundle.

```yaml
endpoints:
- port: metrics
  scheme: https
  tlsConfig:
    ca:
      configMap:
        name: openshift-service-ca.crt
        key: service-ca.crt
    serverName: payments-metrics.payments.svc.cluster.local
```

### Scenario 5: Target down due to NetworkPolicy

**Symptom:** Curl from app namespace works, curl from `openshift-user-workload-monitoring` fails.

**Fix:** Add ingress allow rule from monitoring namespace to metrics port.

### Scenario 6: ServiceMonitor rejected because of bearerTokenFile

**Symptom:** Target absent. Prometheus Operator logs show skipping ServiceMonitor because it uses `bearerTokenFile`.

**Fix:** Replace `bearerTokenFile` with Secret-based `authorization.credentials`.

### Scenario 7: Target flapping

**Symptom:** `changes(up[30m]) > 2`.

Possible causes:

- exporter occasionally slow
- pod restarts
- readiness probe toggling
- node pressure
- DNS or network issues
- NetworkPolicy update churn

Check:

```bash
oc -n <ns> get pods
oc -n <ns> describe pod <pod>
oc -n <ns> get events --sort-by=.lastTimestamp | tail -50
```

PromQL:

```promql
changes(up{namespace="<ns>", job="<job>"}[30m])
max_over_time(scrape_duration_seconds{namespace="<ns>", job="<job>"}[30m])
```

## 24. Preventive best practices

### Use consistent labels

Recommended Service and Deployment labels:

```yaml
app.kubernetes.io/name: myapp
app.kubernetes.io/instance: myapp-prod
app.kubernetes.io/component: api
app.kubernetes.io/part-of: payments
```

Then ServiceMonitor selector:

```yaml
selector:
  matchLabels:
    app.kubernetes.io/name: myapp
    app.kubernetes.io/component: api
```

### Always name ports

Bad:

```yaml
ports:
- port: 8080
```

Good:

```yaml
ports:
- name: metrics
  port: 8080
  targetPort: metrics
```

### Keep metrics endpoint lightweight

Metrics endpoint should:

- avoid slow database queries
- avoid external API calls
- avoid per-user labels
- avoid per-request IDs
- complete well below scrape timeout

### Separate app traffic and metrics ports

This is often cleaner:

```yaml
ports:
- name: http
  containerPort: 8080
- name: metrics
  containerPort: 9090
```

### Use service CA for HTTPS

For internal HTTPS, use OpenShift service-serving certificates and configure `tlsConfig.ca` in monitors.

### Test every monitor during deployment

Add CI/CD checks:

```bash
oc -n $NS get sm
oc -n $NS get svc -l app=$APP
oc -n $NS get endpoints $SVC
curl http://$SVC.$NS.svc:8080/metrics
```

### Avoid unsupported monitoring modifications

Do not manually edit generated resources in:

```text
openshift-monitoring
openshift-user-workload-monitoring
```

Use supported ConfigMaps and CRDs.

### Build a standard runbook

Every team should document:

```text
metrics path:
metrics port:
scheme:
auth method:
ServiceMonitor name:
PromQL job label:
expected sample count:
expected scrape duration:
owner/team:
```

## 25. Interview and exam-style notes

### Key explanation

A Prometheus target down issue in OpenShift is investigated by checking whether the target is discovered and whether the scrape succeeds. Discovery problems are usually caused by ServiceMonitor/PodMonitor selector mismatch, namespace/user workload monitoring configuration, or missing endpoints. Scrape problems are usually caused by wrong port/path/scheme, NetworkPolicy, TLS, authentication, timeout, invalid metrics format, or exporter performance.

### Common exam command set

```bash
oc get co monitoring
oc -n openshift-monitoring get pods
oc -n openshift-user-workload-monitoring get pods
oc -n <ns> get servicemonitor,podmonitor
oc -n <ns> get svc --show-labels
oc -n <ns> get endpoints -o wide
oc -n <ns> get pods --show-labels
oc -n <ns> describe servicemonitor <name>
oc -n openshift-user-workload-monitoring logs deploy/prometheus-operator -c prometheus-operator
```

### Explain `up == 0`

`up == 0` means Prometheus discovered the target but the last scrape failed. It is different from the target being absent, which usually means discovery failed.

### Explain ServiceMonitor selection

`ServiceMonitor.spec.selector` matches Service labels. The Service then uses `spec.selector` to select pods. The endpoint port in ServiceMonitor should match the Service port name.

### Explain target down with empty endpoints

If the Service has no endpoints, Prometheus might discover the Service but has no healthy backend pod to scrape. Fix the Service selector, pod labels, or pod readiness.

### Explain target down with 401

HTTP 401 means authentication is required or invalid. Configure `authorization.credentials`, `basicAuth`, or OAuth2 using Secrets in the same namespace as the ServiceMonitor.

### Explain target down with x509

Prometheus does not trust the certificate or the server name does not match. Configure `tlsConfig.ca` and `tlsConfig.serverName`, or fix the certificate SAN.

## Final senior-admin summary

Troubleshooting Prometheus target down in OpenShift is not about immediately restarting Prometheus. A strong administrator follows the object chain and failure class:

```text
Is target discovered?
  No  -> ServiceMonitor/PodMonitor/namespace/selector discovery issue.
  Yes -> Scrape failure.

For scrape failure:
  Check exact error -> connectivity -> endpoint -> path -> port -> scheme -> TLS -> auth -> format -> timeout -> cardinality.
```

Most incidents are fixed by correcting the Kubernetes objects that feed discovery, not by changing Prometheus itself.
