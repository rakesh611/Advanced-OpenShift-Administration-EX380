# Thanos Querier in OpenShift Monitoring and Metrics

**Audience:** Advanced OpenShift Administration / DO380-style learning / 10+ years Linux-DevOps experience  
**Scope:** OpenShift Container Platform 4.x monitoring stack, especially OpenShift 4.19+ / Monitoring Stack for Red Hat OpenShift 4.x  
**Component focus:** `thanos-querier` in the `openshift-monitoring` namespace

---

## 1. Executive summary

**Thanos Querier** is the query aggregation layer in the OpenShift monitoring stack. In normal OpenShift operations, you do not query every Prometheus replica directly. Instead, the web console, API clients, and observability tools query **Thanos Querier**, which exposes a Prometheus-compatible API and combines metrics from the underlying Prometheus data sources.

In OpenShift, Thanos Querier is important because it provides:

- A **single query endpoint** for cluster metrics.
- **Aggregation** across platform monitoring and, when enabled, user workload monitoring.
- **HA deduplication** of metrics from multiple Prometheus replicas.
- A **multi-tenant access layer** protected by OpenShift authentication and authorization.
- A Prometheus-compatible HTTP API for `/api/v1/query`, `/api/v1/query_range`, `/api/v1/metadata`, labels, series, and related query operations.

A senior OpenShift administrator should understand that Thanos Querier is **not** the component that scrapes metrics, stores metrics, evaluates most platform rules, sends alerts, or provides long-term storage by itself. It is a **stateless query frontend/aggregator** over data sources that implement the Thanos StoreAPI, such as Prometheus sidecars.

## 2. Where Thanos Querier fits in OpenShift monitoring

OpenShift installs the default monitoring stack in the `openshift-monitoring` project during cluster installation. The major default components include:

- Cluster Monitoring Operator (`cluster-monitoring-operator`)
- Prometheus Operator
- Prometheus for platform metrics (`prometheus-k8s`)
- Alertmanager
- kube-state-metrics
- openshift-state-metrics
- node-exporter
- monitoring web console plugin
- Metrics Server
- Telemeter Client
- **Thanos Querier**

When user workload monitoring is enabled, OpenShift also deploys components in `openshift-user-workload-monitoring`, including a user workload Prometheus stack and Thanos Ruler.

High-level flow:

```text
Platform and workload targets
        |
        | scrape
        v
Prometheus replicas
        |
        | local TSDB + sidecar StoreAPI
        v
Thanos Querier
        |
        | Prometheus HTTP API / OpenShift Console Observe UI
        v
Admins, developers, Grafana, scripts, automation
```

Thanos Querier is therefore the **query access point**. Prometheus remains the **scrape, TSDB, and rule engine** for platform metrics, while Thanos Querier provides the consolidated view.

## 3. Why OpenShift uses Thanos Querier

### 3.1 The HA Prometheus problem

OpenShift runs Prometheus in a highly available style. Multiple Prometheus replicas can scrape the same targets. This improves availability, but it creates query complexity:

- Directly load balancing across Prometheus replicas can show gaps if one replica restarted or missed samples.
- Querying both Prometheus replicas without deduplication can produce duplicate series.
- Users and tools should not need to know which Prometheus replica has the best data.

Thanos Querier solves this by querying multiple backends and optionally deduplicating the returned series.

### 3.2 Single API endpoint

Instead of users remembering several endpoints, OpenShift exposes Thanos Querier as the main metrics query endpoint.

Typical API route lookup:

```bash
oc get route -n openshift-monitoring thanos-querier \
  -o jsonpath='{.status.ingress[0].host}'
```

Typical API request:

```bash
THANOS_ROUTE=$(oc get route -n openshift-monitoring thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_ROUTE}/api/v1/query?query=up"
```

### 3.3 Multi-tenant visibility

OpenShift does not simply expose raw Thanos to everyone. Access is controlled through OpenShift authentication and RBAC. A cluster administrator can see cluster-level metrics. A developer or project user sees only the metrics they are authorized to view.

For user workload metrics, the user must have the right project permissions and usually must select or scope the query to a project in the console.

## 4. Core concepts

### 4.1 Thanos Query / Querier

Upstream Thanos calls this component `thanos query`. It implements the Prometheus HTTP v1 API and evaluates PromQL by pulling data from StoreAPI backends.

In OpenShift, this component appears as:

```bash
oc -n openshift-monitoring get deploy thanos-querier
oc -n openshift-monitoring get pods -l app.kubernetes.io/name=thanos-query
```

Labels can vary by version, so always confirm with:

```bash
oc -n openshift-monitoring get deploy thanos-querier -o yaml | less
oc -n openshift-monitoring get pods --show-labels | grep thanos
```

### 4.2 StoreAPI

Thanos Querier does not directly read every Prometheus TSDB file. It queries backends that expose the Thanos **StoreAPI** over gRPC. In OpenShift, Prometheus pods normally include a Thanos sidecar/container or related integration that makes Prometheus data queryable through Thanos.

Conceptual flow:

```text
PromQL request
   -> Thanos Querier
      -> fan out to StoreAPI backends
      -> fetch matching series/chunks
      -> deduplicate if enabled
      -> evaluate PromQL
      -> return Prometheus-compatible JSON response
```

### 4.3 Deduplication

Deduplication merges equivalent time series from HA replicas. Two Prometheus replicas may scrape the same target and produce almost identical series, differing only by a replica label. Thanos Querier can treat that replica label as an HA replica indicator and return one logical series.

Example concept:

```text
Without deduplication:
up{job="kubelet", instance="node1", prometheus_replica="prometheus-k8s-0"} 1
up{job="kubelet", instance="node1", prometheus_replica="prometheus-k8s-1"} 1

With deduplication:
up{job="kubelet", instance="node1"} 1
```

The exact internal replica labels are managed by the OpenShift monitoring stack. You should not normally override Thanos command-line flags manually because the Cluster Monitoring Operator owns the deployment.

### 4.4 Statelessness

Thanos Querier is stateless. It does not need persistent storage. If a Thanos Querier pod restarts, metrics data is not lost because the metrics are stored by Prometheus or other StoreAPI backends.

Operational meaning:

- Scaling or restarting Thanos Querier does not delete metrics.
- Query availability depends on Querier pods, proxies, routes, and backend StoreAPI reachability.
- Data retention is controlled by Prometheus or external storage, not by Querier.

### 4.5 Prometheus-compatible API

Thanos Querier supports common Prometheus API paths. In OpenShift, these are protected by bearer-token authentication and RBAC.

Common paths:

```text
/api/v1/query
/api/v1/query_range
/api/v1/metadata
/api/v1/labels
/api/v1/label/<label_name>/values
/api/v1/series
```

Example instant query:

```bash
curl -k -G \
  -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=cluster_version' \
  "https://${THANOS_ROUTE}/api/v1/query"
```

Example range query:

```bash
curl -k -G \
  -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=sum(rate(container_cpu_usage_seconds_total{namespace="openshift-apiserver"}[5m]))' \
  --data-urlencode "start=$(date -u -d '1 hour ago' +%FT%TZ)" \
  --data-urlencode "end=$(date -u +%FT%TZ)" \
  --data-urlencode 'step=60s' \
  "https://${THANOS_ROUTE}/api/v1/query_range"
```

## 6. Thanos Querier vs Prometheus vs Thanos Ruler

| Component | Main responsibility | Stores metrics? | Scrapes targets? | Evaluates alert/rules? | Typical namespace |
|---|---:|---:|---:|---:|---|
| Prometheus | Scrape, store, query, platform rules | Yes | Yes | Yes | `openshift-monitoring` or `openshift-user-workload-monitoring` |
| Thanos Querier | Query aggregation and deduplication | No | No | No | `openshift-monitoring` |
| Alertmanager | Alert routing and notifications | Stores alert state/silences if persistent storage configured | No | No | `openshift-monitoring`, optional user workload alertmanager |
| Thanos Ruler | Rule/alert evaluation for user-defined projects | Limited rule data/retention | No | Yes | `openshift-user-workload-monitoring` |
| Metrics Server | Kubernetes resource metrics API | No long-term TSDB | Pulls resource metrics | No | `openshift-monitoring` |

Important distinction:

- Prometheus is the **source of truth for recently scraped time-series data**.
- Thanos Querier is the **federated query layer**.
- Thanos Ruler is for **rule evaluation**, especially user workload alerting.

## 7. How a query works internally

Assume the user runs this PromQL query from Observe → Metrics:

```promql
sum by (namespace) (rate(container_cpu_usage_seconds_total[5m]))
```

The flow is:

1. The browser sends the query to the OpenShift console backend / monitoring API path.
2. OpenShift authentication confirms the user identity.
3. OpenShift authorization decides what namespaces/projects the user is allowed to access.
4. The request reaches Thanos Querier.
5. Thanos Querier identifies which StoreAPI backends can satisfy the query.
6. It sends StoreAPI requests to the relevant Prometheus-sidecar backends.
7. It receives matching time series.
8. It deduplicates HA replica data if applicable.
9. It evaluates the PromQL expression.
10. It returns a Prometheus API-compatible JSON response.
11. The console plots the result.


### 8.4 Query API server request rate

```bash
curl -k -G \
  -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=sum(rate(apiserver_request_total[5m])) by (verb,code)' \
```

```bash

  -H "Authorization: Bearer $(oc whoami -t)" \
```

For user workload metrics, verify that user workload monitoring is enabled and that your account has permissions for the target project.


If this returns empty, do not immediately blame Thanos Querier. Check whether the application metric endpoint is scraped by Prometheus first.

## 9. RBAC and authentication

### 9.1 Bearer token authentication

For the Thanos Querier API route, use an OpenShift bearer token:

```bash
oc whoami -t
```

Then pass it as:

```bash
-H "Authorization: Bearer $(oc whoami -t)"
```

Common mistakes:

- Calling the route without a bearer token.
- Using basic authentication against the API route.
- Using an expired or wrong-context token.
- Querying a project that the user cannot view.
- Testing from a pod with a service account that lacks monitoring permissions.

### 9.2 Granting API access

A cluster administrator can grant monitoring API access with the appropriate monitoring role. Example pattern:

```bash
oc adm policy add-cluster-role-to-user cluster-monitoring-metrics-api <user> \
  -n openshift-monitoring
```

For project-scoped monitoring access, bind the appropriate monitoring role or view permissions in the target namespace.

Example:

```bash
oc adm policy add-role-to-user view <user> -n my-app
```

Always validate with the exact user:

```bash
oc auth can-i get pods -n my-app --as=<user>
oc auth can-i get --raw /api/v1/namespaces/openshift-monitoring/services/thanos-querier --as=<user>
```

The exact `oc auth can-i --raw` path can vary depending on how the API path is exposed, so treat this as an authorization investigation pattern rather than the only test.

## 10. Configuring Thanos Querier in OpenShift

Supported configuration belongs under the `thanosQuerier` key in `cluster-monitoring-config`.

Supported categories include:

- `enableRequestLogging`
- `logLevel`
- `enableCORS`
- `nodeSelector`
- `resources`
- `tolerations`
- `topologySpreadConstraints`

Do not assume every upstream Thanos flag is supported directly in OpenShift. OpenShift exposes only selected fields through the Cluster Monitoring Operator configuration API.

### 10.1 Example: resources and log level

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    thanosQuerier:
      logLevel: info
      resources:
        requests:
          cpu: 200m
          memory: 500Mi
        limits:
          cpu: 500m
          memory: 1Gi
```

Apply or edit:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

Verify rollout:

```bash
oc -n openshift-monitoring rollout status deploy/thanos-querier
oc -n openshift-monitoring get pods | grep thanos-querier
```

### 10.2 Example: debug logging for troubleshooting

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    thanosQuerier:
      logLevel: debug
```

Verify configured args or logs:

```bash
oc -n openshift-monitoring get deploy thanos-querier -o yaml | grep -i log
oc -n openshift-monitoring logs deploy/thanos-querier -c thanos-query --tail=100
```

After troubleshooting, return to a normal log level:

```yaml
thanosQuerier:
  logLevel: info
```

### 10.3 Example: enable request logging temporarily

Use request logging only for troubleshooting because it can create high-volume logs.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    thanosQuerier:
      enableRequestLogging: true
      logLevel: info
```

Generate a test query:

```bash
THANOS_ROUTE=$(oc get route -n openshift-monitoring thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

curl -k -G \
  -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=cluster_version' \
  "https://${THANOS_ROUTE}/api/v1/query"
```

Read logs:

```bash
POD=$(oc -n openshift-monitoring get pods | awk '/thanos-querier/ {print $1; exit}')
oc -n openshift-monitoring logs "$POD" -c thanos-query --tail=200
```

Disable request logging after investigation:

```yaml
thanosQuerier:
  enableRequestLogging: false
  logLevel: info
```

### 10.4 Example: schedule Thanos Querier on infra nodes

First label infra nodes:

```bash
oc label node <node_name> node-role.kubernetes.io/infra=
```

If infra nodes are tainted, add tolerations.

Example config:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    thanosQuerier:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

Verification:

```bash
oc -n openshift-monitoring get pods -o wide | grep thanos-querier
oc describe pod -n openshift-monitoring <thanos_querier_pod>
```

If pods remain Pending, check:

```bash
oc -n openshift-monitoring describe pod <thanos_querier_pod> | sed -n '/Events:/,$p'
oc get nodes --show-labels | grep infra
oc describe node <infra_node> | grep -i taint -A2
```

### 10.5 Example: topology spread constraints

Use this when you want Thanos Querier replicas spread across zones or worker nodes.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    thanosQuerier:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app.kubernetes.io/name: thanos-query
```

Validate actual labels before using the selector:

```bash
oc -n openshift-monitoring get pods --show-labels | grep thanos-querier
```

## 12. Practical PromQL for OpenShift admins

### 12.1 Cluster version

```promql
cluster_version
```

### 12.2 API server request rate

```promql
sum by (verb, code) (rate(apiserver_request_total[5m]))
```

### 12.3 API server 5xx errors

```promql
sum by (resource, verb) (rate(apiserver_request_total{code=~"5.."}[5m]))
```

### 12.4 Node readiness

```promql
kube_node_status_condition{condition="Ready",status="true"}
```

### 12.5 Node CPU usage percentage

```promql
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

### 12.6 Container CPU usage by namespace

```promql
sum by (namespace) (rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m]))
```

### 12.7 Container memory usage by namespace

```promql
sum by (namespace) (container_memory_working_set_bytes{container!="",pod!=""})
```

### 12.8 Top pods by CPU in a namespace

```promql
topk(10, sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="my-app",container!=""}[5m])))
```

### 12.9 Top pods by memory in a namespace

```promql
topk(10, sum by (pod) (container_memory_working_set_bytes{namespace="my-app",container!=""}))
```

### 12.10 Target health

```promql
up == 0
```

For one namespace:

```promql
up{namespace="my-app"} == 0
```

### 12.11 Prometheus scrape sample volume

```promql
sum by (job) (rate(scrape_samples_scraped[5m]))
```

### 12.12 High-cardinality investigation

```promql
topk(20, count by (__name__) ({__name__=~".+"}))
```

Use carefully. This can be expensive on large clusters.

## 13. Performance engineering for Thanos Querier

### 13.1 What makes queries slow

Common reasons:

- Large time range with small step.
- High-cardinality metrics.
- Regex matchers on wide labels.
- Unscoped queries across all namespaces.
- Expensive joins such as `group_left` or `group_right`.
- Large `topk` or `count by` queries over all metrics.
- Duplicate or poorly labeled application metrics.
- Slow or overloaded Prometheus StoreAPI backends.
- Insufficient CPU or memory for Thanos Querier.

### 13.2 Bad query pattern

```promql
count by (pod, container, image, id, name, endpoint, instance) ({__name__=~".+"})
```

Problems:

- Queries all metrics.
- Groups by too many labels.
- Can explode result cardinality.
- Can overload the browser and Thanos Querier.

### 13.3 Better query pattern

Scope by namespace, metric name, and time window:

```promql
topk(10, sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="my-app",container!=""}[5m])))
```

### 13.4 Query tuning checklist

Before increasing resources, ask:

1. Is the query scoped by namespace, job, pod, route, or service?
2. Is the time range reasonable?
3. Is the step reasonable for the time range?
4. Can a recording rule precompute the expensive expression?
5. Is the dashboard refreshing too frequently?
6. Are application metrics exposing unbounded labels?
7. Are multiple dashboards hitting Thanos Querier at the same time?
8. Did a recent deployment introduce new high-cardinality metrics?

### 13.5 When to increase Thanos Querier resources

Increase resources when:

- Thanos Querier pods are OOMKilled.
- CPU throttling is visible.
- Query latency increases under normal query patterns.
- Console Observe metrics frequently time out.
- Request logs show legitimate heavy usage.
- Prometheus backends are healthy but Querier is the bottleneck.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    thanosQuerier:
      resources:
        requests:
          cpu: 500m
          memory: 1Gi
        limits:
          cpu: 2
          memory: 4Gi
```

Tune according to cluster size and workload. Do not copy values blindly into production.

```bash
  'https://thanos-querier.openshift-monitoring.svc:9091/api/v1/query?query=cluster_version'
```

If internal service works but external route fails, investigate route, router, ingress, certificates, OAuth proxy, or external network/DNS.

## 15. Troubleshooting scenarios

### Scenario 1: `401 Unauthorized` from Thanos Querier route

Symptoms:

```text
{"error":"unauthorized"}
```

Likely causes:

- Missing bearer token.
- Expired token.
- Wrong OpenShift context.
- Calling with basic auth instead of bearer token.

Fix:

```bash
oc whoami
oc whoami -t

curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://${THANOS_ROUTE}/api/v1/query?query=up"
```

### Scenario 2: `403 Forbidden`

Likely causes:

- User authenticated but lacks monitoring access.
- User is querying a project they cannot view.
- Service account token has insufficient permissions.

Check:

```bash
oc auth can-i get pods -n <project> --as=<user>
oc auth can-i view project <project> --as=<user>
```

Grant appropriate access:

```bash
oc adm policy add-role-to-user view <user> -n <project>
```

For platform metrics API access, use the monitoring API role pattern:

```bash
oc adm policy add-cluster-role-to-user cluster-monitoring-metrics-api <user> \
  -n openshift-monitoring
```

### Scenario 3: Query returns empty result for user application

Do not start with Thanos. Validate the scrape path.

Checklist:

```bash
oc -n <app_ns> get pod,svc,endpoints
oc -n <app_ns> get servicemonitor,podmonitor
oc -n openshift-user-workload-monitoring get pods
```

Check common issues:

- User workload monitoring not enabled.
- ServiceMonitor selector does not match the Service labels.
- Service port name does not match `endpoints.port` in ServiceMonitor.
- Application does not expose `/metrics`.
- NetworkPolicy blocks Prometheus from scraping the target.
- TLS or scheme mismatch.
- User lacks permission to view the namespace.

### Scenario 4: Observe → Metrics times out

Likely causes:

- Query too expensive.
- Browser overloaded by huge graph output.
- Thanos Querier CPU/memory too small.
- Prometheus backend slow.
- High-cardinality application metrics.

Actions:

```bash
oc -n openshift-monitoring top pod | grep thanos
oc -n openshift-monitoring top pod | grep prometheus
oc -n openshift-monitoring logs deploy/thanos-querier -c thanos-query --tail=200
```

Tune query:

- Add namespace selector.
- Increase query step.
- Reduce time range.
- Use `topk` after aggregation.
- Build recording rules for dashboard-heavy calculations.
- Temporarily enable request logging to find expensive queries.

### Scenario 5: Thanos Querier pods Pending

Likely causes:

- Invalid `nodeSelector`.
- Taint without matching toleration.
- Insufficient node resources.
- Topology spread constraints too strict.

Check:

```bash
oc -n openshift-monitoring describe pod <thanos_pod> | sed -n '/Events:/,$p'
oc get nodes --show-labels
oc describe node <node> | grep -i taints -A2
```

Fix the `cluster-monitoring-config` scheduling settings.

### Scenario 6: Monitoring ClusterOperator degraded after config change

Likely causes:

- Invalid YAML under `data.config.yaml`.
- Unsupported field under `thanosQuerier`.
- Wrong indentation.
- Invalid `logLevel` value.
- Invalid resource quantity.

Check:

```bash
oc get co monitoring
oc describe co monitoring
oc -n openshift-monitoring logs deploy/cluster-monitoring-operator --tail=200
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml
```

Validate YAML locally before applying:

```bash
oc apply --dry-run=client -f cluster-monitoring-config.yaml
```

Remember: YAML can be syntactically valid but semantically unsupported by CMO.

### Scenario 7: Duplicate metrics or unexpected duplicate series

Likely causes:

- Deduplication disabled for a query using `dedup=false`.
- Replica labels changed or conflicting external labels.
- Multiple ServiceMonitors scrape the same target with different labels.
- Application exposes duplicate metrics.

Investigate:

```promql
count by (__name__, job, instance, namespace, pod) (up)
```

For a specific metric:

```promql
count by (namespace, pod, instance, job) (your_metric_name)
```

Also inspect ServiceMonitor/PodMonitor duplication:

```bash
oc get servicemonitor,podmonitor -A | grep <app_or_namespace>
```

### Scenario 8: High memory/OOMKilled in Thanos Querier

Check:

```bash
oc -n openshift-monitoring get pod <thanos_pod> -o jsonpath='{.status.containerStatuses[*].lastState}' | jq .
oc -n openshift-monitoring describe pod <thanos_pod> | grep -i oom -A5 -B5
```

Actions:

- Find expensive queries.
- Temporarily enable request logging.
- Increase memory request/limit.
- Educate dashboard authors.
- Reduce dashboard refresh frequency.
- Create recording rules.
- Reduce application metric cardinality.

## 16. Common senior-admin mistakes

### Mistake 1: Querying Prometheus directly instead of Thanos Querier

Direct Prometheus queries can be useful for debugging, but for the supported OpenShift user experience and multi-source view, use Thanos Querier.

### Mistake 2: Manually editing generated deployments

Wrong:

```bash
oc -n openshift-monitoring edit deploy thanos-querier
```

Why wrong:

- CMO can revert the change.
- The operator might become degraded.
- Upgrades can behave unpredictably.
- Red Hat support generally expects supported config paths.

Correct:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

### Mistake 3: Thinking Thanos Querier is long-term storage

Thanos has long-term storage components upstream, but OpenShift Thanos Querier by itself is not long-term object storage. It queries configured backends. For long-term retention, design remote write or an external Thanos architecture separately.

### Mistake 4: Increasing resources before fixing query design

If a dashboard runs huge unscoped PromQL every 15 seconds, increasing Thanos Querier memory only delays the next incident.

### Mistake 5: Ignoring user RBAC

An admin may see metrics while a developer sees nothing. This can be correct behavior if the developer lacks access to the namespace or monitoring API path.

### Mistake 6: ServiceMonitor port mismatch

This is one of the most common user workload monitoring issues.

Service:

```yaml
ports:
- name: metrics
  port: 8080
```

ServiceMonitor must reference the port **name**, not necessarily the numeric port:

```yaml
endpoints:
- port: metrics
```

## 18. Production hardening recommendations

### 18.1 Keep configuration supported

Only configure fields exposed by `cluster-monitoring-config`. Avoid direct edits to managed resources.

### 18.2 Separate monitoring workloads

For production clusters, consider scheduling monitoring components on infra nodes using `nodeSelector` and `tolerations`, especially in large clusters.

### 18.3 Size resources based on query behavior

Resource needs depend on:

- Number of nodes.
- Number of namespaces.
- Number of scraped targets.
- Metric cardinality.
- Dashboard refresh frequency.
- Number of active users/tools querying metrics.
- Query complexity.

### 18.4 Control high cardinality at source

Bad application metric labels:

```text
user_id
session_id
request_id
transaction_id
pod_uid when not needed
full URL path with IDs
```

Better:

```text
method
route template
status code
namespace
service
pod only when operationally required
```

### 18.5 Use recording rules

For expensive dashboard queries, precompute:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: app-recording-rules
  namespace: my-app
spec:
  groups:
  - name: app.rules
    rules:
    - record: namespace:container_cpu_usage_seconds:rate5m
      expr: sum by (namespace) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))
```

Then dashboard query becomes cheaper:

```promql
namespace:container_cpu_usage_seconds:rate5m{namespace="my-app"}
```

### 18.6 Keep request logging temporary

Request logging helps during incidents but can generate large logs. Enable it only while diagnosing heavy queries, then disable it.

### 18.7 Watch monitoring operator after changes

Every monitoring config change should be followed by:

```bash
oc get co monitoring
oc -n openshift-monitoring get pods
oc -n openshift-monitoring logs deploy/cluster-monitoring-operator --tail=100
```

## 19. Thanos Querier and external observability tools

### 19.1 Grafana-style access

External tools can query Thanos Querier using the Prometheus API, but they must authenticate with a valid bearer token and must be authorized for the metrics they request.

Example data source URL:

```text
https://<thanos_querier_route>
```

Header:

```text
Authorization: Bearer <token>
```

Do not use a personal admin token permanently in production dashboards. Prefer a dedicated service account with minimum required access, token lifecycle management, and strong audit controls.

### 19.2 CORS

OpenShift exposes an `enableCORS` option for Thanos Querier configuration. Use it only when you have a real browser-based integration requirement and you understand the security impact.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    thanosQuerier:
      enableCORS: true
```

Default best practice: leave CORS disabled unless required.

## 20. Exam/interview-style Q&A

### Q1. What is Thanos Querier in OpenShift?

It is the Prometheus-compatible query aggregation layer for OpenShift monitoring. It aggregates and optionally deduplicates platform and user workload metrics behind a single multi-tenant query interface.

### Q2. Does Thanos Querier scrape metrics?

No. Prometheus scrapes metrics. Thanos Querier queries metrics from StoreAPI backends.

### Q3. Does Thanos Querier store metrics?

No. It is stateless. Metrics are stored by Prometheus or external long-term storage systems.

### Q4. Why not query Prometheus directly?

Direct Prometheus querying can miss the complete HA/multi-source view and bypass the intended OpenShift access pattern. Thanos Querier provides a single deduplicated query interface.

### Q5. What namespace contains Thanos Querier?

`openshift-monitoring`.

### Q6. How do you get the Thanos Querier route?

```bash
oc get route -n openshift-monitoring thanos-querier \
  -o jsonpath='{.status.ingress[0].host}'
```

### Q7. How do you access the API?

Use bearer token authentication:

```bash
curl -k -H "Authorization: Bearer $(oc whoami -t)" \
  "https://<route>/api/v1/query?query=up"
```

### Q8. Which ConfigMap configures Thanos Querier?

`cluster-monitoring-config` in `openshift-monitoring`.

Component key:

```yaml
thanosQuerier:
```

### Q9. Name supported Thanos Querier config options in OpenShift.

Common supported options include `enableRequestLogging`, `logLevel`, `enableCORS`, `nodeSelector`, `resources`, `tolerations`, and `topologySpreadConstraints`.

### Q10. How do you troubleshoot slow queries?

Check query scope, time range, step, cardinality, Thanos Querier resource usage, Prometheus backend health, dashboards, and temporarily enable request logging.

### Q11. What does deduplication solve?

It merges equivalent series from HA Prometheus replicas so users see one logical series instead of duplicate replica series and can avoid gaps when one replica is temporarily unavailable.

### Q12. If user workload metrics are missing, where do you check first?

Check whether user workload monitoring is enabled, the app exposes metrics, ServiceMonitor/PodMonitor selectors match, endpoints exist, Prometheus is scraping the target, and the user has RBAC access.

## 22. Senior-level mental model

Think of OpenShift monitoring as four planes:

### 22.1 Collection plane

Prometheus, ServiceMonitors, PodMonitors, exporters, node-exporter, kube-state-metrics, openshift-state-metrics.

### 22.2 Storage plane

Prometheus TSDB and any configured external remote-write/long-term system.

### 22.3 Query plane

Thanos Querier, PromQL, Observe UI, API clients, dashboards.

### 22.4 Alerting plane

Prometheus rules, Thanos Ruler for user-defined projects, Alertmanager routing and receivers.

Thanos Querier belongs to the **query plane**. Many incidents blamed on Thanos Querier are actually collection-plane or RBAC issues.

## 24. Lab exercise

### Goal

Configure Thanos Querier resource requests/limits, enable temporary request logging, run a query, read logs, then disable request logging.

### Task 1: Backup current config

```bash
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml \
  > cluster-monitoring-config.backup.yaml
```

### Task 2: Edit config

```bash
oc -n openshift-monitoring edit cm cluster-monitoring-config
```

Add:

```yaml
data:
  config.yaml: |
    thanosQuerier:
      logLevel: info
      enableRequestLogging: true
      resources:
        requests:
          cpu: 200m
          memory: 500Mi
        limits:
          cpu: 500m
          memory: 1Gi
```

If `config.yaml` already contains settings, merge carefully. Do not overwrite existing unrelated monitoring configuration.

### Task 3: Verify rollout

```bash
oc get co monitoring
oc -n openshift-monitoring rollout status deploy/thanos-querier
oc -n openshift-monitoring get pods | grep thanos-querier
```

### Task 4: Run query

```bash
THANOS_ROUTE=$(oc get route -n openshift-monitoring thanos-querier \
  -o jsonpath='{.status.ingress[0].host}')

curl -k -G \
  -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode 'query=cluster_version' \
```

## 25. Summary

Thanos Querier is the OpenShift monitoring query aggregation layer. It gives administrators and authorized users a single Prometheus-compatible endpoint for querying metrics across OpenShift platform monitoring and, when enabled, user workload monitoring.

Remember these senior-admin points:

- Thanos Querier is stateless.
- It does not scrape or store metrics.
- It aggregates and deduplicates data from Prometheus/StoreAPI backends.
- OpenShift protects it with authentication and RBAC.
- Access the API with a bearer token.
- Configure it only through `cluster-monitoring-config` under `thanosQuerier`.
- Use request logging temporarily for troubleshooting.
- Slow metrics pages are often caused by expensive PromQL or high-cardinality application metrics, not only by Thanos Querier resource limits.
- If user metrics are missing, first validate ServiceMonitor/PodMonitor, endpoints, user workload monitoring, and RBAC.
