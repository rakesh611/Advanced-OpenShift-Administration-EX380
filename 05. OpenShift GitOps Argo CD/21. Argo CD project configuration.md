# Argo CD Project Configuration in OpenShift GitOps

**Audience:** Advanced OpenShift / Kubernetes administrators with production experience  
**Context:** Red Hat OpenShift GitOps, Argo CD, multi-team/multi-namespace administration  
**Goal:** Understand how to design, configure, secure, operate, and troubleshoot Argo CD `AppProject` resources in OpenShift.

---

## 1. What is an Argo CD Project?

In Argo CD, a **Project** is represented by the Kubernetes custom resource named **`AppProject`**.

An `AppProject` is a logical security and governance boundary for Argo CD `Application` resources. It answers four major questions:

1. **What source repositories are trusted?**
2. **Where can applications deploy?**
3. **Which Kubernetes/OpenShift resource kinds can be created?**
4. **Who can perform actions on applications inside this project?**

In production OpenShift GitOps, an `AppProject` is not only a grouping object. It is one of the most important controls for preventing accidental or malicious deployments.

Think of it as:

```text
Git repository + target cluster/namespace + allowed resource kinds + Argo CD RBAC = AppProject boundary
```

Without a properly configured `AppProject`, a user who can create or modify an Argo CD `Application` might be able to deploy resources into the wrong namespace, use an untrusted repository, create privileged Kubernetes resources, or bind sensitive OpenShift permissions.

---

## 2. Why AppProject matters in OpenShift GitOps

OpenShift GitOps uses Argo CD to reconcile declared state from Git into OpenShift. In a single-admin lab cluster, using the default project might look harmless. In a real enterprise OpenShift cluster, this becomes dangerous.

A production OpenShift cluster usually has:

- multiple teams,
- multiple namespaces,
- multiple environments such as `dev`, `test`, `stage`, and `prod`,
- platform-owned namespaces,
- restricted security policies,
- Operators and CRDs,
- secrets, routes, RBAC, quotas, limit ranges, and network policies,
- compliance requirements,
- Git repositories with different trust levels.

`AppProject` allows you to divide this environment into controlled GitOps zones.

Example project model:

```text
openshift-gitops namespace
│
├── AppProject: payments-dev
│   ├── sourceRepos: https://git.example.com/payments/*
│   ├── destinations: dev namespaces only
│   ├── allowed resources: Deployment, Service, Route, ConfigMap, Secret
│   └── roles: payments-devs can sync dev apps
│
├── AppProject: payments-prod
│   ├── sourceRepos: approved production config repo only
│   ├── destinations: prod namespace only
│   ├── syncWindows: maintenance windows
│   ├── GPG signature verification
│   └── roles: SRE group can sync; developers read-only
│
└── AppProject: cluster-config
    ├── sourceRepos: platform-config repo only
    ├── destinations: selected cluster namespaces
    ├── allowed cluster resources: Namespace, ClusterRole, etc.
    └── roles: platform-admins only
```

## 3. AppProject vs Application

A common confusion is the difference between an `Application` and an `AppProject`.

| Object | Purpose |
|---|---|
| `Application` | Defines one deployable workload or configuration unit. It points to Git, a path/chart/kustomize config, a revision, and a destination. |
| `AppProject` | Defines the security and governance boundary within which one or more `Application` resources must operate. |

Example relationship:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-api-dev
  namespace: openshift-gitops
spec:
  project: payments-dev
  source:
    repoURL: https://git.example.com/platform/payments-gitops.git
    targetRevision: main
    path: apps/payments-api/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
```

Here, `spec.project: payments-dev` means Argo CD checks the `payments-dev` `AppProject` before allowing this application to deploy.

The `Application` must satisfy the project rules:

```text
Application source repo must be allowed by AppProject.spec.sourceRepos
Application destination must be allowed by AppProject.spec.destinations
Application resource kinds must be allowed by AppProject resource allow/deny rules
Application namespace must be allowed by AppProject.spec.sourceNamespaces when using applications in any namespace
User action must be allowed by Argo CD RBAC / project role policies
```

## 4. Important OpenShift GitOps namespace model

In a standard OpenShift GitOps installation, the default Argo CD instance runs in:

```text
openshift-gitops
```

Common objects are usually created there:

```bash
oc get argocd -n openshift-gitops
oc get appproject -n openshift-gitops
oc get applications.argoproj.io -n openshift-gitops
```

### 4.1 Default cluster-scoped instance

The default OpenShift GitOps Argo CD instance in `openshift-gitops` is commonly called the default cluster-scoped Argo CD instance. It can be configured with permissions to manage resources outside its own namespace.

For many application deployment scenarios, the target application namespace must be labeled so that the Argo CD instance can manage it.

Example:

```bash
oc label namespace payments-dev argocd.argoproj.io/managed-by=openshift-gitops
```

Then verify:

```bash
oc get ns payments-dev --show-labels
```

Expected label:

```text
argocd.argoproj.io/managed-by=openshift-gitops
```

### 4.2 User-defined Argo CD instances

You can also run a user-defined Argo CD instance in another namespace, for example:

```text
spring-petclinic
team-a-gitops
platform-gitops
```

A user-defined instance is useful when you want stronger separation between teams or when the default `openshift-gitops` namespace should remain platform-only.

Important security principle:

```text
Access to the Argo CD control plane namespace is effectively Argo CD admin-level access.
```

Do not grant ordinary application teams write access to the namespace that hosts the Argo CD control plane.

## 5. The default AppProject

Argo CD automatically creates a project named:

```text
default
```

By default, the `default` project is very permissive. A typical default project allows:

```yaml
spec:
  sourceRepos:
    - '*'
  destinations:
    - namespace: '*'
      server: '*'
  clusterResourceWhitelist:
    - group: '*'
      kind: '*'
```

This is acceptable for initial testing but risky in production.

### 5.1 Why the default project is dangerous

If users can create applications against the default project, they might be able to:

- deploy from any Git repository,
- deploy into any namespace,
- deploy cluster-scoped resources,
- create RBAC resources,
- deploy CRDs or Operator resources,
- bypass intended team/environment isolation.

### 5.2 Production recommendation: lock down the default project

In mature OpenShift GitOps environments, you should normally lock down the default project and create dedicated projects per team/environment.

Example lockdown:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: default
  namespace: openshift-gitops
spec:
  sourceRepos: []
  sourceNamespaces: []
  destinations: []
  namespaceResourceBlacklist:
    - group: '*'
      kind: '*'
```

Apply:

```bash
oc apply -f default-project-lockdown.yaml
```

Verify:

```bash
oc get appproject default -n openshift-gitops -o yaml
```

Any application still using `spec.project: default` should be migrated to a properly scoped project.

## 6. AppProject full structure

A production `AppProject` commonly contains these sections:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-dev
  namespace: openshift-gitops
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  description: Payments team development project

  sourceRepos:
    - https://git.example.com/payments/*

  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev

  clusterResourceWhitelist: []

  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
    - group: ''
      kind: ConfigMap
    - group: ''
      kind: Secret
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy

  orphanedResources:
    warn: true

  roles:
    - name: dev-sync
      description: Allow payments developers to view and sync development applications
      groups:
        - openshift-payments-devs
      policies:
        - p, proj:payments-dev:dev-sync, applications, get, payments-dev/*, allow
        - p, proj:payments-dev:dev-sync, applications, sync, payments-dev/*, allow
```

Now let us break down every important field.

## 7. `metadata.name`

`metadata.name` is the Argo CD project name used by applications.

Example:

```yaml
metadata:
  name: payments-dev
```

Application reference:

```yaml
spec:
  project: payments-dev
```

Recommended naming patterns:

```text
<team>-<environment>
<business-unit>-<environment>
<platform-domain>
<cluster-purpose>
```

Examples:

```text
payments-dev
payments-prod
retail-stage
platform-config
security-baseline
observability
```

Avoid vague names:

```text
project1
apps
test
misc
common
```

A project name should clearly communicate its security boundary.

---

## 8. `metadata.namespace`

In OpenShift GitOps, `AppProject` resources are normally created in the Argo CD control plane namespace.

For the default OpenShift GitOps instance:

```yaml
metadata:
  namespace: openshift-gitops
```

Important:

```text
The AppProject namespace is where Argo CD control plane resources live.
It is not necessarily the namespace where workloads are deployed.
```

Workload destination is controlled separately by:

```yaml
spec:
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
```

## 9. `finalizers`

Example:

```yaml
metadata:
  finalizers:
    - resources-finalizer.argocd.argoproj.io
```

The finalizer prevents accidental deletion of a project while applications still depend on it.

Production recommendation:

Use the finalizer for important projects:

```yaml
finalizers:
  - resources-finalizer.argocd.argoproj.io
```

Why this matters:

- prevents deleting a project that still has applications,
- avoids leaving applications in broken state,
- protects GitOps control-plane integrity.

Troubleshooting deletion:

```bash
oc get applications.argoproj.io -A | grep <project-name>
oc get appproject <project-name> -n openshift-gitops -o yaml
```

Do not remove finalizers blindly unless you understand what is still referencing the project.

## 10. `spec.description`

Example:

```yaml
spec:
  description: Payments team development workloads only
```

This is simple but important for large environments.

A good description should include:

- owning team,
- allowed environment,
- intended target namespaces,
- whether cluster-scoped resources are allowed,
- whether the project is for application workloads or cluster configuration.

Example:

```yaml
spec:
  description: >-
    Payments team DEV project. Allows deployment from the payments GitOps repo
    into payments-dev namespace only. Cluster-scoped resources are not allowed.
```

## 11. `spec.sourceRepos`

`sourceRepos` defines which Git or Helm repositories applications in this project can use.

Example:

```yaml
spec:
  sourceRepos:
    - https://git.example.com/payments/payments-gitops.git
```

Wildcard example:

```yaml
spec:
  sourceRepos:
    - https://git.example.com/payments/*
```

Allow everything:

```yaml
spec:
  sourceRepos:
    - '*'
```

Production warning:

```text
Avoid sourceRepos: ['*'] for production projects.
```

A repository is part of your trust boundary. If a project allows untrusted repositories, Argo CD might deploy unreviewed or malicious manifests.

### 11.1 Deny rules in sourceRepos

Argo CD supports negation rules using `!`.

Example:

```yaml
spec:
  sourceRepos:
    - '!https://git.example.com/payments/experimental/**'
    - 'https://git.example.com/payments/**'
```

Meaning:

```text
Allow repositories under https://git.example.com/payments/**
except https://git.example.com/payments/experimental/**
```

A source is valid only when:

```text
At least one allow rule matches
AND
No deny rule matches
```

Avoid confusing patterns. Prefer explicit allow lists whenever possible.

### 11.2 Repository examples by environment

Development project:

```yaml
sourceRepos:
  - https://git.example.com/payments/*
```

Production project:

```yaml
sourceRepos:
  - https://git.example.com/platform/production-gitops.git
```

Platform configuration project:

```yaml
sourceRepos:
  - https://git.example.com/platform/cluster-config.git
```

### 11.3 Source repo security checklist

For production:

- use private repositories,
- require merge reviews,
- protect production branches,
- require signed commits where appropriate,
- restrict who can modify Kustomize overlays and Helm values,
- do not allow arbitrary user forks,
- avoid using `HEAD` for production unless the branch is protected,
- prefer pinned tags or release branches for critical environments.

## 12. `spec.destinations`

`destinations` defines where applications in the project are allowed to deploy.

Example:

```yaml
spec:
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
```

This allows deployment to the `payments-dev` namespace on the in-cluster Kubernetes API.

### 12.1 Destination fields

```yaml
- server: https://kubernetes.default.svc
  namespace: payments-dev
```

| Field | Meaning |
|---|---|
| `server` | Kubernetes API server URL for target cluster. In-cluster is usually `https://kubernetes.default.svc`. |
| `name` | Optional cluster name registered in Argo CD. |
| `namespace` | Target namespace where resources are deployed. |

### 12.2 Single namespace destination

```yaml
destinations:
  - server: https://kubernetes.default.svc
    namespace: payments-dev
```

Use this for strict team namespace isolation.

### 12.3 Multiple namespace destination

```yaml
destinations:
  - server: https://kubernetes.default.svc
    namespace: payments-dev
  - server: https://kubernetes.default.svc
    namespace: payments-test
```

Use this when one team owns multiple non-production namespaces.

### 12.4 Wildcard namespace destination

```yaml
destinations:
  - server: https://kubernetes.default.svc
    namespace: payments-*
```

This allows namespaces like:

```text
payments-dev
payments-test
payments-stage
payments-feature-a
```

Use wildcard destinations carefully. They are convenient but broaden the project boundary.

### 12.5 Deny destination example

```yaml
destinations:
  - namespace: '!kube-system'
    server: '*'
  - namespace: '!openshift-*'
    server: '*'
  - namespace: '*'
    server: '*'
```

This allows most destinations except selected critical namespaces.

Production recommendation:

Prefer explicit allow lists instead of broad allow with deny exceptions.

### 12.6 Multi-cluster destination example

```yaml
destinations:
  - name: dev-cluster
    namespace: payments-dev
  - name: stage-cluster
    namespace: payments-stage
```

For multi-cluster OpenShift GitOps, keep environment separation clear. Do not allow a dev project to deploy to production clusters.

## 13. AppProject does not replace Kubernetes RBAC

This is a critical administrator point.

`AppProject` restricts what Argo CD is allowed to do logically, but the Argo CD application controller still needs Kubernetes/OpenShift permissions to create resources in the target namespace or cluster.

Both must be correct:

```text
OpenShift RBAC / namespace label / Argo CD instance permissions
AND
AppProject source/destination/resource rules
```

Example failure cases:

| Problem | Symptom |
|---|---|
| Namespace not labeled for default OpenShift GitOps instance | Argo CD cannot manage resources in namespace. |
| AppProject destination missing namespace | Application validation fails or sync denied. |
| Argo CD service account lacks permission | Sync fails with Kubernetes RBAC forbidden error. |
| Resource kind blocked by AppProject | Application fails with project permission error. |

Troubleshooting commands:

```bash
oc get ns payments-dev --show-labels
oc get appproject payments-dev -n openshift-gitops -o yaml
oc get application payments-api-dev -n openshift-gitops -o yaml
oc auth can-i create deployments -n payments-dev --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Service account names can vary by instance name. Check actual service accounts:

```bash
oc get sa -n openshift-gitops | grep argocd
```

## 14. Resource allow/deny controls

`AppProject` can restrict which Kubernetes/OpenShift resource kinds applications can create.

There are two scopes:

1. **Cluster-scoped resources**
2. **Namespaced resources**

Cluster-scoped examples:

```text
Namespace
ClusterRole
ClusterRoleBinding
CustomResourceDefinition
StorageClass
PersistentVolume
SecurityContextConstraints
```

Namespaced examples:

```text
Deployment
Service
Route
ConfigMap
Secret
NetworkPolicy
Role
RoleBinding
ResourceQuota
LimitRange
ServiceAccount
```

## 15. `clusterResourceWhitelist`

`clusterResourceWhitelist` defines cluster-scoped resources that are allowed.

Example: allow only Namespace creation:

```yaml
spec:
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
```

The empty group `''` means the core Kubernetes API group.

Example: allow selected OpenShift cluster-scoped resources:

```yaml
clusterResourceWhitelist:
  - group: ''
    kind: Namespace
  - group: rbac.authorization.k8s.io
    kind: ClusterRole
  - group: rbac.authorization.k8s.io
    kind: ClusterRoleBinding
```

Production warning:

Allowing cluster-scoped resources is powerful. Do it only for platform-admin projects.

Application team projects should usually have:

```yaml
clusterResourceWhitelist: []
```

or omit cluster-scoped permissions entirely, depending on your policy model.

---

## 16. `clusterResourceBlacklist`

`clusterResourceBlacklist` denies specific cluster-scoped resources.

Example:

```yaml
clusterResourceBlacklist:
  - group: ''
    kind: Namespace
    name: kube-*
```

This denies Namespaces whose names match `kube-*`.

Use cases:

- prevent creation of namespaces with protected prefixes,
- deny CRD creation from application projects,
- deny cluster RBAC creation outside platform projects.

Production guidance:

For platform projects, use an explicit whitelist. For application projects, do not permit cluster-scoped resources unless there is a strong operational reason.

---

## 17. Restrict cluster resources by name

Argo CD supports restricting cluster-scoped resources by resource name.

Example: allow only namespaces starting with `team1-`:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team1-platform
  namespace: openshift-gitops
spec:
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
      name: team1-*
```

This is useful for self-service namespace creation while preventing teams from creating arbitrary namespaces.

OpenShift example:

```yaml
clusterResourceWhitelist:
  - group: ''
    kind: Namespace
    name: payments-*
```

Then the team can create:

```text
payments-dev
payments-test
payments-feature-x
```

But cannot create:

```text
openshift-config
kube-system
security-admin
```

## 18. `namespaceResourceWhitelist`

`namespaceResourceWhitelist` defines which namespaced resources are allowed. If you use a whitelist approach, anything not listed should be considered denied.

Strict application workload example:

```yaml
namespaceResourceWhitelist:
  - group: apps
    kind: Deployment
  - group: apps
    kind: StatefulSet
  - group: ''
    kind: Service
  - group: ''
    kind: ConfigMap
  - group: ''
    kind: Secret
  - group: ''
    kind: ServiceAccount
  - group: route.openshift.io
    kind: Route
  - group: networking.k8s.io
    kind: NetworkPolicy
```

This model is strong for regulated environments because the administrator declares exactly what is allowed.

### 18.1 Common OpenShift namespaced API groups

| Resource | API group | Scope |
|---|---|---|
| Pod | `''` | Namespaced |
| Service | `''` | Namespaced |
| ConfigMap | `''` | Namespaced |
| Secret | `''` | Namespaced |
| ServiceAccount | `''` | Namespaced |
| PersistentVolumeClaim | `''` | Namespaced |
| Deployment | `apps` | Namespaced |
| StatefulSet | `apps` | Namespaced |
| DaemonSet | `apps` | Namespaced |
| Job | `batch` | Namespaced |
| CronJob | `batch` | Namespaced |
| Route | `route.openshift.io` | Namespaced |
| BuildConfig | `build.openshift.io` | Namespaced |
| ImageStream | `image.openshift.io` | Namespaced |
| DeploymentConfig | `apps.openshift.io` | Namespaced |
| NetworkPolicy | `networking.k8s.io` | Namespaced |
| Role | `rbac.authorization.k8s.io` | Namespaced |
| RoleBinding | `rbac.authorization.k8s.io` | Namespaced |
| ResourceQuota | `''` | Namespaced |
| LimitRange | `''` | Namespaced |
| HorizontalPodAutoscaler | `autoscaling` | Namespaced |
| PodDisruptionBudget | `policy` | Namespaced |

### 18.2 Example: allow normal app deployment but block RBAC

```yaml
namespaceResourceWhitelist:
  - group: apps
    kind: Deployment
  - group: ''
    kind: Service
  - group: ''
    kind: ConfigMap
  - group: ''
    kind: Secret
  - group: route.openshift.io
    kind: Route
  - group: networking.k8s.io
    kind: NetworkPolicy
```

This blocks `Role`, `RoleBinding`, `ResourceQuota`, and `LimitRange` unless explicitly listed.

Good for teams where namespace-level governance is platform-controlled.

### 18.3 Example: app team can manage NetworkPolicy

```yaml
namespaceResourceWhitelist:
  - group: apps
    kind: Deployment
  - group: ''
    kind: Service
  - group: networking.k8s.io
    kind: NetworkPolicy
```

This is useful when application teams own east-west traffic rules.

## 19. `namespaceResourceBlacklist`

`namespaceResourceBlacklist` denies selected namespaced resources while allowing others.

Example:

```yaml
namespaceResourceBlacklist:
  - group: rbac.authorization.k8s.io
    kind: RoleBinding
  - group: rbac.authorization.k8s.io
    kind: Role
  - group: ''
    kind: ResourceQuota
  - group: ''
    kind: LimitRange
```

Use this model when you want broad application flexibility but still block sensitive objects.

Production warning:

A blacklist model is easier to misconfigure because new CRDs or new resource types might become deployable unless blocked. For high-security environments, prefer whitelist.

## 20. Whitelist vs blacklist design

### Whitelist model

```text
Default deny. Only listed resources are allowed.
```

Best for:

- production,
- regulated environments,
- platform-controlled namespaces,
- teams with limited deployment scope,
- clusters with many Operators and CRDs.

### Blacklist model

```text
Default allow. Only listed resources are denied.
```

Best for:

- development,
- trusted internal platform teams,
- lower-risk clusters,
- faster onboarding environments.

### Recommendation

Use one consistent model per project. Avoid mixing whitelist and blacklist heavily in the same project unless you have tested and documented the behavior.

For most enterprise OpenShift environments:

```text
Application teams: namespaceResourceWhitelist + no clusterResourceWhitelist
Platform teams: explicit clusterResourceWhitelist + controlled destinations
Default project: locked down
```

## 21. OpenShift-specific resource risk examples

### 21.1 `Route`

OpenShift `Route` exposes applications externally.

API group:

```yaml
- group: route.openshift.io
  kind: Route
```

Allowing `Route` means teams can expose services through OpenShift ingress.

Control considerations:

- hostname policy,
- TLS termination type,
- wildcard routes,
- external exposure review,
- route annotations.

### 21.2 `RoleBinding`

API group:

```yaml
- group: rbac.authorization.k8s.io
  kind: RoleBinding
```

Allowing RoleBinding can be risky because users might bind powerful roles to service accounts.

Example risk:

```yaml
kind: RoleBinding
roleRef:
  kind: ClusterRole
  name: admin
```

Even though `RoleBinding` is namespaced, it can reference a `ClusterRole`.

### 21.3 `ServiceAccount`

Service accounts are often needed by workloads.

Risk appears when combined with:

- RoleBinding,
- SecurityContextConstraints access,
- image pull secrets,
- token access.

### 21.4 `SecurityContextConstraints`

`SecurityContextConstraints` is OpenShift-specific and cluster-scoped.

API group:

```text
security.openshift.io
```

Kind:

```text
SecurityContextConstraints
```

Application projects should almost never be allowed to manage SCCs. SCC binding is usually done by platform admins using `oc adm policy add-scc-to-user` or a controlled platform GitOps project.

### 21.5 `CustomResourceDefinition`

CRDs are cluster-scoped and powerful.

Do not allow CRD creation in normal application projects. Operators or platform teams should manage CRDs.

### 21.6 Operator custom resources

OpenShift Operators introduce many CRDs. Some namespaced custom resources are still powerful because their Operator reconciles cluster-wide behavior.

Example risk categories:

- storage CRs,
- networking CRs,
- security CRs,
- monitoring CRs,
- service mesh CRs,
- logging CRs.

Do not allow arbitrary CRs just because they are namespaced. Understand what the Operator does.

## 22. `sourceNamespaces`

`sourceNamespaces` controls where Argo CD `Application` resources are allowed to live when using the **Applications in any namespace** model.

Do not confuse this with destination namespaces.

```text
sourceNamespaces = namespaces where Application CRs are created
spec.destinations.namespace = namespaces where workloads are deployed
```

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: project-one
  namespace: openshift-gitops
spec:
  sourceNamespaces:
    - dev
    - app-team-*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: app-team-*
  sourceRepos:
    - https://git.example.com/app-team/*
```

This allows Application CRs to be created in namespaces such as:

```text
dev
app-team-1
app-team-2
```

But the workloads are governed by `destinations`.

### 22.1 Required OpenShift GitOps configuration

For applications in non-control-plane namespaces, OpenShift GitOps requires configuration in multiple places:

1. `ArgoCD` custom resource
2. `AppProject` custom resource
3. `Application` custom resource
4. Kubernetes/OpenShift RBAC for users
5. Namespace labels/Operator-created bindings depending on the instance model

Example `ArgoCD` CR:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: example
  namespace: spring-petclinic
spec:
  sourceNamespaces:
    - dev
    - app-team-*
```

Example `AppProject`:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: project-one
  namespace: openshift-gitops
spec:
  sourceNamespaces:
    - dev
    - app-team-*
  destinations:
    - name: '*'
      namespace: '*'
      server: '*'
  sourceRepos:
    - '*'
```

Example `Application` in a non-control-plane namespace:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-configs
  namespace: dev
spec:
  project: project-one
  source:
    repoURL: https://git.example.com/platform/cluster-configs.git
    targetRevision: main
    path: clusters/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: dev
```

### 22.2 Security warning for sourceNamespaces

Never add user-controlled namespaces to a privileged project such as `default`.

Dangerous example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: default
  namespace: openshift-gitops
spec:
  sourceNamespaces:
    - '*'
  sourceRepos:
    - '*'
  destinations:
    - server: '*'
      namespace: '*'
  clusterResourceWhitelist:
    - group: '*'
      kind: '*'
```

This can create a privilege escalation path.

Safer model:

```text
One non-privileged AppProject per team or environment.
Each AppProject allows only that team’s Application source namespaces.
No user AppProject grants access to openshift-gitops namespace.
Default project is locked down.
```

## 24. Project role policies

Argo CD RBAC policy format is Casbin-style:

```text
p, <subject>, <resource>, <action>, <object>, <effect>
```

Example:

```text
p, proj:payments-dev:dev-sync, applications, sync, payments-dev/*, allow
```

Breakdown:

| Part | Meaning |
|---|---|
| `p` | Policy line |
| `proj:payments-dev:dev-sync` | Project role subject |
| `applications` | Argo CD resource type |
| `sync` | Action |
| `payments-dev/*` | Object scope: all apps in project `payments-dev` |
| `allow` | Effect |

### 24.1 Common application actions

| Action | Meaning |
|---|---|
| `get` | View application |
| `sync` | Sync application |
| `update` | Modify application |
| `delete` | Delete application |
| `action/*` | Run resource actions |
| `override` | Override parameters during sync |

Example read-only role:

```yaml
roles:
  - name: read-only
    groups:
      - openshift-payments-viewers
    policies:
      - p, proj:payments-dev:read-only, applications, get, payments-dev/*, allow
```

Example sync-only CI role:

```yaml
roles:
  - name: ci-sync
    description: CI pipeline can sync only payments-api-dev
    policies:
      - p, proj:payments-dev:ci-sync, applications, get, payments-dev/payments-api-dev, allow
      - p, proj:payments-dev:ci-sync, applications, sync, payments-dev/payments-api-dev, allow
```

Example admin-like project role:

```yaml
roles:
  - name: project-admin
    groups:
      - openshift-payments-sre
    policies:
      - p, proj:payments-dev:project-admin, applications, *, payments-dev/*, allow
```

Use project-admin roles carefully.

## 26. JWT tokens for project roles

Project roles can have JWT tokens. This is useful for CI/CD systems that need limited Argo CD API access.

Example CLI flow:

```bash
argocd proj role create payments-dev ci-sync
argocd proj role add-policy payments-dev ci-sync \
  --action sync \
  --permission allow \
  --object payments-dev/payments-api-dev

argocd proj role create-token payments-dev ci-sync -e 1h
```

The token should be stored securely in your CI secret manager.

Important points:

- token is shown only when created,
- token can be time-limited,
- token permissions follow the project role policy,
- changing the role policy affects future authorization,
- deleting the token entry revokes it.

Example declarative token metadata:

```yaml
roles:
  - name: ci-sync
    policies:
      - p, proj:payments-dev:ci-sync, applications, sync, payments-dev/payments-api-dev, allow
    jwtTokens:
      - iat: 1710000000
```

Do not commit actual token values into Git.

## 27. `syncWindows`

`syncWindows` restrict when applications in a project may sync.

Use cases:

- block production syncs during business hours,
- allow syncs only during maintenance windows,
- allow emergency manual syncs,
- control change-freeze periods,
- prevent automated sync during audits or major events.

Example: allow production sync only at night:

```yaml
syncWindows:
  - kind: allow
    schedule: '0 22 * * *'
    duration: 2h
    applications:
      - '*-prod'
    manualSync: true
```

Example: deny sync during business hours:

```yaml
syncWindows:
  - kind: deny
    schedule: '0 9 * * 1-5'
    duration: 8h
    applications:
      - '*'
    manualSync: false
```

### 27.1 `kind`

```yaml
kind: allow
```

or

```yaml
kind: deny
```

### 27.2 `schedule`

Cron-style schedule.

Example:

```yaml
schedule: '0 22 * * *'
```

### 27.3 `duration`

Example:

```yaml
duration: 2h
```

### 27.4 `manualSync`

If `manualSync: true`, manual sync may still be allowed according to the window behavior.

Example:

```yaml
manualSync: true
```

### 27.5 `syncOverrun`

Example:

```yaml
syncOverrun: true
```

This controls whether a sync that started inside a window can continue after the window ends, or whether a sync that started before a deny window can continue during the deny window.

### 27.6 Production pattern

For production:

```yaml
syncWindows:
  - kind: deny
    schedule: '0 9 * * 1-5'
    duration: 8h
    applications:
      - '*'
    manualSync: false
  - kind: allow
    schedule: '0 22 * * 1-5'
    duration: 2h
    applications:
      - '*'
    manualSync: true
```

Test sync windows in non-production first. Misconfigured sync windows can block emergency changes.

## 28. `orphanedResources`

Orphaned resources are namespaced Kubernetes resources that exist in a namespace but are not managed by any Argo CD application.

Example:

```yaml
orphanedResources:
  warn: true
```

This helps detect:

- manually created resources,
- old resources left after refactoring,
- resources created by failed deployment tools,
- resources outside GitOps control,
- configuration drift.

Example with ignore rules:

```yaml
orphanedResources:
  warn: true
  ignore:
    - group: ''
      kind: Secret
      name: builder-dockercfg-*
    - group: ''
      kind: Secret
      name: default-token-*
```

OpenShift namespaces often contain automatically generated resources, so ignore rules may be necessary.

### 28.1 Performance warning

Do not enable orphaned resource monitoring broadly on huge namespaces with many unmanaged resources unless you have tested performance impact.

Best use:

```text
Enable it on well-scoped application namespaces, not broad platform namespaces.
```

## 29. GnuPG signature verification at project level

Argo CD can enforce Git commit signature verification at project level.

Concept:

```text
Only sync commits signed by trusted GPG keys.
```

Use cases:

- production deployment integrity,
- regulated environments,
- prevent unauthorized Git changes from being deployed,
- ensure GitOps commits come from trusted identities or pipelines.

High-level flow:

1. Import trusted GPG public keys into Argo CD.
2. Configure the project to require the key.
3. Applications in that project only sync valid signed commits.

Example concept:

```yaml
spec:
  signatureKeys:
    - keyID: ABCD1234EFGH5678
```

Operational note:

- Signature verification is for Git repositories.
- It is not a replacement for branch protection and code review.
- It should be part of a larger supply-chain control model.

## 30. Project-scoped repositories

Normally repositories are global in Argo CD. Argo CD also supports project-scoped repositories.

A project-scoped repository can only be used by applications or ApplicationSets in the matching project.

Example repository secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: payments-gitops-repo
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: repository
type: Opaque
stringData:
  project: payments-dev
  url: https://git.example.com/payments/payments-gitops.git
  username: gitops-bot
  password: ${TOKEN}
```

Why this is useful:

- team-specific repo credentials,
- self-service onboarding,
- reduced blast radius,
- better tenant separation.

Security note:

If a repository secret is scoped to `payments-dev`, an application in `platform-config` cannot use it.

## 33. Global projects

Global projects let other projects inherit selected settings.

Inherited fields can include:

- `namespaceResourceBlacklist`,
- `namespaceResourceWhitelist`,
- `clusterResourceBlacklist`,
- `clusterResourceWhitelist`,
- `syncWindows`,
- `sourceRepos`,
- `destinations`.

Conceptual example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: openshift-gitops
data:
  globalProjects: |-
    - labelSelector:
        matchExpressions:
          - key: security-tier
            operator: In
            values:
              - restricted
      projectName: global-restricted-baseline
```

Then projects with label:

```yaml
metadata:
  labels:
    security-tier: restricted
```

can inherit from `global-restricted-baseline`.

Use cases:

- enforce common deny lists,
- apply standard sync windows,
- apply organization-wide resource constraints,
- keep project manifests smaller.

Operational warning:

Global inheritance can become confusing. Document it clearly and validate effective policy in lower environments.

## 38. How Argo CD evaluates an Application against AppProject

When Argo CD processes an application, it validates the application against the referenced project.

High-level flow:

```text
1. Read Application.spec.project
2. Load matching AppProject from Argo CD control plane namespace
3. Check whether source repo is allowed
4. Check whether destination cluster and namespace are allowed
5. Render manifests from Git/Helm/Kustomize/plugin
6. Check rendered resource kinds against project resource rules
7. Check user/API action against Argo CD RBAC/project role
8. If allowed, reconcile resources using Argo CD controller permissions
```

Failure at any stage causes sync or application processing errors.

## 39. Common error messages and meaning

### 39.1 Application not allowed to use project

Example:

```text
error while validating and normalizing app: error getting application's project: application 'app' in namespace 'dev' is not allowed to use project 'default'
```

Likely cause:

- Application is created in a non-control-plane namespace.
- The referenced AppProject does not include that namespace in `spec.sourceNamespaces`.
- The ArgoCD CR does not include that namespace in `spec.sourceNamespaces`.
- The Application is trying to use privileged `default` project.

Check:

```bash
oc get application app -n dev -o yaml
oc get appproject default -n openshift-gitops -o yaml
oc get argocd -A -o yaml | grep -A10 sourceNamespaces
```

Fix:

- create a dedicated AppProject,
- configure `sourceNamespaces`,
- move application to allowed project,
- do not use `default` for team-managed apps.

### 39.2 Source repository not permitted

Example symptoms:

```text
application repo is not permitted in project
source repo is not allowed
```

Check:

```bash
oc get app <app-name> -n openshift-gitops -o jsonpath='{.spec.source.repoURL}'
oc get appproject <project> -n openshift-gitops -o yaml | grep -A20 sourceRepos
```

Fix:

```yaml
sourceRepos:
  - https://git.example.com/payments/payments-gitops.git
```

Watch for:

- HTTPS vs SSH URL mismatch,
- trailing `.git` mismatch,
- case differences,
- wildcard pattern too narrow,
- deny rule using `!`.

### 39.3 Destination not permitted

Example symptoms:

```text
application destination is not permitted in project
```

Check:

```bash
oc get app <app-name> -n openshift-gitops -o yaml | yq '.spec.destination'
oc get appproject <project> -n openshift-gitops -o yaml | yq '.spec.destinations'
```

Fix:

```yaml
destinations:
  - server: https://kubernetes.default.svc
    namespace: payments-dev
```

Watch for:

- destination server mismatch,
- using cluster `name` in project but server in application,
- wrong namespace,
- wildcard too narrow,
- deny destination rule.

### 39.4 Resource kind not permitted

Example symptoms:

```text
resource <group>/<kind> is not permitted in project
```

Check rendered manifests:

```bash
argocd app manifests <app-name>
```

Or inspect Git path:

```bash
find apps/payments-api/overlays/dev -type f -name '*.yaml' -o -name '*.yml'
```

Check project resource rules:

```bash
oc get appproject <project> -n openshift-gitops -o yaml | grep -A50 Resource
```

Fix by adding the resource kind only if it is approved.

Example:

```yaml
namespaceResourceWhitelist:
  - group: route.openshift.io
    kind: Route
```

### 39.5 Kubernetes RBAC forbidden

Example:

```text
forbidden: User "system:serviceaccount:openshift-gitops:..." cannot create resource "deployments" in API group "apps" in namespace "payments-dev"
```

Meaning:

The AppProject allowed the action, but the Argo CD controller does not have OpenShift RBAC permission.

Check:

```bash
oc auth can-i create deployments.apps -n payments-dev \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Fix:

- label namespace for default OpenShift GitOps instance,
- configure target namespace for user-defined instance,
- create appropriate RoleBinding,
- ensure Operator-managed bindings are present.

### 39.6 User cannot sync application

Check project role:

```bash
oc get appproject <project> -n openshift-gitops -o yaml | yq '.spec.roles'
```

Check user groups:

```bash
oc get groups
oc get group <group-name> -o yaml
```

Check policy object:

```text
p, proj:<project>:<role>, applications, sync, <project>/<app>, allow
```

For applications in any namespace, RBAC object matching may include namespace-aware formats depending on Argo CD version and configuration. Confirm with the Argo CD RBAC documentation for your installed version.

## 41. Designing projects for enterprise OpenShift

### 41.1 Per team and environment

Recommended model:

```text
payments-dev
payments-stage
payments-prod
orders-dev
orders-stage
orders-prod
platform-config
security-config
observability-config
```

Benefits:

- least privilege,
- clear ownership,
- clean audit trail,
- environment-specific controls,
- easier incident isolation.

### 41.2 Avoid one giant project

Bad design:

```text
AppProject: all-apps
sourceRepos: '*'
destinations: '*'
clusterResourceWhitelist: '*'
```

Problems:

- no team isolation,
- no environment isolation,
- hard to audit,
- dangerous for production,
- difficult to troubleshoot authorization issues,
- increased blast radius.

### 41.3 Separate app GitOps from cluster GitOps

Application GitOps:

```text
Deployment, Service, Route, ConfigMap, Secret, NetworkPolicy
```

Cluster GitOps:

```text
Namespace, Operator, Subscription, RBAC, policy, monitoring, ingress, storage config
```

Keep them in separate projects.

### 41.4 Separate dev from prod

Development project can be flexible:

```yaml
sourceRepos:
  - https://git.example.com/payments/*
destinations:
  - namespace: payments-dev
```

Production project should be strict:

```yaml
sourceRepos:
  - https://git.example.com/platform/payments-prod-gitops.git
destinations:
  - namespace: payments-prod
syncWindows:
  - kind: deny
    schedule: '0 9 * * 1-5'
    duration: 8h
```

## 43. Managing AppProjects declaratively

Best practice:

```text
Manage AppProjects from Git, not manually from UI.
```

Example bootstrap structure:

```text
cluster-bootstrap/
├── argocd/
│   ├── projects/
│   │   ├── default-lockdown.yaml
│   │   ├── payments-dev.yaml
│   │   └── platform-cluster-config.yaml
│   └── apps/
│       └── app-of-apps.yaml
```

Apply initial bootstrap manually:

```bash
oc apply -f argocd/projects/default-lockdown.yaml
oc apply -f argocd/projects/payments-dev.yaml
```

Then let Argo CD manage future changes.

Be careful when Argo CD manages its own projects. A bad project change can lock out applications.

Recommended change flow:

1. Test in non-production Argo CD instance.
2. Validate rendered manifests.
3. Review AppProject diff carefully.
4. Apply during safe window.
5. Keep break-glass cluster-admin access.

## 44. Project configuration and App-of-Apps pattern

The App-of-Apps pattern commonly uses one parent application to create child applications.

Example:

```text
root-app
└── creates Application resources
    ├── payments-api-dev
    ├── orders-api-dev
    └── inventory-api-dev
```

Project consideration:

- The root app needs permission to deploy `Application` resources.
- Child apps must reference allowed projects.
- Do not let a team-owned root app create child apps in privileged projects.

If Application resources are created declaratively in `openshift-gitops`, access to that namespace is sensitive.

In multi-tenant environments, prefer the Applications-in-any-namespace model with carefully configured `sourceNamespaces`.

## 45. Project configuration and ApplicationSet

ApplicationSet can generate many `Application` resources.

Project considerations:

- Generated applications still reference `spec.project`.
- The project must allow their source repositories and destinations.
- If the generator templates `project`, review carefully.
- Avoid letting untrusted teams generate apps into privileged projects.
- With project-scoped repositories, understand limitations around templated project fields.

Example generated app should still land in a safe project:

```yaml
spec:
  template:
    spec:
      project: payments-dev
```

Do not use:

```yaml
project: '{{teamProject}}'
```

unless the generator source and values are tightly controlled.

## 46. OpenShift GitOps multi-tenancy model

A strong OpenShift GitOps tenant model includes multiple layers:

```text
Layer 1: OpenShift RBAC
Layer 2: Argo CD RBAC
Layer 3: AppProject sourceRepos/destinations/resources
Layer 4: Namespace labels and ArgoCD CR sourceNamespaces
Layer 5: Git branch protection and code review
Layer 6: NetworkPolicy, ResourceQuota, LimitRange, SCC/PSA controls
Layer 7: Audit and monitoring
```

Do not rely on only one layer.

Example tenant boundary:

```text
Team payments
├── OpenShift group: openshift-payments-devs
├── Namespace: payments-dev
├── AppProject: payments-dev
├── Git repo: payments-gitops
├── Argo CD role: dev-sync
├── Allowed resources: app workload objects only
└── No access to openshift-gitops namespace
```

## 47. Security hardening checklist

### 47.1 Default project

- [ ] Lock down `default` project.
- [ ] Find applications still using `default`.
- [ ] Migrate apps to dedicated projects.
- [ ] Prevent non-admin users from using privileged projects.

### 47.2 Repositories

- [ ] Avoid `sourceRepos: ['*']` in production.
- [ ] Use explicit approved repositories.
- [ ] Protect production branches.
- [ ] Require pull request review.
- [ ] Consider signed commits for production.
- [ ] Store repo credentials securely.

### 47.3 Destinations

- [ ] Avoid `server: '*'` and `namespace: '*'` for team projects.
- [ ] Explicitly list namespaces.
- [ ] Separate dev/stage/prod.
- [ ] Do not allow team projects to deploy into `openshift-*`, `kube-*`, or control-plane namespaces.

### 47.4 Resource kinds

- [ ] Deny cluster-scoped resources for app teams.
- [ ] Do not allow CRDs in app projects.
- [ ] Do not allow SCC management in app projects.
- [ ] Be cautious with RoleBinding.
- [ ] Be cautious with Operator custom resources.
- [ ] Use whitelist for production.

### 47.5 RBAC

- [ ] Use project roles for project-scoped access.
- [ ] Match group names exactly.
- [ ] Avoid broad `applications, *, *, allow` unless necessary.
- [ ] Do not grant users write access to `openshift-gitops` namespace.
- [ ] Use short-lived JWT tokens for CI.

### 47.6 Applications in any namespace

- [ ] Configure `ArgoCD.spec.sourceNamespaces`.
- [ ] Configure `AppProject.spec.sourceNamespaces`.
- [ ] Do not add user namespaces to privileged projects.
- [ ] Do not grant access to the Argo CD control plane namespace.
- [ ] Validate namespace wildcard patterns.

### 47.7 Operations

- [ ] Enable orphaned resource warnings on scoped namespaces.
- [ ] Monitor Argo CD project changes.
- [ ] Audit project manifests through Git.
- [ ] Use sync windows for production.
- [ ] Maintain break-glass admin process.

## 48. Common production anti-patterns

### Anti-pattern 1: Using default project everywhere

```yaml
spec:
  project: default
```

Why bad:

- too permissive,
- no team boundary,
- no environment control,
- difficult audit.

Fix:

Create dedicated projects.

### Anti-pattern 2: Wildcard everything

```yaml
sourceRepos:
  - '*'
destinations:
  - server: '*'
    namespace: '*'
clusterResourceWhitelist:
  - group: '*'
    kind: '*'
```

Why bad:

This is effectively no project security.

Fix:

Use explicit repos, namespaces, and resources.

### Anti-pattern 3: Developers have write access to `openshift-gitops`

Why bad:

A user with write access to Argo CD control plane namespace can often bypass intended Argo CD RBAC boundaries.

Fix:

Use Argo CD RBAC and Applications-in-any-namespace correctly.

### Anti-pattern 4: App team can create RoleBinding

Why risky:

RoleBinding can bind powerful ClusterRoles to service accounts.

Fix:

Keep RBAC in platform-controlled projects.

### Anti-pattern 5: Production app project allows dev repo

Why risky:

Dev branches or repos may not have production review controls.

Fix:

Use production-only GitOps repository or protected production path.

## 49. Troubleshooting workflow for AppProject issues

When an application fails because of project configuration, troubleshoot in this order.

### Step 1: Identify application project

```bash
oc get application <app> -n <app-ns> -o jsonpath='{.spec.project}{"\n"}'
```

### Step 2: Inspect project

```bash
oc get appproject <project> -n openshift-gitops -o yaml
```

### Step 3: Check source repo

```bash
oc get application <app> -n <app-ns> -o jsonpath='{.spec.source.repoURL}{"\n"}'
```

Compare with:

```bash
oc get appproject <project> -n openshift-gitops -o jsonpath='{.spec.sourceRepos}{"\n"}'
```

### Step 4: Check destination

```bash
oc get application <app> -n <app-ns> -o yaml | yq '.spec.destination'
```

Compare with:

```bash
oc get appproject <project> -n openshift-gitops -o yaml | yq '.spec.destinations'
```

### Step 5: Check rendered resource kinds

```bash
argocd app manifests <app>
```

List kinds from local repo:

```bash
grep -R "^kind:" -n apps/<app-path>
```

Compare with:

```yaml
namespaceResourceWhitelist
namespaceResourceBlacklist
clusterResourceWhitelist
clusterResourceBlacklist
```

### Step 6: Check application source namespace

If using Application in non-control-plane namespace:

```bash
oc get application <app> -n <source-ns> -o yaml
oc get appproject <project> -n openshift-gitops -o yaml | yq '.spec.sourceNamespaces'
oc get argocd -A -o yaml | grep -A10 sourceNamespaces
```

### Step 7: Check OpenShift RBAC

```bash
oc auth can-i create deployments.apps -n <target-ns> \
  --as=system:serviceaccount:<argocd-ns>:<argocd-controller-sa>
```

Find controller service account:

```bash
oc get sa -n <argocd-ns> | grep controller
```

### Step 8: Check controller logs

```bash
oc logs -n <argocd-ns> deploy/<argocd-application-controller-deployment>
```

## 50. Practical lab: create secure project and app

### 50.1 Create namespace

```bash
oc new-project payments-dev
```

### 50.2 Label namespace for default OpenShift GitOps instance

```bash
oc label namespace payments-dev argocd.argoproj.io/managed-by=openshift-gitops --overwrite
```

### 50.3 Create AppProject

```bash
cat <<'EOF_PROJECT' | oc apply -f -
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-dev
  namespace: openshift-gitops
spec:
  description: Payments development project
  sourceRepos:
    - https://github.com/example/payments-gitops.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
    - group: ''
      kind: ConfigMap
    - group: route.openshift.io
      kind: Route
EOF_PROJECT
```

### 50.4 Create Application

```bash
cat <<'EOF_APP' | oc apply -f -
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-api-dev
  namespace: openshift-gitops
spec:
  project: payments-dev
  source:
    repoURL: https://github.com/example/payments-gitops.git
    targetRevision: main
    path: apps/payments-api/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
EOF_APP
```

### 50.5 Verify

```bash
oc get app payments-api-dev -n openshift-gitops
oc describe app payments-api-dev -n openshift-gitops
oc get all -n payments-dev
```

## 51. Exam and interview style notes

### Question: What problem does AppProject solve?

Answer:

`AppProject` provides a security boundary for Argo CD applications. It restricts source repositories, destination clusters/namespaces, allowed resource kinds, and project-level RBAC.

### Question: Is AppProject the same as OpenShift RBAC?

Answer:

No. AppProject is Argo CD-level authorization and policy. OpenShift RBAC still controls what the Argo CD service account can actually create in the cluster.

### Question: Why should default project be locked down?

Answer:

The default project is initially permissive. If non-admin users can deploy through it, they may deploy from any repo to any namespace and potentially create powerful resources.

### Question: What is `sourceRepos`?

Answer:

It is the list of Git or Helm repositories that applications in the project are allowed to use.

### Question: What is `destinations`?

Answer:

It defines the target clusters and namespaces where applications in the project can deploy.

### Question: What is `sourceNamespaces`?

Answer:

It defines where `Application` CRs are allowed to reside when using Applications in any namespace. It does not define where workloads are deployed.

### Question: Can a project role grant cluster-admin permissions in OpenShift?

Answer:

No directly. Project roles control Argo CD API actions. But if the Argo CD controller has powerful Kubernetes permissions and the project allows dangerous resources, a user with sync/update rights could indirectly deploy powerful resources. That is why AppProject and OpenShift RBAC must both be designed carefully.

### Question: Why is allowing RoleBinding risky?

Answer:

A namespaced RoleBinding can reference a ClusterRole. If a team can create arbitrary RoleBindings, they may bind powerful permissions to users or service accounts inside the namespace.

### Question: What is a good project design for production?

Answer:

Use one project per team/environment, explicit repositories, explicit destinations, whitelist approved resource kinds, no cluster-scoped resources for app teams, sync windows, read-only developer access, SRE sync access, and default project lockdown.

## 53. Advanced design recommendations from field experience

### 53.1 Start strict, loosen intentionally

It is easier to add allowed resources later than to clean up after a project allowed too much.

Start with:

```yaml
clusterResourceWhitelist: []
namespaceResourceWhitelist:
  - group: apps
    kind: Deployment
  - group: ''
    kind: Service
  - group: ''
    kind: ConfigMap
```

Then add `Route`, `Secret`, `NetworkPolicy`, `HPA`, or others after review.

### 53.2 Treat Git repo path as a security boundary

Even if `sourceRepos` allows one repository, a path inside that repository may still be controlled by different people.

Example:

```text
repo: platform-gitops
paths:
  apps/team-a
  apps/team-b
  clusters/prod
```

If team A can modify `clusters/prod`, project restrictions may not help. Protect paths using Git permissions, CODEOWNERS, branch protection, and review workflow.

### 53.3 Avoid mixing unrelated teams in one project

A project should map to a real ownership boundary.

Bad:

```text
AppProject: all-dev-apps
```

Better:

```text
payments-dev
orders-dev
inventory-dev
```

### 53.4 Keep cluster config separate

Do not let normal app projects manage:

- namespaces,
- CRDs,
- cluster roles,
- SCCs,
- Operator subscriptions,
- storage classes,
- ingress controllers,
- image registry config,
- authentication config.

Use platform-owned GitOps projects for these.

### 53.5 Use sync windows for production, not development

Development should be fast. Production should be controlled.

Typical model:

```text
Dev: auto-sync allowed
Stage: auto-sync or scheduled
Prod: controlled sync window, manual approval, signed commits
```

### 53.6 Audit AppProject changes

AppProject changes are security changes.

Review them like firewall or RBAC changes.

High-risk changes:

```yaml
sourceRepos:
  - '*'

destinations:
  - server: '*'
    namespace: '*'

clusterResourceWhitelist:
  - group: '*'
    kind: '*'
```

Any pull request adding these should be treated as a security-sensitive change.

## 54. AppProject review checklist before production approval

Before approving an AppProject, verify:

```text
[ ] Project name clearly identifies team/environment.
[ ] Default project is not used for this app.
[ ] Source repositories are explicit and trusted.
[ ] Destination namespaces are explicit.
[ ] Destination does not include openshift-* or kube-* unless platform-owned.
[ ] Cluster-scoped resources are denied for app teams.
[ ] Namespaced resources are whitelisted for production.
[ ] RoleBinding is denied unless needed and reviewed.
[ ] Secrets are allowed only if the team owns secret management.
[ ] Route exposure is reviewed.
[ ] NetworkPolicy ownership is clear.
[ ] Sync windows exist for production if required.
[ ] Project roles follow proj:<project>:<role> format.
[ ] Groups are correct and come from the identity provider.
[ ] CI tokens are short-lived and scoped.
[ ] Applications-in-any-namespace sourceNamespaces are safe.
[ ] No user namespace is added to privileged projects.
[ ] Project is managed declaratively from Git.
```

## 55. Fast mental model for senior administrators

Use this model while reviewing any `AppProject`:

```text
sourceRepos       = what code/config can enter Argo CD
sourceNamespaces = where Application CRs can live
roles            = who can operate apps through Argo CD
destinations     = where rendered resources can land
resource rules   = what Kubernetes/OpenShift objects can be created
OpenShift RBAC   = whether Argo CD service account can actually create them
Git controls     = who can change the desired state
```

A secure deployment requires all of these to be correct.

## 56. Summary

Argo CD project configuration is one of the most important advanced OpenShift GitOps administration topics.

For a beginner, an `AppProject` looks like a simple grouping object. For an experienced administrator, it is a security boundary that controls Git trust, target namespaces, resource kinds, team access, sync behavior, and multi-tenant safety.

Key takeaways:

- Do not use the permissive default project in production.
- Create dedicated projects per team and environment.
- Restrict source repositories.
- Restrict destination clusters and namespaces.
- Deny cluster-scoped resources for application teams.
- Prefer resource whitelists for production.
- Use project roles for scoped Argo CD RBAC.
- Be careful with `sourceNamespaces` in OpenShift GitOps.
- Never grant non-admin users write access to the Argo CD control plane namespace.
- Treat AppProject changes as security changes.
- Combine AppProject controls with OpenShift RBAC, namespace labels, Git branch protection, and operational audit.

A well-designed `AppProject` model gives OpenShift GitOps the discipline needed for real enterprise operations.
