# Kustomize Integration in OpenShift GitOps Argo CD

**Audience:** Advanced OpenShift Administration / OpenShift GitOps / Argo CD engineers with production experience  
**Level:** Deep-dive, 10-years-experience style  
**Last reviewed:** 2026-07-03  

---

## 1. Executive Summary

Kustomize integration in OpenShift GitOps means Argo CD can render Kubernetes and OpenShift manifests from a Git repository using `kustomization.yaml` before comparing and syncing those manifests to the OpenShift cluster.

In simple terms:

```text
Git repository
   |
   |  base + overlays + patches + generators
   v
Argo CD repo-server
   |
   |  runs kustomize build
   v
Rendered manifests
   |
   |  compare with live OpenShift resources
   v
Argo CD application-controller
   |
   |  sync / prune / self-heal
   v
OpenShift cluster
```

Kustomize is useful when the same application or platform component must be deployed differently across environments such as `dev`, `qa`, `stage`, `prod`, `dr`, `east`, `west`, or across multiple OpenShift clusters.

Kustomize is **not a template engine** like Helm. It works by taking valid Kubernetes YAML and applying structured customizations such as overlays, patches, image changes, labels, annotations, name prefixes, namespace changes, and generated ConfigMaps or Secrets.

For an advanced OpenShift administrator, Kustomize integration is important because it allows you to manage:

- Environment-specific application configuration
- OpenShift `Route`, `Deployment`, `Service`, `ConfigMap`, `Secret`, `NetworkPolicy`, `RoleBinding`, `SCC`-related service account bindings, and namespace objects
- Platform configuration such as operators, subscriptions, namespaces, RBAC, quotas, limit ranges, monitoring, logging, and policy resources
- Multi-cluster GitOps using ApplicationSet
- App-of-apps bootstrap models
- Drift detection and self-healing
- Safe promotion from lower to higher environments

## 2. What Kustomize Does in Argo CD

Argo CD supports different manifest sources, including plain YAML directories, Helm charts, Jsonnet, config management plugins, and Kustomize.

When Argo CD sees a `kustomization.yaml`, `kustomization.yml`, or equivalent Kustomize configuration in the application source path, it treats the path as a Kustomize application and renders the final manifests using Kustomize.

Example Argo CD Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-dev
  namespace: openshift-gitops
spec:
  project: retail-platform
  source:
    repoURL: https://git.example.com/platform/retail-gitops.git
    targetRevision: main
    path: apps/frontend/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: retail-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Important point:

```text
spec.source.path = the folder Argo CD sends to kustomize build
```

If the folder is:

```text
apps/frontend/overlays/dev
```

then Argo CD effectively renders something similar to:

```bash
kustomize build apps/frontend/overlays/dev
```

or locally:

```bash
kubectl kustomize apps/frontend/overlays/dev
```

## 3. Why Kustomize Is Important in OpenShift GitOps

In real OpenShift environments, you rarely deploy the exact same YAML everywhere.

A production environment may require:

- More replicas
- Different resource requests and limits
- Different route hostnames
- Different TLS route configuration
- Different image tags or digests
- Different node selectors
- Different tolerations
- Different namespace
- Different ConfigMap values
- Different secrets managed by External Secrets or Sealed Secrets
- Different monitoring labels
- Different NetworkPolicy rules
- Different PodDisruptionBudget values
- Different SCC service account bindings

Without Kustomize, teams often copy full YAML files per environment. That causes configuration drift.

Bad pattern:

```text
frontend-dev/deployment.yaml
frontend-qa/deployment.yaml
frontend-prod/deployment.yaml
```

Each file is almost identical, but one day someone patches only `prod`, another person patches only `dev`, and after a few months nobody knows which manifest is the real source of truth.

Kustomize solves this by separating common base manifests from environment-specific overlays.

Good pattern:

```text
apps/frontend/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── route.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml
    │   └── patch-replicas.yaml
    ├── stage/
    │   ├── kustomization.yaml
    │   └── patch-route.yaml
    └── prod/
        ├── kustomization.yaml
        ├── patch-replicas.yaml
        ├── patch-resources.yaml
        └── patch-pdb.yaml
```

## 4. Core Kustomize Concepts

### 4.1 Base

A base contains reusable YAML resources.

Example:

```text
apps/frontend/base/
├── deployment.yaml
├── service.yaml
├── route.yaml
└── kustomization.yaml
```

`apps/frontend/base/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - deployment.yaml
  - service.yaml
  - route.yaml

commonLabels:
  app.kubernetes.io/name: frontend
  app.kubernetes.io/part-of: retail
```

Base manifests should be usable and valid by themselves, but they usually do not contain final production-specific settings.

### 4.2 Overlay

An overlay references a base and customizes it.

Example:

```text
apps/frontend/overlays/prod/
├── kustomization.yaml
├── patch-replicas.yaml
├── patch-resources.yaml
└── patch-route.yaml
```

`apps/frontend/overlays/prod/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: retail-prod

resources:
  - ../../base

namePrefix: prod-

images:
  - name: quay.io/example/frontend
    newTag: v1.4.8

replicas:
  - name: frontend
    count: 5

patches:
  - path: patch-resources.yaml
    target:
      kind: Deployment
      name: frontend
  - path: patch-route.yaml
    target:
      kind: Route
      name: frontend
```

### 4.3 Patch

A patch changes part of a resource from the base.

Example resource patch:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  template:
    spec:
      containers:
        - name: frontend
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 1
              memory: 1Gi
```

Example JSON 6902 patch:

```yaml
- op: replace
  path: /spec/template/spec/containers/0/resources/requests/cpu
  value: 500m
```

For OpenShift custom resources such as `Route`, `Subscription`, `ArgoCD`, `BuildConfig`, or operator CRs, JSON 6902 patches are often safer than strategic merge patches because Kubernetes strategic merge behavior is strongest for built-in Kubernetes types.

### 4.4 Generator

Kustomize can generate ConfigMaps and Secrets.

Example:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

configMapGenerator:
  - name: frontend-config
    literals:
      - LOG_LEVEL=info
      - FEATURE_FLAG_CHECKOUT=true

secretGenerator:
  - name: frontend-secret
    literals:
      - DB_USERNAME=frontend
      - DB_PASSWORD=change-me
```

By default, generated ConfigMaps and Secrets get a hash suffix, such as:

```text
frontend-config-7d8gk6h9m2
```

That is useful because a changed ConfigMap name can trigger a rollout when referenced by a Deployment.

However, for stable names you can disable the suffix:

```yaml
generatorOptions:
  disableNameSuffixHash: true
```

Production warning: Do not store real secrets in Git as plain text. Use External Secrets Operator, Sealed Secrets, SOPS with a supported plugin, Vault integration, or another enterprise secret-management model.

### 4.5 Component

A component is a reusable package of resources and patches that can be included by multiple overlays.

Example:

```text
components/
├── monitoring/
│   ├── servicemonitor.yaml
│   └── kustomization.yaml
├── network-policy/
│   ├── default-deny.yaml
│   └── kustomization.yaml
└── pdb/
    ├── pdb.yaml
    └── kustomization.yaml
```

Overlay:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - ../../base

components:
  - ../../../components/monitoring
  - ../../../components/network-policy
  - ../../../components/pdb
```

In Argo CD, components can also be referenced in the `Application` under `spec.source.kustomize.components`.

## 5. OpenShift GitOps Architecture with Kustomize

OpenShift GitOps is Red Hat’s supported distribution of Argo CD on OpenShift.

Important components:

| Component | Role |
|---|---|
| OpenShift GitOps Operator | Installs and reconciles Argo CD components |
| Argo CD server | UI and API |
| Argo CD repo-server | Clones Git repositories and renders manifests, including Kustomize builds |
| Argo CD application-controller | Compares desired state with live cluster state and performs sync |
| Redis | Cache for Argo CD data |
| ApplicationSet controller | Generates Applications dynamically |
| Dex / OpenShift OAuth integration | Authentication, depending on configuration |

Kustomize rendering happens mainly in the repo-server.

Flow:

```text
1. Application points to repoURL + targetRevision + path
2. repo-server clones repository revision
3. repo-server detects Kustomize source
4. repo-server runs kustomize build with Argo CD options
5. rendered YAML is sent to application-controller
6. application-controller compares desired state with live state
7. sync applies resources to OpenShift using Argo CD service account permissions
```

OpenShift-specific consideration:

The default OpenShift GitOps instance is usually installed in the `openshift-gitops` namespace. A user-defined Argo CD instance can also be installed. A namespace managed by the default instance often needs the label:

```bash
oc label namespace retail-dev argocd.argoproj.io/managed-by=openshift-gitops
```

This is especially important when the default Argo CD instance is managing resources outside its own namespace.

## 8. Argo CD `spec.source.kustomize` Options

Argo CD allows Kustomize customizations directly in the Application spec.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-dev
  namespace: openshift-gitops
spec:
  project: retail-platform
  source:
    repoURL: https://git.example.com/platform/retail-gitops.git
    targetRevision: main
    path: apps/frontend/base
    kustomize:
      namePrefix: dev-
      namespace: retail-dev
      images:
        - quay.io/example/frontend:v1.4.8-dev
      replicas:
        - name: frontend
          count: 2
      commonLabels:
        env: dev
      commonAnnotations:
        owner: platform-team
      patches:
        - target:
            kind: Deployment
            name: frontend
          patch: |-
            - op: add
              path: /spec/template/spec/nodeSelector
              value:
                node-role.kubernetes.io/app: ""
  destination:
    server: https://kubernetes.default.svc
    namespace: retail-dev
```

Common Argo CD Kustomize fields:

| Field | Purpose |
|---|---|
| `namePrefix` | Adds prefix to generated resource names |
| `nameSuffix` | Adds suffix to generated resource names |
| `images` | Overrides image names/tags/digests |
| `replicas` | Overrides replica counts |
| `commonLabels` | Adds labels across rendered resources |
| `commonAnnotations` | Adds annotations across rendered resources |
| `namespace` | Tells Kustomize to set resource namespaces |
| `patches` | Adds inline patches in the Application spec |
| `components` | Adds Kustomize components |
| `ignoreMissingComponents` | Allows optional components to be skipped if missing |
| `version` | Uses a configured custom Kustomize binary version |
| `commonAnnotationsEnvsubst` | Allows Argo CD build variables in common annotations |

### Best practice

For GitOps purity, keep most Kustomize logic in Git under `kustomization.yaml` files. Use `spec.source.kustomize` for controlled platform-level customization, ApplicationSet-driven templating, or special cases.

Avoid relying heavily on UI or CLI parameter overrides because they can create hidden desired state outside the Git repository.

## 9. Namespace Handling: Very Important in OpenShift

Namespace handling is a common source of production issues.

There are two different namespace fields:

```yaml
spec:
  destination:
    namespace: retail-prod
```

and:

```yaml
spec:
  source:
    kustomize:
      namespace: retail-prod
```

They are not always equivalent.

### 9.1 `spec.destination.namespace`

This tells Argo CD where to apply namespaced resources when a namespace is missing from the rendered manifests.

### 9.2 `spec.source.kustomize.namespace`

This tells Kustomize itself to inject namespace fields while rendering.

This is usually safer when manifests include resources with nested namespace fields, such as `RoleBinding` subjects.

Example issue:

```yaml
kind: RoleBinding
subjects:
  - kind: ServiceAccount
    name: deployer
    namespace: MISSING
```

If namespace injection is done only by Argo CD after rendering, some nested fields might not be updated. Using Kustomize namespace handling can avoid errors like:

```text
subjects[0].namespace: Required value
```

Recommended production pattern:

```yaml
source:
  path: apps/frontend/overlays/prod
  kustomize:
    namespace: retail-prod
destination:
  namespace: retail-prod
```

Also ensure the namespace exists or use:

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
```

For OpenShift GitOps default instance, also label the namespace if required:

```bash
oc label namespace retail-prod argocd.argoproj.io/managed-by=openshift-gitops --overwrite
```

## 11. Kustomize with AppProject

In production, never allow all applications to use the unrestricted default AppProject.

Create a restricted AppProject:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: retail-platform
  namespace: openshift-gitops
spec:
  description: Retail platform applications

  sourceRepos:
    - https://git.example.com/platform/retail-gitops.git

  destinations:
    - namespace: retail-dev
      server: https://kubernetes.default.svc
    - namespace: retail-stage
      server: https://kubernetes.default.svc
    - namespace: retail-prod
      server: https://kubernetes.default.svc

  clusterResourceWhitelist:
    - group: ""
      kind: Namespace

  namespaceResourceWhitelist:
    - group: ""
      kind: ConfigMap
    - group: ""
      kind: Secret
    - group: ""
      kind: Service
    - group: apps
      kind: Deployment
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy
    - group: policy
      kind: PodDisruptionBudget
```

Why this matters:

- Kustomize can render anything from Git.
- Argo CD can apply what its service account is allowed to apply.
- AppProject limits reduce blast radius.
- OpenShift RBAC still provides final enforcement.

Production rule:

```text
Git path restrictions + AppProject restrictions + OpenShift RBAC = safe GitOps boundary
```

## 12. Kustomize with ApplicationSet

ApplicationSet is powerful when the same Kustomize structure must create many Argo CD Applications.

### 12.1 Directory generator

Repository:

```text
apps/frontend/overlays/dev
apps/frontend/overlays/stage
apps/frontend/overlays/prod
```

ApplicationSet:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: frontend-envs
  namespace: openshift-gitops
spec:
  generators:
    - git:
        repoURL: https://git.example.com/platform/retail-gitops.git
        revision: main
        directories:
          - path: apps/frontend/overlays/*
  template:
    metadata:
      name: 'frontend-{{path.basename}}'
    spec:
      project: retail-platform
      source:
        repoURL: https://git.example.com/platform/retail-gitops.git
        targetRevision: main
        path: '{{path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'retail-{{path.basename}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

This creates:

```text
frontend-dev
frontend-stage
frontend-prod
```

### 12.2 Cluster generator for multi-cluster

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: frontend-multicluster
  namespace: openshift-gitops
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            platform.example.com/env: prod
  template:
    metadata:
      name: 'frontend-{{name}}'
    spec:
      project: retail-platform
      source:
        repoURL: https://git.example.com/platform/retail-gitops.git
        targetRevision: main
        path: apps/frontend/overlays/prod
      destination:
        server: '{{server}}'
        namespace: retail-prod
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

Advanced use:

- One overlay per environment
- One Application per cluster
- Cluster labels decide placement
- Kustomize patches can inject cluster-specific annotations or hostnames

## 13. Inline Patches in Argo CD Applications

Argo CD supports inline Kustomize patches inside the Application spec.

Example:

```yaml
spec:
  source:
    repoURL: https://git.example.com/platform/retail-gitops.git
    targetRevision: main
    path: apps/external-dns/base
    kustomize:
      patches:
        - target:
            kind: Deployment
            name: external-dns
          patch: |-
            - op: add
              path: /spec/template/spec/containers/0/args/-
              value: --txt-owner-id=prod-cluster-01
```

This is useful with ApplicationSet because generator variables can be injected into the patch.

Example:

```yaml
patch: |-
  - op: add
    path: /spec/template/spec/containers/0/args/-
    value: --txt-owner-id={{name}}
```

Production caution:

Inline patches make the Application CR itself part of the desired configuration. That is acceptable if Application CRs are also stored in Git. Avoid manually edited inline patches from the UI because they are hard to review and promote.

## 14. Image Overrides and Promotion

Kustomize supports image overrides.

Base Deployment:

```yaml
image: quay.io/example/frontend:latest
```

Overlay:

```yaml
images:
  - name: quay.io/example/frontend
    newTag: v1.4.8
```

Or using digest:

```yaml
images:
  - name: quay.io/example/frontend
    digest: sha256:abc123...
```

Recommended production approach:

```text
Build once -> tag/digest image -> promote by Git change -> Argo CD syncs
```

Avoid deploying mutable tags like `latest` in production.

Better:

```yaml
images:
  - name: quay.io/example/frontend
    newName: quay.io/prod/frontend
    digest: sha256:5f2d...
```

### Argo CD Image Updater note

Recent Red Hat OpenShift GitOps versions include Argo CD Image Updater capabilities. Image Updater can update applications built with Kustomize or Helm. In strict GitOps environments, prefer Git write-back or pull-request workflow so that image promotions remain auditable.

## 15. ConfigMap and Secret Generators in Argo CD

### 15.1 ConfigMap generator

```yaml
configMapGenerator:
  - name: app-config
    files:
      - application.properties
```

Deployment reference:

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

Kustomize automatically updates the reference to the generated name with hash.

### 15.2 Secret generator

```yaml
secretGenerator:
  - name: app-secret
    literals:
      - username=admin
      - password=redhat
```

Do not store real secret literals in Git.

Better enterprise options:

- External Secrets Operator
- Sealed Secrets
- SOPS with Argo CD config management plugin
- HashiCorp Vault plugin
- OpenShift service account tokens where appropriate
- CSI Secrets Store driver

### 15.3 Generated resource drift

Generated names can sometimes create extra resources when old generated objects are not pruned as expected. Ensure:

```yaml
syncPolicy:
  automated:
    prune: true
```

For special generated resources, use compare options carefully:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/compare-options: IgnoreExtraneous
```

Use this only when you understand the impact. Overusing ignore rules can hide real drift.

## 16. Sync Waves and Kustomize

Kustomize controls manifest rendering. Argo CD controls sync ordering.

Use sync waves when order matters.

Example namespace first:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: retail-prod
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

OperatorGroup before Subscription:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: elasticsearch-og
  namespace: openshift-operators-redhat
  annotations:
    argocd.argoproj.io/sync-wave: "1"
```

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: elasticsearch-operator
  namespace: openshift-operators-redhat
  annotations:
    argocd.argoproj.io/sync-wave: "2"
```

Custom resource after CRD/operator:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "3"
```

Common OpenShift ordering:

```text
wave 0  namespaces
wave 1  operatorgroups / rbacs / serviceaccounts
wave 2  subscriptions
wave 3  operator custom resources
wave 4  application workloads
wave 5  routes / monitors / final policies
```

## 17. Health Checks and OpenShift Custom Resources

Argo CD understands many Kubernetes resource health states, but custom resources may need custom health checks.

OpenShift operators create many CRs. Some may show as `Progressing` or `Unknown` in Argo CD even when they are fine.

For advanced production GitOps, define health customizations when required.

Example concept in Argo CD config:

```yaml
resource.customizations.health.example.com_MyResource: |
  hs = {}
  if obj.status ~= nil and obj.status.conditions ~= nil then
    for i, condition in ipairs(obj.status.conditions) do
      if condition.type == "Ready" and condition.status == "True" then
        hs.status = "Healthy"
        hs.message = condition.message
        return hs
      end
    end
  end
  hs.status = "Progressing"
  hs.message = "Waiting for Ready condition"
  return hs
```

In OpenShift GitOps, prefer configuring Argo CD settings through the ArgoCD custom resource where supported, especially because the Operator manages Argo CD components and related ConfigMaps.

## 18. Build Options: `kustomize.buildOptions`

Argo CD can pass additional options to `kustomize build`.

Upstream Argo CD uses the `argocd-cm` ConfigMap keys such as:

```yaml
data:
  kustomize.buildOptions: --load-restrictor LoadRestrictionsNone
```

For OpenShift GitOps Operator-managed Argo CD, prefer configuring equivalent settings through the `ArgoCD` custom resource `spec.extraConfig` when supported:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  extraConfig:
    kustomize.buildOptions: "--load-restrictor LoadRestrictionsNone"
```

Important warning:

`--load-restrictor LoadRestrictionsNone` relaxes Kustomize file loading restrictions. Do not enable it casually in a multi-tenant GitOps environment because it can allow a kustomization to read files outside its root.

Use it only when:

- You understand the security impact
- Repositories are trusted
- AppProjects and repo access are controlled
- Peer review is mandatory
- You have tested the result in non-production

## 19. Kustomize with Helm Charts

Kustomize can render Helm charts only when Kustomize is run with `--enable-helm`.

In Argo CD, this is not a normal per-Application Kustomize option. Common choices are:

1. Use Helm directly as the Argo CD source type.
2. Use Kustomize with global build option `--enable-helm`.
3. Use a config management plugin.

OpenShift GitOps example using `spec.extraConfig`:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  extraConfig:
    kustomize.buildOptions: "--enable-helm"
```

Production caution:

This affects Kustomize builds globally for that Argo CD instance. If you enable it, test all Kustomize Applications because behavior and dependency fetching may change.

For most OpenShift production environments, use:

```text
Helm source for Helm charts
Kustomize source for Kustomize overlays
ApplicationSet for generating many Applications
```

Use Kustomize-over-Helm only when there is a strong operational reason.

## 21. Private Remote Bases

Kustomize supports remote bases, for example:

```yaml
resources:
  - git::ssh://git@git.example.com/platform/common-base.git//apps/java?ref=v1.2.0
```

Argo CD behavior:

- Remote bases can inherit credentials from the Application repository if they use the same credentials.
- They will not automatically use credentials from unrelated repositories just because Argo CD knows those repositories.
- This is intentional for security isolation.

Recommended production pattern:

```text
Prefer local bases inside the same repository or same credential boundary.
```

If you must use remote bases:

- Pin by tag, commit SHA, or immutable version reference
- Avoid tracking `main` for production bases
- Ensure Git credentials are scoped correctly
- Test repo-server access
- Consider vendoring the base into the platform repository for stronger control

## 22. Resource Tracking and Label Conflicts

Argo CD tracks resources it manages. Historically, it commonly uses the label:

```text
app.kubernetes.io/instance
```

Kustomize also commonly adds labels.

Problem pattern:

```yaml
commonLabels:
  app.kubernetes.io/instance: frontend
```

This can conflict with Argo CD resource tracking.

Better:

```yaml
commonLabels:
  app.kubernetes.io/name: frontend
  app.kubernetes.io/part-of: retail
  app.kubernetes.io/managed-by: argocd
```

If enterprise standards require using `app.kubernetes.io/instance`, consider configuring Argo CD to use a different tracking label, such as:

```yaml
spec:
  applicationInstanceLabelKey: argocd.argoproj.io/instance
```

or equivalent Argo CD config, depending on your OpenShift GitOps version and operator-managed configuration model.

Production warning:

Changing resource tracking label behavior can make many Applications appear out of sync. Plan and test the migration.

## 23. Common Label and Selector Pitfalls

Kustomize `commonLabels` can affect selectors depending on configuration and Kustomize version.

Risk:

Changing selectors of existing Deployments, Services, or NetworkPolicies can cause:

- Deployment immutable selector errors
- Service endpoint mismatch
- NetworkPolicy not matching intended pods
- Argo CD sync failure
- Traffic outage

Bad example after workload already exists:

```yaml
commonLabels:
  env: prod
```

If this mutates selectors, it may require resource recreation.

Safer approach:

- Put stable selector labels in the base from day one.
- Use annotations for changing metadata.
- Avoid changing selector labels after first deployment.
- Review rendered manifests before merging.

Local check:

```bash
kustomize build apps/frontend/overlays/prod | yq '. | select(.kind=="Deployment") | .spec.selector'
```

OpenShift check:

```bash
oc get deployment frontend -n retail-prod -o yaml | yq '.spec.selector'
oc get svc frontend -n retail-prod -o yaml | yq '.spec.selector'
oc get pods -n retail-prod --show-labels
oc get endpoints frontend -n retail-prod -o wide
```

## 24. OpenShift RBAC and Permissions

Kustomize only renders YAML. Argo CD still needs permission to apply that YAML.

If sync fails with forbidden errors:

```text
User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller" cannot create resource ...
```

Check:

```bash
oc auth can-i create routes.route.openshift.io \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n retail-prod
```

For namespace management by default OpenShift GitOps instance:

```bash
oc label namespace retail-prod argocd.argoproj.io/managed-by=openshift-gitops --overwrite
```

For user-defined Argo CD instances, grant only required access.

Example RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: argocd-manage-retail-prod
  namespace: retail-prod
subjects:
  - kind: ServiceAccount
    name: example-argocd-application-controller
    namespace: platform-gitops
roleRef:
  kind: ClusterRole
  name: admin
  apiGroup: rbac.authorization.k8s.io
```

Production rule:

```text
Do not solve every GitOps permission issue by granting cluster-admin.
```

Use least privilege.

## 25. SCC and Security Context with Kustomize

OpenShift SecurityContextConstraints are a frequent cause of deployment failures.

Example error:

```text
unable to validate against any security context constraint
```

Kustomize can manage service accounts and RoleBindings, but SCC bindings are often applied using OpenShift-specific RBAC commands or manifests.

Example service account:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: frontend-sa
```

Deployment patch:

```yaml
- op: add
  path: /spec/template/spec/serviceAccountName
  value: frontend-sa
```

SCC binding command:

```bash
oc adm policy add-scc-to-user restricted-v2 -z frontend-sa -n retail-prod
```

If a workload truly requires `anyuid`, document the reason and use the smallest scope:

```bash
oc adm policy add-scc-to-user anyuid -z frontend-sa -n retail-prod
```

GitOps approach for SCC binding:

An SCC binding is represented through RBAC against the SCC resource. For example, depending on OpenShift version and policy, a RoleBinding/ClusterRoleBinding may reference a ClusterRole such as `system:openshift:scc:anyuid`.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: use-anyuid-scc
  namespace: retail-prod
subjects:
  - kind: ServiceAccount
    name: frontend-sa
    namespace: retail-prod
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:openshift:scc:anyuid
```

Always validate this against your OpenShift version and security policy.

## 26. NetworkPolicy with Kustomize Components

NetworkPolicy is ideal for Kustomize components.

Example component:

```text
components/default-deny/
├── default-deny.yaml
└── kustomization.yaml
```

`default-deny.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

`kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component

resources:
  - default-deny.yaml
```

Overlay:

```yaml
components:
  - ../../../components/default-deny
```

Allow frontend to backend:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: backend
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: frontend
      ports:
        - protocol: TCP
          port: 8080
  policyTypes:
    - Ingress
```

Troubleshooting:

```bash
oc get netpol -n retail-prod
oc describe netpol allow-frontend-to-backend -n retail-prod
oc get pods -n retail-prod --show-labels
oc run test-client -n retail-prod --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc rsh -n retail-prod test-client
```

## 28. App-of-Apps with Kustomize

App-of-apps means one root Argo CD Application manages other Argo CD Application manifests.

Repository:

```text
argocd/root/
├── applications/
│   ├── frontend-dev.yaml
│   ├── frontend-prod.yaml
│   └── backend-prod.yaml
└── kustomization.yaml
```

`argocd/root/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - applications/frontend-dev.yaml
  - applications/frontend-prod.yaml
  - applications/backend-prod.yaml
```

Root Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-app
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/retail-gitops.git
    targetRevision: main
    path: argocd/root
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

Production caution:

App-of-apps is powerful but can become hard to debug if there are too many nested layers. ApplicationSet is often cleaner for large multi-cluster/multi-env generation.

## 30. Troubleshooting Kustomize in Argo CD

### 30.1 Application shows `ComparisonError`

Typical causes:

- Invalid `kustomization.yaml`
- Missing resource file
- Bad relative path
- Remote base access failure
- Kustomize version mismatch
- Invalid patch target
- YAML syntax error

Commands:

```bash
oc get application frontend-prod -n openshift-gitops -o yaml
argocd app get frontend-prod
argocd app manifests frontend-prod
```

Repo-server logs:

```bash
oc logs -n openshift-gitops deploy/openshift-gitops-repo-server
```

### 30.2 Error: accumulation failed

Example:

```text
accumulating resources: accumulation err='accumulating resources from ...'
```

Check:

```bash
ls -l apps/frontend/overlays/prod
cat apps/frontend/overlays/prod/kustomization.yaml
kustomize build apps/frontend/overlays/prod
```

Common reasons:

- Wrong relative path to base
- File name typo
- Directory not committed
- Case-sensitive path mismatch

### 30.3 Error: no matches for Id

Example:

```text
no matches for Id Deployment.v1.apps/frontend.[noNs]
```

Meaning:

Your patch target does not match any rendered resource.

Fix:

- Check resource name after namePrefix/nameSuffix
- Check kind/group/version
- Check namespace
- Check whether base includes that resource

### 30.4 Error: failed to find unique target for patch

Meaning:

Patch matches zero or multiple resources.

Fix with explicit target:

```yaml
patches:
  - path: patch.yaml
    target:
      group: apps
      version: v1
      kind: Deployment
      name: frontend
      namespace: retail-prod
```

### 30.5 Namespace issue in RoleBinding subject

Error:

```text
subjects[0].namespace: Required value
```

Fix:

Use Kustomize namespace injection:

```yaml
spec:
  source:
    kustomize:
      namespace: retail-prod
  destination:
    namespace: retail-prod
```

or explicitly set subject namespace in the YAML.

### 30.6 OpenShift Route host not changing

Check rendered output:

```bash
kustomize build apps/frontend/overlays/prod | yq '. | select(.kind=="Route")'
```

Check live route:

```bash
oc get route frontend -n retail-prod -o yaml
```

If route name has prefix/suffix, check actual name:

```bash
oc get route -n retail-prod
```

### 30.7 Sync fails with immutable field

Example:

```text
field is immutable
```

Typical causes:

- Deployment selector changed
- Service clusterIP changed
- PVC storageClass changed
- Route fields changed in unsupported way

Fix options:

- Avoid changing immutable fields
- Recreate resource during maintenance
- Use blue/green naming
- Use sync option `Replace=true` only with full understanding

### 30.8 Resource is OutOfSync immediately after sync

Possible causes:

- OpenShift defaulting changed live object
- Operator mutates custom resource
- Admission webhook injects fields
- Resource quantity normalization, for example `1000m` vs `1`
- Generated fields not ignored
- Argo CD tracking label conflict

Check:

```bash
argocd app diff frontend-prod
oc get <kind> <name> -n <namespace> -o yaml
```

Use diff customization only after identifying the exact field.

### 30.9 Repo-server cannot access private remote base

Symptoms:

```text
authentication required
repository not found
permission denied
```

Fix:

- Use same credentials boundary
- Add repo credentials correctly
- Prefer HTTPS if SSH has FIPS or firewall issues
- Avoid remote private bases across unrelated teams

### 30.10 Kustomize build works locally but not in Argo CD

Common causes:

- Different Kustomize version
- Different working directory
- Missing committed files
- Local environment variables not present in repo-server
- Local plugin available but not available in repo-server
- Helm support enabled locally but not in Argo CD

Check:

```bash
kustomize version
argocd app manifests frontend-prod
oc exec -n openshift-gitops deploy/openshift-gitops-repo-server -- kustomize version
```

## 31. Production Best Practices

### 31.1 Keep base clean

Base should contain common, environment-neutral resources.

Do not put production-only settings in base unless all environments truly need them.

### 31.2 Keep overlays small

If an overlay is larger than the base, your design is probably wrong.

### 31.3 Use stable labels from day one

Avoid mutating selectors later.

### 31.4 Prefer JSON 6902 patches for OpenShift CRs

OpenShift CRDs and operator CRs often behave better with explicit JSON patch paths.

### 31.5 Pin production revisions

For production Applications, prefer tag, release branch, or commit SHA:

```yaml
targetRevision: release-2026.07.03
```

Avoid:

```yaml
targetRevision: HEAD
```

for critical production workloads unless your promotion workflow is designed around it.

### 31.6 Do not store plain secrets in Git

Use a supported secret-management workflow.

### 31.7 Use AppProjects seriously

Restrict source repos, destinations, and resource kinds.

### 31.8 Validate with CI

Pipeline steps:

```bash
kustomize build apps/frontend/overlays/dev > /tmp/dev.yaml
kustomize build apps/frontend/overlays/prod > /tmp/prod.yaml
oc apply --dry-run=server -f /tmp/prod.yaml
conftest test /tmp/prod.yaml
kubeconform -strict /tmp/prod.yaml
```

### 31.9 Use sync waves for operators and dependencies

Especially for:

- Namespaces
- CRDs
- Operators
- Operator custom resources
- RBAC
- Webhooks

### 31.10 Avoid global build options unless necessary

Global Kustomize options affect all Kustomize applications in that Argo CD instance.

### 32.1 Base + environment overlay

Best for application teams.

```text
base -> dev/stage/prod overlays
```

### 32.2 Base + cluster overlay

Best for multi-cluster platform operations.

```text
base -> ocp-east/ocp-west/ocp-dr overlays
```

### 32.3 Components for optional features

Best for cross-cutting features.

```text
monitoring component
network-policy component
```

### 32.4 ApplicationSet + Kustomize overlays

Best for many environments or clusters.

```text

```

### 32.5 App-of-apps bootstrap

Best for initial cluster bootstrapping.


Kustomize is not a progressive delivery controller. For canary/blue-green, combine GitOps with:

- Argo Rollouts
- OpenShift Service Mesh
- Route weighted backends
- Separate Applications per color

## 34. Example: Patching Node Placement

Base Deployment does not care where it runs.

Production overlay adds node placement:

```yaml
- op: add
  path: /spec/template/spec/nodeSelector
  value:
    node-role.kubernetes.io/app: ""
- op: add
  path: /spec/template/spec/tolerations
  value:

      operator: Equal
      value: app
      effect: NoSchedule
```

Useful for OpenShift clusters with dedicated node pools:

## 37. Interview and Real-World Questions

### Q1. How does Argo CD know to use Kustomize?

Argo CD detects a Kustomize application when the source path contains a Kustomize configuration file such as `kustomization.yaml`. It renders the path using Kustomize in the repo-server.

### Q2. What is the difference between Helm and Kustomize?

Helm templates YAML using values. Kustomize starts with valid YAML and applies overlays, patches, generators, and transformers. Helm is packaging plus templating. Kustomize is template-free customization.

### Q3. Where does Kustomize run in Argo CD?

In the repo-server, during manifest generation.

### Q4. Why can Kustomize work locally but fail in Argo CD?

Different Kustomize version, missing files in Git, private remote base credentials, disabled Helm support, unavailable plugins, or different build options.

### Q5. Why should you be careful with `commonLabels`?

Because labels can affect selectors. Changing selectors can cause immutable field errors or traffic mismatch.

### Q6. What is the best way to manage dev/stage/prod differences?

Use a common base and overlays per environment. Keep overlays small and review rendered diffs.

### Q7. How do you patch an OpenShift Route with Kustomize?

Use JSON 6902 patches targeting `route.openshift.io/v1`, kind `Route`.

### Q8. What is the difference between `destination.namespace` and `source.kustomize.namespace`?

`destination.namespace` tells Argo CD where to apply namespaced resources when namespace is missing. `source.kustomize.namespace` tells Kustomize to inject namespace fields during rendering and is often safer for nested namespace fields.

### Q9. What is the risk of global `kustomize.buildOptions`?

It affects all Kustomize apps in that Argo CD instance and can alter rendering or security behavior globally.

### Q10. How do you troubleshoot Kustomize render errors?

Run local `kustomize build`, check `argocd app manifests`, inspect repo-server logs, verify paths, patch targets, and Kustomize version.

## 40. Production Mental Model

Think of Kustomize integration in OpenShift GitOps like this:

```text
Kustomize decides what YAML should look like.
Argo CD decides whether the cluster matches that YAML.
OpenShift RBAC decides whether Argo CD is allowed to apply that YAML.
OpenShift admission decides whether that YAML is allowed to run.
Operators may mutate or reconcile custom resources after sync.
```

A strong OpenShift GitOps administrator must understand all five layers.

Most real incidents are not caused by Kustomize alone. They happen at boundaries:

- Kustomize rendered the wrong namespace
- Argo CD applied with insufficient permission
- OpenShift SCC rejected the pod
- NetworkPolicy blocked traffic
- Route hostname conflicted
- Operator mutated the resource
- Selector labels changed
- Generated ConfigMap name changed unexpectedly
- Remote base was unreachable
- Kustomize version differed between laptop and repo-server

The solution is disciplined Git structure, local rendering, CI validation, restricted AppProjects, controlled RBAC, and careful sync strategy.

## 42. Final Takeaway

Kustomize integration in OpenShift GitOps is not just a way to change image tags or replica counts. In a mature OpenShift environment, it becomes a disciplined configuration-management layer for applications, namespaces, operators, policies, and cluster standards.

Use Kustomize for reusable YAML composition. Use Argo CD for continuous reconciliation. Use OpenShift RBAC, SCC, NetworkPolicy, and AppProject controls to make the model safe. Use CI and local rendering to catch problems before Argo CD catches them in production.
