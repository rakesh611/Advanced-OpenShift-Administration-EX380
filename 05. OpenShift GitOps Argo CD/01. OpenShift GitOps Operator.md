# OpenShift GitOps Operator in OpenShift GitOps / Argo CD

**Audience:** Advanced OpenShift Administration / 10+ years experience  
**Focus:** Red Hat OpenShift GitOps Operator, Argo CD control plane, production operations, security, troubleshooting, and real-world administration  
**Platform context:** OpenShift Container Platform with Red Hat OpenShift GitOps Operator

---

## 1. What is the OpenShift GitOps Operator?

The **OpenShift GitOps Operator** is the Red Hat-supported Operator that installs, manages, upgrades, and reconciles **Argo CD** on OpenShift.

In simple words:

> OpenShift GitOps Operator manages the Argo CD control plane, and Argo CD manages your cluster/application desired state from Git.

The Operator is responsible for:

- Installing Argo CD components
- Creating a default cluster-scoped Argo CD instance
- Managing Argo CD custom resources
- Reconciling Argo CD deployments, services, routes, RBAC, config maps, secrets, and service accounts
- Handling upgrades through Operator Lifecycle Manager, also called OLM
- Integrating Argo CD with OpenShift authentication, routes, monitoring, and security controls
- Supporting additional user-defined Argo CD instances
- Supporting multi-tenancy patterns for teams and namespaces

Argo CD itself is responsible for:

- Reading desired state from Git
- Comparing Git state with live cluster state
- Showing drift
- Syncing manifests into OpenShift
- Enforcing declarative application delivery
- Managing applications, AppProjects, ApplicationSets, and sync policies

## 2. Why OpenShift GitOps Operator matters for advanced administration

In a small lab, you can install upstream Argo CD manually with YAML or Helm. In enterprise OpenShift, that is usually not enough.

A senior OpenShift administrator needs:

- Supported installation lifecycle
- Controlled upgrades
- OpenShift route integration
- OAuth / Dex integration
- Cluster monitoring support
- Security context compatibility
- Multi-tenant isolation
- GitOps control-plane lifecycle management
- Declarative Argo CD instance management
- Repeatable disaster recovery
- Clear RBAC boundaries
- Auditability
- Integration with OpenShift Console

The OpenShift GitOps Operator provides those enterprise controls.

## 3. Core GitOps concept

GitOps means Git becomes the source of truth for application and platform configuration.

Traditional administration:

```text
Admin runs oc apply manually
Cluster changes immediately
Git may or may not be updated later
No reliable drift control
```

GitOps administration:

```text
Admin changes Git
Pull request review happens
Argo CD detects change
Argo CD applies desired state
Cluster converges to Git
Drift is visible and correctable
```

The workflow is:

```text
Developer/Admin -> Git repo -> Argo CD -> OpenShift API -> Cluster resources
```

## 5. Main Argo CD components installed by the Operator

### 5.1 Argo CD API Server / UI

Component usually appears as:

```bash
openshift-gitops-server
```

Purpose:

- Serves Argo CD UI
- Serves Argo CD API
- Handles CLI access
- Integrates with OpenShift Routes
- Handles login through local admin or SSO
- Communicates with Redis, repo server, and application controller

Common checks:

```bash
oc get deploy -n openshift-gitops | grep server
oc get route -n openshift-gitops
oc logs deploy/openshift-gitops-server -n openshift-gitops
```

### 5.2 Application Controller

Component usually appears as:

```bash
openshift-gitops-application-controller
```

Purpose:

- Watches `Application` resources
- Compares desired Git state with live state
- Calculates sync status
- Applies resources during sync
- Handles pruning, self-healing, hooks, sync waves, and health assessment

Common checks:

```bash
oc get statefulset -n openshift-gitops | grep application-controller
oc logs statefulset/openshift-gitops-application-controller -n openshift-gitops
```

Important production point:

- If the controller is down, the UI might still load, but sync and reconciliation will be impacted.

### 5.3 Repo Server

Component usually appears as:

```bash
openshift-gitops-repo-server
```

Purpose:

- Clones Git repositories
- Renders manifests from Helm, Kustomize, Jsonnet, plain YAML, or Config Management Plugins
- Talks to Git servers
- Uses SSH known hosts, TLS certificates, repository credentials, and plugins

Common issues:

- Git authentication failure
- Unknown SSH host key
- TLS certificate error
- Helm chart rendering error
- Kustomize build error
- Plugin sidecar failure
- Large repository performance issues

Common checks:

```bash
oc logs deploy/openshift-gitops-repo-server -n openshift-gitops
oc get cm -n openshift-gitops | grep argocd
oc get secret -n openshift-gitops | grep repo
```

### 5.4 Redis

Purpose:

- Caches Argo CD state
- Improves API/UI performance
- Stores temporary application and comparison data

In HA mode, Redis can be deployed with HA-related components.

Common checks:

```bash
oc get pods -n openshift-gitops | grep redis
oc logs -n openshift-gitops <redis-pod-name>
```

### 5.5 Dex / SSO

Purpose:

- Provides identity federation for Argo CD
- Integrates with OpenShift OAuth
- Allows OpenShift users and groups to log in to Argo CD

In modern OpenShift GitOps versions, SSO should be configured through `.spec.sso`, not the old `.spec.dex` method.

### 5.6 ApplicationSet Controller

Purpose:

- Generates multiple Argo CD `Application` resources
- Supports Git, cluster, list, matrix, merge, pull request, and other generator patterns
- Useful for multi-cluster and multi-environment deployments

Example use cases:

- Deploy same application to dev, test, prod
- Deploy same baseline to many clusters
- Generate applications from directories in a Git repository
- Manage tenant applications dynamically

### 5.7 Notifications Controller

Purpose:

- Sends notifications for sync failures, health changes, degraded apps, or successful syncs
- Can integrate with webhook, Slack, email, Teams, and other services depending on configuration

Enable example:

```bash
oc patch argocd openshift-gitops \
  -n openshift-gitops \
  --type merge \
  --patch '{"spec":{"notifications":{"enabled":true}}}'
```

## 6. Installing the OpenShift GitOps Operator

### 6.1 Prerequisites

You normally need:

- OpenShift cluster access
- `cluster-admin` privileges
- `oc` CLI installed
- Marketplace capability enabled or Red Hat Operator catalog configured
- No conflicting community Argo CD Operator installed

Check login:

```bash
oc whoami
oc auth can-i '*' '*' --all-namespaces
```

Check catalog source:

```bash
oc get catalogsource -n openshift-marketplace
oc get packagemanifest openshift-gitops-operator -n openshift-marketplace
```

### 6.2 Install by CLI

Create namespace:

```bash
oc create ns openshift-gitops-operator
```

Enable cluster monitoring for the Operator namespace:

```bash
oc label namespace openshift-gitops-operator openshift.io/cluster-monitoring=true
```

Create OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec: {}
```

Apply:

```bash
oc apply -f gitops-operatorgroup.yaml
```

Create Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  channel: latest
  installPlanApproval: Automatic
  name: openshift-gitops-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Apply:

```bash
oc apply -f gitops-subscription.yaml
```

Verify:

```bash
oc get csv -n openshift-gitops-operator
oc get pods -n openshift-gitops-operator
oc get argocd -A
```

### 6.3 Install with specific channel

For production, many organizations avoid blindly tracking `latest`. They pin to a supported minor channel such as:

```yaml
spec:
  channel: gitops-1.20
```

Example Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  channel: gitops-1.20
  installPlanApproval: Manual
  name: openshift-gitops-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Production recommendation:

- Use `Manual` approval in regulated environments.
- Test upgrades in non-production first.
- Keep GitOps Operator version compatible with your OpenShift version.
- Review release notes before approving InstallPlans.

Check pending InstallPlan:

```bash
oc get installplan -n openshift-gitops-operator
oc describe installplan <installplan-name> -n openshift-gitops-operator
```

Approve manually:

```bash
oc patch installplan <installplan-name> \
  -n openshift-gitops-operator \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

## 10. User-defined Argo CD instances

### 10.1 Why create user-defined instances?

Create separate Argo CD instances when you need:

- Team isolation
- Separate RBAC boundaries
- Separate Git credentials
- Separate sync windows
- Separate maintenance windows
- Separate lifecycle and scaling
- Tenant-specific Argo CD admins
- Reduced blast radius

Example model:

```text
openshift-gitops        -> platform/cluster configuration
team-a-gitops           -> team A applications
team-b-gitops           -> team B applications
payments-gitops         -> payment workloads
security-gitops         -> security policies
```

### 10.2 Create user-defined namespace

```bash
oc new-project team-a-gitops
```

### 10.3 Create ArgoCD instance

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: team-a-gitops
  namespace: team-a-gitops
spec:
  server:
    route:
      enabled: true
  rbac:
    defaultPolicy: role:readonly
    policy: |
      g, team-a-admins, role:admin
      g, team-a-developers, role:readonly
    scopes: '[groups]'
```

Apply:

```bash
oc apply -f team-a-argocd.yaml
```

Verify:

```bash
oc get argocd -n team-a-gitops
oc get pods -n team-a-gitops
oc get route -n team-a-gitops
```

### 10.4 Namespace-scoped behavior

By default, a user-defined Argo CD instance has permissions mainly in its own namespace. For managing other namespaces, you must explicitly configure permissions and namespace association.

This is a major difference between:

- Default cluster-scoped Argo CD instance
- User-defined namespaced Argo CD instance
- User-defined cluster-scoped Argo CD pattern

## 11. Managing Application resources outside the control-plane namespace

Modern OpenShift GitOps supports controlling where `Application` and `ApplicationSet` resources can be created.

This is useful for multi-tenancy.

Example:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: platform-gitops
  namespace: platform-gitops
spec:
  sourceNamespaces:
    - team-a
    - team-b
    - app-*
  applicationSet:
    sourceNamespaces:
      - team-a
      - team-b
```

Meaning:

- Users can create `Application` resources in allowed source namespaces.
- Argo CD can reconcile those Applications.
- ApplicationSet creation can also be delegated to selected namespaces.

Important:

- You must configure `AppProject` boundaries also.
- Do not rely only on Argo CD RBAC.
- Use Kubernetes RBAC and AppProject restrictions together.

## 12. AppProject security model

`AppProject` is one of the most important security objects in Argo CD.

It controls:

- Which Git repositories are allowed
- Which destination clusters are allowed
- Which namespaces are allowed
- Which cluster-scoped resources are allowed
- Which namespace-scoped resources are allowed
- Sync windows
- Project roles

### 12.1 Dangerous default AppProject

The default `AppProject` is often too permissive.

Example dangerous behavior:

```yaml
sourceRepos:
  - '*'
destinations:
  - namespace: '*'
    server: '*'
clusterResourceWhitelist:
  - group: '*'
    kind: '*'
```

For production, lock it down.

### 12.2 Locked-down default project

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: default
  namespace: openshift-gitops
spec:
  sourceRepos: []
  destinations: []
  clusterResourceWhitelist: []
  namespaceResourceWhitelist: []
```

### 12.3 Production project example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-a
  namespace: team-a-gitops
spec:
  description: Team A application boundary
  sourceRepos:
    - https://git.example.com/team-a/*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: team-a-dev
    - server: https://kubernetes.default.svc
      namespace: team-a-test
    - server: https://kubernetes.default.svc
      namespace: team-a-prod
  namespaceResourceWhitelist:
    - group: '*'
      kind: '*'
  clusterResourceWhitelist: []
```

This prevents the team from deploying cluster-scoped objects unless explicitly allowed.

## 13. Argo CD RBAC in OpenShift GitOps

Argo CD RBAC controls what a logged-in Argo CD user can do inside Argo CD.

It does not replace Kubernetes RBAC.

You need both:

```text
Kubernetes RBAC -> controls access to Kubernetes/OpenShift objects
Argo CD RBAC    -> controls access inside Argo CD
AppProject      -> controls what Argo CD is allowed to deploy
```

### 13.1 Configure RBAC in ArgoCD CR

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  rbac:
    defaultPolicy: role:readonly
    policy: |
      p, role:team-a-admin, applications, get, team-a/*, allow
      p, role:team-a-admin, applications, sync, team-a/*, allow
      p, role:team-a-admin, applications, update, team-a/*, allow
      p, role:team-a-admin, logs, get, team-a/*, allow
      g, ocp-team-a-admins, role:team-a-admin
    scopes: '[groups]'
```

### 13.2 Disable built-in admin account

For production with SSO enabled:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  disableAdmin: true
```

Senior admin recommendation:

- Keep admin enabled only during initial bootstrap or emergency break-glass.
- Prefer SSO group-based admin access.
- Store break-glass credentials in a controlled vault if the admin user is temporarily needed.
- Audit who has access to the Argo CD namespace.

## 14. SSO with OpenShift OAuth

OpenShift GitOps can use Dex with OpenShift OAuth.

### 14.1 Example SSO configuration

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  sso:
    provider: dex
    dex:
      openShiftOAuth: true
```

Apply:

```bash
oc patch argocd openshift-gitops \
  -n openshift-gitops \
  --type merge \
  -p '{"spec":{"sso":{"provider":"dex","dex":{"openShiftOAuth":true}}}}'
```

Check Dex:

```bash
oc get pods -n openshift-gitops | grep dex
oc logs deploy/openshift-gitops-dex-server -n openshift-gitops
```

### 14.2 Map OpenShift groups to Argo CD roles

Create OpenShift group:

```bash
oc adm groups new ocp-gitops-admins rakesh
```

RBAC mapping:

```yaml
spec:
  rbac:
    defaultPolicy: role:readonly
    policy: |
      g, ocp-gitops-admins, role:admin
    scopes: '[groups]'
```

### 14.3 SSO troubleshooting

Check OAuth route/callback issues:

```bash
oc get route -n openshift-gitops
oc logs deploy/openshift-gitops-server -n openshift-gitops
oc logs deploy/openshift-gitops-dex-server -n openshift-gitops
oc get oauthclient
```

Common symptoms:

| Symptom | Possible cause |
|---|---|
| Login button missing | SSO not configured or server not reconciled |
| Redirect loop | Callback URL / route / TLS issue |
| User logs in but has no permission | RBAC group mapping missing |
| Groups not visible | `scopes` not configured correctly |
| Dex pod crash | Invalid SSO configuration |

## 15. TLS, routes, and certificates

### 15.1 Route behavior

Argo CD server is exposed through an OpenShift Route when enabled.

Example:

```yaml
spec:
  server:
    route:
      enabled: true
```

In recent OpenShift GitOps versions, route TLS defaults changed to re-encrypt for Argo CD routes. That means traffic from router to backend is also encrypted.

Check route:

```bash
oc get route openshift-gitops-server -n openshift-gitops -o yaml
```

### 15.2 Custom hostname

```yaml
spec:
  server:
    route:
      enabled: true
      host: argocd.apps.example.com
```

### 15.3 Custom TLS

Depending on your version and policy, custom TLS can be configured through route TLS settings and Kubernetes TLS secrets.

Example TLS secret:

```bash
oc create secret tls argocd-custom-tls \
  -n openshift-gitops \
  --cert=tls.crt \
  --key=tls.key
```

Example concept in ArgoCD CR:

```yaml
spec:
  server:
    route:
      enabled: true
      tls:
        termination: reencrypt
```

Always verify the exact supported field names with:

```bash
oc explain argocd.spec.server.route.tls
```

### 15.4 Git repository TLS trust

Repo server must trust Git server certificates.

Common issue:

```text
x509: certificate signed by unknown authority
```

Fix options:

- Use public CA-signed Git certificate
- Configure custom CA trust for repo server
- Add certificate trust through supported ArgoCD CR fields/config maps based on version

Check repo server logs:

```bash
oc logs deploy/openshift-gitops-repo-server -n openshift-gitops
```

## 16. Repository credentials and secrets

Argo CD supports different repository authentication methods:

- HTTPS username/password
- HTTPS token
- SSH private key
- GitHub App credentials
- TLS client certificate

### 16.1 Add repository with CLI

```bash
argocd repo add https://git.example.com/platform/cluster-config.git \
  --username gituser \
  --password '<TOKEN>'
```

### 16.2 Declarative repository secret

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: repo-platform-cluster-config
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  type: git
  url: https://git.example.com/platform/cluster-config.git
  username: gituser
  password: REPLACE_WITH_TOKEN
```

Production recommendation:

- Do not commit real tokens to Git.
- Use Sealed Secrets, External Secrets Operator, Vault, or another secret management approach.
- Use read-only deploy tokens when possible.
- Rotate tokens regularly.
- Scope tokens to specific repositories.

## 17. Application object deep dive

An `Application` connects Git source to OpenShift destination.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-dev
  namespace: openshift-gitops
spec:
  project: team-a
  source:
    repoURL: https://git.example.com/team-a/nginx.git
    targetRevision: main
    path: overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: team-a-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=false
```

### 17.1 Key fields

| Field | Meaning |
|---|---|
| `spec.project` | AppProject boundary |
| `spec.source.repoURL` | Git repo URL |
| `spec.source.targetRevision` | Branch, tag, or commit |
| `spec.source.path` | Manifest path |
| `spec.destination.server` | Target Kubernetes API |
| `spec.destination.namespace` | Target namespace |
| `spec.syncPolicy.automated` | Auto-sync settings |
| `spec.syncPolicy.syncOptions` | Sync behavior options |

### 17.2 Manual sync

```bash
argocd app sync nginx-dev
```

### 17.3 Check status

```bash
argocd app get nginx-dev
oc get application nginx-dev -n openshift-gitops -o yaml
```

## 18. Sync policies and operational safety

### 18.1 Manual sync

Manual sync is safer during early adoption.

```yaml
syncPolicy: {}
```

Use when:

- New GitOps migration
- Sensitive production systems
- Operators or CRDs are involved
- You need manual approval outside Git

### 18.2 Automated sync

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

Meaning:

- `prune: true` removes resources deleted from Git
- `selfHeal: true` corrects manual drift

Production caution:

- Automated prune can delete resources if Git path, branch, or generator logic is wrong.
- Use AppProject and sync windows.
- Use pull request reviews.
- Avoid broad wildcards for cluster resources.

### 18.3 Sync options

Common options:

```yaml
syncOptions:
  - CreateNamespace=true
  - PrunePropagationPolicy=foreground
  - PruneLast=true
  - ApplyOutOfSyncOnly=true
  - ServerSideApply=true
```

Use carefully:

| Option | Use case | Risk |
|---|---|---|
| `CreateNamespace=true` | Auto-create target namespace | May bypass namespace governance |
| `PruneLast=true` | Delete old resources after apply | Safer dependency handling |
| `ServerSideApply=true` | Large resources / SSA workflows | Field ownership conflicts |
| `ApplyOutOfSyncOnly=true` | Reduce API load | Can hide repeated apply behavior |

## 19. Sync waves and hooks

Sync waves control order.

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

Lower wave runs first:

```text
-10 -> CRDs
0   -> namespaces, service accounts, config maps
10  -> deployments
20  -> routes
30  -> post-sync jobs
```

Hook example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
```

Common hook types:

- `PreSync`
- `Sync`
- `PostSync`
- `SyncFail`
- `PostDelete`

Use cases:

- Database migrations
- Smoke tests
- Validation jobs
- Cleanup jobs

Production caution:

- Hooks can block sync.
- Failed hooks can leave apps degraded.
- Avoid long-running hooks unless needed.

## 20. Resource tracking

Argo CD tracks managed resources using labels and/or annotations.

Common setting:

```yaml
spec:
  resourceTrackingMethod: annotation+label
  installationID: platform-gitops
```

Why this matters:

- Multiple Argo CD instances can otherwise conflict.
- Applications with same names can cause tracking confusion.
- Annotation-based tracking is safer in multi-instance environments.

Recommendation for multi-instance production:

```yaml
spec:
  installationID: team-a-gitops
  resourceTrackingMethod: annotation+label
```

## 22. Resource requests and limits

Argo CD can consume significant CPU and memory in large environments.

Factors that increase usage:

- Number of Applications
- Number of clusters
- Large Git repositories
- Helm rendering
- Kustomize overlays
- ApplicationSet generators
- Auto-sync frequency
- Number of live resources
- Diff complexity
- Repo server plugins

Example resource configuration:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  server:
    resources:
      requests:
        cpu: 250m
        memory: 512Mi
      limits:
        cpu: "1"
        memory: 1Gi
  repo:
    resources:
      requests:
        cpu: 500m
        memory: 1Gi
      limits:
        cpu: "2"
        memory: 2Gi
  controller:
    resources:
      requests:
        cpu: 500m
        memory: 1Gi
      limits:
        cpu: "2"
        memory: 2Gi
```

Patch example:

```bash
oc patch argocd openshift-gitops \
  -n openshift-gitops \
```

### 27.4 Application sync fails due to RBAC

Error example:

```text

cannot create resource
forbidden: User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller" cannot create ...
```

Check service account:

```bash

  --as system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n team-a-dev
```

Fix namespace role binding:

```bash
oc adm policy add-role-to-user admin \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n team-a-dev
```

For cluster-scoped resources, use carefully:

```bash
oc adm policy add-cluster-role-to-user <cluster-role> \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Senior admin warning:

- Do not blindly give `cluster-admin` to the Argo CD controller.
- Create narrow ClusterRoles where possible.
- Use AppProject restrictions to limit what Argo CD can deploy.

## 29. Backup and disaster recovery

For Argo CD, the real source of truth should be Git, but you still need backup for operational state and credentials.

Back up:

- `ArgoCD` CRs
- `Application` CRs
- `ApplicationSet` CRs
- `AppProject` CRs
- Repository credential secrets
- Cluster credential secrets
- SSO configuration
- TLS secrets
- Notifications configuration
- Custom ConfigMaps
- Custom RBAC policies

Example backup:

```bash
oc get argocd,applications,applicationsets,appprojects -A -o yaml > argocd-resources.yaml
oc get secrets,cm -n openshift-gitops -o yaml > argocd-config-secrets.yaml
```

Restore order:

1. Install OpenShift GitOps Operator.
2. Restore ArgoCD CR.
3. Restore secrets/config maps.
4. Restore AppProjects.
5. Restore Applications/ApplicationSets.
6. Validate Git repo connectivity.
7. Sync carefully.

Disaster recovery caution:

- If Git is unavailable, Argo CD cannot render desired state.
- If repository credentials are lost, apps may show Unknown/OutOfSync.
- If Argo CD is restored with automated prune enabled, validate destination before allowing sync.

```text
    ├── dev/
    │   └── kustomization.yaml
    ├── test/
    │   └── kustomization.yaml

        └── kustomization.yaml
```

### 30.2 App-of-apps pattern

Root app:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-app
  namespace: openshift-gitops
spec:
  project: platform
  source:
    repoURL: https://git.example.com/platform/cluster-config.git

```

This root app manages child Application manifests.

Production caution:

- Bad root app commit can affect many apps.
- Use branch protection and mandatory review.
- Consider sync windows for production.

## 31. Multi-tenancy design

### 31.1 Shared Argo CD instance model

```text
One Argo CD instance
Multiple AppProjects
Multiple teams
```

Pros:

- Easier central administration
- Lower resource usage
- Single UI
- Easier platform governance

Cons:

- Larger blast radius
- RBAC must be perfect
- More complex AppProject design
- Shared repo-server and controller load

### 31.2 Dedicated Argo CD per team model

```text
team-a-gitops -> team-a namespaces
team-b-gitops -> team-b namespaces
```

Pros:

- Stronger isolation
- Separate credentials
- Separate upgrades/configuration
- Smaller blast radius

Cons:

- More resources
- More operational overhead
- More instances to monitor
- More certificate/routes/RBAC to manage

### 31.3 Recommended enterprise pattern

Use a hybrid model:

```text
platform-gitops       -> cluster config, operators, security baseline
team-gitops-shared    -> low-risk app teams
critical-team-gitops  -> high-risk/high-compliance teams
```

## 32. Security best practices

### 32.1 Protect the Argo CD namespace

Do not grant developers access to:

```text
openshift-gitops
team-a-gitops
platform-gitops
```

unless they are intended Argo CD administrators for that instance.

Why?

- Repo credentials are stored there.
- Argo CD admin secrets are stored there.
- RBAC config maps are stored there.
- Application controller service account exists there.
- Editing Applications there can deploy workloads.

### 32.2 Lock down default AppProject

Do not leave default project unrestricted.

### 32.3 Disable admin account after SSO

```yaml
spec:
  disableAdmin: true
```

### 32.4 Use least privilege for controller

Avoid:

```bash
oc adm policy add-cluster-role-to-user cluster-admin system:serviceaccount:...
```

Prefer:

- Namespace `admin` only where needed
- Custom ClusterRoles for limited cluster resources
- Separate Argo CD instances for cluster config vs applications

### 32.5 Secure Git credentials

- Use read-only tokens
- Rotate regularly
- Use secret operators
- Avoid personal access tokens where possible
- Prefer deploy keys or GitHub App integration
- Limit token scope

### 32.6 Use signed commits/tags where possible

For regulated environments:

- Protect production branches
- Require pull request approval
- Require signed commits
- Require CI validation
- Require security scans

### 32.7 Avoid direct cluster changes

Use manual changes only for emergency break-glass, then commit the change back to Git.

## 34. Advanced troubleshooting scenarios

### Scenario 1: Application stuck in `Unknown`

Symptoms:

```text
Health: Unknown
Sync: Unknown
```

Check:

```bash
argocd app get <app>
oc describe application <app> -n <argocd-ns>
oc logs deploy/openshift-gitops-repo-server -n openshift-gitops
oc logs statefulset/openshift-gitops-application-controller -n openshift-gitops
```

Likely causes:

- Repo connection failure
- Manifest generation failure
- Kubernetes API access failure
- CRD missing
- Controller cannot list target resource

Fix:

- Fix Git credentials
- Fix manifest path
- Install required CRDs before CRs
- Fix controller RBAC
- Check API server connectivity

---

### Scenario 2: Application sync succeeds but pod fails in OpenShift

Argo CD sync means resources were applied. It does not guarantee application runtime success.

Check:

```bash
oc get pods -n <app-ns>
oc describe pod <pod> -n <app-ns>
oc logs <pod> -n <app-ns>
oc get events -n <app-ns> --sort-by=.lastTimestamp
```

Possible OpenShift-specific causes:

- SCC violation
- ImagePullBackOff
- Quota exceeded
- LimitRange missing default
- PVC pending
- Route/service selector mismatch
- NetworkPolicy blocking traffic
- Readiness/liveness probe failing

---

### Scenario 3: Argo CD keeps reverting manual fixes

Cause:

- Self-heal enabled.

Check:

```bash
argocd app get <app>
```

Fix:

- Commit the desired fix to Git.
- Or temporarily disable self-heal:

```yaml
syncPolicy:
  automated:
    selfHeal: false
```

Operational rule:

> In GitOps, live cluster changes are temporary unless Git is updated.

---

### Scenario 4: App deletion does not delete resources

Possible causes:

- Finalizers missing
- Prune disabled
- Resource finalizers stuck
- AppProject does not allow deletion
- Kubernetes finalizer protection

Check:

```bash
oc get application <app> -n <argocd-ns> -o yaml | grep -A5 finalizers
argocd app delete <app>
```

Foreground deletion finalizer example:

```yaml
metadata:
  finalizers:
    - resources-finalizer.argocd.argoproj.io
```

---

### Scenario 5: Operator overwrites manual changes

Cause:

- The OpenShift GitOps Operator reconciles owned resources.

Bad practice:

```bash
oc edit deployment openshift-gitops-server -n openshift-gitops
```

Better practice:

```bash
oc edit argocd openshift-gitops -n openshift-gitops
```

Rule:

> Modify the ArgoCD CR, not the generated deployments, unless Red Hat support directs otherwise.

## 36. Interview-level explanation

If asked, “What is the OpenShift GitOps Operator?” answer like this:

> The OpenShift GitOps Operator is the Red Hat-supported Operator that installs and manages Argo CD on OpenShift. It creates a default Argo CD instance in the `openshift-gitops` namespace and allows administrators to create additional Argo CD instances using the `ArgoCD` custom resource. The Operator reconciles Argo CD components such as the server, repo server, application controller, Redis, Dex, ApplicationSet controller, and notifications controller. It integrates Argo CD with OpenShift features like Routes, OAuth, RBAC, monitoring, NetworkPolicy, and OLM-based upgrades. In production, we use it to declaratively manage platform and application delivery from Git while controlling access through Kubernetes RBAC, Argo CD RBAC, and AppProjects.

## 38. Common mistakes by administrators

| Mistake | Impact | Better approach |
|---|---|---|
| Giving developers access to `openshift-gitops` namespace | They can become Argo CD admins | Grant access through Argo CD RBAC, not namespace access |
| Leaving default AppProject unrestricted | Users can deploy too broadly | Lock default project and create scoped projects |
| Giving Argo CD controller `cluster-admin` | Huge blast radius | Use least-privilege roles |
| Editing generated deployments directly | Operator reverts changes | Edit ArgoCD CR |
| Enabling auto-prune everywhere | Accidental deletion risk | Use carefully with reviews and sync windows |
| Ignoring repo-server sizing | Slow sync/render failures | Allocate resources and split repos |
| Using personal Git tokens | Token expiry/security risk | Use service/deploy tokens |
| No backup of secrets | DR failure | Backup encrypted secrets/configs |
| No version pinning | Surprise upgrades | Use manual InstallPlans/channels |
| No AppProject governance | Weak tenant isolation | AppProject per team/environment |

### Task 2: Enable OpenShift SSO

Patch:

```bash
oc patch argocd openshift-gitops \

  -p '{"spec":{"sso":{"provider":"dex","dex":{"openShiftOAuth":true}}}}'
```

### Task 3: Configure RBAC

```yaml
spec:
  rbac:
    defaultPolicy: role:readonly
    policy: |
      g, ocp-gitops-admins, role:admin
    scopes: '[groups]'
```

### Task 4: Create AppProject

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-a
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://git.example.com/team-a/*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: team-a-dev
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
    - group: '*'
      kind: '*'
```

### Task 5: Create Application

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: team-a-nginx
  namespace: openshift-gitops
spec:
  project: team-a
  source:
    repoURL: https://git.example.com/team-a/nginx.git
    targetRevision: main
    path: overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: team-a-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

## 40. Final senior-admin notes

For a 10-year experienced OpenShift administrator, OpenShift GitOps Operator should not be treated as only an installation tool. It is a control-plane lifecycle manager for Argo CD.

Think in three layers:

```text
Layer 1: OpenShift GitOps Operator
  Manages Argo CD lifecycle

Layer 2: Argo CD
  Manages GitOps reconciliation

Layer 3: Applications/platform manifests
  Desired state from Git
```

The most important production principles are:

1. Protect the Argo CD namespace.
2. Lock down default AppProject.
3. Use SSO and group-based RBAC.
4. Disable the built-in admin account after bootstrap.
5. Use least-privilege Kubernetes RBAC for Argo CD service accounts.
6. Pin Operator upgrade channels in production.
7. Test upgrades before production.
8. Monitor repo-server and application-controller carefully.
9. Treat Git as the source of truth.
10. Never let convenience destroy tenant isolation.
