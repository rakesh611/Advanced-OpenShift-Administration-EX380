# Multi-cluster GitOps Concept in OpenShift GitOps / Argo CD

**Audience:** Advanced OpenShift Administration, senior Linux/OpenShift/Kubernetes administrators, SREs, platform engineers, and DevOps engineers with production responsibilities.  
**Experience level:** Written from a 10-year operations mindset: security, scale, RBAC, failure handling, drift, lifecycle, audit, and production governance.  
**Focus:** Red Hat OpenShift GitOps, Argo CD, ApplicationSet, RHACM integration, and Argo CD Agent-based multi-cluster models.

---

## 1. Executive summary

Multi-cluster GitOps means using Git as the source of truth to define **what should run on many OpenShift clusters**, and using Argo CD/OpenShift GitOps controllers to continuously compare and reconcile the live cluster state against the desired state stored in Git.

In a single-cluster GitOps setup, one Argo CD instance manages applications or cluster configuration in one OpenShift cluster. In a multi-cluster GitOps setup, you extend the same model across many clusters such as:

- `dev`, `stage`, and `prod` clusters
- different data centers
- different cloud providers
- edge clusters
- DR clusters
- regional clusters such as `india-prod`, `us-prod`, `eu-prod`
- tenant-specific clusters
- workload-specific clusters such as platform, logging, monitoring, GPU, or payment clusters

The important idea is not only “deploy one app to many clusters.” The real enterprise goal is:

> A controlled, auditable, repeatable, policy-driven operating model where application configuration, cluster configuration, security controls, RBAC, quotas, limits, namespaces, network policies, operators, and workload placement can be managed consistently across many OpenShift clusters.

For a senior OpenShift administrator, multi-cluster GitOps is about answering these production questions:

- How do we keep 20 clusters configured consistently?
- How do we deploy the same application differently to dev, stage, and prod?
- How do we prevent manual cluster changes from becoming permanent drift?
- How do we onboard a new cluster safely?
- How do we allow application teams to deploy without giving them cluster-admin?
- How do we handle disaster recovery, credentials, RBAC, sync windows, and promotion?
- How do we troubleshoot sync failures across many clusters?
- How do we scale Argo CD safely when the number of clusters and applications grows?

## 2. Official context and current features

This note is aligned with current Red Hat OpenShift GitOps 1.21 and Argo CD documentation available as of **2026-07-03**.

Key official points used in this guide:

- Red Hat OpenShift GitOps is based on Argo CD and is used for declarative continuous delivery and cluster configuration.
- ApplicationSets allow administrators to generate many Argo CD `Application` resources from one `ApplicationSet`, which is one of the main tools for multi-cluster GitOps.
- The Argo CD cluster generator automatically identifies clusters registered with Argo CD by reading Argo CD cluster secrets.
- External cluster credentials are stored by Argo CD as Kubernetes Secrets in the Argo CD namespace.
- Red Hat Advanced Cluster Management can integrate with OpenShift GitOps and use Placement decisions to target managed clusters.
- Argo CD Agent introduces a hub-and-spoke model for managing multiple clusters with pull-based behavior. Argo CD Agent became generally available in OpenShift GitOps 1.19, while the hybrid architecture for gradual adoption is Technology Preview in OpenShift GitOps 1.21.

Official references are listed at the end of this file.

## 3. Mental model: what actually happens

Think of multi-cluster GitOps as a **control loop**.

```text
Git repository
     |
     | desired state: YAML, Helm, Kustomize, Jsonnet, operators, policies
     v
Argo CD / OpenShift GitOps control plane
     |
     | compare desired state with live cluster state
     | detect drift
     | apply manifests if sync is manual or automatic
     v
Target OpenShift clusters
     |
     | live resources: Namespace, Deployment, Route, NetworkPolicy,
     | ResourceQuota, LimitRange, Subscription, OperatorGroup, RBAC, etc.
     v
Status, health, sync result, events, metrics, logs
```

In multi-cluster mode, the destination is not just one cluster. The destination can be generated dynamically from:

- Argo CD cluster secrets
- cluster labels such as `env=prod`, `region=apac`, `team=payments`
- ACM Placement decisions
- Git directory structure
- ApplicationSet generators
- Argo CD Agent mappings

A senior admin must understand three states:

| State | Meaning |
|---|---|
| Desired state | What Git says should exist |
| Live state | What actually exists in the target cluster |
| Reconciled state | The result after Argo CD compares and syncs |

When live state differs from Git, Argo CD marks the application `OutOfSync`. If automated sync and self-heal are enabled, Argo CD can bring the cluster back to the Git-defined state.

## 4. Why multi-cluster GitOps is important in OpenShift

OpenShift clusters are rarely isolated in enterprise environments. A company may have multiple clusters for lifecycle, compliance, geography, capacity, or ownership reasons.

Common examples:

```text
hub-cluster
├── dev-cluster
├── qa-cluster
├── stage-cluster
├── prod-cluster-a
├── prod-cluster-b
├── dr-cluster
├── edge-cluster-01
└── edge-cluster-02
```

Without GitOps, admins often use manual `oc apply`, scripts, Jenkins jobs, or ad-hoc Ansible runs. That works for small environments but becomes risky at scale.

Problems without GitOps:

- No clear source of truth
- Difficult audit trail
- Manual drift between clusters
- Different admins applying different commands
- Hard rollback
- Difficult compliance proof
- Cluster rebuilds take longer
- Security objects differ between environments
- Production changes can bypass review

GitOps solves this by enforcing:

- version control
- pull request review
- approval workflows
- repeatable deployment
- automatic drift detection
- rollback through Git revert
- environment promotion
- standard naming and structure
- cluster configuration as code

For an experienced OpenShift admin, GitOps is not only a deployment tool. It is an **operational governance model**.

## 5. Core components in OpenShift GitOps multi-cluster architecture

### 5.1 Git repository

Git stores desired state.

Examples of content:

- `Namespace`
- `ResourceQuota`
- `LimitRange`
- `NetworkPolicy`
- `Role`, `RoleBinding`, `ClusterRole`, `ClusterRoleBinding`
- `Deployment`, `StatefulSet`, `DaemonSet`
- `Service`, `Route`, `Ingress`
- `ConfigMap`, `Secret` references
- `ServiceAccount`
- `Subscription`, `OperatorGroup`
- `MachineConfig` only with strong governance
- `ArgoCD`, `Application`, `ApplicationSet`, `AppProject`
- Helm charts
- Kustomize overlays

Git should not store raw sensitive values unless encrypted with a proper mechanism such as Sealed Secrets, SOPS, External Secrets Operator, or a vault-backed workflow.

### 5.2 Argo CD / OpenShift GitOps instance

In OpenShift, Red Hat OpenShift GitOps installs and manages Argo CD through the GitOps Operator. The default Argo CD instance commonly runs in:

```text
openshift-gitops
```

Important components:

| Component | Role |
|---|---|
| `argocd-server` | UI/API server |
| `argocd-application-controller` | Reconciliation engine |
| `argocd-repo-server` | Fetches and renders Git, Helm, Kustomize, plugins |
| `argocd-dex-server` | Authentication integration when Dex is used |
| `redis` | Cache and internal state support |
| `applicationset-controller` | Generates Applications from ApplicationSets |
| `notifications-controller` | Sends sync/health notifications when configured |

### 5.3 Argo CD Application

An `Application` maps one Git source to one destination cluster/namespace.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-dev
  namespace: openshift-gitops
spec:
  project: platform-dev
  source:
    repoURL: https://git.example.com/platform/apps.git
    targetRevision: main
    path: apps/web/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: web-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

For multi-cluster GitOps, managing hundreds of `Application` objects manually is not scalable. That is why ApplicationSet becomes important.

### 5.4 Argo CD ApplicationSet

An `ApplicationSet` is a generator of Applications.

It lets you say:

> For every cluster matching this selector, create an Application using this template.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: web-all-dev-clusters
  namespace: openshift-gitops
spec:
  goTemplate: true
  goTemplateOptions:
    - missingkey=error
  generators:
    - clusters:
        selector:
          matchLabels:
            env: dev
  template:
    metadata:
      name: '{{.name}}-web'
    spec:
      project: platform-dev
      source:
        repoURL: https://git.example.com/platform/apps.git
        targetRevision: main
        path: apps/web/overlays/dev
      destination:
        server: '{{.server}}'
        namespace: web
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

This example automatically creates one `Application` per registered cluster labeled `env=dev`.

### 5.5 AppProject

An `AppProject` is a security and governance boundary.

It controls:

- allowed Git repositories
- allowed destination clusters
- allowed destination namespaces
- allowed cluster-scoped resources
- denied resources
- project roles
- JWT tokens for automation

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-prod
  namespace: openshift-gitops
spec:
  description: Payments production GitOps project
  sourceRepos:
    - https://git.example.com/payments/*
  destinations:
    - namespace: payments-*
      server: https://api.prod-a.example.com:6443
    - namespace: payments-*
      server: https://api.prod-b.example.com:6443
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy
```

Production rule:

> Never put every application into the default Argo CD project in a real enterprise environment. Use AppProjects to isolate teams and environments.

### 5.6 Cluster secret

Argo CD knows about external clusters through cluster credentials. These are normally stored as Kubernetes Secrets in the Argo CD namespace.

Simplified example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: prod-a-cluster
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: cluster
    env: prod
    region: india
    team: platform
stringData:
  name: prod-a
  server: https://api.prod-a.example.com:6443
  config: |
    {
      "bearerToken": "REDACTED",
      "tlsClientConfig": {
        "insecure": false,
        "caData": "REDACTED"
      }
    }
```

Those labels become very important for ApplicationSet cluster selection.

## 6. Main multi-cluster GitOps architecture patterns

There is no single correct pattern for every company. Senior administrators must choose based on scale, security, network layout, ownership, compliance, and operations maturity.

### Pattern 1: Central Argo CD pushes to many clusters

This is the classic model.

```text
                Git
                 |
                 v
        Argo CD on hub cluster
          /       |       \
         v        v        v
   dev-cluster stage-cluster prod-cluster
```

How it works:

1. Argo CD runs on a hub or management OpenShift cluster.
2. Each target OpenShift cluster is registered in Argo CD.
3. Argo CD stores each target cluster credential as a cluster secret.
4. Applications target the destination cluster by `server` or `name`.
5. ApplicationSet can generate Applications for selected clusters.
6. The hub Argo CD application controller talks directly to target Kubernetes/OpenShift APIs.

Advantages:

- Simple mental model
- One UI for many clusters
- Easy to start
- ApplicationSet cluster generator works well
- Good for small to medium cluster counts
- Centralized credentials and access control

Disadvantages:

- Hub needs network connectivity to every target API server
- Target cluster credentials are stored centrally
- Hub controller CPU/memory grows with clusters and applications
- One control plane can become a scaling or blast-radius concern
- Firewall and private cluster access can be difficult

Best use cases:

- 2 to 20 clusters
- central platform team
- clusters reachable from hub
- consistent security model
- early enterprise GitOps adoption

### Pattern 2: Argo CD instance per cluster

```text
Git
 |
 +--> Argo CD dev cluster   --> dev workloads
 +--> Argo CD stage cluster --> stage workloads
 +--> Argo CD prod cluster  --> prod workloads
```

How it works:

1. Each cluster runs its own Argo CD instance.
2. Each instance pulls from Git and reconciles locally.
3. Git repository structure determines which cluster gets which configuration.
4. Promotion happens by branch, tag, directory, or pull request.

Advantages:

- No central cluster credential store for all clusters
- Each cluster reconciles locally
- Good network isolation
- Lower blast radius per cluster
- Useful when clusters are owned by different teams or business units

Disadvantages:

- No single UI unless you add ACM, Argo CD Agent, or separate dashboards
- More Argo CD instances to operate
- Need consistent bootstrap process
- Harder cross-cluster reporting

Best use cases:

- strict isolation
- regulated environments
- disconnected or private clusters
- edge clusters
- cluster-per-tenant models

### Pattern 3: RHACM + OpenShift GitOps using Placement

Red Hat Advanced Cluster Management can manage cluster inventory, placement decisions, and integration with OpenShift GitOps.

```text
                Git
                 |
                 v
       Hub cluster with RHACM + OpenShift GitOps
                 |
          Placement / ManagedCluster labels
                 |
       +---------+----------+
       |                    |
 prod clusters         dev clusters
```

In this model:

- ACM knows the managed clusters.
- Placement selects clusters based on labels, claims, or policies.
- ApplicationSet can use ACM placement decisions to generate Applications.
- The deployment can follow a Push model or Pull model depending on configuration.

Advantages:

- Enterprise-grade cluster inventory
- Placement-based targeting
- Better integration with multi-cluster OpenShift operations
- Good for large fleets
- Works well with governance and policy management

Disadvantages:

- More components to understand
- Requires ACM knowledge
- Troubleshooting involves Argo CD and ACM resources
- Pull model requires GitOps on managed clusters

Best use cases:

- large OpenShift estates
- cluster lifecycle through ACM
- teams already using ACM governance/policies
- regional or fleet management

### Pattern 4: Argo CD Agent hub-and-spoke model

Argo CD Agent introduces a hub-and-spoke architecture where a control plane cluster provides centralized visibility while workload clusters run lightweight Argo CD components and agents.

```text
                    Git
                     |
                     v
          Argo CD Agent Control Plane
          single pane of glass / principal
                     |
        agent synchronization channel
       /             |              \
      v              v               v
 workload-1      workload-2       workload-3
 local Argo CD   local Argo CD    local Argo CD
 local reconcile local reconcile  local reconcile
```

Important terms:

| Term | Meaning |
|---|---|
| Control plane cluster | Hub cluster providing centralized view and management |
| Workload cluster | Spoke cluster running application workloads |
| Principal | Control plane side of Argo CD Agent |
| Agent | Workload cluster side component |
| Managed mode | Application definitions are managed from the control plane |
| Autonomous mode | Workload cluster owns the Application definitions locally |
| Hybrid architecture | Existing push model and agent pull model can coexist for gradual migration |

Advantages:

- Better scaling model for large fleets
- Centralized visibility
- Local reconciliation on workload clusters
- Reduces need for direct push from hub to every cluster in some designs
- More suitable for edge or distributed environments

Disadvantages:

- More advanced architecture
- Requires agent installation and certificate/trust management
- Requires strong operational maturity
- Hybrid architecture in OpenShift GitOps 1.21 is Technology Preview, so production use must be evaluated carefully

Best use cases:

- large fleets
- edge OpenShift
- disconnected or semi-connected environments
- organizations needing a single pane of glass with distributed reconciliation

### Pattern 5: App-of-apps or bootstrap pattern

The app-of-apps pattern uses one parent Argo CD Application to create other Applications.

```text
bootstrap Application
├── cluster-config Application
├── operators Application
├── namespaces Application
├── monitoring Application
├── apps ApplicationSet
└── policies ApplicationSet
```

This is useful for bootstrapping a cluster.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-bootstrap
  namespace: openshift-gitops
spec:
  project: platform
  source:
    repoURL: https://git.example.com/platform/gitops.git
    targetRevision: main
    path: bootstrap/prod-a
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: false
      selfHeal: true
```

Production note:

> Use app-of-apps carefully. It is powerful, but if the bootstrap application is misconfigured, it can create widespread changes. Apply RBAC, code review, and sync windows.

## 7. Choosing the right architecture

| Requirement | Recommended pattern |
|---|---|
| Few clusters, easy start | Central Argo CD push model |
| Many OpenShift clusters with ACM | RHACM + OpenShift GitOps Placement |
| Strict cluster isolation | Argo CD per cluster |
| Edge or disconnected sites | Argo CD per cluster or Argo CD Agent |
| Need central visibility and distributed reconciliation | Argo CD Agent |
| Need gradual migration from central push to agent | Hybrid Argo CD Agent architecture |
| Team-based self-service | ApplicationSet + AppProject + Apps-in-any-namespace |
| Large fleet with placement rules | ACM Placement + ApplicationSet |

A practical production decision:

```text
Small environment:
  Start with central Argo CD + ApplicationSet cluster generator.

Medium OpenShift platform:
  Use central OpenShift GitOps with AppProjects, cluster labels, and strong RBAC.

Large Red Hat estate:
  Use ACM for cluster inventory and placement, OpenShift GitOps for deployment, and evaluate Argo CD Agent for scale.

Highly regulated environment:
  Prefer local reconciliation per cluster, limited credentials, strict AppProjects, signed commits, PR approvals, and controlled promotion.
```

## 8. Cluster onboarding workflow

Onboarding a new cluster into multi-cluster GitOps should be treated as a controlled platform operation.

### 8.1 Manual registration using `argocd cluster add`

High-level flow:

```bash
# Login to hub cluster where Argo CD runs
oc login https://api.hub.example.com:6443

# Login to Argo CD
argocd login openshift-gitops-server-openshift-gitops.apps.hub.example.com

# Confirm kubeconfig contexts
oc config get-contexts

# Add target cluster context
argocd cluster add prod-a-context --name prod-a

# Verify
argocd cluster list
```

What happens internally:

- Argo CD creates or uses a service account on the target cluster.
- Argo CD stores cluster connection information in a Kubernetes Secret in the Argo CD namespace.
- The Application controller uses that credential to compare and apply resources.

### 8.2 Declarative cluster registration

In production, many teams prefer declarative cluster registration because it is auditable.

Example cluster secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: cluster-prod-a
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: cluster
    env: prod
    region: india
    cloud: vmware
    owner: platform
stringData:
  name: prod-a
  server: https://api.prod-a.example.com:6443
  config: |
    {
      "bearerToken": "${TOKEN_FROM_SECRET_MANAGER}",
      "tlsClientConfig": {
        "insecure": false,
        "caData": "${BASE64_CA}"
      }
    }
```

Do not commit plain tokens to Git. Use a secure secret management approach.

### 8.3 Cluster labels for targeting

Cluster secret labels drive ApplicationSet selection.

Example labels:

```yaml
labels:
  argocd.argoproj.io/secret-type: cluster
  env: prod
  region: apac
  country: india
  datacenter: delhi-dc1
  team: payments
  compliance: pci
  platform-version: ocp-4.18
```

Then ApplicationSet can target only PCI prod clusters:

```yaml
generators:
  - clusters:
      selector:
        matchLabels:
          env: prod
          compliance: pci
```

### 8.4 OpenShift namespace management label

When the default OpenShift GitOps instance in `openshift-gitops` manages resources in a namespace, the namespace often needs this label:

```bash
oc label namespace web-dev argocd.argoproj.io/managed-by=openshift-gitops
```

Without proper namespace permission/labeling, sync might fail with RBAC or permission errors.

## 9. Repository structure for multi-cluster GitOps

Repository structure is one of the most important design decisions.

### 9.1 Simple environment overlay model

```text
gitops-repo/
├── apps/
│   └── web/
│       ├── base/
│       │   ├── deployment.yaml
│       │   ├── service.yaml
│       │   └── route.yaml
│       └── overlays/
│           ├── dev/
│           │   └── kustomization.yaml
│           ├── stage/
│           │   └── kustomization.yaml
│           └── prod/
│               └── kustomization.yaml
├── clusters/
│   ├── dev-a/

│   ├── stage-a/
│   │   └── apps.yaml
│   └── prod-a/
│       └── apps.yaml
└── projects/
    └── appprojects.yaml
```

Good for:

- small to medium teams
- clear app lifecycle
- Kustomize-based configuration

### 9.2 Platform and application separation

```text
gitops-platform/
├── cluster-config/
│   ├── namespaces/
│   ├── quotas/
│   ├── limits/
```

Good for:

- platform team owns cluster baseline

### 9.3 Cluster catalog model

- ACM integration

## 10. ApplicationSet deep dive for multi-cluster deployment

### 10.1 Cluster generator

The cluster generator uses clusters already registered in Argo CD.

Example: deploy `guestbook` to all registered clusters.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook-all-clusters
  namespace: openshift-gitops
spec:
  goTemplate: true
  goTemplateOptions:
    - missingkey=error
  generators:
    - clusters: {}
  template:
    metadata:
      name: '{{.name}}-guestbook'
    spec:
      project: default
      source:
        repoURL: https://github.com/argoproj/argocd-example-apps
        targetRevision: HEAD
        path: guestbook
      destination:
        server: '{{.server}}'
        namespace: guestbook
      syncPolicy:
        syncOptions:
          - CreateNamespace=true
```

Important generated parameters include:

- cluster name
- normalized cluster name
- cluster server URL
- labels from cluster secret
- annotations from cluster secret

### 10.2 Cluster generator with selector

Deploy only to production clusters:

```yaml
generators:
  - clusters:
      selector:
        matchLabels:
          env: prod
```

Deploy only to clusters matching multiple labels:

```yaml
generators:
  - clusters:
      selector:
        matchLabels:
          env: prod
          region: apac
          compliance: pci
```

### 10.3 Git generator

The Git generator reads directories or files from Git.

Example directory structure:

```text
apps/
├── web/
├── api/
└── worker/
```

Example ApplicationSet:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: apps-from-git
  namespace: openshift-gitops
spec:
  goTemplate: true
  generators:
    - git:
        repoURL: https://git.example.com/platform/apps.git
        revision: main
        directories:
          - path: apps/*
  template:
    metadata:
      name: '{{.path.basename}}'
    spec:
      project: platform
      source:
        repoURL: https://git.example.com/platform/apps.git
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{.path.basename}}'
```

### 10.4 Matrix generator: apps × clusters

This is powerful for multi-cluster GitOps.

```text
applications from Git  X  selected clusters
```

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: platform-apps-prod
  namespace: openshift-gitops
spec:
  goTemplate: true
  goTemplateOptions:
    - missingkey=error
  generators:
    - matrix:
        generators:
          - git:
              repoURL: https://git.example.com/platform/apps.git
              revision: main
              directories:
                - path: apps/*/overlays/prod
          - clusters:
              selector:
                matchLabels:
                  env: prod
  template:
    metadata:
      name: '{{.name}}-{{index .path.segments 1}}'
    spec:
      project: platform-prod
      source:
        repoURL: https://git.example.com/platform/apps.git
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: '{{.server}}'
        namespace: '{{index .path.segments 1}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

This can generate:

```text
prod-a-web
prod-a-api
prod-a-worker
prod-b-web
prod-b-api
prod-b-worker
```

### 10.5 List generator

Useful when you want explicit control.

```yaml
generators:
  - list:
      elements:
        - cluster: dev-a
          url: https://api.dev-a.example.com:6443
          env: dev
        - cluster: prod-a
          url: https://api.prod-a.example.com:6443
          env: prod
```

Good for:

- small fixed cluster list
- demos
- early migration
- controlled rollout

Not ideal for:

- large dynamic fleet
- clusters added/removed frequently

### 10.6 ACM Placement / clusterDecisionResource generator

With RHACM, cluster selection can come from Placement decisions.

High-level concept:

```text
ManagedCluster labels -> Placement -> PlacementDecision -> ApplicationSet -> Applications
```

Example conceptual ApplicationSet:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook-acm-placement
  namespace: openshift-gitops
spec:
  goTemplate: true
  generators:
    - clusterDecisionResource:
        configMapRef: ocm-placement-generator
        labelSelector:
          matchLabels:
            cluster.open-cluster-management.io/placement: prod-placement
        requeueAfterSeconds: 30
  template:
    metadata:
      name: '{{.name}}-guestbook'
    spec:
      project: platform-prod
      source:
        repoURL: https://git.example.com/platform/apps.git
        targetRevision: main
        path: guestbook
      destination:
        server: '{{.server}}'
        namespace: guestbook
```

This pattern is better than hardcoding cluster lists when ACM already manages cluster inventory.

## 11. Push model vs Pull model

### 11.1 Push model

In the push model, the hub Argo CD controller directly applies resources to remote clusters.

```text
Hub Argo CD application-controller
        |
        | Kubernetes API call
        v
Target OpenShift cluster
```

Characteristics:

- Hub stores credentials for target clusters.
- Hub must reach target API servers.
- Hub does the comparison and apply operation.
- Simpler to start.

Risk:

- If the hub is compromised, many clusters can be affected.
- Over-permissive cluster credentials can create a large blast radius.

### 11.2 Pull model

In the pull model, the target cluster has local GitOps components that pull desired state and reconcile locally.

```text
Git
 |
 v
Workload cluster local Argo CD
 |
 v
Local resources
```

Characteristics:

- Better for isolated clusters.
- Less direct access from hub to workload API may be needed.
- Each cluster reconciles itself.
- Requires installing and operating GitOps components per cluster.

### 11.3 ACM pull model

With ACM integration, the hub can propagate Application definitions or work to managed clusters, and local OpenShift GitOps instances reconcile resources.

Important point:

> Pull model can reduce stress on the hub controller, but every managed cluster must have appropriate GitOps components and repository access.

### 11.4 Argo CD Agent pull model

Argo CD Agent extends the pull model with centralized visibility through a control plane and agents on workload clusters.

Key idea:

> The control plane gives a single pane of glass, while workload clusters perform local reconciliation.

## 12. OpenShift-specific administration concerns

### 12.1 Cluster-scoped resources

OpenShift GitOps can manage cluster-scoped resources, but this must be done carefully.

Examples of cluster-scoped resources:

- `ClusterRole`
- `ClusterRoleBinding`
- `Namespace`
- `CustomResourceDefinition`
- `MachineConfig`
- `OAuth`
- `IngressController`
- `ImageContentSourcePolicy` / IDMS / ITMS depending on OpenShift version
- `OperatorHub`
- `ConsoleLink`
- cluster-wide `Subscription` resources in some operator models

Production warning:

> Do not grant cluster-admin-like access to an Argo CD instance unless there is a clear use case, strict code review, and limited human access to that Argo CD namespace.

Reason:

If a user can modify Applications or Git sources used by a cluster-scoped Argo CD instance, that user may effectively gain cluster-level control.

### 12.2 Namespace-scoped resources

Most application teams should manage only namespace-scoped resources:

- `Deployment`
- `Service`
- `Route`
- `ConfigMap`
- `Secret` references
- `NetworkPolicy`
- `HorizontalPodAutoscaler`
- `ServiceAccount`
- `Role`, `RoleBinding`

Use AppProject restrictions to keep teams inside approved namespaces.

### 12.3 Operator installation through GitOps

OpenShift Operators can be managed through GitOps using:

- `Namespace`
- `OperatorGroup`
- `Subscription`

Example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-pipelines
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-pipelines-og
  namespace: openshift-pipelines
spec:
  targetNamespaces:
    - openshift-pipelines
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-pipelines-operator-rh
  namespace: openshift-pipelines
spec:
  channel: latest
  installPlanApproval: Manual
  name: openshift-pipelines-operator-rh
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Senior admin note:

> Use `installPlanApproval: Manual` for critical operators in production unless your organization has validated automatic upgrades.

### 12.4 ResourceQuota and LimitRange through GitOps

Example:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: payments-prod
spec:
  hard:
    pods: "50"
    requests.cpu: "20"
    requests.memory: 64Gi
    limits.cpu: "40"
    limits.memory: 128Gi
    services: "20"
    secrets: "50"
```

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: payments-prod
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 256Mi
      default:
        cpu: 500m
        memory: 512Mi
      min:
        cpu: 10m
        memory: 64Mi
      max:
        cpu: "2"
        memory: 2Gi
```

This is a strong multi-cluster use case because quotas and limits often drift when manually managed.

### 12.5 NetworkPolicy through GitOps

Example: allow only `frontend` namespace to reach `backend` pods on port 8080.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: frontend
      ports:
        - protocol: TCP
          port: 8080
```

Production note:

> Always test NetworkPolicy in lower environments first. A bad policy can cause application outage even though Argo CD shows sync success.

### 12.6 SCC and security context

OpenShift Security Context Constraints can affect workloads deployed by GitOps.

Common symptoms:

```text
Error creating: pods "..." is forbidden: violates PodSecurity or SCC restrictions
```

Fix should be intentional, not random.

Example:

```bash
oc adm policy add-scc-to-user anyuid -z my-sa -n my-project
```

Better approach:

- use restricted-compatible images
- avoid running as root
- use explicit service accounts
- document SCC grants in Git
- review SCC grants as privileged actions

## 13. Environment promotion strategy

A mature multi-cluster GitOps process separates deployment from promotion.

### 13.1 Branch-based promotion

```text
main     -> dev
release  -> stage
prod     -> prod
```

Advantages:

- clear separation
- familiar Git workflow

Disadvantages:

- merge conflicts
- long-lived branches can drift

### 13.2 Directory-based promotion

```text
apps/web/overlays/dev
apps/web/overlays/stage
apps/web/overlays/prod
```

Promotion means copying or updating image tags/values from one overlay to another.

Advantages:

- clear environment differences
- works well with Kustomize

Disadvantages:

- duplicated values if not managed carefully

### 13.3 Tag-based promotion

```yaml
source:
  targetRevision: v1.2.3
```

Advantages:

- immutable release reference
- good auditability

Disadvantages:

- changing config needs new tag

### 13.4 Helm values promotion

```text
charts/web/
values/dev.yaml
values/stage.yaml
values/prod.yaml
```

ApplicationSet can select values per environment.

Example:

```yaml
source:
  repoURL: https://git.example.com/apps/web-chart.git
  chart: web
  targetRevision: 1.2.3
  helm:
    valueFiles:
      - values-prod.yaml
```

### 13.5 Recommended production model

For serious OpenShift platforms:

```text
Build image once -> scan -> sign -> promote immutable digest -> update Git -> Argo CD sync
```

Avoid rebuilding different images for each environment unless required. Promote the same artifact with environment-specific configuration.

## 14. Sync policy and drift control

### 14.1 Manual sync

Manual sync is safer for production-critical platform configuration.

```yaml
syncPolicy: {}
```

Use when:

- managing cluster-scoped resources
- modifying RBAC
- modifying networking
- changing operators
- production release requires change approval

### 14.2 Automated sync

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

Use when:

- app workloads are well-tested
- rollback process is clear
- Git PR approval is strong
- team accepts automatic reconciliation

### 14.3 Prune

`prune: true` removes live resources that are no longer present in Git.

Risk:

- Accidental deletion from Git can delete production resources.
- Bad path or generator error can remove resources.

Best practice:

- Use prune in dev first.
- Be cautious with cluster-scoped resources.
- Consider manual sync for critical applications.
- Use finalizers and backups where required.

### 14.4 Self-heal

`selfHeal: true` reverts live manual changes back to Git.

This is useful for drift prevention.

Example:

```text
Admin manually changes replicas from 3 to 5.
Git says replicas: 3.
Argo CD detects drift.
Self-heal changes replicas back to 3.
```

Senior admin note:

> Self-heal is good for compliance but can surprise people during emergency troubleshooting. Have a documented break-glass process.

### 14.5 Sync options

Common sync options:

```yaml
syncOptions:
  - CreateNamespace=true
  - PruneLast=true
  - ApplyOutOfSyncOnly=true
  - ServerSideApply=true
```

Use carefully:

| Option | Use case |
|---|---|
| `CreateNamespace=true` | Auto-create app namespace |
| `PruneLast=true` | Delete old resources after applying new ones |
| `ApplyOutOfSyncOnly=true` | Reduce unnecessary applies |
| `ServerSideApply=true` | Better field ownership in some operator-heavy cases |

### 14.6 Ignore differences

Operators often mutate resources. This can cause constant OutOfSync.

Example:

```yaml
ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
      - /spec/replicas
```

Use carefully. Ignoring too much hides real drift.

## 15. Security model for multi-cluster GitOps

Security is the most important part of multi-cluster GitOps.

### 15.1 Credential blast radius

In the central push model, hub Argo CD has credentials for many clusters.

Risk:

```text
Compromise hub Argo CD namespace -> possible compromise of many target clusters
```

Controls:

- least-privilege cluster roles
- separate Argo CD instances for critical environments
- restrict access to `openshift-gitops` namespace
- protect cluster secrets
- use external secret management
- rotate tokens
- audit Argo CD API access
- avoid sharing admin credentials

### 15.2 Least privilege for target clusters

Argo CD often needs broad read permissions to compare resources, but write permissions should be restricted where possible.

Bad pattern:

```text
Every target cluster credential = cluster-admin
```

Better pattern:

```text
App team Argo CD project -> only approved namespaces/resources
Platform Argo CD project -> controlled cluster-scoped permissions
Production cluster config -> manual approval and restricted maintainers
```

### 15.3 AppProject restrictions

Use AppProjects to limit:

```yaml
sourceRepos:
  - https://git.example.com/team-a/*
destinations:
  - server: https://api.prod-a.example.com:6443
    namespace: team-a-*
clusterResourceWhitelist: []
namespaceResourceWhitelist:
  - group: apps
    kind: Deployment
  - group: ''
    kind: Service
  - group: route.openshift.io
    kind: Route
```

This prevents a team from deploying arbitrary manifests to arbitrary clusters.

### 15.4 Git security

Protect Git because Git is the source of truth.

Controls:

- branch protection
- mandatory pull requests
- code owners
- signed commits if required
- protected tags
- CI validation
- policy checks
- secret scanning
- YAML linting
- Kubernetes schema validation
- OpenShift dry-run validation

### 15.5 Secrets

Never store raw secrets in plain Git.

Use one of these approaches:

- External Secrets Operator
- HashiCorp Vault integration
- Sealed Secrets
- SOPS with age/KMS/GPG
- OpenShift Secrets populated by CI/CD from a secret manager

Example ExternalSecret-style concept:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-password
  namespace: payments-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: db-password
  data:
    - secretKey: password
      remoteRef:
        key: payments/prod/db
        property: password
```

### 15.6 TLS and custom CA

Multi-cluster GitOps often fails because of TLS trust problems.

Common cases:

- private Git server uses internal CA
- target OpenShift API uses custom CA
- proxy intercepts TLS
- repo-server does not trust CA
- cluster secret has missing or wrong CA bundle

Senior admin checklist:

```bash
# Check cluster secret labels
oc get secret -n openshift-gitops -l argocd.argoproj.io/secret-type=cluster

# Check repo-server logs
oc logs deploy/openshift-gitops-repo-server -n openshift-gitops

# Check application-controller logs
oc logs deploy/openshift-gitops-application-controller -n openshift-gitops
```

### 15.7 Network security

Hub Argo CD needs egress to:

- Git repositories
- Helm repositories
- target cluster API servers
- container registries only if plugins or validations need them
- OIDC/OAuth endpoints

Target clusters may need egress to Git in pull/agent models.

OpenShift NetworkPolicy around Argo CD namespaces must allow required traffic. OpenShift GitOps newer releases also include stronger network policy controls for GitOps components.

## 16. Scaling and performance

Multi-cluster GitOps scale depends on:

- number of clusters
- number of Applications
- number of resources per Application
- sync frequency
- repo size
- Kustomize/Helm rendering cost
- controller workers
- repo-server CPU/memory
- network latency to target APIs
- number of ApplicationSets and generators

### 16.1 Symptoms of scale problems

- slow refresh
- repo-server CPU high
- application-controller memory high
- frequent reconciliation delays
- ApplicationSet generation delay
- API throttling against target clusters
- Redis issues
- UI slow or timeout
- sync operations queued for long periods

### 16.2 Scale controls

Practical controls:

- split very large apps into smaller Applications
- avoid one giant Application for entire cluster
- avoid excessive generator frequency
- use `requeueAfterSeconds` carefully
- scale repo-server replicas where supported/configured
- allocate enough CPU/memory to controller and repo-server
- use ApplicationSet selectors instead of generating everything everywhere
- use sharding or distributed architectures when needed
- consider ACM or Argo CD Agent for large fleets

### 16.3 Application granularity

Bad:

```text
one Application = entire company platform across all clusters
```

Better:

```text
Application 1 = namespace baseline
Application 2 = operators
Application 3 = monitoring
Application 4 = team app
Application 5 = team network policies
```

But do not go too small either. Thousands of tiny Applications can create operational noise.

A balanced approach:

- one Application per app per environment/cluster
- one Application per platform capability
- one ApplicationSet to generate repeatable groups

## 18. Troubleshooting multi-cluster GitOps

### 18.1 Application is `OutOfSync`

Check:

```bash
argocd app get <app-name>
argocd app diff <app-name>
```

Common reasons:

- manual change in cluster
- operator mutated fields
- generated fields differ
- Helm template output changed
- wrong Git revision
- wrong path
- missing resource in Git
- prune disabled

Fix:

- sync if desired
- update Git if live change is correct
- configure `ignoreDifferences` only when justified
- review operator-managed fields

### 18.2 Application is `Degraded`

Argo CD sync may be successful but health can be bad.

Check OpenShift resources:

```bash
oc get pods -n <namespace>
oc get deployment -n <namespace>
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common reasons:

- image pull error
- SCC denial
- quota exceeded
- PVC pending
- route/service mismatch
- readiness probe failing
- config missing

### 18.3 Cluster is `Unknown` or unreachable

Check:

```bash
argocd cluster list
oc get secret -n openshift-gitops -l argocd.argoproj.io/secret-type=cluster
```

Common reasons:

- API server unreachable from hub
- expired token
- wrong CA
- firewall blocked
- proxy problem
- cluster secret malformed
- service account removed
- target cluster API certificate changed

Debug:

```bash
# From hub cluster, create debug pod if needed and test API reachability
oc run curl-test -n openshift-gitops --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc rsh -n openshift-gitops curl-test
curl -vk https://api.prod-a.example.com:6443/version
```

### 18.4 Permission denied / forbidden

Error example:

```text
cannot create resource "networkpolicies" in API group "networking.k8s.io" in namespace "payments-prod"
```

Check:

```bash
oc auth can-i create networkpolicies.networking.k8s.io \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-prod
```

Fix:

- adjust Role/RoleBinding or ClusterRole/ClusterRoleBinding
- check AppProject destination restrictions
- check namespace label/management configuration
- avoid granting cluster-admin as a shortcut

### 18.5 ApplicationSet not creating Applications

Check:

```bash
oc get applicationset -n openshift-gitops
oc describe applicationset <name> -n openshift-gitops
oc logs deploy/openshift-gitops-applicationset-controller -n openshift-gitops
```

Common reasons:

- cluster selector matches no cluster secrets
- cluster secret missing required label
- template variable wrong
- `missingkey=error` catches missing values
- generator path wrong
- Git repo auth failure
- AppProject missing or denies destination

### 18.6 Namespace is not managed

Symptom:

```text
namespace is not permitted or Argo CD cannot manage resources in target namespace
```

Check:

```bash
oc get ns <namespace> --show-labels
```

Fix:

```bash
oc label namespace <namespace> argocd.argoproj.io/managed-by=openshift-gitops --overwrite
```

Or configure the correct source/destination namespace model for your user-defined Argo CD instance.

### 18.7 Helm rendering failure

Check repo-server logs:

```bash
oc logs deploy/openshift-gitops-repo-server -n openshift-gitops
```

Common reasons:

- invalid values file
- missing chart dependency
- Helm repo unreachable
- private repo credentials missing
- unsupported Helm version behavior
- template uses required value not provided

### 18.8 Kustomize failure

Common reasons:

- wrong relative path
- missing base
- invalid patch target
- duplicate resource ID
- namespace conflicts

Test locally:

```bash
kustomize build apps/web/overlays/prod
```

Or through Argo CD repo-server logs.

### 18.9 Prune deleted something unexpectedly

Immediate actions:

1. Identify the Git commit that removed the resource.
2. Revert or restore the manifest.
3. Sync the application.
4. If data resource was deleted, follow backup/restore procedure.
5. Review prune policy and approval process.

Command:

```bash
argocd app history <app-name>
argocd app get <app-name>
```

Production prevention:

- use manual sync for critical resources
- separate data resources from stateless resources
- avoid broad app paths
- use PR review with code owners
- require approvals for `prune: true` changes

### 18.10 Agent architecture troubleshooting

Check:

- principal component health on control plane
- agent component health on workload cluster
- certificate trust
- mapping mode
- Application destination
- whether managed or autonomous mode is used
- status propagation delay
- logs on both hub and spoke

General checks:

```bash
oc get pods -n <argocd-namespace>
oc get applications -A
oc get appprojects -A
oc logs -n <argocd-namespace> <principal-or-agent-pod>
```

## 21. Advanced best practices from a senior admin perspective

### 21.1 Do not start with full automation everywhere

Bad approach:

```text
Day 1: auto-sync + prune + self-heal for all clusters and cluster-scoped resources
```

Better approach:

```text
Phase 1: manual sync for cluster config
Phase 2: auto-sync for dev workloads
Phase 3: auto-sync for selected production apps
Phase 4: controlled prune/self-heal with strong review
```

### 21.2 Treat GitOps namespace as sensitive

The namespace containing Argo CD can be equivalent to a control plane.

Restrict:

```bash
oc adm policy who-can '*' '*' -n openshift-gitops
```

Review who can:

- edit Applications
- edit ApplicationSets
- edit AppProjects
- read Secrets
- exec into repo-server/controller pods
- modify ArgoCD CR

### 21.3 Use separate AppProjects by team and environment

Recommended:

```text
platform-dev
platform-prod
payments-dev
payments-prod
web-dev
web-prod
```

Avoid:

```text
default project for everything
```

### 21.4 Label clusters consistently

Bad labels:

```yaml
environment: production
Env: prod
stage: live
```

Good labels:

```yaml
env: prod
region: apac
country: india
datacenter: delhi-dc1
owner: platform
compliance: pci
```

### 21.5 Keep dangerous resources separate

Separate Applications for:

- RBAC
- operators
- cluster networking
- MachineConfig
- security configuration
- application workloads

This reduces accidental blast radius.

### 21.6 Prefer immutable image references in production

Better:

```yaml
image: registry.example.com/payments/api@sha256:abcd...
```

Less controlled:

```yaml
image: registry.example.com/payments/api:latest
```

### 21.7 Validate manifests before merge

CI checks:

```bash
kustomize build overlays/prod
helm template ./chart -f values-prod.yaml
kubectl apply --dry-run=server -f rendered.yaml
conftest test rendered.yaml
kubeconform rendered.yaml
```

For OpenShift:

```bash
oc apply --dry-run=server -f rendered.yaml
```

### 21.8 Avoid giant monolithic syncs

Large syncs are hard to troubleshoot.

Better split:

```text
01-namespaces
02-rbac
03-operators
04-network-policies
05-apps
```

Use sync waves if dependencies matter.

### 21.9 Use sync waves for ordering

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

Suggested order:

```text
-5 namespaces
-4 operator groups/subscriptions
-3 RBAC/service accounts
-2 secrets/configmaps
-1 network policies
 0 deployments/services
 1 routes/hpa
```

### 21.10 Document break-glass process

Example break-glass procedure:

1. Disable auto-sync or pause Application.
2. Perform emergency manual fix.
3. Open incident/change record.
4. Backport fix to Git.
5. Re-enable sync.
6. Confirm Argo CD is synced and healthy.

Never allow long-term manual drift after emergency changes.

## 22. Common anti-patterns

### Anti-pattern 1: Argo CD has cluster-admin everywhere

This is easy but dangerous.

Impact:

- large blast radius
- weak tenant isolation
- compliance concern

### Anti-pattern 2: All teams use the default project

Impact:

- no destination control
- no repo control
- hard audit
- high privilege risk

### Anti-pattern 3: Raw secrets in Git

Impact:

- credential leak
- audit failure
- secret rotation pain

### Anti-pattern 4: One repo path controls everything

Impact:

- accidental prune can delete many resources
- difficult ownership
- noisy diffs

### Anti-pattern 5: No cluster label standard

Impact:

- ApplicationSet targets wrong clusters
- production apps deployed to dev or vice versa
- hard automation

### Anti-pattern 6: Ignoring all differences

Impact:

- Argo CD shows healthy/synced while real drift exists

### Anti-pattern 7: Automatic operator upgrades in production without review

Impact:

- unexpected CRD changes
- operator behavior changes
- platform outage

## 23. Interview and real-world explanation

If asked in an interview: **“Explain multi-cluster GitOps in OpenShift GitOps/Argo CD.”**

Strong answer:

> Multi-cluster GitOps is a model where Git stores the desired state for applications and cluster configuration across multiple OpenShift clusters, and Argo CD/OpenShift GitOps continuously reconciles each cluster to that desired state. A central Argo CD instance can push changes to registered remote clusters using cluster credentials, or each cluster can run its own GitOps instance and pull changes locally. For scale, we use ApplicationSet to generate many Applications based on cluster labels, Git directories, or ACM Placement decisions. In Red Hat environments, RHACM integrates with OpenShift GitOps for managed cluster selection. For larger or distributed fleets, Argo CD Agent provides hub-and-spoke centralized visibility with local reconciliation. The main production concerns are AppProject isolation, least-privilege cluster credentials, Git review workflow, sync/prune safety, drift control, observability, and clear rollback.

Follow-up details to mention:

- ApplicationSet cluster generator reads registered cluster secrets.
- Cluster labels drive targeting.
- AppProjects restrict repositories, destinations, and resource kinds.
- Push model is simpler but centralizes credentials.
- Pull/agent model improves distributed reconciliation.
- OpenShift-specific permissions and namespace labels matter.
- Cluster-scoped GitOps must be restricted because it can become equivalent to cluster-admin.

## 24. Practice lab: deploy one app to multiple OpenShift clusters

### Goal

Deploy a sample app to all clusters labeled `env=dev` using ApplicationSet.

### Step 1: verify clusters

```bash
argocd cluster list
oc get secrets -n openshift-gitops -l argocd.argoproj.io/secret-type=cluster --show-labels
```

### Step 2: label cluster secrets

```bash
oc label secret cluster-dev-a -n openshift-gitops env=dev region=india --overwrite
oc label secret cluster-dev-b -n openshift-gitops env=dev region=india --overwrite
```

### Step 3: create AppProject

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: dev-apps
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://github.com/argoproj/argocd-example-apps
  destinations:
    - server: '*'
      namespace: guestbook
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
```

Apply:

```bash
oc apply -f appproject-dev-apps.yaml
```

### Step 4: create ApplicationSet

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook-dev-clusters
  namespace: openshift-gitops
spec:
  goTemplate: true
  goTemplateOptions:
    - missingkey=error
  generators:
    - clusters:
        selector:
          matchLabels:
            env: dev
  template:
    metadata:
      name: '{{.name}}-guestbook'
    spec:
      project: dev-apps
      source:
        repoURL: https://github.com/argoproj/argocd-example-apps
        targetRevision: HEAD
        path: guestbook
      destination:
        server: '{{.server}}'
        namespace: guestbook
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

Apply:

```bash
oc apply -f applicationset-guestbook-dev.yaml
```

### Step 5: verify generated Applications

```bash
oc get applications -n openshift-gitops
argocd app list | grep guestbook
```

### Step 6: verify on target cluster

```bash
oc login https://api.dev-a.example.com:6443
oc get all -n guestbook
```

### Step 7: test drift

Manually change replicas:

```bash
oc scale deployment guestbook-ui -n guestbook --replicas=5
```

Watch Argo CD self-heal it back if Git says a different value.

## 27. Senior admin final recommendations

For a production OpenShift environment, I would normally recommend this adoption path:

### Phase 1: Foundation

- Install OpenShift GitOps.
- Use one Argo CD instance for non-production.
- Create AppProjects.
- Define Git repo structure.
- Deploy namespaces, quotas, limits, and simple apps.
- Keep production manual initially.

### Phase 2: Multi-cluster push

- Register dev/stage/prod clusters.
- Label cluster secrets consistently.
- Use ApplicationSet cluster generator.
- Add PR review and CI validation.
- Enable auto-sync for dev.

### Phase 3: Governance

- Integrate RBAC properly.
- Add secret management.
- Add notifications and monitoring.
- Control prune and self-heal.
- Use sync windows for production.

### Phase 4: Enterprise scale

- Integrate RHACM if managing many OpenShift clusters.
- Use Placement-based cluster targeting.
- Evaluate pull model for scale and security.
- Evaluate Argo CD Agent for distributed fleet visibility and local reconciliation.

### Phase 5: Mature operations

- Enforce policy-as-code.
- Sign and promote immutable images.
- Use progressive delivery where suitable.
- Maintain disaster recovery runbooks.
- Periodically audit GitOps permissions and cluster credentials.

## 28. Summary

Multi-cluster GitOps in OpenShift GitOps/Argo CD is not just a deployment trick. It is a platform operating model.

At a 10-year experience level, you should understand:

- how Git becomes the source of truth
- how Argo CD compares and reconciles desired state
- how Applications target clusters
- how ApplicationSets generate Applications across clusters
- how cluster secrets and labels drive multi-cluster targeting
- how AppProjects enforce security boundaries
- when to use push, pull, ACM, or Agent architecture
- how OpenShift-specific RBAC, SCC, namespace labels, operators, routes, and quotas affect GitOps
- how to troubleshoot sync, health, permission, cluster connectivity, and drift issues
- how to design safe production promotion and rollback

The most important production rule is:

> Multi-cluster GitOps gives great power. Treat the GitOps control plane, Git repositories, cluster credentials, and AppProjects as critical security boundaries.
