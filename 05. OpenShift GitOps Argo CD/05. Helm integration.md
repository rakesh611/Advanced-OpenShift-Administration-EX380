**Audience:** Advanced OpenShift Administration / OpenShift GitOps / Argo CD administrators with around 10 years of Linux, DevOps, Kubernetes, or platform operations experience.

## 1. Executive Summary

Helm integration in OpenShift GitOps means that Argo CD can consume Helm charts as an application source, render them into Kubernetes/OpenShift manifests, compare those manifests with the live cluster state, and synchronize drift back to the desired state.

The most important point is this:

> In Argo CD, Helm is mainly a **template rendering engine**, not the lifecycle owner.

Argo CD normally does **not** run `helm install`, `helm upgrade`, or `helm rollback` as a Helm release manager. Instead, Argo CD uses Helm to generate YAML, usually equivalent to `helm template`, and then Argo CD manages apply, prune, self-heal, health status, drift detection, RBAC boundaries, and sync history.

That changes the operational model:

| Traditional Helm | Argo CD + Helm |
|---|---|
| Operator runs `helm install` or `helm upgrade` | Argo CD renders chart and applies manifests |
| Helm release state is stored as Helm release secrets/configmaps | Argo CD Application is the source of deployment state |
| `helm list` shows releases | `helm list` usually does not show Argo CD-rendered apps as Helm releases |
| Rollback often uses `helm rollback` | Rollback normally means Git revert, chart version change, or Application sync to an older Git revision |
| Drift is not continuously corrected by Helm | Argo CD can detect and optionally self-heal drift |

For a senior OpenShift administrator, the practical skill is not only creating an Argo CD Application with a Helm chart. The real skill is understanding how Helm rendering interacts with OpenShift security, SCCs, Routes, CRDs, Operators, namespace permissions, AppProjects, values promotion, private repositories, OCI registries, and troubleshooting manifest generation errors from the Argo CD repo-server.

## 2. Where Helm Fits in OpenShift GitOps Architecture

A typical OpenShift GitOps installation has these important components:

| Component | Role in Helm integration |
|---|---|
| `openshift-gitops-server` | API/UI endpoint used by users and CLI |
| `openshift-gitops-repo-server` | Fetches Git/Helm/OCI sources and renders manifests; most Helm errors appear here |
| `openshift-gitops-application-controller` | Compares desired state vs live state and performs sync operations |
| `openshift-gitops-applicationset-controller` | Generates many Applications from templates/generators |
| `argocd-cm` | Main Argo CD configuration ConfigMap |
| Repository Secrets | Store Git/Helm/OCI repository credentials |
| `Application` CR | Defines one deployable GitOps workload |
| `AppProject` CR | Defines boundaries: allowed repos, destinations, resource kinds, roles |

In Red Hat OpenShift GitOps, the default Argo CD instance is created in the `openshift-gitops` namespace. This default instance is cluster-scoped and has elevated permissions for cluster-configuration use cases. For application delivery, many enterprises create separate user-defined Argo CD instances or tightly restrict the default instance using AppProjects and namespace management.

## 3. Two Meanings of “Helm Integration”

When people say “Helm integration with Argo CD,” they usually mean one of two things.

### 3.1 Argo CD deploys applications from Helm charts

This is the most common meaning.

Example sources:

- Public Helm repository
- Private Helm repository
- OCI Helm registry
- Git repository containing a Helm chart
- Git repository containing only values files while chart comes from a Helm repository

This document mainly focuses on this model.

### 3.2 Argo CD itself is installed by Helm

The upstream Argo project provides community Helm charts for installing Argo CD. On OpenShift, the supported Red Hat approach is to install **Red Hat OpenShift GitOps Operator** from OperatorHub or the Red Hat Operator catalog. For production OpenShift environments, prefer the Red Hat GitOps Operator because it integrates with OpenShift lifecycle, supported images, Operator Lifecycle Manager, Routes, monitoring, and OpenShift-specific defaults.

In short:

- **Supported OpenShift approach:** OpenShift GitOps Operator
- **Community Kubernetes approach:** Argo CD Helm chart

For Red Hat production support, do not casually replace OpenShift GitOps Operator with the upstream Argo CD Helm chart unless your organization explicitly accepts that support model.

## 4. Argo CD Helm Rendering Flow

When an Argo CD Application points to a Helm chart, the internal flow is roughly:

1. Application controller notices the `Application` object.
2. Repo-server fetches the source:
   - Git repository, or
   - Helm repository, or
   - OCI registry.
3. Repo-server resolves chart version and values.
4. Repo-server runs Helm rendering, conceptually similar to:

   ```bash
   helm template <release-name> <chart> \
     --namespace <destination-namespace> \
     --values <value-file> \
     --set key=value
   ```

5. Argo CD receives rendered YAML.
6. Application controller compares rendered YAML with live cluster objects.
7. Sync applies missing or changed resources.
8. Optional automated policy prunes extra resources and self-heals drift.

Important result:

```bash
helm list -n <namespace>
```

usually does not show a Helm release for an Argo CD Helm Application, because Helm did not install a release. Argo CD rendered the chart and became the lifecycle controller.

## 5. Basic Application from a Helm Repository

Example: Deploy a chart from a standard Helm repository.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-helm
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://charts.bitnami.com/bitnami
    chart: nginx
    targetRevision: 18.2.5
    helm:
      releaseName: nginx
      valuesObject:
        service:
          type: ClusterIP
        replicaCount: 2
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-demo
  syncPolicy:
    syncOptions:
      - CreateNamespace=true
```

Apply it:

```bash
oc apply -f nginx-helm-application.yaml
```

Check status:

```bash
oc get application nginx-helm -n openshift-gitops
argocd app get nginx-helm
```

Sync manually:

```bash
argocd app sync nginx-helm
```

## 6. Application from a Git Repository Containing a Helm Chart

If the chart is stored inside Git, use `path` instead of `chart`.

Repository example:

```text
platform-apps/
└── apps/
    └── payment-api/
        ├── Chart.yaml
        ├── values.yaml
        ├── values-dev.yaml
        ├── values-prod.yaml
        └── templates/
            ├── deployment.yaml
            ├── service.yaml
            └── route.yaml
```

Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-dev
  namespace: openshift-gitops
spec:
  project: payment
  source:
    repoURL: https://git.example.com/platform/platform-apps.git
    targetRevision: main
    path: apps/payment-api
    helm:
      releaseName: payment-api
      valueFiles:
        - values-dev.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

This is a clean pattern when your organization owns the chart.

## 7. Application from an OCI Helm Registry

For OCI Helm charts, Argo CD supports two common approaches.

### 7.1 Helm repository style for OCI Helm charts

Add the OCI Helm repository:

```bash
argocd repo add registry-1.docker.io/bitnamicharts \
  --type helm \
  --enable-oci=true
```

Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-oci-helm
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: registry-1.docker.io/bitnamicharts
    chart: nginx
    targetRevision: 18.2.5
    helm:
      valuesObject:
        replicaCount: 2
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-oci
  syncPolicy:
    syncOptions:
      - CreateNamespace=true
```

Notice that in this Helm repository style, the `repoURL` does **not** include `oci://`.

### 7.2 OCI source style

Some Argo CD versions also support OCI sources directly with `oci://` source URLs. In that model, the source is treated as an OCI artifact source. For Helm charts, follow the exact syntax supported by your deployed Argo CD / OpenShift GitOps version and test it with `argocd app manifests` before production rollout.

## 8. Adding Helm Repositories to Argo CD

### 8.1 Public Helm repository using CLI

```bash
argocd repo add https://charts.bitnami.com/bitnami --type helm
```

### 8.2 Private Helm repository using CLI

```bash
argocd repo add https://helm.example.com/charts \
  --type helm \
  --username helm-reader \
  --password '<PASSWORD_OR_TOKEN>'
```

### 8.3 Private OCI Helm registry using CLI

```bash
argocd repo add registry.example.com/platform/charts \
  --type helm \
  --enable-oci=true \
  --username helm-reader \
  --password '<TOKEN>'
```

### 8.4 Declarative repository Secret

Create the Secret in the Argo CD control-plane namespace, usually `openshift-gitops` for the default instance.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: repo-platform-helm
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  name: platform-helm
  type: helm
  url: https://helm.example.com/charts
  username: helm-reader
  password: <TOKEN>
type: Opaque
```

For OCI Helm repository credentials:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: repo-platform-oci-helm
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  name: platform-oci-helm
  type: helm
  enableOCI: "true"
  url: registry.example.com/platform/charts
  username: helm-reader
  password: <TOKEN>
type: Opaque
```

Apply:

```bash
oc apply -f repo-platform-helm.yaml
```

Verify:

```bash
argocd repo list
argocd repo get https://helm.example.com/charts
```

## 9. Helm Values in Argo CD

Argo CD supports multiple ways to pass values to Helm.

### 9.1 `valueFiles`

```yaml
source:
  repoURL: https://git.example.com/platform/apps.git
  targetRevision: main
  path: charts/payment-api
  helm:
    valueFiles:
      - values.yaml
      - values-dev.yaml
```

The files are resolved relative to the chart root when the chart is in Git.

### 9.2 `valuesObject`

```yaml
source:
  repoURL: https://charts.example.com
  chart: payment-api
  targetRevision: 1.4.2
  helm:
    valuesObject:
      replicaCount: 3
      image:
        tag: "1.4.2"
      route:
        enabled: true
```

This is often cleaner than a multi-line `values` string.

### 9.3 `values`

```yaml
source:
  repoURL: https://charts.example.com
  chart: payment-api
  targetRevision: 1.4.2
  helm:
    values: |
      replicaCount: 3
      image:
        tag: "1.4.2"
```

This works, but for maintainability, prefer `valuesObject` or Git-based values files.

### 9.4 `parameters`

Equivalent to Helm `--set`.

```yaml
source:
  repoURL: https://charts.example.com
  chart: payment-api
  targetRevision: 1.4.2
  helm:
    parameters:
      - name: replicaCount
        value: "3"
      - name: image.tag
        value: "1.4.2"
```

### 9.5 `fileParameters`

Equivalent to Helm `--set-file`.

```yaml
source:
  repoURL: https://git.example.com/platform/apps.git
  targetRevision: main
  path: charts/tls-app
  helm:
    fileParameters:
      - name: tls.crt
        path: certs/tls.crt
      - name: tls.key
        path: certs/tls.key
```

Be careful with secrets in Git. Do not commit private keys or sensitive values unless they are encrypted and governed.

## 10. Helm Values Precedence

Argo CD follows Helm-style precedence, with Argo CD-specific layers.

Highest precedence wins:

```text
parameters
valuesObject
values
valueFiles
chart's default values.yaml
```

Senior admin rule:

> Do not mix too many value injection styles in one Application unless you have a strong reason.

Recommended enterprise pattern:

```text
Chart default values.yaml        -> chart owner default
values-common.yaml               -> platform/team standard
values-dev.yaml                  -> environment override
values-prod.yaml                 -> production override
parameters                       -> emergency or very small override only
```

Avoid long-term production configuration hidden in `argocd app set -p ...` because it becomes less visible than Git-managed values.

## 11. Multi-Source Application: External Helm Chart + Git Values

A powerful pattern is to keep vendor/upstream chart source separate from your environment-specific values repository.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: redis-dev
  namespace: openshift-gitops
spec:
  project: platform-services
  sources:
    - repoURL: https://charts.bitnami.com/bitnami
      chart: redis
      targetRevision: 20.6.3
      helm:
        valueFiles:
          - $values/envs/dev/redis/values.yaml
    - repoURL: https://git.example.com/platform/gitops-values.git
      targetRevision: main
      ref: values
  destination:
    server: https://kubernetes.default.svc
    namespace: redis-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

This pattern is good when:

- Chart comes from a vendor repository.
- Your organization only owns values.
- You want promotion by changing values or chart version through Git pull requests.
- Security wants chart version pinning and auditable values changes.

Avoid using floating chart versions like `latest` in production. Pin exact chart versions.

## 12. Helm Release Name in Argo CD

By default, Argo CD sets the Helm release name to the Application name.

```yaml
metadata:
  name: payment-api-dev
spec:
  source:
    helm:
      releaseName: payment-api
```

Be careful when overriding `releaseName`.

Many Helm charts use this label for selectors:

```yaml
app.kubernetes.io/instance: <release-name>
```

Argo CD also uses `app.kubernetes.io/instance` for resource tracking by default. If your Application name and Helm release name differ, some charts can break because Argo CD tracking labels may not match chart selectors.

Best practice:

- Keep Application name and Helm release name aligned when possible.
- If you must override release name, test Service selectors, Deployment pod labels, NetworkPolicies, ServiceMonitors, and Route target service labels.
- In multi-instance Argo CD designs, consider annotation-based or `annotation+label` resource tracking according to platform policy.

## 13. OpenShift Namespace Management

In OpenShift GitOps, Argo CD can manage resources in namespaces outside its own control-plane namespace only when permissions allow it.

For the default instance in `openshift-gitops`, label the target namespace:

```bash
oc label namespace payment-dev \
  argocd.argoproj.io/managed-by=openshift-gitops
```

General format:

```bash
oc label namespace <target_namespace> \
  argocd.argoproj.io/managed-by=<argocd_namespace>
```

Important security note:

Giving Argo CD access to a namespace can grant powerful permissions to Argo CD components in that namespace. Do not label broad namespaces casually. In a multi-tenant cluster, namespace management must be part of your platform governance model.

## 14. AppProject Design for Helm Applications

`AppProject` is one of the most important security controls in Argo CD.

Example AppProject for a team:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payment
  namespace: openshift-gitops
spec:
  description: Payment team application delivery boundary

  sourceRepos:
    - https://git.example.com/payment/*
    - https://helm.example.com/payment-charts

  destinations:
    - server: https://kubernetes.default.svc
      namespace: payment-dev
    - server: https://kubernetes.default.svc
      namespace: payment-test
    - server: https://kubernetes.default.svc
      namespace: payment-prod

  clusterResourceWhitelist: []

  namespaceResourceWhitelist:
    - group: ""
      kind: ConfigMap
    - group: ""
      kind: Secret
    - group: ""
      kind: Service
    - group: apps
      kind: Deployment
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy
    - group: autoscaling
      kind: HorizontalPodAutoscaler

  roles:
    - name: payment-admin
      description: Payment team admins
      policies:
        - p, proj:payment:payment-admin, applications, get, payment/*, allow
        - p, proj:payment:payment-admin, applications, sync, payment/*, allow
      groups:
        - payment-platform-admins
```

Production guidance:

- Do not let application teams use the unrestricted `default` AppProject.
- Restrict source repositories.
- Restrict destinations.
- Restrict cluster-scoped resources.
- Separate platform charts from application charts.
- Use different AppProjects for dev/test/prod if approval boundaries differ.

## 15. OpenShift-Specific Helm Chart Concerns

Many upstream Helm charts are built for generic Kubernetes. OpenShift has stricter and different platform behavior.

### 15.1 Security Context Constraints and Pod Security

OpenShift uses SCCs and Pod Security Admission behavior. Charts that assume root, privileged containers, hostPath, hostNetwork, or fixed UIDs can fail.

Symptoms:

```text
Error creating: pods "x" is forbidden: unable to validate against any security context constraint
```

or

```text
would violate PodSecurity "restricted"
```

Check chart values for:

```yaml
securityContext:
  runAsUser:
  runAsNonRoot:
  fsGroup:
containerSecurityContext:
  allowPrivilegeEscalation:
  capabilities:
```

OpenShift-friendly defaults usually include:

```yaml
podSecurityContext:
  enabled: false
containerSecurityContext:
  enabled: false
```

or allow OpenShift to assign a random UID.

Avoid this unless truly required:

```bash
oc adm policy add-scc-to-user anyuid -z default -n app-ns
```

Better pattern:

```bash
oc create sa payment-api -n payment-dev
oc adm policy add-scc-to-user anyuid -z payment-api -n payment-dev
```

Then set chart values:

```yaml
serviceAccount:
  create: false
  name: payment-api
```

### 15.2 Routes vs Ingress

Many Helm charts create Kubernetes Ingress. OpenShift can process Ingress through the router, but Routes are still widely used in OpenShift operations.

Chart options may look like:

```yaml
ingress:
  enabled: true
  className: openshift-default
```

Some charts provide OpenShift Route support:

```yaml
route:
  enabled: true
  host: app.apps.ocp4.example.com
  tls:
    termination: edge
```

If a chart does not support Route, options include:

1. Use Ingress if acceptable.
2. Use chart `extraObjects` if available.
3. Wrap the upstream chart in your own Helm chart and add a Route template.
4. Deploy Route as a separate Argo CD Application with sync waves.

Example Route as an extra object if the chart supports `extraObjects`:

```yaml
extraObjects:
  - apiVersion: route.openshift.io/v1
    kind: Route
    metadata:
      name: payment-api
      labels:
        app.kubernetes.io/name: payment-api
    spec:
      host: payment-api.apps.ocp4.example.com
      to:
        kind: Service
        name: payment-api
      port:
        targetPort: http
      tls:
        termination: edge
        insecureEdgeTerminationPolicy: Redirect
```

### 15.3 Image Registry and Pull Secrets

Charts may default to Docker Hub or public registries. Enterprise OpenShift clusters often require mirrored images in an internal registry.

Values example:

```yaml
image:
  registry: registry.ocp4.example.com:8443
  repository: platform/payment-api
  tag: "1.4.2"
imagePullSecrets:
  - name: platform-registry-pull
```

If the chart does not expose registry values cleanly, consider patching the chart, creating a wrapper chart, or using a chart designed for enterprise deployment.

### 15.4 ServiceMonitor and OpenShift Monitoring

Charts often include Prometheus Operator resources:

```yaml
serviceMonitor:
  enabled: true
```

Before enabling, check whether the CRD exists:

```bash
oc api-resources | grep -i servicemonitor
```

If the CRD is missing, Helm rendering may succeed but sync may fail with:

```text
no matches for kind "ServiceMonitor" in version "monitoring.coreos.com/v1"
```

In OpenShift, user workload monitoring may also require namespace labels and cluster monitoring configuration.

### 15.5 NetworkPolicy

Charts may create NetworkPolicies that block OpenShift router, monitoring, or cross-namespace traffic.

Check rendered manifests before sync:

```bash
argocd app manifests <app-name> | less
```

Check live policies:

```bash
oc get networkpolicy -n <namespace>
oc describe networkpolicy <name> -n <namespace>
```

### 15.6 Persistent Volumes

Charts commonly expose values like:

```yaml
persistence:
  enabled: true
  storageClass: lvms-vg1
  size: 10Gi
```

On OpenShift, verify the StorageClass and access mode:

```bash
oc get sc
oc get pvc -n <namespace>
oc describe pvc <pvc-name> -n <namespace>
```

For `WaitForFirstConsumer` storage classes, a PVC can remain pending until a pod is scheduled.

## 16. CRD Handling in Helm Charts

Helm charts may include CRDs in a `crds/` directory. Examples:

- Prometheus Operator CRDs
- cert-manager CRDs
- External Secrets CRDs
- Custom platform operator CRDs

Argo CD/Helm can render and apply them, but production administrators should decide whether CRDs belong to:

1. The application chart, or
2. A platform/bootstrap layer managed separately.

Recommended enterprise pattern:

```text
Layer 0: OpenShift cluster + GitOps Operator
Layer 1: Platform Operators and CRDs
Layer 2: Shared platform services
Layer 3: Application workloads
```

If CRDs are platform-owned, skip CRD installation in the application chart:

```yaml
source:
  helm:
    skipCrds: true
```

If CRDs and CRs are in the same GitOps flow, use sync waves:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

for CRDs, and:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "1"
```

for custom resources.

## 17. Helm Hooks vs Argo CD Hooks

Helm hooks use annotations like:

```yaml
helm.sh/hook: pre-install
helm.sh/hook: post-install
```

Argo CD supports many Helm hooks by mapping Helm hook annotations to Argo CD hook behavior, but the lifecycle is not identical to a normal Helm install/upgrade flow.

Senior admin guidance:

- Avoid complex Helm hooks for production GitOps where possible.
- Prefer Argo CD sync waves and Argo CD resource hooks.
- Be careful with database migration Jobs.
- Make hook Jobs idempotent.
- Avoid hooks that mutate resources outside GitOps ownership.
- Avoid hooks that require manual cleanup unless delete policies are defined.

Example Argo CD hook:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: payment-db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation,HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/payment/migrate:1.4.2
```

## 18. Random Data in Helm Charts

Some charts use Helm template functions like:

```gotemplate
{{ randAlphaNum 32 }}
```

This can cause Argo CD to show the Application as OutOfSync repeatedly because each render generates a different value.

Symptoms:

```text
Application keeps going OutOfSync immediately after sync
Secret value changes every comparison
Diff shows generated random password or token
```

Fixes:

1. Provide stable values explicitly:

   ```yaml
   auth:
     password: "use-a-secret-manager-not-this-literal-example"
   ```

2. Use an existing Secret:

   ```yaml
   auth:
     existingSecret: redis-auth
   ```

3. Manage secrets with External Secrets, Sealed Secrets, SOPS, Vault plugin, or another approved secret management workflow.

## 19. Helm Dependencies

A Helm chart may depend on subcharts:

```yaml
# Chart.yaml
apiVersion: v2
name: payment-platform
version: 1.0.0
dependencies:
  - name: redis
    version: 20.6.3
    repository: https://charts.bitnami.com/bitnami
```

Operational guidance:

- Commit `Chart.lock` when possible.
- Ensure dependent chart repositories are reachable from the Argo CD repo-server.
- Configure credentials for private dependency repositories.
- Avoid unpinned dependency versions.
- Test dependency rendering in CI:

  ```bash
  helm dependency build ./charts/payment-platform
  helm template payment-platform ./charts/payment-platform -f values-dev.yaml
  ```

If dependency fetching fails inside Argo CD, check repo-server logs.

## 20. Wrapper Chart Pattern

When an upstream chart does not fit OpenShift requirements, create a wrapper chart.

Repository:

```text
payment-wrapper/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── route.yaml
    ├── networkpolicy.yaml
    └── servicemonitor.yaml
```

`Chart.yaml`:

```yaml
apiVersion: v2
name: payment-wrapper
version: 1.0.0
dependencies:
  - name: payment-api
    version: 1.4.2
    repository: https://helm.example.com/payment
```

`templates/route.yaml`:

```yaml
{{- if .Values.openshiftRoute.enabled }}
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: {{ .Release.Name }}
spec:
  host: {{ .Values.openshiftRoute.host | quote }}
  to:
    kind: Service
    name: {{ .Release.Name }}
  port:
    targetPort: http
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
{{- end }}
```

`values.yaml`:

```yaml
payment-api:
  replicaCount: 2
  image:
    registry: registry.example.com
    repository: payment/payment-api
    tag: "1.4.2"

openshiftRoute:
  enabled: true
  host: payment.apps.ocp4.example.com
```

This pattern lets you consume upstream charts while keeping OpenShift-specific resources under platform control.

## 21. ApplicationSet with Helm

ApplicationSet is useful when deploying the same Helm chart across environments, clusters, or tenants.

### 21.1 List generator example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: payment-api-envs
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - env: dev
            namespace: payment-dev
            valuesFile: values-dev.yaml
          - env: test
            namespace: payment-test
            valuesFile: values-test.yaml
          - env: prod
            namespace: payment-prod
            valuesFile: values-prod.yaml
  template:
    metadata:
      name: payment-api-{{env}}
    spec:
      project: payment
      source:
        repoURL: https://git.example.com/payment/payment-api-chart.git
        targetRevision: main
        path: chart
        helm:
          releaseName: payment-api
          valueFiles:
            - "{{valuesFile}}"
      destination:
        server: https://kubernetes.default.svc
        namespace: "{{namespace}}"
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

```text
│   └── values.yaml

│   └── values.yaml
```

This pattern is useful for GitOps promotion, but be careful with automatic production sync. Many enterprises keep automated sync for dev/test and manual sync for prod.

## 23. Sync Policy for Helm Applications

Manual sync:

```yaml
syncPolicy: {}
```

Automated sync:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

Common sync options:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
    - CreateNamespace=true
    - ApplyOutOfSyncOnly=true
    - PrunePropagationPolicy=foreground
```

Use `ServerSideApply=true` when required for large objects or fields managed by multiple controllers:

```yaml
syncPolicy:
  syncOptions:
    - ServerSideApply=true
```

Be careful with:

```yaml
- Replace=true
```

because it can delete and recreate resources depending on the object and situation.

## 24. Diff Management for Helm Applications

Helm charts often produce resources that are later mutated by OpenShift or controllers.

Examples:

- Defaulted fields added by Kubernetes API
- Mutating webhooks injecting sidecars or annotations
- OpenShift image triggers
- Route admitted status
- HPA changing replica count
- Operators modifying owned resources

If Argo CD shows noisy diffs, first understand the cause:

```bash
argocd app diff <app-name>
argocd app get <app-name> --hard-refresh
oc get <resource> <name> -n <namespace> -o yaml
```

For true controller-owned fields, use `ignoreDifferences` carefully.

Example ignoring replicas because HPA controls them:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

Do not hide real drift just to get a green dashboard.

## 25. Rollback Strategy

Because Argo CD does not normally create Helm release history, do not rely on:

```bash
helm rollback
```

Preferred rollback methods:

### 25.1 Git revert

```bash
git revert <bad-commit>
git push
argocd app sync payment-api-prod
```

### 25.2 Pin previous chart version

Change:

```yaml
targetRevision: 1.4.3
```

to:

```yaml
targetRevision: 1.4.2
```

Commit and sync.

### 25.3 Pin previous image tag in values

```yaml
image:
  tag: "1.4.2"
```

### 25.4 Sync to previous Git revision

Useful in emergency, but long-term desired state must still be fixed in Git.

```bash
argocd app sync payment-api-prod --revision <commit-sha>
```

## 26. Secure Secrets Handling with Helm Values

Never put real production secrets in plain Helm values.

Bad:

```yaml
auth:
  password: MyProdPassword123
```

Better options:

- External Secrets Operator
- Sealed Secrets
- SOPS with an approved Argo CD plugin or workflow
- Vault integration
- Existing Kubernetes Secret created by secure pipeline
- OpenShift Secrets managed by platform automation

Chart values should reference existing secrets:

```yaml
auth:
  existingSecret: payment-db-auth
  usernameKey: username
  passwordKey: password
```

GitOps rule:

> Git should store desired state, not unencrypted confidential data.

## 29. Troubleshooting Matrix

| Problem | Common Cause | Check | Fix |
|---|---|---|---|
| `failed to generate manifests` | Helm rendering error | Repo-server logs, `argocd app manifests` | Fix chart values, chart path, dependencies |
| `chart not found` | Wrong `repoURL`, `chart`, or version | `argocd repo list`, chart repo index | Correct chart name/version |
| `values file not found` | Wrong path or missing file | Application source config | Fix relative path or use multi-source `$values` correctly |
| OCI repo fails | Used `oci://` incorrectly for Helm repo mode | Repository config | Omit `oci://` when using Helm repo + `enableOCI` |
| Namespace forbidden | Target namespace not managed by Argo CD | Namespace labels, rolebindings | Label namespace or configure instance permissions |
| AppProject denies sync | Source or destination not allowed | `oc get appproject -o yaml` | Update AppProject restrictions |
| SCC error | Chart requires root/privileged permissions | Pod events | Adjust values or bind proper SCC to dedicated SA |
| Route not created | Chart only supports Ingress | Rendered manifests | Add Route via values, wrapper chart, or separate app |
| Service has no endpoints | Label selector mismatch, releaseName issue | Service selectors, pod labels | Align releaseName/Application name and chart labels |
| App always OutOfSync | Random values, webhook mutation, HPA | `argocd app diff` | Stable values or ignore legitimate controller fields |
| CR sync fails | CRD missing or applied too late | `oc api-resources`, sync events | Manage CRDs first or use sync waves |
| Private repo TLS error | Missing CA trust | Repo-server logs | Add repo cert/CA or fix TLS chain |
| Helm dependency error | Dependency repo unreachable | Repo-server logs | Add repo credentials and commit Chart.lock |
| `helm list` empty | Argo CD is not using Helm release lifecycle | Application state | Use `argocd app list/get`, not `helm list` |

## 31. Helm Chart Review Checklist for OpenShift

Before approving a Helm chart for OpenShift GitOps, review:

### Chart source

- Is the chart from a trusted repository?
- Is chart version pinned?
- Is the chart maintained?
- Are dependencies pinned?
- Is `Chart.lock` committed for internal charts?

### Security

- Does it run as root?
- Does it require privileged SCC?
- Does it use hostPath, hostNetwork, hostPID, or hostIPC?
- Does it request dangerous Linux capabilities?
- Does it mount Docker socket or host filesystems?
- Are secrets externalized?

### OpenShift compatibility

- Does it support random UID?
- Does it support Route or acceptable Ingress?
- Does it work with OpenShift registry/mirrors?
- Does it support ServiceMonitor if needed?
- Does it create NetworkPolicies compatible with router/monitoring traffic?

### GitOps behavior

- Does it use random values?
- Does it rely on Helm hooks?
- Does it create CRDs?
- Does it mutate resources outside GitOps?
- Does it generate stable object names?
- Does it work with Argo CD prune?

### Operations

- Are resources requests/limits defined?
- Is HPA configured correctly?
- Is PDB configured for HA workloads?
- Are probes configured?
- Are PVCs configured with correct StorageClass/access mode?
- Are logs and metrics available?

## 32. Recommended Production Patterns

### Pattern 1: One chart, many values files

```text
chart/
  values.yaml
  values-dev.yaml
  values-test.yaml
  values-prod.yaml
```

Good for internally owned apps.

### Pattern 2: External chart, internal values repo

```text
Vendor chart: https://charts.vendor.com
Internal values: https://git.example.com/platform/values.git
```

Good for third-party platform tools.

### Pattern 3: Wrapper chart

Use when vendor chart needs OpenShift-specific Route, SCC, NetworkPolicy, or monitoring resources.

### Pattern 4: Platform-owned CRDs, app-owned CRs

CRDs installed once by platform GitOps. Application teams deploy custom resources only after CRDs are available.

### Pattern 5: Manual prod sync, automated lower environments

```text
Dev: automated prune + selfHeal
Test: automated or manual depending on QA
Prod: manual sync with approval
```

---

## 33. Anti-Patterns

Avoid these in production:

1. Using `targetRevision: latest` or unpinned chart versions.
2. Giving all apps access to the `default` AppProject.
3. Storing production secrets in plain values files.
4. Relying on `helm upgrade` for an Argo CD-managed app.
5. Manually editing live resources and expecting changes to persist with self-heal enabled.
6. Ignoring repo-server errors and repeatedly syncing.
7. Granting `anyuid` or `privileged` SCC to default service accounts broadly.
8. Letting application charts install cluster-wide CRDs without governance.
9. Overriding Helm `releaseName` without checking selectors.
10. Hiding every diff with `ignoreDifferences` instead of fixing root causes.

### Broken Application

```yaml
helm:
  valueFiles:
    - values-production.yaml
```

But the file does not exist.

Expected error:

```text
failed to generate manifests: open ... values-production.yaml: no such file or directory
```

```bash
argocd app get <app-name>
argocd app manifests <app-name>
oc logs -n openshift-gitops deploy/openshift-gitops-repo-server | tail -100
```

### Fix options

Option 1: Correct the file path.

```yaml
helm:
  valueFiles:
    - values-prod.yaml
```

```yaml
helm:
  valueFiles:
    - values-common.yaml
    - values-prod-optional.yaml
  ignoreMissingValueFiles: true
```

Use `ignoreMissingValueFiles` only when the file is genuinely optional.

## 36. Practical Lab: SCC Failure with Helm Chart

### Symptom

```bash
oc get pods -n app-ns
oc describe pod <pod> -n app-ns
```

Error:

```text
unable to validate against any security context constraint
```

### Investigation

Check chart values:

```bash
helm show values <repo>/<chart> | grep -i security -A20
```

Check rendered pod spec:

```bash
argocd app manifests <app-name> | grep -i "runAs\|privileged\|hostPath" -A5 -B5
```

### Safer fix

Create a dedicated ServiceAccount:

```bash
oc create sa app-sa -n app-ns
```

Bind only the required SCC:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n app-ns
```

Set chart values:

```yaml
serviceAccount:
  create: false
  name: app-sa
```

Avoid broad grants to `default` unless it is a lab or temporary emergency.

## 37. Exam/Interview Style Questions

### Q1. Does Argo CD run `helm install`?

Usually no. Argo CD uses Helm to render manifests and then Argo CD applies/manages them.

### Q2. Why is `helm list` empty for an Argo CD Helm app?

Because Argo CD did not create a Helm release. It rendered the chart and owns the resources through the Application controller.

### Q3. What is the values precedence order?

From highest to lowest:

```text
parameters > valuesObject > values > valueFiles > chart values.yaml
```

### Q4. Why does my app stay OutOfSync after sync?

Common reasons:

- Helm chart uses random template functions.
- Mutating webhook changes live resources.
- HPA changes replicas.
- OpenShift/controller defaulting changes fields.
- Chart labels/selectors are unstable.

### Q5. Why does an OCI Helm repo fail when I use `oci://`?

When using Argo CD's Helm repository mode with `--enable-oci`, the repository URL generally omits `oci://`. Use the syntax supported by your Argo CD version.

### Q6. How do you make Argo CD manage another OpenShift namespace?

Label the target namespace:

```bash
oc label namespace <target_namespace> argocd.argoproj.io/managed-by=<argocd_namespace>
```

For the default OpenShift GitOps instance:

```bash
oc label namespace app-ns argocd.argoproj.io/managed-by=openshift-gitops
```

### Q7. How do you restrict Helm chart deployments?

Use AppProjects to restrict:

- Source repositories
- Target clusters/namespaces
- Cluster-scoped resources
- Namespace-scoped resource kinds
- Project roles and groups

### Q8. What is the safest rollback model?

Git revert or chart/image version rollback through Git, followed by Argo CD sync.

## 38. Senior Admin Mental Model

Think of Helm in Argo CD like this:

```text
Git / Helm repo / OCI registry
        |
        v
Argo CD repo-server
        |
        |  helm template + values + chart version
        v
Rendered manifests
        |
        v
Argo CD application-controller
        |
        |  compare, sync, prune, self-heal
        v
OpenShift API
        |
        v
Live cluster resources
```

Your job as an advanced OpenShift administrator is to control every boundary:

- Who can define Applications?
- Which Helm repositories are trusted?
- Which chart versions are allowed?
- Which namespaces can be targeted?
- Which resource kinds can be deployed?
- Which SCCs are permitted?
- Which secrets workflow is approved?
- Which values files represent dev/test/prod?
- Which changes are automatically synced?
- Which changes require manual production approval?

## 39. Final Best Practices Summary

1. Use OpenShift GitOps Operator for supported OpenShift GitOps deployments.
2. Treat Helm as a renderer inside Argo CD, not as the release owner.
3. Pin chart versions.
4. Store values in Git.
5. Avoid plain-text secrets in values files.
6. Use AppProjects for source/destination/resource restrictions.
7. Label target namespaces intentionally with `argocd.argoproj.io/managed-by`.
8. Test charts with `helm template` and `oc apply --dry-run=server` before merge.
9. Use wrapper charts for OpenShift-specific resources when upstream charts are generic.
10. Manage CRDs at the platform layer unless the application genuinely owns them.
11. Avoid complex Helm hooks; prefer Argo CD sync waves and hooks.
12. Watch repo-server logs for Helm rendering failures.
13. Understand SCC and Route requirements before approving charts.
14. Use Git revert or chart version rollback instead of `helm rollback`.
15. Do not use the unrestricted `default` AppProject for real multi-tenant production workloads.

## 41. One-Line Definition

**Helm integration in OpenShift GitOps means Argo CD uses Helm charts as declarative sources, renders them into OpenShift/Kubernetes manifests, and then Argo CD — not Helm — continuously manages synchronization, drift correction, pruning, health, and operational lifecycle according to Git-defined desired state.**
