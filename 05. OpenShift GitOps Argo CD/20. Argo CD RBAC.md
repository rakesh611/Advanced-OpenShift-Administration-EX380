## 1. Executive Summary

**Argo CD RBAC** controls what an authenticated Argo CD user, group, or local account can do **inside Argo CD**. It decides whether a user can see applications, sync them, delete them, access logs, execute into pods, create projects, manage repositories, create ApplicationSets, or administer Argo CD resources.

In **OpenShift GitOps**, RBAC must be understood at two major levels:

1. **Kubernetes/OpenShift RBAC**
   - Controls what the Argo CD controller service account can do against the Kubernetes API.
   - Example: Can the Argo CD application controller create Deployments, Routes, NetworkPolicies, Secrets, or Namespaces?

2. **Argo CD RBAC**
   - Controls what human users and automation users can do in Argo CD.
   - Example: Can user `alice` sync `payments-dev/payment-api` or only view it?

A common senior-admin mistake is to configure only Argo CD RBAC and forget Kubernetes RBAC, or to configure only Kubernetes RBAC and assume Argo CD users are restricted. Both are wrong. In OpenShift GitOps, these two access models are separate and must be designed together.

For production multi-tenancy, the safest design is:

- Use **separate Argo CD instances** for cluster administration and application teams when risk is high.
- Use **AppProjects** to restrict:
  - allowed Git repositories,
  - allowed destination clusters/namespaces,
  - allowed Kubernetes resource kinds,
  - sync windows,
  - project-scoped roles.
- Use **Argo CD RBAC** to control user operations.
- Do not rely on the unrestricted `default` AppProject.
- Do not give normal users access to the Argo CD control-plane namespace.
- Avoid broad `policy.default: role:readonly` if users should not see all applications.
- Avoid granting `exec`, `override`, wildcard `applications, *`, and `projects, *` unless absolutely required.

## 2. What Argo CD RBAC Actually Controls

Argo CD RBAC controls access to **Argo CD resources and Argo CD operations**, not direct Kubernetes permissions of the user.

Examples of things Argo CD RBAC controls:

| Area | Example Permission |
|---|---|
| Applications | View, create, update, delete, sync, override, run resource actions |
| ApplicationSets | View, create, update, delete |
| Projects | View, create, update, delete |
| Repositories | View, add, update, delete Git repositories |
| Clusters | View, add, update, delete target clusters |
| Logs | View application pod logs from Argo CD UI |
| Exec | Open web terminal / exec into application pods |
| Accounts | View or update Argo CD accounts |
| Certificates / GPG keys | Manage trust material |
| Extensions | Invoke configured proxy extensions |

Important point:

> A user may have **no direct OpenShift RBAC permission** to create Deployments, but if Argo CD RBAC allows that user to sync an Application, and the Argo CD controller service account has permission to create Deployments, the user can indirectly cause that Deployment to be created.

That is why Argo CD is a powerful privilege boundary and must be treated as a security-sensitive control plane.

## 3. Three RBAC Layers in OpenShift GitOps

In production OpenShift GitOps, think in three layers.

### 3.1 OpenShift/Kubernetes RBAC for Human Users

This is normal OpenShift RBAC:

```bash
oc adm policy add-role-to-user edit alice -n dev
oc adm policy add-cluster-role-to-group cluster-admin cluster-admins
oc auth can-i create deployments -n dev --as alice
```

It controls direct API access through `oc`, Kubernetes clients, OpenShift console, and service accounts.

### 3.2 OpenShift/Kubernetes RBAC for Argo CD Components

Argo CD components run as Kubernetes service accounts. The most security-sensitive one is normally:

```text
argocd-application-controller
```

The application controller reconciles desired state from Git into the cluster. It needs Kubernetes permissions to create, update, delete, watch, and list the resources it manages.

For a namespace-scoped instance, the controller may only manage its namespace initially. OpenShift GitOps can extend this access to other namespaces using labels or namespace management features.

For a cluster-scoped instance, the controller has cluster-level visibility and a controlled set of cluster-level permissions.

### 3.3 Argo CD RBAC for Argo CD Users

This is the policy engine inside Argo CD. It controls operations such as:

```text
Can user alice sync application payments-dev/api?
Can group ocp-devs create repositories?
Can group qa-team view logs?
Can group prod-ops delete production apps?
```

Argo CD RBAC is commonly configured through:

- OpenShift GitOps `ArgoCD` custom resource `.spec.rbac`
- Generated `argocd-rbac-cm` ConfigMap
- AppProject `.spec.roles`
- SSO group claims from OpenShift OAuth/Dex/OIDC
- local Argo CD users for automation

## 4. Default Behavior in OpenShift GitOps

Default behavior matters because many RBAC incidents happen before custom policies are added.

### 4.1 Default Argo CD Instance

The OpenShift GitOps Operator normally creates a default Argo CD instance in:

```text
openshift-gitops
```

This default instance is intended for cluster configuration use cases, not general application delivery for many tenants.

For multi-tenant production design, do not allow normal developer teams to administer or freely use this default instance.

### 4.2 Default User Access

In current Red Hat OpenShift GitOps documentation, default access differs depending on instance type:

- A user logged into the **default Argo CD instance** normally does not have service access, except `kube:admin`.
- A user logged into a **custom Argo CD instance** is read-only by default.

Always verify the effective policy in your running environment because upgrades, custom CR fields, and existing ConfigMaps can change behavior.

### 4.3 Default `admin` User

Argo CD has a built-in `admin` user. This user is a superuser in Argo CD. In production, many organizations disable it after SSO and break-glass access are configured.

Typical hardening approach:

1. Configure SSO through OpenShift OAuth/Dex or external OIDC.
2. Bind a controlled OpenShift group to Argo CD admin.
3. Test break-glass procedure.
4. Disable or restrict the built-in admin user if your policy allows it.

### 4.4 Default AppProject Risk

Argo CD creates a `default` AppProject. The default project is usually broad and should not be used for production tenant applications.

A dangerous combination is:

```text
User can create Applications + default AppProject allows everything + Argo CD controller has broad Kubernetes permissions
```

That combination can become privilege escalation.

## 5. Core RBAC Objects and Files

### 5.1 `ArgoCD` Custom Resource

In OpenShift GitOps, the Operator manages Argo CD. You usually configure RBAC declaratively in the `ArgoCD` CR.

Example:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  rbac:
    policy: |
      g, ocp-cluster-admins, role:admin
      g, gitops-platform-admins, role:admin
      p, role:authenticated, applications, get, */*, allow
    scopes: '[groups]'
```

The Operator reconciles this into the Argo CD RBAC configuration.

### 5.2 `argocd-rbac-cm` ConfigMap

Upstream Argo CD stores global RBAC in:

```text
argocd-rbac-cm
```

Typical structure:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: openshift-gitops
data:
  policy.csv: |
    p, role:dev-sync, applications, get, team-a/*, allow
    p, role:dev-sync, applications, sync, team-a/*, allow
    g, ocp-team-a-devs, role:dev-sync
  policy.default: role:authenticated
  scopes: '[groups]'
```

In OpenShift GitOps, prefer updating the `ArgoCD` CR unless your operational model explicitly manages the ConfigMap and you understand Operator reconciliation behavior.

### 5.3 `AppProject`

The AppProject is the most important multi-tenant security object in Argo CD.

It controls:

- which Git repositories are allowed,
- which clusters and namespaces are allowed,
- which cluster-scoped resources are allowed or denied,
- which namespace-scoped resources are allowed or denied,
- project-level RBAC roles,
- sync windows.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-dev
  namespace: openshift-gitops
spec:
  description: Payments team development project
  sourceRepos:
    - 'https://git.example.com/payments/*'
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
    - group: route.openshift.io
      kind: Route
  roles:
    - name: developer
      description: Payments developers can view and sync dev apps
      groups:
        - ocp-payments-devs
      policies:
        - p, proj:payments-dev:developer, applications, get, payments-dev/*, allow
        - p, proj:payments-dev:developer, applications, sync, payments-dev/*, allow
```

### 5.4 OpenShift Groups

OpenShift OAuth/Dex can pass group membership into Argo CD. Manage groups in OpenShift:

```bash
oc adm groups new ocp-payments-devs
oc adm groups add-users ocp-payments-devs alice bob
oc get groups
```

Then bind that group inside Argo CD RBAC:

```text
g, ocp-payments-devs, role:payments-dev-sync
```

or in AppProject roles:

```yaml
groups:
  - ocp-payments-devs
```

### 5.5 Local Users

Local users are useful for automation, CI/CD, monitoring, and service integrations. They should not replace enterprise SSO for normal human users.

OpenShift GitOps supports declarative local users in the `ArgoCD` CR in newer versions:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: example-argocd
  namespace: argocd
spec:
  localUsers:
    - name: ci-system
      enabled: true
      apiKey: true
      login: false
      tokenLifetime: "720h"
      autoRenewToken: true
```

Then grant only required RBAC to that local account:

```text
p, ci-system, applications, sync, payments-dev/*, allow
p, ci-system, applications, get, payments-dev/*, allow
```

## 6. Argo CD RBAC Policy Syntax

Argo CD RBAC is based on a Casbin-style policy model.

There are two main line types:

1. `p` policy lines
2. `g` grouping / role-binding lines

### 6.1 Policy Line Syntax

```text
p, <subject>, <resource>, <action>, <object>, <effect>
```

Example:

```text
p, role:payments-dev, applications, sync, payments-dev/*, allow
```

Meaning:

```text
Allow role:payments-dev to sync applications matching payments-dev/*
```

Fields:

| Field | Meaning | Example |
|---|---|---|
| `p` | Policy rule marker | `p` |
| subject | User, group, or role | `role:payments-dev` |
| resource | Argo CD resource type | `applications` |
| action | Operation | `get`, `sync`, `delete` |
| object | Target object pattern | `payments-dev/*` |
| effect | `allow` or `deny` | `allow` |

### 6.2 Grouping Line Syntax

```text
g, <user-or-group>, <role>
```

Example:

```text
g, ocp-payments-devs, role:payments-dev
```

Meaning:

```text
Members of OpenShift/OIDC group ocp-payments-devs receive role:payments-dev
```

### 6.3 Role Naming

Use a clear role naming convention:

```text
role:<scope>-<environment>-<capability>
```

Examples:

```text
role:payments-dev-readonly
role:payments-dev-sync
role:payments-prod-readonly
role:platform-admin
role:qa-logs
role:ci-sync
```

### 6.4 Subject Types

A subject can be:

- local user: `ci-system`
- SSO user: `alice@example.com`
- SSO group: `ocp-payments-devs`
- internal Argo CD role: `role:payments-dev-sync`
- AppProject role subject: `proj:payments-dev:developer`

### 6.5 Comments

Policy files can include comments depending on how they are processed, but keep production policy simple. Avoid relying on comments in generated policy strings if your templating tool might strip or corrupt them.

## 7. Built-in Roles and Default Policy

Argo CD has two common built-in roles:

| Role | Meaning |
|---|---|
| `role:readonly` | Read-only access to resources |
| `role:admin` | Unrestricted Argo CD admin access |

### 7.1 `role:admin`

This role is powerful. It can manage Argo CD resources broadly. Do not map large groups to `role:admin`.

Bad example:

```text
g, system:authenticated, role:admin
```

Good example:

```text
g, gitops-platform-admins, role:admin
```

### 7.2 `role:readonly`

`role:readonly` can still reveal sensitive operational information. In some setups, read access to all applications may expose:

- application names,
- namespaces,
- Git repository URLs,
- resource manifests,
- sync status,
- image names,
- health details,
- deployment topology.

Do not assume read-only means harmless.

### 7.3 `policy.default`

`policy.default` applies to authenticated users by default.

Example:

```yaml
data:
  policy.default: role:readonly
```

This means every authenticated user gets `role:readonly` before more specific policies are evaluated.

For stricter environments, create a minimal default role:

```text
p, role:authenticated, applications, get, none/none, deny
```

and then:

```yaml
policy.default: role:authenticated
```

A practical approach is:

```yaml
policy.default: role:none
```

with:

```text
p, role:none, applications, get, no-project/no-app, deny
```

Then explicitly assign permissions through project roles or specific global roles.

### 7.4 Why Broad `policy.default` Is Dangerous

If you set:

```yaml
policy.default: role:readonly
```

then every SSO-authenticated user may see applications unless additional controls are applied. A later `deny` rule might not remove default policy access the way you expect because default policy evaluation has special behavior.

Production recommendation:

> Keep `policy.default` minimal and grant real access through explicit groups and AppProject roles.

## 8. Resources, Actions, and Object Patterns

Argo CD RBAC supports different resources and actions. The most important ones for OpenShift administrators are listed below.

| Resource | Common Actions | Production Risk |
|---|---|---|
| `applications` | `get`, `create`, `update`, `delete`, `sync`, `action`, `override` | Very high |
| `applicationsets` | `get`, `create`, `update`, `delete` | Very high |
| `projects` | `get`, `create`, `update`, `delete` | Very high |
| `repositories` | `get`, `create`, `update`, `delete` | High |
| `clusters` | `get`, `create`, `update`, `delete` | Critical |
| `logs` | `get` | Medium to high |
| `exec` | `create` | Critical |
| `accounts` | `get`, `update` | High |
| `certificates` | `get`, `create`, `delete` | High |
| `gpgkeys` | `get`, `create`, `delete` | High |
| `extensions` | `invoke` | Depends on extension |

### 8.1 Application Object Format

For normal applications:

```text
<project>/<application-name>
```

Example:

```text
payments-dev/payment-api
```

Policy:

```text
p, role:payments-dev-sync, applications, sync, payments-dev/payment-api, allow
```

For all apps in a project:

```text
payments-dev/*
```

Policy:

```text
p, role:payments-dev-sync, applications, sync, payments-dev/*, allow
```

For any project and any app:

```text
*/*
```

Avoid this except for trusted platform admins.

### 8.2 Application in Any Namespace Object Format

If Argo CD is configured to support Applications in any namespace, object matching can include the application namespace:

```text
<project>/<application-namespace>/<application-name>
```

Example:

```text
payments-dev/payments-gitops/payment-api
```

Policy:

```text
p, role:payments-dev-read, applications, get, payments-dev/payments-gitops/*, allow
```

### 8.3 Repository Object Format

Repositories are usually matched by URL or wildcard pattern.

Example:

```text
p, role:repo-admin, repositories, create, *, allow
p, role:repo-reader, repositories, get, *, allow
```

Be careful with repository create/update permissions because users can point Argo CD to untrusted or unauthorized Git sources.

### 8.4 Cluster Object Format

Cluster permissions are highly sensitive.

```text
p, role:cluster-admin, clusters, get, *, allow
p, role:cluster-admin, clusters, create, *, allow
p, role:cluster-admin, clusters, update, *, allow
p, role:cluster-admin, clusters, delete, *, allow
```

Only platform administrators should manage target clusters.

## 9. Global RBAC vs AppProject RBAC

Argo CD RBAC can be configured globally or at AppProject level.

### 9.1 Global RBAC

Global RBAC is stored in the RBAC ConfigMap or configured through the OpenShift GitOps `ArgoCD` CR.

Use global RBAC for:

- platform admin role mappings,
- repository admin roles,
- cluster admin roles,
- global read-only roles,
- cross-project roles,
- shared automation accounts.

Example:

```text
g, gitops-platform-admins, role:admin
p, role:repo-admin, repositories, *, *, allow
g, gitops-repo-admins, role:repo-admin
```

### 9.2 AppProject RBAC

AppProject RBAC is scoped to one AppProject.

Use AppProject RBAC for tenant teams:

- team developers,
- QA testers,
- production release managers,
- service-specific automation,
- environment-based permissions.

Example:

```yaml
spec:
  roles:
    - name: dev-sync
      groups:
        - ocp-payments-devs
      policies:
        - p, proj:payments-dev:dev-sync, applications, get, payments-dev/*, allow
        - p, proj:payments-dev:dev-sync, applications, sync, payments-dev/*, allow
```

### 9.3 Which One Should You Use?

Production recommendation:

| Use Case | Recommended Place |
|---|---|
| Platform admins | Global RBAC |
| Repository/cluster administrators | Global RBAC |
| Tenant application access | AppProject roles |
| Team-based sync rights | AppProject roles |
| Environment-specific access | AppProject roles |
| Cross-project support role | Global RBAC, carefully scoped |
| CI user for one project | AppProject role or direct local user policy |

### 9.4 Why AppProject RBAC Is Better for Tenants

AppProject keeps authorization close to the project boundary:

- app access,
- destination namespace restrictions,
- allowed Git repos,
- allowed resource kinds,
- sync windows,
- group-to-role mappings.

This creates a more complete tenant boundary than global RBAC alone.

## 10. SSO, OpenShift OAuth, Dex, Groups, and Scopes

### 10.1 OpenShift OAuth Through Dex

OpenShift GitOps can use Dex to authenticate users through the OpenShift OAuth server.

Example `ArgoCD` CR snippet:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  sso:
    provider: dex
    dex:
      openShiftOAuth: true
  rbac:
    policy: |
      g, cluster-admins, role:admin
      g, gitops-platform-admins, role:admin
    scopes: '[groups]'
```

### 10.2 OpenShift Groups

Create and manage OpenShift groups:

```bash
oc adm groups new gitops-platform-admins
oc adm groups add-users gitops-platform-admins alice
oc get groups gitops-platform-admins -o yaml
```

Bind group to Argo CD role:

```text
g, gitops-platform-admins, role:admin
```

### 10.3 Direct ClusterRoleBinding Does Not Always Map as Expected

In OpenShift GitOps, mapping a user to Argo CD admin through a direct `ClusterRoleBinding` may not be enough for Argo CD SSO role mapping. A safer and clearer method is:

```bash
oc adm groups new cluster-admins
oc adm groups add-users cluster-admins alice
oc adm policy add-cluster-role-to-group cluster-admin cluster-admins
```

Then in Argo CD RBAC:

```text
g, cluster-admins, role:admin
```

### 10.4 Scopes

Scopes tell Argo CD which OIDC claims to inspect for RBAC matching.

Common value:

```yaml
scopes: '[groups]'
```

Sometimes you may also use email:

```yaml
scopes: '[groups, email]'
```

Then you can bind:

```text
g, alice@example.com, role:admin
```

### 10.5 Group Naming Strategy

Use predictable OpenShift groups:

```text
gitops-platform-admins
gitops-repo-admins
ocp-payments-devs
ocp-payments-prod-release
ocp-payments-qa
ocp-inventory-devs
ocp-inventory-prod-readonly
```

Avoid vague group names:

```text
admins
devs
users
test
team1
```

### 10.6 SSO Debug Commands

Check user identity:

```bash
oc whoami
oc whoami --show-groups
```

Check OpenShift group:

```bash
oc get groups
oc get group ocp-payments-devs -o yaml
```

Check Argo CD RBAC ConfigMap:

```bash
oc get cm argocd-rbac-cm -n openshift-gitops -o yaml
```

Check Argo CD CR:

```bash
oc get argocd openshift-gitops -n openshift-gitops -o yaml
```

## 11. Local Users and Automation Tokens

### 11.1 When to Use Local Users

Use local users for:

- CI/CD automation,
- monitoring tools,
- webhook integrations,
- temporary break-glass automation,
- service accounts that cannot use SSO.

Do not use local users as the primary identity model for normal enterprise users.

### 11.2 Local User Example

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: example-argocd
  namespace: argocd
spec:
  localUsers:
    - name: ci-payments
      enabled: true
      apiKey: true
      login: false
      tokenLifetime: "168h"
      autoRenewToken: true
```

Grant minimal access:

```yaml
spec:
  rbac:
    policy: |
      p, ci-payments, applications, get, payments-dev/*, allow
      p, ci-payments, applications, sync, payments-dev/*, allow
    scopes: '[groups]'
```

### 11.3 Retrieve Token

Token secret format may vary by version and configuration. For Operator-managed local users, check for a secret named like:

```text
<username>-local-user
```

Example:

```bash
oc get secret ci-payments-local-user -n argocd \
  -o jsonpath='{.data.apiToken}' | base64 -d
```

Use token:

```bash
argocd --server <argocd-server> --auth-token <token> app list
```

### 11.4 Local User Security Notes

Do:

- use short token lifetimes for CI where possible,
- rotate tokens,
- bind direct policies to local users,
- store tokens in a real secret manager,
- audit token use.

Avoid:

- mapping local users to broad roles,
- using local users with SSO group names that could collide,
- non-expiring tokens for high-privilege users,
- shared human local accounts.

## 12. Designing RBAC for Multi-Tenant OpenShift

### 12.1 Multi-Tenant RBAC Goal

A strong multi-tenant design should answer these questions:

1. Who can see which applications?
2. Who can sync which applications?
3. Who can create or update Applications?
4. Who can delete Applications?
5. Which Git repositories can a project use?
6. Which namespaces can a project deploy into?
7. Which Kubernetes resource kinds are allowed?
8. Who can view logs?
9. Who can exec into pods?
10. Who can manage repositories, clusters, and projects?
11. Can tenants escalate by changing AppProject or ApplicationSet configuration?
12. Can tenants deploy cluster-scoped resources?

### 12.2 Recommended Instance Separation

Use separate Argo CD instances when possible:

| Instance | Namespace | Purpose | Users |
|---|---|---|---|
| `openshift-gitops` | `openshift-gitops` | Cluster configuration | Cluster admins only |
| `payments-gitops` | `payments-gitops` | Payments apps | Payments team |
| `shared-apps-gitops` | `shared-gitops` | Shared application delivery | Multiple app teams |
| `infra-gitops` | `infra-gitops` | Infra components | Platform team |

### 12.3 Namespace-Scoped vs Cluster-Scoped

#### Namespace-scoped instance

Best for:

- one team,
- one or few namespaces,
- application delivery,
- lower blast radius.

Limitations:

- cannot manage cluster-scoped resources such as Namespaces, CRDs, ClusterRoles.
- must be granted access to each managed namespace.

#### Cluster-scoped instance

Best for:

- cluster configuration,
- platform infrastructure,
- central management by platform team.

Risk:

- users with admin control of that Argo CD instance may indirectly gain cluster-level impact.

### 12.4 Tenant Boundary Checklist

For each tenant:

- Dedicated AppProject.
- Dedicated OpenShift group(s).
- Dedicated namespace(s).
- Restricted `sourceRepos`.
- Restricted `destinations`.
- Restricted resource allowlist.
- No cluster-scoped resources unless approved.
- No unrestricted ApplicationSet project templating.
- No access to Argo CD namespace.
- No use of default AppProject.
- No broad `applications, *, */*` policy.

## 15. AppProject Deep Dive

### 15.1 `sourceRepos`

Controls which Git repositories can be used.

Strict:

```yaml
sourceRepos:
  - 'https://git.example.com/payments/payment-api.git'
```

Moderate:

```yaml
sourceRepos:
  - 'https://git.example.com/payments/*'
```

Dangerous:

```yaml
sourceRepos:
  - '*'
```

### 15.2 `destinations`

Controls where applications can deploy.

Strict:

```yaml
destinations:
  - server: https://kubernetes.default.svc
    namespace: payments-dev
```

Multiple approved namespaces:

```yaml
destinations:
  - server: https://kubernetes.default.svc
    namespace: payments-dev
  - server: https://kubernetes.default.svc
    namespace: payments-test
```

Dangerous:

```yaml
destinations:
  - server: '*'
    namespace: '*'
```

### 15.3 `clusterResourceWhitelist`

Controls allowed cluster-scoped resources.

For normal app teams:

```yaml
clusterResourceWhitelist: []
```

For platform config projects:

```yaml
clusterResourceWhitelist:
  - group: ''
    kind: Namespace
  - group: rbac.authorization.k8s.io
    kind: ClusterRole
  - group: rbac.authorization.k8s.io
    kind: ClusterRoleBinding
```

Only platform admins should manage projects that allow cluster-scoped resources.

### 15.4 `namespaceResourceWhitelist`

Controls allowed namespaced resources.

Example:

```yaml
namespaceResourceWhitelist:
  - group: apps
    kind: Deployment
  - group: ''
    kind: Service
  - group: route.openshift.io
    kind: Route
```

### 15.5 Blacklist vs Whitelist

Prefer allowlists in regulated environments.

Denylist example:

```yaml
namespaceResourceBlacklist:
  - group: ''
    kind: Secret
```

This blocks Secrets but may still allow many unexpected resource types. Allowlist is usually stronger.

### 15.6 Sync Windows

Use sync windows to restrict production changes:

```yaml
syncWindows:
  - kind: deny
    schedule: '0 18 * * 1-5'
    duration: 12h
    applications:
      - '*'
    manualSync: false
```

This kind of rule is useful for change-control windows, but it must align with your real operational policy.

## 17. Fine-Grained Application Permissions

### 17.1 Basic Application Permissions

Read-only:

```text
p, role:app-read, applications, get, payments-dev/*, allow
```

Sync:

```text
p, role:app-sync, applications, sync, payments-dev/*, allow
```

Create:

```text
p, role:app-create, applications, create, payments-dev/*, allow
```

Update:

```text
p, role:app-update, applications, update, payments-dev/*, allow
```

Delete:

```text
p, role:app-delete, applications, delete, payments-dev/*, allow
```

### 17.2 Production Safe Pattern

Developers:

```text
p, role:payments-dev, applications, get, payments-dev/*, allow
p, role:payments-dev, applications, sync, payments-dev/*, allow
p, role:payments-dev, logs, get, payments-dev/*, allow
```

Production release managers:

```text
p, role:payments-prod-release, applications, get, payments-prod/*, allow
p, role:payments-prod-release, applications, sync, payments-prod/*, allow
p, role:payments-prod-release, logs, get, payments-prod/*, allow
p, role:payments-prod-release, applications, delete, payments-prod/*, deny
```

Platform admins:

```text
g, gitops-platform-admins, role:admin
```

### 17.3 Resource-Level Update/Delete

Argo CD supports fine-grained update/delete actions on application resources.

Pattern:

```text
<action>/<group>/<kind>/<namespace>/<name>
```

Allow deleting only Pods in one app:

```text
p, example-user, applications, delete/*/Pod/*/*, payments-dev/payment-api, allow
```

Deny deleting the Application itself:

```text
p, example-user, applications, delete, payments-dev/payment-api, deny
```

Practical use:

- allow restarting workloads by deleting pods,
- deny deleting Argo CD Application objects,
- allow controlled operations without full app admin.

### 17.4 Wildcard Warning

Avoid short ambiguous patterns such as:

```text
p, user, applications, delete/*/Pod/*, payments-dev/payment-api, allow
```

Use the full pattern with all components:

```text
p, user, applications, delete/*/Pod/*/*, payments-dev/payment-api, allow
```

## 18. Logs, Exec, Resource Actions, and Override

### 18.1 Logs

Policy:

```text
p, role:qa-logs, logs, get, payments-qa/*, allow
```

Risk:

- logs may contain tokens,
- logs may contain customer data,
- logs may expose internal endpoints.

Grant logs intentionally.

### 18.2 Exec

Policy:

```text
p, role:debug-exec, exec, create, payments-dev/*, allow
```

Risk:

- equivalent to shell access into workloads,
- may expose mounted secrets,
- may bypass normal operational controls,
- can be dangerous in production.

Production recommendation:

- disable or deny exec broadly,
- grant only temporary access,
- audit usage,
- prefer debug pods with OpenShift RBAC workflows.

### 18.3 Resource Actions

Argo CD supports resource actions such as restart-like actions depending on resource customizations.

Pattern:

```text
p, role:operator, applications, action/<group>/<kind>/<action-name>, <project>/<app>, allow
```

Example:

```text
p, role:payments-ops, applications, action/apps/Deployment/restart, payments-dev/payment-api, allow
```

Use cases:

- restart Deployment,
- resume Rollout,
- custom operational actions.

### 18.4 Override

`override` can allow syncing local manifests or non-Git desired state behavior depending on configuration. Treat it as high risk because it can weaken Git as the source of truth.

Avoid:

```text
p, role:dev, applications, override, */*, allow
```

Prefer:

```text
p, role:trusted-release-engineer, applications, override, payments-dev/payment-api, allow
```

only if your operating model requires it.

## 19. ApplicationSet RBAC

ApplicationSets can create Applications automatically. If a user can create an ApplicationSet, they may indirectly create Applications.

Basic policy:

```text
p, role:appset-dev, applicationsets, create, payments-dev/*, allow
```

Important security point:

> ApplicationSet RBAC must be aligned with AppProject restrictions. A user should not be able to create an ApplicationSet that creates Applications outside their allowed project or namespace.

Safe pattern:

```text
p, role:payments-appset, applicationsets, get, payments-dev/*, allow
p, role:payments-appset, applicationsets, create, payments-dev/*, allow
p, role:payments-appset, applicationsets, update, payments-dev/*, allow
```

Dangerous pattern:

```text
p, role:devs, applicationsets, *, */*, allow
```

ApplicationSet permissions are especially sensitive in shared Argo CD instances.

## 20. OpenShift Namespace Access and Controller Permissions

### 20.1 Argo CD User RBAC Is Not Enough

A user may be allowed to sync an Application, but sync can still fail if the Argo CD controller cannot create resources in the destination namespace.

Example failure symptoms:

```text
permission denied
forbidden: User "system:serviceaccount:...:argocd-application-controller" cannot create resource "deployments"
```

### 20.2 Namespace-Scoped Instance Managing Another Namespace

Label target namespace:

```bash
oc label namespace payments-dev argocd.argoproj.io/managed-by=payments-gitops
```

Where `payments-gitops` is the namespace where the Argo CD instance runs.

Verify role bindings:

```bash
oc get rolebinding -n payments-dev | grep argocd
oc get role -n payments-dev | grep argocd
```

### 20.3 Custom Controller Cluster Role

For tighter control, define custom roles and configure Operator environment variables such as controller/server role selection where supported by your OpenShift GitOps version.

Reason:

- default managed namespace access may be equivalent to broad namespace admin,
- some teams require only deploy/update for specific resource kinds,
- compliance may require least privilege.

### 20.4 Cluster-Scoped Resources

A namespace-scoped Argo CD instance cannot manage cluster-scoped resources such as:

- Namespaces,
- CRDs,
- ClusterRoles,
- ClusterRoleBindings,
- StorageClasses,
- MachineConfigs.

Use a carefully controlled cluster-scoped instance for cluster configuration.

## 22. Troubleshooting Guide

### 22.1 User Logs In but Sees No Applications

Possible causes:

- no RBAC policy assigned,
- wrong group claim,
- `scopes` missing or wrong,
- AppProject role does not include user's group,
- application object pattern wrong,
- `policy.default` too restrictive.

Commands:

```bash
oc whoami --show-groups
oc get cm argocd-rbac-cm -n openshift-gitops -o yaml
oc get appproject -n openshift-gitops -o yaml
```

Check policy object format:

```text
project/app-name
```

Example:

```text
payments-dev/payment-api
```

### 22.2 User Is Read-Only but Should Be Admin

Possible causes:

- group mismatch,
- direct ClusterRoleBinding instead of group mapping,
- SSO claim does not include expected group,
- `g, group, role:admin` missing,
- user logged into wrong Argo CD instance.

Fix:

```bash
oc adm groups new gitops-platform-admins
oc adm groups add-users gitops-platform-admins alice
```

Policy:

```text
g, gitops-platform-admins, role:admin
```

### 22.3 User Can See Too Many Apps

Possible causes:

- `policy.default: role:readonly`,
- global wildcard policy,
- group assigned to broad role,
- AppProject role has wildcard object,
- app uses wrong project.

Find broad policies:

```bash
oc get cm argocd-rbac-cm -n openshift-gitops -o yaml | grep -E '\*/\*|role:readonly|role:admin'
```

Check Applications:

```bash
oc get applications.argoproj.io -A \
  -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,PROJECT:.spec.project
```

### 22.4 Sync Button Missing

Possible causes:

- user has `get` but not `sync`,
- app belongs to different project than policy object,
- deny policy matches,
- default policy does not grant sync,
- AppProject role policy is wrong.

Policy required:

```text
p, role:team-sync, applications, sync, payments-dev/*, allow
```

### 22.5 Sync Fails with Kubernetes Forbidden Error

This is not Argo CD user RBAC. This is OpenShift RBAC for the Argo CD controller.

Check:

```bash
oc describe application payment-api -n openshift-gitops
oc get events -n payments-dev --sort-by=.lastTimestamp
oc auth can-i create deployments \
  --as system:serviceaccount:openshift-gitops:<controller-sa> \
  -n payments-dev
```

Fix namespace access:

```bash
oc label namespace payments-dev argocd.argoproj.io/managed-by=openshift-gitops
```

or create explicit Role/RoleBinding.

### 22.6 AppProject Blocks Deployment

Symptoms:

```text
application destination is not permitted in project
repository is not permitted in project
resource kind is not permitted in project
```

Check:

```bash
oc get appproject payments-dev -n openshift-gitops -o yaml
```

Validate:

- `source.repoURL` matches `sourceRepos`,
- `destination.namespace` matches `destinations`,
- resource kind is whitelisted,
- cluster-scoped resources are not blocked.

### 22.7 Policy Changes Not Taking Effect

Possible causes:

- edited `argocd-rbac-cm` directly but Operator overwrote it,
- edited wrong namespace,
- syntax error,
- Argo CD server needs reload/restart depending on version,
- browser session stale,
- user token/group membership stale.

Actions:

```bash
oc get argocd -A
oc get cm argocd-rbac-cm -A
oc rollout restart deployment/<argocd-server-deployment> -n <argocd-namespace>
```

Log out and log back into Argo CD.

### 22.8 Group Exists in OpenShift but Argo CD Does Not Match It

Check:

```bash
oc whoami --show-groups
```

If the group is not shown, the user is not in that OpenShift group.

If group appears in OpenShift but not effective in Argo CD:

- check Dex/OpenShift OAuth config,
- check `scopes: '[groups]'`,
- check exact case-sensitive group name,
- check user logged into correct Argo CD instance.

### 22.9 User Can Create ApplicationSet and Bypass Restrictions

Possible causes:

- `applicationsets, create, */*` too broad,
- AppProject allows too many destinations,
- default project open,
- ApplicationSet can create apps in unauthorized project.

Fix:

```text
p, role:team-appset, applicationsets, create, payments-dev/*, allow
```

Lock down projects and default project.

## 23. Security Hardening Checklist

### 23.1 Identity and Authentication

- [ ] Enable SSO with OpenShift OAuth/Dex or enterprise OIDC.
- [ ] Use OpenShift groups, not individual users, for normal access.
- [ ] Keep platform admin group small.
- [ ] Avoid direct user-to-admin bindings except emergency break-glass.
- [ ] Review local users and tokens regularly.
- [ ] Disable or tightly control built-in `admin` user where appropriate.

### 23.2 Global RBAC

- [ ] Avoid `policy.default: role:readonly` if application visibility is sensitive.
- [ ] Avoid `g, system:authenticated, role:admin`.
- [ ] Avoid wildcard admin policies for broad groups.
- [ ] Keep repository and cluster management permissions platform-only.
- [ ] Test policies before applying.

### 23.3 AppProject

- [ ] Do not use default project for production.
- [ ] Lock down default project.
- [ ] Define one AppProject per team/environment where practical.
- [ ] Restrict `sourceRepos`.
- [ ] Restrict `destinations`.
- [ ] Use resource allowlists.
- [ ] Deny cluster-scoped resources for app teams.
- [ ] Use sync windows for production if required.

### 23.4 Dangerous Permissions

Review every use of:

```text
applications, *, */*
applications, delete
applications, override
applications, action
applicationsets, create
projects, update
repositories, create
clusters, create
exec, create
logs, get
```

### 23.5 Namespace and Controller Permissions

- [ ] Do not give tenants admin access to the Argo CD namespace.
- [ ] Limit controller permissions to required namespaces.
- [ ] Prefer namespace-scoped instances for tenant app delivery.
- [ ] Use cluster-scoped instances only for trusted platform teams.
- [ ] Do not elevate self-managed tenant Argo CD instances to cluster-scoped.

### 23.6 Audit and Operations

- [ ] Store RBAC in Git.
- [ ] Require pull request review for RBAC changes.
- [ ] Validate RBAC in CI.
- [ ] Keep break-glass process documented.
- [ ] Review Argo CD logs and OpenShift audit logs after RBAC incidents.
- [ ] Periodically list users/groups with admin-like access.

```bash
argocd app sync team-a-prod/app1   # should fail unless release group
```

### 24.2 Remove a User

1. Remove from OpenShift group.

```bash
oc adm groups remove-users ocp-team-a-devs alice
```

2. Ask user to log out/in or revoke sessions according to your identity provider procedure.

3. Verify:

```bash
oc get group ocp-team-a-devs -o yaml
```

4. Test if access is removed.

For Operator-managed local user:

```bash
oc delete secret ci-payments-local-user -n argocd
```

Retrieve new token:

```bash
oc get secret ci-payments-local-user -n argocd \
  -o jsonpath='{.data.apiToken}' | base64 -d
```

Update secret manager / CI system.



## 25. Interview and Real-World Scenario Questions

### Q1. What is the difference between OpenShift RBAC and Argo CD RBAC?

OpenShift RBAC controls access to the Kubernetes/OpenShift API. Argo CD RBAC controls what users can do inside Argo CD. A user may not have OpenShift permission to create a Deployment directly, but if Argo CD RBAC allows sync and the Argo CD controller has permission, the user can cause Argo CD to create that Deployment.

### Q2. Why is the Argo CD controller service account security-sensitive?

Because it applies manifests to the cluster. Its Kubernetes permissions define the real maximum impact of sync operations. If the controller has broad cluster permissions, users who can control Applications may indirectly perform privileged actions.

### Q3. Why should the default AppProject not be used in production?

The default AppProject is generally broad and can allow unrestricted repositories, destinations, and resource kinds. In production, every application should belong to a deliberately restricted AppProject.

### Q4. How do you give a team sync access to only one project?

Create an AppProject role scoped to that project:

```yaml
roles:
  - name: developer
    groups:
      - ocp-team-devs
    policies:
      - p, proj:team-dev:developer, applications, get, team-dev/*, allow
      - p, proj:team-dev:developer, applications, sync, team-dev/*, allow
```

### Q5. A user can click Sync but sync fails with `forbidden`. Is this Argo CD RBAC?

Usually no. If the Sync button is available, Argo CD RBAC allowed sync. The `forbidden` error usually means the Argo CD application controller service account lacks Kubernetes RBAC in the target namespace or for the target resource.

### Q6. Why is `exec` permission dangerous?

It allows terminal access into application pods through Argo CD. This can expose secrets, service account tokens, runtime data, and application internals. It should be tightly controlled.

### Q7. What is a good pattern for production access?

Developers get dev sync, QA gets QA sync/logs, release managers get prod sync, most users get prod read-only, and only platform admins get Argo CD admin.

### Q8. What is the risk of ApplicationSet create permission?

ApplicationSets can generate Applications. If unrestricted, a user may create many apps or apps targeting unauthorized projects/namespaces. ApplicationSet RBAC must align with AppProject restrictions.

### Q9. How do you validate RBAC before applying?

Use:

```bash
argocd admin settings rbac validate --policy-file policy.csv
argocd admin settings rbac can --policy-file policy.csv <subject> <action> <resource> <object>
```

### Q10. Why should tenants not have access to the Argo CD namespace?

A user with Kubernetes access to Argo CD control-plane resources may edit ConfigMaps, Secrets, Applications, AppProjects, or service accounts and bypass Argo CD RBAC.

## 27. Key Takeaways

1. Argo CD RBAC controls user actions inside Argo CD; OpenShift RBAC controls Kubernetes API access.
2. The Argo CD controller service account is the real deployment identity.
3. A user with sync access can indirectly use the controller's Kubernetes permissions.
4. Use AppProjects for tenant boundaries.
5. Use global RBAC for platform-wide roles only.
6. Avoid the default AppProject for production.
7. Keep `policy.default` minimal.
8. Map OpenShift groups to Argo CD roles; avoid per-user sprawl.
9. Restrict ApplicationSet, exec, override, repository, cluster, and project permissions.
10. Validate policies before applying.
11. Do not grant normal users access to the Argo CD namespace.
12. Separate cluster-config GitOps from application-delivery GitOps where possible.
