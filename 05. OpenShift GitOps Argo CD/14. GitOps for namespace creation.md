# GitOps for Namespace Creation in OpenShift GitOps / Argo CD

**Audience:** Advanced OpenShift Administration / OpenShift GitOps administrators with production experience  
**Focus:** How to create, manage, govern, troubleshoot, and secure OpenShift namespaces/projects through GitOps using Argo CD  
**Primary tools:** OpenShift GitOps Operator, Argo CD `Application`, `AppProject`, `ApplicationSet`, Kustomize, Helm, `oc`

---

## 1. Executive Summary

In OpenShift, namespace creation is not just a simple `kind: Namespace` object. A namespace is the foundation of tenancy, RBAC delegation, quota control, network isolation, image pull policy, workload security, monitoring boundaries, and application lifecycle. In OpenShift terminology, a **Project** is effectively a Kubernetes **Namespace** with OpenShift-specific behavior, metadata, and user-facing project workflows.

When namespace creation is managed through GitOps, Git becomes the source of truth for:

- which namespaces are allowed to exist,
- who owns them,
- which Argo CD instance manages them,
- what quotas and limits are applied,
- what default network security exists,
- which groups can administer or view them,
- which applications are allowed to deploy into them,
- and how drift is detected and corrected.

For an advanced administrator, GitOps namespace creation should be treated as **tenant onboarding automation**, not merely as a YAML file that creates a namespace.

The most important design decision is this:

> Should the namespace be created as a platform-owned cluster resource, or should it be created implicitly by an application using `CreateNamespace=true`?

Both approaches are valid, but they serve different operational models.

## 2. Namespace vs Project in OpenShift

Kubernetes has `Namespace`. OpenShift exposes the same isolation concept as `Project` for users. When you run:

```bash
oc new-project payments-dev
```

OpenShift creates a Kubernetes namespace and applies OpenShift project behavior around it, such as project metadata and user access workflows.

You can also create the namespace directly:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-dev
```

From a GitOps perspective, Argo CD normally applies Kubernetes/OpenShift manifests. Therefore, most GitOps namespace creation uses `kind: Namespace`, not `oc new-project`. This is important because `oc new-project` uses the OpenShift ProjectRequest flow, while applying a raw Namespace bypasses some user-facing project request semantics.

### 2.1 Why this matters

In production OpenShift clusters, the namespace/project normally carries more than a name:

- `ResourceQuota`
- `LimitRange`
- default deny `NetworkPolicy`
- team RBAC `RoleBinding`
- service accounts
- image pull secrets
- pod security admission labels
- workload placement labels
- monitoring labels
- cost allocation labels
- owner metadata
- backup labels
- Argo CD management labels

If you only create a namespace and forget the governance objects, the team may get an empty project that is not production-ready.

## 3. Why Manage Namespace Creation with GitOps?

GitOps namespace creation gives the platform team a consistent, auditable onboarding process.

Without GitOps, namespace creation often looks like this:

```bash
oc new-project app1-dev
oc adm policy add-role-to-group admin app1-admins -n app1-dev
oc create quota app1-quota --hard=requests.cpu=4,requests.memory=8Gi,pods=30 -n app1-dev
oc apply -f default-networkpolicy.yaml -n app1-dev
```

This works, but it is not ideal at scale. It creates several problems:

- no single source of truth,
- weak peer review,
- hard-to-audit manual changes,
- inconsistent quotas,
- missed NetworkPolicies,
- undocumented team ownership,
- difficult disaster recovery,
- and inconsistent namespace cleanup.

With GitOps, the namespace onboarding request becomes a pull request:

```text
platform-gitops/
└── clusters/
    └── prod/
        └── namespaces/
            └── payments-dev/
                ├── namespace.yaml
                ├── resourcequota.yaml
                ├── limitrange.yaml
                ├── networkpolicy-default-deny.yaml
                ├── rolebindings.yaml
                └── kustomization.yaml
```

After approval and merge, Argo CD reconciles the desired state into the cluster.

## 5. Pattern 1: Explicit Namespace Manifest Managed by a Platform Application

This is the most common production pattern for enterprise OpenShift.

The platform team creates a dedicated Argo CD application that owns namespace onboarding resources.

### 5.1 Repository layout

```text
platform-gitops/
├── clusters/
│   └── prod/
│       ├── bootstrap/
│       │   └── root-app.yaml
│       └── namespaces/
│           ├── kustomization.yaml
│           ├── payments-dev/
│           │   ├── namespace.yaml
│           │   ├── resourcequota.yaml
│           │   ├── limitrange.yaml
│           │   ├── networkpolicy-default-deny.yaml
│           │   ├── rolebindings.yaml
│           │   └── kustomization.yaml
│           └── payments-prod/
│               ├── namespace.yaml
│               ├── resourcequota.yaml
│               ├── limitrange.yaml
│               ├── networkpolicy-default-deny.yaml
│               ├── rolebindings.yaml
│               └── kustomization.yaml
```

### 5.10 Argo CD Application for namespace onboarding

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prod-namespaces
  namespace: openshift-gitops
spec:
  project: platform-admin
  source:
    repoURL: https://git.example.com/platform/platform-gitops.git
    targetRevision: main
    path: clusters/prod/namespaces
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - ServerSideApply=true
      - ApplyOutOfSyncOnly=true
```

### 5.11 Why destination namespace is `openshift-gitops`

A `Namespace` object is cluster-scoped, so it does not actually live inside `openshift-gitops`. However, Argo CD `Application.spec.destination.namespace` still needs a value for namespaced resources if they do not explicitly set `metadata.namespace`.

For a namespace onboarding application, all namespaced resources such as `ResourceQuota`, `LimitRange`, `RoleBinding`, and `NetworkPolicy` should explicitly include `metadata.namespace`. The destination namespace is less important for the Namespace object itself, but it should be set consistently.

## 6. Pattern 2: Application Uses `CreateNamespace=true`

Argo CD supports a sync option called `CreateNamespace=true`. This allows Argo CD to create the namespace specified in:

```yaml
spec.destination.namespace
```

if that namespace does not already exist.

### 6.1 Example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-api-dev
  namespace: openshift-gitops
spec:
  project: payments
  source:
    repoURL: https://git.example.com/payments/payments-api.git
    targetRevision: main
    path: deploy/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

With this option, if `payments-dev` does not exist, Argo CD tries to create it.

### 6.2 Important behavior

`CreateNamespace=true` creates only the namespace defined under `spec.destination.namespace`.

The child manifests must either:

1. omit `metadata.namespace`, so Argo CD applies them into `spec.destination.namespace`, or
2. use the same namespace as `spec.destination.namespace`.

Bad example:

```yaml
spec:
  destination:
    namespace: payments-dev
```

but child manifest says:

```yaml
metadata:
  namespace: wrong-namespace
```

This causes inconsistent deployment behavior and can fail depending on AppProject destination restrictions and Argo CD validation.

### 6.3 When to use `CreateNamespace=true`

Use it for:

- development clusters,
- ephemeral preview environments,
- short-lived namespaces,
- simple app-owned namespaces,
- internal sandbox workflows,
- ApplicationSet-generated environments,
- non-regulated workloads.

Avoid it as the only namespace creation mechanism for heavily governed production namespaces unless you also apply the governance objects immediately.

### 6.4 Limitation

`CreateNamespace=true` creates the namespace, but it does not automatically create a complete OpenShift tenant boundary. It does not, by itself, guarantee:

- quota,
- limit range,
- RBAC,
- network policies,
- image pull secrets,
- monitoring labels,
- backup policy labels,
- team ownership metadata,
- pod security labels,
- compliance labels.

You must manage those separately.

## 7. Pattern 3: `managedNamespaceMetadata`

Argo CD can manage labels and annotations on the destination namespace by using `managedNamespaceMetadata` together with `CreateNamespace=true`.

### 7.1 Example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-api-dev
  namespace: openshift-gitops
spec:
  project: payments
  source:
    repoURL: https://git.example.com/payments/payments-api.git
    targetRevision: main
    path: deploy/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
  syncPolicy:
    managedNamespaceMetadata:
      labels:
        argocd.argoproj.io/managed-by: openshift-gitops
        platform.example.com/team: payments
        platform.example.com/environment: dev
        pod-security.kubernetes.io/enforce: restricted
        pod-security.kubernetes.io/audit: restricted
        pod-security.kubernetes.io/warn: restricted
      annotations:
        openshift.io/display-name: Payments Development
        openshift.io/description: Payments API development namespace
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

### 7.2 Key rule

`managedNamespaceMetadata` only takes effect when `CreateNamespace=true` is enabled.

### 7.3 Precedence warning

If the same Argo CD application also contains a `kind: Namespace` manifest for the same namespace, the explicit Namespace manifest takes precedence over `managedNamespaceMetadata`.

Example conflict:

```yaml
syncPolicy:
  managedNamespaceMetadata:
    annotations:
      owner: app-team
  syncOptions:
    - CreateNamespace=true
```

and the repository also contains:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-dev
  annotations:
    owner: platform-team
```

The explicit Namespace manifest wins. For production, avoid mixing both ownership models in the same application unless you are very clear about precedence.

### 7.4 Existing namespace warning

When adopting an existing namespace that already has labels and annotations, be careful. If a namespace was previously managed with client-side apply or manual operations, changing metadata ownership can remove or overwrite existing metadata unexpectedly.

For mature clusters, prefer an explicit Namespace manifest with Server-Side Apply and a controlled migration plan.

## 8. Pattern 4: ApplicationSet for Namespace Factories

ApplicationSet is useful when you want to create many similar namespaces from a standard template.

Example use cases:

- one namespace per team,
- one namespace per environment,
- one preview namespace per pull request,
- one namespace per cluster,
- one namespace per customer tenant.

### 8.1 Git generator example

```text
platform-gitops/
└── tenants/
    ├── payments-dev/config.yaml
    ├── payments-prod/config.yaml
    ├── orders-dev/config.yaml
    └── orders-prod/config.yaml
```

Each `config.yaml` could contain values like:

```yaml
team: payments
environment: dev
namespace: payments-dev
quotaCpu: "4"
quotaMemory: 8Gi
adminGroup: payments-admins
editGroup: payments-developers
```

### 8.2 ApplicationSet example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: tenant-namespaces
  namespace: openshift-gitops
spec:
  generators:
    - git:
        repoURL: https://git.example.com/platform/platform-gitops.git
        revision: main
        files:
          - path: tenants/*/config.yaml
  template:
    metadata:
      name: '{{namespace}}-bootstrap'
    spec:
      project: platform-admin
      source:
        repoURL: https://git.example.com/platform/platform-gitops.git
        targetRevision: main
        path: templates/namespace
        helm:
          parameters:
            - name: namespace
              value: '{{namespace}}'
            - name: team
              value: '{{team}}'
            - name: environment
              value: '{{environment}}'
            - name: adminGroup
              value: '{{adminGroup}}'
            - name: editGroup
              value: '{{editGroup}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: openshift-gitops
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - ServerSideApply=true
```

This pattern is powerful but must be controlled carefully. A bad generator or broad wildcard can create many namespaces accidentally.

## 9. OpenShift GitOps-Specific Access Model

OpenShift GitOps is Red Hat's supported distribution of Argo CD. In OpenShift, an Argo CD instance must have permission to manage resources in target namespaces.

For the default instance in `openshift-gitops`, a common requirement is labeling the target namespace:

```bash
oc label namespace payments-dev argocd.argoproj.io/managed-by=openshift-gitops
```

Declaratively:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-dev
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

This label tells the OpenShift GitOps Operator that the namespace is managed by the Argo CD instance in the `openshift-gitops` namespace. The operator can then create the needed RoleBindings for the Argo CD control plane components.

### 9.1 Why this label is important

Without proper permissions, Argo CD might show errors such as:

```text
namespaces "payments-dev" is forbidden
```

or:

```text
deployments.apps is forbidden: User "system:serviceaccount:openshift-gitops:..." cannot create resource "deployments" in API group "apps" in the namespace "payments-dev"
```

The namespace may exist, but Argo CD may not have permission to manage resources inside it.

### 9.2 Cluster-scoped vs namespace-scoped Argo CD

There are two broad operational models:

| Model | Description | Namespace creation impact |
|---|---|---|
| Cluster-scoped Argo CD | Argo CD has cluster-wide visibility and can manage cluster-scoped resources if permitted | Can be used for platform namespace onboarding |
| Namespace-scoped Argo CD | Argo CD is limited to specific namespaces | Usually cannot create cluster-scoped `Namespace` objects unless explicitly granted extra permissions |

Namespace creation is a cluster-scoped operation. If your Argo CD instance is namespace-scoped and does not have permission to create namespaces, `CreateNamespace=true` or a `kind: Namespace` manifest will fail.

Check permission:

```bash
oc auth can-i create namespaces \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

For user-defined Argo CD instances, adjust the service account name according to the actual instance.

## 10. AppProject Design for Namespace Creation

An `AppProject` controls which repositories, destinations, and resource kinds an Argo CD application can use. For namespace creation, this is critical.

A risky AppProject:

```yaml
spec:
  sourceRepos:
    - '*'
  destinations:
    - server: '*'
      namespace: '*'
  clusterResourceWhitelist:
    - group: '*'
      kind: '*'
```

This is easy but dangerous. It allows too much.

### 10.1 Safer platform AppProject

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: platform-admin
  namespace: openshift-gitops
spec:
  description: Platform-owned namespace and cluster bootstrap resources
  sourceRepos:
    - https://git.example.com/platform/platform-gitops.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: '*'
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
    - group: rbac.authorization.k8s.io
      kind: ClusterRoleBinding
    - group: rbac.authorization.k8s.io
      kind: ClusterRole
  namespaceResourceWhitelist:
    - group: ''
      kind: ResourceQuota
    - group: ''
      kind: LimitRange
    - group: networking.k8s.io
      kind: NetworkPolicy
    - group: rbac.authorization.k8s.io
      kind: RoleBinding
    - group: ''
      kind: ServiceAccount
    - group: ''
      kind: Secret
    - group: ''
      kind: ConfigMap
```

### 10.2 App team AppProject

Application teams should usually not get permission to create arbitrary namespaces in production.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  description: Payments application deployments
  sourceRepos:
    - https://git.example.com/payments/*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
    - server: https://kubernetes.default.svc
      namespace: payments-test
    - server: https://kubernetes.default.svc
      namespace: payments-prod
  clusterResourceBlacklist:
    - group: ''
      kind: Namespace
    - group: rbac.authorization.k8s.io
      kind: ClusterRole
    - group: rbac.authorization.k8s.io
      kind: ClusterRoleBinding
```

This allows app deployment into approved namespaces but blocks the team from creating or modifying cluster-scoped resources.

## 11. Applications in Any Namespace

Modern Argo CD supports `Application` resources outside the Argo CD control plane namespace. OpenShift GitOps supports this with explicit configuration. This is useful for multitenant environments where each team creates its own `Application` CR in its own namespace.

Important requirements:

1. The Argo CD instance must allow source namespaces.
2. The `AppProject` must allow those source namespaces through `.spec.sourceNamespaces`.
3. The `Application.metadata.namespace` must be one of the allowed namespaces.
4. The application must reference an allowed AppProject.

### 11.1 ArgoCD CR sourceNamespaces example

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: example
  namespace: openshift-gitops
spec:
  sourceNamespaces:
    - payments-gitops
    - orders-gitops
    - app-team-*
```

### 11.2 AppProject sourceNamespaces example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  sourceNamespaces:
    - payments-gitops
  sourceRepos:
    - https://git.example.com/payments/*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
    - server: https://kubernetes.default.svc
      namespace: payments-prod
```

### 11.3 Application in team namespace

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-api-dev
  namespace: payments-gitops
spec:
  project: payments
  source:
    repoURL: https://git.example.com/payments/payments-api.git
    targetRevision: main
    path: deploy/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
```

### 11.4 Common error

```text
error while validating and normalizing app: error getting application's project:
application 'app' in namespace 'dev' is not allowed to use project 'default'
```

This means the `Application` namespace is not allowed to use that `AppProject`, or the Argo CD instance is not configured to watch that source namespace.

## 12. Sync Waves for Namespace Bootstrapping

When a namespace and its governance resources are applied together, order matters. Argo CD sync waves help control ordering.

Recommended wave strategy:

| Wave | Resource | Reason |
|---:|---|---|
| `-20` | Namespace | Must exist first |
| `-15` | OperatorGroup / Subscription if namespace-local operator is required | Operator install before custom resources |
| `-10` | ResourceQuota / LimitRange | Governance before workloads |
| `-8` | ServiceAccount / image pull secret | Required before pods |
| `-7` | RBAC RoleBinding | Team access before handover |
| `-6` | NetworkPolicy | Security baseline before workloads |
| `0` | Application workloads | Deploy after namespace is prepared |

### 12.1 Namespace with sync wave

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-dev
  annotations:
    argocd.argoproj.io/sync-wave: "-20"
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

### 12.2 ResourceQuota with sync wave

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: payments-dev-quota
  namespace: payments-dev
  annotations:
    argocd.argoproj.io/sync-wave: "-10"
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
```

### 12.3 Workload Application depends on namespace bootstrap

For strict sequencing, use app-of-apps:

```text
root-app
├── namespace-bootstrap-app
└── workload-app
```

Then sync namespace bootstrap first. In regulated production, avoid deploying workloads into a namespace until the namespace bootstrap app is Synced and Healthy.

## 13. Recommended Production Architecture

For a serious enterprise OpenShift platform, use separate ownership layers.

```text
Root Argo CD Application
│
├── cluster-config
│   ├── operators
│   ├── cluster-rbac
│   ├── storageclasses
│   └── admission-policies
│
├── namespace-onboarding
│   ├── team-a-dev
│   ├── team-a-prod
│   ├── team-b-dev
│   └── team-b-prod
│
└── application-deployments
    ├── team-a-apps
    └── team-b-apps
```

### 13.1 Why separate namespace and workload apps?

Because namespace creation is a platform responsibility, while application deployment is usually an application team responsibility.

Separate applications give you:

- better RBAC separation,
- safer pruning,
- cleaner ownership,
- easier troubleshooting,
- clearer audit history,
- and better blast-radius control.

### 13.2 Recommended ownership

| Layer | Owner | Git repo | Argo CD project |
|---|---|---|---|
| Cluster bootstrap | Platform team | platform-gitops | platform-admin |
| Namespace onboarding | Platform team + security approval | platform-gitops | platform-admin |
| App deployment | App team | app repo | team-specific project |
| Policy enforcement | Platform/security team | policy repo | platform-admin |

## 14. Complete Production Example

### 14.1 Namespace bootstrap directory

```text
clusters/prod/namespaces/payments-prod/
├── namespace.yaml
├── quota.yaml
├── limitrange.yaml
├── networkpolicy-default-deny.yaml
├── networkpolicy-allow-ingress-from-router.yaml
```

### 14.2 `namespace.yaml`

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  annotations:
    argocd.argoproj.io/sync-wave: "-20"
    openshift.io/display-name: Payments Production
    openshift.io/description: Production namespace for payments workloads
    platform.example.com/owner-email: payments-platform@example.com
```

## 15. Safe Pruning Strategy for Namespaces

Pruning namespaces is dangerous.

If Argo CD prunes a namespace, Kubernetes deletes everything inside it:

- deployments,
- pods,
- services,
- routes,
- secrets,
- PVCs,
- configmaps,
- rolebindings,
- jobs,
- operator-managed resources,
- and possibly application data references.

### 15.1 Avoid automatic namespace deletion in production

For production namespaces, consider disabling prune on the Namespace object:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

This means removing the namespace YAML from Git will not automatically delete the namespace.

### 15.2 Require prune confirmation

Another option:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

This requires manual confirmation before pruning critical resources.

### 15.3 Recommended deletion process

A safe production namespace decommission process should include:

1. business approval,
2. data backup confirmation,
3. PVC/PV review,
4. route/DNS review,
5. external dependency review,
6. final application shutdown,
7. namespace prune approval,
8. post-delete validation.

Never rely on a casual Git deletion for production namespace removal.

## 18. Policy Enforcement

GitOps should not be the only guardrail. Use admission policy to ensure bad namespace manifests cannot enter the cluster.

Possible controls:

- Gatekeeper constraints,
- Kyverno policies,
- Kubernetes ValidatingAdmissionPolicy,
- OpenShift admission plugins,
- CI checks with `kubeconform`, `conftest`, or `oc apply --dry-run=server`.

### 18.1 Example policy requirements

Every production namespace must have:

- `platform.example.com/team`

- `platform.example.com/owner`
- pod security labels
- `ResourceQuota`

## 19. Common Failure Scenarios and Fixes

### 19.1 Namespace does not exist

Error:

```text
namespaces "payments-dev" not found
```

Cause:

- `CreateNamespace=true` is missing,
- namespace bootstrap app has not synced,
- child manifests specify a wrong namespace,
- AppProject does not allow destination namespace.

Fix:

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
```

or create the namespace in a platform bootstrap app.

---

### 19.2 Argo CD cannot create namespace

Error:

```text
namespaces is forbidden: User "system:serviceaccount:openshift-gitops:..." cannot create resource "namespaces"
```

Cause:

- Argo CD instance lacks cluster-scoped permission,
- AppProject blocks `Namespace`,
- namespace-scoped Argo CD instance is being used for cluster-scoped resource creation.

Checks:

```bash
oc auth can-i create namespaces \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller

oc get appproject platform-admin -n openshift-gitops -o yaml
```

Fix:

- Use a cluster-scoped/platform Argo CD instance for namespace onboarding.
- Update AppProject cluster resource whitelist.
- Keep namespace creation in platform-owned GitOps, not team-owned application GitOps.

---

### 19.3 Argo CD can create namespace but cannot deploy into it

Error:

```text
cannot create resource "deployments" in namespace "payments-dev"
```

Cause:

- namespace lacks `argocd.argoproj.io/managed-by=openshift-gitops`,
- OpenShift GitOps Operator did not create RoleBindings,
- wrong Argo CD instance name/namespace in label,
- service account permissions are missing.

Fix:

```bash
oc label namespace payments-dev argocd.argoproj.io/managed-by=openshift-gitops --overwrite
oc get rolebinding -n payments-dev | grep gitops
```

Declarative fix:

```yaml
metadata:
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

---

### 19.4 `managedNamespaceMetadata` does nothing

Cause:

- `CreateNamespace=true` is not enabled,
- an explicit Namespace manifest takes precedence,
- namespace metadata is already managed differently,
- Argo CD version behavior differs from expectation.

Fix:

```yaml
syncPolicy:
  managedNamespaceMetadata:
    labels:
      platform.example.com/team: payments
  syncOptions:
    - CreateNamespace=true
```

If using explicit Namespace YAML, manage labels there instead.

---

### 19.5 Application not allowed to use project

Error:

```text
application 'payments-api-dev' in namespace 'payments-gitops' is not allowed to use project 'payments'
```

Cause:

- Applications in any namespace is not configured,
- ArgoCD CR `sourceNamespaces` does not include the Application namespace,
- AppProject `.spec.sourceNamespaces` does not include the Application namespace,
- Application references the wrong project.

Fix:

```yaml
spec:
  sourceNamespaces:
    - payments-gitops
```

in both the ArgoCD CR and the AppProject where appropriate.

---

### 19.6 Namespace stuck in Terminating

Cause:

- finalizers on resources,
- unavailable APIService,
- operator-managed CRs not deleting,
- PVC/PV cleanup issues,
- custom resource finalizers.

Checks:

```bash
oc get namespace payments-dev -o yaml
oc api-resources --verbs=list --namespaced -o name | xargs -n 1 oc get -n payments-dev --ignore-not-found
oc get apiservice | grep False
```

Fix carefully. Do not blindly remove finalizers in production without understanding what cleanup is being skipped.

---

### 19.7 Namespace deleted by prune

Cause:

- Namespace manifest removed from Git,
- automated prune enabled,
- Namespace object was tracked by Argo CD,
- no prune protection annotation.

Prevention:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

or:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

## 21. Advanced Best Practices

### 21.1 Use separate repos or directories for platform and applications

Avoid letting application teams modify platform namespace YAML directly unless there is strong review control.

Recommended:

```text
platform-gitops      -> namespaces, quotas, RBAC, operators, policies
application-gitops   -> deployments, services, routes, HPAs
```

### 21.2 Use CODEOWNERS

Example:

```text
/clusters/prod/namespaces/ @platform-team @security-team
/clusters/dev/namespaces/  @platform-team
```

### 21.3 Avoid direct user RoleBindings

Prefer groups:

```yaml
subjects:
  - kind: Group
    name: payments-admins
```

Avoid:

```yaml
subjects:
  - kind: User
    name: rakesh
```

Group-based RBAC scales better and integrates with LDAP/OIDC.

### 21.4 Do not use broad wildcards in production AppProjects

Avoid:

```yaml
sourceRepos:
  - '*'
destinations:
  - namespace: '*'
    server: '*'
```

Use explicit repositories and namespaces.

### 21.5 Add namespace deletion protection

For production:

```yaml
argocd.argoproj.io/sync-options: Prune=confirm
```

or:

```yaml
argocd.argoproj.io/sync-options: Prune=false
```

### 21.6 Use Server-Side Apply for platform resources

```yaml
syncOptions:
  - ServerSideApply=true
```

This is especially useful when multiple controllers add metadata to namespaces.

### 21.7 Avoid shared namespace ownership

One namespace should have one clear GitOps owner for platform-level resources. Do not let multiple Argo CD applications own and mutate the same Namespace metadata unless you have a documented ownership model.

### 21.8 Avoid putting app workloads in `openshift-gitops`

The `openshift-gitops` namespace is the control plane namespace for GitOps. Do not deploy regular business applications there.

### 21.9 Use naming standards

Example:

```text
<team>-<app>-<environment>
payments-api-dev
payments-api-test
payments-api-prod
```

or:

```text
<business-unit>-<environment>
payments-dev
payments-prod
```

Keep names under DNS label limits and avoid uppercase or special characters.

### 21.10 Enforce namespace labels

Labels drive:

- cost reports,
- network policy selection,
- monitoring,
- backup automation,
- ownership,
- compliance reporting.

Do not rely only on human-readable descriptions.

## 22. Security Considerations

Namespace creation can become a privilege escalation path.

### 22.1 Risk: application team creates arbitrary namespace

If a team can create namespaces, they may bypass platform controls. They might create a namespace without quota, network policies, pod security labels, or monitoring.

Mitigation:

- restrict `Namespace` creation to platform AppProject,
- block `Namespace` in team AppProjects,
- enforce admission policies,
- require PR approval for namespace onboarding.

### 22.2 Risk: privileged AppProject with sourceNamespaces

If you allow team-controlled `Application` resources to use a privileged AppProject, users may deploy resources beyond their intended permissions.

Mitigation:

- do not allow team namespaces in privileged AppProject `.spec.sourceNamespaces`,
- create user-defined AppProjects with limited destinations,
- avoid granting access to the GitOps control plane namespace,
- avoid wildcard repos and destinations for team projects.

### 22.3 Risk: namespace prune deletes production

Mitigation:

- `Prune=confirm` or `Prune=false` on production Namespace objects,
- separate namespace lifecycle app from workload app,
- require manual decommission workflow,
- backup and PVC review before deletion.

### 22.4 Risk: metadata drift

Many operators and OpenShift components add labels/annotations to namespaces. If GitOps is too aggressive, it may remove important metadata.

Mitigation:

- use Server-Side Apply,
- do not overwrite unknown annotations blindly,
- avoid replacing Namespace objects,
- use controlled patches.

## 24. Recommended Decision Matrix

| Requirement | Recommended approach |
|---|---|
| Production namespace | Explicit Namespace manifest in platform GitOps repo |
| Dev sandbox namespace | `CreateNamespace=true` acceptable |
| Preview environment per PR | ApplicationSet + `CreateNamespace=true` |
| Strict RBAC/quota/network policy | Platform namespace bootstrap app |
| Multi-tenant team-owned Application CRs | Applications in any namespace + restricted AppProjects |
| Namespace metadata only | `managedNamespaceMetadata` with `CreateNamespace=true` |
| Existing namespace adoption | Explicit manifest + careful Server-Side Apply migration |
| Prevent accidental deletion | `Prune=confirm` or `Prune=false` |
| Team app deployment only | Team AppProject with fixed destinations; blacklist Namespace |

## 25. Interview / Real-World Explanation

A strong senior-level answer:

> In OpenShift GitOps, namespace creation should be handled as part of platform onboarding. I normally keep namespace creation in a platform GitOps repository and deploy it through a privileged Argo CD AppProject. The namespace manifest includes the OpenShift GitOps managed-by label, ownership labels, pod security labels, quotas, limit ranges, default network policies, service accounts, and RoleBindings. For simple dev or preview environments, I may allow `CreateNamespace=true`, but for production I avoid letting app teams create namespaces implicitly. I also protect production namespaces from accidental prune using `Prune=confirm` or `Prune=false`. App teams deploy into pre-approved namespaces through restricted AppProjects that limit source repositories, destination namespaces, and cluster-scoped resources.

## 26. Exam-Oriented Notes

For OpenShift administration and GitOps troubleshooting, remember:

1. `CreateNamespace=true` creates `spec.destination.namespace` only.
2. `managedNamespaceMetadata` requires `CreateNamespace=true`.
3. Existing namespace permissions in OpenShift GitOps often require:

   ```bash
   oc label namespace <target_namespace> argocd.argoproj.io/managed-by=<argocd_namespace>
   ```

4. Namespace creation is cluster-scoped; not every Argo CD instance can do it.
5. AppProject can block Namespace creation even if the service account has RBAC.
6. Child manifests should not point to a different namespace than `spec.destination.namespace` unless intentionally allowed.
7. Pruning namespaces is dangerous.
8. For production, namespace bootstrap should include quota, limit range, network policy, and RBAC.

## 28. Final Best Practice

For advanced OpenShift administration, do not think of namespace GitOps as:

```yaml
kind: Namespace
metadata:
  name: app-dev
```

Think of it as:

```text
Namespace = tenant boundary + security baseline + quota + RBAC + network policy + ownership + lifecycle control
```

The safest production model is:

```text
Platform GitOps creates and governs namespaces.
Application GitOps deploys workloads into approved namespaces.
AppProject and RBAC enforce the boundary.
Prune protection prevents accidental namespace deletion.
```

That is the operational difference between basic Argo CD usage and production-grade OpenShift GitOps administration.
