## 1. What Sync Policy Means in GitOps

In OpenShift GitOps, Argo CD continuously compares two states:

- **Desired state:** YAML, Helm chart output, or Kustomize-rendered manifests stored in Git.
- **Live state:** Actual Kubernetes/OpenShift resources running in the cluster.

A **sync** is the operation that makes the live state match the desired state.

A **sync policy** defines **when** and **how** Argo CD should perform that operation.

At a high level:

| Area | Meaning |
|---|---|
| Manual sync | Administrator or pipeline triggers sync manually. |
| Automated sync | Argo CD syncs automatically when it detects Git/live drift. |
| Prune | Argo CD deletes live resources that are no longer in Git. |
| Self-heal | Argo CD reverts unauthorized/manual live changes back to Git. |
| Retry | Argo CD retries failed syncs using backoff. |
| Sync options | Advanced behavior such as namespace creation, server-side apply, prune order, dry-run behavior, and validation behavior. |

For a senior OpenShift administrator, sync policy is not just a checkbox in the Argo CD UI. It is a **control plane behavior decision** that affects:

- Production stability
- Change-control compliance
- Drift management
- Disaster recovery
- Operator-managed resources
- Namespace lifecycle
- API server pressure
- Multi-team ownership boundaries
- Rollback and incident response

A poorly designed sync policy can delete namespaces, fight with Operators, overwrite emergency hotfixes, or leave abandoned resources behind. A good sync policy gives you predictable, auditable, Git-driven operations.

## 2. Where Sync Policy Lives

Sync policy is configured inside the Argo CD `Application` custom resource.

Basic structure:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/apps.git
    targetRevision: main
    path: apps/my-app/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: my-app-prod
  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
      allowEmpty: false
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
    syncOptions:
      - CreateNamespace=true
      - PruneLast=true
      - ApplyOutOfSyncOnly=true
```

The important part is:

```yaml
spec:
  syncPolicy:
```

Under `syncPolicy`, you normally work with three major sections:

```yaml
syncPolicy:
  automated: {}
  retry: {}
  syncOptions: []
```

| Field | Purpose |
|---|---|
| `automated` | Enables and controls auto-sync behavior. |
| `retry` | Controls retries after sync failure. |
| `syncOptions` | Modifies low-level sync behavior. |
| `managedNamespaceMetadata` | Applies labels/annotations to destination namespace when `CreateNamespace=true` is used. |

## 3. OpenShift GitOps Context

Red Hat OpenShift GitOps packages Argo CD as an Operator-managed service on OpenShift.

Typical default installation components:

```bash
oc get pods -n openshift-gitops
```

Common components include:

| Component | Purpose |
|---|---|
| `openshift-gitops-server` | Argo CD API/UI server. |
| `openshift-gitops-application-controller` | Reconciles Applications and executes sync operations. |
| `openshift-gitops-repo-server` | Generates manifests from Git, Helm, and Kustomize. |
| `openshift-gitops-redis` | Caching/state support. |
| `openshift-gitops-dex-server` | Identity/OIDC integration, depending on configuration. |
| `openshift-gitops-applicationset-controller` | Generates Applications from ApplicationSets. |

The component most relevant to sync policy is the **application controller**.

When you define a sync policy, you are effectively instructing the application controller how aggressively it should reconcile live state to Git.

Important OpenShift-specific points:

- Argo CD itself runs as pods inside OpenShift.
- Application CRs usually live in the Argo CD control namespace, commonly `openshift-gitops`.
- Target application resources may live in other namespaces.
- OpenShift RBAC determines what the Argo CD controller can create, update, delete, or watch.
- OpenShift security controls such as SCC, namespace labels, NetworkPolicy, admission controllers, and Operators can influence sync success.
- Some OpenShift resources are cluster-scoped, for example `ClusterRole`, `ClusterRoleBinding`, `CustomResourceDefinition`, `SecurityContextConstraints`, `MachineConfig`, and Operator lifecycle resources.

Senior-admin mindset:

> Sync policy is not only an Argo CD setting. It must be aligned with OpenShift RBAC, namespace boundaries, Operator ownership, and production change governance.

## 4. Manual Sync Policy

Manual sync is the default behavior when no automated sync policy is configured.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-prod
  namespace: openshift-gitops
spec:
  project: prod
  source:
    repoURL: https://git.example.com/apps/frontend.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: frontend-prod
```

There is no `syncPolicy.automated` section. Argo CD will detect differences and mark the application as `OutOfSync`, but it will not automatically apply changes.

### 4.1 When Manual Sync Is Useful

Manual sync is useful when:

- Production requires approval before deployment.
- You want Argo CD to show drift but not fix it automatically.
- You are onboarding a new application into GitOps.
- You are testing manifests before enabling automation.
- The application includes risky resources such as namespaces, CRDs, cluster roles, storage, or shared services.
- A team is not yet mature enough for full auto-sync.

### 4.2 Manual Sync Commands

Using Argo CD CLI:

```bash
argocd app sync frontend-prod
```

With pruning:

```bash
argocd app sync frontend-prod --prune
```

With dry-run preview:

```bash
argocd app diff frontend-prod
```

Using `oc` to inspect the Application:

```bash
oc get application frontend-prod -n openshift-gitops
oc describe application frontend-prod -n openshift-gitops
```

### 4.3 Manual Sync Risk

Manual sync sounds safer, but it can create problems:

- Teams forget to sync after Git changes.
- Drift remains in the cluster for a long time.
- Emergency manual changes become permanent.
- Configuration in Git no longer represents reality.
- Pipelines may need credentials to call Argo CD directly.

Manual sync gives control, but weakens the GitOps principle of continuous reconciliation.

## 5. Automated Sync Policy

Automated sync tells Argo CD to sync automatically when it detects that the application is `OutOfSync`.

Minimal automated sync:

```yaml
syncPolicy:
  automated: {}
```

Explicit modern form:

```yaml
syncPolicy:
  automated:
    enabled: true
```

CLI:

```bash
argocd app set frontend-prod --sync-policy automated
```

### 5.1 What Automated Sync Does

Automated sync applies Git changes to the cluster without a human clicking `SYNC`.

Typical flow:

1. Developer/platform engineer updates manifests in Git.
2. Git commit is pushed to the tracked branch or tag.
3. Argo CD detects that desired state changed.
4. Application becomes `OutOfSync`.
5. Argo CD application controller syncs resources automatically.
6. Application becomes `Synced` if live state now matches Git.

### 5.2 Why Automated Sync Is Important

Automated sync is the heart of GitOps because CI/CD pipelines do not need direct cluster access.

Instead of this risky model:

```text
CI pipeline -> logs in to OpenShift -> runs oc apply
```

You use this safer model:

```text
CI pipeline -> builds image -> updates Git manifest -> Argo CD reconciles cluster
```

Benefits:

- Reduced need for CI systems to hold OpenShift admin credentials.
- Better audit trail through Git commits.
- Consistent deployment flow across clusters.
- Faster recovery from drift.
- Easier multi-cluster deployment using ApplicationSet.

### 5.3 Automated Sync Is Not Always Full Automation

Automated sync by itself does **not** necessarily mean:

- Deleted Git resources are deleted from the cluster.
- Manual live changes are reverted.
- Failed syncs are retried forever.
- The namespace is created automatically.
- CRDs and CRs always sync in correct order.
- Sync is safe for all resource types.

Those behaviors require additional fields and options.

## 6. Automated Sync Fields

The main automated sync fields are:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
```

| Field | Default Behavior | Meaning |
|---|---|---|
| `enabled` | Enabled if `automated` is present or null depending on version semantics | Explicitly turns auto-sync on or off. |
| `prune` | `false` | Deletes live resources removed from Git during auto-sync. |
| `selfHeal` | `false` | Reverts live cluster drift even when Git has not changed. |
| `allowEmpty` | `false` | Allows auto-sync with prune to delete all application resources when Git renders zero resources. |

---

### 6.1 `enabled`

Example:

```yaml
syncPolicy:
  automated:
    enabled: true
```

`enabled: true` explicitly enables automated sync.

Example disabled but with fields staged:

```yaml
syncPolicy:
  automated:
    enabled: false
    prune: true
    selfHeal: true
    allowEmpty: false
```

This pattern is useful when you want to store the intended production policy in Git but keep auto-sync disabled until a change window.

For example:

```bash
oc patch application frontend-prod -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":true}}}}'
```

Then later:

```bash
oc patch application frontend-prod -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":false}}}}'
```

Senior admin note:

> In production, explicit is better than implicit. Use `enabled: true` or `enabled: false` instead of relying only on `automated: {}` semantics.

---

### 6.2 `prune`

Example:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
```

`prune: true` allows Argo CD to delete resources from the cluster when they are removed from Git.

Without prune:

```text
Resource deleted from Git -> live resource remains in cluster -> app may show OutOfSync
```

With prune:

```text
Resource deleted from Git -> Argo CD deletes live resource during sync
```

CLI:

```bash
argocd app set frontend-prod --auto-prune
```

#### Example Scenario

Git previously contained:

```yaml
kind: ConfigMap
metadata:
  name: old-feature-config
```

You delete it from Git.

If `prune: false`, the ConfigMap remains in OpenShift.

If `prune: true`, Argo CD deletes it.

#### Production Warning

Prune can delete:

- Deployments
- Services
- Routes
- ConfigMaps
- Secrets
- PVCs if managed by the application
- Namespaces if namespace ownership/tracking is configured incorrectly
- Cluster-scoped resources if managed by the app

For production, combine pruning with:

- Pull request review
- AppProject restrictions
- Resource-level `Prune=confirm` for dangerous resources
- `PruneLast=true`
- Separate apps for shared resources
- Clear ownership labels

---

### 6.3 `selfHeal`

Example:

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
```

`selfHeal: true` tells Argo CD to sync when the live cluster drifts from Git, even if Git has not changed.

Example:

```bash
oc scale deployment frontend -n frontend-prod --replicas=5
```

Git says:

```yaml
spec:
  replicas: 3
```

With `selfHeal: true`, Argo CD detects the drift and restores replicas to `3`.

With `selfHeal: false`, Argo CD detects drift and shows `OutOfSync`, but does not automatically fix it unless another auto-sync is triggered by a Git change or a manual sync is run.

#### Why Self-Heal Matters

Self-heal protects against:

- Manual hotfixes that were not committed to Git
- Accidental `oc edit`
- Unauthorized changes
- Configuration drift after incidents
- Changes made by scripts or pipelines bypassing GitOps

#### Self-Heal Risk

Self-heal can also fight legitimate controllers.

Examples:

| Resource | Possible Conflict |
|---|---|
| `Deployment.spec.replicas` | HPA changes replicas; Argo CD changes them back. |
| Operator-managed CRs | Operator mutates defaults/status/spec fields. |
| ServiceAccount tokens/secrets | Kubernetes controllers inject fields. |
| Routes | Router/admission may add annotations/status. |
| Stateful workloads | Storage controllers may modify PVC-related fields. |

The solution is usually to configure `ignoreDifferences`, use `RespectIgnoreDifferences=true`, or avoid managing fields that another controller owns.

---

### 6.4 `allowEmpty`

Example:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    allowEmpty: true
```

By default, Argo CD protects you from accidentally deleting everything when Git renders zero manifests.

A zero-resource render can happen due to:

- Wrong Git path
- Broken Kustomize overlay
- Helm values disabling all templates
- Branch accidentally emptied
- Generator failure
- Incorrect ApplicationSet parameters

Without `allowEmpty: true`, automated prune will not delete all resources just because the desired state is empty.

Use `allowEmpty: true` only when an empty desired state is intentional.

Good use cases:

- Ephemeral preview environments
- Temporary labs
- ApplicationSet-generated environments that are intentionally destroyed by removing Git entries
- Controlled decommission workflows

Bad use cases:

- Shared production namespace
- Cluster configuration application
- Operator lifecycle application
- Storage/PVC-heavy application
- Any app where a wrong Git path could wipe production resources

Senior admin recommendation:

```yaml
allowEmpty: false
```

Keep it false unless you have a strong decommission automation requirement.

---

### 6.5 Recommended Automated Sync Combination

Common production-safe starting point:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
  syncOptions:
    - PruneLast=true
    - ApplyOutOfSyncOnly=true
```

This means:

- Auto-apply Git changes.
- Remove resources deleted from Git.
- Correct live drift.
- Do not delete everything if Git renders empty.
- Prune only after other resources are healthy.
- Reduce API load by applying only out-of-sync objects.

Use additional safety for critical resources:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

## 7. Retry Policy

A sync can fail because of temporary conditions:

- Webhook temporarily unavailable
- API server pressure
- CRD not established yet
- Operator not ready yet
- Namespace admission delay
- Image pull secret not yet created
- Resource quota timing issue
- Network glitch between controller and API server

The retry policy controls automatic retry behavior after sync failure.

Example:

```yaml
syncPolicy:
  retry:
    limit: 5
    backoff:
      duration: 5s
      factor: 2
      maxDuration: 3m
```

| Field | Meaning |
|---|---|
| `limit` | Number of retry attempts. Use `-1` for unlimited retries. |
| `backoff.duration` | Initial wait before retry. |
| `backoff.factor` | Multiplier after each failure. |
| `backoff.maxDuration` | Maximum wait between retries. |

With the example above, retry waits roughly:

```text
5s -> 10s -> 20s -> 40s -> 80s
```

Bounded by `maxDuration`.

### 7.1 Retry with Refresh

Some Argo CD versions support refresh during sync retry:

```yaml
syncPolicy:
  retry:
    refresh: true
```

This allows Argo CD to refresh when a new revision appears while the current sync is retrying.

CLI equivalent:

```bash
argocd app set frontend-prod --sync-retry-refresh
```

### 7.2 Retry Is Not a Replacement for Correct Ordering

Do not use retry to hide broken design.

Bad pattern:

```text
CR applied before CRD -> sync fails -> retry eventually works
```

Better pattern:

- Put CRDs in an earlier sync wave.
- Put Operators in separate bootstrap applications.
- Use health checks and sync waves.
- Use `SkipDryRunOnMissingResource=true` only where appropriate.

### 7.3 Unlimited Retry Warning

```yaml
retry:
  limit: -1
```

Use unlimited retries carefully.

It can be useful for:

- Edge clusters with intermittent connectivity
- Remote clusters that frequently restart
- Short-lived admission webhook outages

It is risky when:

- The manifest is invalid
- RBAC is wrong
- Quota prevents creation
- Operator CR is rejected forever
- Destination namespace is wrong

In those cases, unlimited retry creates noise and repeated API traffic.

## 8. Sync Options

`syncOptions` modify low-level sync behavior.

They can be configured at the Application level:

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
    - PruneLast=true
```

Or as a resource annotation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false,Validate=false
```

Resource-level sync options are useful when one resource needs special behavior without changing the entire Application.

---

### 8.1 `CreateNamespace=true`

Application-level example:

```yaml
spec:
  destination:
    server: https://kubernetes.default.svc
    namespace: backend-prod
  syncPolicy:
    syncOptions:
      - CreateNamespace=true
```

This tells Argo CD to create the destination namespace if it does not exist.

Without it, the sync fails if the namespace is missing.

Important rules:

- The namespace must be specified in `spec.destination.namespace`.
- Child manifests should either omit `metadata.namespace` or match the destination namespace.
- Do not mix namespace ownership across multiple Applications.

OpenShift note:

In OpenShift GitOps, the Argo CD instance must also have permission to manage the target namespace. In many default shared-instance workflows, target namespaces are labeled so the Argo CD instance in `openshift-gitops` can manage them:

```bash
oc label namespace backend-prod argocd.argoproj.io/managed-by=openshift-gitops
```

If the namespace does not exist and Argo CD is expected to create it, verify your OpenShift GitOps instance configuration and AppProject permissions allow namespace creation/management.

---

### 8.2 `managedNamespaceMetadata`

Used with `CreateNamespace=true`.

Example:

```yaml
syncPolicy:
  managedNamespaceMetadata:
    labels:
      argocd.argoproj.io/managed-by: openshift-gitops
      app.kubernetes.io/part-of: banking-platform
      environment: prod
    annotations:
      owner: platform-team
      cost-center: cc-1001
  syncOptions:
    - CreateNamespace=true
```

This lets Argo CD add labels and annotations to the destination namespace.

Important production warning:

If your Git repository also contains a `Namespace` manifest for the same namespace, that manifest can take precedence over `managedNamespaceMetadata`. Avoid managing the same namespace metadata in two places.

Recommended pattern:

- Platform/bootstrap app owns namespace creation and metadata.
- Workload app deploys namespaced resources only.

---

### 8.3 `Prune=false`

Resource-level example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

This prevents the resource from being pruned even if it is removed from Git.

Use for:

- PVCs
- Long-lived Secrets
- Migration ConfigMaps
- Emergency break-glass resources
- Resources that must survive app decommissioning

But avoid overusing it. Too many `Prune=false` resources create unmanaged drift.

---

### 8.4 `Prune=confirm`

Example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payment-prod
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

This requires manual confirmation before pruning.

Use for critical resources:

- Namespaces
- PVCs
- CRDs
- ClusterRoles
- ClusterRoleBindings
- Shared ConfigMaps
- Shared Secrets
- Operator subscriptions

Manual approval can be done from UI, CLI, or by adding the deletion-approved annotation on the Application:

```bash
oc annotate application payment-prod -n openshift-gitops \
  argocd.argoproj.io/deletion-approved="$(date -Iseconds)" --overwrite
```

---

### 8.5 `Delete=false`

`Delete=false` prevents a resource from being deleted when the Application itself is deleted.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: database-data
  annotations:
    argocd.argoproj.io/sync-options: Delete=false
```

Difference between prune and delete:

| Option | When It Applies |
|---|---|
| `Prune=false` | Resource removed from Git during sync. |
| `Delete=false` | Application is deleted and Argo CD cascades cleanup. |

Use `Delete=false` for data-retention resources.

---

### 8.6 `Delete=confirm`

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Delete=confirm
```

This requires approval before the resource is deleted during Application deletion.

Use for:

- Namespaces
- PVCs
- Persistent data
- Cluster-scoped resources
- Production shared services

---

### 8.7 `Validate=false`

Example:

```yaml
syncPolicy:
  syncOptions:
    - Validate=false
```

Or resource-level:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Validate=false
```

This is equivalent to applying with validation disabled.

Use only when needed, such as:

- Some CRDs or resources with raw extension fields
- Partial manifests with server-side apply
- Special Operator resources that fail client validation but are accepted by the API server

Avoid globally disabling validation unless required.

---

### 8.8 `SkipDryRunOnMissingResource=true`

Example:

```yaml
syncPolicy:
  syncOptions:
    - SkipDryRunOnMissingResource=true
```

Use when Argo CD sees a custom resource before its CRD is known.

Common OpenShift/Operator examples:

- Installing an Operator and applying its custom resource in the same delivery flow
- Gatekeeper/Kyverno-like controllers that dynamically create CRDs
- ServiceMesh/Serverless/Pipelines custom resources where CRDs may appear after Operator installation

Better design:

- Bootstrap CRDs/Operators first.
- Wait until CRDs are established.
- Sync custom resources afterward.

Example check:

```bash
oc get crd | grep example
oc get csv -n openshift-operators
oc get subscription -A
```

---

### 8.9 `ApplyOutOfSyncOnly=true`

Example:

```yaml
syncPolicy:
  syncOptions:
    - ApplyOutOfSyncOnly=true
```

Default sync behavior applies every object in the application.

For large applications with hundreds or thousands of resources, this can:

- Increase API server load
- Increase etcd writes
- Grow Application operation history fields
- Slow down syncs

`ApplyOutOfSyncOnly=true` applies only objects that are actually out of sync.

Good for:

- Large platform apps
- Cluster configuration repos
- Multi-namespace apps
- Applications with many ConfigMaps/Secrets/Policies

Caution:

- Make sure hooks and health checks still behave as expected.
- Do not use it to hide bad diff configuration.

---

### 8.10 `PrunePropagationPolicy`

Example:

```yaml
syncPolicy:
  syncOptions:
    - PrunePropagationPolicy=foreground
```

Supported values:

```text
foreground
background
orphan
```

| Policy | Behavior |
|---|---|
| `foreground` | Kubernetes waits for dependents to be deleted before deleting owner. Common default. |
| `background` | Owner is deleted immediately; dependents are cleaned in background. |
| `orphan` | Dependents are left behind. |

Use cases:

- `foreground`: safest for most applications.
- `background`: faster cleanup where dependent resources are not critical.
- `orphan`: intentionally keep children after parent removal; rare and should be documented.

OpenShift production recommendation:

```yaml
- PrunePropagationPolicy=foreground
```

Use `orphan` only with explicit operational justification.

---

### 8.11 `PruneLast=true`

Example:

```yaml
syncPolicy:
  syncOptions:
    - PruneLast=true
```

This makes pruning happen as the final implicit wave after other resources are deployed and healthy.

Why this matters:

Suppose you rename a Service or Route:

```text
old-service -> new-service
```

Without `PruneLast=true`, Argo CD may delete the old resource too early.

With `PruneLast=true`, Argo CD first creates/updates the new resources, waits for health where applicable, and then prunes old resources.

Good for:

- Production rollouts
- Route/Service migration
- Blue-green-like object replacement
- CRD or Operator transitions
- Shared dependency changes

Recommended in most production applications:

```yaml
- PruneLast=true
```

---

### 8.12 `Replace=true`

Example:

```yaml
syncPolicy:
  syncOptions:
    - Replace=true
```

Or resource-level:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Replace=true
```

By default, Argo CD uses apply semantics. `Replace=true` changes behavior to `kubectl replace` or `kubectl create`.

Use when:

- The resource is too large for client-side apply annotation limits.
- Apply cannot handle immutable field changes.
- You intentionally want replace behavior.

Warning:

`Replace=true` can be disruptive. Some resources may be recreated or experience outage.

Avoid applying it globally unless you know exactly why.

---

### 8.13 `Force=true`

Example:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    argocd.argoproj.io/sync-options: Force=true,Replace=true
```

`Force=true` deletes and recreates the resource.

Common use case:

- Kubernetes Job that must run every sync.

Warning:

This is destructive. Use resource-level only.

Do **not** globally force-sync Deployments, StatefulSets, Routes, Services, PVCs, or Operators unless you are intentionally accepting downtime/risk.

---

### 8.14 `ServerSideApply=true`

Example:

```yaml
syncPolicy:
  syncOptions:
    - ServerSideApply=true
```

Server-side apply uses Kubernetes field management instead of relying on the large `kubectl.kubernetes.io/last-applied-configuration` annotation.

Good use cases:

- Large CRDs/resources exceeding annotation size limits
- Partial manifests
- Co-management of fields by different controllers
- Transition from imperative/manual resources to GitOps

Example partial manifest with server-side apply:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 3
```

Because this is not a full valid Deployment manifest, you may need:

```yaml
syncPolicy:
  syncOptions:
    - ServerSideApply=true
    - Validate=false
```

Important:

- `Replace=true` takes precedence over `ServerSideApply=true`.
- Server-side apply can cause field ownership conflicts.
- Operators may own fields; understand `managedFields` before forcing ownership.

Inspect managed fields:

```bash
oc get deployment frontend -n frontend-prod -o yaml | less
```

Search for:

```yaml
managedFields:
```

---

### 8.15 `ClientSideApplyMigration=false`

Example:

```yaml
syncPolicy:
  syncOptions:
    - ClientSideApplyMigration=false
```

Argo CD can help migrate resources from client-side apply to server-side apply. In some environments, you may want to disable this migration.

Use with caution and only after testing.

---

### 8.16 `FailOnSharedResource=true`

Example:

```yaml
syncPolicy:
  syncOptions:
    - FailOnSharedResource=true
```

This fails the sync if the current Application tries to manage a resource already managed by another Application.

This is very important in large OpenShift environments.

Problem scenario:

```text
Application A manages namespace team-a
Application B also contains namespace team-a
```

Without protection, two Applications may fight over ownership.

With `FailOnSharedResource=true`, Argo CD stops the sync and exposes the ownership problem.

Recommended for:

- Multi-team clusters
- Shared platform GitOps instances
- Production namespaces
- Cluster configuration repositories
- App-of-apps models

---

### 8.17 `RespectIgnoreDifferences=true`

Example:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

By default, `ignoreDifferences` affects diff calculation. `RespectIgnoreDifferences=true` makes Argo CD also respect ignored fields during sync.

Important for OpenShift:

- HPA changes `spec.replicas`.
- Operators default/mutate fields.
- Webhooks inject values.
- Service mesh sidecar injection changes pod specs.
- Build/DeploymentConfig controllers may mutate fields.

Example for HPA-managed replicas:

```yaml
ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
      - /spec/replicas
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
  syncOptions:
    - RespectIgnoreDifferences=true
```

Without this, self-heal can fight autoscaling.

## 9. Sync Policy, Health, and Diff Are Different Things

A senior admin must understand three separate concepts:

| Concept | Meaning |
|---|---|
| Sync status | Does live state match Git desired state? |
| Health status | Are the resources operational/healthy? |
| Operation status | Did the last sync operation succeed or fail? |

Example:

```text
Application: Synced
Health: Degraded
```

This means Argo CD successfully applied the desired manifests, but the app is not healthy.

Possible causes:

- Pod image pull failure
- CrashLoopBackOff
- Readiness probe failure
- PVC pending
- Route admitted=false
- Deployment unavailable
- Operator CR degraded

Commands:

```bash
argocd app get frontend-prod
oc describe application frontend-prod -n openshift-gitops
oc get pods -n frontend-prod
oc describe pod <pod> -n frontend-prod
oc get events -n frontend-prod --sort-by=.lastTimestamp
```

Do not assume `Synced` means the workload is running correctly.

## 10. OpenShift-Specific Sync Policy Design

OpenShift adds platform concerns that are less visible in generic Kubernetes.

### 10.1 SecurityContextConstraints

If your application needs non-default privileges, sync may fail or pods may not start.

Example symptom:

```text
Error creating: pods "x" is forbidden: unable to validate against any security context constraint
```

GitOps-safe approach:

- Avoid privileged workloads where possible.
- Use proper ServiceAccount.
- Bind SCC through Git if allowed by platform policy.
- Put SCC bindings in a platform/security Application, not in the app team repo, unless delegated.

Example SCC binding command:

```bash
oc adm policy add-scc-to-user anyuid -z my-sa -n my-namespace
```

Declarative RoleBinding/SCC management should be carefully controlled because SCC is security-sensitive.

### 10.2 Routes

OpenShift Routes may receive status and annotations from the router/admission controllers.

Do not manage status fields. If admission/defaulting creates persistent diffs, configure ignore differences for safe fields.

### 10.3 ImageStreams and Builds

If GitOps manages ImageStreams while OpenShift Builds or external automation updates image tags, decide ownership carefully.

Patterns:

- Git owns Deployment image tag only.
- Image automation commits new tag to Git.
- Avoid live `oc set image` in production.
- Ignore fields only when there is a clear reason.

### 10.4 Operators

Operators often mutate custom resources.

Examples:

- They add defaults.
- They change status.
- They reconcile generated resources.
- They reject invalid state transitions.

Do not fight Operators with aggressive self-heal unless you understand the CR ownership model.

### 10.5 Cluster-Scoped Resources

Cluster-scoped resources are dangerous with auto-prune:

- `Namespace`
- `ClusterRole`
- `ClusterRoleBinding`
- `CustomResourceDefinition`
- `SecurityContextConstraints`
- `MachineConfig`
- `MachineConfigPool`
- `OperatorGroup`
- `Subscription`

Use dedicated platform Applications and restrictive AppProjects.

## 11. Namespaces and OpenShift GitOps Management

In OpenShift, namespace/project management is central to safe GitOps.

### 11.1 Namespace Created Outside Argo CD

Create namespace:

```bash
oc new-project frontend-prod
```

Allow default OpenShift GitOps instance to manage it:

```bash
oc label namespace frontend-prod argocd.argoproj.io/managed-by=openshift-gitops
```

Then Application destination:

```yaml
destination:
  server: https://kubernetes.default.svc
  namespace: frontend-prod
```

### 11.2 Namespace Created by Argo CD

Application:

```yaml
spec:
  destination:
    server: https://kubernetes.default.svc
    namespace: frontend-prod
  syncPolicy:
    managedNamespaceMetadata:
      labels:
        argocd.argoproj.io/managed-by: openshift-gitops
        environment: prod
    syncOptions:
      - CreateNamespace=true
```

Make sure:

- Argo CD has RBAC to create namespaces/projects.
- AppProject permits the destination namespace or pattern.
- Namespace ownership is not shared across multiple apps.
- You understand deletion behavior.

### 11.3 Recommended Namespace Pattern

For production:

```text
platform-namespaces app:
  owns Namespace, ResourceQuota, LimitRange, NetworkPolicy baseline, RBAC baseline

workload app:
  owns Deployment, Service, Route, ConfigMap, Secret references, HPA
```

This avoids workload app deletion accidentally deleting the whole namespace.

## 12. CRDs, Operators, and Sync Policy

OpenShift heavily uses Operators. Sync policy must account for CRD lifecycle.

### 12.1 Bad Pattern

Single Application contains:

```text
Subscription
OperatorGroup
CustomResourceDefinition
CustomResource
Operand resources
```

Auto-sync applies everything at once. CR may fail because CRD is not available yet or Operator is not ready.

### 12.2 Better Pattern

Split into Applications:

```text
01-operator-subscription
02-operator-instance
03-workloads-that-depend-on-operator
```

Or use sync waves:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

For Operator subscription:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

For custom resource:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

For workloads:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "20"
```

### 12.3 CRD Dry Run Problem

If a custom resource is rendered before the CRD exists, dry-run can fail.

Possible option:

```yaml
syncPolicy:
  syncOptions:
    - SkipDryRunOnMissingResource=true
```

But use it carefully. It should not replace correct Operator readiness handling.

### 12.4 Operator Health

Argo CD may not know custom health for every Operator CR.

Symptoms:

```text
Application remains Progressing
Application health Unknown
Application sync succeeded but operand not ready
```

Fixes:

- Add custom health checks in Argo CD configuration if supported by your GitOps version/policy.
- Split Operator installation and operand configuration.
- Use PostSync hooks for smoke checks.
- Verify CSV and Operator status with `oc`.

Commands:

```bash
oc get subscription -A
oc get csv -A
oc describe csv <csv-name> -n <operator-namespace>
oc get pods -n <operator-namespace>
```

## 13. Pruning Strategy in Production

Pruning is powerful and dangerous.

### 13.1 Prune Off

```yaml
automated:
  enabled: true
  prune: false
```

Good during:

- Initial onboarding
- Migration into GitOps
- Audit phase
- Production stabilization

Downside:

- Removed Git resources remain live.
- Cluster accumulates abandoned resources.
- OutOfSync may persist.

### 13.2 Prune On

```yaml
automated:
  enabled: true
  prune: true
```

Good when:

- Git ownership is mature.
- App boundaries are clear.
- PR review is enforced.
- AppProject restricts resource scope.
- Dangerous resources have confirmation.

### 13.3 Safe Production Prune Policy

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
  syncOptions:
    - PruneLast=true
    - PrunePropagationPolicy=foreground
    - FailOnSharedResource=true
```

Resource-level safety:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm,Delete=confirm
```

### 13.4 Resources That Usually Need Prune Protection

| Resource | Recommended Protection |
|---|---|
| Namespace | `Prune=confirm`, sometimes separate owner app. |
| PVC | `Prune=false` or `Delete=false`, depending on retention policy. |
| Secret | Case-by-case. Avoid accidental deletion of credentials. |
| CRD | Usually separate platform app; avoid app-level prune. |
| ClusterRole | Separate platform/security app. |
| Operator Subscription | Confirm before pruning in production. |

## 14. Self-Healing Strategy in Production

Self-healing is desirable when Git must be the absolute source of truth.

### 14.1 Recommended Use

Enable self-heal for:

- Stateless app manifests
- ConfigMaps managed by Git
- Services and Routes
- NetworkPolicies
- RBAC controlled by platform repo
- LimitRanges/ResourceQuotas controlled by platform repo

Example:

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
```

### 14.2 Caution Areas

Be careful with self-heal for:

- HPA-managed replicas
- Operator-mutated CRs
- Resources with defaulting webhooks
- Service mesh injected workloads
- Secrets updated by external secret controllers
- Image tags updated outside Git

### 14.3 HPA Example

Deployment in Git:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 2
```

HPA scales it to 6.

Argo CD with self-heal may try to restore replicas to 2.

Solution:

```yaml
ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
      - /spec/replicas
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
  syncOptions:
    - RespectIgnoreDifferences=true
```

Alternative:

- Remove `replicas` from the Deployment manifest if your tooling permits.
- Let HPA own scaling.
- Manage min/max in the HPA manifest.

## 15. Sync Waves and Hooks with Sync Policy

Sync policy controls when/how sync runs. Sync waves and hooks control ordering inside the sync.

### 15.1 Sync Waves

Annotation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

Lower waves apply first.

Example ordering:

| Wave | Resources |
|---|---|
| `-10` | Namespaces, CRDs |
| `0` | RBAC, ServiceAccounts, Secrets, ConfigMaps |
| `10` | Deployments, StatefulSets |
| `20` | Services, Routes, HPA |
| `30` | Smoke-test Job |

### 15.2 Hooks

Hook examples:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/hook: PreSync
```

Common hook phases:

| Hook | Purpose |
|---|---|
| `PreSync` | Run before normal resources. Good for validation or migration pre-checks. |
| `Sync` | Run during normal sync. |
| `PostSync` | Run after resources are synced and healthy. Good for smoke tests. |
| `SyncFail` | Run when sync fails. Good for cleanup/notification. |
| `PreDelete` | Run before Application deletion. |
| `PostDelete` | Run after Application resources are deleted. |
| `Skip` | Do not apply this manifest. |

### 15.3 Database Migration Job Example

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
    argocd.argoproj.io/sync-options: Force=true,Replace=true
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/payments/migrate:v1.2.3
          command: ["/bin/sh", "-c", "./migrate.sh"]
```

Explanation:

- `PreSync`: migration runs before app rollout.
- `HookSucceeded`: successful hook is cleaned up.
- `Force=true,Replace=true`: Job can run again on next sync.

### 15.4 Important Hook Warning

Selective sync has special behavior around hooks. Do not assume every hook runs in every selective operation. For mission-critical workflows, test your exact sync method.

## 16. ApplicationSet and Sync Policy

ApplicationSet generates multiple Argo CD Applications.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-apps
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - name: frontend-dev
            namespace: frontend-dev
          - name: frontend-prod
            namespace: frontend-prod
  template:
    metadata:
      name: '{{name}}'
    spec:
      project: default
      source:
        repoURL: https://git.example.com/apps/frontend.git
        targetRevision: main
        path: overlays/{{name}}
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{namespace}}'
      syncPolicy:
        automated:
          enabled: true
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
          - PruneLast=true
```

Important:

- For ApplicationSet-managed Applications, edit the ApplicationSet template, not the generated Application.
- If you manually patch a generated Application, the ApplicationSet controller can overwrite it.
- Use different templates or parameters for dev/stage/prod sync behavior.

Example with environment-specific sync:

```yaml
# dev: auto-sync, prune, self-heal
# prod: auto-sync disabled or prune protected
```

ApplicationSet is powerful for multi-cluster OpenShift operations, but it increases blast radius if sync policy is too aggressive.

## 17. App-of-Apps Pattern and Sync Policy

In app-of-apps, a parent Application manages child Application manifests.

Example layout:

```text
gitops-repo/
  bootstrap/
    root-app.yaml
  apps/
    namespaces/
      app.yaml
    operators/
      app.yaml
    monitoring/
      app.yaml
    workloads/
      app.yaml
```

Parent Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: openshift-gitops
spec:
  project: platform
  source:
    repoURL: https://git.example.com/platform/gitops.git
    targetRevision: main
    path: apps
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
    syncOptions:
      - PruneLast=true
      - FailOnSharedResource=true
```

Child Applications define their own sync policies.

Senior admin guidance:

- Root app may auto-sync child Application CRs.
- Child apps should have environment-specific sync policy.
- Be careful with pruning child Applications because deleting a child Application may cascade delete its resources if finalizers are set.
- Use AppProjects to restrict child apps.

## 18. Recommended Sync Policies by Environment

### 18.1 Development

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
  syncOptions:
    - CreateNamespace=true
    - PruneLast=true
```

Reasoning:

- Fast feedback
- Low-risk environment
- Encourages Git-first behavior
- Cleans up removed resources

### 18.2 Test / QA

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
  retry:
    limit: 5
    backoff:
      duration: 10s
      factor: 2
      maxDuration: 3m
  syncOptions:
    - PruneLast=true
    - ApplyOutOfSyncOnly=true
    - FailOnSharedResource=true
```

Reasoning:

- Similar to production behavior
- Safe cleanup
- Detects ownership conflicts early

### 18.3 Production Conservative

```yaml
syncPolicy:
  automated:
    enabled: false
    prune: true
    selfHeal: true
    allowEmpty: false
  syncOptions:
    - PruneLast=true
    - PrunePropagationPolicy=foreground
    - FailOnSharedResource=true
```

Reasoning:

- Policy is defined but auto-sync disabled.
- Admin enables during approved windows.
- Prune/self-heal intention is visible in Git.

### 18.4 Production Mature GitOps

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
  retry:
    limit: 5
    backoff:
      duration: 10s
      factor: 2
      maxDuration: 5m
  syncOptions:
    - PruneLast=true
    - PrunePropagationPolicy=foreground
    - ApplyOutOfSyncOnly=true
    - FailOnSharedResource=true
    - RespectIgnoreDifferences=true
```

Reasoning:

- Git is source of truth.
- Mature review process exists.
- Resource ownership is clear.
- Operator/HPA differences are controlled.

### 18.5 Cluster Bootstrap

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: false
    selfHeal: true
    allowEmpty: false
  retry:
    limit: 10
    backoff:
      duration: 15s
      factor: 2
      maxDuration: 5m
  syncOptions:
    - PruneLast=true
    - SkipDryRunOnMissingResource=true
```

Reasoning:

- Bootstrap often has ordering issues.
- Prune should be introduced only after ownership is clear.
- CRDs/Operators may appear during the process.

```bash
oc annotate application payments-prod -n openshift-gitops \
  argocd.argoproj.io/deletion-approved="$(date -Iseconds)" --overwrite
```

## 21. Troubleshooting Sync Policy Issues

### 21.1 Application Is OutOfSync but Not Syncing

Checklist:

```bash
oc get application <app> -n openshift-gitops -o yaml | yq '.spec.syncPolicy'
```

Check:

- Is `automated.enabled` false?
- Is `automated` missing?
- Is a sync window blocking sync?
- Is the application in error state?
- Did previous auto-sync fail for the same commit?
- Is the generated Application controlled by ApplicationSet?

Commands:

```bash
argocd app get <app>
argocd app history <app>
argocd app diff <app>
```

### 21.2 Live Change Not Reverted

Cause:

```yaml
selfHeal: false
```

Fix:

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
```

But first verify the live change is not owned by HPA/Operator/webhook.

### 21.3 Deleted Git Resource Still Exists

Cause:

```yaml
prune: false
```

or resource annotation:

```yaml
argocd.argoproj.io/sync-options: Prune=false
```

Fix:

```yaml
automated:
  prune: true
```

or run:

```bash
argocd app sync <app> --prune
```

### 21.4 Prune Waiting for Confirmation

Cause:

```yaml
argocd.argoproj.io/sync-options: Prune=confirm
```

Fix:

Approve from UI or annotate Application:

```bash
oc annotate application <app> -n openshift-gitops \
  argocd.argoproj.io/deletion-approved="$(date -Iseconds)" --overwrite
```

### 21.5 Namespace Does Not Exist

Error example:

```text
namespaces "my-app" not found
```

Fix options:

Create namespace manually:

```bash
oc new-project my-app
oc label namespace my-app argocd.argoproj.io/managed-by=openshift-gitops
```

Or enable namespace creation:

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
```

Verify destination:

```yaml
spec:
  destination:
    namespace: my-app
```

### 21.6 Argo CD Cannot Manage Target Namespace

Symptoms:

```text
permission denied
forbidden
cannot create resource
```

Check:

```bash
oc auth can-i create deployment -n target-ns \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Check namespace label:

```bash
oc get ns target-ns --show-labels
```

Add label if appropriate:

```bash
oc label ns target-ns argocd.argoproj.io/managed-by=openshift-gitops --overwrite
```

### 21.7 CRD Missing During Sync

Error:

```text
the server could not find the requested resource
```

Fix options:

- Sync CRD/Operator first.
- Use sync waves.
- Split Application.
- Use `SkipDryRunOnMissingResource=true` where appropriate.

### 21.8 Sync Fails Due to Immutable Field

Example:

```text
field is immutable
```

Options:

- Change resource name.
- Delete/recreate during maintenance.
- Use `Replace=true` cautiously.
- Use `Force=true,Replace=true` only for safe resources like Jobs.

### 21.9 HPA Fighting with Argo CD

Symptoms:

- HPA scales Deployment up.
- Argo CD scales it back down.
- Application constantly OutOfSync.

Fix:

```yaml
ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
      - /spec/replicas
syncPolicy:
  syncOptions:
    - RespectIgnoreDifferences=true
```

### 21.10 ApplicationSet Keeps Reverting Sync Policy

Cause:

You edited generated Application directly.

Fix:

Edit ApplicationSet template:

```bash
oc edit applicationset <name> -n openshift-gitops
```

Then change:

```yaml
spec:
  template:
    spec:
      syncPolicy:
```

### 21.11 Sync Succeeds but Pods Fail

Sync success does not mean workload success.

Check:

```bash
oc get pods -n <namespace>
oc describe pod <pod> -n <namespace>
oc logs <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common OpenShift causes:

- SCC rejection
- ImagePullBackOff
- Missing image pull secret
- ResourceQuota exceeded
- PVC pending
- Route not admitted
- NetworkPolicy blocking traffic
- Probe misconfiguration

## 22. Advanced Failure Scenarios

### 22.1 Sync Policy Accidentally Deletes Production Resources

Likely causes:

- `prune: true`
- wrong Git path
- ApplicationSet generator removed an element
- Kustomize overlay rendered empty
- Helm values disabled all resources
- `allowEmpty: true`
- Application finalizer caused cascading deletion

Immediate response:

```bash
argocd app terminate-op <app>
```

Disable auto-sync:

```bash
oc patch application <app> -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":false}}}}'
```

Check Git commit:

```bash
git log --oneline
```

Restore commit or path, then sync intentionally.

Preventive controls:

- Keep `allowEmpty: false`.
- Use PR approval.
- Use `Prune=confirm` for critical resources.
- Use AppProject allow/deny lists.
- Use separate apps for shared resources.

### 22.2 Operator and Argo CD Fight Over CR Fields

Symptoms:

- App constantly OutOfSync.
- Operator keeps changing fields.
- Argo CD self-heal changes them back.
- Operator reverts again.

Fix:

- Identify mutated fields:

```bash
argocd app diff <app>
oc get <kind> <name> -n <ns> -o yaml
```

- Add `ignoreDifferences` for fields safely owned by Operator.
- Enable `RespectIgnoreDifferences=true` if needed.
- Move Operator-owned generated resources out of Git.

### 22.3 API Server Pressure from Large Apps

Symptoms:

- Syncs are slow.
- API server latency increases.
- Application status objects become huge.
- Controller CPU/memory increases.

Mitigations:

```yaml
syncOptions:
  - ApplyOutOfSyncOnly=true
```

Also:

- Split large Applications.
- Avoid unnecessary generated resources.
- Tune reconciliation interval only with platform-level review.
- Avoid constantly changing generated manifests.

### 22.4 Shared Resource Ownership Conflict

Symptoms:

- Two apps change same ConfigMap/Namespace/ClusterRole.
- Sync alternates between desired states.
- Teams overwrite each other.

Fix:

```yaml
syncOptions:
  - FailOnSharedResource=true
```

Then redesign ownership:

```text
One resource -> one owning Application -> one owning team/repo
```

### 22.5 Auto-Sync Does Not Retry Same Failed Commit

Argo CD automated sync has specific semantics. It does not endlessly retry the exact same failed sync unless retry policy/self-heal/new revision behavior applies.

Operational fixes:

- Fix Git and push a new commit.
- Run manual sync after fixing cluster dependency.
- Configure retry policy for transient failures.
- Use `retry.refresh: true` if new revisions should refresh during retry.

## 23. Security and Governance

### 23.1 Sync Policy Is a Security Boundary

With auto-sync, a Git commit can create, modify, or delete OpenShift resources.

Therefore protect:

- Git repository write access
- Branch protection
- Pull request reviews
- CODEOWNERS
- Signed commits/tags if required
- Argo CD AppProject permissions
- Cluster-scoped resource access
- Secret management

### 23.2 AppProject Controls

Use AppProjects to restrict:

- Allowed Git repositories
- Allowed destination clusters
- Allowed namespaces
- Allowed cluster-scoped resources
- Denied resource kinds
- Source namespaces where applicable

Example concept:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://git.example.com/payments/*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-*
  clusterResourceWhitelist:
    - group: ""
      kind: Namespace
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ""
      kind: Service
    - group: route.openshift.io
      kind: Route
```

For many production teams, AppProject restrictions are as important as sync policy.

### 23.3 Secrets

Avoid storing raw Secrets in Git.

Better options:

- Sealed Secrets
- External Secrets Operator
- Vault integration
- SOPS/KSOPS if supported by your platform model
- OpenShift secret management with controlled injection

Sync policy with Secrets:

- `selfHeal` can overwrite manually rotated secrets if Git owns them.
- `prune` can delete Secrets removed from Git.
- Secret rotation tools may mutate Secret data.

Define clear ownership.

### 23.4 Emergency Break-Glass

For production, document break-glass steps:

1. Disable auto-sync for the affected app.
2. Apply emergency patch.
3. Open incident/change record.
4. Commit the patch back to Git.
5. Re-enable auto-sync.
6. Verify app health.

Commands:

```bash
oc patch application <app> -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":false}}}}'
```

Then after Git is fixed:

```bash
oc patch application <app> -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":true}}}}'
```

## 24. Best Practices Checklist

### 24.1 General

- [ ] Keep Git as the source of truth.
- [ ] Use explicit `automated.enabled`.
- [ ] Use `allowEmpty: false` for production.
- [ ] Use `PruneLast=true` with production pruning.
- [ ] Use `FailOnSharedResource=true` in multi-team environments.
- [ ] Use `ApplyOutOfSyncOnly=true` for large applications.
- [ ] Use `RespectIgnoreDifferences=true` when ignoring fields that must not be reapplied.
- [ ] Keep sync policy in Git, not only in UI.

### 24.2 Pruning

- [ ] Enable prune only after ownership is clear.
- [ ] Protect PVCs and Namespaces.
- [ ] Use `Prune=confirm` for critical resources.
- [ ] Avoid `allowEmpty: true` unless intentionally decommissioning.
- [ ] Split shared resources into separate Applications.

### 24.3 Self-Heal

- [ ] Enable self-heal for Git-owned resources.
- [ ] Do not fight HPA or Operators.
- [ ] Configure `ignoreDifferences` for controller-owned fields.
- [ ] Document manual hotfix procedure.

### 24.4 OpenShift

- [ ] Verify namespace is manageable by OpenShift GitOps.
- [ ] Label target namespaces when using the default shared instance model.
- [ ] Confirm Argo CD controller RBAC with `oc auth can-i`.
- [ ] Treat SCC and cluster-scoped resources as sensitive.
- [ ] Handle Operators in separate waves/apps.
- [ ] Validate Routes, PVCs, NetworkPolicies, and Quotas after sync.

### 24.5 ApplicationSet

- [ ] Configure sync policy in ApplicationSet template.
- [ ] Do not manually edit generated Applications.
- [ ] Use environment-specific parameters.
- [ ] Review blast radius before enabling prune across generated apps.

## 25. Interview / Exam-Style Questions

### Q1. What is the difference between automated sync and self-heal?

Automated sync applies changes when Argo CD detects the Application is OutOfSync, usually because Git desired state changed. Self-heal specifically tells Argo CD to correct live-cluster drift even when Git has not changed.

### Q2. What happens if a manifest is removed from Git but `prune` is false?

The resource remains in the cluster. Argo CD may show the application as OutOfSync because the live resource is no longer part of desired state.

### Q3. Why is `allowEmpty: false` safer in production?

It prevents automatic pruning from deleting all application resources if Git renders zero manifests due to a wrong path, bad Helm values, broken Kustomize overlay, or accidental repository cleanup.

### Q4. Why can self-heal cause issues with HPA?

HPA updates `Deployment.spec.replicas`. If Git also defines replicas and Argo CD self-heal is enabled, Argo CD can reset replicas back to the Git value. Use `ignoreDifferences` and `RespectIgnoreDifferences=true` or remove replica ownership from Git.

### Q5. Why use `PruneLast=true`?

It delays pruning until other resources are applied and healthy. This reduces downtime risk during object replacement or migration.

### Q6. What does `CreateNamespace=true` do?

It allows Argo CD to create the destination namespace if it does not already exist. In OpenShift, Argo CD still needs RBAC and namespace-management permissions.

### Q7. When should `SkipDryRunOnMissingResource=true` be used?

When a custom resource may be synced before its CRD is known to the API server, commonly during Operator/CRD bootstrapping. It should be used carefully and not as a substitute for correct ordering.

### Q8. Why use `FailOnSharedResource=true`?

It prevents multiple Applications from managing the same resource, which avoids ownership conflicts and reconciliation fights.

### Q9. What is the difference between `Prune=false` and `Delete=false`?

`Prune=false` protects a resource from being deleted when it is removed from Git during sync. `Delete=false` protects it from being deleted when the Argo CD Application itself is deleted.

### Q10. How do you temporarily stop auto-sync for an incident?

Patch the Application:

```bash
oc patch application <app> -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":false}}}}'
```

Then commit the final fix to Git and re-enable auto-sync.

## Final Senior Admin Summary

For an advanced OpenShift administrator, Argo CD sync policy should be treated as a production reconciliation contract:

```text
Git says what should exist.
Sync policy says how aggressively Argo CD makes it true.
OpenShift RBAC and governance say what Argo CD is allowed to change.
```

The safest mature production baseline is usually:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
  retry:
    limit: 5
    backoff:
      duration: 10s
      factor: 2
      maxDuration: 5m
  syncOptions:
    - PruneLast=true
    - PrunePropagationPolicy=foreground
    - ApplyOutOfSyncOnly=true
    - FailOnSharedResource=true
    - RespectIgnoreDifferences=true
```

But do not blindly apply this everywhere. Adjust it based on:

- Environment: dev, test, prod, DR, bootstrap
- Resource type: workload, namespace, Operator, CRD, PVC, cluster-scoped resource
- Ownership: app team, platform team, security team, external controller
- Risk: deletion impact, downtime impact, compliance requirement
- OpenShift controls: RBAC, SCC, quotas, NetworkPolicy, admission, Operators

A senior admin does not just enable auto-sync. A senior admin designs the reconciliation boundary.
