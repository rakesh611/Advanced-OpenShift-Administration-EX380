# GitOps Troubleshooting in OpenShift GitOps / Argo CD

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and OpenShift GitOps owners with production responsibility.  
**Level:** Senior / 10+ years operations mindset.  
**Focus:** Troubleshooting Red Hat OpenShift GitOps Operator and Argo CD in real OpenShift environments.

---

## 1. Executive Summary

GitOps troubleshooting is not only about fixing an Argo CD `Application` that shows `OutOfSync` or `Degraded`. In OpenShift, GitOps troubleshooting spans the full control plane:

- Red Hat OpenShift GitOps Operator lifecycle
- `ArgoCD` custom resource reconciliation
- Argo CD control-plane pods
- repository connectivity and credential handling
- manifest generation through Helm, Kustomize, Jsonnet, plain YAML, or plugins
- Kubernetes/OpenShift admission failures
- OpenShift RBAC, SCC, namespace labels, quotas, NetworkPolicy, Routes, image registry, Operators, CRDs, MachineConfig, and multicluster access
- drift detection and sync behavior
- observability, metrics, logs, audit trails, and incident runbooks

A senior administrator should troubleshoot GitOps by separating the issue into **five planes**:

| Plane | What it means | Main components |
|---|---|---|
| Operator plane | Is OpenShift GitOps Operator healthy? | Subscription, CSV, Operator pod, `ArgoCD` CR |
| Argo CD control plane | Is Argo CD itself healthy? | server, application-controller, repo-server, Redis, Dex, ApplicationSet, notifications |
| Source plane | Can Argo CD read desired state? | Git/Helm/OCI repo, credentials, TLS, SSH, webhook |
| Render plane | Can Argo CD generate manifests? | Helm, Kustomize, plugins, values files, CRD schemas |
| Destination plane | Can OpenShift accept and run the desired state? | RBAC, SCC, PSA, quotas, admission webhooks, CRDs, pods, routes, storage, network |

The most common mistake is to jump directly to the application pod logs. In GitOps, the pod is usually the **last symptom**, not the first root cause. Start from the Argo CD `Application` object, then follow the chain: source → render → diff → sync → OpenShift admission → workload runtime.

## 2. Mental Model: How Argo CD Reconciliation Works

At a high level, Argo CD does the following:

1. Reads an `Application` CR.
2. Pulls desired state from Git, Helm repo, OCI source, or another supported source.
3. Generates manifests using the configured tool.
4. Compares generated manifests with live cluster objects.
5. Marks status as `Synced`, `OutOfSync`, `Unknown`, `Healthy`, `Progressing`, `Degraded`, or `Missing` depending on diff and health checks.
6. Applies changes when manual or automated sync is triggered.
7. Optionally prunes removed resources and self-heals live drift.

In OpenShift GitOps, Argo CD is normally installed and managed by the **Red Hat OpenShift GitOps Operator**. The default instance is created in the `openshift-gitops` namespace and is intended mainly for cluster configuration use cases. User-defined instances can be namespace-scoped or cluster-scoped depending on how your platform model is designed.

### Key OpenShift-specific difference

Generic upstream Argo CD assumes a Kubernetes environment. OpenShift adds additional controls:

- Security Context Constraints (SCC)
- OpenShift Routes
- OpenShift OAuth integration
- Red Hat Operators and Operator Lifecycle Manager (OLM)
- namespace/project labels for GitOps management
- cluster-scoped vs namespace-scoped Argo CD instances
- OpenShift monitoring stack integration
- restricted pod security admission labels in some GitOps namespaces
- OpenShift image registry and pull secret behavior
- MachineConfig Operator behavior for node-level configuration

Therefore, an issue that looks like an Argo CD sync failure might actually be OpenShift RBAC, SCC, quota, route, storage, or admission failure.

## 4. First 10-Minute Triage Workflow

When an incident starts, do not begin by editing YAML. First identify the failing plane.

### 4.1 Confirm OpenShift GitOps Operator health

```bash
oc get subscription -A | grep -i gitops
oc get csv -A | grep -i gitops
oc get pods -n openshift-gitops-operator
oc get events -n openshift-gitops-operator --sort-by=.lastTimestamp | tail -50
```

Check CSV phase:

```bash
oc get csv -n openshift-gitops-operator
oc describe csv -n openshift-gitops-operator <csv-name>
```

Healthy CSV should normally show `Succeeded`. If the CSV is `Pending`, `Failed`, or `Replacing`, troubleshoot OLM first.

### 4.2 Confirm Argo CD instance health

```bash
oc get argocd -A
oc describe argocd -n openshift-gitops openshift-gitops
oc get pods -n openshift-gitops -o wide
oc get deployments,statefulsets -n openshift-gitops
```

Look for:

- pod restarts
- image pull failures
- crash loops
- pending pods
- unavailable deployments
- Redis unavailable
- repo-server unavailable
- application-controller not ready
- route/certificate problems

### 4.3 Confirm the Application object

```bash
oc get applications.argoproj.io -A
oc get application -n openshift-gitops <app-name> -o yaml
oc describe application -n openshift-gitops <app-name>
```

Important fields:

```yaml
status:
  sync:
    status: Synced | OutOfSync | Unknown
  health:
    status: Healthy | Progressing | Degraded | Missing | Unknown
  operationState:
    phase: Succeeded | Failed | Running | Error
    message: ...
  conditions:
  - type: ...
    message: ...
```

### 4.4 Check Argo CD CLI status

```bash
argocd app list
argocd app get <app-name>
argocd app diff <app-name>
argocd app history <app-name>
argocd app manifests <app-name>
```

When using OpenShift route with TLS, login might look like:

```bash
ARGOCD_ROUTE=$(oc get route openshift-gitops-server -n openshift-gitops -o jsonpath='{.spec.host}')
argocd login $ARGOCD_ROUTE --sso --grpc-web
```

If using local admin password:

```bash
oc extract secret/openshift-gitops-cluster -n openshift-gitops --to=-
```

Password secret names vary by instance and version. Always inspect secrets in the Argo CD namespace.

## 5. Troubleshooting Decision Tree

### Symptom: Argo CD UI/API not reachable

Check:

```bash
oc get route -n openshift-gitops
oc describe route -n openshift-gitops openshift-gitops-server
oc get svc -n openshift-gitops
oc get endpoints -n openshift-gitops openshift-gitops-server
oc logs -n openshift-gitops deploy/openshift-gitops-server --tail=100
```

Likely causes:

- route missing or misconfigured
- TLS termination mismatch
- server pod not ready
- service selector mismatch
- router/ingress issue
- OAuth/Dex issue
- certificate trust issue
- network policy blocking ingress

### Symptom: Application shows `Unknown`

Check:

```bash
oc describe application -n <argocd-ns> <app>
oc logs -n <argocd-ns> statefulset/<argocd-name>-application-controller --tail=200
oc logs -n <argocd-ns> deploy/<argocd-name>-repo-server --tail=200
oc get secret,cm -n <argocd-ns>
```

Likely causes:

- application-controller cannot calculate state
- Redis unavailable or unstable
- destination cluster credentials invalid
- repository access failure
- repo-server cannot generate manifests
- API discovery/cache problem
- target namespace deleted
- CRD missing
- controller pod restarted during reconciliation

### Symptom: Application is `OutOfSync`

Run:

```bash
argocd app diff <app>
argocd app get <app> --show-operation
oc get application -n <argocd-ns> <app> -o jsonpath='{.status.summary}'
```

Likely causes:

- Git changed and app has not synced yet
- automated sync disabled
- resource created manually in cluster
- mutation by admission webhook/operator
- prune disabled or needs confirmation
- generated fields not ignored
- Helm chart rendered differently
- Kustomize remote base changed
- resource tracking label/annotation conflict

### Symptom: Sync failed

Check operation message:

```bash
argocd app get <app>
oc describe application -n <argocd-ns> <app>
oc logs -n <argocd-ns> statefulset/<argocd-name>-application-controller --tail=300
```

Classify the failure:

| Error text | Likely root cause |
|---|---|
| `permission denied`, `forbidden` | Argo CD service account lacks RBAC |
| `no matches for kind` | CRD missing or not established |
| `admission webhook denied` | Validating/mutating webhook rejected object |
| `exceeded quota` | ResourceQuota in target namespace |
| `violates PodSecurity` | PSA/SCC/securityContext issue |
| `ImagePullBackOff` | image, registry, pull secret, CA, credentials |
| `context deadline exceeded` | API server, webhook, repo-server, or network timeout |
| `manifest generation error` | Helm/Kustomize/plugin/render issue |
| `namespaces ... not found` | target namespace missing or CreateNamespace disabled |

## 6. Operator Plane Troubleshooting

The Operator plane owns installation and reconciliation of Argo CD instances.

### 6.1 Subscription and CSV checks

```bash
oc get subscription -n openshift-gitops-operator
oc get installplan -n openshift-gitops-operator
oc get csv -n openshift-gitops-operator
oc describe subscription -n openshift-gitops-operator <subscription-name>
oc describe installplan -n openshift-gitops-operator <installplan-name>
oc describe csv -n openshift-gitops-operator <csv-name>
```

Common OLM problems:

- InstallPlan waiting for manual approval
- catalog source unavailable
- disconnected cluster missing mirrored images
- CSV replacement stuck
- CRD conflict
- insufficient permissions
- Operator pod crash looping

### 6.2 Operator pod logs

```bash
oc get pods -n openshift-gitops-operator
oc logs -n openshift-gitops-operator deploy/openshift-gitops-operator-controller-manager -c manager --tail=300
```

Look for:

- reconciliation errors for `ArgoCD` CR
- RBAC creation failure
- route/TLS reconciliation failure
- deployment/statefulset creation errors
- invalid `ArgoCD` spec fields

### 6.3 ArgoCD CR status

```bash
oc get argocd -A
oc get argocd -n <argocd-ns> <argocd-name> -o yaml
oc describe argocd -n <argocd-ns> <argocd-name>
```

Important fields:

```yaml
status:
  phase: Available | Pending | Failed
  applicationController: Running
  server: Running
  repo: Running
  redis: Running
```

If the `ArgoCD` CR is not `Available`, do not troubleshoot only the application. The GitOps control plane itself is unhealthy.

## 7. Argo CD Control-Plane Troubleshooting

### 7.1 Pod overview

```bash
oc get pods -n <argocd-ns> -o wide
oc get deploy,sts,rs -n <argocd-ns>
oc get events -n <argocd-ns> --sort-by=.lastTimestamp | tail -100
```

### 7.2 Readiness and liveness failures

```bash
oc describe pod -n <argocd-ns> <pod-name>
oc logs -n <argocd-ns> <pod-name> --all-containers --tail=200
oc get pod -n <argocd-ns> <pod-name> -o jsonpath='{.status.containerStatuses}' | jq
```

Common causes:

- insufficient CPU/memory requests
- OOMKilled repo-server or controller
- Redis connection problems
- config error in `argocd-cm`, `argocd-rbac-cm`, or TLS secret
- corrupted or incompatible plugin configuration
- unavailable cluster DNS
- missing mounted secret/configmap
- unsupported custom image

### 7.3 Application controller logs

The application controller is responsible for comparing desired and live state and performing sync.

```bash
oc logs -n <argocd-ns> statefulset/<argocd-name>-application-controller --tail=300
```

Search for:

```bash
oc logs -n <argocd-ns> statefulset/<argocd-name>-application-controller | egrep -i 'error|failed|forbidden|timeout|permission|cache|comparison|sync'
```

Typical messages:

- cannot get resource
- comparison error
- failed to apply resource
- failed to update application status
- cluster cache sync error
- permission denied
- timeout waiting for condition

### 7.4 Repo-server logs

Repo-server pulls source repos and renders manifests.

```bash
oc logs -n <argocd-ns> deploy/<argocd-name>-repo-server --tail=300
```

Look for:

- Git authentication failure
- TLS/CA failure
- SSH known_hosts failure
- Helm dependency build failure
- Kustomize build failure
- plugin timeout
- out of disk space in `/tmp`
- OOMKilled

### 7.5 Redis checks

Redis stores Argo CD application state/cache data.

```bash
oc get pods -n <argocd-ns> | grep redis
oc logs -n <argocd-ns> deploy/<argocd-name>-redis --tail=100
oc describe pod -n <argocd-ns> <redis-pod>
```

If Redis is unavailable, applications can show `Unknown`, UI can become slow, and controller reconciliation may fail.

## 8. Repository and Credential Troubleshooting

### 8.1 Repository connection test

```bash
argocd repo list
argocd repo get <repo-url>
```

For private Git:

```bash
argocd repo add https://git.example.com/org/repo.git \
  --username <user> \
  --password <token>
```

For SSH:

```bash
argocd repo add git@git.example.com:org/repo.git \
  --ssh-private-key-path ~/.ssh/id_rsa
```

### 8.2 Secret-based repository credentials

Repo credentials are stored as Kubernetes secrets in the Argo CD namespace. Inspect labels carefully:

```bash
oc get secrets -n <argocd-ns> -l argocd.argoproj.io/secret-type=repository
oc get secrets -n <argocd-ns> -l argocd.argoproj.io/secret-type=repo-creds
oc get secret -n <argocd-ns> <secret-name> -o yaml
```

Example repository secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: repo-myapp
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  type: git
  url: https://git.example.com/platform/myapp.git
  username: gitops-bot
  password: <token>
```

### 8.3 Common Git errors

| Error | Meaning | Fix |
|---|---|---|
| `authentication required` | wrong token/user | rotate token, update secret |
| `repository not found` | wrong URL or no access | verify URL and permissions |
| `x509: certificate signed by unknown authority` | internal Git CA not trusted | configure TLS cert/CA |
| `ssh: handshake failed` | SSH key or algorithm issue | update key/known_hosts |
| `permission denied (publickey)` | bad SSH key | recreate repository secret |
| `context deadline exceeded` | network/proxy/firewall/DNS | test from repo-server pod |

### 8.4 Test network from repo-server pod

Use an approved debug method in your environment. Example:

```bash
oc rsh -n <argocd-ns> deploy/<argocd-name>-repo-server
```

Inside container, tools might be limited. If tooling is unavailable, use a temporary debug pod in the same namespace or verify egress from a controlled utility image approved by your security team.

```bash
oc run gitops-net-debug -n <argocd-ns> --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc rsh -n <argocd-ns> gitops-net-debug
curl -vk https://git.example.com
```

Clean up:

```bash
oc delete pod -n <argocd-ns> gitops-net-debug
```

## 9. Manifest Generation Troubleshooting

Manifest generation happens before sync. If generation fails, OpenShift never receives the objects.

### 9.1 Universal checks

```bash
argocd app get <app>
argocd app manifests <app>
oc logs -n <argocd-ns> deploy/<argocd-name>-repo-server --tail=300
```

Check application source:

```bash
oc get application -n <argocd-ns> <app> -o jsonpath='{.spec.source}' | jq
```

For multi-source applications:

```bash
oc get application -n <argocd-ns> <app> -o jsonpath='{.spec.sources}' | jq
```

### 9.2 Helm errors

Common Helm issues:

- invalid chart path
- missing values file
- wrong value key
- dependency not built
- chart repo auth failure
- incompatible Kubernetes API version
- template renders invalid YAML
- Helm hook conflicts with Argo CD hooks

Commands:

```bash
argocd app manifests <app>
oc logs -n <argocd-ns> deploy/<argocd-name>-repo-server | grep -i helm
```

Reproduce locally:

```bash
git clone <repo>
cd <repo>/<chart-path>
helm dependency build
helm template <release-name> . -f values.yaml --namespace <target-ns>
```

If local rendering succeeds but repo-server fails, compare:

- Helm version in Argo CD image
- repo-server environment
- custom plugin sidecars
- credentials
- network access to dependency repositories
- chart dependency lock files

### 9.3 Kustomize errors

Common Kustomize issues:

- wrong overlay path
- remote base inaccessible
- patch target not found
- duplicate resource IDs
- deprecated patch format
- namespace transformer conflict
- generated ConfigMap/Secret names changing unexpectedly

Reproduce locally:

```bash
git clone <repo>
cd <repo>/<overlay-path>
kustomize build .
```

Or with `kubectl`/`oc`:

```bash
oc kustomize .
```

Typical error examples:

```text
accumulating resources: accumulation err='accumulating resources from ...'
no matches for Id Deployment.v1.apps/myapp.[noNs]
may not add resource with an already registered id
```

### 9.4 Config Management Plugin issues

Plugins are powerful but increase troubleshooting complexity.

Check:

```bash
oc get cm -n <argocd-ns> | grep -i cmp
oc get deploy -n <argocd-ns> <argocd-name>-repo-server -o yaml
oc logs -n <argocd-ns> deploy/<argocd-name>-repo-server --all-containers --tail=300
```

Common plugin issues:

- sidecar missing
- plugin command not executable
- binary not present in image
- plugin discovery misidentifies repository
- plugin timeout
- plugin writes excessive data to disk
- permissions issue in `/tmp`
- environment variable missing

Senior recommendation: for production, keep plugin logic minimal and versioned. Prefer standard Helm/Kustomize whenever possible.

## 10. Sync Troubleshooting

### 10.1 Manual sync diagnostics

```bash
argocd app sync <app> --dry-run
argocd app sync <app>
argocd app wait <app> --health --sync --timeout 300
argocd app get <app> --show-operation
```

OpenShift equivalent inspection:

```bash
oc get application -n <argocd-ns> <app> -o yaml
oc describe application -n <argocd-ns> <app>
```

### 10.2 Automated sync not happening

Check `syncPolicy`:

```bash
oc get application -n <argocd-ns> <app> -o jsonpath='{.spec.syncPolicy}' | jq
```

Expected automated example:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
  - CreateNamespace=true
```

Common causes:

- automated sync not configured
- sync window blocks sync
- app project denies destination/source
- previous operation still running
- app has `Skip` annotation
- manual intervention required for prune confirmation
- Git revision is pinned to old commit/tag
- webhook not configured and refresh interval has not detected change yet

### 10.3 Sync waves and hooks

Argo CD applies resources in phases and waves. This matters when deploying CRDs, Operators, namespaces, RBAC, and custom resources.

Common order problem:

```text
CustomResource is applied before its CRD exists.
```

Fix using sync waves:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
```

Example:

- CRDs: wave `-2`
- Namespace/RBAC/ServiceAccount/SCC binding: wave `-1`
- Operator Subscription: wave `0`
- Custom Resources: wave `1`
- Workloads depending on operator-created resources: wave `2`

Hook phases:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation
```

Troubleshoot stuck hooks:

```bash
argocd app get <app>
oc get jobs,pods -n <target-ns>
oc describe job -n <target-ns> <job>
oc logs -n <target-ns> job/<job>
```

### 10.4 Prune issues

Symptoms:

- Application remains `OutOfSync`
- Deleted Git resource still exists in cluster
- Sync operation waits for confirmation
- Resource has finalizers

Check:

```bash
argocd app diff <app>
argocd app get <app>
oc get <kind> <name> -n <ns> -o yaml
```

Common annotations:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

Prune with confirmation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

Finalizer troubleshooting:

```bash
oc get <kind> <name> -n <ns> -o jsonpath='{.metadata.finalizers}'
oc describe <kind> <name> -n <ns>
```

Do not remove finalizers blindly in production. Identify the owning controller first. Manual finalizer removal should be an incident-level decision.

## 11. OpenShift RBAC Troubleshooting

RBAC is one of the most common OpenShift GitOps failures.

### 11.1 Identify the service account used by Argo CD

```bash
oc get pods -n <argocd-ns> -o jsonpath='{range .items[*]}{.metadata.name}{" => "}{.spec.serviceAccountName}{"\n"}{end}'
```

Common service accounts:

```bash
oc get sa -n <argocd-ns>
```

Usually important:

- `<argocd-name>-argocd-application-controller`
- `<argocd-name>-argocd-server`
- `<argocd-name>-argocd-applicationset-controller`

### 11.2 Use `oc auth can-i`

Check whether the controller can perform the action:

```bash
oc auth can-i create deployments.apps \
  --as system:serviceaccount:<argocd-ns>:<controller-sa> \
  -n <target-ns>

oc auth can-i create routes.route.openshift.io \
  --as system:serviceaccount:<argocd-ns>:<controller-sa> \
  -n <target-ns>

oc auth can-i create clusterroles.rbac.authorization.k8s.io \
  --as system:serviceaccount:<argocd-ns>:<controller-sa>
```

### 11.3 Fix namespace-scoped application delivery

For namespace-scoped deployment, bind a Role or ClusterRole to the controller service account in the target namespace.

Example:

```bash
oc adm policy add-role-to-user admin \
  system:serviceaccount:<argocd-ns>:<controller-sa> \
  -n <target-ns>
```

Or create explicit least-privilege RBAC:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: gitops-deployer
  namespace: myapp-dev
rules:
- apiGroups: ["", "apps", "route.openshift.io"]
  resources: ["services", "configmaps", "secrets", "deployments", "routes"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: gitops-deployer
  namespace: myapp-dev
subjects:
- kind: ServiceAccount
  name: openshift-gitops-argocd-application-controller
  namespace: openshift-gitops
roleRef:
  kind: Role
  name: gitops-deployer
  apiGroup: rbac.authorization.k8s.io
```

### 11.4 Cluster-scoped permissions

Cluster-scoped resources include:

- `Namespace`
- `ClusterRole`
- `ClusterRoleBinding`
- `PersistentVolume`
- `StorageClass`
- `MachineConfig`
- `OperatorGroup`
- `Subscription`
- many cluster-level CRDs

For these, namespace `admin` is not enough. You need cluster-level RBAC for the Argo CD controller service account.

Example check:

```bash
oc auth can-i create namespaces \
  --as system:serviceaccount:<argocd-ns>:<controller-sa>
```

If false, either:

- use a cluster-scoped Argo CD instance designed for platform configuration, or
- grant a narrow ClusterRole to the controller service account, or
- separate cluster config and app delivery into different Argo CD instances.

Senior practice: never give every tenant application instance broad cluster-wide permissions. Use separate instances and projects for cluster configuration vs application delivery.

## 12. AppProject Troubleshooting

`AppProject` controls what an application is allowed to deploy, from where, and to which destination.

### 12.1 Inspect project

```bash
oc get appproject -n <argocd-ns>
oc get appproject -n <argocd-ns> <project> -o yaml
argocd proj get <project>
```

Important sections:

```yaml
spec:
  sourceRepos:
  - https://git.example.com/platform/*
  destinations:
  - namespace: myapp-*
    server: https://kubernetes.default.svc
  clusterResourceWhitelist:
  - group: '*'
    kind: '*'
  namespaceResourceWhitelist:
  - group: '*'
    kind: '*'
```

### 12.2 Common AppProject failures

| Error | Meaning | Fix |
|---|---|---|
| source repo is not permitted | `sourceRepos` does not allow repo | add repo pattern |
| destination server/namespace is not permitted | `destinations` denies target | add destination |
| resource is not permitted in project | whitelist/blacklist blocks resource | update resource rules |
| app uses default project accidentally | weak tenancy design | create dedicated project |

### 12.3 Senior security note

The default project is often too permissive. In shared OpenShift clusters, lock down the default `AppProject` and create dedicated projects with explicit `sourceRepos`, `destinations`, and resource whitelists.

## 13. Namespace Management Issues

### 13.1 Target namespace not found

Error:

```text
namespaces "myapp-dev" not found
```

Options:

1. Create the namespace separately with GitOps.
2. Enable namespace creation:

```yaml
spec:
  syncPolicy:
    syncOptions:
    - CreateNamespace=true
```

3. Use a separate cluster-config application to create namespaces before app applications.

### 13.2 Argo CD cannot manage namespace

In OpenShift GitOps, namespace management might require labels allowing an Argo CD instance to manage the namespace, depending on instance model and version.

Example:

```bash
oc label namespace <target-ns> argocd.argoproj.io/managed-by=<argocd-ns>
```

Check:


## 16. Drift and Persistent OutOfSync Troubleshooting

### 16.1 Understand the difference

`OutOfSync` means Argo CD sees a difference between desired manifests and live objects. It does not always mean the application is broken.

`Degraded` means Argo CD health checks think the resource is not operationally healthy.

A healthy app can be `OutOfSync`, and a synced app can be `Degraded`.

### 16.2 Diff investigation

```bash
argocd app diff <app>
argocd app get <app>
argocd app manifests <app> > desired.yaml
oc get <kind> <name> -n <ns> -o yaml > live.yaml
```

Compare:

```bash
diff -u desired.yaml live.yaml
```

### 16.3 Common drift sources

| Drift source | Example |
|---|---|
| Mutating webhook | injects sidecars, labels, env vars |
| Operator reconciliation | changes CR status/spec defaults |
| OpenShift defaulting | adds route fields, deployment defaults |
| HPA | changes replica count |
| image tag mutation | `latest` or image stream behavior |
| Helm random functions | random secrets generated each render |
| generated names | Kustomize ConfigMap hash names |
| manual hotfix | someone edited live object |
| omitted fields | API server defaults them live |

### 16.4 Ignore differences carefully

Application-level example:

```yaml
spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
    - /spec/replicas
```

System-level customization can be configured in Argo CD settings, but use cautiously.

Senior rule:

- Ignore fields only after you understand who changes them and why.
- Do not ignore security-sensitive fields like container image, RBAC rules, service account, SCC-related settings, or secrets unless you have a very specific control.
- For HPA-managed deployments, ignoring `/spec/replicas` is common.

### 16.5 Self-heal loop

If `selfHeal: true` and a controller/webhook keeps changing the same field, Argo CD may repeatedly patch it back. This causes noisy events and possible instability.

Fix options:

- change Git to match OpenShift/operator default behavior
- configure `ignoreDifferences`
- disable self-heal for that app
- fix webhook/operator configuration
- separate ownership boundaries

## 17. Health Troubleshooting

### 17.1 Health statuses

Common health states:

| Status | Meaning |
|---|---|
| Healthy | Resource is operational according to Argo CD health logic |
| Progressing | Resource is being created/updated |
| Degraded | Resource reports failure or unavailable state |
| Missing | Desired resource is absent from cluster |
| Unknown | Argo CD cannot determine health |

### 17.2 Deployment degraded

```bash
oc get deploy -n <ns>
oc describe deploy -n <ns> <deploy>
oc get rs,pods -n <ns> -l app=<label>
oc describe pod -n <ns> <pod>
oc logs -n <ns> <pod> --all-containers --tail=100
```

Common causes:

- image pull failure
- crash loop
- failed readiness probe
- insufficient resources
- SCC rejection
- config/secret missing
- PVC unbound
- node scheduling issue

### 17.3 Route degraded or not reachable

```bash
oc get route -n <ns>
oc describe route -n <ns> <route>
oc get svc,endpoints -n <ns>
oc get pods -n <ns> -o wide
```

Check:

- route host correct
- service targetPort correct
- endpoints exist
- pod labels match service selector
- TLS termination correct
- certificate/key valid
- DNS points to router
- router health

### 17.4 Service has no endpoints

```bash
oc get svc -n <ns> <svc> -o yaml
oc get endpoints -n <ns> <svc> -o yaml
oc get pods -n <ns> --show-labels
```

Typical fix: service selector must match pod labels.

### 17.5 Custom Resource health unknown

For CRDs, Argo CD might not know how to evaluate health because CRDs do not share a universal status format. Use custom Lua health checks only when necessary and after understanding the CR status fields.

Example concept:

```yaml
resource.customizations.health.example.com_MyKind: |
  hs = {}
  if obj.status ~= nil and obj.status.phase == "Ready" then
    hs.status = "Healthy"
    hs.message = "Resource is ready"
    return hs
  end
  hs.status = "Progressing"
  hs.message = "Waiting for Ready phase"
  return hs
```

Apply custom health checks through Argo CD configuration, normally controlled by the platform team.

## 19. MachineConfig and Cluster Configuration Troubleshooting

GitOps can manage cluster configuration, but node-level changes require care.

### 19.1 MachineConfig sync risk

When Argo CD applies a `MachineConfig`, the Machine Config Operator can reboot nodes. If the node running the Argo CD application controller is rebooted during sync, the sync operation can abort or remain in an uncertain intermediate state until nodes finish updating.

### 19.2 Checks

```bash
oc get mcp
oc describe mcp <pool>
oc get mc
oc get nodes
oc get pods -n openshift-gitops -o wide
```

### 19.3 Senior recommendations

- Run GitOps control-plane workloads on infrastructure nodes where possible.
- Do not combine many disruptive `MachineConfig` changes in one sync.
- Use maintenance windows for node rebooting changes.
- Monitor MCP `Updating`, `Updated`, and `Degraded` status.
- Use sync waves for cluster config dependencies.
- Avoid automatic prune on critical cluster-scoped resources unless reviewed.

## 25. Performance and Scale Troubleshooting

### 25.1 Symptoms

- UI slow
- app refresh delayed
- sync queue backed up
- repo-server OOMKilled
- application-controller high CPU
- Redis memory pressure
- comparison taking too long
- many apps stuck `Unknown`

### 25.2 Check resources

```bash
oc adm top pods -n <argocd-ns>
oc adm top pod -n <argocd-ns> <pod>
oc describe pod -n <argocd-ns> <pod> | egrep -i 'oom|killed|memory|cpu|evicted'
```

### 25.3 Argo CD metrics

In OpenShift console, use Observe → Metrics or Prometheus queries.

Useful metric families often include:

```text
argocd_app_info
argocd_app_sync_total
argocd_app_reconcile_count
argocd_app_k8s_request_total
argocd_cluster_connection_status
argocd_git_request_total
argocd_redis_request_total
```

Example health status query:

```promql
sum(argocd_app_info{health_status!=""}) by (health_status)
```

Example sync status query:

```promql
sum(argocd_app_info{sync_status!=""}) by (sync_status)
```

### 25.4 Repo-server scaling considerations

Repo-server can become bottlenecked because it clones repositories, runs Helm/Kustomize/plugin commands, and caches generated manifests. Large monorepos, many applications, remote bases, Helm dependencies, and plugins can cause CPU, memory, disk, and timeout issues.

Actions:

- increase repo-server CPU/memory
- reduce monorepo blast radius
- use manifest generate paths where appropriate
- avoid large binary files in Git repos
- pin chart versions
- avoid Helm charts that change without version bumps
- review repo-server `/tmp` disk usage
- consider persistent volume for repo-server if supported by your design
- tune parallelism and execution timeout only after measuring

### 25.5 Controller scale considerations

Application controller manages diffing, live state cache, sync operations, and cluster API calls.

Actions:

- check number of applications and resources per app
- avoid one giant application for the whole cluster
- split apps by lifecycle and failure domain
- use sync waves intentionally
- watch API server throttling
- monitor controller restarts and memory usage
- review cluster cache errors

## 27. Incident Patterns and Fix Examples

### Pattern 1: App is Synced but pod is failing

Meaning: Git desired state was applied, but runtime health is bad.

Check:

```bash
argocd app get <app>
oc get pods -n <ns>
oc describe pod -n <ns> <pod>
oc logs -n <ns> <pod> --previous
```

Likely root causes:

- app crash
- bad config
- missing secret
- wrong image
- failed probe
- PVC issue
- SCC issue

Fix in Git, not by editing live objects.

### Pattern 2: App is OutOfSync after every sync

Meaning: something changes the live resource after Argo CD applies it.

Check:

```bash
argocd app diff <app>
oc get events -n <ns> --sort-by=.lastTimestamp | tail -100
```

Likely root causes:

- mutating admission webhook
- OpenShift defaulting
- HPA changes replicas
- Operator modifies CR
- random Helm template function

Fix:

- align Git with actual controller behavior
- ignore safe generated fields
- remove randomness from chart
- split ownership

### Pattern 3: Sync fails with forbidden

Meaning: Argo CD controller lacks permission.

Check:

```bash
oc auth can-i <verb> <resource> \
  --as system:serviceaccount:<argocd-ns>:<controller-sa> \
  -n <target-ns>
```

Fix:

- grant least-privilege Role/RoleBinding
- for cluster resources, use ClusterRole/ClusterRoleBinding
- ensure AppProject allows the destination and resource

### Pattern 4: Repo access randomly fails

Meaning: repo-server cannot consistently access source.

Check:

```bash
oc logs -n <argocd-ns> deploy/<argocd-name>-repo-server | egrep -i 'git|timeout|x509|authentication|ls-remote'
oc describe pod -n <argocd-ns> -l app.kubernetes.io/name=<argocd-name>-repo-server
```

Fix:

- inspect Git server availability
- check corporate proxy
- configure CA trust
- rotate token
- increase retry count if transient network issue
- avoid ambiguous `HEAD` when stability matters

### Pattern 5: CRD not found during sync

Meaning: custom resource applied before CRD exists.

Fix:

- split CRD/operator and CR resources
- use sync waves
- wait for CSV/CRD readiness
- add custom health checks if necessary

### Pattern 6: MachineConfig sync causes Argo CD interruption

Meaning: Argo CD applied node-level config that reboots nodes, possibly including the node running Argo CD controller.

Fix:

- schedule maintenance window
- run GitOps on infra nodes
- separate MachineConfig app
- monitor MCP rollout
- use manual sync for disruptive cluster changes

## 28. Production Best Practices for Easier Troubleshooting

### 28.1 Separate ownership boundaries

Use separate Argo CD instances or projects for:

- platform cluster configuration
- tenant application delivery
- operators
- infrastructure workloads
- security policies
- shared services

### 28.2 Avoid giant applications

One huge app for everything causes:

- slow diff
- unclear blast radius
- painful rollbacks
- difficult ownership
- higher risk prune events

Prefer app-of-apps or ApplicationSet patterns with logical boundaries.

### 28.3 Pin versions

Avoid tracking floating references in production:

- avoid `HEAD` for critical cluster config
- prefer commit SHA, release tag, or controlled branch promotion
- pin Helm chart versions
- pin container image digests for critical workloads

### 28.4 Keep Git clean

- no generated artifacts unless intentional
- no large binary blobs
- no secrets in plaintext
- clear directory structure
- environment overlays separated
- meaningful commit messages
- pull request review for cluster-scoped changes

### 28.5 Design AppProjects strictly

Each AppProject should define:

- allowed source repos
- allowed destination clusters/namespaces
- allowed namespace-scoped resources
- allowed cluster-scoped resources
- project-level roles if needed

### 28.6 Treat prune as dangerous for cluster config

For application resources, prune is often useful. For cluster resources, prune can be risky.

Use:

```yaml
syncPolicy:
  automated:
    prune: false
```

or resource-level:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

### 28.7 Make OpenShift policies GitOps-managed

Manage these through GitOps:

- namespaces/projects
- ResourceQuota
- LimitRange
- RBAC
- NetworkPolicy
- SCC grants
- OperatorGroup/Subscription
- route/cert configuration
- monitoring alerts

But separate platform policy repos from application repos.

```yaml
  namespace: openshift-gitops

  kind: ClusterRole
  name: admin
  apiGroup: rbac.authorization.k8s.io
```

### Step 6: Sync platform config, then app

```bash
argocd app sync platform-namespaces
argocd app wait platform-namespaces --health --sync --timeout 300
```

## 32. Senior-Level Interview/Exam Points

If asked to explain GitOps troubleshooting in OpenShift GitOps, answer with this structure:

1. I first separate the issue into Operator, Argo CD control plane, source, render, sync/admission, and runtime planes.
2. I check `Application` status, conditions, operation state, controller logs, and repo-server logs.
3. For repo issues, I validate credentials, TLS, SSH, network egress, and render locally.
4. For sync failures, I inspect OpenShift admission errors: RBAC, SCC, quotas, CRDs, webhooks, and namespace labels.
5. For persistent `OutOfSync`, I analyze diff, mutation, HPA changes, operator defaults, prune settings, and ignore differences.
6. For health issues, I troubleshoot Kubernetes/OpenShift resources directly: pods, deployments, routes, services, endpoints, PVCs, and events.
7. I avoid manual live fixes unless it is an emergency; permanent fixes go back to Git.
8. I keep cluster configuration and application delivery separated using AppProjects, RBAC, and often separate Argo CD instances.

## 34. Final Practical Advice

For production OpenShift GitOps troubleshooting, remember this rule:

> **Argo CD tells you what failed, but OpenShift usually tells you why.**

Always correlate:

- Argo CD `Application` condition
- Argo CD controller/repo-server log
- OpenShift namespace event
- failing Kubernetes/OpenShift object status
- RBAC/admission result
- Git commit that introduced the desired state

This discipline prevents random patching and turns GitOps troubleshooting into a repeatable, auditable operational process.
