# Git Repository Structure in OpenShift GitOps / Argo CD

**Audience:** Advanced OpenShift Administration / senior platform engineers  
**Level:** 10+ years Linux, Kubernetes, OpenShift, DevOps experience  
**Scope:** Repository layout, GitOps design patterns, Argo CD `Application`, `ApplicationSet`, Kustomize, Helm, OpenShift platform configuration, multicluster structure, promotion, secrets, RBAC, validation, troubleshooting, and production governance.

---

## 1. Why Git Repository Structure Matters in OpenShift GitOps

In OpenShift GitOps, the Git repository is not just a place to store YAML files. It becomes the **desired-state control plane** for application and platform configuration. Argo CD continuously compares this Git desired state with the live OpenShift cluster state and reports or reconciles drift.

A poor repository structure usually causes these problems:

- Too much duplicate YAML across `dev`, `test`, `stage`, and `prod`.
- Unclear ownership between application teams and platform teams.
- Unsafe promotion because production tracks `HEAD` or an uncontrolled branch.
- Accidental deletion of namespaces, routes, PVCs, operators, or RBAC objects.
- Argo CD `OutOfSync` noise because generated or operator-created resources are mixed with Git-managed resources.
- Secrets accidentally committed in plain text.
- One large Argo CD project with excessive permissions.
- Hard-to-review pull requests because one commit changes many unrelated environments.
- Difficulty bootstrapping new clusters consistently.

For senior OpenShift administrators, repository structure is a **design decision**, not a cosmetic folder naming choice.

## 2. Core GitOps Repository Principle

A mature OpenShift GitOps setup normally separates:

1. **Application source code repository**  
   Contains Java, Go, Python, Node.js, Dockerfile/Containerfile, unit tests, CI pipeline, and build logic.

2. **Environment configuration repository**  
   Contains Kubernetes/OpenShift manifests, Kustomize overlays, Helm values, Argo CD `Application` definitions, `ApplicationSet` definitions, RBAC, namespace definitions, routes, quotas, network policies, and platform configuration.

This separation is important because source code and deployment configuration have different lifecycles. A developer may commit code many times a day, but production deployment configuration should move through controlled review, validation, promotion, and approval.

### Practical rule

Do not let every source-code commit automatically become a GitOps desired-state change unless your release governance explicitly allows it.

A better flow is:

```text
Developer commits source code
        |
        v
CI builds image and pushes immutable image tag
        |
        v
CI or release manager updates GitOps repo image tag / chart version
        |
        v
Argo CD reconciles OpenShift desired state
```

## 3. Repository Types in an Enterprise OpenShift GitOps Design

A real enterprise often uses more than one Git repository. The following repository types are common.

### 3.1 Application source repository

Example:

```text
payment-api-source/
├── src/
├── tests/
├── Containerfile
├── pom.xml
├── Jenkinsfile
└── README.md
```

This repository should not usually contain production OpenShift deployment state. It may contain local development examples, but the production desired state should live in the GitOps config repository.

---

### 3.2 Application configuration repository

Example:

```text
payment-api-gitops/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── route.yaml
│   ├── kustomization.yaml
│   └── configmap.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml
    │   ├── patch-replicas.yaml
    │   └── patch-image.yaml
    ├── stage/
    │   ├── kustomization.yaml
    │   └── patch-replicas.yaml
    └── prod/
        ├── kustomization.yaml
        ├── patch-replicas.yaml
        ├── hpa.yaml
        └── pdb.yaml
```

This model works well when each application team owns its own deployment configuration.

---

### 3.3 Platform configuration repository

Example:

```text
openshift-platform-gitops/
├── clusters/
│   ├── ocp-dev/
│   ├── ocp-stage/
│   └── ocp-prod/
├── components/
│   ├── namespaces/
│   ├── rbac/
│   ├── network-policies/
│   ├── quotas/
│   ├── operators/
│   ├── monitoring/
│   ├── logging/
│   ├── ingress/
│   ├── storage/
│   └── security/
├── argocd/
│   ├── projects/
│   ├── applications/
│   └── applicationsets/
└── README.md
```

This repository is usually owned by the platform/SRE/OpenShift administration team.

It commonly manages:

- Namespaces / OpenShift `Project` objects
- `ResourceQuota`
- `LimitRange`
- `NetworkPolicy`
- Tenant RBAC
- Operator subscriptions
- Monitoring stack configuration
- Logging stack configuration
- IngressController configuration
- Image registry configuration
- StorageClass-related configuration
- MachineConfig and MachineConfigPool definitions, if GitOps governance allows it
- Cluster-wide security objects, carefully controlled

---

### 3.4 Bootstrap repository

A bootstrap repository defines how a new cluster gets its baseline GitOps configuration.

Example:

```text
ocp-bootstrap/
├── bootstrap-root-app.yaml
├── argocd/
│   ├── argocd-instance.yaml
│   ├── projects/
│   ├── repo-creds/
│   └── rbac/
├── cluster-addons/
│   ├── cert-manager/
│   ├── external-secrets/
│   ├── logging/
│   ├── monitoring/
│   └── sealed-secrets/
└── README.md
```

This design often uses the **app-of-apps** or **ApplicationSet** pattern to install many child applications after the first root application is applied.

| `scripts/` | Validation and rendering helpers | Platform engineering |
| `docs/` | Operating model and contribution rules | All teams |

## 5. Important Argo CD Concepts That Drive Repository Structure

### 5.1 Argo CD Application

An Argo CD `Application` maps one Git/Helm/OCI source path to one destination cluster/namespace.

Basic example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-dev
  namespace: openshift-gitops
spec:
  project: payments
  source:
    repoURL: https://git.example.com/platform/openshift-gitops-repo.git
    targetRevision: main
    path: apps/payment-api/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=false
```

Repository implication:

```text
apps/payment-api/overlays/dev
```

must be a valid renderable unit. It should contain one of:

- `kustomization.yaml`
- Helm chart structure
- plain YAML files, if using directory mode
- Jsonnet files, if used in your organization

For OpenShift administrators, the path should be treated like an API boundary: if the path is wrong, too broad, or recursively includes unrelated resources, Argo CD may attempt to manage resources it should not manage.

---

### 5.2 AppProject

An `AppProject` is the security and tenancy boundary for Argo CD applications.

A good repository structure maps cleanly to AppProjects.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  description: Payments team applications
  sourceRepos:
    - https://git.example.com/platform/openshift-gitops-repo.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payment-dev
    - server: https://kubernetes.default.svc
      namespace: payment-stage
    - server: https://kubernetes.default.svc
      namespace: payment-prod
  namespaceResourceWhitelist:
    - group: ""
      kind: ConfigMap
    - group: ""
      kind: Service
    - group: apps
      kind: Deployment
    - group: route.openshift.io
      kind: Route
    - group: autoscaling
      kind: HorizontalPodAutoscaler
    - group: networking.k8s.io
      kind: NetworkPolicy
  clusterResourceWhitelist: []
  roles:
    - name: payments-dev-admin
      description: Payments dev environment admins
      policies:
        - p, proj:payments:payments-dev-admin, applications, get, payments/*, allow
        - p, proj:payments:payments-dev-admin, applications, sync, payments/payment-api-dev, allow
      groups:
        - oidc:payments-dev-admins
```

Repository implication:

```text
argocd/projects/payments.yaml
apps/payment-api/overlays/dev
apps/payment-api/overlays/stage
apps/payment-api/overlays/prod
```

The repo layout and AppProject must tell the same story. If the directory says `payments`, but the AppProject allows `*` repositories, `*` clusters, and `*` resources, then the GitOps boundary is weak.

---

### 5.3 ApplicationSet

`ApplicationSet` generates multiple Argo CD `Application` objects from a template.

It is very useful when:

- Many applications follow the same directory pattern.
- The same add-ons must be deployed to many clusters.
- New tenants should be onboarded by adding a YAML/JSON file.
- App teams create new app directories and Argo CD auto-generates Applications.

Example repository:

```text
apps/
├── payment-api/
│   └── overlays/
│       ├── dev/
│       ├── stage/
│       └── prod/
├── order-api/
│   └── overlays/
│       ├── dev/
│       ├── stage/
│       └── prod/
└── frontend/
    └── overlays/
        ├── dev/
        ├── stage/
        └── prod/
```

Example `ApplicationSet` using Git directory generator:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: apps-dev
  namespace: openshift-gitops
spec:
  goTemplate: true
  goTemplateOptions:
    - missingkey=error
  generators:
    - git:
        repoURL: https://git.example.com/platform/openshift-gitops-repo.git
        revision: main
        directories:
          - path: apps/*/overlays/dev
  template:
    metadata:
      name: '{{ index .path.segments 1 }}-dev'
      labels:
        env: dev
        generated-by: applicationset
    spec:
      project: payments
      source:
        repoURL: https://git.example.com/platform/openshift-gitops-repo.git
        targetRevision: main
        path: '{{ .path.path }}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{ index .path.segments 1 }}-dev'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

The directory name becomes a control input. That means folder naming must be strict and validated.

Bad:

```text
apps/payment api/overlays/dev
apps/payment-api-dev-old/overlays/dev
apps/payment-api/overlays/development
```

Good:

```text
apps/payment-api/overlays/dev
apps/order-api/overlays/dev
apps/frontend/overlays/dev
```

## 6. Kustomize-Based Repository Structure

Kustomize is commonly used in OpenShift GitOps because it supports base/overlay composition without heavy templating.

### 6.1 Standard structure

```text
apps/payment-api/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── route.yaml
│   ├── configmap.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml
    │   ├── patch-image.yaml
    │   ├── patch-replicas.yaml
    │   └── configmap-env.yaml
    ├── stage/
    │   ├── kustomization.yaml
    │   ├── patch-image.yaml
    │   ├── patch-replicas.yaml
    │   └── hpa.yaml
    └── prod/
        ├── kustomization.yaml
        ├── patch-image.yaml
        ├── patch-replicas.yaml
        ├── hpa.yaml
        ├── pdb.yaml
        └── route-prod.yaml
```

### 6.2 Base manifests

`apps/payment-api/base/deployment.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  labels:
    app.kubernetes.io/name: payment-api
    app.kubernetes.io/component: api
    app.kubernetes.io/part-of: payments
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: payment-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: payment-api
        app.kubernetes.io/component: api
    spec:
      containers:
        - name: payment-api
          image: image-registry.openshift-image-registry.svc:5000/payment/payment-api:placeholder
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 20
```

`apps/payment-api/base/service.yaml`

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-api
  labels:
    app.kubernetes.io/name: payment-api
spec:
  selector:
    app.kubernetes.io/name: payment-api
  ports:
    - name: http
      port: 8080
      targetPort: 8080
```

`apps/payment-api/base/route.yaml`

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payment-api
  labels:
    app.kubernetes.io/name: payment-api
spec:
  to:
    kind: Service
    name: payment-api
  port:
    targetPort: http
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
```

`apps/payment-api/base/kustomization.yaml`

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
  - route.yaml
  - configmap.yaml
commonLabels:
  app.kubernetes.io/managed-by: argocd
  app.kubernetes.io/part-of: payments
```

### 6.3 Environment overlay

`apps/payment-api/overlays/dev/kustomization.yaml`

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payment-dev
resources:
  - ../../base
patches:
  - path: patch-image.yaml
  - path: patch-replicas.yaml
  - path: configmap-env.yaml
nameSuffix: -dev
commonLabels:
  environment: dev
```

`apps/payment-api/overlays/dev/patch-image.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  template:
    spec:
      containers:
        - name: payment-api
          image: image-registry.openshift-image-registry.svc:5000/payment-dev/payment-api:1.4.2-dev.17
```

`apps/payment-api/overlays/prod/kustomization.yaml`

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payment-prod
resources:
  - ../../base
  - hpa.yaml
  - pdb.yaml
patches:
  - path: patch-image.yaml
  - path: patch-replicas.yaml
  - path: route-prod.yaml
commonLabels:
  environment: prod
```

### 6.4 Senior engineer notes for Kustomize structure

Use base/overlay when differences are mostly:

- replicas
- image tags
- route hostnames
- resource limits
- config values
- HPA/PDB presence
- environment labels
- namespace names

Avoid Kustomize overlays becoming a dumping ground. If each environment has completely different resources, you may not have one application with overlays; you may have separate deployable units.

## 7. Helm-Based Repository Structure

Helm is useful when you need parameterized templates, reusable charts, and many values. In Argo CD, Helm is used to render manifests; Argo CD owns the application lifecycle after rendering.

### 7.1 Chart in same GitOps repo

```text
apps/payment-api-helm/
├── Chart.yaml
├── values.yaml
├── values-dev.yaml
├── values-stage.yaml
├── values-prod.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── route.yaml
    ├── hpa.yaml
    └── pdb.yaml
```

Example Argo CD Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
spec:
  project: payments
  source:
    repoURL: https://git.example.com/platform/openshift-gitops-repo.git
    targetRevision: v1.4.2
    path: apps/payment-api-helm
    helm:
      releaseName: payment-api
      valueFiles:
        - values-prod.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
```

### 7.2 Chart in chart repository, values in GitOps repo

This is common in enterprises.

```text
openshift-gitops-repo/
└── helm-values/
    └── payment-api/
        ├── dev.yaml
        ├── stage.yaml
        └── prod.yaml
```

The chart can be versioned in a Helm/OCI repository, while values are reviewed in Git.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
spec:
  project: payments
  source:
    repoURL: oci://registry.example.com/helm
    chart: payment-api
    targetRevision: 1.4.2
    helm:
      releaseName: payment-api
      values: |
        replicaCount: 5
        image:
          tag: "1.4.2"
        route:
          host: payment.apps.prod.example.com
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
```

### 7.3 Senior engineer notes for Helm structure

Use Helm when:

- Many parameters vary by environment.
- You publish reusable charts for many teams.
- Operators/add-ons are distributed as Helm charts.
- Templates need loops, conditionals, or generated resources.

Avoid Helm when:

- You only need simple environment patches.
- The chart becomes unreadable due to excessive templating.
- Every values file has hundreds of unrelated keys.
- Nobody validates rendered output before merge.

Always validate the rendered output:

```bash
helm template payment-api ./apps/payment-api-helm -f values-prod.yaml > /tmp/payment-api-prod.yaml
oc apply --dry-run=server -f /tmp/payment-api-prod.yaml
```

## 8. Plain YAML Directory Structure

Argo CD can deploy a directory of plain manifests. This is simple, but risky when the directory grows.

Example:

```text
apps/simple-nginx/prod/
├── deployment.yaml
├── service.yaml
├── route.yaml
└── networkpolicy.yaml
```

Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: simple-nginx-prod
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/openshift-gitops-repo.git
    targetRevision: main
    path: apps/simple-nginx/prod
    directory:
      recurse: false
  destination:
    server: https://kubernetes.default.svc
    namespace: simple-nginx-prod
```

### Directory mode warning

Directory mode is only for plain manifests. If a directory contains Kustomize or Helm files and you configure it as a plain directory source, rendering can fail or behave differently from what you expect.

Senior rule:

Use plain YAML only for very small, stable components or generated output that is already validated. For most enterprise OpenShift repositories, prefer Kustomize or Helm.

## 9. Environment Organization Patterns

There are three common ways to represent environments.

---

### 9.1 Directory-per-environment

```text
apps/payment-api/overlays/
├── dev/
├── stage/
└── prod/
```

Advantages:

- Easy to understand.
- Easy to review environment-specific changes.
- Works well with Kustomize.
- Good for AppProject namespace mapping.

Disadvantages:

- Can duplicate environment configuration if not handled carefully.
- Promotion means copying a change from one folder to another.

Good for:

- Most OpenShift teams.
- Kustomize-heavy environments.
- Clear dev/stage/prod separation.

---

### 9.2 Branch-per-environment

```text
main      -> dev
stage     -> stage
prod      -> prod
```

Advantages:

- Promotion can be Git merge based.
- Environment state is isolated by branch.

Disadvantages:

- Harder to compare all environments at once.
- Merge conflicts can become operational blockers.
- Argo CD target revisions must be carefully controlled.
- Branch protection becomes critical.

Good for:

- Organizations with strong branch-based release workflows.

Not recommended when:

- Teams frequently need to compare `dev`, `stage`, and `prod` manifests side by side.
- Many teams share one repo and branch conflicts are common.

---

### 9.3 Repository-per-environment

```text
payment-api-dev-gitops/
payment-api-stage-gitops/
payment-api-prod-gitops/
```

Advantages:

- Strong separation.
- Production access can be locked down tightly.
- Works well in highly regulated environments.

Disadvantages:

- More repository management overhead.
- Promotion needs automation.
- Harder to reuse common base config unless using remote bases or packages.

Good for:

- Banking, telecom, defense, healthcare, or strict compliance environments.
- Teams requiring separate production Git permissions.

---

## 10. Cluster Organization Patterns

For multicluster OpenShift, structure must answer:

- Which cluster gets which application?
- Which platform components are common?
- Which cluster has special configuration?
- Which applications are region-specific?
- How is disaster recovery represented?

### 10.1 Cluster-first structure

```text
clusters/
├── ocp-dev/
│   ├── apps/
│   │   ├── payment-api.yaml
│   │   └── order-api.yaml
│   └── platform/
│       ├── logging.yaml
│       └── monitoring.yaml
├── ocp-stage/
│   ├── apps/
│   └── platform/
└── ocp-prod/
    ├── apps/
    └── platform/
```

Good when:

- Clusters are the primary operational unit.
- Platform team owns cluster onboarding.
- You have different clusters for different business units.

---

### 10.2 Application-first structure

```text
apps/
├── payment-api/
│   └── clusters/
│       ├── ocp-dev/
│       ├── ocp-stage/

└── order-api/
    └── clusters/
        ├── ocp-dev/
        ├── ocp-stage/
        └── ocp-prod/
```

Good when:

- Application team owns deployment to multiple clusters.
- Application lifecycle is more important than cluster lifecycle.

## 11. App-of-Apps Repository Pattern

The app-of-apps pattern uses one parent Argo CD `Application` to create child `Application` objects.

Example structure:

```text
argocd/
├── root/
│   ├── root-dev.yaml
│   ├── root-stage.yaml
│   └── root-prod.yaml
└── applications/
    ├── dev/
    │   ├── payment-api.yaml
    │   ├── order-api.yaml
    │   └── frontend.yaml
    ├── stage/
    │   ├── payment-api.yaml
    │   ├── order-api.yaml
    │   └── frontend.yaml
    └── prod/
        ├── payment-api.yaml
        ├── order-api.yaml
        └── frontend.yaml
```

Parent app:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-apps-prod
  namespace: openshift-gitops
spec:
  project: platform
  source:
    repoURL: https://git.example.com/platform/openshift-gitops-repo.git
    targetRevision: main
    path: argocd/applications/prod
    directory:
      recurse: false
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

Child app example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
spec:
  project: payments
  source:
    repoURL: https://git.example.com/platform/openshift-gitops-repo.git
    targetRevision: main
    path: apps/payment-api/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
```

### App-of-apps advantages

- Easy bootstrap.
- Clear parent-child relationship.
- Easy to onboard applications by adding one child app manifest.
- Works well for platform components.

### App-of-apps risks

- Parent app pruning can delete child apps if a file is removed.
- Bad child app path can cause broad failure.
- Sync order must be controlled for dependencies.
- Parent app must be restricted to the Argo CD namespace and Application resources.

## 12. ApplicationSet Repository Pattern

ApplicationSet is more dynamic than app-of-apps.

### 12.1 Directory generator pattern

Structure:

```text
cluster-addons/
├── logging/
│   ├── kustomization.yaml
│   └── subscription.yaml
├── monitoring/
│   ├── kustomization.yaml
│   └── config.yaml
└── external-secrets/
    ├── kustomization.yaml
    └── helm-values.yaml
```

ApplicationSet:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-addons
  namespace: openshift-gitops
spec:
  goTemplate: true
  goTemplateOptions:
    - missingkey=error
  generators:
    - git:
        repoURL: https://git.example.com/platform/openshift-gitops-repo.git
        revision: main
        directories:
          - path: cluster-addons/*
  template:
    metadata:
      name: '{{ .path.basename }}'
    spec:
      project: platform
      source:
        repoURL: https://git.example.com/platform/openshift-gitops-repo.git
        targetRevision: main
        path: '{{ .path.path }}'
      destination:
        server: https://kubernetes.default.svc
        namespace: openshift-operators
```

### 12.2 File generator pattern

Structure:

```text
tenants/
├── payments.yaml
├── ecommerce.yaml
└── analytics.yaml
```

`tenants/payments.yaml`

```yaml
name: payments
namespace: payment-dev
project: payments
path: apps/payment-api/overlays/dev
repoURL: https://git.example.com/platform/openshift-gitops-repo.git
```

ApplicationSet:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: tenant-apps
  namespace: openshift-gitops
spec:
  goTemplate: true
  generators:
    - git:
        repoURL: https://git.example.com/platform/openshift-gitops-repo.git
        revision: main
        files:
          - path: tenants/*.yaml
  template:
    metadata:
      name: '{{ .name }}'
    spec:
      project: '{{ .project }}'
      source:
        repoURL: '{{ .repoURL }}'
        targetRevision: main
        path: '{{ .path }}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{ .namespace }}'
```

### 12.3 ApplicationSet production caution

Do not allow arbitrary teams to template sensitive fields such as:

- `project`
- `repoURL`
- destination cluster
- destination namespace
- Helm values containing credentials
- plugin parameters

In multitenant environments, ApplicationSet permissions must be handled carefully. A templated `project` field can weaken project boundaries if not reviewed.

## 15. Sync Waves and Dependency-Aware Structure

Some resources must be created before others.

Typical ordering:

```text
Wave -10: Namespaces / Projects
Wave -9 : OperatorGroups / Subscriptions
Wave -8 : CRDs or operator installation resources
Wave -7 : RBAC / ServiceAccounts
Wave -6 : Secrets / ExternalSecret / SealedSecret
Wave -5 : ConfigMaps
Wave 0  : Deployments / StatefulSets / DaemonSets
Wave 1  : Services
Wave 2  : Routes / Ingress
Wave 3  : HPA / PDB / monitoring rules
```

Example annotation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-10"
```

Repository implication:

```text
platform/tenant-bootstrap/payments/
├── 00-namespace.yaml
├── 01-rbac.yaml
├── 02-quota.yaml
├── 03-networkpolicy.yaml
└── kustomization.yaml
```

File names alone do not control Argo CD sync ordering reliably. Use sync waves for dependency-sensitive objects.

## 16. Secrets Repository Structure

Never commit plain-text secrets.

Common GitOps-friendly options:

1. **Encrypted secrets in Git**  
   Examples: Sealed Secrets, SOPS-encrypted files.

2. **Secret references in Git**  
   Examples: External Secrets Operator, Vault CSI provider, cloud secret managers.

### 16.1 External secret reference pattern

```text
apps/payment-api/base/
├── deployment.yaml
├── service.yaml
├── externalsecret.yaml
└── kustomization.yaml
```

Example:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: payment-api-db
  namespace: payment-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-prod
    kind: ClusterSecretStore
  target:
    name: payment-api-db
    creationPolicy: Owner
  data:
    - secretKey: DB_PASSWORD
      remoteRef:
        key: payments/prod/db
        property: password
```

Git contains only the reference, not the secret value.

### 16.2 SealedSecret pattern

```text
apps/payment-api/overlays/prod/
├── sealedsecret-db.yaml
└── kustomization.yaml
```

Example:

```yaml
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: payment-api-db
  namespace: payment-prod
spec:
  encryptedData:
    DB_PASSWORD: AgBxxxxxxxxxxxxxxxxxxxxxxxx
  template:
    metadata:
      name: payment-api-db
      namespace: payment-prod
```

### 16.3 Senior engineer secret rules

- Add secret scanners to CI.
- Block Kubernetes `Secret` manifests unless explicitly encrypted or generated.
- Prefer external secret references for large multicluster environments.
- Rotate credentials outside Git whenever possible.
- Never store kubeconfig, registry passwords, database passwords, TLS private keys, or OAuth client secrets in plain text.
- Restrict who can edit secret reference paths.
- Document emergency rotation and key-loss procedures.

## 20. Pull Request Validation Pipeline

Before Argo CD sees a change, CI should validate it.

Recommended checks:

```bash
# YAML syntax
find . -name '*.yaml' -o -name '*.yml' | xargs yamllint

# Kustomize render
kustomize build apps/payment-api/overlays/prod > /tmp/payment-api-prod.yaml

# Kubernetes/OpenShift server-side validation
oc apply --dry-run=server -f /tmp/payment-api-prod.yaml

# Helm validation
helm lint apps/payment-api-helm
helm template payment-api apps/payment-api-helm -f apps/payment-api-helm/values-prod.yaml > /tmp/payment-api-helm.yaml
oc apply --dry-run=server -f /tmp/payment-api-helm.yaml

# Policy validation
conftest test /tmp/payment-api-prod.yaml

# Secret scanning
gitleaks detect --source .
```

### 20.1 What to block in CI

Block pull requests that:

- Add plain Kubernetes `Secret` values.
- Use `latest` image tags in production.
- Add wildcard RBAC.
- Add privileged SCC without approval.
- Add `hostPath`, `hostNetwork`, or `hostPID` without approval.
- Remove production namespaces.
- Change Argo CD `AppProject` permissions broadly.
- Change destination cluster or namespace unexpectedly.
- Disable NetworkPolicy in production.
- Add routes with wrong hostnames.
- Add unsupported API versions.

## 27. Handling Namespaces in Argo CD

There are two common models.

### 27.1 Platform creates namespaces

Recommended for production.

```text
platform/namespaces/payment-prod/namespace.yaml
apps/payment-api/overlays/prod/deployment.yaml
```

Argo CD app uses:

```yaml
syncOptions:
  - CreateNamespace=false
```

This ensures namespace labels, quotas, limits, RBAC, and network policies are created before workloads.

### 27.2 Argo CD app creates namespace

Possible for dev/test:

```yaml
syncOptions:
  - CreateNamespace=true
```

Risk:

- Namespace may be created without quota, labels, or network policies.
- Security policy may lag behind workload creation.

Production recommendation:

Use platform-managed namespaces.

## 28. Handling Cluster-Scoped Resources

Cluster-scoped resources are dangerous because they are not limited to one namespace.

Examples:

- `ClusterRole`
- `ClusterRoleBinding`
- `CustomResourceDefinition`

## 30. Practical Bootstrap Flow

### Step 1: Install OpenShift GitOps Operator

Usually installed by OperatorHub, Subscription, or cluster bootstrap automation.

### Step 2: Create Argo CD instance

```bash
oc get argocd -n openshift-gitops
```

### Step 3: Create repository credentials

Store Git credentials securely in the Argo CD namespace.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: private-git-repo
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  type: git
  url: https://git.example.com/platform/openshift-gitops-repo.git
  username: gitops-bot
  password: ${TOKEN}
```

Do not commit this secret with real credentials.

### Step 4: Apply root application

```bash
oc apply -f argocd/root/root-platform.yaml
```

### Step 5: Root app creates AppProjects, ApplicationSets, platform apps

```text
root-platform
  ├── appproject-platform
  ├── appproject-payments
  ├── applicationset-cluster-addons
  ├── applicationset-apps-dev
  └── applicationset-apps-prod
```

### Step 6: Argo CD reconciles platform and workloads

```bash
oc get applications -n openshift-gitops
oc get applicationsets -n openshift-gitops
```

## 31. Troubleshooting Repository Structure Problems

### 31.1 Application path is wrong

Symptoms:

```text
ComparisonError
Manifest generation error
app path does not exist
```

Check:

```bash
oc get application payment-api-prod -n openshift-gitops -o yaml | yq '.spec.source.path'
```

Verify path exists:

```bash
git ls-tree -r main --name-only | grep 'apps/payment-api/overlays/prod'
```

---

### 31.2 Kustomize build fails

Symptoms:

```text
kustomize build failed
accumulating resources
no matches for Id
```

Local validation:

```bash
kustomize build apps/payment-api/overlays/prod
```

Common causes:

- Wrong relative path to base.
- Patch references a resource name changed by `namePrefix` or `nameSuffix`.
- Duplicate resource IDs.
- Missing `kustomization.yaml`.
- YAML indentation error.

---

### 31.3 Helm rendering fails

Symptoms:

```text
helm template failed
values file not found
nil pointer evaluating interface
```

Check:

```bash
helm template payment-api apps/payment-api-helm -f apps/payment-api-helm/values-prod.yaml
```

Common causes:

- Wrong values file path.
- Required values missing.
- Template expects a nested key that is absent.
- Chart version changed but values file was not updated.

---

### 31.4 Argo CD deploys too many files

Symptoms:

- Unexpected resources appear in Argo CD.
- Argo CD tries to apply test manifests.
- Documentation or sample YAML gets applied.

Causes:

- `directory.recurse: true` used too broadly.
- No `.argocdignore`.
- Application path points at repository root.
- Plain YAML directory mode used where Kustomize should be used.

Fix:

- Narrow `.spec.source.path`.
- Disable recursion unless needed.
- Use Kustomize with explicit `resources:`.
- Add `.argocdignore` carefully.

---

### 31.5 AppProject blocks sync

Symptoms:

```text
application destination is not permitted in project
source repo is not permitted in project
resource kind is not permitted in project
```

Check:

```bash
oc get appproject payments -n openshift-gitops -o yaml
```

Fix:

- Add the correct source repo.
- Add destination namespace.
- Add required resource kind to whitelist.
- Avoid broad wildcard permissions unless justified.

---

### 31.6 ApplicationSet creates wrong application names

Symptoms:

- Generated app names are wrong.
- Multiple apps collide on the same name.
- Apps point to wrong namespace.

Check generated Applications:

```bash
oc get applications -n openshift-gitops -l generated-by=applicationset
oc get applicationset apps-dev -n openshift-gitops -o yaml
```

Common causes:

- Wrong `path.segments` index.
- Folder name does not follow naming convention.
- Directory glob too broad.
- Missing `goTemplateOptions: ["missingkey=error"]`.

## 32. Production Guardrails Checklist

Use this checklist before declaring your GitOps repository production-ready.

### Repository structure

- [ ] Source code and deployment config are separated.
- [ ] Platform and application resources are separated.
- [ ] Cluster-scoped resources are isolated.
- [ ] Environment overlays are consistent.
- [ ] Directory naming is deterministic and documented.
- [ ] No application points at repository root.
- [ ] No uncontrolled recursive directory scanning.

### Security

- [ ] No plain-text secrets in Git.
- [ ] Secret scanning is enabled.
- [ ] AppProjects are not using broad wildcard permissions.
- [ ] Default AppProject is not used for production apps.
- [ ] SCC, privileged workloads, and cluster RBAC require review.
- [ ] Production changes require approval.
- [ ] Git branch protection is enabled.

### Validation

- [ ] Kustomize overlays render in CI.
- [ ] Helm charts render in CI.
- [ ] `oc apply --dry-run=server` is used where possible.
- [ ] Policy checks block dangerous manifests.
- [ ] Deprecated API versions are blocked.
- [ ] Image tags are immutable or pinned.

### Operations

- [ ] Rollback process is documented.
- [ ] Emergency break-glass process is documented.
- [ ] Root app recovery is documented.
- [ ] Argo CD RBAC recovery is documented.
- [ ] Sync waves are used for dependencies.
- [ ] App health and sync status are monitored.

## 33. Senior-Level Design Recommendations

### 33.1 Keep config repositories clean

Avoid mixing:

- application source code
- test manifests
- screenshots
- large binaries
- generated YAML not meant for deployment
- abandoned old manifests

A GitOps repo should be boring, deterministic, and reviewable.

### 33.2 Do not over-template everything

Over-templating causes operational blindness. If an incident happens at 2 AM, the on-call engineer must understand what Argo CD will apply.

Prefer readable overlays and simple patches over deeply nested templates.

### 33.3 Treat Git paths as security boundaries

An Argo CD `Application` source path controls what gets applied. A broad path is similar to broad RBAC.

Bad:

```yaml
path: .
directory:
  recurse: true
```

Good:

```yaml
path: apps/payment-api/overlays/prod
```

### 33.4 Use AppProjects aggressively

Create AppProjects per team, tenant, or platform domain.

Avoid:

```yaml
sourceRepos:
  - '*'
destinations:
  - namespace: '*'
    server: '*'
clusterResourceWhitelist:
  - group: '*'
    kind: '*'
```

except for tightly controlled bootstrap/testing.

### 33.5 Make production boring

Production should use:

- pinned versions
- reviewed PRs
- protected branches/tags
- explicit namespace ownership
- explicit network policy
- explicit resource requests/limits
- validated manifests
- controlled sync windows where required

## 38. Anti-Patterns

### 38.1 One giant YAML folder

```text
manifests/
├── deployment1.yaml
├── deployment2.yaml
├── route-prod.yaml
├── old-route.yaml
├── secret-test.yaml
├── namespace.yaml
├── clusterrole.yaml
└── random.yaml
```

Problem:

No ownership, no environment boundary, no render boundary, no promotion model.

---

### 38.2 Application and platform resources mixed

```text
apps/payment-api/prod/
├── deployment.yaml
├── service.yaml
├── clusterrolebinding.yaml
├── machineconfig.yaml
└── oauth.yaml
```

Problem:

Application team can change cluster-wide behavior.

---

### 38.3 Production tracking `HEAD` with no protection

```yaml
source:
  targetRevision: HEAD
```

Problem:

Every merge can become production desired state without controlled release semantics.

---

### 38.4 Default AppProject everywhere

Problem:

The default project is often too permissive. It weakens multi-tenancy and makes audit harder.

---

### 38.5 Recursive directory source at repo root

```yaml
path: .
directory:
  recurse: true
```

Problem:

Argo CD may attempt to apply examples, tests, app manifests, platform manifests, and random YAML together.

## 40. Interview / Senior Admin Explanation

If asked in an interview, explain Git repository structure like this:

> In OpenShift GitOps, I design Git repositories around ownership, lifecycle, security boundary, and promotion flow. I keep source code separate from environment configuration. I usually maintain a platform GitOps repo for cluster-wide resources and application GitOps repos or app folders for workload manifests. For applications, I prefer Kustomize base/overlay or Helm chart plus environment values. For multicluster, I use a cluster composition layer under `clusters/<cluster-name>` and generate Applications using App-of-Apps or ApplicationSet. I avoid the default AppProject in production and define AppProjects per tenant/team with explicit source repositories, destination namespaces, and allowed resource kinds. For production, I avoid tracking uncontrolled `HEAD`, avoid `latest` images, validate all rendered manifests in CI, scan for secrets, protect branches, and require approval for cluster-scoped resources, SCC bindings, and RBAC changes.

## 41. Quick Decision Matrix

| Requirement | Recommended structure |
|---|---|
| Small single app | `apps/<app>/base` + `apps/<app>/overlays/<env>` |
| Many apps, same pattern | ApplicationSet Git directory generator |
| Many clusters | `clusters/<cluster>/...` composition layer |
| Platform add-ons | `cluster-addons/<addon>/base` + overlays |
| Strict compliance | repo-per-environment or protected prod folder with CODEOWNERS |
| Simple environment differences | Kustomize overlays |
| Heavy templating | Helm chart + values |
| Secret references | External Secrets / Vault references in Git |
| Encrypted secrets in Git | SealedSecrets or SOPS |
| New cluster bootstrap | root app / app-of-apps / ApplicationSet |
| Multi-tenant Argo CD | AppProject per tenant/team |

## 42. Final Best-Practice Summary

A production-grade OpenShift GitOps repository should be:

- **Declarative:** Git contains desired state, not manual instructions.
- **Separated:** Source code, application config, and platform config are not mixed randomly.
- **Composable:** Common base config is reused through Kustomize, Helm, or structured packages.
- **Secure:** Secrets are never committed in plain text, and AppProjects restrict blast radius.
- **Auditable:** Production changes happen through protected branches, PRs, and clear ownership.
- **Validated:** CI renders and validates manifests before merge.
- **Promotable:** Dev, stage, and prod promotion is explicit and reversible.
- **Recoverable:** Bootstrap and rollback procedures are documented.
- **OpenShift-aware:** Namespaces, quotas, NetworkPolicy, SCC, routes, operators, and cluster-scoped resources are structured intentionally.

For a 10-year OpenShift administrator, the goal is not simply to make Argo CD sync. The goal is to design a repository structure that supports safe operations, clear ownership, fast troubleshooting, controlled production change, and repeatable cluster/application delivery.
