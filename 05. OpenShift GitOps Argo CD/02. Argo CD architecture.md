# Argo CD Architecture in Red Hat OpenShift GitOps

**Audience:** Advanced OpenShift Administration / senior platform engineer level  
**Experience target:** ~10 years Linux, DevOps, Kubernetes, OpenShift administration  
**Focus area:** OpenShift GitOps, Argo CD architecture, control loops, security, HA, multi-tenancy, operations, and troubleshooting  
**Generated on:** 2026-07-03

---

## 1. Executive Summary

Argo CD is a declarative GitOps continuous delivery controller for Kubernetes and OpenShift. In OpenShift, it is delivered as **Red Hat OpenShift GitOps**, an Operator-managed product that installs and reconciles Argo CD components using Kubernetes Custom Resources.

At enterprise level, Argo CD should not be understood only as a deployment UI. It is a **control-plane system** that continuously compares:

```text
Desired state  = Git / Helm / Kustomize / Jsonnet / OCI source
Live state     = Kubernetes or OpenShift cluster resources
```

When drift is detected, Argo CD marks the application as **OutOfSync** and can either wait for manual sync or automatically reconcile the live cluster back to Git.

In OpenShift GitOps, the architecture has three major layers:

```text
+-------------------------------------------------------------+
| OpenShift GitOps Operator                                   |
| - Watches ArgoCD CRs                                        |
| - Creates Argo CD control-plane components                  |
| - Reconciles config, RBAC, Routes, workloads, secrets       |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
| Argo CD Control Plane                                       |
| - argocd-server                                             |
| - argocd-application-controller                             |
| - argocd-repo-server                                        |
| - argocd-applicationset-controller                          |
| - argocd-redis / redis-ha                                   |
| - argocd-dex-server or external OIDC integration            |
| - notifications controller                                  |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
| Managed OpenShift/Kubernetes Resources                      |
| - Deployments, StatefulSets, Routes, Services, ConfigMaps   |
| - Operators, Subscriptions, RBAC, NetworkPolicies, CRDs     |
| - Namespace-scoped or cluster-scoped resources              |
+-------------------------------------------------------------+
```

A senior administrator must understand the **component responsibilities**, **service account permissions**, **namespace scope**, **resource tracking**, **sync workflow**, **repository rendering pipeline**, **HA limitations**, and **multi-tenant security model**.

## 2. What Problem Argo CD Solves

Traditional deployment often depends on imperative actions:

```bash
oc apply -f deployment.yaml
helm upgrade --install app ./chart
kubectl patch deployment app ...
```

This creates questions:

- Who changed the cluster?
- Is the cluster still matching source control?
- Which version is deployed?
- Can we roll back safely?
- Can we prove configuration history?
- Can developers deploy without direct cluster-admin access?

Argo CD changes the operating model:

```text
Git becomes the source of truth.
Argo CD becomes the reconciler.
The cluster becomes the runtime target.
```

Instead of directly changing the cluster, teams change Git. Argo CD observes Git, renders manifests, compares them with the cluster, and applies changes.

## 3. Core GitOps Flow

### 3.1 High-Level Flow

```text
Developer / Platform Engineer
        |
        | 1. Commit manifests, Helm chart values, or Kustomize overlays
        v
Git Repository
        |
        | 2. Argo CD polls Git or receives webhook
        v
argocd-repo-server
        |
        | 3. Clone/fetch repo and render desired manifests
        v
argocd-application-controller
        |
        | 4. Compare desired state with live OpenShift state
        v
OpenShift Kubernetes API
        |
        | 5. Sync if manual/auto-sync is triggered
        v
OpenShift Resources
```

### 3.2 Reconciliation Logic

Argo CD constantly performs these actions:

1. Read the `Application` custom resource.
2. Identify the Git/Helm/Kustomize source.
3. Ask the repo-server to render the manifests.
4. Read the live objects from the Kubernetes API.
5. Compare desired vs live state.
6. Calculate sync status:
   - `Synced`
   - `OutOfSync`
   - `Unknown`
7. Calculate health status:
   - `Healthy`
   - `Progressing`
   - `Degraded`
   - `Suspended`
   - `Missing`
   - `Unknown`
8. Apply changes when sync is triggered.
9. Prune resources when enabled and when objects are removed from Git.
10. Self-heal live drift when enabled.

## 4. OpenShift GitOps vs Upstream Argo CD

### 4.1 Upstream Argo CD

Upstream Argo CD provides the GitOps engine:

- API server
- Web UI
- CLI API
- Application controller
- Repo server
- Redis cache
- Dex integration
- ApplicationSet controller
- Notifications controller
- CRDs such as `Application`, `AppProject`, and `ApplicationSet`

### 4.2 Red Hat OpenShift GitOps

Red Hat OpenShift GitOps packages Argo CD as an OpenShift Operator-supported product.

It adds OpenShift-specific integration:

- Operator Lifecycle Manager installation
- `ArgoCD` custom resource management
- Default Argo CD instance in `openshift-gitops`
- OpenShift Route integration
- OpenShift OAuth / Dex integration depending on cluster authentication mode
- OpenShift RBAC integration
- Namespace-scoped and cluster-scoped Argo CD instance models
- OpenShift SCC and Pod Security integration
- Supportability through Red Hat product lifecycle
- OpenShift console integration
- Declarative control of Argo CD component settings through CR fields

### 4.3 Key Architectural Difference

In upstream installation, administrators often manage YAML manifests directly.

In OpenShift GitOps, administrators normally manage this object:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  # desired Argo CD platform configuration
```

The OpenShift GitOps Operator reads this `ArgoCD` CR and creates or updates the actual Argo CD workloads.

## 5. Main Argo CD Components

## 5.1 OpenShift GitOps Operator

The OpenShift GitOps Operator is the lifecycle manager for Argo CD on OpenShift.

### Responsibilities

- Watches `ArgoCD` custom resources.
- Creates Argo CD Deployments, StatefulSets, Services, Routes, ConfigMaps, Secrets, and RBAC.
- Reconciles component configuration from the `ArgoCD` CR.
- Handles upgrades of managed Argo CD components.
- Creates default cluster-scoped Argo CD instance in `openshift-gitops` after installation.
- Supports namespace-scoped Argo CD instances for tenant teams.
- Manages some OpenShift-specific integration, such as Routes and OAuth/Dex configuration.

### Important Commands

```bash
oc get pods -n openshift-gitops-operator
oc get subscription -n openshift-gitops-operator
oc get csv -n openshift-gitops-operator
oc describe deployment openshift-gitops-operator-controller-manager -n openshift-gitops-operator
```

### Senior Admin Note

Do not manually edit Operator-owned Deployments unless you are troubleshooting temporarily. The Operator will revert many changes. Permanent configuration should be done through:

```bash
oc edit argocd <name> -n <argocd-namespace>
```

or through Git-managed `ArgoCD` CR manifests.

## 5.2 ArgoCD Custom Resource

The `ArgoCD` custom resource describes the desired state of an Argo CD instance.

Example:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: platform-gitops
  namespace: platform-gitops
spec:
  server:
    route:
      enabled: true
    replicas: 2
  repo:
    replicas: 2
  ha:
    enabled: true
  applicationSet:
    enabled: true
  controller:
    processors:
      status: 50
      operation: 25
  resourceTrackingMethod: annotation
```

### What It Controls

Depending on version and support level, the CR can configure:

- Argo CD server settings
- Repo server settings
- Application controller settings
- ApplicationSet controller
- Notifications controller
- Dex / OIDC
- HA mode
- Redis HA
- RBAC
- TLS certificates
- custom CA trust
- node placement
- resource limits
- logging
- config management plugins
- resource tracking behavior
- network policies
- source namespaces
- namespace management

### One ArgoCD CR Per Namespace

In OpenShift GitOps, an Argo CD instance is represented by one `ArgoCD` CR in a namespace. Practically, treat one namespace as one Argo CD control-plane boundary.

## 5.3 argocd-server

`argocd-server` is the API and UI front end.

### Responsibilities

- Serves the Argo CD web UI.
- Exposes the Argo CD API used by the CLI.
- Handles user login and session creation.
- Integrates with Dex or external OIDC.
- Enforces Argo CD RBAC for UI/API requests.
- Talks to Kubernetes API to read Argo CD CRs.
- Talks to Redis for cache/session-related behavior.
- Exposes gRPC/REST endpoints.

### OpenShift Objects

Typical resources:

```bash
oc get deployment -n openshift-gitops | grep server
oc get svc -n openshift-gitops | grep server
oc get route -n openshift-gitops
```

Example:

```bash
oc get route openshift-gitops-server -n openshift-gitops
```

### Traffic Flow

```text
Browser / argocd CLI
        |
        v
OpenShift Route
        |
        v
argocd-server Service
        |
        v
argocd-server Pod
        |
        +--> Kubernetes API
        +--> Redis
        +--> Dex / OIDC provider
        +--> Application Controller indirectly through API state
```

### Failure Symptoms

| Symptom | Possible Cause |
|---|---|
| Argo CD UI not opening | Route, service, pod, TLS, OAuth/Dex issue |
| Login loop | OIDC/Dex callback misconfiguration |
| CLI cannot login | Route TLS, grpc-web requirement, bad password/token |
| Applications visible but not syncing | Server is healthy but controller/repo-server may be unhealthy |

### Useful Commands

```bash
oc logs deployment/openshift-gitops-server -n openshift-gitops
oc describe route openshift-gitops-server -n openshift-gitops
oc get endpoints openshift-gitops-server -n openshift-gitops
```

CLI login example:

```bash
ARGOCD_ROUTE=$(oc get route openshift-gitops-server -n openshift-gitops -o jsonpath='{.spec.host}')
argocd login "$ARGOCD_ROUTE" --sso --grpc-web
```

For local admin password:

```bash
oc get secret openshift-gitops-cluster -n openshift-gitops \
  -o jsonpath='{.data.admin\.password}' | base64 -d; echo
```

Secret names can vary depending on the instance name.

## 5.4 argocd-application-controller

The `argocd-application-controller` is the heart of Argo CD. It is the reconciliation engine.

### Responsibilities

- Watches `Application` resources.
- Watches `AppProject` resources.
- Compares desired manifests with live cluster state.
- Calculates application sync status.
- Calculates resource health status.
- Performs sync operations.
- Performs pruning when enabled.
- Performs self-healing when enabled.
- Manages finalizers for application deletion behavior.
- Uses destination cluster credentials stored as Kubernetes Secrets.
- Calls `argocd-repo-server` to generate manifests.
- Talks to Kubernetes API servers for managed clusters.

### Control Loop

```text
Application CR changed or refresh interval reached
        |
        v
Controller loads Application spec
        |
        v
Controller validates AppProject restrictions
        |
        v
Controller requests manifests from repo-server
        |
        v
Controller lists live resources from cluster API
        |
        v
Diff desired vs live
        |
        +--> update status only
        |
        +--> sync resources if sync requested / auto-sync enabled
```

### Controller Queues

The controller has separate queues for:

- status reconciliation
- operation/sync processing

For large environments, tuning these matters:

```yaml
spec:
  controller:
    processors:
      status: 50
      operation: 25
```

### Senior Admin Note

If Argo CD UI works but apps are stuck in `Unknown`, `OutOfSync`, or sync does not start, always inspect the application controller logs first:

```bash
oc logs statefulset/openshift-gitops-application-controller -n openshift-gitops
```

For large multi-cluster setups, controller sharding may be required:

```yaml
spec:
  controller:
    sharding:
      enabled: true
      replicas: 3
```

Dynamic sharding can be used where supported by the OpenShift GitOps version:

```yaml
spec:
  controller:
    sharding:
      dynamicScalingEnabled: true
      minShards: 2
      maxShards: 10
      clustersPerShard: 10
```

## 5.5 argocd-repo-server

The `argocd-repo-server` is responsible for repository access and manifest generation.

### Responsibilities

- Clones Git repositories.
- Fetches repository updates.
- Resolves branches, tags, and commits.
- Renders manifests using:
  - plain YAML
  - Kustomize
  - Helm
  - Jsonnet
  - Config Management Plugins
  - OCI sources where configured
- Maintains local repository cache.
- Returns rendered manifests to the application controller.

### Flow

```text
Application Controller
        |
        | manifest generation request
        v
Repo Server
        |
        +--> Git repo
        +--> Helm repo
        +--> OCI registry
        +--> Kustomize build
        +--> Helm template
        +--> Config Management Plugin
        |
        v
Rendered Kubernetes/OpenShift YAML
```

### Why Repo Server Is Security Sensitive

Repo server executes manifest-generation tools such as `helm template`, `kustomize build`, and plugins. A malicious Git repo can attempt to abuse templating behavior, remote bases, Helm hooks, or plugins.

Hardening recommendations:

- Use trusted repositories only.
- Restrict AppProjects to known repositories.
- Avoid wildcard `sourceRepos: ['*']` in production.
- Pin Helm chart versions.
- Avoid running unnecessary plugins.
- Use separate Argo CD instances for high-risk tenants.
- Configure custom CA trust through supported CR fields instead of manual pod modification.
- Apply resource requests/limits to repo-server.
- Use persistent volume for repo-server cache if repositories are large.

### Common Repo Server Problems

| Problem | Example Error | Root Cause |
|---|---|---|
| Git auth failure | authentication required | Missing repo secret or token |
| TLS failure | x509 unknown authority | Missing custom CA |
| Helm failure | chart not found | Wrong repo URL or chart version |
| Kustomize failure | accumulation error | Bad overlay/base path |
| Timeout | context deadline exceeded | Heavy Helm/Kustomize rendering |
| OOMKilled | repo-server restarted | Large repo, too much parallelism |
| Disk pressure | no space left on device | Too many repo clones in `/tmp` |

### Useful Commands

```bash
oc logs deployment/openshift-gitops-repo-server -n openshift-gitops
oc describe pod -l app.kubernetes.io/name=openshift-gitops-repo-server -n openshift-gitops
oc adm top pod -n openshift-gitops
```

### Repo Server Scaling

```yaml
spec:
  repo:
    replicas: 2
    resources:
      requests:
        cpu: "500m"
        memory: "1Gi"
      limits:
        cpu: "2"
        memory: "4Gi"
```

For monorepos, scaling repo-server alone may not solve all performance problems because Git operations and manifest rendering can still bottleneck on cache behavior and repo size.

## 5.6 Redis

Redis is used as a cache layer.

### Responsibilities

- Reduces repeated Kubernetes API and Git provider calls.
- Caches application tree/resource data.
- Supports UI operations and state lookup.
- Improves API responsiveness.

### Important Point

Argo CD persists desired state and operational state mainly in Kubernetes resources and etcd. Redis is considered disposable cache. Losing Redis should not destroy Argo CD applications, but it can temporarily affect performance or UI behavior while cache rebuilds.

### HA Mode

In HA mode, OpenShift GitOps can deploy Redis HA components such as Redis HAProxy and Redis server StatefulSets, depending on version and CR configuration.

```yaml
spec:
  ha:
    enabled: true
```

### Troubleshooting

```bash
oc get pods -n openshift-gitops | grep redis
oc logs deployment/openshift-gitops-redis -n openshift-gitops
oc logs statefulset/openshift-gitops-redis-server -n openshift-gitops
```

## 5.7 Dex / OIDC Authentication Component

Dex is an identity broker commonly used by Argo CD for SSO.

### Responsibilities

- Integrates Argo CD with identity providers.
- Handles OAuth2/OIDC login flow.
- Maps identity provider claims/groups into Argo CD RBAC decisions.

### OpenShift Integration

In many OpenShift GitOps deployments, Argo CD login integrates with OpenShift OAuth through Dex. In newer OpenShift authentication models, especially where external authentication is enabled at the cluster level, external OIDC may need to be configured directly in the `ArgoCD` CR.

### Typical Login Flow

```text
User opens Argo CD UI
        |
        v
argocd-server redirects to Dex/OIDC
        |
        v
Identity provider authenticates user
        |
        v
User receives token
        |
        v
argocd-server evaluates RBAC
        |
        v
UI/API access granted or denied
```

### Troubleshooting

```bash
oc logs deployment/openshift-gitops-dex-server -n openshift-gitops
oc get cm openshift-gitops-cm -n openshift-gitops -o yaml
oc get secret -n openshift-gitops | grep dex
```

Common issues:

- Callback URL mismatch
- Wrong issuer URL
- Invalid client secret
- Missing group claim
- RBAC policy does not map provider group
- OAuth route/certificate problem

## 5.8 ApplicationSet Controller

ApplicationSet is used to generate many Argo CD `Application` objects from templates.

### Use Cases

- Deploy same app to many clusters.
- Deploy many apps from one Git repository.
- Deploy environment overlays automatically.
- Generate apps per team, namespace, or cluster label.
- Fleet management.

### Common Generators

- List generator
- Git directory generator
- Git file generator
- Cluster generator
- Matrix generator
- Merge generator
- Pull request generator
- SCM provider generator

### Architecture

```text
ApplicationSet CR
        |
        v
ApplicationSet Controller
        |
        | renders template for each generator output
        v
Multiple Application CRs
        |
        v
Application Controller reconciles each Application
```

### Example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-addons
  namespace: openshift-gitops
spec:
  generators:
  - clusters: {}
  template:
    metadata:
      name: '{{name}}-logging'
    spec:
      project: platform
      source:
        repoURL: https://git.example.com/platform/addons.git
        targetRevision: main
        path: logging/overlays/{{metadata.labels.env}}
      destination:
        server: '{{server}}'
        namespace: openshift-logging
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

### Senior Admin Warning

ApplicationSet can create or delete many Applications quickly. A wrong generator pattern can impact many clusters. Protect it with:

- AppProject restrictions
- code review
- protected branches
- progressive sync where available
- sync windows
- separate staging validation

## 6. Argo CD Kubernetes Custom Resources

## 6.1 Application

The `Application` CR defines one deployable unit.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-prod
  namespace: openshift-gitops
spec:
  project: app-team
  source:
    repoURL: https://git.example.com/apps/nginx.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
    - CreateNamespace=true
```

### Important Fields

| Field | Meaning |
|---|---|
| `spec.project` | AppProject boundary/policy |
| `spec.source.repoURL` | Git/Helm/OCI source |
| `spec.source.targetRevision` | branch, tag, commit, chart version |
| `spec.source.path` | manifest path for Git source |
| `spec.destination.server` | target cluster API URL |
| `spec.destination.name` | named cluster destination |
| `spec.destination.namespace` | target namespace |
| `spec.syncPolicy.automated` | auto-sync behavior |
| `prune` | delete live resources removed from Git |
| `selfHeal` | revert manual live drift |
| `syncOptions` | advanced apply behavior |

---

## 6.2 AppProject

`AppProject` is one of the most important security boundaries in Argo CD.

### What AppProject Controls

- Which Git repositories are allowed.
- Which clusters and namespaces are allowed.
- Which resource kinds can be deployed.
- Which cluster-scoped resources are allowed or denied.
- Project-specific RBAC roles.
- Sync windows.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: app-team
  namespace: openshift-gitops
spec:
  description: Application team controlled project
  sourceRepos:
  - https://git.example.com/apps/*
  destinations:
  - namespace: app-team-*
    server: https://kubernetes.default.svc
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
  - group: apps
    kind: Deployment
  - group: ""
    kind: Service
  - group: route.openshift.io
    kind: Route
  roles:
  - name: developer
    description: App team deploy role
    policies:
    - p, proj:app-team:developer, applications, get, app-team/*, allow
    - p, proj:app-team:developer, applications, sync, app-team/*, allow
    groups:
    - app-team-developers
```

### Production Recommendation

Avoid using the default project for real production workloads. Create explicit AppProjects per team, platform domain, or environment.

Bad pattern:

```yaml
sourceRepos:
- '*'
destinations:
- namespace: '*'
  server: '*'
clusterResourceWhitelist:
- group: '*'
  kind: '*'
```

Better pattern:

```yaml
sourceRepos:
- https://git.example.com/app-team/*
destinations:
- namespace: app-team-prod
  server: https://kubernetes.default.svc
clusterResourceWhitelist: []
```

## 7. Resource Tracking Architecture

Argo CD must know which live Kubernetes objects belong to which Application.

### Tracking Methods

Common tracking methods include:

- label-based tracking
- annotation-based tracking
- annotation + label tracking

Historically, many installs used:

```text
app.kubernetes.io/instance=<application-name>
```

Modern designs often prefer annotation-based tracking to avoid conflicts with Helm and other tools that also use `app.kubernetes.io/instance`.

Example CR setting:

```yaml
spec:
  resourceTrackingMethod: annotation
```

### Why This Matters

Resource tracking conflicts can cause:

- resources appearing under the wrong app
- pruning the wrong object
- orphaned resources
- sync status confusion
- Helm label collision

### Senior Admin Best Practice

For multi-tenant OpenShift GitOps, use annotation-based tracking where supported and keep naming conventions clean:

```text
<team>-<app>-<env>
```

Example:

```text
payments-api-prod
payments-api-stage
platform-logging-prod
```

## 8. Sync Architecture

## 8.1 Manual Sync

In manual mode, Argo CD detects drift but does not apply changes until a user or automation triggers sync.

```yaml
syncPolicy: {}
```

Good for:

- production approval workflows
- high-risk infrastructure changes
- regulated environments

---

## 8.2 Automated Sync

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

### Automated Sync Behavior

| Option | Meaning |
|---|---|
| `automated` | Sync automatically when Git changes |
| `prune` | Delete resources removed from Git |
| `selfHeal` | Revert manual cluster drift |
| `allowEmpty` | Allow app to have no resources; dangerous if misused |

### Senior Admin Warning

`prune: true` is powerful. If a Git path becomes empty due to branch mistake, generator bug, or repo restructuring, Argo CD may delete live resources if `allowEmpty` and prune behavior permit it.

Use:

- branch protection
- CODEOWNERS
- CI manifest validation
- separate AppProjects
- sync windows
- staged rollout

---

## 8.3 Sync Phases and Hooks

Argo CD supports sync hooks using annotations:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/hook: PreSync
```

Hook phases:

- `PreSync`
- `Sync`
- `PostSync`
- `SyncFail`
- `PostDelete`
- `Skip`

Example migration Job:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migrate
        image: registry.example.com/app/db-migrate:1.0
```

---

## 8.4 Sync Waves

Sync waves control ordering inside a sync phase.

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

Example ordering:

```text
Wave -10: Namespaces
Wave -5 : OperatorGroup / Subscription
Wave 0  : ConfigMaps / Secrets
Wave 5  : Services / PVCs
Wave 10 : Deployments / StatefulSets
Wave 20 : Routes / Ingress
Wave 30 : Post-deployment Jobs
```

### OpenShift Example

```yaml
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: myapp-prod
  annotations:
    argocd.argoproj.io/sync-wave: "-10"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: myapp-prod
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

## 9.2 Cluster-Scoped vs Namespace-Scoped Instances

OpenShift GitOps supports different Argo CD instance scopes.

### Namespace-Scoped Instance

A namespace-scoped Argo CD instance initially manages only its own namespace.

Good for:

- application delivery teams
- tenant isolation
- limited blast radius
- self-service GitOps

Limitations:

- cannot manage cluster-scoped resources such as CRDs, ClusterRoles, Namespaces, unless explicitly elevated or handled by a cluster-scoped instance
- requires namespace labeling or namespace management to deploy into other namespaces

### Cluster-Scoped Instance

A cluster-scoped instance can manage resources across the cluster.

Good for:

- cluster configuration
- Operators
- namespaces
- RBAC
- shared platform resources
- infrastructure add-ons

Risk:

- application teams using a cluster-scoped instance can indirectly gain powerful access if AppProjects and RBAC are weak

### Default Cluster-Scoped Instance

The default `openshift-gitops` instance is opinionated and primarily useful for cluster administrators.

## 10. RBAC Architecture

Argo CD security has two layers:

```text
1. Kubernetes/OpenShift RBAC
   - What the Argo CD service account can do in the cluster

2. Argo CD RBAC
   - What a logged-in Argo CD user can do through Argo CD
```

These are separate.

A user might not have direct Kubernetes permission to update Deployments, but if Argo CD RBAC allows them to sync an Application and the Argo CD controller service account has deployment permissions, the user can indirectly change the cluster through Argo CD.

---

## 10.1 Kubernetes/OpenShift RBAC

The application controller uses Kubernetes credentials to deploy resources.

For in-cluster deployments:

```bash
oc get sa -n openshift-gitops
oc get clusterrolebinding | grep gitops
oc get rolebinding -A | grep gitops
```

For managed namespaces, inspect:

```bash
oc auth can-i create deployment \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n myapp-prod
```

Service account names may vary by Argo CD instance name.

## 10.2 Argo CD RBAC

Argo CD RBAC is normally configured in `argocd-rbac-cm` or through the `ArgoCD` CR depending on the OpenShift GitOps version and pattern.

Example policy:

```csv
p, role:platform-admin, clusters, get, *, allow
g, openshift-platform-admins, role:platform-admin
```

Common Argo CD resources for RBAC:

- `applications`
- `clusters`
- `repositories`
- `projects`
- `accounts`
- `exec`
- `logs`

Common actions:

- `get`
- `create`
- `update`
- `delete`
- `sync`
- `override`
- `action/*`

### Pros

- central control plane
- single UI
- simple for small fleet

### Cons

- network/firewall complexity

## 13. Argo CD Agent Architecture

OpenShift GitOps also documents Argo CD Agent architecture for advanced multi-cluster management.

### Concept

Argo CD Agent uses a hub-and-spoke model.

```text
Control Plane Cluster / Hub
        |
        | Principal agent + Argo CD UI visibility
        v
Workload Cluster / Spoke 1
        - local Argo CD instance
        - local agent
        - local reconciliation

Workload Cluster / Spoke 2
        - local Argo CD instance
        - local agent
        - local reconciliation
```

### Traditional Push vs Agent Pull

| Area | Traditional Argo CD | Argo CD Agent |
|---|---|---|
| Reconciliation location | central Argo CD | local cluster Argo CD |
| Cluster API access | hub needs API access to spokes | local agent/Argo CD handles local cluster |
| Credential exposure | hub stores cluster credentials | reduced central credential exposure |
| Scalability | central controller can bottleneck | distributed per workload cluster |
| Failure domain | central outage affects many clusters | cluster-local reconciliation continues |
| Complexity | simpler initially | more complex but better for large/firewalled fleets |

### Agent Modes

#### Managed Mode

- Application specs originate from the control plane.
- Workload clusters receive the desired Application specs.
- Control plane is the source of truth for Application `.spec`.

#### Autonomous Mode

- Application specs originate on workload clusters.
- Control plane provides central visibility.
- Workload cluster owns its own desired state.

### Security

Agent architecture uses mTLS between principal and workload agents. It reduces the need for the hub to store direct workload cluster API credentials.

### When to Use

Use Agent architecture when:

- clusters are behind firewalls
- direct API access from hub is not possible
- large fleet scale creates controller pressure
- security policy discourages central storage of all cluster credentials
- each cluster should reconcile locally

Avoid it initially when:

- your team is new to Argo CD
- only one or two clusters exist
- traditional hub-spoke is sufficient
- operational maturity is low

## 14. High Availability Architecture

Argo CD is mostly stateless; desired state is stored in Kubernetes resources and etcd. Still, the control plane needs HA for UI/API, repo rendering, and reconciliation availability.

### HA Components

Typical HA design includes:

- multiple `argocd-server` replicas
- multiple `argocd-repo-server` replicas
- HA Redis
- application controller sharding or HA mode depending on configuration
- pod anti-affinity across nodes
- sufficient CPU/memory
- monitoring and alerting

Example:

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  ha:
    enabled: true
  server:
    replicas: 2
  repo:
    replicas: 2
```

### Node Requirements

HA deployments should run across multiple nodes. Anti-affinity rules may require at least three schedulable nodes for full HA placement.

### What HA Does Not Solve

HA does not fix:

- bad Git commits
- wrong AppProject permissions
- broken Helm charts
- invalid OpenShift manifests
- insufficient service account permissions
- API server rate limits
- large monorepo rendering bottlenecks without tuning

## 16. Network Security Architecture

OpenShift GitOps 1.20 introduced network policies for core Argo CD workload pods to support least-privilege network posture.

### Typical Required Traffic

```text
User Browser/CLI -> OpenShift Route -> argocd-server
argocd-server -> Dex/OIDC
argocd-server -> Redis
argocd-application-controller -> repo-server
argocd-application-controller -> Kubernetes API
argocd-repo-server -> Git/Helm/OCI repositories
application-controller -> destination cluster APIs
notifications-controller -> external webhook/chat/email systems
```

### Secure Network Design

Restrict:

- ingress to Argo CD UI/API
- repo-server egress only to approved Git/Helm/OCI sources
- controller egress only to Kubernetes APIs it manages
- Redis access only from Argo CD components
- Dex/OIDC endpoints only as needed

### Example Egress Concept

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: repo-server-egress-git-only
  namespace: openshift-gitops
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: openshift-gitops-repo-server
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector: {}
    ports:
    - protocol: TCP
      port: 443
```

Adjust labels and CIDRs to your actual environment.

## 22. Troubleshooting Architecture

## 22.1 Application Is OutOfSync

Check:

```bash
oc get application <app> -n openshift-gitops -o yaml
argocd app diff <app>
argocd app get <app>
```

Possible causes:

- Git desired state changed
- manual cluster drift
- defaulted fields in Kubernetes API
- mutating admission controller changed object
- OpenShift Operator mutated resource
- ignored differences not configured

### Fix Options

- sync app
- revert Git change
- configure ignore differences for expected controller-mutated fields
- avoid managing fields owned by another Operator

---

## 22.2 Application Sync Fails

Check:

```bash
argocd app get <app>
argocd app history <app>
argocd app logs <app>
oc describe application <app> -n openshift-gitops
```

Common causes:

| Error | Cause |
|---|---|
| permission denied | Argo CD service account lacks RBAC |
| namespace not found | namespace missing or CreateNamespace not enabled |
| resource not found for kind | CRD missing |
| admission denied | SCC, policy, quota, limit range, validating webhook |
| immutable field | Kubernetes object field cannot be changed |
| timed out waiting for health | deployment/pod not becoming healthy |

---

## 22.3 Repo Server Manifest Generation Fails

```bash
oc logs deployment/openshift-gitops-repo-server -n openshift-gitops
argocd app manifests <app>
```

Check:

- repo URL
- credentials
- branch/tag
- path
- Helm values file
- Kustomize base path
- TLS CA
- plugin sidecar
- resource limits

---

## 22.4 Permission Problem

Use `oc auth can-i` as the Argo CD controller service account.

```bash
oc auth can-i create deployments.apps \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n myapp-prod
```

Check AppProject too:

```bash
oc get appproject <project> -n openshift-gitops -o yaml
```

Remember: Kubernetes RBAC and AppProject restrictions can both block deployment.

---

## 22.5 Application Stuck Deleting

Common cause: finalizer.

```bash
oc get application <app> -n openshift-gitops -o yaml | grep finalizers -A5
```

Argo CD finalizer:

```yaml
resources-finalizer.argocd.argoproj.io
```

It tells Argo CD to delete managed resources during app deletion.

Emergency removal:

```bash
oc patch application <app> -n openshift-gitops \
  --type=json \
  -p='[{"op":"remove","path":"/metadata/finalizers"}]'
```

Use only when you understand orphaning impact.

## 25. Security Best Practices

1. Disable or tightly control the built-in `admin` account.
2. Use SSO/OIDC integrated with enterprise identity.
3. Use groups, not individual users, in RBAC.
4. Use AppProjects for every team/environment.
5. Avoid wildcard source repos and destinations.
6. Avoid wildcard cluster resource permissions.
7. Use separate Argo CD instances for strong tenant isolation.
8. Protect Git branches with reviews and CI checks.
9. Do not store plaintext secrets in Git.
10. Pin chart versions and validate manifests before merge.
11. Restrict repo-server egress to trusted endpoints.
12. Configure custom CA trust declaratively.
13. Use annotation-based resource tracking where appropriate.
14. Monitor application health and sync status.
15. Keep Operator and Argo CD versions patched.
16. Test auto-prune behavior in non-production first.
17. Use sync windows for production freeze periods.
18. Audit who can modify `Application`, `ApplicationSet`, and `AppProject` resources.
19. Separate platform GitOps from application GitOps.
20. Treat Argo CD service account permissions as highly privileged.

---

## 26. Common Anti-Patterns

### Anti-Pattern 1: One Argo CD for Everyone with Cluster Admin

Problem:

```text
All teams use default openshift-gitops instance with broad permissions.
```

Risk:

- privilege escalation
- accidental cluster-wide deletion
- no tenant boundary

Better:

- separate instances
- strict AppProjects
- namespace-scoped delivery

---

### Anti-Pattern 2: Wildcard AppProject

Bad:

```yaml
sourceRepos:
- '*'
destinations:
- namespace: '*'
  server: '*'
clusterResourceWhitelist:
- group: '*'
  kind: '*'
```

This is effectively Git-driven cluster-admin access.

---

### Anti-Pattern 3: Managing Operator-Owned Fields

OpenShift Operators mutate and own many resources. If Argo CD tries to manage fields that another Operator constantly changes, you get endless drift.

Fix:

- manage the Operator CR, not its generated resources
- configure ignore differences for known mutated fields
- avoid managing generated resources directly

---

### Anti-Pattern 4: Auto-Prune Without Guardrails

Auto-prune is useful but dangerous.

Guardrails:

- branch protection
- required review
- CI manifest validation
- staged sync
- AppProject restrictions
- backups for critical resources

## 28. Interview-Level Explanation

If asked, “Explain Argo CD architecture in OpenShift GitOps,” answer like this:

> Red Hat OpenShift GitOps packages Argo CD as an Operator-managed GitOps control plane. The OpenShift GitOps Operator watches ArgoCD custom resources and creates the Argo CD components such as argocd-server, repo-server, application-controller, Redis, Dex/OIDC integration, ApplicationSet controller, and notifications controller. The repo-server fetches Git, Helm, Kustomize, Jsonnet, or plugin sources and renders manifests. The application-controller compares those desired manifests with live cluster state through the Kubernetes API, updates sync and health status, and performs sync, prune, and self-heal operations according to the Application and AppProject policies. The server exposes UI/API access through an OpenShift Route and enforces Argo CD RBAC. Redis is used as a cache. In OpenShift, security and multi-tenancy depend heavily on Kubernetes RBAC, Argo CD RBAC, AppProjects, namespace-scoped versus cluster-scoped instances, and namespace management. For scale, we tune repo-server, controller processors, HA, Redis HA, and controller sharding. For multi-cluster, Argo CD can use a traditional central push model or the newer Argo CD Agent hub-and-spoke model where workload clusters reconcile locally.

- [ ] Namespace-scoped instances used for tenants where possible.
- [ ] Cluster-scoped instance access limited to platform admins.
- [ ] Git branch protection enabled.
- [ ] Secrets not stored in plaintext.
- [ ] Repo-server egress controlled.
- [ ] Custom CA trust configured declaratively.
- [ ] NetworkPolicy reviewed.

### Operations

- [ ] Sync waves used for ordered resources.
- [ ] Operator CRDs applied before CRs.
- [ ] Auto-prune tested before production use.
- [ ] Rollback process documented.
- [ ] Application deletion/finalizer behavior understood.
- [ ] Disaster recovery process documented.
- [ ] Upgrade process tested.

### Scale

- [ ] Repo-server sized for repo count and manifest complexity.
- [ ] Controller processors tuned.
- [ ] Controller sharding considered for many clusters.
- [ ] ApplicationSet generator blast radius reviewed.
- [ ] Large monorepos optimized or split.

## 31. Quick Mental Model

Remember Argo CD architecture like this:

```text
server       = UI/API/auth/RBAC entry point
repo-server  = Git/Helm/Kustomize rendering engine
controller   = reconciliation and sync brain
redis        = cache
appset       = Application factory
dex/oidc     = login bridge
operator     = OpenShift lifecycle manager
appproject   = security boundary
application  = deployment intent
```

The most important production question is not “Can Argo CD deploy?”

The important question is:

```text
Who can make Argo CD deploy what, from where, to which cluster/namespace, using which service account permissions, and with what blast radius?
```

That is the mindset of an advanced OpenShift administrator.
