## 1. What is the Prune option?

In Argo CD, **pruning** means deleting Kubernetes/OpenShift resources from the cluster when those resources are no longer present in the desired state stored in Git.

In simple words:

```text
Git says the resource should not exist anymore.
Cluster still has the resource.
Argo CD marks it as extraneous / OutOfSync.
Prune deletes it from the cluster.
```

Example:

You previously had this file in Git:

```text
apps/payment/base/route.yaml
```

It created this OpenShift Route:

```text
Route/payment-route
```

Later, you remove `route.yaml` from Git. The Route still exists in OpenShift. Argo CD detects that the Route is no longer part of the desired manifests. If pruning is enabled during sync, Argo CD deletes that Route.

---

## 2. Why pruning exists in GitOps

GitOps is based on the idea that Git is the source of truth.

That means Git should define:

- what should be created,
- what should be updated,
- what should remain,
- and what should be removed.

Without pruning, GitOps is incomplete.

### Without prune

```text
Resource removed from Git  --->  Resource remains in OpenShift
```

This creates orphaned resources.

Examples of orphaned resources:

- old `Deployment` objects still running pods,
- old `Service` objects still exposing endpoints,
- old `Route` objects still exposing URLs,
- old `ConfigMap` or `Secret` objects still consumed by workloads,
- old `NetworkPolicy` objects still blocking or allowing traffic,
- old `RoleBinding` objects still granting access,
- old `Operator` custom resources still controlling operators,
- old `PVC` objects still retaining data.

### With prune

```text
Resource removed from Git  --->  Argo CD deletes it from OpenShift
```

This keeps the live cluster aligned with Git.

## 3. Argo CD reconciliation model

Argo CD continuously compares two states:

| State | Meaning |
|---|---|
| Desired state | Rendered manifests from Git, Helm, Kustomize, Jsonnet, plugin, or directory source |
| Live state | Actual resources currently present in the OpenShift/Kubernetes API |

After comparison, resources usually fall into one of these categories:

| Category | Meaning |
|---|---|
| Synced | Resource exists and matches Git |
| OutOfSync | Resource exists but differs from Git |
| Missing | Resource exists in Git but not in cluster |
| Extraneous | Resource exists in cluster but no longer exists in Git |

**Prune acts on extraneous resources.**

Example:

```text
Git desired state:
- Deployment/frontend
- Service/frontend

Live cluster:
- Deployment/frontend
- Service/frontend
- Route/frontend

Result:
- Route/frontend is extraneous
- Route/frontend is a prune candidate
```

## 4. Prune vs sync vs self-heal

Many administrators confuse `sync`, `selfHeal`, and `prune`. They are related but not the same.

| Feature | What it does | Example |
|---|---|---|
| Sync | Applies desired manifests from Git to the cluster | Git has Deployment with 3 replicas; Argo applies it |
| Self-heal | Reverts live cluster drift back to Git | Someone manually changes replicas from 3 to 5; Argo reverts to 3 |
| Prune | Deletes resources that are no longer in Git | Git removed a Route; Argo deletes the live Route |

### Key difference

`selfHeal` handles **modified resources**.

`prune` handles **removed resources**.

Example:

```text
Case 1: Deployment exists in Git and cluster, but replicas changed manually.
Action needed: selfHeal

Case 2: Deployment removed from Git but still exists in cluster.
Action needed: prune
```

## 5. How Argo CD identifies resources to prune

Argo CD must know which live resources belong to an Application before it can decide what is extraneous.

It tracks resources using Argo CD resource tracking methods, commonly through labels, annotations, or internal tracking IDs depending on configuration and version.

A typical resource managed by Argo CD might contain labels or annotations like:

```yaml
metadata:
  labels:
    app.kubernetes.io/instance: payment-app
```

or an annotation-based tracking ID.

Conceptually, pruning uses this logic:

```text
1. Render desired manifests from Git.
2. Discover live resources tracked by the Application.
3. Compare desired resource identities with live resource identities.
4. Mark live tracked resources missing from Git as extraneous.
5. Delete extraneous resources only if pruning is enabled or approved.
```

A resource identity normally includes:

```text
Group + Kind + Namespace + Name
```

For example:

```text
route.openshift.io/Route + Namespace payment + Name payment-route
```

If that exact resource identity disappears from rendered Git output, it becomes a prune candidate.

## 6. Manual prune

Manual pruning means an administrator explicitly chooses to prune during a sync operation.

This is the safer default for production environments because deletion does not happen automatically after every Git change.

### Manual prune from Argo CD UI

In the Argo CD web console:

```text
Application -> Sync -> enable PRUNE -> Synchronize
```

Typical workflow:

1. Review diff.
2. Confirm which resources will be deleted.
3. Select `Prune`.
4. Start sync.
5. Verify resource deletion.

### Manual prune from CLI

```bash
argocd app sync payment-app --prune
```

### Manual prune with OpenShift GitOps CLI login

For the default OpenShift GitOps instance:

```bash
oc get route openshift-gitops-server -n openshift-gitops

ARGOCD_SERVER=$(oc get route openshift-gitops-server \
  -n openshift-gitops \
  -o jsonpath='{.spec.host}')

ADMIN_PASSWORD=$(oc get secret openshift-gitops-cluster \
  -n openshift-gitops \
  -o jsonpath='{.data.admin\.password}' | base64 -d)

argocd login "$ARGOCD_SERVER" \
  --username admin \
  --password "$ADMIN_PASSWORD" \
  --grpc-web

argocd app sync payment-app --prune
```

### When manual prune is preferred

Use manual prune when:

- working in production,
- deleting namespaces,
- deleting PVCs,
- deleting Routes used by external clients,
- deleting NetworkPolicies,
- deleting RBAC resources,
- deleting Operator custom resources,
- deleting cluster-scoped resources,
- performing application migration or resource rename,
- working with shared services.

## 7. Automated prune

Automated pruning allows Argo CD to delete extraneous resources automatically during automated sync.

Application example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-app
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/payment.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
      allowEmpty: false
```

### Important fields

| Field | Meaning |
|---|---|
| `enabled: true` | Enables automated sync behavior |
| `prune: true` | Allows Argo CD to automatically delete resources removed from Git |
| `selfHeal: true` | Allows Argo CD to correct live cluster drift |
| `allowEmpty: false` | Prevents deleting everything if Git renders zero manifests |

### CLI command

```bash
argocd app set payment-app --sync-policy automated --auto-prune
```

### When automated prune is useful

Automated prune is useful for:

- development namespaces,
- temporary preview environments,
- ephemeral review apps,
- generated per-branch environments,
- non-critical test clusters,
- staging environments with strong Git review controls,
- applications with low deletion risk.

### When automated prune is dangerous

Automated prune can be dangerous when:

- Git path is wrong,
- Helm values accidentally disable important manifests,
- Kustomize overlay accidentally removes resources,
- ApplicationSet generator produces wrong output,
- repository branch is force-pushed,
- chart rendering returns zero manifests,
- a namespace manifest disappears,
- PVC manifests disappear,
- CRDs or Operator CRs are removed unintentionally,
- cluster-scoped RBAC is removed unintentionally.

## 8. `allowEmpty` and full-application deletion protection

`allowEmpty` is a safety guard for automated pruning.

By default, automated pruning protects against the situation where the desired application renders no resources at all.

Example dangerous condition:

```text
Git path: overlays/prod
Rendered manifests: zero resources
Live cluster: 40 managed resources
```

Without protection, auto-prune could delete all 40 resources.

That can happen because of:

- wrong `path`,
- broken Kustomize overlay,
- Helm condition disabling all templates,
- wrong branch,
- empty directory,
- failed generator logic,
- ApplicationSet parameter issue.

### Safe default

```yaml
syncPolicy:
  automated:
    prune: true
    allowEmpty: false
```

This means:

```text
Auto-prune is enabled, but Argo CD should not automatically delete all resources when desired state is empty.
```

### Intentional empty application

Use this only when deleting everything is intentional:

```yaml
syncPolicy:
  automated:
    prune: true
    allowEmpty: true
```

Example use cases:

- ephemeral preview environment cleanup,
- temporary lab namespace cleanup,
- controlled app retirement workflow,
- generated ApplicationSet cleanup where deletion is expected.

### Production rule

For production:

```yaml
allowEmpty: false
```

Keep `allowEmpty: true` only for clearly documented cleanup workflows.

## 9. `Prune=false`: protecting specific resources

`Prune=false` prevents a resource from being pruned even if it disappears from Git desired state.

This is configured as an Argo CD sync option annotation on the resource:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

Example PVC protection:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: payment-db-data
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

If this PVC is removed from Git, Argo CD will not prune it automatically.

### Important behavior

If Argo CD expects a protected resource to be pruned but `Prune=false` blocks deletion, the Application can remain `OutOfSync` because live state still contains an extraneous resource.

That is expected.

### Use cases for `Prune=false`

Use `Prune=false` for resources such as:

- PVCs containing production data,
- manually managed Secrets,
- externally controlled ConfigMaps,
- long-lived Routes during cutover,
- shared Services,
- critical Namespaces,
- custom resources with destructive finalizers,
- resources owned jointly by GitOps and another controller.

### Do not overuse `Prune=false`

If you add `Prune=false` everywhere, Git is no longer a complete source of truth.

Use it only where deletion has special operational risk.

## 10. `Prune=confirm`: pruning only after approval

`Prune=confirm` requires manual approval before pruning a resource.

Example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payment-prod
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

This is useful for critical resources where automatic deletion should not happen without human review.

### Confirm pruning by annotation

Argo CD can confirm pruning through UI, CLI, or by annotating the Application with a deletion approval timestamp.

Example:

```bash
oc annotate application payment-app \
  -n openshift-gitops \
  argocd.argoproj.io/deletion-approved="$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --overwrite
```

Then sync/prune again:

```bash
argocd app sync payment-app --prune
```

### Use cases for `Prune=confirm`

Use this for:

- Namespaces,
- CRDs,
- ClusterRoles,
- ClusterRoleBindings,
- StorageClasses,
- Operator custom resources,
- database CRs,
- certificates and issuers,
- ingress controllers,
- production Routes,
- externally visible resources.

### `Prune=false` vs `Prune=confirm`

| Option | Behavior |
|---|---|
| `Prune=false` | Never prune automatically; resource is protected |
| `Prune=confirm` | Prune only after explicit approval |

Use `Prune=false` when the resource should normally survive Git removal.

Use `Prune=confirm` when the resource can be deleted, but only after approval.

## 11. `PruneLast=true`: pruning at the end of sync

`PruneLast=true` makes pruning happen as the final implicit sync wave, after other resources are applied and healthy.

Application-level example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-app
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/payment.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - PruneLast=true
```

Resource-level example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: PruneLast=true
```

### Why `PruneLast=true` matters

During migration, you often need new resources to become healthy before old resources are deleted.

Example migration:

```text
Old resource: Deployment/payment-v1
New resource: Deployment/payment-v2
```

Without `PruneLast=true`, Argo CD might delete old resources during the sync while new resources are not yet healthy.

With `PruneLast=true`:

```text
1. Create/update new resources.
2. Wait for health.
3. Complete sync waves.
4. Prune old resources last.
```

### Good use cases

- blue/green migration,
- Route cutover,
- Service selector migration,
- Deployment rename,
- StatefulSet migration,
- ConfigMap or Secret rename,
- CRD version migration,
- Operator custom resource replacement,
- network policy migration.

### Example: Deployment rename with safer pruning

Before:

```text
Deployment/payment-api
Service/payment-api -> selector app=payment-api
```

After:

```text
Deployment/payment-api-v2
Service/payment-api -> selector app=payment-api-v2
```

Safe flow:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
    - PruneLast=true
```

Argo CD applies the new deployment and service update first. Only after success does it prune the old deployment.

## 12. `PrunePropagationPolicy`: foreground, background, orphan

When Argo CD prunes a Kubernetes resource, Kubernetes deletion semantics decide what happens to dependent resources.

Argo CD supports:

```yaml
syncOptions:
  - PrunePropagationPolicy=foreground
```

Possible values:

```text
foreground
background
orphan
```

### Foreground pruning

```yaml
syncOptions:
  - PrunePropagationPolicy=foreground
```

Foreground means Kubernetes deletes dependents before fully deleting the owner object.

Example:

```text
Deployment
  -> ReplicaSet
      -> Pods
```

With foreground deletion:

```text
Pods deleted -> ReplicaSet deleted -> Deployment deleted
```

This is safer and more deterministic, but deletion can take longer.

Argo CD uses foreground deletion as the default for pruning extraneous resources.

### Background pruning

```yaml
syncOptions:
  - PrunePropagationPolicy=background
```

Background means Kubernetes deletes the owner object immediately and garbage-collects dependents in the background.

This is faster but less visibly ordered.

Good for:

- large numbers of simple resources,
- non-critical cleanup,
- ephemeral environments,
- cases where waiting for all dependents slows sync.

Risk:

- dependents may remain temporarily,
- finalizer issues may be noticed later,
- troubleshooting requires checking dependent resources separately.

### Orphan pruning

```yaml
syncOptions:
  - PrunePropagationPolicy=orphan
```

Orphan means Kubernetes deletes the owner but leaves dependent resources behind.

Example:

```text
Deployment deleted
ReplicaSet/Pods may remain orphaned depending on owner references and controller behavior
```

Use carefully.

Possible use cases:

- migration where dependents must temporarily survive,
- advanced controller debugging,
- preventing cascading deletion during operator replacement,
- manual takeover of child resources.

For normal OpenShift application delivery, `orphan` is rarely the right default.

### Quick comparison

| Policy | Owner deletion | Dependent cleanup | Best for |
|---|---|---|---|
| foreground | Waits until dependents are handled | Before owner disappears fully | Safe production cleanup |
| background | Owner removed quickly | Cleanup happens asynchronously | Fast cleanup |
| orphan | Owner removed | Dependents remain | Special migrations/debugging |

## 13. Prune vs application deletion

Pruning and deleting an Argo CD Application are different operations.

### Prune

Prune happens during sync.

```text
Application remains.
Only extraneous managed resources are deleted.
```

Example:

```bash
argocd app sync payment-app --prune
```

### Application deletion

Deleting the Application removes the Argo CD Application object itself.

Depending on finalizers and deletion options, this may also delete resources managed by the Application.

Example:

```bash
oc delete application payment-app -n openshift-gitops
```

### `Delete=false`

`Delete=false` is not the same as `Prune=false`.

`Delete=false` protects a resource from being deleted when the Argo CD Application is deleted.

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Delete=false
```

Use `Delete=false` for resources that should survive Application deletion, such as PVCs.

### Difference table

| Option | Applies during | Purpose |
|---|---|---|
| `Prune=false` | Sync/prune | Prevent deletion when resource is removed from Git |
| `Prune=confirm` | Sync/prune | Require approval before prune |
| `Delete=false` | Application deletion | Prevent resource cleanup when Application is deleted |
| `Delete=confirm` | Application deletion | Require approval before app deletion removes resource |

## 14. OpenShift GitOps-specific considerations

OpenShift GitOps is Red Hat’s supported distribution of Argo CD for OpenShift.

In the default installation, the main Argo CD instance runs in:

```text
openshift-gitops
```

### Managing resources in another namespace

If Argo CD is installed in `openshift-gitops` and should manage resources in `payment-prod`, label the target namespace:

```bash
oc label namespace payment-prod \
  argocd.argoproj.io/managed-by=openshift-gitops
```

Without proper namespace access, Argo CD may fail to create, update, or prune resources in that namespace.

### OpenShift resources commonly affected by prune

Pruning is not limited to Kubernetes core resources. In OpenShift, Argo CD may prune resources such as:

- `route.openshift.io/Route`,
- `build.openshift.io/BuildConfig`,
- `image.openshift.io/ImageStream`,
- `security.openshift.io/SecurityContextConstraints` if managed,
- `project.openshift.io/Project`,
- `apps.openshift.io/DeploymentConfig`,
- `operator.openshift.io` custom resources,
- Operator Lifecycle Manager resources such as `Subscription`, `OperatorGroup`, `ClusterServiceVersion`,
- `NetworkPolicy`,
- `Role`, `RoleBinding`, `ClusterRole`, `ClusterRoleBinding`,
- `PersistentVolumeClaim`,
- `Secret`, `ConfigMap`.

### Cluster-scoped resources

Pruning cluster-scoped resources is high-risk.

Examples:

```text
ClusterRole
ClusterRoleBinding
CustomResourceDefinition
StorageClass
Namespace
SecurityContextConstraints
OperatorGroup
Subscription
```

Before enabling auto-prune for cluster-scoped configuration, verify:

- AppProject permissions,
- Argo CD service account RBAC,
- destination scope,
- sync windows,
- manual confirmation policy,
- backup/restore plan,
- break-glass access.

### AppProject control

Use `AppProject` to limit what an Application can prune.

Example controls:

- allowed repositories,
- allowed destination clusters,
- allowed destination namespaces,
- allowed cluster-scoped resource kinds,
- denied resource kinds.

A production AppProject should not allow broad deletion of every cluster-scoped resource unless that is intentional.

### OpenShift finalizers

Some OpenShift resources use finalizers. Finalizers can delay or block pruning.

Common examples:

- PVC protection finalizers,
- Namespace finalizers,
- Operator finalizers,
- custom resource finalizers,
- external storage finalizers,
- service mesh or cert-manager finalizers.

If pruning appears stuck, always inspect finalizers before force-removing anything.

## 15. Production design patterns

### Pattern 1: Manual prune in production

```yaml
syncPolicy:
  automated:
    enabled: false
```

Then use:

```bash
argocd app sync payment-app --prune
```

Best for:

- critical applications,
- regulated environments,
- cluster-scoped configuration,
- shared infrastructure.

### Pattern 2: Auto-sync without auto-prune

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: false
    selfHeal: true
```

This allows Git changes and drift correction but prevents automatic deletion of removed resources.

Best for conservative production environments.

### Pattern 3: Auto-prune with guardrails

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
  syncOptions:
    - PruneLast=true
    - PrunePropagationPolicy=foreground
```

Add resource-specific protection:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

Best for mature teams with:

- Git branch protection,
- pull request review,
- CI manifest validation,
- staging promotion,
- observability,
- rollback procedure,
- AppProject restrictions.

### Pattern 4: Ephemeral environment cleanup

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: true
```

Best for:

- preview apps,
- lab namespaces,
- short-lived developer environments.

Avoid this pattern for persistent production workloads.

## 18. Troubleshooting prune problems

### Problem 1: Resource removed from Git but still exists in cluster

Symptoms:

```text
Application is OutOfSync.
Resource appears as extraneous.
Resource is not deleted.
```

Check:

```bash
argocd app get payment-app
argocd app resources payment-app
argocd app diff payment-app
```

Possible causes:

- prune not enabled,
- manual sync was run without `--prune`,
- auto-prune disabled,
- resource has `Prune=false`,
- resource has `Prune=confirm`,
- sync window blocks sync,
- AppProject disallows deletion,
- Argo CD lacks RBAC permission,
- resource has finalizers,
- resource is no longer tracked by Argo CD.

Fix:

```bash
argocd app sync payment-app --prune
```

or enable auto-prune:

```yaml
syncPolicy:
  automated:
    prune: true
```

---

### Problem 2: Application stuck in Syncing during prune

Possible causes:

- resource requires prune confirmation,
- foreground deletion waiting for dependents,
- finalizer blocks deletion,
- Kubernetes API cannot delete dependent object,
- Operator custom resource cleanup is slow.

Check:

```bash
oc describe application payment-app -n openshift-gitops
argocd app get payment-app
argocd app resources payment-app
oc get events -A --sort-by=.lastTimestamp | tail -50
```

Check target resource:

```bash
oc get <kind> <name> -n <namespace> -o yaml
```

Look for:

```yaml
metadata:
  deletionTimestamp: ...
  finalizers:
    - ...
```

Do not remove finalizers unless you understand what cleanup is being skipped.

---

### Problem 3: Auto-prune did not delete everything after Git path became empty

Likely cause:

```yaml
allowEmpty: false
```

This is a safety feature.

If the empty desired state is intentional:

```yaml
syncPolicy:
  automated:
    prune: true
    allowEmpty: true
```

Then sync again.

Use this carefully.

---

### Problem 4: Resource is protected by `Prune=false`

Check annotation:

```bash
oc get pvc mysql-data -n mysql-prod -o yaml | grep -A5 annotations
```

You may see:

```yaml
argocd.argoproj.io/sync-options: Prune=false
```

Options:

1. Keep it and accept OutOfSync/extraneous status.
2. Remove the annotation in Git.
3. Delete the resource manually after backup/approval.

---

### Problem 5: Argo CD does not have permission to prune

Symptoms:

```text
permission denied
forbidden
cannot delete resource
```

Check Application destination namespace:

```bash
oc get application payment-app -n openshift-gitops -o yaml
```

Check namespace label:

```bash
oc get namespace payment-prod --show-labels
```

For default OpenShift GitOps instance, ensure:

```bash
oc label namespace payment-prod \
  argocd.argoproj.io/managed-by=openshift-gitops \
  --overwrite
```

Check AppProject restrictions:

```bash
oc get appproject -n openshift-gitops
oc get appproject <project-name> -n openshift-gitops -o yaml
```

---

### Problem 6: Resource disappeared from Argo CD tracking

If someone manually changed tracking labels or annotations, Argo CD may stop associating the resource with the Application.

Check labels:

```bash
oc get deploy payment-api -n payment-prod --show-labels
```

Check annotations:

```bash
oc get deploy payment-api -n payment-prod -o yaml | grep -A10 annotations
```

Fix by restoring Git-managed metadata and resyncing.

## 19. Risk scenarios and safe handling

### Scenario 1: Accidentally deleting a Route

Risk:

```text
External users lose application access.
```

Safe approach:

- Use PR review for route deletion.
- Use `PruneLast=true` during cutover.
- Use `Prune=confirm` for production Routes.
- Verify DNS and ingress behavior.

---

### Scenario 2: Removing NetworkPolicy from Git

Risk:

```text
Traffic that was previously denied may become allowed, or required traffic may stay blocked depending on remaining policies.
```

Safe approach:

```bash
oc get networkpolicy -n app-prod
argocd app diff app-prod
```

Use manual prune for security-sensitive policy changes.

---

### Scenario 3: Removing PVC from Git

Risk:

```text
Data loss or storage release depending on reclaim policy and storage class behavior.
```

Safe approach:

- Add `Prune=false`.
- Add `Delete=false`.
- Confirm backups.
- Check PV reclaim policy.
- Manually delete only after approval.

PVC example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false,Delete=false
```

---

### Scenario 4: Removing Operator custom resource

Risk:

```text
Operator may delete workloads, operands, storage, routes, CRDs, or external integrations.
```

Safe approach:

- Read Operator documentation.
- Understand finalizers.
- Use `Prune=confirm`.
- Test in staging.
- Take backup of custom resources.
- Monitor operator logs.

---

### Scenario 5: Removing namespace manifest

Risk:

```text
Entire namespace and all namespaced resources may be deleted.
```

Safe approach:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm,Delete=confirm
```

Never auto-prune production namespaces without confirmation.

---

### Scenario 6: Helm values accidentally disable resources

Example:

```yaml
route:
  enabled: false
```

This may remove the Route from rendered manifests, making it a prune candidate.

Safe approach:

```bash
helm template . -f values-prod.yaml
argocd app diff payment-app
```

Use CI to validate rendered manifests before merge.

---

### Scenario 7: Kustomize overlay removes a base resource

Example:

```text
base/service.yaml removed
```

or overlay path changed incorrectly.

Safe approach:

```bash
kustomize build overlays/prod
argocd app diff payment-app
```

## 20. Interview and exam-style questions

### Q1. What does prune do in Argo CD?

Prune deletes live cluster resources that are tracked by an Argo CD Application but no longer exist in the desired manifests rendered from Git.

---

### Q2. Is prune enabled by default?

Manual sync can be performed with pruning selected, but automated sync does not automatically delete resources removed from Git unless automated pruning is enabled with `prune: true`.

---

### Q3. What is the difference between `prune: true` and `selfHeal: true`?

`selfHeal: true` corrects live drift for resources that still exist in Git. `prune: true` deletes resources that no longer exist in Git.

---

### Q4. Why is `allowEmpty: false` important?

It prevents automated pruning from deleting all managed resources when the Application renders zero manifests due to a mistake such as a wrong Git path, broken Helm values, or empty Kustomize output.

---

### Q5. How do you prevent a PVC from being pruned?

Add:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

For Application deletion protection also add:

```yaml
argocd.argoproj.io/sync-options: Prune=false,Delete=false
```

---

### Q6. How do you require approval before pruning a namespace?

Add:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

---

### Q7. What does `PruneLast=true` do?

It delays pruning until the final implicit sync wave, after other resources are deployed and healthy.

---

### Q8. What is the default Argo CD prune propagation policy?

Argo CD prunes extraneous resources using foreground deletion by default, unless `PrunePropagationPolicy` is configured differently.

---

### Q9. What OpenShift command labels a namespace so the default OpenShift GitOps instance can manage it?

```bash
oc label namespace <target_namespace> \
  argocd.argoproj.io/managed-by=openshift-gitops
```

---

### Q10. Why might a pruned resource remain stuck in Terminating?

Common reasons include finalizers, dependent resources not deleting, Operator cleanup delays, PVC protection, namespace finalizers, or insufficient permissions.

## 21. Best-practice checklist

### General

- [ ] Understand the difference between sync, self-heal, prune, and delete.
- [ ] Use manual prune for high-risk production applications.
- [ ] Use automated prune first in dev/staging before production.
- [ ] Keep `allowEmpty: false` for production.
- [ ] Use `PruneLast=true` for migrations and resource renames.
- [ ] Use `PrunePropagationPolicy=foreground` for safer production cleanup.
- [ ] Use `Prune=confirm` for namespaces and critical cluster-scoped resources.
- [ ] Use `Prune=false` for resources that must survive Git removal.
- [ ] Use `Delete=false` for resources that must survive Application deletion.

### OpenShift-specific

- [ ] Label managed namespaces with `argocd.argoproj.io/managed-by=<argocd_namespace>`.
- [ ] Verify AppProject restrictions.
- [ ] Avoid broad cluster-scoped prune permissions unless required.
- [ ] Treat SCC, ClusterRole, CRD, Namespace, StorageClass, and Operator resources as high-risk.
- [ ] Check finalizers before force-deleting stuck resources.
- [ ] Use OpenShift monitoring/alerts for OutOfSync and degraded Applications.

### Before enabling automated prune

- [ ] Validate rendered manifests in CI.
- [ ] Run `argocd app diff`.
- [ ] Confirm Git path and branch.
- [ ] Confirm Helm values and Kustomize output.
- [ ] Confirm resource list expected to be pruned.
- [ ] Confirm backup for stateful workloads.
- [ ] Confirm rollback plan.
- [ ] Confirm team review and approval process.

## Final takeaway

The `prune` option is one of the most powerful and risky parts of Argo CD.

For a junior administrator, prune means:

```text
Delete resources removed from Git.
```

For an advanced OpenShift administrator, prune means:

```text
Controlled lifecycle enforcement of Git desired state, with deletion safety, RBAC boundaries, AppProject restrictions, finalizer awareness, storage protection, namespace protection, sync ordering, and production approval workflow.
```

Use prune confidently, but never casually.
