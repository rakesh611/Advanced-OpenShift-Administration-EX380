# Self-Healing in OpenShift GitOps Argo CD

**Audience:** Advanced OpenShift Administration / senior OpenShift, Kubernetes, DevOps, and SRE engineers  
**Experience level:** Written for administrators with around 10 years of Linux, container, Kubernetes, and platform operations experience  
**Scope:** Red Hat OpenShift GitOps, Argo CD `Application`, automated sync, drift correction, pruning, diff customization, OpenShift-specific RBAC, namespace management, troubleshooting, and production design

---

## 1. Executive Summary

In OpenShift GitOps, **self-healing** means Argo CD continuously compares the **desired state** stored in Git with the **live state** running in the OpenShift cluster. When a resource is changed directly in the cluster and no longer matches Git, Argo CD detects the drift and, when self-healing is enabled, automatically syncs the live resource back to the Git-defined state.

Self-healing is one of the most important production GitOps features because it protects the cluster from configuration drift caused by manual `oc edit`, emergency hotfixes, accidental console changes, operator mutations, unauthorized changes, or inconsistent rollout practices.

However, self-healing must be understood carefully. It is powerful, but it is not magic. It does not fix bad Git manifests. It does not replace Kubernetes controllers, health probes, Operators, monitoring, backup, admission control, or change management. It simply enforces that Argo CD-managed resources converge back to the desired state defined in Git.

At a high level:

```text
Git Repository
   |
   | desired Kubernetes/OpenShift manifests
   v
Argo CD Application Controller
   |
   | compares desired state with live cluster state
   v
OpenShift Cluster
   |
   | if drift is detected and selfHeal=true
   v
Argo CD applies Git state back to the cluster
```

---

## 2. What Self-Healing Means in GitOps

Self-healing in Argo CD is best understood as **drift remediation**.

A resource is considered drifted when:

- Git says a Deployment should have `replicas: 3`, but someone scales it to `replicas: 6` from the OpenShift console.
- Git says a Route should use a specific hostname, but someone changes the Route manually.
- Git defines a ConfigMap value, but a user edits the ConfigMap directly in the cluster.
- Git defines an image tag, but someone runs `oc set image` manually.
- Git defines labels, annotations, resource limits, tolerations, or environment variables, but the live object is changed outside Git.

When self-healing is enabled, Argo CD treats Git as the source of truth and overwrites the live cluster change with the Git version.

### Simple Example

Git desired state:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: prod-app
spec:
  replicas: 3
```

Someone manually runs:

```bash
oc scale deployment frontend -n prod-app --replicas=5
```

Without self-healing:

```text
Argo CD shows OutOfSync, but does not automatically fix it.
```

With self-healing:

```text
Argo CD detects that live replicas=5 but Git replicas=3.
Argo CD automatically syncs the Deployment back to replicas=3.
```

## 3. Self-Healing Is Not the Same as Kubernetes Self-Healing

This distinction is very important in interviews, real operations, and troubleshooting.

| Feature | Kubernetes / OpenShift Self-Healing | Argo CD Self-Healing |
|---|---|---|
| Main purpose | Keeps workloads running | Keeps configuration matching Git |
| Example | Restart failed pods | Revert manual YAML changes |
| Controller | Deployment, ReplicaSet, StatefulSet, DaemonSet, Operator, kubelet | Argo CD application-controller |
| Source of truth | Kubernetes object spec in etcd | Git repository manifests |
| Fixes pod crash? | Yes, if managed by controller | No |
| Fixes manual config drift? | Usually no | Yes, if managed and configured |
| Example action | Recreate a failed pod | Reapply Git manifest |

### Kubernetes/OpenShift self-healing example

If a pod crashes, the Deployment controller creates a replacement pod.

### Argo CD self-healing example

If someone changes the Deployment image from `v1.0` to `v2.0` directly in the cluster, Argo CD changes it back to the image version defined in Git.

A senior administrator should never confuse the two. Kubernetes self-healing is workload-runtime recovery. Argo CD self-healing is desired-state enforcement.

## 4. Where Self-Healing Fits in OpenShift GitOps Architecture

A typical Red Hat OpenShift GitOps installation deploys an Argo CD control plane, often in the `openshift-gitops` namespace. The major components involved in self-healing are:

```text
openshift-gitops namespace

+-------------------------+
| argocd-server           |
| UI / API / CLI endpoint |
+-------------------------+
            |
            v
+-------------------------+
| argocd-application-     |
| controller              |
| compares desired/live   |
| and performs sync       |
+-------------------------+
            |
            v
+-------------------------+
| argocd-repo-server      |
| renders manifests from  |
| Git / Helm / Kustomize  |
+-------------------------+
            |
            v
+-------------------------+
| OpenShift API Server    |
| target cluster objects  |
+-------------------------+
```

### Key component: `argocd-application-controller`

The **application-controller** is the component responsible for:

- Watching Argo CD `Application` resources.
- Comparing desired manifests with live OpenShift resources.
- Marking applications as `Synced`, `OutOfSync`, `Healthy`, `Degraded`, or `Missing`.
- Performing automated sync when enabled.
- Performing self-healing when `selfHeal: true` is set.
- Applying, pruning, and deleting resources according to sync policy and sync options.

### Key component: `argocd-repo-server`

The repo-server renders manifests from:

- Plain YAML directories.
- Kustomize overlays.
- Helm charts.
- Jsonnet.
- Config Management Plugins.
- Multi-source applications.

The application-controller asks the repo-server for the desired manifests, then compares them with live objects from the OpenShift API server.

## 5. OpenShift-Specific Management Requirements

OpenShift GitOps adds OpenShift-specific operational rules around namespace and RBAC management.

For the default `openshift-gitops` Argo CD instance to manage workloads in an application namespace, that namespace is commonly labeled as managed by the Argo CD instance:

```bash
oc label namespace prod-app argocd.argoproj.io/managed-by=openshift-gitops
```

If the namespace is not properly configured for the Argo CD instance, the application might exist in Argo CD but fail to create, update, or self-heal resources in the target namespace.

### Verify namespace label

```bash
oc get namespace prod-app --show-labels | grep argocd.argoproj.io/managed-by
```

Expected example:

```text
argocd.argoproj.io/managed-by=openshift-gitops
```

### Verify Argo CD can access the namespace

```bash
oc auth can-i patch deployment -n prod-app \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

Depending on the installed instance and service account naming, adjust the service account name.

## 6. Core Configuration: Enabling Self-Healing

Self-healing is configured inside the Argo CD `Application` resource under:

```yaml
spec:
  syncPolicy:
    automated:
      selfHeal: true
```

In modern Argo CD versions, automated sync can also be explicitly enabled or disabled using:

```yaml
spec:
  syncPolicy:
    automated:
      enabled: true
```

A production-grade automated self-healing policy usually looks like this:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-prod
  namespace: openshift-gitops
spec:
  project: prod-platform
  source:
    repoURL: https://git.example.com/platform/apps.git
    targetRevision: main
    path: apps/frontend/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod-app
  syncPolicy:
    automated:
      enabled: true
      selfHeal: true
      prune: true
    syncOptions:
      - CreateNamespace=false
```

### Meaning of each field

| Field | Meaning |
|---|---|
| `automated.enabled: true` | Enables automated synchronization. |
| `selfHeal: true` | Re-syncs when live cluster state drifts from Git. |
| `prune: true` | Deletes live resources that were removed from Git. |
| `CreateNamespace=false` | Prevents Argo CD from auto-creating the namespace; useful when namespaces are platform-controlled. |

---

## 7. Auto-Sync vs Self-Heal vs Prune

These three settings are related, but they solve different problems.

| Setting | Trigger | Action |
|---|---|---|
| Auto-sync | Git changes | Applies new desired state from Git |
| Self-heal | Live cluster drift | Reverts live state back to Git |
| Prune | Resource removed from Git | Deletes extra live resource |

### Auto-sync only

```yaml
syncPolicy:
  automated:
    enabled: true
```

This means Argo CD automatically deploys Git changes, but live cluster changes might only show as `OutOfSync` and not be corrected automatically.

### Auto-sync with self-heal

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
```

This means Argo CD automatically deploys Git changes and also corrects live drift.

### Auto-sync with self-heal and prune

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
    prune: true
```

This is a strong GitOps enforcement mode. It keeps resources aligned with Git and removes resources that are deleted from Git.

### Important caution

`prune: true` is powerful. If someone removes a Namespace, PVC, Route, Secret, Operator subscription, or cluster-scoped object from Git, Argo CD can delete it from the cluster depending on ownership, permissions, and sync options.

For production, use prune carefully with:

- Pull request review.
- Protected branches.
- AppProject restrictions.
- Sync windows.
- `Prune=confirm` for critical resources.
- Backup and restore strategy for persistent data.

## 8. Important Modern Behavior: `automated.enabled`

Modern Argo CD supports explicit control of automated sync with:

```yaml
spec:
  syncPolicy:
    automated:
      enabled: false
      prune: true
      selfHeal: true
```

This configuration can look confusing.

It means:

```text
Prune and selfHeal are configured, but automated sync is disabled.
The controller will not perform automated sync/self-heal actions.
```

This is useful when you want to store policy intent in Git but temporarily disable automation.

### Interview-ready point

If `selfHeal: true` is present but `automated.enabled: false`, self-healing will not actively fix drift because automated sync is disabled.

## 9. How Argo CD Detects Drift

Argo CD performs a comparison between:

1. **Desired manifests** rendered from Git.
2. **Live manifests** retrieved from the OpenShift API server.

The rendered desired manifests may come from:

- Helm templates.
- Kustomize overlays.
- Plain YAML.
- Jsonnet.
- Config Management Plugin output.

The live state comes from Kubernetes/OpenShift resources such as:

- `Deployment`
- `DeploymentConfig`
- `Service`
- `Route`
- `ConfigMap`
- `Secret`
- `RoleBinding`
- `NetworkPolicy`
- `ServiceAccount`
- `HorizontalPodAutoscaler`
- `Subscription`
- `OperatorGroup`
- `MachineConfig`, if allowed and intentionally managed
- Custom resources from installed Operators

If the desired and live states differ, Argo CD marks the resource or application as `OutOfSync`.

## 10. Self-Healing Reconciliation Flow

The practical flow looks like this:

```text
1. Application exists in Argo CD.
2. Argo CD renders desired manifests from Git.
3. Argo CD reads live resources from OpenShift API.
4. Argo CD compares desired vs live state.
5. If different, application becomes OutOfSync.
6. If automated sync is enabled and selfHeal=true, Argo CD schedules a sync.
7. Argo CD applies Git-defined fields back to the cluster.
8. Application returns to Synced if sync succeeds.
```

### Flow diagram

```text
Manual change in OpenShift
        |
        v
Live object differs from Git
        |
        v
Argo CD comparison detects OutOfSync
        |
        v
Is automated sync enabled?
        |
        +-- No --> Show OutOfSync only
        |
        +-- Yes
             |
             v
        Is selfHeal true?
             |
             +-- No --> Show OutOfSync only
             |
             +-- Yes
                  |
                  v
             Reapply Git state
                  |
                  v
             Synced / Healthy or Sync Failed
```

## 11. Reconciliation Timing and Self-Heal Timeout

Argo CD does not continuously perform a busy loop every millisecond. It reconciles applications on an interval and responds to watched events.

Important timing concepts:

| Timing concept | Practical meaning |
|---|---|
| Reconciliation interval | Argo CD periodically refreshes application state. |
| Watch events | Kubernetes watch events can speed up detection. |
| Self-heal timeout | After drift is detected, self-heal sync is retried after a configured timeout. |
| Default self-heal timeout | Common upstream default is 5 seconds. |
| Default reconciliation interval | Common upstream default is 120 seconds plus jitter, often up to around 3 minutes. |

In real OpenShift operations, do not assume every drift will be reverted instantly. Depending on cache, cluster load, controller load, API latency, and reconciliation settings, it might take seconds to a few minutes to show and correct.

## 12. Production Example: Application with Self-Healing

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
  labels:
    app.kubernetes.io/part-of: payments
    environment: prod
spec:
  project: payments-prod
  source:
    repoURL: https://git.example.com/openshift-gitops/payments.git
    targetRevision: main
    path: payment-api/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
  syncPolicy:
    automated:
      enabled: true
      selfHeal: true
      prune: true
    syncOptions:
      - CreateNamespace=false
      - ApplyOutOfSyncOnly=true
      - PruneLast=true
```

### Why this is production-style

- Application belongs to a controlled `AppProject`.
- Target namespace is explicit.
- Git path points to a production overlay.
- Auto-sync is explicit.
- Self-heal is enabled.
- Prune is enabled but controlled.
- Namespace creation is disabled because namespace lifecycle should normally be platform-owned.
- `ApplyOutOfSyncOnly=true` reduces unnecessary apply operations.
- `PruneLast=true` helps apply/update resources before pruning old ones.

## 13. AppProject Control for Safe Self-Healing

A serious OpenShift GitOps design should not put all applications into the default project with unrestricted permissions.

Use `AppProject` to restrict:

- Allowed source repositories.
- Allowed target clusters.
- Allowed namespaces.
- Allowed namespaced resources.
- Allowed cluster-scoped resources.
- Denied resource kinds.
- Project roles.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-prod
  namespace: openshift-gitops
spec:
  description: Production payment workloads
  sourceRepos:
    - https://git.example.com/openshift-gitops/payments.git
  destinations:
    - namespace: payment-prod
      server: https://kubernetes.default.svc
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy
    - group: autoscaling
      kind: HorizontalPodAutoscaler
    - group: ''
      kind: ConfigMap
    - group: ''
      kind: Secret
```

### Why AppProject matters for self-healing

If self-healing is enabled on an overly privileged project, a bad Git commit can automatically affect sensitive resources. Restricting projects limits the blast radius.

## 15. What Happens When Someone Runs `oc edit`?

Assume Git defines:

```yaml
spec:
  template:
    spec:
      containers:
        - name: payment-api
          image: registry.example.com/payment-api:1.0.0
```

Someone runs:

```bash
oc set image deployment/payment-api \
  payment-api=registry.example.com/payment-api:2.0.0 \
  -n payment-prod
```

With self-healing enabled:

```text
1. Deployment image changes to 2.0.0.
2. Argo CD detects live image differs from Git image 1.0.0.
3. Application becomes OutOfSync.
4. Argo CD syncs the Deployment.
5. Image is changed back to 1.0.0.
```

This behavior is correct in GitOps.

Emergency production changes should be made through Git, not direct cluster mutation. If a direct hotfix is unavoidable, it must be followed immediately by a Git commit, or Argo CD will revert it.

## 17. Self-Healing with Helm

When an Argo CD application uses Helm, Argo CD renders the Helm chart and compares the rendered output with live resources.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-helm
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://charts.bitnami.com/bitnami
    chart: nginx
    targetRevision: 15.0.0
    helm:
      values: |
        replicaCount: 3
        service:
          type: ClusterIP
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-prod
  syncPolicy:
    automated:
      enabled: true
      selfHeal: true
      prune: true
```

If someone manually changes the live Deployment replicas to `5`, Argo CD compares the live object against the Helm-rendered desired output where `replicaCount: 3`, then reverts it.

### Helm self-healing gotchas

- If a chart uses random values, generated names, or timestamps, Argo CD may show repeated drift.
- Avoid non-deterministic Helm templates.
- Pin chart versions for production.
- Store values files in Git.
- Avoid changing live Helm-managed objects directly.

## 18. Self-Healing with Kustomize

For Kustomize, Argo CD renders the final overlay and compares it with live resources.

Example application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-kustomize-prod
  namespace: openshift-gitops
spec:
  project: frontend-prod
  source:
    repoURL: https://git.example.com/gitops/frontend.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: frontend-prod
  syncPolicy:
    automated:
      enabled: true
      selfHeal: true
      prune: true
```

Kustomize structure:

```text
frontend/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    ├── test/
    └── prod/
        ├── kustomization.yaml
        └── patch-replicas.yaml
```

If the production overlay defines `replicas: 4`, self-healing restores the live Deployment to `4` after manual drift.

## 19. Self-Healing and Horizontal Pod Autoscaler

This is a classic production issue.

If Git defines:

```yaml
spec:
  replicas: 3
```

And an HPA changes replicas to `6`, Argo CD might detect drift because live replicas no longer match Git.

This can create a fight:

```text
HPA: scale to 6 because CPU is high
Argo CD: revert to 3 because Git says 3
HPA: scale to 6 again
Argo CD: revert to 3 again
```

### Correct design

When using HPA, usually do one of the following:

#### Option 1: Remove `replicas` from Git-managed Deployment

Let HPA own the replica count.

#### Option 2: Ignore replica differences

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-prod
  namespace: openshift-gitops
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    automated:
      enabled: true
      selfHeal: true
      prune: true
    syncOptions:
      - RespectIgnoreDifferences=true
```

### Important detail

`ignoreDifferences` changes how Argo CD compares resources. `RespectIgnoreDifferences=true` tells Argo CD to also respect those ignore rules during sync.

For HPA-managed workloads, this is often mandatory to prevent GitOps from fighting autoscaling.

## 20. Self-Healing and Operator-Managed Resources

OpenShift uses many Operators:

- Cluster Version Operator.
- Machine Config Operator.
- Ingress Operator.
- Monitoring Operator.
- Logging Operator.
- Service Mesh Operator.
- OpenShift Data Foundation Operator.
- External Secrets Operator.
- Cert Manager Operator.
- Compliance Operator.

Operators often mutate resources by adding:

- Default values.
- Finalizers.
- Status fields.
- Owner references.
- Certificates.
- CA bundles.
- Generated labels and annotations.
- Sidecars or injected fields.

Argo CD normally ignores `status`, but spec-level mutations can still cause drift.

### Example: ignoring fields managed by a Kubernetes controller

```yaml
spec:
  ignoreDifferences:
    - group: '*'
      kind: '*'
      managedFieldsManagers:
        - kube-controller-manager
```

### Production recommendation

Do not blindly ignore all differences for all resources. Start narrow:

```yaml
spec:
  ignoreDifferences:
    - group: admissionregistration.k8s.io
      kind: MutatingWebhookConfiguration
      jqPathExpressions:
        - '.webhooks[]?.clientConfig.caBundle'
```

Ignoring too much can hide real drift and security issues.

## 21. Self-Healing and Secrets

Self-healing Secrets can be dangerous if not designed correctly.

### Common patterns

| Pattern | Description | Self-healing impact |
|---|---|---|
| Plain Secret in Git | Secret YAML committed directly | Not recommended for sensitive data |
| Sealed Secrets | Encrypted secret committed to Git | Good GitOps pattern |
| External Secrets Operator | Secret generated from external vault | Argo CD manages ExternalSecret, not generated Secret |
| Secrets Store CSI | SecretProviderClass managed by Git | Secret contents externalized |
| Vault plugin / CMP | Secret rendered at sync time | Requires secure plugin design |

### Bad design

```text
Argo CD manages a generated Secret while another controller also rotates it.
```

This can cause a loop:

```text
Secret controller rotates value
Argo CD detects drift
Argo CD reverts Secret to old Git value
Controller rotates again
```

### Better design

Let Argo CD manage the declaration, not the generated runtime secret:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: payment-db-secret
  namespace: payment-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: payment-db-secret
  data:
    - secretKey: password
      remoteRef:
        key: prod/payment/db
        property: password
```

Here, Argo CD self-heals the `ExternalSecret` definition, while the External Secrets Operator owns the actual generated Kubernetes Secret.

## 22. Self-Healing and Resource Pruning

Self-healing corrects changed resources. Pruning deletes resources that no longer exist in Git.

Example:

Git initially contains:

```text
deployment.yaml
service.yaml
route.yaml
```

Later, `route.yaml` is removed from Git.

With:

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
    prune: true
```

Argo CD can delete the live Route.

### Use `Prune=false` for special resources

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

### Use `Prune=confirm` for critical resources

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

Critical resources where confirmation may be appropriate:

- Namespaces.
- PVCs.
- ClusterRoles.
- CRDs.
- Operator Subscriptions.
- Production Routes.
- Database custom resources.
- Storage custom resources.

## 23. Self-Healing and Sync Windows

Sync windows can allow or deny sync operations during specific periods.

Self-healing is still a sync operation. If a deny sync window blocks synchronization, drift might be detected but not remediated until the window allows it.

Example operational policy:

```text
Production auto-sync allowed: Monday-Friday 10:00-18:00
Emergency deny window: during database migration
Manual sync override: platform-admin only
```

### Production consideration

If self-healing is blocked by sync windows, then manual drift can remain in the cluster longer than expected. This can be intentional or dangerous depending on the business requirement.

---

## 24. Self-Healing and Sync Waves

Self-healing uses normal sync behavior. Therefore, sync waves and hooks can affect the order in which resources are applied.

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
```

A common order:

```text
Wave -2: Namespace, ResourceQuota, LimitRange
Wave -1: ServiceAccount, Role, RoleBinding
Wave  0: ConfigMap, Secret, Service
Wave  1: Deployment, StatefulSet
Wave  2: Route, HPA, NetworkPolicy
```

### Why this matters for self-healing

If multiple resources drift at the same time, Argo CD applies them according to sync ordering. This avoids cases where a Deployment is applied before its ServiceAccount, ConfigMap, or Secret exists.

## 25. Self-Healing and Health Checks

Argo CD has two major concepts:

| Concept | Meaning |
|---|---|
| Sync status | Does live state match Git? |
| Health status | Is the resource operationally healthy? |

Possible combinations:

| Sync | Health | Meaning |
|---|---|---|
| Synced | Healthy | Desired state matches Git and app is healthy |
| Synced | Degraded | Git matches cluster, but workload is unhealthy |
| OutOfSync | Healthy | Workload may be running, but config drift exists |
| OutOfSync | Degraded | Drift exists and workload is unhealthy |

Self-healing primarily addresses **OutOfSync**. It does not guarantee **Healthy**.

Example:

```text
Git defines a Deployment with bad image: registry.example.com/app:does-not-exist
Argo CD self-heals the Deployment back to that bad image
Application becomes Synced but Degraded
Pods remain ImagePullBackOff
```

Self-healing enforces Git. It does not validate that Git is correct.

## 26. Self-Healing and Rollbacks

A common mistake is to think self-healing is rollback.

It is not.

| Operation | Description |
|---|---|
| Self-healing | Reapply current Git desired state when live cluster drifts |
| Rollback | Move application back to an older desired state |

If Git currently points to `v2.0.0`, self-healing keeps the cluster at `v2.0.0`.

To roll back to `v1.0.0`, you should normally commit a Git revert or change the target revision/path/values to the older version.

### GitOps rollback pattern

```bash
git revert <bad-commit>
git push origin main
```

Argo CD then auto-syncs the reverted desired state.

## 27. Self-Healing in ApplicationSet-Managed Applications

If an `Application` is generated by an `ApplicationSet`, directly editing the generated `Application` might not work as expected because the ApplicationSet controller owns the generated spec.

Bad approach:

```bash
oc patch application app1 -n openshift-gitops --type merge -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":false}}}}'
```

The ApplicationSet controller may revert the generated Application back to its template.

Correct approach: change the ApplicationSet template.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-apps
  namespace: openshift-gitops
spec:
  generators:
    - git:
        repoURL: https://git.example.com/platform/apps.git
        revision: main
        directories:
          - path: apps/*/overlays/prod
  template:
    metadata:
      name: '{{path.basename}}'
    spec:
      project: prod
      source:
        repoURL: https://git.example.com/platform/apps.git
        targetRevision: main
        path: '{{path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{path.basename}}'
      syncPolicy:
        automated:
          enabled: true
          selfHeal: true
          prune: true
```

### Senior-level point

When troubleshooting self-healing on an ApplicationSet-managed app, always inspect the ApplicationSet template first.

Argo CD tracks resources that belong to an application. Tracking can use labels or annotations depending on configuration.

Common tracking label:

```text
app.kubernetes.io/instance=<application-name>
```

If resources are missing tracking metadata, duplicated across applications, or manually copied, Argo CD may behave unexpectedly.

```bash

```

```bash

```

```bash

```

### Watch for shared resources

Avoid multiple Argo CD applications managing the same object. Two applications self-healing the same resource is a serious design bug.

Symptoms:

```text
Application A syncs Deployment to image v1
Application B syncs same Deployment to image v2
Application A reverts it
Application B reverts it again
```

This creates a GitOps fight.

## 30. Common Troubleshooting: Self-Healing Not Working

### Problem 1: Application is OutOfSync but not reverting

Check:

```bash
argocd app get <app-name>
```

Possible causes:

- `automated.enabled` is `false`.
- `selfHeal` is not `true`.
- Sync window denies sync.
- Previous sync failed.
- Resource is ignored by `ignoreDifferences`.
- Resource has `argocd.argoproj.io/sync-options: Prune=false` or other special sync option.
- Argo CD lacks RBAC permissions.
- Application is generated by ApplicationSet and template differs from live Application.
- The drift is in a field that Argo CD intentionally ignores.

### Problem 2: Drift returns again after self-healing

Possible causes:

- HPA modifies replicas.
- Operator modifies the resource.
- Admission webhook injects fields.
- Mutating webhook changes defaults.
- Another Argo CD application manages the same resource.
- Another automation tool such as Ansible, Helm, Terraform, Jenkins, or a custom controller changes the object.

### Problem 3: Application repeatedly goes OutOfSync

Check diff:

```bash
argocd app diff <app-name>
```

Check managed fields:

```bash
oc get deployment <name> -n <namespace> -o yaml --show-managed-fields
```

Check events:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Check controllers:

```bash
oc describe deployment <name> -n <namespace>
oc get hpa -n <namespace>
oc get mutatingwebhookconfiguration
oc get validatingwebhookconfiguration
```

### Problem 4: Manual hotfix keeps disappearing

This is expected if the hotfix was not committed to Git.

Correct process:

```text
1. Make emergency change in Git.
2. Merge through approved emergency process.
3. Let Argo CD sync/self-heal.
```

Temporary workaround, only if approved:

```bash
argocd app set <app-name> --sync-policy none
```

Or patch automated sync off:

```bash
oc patch application <app-name> -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":false}}}}'
```

For ApplicationSet-managed apps, change the ApplicationSet template or use the supported temporary toggle process for your Argo CD version and organization standard.

## 32. Production Policy Recommendations

### Recommended for dev/test

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
    prune: true
  syncOptions:
    - CreateNamespace=true
```

Reason:

- Fast feedback.
- Developers learn GitOps discipline.
- Lower risk environment.
- Automatic namespace creation may be acceptable.

### Recommended for production applications

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
    prune: true
  syncOptions:
    - CreateNamespace=false
    - PruneLast=true
    - ApplyOutOfSyncOnly=true
```

Additional production controls:

- Protected Git branches.
- Mandatory pull request review.
- CODEOWNERS.
- Signed commits, if required.
- AppProject restrictions.
- Sync windows for high-risk apps.
- Notifications on sync failure and repeated drift.
- Separate Argo CD projects per team/environment.
- Avoid broad cluster-admin permissions.

### Recommended for cluster configuration

For sensitive cluster-level configuration, consider:

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
    prune: false
```

Or:

```yaml
syncPolicy:
  automated:
    enabled: false
    selfHeal: true
    prune: true
```

The second option records policy intent but disables active automation until explicitly enabled.

Use manual sync for high-risk cluster-scoped resources if the organization is not mature enough for full auto-remediation.

## 33. Security Considerations

Self-healing has security benefits and risks.

### Security benefits

- Reverts unauthorized manual changes.
- Reduces configuration drift.
- Enforces Git-reviewed desired state.
- Makes cluster state auditable.
- Helps detect direct cluster tampering.
- Supports compliance baselines.

### Security risks

- A malicious or bad Git commit can be automatically applied.
- Over-privileged Argo CD can modify too much.
- Incorrect prune can delete important resources.
- Ignoring too many differences can hide attacks.
- Storing plain Secrets in Git is unsafe.
- Self-healing can revert emergency incident-response changes if Git is not updated.

### Controls

Use:

- Git branch protection.
- Least-privilege AppProjects.
- Least-privilege OpenShift RBAC.
- Commit signing, where required.
- Admission control policies.
- Secret management tooling.
- Argo CD notifications.
- Audit logs.
- Pull request approvals.
- Sync windows for critical workloads.

## 35. Real-World Failure Scenarios

### Scenario 1: HPA fight

Symptom:

```text
Deployment repeatedly flips replicas between 3 and 6.
```

Cause:

```text
HPA scales replicas, Argo CD self-heals replicas back to Git.
```

Fix:

```yaml
ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:
      - /spec/replicas
syncPolicy:
  syncOptions:
    - RespectIgnoreDifferences=true
```

---

### Scenario 2: Route hotfix reverted

Symptom:

```text
Admin changes Route hostname or TLS config from console. Argo CD reverts it.
```

Cause:

```text
Route is Git-managed and selfHeal=true.
```

Fix:

```text
Update Route YAML in Git and merge.
```

---

### Scenario 3: Operator mutation causes OutOfSync loop

Symptom:

```text
Application constantly OutOfSync, but nobody changed Git.
```

Cause:

```text
Operator or webhook mutates spec fields after sync.
```

Fix:

```text
Use targeted ignoreDifferences only for the specific field and resource.
```

---

### Scenario 4: Self-healing not working after patching Application

Symptom:

```text
Admin patches Application to disable self-heal, but it returns.
```

Cause:

```text
Application is generated by ApplicationSet.
```

Fix:

```text
Change ApplicationSet template, not generated Application.
```

---

### Scenario 5: Prune deletes unexpected resource

Symptom:

```text
Resource disappears after Git cleanup.
```

Cause:

```text
Resource was removed from Git and automated prune is enabled.
```

Fix:

```text
Restore Git manifest or recover from backup. For future, use Prune=confirm or Prune=false for critical resources.
```

## 36. Best Practices for 10-Year Experienced Administrators

1. Treat Git as the only supported write path for managed resources.
2. Use self-healing for workloads, but design exceptions for autoscalers and operators.
3. Do not allow multiple tools to own the same Kubernetes field.
4. Do not allow multiple Argo CD applications to own the same resource.
5. Keep AppProjects strict and environment-specific.
6. Enable `selfHeal` in production only after Git review and RBAC controls are mature.
7. Use `prune` carefully and add confirmation for critical resources.
8. Do not store plain sensitive Secrets in Git.
9. Use `ignoreDifferences` narrowly, not globally.
10. Document emergency hotfix procedure.
11. Monitor repeated drift as a security and process smell.
12. Ensure teams understand that console changes to GitOps-managed resources are temporary.
13. Use sync waves for ordered recovery when dependencies matter.
14. Use protected branches and CODEOWNERS for production directories.
15. Test self-healing in lower environments before enabling it cluster-wide.

## 37. Recommended Emergency Procedure

Sometimes production requires an emergency manual change. Self-healing changes how that procedure works.

### Preferred emergency GitOps flow

```text
1. Create emergency branch.
2. Commit required manifest change.
3. Fast-track review and approval.
4. Merge to protected branch.
5. Let Argo CD sync automatically.
6. Verify health and sync status.
7. Create post-incident review.
```

### Temporary manual hotfix flow

Use only when Git flow is too slow for the incident.

```text
1. Temporarily disable automated sync for the affected application.
2. Apply manual cluster fix.
3. Immediately commit the same fix to Git.
4. Re-enable automated sync and self-heal.
5. Confirm Argo CD is Synced and Healthy.
```

Example disable command:

```bash
oc patch application payment-api-prod -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":false}}}}'
```

Example re-enable command:

```bash
oc patch application payment-api-prod -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":{"automated":{"enabled":true,"selfHeal":true,"prune":true}}}}'
```

For ApplicationSet-generated apps, change the ApplicationSet or use the organization's approved temporary override process.

## 38. Interview Explanation

A strong interview answer:

```text
In OpenShift GitOps, self-healing is Argo CD's ability to detect configuration drift between Git and the live OpenShift cluster and automatically reconcile the live state back to Git. It is enabled under spec.syncPolicy.automated.selfHeal=true, usually together with automated sync. Auto-sync handles Git changes; self-heal handles live cluster drift; prune handles resources removed from Git. The application-controller performs the comparison and sync. In OpenShift, we must also ensure the target namespace is managed by the Argo CD instance, AppProject permissions allow the destination and resource kinds, and the controller has RBAC permission to patch/update resources. For production, I would combine self-heal with protected Git branches, AppProject restrictions, sync windows where needed, narrow ignoreDifferences for HPA/operator-managed fields, and careful pruning controls like Prune=confirm for critical resources.
```

## 39. Exam / Lab Style Task

### Task

Create an Argo CD application named `web-prod` in `openshift-gitops` namespace that deploys manifests from:

```text
https://git.example.com/gitops/web.git
path: overlays/prod
target namespace: web-prod
```

Requirements:

- Auto-sync enabled.
- Self-healing enabled.
- Pruning enabled.
- Do not auto-create namespace.
- Ignore `/spec/replicas` for Deployments because HPA manages scaling.

### Answer

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-prod
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/gitops/web.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: web-prod
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    automated:
      enabled: true
      selfHeal: true
      prune: true
    syncOptions:
      - CreateNamespace=false
      - RespectIgnoreDifferences=true
      - PruneLast=true
```

### Test

```bash
oc label namespace web-prod argocd.argoproj.io/managed-by=openshift-gitops --overwrite
oc apply -f web-prod-application.yaml
oc get application web-prod -n openshift-gitops
argocd app get web-prod
```

Create drift:

```bash
oc set env deployment/web -n web-prod TEST_DRIFT=true
```

Watch self-heal:

```bash
watch -n 2 'argocd app get web-prod | egrep "Sync Status|Health Status"'
```

If `TEST_DRIFT=true` is not in Git, Argo CD should remove that manual env var during self-healing.

## 41. Final Production Checklist

Before enabling self-healing broadly, confirm:

- [ ] Application manifests are clean and deterministic.
- [ ] Git repository structure separates dev/test/prod.
- [ ] Production branch is protected.
- [ ] Pull request review is mandatory.
- [ ] AppProject restricts repositories and destinations.
- [ ] Argo CD has only required permissions.
- [ ] Target namespaces are correctly managed by the Argo CD instance.
- [ ] HPA-managed replicas are ignored or removed from Git.
- [ ] Operator-mutated fields are handled with narrow ignore rules.
- [ ] Prune policy is agreed and documented.
- [ ] Critical resources use `Prune=confirm` or `Prune=false` if needed.
- [ ] Emergency hotfix process is documented.
- [ ] Application sync failures trigger alerts.
- [ ] Repeated drift is investigated, not ignored.
- [ ] Teams are trained not to edit GitOps-managed resources directly in console.

## 42. Key Takeaways

- Self-healing means Argo CD automatically fixes live cluster drift by restoring Git-defined desired state.
- Auto-sync handles Git changes; self-healing handles live cluster changes; prune handles deletion of resources removed from Git.
- `selfHeal: true` only works as active automation when automated sync is enabled.
- OpenShift namespace management, AppProject rules, and RBAC are critical for self-healing to work.
- HPA, Operators, mutating webhooks, and external secret controllers can create legitimate drift; handle these with careful ownership boundaries and narrow `ignoreDifferences` rules.
- Self-healing improves compliance and operational consistency, but a bad Git commit can be automatically enforced.
- In production, self-healing should be combined with Git controls, AppProject restrictions, monitoring, and a documented emergency process.
