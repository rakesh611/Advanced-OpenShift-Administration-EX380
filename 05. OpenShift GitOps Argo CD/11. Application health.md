## 1. What Application Health Means

In OpenShift GitOps, **Application health** is Argo CD's operational view of whether the Kubernetes/OpenShift resources managed by an `Application` appear to be functioning correctly.

It answers this question:

> "The desired manifests were applied, but are the resulting resources actually ready, admitted, bound, running, or otherwise operational?"

For an experienced OpenShift administrator, this distinction is critical. GitOps is not only about applying YAML from Git. A production deployment is successful only when the desired state converges **and** the runtime resources reach a usable condition.

For example:

- A `Deployment` can be applied successfully but have pods in `ImagePullBackOff`.
- A `Route` can exist but not be admitted by the router.
- A `PersistentVolumeClaim` can be created but stay `Pending` because no matching storage exists.
- An Operator `Subscription` can be applied but wait forever for an install plan or catalog source.
- A `Service` can be created but point to no endpoints because labels do not match pods.

In all of these examples, the Git manifests may be present in the cluster, but the application is not truly healthy.

Argo CD surfaces this using **health status** on resources and on the parent `Application`.

## 2. Health vs Sync vs Operation Status

A common admin mistake is treating `Synced` as equal to `Healthy`. They are different dimensions.

### 2.1 Sync Status

**Sync status** tells you whether the live cluster state matches the desired state from Git.

Typical sync values:

| Sync status | Meaning |
|---|---|
| `Synced` | Live objects match the desired Git revision according to Argo CD's comparison logic. |
| `OutOfSync` | Live objects differ from Git, or expected objects are missing/extra. |
| `Unknown` | Argo CD cannot reliably compare desired and live state, usually because of access, rendering, cluster, or cache issues. |

### 2.2 Health Status

**Health status** tells you whether the live resources are operational according to built-in or custom health logic.

Typical health values:

| Health status | Meaning |
|---|---|
| `Healthy` | Resource appears operational. |
| `Progressing` | Resource is moving toward readiness but is not ready yet. |
| `Degraded` | Resource exists but is failing or has exceeded expectations. |
| `Missing` | Expected resource is absent from the live cluster. |
| `Suspended` | Resource is intentionally paused/suspended. |
| `Unknown` | Argo CD cannot determine health. |

### 2.3 Operation Status

**Operation status** describes the current or last Argo CD operation, usually a sync.

Examples:

- `Running`
- `Succeeded`
- `Failed`
- `Error`
- `Terminating`

### 2.4 Important Production Combinations

| Sync | Health | What it means operationally |
|---|---|---|
| `Synced` | `Healthy` | Desired target state is applied and resources look healthy. This is the normal good state. |
| `Synced` | `Progressing` | Git desired state is applied, but rollout/readiness is still ongoing. Wait or investigate if it is stuck. |
| `Synced` | `Degraded` | Git state is applied, but runtime is broken. This is a real production problem. |
| `OutOfSync` | `Healthy` | Current live app may be running, but it does not match Git. This is drift or pending change. |
| `OutOfSync` | `Degraded` | Both desired-state convergence and runtime are problematic. Treat as high priority. |
| `Unknown` | `Unknown` | Argo CD lacks enough information. Check repo-server, controller, cluster credentials, RBAC, API discovery, and cache. |

### 2.5 Senior Admin Rule

Never close a deployment incident only because the Argo CD application is `Synced`. Confirm the health status, managed resources, events, workload readiness, route/service reachability, and application-level probes.

## 3. Where Health Is Calculated in Argo CD Architecture

Application health is mainly handled by the **Argo CD application controller**.

At a high level:

1. The repo-server renders manifests from Git, Helm, Kustomize, Jsonnet, or plain YAML.
2. The application controller compares desired resources against live resources.
3. The controller watches/caches Kubernetes resources from destination clusters.
4. For each managed resource, Argo CD runs built-in or custom health logic.
5. Argo CD aggregates immediate child resource health into the `Application` health.
6. The API server/UI/CLI expose the result.
7. Metrics expose health status through Prometheus labels such as `health_status`.

### 3.1 Key Components Involved

| Component | Health-related responsibility |
|---|---|
| `argocd-application-controller` | Main reconciliation engine. Calculates sync and health status. |
| `argocd-repo-server` | Renders desired manifests; render failures can prevent useful health evaluation. |
| `argocd-server` | Exposes UI/API/CLI view of health. |
| Redis | Caches state; cache problems may cause stale or delayed UI/API status. |
| Kubernetes/OpenShift API | Source of live resource status, events, and conditions. |
| OpenShift GitOps Operator | Manages Argo CD instance configuration, including health customization fields in the `ArgoCD` CR. |

### 3.2 Why Controller Health Logic Matters

When an application remains `Progressing` or `Unknown`, do not only look at the Argo CD UI. Check:

```bash
oc get pods -n openshift-gitops
oc logs -n openshift-gitops statefulset/openshift-gitops-application-controller
oc get applications.argoproj.io -A
oc describe application <app-name> -n <argocd-namespace>
```

In a user-defined Argo CD instance, replace `openshift-gitops` with the namespace where your instance is installed.

## 4. Application Health Status Values

Argo CD uses a small set of health states. Understanding them precisely is important for troubleshooting and alerting.

### 4.1 `Healthy`

`Healthy` means the resource has reached the expected operational condition.

Examples:

- `Deployment` observed generation matches desired generation and updated replicas match desired replicas.
- `PVC` is `Bound`.
- `Ingress` has load balancer ingress populated.
- A custom resource health check finds a `Ready=True` condition.

Admin meaning:

> The resource is not obviously broken from Argo CD's perspective.

Important: `Healthy` does not always mean the business application is working. Argo CD does not automatically run HTTP transactions, database queries, login tests, or synthetic monitoring. It evaluates Kubernetes/OpenShift resource status.

### 4.2 `Progressing`

`Progressing` means the resource is not healthy yet, but it might become healthy soon.

Examples:

- Deployment rollout is still updating.
- StatefulSet has not updated all replicas yet.
- PVC is waiting for binding.
- Route is waiting for admission.
- Operator installation is waiting for an install plan or CSV.

Admin meaning:

> This is acceptable for a short rollout window, but suspicious if it remains for too long.

A 30-second `Progressing` deployment is normal. A 45-minute `Progressing` deployment is usually an incident.

### 4.3 `Degraded`

`Degraded` means the resource exists but is in a failed or unhealthy condition.

Examples:

- Rollout timeout.
- Failed job.
- CronJob last scheduled job failed.
- Custom resource reports `Ready=False` with an error reason.
- Route admission failed.
- Operator CSV failed.

Admin meaning:

> Argo CD sees a live object, but that object is reporting failure.

### 4.4 `Missing`

`Missing` means Argo CD expects the resource because it is in the desired source, but the live resource is not found.

Common reasons:

- Resource was manually deleted.
- Namespace was deleted.
- CRD is not installed, so the resource cannot be created.
- Sync failed before creating the resource.
- RBAC prevents Argo CD from reading the resource.
- Resource tracking labels/annotations are wrong.

Admin meaning:

> Check whether this is intentional pruning, an apply failure, missing CRD, namespace issue, or tracking problem.

### 4.5 `Suspended`

`Suspended` means the resource is intentionally paused or suspended.

Examples:

- Suspended Kubernetes `Job`.
- Paused/suspended workload type supported by health logic.

Admin meaning:

> Not necessarily broken; verify whether the suspension is intentional.

### 4.6 `Unknown`

`Unknown` means Argo CD cannot determine the health.

Common reasons:

- No built-in health check exists for a custom resource.
- Custom health script has a bug.
- Argo CD has API/RBAC/discovery problems.
- Cluster cache is stale.
- Resource status fields do not follow a predictable pattern.

Admin meaning:

> You need to inspect the resource type, its `.status`, and whether a custom health check is required.

## 5. How Argo CD Calculates Application Health

### 5.1 Immediate Child Resource Model

Argo CD calculates an application's health from the health of the application's **immediate child resources** represented in the application source.

For example, suppose your Git path contains:

```text
app/
├── deployment.yaml
├── service.yaml
├── route.yaml
└── configmap.yaml
```

The Argo CD `Application` health is calculated from those direct resources.

### 5.2 Worst-Health Aggregation

The application receives the worst relevant health among its immediate children.

A simple mental model:

```text
Application
├── Deployment      Healthy
├── Service         Healthy
├── Route           Progressing
└── ConfigMap       Healthy / no health impact

Application health = Progressing
```

If one important child is `Degraded`, the parent application becomes `Degraded`.

### 5.3 Health Is Not Automatically Inherited from Grandchildren

This is very important.

Argo CD does **not** automatically infer a parent resource's health from all child resources below it.

Example:

```text
Application
└── CustomResource        Healthy
    └── GeneratedPod      CrashLoopBackOff
```

If the custom resource's own `.status` says it is healthy, or if the custom health check ignores generated child objects, the Argo CD application may still appear healthy.

Why?

Because the health check for the custom resource sees only the custom resource object. It does not automatically traverse all children created by that controller.

### 5.4 Operator-Managed Resources

OpenShift Operators often create secondary resources:

- Deployments
- Services
- Secrets
- ConfigMaps
- Routes
- Pods
- Jobs
- Operand CRs

If Git only contains the top-level custom resource, then Argo CD health depends heavily on whether that custom resource reports meaningful `.status.conditions` and whether Argo CD has a health check for that kind.

Senior admin recommendation:

> For every critical custom resource managed by GitOps, inspect its `.status.conditions` and decide whether built-in health is enough or a custom health check is required.

## 6. Built-in Health Checks

Argo CD ships built-in health assessment for common Kubernetes resource kinds. The exact behavior can vary by Argo CD version, but the following are the standard operational patterns.

### 6.1 Deployment, ReplicaSet, StatefulSet, DaemonSet

Argo CD checks rollout-related status such as:

- Observed generation equals desired generation.
- Updated replicas match desired replicas.
- Controller has reconciled the latest spec.

Typical problems causing `Progressing` or `Degraded`:

```bash
oc get deploy -n <ns>
oc rollout status deploy/<name> -n <ns>
oc describe deploy/<name> -n <ns>
oc get rs,pod -n <ns> -l app=<label>
oc get events -n <ns> --sort-by=.lastTimestamp
```

Common causes:

- Image pull failure
- Bad readiness probe
- Insufficient CPU/memory
- SCC/PSA denial
- Volume mount failure
- Node selector mismatch
- Taint/toleration mismatch
- CrashLoopBackOff
- Deployment paused
- Quota/LimitRange denial

### 6.2 Service

For a `LoadBalancer` service, health expects load balancer ingress information to be populated.

On OpenShift, many internal services are `ClusterIP`, and service health may not be enough to confirm traffic. You should also check endpoints:

```bash
oc get svc <svc> -n <ns>
oc get endpoints <svc> -n <ns>
oc get endpointslice -n <ns> -l kubernetes.io/service-name=<svc>
```

A service can exist and still be useless if selectors do not match pods.

### 6.3 Ingress

For Kubernetes `Ingress`, Argo CD checks load balancer ingress status.

On OpenShift, many environments use `Route` instead of `Ingress`, so Route health must be handled through OpenShift-specific checks or custom health logic when needed.

### 6.4 CronJob

A CronJob may be marked degraded if the last scheduled job failed, or progressing if the current job is running.

Useful commands:

```bash
oc get cronjob -n <ns>
oc get jobs -n <ns>
oc describe cronjob <name> -n <ns>
oc logs job/<job-name> -n <ns>
```

### 6.5 Job

A Job may be healthy, progressing, degraded, or suspended depending on completion/failure/suspension state.

GitOps warning:

> Do not manage one-shot Jobs casually with auto-sync and prune unless you understand hooks, delete policies, and idempotency.

### 6.6 PersistentVolumeClaim

A PVC is generally healthy when it is `Bound`.

Common `Progressing` causes:

- No matching PV.
- StorageClass unavailable.
- Dynamic provisioner issue.
- `WaitForFirstConsumer` waiting for a pod.
- Access mode mismatch.
- Requested capacity too large.
- Topology/zone mismatch.

Commands:

```bash
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get pv
oc get sc
oc get events -n <ns> --sort-by=.lastTimestamp
```

## 7. OpenShift-Specific Health Considerations

OpenShift GitOps is Argo CD integrated and packaged for OpenShift. OpenShift adds resources and operational behavior that a plain Kubernetes Argo CD installation might not understand without customization.

### 7.1 OpenShift Route Health

A `Route` can exist but not be admitted by the router.

Check:

```bash
oc get route -n <ns>
oc describe route <route> -n <ns>
oc get route <route> -n <ns> -o yaml
```

Look for:

```yaml
status:
  ingress:
  - conditions:
    - type: Admitted
      status: "True"
```

Common route health issues:

- Hostname conflict.
- Router shard does not select the route.
- TLS configuration error.
- Service target does not exist.
- Wrong service port.
- No endpoints behind service.

### 7.2 DeploymentConfig Health

Some legacy or OpenShift-native workloads still use `DeploymentConfig`.

Check:

```bash
oc get dc -n <ns>
oc rollout status dc/<name> -n <ns>
oc describe dc/<name> -n <ns>
oc get rc,pod -n <ns> -l deploymentconfig=<name>
```

Common issues:

- DeploymentConfig rollout stuck.
- ImageStream trigger not resolving.
- ReplicationController old/new replica mismatch.
- Hook failure.
- ConfigChange/ImageChange trigger confusion.

### 7.3 Operator Lifecycle Manager Resources

OpenShift Operators are installed through OLM resources such as:

- `Subscription`
- `InstallPlan`
- `ClusterServiceVersion` / CSV
- `OperatorGroup`
- `CatalogSource`

Useful commands:

```bash
oc get sub,ip,csv,og -n <operator-namespace>
oc describe sub <subscription> -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc get catalogsource -A
```

Common OLM health problems:

- CatalogSource not ready.
- Package/channel does not exist.
- Manual InstallPlan approval pending.
- CSV failed requirements.
- OperatorGroup mismatch.
- Operator namespace has insufficient permissions.
- Dependency operator missing.

### 7.4 SCC and Pod Security Admission

On OpenShift, pod creation can fail because of Security Context Constraints or restricted Pod Security Admission labels.

Symptoms:

- Deployment `Progressing` forever.
- ReplicaSet exists but no pods are created.
- Events show `would violate PodSecurity` or SCC denial.

Commands:

```bash
oc get events -n <ns> --sort-by=.lastTimestamp
oc describe rs <replicaset> -n <ns>
oc get sa -n <ns>
oc adm policy who-can use scc anyuid
```

For production, prefer a properly designed SCC/RBAC model. Avoid giving `anyuid` broadly.

### 7.5 Namespace Management Label

For an Argo CD instance to manage resources outside its own namespace in OpenShift GitOps, the target namespace normally needs the management label:

```bash
oc label namespace <target_namespace> \
  argocd.argoproj.io/managed-by=<argocd_namespace>
```

Example for the default GitOps instance:

```bash
oc label namespace my-app \
  argocd.argoproj.io/managed-by=openshift-gitops
```

If this label is missing, you can see sync failures, resource access problems, or missing/unknown status depending on RBAC and instance scope.

### 7.6 Multi-Instance Tracking

In multi-tenant clusters, multiple Argo CD instances may manage separate namespaces. Resource tracking must be designed carefully to avoid conflicts.

OpenShift GitOps supports configuring the tracking method, and newer guidance recommends unique `installationID` values and `annotation+label` tracking in multi-instance scenarios.

## 8. Reading Health from CLI, YAML, UI, and Metrics

### 8.1 Argo CD CLI

```bash
argocd app get <app-name>
```

Example output fields to inspect:

```text
Name:               openshift-gitops/my-app
Project:            default
Sync Status:        Synced to main (abc1234)
Health Status:      Healthy
```

Wait for health:

```bash
argocd app wait <app-name> --health
```

Wait for sync and health:

```bash
argocd app wait <app-name> --sync --health --timeout 300
```

List applications:

```bash
argocd app list
```

### 8.2 OpenShift CLI Using Application CR

```bash
oc get applications.argoproj.io -A
```

Get sync and health quickly:

```bash
oc get application <app-name> -n <argocd-namespace> \
  -o jsonpath='{.status.sync.status}{"\t"}{.status.health.status}{"\n"}'
```

Get health message:

```bash
oc get application <app-name> -n <argocd-namespace> \
  -o jsonpath='{.status.health.message}{"\n"}'
```

Show managed resources and health:

```bash
oc get application <app-name> -n <argocd-namespace> -o json | jq '.status.resources[] | {kind,name,namespace,status,health}'
```

Without `jq`:

```bash
oc get application <app-name> -n <argocd-namespace> -o yaml
```

### 8.3 Argo CD UI

In UI, check:

- Application tile health badge.
- Resource tree.
- Individual resource status icons.
- Events tab.
- Manifest tab.
- Diff tab.
- Sync result.

For production troubleshooting, the UI is useful but not enough. Always verify with `oc describe`, events, logs, and resource YAML.

### 8.4 OpenShift Console Developer Perspective

The OpenShift Console can show GitOps environment information and health indicators when applications/namespaces use the expected labels and annotations.

Useful for teams:

- Environment status.
- Deployment history.
- Resource health indicators.
- Links to Git revisions.

### 8.5 Prometheus Metrics

Argo CD exposes application metrics such as `argocd_app_info`, with labels including `sync_status` and `health_status`.

Example PromQL:

```promql
sum(argocd_app_info{health_status!=""}) by (health_status)
```

For a namespace:

```promql

```

Degraded apps:

```promql

```

Apps stuck progressing:

```promql
argocd_app_info{health_status="Progressing"}
```

Unknown health:

```promql
argocd_app_info{health_status="Unknown"}
```

## 9. Application Health in the Argo CD Application CR

An Argo CD application is represented by a Kubernetes custom resource:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/apps.git
    targetRevision: main
    path: apps/my-app
  destination:
    server: https://kubernetes.default.svc
    namespace: my-app
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

After reconciliation, status appears under `.status`:

```yaml
status:
  sync:
    status: Synced
    revision: abcdef123456
  health:
    status: Healthy
    message: ""
  resources:
  - group: apps
    kind: Deployment
    namespace: my-app
    name: my-app
    status: Synced
    health:
      status: Healthy
  - kind: Service
    namespace: my-app
    name: my-app
    status: Synced
  - group: route.openshift.io
    kind: Route
    namespace: my-app
    name: my-app
    status: Synced
    health:
      status: Healthy
```

### 9.1 Important Fields

| Field | Meaning |
|---|---|
| `.status.sync.status` | Whether live state matches Git. |
| `.status.health.status` | Application-level health. |
| `.status.resources[]` | List of managed resources. |
| `.status.resources[].health.status` | Resource-level health when available. |
| `.status.conditions[]` | Application-level warnings/errors. |
| `.status.operationState` | Current or previous sync operation state. |
| `.status.reconciledAt` | Last reconciliation timestamp. |

### 9.2 Useful JSONPath Commands

```bash
# Application health only
oc get app my-app -n openshift-gitops \
  -o jsonpath='{.status.health.status}{"\n"}'

# Application sync and health
oc get app my-app -n openshift-gitops \
  -o jsonpath='{.status.sync.status}{" "}{.status.health.status}{"\n"}'

# Reconciled revision
oc get app my-app -n openshift-gitops \
  -o jsonpath='{.status.sync.revision}{"\n"}'

# Operation phase
oc get app my-app -n openshift-gitops \
  -o jsonpath='{.status.operationState.phase}{"\n"}'
```

## 10. Custom Resource Health Checks with Lua

Argo CD supports custom health checks written in Lua. This is essential for CRDs and OpenShift/Operator resources that do not have reliable built-in health logic.

### 10.1 Why Custom Health Checks Are Needed

Kubernetes CRDs do not have a universal health schema. One operator may use:

```yaml
status:
  conditions:
  - type: Ready
    status: "True"
```

Another may use:

```yaml
status:
  phase: Available
```

Another may use:

```yaml
status:
  state: Reconciled
```

Argo CD cannot guess every controller's meaning. For reliable health, you must teach Argo CD how to interpret that CRD's `.status`.

### 10.2 Lua Health Check Contract

A Lua health check receives the resource object as the global variable `obj` and returns a table with:

```lua
hs = {}
hs.status = "Healthy"      -- or Progressing, Degraded, Suspended
hs.message = "message"
return hs
```

Common statuses returned by custom checks:

- `Healthy`
- `Progressing`
- `Degraded`
- `Suspended`

### 10.3 Good Health Check Design

A production-grade health check should:

1. Use `.metadata.generation` and `.status.observedGeneration` when available.
2. Prefer explicit conditions such as `Ready=True` or `Available=True`.
3. Return `Progressing` while the controller has not observed the latest generation.
4. Return `Degraded` for terminal failure conditions.
5. Include a useful message from the resource condition.
6. Be small and specific to one resource kind.
7. Avoid broad wildcard scripts unless the resources share a status schema.
8. Be tested with real resource YAML from the cluster.

### 10.4 Observed Generation Pattern

Many controllers expose:

```yaml
metadata:
  generation: 7
status:
  observedGeneration: 6
```

This means the controller has not reconciled the newest spec yet.

A good health script should return `Progressing` until observed generation catches up:

```lua
if obj.status ~= nil and obj.status.observedGeneration ~= nil then
  if obj.metadata ~= nil and obj.metadata.generation ~= nil then
    if obj.status.observedGeneration < obj.metadata.generation then
      hs.status = "Progressing"
      hs.message = "Waiting for controller to observe latest generation"
      return hs
    end
  end
end
```

### 10.5 Condition Pattern

Many resources use conditions:

```yaml
status:
  conditions:
  - type: Ready
    status: "True"
    reason: Reconciled
    message: Resource is ready
```

Lua pattern:

```lua
if obj.status ~= nil and obj.status.conditions ~= nil then
  for i, condition in ipairs(obj.status.conditions) do
    if condition.type == "Ready" and condition.status == "True" then
      hs.status = "Healthy"
      hs.message = condition.message
      return hs
    end
    if condition.type == "Ready" and condition.status == "False" then
      hs.status = "Degraded"
      hs.message = condition.message
      return hs
    end
  end
end
```

## 11. Configuring Health Checks in OpenShift GitOps

In plain Argo CD, custom health checks are commonly placed in the `argocd-cm` ConfigMap.

In **OpenShift GitOps**, the Argo CD instance is Operator-managed. You should normally configure custom health checks through the `ArgoCD` custom resource instead of manually editing generated ConfigMaps that the Operator may reconcile.

### 11.1 Check the Argo CD Instance

```bash
oc get argocd -A
```

Example:

```text
NAMESPACE          NAME              AGE
openshift-gitops   openshift-gitops  30d
```

### 11.2 Edit the ArgoCD CR

```bash
oc edit argocd openshift-gitops -n openshift-gitops
```

### 11.3 Example Custom Health Check in ArgoCD CR

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  resourceHealthChecks:
    - group: cert-manager.io
      kind: Certificate
      check: |
        hs = {}
        if obj.status ~= nil then
          if obj.status.conditions ~= nil then
            for i, condition in ipairs(obj.status.conditions) do
              if condition.type == "Ready" and condition.status == "False" then
                hs.status = "Degraded"
                hs.message = condition.message
                return hs
              end
              if condition.type == "Ready" and condition.status == "True" then
                hs.status = "Healthy"
                hs.message = condition.message
                return hs
              end
            end
          end
        end
        hs.status = "Progressing"
        hs.message = "Waiting for certificate to become Ready"
        return hs
```

### 11.4 Verify Generated Configuration

Depending on the instance name and Operator behavior, generated ConfigMaps may be named with the instance prefix. Check them rather than assuming:

```bash
oc get cm -n openshift-gitops | grep cm
oc get cm -n openshift-gitops -o name | grep gitops
```

Then inspect:

```bash
oc get cm <argocd-config-cm> -n openshift-gitops -o yaml
```

Look for keys similar to:

```yaml
resource.customizations.health.cert-manager.io_Certificate: |
  hs = {}
  ...
```

### 11.5 Restart/Reconcile Consideration

The Operator and Argo CD components usually reconcile configuration, but if the health check does not appear to take effect, check:

```bash
oc get argocd openshift-gitops -n openshift-gitops -o yaml
oc get pods -n openshift-gitops
oc logs -n openshift-gitops deploy/openshift-gitops-server
oc logs -n openshift-gitops statefulset/openshift-gitops-application-controller
```

In some cases, a component restart or waiting for reconciliation is required.

## 12. Practical Health Check Examples

These examples are intentionally written in an operational style. Validate them against your actual resource `.status` before using in production.

### 12.1 OpenShift Route Health Check

Purpose: mark a Route healthy only when admitted.

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  resourceHealthChecks:
    - group: route.openshift.io
      kind: Route
      check: |
        hs = {}
        hs.status = "Progressing"
        hs.message = "Waiting for route admission"

        if obj.status ~= nil and obj.status.ingress ~= nil then
          for i, ingress in ipairs(obj.status.ingress) do
            if ingress.conditions ~= nil then
              for j, condition in ipairs(ingress.conditions) do
                if condition.type == "Admitted" and condition.status == "True" then
                  hs.status = "Healthy"
                  hs.message = "Route admitted"
                  return hs
                end
                if condition.type == "Admitted" and condition.status == "False" then
                  hs.status = "Degraded"
                  if condition.message ~= nil then
                    hs.message = condition.message
                  else
                    hs.message = "Route admission failed"
                  end
                  return hs
                end
              end
            end
          end
        end

        return hs
```

Troubleshoot if degraded:

```bash
oc describe route <route> -n <ns>
oc get route <route> -n <ns> -o yaml
oc get svc <svc> -n <ns>
oc get endpoints <svc> -n <ns>
```

### 12.2 DeploymentConfig Health Check

Purpose: support OpenShift `DeploymentConfig` health in environments where it is not already covered.

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  resourceHealthChecks:
    - group: apps.openshift.io
      kind: DeploymentConfig
      check: |
        hs = {}
        hs.status = "Progressing"
        hs.message = "Waiting for DeploymentConfig rollout"

        if obj.status ~= nil then
          if obj.status.observedGeneration ~= nil and obj.metadata ~= nil and obj.metadata.generation ~= nil then
            if obj.status.observedGeneration < obj.metadata.generation then
              hs.status = "Progressing"
              hs.message = "Controller has not observed latest generation"
              return hs
            end
          end

          if obj.status.conditions ~= nil then
            for i, condition in ipairs(obj.status.conditions) do
              if condition.type == "Available" and condition.status == "True" then
                hs.status = "Healthy"
                hs.message = condition.message or "DeploymentConfig is available"
                return hs
              end
              if condition.type == "Progressing" and condition.status == "False" then
                hs.status = "Degraded"
                hs.message = condition.message or "DeploymentConfig rollout failed"
                return hs
              end
            end
          end
        end

        return hs
```

Troubleshoot:

```bash
oc rollout status dc/<dc-name> -n <ns>
oc describe dc/<dc-name> -n <ns>
oc get rc,pod -n <ns> -l deploymentconfig=<dc-name>
```

### 12.3 Generic Ready Condition Health Check

Purpose: for CRDs with a standard `Ready` condition.

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  resourceHealthChecks:
    - group: example.com
      kind: ExampleResource
      check: |
        hs = {}

        if obj.status ~= nil and obj.status.observedGeneration ~= nil then
          if obj.metadata ~= nil and obj.metadata.generation ~= nil then
            if obj.status.observedGeneration < obj.metadata.generation then
              hs.status = "Progressing"
              hs.message = "Waiting for controller to observe latest generation"
              return hs
            end
          end
        end

        if obj.status ~= nil and obj.status.conditions ~= nil then
          for i, condition in ipairs(obj.status.conditions) do
            if condition.type == "Ready" and condition.status == "True" then
              hs.status = "Healthy"
              hs.message = condition.message or "Ready"
              return hs
            end
            if condition.type == "Ready" and condition.status == "False" then
              hs.status = "Degraded"
              hs.message = condition.message or condition.reason or "Not Ready"
              return hs
            end
          end
        end

        hs.status = "Progressing"
        hs.message = "Waiting for Ready condition"
        return hs
```

### 12.4 Cert-Manager Certificate Health

Purpose: treat `Ready=True` as healthy and `Ready=False` as degraded.

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  resourceHealthChecks:
    - group: cert-manager.io
      kind: Certificate
      check: |
        hs = {}
        if obj.status ~= nil then
          if obj.status.conditions ~= nil then
            for i, condition in ipairs(obj.status.conditions) do
              if condition.type == "Ready" and condition.status == "True" then
                hs.status = "Healthy"
                hs.message = condition.message or "Certificate is ready"
                return hs
              end
              if condition.type == "Ready" and condition.status == "False" then
                hs.status = "Degraded"
                hs.message = condition.message or "Certificate is not ready"
                return hs
              end
            end
          end
        end
        hs.status = "Progressing"
        hs.message = "Waiting for certificate readiness"
        return hs
```

### 12.5 Subscription Health Check Pattern

OLM `Subscription` status differs across versions and scenarios. Use this as a starting pattern only after validating actual `.status` in your cluster.

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  resourceHealthChecks:
    - group: operators.coreos.com
      kind: Subscription
      check: |
        hs = {}
        hs.status = "Progressing"
        hs.message = "Waiting for Subscription resolution"

        if obj.status ~= nil then
          if obj.status.conditions ~= nil then
            for i, condition in ipairs(obj.status.conditions) do
              if condition.type == "CatalogSourcesUnhealthy" and condition.status == "True" then
                hs.status = "Degraded"
                hs.message = condition.message or "Catalog source unhealthy"
                return hs
              end
              if condition.type == "ResolutionFailed" and condition.status == "True" then
                hs.status = "Degraded"
                hs.message = condition.message or "Subscription resolution failed"
                return hs
              end
            end
          end

          if obj.status.installedCSV ~= nil and obj.status.installedCSV ~= "" then
            hs.status = "Healthy"
            hs.message = "Subscription installed CSV: " .. obj.status.installedCSV
            return hs
          end
        end

        return hs
```

After using this, still verify CSV health:

```bash
oc get sub,csv,installplan -n <operator-ns>
oc describe sub <sub> -n <operator-ns>
oc describe csv <csv> -n <operator-ns>
```

## 13. App-of-Apps and Health Propagation

### 13.1 Problem

In the app-of-apps pattern, a parent Argo CD application manages child `Application` resources.

Example:

```text
platform-root
├── app-dev.yaml       # Argo CD Application
├── app-test.yaml      # Argo CD Application
└── app-prod.yaml      # Argo CD Application
```

The parent application manages child `Application` CRs, not the workloads directly.

Argo CD removed built-in health assessment for `argoproj.io/Application` CRs in older versions. This means parent app health may not automatically reflect child app health unless you add a custom health check.

### 13.2 Restore Application Health Propagation

```yaml
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  resourceHealthChecks:
    - group: argoproj.io
      kind: Application
      check: |
        hs = {}
        hs.status = "Progressing"
        hs.message = "Waiting for child Application health"
        if obj.status ~= nil then
          if obj.status.health ~= nil then
            hs.status = obj.status.health.status
            if obj.status.health.message ~= nil then
              hs.message = obj.status.health.message
            end
          end
        end
        return hs
```

### 13.3 Production Warning

This changes how parent apps behave. It is usually useful for platform bootstrapping, sync waves, and dependency ordering, but test it carefully.

Potential side effects:

- Parent remains `Progressing` until all children are healthy.
- Parent may become `Degraded` because one child application is degraded.
- Sync-wave orchestration becomes more deterministic but can also block later waves.

## 14. Ignoring Health for Specific Resources

Sometimes a resource should not influence parent application health.

Example use cases:

- A helper `Job` that is intentionally suspended.
- A generated or optional resource that is not critical.
- A resource with noisy/flapping health that is monitored elsewhere.

Add annotation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/ignore-healthcheck: "true"
```

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: optional-helper
  annotations:
    argocd.argoproj.io/ignore-healthcheck: "true"
spec:
  replicas: 1
```

Production warning:

> Do not use `ignore-healthcheck` to hide real problems. Use it only when the resource truly should not affect application health and you have another monitoring path.

## 15. Common Application Health Problems

### 15.1 Application Stuck in `Progressing`

Common causes:

- Deployment rollout not complete.
- Pods cannot schedule.
- Image pull error.
- PVC pending.
- Route not admitted.
- Job running too long.
- Operator install waiting.
- Readiness probe failing.
- Controller has not updated `.status.observedGeneration`.

Workflow:

```bash
argocd app get <app>
oc get app <app> -n <argocd-ns> -o yaml
oc get all -n <target-ns>
oc get events -n <target-ns> --sort-by=.lastTimestamp
```

### 15.2 Application `Synced` but `Degraded`

This means manifests are applied but runtime is broken.

Typical causes:

- CrashLoopBackOff.
- Failed rollout.
- Failed job.
- Route admission failure.
- Failed custom resource reconciliation.
- Certificate not issued.
- Operator CSV failed.

Workflow:

```bash
oc get application <app> -n <argocd-ns> -o json | jq '.status.resources[] | select(.health.status=="Degraded")'
oc describe <kind> <name> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
```

### 15.3 Application `OutOfSync` but `Healthy`

Runtime may be fine, but Git drift exists.

Causes:

- Manual cluster change.
- Auto-generated fields not ignored.
- HPA changed replicas.
- Operator mutated resources.
- Admission webhook injected fields.
- Someone hotfixed live state.

Workflow:

```bash
argocd app diff <app>
argocd app get <app>
oc get app <app> -n <argocd-ns> -o yaml
```

### 15.4 Health `Unknown`

Causes:

- No health check for CRD.
- Broken custom health Lua.
- API discovery problem.
- Missing RBAC.
- Cluster connection issue.
- Resource status not populated.

Workflow:

```bash
oc get <resource> <name> -n <ns> -o yaml
oc auth can-i get <resource> -n <ns> --as=system:serviceaccount:<argocd-ns>:<controller-sa>
oc logs -n <argocd-ns> statefulset/<argocd-application-controller>
```

### 15.5 Application `Missing`

Causes:

- Resource deleted manually.
- Namespace missing.
- Sync failed to create object.
- CRD missing.
- Resource tracking changed.
- Argo CD lacks access to read the object.

Workflow:

```bash
argocd app get <app>
argocd app diff <app>
oc get ns <target-ns>
oc api-resources | grep <kind>
oc get <kind> <name> -n <ns>
oc describe app <app> -n <argocd-ns>
```

## 18. Production Best Practices

### 18.1 Treat Health as a Deployment Gate

For controlled deployments:

```bash
argocd app sync my-app
argocd app wait my-app --sync --health --timeout 600
```

CI/CD promotion should not proceed only after `sync` succeeds. It should wait for health.

### 18.2 Use Meaningful Readiness Probes

Argo CD health for Deployments depends on Kubernetes rollout readiness. If readiness probes are weak, Argo CD may show healthy too early.

Bad readiness probe:

```yaml
readinessProbe:
  tcpSocket:
    port: 8080
```

Better readiness probe:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 6
```

### 18.3 Add Custom Health Checks for Critical CRDs

Any production CRD that controls real workloads should have a clear health strategy.

Examples:

- Cert-manager `Certificate`
- External Secrets `ExternalSecret`
- Kafka topic/user CRDs
- OpenShift Pipelines/Tekton CRDs
- ServiceMesh/Istio CRDs
- Operators managing databases
- Crossplane resources
- Custom internal platform CRDs

### 18.4 Avoid Massive Wildcard Health Scripts

Do not write one huge Lua script for many unrelated resources. It becomes hard to test and risky to modify.

Prefer:

- One kind-specific health check.
- Small logic.
- Clear messages.
- Real YAML test fixtures.

### 18.5 Avoid Hiding Problems with Ignore Health

`argocd.argoproj.io/ignore-healthcheck: "true"` is powerful but dangerous.

Use it only when:

- The resource is non-critical.
- Health is noisy by design.
- Another monitoring system covers it.
- The team documents why it is ignored.

### 18.6 Design Alerts with Time Windows

Do not page immediately on `Progressing`. Rollouts need time.

Recommended pattern:

| Health state | Suggested alert behavior |
|---|---|
| `Degraded` | Alert after 5-10 minutes for production. |
| `Progressing` | Alert after expected rollout SLO, for example 20-30 minutes. |
| `Unknown` | Alert as warning/info after 10-15 minutes. |
| `Missing` | Alert quickly in auto-sync production unless expected during migration. |

### 18.7 Align Health with Sync Waves

If you use sync waves, hooks, or app-of-apps, health determines whether later phases should continue in many operational workflows.

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

Best practice:

- CRDs wave `0`
- Operators wave `5`
- Operator operands wave `10`
- Applications wave `20`
- Routes/ingress wave `30`
- Smoke test hooks wave `40`

### 18.8 Keep Health Checks in Git

Manage ArgoCD CR customization declaratively:

```text
cluster-config/
└── openshift-gitops/
    ├── argocd-instance.yaml
    ├── resource-healthchecks.yaml
    └── notifications.yaml
```

Avoid manual UI edits in production.

### 18.9 Use Health Messages That Help On-Call Engineers

Bad message:

```text
Not ready
```

Better message:

```text
Ready=False: Route admission failed because host is already claimed
```

A good health message shortens incident resolution time.

## 19. Real-World Troubleshooting Scenarios

### Scenario 1: Application is `Synced` but `Degraded`

Symptoms:

```text
Sync:   Synced
Health: Degraded
```

Investigation:

```bash
oc get app payment-api -n openshift-gitops -o json | jq '.status.resources[] | select(.health.status=="Degraded")'
```

Suppose output shows Deployment degraded.

Next:

```bash
oc rollout status deploy/payment-api -n payment
oc describe deploy/payment-api -n payment
oc get pods -n payment
oc describe pod <bad-pod> -n payment
oc logs <bad-pod> -n payment --previous
```

Likely root causes:

- Bad image tag.
- Missing secret/configmap.
- Readiness probe failing.
- Runtime exception.

Resolution:

- Fix Git manifest.
- Commit change.
- Let Argo CD sync.
- Wait for health.

```bash
argocd app wait payment-api --sync --health --timeout 600
```

### Scenario 2: Route Resource is `Progressing`

Symptoms:

```text
Route route.openshift.io/payment-api Progressing
```

Check:

```bash
oc describe route payment-api -n payment
oc get route payment-api -n payment -o yaml
```

Possible findings:

```yaml
conditions:
- type: Admitted
  status: "False"
  reason: HostAlreadyClaimed
```

Resolution:

- Use a unique hostname.
- Fix router shard labels.
- Fix TLS route configuration.
- Ensure target service exists.

### Scenario 3: PVC is `Progressing`

Symptoms:

```text
PersistentVolumeClaim data-db Progressing
```

Check:

```bash
oc describe pvc data-db -n database
oc get sc
oc get events -n database --sort-by=.lastTimestamp
```

Possible cause:

```text
waiting for first consumer to be created before binding
```

This may be normal for `WaitForFirstConsumer`. Then check pod scheduling:

```bash
oc get pod -n database
oc describe pod <db-pod> -n database
```

Resolution depends on root cause:

- Fix node selector.
- Fix zone topology.
- Create matching PV.
- Correct storage class.

### Scenario 4: Operator Subscription is `Progressing`

Symptoms:

```text
Subscription openshift-pipelines Progressing
```

Check:

```bash
oc get sub,ip,csv,catalogsource -n openshift-operators
oc describe sub openshift-pipelines-operator-rh -n openshift-operators
```

Possible causes:

- Manual install plan approval pending.
- Catalog source unhealthy.
- Wrong channel.
- Dependency missing.

Resolution:

```bash
oc get installplan -n openshift-operators
oc patch installplan <ip-name> -n openshift-operators --type merge -p '{"spec":{"approved":true}}'
```

Only approve manually after reviewing the InstallPlan in production.

### Scenario 5: Parent App Healthy but Child App Broken

Symptoms:

- Parent app-of-apps is `Healthy`.
- One child application is `Degraded`.

Cause:

- Parent app manages `Application` CRs, but `Application` CR health is not propagated.

Resolution:

- Add custom health check for `argoproj.io/Application`.
- Test sync waves carefully.

## 21. Interview and Exam-Level Questions

### Q1. Can an Argo CD application be `Synced` but `Degraded`?

Yes. `Synced` means the live manifests match Git. `Degraded` means the live resources are not healthy. A Deployment with crash-looping pods can be `Synced` because the YAML was applied, but `Degraded` because the rollout failed.

### Q2. What component calculates Argo CD application health?

The application controller calculates health during reconciliation by evaluating managed live resources using built-in or custom health checks.

### Q3. Why is a custom resource health `Unknown`?

Usually because Argo CD has no built-in health check for that CRD, the CRD status format is not standard, the custom health Lua script failed, or Argo CD cannot read the resource due to RBAC/API/cache issues.

### Q4. How do you make Argo CD understand a CRD's health?

Write a custom Lua health check and configure it through the Argo CD configuration. In OpenShift GitOps, prefer the Operator-managed `ArgoCD` CR `spec.resourceHealthChecks` field.

### Q5. What should a good custom health check inspect?

It should inspect `.status.conditions`, failure reasons, and `.status.observedGeneration` when available. It should return `Progressing` while reconciliation is incomplete, `Healthy` when ready, and `Degraded` for failure conditions.

### Q6. Does Argo CD automatically inspect pods created by a custom resource?

No. Health is not automatically inherited from child resources. If a custom resource creates pods, the custom resource's controller must expose meaningful status, and the Argo CD health check must interpret that status.

### Q7. How do you troubleshoot `Progressing` for a Deployment?

Check rollout status, ReplicaSet, pods, events, image pulls, readiness probes, scheduling, PVCs, quotas, LimitRanges, SCC/PSA errors, and node conditions.

### Q8. How do you monitor application health at scale?

Use Prometheus metrics such as `argocd_app_info` and aggregate by `health_status`, `sync_status`, project, destination namespace, cluster, and team labels.

### Q9. What is the risk of `ignore-healthcheck`?

It can hide real production failures from Argo CD application health. Use it only for intentionally non-critical/noisy resources and document why.

### Q10. Why is Route health important in OpenShift?

A Route can exist but not be admitted. Without route health logic, a GitOps application may look better than it really is even though external traffic cannot reach it.

## Final Admin Summary

Application health is the operational side of GitOps. Sync tells you whether Git was applied. Health tells you whether the resulting resources are actually ready. In OpenShift production environments, always evaluate both.

A senior OpenShift GitOps administrator should be comfortable with:

- Reading `.status.health.status` from the Application CR.
- Finding the exact degraded/progressing resource.
- Mapping Argo CD health to OpenShift events, routes, PVCs, SCCs, pods, deployments, and OLM resources.
- Writing safe custom Lua health checks for important CRDs.
- Monitoring health at fleet scale with Prometheus.
- Avoiding false confidence from `Synced` alone.

The golden rule:

> `Synced` means desired state was applied. `Healthy` means the platform believes the runtime state is good. For production, you need both.
