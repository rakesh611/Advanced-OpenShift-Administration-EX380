## 1. What an Argo CD Application Is

An **Argo CD Application** is a Kubernetes custom resource that tells Argo CD:

- **Where the desired state is stored** — Git repository, branch/tag/commit, path, Helm chart, Kustomize overlay, or manifest directory.
- **Where to deploy it** — Kubernetes/OpenShift cluster and namespace.
- **How to reconcile it** — manual sync, automatic sync, prune, self-heal, retry, sync options, diff behavior, and resource ordering.
- **Which governance boundary applies** — AppProject, source restrictions, destination restrictions, cluster-resource restrictions, namespace-resource restrictions, and Argo CD RBAC.

In simple terms:

```text
Git repository desired state
        |
        v
Argo CD Application CR
        |
        v
Argo CD application-controller compares Git state with OpenShift live state
        |
        v
Sync / drift detection / health analysis / pruning / self-healing
```

In OpenShift GitOps, the `Application` CR is usually created in the Argo CD control-plane namespace, commonly:

```text
openshift-gitops
```

The target workload namespace can be different, for example:

```text
dev
stage
prod
payments
logging
monitoring
```

A critical point for senior administrators: **an Argo CD Application is not the application workload itself**. It is the **declarative deployment controller object** that manages workload resources such as `Deployment`, `Service`, `Route`, `ConfigMap`, `Secret`, `PVC`, `NetworkPolicy`, `ServiceAccount`, `RoleBinding`, `Subscription`, and other OpenShift/Kubernetes resources.

## 2. Application in OpenShift GitOps Context

Red Hat OpenShift GitOps packages Argo CD for OpenShift and installs it through the OpenShift GitOps Operator. A default cluster-scoped Argo CD instance is commonly installed in:

```text
openshift-gitops
```

From an administration point of view, the key OpenShift GitOps objects are:

| Object | Purpose |
|---|---|
| `ArgoCD` | Operator-managed Argo CD control-plane instance. |
| `Application` | Defines one GitOps deployment target. |
| `AppProject` | Security and governance boundary for Applications. |
| `ApplicationSet` | Generates many Applications from templates. |
| Repository Secret | Stores Git/Helm repository credentials. |
| Cluster Secret | Stores target cluster credentials for multi-cluster deployment. |
| Namespace label `argocd.argoproj.io/managed-by` | Allows an Argo CD instance to manage another namespace in many OpenShift GitOps setups. |

OpenShift GitOps differs from a generic upstream installation in a few practical ways:

1. It is Operator-managed.
2. It integrates with OpenShift Routes, OAuth, cluster monitoring, and OpenShift RBAC patterns.
3. The default instance has OpenShift-specific permissions and restrictions.
4. User-defined Argo CD instances can be namespace-scoped or cluster-scoped depending on configuration.
5. OpenShift administrators must carefully design namespace access, AppProject restrictions, and service account permissions.

## 3. How an Application Works Internally

When you create an `Application`, Argo CD performs a reconciliation loop:

```text
1. Read Application spec
2. Fetch source from Git/Helm/OCI/plugin source
3. Generate manifests
4. Compare generated desired manifests with live OpenShift resources
5. Calculate sync status and resource differences
6. Calculate health status
7. Apply manifests if sync is manual and triggered, or automated sync is enabled
8. Optionally prune resources removed from Git
9. Optionally self-heal live drift
10. Record operation state, history, events, and conditions
```

### Main Argo CD components involved

| Component | Role in Application lifecycle |
|---|---|
| `argocd-application-controller` | Watches Applications, compares desired vs live state, performs syncs, updates status. |
| `argocd-repo-server` | Clones Git repos and renders Helm/Kustomize/plain YAML manifests. |
| `argocd-server` | API/UI endpoint for users and CLI. |
| `argocd-redis` | Caches application state and manifest generation data. |
| `argocd-dex-server` or OpenShift OAuth integration | Handles authentication depending on configuration. |

### Application reconciliation is not the same as pod scheduling

Argo CD does not directly schedule pods. It applies Kubernetes/OpenShift objects. The Kubernetes controllers then act:

```text
Argo CD applies Deployment
        |
        v
Deployment controller creates ReplicaSet
        |
        v
ReplicaSet creates Pods
        |
        v
Scheduler places Pods on Nodes
        |
        v
Kubelet starts containers
```

So if an Application is `Synced` but pods are `Pending`, the problem is not necessarily Argo CD. It could be scheduler constraints, taints, quota, SCC, PVC binding, image pull, or network policies.

## 4. Application CRD Anatomy

A typical `Application` resource looks like this:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-api-dev
  namespace: openshift-gitops
  labels:
    app.kubernetes.io/part-of: payments
    env: dev
spec:
  project: payments
  source:
    repoURL: https://github.com/example-org/payments-gitops.git
    targetRevision: main
    path: environments/dev/payments-api
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - PrunePropagationPolicy=foreground
      - ApplyOutOfSyncOnly=true
```

### Major fields

| Field | Meaning |
|---|---|
| `metadata.name` | Name of the Argo CD Application object. |
| `metadata.namespace` | Namespace where the Application CR is created, often `openshift-gitops`. |
| `spec.project` | AppProject that authorizes and governs the Application. |
| `spec.source.repoURL` | Git/Helm repository URL. |
| `spec.source.targetRevision` | Branch, tag, semantic version, or commit SHA. |
| `spec.source.path` | Path inside repo for manifest generation. |
| `spec.destination.server` | Target cluster API server. In-cluster is `https://kubernetes.default.svc`. |
| `spec.destination.name` | Named cluster destination alternative in newer Argo CD/OpenShift GitOps patterns. |
| `spec.destination.namespace` | Target namespace for namespaced resources. |
| `spec.syncPolicy` | Controls manual/automatic sync, pruning, self-healing, retry, and sync options. |
| `spec.ignoreDifferences` | Tells Argo CD to ignore selected differences during comparison. |
| `status.sync.status` | `Synced`, `OutOfSync`, or `Unknown`. |
| `status.health.status` | `Healthy`, `Progressing`, `Degraded`, `Suspended`, `Missing`, or `Unknown`. |

## 5. Minimal OpenShift GitOps Application Example

### Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: demo-app
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

### Application

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: demo-app
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://github.com/example-org/demo-gitops.git
    targetRevision: main
    path: overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: demo-app
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Apply it:

```bash
oc apply -f demo-app-application.yaml
```

Check it:

```bash
oc get applications -n openshift-gitops
oc describe application demo-app -n openshift-gitops
```

Or with Argo CD CLI:

```bash
argocd app get demo-app
argocd app sync demo-app
argocd app wait demo-app --health --sync
```

## 7. Source Configuration

The `source` section defines where desired manifests come from.

### Plain Git path source

```yaml
spec:
  source:
    repoURL: https://github.com/example-org/platform-gitops.git
    targetRevision: main
    path: apps/payments/overlays/prod
```

### Branch tracking

```yaml
targetRevision: main
```

Use for fast-changing dev/stage environments.

### Tag tracking

```yaml
targetRevision: v1.4.2
```

Use for controlled release promotion.

### Commit pinning

```yaml
targetRevision: 7f3ab82c9f4e0c9d3e8a...
```

Use for immutable production rollback and high-compliance environments.

### Source strategy comparison

| Strategy | Best for | Risk |
|---|---|---|
| Branch | Dev and continuous deployment | Latest commit can change behavior quickly. |
| Tag | Release promotion | Tags can be moved unless protected. |
| Commit SHA | Production immutability | Requires automation for promotion. |
| Helm chart version | Third-party chart deployment | Values and chart version must be controlled. |

### Mature production recommendation

For production:

```text
Do not blindly track HEAD of main for critical workloads.
Prefer immutable tags or commit SHAs, protected branches, signed commits, and pull request review.
```

## 8. Destination Configuration

The `destination` section tells Argo CD where to apply resources.

### In-cluster deployment

```yaml
spec:
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-prod
```

This means the Argo CD instance deploys to the same OpenShift cluster where it runs.

### Named cluster destination

Some newer OpenShift GitOps/Argo CD patterns support using a named destination:

```yaml
spec:
  destination:
    name: prod-east
    namespace: payments-prod
```

This is useful when Argo CD manages multiple clusters and you do not want Application routing to depend only on namespace placement.

### Multi-cluster deployment

```yaml
spec:
  destination:
    server: https://api.prod-east.example.com:6443
    namespace: payments-prod
```

For this to work, Argo CD must have a registered cluster secret with appropriate credentials.

### Destination security considerations

Never allow every application to deploy everywhere unless you intentionally operate a trusted single-admin platform.

Bad unrestricted pattern:

```yaml
spec:
  destinations:
    - server: '*'
      namespace: '*'
```

Better pattern:

```yaml
spec:
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-* 
```

Best controlled pattern:

```yaml
spec:
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
    - server: https://kubernetes.default.svc
      namespace: payments-stage
    - server: https://kubernetes.default.svc
      namespace: payments-prod
```

## 9. Project Binding with AppProject

Every Application belongs to an `AppProject`:

```yaml
spec:
  project: payments
```

The AppProject controls:

- Allowed Git repositories.
- Allowed destination clusters.
- Allowed destination namespaces.
- Allowed cluster-scoped resources.
- Allowed namespaced resources.
- Denied resources.
- Roles for Argo CD RBAC.
- Source namespaces for Applications in non-control-plane namespaces.

### Why AppProject matters

`AppProject` is one of the most important security controls in Argo CD.

Without a proper AppProject model, a user who can create or modify an Application may be able to deploy unauthorized workloads, create RoleBindings, bind privileged SCCs, create Operators, or manage cluster-scoped resources.

### Example restricted AppProject

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  description: Payments team GitOps boundary

  sourceRepos:
    - https://github.com/example-org/payments-gitops.git

  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
    - server: https://kubernetes.default.svc
      namespace: payments-stage
    - server: https://kubernetes.default.svc
      namespace: payments-prod

  clusterResourceWhitelist: []

  namespaceResourceWhitelist:
    - group: ""
      kind: ConfigMap
    - group: ""
      kind: Service
    - group: apps
      kind: Deployment
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy
```

### Locking down the default project

The default AppProject is useful for initial testing but risky in production if left unrestricted.

A hardened default project pattern:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: default
  namespace: openshift-gitops
spec:
  sourceRepos: []
  destinations: []
  clusterResourceWhitelist: []
  namespaceResourceBlacklist:
    - group: '*'
      kind: '*'
```

Use dedicated AppProjects instead of allowing production workloads to use `default`.

## 10. Sync Policy

`syncPolicy` controls how Argo CD reconciles desired state into the cluster.

### Manual sync

No automated policy:

```yaml
spec:
  syncPolicy: {}
```

Or omit `syncPolicy` entirely.

Manual sync means:

- Argo CD detects drift.
- Application becomes `OutOfSync`.
- An operator or automation must trigger sync.

Command:

```bash
argocd app sync payments-api-prod
```

### Automated sync

```yaml
spec:
  syncPolicy:
    automated: {}
```

Automated sync means Argo CD syncs when Git desired state changes.

### Automated with prune and self-heal

```yaml
spec:
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

This is common in mature GitOps setups, but it must be combined with strong Git review and AppProject restrictions.

### Retry policy

```yaml
spec:
  syncPolicy:
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
```

This is useful when cluster controllers need time to create CRDs, webhooks, or dependent resources.

## 11. Automated Sync, Prune, Self-Heal, and Allow-Empty

### Automated sync

Automated sync tells Argo CD:

```text
When desired state changes in Git, apply it automatically.
```

Example:

```yaml
syncPolicy:
  automated:
    enabled: true
```

### Prune

Prune tells Argo CD:

```text
If a resource was previously managed by this Application but is now removed from Git, delete it from the cluster.
```

Example:

```yaml
syncPolicy:
  automated:
    prune: true
```

Without prune, deleted Git manifests can leave orphan resources in the cluster.

### Self-heal

Self-heal tells Argo CD:

```text
If someone changes live cluster state manually, revert it back to Git.
```

Example:

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

Example drift:

```bash
oc scale deployment payments-api --replicas=10 -n payments-prod
```

If Git says replicas should be `3`, Argo CD self-heal will restore it.

### Allow-empty

Allow-empty controls whether Argo CD allows an Application to have no generated resources.

```yaml
syncPolicy:
  automated:
    prune: true
    allowEmpty: true
```

Use carefully. In a bad commit, an empty manifest path plus prune can delete resources.

### Senior admin rule

```text
Automated sync + prune + selfHeal is powerful.
It is safe only when Git protection, code review, AppProject restrictions, and rollback strategy are strong.
```

## 12. Sync Options

Sync options customize how Argo CD applies manifests.

### Application-level sync options

```yaml
spec:
  syncPolicy:
    syncOptions:
      - CreateNamespace=true
      - PrunePropagationPolicy=foreground
      - PruneLast=true
      - ApplyOutOfSyncOnly=true
```

### Resource-level sync options

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

### Important sync options

| Sync option | Use case |
|---|---|
| `CreateNamespace=true` | Create destination namespace if absent. |
| `Prune=false` | Prevent specific resource from being pruned. |
| `Prune=confirm` | Require manual confirmation before pruning critical resources. |
| `Validate=false` | Skip kubectl validation for problematic resource schemas. |
| `SkipDryRunOnMissingResource=true` | Useful when CRDs are created by another controller. |
| `ApplyOutOfSyncOnly=true` | Apply only resources that are out of sync, useful at scale. |
| `PruneLast=true` | Prune after other resources become healthy. |
| `Replace=true` | Replace instead of apply; dangerous for some resources. |
| `ServerSideApply=true` | Use server-side apply behavior. |
| `RespectIgnoreDifferences=true` | Honor ignored differences during sync, not only during diff. |

### Example with safer namespace pruning

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

This prevents accidental namespace deletion without approval.

### When to use `SkipDryRunOnMissingResource=true`

Typical case:

- You deploy an Operator Subscription.
- The Operator later creates CRDs.
- Your Application also contains CRs that depend on those CRDs.
- Argo CD dry-run fails because the CRD is not available yet.

Example:

```yaml
spec:
  syncPolicy:
    syncOptions:
      - SkipDryRunOnMissingResource=true
```

Better production design may split CRD/Operator installation and CR creation into separate Applications or sync waves.

## 13. Health Status vs Sync Status

A senior admin must clearly separate **sync** from **health**.

### Sync status

Sync status answers:

```text
Does live cluster configuration match Git desired configuration?
```

Possible statuses:

| Sync status | Meaning |
|---|---|
| `Synced` | Live state matches desired state. |
| `OutOfSync` | Live state differs from Git. |
| `Unknown` | Argo CD cannot determine state. |

### Health status

Health status answers:

```text
Are the deployed resources operational from Kubernetes/OpenShift perspective?
```

Possible statuses include:

| Health status | Meaning |
|---|---|
| `Healthy` | Resource appears operational. |
| `Progressing` | Resource is still rolling out. |
| `Degraded` | Resource has failed or is not meeting expected state. |
| `Suspended` | Resource is intentionally suspended. |
| `Missing` | Resource is expected but absent. |
| `Unknown` | Argo CD cannot assess health. |

### Example: Synced but Degraded

```text
Application: Synced
Health: Degraded
```

Meaning:

- Git was applied correctly.
- But something is wrong at runtime.

Possible causes:

- Pods `CrashLoopBackOff`.
- ImagePullBackOff.
- PVC not bound.
- Route misconfigured.
- Deployment rollout timeout.
- SCC denial.
- Quota exceeded.
- NetworkPolicy blocks dependency.

Troubleshooting:

```bash
argocd app get payments-api-prod
oc get all -n payments-prod
oc get events -n payments-prod --sort-by=.lastTimestamp
oc describe deployment payments-api -n payments-prod
oc logs deploy/payments-api -n payments-prod
```

### Example: OutOfSync but Healthy

```text
Application: OutOfSync
Health: Healthy
```

Meaning:

- Runtime is healthy.
- But live state differs from Git.

Possible causes:

- Manual hotfix.
- HPA changed replicas.
- Operator mutated fields.
- Admission webhook injected sidecars or labels.
- Defaulting changed fields.

## 14. Resource Tracking and Drift Detection

Argo CD tracks resources managed by an Application. It compares:

```text
Desired manifests generated from source
vs
Live resources in OpenShift
```

### Common drift examples

#### Manual replica change

```bash
oc scale deployment frontend --replicas=5 -n web-prod
```

Git says:

```yaml
spec:
  replicas: 3
```

Argo CD detects OutOfSync.

#### Manual ConfigMap edit

```bash
oc edit configmap app-config -n web-prod
```

Argo CD detects OutOfSync.

#### Operator mutation

Some Operators update fields dynamically. Argo CD may show persistent differences unless configured with `ignoreDifferences`.

Example:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

Use this carefully. Ignoring too much hides real drift.

### HPA and replicas drift

If HPA manages replicas, do not fight it with Argo CD.

Option 1: Remove `spec.replicas` from Git if your templating supports it.

Option 2: Ignore replicas:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

## 15. Sync Phases, Hooks, and Waves

Complex OpenShift deployments often require ordering.

Examples:

- Namespace before workloads.
- CRDs before CRs.
- Operator Subscription before custom resources.
- Database migration before application rollout.
- Smoke test after deployment.
- Cleanup after failed deployment.

Argo CD supports:

1. **Sync phases** using hooks.
2. **Sync waves** using integer ordering.

### Hook phases

| Hook | When it runs |
|---|---|
| `PreSync` | Before normal resources are applied. |
| `Sync` | During sync. |
| `PostSync` | After sync succeeds and resources are healthy. |
| `SyncFail` | When sync fails. |
| `Skip` | Resource is skipped by Argo CD. |
| `PreDelete` | Before Application resources are deleted. |
| `PostDelete` | After Application resources are deleted. |

### PreSync migration Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: payments-db-migration
  namespace: payments-prod
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/payments/migrator:v1.4.2
          command: ["/bin/sh", "-c"]
          args:
            - ./migrate.sh
```

### PostSync smoke test

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: payments-smoke-test
  namespace: payments-prod
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: curl
          image: registry.access.redhat.com/ubi9/ubi
          command: ["/bin/bash", "-c"]
          args:
            - curl -kf https://payments-prod.apps.example.com/healthz
```

### Sync waves

Sync waves use annotation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

Lower number runs first. Default is `0`. Negative values are allowed.

### Example ordering

| Wave | Resource |
|---|---|
| `-10` | Namespace |
| `-5` | OperatorGroup, Subscription |
| `0` | ConfigMap, Secret, ServiceAccount |
| `5` | Deployment, Service |
| `10` | Route, NetworkPolicy |
| `20` | PostSync test Job |

### Namespace wave example

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  annotations:
    argocd.argoproj.io/sync-wave: "-10"
```

### Deployment wave example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: payments-prod
  annotations:
    argocd.argoproj.io/sync-wave: "5"
```

### Senior admin note

Do not overuse waves. If you need 20 waves for one app, your deployment model may be too tightly coupled. Split platform dependencies, Operators, databases, and app workloads into different Applications when lifecycle ownership is different.

## 16. Helm Applications

Argo CD can deploy Helm charts, but Argo CD does not use Helm as a release manager in the normal Helm CLI sense. Argo CD renders templates and owns the resulting Kubernetes resources.

### Helm chart from Git

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-helm-dev
  namespace: openshift-gitops
spec:
  project: web
  source:
    repoURL: https://github.com/example-org/charts.git
    targetRevision: main
    path: nginx
    helm:
      valueFiles:
        - values-dev.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

### Helm chart repository

```yaml
spec:
  source:
    repoURL: https://charts.example.com
    chart: myapp
    targetRevision: 1.2.3
    helm:
      releaseName: myapp
      values: |
        replicaCount: 3
        image:
          tag: v1.2.3
```

### Helm values hierarchy

Common options:

```yaml
helm:
  valueFiles:
    - values.yaml
    - values-prod.yaml
  parameters:
    - name: image.tag
      value: v1.2.3
  values: |
    service:
      type: ClusterIP
```

### Helm best practices in OpenShift GitOps

1. Keep environment-specific values in Git.
2. Avoid using Argo CD UI parameter overrides for production; they create state outside Git.
3. Do not store secrets in plain Helm values.
4. Understand OpenShift SCC requirements before deploying upstream charts.
5. Validate charts for OpenShift Route vs Kubernetes Ingress behavior.
6. Be careful with charts that create cluster-wide RBAC.
7. Avoid chart auto-upgrades directly in production without testing.

### Common Helm/OpenShift issues

| Issue | Cause | Fix |
|---|---|---|
| Pod denied by SCC | Chart requests privileged/root behavior. | Adjust chart securityContext or bind proper SCC only if justified. |
| Ingress not reachable | Chart creates Ingress but cluster expects Route. | Use Route template or OpenShift ingress configuration. |
| Resource already exists | Helm chart resource ownership collision. | Split Applications or rename release/resources. |
| CRD timing failure | Chart installs CRDs and CRs together. | Use sync waves or separate CRD app. |

## 17. Kustomize Applications

Kustomize is widely used for OpenShift GitOps because it supports base/overlay patterns naturally.

### Repository structure

```text
payments-gitops/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── route.yaml

        ├── kustomization.yaml
```

```yaml
spec:
```

## 19. Multiple Sources

Modern Argo CD supports multiple sources for a single Application. This is useful when you want manifests from one repo and values from another repo.

Example concept:

```yaml
spec:
  sources:
    - repoURL: https://charts.example.com
      chart: myapp
      targetRevision: 1.2.3
      helm:
        valueFiles:
          - $values/environments/prod/values.yaml
    - repoURL: https://github.com/example-org/environment-values.git
      targetRevision: main
      ref: values
```

### When multiple sources make sense

- Third-party Helm chart plus internal values repo.
- Shared platform chart plus environment-specific repo.

Avoid using multiple sources to hide poor repository design. If every Application has five sources, troubleshooting becomes harder.

## 20. Application of Applications Pattern

The **app-of-apps** pattern uses one parent Application to create child Applications.

```text
bootstrap Application
        |
        +-- cluster-config Application
        +-- monitoring Application
        +-- logging Application
        +-- payments-dev Application
        +-- payments-prod Application
```

### Parent Application

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-bootstrap
  namespace: openshift-gitops
spec:
  project: platform
  source:
    repoURL: https://github.com/example-org/cluster-bootstrap.git
    targetRevision: main
    path: applications
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

The `applications/` directory contains child `Application` YAMLs.

### Advantages

- Declarative bootstrap.
- Single entry point for cluster GitOps.
- Easy disaster recovery.
- Consistent onboarding of cluster components.

### Risks

- Parent app misconfiguration can affect many child apps.
- Circular dependencies are possible.
- AppProject restrictions must be strong.
- Deleting the parent with prune can delete child Application CRs.

### Production recommendation

Use app-of-apps for platform-controlled bootstrapping, but use ApplicationSet for large generated fleets such as many clusters, many namespaces, or many environments.

## 21. Applications in Any Namespace / Non-Control-Plane Namespaces

Traditionally, Applications are created in the Argo CD control-plane namespace, for example:

```text
openshift-gitops
```

OpenShift GitOps also supports controlled models where users can create Application resources in selected non-control-plane namespaces, when the Argo CD instance and AppProjects are configured for it.

### Why this matters

A platform team may want:

- Developers to manage their own Application CRs.
- Teams to create Applications in their own namespace.
- Argo CD control plane to remain protected.
- AppProject to restrict where those Applications can deploy.

### Security rule

Do not simply allow users to create Applications in arbitrary namespaces with unrestricted AppProjects.

A user who can create an Application that references a privileged project can potentially deploy powerful resources.

### Safe pattern

1. Define allowed source namespaces in the ArgoCD CR.
2. Create restricted AppProjects in the control-plane namespace.
3. Add only approved namespaces to `spec.sourceNamespaces` of the AppProject.
4. Do not allow non-admin users to use the default unrestricted AppProject.
5. Do not grant ordinary users access to the Argo CD control-plane namespace.

### Example AppProject source namespace restriction

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  sourceNamespaces:
    - payments-gitops
  sourceRepos:
    - https://github.com/example-org/payments-gitops.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payments-dev
    - server: https://kubernetes.default.svc
      namespace: payments-stage
  clusterResourceWhitelist: []
```

### 22.1 Namespace management label

In many OpenShift GitOps workflows, a target namespace must be labeled so the Argo CD instance can manage it:

```bash
oc label namespace payments-prod argocd.argoproj.io/managed-by=openshift-gitops
```

YAML:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

### 22.2 Routes instead of Ingress

OpenShift commonly uses `Route`:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments-api
  namespace: payments-prod
spec:
  host: payments-api.apps.example.com
  to:
    kind: Service
    name: payments-api
  port:
    targetPort: http
  tls:
    termination: edge
```

AppProject must allow this resource:

```yaml
namespaceResourceWhitelist:
  - group: route.openshift.io
    kind: Route
```

### 22.3 Security Context Constraints

Some workloads fail after sync because OpenShift SCC rejects pod security settings.

Symptoms:

```text
Error creating: pods ... is forbidden: unable to validate against any security context constraint
```

Fix properly:

- Prefer non-root images.
- Avoid privileged containers.
- Set correct `securityContext`.
- Only bind SCCs deliberately.

Example controlled SCC binding:

```bash
oc adm policy add-scc-to-user anyuid -z payments-api -n payments-prod
```

GitOps version:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: use-anyuid-scc
  namespace: payments-prod
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:openshift:scc:anyuid
subjects:
  - kind: ServiceAccount
    name: payments-api
    namespace: payments-prod
```

Use only after security review.

### 22.4 ImageStreams

OpenShift ImageStreams may be used instead of direct image references.

```yaml
apiVersion: image.openshift.io/v1
kind: ImageStream
metadata:
  name: payments-api
  namespace: payments-prod
```

If using GitOps, define whether image promotion is Git-driven, pipeline-driven, or ImageStreamTag-driven. Avoid uncontrolled image drift.

### 22.5 Operators and OLM

OpenShift Operators introduce timing challenges:

```text
Namespace -> OperatorGroup -> Subscription -> CSV -> CRD -> Custom Resource
```

Use either:

- Separate Applications for Operator installation and CR creation.
- Sync waves and hooks.
- Retry policy.
- Health checks.

Example waves:

```yaml
# Subscription
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"

# Custom Resource
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

### 22.6 Cluster-scoped resources

Cluster-scoped resources require special governance:

- `ClusterRole`
- `ClusterRoleBinding`
- `CustomResourceDefinition`
- `Namespace`
- `StorageClass`
- `MachineConfig`
- `ConsolePlugin`
- `OAuth`
- `IngressController`

Do not allow application teams to deploy arbitrary cluster-scoped resources through a broad AppProject.

## 23. RBAC and Security Model

There are multiple layers of authorization.

```text
OpenShift user RBAC
        |
        v
Access to Argo CD UI/API/Application CR
        |
        v
Argo CD RBAC
        |
        v
AppProject restrictions
        |
        v
Argo CD controller Kubernetes service account permissions
        |
        v
OpenShift admission controls: SCC, PSA labels, quotas, network policies
```

### Critical security rule

Anyone with write access to the Argo CD control-plane namespace may effectively become an Argo CD administrator.

Do not grant regular developers edit/admin access to:

```text
openshift-gitops
```

### Application permissions are not enough

Even if Argo CD RBAC says a user can sync only one app, if the user can modify the Git repo for that app and the AppProject is broad, they may deploy dangerous manifests.

Protect:

1. Git repository.
2. Application CR.
3. AppProject.
4. Argo CD namespace.
5. Argo CD controller service account permissions.
6. OpenShift admission policies.

### AppProject least privilege example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: frontend
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://github.com/example-org/frontend-gitops.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: frontend-dev
    - server: https://kubernetes.default.svc
      namespace: frontend-prod
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
    - group: ""
      kind: Service
    - group: ""
      kind: ConfigMap
    - group: apps
      kind: Deployment
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy
```

### SSH repository secret

```yaml
apiVersion: v1

metadata:
  name: repo-payments-ssh
  namespace: openshift-gitops

    argocd.argoproj.io/secret-type: repository
```

| repository not accessible | Network/proxy/firewall issue. | Check egress and proxy config. |
| path does not exist | Wrong `spec.source.path`. | Correct path or branch. |

## 25. Namespace Management

There are three common namespace strategies.

### Strategy 1: Namespace pre-created by platform

Platform team creates namespace, quotas, limits, RBAC, and labels.

Application deploys only workload resources.

Best for production.

### Strategy 2: Argo CD creates namespace

```yaml
spec:
  destination:
    namespace: payments-dev
  syncPolicy:
    syncOptions:
      - CreateNamespace=true
```

Good for dev/test, but be careful with quotas, labels, and RBAC.

### Strategy 3: Namespace manifest included in Git

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
  annotations:
    argocd.argoproj.io/sync-wave: "-10"
    argocd.argoproj.io/sync-options: Prune=confirm
```

Good for cluster configuration repos.

### Namespace deletion danger

If `prune: true` and Namespace is managed by Argo CD, deleting the namespace manifest from Git may delete the namespace and all workloads inside it.

Protect critical namespaces:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

### 28.1 Application is not visible

Check namespace:

```bash
oc get applications -A
```

```bash

```

```bash

```

### 28.2 Application stuck `OutOfSync`

Check details:


| Cause | Diagnosis | Fix |
|---|---|---|

| Symptom | Likely cause |
|---|---|

| `CrashLoopBackOff` | App/runtime issue. |

- Branch/tag exists.

## 29. Production Design Patterns

### Pattern 1: One Application per service per environment

```text
payments-api-dev
payments-api-stage
payments-api-prod
```

Good because:

- Clear ownership.
- Easier rollback.
- Environment-specific control.
- Blast radius is limited.

### Pattern 2: Separate platform and application GitOps

```text
platform-gitops repo
  - namespaces
  - operators
  - monitoring
  - logging
  - cluster-rbac

application-gitops repo
  - service manifests
  - app config
  - routes
  - network policies
```

### Pattern 3: Bootstrap app-of-apps

Use one bootstrap Application to install core Applications.

### Pattern 4: AppProject per team

```text
payments AppProject
frontend AppProject
observability AppProject
security AppProject
```

Each team gets restricted repos and destinations.

### Pattern 5: Production uses immutable versions

```yaml
targetRevision: v1.4.2
```

or commit SHA.

### Pattern 6: Git PR as deployment approval

```text
Change manifests -> Pull Request -> Review -> Merge -> Argo CD deploys
```

This gives auditability and rollback.

### Pattern 7: Separate operator install from operator configuration

```text
operator-install Application
operator-config Application
```

This reduces CRD timing issues.

### Pattern 8: Critical resources require prune confirmation

Namespaces and PVC-related resources should not be deleted accidentally.

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

## 30. Anti-Patterns

### Anti-pattern 1: Everyone uses default project

Risk:

```text
Users can deploy to unintended namespaces or create powerful resources.
```

Fix:

```text
Create dedicated AppProjects with least privilege.
```

### Anti-pattern 2: Developers have edit access to `openshift-gitops`

Risk:

```text
They can modify Applications, repository credentials, Projects, or Argo CD configuration.
```

Fix:

```text
Only platform admins should have write access to Argo CD control-plane namespace.
```

### Anti-pattern 3: One huge Application manages entire cluster

Risk:

- Hard troubleshooting.
- Large blast radius.
- Slow sync.
- Ownership confusion.

Fix:

- Split by lifecycle and ownership.

### Anti-pattern 4: Auto-prune enabled on critical cluster resources without confirmation

Risk:

- Namespace deletion.
- Cluster config deletion.
- Operator removal.

Fix:

- Use `Prune=confirm`.
- Use review process.
- Separate dangerous resources.

### Anti-pattern 5: Secrets committed in Git

Risk:

- Credential exposure.

Fix:

- Use sealed/external secret patterns.

### Anti-pattern 6: Fighting Operators or HPAs

Risk:

- Constant OutOfSync.
- Controller conflicts.

Fix:

- Understand field ownership.
- Use `ignoreDifferences` carefully.

### Anti-pattern 7: Using Argo CD UI overrides for production configuration

Risk:

- Desired state moves outside Git.

Fix:

- Store all production config in Git.

## 31. Interview / Real-World Explanation

A strong 10-year-experience explanation:

```text
In OpenShift GitOps, an Argo CD Application is the declarative object that binds a Git source to a target OpenShift namespace or cluster. It tells Argo CD which repository path, branch, tag, Helm chart, or Kustomize overlay represents desired state, and where that desired state must be reconciled.

The application-controller continuously compares generated manifests from the repo-server with live resources in the cluster. If there is a difference, the Application becomes OutOfSync. Depending on sync policy, Argo CD can sync manually or automatically. With prune, it removes resources deleted from Git. With selfHeal, it reverses live manual drift.

In production OpenShift, I would not treat Applications as simple deployment objects only. I would design AppProjects, RBAC, namespace labels, repository credentials, sync policies, resource whitelists, and OpenShift SCC/Route/Operator behavior carefully. I would avoid using the default project for teams, restrict source repos and destinations, protect the openshift-gitops namespace, and separate platform-level cluster resources from normal application workloads.

For troubleshooting, I separate sync status from health status. Synced means Git and live state match; Healthy means the workload is actually functioning. A Synced but Degraded app usually points to OpenShift runtime issues such as SCC denial, image pull failure, PVC pending, quota, scheduling, or bad rollout. An OutOfSync but Healthy app usually points to manual drift, HPA changes, webhook mutation, or missing prune.
```

## Final Senior-Level Summary

An Argo CD Application in OpenShift GitOps is the main reconciliation unit that connects Git desired state to OpenShift live state. For beginner usage, it deploys manifests. For advanced administration, it becomes a controlled operational boundary involving repository strategy, AppProject governance, OpenShift namespace permissions, sync policy, pruning safety, drift management, health analysis, RBAC, and troubleshooting.

A mature OpenShift GitOps administrator should design Applications with these rules:

1. Use Git as the source of truth.
2. Use AppProjects as security boundaries.
3. Protect the Argo CD control-plane namespace.
4. Restrict source repositories and destinations.
5. Avoid broad cluster-scoped permissions for app teams.
6. Separate platform resources from application resources.
7. Use auto-sync, prune, and self-heal only with strong Git controls.
8. Understand sync status versus health status.
9. Use hooks and waves only where ordering is genuinely required.
10. Troubleshoot from Argo CD down to OpenShift controllers, pods, events, SCCs, PVCs, routes, and network policies.
