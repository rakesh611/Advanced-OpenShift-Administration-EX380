# GitOps for Quotas and Limits in Red Hat OpenShift GitOps / Argo CD

**Audience:** Advanced OpenShift Administrator / Platform Engineer  
**Experience level:** ~10 years Linux, Kubernetes, OpenShift, DevOps, SRE  
**Main topic:** Managing `ResourceQuota`, `LimitRange`, and OpenShift quota governance through GitOps using Red Hat OpenShift GitOps / Argo CD.

---

## 1. Executive Summary

In an enterprise OpenShift platform, quotas and limits are not only YAML objects. They are platform guardrails.

A good GitOps design for quotas and limits answers these questions:

- How much CPU, memory, storage, object count, and ephemeral storage can each project consume?
- What default requests and limits are applied when developers forget to define resources?
- How do you prevent one namespace or team from consuming shared cluster capacity?
- How do you safely roll out quota changes across many namespaces and clusters?
- How do you detect and revert manual drift?
- How do you avoid breaking running workloads when quota policies become stricter?

With Red Hat OpenShift GitOps, Argo CD becomes the reconciliation engine for these platform policies. Git becomes the source of truth, and OpenShift becomes the enforced runtime state.

For advanced administration, treat quota and limit GitOps as part of **multi-tenancy, reliability, cost control, capacity management, and security governance**.

## 2. What Are Quotas and Limits in OpenShift?

OpenShift uses Kubernetes quota and limit objects, plus OpenShift-specific quota APIs, to control resource consumption.

### 2.1 ResourceQuota

A `ResourceQuota` sets aggregate limits inside a namespace/project.

It can control:

- Number of pods
- Total CPU requests
- Total CPU limits
- Total memory requests
- Total memory limits
- Total ephemeral storage requests and limits
- Number of services
- Number of secrets
- Number of config maps
- Number of PVCs
- Total storage requested
- Storage consumption per StorageClass
- OpenShift-specific resources such as ImageStreams, where applicable

Example:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-compute-quota
  namespace: team-a-dev
spec:
  hard:
    pods: "20"
    requests.cpu: "8"
    requests.memory: 16Gi
    limits.cpu: "16"
    limits.memory: 32Gi
    requests.ephemeral-storage: 20Gi
    limits.ephemeral-storage: 40Gi
```

This means the namespace cannot create workloads that collectively exceed these values.

### 2.2 LimitRange

A `LimitRange` defines per-object constraints and defaults.

It can apply to:

- Containers
- Pods
- PersistentVolumeClaims
- Images
- ImageStreams, depending on OpenShift resource usage

A `LimitRange` can define:

- Minimum request
- Maximum limit
- Default request
- Default limit
- Maximum limit-to-request ratio

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: team-a-container-limits
  namespace: team-a-dev
spec:
  limits:
    - type: Container
      min:
        cpu: 50m
        memory: 64Mi
      max:
        cpu: "2"
        memory: 2Gi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      default:
        cpu: 500m
        memory: 512Mi
      maxLimitRequestRatio:
        cpu: "10"
        memory: "4"
```

If a developer deploys a container without requests and limits, the defaults can be applied by admission control.

### 2.3 ClusterResourceQuota

`ClusterResourceQuota` is OpenShift-specific and works across multiple projects selected by labels or annotations.

Use it when a team owns multiple namespaces and you want a shared quota pool.

Example:

```yaml
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata:
  name: team-a-shared-quota
spec:
  selector:
    labels:
      matchLabels:
        quota.openshift.io/team: team-a
  quota:
    hard:
      pods: "100"
      requests.cpu: "40"
      requests.memory: 80Gi
      limits.cpu: "80"
      limits.memory: 160Gi
      requests.storage: 500Gi
```

Namespaces selected by this label share the same quota pool:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-dev
  labels:
    quota.openshift.io/team: team-a
---
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-prod
  labels:
    quota.openshift.io/team: team-a
```

### 2.4 ResourceQuota vs LimitRange vs ClusterResourceQuota

| Object | Scope | Purpose | Common Owner |
|---|---:|---|---|
| `ResourceQuota` | Namespace | Total resource budget per project | Platform team |
| `LimitRange` | Namespace | Per-container, per-pod, or per-PVC defaults and boundaries | Platform team |
| `ClusterResourceQuota` | Cluster-level selector across projects | Shared quota budget across multiple namespaces | Platform team |
| Workload resources | Namespace | Application-level request and limit declaration | App team |

## 3. Why GitOps for Quotas and Limits?

Manual quota management does not scale.

In a small cluster, you can run:

```bash
oc create quota ...
oc create -f limitrange.yaml
```

But in a real enterprise platform, you might have:

- 20+ teams
- 200+ namespaces
- Multiple OpenShift clusters
- Dev, test, stage, prod environments
- Separate quota tiers
- Audit requirements
- Change approvals
- Drift caused by emergency manual edits

GitOps solves these operational problems.

### 3.1 GitOps Benefits

| Requirement | GitOps Benefit |
|---|---|
| Audit | Every quota change is a Git commit |
| Approval | Pull request workflow before production change |
| Rollback | Revert commit to restore previous quota |
| Consistency | Same quota model across clusters |
| Drift detection | Argo CD marks manual edits as OutOfSync |
| Self-healing | Argo CD can restore Git state automatically |
| Multi-cluster | ApplicationSet can generate policy apps per cluster |
| Compliance | Git history proves who changed resource governance |

### 3.2 Quotas Are Platform Policies

Do not treat quota YAML as application configuration only.

Quotas and limits belong to platform policy because they affect:

- Cluster stability
- Scheduling fairness
- Node capacity planning
- Cost allocation
- Storage consumption
- Namespace onboarding
- Developer self-service
- Production reliability

## 4. GitOps Design Model

A mature design separates:

1. **Platform bootstrap**
2. **Project onboarding**
3. **Quota and limit policy**
4. **Application deployment**
5. **Validation and observability**

Recommended dependency order:

```text
Cluster
  └── OpenShift GitOps Operator
       └── Argo CD instance
            └── AppProject
                 └── Namespace / Project
                      ├── Labels / annotations
                      ├── RBAC
                      ├── ResourceQuota
                      ├── LimitRange
                      ├── NetworkPolicy
                      └── Application workloads
```

Quotas and limit ranges must exist before heavy workloads are deployed.

## 6. Base Manifests

### 6.1 Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-dev
  labels:
    kubernetes.io/metadata.name: team-a-dev
    app.kubernetes.io/managed-by: argocd
    quota.openshift.io/team: team-a
    environment: dev
  annotations:
    openshift.io/display-name: "Team A Development"
    openshift.io/description: "Development namespace for Team A"
    argocd.argoproj.io/sync-wave: "-3"
```

Important design notes:

- Namespace should be created before quota and limit objects.
- Namespace labels can drive `ClusterResourceQuota` selection.
- Namespace labels can also drive automation, NetworkPolicy, monitoring, and chargeback.
- Be careful with pruning namespaces. Namespace deletion can delete all objects inside it.

For production, consider requiring prune confirmation on namespaces:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

### 6.2 ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-compute-object-storage-quota
  namespace: team-a-dev
  labels:
    app.kubernetes.io/part-of: platform-quota-policy
    app.kubernetes.io/managed-by: argocd
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  hard:
    pods: "20"

    requests.cpu: "8"
    requests.memory: 16Gi
    limits.cpu: "16"
    limits.memory: 32Gi

    requests.ephemeral-storage: 20Gi
    limits.ephemeral-storage: 40Gi

    persistentvolumeclaims: "10"
    requests.storage: 200Gi

    services: "10"
    services.loadbalancers: "0"
    services.nodeports: "0"
    configmaps: "50"
    secrets: "50"
```

Why include object counts?

Because CPU and memory are not the only resources that can hurt a cluster.

Object explosion can impact:

- etcd size
- API server performance
- controller performance
- namespace cleanup
- backup and restore time

Common object-count controls:

```yaml
hard:
  pods: "50"
  services: "20"
  configmaps: "100"
  secrets: "100"
  persistentvolumeclaims: "20"
  replicationcontrollers: "50"
  count/deployments.apps: "30"
  count/replicasets.apps: "60"
  count/jobs.batch: "20"
  count/cronjobs.batch: "10"
```

### 6.3 StorageClass-specific quota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-storageclass-quota
  namespace: team-a-dev
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  hard:
    persistentvolumeclaims: "10"
    requests.storage: 200Gi
    fast.storageclass.storage.k8s.io/requests.storage: 50Gi
    standard.storageclass.storage.k8s.io/requests.storage: 150Gi
    fast.storageclass.storage.k8s.io/persistentvolumeclaims: "2"
    standard.storageclass.storage.k8s.io/persistentvolumeclaims: "8"
```

Use this when:

- Fast storage is expensive
- SSD-backed storage must be limited
- Different teams share OpenShift Data Foundation or cloud block storage
- You want to stop a namespace from creating unlimited PVCs

## 7. Argo CD Application for Quotas and Limits

### 7.1 Basic Application

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: team-a-dev-quota-policy
  namespace: openshift-gitops
spec:
  project: platform-governance

  source:
    repoURL: https://git.example.com/platform/openshift-platform-gitops.git
    targetRevision: main
    path: policies/quota-limit/overlays/dev

  destination:
    server: https://kubernetes.default.svc
    namespace: team-a-dev

  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - ServerSideApply=true
      - ApplyOutOfSyncOnly=true
      - PruneLast=true
      - FailOnSharedResource=true
```

### 7.2 About important sync options

| Option | Why it matters for quota GitOps |
|---|---|
| `ServerSideApply=true` | Better for field ownership and large/multi-manager resources |
| `ApplyOutOfSyncOnly=true` | Reduces unnecessary API writes |
| `PruneLast=true` | Deletes removed resources after other resources are applied |
| `FailOnSharedResource=true` | Prevents two Argo CD applications from fighting over same quota object |
| `CreateNamespace=true` | Useful when Argo CD should create the namespace |
| `Prune=confirm` | Safer for critical resources such as Namespace |
| `Delete=confirm` | Requires approval before deleting sensitive objects |

For platform guardrails, `FailOnSharedResource=true` is especially useful. Quotas should not be owned by multiple Argo CD Applications.

### 7.3 Namespace management warning

There are two valid patterns.

#### Pattern A: Namespace manifest in Git

You commit the namespace YAML.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-dev
```

Use this when you want full control over labels and annotations.

#### Pattern B: Argo CD creates namespace

You use:

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
```

Use this for simple app namespaces.

For advanced OpenShift administration, Pattern A is usually better for platform governance because namespace labels are often used by:

- `ClusterResourceQuota`
- NetworkPolicy
- RBAC automation
- Monitoring rules
- Cost allocation
- ApplicationSet generators

## 8. AppProject for Governance

Do not allow all teams to manage quota objects freely.

Create an Argo CD `AppProject` for platform governance.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: platform-governance
  namespace: openshift-gitops
spec:
  description: Platform-owned namespace policy, quotas, limits, RBAC, and guardrails

  sourceRepos:
    - https://git.example.com/platform/openshift-platform-gitops.git

  destinations:
    - server: https://kubernetes.default.svc
      namespace: '*'

  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
    - group: quota.openshift.io
      kind: ClusterResourceQuota

  namespaceResourceWhitelist:
    - group: ''
      kind: ResourceQuota
    - group: ''
      kind: LimitRange
    - group: ''
      kind: ServiceAccount
    - group: rbac.authorization.k8s.io
      kind: Role
    - group: rbac.authorization.k8s.io
      kind: RoleBinding
```

Recommended separation:

| Argo CD Project | Managed by | Allowed objects |
|---|---|---|
| `platform-governance` | Platform team | Namespace, ResourceQuota, LimitRange, RBAC |
| `team-apps` | Application team | Deployment, Service, Route, ConfigMap |
| `cluster-config` | Cluster admin team | Cluster-scoped operators and config |
| `security-policy` | Security team | NetworkPolicy, SCC binding process, policy CRs |

This separation avoids accidental privilege escalation.

## 9. RBAC Required for Argo CD

If the default OpenShift GitOps Argo CD instance manages quotas across namespaces, the Argo CD application controller service account must have permission.

Typical service account:

```text
system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

For namespace-scoped quota management:

```bash
oc adm policy add-role-to-user admin \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n team-a-dev
```

For cluster-scoped objects such as `ClusterResourceQuota`, create a tighter custom `ClusterRole` instead of using broad `cluster-admin`.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: argocd-quota-governance-manager
rules:
  - apiGroups: [""]
    resources:
      - namespaces
      - resourcequotas
      - limitranges
    verbs:
      - get
      - list
      - watch
      - create
      - update
      - patch
      - delete

  - apiGroups: ["quota.openshift.io"]
    resources:
      - clusterresourcequotas
    verbs:
      - get
      - list
      - watch
      - create
      - update
      - patch
      - delete
```

Bind it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: argocd-quota-governance-manager
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: argocd-quota-governance-manager
subjects:
  - kind: ServiceAccount
    name: openshift-gitops-argocd-application-controller
    namespace: openshift-gitops
```

Production advice:

- Avoid giving Argo CD `cluster-admin` permanently.
- Create separate Argo CD instances or AppProjects for platform vs app teams.
- Restrict repositories and destinations.
- Use signed commits or protected branches for quota policy repos.
- Require pull request approval for production quota changes.

## 11. Helm-Based Quota Management

Helm can also generate quotas and limit ranges.

Use Helm when teams require a reusable chart with values per environment.

### 11.1 Chart structure

```text
quota-limit-chart/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── resourcequota.yaml
    ├── limitrange.yaml
    └── namespace.yaml
```

### 11.2 values.yaml

```yaml
namespace:
  create: true
  name: team-a-dev
  labels:
    quota.openshift.io/team: team-a
    environment: dev

resourceQuota:
  enabled: true
  hard:
    pods: "20"
    requests.cpu: "8"
    requests.memory: 16Gi
    limits.cpu: "16"
    limits.memory: 32Gi
    persistentvolumeclaims: "10"
    requests.storage: 200Gi
    services: "10"
    secrets: "50"
    configmaps: "50"

limitRange:
  enabled: true
  container:
    min:
      cpu: 50m
      memory: 64Mi
    max:
      cpu: "2"
      memory: 2Gi
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
```

### 11.3 ResourceQuota template

```yaml
{{- if .Values.resourceQuota.enabled }}
apiVersion: v1
kind: ResourceQuota
metadata:
  name: {{ .Release.Name }}-quota
  namespace: {{ .Values.namespace.name }}
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  hard:
{{ toYaml .Values.resourceQuota.hard | indent 4 }}
{{- end }}
```

### 11.4 LimitRange template

```yaml
{{- if .Values.limitRange.enabled }}
apiVersion: v1
kind: LimitRange
metadata:
  name: {{ .Release.Name }}-limits
  namespace: {{ .Values.namespace.name }}
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  limits:
    - type: Container
      min:
{{ toYaml .Values.limitRange.container.min | indent 8 }}
      max:
{{ toYaml .Values.limitRange.container.max | indent 8 }}
      defaultRequest:
{{ toYaml .Values.limitRange.container.defaultRequest | indent 8 }}

{{ toYaml .Values.limitRange.container.default | indent 8 }}
{{- end }}
```

Helm is powerful, but avoid hiding too much quota logic inside templates. Platform teams should still be able to review exact rendered quotas during pull requests.

## 12. Sync Waves for Correct Ordering

Quota GitOps should use sync waves where ordering matters.

Recommended waves:

| Wave | Resource |
|---:|---|
| `-5` | CRDs / required operators, if any |
| `-4` | AppProject / RBAC for Argo CD |
| `-3` | Namespace |
| `-2` | Namespace labels, role bindings, service accounts |
| `-1` | ResourceQuota, LimitRange |
| `0` | Application workloads |
| `1` | Post-sync validation jobs |

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
```

Why quotas before workloads?

Because you want workloads to be admitted with correct governance from the beginning.

If workloads deploy before `LimitRange`, pods without requests and limits may be created without default governance. If workloads deploy before `ResourceQuota`, the namespace may consume resources before quota is active.

## 13. Hooks for Quota Validation

Use Argo CD hooks for advanced validation.

Example PostSync job that checks quota after sync:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: validate-team-a-quota
  namespace: team-a-dev
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      serviceAccountName: quota-validator
      restartPolicy: Never
      containers:
        - name: validate
          image: registry.access.redhat.com/ubi9/ubi
          command:
            - /bin/bash
            - -c
            - |
              echo "Checking quota..."
              oc get resourcequota -n team-a-dev
              oc describe resourcequota namespace-standard-quota -n team-a-dev
```

In production, validation jobs should not require cluster-admin. Use least privilege.

## 14. Multi-Environment Quota Tiers

A practical quota model uses tiers.

### 14.1 Example tiers

| Tier | Use case | CPU request | Memory request | Storage |
|---|---|---:|---:|---:|
| `sandbox-small` | Developer testing | 1 core | 2Gi | 10Gi |
| `dev-standard` | Team development | 8 cores | 16Gi | 200Gi |
| `test-standard` | QA / integration | 16 cores | 32Gi | 300Gi |
| `prod-standard` | Production app | 40 cores | 96Gi | 1Ti |
| `prod-large` | Business-critical app | 80 cores | 192Gi | 2Ti |

### 14.2 Example tier annotation

## 17. Drift Detection

GitOps drift happens when live state differs from Git state.

Example: An admin manually changes quota.

```bash
oc patch resourcequota namespace-standard-quota \
  -n team-a-dev \
  --type merge \
  -p '{"spec":{"hard":{"pods":"100"}}}'
```

Argo CD detects:

```text
Application: team-a-dev-quota-policy
Status: OutOfSync
Diff: spec.hard.pods changed from 20 to 100
```

If `selfHeal: true` is enabled, Argo CD can revert it automatically.

### 17.1 When to enable self-heal

Enable self-heal for:

- Standard quota policy
- LimitRange defaults
- Namespace labels controlled by platform team
- Object count controls

Be careful with self-heal when:

- Teams frequently request temporary quota increases
- Emergency changes happen outside Git
- You have no clear break-glass process
- Multiple controllers modify the same resource

### 17.2 Break-glass pattern

Emergency quota increase should still be traceable.

Recommended process:

1. Temporary manual change allowed only by incident commander.
2. Create incident ticket.
3. Commit same change to Git within defined SLA.
4. Argo CD sync confirms desired state.
5. Revert after incident if temporary.

Better process:

1. Commit emergency quota increase to Git.
2. Fast-track pull request approval.
3. Argo CD sync applies change.
4. Git remains source of truth.

## 18. How Quota Admission Affects Workloads

### 18.1 ResourceQuota behavior

When a pod or object is created, OpenShift checks whether the namespace quota would be exceeded.

If yes, creation is rejected.

Typical error:

```text
Error creating: pods "app-xxx" is forbidden:
exceeded quota: namespace-standard-quota,
requested: requests.cpu=500m,
used: requests.cpu=8,
limited: requests.cpu=8
```

### 18.2 LimitRange behavior

When a pod is created, `LimitRange` admission can:

- Apply default requests and limits
- Reject containers below minimum values
- Reject containers above maximum values
- Reject containers that exceed max limit-to-request ratio

Typical error:

```text
Error from server (Forbidden):
pods "big-pod" is forbidden:
maximum cpu usage per Container is 2, but limit is 4
```

### 18.3 ResourceQuota plus LimitRange

ResourceQuota and LimitRange should be designed together.

Example:

```yaml
ResourceQuota:
  requests.cpu: "8"
  limits.cpu: "16"

LimitRange:
  defaultRequest.cpu: 100m
  default.cpu: 500m
```

If every container gets a default request of `100m`, a namespace with `requests.cpu: 8` can admit around 80 default-sized containers, subject to other quota constraints.

Poor design example:

```yaml
ResourceQuota:
  requests.cpu: "2"

LimitRange:
  defaultRequest.cpu: "1"
```

Only two default containers can be admitted before quota is exhausted.

## 19. Safe Rollout Strategy

Quota changes can break deployments if they are too strict.

### 19.1 Before reducing quota

Check current usage:

```bash
oc describe quota -n team-a-prod
oc get resourcequota -n team-a-prod -o yaml
```

Check pod requests and limits:

```bash
oc get pods -n team-a-prod \
  -o custom-columns=NAME:.metadata.name,CPU_REQ:.spec.containers[*].resources.requests.cpu,MEM_REQ:.spec.containers[*].resources.requests.memory,CPU_LIM:.spec.containers[*].resources.limits.cpu,MEM_LIM:.spec.containers[*].resources.limits.memory
```

Check PVCs:

```bash
oc get pvc -n team-a-prod
```

Check pending or failed create events:

```bash
oc get events -n team-a-prod --sort-by=.lastTimestamp
```

### 19.2 Rollout stages

For production:

1. **Observe current usage**
2. **Set quota above current usage**
3. **Apply defaults with LimitRange**
4. **Require app manifests to declare requests and limits**
5. **Gradually lower maximums**
6. **Add storage and object-count quotas**
7. **Enable stricter validation in CI**
8. **Enable Argo CD self-heal**

### 19.3 Never start with very strict quotas

A new quota can immediately block:

- Deployment scale-up
- ReplicaSet rollout
- Job creation
- CronJob execution
- PVC creation
- Route/service creation if object-count quotas are too low
- Build or pipeline objects, depending on quota coverage

## 20. CI Validation Before Argo CD Sync

A strong GitOps pipeline validates manifests before Argo CD applies them.

### 20.1 Example validation pipeline

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "Rendering Kustomize..."
oc kustomize policies/quota-limit/overlays/dev > /tmp/rendered.yaml

echo "Client validation..."
oc apply --dry-run=client -f /tmp/rendered.yaml

echo "Server validation..."
oc apply --dry-run=server -f /tmp/rendered.yaml

echo "Check for ResourceQuota..."
grep -q "kind: ResourceQuota" /tmp/rendered.yaml

echo "Check for LimitRange..."
grep -q "kind: LimitRange" /tmp/rendered.yaml
```

### 20.2 Policy checks

Use policy-as-code to enforce standards.

Example rules:

- Every non-system namespace must have a `ResourceQuota`.
- Every team namespace must have a `LimitRange`.
- Dev namespaces cannot request load balancers.
- Prod namespaces must have object-count quotas.
- PVC max size must be defined.
- `limits.cpu` cannot be more than 4x `requests.cpu` for standard workloads.
- No namespace can set `services.loadbalancers` above 0 unless approved.

Pseudo Rego policy idea:

```rego
package quota_policy

deny[msg] {
  input.kind == "ResourceQuota"
  not input.spec.hard["requests.cpu"]
  msg := "ResourceQuota must define requests.cpu"
}

deny[msg] {
  input.kind == "ResourceQuota"
  not input.spec.hard["requests.memory"]
  msg := "ResourceQuota must define requests.memory"
}

deny[msg] {
  input.kind == "LimitRange"
  not input.spec.limits[_].defaultRequest.cpu
  msg := "LimitRange must define defaultRequest.cpu"
}
```

## 22. Troubleshooting

### 22.1 Argo CD sync fails with Forbidden

Symptom:

```text
resourcequotas is forbidden:
User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller"
cannot create resource "resourcequotas" in API group "" in namespace "team-a-dev"
```

Cause:

Argo CD application controller does not have permission.

Fix:

```bash
oc adm policy add-role-to-user admin \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n team-a-dev
```

For cluster-scoped quota:

```bash
oc adm policy add-cluster-role-to-user argocd-quota-governance-manager \
  system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

### 22.2 Workload rollout fails after quota applied

Check deployment:

```bash
oc rollout status deployment/myapp -n team-a-dev
```

Check ReplicaSet events:

```bash
oc describe rs -n team-a-dev
```

Check namespace events:

```bash
oc get events -n team-a-dev --sort-by=.lastTimestamp
```

Likely errors:

```text
exceeded quota
```

or:

```text
maximum memory usage per Container is 2Gi, but limit is 4Gi
```

Fix options:

- Increase quota through Git
- Reduce app requests/limits
- Reduce replicas
- Delete unused pods/jobs/PVCs
- Move workload to larger quota tier

### 22.3 LimitRange default not visible in Deployment YAML

This is expected.

A `LimitRange` can default resource values at pod admission time. Your Deployment manifest in Git might still not show resources.

Best practice:

Always define resource requests and limits in application Deployment manifests even if a `LimitRange` exists.

Example:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

Treat `LimitRange` defaults as safety net, not as replacement for good application manifests.

### 22.4 ResourceQuota stuck or usage looks stale

Check status:

```bash
oc get resourcequota namespace-standard-quota -n team-a-dev -o yaml
```

Check deleted resources:

```bash
oc get pods,pvc,secrets,configmaps -n team-a-dev
```

Quota usage is maintained by quota controllers and can temporarily lag after deletion. Wait and re-check. If it persists, inspect controller health and API server events.

### 22.5 Multiple quotas confuse developers

If multiple `ResourceQuota` objects exist in a namespace, all applicable quota constraints must be satisfied. A pod can be rejected even if one quota appears to have space but another quota is exhausted.

Recommendation:

- Use one main compute/object quota per namespace.
- Use separate storage-class quota only when required.
- Keep names descriptive.
- Document purpose in annotations.

Example:

```yaml
metadata:
  annotations:
    platform.example.com/purpose: "Main namespace compute and object-count quota"
```

### 22.6 Argo CD cannot delete old quota

If a quota object is removed from Git and pruning is enabled, Argo CD will delete it.

For critical quota objects, you may want deletion confirmation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Delete=confirm
```

Or keep pruning manual for platform governance apps.

### 22.7 Namespace deletion risk

If Argo CD manages Namespace and pruning is enabled, removing the namespace YAML from Git can trigger namespace deletion.

Production safety:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm,Delete=confirm
```

Also use branch protection and code owner approval.

## 23. Advanced Production Best Practices

### 23.1 Keep quotas platform-owned

Application teams should not own their own quota guardrails in the same repo where they deploy workloads.

Why?

Because a team under pressure might increase its own quota without platform approval.

Recommended ownership:

| Object | Owner |
|---|---|
| Namespace | Platform team |
| ResourceQuota | Platform team |
| LimitRange | Platform team |
| ClusterResourceQuota | Platform team |
| Deployment requests/limits | Application team |
| HPA | Application team with platform review |
| PVC size | Application team within platform rules |

### 23.2 Use quota tiers instead of one-off values

Avoid every namespace having unique quota values.

Use standard tiers:

```text
dev-small
dev-standard
test-standard
prod-standard
prod-large
```

Benefits:

- Easier capacity planning
- Easier troubleshooting
- Easier chargeback
- Easier automation
- Less YAML drift

### 23.3 Define object-count quotas

Many admins only define CPU and memory. That is not enough.

Add quotas for:

```yaml
services: "20"
secrets: "100"
configmaps: "100"
persistentvolumeclaims: "20"
count/jobs.batch: "50"
count/cronjobs.batch: "20"
```

Object quotas protect API server and etcd from namespace-level object sprawl.

### 23.4 Prevent accidental LoadBalancer and NodePort services

In OpenShift on cloud or bare metal, these services can have infrastructure impact.

For namespaces that should not create them:

```yaml
hard:
  services.loadbalancers: "0"
  services.nodeports: "0"
```

### 23.5 Use ephemeral storage quota

Without ephemeral storage governance, workloads can fill node disks.

Example:

```yaml
hard:
  requests.ephemeral-storage: 20Gi
  limits.ephemeral-storage: 40Gi
```

And in app workloads:

```yaml
resources:
  requests:
    ephemeral-storage: 1Gi
  limits:
    ephemeral-storage: 2Gi
```

### 23.6 Balance requests and limits

CPU limits can throttle workloads. Memory limits can kill workloads.

Recommended approach:

- Always set memory requests and limits.
- Set CPU requests.
- Use CPU limits carefully, especially for latency-sensitive applications.
- Avoid extremely high limit-to-request ratios.
- For production Java workloads, tune JVM memory with container limits.

### 23.7 Do not apply aggressive quotas to OpenShift system namespaces

Avoid applying generic quotas to:

```text
openshift-*
kube-*
default
```

unless you fully understand the operator and system workload impact.

System namespaces are managed by operators and cluster components. Incorrect quota can break upgrades, monitoring, logging, registry, networking, or operator reconciliation.

### 23.8 Use dry-run before production sync

Always run:

```bash
oc apply --dry-run=server -k policies/quota-limit/overlays/prod
```

Server-side dry-run catches API validation issues that local rendering cannot.

### 23.9 Protect production branches

Recommended branch protection:

- Pull request required
- At least two reviewers
- CODEOWNERS for platform team
- CI validation required
- Signed commits for critical policy repos
- No direct push to `main`
- Separate dev and prod promotion branches if needed

### 23.10 Track quota changes in change management

Quota changes affect capacity and availability.

For production, include:

- Reason for change
- Current usage
- Proposed hard limit
- Impact analysis
- Rollback plan
- Expiry date for temporary increase
- Approval ticket

## 26. Interview-Level Explanation

If asked in an advanced OpenShift interview:

> How would you manage quotas and limits using GitOps in OpenShift?

Strong answer:

> I would manage namespace guardrails as platform-owned GitOps resources. Each project would have a Git-defined Namespace, ResourceQuota, and LimitRange. Argo CD would reconcile these through a platform governance AppProject with restricted source repos, destinations, and resource whitelists. I would use sync waves so namespaces are created first, then RBAC, then ResourceQuota and LimitRange, and only then application workloads. For multiple namespaces owned by the same team, I would use OpenShift ClusterResourceQuota with controlled namespace labels. All changes would go through pull requests, server-side dry-run, policy checks, and Argo CD sync. Drift from manual quota changes would be detected and optionally self-healed. For production, I would avoid aggressive quota reductions without checking current usage, and I would protect namespace deletion with prune/delete confirmation.

      command: ["sleep", "3600"]
      resources:
        limits:
          cpu: "1"
          memory: 1Gi

## 28. Common Design Mistakes

### Mistake 1: Application teams can modify their own quota

Problem:

Application team can increase quota without capacity approval.

Fix:

Keep quotas in platform repo and restrict write access.

### Mistake 2: No LimitRange defaults

Problem:

Pods without requests can be scheduled poorly or rejected when quota requires requests.

Fix:

Define `defaultRequest` and `default` in LimitRange.

### Mistake 3: Quota applied after workloads

Problem:

Existing workloads may not follow expected defaults.

Fix:

Use sync waves and apply namespace policy before workloads.

### Mistake 4: No object-count quotas

Problem:

Namespace creates too many secrets, configmaps, jobs, or services.

Fix:

Add object-count quotas.

### Mistake 5: No storage quota

Problem:

A namespace consumes too much dynamic storage.

Fix:

Add `requests.storage`, PVC count, and StorageClass-specific quotas.

### Mistake 6: Namespace pruning enabled without confirmation

Problem:

Removing one YAML file deletes the entire namespace.

Fix:

Use `Prune=confirm` and `Delete=confirm`.

### Mistake 7: Too many unique quota sizes

Problem:

Hard to manage capacity and support.

Fix:

Use quota tiers.

### Mistake 8: Lowering quota below current usage without plan

Problem:

New pods, PVCs, or objects may be blocked.

Fix:

Check `oc describe quota` before merge.

## 31. Summary

GitOps for quotas and limits is a mature OpenShift platform engineering practice.

A strong design includes:

- Git-managed `ResourceQuota`
- Git-managed `LimitRange`
- Optional OpenShift `ClusterResourceQuota`
- Namespace labels controlled by platform team
- Argo CD AppProjects with least privilege
- Sync waves for correct ordering
- CI validation and server-side dry-run
- Pull request approval for production changes
- Drift detection and optional self-healing
- Monitoring for quota usage and admission failures

For advanced OpenShift administration, quotas and limits should be treated as policy-as-code, not as one-time namespace setup.

When implemented correctly, this gives the organization:

- Stable shared clusters
- Predictable resource consumption
- Safer developer self-service
- Better capacity planning
- Clear audit trail
- Faster rollback
- Reduced configuration drift
