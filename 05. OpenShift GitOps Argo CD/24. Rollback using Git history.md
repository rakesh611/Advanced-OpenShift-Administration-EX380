## 1. Core Idea

In OpenShift GitOps, rollback using Git history means restoring the desired state in Git to a previously known-good configuration and allowing Argo CD to reconcile the OpenShift cluster back to that state.

In simple terms:

```text
Bad commit in Git
        ↓
Argo CD syncs bad desired state
        ↓
Application or cluster config breaks
        ↓
Admin reverts Git to a good state
        ↓
Argo CD detects Git desired state changed
        ↓
Argo CD syncs cluster back to working state
```

This is different from directly running `oc edit`, `oc patch`, or `kubectl rollout undo` on live resources. In GitOps, live-cluster changes are temporary unless they are represented in Git.

---

## 2. Why Git History Is the Correct Rollback Mechanism in GitOps

GitOps has one important operational rule:

> Git is the source of truth. The cluster should match Git, not the other way around.

Because of this, the safest rollback method is usually not to manually change the cluster. The safest method is to change Git back to a previously valid desired state.

Git history gives you:

- **Audit trail:** who changed what, when, and why.
- **Repeatability:** the same rollback can be replayed across dev, test, stage, and prod.
- **Peer review:** rollback can go through pull request approval.
- **Disaster recovery:** a new cluster can be rebuilt from Git.
- **Change traceability:** Git commits map to incidents, tickets, and deployment records.
- **Multi-cluster consistency:** the same revert can repair multiple clusters if they track the same Git source.

For advanced OpenShift administrators, the key mindset is this:

```text
Do not roll back only the pod.
Do not roll back only the Deployment.
Do not roll back only the ReplicaSet.
Roll back the desired declarative state.
```

## 3. How OpenShift GitOps and Argo CD Treat Desired State

Red Hat OpenShift GitOps uses Argo CD as the continuous delivery engine. Argo CD continuously compares:

```text
Desired state  = manifests generated from Git / Helm / Kustomize / OCI
Live state     = resources currently present in OpenShift
```

If the desired state and live state differ, the Argo CD Application becomes `OutOfSync`.

Depending on sync policy, Argo CD can:

- only report drift,
- wait for manual sync,
- automatically sync,
- self-heal live drift,
- prune deleted resources,
- run hooks and sync waves,
- sync only selected resources,
- apply server-side apply or replace behavior.

Example Argo CD `Application`:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
spec:
  project: production
  source:
    repoURL: https://git.example.com/platform/payment-api-gitops.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

In this example, rollback depends on what `main` and `overlays/prod` contain. If you revert Git, Argo CD sees a new desired state and applies it.

## 4. Rollback Types in Argo CD

There are several rollback patterns:

| Rollback Type | Where rollback happens | Git remains source of truth? | Recommended for production? |
|---|---|---:|---:|
| Git revert | Git repository | Yes | Yes |
| Pull request revert | Git repository | Yes | Yes |
| Reset branch to old commit | Git repository | Risky | Sometimes |
| Move `targetRevision` to old tag/commit | Argo CD Application spec | Yes, if Application spec is Git-managed | Yes, with control |
| Argo CD history rollback | Argo CD deployment history | Not always | Emergency only |
| `oc rollout undo` | OpenShift live resource | No | Temporary emergency only |
| Manual `oc edit` | OpenShift live resource | No | Avoid except break-glass |

## 5. Git History Rollback vs Argo CD History Rollback

This distinction is very important.

### Git history rollback

Git history rollback changes the desired state in Git.

Example:

```bash
git revert <bad_commit_sha>
git push origin main
argocd app sync payment-api-prod
```

Result:

```text
Git desired state is corrected.
Argo CD syncs the cluster to corrected desired state.
Future syncs remain stable.
Audit trail is preserved.
```

### Argo CD history rollback

Argo CD can roll back an application to a previously deployed revision by history ID:

```bash
argocd app history payment-api-prod
argocd app rollback payment-api-prod <history_id>
```

This can be useful during an outage, but it does not automatically fix the Git branch if the branch still points to the bad commit. If automated sync later detects that Git still contains the bad desired state, the bad state can be reapplied.

Therefore:

```text
Argo CD history rollback = operational recovery
Git revert rollback      = desired-state correction
```

In production GitOps, always repair Git after any emergency rollback.

## 6. Production Rollback Decision Matrix

| Situation | Best action |
|---|---|
| Bad image tag deployed | Revert image tag commit in Git |
| Bad ConfigMap value | Revert ConfigMap commit in Git |
| Bad Route/TLS config | Revert Route or certificate manifest in Git |
| Bad NetworkPolicy blocking traffic | Revert NetworkPolicy commit in Git |
| Bad RBAC removing admin access | Use break-glass access, then revert Git |
| Bad SCC/securityContext causing pods to fail | Revert SCC/RBAC/securityContext Git change |
| Bad Helm values | Revert `values.yaml` or chart version commit |
| Bad Kustomize overlay | Revert overlay patch commit |
| Bad ApplicationSet generator | Revert ApplicationSet commit carefully |
| Production outage, no time for PR | Temporarily Argo CD rollback, then Git revert immediately |
| Database schema incompatible | Do not blindly rollback app; use DB rollback/migration plan |

## 7. Reference Architecture

A mature OpenShift GitOps rollback architecture usually has this flow:

```text
Developer / Platform Engineer
        ↓
Pull Request
        ↓
Git review + CI validation
        ↓
Merge to environment branch
        ↓
Argo CD detects new Git revision
        ↓
OpenShift resources sync
        ↓
Monitoring validates health
        ↓
If issue found: revert PR / revert commit
        ↓
Argo CD reconciles previous desired state
```

For production, avoid direct cluster changes unless:

- API access is broken,
- Argo CD is down,
- Git server is down,
- a security incident requires immediate containment,
- a bad GitOps change removed your ability to repair through normal path.

## 9. Common Rollback Scenarios

### Scenario A: Bad image tag

Bad commit:

```yaml
image: image-registry.openshift-image-registry.svc:5000/payment/payment-api:v2.1.0
```

Known good state:

```yaml
image: image-registry.openshift-image-registry.svc:5000/payment/payment-api:v2.0.5
```

Rollback action:

```bash
git revert <commit_that_changed_v205_to_v210>
git push origin main
argocd app sync payment-api-prod
```

### Scenario B: Bad ConfigMap

Bad commit changed:

```yaml
FEATURE_PAYMENT_GATEWAY_V2: "true"
```

Rollback returns it to:

```yaml
FEATURE_PAYMENT_GATEWAY_V2: "false"
```

Important: pods might not restart automatically when ConfigMap changes unless you use checksum annotations, restart automation, or a rollout trigger.

### Scenario C: Bad NetworkPolicy

Bad NetworkPolicy blocks route-to-pod or app-to-db traffic.

Rollback action:

```bash
git revert <bad_networkpolicy_commit>
git push origin main
argocd app sync payment-api-prod
oc get networkpolicy -n payment-prod
oc get endpoints -n payment-prod
```

### Scenario D: Bad Route TLS config

Bad commit changed edge termination to passthrough or updated wrong certificate.

Rollback action:

```bash
git revert <bad_route_tls_commit>
git push origin main
argocd app sync payment-api-prod
oc get route -n payment-prod
curl -k https://payment.example.com/healthz
```

## 10. Method 1: Rollback by `git revert`

This is the safest and most common production method.

### When to use

Use `git revert` when:

- bad commit is already merged to shared branch,
- you want to preserve history,
- team uses pull requests,
- branch protection is enabled,
- rollback must be auditable.

### Flow

```text
Find bad commit
        ↓
Create revert commit
        ↓
Push revert commit
        ↓
Argo CD sees new revision
        ↓
Sync application
        ↓
Validate OpenShift state
```

### Commands

```bash
# 1. Clone repository
git clone https://git.example.com/platform/payment-api-gitops.git
cd payment-api-gitops

# 2. Inspect recent history
git log --oneline --decorate --graph -n 20

# 3. See what the bad commit changed
git show <bad_commit_sha>

# 4. Revert the bad commit
git revert <bad_commit_sha>

# 5. Push revert commit
git push origin main

# 6. Ask Argo CD to refresh/sync
argocd app get payment-api-prod --refresh
argocd app diff payment-api-prod
argocd app sync payment-api-prod
argocd app wait payment-api-prod --health --sync --timeout 300
```

### OpenShift validation

```bash
oc get deploy,rs,pod,svc,route -n payment-prod
oc rollout status deploy/payment-api -n payment-prod
oc logs deploy/payment-api -n payment-prod --tail=100
oc get events -n payment-prod --sort-by=.lastTimestamp | tail -30
curl -k https://payment.example.com/healthz
```

### Why `git revert` is safer than `git reset`

`git revert` creates a new commit that reverses an old commit. It does not rewrite branch history.

```text
A -- B -- C -- D          main has bad commit D
A -- B -- C -- D -- E     E reverts D
```

This is good for shared branches because all users can pull normally.

## 11. Method 2: Rollback by Reverting a Pull Request

Most enterprise GitOps systems merge changes through pull requests.

### Example flow

```text
PR #145 introduced bad change
        ↓
Open Git provider
        ↓
Click Revert PR
        ↓
New PR #146 is created
        ↓
Review and merge PR #146
        ↓
Argo CD syncs corrected desired state
```

### Why this is preferred in regulated environments

A PR-based rollback gives:

- approval record,
- incident link,
- CI validation,
- change-management evidence,
- easy audit trail,
- cleaner communication between app and platform teams.

### Recommended revert PR title

```text
Revert PR #145: rollback payment-api image v2.1.0 from production
```

### Recommended revert PR description

```markdown
## Reason
Rolling back production deployment because payment-api v2.1.0 is failing readiness checks and causing 5xx responses.

## Change
This PR reverts image tag from v2.1.0 to v2.0.5 in overlays/prod.

## Validation
- Argo CD diff reviewed
- Deployment rollout completed
- Route health endpoint verified
- Error rate returned to baseline

## Incident
INC-2026-000123
```

## 12. Method 3: Rollback by Resetting a Git Branch

`git reset` is more dangerous because it rewrites history.

### Soft warning

Use branch reset only when you fully understand the Git collaboration impact.

### Example

```bash
git checkout main
git pull origin main
git reset --hard <known_good_commit_sha>
git push --force-with-lease origin main
```

### Why it is risky

```text
Before reset:
A -- B -- C -- D   main

After reset to B:
A -- B             main
```

Commits `C` and `D` disappear from the visible branch history, although they may still exist in reflog or remote references for some time.

### When branch reset may be acceptable

- dedicated environment branch, such as `dev` or `test`,
- no strict audit requirement,
- no shared development dependency,
- platform-admin-approved emergency,
- Git provider allows force push only for maintainers.

### When not to use

Avoid branch reset for:

- production branch,
- protected branch,
- regulated environments,
- multi-team shared repositories,
- repositories used by ApplicationSet for many clusters.

For production, prefer `git revert`.

## 13. Method 4: Rollback by Moving `targetRevision`

Argo CD `Application.spec.source.targetRevision` decides which Git revision, branch, tag, or commit the application tracks.

Example:

```yaml
spec:
  source:
    repoURL: https://git.example.com/platform/payment-api-gitops.git
    targetRevision: main
    path: overlays/prod
```

You can roll back by changing `targetRevision`:

```yaml
spec:
  source:
    repoURL: https://git.example.com/platform/payment-api-gitops.git
    targetRevision: release-2026-07-01
    path: overlays/prod
```

or:

```yaml
spec:
  source:
    targetRevision: v2.0.5
```

or even:

```yaml
spec:
  source:
    targetRevision: 9fceb02a9b9c0f1c6a2b1a0e7d6c5b4a3f2e1d0c
```

### Important production point

If your Argo CD `Application` itself is managed by Git, do not patch it manually unless it is an emergency. Change the Application manifest in Git.

Good:

```bash
vi argocd/app-prod.yaml
git commit -am "Rollback payment-api-prod targetRevision to v2.0.5"
git push origin main
```

Emergency only:

```bash
oc patch application payment-api-prod -n openshift-gitops --type merge -p \
'{"spec":{"source":{"targetRevision":"v2.0.5"}}}'
```

If the Application is Git-managed, manual patching may be reverted by the parent app or app-of-apps controller.

## 14. Method 5: Rollback by Git Tag or Release Branch

For production workloads, tagging known-good states is a strong practice.

### Release tag strategy

```bash
git tag -a prod-payment-api-v2.0.5 -m "Known good production release v2.0.5"
git push origin prod-payment-api-v2.0.5
```

Argo CD Application:

```yaml
spec:
  source:
    targetRevision: prod-payment-api-v2.0.5
```

### Release branch strategy

```text
main                 continuous integration branch
release/prod         production desired state
release/stage        staging desired state
release/dev          development desired state
```

Rollback production branch:

```bash
git checkout release/prod
git revert <bad_commit_sha>
git push origin release/prod
```

Application:

```yaml
spec:
  source:
    targetRevision: release/prod
```

### Tag vs branch

| Option | Mutable? | Best for |
|---|---:|---|
| Branch | Yes | continuous environment tracking |
| Tag | Usually no | immutable release references |
| Commit SHA | No | precise emergency pinning |

## 15. Emergency Rollback with Argo CD History

Argo CD stores deployment history for Applications. You can inspect it:

```bash
argocd app history payment-api-prod
```

Example output style:

```text
ID  DATE                           REVISION
0   2026-07-01 11:30:10 +0530     71c1a2b
1   2026-07-02 14:10:42 +0530     8c92f10
2   2026-07-03 09:21:05 +0530     bad1234
```

Rollback to history ID `1`:

```bash
argocd app rollback payment-api-prod 1
```

Rollback and allow prune:

```bash
argocd app rollback payment-api-prod 1 --prune
```

Wait:

```bash
argocd app wait payment-api-prod --sync --health --timeout 300
```

### Critical warning

If the tracked Git branch still points to the bad commit, automated sync can eventually bring the bad state back.

Therefore the full emergency process should be:

```text
1. Argo CD rollback to restore service quickly.
2. Disable automated sync if needed.
3. Revert Git commit or revert PR.
4. Re-enable automated sync if disabled.
5. Sync from corrected Git state.
6. Validate application and cluster state.
```

## 16. Rollback with Automated Sync Enabled

Automated sync means Argo CD can sync when it detects a difference between Git desired manifests and live cluster state.

Example:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

### With automated sync, rollback flow is simple

```bash
git revert <bad_commit_sha>
git push origin main
```

Argo CD detects the new Git commit and syncs automatically.

### Watch sync

```bash
argocd app get payment-api-prod --refresh
argocd app wait payment-api-prod --health --sync --timeout 300
```

### When to temporarily disable automated sync

Disable automated sync if:

- bad state is repeatedly reapplying,
- you need investigation time,
- rollback requires ordered manual actions,
- database or external dependency must be handled first,
- prune could delete important resources during rollback.

Disable automated sync using CLI:

```bash
argocd app set payment-api-prod --sync-policy manual
```

Or patch the Application:

```bash
oc patch application payment-api-prod -n openshift-gitops --type merge -p \
'{"spec":{"syncPolicy":null}}'
```

Better Git-managed approach:

```yaml
syncPolicy: {}
```

or:

```yaml
syncPolicy:
  automated:
    enabled: false
```

## 17. Rollback with Manual Sync Enabled

If sync policy is manual, Git revert only makes the Argo CD app `OutOfSync`; it does not change the cluster until you sync.

### Flow

```bash
git revert <bad_commit_sha>
git push origin main

argocd app get payment-api-prod --refresh
argocd app diff payment-api-prod
argocd app sync payment-api-prod --preview-changes
argocd app wait payment-api-prod --health --sync --timeout 300
```

### Why manual sync is useful for production

Manual sync gives the admin a final checkpoint:

- review diff,
- confirm resources to be changed,
- decide whether prune is safe,
- coordinate with DB/network/security teams,
- control exact rollback timing.

## 18. Rollback with Prune and Self-Heal

### Prune

Prune deletes live resources that are no longer in Git.

Example:

```yaml
syncPolicy:
  automated:
    prune: true
```

During rollback, prune can be dangerous if the old Git state does not contain a resource created later but still needed.

Example:

```text
Commit D added ConfigMap payment-feature-flags.
Commit E made bad app change.
Rollback to commit C with prune enabled.
ConfigMap from D may be deleted.
```

### Self-heal

Self-heal corrects live drift back to Git.

Example:

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

If an admin manually patches a live Deployment during an incident, self-heal can revert that patch back to Git.

### Production guidance

Before rollback, check:

```bash
argocd app get payment-api-prod -o yaml | yq '.spec.syncPolicy'
```

During risky rollback:

```bash
argocd app sync payment-api-prod --prune --preview-changes
```

For critical resources such as Namespaces, consider using prune confirmation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

## 19. Rollback of Kubernetes Deployments

### GitOps rollback

Change image tag in Git:

```yaml
spec:
  template:
    spec:
      containers:
        - name: payment-api
          image: quay.io/example/payment-api:v2.0.5
```

Commit and push:

```bash
git commit -am "Rollback payment-api image to v2.0.5"
git push origin main
argocd app sync payment-api-prod
```

Validate:

```bash
oc rollout status deployment/payment-api -n payment-prod
oc get pods -n payment-prod -l app=payment-api
oc describe deployment/payment-api -n payment-prod
```

### Avoid depending only on ReplicaSet rollback

This command is not GitOps-safe as a permanent fix:

```bash
oc rollout undo deployment/payment-api -n payment-prod
```

Why?

Because Argo CD can later reconcile the Deployment back to Git.

Use `oc rollout undo` only as a break-glass temporary action, then fix Git.

## 20. Rollback of OpenShift Routes

Route rollback can involve:

- hostname,
- TLS termination type,
- certificate/key/CA bundle,
- service target,
- wildcard policy,
- annotations.

Example bad Route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payment-api
spec:
  host: payment.example.com
  to:
    kind: Service
    name: payment-api

    termination: passthrough
```

Known good Route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payment-api
spec:
  host: payment.example.com
  to:
    kind: Service
    name: payment-api
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
```

Rollback:

```bash
git revert <bad_route_commit>
git push origin main
argocd app sync payment-api-prod
```

Validate:

```bash
oc get route payment-api -n payment-prod -o yaml
curl -k -I https://payment.example.com
curl -k https://payment.example.com/healthz
```

## 21. Rollback of ConfigMaps and Secrets

### ConfigMap rollback

Bad ConfigMap commit:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: payment-api-config
data:
  FEATURE_X_ENABLED: "true"
```

Rollback:

```bash
git revert <bad_configmap_commit>
git push origin main
argocd app sync payment-api-prod
```

### Important issue: pods may not reload ConfigMap automatically

If a ConfigMap is mounted as a volume, kubelet eventually updates mounted content, but applications may not reload it. If a ConfigMap is consumed as environment variables, pods must restart to pick up the change.

Common GitOps pattern:

```yaml
metadata:
  annotations:
    checksum/config: "{{ checksum-of-configmap }}"
```

For Kustomize, you can use generated ConfigMap names:

```yaml
configMapGenerator:
  - name: payment-api-config
    literals:
      - FEATURE_X_ENABLED=false
```

This changes the ConfigMap name when data changes and causes a Deployment rollout if referenced correctly.

### Secret rollback

Do not commit plain-text secrets to Git.

Use one of these approaches:

- Sealed Secrets,
- External Secrets Operator,
- Vault integration,
- SOPS-encrypted YAML,
- OpenShift GitOps-supported secret management pattern approved by your organization.

Rollback of a secret should be handled carefully because old credentials may have been rotated, revoked, or compromised.

## 22. Rollback of RBAC, SCC, Quota, LimitRange, and NetworkPolicy

Cluster and namespace configuration rollback is higher risk than app image rollback.

### RBAC rollback

Bad commit removed admin group from RoleBinding:

```yaml
kind: RoleBinding
subjects: []
```

Rollback:

```bash
git revert <bad_rbac_commit>
git push origin main
argocd app sync platform-rbac-prod
```

If GitOps itself loses permission to repair RBAC, use a cluster-admin break-glass account:

```bash
oc adm policy add-role-to-group admin platform-admins -n payment-prod
```

Then fix Git immediately.

### SCC rollback

Bad securityContext or SCC binding may cause pods to fail with errors such as:

```text
would violate PodSecurity "restricted"
unable to validate against any security context constraint
```

Rollback Git changes affecting:

- ServiceAccount,
- RoleBinding / ClusterRoleBinding,
- SCC binding,
- `runAsUser`,
- `fsGroup`,
- `seLinuxOptions`,
- `allowPrivilegeEscalation`,
- capabilities.

Validation:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp | tail -50
oc adm policy who-can use scc anyuid
```

### ResourceQuota rollback

Bad quota may block new pods:

```text
exceeded quota: compute-quota
```

Rollback quota commit:

```bash
git revert <bad_quota_commit>
git push origin main
argocd app sync namespace-policy-prod
```

Validate:

```bash
oc describe quota -n payment-prod
oc describe limitrange -n payment-prod
```

### NetworkPolicy rollback

Bad NetworkPolicy can silently block traffic.

Validate labels before blaming policy:

```bash
oc get pods -n payment-prod --show-labels
oc get netpol -n payment-prod -o yaml
oc get endpoints -n payment-prod
```

Rollback:

```bash
git revert <bad_networkpolicy_commit>
git push origin main
argocd app sync network-policy-prod
```

Test connectivity from a debug pod:

```bash
oc run net-debug -n payment-prod --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -v http://payment-api:8080/healthz
```

## 23. Rollback of Operators and Operator-Managed Resources

Operator rollback is not the same as application rollback.

OpenShift Operators are managed through:

- `Subscription`,
- `OperatorGroup`,
- `CatalogSource`,
- `InstallPlan`,
- CRDs,
- operator custom resources.

### Example Subscription

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: my-operator
  namespace: my-operator-ns
spec:
  channel: stable
  installPlanApproval: Manual
  name: my-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

### Rollback considerations

Rolling back the Subscription manifest may not downgrade the installed operator automatically. Operator Lifecycle Manager behavior depends on channel, installed CSV, available versions, and upgrade graph.

For production:

1. Review installed CSV:

```bash
oc get csv -n my-operator-ns
oc describe subscription my-operator -n my-operator-ns
```

2. Review InstallPlans:

```bash
oc get installplan -n my-operator-ns
```

3. Revert Git only after confirming OLM downgrade/upgrade behavior.

4. Check operator-managed custom resources separately.

A Git revert may correct desired Subscription YAML but may not safely reverse data-plane changes made by the operator.

## 24. Rollback of Helm-Based Argo CD Applications

Argo CD can render Helm charts. Rollback may involve:

- chart version,
- Helm values,
- image tag,
- resource limits,
- ingress/route settings,
- serviceAccount/RBAC settings.

Example Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: etherpad-prod
  namespace: openshift-gitops
spec:
  source:
    repoURL: https://charts.example.com
    chart: etherpad
    targetRevision: 1.2.3
    helm:
      valueFiles:
        - values-prod.yaml
```

### Rollback chart version

```yaml
targetRevision: 1.2.2
```

### Rollback values

```bash
git revert <bad_values_commit>
git push origin main
argocd app sync etherpad-prod
```

### Validate rendered manifests before syncing

```bash
argocd app diff etherpad-prod
argocd app manifests etherpad-prod > rendered.yaml
```

### Helm rollback warning

Do not use `helm rollback` directly against an Argo CD-managed release unless it is break-glass. Argo CD will reconcile back to Git-rendered desired state.

## 25. Rollback of Kustomize-Based Argo CD Applications

Kustomize is very common in OpenShift GitOps because it cleanly separates base from overlays.

### Bad overlay patch

```yaml
patches:
  - path: patch-resources-too-low.yaml
```

Rollback:

- reverting only the patch file but not `kustomization.yaml`,

## 26. Rollback in App-of-Apps Pattern

In app-of-apps, a parent Argo CD Application manages child Applications.

Example:

```text
root-platform-app
├── namespace-config-app
├── rbac-app
├── network-policy-app
├── payment-api-app
└── monitoring-app
```

If you manually patch a child Application, the parent may revert it.

### Correct rollback location

If the bad change is in:

```text
apps/payment-api-app.yaml
```

rollback that file in Git, not only the generated child app in OpenShift.

### Commands

```bash
argocd app get root-platform-app
argocd app get payment-api-prod

git revert <bad_child_app_commit>
git push origin main

argocd app sync root-platform-app
argocd app sync payment-api-prod
```

### Advanced point

Sometimes you must sync the parent first so it updates the child Application spec, then sync the child so it updates workload resources.

## 27. Rollback in ApplicationSet / Multi-Cluster GitOps

ApplicationSet can generate many Applications across clusters or namespaces.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: payment-api-clusters
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - cluster: prod-east
            url: https://api.prod-east.example.com:6443
          - cluster: prod-west
            url: https://api.prod-west.example.com:6443
  template:
    metadata:
      name: 'payment-api-{{cluster}}'
    spec:
      source:
        repoURL: https://git.example.com/platform/payment-api-gitops.git
        targetRevision: main
        path: overlays/prod
      destination:
        server: '{{url}}'
        namespace: payment-prod
```

### Risk

One bad Git commit can break many clusters.

### Safer rollback strategy

Use phased environment promotion:

```text
overlays/dev      → dev clusters
overlays/stage    → stage clusters
overlays/prod     → prod clusters
```

or cluster-specific paths:

```text
overlays/prod-east
overlays/prod-west
```

### Multi-cluster rollback

```bash
git revert <bad_commit_sha>
git push origin main

argocd app sync -l app.kubernetes.io/part-of=payment-api
argocd app wait -l app.kubernetes.io/part-of=payment-api --health --sync --timeout 600
```

### Production caution

For multi-cluster outages, avoid simultaneous uncontrolled rollback if clusters have different live conditions. Consider progressive sync, sync windows, or label-based sync groups.

## 29. Troubleshooting Failed Rollbacks

### Problem 1: Argo CD still syncs bad version

Possible causes:

- Git revert was pushed to wrong branch.
- Application tracks a different branch/tag.
- Application path points to another overlay.
- Parent app or ApplicationSet overwrote child app.
- Helm chart values still override image tag.
- Kustomize overlay still overrides base.

Check:

```bash
argocd app get payment-api-prod -o yaml | yq '.spec.source'
git branch --show-current
git log --oneline -n 5
```

### Problem 2: App is `OutOfSync` after rollback

Check diff:

```bash
argocd app diff payment-api-prod
```

Common reasons:

- live resources mutated by admission controllers,
- generated fields,
- HPA changed replicas,
- operator modified managed fields,
- ConfigMap or Secret generated name changed,
- ignored differences not configured.

### Problem 3: App is `Synced` but not `Healthy`

This means desired state was applied, but workload is failing.

Check:

```bash
argocd app get payment-api-prod
oc get pods -n payment-prod
oc describe pod <pod> -n payment-prod
oc logs <pod> -n payment-prod --previous
```

Common reasons:

- image pull error,
- bad probe,
- SCC denial,
- missing Secret,
- PVC pending,
- quota exceeded,
- Route points to Service with no endpoints.

### Problem 4: Rollback stuck because prune confirmation is required

Check Application events and sync status.

Approve prune only after confirming resource deletion is safe.

```bash
argocd app get payment-api-prod
argocd app sync payment-api-prod --prune
```

For resources annotated with `Prune=confirm`, use UI confirmation or approved annotation as per your organization policy.

### Problem 5: ApplicationSet reverts manual rollback

If ApplicationSet owns the Application, direct changes to the generated Application may be overwritten.

Fix the ApplicationSet source in Git:

```bash
oc get applicationset -n openshift-gitops
oc get applicationset payment-api-clusters -n openshift-gitops -o yaml
```

Then revert the generator/template commit.

### Problem 6: Rollback changed Git but Argo CD does not detect it

Refresh hard:

```bash
argocd app get payment-api-prod --hard-refresh
```

Check repo-server:

```bash
oc get pods -n openshift-gitops
oc logs deploy/openshift-gitops-repo-server -n openshift-gitops --tail=100
```

Check repository credentials and webhook:

```bash
argocd repo list
argocd app get payment-api-prod
```

## 31. Best Practices

### 1. Prefer `git revert` over branch reset

Use revert for production because it preserves history.

### 2. Keep environment branches protected

Protect:

```text
main
release/prod
cluster-config-prod
```

Require:

- pull request review,
- CI validation,
- signed commits if required,
- no force push,
- CODEOWNERS approval.

### 3. Use tags for known-good releases

Tag releases:

```bash
git tag -a payment-api-v2.0.5 -m "Known good production release"
git push origin payment-api-v2.0.5
```

### 4. Keep Application manifests in Git

Do not create important Argo CD Applications only through UI. Store them declaratively.

### 5. Review Argo CD diff before manual sync

```bash
argocd app diff <app>
```

### 6. Use sync waves for dependency order

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
```

Common ordering:

```text
Namespace      wave -3
RBAC/SCC       wave -2
Secrets        wave -1
ConfigMaps     wave -1
Deployments    wave  0
Services       wave  1
Routes         wave  2
Jobs/tests     wave  3
```

### 7. Use hooks for validation

PreSync hooks can block bad deployment. PostSync hooks can run smoke tests.

### 8. Be careful with prune

Prune is powerful but can delete resources. Use confirmation for critical resources.

### 9. Do not store plain secrets in Git

Use approved secret encryption or external secret tooling.

### 10. Separate app GitOps from cluster-config GitOps

A common enterprise pattern:

```text
app-gitops-repo            app Deployments, Services, Routes
cluster-config-gitops-repo RBAC, SCC, Operators, Quotas, NetworkPolicies
```

This reduces blast radius.

### 11. Keep rollback simple

During an incident, rollback should be:

```text
Known bad commit → known good commit → sync → validate
```

Avoid complicated manual patch chains.

## 32. Interview / Exam-Oriented Notes

### What is rollback using Git history?

It is the process of restoring the Git desired state to a previous working commit, tag, branch, or pull-request state and letting Argo CD reconcile the OpenShift cluster to that state.

### Why not use `oc rollout undo`?

Because `oc rollout undo` changes the live cluster only. If Git still contains the bad desired state, Argo CD can reapply it. In GitOps, the permanent fix must be in Git.

### What is the safest production rollback?

Usually:

```bash
git revert <bad_commit>
git push
argocd app sync <app>
argocd app wait <app> --sync --health
```

### What does Argo CD history rollback do?

It rolls an Application back to a previous deployed history ID. It can restore service quickly, but it should be followed by a Git revert so the source of truth is corrected.

### What happens with automated sync?

If automated sync is enabled, a Git revert can be applied automatically. If the bad Git revision still exists on the tracked branch, Argo CD may reapply it after an emergency rollback.

### What should be checked after rollback?

Check:

```text
Argo CD sync status
Argo CD health status
Deployment rollout
Pods readiness
Service endpoints
Route health
Logs
Events
NetworkPolicy/RBAC/SCC if relevant
```

## Final Admin Summary

For production OpenShift GitOps, the correct rollback mindset is:

```text
Do not fight Argo CD.
Do not patch random live resources and forget Git.
Rollback Git first, then let Argo CD reconcile.
```

A clean production rollback usually looks like this:

```bash
git revert <bad_commit_sha>
git push origin <tracked_branch>
argocd app get <app> --refresh
argocd app diff <app>
argocd app sync <app>
argocd app wait <app> --sync --health --timeout 300
oc rollout status deploy/<deployment> -n <namespace>
```

Emergency Argo CD rollback is useful, but it is not the final GitOps correction unless Git is also fixed.
