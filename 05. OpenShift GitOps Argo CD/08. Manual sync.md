# Manual Sync in OpenShift GitOps Argo CD

**Audience:** Advanced OpenShift Administration / OpenShift GitOps / Argo CD administrators with around 10 years of Linux, Kubernetes, OpenShift, DevOps, or platform operations experience.

**Focus topic:** Manual Sync in Red Hat OpenShift GitOps Argo CD.

---

## 1. What is Manual Sync?

In OpenShift GitOps, **manual sync** means Argo CD continuously observes and compares the desired state from Git with the live state in the OpenShift cluster, but it **does not automatically apply changes** until an authorized user explicitly triggers a sync operation.

In simple words:

```text
Git has desired YAML/Helm/Kustomize manifests
        ↓
Argo CD detects difference
        ↓
Application becomes OutOfSync
        ↓
Administrator reviews diff
        ↓
Administrator manually clicks Sync or runs argocd app sync
        ↓
Argo CD applies desired state to OpenShift
```

Manual sync is the controlled deployment model. It is useful when production changes require human approval, change windows, CAB approval, audit checks, security review, or staged rollout control.

---

## 2. Manual Sync vs Automated Sync

| Feature | Manual Sync | Automated Sync |
|---|---|---|
| Git change detection | Yes | Yes |
| Application becomes `OutOfSync` | Yes | Yes |
| Argo CD applies changes automatically | No | Yes |
| Human approval before deployment | Yes | Usually no |
| Best for | Production, regulated environments, sensitive cluster configuration | Dev, test, fast-moving environments |
| Drift correction | Only when manually synced, unless auto-sync/self-heal is enabled | Can be automatic with `selfHeal` |
| Risk of accidental Git change affecting production immediately | Lower | Higher |

Manual sync does **not** mean Argo CD is inactive. Argo CD still reconciles, compares, displays drift, calculates health, and shows diff. Only the apply/prune operation waits for user action.

---

## 3. Why Manual Sync Matters for Advanced OpenShift Administration

For a senior OpenShift administrator, manual sync is not just a button. It is a release-control mechanism.

Manual sync helps when:

- Production deployments must happen only during approved maintenance windows.
- Platform configuration changes require review before applying to the cluster.
- Cluster-scoped resources such as `ClusterRole`, `SecurityContextConstraints`, `OAuth`, `MachineConfig`, `Namespace`, or Operators must not change automatically.
- Application teams use GitOps, but platform admins need controlled promotion from dev to test to production.
- You want to review Argo CD diff before applying potentially destructive changes.
- Pruning deleted resources must be reviewed before Argo CD removes live objects.
- You are troubleshooting and want to separate **comparison** from **deployment**.

For production OpenShift GitOps, manual sync is commonly used with:

- Git pull request approval
- Image tag promotion
- ApplicationSet-generated apps
- Argo CD RBAC
- Sync windows
- Progressive delivery tools
- OpenShift change management
- Cluster configuration repositories

## 4. Argo CD Reconciliation Mental Model

Argo CD works as a Kubernetes controller. It continuously compares:

```text
Desired state = rendered manifests from Git / Helm / Kustomize / Jsonnet / plugin
Live state    = actual Kubernetes/OpenShift objects in the cluster
```

Based on this comparison, an Argo CD Application gets two important statuses:

```text
Sync Status   → Does live state match Git desired state?
Health Status → Are the live resources operational/healthy?
```

Examples:

| Sync Status | Health Status | Meaning |
|---|---|---|
| `Synced` | `Healthy` | Desired state is applied and resources look healthy |
| `OutOfSync` | `Healthy` | Cluster is running, but Git and live state differ |
| `Synced` | `Degraded` | Desired manifests are applied, but workload is unhealthy |
| `OutOfSync` | `Degraded` | Git/live differ and app is unhealthy |
| `Unknown` | `Unknown` | Argo CD cannot compare or determine state |

Manual sync mainly acts on the **Sync Status**. It does not guarantee the application will become healthy. A sync can succeed while the application later becomes `Progressing` or `Degraded` because of image pull errors, readiness probe failures, PVC issues, SCC restrictions, or OpenShift scheduling problems.

## 5. Manual Sync Application CR Example

A basic manually synced Argo CD `Application` normally does **not** define `spec.syncPolicy.automated`.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api
  namespace: openshift-gitops
spec:
  project: default

  source:
    repoURL: https://git.example.com/platform/payment-api-gitops.git
    targetRevision: main
    path: overlays/prod

  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod

  syncPolicy:
    syncOptions:
      - CreateNamespace=false
```

This application behaves as follows:

1. Argo CD watches the Git repository.
2. Argo CD renders the manifests from `overlays/prod`.
3. Argo CD compares the rendered manifests with live resources in `payment-prod`.
4. If Git changes, the application becomes `OutOfSync`.
5. Nothing is applied until a user manually syncs.

## 6. Explicitly Disabling Automated Sync

In newer Argo CD / OpenShift GitOps versions, an Application can contain an `automated` block but still have automated sync explicitly disabled by using `enabled: false`.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api
  namespace: openshift-gitops
spec:
  project: default

  source:
    repoURL: https://git.example.com/platform/payment-api-gitops.git
    targetRevision: main
    path: overlays/prod

  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod

  syncPolicy:
    automated:
      enabled: false
      prune: true
      selfHeal: true
    syncOptions:
      - PruneLast=true
```

Important point:

```text
syncPolicy.automated.enabled: false
```

means auto-sync is disabled even if `prune` and `selfHeal` fields are present. This is useful when you want to preserve sync-policy intent but temporarily force manual promotion.

Operationally, this pattern is useful during:

- Production freeze periods
- Release hold
- Incident response
- Maintenance windows
- Compliance review
- Manual cutover

## 7. OpenShift GitOps Namespace Management Requirement

In the default Red Hat OpenShift GitOps installation, the default Argo CD instance usually runs in:

```text
openshift-gitops
```

When this instance manages workloads in another namespace, the target namespace often needs the managed-by label:

```bash
oc label namespace payment-prod argocd.argoproj.io/managed-by=openshift-gitops
```

Without correct namespace permissions, sync can fail with RBAC errors such as:

```text
permission denied
namespaces "payment-prod" is forbidden
applications.argoproj.io is not allowed to manage namespace
```

For advanced administration, always verify:

```bash
oc get ns payment-prod --show-labels
oc get rolebinding -n payment-prod | grep openshift-gitops
oc get application payment-api -n openshift-gitops -o yaml
```

## 11. What Happens Internally During Manual Sync?

A manual sync operation roughly follows this flow:

```text
User triggers sync
        ↓
Argo CD validates requested revision and options
        ↓
Repo server renders manifests from Git/Helm/Kustomize
        ↓
Application controller compares desired vs live state
        ↓
Sync plan is built
        ↓
Resources are ordered by phase, wave, kind, and dependency
        ↓
PreSync hooks run, if configured
        ↓
Normal resources are applied
        ↓
PostSync hooks run, if configured
        ↓
Prune happens if enabled/requested
        ↓
Health is evaluated
        ↓
Operation history is updated
```

Important components:

| Component | Role in manual sync |
|---|---|
| `argocd-server` | Receives UI/API/CLI sync request |
| `argocd-application-controller` | Executes comparison and sync operation |
| `argocd-repo-server` | Renders manifests from Git/Helm/Kustomize |
| Kubernetes/OpenShift API server | Accepts object create/update/delete operations |
| Redis | Caches app state and operation data in many Argo CD deployments |

## 12. Manual Sync and Git Revisions

By default, manual sync applies the desired state from the Application's configured `targetRevision`.

Examples:

```yaml
source:
  targetRevision: main
```

or:

```yaml
source:
  targetRevision: v1.2.3
```

or:

```yaml
source:
  targetRevision: 7a3e8d3c9a1b2f
```

For production, pinning to a Git tag or commit SHA gives stronger release control:

```yaml
source:
  targetRevision: release-2026-07-03
```

CLI sync to a specific revision:

```bash
argocd app sync payment-api --revision release-2026-07-03
```

This is useful when:

- `main` has moved ahead but production should deploy a specific approved commit.
- You need rollback-like behavior by syncing to an older Git tag.
- You want deterministic deployment during a release window.

## 14. Diff Review Before Manual Sync

Before syncing production, always review diff.

CLI:

```bash
argocd app diff payment-api
```

Common diff examples:

```diff
- replicas: 3
+ replicas: 5
```

```diff
- image: registry.example.com/payment-api:v1.4.0
```

```diff
+ kind: NetworkPolicy

+   name: allow-api-to-db
```

```diff

-   name: old-payment-route
```

For a 10-year-experience admin, the diff is where you catch dangerous production mistakes:

- Namespace deletion
- Route hostname change
- Service selector change
- PVC storage class change
- Deployment selector immutability issue
- SCC or ServiceAccount change
- ResourceQuota reduction
- NetworkPolicy blocking traffic
- Secret reference change
- Ingress/Route TLS change
- Operator Subscription channel change
- CRD or API version change

## 15. Manual Sync with Prune

By default, sync applies desired resources. **Prune** means Argo CD deletes live resources that were previously managed but are no longer present in Git.

Manual sync with prune:

```bash
argocd app sync payment-api --prune
```

Prune is powerful and dangerous.

Example:

```text
Git removed route/payment-api-old
Manual sync with prune deletes route/payment-api-old from OpenShift
```

Use prune carefully for:

- Namespaces
- PVCs
- Routes
- Services used by external systems
- NetworkPolicies
- RBAC objects
- Operator CRs
- CRDs
- Cluster-scoped resources

Application-level sync option:

```yaml
spec:
  syncPolicy:
    syncOptions:
      - PruneLast=true
```

Resource-level option to prevent pruning:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

Resource-level option to require explicit prune confirmation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

This is highly recommended for critical resources such as Namespaces or shared infrastructure resources.

---

## 16. Manual Sync Without Prune

Manual sync without prune applies changes but leaves extra live resources untouched.

```bash
argocd app sync payment-api
```

If a resource exists in the cluster but no longer exists in Git, the app can remain `OutOfSync` because Argo CD sees a live object that should be pruned.

This is common when:

- A manifest was deleted from Git.
- Helm chart stopped rendering a resource.
- Kustomize overlay removed a patch/resource.
- A resource was renamed.

To investigate:

```bash
argocd app get payment-api
argocd app diff payment-api
```

## 17. Dry Run Before Manual Sync

Dry run helps validate what Argo CD would apply.

```bash
argocd app sync payment-api --dry-run
```

Use dry run before production sync to catch:

- Invalid API versions
- Missing CRDs
- Schema validation errors
- Immutable field changes
- RBAC denial
- Resource quota problems
- Admission webhook rejection

Dry run is not a replacement for a real staging test, but it is a useful safety check.

## 18. Manual Sync Only Out-of-Sync Resources

For very large applications, applying every resource can be slow and can put pressure on the OpenShift API server.

CLI:

```bash
argocd app sync payment-api --apply-out-of-sync-only
```

Application sync option:

```yaml
spec:
  syncPolicy:
    syncOptions:
      - ApplyOutOfSyncOnly=true
```

Use this for:

- Large app-of-apps patterns
- Large Helm charts
- Platform repositories with many resources
- Reducing API server load

Be careful with hooks and partial/selective sync behavior. Do not assume every hook or validation job will run in every partial-sync scenario.

## 19. Manual Sync of a Specific Resource

Sometimes you do not want to sync the whole application.

Example: sync only a Deployment:

```bash
argocd app sync payment-api --resource apps:Deployment:payment-api
```

Example: sync only a Service:

```bash
argocd app sync payment-api --resource :Service:payment-api
```

Example: sync namespaced resource if same resource name appears in multiple namespaces:

```bash
argocd app sync payment-api --resource apps:Deployment:payment-prod/payment-api
```

Advanced use cases:

- Fix only one failed object.
- Apply CRD before applying CRs.
- Sync only a Route after a certificate update.
- Sync only ConfigMap/Secret after configuration change.
- Avoid restarting workloads during partial maintenance.

Warning:

```text
Selective resource sync can bypass the normal full-application deployment logic.
Use it carefully in production.
```

## 20. Manual Sync and Sync Waves

Argo CD can order resources using sync waves.

Example:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

Lower wave numbers apply first.

Example deployment order:

```text
Wave -1: Namespace, RBAC, ServiceAccount
Wave  0: ConfigMap, Secret, Service
Wave  1: Deployment, StatefulSet
Wave  2: Route, Ingress, HPA
Wave  3: Post-deployment Job
```

Example:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-api
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/sync-wave: "1"
```

Why this matters in OpenShift:

- Namespace must exist before namespaced resources.
- ServiceAccount should exist before Deployment references it.
- SCC/RBAC should exist before pods are created.
- CRD should exist before CR instances.
- Operator Subscription should be ready before custom resources are applied.

## 21. Manual Sync and Hooks

Argo CD supports resource hooks around sync operations.

Common hook phases:

| Hook | Purpose |
|---|---|
| `PreSync` | Run before normal sync resources |
| `Sync` | Run as part of sync |
| `PostSync` | Run after sync completes and resources are healthy |
| `SyncFail` | Run when sync fails |
| `PostDelete` | Run after app deletion resources are deleted |

Example PreSync migration Job:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  generateName: db-migration-
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migration
          image: registry.example.com/payment-migration:v1.5.0
          command: ["/bin/sh", "-c"]
          args:
            - ./migrate.sh
```

Manual sync with hooks gives controlled release gates:

```text
Admin clicks Sync
        ↓
PreSync migration runs
        ↓
If migration succeeds, Deployment updates
        ↓
PostSync smoke test runs
        ↓
Application becomes Synced/Healthy
```

Important production note:

```text
A failed PreSync hook can block deployment.
A failed PostSync hook can mark the operation failed even if workloads were applied.
```

## 22. Manual Sync with Helm Applications

Example Application using Helm:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-prod
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://charts.bitnami.com/bitnami
    chart: nginx
    targetRevision: 15.14.0
    helm:
      releaseName: nginx-prod
      values: |
        replicaCount: 3
        service:
          type: ClusterIP
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-prod
```

Manual sync considerations for Helm:

- Argo CD renders Helm templates; it does not run `helm install` in the same way as a human CLI workflow.
- Helm hooks and Argo CD hooks are not the same operational model.
- `values.yaml` changes cause rendered manifest changes.
- Chart version changes can introduce CRD, API, or immutable field issues.
- Always review diff before chart upgrades.

Useful commands:

```bash
argocd app diff nginx-prod
argocd app sync nginx-prod --dry-run
argocd app sync nginx-prod
```

- ResourceQuotas
- LimitRanges

- Operator Subscriptions
- OperatorGroups
- OpenShift Routes

## 25. OpenShift-Specific Risks During Manual Sync

### 25.1 SCC / Pod Security Errors

Error example:

```text
pods "payment-api" is forbidden: violates PodSecurity "restricted"
```

or:

```text
unable to validate against any security context constraint
```

Check:

```bash
oc adm policy who-can use scc anyuid
oc get sa -n payment-prod
oc describe pod <pod> -n payment-prod
```

Fix through Git, not live cluster, where possible:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payment-api-anyuid
  namespace: payment-prod
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:openshift:scc:anyuid
subjects:
  - kind: ServiceAccount
    name: payment-api
    namespace: payment-prod
```

### 25.2 Route and TLS Issues

Route changes can break external traffic.

Check before sync:

```bash
argocd app diff payment-api | grep -i route -A20
```

Verify after sync:

```bash
oc get route -n payment-prod
curl -vk https://payment.apps.ocp4.example.com
```

### 25.3 NetworkPolicy Blocking Traffic

A manual sync can successfully apply a NetworkPolicy and still break traffic.

Check:

```bash
oc get networkpolicy -n payment-prod
oc describe networkpolicy -n payment-prod
oc get pods -n payment-prod --show-labels
```

Validate source and destination labels carefully.

### 25.4 ResourceQuota and LimitRange Failures

Sync can fail if resource requests exceed quota.

Check:

```bash
oc describe quota -n payment-prod
oc describe limitrange -n payment-prod
oc get events -n payment-prod --sort-by=.lastTimestamp
```

### 25.5 PVC and Storage Problems

Sync can apply a StatefulSet successfully, but pods remain pending due to PVC or storage class issues.

Check:

```bash
oc get pvc -n payment-prod
oc describe pvc <pvc-name> -n payment-prod
oc get sc
oc describe pod <pod-name> -n payment-prod
```

## 26. Manual Sync RBAC Control

In production, not every user should be able to sync every app.

Typical policy:

| Role | Permission |
|---|---|
| Developer | View app, view diff, maybe sync dev |
| Team lead | Sync test/stage |
| Platform admin | Sync prod and cluster config |
| Security admin | Approve/sync security-sensitive apps |
| Read-only auditor | View history and diffs only |

Example Argo CD RBAC concept:

```csv
p, role:prod-syncer, applications, get, prod/*, allow
p, role:prod-syncer, applications, sync, prod/*, allow
p, role:prod-syncer, applications, action/*, prod/*, allow
g, rakesh, role:prod-syncer
```

OpenShift-side RBAC must also allow Argo CD service accounts to apply resources in target namespaces.

## 27. Manual Sync and Sync Windows

Sync windows can restrict when sync is allowed.

Use cases:

- Allow production sync only during maintenance windows.
- Deny sync during business hours.
- Allow emergency override only to admins.

Example behavior:

```text
Application is OutOfSync
Admin clicks Sync
Argo CD says sync is blocked by sync window
Admin waits for allowed window or uses authorized override
```

Sync windows are useful with manual sync because they enforce operational discipline even when a user has sync permission.

## 28. Manual Sync with App-of-Apps Pattern

In app-of-apps, a parent Application manages child Applications.

Example:

```text
bootstrap-root-app
├── namespace-config-app
├── monitoring-app
├── logging-app
├── payment-api-app
└── frontend-app
```

Manual sync strategies:

### Strategy 1: Manual sync parent only

```bash
argocd app sync bootstrap-root-app
```

This creates/updates child Applications. Child apps may still require their own manual sync depending on their sync policy.

### Strategy 2: Manual sync each child

```bash
argocd app sync namespace-config-app
argocd app sync monitoring-app
argocd app sync payment-api-app
```

This provides better production control.

### Strategy 3: Label-based sync

```bash
argocd app sync -l environment=prod
```

Use with caution. Label-based sync can impact many apps at once.

## 29. Manual Sync with ApplicationSet

ApplicationSet generates Argo CD Applications from templates.

Important distinction:

```text
ApplicationSet controller manages Application objects.
Argo CD Application controller syncs resources created by each Application.
```

Manual sync is configured on generated Applications, usually inside the ApplicationSet template.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-apps
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - name: payment-api
            namespace: payment-prod
          - name: order-api
            namespace: order-prod
  template:
    metadata:
      name: '{{name}}'
    spec:
      project: default
      source:
        repoURL: https://git.example.com/platform/apps.git
        targetRevision: main
        path: '{{name}}/overlays/prod'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{namespace}}'
      syncPolicy:
        syncOptions:
          - CreateNamespace=false
```

No `automated` block means generated apps are manually synced.

## 30. Manual Sync and Multi-Source Applications

Argo CD supports Applications with multiple sources. Example:

- Helm chart from chart repo
- Values from Git repo
- Extra manifests from Git repo

Manual sync can target revisions for specific sources using CLI options.

Conceptual example:

```bash
argocd app sync my-app \
  --revisions 1.2.3 --source-positions 1 \
  --revisions main  --source-positions 2
```

Use case:

```text
Deploy chart version 1.2.3 with production values from Git main.
```

Advanced advice:

- Pin chart versions.
- Pin values repo revisions for production.
- Review rendered diff carefully.
- Avoid mixing unreviewed chart upgrades with application config changes.

## 31. Manual Sync Rollback Strategy

Argo CD rollback is not the same as `oc rollout undo`.

GitOps rollback best practice:

1. Revert Git commit or update Git target revision.
2. Review diff.
3. Manually sync.
4. Verify health.

Example:

```bash
git revert <bad_commit>
git push
argocd app diff payment-api
argocd app sync payment-api
argocd app wait payment-api --health --timeout 300
```

Emergency rollback to previous Git tag:

```bash
argocd app sync payment-api --revision release-2026-07-02
```

However, after emergency sync to older revision, update Git/release process properly so the Application does not drift from intended source control state.

## 32. Manual Sync Failure Scenarios and Fixes

### 32.1 Another Operation Is Already in Progress

Error:

```text
another operation is already in progress
```

Check:

```bash
argocd app get payment-api
```

Terminate stuck operation carefully:

```bash
argocd app terminate-op payment-api
```

Then resync:

```bash
argocd app sync payment-api
```

### 32.2 Manifest Generation Error

Error:

```text
Manifest generation error
```

Possible causes:

- Helm values syntax error
- Kustomize patch failure
- Missing file path
- Invalid chart version
- Repo authentication failure
- Plugin failure

Check:

```bash
argocd app get payment-api
argocd app manifests payment-api
oc logs -n openshift-gitops deploy/openshift-gitops-repo-server
```

### 32.3 Missing CRD

Error:

```text
no matches for kind "Example" in version "example.com/v1"
```

Fix options:

- Install CRD before CR.
- Put CRD in lower sync wave.
- Sync CRD first.
- Use `SkipDryRunOnMissingResource=true` only when appropriate.

Example:

```yaml
spec:
  syncPolicy:
    syncOptions:
      - SkipDryRunOnMissingResource=true
```

### 32.4 Immutable Field Change

Error:

```text
field is immutable
```

Common examples:

- Deployment selector change
- Service clusterIP change
- PVC storage class or requested field issue
- StatefulSet volumeClaimTemplates change

Fix:

- Revert immutable field change in Git, or
- Plan resource recreation with downtime/change approval, or
- Use controlled prune/delete and recreate strategy.

### 32.5 Permission Denied

Error:

```text
forbidden: User "system:serviceaccount:openshift-gitops:..." cannot create resource
```

Check:

```bash
oc auth can-i create deployment \
  --as system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payment-prod
```

Check namespace label:

```bash
oc get ns payment-prod --show-labels
```

### 32.6 App Remains OutOfSync After Successful Sync

Possible causes:

- Mutating admission webhook changes live object.
- OpenShift adds default fields.
- HPA changes replica count.
- Controller changes status/spec fields.
- Helm chart generates nondeterministic data.
- Secret or certificate controller rotates data.
- Prune required but not enabled.

Investigate:

```bash
argocd app diff payment-api
argocd app get payment-api
```

Possible solution: configure ignore differences only for expected controller-managed fields.

## 36. Manual Sync Interview / Exam Style Questions

### Q1. If an Application is manual sync and Git changes, what happens?

The Application becomes `OutOfSync`. Argo CD shows the diff, but it does not apply changes until a user manually triggers sync.

### Q2. Does manual sync disable Argo CD reconciliation?

No. Argo CD still reconciles for comparison and status. It only avoids automatic apply/prune.

### Q3. Can manual sync prune resources?

Yes, if prune is selected during manual sync or configured/requested as a sync option. Without prune, extra live resources can keep the app `OutOfSync`.

### Q4. Why can an app be `Synced` but `Degraded`?

Because sync status only means desired manifests match live manifests. Health depends on runtime conditions like pod readiness, image pulls, PVC binding, probes, and controller status.

### Q5. What is the safest production workflow?

```text
Pull request → approval → merge/tag → argocd diff → dry-run → manual sync → health wait → route/service validation → monitoring check
```

### Q6. What should you check if manual sync fails with forbidden errors?

Check Argo CD service account RBAC, target namespace managed-by label, AppProject destination/resource permissions, and OpenShift namespace rolebindings.

### Q7. Why does the app remain OutOfSync after sync?

Common reasons include missing prune, controller-mutated fields, admission webhook changes, HPA replica changes, generated secrets/certs, or nondeterministic rendered manifests.

## 37. Advanced Best Practices

1. Use manual sync for production and cluster-scoped configuration.
2. Always review diff before syncing.
3. Use Git tags or commit SHAs for production releases.
4. Avoid syncing directly from a fast-moving branch for critical workloads.
5. Use `Prune=confirm` for critical resources.
6. Use sync waves for namespaces, RBAC, CRDs, operators, and workloads.
7. Keep Application definitions in Git as well.
8. Restrict sync permissions using Argo CD RBAC.
9. Use sync windows for production change control.
10. Prefer fixing Git over editing live resources.
11. Document rollback revision before sync.
12. Watch OpenShift events during sync.
13. Treat `Synced` and `Healthy` as different signals.
14. Avoid large unreviewed Helm chart upgrades.
15. Use `ApplyOutOfSyncOnly=true` carefully for large apps.
16. Avoid pruning PVCs or Namespaces without explicit approval.
17. Validate NetworkPolicy changes before syncing.
18. Check SCC and pod security impact for OpenShift workloads.
19. Use staging clusters to test rendered manifests first.
20. Keep Argo CD, OpenShift GitOps Operator, and CRDs version-aligned.

## 39. Final Mental Model

Manual sync is the GitOps equivalent of a controlled deployment approval gate.

```text
Git is still the source of truth.
Argo CD still detects drift.
Argo CD still shows diff.
But humans decide when desired state is applied.
```

For advanced OpenShift administration, manual sync is especially important for production, platform configuration, multi-tenant clusters, security-sensitive resources, and enterprise change-control environments.

A strong administrator does not simply click **Sync**. A strong administrator checks:

```text
What changed?
Who approved it?
Which cluster is targeted?
Which namespace is affected?
Will anything be pruned?
Will network/security/storage behavior change?
Can we roll back from Git?
Did the application become both Synced and Healthy?
```

That is the real operational discipline behind Manual Sync in OpenShift GitOps Argo CD.
