## 1. What GitOps for NetworkPolicy Means

**GitOps for NetworkPolicy** means that pod network access rules are not created manually with `oc create` or `oc edit` as a long-term practice. Instead, the desired network security state is stored as YAML in Git, reviewed through pull requests, synchronized by Argo CD, and continuously reconciled into OpenShift.

In simple words:

```text
Git repository = desired network security policy
Argo CD        = reconciler / enforcer of declared YAML
OpenShift API  = receives NetworkPolicy objects
OVN-Kubernetes = enforces allowed pod traffic
```

A senior OpenShift administrator should treat `NetworkPolicy` the same way as RBAC, SCC usage, namespaces, quotas, routes, and deployment manifests: **as code**.

Manual command:

```bash
oc apply -f networkpolicy.yaml -n production
```

GitOps method:

```text
1. Developer/platform engineer opens a PR.
2. Team reviews the proposed traffic rule.
3. PR is merged into main or release branch.
4. Argo CD detects Git change.
5. Argo CD applies NetworkPolicy to the OpenShift namespace.
6. Argo CD reports Synced / OutOfSync / Degraded.
7. Any manual cluster drift is reverted when self-heal is enabled.
```

---

## 2. Why NetworkPolicy Should Be Managed by GitOps

Network policy is security-sensitive. A single wrong selector can either block production traffic or expose a database to workloads that should not reach it.

GitOps gives these advantages:

| Requirement | Manual NetworkPolicy | GitOps NetworkPolicy |
|---|---|---|
| Audit trail | Weak, depends on audit logs | Strong, every change is in Git history |
| Review process | Often missing | Pull request / merge request review |
| Rollback | Manual and error-prone | Revert commit |
| Multi-cluster consistency | Difficult | Same base, environment overlays |
| Drift detection | Manual comparison | Argo CD OutOfSync status |
| Security approval | Informal | Code owners / branch protection |
| Disaster recovery | Recreate manually | Re-sync from Git |

In enterprise OpenShift, GitOps for NetworkPolicy is important for:

- multi-tenant cluster isolation,
- PCI / banking / government workloads,
- zero-trust pod communication,
- controlled egress,
- blue/green or canary environments,
- standard namespace onboarding,
- audit and compliance evidence.

## 3. Mental Model: Git to Argo CD to OpenShift SDN/OVN Enforcement

A `NetworkPolicy` object does not directly block traffic by itself. It is an API object. The actual traffic enforcement is done by the OpenShift networking plugin, commonly OVN-Kubernetes in modern OpenShift.

Flow:

```text
Developer / Platform Admin
        |
        v
Git commit containing NetworkPolicy YAML
        |
        v
Argo CD repo-server renders manifests
        |
        v
Argo CD application-controller compares Git vs live state
        |
        v
Argo CD applies NetworkPolicy through Kubernetes API
        |
        v
OpenShift stores object in etcd
        |
        v
OVN-Kubernetes programs network rules
        |
        v
Pod traffic is allowed only if matching policy allows it
```

Important senior-level point:

**Argo CD does not enforce network traffic. Argo CD enforces Kubernetes objects. The CNI plugin enforces traffic behavior.**

So troubleshooting must follow both planes:

1. **GitOps plane:** Is the correct YAML synced?
2. **Kubernetes API plane:** Does the correct `NetworkPolicy` exist in the right namespace?
3. **Label/selector plane:** Do namespace and pod labels match?
4. **Network dataplane:** Is traffic actually allowed or denied?

## 4. NetworkPolicy Fundamentals You Must Know

### 4.1 NetworkPolicy is namespace-scoped

A `NetworkPolicy` is created inside one namespace/project and selects pods in that same namespace using `spec.podSelector`.

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: backend
```

This policy is in the `backend` namespace and applies only to pods in `backend` matching `app=backend`.

It does **not** apply to frontend pods in another namespace. It controls traffic **to or from selected backend pods**, depending on `policyTypes`.

---

### 4.2 Default behavior: pods are open until isolated

By default, if no NetworkPolicy selects a pod for ingress, that pod accepts ingress traffic. If no NetworkPolicy selects a pod for egress, that pod can send egress traffic.

Once a pod is selected by at least one NetworkPolicy for ingress, only explicitly allowed ingress is accepted.

Once a pod is selected by at least one NetworkPolicy for egress, only explicitly allowed egress is accepted.

---

### 4.3 NetworkPolicy is allow-list based, not deny-list based

Kubernetes `NetworkPolicy` does not define explicit deny rules like a traditional firewall ACL.

You do not write:

```yaml
- deny from app=bad-client
```

Instead, you design isolation like this:

```text
1. Deny everything by selecting pods with no allowed rules.
2. Add small allow policies for required traffic.
```

Example default deny ingress:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

This selects all pods in the namespace and allows no ingress traffic.

---

### 4.4 Policies are additive

If multiple policies select the same pod, allowed traffic is the union of all matching policies.

Example:

```text
Policy A allows frontend -> backend on TCP/8080
Policy B allows monitoring -> backend on TCP/9090
Final result: backend allows both traffic paths
```

This is a common source of confusion. Adding a second policy usually **opens additional allowed traffic**; it does not override the first policy.

---

### 4.5 `podSelector: {}` means all pods in that policy namespace

Example:

```yaml
spec:
  podSelector: {}
```

This selects every pod in the namespace where the NetworkPolicy exists.

Use this for namespace-level defaults:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

---

### 4.6 `namespaceSelector` selects namespaces by label

Example:

```yaml
from:
- namespaceSelector:
    matchLabels:
      environment: prod
```

This allows traffic from namespaces labeled `environment=prod`.

You must ensure the namespace label exists:

```bash
oc label namespace frontend environment=prod
```

For GitOps, namespace labels should also be declared in Git, not added manually.

---

### 4.7 `namespaceSelector` and `podSelector`: AND vs OR behavior

This is one of the most important exam and production troubleshooting topics.

#### AND condition: same list item

```yaml
ingress:
- from:
  - namespaceSelector:
      matchLabels:
        team: payments
    podSelector:
      matchLabels:
        app: api
```

Meaning:

```text
Allow pods with app=api from namespaces with team=payments
```

Both namespace and pod labels must match.

#### OR condition: separate list items

```yaml
ingress:
- from:
  - namespaceSelector:
      matchLabels:
        team: payments
  - podSelector:
      matchLabels:
        app: api
```

Meaning:

```text
Allow all pods from namespaces with team=payments
OR
Allow pods with app=api from the same namespace as the NetworkPolicy
```

This difference causes many real incidents.

---

### 4.8 `policyTypes`

Use `policyTypes` to declare whether the policy controls ingress, egress, or both.

```yaml
policyTypes:
- Ingress
- Egress
```

If you only define ingress rules, do not assume egress is restricted. Egress remains allowed unless a policy selects the pod for egress.

---

### 4.9 Egress default deny blocks DNS unless allowed

If you apply default deny egress, applications may fail with errors like:

```text
Temporary failure in name resolution
Name or service not known
Could not resolve host
```

Because DNS traffic to CoreDNS / OpenShift DNS is also egress traffic.

A typical DNS allow policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

Validate namespace labels in your cluster:

```bash
oc get ns openshift-dns --show-labels
```

## 5. OpenShift-Specific NetworkPolicy Considerations

### 5.1 Project equals namespace

In OpenShift, a project is a Kubernetes namespace with OpenShift project metadata and RBAC behavior.

These commands point to the same namespace object:

```bash
oc get project payments
oc get namespace payments
```

A NetworkPolicy created in project `payments` is a NetworkPolicy in namespace `payments`.

---

### 5.2 OpenShift router / ingress traffic

If you apply default deny ingress to an application namespace, external Route traffic may stop reaching pods unless traffic from the OpenShift router namespace is allowed.

OpenShift documentation recommends the following namespace selector label for OVN-Kubernetes ingress/router traffic:

```yaml
policy-group.network.openshift.io/ingress: ""
```

Policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/ingress: ""
```

Use this when the namespace hosts workloads exposed by OpenShift Routes.

---

### 5.3 OpenShift monitoring traffic

If Prometheus or monitoring components scrape application pods, default deny ingress can block scraping.

Typical allow policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-monitoring
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          network.openshift.io/policy-group: monitoring
```

Restrict ports if your standards require it:

```yaml
ports:
- protocol: TCP
  port: 9090
```

---

### 5.4 Do not manually label OpenShift system namespaces with reserved labels

Do not add reserved OpenShift networking labels to your own namespaces to bypass policy.

Bad idea:

```bash
oc label ns my-app policy-group.network.openshift.io/ingress=""
```

That label is intended for OpenShift-managed networking namespaces. Treat it as platform-owned.

---

### 5.5 NetworkPolicy cannot solve every network security problem

NetworkPolicy is useful, but it is not a complete firewall replacement.

It does not normally handle:

- L7 HTTP path rules,
- user identity authorization,
- TLS certificate validation,
- API authentication,
- external firewall policy,
- service mesh authorization,
- node-local traffic in every case,
- application-level security.

Use it with:

- OpenShift Routes / ingress policy,
- service mesh authorization policies if applicable,
- RBAC,
- SCC / PSA controls,
- egress firewall / egress IP / firewall appliances,
- audit logging,
- image security.

## 6. Prerequisites for GitOps-Controlled NetworkPolicy

### 6.1 OpenShift GitOps Operator installed

Check:

```bash
oc get operators
oc get pods -n openshift-gitops
oc get argocd -A
```

Default Argo CD namespace:

```text
openshift-gitops
```

Default Argo CD instance normally runs in:

```text
openshift-gitops
```

---

### 6.2 Destination namespace must be manageable by Argo CD

For the default OpenShift GitOps instance, label the destination namespace:

```bash
oc label namespace payments argocd.argoproj.io/managed-by=openshift-gitops
```

In GitOps, prefer managing this label declaratively as part of namespace bootstrap.

Example namespace manifest:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
    team: payments
    environment: prod
```

---

### 6.3 Argo CD service account must have permission

The Argo CD application controller must be able to create/update/delete `NetworkPolicy` in the target namespace.

Check:

```bash
oc auth can-i create networkpolicy \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments

oc auth can-i update networkpolicy \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments

oc auth can-i delete networkpolicy \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments
```

If using a user-defined Argo CD instance, service account names differ. Check:

```bash
oc get sa -n <argocd-namespace>
```

---

### 6.4 Network plugin must support NetworkPolicy

Check cluster network type:

```bash
oc get network.operator cluster -o yaml
```

Look for fields such as:

```yaml
spec:
  defaultNetwork:
    type: OVNKubernetes
```

---

### 6.5 Labels must be stable and Git-managed

NetworkPolicy depends heavily on labels. If labels are manually changed, policies break.

Manage these labels in Git:

- namespace labels,
- deployment pod template labels,
- service selectors,
- policy selectors.

Bad pattern:

```bash
oc label pod backend-abc123 app=backend
```

Good pattern:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
        tier: backend
```

## 7. Recommended Git Repository Structure

For a senior platform team, keep network policy separate enough to review, but close enough to the application to understand traffic requirements.

### 7.1 App-owned policy model

Application team owns its own policies.

```text
platform-gitops/
├── apps/
│   └── payments/
│       ├── base/
│       │   ├── deployment-frontend.yaml
│       │   ├── deployment-backend.yaml
│       │   ├── service-backend.yaml
│       │   ├── networkpolicy-default-deny.yaml
│       │   ├── networkpolicy-allow-frontend-to-backend.yaml
│       │   └── kustomization.yaml
│       └── overlays/
│           ├── dev/
│           │   ├── kustomization.yaml
│           │   └── networkpolicy-extra-debug.yaml
│           ├── stage/
│           │   └── kustomization.yaml
│           └── prod/
│               ├── kustomization.yaml
│               └── networkpolicy-egress-restricted.yaml
└── argocd/
    └── applications/
        └── payments-prod.yaml
```

Best when teams are mature and security has PR review ownership.

---

### 7.2 Platform-owned baseline policy model

Platform team owns namespace baseline policies.

```text
cluster-config/
├── namespaces/
│   └── payments.yaml
├── network-policies/
│   ├── base/
│   │   ├── default-deny-ingress.yaml
│   │   ├── allow-from-openshift-ingress.yaml
│   │   ├── allow-from-openshift-monitoring.yaml
│   │   ├── allow-same-namespace.yaml
│   │   └── kustomization.yaml
│   └── overlays/
│       ├── dev/
│       ├── stage/
│       └── prod/
└── argocd/
    ├── projects/
    └── applications/
```

Best for regulated clusters where platform/security controls base isolation.

---

### 7.3 Hybrid model

Recommended for most enterprises:

```text
1. Platform repo owns baseline deny/allow policies.
2. Application repo owns application-specific allow rules.
3. Security team reviews both through CODEOWNERS.
```

Example:

```text
cluster-baseline repo:
- default deny ingress
- allow router
- allow monitoring
- allow DNS
- namespace labels

application repo:
- allow frontend to backend
- allow backend to database
- allow backend egress to external API
```

This allows pods in the same namespace to talk to each other.

## 9. Complete GitOps Example: Frontend to Backend to Database

### 9.1 Requirement

Design policies for this architecture:

```text
frontend namespace:
  frontend pods expose HTTP route

backend namespace:
  backend pods accept traffic only from frontend pods on TCP/8080

database namespace:
  mysql pods accept traffic only from backend pods on TCP/3306
```

Required isolation:

```text
frontend -> backend: allowed TCP/8080
backend -> database: allowed TCP/3306
frontend -> database: denied
random namespace -> backend: denied
random namespace -> database: denied
OpenShift router -> frontend: allowed
monitoring -> all namespaces: allowed where needed
```

---

### 9.2 Namespace manifests

`namespaces/frontend.yaml`

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: frontend
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
    team: payments
    layer: frontend
    environment: prod
```

`namespaces/backend.yaml`

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: backend
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
    team: payments
    layer: backend
    environment: prod
```

`namespaces/database.yaml`

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: database
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
    team: payments
    layer: database
    environment: prod
```

---

### 9.3 Frontend baseline policies

`network-policies/frontend/default-deny-ingress.yaml`

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: frontend
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

`network-policies/frontend/allow-from-openshift-ingress.yaml`

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
  namespace: frontend
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/ingress: ""
    ports:
    - protocol: TCP
      port: 8080
```

If your frontend container listens on port `8080`, allow `8080`. If it listens on `8443`, allow `8443`. Match the target pod port, not necessarily the Route port.

---

### 9.4 Backend baseline and allow frontend policy

`network-policies/backend/default-deny-ingress.yaml`

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: backend
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

`network-policies/backend/allow-frontend-to-backend.yaml`

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          layer: frontend
      podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
```

Meaning:

```text
Allow traffic to backend pods labeled app=backend
from pods labeled app=frontend
inside namespaces labeled layer=frontend
on TCP/8080 only.
```

Because `namespaceSelector` and `podSelector` are in the same list item, both conditions must match.

---

### 9.5 Database baseline and allow backend policy

`network-policies/database/default-deny-ingress.yaml`

```yaml
apiVersion: networking.k8s.io/v1

metadata:
  name: default-deny-ingress
  namespace: database
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

`network-policies/database/allow-backend-to-mysql.yaml`

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-backend-to-mysql
  namespace: database
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:

```

This is a classic EX280-style / real-world pattern:

```text
Target namespace: database
Target pod: app=mysql
Allowed source namespace: layer=backend
Allowed source pod: app=backend
Allowed port: 3306/TCP
```

```yaml
  project: payments-networking
  source:
    repoURL: https://git.example.com/platform/openshift-gitops.git
    targetRevision: main
    path: network-policies/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: backend
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
    - CreateNamespace=false
    - PruneLast=true
    - ApplyOutOfSyncOnly=true
```

Important notes:

1. `destination.namespace` is required by Argo CD, but each `NetworkPolicy` can include its own `metadata.namespace`.
2. If policies span many namespaces, ensure the AppProject allows those destination namespaces.
3. `CreateNamespace=false` is safer if namespaces are managed separately by a namespace bootstrap application.
4. `PruneLast=true` helps avoid deleting old policies before new policies are applied in some rollout patterns.
5. `ApplyOutOfSyncOnly=true` reduces unnecessary apply operations in large policy repositories.

## 11. AppProject Design for Safer NetworkPolicy GitOps

Do not allow every Argo CD application to deploy everything everywhere.

Create an AppProject that only allows the required source repository, destination namespaces, and resource kinds.

`argocd/projects/payments-networking.yaml`

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-networking
  namespace: openshift-gitops
spec:
  description: Allows GitOps management of payments NetworkPolicy objects only

  sourceRepos:
  - https://git.example.com/platform/openshift-gitops.git

  destinations:
  - server: https://kubernetes.default.svc
    namespace: frontend
  - server: https://kubernetes.default.svc
    namespace: backend
  - server: https://kubernetes.default.svc
    namespace: database

  clusterResourceWhitelist: []

  namespaceResourceWhitelist:
  - group: networking.k8s.io
    kind: NetworkPolicy
```

This limits blast radius.

Bad AppProject design:

```yaml
sourceRepos:
- '*'
destinations:
- namespace: '*'
  server: '*'
clusterResourceWhitelist:
- group: '*'
  kind: '*'
```

That pattern is dangerous for security-sensitive GitOps.

## 12. Sync Policy, Prune, Self-Heal, and Drift Detection

### 12.1 Automated sync

Automated sync means Argo CD applies Git changes without a human clicking `Sync`.

```yaml
syncPolicy:
  automated: {}
```

For NetworkPolicy, automated sync is useful when:

- policies are reviewed by PR,
- lower environments need fast updates,
- baseline policy must be consistently enforced.

For production, combine it with branch protection and security review.

---

### 12.2 Self-heal

Self-heal tells Argo CD to correct live cluster drift.

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

Example drift:

```bash
oc delete networkpolicy default-deny-ingress -n database
```

With self-heal enabled, Argo CD recreates it from Git.

This is excellent for security because manual weakening of policies does not persist.

---

### 12.3 Prune

Prune means Argo CD deletes resources that were previously managed but no longer exist in Git.

```yaml
syncPolicy:
  automated:
    prune: true
```

Example:

```text
Old Git file: allow-debug-client.yaml
File deleted from Git
Argo CD with prune: deletes allow-debug-client NetworkPolicy from the cluster
```

Security benefit:

```text
Temporary exception policies do not remain forever after removal from Git.
```

Risk:

```text
Wrong branch/path or bad Kustomize overlay can delete valid policies.
```

Production recommendation:

```yaml
syncOptions:
- PruneLast=true
```

For extremely sensitive policies, consider manual production sync or PR gates before pruning.

---

### 12.4 Drift detection example

Live cluster changed:

```bash
oc patch networkpolicy allow-backend-to-mysql -n database --type=json \
  -p='[{"op":"replace","path":"/spec/ingress/0/ports/0/port","value":3307}]'
```

Argo CD status becomes:

```text
OutOfSync
```

With self-heal:

```text
Argo CD restores port 3306 from Git.
```

Check:

```bash
argocd app get payments-networkpolicy-prod
oc get networkpolicy allow-backend-to-mysql -n database -o yaml
```

## 13. Sync Waves for Namespaces, Labels, and Policies

NetworkPolicy depends on namespaces and labels. In GitOps, apply order matters.

Recommended order:

```text
Wave -20: Namespaces
Wave -10: Namespace labels / RBAC / quotas
Wave   0: Deployments / Services
Wave  10: NetworkPolicy baseline
Wave  20: Application-specific allow policies
Wave  30: Smoke test Job
```

Example namespace:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: backend
  annotations:
    argocd.argoproj.io/sync-wave: "-20"
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
    layer: backend
```

Example NetworkPolicy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: backend
  annotations:
    argocd.argoproj.io/sync-wave: "20"
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          layer: frontend
      podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
```

Senior-level warning:

Do not use sync waves as a replacement for correct dependencies and labels. They help ordering, but they do not fix wrong selectors.

## 15. Helm Strategy for Reusable NetworkPolicy Templates

Helm is useful when many applications need the same policy shape with different labels and ports.

Example chart values:

`values.yaml`

```yaml
networkPolicy:
  enabled: true
  defaultDenyIngress: true
  allowOpenShiftIngress: true
  appLabel: backend
  allowedSources:
    - namespaceLabels:
        layer: frontend
      podLabels:
        app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

Template:

`templates/networkpolicy-allow-sources.yaml`

```yaml
{{- if .Values.networkPolicy.enabled }}
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-to-{{ .Values.networkPolicy.appLabel }}
spec:
  podSelector:
    matchLabels:
      app: {{ .Values.networkPolicy.appLabel | quote }}
  policyTypes:
  - Ingress
  ingress:
{{- range .Values.networkPolicy.allowedSources }}
  - from:
    - namespaceSelector:
        matchLabels:
{{ toYaml .namespaceLabels | indent 10 }}
      podSelector:
        matchLabels:
{{ toYaml .podLabels | indent 10 }}
    ports:
{{ toYaml .ports | indent 4 }}
{{- end }}
{{- end }}
```

Senior recommendation:

Use Helm for repeatable policy generation, but keep rendered YAML simple and reviewable. Over-templated security logic becomes hard to audit.

## 17. Troubleshooting NetworkPolicy with Argo CD

### 17.1 Argo CD says Synced but traffic still fails

Possible causes:

1. YAML is applied, but labels do not match.
2. Policy is in wrong namespace.
3. Wrong port is allowed.
4. Service target port differs from container port.
5. Egress is blocked from source namespace.
6. DNS egress is blocked.
7. Application is not listening.
8. Route traffic is blocked because router namespace is not allowed.
9. NetworkPolicy plugin behavior or cluster network issue.

Commands:

```bash
oc get netpol -n <namespace>
oc describe netpol <policy> -n <namespace>
oc get pods -n <namespace> --show-labels
oc get ns --show-labels
oc get svc -n <namespace> -o wide
oc get endpoints -n <namespace>
oc logs <pod> -n <namespace>
```

---

### 17.2 Argo CD says OutOfSync

Check diff:

```bash
argocd app diff payments-networkpolicy-prod
```

Check live object:

```bash
oc get networkpolicy -n backend allow-frontend-to-backend -o yaml
```

Common reasons:

- manual `oc edit`,
- generated labels/annotations,
- Kustomize overlay mismatch,
- deleted file but prune disabled,
- Application path points to wrong directory,
- AppProject does not allow resource.

---

### 17.3 Argo CD sync fails with permission error

Error example:

```text
networkpolicies.networking.k8s.io is forbidden
```

Check permissions:

```bash
oc auth can-i create networkpolicy \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n backend
```

Fix by granting namespace-level rights or using the correct Argo CD instance/AppProject model.

Example role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: networkpolicy-manager
  namespace: backend
rules:
- apiGroups: ["networking.k8s.io"]
  resources: ["networkpolicies"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
```

RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: argocd-networkpolicy-manager
  namespace: backend
subjects:
- kind: ServiceAccount
  name: openshift-gitops-argocd-application-controller
  namespace: openshift-gitops
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: networkpolicy-manager
```

---

### 17.4 Route stopped working after default deny

Check router allow policy:

```bash
oc get netpol allow-from-openshift-ingress -n frontend -o yaml
```

Check route and service:

```bash
oc get route -n frontend
oc get svc -n frontend
oc get endpoints -n frontend
```

Ensure policy allows traffic to the pod target port.

---

### 17.5 Database still reachable from unauthorized namespace

Check these issues:

1. Is default deny ingress present in database namespace?
2. Does another additive policy allow broader traffic?
3. Does `allow-same-namespace` accidentally allow a test pod inside database namespace?
4. Are namespace labels too broad?
5. Are `namespaceSelector` and `podSelector` accidentally separated into OR rules?

Commands:

```bash
oc get netpol -n database
oc describe netpol -n database
oc get ns --show-labels | grep -E 'backend|frontend|database|random'
oc get pods -A --show-labels | grep mysql
```

## 18. Production Rollout Strategy

NetworkPolicy rollout should be staged. Do not blindly apply default deny to production namespaces without observing traffic.

### Phase 1: Inventory

Collect current communication paths:

```bash
oc get svc,endpoints,route -A
oc get pods -A --show-labels
```

Use available observability tools:

- Network Observability Operator,
- flow logs,
- application logs,
- service mesh telemetry if present,
- Prometheus metrics,
- firewall logs.

---

### Phase 2: Add labels

Make sure all namespaces and deployments have stable labels.

```yaml
metadata:
  labels:
    team: payments
    environment: prod
    layer: backend
```

---

### Phase 3: Add allow policies before default deny

Apply intended allow policies first.

Example:

```text
allow-from-openshift-ingress
allow-from-openshift-monitoring
allow-frontend-to-backend
allow-backend-to-database
allow-dns-egress
```

---

### Phase 4: Apply default deny in lower environment

Test in dev/stage:

```text
default-deny-ingress
optional default-deny-egress
```

---

### Phase 5: Production rollout with monitoring

Recommended production controls:

- PR approval from platform + application owner,
- short deployment window,
- Argo CD manual sync for first rollout,
- health checks after sync,
- quick rollback by reverting commit,
- alert monitoring.

---

### Phase 6: Enable self-heal and prune

After confidence:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

## 20. Common Mistakes

### Mistake 1: Policy created in source namespace instead of destination namespace

Wrong:

```yaml
metadata:
  namespace: frontend
spec:
  podSelector:
    matchLabels:
      app: mysql
```

If MySQL is in `database`, this does nothing for MySQL.

Correct:

```yaml
metadata:
  namespace: database
spec:
  podSelector:
    matchLabels:
      app: mysql
```

---

### Mistake 2: Missing default deny

An allow policy without a matching isolation/default-deny policy may not restrict anything.

If no policy selects a pod for ingress, it remains open.

---

### Mistake 3: Wrong labels

Policy expects:

```yaml
podSelector:
  matchLabels:
    app: mysql
```

Pod has:

```text
deployment=mysql
```

Result: policy does not select the pod.

Check:

```bash
oc get pods -n database --show-labels
```

---

### Mistake 4: Confusing service port and pod port

NetworkPolicy ports refer to pod traffic ports. If a service exposes port `80` but forwards to targetPort `8080`, usually allow `8080` at the pod level.

Check:

```bash
oc get svc backend -n backend -o yaml
oc get pod <backend-pod> -n backend -o yaml | grep -A5 ports
```

---

### Mistake 5: Blocking DNS with default deny egress

Symptom:

```text
curl: Could not resolve host
```

Fix: allow DNS egress to OpenShift DNS.

---

### Mistake 6: Breaking Route traffic

Symptom:

```text
Route exists, service has endpoints, but external access times out
```

Fix: allow OpenShift ingress/router namespace traffic.

---

### Mistake 7: Dangerous broad namespace selector

Dangerous in prod:

```yaml
from:
- namespaceSelector: {}
```

This allows from all namespaces.

Better:

```yaml
from:
- namespaceSelector:
    matchLabels:
      team: payments
      environment: prod
```

---

### Mistake 8: AppProject too permissive

Avoid allowing application teams to deploy arbitrary cluster-scoped resources or all namespaces unless intentionally required.

## 21. Advanced Enterprise Patterns

### 21.1 App-of-apps for network security

Root application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: network-security-root
  namespace: openshift-gitops
spec:
  project: platform
  source:
    repoURL: https://git.example.com/platform/cluster-config.git

  destination:
    server: https://kubernetes.default.svc

      selfHeal: true
```

Child applications:

```text
payments-networkpolicy-prod
hr-networkpolicy-prod
crm-networkpolicy-prod
shared-services-networkpolicy-prod
```

This scales better than one giant Argo CD app.

---

### 21.2 Separate baseline and app traffic policies

```text
baseline-networkpolicy-prod:
  default deny
  allow router
  allow monitoring
  allow dns

payments-app-networkpolicy-prod:
  frontend to backend
  backend to database
  backend to external API
```

This separation gives platform teams control over global standards while app teams own application-specific flows.

---

### 21.3 Progressive tightening

Start with:

```text
allow same namespace
allow router
allow monitoring
```

Then add:

```text
specific cross-namespace allow rules
```

Then apply:

```text
default deny ingress
```

Then, if mature:

```text
default deny egress + explicit DNS/API/database egress
```

---

### 21.4 Multi-cluster policy promotion

Use branches or directories:

```text
overlays/dev
overlays/stage
overlays/prod
```

Promotion flow:

```text
Merge to dev branch -> Argo CD dev sync
Promote to stage -> Argo CD stage sync
Promote to prod -> Argo CD prod sync
```

Avoid direct untested policy changes to production.

---

### 21.5 Temporary access with automated cleanup

Create temporary exception file:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: temporary-allow-debug-client
  namespace: database
  annotations:
    security.example.com/expires-on: "2026-07-10"

  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          purpose: debug
    ports:
    - protocol: TCP
      port: 3306
```

After the change window, remove the file from Git. Argo CD prune deletes it from the cluster.

### Scenario 1: Allow checker namespace to access MySQL

Requirement:

```text
Namespace: database
Target pod label: deployment=web-mysql
Source namespace label: team=devsecops
Source pod label: deployment=checker
Port: 3306/TCP
Policy name: mysql-db-conn
```

Manifest:

```yaml

  name: mysql-db-conn
  namespace: database
spec:
  podSelector:
    matchLabels:
      deployment: web-mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:

        matchLabels:
          deployment: checker

```

Validation:

```bash
oc get ns checker --show-labels
oc get pods -n checker --show-labels
oc get pods -n database --show-labels
oc describe netpol mysql-db-conn -n database
```

---

### Scenario 2: Argo CD synced, but MySQL still reachable from frontend

Likely causes:

- no default deny ingress in database namespace,
- another policy allows frontend broadly,
- frontend pod is in namespace labeled `team=devsecops`,
- frontend pod label accidentally matches `deployment=checker`,
- testing from a pod inside database namespace and same-namespace allow exists.

Commands:

```bash
oc get netpol -n database
oc describe netpol -n database
oc get ns --show-labels
oc get pods -A --show-labels | grep -E 'frontend|checker|mysql'
```

---

### Scenario 3: Route returns timeout after GitOps sync

Likely cause:

```text
default-deny-ingress applied but no allow-from-openshift-ingress policy
```

Fix:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/ingress: ""
```

---

### Scenario 4: DNS stopped working after egress lockdown

Likely cause:

```text
default-deny-egress without allow-dns-egress
```

Fix:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

## Final Senior Admin Summary

For advanced OpenShift administration, GitOps for NetworkPolicy means:

```text
Do not treat network security as a one-time oc command.
Treat it as reviewed, versioned, reconciled, and continuously enforced platform code.
```

A production-grade design should include:

- namespace labels managed in Git,
- stable pod labels managed in Deployments,
- default deny baseline policies,
- explicit allow policies,
- OpenShift router and monitoring exceptions where required,
- DNS egress handling when using egress lockdown,
- AppProject restrictions,
- PR approval from platform/security teams,
- Argo CD self-heal for drift correction,
- careful prune strategy,
- lower-environment testing before production rollout.

The key troubleshooting rule:

```text
When NetworkPolicy does not behave as expected, check namespace, labels, selectors, ports, egress, and additive policies before blaming Argo CD.
```
