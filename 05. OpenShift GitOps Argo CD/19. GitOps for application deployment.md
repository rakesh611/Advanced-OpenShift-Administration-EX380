## 1. What “GitOps for application deployment” means

**GitOps for application deployment** means that the desired state of an application is stored in Git, and Argo CD continuously compares that desired state with the live state running in OpenShift. When a difference is detected, Argo CD reports the application as `OutOfSync`. Depending on the sync policy, Argo CD can either wait for an administrator to approve the deployment or automatically reconcile the cluster back to the Git-defined state.

In an OpenShift environment, GitOps application deployment usually manages resources such as:

- `Namespace` or `Project`
- `Deployment` / `DeploymentConfig` / `StatefulSet`
- `Service`
- `Route`
- `ConfigMap`
- `Secret` references or encrypted secret objects
- `ServiceAccount`
- `Role`, `RoleBinding`
- `NetworkPolicy`
- `ResourceQuota`
- `LimitRange`
- `HorizontalPodAutoscaler`
- `PodDisruptionBudget`
- `PersistentVolumeClaim`
- OpenShift-specific security settings such as SCC-related service account binding, where appropriate

The key point is this:

> In GitOps, Git is the deployment control plane. The cluster is not the source of truth. The cluster is only the runtime state.

For a senior OpenShift administrator, this changes the operational model. You no longer ask, “Who changed the deployment in the cluster?” You ask, “Which Git commit changed the desired state, who approved it, and did Argo CD reconcile it correctly?”

## 2. Traditional deployment vs GitOps deployment

### Traditional deployment model

In a traditional OpenShift deployment model, a CI/CD pipeline often performs direct cluster actions:

```bash
oc login https://api.ocp4.example.com:6443
oc project payment-prod
oc set image deployment/payment-api payment-api=registry.example.com/payment-api:v1.2.3
oc rollout status deployment/payment-api
```

This works, but it creates several operational issues:

- The pipeline needs powerful credentials against the cluster.
- Deployment history may live in Jenkins, GitLab CI, or another CI tool instead of Git.
- Manual `oc edit` changes can drift away from the intended configuration.
- Production state can become difficult to reproduce.
- Rollback depends on pipeline logic or manual OpenShift commands.

### GitOps deployment model

In GitOps, the CI system usually builds and pushes an image, then updates a Git repository that contains deployment manifests:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  template:
    spec:
      containers:
        - name: payment-api
          image: registry.example.com/payment-api:v1.2.3
```

Argo CD watches the Git repository and applies the change into OpenShift.

The CI system does **not** need cluster-admin access. It only needs permission to update Git, usually through a pull request or controlled automation.

### Practical comparison

| Area | Traditional CI/CD | GitOps with Argo CD |
|---|---|---|
| Source of truth | Pipeline/job history or cluster | Git repository |
| Deployment trigger | Pipeline runs `oc`/`kubectl` | Git commit changes desired state |
| Cluster credentials | Often held by CI tool | Held by Argo CD controller |
| Drift detection | Usually manual | Built in |
| Rollback | Pipeline/manual command | Revert Git commit or sync previous revision |
| Audit | Spread across tools | Git commit, PR, Argo CD events |
| Security model | CI can mutate cluster | CI only changes Git |

## 3. OpenShift GitOps and Argo CD architecture

Red Hat OpenShift GitOps packages Argo CD for OpenShift through an Operator. In a default installation, the main Argo CD instance is commonly installed in the `openshift-gitops` namespace.

Important components include:

### 3.1 Argo CD API server

The API server exposes the Argo CD UI and API. Administrators and developers use it to:

- View applications
- Trigger syncs
- Compare Git and live state
- View resource tree
- Review sync history
- Configure repositories and clusters

In OpenShift, this is exposed through a `Route`, for example:

```bash
oc get route openshift-gitops-server -n openshift-gitops
```

### 3.2 Application controller

The application controller is the main reconciliation engine. It watches Argo CD `Application` resources and compares:

- Desired state from Git
- Live state from OpenShift

Then it determines whether the application is:

- `Synced`
- `OutOfSync`
- `Healthy`
- `Progressing`
- `Degraded`
- `Missing`
- `Unknown`

If automatic sync is enabled, the controller can apply changes without manual intervention.

### 3.3 Repository server

The repository server fetches and renders manifests from Git repositories. It supports common manifest sources such as:

- Plain YAML
- Kustomize
- Helm
- Jsonnet
- Config management plugins

For example, when an `Application` points to a Kustomize overlay, the repo server runs the render operation and gives the final manifests to the controller.

### 3.4 Redis

Redis is used by Argo CD for caching and performance. In large environments, this becomes important for UI responsiveness, manifest cache, and controller performance.

### 3.5 Dex / SSO integration

Argo CD can integrate with identity providers. In OpenShift GitOps, administrators commonly integrate authentication with OpenShift OAuth, LDAP, OIDC, or enterprise SSO.

### 3.6 OpenShift GitOps Operator

The Operator manages Argo CD lifecycle. It deploys, upgrades, and reconciles the Argo CD instance. As a senior admin, avoid manually editing generated deployments unless documentation specifically requires it. Prefer changing the `ArgoCD` custom resource.

Example:

```bash
oc get argocd -A
oc edit argocd openshift-gitops -n openshift-gitops
```

## 4. Core GitOps objects used for application deployment

### 4.1 Application

The `Application` CR is the most important object for deployment. It defines:

- Source repository
- Revision or branch
- Path/chart
- Destination cluster
- Destination namespace
- Sync policy
- Sync options
- Project boundary

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-dev
  namespace: openshift-gitops
spec:
  project: payment-team
  source:
    repoURL: https://git.example.com/platform/payment-gitops.git
    targetRevision: main
    path: apps/payment-api/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

### 4.2 AppProject

`AppProject` is the guardrail. It controls what an application is allowed to deploy, from where, and to which cluster/namespace.

It can restrict:

- Allowed Git repositories
- Allowed destination clusters
- Allowed destination namespaces
- Allowed cluster-scoped resources
- Allowed namespace-scoped resources
- Denied resource kinds
- Roles and policies for Argo CD RBAC

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payment-team
  namespace: openshift-gitops
spec:
  description: Payment team application deployment boundary
  sourceRepos:
    - https://git.example.com/platform/payment-gitops.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payment-dev
    - server: https://kubernetes.default.svc
      namespace: payment-qa
    - server: https://kubernetes.default.svc
      namespace: payment-prod
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
    - group: route.openshift.io
      kind: Route
    - group: ''
      kind: ConfigMap
    - group: networking.k8s.io
      kind: NetworkPolicy
```

### 4.3 Repository configuration

Argo CD must know how to access private Git repositories.

Example using HTTPS token:

```bash
argocd repo add https://git.example.com/platform/payment-gitops.git \
  --username gitops-bot \
  --password '<TOKEN>'
```

Example using Kubernetes secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: payment-gitops-repo
  namespace: openshift-gitops
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  type: git
  url: https://git.example.com/platform/payment-gitops.git
  username: gitops-bot
  password: <token>
```

### 4.4 Cluster secret

For multi-cluster deployment, Argo CD stores cluster access information as secrets. In a single-cluster OpenShift deployment, most applications target:

```yaml
server: https://kubernetes.default.svc
```

This means the same OpenShift cluster where Argo CD is running.

## 5. End-to-end deployment flow

A practical GitOps application deployment flow looks like this:

```text
Developer pushes application code
        |
        v
CI pipeline builds container image
        |
        v
CI pipeline pushes image to registry
        |
        v
CI updates GitOps repository image tag / Helm values / Kustomize patch
        |
        v
Pull request review and merge
        |
        v
Argo CD detects Git change
        |
        v
Argo CD renders manifests
        |
        v
Argo CD compares desired vs live state
        |
        v
Argo CD syncs application to OpenShift
        |
        v
OpenShift deploys pods, services, routes, config, policies
        |
        v
Argo CD reports Synced + Healthy, or OutOfSync/Degraded
```

The CI tool builds the artifact. Argo CD deploys the desired state.

A senior admin rule:

> CI should build. Git should approve. Argo CD should deploy. OpenShift should run.

## 6. Recommended Git repository structures

Repository structure is one of the biggest design decisions in GitOps.

### 6.1 Single application repository with deployment manifests

```text
payment-api/
├── src/
├── Dockerfile
├── manifests/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── route.yaml
└── .gitlab-ci.yml
```

This is simple but not always ideal for production because application developers and platform admins modify the same repository.

### 6.2 Separate application code repository and GitOps repository

```text
payment-api-code/
├── src/
├── Dockerfile
└── pipeline.yaml

payment-gitops/
└── apps/
    └── payment-api/
        ├── base/
        │   ├── deployment.yaml
        │   ├── service.yaml
        │   ├── route.yaml
        │   └── kustomization.yaml
        └── overlays/
            ├── dev/
            │   ├── kustomization.yaml
            │   └── patch-replicas.yaml
            ├── qa/
            │   ├── kustomization.yaml
            │   └── patch-replicas.yaml
            └── prod/
                ├── kustomization.yaml
                ├── patch-replicas.yaml
                └── patch-resources.yaml
```

This is a common production pattern.

Advantages:

- Developers own application code.
- Platform/admin team controls deployment standards.
- Pull requests can enforce review gates.
- Environment promotion becomes clean.
- Audit trail is separate from code commits.

### 6.3 Environment-centric repository

```text
cluster-gitops/
├── clusters/
│   ├── dev/
│   │   └── applications/
│   ├── qa/
│   │   └── applications/
│   └── prod/
│       └── applications/
└── apps/
    ├── payment-api/
    └── inventory-api/
```

This is useful when platform teams manage many applications across many clusters.

### 6.4 App-of-apps structure

```text
gitops-root/
├── bootstrap/
│   └── root-application.yaml
├── applications/
│   ├── payment-api-dev.yaml
│   ├── inventory-api-dev.yaml
│   └── frontend-dev.yaml
└── apps/
    ├── payment-api/
    ├── inventory-api/
    └── frontend/
```

The root application deploys other Argo CD applications. This is called the **app-of-apps** pattern.

Useful for:

- Cluster bootstrap
- Managing many applications from one root
- Standardizing application registration

Risk:

- A bad root sync can affect many applications.
- Strong review and branch protection are mandatory.

### 6.5 Mono-repo vs multi-repo

| Design | Good for | Risk |
|---|---|---|
| Mono-repo | Central governance, platform-owned config | Repository becomes huge |
| Multi-repo | Team independence | Governance becomes harder |
| App repo contains manifests | Small/simple teams | App code and deployment concerns mix |
| Separate GitOps repo | Production-grade environments | Requires additional workflow discipline |

For enterprise OpenShift, prefer a separate GitOps repository for production deployment state.

## 7. Application deployment using plain YAML

Plain YAML is the simplest GitOps source type.

Example directory:

```text
apps/hello-openshift/plain/
├── namespace.yaml
├── deployment.yaml
├── service.yaml
└── route.yaml
```

### 7.1 Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: hello-dev
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

### 7.2 Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  namespace: hello-dev
  labels:
    app: hello
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: hello
          image: registry.ocp4.example.com:8443/redhattraining/hello-world-nginx:v1.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 256Mi
          readinessProbe:
            httpGet:
              path: /
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 20
```

### 7.3 Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hello
  namespace: hello-dev
spec:
  selector:
    app: hello
  ports:
    - name: http
      port: 8080
      targetPort: 8080
```

### 7.4 Route

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: hello
  namespace: hello-dev
spec:
  to:
    kind: Service
    name: hello
  port:
    targetPort: http
```

### 7.5 Argo CD Application for plain YAML

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: hello-dev
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/hello-gitops.git
    targetRevision: main
    path: apps/hello-openshift/plain
  destination:
    server: https://kubernetes.default.svc
    namespace: hello-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Plain YAML is good for learning and simple workloads. For multiple environments, Kustomize or Helm is usually better.

## 8. Application deployment using Kustomize

Kustomize is very common for OpenShift GitOps because it supports base-plus-overlay patterns without requiring a template language.

### 8.1 Directory structure

```text
apps/payment-api/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── route.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml
    │   └── patch.yaml
    ├── qa/
    │   ├── kustomization.yaml
    │   └── patch.yaml
    └── prod/
        ├── kustomization.yaml
        ├── patch.yaml
        └── resource-patch.yaml
```

### 8.2 Base deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  labels:
    app: payment-api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
        - name: payment-api
          image: registry.example.com/payment-api:latest
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
```

### 8.3 Base kustomization

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
  - route.yaml
commonLabels:
  app.kubernetes.io/name: payment-api
  app.kubernetes.io/managed-by: argocd
```

### 8.4 Dev overlay

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payment-dev
resources:
  - ../../base
images:
  - name: registry.example.com/payment-api
    newTag: v1.2.3-dev
patches:
  - path: patch.yaml
```

`patch.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 1
```

### 8.5 Prod overlay

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payment-prod
resources:
  - ../../base
images:
  - name: registry.example.com/payment-api
    newTag: v1.2.3
patches:
  - path: patch.yaml
  - path: resource-patch.yaml
```

`patch.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 4
```

`resource-patch.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  template:
    spec:
      containers:
        - name: payment-api
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
            limits:
              cpu: 2
              memory: 2Gi
```

### 8.6 Argo CD Application for Kustomize overlay

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
spec:
  project: payment-team
  source:
    repoURL: https://git.example.com/platform/payment-gitops.git
    targetRevision: main
    path: apps/payment-api/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Kustomize is excellent when you want environment differences to be visible and version-controlled without heavy templating.

## 9. Application deployment using Helm

Helm is useful when:

- The application already ships as a chart.
- You need reusable parameterized templates.
- Many teams deploy the same app with different values.
- You deploy common middleware or third-party applications.

### 9.1 Helm source example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: etherpad-dev
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: http://helm.ocp4.example.com/charts
    chart: etherpad
    targetRevision: 0.0.4
    helm:
      releaseName: etherpad
      values: |
        replicaCount: 1
        route:
          enabled: true
        persistence:
          enabled: true
          size: 1Gi
  destination:
    server: https://kubernetes.default.svc
    namespace: etherpad-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

### 9.2 Helm values per environment

A common GitOps pattern:

```text
apps/etherpad/
├── Chart.yaml
├── templates/
└── values/
    ├── dev.yaml
    ├── qa.yaml
    └── prod.yaml
```

Application pointing to chart plus values:

```yaml
source:
  repoURL: https://git.example.com/platform/charts.git
  targetRevision: main
  path: apps/etherpad
  helm:
    valueFiles:
      - values/prod.yaml
```

### 9.3 Helm operational cautions

For production OpenShift:

- Avoid random template generation that changes every sync.
- Do not generate secrets with random values inside Helm unless lifecycle is understood.
- Be careful with hooks that create Jobs every sync.
- Pin chart versions.
- Store environment values in Git.
- Validate rendered output using `helm template` or Argo CD diff.

## 10. Creating an Argo CD Application for OpenShift

You can create an application using:

- Argo CD UI
- `oc apply -f application.yaml`
- `argocd app create`
- GitOps bootstrap pattern

For advanced administration, declarative `Application` manifests are preferred.

### 10.1 Application manifest anatomy

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: backend-prod
  namespace: openshift-gitops
  labels:
    app.kubernetes.io/part-of: backend
    environment: prod
spec:
  project: backend-team
  source:
    repoURL: https://git.example.com/backend/backend-gitops.git
    targetRevision: main
    path: apps/backend/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: backend-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      allowEmpty: false
    syncOptions:
      - CreateNamespace=true
      - PrunePropagationPolicy=foreground
      - PruneLast=true
  revisionHistoryLimit: 10
```

### 10.2 Important fields

| Field | Meaning |
|---|---|
| `metadata.name` | Name of the Argo CD Application |
| `metadata.namespace` | Namespace where Application CR is stored, commonly `openshift-gitops` |
| `spec.project` | AppProject boundary |
| `spec.source.repoURL` | Git/Helm repository |
| `spec.source.targetRevision` | Branch, tag, or commit |
| `spec.source.path` | Directory path for YAML/Kustomize/Helm chart |
| `spec.destination.server` | Target Kubernetes API server |
| `spec.destination.namespace` | Target namespace/project |
| `spec.syncPolicy` | Manual or automatic sync behavior |
| `spec.revisionHistoryLimit` | Argo CD application revision history |

### 10.3 Apply the Application

```bash
oc apply -f application-backend-prod.yaml
```

Check status:

```bash
oc get application backend-prod -n openshift-gitops
argocd app get backend-prod
```

Sync manually:

```bash
argocd app sync backend-prod
```

Wait for health:

```bash
argocd app wait backend-prod --health --sync --timeout 300
```

## 11. Application deployment with automatic sync

Automatic sync allows Argo CD to apply Git changes when it detects that the desired state differs from live state.

Example:

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
    - CreateNamespace=true
```

### 11.1 `automated` behavior

When enabled, Argo CD can deploy automatically after a Git change.

This is useful for:

- Dev environments
- QA environments
- Low-risk internal services
- Platform bootstrap resources
- Environments with strong PR approval controls

### 11.2 `prune: true`

If a resource is removed from Git, Argo CD deletes it from the cluster.

Example:

```yaml
syncPolicy:
  automated:
    prune: true
```

Use carefully in production. Accidentally deleting a YAML file from Git can remove live resources.

### 11.3 `selfHeal: true`

If someone changes the live object directly in OpenShift, Argo CD reverts it back to Git.

Example:

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

This prevents configuration drift.

### 11.4 `allowEmpty: false`

This protects against accidentally syncing an empty directory and pruning everything.

```yaml
syncPolicy:
  automated:
    allowEmpty: false
```

For production, keep `allowEmpty: false` unless you have a specific controlled reason.

### 11.5 Practical production recommendation

For production:

- Use automatic sync only with branch protection and mandatory review.
- Enable `selfHeal` for drift control.
- Enable `prune` only after deletion workflow is mature.
- Use `Prune=confirm` for critical resources such as namespaces or persistent resources.
- Consider manual sync for high-risk production applications.

## 12. Application deployment with manual sync

Manual sync means Argo CD detects drift but does not apply changes until a user or pipeline triggers sync.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
spec:
  project: payment-team
  source:
    repoURL: https://git.example.com/platform/payment-gitops.git
    targetRevision: main
    path: apps/payment-api/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod
```

No `syncPolicy.automated` means manual sync.

Manual sync is useful for:

- Production environments
- Regulated environments
- Change windows
- Applications with database migration risk
- Applications that require operator approval

Manual sync command:

```bash
argocd app sync payment-api-prod
```

Sync specific resources:

```bash
argocd app sync payment-api-prod \
  --resource apps:Deployment:payment-api
```

Preview diff:

```bash
argocd app diff payment-api-prod
```

## 13. Self-healing and application drift correction

Application drift happens when live cluster state differs from Git.

Examples:

```bash
oc scale deployment payment-api --replicas=10 -n payment-prod
oc edit route payment-api -n payment-prod
oc patch deployment payment-api -n payment-prod --type merge -p '{"spec":{"replicas":1}}'
```

If Git says replicas should be `4`, and someone changes replicas to `10` in the cluster, Argo CD detects drift.

With self-heal enabled:

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

Argo CD reverts live state to Git.

### 13.1 Why self-healing matters

Self-healing is important because it:

- Enforces Git as source of truth
- Prevents configuration snowflakes
- Improves auditability
- Reduces manual troubleshooting
- Makes cluster recovery easier

### 13.2 When self-healing can surprise you

Self-healing can fight against tools that intentionally modify live state.

Examples:

- HPA changes `spec.replicas`
- Operators mutate fields
- Admission controllers inject fields
- Service mesh sidecar injection changes pod templates
- OpenShift defaulting adds fields

For HPA-managed deployments, avoid treating `spec.replicas` as a strict field if HPA controls it. You can use Argo CD ignore differences where appropriate.

Example:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

Use this carefully. Ignoring too many fields weakens drift detection.

## 14. Prune behavior during application deployment

Prune means deleting resources that exist in the cluster but no longer exist in Git for that application.

### 14.1 Example

Initial Git state:

```text
apps/payment-api/base/
├── deployment.yaml
├── service.yaml
└── route.yaml
```

Later, `route.yaml` is removed from Git.

If `prune: true`, Argo CD removes the OpenShift `Route` during sync.

### 14.2 Application-level prune

```yaml
syncPolicy:
  automated:
    prune: true
```

### 14.3 Resource-level no prune

For important resources:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

Example PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: payment-data
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

### 14.4 Prune with confirmation

For critical objects:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

This is useful for:

- `Namespace`
- PVCs
- CRDs
- Database-related objects
- Shared services

### 14.5 PruneLast

```yaml
syncOptions:
  - PruneLast=true
```

This makes prune happen after other resources are applied and healthy. Useful when dependencies matter.

## 15. CreateNamespace and OpenShift namespace management

Argo CD can create the destination namespace if it does not exist:

```yaml
syncOptions:
  - CreateNamespace=true
```

However, OpenShift has additional operational expectations.

### 15.1 Namespace label for default OpenShift GitOps instance

For the default `openshift-gitops` Argo CD instance to manage a namespace, the namespace often needs the managed-by label:

```bash
oc label namespace payment-dev argocd.argoproj.io/managed-by=openshift-gitops
```

Declarative namespace:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payment-dev
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

### 15.2 Namespace ownership approaches

There are two common approaches:

#### Approach A: Argo CD creates namespace

```yaml
syncOptions:
  - CreateNamespace=true
```

Good for simple application namespaces.

#### Approach B: Platform repo manages namespace separately

```text
cluster-config/
└── namespaces/
    └── payment-prod.yaml

apps/
└── payment-api/
```

Good for production because namespace governance includes:

- Quota
- LimitRange
- NetworkPolicy baseline
- RBAC
- Labels
- Annotations
- Pod security labels
- Default service accounts

### 15.3 Recommended production model

For production:

- Platform GitOps manages namespaces and guardrails.
- Application GitOps manages application resources inside namespaces.
- AppProject restricts application teams to their namespaces.

## 16. Using AppProject for safe multi-team deployment

Without AppProject restrictions, teams may deploy resources outside their intended scope.

### 16.1 Bad practice

All applications use:

```yaml
spec:
  project: default
```

The default project is often too broad.

### 16.2 Better practice

Create one project per team/application boundary:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: openshift-gitops
spec:
  description: Payments application delivery boundary
  sourceRepos:
    - https://git.example.com/payments/*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: payment-dev
    - server: https://kubernetes.default.svc
      namespace: payment-qa
    - server: https://kubernetes.default.svc
      namespace: payment-prod
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ''
      kind: Service
    - group: route.openshift.io
      kind: Route
    - group: ''
      kind: ConfigMap
    - group: autoscaling
      kind: HorizontalPodAutoscaler
    - group: networking.k8s.io
      kind: NetworkPolicy
  clusterResourceWhitelist: []
```

### 16.3 Denying dangerous resources

You can deny resources such as:

- `ClusterRole`
- `ClusterRoleBinding`
- `SecurityContextConstraints`
- `CustomResourceDefinition`
- `Namespace`, unless platform-owned
- Storage classes
- MachineConfig

Application teams should not usually deploy cluster-admin-level resources.

### 16.4 AppProject as a compliance control

AppProject helps answer:

- Which team can deploy to prod?
- Which Git repositories are trusted?
- Which resource kinds are allowed?
- Which namespaces are in scope?
- Can this app create cluster-scoped resources?

For advanced OpenShift administration, AppProject is not optional. It is the security boundary of Argo CD application deployment.

## 17. Application deployment into non-control-plane namespaces

In newer Red Hat OpenShift GitOps versions, administrators can allow `Application` resources to be created outside the Argo CD control-plane namespace. This is useful for multi-tenancy.

Default model:

```text
Application CRs live in openshift-gitops
Application deploys into team namespaces
```

Multi-tenant model:

```text
Application CR for payment team lives in payment-gitops
Application deploys into payment-dev/payment-prod
```

This requires explicit configuration in:

- The `ArgoCD` custom resource
- The `AppProject`
- The `Application` CR namespace/project reference

### 17.1 Why this matters

This allows teams to manage their own `Application` CRs without direct access to the central `openshift-gitops` namespace.

### 17.2 Security warning

Do not allow untrusted teams to use privileged AppProjects. Do not grant access to the Argo CD control-plane namespace. Keep AppProject restrictions tight.

Bad:

```yaml
sourceRepos:
  - '*'
destinations:
  - namespace: '*'
    server: '*'
clusterResourceWhitelist:
  - group: '*'
    kind: '*'
```

Good:

```yaml
sourceRepos:
  - https://git.example.com/payments/payment-gitops.git
destinations:
  - namespace: payment-dev
    server: https://kubernetes.default.svc
  - namespace: payment-prod
    server: https://kubernetes.default.svc
clusterResourceWhitelist: []
```

## 18. Sync waves and hooks for ordered application rollout

Application deployment is not always a flat set of YAML files. Some resources must be applied before others.

Examples:

- Namespace before workload
- CRD before CR
- Secret before Deployment
- Database migration before application rollout
- Smoke test after deployment
- Cleanup after failed sync

Argo CD supports ordering through:

- Sync waves
- Sync phases/hooks

### 18.1 Sync waves

Sync waves are controlled by annotation:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

Lower wave numbers apply first.

Example ordering:

| Wave | Resources |
|---|---|
| `-1` | Namespace, quota, limitrange |
| `0` | ServiceAccount, ConfigMap, Secret |
| `1` | Deployment, Service |
| `2` | Route, HPA, PDB |
| `3` | Post-deploy validation Job |

### 18.2 Example Namespace wave

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payment-prod
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

### 18.3 Example Deployment wave

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/sync-wave: "1"
spec:
  replicas: 4
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
        - name: payment-api
          image: registry.example.com/payment-api:v1.2.3
```

### 18.4 Sync hooks

Argo CD supports hook phases such as:

- `PreSync`
- `Sync`
- `PostSync`
- `SyncFail`
- `PreDelete`
- `PostDelete`
- `Skip`

### 18.5 PreSync migration Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: payment-db-migration
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/payment-migrator:v1.2.3
          command: ["/bin/sh", "-c"]
          args:
            - ./migrate.sh
```

If the migration fails, the deployment sync fails. This prevents rolling out a version that requires a schema change that did not happen.

### 18.6 PostSync smoke test

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: payment-smoke-test
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: smoke-test
          image: registry.access.redhat.com/ubi9/ubi
          command: ["/bin/bash", "-c"]
          args:
            - curl -sf http://payment-api:8080/healthz
```

### 18.7 Hook caution

Hooks are powerful, but overusing hooks can make deployment hard to reason about.

Use hooks for:

- Migration
- Validation
- External readiness checks
- Smoke tests

Avoid hooks for normal app deployment objects such as Deployment, Service, and Route unless you have a specific reason.

## 19. OpenShift-specific resources in GitOps deployment

OpenShift application deployment usually includes resources beyond standard Kubernetes.

### 19.1 Route

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payment-api
  namespace: payment-prod
spec:
  host: payment-api.apps.ocp4.example.com
  to:
    kind: Service
    name: payment-api
  port:
    targetPort: http
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
```

### 19.2 BuildConfig and ImageStream

Some OpenShift environments still use BuildConfig/ImageStream. In modern GitOps deployment, many enterprises build outside OpenShift and deploy images directly. But if you use OpenShift builds, you can GitOps-manage:

- `BuildConfig`
- `ImageStream`
- `ImageStreamTag`

Be careful: ImageStreams are often updated dynamically by image imports or builds, which may cause drift noise.

### 19.3 SecurityContextConstraints and service accounts

Direct SCC modification is cluster-sensitive. A common pattern is:

- Platform GitOps manages SCC grants.
- Application GitOps uses approved service accounts.

Example command for manual grant:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n payment-prod
```

Declarative RoleBinding-style SCC grant is possible, but treat it as platform-owned, not developer-owned.

### 19.4 NetworkPolicy

GitOps should include NetworkPolicy for application security.

Example allowing traffic only from frontend namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-payment-api
  namespace: payment-prod
spec:
  podSelector:
    matchLabels:
      app: payment-api
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              team: frontend
      ports:
        - protocol: TCP
          port: 8080
```

### 19.5 ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: payment-prod-quota
  namespace: payment-prod
spec:
  hard:
    pods: "20"
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    services: "10"
    secrets: "20"
    configmaps: "20"
```

### 19.6 LimitRange

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: payment-prod-limits
  namespace: payment-prod
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      default:
        cpu: 500m
        memory: 512Mi
      min:
        cpu: 50m
        memory: 64Mi
      max:
        cpu: "2"
        memory: 2Gi
```

### 19.7 HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-api
  namespace: payment-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api
  minReplicas: 2
  maxReplicas: 10

      resource:
        name: cpu
        target:
          type: Utilization
```


## 20. Secrets and sensitive configuration

A senior admin must design secret management before enabling full GitOps.

### 20.1 Do not store plain secrets in Git

Bad:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: database-password
type: Opaque
stringData:
  password: redhat123
```

This is not acceptable for production Git repositories.

### 20.2 Common secret management patterns

| Pattern | Description | Notes |
|---|---|---|
| Sealed Secrets | Encrypt Secret into safe-to-store object | Common GitOps pattern |
| External Secrets Operator | Pulls secret from Vault/AWS/GCP/Azure secret manager | Strong enterprise model |
| SOPS + age/GPG | Encrypt YAML values in Git | Good for GitOps repos |
| Argo CD Vault Plugin | Render secrets from Vault at sync time | Requires plugin governance |
| Manual secret pre-provisioning | Platform creates secret outside app GitOps | Simple but less automated |

### 20.3 Secret reference in Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payment-prod
spec:
  template:
    spec:
      containers:
        - name: payment-api
          image: registry.example.com/payment-api:v1.2.3
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: payment-db-secret
                  key: password
```

The deployment references the secret, but the secret material itself should be managed securely.

### 20.4 ConfigMap vs Secret

Use `ConfigMap` for non-sensitive values:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: payment-config
  namespace: payment-prod
data:
  LOG_LEVEL: INFO
  FEATURE_X_ENABLED: "true"
```

Use `Secret` only for sensitive values.

## 21. Image promotion and environment promotion

GitOps application deployment must answer a basic question:

> How does version `v1.2.3` move from dev to qa to prod?

### 21.1 Anti-pattern: tracking `latest`

Bad:

```yaml
image: registry.example.com/payment-api:latest
```

Problems:

- Not reproducible
- Difficult rollback
- Argo CD may not detect a tag change if tag name remains same
- Production audit becomes weak

### 21.2 Better: immutable image tags

```yaml
image: registry.example.com/payment-api:v1.2.3
```

Even better, use digest pinning for critical workloads:

```yaml
image: registry.example.com/payment-api@sha256:abc123...
```

### 21.3 Promotion by pull request

Dev overlay:

```yaml
images:
  - name: registry.example.com/payment-api
    newTag: v1.2.3
```

QA overlay:

```yaml
images:
  - name: registry.example.com/payment-api
    newTag: v1.2.2
```

Promotion PR changes QA from `v1.2.2` to `v1.2.3`.

Production PR changes prod from `v1.2.2` to `v1.2.3` after approval.

### 21.4 Promotion branches

Some organizations use branches:

```text
main      -> dev
release   -> qa
prod      -> production
```

Application target revisions:

```yaml
source:
  targetRevision: prod
```

This can work, but branch drift and cherry-picking need discipline.

### 21.5 Promotion directories

Another pattern:

```text
apps/payment-api/overlays/dev/kustomization.yaml
apps/payment-api/overlays/qa/kustomization.yaml
apps/payment-api/overlays/prod/kustomization.yaml
```

This makes environment state visible in one branch.

For most enterprise OpenShift setups, environment directories with PR-based promotion are clearer.

## 23. ApplicationSet for scalable application deployment

`ApplicationSet` generates multiple Argo CD Applications from a template.

Useful for:

- Deploying one app to many clusters
- Deploying many apps from a directory
- Deploying environment-specific apps from generator data
- Reducing repetitive Application YAML

### 23.1 List generator example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: payment-api-environments
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - env: dev
            namespace: payment-dev
          - env: qa
            namespace: payment-qa
          - env: prod
            namespace: payment-prod
  template:
    metadata:
      name: 'payment-api-{{env}}'
    spec:
      project: payment-team
      source:
        repoURL: https://git.example.com/platform/payment-gitops.git
        targetRevision: main
        path: 'apps/payment-api/overlays/{{env}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{namespace}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

### 23.2 Git directory generator example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: all-dev-apps
  namespace: openshift-gitops
spec:
  generators:
    - git:
        repoURL: https://git.example.com/platform/apps-gitops.git
        revision: main
        directories:
          - path: apps/*/overlays/dev
  template:
    metadata:
      name: '{{path.basename}}-dev'
    spec:
      project: dev-apps
      source:
        repoURL: https://git.example.com/platform/apps-gitops.git
        targetRevision: main
        path: '{{path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{path.basename}}-dev'
```

### 23.3 ApplicationSet cautions

- A bad template can create many bad Applications.
- Use AppProject restrictions.
- Test generator output before production.
- Keep naming deterministic.
- Avoid broad wildcard deployment into production.

## 24. Progressive deployment concepts

Progressive delivery means rolling changes in stages instead of applying everything at once.

In GitOps, this can be done using:

- Separate environment promotion PRs
- Manual sync gates
- Sync waves
- ApplicationSet strategies
- Argo Rollouts
- OpenShift deployment strategies
- Canary or blue-green rollout patterns

### 24.1 Simple progressive promotion

```text
Commit image v1.2.3 to dev
        |
        v
Tests pass
        |
        v
PR promotes v1.2.3 to qa
        |
        v
QA approval
        |
        v
PR promotes v1.2.3 to prod
```

### 24.2 Sync-wave progressive ordering

```text
Wave -1: namespace, quota, network baseline
Wave  0: service account, config, secret reference
Wave  1: database migration
Wave  2: deployment, service
Wave  3: route, HPA, PDB
Wave  4: smoke test
```

### 24.3 ApplicationSet rolling sync

Some OpenShift GitOps versions include progressive sync capabilities for ApplicationSet rollout strategies. Treat technology preview features carefully and validate support status for your installed OpenShift GitOps version before using in production.

### 24.4 Argo Rollouts

For advanced progressive delivery, Argo Rollouts can support canary and blue-green deployment patterns. This is separate from basic Argo CD sync behavior. Argo CD applies the Rollout CR; the rollout controller manages traffic shifting and rollout behavior.

| OutOfSync | Degraded | Both config drift and runtime problem |

## 26. Rollback and recovery

### 26.1 Rollback by Git revert

Preferred GitOps rollback:

```bash
git revert <bad-commit>
git push origin main
```

Argo CD detects the Git change and reconciles to the previous known-good state.

### 26.2 Rollback by image tag change

Change:

```yaml
newTag: v1.2.4
```

Back to:

```yaml
newTag: v1.2.3
```

Commit and push.

### 26.3 Argo CD rollback command

Argo CD supports syncing to previous revisions, but for production audit, Git revert is usually cleaner because Git remains the source of truth.

### 26.4 Emergency manual fix

Sometimes production requires emergency action:

```bash
oc scale deployment payment-api --replicas=0 -n payment-prod
```

If self-heal is enabled, Argo CD may revert the change. In a real incident, either:

- Disable auto-sync temporarily
- Make the emergency change in Git
- Use Argo CD sync window controls if configured
- Pause automation through an approved incident process

### 26.5 Disable auto-sync temporarily

```bash
argocd app set payment-api-prod --sync-policy none
```

After emergency is resolved, re-enable:

```bash
argocd app set payment-api-prod --sync-policy automated --self-heal --auto-prune
```

Use this carefully and document the incident.

## 27. Security and RBAC design

### 27.1 Separate responsibilities

| Role | Responsibility |
|---|---|
| Developer | Application code and app-level config |
| CI system | Build/test/push image/update GitOps repo |
| Platform admin | Argo CD, AppProjects, cluster policies, namespaces |
| Security team | Policy validation, secret strategy, approvals |
| Argo CD | Reconcile Git state into OpenShift |

### 27.2 Do not give every team access to `openshift-gitops`

The central Argo CD namespace is powerful. Avoid giving broad edit access.

### 27.3 Use OpenShift RBAC and Argo CD RBAC together

OpenShift RBAC controls Kubernetes/OpenShift API permissions.

Argo CD RBAC controls Argo CD actions such as:

- View applications
- Sync applications
- Override parameters
- Delete applications
- Manage repositories
- Manage projects

### 27.4 Restrict repositories

AppProject should allow only approved repositories:

```yaml
sourceRepos:
  - https://git.example.com/payments/payment-gitops.git
```

Avoid:

```yaml
sourceRepos:
  - '*'
```

### 27.5 Restrict destinations

```yaml
destinations:
  - server: https://kubernetes.default.svc
    namespace: payment-prod
```

Avoid:

```yaml
destinations:
  - server: '*'
    namespace: '*'
```

### 27.6 Restrict cluster resources

Application deployments should not normally deploy cluster-scoped resources.

Good default:

```yaml
clusterResourceWhitelist: []
```

Let platform GitOps manage cluster-scoped resources separately.

### 27.7 Admission policies

Use OpenShift/Kubernetes admission controls to enforce standards:

- No privileged containers
- Required resource requests and limits
- Approved registries only
- No latest tag
- Required labels
- Required NetworkPolicy
- Required probes

GitOps does not replace policy. GitOps applies desired state. Policy decides whether desired state is allowed.

## 28. Common production patterns

### 28.1 App-of-apps bootstrap

Root application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-apps-root
  namespace: openshift-gitops
spec:
  project: platform
  source:
    repoURL: https://git.example.com/platform/cluster-gitops.git
    targetRevision: main
    path: bootstrap/applications
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

The root app deploys child Application manifests.

### 28.2 Platform repo + app repo separation

```text
platform-gitops/
├── namespaces/
├── quotas/
├── networkpolicies/
├── appprojects/
└── cluster-addons/

application-gitops/
└── apps/
    └── payment-api/
```

### 28.3 Namespace baseline

Every app namespace should have:

- Owner labels
- Environment labels
- Quota
- LimitRange
- Default deny NetworkPolicy
- Required allow NetworkPolicies
- RBAC bindings
- Monitoring labels

### 28.4 Default deny network model

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: payment-prod
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

Then add explicit allow policies.

### 28.5 GitOps change control

For production branch:

- Require pull request
- Require at least two approvals
- Require CI validation
- Require manifest linting
- Require policy checks
- Require signed commits if organization mandates it
- Protect direct push

### 28.6 Manifest validation pipeline

Before merge:

```bash
kustomize build apps/payment-api/overlays/prod
kubectl apply --dry-run=server -f rendered.yaml
conftest test rendered.yaml
kubeconform -summary rendered.yaml
```

For OpenShift-specific resources, validate against the OpenShift cluster API if possible.

## 29. Common failure scenarios and troubleshooting

### 29.1 Application stuck OutOfSync

Check:

```bash
argocd app get payment-api-prod
argocd app diff payment-api-prod
oc describe application payment-api-prod -n openshift-gitops
```

Common causes:

- Manual change in cluster
- Generated fields differ
- HPA changes replicas
- Operator mutates resource
- Webhook injects sidecars
- Resource failed to apply
- Namespace missing

Fix:

- Revert manual change
- Enable selfHeal
- Add targeted ignoreDifferences
- Correct manifest
- Fix namespace/AppProject permissions

### 29.2 Application Degraded

Check OpenShift workload:

```bash
oc get pods -n payment-prod
oc describe pod <pod> -n payment-prod
oc logs <pod> -n payment-prod
oc get events -n payment-prod --sort-by=.lastTimestamp
```

Common causes:

- Image pull error
- Bad image tag
- Readiness probe failure
- Liveness probe killing pod
- Missing secret/configmap
- SCC violation
- Quota exceeded
- PVC pending
- NetworkPolicy blocking dependency

### 29.3 ComparisonError

Usually repo-server rendering problem.

Check:

```bash
argocd app get payment-api-prod
oc logs deployment/openshift-gitops-repo-server -n openshift-gitops
```

Common causes:

- Invalid YAML
- Kustomize path wrong
- Helm chart render error
- Missing values file
- Private repo auth failure
- Unsupported plugin

### 29.4 Permission denied by AppProject

Error example:

```text
application is not allowed to use project
namespace is not permitted in project
repository is not permitted in project
resource kind is not permitted
```

Check:

```bash
oc get appproject payment-team -n openshift-gitops -o yaml
oc get application payment-api-prod -n openshift-gitops -o yaml
```

Fix:

- Add repository to `sourceRepos`
- Add namespace to `destinations`
- Add resource kind to whitelist
- Avoid using privileged default project

### 29.5 Namespace not managed

Symptoms:

- Argo CD cannot deploy to namespace
- Permission errors
- Resources fail to apply

Fix for default OpenShift GitOps instance:

```bash
oc label namespace payment-prod argocd.argoproj.io/managed-by=openshift-gitops
```

Declarative fix:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payment-prod
  labels:
    argocd.argoproj.io/managed-by: openshift-gitops
```

### 29.6 ImagePullBackOff

Check:

```bash
oc describe pod <pod> -n payment-prod
oc get secret -n payment-prod
oc get sa default -n payment-prod -o yaml
```

Common causes:

- Wrong image tag
- Registry unreachable
- Missing pull secret
- Image does not exist
- TLS trust issue
- Registry auth failure

Fix:

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=<user> \
  --docker-password=<password> \
  -n payment-prod

oc secrets link default regcred --for=pull -n payment-prod
```

For GitOps, manage pull secret securely and service account linkage declaratively where possible.

### 29.7 Quota exceeded

Error:

```text
exceeded quota: payment-prod-quota
```

Check:

```bash
oc describe quota -n payment-prod
oc get resourcequota -n payment-prod
```

Fix:

- Increase quota through platform GitOps
- Reduce app resource requests
- Remove unused resources
- Correct LimitRange defaults

### 29.8 SCC violation

Error:

```text
would violate PodSecurity
unable to validate against any security context constraint
```

Check:

```bash
oc describe pod <pod> -n payment-prod
oc get sa -n payment-prod
```

Fix options:

- Use OpenShift-compatible image that can run as arbitrary UID
- Avoid `runAsUser: 0`
- Remove privileged settings
- Use correct service account
- Platform admin grants needed SCC only when justified

Manual grant example:

```bash
oc adm policy add-scc-to-user anyuid -z payment-sa -n payment-prod
```

Do not normalize `anyuid` as a default. It should be an exception.

### 29.9 PVC Pending

Check:

```bash
oc get pvc -n payment-prod
oc describe pvc payment-data -n payment-prod
oc get sc
```

Common causes:

- No default StorageClass
- Wrong StorageClass
- WaitForFirstConsumer behavior
- No matching PV
- Storage backend issue

Fix:

- Correct `storageClassName`
- Ensure pod exists if using WaitForFirstConsumer
- Check storage operator health
- Avoid pruning PVC accidentally

### 29.10 Route not reachable

Check:

```bash
oc get route -n payment-prod
oc describe route payment-api -n payment-prod
oc get svc payment-api -n payment-prod
oc get endpoints payment-api -n payment-prod
```

Common causes:

- Service selector mismatch
- Pod not ready
- Wrong targetPort
- Route host DNS missing
- TLS configuration error
- NetworkPolicy blocking ingress

Fix service selector:

```bash
oc get pods --show-labels -n payment-prod
oc get svc payment-api -n payment-prod -o yaml
```

Make labels/selectors match.

## 31. Interview and real-world admin notes

### 31.1 How would you explain GitOps deployment?

A strong answer:

> GitOps deployment means the complete desired application state is stored in Git. Argo CD watches that Git repository, renders the manifests, compares them with the live OpenShift state, and synchronizes the cluster to match Git. CI builds images, but Argo CD performs the deployment. This gives auditability, drift detection, rollback through Git, and a clear separation between build and deploy permissions.

### 31.2 What is the difference between Synced and Healthy?

- `Synced` means live state matches Git.
- `Healthy` means the resources are running correctly according to health checks.

An application can be `Synced` but `Degraded` if the desired state was applied but pods are failing.

### 31.3 Why use AppProject?

AppProject restricts what an Argo CD application can deploy. It limits repositories, namespaces, clusters, and resource kinds. In enterprise OpenShift, AppProject is a major security control for multi-team GitOps.

### 31.4 Why should CI not deploy directly to OpenShift?

Because CI systems should not need powerful cluster credentials. CI should build and update Git. Argo CD should deploy. This improves security, auditability, and consistency.

### 31.5 What is self-healing?

Self-healing means Argo CD automatically corrects live cluster changes that drift from Git. If someone runs `oc scale` or `oc edit`, Argo CD detects the difference and restores Git-defined state.

### 31.6 What is prune?

Prune deletes resources from the cluster when they are removed from Git. It keeps the cluster clean, but it can be dangerous for critical resources such as namespaces and PVCs. Use `Prune=confirm` or `Prune=false` where needed.

### 31.7 How do you promote app versions?

Use immutable image tags and promote them through Git changes, usually by pull request. For example, update dev overlay to `v1.2.3`, test it, then update QA, then production.

### 31.8 How do you handle secrets?

Do not store plain secrets in Git. Use Sealed Secrets, External Secrets Operator, SOPS, Vault integration, or platform-managed secrets. Application manifests should reference secrets without exposing secret values.

### 31.9 How do you troubleshoot OutOfSync?

Use:

```bash
argocd app get <app>
argocd app diff <app>
oc describe application <app> -n openshift-gitops
```

Then check whether drift is caused by manual changes, HPA, operators, admission mutation, or invalid manifests.

### 31.10 How do you troubleshoot Degraded?

Use OpenShift runtime checks:

```bash
oc get pods -n <namespace>
oc describe pod <pod> -n <namespace>
oc logs <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Degraded usually means a workload problem, not necessarily a Git problem.

## Final senior-admin summary

For production OpenShift GitOps application deployment:

1. Keep application desired state in Git.
2. Use Argo CD `Application` for each deployable unit.
3. Use `AppProject` as the security boundary.
4. Separate platform GitOps from application GitOps.
5. Use Kustomize overlays or Helm values for environments.
6. Prefer immutable image tags.
7. Use PR-based promotion between dev, QA, and prod.
8. Enable self-healing where drift control is required.
9. Enable prune only after deletion risk is understood.
10. Do not store plain secrets in Git.
11. Use sync waves/hooks only where ordering is necessary.
12. Monitor both Argo CD sync status and OpenShift workload health.
13. Roll back by reverting Git whenever possible.
14. Protect production with branch protection, policy checks, AppProject restrictions, and controlled sync policies.
