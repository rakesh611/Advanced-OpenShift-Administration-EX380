## 1. Core Idea

In OpenShift GitOps, **Automatic Sync** means Argo CD automatically applies the desired state from Git to the target OpenShift cluster when it detects that the application is **OutOfSync**.

In simple terms:

```text
Git desired state != Cluster live state
              ↓
        Application OutOfSync
              ↓
    Argo CD automatically syncs
              ↓
Cluster becomes closer to Git desired state
```

For a senior administrator, the important point is this:

> Automatic Sync changes the deployment model from **push-based deployment** to **Git-driven reconciliation**.

A CI/CD pipeline does not need to log in to OpenShift and run `oc apply`. The pipeline only needs to build, test, scan, update manifests or image tags in Git, and push/merge the change. Argo CD then reconciles the cluster from Git.

---

## 2. Manual Sync vs Automatic Sync

### Manual Sync

With manual sync, Argo CD detects drift but waits for a human or pipeline to click **Sync** or run an `argocd app sync` command.

```text
Git changed
  ↓
Argo CD detects OutOfSync
  ↓
No deployment happens until manual approval/sync
```

Manual sync is useful for:

- Training environments
- Production environments that require manual approval
- Risky migrations
- First-time onboarding of an application
- Debugging sync behavior
- Regulated environments where deployment requires explicit release approval

### Automatic Sync

With automatic sync, Argo CD automatically applies the change after detecting the application as OutOfSync.

```text
Git changed
  ↓
Argo CD detects OutOfSync
  ↓
Argo CD starts sync automatically
  ↓
OpenShift resources are applied/updated/deleted depending on policy
```

Automatic sync is useful for:

- GitOps-native application delivery
- Platform configuration management
- Namespace baseline enforcement
- Dev/test/staging environments
- Infrastructure-as-code style cluster configuration
- Drift correction when combined with `selfHeal`

## 3. Where Automatic Sync Fits in Argo CD Architecture

Automatic Sync is mainly handled by the **Argo CD Application Controller**.

Typical OpenShift GitOps components include:

| Component | Role in Automatic Sync |
|---|---|
| `argocd-server` / OpenShift GitOps route | UI and API access |
| `argocd-repo-server` | Pulls Git repositories and renders manifests through Helm, Kustomize, Jsonnet, or plain YAML |
| `argocd-application-controller` | Compares desired vs live state and performs sync operations |
| Redis | Caching and state coordination, depending on deployment mode |
| Kubernetes/OpenShift API server | Receives applied resources |
| `Application` CR | Defines source, destination, sync policy, sync options, and tracking behavior |
| `AppProject` CR | Controls allowed Git repositories, clusters, namespaces, and resource kinds |

Automatic sync is not a separate product or controller. It is a mode of the `Application` reconciliation logic.

## 4. Automatic Sync Control Loop

A production administrator should understand the control loop clearly.

### Step-by-step flow

```text
1. Developer or pipeline merges a Git change
2. Argo CD notices a new Git revision through polling, webhook, or refresh
3. Repo server renders the desired manifests
4. Application controller compares rendered manifests with live OpenShift resources
5. Application becomes OutOfSync
6. If automatic sync is enabled, Argo CD creates a sync operation
7. Resources are applied according to phases, waves, and sync options
8. Health checks are evaluated
9. Application status becomes Synced/Healthy, Synced/Degraded, OutOfSync, or SyncFailed
```

### Key senior-level point

Automatic sync is not just `oc apply` on a timer. It is a reconciliation process that considers:

- Git revision
- Application parameters
- Rendered manifests
- Resource tracking labels/annotations
- AppProject permissions
- Sync windows
- Sync hooks
- Sync waves
- Health state
- Diff customizations
- Sync options
- Cluster RBAC
- Kubernetes/OpenShift admission controllers

## 5. Application CRD Fields for Automatic Sync

Automatic Sync is configured under:

```yaml
spec:
  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
      allowEmpty: false
```

### Field summary

| Field | Default Behavior | Meaning |
|---|---|---|
| `automated: {}` | Enables automatic sync | Minimal automatic sync configuration |
| `enabled: true` | Enables auto-sync explicitly | Makes intent clear |
| `enabled: false` | Disables auto-sync | Allows keeping prune/selfHeal settings without activating them |
| `prune: true` | Disabled by default | Deletes resources removed from Git |
| `selfHeal: true` | Disabled by default | Corrects live cluster drift without a Git change |
| `allowEmpty: true` | Disabled by default | Allows automatic sync to result in zero managed resources |

### Important behavior

An empty automated block means automatic sync is enabled:

```yaml
syncPolicy:
  automated: {}
```

A more explicit production style is:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
```

## 6. Basic Automatic Sync Examples

### Example 1: Minimal automatic sync

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-auto-sync
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://github.com/example/gitops-apps.git
    targetRevision: main
    path: apps/nginx/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-dev
  syncPolicy:
    automated: {}
```

This enables auto-sync, but does not automatically prune deleted resources and does not self-heal live cluster drift by default.

### Example 2: Automatic sync with self-healing

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
```

This means Argo CD can correct changes made directly in the cluster, such as:

```bash
oc scale deployment nginx --replicas=5 -n nginx-dev
```

If Git says `replicas: 2`, Argo CD will eventually drive the Deployment back toward `replicas: 2`.

### Example 3: Automatic sync with pruning

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
```

This means if a resource is deleted from Git, Argo CD can delete the corresponding live resource from OpenShift.

### Example 4: Automatic sync with prune and self-heal

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
    allowEmpty: false
```

This is common for GitOps-managed application environments, but must be used carefully in production.

## 7. Advanced Production-Ready Application Example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: openshift-gitops
  labels:
    app.kubernetes.io/part-of: payments
    environment: prod
  annotations:
    notifications.argoproj.io/subscribe.on-sync-failed.slack: payments-platform
    notifications.argoproj.io/subscribe.on-health-degraded.slack: payments-platform
spec:
  project: payments-prod

  source:
    repoURL: https://github.com/example/platform-gitops.git
    targetRevision: main
    path: applications/payment-api/overlays/prod

  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod

  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
      allowEmpty: false

    syncOptions:
      - CreateNamespace=true
      - PrunePropagationPolicy=foreground
      - PruneLast=true
      - ApplyOutOfSyncOnly=true
      - RespectIgnoreDifferences=true

    retry:
      limit: 5
      backoff:
        duration: 10s
        factor: 2
        maxDuration: 3m
      refresh: true

    managedNamespaceMetadata:
      labels:
        argocd.argoproj.io/managed-by: openshift-gitops
        environment: prod
        owner: payments
      annotations:
        openshift.io/description: Payment API production namespace

  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

### Why this is production-style

It includes:

- Explicit `enabled: true`
- Pruning enabled but protected by `allowEmpty: false`
- Self-healing enabled
- Namespace auto-creation
- Foreground deletion behavior
- Pruning after normal resources become healthy
- Sync only on out-of-sync resources
- Respect for ignored differences
- Retry policy
- Managed namespace metadata
- Notifications through annotations
- AppProject separation through `payments-prod`

## 8. Automatic Pruning

### What pruning means

Pruning means Argo CD deletes live resources that are tracked as part of the application but no longer exist in Git.

Example:

```text
Git before:
  deployment.yaml
  service.yaml
  route.yaml

Git after:
  deployment.yaml
  service.yaml

Live cluster still has:
  route/payment-api

With prune: true
  Argo CD deletes route/payment-api
```

### Why pruning is disabled by default

Pruning is dangerous if Git is wrong. A bad commit, wrong path, broken generator, or empty rendered output could cause resource deletion. Therefore, automatic sync does not automatically delete resources unless `prune: true` is set.

### Enable pruning

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
```

### Resource-level no-prune

For critical resources, you can prevent pruning:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
```

Use this for resources such as:

- PersistentVolumeClaims
- Namespaces
- Important Secrets
- Shared ConfigMaps
- Cluster-scoped resources
- Resources managed jointly by another operator

### Prune with confirmation

For sensitive resources:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=confirm
```

This is useful for resources where accidental deletion is unacceptable.

### PruneLast

```yaml
syncOptions:
  - PruneLast=true
```

This makes pruning happen after other resources are applied and healthy. It is helpful when replacing resources or changing ownership patterns.

### Prune propagation policy

```yaml
syncOptions:
  - PrunePropagationPolicy=foreground
```

Common values:

| Value | Behavior |
|---|---|
| `foreground` | Wait for dependent resources to be deleted before parent deletion completes |
| `background` | Parent deletion returns quickly; dependents are garbage-collected later |
| `orphan` | Dependents are orphaned instead of deleted |

For production, `foreground` is often safer because deletion behavior is more visible.

## 9. Automatic Self-Healing

### What self-healing means

Self-healing means Argo CD corrects live cluster drift even when Git has not changed.

Example:

```bash
oc scale deployment payment-api --replicas=10 -n payment-prod
```

Git says:

```yaml
spec:
  replicas: 3
```

With self-heal enabled, Argo CD detects drift and syncs back to Git:

```text
Live replicas: 10
Git replicas: 3
Application: OutOfSync
Argo CD: automatic sync
Live replicas: 3
```

### Enable self-healing

```yaml
syncPolicy:
  automated:
    enabled: true
    selfHeal: true
```

### What self-healing protects against

- Manual `oc edit`
- Manual `oc scale`
- Emergency hotfix not committed to Git
- Accidental resource modification
- Drift caused by scripts
- Unapproved cluster-side changes

### What self-healing does not solve

Self-healing does not automatically fix:

- Broken Git manifests
- Invalid YAML
- Failed admission policies
- Image pull errors
- SCC violations
- ResourceQuota failures
- LimitRange violations
- NetworkPolicy connectivity issues
- Application runtime bugs
- Failed database migrations

### Senior admin warning

Self-healing can fight humans and controllers.

If an HPA changes `spec.replicas`, and Git also declares replicas, Argo CD may show OutOfSync or keep forcing replicas back depending on configuration. For HPA-managed workloads, either remove fixed replicas from Git where appropriate or configure `ignoreDifferences` for `/spec/replicas` with `RespectIgnoreDifferences=true`.

## 10. allowEmpty Protection

`allowEmpty` controls whether auto-sync is allowed to result in zero managed resources.

Default protection:

```yaml
allowEmpty: false
```

This protects against scenarios such as:

- Wrong Git path
- Broken Helm/Kustomize output
- Empty directory
- Bad branch
- Generator bug
- Accidental deletion of all manifests

### Dangerous example

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    allowEmpty: true
```

If the rendered manifest set becomes empty, Argo CD may prune all previously managed application resources.

### When allowEmpty may be valid

Use `allowEmpty: true` only when an empty desired state is intentional, such as:

- Temporary environment teardown
- Preview environment cleanup
- Generated applications that intentionally produce no resources for some tenants
- Controlled decommissioning workflows

Production default recommendation:

```yaml
allowEmpty: false
```

## 11. enabled Field Behavior

Modern Argo CD/OpenShift GitOps supports explicit control with:

```yaml
syncPolicy:
  automated:
    enabled: false
    prune: true
    selfHeal: true
```

This means:

- The application stores pruning and self-healing preferences.
- Automatic sync is not active.
- Argo CD does not auto-sync even though `prune` and `selfHeal` are present.

This is useful for:

- Temporarily freezing an application
- Preparing a policy before enabling it
- Production change windows
- Migration from manual to automatic sync
- ApplicationSet templates where you want flags preserved but inactive

### Explicit enable

```yaml
syncPolicy:
  automated:
    enabled: true
```

### Implicit enable

```yaml
syncPolicy:
  automated: {}
```

For production, use `enabled: true` because it is clearer during audits and code review.

## 12. Sync Retry and Refresh

Automatic sync may fail due to temporary errors:

- API server transient issue
- Webhook timeout
- Temporary image pull delay
- Operator CRD not ready yet
- Namespace just created
- Admission controller temporarily unavailable

A retry policy can reduce manual intervention.

```yaml
syncPolicy:
  retry:
    limit: 5
    backoff:
      duration: 10s
      factor: 2
      maxDuration: 3m
    refresh: true
```

### Meaning

| Field | Meaning |
|---|---|
| `limit` | Number of retry attempts |
| `duration` | Initial retry wait |
| `factor` | Backoff multiplier |
| `maxDuration` | Maximum backoff delay |
| `refresh: true` | Refresh when a new revision appears while retrying |

### Senior admin view

Retries are not a replacement for fixing root cause. They are useful for transient issues, but repeated sync failures usually mean:

- bad manifests,
- missing permissions,
- invalid CRDs,
- operator dependency problem,
- quota/limit issue,
- SCC/admission problem,
- or wrong resource ordering.

## 13. Sync Options That Matter with Automatic Sync

Sync options change how Argo CD applies resources.

### Application-level sync options

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
    - PruneLast=true
    - ApplyOutOfSyncOnly=true
    - RespectIgnoreDifferences=true
```

### Resource-level sync options

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false,Validate=false
```

### Important options

| Sync Option | Use Case |
|---|---|
| `CreateNamespace=true` | Create destination namespace automatically |
| `PruneLast=true` | Delete removed resources after apply/health succeeds |
| `PrunePropagationPolicy=foreground` | Safer visible pruning behavior |
| `ApplyOutOfSyncOnly=true` | Reduce unnecessary apply operations |
| `RespectIgnoreDifferences=true` | During sync, respect configured ignored fields |
| `Validate=false` | Skip client-side validation for some custom resources |
| `SkipDryRunOnMissingResource=true` | Useful when CRDs are created by another controller or in same sync flow |
| `ServerSideApply=true` | Use Kubernetes server-side apply behavior |
| `Replace=true` | Use replace/create instead of apply; dangerous for some resources |
| `Force=true` | Delete/recreate resources; use with extreme care |

### CreateNamespace example

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
  managedNamespaceMetadata:
    labels:
      environment: dev
      argocd.argoproj.io/managed-by: openshift-gitops
```

### SkipDryRunOnMissingResource example

Useful when a custom resource appears before the API server recognizes the CRD:

```yaml
syncPolicy:
  syncOptions:
    - SkipDryRunOnMissingResource=true
```

Better approach: place CRDs/operators in earlier sync waves and application resources in later waves.

## 14. OpenShift-Specific Considerations

OpenShift GitOps is Argo CD packaged and integrated with OpenShift through the Red Hat OpenShift GitOps Operator. Automatic sync behavior is mostly Argo CD behavior, but OpenShift adds important operational realities.

### 14.1 OpenShift GitOps namespace

Default OpenShift GitOps installation commonly uses:

```text
openshift-gitops
```

Applications are often created in this namespace:

```bash
oc get applications -n openshift-gitops
```

### 14.2 Namespace management label

For the default OpenShift GitOps instance to manage a target namespace, the namespace is commonly labeled:

```bash
oc label namespace <target-namespace> argocd.argoproj.io/managed-by=openshift-gitops
```

Example:

```bash
oc new-project payment-dev
oc label namespace payment-dev argocd.argoproj.io/managed-by=openshift-gitops
```

If this is missing, Argo CD may not be able to manage resources in the namespace depending on your OpenShift GitOps configuration.

### 14.3 OpenShift RBAC

Automatic sync uses Argo CD controller credentials. If the controller lacks permission, auto-sync fails.

Examples of permission-related failures:

```text
services is forbidden
routes.route.openshift.io is forbidden
securitycontextconstraints.security.openshift.io is forbidden
networkpolicies.networking.k8s.io is forbidden
```

You must design RBAC carefully. Avoid giving every application unrestricted cluster-admin access.

### 14.4 OpenShift-specific resources

Argo CD can manage OpenShift resources such as:

- `Route`
- `BuildConfig`
- `DeploymentConfig`
- `ImageStream`
- `SecurityContextConstraints`
- `OperatorGroup`
- `Subscription`
- `ConsoleLink`
- `Project`
- `NetworkPolicy`
- `LimitRange`
- `ResourceQuota`

Each resource may have different admission, status, and health behavior.

### 14.5 Operators and CRDs

When managing Operators with GitOps:

- Install `Namespace`, `OperatorGroup`, and `Subscription` first.
- Wait for CRDs to exist.
- Apply custom resources after CRDs are available.
- Use sync waves to order dependencies.
- Avoid applying a CR before the API server recognizes its CRD.

Example ordering:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-10"
```

for `Namespace` and `OperatorGroup`, then:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

for `Subscription`, then:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

for the custom resource.

### 14.6 SCC and Pod Security Admission

If Argo CD syncs a Deployment that violates OpenShift security rules, sync might succeed at object creation but workload health will fail because pods cannot run.

Examples:

```text
Error creating: pods is forbidden: violates PodSecurity
unable to validate against any security context constraint
```

Fix through correct securityContext, service account, or SCC binding where justified:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

Use SCC exceptions carefully and keep them declarative where possible.

### 14.7 Routes and TLS

For OpenShift Routes, automatic sync can manage:

- hostnames
- TLS termination
- edge/passthrough/reencrypt config
- annotations
- service target

But cluster DNS and certificate trust are outside normal application sync unless you manage them declaratively too.

### 14.8 ResourceQuota and LimitRange

Automatic sync can fail if manifests violate quota or limits:

```text
exceeded quota
minimum cpu usage per Container is 5m
maximum memory usage per Container is 1Gi
```

For production, keep quotas, limit ranges, and workload requests/limits in the same GitOps model.

## 15. AppProject Guardrails

`AppProject` is one of the most important enterprise controls for automatic sync.

Without strict AppProject configuration, auto-sync can become dangerous.

### Example AppProject

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-prod
  namespace: openshift-gitops
spec:
  description: Production applications for payment platform

  sourceRepos:
    - https://github.com/example/platform-gitops.git

  destinations:
    - server: https://kubernetes.default.svc
      namespace: payment-prod

  clusterResourceWhitelist:
    - group: ""
      kind: Namespace

  namespaceResourceWhitelist:
    - group: "apps"
      kind: Deployment
    - group: ""
      kind: Service
    - group: "route.openshift.io"
      kind: Route
    - group: "networking.k8s.io"
      kind: NetworkPolicy
    - group: ""
      kind: ConfigMap
    - group: ""
      kind: Secret

  syncWindows:
    - kind: deny
      schedule: "0 9 * * 1-5"
      duration: 8h
      applications:
        - payment-api-prod
      manualSync: true
      timeZone: Asia/Kolkata
```

### What AppProject controls

| Control | Why it matters |
|---|---|
| `sourceRepos` | Prevents apps from pulling untrusted Git repositories |
| `destinations` | Prevents apps from deploying into unauthorized namespaces/clusters |
| resource whitelist/blacklist | Restricts dangerous resource kinds |
| sync windows | Controls when automatic sync can occur |
| project roles | Enables scoped RBAC |

### Senior recommendation

Do not run enterprise workloads in the unrestricted `default` project. Create dedicated AppProjects per team, environment, or platform domain.

## 16. ApplicationSet and Automatic Sync

`ApplicationSet` generates multiple `Application` resources from templates.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-services
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - name: payment-api
            namespace: payment-dev
            path: apps/payment-api/overlays/dev
          - name: order-api
            namespace: order-dev
            path: apps/order-api/overlays/dev
  template:
    metadata:
      name: '{{name}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/example/platform-gitops.git
        targetRevision: main
        path: '{{path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{namespace}}'
      syncPolicy:
        automated:
          enabled: true
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

### Important ApplicationSet behavior

For an application generated by ApplicationSet, directly editing the generated `Application` may not have lasting effect because the ApplicationSet controller reconciles it back from the template.

Correct approach:

- Change the ApplicationSet template, or
- Use ApplicationSet-supported mechanisms for controlled modification, or
- Use generator parameters to control auto-sync per environment.

### Pattern: auto-sync dev, manual prod

```yaml
# generator values
- name: payment-api-dev
  autoSyncEnabled: "true"
- name: payment-api-prod
  autoSyncEnabled: "false"
```

Template:

```yaml
syncPolicy:
  automated:
    enabled: '{{autoSyncEnabled}}'
    prune: true
    selfHeal: true
```

Validate generated YAML carefully because templated booleans can become strings if not handled correctly by the generator/template mechanism.

## 17. Sync Waves and Hooks with Automatic Sync

Automatic sync still respects sync phases and waves.

### Sync phases

| Phase | Use Case |
|---|---|
| `PreSync` | Run checks or preparation before normal resources |
| `Sync` | Run during normal sync |
| `PostSync` | Run validation after resources are applied and healthy |
| `SyncFail` | Run cleanup or notification job after failed sync |
| `Skip` | Do not apply a manifest |

### Example PreSync migration job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/payment-api-migration:v1.2.3
          command: ["/bin/sh", "-c", "./migrate.sh"]
```

### Example PostSync smoke test

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: payment-api-smoke-test
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: smoke-test
          image: registry.access.redhat.com/ubi9/ubi
          command:
            - /bin/bash
            - -c
            - curl -ksf https://payment-api.apps.example.com/healthz
```

### Sync waves

Sync waves control ordering. Lower wave numbers run first.

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-5"
```

Typical ordering:

| Wave | Resource Type |
|---|---|
| `-10` | Namespace, ResourceQuota, LimitRange |
| `-5` | ServiceAccount, Role, RoleBinding, Secret, ConfigMap |
| `0` | Deployment, Service |
| `5` | Route, Ingress, HPA |
| `10` | Post-deployment validation jobs |

### Senior warning

Automatic sync plus hooks can deploy automatically and also run jobs automatically. Be careful with destructive migration jobs. Database migrations should be idempotent, observable, and reviewed.

## 18. Sync Windows and Change Control

Sync windows define when syncs are allowed or denied.

Example: Deny automatic production sync during business hours, but allow manual override.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-prod
  namespace: openshift-gitops
spec:
  syncWindows:
    - kind: deny
      schedule: "0 9 * * 1-5"
      duration: 8h
      applications:
        - payment-api-prod
      manualSync: true
      timeZone: Asia/Kolkata
```

### Meaning

```text
Monday-Friday, from 09:00 for 8 hours:
  automatic sync denied
  manual sync allowed
```

### Production use cases

- Block production auto-sync during peak hours
- Allow auto-sync only during maintenance windows
- Freeze critical applications during audits
- Enable manual break-glass sync
- Prevent surprise changes during business events

## 19. Diff, Drift, and Reconciliation Noise

Automatic sync depends on diff detection. If Argo CD constantly sees differences, it may repeatedly mark applications OutOfSync.

### Common sources of drift

- HPA modifies replicas
- Operators mutate CR fields
- Admission webhooks add defaults
- OpenShift adds annotations
- Controllers update status-like fields in spec
- Helm chart renders random values
- Secrets generated with changing values
- Image tags use mutable tags such as `latest`

### ignoreDifferences example

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

### Senior recommendation

Do not blindly ignore differences. First understand why the field changes. Ignore only fields that are intentionally controlled outside Git.

## 20. Automatic Sync and Health Status

Argo CD tracks both sync status and health status.

| Status | Meaning |
|---|---|
| `Synced` | Desired manifests match live manifests |
| `OutOfSync` | Git and live cluster differ |
| `Healthy` | Resource health checks pass |
| `Progressing` | Resource is still rolling out |
| `Degraded` | Resource is failing or unhealthy |
| `Missing` | Tracked resource is missing |
| `Unknown` | Health cannot be determined |

### Important distinction

An application can be:

```text
Synced but Degraded
```

This means Argo CD applied the desired state, but the workload is unhealthy. Example:

- Deployment applied successfully
- Pods fail because of ImagePullBackOff
- Application is Synced but not Healthy

Automatic sync solves desired-state application, not application runtime correctness.

## 22. Security and Governance

Automatic sync can be powerful and risky. The real security boundary becomes Git plus Argo CD permissions.

### Controls required for enterprise use

| Control | Why it matters |
|---|---|
| Protected branches | Prevent unauthorized deployment commits |
| Pull request approval | Human review before cluster change |
| CI validation | Catch YAML, Helm, Kustomize, and policy errors |
| Image scanning | Prevent vulnerable image deployment |
| AppProject restrictions | Limit blast radius |
| Least privilege RBAC | Prevent cluster-wide compromise |
| Sync windows | Enforce change windows |
| Notifications | Alert on sync failures/degraded health |
| Audit logs | Trace who changed desired state |
| Secrets management | Avoid storing plaintext secrets in Git |

### Git becomes a production control plane

With automatic sync enabled:

```text
Who can merge to Git can indirectly deploy to OpenShift.
```

Therefore:

- Do not allow direct pushes to protected branches.
- Require review for production paths.
- Separate dev/stage/prod overlays.
- Separate application and cluster-admin repositories where needed.
- Use CODEOWNERS for sensitive paths.
- Avoid shared admin credentials.

### Secrets warning

Do not store plaintext production secrets in Git. Use secure patterns such as:

- Sealed Secrets
- External Secrets Operator
- Secrets Store CSI Driver
- Vault integration
- SOPS with KMS/GPG
- OpenShift trusted secret management patterns

## 23. Troubleshooting Automatic Sync

When automatic sync does not work, troubleshoot in this order.

### 1. Is the application OutOfSync?

```bash
oc get application <app> -n openshift-gitops -o wide
```

If it is `Synced`, auto-sync will not trigger.

### 2. Is automatic sync enabled?

```bash
oc get application <app> -n openshift-gitops -o yaml | yq '.spec.syncPolicy.automated'
```

Look for:

```yaml
enabled: true
```

or:

```yaml
{}
```

If you see:

```yaml
enabled: false
```

then auto-sync is disabled.

### 3. Is the app controlled by ApplicationSet?

```bash
oc get application <app> -n openshift-gitops -o jsonpath='{.metadata.ownerReferences}'
```

If ApplicationSet owns it, update the ApplicationSet template, not the generated Application.

### 4. Is a sync window blocking it?

```bash
argocd app get <app>
argocd proj windows list <project>
```

Check if a deny window is active.

### 5. Did a previous sync fail for the same revision?

Automatic sync may not keep retrying the same failed revision forever. Check history:

```bash
argocd app history <app>
argocd app get <app>
```

Fix the root cause and create a new Git commit or configure retry appropriately.

### 6. Does AppProject allow the source and destination?

```bash
oc get appproject <project> -n openshift-gitops -o yaml
```

Check:

- `sourceRepos`
- `destinations`
- resource whitelist/blacklist
- sync windows

### 7. Does Argo CD have OpenShift permissions?

Look for forbidden errors:

```bash
oc describe application <app> -n openshift-gitops
```

Check controller logs:

```bash
oc logs -n openshift-gitops \
  -l app.kubernetes.io/name=openshift-gitops-application-controller \
  --tail=200
```

If labels differ in your installation, find the controller pod:

```bash
oc get pods -n openshift-gitops | grep controller
```

### 8. Is the namespace manageable?

```bash
oc get namespace <target-namespace> --show-labels
```

For the default OpenShift GitOps instance, verify:

```text
argocd.argoproj.io/managed-by=openshift-gitops
```

### 9. Are manifests rendering correctly?

For Helm/Kustomize/path problems:

```bash
argocd app manifests <app>
argocd app diff <app>
```

Common causes:

- wrong `path`
- wrong `targetRevision`
- broken `kustomization.yaml`
- Helm values error
- missing chart dependency
- inaccessible Git repository

### 10. Are OpenShift admission policies blocking resources?

Check resource events:

```bash
oc get events -n <target-namespace> --sort-by=.lastTimestamp
```

Check workload status:

```bash
oc get pods -n <target-namespace>
oc describe pod <pod> -n <target-namespace>
```

## 25. Common Failure Scenarios

### Scenario 1: Auto-sync enabled but nothing deploys

Possible causes:

- Application is not OutOfSync
- `enabled: false`
- Sync window is blocking
- Previous failed sync for the same revision
- ApplicationSet overwrites the setting
- AppProject denies source/destination
- Git repo cannot be accessed
- Manifest generation failed

### Scenario 2: Application OutOfSync repeatedly

Possible causes:

- HPA changing replicas
- Operator mutating resources
- Webhook defaulting fields
- Random Helm template output
- Unsupported ignored differences
- Resource tracking issue

Fix:

- Make manifests deterministic
- Use `ignoreDifferences` carefully
- Use `RespectIgnoreDifferences=true` when needed
- Avoid mutable image tags

### Scenario 3: Auto-prune deleted too much

Possible causes:

- Wrong Git path
- Empty rendered output
- `allowEmpty: true`
- Generator removed resources unintentionally
- App path restructure not reviewed

Prevention:

- Keep `allowEmpty: false`
- Require PR reviews for production
- Use `Prune=confirm` for critical resources
- Use `PruneLast=true`
- Review diffs before enabling prune

### Scenario 4: Sync succeeds but pods fail

Possible causes:

- ImagePullBackOff
- SCC violation
- missing Secret/ConfigMap
- bad environment variable
- ResourceQuota exceeded
- LimitRange violation
- insufficient node resources
- NetworkPolicy blocking dependencies

Argo CD applies manifests, but OpenShift still controls runtime scheduling, admission, and pod lifecycle.

### Scenario 5: Namespace creation fails

Possible causes:

- Missing `CreateNamespace=true`
- AppProject does not allow namespace destination
- Argo CD lacks permission to create namespace
- Namespace already exists but lacks managed label
- Cluster policy blocks namespace creation

### Scenario 6: CRD-related sync failure

Example error:

```text
the server could not find the requested resource
```

Possible causes:

- Custom resource applied before CRD exists
- Operator not ready
- CRD is installed in another application that has not synced yet

Fix:

- Put CRDs/operators in earlier waves
- Split platform and application apps
- Use app-of-apps ordering
- Use `SkipDryRunOnMissingResource=true` only when appropriate

### Scenario 7: Manual cluster fix gets reverted

Cause:

- `selfHeal: true`

Correct process:

- Commit the emergency fix to Git
- Or temporarily disable auto-sync/self-heal
- Or patch Git desired state first, then let Argo CD apply it

## 26. Senior Admin Best Practices

### 1. Treat Git as the source of truth

Never make long-lived manual cluster changes. If a change must persist, commit it to Git.

### 2. Use explicit auto-sync settings

Prefer:

```yaml
automated:
  enabled: true
  prune: true
  selfHeal: true
  allowEmpty: false
```

instead of:

```yaml
automated: {}
```

Explicit settings are better for audit and review.

### 3. Be careful with prune in production

Use:

```yaml
allowEmpty: false
PruneLast=true
Prune=confirm
```

where appropriate.

### 4. Use AppProjects seriously

Do not use the unrestricted `default` AppProject for production.

### 5. Separate environments

Use overlays:

```text
apps/payment-api/base
apps/payment-api/overlays/dev
apps/payment-api/overlays/stage
apps/payment-api/overlays/prod
```

### 6. Avoid mutable image tags

Avoid:

```yaml
image: payment-api:latest
```

Prefer immutable tags or digests:

```yaml
image: payment-api@sha256:<digest>
```

or:

```yaml
image: payment-api:v1.4.18
```

### 7. Validate before merge

CI should run:

```bash
kustomize build overlays/prod
helm template ...
kubeconform ...
conftest test ...
oc apply --dry-run=server -f ...
```

### 8. Use sync waves for dependencies

Do not rely on alphabetical resource ordering.

### 9. Make hooks idempotent

PreSync and PostSync jobs may run again. Design them safely.

### 10. Monitor Argo CD itself

Watch:

- Application sync status
- Application health status
- Application controller logs
- repo-server errors
- Git access failures
- sync duration
- repeated OutOfSync loops
- Kubernetes API throttling

### 11. Use notifications

Notify teams on:

- sync failed
- health degraded
- app out of sync for too long
- sync succeeded in production
- app deleted/pruned

### 12. Understand rollback in GitOps

With auto-sync enabled, rollback is usually a Git revert or a commit that restores previous desired state. Avoid doing ad-hoc live cluster rollback while auto-sync is still enforcing Git.

## 28. Interview / Real-World Questions

### Q1. What is automatic sync in Argo CD?

Automatic sync is the Argo CD behavior that automatically applies Git desired state to the target cluster when an application is OutOfSync.

### Q2. Does automatic sync delete resources removed from Git?

Only if automatic pruning is enabled with:

```yaml
prune: true
```

### Q3. Does automatic sync correct manual changes in the cluster?

Only if self-healing is enabled:

```yaml
selfHeal: true
```

### Q4. Why is `allowEmpty` dangerous?

Because if Git renders zero resources and `allowEmpty: true` with pruning enabled, Argo CD may delete all previously managed resources for the application.

### Q5. Why might an app be Synced but unhealthy?

Because sync status means desired manifests were applied. Health status depends on runtime state, such as pods becoming ready, routes working, PVCs binding, and deployments progressing.

### Q6. Why does auto-sync not happen even though the app is OutOfSync?

Possible causes include disabled auto-sync, active sync window, failed previous sync for same revision, AppProject denial, ApplicationSet overwrite, manifest generation failure, or missing OpenShift RBAC.

### Q7. How do you stop auto-sync temporarily?

Declaratively:

```yaml
syncPolicy:
  automated:
    enabled: false
```

### Q8. How should rollback work with auto-sync enabled?

Prefer Git revert or a new Git commit restoring the previous desired state. Avoid manually changing live resources because self-healing may revert those changes.

### Q9. How do sync waves help automatic sync?

They control resource order. For example, namespaces and quotas first, RBAC and secrets next, deployments later, routes and smoke tests after that.

### Q10. What is the difference between prune and selfHeal?

| Feature | Purpose |
|---|---|
| `prune` | Deletes resources that were removed from Git |
| `selfHeal` | Reverts live cluster drift back to Git |

## Final Senior-Level Summary

Automatic Sync is not only a convenience feature. In OpenShift GitOps, it is a production reconciliation mechanism. It changes the operating model from manual deployment to continuous Git-based enforcement.

For a 10-year OpenShift administrator, the key is not just knowing how to set:

```yaml
syncPolicy:
  automated: {}
```

The real skill is knowing when to combine it with:

```yaml
prune: true
selfHeal: true
allowEmpty: false
syncOptions:
  - PruneLast=true
  - RespectIgnoreDifferences=true
  - CreateNamespace=true
```

and when to restrict it with:

- AppProjects
- RBAC
- sync windows
- branch protection
- approvals
- notifications
- sync waves
- hooks
- diff customizations
- OpenShift security policies

Automatic Sync should be treated as a controlled production automation system, not just a checkbox in the Argo CD UI.
