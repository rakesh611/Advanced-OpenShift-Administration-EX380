## 1. What LDAP Integration Means in OpenShift

LDAP integration in OpenShift means connecting the OpenShift OAuth authentication layer to an external LDAP-compatible directory such as:

- Microsoft Active Directory
- Red Hat Identity Management / FreeIPA
- 389 Directory Server
- OpenLDAP
- Enterprise LDAP appliances

The purpose is to avoid local user management inside OpenShift and instead use the enterprise directory as the central identity source.

In a production OpenShift environment, LDAP integration normally covers two different areas:

| Area | Purpose | OpenShift Component |
|---|---|---|
| User authentication | Validate username and password against LDAP | `OAuth` custom resource with `type: LDAP` |
| Group-based authorization | Sync LDAP groups into OpenShift groups | `oc adm groups sync` with `LDAPSyncConfig` |

These are related but separate. A user can authenticate through LDAP even if LDAP groups are not synchronized. However, for enterprise RBAC, LDAP group sync is usually required because permissions should be assigned to groups, not individual users.

### Senior Admin View

A 10-year experienced OpenShift administrator should not treat LDAP as only a login configuration. You must design the full identity lifecycle:

1. Who can log in?
2. Which LDAP attribute becomes the OpenShift username?
3. Which LDAP attribute becomes the immutable identity?
4. How are groups synchronized?
5. How are synced groups mapped to OpenShift RBAC?
6. How are disabled users handled?
7. How are deleted LDAP groups pruned?
8. How is authentication monitored?
9. How is break-glass access preserved?
10. How is the integration rolled back safely?

## 2. Enterprise Authentication Architecture

A typical enterprise OpenShift LDAP architecture looks like this:

```text
User / Admin
    |
    |  oc login / Web Console login
    v
OpenShift OAuth Server
    |
    |  LDAP search + simple bind
    v
LDAP / Active Directory Server
    |
    |  Search user entry
    |  Validate password using bind
    v
OpenShift Identity + User Object
    |
    |  RBAC evaluation
    v
OpenShift API Server Authorization
```

### Important Components

| Component | Role |
|---|---|
| OpenShift OAuth Server | Authenticates users through configured identity providers |
| OAuth CR | Cluster-wide authentication provider configuration |
| LDAP Server | Source of enterprise users and optionally groups |
| Secret in `openshift-config` | Stores LDAP bind password |
| ConfigMap in `openshift-config` | Stores LDAP CA certificate bundle |
| User object | OpenShift representation of the person or identity principal |
| Identity object | Mapping between external identity provider and OpenShift user |
| Group object | OpenShift group used in RBAC bindings |
| RoleBinding / ClusterRoleBinding | Grants namespace or cluster permissions |

### Authentication vs Authorization

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What are you allowed to do?
```

LDAP identity provider configuration solves authentication. RBAC with synced LDAP groups solves authorization.

## 3. Important OpenShift Identity Objects

OpenShift uses Kubernetes-style API objects for users and groups.

### User Object

A `User` object represents the OpenShift user.

```bash
oc get users
oc get user <username> -o yaml
```

Example:

```yaml
apiVersion: user.openshift.io/v1
kind: User
metadata:
  name: rakesh
fullName: Rakesh Kumar Jha
identities:
- ldapidp:uid=rakesh,ou=users,dc=example,dc=com
```

### Identity Object

An `Identity` object maps an external provider identity to an OpenShift user.

```bash
oc get identities
oc get identity ldapidp:<identity-value> -o yaml
```

Example:

```yaml
apiVersion: user.openshift.io/v1
kind: Identity
metadata:
  name: ldapidp:uid=rakesh,ou=users,dc=example,dc=com
providerName: ldapidp
providerUserName: uid=rakesh,ou=users,dc=example,dc=com
user:
  name: rakesh
```

### Group Object

A `Group` object contains users and is used for RBAC.

```bash
oc get groups
oc get group openshift-admins -o yaml
```

Example:

```yaml
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  name: openshift-admins
users:
- rakesh@example.com
- admin@example.com
```

### Senior-Level Point

LDAP authentication does not automatically grant permissions. A user can log in but still have almost no access until RBAC is assigned. In production, assign permissions to OpenShift groups synchronized from LDAP.

## 4. LDAP Authentication Flow in OpenShift

When a user runs:

```bash
oc login -u rakesh
```

OpenShift performs these steps:

1. OpenShift OAuth server receives username and password.
2. OAuth server builds an LDAP search filter using the configured LDAP URL.
3. LDAP directory is searched for a matching user entry.
4. If the search returns zero entries, login fails.
5. If the search returns more than one entry, login fails.
6. If exactly one entry is found, OpenShift attempts a simple bind using that user DN and the provided password.
7. If bind succeeds, OpenShift builds identity information from configured LDAP attributes.
8. OpenShift maps the external identity to an OpenShift `User` object.
9. OAuth token is issued.
10. Kubernetes/OpenShift RBAC evaluates what that user can do.

### Example Flow

LDAP URL:

```text
ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(enabled=true)
```

User logs in as:

```text
rakesh
```

Search filter becomes:

```text
(&(enabled=true)(uid=rakesh))
```

If LDAP returns:

```text
dn: uid=rakesh,ou=users,dc=example,dc=com
cn: Rakesh Kumar Jha
uid: rakesh
mail: rakesh@example.com
```

OpenShift attempts bind as:

```text
uid=rakesh,ou=users,dc=example,dc=com
```

with the password entered by the user.

## 5. LDAP vs Active Directory vs IdM vs OIDC

| Technology | What It Is | OpenShift Integration Pattern |
|---|---|---|
| LDAP | Protocol for directory access | `type: LDAP` identity provider |
| OpenLDAP / 389 DS | LDAP directory server | LDAP identity provider + RFC2307 group sync |
| Microsoft Active Directory | Directory service that supports LDAP/Kerberos | LDAP identity provider + AD group sync |
| Red Hat IdM / FreeIPA | Linux identity management based on LDAP/Kerberos/PKI | LDAP identity provider or OIDC/SAML through IdP front end |
| OIDC | Modern token-based identity federation | `type: OpenID` identity provider |
| SAML | Enterprise SSO protocol | Usually through external IdP/proxy, not direct native LDAP provider |

### LDAP Provider vs OIDC Provider

LDAP provider is simple username/password validation against a directory. OIDC is usually preferred for modern enterprise SSO because it supports MFA, conditional access, centralized login policy, and federation.

However, LDAP is still common in internal/private clusters, disconnected environments, lab environments, and organizations where AD/LDAP is the only available enterprise identity source.

### Senior Recommendation

For large production enterprises, prefer this hierarchy:

1. OIDC/SAML through enterprise IdP if MFA and SSO are mandatory.
2. LDAP/LDAPS direct integration if the enterprise directory is authoritative and SSO is not required.
3. HTPasswd only for bootstrap, lab, or emergency users.

## 6. Pre-Implementation Design Checklist

Before touching the OpenShift OAuth CR, collect these details.

### LDAP Server Details

| Item | Example |
|---|---|
| LDAP hostname | `ldap.example.com` |
| LDAP port | `389` for LDAP, `636` for LDAPS |
| Protocol | `ldap://` or `ldaps://` |
| Base DN for users | `ou=users,dc=example,dc=com` |
| Base DN for groups | `ou=groups,dc=example,dc=com` |
| Bind DN | `cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com` |
| Bind password | Stored in OpenShift Secret |
| CA certificate | Stored in ConfigMap as `ca.crt` |
| User search attribute | `uid`, `sAMAccountName`, `userPrincipalName`, or `mail` |
| Display name attribute | `cn`, `displayName` |
| Email attribute | `mail` |
| Unique identity attribute | `dn`, `entryUUID`, `objectGUID`, or immutable enterprise ID |

### Critical Design Questions

#### 1. Which username will users type?

Examples:

```text
rakesh
rakesh@example.com
DOMAIN\rakesh
```

Most OpenShift environments prefer one of these:

- `uid` for Linux LDAP
- `sAMAccountName` for Active Directory short names
- `userPrincipalName` or `mail` for email-style login

#### 2. Which attribute is immutable?

For `attributes.id`, avoid a value that can change easily. If the identity value changes, OpenShift sees the same person as a new user.

Good candidates:

| Directory | Better Identity Attribute |
|---|---|
| OpenLDAP / 389 DS | `entryUUID` if available, otherwise `dn` |
| Active Directory | `objectGUID` or carefully selected DN/UPN depending on policy |
| Simple lab | `dn` |

#### 3. Will disabled LDAP accounts still match the search filter?

You should filter out disabled users at LDAP search level if possible.

Example for generic LDAP:

```text
(enabled=true)
```

Example for Active Directory is more complex because disabled status is in `userAccountControl`. Many enterprises use a directory group, OU, or custom attribute to simplify filtering.

#### 4. Do you need group-based RBAC?

The answer for enterprise is almost always yes.

Good RBAC model:

```text
LDAP group -> OpenShift group -> RoleBinding / ClusterRoleBinding
```

Bad RBAC model:

```text
Individual users -> direct ClusterRoleBinding
```

## 7. LDAP URL and Search Filter Design

OpenShift LDAP identity provider uses an RFC2255-style LDAP URL.

Format:

```text
ldap://host:port/baseDN?attribute?scope?filter
```

For LDAPS:

```text
ldaps://host:636/baseDN?attribute?scope?filter
```

### Components

| Component | Meaning | Example |
|---|---|---|
| Scheme | LDAP or LDAPS | `ldap`, `ldaps` |
| Host | LDAP server | `ldap.example.com` |
| Port | LDAP port | `389`, `636` |
| Base DN | Search starting point | `ou=users,dc=example,dc=com` |
| Attribute | Attribute matched with username | `uid` |
| Scope | Search scope | `one` or `sub` |
| Filter | Extra LDAP filter | `(objectClass=person)` |

### Example: Basic OpenLDAP URL

```text
ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid
```

This means:

- Connect to `ldap.example.com` using LDAPS
- Search below `ou=users,dc=example,dc=com`
- Match user input against `uid`
- Use default subtree search and default object filter

### Example: Filter Only Human Users

```text
ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(objectClass=inetOrgPerson)
```

Final search filter for login `rakesh`:

```text
(&(objectClass=inetOrgPerson)(uid=rakesh))
```

### Example: Active Directory with `sAMAccountName`

```text
ldaps://ad.example.com/DC=example,DC=com?sAMAccountName?sub?(objectClass=user)
```

### Example: Active Directory with Email Login

```text
ldaps://ad.example.com/DC=example,DC=com?userPrincipalName?sub?(objectClass=user)
```

Login:

```bash
oc login -u rakesh@example.com
```

### Scope: `one` vs `sub`

| Scope | Meaning | When to Use |
|---|---|---|
| `one` | Search only one level below base DN | Strict OU layout |
| `sub` | Search entire subtree | Most common enterprise setup |

### Best Practice

Use a base DN that is narrow enough to avoid duplicate matches and unnecessary LDAP load.

Bad:

```text
ldaps://ad.example.com/DC=example,DC=com?sAMAccountName?sub?(objectClass=user)
```

Better:

```text
ldaps://ad.example.com/OU=Employees,DC=example,DC=com?sAMAccountName?sub?(objectClass=user)
```

Best when possible:

```text
ldaps://ad.example.com/OU=OpenShiftUsers,OU=Employees,DC=example,DC=com?sAMAccountName?sub?(&(objectClass=user)(memberOf=CN=OCP-Login,OU=Groups,DC=example,DC=com))
```

Be careful with complex filters. Test with `ldapsearch` before configuring OpenShift.

## 8. Secure LDAP: TLS, LDAPS, StartTLS, CA Bundle

For production, do not send credentials over clear-text LDAP.

OpenShift LDAP identity provider supports secure behavior through:

- `ldaps://` URL with TLS from the beginning of the connection
- `ldap://` URL with TLS upgrade when `insecure: false`
- Custom CA certificate bundle through a ConfigMap

### `insecure` Behavior

| Setting | Behavior |
|---|---|
| `insecure: true` | No TLS connection is made to LDAP server |
| `insecure: false` + `ldaps://` | Connects using TLS |
| `insecure: false` + `ldap://` | LDAP connection is upgraded to TLS |

### CA Bundle Requirement

If LDAP server certificate is signed by an internal CA, OpenShift must trust that CA.

Create ConfigMap:

```bash
oc create configmap ca-config-map \
  --from-file=ca.crt=/path/to/ldap-ca.crt \
  -n openshift-config
```

The key must be named:

```text
ca.crt
```

Example YAML:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ca-config-map
  namespace: openshift-config
data:
  ca.crt: |
    -----BEGIN CERTIFICATE-----
    <CA_CERTIFICATE_CONTENT>
    -----END CERTIFICATE-----
```

### Validate TLS Before OpenShift Configuration

From an admin host that can reach LDAP:

```bash
openssl s_client -connect ldap.example.com:636 -showcerts
```

Check:

```text
Verify return code: 0 (ok)
```

For StartTLS-style check:

```bash
openssl s_client -connect ldap.example.com:389 -starttls ldap -showcerts
```

Use `ldapsearch`:

```bash
LDAPTLS_CACERT=/path/to/ldap-ca.crt \
ldapsearch -H ldaps://ldap.example.com:636 \
  -D "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com" \
  -W \
  -b "ou=users,dc=example,dc=com" \
  "(uid=rakesh)" dn cn uid mail
```

### Common TLS Mistakes

| Mistake | Symptom |
|---|---|
| Missing CA bundle | Login fails, OAuth logs show certificate unknown |
| Wrong key name in ConfigMap | Identity provider not honored or TLS verification fails |
| Hostname mismatch | Certificate valid but not for LDAP hostname |
| Using IP with hostname-only certificate | TLS verification fails |
| `insecure: true` with `ldaps://` | Invalid design; use `insecure: false` |

## 9. Configure LDAP Identity Provider in OpenShift

### Step 1: Keep Break-Glass Admin Access

Before changing LDAP, ensure you have a working cluster-admin path.

Options:

- Keep `kubeadmin` until LDAP admin login is validated.
- Maintain an emergency `htpasswd` identity provider.
- Keep a documented kubeconfig for recovery.

Check current OAuth configuration:

```bash
oc get oauth cluster -o yaml
```

Check cluster-admin bindings:

```bash
oc get clusterrolebinding -o wide | grep -E 'cluster-admin|admin'
```

### Step 2: Create LDAP Bind Secret

If LDAP requires an authenticated search, create a secret.

```bash
oc create secret generic ldap-secret \
  --from-literal=bindPassword='YourStrongBindPasswordHere' \
  -n openshift-config
```

Important:

```text
The key must be bindPassword.
```

Verify:

```bash
oc get secret ldap-secret -n openshift-config
```

Do not print production secret values on screen unless required.

### Step 3: Create CA ConfigMap

```bash
oc create configmap ca-config-map \
  --from-file=ca.crt=/root/ldap-ca.crt \
  -n openshift-config
```

Verify:

```bash
oc get configmap ca-config-map -n openshift-config -o yaml
```

### Step 4: Create OAuth LDAP CR

File: `oauth-ldap.yaml`

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: ldapidp
    mappingMethod: claim
    type: LDAP
    ldap:
      attributes:
        id:
        - dn
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
      bindDN: "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com"
      bindPassword:
        name: ldap-secret
      ca:
        name: ca-config-map
      insecure: false
      url: "ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(objectClass=inetOrgPerson)"
```

Apply:

```bash
oc apply -f oauth-ldap.yaml
```

### Step 5: Watch OAuth Operator

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc get pods -n openshift-authentication-operator
```

Watch rollout:

```bash
oc get pods -n openshift-authentication -w
```

Check operator logs:

```bash
oc logs -n openshift-authentication-operator deploy/authentication-operator
```

Check OAuth server logs:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift
```

### Step 6: Test Login

```bash
oc login -u rakesh
oc whoami
oc get user rakesh -o yaml
oc get identities | grep ldapidp
```

### Step 7: Verify Access

```bash
oc auth can-i get pods
oc auth can-i create projects
oc auth can-i '*' '*' --all-namespaces
```

If login works but access is denied, authentication is successful and RBAC must be configured.

## 10. Example 1: OpenLDAP / 389 Directory Server Integration

Assume user entries:

```ldif
dn: uid=rakesh,ou=users,dc=example,dc=com
objectClass: inetOrgPerson
uid: rakesh
cn: Rakesh Kumar Jha
sn: Jha
mail: rakesh@example.com
```

### Test LDAP Search

```bash
ldapsearch -x \
  -H ldaps://ldap.example.com:636 \
  -D "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com" \
  -W \
  -b "ou=users,dc=example,dc=com" \
  "(&(objectClass=inetOrgPerson)(uid=rakesh))" \
  dn uid cn mail
```

Expected one result only.

### OAuth Config

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: openldap
    mappingMethod: claim
    type: LDAP
    ldap:
      attributes:
        id:
        - dn
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
      bindDN: "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com"
      bindPassword:
        name: ldap-secret
      ca:
        name: ca-config-map
      insecure: false
      url: "ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(objectClass=inetOrgPerson)"
```

### Notes for 389 Directory Server

For Red Hat Directory Server / 389 DS, common attributes include:

| Purpose | Attribute |
|---|---|
| Login | `uid` |
| Display name | `cn` |
| Email | `mail` |
| Immutable ID | `entryUUID` or `dn` |
| Group membership | `member`, `uniqueMember`, or `memberUid` depending on schema |

If `entryUUID` exists, consider using it for `attributes.id`:

```yaml
attributes:
  id:
  - entryUUID
```

This prevents identity breakage if the user's DN changes.

### AD Disabled Account Filter

AD disabled flag is inside `userAccountControl`. A common LDAP matching filter for enabled users excludes disabled accounts:

```text
(!(userAccountControl:1.2.840.113556.1.4.803:=2))
```

Example URL:

```text
ldaps://ad.example.com/DC=example,DC=com?sAMAccountName?sub?(&(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))
```

Test the filter carefully with `ldapsearch`. LDAP URL escaping can be error-prone.

## 12. Mapping Methods: claim, add, lookup, generate

`mappingMethod` controls how external identities are mapped to OpenShift `User` objects.

### Common Mapping Methods

| Method | Behavior | Typical Use |
|---|---|---|
| `claim` | Claims the preferred username if not already mapped | Most common production use |
| `add` | Adds identity to an existing user if username already exists | Useful when migrating identity providers |
| `lookup` | Only allows login if User and Identity already exist | Whitelist / pre-provisioned users |
| `generate` | Generates unique usernames to avoid conflicts | Rare for enterprise LDAP |

### `claim`

This is common for LDAP. First successful login creates User and Identity objects if no conflict exists.

```yaml
mappingMethod: claim
```

Use when:

- LDAP is trusted source.
- You want automatic user provisioning.
- Username collisions are controlled.

Risk:

- If two identity providers provide same preferred username, conflict may happen.

### `lookup`

`lookup` requires pre-created `User` and `Identity` objects. It is useful when only approved users should log in.

```yaml
mappingMethod: lookup
```

Use when:

- You need strict login whitelist.
- Only selected LDAP users can access OpenShift.
- You pre-provision identities through automation.

Operational impact:

- Users cannot log in until admin creates mappings.
- Good for restricted clusters.
- More operational overhead.

### Example Pre-Created Identity for `lookup`

```yaml
apiVersion: user.openshift.io/v1
kind: User
metadata:
  name: rakesh
identities:
- ldapidp:uid=rakesh,ou=users,dc=example,dc=com
---
apiVersion: user.openshift.io/v1
kind: Identity
metadata:
  name: ldapidp:uid=rakesh,ou=users,dc=example,dc=com
providerName: ldapidp
providerUserName: uid=rakesh,ou=users,dc=example,dc=com
user:
  name: rakesh
  uid: ""
```

In real production, generate this carefully from actual OpenShift object output or automation.

## 13. LDAP Group Synchronization

LDAP group sync brings LDAP groups into OpenShift as `Group` objects.

This enables group-based RBAC:

```text
LDAP group: CN=OCP-Cluster-Admins,OU=Groups,DC=example,DC=com
        |
        v
OpenShift group: ocp-cluster-admins
        |
        v
ClusterRoleBinding: cluster-admin
```

### Supported Group Sync Schemas

OpenShift supports these common LDAP group sync schemas:

| Schema | Common Directory | Membership Style |
|---|---|---|
| RFC2307 | OpenLDAP, 389 DS, Unix-style LDAP | Group entries list members or member UIDs |
| Active Directory | Microsoft AD | User entries contain `memberOf` |
| Augmented Active Directory | AD with more group query control | Queries users and groups |

### Why Group Sync Is Separate from Login

LDAP login validates credentials. It does not dynamically import all groups into the user token the way OIDC can. For LDAP-based RBAC, OpenShift groups must be synced separately.

### Group Sync Command

Dry-run first:

```bash
oc adm groups sync --sync-config=config.yaml
```

Apply changes:

```bash
oc adm groups sync --sync-config=config.yaml --confirm
```

Sync existing OpenShift groups only:

```bash
oc adm groups sync --type=openshift --sync-config=config.yaml --confirm
```

Sync subset with whitelist:

```bash
oc adm groups sync --whitelist=whitelist.txt --sync-config=config.yaml --confirm
```

Prune deleted groups:

```bash
oc adm prune groups --sync-config=config.yaml --confirm
```

### Senior-Level Best Practice

Never sync the entire enterprise directory without a whitelist or narrow group search base. Large AD environments can contain thousands of groups. Syncing everything can create noise, performance impact, and security confusion.

## 14. RFC2307 Group Sync Example

RFC2307 is common in OpenLDAP, 389 Directory Server, and Unix-style LDAP.

### Example Group Entry

```ldif
dn: cn=ocp-admins,ou=groups,dc=example,dc=com
objectClass: groupOfNames
cn: ocp-admins
member: uid=rakesh,ou=users,dc=example,dc=com
member: uid=admin1,ou=users,dc=example,dc=com
```

### Example User Entry

```ldif
dn: uid=rakesh,ou=users,dc=example,dc=com
objectClass: inetOrgPerson
uid: rakesh
cn: Rakesh Kumar Jha
mail: rakesh@example.com
```

### Sync Config

File: `rfc2307_config.yaml`

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ldap.example.com:636
insecure: false
ca: /etc/ldap-ca/ca.crt
bindDN: cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com
bindPassword:
  file: /etc/secrets/bindPassword
rfc2307:
  groupsQuery:
    baseDN: "ou=groups,dc=example,dc=com"
    scope: sub
    derefAliases: never
    filter: "(cn=ocp-*)"
    pageSize: 0
  groupUIDAttribute: dn
  groupNameAttributes:
  - cn
  groupMembershipAttributes:
  - member
  usersQuery:
    baseDN: "ou=users,dc=example,dc=com"
    scope: sub
    derefAliases: never
    filter: "(objectClass=inetOrgPerson)"
    pageSize: 0
  userUIDAttribute: dn
  userNameAttributes:
  - uid
```

### Run Sync

```bash
oc adm groups sync --sync-config=rfc2307_config.yaml
```

If output is correct:

```bash
oc adm groups sync --sync-config=rfc2307_config.yaml --confirm
```

Verify:

```bash
oc get groups
oc get group ocp-admins -o yaml
```

### User-Defined Group Name Mapping

If LDAP group DN is ugly but OpenShift group should be readable:

```yaml

  "cn=ocp-admins,ou=groups,dc=example,dc=com": "openshift-admins"
```

## 15. Active Directory Group Sync Example

Active Directory often stores group membership on the user object through `memberOf`.

### Example User Attributes

```text
dn: CN=Rakesh Jha,OU=Users,DC=example,DC=com
sAMAccountName: rakesh
userPrincipalName: rakesh@example.com
mail: rakesh@example.com
memberOf: CN=OCP-Admins,OU=Groups,DC=example,DC=com

```

### Active Directory Sync Config

File: `active_directory_config.yaml`

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636

bindDN: CN=openshift-bind,OU=Service Accounts,DC=example,DC=com

  file: /etc/secrets/bindPassword
activeDirectory:
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(&(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))"
    pageSize: 0
  userNameAttributes:
  - userPrincipalName
  groupMembershipAttributes:
  - memberOf
```

### Run Sync

Dry-run:

```bash
oc adm groups sync --sync-config=active_directory_config.yaml
```

Apply:

```bash
oc adm groups sync --sync-config=active_directory_config.yaml --confirm
```

Verify:

```bash
oc get groups
oc get group OCP-Admins -o yaml
```

### Whitelist AD Groups

Create `whitelist.txt`:

```text
CN=OCP-Admins,OU=Groups,DC=example,DC=com
CN=OCP-Developers,OU=Groups,DC=example,DC=com
CN=OCP-Viewers,OU=Groups,DC=example,DC=com
```

Run:

```bash
oc adm groups sync \
  --sync-config=active_directory_config.yaml \
  --whitelist=whitelist.txt \
  --confirm
```

### Senior Note

For AD, confirm whether OpenShift group names will become full DNs or CNs. Long DN-based group names are difficult to manage in RBAC. Use name mapping or augmented AD schema if needed.

## 16. Augmented Active Directory Group Sync Example

Augmented AD sync is useful when you need better control over group query and group names.

### Sync Config

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636
insecure: false
ca: /etc/ldap-ca/ca.crt
bindDN: CN=openshift-bind,OU=Service Accounts,DC=example,DC=com
bindPassword:
  file: /etc/secrets/bindPassword
augmentedActiveDirectory:
  groupsQuery:
    baseDN: "OU=OpenShift Groups,OU=Groups,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(cn=OCP-*)"
    pageSize: 0
  groupUIDAttribute: dn
  groupNameAttributes:
  - cn
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(&(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))"
    pageSize: 0
  userNameAttributes:
  - userPrincipalName
  groupMembershipAttributes:
  - memberOf
```

### Why Use Augmented AD?

Use it when:

- You want group names as `cn` instead of full DN.
- You need group query filtering.
- You want to sync only groups from a specific OU.
- You want a clean OpenShift group naming convention.


### Namespace Edit Group

```bash
oc adm policy add-role-to-group edit openshift-app-prod-devs -n app-prod
```

### Namespace View Group

```bash
oc adm policy add-role-to-group view openshift-app-prod-viewers -n app-prod
```

### Recommended Group Naming Standard

| Purpose | LDAP Group | OpenShift Group |
|---|---|---|
| Cluster admins | `OCP-Cluster-Admins` | `ocp-cluster-admins` |
| Project admins | `OCP-App1-Admins` | `ocp-app1-admins` |
| Developers | `OCP-App1-Devs` | `ocp-app1-devs` |
| Read-only | `OCP-App1-Viewers` | `ocp-app1-viewers` |
| CI/CD service users | `OCP-App1-CICD` | `ocp-app1-cicd` |

Avoid:


Prefer:

```bash

```

- Easier audit
- Cleaner offboarding
- Less RBAC drift
- Better compliance
- Matches enterprise IAM process
- Easier automation

### CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: ldap-group-sync
  namespace: ldap-sync
spec:
  schedule: "*/30 * * * *"
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: ldap-group-syncer
          restartPolicy: Never
          containers:
          - name: ldap-group-sync
            image: quay.io/openshift/origin-cli:latest
            command:
            - /bin/bash
            - -c
            - oc adm groups sync --sync-config=/etc/config/sync.yaml --confirm
            volumeMounts:
            - mountPath: /etc/config
              name: ldap-sync-config
            - mountPath: /etc/secrets
              name: ldap-bind-password
              readOnly: true
            - mountPath: /etc/ldap-ca
              name: ldap-ca
              readOnly: true
          volumes:
          - name: ldap-sync-config
            configMap:
              name: ldap-group-syncer
          - name: ldap-bind-password
            secret:
              secretName: ldap-secret
          - name: ldap-ca
            configMap:
              name: ca-config-map
```

### Production Image Note

Use an OpenShift CLI image that matches or is compatible with your cluster version. Avoid unpinned `latest` in production if your organization requires deterministic deployments.

Example safer pattern:

```yaml
image: registry.redhat.io/openshift4/ose-cli:<version-compatible-tag>
```

Use the image available in your disconnected or enterprise registry.

```bash

oc get jobs -n ldap-sync
```

## 20. Troubleshooting LDAP Login Failures

### Symptom 1: Login Fails with Invalid Credentials

Command:

```bash
oc login -u rakesh
```

Error:

```text
Login failed (401 Unauthorized)
```

Possible causes:

| Cause | How to Check | Fix |
|---|---|---|
| Wrong password | Try LDAP bind with `ldapsearch` | Reset password or unlock account |
| Search filter returns no user | Run same LDAP filter manually | Fix baseDN, attribute, filter |
| Search filter returns multiple users | Use `ldapsearch` and count results | Use unique login attribute |
| Bind DN wrong | Test bind DN separately | Correct service account DN |
| Bind password wrong | Test bind password | Update OpenShift Secret |
| TLS failure | OAuth logs, `openssl s_client` | Fix CA or hostname |
| Disabled account filtered out | LDAP search returns zero | Correct account status or filter |

### Required Troubleshooting Commands

Check OAuth configuration:

```bash
oc get oauth cluster -o yaml
```

Check LDAP secret exists:

```bash
oc get secret ldap-secret -n openshift-config
```

Check CA ConfigMap:

```bash
oc get configmap ca-config-map -n openshift-config -o yaml
```

Check authentication operator:

```bash
oc get co authentication
oc describe co authentication
```

Check OAuth pods:

```bash
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

### Manual LDAP Search Test

OpenLDAP:

```bash
ldapsearch -x \
  -H ldaps://ldap.example.com:636 \
  -D "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com" \
  -W \
  -b "ou=users,dc=example,dc=com" \
  "(&(objectClass=inetOrgPerson)(uid=rakesh))" \
  dn uid cn mail
```

AD:

```bash
ldapsearch -x \
  -H ldaps://ad.example.com:636 \
  -D "CN=openshift-bind,OU=Service Accounts,DC=example,DC=com" \
  -W \
  -b "DC=example,DC=com" \
  "(&(objectClass=user)(sAMAccountName=rakesh))" \
  dn sAMAccountName userPrincipalName mail displayName
```

### Symptom 2: Authentication Operator Degraded

Check:

```bash
oc get co authentication
oc describe co authentication
oc logs -n openshift-authentication-operator deploy/authentication-operator
```

Common causes:

- OAuth CR invalid YAML
- Secret name mismatch
- ConfigMap name mismatch
- Missing `bindPassword` key
- CA bundle malformed
- Unsupported username characters
- Duplicate identity provider names

### Symptom 3: User Can Log In But Cannot See Projects

This is not LDAP failure. This is RBAC.

Check:

```bash
oc whoami
oc auth can-i get projects
oc get groups | grep -i ocp
oc get group <group-name> -o yaml
```

Fix:

```bash
oc adm policy add-role-to-group view <group-name> -n <namespace>
```

or:

```bash
oc adm policy add-cluster-role-to-group self-provisioner <group-name>
```

Use `self-provisioner` carefully because it allows project creation.

### Symptom 4: User Login Creates Wrong Username

Cause:

```yaml
preferredUsername:
- wrongAttribute
```

Check user object:

```bash
oc get user
oc get identity
```

Fix preferredUsername attribute. If wrong User/Identity objects were created, clean them carefully.

Example cleanup:

```bash
oc delete user wronguser
oc delete identity 'ldapidp:<identity-value>'
```

Be careful: deleting user identity mappings can disrupt RBAC references and audit continuity.

### Symptom 5: Duplicate User Conflict

Cause:

- Multiple identity providers return same preferred username.
- Existing local user conflicts with LDAP user.
- Mapping method `claim` cannot claim username already owned by another identity.

Check:

```bash
oc get users
oc get identities
oc get user <username> -o yaml
```

Possible fixes:

- Use different `preferredUsername` attribute.
- Use `add` during migration if appropriate.
- Clean stale users/identities after backup.
- Use `lookup` for strict manual mappings.

## 21. Troubleshooting Group Sync Failures

### Dry-Run First

Always run without `--confirm` first:

```bash
oc adm groups sync --sync-config=config.yaml
```

If dry-run output is wrong, do not use `--confirm`.

### Symptom 1: No Groups Returned

Possible causes:

| Cause | Check | Fix |
|---|---|---|
| Wrong group baseDN | `ldapsearch` group query | Correct baseDN |
| Filter too strict | Remove filter temporarily | Adjust filter |
| Bind DN lacks group read permission | Test with bind account | Delegate read access |
| Wrong schema type | Inspect LDAP entries | Use RFC2307/AD/augmented AD correctly |
| TLS failure | `openssl`, logs | Fix CA |

### Symptom 2: Groups Sync But Users Missing

Possible causes:

- `userUIDAttribute` does not match group member values.
- `userNameAttributes` points to missing attribute.
- Users query baseDN is wrong.
- Group membership attribute is wrong.

For RFC2307, check whether group uses:

```text
member
uniqueMember
memberUid
```

Example mismatch:

Group contains:

```text
memberUid: rakesh
```

But config expects:

```yaml
groupMembershipAttributes:
- member
userUIDAttribute: dn
```

Fix:

```yaml
groupMembershipAttributes:
- memberUid
userUIDAttribute: uid
```

### Symptom 3: Group Names Are Full DNs

Example:

```text
CN=OCP-Admins,OU=Groups,DC=example,DC=com
```

This is hard for RBAC commands.

Fix options:

- Use `groupUIDNameMapping`.
- Use augmented AD with `groupNameAttributes: [ cn ]`.
- Use a clean LDAP attribute for group names.

### Symptom 4: Group Sync Works Manually But CronJob Fails

Check:

```bash
oc get jobs -n ldap-sync
oc logs job/<job-name> -n ldap-sync
oc describe job/<job-name> -n ldap-sync
```

Possible causes:

| Cause | Fix |
|---|---|
| ServiceAccount lacks RBAC | Fix ClusterRole/ClusterRoleBinding |
| Secret missing in namespace | Copy secret to `ldap-sync` |
| ConfigMap missing | Create config map |
| CA file path mismatch | Match mounted path and `ca:` path |
| CLI image missing `oc` | Use proper OpenShift CLI image |
| NetworkPolicy blocks LDAP | Allow egress to LDAP |
| Proxy blocks LDAP | Configure proxy/no_proxy as needed |

### Symptom 5: Deleted LDAP Groups Still Exist in OpenShift

Group sync updates and creates groups. To remove stale groups, run prune:

```bash
oc adm prune groups --sync-config=config.yaml
```

Apply:

```bash
oc adm prune groups --sync-config=config.yaml --confirm
```

Use pruning carefully. Validate with dry-run and whitelist/blacklist where needed.

## 22. Security Hardening Best Practices

### 1. Use LDAPS or TLS Upgrade

Never use insecure LDAP for production credentials.

```yaml
insecure: false
```

### 2. Use Dedicated Bind Account

Do not use domain admin or personal account as Bind DN.

Good:

```text
CN=openshift-bind,OU=Service Accounts,DC=example,DC=com
```

Bad:

```text
CN=Administrator,CN=Users,DC=example,DC=com
```

### 3. Least Privilege for Bind Account

Bind account needs read-only access to required user and group attributes only.

### 4. Restrict Login Scope

Use narrow base DN and/or filter.

Bad:

```text
DC=example,DC=com
```

Better:

```text
OU=OpenShiftUsers,OU=Users,DC=example,DC=com
```

### 5. Filter Disabled Users

Do not allow disabled accounts to authenticate.

### 6. Use Groups for RBAC

Do not directly grant cluster-admin to individual users unless emergency.

### 7. Protect Secrets

```bash
oc get secret ldap-secret -n openshift-config
```

Avoid printing secret values:

```bash
oc get secret ldap-secret -n openshift-config -o yaml
```

Limit who can read secrets in `openshift-config`.

### 8. Rotate Bind Password

Recommended process:

1. Create new bind password in LDAP.
2. Update OpenShift Secret.
3. Restart/rollout OAuth if needed.
4. Test login.
5. Remove old password.

Update secret:

```bash
oc create secret generic ldap-secret \
  --from-literal=bindPassword='NewPassword' \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

### 9. Audit Login and RBAC

Useful commands:

```bash
oc get users
oc get identities
oc get groups
oc get clusterrolebindings -o wide
oc get rolebindings -A -o wide
```

### 10. Avoid Over-Syncing Groups

Use whitelist or group filters.

### 11. Preserve Break-Glass Access

Keep emergency access independent from LDAP outage.

### 12. Monitor Authentication Health

Monitor:

```bash
oc get co authentication
oc get pods -n openshift-authentication
```

Set alerts for authentication operator degraded state.

## 24. Disaster Recovery and Break-Glass Access

LDAP outages can block normal OpenShift logins. You must preserve emergency access.

### Option 1: Keep `kubeadmin` Until Enterprise Auth Is Stable

During initial setup, do not remove `kubeadmin` until LDAP login and RBAC are fully tested.

### Option 2: Emergency HTPasswd Provider

Example OAuth with both LDAP and htpasswd:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: emergency-local
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpasswd-secret
  - name: ldapidp
    mappingMethod: claim
    type: LDAP
    ldap:
      attributes:
        id:
        - dn
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
      bindDN: "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com"
      bindPassword:
        name: ldap-secret
      ca:
        name: ca-config-map
      insecure: false
      url: "ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(objectClass=inetOrgPerson)"
```

### Create HTPasswd Secret

```bash
htpasswd -c -B -b users.htpasswd emergency-admin 'StrongPassword'

oc create secret generic htpasswd-secret \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config
```

Grant emergency admin:

```bash
oc adm policy add-cluster-role-to-user cluster-admin emergency-admin
```

### Rollback OAuth CR

If LDAP change breaks login but you still have admin kubeconfig:

```bash
oc apply -f oauth-cluster-backup.yaml
```

Or edit:

```bash
oc edit oauth cluster
```

Monitor:

```bash
oc get co authentication
```

## 25. Real Interview Scenarios and Answers

### Scenario 1: User says LDAP login fails. How do you troubleshoot?

Answer:

I divide the issue into OpenShift OAuth configuration, LDAP search, LDAP bind, TLS, and RBAC. First, I check whether the authentication operator is healthy:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

Then I verify the OAuth CR:

```bash
oc get oauth cluster -o yaml
```

I confirm secret and CA objects exist in `openshift-config`:

```bash
oc get secret ldap-secret -n openshift-config
oc get configmap ca-config-map -n openshift-config
```

Then I reproduce the exact LDAP search using `ldapsearch`. The search must return exactly one user. If it returns zero, the baseDN/filter/attribute is wrong. If it returns multiple, the login attribute is not unique. If search works, I test simple bind and TLS certificate validation.

### Scenario 2: User can log in but cannot access any project.

Answer:

This means authentication is successful but authorization is missing. I check the user and groups:

```bash
oc whoami
oc get user <user> -o yaml
oc get groups
oc get group <expected-group> -o yaml
```

Then I check RBAC:

```bash
oc auth can-i get pods -n <namespace> --as=<user>
oc get rolebinding -n <namespace> -o wide
oc get clusterrolebinding -o wide
```

I fix by binding a role to the synced OpenShift group:

```bash
oc adm policy add-role-to-group edit <group> -n <namespace>
```

### Scenario 3: LDAP group sync returns groups but no users.

Answer:

This is usually schema mismatch. I inspect actual LDAP group entries and user entries. For RFC2307, I verify whether group membership uses `member`, `uniqueMember`, or `memberUid`. If group has `memberUid: rakesh`, then `userUIDAttribute` should normally be `uid`, not `dn`. If group has full DN members, `userUIDAttribute` should be `dn`.

Commands:

```bash
ldapsearch -x -H ldaps://ldap.example.com \
  -D '<bindDN>' -W \
  -b 'ou=groups,dc=example,dc=com' \
  '(cn=ocp-admins)' '*'
```

Then I correct `LDAPSyncConfig` and re-run dry-run before `--confirm`.

### Scenario 4: Authentication broke after applying LDAP OAuth CR.

Answer:

I use break-glass admin kubeconfig or existing kubeadmin session. I check operator status:

```bash
oc get co authentication
oc describe co authentication
oc logs -n openshift-authentication-operator deploy/authentication-operator
```

Common issues are invalid YAML, wrong secret name, missing `bindPassword` key, invalid CA, or bad LDAP URL. If immediate recovery is needed, I roll back:

```bash
oc apply -f oauth-cluster-backup.yaml
```

Then I fix and reapply during a controlled change window.

### Scenario 5: How do you restrict OpenShift login to only selected LDAP users?

Answer:

I prefer one of these approaches:

1. Put allowed users in a dedicated LDAP OU and use that as baseDN.
2. Use LDAP filter based on group membership or attribute.
3. Use `mappingMethod: lookup` and pre-create User/Identity objects.

For strict whitelisting, `lookup` is strongest because authentication is allowed only if OpenShift already has a matching User and Identity mapping.

### Scenario 6: How do you handle LDAP group deletion?

Answer:

Normal sync updates groups but stale groups may remain. I use prune after dry-run:

```bash
oc adm prune groups --sync-config=config.yaml
oc adm prune groups --sync-config=config.yaml --confirm
```

In production, I use whitelist and change approval before pruning because deleting groups can affect RBAC bindings and user access.

### Scenario 7: Which LDAP attribute should be used as OpenShift identity ID?

Answer:

I avoid mutable attributes like email or display name for identity ID. For OpenLDAP/389 DS, I prefer `entryUUID` if available. For AD, `objectGUID` is generally stable but may need special handling. In many practical configurations, `dn` is used, but it can change if users are moved between OUs. The final decision depends on directory policy and whether DN changes are expected.

### Scenario 8: How do you ensure LDAP integration is highly available?

Answer:

I do not point OpenShift to a single fragile LDAP host. I use a highly available LDAP endpoint, such as a load-balanced VIP or DNS name backed by multiple domain controllers. I ensure TLS certificate SANs match the DNS name. I also preserve break-glass access because even HA LDAP can fail due to network, certificate, DNS, or bind account issues.

### Scenario 9: How do you validate that LDAP is not allowing disabled users?

Answer:

I test disabled users explicitly with `ldapsearch` and `oc login`. For AD, I include a filter excluding disabled users using `userAccountControl`. For generic LDAP, I use an enterprise attribute such as `accountStatus=active` or membership in an allowed-login group. I document the filter and test it during change validation.

### Scenario 10: Why should RBAC be assigned to groups, not users?

Answer:

Group-based RBAC aligns OpenShift access with enterprise IAM. When users join or leave teams, the directory group changes and OpenShift access follows after sync. Direct user bindings create audit problems, orphaned permissions, and offboarding risk.

## 27. Common Mistakes

| Mistake | Impact | Correct Approach |
|---|---|---|
| Using insecure LDAP | Password exposure risk | Use LDAPS/TLS with `insecure: false` |
| Missing `bindPassword` key | Provider fails | Secret key must be `bindPassword` |
| CA ConfigMap key not `ca.crt` | TLS trust fails | Use key `ca.crt` |
| Using non-unique login attribute | Login denied due to multiple matches | Use unique attribute |
| Using mutable identity attribute | Duplicate users after rename/move | Use stable ID |
| Forgetting group sync | Users log in but have no access | Configure `oc adm groups sync` |
| Binding RBAC to users | Offboarding risk | Bind RBAC to groups |
| Syncing all AD groups | Noise and security risk | Use whitelist/filter/baseDN |
| No break-glass account | LDAP outage blocks admin access | Keep emergency admin path |
| Applying OAuth without backup | Hard rollback | Backup OAuth CR before changes |
| Running prune blindly | Access outage | Dry-run and whitelist first |
| Wrong AD schema choice | Missing groups/users | Inspect LDAP entries and choose correct schema |

## 28. Final Senior-Level Summary

LDAP integration in OpenShift is not only an authentication task. It is a full enterprise identity and access management design.

A senior OpenShift administrator should implement it in this order:

1. Confirm enterprise identity source and schema.
2. Design login attribute and immutable identity attribute.
3. Validate LDAP search and TLS outside OpenShift.
4. Create bind password secret and CA ConfigMap in `openshift-config`.
5. Configure OAuth LDAP identity provider.
6. Test user login.
7. Sync LDAP groups into OpenShift.
8. Map groups to RBAC using RoleBinding and ClusterRoleBinding.
9. Automate group sync with CronJob.
10. Monitor authentication health.
11. Preserve emergency access.
12. Document rollback and password rotation.

The key production rule is:

```text
LDAP authenticates users. OpenShift RBAC authorizes users. LDAP groups should drive RBAC through synchronized OpenShift groups.
```
