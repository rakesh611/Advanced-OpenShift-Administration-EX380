# Scheduled Group Sync in OpenShift

**Area:** Enterprise Authentication and Identity Management  
**Level:** Advanced OpenShift Administration / 10+ Years Experience  
**Focus:** Scheduled LDAP / Active Directory group synchronization into OpenShift groups for RBAC automation

---

## 1. What is Scheduled Group Sync?

**Scheduled group sync** means automatically synchronizing groups and group memberships from an external identity source, usually **LDAP**, **Microsoft Active Directory**, **FreeIPA**, or another LDAP-compatible directory, into OpenShift on a fixed schedule by using an OpenShift/Kubernetes `CronJob`.

In enterprise OpenShift environments, users normally authenticate through an external identity provider, but OpenShift authorization is usually controlled through **RBAC bindings** that reference OpenShift `Group` objects.

For example:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
oc adm policy add-role-to-group edit app1-dev-team -n app1-dev
oc adm policy add-role-to-group view app1-readonly-team -n app1-prod
```

The important point is this:

> LDAP authentication and LDAP group synchronization are related, but they are not the same thing.

LDAP authentication allows a user to log in. LDAP group sync imports or updates group membership into OpenShift so that RBAC can be applied to groups.

Without group sync, OpenShift may authenticate the user, but RBAC rules that depend on external directory groups will not automatically reflect LDAP or Active Directory group membership.

---

## 2. Why Scheduled Group Sync is Required in Enterprise OpenShift

In a small lab, an administrator might manually create OpenShift groups:

```bash
oc adm groups new app1-dev-team user1 user2 user3
```

In a real enterprise, this does not scale. Users join and leave teams every day. Security teams modify Active Directory groups. Contractors are removed. Application teams change. Compliance requires centralized access control.

Scheduled group sync solves this problem by making OpenShift consume group membership from the enterprise identity source at regular intervals.

Typical enterprise reasons:

| Requirement | Why Scheduled Sync Helps |
|---|---|
| Centralized access control | Group ownership stays in LDAP/AD/FreeIPA |
| RBAC automation | OpenShift roles are bound to synced groups |
| Reduced manual work | Admins do not manually add/remove users in OpenShift groups |
| Compliance | Access follows corporate directory membership |
| Faster offboarding | Removed users lose OpenShift group-based access after sync |
| Multi-cluster consistency | Same directory groups can be synced into many clusters |
| Auditability | Directory team owns membership; platform team owns RBAC |

## 3. Core Architecture

```text
+-----------------------------+
| Enterprise Directory         |
| LDAP / AD / FreeIPA          |
|                             |
| cn=ocp-admins               |
| cn=app1-dev-team            |
| cn=app1-readonly-team       |
+--------------+--------------+
               |
               | LDAP query
               v
+--------------+--------------+
| OpenShift CronJob            |
| Namespace: ldap-sync         |
| ServiceAccount: syncer       |
| oc adm groups sync           |
+--------------+--------------+
               |
               | Creates / updates OpenShift groups
               v
+--------------+--------------+
| OpenShift Group Objects      |
| user.openshift.io/v1 Group   |
+--------------+--------------+
               |
               | Used by RBAC
               v
+--------------+--------------+
| RoleBinding / ClusterRoleBinding |
| view / edit / admin / custom role |
+----------------------------------+
```

A scheduled sync solution normally contains these OpenShift resources:

| Resource | Purpose |
|---|---|
| `Project` / `Namespace` | Dedicated namespace such as `ldap-sync` |
| `ServiceAccount` | Identity used by the sync job |
| `ClusterRole` | Permissions to read/create/update OpenShift groups |
| `ClusterRoleBinding` | Binds the ClusterRole to the ServiceAccount |
| `Secret` | Stores LDAP bind password |
| `ConfigMap` | Stores LDAP sync configuration and optional whitelist/blacklist |
| `CronJob` | Runs `oc adm groups sync` on a schedule |
| Optional prune job | Removes orphaned OpenShift groups that no longer exist in LDAP |

## 4. Authentication vs Group Sync vs RBAC

Many administrators confuse these three layers. For advanced OpenShift administration, you must separate them clearly.

### 4.1 Authentication

Authentication answers:

> Who are you?

This is configured through the cluster OAuth configuration:

```bash
oc get oauth cluster -o yaml
```

Example identity providers:

- LDAP
- HTPasswd
- GitHub
- GitLab
- OpenID Connect
- Keycloak / Red Hat SSO
- Google
- Azure AD / Entra ID through OIDC

LDAP authentication allows the user to log in, but it does not automatically maintain OpenShift group membership.

### 4.2 Group Synchronization

Group synchronization answers:

> Which enterprise groups should exist in OpenShift and which users belong to them?

This is handled by:

```bash
oc adm groups sync --sync-config=/path/to/sync.yaml --confirm
```

It creates or updates OpenShift `Group` objects.

### 4.3 Authorization / RBAC

Authorization answers:

> What can this user or group do?

This is handled through `RoleBinding` and `ClusterRoleBinding` objects.

Example:

```bash
oc adm policy add-role-to-group edit app1-dev-team -n app1-dev
```

This means users in the synced OpenShift group `app1-dev-team` receive `edit` permission in namespace `app1-dev`.

## 5. OpenShift Group Object Internals

OpenShift groups are API objects under the `user.openshift.io` API group.

Check groups:

```bash
oc get groups
oc get group app1-dev-team -o yaml
```

Example output:

```yaml
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  name: app1-dev-team
users:
- alice@example.com
- bob@example.com
- charlie@example.com
```

The `users` field is what OpenShift RBAC evaluates when a user performs an action.

Important behavior:

- Group sync updates OpenShift group membership.
- RBAC bindings do not need to be recreated after every sync.
- If the OpenShift group name remains stable, existing `RoleBinding` and `ClusterRoleBinding` objects continue working.
- Usernames generated by LDAP sync must match the usernames produced by the identity provider login flow.

That last point is critical. If LDAP login creates user `alice`, but group sync imports `alice@example.com`, RBAC will not match correctly.

## 6. Supported LDAP Group Sync Schemas

OpenShift LDAP group sync supports three common schemas:

1. **RFC2307**
2. **Active Directory**
3. **Augmented Active Directory**

Choosing the wrong schema is one of the most common causes of empty synced groups.

---

## 7. RFC2307 Group Sync

RFC2307 is common in Linux/UNIX-style LDAP and FreeIPA-like environments.

### 7.1 Membership Model

In RFC2307, users and groups are separate LDAP entries. Group membership is usually stored in an attribute on the group.

Example group:

```ldif
dn: cn=app1-dev-team,ou=groups,dc=example,dc=com
objectClass: groupOfNames
cn: app1-dev-team
member: uid=alice,ou=users,dc=example,dc=com
member: uid=bob,ou=users,dc=example,dc=com
```

### 7.2 RFC2307 Sync Config Example

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ldap.example.com:636
bindDN: cn=openshift-sync,ou=service-accounts,dc=example,dc=com
bindPassword:
  file: /etc/secrets/bindPassword
insecure: false
ca: /etc/ldap-ca/ca.crt
rfc2307:
  groupsQuery:
    baseDN: ou=groups,dc=example,dc=com
    scope: sub
    derefAliases: never
    filter: "(|(cn=ocp-*)(cn=app*-*-team))"
    pageSize: 0
  groupUIDAttribute: dn
  groupNameAttributes:
  - cn
  groupMembershipAttributes:
  - member
  usersQuery:
    baseDN: ou=users,dc=example,dc=com
    scope: sub
    derefAliases: never
    filter: "(objectClass=person)"
    pageSize: 0
  userUIDAttribute: dn
  userNameAttributes:
  - mail
  tolerateMemberNotFoundErrors: false
  tolerateMemberOutOfScopeErrors: false
```

### 7.3 Key RFC2307 Fields

| Field | Meaning |
|---|---|
| `groupsQuery.baseDN` | LDAP subtree where groups are searched |
| `groupsQuery.filter` | LDAP filter used to select groups |
| `groupUIDAttribute` | Unique identifier for the group, often `dn` |
| `groupNameAttributes` | Attribute used as OpenShift group name, often `cn` |
| `groupMembershipAttributes` | Attribute containing member references |
| `usersQuery.baseDN` | LDAP subtree where users are searched |
| `userUIDAttribute` | Unique user identifier used to resolve membership |
| `userNameAttributes` | Attribute used as OpenShift username |

## 8. Active Directory Group Sync

Active Directory normally stores group membership on the user object through `memberOf`.

### 8.1 Membership Model

Example user:

```ldif
dn: CN=Alice Singh,OU=Users,DC=example,DC=com
objectClass: user
mail: alice@example.com
sAMAccountName: alice
memberOf: CN=app1-dev-team,OU=OpenShift,OU=Groups,DC=example,DC=com
memberOf: CN=ocp-admins,OU=OpenShift,OU=Groups,DC=example,DC=com
```

### 8.2 Active Directory Sync Config Example

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636
bindDN: CN=svc-ocp-sync,OU=Service Accounts,DC=example,DC=com
bindPassword:
  file: /etc/secrets/bindPassword
insecure: false
ca: /etc/ldap-ca/ca.crt
activeDirectory:
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(&(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))"
    pageSize: 0
  userNameAttributes:
  - mail
  groupMembershipAttributes:
  - memberOf
```

### 8.3 Active Directory Notes

- `memberOf` is commonly used for AD group membership.
- `mail` is often a good username attribute only if OAuth login also maps usernames to email.
- `sAMAccountName` may be preferred in some environments.
- Nested AD groups require special planning and testing.
- Disabled users can be filtered with an LDAP matching rule using `userAccountControl`.

## 9. Augmented Active Directory Group Sync

Augmented Active Directory is useful when you need both:

- A group query, and
- A user query

This gives more control over which groups are imported and how group names are mapped.

Example:

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636
bindDN: CN=svc-ocp-sync,OU=Service Accounts,DC=example,DC=com
bindPassword:
  file: /etc/secrets/bindPassword
insecure: false
ca: /etc/ldap-ca/ca.crt
augmentedActiveDirectory:
  groupsQuery:
    baseDN: "OU=OpenShift,OU=Groups,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(objectClass=group)"
    pageSize: 0
  groupUIDAttribute: dn
  groupNameAttributes:
  - cn
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(&(objectClass=user)(mail=*))"
    pageSize: 0
  userNameAttributes:
  - mail
  groupMembershipAttributes:
  - memberOf
```

Use this when you want OpenShift to explicitly search the AD group subtree and only sync selected groups.

## 10. Manual Sync Before Scheduled Sync

Never start with a CronJob directly. First test sync manually from your workstation or bastion host.

### 10.1 Dry Run

By default, OpenShift group sync is a dry run unless `--confirm` is provided.

```bash
oc adm groups sync --sync-config=sync.yaml
```

Review the output. Confirm:

- Expected groups are detected.
- Expected users are detected.
- Usernames match OpenShift usernames.
- No unwanted groups are imported.
- No empty groups are unexpectedly created.

### 10.2 Confirmed Sync

```bash
oc adm groups sync --sync-config=sync.yaml --confirm
```

### 10.3 Verify Groups

```bash
oc get groups
oc get group app1-dev-team -o yaml
```

### 10.4 Verify RBAC

```bash
oc adm policy who-can get pods -n app1-dev
oc auth can-i create deployments -n app1-dev --as=alice@example.com
```

## 11. Sync Type: LDAP vs OpenShift

The `oc adm groups sync` command can work in different modes.

### 11.1 Default Sync

```bash
oc adm groups sync --sync-config=sync.yaml --confirm
```

This syncs groups returned by the LDAP query.

### 11.2 OpenShift-Type Sync

```bash
oc adm groups sync --type=openshift --sync-config=sync.yaml --confirm
```

This syncs OpenShift groups that already exist and correspond to LDAP groups in the sync configuration.

This is useful when:

- You want to avoid importing every matching LDAP group.
- You already created or synced selected groups earlier.
- You want a safer recurring sync mode for known groups.

## 12. Whitelist and Blacklist Strategy

In production, avoid syncing the entire corporate directory. Use whitelists, blacklists, or LDAP filters.

### 12.1 Whitelist File

`whitelist.txt`:

```text
cn=ocp-admins,ou=openshift,ou=groups,dc=example,dc=com
cn=app1-dev-team,ou=openshift,ou=groups,dc=example,dc=com
cn=app1-readonly-team,ou=openshift,ou=groups,dc=example,dc=com
```

Command:

```bash
oc adm groups sync \
  --whitelist=/etc/config/whitelist.txt \
  --sync-config=/etc/config/sync.yaml \
  --confirm
```

### 12.2 Blacklist File

`blacklist.txt`:

```text
cn=domain-users,cn=users,dc=example,dc=com
cn=all-employees,ou=groups,dc=example,dc=com
```

Command:

```bash
oc adm groups sync \
  --blacklist=/etc/config/blacklist.txt \
  --sync-config=/etc/config/sync.yaml \
  --confirm
```

### 12.3 Best Practice

For a 10+ years experienced admin, the safest enterprise pattern is:

1. LDAP filter narrows groups to an OpenShift OU or naming convention.
2. Whitelist explicitly selects production groups.
3. `--type=openshift` is considered for recurring sync if only existing groups should be refreshed.
4. Dangerous broad groups such as `Domain Users` are blocked.

## 13. Production Scheduled Group Sync Implementation

The following is a complete, production-style implementation.

Assumptions:

- Namespace: `ldap-sync`
- ServiceAccount: `ldap-group-syncer`
- LDAP bind password secret: `ldap-secret`
- LDAP CA ConfigMap: `ca-config-map`

- Sync command uses whitelist

## 14. Create Dedicated Namespace

```bash
oc new-project ldap-sync
```

Why dedicated namespace?

- Cleaner access control
- Easier troubleshooting
- Separation from application namespaces
- Easier backup/export of sync resources
- Easier audit of service account activity

## 15. Create LDAP Bind Secret

Do not store bind passwords directly in ConfigMaps.

```bash
oc create secret generic ldap-secret \
  -n ldap-sync \
  --from-literal=bindPassword='REPLACE_WITH_STRONG_PASSWORD'
```

Verify:

```bash
oc get secret ldap-secret -n ldap-sync
```

Security notes:

- Use a dedicated LDAP service account.
- Give it read-only LDAP permissions.
- Restrict it to required user and group OUs.
- Rotate the password periodically.
- Avoid using a human administrator DN.

## 16. Create LDAP CA ConfigMap

Verify:


Best practice:

- Use `ldaps://` on port `636`, or LDAP with StartTLS where supported.
- Avoid `insecure: true` in production.
- Validate certificate chain and subject alternative names.

## 21. Create Scheduled Group Sync CronJob

`ldap-sync-cronjob.yaml`:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
  labels:
    app: ldap-group-syncer
spec:
  schedule: "*/30 * * * *"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  suspend: false
  jobTemplate:
    spec:
      backoffLimit: 0
      ttlSecondsAfterFinished: 1800
      template:
        metadata:
          labels:
            app: ldap-group-syncer
        spec:
          serviceAccountName: ldap-group-syncer
          restartPolicy: Never
          terminationGracePeriodSeconds: 30
          activeDeadlineSeconds: 500
          dnsPolicy: ClusterFirst
          containers:
          - name: ldap-group-sync
            image: registry.redhat.io/openshift4/ose-cli:latest
            imagePullPolicy: IfNotPresent
            command:
            - /bin/bash
            - -c
            - |
              set -euo pipefail
              echo "Starting LDAP group sync at $(date -Iseconds)"
              oc adm groups sync \
                --whitelist=/etc/config/whitelist.txt \
                --sync-config=/etc/config/sync.yaml \
                --confirm
              echo "LDAP group sync completed at $(date -Iseconds)"
            resources:
              requests:
                cpu: 50m
                memory: 128Mi
              limits:
                cpu: 500m
                memory: 512Mi
            volumeMounts:
            - name: ldap-sync-volume
              mountPath: /etc/config
              readOnly: true
            - name: ldap-bind-password
              mountPath: /etc/secrets
              readOnly: true
            - name: ldap-ca
              mountPath: /etc/ldap-ca
              readOnly: true
          volumes:
          - name: ldap-sync-volume
            configMap:
              name: ldap-group-syncer
          - name: ldap-bind-password
            secret:
              secretName: ldap-secret
          - name: ldap-ca
            configMap:
              name: ca-config-map
```

Apply:

```bash
oc apply -f ldap-sync-cronjob.yaml
```

Verify:

```bash
oc get cronjob -n ldap-sync
oc describe cronjob ldap-group-syncer -n ldap-sync
```

## 23. Recommended Schedule Frequency

There is no universal correct frequency. It depends on enterprise requirements.

| Environment | Suggested Schedule |
|---|---|
| Lab | Every 10 to 30 minutes |
| Normal enterprise | Every 30 to 60 minutes |
| High-security environment | Every 5 to 15 minutes after testing performance |
| Very large AD | Every 1 to 4 hours with scoped whitelist |
| Multi-cluster fleet | Stagger schedules across clusters |

Do not blindly run every minute in production. LDAP/AD queries can be expensive, and large group membership resolution can stress the directory.

Recommended production pattern:

```yaml
schedule: "*/30 * * * *"
concurrencyPolicy: Forbid
activeDeadlineSeconds: 500
backoffLimit: 0
```

Why?

- `concurrencyPolicy: Forbid` prevents overlapping syncs.
- `activeDeadlineSeconds` prevents hung jobs.
- `backoffLimit: 0` avoids repeated LDAP load if the config is broken.
- Job history limits keep troubleshooting data without accumulating too many jobs.

---

## 24. Why `concurrencyPolicy: Forbid` Matters

LDAP sync is not a task that should overlap with itself.

If one sync is still running and another starts:

- LDAP load can increase.
- Group updates can overlap.
- Troubleshooting becomes confusing.
- Large directories may experience slow response.

Use:

```yaml
concurrencyPolicy: Forbid
```

This tells Kubernetes not to start a new scheduled job if the previous job from the same CronJob is still running.

## 25. Production Hardening Checklist

### 25.1 Security

- Use a dedicated namespace.
- Use a dedicated LDAP bind account.
- Store bind password in a `Secret`, not a `ConfigMap`.
- Use LDAPS or StartTLS.
- Do not use `insecure: true` in production.
- Use least-privilege RBAC for the sync service account.
- Restrict who can edit the sync ConfigMap and CronJob.
- Use namespace-level RBAC to protect `ldap-sync`.
- Avoid broad directory groups such as `Domain Users`.

### 25.2 Reliability

- Set `concurrencyPolicy: Forbid`.
- Set `activeDeadlineSeconds`.
- Set `backoffLimit` deliberately.
- Keep failed job history for troubleshooting.
- Use `ttlSecondsAfterFinished` to clean old jobs.
- Test manual dry run before enabling `--confirm`.
- Monitor CronJob failures.

### 25.3 Performance

- Use LDAP filters to reduce search scope.
- Use a dedicated OU for OpenShift groups.
- Use whitelist for critical groups.
- Avoid syncing thousands of irrelevant groups.
- Coordinate with AD/LDAP team before aggressive schedules.
- Stagger schedules across multiple OpenShift clusters.

### 25.4 Operational Safety

- Maintain sync config in GitOps.
- Review group naming standards.
- Separate cluster-admin groups from application groups.
- Test in non-production first.
- Keep a documented rollback plan.

## 27. Group Pruning

Sync updates groups that are found in LDAP. It does not automatically delete every obsolete OpenShift group in all cases. For removing OpenShift groups that reference missing LDAP records, use group pruning carefully.

Dry run:

```bash
oc adm prune groups --sync-config=/path/to/sync.yaml
```

Confirmed prune:

```bash
oc adm prune groups --sync-config=/path/to/sync.yaml --confirm
```

With whitelist:

```bash
oc adm prune groups \
  --whitelist=/etc/config/whitelist.txt \
  --sync-config=/etc/config/sync.yaml \
  --confirm
```

### 27.1 Should Pruning Be Scheduled?

Be careful. In many enterprises, schedule sync frequently but run prune manually or less frequently.

Recommended approach:

| Action | Frequency |
|---|---|
| Group sync | Every 30 to 60 minutes |
| Prune dry run | Daily or weekly |
| Prune confirm | Manual change-controlled operation |

Why prune is sensitive:

- A temporary LDAP outage can make groups appear missing.
- A bad LDAP filter can make valid groups look orphaned.
- Deleting groups can affect RBAC bindings.
- It should often go through change control.

### 27.2 Optional Prune Permissions

If you create a separate prune job, the service account may need delete permission on groups:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ldap-group-pruner
rules:
- apiGroups:
  - user.openshift.io
  resources:
  - groups
  verbs:
  - get
  - list
  - delete
```

Use a separate service account for pruning if your security policy requires strict separation.

### 28.5 Groups Created but Users Missing

This is one of the most common problems.

Check group:

```bash
oc get group app1-dev-team -o yaml
```

Symptoms:

```yaml
users: []
```

Common causes:

- Wrong schema selected
- Wrong `groupMembershipAttributes`
- Wrong `userUIDAttribute`
- Users are outside `usersQuery.baseDN`
- LDAP filter excludes the users
- Nested group membership is not handled as expected
- User entries do not have the attribute used by `userNameAttributes`

Test LDAP directly from a debug pod or bastion host:

```bash
ldapsearch -LLL \
  -H ldaps://ad.example.com:636 \
  -D 'CN=svc-ocp-sync,OU=Service Accounts,DC=example,DC=com' \
  -W \

```

### 28.6 Users Synced but RBAC Not Working

Example:

User logs in as:

```text
alice
```

Group sync imports:

```text

```

RBAC will not match.

Check OpenShift user:

```bash

```

Check OAuth identity mapping:

```bash

```

Fix the username mapping so LDAP IDP login and group sync produce the same username format.

Common mapping choices:

| Attribute | Example | Notes |
|---|---|---|
| `uid` | `alice` | Common in LDAP/Linux |
| `sAMAccountName` | `alice` | Common in AD |
| `mail` | `alice@example.com` | Good if email is used consistently |
| `userPrincipalName` | `alice@example.com` | Common in AD login flows |

### 28.7 Sync Takes Too Long

Check job duration:

```bash

oc describe job <job-name> -n ldap-sync
```

Improve:

- Narrow `baseDN`.
- Add LDAP filters.
- Use whitelist.
- Avoid syncing entire domain.
- Use `pageSize` where suitable for the directory.
- Coordinate with AD team about indexes.
- Increase `activeDeadlineSeconds` only after understanding why it is slow.

## 31. Multi-Cluster Strategy

In enterprises with many OpenShift clusters, avoid unmanaged differences.

### 31.1 Common Pattern

```text
AD/LDAP
  |
  +-- hub-cluster ldap-sync
  +-- prod-cluster-1 ldap-sync
  +-- prod-cluster-2 ldap-sync
  +-- nonprod-cluster ldap-sync
```

Each cluster syncs from the same source, but may use cluster-specific whitelists.

### 31.2 Naming Convention

Use clear group names:

```text
ocp-global-platform-admins
ocp-prod-readonly
ocp-prod-cluster1-admins
ocp-nonprod-developers
app1-dev-admins
app1-prod-readonly
```

Avoid vague names:

```text
admins
users
dev
team1
all
```

### 31.3 Schedule Staggering

Do not make 30 clusters query AD at exactly the same minute.

Bad:

```yaml
schedule: "*/30 * * * *"
```

on every cluster.

Better:

```yaml
# cluster 1
schedule: "3,33 * * * *"

# cluster 2
schedule: "8,38 * * * *"

# cluster 3
schedule: "13,43 * * * *"
```

## 32. Failure Scenarios and Senior-Level Response

### Scenario 1: User Removed from AD Group but Still Has OpenShift Access

Investigation:

```bash
oc get group app1-dev-team -o yaml
oc logs -n ldap-sync job/<latest-job>
oc get cronjob ldap-group-syncer -n ldap-sync
```

Check:

- Did the latest CronJob run?
- Did it succeed?
- Is the user still present in LDAP group?
- Is there another OpenShift group granting access?
- Is there a direct RoleBinding to the user?

Commands:

```bash
oc adm policy who-can create pods -n app1-dev
oc get rolebinding -n app1-dev -o yaml | grep -A5 -B5 alice
oc get clusterrolebinding -o yaml | grep -A5 -B5 alice
```

Senior answer:

> I would not assume group sync failed. I would first verify actual effective RBAC using `who-can` and `oc auth can-i`, then validate synced group membership, then inspect latest CronJob logs, and finally check whether the user is receiving access from another group or direct binding.

---

### Scenario 2: CronJob Succeeds but Group is Empty

Likely causes:

- LDAP query finds group but cannot resolve members.
- Wrong schema selected.
- User search base excludes users.
- `userUIDAttribute` does not match member values.
- Nested group membership not handled.

Actions:

```bash
oc logs -n ldap-sync job/<job-name>
oc get configmap ldap-group-syncer -n ldap-sync -o yaml
ldapsearch ...
```

Senior answer:

> Empty groups usually mean LDAP bind and group search are working, but membership resolution is broken. I would compare the group membership attribute values with the user UID attribute expected by the sync config.

---

### Scenario 3: LDAP Server Temporarily Unavailable

Symptoms:

- CronJob failed
- LDAP timeout in logs
- No group update occurred

Actions:

```bash
oc logs -n ldap-sync job/<failed-job>
oc get events -n ldap-sync
```

Response:

- Do not run prune.
- Confirm whether previous group state remains in OpenShift.
- Coordinate with LDAP team.
- Re-run manual job after LDAP is restored.

---

### Scenario 4: A Bad ConfigMap Syncs Wrong Groups

Actions:

1. Suspend CronJob:

```bash
oc patch cronjob ldap-group-syncer -n ldap-sync -p '{"spec":{"suspend":true}}'
```

2. Inspect changed ConfigMap:

```bash
oc get configmap ldap-group-syncer -n ldap-sync -o yaml
```

3. Restore previous known-good config from Git.

4. Dry run manually:

```bash
oc adm groups sync --sync-config=sync.yaml
```

5. Resume CronJob:

```bash
oc patch cronjob ldap-group-syncer -n ldap-sync -p '{"spec":{"suspend":false}}'
```

## 33. Common Mistakes

| Mistake | Impact | Fix |
|---|---|---|
| Assuming LDAP IDP automatically syncs groups | RBAC does not work as expected | Configure `oc adm groups sync` |
| Using `insecure: true` in production | Credentials can be exposed | Use LDAPS/StartTLS |
| Binding sync service account to `cluster-admin` | Excessive privilege | Use least-privilege ClusterRole |
| Syncing entire AD domain | Performance and security risk | Use OU, filter, whitelist |
| Username mismatch | User logs in but does not get permissions | Align OAuth and group sync username attributes |
| No `concurrencyPolicy` | Overlapping jobs | Use `Forbid` |
| No job history | Hard to troubleshoot failures | Keep failed job history |
| Pruning automatically without safety | Accidental access disruption | Use dry run and change control |
| Using broad groups like Domain Users | Excessive access | Use dedicated OpenShift groups |
| Not monitoring job failures | Stale RBAC membership | Add alerts |

```yaml
  name: ldap-group-syncer
  namespace: ldap-sync

    app: ldap-group-syncer

    kind: LDAPSyncConfig
    apiVersion: v1

    ca: /etc/ldap-ca/ca.crt
    augmentedActiveDirectory:

        scope: sub
        derefAliases: never
        filter: "(objectClass=group)"
        pageSize: 0
      groupUIDAttribute: dn
      groupNameAttributes:
      - cn
      usersQuery:
        baseDN: "OU=Users,DC=example,DC=com"
        scope: sub
        derefAliases: never
        filter: "(&(objectClass=user)(mail=*))"
        pageSize: 0
      userNameAttributes:
      - mail
      groupMembershipAttributes:
      - memberOf
  whitelist.txt: |
    CN=ocp-admins,OU=OpenShift,OU=Groups,DC=example,DC=com
    CN=app1-dev-team,OU=OpenShift,OU=Groups,DC=example,DC=com
    CN=app1-readonly-team,OU=OpenShift,OU=Groups,DC=example,DC=com

apiVersion: batch/v1
kind: CronJob
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
  labels:
    app: ldap-group-syncer
spec:
  schedule: "*/30 * * * *"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  suspend: false
  jobTemplate:
    spec:
      backoffLimit: 0
      ttlSecondsAfterFinished: 1800
      template:
        metadata:
          labels:
            app: ldap-group-syncer
        spec:
          serviceAccountName: ldap-group-syncer
          restartPolicy: Never
          activeDeadlineSeconds: 500
          containers:
          - name: ldap-group-sync
            image: registry.redhat.io/openshift4/ose-cli:latest
            imagePullPolicy: IfNotPresent
            command:
            - /bin/bash
            - -c
            - |
              set -euo pipefail
              oc adm groups sync \
                --whitelist=/etc/config/whitelist.txt \
                --sync-config=/etc/config/sync.yaml \
```

## 36. Interview-Level Explanation

### Question

**How would you configure scheduled LDAP group sync in OpenShift?**

### Strong Senior Answer

I would first separate authentication from authorization. LDAP or AD as an OAuth identity provider only authenticates users; it does not automatically keep OpenShift group objects updated for RBAC. For RBAC based on enterprise groups, I would configure LDAP group synchronization using `oc adm groups sync`.

Before scheduling anything, I would build and test the LDAP sync config manually with a dry run. I would confirm the correct schema, such as RFC2307, Active Directory, or augmented Active Directory, and verify that the username attribute produced by group sync matches the username created by the OpenShift identity provider.

After manual validation, I would create a dedicated namespace such as `ldap-sync`, a service account, and a least-privilege ClusterRole that can get, list, create, and update `groups.user.openshift.io`. I would store the LDAP bind password in a Secret, store the LDAP CA certificate in a ConfigMap, and store the sync configuration and whitelist in a ConfigMap.

Then I would create a Kubernetes `CronJob` that runs the OpenShift CLI image and executes:

```bash
oc adm groups sync --whitelist=/etc/config/whitelist.txt --sync-config=/etc/config/sync.yaml --confirm
```

For production, I would set `concurrencyPolicy: Forbid`, define job history limits, set `activeDeadlineSeconds`, use LDAPS, avoid `insecure: true`, and monitor job failures. I would usually schedule sync every 30 to 60 minutes depending on directory size and security requirements. I would not schedule automatic prune aggressively; pruning should usually be dry-run and change-controlled because a bad LDAP filter or outage can make valid groups appear orphaned.

Finally, I would bind OpenShift roles to the synced groups using `RoleBinding` or `ClusterRoleBinding`, not to individual users.

## 38. Best Practices Summary

For enterprise-grade scheduled group sync:

1. Authenticate users with LDAP/OIDC/SSO.
2. Sync groups separately using `oc adm groups sync`.
3. Use a dedicated namespace.
4. Use a dedicated service account.
5. Grant least privilege only on OpenShift group resources.
6. Store bind password in Secret.
7. Use LDAPS or StartTLS.
8. Use ConfigMap for sync config and whitelist.
9. Use whitelist and LDAP filters to avoid broad sync.
10. Align username attributes between OAuth and group sync.
11. Use `concurrencyPolicy: Forbid`.
12. Keep failed job history for troubleshooting.
13. Monitor CronJob execution.
14. Use GitOps for configuration management.
15. Treat pruning as a sensitive operation.
