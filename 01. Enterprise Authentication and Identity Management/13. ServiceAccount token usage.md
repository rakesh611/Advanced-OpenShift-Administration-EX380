# ServiceAccount Token Usage in OpenShift

**Area:** Enterprise Authentication and Identity Management  
**Level:** Advanced OpenShift Administration / 10+ Years Experience  
**Focus:** ServiceAccount identity, token lifecycle, TokenRequest API, bound tokens, RBAC, troubleshooting, and production security.

---

## 1. Executive Summary

A **ServiceAccount** is a non-human identity used by pods, controllers, Operators, CI/CD systems, monitoring tools, and automation to authenticate to the OpenShift or Kubernetes API.

A ServiceAccount token is a **bearer credential**. Any process that has the token can authenticate as that ServiceAccount until the token expires or is revoked. Therefore, token handling must be treated like password, SSH key, or cloud IAM key handling.

Modern OpenShift uses **bound ServiceAccount tokens** instead of relying on old long-lived token Secrets. Bound tokens are better because they are:

- **Time-bound**: they have an expiration.
- **Audience-bound**: the token is intended for a specific receiver such as the Kubernetes API server, Vault, AWS STS, or another trusted service.
- **Object-bound**: they can be tied to a pod or secret so that token validity can depend on the lifecycle of that object.
- **Projected into pods**: kubelet can mount and rotate tokens through a projected volume.

From OpenShift 4.16 onward, OpenShift no longer automatically creates a long-lived ServiceAccount API token Secret for every ServiceAccount. Existing long-lived token Secrets from older clusters are not automatically removed and can continue to work, so senior administrators must audit and clean them carefully during upgrades and security reviews.

## 2. What Is a ServiceAccount?

A ServiceAccount is an OpenShift API object that represents an application or automation identity inside a namespace.

Human users authenticate through identity providers such as LDAP, GitHub, OpenID Connect, SSO, HTPasswd, or kubeadmin during early installation. ServiceAccounts are different: they are intended for workloads and automation.

Example ServiceAccount identity format:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

Example:

```text
system:serviceaccount:payments:payment-api
```

Every ServiceAccount is also part of these groups:

```text
system:serviceaccounts
system:serviceaccounts:<namespace>
```

Example:

```text
system:serviceaccounts
system:serviceaccounts:payments
```

This matters because RBAC can be granted to:

- One specific ServiceAccount.
- All ServiceAccounts in one namespace.
- All ServiceAccounts cluster-wide.

For production, avoid broad grants to `system:serviceaccounts` unless there is a very strong reason.

## 3. Why ServiceAccount Tokens Exist

A pod often needs to call the API server. Examples:

- An Operator watches custom resources.
- A controller creates pods, config maps, or routes.
- A backup job lists PVCs and snapshots.
- A monitoring agent queries pods, nodes, endpoints, or metrics.
- A CI/CD tool deploys workloads.
- An application uses API discovery.
- An OAuth proxy validates users against OpenShift.
- A workload exchanges an OpenShift token for cloud IAM credentials.

Instead of embedding a human user's password or token into the workload, OpenShift lets the workload run as a ServiceAccount and grants that ServiceAccount only the permissions it needs.

Correct design:

```text
Application -> ServiceAccount token -> API server authentication -> RBAC authorization
```

Bad design:

```text
Application -> admin user's token -> cluster-admin permissions
```

## 4. Authentication vs Authorization

ServiceAccount token usage has two separate phases.

### 4.1 Authentication

Authentication answers:

```text
Who are you?
```

A pod sends a bearer token:

```http
Authorization: Bearer <token>
```

The API server validates the token and identifies the caller as:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

### 4.2 Authorization

Authorization answers:

```text
What are you allowed to do?
```

After the identity is known, RBAC decides whether the request is allowed.

Example:

```bash
oc auth can-i list pods \
  --as=system:serviceaccount:payments:payment-api \
  -n payments
```

Possible result:

```text
yes
```

or:

```text
no
```

A token can be valid but still receive `403 Forbidden` if RBAC does not allow the requested action.

## 5. Important Token Types in OpenShift

There are several token patterns you must understand.

| Token Type | Modern Status | Typical Use | Risk |
|---|---|---|---|
| Projected bound token | Recommended | Pod calls API or external identity system | Lower risk because it rotates and can be audience/time/object-bound |
| `oc create token` token | Recommended for short-lived external use | Temporary automation, testing, scripts | Medium risk; must handle expiration |
| Manually created ServiceAccount token Secret | Use only when unavoidable | Legacy tools needing non-expiring token | High risk because it persists in a readable API object |
| Old auto-generated token Secret | Legacy | Pre-upgrade workloads | High risk; audit and migrate |
| Image pull Secret | Registry auth, not normal API auth | Pull internal registry images | Different purpose; do not confuse with API token |

## 6. OpenShift Version Behavior You Must Know

### 6.1 Older OpenShift Behavior

Older OpenShift and Kubernetes versions commonly created long-lived ServiceAccount token Secrets automatically. Administrators frequently used commands such as:

```bash
oc serviceaccounts get-token <serviceaccount>
oc sa get-token <serviceaccount>
```

These tokens were often copied into Jenkins, Ansible, GitLab, monitoring systems, backup tools, or external scripts.

The problem is that many of these tokens were:

- Long-lived.
- Stored in Secrets.
- Sometimes copied into external systems.
- Hard to rotate.
- Over-permissioned.
- Forgotten after project ownership changed.

### 6.2 Modern OpenShift Behavior

Modern OpenShift prefers TokenRequest-based bound tokens. In OpenShift 4.16 and later, long-lived ServiceAccount API token Secrets are not automatically created for each new ServiceAccount. If you run:

```bash
oc describe sa robot -n project1
```

You might see:

```text
Tokens: <none>
```

This can be normal on newer OpenShift versions.

Do not assume that `Tokens: <none>` means the ServiceAccount cannot be used by pods. Kubelet can still request and mount projected ServiceAccount tokens for pods.

## 7. Default ServiceAccounts in a Project

OpenShift creates default ServiceAccounts in projects, commonly including:

```text
builder
deployer
default
```

Typical usage:

| ServiceAccount | Purpose |
|---|---|
| `builder` | Build pods; commonly has image build permissions |
| `deployer` | DeploymentConfig deployment pods |
| `default` | Used by pods that do not specify a ServiceAccount |

Senior admin rule:

```text
Do not grant broad permissions to the default ServiceAccount.
```

Reason: any pod that does not explicitly set `serviceAccountName` runs as `default`. If you grant `edit`, `admin`, or custom high permissions to `default`, every unspecified workload in that namespace inherits those permissions.

Better design:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments
spec:
  replicas: 2
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      serviceAccountName: payment-api
      containers:
      - name: payment-api
        image: registry.example.com/payments/payment-api:1.0
```

## 8. Creating a Dedicated ServiceAccount

Create a namespace:

```bash
oc new-project ent-auth-demo
```

Create a ServiceAccount:

```bash
oc create sa app-reader -n ent-auth-demo
```

Check it:

```bash
oc get sa -n ent-auth-demo
oc describe sa app-reader -n ent-auth-demo
```

Grant read-only access inside the namespace:

```bash
oc policy add-role-to-user view -z app-reader -n ent-auth-demo
```

The `-z` flag means "ServiceAccount in the current or specified namespace." It helps avoid mistakes in the full ServiceAccount username.

Equivalent full identity form:

```bash
oc policy add-role-to-user view \
  system:serviceaccount:ent-auth-demo:app-reader \
  -n ent-auth-demo
```

Verify access:

```bash
oc auth can-i get pods \
  --as=system:serviceaccount:ent-auth-demo:app-reader \
  -n ent-auth-demo

oc auth can-i delete pods \
  --as=system:serviceaccount:ent-auth-demo:app-reader \
  -n ent-auth-demo
```

Expected:

```text
yes
no
```

## 9. How a Pod Uses a ServiceAccount Token

A pod can receive a ServiceAccount token automatically unless token automount is disabled.

Typical in-pod files:

```text
/var/run/secrets/kubernetes.io/serviceaccount/token
/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
/var/run/secrets/kubernetes.io/serviceaccount/namespace
```

From inside a pod:

```bash
TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
CACERT=/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
NAMESPACE=$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace)

curl --cacert "$CACERT" \
  -H "Authorization: Bearer $TOKEN" \
  https://kubernetes.default.svc/api/v1/namespaces/$NAMESPACE/pods
```

Production note:

- Read the token from the file when making requests, or use a Kubernetes client library that reloads rotated credentials correctly.
- Do not copy the token into an environment variable at container startup and keep using it forever.
- Do not log the token.
- Do not print the token in application debug output.
- Do not paste the token into online JWT decoders.

## 10. Bound ServiceAccount Tokens

A bound ServiceAccount token is a JWT issued through the TokenRequest API.

It can include:

| Claim / Field | Meaning |
|---|---|
| `iss` | Issuer |
| `sub` | Subject, usually `system:serviceaccount:<namespace>:<name>` |
| `aud` | Intended audience |
| `exp` | Expiration timestamp |
| `iat` | Issued-at timestamp |
| `nbf` | Not-before timestamp |
| `kubernetes.io` | Kubernetes-specific metadata such as namespace, ServiceAccount name, UID, pod binding info |

Bound token properties:

```text
Time-bound + audience-bound + optionally object-bound
```

### Why Audience Matters

Audience controls who should accept the token.

Example audiences:

```text
https://kubernetes.default.svc
vault
sts.amazonaws.com
openshift
custom-api
```

If a token was created for `vault`, the Kubernetes API server should not automatically accept it as a general API token unless its audience is valid for the API server.

This prevents a token issued for one system from being replayed against another system.

## 11. Projected ServiceAccount Token Volume

A projected volume lets a pod request an additional bound token with custom path, audience, and expiration.

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: token-demo
  namespace: ent-auth-demo
spec:
  serviceAccountName: app-reader
  containers:
  - name: curl
    image: registry.access.redhat.com/ubi9/ubi-minimal
    command: ["/bin/sh", "-c"]
    args:
    - |
      echo "Token files:"
      ls -l /var/run/secrets/tokens
      sleep 3600
    volumeMounts:
    - name: vault-token
      mountPath: /var/run/secrets/tokens
      readOnly: true
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
  volumes:
  - name: vault-token
    projected:
      sources:
      - serviceAccountToken:
          path: vault-token
          audience: vault
          expirationSeconds: 7200
```

Create it:

```bash
oc apply -f token-demo.yaml
```

Check token file:

```bash
oc exec -n ent-auth-demo token-demo -- \
  ls -l /var/run/secrets/tokens
```

Read token payload safely inside lab only:

```bash
oc exec -n ent-auth-demo token-demo -- \
  sh -c 'cut -d "." -f2 /var/run/secrets/tokens/vault-token | base64 -d 2>/dev/null'
```

Production warning:

```text
Never decode production tokens using public websites.
```

Use local tools only.

## 12. Token Rotation Behavior

Projected tokens are rotated by kubelet. Applications must be designed to handle token file changes.

Bad pattern:

```python
# Bad: token read once at startup
TOKEN = open("/var/run/secrets/kubernetes.io/serviceaccount/token").read()
```

Better pattern:

```python
# Better: read token when needed or rely on official Kubernetes client configuration reload behavior
def get_token():
    with open("/var/run/secrets/kubernetes.io/serviceaccount/token") as f:
        return f.read().strip()
```

Operational symptom of bad token handling:

```text
Application works after pod start, then later API calls fail with 401 Unauthorized.
```

Common root cause:

```text
The token rotated, but the application kept using the old token cached in memory.
```

## 13. Creating a Short-Lived Token Outside a Pod

For temporary external automation, use:

```bash
oc create token app-reader -n ent-auth-demo
```

Store it in a shell variable:

```bash
TOKEN=$(oc create token app-reader -n ent-auth-demo)
APISERVER=$(oc whoami --show-server)

curl -k \
  -H "Authorization: Bearer $TOKEN" \
  "$APISERVER/api/v1/namespaces/ent-auth-demo/pods"
```

Request a specific duration if your `oc` version supports it:

```bash
TOKEN=$(oc create token app-reader -n ent-auth-demo --duration=30m)
```

Request a specific audience if your `oc` version supports it:

```bash
TOKEN=$(oc create token app-reader -n ent-auth-demo \
  --audience=https://kubernetes.default.svc \
  --duration=30m)
```

Check help on your cluster admin host:

```bash
oc create token -h
```

Senior admin guidance:

- Use `oc create token` for short-lived operational tasks.
- Avoid using it as a permanent secret for Jenkins, GitLab, Ansible Tower, Zabbix, or external monitoring unless the external system can refresh the token.
- For tools that cannot handle expiration, prefer redesigning the integration. If no redesign is possible, use a manually created long-lived token Secret with strict compensating controls.

## 14. Manually Creating a Long-Lived ServiceAccount Token Secret

Use this only when you cannot use TokenRequest-based tokens.

Create ServiceAccount:

```bash
oc create sa cicd-robot -n ent-auth-demo
```

Grant minimum required access:

```bash
oc policy add-role-to-user edit -z cicd-robot -n ent-auth-demo
```

Create token Secret:

```bash
cat <<'EOF' | oc apply -n ent-auth-demo -f -
apiVersion: v1
kind: Secret
metadata:
  name: cicd-robot-token
  annotations:
    kubernetes.io/service-account.name: cicd-robot
type: kubernetes.io/service-account-token
EOF
```

Wait for token population:

```bash
oc get secret cicd-robot-token -n ent-auth-demo -o yaml
```

Extract token:

```bash
TOKEN=$(oc get secret cicd-robot-token -n ent-auth-demo \
  -o jsonpath='{.data.token}' | base64 -d)

echo "$TOKEN"
```

Security warning:

```text
A long-lived token Secret is a persistent bearer credential stored in the API.
Anyone with read access to that Secret can authenticate as the ServiceAccount.
Anyone with permission to create this Secret type can request a token for that ServiceAccount.
```

Hardening controls if long-lived tokens are unavoidable:

- Use a dedicated ServiceAccount per external integration.
- Bind only minimum RBAC.
- Use a dedicated namespace.
- Store token only in an enterprise secret manager.
- Rotate on a defined schedule.
- Monitor API usage by that ServiceAccount.
- Do not grant generic users `get/list/watch secrets`.
- Do not grant developers the ability to create `kubernetes.io/service-account-token` Secrets unless required.
- Prefer secret-bound short-lived tokens where possible.

## 15. Binding a Token to a Secret for Revocation

If your `oc create token` supports bound-object flags, create a revocation object:

```bash
oc create secret generic app-reader-revoker \
  -n ent-auth-demo \
  --from-literal=purpose=token-revocation
```

Create token bound to that Secret:

```bash
TOKEN=$(oc create token app-reader \
  -n ent-auth-demo \
  --duration=12h \
  --bound-object-kind=Secret \
  --bound-object-name=app-reader-revoker)
```

Use token:

```bash
curl -k -H "Authorization: Bearer $TOKEN" \
  "$(oc whoami --show-server)/api/v1/namespaces/ent-auth-demo/pods"
```

Revoke by deleting the bound object:

```bash
oc delete secret app-reader-revoker -n ent-auth-demo
```

This pattern is useful for emergency revocation without deleting the entire ServiceAccount.

Always confirm available options:

```bash
oc create token -h
```

## 16. Disabling Automatic Token Mounting

Some pods do not need to call the OpenShift API. Do not mount tokens into those pods.

### 16.1 Disable at Pod Level

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: no-api-pod
  namespace: ent-auth-demo
spec:
  serviceAccountName: default
  automountServiceAccountToken: false
  containers:
  - name: app
    image: registry.access.redhat.com/ubi9/ubi-minimal
    command: ["sleep", "3600"]
```

### 16.2 Disable at ServiceAccount Level

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: no-api-sa
  namespace: ent-auth-demo
automountServiceAccountToken: false
```

### 16.3 Why Disable Automount?

If an application has a remote code execution vulnerability and the pod has a mounted ServiceAccount token, the attacker can steal it and attempt API access.

Defense:

```text
No API need -> no token mount.
```

This is one of the easiest ways to reduce blast radius.

## 17. RBAC Design for ServiceAccount Tokens

A token is only as dangerous as the permissions behind it.

### 17.1 Least Privilege Rules

Follow these rules:

1. One ServiceAccount per application or automation.
2. One Role/ClusterRole per responsibility.
3. Namespace-scoped RoleBinding when possible.
4. ClusterRoleBinding only when required.
5. Never bind `cluster-admin` to application ServiceAccounts.
6. Avoid binding broad groups such as `system:serviceaccounts`.
7. Avoid giving workloads access to Secrets unless absolutely required.
8. Regularly run `oc auth can-i` and audit RoleBindings.

### 17.2 Example: Read Pods Only

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader-custom
  namespace: ent-auth-demo
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
```

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-custom-binding
  namespace: ent-auth-demo
subjects:
- kind: ServiceAccount
  name: app-reader
  namespace: ent-auth-demo
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader-custom
```

Apply:

```bash
oc apply -f pod-reader-role.yaml
oc apply -f pod-reader-rolebinding.yaml
```

Test:

```bash
oc auth can-i list pods \
  --as=system:serviceaccount:ent-auth-demo:app-reader \
  -n ent-auth-demo

oc auth can-i list secrets \
  --as=system:serviceaccount:ent-auth-demo:app-reader \
  -n ent-auth-demo
```

Expected:

```text
yes
no
```

### 17.3 Example: External Monitoring

A monitoring ServiceAccount may need:

```text
get/list/watch pods
get/list/watch services
get/list/watch endpoints
get/list/watch routes
get/list/watch namespaces
```

It probably does not need:

```text
create pods
delete pods
get secrets
update deployments
impersonate users
bind roles
escalate privileges
```

Be very careful with verbs:

| Verb | Risk |
|---|---|
| `get/list/watch` | Read-only, but sensitive if resource is Secrets |
| `create` | Can create objects; may lead to privilege abuse |
| `update/patch` | Can alter workloads or RBAC |
| `delete` | Can cause outage |
| `impersonate` | Highly sensitive |
| `bind` | Can bind roles |
| `escalate` | Can create higher-privilege roles |

## 18. ServiceAccount Token and OpenShift OAuth Client Usage

OpenShift can use a ServiceAccount as a constrained OAuth client. This is common with `oauth-proxy` patterns.

ServiceAccount OAuth client identity:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

The ServiceAccount can request limited scopes such as:

```text
user:info
user:check-access
role:<role>:<serviceaccount_namespace>
role:<role>:<serviceaccount_namespace>:!
```

Example OAuth redirect annotation:

```bash
oc annotate sa oauth-proxy -n ent-auth-demo \
  'serviceaccounts.openshift.io/oauth-redirecturi.primary=https://myapp-ent-auth-demo.apps.example.com/oauth/callback'
```

Route-based redirect reference example:

```bash
oc annotate sa oauth-proxy -n ent-auth-demo \
  'serviceaccounts.openshift.io/oauth-redirectreference.primary={"kind":"OAuthRedirectReference","apiVersion":"v1","reference":{"kind":"Route","name":"myapp"}}'
```

Challenge annotation:

```bash
oc annotate sa oauth-proxy -n ent-auth-demo \
  serviceaccounts.openshift.io/oauth-want-challenges=true
```

Important distinction:

- A ServiceAccount API token authenticates the ServiceAccount to the Kubernetes/OpenShift API.
- A ServiceAccount as an OAuth client is used in OAuth flows and proxy integrations.
- Do not mix OAuth client secrets, API tokens, and user OAuth access tokens without understanding the flow.

## 19. TokenReview and SubjectAccessReview

### 19.1 TokenReview

A TokenReview validates a token and returns the authenticated user information if valid.

Conceptual flow:

```text
External service receives token
External service sends TokenReview to API server
API server validates token
API server returns username and groups
External service makes authorization decision
```

TokenReview is useful for:

- Custom API gateways.
- Webhooks.
- Authentication proxies.
- External systems validating OpenShift tokens.

### 19.2 SubjectAccessReview

SubjectAccessReview checks whether a user or ServiceAccount can perform an action.

Example with `oc auth can-i`:

```bash
oc auth can-i get pods \
  --as=system:serviceaccount:ent-auth-demo:app-reader \
  -n ent-auth-demo
```

This is functionally the admin-friendly way to test authorization.

For troubleshooting, remember:

```text
TokenReview answers: Is this token valid and who is it?
SubjectAccessReview answers: Can this identity do this action?
```

## 20. ServiceAccount Tokens and Image Pull Secrets

OpenShift automatically creates image pull Secrets for ServiceAccounts to integrate with the internal registry.

Do not confuse these:

| Object | Purpose |
|---|---|
| ServiceAccount API token | Authenticate to Kubernetes/OpenShift API |
| Image pull Secret | Authenticate image pulls from registry |
| Docker config Secret | Registry credential format |
| OAuth access token | Human or OAuth client access to API |

Typical ServiceAccount output can show image pull Secrets but no API token:

```text
Image pull secrets:  robot-dockercfg-qzbhb
Mountable secrets:   robot-dockercfg-qzbhb
Tokens:              <none>
```

On modern OpenShift, this can be normal.

## 21. Security Risks and Attack Paths

### 21.1 Token Theft from a Pod

Attack path:

```text
Attacker gets shell in pod
Attacker reads /var/run/secrets/kubernetes.io/serviceaccount/token
Attacker uses token from outside or inside cluster
API server authenticates attacker as ServiceAccount
RBAC controls final damage
```

Mitigation:

- Disable automount where not needed.
- Use dedicated ServiceAccounts.
- Use least privilege.
- Restrict `exec` access.
- Use SCC/Pod Security Admission properly.
- Use NetworkPolicy.
- Avoid root containers.
- Drop Linux capabilities.
- Do not mount hostPath unnecessarily.
- Monitor API calls.

### 21.2 Secret Read Privilege Abuse

If a user can read Secrets in a namespace, they might read manually created ServiceAccount token Secrets.

If a user can create ServiceAccount token Secrets, they may be able to cause a token to be generated for a ServiceAccount.

Avoid broad grants like:

```yaml
resources: ["secrets"]
verbs: ["get", "list", "watch", "create"]
```

unless required.

### 21.3 Over-Permissioned Default ServiceAccount

Bad:

```bash
oc policy add-role-to-user edit -z default -n production
```

Worse:

```bash
oc adm policy add-cluster-role-to-user cluster-admin \
  system:serviceaccount:production:default
```

Impact:

```text
Every pod without serviceAccountName in production can now act with high privilege.
```

### 21.4 Tokens in CI/CD Logs

Common incident:

```text
Pipeline runs: echo $TOKEN
Log retention keeps token for 90 days
Many users can read pipeline logs
Token is copied and abused
```

Mitigation:

- Mask secrets in CI/CD.
- Never echo tokens.
- Use short-lived tokens.
- Rotate secrets after accidental exposure.
- Review logs after incidents.

## 22. Production Troubleshooting Matrix

| Symptom | Likely Cause | Checks | Fix |
|---|---|---|---|
| `401 Unauthorized` | Token invalid, expired, wrong audience, bad issuer | Decode token locally; check `exp`, `aud`, `iss`; try new token | Refresh token, correct audience, restart pod, fix issuer |
| `403 Forbidden` | Token valid but RBAC denies action | `oc auth can-i ... --as=system:serviceaccount:ns:sa` | Add minimum RBAC |
| `Tokens: <none>` | Modern OpenShift no longer auto-creates API token Secret | `oc version`; check projected token behavior | Use `oc create token` or projected token |
| App fails after hours/days | App cached rotated token | Check app logs for 401 after rotation window | Update app to reread token file or restart |
| External monitor fails after token expiry | Used short-lived `oc create token` as permanent credential | Check token `exp`; review monitor config | Implement refresh or create long-lived token with controls |
| OAuth proxy reports no SA tokens | OAuth client pattern expecting token Secret | Check SA annotations and token availability | Configure OAuth correctly; use supported token method |
| Pod cannot list pods | RBAC missing | `oc auth can-i list pods --as=...` | Add RoleBinding |
| Token works in one API but not another | Audience mismatch | Check `aud` claim | Request correct audience |
| Token still works after SA Secret cleanup | Token is bound/projected or old external token | Check token type and binding | Delete pod/Secret/SA depending token type |
| Image pull fails | Registry Secret issue, not API token issue | `oc describe pod`; check imagePullSecrets | Fix registry auth or image registry config |

## 23. Investigating a ServiceAccount Token Issue

### Step 1: Identify the ServiceAccount

```bash
oc get pod <pod-name> -n <namespace> \
  -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

### Step 2: Inspect ServiceAccount

```bash
oc describe sa <serviceaccount> -n <namespace>
```

### Step 3: Check RBAC Bindings

```bash
oc get rolebinding -n <namespace> -o wide
oc get clusterrolebinding -o wide | grep <serviceaccount>
```

More targeted:

```bash
oc get rolebinding -n <namespace> -o yaml | grep -A10 -B5 <serviceaccount>
oc get clusterrolebinding -o yaml | grep -A10 -B5 <serviceaccount>
```

### Step 4: Test Permission

```bash
oc auth can-i get pods \
  --as=system:serviceaccount:<namespace>:<serviceaccount> \
  -n <namespace>
```

### Step 5: Generate Fresh Token for Testing

```bash
TOKEN=$(oc create token <serviceaccount> -n <namespace>)
APISERVER=$(oc whoami --show-server)

curl -k -H "Authorization: Bearer $TOKEN" \
  "$APISERVER/api/v1/namespaces/<namespace>/pods"
```

### Step 6: Decode Token Locally

```bash
python3 - <<PY
import base64, json
```

## 27. Advanced Scenario: CI/CD Deployment ServiceAccount

### Requirement

A GitLab/Jenkins/Ansible automation needs to deploy only into namespace `dev-app`.

### Bad Approach

```bash
oc adm policy add-cluster-role-to-user cluster-admin \
  system:serviceaccount:dev-app:cicd
```

### Better Approach

Create ServiceAccount:

```bash
oc create sa cicd-deployer -n dev-app
```

Create Role with required permissions:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: cicd-deployer
  namespace: dev-app
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["services", "configmaps"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: ["route.openshift.io"]
  resources: ["routes"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
```

Bind:

```bash
oc apply -f cicd-role.yaml
oc create rolebinding cicd-deployer \
  --role=cicd-deployer \
  --serviceaccount=dev-app:cicd-deployer \
  -n dev-app
```

Generate short token if pipeline can refresh:

```bash
oc create token cicd-deployer -n dev-app --duration=1h
```

If pipeline cannot refresh and business accepts risk, create a long-lived token Secret and store it in a proper enterprise secret manager.

- If it cannot, consider a long-lived token Secret with strict controls.
- Never use `cluster-admin` for monitoring.

## 29. Revocation Strategy

Revocation depends on token type.

| Token Type | How to Revoke |
|---|---|
| Projected pod-bound token | Delete the pod |
| Secret-bound token | Delete the bound Secret |
| TokenRequest token not bound to object | Usually wait for expiration or delete ServiceAccount |
| Manual long-lived token Secret | Delete the Secret |
| Compromised ServiceAccount broadly | Delete/recreate ServiceAccount and RBAC; rotate all related credentials |
| Human OAuth token | Revoke OAuthAccessToken or force user/session action |

Emergency response:

```bash
# Identify SA
oc get sa -n <namespace>

# Remove risky bindings
oc delete rolebinding <binding> -n <namespace>
oc delete clusterrolebinding <binding>

# Delete token secret if long-lived
oc delete secret <token-secret> -n <namespace>

# Delete compromised pods if projected tokens might be stolen
oc delete pod <pod> -n <namespace>

# Last resort: delete ServiceAccount
oc delete sa <serviceaccount> -n <namespace>
```

After revocation:

- Review audit logs.
- Rotate external stored tokens.
- Recreate ServiceAccount only if needed.
- Rebind minimum RBAC.
- Add monitoring alerts.

## 31. Common Interview Questions and Senior-Level Answers

### Q1. What is the difference between 401 and 403 for ServiceAccount token calls?

**Answer:**  
`401 Unauthorized` means authentication failed. The token might be expired, invalid, malformed, wrong audience, or signed by an issuer the API server does not trust. `403 Forbidden` means authentication succeeded, but RBAC denied the requested action. For 403, use `oc auth can-i` with `--as=system:serviceaccount:<ns>:<sa>`.

### Q2. Why does `oc describe sa` show `Tokens: <none>`?

**Answer:**  
On modern OpenShift, long-lived API token Secrets are not automatically created for every ServiceAccount. This is expected from newer OpenShift behavior. Pods can still receive projected tokens through kubelet, and administrators can request temporary tokens with `oc create token`.

### Q3. Why are bound tokens more secure than legacy Secret tokens?

**Answer:**  
Bound tokens can have a bounded lifetime, an intended audience, and an object binding. Legacy Secret tokens are long-lived credentials stored as API objects, which increases exposure if users can read Secrets or if tokens are copied into external tools.

### Q4. A pod can read pods but cannot read secrets. Is this token issue or RBAC issue?

**Answer:**  
RBAC issue, not token issue. The token authenticated successfully. The ServiceAccount has permission for pods but not secrets.

### Q5. An app works for some time then starts failing with 401. What do you check?

**Answer:**  
Check whether the app caches the token at startup. Projected tokens rotate. The app must reread the token file or use a client library that handles token rotation.

### Q6. How do you give a CI/CD system access to deploy only to one namespace?

**Answer:**  
Create a dedicated ServiceAccount in that namespace, create a Role with only deployment-related verbs and resources, bind it with RoleBinding, and provide a short-lived token if the CI/CD tool can refresh it. Avoid cluster-admin.

### Q7. When would you use a long-lived token Secret?

**Answer:**  
Only when the integration cannot use short-lived TokenRequest tokens and the business accepts the security exposure. Apply strict RBAC, secret manager storage, rotation, audit monitoring, and limited namespace scope.

### Q8. How do you revoke a projected token?

**Answer:**  
If it is pod-bound, delete the pod. Kubelet will issue a new token to the replacement pod. If it is bound to a Secret, delete the Secret. If it is an unbound TokenRequest token, generally wait for expiration or delete the ServiceAccount in an emergency.

### Q9. Why should you not grant permissions to the `default` ServiceAccount?

**Answer:**  
Any pod without explicit `serviceAccountName` uses `default`. Broad permissions on `default` silently grant those permissions to many workloads, increasing blast radius and reducing audit clarity.

### Q10. What is token audience?

**Answer:**  
Audience is the intended recipient of the token. A recipient must verify that it is included in the token's `aud` claim. This prevents a token issued for one service from being replayed against another service.

## 32. Production Best Practices

Use this checklist in enterprise OpenShift environments.

### Identity Design

- Create dedicated ServiceAccounts per workload.
- Use meaningful names: `backup-reader`, `vault-auth`, `payment-api`, `gitops-deployer`.
- Avoid using `default` for real applications.
- Avoid sharing one ServiceAccount across multiple applications.

### Token Design

- Prefer projected bound tokens for pods.
- Prefer `oc create token` for temporary external tasks.
- Avoid long-lived token Secrets.
- Use custom audience for external systems.
- Use short expiration where possible.
- Bind tokens to objects where revocation matters.
- Make applications handle token rotation.

### RBAC Design

- Use namespace RoleBinding where possible.
- Use ClusterRoleBinding only when cluster-wide resources are required.
- Avoid `cluster-admin`.
- Avoid access to Secrets.
- Avoid `impersonate`, `bind`, and `escalate` unless fully justified.
- Test with `oc auth can-i`.

### Runtime Hardening

- Disable token automount for pods that do not need API access.
- Use `runAsNonRoot`.
- Drop capabilities.
- Disable privilege escalation.
- Use NetworkPolicy.
- Restrict `exec` permissions.
- Avoid hostPath and privileged SCC unless required.

### Operations

- Audit long-lived token Secrets.
- Audit ClusterRoleBindings to ServiceAccounts.
- Rotate external tokens.
- Review API audit logs.
- Remove unused ServiceAccounts.
- Document token owners.
- Use a secret manager for external integrations.
- Run periodic access reviews.

## 35. Real-World Incident Examples

### Incident 1: Token Printed in Jenkins Log

A deployment pipeline did:

```bash
echo $OPENSHIFT_TOKEN
```

The token belonged to a ServiceAccount with `edit` permissions in production. Logs were readable by all developers.

Fix:

- Revoke token.
- Rotate Jenkins credential.
- Mask token variables.
- Reduce RBAC from `edit` to custom deploy Role.
- Audit API calls from the ServiceAccount.
- Add policy preventing `echo` of known secret variable patterns where possible.

### Incident 2: Default ServiceAccount Given Admin

A team ran:

```bash
oc policy add-role-to-user admin -z default -n app-prod
```

A compromised low-risk debug pod inherited admin access.

Fix:

- Remove binding from `default`.
- Create dedicated ServiceAccounts.
- Bind only required Roles.
- Disable automount for debug/test pods.
- Audit pods using `default`.

### Incident 3: Monitoring Tool Fails After OpenShift Upgrade

An external monitoring system used an old auto-generated token Secret. After upgrade and cleanup, the token was removed or became invalid.

Fix:

- Identify required permissions.
- Create dedicated monitoring ServiceAccount.
- Use `oc create token` if the tool supports refresh.
- Otherwise create manual token Secret with approval.
- Store token in secret manager.
- Document rotation.

### Incident 4: App Fails After Token Rotation

An app reads the ServiceAccount token once at startup. After token rotation, API calls fail.

Fix:

- Update app to reread token file.
- Use Kubernetes client library with proper token reload support.
- Restart pods as temporary workaround.

## 36. Final Key Points

Remember these points for Advanced OpenShift Administration:

1. ServiceAccounts are workload identities.
2. ServiceAccount usernames follow `system:serviceaccount:<namespace>:<name>`.
3. Authentication and authorization are separate.
4. `401` means token/authentication issue.
5. `403` means RBAC/authorization issue.
6. Modern OpenShift uses bound tokens and projected volumes.
7. Long-lived token Secrets are legacy/high-risk.
8. `Tokens: <none>` can be normal on newer OpenShift.
9. Do not grant broad permissions to the `default` ServiceAccount.
10. Disable token automount when API access is not needed.
11. Use `oc auth can-i --as=system:serviceaccount:...` for troubleshooting.
12. Never paste production tokens into online decoders.
13. External integrations should use short-lived tokens if possible.
14. Audit ServiceAccount token Secrets and ClusterRoleBindings regularly.
15. Treat every ServiceAccount token as a password with API access.
