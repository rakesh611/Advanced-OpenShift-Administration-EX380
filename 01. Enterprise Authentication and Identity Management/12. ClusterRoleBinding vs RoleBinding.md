# ClusterRoleBinding vs RoleBinding in OpenShift RBAC

**Area:** Enterprise Authentication and Identity Management  
**Level:** Advanced OpenShift Administration / 10+ years experience  
**Focus:** OpenShift RBAC authorization, user/group/service account access, enterprise identity integration, least privilege, troubleshooting, and production design.

---

## 1. Executive Summary

In OpenShift, authentication answers:

> **Who are you?**

Authorization answers:

> **What are you allowed to do?**

OpenShift uses Kubernetes RBAC objects to authorize users, groups, and service accounts. The two most commonly confused RBAC binding objects are:

| Object | Scope | What it binds | Typical use |
|---|---|---|---|
| `RoleBinding` | Project / namespace | A `Role` in the same namespace or a `ClusterRole` | Grant access only inside one project |
| `ClusterRoleBinding` | Whole cluster | A `ClusterRole` only | Grant access across all projects or to cluster-scoped resources |

The most important rule is:

> **Use `RoleBinding` when access should be limited to one project. Use `ClusterRoleBinding` only when access must apply cluster-wide or to cluster-scoped resources.**

A `ClusterRole` does not automatically mean cluster-wide access. A `ClusterRole` becomes project-scoped when it is attached through a `RoleBinding`.

---

## 2. Why This Topic Matters in Enterprise OpenShift

In a small lab, giving `cluster-admin` to everyone may appear convenient. In enterprise OpenShift, that is dangerous.

A production OpenShift cluster usually has:

- Multiple business teams
- Multiple projects / namespaces
- LDAP, Active Directory, OIDC, Keycloak, or Red Hat SSO integration
- CI/CD service accounts
- Platform engineering users
- Application developers
- Security auditors
- Monitoring and backup operators
- Compliance requirements
- Separation between dev, test, stage, and production workloads

RBAC mistakes can cause:

- Developers accessing production secrets
- CI/CD pipelines modifying unrelated namespaces
- A service account escalating privileges
- A user deleting cluster-scoped resources
- Accidental exposure of OAuth, route, secret, or image registry data
- Compliance audit failure
- Complete cluster compromise

For this reason, an advanced OpenShift administrator must understand the exact difference between `RoleBinding` and `ClusterRoleBinding`.

## 3. OpenShift RBAC Building Blocks

RBAC has four core Kubernetes objects:

| Object | Scope | Purpose |
|---|---|---|
| `Role` | Namespace / project | Defines permissions inside one namespace |
| `ClusterRole` | Cluster | Defines reusable permissions; can include namespaced or cluster-scoped resources |
| `RoleBinding` | Namespace / project | Assigns a `Role` or `ClusterRole` to users, groups, or service accounts inside one namespace |
| `ClusterRoleBinding` | Cluster | Assigns a `ClusterRole` to users, groups, or service accounts across the cluster |

OpenShift also uses projects. In Kubernetes terms:

```text
OpenShift Project = Kubernetes Namespace + OpenShift project metadata
```

So when we say `RoleBinding` is project-scoped in OpenShift, it means it is namespace-scoped in Kubernetes.

## 4. Authorization Flow in OpenShift

When a user runs a command such as:

```bash
oc get pods -n finance-prod
```

OpenShift evaluates:

```text
1. Who is the user?
2. Which groups does the user belong to?
3. Which action is requested?
4. Which project/namespace is targeted?
5. Which RoleBindings apply in that namespace?
6. Which ClusterRoleBindings apply cluster-wide?
7. Which roles are referenced by those bindings?
8. Do any rules allow the requested verb/resource/API group?
9. If no rule matches, deny by default.
```

RBAC is additive:

```text
Allowed + Allowed = Allowed
Allowed + No rule = Allowed
No matching rule = Denied
```

There is no normal RBAC `deny` rule. If a user gets permission from any applicable binding, the request is allowed.

## 5. What Is a RoleBinding?

A `RoleBinding` connects a subject to a role **inside a specific namespace/project**.

Subjects can be:

- User
- Group
- ServiceAccount

A `RoleBinding` can reference:

- A `Role` in the same namespace
- A `ClusterRole` from the cluster scope

But the effect remains limited to the namespace where the `RoleBinding` exists.

### 5.1 Simple Definition

```text
RoleBinding = give this user/group/service account these permissions only in this project
```

### 5.2 Example Use Case

User `alice` should view pods only in project `app-dev`.

```bash
oc adm policy add-role-to-user view alice -n app-dev
```

This creates a `RoleBinding` in the `app-dev` project.

Alice can run:

```bash
oc get pods -n app-dev
```

But she cannot automatically run:

```bash
oc get pods -n app-prod
oc get nodes
oc get projects
```

### 5.3 RoleBinding YAML Referencing a ClusterRole

This is very common in OpenShift because default roles like `view`, `edit`, and `admin` are `ClusterRole` objects, but you usually bind them locally.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-dev-view
  namespace: app-dev
subjects:
  - kind: User
    apiGroup: rbac.authorization.k8s.io
    name: alice
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: view
```

Important point:

```text
ClusterRole + RoleBinding = namespace-level access
```

Even though `view` is a `ClusterRole`, Alice gets `view` access only in `app-dev` because the binding is a `RoleBinding`.

## 6. What Is a ClusterRoleBinding?

A `ClusterRoleBinding` connects a subject to a `ClusterRole` at cluster scope.

### 6.1 Simple Definition

```text
ClusterRoleBinding = give this user/group/service account these permissions across the whole cluster
```

A `ClusterRoleBinding` can reference only a `ClusterRole`. It cannot reference a namespace-scoped `Role`.

### 6.2 Example Use Case

Security auditor `audit-user` should read most cluster objects across all projects.

```bash
oc adm policy add-cluster-role-to-user cluster-reader audit-user
```

This creates a cluster-wide binding.

The user can now inspect resources across namespaces depending on the `cluster-reader` rules.

### 6.3 ClusterRoleBinding YAML

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: audit-user-cluster-reader
subjects:
  - kind: User
    apiGroup: rbac.authorization.k8s.io
    name: audit-user
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: cluster-reader
```

Important point:

```text
ClusterRole + ClusterRoleBinding = cluster-wide access
```

## 7. Core Difference: RoleBinding vs ClusterRoleBinding

| Area | RoleBinding | ClusterRoleBinding |
|---|---|---|
| API kind | `RoleBinding` | `ClusterRoleBinding` |
| Scope | Namespace / project | Entire cluster |
| Has namespace in metadata? | Yes | No |
| Can reference `Role`? | Yes, but only in same namespace | No |
| Can reference `ClusterRole`? | Yes | Yes |
| Grants access to one namespace? | Yes | No, it grants cluster-wide according to role rules |
| Grants access to all namespaces? | No | Yes, if role rules allow namespaced resources |
| Grants access to cluster-scoped resources? | No, normally use ClusterRoleBinding | Yes |
| Used for developers? | Usually yes | Rarely |
| Used for cluster admins? | Sometimes for project admin only | Yes for real cluster admin |
| Risk level | Lower blast radius | Higher blast radius |
| `oc adm policy` command | `add-role-to-user`, `add-role-to-group` | `add-cluster-role-to-user`, `add-cluster-role-to-group` |

## 8. The Most Important Concept: Binding Scope Controls Effective Scope

Many administrators misunderstand this point.

### 8.1 ClusterRole Bound Locally

```text
ClusterRole: view
Binding: RoleBinding in namespace app1
Effective access: view only in app1
```

Command:

```bash
oc adm policy add-role-to-user view alice -n app1
```

Result:

```text
alice can view resources in app1 only.
```

### 8.2 ClusterRole Bound Cluster-Wide

```text
ClusterRole: view
Binding: ClusterRoleBinding
Effective access: view across all namespaces where that role's rules apply
```

Command:

```bash
oc adm policy add-cluster-role-to-user view alice
```

Result:

```text
alice can view resources across many/all projects, depending on the role rules.
```

### 8.3 Same ClusterRole, Different Binding, Different Result

| ClusterRole | Binding type | Effective permission |
|---|---|---|
| `view` | `RoleBinding` in `app1` | View only `app1` |
| `view` | `ClusterRoleBinding` | View across namespaces |
| `edit` | `RoleBinding` in `app1` | Edit only `app1` |
| `edit` | `ClusterRoleBinding` | Edit across namespaces; dangerous |
| `cluster-admin` | `RoleBinding` in `app1` | Administrative power inside `app1` only |
| `cluster-admin` | `ClusterRoleBinding` | Full cluster administrator |

## 9. RoleBinding Deep Dive

### 9.1 RoleBinding with a Namespace Role

Create a custom `Role` in project `finance-dev`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-log-reader
  namespace: finance-dev
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
```

Bind it to user `rakesh`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: rakesh-pod-log-reader
  namespace: finance-dev
subjects:
  - kind: User
    apiGroup: rbac.authorization.k8s.io
    name: rakesh
roleRef:
  kind: Role
  apiGroup: rbac.authorization.k8s.io
  name: pod-log-reader
```

Apply:

```bash
oc apply -f pod-log-reader-role.yaml
oc apply -f rakesh-pod-log-reader-rolebinding.yaml
```

Verify:

```bash
oc auth can-i get pods/log --as=rakesh -n finance-dev
oc auth can-i delete pods --as=rakesh -n finance-dev
oc auth can-i get pods/log --as=rakesh -n finance-prod
```

Expected:

```text
yes
no
no
```

### 9.2 RoleBinding with a ClusterRole

This is more common than creating custom local roles.

```bash
oc adm policy add-role-to-group edit app-dev-team -n finance-dev
```

This grants the group `app-dev-team` the `edit` ClusterRole only inside `finance-dev`.

Equivalent YAML:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-dev-team-edit
  namespace: finance-dev
subjects:
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: app-dev-team
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: edit
```

### 9.3 RoleBinding for a Service Account

A CI/CD pipeline service account should deploy only in `app-dev`.

```bash
oc create serviceaccount deployer-sa -n app-dev
oc adm policy add-role-to-user edit system:serviceaccount:app-dev:deployer-sa -n app-dev
```

Equivalent YAML:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: deployer-sa-edit
  namespace: app-dev
subjects:
  - kind: ServiceAccount
    name: deployer-sa
    namespace: app-dev
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: edit
```

Validate:

```bash
oc auth can-i create deployment \
  --as=system:serviceaccount:app-dev:deployer-sa \
  -n app-dev

oc auth can-i create deployment \
  --as=system:serviceaccount:app-dev:deployer-sa \
  -n app-prod
```

Expected:

```text
yes
no
```

## 10. ClusterRoleBinding Deep Dive

### 10.1 ClusterRoleBinding for a Cluster Administrator

```bash
oc adm policy add-cluster-role-to-user cluster-admin rakesh
```

This grants full cluster administrator privileges.

Verify:

```bash
oc auth can-i '*' '*' --as=rakesh --all-namespaces
oc auth can-i get nodes --as=rakesh
oc auth can-i delete project app-dev --as=rakesh
```

Expected:

```text
yes
yes
yes
```

### 10.2 ClusterRoleBinding for a Read-Only Cluster Auditor

```bash
oc adm policy add-cluster-role-to-user cluster-reader audit-user
```

Verify:

```bash
oc auth can-i get clusteroperators --as=audit-user
oc auth can-i list pods --as=audit-user --all-namespaces
oc auth can-i delete pods --as=audit-user -n app-dev
```

Expected:

```text
yes
yes
no
```

### 10.3 ClusterRoleBinding for an LDAP / AD Group

In enterprise environments, users should usually receive access through groups, not direct per-user bindings.

Example group:

```text
ocp-prod-admins
```

Command:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-prod-admins
```

YAML:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: ocp-prod-admins-cluster-admin
subjects:
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: ocp-prod-admins
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: cluster-admin
```

This is powerful and should be tightly controlled.

## 11. OpenShift Default ClusterRoles

OpenShift ships several default `ClusterRole` objects. These can be bound locally with `RoleBinding` or cluster-wide with `ClusterRoleBinding`, depending on your requirement.

| ClusterRole | Typical use | Safe binding pattern |
|---|---|---|
| `view` | Read application resources in a project | `RoleBinding` |
| `edit` | Modify application resources in a project | `RoleBinding` |
| `admin` | Manage most resources in a project | `RoleBinding` |
| `cluster-reader` | Read most cluster resources | `ClusterRoleBinding` for auditors/platform teams |
| `cluster-admin` | Full cluster administration | `ClusterRoleBinding` only for trusted admins |
| `basic-user` | Basic user information | Usually default/system-managed |
| `self-provisioner` | Create projects | Cluster-level group binding, carefully controlled |

Important:

```text
Default ClusterRoles should not be manually edited.
```

If you need extra permissions, create a new custom `ClusterRole` or use cluster role aggregation where appropriate.

## 12. Local cluster-admin vs Real cluster-admin

This is a common interview and production issue.

### 12.1 Local cluster-admin

Command:

```bash
oc adm policy add-role-to-user cluster-admin rakesh -n app-dev
```

This creates a `RoleBinding` in `app-dev`.

Effective result:

```text
rakesh has high/admin-level permissions only inside app-dev.
```

He is not a true cluster admin.

He may be able to:

```bash
oc delete all --all -n app-dev
oc edit quota -n app-dev
```

But he should not be able to:

```bash
oc get nodes
oc get clusteroperators
oc delete project other-team-prod
```

### 12.2 Real cluster-admin

Command:

```bash
oc adm policy add-cluster-role-to-user cluster-admin rakesh
```

This creates a `ClusterRoleBinding`.

Effective result:

```text
rakesh can perform any action on any resource in the cluster.
```

### 12.3 Interview Answer

If asked:

> What is the difference between binding `cluster-admin` using `add-role-to-user` and `add-cluster-role-to-user`?

Answer:

```text
add-role-to-user creates a namespace-scoped RoleBinding. If cluster-admin is bound this way, the user gets admin-like power only in that project. add-cluster-role-to-user creates a ClusterRoleBinding, so the user becomes a real cluster administrator across the entire cluster.
```

## 13. Namespaced Resources vs Cluster-Scoped Resources

### 13.1 Namespaced Resources

These exist inside a project/namespace:

- Pods
- Deployments
- DeploymentConfigs
- Services
- Routes
- ConfigMaps
- Secrets
- PersistentVolumeClaims
- RoleBindings
- Roles
- Jobs
- CronJobs

`RoleBinding` is usually suitable for these.

Example:

```bash
oc adm policy add-role-to-user view alice -n app-dev
```

### 13.2 Cluster-Scoped Resources

These exist outside a namespace:

- Nodes
- PersistentVolumes
- Namespaces / Projects
- ClusterRoles
- ClusterRoleBindings
- CustomResourceDefinitions
- ClusterOperators
- OAuth cluster object
- IngressControllers
- StorageClasses
- MachineConfigPools
- SecurityContextConstraints

For these, you normally need a `ClusterRole` and `ClusterRoleBinding`.

Example:

```bash
oc adm policy add-cluster-role-to-user cluster-reader audit-user
```

### 13.3 Important Edge Case

A `RoleBinding` can reference a `ClusterRole`, but the binding is still namespace-scoped.

So if a `ClusterRole` contains permissions for cluster-scoped resources, binding it through a `RoleBinding` does not make those cluster-scoped permissions effective in the whole cluster.

For cluster-scoped resources, use `ClusterRoleBinding`.

## 16. Practical Enterprise Access Design

### 16.1 Recommended Group-Based Access Model

Avoid assigning access directly to individual users unless it is temporary or exceptional.

Recommended pattern:

```text
Identity Provider / LDAP / AD / OIDC group
        ↓
OpenShift Group
        ↓
RoleBinding or ClusterRoleBinding
        ↓
Effective access
```

Example groups:

```text
ocp-platform-admins
ocp-security-auditors
finance-dev-admins
finance-dev-developers
finance-dev-viewers
finance-prod-viewers
cicd-deployers-app1
```

### 16.2 Project-Level Developer Access

Use `RoleBinding`:

```bash
oc adm policy add-role-to-group edit finance-dev-developers -n finance-dev
```

### 16.3 Production Read-Only Access

Use `RoleBinding`:

```bash
oc adm policy add-role-to-group view finance-prod-viewers -n finance-prod
```

### 16.4 Project Admin Access

Use `RoleBinding`:

```bash
oc adm policy add-role-to-group admin finance-dev-admins -n finance-dev
```

### 16.5 Cluster Auditor Access

Use `ClusterRoleBinding`:

```bash
oc adm policy add-cluster-role-to-group cluster-reader ocp-security-auditors
```

### 16.6 Full Platform Admin Access

Use `ClusterRoleBinding`, but restrict heavily:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
```

## 17. CI/CD Service Account Design

### 17.1 Bad Design

Do not give a Jenkins, GitLab, Argo CD, or Tekton service account cluster-admin unless it is truly required.

Bad example:

```bash
oc adm policy add-cluster-role-to-user cluster-admin system:serviceaccount:cicd:jenkins
```

This lets the CI/CD service account control the whole cluster.

### 17.2 Better Design: Namespace-Scoped Deployment

```bash
oc create serviceaccount app1-deployer -n app1-dev
oc adm policy add-role-to-user edit system:serviceaccount:app1-dev:app1-deployer -n app1-dev
```

### 17.3 Better Design: Custom Least-Privilege Role

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-deployer-minimal
  namespace: app1-dev
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: ["route.openshift.io"]
    resources: ["routes"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
```

Bind it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app1-deployer-minimal
  namespace: app1-dev
subjects:
  - kind: ServiceAccount
    name: app1-deployer
    namespace: app1-dev
roleRef:
  kind: Role
  apiGroup: rbac.authorization.k8s.io
  name: app-deployer-minimal
```

## 18. Security Risks and Privilege Escalation Areas

### 18.1 Dangerous Verbs

Be very careful with these verbs:

| Verb | Risk |
|---|---|
| `create` | Can create workloads or RBAC objects |
| `update` / `patch` | Can modify existing resources |
| `delete` | Can remove workloads or access controls |
| `bind` | Can bind roles to users/groups/service accounts |
| `escalate` | Can create/update roles with permissions the user does not already hold |
| `impersonate` | Can act as another user/group/service account |
| `use` | Important for SCC access in OpenShift |
| `*` | Wildcard; expands to future resources/verbs too |

### 18.2 Dangerous Resources

Be very careful with these resources:

| Resource | Risk |
|---|---|
| `secrets` | Can expose credentials, tokens, database passwords |
| `pods/exec` | Can enter running containers |
| `pods/attach` | Can attach to container processes |
| `pods/portforward` | Can tunnel to internal services |
| `roles` / `rolebindings` | Can alter namespace RBAC |
| `clusterroles` / `clusterrolebindings` | Can alter cluster RBAC |
| `securitycontextconstraints` | Can allow privileged workloads |
| `nodes/proxy` | Can expose node-level attack surface |
| `persistentvolumes` | Can expose storage access |
| `oauths` | Can affect cluster authentication configuration |

### 18.3 Wildcards Are Dangerous

Avoid:

```yaml
verbs: ["*"]
resources: ["*"]
apiGroups: ["*"]
```

Because Kubernetes and OpenShift are extensible. New APIs and CRDs added later may automatically become accessible if wildcards are used.

### 18.4 Avoid `system:masters`

Do not add normal users to `system:masters`.

Why?

```text
system:masters bypasses normal RBAC checks and gives unrestricted API server access.
```

Use a `ClusterRoleBinding` to `cluster-admin` for controlled cluster administrator access instead.

## 19. RoleRef Immutability

In both `RoleBinding` and `ClusterRoleBinding`, the `roleRef` field is immutable.

That means you cannot change this:

```yaml
roleRef:
  kind: ClusterRole
  name: view
```

To this:

```yaml
roleRef:
  kind: ClusterRole
  name: edit
```

by patching the same binding.

You must delete and recreate the binding:

```bash
oc delete rolebinding app-dev-view -n app-dev
oc adm policy add-role-to-user edit alice -n app-dev
```

For cluster role bindings:

```bash
oc delete clusterrolebinding audit-user-cluster-reader
oc adm policy add-cluster-role-to-user cluster-admin audit-user
```

This is intentional. It prevents accidental or malicious silent privilege escalation through changing the role reference of an existing binding.

## 20. Troubleshooting 403 Forbidden Errors

A typical error:

```text
Error from server (Forbidden): pods is forbidden:
User "alice" cannot list resource "pods" in API group "" in the namespace "app-dev"
```

### 20.1 Troubleshooting Flow

```text
1. Confirm user identity
2. Confirm groups
3. Confirm namespace
4. Check RoleBindings in namespace
5. Check ClusterRoleBindings

Reading pods is not always the same as reading logs.

resources: ["pods/exec"]

```

## 21. Common Mistakes

### Mistake 1: Thinking ClusterRole Always Means Cluster-Wide Access

Wrong:

```text
ClusterRole always gives cluster-wide access.
```

Correct:

```text
ClusterRole defines reusable rules. Binding type decides effective scope.
```

### Mistake 2: Using ClusterRoleBinding for Developers

Bad:

```bash
oc adm policy add-cluster-role-to-group edit app-developers
```

This can grant edit permissions across many/all namespaces.

Better:

```bash
oc adm policy add-role-to-group edit app-developers -n app-dev
```

### Mistake 3: Giving CI/CD cluster-admin

Bad:

```bash
oc adm policy add-cluster-role-to-user cluster-admin system:serviceaccount:cicd:pipeline
```

Better:

```bash
oc adm policy add-role-to-user edit system:serviceaccount:app-dev:pipeline -n app-dev
```

Best:

```text
Create a custom minimal Role and bind it with RoleBinding.
```

### Mistake 4: Binding Users Instead of Groups

Bad:

```bash
oc adm policy add-role-to-user edit user1 -n app-dev
oc adm policy add-role-to-user edit user2 -n app-dev
oc adm policy add-role-to-user edit user3 -n app-dev
```

Better:

```bash
oc adm policy add-role-to-group edit app-dev-developers -n app-dev
```

### Mistake 5: Forgetting ServiceAccount Namespace

Wrong YAML:

```yaml
subjects:
  - kind: ServiceAccount
    name: deployer-sa
```

Better YAML:

```yaml
subjects:
  - kind: ServiceAccount
    name: deployer-sa
    namespace: app-dev
```

### Mistake 6: Editing Default ClusterRoles

Do not manually edit default roles like:

```text
view
edit
admin
cluster-admin
cluster-reader
```

Create a custom role instead.

## 25. RBAC and OpenShift SCC

OpenShift has Security Context Constraints, known as SCCs. SCC permissions are commonly granted using RBAC with the `use` verb.

Example:

```bash
oc adm policy add-scc-to-user anyuid -z my-sa -n app-dev
```

This is not exactly the same as manually creating a normal RoleBinding, but it results in RBAC permissions that allow the service account to use a particular SCC.

Be careful with SCCs such as:

```text
privileged
anyuid
hostnetwork
hostmount-anyuid
```

Grant SCC access only to trusted service accounts and only in required namespaces.

Check who can use privileged SCC:

```bash
oc adm policy who-can use scc/privileged
```

## 27. Decision Tree

Use this decision tree when choosing between `RoleBinding` and `ClusterRoleBinding`.

```text
Do you need to grant permissions only inside one project?
    └── Yes → Use RoleBinding

Do you need to grant access across all projects?
    └── Yes → Use ClusterRoleBinding

Do you need access to cluster-scoped resources like nodes, PVs, CRDs, ClusterOperators, OAuth, or namespaces?
    └── Yes → Use ClusterRole + ClusterRoleBinding

Do you want to reuse a standard role like view/edit/admin in one project?
    └── Use RoleBinding referencing ClusterRole

Do you want a developer to deploy only in one namespace?
    └── Use RoleBinding

Do you want a security auditor to view cluster resources?
    └── Use ClusterRoleBinding to cluster-reader or a custom read-only ClusterRole

Are you about to use cluster-admin?
    └── Stop, verify business justification, approval, owner, expiry, and audit requirement
```

## 28. Exam and Interview Notes

### Q1. What is the difference between RoleBinding and ClusterRoleBinding?

`RoleBinding` grants permissions inside a specific namespace/project. `ClusterRoleBinding` grants permissions at cluster scope using a `ClusterRole`.

### Q2. Can a RoleBinding reference a ClusterRole?

Yes. A `RoleBinding` can reference a `ClusterRole`, but the permission is limited to the namespace where the `RoleBinding` exists.

### Q3. Can a ClusterRoleBinding reference a Role?

No. A `ClusterRoleBinding` can reference only a `ClusterRole`.

### Q4. Why are OpenShift default roles like view/edit/admin ClusterRoles?

Because they are reusable across projects. OpenShift defines them once as `ClusterRole` objects, and administrators bind them locally with `RoleBinding` in different projects.

### Q5. What happens if I bind `cluster-admin` using RoleBinding?

The user gets admin-like privileges only in that namespace/project, not across the whole cluster.

### Q6. What happens if I bind `cluster-admin` using ClusterRoleBinding?

The user becomes a real cluster administrator with full cluster-wide control.

### Q7. Which command gives a user edit access only in one project?

```bash
oc adm policy add-role-to-user edit <user> -n <project>
```

### Q8. Which command gives a user cluster-wide cluster-admin?

```bash
oc adm policy add-cluster-role-to-user cluster-admin <user>
```

### Q9. Which command checks whether a user can delete pods in a namespace?

```bash
oc auth can-i delete pods --as=<user> -n <project>
```

### Q10. Which command shows who can perform an action?

```bash
oc adm policy who-can <verb> <resource> -n <project>
```

Example:

```bash
oc adm policy who-can delete pods -n app-dev
```

## 30. Production Best Practices

1. Prefer `RoleBinding` over `ClusterRoleBinding` whenever possible.
2. Bind access to groups, not individual users.
3. Use LDAP/AD/OIDC groups for enterprise lifecycle management.
4. Avoid `cluster-admin` for daily work.
5. Avoid service account `cluster-admin` unless absolutely required.
6. Use custom roles for CI/CD pipelines.
7. Avoid wildcard verbs/resources.
8. Review `ClusterRoleBinding` objects regularly.
9. Review production project `RoleBinding` objects regularly.
10. Use `oc auth can-i` before and after changes.
11. Use `oc adm policy who-can` during audits.
12. Remove temporary access after change windows.
13. Document owner, purpose, and expiry for elevated access.
14. Do not manually edit default ClusterRoles.
15. Treat access to secrets, SCCs, pods/exec, bind, escalate, and impersonate as high risk.

## 33. Final Senior-Level Explanation

In OpenShift, a `RoleBinding` and a `ClusterRoleBinding` do not define permissions by themselves. They attach a subject to a role. The difference is the scope of the attachment.

A `RoleBinding` lives inside a namespace/project and grants the referenced role only in that project. It can reference either a local `Role` or a reusable `ClusterRole`. This is why OpenShift commonly uses `RoleBinding` to bind default ClusterRoles like `view`, `edit`, and `admin` to users or groups in one project.

A `ClusterRoleBinding` lives at cluster scope and grants a `ClusterRole` across the cluster. It is required for cluster-scoped resources such as nodes, PVs, namespaces, CRDs, cluster operators, OAuth configuration, storage classes, and cluster-wide administration.

From a production security perspective, the binding type controls the blast radius. A local `RoleBinding` limits impact to one project. A `ClusterRoleBinding` can affect the entire cluster. Therefore, advanced OpenShift administrators should use `RoleBinding` by default and reserve `ClusterRoleBinding` for platform admins, auditors, operators, and services that genuinely need cluster-wide access.
