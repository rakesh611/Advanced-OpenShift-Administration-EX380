# Certificate and CA Trust Issues in Enterprise Authentication and Identity Management

**Track:** Advanced OpenShift Administration  
**Audience:** Senior Linux / Kubernetes / OpenShift administrator with ~10 years of experience  
**Focus:** OpenShift 4.x enterprise authentication, OAuth, LDAP, OIDC, ingress, API certificates, service CA, and custom CA trust troubleshooting

---

## 1. Why certificates and CA trust matter in OpenShift authentication

In enterprise OpenShift, authentication is rarely isolated. A login request can involve the user browser, OpenShift OAuth, the API server, the ingress router, an external identity provider, LDAP, OIDC discovery endpoints, corporate proxies, and internal service-to-service TLS. If any certificate or trust bundle is wrong, users might see a simple login failure, but the real issue can be deep in the TLS trust chain.

Common production symptoms include:

- `x509: certificate signed by unknown authority`
- `certificate is valid for X, not Y`
- `unable to get local issuer certificate`
- `self signed certificate in certificate chain`
- `LDAP Result Code 200 "Network Error"`
- `OAuth login failed after redirect`
- `authentication operator degraded`
- `oauth-openshift` pods restarting or refusing connections to the IDP
- Web console certificate warning after custom ingress certificate change
- `oc login` fails, but browser login partially works
- OIDC discovery URL works from laptop but fails from OpenShift
- Router certificate renewed, but clients still complain because intermediate CA is missing

For an advanced administrator, the key is to identify **which side is presenting the certificate** and **which component must trust the CA**.

## 2. Core TLS and CA concepts you must know

### 2.1 Certificate

A certificate binds an identity to a public key. In OpenShift, identities can include:

- `api.<cluster>.<base-domain>`
- `*.apps.<cluster>.<base-domain>`
- `oauth-openshift.apps.<cluster>.<base-domain>`
- `ldap.example.com`
- `keycloak.example.com`
- Internal service names such as `my-service.my-namespace.svc`

A certificate usually contains:

- Subject
- Issuer
- Validity period
- Public key
- Extended Key Usage
- Subject Alternative Name, also called SAN
- Signature from a CA

Modern TLS clients validate hostname mainly through **SAN**, not only Common Name. If the certificate does not contain the correct DNS name in SAN, authentication can fail even if the certificate is otherwise trusted.

### 2.2 CA certificate

A CA certificate is used to verify certificates signed by that CA. OpenShift components do not magically trust every corporate CA. You must place the CA bundle in the correct place depending on the use case.

### 2.3 Root CA and intermediate CA

A production certificate chain is often:

```text
Server certificate
  signed by Intermediate CA
    signed by Root CA
```

The server usually presents the server certificate plus intermediate certificates. The client usually already trusts the root CA. If the server does not present the intermediate CA, many clients fail with chain validation errors.

### 2.4 Trust store

A trust store is the list of CA certificates a client trusts.

In OpenShift, there are multiple trust stores:

- RHCOS node OS trust store
- Cluster-wide OpenShift trust bundle through `proxy/cluster.spec.trustedCA`
- Identity provider-specific CA bundle through `OAuth.spec.identityProviders[].<provider>.ca`
- Service CA bundle injected into ConfigMaps, APIServices, CRDs, and webhook configurations
- Application container image trust store
- Java trust store inside JVM-based applications
- Browser or laptop trust store
- External corporate proxy trust store

A major production mistake is updating one trust store and assuming all components use it. They do not.

## 3. OpenShift certificate and trust areas

### 3.1 Ingress wildcard certificate

The ingress certificate is what external users see when they access routes under:

```text
*.apps.<cluster-name>.<base-domain>
```

Examples:

```text
https://console-openshift-console.apps.ocp.example.com
https://oauth-openshift.apps.ocp.example.com
https://myapp-prod.apps.ocp.example.com
```

By default, OpenShift creates an internal CA and uses it to issue a wildcard certificate for the `.apps` subdomain. This is acceptable for internal cluster trust, but enterprise users usually replace it with a certificate signed by a public or corporate CA.

Important points:

- The certificate must include SAN for `*.apps.<cluster>.<domain>`.
- The certificate file must include the chain in the correct order: wildcard certificate first, intermediate CA certificates next, and root CA last if required by your PKI process.
- The private key must be unencrypted.
- The secret is created in `openshift-ingress`.
- The Ingress Controller is patched in `openshift-ingress-operator`.
- Updating the secret contents allows router hot reload when the secret name remains the same.

Example:

```bash
oc create secret tls apps-wildcard-cert \
  --cert=/root/certs/apps-wildcard-chain.crt \
  --key=/root/certs/apps-wildcard.key \
  -n openshift-ingress

oc patch ingresscontroller.operator default \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"apps-wildcard-cert"}}}' \
  -n openshift-ingress-operator

oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get pods -n openshift-ingress
```

Verify from an external client:

```bash
openssl s_client \
  -connect console-openshift-console.apps.ocp.example.com:443 \
  -servername console-openshift-console.apps.ocp.example.com \
  -showcerts </dev/null
```

Check the SAN:

```bash
openssl s_client \
  -connect console-openshift-console.apps.ocp.example.com:443 \
  -servername console-openshift-console.apps.ocp.example.com </dev/null 2>/dev/null \
| openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### 3.2 API server certificate

The API server certificate is used by clients connecting to:

```text
https://api.<cluster-name>.<base-domain>:6443
```

By default, the API certificate is issued by an internal OpenShift CA. External clients might not trust it unless their kubeconfig contains the CA data or their OS trust store has the CA. In enterprise environments, you can configure an API server named certificate.

Important points:

- Use a certificate for `api.<cluster>.<domain>`.
- Include SAN for the API FQDN.
- Do not configure a named certificate for `api-int.<cluster>.<domain>`; that endpoint is used internally.
- The secret is created in `openshift-config`.
- The API server config is patched through `apiserver/cluster`.
- Initial named certificate configuration rolls out a new API server revision.
- Renewal by replacing the referenced secret can be hot-reloaded.

Example:

```bash
oc create secret tls api-cert \
  --cert=/root/certs/api-chain.crt \
  --key=/root/certs/api.key \
  -n openshift-config

oc patch apiserver cluster --type=merge -p '
{
  "spec": {
    "servingCerts": {
      "namedCertificates": [
        {
          "names": ["api.ocp.example.com"],
          "servingCertificate": {
            "name": "api-cert"
          }
        }
      ]
    }
  }
}'

oc get clusteroperator kube-apiserver
oc get pods -n openshift-kube-apiserver
```

Renew existing secret without changing its name:

```bash
oc create secret tls api-cert \
  --cert=/root/certs/new-api-chain.crt \
  --key=/root/certs/new-api.key \
  -n openshift-config \
  --dry-run=client -o yaml | oc replace -f -

oc get clusteroperator kube-apiserver
```

### 3.3 OAuth route certificate

The OpenShift OAuth endpoint is normally exposed through a route such as:

```text
https://oauth-openshift.apps.<cluster>.<domain>
```

This route uses the ingress wildcard certificate unless you customize the route or ingress behavior. Therefore, a bad ingress certificate can break authentication flows even if the identity provider configuration is correct.

Common OAuth route certificate problems:

- Browser blocks OAuth endpoint because corporate CA is not trusted on user laptops.
- OIDC provider rejects callback URL because TLS endpoint is invalid or callback URI mismatched.
- `oc login` token retrieval fails due to untrusted `oauth-openshift.apps` certificate.
- CLI works with `--insecure-skip-tls-verify`, but this is not acceptable for production.

Check OAuth route:

```bash
oc get route oauth-openshift -n openshift-authentication -o wide
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift --tail=100
```

External check:

```bash
curl -Iv https://oauth-openshift.apps.ocp.example.com
```

## 4. Identity provider-specific CA trust

OpenShift identity providers use the `OAuth` cluster resource:

```bash
oc get oauth cluster -o yaml
oc edit oauth cluster
```

The most important namespace for authentication secrets and CA bundles is:

```text
openshift-config
```

Identity provider CA ConfigMaps must normally be in `openshift-config` and must use the key:

```text
ca.crt
```

If the key name is wrong, the identity provider can be ignored or fail TLS validation.

Create an IDP CA ConfigMap:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/root/certs/corp-root-and-intermediate-ca.pem \
  -n openshift-config

oc get configmap ldap-ca -n openshift-config -o yaml
```

Do not use `ca-bundle.crt` for an identity provider CA ConfigMap. For OAuth identity providers, the expected key is usually `ca.crt`. `ca-bundle.crt` is used for cluster-wide trusted CA through the `Proxy` object.

## 5. LDAP certificate and trust issues

### 5.1 LDAP modes

OpenShift LDAP identity provider can use:

```text
ldap://host:389
ldaps://host:636
```

With `ldap://`, OpenShift can use StartTLS depending on the `insecure` setting. With `ldaps://`, TLS starts immediately on port 636.

High-level meaning:

```yaml
insecure: true
```

- Uses insecure LDAP for `ldap://`.
- Should not be used in production.
- Does not make sense with `ldaps://` because LDAPS always uses TLS.

```yaml
insecure: false
```

- For `ldap://`, OpenShift attempts StartTLS.
- For `ldaps://`, OpenShift uses LDAPS.

### 5.2 LDAP IDP example with CA

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corp-ldap
    mappingMethod: claim
    type: LDAP
    ldap:
      url: ldaps://ldap.example.com:636/ou=users,dc=example,dc=com?uid?sub?(objectClass=person)
      bindDN: uid=openshift-bind,ou=svc,dc=example,dc=com
      bindPassword:
        name: ldap-bind-secret
      ca:
        name: ldap-ca
      insecure: false
      attributes:
        id:
        - dn
        preferredUsername:
        - uid
        name:
        - cn
        email:
        - mail
```

Create bind password secret:

```bash
oc create secret generic ldap-bind-secret \
  --from-literal=bindPassword='StrongPasswordHere' \
  -n openshift-config
```

Create CA ConfigMap:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/root/certs/ldap-ca.pem \
  -n openshift-config
```

Apply OAuth configuration:

```bash
oc apply -f oauth-ldap.yaml
oc get co authentication
oc get pods -n openshift-authentication
```

### 5.3 LDAP TLS troubleshooting

From an admin workstation:

```bash
openssl s_client -connect ldap.example.com:636 \
  -servername ldap.example.com \
  -showcerts </dev/null
```

Check certificate details:

```bash
openssl s_client -connect ldap.example.com:636 \
  -servername ldap.example.com </dev/null 2>/dev/null \
| openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

Verify with CA:

```bash
openssl s_client -connect ldap.example.com:636 \
  -servername ldap.example.com \
  -CAfile ldap-ca.pem </dev/null
```

Test LDAP bind from a Linux host:

```bash
LDAPTLS_CACERT=/root/certs/ldap-ca.pem ldapsearch \
  -H ldaps://ldap.example.com:636 \
  -D 'uid=openshift-bind,ou=svc,dc=example,dc=com' \
  -W \
  -b 'ou=users,dc=example,dc=com' \
  '(uid=rakesh)'
```

StartTLS test:

```bash
LDAPTLS_CACERT=/root/certs/ldap-ca.pem ldapsearch \
  -H ldap://ldap.example.com:389 \
  -ZZ \
  -D 'uid=openshift-bind,ou=svc,dc=example,dc=com' \
  -W \
  -b 'ou=users,dc=example,dc=com' \
  '(uid=rakesh)'
```

Common LDAP CA mistakes:

| Mistake | Result | Fix |
|---|---|---|
| ConfigMap key is `ca-bundle.crt` instead of `ca.crt` | IDP not honored or TLS trust fails | Recreate ConfigMap with `ca.crt` |
| CA ConfigMap created in wrong namespace | OAuth cannot find it | Create in `openshift-config` |
| LDAP cert SAN has old hostname | Hostname mismatch | Reissue LDAP cert with correct SAN |
| Missing intermediate CA | Unknown authority | Include intermediate in CA bundle or server chain |
| Using `ldaps://IP:636` while cert has DNS SAN only | Hostname mismatch | Use DNS name or reissue cert with IP SAN |
| `insecure: true` used in production | Credentials exposed | Use LDAPS or StartTLS with CA |
| Firewall allows 389 but not 636 | Timeout | Open required port |
| Corporate proxy intercepts LDAP path | Unexpected issuer | Bypass proxy; LDAP should not go through HTTP proxy |

## 6. OIDC, Keycloak, Red Hat SSO, and CA trust issues

OIDC authentication depends heavily on HTTPS. OpenShift must connect to the issuer and discovery endpoints, for example:

```text
https://keycloak.example.com/realms/ocp/.well-known/openid-configuration
```

If the issuer certificate is signed by a private CA, OpenShift must trust that CA through the OIDC IDP `ca` field.

### 6.1 OIDC IDP with custom CA

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: keycloak
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift
      clientSecret:
        name: keycloak-client-secret
      ca:
        name: keycloak-ca
      issuer: https://keycloak.example.com/realms/ocp
      claims:
        preferredUsername:
        - preferred_username
        - email
        name:
        - name
        email:
        - email
        groups:
        - groups
```

Create secret:

```bash
oc create secret generic keycloak-client-secret \
  --from-literal=clientSecret='OIDC_CLIENT_SECRET' \
  -n openshift-config
```

Create CA ConfigMap:

```bash
oc create configmap keycloak-ca \
  --from-file=ca.crt=/root/certs/keycloak-ca.pem \
  -n openshift-config
```

### 6.2 OIDC discovery troubleshooting

Test discovery from workstation:

```bash
curl -v --cacert keycloak-ca.pem \
  https://keycloak.example.com/realms/ocp/.well-known/openid-configuration
```

Check certificate:

```bash
openssl s_client \
  -connect keycloak.example.com:443 \
  -servername keycloak.example.com \
  -showcerts </dev/null
```

Check issuer value:

```bash
curl -s --cacert keycloak-ca.pem \
  https://keycloak.example.com/realms/ocp/.well-known/openid-configuration \
| jq -r .issuer
```

The `issuer` in OpenShift must exactly match the issuer returned by discovery. Mismatches such as trailing slash differences, HTTP vs HTTPS, internal hostname vs external hostname, or realm path differences can break login.

### 6.3 OIDC CA trust checklist

- Can OpenShift resolve the OIDC hostname?
- Is the OIDC certificate valid and not expired?
- Does the certificate SAN include the hostname used in `issuer`?
- Does the certificate chain include intermediate CAs?
- Is the private CA stored in `openshift-config` ConfigMap with key `ca.crt`?
- Is the `openID.ca.name` correct?
- Is the `clientSecret` secret in `openshift-config`?
- Is the redirect URI exactly configured in Keycloak or the OIDC provider?
- Is the OAuth route certificate trusted by user browsers?
- Is a corporate proxy intercepting outbound HTTPS from OpenShift to the OIDC provider?

## 7. Request-header identity provider and CA trust

Request-header identity provider is usually used behind an authenticating proxy. OpenShift trusts the proxy to inject identity headers. This is powerful and dangerous if not secured properly.

In this model, CA trust is used to verify incoming requests from the authenticating proxy and prevent header spoofing.

Important points:

- The request-header IDP requires a CA bundle.
- The CA must validate the client certificate used by the authenticating proxy.
- If any client can spoof headers without certificate verification, authentication can be compromised.
- `clientCommonNames` can restrict which client certificate common names are accepted.

Example structure:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: request-header-idp
    mappingMethod: claim
    type: RequestHeader
    requestHeader:
      ca:
        name: proxy-client-ca
      clientCommonNames:
      - auth-proxy.example.com
      headers:
      - X-Remote-User
      emailHeaders:
      - X-Remote-User-Email
      nameHeaders:
      - X-Remote-User-Display-Name
      preferredUsernameHeaders:
      - X-Remote-User
```

Troubleshooting questions:

- Is the proxy client certificate signed by the CA in `proxy-client-ca`?
- Is the ConfigMap key `ca.crt`?
- Does the client certificate CN match `clientCommonNames`, if configured?
- Is the proxy the only component allowed to connect to OAuth with those headers?
- Are headers stripped from untrusted requests before reaching OpenShift?

## 8. Cluster-wide custom CA trust

Cluster-wide custom CA trust is configured through the `Proxy` object named `cluster`.

This is used when platform components need to trust a corporate CA for outbound HTTPS, such as:

- Proxy TLS interception CA
- Corporate registry CA
- Internal Git server CA
- Internal artifact repository CA
- Internal OIDC/LDAP endpoints in some cases
- Egress HTTPS endpoints used by platform components

The required ConfigMap key is:

```text
ca-bundle.crt
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: custom-ca-bundle
  namespace: openshift-config
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    <PEM_ENCODED_CA>
    -----END CERTIFICATE-----
```

Apply and patch:

```bash
oc apply -f custom-ca-bundle.yaml

oc patch proxy/cluster --type=merge \
  --patch='{"spec":{"trustedCA":{"name":"custom-ca-bundle"}}}'
```

Verify:

```bash
oc get proxy cluster -o yaml
oc get configmap trusted-ca-bundle -n openshift-config-managed -o yaml
oc get mcp
oc get nodes
```

### 8.1 Cluster-wide CA versus IDP CA

This distinction is critical.

| Use case | Namespace | Key | Referenced by |
|---|---:|---:|---|
| Cluster-wide additional CA | `openshift-config` | `ca-bundle.crt` | `proxy/cluster.spec.trustedCA.name` |
| LDAP/OIDC/GitHub Enterprise/GitLab Enterprise IDP CA | `openshift-config` | `ca.crt` | `oauth/cluster.spec.identityProviders[].<provider>.ca.name` |
| Service CA injection into pod ConfigMap | Application namespace | `service-ca.crt` injected automatically | `service.beta.openshift.io/inject-cabundle=true` |
| Webhook CA injection | Cluster-scoped webhook resource | `clientConfig.caBundle` injected | `service.beta.openshift.io/inject-cabundle=true` |

A very common mistake is creating a single ConfigMap and trying to use it for all cases. Do not do that. The expected key names and controllers are different.

## 9. Service CA and internal service certificates

OpenShift has a Service CA Operator. It can issue serving certificates for internal services. This is useful for service-to-service TLS inside the cluster.

### 9.1 Generate service serving certificate

Annotate a service:

```bash
oc annotate service my-service \
  service.beta.openshift.io/serving-cert-secret-name=my-service-tls \
  -n my-namespace
```

OpenShift creates a secret:

```bash
oc get secret my-service-tls -n my-namespace -o yaml
```

The secret contains:

```text
tls.crt
tls.key
```

The generated certificate is valid for internal service DNS names such as:

```text
my-service.my-namespace.svc
```

### 9.2 Inject service CA into ConfigMap

Create an empty ConfigMap:

```bash
oc create configmap service-ca-bundle -n my-namespace
```

Annotate it:

```bash
oc annotate configmap service-ca-bundle \
  service.beta.openshift.io/inject-cabundle=true \
  -n my-namespace
```

Verify:

```bash
oc get configmap service-ca-bundle -n my-namespace -o yaml
```

The Service CA Operator injects:

```text
service-ca.crt
```

Important warning: when you annotate a ConfigMap for service CA injection, existing data in that ConfigMap can be deleted. Use a dedicated ConfigMap only for the service CA bundle.

### 9.3 Inject service CA into webhook configurations

For admission webhooks backed by services using OpenShift service serving certificates, annotate the webhook configuration:

```bash
oc annotate validatingwebhookconfiguration my-webhook \
  service.beta.openshift.io/inject-cabundle=true

oc get validatingwebhookconfiguration my-webhook -o yaml \
  | grep -A5 caBundle
```

For mutating webhook:

```bash
oc annotate mutatingwebhookconfiguration my-webhook \
  service.beta.openshift.io/inject-cabundle=true
```

If `caBundle` is empty or wrong, the Kubernetes API server cannot validate the webhook service certificate. This can block object creation and cause severe admission failures.

### 9.4 Rotate service certificate

Delete the generated secret. The Service CA Operator recreates it.

```bash
oc describe service my-service -n my-namespace \
  | grep service.beta.openshift.io/serving-cert-secret-name

oc delete secret my-service-tls -n my-namespace

oc get secret my-service-tls -n my-namespace
```

## 10. Certificate chain validation commands

### 10.1 Show remote certificate chain

```bash
openssl s_client -connect HOST:PORT -servername HOST -showcerts </dev/null
```

Examples:

```bash
openssl s_client -connect api.ocp.example.com:6443 -servername api.ocp.example.com -showcerts </dev/null
openssl s_client -connect oauth-openshift.apps.ocp.example.com:443 -servername oauth-openshift.apps.ocp.example.com -showcerts </dev/null
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com -showcerts </dev/null
openssl s_client -connect keycloak.example.com:443 -servername keycloak.example.com -showcerts </dev/null
```

### 10.2 Decode certificate

```bash
openssl x509 -in cert.crt -noout -text
openssl x509 -in cert.crt -noout -subject -issuer -dates
openssl x509 -in cert.crt -noout -ext subjectAltName
openssl x509 -in cert.crt -noout -fingerprint -sha256
```

### 10.3 Verify certificate against CA

```bash
openssl verify -CAfile ca.pem server.crt
```

With intermediate:

```bash
cat intermediate.pem root-ca.pem > ca-chain.pem
openssl verify -CAfile ca-chain.pem server.crt
```

### 10.4 Extract certificate from Kubernetes secret

```bash
oc get secret apps-wildcard-cert -n openshift-ingress \
  -o jsonpath='{.data.tls\.crt}' | base64 -d > tls.crt

openssl x509 -in tls.crt -noout -subject -issuer -dates -ext subjectAltName
```

Extract key and compare modulus:

```bash
oc get secret apps-wildcard-cert -n openshift-ingress \
  -o jsonpath='{.data.tls\.key}' | base64 -d > tls.key

openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

The hashes must match. If they do not match, the certificate and private key are not a pair.

### 10.5 Check expiration across secrets

Ingress certificate:

```bash
oc get secret apps-wildcard-cert -n openshift-ingress \
  -o jsonpath='{.data.tls\.crt}' | base64 -d \
| openssl x509 -noout -enddate
```

API certificate:

```bash
oc get secret api-cert -n openshift-config \
  -o jsonpath='{.data.tls\.crt}' | base64 -d \
| openssl x509 -noout -enddate
```

Service CA signing key:

```bash
oc get secret signing-key -n openshift-service-ca \
  -o jsonpath='{.data.tls\.crt}' | base64 -d \
| openssl x509 -noout -enddate
```

## 11. OpenShift authentication troubleshooting workflow

### Step 1: Identify the failed path

Ask:

- Does `oc login` fail or only browser login?
- Does `kubeadmin` still work?
- Does only LDAP login fail?
- Does only OIDC login fail?
- Does the console load but login redirect fails?
- Does the API server certificate fail before OAuth is reached?
- Are all users impacted or only users from one IDP?

### Step 2: Check cluster operators

```bash
oc get co authentication
oc get co kube-apiserver
oc get co ingress
oc get co console
oc get co openshift-apiserver
```

Detailed:

```bash
oc describe co authentication
oc describe co kube-apiserver
oc describe co ingress
```

### Step 3: Check OAuth pods

```bash
oc get pods -n openshift-authentication -o wide
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

Authentication operator:

```bash
oc get pods -n openshift-authentication-operator
oc logs -n openshift-authentication-operator deploy/authentication-operator --tail=200
```

### Step 4: Check OAuth configuration

```bash
oc get oauth cluster -o yaml
```

Look for:

- Correct provider type
- Correct `ca.name`
- Correct secret name
- Correct `mappingMethod`
- Correct `issuer` for OIDC
- Correct LDAP URL
- Correct `insecure` setting
- Multiple IDPs accidentally overwritten

### Step 5: Check referenced objects

```bash
oc get configmap -n openshift-config
oc get secret -n openshift-config

oc get configmap ldap-ca -n openshift-config -o yaml
oc get secret ldap-bind-secret -n openshift-config -o yaml
```

Validate keys:

```bash
oc get configmap ldap-ca -n openshift-config -o jsonpath='{.data.ca\.crt}' | head
oc get secret ldap-bind-secret -n openshift-config -o jsonpath='{.data.bindPassword}' | base64 -d
```

### Step 6: Test external endpoint TLS

LDAP:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com -showcerts </dev/null
```

OIDC:

```bash
curl -v --cacert keycloak-ca.pem \
  https://keycloak.example.com/realms/ocp/.well-known/openid-configuration
```

OAuth route:

```bash
openssl s_client -connect oauth-openshift.apps.ocp.example.com:443 \
  -servername oauth-openshift.apps.ocp.example.com \
  -showcerts </dev/null
```

API server:

```bash
openssl s_client -connect api.ocp.example.com:6443 \
  -servername api.ocp.example.com \
  -showcerts </dev/null
```

### Step 7: Determine who needs to trust whom

Use this table:

| Scenario | Server presents cert | Client that must trust CA |
|---|---|---|
| User opens console | Ingress router | User browser / workstation |
| `oc login` to API | API server | Admin workstation / kubeconfig |
| OAuth connects to LDAP | LDAP server | OAuth pod / authentication component |
| OAuth connects to Keycloak | Keycloak server | OAuth pod / authentication component |
| Keycloak redirects back to OpenShift | OAuth route | User browser and OIDC provider behavior |
| API server calls admission webhook | Webhook service | Kubernetes API server via `caBundle` |
| App calls internal service | Internal service | App pod trust store |
| Platform component calls corporate HTTPS endpoint | External endpoint or proxy | Cluster-wide trust bundle or component-specific trust |

### Step 8: Avoid unsafe shortcuts

Do not use these as permanent fixes:

```bash
oc login --insecure-skip-tls-verify
curl -k
insecure: true
```

They are useful only to confirm that the issue is TLS trust. Production fix requires correct certificates and CA trust.

## 12. Common root causes and fixes

### 12.1 Unknown authority

Error:

```text
x509: certificate signed by unknown authority
```

Meaning:

The client does not trust the CA that signed the server certificate.

Fix:

- Add correct CA to the correct trust store.
- For LDAP/OIDC IDP, create ConfigMap in `openshift-config` with `ca.crt` and reference it in OAuth.
- For cluster-wide egress CA, create ConfigMap with `ca-bundle.crt` and patch `proxy/cluster`.
- For browser trust, install corporate root CA on user workstation or use public CA.
- For application pod trust, mount CA or bake CA into image trust store.

### 12.2 Hostname mismatch

Error:

```text
certificate is valid for ldap01.example.com, not ldap.example.com
```

Meaning:

The hostname used by the client does not match certificate SAN.

Fix:

- Use the DNS name present in the certificate SAN.
- Reissue certificate with correct SAN.
- Avoid connecting by IP unless IP SAN exists.
- Ensure OIDC `issuer` uses the same hostname as certificate SAN.

### 12.3 Expired certificate

Error:

```text
certificate has expired or is not yet valid
```

Fix:

- Check `notBefore` and `notAfter`.
- Confirm node and client time synchronization.
- Renew certificate.
- Replace secret content without changing secret name where possible.
- Watch operator rollout.

### 12.4 Missing intermediate certificate

Error:

```text
unable to get local issuer certificate
```

Fix:

- Include intermediate CA in server chain.
- For ingress/API secret, use full chain file.
- Verify with `openssl s_client -showcerts`.

### 12.5 Wrong ConfigMap key

Examples:

```text
ca-bundle.crt used for LDAP IDP
ca.crt used for proxy trustedCA
```

Fix:

- For OAuth IDP CA, key must be `ca.crt`.
- For cluster-wide Proxy trusted CA, key must be `ca-bundle.crt`.
- For service CA injected ConfigMap, key becomes `service-ca.crt`.

### 12.6 ConfigMap or Secret in wrong namespace

Fix:

- OAuth IDP secrets and CA ConfigMaps go in `openshift-config`.
- Ingress wildcard TLS secret goes in `openshift-ingress`.
- Service serving certificate secret is created in the same namespace as the service.
- Service CA injected ConfigMap is usually in the application namespace.

### 12.7 Certificate and private key mismatch

Fix:

```bash
openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

If output differs, use the correct key.

### 12.8 OAuth IDP not honored

Possible causes:

- Referenced ConfigMap missing
- Referenced Secret missing
- Wrong expected key name
- Invalid PEM content
- YAML indentation issue
- Unsupported field for provider type
- Invalid LDAP URL
- Invalid OIDC issuer

Check:

```bash
oc describe co authentication
oc logs -n openshift-authentication-operator deploy/authentication-operator --tail=200
oc get oauth cluster -o yaml
```

## 13. Enterprise scenarios

### Scenario 1: LDAP login fails after LDAP certificate renewal

Symptoms:

```text
Login failed
x509: certificate signed by unknown authority
```

Investigation:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com -showcerts </dev/null
oc get oauth cluster -o yaml
oc get cm ldap-ca -n openshift-config -o yaml
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

Likely cause:

LDAP team renewed the LDAP certificate using a new intermediate or new root CA. OpenShift still has the old CA bundle.

Fix:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/root/certs/new-ldap-ca-chain.pem \
  -n openshift-config \
  --dry-run=client -o yaml | oc replace -f -

oc delete pod -n openshift-authentication -l app=oauth-openshift
oc get co authentication
```

### Scenario 2: Console shows certificate warning after ingress certificate update

Symptoms:

- Browser warns about `console-openshift-console.apps...`
- `oc login` token page warning
- Apps under `.apps` show warning

Investigation:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get secret <secret> -n openshift-ingress -o yaml
openssl s_client -connect console-openshift-console.apps.ocp.example.com:443 \
  -servername console-openshift-console.apps.ocp.example.com -showcerts </dev/null
```

Likely causes:

- Wildcard certificate SAN is wrong.
- Secret contains only leaf certificate and not intermediate chain.
- Root CA is private and not trusted by user workstations.
- Wrong secret referenced in IngressController.

Fix:

- Rebuild full chain file.
- Replace TLS secret.
- Patch IngressController if needed.
- Ensure enterprise root CA is trusted by corporate devices or use public CA.

### Scenario 3: OIDC discovery fails from OpenShift but works from laptop

Symptoms:

```text
failed to fetch provider discovery document
x509: certificate signed by unknown authority
```

Investigation:

```bash
curl -v --cacert keycloak-ca.pem \
  https://keycloak.example.com/realms/ocp/.well-known/openid-configuration

oc get cm keycloak-ca -n openshift-config -o yaml
oc get oauth cluster -o yaml
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

Likely causes:

- Laptop trusts corporate CA but OpenShift OAuth does not.
- OIDC CA ConfigMap missing or key is wrong.
- Corporate proxy is presenting a different certificate to OpenShift.
- `issuer` uses internal hostname but certificate SAN has public hostname.

Fix:

- Add correct CA to `openID.ca.name` ConfigMap with key `ca.crt`.
- Correct issuer URL.
- Fix Keycloak certificate SAN.
- Configure proxy/noProxy correctly if a corporate proxy is involved.

### Scenario 4: API certificate renewed and custom automation starts failing

Symptoms:

```text
x509: certificate signed by unknown authority
```

Only custom automation fails. `oc` from admin laptop works.

Likely cause:

Automation has a pinned CA bundle or old kubeconfig. The API certificate was renewed by a new CA.

Fix:

- Update automation kubeconfig CA data.
- Update trust store in automation runner.
- Restart long-running clients that do not hot-reload trust stores.

### Scenario 5: Admission webhook blocks deployments after certificate change

Symptoms:

```text
failed calling webhook: x509: certificate signed by unknown authority
```

Investigation:

```bash
oc get validatingwebhookconfigurations
oc get validatingwebhookconfiguration <name> -o yaml | grep -A10 caBundle
oc get svc -n <webhook-namespace>
oc get secret -n <webhook-namespace>
```

Likely cause:

Webhook service certificate rotated, but `caBundle` was not updated.

Fix if using OpenShift service CA:

```bash
oc annotate validatingwebhookconfiguration <name> \
  service.beta.openshift.io/inject-cabundle=true --overwrite
```

Then confirm `clientConfig.caBundle` is populated.

### Scenario 6: ConfigMap data disappeared after adding service CA annotation

Symptoms:

Application configuration stored in ConfigMap disappears.

Cause:

The ConfigMap was annotated with:

```text
service.beta.openshift.io/inject-cabundle=true
```

The Service CA Operator owns the data and injects `service-ca.crt`. Existing data can be removed.

Fix:

- Use a dedicated ConfigMap only for service CA.
- Restore application config to a separate ConfigMap.
- Mount both ConfigMaps in the pod.

## 14. Production best practices

### 14.1 Certificate design

- Use public CA for external-facing production clusters when possible.
- Use corporate CA only if corporate devices and OpenShift trust are properly managed.
- Always include SAN; do not rely on CN.
- Use full certificate chains for ingress and API certificates.
- Keep private keys unencrypted when importing into OpenShift secrets.
- Use separate certificates for API and apps wildcard.
- Avoid using internal OpenShift-generated ingress certificates in production-facing clusters.

### 14.2 CA bundle design

- Maintain a central source of truth for corporate root and intermediate CAs.
- Version CA bundles in GitOps.
- Separate ConfigMaps by purpose.
- Do not mix service CA injection and cluster trusted CA injection in the same ConfigMap.
- Do not manually edit Operator-managed injected ConfigMaps.
- Track CA expiry, not only leaf certificate expiry.

### 14.3 Change management

Before certificate change:

```bash
oc get co
oc get nodes
oc get ingresscontroller default -n openshift-ingress-operator -o yaml > before-ingress.yaml
oc get apiserver cluster -o yaml > before-apiserver.yaml
oc get oauth cluster -o yaml > before-oauth.yaml
```

Validate files:

```bash
openssl x509 -in cert.crt -noout -subject -issuer -dates -ext subjectAltName
openssl rsa -in cert.key -check -noout
openssl verify -CAfile ca-chain.pem cert.crt
```

After change:

```bash
oc get co
oc get pods -A | egrep 'authentication|ingress|kube-apiserver|console'
oc login -u testuser
curl -Iv https://console-openshift-console.apps.ocp.example.com
```

### 14.4 Monitoring and alerting

Monitor:

- Cluster operator degraded conditions
- Certificate expiration alerts
- Router reload errors
- OAuth login failures
- LDAP bind failures
- OIDC discovery failures
- Webhook TLS errors
- Node NotReady events after trust updates

Useful commands:

```bash
oc get co
oc adm top nodes
oc get events -A --sort-by=.lastTimestamp | tail -100
oc get apiserver cluster -o yaml
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get proxy cluster -o yaml
```

## 15. Exam and interview-style quick answers

### Q1. User login fails with `x509: certificate signed by unknown authority` after configuring LDAP. What will you check?

Check the LDAP server certificate chain with `openssl s_client`, verify SAN and expiry, confirm the LDAP CA bundle exists in `openshift-config`, confirm the ConfigMap key is `ca.crt`, confirm `OAuth.spec.identityProviders[].ldap.ca.name` references it, and review `oauth-openshift` and authentication operator logs.

### Q2. What is the difference between `ca.crt` and `ca-bundle.crt` in OpenShift?

`ca.crt` is commonly used by identity provider CA ConfigMaps referenced by OAuth IDP configuration. `ca-bundle.crt` is used by the cluster-wide trusted CA ConfigMap referenced by `proxy/cluster.spec.trustedCA`. Service CA injection creates `service-ca.crt` in an annotated ConfigMap.

### Q3. Why does `curl -k` work but OpenShift login fails?

`curl -k` disables certificate verification. It proves the endpoint is reachable but does not prove trust is configured correctly. OpenShift login requires proper TLS validation unless intentionally configured otherwise, which should not be done in production.

### Q4. Why should you not use `insecure: true` for LDAP?

Because credentials can be sent without TLS protection for `ldap://` connections. In enterprise environments, use LDAPS or StartTLS with a trusted CA.

### Q5. Why did the router not roll out after renewing the wildcard certificate?

If the secret name remains the same and only certificate/key content changes, kubelet propagates the updated mounted secret and the router can hot-reload the certificate. A rolling update is not necessarily triggered.

### Q6. Why did API clients fail after renewing an API certificate signed by a new CA?

Clients that communicate with the API server must trust the new CA chain. Long-running clients or custom pods might not hot-reload trust stores and may require restart or kubeconfig/trust bundle update.

### Q7. What is the safest way to rotate a service serving certificate?

Delete the generated service certificate secret. The Service CA Operator recreates it. Ensure clients trust the service CA bundle and restart clients if they do not reload trust automatically.

### Q8. How do you confirm a certificate and key match?

Compare modulus hashes:

```bash
openssl x509 -noout -modulus -in tls.crt | openssl md5
openssl rsa  -noout -modulus -in tls.key | openssl md5
```

The output must match.

## 21. Key takeaways

Certificate and CA trust issues in OpenShift are not solved by one universal CA bundle. You must map the TLS relationship correctly:

```text
Who is the server?
Who is the client?
Which certificate is presented?
Which CA signed it?
Where does the client load trusted CAs from?
```

For enterprise authentication:

- LDAP and OIDC CA trust is usually configured in `oauth/cluster` using a ConfigMap in `openshift-config` with key `ca.crt`.
- Cluster-wide trusted CA uses `proxy/cluster.spec.trustedCA` and a ConfigMap in `openshift-config` with key `ca-bundle.crt`.
- Ingress wildcard certificates affect console, OAuth route, and application routes under `.apps`.
- API server named certificates affect `oc`, automation, and Kubernetes clients.
- Service CA is for internal service-to-service TLS and webhook CA injection.
- Wrong namespace, wrong key name, missing intermediate CA, SAN mismatch, and expired certificates are the most common real-world problems.

A 10-year experienced OpenShift administrator should troubleshoot trust issues with structured evidence: `openssl`, `curl`, `oc get/describe`, operator logs, certificate chain validation, and a clear understanding of which trust store is involved.
