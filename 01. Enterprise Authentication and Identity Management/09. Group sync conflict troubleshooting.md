# Group Sync Conflict Troubleshooting in OpenShift

**Area:** Enterprise Authentication and Identity Management  
**Level:** Advanced OpenShift Administration / 10+ years production experience  
**Focus:** LDAP / Active Directory group synchronization conflicts, RBAC impact, stale groups, duplicate mappings, username mismatches, nested groups, CronJob sync failures, and safe remediation.

---

## 1. Why Group Sync Conflict Troubleshooting Matters

In enterprise OpenShift environments, users usually authenticate through an external identity provider such as LDAP, Active Directory, Keycloak, Red Hat SSO, OIDC, or GitHub Enterprise. Authorization is then commonly handled through OpenShift `Group` objects that are bound to cluster roles or project roles.

A **group sync conflict** happens when the group membership expected from the external directory does not match the group membership, group name, group unique identifier, or RBAC behavior seen inside OpenShift.

Typical production symptoms are:

- A user is in the correct LDAP or AD group but cannot access the OpenShift project.
- A removed user still has access after being removed from LDAP.
- A group appears empty after synchronization.
- A manually added user disappears from an OpenShift group after the next sync.
- Two LDAP groups map to the same OpenShift group name.
- The same OpenShift group appears to be owned by a different LDAP server or sync configuration.
- Sync works manually but fails from the scheduled CronJob.
- Nested Active Directory groups do not produce expected users in OpenShift.
- `oc adm groups sync` dry-run output differs from what the cluster currently has.
- A group rename in LDAP creates a new OpenShift group instead of updating the old one.

From a senior administrator perspective, this is not only an authentication issue. It is an **authorization, identity mapping, RBAC, compliance, and change-control issue**.

## 2. OpenShift Group Sync Architecture Refresher

OpenShift group synchronization imports external directory group data into OpenShift `Group` objects. These objects live in the OpenShift user API group:

```yaml
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  name: ocp-prod-admins
users:
- rakesh@example.com
- platform.admin@example.com
```

The group itself does not authenticate anyone. Authentication is handled by the configured identity provider. Group sync only creates or updates OpenShift group membership records.

### 2.1 Important Separation

| Layer | Purpose | Example |
|---|---|---|
| Identity Provider | Authenticates users | LDAP, AD, OIDC, Keycloak |
| User / Identity Objects | Represent logged-in users and identity mappings | `User`, `Identity` |
| Group Sync | Imports directory group membership into OpenShift groups | `oc adm groups sync` |
| RBAC | Grants permissions to groups or users | `RoleBinding`, `ClusterRoleBinding` |
| Application Access | Actual project, route, console, or API access | `oc get pods`, web console login |

A common mistake is troubleshooting LDAP authentication when the real issue is group membership or RBAC. Another common mistake is troubleshooting RBAC when the real issue is username mismatch between the LDAP identity provider and the group sync configuration.

## 3. Supported LDAP Group Sync Schemas

OpenShift supports the common LDAP group synchronization patterns used in enterprise directories.

### 3.1 RFC 2307

RFC 2307 style group membership stores members as attributes on the group object.

Example concept:

```ldif
dn: cn=ocp-admins,ou=groups,dc=example,dc=com
objectClass: groupOfNames
cn: ocp-admins
member: uid=rakesh,ou=users,dc=example,dc=com
member: uid=amit,ou=users,dc=example,dc=com
```

OpenShift sync config normally needs:

- `groupsQuery`
- `groupUIDAttribute`
- `groupNameAttributes`
- `groupMembershipAttributes`
- `usersQuery`
- `userUIDAttribute`
- `userNameAttributes`

### 3.2 Active Directory

Active Directory style often stores membership on the user using `memberOf`.

Example concept:

```ldif
dn: CN=Rakesh,OU=Users,DC=example,DC=com
mail: rakesh@example.com
sAMAccountName: rakesh
memberOf: CN=ocp-admins,OU=Groups,DC=example,DC=com
```

OpenShift sync config normally needs:

- `usersQuery`
- `userNameAttributes`
- `groupMembershipAttributes`

### 3.3 Augmented Active Directory

Augmented AD has both user entries and group entries as first-class LDAP objects. Membership may be available through `memberOf` on the user and group attributes on the group object.

This is common where you need:

- Group display name from group entry
- Group UID from group DN
- User membership from `memberOf`
- Nested group handling

## 4. What Exactly Is a Group Sync Conflict?

A group sync conflict is any mismatch between these four layers:

```text
Directory source of truth
        ↓
LDAP sync configuration
        ↓
OpenShift Group object
        ↓
RBAC result seen by user
```

A conflict can exist even when the sync command exits successfully. For example:

- Sync creates group `admins`, but RBAC is bound to `ocp-admins`.
- Sync creates users as email addresses, but OpenShift login users are `sAMAccountName` values.
- Sync imports only direct members, but AD team expects nested group members.
- A stale OpenShift group still exists because sync does not automatically prune removed external groups.
- A manually edited group is overwritten by the next sync.

## 5. Golden Rule for Troubleshooting

Never start troubleshooting with `--confirm`.

Always start with dry-run mode:

```bash
oc adm groups sync --sync-config=ldap-sync-config.yaml
```

Only apply changes after you understand the difference between expected LDAP state and current OpenShift state:

```bash
oc adm groups sync --sync-config=ldap-sync-config.yaml --confirm
```

For production, capture every dry-run and confirmed run:

```bash
mkdir -p /root/group-sync-troubleshooting/$(date +%F-%H%M%S)
WORKDIR=/root/group-sync-troubleshooting/$(date +%F-%H%M%S)

oc get groups -o yaml > ${WORKDIR}/groups-before.yaml
oc adm groups sync --sync-config=ldap-sync-config.yaml > ${WORKDIR}/sync-dry-run.txt
```

## 6. How OpenShift Tracks Synced Groups

Synced groups usually contain LDAP-related annotations. These annotations are very important during conflict troubleshooting.

Example:

```yaml
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  annotations:
    openshift.io/ldap.sync-time: "2026-07-02T10:08:38+0530"
    openshift.io/ldap.uid: "cn=ocp-admins,ou=groups,dc=example,dc=com"
    openshift.io/ldap.url: "ldap.example.com:389"
  name: ocp-admins
users:
- rakesh@example.com
- admin2@example.com
```

Key annotations:

| Annotation | Meaning | Troubleshooting Use |
|---|---|---|
| `openshift.io/ldap.sync-time` | Last sync time | Confirms whether recent sync touched the group |
| `openshift.io/ldap.uid` | LDAP unique identifier for the group | Detects group rename, duplicate UID, wrong source DN |
| `openshift.io/ldap.url` | LDAP server used during sync | Detects migration or wrong LDAP server conflicts |

Command:

```bash
oc get group ocp-admins -o yaml
```

Quick annotation check:

```bash
oc get group ocp-admins -o jsonpath='{.metadata.annotations}' | jq
```

Without `jq`:

```bash
oc get group ocp-admins -o jsonpath='{.metadata.annotations.openshift\.io/ldap\.uid}{"\n"}'
oc get group ocp-admins -o jsonpath='{.metadata.annotations.openshift\.io/ldap\.url}{"\n"}'
oc get group ocp-admins -o jsonpath='{.metadata.annotations.openshift\.io/ldap\.sync-time}{"\n"}'
```

## 7. Main Conflict Types

## 7.1 Conflict Type 1: OpenShift Group Name Conflict

### Symptom

Two different LDAP groups produce the same OpenShift group name.

Example:

```text
LDAP Group 1: cn=admins,ou=prod,dc=example,dc=com
LDAP Group 2: cn=admins,ou=dev,dc=example,dc=com
OpenShift groupNameAttributes: [ cn ]
Result: both want OpenShift group name "admins"
```

### Why It Happens

The group name attribute is not globally unique. In LDAP and AD, `cn=admins` may exist in multiple OUs. If OpenShift uses only `cn` as the group name, both groups collide.

### Confirm

Search LDAP:

```bash
ldapsearch -x -LLL \
  -H ldap://ldap.example.com:389 \
  -D "cn=admin,dc=example,dc=com" -W \
  -b "dc=example,dc=com" \
  "(cn=admins)" dn cn
```

Check OpenShift:

```bash
oc get group admins -o yaml
```

Run dry-run:

```bash
oc adm groups sync --sync-config=ldap-sync-config.yaml
```

### Fix Options

Option 1: Use `groupUIDNameMapping` to map each LDAP unique ID to a unique OpenShift group name.

```yaml
kind: LDAPSyncConfig
apiVersion: v1
groupUIDNameMapping:
  "cn=admins,ou=prod,dc=example,dc=com": "ocp-prod-admins"
  "cn=admins,ou=dev,dc=example,dc=com": "ocp-dev-admins"
rfc2307:
  groupsQuery:
    baseDN: "ou=groups,dc=example,dc=com"
    scope: sub
    derefAliases: never
    pageSize: 0
  groupUIDAttribute: dn
  groupNameAttributes: [ cn ]
  groupMembershipAttributes: [ member ]
  usersQuery:
    baseDN: "ou=users,dc=example,dc=com"
    scope: sub
    derefAliases: never
    pageSize: 0
  userUIDAttribute: dn
  userNameAttributes: [ mail ]
```

Option 2: Change the LDAP group naming standard.

```text
Bad:  admins
Good: ocp-prod-admins, ocp-dev-admins, ocp-stage-admins
```

Option 3: Limit sync scope using whitelist.

```bash
cat > whitelist.txt <<EOF2
cn=admins,ou=prod,dc=example,dc=com
EOF2

oc adm groups sync --whitelist=whitelist.txt --sync-config=ldap-sync-config.yaml
```

After validation:

```bash
oc adm groups sync --whitelist=whitelist.txt --sync-config=ldap-sync-config.yaml --confirm
```

## 7.2 Conflict Type 2: Existing Manual Group Conflicts with LDAP-Synced Group

### Symptom

A group was manually created in OpenShift and later LDAP sync tries to manage the same group name.

Example:

```bash
oc adm groups new ocp-admins rakesh@example.com
```

Later LDAP sync also wants to create/update `ocp-admins`.

### Why It Happens

OpenShift allows manually created groups and LDAP-synced groups. A conflict occurs when the same group name is used by both human administration and automation.

### Confirm

```bash
oc get group ocp-admins -o yaml
```

If the group has no LDAP annotations, it may be manually created:

```bash
oc get group ocp-admins -o jsonpath='{.metadata.annotations}{"\n"}'
```

### Risk

Manual membership can be overwritten by the next LDAP sync. If the group is bound to powerful roles such as `cluster-admin`, this can become a serious access-control issue.

Check RBAC binding:

```bash
oc get clusterrolebinding -o wide | grep ocp-admins
oc get rolebinding -A -o wide | grep ocp-admins
```

### Fix Options

Recommended: use separate naming conventions.

```text
ldap-ocp-admins      # LDAP-managed
manual-breakglass    # Manually managed
```

Move RBAC binding to LDAP-managed group after validation:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ldap-ocp-admins
oc adm policy remove-cluster-role-from-group cluster-admin ocp-admins
```

Backup first:

```bash
oc get group ocp-admins -o yaml > ocp-admins-before-change.yaml
oc get clusterrolebinding -o yaml > clusterrolebindings-before-change.yaml
```

## 7.3 Conflict Type 3: LDAP UID Conflict After Directory Migration

### Symptom

After migrating LDAP or AD, group names remain the same but group DNs or unique IDs changed.

Example old source:

```text
cn=ocp-admins,ou=groups,dc=old,dc=example,dc=com
```

New source:

```text
cn=ocp-admins,ou=openshift,dc=new,dc=example,dc=com
```

OpenShift group still contains old annotation:

```yaml
openshift.io/ldap.uid: cn=ocp-admins,ou=groups,dc=old,dc=example,dc=com
openshift.io/ldap.url: old-ldap.example.com:389
```

### Confirm

```bash
oc get group ocp-admins -o yaml
```

Compare with LDAP:

```bash
ldapsearch -x -LLL \
  -H ldap://new-ldap.example.com:389 \
  -D "cn=admin,dc=new,dc=example,dc=com" -W \
  -b "dc=new,dc=example,dc=com" \
  "(cn=ocp-admins)" dn cn member memberOf
```

Dry-run with new config:

```bash
oc adm groups sync --sync-config=new-ldap-sync-config.yaml
```

### Fix Strategy

1. Backup OpenShift groups.
2. Decide whether you are preserving the same OpenShift group name.
3. Update `groupUIDNameMapping` if needed.
4. Dry-run against only one group.
5. Confirm sync for only one group.
6. Run prune only after you are sure stale groups are safe to remove.

Example targeted sync:

```bash
oc adm groups sync \
  'cn=ocp-admins,ou=openshift,dc=new,dc=example,dc=com' \
  --sync-config=new-ldap-sync-config.yaml
```

Apply after validation:

```bash
oc adm groups sync \
  'cn=ocp-admins,ou=openshift,dc=new,dc=example,dc=com' \
  --sync-config=new-ldap-sync-config.yaml \
  --confirm
```

Avoid immediately deleting the old group if it is bound to production RBAC. First inspect bindings:

```bash
oc get clusterrolebinding -o yaml | grep -B5 -A10 'name: ocp-admins'
oc get rolebinding -A -o yaml | grep -B5 -A10 'name: ocp-admins'
```

## 7.4 Conflict Type 4: Username Attribute Mismatch

### Symptom

User logs in as `rakesh`, but group sync adds `rakesh@example.com` to the group. RBAC does not apply.

OpenShift group:

```yaml
users:
- rakesh@example.com
```

Actual OpenShift user:

```bash
oc get users
```

Output:

```text
NAME      UID
rakesh    xxxxx
```

### Why It Happens

The LDAP identity provider and the LDAP group sync configuration use different user name attributes.

Examples:

| Layer | Attribute Used | Result |
|---|---|---|
| LDAP IDP login | `uid` | `rakesh` |
| Group sync | `mail` | `rakesh@example.com` |
| RBAC subject | group has `rakesh@example.com` | User `rakesh` does not match |

### Confirm

Check users:

```bash
oc get users
oc get identities
```

Check group members:

```bash
oc get group ocp-admins -o jsonpath='{.users}{"\n"}'
```

Check OAuth identity provider configuration:

```bash
oc get oauth cluster -o yaml
```

Look for LDAP mapping attributes, such as:

```yaml
mappingMethod: claim
ldap:
  attributes:
    id:
    - dn
    preferredUsername:
    - uid
    name:
    - cn
    email:
    - mail
```

Check group sync config:

```yaml
userNameAttributes: [ mail ]
```

### Fix

Align the group sync `userNameAttributes` with the username produced by the identity provider.

If OpenShift usernames are email addresses:

```yaml
userNameAttributes: [ mail ]
```

If OpenShift usernames are AD login names:

```yaml
userNameAttributes: [ sAMAccountName ]
```

If OpenShift usernames are LDAP `uid`:

```yaml
userNameAttributes: [ uid ]
```

After changing, dry-run:

```bash
oc adm groups sync --sync-config=ldap-sync-config.yaml
```

Then apply:

```bash
oc adm groups sync --sync-config=ldap-sync-config.yaml --confirm
```

### Senior Admin Note

This is one of the most common production issues. The group exists. The user exists. The role binding exists. But the string in the OpenShift `Group.users[]` list does not match the actual OpenShift `User.metadata.name`.

## 7.5 Conflict Type 5: Nested Active Directory Group Conflict

### Symptom

AD group `ocp-admins` contains another group `platform-admins`, and `platform-admins` contains users. OpenShift group sync only imports direct members, not nested members.

Example:

```text
ocp-admins
└── platform-admins
    ├── rakesh
    └── amit
```

Expected:

```text
ocp-admins includes rakesh and amit
```

Actual:

```text
ocp-admins is empty or missing nested users
```

### Why It Happens

OpenShift groups do not nest. The directory must provide flattened membership data before OpenShift can consume it. For Microsoft AD nested groups, use the LDAP matching rule in chain when supported:

```text
1.2.840.113556.1.4.1941
```

### Correct Pattern for Nested AD

For augmented Active Directory nested membership, use:

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldap://LDAP_SERVICE_IP:389
augmentedActiveDirectory:
  groupsQuery:
    derefAliases: never
    pageSize: 0
  groupUIDAttribute: dn
  groupNameAttributes: [ cn ]
  usersQuery:
    baseDN: "ou=users,dc=example,dc=com"
    scope: sub
    derefAliases: never
    filter: (objectclass=person)
    pageSize: 0
  userNameAttributes: [ mail ]
  groupMembershipAttributes: [ "memberOf:1.2.840.113556.1.4.1941:" ]
```

Targeted sync must explicitly whitelist the group:

```bash
oc adm groups sync \
  'cn=ocp-admins,ou=groups,dc=example,dc=com' \
  --sync-config=augmented-ad-nested.yaml
```

Apply only after dry-run looks correct:

```bash
oc adm groups sync \
  'cn=ocp-admins,ou=groups,dc=example,dc=com' \
  --sync-config=augmented-ad-nested.yaml \
  --confirm
```

### Mistakes

Do not expect this to work automatically:

```yaml
groupMembershipAttributes: [ memberOf ]
```

For nested AD membership, plain `memberOf` often returns only direct memberships.

## 7.6 Conflict Type 6: Whitelist and Blacklist Conflict

### Symptom

A group is present in LDAP but is not synced.

### Causes

- The group is missing from whitelist.
- The group is included in blacklist.
- The whitelist uses group name but sync expects group UID.
- The whitelist uses CN but `groupUIDAttribute` is DN.
- The whitelist contains extra spaces, Windows CRLF, or wrong case.

### Confirm

Show whitelist with hidden characters:

```bash
cat -vet whitelist.txt
```

Check group UID used by config:

```yaml
groupUIDAttribute: dn
```

If `groupUIDAttribute: dn`, whitelist must contain full DN:

```text
cn=ocp-admins,ou=groups,dc=example,dc=com
```

Not only:

```text
ocp-admins
```

Run dry-run:

```bash
oc adm groups sync --whitelist=whitelist.txt --sync-config=ldap-sync-config.yaml
```

### Fix

Normalize whitelist:

```bash
dos2unix whitelist.txt
sed -i 's/[[:space:]]*$//' whitelist.txt
sort -u whitelist.txt -o whitelist.txt
```

Use literal group UID test:

```bash
oc adm groups sync \
  'cn=ocp-admins,ou=groups,dc=example,dc=com' \
  --sync-config=ldap-sync-config.yaml
```

## 7.7 Conflict Type 7: Stale OpenShift Groups Because Prune Was Not Run

### Symptom

An LDAP group was deleted or moved, but the OpenShift group still exists and may still have RBAC permissions.

### Why It Happens

`oc adm groups sync` updates or creates group records. Removing stale groups is handled separately with `oc adm prune groups`.

### Confirm

Check group annotation:

```bash
oc get group old-ocp-admins -o yaml
```

Check if LDAP still has it:

```bash
ldapsearch -x -LLL \
  -H ldap://ldap.example.com:389 \
  -D "cn=admin,dc=example,dc=com" -W \
  -b "dc=example,dc=com" \
  "(cn=old-ocp-admins)" dn cn
```

Dry-run prune:

```bash
oc adm prune groups --sync-config=ldap-sync-config.yaml
```

Apply prune:

```bash
oc adm prune groups --sync-config=ldap-sync-config.yaml --confirm
```

### Production Warning

Before pruning, check RBAC:

```bash
oc get clusterrolebinding -o yaml | grep -B5 -A10 'old-ocp-admins'
oc get rolebinding -A -o yaml | grep -B5 -A10 'old-ocp-admins'
```

If the group is bound to sensitive roles, migrate RBAC first.

## 7.8 Conflict Type 8: Manual Changes Are Overwritten

### Symptom

Admin manually adds a user:

```bash
oc adm groups add-users ocp-admins temporary.user@example.com
```

After scheduled sync, the user disappears.

### Why It Happens

LDAP sync treats LDAP as the source of truth for synced groups. Manual edits to LDAP-managed groups are temporary and unsafe.

### Confirm

Check sync annotations:

```bash
oc get group ocp-admins -o yaml
```

If LDAP annotations exist, treat the group as automation-managed.

### Fix

Add users in LDAP, not directly in OpenShift:

```text
Correct source of truth: LDAP / AD group membership
Wrong long-term fix: oc adm groups add-users on LDAP-managed group
```

For emergency access, create a separate break-glass group:

```bash
oc adm groups new breakglass-admins rakesh@example.com
oc adm policy add-cluster-role-to-group cluster-admin breakglass-admins
```

Then remove emergency access after incident:

```bash
oc adm policy remove-cluster-role-from-group cluster-admin breakglass-admins
oc delete group breakglass-admins
```

## 7.9 Conflict Type 9: Case Sensitivity and Username Normalization

### Symptom

LDAP returns:

```text
Rakesh.Jha@example.com
```

OpenShift user is:

```text
rakesh.jha@example.com
```

RBAC does not apply because usernames are string matches.

### Confirm

```bash
oc get users
oc get group ocp-admins -o yaml
```

Check LDAP attribute value exactly:

```bash
ldapsearch -x -LLL \
  -H ldap://ldap.example.com:389 \
  -D "cn=admin,dc=example,dc=com" -W \
  -b "ou=users,dc=example,dc=com" \
  "(mail=*rakesh*)" mail uid sAMAccountName
```

### Fix

Standardize username attribute across:

- LDAP IDP config
- LDAP group sync config
- Directory data hygiene
- RBAC subject references

Best enterprise practice is to use one stable, immutable login name strategy.

Recommended options:

| Environment | Preferred Username Attribute |
|---|---|
| AD enterprise | `sAMAccountName` or UPN/email, consistently chosen |
| LDAP enterprise | `uid` or `mail`, consistently chosen |
| Mixed OIDC + LDAP | Use email only if all systems normalize consistently |

## 7.10 Conflict Type 10: Wrong LDAP Query Scope or Filter

### Symptom

Group sync returns empty groups or missing users.

### Common Causes

- `baseDN` points to the wrong OU.
- `scope: one` is used when users are deeper in nested OUs.
- LDAP filter excludes disabled or service accounts unexpectedly.
- `groupsQuery` filter does not match actual objectClass.
- `usersQuery` filter excludes users who are valid group members.

### Confirm Group Search

```bash
ldapsearch -x -LLL \
  -H ldap://ldap.example.com:389 \
  -D "cn=admin,dc=example,dc=com" -W \
  -b "ou=groups,dc=example,dc=com" \
  -s sub \
  "(cn=ocp-admins)" dn cn member
```

### Confirm User Search

```bash
ldapsearch -x -LLL \
  -H ldap://ldap.example.com:389 \
  -D "cn=admin,dc=example,dc=com" -W \
  -b "ou=users,dc=example,dc=com" \
  -s sub \
  "(objectClass=person)" dn cn mail uid sAMAccountName memberOf
```

### Fix

Use the smallest correct search base, but not so narrow that real users or groups are out of scope.

Example:

```yaml
usersQuery:
  baseDN: "dc=example,dc=com"
  scope: sub
  derefAliases: never
  filter: "(&(objectClass=person)(mail=*))"
  pageSize: 500
```

## 7.11 Conflict Type 11: Member Not Found or Out-of-Scope Members

### Symptom

Group sync fails or partially syncs because a group contains members that are not visible under `usersQuery.baseDN`.

Example:

```text
Group: cn=ocp-admins,ou=groups,dc=example,dc=com
Member: cn=contractor1,ou=external,dc=example,dc=com
usersQuery.baseDN: ou=employees,dc=example,dc=com
```

The contractor is outside the configured search scope.

### Fix Option 1: Expand Users Query

```yaml
usersQuery:
  baseDN: "dc=example,dc=com"
  scope: sub
```

### Fix Option 2: Use Error Tolerance Carefully

For RFC 2307, OpenShift sync config can use tolerances:

```yaml
tolerateMemberNotFoundErrors: true
tolerateMemberOutOfScopeErrors: true
```

Use this only when you understand the impact. It can hide real data quality issues.

### Senior Recommendation

In regulated environments, do not blindly tolerate missing members. First generate a report of missing DNs and fix the directory or query scope.

## 7.12 Conflict Type 12: CronJob Sync Conflict

### Symptom

Manual sync works, but scheduled sync fails or produces different results.

### Causes

- CronJob service account lacks permissions.
- Secret or CA ConfigMap missing in CronJob namespace.
- CronJob runs with an old sync config.
- Multiple CronJobs sync the same groups with different configs.
- Jobs overlap and race.
- Network policy blocks LDAP from the CronJob pod.
- Image used by CronJob has different `oc` client behavior.

### Check CronJob

```bash
oc -n ldap-sync get cronjob
oc -n ldap-sync describe cronjob ldap-group-syncer
oc -n ldap-sync get jobs
oc -n ldap-sync get pods
```

Check logs:

```bash
oc -n ldap-sync logs job/<job-name>
```

Check service account RBAC:

```bash
oc auth can-i get groups \
  --as system:serviceaccount:ldap-sync:ldap-group-syncer

oc auth can-i update groups \
  --as system:serviceaccount:ldap-sync:ldap-group-syncer

oc auth can-i create groups \
  --as system:serviceaccount:ldap-sync:ldap-group-syncer
```

Check mounted files:

```bash
oc -n ldap-sync exec -it <sync-pod> -- ls -l /etc/secrets
oc -n ldap-sync exec -it <sync-pod> -- ls -l /etc/ldap-ca
oc -n ldap-sync exec -it <sync-pod> -- cat /etc/config/sync.yaml
```

### Recommended CronJob Settings

Use `concurrencyPolicy: Forbid` so two sync jobs do not overlap.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
spec:
  schedule: "*/30 * * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 1
      template:
        spec:
          serviceAccountName: ldap-group-syncer
          restartPolicy: Never
          containers:
          - name: ldap-group-sync
            image: registry.redhat.io/openshift4/ose-cli:latest
            command:
            - /bin/bash
            - -c
            - |
              oc adm groups sync \
                --sync-config=/etc/config/sync.yaml \
                --confirm
```

### Production Practice

Do not run multiple CronJobs against the same OpenShift group set unless they are clearly partitioned with non-overlapping whitelists.

## 7.13 Conflict Type 13: RBAC Binding Points to Wrong Group

### Symptom

Group sync is correct, but user still has no access.

### Example

OpenShift group created by sync:

```text
ldap-ocp-admins
```

RoleBinding points to:

```text
ocp-admins
```

### Confirm

```bash
oc get group ldap-ocp-admins -o yaml

oc get clusterrolebinding -o yaml | grep -B5 -A10 'kind: Group'
```

Use `who-can`:

```bash
oc auth can-i get pods -n app-prod --as=rakesh@example.com
```

Bind the correct group:

## 7.14 Conflict Type 14: Duplicate Access Through Multiple Groups

### Symptom

A user is removed from one LDAP group but still retains access.

### Why It Happens

RBAC is additive. A user can receive permissions through multiple groups.

Example:

```text
User rakesh@example.com is removed from ocp-prod-admins
But still exists in ocp-platform-admins
Both groups have admin RBAC in app-prod
```

### Confirm

Find all groups containing user:

```bash
for g in $(oc get groups -o jsonpath='{.items[*].metadata.name}'); do
  oc get group "$g" -o jsonpath='{.users}' | grep -q 'rakesh@example.com' && echo "$g"
done
```

Check RBAC for all groups:

```bash
oc get rolebinding -A -o wide | egrep 'ocp-prod-admins|ocp-platform-admins'
oc get clusterrolebinding -o wide | egrep 'ocp-prod-admins|ocp-platform-admins'
```

Check effective access:

```bash
oc auth can-i delete pods -n app-prod --as=rakesh@example.com
```

### Fix

Remove or correct all RBAC paths, not only one group membership.

## 7.15 Conflict Type 15: Group Rename in LDAP

### Symptom

LDAP group renamed from `ocp-dev-admins` to `ocp-platform-dev-admins`. OpenShift now has both old and new groups.

### Why It Happens

OpenShift group sync may create a new group when group name mapping changes. The old group might remain until pruned or manually removed.

### Confirm

```bash
oc get groups | grep dev-admins
oc get group ocp-dev-admins -o yaml
oc get group ocp-platform-dev-admins -o yaml
```

Check RBAC:

```bash
oc get rolebinding -A -o yaml | grep -B5 -A10 'ocp-dev-admins'
oc get clusterrolebinding -o yaml | grep -B5 -A10 'ocp-dev-admins'
```

### Safe Fix

1. Create new group by sync.
2. Add RBAC to new group.
3. Validate user access.
4. Remove RBAC from old group.
5. Prune or delete old group.

```bash
oc adm policy add-role-to-group edit ocp-platform-dev-admins -n dev-project
oc auth can-i create pods -n dev-project --as=dev.user@example.com
oc adm policy remove-role-from-group edit ocp-dev-admins -n dev-project
```

## 7.16 Conflict Type 16: Wrong Bind DN Permissions

### Symptom

Sync returns empty or incomplete groups, but the LDAP query appears correct.

### Why It Happens

The bind DN used by OpenShift may not have permission to read:

- `member`
- `memberOf`
- `mail`
- `sAMAccountName`
- group OU
- user OU
- nested group attributes

### Confirm Using Same Bind DN

Always test with the exact bind DN used by sync:

```bash
ldapsearch -x -LLL \
  -H ldap://ldap.example.com:389 \
  -D "cn=openshift-sync,ou=svc,dc=example,dc=com" -W \
  -b "dc=example,dc=com" \
  "(cn=ocp-admins)" dn cn member memberOf
```

Do not test with a domain admin account and assume the service account sees the same data.

### Fix

Ask AD/LDAP team to grant read access to required attributes and OUs. Then dry-run again.

## 7.17 Conflict Type 17: TLS / CA / LDAP URL Conflict

### Symptom

Manual LDAP search from your laptop works, but OpenShift CronJob sync fails.

### Causes

- Wrong LDAP URL: `ldap://` vs `ldaps://`
- `insecure: false` without correct CA
- CA ConfigMap not mounted
- Certificate CN/SAN mismatch
- Firewall or proxy issue
- LDAP endpoint different inside cluster network

### Confirm

From the CronJob pod or debug pod:

```bash
oc -n ldap-sync exec -it <pod> -- bash
```

Inside pod:

```bash
openssl s_client -connect ldap.example.com:636 -showcerts
```

Check sync config:

```yaml
url: ldaps://ldap.example.com:636
insecure: false
ca: /etc/ldap-ca/ca.crt
```

Check mounted CA:

```bash
ls -l /etc/ldap-ca/ca.crt
```

### Fix

Mount the correct CA bundle and ensure URL scheme matches TLS expectation.

## 8. Production Troubleshooting Runbook

Use this runbook during real incidents.

### Step 1: Freeze Automation

Suspend scheduled sync before making manual corrections.

```bash
oc -n ldap-sync patch cronjob ldap-group-syncer \
  -p '{"spec":{"suspend":true}}'
```

Confirm:

```bash
oc -n ldap-sync get cronjob ldap-group-syncer
```

### Step 2: Backup Current State

```bash
TS=$(date +%F-%H%M%S)
mkdir -p /root/ocp-group-sync-$TS

oc get groups -o yaml > /root/ocp-group-sync-$TS/groups.yaml
oc get users -o yaml > /root/ocp-group-sync-$TS/users.yaml
oc get identities -o yaml > /root/ocp-group-sync-$TS/identities.yaml
oc get rolebinding -A -o yaml > /root/ocp-group-sync-$TS/rolebindings.yaml
oc get clusterrolebinding -o yaml > /root/ocp-group-sync-$TS/clusterrolebindings.yaml
oc get oauth cluster -o yaml > /root/ocp-group-sync-$TS/oauth-cluster.yaml
```

### Step 3: Identify Affected User and Group

```bash
USER_NAME="rakesh@example.com"
GROUP_NAME="ocp-admins"
PROJECT="app-prod"

oc get user "$USER_NAME" -o yaml
oc get group "$GROUP_NAME" -o yaml
oc auth can-i get pods -n "$PROJECT" --as="$USER_NAME"
```

### Step 4: Confirm Current Group Membership

```bash
oc get group "$GROUP_NAME" -o jsonpath='{.users}{"\n"}'
```

Readable output:

```bash
oc get group "$GROUP_NAME" -o json | jq -r '.users[]?'
```

### Step 5: Inspect LDAP Annotations

```bash
oc get group "$GROUP_NAME" -o jsonpath='{.metadata.annotations.openshift\.io/ldap\.uid}{"\n"}'
oc get group "$GROUP_NAME" -o jsonpath='{.metadata.annotations.openshift\.io/ldap\.url}{"\n"}'
oc get group "$GROUP_NAME" -o jsonpath='{.metadata.annotations.openshift\.io/ldap\.sync-time}{"\n"}'
```

Interpretation:

| Observation | Meaning |
|---|---|
| No LDAP annotations | Possibly manual group |
| Old LDAP URL | Migration conflict |
| Old sync time | CronJob not running or group not selected |
| UID points to unexpected DN | Wrong group mapping or duplicate name |

### Step 6: Dry-Run Sync

```bash
oc adm groups sync --sync-config=ldap-sync-config.yaml > /root/ocp-group-sync-$TS/dry-run.txt
cat /root/ocp-group-sync-$TS/dry-run.txt
```

For one group:

```bash
oc adm groups sync \
  'cn=ocp-admins,ou=groups,dc=example,dc=com' \
  --sync-config=ldap-sync-config.yaml
```

### Step 7: Verify LDAP Directly

RFC 2307 group:

```bash
ldapsearch -x -LLL \
  -H ldap://ldap.example.com:389 \
  -D "cn=openshift-sync,ou=svc,dc=example,dc=com" -W \
  -b "ou=groups,dc=example,dc=com" \
  "(cn=ocp-admins)" dn cn member
```

AD user membership:

```bash
ldapsearch -x -LLL \
  -H ldap://ad.example.com:389 \
  -D "CN=openshift-sync,OU=Service Accounts,DC=example,DC=com" -W \
  -b "OU=Users,DC=example,DC=com" \
  "(sAMAccountName=rakesh)" dn mail sAMAccountName memberOf
```

Nested AD membership:

```bash
ldapsearch -x -LLL \
  -H ldap://ad.example.com:389 \
  -D "CN=openshift-sync,OU=Service Accounts,DC=example,DC=com" -W \
  -b "OU=Users,DC=example,DC=com" \
  "(memberOf:1.2.840.113556.1.4.1941:=CN=ocp-admins,OU=Groups,DC=example,DC=com)" \
  dn mail sAMAccountName
```

### Step 8: Compare Username Mapping

```bash
oc get users
oc get identities
oc get group "$GROUP_NAME" -o json | jq -r '.users[]?'
```

If group has email but OpenShift user is short name, fix `userNameAttributes`.

### Step 9: Check RBAC

```bash

oc get clusterrolebinding -o yaml | grep -B5 -A10 "$GROUP_NAME"
```

Effective access check:

```bash

oc auth can-i create deployments -n "$PROJECT" --as="$USER_NAME"

```

### Step 10: Apply Targeted Fix

Prefer targeted sync first:

```bash

  'cn=ocp-admins,ou=groups,dc=example,dc=com' \
```

Then check:

## 9. Conflict Troubleshooting Decision Matrix

| Symptom | First Check | Likely Cause | Fix |
|---|---|---|---|
| User in LDAP group but no access | `oc get group <group>` | Username mismatch | Align `userNameAttributes` with IDP username |
| Group exists but empty | LDAP query with same bind DN | Wrong query/filter or no readable attributes | Fix `usersQuery`, `groupsQuery`, bind permissions |
| Group not synced | Whitelist/blacklist | Wrong group UID in whitelist | Use full DN if `groupUIDAttribute: dn` |
| Removed group still has access | `oc adm prune groups` dry-run | Prune not run | Prune after RBAC validation |
| Manual user disappears | Group has LDAP annotations | Manual edit overwritten | Add user in LDAP or use break-glass group |
| Nested AD members missing | Check `memberOf` rule | Nested groups not flattened | Use `LDAP_MATCHING_RULE_IN_CHAIN` and explicit whitelist |
| Same group name from multiple OUs | LDAP search `(cn=<name>)` | Non-unique group name | Use `groupUIDNameMapping` |
| Sync works manually but not CronJob | CronJob logs and SA permissions | Missing secret, CA, RBAC, network | Fix CronJob namespace resources and permissions |
| User still has access after removal | Find all groups for user | RBAC additive via another group | Remove all access paths |
| New LDAP server not reflected | Group annotations | Old LDAP UID/URL | Migration runbook and targeted sync |

## 11. Safe Remediation Patterns

## 11.1 Use One Source of Truth Per Group

Do not manage the same group manually and through LDAP sync.

Recommended:

```text
LDAP-managed:      ocp-prod-admins
Manual emergency:  breakglass-admins
Application local: app-team-temporary
```

## 11.2 Use Stable Group Names

Avoid generic group names:

```text
Bad: admins
Bad: developers
Bad: users
```

Use environment and purpose:

```text
Good: ocp-prod-cluster-admins
Good: ocp-dev-editors
Good: ocp-finance-viewers
Good: ocp-platform-readonly
```

## 11.3 Use `groupUIDNameMapping` for Enterprise Stability

This prevents OpenShift group names from changing accidentally when LDAP display attributes change.

```yaml
groupUIDNameMapping:
  "cn=OCP_PROD_ADMINS,ou=groups,dc=example,dc=com": "ocp-prod-admins"
  "cn=OCP_DEV_EDIT,ou=groups,dc=example,dc=com": "ocp-dev-editors"
```

## 11.4 Treat Sync Config as Code

Store these in Git:

```text
ldap-sync-config.yaml
whitelist.txt
blacklist.txt
cronjob.yaml
serviceaccount.yaml
clusterrole.yaml
clusterrolebinding.yaml
README.md
```

Every change should go through peer review.

## 11.5 Always Dry-Run in CI/CD

Example pipeline logic:

```bash
oc adm groups sync --sync-config=ldap-sync-config.yaml > dry-run.txt

if grep -iE 'error|conflict|failed' dry-run.txt; then
  echo "Group sync dry-run failed"
  exit 1
fi
```

## 11.6 Partition Large Enterprises by Whitelist

Instead of syncing the full AD directory, sync only approved OpenShift groups.

```bash
oc adm groups sync --whitelist=openshift-groups.txt --sync-config=ldap-sync-config.yaml --confirm
```

Example whitelist:

```text
cn=ocp-prod-admins,ou=openshift,ou=groups,dc=example,dc=com
cn=ocp-prod-viewers,ou=openshift,ou=groups,dc=example,dc=com
cn=ocp-dev-editors,ou=openshift,ou=groups,dc=example,dc=com
```

## 11.7 Avoid Syncing Broad Enterprise Groups

Do not sync groups such as:

```text
Domain Users
All Employees
Everyone
Authenticated Users
```

These can accidentally grant access to thousands of users if bound to RBAC.

## 11.8 Protect High-Privilege Bindings

Audit groups bound to powerful roles:

```bash
oc get clusterrolebinding -o json | jq -r '
.items[] |
select(.roleRef.name=="cluster-admin") |
.metadata.name as $crb |
.subjects[]? |
select(.kind=="Group") |
[$crb, .name] | @tsv'
```

Review all groups bound to:

- `cluster-admin`
- `admin`
- `edit`
- custom roles with secret access
- custom roles with impersonation permissions
- custom roles with node, SCC, or OAuth access

## 12. Example End-to-End Scenario

### Problem

User `rakesh` is a member of AD group `CN=OCP_PROD_ADMINS,OU=OpenShift,DC=example,DC=com`, but cannot administer namespace `prod-app`.

### Investigation

Check OpenShift user:

```bash
oc get users | grep -i rakesh
```

Output:

```text
rakesh
```

Check group:

```bash
oc get group ocp-prod-admins -o yaml
```

Output:

```yaml
users:
- rakesh.jha@example.com
```

Check RBAC:

```bash
oc get rolebinding -n prod-app -o yaml | grep -B5 -A10 ocp-prod-admins
```

RoleBinding is correct.

Check permission:

```bash
oc auth can-i create deployments -n prod-app --as=rakesh
```

Output:

```text
no
```

Check as email:

```bash
oc auth can-i create deployments -n prod-app --as=rakesh.jha@example.com
```

Output:

```text
yes
```

### Root Cause

OpenShift login user is `rakesh`, but group sync adds `rakesh.jha@example.com` because sync config uses:

```yaml
userNameAttributes: [ mail ]
```

OAuth LDAP IDP uses:

```yaml
preferredUsername:
- sAMAccountName
```

### Fix

Change group sync config:

```yaml
userNameAttributes: [ sAMAccountName ]
```

Dry-run:

```bash
oc adm groups sync \
  'CN=OCP_PROD_ADMINS,OU=OpenShift,DC=example,DC=com' \
  --sync-config=ad-sync.yaml
```

Apply:

```bash
oc adm groups sync \
  'CN=OCP_PROD_ADMINS,OU=OpenShift,DC=example,DC=com' \
  --sync-config=ad-sync.yaml \
  --confirm
```

Validate:

```bash
oc get group ocp-prod-admins -o yaml
oc auth can-i create deployments -n prod-app --as=rakesh
```

Expected:

```text
yes
```

## 13. Interview-Style Explanation

### Question

A user is part of the correct LDAP group, but still cannot access the OpenShift project. How do you troubleshoot?

### Senior Answer

I would not start by changing RBAC or rerunning sync with `--confirm`. First, I would verify the four layers: LDAP membership, sync configuration, OpenShift group object, and RBAC binding.

1. Confirm the actual OpenShift username with `oc get users` and `oc get identities`.
2. Confirm the group membership in OpenShift with `oc get group <group> -o yaml`.
3. Compare `Group.users[]` with the actual `User.metadata.name`.
4. Inspect LDAP sync annotations such as `openshift.io/ldap.uid`, `openshift.io/ldap.url`, and `openshift.io/ldap.sync-time`.
5. Run `oc adm groups sync --sync-config=<file>` in dry-run mode.
6. Query LDAP directly using the same bind DN used by OpenShift.
7. Check whether the group is filtered by whitelist or blacklist.
8. Check whether nested AD group membership requires `LDAP_MATCHING_RULE_IN_CHAIN`.
9. Validate RBAC using `oc auth can-i --as=<user>` and `oc adm policy who-can`.
10. Apply a targeted sync only after the dry-run output is correct.

Most real-world issues are caused by username mismatch, stale groups, nested group expectations, wrong whitelist UID, or RBAC bound to a different group name.

## 14. Common Mistakes to Avoid

- Running `oc adm groups sync --confirm` without a dry-run.
- Assuming LDAP authentication and LDAP group sync use the same username attribute.
- Binding RBAC to a manually created group that later becomes LDAP-managed.
- Syncing `Domain Users` or broad enterprise groups.
- Expecting nested AD groups to work without flattening membership.
- Forgetting to run group prune for stale groups.
- Testing LDAP with a domain admin instead of the OpenShift sync bind DN.
- Using `cn` as group name when duplicate CNs exist in multiple OUs.
- Running multiple CronJobs that manage the same groups.
- Ignoring case sensitivity in usernames.
- Treating a successful sync exit code as proof that RBAC is correct.

## 19. Final Senior-Level Summary

Group sync conflict troubleshooting in OpenShift is about proving alignment between directory data, sync configuration, OpenShift group records, and RBAC. A senior OpenShift administrator should always troubleshoot in this order:

1. Identify the affected user, group, and namespace.
2. Confirm the actual OpenShift username.
3. Check the OpenShift group object and LDAP annotations.
4. Run group sync in dry-run mode.
5. Query LDAP with the same bind DN used by OpenShift.
6. Verify username attribute consistency.
7. Check whitelist, blacklist, and group UID mapping.
8. Validate nested group behavior if Active Directory is involved.
9. Confirm RBAC bindings and effective permissions.
10. Apply targeted sync, then broader sync.
11. Prune stale groups only after RBAC impact review.
12. Keep CronJob automation controlled, observable, and non-overlapping.

The most dangerous mistakes are syncing broad groups, overwriting manually managed privileged groups, failing to align username attributes, and pruning without checking RBAC bindings. In production, group sync should be treated as identity infrastructure code, not as an ad hoc command.
