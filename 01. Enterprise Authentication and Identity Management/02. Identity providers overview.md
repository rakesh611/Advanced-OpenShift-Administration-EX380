# Identity Providers Overview
## Enterprise Authentication and Identity Management for Advanced OpenShift Administration

**Target audience:** Senior Linux / Kubernetes / OpenShift administrators with around 10 years of production experience  
**Focus area:** OpenShift Container Platform user authentication, identity provider design, OAuth integration, RBAC handoff, troubleshooting, and enterprise best practices

---

## 1. What is an Identity Provider in OpenShift?

An **Identity Provider**, usually called an **IdP**, is the external or internal authentication source that OpenShift uses to verify who a human user is.

In simple words:

> OpenShift does not normally store enterprise user passwords itself. It delegates login validation to an identity provider, then maps the authenticated identity to an OpenShift `User` object, which is later authorized through RBAC.

OpenShift authentication answers:

```text
Who are you?
```

OpenShift authorization answers:

```text
What are you allowed to do?
```

Example:

```text
User enters corporate LDAP username/password
        ↓
OpenShift OAuth server sends credentials to LDAP
        ↓
LDAP validates the user
        ↓
OpenShift creates or maps Identity -> User
        ↓
RBAC decides whether that user can create pods, manage projects, view nodes, etc.
```

A senior OpenShift administrator must clearly separate these two layers:

| Layer | OpenShift Component | Purpose |
|---|---|---|
| Authentication | OAuth server + Identity Provider | Verifies user identity |
| Identity mapping | `Identity`, `User`, `UserIdentityMapping` | Maps external identity to OpenShift user |
| Authorization | RBAC | Grants or denies API actions |
| Audit | API server audit logs | Records who did what |

---

## 2. Why Identity Providers Matter in Enterprise OpenShift

In an enterprise environment, identity provider configuration is not just a login setup. It affects:

- Security compliance
- RBAC design
- Auditability
- User lifecycle management
- Multi-cluster governance
- SSO integration
- Break-glass access
- Separation of duty
- Automation and GitOps workflows
- Production outage recovery

A weak identity provider design can cause serious problems:

- Users cannot log in after cluster installation
- `kubeadmin` remains active permanently
- Multiple users accidentally map to the same OpenShift account
- Admins lose cluster access after IdP failure
- RBAC is assigned directly to users instead of groups
- LDAP/OIDC claims do not match enterprise usernames
- Audit logs become hard to interpret
- Migration from one IdP to another breaks user mappings

## 3. Default Authentication State After OpenShift Installation

After a fresh OpenShift installation, the cluster normally starts with the temporary `kubeadmin` user.

Important points:

- `kubeadmin` is a bootstrap-style administrative user.
- It is not integrated with enterprise identity management.
- It should not be used as a long-term operational account.
- Before removing it, another real user must be granted `cluster-admin`.

Typical secure sequence:

```text
1. Install OpenShift cluster
2. Log in with kubeadmin
3. Configure enterprise identity provider
4. Log in as enterprise admin user
5. Grant cluster-admin to the enterprise admin or admin group
6. Verify access
7. Remove kubeadmin secret
```

Command to remove `kubeadmin` only after another cluster-admin exists:

```bash
oc delete secret kubeadmin -n kube-system
```

Never remove `kubeadmin` before validating another `cluster-admin` login. If no other cluster-admin exists, recovery can be very difficult and may require reinstalling the cluster.

## 4. OpenShift Authentication Architecture

OpenShift uses an integrated OAuth server by default.

High-level architecture:

```text
User / Browser / oc CLI
        ↓
OpenShift OAuth route
        ↓
OpenShift OAuth server
        ↓
Configured Identity Provider
        ↓
Identity mapping
        ↓
OpenShift User object
        ↓
RBAC authorization
        ↓
Kubernetes / OpenShift API access
```

Main components:

| Component | Namespace / API | Purpose |
|---|---|---|
| OAuth server | `openshift-authentication` | Handles login and token issuance |
| OAuth configuration | `oauth.config.openshift.io/cluster` | Cluster-wide IdP configuration |
| Authentication operator | `authentication` ClusterOperator | Manages authentication stack |
| Secrets for IdP | `openshift-config` | Stores client secrets, bind passwords, htpasswd files |
| ConfigMaps for CA | `openshift-config` | Stores custom CA bundles for IdP TLS trust |
| Users | `user.openshift.io/v1` | Represents OpenShift users |
| Identities | `user.openshift.io/v1` | Represents identities from providers |
| UserIdentityMapping | `user.openshift.io/v1` | Maps external identity to OpenShift user |
| RBAC | Kubernetes/OpenShift RBAC APIs | Grants access after authentication |

## 5. Authentication Flow in Detail

### 5.1 Web Console Login Flow

```text
1. User opens OpenShift web console.
2. Console redirects user to OpenShift OAuth server.
3. OAuth server shows provider selection page if multiple IdPs exist.
4. User selects IdP, for example LDAP or OIDC.
5. User authenticates with the external provider.
6. OAuth server receives successful authentication result.
7. OAuth server maps identity to an OpenShift User.
8. OAuth server issues token.
9. Console uses token to call the OpenShift API.
10. API server checks RBAC for every request.
```

### 5.2 CLI Login Flow

For password-based providers such as LDAP or HTPasswd:

```bash
oc login https://api.cluster.example.com:6443 -u rakesh
```

For browser/token-based providers such as OIDC, GitHub, GitLab, or Google:

```bash
oc login --token=<token> --server=https://api.cluster.example.com:6443
```

The CLI does not automatically mean a user has permissions. A login token only proves identity. RBAC still controls what the user can do.

Example:

```bash
oc whoami
oc auth can-i get pods -n dev
oc auth can-i create deployment -n dev
oc auth can-i get nodes
```

## 6. Authentication vs Authorization

This is a common interview and real-world confusion area.

| Topic | Authentication | Authorization |
|---|---|---|
| Question | Who are you? | What can you do? |
| OpenShift object | OAuth, IdP, User, Identity | Role, ClusterRole, RoleBinding, ClusterRoleBinding |
| Example failure | Login failed, 401 Unauthorized | Login works but access denied, 403 Forbidden |
| Troubleshooting area | OAuth server, IdP, certificates, callback URL, LDAP bind | RBAC bindings, group membership, namespace roles |
| Example command | `oc get oauth cluster -o yaml` | `oc auth can-i get pods` |

Example:

```text
User can log in successfully but cannot list pods.
```

This is not an identity provider problem. It is an RBAC problem.

Example:

```text
User enters username/password but login fails with invalid credentials.
```

This is likely an authentication or IdP validation problem.

## 7. Main OpenShift Identity Objects

### 7.1 `User`

A `User` object represents a human or logical actor that can be granted permissions.

Command:

```bash
oc get users
oc describe user <username>
```

Example:

```text
rakesh
john
alice@example.com
```

A `User` is the object to which RBAC can apply directly, although group-based RBAC is preferred in enterprise environments.

---

### 7.2 `Identity`

An `Identity` object represents a user identity from a specific provider.

Format:

```text
<identity_provider_name>:<provider_user_identifier>
```

Example:

```text
ldapidp:rakesh
keycloak:8f7c9c2e-6d44-4f65-9e1d-123456789abc
githubidp:rakesh-admin
```

Command:

```bash
oc get identities
oc describe identity <identity-name>
```

Important point:

> The same human user can have multiple identities if the cluster has multiple identity providers.

Example:

```text
ldapidp:rakesh        -> User rakesh
keycloak:rakesh       -> User rakesh
```

Whether OpenShift maps them to the same user depends on `mappingMethod`.

---

### 7.3 `UserIdentityMapping`

`UserIdentityMapping` links an external identity to an OpenShift user.

Commands:

```bash
oc get useridentitymappings
oc create useridentitymapping <identity_provider>:<provider_user_id> <username>
oc delete useridentitymapping <identity_provider>:<provider_user_id>
```

This becomes important when using `mappingMethod: lookup`, identity migrations, or advanced enterprise user lifecycle controls.

---

### 7.4 Groups

Groups allow admins to apply RBAC at scale.

Commands:

```bash
oc get groups
oc describe group <group-name>
oc adm groups new ocp-admins rakesh
oc adm groups add-users ocp-admins user1 user2
oc adm groups remove-users ocp-admins user1
```

Enterprise best practice:

```text
Do not bind cluster-admin to many individual users.
Bind roles to approved groups.
```

Example:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-cluster-admins
```

---

## 8. OAuth Cluster Custom Resource

Identity providers are configured in the cluster-wide OAuth resource:

```bash
oc get oauth cluster -o yaml
```

Resource identity:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: my_identity_provider
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpass-secret
```

Important points:

- The OAuth resource name is always `cluster`.
- It is cluster-wide.
- The `identityProviders` list is ordered.
- If multiple providers exist, users may see a provider selection page.
- Provider secrets and CA ConfigMaps usually live in `openshift-config`.
- Authentication pods are managed by operators; do not manually edit their deployments.

## 9. Common Identity Provider Parameters

### 9.1 `name`

Example:

```yaml
name: ldapidp
```

This name is not only cosmetic. It becomes part of the identity name:

```text
ldapidp:rakesh
```

Best practice:

- Use stable names.
- Avoid changing provider names casually.
- Changing provider name can create new identities and break existing mappings.

Good examples:

```text
corp-ldap
corp-oidc
keycloak-prod
entra-prod
```

Poor examples:

```text
test
idp1
newldap
final-prod-2
```

---

### 9.2 `type`

The `type` field defines the provider backend.

Examples:

```yaml
type: LDAP
```

```yaml
type: OpenID
```

```yaml
type: HTPasswd
```

---

### 9.3 `mappingMethod`

`mappingMethod` controls how an authenticated external identity becomes an OpenShift user.

Supported common values:

| Mapping method | Behavior | Enterprise use case |
|---|---|---|
| `claim` | Default. Creates user using preferred username. Fails if username already maps to another identity. | Simple single IdP setup |
| `add` | Adds identity to an existing user if username already exists. | Migration or multiple IdPs sharing usernames |
| `lookup` | Does not auto-create users or identities. Requires manual provisioning. | Strict enterprise control, regulated environments |

---

## 10. Deep Dive: `mappingMethod: claim`

Example:

```yaml
mappingMethod: claim
```

Behavior:

```text
External identity authenticates successfully
        ↓
OpenShift checks preferred username
        ↓
If no conflict exists, OpenShift creates User and Identity
        ↓
Identity is mapped to User
```

Advantages:

- Simple
- Default behavior
- Good for most single-provider clusters
- Less administrative overhead

Risks:

- Username collisions can block login
- Migration from LDAP to OIDC can create mapping conflicts
- Less control over who gets provisioned if IdP allows broad access

Use it when:

- You have one enterprise IdP
- Usernames are stable
- You rely on RBAC to control permissions after login
- Auto-provisioning is acceptable

---

## 11. Deep Dive: `mappingMethod: add`

Example:

```yaml
mappingMethod: add
```

Behavior:

```text
External identity authenticates successfully
        ↓
Preferred username already exists
        ↓
OpenShift maps this new identity to existing user
```

Use cases:

- Migration from LDAP to OIDC
- Running two IdPs temporarily
- Same user base exposed through different providers
- Combining GitHub Enterprise and corporate SSO

Example scenario:

```text
Existing identity: ldapidp:rakesh -> User rakesh
New identity:      keycloak:rakesh -> User rakesh
```

With `mappingMethod: add`, OpenShift can map the new Keycloak identity to the existing OpenShift user.

Risk:

If usernames are not tightly controlled, one user could accidentally or maliciously claim another username. Use only with trusted providers and verified claim design.

---

## 12. Deep Dive: `mappingMethod: lookup`

Example:

```yaml
mappingMethod: lookup
```

Behavior:

```text
External identity authenticates successfully
        ↓
OpenShift checks whether matching Identity/User/UserIdentityMapping already exists
        ↓
If mapping exists, login succeeds
        ↓
If mapping does not exist, login fails
```

Manual provisioning example:

```bash
oc create user rakesh
oc create identity corp-ldap:rakesh
oc create useridentitymapping corp-ldap:rakesh rakesh
```

Use cases:

- High-security enterprise clusters
- Regulated environments
- Production admin clusters
- Environments where only pre-approved users can log in
- External onboarding workflow controls access

Advantages:

- Prevents automatic user provisioning
- Strong administrative control
- Useful for tightly controlled production clusters

Disadvantages:

- More administrative overhead
- Requires automation for onboarding/offboarding
- Incorrect mappings can lock users out

## 13. Supported Identity Provider Types

OpenShift supports several identity provider types through the integrated OAuth server.

| Provider type | Common backend | Best use case | Production suitability |
|---|---|---|---|
| HTPasswd | Local htpasswd file | Lab, bootstrap, emergency admin | Limited for enterprise production |
| LDAP | Active Directory, 389 DS, OpenLDAP | Corporate directory authentication | Common enterprise option |
| OpenID Connect | Keycloak, Microsoft Entra ID, Okta, Ping, RHSSO | Enterprise SSO | Preferred modern option |
| GitHub | GitHub / GitHub Enterprise | Developer-centric organizations | Useful with GitHub Enterprise |
| GitLab | GitLab.com / self-managed GitLab | DevOps organizations | Useful with GitLab Enterprise |
| Google | Google identity | Google Workspace environments | Suitable for Google-based enterprises |
| Request header | Authenticating proxy | Advanced SSO/proxy integration | Powerful but sensitive |
| Basic authentication | Remote basic auth endpoint | Custom integrations | Advanced/custom use only |
| Keystone | OpenStack Keystone | OpenStack-integrated environments | Niche use case |

## 14. HTPasswd Identity Provider

### 14.1 Overview

HTPasswd validates users against a flat file containing usernames and hashed passwords.

It is often used for:

- Lab clusters
- Training clusters
- Small disconnected environments
- Temporary break-glass access
- Initial proof-of-concept clusters

It is not ideal for large enterprise production environments because it lacks centralized lifecycle management, password policy integration, MFA, and enterprise audit integration.

---

### 14.2 Create HTPasswd File

Install required tool if needed:

```bash
sudo dnf install -y httpd-tools
```

Create first user:

```bash
htpasswd -c -B -b users.htpasswd rakesh 'StrongPassword123!'
```

Add another user:

```bash
htpasswd -B -b users.htpasswd admin2 'StrongPassword123!'
```

Check file:

```bash
cat users.htpasswd
```

---

### 14.3 Create Secret

```bash
oc create secret generic htpass-secret \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config
```

Important:

- The secret must be in `openshift-config`.
- The key must be `htpasswd`.

---

### 14.4 Configure OAuth

Create file `oauth-htpasswd.yaml`:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: local-htpasswd
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpass-secret
```

Apply:

```bash
oc apply -f oauth-htpasswd.yaml
```

Validate:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc login -u rakesh
oc whoami
```

---

### 14.5 Updating HTPasswd Users

Extract existing file:

```bash
oc get secret htpass-secret \
  -n openshift-config \
  -o jsonpath='{.data.htpasswd}' | base64 -d > users.htpasswd
```

Add user:

```bash
htpasswd -B -b users.htpasswd newuser 'NewPassword123!'
```

Update secret:

```bash
oc create secret generic htpass-secret \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config \
  --dry-run=client -o yaml | oc replace -f -
```

Watch authentication rollout:

```bash
oc get pods -n openshift-authentication -w
```

## 15. LDAP Identity Provider

### 15.1 Overview

LDAP is commonly used with:

- Microsoft Active Directory
- Red Hat Directory Server / 389 Directory Server
- OpenLDAP
- Enterprise directory services

LDAP IdP validates username/password using LDAP simple bind.

Important LDAP concepts:

| Term | Meaning |
|---|---|
| LDAP URL | Location and search base used to find users |
| Bind DN | Service account used to search directory |
| Bind password | Password for bind DN |
| CA certificate | Trust bundle for LDAPS certificate validation |
| Attributes | LDAP attributes mapped to OpenShift identity fields |
| DN | Distinguished Name of user or service account |

---

### 15.2 LDAP Authentication Flow

```text
User enters username/password
        ↓
OpenShift OAuth server searches LDAP using bind DN
        ↓
LDAP returns matching user DN
        ↓
OpenShift attempts bind as that user with supplied password
        ↓
If bind succeeds, authentication succeeds
        ↓
OpenShift maps LDAP identity to OpenShift User
```

---

### 15.3 LDAP Example Design

Example environment:

```text
LDAP server: ldap.example.com
Base DN:     dc=example,dc=com
User OU:     ou=users,dc=example,dc=com
Bind DN:     uid=openshift-bind,ou=serviceaccounts,dc=example,dc=com
Username:    uid
Email:       mail
Name:        cn
```

---

### 15.4 Create Bind Password Secret

```bash
oc create secret generic ldap-bind-password \
  --from-literal=bindPassword='LDAPBindPasswordHere' \
  -n openshift-config
```

---

### 15.5 Create LDAP CA ConfigMap

For LDAPS or private CA certificates:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/path/to/ldap-ca.crt \
  -n openshift-config
```

Important:

- The key must be `ca.crt`.
- Use LDAPS where possible.
- Avoid plain LDAP over untrusted networks.

---

### 15.6 LDAP OAuth Example

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corp-ldap
    mappingMethod: claim
    type: LDAP
    ldap:
      attributes:
        id:
        - dn
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
      bindDN: uid=openshift-bind,ou=serviceaccounts,dc=example,dc=com
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
      insecure: false
      url: ldaps://ldap.example.com:636/ou=users,dc=example,dc=com?uid
```

Apply:

```bash
oc apply -f oauth-ldap.yaml
```

Validate:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc login -u rakesh
oc whoami
oc get users
oc get identities | grep corp-ldap
```

---

### 15.7 LDAP Group Sync vs LDAP Authentication

LDAP authentication and LDAP group sync are related but separate.

| Function | Purpose |
|---|---|
| LDAP Identity Provider | Authenticates users |
| LDAP Group Sync | Imports LDAP groups into OpenShift groups |

A user can authenticate successfully through LDAP but still have no useful permissions until RBAC is assigned.

Enterprise pattern:

```text
LDAP authenticates users
LDAP group sync creates OpenShift groups
RBAC binds OpenShift roles to those groups
```

Example RBAC:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-admins
oc adm policy add-role-to-group edit app-devs -n application-dev
oc adm policy add-role-to-group view auditors -n application-prod
```

## 16. OpenID Connect Identity Provider

### 16.1 Overview

OpenID Connect, or OIDC, is a modern identity layer on top of OAuth 2.0. It is widely used for enterprise SSO.

Common OIDC providers:

- Red Hat Single Sign-On / Keycloak
- Microsoft Entra ID
- Okta
- Ping Identity
- Google
- GitLab
- Other standards-compliant OIDC providers

OIDC is usually preferred for modern enterprise OpenShift because it supports stronger SSO patterns, external MFA, centralized claims, and integration with enterprise identity platforms.

---

### 16.2 OIDC Flow in OpenShift

```text
User opens OpenShift console
        ↓
OpenShift redirects to OIDC provider
        ↓
User authenticates with SSO/MFA
        ↓
OIDC provider redirects back to OpenShift OAuth callback URL
        ↓
OpenShift validates token/claims
        ↓
OpenShift maps claims to User/Identity
        ↓
OpenShift issues its own OAuth token
```

---

### 16.3 OIDC Redirect URI

OIDC provider application must include a redirect URI similar to:

```text
https://oauth-openshift.apps.<cluster_name>.<base_domain>/oauth2callback/<idp_name>
```

Example:

```text
https://oauth-openshift.apps.ocp4.example.com/oauth2callback/corp-oidc
```

If redirect URI is wrong, login usually fails after successful external authentication.

---

### 16.4 Create OIDC Client Secret

```bash
oc create secret generic oidc-client-secret \
  --from-literal=clientSecret='<OIDC_CLIENT_SECRET>' \
  -n openshift-config
```

---

### 16.5 OIDC CA ConfigMap

Required when the OIDC provider uses a private/internal CA:

```bash
oc create configmap oidc-ca \
  --from-file=ca.crt=/path/to/oidc-ca.crt \
  -n openshift-config
```

---

### 16.6 OIDC OAuth Example

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corp-oidc
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift-console
      clientSecret:
        name: oidc-client-secret
      ca:
        name: oidc-ca
      claims:
        preferredUsername:
        - preferred_username
        - email
        name:
        - name
        email:
        - email
      issuer: https://sso.example.com/realms/openshift
```

Apply:

```bash
oc apply -f oauth-oidc.yaml
```

Validate:

```bash
oc get co authentication
oc get route oauth-openshift -n openshift-authentication
oc login --server=https://api.ocp4.example.com:6443
oc whoami
oc get users
oc get identities | grep corp-oidc
```

---

### 16.7 OIDC Claims Design

Claims are very important. Bad claim design causes unstable usernames and broken RBAC.

Important claims:

| Claim | Purpose |
|---|---|
| `sub` | Stable unique subject identifier |
| `preferred_username` | Human-friendly username |
| `email` | User email address |
| `name` | Display name |
| `groups` | Group membership, depending on provider and configuration |

Best practice:

- Use stable unique identifiers for identity.
- Use human-readable username for display only when stable.
- Avoid claims that can change frequently.
- Be careful when using email as username if email addresses can change.
- Keep claim mapping consistent across clusters.

## 17. GitHub Identity Provider

### 17.1 Overview

GitHub IdP can authenticate users through GitHub or GitHub Enterprise OAuth.

Good use cases:

- Developer-heavy organizations
- GitHub Enterprise environments
- Platform engineering teams using GitHub as source control and identity boundary

Important design concern:

For public GitHub, avoid allowing broad access without organization/team restrictions. In enterprise clusters, GitHub Enterprise is usually more appropriate.

---

### 17.2 GitHub OAuth Example

```yaml
apiVersion: config.openshift.io/v1

  name: cluster

  identityProviders:
  - name: github-enterprise
    mappingMethod: claim
    type: GitHub

      clientID: <client_id>
      clientSecret:
        name: github-client-secret
      hostname: github.example.com
      ca:
        name: github-ca

      - platform-team
```

Secret:

```bash

  --from-literal=clientSecret='<github_oauth_secret>' \
```

## 20. Request Header Identity Provider

### 20.1 Overview

Request header identity provider is an advanced integration pattern where an authenticating proxy performs authentication and passes the authenticated username to OpenShift using headers such as:

```text
X-Remote-User
X-Remote-Group
X-Remote-Email
```

Architecture:

```text
User
  ↓
External authenticating proxy
  ↓
Proxy validates user with enterprise SSO
  ↓
Proxy injects trusted headers
  ↓
OpenShift OAuth server trusts configured headers
```

This is powerful but dangerous if not secured correctly.

---

### 20.2 Request Header Risks

If an attacker can spoof headers, they can impersonate users.

Therefore:

- Only trusted proxies must reach the OAuth server.
- Mutual TLS should be used where applicable.
- Header names must be carefully controlled.
- Network access to OAuth route must be restricted if possible.
- Certificate trust must be correctly configured.

This provider is usually used by advanced platform/security teams only.

---

## 21. Basic Authentication Identity Provider

Basic authentication IdP sends credentials to a remote HTTP endpoint that validates them.

It is a generic integration mechanism.

Use cases:

- Custom authentication systems
- Legacy authentication middleware
- Advanced enterprise integration where LDAP/OIDC is not directly usable

Production caution:

- Ensure TLS is valid.
- Ensure endpoint returns expected responses.
- Avoid using it when OIDC/LDAP can solve the requirement cleanly.

## 22. Keystone Identity Provider

Keystone IdP integrates with OpenStack Keystone v3.

Use cases:

- OpenShift integrated with Red Hat OpenStack Platform
- Shared OpenStack/OpenShift user authentication

This is a niche provider compared with LDAP and OIDC.

## 23. Direct Authentication with External OIDC Provider

Modern OpenShift versions also document a separate model called **direct authentication with an external OIDC identity provider**.

This differs from the traditional integrated OAuth model.

Traditional model:

```text
External IdP -> OpenShift OAuth server -> OpenShift token
```

Direct OIDC model:

```text
External OIDC provider issues tokens directly for authentication
```

Important enterprise considerations:

- It changes how the built-in OAuth server is used.
- It can affect user/group and OAuth APIs.
- It requires careful backup and break-glass access planning.
- It is suitable only when the OpenShift version and support status match your production requirements.
- Always validate supportability before using it in production.

For most production clusters today, the traditional integrated OAuth server with OIDC IdP remains the common design unless there is a specific reason to use direct external OIDC authentication.

## 24. Secrets and ConfigMaps Used by Identity Providers

Identity providers commonly use:

| Object | Namespace | Purpose |
|---|---|---|
| Secret | `openshift-config` | Client secret, bind password, htpasswd file, TLS key |
| ConfigMap | `openshift-config` | CA certificate bundle |

Common key names:

| Use case | Required key |
|---|---|
| HTPasswd file | `htpasswd` |
| OAuth client secret | `clientSecret` |
| LDAP bind password | `bindPassword` |
| CA bundle | `ca.crt` |
| TLS client certificate | `tls.crt` |
| TLS client key | `tls.key` |

Examples:

```bash
oc create secret generic oidc-client-secret \
  --from-literal=clientSecret='<secret>' \
  -n openshift-config
```

```bash
oc create secret generic ldap-bind-password \
  --from-literal=bindPassword='<password>' \
  -n openshift-config
```

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/path/to/ca.crt \
  -n openshift-config
```

## 25. Enterprise Identity Provider Design Patterns

### 25.1 Small Lab / Training Cluster

Recommended:

```text
HTPasswd
```

Why:

- Fast setup
- No external dependency
- Good for learning and demos

Not ideal for production.

---

### 25.2 Enterprise On-Prem Cluster with Active Directory

Recommended:

```text
LDAP IdP + LDAP group sync + RBAC to groups
```

Design:

```text
AD authenticates users
OpenShift syncs AD groups
RBAC assigned to synced groups
```

Example groups:

```text
OCP-Cluster-Admins
OCP-Project-Admins
OCP-Developers
OCP-Auditors
```

---

### 25.3 Modern Enterprise SSO

Recommended:

```text
OIDC with Keycloak / Microsoft Entra ID / Okta / Ping
```

Why:

- SSO support
- MFA handled outside OpenShift
- Better enterprise governance
- Cloud and hybrid identity alignment
- Better user experience

---

### 25.4 Multi-Cluster OpenShift Platform

Recommended:

```text
Common OIDC provider across all clusters
Consistent IdP name
Consistent claim mapping
Centralized group model
GitOps-managed OAuth configuration
```

Important:

Use the same `name` and claim strategy across clusters where possible.

Example:

```yaml
name: corp-oidc
```

across:

```text
dev cluster
stage cluster
prod cluster
disaster recovery cluster
```

This improves audit consistency and reduces mapping surprises.

---

### 25.5 Regulated / High-Security Cluster

Recommended:

```text
OIDC or LDAP + mappingMethod lookup + pre-provisioned users + group-based RBAC
```

Why:

- No automatic user provisioning
- Only approved identities can log in
- Better control for regulated systems

Trade-off:

Requires automation for onboarding/offboarding.

## 27. Safe Change Management for IdP Configuration

Identity provider changes can lock users out. Treat OAuth configuration as a production control-plane change.

Recommended process:

```text
1. Export current OAuth configuration
2. Confirm break-glass access
3. Prepare new Secret/ConfigMap
4. Validate IdP endpoint, DNS, TLS, callback URL
5. Apply change in maintenance window if production critical
6. Watch authentication ClusterOperator
7. Test login with normal user
8. Test login with admin user
9. Verify RBAC
10. Keep rollback YAML ready
```

Backup current OAuth config:

```bash
oc get oauth cluster -o yaml > oauth-cluster-backup-$(date +%F).yaml
```

Check current admin access:

```bash
oc whoami
oc auth can-i '*' '*' --all-namespaces
```

Apply new config:

```bash
oc apply -f oauth-new.yaml
```

Watch:

```bash
oc get co authentication -w
oc get pods -n openshift-authentication -w
```

Rollback:

```bash
oc apply -f oauth-cluster-backup-YYYY-MM-DD.yaml
```

## 28. Production Best Practices

### 28.1 Prefer Enterprise SSO or LDAP Over HTPasswd

HTPasswd is acceptable for labs and emergency local access, but enterprise production should normally use:

- OIDC
- LDAP/AD
- GitHub Enterprise / GitLab Enterprise where appropriate

### 28.2 Keep a Break-Glass Admin Path

Always maintain emergency administrative access independent of the main IdP.

Examples:

- Carefully controlled HTPasswd emergency admin
- Certificate-based kubeconfig from installation artifacts
- Privileged service account token stored securely according to company policy

Break-glass accounts must be:

- Highly restricted
- Audited
- Stored in a secure vault
- Rotated regularly
- Tested periodically

### 28.3 Use Group-Based RBAC

Avoid this pattern:

```bash
oc adm policy add-cluster-role-to-user cluster-admin rakesh
oc adm policy add-cluster-role-to-user cluster-admin john
oc adm policy add-cluster-role-to-user cluster-admin alice
```

Prefer:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-cluster-admins
```

Advantages:

- Easier auditing
- Easier onboarding/offboarding
- Cleaner compliance
- Consistent across clusters

### 28.4 Use Stable IdP Names

Do not frequently rename IdPs.

Changing:

```yaml
name: ldap
```

to:

```yaml
name: corp-ldap
```

can create new identity names and break mappings.

### 28.5 Plan Username and Claim Strategy

OIDC claim mistakes are common.

Bad strategy:

```text
Use display name as username
```

Why bad:

- Display names may contain spaces
- Names can change
- Not guaranteed unique

Better strategy:

```text
Use preferred_username or email only if stable and unique
Use sub for uniqueness where appropriate
```

### 28.6 Validate TLS and CA Chains

For LDAP, GitLab Enterprise, GitHub Enterprise, internal OIDC, and request-header providers, custom CA trust is often required.

Check:

```bash
openssl s_client -connect ldap.example.com:636 -showcerts
openssl s_client -connect sso.example.com:443 -showcerts
```

### 28.7 Use GitOps for OAuth Configuration

Store OAuth configuration templates in Git, but do not store plain secrets.

Recommended:

- OAuth CR in Git
- SealedSecrets / External Secrets / Vault integration for secrets
- Clear rollback history
- Review process for authentication changes

### 28.8 Do Not Confuse Login Access with Platform Access

Allowing a user to authenticate does not automatically grant meaningful access.

A logged-in user may still have no project permissions.

This is correct and secure.

Grant access using RBAC.

## 29. Common Failure Scenarios and Troubleshooting

### Scenario 1: User Cannot Log In

Symptoms:

```text
Login failed
Invalid credentials
OAuth error
401 Unauthorized
```

Check:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift
oc get oauth cluster -o yaml
```

For LDAP:

```bash
ldapsearch -x -H ldaps://ldap.example.com:636 \
  -D 'uid=openshift-bind,ou=serviceaccounts,dc=example,dc=com' \
  -W \
  -b 'ou=users,dc=example,dc=com' '(uid=rakesh)'
```

Possible causes:

- Wrong password
- Wrong LDAP URL
- Wrong bind DN
- Wrong bind password secret key
- LDAP certificate not trusted
- User not found by search filter
- OIDC redirect URI mismatch
- OIDC client secret mismatch
- IdP endpoint DNS issue
- OAuth pod not rolled out

---

### Scenario 2: User Can Log In but Gets Forbidden

Symptoms:

```text
Error from server (Forbidden)
User cannot list pods
User cannot create project
User cannot view nodes
```

This is an RBAC issue, not an authentication issue.

Check:

```bash
oc whoami
oc auth can-i get pods -n dev
oc auth can-i get pods --as=rakesh -n dev
oc get rolebindings -n dev
oc get clusterrolebindings | grep rakesh
oc get groups
```

Fix example:

```bash
oc adm policy add-role-to-user edit rakesh -n dev
```

Better enterprise fix:

```bash
oc adm policy add-role-to-group edit app-devs -n dev
```

---

### Scenario 3: Login Fails After Changing IdP Name

Cause:

Changing provider name changes identity prefix.

Old identity:

```text
ldap:rakesh
```

New identity:

```text
corp-ldap:rakesh
```

OpenShift treats this as a different identity.

Check:

```bash
oc get identities | grep rakesh
oc get useridentitymappings | grep rakesh
```

Fix options:

- Restore old provider name
- Use `mappingMethod: add` carefully
- Manually create user identity mapping

---

### Scenario 4: OIDC Redirect Error

Symptoms:

```text
redirect_uri mismatch
invalid redirect_uri
OAuth callback failed
```

Check OAuth route:

```bash
oc get route oauth-openshift -n openshift-authentication
```

Expected callback format:

```text
https://oauth-openshift.apps.<cluster-domain>/oauth2callback/<idp-name>
```

Fix:

- Add exact callback URL in OIDC client configuration
- Verify cluster apps domain
- Verify IdP name in OAuth CR
- Verify HTTPS certificate trust

---

### Scenario 5: LDAP TLS Certificate Error

Symptoms:

```text
certificate signed by unknown authority
x509: certificate signed by unknown authority
LDAP connection failure
```

Check:

```bash
openssl s_client -connect ldap.example.com:636 -showcerts
oc get configmap ldap-ca -n openshift-config -o yaml
```

Fix:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/path/to/ldap-ca.crt \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

Then ensure OAuth CR references:

```yaml
ca:
  name: ldap-ca
```

---

### Scenario 6: HTPasswd User Added but Cannot Login

Check whether secret was updated correctly:

```bash
oc get secret htpass-secret -n openshift-config -o yaml
```

Decode and verify:

```bash
oc get secret htpass-secret \
  -n openshift-config \
  -o jsonpath='{.data.htpasswd}' | base64 -d
```

Check OAuth rollout:

```bash
oc get pods -n openshift-authentication
oc delete pod -n openshift-authentication -l app=oauth-openshift
```

Usually the operator handles rollout, but checking pod refresh helps confirm whether new secret data is being consumed.

## 30. Interview-Style Explanation

### Question

**What is an identity provider in OpenShift?**

### Senior-Level Answer

An identity provider in OpenShift is the authentication backend used by the integrated OAuth server to validate users. OpenShift itself does not need to own enterprise passwords. Instead, it delegates authentication to providers such as LDAP, OpenID Connect, GitHub Enterprise, GitLab, Google, HTPasswd, Keystone, request-header, or basic authentication backends.

Once a user successfully authenticates, OpenShift maps the external identity to an OpenShift `User` object using the configured `mappingMethod`, such as `claim`, `add`, or `lookup`. After that, authorization is handled separately through RBAC. This distinction is important because successful login does not mean the user has permissions to create pods, view nodes, or manage projects.

In production, I prefer OIDC or LDAP integrated with enterprise SSO/directory services, group-based RBAC, stable provider names, carefully designed username claims, and a tested break-glass admin path. I avoid long-term use of `kubeadmin`, remove it only after another cluster-admin is verified, and manage OAuth configuration through controlled change management or GitOps.

## 31. Practical Checklist for Production IdP Setup

Use this checklist before touching production authentication.

### Planning

- [ ] Identify primary IdP: LDAP, OIDC, GitHub Enterprise, etc.
- [ ] Confirm whether MFA is required.
- [ ] Confirm username claim or LDAP attribute.
- [ ] Confirm group strategy.
- [ ] Confirm RBAC model.
- [ ] Confirm break-glass access.
- [ ] Confirm rollback plan.

### Technical Validation

- [ ] DNS resolution works from cluster nodes/pods.
- [ ] IdP TLS certificate is valid.
- [ ] CA bundle is available if private CA is used.
- [ ] OIDC redirect URI is exact.
- [ ] LDAP bind DN and password work.
- [ ] Required secrets exist in `openshift-config`.
- [ ] Required ConfigMaps exist in `openshift-config`.
- [ ] OAuth CR YAML is reviewed.

### Post-Change Validation

- [ ] `oc get co authentication` is healthy.
- [ ] OAuth pods are running.
- [ ] Normal user can log in.
- [ ] Admin user can log in.
- [ ] `oc whoami` returns expected username.
- [ ] `oc get identities` shows expected identity prefix.
- [ ] RBAC permissions are correct.
- [ ] Audit logs show correct user identity.

## 33. Real-World Architecture Recommendation

For a serious enterprise OpenShift platform, use this pattern:

```text
Enterprise IdP:      OIDC with Keycloak / Entra ID / Okta / Ping
Fallback IdP:        Restricted HTPasswd break-glass admin
RBAC:                Group-based only
Admin access:        Dedicated admin group
Developer access:    Namespace/project-specific groups
Audit:               API audit logs + central SIEM
Configuration:       GitOps-managed OAuth CR
Secrets:             Vault / External Secrets / sealed secrets
Offboarding:         Central IdP disables user + group sync removes access
```

Example role model:

| Group | Scope | Role |
|---|---|---|
| `ocp-cluster-admins` | Cluster | `cluster-admin` |
| `ocp-platform-ops` | Cluster | Custom platform role |
| `ocp-security-auditors` | Cluster/projects | `view` / audit role |
| `app-dev-team-a` | Namespace `app-a-dev` | `edit` |
| `app-prod-viewers` | Namespace `app-prod` | `view` |

## 34. Key Takeaways

- Identity providers authenticate users; RBAC authorizes actions.
- OpenShift uses the integrated OAuth server by default.
- The cluster-wide OAuth configuration is stored in `OAuth` resource `cluster`.
- Users, identities, and user identity mappings are separate but related objects.
- `mappingMethod` is critical for user provisioning and IdP migration.
- HTPasswd is useful for labs and emergency access but weak for enterprise production.
- LDAP is common for on-prem enterprise directories.
- OIDC is usually the preferred modern SSO pattern.
- Group-based RBAC is better than user-based RBAC.
- Never remove `kubeadmin` until another cluster-admin is tested.
- Always keep a break-glass access path.
- Treat OAuth changes as control-plane production changes.
