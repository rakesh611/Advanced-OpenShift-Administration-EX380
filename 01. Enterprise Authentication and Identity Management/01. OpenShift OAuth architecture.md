# OpenShift OAuth Architecture
## Enterprise Authentication and Identity Management for Advanced OpenShift Administration

**Audience:** Senior OpenShift / Kubernetes administrators, platform engineers, SREs, and Red Hat OpenShift interview preparation for 10+ years experience.

**Scope:** OpenShift Container Platform 4.x OAuth architecture, identity provider integration, token flow, user/identity mapping, OAuth clients, RBAC integration, production design, security hardening, and troubleshooting.

---

## 1. Executive Summary

OpenShift authentication is not only a login page. It is a complete control-plane authentication architecture that connects external enterprise identity systems such as LDAP, Active Directory, GitHub Enterprise, GitLab, Google, Keycloak, Red Hat SSO, Microsoft Entra ID, Okta, Ping Identity, and other OIDC providers to the Kubernetes API.

In the default OpenShift 4.x architecture, the OpenShift control plane includes an **integrated OAuth server**. Users authenticate through a configured **Identity Provider**. The OAuth server validates the user, maps the external identity to an OpenShift `User`, issues an OAuth access token, and that token is then used to authenticate API requests.

After authentication, authorization is evaluated separately through Kubernetes/OpenShift RBAC. OAuth answers: **Who are you?** RBAC answers: **What are you allowed to do?**

At enterprise scale, OAuth architecture must be designed around:

- Centralized identity integration
- Secure token lifetime
- Inactivity timeout
- Group synchronization
- RBAC least privilege
- Break-glass admin access
- HA and operator-managed control-plane components
- Auditability
- Disaster recovery for identity provider outages
- Safe migration from `kubeadmin` to enterprise users
- Avoiding accidental cluster lockout

## 2. Core Authentication Concepts

### 2.1 Authentication vs Authorization

| Area | Meaning | OpenShift Component |
|---|---|---|
| Authentication | Verifies user identity | OAuth server, identity provider, certificates, service account tokens |
| Authorization | Checks whether the authenticated user can perform an action | RBAC, Roles, ClusterRoles, RoleBindings, ClusterRoleBindings |
| Admission | Validates or mutates the request after authorization | Admission controllers, SCC, Pod Security Admission, webhooks |
| Audit | Records who did what | Kubernetes/OpenShift audit logs |

Example flow:

```text
User logs in  --->  OAuth authenticates user  --->  API receives bearer token
             --->  RBAC checks permission     --->  Admission validates request
             --->  Audit logs record action
```

### 2.2 OAuth in OpenShift

OAuth is the token-issuing layer for human users and applications that need to access the OpenShift API. The OpenShift OAuth server supports OAuth flows such as authorization code grant and implicit grant.

The token is normally sent to the API server as:

```http
Authorization: Bearer <oauth_access_token>
```

The API server validates the token, identifies the user and groups, then performs RBAC authorization.

### 2.3 Identity Provider

An Identity Provider, usually called **IdP**, is the backend that validates user credentials or federated identity.

Common OpenShift IdPs include:

- `HTPasswd`
- `LDAP`
- `BasicAuth`
- `RequestHeader`
- `GitHub`
- `GitLab`
- `Google`
- `OpenID Connect`
- `Keystone`

In enterprise environments, the most common patterns are:

- LDAP or Active Directory for internal users
- OIDC with Keycloak, Red Hat SSO, Okta, Microsoft Entra ID, or Ping Identity
- GitHub Enterprise or GitLab for developer identity
- Request-header authentication behind a trusted enterprise authentication proxy
- HTPasswd only for lab, bootstrap, emergency, or small non-production environments

## 4. Main Components in OAuth Architecture

### 4.1 `OAuth` Cluster Configuration Object

The main configuration object for the integrated OAuth server is:

```bash
oc get oauth cluster -o yaml
```

Full resource name:

```bash
oauth.config.openshift.io/cluster
```

This object defines:

- Identity providers
- Token configuration
- Login, provider selection, and error page templates
- OAuth server options

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corporate-ldap
    mappingMethod: claim
    type: LDAP
    ldap:
      attributes:
        id:
        - dn
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
      bindDN: "uid=ldap-bind,ou=users,dc=example,dc=com"
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
      insecure: false
      url: "ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid"
```

### 4.2 `Authentication` Cluster Configuration Object

The cluster-wide authentication mode is configured through:

```bash
oc get authentication cluster -o yaml
```

Full resource name:

```bash
authentication.config.openshift.io/cluster
```

Important concept:

- Default user-facing authentication mode is usually `IntegratedOAuth`.
- Newer OpenShift versions also support direct external OIDC authentication modes where an external OIDC provider issues tokens directly to the cluster.

The `Authentication` object is higher-level authentication control-plane configuration. The `OAuth` object is used for integrated OAuth server configuration.

### 4.3 Cluster Authentication Operator

The **Cluster Authentication Operator** manages OpenShift authentication operands. It is visible as:

```bash
oc get clusteroperator authentication
oc describe clusteroperator authentication
```

Important managed operands:

| Operand | Namespace | Purpose |
|---|---|---|
| `oauth-openshift` | `openshift-authentication` | OAuth login flows, login templates, token generation |
| `oauth-apiserver` | `openshift-oauth-apiserver` | OAuth API resources such as `OAuthAccessToken`, `OAuthAuthorizeToken`, `OAuthClient` |

Check operator status:

```bash
oc get co authentication
oc describe co authentication
```

Healthy output should show:

```text
AVAILABLE=True
PROGRESSING=False
DEGRADED=False
```

### 4.4 `oauth-openshift` Deployment

This is the actual integrated OAuth server deployment.

Useful commands:

```bash
oc get pods -n openshift-authentication
oc get deploy -n openshift-authentication
oc get svc -n openshift-authentication
oc get route -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift
```

Typical route:

```bash
oc get route oauth-openshift -n openshift-authentication
```

The route normally exposes the OAuth server externally through the OpenShift router.

### 4.5 `oauth-apiserver` Deployment

This component serves OAuth API resources.

Useful commands:

```bash
oc get pods -n openshift-oauth-apiserver
oc logs -n openshift-oauth-apiserver deploy/apiserver
oc get apiservices | grep oauth
```

OAuth API resources include:

```bash
oc api-resources | grep oauth
```

Common resources:

```text
oauthclients.oauth.openshift.io
oauthaccesstokens.oauth.openshift.io
oauthauthorizetokens.oauth.openshift.io
useroauthaccesstokens.oauth.openshift.io
```

### 4.6 Kubernetes API Server

The Kubernetes API server receives authenticated API requests. It does not normally ask the user for a password. Instead, the API request already contains a token or client certificate.

Example:

```bash
oc get pods -A --token=<token>
```

For normal `oc login`, the CLI stores the token in kubeconfig.

Check kubeconfig:

```bash
oc config view --minify
```

### 4.7 OpenShift Router / Ingress

The OAuth server is exposed as a route through the cluster ingress/router.

Check route:

```bash
oc get route -n openshift-authentication
oc describe route oauth-openshift -n openshift-authentication
```

If the OAuth route is broken, both console login and browser-based CLI login can fail.

### 4.8 Web Console

The OpenShift console uses OAuth for login. The console redirects users to the OAuth server. After successful authentication, the browser session is associated with an OAuth token.

### 4.9 `oc` CLI

The OpenShift CLI can use browser login, username/password login, or token login.

Examples:

```bash
oc login https://api.cluster.example.com:6443
oc login -u user1 -p 'password' https://api.cluster.example.com:6443
oc login --token=<token> https://api.cluster.example.com:6443
```

## 5. Detailed Login Flow

### 5.1 Browser / Web Console Login Flow

```text
1. User opens OpenShift web console.
2. Console redirects user to OAuth authorization endpoint.
3. OAuth server displays provider selection page if multiple IdPs exist.
4. User selects IdP.
5. OAuth server redirects or validates credentials with external IdP.
6. IdP validates user.
7. OAuth maps external identity to OpenShift User.
8. OAuth issues access token.
9. Browser returns to console with authenticated session.
10. Console calls Kubernetes/OpenShift API using token.
11. API server validates token.
12. RBAC checks user/group permissions.
```

### 5.2 CLI Login Flow

```text
1. Admin runs: oc login https://api.cluster.example.com:6443
2. CLI discovers OAuth metadata.
3. CLI starts browser or challenge flow depending on configuration.
4. User authenticates with configured IdP.
5. OAuth server returns access token.
6. CLI stores token in kubeconfig.
7. Future oc commands use Authorization: Bearer <token>.
```

### 5.3 Token-Based API Request Flow

```text
oc get pods
   |
   v
API request with bearer token
   |
   v
Kube API server authenticates token
   |
   v
User + Groups identified
   |
   v
RBAC checks permissions
   |
   v
Request allowed or denied
```

Example allowed request:

```bash
oc auth can-i get pods -n myproject
```

Example denied request:

```text
Error from server (Forbidden): pods is forbidden: User "user1" cannot list resource "pods" in API group "" in the namespace "prod"
```

This means OAuth authentication succeeded, but RBAC authorization failed.

## 7. OAuth Token Types

### 7.1 Access Token

Access tokens are longer-lived tokens used to authenticate to the OpenShift API.

Example:

```bash
oc whoami -t
```

Use token manually:

```bash
TOKEN=$(oc whoami -t)
curl -k -H "Authorization: Bearer ${TOKEN}" https://api.cluster.example.com:6443/apis
```

### 7.2 Authorize Code

Authorize codes are short-lived intermediate tokens used in the authorization code flow. They are exchanged for access tokens.

### 7.3 User-Owned OAuth Tokens

Users can list their own tokens:

```bash
oc get useroauthaccesstokens
```

Filter by OAuth client:

```bash
oc get useroauthaccesstokens --field-selector=clientName="console"
```

Delete a token:

```bash
oc delete useroauthaccesstoken <token-name>
```

### 7.4 Cluster Admin Token Review

Cluster administrators can inspect OAuth tokens at cluster scope:

```bash
oc get oauthaccesstokens
oc describe oauthaccesstoken <token-name>
```

Be careful: token object names are not normally useful for login by themselves, but token data must still be treated carefully.

## 8. Token Lifetime and Security Configuration

### 8.1 Default Token Lifetime

By default, OpenShift OAuth access tokens are valid for 24 hours unless configured otherwise.

Check current configuration:

```bash
oc get oauth cluster -o yaml
```

### 8.2 Configure Access Token Maximum Age

Example: set OAuth access tokens to 48 hours.

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  tokenConfig:
    accessTokenMaxAgeSeconds: 172800
```

Apply:

```bash
oc apply -f oauth-token-max-age.yaml
```

Verify:

```bash
oc describe oauth.config.openshift.io/cluster
```

### 8.3 Configure Token Inactivity Timeout

Inactivity timeout expires the token if it has not been used for a defined time.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  tokenConfig:
    accessTokenInactivityTimeout: 30m
```

Apply:

```bash
oc apply -f oauth-token-inactivity.yaml
```

Verify operators:

```bash
oc get co authentication
oc get co kube-apiserver
```

Important points:

- If no inactivity timeout is configured, tokens do not expire due to inactivity.
- In recent OpenShift documentation, the minimum inactivity timeout value is `300s`.
- OAuth client-level inactivity timeout can override the internal OAuth server setting.

### 8.4 Enterprise Token Policy Recommendations

| Environment | Suggested Token Max Age | Suggested Inactivity Timeout |
|---|---:|---:|
| Lab | 24h to 7d | Optional |
| Shared non-prod | 24h | 30m to 2h |
| Production | 8h to 24h | 15m to 1h |
| High-security production | 1h to 8h | 15m to 30m |

Practical senior admin advice:

- Do not set very long token lifetime for production users.
- Use short inactivity timeout for sensitive clusters.
- Keep break-glass access documented and tested.
- Rotate tokens after identity provider or RBAC incidents.
- Review token usage during audits.

## 9. OAuth Clients

An OAuth client represents an application or client that requests tokens from the OAuth server.

### 9.1 Default OAuth Clients

OpenShift automatically creates default OAuth clients for platform authentication.

Common default clients:

| OAuth Client | Purpose |
|---|---|
| `openshift-browser-client` | Browser-based interactive login |
| `openshift-challenging-client` | CLI/client login that can handle `WWW-Authenticate` challenges |

### 9.2 Custom OAuth Client

You can register an application as an OAuth client.

Example:

```yaml
kind: OAuthClient
apiVersion: oauth.openshift.io/v1
metadata:
  name: demo-app
secret: "super-secret-value"
redirectURIs:
- "https://demo.apps.cluster.example.com/oauth/callback"
grantMethod: prompt
```

Apply:

```bash
oc create -f oauthclient-demo.yaml
```

List clients:

```bash
oc get oauthclients
oc describe oauthclient demo-app
```

### 9.3 Grant Method

| Grant Method | Behavior | Use Case |
|---|---|---|
| `auto` | Automatically approve grant | Trusted internal clients |
| `prompt` | Prompt user to approve or deny | Third-party or user-facing apps |

Senior-level recommendation:

- Use `prompt` for most custom OAuth clients.
- Use `auto` only for trusted platform components or controlled internal applications.
- Restrict redirect URIs tightly.
- Do not use wildcard redirect URIs unless absolutely necessary.

## 10. Identity, User, and Mapping Architecture

OpenShift separates external identity from OpenShift user objects.

### 10.1 Important Objects

| Object | API Group | Meaning |
|---|---|---|
| `User` | `user.openshift.io/v1` | OpenShift user account |
| `Identity` | `user.openshift.io/v1` | External IdP identity record |
| `UserIdentityMapping` | `user.openshift.io/v1` | Link between Identity and User |
| `Group` | `user.openshift.io/v1` | Group object used for RBAC |

Check users:

```bash
oc get users
oc describe user <username>
```

Check identities:

```bash
oc get identities
oc describe identity <idp-name>:<idp-user-id>
```

Check groups:

```bash
oc get groups
oc describe group <group-name>
```

### 10.2 Mapping Method

`mappingMethod` controls how an IdP identity maps to an OpenShift user.

| Mapping Method | Behavior | Enterprise Usage |
|---|---|---|
| `claim` | Default. Creates user with preferred username. Fails if username already maps to another identity. | Good default for single IdP |
| `add` | Maps identity to existing user if same username exists. | Useful when multiple IdPs represent the same users |
| `lookup` | Does not automatically create users or identities. Admin must pre-create them. | Strict enterprise control / regulated environments |

### 10.3 `claim` Mapping Example

```yaml
spec:
  identityProviders:
  - name: corporate-oidc
    mappingMethod: claim
    type: OpenID
```

Behavior:

```text
External identity: corporate-oidc:00u123456
Preferred username: rakesh
OpenShift user: rakesh
```

### 10.4 `add` Mapping Example

Use case: migrate from LDAP to OIDC while keeping same OpenShift usernames.

```yaml
spec:
  identityProviders:
  - name: new-oidc
    mappingMethod: add
    type: OpenID
```

This can add the new identity to an existing OpenShift user if the username matches.

### 10.5 `lookup` Mapping Example

Use case: manually approved user onboarding.

```bash
oc create user rakesh
oc create identity corporate-ldap:uid=rakesh,ou=users,dc=example,dc=com
oc create useridentitymapping corporate-ldap:uid=rakesh,ou=users,dc=example,dc=com rakesh
```

Then configure IdP with:

```yaml
mappingMethod: lookup
```

This prevents automatic provisioning of users during login.

## 11. Supported Identity Provider Architecture

### 11.1 HTPasswd

Best for:

- Lab
- Training
- Bootstrap
- Emergency break-glass
- Small test clusters

Not recommended as the main enterprise production identity source.

Create HTPasswd file:

```bash
htpasswd -c -B -b users.htpasswd admin1 'StrongPassword'
htpasswd -B -b users.htpasswd user1 'UserPassword'
```

Create secret:

```bash
oc create secret generic htpass-secret \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config
```

Configure OAuth:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: local-htpasswd
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpass-secret
```

Apply:

```bash
oc apply -f htpasswd-oauth.yaml
```

### 11.2 LDAP / Active Directory

Best for:

- Enterprise Linux/Windows identity
- Centralized username/password login
- Mature organization identity management

Important design points:

- Use `ldaps://`, not plain `ldap://`, whenever possible.
- Use a dedicated bind account.
- Store bind password in `openshift-config` Secret.
- Store CA bundle in `openshift-config` ConfigMap.
- Decide `id`, `preferredUsername`, `name`, and `email` attributes carefully.
- Sync LDAP groups separately with `oc adm groups sync` if you need group-based RBAC.

LDAP secret example:

```bash
oc create secret generic ldap-bind-password \
  --from-literal=bindPassword='BindPasswordHere' \
  -n openshift-config
```

LDAP CA ConfigMap:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=ldap-ca.crt \
  -n openshift-config
```

OAuth LDAP example:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corp-ldap
    mappingMethod: claim
    type: LDAP
    ldap:
      attributes:
        id:
        - dn
        preferredUsername:
        - sAMAccountName
        name:
        - cn
        email:
        - mail
      bindDN: "CN=openshift-bind,OU=ServiceAccounts,DC=example,DC=com"
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
      insecure: false
      url: "ldaps://ad.example.com:636/OU=Users,DC=example,DC=com?sAMAccountName"
```

### 11.3 OpenID Connect / OIDC

Best for:

- SSO
- MFA
- Federation
- Cloud identity providers
- Keycloak / Red Hat SSO
- Microsoft Entra ID
- Okta
- Ping Identity

OIDC secret:

```bash
oc create secret generic oidc-client-secret \
  --from-literal=clientSecret='OIDC_CLIENT_SECRET' \
  -n openshift-config
```

OIDC OAuth example:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corporate-oidc
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift
      clientSecret:
        name: oidc-client-secret
      issuer: https://sso.example.com/realms/platform
      claims:
        preferredUsername:
        - preferred_username
        name:
        - name
        email:
        - email
      extraScopes:
      - email
      - profile
```

Important OIDC checks:

```bash
curl -k https://sso.example.com/realms/platform/.well-known/openid-configuration | jq
```

Common OIDC problems:

- Wrong issuer URL
- Wrong redirect URI registered on IdP side
- Missing `openid` scope
- Wrong claim mapping
- TLS trust failure
- Client secret mismatch
- User authenticates but RBAC denies access

### 11.4 GitHub / GitHub Enterprise

Best for:

- Developer teams
- Organizations already using GitHub Enterprise
- Source-control-centered access workflows

Important controls:

- Restrict to GitHub organizations/teams where possible.
- Avoid allowing any public GitHub user into production clusters.
- Use group/team mapping carefully.

### 11.5 GitLab

Best for:

- GitLab-centered DevOps teams
- GitLab.com or self-managed GitLab

### 11.6 Request Header

Best for:

- Advanced enterprise authentication proxy
- Kerberos/SPNEGO proxy
- Existing SSO gateway
- Custom authentication gateway

Warning:

Request-header IdP must be protected carefully. Only a trusted proxy must be able to set the remote user headers. Otherwise, a user could spoof headers and impersonate another user.

### 11.7 Keystone

Used when integrating with OpenStack Keystone v3 environments.

## 12. Direct External OIDC Authentication vs Integrated OAuth

Newer OpenShift 4.x versions support a direct authentication mode where an external OIDC provider issues tokens directly for cluster authentication. This can replace the built-in OAuth server for some use cases.

### 12.1 Integrated OAuth Mode

```text
User ---> OpenShift OAuth Server ---> External IdP ---> OAuth token issued by OpenShift ---> API
```

Benefits:

- Traditional OpenShift behavior
- Supports multiple OpenShift identity provider types
- Uses OpenShift OAuth token resources
- Works with default console and CLI model
- Familiar for many admins

### 12.2 Direct External OIDC Mode

```text
User ---> External OIDC Provider ---> OIDC token issued by external provider ---> API
```

Benefits:

- Centralized token issuing outside OpenShift
- Better alignment with enterprise SSO platforms
- Can use advanced OIDC provider capabilities
- Useful for multi-cluster/hybrid identity design

Important cautions:

- Only one direct OIDC provider is supported in current documentation.
- Existing users/groups/OAuth clients/identity provider configuration should be backed up before switching.
- Keep a long-lived emergency admin access method before replacing the integrated OAuth server.
- Direct OIDC changes the operational model; test in non-production first.

### 12.3 Decision Matrix

| Requirement | Integrated OAuth | Direct External OIDC |
|---|---|---|
| Traditional OpenShift login | Strong | Different model |
| Multiple IdP types | Strong | Limited |
| Enterprise SSO with advanced IdP controls | Good | Strong |
| Existing OAuth clients | Strong | Requires review |
| Central token governance outside cluster | Moderate | Strong |
| Operational familiarity | Strong | Requires planning |
| Migration risk | Lower | Higher |

## 13. RBAC Integration After OAuth Authentication

OAuth does not grant permissions by itself. After login, RBAC decides access.

### 13.1 RBAC Evaluation Logic

```text
Authenticated user + groups
        |
        v
Find RoleBindings / ClusterRoleBindings for user/groups
        |
        v
Resolve Roles / ClusterRoles
        |
        v
Check verb + resource + namespace
        |
        v
Allow or deny
```

### 13.2 Example: Grant Cluster Admin

```bash
oc adm policy add-cluster-role-to-user cluster-admin rakesh
```

Verify:

```bash
oc auth can-i '*' '*' --all-namespaces --as=rakesh
```

### 13.3 Example: Grant Project Admin

```bash
oc adm policy add-role-to-user admin rakesh -n dev-project
```

### 13.4 Example: Grant Group Access

```bash
oc adm policy add-role-to-group edit dev-team -n dev-project
```

### 13.5 Enterprise Best Practice

Prefer group-based RBAC:

```text
IdP group / LDAP group ---> OpenShift Group ---> RoleBinding / ClusterRoleBinding
```

Avoid assigning permissions to individual users unless required for break-glass or temporary troubleshooting.

## 14. LDAP Group Synchronization

OpenShift can synchronize LDAP groups into OpenShift `Group` objects.

Example dry run:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml
```

Apply changes:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

Example cron-style pattern:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

Then bind RBAC to groups:

```bash
oc adm policy add-cluster-role-to-group view ldap-viewers
oc adm policy add-role-to-group edit app-devs -n dev
```

Production advice:

- Synchronize groups from a controlled OU or allowlist.
- Avoid syncing the entire directory if unnecessary.
- Use group allowlists and blacklists.
- Run group sync from a controlled admin automation environment.
- Audit group-to-role bindings regularly.

## 15. `kubeadmin` User and Break-Glass Strategy

During installation, OpenShift creates a temporary `kubeadmin` user.

Production process:

```text
1. Install cluster.
2. Log in with kubeadmin.
3. Configure enterprise IdP.
4. Log in as enterprise admin user.
5. Grant cluster-admin to enterprise admin/group.
6. Verify new admin can access cluster.
7. Remove kubeadmin secret.
```

Remove `kubeadmin`:

```bash
oc delete secret kubeadmin -n kube-system
```

Critical warning:

Do **not** delete `kubeadmin` before another user has working `cluster-admin` access. If you remove `kubeadmin` too early and no other cluster-admin exists, you can lock yourself out and may need to reinstall or recover using special procedures.

Recommended break-glass methods:

- Certificate-based admin kubeconfig stored securely
- Long-lived service account token for emergency automation, where approved
- Dedicated emergency HTPasswd IdP in restricted environments
- Offline documented recovery process
- Tested quarterly in non-production

## 16. Custom OAuth Server URL

The OAuth route can be customized using the cluster `Ingress` component route configuration.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Ingress
metadata:
  name: cluster
spec:
  componentRoutes:
  - name: oauth-openshift
    namespace: openshift-authentication
    hostname: oauth.example.com
    servingCertKeyPairSecret:
      name: oauth-custom-cert
```

Create TLS secret:

```bash
oc create secret tls oauth-custom-cert \
  --cert=tls.crt \
  --key=tls.key \
  -n openshift-config
```

Edit ingress:

```bash
oc edit ingress.config.openshift.io cluster
```

Important cautions:

- Changing OAuth hostname can break trust for clients that use the old CA or route.
- Update IdP redirect URIs after hostname changes.
- Validate console login and CLI login after change.
- Validate custom CA trust with `oc login --certificate-authority=<ca.crt>` when needed.

## 17. Production Enterprise Design Patterns

### 17.1 Single Corporate LDAP/AD IdP

```text
OpenShift OAuth ---> LDAPS ---> Active Directory
OpenShift Groups <--- LDAP group sync
RBAC ---> OpenShift Groups
```

Best when the organization uses AD as the primary identity system.

Pros:

- Simple
- Familiar
- Good for internal users
- Group sync works well

Cons:

- MFA may require additional integration
- Password handling goes through OpenShift login flow
- External users are harder to integrate

### 17.2 OIDC SSO with Keycloak / Red Hat SSO / Entra / Okta

```text
OpenShift OAuth ---> OIDC Provider ---> Enterprise SSO / MFA / Federation
```

Pros:

- SSO support
- MFA support
- Federation
- Better for hybrid and cloud-native enterprise environments

Cons:

- Requires correct OIDC claims and redirect URI configuration
- Group claim design can be complex
- Migration from LDAP must be planned carefully

### 17.3 Multiple IdPs

Example:

```yaml
spec:
  identityProviders:
  - name: corp-oidc
    type: OpenID
    mappingMethod: claim
  - name: emergency-htpasswd
    type: HTPasswd
    mappingMethod: claim
```

Use cases:

- Corporate SSO for normal users
- Emergency HTPasswd for break-glass
- Separate IdPs for internal/external teams

Caution:

When multiple IdPs can produce the same username, use `mappingMethod` carefully. Wrong mapping can create duplicate users or identity collision problems.

### 17.4 Hub-and-Spoke Multi-Cluster Identity

For multiple OpenShift clusters:

```text
Central IdP / SSO
      |
      +-- Cluster A OAuth
      +-- Cluster B OAuth
      +-- Cluster C OAuth
      +-- ACM Hub / GitOps
```

Recommendations:

- Use same IdP across clusters.
- Use group-based RBAC across clusters.
- Manage OAuth configuration through GitOps where possible.
- Use consistent group names and ClusterRoleBindings.
- Keep per-cluster break-glass access.

### 17.5 Regulated Enterprise Pattern

```text
Direct OIDC / Integrated OAuth + lookup mapping
Manual user provisioning
Group-based RBAC
Short token lifetime
Audit log forwarding
Break-glass certificate kubeconfig
```

Use this for banking, defense, government, or high-compliance environments.

## 18. Security Hardening Checklist

### 18.1 Identity Provider Security

- Use enterprise IdP, not `kubeadmin`, for normal production access.
- Use LDAPS, not plain LDAP.
- Use trusted CA bundles.
- Store secrets only in `openshift-config` with restricted access.
- Rotate client secrets and bind passwords.
- Enforce MFA at the IdP layer when possible.
- Restrict GitHub/GitLab providers to trusted organizations or groups.
- Protect request-header IdP behind trusted proxy and mTLS.

### 18.2 Token Security

- Keep token max age appropriate for risk level.
- Configure inactivity timeout for production.
- Delete stale user-owned tokens.
- Avoid sharing `oc whoami -t` output.
- Do not put tokens in scripts without secret management.
- Rotate tokens after admin role or IdP compromise.

### 18.3 RBAC Security

- Use group-based RBAC.
- Avoid direct `cluster-admin` to many users.
- Use project-scoped roles when possible.
- Regularly audit ClusterRoleBindings.
- Avoid binding `system:authenticated` to powerful roles.
- Review service account permissions separately.

### 18.4 Operational Security

- Keep a tested break-glass method.
- Monitor `clusteroperator authentication`.
- Alert on OAuth pod failures.
- Forward audit logs to SIEM.
- Back up OAuth/Authentication configs before major changes.
- Test IdP failover and outage behavior.

## 20. Troubleshooting OAuth Login Issues

### 20.1 Problem: Console Login Page Not Opening

Symptoms:

```text
Browser cannot open login page
OAuth route returns 503
Console redirects repeatedly
```

Checks:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc get route oauth-openshift -n openshift-authentication
oc describe route oauth-openshift -n openshift-authentication
oc get endpoints -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift
```

Likely causes:

- OAuth pods not running
- Router issue
- Route misconfiguration
- Custom certificate issue
- Authentication operator degraded
- Ingress component route misconfigured

### 20.2 Problem: `oc login` Fails with Unauthorized

Symptoms:

```text
error: You must be logged in to the server (Unauthorized)
Login failed (401 Unauthorized)
```

Checks:

```bash
oc get oauth cluster -o yaml
oc logs -n openshift-authentication deploy/oauth-openshift
oc get secrets -n openshift-config
oc get configmaps -n openshift-config
```

Likely causes:

- Wrong username/password
- IdP bind failure
- OIDC client secret wrong
- LDAP bind password wrong
- LDAP search base wrong
- TLS CA issue
- User not found in IdP
- Token expired due to max age or inactivity timeout

### 20.3 Problem: Authentication Works but User Has No Access

Symptoms:

```text
You are logged in but cannot list projects
Forbidden errors
```

Example:

```text
Error from server (Forbidden): users.user.openshift.io is forbidden
```

Checks:

```bash
oc whoami
oc get user $(oc whoami) -o yaml
oc get identities | grep $(oc whoami)
oc auth can-i get projects
oc auth can-i get pods -n dev
oc get rolebindings -A | grep $(oc whoami)
oc get clusterrolebindings | grep $(oc whoami)
```

Cause:

Authentication succeeded. RBAC authorization failed.

Fix:

```bash
oc adm policy add-role-to-user view <user> -n <project>
oc adm policy add-role-to-user edit <user> -n <project>
oc adm policy add-cluster-role-to-user cluster-admin <user>
```

Prefer groups:

```bash
oc adm policy add-role-to-group edit dev-team -n dev
```

### 20.4 Problem: LDAP Login Fails

Checks:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift | grep -i ldap
oc get secret ldap-bind-password -n openshift-config -o yaml
oc get configmap ldap-ca -n openshift-config -o yaml
```

External tests from admin machine:

```bash
ldapsearch -x -H ldaps://ad.example.com:636 \
  -D 'CN=openshift-bind,OU=ServiceAccounts,DC=example,DC=com' \
  -W \
  -b 'OU=Users,DC=example,DC=com' \
  '(sAMAccountName=user1)'
```

Likely causes:

- Wrong bind DN
- Wrong bind password
- Wrong search base
- Wrong attribute mapping
- CA certificate missing or incorrect
- Firewall between cluster and LDAP
- DNS resolution failure from OAuth pod

Network test from a debug pod:

```bash
oc run ldap-test --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk ldaps://ad.example.com:636
```

### 20.5 Problem: OIDC Login Fails

Checks:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift | grep -i oidc
curl -k https://sso.example.com/realms/platform/.well-known/openid-configuration | jq
```

Validate redirect URI in OIDC provider:

```text
https://oauth-openshift.apps.<cluster-domain>/oauth2callback/<idp-name>
```

Common causes:

- Wrong issuer URL
- OIDC provider does not expose discovery endpoint
- Wrong client ID
- Wrong client secret
- Missing redirect URI
- Wrong TLS CA
- Claims do not contain expected username/email
- User authenticated but RBAC not granted

### 20.6 Problem: Multiple IdPs Create Duplicate Users

Symptoms:

```text
rakesh
rakesh2
corporate:rakesh
github:rakesh
```

Checks:

```bash
oc get users
oc get identities
oc describe user rakesh
```

Fix strategy:

- Review `mappingMethod`.
- Use `add` when multiple IdPs identify the same user population and usernames match.
- Use `lookup` for strict manual control.
- Clean wrong mappings carefully.

Warning:

Do not randomly delete users/identities in production without understanding rolebindings, audit records, and identity mappings.

### 20.7 Problem: `clusteroperator/authentication` Degraded

Checks:

```bash
oc describe co authentication
oc get pods -n openshift-authentication
oc get pods -n openshift-oauth-apiserver
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Possible causes:

- Invalid OAuth configuration
- Missing referenced Secret or ConfigMap
- Bad custom login template
- Bad IdP CA data
- OAuth deployment rollout failure
- APIService issue
- Router/route/certificate problem

Rollback approach:

```bash
oc get oauth cluster -o yaml > oauth-before-fix.yaml
oc edit oauth cluster
```

If GitOps manages OAuth, revert the last commit and allow reconciliation.

### 20.8 Problem: After Custom OAuth URL Change, Login Breaks

Checks:

```bash
oc get ingress.config.openshift.io cluster -o yaml
oc get secret -n openshift-config <oauth-cert-secret>
oc get route oauth-openshift -n openshift-authentication -o yaml
```

Likely causes:

- Certificate CN/SAN does not match custom hostname
- CA not trusted by client
- OIDC redirect URI still points to old OAuth route
- DNS for custom hostname missing
- Router not serving expected certificate

Fix:

- Correct DNS.
- Correct certificate.
- Update OIDC redirect URI.
- Test with `oc login --certificate-authority=ca.crt` if private CA is used.

## 21. Interview-Style Deep-Dive Questions and Answers

### Q1. What happens when a user logs in to OpenShift?

A user accesses the console or runs `oc login`. The client is redirected to the OpenShift OAuth server. The OAuth server uses the configured identity provider to validate the user. After successful authentication, it maps the IdP identity to an OpenShift `User`, issues an OAuth access token, and returns that token to the client. The client then sends the token to the Kubernetes API server. The API server authenticates the token, builds the user and group identity, and evaluates RBAC for every request.

### Q2. Is OAuth responsible for permissions?

No. OAuth is responsible for authentication and token issuance. Permissions are handled by RBAC using Roles, ClusterRoles, RoleBindings, and ClusterRoleBindings.

### Q3. What is the difference between `User` and `Identity`?

`Identity` represents the external identity from an IdP, for example `corporate-ldap:uid=rakesh`. `User` is the OpenShift account used for RBAC. `UserIdentityMapping` connects an external identity to an OpenShift user.

### Q4. Why can login succeed but `oc get pods` fail?

Because authentication succeeded but authorization failed. The user has a valid OAuth token, but RBAC does not grant permission to list pods in that namespace.

### Q5. Which namespace contains the OAuth server?

The integrated OAuth server deployment runs in `openshift-authentication` as `oauth-openshift`. The OAuth API server runs in `openshift-oauth-apiserver`.

### Q6. What is the role of the Authentication Operator?

The Authentication Operator manages authentication-related operands such as the OAuth server and OAuth API server. It watches cluster authentication/OAuth configuration and reconciles deployments, services, RBAC, network policies, and monitoring resources.

### Q7. What is the safest way to remove `kubeadmin`?

First configure an enterprise IdP. Then log in as an enterprise user. Grant that user or group `cluster-admin`. Verify access. Only then delete the `kubeadmin` secret from `kube-system`.

### Q8. How do you avoid lockout while changing OAuth?

Keep a working admin session open, export current OAuth config, keep a certificate-based admin kubeconfig, validate IdP settings in non-production, and avoid deleting `kubeadmin` until another admin is confirmed.

### Q9. What is `mappingMethod: lookup`?

It disables automatic user and identity creation. Administrators must create the user, identity, and user identity mapping manually. It is useful for regulated environments where only pre-approved users can log in.

### Q10. How do you troubleshoot OAuth issues at senior level?

Start from control-plane health, then OAuth pods, route, logs, IdP connectivity, referenced Secrets/ConfigMaps, certificate trust, token configuration, user/identity mapping, and finally RBAC.

## 23. Common Mistakes by Administrators

1. Deleting `kubeadmin` before verifying another `cluster-admin` user.
2. Assuming successful login means user has access.
3. Giving `cluster-admin` to individual users instead of groups.
4. Using plain LDAP instead of LDAPS.
5. Forgetting CA bundle for LDAP/OIDC private certificates.
6. Misconfiguring OIDC redirect URI.
7. Using wrong OIDC issuer URL.
8. Creating multiple IdPs without understanding `mappingMethod`.
9. Not backing up OAuth config before changes.
10. Setting token lifetime too long in production.
11. Not configuring inactivity timeout in sensitive environments.
12. Not testing IdP outage behavior.
13. Treating OAuth token leaks as low severity.
14. Forgetting to update GitOps manifests after manual changes.
15. Troubleshooting RBAC as an OAuth issue.

## 26. Final Mental Model

Remember OpenShift OAuth architecture like this:

```text
IdP validates identity.
OAuth issues token.
API server authenticates token.
RBAC authorizes action.
Admission validates request.
Audit records the event.
```

For a 10+ years OpenShift administrator, the key is not only knowing how to configure an IdP. The key is understanding the complete chain:

```text
Enterprise IdP
  -> OAuth server
  -> User / Identity mapping
  -> Token issuance
  -> API authentication
  -> Group membership
  -> RBAC authorization
  -> Audit and compliance
  -> Break-glass recovery
```

When troubleshooting, always identify where the failure occurs:

| Failure Point | Symptom | Example Fix |
|---|---|---|
| OAuth route | Login page unavailable | Check router, route, OAuth pods |
| IdP validation | 401 login failure | Check LDAP/OIDC config, secrets, CA |
| Identity mapping | Wrong or duplicate user | Review `mappingMethod`, identities |
| Token lifecycle | Session expires unexpectedly | Check max age/inactivity timeout |
| RBAC | Forbidden after login | Add RoleBinding/ClusterRoleBinding |
| Operator | Authentication degraded | Check `co authentication`, pod logs |
