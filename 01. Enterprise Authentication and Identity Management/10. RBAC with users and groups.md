## 1. Core Idea

**RBAC** means **Role-Based Access Control**.

In OpenShift, RBAC answers this question:

> **Who can do what, on which resource, in which scope?**

Example:

```text
Can user rakesh create deployments in project finance-prod?
Can group ocp-dev-team-a view pods in project app-dev?
Can group ocp-platform-admins manage the full cluster?
Can service account pipeline-sa patch deployments in project payment-prod?
```

RBAC is not about login password verification. RBAC starts **after authentication succeeds**.

A senior administrator should always separate these two steps:

```text
Authentication:
    Who are you?

Authorization:
    What are you allowed to do?
```

OpenShift uses OAuth and identity providers for authentication, and RBAC for authorization.

## 2. Authentication vs Authorization

### 2.1 Authentication

Authentication verifies the identity of the user.

Examples of authentication providers:

```text
HTPasswd
LDAP
Active Directory
OpenID Connect
Keycloak / Red Hat SSO
GitHub
GitLab
Google
Request Header
Keystone
```

After successful login, OpenShift creates or maps identity information such as:

```text
User
Identity
Group membership
OAuth token
```

Example commands:

```bash
oc whoami
oc whoami --show-token
oc whoami --show-groups
oc get users
oc get identities
```

### 2.2 Authorization

Authorization decides whether the authenticated identity can perform an action.

Example:

```bash
oc auth can-i create pods -n finance-dev
oc auth can-i delete nodes
oc auth can-i patch deployment/payment-api -n payment-prod
```

Expected output:

```text
yes
```

or:

```text
no
```

Authorization is controlled by:

```text
Role
ClusterRole
RoleBinding
ClusterRoleBinding
Users
Groups
ServiceAccounts
```

## 3. OpenShift RBAC Object Model

OpenShift uses Kubernetes RBAC APIs plus OpenShift-specific administrative commands and user/group integration.

### 3.1 Main RBAC Objects

| Object | Scope | Purpose |
|---|---|---|
| `Role` | Namespace/project | Defines permissions inside one namespace |
| `ClusterRole` | Cluster-wide | Defines reusable permissions across the cluster |
| `RoleBinding` | Namespace/project | Binds a `Role` or `ClusterRole` to users/groups/serviceaccounts inside one namespace |
| `ClusterRoleBinding` | Cluster-wide | Binds a `ClusterRole` to users/groups/serviceaccounts across the cluster |
| `User` | Cluster object | Represents a human or external identity mapped into OpenShift |
| `Group` | Cluster object | Collection of users for easier permission management |
| `ServiceAccount` | Namespace object | Identity used by pods, controllers, jobs, pipelines, and automation |

### 3.2 Mental Model

```text
User / Group / ServiceAccount
        |
        |  bound by
        v
RoleBinding / ClusterRoleBinding
        |
        |  references
        v
Role / ClusterRole
        |
        |  contains
        v
Rules: apiGroups + resources + verbs + resourceNames
```

### 3.3 PolicyRule Structure

A rule usually contains:

```yaml
apiGroups:
  - apps
resources:
  - deployments
verbs:
  - get
  - list
  - watch
  - patch
```

Meaning:

```text
Allow get/list/watch/patch on apps/deployments.
```

### 3.4 Common Verbs

| Verb | Meaning |
|---|---|
| `get` | Read one object |
| `list` | List multiple objects |
| `watch` | Watch changes |
| `create` | Create a new object |
| `update` | Replace an object |
| `patch` | Partially modify an object |
| `delete` | Delete one object |
| `deletecollection` | Delete multiple objects |
| `bind` | Bind a role to a subject |
| `escalate` | Create or modify roles with permissions the actor does not already have |
| `impersonate` | Act as another user/group/serviceaccount |
| `use` | Used by some OpenShift resources such as Security Context Constraints |

## 4. Users, Identities, Groups, and ServiceAccounts

## 4.1 User

A `User` is the OpenShift representation of a human account.

Example:

```bash
oc get users
```

Example output:

```text
NAME           UID                                    FULL NAME        IDENTITIES
rakesh         8d91f6f1-xxxx-xxxx-xxxx-123456789abc   Rakesh Jha       ldap:rakesh
alice          99f2c8a7-xxxx-xxxx-xxxx-987654321abc   Alice Sharma     oidc:alice
```

View a user:

```bash
oc describe user rakesh
```

Important point:

> A user object in OpenShift does not necessarily mean OpenShift stores the user's password. Passwords are normally stored in the external identity provider.

---

## 4.2 Identity

An `Identity` maps an external identity provider account to an OpenShift `User`.

Example:

```bash
oc get identities
```

Example output:

```text
NAME                 IDP NAME   IDP USER NAME   USER NAME   USER UID
ldap:rakesh          ldap       rakesh          rakesh      8d91f6f1-...
oidc:alice           oidc       alice           alice       99f2c8a7-...
```

Typical identity format:

```text
<identity-provider-name>:<provider-user-id>
```

Examples:

```text
ldap:rakesh
htpasswd:admin
keycloak:35ca6d98-1111-2222-3333-abcd
github:1234567
```

### Why identity matters

A common production mistake is changing identity provider mapping without understanding existing identities.

Example issue:

```text
Old identity:
ldap:rakesh

New identity:
ad:rakesh.jha
```

If mapping changes, OpenShift might treat the same human as a new user unless identity mapping is handled properly.

---

## 4.3 Group

A `Group` is a collection of users.

Groups are preferred for enterprise RBAC because permissions should be assigned to teams, not to individual people.

Example:

```bash
oc get groups
```

Example output:

```text
NAME                    USERS
ocp-platform-admins     rakesh, anil
ocp-dev-team-a          alice, bob
ocp-readonly            auditor1, auditor2
```

Describe a group:

```bash
oc describe group ocp-dev-team-a
```

### Manual group creation

```bash
oc adm groups new ocp-dev-team-a alice bob
```

Add users to an existing group:

```bash
oc adm groups add-users ocp-dev-team-a charlie
```

Remove users:

```bash
oc adm groups remove-users ocp-dev-team-a bob
```

Delete group:

```bash
oc delete group ocp-dev-team-a
```

### Enterprise group source

In production, groups usually come from:

```text
LDAP
Active Directory
OIDC group claims
Keycloak groups
Scheduled LDAP group sync
Manual group objects
```

## 4.4 ServiceAccount

A `ServiceAccount` is an identity for workloads and automation.

Examples:

```text
Pod identity
Deployment identity
Job identity
CronJob identity
OpenShift Pipeline identity
GitOps controller identity
Monitoring agent identity
Backup operator identity
```

View service accounts:

```bash
oc get sa -n app-dev
```

Example:

```bash
oc create sa pipeline-deployer -n payment-dev
```

A service account username format is:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

Example:

```text
system:serviceaccount:payment-dev:pipeline-deployer
```

Service account groups include:

```text
system:serviceaccounts
system:serviceaccounts:<namespace>
system:authenticated
```

## 5. RBAC Scopes: Project-Level vs Cluster-Level

OpenShift RBAC has two major scopes.

---

## 5.1 Local / Project-Level RBAC

Project-level RBAC controls access inside one namespace/project.

Objects:

```text
Role
RoleBinding
```

A `RoleBinding` can bind:

```text
Role
ClusterRole
```

But the access is limited to the namespace where the `RoleBinding` exists.

Example:

```bash
oc adm policy add-role-to-group edit ocp-dev-team-a -n payment-dev
```

Meaning:

```text
Group ocp-dev-team-a gets edit access only in payment-dev.
```

It does not give access to:

```text
payment-prod
openshift-monitoring
kube-system
other namespaces
cluster nodes
cluster operators
```

---

## 5.2 Cluster-Level RBAC

Cluster-level RBAC controls access across the whole cluster.

Objects:

```text
ClusterRole
ClusterRoleBinding
```

Example:

```bash
oc adm policy add-cluster-role-to-group cluster-reader ocp-readonly
```

Meaning:

```text
Group ocp-readonly can read most cluster-level objects and project objects according to the cluster-reader role.
```

Cluster-level permissions are powerful. Use them carefully.

---

## 5.3 Important Difference

### Namespaced access

```bash
oc adm policy add-role-to-group view ocp-dev-team-a -n app-dev
```

Access is only in:

```text
app-dev
```

### Cluster-wide access

```bash
oc adm policy add-cluster-role-to-group view ocp-dev-team-a
```

Access applies cluster-wide where the role rules are effective.

For normal application teams, prefer namespaced `RoleBinding`.

## 6. Default OpenShift Roles

OpenShift includes useful default cluster roles.

| Role | Typical Use |
|---|---|
| `cluster-admin` | Full superuser access |
| `admin` | Project administrator; manage most resources inside a project |
| `edit` | Modify most application resources inside a project |
| `view` | Read-only access to most project resources |
| `basic-user` | Basic user/project information |
| `self-provisioner` | Allows users to create new projects |
| `cluster-reader` | Read most cluster objects |
| `cluster-status` | Read basic cluster status |

---

## 6.1 `cluster-admin`

Highest privilege role.

Example:

```bash
oc adm policy add-cluster-role-to-user cluster-admin rakesh
```

Use only for:

```text
Platform administrators
Break-glass emergency admin
Automation under strict control
```

Avoid giving this to developers.

---

## 6.2 `admin`

Project administrator.

Example:

```bash
oc adm policy add-role-to-group admin ocp-team-leads -n app-dev
```

Typical capabilities:

```text
Create deployments
Create services
Create routes
Manage rolebindings inside project depending on allowed escalation controls
Manage most namespaced resources
```

Use for:

```text
Project owners
Team leads
Namespace administrators
```

---

## 6.3 `edit`

Application developer role.

Example:

```bash
oc adm policy add-role-to-group edit ocp-dev-team-a -n app-dev
```

Typical capabilities:

```text
Create/update/delete deployments
Create/update/delete services
Create/update/delete routes
Manage configmaps/secrets depending on role rules
Scale workloads
Restart applications
```

Usually does not allow managing RBAC roles/bindings.

---

## 6.4 `view`

Read-only role.

Example:

```bash
oc adm policy add-role-to-group view ocp-readonly -n app-prod
```

Typical capabilities:

```text
View pods
View deployments
View services
View routes
View events
View logs if included by policy
```

Use for:

```text
Auditors
Support teams
Developers needing read-only production access
NOC teams
```

---

## 6.5 `self-provisioner`

Allows users to create their own projects.

In enterprise environments, this is often restricted.

Check who has it:

```bash
oc describe clusterrolebinding self-provisioners
```

Common default binding can include:

```text
system:authenticated:oauth
```

To restrict self-provisioning, first verify the current binding:

```bash
oc get clusterrolebinding self-provisioners -o yaml
```

Then remove the default group if it exists:

```bash
oc adm policy remove-cluster-role-from-group self-provisioner system:authenticated:oauth
```

After this, create projects through controlled onboarding, GitOps, ServiceNow, or platform team automation.

## 7. How OpenShift Evaluates Authorization

When a request reaches the API server, OpenShift evaluates:

```text
Identity:
    username
    groups

Action:
    verb
    API group
    resource
    subresource
    namespace/project
    resource name

Bindings:
    rolebindings
    clusterrolebindings

Rules:
    allowed verbs and resources
```

Authorization flow:

```text
1. User authenticates and receives token.
2. User sends API request.
3. API server identifies username and groups.
4. API server finds applicable RoleBindings and ClusterRoleBindings.
5. Bindings point to Roles and ClusterRoles.
6. Rules inside those roles are evaluated.
7. If any rule matches, request is allowed.
8. If no rule matches, request is denied.
```

Important:

```text
RBAC is additive.
There is no normal "deny" rule.
If you need to remove access, remove the binding or reduce the role.
Default result is deny.
```

## 8. Production RBAC Design with Users and Groups

## 8.1 Golden Rule

> Bind roles to groups, not individual users.

Bad design:

```bash
oc adm policy add-role-to-user edit alice -n app-dev
oc adm policy add-role-to-user edit bob -n app-dev
oc adm policy add-role-to-user edit charlie -n app-dev
```

Good design:

```bash
oc adm groups new ocp-app-devs alice bob charlie
oc adm policy add-role-to-group edit ocp-app-devs -n app-dev
```

Why group-based RBAC is better:

```text
Easier onboarding
Easier offboarding
Cleaner audit
Less manual error
Better integration with AD/LDAP
Better separation of duties
```

---

## 8.2 Suggested Enterprise Group Naming

Use clear naming standards.

Example pattern:

```text
ocp-<environment>-<application>-<role>
```

Examples:

```text
ocp-dev-payment-edit
ocp-prod-payment-view
ocp-prod-payment-admin
ocp-platform-admins
ocp-cluster-readers
ocp-security-auditors
ocp-cicd-deployers
```

Alternative pattern:

```text
ocp:<cluster>:<namespace>:<access-level>
```

Examples:

```text
ocp:cluster01:payment-dev:edit
ocp:cluster01:payment-prod:view
ocp:cluster01:platform:admin
```

Choose a naming standard and document it.

---

## 8.3 Recommended Role Mapping

| Team | Group | Role | Scope |
|---|---|---|---|
| Platform admins | `ocp-platform-admins` | `cluster-admin` | Cluster |
| Platform read-only | `ocp-platform-readers` | `cluster-reader` | Cluster |
| App developers dev env | `ocp-payment-devs` | `edit` | `payment-dev` |
| App team lead | `ocp-payment-admins` | `admin` | `payment-dev` |
| Production developers | `ocp-payment-prod-readonly` | `view` | `payment-prod` |
| SRE production support | `ocp-prod-support` | custom role | Production namespaces |
| CI/CD deployer | service account or group | custom deploy role | Target namespace |
| Auditors | `ocp-auditors` | `view` or custom read-only | Selected namespaces |

---

## 8.4 Separation of Duties

Production RBAC should separate:

```text
Application development
Production deployment
Security administration
Cluster administration
Audit/read-only access
CI/CD automation
Break-glass access
```

Example:

```text
Developers:
    edit in dev
    view in prod

Team leads:
    admin in dev/test
    view in prod

SRE:
    custom troubleshoot role in prod

Pipeline:
    patch deployments in prod
    cannot read all secrets unless required

Platform admins:
    cluster-admin

Auditors:
    read-only cluster and namespace access
```

---

## 8.5 Avoid Direct User Bindings

Direct user binding is acceptable only for:

```text
Temporary emergency access
Initial bootstrap admin
Break-glass account
Small lab environment
Exam practice
```

In production, every direct user binding should have:

```text
Ticket number
Expiry date
Owner approval
Audit record
Removal process
```

## 10. YAML Examples

## 10.1 RoleBinding: Give Group `view` Access to One Project

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: view-to-ocp-dev-team-a
  namespace: app-dev
subjects:
  - kind: Group
    name: ocp-dev-team-a
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: view
  apiGroup: rbac.authorization.k8s.io
```

Apply:

```bash
oc apply -f view-to-ocp-dev-team-a.yaml
```

Validate:

```bash
oc auth can-i get pods -n app-dev --as=alice --as-group=ocp-dev-team-a
oc auth can-i delete pods -n app-dev --as=alice --as-group=ocp-dev-team-a
```

Expected:

```text
yes
no
```

## 10.4 Custom Role: Pod Logs Only

Use case:

```text
Support team can view pods and logs but cannot change workloads.
```

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-log-reader
  namespace: app-prod
rules:
  - apiGroups:
      - ""
    resources:
      - pods
      - pods/log
    verbs:
      - get
      - list
      - watch
```

Bind it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-log-reader-to-prod-support
  namespace: app-prod
subjects:
  - kind: Group
    name: ocp-prod-support
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-log-reader
  apiGroup: rbac.authorization.k8s.io
```

Validate:

```bash
oc auth can-i get pods/log -n app-prod --as=support1 --as-group=ocp-prod-support
oc auth can-i delete pods -n app-prod --as=support1 --as-group=ocp-prod-support
```

## 10.5 Custom Role: Restart Deployment Without Full Edit

In Kubernetes/OpenShift, a rollout restart patches the deployment annotation.

Use case:

```text
Operations team can restart deployments but cannot edit everything.
```

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployment-restarter
  namespace: app-prod
rules:
  - apiGroups:
      - apps
    resources:
      - deployments
    verbs:
      - get
      - list
      - watch
      - patch
```

Bind to group:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: deployment-restarter-to-ops
  namespace: app-prod
subjects:
  - kind: Group
    name: ocp-prod-ops
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: deployment-restarter
```

## 12. RBAC and Identity Providers

## 12.1 Why IdP Integration Matters

In enterprise OpenShift, users and groups are usually managed outside the cluster.

Common IdP sources:

```text
Active Directory
LDAP
Keycloak / Red Hat SSO
Azure AD / Entra ID
Okta
GitHub Enterprise
GitLab
```

OpenShift consumes identities and groups, then RBAC uses those users/groups.

---

## 12.2 LDAP / Active Directory Group Sync

LDAP group sync imports external LDAP/AD groups into OpenShift group objects.

Basic flow:

```text
AD/LDAP group:
    CN=OCP-PAYMENT-DEVS,OU=Groups,DC=example,DC=com

OpenShift group:
    ocp-payment-devs

RBAC:
    oc adm policy add-role-to-group edit ocp-payment-devs -n payment-dev
```

Sync command:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml
```

Dry-run is default.

To apply changes:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

Prune removed groups:

```bash
oc adm prune groups --sync-config=ldap-sync.yaml --confirm
```

Production note:

```text
Use dry-run first.
Review group mappings.
Use whitelist/blacklist to avoid importing unnecessary AD groups.
Schedule sync with CronJob or external automation.
Monitor sync failures.
```

---

## 12.3 OIDC Group Claims

With OIDC, group membership can come from token claims.

Example OIDC claims:

```json
{
  "sub": "9b0c4f1e-1111-2222-3333-abcdef",
  "preferred_username": "rakesh",
  "email": "rakesh@example.com",
  "groups": [
    "ocp-payment-devs",
    "ocp-platform-readers"
  ]
}
```

OpenShift OAuth configuration can map the `groups` claim:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
    - name: oidc
      mappingMethod: claim
      type: OpenID
      openID:
        clientID: openshift
        clientSecret:
          name: oidc-client-secret
        issuer: https://keycloak.example.com/realms/ocp
        claims:
          preferredUsername:
            - preferred_username
            - email
          name:
            - name
          email:
            - email
          groups:
            - groups
```

Important:

```text
Group claims are normally evaluated during login.
If group membership changes in IdP, the user may need to log in again or refresh the session/token.
```

## 12.4 Mapping Method Impact

OpenShift identity provider `mappingMethod` affects how external identities map to OpenShift users.

Common values:

```text
claim
lookup
generate
add
```

Senior admin note:

```text
Use mappingMethod carefully.
Changing mapping later can create duplicate users or break RBAC expectations.
In regulated environments, use stable unique IDs from IdP.
```

## 13. RBAC and OpenShift Security Context Constraints

OpenShift has an additional security layer called **Security Context Constraints** or **SCC**.

RBAC can grant the ability to use an SCC.

Example:

```bash
oc adm policy add-scc-to-user anyuid -z myserviceaccount -n app-dev
```

Equivalent service account identity:

```text
system:serviceaccount:app-dev:myserviceaccount
```

Important:

```text
SCC access can be highly privileged.
Do not give anyuid, privileged, hostnetwork, hostmount-anyuid, or hostaccess casually.
```

Check SCCs:

```bash
oc get scc
oc describe scc restricted-v2
oc describe scc anyuid
oc describe scc privileged
```

Check if a service account can use an SCC:

```bash
oc auth can-i use scc/anyuid \
  --as=system:serviceaccount:app-dev:myserviceaccount
```

Senior note:

```text
A user with permission to create pods and use privileged SCC can effectively gain powerful node/container access.
Always evaluate RBAC and SCC together.
```

## 14.2 Step-by-Step Troubleshooting Flow

### Step 1: Confirm current user

```bash
oc whoami
oc whoami --show-groups
```

### Step 2: Confirm namespace/project

```bash
oc project

```

### Step 3: Test permission


```bash

```

### Step 4: Test as affected user

```bash
oc auth can-i create deployments -n app-dev --as=alice
```

### Step 5: Test as user plus group

```bash
oc auth can-i create deployments -n app-dev \
  --as=alice \
  --as-group=ocp-dev-team-a
```

### Step 6: Inspect rolebindings

```bash
oc get rolebindings -n app-dev
```

### Step 7: Inspect clusterrolebindings


### Step 10: Check IdP/group sync

```bash

```

## 14.3 Most Common Root Causes

| Symptom | Likely Cause | Fix |
|---|---|---|
| User can log in but cannot see project | No `RoleBinding` in that project | Bind `view`, `edit`, or custom role |
| User has access in dev but not prod | Binding exists only in dev | Add controlled prod binding |
| User is in AD group but not OpenShift group | LDAP group sync not run or failed | Run sync, check config |
| User changed group in Keycloak but OpenShift not updated | Token/session not refreshed | Re-login or refresh token |
| RoleBinding exists but access denied | Wrong namespace | Create binding in correct namespace |
| Subject kind wrong | Used `User` instead of `Group` or typo | Fix subject |
| Resource missing subresource | Need `pods/log`, `pods/exec`, `deployments/scale` | Add subresource carefully |
| API group wrong | Used `""` for apps resources | Use correct API group |
| User can do too much | Bound broad role or cluster role | Replace with least-privilege custom role |
| Cannot create project | `self-provisioner` removed | Use approved project request process |

## 15. Security Risks and Hardening

## 15.1 Avoid Wildcards

Dangerous:

```yaml
apiGroups:
  - "*"
resources:
  - "*"
verbs:
  - "*"
```

Why dangerous:

```text
It grants current and future resources.
New CRDs may automatically become accessible.
It is difficult to audit.
It can cause privilege escalation.
```

Use exact resources and verbs instead.

---

## 15.2 Be Careful with `pods/exec`

Access to `pods/exec` can allow shell access inside containers.

Example:

```yaml
resources:
  - pods/exec
verbs:
  - create
```

Risk:

```text
User can execute commands inside application containers.
May access app secrets, mounted tokens, data, or internal network.
```

Only grant to trusted support/SRE groups.

---

## 15.3 Be Careful with `pods/log`

Logs may contain:

```text
Passwords
Tokens
Customer data
Debug dumps
Connection strings
PII
```

Read-only does not always mean low-risk.

---

## 15.4 Be Careful with Secrets

Access to secrets is sensitive.

```yaml
resources:
  - secrets
verbs:
  - get
  - list
```

Risks:

```text
User can read credentials.
User can read service account tokens if present.
User can access database passwords.
User can access TLS private keys.
```

Avoid giving secret read access unless required.

---

## 15.5 Be Careful with `impersonate`

`impersonate` allows acting as another identity.

Example risk:

```text
User can impersonate cluster-admin or privileged service account.
```

Treat it as highly privileged.

---

## 15.6 Be Careful with `bind` and `escalate`

`bind` can allow a user to bind roles to themselves or others.

`escalate` can allow creating/updating roles with permissions the user does not currently hold.

These are advanced administrative permissions and should be tightly controlled.

---

## 15.7 Avoid `system:masters`

The `system:masters` group is extremely powerful.

In Kubernetes, membership in `system:masters` bypasses normal RBAC checks. Do not use it for normal administration.

Preferred approach:

```text
Use explicit cluster-admin ClusterRoleBinding for named break-glass/admin users or groups.
Audit and review regularly.
```

---

## 15.8 Restrict Self-Provisioning

In enterprise clusters, uncontrolled project creation can create:

```text
Quota problems
Naming problems
Network policy gaps
Security review bypass
Cost tracking issues
Compliance gaps
```

Recommended:

```text
Remove self-provisioner from broad authenticated users.
Create namespaces through approved workflow.
Apply ResourceQuota, LimitRange, NetworkPolicy, RBAC, labels, and annotations during onboarding.
```

---

## 15.9 Audit RBAC Regularly

Useful commands:

```bash
oc get clusterrolebindings -o wide
oc get rolebindings -A -o wide
oc adm policy who-can delete secrets -A
oc adm policy who-can create pods/exec -A
oc adm policy who-can use scc/privileged
```

Export RBAC:

```bash
oc get clusterrolebindings -o yaml > clusterrolebindings.yaml
oc get rolebindings -A -o yaml > rolebindings-all-namespaces.yaml
oc get clusterroles -o yaml > clusterroles.yaml
oc get roles -A -o yaml > roles-all-namespaces.yaml
```

Review for:

```text
cluster-admin
wildcards
secrets access
pods/exec
pods/portforward
impersonate
bind
escalate
privileged SCC use
unexpected direct user bindings
old employees
stale groups
```

## 17. Interview Questions and Senior-Level Answers

## Q1. What is RBAC in OpenShift?

RBAC is the authorization mechanism that controls what authenticated users, groups, and service accounts can do in the cluster. It uses roles or cluster roles to define permissions and bindings to attach those permissions to subjects.

A senior answer should mention:

```text
Authentication is separate from authorization.
RBAC is additive.
Default is deny.
RoleBinding is namespace scoped.
ClusterRoleBinding is cluster scoped.
Groups are preferred over direct users.
```

---

## Q2. Difference between Role and ClusterRole?

`Role` is namespaced. It defines permissions inside one project.

`ClusterRole` is cluster-scoped. It can define cluster-level permissions or reusable namespaced permissions.

A `ClusterRole` can be bound inside one namespace using a `RoleBinding`.

Example:

```bash
oc adm policy add-role-to-group view ocp-devs -n app-dev
```

This uses the default `view` ClusterRole but grants it only in `app-dev`.

---

## Q3. Difference between RoleBinding and ClusterRoleBinding?

`RoleBinding` gives access only in one namespace.

`ClusterRoleBinding` gives access cluster-wide.

Example namespaced access:

```bash
oc adm policy add-role-to-group edit ocp-devs -n app-dev
```

Example cluster-wide access:

```bash
oc adm policy add-cluster-role-to-group cluster-reader ocp-auditors
```

---

## Q4. Why should roles be assigned to groups instead of users?

Because group-based RBAC is easier to manage and audit.

Benefits:

```text
Cleaner onboarding/offboarding
Centralized IdP integration
Reduced manual mistakes
Better compliance
Less RBAC sprawl
```

---

## Q5. User can login but cannot access project. Why?

Authentication succeeded but authorization is missing.

Troubleshooting:

```bash
oc whoami
oc whoami --show-groups
oc auth can-i get pods -n <project>
oc get rolebindings -n <project>
oc describe group <group>
```

Fix:

```bash
oc adm policy add-role-to-group view <group> -n <project>
```

---

## Q6. What is the risk of `cluster-admin`?

`cluster-admin` allows any action on any resource in the cluster. It can modify cluster operators, nodes, RBAC, secrets, workloads, SCCs, and security-sensitive resources.

Use it only for platform admins and break-glass access.

---

## Q7. How do you audit who can delete secrets?

```bash
oc adm policy who-can delete secrets -n app-prod
```

For all namespaces, review:

```bash
oc get rolebindings -A -o yaml
oc get clusterrolebindings -o yaml
```

## Q8. What is RBAC privilege escalation?

Privilege escalation happens when a user can grant themselves or others more permissions than intended.

Dangerous permissions include:

```text
bind
escalate
impersonate
create pods with privileged SCC
read secrets
create rolebindings
create clusterrolebindings
wildcard permissions
```

---

## Q9. Can RBAC deny a user explicitly?

Standard Kubernetes/OpenShift RBAC is additive and allow-based. There is no normal explicit deny rule.

To remove access:

```text
Remove RoleBinding/ClusterRoleBinding.
Remove user from group.
Reduce role permissions.
Use admission policies or external controls for additional restrictions.
```

## Q10. How do you give a user read-only access to one namespace?

```bash
oc adm policy add-role-to-user view alice -n app-prod
```

Better with group:

```bash
oc adm groups new ocp-app-prod-view alice
oc adm policy add-role-to-group view ocp-app-prod-view -n app-prod
```

## 20. Quick Revision Notes

```text
RBAC = who can do what on which resource and scope.

Authentication = identity verification.
Authorization = permission decision.

OpenShift user = authenticated human identity mapped from IdP.
OpenShift identity = external provider identity mapped to user.
OpenShift group = collection of users.
ServiceAccount = workload/automation identity.

Role = namespaced permissions.
ClusterRole = cluster-wide/reusable permissions.
RoleBinding = namespace-level binding.
ClusterRoleBinding = cluster-wide binding.

RoleBinding can bind a ClusterRole in one namespace.
ClusterRoleBinding can bind only ClusterRole cluster-wide.

RBAC is additive.
No normal explicit deny.
Default is deny.

Prefer groups over users.
Use least privilege.
Avoid wildcards.
Avoid direct cluster-admin.
Audit regularly.

Use:
oc auth can-i
oc adm policy who-can
oc get rolebindings -A
oc get clusterrolebindings
oc whoami --show-groups
```

## Final Senior Admin Summary

For a 10+ year OpenShift administrator, RBAC with users and groups is not just command syntax. It is an enterprise access-control design discipline.

A mature RBAC implementation should:

```text
Integrate with enterprise IdP.
Use groups, not individual users.
Separate dev/test/prod access.
Use least-privilege custom roles where default roles are too broad.
Control cluster-admin tightly.
Audit dangerous permissions.
Manage RBAC declaratively through GitOps.
Validate every access request with oc auth can-i and oc adm policy who-can.
```

The best production model is:

```text
Identity Provider manages users and groups.
OpenShift syncs or consumes those groups.
RBAC binds groups to roles.
GitOps manages RBAC objects.
Auditing verifies actual effective access.
```
