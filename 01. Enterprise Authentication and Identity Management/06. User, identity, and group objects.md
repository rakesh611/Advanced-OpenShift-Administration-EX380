# User, Identity, and Group Objects in OpenShift

**Area:** Enterprise Authentication and Identity Management  
**Level:** Advanced OpenShift Administration / 10+ years experience  
**API group:** `user.openshift.io/v1`  
**Primary objects:** `User`, `Identity`, `UserIdentityMapping`, `Group`  

---

## 1. Executive Summary

In OpenShift, authentication and authorization are intentionally separated.

Authentication answers:

> Who is making this API request?

Authorization answers:

> Is this authenticated subject allowed to perform this action on this resource?

OpenShift identifies a human or system actor through a combination of these objects:

| Object | Purpose |
|---|---|
| `User` | Represents an actor that can be granted permissions directly or through groups. |
| `Identity` | Records a successful authentication from an identity provider such as LDAP, HTPasswd, OIDC, GitHub, GitLab, or request-header auth. |
| `UserIdentityMapping` | Links one `Identity` to one `User`. It is very important when using the `lookup` mapping method or when manually controlling identity-to-user mapping. |
| `Group` | Represents a set of users. RBAC should normally be granted to groups instead of individual users in enterprise environments. |

A senior OpenShift administrator must understand that OpenShift does **not** usually store user passwords. Password validation normally happens in the configured external identity provider. OpenShift stores the resulting identity relationship and uses RBAC, SCC, project membership, and admission decisions based on the authenticated username and group list.

## 2. Big Picture: Authentication Flow

Typical login flow:

```text
User runs oc login or opens Web Console
        |
        v
OpenShift OAuth Server
        |
        v
Configured Identity Provider
LDAP / HTPasswd / OIDC / GitHub / GitLab / Request Header / Keystone / Basic Auth
        |
        v
Identity is verified
        |
        v
OpenShift maps Identity -> User
        |
        v
OAuth token is issued
        |
        v
API request reaches Kubernetes/OpenShift API
        |
        v
RBAC + SCC + admission evaluate username and groups
```

Important point:

```text
Authentication creates identity.
Authorization grants permissions.
```

A user can successfully log in and still receive `Forbidden` errors if RBAC does not allow the requested action.

## 3. Authentication vs Authorization

### 3.1 Authentication

Authentication validates the request identity. OpenShift supports multiple authentication methods, including:

- OAuth access tokens
- X.509 client certificates
- Service account tokens
- External identity providers through OpenShift OAuth configuration

For regular users, the most common path is:

```bash
oc login https://api.<cluster>.<domain>:6443
```

The login flow goes through the OpenShift OAuth server and configured identity provider.

### 3.2 Authorization

Authorization uses RBAC objects:

- `Role`
- `ClusterRole`
- `RoleBinding`
- `ClusterRoleBinding`

Authorization evaluates:

- Username
- Groups
- Requested verb: `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`, etc.
- Resource: `pods`, `deployments`, `secrets`, `routes`, `nodes`, etc.
- Namespace/project scope
- Cluster scope

Example:

```bash
oc auth can-i get pods -n finance
oc auth can-i create deployments -n finance --as=rakesh
oc auth can-i delete nodes --as=rakesh
```

## 4. Core OpenShift Objects

## 4.1 `User` Object

### Definition

A `User` object represents an actor that can make requests to the OpenShift API. In most enterprise cases, it represents a developer, application administrator, platform administrator, auditor, SRE, or automation operator.

API:

```yaml
apiVersion: user.openshift.io/v1
kind: User
```

### Key Characteristics

- Cluster-scoped object.
- Represents the OpenShift-side user record.
- Does not normally contain the password.
- Can be created automatically at first successful login.
- Can be created manually with `oc create user`.
- Can be bound directly to roles, but group-based RBAC is preferred.
- Can have one or more identities associated with it.

### Example User Object

```yaml
apiVersion: user.openshift.io/v1
kind: User
metadata:
  name: rakesh
fullName: Rakesh Kumar Jha
identities:
- ldapidp:rakesh
```

### View Users

```bash
oc get users
oc get user rakesh -o yaml
oc describe user rakesh
```

### Create a User Manually

```bash
oc create user rakesh --full-name="Rakesh Kumar Jha"
```

### Delete a User

```bash
oc delete user rakesh
```

### Senior Admin Note

Deleting an OpenShift `User` object does **not** delete the external LDAP, OIDC, Keycloak, GitHub, or HTPasswd account. It only removes the OpenShift API object. If the identity provider still allows the account and the mapping method allows automatic provisioning, the user may be recreated on the next login.

---

## 4.2 Types of Users in OpenShift

OpenShift users generally fall into three categories.

### 4.2.1 Regular Users

Examples:

```text
alice
bob
rakesh
platform-admin1
```

These are human users, usually authenticated by LDAP, HTPasswd, OIDC, GitHub, GitLab, or another identity provider.

### 4.2.2 System Users

Examples:

```text
system:admin
system:node:worker01.example.com
system:openshift-registry
system:anonymous
```

These are used internally by OpenShift components, nodes, controllers, registry, routers, and infrastructure.

### 4.2.3 Service Accounts

Examples:

```text
system:serviceaccount:default:builder
system:serviceaccount:default:deployer
system:serviceaccount:finance:jenkins
system:serviceaccount:openshift-monitoring:prometheus-k8s
```

Service accounts are Kubernetes/OpenShift identities used by workloads, pods, operators, pipelines, and automation.

View service accounts:

```bash
oc get sa -n finance
oc get sa jenkins -n finance -o yaml
```

A service account is represented by a `ServiceAccount` object, not by a `User` object, but it appears as a user-like subject in RBAC.

Example RBAC subject:

```yaml
subjects:
- kind: ServiceAccount
  name: jenkins
  namespace: finance
```

## 4.3 `Identity` Object

### Definition

An `Identity` object records a successful authentication from an identity provider.

API:

```yaml
apiVersion: user.openshift.io/v1
kind: Identity
```

### Key Characteristics

- Cluster-scoped object.
- Represents the source identity from the identity provider.
- Contains provider name and provider-specific username or unique ID.
- Maps to one `User` object.
- Multiple identities can reference a single user.
- Common name format:

```text
<identity-provider-name>:<provider-user-name-or-id>
```

Example:

```text
ldapidp:rakesh
keycloak:8f7a6c11-1234-4a2b-9f01-111111111111
htpasswd:rakesh
```

### Example Identity Object

```yaml
apiVersion: user.openshift.io/v1
kind: Identity
metadata:
  name: ldapidp:rakesh
providerName: ldapidp
providerUserName: rakesh
user:
  name: rakesh
  uid: 7b0b6c5e-1111-2222-3333-444444444444
extra:
  email:
  - rakesh@example.com
```

### View Identities

```bash
oc get identities
oc get identity ldapidp:rakesh -o yaml
oc describe identity ldapidp:rakesh
```

### Create Identity Manually

```bash
oc create identity ldapidp:rakesh
```

### Delete Identity

```bash
oc delete identity ldapidp:rakesh
```

### Senior Admin Note

If you delete only the `Identity` object but leave the `User` object, a future login might recreate the identity depending on `mappingMethod`. If you delete only the `User` but leave the `Identity`, the identity mapping may become inconsistent. For clean removal, inspect and remove all related objects carefully.

## 4.4 `UserIdentityMapping` Object

### Definition

`UserIdentityMapping` maps one `Identity` to one `User`.

API:

```yaml
apiVersion: user.openshift.io/v1
kind: UserIdentityMapping
```

### Why It Matters

This object is especially important when using:

- `mappingMethod: lookup`
- Manual identity provisioning
- Identity migration
- Multiple identity providers
- Controlled user onboarding
- Avoiding accidental user creation

### Example

```yaml
apiVersion: user.openshift.io/v1
kind: UserIdentityMapping
metadata:
  name: ldapidp:rakesh
identity:
  name: ldapidp:rakesh
  kind: Identity
  apiVersion: user.openshift.io/v1
user:
  name: rakesh
  kind: User
  apiVersion: user.openshift.io/v1
```

### Create Mapping Manually

```bash
oc create useridentitymapping ldapidp:rakesh rakesh
```

### View Mapping

```bash
oc get useridentitymapping
oc get useridentitymapping ldapidp:rakesh -o yaml
```

### Delete Mapping

```bash
oc delete useridentitymapping ldapidp:rakesh
```

### Manual Provisioning Flow for `mappingMethod: lookup`

When using `lookup`, OpenShift does not automatically create the user and identity during login. You must manually create them.

```bash
oc create user rakesh --full-name="Rakesh Kumar Jha"
oc create identity ldapidp:rakesh
oc create useridentitymapping ldapidp:rakesh rakesh
```

Then the user can log in, assuming the identity provider accepts the credentials.

## 4.5 `Group` Object

### Definition

A `Group` object represents a set of OpenShift users.

API:

```yaml
apiVersion: user.openshift.io/v1
kind: Group
```

### Key Characteristics

- Cluster-scoped object.
- Contains a list of users.
- Preferred subject for enterprise RBAC.
- Can be managed manually.
- Can be synchronized from LDAP.
- Can be populated from OIDC group claims when configured.

### Example Group Object

```yaml
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  name: devops-admins
users:
- rakesh
- alice
- bob
```

### View Groups

```bash
oc get groups
oc get group devops-admins -o yaml
oc describe group devops-admins
```

### Create Group

```bash
oc adm groups new devops-admins rakesh alice bob
```

### Add Users to Group

```bash
oc adm groups add-users devops-admins amit priya
```

### Remove Users from Group

```bash
oc adm groups remove-users devops-admins bob
```

### Delete Group

```bash
oc delete group devops-admins
```

### Senior Admin Note

Do not confuse OpenShift `Group` objects with external LDAP or Keycloak groups. OpenShift RBAC works against the group names visible to OpenShift. Those groups may be manually created, synced from LDAP, or supplied through an identity provider claim.

## 6. Identity Provider Mapping Methods

Identity provider configuration includes `mappingMethod`. This controls how an authenticated identity is mapped to an OpenShift `User`.

Example OAuth CR:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: ldapidp
    mappingMethod: claim
    type: LDAP
    ldap:
      # LDAP configuration here
```

### 6.1 `mappingMethod: claim`

Default method.

Behavior:

- Provisions a user using the identity provider's preferred username.
- Fails if that username is already mapped to another identity.
- Good for simple environments with one identity provider.

Use case:

```text
Single HTPasswd provider
Single LDAP provider
Small cluster lab
Straightforward identity mapping
```

Risk:

```text
If you add another identity provider later with overlapping usernames, login conflicts can occur.
```

### 6.2 `mappingMethod: add`

Behavior:

- Provisions a user using the preferred username.
- If the user already exists, maps the new identity to that existing user.
- Useful when multiple identity providers identify the same users.

Use case:

```text
Migrating from HTPasswd to LDAP
Migrating from LDAP to Keycloak/OIDC
Running LDAP and OIDC together temporarily
Same username exists across two providers and should map to one OpenShift user
```

Example:

```text
htpasswd:rakesh  ---> User rakesh
ldapidp:rakesh   ---> User rakesh
```

### 6.3 `mappingMethod: lookup`

Behavior:

- Does not automatically provision users or identities.
- Looks up existing `Identity`, `UserIdentityMapping`, and `User` objects.
- Requires manual provisioning.
- Gives maximum administrative control.

Use case:

```text
Highly controlled enterprise onboarding
Regulated environments
Production clusters with strict user lifecycle
DRDO/government-style restricted access
No automatic user creation allowed
```

Manual setup:

```bash
oc create user rakesh --full-name="Rakesh Kumar Jha"
oc create identity ldapidp:rakesh
oc create useridentitymapping ldapidp:rakesh rakesh
```

## 7. Built-in Virtual Groups

OpenShift automatically assigns some virtual groups during authentication.

| Virtual Group | Meaning |
|---|---|
| `system:authenticated` | All authenticated users. |
| `system:authenticated:oauth` | Users authenticated using an OAuth access token. |
| `system:unauthenticated` | Requests without valid authentication. |

Example check:

```bash
oc auth can-i get projects --as=system:anonymous --as-group=system:unauthenticated
oc auth can-i get pods --as=rakesh --as-group=system:authenticated
```

Senior admin warning:

Never casually bind powerful roles to broad virtual groups such as `system:authenticated`. That can accidentally grant cluster-wide capabilities to all logged-in users.

Dangerous example:

```bash
oc adm policy add-cluster-role-to-group cluster-admin system:authenticated
```

Do **not** do this.

## 8. RBAC with Users and Groups

## 8.1 Bind Role to User in a Project

```bash
oc adm policy add-role-to-user view rakesh -n finance
oc adm policy add-role-to-user edit rakesh -n finance
oc adm policy add-role-to-user admin rakesh -n finance
```

## 8.2 Bind Role to Group in a Project

```bash
oc adm policy add-role-to-group view finance-viewers -n finance
oc adm policy add-role-to-group edit finance-developers -n finance
oc adm policy add-role-to-group admin finance-admins -n finance
```

## 8.3 Bind Cluster Role to User

```bash
oc adm policy add-cluster-role-to-user cluster-reader rakesh
oc adm policy add-cluster-role-to-user cluster-admin rakesh
```

## 8.4 Bind Cluster Role to Group

```bash
oc adm policy add-cluster-role-to-group cluster-reader auditors
oc adm policy add-cluster-role-to-group self-provisioner project-creators
```

## 8.5 Remove Role from User or Group

```bash
oc adm policy remove-role-from-user edit rakesh -n finance
oc adm policy remove-role-from-group edit finance-developers -n finance

oc adm policy remove-cluster-role-from-user cluster-reader rakesh
oc adm policy remove-cluster-role-from-group cluster-reader auditors
```

## 8.6 Inspect Who Can Perform an Action

```bash
oc adm policy who-can get pods -n finance
oc adm policy who-can create deployments -n finance
oc adm policy who-can delete nodes
```

## 8.7 Test Access as a User


## 9. Enterprise Design Pattern

For real enterprise OpenShift clusters, avoid assigning permissions directly to users unless it is an emergency or a temporary break-glass scenario.

Preferred model:

```text
External directory groups
        |
        v
OpenShift Group objects
        |
        v
RoleBinding / ClusterRoleBinding
        |
        v
Projects / cluster resources
```

Example enterprise RBAC model:

| External Group | OpenShift Group | Binding | Scope |
|---|---|---|---|
| `CN=OCP-Platform-Admins` | `ocp-platform-admins` | `cluster-admin` | Cluster |
| `CN=OCP-Cluster-Readers` | `ocp-cluster-readers` | `cluster-reader` | Cluster |
| `CN=Finance-App-Admins` | `finance-admins` | `admin` | `finance` project |
| `CN=Finance-Developers` | `finance-developers` | `edit` | `finance` project |
| `CN=Finance-Auditors` | `finance-viewers` | `view` | `finance` project |

Commands:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
oc adm policy add-cluster-role-to-group cluster-reader ocp-cluster-readers

oc adm policy add-role-to-group admin finance-admins -n finance
oc adm policy add-role-to-group edit finance-developers -n finance
oc adm policy add-role-to-group view finance-viewers -n finance
```

## 10. LDAP Group Synchronization

In LDAP-backed enterprises, user authentication and group synchronization are related but separate topics.

LDAP authentication:

```text
Can this username/password authenticate?
```

LDAP group synchronization:

```text
Which OpenShift Group objects should be created or updated based on LDAP groups?
```

Typical command:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

Dry run:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml
```

View synced groups:

```bash
oc get groups
oc get group finance-developers -o yaml
```

Senior admin practice:

- Always dry-run first.
- Use whitelist/blacklist for controlled sync.
- Use a dedicated bind account.
- Protect LDAP bind secrets.
- Avoid syncing every corporate group into OpenShift.
- Define naming standards for OpenShift groups.
- Automate sync using CronJob or external automation, depending on organizational policy.

## 11. OIDC / Keycloak Group Claims

With OIDC providers such as Keycloak or Red Hat SSO, OpenShift can use configured claims for:

- Preferred username
- Display name
- Email
- Identity value
- Groups

Example conceptual OIDC claims:

```yaml
claims:
  preferredUsername:
  - preferred_username
  - email
  name:
  - name
  email:
  - email
  groups:
  - groups
```

Important design decision:

```text
The group value emitted by the OIDC provider must match the group name used in OpenShift RBAC.
```

Example:

```text
OIDC token group claim: finance-developers
OpenShift RoleBinding subject: finance-developers
```

RBAC example:

```bash
oc adm policy add-role-to-group edit finance-developers -n finance
```

If Keycloak emits `/ocp/finance-developers` but OpenShift RBAC expects `finance-developers`, authorization will fail unless you align the claim format or bind the exact emitted group name.

## 12. User and Identity Lifecycle Operations

## 12.1 New User First Login with `claim`

```text
1. User logs in through OAuth.
2. Identity provider validates credentials.
3. OpenShift creates Identity.
4. OpenShift creates User.
5. OpenShift links Identity to User.
6. OpenShift issues token.
7. RBAC determines access.
```

Validate:

```bash
oc get user rakesh -o yaml
oc get identity ldapidp:rakesh -o yaml
```

## 12.2 New User with `lookup`

```text
1. Admin creates User.
2. Admin creates Identity.
3. Admin creates UserIdentityMapping.
4. User logs in.
5. OpenShift finds existing mapping.
6. Token is issued.
```

Commands:

```bash
oc create user rakesh --full-name="Rakesh Kumar Jha"
oc create identity ldapidp:rakesh
oc create useridentitymapping ldapidp:rakesh rakesh
```

## 12.3 Migrating User from HTPasswd to LDAP

Old identity:

```text
htpasswd:rakesh -> User rakesh
```

New identity:

```text
ldapidp:rakesh -> User rakesh
```

Recommended method during migration:

```yaml
mappingMethod: add
```

Validation:

```bash
oc get user rakesh -o yaml
```

Expected:

```yaml
identities:
- htpasswd:rakesh
- ldapidp:rakesh
```

After migration, remove old identity if required:

```bash
oc delete identity htpasswd:rakesh
```

Be careful: do this only after confirming the new login works and RBAC remains correct.

## 14. Troubleshooting Scenarios

## 14.1 User Gets `401 Unauthorized`

Meaning:

```text
Authentication failed.
```

Possible causes:

- Wrong password.
- Identity provider unreachable.
- LDAP bind failure.
- OIDC client secret wrong.
- OAuth route problem.
- CA certificate problem.
- Token expired or invalid.
- User not manually provisioned when `mappingMethod: lookup` is used.

Check:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift
oc get oauth cluster -o yaml
```

For OIDC:

```bash
oc get secret -n openshift-config
oc get configmap -n openshift-config
```

For LDAP:

```bash
oc get secret -n openshift-config
oc get oauth cluster -o yaml
```

---

## 14.2 User Gets `403 Forbidden`

Meaning:

```text
Authentication succeeded, but authorization failed.
```

Example error:

```text
Error from server (Forbidden): pods is forbidden: User "rakesh" cannot list resource "pods" in API group "" in the namespace "finance"
```

Check access:

```bash
oc auth can-i list pods -n finance --as=rakesh
oc adm policy who-can list pods -n finance
oc get rolebinding -n finance
oc get clusterrolebinding | grep rakesh
oc get groups | grep finance
```

Fix with group-based RBAC:

```bash
oc adm groups add-users finance-developers rakesh
oc adm policy add-role-to-group edit finance-developers -n finance
```

---

## 14.3 User Can Login but Cannot See Any Project

Possible causes:

- No `view`, `edit`, or `admin` role in any project.
- Removed from all relevant groups.
- `self-provisioner` removed, so user cannot create projects.
- Console perspective shows limited resources.

Check:

```bash
oc auth can-i list projects --as=rakesh
oc get rolebindings -A | grep rakesh
oc get clusterrolebindings | grep rakesh
oc get groups -o yaml | grep -B5 -A5 rakesh
```

Grant project access:

```bash
oc adm policy add-role-to-user view rakesh -n finance
```

Preferred:

```bash
oc adm groups add-users finance-viewers rakesh
oc adm policy add-role-to-group view finance-viewers -n finance
```

---

## 14.4 User Exists but Login Fails After Changing Mapping Method

Scenario:

```text
OAuth identity provider was changed from claim to lookup.
```

Impact:

```text
Automatic user creation stops. Existing users must have valid User, Identity, and UserIdentityMapping objects.
```

Check:

```bash
oc get user rakesh -o yaml
oc get identity ldapidp:rakesh -o yaml
oc get useridentitymapping ldapidp:rakesh -o yaml
```

Fix:

```bash
oc create identity ldapidp:rakesh
oc create useridentitymapping ldapidp:rakesh rakesh
```

---

## 14.5 Duplicate Username Conflict

Scenario:

```text
Two identity providers return the same preferred username.
```

Example:

```text
htpasswd:rakesh
ldapidp:rakesh
```

With `mappingMethod: claim`, login may fail if the username is already mapped to another identity.

Options:

1. Use `mappingMethod: add` during migration.
2. Manually map identities.
3. Rename the preferred username claim.
4. Clean stale identities carefully.

Check:

```bash
oc get user rakesh -o yaml
oc get identities | grep rakesh
```

---

## 14.6 Group Membership Looks Correct in LDAP but RBAC Fails

Possible causes:

- LDAP group sync has not run.
- Group name differs between LDAP and OpenShift.
- User value in OpenShift group does not match OpenShift username.
- OIDC group claim emits different format.
- RoleBinding references wrong group name.
- Binding exists in wrong namespace.

Check:

```bash
oc get group finance-developers -o yaml
oc get rolebinding -n finance -o yaml | grep -A10 finance-developers
oc auth can-i create deployments -n finance --as=rakesh --as-group=finance-developers
```

Fix:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
oc adm policy add-role-to-group edit finance-developers -n finance
```

## 15. User Removal / Offboarding Procedure

In enterprise environments, offboarding must be coordinated with the external identity provider.

Recommended offboarding checklist:

```text
1. Disable or remove the user in external IdP.
2. Remove user from external groups.
3. Sync OpenShift groups if LDAP sync is used.
4. Remove direct RoleBindings and ClusterRoleBindings.
5. Remove user from manually managed OpenShift groups.
6. Delete OpenShift Identity if required.
7. Delete OpenShift User if required.
8. Revoke OAuth tokens if needed.
9. Validate with oc auth can-i.
10. Record audit evidence.
```

Find direct bindings:

```bash
oc get rolebinding -A -o yaml | grep -B10 -A10 "name: rakesh"
oc get clusterrolebinding -o yaml | grep -B10 -A10 "name: rakesh"
```

Remove direct bindings manually if required:

```bash
oc adm policy remove-role-from-user edit rakesh -n finance
oc adm policy remove-cluster-role-from-user cluster-reader rakesh
```

Remove from groups:

```bash
oc adm groups remove-users finance-developers rakesh
```

Delete identity and user:

```bash
oc delete identity ldapidp:rakesh
oc delete user rakesh
```

Important:

```text
If the external IdP still permits authentication and mapping allows auto-provisioning, the user can come back on next login.
```

## 16. Security Best Practices

### 16.1 Prefer Group-Based RBAC

Bad long-term design:

```bash
oc adm policy add-role-to-user edit rakesh -n app1
oc adm policy add-role-to-user edit rakesh -n app2
oc adm policy add-role-to-user edit rakesh -n app3
```

Better design:

```bash
oc adm groups add-users app-developers rakesh
oc adm policy add-role-to-group edit app-developers -n app1
oc adm policy add-role-to-group edit app-developers -n app2
oc adm policy add-role-to-group edit app-developers -n app3
```

### 16.2 Use Least Privilege

Avoid unnecessary `cluster-admin`.

Use:

```bash
cluster-reader
view
edit
admin
custom ClusterRole
custom Role
```

### 16.3 Protect `cluster-admin`

Grant `cluster-admin` only to a small controlled group.

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
```

Audit:

```bash
oc get clusterrolebinding -o wide | grep cluster-admin
```

### 16.4 Avoid Direct User Bindings

Direct user bindings are hard to audit and maintain. Use direct bindings only for temporary troubleshooting or emergency access.

### 16.5 Remove `kubeadmin` After IdP and Admin User Are Ready

After configuring an identity provider and assigning a real admin user or group, remove `kubeadmin` to improve security.

```bash
oc delete secret kubeadmin -n kube-system
```

Warning:

```text
Do not delete kubeadmin before another user has cluster-admin access.
```

### 16.6 Validate Before and After Changes

Before RBAC change:

```bash
oc auth can-i get pods -n finance --as=rakesh
```

After RBAC change:

```bash
oc auth can-i get pods -n finance --as=rakesh
```

## 18. Advanced Interview-Style Explanation

### Question

Explain `User`, `Identity`, and `Group` objects in OpenShift.

### Senior-Level Answer

In OpenShift, a `User` is the OpenShift-side representation of an actor that can access the API. It does not usually store the password. The password or credential validation happens in the configured identity provider, such as LDAP, HTPasswd, OIDC, GitHub, or Keycloak.

When a user logs in successfully, OpenShift creates or uses an `Identity` object. The identity records the authentication source, for example `ldapidp:rakesh`. That identity is mapped to a `User` object. The mapping can be automatic or manual depending on the identity provider's `mappingMethod`.

A `UserIdentityMapping` object links a specific identity to a specific user. This is especially important with `mappingMethod: lookup`, because OpenShift will not automatically create users or identities. The administrator must pre-create the `User`, `Identity`, and `UserIdentityMapping`.

A `Group` is a set of OpenShift users. In enterprise administration, groups are the preferred RBAC subject. Instead of granting roles directly to individual users, we synchronize groups from LDAP or map groups from OIDC claims, then bind those groups to roles or cluster roles. This gives cleaner lifecycle management, better auditability, and easier offboarding.

Authentication decides who the user is. Authorization decides what that user or group can do. A successful login only proves identity. Permissions are controlled by `RoleBinding` and `ClusterRoleBinding` objects.

## 19. Common Mistakes

| Mistake | Impact | Correct Approach |
|---|---|---|
| Binding roles directly to many users | Hard to audit and offboard | Bind roles to groups |
| Deleting only `User` during offboarding | User may reappear on login | Disable in IdP and clean mappings |
| Confusing LDAP group with OpenShift group | RBAC fails | Ensure OpenShift `Group` exists and names match |
| Using `claim` during multi-IdP migration | Username conflicts | Use `add` or manual mapping |
| Using `lookup` without creating mappings | Login fails | Create `User`, `Identity`, `UserIdentityMapping` |
| Binding powerful roles to `system:authenticated` | Massive privilege exposure | Bind only to controlled admin groups |
| Removing `kubeadmin` too early | Possible lockout | Create another `cluster-admin` first |
| Assuming login means access | User gets `403` | Configure RBAC |

## 24. Real-World Design Recommendation

For a mature OpenShift environment, use this design:

```text
1. Use enterprise IdP: LDAP, Keycloak, Red Hat SSO, or OIDC provider.
2. Use stable usernames that do not change when email or display name changes.
3. Use group-based RBAC.
4. Use separate groups for platform admins, project admins, developers, viewers, and auditors.
5. Avoid direct user RoleBindings.
6. Use `mappingMethod: add` during identity migration.
7. Use `mappingMethod: lookup` for strict regulated onboarding.
8. Keep `cluster-admin` limited to a small admin group.
9. Regularly audit users, groups, and role bindings.
10. Disable users in the external IdP first during offboarding.
```

Example final model:

```text
Keycloak / LDAP
  |
  +-- ocp-platform-admins   -> cluster-admin
  +-- ocp-cluster-readers   -> cluster-reader
  +-- finance-admins        -> admin in finance namespace
  +-- finance-developers    -> edit in finance namespace
  +-- finance-viewers       -> view in finance namespace
```

## 25. Quick Revision Notes

- `User` = OpenShift actor.
- `Identity` = successful login identity from a provider.
- `UserIdentityMapping` = link between identity and user.
- `Group` = set of users for RBAC.
- Users do not usually store passwords in OpenShift.
- IdP validates credentials.
- OAuth server issues tokens.
- RBAC controls permissions.
- `401` means authentication problem.
- `403` means authorization problem.
- Prefer groups over direct user bindings.
- Use `claim` for simple automatic provisioning.
- Use `add` for multi-IdP or migration.
- Use `lookup` for strict manual provisioning.
- Do not bind powerful roles to `system:authenticated`.
- Do not remove `kubeadmin` before creating another cluster admin.
