# LDAP Group Synchronization in OpenShift

**Area:** Enterprise Authentication and Identity Management  
**Level:** Advanced OpenShift Administration / 10+ years experience  
**Platform focus:** Red Hat OpenShift Container Platform 4.x  
**Main command:** `oc adm groups sync`

---

## 1. Purpose of LDAP Group Synchronization

LDAP group synchronization is the process of importing group membership information from an external LDAP-compatible directory into OpenShift `Group` objects.

In enterprise environments, user and group ownership normally lives outside OpenShift, for example:

- Microsoft Active Directory
- Red Hat Directory Server / 389 Directory Server
- FreeIPA / IdM
- OpenLDAP
- Enterprise LDAP gateways

OpenShift can authenticate users against LDAP, but authentication alone does not automatically give users permissions. Authorization is normally handled through OpenShift RBAC. LDAP group synchronization bridges that gap by converting external LDAP groups into OpenShift groups, so administrators can bind those groups to OpenShift roles.

### Simple enterprise flow

```text
LDAP / Active Directory
        |
        | 1. User authenticates through LDAP identity provider
        v
OpenShift OAuth Server
        |
        | 2. OpenShift creates/uses User and Identity objects
        v
OpenShift User
        |
        | 3. LDAP group sync imports external group membership
        v
OpenShift Group
        |
        | 4. RoleBinding / ClusterRoleBinding grants permissions
        v
Project or Cluster Access
```

### Key point

LDAP identity provider configuration answers this question:

```text
Can this user log in?
```

LDAP group synchronization answers this question:

```text
Which OpenShift groups should this user belong to for RBAC?
```

They are related but separate.

## 2. Why LDAP Group Synchronization Matters in Enterprise OpenShift

In a small lab, you can manually add users to groups:

```bash
oc adm groups new dev-team user1 user2
oc adm policy add-role-to-group edit dev-team -n app-dev
```

In a real enterprise cluster, this approach does not scale. You may have hundreds or thousands of users and teams. LDAP group synchronization allows OpenShift administrators to:

- Use existing enterprise groups for OpenShift access.
- Avoid manually maintaining OpenShift group membership.
- Centralize user lifecycle management in LDAP/AD.
- Automatically remove access when users leave a directory group.
- Apply RBAC using stable business groups, not individual users.
- Support audit, compliance, and separation of duties.

Example enterprise mappings:

```text
LDAP Group                         OpenShift Permission
--------------------------------------------------------------
ocp-cluster-admins                 cluster-admin
ocp-platform-operators             cluster-monitoring-view / admin
ocp-app1-dev                       edit on app1-dev namespace
ocp-app1-prod-readonly             view on app1-prod namespace
ocp-security-auditors              view / cluster-reader
ocp-cicd-admins                    admin on cicd namespace
```

## 3. OpenShift Objects Involved

LDAP group sync primarily creates or updates objects from the `user.openshift.io/v1` API group.

### 3.1 User

A `User` represents a person or service identity known to OpenShift.

```bash
oc get users
oc get user <username> -o yaml
```

Example:

```yaml
apiVersion: user.openshift.io/v1
kind: User
metadata:
  name: rakesh.jha@example.com
identities:
- ldapidp:uid=rakesh,ou=users,dc=example,dc=com
```

### 3.2 Identity

An `Identity` connects an external identity provider login to an OpenShift user.

```bash
oc get identities
```

Example:

```text
ldapidp:uid=rakesh,ou=users,dc=example,dc=com
```

### 3.3 Group

A `Group` contains OpenShift usernames.

```bash
oc get groups
oc get group ocp-admins -o yaml
```

Example:

```yaml
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  name: ocp-admins
  annotations:
    openshift.io/ldap.sync-time: "2026-07-02T10:30:00+0530"
    openshift.io/ldap.uid: "cn=ocp-admins,ou=groups,dc=example,dc=com"
    openshift.io/ldap.url: "ldap.example.com:636"
users:
- rakesh.jha@example.com
- platform.admin@example.com
```

Important annotations:

| Annotation | Meaning |
|---|---|
| `openshift.io/ldap.sync-time` | Last sync time |
| `openshift.io/ldap.uid` | LDAP unique identifier used for the group |
| `openshift.io/ldap.url` | LDAP server used during sync |

### 3.4 RoleBinding and ClusterRoleBinding

After groups are synced, permissions are granted using normal OpenShift RBAC.

Namespace-level access:

```bash
oc adm policy add-role-to-group edit ocp-app1-dev -n app1-dev
```

Cluster-level access:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-cluster-admins
```

Check bindings:

```bash
oc get rolebinding -n app1-dev
oc get clusterrolebinding | grep ocp-cluster-admins
```

## 4. Supported LDAP Group Membership Schemas

OpenShift LDAP group sync supports three common membership models:

1. RFC 2307
2. Active Directory
3. Augmented Active Directory

Choosing the wrong schema is one of the most common causes of empty groups or failed sync jobs.

---

## 5. RFC 2307 Schema

RFC 2307-style directories usually store both users and groups as first-class LDAP entries. Group membership is stored on the group entry.

### 5.1 Data model

```text
User entry:
  dn: uid=rakesh,ou=users,dc=example,dc=com
  uid: rakesh
  mail: rakesh.jha@example.com

Group entry:
  dn: cn=ocp-admins,ou=groups,dc=example,dc=com
  cn: ocp-admins
  member: uid=rakesh,ou=users,dc=example,dc=com
```

### 5.2 When to use RFC 2307

Use `rfc2307` when:

- Groups exist as LDAP entries.
- Users exist as LDAP entries.
- Group membership is stored in group attributes such as `member`, `memberUid`, or `uniqueMember`.
- You use OpenLDAP, Red Hat Directory Server, 389 DS, FreeIPA/IdM, or Unix-style LDAP groups.

### 5.3 RFC 2307 sync configuration

File: `ldap-sync-rfc2307.yaml`

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ldap.example.com:636
bindDN: "cn=openshift-sync,ou=serviceaccounts,dc=example,dc=com"
bindPassword:
  file: "/etc/secrets/bindPassword"
insecure: false
ca: /etc/ldap-ca/ca.crt
rfc2307:
  groupsQuery:
    baseDN: "ou=groups,dc=example,dc=com"
    scope: sub
    derefAliases: never
    timeout: 10
    filter: "(&(objectClass=groupOfNames)(cn=ocp-*))"
    pageSize: 500
  groupUIDAttribute: dn
  groupNameAttributes: [ cn ]
  groupMembershipAttributes: [ member ]
  usersQuery:
    baseDN: "ou=users,dc=example,dc=com"
    scope: sub
    derefAliases: never
    timeout: 10
    filter: "(objectClass=inetOrgPerson)"
    pageSize: 500
  userUIDAttribute: dn
  userNameAttributes: [ mail ]
  tolerateMemberNotFoundErrors: false
  tolerateMemberOutOfScopeErrors: false
```

### 5.4 Important RFC 2307 mapping logic

```text
groupMembershipAttributes values must match userUIDAttribute values.
```

Example:

```yaml
groupMembershipAttributes: [ member ]
userUIDAttribute: dn
```

This means the group contains full user DNs:

```text
member: uid=rakesh,ou=users,dc=example,dc=com
```

If your group contains only usernames:

```text
memberUid: rakesh
```

then your config should look more like:

```yaml
groupMembershipAttributes: [ memberUid ]
userUIDAttribute: uid
userNameAttributes: [ uid ]
```

## 6. Active Directory Schema

In Active Directory-style synchronization, membership is usually read from user attributes such as `memberOf`. Group entries might not be queried as full metadata objects in the same way as RFC 2307.

### 6.1 Data model

```text
User entry:
  dn: CN=Rakesh Jha,OU=Users,DC=example,DC=com
  sAMAccountName: rjha
  mail: rakesh.jha@example.com
  memberOf: CN=ocp-admins,OU=Groups,DC=example,DC=com
  memberOf: CN=ocp-app1-dev,OU=Groups,DC=example,DC=com
```

### 6.2 When to use Active Directory schema

Use `activeDirectory` when:

- The LDAP server is Microsoft Active Directory.
- Membership is available on users through `memberOf`.
- You want group names derived from user membership values.
- You do not need additional group metadata from actual group entries.

### 6.3 Active Directory sync configuration

File: `ldap-sync-ad.yaml`

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636
bindDN: "CN=openshift-sync,OU=Service Accounts,DC=example,DC=com"
bindPassword:
  file: "/etc/secrets/bindPassword"
insecure: false
ca: /etc/ldap-ca/ca.crt
activeDirectory:
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    timeout: 10
    filter: "(&(objectClass=user)(!(objectClass=computer))(mail=*))"
    pageSize: 500
  userNameAttributes: [ mail ]
  groupMembershipAttributes: [ memberOf ]
```

### 6.4 Username choice in AD

Common options:

```yaml
userNameAttributes: [ mail ]
```

or:

```yaml
userNameAttributes: [ sAMAccountName ]
```

Production recommendation:

The value selected in `userNameAttributes` should match the username OpenShift creates during LDAP login. If users log in and OpenShift creates users as `rjha`, but group sync creates membership as `rakesh.jha@example.com`, RBAC will not match correctly.

Verify with:

```bash
oc get users
oc get user rjha -o yaml
oc get group ocp-admins -o yaml
```

## 7. Augmented Active Directory Schema

Augmented Active Directory combines AD-style user membership with first-class group entries. Membership is still read from user attributes, but OpenShift also queries group entries for stable group names and metadata.

### 7.1 Data model

```text
User entry:
  dn: CN=Rakesh Jha,OU=Users,DC=example,DC=com
  mail: rakesh.jha@example.com
  memberOf: CN=ocp-admins,OU=Groups,DC=example,DC=com

Group entry:
  dn: CN=ocp-admins,OU=Groups,DC=example,DC=com
  cn: ocp-admins
  description: OpenShift platform administrators
```

### 7.2 When to use augmented Active Directory

Use `augmentedActiveDirectory` when:

- Users have `memberOf` attributes.
- Groups also exist as searchable objects.
- You want OpenShift group names from attributes like `cn`.
- You want better control over which groups are imported.
- You need nested AD membership handling with whitelisted groups.

### 7.3 Augmented AD sync configuration

File: `ldap-sync-augmented-ad.yaml`

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636
bindDN: "CN=openshift-sync,OU=Service Accounts,DC=example,DC=com"
bindPassword:
  file: "/etc/secrets/bindPassword"
insecure: false
ca: /etc/ldap-ca/ca.crt
augmentedActiveDirectory:
  groupsQuery:
    baseDN: "OU=Groups,DC=example,DC=com"
    scope: sub
    derefAliases: never
    timeout: 10
    filter: "(&(objectClass=group)(cn=ocp-*))"
    pageSize: 500
  groupUIDAttribute: dn
  groupNameAttributes: [ cn ]
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    timeout: 10
    filter: "(&(objectClass=user)(!(objectClass=computer))(mail=*))"
    pageSize: 500
  userNameAttributes: [ mail ]
  groupMembershipAttributes: [ memberOf ]
```

## 8. LDAPSyncConfig Field Deep Dive

### 8.1 Top-level fields

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ldap.example.com:636
bindDN: "cn=openshift-sync,ou=serviceaccounts,dc=example,dc=com"
bindPassword:
  file: "/etc/secrets/bindPassword"
insecure: false
ca: /etc/ldap-ca/ca.crt
```

| Field | Meaning | Production advice |
|---|---|---|
| `url` | LDAP server URL | Prefer `ldaps://host:636` or StartTLS-capable `ldap://host:389` with `insecure: false` |
| `bindDN` | Service account DN used to query LDAP | Use read-only LDAP service account |
| `bindPassword` | Password source | Use `file` or mounted Secret, not inline clear text |
| `insecure` | Whether TLS is disabled | Keep `false` in production |
| `ca` | CA bundle path | Use enterprise CA bundle for LDAPS/StartTLS |
| `groupUIDNameMapping` | Explicit LDAP UID to OpenShift group name mapping | Useful when LDAP group names are ugly or unstable |
| `rfc2307` | RFC 2307 schema config | Use for OpenLDAP/IdM/389-style groups |
| `activeDirectory` | AD-style config | Use when membership is read from user `memberOf` |
| `augmentedActiveDirectory` | AD membership plus group metadata | Best for many enterprise AD deployments |

### 8.2 LDAPQuery fields

Example:

```yaml
usersQuery:
  baseDN: "OU=Users,DC=example,DC=com"
  scope: sub
  derefAliases: never
  timeout: 10
  filter: "(&(objectClass=user)(mail=*))"
  pageSize: 500
```

| Field | Meaning |
|---|---|
| `baseDN` | LDAP subtree where search begins |
| `scope` | `base`, `one`, or `sub` |
| `derefAliases` | Alias dereference behavior: `never`, `search`, `base`, `always` |
| `timeout` | Client-side timeout in seconds; `0` means no client-side limit |
| `filter` | LDAP filter used to select entries |
| `pageSize` | LDAP paging size; useful for large directories |

## 9. Running LDAP Group Sync Manually

### 9.1 Always test dry-run first

By default, sync is dry-run. It shows what would change but does not modify OpenShift groups.

```bash
oc adm groups sync --sync-config=ldap-sync-rfc2307.yaml
```

### 9.2 Apply changes with `--confirm`

```bash
oc adm groups sync --sync-config=ldap-sync-rfc2307.yaml --confirm
```

### 9.3 Sync only existing OpenShift groups

This mode updates only OpenShift groups that already correspond to LDAP groups.

```bash
oc adm groups sync --type=openshift --sync-config=ldap-sync-rfc2307.yaml --confirm
```

Useful when:

- You do not want all LDAP groups imported.
- You pre-created selected groups.
- You want controlled production behavior.

### 9.4 Sync only one group

```bash
oc adm groups sync "cn=ocp-admins,ou=groups,dc=example,dc=com" \
  --sync-config=ldap-sync-rfc2307.yaml \
  --confirm
```

### 9.5 Sync using whitelist

File: `whitelist.txt`

```text
cn=ocp-admins,ou=groups,dc=example,dc=com
cn=ocp-app1-dev,ou=groups,dc=example,dc=com
cn=ocp-app1-prod-readonly,ou=groups,dc=example,dc=com
```

Command:

```bash
oc adm groups sync \
  --whitelist=whitelist.txt \
  --sync-config=ldap-sync-rfc2307.yaml \
  --confirm
```

### 9.6 Sync using blacklist

File: `blacklist.txt`

```text
cn=domain users,cn=users,dc=example,dc=com
cn=all employees,ou=groups,dc=example,dc=com
```

Command:

```bash
oc adm groups sync \
  --blacklist=blacklist.txt \
  --sync-config=ldap-sync-rfc2307.yaml \
  --confirm
```

### 9.7 Production recommendation

For production OpenShift clusters, prefer whitelisting OpenShift-specific groups such as:

```text
ocp-cluster-admins
ocp-platform-admins
ocp-app1-dev
ocp-app1-prod-view
```

Avoid blindly syncing broad groups such as:

```text
Domain Users
All Employees
Authenticated Users
```

## 10. Pruning Removed LDAP Groups

Sync creates and updates groups, but if a group disappears from LDAP, you may need pruning to remove stale OpenShift group records.

Dry-run:

```bash
oc adm prune groups --sync-config=ldap-sync-rfc2307.yaml
```

Apply:

```bash
oc adm prune groups --sync-config=ldap-sync-rfc2307.yaml --confirm
```

With whitelist:

```bash
oc adm prune groups \
  --whitelist=whitelist.txt \
  --sync-config=ldap-sync-rfc2307.yaml \
  --confirm
```

### Production warning

Do not automate pruning without strong controls. A bad LDAP filter, wrong `baseDN`, network issue, or bind account issue can make groups appear missing. Run pruning first in dry-run and review the proposed deletions.

If you use a service account for pruning, it needs permission to delete groups:

```yaml
verbs:
- get
- list
- create
- update
- delete
```

## 11. Automating LDAP Group Sync with CronJob

For enterprise clusters, group sync should run periodically, commonly every 15, 30, or 60 minutes depending on business requirements.

### 11.1 Architecture

```text
Namespace: ldap-sync
  ServiceAccount: ldap-group-syncer
  ClusterRole: can get/list/create/update OpenShift groups
  ClusterRoleBinding: binds role to SA
  Secret: LDAP bind password
  ConfigMap: LDAP CA certificate
  ConfigMap: LDAPSyncConfig YAML
  CronJob: runs oc adm groups sync --confirm
```

### 11.2 Create namespace

```bash
oc new-project ldap-sync
```

### 11.3 Create LDAP bind password secret

```bash
oc create secret generic ldap-secret \
  -n ldap-sync \
  --from-literal=bindPassword='REPLACE_WITH_PASSWORD'
```

### 11.4 Create CA config map

```bash
oc create configmap ca-config-map \
  -n ldap-sync \
  --from-file=ca.crt=/path/to/ldap-ca.crt
```

### 11.5 ServiceAccount

File: `ldap-sync-service-account.yaml`

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
```

Apply:

```bash
oc apply -f ldap-sync-service-account.yaml
```

### 11.6 ClusterRole

File: `ldap-sync-cluster-role.yaml`

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ldap-group-syncer
rules:
- apiGroups:
  - user.openshift.io
  resources:
  - groups
  verbs:
  - get
  - list
  - create
  - update
```

Apply:

```bash
oc apply -f ldap-sync-cluster-role.yaml
```

### 11.7 ClusterRoleBinding

File: `ldap-sync-cluster-role-binding.yaml`

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: ldap-group-syncer
subjects:
- kind: ServiceAccount
  name: ldap-group-syncer
  namespace: ldap-sync
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: ldap-group-syncer
```

Apply:

```bash
oc apply -f ldap-sync-cluster-role-binding.yaml
```

### 11.8 ConfigMap containing sync config

File: `ldap-sync-config-map.yaml`

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
data:
  sync.yaml: |
    kind: LDAPSyncConfig
    apiVersion: v1
    url: ldaps://ldap.example.com:636
    insecure: false
    bindDN: "cn=openshift-sync,ou=serviceaccounts,dc=example,dc=com"
    bindPassword:
      file: "/etc/secrets/bindPassword"
    ca: /etc/ldap-ca/ca.crt
    rfc2307:
      groupsQuery:
        baseDN: "ou=groups,dc=example,dc=com"
        scope: sub
        derefAliases: never
        timeout: 10
        filter: "(&(objectClass=groupOfNames)(cn=ocp-*))"
        pageSize: 500
      groupUIDAttribute: dn
      groupNameAttributes: [ cn ]
      groupMembershipAttributes: [ member ]
      usersQuery:
        baseDN: "ou=users,dc=example,dc=com"
        scope: sub
        derefAliases: never
        timeout: 10
        filter: "(objectClass=inetOrgPerson)"
        pageSize: 500
      userUIDAttribute: dn
      userNameAttributes: [ mail ]
      tolerateMemberNotFoundErrors: false
      tolerateMemberOutOfScopeErrors: false
```

Apply:

```bash
oc apply -f ldap-sync-config-map.yaml
```

### 11.9 CronJob

File: `ldap-sync-cronjob.yaml`

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: ldap-group-syncer
  namespace: ldap-sync
spec:
  schedule: "*/30 * * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 0
      ttlSecondsAfterFinished: 1800
      template:
        spec:
          serviceAccountName: ldap-group-syncer
          restartPolicy: Never
          activeDeadlineSeconds: 500
          containers:
          - name: ldap-group-sync
            image: registry.redhat.io/openshift4/ose-cli:latest
            command:
            - /bin/bash
            - -c
            - oc adm groups sync --sync-config=/etc/config/sync.yaml --confirm
            volumeMounts:
            - name: ldap-sync-volume
              mountPath: /etc/config
            - name: ldap-bind-password
              mountPath: /etc/secrets
            - name: ldap-ca
              mountPath: /etc/ldap-ca
          volumes:
          - name: ldap-sync-volume
            configMap:
              name: ldap-group-syncer
          - name: ldap-bind-password
            secret:
              secretName: ldap-secret
          - name: ldap-ca
            configMap:
              name: ca-config-map
```

Apply:

```bash
oc apply -f ldap-sync-cronjob.yaml
```

### 11.10 Trigger one manual CronJob run

```bash
oc create job ldap-group-syncer-manual-$(date +%s) \
  --from=cronjob/ldap-group-syncer \
  -n ldap-sync
```

Check job and logs:

```bash
oc get jobs -n ldap-sync
oc get pods -n ldap-sync
oc logs job/<job-name> -n ldap-sync
```

## 12. Nested Group Synchronization

OpenShift groups do not nest. OpenShift expects a flat list of users inside a group.

Example unsupported direct nesting in OpenShift:

```text
OpenShift Group A
  - User rakesh
  - Group B
```

OpenShift needs this instead:

```text
OpenShift Group A
  - User rakesh
  - User jim
  - User jane
```

For Microsoft Active Directory, nested membership can be flattened by using the LDAP matching rule in chain OID:

```text
1.2.840.113556.1.4.1941
```

Example augmented AD nested config fragment:

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636
augmentedActiveDirectory:
  groupsQuery:
    derefAliases: never
    pageSize: 500
  groupUIDAttribute: dn
  groupNameAttributes: [ cn ]
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(&(objectClass=user)(!(objectClass=computer))(mail=*))"
    pageSize: 500
  userNameAttributes: [ mail ]
  groupMembershipAttributes:
  - "memberOf:1.2.840.113556.1.4.1941:"
```

Run with explicit whitelist:

```bash
oc adm groups sync \
  --whitelist=whitelist.txt \
  --sync-config=ldap-sync-nested-ad.yaml \
  --confirm
```

### Nested group production cautions

- Explicitly whitelist groups.
- Avoid syncing broad parent groups.
- Test dry-run carefully.
- Validate final OpenShift group users.
- Understand AD query cost before running frequently.

## 13. User-Defined Group Name Mapping

Sometimes LDAP group names are not suitable as OpenShift group names.

Example LDAP group DN:

```text
CN=OCP_PRD_PLATFORM_ADMIN_L3,OU=Groups,DC=example,DC=com
```

Desired OpenShift group name:

```text
ocp-prod-platform-admins
```

Use `groupUIDNameMapping`:

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad.example.com:636
groupUIDNameMapping:
  "CN=OCP_PRD_PLATFORM_ADMIN_L3,OU=Groups,DC=example,DC=com": ocp-prod-platform-admins
augmentedActiveDirectory:
  groupsQuery:
    baseDN: "OU=Groups,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(cn=OCP_*)"
  groupUIDAttribute: dn
  groupNameAttributes: [ cn ]
  usersQuery:
    baseDN: "OU=Users,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(&(objectClass=user)(mail=*))"
  userNameAttributes: [ mail ]
  groupMembershipAttributes: [ memberOf ]
```

This is useful when:

- LDAP naming standards are not friendly.
- You want stable OpenShift group names.
- Different LDAP group names should map to clean RBAC names.
- You want to avoid exposing internal AD naming conventions to OpenShift users.

## 14. Applying RBAC After Group Sync

LDAP sync only creates OpenShift groups. It does not automatically grant permissions.

### 14.1 Namespace/project access

Create project:

```bash
oc new-project app1-dev
```

Give edit access to synced LDAP group:

```bash
oc adm policy add-role-to-group edit ocp-app1-dev -n app1-dev
```

Give view access:

```bash
oc adm policy add-role-to-group view ocp-app1-readonly -n app1-dev
```

Give admin access inside namespace:

```bash
oc adm policy add-role-to-group admin ocp-app1-admins -n app1-dev
```

### 14.2 Cluster access

Cluster reader:

```bash
oc adm policy add-cluster-role-to-group cluster-reader ocp-auditors
```

Cluster admin:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-cluster-admins
```

### 14.3 Verify effective permission

As admin:

```bash
oc auth can-i get pods -n app1-dev --as=rakesh.jha@example.com
oc auth can-i create deployments -n app1-dev --as=rakesh.jha@example.com
oc auth can-i '*' '*' --all-namespaces --as=rakesh.jha@example.com
```

## 15. End-to-End Implementation Runbook

### Step 1: Confirm LDAP/AD search manually

For LDAPS:

```bash
ldapsearch -x \
  -H ldaps://ldap.example.com:636 \
  -D "cn=openshift-sync,ou=serviceaccounts,dc=example,dc=com" \
  -W \
  -b "ou=groups,dc=example,dc=com" \
  "(&(objectClass=groupOfNames)(cn=ocp-*))" cn member
```

For AD users:

```bash
ldapsearch -x \
  -H ldaps://ad.example.com:636 \
  -D "CN=openshift-sync,OU=Service Accounts,DC=example,DC=com" \
  -W \
  -b "OU=Users,DC=example,DC=com" \
  "(&(objectClass=user)(!(objectClass=computer))(mail=*))" mail sAMAccountName memberOf
```

### Step 2: Decide schema

| Directory design | Use schema |
|---|---|
| Group has `member` or `memberUid` | `rfc2307` |
| User has `memberOf`; group metadata not required | `activeDirectory` |
| User has `memberOf`; group entries also queried | `augmentedActiveDirectory` |
| Nested AD groups required | `augmentedActiveDirectory` with matching rule and whitelist |

### Step 3: Create sync config

```bash
vi ldap-sync.yaml
```

### Step 4: Dry-run sync

```bash
oc adm groups sync --sync-config=ldap-sync.yaml
```

### Step 5: Review output

Look for:

- Groups to be created.
- Users inside each group.
- Empty groups.
- Missing user errors.
- Out-of-scope errors.
- Unexpected group names.

### Step 6: Apply sync

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

### Step 7: Validate OpenShift groups

```bash
oc get groups
oc describe group ocp-admins
oc get group ocp-admins -o yaml
```

### Step 8: Bind RBAC


### Step 9: Test access

```bash

```

Create namespace, service account, RBAC, secrets, config maps, and CronJob.

## 16. Troubleshooting Guide

### Problem 1: LDAP login works, but user has no access

#### Symptoms

```text
User can log in to OpenShift console.
User sees no projects.
oc auth can-i returns no.
```

#### Common causes

- LDAP group sync has not run.
- User is not in synced OpenShift group.
- OpenShift group exists but no RoleBinding/ClusterRoleBinding exists.
- Username in group does not match OpenShift username.

#### Checks

```bash
oc get users
oc get group <group-name> -o yaml
oc get rolebindings -n <namespace>
oc get clusterrolebindings | grep <group-name>
oc auth can-i get pods -n <namespace> --as=<username>
```

#### Fix

Ensure `userNameAttributes` matches the username created by the LDAP identity provider.

Example mismatch:

```text
OpenShift user: rjha
Group synced user: rakesh.jha@example.com
```

Fix by aligning:

```yaml
userNameAttributes: [ sAMAccountName ]
```

or update the LDAP identity provider preferred username mapping to use mail consistently.

---

### Problem 2: Groups are created but empty

#### Common causes

- `groupMembershipAttributes` does not match LDAP data.
- `userUIDAttribute` does not match membership values.
- `usersQuery.baseDN` is wrong.
- `usersQuery.filter` excludes valid users.
- AD `memberOf` is not returned due to permissions or LDAP control behavior.

#### Checks

```bash
ldapsearch -x -H ldaps://ldap.example.com:636 \
  -D "<bindDN>" -W \
  -b "<users-base-dn>" \
  "(mail=rakesh.jha@example.com)" dn uid mail memberOf
```

For RFC 2307:

```bash
ldapsearch -x -H ldaps://ldap.example.com:636 \
  -D "<bindDN>" -W \
  -b "<groups-base-dn>" \
  "(cn=ocp-admins)" cn member memberUid uniqueMember
```

#### Fix examples

If group stores full DN:

```yaml
groupMembershipAttributes: [ member ]
userUIDAttribute: dn
```

If group stores uid:

```yaml
groupMembershipAttributes: [ memberUid ]
userUIDAttribute: uid
```

---

### Problem 3: Sync fails with member out-of-scope errors

#### Meaning

A group member points to a user DN outside your `usersQuery.baseDN`.

Example:

```text
usersQuery.baseDN: ou=employees,dc=example,dc=com
member: uid=contractor1,ou=contractors,dc=example,dc=com
```

#### Correct fix

Expand `usersQuery.baseDN` or adjust group membership scope.

```yaml
usersQuery:
  baseDN: "dc=example,dc=com"
```

#### Optional tolerance

```yaml
tolerateMemberOutOfScopeErrors: true
```

Production warning: this ignores out-of-scope members and can cause incomplete OpenShift group membership.

---

### Problem 4: Sync fails with member not found errors

#### Meaning

The group references a user that LDAP cannot find.

Common causes:

- Deleted LDAP user still exists in group member attribute.
- Wrong `userUIDAttribute`.
- Wrong `usersQuery.filter`.
- Bind account cannot read that user.

#### Optional tolerance

```yaml
tolerateMemberNotFoundErrors: true
```

Production warning: use only when you intentionally accept missing users.

---

### Problem 5: TLS certificate error

#### Symptoms

```text
x509: certificate signed by unknown authority
certificate is not trusted
```

#### Fix

Provide CA bundle:

```yaml
insecure: false
ca: /etc/ldap-ca/ca.crt
```

Test:

```bash
openssl s_client -connect ldap.example.com:636 -showcerts
```

Do not solve production TLS problems with:

```yaml
insecure: true
```

unless it is a temporary lab-only test.

---

### Problem 6: CronJob runs but groups are not updated

#### Checks

```bash
oc get cronjob -n ldap-sync
oc get jobs -n ldap-sync
oc get pods -n ldap-sync
oc logs <pod-name> -n ldap-sync
oc auth can-i update groups.user.openshift.io \
  --as=system:serviceaccount:ldap-sync:ldap-group-syncer
```

#### Common causes

- ServiceAccount lacks group update permission.
- LDAP secret not mounted correctly.
- ConfigMap path wrong.
- CA file path wrong.
- `oc adm groups sync` command missing `--confirm`.
- NetworkPolicy, proxy, or firewall blocks LDAP server.

---

### Problem 7: User removed from LDAP group but still has access

#### Explanation

`oc adm groups sync` should update membership if LDAP is reachable and data is correct. But access may persist if:

- CronJob has not run yet.
- User is in another group with the same RBAC access.
- A direct RoleBinding exists for the user.
- Sync failed silently and old group object remains.

#### Checks

```bash
oc get group <group> -o yaml
oc adm policy who-can get pods -n <namespace>
oc get rolebinding -A -o wide | grep <username>
oc get clusterrolebinding -o wide | grep <username>
```

## 17. Security Best Practices

### 17.1 Use secure transport

Prefer:

```yaml
url: ldaps://ldap.example.com:636
insecure: false
ca: /etc/ldap-ca/ca.crt
```

Avoid production use of:

```yaml
insecure: true
```

### 17.2 Use a dedicated LDAP bind account

Do not use a domain admin account.

Recommended account:

```text
cn=openshift-sync,ou=serviceaccounts,dc=example,dc=com
```

Permissions:

- Read users required for OpenShift.
- Read groups required for OpenShift.
- No write permission.
- No administrative privilege.

### 17.3 Protect secrets

Use Kubernetes Secrets for bind password:

```bash
oc create secret generic ldap-secret \
  --from-literal=bindPassword='<password>' \
  -n ldap-sync
```

Restrict access:

```bash
oc adm policy who-can get secret/ldap-secret -n ldap-sync
```

### 17.4 Use least privilege for sync automation

CronJob service account should only manage OpenShift group objects.

Sync-only verbs:

```yaml
verbs:
- get
- list
- create
- update
```

If pruning is automated, add `delete` intentionally and document why.

### 17.5 Avoid dangerous RBAC bindings

Dangerous:

```bash
oc adm policy add-cluster-role-to-group cluster-admin "Domain Users"
```

Safer:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-cluster-admins
```

### 17.6 Use naming standards

Good group naming:

```text
ocp-cluster-admins
ocp-platform-readonly
ocp-app1-dev-edit
ocp-app1-prod-view
ocp-cicd-admins
```

Bad group naming:

```text
admins
users
team1
all
prod
```

### 17.7 Audit regularly

Useful audit commands:

```bash
oc get groups
oc get group <group> -o yaml
oc adm policy who-can '*' '*' -A
oc get clusterrolebinding -o yaml | grep -A20 -B5 '<group-name>'
oc get rolebinding -A -o yaml | grep -A20 -B5 '<group-name>'
```

## 18. Performance and Scale Considerations

Large enterprises can have tens of thousands of users and groups. Poor LDAP sync design can create unnecessary load.

### 18.1 Use narrow filters

Avoid:

```yaml
filter: "(objectClass=group)"
```

Prefer:

```yaml
filter: "(&(objectClass=group)(cn=ocp-*))"
```

### 18.2 Use correct baseDN

Avoid searching the whole directory when unnecessary:

```yaml
baseDN: "dc=example,dc=com"
```

Prefer targeted OUs:

```yaml
baseDN: "ou=openshift-groups,dc=example,dc=com"
```

### 18.3 Use paging

```yaml
pageSize: 500
```

This helps when LDAP server limits search result size.

### 18.4 Tune schedule

Do not sync every minute unless absolutely required.

Common schedule:

```yaml
schedule: "*/30 * * * *"
```

For less dynamic environments:

```yaml
schedule: "0 * * * *"
```

### 18.5 Avoid expensive nested queries

Nested AD queries using matching rule in chain can be more expensive. Use explicit whitelist and longer schedules when possible.

Before major changes:

```bash

oc get rolebindings -A -o yaml > rolebindings-backup-$(date +%F).yaml
oc get clusterrolebindings -o yaml > clusterrolebindings-backup-$(date +%F).yaml
```


Rollback RBAC carefully:

## 21. Common Interview Questions and Senior-Level Answers

### Q1. What is the difference between LDAP authentication and LDAP group synchronization?

LDAP authentication validates user credentials and creates/maps OpenShift `User` and `Identity` objects. LDAP group synchronization imports LDAP group membership into OpenShift `Group` objects. Authentication decides whether a user can log in; group sync helps determine what the user can access through RBAC.

### Q2. Why can a user log in but see no projects?

Because login only proves identity. The user may not belong to a synced OpenShift group, or the synced group may not be bound to any OpenShift role. I would check `oc get users`, `oc get group`, RoleBindings, ClusterRoleBindings, and `oc auth can-i`.

### Q3. Why are synced groups empty?

Usually because the membership mapping is wrong. In RFC 2307, `groupMembershipAttributes` values must match `userUIDAttribute`. In AD, the issue is often `memberOf` not being returned, a bad `usersQuery`, or a username mismatch between LDAP login and group sync.

### Q4. What does `--confirm` do?

`oc adm groups sync` is dry-run by default. Without `--confirm`, it only prints what would happen. With `--confirm`, it actually creates or updates OpenShift group records.

### Q5. How do you safely sync only selected LDAP groups?

Use whitelist files or literal group unique identifiers. In production, I prefer explicit whitelists for high-impact groups, especially groups that are bound to `cluster-admin` or production namespaces.

### Q6. How do you handle nested Active Directory groups?

OpenShift groups are flat and do not nest. AD nested membership must be flattened before OpenShift consumes it. For AD, use the matching rule in chain OID `1.2.840.113556.1.4.1941` with augmented AD configuration and explicit whitelisting.

### Q7. Should you use `insecure: true`?

Only for temporary lab troubleshooting. In production, use LDAPS or StartTLS with `insecure: false` and a trusted CA bundle.

### Q8. How do you remove stale groups?

Use `oc adm prune groups --sync-config=<file>`, first as dry-run and then with `--confirm` after reviewing the output. Be very careful automating prune because bad LDAP queries can make valid groups appear missing.

### Q9. What is the best practice for cluster-admin access from LDAP?

Create a dedicated LDAP group such as `ocp-cluster-admins`, sync only that group, and bind it to `cluster-admin`. Never bind broad groups such as `Domain Users` or `All Employees` to powerful cluster roles.

### Q10. How do you troubleshoot username mismatch?

Compare OpenShift users with synced group users:

```bash
oc get users
oc get group <group> -o yaml
```

If the OpenShift user is `rjha` but the group contains `rakesh.jha@example.com`, align `userNameAttributes` with the LDAP identity provider username mapping.

## 24. Final Summary

LDAP group synchronization is a core day-2 identity management task in enterprise OpenShift. It does not replace LDAP authentication; it complements authentication by importing external group membership into OpenShift group objects. Those groups are then used by RoleBindings and ClusterRoleBindings to grant access.

A senior OpenShift administrator should be able to:

- Understand the difference between authentication, identity, group sync, and RBAC.
- Choose the correct LDAP sync schema.
- Write and validate `LDAPSyncConfig` files.
- Run sync safely using dry-run and `--confirm`.
- Use whitelist/blacklist controls.
- Automate sync through CronJob with least privilege.
- Troubleshoot empty groups, missing users, TLS issues, username mismatches, and nested groups.
- Design a secure enterprise RBAC model based on LDAP groups.

The safest production pattern is:

```text
LDAP/AD login + explicitly whitelisted OpenShift-specific LDAP groups + periodic sync CronJob + Git-managed RBAC bindings + regular audit
```
