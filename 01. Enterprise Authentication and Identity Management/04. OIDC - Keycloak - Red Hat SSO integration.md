# OIDC / Keycloak / Red Hat SSO Integration in Enterprise Authentication and Identity Management

**Track:** Advanced OpenShift Administration  
**Audience:** 10+ years Linux / OpenShift / Kubernetes / Platform Administration  
**Focus:** Enterprise authentication, SSO, Keycloak / Red Hat SSO integration, OpenShift OAuth, claims, groups, RBAC, TLS, troubleshooting, production operations

---

## 1. Executive Summary

OIDC / Keycloak / Red Hat SSO integration in OpenShift is used to centralize user authentication and provide enterprise single sign-on for OpenShift web console and CLI users.

In a production OpenShift environment, the most common and supported model is:

```text
User Browser / oc CLI
        |
        v
OpenShift OAuth Server
        |
        v
OIDC Identity Provider
Keycloak / Red Hat SSO / Red Hat build of Keycloak
        |
        v
Enterprise Identity Source
LDAP / Active Directory / IdM / External IdP
```

OpenShift does not normally store enterprise passwords. OpenShift delegates authentication to an external identity provider. After successful authentication, OpenShift creates or maps a `User` and `Identity`, optionally reads group claims, and then authorizes access through OpenShift RBAC.

For a senior administrator, the key point is this:

> OIDC solves authentication. OpenShift RBAC solves authorization. Keycloak can provide identity, claims, and groups, but OpenShift roles and permissions must still be designed, bound, audited, and operated inside OpenShift.

## 2. Terminology

| Term | Meaning in OpenShift / Keycloak integration |
|---|---|
| OIDC | OpenID Connect, an identity layer built on OAuth 2.0. It is commonly used for SSO authentication. |
| OAuth 2.0 | Authorization framework used for delegated access and token flows. |
| OpenShift OAuth server | Built-in OpenShift component that handles login flows and issues OpenShift access tokens. |
| IdP | Identity Provider. Keycloak / Red Hat SSO acts as the external IdP. |
| RP / Client | Relying party. In this case, OpenShift is registered as an OIDC client in Keycloak. |
| Realm | Keycloak security domain containing users, groups, clients, roles, identity providers, and mappers. |
| Client ID | Identifier of the OpenShift client registered in Keycloak. Example: `openshift`. |
| Client Secret | Secret used by OpenShift OAuth server to authenticate to Keycloak. |
| Issuer URL | Keycloak realm issuer URL. Example: `https://sso.example.com/realms/openshift`. |
| Redirect URI | Callback URL where Keycloak redirects users after successful login. |
| Claim | Attribute inside ID token or UserInfo response, such as `sub`, `preferred_username`, `email`, `name`, `groups`. |
| Scope | Requested permission/claim bundle such as `openid`, `profile`, `email`, `groups`. |
| RBAC | Role-Based Access Control in OpenShift/Kubernetes. |
| User | OpenShift object representing a person or identity after login. |
| Identity | OpenShift object mapping external provider identity to an OpenShift user. |
| Group | OpenShift group object used with RBAC role bindings. |

## 3. Why Enterprises Use Keycloak / Red Hat SSO with OpenShift

Enterprise OpenShift clusters rarely use local `htpasswd` users except for labs or emergency access. In real operations, users are normally managed in LDAP, Active Directory, IdM, or another enterprise identity platform.

Keycloak / Red Hat SSO sits between OpenShift and enterprise identity sources and provides:

- Centralized login
- Browser-based SSO
- Federation with LDAP / Active Directory
- Identity brokering to other IdPs such as SAML or OIDC providers
- Multi-factor authentication policies
- Login flows and conditional authentication
- Claims transformation
- Group and role mapping
- Token signing and OIDC discovery
- Central audit trail for login events

This is important in large OpenShift environments because administrators must manage authentication consistently across multiple clusters, multiple teams, and multiple security zones.

## 4. OpenShift Authentication Architecture

### 4.1 Default OpenShift Authentication Flow

OpenShift includes a built-in OAuth server. Users authenticate through this server to obtain an OpenShift OAuth access token.

When an OIDC provider is configured, the OpenShift OAuth server redirects the user to Keycloak. Keycloak authenticates the user and returns an authorization code to the OpenShift callback URL. OpenShift exchanges that code for tokens, reads claims, maps the identity, and issues an OpenShift token.

```text
1. User opens OpenShift console
2. OpenShift OAuth server redirects to Keycloak
3. User authenticates in Keycloak
4. Keycloak redirects to OpenShift callback URL with authorization code
5. OpenShift OAuth server exchanges code for tokens
6. OpenShift validates token / claims
7. OpenShift creates or maps User and Identity
8. OpenShift applies RBAC based on user/group bindings
9. User accesses console/API according to permissions
```

### 4.2 CLI Authentication Flow

For CLI access, many OIDC providers do not support direct username/password login. Therefore, users often retrieve a token from the OpenShift web flow:

```bash
oc login --token=<token> --server=https://api.<cluster>.<domain>:6443
```

Users can get the token from:

```text
OpenShift Console -> ? Help -> Command Line Tools -> Copy Login Command
```

Or from the OAuth token request route:

```text
https://oauth-openshift.apps.<cluster>.<domain>/oauth/token/request
```

## 5. Production-Supported Design Pattern

### 5.1 Recommended Production Model

```text
OpenShift Integrated OAuth Server
        |
        | OIDC Authorization Code Flow
        v
Keycloak / Red Hat SSO / Red Hat build of Keycloak
        |
        | LDAP federation / Identity brokering
        v
AD / LDAP / IdM / External Corporate IdP
```

Use this design when:

- You want production support.
- You want OpenShift web console login through Keycloak.
- You want `oc login` through OpenShift token flow.
- You want OpenShift RBAC to remain the authorization control plane.
- You need multiple identity providers in OpenShift.

### 5.2 Direct External OIDC Authentication

Newer OpenShift releases also document direct authentication with an external OIDC provider, where the external provider issues tokens directly and bypasses or replaces the built-in OAuth server.

As of OpenShift 4.19 documentation, direct external OIDC authentication is Technology Preview and not recommended by Red Hat for production SLA-backed environments. It also has important operational caveats, such as currently allowing only one direct OIDC provider and requiring a long-lived emergency admin access method before switching.

For enterprise production design, use integrated OpenShift OAuth with OIDC unless your architecture specifically requires direct OIDC and your organization accepts Technology Preview limitations.

## 7. Key OpenShift OIDC Requirements

OpenShift OIDC integration requires:

1. The OIDC provider must implement OIDC Discovery.
2. The issuer must use HTTPS.
3. The issuer URL must not include a query string or fragment.
4. OpenShift must trust the TLS certificate of the Keycloak endpoint.
5. The Keycloak client must allow the OpenShift OAuth callback redirect URI.
6. OpenShift stores the client secret in a Secret in the `openshift-config` namespace.
7. Any custom CA bundle is stored in a ConfigMap in the `openshift-config` namespace using key `ca.crt`.
8. Claims must be available in the ID token or UserInfo response.
9. Usernames must not contain `/`, `:`, or `%`.
10. RBAC must be configured after authentication is working.

## 11. Keycloak / Red Hat SSO Configuration

### 11.1 Create Realm

In Keycloak Admin Console:

```text
Realm name: openshift
```

Avoid using the `master` realm for OpenShift production login. Use a dedicated realm per environment or security boundary.

Recommended realm examples:

```text
openshift-prod
openshift-nonprod
openshift-dr
ocp-platform
```

### 11.2 Configure Realm URL

The issuer URL must match exactly what OpenShift sees:

```text
https://sso.example.com/realms/openshift
```

Check the OIDC discovery endpoint:

```bash
curl -k https://sso.example.com/realms/openshift/.well-known/openid-configuration | jq .
```

Important fields:

```text
issuer
authorization_endpoint
token_endpoint
userinfo_endpoint
jwks_uri
end_session_endpoint
```

The `issuer` value returned by discovery must match the issuer configured in OpenShift.

### 11.3 Create OIDC Client

In Keycloak:

```text
Clients -> Create client
Client type: OpenID Connect
Client ID: openshift
Name: OpenShift OAuth
```

Recommended client settings:

```text
Client authentication: ON
Authorization: OFF unless specifically needed
Standard flow: ON
Direct access grants: OFF by default
Implicit flow: OFF
Service accounts: OFF unless needed for automation
```

For production, use Authorization Code Flow. Avoid implicit flow.

### 11.4 Configure Redirect URI

In Keycloak client settings:

```text
Valid redirect URIs:
https://oauth-openshift.apps.ocp4.example.com/oauth2callback/keycloak
```

For lab only, you might use a wildcard temporarily:

```text
https://oauth-openshift.apps.ocp4.example.com/*
```

Do not use broad wildcards in production because redirect URI misconfiguration can create open redirect risk.

### 11.5 Configure Web Origins

Recommended:

```text
Web origins:
https://oauth-openshift.apps.ocp4.example.com
```

For troubleshooting only:

```text
+
```

In production, prefer explicit origins.

### 11.6 Copy Client Secret

In Keycloak:

```text
Clients -> openshift -> Credentials -> Client secret
```

Save securely. This is the secret OpenShift uses to authenticate to Keycloak.

## 12. Keycloak Claims and Mappers

OpenShift reads standard claims such as:

```text
sub
preferred_username
email
name
groups
```

### 12.1 Recommended Claim Strategy

| Purpose | Recommended claim |
|---|---|
| Stable identity | `sub` |
| OpenShift username | `preferred_username`, fallback `email` |
| Display name | `name` |
| Email | `email` |
| Group sync | `groups` |

Important:

- `sub` is stable and should not change when username or email changes.
- `preferred_username` is human-readable and usually becomes the OpenShift username.
- `groups` enables group-based RBAC if emitted correctly.

### 12.2 Create Group Claim Mapper

In Keycloak client:

```text
Clients -> openshift -> Client scopes / Mappers
```

Create mapper:

```text
Mapper type: Group Membership
Name: groups
Token Claim Name: groups
Claim JSON Type: String
Add to ID token: ON
Add to access token: ON
Add to userinfo: ON
Full group path: depends on RBAC design
```

Group claim examples:

Full path enabled:

```json
{
  "groups": ["/openshift-admins", "/dev/team-a", "/dev/team-b"]
}
```

Full path disabled:

```json
{
  "groups": ["openshift-admins", "team-a", "team-b"]
}
```

For OpenShift RBAC, simpler group names are often easier:

```text
ocp-cluster-admins
ocp-project-admins
ocp-developers
ocp-viewers
```

### 12.3 Group Naming Best Practices

Use clear, cluster-aware groups:

```text
ocp-prod-cluster-admins
ocp-prod-platform-admins
ocp-prod-dev-team-a-admins
ocp-prod-dev-team-a-edit
ocp-prod-dev-team-a-view
ocp-nonprod-cluster-admins
```

Avoid vague names:

```text
admins
users
developers
team1
```

In enterprises, group naming should answer:

```text
Which cluster?
Which environment?
Which team?
Which access level?
```

## 13. OpenShift Configuration

### 13.1 Create Client Secret in OpenShift

```bash
oc create secret generic keycloak-client-secret \
  --from-literal=clientSecret='<KEYCLOAK_CLIENT_SECRET>' \
  -n openshift-config
```

Verify:

```bash
oc get secret keycloak-client-secret -n openshift-config
```

The key must be named:

```text
clientSecret
```

### 13.2 Create CA ConfigMap if Keycloak Uses Private CA

If Keycloak uses a private/internal CA:

```bash
oc create configmap keycloak-ca \
  --from-file=ca.crt=/path/to/keycloak-ca.crt \
  -n openshift-config
```

Verify:

```bash
oc get configmap keycloak-ca -n openshift-config -o yaml
```

The CA key must be:

```text
ca.crt
```

If Keycloak uses a publicly trusted certificate, the custom CA configmap might not be needed.

### 13.3 Create OAuth OIDC Configuration

Create file:

```bash
vi oauth-keycloak.yaml
```

Content:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: keycloak
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift
      clientSecret:
        name: keycloak-client-secret
      ca:
        name: keycloak-ca
      extraScopes:
      - email
      - profile
      - groups
      claims:
        preferredUsername:
        - preferred_username
        - email
        name:
        - name
        email:
        - email
        groups:
        - groups
      issuer: https://sso.example.com/realms/openshift
```

Apply:

```bash
oc apply -f oauth-keycloak.yaml
```

Monitor:

```bash
watch 'oc get co authentication oauth-apiserver console'
oc get pods -n openshift-authentication
oc get pods -n openshift-authentication-operator
```

### 13.4 If Existing Identity Providers Already Exist

Do not overwrite existing OAuth identity providers blindly.

Backup first:

```bash
oc get oauth cluster -o yaml > oauth-before-keycloak.yaml
```

View existing providers:

```bash
oc get oauth cluster -o jsonpath='{.spec.identityProviders[*].name}{"\n"}'
```

If `htpasswd` or LDAP provider already exists, merge the new `keycloak` provider into the existing `identityProviders` list instead of replacing the whole list.

## 14. Mapping Method Deep Dive

OpenShift supports mapping methods that control how external identities map to OpenShift users.

### 14.1 `claim`

```yaml
mappingMethod: claim
```

Behavior:

- Provisions a user using the preferred username from the identity provider.
- Fails if that username is already mapped to another identity.
- Safest default for most environments.

Use when:

- You want predictable user creation.
- You want to avoid accidental account linking.
- You have clean unique usernames.

### 14.2 `lookup`

```yaml
mappingMethod: lookup
```

Behavior:

- Only allows login for identities/users that already exist and are mapped.
- Does not automatically provision users.

Use when:

- You want strict pre-provisioning.
- You have a controlled regulated environment.
- You automate identity creation separately.

### 14.3 `add`

```yaml
mappingMethod: add
```

Behavior:

- Provisions user and may add identity mappings to an existing user.

Use carefully because it can link multiple identities to one OpenShift user if names match.

### 14.4 `generate`

```yaml
mappingMethod: generate
```

Behavior:

- Provisions a user and generates a unique name if there is a conflict.

Use rarely in enterprise because generated usernames can become confusing.

### 14.5 Recommendation

For Keycloak enterprise integration:

```yaml
mappingMethod: claim
```

For highly controlled environments:

```yaml
mappingMethod: lookup
```

## 15. RBAC Integration

Authentication only proves who the user is. Authorization decides what the user can do.

### 15.1 Verify User After Login

After a test user logs in:

```bash
oc get users
oc get identities
oc describe user <username>
oc get groups
```

Example:

```bash
oc describe user rakesh
```

You should see identity mapping similar to:

```text
Identities: keycloak:<external-sub-or-identity>
Groups:     ocp-platform-admins, ocp-developers
```

### 15.2 Bind Cluster Admin Role to Keycloak Group

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-prod-cluster-admins
```

Verify:

```bash
oc get clusterrolebinding | grep ocp-prod-cluster-admins
oc adm policy who-can '*' '*'
```

### 15.3 Bind Project Admin Role

```bash
oc new-project app-team-a
oc adm policy add-role-to-group admin ocp-team-a-admins -n app-team-a
```

### 15.4 Bind Edit Role

```bash
oc adm policy add-role-to-group edit ocp-team-a-edit -n app-team-a
```

### 15.5 Bind View Role

```bash
oc adm policy add-role-to-group view ocp-team-a-view -n app-team-a
```

### 15.6 Recommended RBAC Model

| Group | Role | Scope |
|---|---|---|
| `ocp-prod-cluster-admins` | `cluster-admin` | Cluster |
| `ocp-prod-platform-admins` | Custom platform admin role | Cluster or selected namespaces |
| `ocp-team-a-admins` | `admin` | Team namespace |
| `ocp-team-a-edit` | `edit` | Team namespace |
| `ocp-team-a-view` | `view` | Team namespace |
| `ocp-auditors` | `view` or custom read-only | Cluster / selected namespaces |

Avoid giving `cluster-admin` to individuals. Bind to groups and manage group membership in Keycloak / AD.

## 16. Group Synchronization Behavior

When using OIDC group claims, OpenShift can synchronize groups from the token at login time.

Important points:

1. The groups must be present in the ID token or UserInfo response.
2. OpenShift reads the first non-empty configured group claim.
3. Group membership changes may require user re-login to refresh token claims.
4. Existing OpenShift group objects may not instantly reflect external changes until authentication occurs.
5. For strict enterprise lifecycle management, some organizations use LDAP group sync or external automation instead of depending only on login-time OIDC group claims.

Recommended validation:

```bash
oc get groups
oc describe group ocp-prod-cluster-admins
oc describe user <username>
```

## 19. Troubleshooting Deep Dive

## 19.1 Login Page Does Not Show Keycloak Provider

Symptoms:

```text
OpenShift console login page does not show the new provider.
```

Check:

```bash
oc get oauth cluster -o yaml
oc get co authentication
oc describe co authentication
oc get pods -n openshift-authentication
```

Possible causes:

- OAuth CR not applied.
- YAML indentation issue.
- Authentication operator degraded.
- Secret/configmap missing.
- Invalid OAuth schema.

Fix:

```bash
oc apply -f oauth-keycloak.yaml
oc get co authentication -w
```

---

## 19.2 Authentication Operator Degraded

Check:

```bash
oc describe co authentication
oc logs -n openshift-authentication-operator deploy/authentication-operator
oc logs -n openshift-authentication deploy/oauth-openshift
```

Common reasons:

- Secret key is not named `clientSecret`.
- Secret is not in `openshift-config` namespace.
- CA configmap missing `ca.crt` key.
- Issuer URL is wrong.
- Keycloak certificate is not trusted.
- Keycloak discovery endpoint unreachable.

---

## 19.3 `invalid_redirect_uri`

Symptoms:

```text
Keycloak error: invalid_redirect_uri
```

Check OpenShift callback URL:

```bash
OAUTH_HOST=$(oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}')
echo "https://${OAUTH_HOST}/oauth2callback/keycloak"
```

Verify Keycloak client has exactly this Valid Redirect URI:

```text
https://oauth-openshift.apps.ocp4.example.com/oauth2callback/keycloak
```

Common causes:

- Wrong identity provider name.
- Redirect URI uses wrong cluster domain.
- HTTP instead of HTTPS.
- Extra trailing slash.
- Wildcard not matching.
- OAuth route changed after cluster route/domain change.

---

## 19.4 Issuer Mismatch

Symptoms:

```text
OIDC discovery works but OpenShift rejects login.
```

Check issuer from Keycloak:

```bash
curl -s https://sso.example.com/realms/openshift/.well-known/openid-configuration | jq -r .issuer
```

Check OpenShift configured issuer:

```bash
oc get oauth cluster -o jsonpath='{.spec.identityProviders[?(@.name=="keycloak")].openID.issuer}{"\n"}'
```

They must match exactly:

```text
https://sso.example.com/realms/openshift
```

Common mismatch examples:

```text
https://sso.example.com/auth/realms/openshift
https://sso.example.com/realms/openshift/
http://sso.example.com/realms/openshift
https://internal-sso.example.local/realms/openshift
```

---

## 19.5 TLS / CA Trust Failure

Symptoms:

```text
x509: certificate signed by unknown authority
certificate is valid for X, not Y
```

Check certificate:

```bash
openssl s_client -connect sso.example.com:443 -servername sso.example.com -showcerts </dev/null
```

If internal CA is used:

```bash
oc create configmap keycloak-ca \
  --from-file=ca.crt=/path/to/ca-chain.pem \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

Ensure OAuth references it:

```yaml
openID:
  ca:
    name: keycloak-ca
```

## 19.6 User Logs In But Has No Access

Symptoms:

```text
Login successful, but user cannot view projects or resources.
```

This is an RBAC issue, not an authentication issue.

Check user:

```bash
oc whoami
oc describe user <username>
oc get groups
```

Check permissions:

```bash
oc auth can-i get projects --as=<username>
oc auth can-i get pods -n app-team-a --as=<username>
```

Fix by binding role:

```bash
oc adm policy add-role-to-group view ocp-team-a-view -n app-team-a
```

Or for cluster admin group:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-prod-cluster-admins
```

## 19.7 Group Claim Not Appearing

Symptoms:

```text
User logs in but OpenShift group membership is empty.
```

Check Keycloak token claims.

Use Keycloak token endpoint for testing if direct grant is enabled in lab:

```bash
curl -s -X POST "https://sso.example.com/realms/openshift/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "client_id=openshift" \
  -d "client_secret=<secret>" \
  -d "grant_type=password" \
  -d "username=<user>" \
  -d "password=<password>" | jq .
```

Decode ID token:

```bash
TOKEN='<id_token>'
echo "$TOKEN" | cut -d. -f2 | base64 -d 2>/dev/null | jq .
```

Check for:

```json
"groups": ["ocp-team-a-view"]
```

If missing:

- Add group mapper in Keycloak.
- Ensure mapper adds groups to ID token or UserInfo.
- Ensure OpenShift OAuth has `groups: [groups]` claim mapping.
- Re-login after mapper change.

## 19.8 Username Contains Unsupported Characters

OpenShift usernames containing `/`, `:`, and `%` are not supported.

If Keycloak emits username values like:

```text
DOMAIN/user
user:domain
user%domain
```

Fix by changing the preferred username mapper. Preferred safe values:

```text
sAMAccountName
uid
employeeID
email without unsupported characters
```

In OpenShift OAuth, fallback claim order can help:

```yaml
claims:
  preferredUsername:
  - preferred_username
  - email
```

But ensure the selected claim does not contain unsupported characters.

```bash
oc describe user <username>
```

## 19.10 Old Group Membership Still Effective

Possible causes:

- User session/token not refreshed.
- Group claim changed but user did not log out/in.
- OpenShift group object still contains old membership.
- External automation or LDAP group sync is also managing groups.

Actions:


Ask user to log out and login again.

## 20. Security Best Practices

### 20.1 Use HTTPS Everywhere

Keycloak issuer must use HTTPS. Use trusted certificates. Avoid `-k` except for troubleshooting.

### 20.2 Restrict Redirect URIs

Use exact redirect URI:

```text
https://oauth-openshift.apps.ocp4.example.com/oauth2callback/keycloak
```

Avoid broad wildcards in production.

### 20.3 Protect Client Secret

The OpenShift client secret is sensitive.

```bash
oc get secret keycloak-client-secret -n openshift-config -o yaml
```

Limit who can read secrets in `openshift-config`.

### 20.4 Use Group-Based RBAC

Prefer:

```bash
oc adm policy add-role-to-group edit ocp-team-a-edit -n app-team-a
```

Avoid:

```bash
oc adm policy add-role-to-user edit user1 -n app-team-a
```

User-based bindings are harder to audit and maintain.

### 20.5 Do Not Remove kubeadmin Too Early

Only remove emergency kubeadmin after:

1. Keycloak login works.
2. At least one external user has `cluster-admin`.
3. Break-glass access is documented.
4. Multiple admins have tested CLI and console login.

### 20.6 Enable MFA in Keycloak

For cluster-admin groups, enforce MFA or conditional access.

Recommended policies:

```text
MFA required for cluster-admins
MFA required for production clusters
Stronger policy for external access
Session timeout aligned with company security policy
```

### 20.7 Audit Regularly

Regular checks:

```bash
oc get clusterrolebinding -o wide
oc get rolebinding -A -o wide
oc get users
oc get groups
```

Review Keycloak:

```text
Admin events
Login events
Client secret rotation
Group membership changes
MFA status
Identity provider changes
```

## 22. Break-Glass Access Design

Every enterprise OpenShift cluster must have emergency access in case SSO fails.

Options:

1. Keep `kubeadmin` until replacement admin access is validated.
2. Maintain certificate-based admin kubeconfig in a secure vault.
3. Use a restricted emergency `htpasswd` provider.
4. Use a long-lived service account token kubeconfig where allowed by policy.

Minimum operational rule:

```text
Never depend on a single external IdP without documented emergency access.
```

Before disabling `kubeadmin`:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-prod-cluster-admins
```

Test as external admin:

```bash
oc auth can-i '*' '*' --all-namespaces
```

Only then consider:

```bash
oc delete secret kubeadmin -n kube-system
```

Warning: Removing kubeadmin before another cluster-admin exists can lock you out.

## 23. Multi-Cluster Enterprise Design

In large companies, you might have many clusters:

```text
ocp-prod-1
ocp-prod-2
ocp-nonprod-1
ocp-dr-1
ocp-edge-1
```

Design options:

### Option A: One Keycloak Realm Per Environment

```text
realm: openshift-prod
realm: openshift-nonprod
realm: openshift-dr
```

Pros:

- Strong separation
- Different policies per environment
- Easier production isolation

Cons:

- More objects to manage
- More client duplication

### Option B: One Realm, One Client Per Cluster

```text
realm: openshift
clients:
  openshift-prod-1
  openshift-prod-2
  openshift-nonprod-1
```

Pros:

- Centralized management
- Easier SSO
- Common user/group model

Cons:

- Strong governance required
- Mistakes can affect many clusters

### Option C: Central Corporate IdP -> Keycloak Broker -> OpenShift

```text
Corporate IdP / AD FS / Entra ID / SAML
        |
        v
Keycloak Identity Broker
        |
        v
Multiple OpenShift clusters
```

Pros:

- Flexible integration
- Keycloak transforms claims
- OpenShift sees consistent OIDC

Cons:

- More moving parts
- Troubleshooting requires IdP + Keycloak + OpenShift knowledge

## 27. Common Interview Scenario Questions and Senior-Level Answers

### Q1. How does OpenShift integrate with Keycloak using OIDC?

OpenShift registers as an OIDC client in Keycloak. The OpenShift OAuth server redirects users to Keycloak through Authorization Code Flow. After authentication, Keycloak returns an authorization code to OpenShift callback URL. OpenShift exchanges the code for tokens, validates claims, maps the external identity to an OpenShift user, optionally synchronizes groups, and then uses RBAC for authorization.

### Q2. What is the redirect URI for OpenShift OIDC integration?

It is:

```text
https://oauth-openshift.apps.<cluster-name>.<cluster-domain>/oauth2callback/<idp-provider-name>
```

Example:

```text
https://oauth-openshift.apps.ocp4.example.com/oauth2callback/keycloak
```

The `<idp-provider-name>` must match the `name` field in the OpenShift OAuth identity provider configuration.

### Q3. What is the issuer URL for Keycloak?

For modern Keycloak / Red Hat build of Keycloak:

```text
https://<keycloak-host>/realms/<realm-name>
```

Example:

```text
https://sso.example.com/realms/openshift
```

Validate it from:

```bash
curl -s https://sso.example.com/realms/openshift/.well-known/openid-configuration | jq -r .issuer
```

### Q4. Why does a user login successfully but cannot access projects?

Authentication succeeded, but authorization is missing. OpenShift access is controlled by RBAC. The user or the user's group must be bound to a role such as `view`, `edit`, `admin`, or `cluster-admin`.

Check:

```bash
oc auth can-i get pods -n app1 --as=<username>
oc describe user <username>
oc get groups
```

Fix:

```bash
oc adm policy add-role-to-group view <group> -n <namespace>
```

### Q5. Why are Keycloak groups not visible in OpenShift?

Common reasons:

- Keycloak group mapper not configured.
- Mapper does not add groups to ID token or UserInfo.
- OpenShift OAuth `claims.groups` does not include the correct claim name.
- User has not re-authenticated after group change.
- Group names are full paths but RBAC bindings expect simple names.

### Q6. Should I bind RBAC to users or groups?

Use groups. User-based RBAC is difficult to audit and maintain. Enterprise RBAC should bind OpenShift roles to groups managed in Keycloak/AD.

### Q7. Can I remove kubeadmin after configuring Keycloak?

Only after confirming another user or group has `cluster-admin` and emergency access is documented. Removing kubeadmin too early can lock administrators out.

### Q8. What is the difference between Keycloak and Red Hat SSO?

Keycloak is the upstream open-source identity and access management project. Red Hat Single Sign-On was Red Hat's supported product based on Keycloak. Newer Red Hat documentation uses Red Hat build of Keycloak. In OpenShift OIDC integration, the operational concepts are similar: realm, client, issuer, redirect URI, claims, groups, and client secret.

### Q9. What is the most common cause of `invalid_redirect_uri`?

The redirect URI configured in Keycloak does not exactly match the URI OpenShift sends. Check the OAuth route and provider name.

```bash
OAUTH_HOST=$(oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}')
echo "https://${OAUTH_HOST}/oauth2callback/keycloak"
```

### Q10. Is direct external OIDC recommended for production?

For OpenShift 4.19, direct external OIDC authentication is documented as Technology Preview. For production, the safer default is the integrated OpenShift OAuth server with Keycloak as an OIDC identity provider.

## 29. Common Error Matrix

| Error / Symptom | Likely Cause | Fix |
|---|---|---|
| Provider not visible on login page | OAuth CR not applied or authentication operator degraded | Check `oc get oauth cluster`, `oc describe co authentication` |
| `invalid_redirect_uri` | Keycloak redirect URI mismatch | Configure exact `/oauth2callback/<provider-name>` URI |
| `x509 unknown authority` | Keycloak cert signed by private CA | Add CA configmap in `openshift-config` and reference it in OAuth |
| Issuer mismatch | OpenShift issuer differs from discovery issuer | Configure issuer exactly as `.well-known` returns |
| User logs in but sees no projects | RBAC missing | Bind role to group/user |
| Groups missing | Keycloak mapper missing or OpenShift claim mismatch | Add `groups` mapper and OAuth claim mapping |
| CLI username/password login fails | OIDC provider does not support ROPC or direct grants disabled | Use web token login flow |
| Authentication operator degraded | Invalid Secret/ConfigMap/OAuth spec | Check operator logs and referenced objects |
| User conflict | Same username already mapped to another identity | Review `mappingMethod` and identities |
| Lockout after removing kubeadmin | No working cluster-admin external identity | Use break-glass kubeconfig or restore access |

## 31. Real-World Design Recommendations for 10+ Years Experience

1. Do not treat SSO as only a login setup. Treat it as identity lifecycle, RBAC, audit, break-glass, and compliance design.
2. Keep OpenShift RBAC separate from Keycloak roles unless there is a clear mapping strategy.
3. Prefer group claims for authorization, not individual user bindings.
4. Use stable identity values. Avoid username formats that change when email/name changes.
5. Use exact redirect URIs.
6. Use trusted TLS with proper SAN and CA chain.
7. Keep emergency admin access outside the external SSO dependency.
8. Test with normal user, namespace admin, project viewer, and cluster admin personas.
9. Document group-to-role mapping before onboarding teams.
10. Rotate client secrets periodically and test the rotation plan.
11. Monitor authentication operator health after each change.
12. Keep Keycloak high availability aligned with OpenShift criticality.
13. For production, do not use Technology Preview direct external OIDC unless formally approved.
14. In multi-cluster setups, standardize realm/client/group naming.
15. Include SSO in disaster recovery and incident response plans.
