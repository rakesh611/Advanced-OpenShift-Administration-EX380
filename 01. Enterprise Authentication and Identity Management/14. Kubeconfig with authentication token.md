# Kubeconfig with Authentication Token in OpenShift

**Area:** Enterprise Authentication and Identity Management  
**Level:** Advanced OpenShift Administration  
**Audience:** Senior Linux / Kubernetes / OpenShift administrators with 10+ years of infrastructure experience  
**Scope:** Token-based kubeconfig usage, OpenShift OAuth tokens, service account tokens, RBAC impact, security, troubleshooting, and production patterns.

---

## 1. Executive Summary

A **kubeconfig** file is the client-side configuration used by `oc`, `kubectl`, automation scripts, CI/CD tools, GitOps controllers, and Kubernetes client libraries to connect to an OpenShift API server.

In OpenShift, when a user logs in with `oc login`, the CLI stores connection and authentication details in kubeconfig. For normal user login, the credential is commonly an **OpenShift OAuth access token** stored under the `users` section.

A token-based kubeconfig usually contains:

```text
cluster endpoint + API server CA + token + context + default namespace
```

High-level flow:

```text
User / Automation
      |
      | oc / kubectl reads kubeconfig
      v
~/.kube/config or custom kubeconfig
      |
      | server + CA + token + context
      v
OpenShift API Server
      |
      | token validation
      v
OpenShift authentication layer / OAuth / service account validation
      |
      | RBAC authorization
      v
API request allowed or denied
```

A kubeconfig containing a valid token must be treated as a **secret credential file**. Anyone who can read it can usually act as that user or service account until the token expires or is revoked.

---

## 2. What Is a Kubeconfig?

A kubeconfig is a YAML configuration file that tells Kubernetes/OpenShift clients:

1. Which API server to contact.
2. How to validate the API server certificate.
3. Which user credential to use.
4. Which namespace/project to use by default.
5. Which context is active.

Default location:

```bash
~/.kube/config
```

Use another file:

```bash
oc --kubeconfig=/path/to/kubeconfig get pods -A
kubectl --kubeconfig=/path/to/kubeconfig get nodes
```

Use environment variable:

```bash
export KUBECONFIG=/path/to/kubeconfig
oc get nodes
```

Merge multiple files:

```bash
export KUBECONFIG=$HOME/.kube/config:$HOME/.kube/prod:$HOME/.kube/dr
```

On Windows PowerShell:

```powershell
$env:KUBECONFIG="$HOME\.kube\config;$HOME\.kube\prod;$HOME\.kube\dr"
```

## 3. Kubeconfig Structure

Typical kubeconfig skeleton:

```yaml
apiVersion: v1
kind: Config
clusters: []
users: []
contexts: []
current-context: ""
preferences: {}
```

### 3.1 `clusters`

The `clusters` section defines API server connection details.

```yaml
clusters:
- name: prod-api
  cluster:
    server: https://api.prod.example.com:6443
    certificate-authority-data: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0t...
```

Important fields:

| Field | Meaning |
|---|---|
| `server` | API server endpoint, normally `https://api.<cluster-domain>:6443` |
| `certificate-authority` | Local path to CA certificate file |
| `certificate-authority-data` | Base64-encoded CA certificate embedded in kubeconfig |
| `insecure-skip-tls-verify` | Disables TLS verification; avoid in production |

Production recommendation:

```text
Use certificate-authority-data or certificate-authority.
Avoid insecure-skip-tls-verify except for temporary lab troubleshooting.
```

---

### 3.2 `users`

The `users` section stores authentication credentials.

Token example:

```yaml
users:
- name: rakesh/prod-api
  user:
    token: REDACTED_TOKEN_VALUE
```

Common authentication methods:

| Method | Use Case |
|---|---|
| `token` | OAuth token or service account token |
| `client-certificate-data` and `client-key-data` | Certificate-based authentication |
| `exec` | External OIDC/cloud plugin authentication |
| `auth-provider` | Older plugin model, mostly replaced by `exec` |

This note focuses on the `token` field.

---

### 3.3 `contexts`

A context links a cluster, user, and namespace.

```yaml
contexts:
- name: app-dev/prod-api/rakesh
  context:
    cluster: prod-api
    user: rakesh/prod-api
    namespace: app-dev
```

Meaning:

```text
Use user rakesh/prod-api
against cluster prod-api
with default namespace app-dev
```

---

### 3.4 `current-context`

The active context is selected by `current-context`.

```yaml
current-context: app-dev/prod-api/rakesh
```

Check current context:

```bash
oc config current-context
oc whoami -c
```

List contexts:

```bash
oc config get-contexts
kubectl config get-contexts
```

Switch context:

```bash
oc config use-context app-prod/prod-api/rakesh
```

Change default namespace in the current context:

```bash
oc config set-context --current --namespace=app-prod
```

Or use OpenShift project command:

```bash
oc project app-prod
```

## 4. Authentication Flow with Token-Based Kubeconfig

When you run:

```bash
oc get pods -n app-dev
```

The client does this internally:

```text
1. Reads kubeconfig.
2. Finds current-context.
3. Finds cluster endpoint and CA certificate.
4. Finds user token.
5. Sends HTTPS request to API server.
6. Adds HTTP header:

   Authorization: Bearer <token>

7. API server validates the token.
8. Request is mapped to a user or service account identity.
9. RBAC checks whether the identity can perform the requested action.
10. API server returns success, 401 Unauthorized, or 403 Forbidden.
```

Important difference:

```text
Authentication = Who are you?
Authorization  = What are you allowed to do?
```

A valid token does not automatically mean admin access. Permissions are decided by RBAC.

## 5. Token Types in OpenShift Kubeconfig

OpenShift administrators mainly see these token categories:

1. User OAuth access token.
2. Service account token.
3. Bound service account token.
4. Legacy long-lived service account token secret.

---

### 5.1 User OAuth Access Token

This is normally created during user login.

Interactive login:

```bash
oc login https://api.prod.example.com:6443 -u rakesh
```

Token login:

```bash
oc login https://api.prod.example.com:6443 --token=<TOKEN>
```

After successful login, `oc` stores cluster details, user token, context, and namespace in kubeconfig.

Useful commands:

```bash
oc whoami
oc whoami -t
oc whoami --show-server
oc whoami -c
oc config view
oc config view --raw
```

`oc whoami -t` shows the active token. Be careful with this command because it exposes the credential.

A user OAuth token is associated with:

```text
OpenShift OAuth server
Configured identity provider
OpenShift user object
Identity object
OAuth client
Token expiry and inactivity timeout
RBAC roles and bindings
```

Supported identity provider examples include HTPasswd, LDAP, OIDC, GitHub, GitLab, Google, Keystone, request-header, and basic authentication.

---

### 5.2 Service Account Token

A service account token is used by workloads or automation instead of a human user.

Service account identity format:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

Example:

```text
system:serviceaccount:cicd:deploy-bot
```

Create service account:

```bash
oc new-project cicd
oc create serviceaccount deploy-bot -n cicd
```

Grant limited permission to deploy into one namespace:

```bash
oc adm policy add-role-to-user edit \
  system:serviceaccount:cicd:deploy-bot \
  -n app-dev
```

Short form:

```bash
oc adm policy add-role-to-user edit -z deploy-bot -n app-dev
```

Create token:

```bash
oc create token deploy-bot -n cicd
```

Use in a shell variable:

```bash
TOKEN=$(oc create token deploy-bot -n cicd)
```

Service account tokens are preferred for:

- CI/CD pipelines
- GitOps controllers
- Monitoring integrations
- Backup tools
- External scripts
- Automation platforms such as Ansible Automation Platform

Never use a personal human admin token for long-running automation.

---

### 5.3 Bound Service Account Token

A bound service account token is a modern service account token that can be:

- Time-bound
- Audience-bound
- Requested by the TokenRequest API
- Mounted into pods through projected volumes

Concept:

```text
Old long-lived token:
  Persistent credential, high risk if leaked.

Bound token:
  Shorter lifetime, scoped audience, better production security.
```

Create a token:

```bash
oc create token deploy-bot -n cicd
```

If your client version supports duration:

```bash
oc create token deploy-bot -n cicd --duration=1h
```

Example pod projected token:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: api-client
  namespace: cicd
spec:
  serviceAccountName: deploy-bot
  containers:
  - name: client
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
    volumeMounts:
    - name: api-token
      mountPath: /var/run/secrets/tokens
      readOnly: true
  volumes:
  - name: api-token
    projected:
      sources:
      - serviceAccountToken:
          path: token
          expirationSeconds: 3600
          audience: https://kubernetes.default.svc
```

---

### 5.4 Legacy Long-Lived Service Account Token Secret

Older OpenShift/Kubernetes environments often automatically generated long-lived service account token secrets.

Modern OpenShift versions no longer automatically create long-lived service account API token secrets for every new service account. Upgraded clusters might still contain old long-lived token secrets that continue to work.

Example old secret type:

```text
kubernetes.io/service-account-token
```

Check old service account token secrets:

```bash
oc get secret -A | grep service-account-token
```

Avoid creating new long-lived tokens unless a legacy integration absolutely requires them.

If you must create one, document the exception, restrict RBAC, monitor usage, and rotate regularly.

Example manifest:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: deploy-bot-token
  namespace: cicd
  annotations:
    kubernetes.io/service-account.name: deploy-bot
type: kubernetes.io/service-account-token
```

Apply:

```bash
oc apply -f deploy-bot-token-secret.yaml
```

Extract token:

```bash
oc get secret deploy-bot-token -n cicd \
  -o jsonpath='{.data.token}' | base64 -d
```

Prefer short-lived/bound tokens instead.

## 6. How `oc login` Builds Kubeconfig

Basic login:

```bash
oc login https://api.cluster.example.com:6443 -u rakesh
```

Flow:

```text
1. User contacts API/OAuth endpoint.
2. User authenticates through configured identity provider.
3. OpenShift OAuth server issues access token.
4. oc stores token in kubeconfig.
5. oc creates or updates a context.
6. oc sets current-context.
```

Login with web-console copied command:

```bash
oc login --token=<TOKEN> --server=https://api.cluster.example.com:6443
```

Browser login:

```bash
oc login https://api.cluster.example.com:6443 --web
```

Export full kubeconfig:

```bash
oc config view --raw > kubeconfig
chmod 600 kubeconfig
```

Use exported kubeconfig:

```bash
export KUBECONFIG=$PWD/kubeconfig
oc get nodes
```

Warning:

```text
oc config view --raw exposes tokens and embedded certificate/key material.
Do not paste its output in tickets, chats, or public notes.
```

## 7. Example Token-Based OpenShift Kubeconfig

```yaml
apiVersion: v1
kind: Config
preferences: {}
clusters:
- name: prod-api
  cluster:
    server: https://api.prod.example.com:6443
    certificate-authority-data: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0t...
users:
- name: rakesh/prod-api
  user:
    token: REDACTED_TOKEN_VALUE
contexts:
- name: app-dev/prod-api/rakesh
  context:
    cluster: prod-api
    user: rakesh/prod-api
    namespace: app-dev
current-context: app-dev/prod-api/rakesh
```

Field meaning:

| Section | Field | Purpose |
|---|---|---|
| `clusters` | `server` | API endpoint |
| `clusters` | `certificate-authority-data` | Trust anchor for API TLS |
| `users` | `token` | Bearer token used for authentication |
| `contexts` | `cluster` | Cluster entry to use |
| `contexts` | `user` | User credential entry to use |
| `contexts` | `namespace` | Default namespace/project |
| `current-context` | value | Active context used by default |

## 8. Manually Creating a Kubeconfig with Token

This is useful for CI/CD, read-only integrations, break-glass files, and external automation.

### 8.1 Required Inputs

```bash
API_SERVER="https://api.prod.example.com:6443"
CLUSTER_NAME="prod-api"
USER_NAME="deploy-bot"
CONTEXT_NAME="deploy-bot-prod"
NAMESPACE="app-dev"
KUBECONFIG_FILE="./deploy-bot.kubeconfig"
TOKEN="<TOKEN>"
CA_FILE="./ca.crt"
```

### 8.2 Set Cluster

```bash
oc config set-cluster "$CLUSTER_NAME" \
  --server="$API_SERVER" \
  --certificate-authority="$CA_FILE" \
  --embed-certs=true \
  --kubeconfig="$KUBECONFIG_FILE"
```

### 8.3 Set User Token

```bash
oc config set-credentials "$USER_NAME" \
  --token="$TOKEN" \
  --kubeconfig="$KUBECONFIG_FILE"
```

### 8.4 Set Context

```bash
oc config set-context "$CONTEXT_NAME" \
  --cluster="$CLUSTER_NAME" \
  --user="$USER_NAME" \
  --namespace="$NAMESPACE" \
  --kubeconfig="$KUBECONFIG_FILE"
```

### 8.5 Use Context

```bash
oc config use-context "$CONTEXT_NAME" \
  --kubeconfig="$KUBECONFIG_FILE"
```

### 8.6 Secure and Test

```bash
chmod 600 "$KUBECONFIG_FILE"

oc --kubeconfig="$KUBECONFIG_FILE" whoami
oc --kubeconfig="$KUBECONFIG_FILE" get pods -n "$NAMESPACE"
oc --kubeconfig="$KUBECONFIG_FILE" auth can-i get pods -n "$NAMESPACE"
```

## 9. Creating a Service Account Kubeconfig for CI/CD

Scenario:

```text
A pipeline must deploy into app-dev namespace only.
It must not have cluster-admin.
It must not access other namespaces.
```

### 9.1 Create Service Account

```bash
oc new-project cicd
oc create serviceaccount deploy-bot -n cicd
```

### 9.2 Grant Namespace-Scoped Permission

```bash
oc adm policy add-role-to-user edit \
  system:serviceaccount:cicd:deploy-bot \
  -n app-dev
```

Validate binding:

```bash
oc get rolebinding -n app-dev | grep deploy-bot
```

### 9.3 Generate Token

```bash
TOKEN=$(oc create token deploy-bot -n cicd)
```

### 9.4 Get API Server and CA Data

```bash
API_SERVER=$(oc whoami --show-server)
CA_DATA=$(oc config view --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')
```

### 9.5 Build Kubeconfig

Use a here-doc delimiter that does not conflict with inner documentation.

```bash
cat > deploy-bot.kubeconfig <<KUBECONFIG_EOF
apiVersion: v1
kind: Config
clusters:
- name: prod-api
  cluster:
    server: ${API_SERVER}
    certificate-authority-data: ${CA_DATA}
users:
- name: deploy-bot
  user:
    token: ${TOKEN}
contexts:
- name: deploy-bot-prod
  context:
    cluster: prod-api
    user: deploy-bot
    namespace: app-dev
current-context: deploy-bot-prod
preferences: {}
KUBECONFIG_EOF

chmod 600 deploy-bot.kubeconfig
```

### 9.6 Validate

```bash
oc --kubeconfig=deploy-bot.kubeconfig whoami
oc --kubeconfig=deploy-bot.kubeconfig get pods -n app-dev
oc --kubeconfig=deploy-bot.kubeconfig auth can-i create deployment -n app-dev
oc --kubeconfig=deploy-bot.kubeconfig auth can-i get nodes
```

Good expected result:

```text
Can create deployment in app-dev: yes
Can get nodes: no
```

## 10. Authentication vs Authorization

Token authentication tells OpenShift:

```text
Who is making the request?
```

RBAC authorization decides:

```text
Can that identity perform this action?
```

Example request:

```bash
oc get pods -n app-dev
```

OpenShift evaluates roughly:

```text
identity: system:serviceaccount:cicd:deploy-bot
verb: get/list
resource: pods
namespace: app-dev
```

Check as service account:

```bash
oc auth can-i get pods -n app-dev \
  --as=system:serviceaccount:cicd:deploy-bot
```

Check dangerous permission:

```bash
oc auth can-i '*' '*' -A \
  --as=system:serviceaccount:cicd:deploy-bot
```

Failure difference:

| Error | Meaning | Layer |
|---|---|---|
| `401 Unauthorized` | Token is missing, invalid, expired, revoked, or not accepted | Authentication |
| `403 Forbidden` | Token is valid, but RBAC denies the action | Authorization |

## 11. User OAuth Token Management

List user-owned OAuth tokens:

```bash
oc get useroauthaccesstokens
```

Describe token details:

```bash
oc describe useroauthaccesstokens <token_name>
```

Useful fields:

```text
Client Name
Expires In
Inactivity Timeout Seconds
Scopes
User Name
Redirect URI
```

Delete a token:

```bash
oc delete useroauthaccesstokens <token_name>
```

Logout current CLI session:

```bash
oc logout
```

Important difference:

```text
oc logout:
  Invalidates/removes the active CLI token.

oc delete useroauthaccesstokens <token_name>:
  Deletes a selected user-owned OAuth token.
```

## 12. Security Best Practices

### 12.1 Treat Kubeconfig as a Secret

Set permissions:

```bash
chmod 600 ~/.kube/config
chmod 600 *.kubeconfig
```

Check:

```bash
ls -l ~/.kube/config
```

Expected:

```text
-rw------- 1 rakesh rakesh ... /home/rakesh/.kube/config
```

Do not store kubeconfig in:

- Git repositories
- Shared folders
- Ticket attachments
- Plain-text emails
- CI logs
- Wiki pages
- Chat tools
- Unencrypted backups

`.gitignore` example:

```gitignore
*.kubeconfig
kubeconfig
.kube/
```

---

### 12.2 Avoid Tokens in Shell History

Risky:

```bash
oc login --token=very-sensitive-token --server=https://api.prod.example.com:6443
```

The token may appear in:

```text
shell history
terminal scrollback
process list
CI logs
session recording
```

Safer:

```bash
oc login https://api.prod.example.com:6443 --web
```

Or read from protected secret storage:

```bash
TOKEN=$(cat /secure/path/token)
oc login https://api.prod.example.com:6443 --token="$TOKEN"
unset TOKEN
```

---

### 12.3 Avoid `insecure-skip-tls-verify`

Bad production pattern:

```yaml
clusters:
- name: prod
  cluster:
    insecure-skip-tls-verify: true
    server: https://api.prod.example.com:6443
```

Risk:

- Disables server certificate validation.
- Allows man-in-the-middle attacks.
- Hides certificate-chain problems.
- Normalizes insecure operations.

Better:

```yaml
clusters:
- name: prod
  cluster:
    server: https://api.prod.example.com:6443
    certificate-authority-data: <BASE64_CA>
```

---

### 12.4 Use Least Privilege

Bad:

```bash
oc adm policy add-cluster-role-to-user cluster-admin \
  system:serviceaccount:cicd:deploy-bot
```

Better:

```bash
oc adm policy add-role-to-user edit \
  system:serviceaccount:cicd:deploy-bot \
  -n app-dev
```

Best for production: custom role.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: cicd-deployer-minimal
  namespace: app-dev
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["services", "configmaps", "secrets"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: ["route.openshift.io"]
  resources: ["routes"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
```

Bind it:

```bash
oc create rolebinding cicd-deployer-minimal-binding \
  --role=cicd-deployer-minimal \
  --serviceaccount=cicd:deploy-bot \
  -n app-dev
```

---

### 12.5 Separate Human and Automation Credentials

Do not use a personal admin kubeconfig in Jenkins, GitLab CI, Argo CD, Ansible Automation Platform, backup jobs, or monitoring integrations.

Recommended model:

| Access Type | Identity |
|---|---|
| Human admin | Named LDAP/OIDC user |
| Developer | Named user or group-based RBAC |
| CI/CD deployment | Dedicated service account |
| GitOps controller | Dedicated service account per controller/scope |
| Monitoring | Read-only service account |
| Backup | Purpose-specific service account |
| Emergency access | Break-glass user with strong controls |

---

### 12.6 Rotate and Revoke

For user OAuth tokens:

```bash
oc get useroauthaccesstokens
oc delete useroauthaccesstokens <token_name>
```

For service account tokens:

- Prefer short-lived tokens.
- Regenerate with `oc create token`.
- Remove unnecessary long-lived token secrets.
- Rotate after staff changes, pipeline compromise, or RBAC changes.

---

### 12.7 CI/CD Storage Rules

In CI/CD:

```text
Store kubeconfig as a protected secret.
Mask token values.
Do not echo kubeconfig.
Do not run set -x around secrets.
Restrict secret use to protected branches/environments.
Use separate kubeconfigs per environment.
Rotate after any suspected exposure.
```

Bad pipeline pattern:

```bash
cat $KUBECONFIG
oc config view --raw
```

Better:

```bash
oc --kubeconfig="$KUBECONFIG_FILE" auth can-i create deployment -n app-dev
oc --kubeconfig="$KUBECONFIG_FILE" apply -f manifests/
```

## 14. Troubleshooting Token-Based Kubeconfig

### 14.1 Error: `You must be logged in to the server`

Possible causes:

- Kubeconfig not found.
- Wrong `KUBECONFIG` path.
- Current context missing.
- Token missing from `users` section.
- Token expired or revoked.

Check:

```bash
echo $KUBECONFIG
oc config current-context
oc config view
oc whoami
```

Fix:

```bash
oc login https://api.cluster.example.com:6443
```

Or select correct file:

```bash
export KUBECONFIG=/path/to/kubeconfig
```

---

### 14.2 Error: `401 Unauthorized`

Meaning:

```text
Authentication failed.
```

Possible causes:

- Invalid token.
- Expired token.
- Token copied incorrectly.
- Token belongs to another cluster.
- Token revoked by logout or token deletion.
- Service account token audience mismatch.
- External OIDC token is not accepted by this API server.

Check:

```bash
oc whoami --kubeconfig=./kubeconfig
oc config view --raw --kubeconfig=./kubeconfig
```

Test token directly:

```bash
TOKEN=$(oc config view --raw -o jsonpath='{.users[0].user.token}')
API=$(oc config view -o jsonpath='{.clusters[0].cluster.server}')

curl -k -H "Authorization: Bearer ${TOKEN}" "${API}/api"
```

Fix:

```bash
oc login https://api.cluster.example.com:6443
```

For service account:

```bash
TOKEN=$(oc create token deploy-bot -n cicd)
```

Then rebuild kubeconfig.

---

### 14.3 Error: `403 Forbidden`

Meaning:

```text
Authentication succeeded, authorization failed.
```

Example:

```text
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:cicd:deploy-bot" cannot list resource "pods" in API group "" in the namespace "app-prod"
```

Check identity:

```bash
oc whoami
```

Check permission:

```bash
oc auth can-i list pods -n app-prod
```

Check as service account:

```bash
oc auth can-i list pods -n app-prod \
  --as=system:serviceaccount:cicd:deploy-bot
```

Fix RBAC carefully:

```bash
oc adm policy add-role-to-user view \
  system:serviceaccount:cicd:deploy-bot \
  -n app-prod
```

Do not blindly grant `cluster-admin`.

---

### 14.4 TLS Certificate Error

Example:

```text
x509: certificate signed by unknown authority
```

Possible causes:

- Missing CA data.
- Wrong CA data.
- API certificate changed.
- Connecting to wrong endpoint.
- Proxy intercepting TLS.

Check:

```bash
oc whoami --show-server
oc config view --raw -o yaml
```

Temporary unsafe lab workaround:

```bash
oc login https://api.cluster.example.com:6443 --insecure-skip-tls-verify=true
```

Production fix:

```bash
oc config set-cluster prod-api \
  --server=https://api.cluster.example.com:6443 \
  --certificate-authority=ca.crt \
  --embed-certs=true
```

Controls:

## 16. Token Exposure Incident Response

If a kubeconfig or token is leaked:

### Step 1: Identify Token Type

Human OAuth token:

```bash
oc get useroauthaccesstokens
```

Service account token:

```bash
oc get sa -A
oc get secret -A | grep service-account-token
```

### Step 2: Revoke or Rotate

For user token:

```bash
oc delete useroauthaccesstokens <token_name>
```

For service account token:

- Delete old long-lived token secret if applicable.
- Generate a new token.
- Update CI/CD secret store.
- Restart affected automation if required.

### Step 3: Review RBAC Blast Radius

```bash
oc auth can-i '*' '*' -A --as=<identity>
```

For service account:

```bash
oc auth can-i '*' '*' -A \
  --as=system:serviceaccount:cicd:deploy-bot
```

### Step 4: Review Audit Logs

Search for:

```text
username
userAgent
sourceIPs
verb
resource
namespace
responseStatus
```

Depending on your logging stack, search audit events in Loki, Elasticsearch, Splunk, or your SIEM.

### Step 5: Rotate Related Secrets

If the leaked token had access to secrets, rotate:

- Application secrets.
- Registry credentials.
- Cloud credentials.
- Git deploy keys.
- Webhook tokens.
- External integration credentials.

## 17. Common Production Mistakes

| Mistake | Risk | Better Practice |
|---|---|---|
| Sharing one admin kubeconfig | No attribution, high blast radius | Named users through IdP |
| Storing kubeconfig in Git | Token leak | Vault / CI secret store |
| Using `cluster-admin` for CI | Full cluster compromise | Namespace-scoped role |
| Using `insecure-skip-tls-verify` | MITM risk | Use CA data |
| Reusing personal token in automation | Breaks when user leaves or token expires | Dedicated service account |
| No token rotation | Long-term compromise risk | Rotation process |
| Generic context names | Wrong-cluster accidents | Unique environment names |
| Copying kubeconfig everywhere | Credential sprawl | Controlled distribution |
| Using old long-lived SA tokens | Persistent leak risk | Bound tokens |

## 18. Interview-Level Answer

**Question:** What is a kubeconfig with authentication token in OpenShift?

**Senior answer:**

A kubeconfig is the client configuration file used by `oc` and `kubectl` to connect to the OpenShift API server. In a token-based kubeconfig, the `users` section contains a Bearer token, usually an OpenShift OAuth access token for a human user or a service account token for automation.

When a command such as `oc get pods` runs, the CLI reads the current context, identifies the cluster endpoint, loads the token, and sends it to the API server in the `Authorization: Bearer` header. The API server authenticates the token and maps it to a user or service account identity. Then RBAC decides whether that identity can perform the requested action.

In production, a token-based kubeconfig must be protected like a secret. It should have strict file permissions, must not be committed to Git, should avoid `insecure-skip-tls-verify`, and should use least-privilege RBAC. For automation, use a dedicated service account with namespace-scoped permissions rather than a human user's token. Prefer short-lived or bound service account tokens over old long-lived token secrets.

```bash

Root cause matrix:

| Finding | Meaning |
|---|---|

```

## 24. Hands-On Lab: Build Read-Only Token Kubeconfig

Objective:

```text
Create a service account kubeconfig that can only view resources in namespace app-dev.
```

### Step 1: Create Namespaces

```bash
oc new-project app-dev
oc new-project automation
```

### Step 2: Create Service Account

```bash
oc create serviceaccount app-reader -n automation
```

### Step 3: Grant View Access

```bash
oc adm policy add-role-to-user view \
  system:serviceaccount:automation:app-reader \
  -n app-dev
```

### Step 4: Generate Token

```bash
TOKEN=$(oc create token app-reader -n automation)
```

### Step 5: Build Kubeconfig

```bash
API_SERVER=$(oc whoami --show-server)
CA_DATA=$(oc config view --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')

cat > app-reader.kubeconfig <<KUBECONFIG_EOF
apiVersion: v1
kind: Config
clusters:
- name: openshift-api
  cluster:
    server: ${API_SERVER}
    certificate-authority-data: ${CA_DATA}
users:
- name: app-reader
  user:
    token: ${TOKEN}
contexts:
- name: app-reader-context
  context:
    cluster: openshift-api
    user: app-reader
    namespace: app-dev
current-context: app-reader-context
preferences: {}
KUBECONFIG_EOF

chmod 600 app-reader.kubeconfig
```

### Step 6: Validate

```bash
oc --kubeconfig=app-reader.kubeconfig whoami
oc --kubeconfig=app-reader.kubeconfig get pods -n app-dev
oc --kubeconfig=app-reader.kubeconfig auth can-i get pods -n app-dev
oc --kubeconfig=app-reader.kubeconfig auth can-i delete pods -n app-dev
oc --kubeconfig=app-reader.kubeconfig auth can-i get nodes
```

Expected:

```text
get pods in app-dev: yes
delete pods in app-dev: no
get nodes: no
```

## 26. Final Best-Practice Checklist

Before approving token-based kubeconfig for production:

```text
[ ] Kubeconfig has chmod 600.
[ ] Token belongs to correct user or service account.
[ ] Context name clearly identifies cluster and namespace.
[ ] API server uses trusted CA data.
[ ] No insecure-skip-tls-verify in production.
[ ] RBAC follows least privilege.
[ ] Human and automation credentials are separate.
[ ] Token is stored in vault or secure CI secret store.
[ ] Token is not committed to Git.
[ ] Token is not printed in logs.
[ ] Token rotation process exists.
[ ] Revocation process is documented.
[ ] Audit logs can identify the token identity.
[ ] Prod and non-prod kubeconfigs are separated.
[ ] Break-glass access is controlled and monitored.
```

## 27. Key Takeaways

- A token-based kubeconfig is a credential file.
- OpenShift user logins commonly store OAuth access tokens in kubeconfig.
- Service account tokens are better for automation than human tokens.
- Bound service account tokens are preferred over old long-lived token secrets.
- Authentication success does not mean authorization success.
- `401 Unauthorized` usually means token/authentication problem.
- `403 Forbidden` usually means RBAC/authorization problem.
- Avoid `insecure-skip-tls-verify` in production.
- Never commit kubeconfig to Git.
- Use least privilege, short-lived tokens, secure storage, and regular rotation.
