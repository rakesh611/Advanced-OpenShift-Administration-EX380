## Executive Summary

A **kubeconfig** file is the client-side configuration file used by `oc` and `kubectl` to connect to a Kubernetes or OpenShift cluster.

A kubeconfig can authenticate to the API server by using different methods, such as:

- OAuth bearer token.
- ServiceAccount token.
- Exec plugin.
- Username/password in older/basic scenarios.
- **Client certificate and private key**.

In a **client certificate based kubeconfig**, the client proves its identity by presenting an X.509 certificate during the TLS handshake with the API server. If the certificate is valid, trusted, not expired, and signed by a CA recognized by the API server, the request is authenticated.

In Kubernetes-style client certificate authentication:

- Certificate `CN` becomes the username.
- Certificate `O` fields become group names.
- RBAC decides what the authenticated identity can do.
- The kubeconfig stores or references:
  - Cluster API server URL.
  - Cluster CA certificate.
  - Client certificate.
  - Client private key.
  - Context that connects cluster + user + namespace.

In OpenShift, most human users normally authenticate through the integrated OAuth server and identity providers such as LDAP, HTPasswd, OIDC, GitHub, Google, or Keystone. However, client-certificate kubeconfigs still matter for:

- Cluster admin access.
- Break-glass access.
- Automation clients.
- kubelet and internal components.
- Certain enterprise PKI integrations.
- Troubleshooting API authentication.
- Understanding how OpenShift API authentication works underneath.

## Where Kubeconfig Fits in OpenShift Authentication

OpenShift CLI authentication can be understood in four layers:

```text
User / Automation / Component
        |
        v
oc / kubectl client
        |
        v
Kubeconfig file
        |
        v
OpenShift API endpoint: https://api.<cluster>.<domain>:6443
        |
        v
Authentication
        |
        v
Authorization: RBAC / SCC / admission / policy
```

A kubeconfig does not grant permission by itself. It only contains information that helps the client:

1. Locate the API server.
2. Trust the API server certificate.
3. Present identity credentials.
4. Select the active context and namespace.

After authentication succeeds, **RBAC authorization** determines whether the user can list pods, create deployments, approve CSRs, modify OAuth configuration, access secrets, or perform cluster-admin operations.

## What Is a Kubeconfig File?

A kubeconfig is a YAML file used by Kubernetes-compatible clients.

Default location:

```bash
~/.kube/config
```

Common OpenShift installation kubeconfig:

```bash
<install-dir>/auth/kubeconfig
```

Common environment variable:

```bash
export KUBECONFIG=/path/to/kubeconfig
```

Multiple kubeconfig files can be merged logically:

```bash
export KUBECONFIG=/path/dev.kubeconfig:/path/prod.kubeconfig:/path/dr.kubeconfig
oc config get-contexts
```

A kubeconfig usually contains three main logical blocks:

```text
clusters  -> Where is the API server and which CA validates it?
users     -> How does the client authenticate?
contexts  -> Which cluster + user + namespace combination should be used?
```

Example high-level structure:

```yaml
apiVersion: v1
kind: Config
clusters:
- name: ocp-prod
  cluster:
    server: https://api.ocp-prod.example.com:6443
    certificate-authority-data: <base64-cluster-ca>
users:
- name: rakesh-cert-user
  user:
    client-certificate-data: <base64-client-cert>
    client-key-data: <base64-client-key>
contexts:
- name: rakesh-prod-context
  context:
    cluster: ocp-prod
    user: rakesh-cert-user
    namespace: dev-project
current-context: rakesh-prod-context
```

## What Is Client Certificate Authentication?

Client certificate authentication is an X.509 certificate based authentication method.

It uses **mutual TLS style identity proof**:

- The API server presents its server certificate to the client.
- The client verifies the API server certificate using the cluster CA.
- The client presents its own client certificate to the API server.
- The API server verifies the client certificate using a trusted client CA bundle.
- If trusted, the API server extracts identity from the certificate subject.
- RBAC checks permissions.

In simple terms:

```text
Token authentication:
  Client says: "Here is my bearer token."

Client certificate authentication:
  Client says: "Here is my certificate, and I can prove I own the private key."
```

A client certificate kubeconfig contains sensitive authentication material. Whoever has the kubeconfig file and private key can authenticate as that certificate identity until the certificate expires or trust is removed.

## OpenShift Authentication vs Kubernetes Client Certificate Authentication

### OpenShift Normal Human Login

Most OpenShift human users log in like this:

```bash
oc login https://api.ocp.example.com:6443 -u rakesh
```

or through the web console:

```bash
oc login --token=<sha256-token> --server=https://api.ocp.example.com:6443
```

OpenShift commonly integrates with:

- HTPasswd.
- LDAP.
- OIDC.
- Keycloak / Red Hat SSO.
- GitHub.
- GitLab.
- Google.
- Keystone.
- RequestHeader identity providers.

In this model:

```text
Identity provider -> OAuth server -> OAuth token -> kubeconfig user entry -> API access
```

### Kubernetes Client Certificate Login

With client certificate authentication:

```text
Client certificate -> kube-apiserver client CA validation -> username/groups -> RBAC
```

The important difference:

| Area | OpenShift OAuth Login | Client Certificate Kubeconfig |
|---|---|---|
| Credential type | OAuth access token | X.509 certificate + private key |
| Identity source | OpenShift identity provider | Certificate subject |
| Common for human users | Yes | Usually no, except admin/break-glass/special cases |
| Revocation | Token can be removed | Usually certificate valid until expiry unless CA trust changes |
| Group source | IdP / group sync / OAuth identity | Certificate `O` fields |
| Rotation | Token/session lifecycle | Certificate lifecycle |
| Risk if leaked | Token compromise | Private key compromise |
| Best enterprise use | Normal user login | Controlled admin/automation/break-glass |

### Important OpenShift Reality

In OpenShift 4, the platform is operator-managed. You should avoid manually editing static API server flags or static pod manifests unless directed by Red Hat Support or official docs. Use supported OpenShift APIs such as:

```bash
oc edit apiserver cluster
```

or:

```bash
oc patch apiserver cluster --type=merge -p '<json>'
```

For client certificate trust, OpenShift exposes `APIServer` configuration such as `spec.clientCA`, which references a ConfigMap in `openshift-config` containing `ca-bundle.crt`.

## Kubeconfig Structure Deep Dive

A kubeconfig has these main fields:

```yaml
apiVersion: v1
kind: Config
preferences: {}
clusters: []
users: []
contexts: []
current-context: ""
```

### 1. `clusters`

The `clusters` section defines API server connection details.

Example:

```yaml
clusters:
- name: ocp-prod
  cluster:
    server: https://api.ocp-prod.example.com:6443
    certificate-authority-data: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0t...
```

Important fields:

| Field | Meaning |
|---|---|
| `server` | API server URL |
| `certificate-authority` | Path to CA file |
| `certificate-authority-data` | Embedded base64 CA certificate |
| `insecure-skip-tls-verify` | Disables server certificate verification; dangerous |
| `tls-server-name` | Overrides server name used for TLS verification |
| `proxy-url` | Proxy URL for API access |

The cluster CA validates the **API server certificate**.

Do not confuse this with the client CA that validates **user certificates**.

```text
certificate-authority-data in kubeconfig:
  Used by client to trust API server.

clientCA in OpenShift apiserver config:
  Used by API server to trust client certificates.
```

### 2. `users`

The `users` section defines authentication credentials.

Example with token:

```yaml
users:
- name: rakesh
  user:
    token: sha256~xxxxx
```

Example with client certificate:

```yaml
users:
- name: rakesh-cert-user
  user:
    client-certificate-data: <base64-pem-cert>
    client-key-data: <base64-pem-private-key>
```

Example with file references:

```yaml
users:
- name: rakesh-cert-user
  user:
    client-certificate: /home/rakesh/certs/rakesh.crt
    client-key: /home/rakesh/certs/rakesh.key
```

Important fields:

| Field | Meaning |
|---|---|
| `token` | Bearer token |
| `tokenFile` | File containing bearer token |
| `client-certificate` | Path to client certificate |
| `client-certificate-data` | Embedded base64 client certificate |
| `client-key` | Path to client private key |
| `client-key-data` | Embedded base64 client private key |
| `exec` | External command/plugin to get credentials |
| `username/password` | Basic auth style credentials, rarely used |
| `as` | Impersonated username |
| `as-groups` | Impersonated groups |

### 3. `contexts`

A context joins:

```text
cluster + user + namespace
```

Example:

```yaml
contexts:
- name: rakesh-prod-dev
  context:
    cluster: ocp-prod
    user: rakesh-cert-user
    namespace: dev-project
current-context: rakesh-prod-dev
```

Commands:

```bash
oc config get-contexts
oc config current-context
oc config use-context rakesh-prod-dev
oc config set-context --current --namespace=dev-project
```

## Client Certificate Fields in Kubeconfig

There are two ways to provide client certificate and key in kubeconfig.

### Option 1: File Path Based

```yaml
users:
- name: app-admin
  user:
    client-certificate: /secure/pki/app-admin.crt
    client-key: /secure/pki/app-admin.key
```

Advantages:

- Easier to rotate certificate without editing kubeconfig.
- Private key can be protected separately.
- Better for controlled admin workstations.
- Can integrate with external secret management or mounted volumes.

Disadvantages:

- File paths must exist on every machine using the kubeconfig.
- Moving the kubeconfig alone is not enough.
- Incorrect permissions on key files are common.

### Option 2: Embedded Data Based

```yaml
users:
- name: app-admin
  user:
    client-certificate-data: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0t...
    client-key-data: LS0tLS1CRUdJTiBSU0EgUFJJVkFURSBLRVkt...
```

Advantages:

- Portable single file.
- Useful for CI/CD runners and automation.
- Easy to store as one secret in controlled vault systems.

Disadvantages:

- Extremely sensitive because private key is inside the kubeconfig.
- Easy to accidentally commit to Git.
- Harder to rotate partially.
- Harder to inspect manually because data is base64 encoded.

### Rule of Thumb

For enterprise security:

```text
Human admin workstation:
  Prefer file-based private key, protected with strict permissions.

Automation:
  Prefer short-lived credentials, vault injection, or ServiceAccount token if in-cluster.

Break-glass:
  Use strongly protected, audited, offline storage.
```

## Authentication Flow with Client Certificate

When you run:

```bash
oc --kubeconfig ./rakesh-cert.kubeconfig get pods -n dev-project
```

The flow is:

```text
1. oc reads kubeconfig.
2. oc selects current-context.
3. Context points to cluster and user.
4. oc connects to cluster.server.
5. oc verifies API server certificate using certificate-authority-data.
6. oc presents client certificate from client-certificate-data.
7. oc proves possession of private key during TLS handshake.
8. kube-apiserver checks whether client certificate is signed by trusted client CA.
9. kube-apiserver checks certificate validity period and key usage.
10. kube-apiserver maps certificate subject to username/groups.
11. Request becomes authenticated as that user.
12. RBAC checks permission.
13. Admission plugins and OpenShift policies apply.
14. API server returns success or error.
```

Authentication and authorization are separate.

A valid certificate can authenticate successfully but still fail with:

```text
Error from server (Forbidden)
```

That means:

```text
Authentication worked.
Authorization failed.
```

## Certificate Identity Mapping: CN and O Fields

For Kubernetes-compatible client certificate authentication:

```text
Certificate Subject Common Name (CN) -> username
Certificate Subject Organization (O) -> group
```

Example CSR subject:

```bash
-subj "/CN=rakesh/O=devops/O=platform-admins"
```

This maps to:

```text
Username: rakesh
Groups:
  - devops
  - platform-admins
  - system:authenticated
```

The API server automatically adds authenticated users to:

```text
system:authenticated
```

### Example Certificate Subject

```text
Subject: CN = rakesh, O = devops, O = platform-admins
```

### RBAC Binding Example for Username

```bash
oc adm policy add-role-to-user edit rakesh -n dev-project
```

Equivalent RoleBinding YAML:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: rakesh-edit
  namespace: dev-project
subjects:
- kind: User
  apiGroup: rbac.authorization.k8s.io
  name: rakesh
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: edit
```

### RBAC Binding Example for Group

```bash
oc adm policy add-role-to-group view devops -n dev-project
```

Equivalent RoleBinding YAML:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: devops-view
  namespace: dev-project
subjects:
- kind: Group
  apiGroup: rbac.authorization.k8s.io
  name: devops
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: view
```

### Dangerous Subject Example

Never issue casual certificates with privileged Kubernetes/OpenShift system groups such as:

```text
O=system:masters
O=system:nodes
O=system:cluster-admins
CN=system:admin
CN=system:node:<node-name>
```

These can create major privilege escalation or cluster compromise.

## Certificate Authority Trust Model

There are two different trust directions.

### 1. Client Trusts API Server

The kubeconfig contains the CA used to verify the API server certificate:

```yaml
clusters:
- name: ocp-prod
  cluster:
    server: https://api.ocp-prod.example.com:6443
    certificate-authority-data: <cluster-api-serving-ca>
```

This protects the client from connecting to a fake API server.

### 2. API Server Trusts Client Certificate

The OpenShift/Kubernetes API server must have a client CA bundle to verify incoming client certificates.

For OpenShift, additional client CA trust can be configured using the `APIServer` cluster configuration object:

```yaml
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  clientCA:
    name: custom-client-ca
```

The referenced ConfigMap must be in:

```text
openshift-config
```

and contain:

```text
ca-bundle.crt
```

Conceptually:

```text
Client certificate signed by Enterprise Client CA
              |
              v
OpenShift APIServer spec.clientCA trusts Enterprise Client CA
              |
              v
Authentication succeeds
```

## OpenShift APIServer `clientCA`

OpenShift manages API server configuration through cluster configuration APIs, not by editing static flags directly.

Check current APIServer configuration:

```bash
oc get apiserver cluster -o yaml
```

Look for:

```yaml
spec:
  clientCA:
    name: custom-client-ca
```

Create a client CA ConfigMap:

```bash
oc create configmap custom-client-ca \
  --from-file=ca-bundle.crt=/path/to/enterprise-client-ca.crt \
  -n openshift-config
```

Patch the APIServer to trust this CA:

```bash
oc patch apiserver cluster --type=merge -p '{
  "spec": {
    "clientCA": {
      "name": "custom-client-ca"
    }
  }
}'
```

Watch cluster operators:

```bash
oc get co
oc get co kube-apiserver openshift-apiserver authentication
```

Check rollout progress:

```bash
oc get pods -n openshift-kube-apiserver
oc get pods -n openshift-apiserver
```

Important notes:

- The ConfigMap must exist before referencing it.
- It must be in `openshift-config`.
- The key must be `ca-bundle.crt`.
- The bundle can contain one or more PEM-encoded CA certificates.
- Changing API server trust can roll out control-plane components.
- Always keep an existing admin session open before modifying authentication-sensitive settings.
- Test on non-production first.

## Practical Lab 1: Inspect Existing Kubeconfig

### Step 1: Check Current Kubeconfig

```bash
oc config view
```

This may hide sensitive data.

To see raw embedded certificate/token data:

```bash
oc config view --raw
```

Save current kubeconfig:

```bash
oc config view --raw > current-kubeconfig.yaml
chmod 600 current-kubeconfig.yaml
```

### Step 2: Check Current Context

```bash
oc config current-context
```

List all contexts:

```bash
oc config get-contexts
```

Example output:

```text
CURRENT   NAME                    CLUSTER      AUTHINFO           NAMESPACE
*         admin/ocp-prod:6443     ocp-prod     admin              default
          dev/ocp-dev:6443        ocp-dev      developer          dev-project
```

### Step 3: Identify Authentication Method

```bash
oc config view --raw -o jsonpath='{.users[*].user}' | jq
```

or:

```bash
oc config view --raw -o yaml
```

Look for one of these:

```yaml
token: sha256~...
```

or:

```yaml
client-certificate-data: ...
client-key-data: ...
```

or:

```yaml
exec:
  apiVersion: client.authentication.k8s.io/v1beta1
```

### Step 4: Decode Embedded Client Certificate

Find the user entry:

```bash
oc config view --raw -o jsonpath='{.users[0].user.client-certificate-data}' | base64 -d > client.crt
```

Inspect certificate:

```bash
openssl x509 -in client.crt -noout -text
```

Short output:

```bash
openssl x509 -in client.crt -noout -subject -issuer -dates
```

Example:

```text
subject=CN = rakesh, O = devops
issuer=CN = kube-csr-signer
notBefore=Jul  3 05:00:00 2026 GMT
notAfter=Jul  3 05:00:00 2027 GMT
```

### Step 5: Verify Current Identity

```bash
oc whoami
oc whoami --show-server
oc whoami --show-context
```

For token-based OpenShift sessions:

```bash
oc whoami -t
```

For client-certificate based kubeconfigs, `oc whoami -t` might not return an OAuth token because the credential is a certificate, not an OAuth session token.

## Practical Lab 2: Create User Client Certificate Using Kubernetes CSR API

This lab creates a certificate-backed kubeconfig for a user called `rakesh` in group `devops`.

> Use this lab in a test cluster first. Do not issue broad admin certificates casually.

### Variables

```bash
export USER_NAME="rakesh"
export USER_GROUP="devops"
export CSR_NAME="${USER_NAME}-client-csr"
export NAMESPACE="dev-project"
export WORKDIR="$HOME/client-cert-lab-${USER_NAME}"
mkdir -p "$WORKDIR"
cd "$WORKDIR"
```

### Step 1: Create Private Key

RSA example:

```bash
openssl genrsa -out ${USER_NAME}.key 4096
chmod 600 ${USER_NAME}.key
```

ECDSA example:

```bash
openssl ecparam -name prime256v1 -genkey -noout -out ${USER_NAME}.key
chmod 600 ${USER_NAME}.key
```

### Step 2: Create Certificate Signing Request

```bash
openssl req -new \
  -key ${USER_NAME}.key \
  -out ${USER_NAME}.csr \
  -subj "/CN=${USER_NAME}/O=${USER_GROUP}"
```

Inspect CSR:

```bash
openssl req -in ${USER_NAME}.csr -noout -subject -text
```

Expected subject:

```text
Subject: CN = rakesh, O = devops
```

### Step 3: Create Kubernetes CSR Object

For Linux GNU base64:

```bash
export CSR_BASE64=$(base64 -w0 ${USER_NAME}.csr)
```

For macOS:

```bash
export CSR_BASE64=$(base64 < ${USER_NAME}.csr | tr -d '\n')
```

Create CSR YAML:

```bash
cat > ${CSR_NAME}.yaml <<EOFYAML
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: ${CSR_NAME}
spec:
  request: ${CSR_BASE64}
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 31536000
  usages:
  - digital signature
  - key encipherment
  - client auth
EOFYAML
```

Apply it:

```bash
oc apply -f ${CSR_NAME}.yaml
```

Check CSR:

```bash
oc get csr ${CSR_NAME}
oc describe csr ${CSR_NAME}
```

Expected status initially:

```text
Pending
```

### Step 4: Approve CSR

Only trusted cluster admins should approve user/client CSRs.

```bash
oc adm certificate approve ${CSR_NAME}
```

Check again:

```bash
oc get csr ${CSR_NAME}
```

Expected:

```text
Approved,Issued
```

### Step 5: Extract Issued Certificate

```bash
oc get csr ${CSR_NAME} \
  -o jsonpath='{.status.certificate}' | base64 -d > ${USER_NAME}.crt
```

Inspect issued certificate:

```bash
openssl x509 -in ${USER_NAME}.crt -noout -subject -issuer -dates -ext extendedKeyUsage
```

Expected signs:

```text
subject=CN = rakesh, O = devops
X509v3 Extended Key Usage:
    TLS Web Client Authentication
```

### Step 6: Grant RBAC Permission

Create project if required:

```bash
oc new-project ${NAMESPACE}
```

Grant group `devops` view access:

```bash
oc adm policy add-role-to-group view ${USER_GROUP} -n ${NAMESPACE}
```

Or grant specific user access:

```bash
oc adm policy add-role-to-user view ${USER_NAME} -n ${NAMESPACE}
```

For admin testing only, avoid giving `cluster-admin` unless necessary.

Bad example for production:

```bash
oc adm policy add-cluster-role-to-user cluster-admin ${USER_NAME}
```

Better controlled example:

```bash
oc adm policy add-role-to-user edit ${USER_NAME} -n ${NAMESPACE}
```

## Practical Lab 3: Build Kubeconfig Manually with Client Certificate

### Step 1: Get API Server URL

```bash
export API_SERVER=$(oc whoami --show-server)
echo $API_SERVER
```

Example:

```text
https://api.ocp.example.com:6443
```

### Step 2: Extract Cluster CA from Current Kubeconfig

```bash
oc config view --raw \
  -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' \
  | base64 -d > cluster-ca.crt
```

Alternative from current kubeconfig:

```bash
oc config view --raw --minify > current-minify.yaml
```

### Step 3: Create Empty Kubeconfig

```bash
export NEW_KUBECONFIG="$WORKDIR/${USER_NAME}.kubeconfig"
rm -f "$NEW_KUBECONFIG"
```

### Step 4: Set Cluster

```bash
oc config --kubeconfig="$NEW_KUBECONFIG" set-cluster ocp-prod \
  --server="$API_SERVER" \
  --certificate-authority=cluster-ca.crt \
  --embed-certs=true
```

### Step 5: Set User with Client Certificate

```bash
oc config --kubeconfig="$NEW_KUBECONFIG" set-credentials ${USER_NAME} \
```

## Practical Lab 4: Use an External Enterprise CA with OpenShift

This lab is for an enterprise where client certificates are issued by a corporate CA, not by the Kubernetes CSR signer.

### Architecture

```text
Enterprise Root CA / Intermediate CA
        |
        v
Signs user/client certificate
        |
        v
OpenShift APIServer spec.clientCA trusts enterprise CA bundle
        |
        v
User authenticates with kubeconfig client certificate
        |
        v
RBAC authorizes based on CN/O identity
```

### Step 1: Prepare Enterprise Client CA Bundle

The CA bundle must contain CA certificates, not the user certificate.

Example:

```bash
cat enterprise-root-ca.crt enterprise-intermediate-ca.crt > ca-bundle.crt
```

Verify:

```bash
openssl x509 -in enterprise-root-ca.crt -noout -subject -issuer -dates
openssl x509 -in enterprise-intermediate-ca.crt -noout -subject -issuer -dates
```

### Step 2: Create ConfigMap in `openshift-config`

```bash
oc create configmap enterprise-client-ca \
  --from-file=ca-bundle.crt=./ca-bundle.crt \
  -n openshift-config
```

Verify:

```bash
oc get configmap enterprise-client-ca -n openshift-config -o yaml
```

### Step 3: Patch APIServer

```bash
oc patch apiserver cluster --type=merge -p '{
  "spec": {
    "clientCA": {
      "name": "enterprise-client-ca"
    }
  }
}'
```

### Step 4: Watch Cluster Operators

```bash
watch 'oc get co kube-apiserver openshift-apiserver authentication'
```

Wait until operators become:

```text
AVAILABLE=True
PROGRESSING=False
DEGRADED=False
```

### Step 5: Create Client Certificate from Enterprise CA

Example OpenSSL config for client certificate:

```bash
cat > client-openssl.cnf <<'EOFCONF'
[ req ]
default_bits       = 4096
prompt             = no
default_md         = sha256
distinguished_name = dn
req_extensions     = req_ext

[ dn ]
CN = rakesh
O  = devops

[ req_ext ]
extendedKeyUsage = clientAuth
keyUsage = digitalSignature, keyEncipherment
EOFCONF
```

Generate key and CSR:

```bash
openssl genrsa -out rakesh.key 4096
chmod 600 rakesh.key

openssl req -new \
  -key rakesh.key \
  -out rakesh.csr \
  -config client-openssl.cnf
```

Enterprise CA signs the CSR:

```bash
openssl x509 -req \
  -in rakesh.csr \
  -CA enterprise-intermediate-ca.crt \
  -CAkey enterprise-intermediate-ca.key \
  -CAcreateserial \
  -out rakesh.crt \
  -days 365 \
  -sha256 \
  -extfile client-openssl.cnf \
  -extensions req_ext
```

Verify:

```bash
openssl verify -CAfile ca-bundle.crt rakesh.crt
openssl x509 -in rakesh.crt -noout -subject -issuer -dates -ext extendedKeyUsage
```

### Step 6: Create Kubeconfig

```bash
export API_SERVER="https://api.ocp.example.com:6443"

oc config --kubeconfig=enterprise-rakesh.kubeconfig set-cluster ocp-prod \
  --server="$API_SERVER" \
  --certificate-authority=cluster-ca.crt \
  --embed-certs=true

oc config --kubeconfig=enterprise-rakesh.kubeconfig set-credentials rakesh \
  --client-certificate=rakesh.crt \
  --client-key=rakesh.key \
  --embed-certs=true

oc config --kubeconfig=enterprise-rakesh.kubeconfig set-context rakesh-context \
  --cluster=ocp-prod \
  --user=rakesh \
  --namespace=dev-project

oc config --kubeconfig=enterprise-rakesh.kubeconfig use-context rakesh-context
chmod 600 enterprise-rakesh.kubeconfig
```

### Step 7: Grant RBAC

```bash
oc adm policy add-role-to-group view devops -n dev-project
```

### Step 8: Test

```bash
oc --kubeconfig=enterprise-rakesh.kubeconfig whoami
oc --kubeconfig=enterprise-rakesh.kubeconfig get pods -n dev-project
oc --kubeconfig=enterprise-rakesh.kubeconfig auth can-i list pods -n dev-project
```

## Admin Kubeconfig vs User Kubeconfig

### Admin Kubeconfig

Generated during OpenShift installation:

```bash
<install-dir>/auth/kubeconfig
```

Commonly used as:

```bash
export KUBECONFIG=<install-dir>/auth/kubeconfig
oc get nodes
```

This kubeconfig is very sensitive.

Characteristics:

- Often has powerful admin credentials.
- Used for initial cluster setup.
- Should not be distributed broadly.
- Should not be stored in ticket attachments, Git repositories, shared drives, or chat.
- Should be stored in a secure vault.

### User Kubeconfig

Generated after login:

```bash
oc login https://api.ocp.example.com:6443 -u rakesh
oc config view --raw > rakesh.kubeconfig
```

Usually token-based in OpenShift.

Characteristics:

- Tied to a specific user/session/token.
- Permissions depend on RBAC.
- Safer than cluster-admin kubeconfig but still sensitive.
- Can be revoked through OAuth token cleanup.

### Certificate User Kubeconfig

Manually built or generated through CSR/PKI.

Characteristics:

- Authentication depends on client certificate validity.
- Cannot be revoked like a normal OAuth token unless trust is removed or certificate expires.
- Best used with short validity and strict RBAC.
- Strongly protect the private key.

## ServiceAccount Token vs Client Certificate

| Feature | ServiceAccount Token | Client Certificate |
|---|---|---|
| Main use | Workloads/pods | Humans, admins, automation, components |
| Identity format | `system:serviceaccount:<namespace>:<name>` | Certificate CN/O |
| Namespace scoped identity | Yes | No, unless RBAC restricts |
| Credential form | Bearer token | Cert + private key |
| In-cluster default | Yes | No |
| Rotation | TokenRequest / projected tokens | Certificate lifecycle |
| Revocation | Delete SA/token/secret or bound token expiry | Expiry or CA trust change |
| Common OpenShift automation | Yes | Sometimes |
| Risk if leaked | Token impersonation | Cert/key impersonation |

### Use ServiceAccount When

- Application runs inside OpenShift.
- CI/CD job runs as an in-cluster workload.
- You need namespace-scoped automation.
- You want Kubernetes-native workload identity.

### Use Client Certificate When

- External admin tool must authenticate through enterprise PKI.
- Break-glass access is required.
- You need certificate-based non-OAuth authentication.
- You are integrating a controlled external system.
- You are dealing with kubelet/control-plane style machine identity.

### Use OAuth/OIDC/LDAP When

- Human users need normal CLI and console login.
- Enterprise identity lifecycle matters.
- You need group sync and centralized access control.
- You need better offboarding and auditing.

## Client Certificate Lifecycle Management

A mature enterprise process should define:

1. Who can request certificates.
2. Who can approve certificates.
3. Which CA signs certificates.
4. Maximum validity period.
5. Naming convention for CN.
6. Group mapping strategy using O fields.
7. RBAC binding policy.
8. Storage and distribution method.
9. Rotation process.
10. Revocation/offboarding process.
11. Audit process.
12. Emergency break-glass process.

### Recommended Naming

Human admin:

```text
CN=rakesh.jha
O=platform-admins
O=ocp-prod-admins
```

Automation:

```text
CN=ci-jenkins-prod
O=automation
O=deployers
```

Read-only audit:

```text
CN=audit-reader-prod
O=auditors
O=platform-readonly
```

Avoid vague names:

```text
CN=admin
CN=user
CN=test
CN=ocp
CN=kubernetes
```

### Recommended Validity

| Identity Type | Suggested Validity |
|---|---|
| Break-glass admin | 30–90 days, tightly controlled |
| Human admin | Prefer OAuth/OIDC; if cert required, 30–180 days |
| Automation | 30–90 days or shorter |
| Temporary vendor access | Hours to days |
| Lab/demo | 1–7 days |

Avoid issuing 5-year or 10-year client certificates.

## Rotation, Expiry, Revocation, and Offboarding

### Check Certificate Expiry

```bash
openssl x509 -in rakesh.crt -noout -dates
```

Check from embedded kubeconfig:

```bash
oc config view --raw \
  -o jsonpath='{.users[0].user.client-certificate-data}' \
  | base64 -d \
  | openssl x509 -noout -subject -issuer -dates
```

### Rotation Process

1. Generate new key.
2. Generate new CSR.
3. Approve/sign CSR.
4. Create new kubeconfig or update user entry.
5. Test new kubeconfig.
6. Replace old kubeconfig securely.
7. Remove old RBAC if identity changed.
8. Archive audit evidence.
9. Destroy old key if policy requires.

### Offboarding Problem

Client certificates are harder to revoke than OAuth tokens.

Options:

1. Remove RBAC bindings for that username/group.
2. Remove or replace the trusted client CA bundle.
3. Use short-lived certificates so access naturally expires.
4. Use a dedicated CA per access class or team to reduce blast radius.
5. Prefer OAuth/OIDC for normal human users.

### Remove RBAC Access

```bash
oc adm policy remove-role-from-user edit rakesh -n dev-project
oc adm policy remove-cluster-role-from-user cluster-reader rakesh
```

Group example:

```bash
oc adm policy remove-role-from-group view devops -n dev-project
```

### Remove External Client CA Trust

To remove custom client CA trust:

```bash
oc patch apiserver cluster --type=json -p '[
  {"op": "remove", "path": "/spec/clientCA"}
]'
```

Then monitor:

```bash
oc get co kube-apiserver openshift-apiserver authentication
```

Be careful: removing CA trust invalidates all client certs signed by that CA.

## Security Hardening Best Practices

### 1. Protect Kubeconfig Like a Password

```bash
chmod 600 ~/.kube/config
chmod 600 *.kubeconfig
chmod 600 *.key
```

Do not store kubeconfigs in:

- Git repositories.
- Email attachments.
- Shared chat channels.
- Public S3 buckets.
- Unencrypted backup folders.
- CI/CD variables without protection.

### 2. Avoid `insecure-skip-tls-verify`

Dangerous kubeconfig:

```yaml
cluster:
  insecure-skip-tls-verify: true
```

This disables API server certificate validation and makes man-in-the-middle attacks easier.

Use CA trust instead:

```yaml
certificate-authority-data: <base64-ca>
```

### 3. Use Least Privilege RBAC

Bad:

```bash
oc adm policy add-cluster-role-to-user cluster-admin app-user
```

Better:

```bash
oc adm policy add-role-to-user edit app-user -n app-namespace
```

Even better for automation:

```bash
oc adm policy add-role-to-user deployer app-deployer -n app-namespace
```

### 4. Prefer Group-Based RBAC

Instead of binding many users:

```bash
oc adm policy add-role-to-user view user1 -n dev
oc adm policy add-role-to-user view user2 -n dev
oc adm policy add-role-to-user view user3 -n dev
```

Use group:

```bash
oc adm policy add-role-to-group view devops -n dev
```

Then issue certs with:

```text
O=devops
```

### 5. Avoid System Prefixes

Avoid creating usernames or groups with privileged system prefixes unless you are managing internal components.

Dangerous examples:

```text
CN=system:admin
CN=system:kube-controller-manager
CN=system:node:worker1
O=system:masters
O=system:nodes
```

### 6. Use Short-Lived Certificates

Short-lived certificates reduce damage if a kubeconfig is leaked.

Example CSR:

```yaml
spec:
  expirationSeconds: 86400
```

This requests 24 hours.

The actual issued duration depends on signer policy and maximum duration.

### 7. Separate Human and Automation Identity

Do not use one certificate for multiple admins.

Bad:

```text
CN=admin
```

Good:

```text
CN=rakesh.jha
CN=sita.kumar
CN=ci-jenkins-prod
```

### 8. Audit API Usage

Useful commands:

```bash
oc adm node-logs --role=master --path=kube-apiserver/
oc get events -A
oc get oauthaccesstokens
oc get rolebindings -A
oc get clusterrolebindings
```

For managed OpenShift platforms, use the supported logging/audit log access mechanism for that platform.

### 9. Store Admin Kubeconfigs in Vault

Examples:

- HashiCorp Vault.
- CyberArk.
- AWS Secrets Manager.
- Azure Key Vault.
- GCP Secret Manager.
- Enterprise password vault with approval workflow.

### 10. Document Ownership

Every certificate identity should have:

```text
Owner: person/team
Purpose: why it exists
RBAC: what access it has
Created: date
Expires: date
CA: signer
Rotation: responsible team
Emergency contact: owner/team
```

## Common Production Use Cases

### Use Case 1: Break-Glass Cluster Admin

Purpose:

- Emergency access if OAuth/LDAP/OIDC fails.

Design:

- Dedicated certificate identity.
- Very limited number of custodians.
- Stored offline or in vault.
- Short validity.
- Strong audit process.
- Tested quarterly.

Example identity:

```text
CN=breakglass-ocp-prod
O=breakglass-admins
```

RBAC:

```bash
oc adm policy add-cluster-role-to-group cluster-admin breakglass-admins
```

Security controls:

- Dual approval to retrieve.
- Audit every use.
- Rotate after each emergency.

### Use Case 2: External CI/CD Deployment System

Purpose:

- Jenkins/GitLab/Argo external runner deploys to OpenShift.

Better default:

- Use ServiceAccount/token with limited namespace RBAC.

Client certificate option:

```text
CN=jenkins-prod-deployer
O=deployers
```

RBAC:

```bash
oc adm policy add-role-to-group edit deployers -n app-prod
```

Security:

- Short certificate validity.
- Dedicated namespace permissions.
- No cluster-admin.
- Store key in CI secret vault.

### Use Case 3: External Monitoring Tool

Purpose:

- Monitoring tool reads API resources.

Identity:

```text
CN=monitoring-reader
O=platform-readonly
```

RBAC:

```bash
oc adm policy add-cluster-role-to-group cluster-reader platform-readonly
```

Better in many cases:

- Use Prometheus ServiceAccount inside cluster.
- Use OpenShift monitoring stack integration.

### Use Case 4: Enterprise PKI Requirement

Purpose:

- Organization requires certificate-based authentication for privileged API access.

Design:

- Enterprise intermediate CA dedicated to OpenShift API clients.
- `APIServer.spec.clientCA` trusts that CA.
- Issuance policy controls CN/O values.
- RBAC maps O fields to least-privilege groups.
- Short validity and centralized audit.

## Common Mistakes and Risks

### Mistake 1: Thinking Kubeconfig Is Harmless

Wrong:

```text
"It is just a config file."
```

Correct:

```text
A kubeconfig can contain live authentication credentials.
If leaked, it can provide direct API access.
```

### Mistake 2: Committing Kubeconfig to Git

Check repository history:

```bash
git log --all --full-history -- "*.kubeconfig"
git grep -n "client-key-data\|token:\|client-certificate-data"
```

If leaked:

1. Remove RBAC.
2. Rotate certificate/token.
3. Purge Git history if required.
4. Review audit logs.
5. Notify security team.

### Mistake 3: Using `system:masters`

This is extremely powerful in Kubernetes-style RBAC.

Dangerous CSR:

```bash
openssl req -new -key admin.key -out admin.csr -subj "/CN=badadmin/O=system:masters"
```

Do not issue this in production without formal break-glass controls.

### Mistake 4: Confusing CA Directions

Wrong mental model:

```text
certificate-authority-data validates my client certificate.
```

Correct:

```text
certificate-authority-data in kubeconfig validates the API server certificate.
APIServer clientCA validates client certificates.
```

### Mistake 5: No Expiry Process

A certificate with one-year validity but no tracking becomes a future outage.

Maintain inventory:

```text
Name | CN | Groups | Owner | Expiry | RBAC | CA | Rotation status
```

### Mistake 6: Embedding Private Keys Everywhere

Embedded kubeconfig is portable but risky:

```yaml
client-key-data: <private-key>
```

Use vault and short-lived credentials for automation.

### Mistake 7: Approving CSRs Blindly

Before approving any CSR:

```bash
oc describe csr <csr-name>
```

Decode and inspect CSR:

```bash
oc get csr <csr-name> -o jsonpath='{.spec.request}' \
  | base64 -d > request.csr
openssl req -in request.csr -noout -subject -text
```

Check:

- CN.
- O groups.
- Key usages.
- Requester.
- Purpose.
- Ticket/change approval.

## Troubleshooting Playbook

### Problem 1: `Unable to connect to the server: x509: certificate signed by unknown authority`

Meaning:

The client does not trust the API server certificate.

Check kubeconfig cluster CA:

```bash
oc config view --raw -o yaml
```

Check API server certificate:

```bash
openssl s_client -connect api.ocp.example.com:6443 -showcerts </dev/null
```

Fix:

```bash
oc config set-cluster ocp-prod \
  --server=https://api.ocp.example.com:6443 \
  --certificate-authority=cluster-ca.crt \
  --embed-certs=true
```

Avoid this except temporary lab testing:

```bash
--insecure-skip-tls-verify=true
```

### Problem 2: `error: You must be logged in to the server`

Possible causes:

- Client certificate not present.
- Client key missing.
- Certificate expired.
- Certificate not signed by trusted client CA.
- Wrong kubeconfig context.
- API server does not trust client CA.

Checks:

```bash
oc config current-context
oc config view --raw --minify -o yaml
openssl x509 -in client.crt -noout -subject -issuer -dates
openssl rsa -in client.key -check -noout
```

Verify certificate and key match:

For RSA:

```bash
openssl x509 -noout -modulus -in client.crt | openssl md5
openssl rsa -noout -modulus -in client.key | openssl md5
```

The hashes should match.

### Problem 3: `Forbidden`

Example:

```text
Error from server (Forbidden): pods is forbidden: User "rakesh" cannot list resource "pods" in API group "" in the namespace "dev-project"
```

Meaning:

Authentication succeeded. RBAC authorization failed.

Check:

```bash
oc --kubeconfig=rakesh.kubeconfig whoami
oc auth can-i list pods -n dev-project --as=rakesh
oc get rolebindings -n dev-project -o wide
oc get clusterrolebindings -o wide | grep rakesh
```

Fix:

```bash
oc adm policy add-role-to-user view rakesh -n dev-project
```

or group-based:

```bash
oc adm policy add-role-to-group view devops -n dev-project
```

### Problem 4: CSR Stuck Pending

Check CSR:

```bash
oc get csr
oc describe csr rakesh-client-csr
```

Decode CSR:

```bash
oc get csr rakesh-client-csr -o jsonpath='{.spec.request}' \
  | base64 -d > rakesh.csr
openssl req -in rakesh.csr -noout -subject -text
```

Approve if valid:

```bash
oc adm certificate approve rakesh-client-csr
```

Deny if suspicious:

```bash
oc adm certificate deny rakesh-client-csr
```

### Problem 5: CSR Approved but Certificate Empty

Check:

```bash
oc get csr rakesh-client-csr -o yaml
```

Look at:

```yaml
status:
  certificate:
```

Possible causes:

- Signer not available.
- Invalid signerName.
- Unsupported usage.
- Control-plane signing issue.
- CSR denied/failed.

Check cluster operators:

```bash
oc get co kube-controller-manager kube-apiserver
```

Check signerName:

```yaml
signerName: kubernetes.io/kube-apiserver-client
```

Check usages:

```yaml
usages:
- digital signature
- key encipherment
- client auth
```

### Problem 6: `certificate has expired or is not yet valid`

Check local clock:

```bash
date
chronyc tracking
```

Check certificate:

```bash
openssl x509 -in client.crt -noout -dates
```

Fix:

- Renew certificate.
- Correct node/workstation time sync.
- Check NTP/chrony.

### Problem 7: Wrong User Appears in `oc whoami`

Cause:

- Wrong current-context.
- KUBECONFIG points to another file.
- Multiple kubeconfigs merged.
- User entry references token instead of certificate.

Check:

```bash
echo $KUBECONFIG
oc config get-contexts
oc config current-context
oc config view --raw --minify -o yaml
```

Use explicit kubeconfig:

```bash
oc --kubeconfig=./rakesh.kubeconfig whoami
```

### Problem 8: API Server Degraded After Client CA Change

Check operators:

```bash
oc get co
oc describe co kube-apiserver
oc describe co openshift-apiserver
oc describe co authentication
```

Check ConfigMap:

```bash
oc get configmap enterprise-client-ca -n openshift-config -o yaml
```

Verify key name:

```text
ca-bundle.crt
```

Check PEM format:

```bash
oc get configmap enterprise-client-ca -n openshift-config \
  -o jsonpath='{.data.ca-bundle\.crt}' > ca-bundle.crt

openssl x509 -in ca-bundle.crt -noout -subject -issuer -dates
```

If multiple certs are in the bundle, split and verify each.

Rollback:

```bash
oc patch apiserver cluster --type=json -p '[
  {"op": "remove", "path": "/spec/clientCA"}
]'
```

```bash
  --from-file=ca-bundle.crt=./ca-bundle.crt \
  -n openshift-config

oc patch apiserver cluster --type=merge -p '{
  "spec": {
    "clientCA": {
      "name": "enterprise-client-ca"
    }
  }
}'

oc get co kube-apiserver openshift-apiserver authentication
```

### Decode Kubeconfig Embedded Certificate

```bash
oc config view --raw \
  -o jsonpath='{.users[0].user.client-certificate-data}' \
  | base64 -d \
  | openssl x509 -noout -subject -issuer -dates
```

## Interview and Real-World Scenario Questions

### Q1. What is kubeconfig?

A kubeconfig is a YAML client configuration file used by `oc` and `kubectl` to connect to a Kubernetes/OpenShift API server. It contains cluster endpoint information, CA trust, user authentication credentials, contexts, and the current context.

### Q2. What are the three main parts of kubeconfig?

```text
clusters  -> API server URL and server CA
users     -> Authentication credentials
contexts  -> Mapping of cluster + user + namespace
```

### Q3. What does `client-certificate-data` mean?

It is a base64-encoded PEM client certificate embedded directly inside kubeconfig. The client presents this certificate to the API server for authentication.

### Q4. What does `client-key-data` mean?

It is a base64-encoded PEM private key embedded directly inside kubeconfig. It proves that the client owns the public key in the client certificate. It is highly sensitive.

### Q5. What is the difference between `certificate-authority-data` and `client-certificate-data`?

| Field | Purpose |
|---|---|
| `certificate-authority-data` | Allows client to verify API server certificate |
| `client-certificate-data` | Allows API server to authenticate client identity |

### Q6. How does Kubernetes map client certificate identity?

```text
CN -> username
O  -> groups
```

Example:

```text
CN=rakesh,O=devops
```

maps to:

```text
User: rakesh
Group: devops
Also group: system:authenticated
```

### Q7. If a user with a valid client certificate gets `Forbidden`, what does it mean?

Authentication succeeded, but RBAC authorization failed. The user needs proper RoleBinding or ClusterRoleBinding.

### Q8. Is client certificate authentication recommended for all OpenShift users?

Usually no. OpenShift human users should normally use OAuth through enterprise identity providers such as LDAP, OIDC, or HTPasswd. Client certificate kubeconfigs are better for controlled admin, break-glass, machine, or special automation use cases.

### Q9. How do you create a client certificate kubeconfig?

High-level process:

1. Generate private key.
2. Generate CSR with CN/O identity.
3. Sign CSR using trusted client CA or Kubernetes CSR signer.
4. Extract certificate.
5. Build kubeconfig with API server, cluster CA, client cert, and client key.
6. Grant RBAC.
7. Test with `oc --kubeconfig`.

### Q10. What is the risk of long-lived client certificates?

They are hard to revoke. If leaked, they may remain usable until expiry unless RBAC is removed or the issuing CA is removed from API server trust.

### Q11. How do you revoke access for a certificate user?

Options:

- Remove RBAC bindings for the username/group.
- Remove trusted client CA from APIServer config.
- Let short-lived certificate expire.
- Rotate the CA if necessary.

### Q12. What is dangerous about `O=system:masters`?

It can give very powerful cluster-level access in Kubernetes RBAC. Issuing a certificate with privileged system groups can bypass intended access controls and compromise the cluster.

### Q13. How do you troubleshoot kubeconfig certificate issues?

Check:

```bash
oc config view --raw --minify -o yaml
openssl x509 -in client.crt -noout -subject -issuer -dates
openssl verify -CAfile ca-bundle.crt client.crt
oc auth can-i --list
oc get apiserver cluster -o yaml
oc get co kube-apiserver openshift-apiserver authentication
```

### Q14. What is `APIServer.spec.clientCA` in OpenShift?

It references a ConfigMap in `openshift-config` containing a CA bundle named `ca-bundle.crt`. OpenShift API servers use this bundle to recognize additional signers for incoming client certificates.

### Q15. Why should you avoid `insecure-skip-tls-verify`?

It disables API server certificate validation, which can expose the client to man-in-the-middle attacks. Use proper `certificate-authority-data` instead.

## Recommended Enterprise Design

For a production-grade OpenShift environment, use this model.

### 1. Human User Authentication

Use OpenShift OAuth with enterprise identity provider:

```text
OIDC / LDAP / SSO / HTPasswd -> OAuth -> token kubeconfig
```

Benefits:

- Centralized user lifecycle.
- Better offboarding.
- Group sync.
- Stronger audit integration.
- Easier MFA integration through IdP.

### 2. Privileged Break-Glass

Use controlled client certificate kubeconfig:

```text
Dedicated CA -> short-lived break-glass cert -> vault -> audited retrieval
```

Controls:

- Short validity.
- Dual approval.
- Strong RBAC.
- Audit every use.
- Rotate after use.

### 3. Automation Inside Cluster

Use ServiceAccount with least privilege:

```text
ServiceAccount -> RoleBinding -> projected token
```

### 4. Automation Outside Cluster

Prefer one of:

- OIDC workload identity if available.
- Short-lived token exchange.
- Dedicated ServiceAccount token with strict RBAC.
- Client certificate only if PKI governance is mature.

### 5. Client CA Strategy

Use dedicated CA hierarchy:

```text
Corporate Root CA
  |
  +-- OpenShift API Client Intermediate CA - Prod
  |
  +-- OpenShift API Client Intermediate CA - NonProd
```

Do not use a broad corporate root directly if avoidable. Trusting a broad root can unintentionally allow certificates from unrelated enterprise processes to authenticate if subject policy is not tightly controlled.

### 6. RBAC Strategy

Use group-oriented RBAC:

```text
O=ocp-prod-readonly     -> cluster-reader
O=ocp-prod-devops       -> edit/admin in selected namespaces
O=ocp-prod-breakglass   -> cluster-admin with strict controls
```

Avoid binding privileged roles directly to generic usernames.

### 7. Certificate Validity

Keep certificate lifetime short:

```text
Automation: 30–90 days
Break-glass: 30–90 days or rotate after each use
Temporary access: hours/days
Human admin: prefer OAuth/OIDC instead
```

### 8. Monitoring and Audit

Track:

- CSR creation.
- CSR approval.
- APIServer clientCA changes.
- RoleBinding and ClusterRoleBinding changes.
- Use of break-glass identity.
- Failed authentication attempts.
- Access to secrets.

## Final Revision Notes

For an advanced OpenShift administrator, the key point is this:

```text
A kubeconfig with a client certificate is not just a connection file.
It is an identity-bearing credential that can directly authenticate to the OpenShift API server.
```

You must understand:

- Which CA signs the client certificate.
- Whether OpenShift trusts that CA.
- What username and groups the certificate maps to.
- Which RBAC permissions those identities have.
- How long the certificate is valid.
- How access will be revoked.
- Where the private key is stored.
- How the kubeconfig is distributed and audited.

In enterprise OpenShift operations, client certificate kubeconfigs should be treated as **high-value privileged credentials**, especially when they belong to admin, automation, or break-glass identities.
