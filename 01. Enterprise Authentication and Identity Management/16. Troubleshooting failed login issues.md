# Troubleshooting Failed Login Issues in Enterprise Authentication and Identity Management

**Course context:** Advanced OpenShift Administration  
**Skill level:** 10+ years Linux/Kubernetes/OpenShift administrator  
**Focus:** OpenShift login failures from web console, `oc login`, OAuth, identity providers, LDAP, OIDC, HTPasswd, user/identity mapping, certificates, routes, operators, and RBAC confusion.

---

## 1. What “failed login” really means in OpenShift

In OpenShift, a login issue can happen at multiple layers. A senior administrator must first identify *where* the failure is happening.

A user login normally flows like this:

```text
User / Browser / oc CLI
        |
        v
OpenShift console route or API endpoint
        |
        v
OAuth route: oauth-openshift.apps.<cluster-domain>
        |
        v
OAuth server pods in openshift-authentication
        |
        v
Configured Identity Provider
LDAP / OIDC / HTPasswd / GitHub / GitLab / Google / Request Header / Basic Auth
        |
        v
OpenShift User + Identity + UserIdentityMapping objects
        |
        v
OAuth access token issued
        |
        v
API server validates token
        |
        v
RBAC authorization decides what the user can do
```

A login problem is **not always an identity provider problem**. It might be:

- DNS failure
- Route or ingress failure
- OAuth server unavailable
- Invalid OAuth configuration
- LDAP bind/search failure
- OIDC issuer/client/redirect/claim problem
- Wrong HTPasswd secret or secret not rolled out
- Expired token
- Broken user-to-identity mapping
- Certificate trust issue
- Browser cookie/session problem
- API server unavailable
- RBAC denial mistakenly treated as login failure

A 10+ year administrator should avoid guessing. Classify the failure first.

## 2. Authentication vs authorization: do not mix them

This is the most common mistake during troubleshooting.

### Authentication failure

Authentication answers:

```text
Who are you?
```

Examples:

```text
Login failed
Unauthorized
Invalid username or password
Authentication error occurred
x509 certificate signed by unknown authority
Unable to obtain OAuth token
```

### Authorization failure

Authorization answers:

```text
What are you allowed to do?
```

Example:

```text
Error from server (Forbidden): users.user.openshift.io is forbidden:
User "john" cannot list resource "users" in API group "user.openshift.io" at the cluster scope
```

This means the user **logged in successfully**, but RBAC denied the action.

### Quick decision rule

| Symptom | Meaning |
|---|---|
| `401 Unauthorized` during login | Authentication/token problem |
| `403 Forbidden` after login | RBAC authorization problem |
| User can run `oc whoami` but cannot run `oc get nodes` | Login works, RBAC missing |
| Web console opens but projects are empty | Login works, RBAC/project access issue |
| `oc login` cannot get token | OAuth/IDP/authentication issue |

## 3. Important OpenShift authentication objects

### 3.1 `OAuth` cluster configuration

OpenShift stores identity provider configuration in the cluster-scoped OAuth object:

```bash
oc get oauth cluster -o yaml
```

Important fields:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: htpasswd_provider
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpasswd-secret
```

Key points:

- The OAuth object name must be `cluster`.
- Identity provider secrets and CA config maps normally live in the `openshift-config` namespace.
- OpenShift OAuth changes trigger rollout/reconciliation by the authentication operator.
- Bad OAuth configuration can break login for all normal users.

---

### 3.2 Identity provider name

The identity provider name is important because it becomes part of the OpenShift identity name.

Example:

```text
htpasswd_provider:rakesh
ldapidp:uid=rakesh,ou=users,dc=example,dc=com
keycloak:rakesh-uuid
```

If you rename the identity provider, OpenShift treats the same external user as a **new identity**.

This can cause:

- Duplicate users
- Mapping conflicts
- Users losing project access
- Unexpected “user already exists” errors

---

### 3.3 `User`

A `User` is the OpenShift object used for RBAC.

```bash
oc get users
oc get user <username> -o yaml
```

Example:

```yaml
kind: User
metadata:
  name: rakesh
identities:
- htpasswd_provider:rakesh
```

RBAC is usually attached to the `User` or to groups that the user belongs to.

---

### 3.4 `Identity`

An `Identity` represents the external identity provider identity.

```bash
oc get identities
oc get identity <idp-name>:<idp-user-id> -o yaml
```

Example:

```yaml
kind: Identity
providerName: htpasswd_provider
providerUserName: rakesh
user:
  name: rakesh
```

If this object is corrupt or mapped to the wrong user, login can fail for one user while everyone else works.

---

### 3.5 `UserIdentityMapping`

This maps an `Identity` to a `User`.

```bash
oc get useridentitymapping
oc create useridentitymapping <identity-provider>:<identity-provider-user-id> <username>
```

This is especially important when `mappingMethod: lookup` is used.

## 4. Common `mappingMethod` values and their impact

OpenShift supports several identity mapping methods.

### 4.1 `claim`

```yaml
mappingMethod: claim
```

Behavior:

- Default behavior.
- Provisions a user from the identity provider preferred username.
- Fails if the username is already mapped to another identity.

Typical failure:

```text
Could not create user because another identity already maps to this username
```

Use case:

- Simple environments with one identity provider.

Risk:

- Multiple identity providers returning the same username can conflict.

---

### 4.2 `add`

```yaml
mappingMethod: add
```

Behavior:

- If the user already exists, OpenShift adds the new identity to the existing user.
- Useful when multiple identity providers represent the same people.

Use case:

```text
Existing HTPasswd users are migrated to LDAP or OIDC but usernames remain same.
```

Risk:

- If misused, an identity from another provider can be attached to an existing user unexpectedly.

---

### 4.3 `lookup`

```yaml
mappingMethod: lookup
```

Behavior:

- OpenShift does not auto-create users or identities.
- Admin must manually create `User`, `Identity`, and `UserIdentityMapping`.

Use case:

- Whitelisting only approved LDAP/OIDC users.
- Highly controlled enterprise environments.

Required commands:

```bash
oc create user rakesh
oc create identity ldapidp:uid=rakesh,ou=users,dc=example,dc=com
oc create useridentitymapping ldapidp:uid=rakesh,ou=users,dc=example,dc=com rakesh
```

Common issue:

```text
Credentials are correct in LDAP, but login fails because mappingMethod lookup requires manual mapping.
```

## 5. Senior-level troubleshooting methodology

Use this sequence during real incidents.

### Phase 1: Identify blast radius

Ask:

```text
Is login failing for all users or one user?
Is only web console failing or both web console and oc CLI?
Is kubeadmin also failing?
Was OAuth/IDP/secret/certificate changed recently?
Was OpenShift upgraded recently?
Is the API reachable?
```

### Phase 2: Separate login path

Test API, OAuth, and user session separately:

```bash
oc whoami
oc whoami --show-server
oc whoami --show-token
oc login -u <username> -p '<password>' https://api.<cluster>:6443 --loglevel=8
```

For deeper CLI troubleshooting:

```bash
oc login -u <username> -p '<password>' https://api.<cluster>:6443 --loglevel=10
```

### Phase 3: Check cluster authentication health

```bash
oc get co authentication kube-apiserver openshift-apiserver console ingress
```

Expected healthy output:

```text
NAME                  AVAILABLE   PROGRESSING   DEGRADED
authentication        True        False         False
kube-apiserver        True        False         False
openshift-apiserver   True        False         False
console               True        False         False
ingress               True        False         False
```

If `authentication` is `Degraded=True` or `Available=False`, login may fail globally.

Describe it:

```bash
oc describe co authentication
```

Check related events:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
```

## 7. Error message interpretation

### 7.1 `error: You must be logged in to the server (Unauthorized)`

Meaning:

- Current token is expired or invalid.
- Kubeconfig context points to wrong cluster.
- API server rejected token.
- OAuth server issued no valid token.

Check:

```bash
oc whoami --show-server
oc config current-context
oc config view --minify
oc login https://api.<cluster>:6443 -u <username> -p '<password>' --loglevel=8
```

Possible fix:

```bash
oc logout
oc login https://api.<cluster>:6443 -u <username> -p '<password>'
```

---

### 7.2 `Login failed (401 Unauthorized)`

Meaning:

- Wrong password.
- Identity provider rejected credentials.
- LDAP bind failed.
- Basic authentication backend returned 401.
- HTPasswd file does not contain user or password hash is wrong.

Check identity provider logs and OpenShift OAuth logs.

```bash
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

---

### 7.3 `Forbidden`

Meaning:

- Login succeeded.
- RBAC denied the requested action.

Confirm:

```bash
oc whoami
oc auth can-i get nodes
oc auth can-i get pods -n <namespace>
```

Fix by binding appropriate role:

```bash
oc adm policy add-cluster-role-to-user cluster-admin <username>
```

Or namespace role:

```bash
oc adm policy add-role-to-user edit <username> -n <namespace>
```

Do not troubleshoot IDP if the actual error is `Forbidden`.

---

### 7.4 `x509: certificate signed by unknown authority`

This can happen in two places:

1. `oc` client does not trust OpenShift API/route certificate.
2. OpenShift OAuth server does not trust external IDP certificate.

For `oc` client trust:

```bash
oc login https://api.<cluster>:6443 --certificate-authority=/path/to/ca.crt
```

For external IDP trust, verify the CA config map in `openshift-config`:

```bash
oc get configmap ca-config-map -n openshift-config -o yaml
```

The certificate bundle must usually be stored under the key:

```text
ca.crt
```

---

### 7.5 `Internal error occurred: unexpected response: 500`

Meaning:

- OAuth server or backend IDP returned an unexpected error.
- User/identity mapping might be corrupt.
- Backend identity provider response might be malformed.
- OIDC claims might not match configuration.
- Basic-auth backend might return non-200 or invalid JSON.

For a single-user failure, inspect user and identity objects:

```bash
oc get user <username> -o yaml
oc get identity | grep -i <username>
oc get identity <identity-name> -o yaml
```

If identity data is wrong, backup before deleting:

```bash
oc get user <username> -o yaml > backup-user-<username>.yaml
oc get identity <identity-name> -o yaml > backup-identity-<username>.yaml

oc delete identity <identity-name>
```

Then ask the user to log in again so OpenShift can recreate the identity mapping if the mapping method allows it.

Do not delete users/identities blindly in production. Always back up first.

---

### 7.6 Web console login fails, but `oc login` works

Possible causes:

- Browser cache/cookies issue.
- Console operator issue.
- Console route/TLS issue.
- OAuth redirect problem.
- OIDC redirect URI not configured for console.
- Corporate proxy/security appliance changing headers.

Check:

```bash
oc get co console
oc get pods -n openshift-console
oc logs -n openshift-console deploy/console --tail=200
oc get route -n openshift-console
oc get route -n openshift-authentication
```

Also test private/incognito browser window.

---

### 7.7 `oc login` fails, but web console works

Possible causes:

- OIDC provider requires browser-based authorization flow.
- CLI cannot perform username/password login with that IDP.
- User must copy login token from web console.
- `openshift-challenging-client` flow unsupported by that IDP.

Use web console:

```text
User menu -> Copy login command -> Display token -> oc login --token=<token>
```

Then run:

```bash
oc whoami
```

## 8. Troubleshooting OAuth route and network path

The OAuth route is critical. If it is broken, login fails even when the IDP is healthy.

### 8.1 Get OAuth route

```bash
oc get route oauth-openshift -n openshift-authentication
oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}{"\n"}'
```

Expected:

```text
oauth-openshift.apps.cluster.example.com
```

### 8.2 DNS check

From your workstation:

```bash
nslookup oauth-openshift.apps.cluster.example.com
dig oauth-openshift.apps.cluster.example.com
```

From inside the cluster:

```bash
oc run dns-test --rm -it --image=registry.access.redhat.com/ubi9/ubi --restart=Never -- bash
curl -kv https://oauth-openshift.apps.cluster.example.com
```

### 8.3 Route and ingress check

```bash
oc get co ingress
oc get pods -n openshift-ingress
oc get route -n openshift-authentication oauth-openshift -o yaml
```

If ingress is degraded, OAuth route can be unreachable.

### 8.4 TLS check

```bash
openssl s_client -connect oauth-openshift.apps.cluster.example.com:443 -servername oauth-openshift.apps.cluster.example.com </dev/null
```

Look for:

```text
Verify return code: 0 (ok)
```

If certificate validation fails, check whether the wildcard/apps certificate or custom OAuth certificate was changed.

## 11. HTPasswd login troubleshooting

HTPasswd is common in labs, exams, bootstrap access, and small clusters.

### 11.1 Example HTPasswd configuration

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: local_htpasswd
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpasswd-secret
```

### 11.2 Verify secret exists

```bash
oc get secret htpasswd-secret -n openshift-config
oc describe secret htpasswd-secret -n openshift-config
```

The secret must contain an `htpasswd` file key.

Check keys:

```bash
oc get secret htpasswd-secret -n openshift-config -o jsonpath='{.data}'
```

### 11.3 Create or update HTPasswd secret

Create file:

```bash
htpasswd -c -B -b users.htpasswd rakesh 'RedHat@123'
```

Add another user:

```bash
htpasswd -B -b users.htpasswd admin1 'Admin@123'
```

Create secret:

```bash
oc create secret generic htpasswd-secret \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config
```

Update secret:

```bash
oc create secret generic htpasswd-secret \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

### 11.4 Wait for rollout

```bash
oc get co authentication
oc get pods -n openshift-authentication
```

Then test:

```bash
oc login -u rakesh -p 'RedHat@123' https://api.<cluster>:6443
oc whoami
```

### 11.5 Common HTPasswd mistakes

| Mistake | Result |
|---|---|
| Secret created in wrong namespace | OAuth cannot find it |
| Secret key not named `htpasswd` | Login fails |
| Forgot to update OAuth CR | Secret exists but unused |
| Password shell special character not quoted | Wrong password stored |
| No rollout after update | Old password still active briefly |
| User removed from htpasswd but identity still exists | User may still have identity object; token behavior depends on existing sessions |

### 11.6 HTPasswd single-user failure checklist

```bash
oc get oauth cluster -o yaml | grep -A10 HTPasswd
oc get secret -n openshift-config htpasswd-secret -o yaml
oc extract secret/htpasswd-secret -n openshift-config --to=/tmp/htpass --confirm
cat /tmp/htpass/htpasswd
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

Test password locally:

```bash
htpasswd -vb /tmp/htpass/htpasswd rakesh 'RedHat@123'
```

## 12. LDAP login troubleshooting

LDAP is common in enterprise environments and often causes subtle failures.

### 12.1 LDAP login process

OpenShift LDAP authentication works like this:

```text
1. User enters username/password.
2. OAuth server builds LDAP search filter from configured URL.
3. OAuth server searches LDAP directory.
4. If exactly one LDAP entry is found, OAuth server binds as that DN using user password.
5. If bind succeeds, OpenShift creates identity using configured attributes.
6. User is mapped according to mappingMethod.
7. OAuth token is issued.
```

### 12.2 Example LDAP OAuth CR

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: ldapidp
    mappingMethod: claim
    type: LDAP
    ldap:
      attributes:
        id:
        - dn
        email:
        - mail
        name:
        - cn
        preferredUsername:
        - uid
      bindDN: "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com"
      bindPassword:
        name: ldap-secret
      ca:
        name: ldap-ca
      insecure: false
      url: "ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(objectClass=person)"
```

### 12.3 Verify LDAP secret

```bash
oc get secret ldap-secret -n openshift-config
oc get secret ldap-secret -n openshift-config -o jsonpath='{.data.bindPassword}' | base64 -d; echo
```

The key must be:

```text
bindPassword
```

### 12.4 Verify LDAP CA config map

```bash
oc get configmap ldap-ca -n openshift-config -o yaml
```

The key must be:

```text
ca.crt
```

### 12.5 Test LDAP connectivity from cluster

Use a temporary debug pod if allowed:

```bash
oc run ldap-test --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi \
  --restart=Never -- bash
```

Install tools if repo access is available:

```bash
dnf install -y openldap-clients
```

Test LDAPS certificate:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com </dev/null
```

Test LDAP search:

```bash
ldapsearch -H ldaps://ldap.example.com:636 \
  -D 'cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com' \
  -W \
  -b 'ou=users,dc=example,dc=com' \
  '(&(objectClass=person)(uid=rakesh))'
```

### 12.6 LDAP URL mistakes

LDAP URL syntax:

```text
ldap://host:port/basedn?attribute?scope?filter
ldaps://host:port/basedn?attribute?scope?filter
```

Example:

```text
ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(objectClass=person)
```

Common mistakes:

| Mistake | Result |
|---|---|
| Wrong base DN | User not found |
| Wrong attribute, e.g. using `cn` but login uses `uid` | Search returns zero entries |
| Search returns multiple entries | Access denied |
| Wrong filter | User not found |
| `insecure: true` with `ldaps://` | Invalid/inconsistent secure LDAP config |
| Missing CA for LDAPS | x509 error |
| Wrong bindDN/bindPassword | Search fails |
| LDAP firewall blocked from cluster nodes | Timeout or connection refused |

### 12.7 LDAP error interpretation

| Error | Likely cause |
|---|---|
| `invalid credentials` | User password wrong or bind password wrong |
| `no such object` | Base DN wrong |
| `size limit exceeded` | Search filter too broad |
| `can't contact LDAP server` | DNS/firewall/TLS/network issue |
| `certificate signed by unknown authority` | Missing/wrong CA config map |
| User exists in LDAP but cannot login | Search filter does not return exactly one entry |

### 12.8 LDAP single-user failure

Check the actual LDAP identity object:

```bash
oc get identity | grep -i rakesh
oc get user rakesh -o yaml
```

If mapping conflict:

```bash
oc get user rakesh -o yaml
oc get identity <identity-name> -o yaml
```

If wrong identity is mapped, backup and carefully recreate mapping.

## 13. OIDC / Keycloak / Red Hat SSO login troubleshooting

OIDC is common with Keycloak, Red Hat SSO, Microsoft Entra ID, Okta, Ping, GitLab, Google, and other enterprise identity platforms.

### 13.1 OIDC login process

```text
1. User accesses console or token request URL.
2. OpenShift redirects user to OIDC issuer authorization endpoint.
3. User authenticates with OIDC provider.
4. OIDC provider redirects back to OpenShift OAuth callback URL.
5. OpenShift validates issuer, client secret, token signature, claims, and optional UserInfo.
6. OpenShift maps identity to User.
7. OAuth token is issued for OpenShift API.
```

### 13.2 Example OIDC OAuth CR

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: keycloak
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift
      clientSecret:
        name: keycloak-client-secret
      issuer: https://keycloak.example.com/realms/ocp
      claims:
        preferredUsername:
        - preferred_username
        name:
        - name
        email:
        - email
      extraScopes:
      - email
      - profile
```

### 13.3 Verify OIDC secret

```bash
oc get secret keycloak-client-secret -n openshift-config
oc get secret keycloak-client-secret -n openshift-config -o jsonpath='{.data.clientSecret}' | base64 -d; echo
```

The key must be:

```text
clientSecret
```

### 13.4 Verify issuer discovery

From a workstation or debug pod:

```bash
curl -k https://keycloak.example.com/realms/ocp/.well-known/openid-configuration | jq
```

Check:

```text
issuer
authorization_endpoint
token_endpoint
jwks_uri
userinfo_endpoint
```

The `issuer` value must exactly match what is configured in OpenShift.

### 13.5 OIDC redirect URI

OIDC provider must allow OpenShift callback redirect URI.

Common callback pattern:

```text
https://oauth-openshift.apps.<cluster-domain>/oauth2callback/<idp-name>
```

Example:

```text
https://oauth-openshift.apps.ocp4.example.com/oauth2callback/keycloak
```

If IDP name is `keycloak`, callback path must include `keycloak`.

If you rename the IDP, the callback URL changes.

### 13.6 OIDC common mistakes

| Mistake | Result |
|---|---|
| Wrong issuer URL | Issuer validation fails |
| Missing `.well-known/openid-configuration` | OpenShift cannot discover provider |
| Wrong client secret | Token exchange fails |
| Redirect URI missing in IDP | Browser login fails after IDP authentication |
| Claim `preferred_username` missing | User provisioning/mapping issue |
| Claim `sub` unstable or changed | Identity mismatch |
| IDP certificate untrusted | x509 failure |
| User must use browser token for CLI | `oc login -u -p` fails but token login works |
| IDP behind proxy not reachable from cluster | Timeout |

### 13.7 OIDC CLI issue: username/password login fails

Many OIDC providers do not support direct CLI username/password login.

Correct method:

```text
OpenShift console -> Copy login command -> Display token
```

Then:

```bash
oc login --token=<token> --server=https://api.<cluster>:6443
```

### 13.8 OIDC Keycloak-specific checks

In Keycloak, check:

```text
Realm URL
Client ID
Client secret
Valid redirect URIs
Web origins
Standard flow enabled
Direct access grants if you expect username/password CLI login
User enabled
Email verified if required by policy
Required actions pending
Mapper for preferred_username/email/name
```

For OpenShift, the most important Keycloak client settings are usually:

```text
Client authentication: enabled for confidential client
Standard flow: enabled
Valid redirect URI: https://oauth-openshift.apps.<cluster>/oauth2callback/<idp-name>
```

### 13.9 OIDC single-user failure

Check whether the user’s OIDC `sub` changed. This can happen after user recreation in the IdP.

Check OpenShift identity:

```bash
oc get identity | grep -i <username>
oc get user <username> -o yaml
```

If the old identity is stale, back up and delete carefully:

```bash
oc get user <username> -o yaml > backup-user.yaml
oc get identity <identity-name> -o yaml > backup-identity.yaml
oc delete identity <identity-name>
```

Then retry login.

## 14. Request-header identity provider troubleshooting

Request-header authentication is used with an authenticating proxy.

Flow:

```text
User -> External auth proxy -> OpenShift OAuth -> Request headers -> User identity
```

Example headers:

```text
X-Remote-User
X-Remote-Group
X-Remote-Email
```

Important points:

- The proxy must authenticate the user before forwarding to OpenShift.
- OpenShift must trust the proxy client certificate/CA.
- Header spoofing must be prevented.
- Request-header IDP cannot be freely mixed with direct password login IDPs in some configurations.

Check:

```bash
oc get oauth cluster -o yaml
oc get configmap -n openshift-config
oc get secret -n openshift-config
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300
```

Common issues:

| Issue | Result |
|---|---|
| Proxy not sending `X-Remote-User` | Login fails |
| Wrong header name in OAuth config | User cannot be identified |
| Proxy cert not trusted | TLS/authentication failure |
| Users can bypass proxy | Serious security vulnerability |
| Header contains unsupported username characters | Login/user creation fails |

## 15. Basic authentication provider troubleshooting

Basic authentication provider validates credentials against a remote HTTPS backend.

Expected backend behavior:

| Backend response | Meaning |
|---|---|
| HTTP 200 with `sub` key | Successful authentication |
| HTTP 401 | Failed authentication |
| Non-200 or JSON with `error` | Backend/authentication error |

Example successful JSON:

```json
{"sub":"userid", "name":"User Name", "email":"user@example.com"}
```

Test from a control-plane reachable environment:

```bash
curl --cacert /path/to/ca.crt \
  --cert /path/to/client.crt \
  --key /path/to/client.key \
  -u <user>:<password> \
  -v https://www.example.com/remote-idp
```

Common failures:

| Failure | Cause |
|---|---|
| Network timeout | OAuth server cannot reach backend |
| 401 | Invalid credentials |
| 500 | Backend application error |
| Invalid JSON | Backend response format wrong |
| Missing `sub` | OpenShift cannot identify user |
| x509 | Backend TLS CA not trusted |

## 26. Certificate and CA troubleshooting in depth

### 26.1 OpenShift route/API certificate trust

User-side issue:

```text
oc login fails because workstation does not trust cluster cert.
```

Fix:

```bash
oc login https://api.<cluster>:6443 --certificate-authority=/path/to/ca.crt
```

Or add cluster CA to system trust store.

### 26.2 IDP certificate trust

Cluster-side issue:

```text
OAuth server cannot trust LDAP/OIDC/basic-auth backend cert.
```

Fix:

```bash
oc create configmap idp-ca \
  --from-file=ca.crt=/path/to/idp-ca.crt \
  -n openshift-config
```

Then reference it in OAuth config.

### 26.3 Check cert from OAuth pod perspective

```bash
oc run tls-test --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi \
  --restart=Never -- bash

openssl s_client -connect keycloak.example.com:443 -servername keycloak.example.com </dev/null
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com </dev/null
```

Look for:

```text
certificate chain
SAN/CN matches hostname
expiration date
issuer
verify return code
```

### 26.4 Common cert mistakes

| Mistake | Symptom |
|---|---|
| CA config map key not `ca.crt` | OpenShift does not load CA |
| Intermediate CA missing | x509 unknown authority |
| Cert CN/SAN does not match hostname | hostname verification failure |
| Expired IDP certificate | sudden login outage |
| Corporate SSL inspection cert not trusted | OIDC/LDAP HTTPS failure |

| Issue | Cause |

## 31. Interview-style troubleshooting answer

### Question

```text
A user says they cannot login to OpenShift. How would you troubleshoot?
```

### Senior answer

I would first determine whether this is an authentication problem, an authorization problem, or a console/browser problem. I would ask whether the failure affects one user or all users, whether CLI login fails as well as web console login, and whether there was a recent OAuth, LDAP, OIDC, certificate, route, or cluster upgrade change.

I would test the API and current context using:

```bash
oc whoami
oc whoami --show-server
oc login https://api.<cluster>:6443 -u <username> -p '<password>' --loglevel=8
```

If the user can authenticate but receives `Forbidden`, I would stop troubleshooting the identity provider and check RBAC:

```bash
oc auth can-i get pods -n <namespace> --as=<username>
oc get rolebinding -A | grep <username>
oc get clusterrolebinding | grep <username>
```

If login truly fails, I would check authentication operator and OAuth health:

```bash
oc get co authentication kube-apiserver openshift-apiserver console ingress
oc describe co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300
```

For all-user failure, I would suspect OAuth rollout, route, DNS, TLS, IDP backend reachability, or a bad OAuth configuration. I would inspect:

```bash
oc get oauth cluster -o yaml
oc get route oauth-openshift -n openshift-authentication
oc get secret -n openshift-config
oc get configmap -n openshift-config
```

For one-user failure, I would inspect User and Identity mapping:

```bash
oc get user <username> -o yaml
oc get identity | grep -i <username>
oc get identity <identity-name> -o yaml
```

If LDAP is used, I would validate base DN, search filter, bindDN, bindPassword, LDAPS CA, and whether the search returns exactly one entry. If OIDC is used, I would validate issuer discovery, client secret, redirect URI, claims, and whether CLI login requires copy-login-token instead of username/password. If HTPasswd is used, I would verify the secret key, password hash, and OAuth rollout.

I would not delete users or identities without backup. If identity corruption is confirmed, I would back up the user and identity YAML, delete the stale identity, and ask the user to login again so OpenShift can recreate mapping where allowed.

```bash
oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}{"\n"}'
```

### Check OIDC issuer

```bash
curl -k https://keycloak.example.com/realms/ocp/.well-known/openid-configuration | jq .issuer
```

This must match:

```yaml
issuer: https://keycloak.example.com/realms/ocp
```

### Fix provider client

In Keycloak/SSO, configure valid redirect URI:

```text
https://oauth-openshift.apps.<cluster-domain>/oauth2callback/keycloak
```

## 35. Checklist before closing the incident

Before closing a failed login incident, confirm:

```text
[ ] User can login successfully.
[ ] `oc whoami` returns expected username.
[ ] Web console works if required.
[ ] User has expected project/cluster access.
[ ] RBAC verified with `oc auth can-i`.
[ ] OAuth operator is healthy.
[ ] OAuth pods are stable.
[ ] No authentication operator degraded condition remains.
[ ] No temporary cluster-admin access left unnecessarily.
[ ] Any changed secret/cert/OAuth config is documented.
[ ] Backup of changed authentication resources is stored securely.
[ ] Root cause is recorded.
```

## 36. Root cause examples

### Example 1: All users cannot login after LDAP certificate renewal

Root cause:

```text
LDAP server certificate was renewed with a new intermediate CA. OpenShift LDAP CA config map still had only old root CA.
```

Fix:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=new-full-chain.pem \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

Then watch authentication rollout.

---

### Example 2: One OIDC user cannot login after account recreation

Root cause:

```text
User was deleted and recreated in Keycloak. Username stayed same, but OIDC sub changed. OpenShift identity still referenced old subject.
```

Fix:

```bash
oc get user rakesh -o yaml > backup-user-rakesh.yaml
oc get identity keycloak:<old-sub> -o yaml > backup-identity-rakesh.yaml
oc delete identity keycloak:<old-sub>
```

User logged in again and a new identity was created.

---

### Example 3: User can login but cannot see projects

Root cause:

```text
Authentication successful. LDAP group sync failed, so RBAC group membership was missing.
```

Fix:

```bash
oc get groups
oc get group dev-team -o yaml
oc adm groups sync --sync-config=ldap-group-sync.yaml --confirm
```

Then verify:

```bash
oc auth can-i get pods -n dev --as=<username>
```

---

### Example 4: CLI login fails for OIDC but web console works

Root cause:

```text
OIDC provider does not support direct username/password CLI flow. Browser authorization flow works.
```

Fix:

```text
Use web console -> Copy login command -> oc login --token=<token>
```

## 38. Final senior-admin mental model

When troubleshooting OpenShift failed login issues, think in layers:

```text
1. Is the API reachable?
2. Is the OAuth route reachable?
3. Are authentication operator and OAuth pods healthy?
4. Is OAuth configuration valid?
5. Are referenced secrets/config maps present and correct?
6. Can OAuth reach the external identity provider?
7. Does the IDP accept the credentials?
8. Does OpenShift receive the expected identity/claims/attributes?
9. Does mappingMethod allow this identity to map to a user?
10. Is the user actually authenticated but blocked by RBAC?
```

Do not start by deleting users. Do not start by changing LDAP or OIDC settings blindly. Start with blast radius, logs, operator status, route/DNS/TLS, then identity mapping.

A good OpenShift administrator fixes login issues by isolating the exact failing layer, validating with commands, backing up objects before modification, and preserving emergency admin access at all times.
