## 1. What CRI-O Is in OpenShift

`CRI-O` is the container runtime used by OpenShift Container Platform nodes. It implements the Kubernetes **Container Runtime Interface** (`CRI`) and is responsible for running pods and containers requested by the kubelet.

In simple terms:

```text
Kubernetes API Server
        ↓
Scheduler decides pod placement
        ↓
Kubelet on target node receives pod spec
        ↓
Kubelet talks to CRI-O through CRI
        ↓
CRI-O pulls image, creates sandbox, configures runtime, starts container
        ↓
Low-level runtime such as crun/runc creates Linux process
```

OpenShift uses CRI-O instead of Docker as the node runtime. On RHCOS-based OpenShift nodes, CRI-O runs directly on the host as a `systemd` service named:

```bash
crio.service
```

CRI-O is not just another pod. It is part of the node operating system layer. If CRI-O is broken, kubelet cannot reliably create pod sandboxes, start containers, pull images, or report container runtime readiness.

## 2. Why CRI-O Logs Matter for Node-Level Administration

For an advanced OpenShift administrator, CRI-O logs are critical because many pod-level symptoms are actually node-runtime problems.

A pod may show:

```text
ContainerCreating
ImagePullBackOff
CrashLoopBackOff
CreateContainerError
RunContainerError
FailedCreatePodSandBox
NodeNotReady
```

But the real cause may be inside CRI-O logs:

```text
failed to pull image
failed to create container
failed to create pod sandbox
failed to setup network for sandbox
overlay mount failed
permission denied
context deadline exceeded
runtime exited unexpectedly
failed to find plugin
invalid image signature
x509 certificate signed by unknown authority
```

CRI-O logs are especially important in these areas:

| Area | Why CRI-O Logs Help |
|---|---|
| Image pull failures | Shows registry, auth, TLS, proxy, mirror, pull secret, and signature errors |
| Pod sandbox failures | Shows CNI/OVN-Kubernetes, pause image, namespace, and runtime errors |
| MachineConfig changes | Shows CRI-O restart/reload after config, registry, CA, or runtime changes |
| Node NotReady | Kubelet often reports runtime unavailable; CRI-O logs show why |
| Storage issues | Shows overlay, graphroot, inode, disk, and container storage errors |
| Security failures | Shows SELinux, seccomp, capabilities, cgroup, and permission problems |
| Upgrade issues | Shows CRI-O version/runtime/storage incompatibilities after reboot |
| Registry trust | Shows CA/certificate errors after custom CA or mirror changes |

A senior OpenShift admin does not troubleshoot runtime-related pod failures only from `oc describe pod`. You always correlate:

```text
Pod events → kubelet logs → CRI-O logs → node state → MachineConfig state
```

## 3. Where CRI-O Logs Come From

CRI-O logging has multiple layers.

### 3.1 CRI-O systemd journal logs

The main CRI-O service logs are stored in `journald` under:

```bash
crio.service
```

Common commands:

```bash
journalctl -u crio.service
journalctl -b -u crio.service
journalctl -b -f -u crio.service
```

These logs show CRI-O service lifecycle and runtime operations.

### 3.2 Kubelet logs related to CRI-O

Kubelet talks to CRI-O. Runtime problems are often visible first in kubelet logs:

```bash
journalctl -u kubelet.service
journalctl -b -u kubelet.service -u crio.service
```

Kubelet logs may show:

```text
container runtime is down
PLEG is not healthy
failed to create pod sandbox
runtime network not ready
container runtime status check may not have completed yet
```

CRI-O logs usually provide the lower-level reason.

### 3.3 Container logs under `/var/log/containers`

Application container logs are normally symlinked under:

```bash
/var/log/containers/
```

These are not CRI-O service logs, but they help correlate whether the runtime started the container successfully and whether the process then failed inside the container.

### 3.4 Raw container runtime storage logs

Some low-level container logs may exist under container storage paths such as:

```bash
/var/lib/containers/storage/overlay-containers/*/userdata/ctr.log
```

This is more useful in installation/bootstrap or severe runtime troubleshooting, not for routine application debugging.

### 3.5 MachineConfig and MCD logs

If CRI-O was restarted because of MachineConfig changes, also inspect Machine Config Daemon logs:

```bash
oc logs -n openshift-machine-config-operator daemonset/machine-config-daemon -c machine-config-daemon
```

Or for a specific node's MCD pod:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node-name>
oc logs -n openshift-machine-config-operator <mcd-pod-name> -c machine-config-daemon
```

## 4. High-Level Troubleshooting Flow

Use this decision flow when you suspect a CRI-O problem:

```text
1. Identify affected pod/node
   ↓
2. Check pod events
   ↓
3. Check node condition and kubelet status
   ↓
4. Check CRI-O logs
   ↓
5. Check CRI-O service health
   ↓
6. Check MachineConfig/MCP state
   ↓
7. Check storage, registry, network, SELinux, or runtime-specific cause
   ↓
8. Fix root cause
   ↓
9. Validate new pod scheduling and runtime creation
```

Basic first commands:

```bash
oc get nodes -o wide
oc describe node <node-name>
oc get pods -A -o wide | grep <node-name>
oc get events -A --sort-by='.lastTimestamp'
oc get mcp
oc get co machine-config
```

Then move to runtime logs:

```bash
oc adm node-logs <node-name> -u crio
oc adm node-logs <node-name> -u kubelet
```

## 5. Prerequisites and Access Requirements

To check CRI-O logs properly, you normally need one of the following:

1. `cluster-admin` access to OpenShift.
2. Ability to run `oc adm node-logs`.
3. Ability to run `oc debug node/<node-name>`.
4. SSH or console access to the node as `core` user for break-glass troubleshooting.

Useful login verification:

```bash
oc whoami
oc auth can-i get nodes
oc auth can-i get nodes/log
oc auth can-i create pods -n default
```

Check nodes:

```bash
oc get nodes
```

Example:

```text
NAME                 STATUS   ROLES                  AGE   VERSION

master-1.example     Ready    control-plane,master   40d   v1.30.x

worker-0.example     Ready    worker                 40d   v1.30.x
```

## 6. Method 1: Check CRI-O Logs Without SSH Using `oc adm node-logs`

This is usually the safest and preferred method because it does not require direct SSH access to the node.

### 6.1 Check CRI-O logs for one node

```bash
oc adm node-logs <node-name> -u crio
```

Example:

```bash
oc adm node-logs worker-0.example.com -u crio
```

For current boot only, depending on `oc` version and available flags, use journal-related options such as `--since`, `--tail`, or `--boot` if supported by your cluster CLI version:

```bash
oc adm node-logs worker-0.example.com -u crio --tail=200
oc adm node-logs worker-0.example.com -u crio --since=1h
```

If unsure:

```bash
oc adm node-logs --help
```

### 6.2 Check CRI-O logs on all worker nodes

```bash
oc adm node-logs --role=worker -u crio
```

### 6.3 Check CRI-O logs on all control plane nodes

```bash
oc adm node-logs --role=master -u crio
```

Many OpenShift versions still use `master` as the node role label and CLI role selector even though the Kubernetes role is also shown as `control-plane`.

### 6.4 Check kubelet and CRI-O together

Some versions allow multiple `-u` values. If supported:

```bash
oc adm node-logs <node-name> -u kubelet -u crio
```

If not supported, run separately:

```bash
oc adm node-logs <node-name> -u kubelet > kubelet.log
oc adm node-logs <node-name> -u crio > crio.log
```

Then compare timestamps.

### 6.5 Save logs to files for analysis

```bash
mkdir -p logs/<node-name>
oc adm node-logs <node-name> -u crio --tail=1000 > logs/<node-name>/crio.log
oc adm node-logs <node-name> -u kubelet --tail=1000 > logs/<node-name>/kubelet.log
```

Search errors:

```bash
grep -Ei 'error|failed|denied|timeout|unavailable|panic|fatal|x509|overlay|cni|sandbox|runtime' logs/<node-name>/crio.log
```

### 6.6 Advantages of `oc adm node-logs`

| Advantage | Explanation |
|---|---|
| No SSH required | Useful when direct host access is disabled |
| Works through API | Uses OpenShift control plane access |
| Good for audits | Less intrusive than logging into hosts |
| Fast triage | Ideal for checking multiple nodes |

### 6.7 Limitations

| Limitation | Explanation |
|---|---|
| Requires API availability | If API is down, this method will not work |
| Requires permission | User must be authorized to read node logs |
| May be less flexible | Direct `journalctl` has more advanced filtering |
| Not enough for severe node failure | If node is unreachable, use SSH/console/provider logs |

## 7. Method 2: Check CRI-O Logs Through `oc debug node`

`oc debug node/<node-name>` creates a privileged debug pod on the node and mounts the host filesystem at `/host`.

### 7.1 Start a debug shell

```bash
oc debug node/<node-name>
```

Example:

```bash
oc debug node/worker-0.example.com
```

You will enter a shell similar to:

```bash
sh-5.1#
```

### 7.2 Chroot into the host

```bash
chroot /host
```

Now your shell sees the host filesystem as `/`.

### 7.3 Check CRI-O logs from the node

```bash
journalctl -b -u crio.service --no-pager
```

Follow live logs:

```bash
journalctl -b -f -u crio.service
```

Check recent errors:

```bash
journalctl -b -u crio.service -p warning..alert --no-pager
```

Check CRI-O and kubelet together:

```bash
journalctl -b -u kubelet.service -u crio.service --no-pager
```

### 7.4 Check CRI-O service state

```bash
systemctl status crio --no-pager
systemctl is-active crio
systemctl is-enabled crio
```

### 7.5 Check CRI-O configuration

```bash
crio status info
crio status config
crio config | grep -E 'log_level|default_runtime|pause_image|pids_limit|cgroup_manager'
```

### 7.6 Check containers and pods through CRI tools

```bash
crictl info
crictl pods
crictl ps -a
crictl images
```

Inspect a pod sandbox:

```bash
crictl pods | grep <pod-name>
crictl inspectp <sandbox-id>
```

Inspect a container:

```bash
crictl ps -a | grep <container-name>
crictl inspect <container-id>
```

### 7.7 Exit safely

```bash
exit   # exit chroot
exit   # exit debug pod
```

Do not leave debug shells open on production nodes.

## 8. Method 3: Check CRI-O Logs Using SSH or Console Access

SSH should normally be a break-glass method in OpenShift 4. Prefer `oc adm node-logs` or `oc debug node` first.

### 8.1 SSH to node

```bash
ssh core@<node-name>
```

Escalate:

```bash
sudo -i
```

### 8.2 Check CRI-O logs

```bash
journalctl -b -u crio.service --no-pager
journalctl -b -f -u crio.service
journalctl -b -u kubelet.service -u crio.service --no-pager
```

### 8.3 Check previous boot logs

If the node rebooted:

```bash
journalctl --list-boots
journalctl -b -1 -u crio.service --no-pager
journalctl -b -1 -u kubelet.service -u crio.service --no-pager
```

### 8.4 When SSH/console is required

Use SSH/console if:

- API server is unavailable.
- `oc debug node` cannot start because CRI-O itself is broken.
- Node is `NotReady` and not accepting debug pods.
- You need boot-time logs after failed node upgrade.
- You need to inspect disk, filesystem, or container storage directly.

## 9. Important `journalctl` Commands for CRI-O

### 9.1 Current boot CRI-O logs

```bash
journalctl -b -u crio.service --no-pager
```

### 9.2 Follow live CRI-O logs

```bash
journalctl -b -f -u crio.service
```

### 9.3 Show last 200 lines

```bash
journalctl -b -u crio.service -n 200 --no-pager
```

### 9.4 Show CRI-O logs since a time

```bash
journalctl -u crio.service --since "2026-07-03 15:30:00" --no-pager
```

### 9.5 Show logs between two times

```bash
journalctl -u crio.service \
  --since "2026-07-03 15:30:00" \
  --until "2026-07-03 16:00:00" \
  --no-pager
```

### 9.6 Show only warnings and errors

```bash
journalctl -b -u crio.service -p warning..alert --no-pager
```

### 9.7 Show high precision timestamps

```bash
journalctl -b -u crio.service -o short-precise --no-pager
```

### 9.8 Show JSON output

```bash
journalctl -b -u crio.service -o json-pretty --no-pager
```

### 9.9 Show previous boot logs

```bash
journalctl --list-boots
journalctl -b -1 -u crio.service --no-pager
```

### 9.10 Check CRI-O with kubelet together

```bash
journalctl -b -u kubelet.service -u crio.service -o short-precise --no-pager
```

This is one of the most useful commands during production incidents.

## 10. Correlating CRI-O Logs with Kubelet Logs

CRI-O and kubelet must be analyzed together.

### 10.1 Relationship

```text
Kubelet asks CRI-O to create pod/container
CRI-O performs image/runtime/storage/network operation
CRI-O returns success or error
Kubelet records pod event and node condition
```

### 10.2 Typical kubelet message

```text
Failed to create pod sandbox: rpc error: code = Unknown desc = failed to setup network for sandbox
```

Then CRI-O may show:

```text
error configuring pod network: plugin type="ovn-k8s-cni-overlay" failed
```

### 10.3 Typical kubelet image pull message

```text
Failed to pull image "registry.example.com/app:v1": rpc error: code = Unknown desc = reading manifest failed
```

CRI-O may show:

```text
x509: certificate signed by unknown authority
```

### 10.4 Practical correlation command

```bash
journalctl -b -u kubelet.service -u crio.service -o short-precise --no-pager \
  | grep -Ei 'failed|error|sandbox|pull|runtime|network|x509|denied'
```

### 10.5 Time-based investigation

If pod failed at `16:05:20`, inspect around that time:

```bash
journalctl -u kubelet.service -u crio.service \
  --since "2026-07-03 16:00:00" \
  --until "2026-07-03 16:10:00" \
  -o short-precise --no-pager
```

## 11. Correlating CRI-O Logs with MachineConfig/MCO Activity

CRI-O configuration is commonly affected by MachineConfig-related operations:

- `ContainerRuntimeConfig`
- Registry mirror configuration
- Custom CA bundle
- ImageDigestMirrorSet / ImageTagMirrorSet
- Registry trust configuration
- Node disruption policy
- RHCOS update
- CRI-O runtime change from `crun` to `runc` or reverse
- Overlay storage size change

### 11.1 Check MachineConfigPool state

```bash
oc get mcp
```

Example:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-abc123                             True      False      False
worker    rendered-worker-def456                             False     True       False
```

### 11.2 Describe pool

```bash
oc describe mcp worker
```

Look for:

```text
Updating=True
Degraded=True
MachineConfigPoolUpdated
NodeDegraded
```

### 11.3 Check MachineConfigDaemon pods

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon
```

Logs for a specific MCD pod:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

### 11.4 Check what MachineConfig is applied to node

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

Expected healthy output:

```text
currentConfig == desiredConfig
state == Done
```

### 11.5 CRI-O restart caused by MCO

After some MachineConfig changes, the MCO may restart or reload `crio.service`, or drain and reboot nodes depending on the change type and node disruption policy.

Check CRI-O restart timestamps:

```bash
journalctl -u crio.service --since "2 hours ago" --no-pager | grep -Ei 'Starting|Started|Stopping|Stopped|reload|restart'
```

Check MCD logs around the same time:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --since=2h
```

## 12. Checking CRI-O Service Health

### 12.1 Systemd status

Inside `oc debug node` with `chroot /host`, or over SSH:

```bash
systemctl status crio --no-pager
```

Healthy indicators:

```text
Active: active (running)
Main PID: <pid>
```

Unhealthy indicators:

```text
Active: failed
start request repeated too quickly
Main process exited
code=exited, status=1/FAILURE
```

### 12.2 Is CRI-O active?

```bash
systemctl is-active crio
```

Expected:

```text
active
```

### 12.3 Check recent service restarts

```bash
journalctl -u crio.service --since "24 hours ago" --no-pager | grep -Ei 'starting|started|stopping|stopped|failed|panic|fatal'
```

### 12.4 Check CRI-O process

```bash
ps -ef | grep '[c]rio'
```

### 12.5 Check CRI socket

```bash
ls -l /var/run/crio/crio.sock
```

Expected:

```text
srw-rw----. 1 root root ... /var/run/crio/crio.sock
```

### 12.6 Kubelet runtime endpoint

Check kubelet command line or config:

```bash
ps -ef | grep '[k]ubelet'
cat /etc/kubernetes/kubelet.conf | grep -i runtime -n
```

## 14. Common CRI-O Log Patterns and What They Mean

### 14.1 `failed to pull image`

Meaning:

- Registry unreachable
- DNS issue
- TLS trust issue
- Pull secret issue
- Image does not exist
- Mirror misconfiguration
- Proxy issue
- Signature policy issue

Check:

```bash
oc describe pod <pod> -n <ns>
oc get secret -n <ns>
oc get image.config.openshift.io/cluster -o yaml
journalctl -b -u crio.service | grep -i pull
```

### 14.2 `x509: certificate signed by unknown authority`

Meaning:

CRI-O does not trust the registry certificate.

Common causes:

- Missing custom CA bundle
- Wrong CA key in ConfigMap
- MachineConfig not rolled out
- CRI-O not restarted after trust change
- Registry serving different certificate chain than expected

Check:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get cm -n openshift-config
oc get mcp
journalctl -b -u crio.service | grep -i x509
```

### 14.3 `unauthorized: authentication required`

Meaning:

CRI-O reached registry but authentication failed.

Check:

```bash
oc get secret -n <namespace>
oc get sa <serviceaccount> -n <namespace> -o yaml
oc get pullsecret -n openshift-config 2>/dev/null || true
oc get secret pull-secret -n openshift-config -o yaml
```

### 14.4 `failed to create pod sandbox`

Meaning:

CRI-O could not create the infrastructure sandbox container for the pod.

Possible causes:

- CNI/OVN-Kubernetes failure
- Pause image pull failure
- Runtime binary issue
- Namespace creation failure
- SELinux/cgroup/seccomp issue
- Disk/storage issue

Check:

```bash
journalctl -b -u kubelet.service -u crio.service | grep -Ei 'sandbox|network|cni|pause|pod'
oc get pods -n openshift-ovn-kubernetes -o wide
oc get pods -n openshift-multus -o wide
```

### 14.5 `failed to setup network for sandbox`

Meaning:

CRI-O created or attempted to create the sandbox, but CNI plugin failed.

Check:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --tail=200
journalctl -b -u crio.service | grep -Ei 'cni|network|sandbox'
```

### 14.6 `no space left on device`

Meaning:

Disk or inode exhaustion on the node.

Check:

```bash
df -h
df -ih
du -sh /var/lib/containers/* 2>/dev/null
crictl images
crictl ps -a
```

Also check kubelet eviction events:

```bash
oc describe node <node-name> | grep -A20 -i pressure
```

### 14.7 `overlay` or `lower layer` errors

Meaning:

Container storage corruption or missing overlay layer.

Example patterns:

```text
can't stat lower layer
error recreating the missing symlinks
/var/lib/containers/storage/overlay/... no such file or directory
```

This can lead to node NotReady or inability to create containers.

Initial checks:

```bash
journalctl -b -u crio.service | grep -Ei 'overlay|lower layer|storage|symlink'
df -h /var/lib/containers
df -ih /var/lib/containers
```

Do not immediately delete `/var/lib/containers`. Follow vendor-supported cleanup procedures and drain/cordon first.

### 14.8 `permission denied`

Meaning can vary:

- SELinux denial
- Invalid securityContext
- SCC conflict
- Filesystem permission issue
- Runtime trying to access restricted path
- Volume mount permission issue

Check:

```bash
journalctl -b -u crio.service | grep -i 'permission denied'
journalctl -b | grep -i avc
oc describe pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o yaml | grep -A20 securityContext
```

### 14.9 `context deadline exceeded`

Meaning:

Operation timed out.

Possible causes:

- Registry slowness
- Network issue
- CRI-O overloaded
- Disk I/O slowness
- CNI latency
- Kubelet/CRI call timeout

Check:

```bash
oc adm top node <node-name>
iostat -xz 1 5 2>/dev/null || true
journalctl -b -u crio.service -u kubelet.service | grep -i 'deadline exceeded'
```

### 14.10 `runtime exited unexpectedly`

Meaning:

Low-level runtime such as `crun` or `runc` failed.

Check:

```bash
crio status config | grep default_runtime
journalctl -b -u crio.service | grep -Ei 'crun|runc|runtime|conmon'
```

Image pull problems are among the most common CRI-O log investigations.

### 15.1 Start from pod event


```text
Failed to pull image
ErrImagePull
ImagePullBackOff
unauthorized
```

## 16. Troubleshooting Pod Sandbox and CNI Issues

A pod sandbox is the base environment for a pod. If sandbox creation fails, application containers will not start.

### 16.1 Pod event

```text
FailedCreatePodSandBox
failed to create pod sandbox
failed to setup network for sandbox
```

### 16.2 Check CRI-O logs

```bash
journalctl -b -u crio.service --no-pager | grep -Ei 'sandbox|network|cni|pod'
```

### 16.3 Check kubelet logs

```bash
journalctl -b -u kubelet.service --no-pager | grep -Ei 'sandbox|network|runtime|PLEG|CNI'
```

### 16.4 Check OpenShift network pods

For OVN-Kubernetes:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --tail=100
```

For Multus:

```bash
oc get pods -n openshift-multus -o wide

```

### 16.5 Check CNI files on node

Inside node:

```bash
ls -l /etc/cni/net.d/
ls -l /opt/cni/bin/
```

### 16.6 Senior-level interpretation

If CRI-O logs say:

```text
failed to setup network for sandbox
```

Do not assume CRI-O itself is broken. CRI-O calls the CNI plugin. The failing layer may be OVN-Kubernetes, Multus, network config, stale CNI cache, or node networking.

## 17. Troubleshooting Overlay Storage Issues

CRI-O stores container images and writable layers under container storage, commonly:

```bash
/var/lib/containers/storage
```

### 17.1 Symptoms

Pods may show:

```text
ContainerCreating
CreateContainerError
RunContainerError
NodeNotReady
```

CRI-O may show:

```text
can't stat lower layer
failed to mount container
no space left on device
error recreating missing symlinks
invalid argument
```

### 17.2 Check disk usage

```bash
df -h
df -ih
```

Important paths:

```bash
df -h /var
df -h /var/lib/containers
du -sh /var/lib/containers/storage 2>/dev/null
```

### 17.3 Check CRI-O storage config

```bash
cat /etc/containers/storage.conf
```

Look for:

```toml
[storage]
driver = "overlay"
runroot = "/var/run/containers/storage"
graphroot = "/var/lib/containers/storage"
```

### 17.4 Check images and stopped containers

```bash
crictl images
crictl ps -a
crictl pods
```

### 17.5 Cleanup warning

Do not manually delete random directories under:

```bash
/var/lib/containers/storage
```

Random deletion can corrupt container storage further.

If CRI-O storage is corrupted, the safe high-level approach is:

```text
1. Cordon node
2. Drain node
3. Stop kubelet
4. Stop workloads/pods through CRI tools if required
5. Stop CRI-O
6. Use supported CRI-O wipe procedure when appropriate
7. Start CRI-O and kubelet
8. Uncordon node
```

Only perform destructive storage cleanup during a maintenance window or under a vendor-supported runbook.

## 18. Troubleshooting SELinux, SCC, and Permission-Related Runtime Failures

OpenShift is security-focused. Runtime permission issues often involve several layers:

```text
SecurityContextConstraints → Pod securityContext → SELinux → filesystem permissions → CRI-O/runtime
```

### 18.1 Pod event may show

```text
container has runAsNonRoot and image will run as root
permission denied
operation not permitted
unable to start container process
```

### 18.2 CRI-O logs may show

```text
permission denied
operation not permitted
setresuid failed
mount permission denied
SELinux relabel failed
```

### 18.3 Check SCC admission first

```bash
oc describe pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o yaml | grep -A30 securityContext
oc get sa <sa-name> -n <ns> -o yaml
```

Check what SCC admitted the pod:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

### 18.4 Check SELinux AVC logs

On node:

```bash
journalctl -b | grep -i avc
ausearch -m AVC -ts recent 2>/dev/null || true
```

### 18.5 Do not disable SELinux

Never fix OpenShift runtime issues by disabling SELinux. Correct the SCC, service account, UID/GID, volume permissions, or application image design.

Bad approach:

```bash
setenforce 0
```

Professional approach:

```text
Find exact denial → identify pod/service account/volume → fix SCC or permissions → redeploy → validate
```

## 20. CRI-O Logs During MachineConfig Changes

MachineConfig and MCO are central to OpenShift node management.

### 20.1 Why MachineConfig affects CRI-O

MachineConfig can manage or indirectly affect:

- systemd units
- CRI-O configuration
- registry config
- custom CA trust
- kubelet configuration
- kernel arguments
- node OS update
- storage and runtime-related files

The Machine Config Operator applies changes by rendering MachineConfigs, updating nodes pool by pool, and sometimes draining/rebooting nodes.

### 20.2 Events during a CRI-O-related config rollout

You may see this sequence:

```text
MachineConfig created/updated
        ↓
MCO renders new config
        ↓
MCP starts Updating=True
        ↓
MCD on node drains workload if needed
        ↓
MCD writes files or applies OS changes
        ↓
crio.service reload/restart or node reboot
        ↓
node returns Ready
        ↓
MCP Updated=True
```

### 20.3 What to check during rollout

```bash
oc get mcp -w
oc get nodes
oc describe mcp worker
oc get pods -n openshift-machine-config-operator -o wide
```

On node:

```bash
journalctl -b -u crio.service -u kubelet.service --no-pager
```

MCD logs:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --since=1h
```

### 20.4 CRI-O config changed but node not updated

Check:

```bash
oc get mcp
oc describe mcp worker
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

If `currentConfig` differs from `desiredConfig`, the node has not completed rollout.

### 20.5 CRI-O restart after custom CA or registry config

After registry trust changes, CRI-O may need reload/restart behavior as part of node config reconciliation.

Check:

```bash
journalctl -u crio.service --since "2 hours ago" --no-pager | grep -Ei 'restart|reload|Started|Starting'
```

Then retest image pull:

```bash
crictl pull <registry>/<repo>/<image>:<tag>
```

## 21. Increasing CRI-O Log Verbosity Using ContainerRuntimeConfig

Sometimes default CRI-O logs are not detailed enough. OpenShift supports changing some CRI-O settings using `ContainerRuntimeConfig`.

Important: changing CRI-O log level in production increases log volume. Use it temporarily and revert after troubleshooting.

### 21.1 Example: set CRI-O log level to debug for worker pool

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: ContainerRuntimeConfig
metadata:
  name: worker-crio-debug
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  containerRuntimeConfig:
    logLevel: debug
```

Apply:

```bash
oc apply -f worker-crio-debug.yaml
```

Watch rollout:

```bash
oc get mcp worker -w
```

Verify on node:

```bash
oc debug node/<worker-node>
chroot /host
crio config | grep log_level
```

Expected:

```text
log_level = "debug"
```

### 21.2 Revert debug log level

Delete the `ContainerRuntimeConfig`:

```bash
oc delete containerruntimeconfig worker-crio-debug
```

Watch rollout:

```bash
oc get mcp worker -w
```

### 21.3 Do not create many temporary configs

Recommended practice:

- Prefer editing one existing `ContainerRuntimeConfig` per MCP.
- Avoid creating many temporary CRs.
- Document why debug logging was enabled.
- Revert once data is collected.

### 21.4 Confirm generated MachineConfig

```bash
oc get mc | grep containerruntime
```

Inspect:

```bash
oc get mc <machineconfig-name> -o yaml
```

## 22. Safe Operational Practices

### 22.1 Do not restart CRI-O casually

Restarting CRI-O on a production node can affect running workloads. Kubelet may recover, but disruption is possible.

Avoid:

```bash
systemctl restart crio
```

unless you understand impact and have a maintenance path.

### 22.2 Cordon and drain before disruptive actions

```bash
oc adm cordon <node-name>
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
```

After fix:

```bash
oc adm uncordon <node-name>
```

### 22.3 Respect PodDisruptionBudgets

Drain may fail because of PDBs:

```bash
oc get pdb -A
```

Do not force-delete business-critical pods unless incident severity justifies it and stakeholders approve.

### 22.4 Do not manually edit RHCOS config permanently

Avoid manual edits to:

```text
/etc/crio/*
/etc/containers/*
/etc/systemd/system/*
```

Use:

- `MachineConfig`
- `ContainerRuntimeConfig`
- `KubeletConfig`
- supported OpenShift image registry configuration
- supported custom CA configuration

Manual changes can cause configuration drift and make MCO mark the node or pool degraded.

### 22.5 Preserve logs before fixing

Before restarting services or rebooting nodes:

```bash
mkdir -p /tmp/node-debug
journalctl -b -u crio.service -u kubelet.service --no-pager > /tmp/node-debug/runtime-current-boot.log
journalctl -b -1 -u crio.service -u kubelet.service --no-pager > /tmp/node-debug/runtime-previous-boot.log 2>/dev/null || true
systemctl status crio --no-pager > /tmp/node-debug/crio-status.txt
crictl info > /tmp/node-debug/crictl-info.json 2>&1
```

From cluster side:

```bash
oc adm must-gather
```

## 23. Production Runbook

Use this runbook during an incident.

### Step 1: Identify failing workload and node

```bash
oc get pods -A -o wide | grep -Ei 'ImagePullBackOff|CrashLoopBackOff|ContainerCreating|CreateContainerError|RunContainerError|Pending'
```

For a specific pod:

```bash
oc get pod <pod> -n <ns> -o wide
oc describe pod <pod> -n <ns>
```

### Step 2: Check node status

```bash
oc get node <node-name>
oc describe node <node-name>
```

Look for:

```text
Ready=False
DiskPressure=True
MemoryPressure=True
PIDPressure=True
NetworkUnavailable=True
container runtime is down
```

### Step 3: Check CRI-O logs

```bash
oc adm node-logs <node-name> -u crio --since=1h > crio.log
grep -Ei 'error|failed|fatal|panic|denied|timeout|x509|sandbox|cni|overlay|runtime' crio.log
```

### Step 4: Check kubelet logs

```bash
oc adm node-logs <node-name> -u kubelet --since=1h > kubelet.log
grep -Ei 'runtime|sandbox|PLEG|failed|error|not ready|container runtime' kubelet.log
```

### Step 5: Check MCO/MCP

```bash
oc get mcp
oc get co machine-config
oc describe mcp worker
```

If specific node is being updated:

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

### Step 6: Enter node only if needed

```bash
oc debug node/<node-name>
chroot /host
systemctl status crio --no-pager
journalctl -b -u crio.service -u kubelet.service --no-pager
crictl info
```

### Step 7: Classify root cause

| Log clue | Likely area |
|---|---|
| `x509` | Registry CA/trust |
| `unauthorized` | Pull secret/auth |
| `manifest unknown` | Wrong image/tag |
| `failed to setup network` | CNI/OVN/Multus |
| `no space left` | Disk/inode pressure |
| `overlay/lower layer` | Container storage |
| `permission denied` | SELinux/SCC/filesystem |
| `runtime exited` | crun/runc/conmon/runtime issue |
| `context deadline exceeded` | Network/storage/overload timeout |

### Step 8: Fix safely

Examples:

- Registry CA issue: fix custom CA config and wait for MCP rollout.
- Pull secret issue: fix service account or namespace secret.
- CNI issue: fix OVN/Multus/node network.
- Disk pressure: clean safely, evict workloads, add capacity.
- Storage corruption: cordon/drain and follow supported cleanup.
- MCO degraded: fix drift or bad MachineConfig.

### Step 9: Validate

```bash
oc get node <node-name>
oc get pods -A -o wide | grep <node-name>
oc describe node <node-name> | grep -A20 Conditions
oc adm node-logs <node-name> -u crio --since=10m | grep -Ei 'error|failed|fatal|panic'
```

Create a test pod if appropriate:

```bash
oc run crio-test --image=registry.access.redhat.com/ubi9/ubi --restart=Never -- sleep 3600
oc get pod crio-test -o wide
oc delete pod crio-test
```

## 24. Interview-Level Explanation

If asked in an interview, explain like this:

> In OpenShift, CRI-O is the container runtime on each node. Kubelet talks to CRI-O through the Kubernetes CRI interface to create pod sandboxes, pull images, and start containers. CRI-O runs as `crio.service` under systemd, so its primary logs are in journald. I normally check them using `oc adm node-logs <node> -u crio` when the API is healthy, or `oc debug node/<node>` followed by `chroot /host` and `journalctl -b -u crio.service` when I need deeper host-level inspection. I always correlate CRI-O logs with kubelet logs because kubelet reports high-level pod failures while CRI-O shows runtime-level reasons such as registry TLS errors, CNI sandbox failures, overlay storage problems, SELinux denials, or runtime crashes. If MachineConfig changes were recently applied, I also check MCP and MCD logs because MCO may restart, reload, or reboot nodes after CRI-O-related config changes.

Key commands to mention:

```bash
oc adm node-logs <node-name> -u crio
oc adm node-logs --role=worker -u crio
oc debug node/<node-name>
chroot /host
journalctl -b -u crio.service --no-pager
journalctl -b -u kubelet.service -u crio.service --no-pager
systemctl status crio --no-pager
crio status config
crictl info
oc get mcp
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

## 25. Real-World Scenarios

### Scenario 1: Pod stuck in `ImagePullBackOff`

Symptoms:

```bash
oc get pod app-1 -n prod
```

```text
NAME    READY   STATUS             RESTARTS
app-1   0/1     ImagePullBackOff    0
```

Check node:

```bash
oc get pod app-1 -n prod -o wide
```

Check CRI-O logs:

```bash
oc adm node-logs <node> -u crio --since=30m | grep -Ei 'pull|x509|unauthorized|manifest|registry'
```

Possible CRI-O log:

```text
x509: certificate signed by unknown authority
```

Root cause:

Registry CA not trusted by node/CRI-O.

Fix direction:

- Add correct registry CA to OpenShift image config.
- Wait for MachineConfigPool rollout.
- Confirm CRI-O restart/reload.
- Retry pod.

---

### Scenario 2: Pods stuck in `ContainerCreating` after MachineConfig rollout

Check pods:

```bash
oc get pods -A -o wide | grep ContainerCreating
```

Check MCP:

```bash
oc get mcp
```

Check CRI-O:

```bash
oc adm node-logs <node> -u crio --since=1h
```

Check MCD:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --since=1h
```

Possible issue:

Bad CRI-O config generated from an incorrect `ContainerRuntimeConfig` or registry-related MachineConfig.

Fix direction:

- Review recent MachineConfig/ContainerRuntimeConfig changes.
- Roll back bad CR.
- Wait for MCP to recover.
- Validate CRI-O config.

---

### Scenario 3: Node NotReady due to runtime down

Check node:

```bash
oc describe node <node>
```

Possible condition:

```text
KubeletNotReady: container runtime is down
```

Check CRI-O:

```bash
oc adm node-logs <node> -u crio --since=1h
```

If `oc adm node-logs` fails, use console/SSH:

```bash
ssh core@<node>
sudo -i
systemctl status crio --no-pager
journalctl -b -u crio.service --no-pager
```

Possible cause:

- CRI-O failed to start due to invalid config.
- Container storage corruption.
- Disk full.
- Runtime binary issue after upgrade.

Fix direction:

- Preserve logs.
- Check MCO/MCP.
- Cordon/drain if possible.
- Correct config or follow storage cleanup runbook.

---

### Scenario 4: `FailedCreatePodSandBox` with network error

Pod event:

```text
Failed to create pod sandbox: failed to setup network for sandbox
```

Check CRI-O:

```bash
journalctl -b -u crio.service --no-pager | grep -Ei 'sandbox|cni|network'
```

Check OVN/Multus:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc get pods -n openshift-multus -o wide
```

Root cause could be:

- OVN node pod not running on that node.
- CNI config missing.
- Node network issue.
- IPAM or network attachment issue.

Fix direction:

- Fix network operator/OVN/Multus issue, not CRI-O directly.

---

### Scenario 5: Overlay storage corruption

CRI-O log:

```text
can't stat lower layer ... because it does not exist
```

Check:

```bash
journalctl -b -u crio.service | grep -Ei 'overlay|lower layer|storage'
df -h
df -ih
```

Fix direction:

- Cordon and drain node.
- Preserve logs.
- Follow supported CRI-O storage cleanup procedure.
- Do not randomly delete overlay directories.

3. Use `journalctl -b -u crio.service` for current boot logs.
4. Always correlate CRI-O logs with kubelet logs.
5. For image pull issues, check registry, pull secret, CA, and mirror config.
6. For sandbox issues, check CNI/OVN/Multus.
7. For MachineConfig-related issues, check `oc get mcp`, node annotations, and MCD logs.
8. Do not manually edit CRI-O config permanently on RHCOS.
9. Do not restart CRI-O blindly on production nodes.
10. For destructive cleanup, cordon/drain first and follow supported procedure.

A strong exam answer usually includes:

```bash
oc get pod -o wide
oc describe pod
oc describe node
oc adm node-logs <node> -u crio
oc adm node-logs <node> -u kubelet
oc debug node/<node>
chroot /host
journalctl -b -u crio.service
systemctl status crio
oc get mcp
```

## 28. Key Takeaways

- CRI-O is the OpenShift node container runtime and runs as `crio.service`.
- Its primary logs are in `journald`.
- Use `oc adm node-logs` first when the API is healthy.
- Use `oc debug node` + `chroot /host` for detailed node investigation.
- Use SSH/console only when API or debug access is unavailable.
- CRI-O logs must be correlated with kubelet logs, pod events, node conditions, and MachineConfig state.
- Many CRI-O errors are symptoms of registry, CNI, storage, SELinux, SCC, or MachineConfig problems.
- `ContainerRuntimeConfig` can change CRI-O log level, overlay size, and default runtime for selected pools.
- Avoid direct permanent host changes on RHCOS; use supported OpenShift APIs.
- In production, preserve logs before restarting services or rebooting nodes.
