## 1. Executive summary

`sysctl` is the Linux interface used to read and change kernel parameters at runtime. In OpenShift, sysctl tuning is powerful but dangerous because the same node can host many workloads, networking components, storage agents, monitoring agents, and cluster daemons. A sysctl that looks harmless on a standalone RHEL server can break pod networking, kubelet behavior, ingress, storage, or node stability in a Kubernetes platform.

For OpenShift node-level administration, you must separate three ideas:

| Requirement | Correct mechanism | Notes |
|---|---|---|
| Persistently set host/node kernel parameters across reboot | **Node Tuning Operator** or **MachineConfig** | Node Tuning Operator is usually better for runtime tuning. MachineConfig is better when you need a host file or early boot behavior. |
| Allow pods to set namespaced unsafe sysctls in `securityContext.sysctls` | **KubeletConfig** plus often **custom SCC** | This does not set the node host sysctl. It only allows pod specs to request selected unsafe sysctls. |
| Set safe namespaced pod sysctls | Pod `securityContext.sysctls` | Safe sysctls are allowed by default, subject to policy. |
| Set interface-specific sysctls for secondary interfaces | **tuning CNI** / network attachment tuning | Do not try to use `allowedUnsafeSysctls` for interface-specific unsafe sysctls. |
| Temporarily test a value on one node | `oc debug node/...` and `chroot /host sysctl -w` | Break-glass only. Not persistent. Might be overwritten by TuneD, systemd-sysctl, NetworkManager, or reboot. |

A senior OpenShift administrator does not randomly add `sysctl -w` commands. The production approach is:

1. Identify whether the setting is **pod-level** or **node-level**.
2. Verify whether it is **safe**, **unsafe**, **namespaced**, **interface-specific**, or **not namespaced**.
3. Scope the change to a dedicated MachineConfigPool or labeled node group.
4. Apply through GitOps-managed YAML.
5. Watch the MachineConfigPool, Node Tuning Operator status, kubelet behavior, workload health, and node metrics.
6. Document the reason, expected value, rollback command, and validation result.

## 2. What sysctl means on Linux

Linux exposes many kernel tunables through the virtual filesystem path:

```bash
/proc/sys/
```

The `sysctl` command is a user-friendly interface for reading and changing those tunables.

Examples:

```bash
sysctl vm.max_map_count
sysctl fs.inotify.max_user_watches
sysctl net.core.somaxconn
sysctl -a | grep '^net.ipv4'
```

A dotted sysctl key maps to a path under `/proc/sys`.

Example:

```text
vm.max_map_count
```

maps to:

```text
/proc/sys/vm/max_map_count
```

A runtime change is usually done like this:

```bash
sysctl -w vm.max_map_count=262144
```

A persistent host-level configuration is normally placed in a file such as:

```text
/etc/sysctl.d/99-custom.conf
```

with content like:

```ini
vm.max_map_count = 262144
fs.inotify.max_user_watches = 524288
```

On a normal RHEL system, `systemd-sysctl` applies sysctl drop-in files during boot. In OpenShift RHCOS, you should not manually edit host files with SSH as a routine practice. Use declarative cluster-managed configuration.

## 3. Why sysctl tuning matters in OpenShift

OpenShift nodes are not ordinary standalone Linux servers. They are managed by the cluster. A node runs:

- kubelet
- CRI-O
- OVN-Kubernetes or other CNI components
- Machine Config Daemon
- node exporter
- log/monitoring agents
- router/ingress pods on selected nodes
- storage agents such as ODF/Ceph components if deployed
- user workloads

Sysctl tuning becomes important when workloads need kernel-level behavior changes, for example:

- Elasticsearch/OpenSearch needing higher `vm.max_map_count`
- high-connection ingress or API gateway workloads needing queue/backlog tuning
- large CI/build nodes needing higher file watcher limits
- CNF/telco workloads needing deterministic latency settings
- database or cache workloads needing network/socket tuning
- host-based security requirements needing kernel hardening values

But every change has a blast radius. A node-level sysctl affects every process or network namespace that depends on that host-level setting. That includes platform components.

## 4. The OpenShift mental model

### 4.1 Components involved

| Component | Role in sysctl/node tuning |
|---|---|
| **Machine Config Operator (MCO)** | Applies host OS configuration through MachineConfig, KubeletConfig, ContainerRuntimeConfig, kernel args, files, and systemd units. |
| **Machine Config Pool (MCP)** | Defines which nodes receive a rendered machine configuration. Common pools: `master`, `worker`, and custom pools. |
| **Machine Config Daemon (MCD)** | Runs on each node, applies rendered config, drains/reboots when required, and detects configuration drift. |
| **RHCOS** | Immutable-style OpenShift host OS managed declaratively. Do not treat it like a hand-edited VM. |
| **Node Tuning Operator (NTO)** | Manages node-level tuning by orchestrating containerized TuneD daemons. |
| **TuneD** | Applies runtime tuning profiles, including sysctl tuning. |
| **Kubelet** | Enforces pod sysctl admission for allowed unsafe sysctls. |
| **Security Context Constraints (SCCs)** | OpenShift admission policy that can further control allowed unsafe sysctls in pod specs. |
| **Pod Security Admission** | Kubernetes security policy layer. In OpenShift, SCC remains a major control. |
| **tuning CNI** | Used for interface-specific sysctls after interfaces are created. |

### 4.2 Why this is different from plain RHEL

On plain RHEL, you might edit:

```text
/etc/sysctl.conf
/etc/sysctl.d/99-custom.conf
```

and run:

```bash
sysctl --system
```

On OpenShift, direct host edits are not the desired state. The cluster will eventually reconcile against declared configuration. If the Machine Config Daemon detects drift in a managed file, the node can become degraded until corrected.

The OpenShift way is:

```text
Desired state YAML -> MCO/NTO -> node rollout -> verification -> monitoring
```

## 5. Namespaced, node-level, safe, and unsafe sysctls

This is the most important section.

### 5.1 Namespaced sysctls

A namespaced sysctl can be set independently for a pod or namespace context. Kubernetes can expose some namespaced sysctls through:

```yaml
spec:
  securityContext:
    sysctls:
    - name: kernel.shm_rmid_forced
      value: "1"
```

Known namespaced groups include examples such as:

```text
kernel.shm*
kernel.msg*
kernel.sem
fs.mqueue.*
many net.* sysctls, depending on kernel and distribution behavior
```

Do not assume every `net.*` sysctl is safe or namespaced in the way you expect. Verify against your OpenShift/Kubernetes version and kernel behavior.

### 5.2 Node-level sysctls

Node-level sysctls are not isolated per pod. They affect the host or a broad host-level subsystem.

Examples commonly treated as node-level operational tunables include:

```text
vm.max_map_count
fs.inotify.max_user_watches
fs.inotify.max_user_instances
net.netfilter.nf_conntrack_max
```

Node-level sysctls must be applied by the cluster administrator using a node-level mechanism such as:

- Node Tuning Operator
- MachineConfig writing `/etc/sysctl.d/*.conf`
- privileged DaemonSet, usually discouraged unless there is no better platform-native option

### 5.3 Safe sysctls

A safe sysctl is a sysctl Kubernetes/OpenShift allows by default because it is namespaced and isolated enough for pod use.

Examples from modern Kubernetes/OpenShift safe lists include:

```text
kernel.shm_rmid_forced
net.ipv4.ip_local_port_range
net.ipv4.ip_unprivileged_port_start
net.ipv4.tcp_syncookies
net.ipv4.ping_group_range
net.ipv4.ip_local_reserved_ports
net.ipv4.tcp_keepalive_time
net.ipv4.tcp_fin_timeout
net.ipv4.tcp_keepalive_intvl
net.ipv4.tcp_keepalive_probes
```

The exact safe set can vary by Kubernetes/OpenShift version.

### 5.4 Unsafe sysctls

An unsafe sysctl is not allowed by default for pod-level use. Unsafe does not always mean "bad"; it means the platform does not consider it safe for untrusted pod authors to set freely.

Unsafe sysctls can cause:

- unexpected container behavior
- node resource exhaustion
- network instability
- breakage of kubelet or CNI assumptions
- security boundary weakening

Examples often appearing in unsafe discussions:

```text
net.core.somaxconn
kernel.msgmax
kernel.msgmnb
kernel.sem
```

For pod-level unsafe sysctls, the administrator must allow specific sysctls through kubelet configuration, and in OpenShift can also restrict through SCC.

### 5.5 Interface-specific sysctls

Interface-specific sysctls look like:

```text
net.ipv4.conf.IFNAME.accept_redirects
net.ipv4.conf.IFNAME.rp_filter
net.ipv6.conf.IFNAME.accept_ra
```

They apply to a specific network interface. In Kubernetes/OpenShift, secondary interfaces can be created after pod admission. For additional network interfaces, use the tuning CNI pattern rather than general node sysctl mechanisms.

## 6. Choosing the correct OpenShift mechanism

### 6.1 Decision matrix

| Scenario | Use | Avoid |
|---|---|---|
| Need `vm.max_map_count=262144` on all dedicated search nodes | Node Tuning Operator or MachineConfig | Pod `securityContext.sysctls` |
| Need `/etc/sysctl.d/99-custom.conf` to exist on worker nodes | MachineConfig | SSH manual edits |
| Need a sysctl applied dynamically and rolled back with profile change | Node Tuning Operator | Raw MachineConfig if runtime profile behavior is desired |
| Need to allow a pod to request `net.core.somaxconn` | KubeletConfig `allowedUnsafeSysctls`, plus SCC governance | Host-level `/etc/sysctl.d` only |
| Need sysctl for pod secondary NIC | tuning CNI | KubeletConfig unsafe sysctls |
| Need one-time emergency test | `oc debug node` + `sysctl -w` | Treating manual test as final state |
| Need boot kernel argument such as hugepages or cgroup behavior | MachineConfig kernel arguments or PerformanceProfile | sysctl file |

### 6.2 MachineConfig vs Node Tuning Operator

Both can configure node-level sysctls, but they are not identical.

| Feature | MachineConfig | Node Tuning Operator |
|---|---|---|
| Writes host files | Yes | Not primarily |
| Can create systemd units | Yes | No, not arbitrary systemd units in NTO custom profiles in OpenShift |
| Usually causes node reboot for config changes | Yes | Usually applies runtime tuning without an MCO reboot, depending on setting |
| Best for early-boot persistent file state | Yes | Sometimes no |
| Best for TuneD runtime profile management | No | Yes |
| Rollback style | Delete/modify MachineConfig; nodes roll | Delete/modify Tuned CR; TuneD profile changes |
| Scoping | MCP labels/roles | Node labels and profile recommendation logic |
| Operational risk | Can reboot and drain node pool | Can change live kernel behavior |

### 6.3 Recommended senior-admin rule

Use this rule in production:

```text
If the setting is a runtime performance tuning value, prefer Node Tuning Operator.
If the setting must exist as a host config file, must be applied very early at boot, or is part of a broader OS config bundle, use MachineConfig.
If pods need to set a namespaced unsafe sysctl themselves, use KubeletConfig and SCC, not MachineConfig.
```

## 7. MachineConfig-based node-level sysctl configuration

MachineConfig can write files to RHCOS nodes. A common pattern is to write a file under:

```text
/etc/sysctl.d/99-openshift-custom.conf
```

The file is then applied at boot by `systemd-sysctl`.

Because MachineConfig changes normally cause MCO-controlled drain and reboot, the persistent sysctl file becomes active after the node reboots.

### 7.1 When to use MachineConfig for sysctl

Use MachineConfig when:

- You need to declaratively create `/etc/sysctl.d/*.conf`
- You want the value applied at boot before workloads land
- The value is part of OS baseline/hardening
- You need GitOps-controlled host file content
- You are already managing related systemd/host files through MachineConfig
- You want the change scoped by MachineConfigPool

Avoid MachineConfig when:

- You need dynamic performance profiles selected by labels
- You need easy profile rollback without node reboot
- You are trying to allow pod-level unsafe sysctls
- You do not want the node pool to roll/reboot

### 7.2 Example: Butane source file

Create a Butane file:

```yaml
# 99-worker-node-sysctl.bu
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-node-sysctl
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
    - path: /etc/sysctl.d/99-openshift-custom.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          # Managed by OpenShift MachineConfig: 99-worker-node-sysctl
          # Validate every value in a non-production pool before production rollout.

          vm.max_map_count = 262144
          fs.inotify.max_user_watches = 524288
          fs.inotify.max_user_instances = 1024
          net.core.somaxconn = 4096
```

Notes:

- Use the Butane version matching your OpenShift minor version and ending in `.0`, for example `4.21.0` for OCP 4.21.
- Use a high number like `99-` so the local custom file wins over lower-numbered defaults when the same key appears elsewhere.
- Validate the values before production rollout.
- Prefer a custom pool for high-risk tuning, not the entire `worker` pool.

Generate a MachineConfig:

```bash
butane 99-worker-node-sysctl.bu -o 99-worker-node-sysctl.yaml
```

Apply it:

```bash
oc apply -f 99-worker-node-sysctl.yaml
oc get mcp worker -w
```

### 7.4 Safer pattern: create a custom MachineConfigPool

For production, do not blindly tune every worker. Create a small canary pool.

Label selected nodes:

```bash
oc label node worker-0.example.com node-role.kubernetes.io/sysctl-tuned=
oc label node worker-1.example.com node-role.kubernetes.io/sysctl-tuned=
```

Create a custom MachineConfigPool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: sysctl-tuned
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - sysctl-tuned
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/sysctl-tuned: ""
```

Then label your MachineConfig for the custom role:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: sysctl-tuned
```

This limits the blast radius.

### 7.5 Applying and watching rollout

```bash
oc apply -f 99-worker-node-sysctl.yaml
oc get mcp
oc get mcp sysctl-tuned -w
oc describe mcp sysctl-tuned
```

Look for:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
```

Check nodes:

```bash
oc get nodes -l node-role.kubernetes.io/sysctl-tuned=
```

### 7.6 Verification on a node

```bash
NODE=worker-0.example.com

oc debug node/$NODE -- chroot /host cat /etc/sysctl.d/99-openshift-custom.conf
oc debug node/$NODE -- chroot /host sysctl vm.max_map_count
oc debug node/$NODE -- chroot /host sysctl fs.inotify.max_user_watches
oc debug node/$NODE -- chroot /host sysctl fs.inotify.max_user_instances
oc debug node/$NODE -- chroot /host sysctl net.core.somaxconn
```

Expected:

```text
vm.max_map_count = 262144
fs.inotify.max_user_watches = 524288
fs.inotify.max_user_instances = 1024
net.core.somaxconn = 4096
```

### 7.7 Confirm which MachineConfig rendered

```bash
oc get mcp sysctl-tuned -o jsonpath='{.status.configuration.name}{"\n"}'
oc describe node $NODE | grep -E 'machineconfiguration.openshift.io/(currentConfig|desiredConfig)'
```

You can inspect rendered config:

```bash
RENDERED=$(oc get mcp sysctl-tuned -o jsonpath='{.status.configuration.name}')
oc get mc "$RENDERED" -o yaml | less
```

### 7.8 Applying immediately without reboot

For MCO-managed changes, you normally let MCO roll and reboot the node. Do not fight it.

For one-off testing only:

```bash
oc debug node/$NODE
chroot /host
sysctl -w vm.max_map_count=262144
exit
exit
```

This is not persistent and might be overwritten by reboot, TuneD, or other host configuration.

### 7.9 Advanced MachineConfig with systemd unit

Usually you do not need this because `systemd-sysctl` applies `/etc/sysctl.d/*.conf` at boot. But in special cases, you might need a dedicated unit for a specific file.

Example concept:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-apply-custom-sysctl-unit
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: apply-custom-sysctl.service
          enabled: true
          contents: |
            [Unit]
            Description=Apply custom sysctl settings from /etc/sysctl.d/99-openshift-custom.conf
            After=systemd-sysctl.service
            ConditionPathExists=/etc/sysctl.d/99-openshift-custom.conf

            [Service]
            Type=oneshot
            ExecStart=/usr/sbin/sysctl -p /etc/sysctl.d/99-openshift-custom.conf
            RemainAfterExit=yes

            [Install]
            WantedBy=multi-user.target
```

Use this only when you have a clear ordering reason. More units mean more operational complexity.

## 8. Node Tuning Operator-based sysctl configuration

The Node Tuning Operator is the OpenShift-native way to manage node-level tuning through TuneD. It runs containerized TuneD daemons on nodes and applies profiles based on recommendation logic.

### 8.1 Why NTO is often better for sysctl tuning

NTO is often preferred because:

- It is designed for node-level tuning.
- It supports custom TuneD profiles.
- It can scope profiles with node labels.
- It provides OpenShift status objects for profile application.
- It can roll back tuning when the profile changes or is removed.
- It avoids unnecessary host file MachineConfig changes for pure runtime tuning.

### 8.2 Important NTO namespace

NTO objects live in:

```text
openshift-cluster-node-tuning-operator
```

View the default Tuned CR:

```bash
oc get tuned.tuned.openshift.io/default -n openshift-cluster-node-tuning-operator -o yaml
```

Do not customize the default CR for your tuning profile. Create your own `Tuned` CR.

### 8.3 Example: set `vm.max_map_count` with Tuned CR

Label selected nodes:

```bash
oc label node worker-0.example.com tuned.openshift.io/search-node=
oc label node worker-1.example.com tuned.openshift.io/search-node=
```

Create a custom Tuned CR:

```yaml
apiVersion: tuned.openshift.io/v1
kind: Tuned
metadata:
  name: search-node-sysctl
  namespace: openshift-cluster-node-tuning-operator
spec:
  profile:
    - name: search-node-sysctl
      data: |
        [main]
        summary=Custom sysctl profile for search workloads
        include=openshift-node

        [sysctl]
        vm.max_map_count=262144
        fs.inotify.max_user_watches=524288
        fs.inotify.max_user_instances=1024
  recommend:
    - match:
        - label: tuned.openshift.io/search-node
      priority: 20
      profile: search-node-sysctl
```

Apply:

```bash
oc apply -f search-node-sysctl.yaml
```

Verify:

```bash
oc get tuned -n openshift-cluster-node-tuning-operator
oc get profile.tuned.openshift.io -n openshift-cluster-node-tuning-operator
oc get co node-tuning
```

Check node value:

```bash
oc debug node/worker-0.example.com -- chroot /host sysctl vm.max_map_count
```

### 8.4 Why include `openshift-node`

The custom profile should normally include the OpenShift base profile:

```ini
include=openshift-node
```

or for control-plane/infra use cases, the relevant OpenShift profile. This avoids accidentally replacing OpenShift-provided baseline tuning.

### 8.5 NTO profile recommendation logic

The `recommend` section controls where the profile applies.

Example:

```yaml
recommend:
  - match:
      - label: tuned.openshift.io/search-node
    priority: 20
    profile: search-node-sysctl
```

Interpretation:

```text
If a node has label tuned.openshift.io/search-node, apply profile search-node-sysctl with priority 20.
```

Higher-priority or more specific profiles can win depending on the operator's recommendation rules and existing profiles. Always check the resulting `Profile` objects.

### 8.6 Verify applied profile per node

```bash
oc get profile.tuned.openshift.io -n openshift-cluster-node-tuning-operator
```

For more detail:

```bash
oc describe profile.tuned.openshift.io/<profile-object-name> -n openshift-cluster-node-tuning-operator
```

Find TuneD pods:

```bash
oc get pods -n openshift-cluster-node-tuning-operator -o wide
```

View logs for one TuneD pod:

```bash
oc logs -n openshift-cluster-node-tuning-operator <tuned-pod-name>
```

### 8.7 Host sysctl files vs TuneD reapplication

OpenShift nodes can have sysctl configuration from host files such as:

```text
/run/sysctl.d/
/etc/sysctl.d/
/etc/sysctl.conf
```

TuneD may apply its custom profile and also reapply host sysctls depending on the `reapply_sysctl` option. If you see values reverting unexpectedly, check whether the value is defined in both:

- a MachineConfig-managed `/etc/sysctl.d/*.conf`
- a NTO/TuneD profile
- a platform-provided sysctl file
- another service such as NetworkManager or CNI

The senior-admin approach is to define ownership:

```text
One sysctl key should have one authoritative owner.
```

Do not manage the same key from both MachineConfig and NTO unless you have documented ordering and reapply behavior.

## 9. KubeletConfig and allowed unsafe pod sysctls

This section is frequently misunderstood.

`KubeletConfig.allowedUnsafeSysctls` does **not** set a node host sysctl value. It only tells kubelet that pods scheduled on that node type are allowed to request specific unsafe, namespaced sysctls in their pod `securityContext`.

### 9.1 Example use case

A workload needs:

```yaml
securityContext:
  sysctls:
    - name: net.core.somaxconn
      value: "1024"
```

Without kubelet permission, the pod can fail with:

```text
SysctlForbidden
```

### 9.2 Create a KubeletConfig for a worker MCP

Label the MachineConfigPool:

```bash
oc label machineconfigpool worker custom-kubelet=sysctl
```

Create:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: allow-selected-unsafe-sysctls
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: sysctl
  kubeletConfig:
    allowedUnsafeSysctls:
      - "kernel.msg*"
      - "net.core.somaxconn"
```

Apply:

```bash
oc apply -f allow-selected-unsafe-sysctls.yaml
oc get mcp worker -w
```

MCO generates a kubelet MachineConfig and rolls the pool.

### 9.3 Pod example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sysctl-example
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
    sysctls:
      - name: net.core.somaxconn
        value: "1024"
      - name: kernel.msgmax
        value: "65536"
  containers:
    - name: test
      image: registry.access.redhat.com/ubi9/ubi
      command: ["/bin/bash", "-c", "sleep infinity"]
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
```

### 9.4 Important scheduling practice

If only some nodes allow unsafe sysctls, schedule those pods only on those nodes:

```bash
oc label node worker-0.example.com sysctl-workload=true
```

Use node selector:

```yaml
spec:
  nodeSelector:
    sysctl-workload: "true"
```

Or taint/toleration:

```bash
oc adm taint node worker-0.example.com sysctl-workload=true:NoSchedule
```

Pod toleration:

```yaml
tolerations:
  - key: "sysctl-workload"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```

This prevents workloads from randomly landing on nodes that do not allow required unsafe sysctls.

## 10. SCC control for unsafe sysctls

In OpenShift, Security Context Constraints can further control which unsafe sysctls pods may request.

Why this matters:

- KubeletConfig allows unsafe sysctls at node level.
- SCC controls pod admission permissions.
- You should not allow every namespace or service account to use risky sysctls.

### 10.1 Do not edit default SCCs

Do not modify default SCCs such as `restricted-v2`, `anyuid`, or `privileged` for this purpose. Create a custom SCC.

### 10.2 Example custom SCC snippet

This is a conceptual SCC snippet. In production, start from a restrictive SCC model and add only what you need.

```yaml
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata:
  name: restricted-with-selected-sysctls
allowPrivilegedContainer: false
allowHostNetwork: false
allowHostPID: false
allowHostIPC: false
allowHostDirVolumePlugin: false
allowedUnsafeSysctls:
  - "net.core.somaxconn"
  - "kernel.msg*"
forbiddenSysctls: []
requiredDropCapabilities:
  - ALL
allowedCapabilities: []
runAsUser:
  type: MustRunAsRange
seLinuxContext:
  type: MustRunAs
fsGroup:
  type: MustRunAs
supplementalGroups:
  type: RunAsAny
readOnlyRootFilesystem: false
volumes:
  - configMap
  - downwardAPI
  - emptyDir
  - persistentVolumeClaim
  - projected
  - secret
```

Grant it to a service account:

```bash
oc adm policy add-scc-to-user restricted-with-selected-sysctls -z app-sa -n app-namespace
```

Check:

```bash
oc auth can-i use scc/restricted-with-selected-sysctls \
  --as system:serviceaccount:app-namespace:app-sa \
  -n app-namespace
```

View selected SCC used by a pod:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

## 11. Interface-specific sysctls and tuning CNI

Interface-specific sysctls apply to an interface, not simply to the pod or host globally.

Examples:

```text
net.ipv4.conf.eth0.rp_filter
net.ipv4.conf.net1.accept_redirects
net.ipv6.conf.net1.accept_ra
```

OpenShift documentation distinguishes system-wide and interface-specific sysctls. Interface-specific sysctls for additional networks should be configured after the interface exists, commonly through tuning CNI configuration on a NetworkAttachmentDefinition.

Conceptual example:

```yaml
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: secondary-net-with-tuning
  namespace: app-namespace
spec:
  config: |
    {
      "cniVersion": "0.4.0",
      "name": "secondary-net-with-tuning",
      "plugins": [
        {
          "type": "macvlan",
          "master": "ens3",
          "mode": "bridge",
          "ipam": {
            "type": "whereabouts",
            "range": "192.168.100.0/24"
          }
        },
        {
          "type": "tuning",
          "sysctl": {
            "net.ipv4.conf.IFNAME.rp_filter": "0"
          }
        }
      ]
    }
```

`IFNAME` is replaced by the actual interface name by the plugin behavior.

Use this only when you are intentionally managing secondary network interface behavior.

## 12. End-to-end production rollout pattern

A 10-year experienced platform engineer should use a process like this.

### 12.1 Requirement capture

Document:

```text
Change: vm.max_map_count from default to 262144
Reason: OpenSearch pods require high virtual memory map count
Scope: dedicated search worker nodes only
Mechanism: Node Tuning Operator
Owner: platform team
Risk: node-wide virtual memory behavior
Rollback: delete Tuned CR and remove node label
Validation: sysctl value, workload readiness, node health, logs
```

### 12.2 Pre-change discovery

```bash
oc get clusterversion
oc get nodes -o wide
oc get mcp
oc get co node-tuning
oc get tuned -n openshift-cluster-node-tuning-operator
oc get profile.tuned.openshift.io -n openshift-cluster-node-tuning-operator
```

Check current values:

```bash
for n in $(oc get nodes -l node-role.kubernetes.io/worker= -o name); do
  echo "### $n"
  oc debug "$n" -- chroot /host sysctl vm.max_map_count 2>/dev/null
done
```

### 12.3 Canary first

Label one non-critical node or create a custom MCP.

```bash
oc label node worker-0.example.com tuned.openshift.io/search-node=
```

Apply NTO profile or MachineConfig.

Watch:

```bash
oc get co node-tuning
oc get profile.tuned.openshift.io -n openshift-cluster-node-tuning-operator
oc get mcp -w
oc get nodes
```

### 12.4 Validate workload behavior

```bash
oc get pods -n search -o wide
oc describe pod <pod> -n search
oc logs <pod> -n search
oc adm top node
oc adm top pod -n search
```

### 12.5 Expand rollout

Label additional nodes gradually.

```bash
oc label node worker-1.example.com tuned.openshift.io/search-node=
oc label node worker-2.example.com tuned.openshift.io/search-node=
```

### 12.6 Record final state

```bash
oc get tuned search-node-sysctl -n openshift-cluster-node-tuning-operator -o yaml
oc get nodes -l tuned.openshift.io/search-node=
oc get profile.tuned.openshift.io -n openshift-cluster-node-tuning-operator
```

## 14. Troubleshooting

### 14.1 Symptom: Pod shows `SysctlForbidden`

Possible causes:

- The sysctl is unsafe and not in kubelet `allowedUnsafeSysctls`.
- The pod landed on a node whose MCP does not include the KubeletConfig.
- SCC does not allow that unsafe sysctl.
- The sysctl is interface-specific and cannot be enabled this way.
- The sysctl is not namespaced.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get kubeletconfig -o yaml
oc get mcp -o wide
oc get node <node> --show-labels
oc get pod <pod> -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
oc describe scc <scc-name>
```

### 14.2 Symptom: MachineConfigPool stuck Updating

Possible causes:

- Node drain blocked by PodDisruptionBudget
- Unhealthy node
- DaemonSet/static pods not moving
- MCD error
- Disk pressure or OS update issue

Commands:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
oc get pods -A -o wide | grep <node>
oc logs -n openshift-machine-config-operator daemonset/machine-config-daemon -c machine-config-daemon
```

Check MCO:

```bash
oc get co machine-config
oc describe co machine-config
```

### 14.3 Symptom: MachineConfigPool degraded

Possible causes:

- File conflict
- Bad Ignition/MachineConfig syntax
- Manual host modification causing drift
- MCD failed to apply config
- Reboot failed

Commands:

```bash
oc describe mcp worker
oc get mc
oc get nodes
oc logs -n openshift-machine-config-operator daemonset/machine-config-daemon -c machine-config-daemon
```

On affected node:

```bash
oc debug node/<node> -- chroot /host journalctl -u machine-config-daemon --no-pager -n 200
```

### 14.4 Symptom: sysctl file exists but value is not active

Possible causes:

- File was written but not applied yet
- Node has not rebooted
- Another later sysctl file overrides it
- TuneD reapplied host/system profile
- CNI/NetworkManager changed networking key later
- You are checking inside a pod namespace instead of host namespace

Commands:

```bash
oc debug node/$NODE -- chroot /host ls -l /etc/sysctl.d /run/sysctl.d /usr/lib/sysctl.d
oc debug node/$NODE -- chroot /host grep -R "vm.max_map_count" /etc/sysctl.d /run/sysctl.d /usr/lib/sysctl.d 2>/dev/null
oc debug node/$NODE -- chroot /host sysctl --system
oc debug node/$NODE -- chroot /host sysctl vm.max_map_count
```

Do not run `sysctl --system` as a permanent fix unless you understand side effects. Use it to test.

### 14.5 Symptom: value works on one node but not another

Possible causes:

- Only one node has the label
- Different MCP
- NTO recommendation not matching
- Different rendered MachineConfig
- Node not updated
- Node has degraded state

Commands:

```bash
oc get nodes --show-labels
oc get mcp -o wide
oc describe node <node> | grep -E 'machineconfiguration.openshift.io/(currentConfig|desiredConfig)'
oc get profile.tuned.openshift.io -n openshift-cluster-node-tuning-operator -o wide
```

### 14.6 Symptom: network breaks after sysctl tuning

Possible risky keys:

```text
net.ipv4.ip_forward
net.ipv4.conf.all.rp_filter
net.ipv4.conf.default.rp_filter
net.ipv4.ip_local_port_range
net.netfilter.nf_conntrack_max
net.ipv4.tcp_tw_reuse
```

Immediate checks:

```bash
oc get co network
oc get pods -n openshift-ovn-kubernetes -o wide
oc logs -n openshift-ovn-kubernetes daemonset/ovnkube-node -c ovnkube-node
oc get nodes
oc get events -A --sort-by=.lastTimestamp | tail -100
```

If the issue is severe, rollback the specific NTO/MachineConfig change.

## 15. Rollback and recovery

### 15.1 Rollback Node Tuning Operator change

Remove the Tuned CR:

```bash
oc delete tuned search-node-sysctl -n openshift-cluster-node-tuning-operator
```

Remove node labels:

```bash
oc label node worker-0.example.com tuned.openshift.io/search-node-

```

Watch:

```bash
oc get profile.tuned.openshift.io -n openshift-cluster-node-tuning-operator
oc get co node-tuning
```

Verify values:

```bash
oc debug node/worker-0.example.com -- chroot /host sysctl vm.max_map_count
```

### 15.2 Rollback MachineConfig change

Delete the MachineConfig:

```bash
oc delete mc 99-worker-node-sysctl
```

Watch pool:

```bash
oc get mcp worker -w
```

The MCO will roll nodes to the new rendered config. This can involve drain and reboot.

### 15.3 Rollback KubeletConfig unsafe sysctl allow list

Delete the KubeletConfig:

```bash
oc delete kubeletconfig allow-selected-unsafe-sysctls
```

Remove the MCP label if no longer needed:

```bash
oc label machineconfigpool worker custom-kubelet-
```

Watch:

```bash
oc get mcp worker -w
```

### 15.4 Emergency runtime rollback

For one node:

```bash
oc debug node/$NODE -- chroot /host sysctl -w vm.max_map_count=<old-value>
```

This is temporary. Follow with declarative rollback.

## 16. Security and compliance guidance

### 16.1 Do not treat sysctl as simple performance tuning

Sysctls can affect:

- process isolation
- network routing
- kernel memory behavior
- conntrack table behavior
- filesystem watcher limits
- local port allocation
- IPC limits
- denial-of-service resistance

### 16.2 Minimum production controls

For every sysctl change, require:

```text
1. Business/workload reason
2. Exact key and value
3. Scope: node label, MCP, namespace, service account
4. Risk assessment
5. Rollback method
6. Canary validation
7. Monitoring indicators
8. GitOps pull request and review
```

### 16.3 Avoid broad wildcard unsafe sysctls

Avoid:

```yaml
allowedUnsafeSysctls:
  - "*"
```

Avoid broad patterns unless absolutely required:

```yaml
allowedUnsafeSysctls:
  - "net.*"
```

Prefer exact keys:

```yaml
allowedUnsafeSysctls:
  - "net.core.somaxconn"
```

### 16.4 Do not edit default SCCs

Create a custom SCC. Default SCC changes can be reset or cause upgrade/platform issues.

### 16.5 Do not tune control plane casually

Control plane nodes run critical platform services. Tune control plane only when:

- Red Hat documentation requires it
- Red Hat support recommends it
- You have a tested maintenance window
- You understand etcd/API impact

## 17. Common real-world tuning examples

These examples are educational. Do not copy values blindly.

### 17.1 Elasticsearch/OpenSearch: `vm.max_map_count`

Requirement:

```text
vm.max_map_count = 262144
```

Recommended mechanism:

```text
Node Tuning Operator on dedicated search nodes
```

NTO profile:

```yaml
apiVersion: tuned.openshift.io/v1
kind: Tuned
metadata:
  name: search-vm-max-map-count
  namespace: openshift-cluster-node-tuning-operator
spec:
  profile:
    - name: search-vm-max-map-count
      data: |
        [main]
        summary=Set vm.max_map_count for search workloads
        include=openshift-node

        [sysctl]
        vm.max_map_count=262144
  recommend:
    - match:
        - label: tuned.openshift.io/search-node
      priority: 20
      profile: search-vm-max-map-count
```

Verify:

```bash
oc debug node/<node> -- chroot /host sysctl vm.max_map_count
```

### 17.2 Large file watcher workloads

Possible keys:

```text
fs.inotify.max_user_watches
fs.inotify.max_user_instances
```

Use case:

- build nodes
- developer workspaces
- large source-tree watchers

Mechanism:

- MachineConfig if you want persistent host baseline
- NTO if this belongs to a runtime tuning profile

### 17.3 High-connection application backlog

Possible key:

```text
net.core.somaxconn
```

Use cases:

- Redis
- NGINX
- HAProxy
- custom TCP servers

Important:

- If set at pod level, it is an unsafe pod sysctl and needs KubeletConfig/SCC.
- If set at host level, use NTO or MachineConfig and understand host namespace impact.
- Application listen backlog and container runtime/network namespace behavior also matter.

### 17.4 Local port range

Possible key:

```text
net.ipv4.ip_local_port_range
```

This can affect outbound connection scaling, but in OpenShift you must ensure it does not overlap with NodePort service ranges. Overlap can cause networking problems.

### 17.5 TCP keepalive settings

Possible keys:

```text
net.ipv4.tcp_keepalive_time
net.ipv4.tcp_keepalive_intvl
net.ipv4.tcp_keepalive_probes
```

Use case:

- long-lived connections
- database clients
- load balancer idle timeout alignment

Important:

- Check whether you need pod-level or host-level behavior.
- Coordinate with app, ingress, cloud LB, firewall, and database timeout settings.

## 18. Interview and exam notes

### 18.1 How to explain in an interview

Use this answer:

```text
In OpenShift, sysctls are split into namespaced pod sysctls and node-level sysctls. Safe namespaced sysctls can be set in pod securityContext. Unsafe namespaced sysctls require kubelet allowedUnsafeSysctls and usually SCC control. Non-namespaced node-level sysctls must be configured by the cluster administrator, typically with the Node Tuning Operator or a MachineConfig writing /etc/sysctl.d files. I avoid manual SSH changes because RHCOS nodes are declaratively managed by MCO. For production, I scope changes to a labeled node pool, canary first, verify through oc debug node and NTO/MCP status, and maintain a rollback plan.
```

### 18.2 Common exam-style question

**Question:** A pod fails with `SysctlForbidden` after adding `net.core.somaxconn` in pod securityContext. What do you check?

Answer:

```bash
oc describe pod <pod> -n <ns>
oc get kubeletconfig -o yaml
oc get mcp -o wide
oc get node <node> --show-labels
oc get pod <pod> -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
oc describe scc <scc>
```

Then confirm:

- the sysctl is allowed in kubelet `allowedUnsafeSysctls`
- the pod is scheduled on a node from that MCP
- SCC allows the unsafe sysctl
- the sysctl is namespaced and not interface-specific

### 18.3 Trick question

**Question:** Can MachineConfig `vm.max_map_count=262144` fix a pod-level `SysctlForbidden` error?

Answer:

```text
No. MachineConfig can set host/node values, but SysctlForbidden is pod admission/kubelet policy. For unsafe pod sysctls, configure KubeletConfig allowedUnsafeSysctls and SCC. For non-namespaced node-level sysctls, use MachineConfig or NTO and do not put them in pod securityContext.
```

### 18.4 Another trick question

**Question:** Is every `net.*` sysctl namespaced and safe?

Answer:

```text
No. Many net.* sysctls are namespaced, but not all are considered safe by Kubernetes/OpenShift. Safe status depends on the allowed list and version. Interface-specific sysctls are a separate category.
```

## Final senior-admin checklist

Before you apply any node-level sysctl change in OpenShift, confirm:

```text
[ ] Is this pod-level or node-level?
[ ] Is it namespaced?
[ ] Is it safe or unsafe?
[ ] Does it need KubeletConfig, SCC, NTO, MachineConfig, or tuning CNI?
[ ] Is the scope limited to the correct nodes?
[ ] Is there a canary?
[ ] Is the rollback tested?
[ ] Are MachineConfigPool and Node Tuning Operator healthy?
[ ] Are application owners aware?
[ ] Are values documented in Git?
```

The best OpenShift administrators are not the ones who know the most sysctl values. They are the ones who can safely control blast radius, preserve platform supportability, and prove the change works.
