# Node Drain and Reboot Behavior in OpenShift MachineConfig and Node-Level Administration

**Target audience:** Advanced OpenShift administrators with Linux/Kubernetes experience  
**Focus area:** MachineConfig, MachineConfigPool, Machine Config Operator, node drain, reboot, cordon/uncordon, PDB impact, troubleshooting  
**Reference baseline:** OpenShift Container Platform 4.x, with emphasis on current OCP 4.21 behavior

---

## 1. Executive Summary

In OpenShift, node drain and reboot behavior is not only a manual maintenance topic. It is deeply connected to the **Machine Config Operator (MCO)**, **MachineConfigPool (MCP)**, **MachineConfig**, **KubeletConfig**, **RHCOS lifecycle**, cluster upgrades, certificate rotation, registry configuration, kernel arguments, systemd changes, and node-level troubleshooting.

When a machine-level change is required, the MCO generally performs a controlled rolling update of affected nodes:

```text
MachineConfig / KubeletConfig / OS change
        ↓
Rendered MachineConfig generated
        ↓
MCP becomes UPDATING
        ↓
MCO selects node according to MCP rollout rules
        ↓
Node cordoned
        ↓
Pods drained / evicted
        ↓
Configuration applied on host
        ↓
Node rebooted if required
        ↓
Node returns Ready
        ↓
Node uncordoned
        ↓
MCP updated count increases
```

For a senior OpenShift administrator, the important point is this:

> A node reboot in OpenShift should normally be treated as a **cluster-orchestrated lifecycle event**, not as a random Linux reboot.

Manual `reboot` from SSH might work technically, but it bypasses Kubernetes-aware sequencing, workload eviction safety, MCP tracking expectations, and maintenance visibility. In production, prefer MCO-driven changes, `oc adm drain`, planned MCP rollout, and clear validation before and after the reboot.

## 2. Core Concepts

### 2.1 Node

A node is a RHCOS or RHEL host that runs OpenShift workloads. Most production OCP 4.x clusters use **Red Hat Enterprise Linux CoreOS (RHCOS)** for control-plane and worker nodes.

A node runs important components such as:

- `kubelet`
- `crio`
- OVN-Kubernetes / network components
- node-exporter
- machine-config-daemon
- CSI node plugins
- logging / monitoring agents
- application pods

### 2.2 Cordon

Cordon means marking a node as **unschedulable**.

Command:

```bash
oc adm cordon <node_name>
```

Effect:

```text
Existing pods continue running.
New normal pods are not scheduled on the node.
DaemonSet pods may still exist because DaemonSets tolerate unschedulable nodes.
```

Verify:

```bash
oc get node <node_name>
```

Expected status:

```text
Ready,SchedulingDisabled
```

### 2.3 Drain

Drain means safely evicting eligible pods from a node before maintenance or reboot.

Command:

```bash
oc adm drain <node_name> --ignore-daemonsets --delete-emptydir-data
```

Drain normally:

- cordons the node if not already cordoned
- evicts pods through the eviction API
- respects PodDisruptionBudgets
- waits for graceful termination
- does not remove mirror/static pods
- does not remove DaemonSet pods
- requires special flags for bare pods and `emptyDir` workloads

### 2.4 Reboot

Reboot restarts the node operating system. In OpenShift, reboots happen during:

- cluster upgrade
- RHCOS update
- kernel argument change
- kubelet configuration change
- CRI-O configuration change
- MachineConfig file/systemd changes that require reboot
- forced node recovery
- hardware / hypervisor maintenance

### 2.5 Uncordon

Uncordon returns the node to scheduling service.

Command:

```bash
oc adm uncordon <node_name>
```

After uncordon, the scheduler can place new pods on the node again.

## 3. Why Drain Before Reboot Matters

A reboot without drain can cause avoidable production issues:

| Area | Risk if node is rebooted without drain |
|---|---|
| Application availability | Pods disappear suddenly instead of graceful eviction |
| Stateful workloads | Write operations can be interrupted |
| PDB compliance | Kubernetes disruption rules are bypassed by node failure behavior |
| Load balancer readiness | Endpoints may not be removed gracefully before connection loss |
| Long shutdown apps | `terminationGracePeriodSeconds` may not be honored fully |
| Jobs / batch | Work may be lost or restarted unexpectedly |
| Monitoring | Alerts show node failure instead of planned maintenance |
| Storage | Local storage and `emptyDir` data can be lost |
| Cluster upgrade | MCO can become stuck if node state does not converge |

In Kubernetes terms, a drain is a **voluntary disruption**. A sudden reboot is closer to an **involuntary disruption**. PDBs protect voluntary disruptions, not all forms of sudden node failure.

## 4. Machine Config Operator Role in Drain and Reboot

The Machine Config Operator manages operating-system-level changes on OpenShift nodes.

Important MCO components:

| Component | Purpose |
|---|---|
| `machine-config-controller` | Coordinates node configuration rollouts from the control plane |
| `machine-config-daemon` | Runs on each node and applies the desired rendered config |
| `machine-config-server` | Serves Ignition configs to nodes joining the cluster |

The MCO manages areas such as:

- RHCOS updates
- kubelet configuration
- CRI-O configuration
- kernel arguments
- systemd units
- files under `/etc` and `/var`
- SSH authorized keys
- registry mirror configuration
- chrony / time sync configuration
- custom MachineConfig changes

When a MachineConfig change produces a new rendered configuration, the MCO updates affected nodes in a controlled rollout.

## 5. Standard MCO Node Update Flow

In most cases, the MCO performs this sequence per affected node:

```text
1. Cordon
2. Drain
3. Apply configuration
4. Reboot
5. Uncordon
```

### 5.1 Cordon Phase

The node is marked unschedulable.

Expected node status:

```bash
oc get nodes
```

Example:

```text
NAME       STATUS                     ROLES    AGE   VERSION
worker-1   Ready,SchedulingDisabled   worker   20d   v1.xx.x
```

At this point:

- existing pods may still be terminating
- new normal workload pods should not land on the node
- DaemonSet pods usually remain
- MCO/MCD continues to run

### 5.2 Drain Phase

MCO attempts to evict eligible pods.

Drain can be blocked by:

- strict PodDisruptionBudget
- single replica application with `minAvailable: 1`
- unhealthy replicas
- pods stuck terminating
- finalizers
- bare pods without controller
- long graceful termination
- storage detach delays
- application not reacting to SIGTERM
- custom workloads on control-plane nodes

### 5.3 Apply Phase

The MCD applies the new desired configuration to the host. Depending on the change, this can include:

- writing files
- changing file permissions
- updating systemd units
- reloading systemd
- changing kubelet config
- changing CRI-O config
- pivoting/updating OS image
- changing kernel arguments

### 5.4 Reboot Phase

If the change requires reboot, MCD reboots the node. During reboot:

- node becomes `NotReady`
- pods on that node are gone or terminating
- control-plane checks node health
- node object remains in the API
- machine-config state remains in progress

After boot:

- kubelet starts
- CRI-O starts
- static pods on control-plane nodes start
- CNI/node networking starts
- MCD validates applied state
- node becomes `Ready`

### 5.5 Uncordon Phase

MCO marks the node schedulable again after successful update.

```bash
oc get node <node_name>
```

Expected:

```text
Ready
```

## 6. MachineConfigPool and maxUnavailable

### 6.1 What MCP Controls

A MachineConfigPool groups nodes that should receive the same rendered machine configuration.

Default pools:

```bash
oc get mcp
```

Typical output:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False
worker    rendered-worker-yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy    True      False      False
```

MCP controls:

- which nodes receive a config
- how many nodes can update at once
- whether rollout is paused
- updated/degraded/readiness counts

### 6.2 maxUnavailable Meaning

`spec.maxUnavailable` defines how many nodes in a pool may be unavailable during an update.

Check:

```bash
oc get mcp worker -o yaml | grep -A5 maxUnavailable
```

Patch example:

```bash
oc patch mcp worker --type merge -p '{"spec":{"maxUnavailable":1}}'
```

Important production guidance:

- Default is usually `1`.
- Do not set control-plane `maxUnavailable` to `3` in a three-master cluster.
- Higher values can speed updates but increase workload pressure.
- `maxUnavailable` includes unavailable nodes for other reasons, not only MCO-updating nodes.
- You cannot use `maxUnavailable: 0` to stop updates; pause the MCP instead.

### 6.3 Why maxUnavailable Can Surprise You

Assume worker MCP has 5 nodes and `maxUnavailable: 1`.

If one worker is already cordoned manually or NotReady, MCO may not proceed with another worker update because the pool already has one unavailable machine.

Check:

```bash
oc get mcp worker
oc describe mcp worker
oc get nodes
```

Look at:

```text
MACHINECOUNT
READYMACHINECOUNT
UPDATEDMACHINECOUNT
DEGRADEDMACHINECOUNT
Unavailable Machine Count
```

## 7. How MCO Chooses Node Update Order

The MCO does not randomly reboot nodes. Node rollout order is controlled.

General behavior:

1. Nodes are grouped by MachineConfigPool.
2. Affected nodes are selected according to pool membership.
3. Nodes are updated up to `maxUnavailable` at a time.
4. For zoned clusters, nodes are processed alphabetically by zone label.
5. If multiple nodes exist in a zone, older nodes are generally updated first.
6. On deployments without zones, such as many bare-metal clusters, older nodes are generally updated first.

Useful labels:

```bash
oc get nodes --show-labels | grep topology.kubernetes.io/zone
```

Check node age:

```bash
oc get nodes --sort-by=.metadata.creationTimestamp
```

## 8. MachineConfig Changes That Usually Trigger Reboot

Most MachineConfig changes that affect host configuration cause drain and reboot.

Common reboot-triggering examples:

| Change | Why reboot may be required |
|---|---|
| Kernel arguments | Kernel command line only applies on boot |
| RHCOS / OS image update | Node must boot into new deployment |
| KubeletConfig change | Node service and config state must converge safely |
| CRI-O config change | Container runtime change impacts workload execution |
| Systemd unit change | Some unit changes require restart/reboot sequencing |
| Files under `/etc` | Depends on path and node disruption policy |
| Chrony config | May be restart-only with policy, otherwise can reboot by default |
| Registry mirror config | Often causes drain; reboot may depend on exact change/policy |

Examples:

```bash
oc get mc
oc get mcp
oc describe mcp worker
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig
```

## 9. MachineConfig Changes That May Not Drain or Reboot

Some changes are handled with little or no disruption.

Examples that can be applied without drain/reboot in current OpenShift behavior include:

- SSH authorized key changes in `spec.config.passwd.users.sshAuthorizedKeys`
- global pull secret changes
- pull secret changes in `openshift-config`
- automatic kubelet CA rotation by the Kubernetes API Server Operator

For `/etc/containers/registries.conf`, MCO has special behavior. Some registry changes can trigger drain/apply/uncordon without reboot, while selected additions such as digest-only mirror additions may avoid drain.

Do not assume every file update behaves the same. Always test in a lower environment and check MCP/MCD behavior.

## 10. Node Disruption Policy

### 10.1 What It Is

A **node disruption policy** allows administrators to define what action the MCO should take for specific MachineConfig changes.

It is configured through the singleton object:

```bash
oc edit MachineConfiguration cluster -n openshift-machine-config-operator
```

Do not confuse:

| Object | Purpose |
|---|---|
| `MachineConfig` | Defines node OS-level desired configuration for a pool |
| `MachineConfiguration` | Defines MCO operator-level behavior such as node disruption policy |

### 10.2 Possible Actions

Node disruption policy actions include:

| Action | Meaning |
|---|---|
| `Reboot` | Drain and reboot nodes. Default behavior for many changes. |
| `None` | Apply change without drain or reboot. |
| `Drain` | Cordon and drain, but not necessarily reboot. |
| `Reload` | Reload a specific service. |
| `Restart` | Restart a specific service. |
| `DaemonReload` | Reload systemd manager configuration. |
| `Special` | Internal MCO logic, mainly for `registries.conf`. |

### 10.3 Example: Restart chronyd Instead of Reboot

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
  namespace: openshift-machine-config-operator
spec:
  nodeDisruptionPolicy:
    files:
    - path: /etc/chrony.conf
      actions:
      - type: Restart
        restart:
          serviceName: chronyd.service
```

### 10.4 Example: CRI-O Restart for Registries Config Directory

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
  namespace: openshift-machine-config-operator
spec:
  nodeDisruptionPolicy:
    files:
    - path: /etc/containers/registries.conf.d
      actions:
      - type: Restart
        restart:
          serviceName: crio.service
```

### 10.5 Important Warnings

- `Reboot` and `None` override other actions and should not be mixed with other actions for the same policy entry.
- Actions are applied in the listed order.
- If another change in the same rendered config requires reboot, that reboot supersedes a less disruptive policy.
- MCO validates policy format but does not guarantee that your chosen action is operationally correct for the changed service/file.
- Do not use node disruption policy to avoid a required reboot without deep testing.

## 11. Pausing an MCP

### 11.1 What Pausing Does

Pausing an MCP prevents MCO from applying new configuration changes to nodes in that pool.

Pause:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":true}}'
```

Unpause:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":false}}'
```

### 11.2 When to Pause

Use pause carefully for:

- maintenance window control
- staging changes before rollout
- canary pool strategy
- preventing immediate reboot after MachineConfig creation
- troubleshooting a bad rollout before more nodes update

### 11.3 Pausing Is Not Free

A paused MCP does not receive pending MachineConfig updates. Long pauses can create operational risk, including delayed automatically rotated certificates and delayed node-level security fixes.

Production rule:

> Pause only for a specific reason, document it, monitor it, and unpause as soon as possible.

Check paused pools:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status,UPDATING:.status.conditions[?(@.type=="Updating")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status
```

## 12. Manual Node Maintenance Workflow

Use this when you need hardware, hypervisor, kernel, firmware, or emergency maintenance outside a MachineConfig rollout.

### 12.1 Pre-checks

```bash
NODE=<node_name>

oc get node $NODE -o wide
oc describe node $NODE
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
oc get pdb -A
oc get mcp
oc get co
```

Check capacity impact:

```bash
oc adm top nodes
oc adm top pods -A --sort-by=cpu | head
oc adm top pods -A --sort-by=memory | head
```

Check critical workloads on node:

```bash
oc get pods -A --field-selector spec.nodeName=$NODE \
  -o custom-columns=NS:.metadata.namespace,POD:.metadata.name,OWNER:.metadata.ownerReferences[0].kind,STATUS:.status.phase,NODE:.spec.nodeName
```

### 12.2 Cordon

```bash
oc adm cordon $NODE
oc get node $NODE
```

### 12.3 Dry-run Drain

```bash
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

If server-side dry run is not supported in your client/version, use:

```bash
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --dry-run=true
```

### 12.4 Drain

Standard production drain:

```bash
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --timeout=30m
```

For bare pods or unmanaged pods:

```bash
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --force --timeout=30m
```

Use `--force` only when you understand which pods are unmanaged.

### 12.5 Reboot

Preferred via debug/chroot:

```bash
oc debug node/$NODE
chroot /host
systemctl reboot
```

Or SSH if allowed:

```bash
ssh core@$NODE
sudo systemctl reboot
```

### 12.6 Wait for Node Return

```bash
watch -n5 "oc get node $NODE; echo; oc get pods -A --field-selector spec.nodeName=$NODE"
```

Check kubelet and CRI-O after reboot:

```bash
oc debug node/$NODE -- chroot /host systemctl is-active kubelet
oc debug node/$NODE -- chroot /host systemctl is-active crio
```

### 12.7 Uncordon

```bash
oc adm uncordon $NODE
oc get node $NODE
```

### 12.8 Post-checks

```bash
oc get nodes
oc get mcp
oc get co
oc get pods -A | egrep -v 'Running|Completed'
oc adm top nodes
```

## 13. Manual Drain Flags Explained

### 13.1 `--ignore-daemonsets`

Drain normally refuses to proceed when DaemonSet-managed pods exist unless you specify this flag.

Why?

DaemonSet pods are controlled by DaemonSets and are generally expected to run on every eligible node. They are not removed by drain like Deployment pods.

Command:

```bash
oc adm drain <node> --ignore-daemonsets
```

### 13.2 `--delete-emptydir-data`

Allows drain to proceed for pods using `emptyDir` volumes.

Warning:

```text
emptyDir data is node-local ephemeral data. It is deleted when the pod is removed from the node.
```

Command:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

### 13.3 `--force`

Allows deletion of pods not managed by a recognized controller, such as bare pods.

Use carefully:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --force
```

Before using force, inspect unmanaged pods:

```bash
oc get pods -A --field-selector spec.nodeName=<node> \
  -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{" owner="}{.metadata.ownerReferences[0].kind}{"\n"}{end}'
```

### 13.4 `--timeout`

Controls how long drain waits.

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=30m
```

### 13.5 `--grace-period`

Overrides pod termination grace period.

Example:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --grace-period=60
```

Be careful with databases and stateful applications.

### 13.6 `--disable-eviction`

This forces delete instead of eviction and bypasses PDB checks.

Avoid in normal production maintenance.

Use only in controlled break-glass situations where availability rules are already impossible to satisfy and business owners accept impact.

## 14. PodDisruptionBudget Impact

### 14.1 Why PDB Matters

A PodDisruptionBudget defines how many pods of an application must remain available during voluntary disruptions such as drain.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: prod
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web
```

If `app=web` has 3 replicas, one can be evicted at a time. If only 2 are healthy, drain may block.

### 14.2 Common PDB Block Scenarios

| Situation | Result |
|---|---|
| Deployment has 1 replica and PDB `minAvailable: 1` | Drain blocked |
| 3 replicas, PDB `minAvailable: 3` | Drain blocked |
| `maxUnavailable: 0` | Drain blocked |
| Pods unhealthy, PDB uses default unhealthy policy | Drain waits |
| StatefulSet replica unavailable | Drain can block |
| Multiple nodes drained together | PDB allows only safe number of evictions |

Check PDBs:

```bash
oc get pdb -A
```

Look at:

```text
MIN AVAILABLE
MAX UNAVAILABLE
ALLOWED DISRUPTIONS
```

If `ALLOWED DISRUPTIONS` is `0`, drain can block.

### 14.3 Troubleshooting PDB Block

Find pods on node:

```bash
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
```

Check PDB details:

```bash
oc describe pdb <pdb_name> -n <namespace>
```

Check unhealthy pods:

```bash
oc get pods -n <namespace> -l <label_selector> -o wide
```

Options:

- temporarily scale replicas up
- fix unhealthy pods first
- adjust PDB after approval
- drain a different node first
- reduce parallel update pressure
- avoid changing MCP `maxUnavailable` blindly

Production recommendation:

```text
Fix application availability first. Do not immediately bypass PDBs.
```

## 15. Special Case: Control-Plane Nodes

Control-plane nodes run critical components:

- kube-apiserver static pods
- kube-controller-manager static pods
- kube-scheduler static pods
- etcd static pods
- authentication components
- monitoring components
- ingress/router if infrastructure placement is configured there

Important behavior:

- MCO does not drain static pods such as etcd-related static pods.
- Control-plane updates should normally happen one node at a time.
- Do not set master/control-plane MCP `maxUnavailable` to all nodes.
- If user workloads run on masters, those workloads can complicate drain.

Check control-plane MCP:

```bash
oc get mcp master
oc describe mcp master
oc get nodes -l node-role.kubernetes.io/master
```

Check etcd health before planned master reboot:

```bash
oc get co etcd kube-apiserver kube-controller-manager kube-scheduler
oc -n openshift-etcd get pods -o wide
oc -n openshift-etcd rsh etcd-<node_name> etcdctl endpoint health
```

If you do not have exact etcd pod name:

```bash
oc -n openshift-etcd get pods -l app=etcd -o wide
```

## 16. Special Case: Single-Node OpenShift

Single-node OpenShift has unique behavior because there is no other node to receive evicted workloads.

Important points:

- Standard drain is not available in the same way as multi-node clusters.
- Workloads cannot be rescheduled elsewhere.
- Reboot means full cluster outage.
- Failed pods after reboot may need manual cleanup.

Common cleanup command:

```bash
oc delete pods --field-selector status.phase=Failed -n <namespace>
```

For SNO maintenance, plan downtime and ensure you have console/SSH access before reboot.

## 17. MCO Status Monitoring During Drain/Reboot

### 17.1 MCP Status

```bash
oc get mcp
```

Example:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
```

Meaning:

| Field | Meaning |

| `READYMACHINECOUNT` | Nodes ready and running current config |
| `UPDATEDMACHINECOUNT` | Nodes that have current config |

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Useful annotations:

```text
machineconfiguration.openshift.io/currentConfig
machineconfiguration.openshift.io/desiredConfig
machineconfiguration.openshift.io/state
machineconfiguration.openshift.io/reason
```

Typical states:

```text
Done
Working
Degraded
```

### 17.3 MachineConfigNode

Newer OpenShift versions provide MachineConfigNode status for update progress.

```bash
oc get machineconfignodes
```

This helps identify whether the node is in:

- update prepared
- cordoned
- drained
- applied files and OS

- uncordoned
- updated
- resumed

## 20. Troubleshooting: MCO Stuck Draining Node

### 20.1 Symptoms

```bash
oc get mcp
```

Shows:

```text
UPDATED=False
UPDATING=True
DEGRADED=False or True
READYMACHINECOUNT lower than MACHINECOUNT
```

MCD logs show drain attempts or eviction failures.

### 20.2 Investigation Flow

Set variables:

```bash
NODE=<node_name>
```

Check node:

```bash
oc get node $NODE
oc describe node $NODE
```

Check pods on node:

```bash
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
```

Check PDBs:

```bash
oc get pdb -A
```

Check non-running pods:

```bash
oc get pods -A | egrep -v 'Running|Completed'
```

Check MCD log:

```bash
MCD=$(oc -n openshift-machine-config-operator get pod -o wide | awk -v n=$NODE '$0 ~ /machine-config-daemon/ && $0 ~ n {print $1; exit}')
oc logs -n openshift-machine-config-operator $MCD -c machine-config-daemon | egrep -i 'drain|evict|pdb|error|failed'
```

### 20.3 Common Root Causes and Fixes

#### Cause: PDB allowed disruptions is zero

Check:

```bash
oc get pdb -A
oc describe pdb <pdb> -n <namespace>
```

Fix options:

```bash
oc scale deploy/<name> -n <namespace> --replicas=<higher_number>
```

Or after approval, adjust PDB temporarily.

#### Cause: Single replica protected by strict PDB

Example bad combination:

```text
replicas: 1
PDB minAvailable: 1
```

Fix:

```bash
oc scale deploy/<name> -n <namespace> --replicas=2
```

Then retry/wait for MCO.

#### Cause: Pod stuck Terminating

Check:

```bash
oc get pod <pod> -n <namespace> -o yaml | grep -A10 finalizers
oc describe pod <pod> -n <namespace>
```

Fix depends on finalizer owner. Avoid deleting finalizers blindly unless you understand the controller and data impact.

#### Cause: Bare pod not managed by controller

Drain may require `--force` manually, but MCO drain behavior is not something you should bypass casually.

Best fix:

- convert bare pod to Deployment/DaemonSet/Job
- delete or move the pod after approval

#### Cause: Long termination grace period

Check:

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.spec.terminationGracePeriodSeconds}{"\n"}'
```

Fix:

- wait if acceptable
- tune app shutdown behavior
- reduce grace period in workload spec after validation

## 21. Troubleshooting: Node Rebooted but MCP Still Updating

### 21.1 Symptoms

- Node is `Ready`
- MCP still `UPDATING=True`
- `currentConfig` does not equal `desiredConfig`
- MCD logs show apply or validation issue

Check:

### 21.2 Common Causes

| Cause | Signal |
|---|---|

| OS pivot failed | MCD pivot errors |
| Disk full | image pull or OS update failure |

## 22. Troubleshooting: MCP Degraded After Drain/Reboot

### 22.1 Check MCP

```bash
oc get mcp
oc describe mcp worker
```

Look for:

```text
NodeDegraded
RenderDegraded
Failed to drain node
content mismatch
unexpected on-disk state
```

### 22.2 Check Node Annotation

```bash
oc describe node <node> | egrep -i 'machineconfiguration|degraded|reason|currentConfig|desiredConfig' -A5
```

### 22.3 Configuration Drift

Configuration drift means the on-disk host state differs from the current MachineConfig.

Common causes:

- admin manually edited a MachineConfig-managed file
- permissions changed
- systemd drop-in modified manually
- file deleted manually
- emergency hotfix not represented in MachineConfig

Correct approach:

1. Identify exact mismatch from MCD reason/log.
2. Compare actual host file with MachineConfig desired state.
3. Restore file/permission manually or update MachineConfig properly.
4. Let MCD re-check.

Avoid repeated manual edits on RHCOS nodes. Use MachineConfig.

## 23. Difference Between MCO-Driven Reboot and Manual Reboot

| Area | MCO-driven reboot | Manual reboot |
|---|---|---|
| Trigger | Rendered config/upgrade | Admin action |
| Drain | MCO performs drain if required | Admin must drain manually |
| Cordon | Automatic | Manual unless using drain |
| Uncordon | Automatic after success | Manual if cordoned |
| MCP awareness | Fully tracked | May appear as node outage only |
| Config apply | Before reboot | Not necessarily |
| Risk | Controlled | Depends on admin process |
| Best use | Config lifecycle | Hardware/emergency maintenance |

Manual reboot is acceptable when planned properly:

```text
cordon → drain → reboot → verify → uncordon
```

Manual reboot is risky when done as:

```text
ssh node → reboot
```

## 24. Cluster Upgrade Drain/Reboot Behavior

During an OpenShift upgrade:

1. CVO applies new release payload.
2. Cluster operators update their components.
3. MCO applies host-level updates.
4. Nodes are cordoned/drained, OS updated, rebooted, and uncordoned.

Upgrade duration depends on:

- number of nodes
- `maxUnavailable`
- PDB restrictions
- node health
- image pull speed
- OS update time
- storage detach/attach time
- workload shutdown behavior

Pre-upgrade checks:

```bash
oc get co
oc get mcp
oc get nodes
oc get pdb -A
oc adm upgrade
```

During upgrade:

```bash
watch -n10 'oc get clusterversion; echo; oc get co; echo; oc get mcp; echo; oc get nodes'
```

Do not force reboot nodes manually during an active MCO update unless following a Red Hat support-approved recovery path.

## 25. Stateful Workloads and Drain/Reboot

### 25.1 StatefulSet Behavior

StatefulSets have stable identities and storage. Drain can evict StatefulSet pods, but safe recovery depends on:

- PDB
- storage backend
- volume access mode
- application replication
- shutdown behavior
- readiness/liveness probes

Examples:

| Workload | Drain concern |
|---|---|
| PostgreSQL | primary failover, WAL consistency |
| Kafka | broker leadership and partition availability |
| Elasticsearch | shard relocation and quorum |
| Redis | primary/replica failover |
| Ceph/ODF | storage quorum and recovery impact |
| OpenShift Virtualization | VM live migration or shutdown behavior |

### 25.2 Best Practices

- Use PDBs, but do not make them impossible to satisfy.
- Use at least 2 or 3 replicas for HA workloads.
- Validate readiness probes.
- Ensure replicas are spread across nodes/zones.
- Use anti-affinity or topology spread constraints.
- Avoid local-only storage unless workload is designed for it.
- Understand storage detach/attach time.

Check pod distribution:

```bash
oc get pods -n <namespace> -o wide
```

Check topology spread/affinity:

```bash
oc get deploy/statefulset <name> -n <namespace> -o yaml | egrep -i 'affinity|topologySpread|podAntiAffinity|topologyKey' -A20
```

## 26. DaemonSets During Drain

DaemonSet pods usually remain on the node during drain.

Examples:

- `machine-config-daemon`
- network node agents
- CSI node plugins
- log collectors
- node exporters

Drain needs:

```bash
--ignore-daemonsets
```

This does not mean DaemonSet pods are deleted. It means drain ignores them so maintenance can continue.

After reboot, DaemonSet pods restart naturally on the node.

## 27. Static Pods and Mirror Pods

Control-plane components such as etcd and kube-apiserver are static pods managed by kubelet manifests on the host.

Drain does not delete mirror/static pods through the API.

This matters because:

- `oc adm drain` may show static/mirror pods but not remove them.
- Control-plane safety is handled by operator-specific logic and quorum design.
- Rebooting a control-plane node temporarily removes that member from service.

Check static pods:

```bash
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-apiserver -o wide
```

Host manifests:

```bash
oc debug node/<master_node>
chroot /host
ls -l /etc/kubernetes/manifests/
```

## 28. Bare Metal vs Cloud Node Maintenance

### 28.1 Cloud / Machine API Clusters

Nodes are often backed by Machine and MachineSet objects.

Check:

```bash
oc get machines -n openshift-machine-api
oc get machinesets -n openshift-machine-api
```

For permanent node removal, use MachineSet/Machine workflows rather than simply deleting the Kubernetes Node object.

### 28.2 Bare Metal Clusters

Bare metal often requires manual hardware lifecycle.

Safe removal sequence:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --force
oc delete node <node>
```

Then decommission hardware appropriately.

Important:

> If the node is unresponsive but still powered on, it might still write to shared storage. Power off or isolate the host before destructive removal.

## 29. OpenShift Virtualization Note

If OpenShift Virtualization is installed, node drain can involve VM migration or shutdown behavior.

Important points:

- VMIs may live migrate only if configured and storage/network supports it.
- RWX storage is often required for live migration.
- NodeMaintenance CRs can be used in virtualization environments.
- Do not treat VM workloads exactly like normal stateless pods.

Basic check:

```bash
oc get vmi -A -o wide
```

Before draining a node running VMIs, confirm migration strategy and storage mode.

## 31. Interview-Level Explanation

### Question: What happens when you apply a MachineConfig that requires reboot?

Answer:

When a MachineConfig is created or modified, the MCO renders a new merged config for the matching MCP. The MCP becomes updating. The MCO then updates nodes in that pool according to `maxUnavailable`. For each selected node, the MCO cordons the node, drains eligible pods while respecting PDBs, applies the host-level change through the machine-config-daemon, reboots the node if required, validates the node has the desired config after boot, and finally uncordons it. MCP counts such as `READYMACHINECOUNT`, `UPDATEDMACHINECOUNT`, and `DEGRADEDMACHINECOUNT` show rollout progress.

### Question: Why can an OpenShift upgrade get stuck during node reboot?

Answer:

The upgrade can get stuck in the MCO phase if one or more nodes cannot drain, cannot apply the OS/config update, cannot reboot, or come back degraded. Common causes are strict PDBs, unhealthy pods, stuck terminating pods, unavailable nodes already consuming `maxUnavailable`, CRI-O/kubelet failures, disk pressure, pivot failures, or configuration drift.

### Question: Does `oc adm drain` delete DaemonSet pods?

Answer:

No. Drain ignores DaemonSet-managed pods only when `--ignore-daemonsets` is provided. It does not delete them because the DaemonSet controller would recreate them and DaemonSet pods commonly tolerate unschedulable nodes.

### Question: Is it safe to SSH and reboot a node?

Answer:

It is technically possible but not the preferred production workflow. A safe manual reboot should use `cordon → drain → reboot → verify → uncordon`. Random SSH reboot bypasses workload eviction safety and can cause avoidable application impact.

### Question: What blocks drain most often?

Answer:

PodDisruptionBudgets with zero allowed disruptions, single-replica apps protected by `minAvailable: 1`, unhealthy replicas, pods stuck terminating, bare pods, and storage detach issues.

## 33. Production Best Practices

1. **Never reboot production nodes casually.** Use Kubernetes-aware maintenance.
2. **Always check PDBs before planned drain.** `ALLOWED DISRUPTIONS=0` is a warning.
3. **Keep control-plane updates one node at a time.** Do not increase master `maxUnavailable` dangerously.
4. **Avoid bare pods.** Use Deployment, StatefulSet, DaemonSet, or Job.
5. **Use MachineConfig for persistent host changes.** Do not manually edit RHCOS files long-term.
6. **Monitor MCP status after any MachineConfig change.**
7. **Do not leave MCPs paused for long periods.**
8. **Use custom MCPs for canary worker rollouts.**
9. **Test node disruption policies in non-production first.**
10. **Do not bypass PDBs unless impact is approved.**
11. **Make apps drain-friendly.** Proper readiness probes, graceful shutdown, replicas, and PDBs matter.
12. **Check storage behavior.** Stateful workloads can extend drain time significantly.
13. **Keep enough spare capacity.** A drain moves workload elsewhere.
14. **Watch MCD logs, not only `oc get mcp`.** Logs explain the real blocker.
15. **Document maintenance windows and node actions.**

## 34. Common Mistakes

| Mistake | Impact |
|---|---|
| SSH reboot without drain | Sudden workload disruption |
| Forgetting uncordon | Node stays unused after maintenance |
| Setting strict PDB on single replica | Drain/upgrade stuck |
| Increasing worker `maxUnavailable` without capacity check | Application overload |
| Increasing master `maxUnavailable` to all masters | Control-plane outage risk |
| Pausing MCP and forgetting it | Missed updates/certs/security fixes |
| Editing rendered MachineConfig | Unsupported/bad rollback behavior |
| Manually editing MachineConfig-managed files | Configuration drift |
| Using `--force` blindly | Data/application impact |
| Ignoring `emptyDir` | Ephemeral data loss surprises |
| Not checking MCD logs | Slow troubleshooting |

## 35. Mental Model for 10-Year Admin

Think about node drain and reboot in four layers:

### Layer 1: Kubernetes Scheduling

```text
cordon controls future scheduling
```

### Layer 2: Workload Eviction

```text
drain removes eligible pods safely and respects PDBs
```

### Layer 3: OpenShift Machine Lifecycle

```text
MCO applies desired host configuration through MCP rollout
```

### Layer 4: Linux/RHCOS Boot State

```text
reboot activates OS/kernel/runtime config and MCD validates convergence
```

If something is stuck, identify the layer:

| Symptom | Likely layer |
|---|---|
| New pods not scheduling to node | cordon/scheduler |
| Drain hangs | PDB/pod eviction |
| MCP updating forever | MCO/MCD/apply/reboot |
| Node NotReady after reboot | kubelet/CRI-O/network/OS |
| MCP degraded with content mismatch | config drift |
| Pods not returning | app/controller/scheduling/storage |

## 38. Final Takeaway

Node drain and reboot behavior in OpenShift is a coordination problem across Kubernetes, MCO, MCP, RHCOS, kubelet, CRI-O, PDBs, storage, and application readiness.

For an advanced administrator, the correct mindset is:

```text
Do not ask only: “How do I reboot the node?”
Ask: “How do I safely remove workload, preserve availability, apply desired host state, validate convergence, and return the node to service?”
```

That is the difference between a basic node reboot and production-grade OpenShift node administration.
