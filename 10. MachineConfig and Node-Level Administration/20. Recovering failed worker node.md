# Recovering a Failed Worker Node in OpenShift

**Area:** MachineConfig and Node-Level Administration  
**Audience:** Advanced OpenShift Administrator / Senior Linux-Kubernetes Engineer  
**Assumption:** OpenShift Container Platform 4.x, RHCOS workers, `oc` CLI access with `cluster-admin` privileges  
**Goal:** Recover service safely, understand when to repair a node, when to replace it, and how MachineConfig/MachineConfigPool behavior affects recovery.

---

## 1. What “failed worker node” really means

A worker node is not “failed” just because `oc get nodes` shows `NotReady`. In OpenShift, a worker node can fail at several layers:

| Layer | Object / Component | Typical symptom |
|---|---|---|
| Kubernetes node health | `Node`, kubelet heartbeat | `NotReady`, `Unknown`, `node.kubernetes.io/unreachable` taint |
| Host operating system | RHCOS, systemd, kernel, filesystem | SSH/debug unavailable, reboot loop, disk full, kernel panic |
| Container runtime | CRI-O, conmon, podman storage | Pods stuck `ContainerCreating`, `CrashLoopBackOff`, runtime socket errors |
| Kubelet | `kubelet.service` | Node registered but cannot manage pods, cert/auth errors, CNI errors |
| Machine API | `Machine`, `MachineSet` | Machine `Failed`, stuck `Deleting`, provider instance gone |
| MachineConfig | MCO, MCD, MCP | MCP `Degraded`, MCD `Working` forever, drift detected, update blocked |
| Network | Node-to-API, DNS, SDN/OVN, MTU, firewall | Node reachable by ping but not kubelet/API, pods cannot reach services |
| Storage | CSI, PV attachment, local disk | Volume attach/detach stuck, RWO volume locked to failed node |
| Platform infrastructure | Cloud VM, hypervisor, bare metal, power, BMC | Host powered off, lost disk, bad NIC, hardware failure |

A senior administrator does not start with `oc delete node`. The first decision is:

> Is this node recoverable, or should it be replaced?

That decision depends on workload risk, data risk, infrastructure type, and whether the node is still capable of writing to shared storage.

## 2. Important OpenShift concepts before recovery

### 2.1 Node object

The Kubernetes `Node` object is the API representation of the host. It contains conditions such as:

- `Ready`
- `MemoryPressure`
- `DiskPressure`
- `PIDPressure`
- `NetworkUnavailable`

A node can be physically running even when the Kubernetes `Node` object is `NotReady` or `Unknown`.

### 2.2 Machine object

On IPI/cloud/Machine API based clusters, the `Machine` object represents the infrastructure instance behind the node.

Examples:

```bash
oc get machines -n openshift-machine-api -o wide
oc describe machine <machine-name> -n openshift-machine-api
```

A worker node usually maps like this:

```text
MachineSet -> Machine -> cloud/baremetal/virtual instance -> Node
```

For Machine API clusters, deleting a `Machine` is usually the correct replacement workflow. Deleting only the `Node` object can leave the real instance, pods, volumes, and Machine API state inconsistent.

### 2.3 MachineSet

A `MachineSet` maintains the desired worker count for a failure domain, zone, or pool. If a failed machine belongs to a MachineSet and you delete the `Machine`, the MachineSet normally creates a replacement to satisfy replica count.

Check:

```bash
oc get machinesets -n openshift-machine-api
oc get machines -n openshift-machine-api -o wide
```

### 2.4 MachineConfigPool

A `MachineConfigPool` groups nodes that receive the same rendered machine configuration.

Check:

```bash
oc get mcp
oc describe mcp worker
```

Important fields:

```text
UPDATED
UPDATING
DEGRADED
MACHINECOUNT
READYMACHINECOUNT
UPDATEDMACHINECOUNT
DEGRADEDMACHINECOUNT
```

If a worker fails during a MachineConfig rollout, the pool might remain `Updating=True` or become `Degraded=True`. That can block future updates and cluster upgrades.

### 2.5 MachineConfigDaemon

The Machine Config Daemon runs on each node and applies rendered MachineConfig content. It can reboot nodes, drain nodes, apply systemd/kubelet/CRI-O/kernel/network configuration, and report degraded state.

Useful checks:

```bash
oc get pods -n openshift-machine-config-operator -o wide
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon
oc describe node <node-name> | egrep -i 'machineconfiguration|currentConfig|desiredConfig|state|reason'
```

Common node annotations:

```text
machineconfiguration.openshift.io/currentConfig
machineconfiguration.openshift.io/desiredConfig
machineconfiguration.openshift.io/state
machineconfiguration.openshift.io/reason
```

Typical states:

```text
Done
Working
Degraded
```

### 2.6 CSR during node replacement

When a new worker joins, kubelet certificate signing requests might require approval, especially in UPI/bare-metal or manually added node workflows.

Check:

```bash
oc get csr
```

Approve only after verifying the requester and node identity:

```bash
oc describe csr <csr-name>
oc adm certificate approve <csr-name>
```

## 3. Recovery decision tree

Use this before taking action.

```text
Worker node failed
│
├── Is the failure affecting many nodes?
│   ├── Yes: suspect MachineConfig rollout, network, DNS, platform, cert, registry, or global infra issue.
│   │        Stop broad remediation. Protect MCP and workloads first.
│   └── No: continue single-node recovery.
│
├── Is the node still reachable at OS level?
│   ├── Yes: debug live, inspect kubelet/CRI-O/MCD/system logs, recover if safe.
│   └── No: decide platform replacement or manual decommission.
│
├── Is the node possibly still writing to shared storage?
│   ├── Yes/Unknown: fence or power off before deleting Node object in bare-metal/manual flows.
│   └── No: proceed with drain/delete/replacement workflow.
│
├── Is the cluster using Machine API/MachineSets?
│   ├── Yes: delete or replace the Machine, not only the Node.
│   └── No: cordon/drain/power-off/delete Node, then manually rebuild/rejoin host.
│
└── Did MachineConfig cause or expose the issue?
    ├── Yes: inspect MCP/MCD/rendered config; fix/revert MC; avoid hand-edit drift.
    └── No: complete node verification and uncordon/replace.
```

## 4. First 10-minute triage

### 4.1 Confirm cluster-wide status

```bash
oc get clusterversion
oc get co
oc get nodes -o wide
oc get mcp
oc get machines -n openshift-machine-api -o wide
oc get machinesets -n openshift-machine-api
```

Look for:

- Only one worker affected vs many workers
- Control plane healthy or degraded
- Machine API operator healthy
- MCO/MCP degraded
- Cluster upgrade in progress
- Node version mismatch
- New MachineConfig rollout

### 4.2 Identify failed node and related Machine

```bash
NODE=<failed-worker-node>

oc get node $NODE -o wide
oc describe node $NODE

oc get machines -n openshift-machine-api -o wide | grep -E "$NODE|NAME"
```

If the node name is not shown in Machine output, search by provider ID:

```bash
oc get node $NODE -o jsonpath='{.spec.providerID}{"\n"}'
oc get machines -n openshift-machine-api -o json | jq -r '.items[] | [.metadata.name,.status.nodeRef.name,.spec.providerID,.status.phase] | @tsv'
```

### 4.3 Check node conditions quickly

```bash
oc get node $NODE -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.message}{"\n"}{end}'
```

Useful interpretation:

| Condition | Meaning |
|---|---|
| `Ready=False` | kubelet is reporting unhealthy |
| `Ready=Unknown` | control plane lost heartbeat from kubelet |
| `DiskPressure=True` | image/log/ephemeral storage pressure |
| `MemoryPressure=True` | node memory pressure |
| `PIDPressure=True` | process exhaustion |
| `NetworkUnavailable=True` | node networking problem |

### 4.4 Check taints

```bash
oc describe node $NODE | sed -n '/Taints:/,/Unschedulable:/p'
```

Common failure taints:

```text
node.kubernetes.io/not-ready:NoExecute
node.kubernetes.io/unreachable:NoExecute
node.kubernetes.io/disk-pressure:NoSchedule
node.kubernetes.io/memory-pressure:NoSchedule
```

### 4.5 See workloads on the failed node

```bash
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
```

Check stateful workloads separately:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=$NODE | egrep -i 'mysql|postgres|mariadb|mongo|redis|kafka|etcd|rook|ceph|odf|stateful|db|database'
```

Check PVC usage:

```bash
oc get pods -A -o json | jq -r --arg NODE "$NODE" '
  .items[]
  | select(.spec.nodeName==$NODE)
  | [.metadata.namespace, .metadata.name, ((.spec.volumes[]? | select(.persistentVolumeClaim) | .persistentVolumeClaim.claimName) // "-")]
  | @tsv'
```

This matters because a failed node can still hold RWO volumes, CSI attachments, or filesystem locks.

## 5. Safety rules for senior administrators

### Rule 1: Do not delete the Node first on Machine API clusters

On cloud/Machine API clusters, prefer Machine/MachineSet actions. The Machine controller handles drain, provider instance deletion, and Node cleanup. Deleting only the `Node` object can create split-brain style operational confusion: the instance might still run, kubelet might re-register, and Machine API might not reconcile the way you expect.

### Rule 2: Treat an unreachable bare-metal node as dangerous until fenced

If the node is `Unknown` or unreachable, it might still be running workloads and writing to shared storage. Before forcing deletion in a bare-metal/manual environment, confirm it is powered off or fenced.

### Rule 3: Avoid hand-editing RHCOS host configuration

For persistent node configuration, use OpenShift APIs such as:

- `MachineConfig`
- `KubeletConfig`
- `ContainerRuntimeConfig`
- `ImageDigestMirrorSet` / registry configuration APIs
- `chrony` MachineConfig pattern
- cluster-supported network configuration APIs

Manual host edits can create MachineConfig drift and degrade the MCP.

### Rule 4: If many workers fail after a config change, stop the rollout

If a new MachineConfig is breaking nodes, pause the affected MCP before more nodes reboot into the same failure:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

After fixing/reverting the bad MachineConfig:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Use this carefully. A paused MCP will also pause legitimate configuration progress.

### Rule 5: Preserve evidence before destructive recovery

Before deletion/replacement, collect enough information:

```bash
oc adm must-gather
oc get node $NODE -o yaml > node-$NODE.yaml
oc describe node $NODE > describe-node-$NODE.txt
oc get pods -A -o wide --field-selector spec.nodeName=$NODE > pods-on-$NODE.txt
oc get mcp -o yaml > mcp.yaml
oc get machines -n openshift-machine-api -o yaml > machines.yaml
```

For support cases, gather MCO and node logs when possible.

## 6. Live recovery path: node reachable

Use this path when `oc debug node/<node>` works or SSH/console access is available.

### 6.1 Enter node debug shell

```bash
oc debug node/$NODE
chroot /host
```

Inside the host namespace:

```bash
hostname
date
uptime
systemctl is-system-running
systemctl status kubelet --no-pager
systemctl status crio --no-pager
systemctl status NetworkManager --no-pager
```

### 6.2 Check kubelet logs

```bash
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u kubelet -b --no-pager | egrep -i 'error|fail|certificate|cni|network|runtime|PLEG|evict|disk|memory|pressure' | tail -100
```

Common kubelet failure classes:

| Log pattern | Likely issue |
|---|---|
| `certificate signed by unknown authority` | CA/cert/bootstrap issue |
| `x509: certificate has expired` | cert expiry or clock issue |
| `container runtime is down` | CRI-O/socket failure |
| `NetworkPluginNotReady` | CNI/OVN issue |
| `PLEG is not healthy` | runtime overloaded or hung |
| `eviction manager` | memory/disk pressure |
| `failed to update node status` | API connectivity/auth/network problem |

### 6.3 Check CRI-O logs

```bash
journalctl -u crio -b --no-pager | tail -200
journalctl -u crio -b --no-pager | egrep -i 'error|fail|panic|overlay|storage|cgroup|conmon|runtime|permission|no space' | tail -100
```

Runtime checks:

```bash
crictl info
crictl ps -a | head
crictl images | head
```

Disk pressure often appears in CRI-O and kubelet logs:

```bash
df -h
findmnt
lsblk
xfs_info /sysroot 2>/dev/null || true
du -xh /var/lib/containers 2>/dev/null | sort -h | tail -20
du -xh /var/log 2>/dev/null | sort -h | tail -20
```

### 6.4 Check MachineConfigDaemon logs

From outside the node:

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide | awk -v n="$NODE" '$0 ~ n && $1 ~ /machine-config-daemon/ {print $1}')
echo $MCD_POD
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=300
```

Inside the node:

```bash
journalctl -u rpm-ostreed -b --no-pager | tail -100
journalctl -u zincati -b --no-pager | tail -100 2>/dev/null || true
journalctl -u machine-config-daemon -b --no-pager | tail -100 2>/dev/null || true
```

Check annotations:

```bash
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 6.5 Check node networking

From node debug shell:

```bash
ip addr
ip route
nmcli con show
nmcli dev status
resolvectl status 2>/dev/null || cat /etc/resolv.conf
```

Check API connectivity:

```bash
API_HOST=$(oc whoami --show-server | sed -E 's#https://([^:/]+).*#\1#')
echo $API_HOST
getent hosts $API_HOST
curl -k https://$API_HOST:6443/readyz?verbose
```

Check DNS and default route:

```bash
getent hosts kubernetes.default.svc
getent hosts image-registry.openshift-image-registry.svc 2>/dev/null || true
ping -c 3 <default-gateway>
```

### 6.6 Check OVN/SDN node components

```bash
oc get pods -n openshift-ovn-kubernetes -o wide | grep $NODE
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --tail=100 --prefix=true | grep -i $NODE -C 2
```

On the node:

```bash
ovs-vsctl show 2>/dev/null || true
ip link | egrep 'br-ex|genev|ovn|ovs|vxlan'
```

### 6.7 Recover common live issues

#### Case A: kubelet stopped

```bash
systemctl status kubelet --no-pager
systemctl restart kubelet
journalctl -u kubelet -f
```

Then verify:

```bash
oc get node $NODE
```

#### Case B: CRI-O stopped or hung

```bash
systemctl status crio --no-pager
systemctl restart crio
journalctl -u crio -f
```

If CRI-O repeatedly fails, inspect storage, cgroups, SELinux denials, and invalid runtime config.

#### Case C: disk full

Check:

```bash
df -h
crictl images
crictl ps -a
```

Prefer safe cleanup:

```bash
crictl rmi --prune
journalctl --vacuum-time=7d
```

Do not randomly delete under `/var/lib/kubelet` or `/var/lib/containers` unless you understand the consequences. Deleting active container storage can corrupt runtime state.

#### Case D: certificate or time issue

Check time:

```bash
timedatectl
chronyc tracking 2>/dev/null || true
```

Check kubelet cert dates:

```bash
openssl x509 -in /var/lib/kubelet/pki/kubelet-client-current.pem -noout -dates 2>/dev/null || true
```

Check pending CSRs:

```bash
oc get csr
```

Approve only valid node CSRs.

#### Case E: MCD degraded because of configuration drift

Inspect the degraded reason:

```bash
oc describe node $NODE | egrep -i 'machineconfiguration|degraded|reason|currentConfig|desiredConfig'
oc describe mcp worker
```

If somebody manually changed a file managed by MachineConfig, either:

1. revert the manual change to match the rendered config, or
2. update the MachineConfig properly so desired state matches the intended file.

Do not patch annotations to fake success unless directed by Red Hat support or in a controlled lab. That hides the problem and can break upgrades.

## 7. Graceful maintenance recovery: node reachable but unhealthy

If the node is reachable and you want to reboot it safely:

```bash
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --timeout=10m
```

If PDBs block the drain, analyze before bypassing:

```bash
oc get pdb -A
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
```

Only when business impact is understood:

```bash
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --force --disable-eviction
```

Reboot:

```bash
oc debug node/$NODE -- chroot /host systemctl reboot
```

Wait and verify:

```bash
watch 'oc get node '$NODE'; echo; oc get mcp'
```

After it returns healthy:

```bash
oc adm uncordon $NODE
oc get node $NODE
oc get mcp
```

## 8. Replacement path for Machine API / cloud / IPI worker

Use this when the node is unrecoverable or replacement is faster/safer.

### 8.1 Confirm Machine ownership

```bash
oc get machines -n openshift-machine-api -o wide
```

Example mapping:

```text
NAME                                      PHASE    NODE
cluster-worker-us-east-1a-x7abc           Running  ip-10-0-1-10.ec2.internal
```

Set variables:

```bash
NODE=<failed-worker-node>
MACHINE=$(oc get machines -n openshift-machine-api -o json | jq -r --arg NODE "$NODE" '.items[] | select(.status.nodeRef.name==$NODE) | .metadata.name')
echo $MACHINE
```

### 8.2 Check MachineSet replica safety

```bash
oc get machinesets -n openshift-machine-api
oc describe machine $MACHINE -n openshift-machine-api | egrep -i 'Owner|MachineSet|ProviderID|Phase|Failure|Error|Node'
```

If the worker belongs to a MachineSet, deleting the Machine should cause a replacement to be created automatically.

### 8.3 Optional: cordon first

If the node is still partially alive:

```bash
oc adm cordon $NODE
```

### 8.4 Delete the failed Machine

```bash
oc delete machine $MACHINE -n openshift-machine-api
```

Watch progress:

```bash
watch 'oc get machines -n openshift-machine-api -o wide; echo; oc get nodes -o wide; echo; oc get mcp'
```

### 8.5 If deletion is stuck because drain is blocked

Inspect:

```bash
oc describe machine $MACHINE -n openshift-machine-api
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
oc get pdb -A
```

The machine controller normally tries to drain the backed node. If drain cannot proceed because of PDB or other conditions, deletion can stall.

You can skip node draining by annotating the specific Machine:

```bash
oc annotate machine $MACHINE -n openshift-machine-api machine.openshift.io/exclude-node-draining="" --overwrite
```

Use this only after you understand the workload/data risk.

### 8.6 Validate replacement node

```bash
oc get machines -n openshift-machine-api -o wide
oc get nodes -o wide
oc get csr
oc get mcp
```

If pending CSRs exist and are valid:

```bash
oc describe csr <csr-name>
oc adm certificate approve <csr-name>
```

Then check the new worker:

```bash
NEWNODE=<new-worker-node>
oc describe node $NEWNODE
oc get pods -A -o wide --field-selector spec.nodeName=$NEWNODE
oc debug node/$NEWNODE -- chroot /host rpm-ostree status
```

### 8.7 Confirm the MCP converged

```bash
oc get mcp worker
oc describe mcp worker
```

Expected:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
READYMACHINECOUNT equals MACHINECOUNT
```

## 9. Replacement path for bare-metal or UPI worker without MachineSet

Use this when the cluster does not use compute MachineSets or Machine API does not own the node.

### 9.1 Confirm no Machine API ownership

```bash
oc get machines -n openshift-machine-api -o wide 2>/dev/null || true
oc get machinesets -n openshift-machine-api 2>/dev/null || true
```

If no machine maps to the node, this is likely manual/UPI style node lifecycle.

### 9.2 Cordon and drain if reachable

```bash
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --timeout=10m
```

If the node is unreachable, drain might fail. Do not blindly force deletion if the host might still be writing to shared storage.

### 9.3 Fence or power off failed host

For physical/virtual infrastructure, confirm one of these before forced deletion:

- BMC/IPMI/iDRAC/iLO says host is powered off
- Hypervisor confirms VM is powered off
- Cloud console confirms instance stopped/terminated
- Network/power team confirms isolation
- Storage team confirms no active I/O

This is especially important for:

- RWX/RWO storage with stale attachments
- local PV workloads
- database workloads
- OpenShift Virtualization VMs
- ODF/Ceph nodes

### 9.4 Delete the Node object

After fencing/power-off:

```bash
oc delete node $NODE
```

### 9.5 Rebuild or reinstall worker

For UPI/bare metal, install a new RHCOS worker using the approved method for your environment. Depending on cluster version and installation design, this might involve:

- booting a generated node ISO
- using PXE/ignition
- Assisted Installer workflows
- platform-specific provisioning
- reusing install-time worker ignition where appropriate

### 9.6 Approve node CSRs

```bash
watch oc get csr
```

Approve valid client and serving CSRs as required:

```bash
oc describe csr <csr-name>
oc adm certificate approve <csr-name>
```

### 9.7 Verify new worker

```bash
oc get nodes -o wide
oc get mcp
oc describe node <new-node>
oc get pods -A -o wide --field-selector spec.nodeName=<new-node>
```

## 10. MachineConfig-related worker failure

MachineConfig failures are common in advanced administration because changes affect the operating system layer. Examples:

- bad kubelet config
- invalid CRI-O config
- wrong systemd unit
- bad kernel argument
- incorrect chrony config
- registry trust/config error
- NetworkManager file mistake
- custom CA error
- SSH key or file permission issue

### 10.1 Detect whether MCO/MCP is involved

```bash
oc get mcp
oc describe mcp worker
oc get mc
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Look for:

```text
Working
Degraded
failed to drain
failed to update OS
content mismatch
unexpected on-disk state
```

### 10.2 Find recent MachineConfig changes

```bash
oc get mc --sort-by=.metadata.creationTimestamp
oc get kubeletconfig
oc get containerruntimeconfig
oc get imagecontentsourcepolicy 2>/dev/null || true
oc get imagedigestmirrorset 2>/dev/null || true
oc get imagetagmirrorset 2>/dev/null || true
```

Compare rendered configs:

```bash
CURRENT=$(oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}')
DESIRED=$(oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}')
echo current=$CURRENT desired=$DESIRED
oc get mc $CURRENT -o yaml > current-$NODE.yaml
oc get mc $DESIRED -o yaml > desired-$NODE.yaml
diff -u current-$NODE.yaml desired-$NODE.yaml | less
```

### 10.3 If MachineConfig rollout is breaking more nodes

Pause the pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Find the bad MachineConfig:

```bash
oc describe mcp worker
oc get mc --sort-by=.metadata.creationTimestamp
```

Fix or remove the bad config:

```bash
oc delete mc <bad-machineconfig-name>
```

or apply corrected YAML:

```bash
oc apply -f corrected-machineconfig.yaml
```

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Watch:

```bash
watch oc get mcp
```

### 10.4 If one node is degraded due to drift

Do not edit the node annotation as the first step. Instead:

1. read the MCD reason,
2. inspect the managed file/service,
3. compare with desired rendered config,
4. revert manual changes or update the MachineConfig properly,
5. restart the relevant service only when safe,
6. let MCD reconcile.

Example:

```bash
oc describe node $NODE | egrep -i 'machineconfiguration|degraded|reason|content|drift'
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=500
```

## 11. Failed node during cluster upgrade

A worker can fail during an OpenShift upgrade due to:

- OS pivot failure
- image pull failure
- bad registry/mirror/trust config
- node drain blocked by PDB
- reboot failure
- disk pressure
- MCD degraded

Check:

```bash
oc get clusterversion
oc describe clusterversion
oc get co
oc get mcp
oc describe mcp worker
```

Check MCD metrics/logs:

```bash
oc get pods -n openshift-machine-config-operator -o wide
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=500
```

Common recovery:

| Symptom | Action |
|---|---|
| Drain blocked by PDB | identify PDB and app owner; temporarily scale app or adjust PDB; avoid `--disable-eviction` unless approved |
| Pivot/image pull error | check registry pull secret, mirror config, proxy, CA trust, DNS |
| Reboot failed | debug host, check systemd/logind, BMC/hypervisor, MCD logs |
| Disk full | clean safely; expand disk if needed |
| One node unrecoverable | replace Machine and let new node join at target config |
| Bad MachineConfig | pause MCP, remove/fix config, unpause |

## 12. Storage considerations during failed worker recovery

Storage is where node recovery becomes dangerous.

### 12.1 Check pods with PVCs on failed node

```bash
oc get pods -A -o json | jq -r --arg NODE "$NODE" '
.items[]
| select(.spec.nodeName==$NODE)
| select(.spec.volumes[]? | has("persistentVolumeClaim"))
| [.metadata.namespace, .metadata.name, (.spec.volumes[]? | select(.persistentVolumeClaim) | .persistentVolumeClaim.claimName)]
| @tsv'
```

### 12.2 Check volume attachments

```bash
oc get volumeattachments
oc get volumeattachments -o json | jq -r --arg NODE "$NODE" '.items[] | select(.spec.nodeName==$NODE) | [.metadata.name,.spec.attacher,.spec.source.persistentVolumeName,.status.attached] | @tsv'
```

### 12.3 RWO volumes

ReadWriteOnce volumes can block pod restart elsewhere until detached. If the failed node is truly down, CSI should eventually detach. If the node is partitioned but still alive, forced detach can corrupt data.

### 12.4 Local PVs

Local PVs are tied to the node. Replacing the worker does not magically move data. Recovery might require:

- restoring from backup,
- rebuilding the same host and disk path,
- manual PV cleanup,
- application-level replication recovery.

### 12.5 ODF/Ceph nodes

If the worker is also an ODF storage node, do not treat it as a generic stateless worker. Check Ceph health first:

```bash
oc get pods -n openshift-storage -o wide | grep $NODE
oc rsh -n openshift-storage deploy/rook-ceph-tools ceph status
oc rsh -n openshift-storage deploy/rook-ceph-tools ceph osd tree
```

Coordinate with storage runbooks before deleting nodes or disks.

## 14. Disk-pressure and filesystem recovery

### 14.1 Identify pressure

```bash

```

Inside node:


### 14.2 Safe cleanup options

```bash

```

Rotate/remove only known safe logs. Avoid deleting random pod directories under `/var/lib/kubelet/pods` unless the pod is gone and you understand kubelet state.

### 14.3 Long-term fix

- Increase worker disk size.
- Tune image garbage collection with supported kubelet configuration.
- Fix runaway logging.
- Configure app log rotation.
- Move stateful data to PVCs, not container writable layer.
- Avoid overpacking nodes.

## 16. Automated remediation options

### 16.1 MachineHealthCheck

`MachineHealthCheck` can automatically remediate unhealthy machines that belong to a MachineSet. Typical behavior is:

- monitor conditions such as `Ready=False` or `Ready=Unknown`,
- wait a configured timeout,
- delete unhealthy machine,
- allow replacement to be created.

Example worker MHC:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineHealthCheck
metadata:
  name: worker-healthcheck
  namespace: openshift-machine-api
spec:
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-machine-role: worker
      machine.openshift.io/cluster-api-machine-type: worker
  unhealthyConditions:
  - type: Ready
    status: Unknown
    timeout: 300s
  - type: Ready
    status: "False"
    timeout: 300s
  maxUnhealthy: 40%
  nodeStartupTimeout: 10m
```

Use conservative values. Too short a timeout can cause remediation loops during slow boot, MachineConfig rollout, or high-latency networks.

### 16.2 Self Node Remediation

Self Node Remediation can reboot unhealthy nodes using watchdog/softdog strategies and can reduce downtime for some stateful/RWO workloads. It can be triggered by MachineHealthCheck or NodeHealthCheck.

This is useful for transient failures, but it does not replace root-cause analysis. Rebooting a node repeatedly can hide kernel, disk, NIC, firmware, CRI-O, or workload pressure problems.

### 16.3 NodeHealthCheck

`NodeHealthCheck` can identify unhealthy nodes and invoke a remediation provider. It is useful in environments where Machine API ownership is not enough or where node-level remediation is required.

## 18. Troubleshooting matrix

| Symptom | Most likely causes | Checks | Recovery |
|---|---|---|---|
| Node `Ready=Unknown` | network partition, kubelet down, host down | `oc describe node`, platform console, API connectivity | recover host, reboot, or replace/fence |
| Node `Ready=False` | kubelet reports unhealthy | kubelet logs, CRI-O logs, node conditions | fix runtime/kubelet/disk/network |
| MCP `Degraded=True` | MCD failed, drift, bad MC | `oc describe mcp`, MCD logs, node annotations | fix drift or bad MachineConfig |
| Machine `Failed` | provider instance error | `oc describe machine` | delete Machine and let MachineSet replace |
| Machine stuck `Deleting` | drain blocked, finalizer/lifecycle hook | `oc describe machine`, PDBs, pods | resolve drain/PDB; annotate skip drain only if safe |
| Pods stuck terminating on failed node | node unreachable, volume detach delay | pods, volumeattachments, CSI logs | wait/fence; avoid unsafe force detach |
| New worker not joining | CSR pending, bootstrap failure, network/DNS | `oc get csr`, boot logs, API reachability | approve valid CSR, fix bootstrap network |
| Runtime down | CRI-O config/storage | `journalctl -u crio`, `df -h` | restart/fix config/clean disk |
| Kubelet certificate error | expired cert, CSR pending, clock skew | kubelet logs, `timedatectl`, `oc get csr` | fix time, approve valid CSR |
| Node disk pressure | image/log growth | `df -h`, `du`, kubelet eviction logs | prune images, vacuum logs, increase disk |
| Repeated node failure after reboot | bad MachineConfig, hardware, kernel, workload pressure | MCD logs, dmesg, hardware logs | rollback config or replace hardware |

## 20. Example full scenario

### Situation

One worker is `NotReady` after a MachineConfig update that changed CRI-O registry configuration.

```bash
oc get nodes
```

Output:

```text
worker-0   Ready      worker   90d
worker-1   NotReady   worker   90d
worker-2   Ready      worker   90d
```

MCP:

```bash
oc get mcp
```

Output:

```text
worker   False   True   True
```

### Investigation

```bash
NODE=worker-1
oc describe node $NODE | egrep -i 'machineconfiguration|reason|degraded|currentConfig|desiredConfig'
```

MCD logs:

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide | awk -v n="$NODE" '$0 ~ n && $1 ~ /machine-config-daemon/ {print $1}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=500
```

CRI-O logs:

```bash
oc debug node/$NODE -- chroot /host journalctl -u crio -b --no-pager | tail -200
```

### Finding

The new registry configuration contains a syntax or trust issue, CRI-O fails, kubelet reports runtime not ready, and MCD cannot complete.

### Recovery

Pause worker MCP to stop rollout:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Fix MachineConfig or image registry config object.

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Restart CRI-O if the node is reachable and config is corrected:

```bash
oc debug node/$NODE -- chroot /host systemctl restart crio
oc debug node/$NODE -- chroot /host systemctl restart kubelet
```

If the node remains broken and Machine API owns it:

```bash
MACHINE=$(oc get machines -n openshift-machine-api -o json | jq -r --arg NODE "$NODE" '.items[] | select(.status.nodeRef.name==$NODE) | .metadata.name')
oc delete machine $MACHINE -n openshift-machine-api
```

Watch replacement:

```bash
watch 'oc get machines -n openshift-machine-api -o wide; echo; oc get nodes; echo; oc get mcp'
```

### Final validation

```bash
oc get nodes
oc get mcp
oc get co
oc get pods -A | egrep -v 'Running|Completed'
```

## 21. Common mistakes in real environments

### Mistake 1: Deleting `Node` on cloud/Machine API cluster

This can leave the Machine and infrastructure instance behind. Use Machine/MachineSet workflow.

### Mistake 2: Force deleting an unreachable bare-metal node without fencing

If the host is still alive and writing to shared storage, you can corrupt application data.

### Mistake 3: Bypassing PDBs without business approval

`--disable-eviction` can cause application outage. Use only when risk is accepted.

### Mistake 4: Fixing RHCOS manually

Manual edits might work temporarily but cause MCO drift and future upgrade failures.

### Mistake 5: Ignoring MachineConfigPool after node recovery

The node might be `Ready`, but MCP can remain degraded. Always verify MCP.

### Mistake 6: Approving all CSRs blindly

CSR approval allows nodes to join or renew serving credentials. Approve only after validating identity.

### Mistake 7: Treating all workers as stateless

Some workers host stateful pods, ODF, local PVs, infra routers, logging, monitoring, or virtualization workloads.

## 23. Interview/exam-style explanation

If asked to explain worker node recovery in an advanced OpenShift administration interview, answer like this:

> I first determine whether the problem is a Kubernetes node health issue, a host-level issue, a Machine API issue, or a MachineConfig/MCO issue. I check cluster operators, nodes, MachineConfigPools, machines, and pods running on the affected node. If the node is reachable, I use `oc debug node/<node>` and `chroot /host` to inspect kubelet, CRI-O, NetworkManager, disk, and MCD logs. If it is a Machine API managed worker and unrecoverable, I delete the corresponding `Machine`, not just the `Node`, so the MachineSet can create a replacement. If it is bare metal or UPI without MachineSets, I cordon/drain when possible, fence or power off the host if unreachable, then delete the Node and rebuild/rejoin it. During replacement I verify CSRs, MCP convergence, node labels/taints, workload rescheduling, and storage attachments. If the failure is caused by a MachineConfig rollout, I may pause the MCP, fix or remove the bad config, and unpause only after validating the correction.
