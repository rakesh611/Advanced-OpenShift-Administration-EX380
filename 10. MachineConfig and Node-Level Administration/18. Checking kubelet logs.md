# Checking kubelet logs in OpenShift

**Area:** MachineConfig and Node-Level Administration  
**Audience:** Advanced OpenShift Administration / Senior Linux-OpenShift Engineers  
**Experience level:** Written from a 10-year production operations point of view  
**Platform focus:** OpenShift Container Platform 4.x, RHCOS nodes, Machine Config Operator managed clusters

---

## 1. Why kubelet logs matter

In OpenShift, the **kubelet** is the node-local agent that keeps a node connected to the cluster. Every worker and control plane node runs kubelet as a host-level systemd service. It is responsible for:

- registering the node with the Kubernetes API server;
- reporting node health, capacity, allocatable resources, pressure conditions, and pod status;
- starting, stopping, and reconciling pods through CRI-O;
- mounting volumes and handling projected secrets/config maps;
- running liveness, readiness, and startup probes;
- enforcing pod resource limits and cgroup behavior;
- communicating with the container runtime, CNI, CSI, and node OS services;
- reacting to MachineConfig and KubeletConfig changes after they are rendered and applied to the host.

When a node becomes `NotReady`, pods remain `Pending`, containers repeatedly restart, probes fail, volume mounts hang, certificates expire, CRI-O communication breaks, or a MachineConfig update causes a reboot loop, kubelet logs are one of the first places a senior administrator checks.

A beginner usually checks only:

```bash
oc get pods
oc describe pod <pod>
oc logs <pod>
```

A production OpenShift administrator also checks:

```bash
oc adm node-logs <node> -u kubelet
oc debug node/<node>
chroot /host
journalctl -u kubelet.service
systemctl status kubelet
systemctl cat kubelet
```

The difference is important: **pod logs show application behavior; kubelet logs show node orchestration behavior**.

## 2. Kubelet in the OpenShift node stack

A simplified OpenShift node stack looks like this:

```text
Kubernetes API / OpenShift API
        |
        | node status, pod specs, secrets, configmaps, events
        v
+-----------------------------+
| kubelet.service             |
| host-level node agent       |
+-----------------------------+
        |
        | CRI calls
        v
+-----------------------------+
| crio.service                |
| container runtime           |
+-----------------------------+
        |
        | containers, images, namespaces, cgroups
        v
+-----------------------------+
| RHCOS / systemd / kernel    |
+-----------------------------+
        |
        | networking and storage plugins
        v
+-----------------------------+
| OVN-Kubernetes / CSI / CNI  |
+-----------------------------+
```

Kubelet is not normally a pod. It is a systemd service on the node. That is why kubelet logs are usually in **journald**, not in `oc logs` output.

On RHCOS and systemd-based Kubernetes nodes, kubelet and the container runtime write to the system journal. Kubernetes system components that run as containers write logs under `/var/log` paths. This distinction matters when choosing between `journalctl`, `oc adm node-logs -u kubelet`, and `/var/log/containers/*`.

## 3. Supported ways to check kubelet logs

There are four practical methods.

### 3.1 From the API using `oc adm node-logs`

This is the cleanest first option when the API server is reachable and your user has enough privileges.

```bash
oc adm node-logs <node-name> -u kubelet
```

Examples:

```bash
# Kubelet logs from one node
oc adm node-logs worker-0.example.com -u kubelet

# Kubelet logs from all worker nodes
oc adm node-logs --role worker -u kubelet

# Kubelet logs from all control plane nodes
oc adm node-logs --role master -u kubelet

# Show only recent logs
oc adm node-logs worker-0.example.com -u kubelet --since=30m

# Show only the last 300 lines
oc adm node-logs worker-0.example.com -u kubelet --tail=300

# Grep for a pattern in node service logs
oc adm node-logs worker-0.example.com -u kubelet -g 'failed|error|certificate|runtime|eviction'

# Output in JSON-like supported log format where available
oc adm node-logs worker-0.example.com -u kubelet -o json
```

Use this when:

- API is reachable;
- the node object exists;
- kubelet log service is accessible through the node log API;
- you do not want to SSH into the node;
- you want a quick cluster-wide comparison.

Senior habit:

```bash
for n in $(oc get nodes --no-headers | awk '{print $1}'); do
  echo "===== $n ====="
  oc adm node-logs "$n" -u kubelet --tail=80 | egrep -i 'error|fail|panic|certificate|runtime|evict|pressure|cni|volume|pleg' || true
done
```

This quickly tells you whether the issue is isolated to one node or widespread.

---

### 3.2 From a node debug session using `oc debug node/<node>`

This is the most useful method when you need to inspect the node OS, systemd status, files under `/etc`, CRI-O status, disk pressure, network state, or MachineConfig-applied content.

```bash
oc debug node/<node-name>
chroot /host
journalctl -u kubelet.service
```

Example:

```bash
oc debug node/worker-0.example.com
chroot /host
systemctl status kubelet --no-pager
journalctl -u kubelet.service -b --no-pager | tail -200
journalctl -u kubelet.service -b -f
```

Use this when:

- `oc adm node-logs` is not enough;
- you need live follow mode;
- you need to inspect host files;
- you need to compare kubelet logs with CRI-O, NetworkManager, or MCD logs;
- you suspect MachineConfig, kernel args, kubelet config, certificates, disk, runtime, or network issues.

Important commands inside `chroot /host`:

```bash
# Kubelet service state
systemctl status kubelet --no-pager
systemctl is-active kubelet
systemctl is-enabled kubelet

# Full systemd definition including drop-ins
systemctl cat kubelet

# Current boot kubelet logs
journalctl -b -u kubelet.service --no-pager

# Previous boot kubelet logs
journalctl -b -1 -u kubelet.service --no-pager

# Follow live kubelet logs
journalctl -b -f -u kubelet.service

# Time-filtered logs
journalctl -u kubelet.service --since '1 hour ago' --no-pager
journalctl -u kubelet.service --since '2026-07-03 10:00:00' --until '2026-07-03 10:30:00' --no-pager

# Show errors from current boot
journalctl -b -u kubelet.service -p warning..alert --no-pager
```

---

### 3.3 By SSH to the node

SSH is useful when:

- the API server is not reachable;
- `oc debug node/<node>` cannot be scheduled;
- the node is in a bad state but SSH still works;
- the installation or bootstrap phase failed;
- you are working in a break-glass support scenario.

Example:

```bash
ssh core@<node-name>
sudo journalctl -b -u kubelet.service --no-pager | tail -200
sudo journalctl -b -f -u kubelet.service
```

On OpenShift 4.x RHCOS, do not use SSH as a normal configuration management method. For persistent node changes, use MachineConfig, KubeletConfig, ContainerRuntimeConfig, PerformanceProfile, NMState, or the relevant Operator-managed API. SSH is for debugging and emergency inspection, not for snowflake node management.

---

### 3.4 Through must-gather and support data

When opening a Red Hat support case or creating a full RCA bundle, collect must-gather data:

```bash
oc adm must-gather
```

For targeted node issues, also collect kubelet logs separately because must-gather output might not always contain the exact journal depth, boot history, or live failure window you need.

Recommended bundle pattern:

```bash
mkdir -p node-debug-$(date +%F-%H%M)
cd node-debug-$(date +%F-%H%M)

oc get nodes -o wide > nodes.txt
oc get mcp > mcp.txt
oc get co > clusteroperators.txt
oc adm node-logs --role worker -u kubelet --since=2h > worker-kubelet-2h.log
oc adm node-logs --role master -u kubelet --since=2h > master-kubelet-2h.log
oc adm must-gather --dest-dir=must-gather

tar czf node-debug-bundle.tar.gz .
```

## 4. Prerequisites and permissions

To check kubelet logs properly, you normally need:

```bash
oc whoami
oc auth can-i get nodes
oc auth can-i get nodes/log
oc adm policy who-can --all-namespaces get nodes/log
```

Typical production role requirement:

- `cluster-admin`; or
- a tightly controlled node-administration role with access to node logs.

Kubelet logs may contain sensitive information such as image names, node paths, volume names, service account references, pod names, namespace names, certificate errors, registry endpoints, and workload metadata. Do not paste full logs into tickets or chats without checking for secrets and environment-specific information.

## 5. First-response workflow: when a node is NotReady

When a node is `NotReady`, do not jump directly to restarting kubelet. First establish the timeline.

### Step 1: Identify the affected node

```bash
oc get nodes
oc get nodes -o wide
oc describe node <node-name>
```

Look for:

```text
Ready=False
Ready=Unknown
MemoryPressure=True
DiskPressure=True
PIDPressure=True
NetworkUnavailable=True
Kubelet stopped posting node status
container runtime is down
PLEG is not healthy
```

### Step 2: Check node events

```bash
oc describe node <node-name> | sed -n '/Events:/,$p'
```

Common useful event messages:

```text
NodeNotReady
NodeReady
InvalidDiskCapacity
ContainerGCFailed
ImageGCFailed
EvictionThresholdMet
NodeHasDiskPressure
NodeHasMemoryPressure
KubeletHasSufficientMemory
Starting kubelet
```

### Step 3: Check kubelet logs

```bash
oc adm node-logs <node-name> -u kubelet --since=1h
```

Focus on the period before and after the node transitioned state.

### Step 4: Compare kubelet with CRI-O

```bash
oc adm node-logs <node-name> -u crio --since=1h
```

If kubelet says `container runtime is down`, CRI-O logs often show the root cause.

### Step 5: Check MCD if this happened after MachineConfig change

```bash
oc get mcp
oc describe mcp worker
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -c machine-config-daemon --since=2h
```

If only one node is broken:

```bash
oc get pod -n openshift-machine-config-operator -o wide | grep <node-name>
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon --since=2h
```

## 6. What to search for in kubelet logs

A senior administrator does not read thousands of lines randomly. Use patterns.

### 6.1 Runtime and CRI-O issues

Search:

```bash
oc adm node-logs <node> -u kubelet --since=1h -g 'runtime|cri|container runtime|PLEG|crio|RunPodSandbox'
```

Typical messages:

```text
container runtime is down
PLEG is not healthy
failed to run Kubelet
failed to create pod sandbox
RunPodSandbox from runtime service failed
rpc error: code = Unknown desc = ...
```

Meaning:

- kubelet cannot communicate with CRI-O;
- CRI-O is hung or restarting;
- image storage is broken;
- CNI setup failed during sandbox creation;
- pod sandbox creation failed before containers started.

Next checks:

```bash
oc adm node-logs <node> -u crio --since=1h
oc debug node/<node>
chroot /host
systemctl status crio --no-pager
journalctl -b -u crio.service --no-pager | tail -200
crictl ps -a
crictl images
```

---

### 6.2 CNI and networking issues

Search:

```bash
oc adm node-logs <node> -u kubelet --since=1h -g 'CNI|network|sandbox|pod network|Multus|ovn|interface'
```

Typical messages:

```text
failed to setup network for sandbox
networkPlugin cni failed to set up pod
failed to destroy network for sandbox
no IP addresses available
Multus: error loading k8s delegates
```

Meaning:

- OVN-Kubernetes or Multus issue;
- CNI config file missing or corrupt;
- node network daemon issue;
- IPAM exhaustion;
- CNI plugin binary missing;
- stale sandbox/network namespace.

Next checks:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide | grep <node>
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --since=1h
oc adm node-logs <node> -u ovs-vswitchd --since=1h
oc adm node-logs <node> -u NetworkManager --since=1h
```

---

### 6.3 Volume mount and CSI issues

Search:

```bash
oc adm node-logs <node> -u kubelet --since=1h -g 'MountVolume|UnmountVolume|AttachVolume|CSI|volume|secret|configmap'
```

Typical messages:

```text
MountVolume.SetUp failed
Unable to attach or mount volumes
timed out waiting for the condition
failed to sync configmap cache
failed to sync secret cache
orphaned pod found
```

Meaning:

- CSI node plugin issue;
- storage backend issue;
- secret/config map API cache sync issue;
- kubelet cannot mount projected volume;
- PVC/PV binding may be OK, but node-side mount failed.

Next checks:

```bash
oc describe pod <pod> -n <namespace>
oc get pvc -n <namespace>
oc get pv
oc get pods -n openshift-cluster-csi-drivers -o wide
oc get pods -A -o wide | grep csi
```

For a specific CSI driver, check its node pod on the same node:

```bash
oc get pods -A -o wide | grep <node> | grep -i csi
oc logs -n <csi-namespace> <csi-node-pod> --since=1h
```

---

### 6.4 Image pull and registry issues

Search:

```bash
oc adm node-logs <node> -u kubelet --since=1h -g 'image|pull|registry|x509|unauthorized|manifest|Back-off pulling'
```

Typical messages:

```text
Failed to pull image
Back-off pulling image
x509: certificate signed by unknown authority
unauthorized: authentication required
manifest unknown
connection refused
context deadline exceeded
```

Meaning:

- registry authentication problem;
- pull secret problem;
- custom CA not trusted by node/runtime;
- disconnected registry mirror issue;
- DNS/firewall/proxy issue;
- wrong image name/tag.

Next checks:

```bash
oc describe pod <pod> -n <namespace>
oc get secret -n <namespace>
oc get image.config.openshift.io/cluster -o yaml
oc adm node-logs <node> -u crio --since=1h -g 'image|pull|registry|x509|auth'
```

If a custom registry CA was added through MachineConfig or image config, verify MCO rollout:

```bash
oc get mcp
oc describe mcp worker
```

---

### 6.5 Certificate and API connectivity issues

Search:

```bash
oc adm node-logs <node> -u kubelet --since=2h -g 'certificate|x509|Unauthorized|forbidden|tls|apiserver|node status'
```

Typical messages:

```text
Unable to register node with API server
failed to ensure node lease exists
Error updating node status
x509: certificate has expired or is not yet valid
Unauthorized
certificate signed by unknown authority
```

Meaning:

- kubelet client certificate issue;
- time/chrony issue causing certificate validity failure;
- API server reachability issue;
- kubelet bootstrap/rotation problem;
- node identity mismatch.

Next checks:

```bash
oc get csr
oc get node <node> -o yaml | grep -i taint -A5
oc adm node-logs <node> -u chronyd --since=2h
oc debug node/<node>
chroot /host
chronyc tracking
timedatectl
```

In production, do not blindly approve all CSRs. Inspect requester, node name, and certificate purpose.

---

### 6.6 Eviction, memory pressure, disk pressure, and PID pressure

Search:

```bash
oc adm node-logs <node> -u kubelet --since=2h -g 'eviction|pressure|DiskPressure|MemoryPressure|PIDPressure|threshold|image gc|container gc'
```

Typical messages:

```text
eviction manager: attempting to reclaim
thresholds have been met
NodeHasDiskPressure
image garbage collection failed
container garbage collection failed
invalid capacity 0 on image filesystem
```

Meaning:

- node filesystem pressure;
- image filesystem pressure;
- too many containers or images;
- PID exhaustion;
- workload requests/limits mismatch;
- `/var`, `/var/lib/containers`, or root filesystem issue.

Next checks:

```bash
oc debug node/<node>
chroot /host
df -h
findmnt
journalctl -b -u kubelet.service --no-pager | egrep -i 'evict|pressure|gc|disk|memory|pid'
crictl images
crictl ps -a
```

Be careful with manual deletion under `/var/lib/containers`. Prefer supported cleanup paths and understand CRI-O storage before deleting anything.

---

### 6.7 Probe failures

Application teams often report, “OpenShift restarted my pod.” Kubelet logs tell you whether a probe failed.

Search:

```bash
oc adm node-logs <node> -u kubelet --since=1h -g 'probe|liveness|readiness|startup|failed container'
```

Typical messages:

```text
Liveness probe failed
Readiness probe failed
Startup probe failed
Killing container with id ... failed liveness probe
```

Meaning:

- application endpoint is slow or failing;
- probe path/port/scheme is wrong;
- app startup delay is longer than configured;
- TLS probe mismatch;
- CPU throttling or node pressure causing response delays.

Next checks:

```bash
oc describe pod <pod> -n <namespace>
oc logs <pod> -n <namespace> --previous
oc get pod <pod> -n <namespace> -o yaml | yq '.spec.containers[].livenessProbe'
oc get events -n <namespace> --sort-by=.lastTimestamp
```

---

### 6.8 Static pod and control plane issues

On control plane nodes, kubelet manages static pods for key control plane components. Kubelet logs can reveal failures for:

- kube-apiserver;
- kube-controller-manager;
- kube-scheduler;
- etcd;
- static pod manifest handling;
- mirror pod creation.

Search:

```bash
oc adm node-logs --role master -u kubelet --since=1h -g 'static|mirror|manifest|etcd|kube-apiserver|scheduler|controller'
```

Next checks:

```bash
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-etcd -o wide
oc get co
oc get clusterversion
```

If API is degraded but still responding, collect control plane logs immediately:

```bash
oc adm node-logs --role master -u kubelet --since=2h > master-kubelet.log
oc adm node-logs --role master -u crio --since=2h > master-crio.log
```

## 7. Kubelet logs and MachineConfig troubleshooting

MachineConfig and kubelet logs are strongly connected because MachineConfig changes can modify host files, systemd drop-ins, kernel arguments, registries, CRI-O, and kubelet configuration.

The Machine Config Operator manages node-level configuration. The Machine Config Daemon runs on each node, applies rendered configuration, drains the node when required, and can reboot the node depending on the change.

### 7.1 Common MachineConfig-related kubelet symptoms

After applying a MachineConfig, you might see:

```text
kubelet.service failed to start
failed to load Kubelet config file
unknown flag
invalid kubelet configuration
container runtime endpoint not found
node not found
failed to get node
failed to update node status
```

Possible causes:

- bad systemd drop-in for kubelet;
- invalid `KUBELET_LOG_LEVEL` syntax;
- invalid KubeletConfig field or value;
- wrong file permissions or SELinux context;
- kubelet config file corrupted;
- CRI-O changed but not restarted correctly;
- node rebooted into a broken rendered config;
- custom MachineConfig overwritten a file managed by OpenShift.

### 7.2 Check rendered configuration relationship

```bash
oc get mcp
oc describe mcp worker
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

Useful states:

```text
Done
Working
Degraded
Unreconcilable
```

### 7.3 Check kubelet unit after MachineConfig

```bash
oc debug node/<node>
chroot /host
systemctl cat kubelet
systemctl status kubelet --no-pager
journalctl -b -u kubelet.service --no-pager | tail -200
```

Check for drop-ins such as:

```text
/etc/systemd/system/kubelet.service.d/20-logging.conf
/etc/systemd/system/kubelet.service.d/30-logging.conf
/etc/systemd/system/kubelet.service.d/*.conf
```

A broken drop-in example:

```ini
[Service]
Environment=KUBELET_LOG_LEVEL=8
```

A safer format:

```ini
[Service]
Environment="KUBELET_LOG_LEVEL=8"
```

Also check whether multiple drop-ins override each other. In systemd, later lexical order wins for many settings. A `30-logging.conf` can override `20-logging.conf`.

## 8. Temporarily increasing kubelet log verbosity

Sometimes default kubelet logs are not enough. OpenShift supports changing kubelet log verbosity for deeper debugging.

### 8.1 One-time temporary method

Use this only for short troubleshooting windows.

```bash
oc debug node/<node>
chroot /host
systemctl cat kubelet
cat > /etc/systemd/system/kubelet.service.d/30-logging.conf <<'DROPIN'
[Service]
Environment="KUBELET_LOG_LEVEL=8"
DROPIN
systemctl daemon-reload
systemctl restart kubelet
journalctl -b -f -u kubelet.service
```

After collecting logs, revert it:

```bash
rm -f /etc/systemd/system/kubelet.service.d/30-logging.conf
systemctl daemon-reload
systemctl restart kubelet
```

Production warning:

- Increasing verbosity can generate a lot of logs.
- High verbosity can expose HTTP headers or request contents depending on level.
- Do not leave trace-level kubelet logs enabled permanently.
- Restarting kubelet can temporarily affect node status and pod reconciliation.

### 8.2 Persistent method using MachineConfig

For a persistent log level change, use a MachineConfig. Example for control plane nodes:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-master-kubelet-loglevel
  labels:
    machineconfiguration.openshift.io/role: master
spec:
  config:
    ignition:
      version: 3.2.0
    systemd:
      units:
        - name: kubelet.service
          enabled: true
          dropins:
            - name: 30-logging.conf
              contents: |
                [Service]
                Environment="KUBELET_LOG_LEVEL=4"
```

For worker nodes, change the role and name:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-kubelet-loglevel
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.2.0
    systemd:
      units:
        - name: kubelet.service
          enabled: true
          dropins:
            - name: 30-logging.conf
              contents: |
                [Service]
                Environment="KUBELET_LOG_LEVEL=4"
```

Apply carefully:

```bash
oc apply -f 99-worker-kubelet-loglevel.yaml
oc get mcp worker -w
```

Remove when finished:

```bash
oc delete mc 99-worker-kubelet-loglevel
oc get mcp worker -w
```

Remember: MachineConfig changes may cause node drain and reboot depending on the content. Do not apply persistent debug verbosity to production nodes casually.

## 9. Verbosity levels explained practically

OpenShift documentation describes kubelet verbosity approximately like this:

| Level | Practical use |
|---:|---|
| `0` | Critical information only. Too quiet for most troubleshooting. |
| `1` | Low verbosity. Basic operational view. |
| `2` | Recommended default. Useful steady-state and important changes. |
| `3` | More detail about changes and reconciliation. |
| `4` | Debug level. Good for many real investigations. |
| `5` | Deep debug. Use for short windows. |
| `6` | Shows requested resources and more detailed internals. |
| `7` | May show HTTP request headers. Sensitive. |
| `8` | May show HTTP request contents. Very sensitive and noisy. |

Senior guidance:

- Start with default logs first.
- Use `4` for practical debug.
- Use `6` only when necessary.
- Use `7` or `8` only in a controlled window and sanitize logs before sharing.
- Always revert elevated verbosity.

## 10. Real production troubleshooting scenarios

### Scenario 1: Pod stuck in `ContainerCreating`

Symptoms:

```bash
oc get pod -n app
oc describe pod <pod> -n app
```

Events:

```text
FailedCreatePodSandBox
failed to setup network for sandbox
```

Workflow:

```bash
NODE=$(oc get pod <pod> -n app -o jsonpath='{.spec.nodeName}')
echo $NODE
oc adm node-logs $NODE -u kubelet --since=1h -g 'sandbox|CNI|network|failed'
oc adm node-logs $NODE -u crio --since=1h -g 'sandbox|network|failed'
oc get pods -n openshift-ovn-kubernetes -o wide | grep $NODE
```

Likely root cause:

- CNI or OVN node issue;
- CRI-O unable to create sandbox;
- node networking broken.

---

### Scenario 2: Node `NotReady` after MachineConfig rollout

Symptoms:

```bash
oc get mcp
oc get nodes
```

MCP shows:

```text
UPDATED=False
UPDATING=True
DEGRADED=True
```

Workflow:

```bash
NODE=<bad-node>
oc adm node-logs $NODE -u kubelet --since=2h
oc get node $NODE -o yaml | egrep 'currentConfig|desiredConfig|state|reason' -A2
oc get pods -n openshift-machine-config-operator -o wide | grep $NODE
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --since=2h
```

If API-side logs are unavailable:

```bash
oc debug node/$NODE
chroot /host
systemctl status kubelet --no-pager
journalctl -b -u kubelet.service --no-pager | tail -300
systemctl cat kubelet
```

Likely root cause:

- invalid MachineConfig file content;
- invalid systemd drop-in;
- kubelet config validation failure;
- node stuck between desired and current rendered config.

---

### Scenario 3: ImagePullBackOff because custom CA is missing

Pod event:

```text
x509: certificate signed by unknown authority
```

Workflow:

```bash
NODE=$(oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeName}')
oc adm node-logs $NODE -u kubelet --since=1h -g 'x509|certificate|pull|image'
oc adm node-logs $NODE -u crio --since=1h -g 'x509|certificate|registry|pull'
oc get image.config.openshift.io/cluster -o yaml
oc get mcp
```

Likely root cause:

- registry CA not configured cluster-wide;
- MachineConfig not rolled out;
- disconnected registry trust problem;
- pull secret/auth issue.

---

### Scenario 4: Node disk pressure evicting pods

Node condition:

```text
DiskPressure=True
```

Workflow:

```bash
NODE=<node>
oc adm node-logs $NODE -u kubelet --since=3h -g 'eviction|DiskPressure|image gc|container gc|threshold'
oc debug node/$NODE
chroot /host
df -h
journalctl -b -u kubelet.service --no-pager | egrep -i 'evict|disk|image gc|container gc'
crictl images | head
```

Likely root cause:

- image filesystem full;
- root filesystem full;
- container logs too large;
- workload emptyDir usage;
- image garbage collection unable to free enough space.

### Scenario 5: Kubelet certificate or time issue

Symptoms:

```text
x509: certificate has expired or is not yet valid
Unable to register node with API server
Error updating node status
```

Workflow:

```bash
NODE=<node>
oc adm node-logs $NODE -u kubelet --since=2h -g 'x509|certificate|Unauthorized|node status|lease'
oc get csr
oc adm node-logs $NODE -u chronyd --since=2h
oc debug node/$NODE
chroot /host
timedatectl
chronyc tracking
```

Likely root cause:

- time skew;
- certificate rotation issue;
- node identity problem;
- API connectivity problem;
- CSR pending or denied.

## 12. Reading kubelet logs like a senior engineer

### 12.1 Always correlate timestamp, node, pod, and event

Do not look at kubelet logs in isolation. Build a timeline:

```text
10:00 MachineConfig applied
10:03 node drained
10:05 node rebooted
10:07 kubelet started
10:08 CRI-O failed
10:09 node NotReady
10:10 workloads Pending
```

Commands:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
oc get mcp
oc describe mcp worker
oc describe node <node>
oc adm node-logs <node> -u kubelet --since=2h
oc adm node-logs <node> -u crio --since=2h
```

### 12.2 Separate symptom from cause

Examples:

| Kubelet log symptom | Possible deeper cause |
|---|---|
| `failed to create pod sandbox` | CNI, CRI-O, image storage, runtime, SELinux, network namespace issue |
| `container runtime is down` | CRI-O service failed, socket unavailable, storage corruption, node pressure |
| `MountVolume.SetUp failed` | CSI node plugin, secret/configmap sync, storage backend, permission issue |
| `Liveness probe failed` | Application failure, wrong probe, slow startup, CPU starvation |
| `DiskPressure` | Logs, images, emptyDir, container storage, filesystem issue |
| `x509 certificate` | Time skew, CA trust, kubelet cert rotation, registry cert, API cert |

### 12.3 Do not restart kubelet as a first reaction

Restarting kubelet may temporarily hide symptoms but does not fix root cause. Restart only when you understand why:

```bash
systemctl restart kubelet
```

Acceptable cases:

- temporary elevated verbosity drop-in applied;
- confirmed stale kubelet process after safe remediation;
- instructed by Red Hat support;
- lab/testing environment;
- controlled maintenance window.

Risk:

- node status flaps;
- pod reconciliation pauses;
- static pod management pauses on control plane;
- active troubleshooting evidence may scroll away if not collected.

## 13. Kubelet logs vs other logs

| Need | Best log source |
|---|---|
| Node readiness and pod reconciliation | `kubelet.service` |
| Container runtime failures | `crio.service` |
| MachineConfig apply/reboot/degraded state | Machine Config Daemon pod logs |
| Node network/CNI sandbox failures | kubelet + OVN/Multus logs |
| Image pull low-level details | kubelet + CRI-O logs |
| Static pod failures | kubelet + component namespace logs |
| Disk pressure and eviction | kubelet + node filesystem checks |
| API server communication from node | kubelet + network/time/cert checks |
| App crash | pod logs and previous pod logs |
| Probe failure | kubelet + pod describe + app logs |

## 14. Exam and interview points

For Advanced OpenShift Administration, be ready to answer:

### Question: How do you check kubelet logs without SSH?

```bash
oc adm node-logs <node-name> -u kubelet
oc adm node-logs --role worker -u kubelet
oc adm node-logs --role master -u kubelet
```

### Question: How do you check kubelet logs from inside a node?

```bash
oc debug node/<node-name>
chroot /host
journalctl -b -f -u kubelet.service
```

### Question: Why not use `oc logs kubelet`?

Because kubelet is a host-level systemd service, not a normal pod workload.

### Question: What logs do you check with kubelet for pod sandbox failures?

```bash
oc adm node-logs <node> -u kubelet --since=1h
oc adm node-logs <node> -u crio --since=1h
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --since=1h
```

### Question: What if kubelet logs show `container runtime is down`?

Check CRI-O:

```bash
oc adm node-logs <node> -u crio --since=1h
oc debug node/<node>
chroot /host
systemctl status crio --no-pager
journalctl -b -u crio.service --no-pager
```

### Question: What if a MachineConfig broke kubelet?

Check MCP, node annotations, MCD logs, kubelet systemd unit, and current boot journal:

```bash
oc get mcp
oc describe mcp worker
oc get node <node> -o yaml | egrep 'currentConfig|desiredConfig|state|reason' -A2
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --since=2h
oc debug node/<node>
chroot /host
systemctl cat kubelet
journalctl -b -u kubelet.service --no-pager | tail -300
```

## 15. Common mistakes

### Mistake 1: Checking only pod logs

Wrong approach:

```bash
oc logs <pod>
```

This misses node-side failures such as CNI, CSI, CRI-O, eviction, and kubelet API communication.

Better:

```bash
NODE=$(oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeName}')
oc describe pod <pod> -n <ns>
oc adm node-logs $NODE -u kubelet --since=1h
```

### Mistake 2: Restarting kubelet blindly

Restarting kubelet may hide the real issue. Collect logs first.

### Mistake 3: Forgetting previous boot logs

If a node rebooted, current boot logs may not include the original failure.

```bash
journalctl -b -1 -u kubelet.service --no-pager
```

### Mistake 4: Ignoring CRI-O

Many kubelet errors are actually runtime errors. Always compare kubelet and CRI-O.

### Mistake 5: Leaving debug verbosity enabled

Trace-level kubelet logs are noisy and may contain sensitive details. Revert after investigation.

### Mistake 6: Manually editing RHCOS config permanently

Use MachineConfig or KubeletConfig for persistent configuration. Direct node edits are not a supported steady-state management practice.

## 19. Final expert summary

Checking kubelet logs is a core node-level administration skill in OpenShift. Kubelet sits between the Kubernetes API, CRI-O, CNI, CSI, systemd, and the RHCOS host. Because of that, kubelet logs expose failures that are invisible from application logs alone.

For normal operations, start with:

```bash
oc adm node-logs <node> -u kubelet --since=1h
```

For deep node troubleshooting, use:

```bash
oc debug node/<node>
chroot /host
journalctl -b -f -u kubelet.service
```

For MachineConfig-related incidents, always correlate:

```bash
oc get mcp
oc describe mcp <pool>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
systemctl cat kubelet
journalctl -b -u kubelet.service
```

A 10-year-level OpenShift administrator does not just read kubelet logs. They correlate kubelet logs with node conditions, events, CRI-O, CNI, CSI, MachineConfig, previous boots, and change timelines. That is how you move from symptom-based troubleshooting to root-cause-driven administration.
