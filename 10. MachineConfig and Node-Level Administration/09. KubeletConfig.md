# KubeletConfig in MachineConfig and Node-Level Administration

**Audience:** Advanced OpenShift administrators with Linux, Kubernetes, RHCOS, and cluster operations experience.  
**Scope:** OpenShift Container Platform 4.x, especially modern OCP 4.19-style Machine Config Operator behavior.  
**Goal:** Understand what `KubeletConfig` is, how it is reconciled through Machine Config Operator, how to apply it safely, and how to troubleshoot node-level problems caused by kubelet tuning.

---

## 1. Executive Summary

`KubeletConfig` is an OpenShift custom resource from the API group:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
```

It is used to manage kubelet settings on OpenShift nodes in a controlled, declarative, pool-based way.

In normal Kubernetes, kubelet configuration is stored on each node as a kubelet configuration file and kubelet command-line arguments. In OpenShift 4, you do **not** SSH into RHCOS nodes and manually edit kubelet files. Instead, you create or update a `KubeletConfig` custom resource. The Machine Config Operator then generates a managed `MachineConfig`, renders it into the target `MachineConfigPool`, drains and updates nodes, restarts/reboots as required, and ensures the node converges to the desired state.

Think of `KubeletConfig` as the OpenShift-supported way to tune kubelet behavior for a node pool.

Typical use cases include:

- Change maximum pods per node.
- Tune `podsPerCore`.
- Configure `systemReserved` resources.
- Enable `autoSizingReserved`.
- Change `podPidsLimit`.
- Tune kubelet API QPS and burst.
- Tune container log rotation.
- Tune image garbage collection and eviction thresholds.
- Configure parallel image pulls.
- Set `reservedSystemCPUs` for CPU isolation scenarios.
- Configure kubelet TLS security profile.
- Disable the default node image list limit with `nodeStatusMaxImages: -1` when appropriate.

## 2. Where KubeletConfig Fits in OpenShift Node Management

OpenShift node-level management has three important layers:

| Layer | Object / Component | Purpose |
|---|---|---|
| Desired node pool | `MachineConfigPool` | Defines a group of nodes and the rendered machine configuration those nodes must run. |
| Generic host changes | `MachineConfig` | Writes files, systemd units, kernel arguments, OS configuration, and other host-level changes. |
| Kubelet-specific tuning | `KubeletConfig` | Lets MCO generate the correct kubelet-related MachineConfig for selected MachineConfigPools. |

The important point is this:

> You usually do not create a raw `MachineConfig` to edit kubelet settings. You create a `KubeletConfig`, and MCO generates the kubelet MachineConfig for you.

This gives OpenShift better validation flow, pool targeting, upgrade behavior, and rollback behavior than manual node changes.

## 3. High-Level Architecture Flow

When you apply a `KubeletConfig`, the flow is:

```text
Admin creates/updates KubeletConfig
        |
        v
Machine Config Controller watches KubeletConfig
        |
        v
MCO generates a kubelet MachineConfig
        |
        v
Render controller produces new rendered MachineConfig for the target MCP
        |
        v
MachineConfigPool enters Updating=True
        |
        v
Machine Config Daemon on each selected node drains workloads
        |
        v
Node applies kubelet configuration
        |
        v
Node restarts/reboots as required
        |
        v
Node returns Ready with updated /etc/kubernetes/kubelet.conf
        |
        v
MCP returns Updated=True, Updating=False, Degraded=False
```

You should always watch both the `KubeletConfig` and the `MachineConfigPool` after applying changes.

```bash
oc get kubeletconfig
oc get machineconfigpool
oc get machineconfig | grep kubelet
oc describe machineconfigpool worker
```

## 4. KubeletConfig vs MachineConfig vs ContainerRuntimeConfig

### 4.1 KubeletConfig

Use `KubeletConfig` when the setting belongs to the kubelet configuration API.

Examples:

```yaml
kubeletConfig:
  maxPods: 250
  podsPerCore: 10
  podPidsLimit: 8192
  containerLogMaxSize: 50Mi
  serializeImagePulls: false
  maxParallelImagePulls: 3
```

### 4.2 MachineConfig

Use `MachineConfig` for host OS configuration.

Examples:

- Write files under `/etc`.
- Create systemd units.
- Add kernel arguments.
- Configure chrony, registries, SSH keys, or other node OS files.

### 4.3 ContainerRuntimeConfig

Use `ContainerRuntimeConfig` for CRI-O runtime tuning.

Examples:

- CRI-O log level.
- Overlay storage size.
- Default runtime selection such as `crun` or `runc`.

### 4.4 Rule of Thumb

| Requirement | Use |
|---|---|
| Change kubelet behavior | `KubeletConfig` |
| Change CRI-O runtime behavior | `ContainerRuntimeConfig` |
| Change OS file, systemd unit, kernel argument | `MachineConfig` |
| Change node grouping and rollout target | `MachineConfigPool` |

## 5. Basic KubeletConfig YAML Structure

A minimal example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-kubelet-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: enabled
  kubeletConfig:
    maxPods: 250
    podsPerCore: 10
```

Before applying it, the target MCP must have the matching label:

```bash
oc label machineconfigpool worker custom-kubelet=enabled
oc apply -f worker-kubelet-tuning.yaml
```

Check rollout:

```bash
oc get kubeletconfig
oc get mc | grep kubelet
oc get mcp worker -w
```

## 6. Field-by-Field Breakdown

### 6.1 `apiVersion`

```yaml
apiVersion: machineconfiguration.openshift.io/v1
```

This tells Kubernetes that the object belongs to OpenShift Machine Configuration APIs.

### 6.2 `kind`

```yaml
kind: KubeletConfig
```

This identifies the custom resource type.

### 6.3 `metadata.name`

```yaml
metadata:
  name: worker-kubelet-tuning
```

Use a meaningful name. Good names include:

- `worker-kubelet-tuning`
- `infra-kubelet-reserved`
- `worker-max-pods`
- `odf-node-kubelet-config`

Avoid random names like `test1`, `newconfig`, or `kc-final` in production.

### 6.4 `spec.machineConfigPoolSelector`

This selector decides which MachineConfigPool receives the kubelet configuration.

Example:

```yaml
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: enabled
```

The MCP must contain the same label:

```bash
oc label machineconfigpool worker custom-kubelet=enabled
```

Check labels:

```bash
oc get mcp --show-labels
oc describe mcp worker
```

Important behavior:

- If the selector is empty or does not match any MCP, the `KubeletConfig` does not apply to nodes.
- The selector selects MachineConfigPools, not individual nodes directly.
- For custom pools, ensure the MCP design is clean and does not accidentally include more nodes than intended.

### 6.5 `spec.kubeletConfig`

This contains kubelet configuration fields. Most values are passed to kubelet from upstream Kubernetes kubelet configuration. That means invalid values might not be caught early by OpenShift admission. The kubelet itself validates many values when it starts. A bad value can cause kubelet startup failure and node unavailability.

Example:

```yaml
spec:
  kubeletConfig:
    maxPods: 250
    podsPerCore: 10
    podPidsLimit: 4096
```

### 6.6 `spec.autoSizingReserved`

This is an OpenShift-specific helper that allows OpenShift to calculate `systemReserved` values automatically based on node resources.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-auto-sizing-reserved
spec:
  autoSizingReserved: true
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
```

When enabled, OpenShift calculates reserved CPU and memory for node/system components such as kubelet and CRI-O. The resulting values are visible on the node:

```bash
oc debug node/<node-name>
chroot /host
cat /etc/node-sizing.env
```

### 6.7 `spec.logLevel`

`logLevel` controls kubelet log verbosity through the OpenShift KubeletConfig API. Use carefully because higher verbosity can increase log volume.

Example:

```yaml
spec:
  logLevel: 2
```

For production, increase only during troubleshooting and revert later.

### 6.8 `spec.tlsSecurityProfile`

This configures the TLS profile used by kubelet when it acts as an HTTPS server.

Example using a predefined profile:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-kubelet-tls
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: tls-profile
  tlsSecurityProfile:
    type: Intermediate
```

If unset, OpenShift uses a default based on cluster TLS behavior. In many OpenShift releases, only some profiles are supported for kubelet, and the minimum TLS version support can be more limited than other components. Always check your exact OCP release documentation before changing TLS profiles.

### 6.9 `status.conditions`

After applying, check status:

```bash
oc get kubeletconfig worker-kubelet-tuning -o yaml
```

Look for:

```yaml
status:
  conditions:
  - message: Success
    status: "True"
    type: Success
```

A successful `KubeletConfig` only means the controller accepted and rendered the configuration. You still need to verify the MCP and nodes.

## 7. Important Supported and Unsupported Kubelet Fields

Most upstream kubelet configuration options can be set, but OpenShift protects some values because they are cluster-critical.

Do **not** expect to override these with `KubeletConfig`:

- `CgroupDriver`
- `ClusterDNS`
- `ClusterDomain`
- `StaticPodPath`

These are managed by OpenShift because changing them can break node registration, DNS behavior, static pod behavior, and control plane assumptions.

Useful fields commonly tuned by administrators:

| Field | Purpose |
|---|---|
| `maxPods` | Fixed maximum pods per node. |
| `podsPerCore` | Maximum pods based on CPU core count. Lower of `maxPods` and `podsPerCore` result applies. |
| `podPidsLimit` | Maximum process IDs per pod. |
| `containerLogMaxSize` | Container log file size before rotation. |
| `containerLogMaxFiles` | Number of rotated log files to retain. |
| `systemReserved` | CPU/memory/ephemeral-storage reserved for system daemons. |
| `reservedSystemCPUs` | Explicit CPU IDs reserved for system processes. |
| `evictionHard` | Hard eviction thresholds. |
| `evictionSoft` | Soft eviction thresholds. |
| `evictionSoftGracePeriod` | Grace periods for soft eviction. |
| `imageGCHighThresholdPercent` | Disk usage percent that triggers image garbage collection. |
| `imageGCLowThresholdPercent` | Disk usage target after image garbage collection. |
| `serializeImagePulls` | Whether image pulls are serial instead of parallel. |
| `maxParallelImagePulls` | Limit for simultaneous image pulls. |
| `nodeStatusMaxImages` | Maximum images reported in node status. `-1` disables the 50-image truncation behavior. |
| `kubeAPIQPS` | Kubelet QPS against API server. |
| `kubeAPIBurst` | Kubelet API burst limit. |

## 8. Best Practices for Production

### 8.1 Use One Long-Lived KubeletConfig per MCP

Do not create a new `KubeletConfig` for every small change.

Bad pattern:

```text
set-maxpods
set-pids
set-logs
set-qps
set-eviction
set-reserved
```

Better pattern:

```text
worker-kubelet-config
infra-kubelet-config
odf-kubelet-config
```

Keep all permanent kubelet tuning for the same pool in one object. Edit that object when you need changes.

### 8.2 Use Temporary KubeletConfig Only for Temporary Tests

Temporary KubeletConfigs are useful for testing, canary pools, or rollback experiments. Delete them after testing.

### 8.3 Avoid Exceeding Generated Kubelet MachineConfig Limits

OpenShift MCO supports multiple generated kubelet MachineConfigs, but there is a practical documented limit of 10 per cluster for these generated kubelet configs. Once suffix numbering reaches `kubelet-9`, creating another `KubeletConfig` might not create a new generated MachineConfig even if fewer than 10 exist.

Operational advice:

- Avoid many separate KubeletConfigs.
- Consolidate settings per MCP.
- Delete generated/test configs in reverse order when cleaning up.

### 8.4 Always Use a Canary Pool for Risky Changes

For risky changes such as eviction thresholds, maxPods, `systemReserved`, PID limits, and API QPS tuning:

1. Create a small custom MCP.
2. Move one or two worker nodes into it.
3. Apply `KubeletConfig` only to that pool.
4. Run workload tests.
5. Roll out to the main worker pool only after verification.

### 8.5 Avoid Direct Node Edits

Do not SSH to RHCOS nodes and edit `/etc/kubernetes/kubelet.conf` manually. MCO detects configuration drift and can mark nodes or pools degraded.

### 8.6 Plan for Drain/Reboot

Most kubelet config changes cause node update and restart/reboot behavior through MCO.

Before applying:

```bash
oc get mcp
oc get nodes
oc get pdb -A
oc adm top nodes
oc get co machine-config
```

Check for workloads that cannot be evicted because of strict PodDisruptionBudgets.

### 8.7 Do Not Tune Without Capacity Math

For example, increasing `maxPods` is not only a scheduler setting. It affects:

- CRI-O load
- kubelet CPU and memory
- image pulls
- log volume
- CNI/OVN scale
- conntrack usage
- node disk pressure
- API server watch/list pressure
- monitoring cardinality
- DNS query load

A node that can run 250 tiny pods in a lab might not safely run 250 real application pods in production.

## 9. MachineConfigPool Targeting Deep Dive

### 9.1 Static Worker Pool Example

The default worker pool can be targeted by adding a label:

```bash
oc label mcp worker custom-kubelet=worker-standard
```

Then:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-standard-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: worker-standard
  kubeletConfig:
    maxPods: 250
```

### 9.2 Using Built-In MCP Labels

Many clusters show built-in labels like:

```yaml
pools.operator.machineconfiguration.openshift.io/worker: ""
```

You can target that label:

```yaml
machineConfigPoolSelector:
  matchLabels:
    pools.operator.machineconfiguration.openshift.io/worker: ""
```

However, for production, custom labels are easier to understand and safer during reviews.

### 9.3 Custom MCP Example: Infra Nodes

A custom `infra` pool usually has both a node selector and a machine config selector.

Example concept:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    custom-kubelet: infra-tuned
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Then target it:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: infra-kubelet-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: infra-tuned
  kubeletConfig:
    maxPods: 150
    systemReserved:
      cpu: 1000m
      memory: 2Gi
```

### 9.4 Dependent Pool Warning

If you target the general `worker` pool, dependent custom pools derived from worker configuration can also be affected. This commonly surprises administrators with `infra`, `odf`, `logging`, or `router` pools.

Safer strategy:

- Create a specific MCP for the nodes you want.
- Use an exclusive label on that MCP.
- Target the exclusive label in `KubeletConfig`.

## 10. Common Production Examples

### 10.1 Configure Maximum Pods per Node

Use `maxPods` for a fixed maximum and `podsPerCore` for CPU-based scaling.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-max-pods
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: worker-maxpods
  kubeletConfig:
    podsPerCore: 10
    maxPods: 250
```

Apply:

```bash
oc label mcp worker custom-kubelet=worker-maxpods
oc apply -f worker-max-pods.yaml
```

Verify:

```bash
oc get mcp worker -w
oc describe node <worker-node> | grep -A10 Allocatable
```

Notes:

- If both `podsPerCore` and `maxPods` are set, the lower effective limit applies.
- `podsPerCore: 0` disables the CPU-core-based limit.
- Increasing pod density requires API, network, CPU, memory, disk, monitoring, and DNS review.

### 10.2 Configure Pod PID Limit

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-pid-limit
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: pid-limit
  kubeletConfig:
    podPidsLimit: 8192
```

Verify on node:

```bash
oc debug node/<node-name>
chroot /host
cat /etc/kubernetes/kubelet.conf | grep -i pids
```

Production warning:

- Higher PID limits can help process-heavy workloads.
- Too high a PID limit can make node-level PID exhaustion more likely.
- Consider maximum pods per node together with `podPidsLimit`.

### 10.3 Configure Container Log Rotation

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-container-log-rotation
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: log-rotation
  kubeletConfig:
    containerLogMaxSize: 50Mi
    containerLogMaxFiles: 5
```

Use case:

- Prevent `/var/log/pods` and container logs from consuming too much node disk.
- Useful for chatty applications when application teams cannot immediately reduce log volume.

Do not treat this as a substitute for proper application logging and log retention policy.

### 10.4 Configure Kubelet API QPS and Burst

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-kube-api-qps
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: qps-tuned
  kubeletConfig:
    maxPods: 500
    kubeAPIQPS: 100
    kubeAPIBurst: 200
```

Use case:

- High pod density nodes.
- Large clusters where kubelet needs more API throughput.

Caution:

- Raising QPS/burst increases pressure on the API server.
- Tune cluster-wide API capacity, etcd health, and monitoring before increasing aggressively.

### 10.5 Enable Auto-Sized System Reserved Resources

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-auto-sizing-reserved
spec:
  autoSizingReserved: true
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: auto-reserved
```

Apply:

```bash
oc label mcp worker custom-kubelet=auto-reserved
oc apply -f worker-auto-sizing-reserved.yaml
```

Verify:

```bash
oc debug node/<node-name>
chroot /host
cat /etc/node-sizing.env
```

Expected output style:

```bash
SYSTEM_RESERVED_MEMORY=3Gi
SYSTEM_RESERVED_CPU=0.08
```

Use case:

- Mixed node sizes.
- Clusters where manual reservation becomes hard to maintain.
- Stability-focused production clusters.

### 10.6 Manually Configure `systemReserved`

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-system-reserved
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: manual-reserved
  kubeletConfig:
    systemReserved:
      cpu: 1000m
      memory: 2Gi
      ephemeral-storage: 5Gi
```

What this means:

- Reserve resources for system daemons such as kubelet, CRI-O, NetworkManager, systemd, node logging, and related services.
- Pods can schedule only against `Allocatable`, not full `Capacity`.

Formula:

```text
Allocatable = Capacity - systemReserved - hardEvictionThresholds
```

Verify:

```bash
oc describe node <node-name> | egrep -A8 'Capacity|Allocatable'
oc debug node/<node-name>
chroot /host
cat /etc/node-sizing.env
```

Important:

- OpenShift does not support Kubernetes `kubeReserved` in the same way upstream Kubernetes does.
- Use `systemReserved` through `KubeletConfig`, not raw MachineConfig.

### 10.7 Reserve Specific CPUs for System Processes

Useful for performance, latency-sensitive, or CPU Manager static policy scenarios.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-reserved-system-cpus
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: reserved-cpus
  kubeletConfig:
    reservedSystemCPUs: "0,1"
```

Use case:

- Reserve CPU 0 and 1 for system daemons.
- Leave remaining CPUs for guaranteed workloads.

Caution:

- CPU IDs depend on hardware topology.
- Validate NUMA, hyperthreading, workload CPU Manager policy, and performance profile settings.

### 10.8 Configure Eviction and Image Garbage Collection

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-eviction-gc
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: eviction-gc
  kubeletConfig:
    evictionSoft:
      memory.available: "500Mi"
      nodefs.available: "10%"
      nodefs.inodesFree: "5%"
      imagefs.available: "15%"
      imagefs.inodesFree: "10%"
    evictionSoftGracePeriod:
      memory.available: "1m30s"
      nodefs.available: "1m30s"
      nodefs.inodesFree: "1m30s"
      imagefs.available: "1m30s"
      imagefs.inodesFree: "1m30s"
    evictionHard:
      memory.available: "200Mi"
      nodefs.available: "5%"
      nodefs.inodesFree: "4%"
      imagefs.available: "10%"
      imagefs.inodesFree: "5%"
    evictionPressureTransitionPeriod: 3m
    imageMinimumGCAge: 5m
    imageGCHighThresholdPercent: 80
    imageGCLowThresholdPercent: 75
```

Use case:

- Nodes under disk pressure.
- Large image churn.
- High pod turnover.

Caution:

- Too aggressive image GC causes repeated image pulls.
- Too relaxed image GC causes disk pressure and pod evictions.
- Check `/var/lib/containers`, `/var/lib/kubelet`, nodefs/imagefs split, and storage backend.

### 10.9 Configure Parallel Image Pulls

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-parallel-image-pulls
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: parallel-pulls
  kubeletConfig:
    serializeImagePulls: false
    maxParallelImagePulls: 3
```

Use case:

- Limit registry/network load.
- Improve startup behavior while avoiding unlimited parallel pulls.

Rules:

- `serializeImagePulls: true` forces one image pull at a time.
- `serializeImagePulls: false` allows parallel pulls.
- `maxParallelImagePulls` sets the maximum parallel pulls.
- Do not set `maxParallelImagePulls` when `serializeImagePulls` is `true`.

Verify:

```bash
oc debug node/<node-name>
chroot /host
cat /etc/kubernetes/kubelet.conf | grep -i maxParallelImagePulls
```

### 10.10 Disable Node Image List Truncation

By default, node image reporting can be limited. On nodes with many images, this can affect scheduling behavior that considers image locality.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-node-status-images
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: image-status
  kubeletConfig:
    nodeStatusMaxImages: -1
```

Use carefully. Reporting more images can increase node status size and API traffic.

## 11. Rollout and Reboot Behavior

KubeletConfig changes usually result in a new rendered MachineConfig for the target MachineConfigPool. The Machine Config Daemon updates nodes one by one according to MCP rollout strategy.

Watch rollout:

```bash
oc get mcp -w
oc describe mcp worker
oc get nodes
```

Important columns:

```text
NAME     CONFIG              UPDATED   UPDATING   DEGRADED
worker   rendered-worker-...  False     True       False
```

Meaning:

| State | Meaning |
|---|---|
| `UPDATED=True` | All nodes in pool have current rendered config. |
| `UPDATING=True` | At least one node is being updated or pending update. |
| `DEGRADED=True` | MCO/MCD hit an error. Investigate immediately. |

Node update behavior normally includes:

1. Cordoning/draining affected node.
2. Applying config.
3. Restarting services or rebooting node as needed.
4. Uncordoning node after success.
5. Moving to next node.

Production impact depends on:

- Number of nodes in the MCP.
- `maxUnavailable` for the MCP.
- PodDisruptionBudgets.
- Stateful workloads.
- Local storage workloads.
- Control plane node availability if targeting master MCP.

## 12. Safe Change Procedure

Use this procedure for production changes.

### Step 1: Capture Baseline

```bash
oc get clusterversion
oc get co machine-config
oc get mcp
oc get nodes -o wide
oc get kubeletconfig
oc get mc | grep kubelet
```

Capture current kubelet config from one node:

```bash
NODE=<node-name>
oc debug node/$NODE
chroot /host
cp /etc/kubernetes/kubelet.conf /tmp/kubelet.conf.before
cat /etc/kubernetes/kubelet.conf
```

From your workstation:

```bash
oc describe node <node-name> > node-before.txt
oc get mcp worker -o yaml > mcp-worker-before.yaml
```

### Step 2: Check Disruption Risk

```bash
oc get pdb -A
oc get pods -A -o wide | grep <node-name>
oc adm top nodes
oc adm top pods -A --sort-by=memory
```

Check stateful workloads:

```bash
oc get statefulset -A
oc get pvc -A
```

### Step 3: Label Target MCP

```bash
oc label mcp worker custom-kubelet=worker-tuning
```

### Step 4: Apply KubeletConfig

```bash
oc apply -f worker-kubelet-config.yaml
```

### Step 5: Watch Render and Rollout

```bash
oc get kubeletconfig worker-kubelet-config -o yaml
oc get mc | grep kubelet
oc get mcp worker -w
```

### Step 6: Verify on Node

```bash
oc describe node <node-name> | grep -A15 Allocatable
oc debug node/<node-name>
chroot /host
cat /etc/kubernetes/kubelet.conf | egrep -i 'maxPods|podsPerCore|podPidsLimit|containerLogMaxSize|kubeAPIQPS|kubeAPIBurst'
```

### Step 7: Validate Workloads

```bash
oc get pods -A --field-selector=status.phase!=Running
oc get co
oc get mcp
oc adm top nodes
```

## 13. Rollback Procedure

Rollback options depend on how you changed the object.

### 13.1 If You Edited an Existing KubeletConfig

Restore the previous values:

```bash
oc edit kubeletconfig worker-kubelet-config
```

or apply a saved previous version:

```bash
oc apply -f worker-kubelet-config-before.yaml
```

### 13.2 If You Created a Temporary KubeletConfig

Delete it:

```bash
oc delete kubeletconfig <name>
```

Then watch MCP:

```bash
oc get mcp -w
oc get mc | grep kubelet
```

### 13.3 If Multiple Generated Kubelet MachineConfigs Exist

Clean up in reverse order where possible. For example, remove the latest test config before older ones. This helps avoid generated suffix and limit problems.

### 13.4 If Nodes Are Unavailable Due to Invalid Kubelet Config

1. Revert or delete the bad `KubeletConfig` immediately.
2. Watch MCO:

```bash
oc get co machine-config
oc get mcp
oc describe mcp <pool>
```

3. Check MCD logs:

```bash
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=200
```

4. If kubelet cannot start on affected nodes, use console/ILO/IPMI/cloud serial access or OpenShift node debugging, depending on node state.
5. If only some nodes are affected, keep workloads away from bad nodes until recovery completes.

## 14. Troubleshooting Runbook

### Problem 1: KubeletConfig Created but No Node Changes

Symptoms:

```bash
oc get kubeletconfig
oc get mc | grep kubelet
oc get mcp
```

No new generated MachineConfig or MCP update.

Check:

```bash
oc get mcp --show-labels
oc get kubeletconfig <name> -o yaml
```

Likely causes:

- `machineConfigPoolSelector` label does not match any MCP.
- Selector is empty or wrong.
- You labeled nodes, but not the MCP.
- You targeted a custom MCP label that does not exist.

Fix:

```bash
oc label mcp worker custom-kubelet=enabled --overwrite
```

or correct the selector:

```yaml
machineConfigPoolSelector:
  matchLabels:
    custom-kubelet: enabled
```

### Problem 2: MCP Stuck Updating

Check:

```bash
oc describe mcp worker
oc get nodes
oc get pods -A -o wide | grep <node-name>
oc get pdb -A
```

Likely causes:

- PodDisruptionBudget prevents drain.
- Node is NotReady.
- MCD failed on a node.
- Workload uses local storage and cannot evict.
- MCP is paused.
- `maxUnavailable` allows only slow one-by-one rollout.

Check if MCP is paused:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

Unpause if required:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":false}}'
```

### Problem 3: MCP Degraded After KubeletConfig

Check:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
oc get kubeletconfig <name> -o yaml
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=300
```

Likely causes:

- Invalid kubelet field.
- Invalid type, such as string instead of integer.
- Invalid quantity format.
- Unsupported kubelet option.
- Kubelet service failed to start after rendered config applied.

Fix strategy:

1. Revert the latest KubeletConfig change.
2. Wait for MCO to render rollback config.
3. Monitor node reboot/recovery.
4. Validate `/etc/kubernetes/kubelet.conf`.

### Problem 4: Custom MCP Also Affected Unexpectedly

Cause:

- You targeted a broad worker-level configuration, and a custom pool is dependent on worker machine configs.

Fix:

- Create a more specific custom MCP.
- Use exclusive labels.
- Target only that label in `KubeletConfig`.

### Problem 5: Node Capacity Looks Correct but Pods Still Do Not Schedule

Check:

```bash
oc describe node <node-name>
oc get events -A --sort-by=.metadata.creationTimestamp | tail -50
oc describe pod <pending-pod> -n <namespace>
```

Possible causes:

- `Allocatable` reduced by `systemReserved` or eviction thresholds.
- `maxPods` reached.
- Taints or node selectors.
- ResourceQuota/LimitRange.
- CPU Manager/static CPU constraints.
- Topology spread constraints.
- Pod anti-affinity.

Remember: scheduler uses `node.Status.Allocatable`, not raw `Capacity`.

### Problem 6: Disk Pressure Continues After Image GC Tuning

Check:

```bash
oc debug node/<node-name>
chroot /host
df -h
findmnt
crictl images
crictl ps -a
journalctl -u kubelet --no-pager | grep -i eviction
```

Possible causes:

- App logs consuming disk.
- `/var/lib/kubelet` and `/var/lib/containers` share one filesystem.
- Image GC thresholds too relaxed.
- Local PVs or hostPath usage.
- Log collector buffering.

### Problem 7: API Server Load Increased After Tuning

Likely causes:

- Increased `maxPods`.
- Increased `kubeAPIQPS` and `kubeAPIBurst`.
- Too many nodes rolled at once.
- Workloads generating high churn.

Check:

```bash
oc get --raw /metrics | grep apiserver_request
oc get co kube-apiserver
oc adm top nodes
```

Also check monitoring dashboards for API server latency, etcd latency, and request rate.

## 15. Advanced Design Patterns

### 15.1 Separate Node Pools by Workload Type

Avoid one kubelet policy for all workers when workloads differ.

Example pools:

| Pool | Example KubeletConfig Focus |
|---|---|
| `worker` | General app workloads, default pod density. |
| `infra` | Router, registry, monitoring, logging overhead. |
| `odf` | Storage-heavy, stronger system reserved memory. |
| `compute-highdensity` | Higher pod density, tuned QPS, log rotation. |
| `performance` | reserved CPUs, static CPU manager, NUMA-aware design. |

### 15.2 Use Canaries for Risky Kubelet Changes

Create a custom canary MCP:

```bash
oc label node <worker-node> node-role.kubernetes.io/canary=
oc label mcp canary custom-kubelet=canary-test
```

Apply only to `custom-kubelet=canary-test`.

Validate:

- Node updates successfully.
- Kubelet starts.
- Workloads schedule.
- Logs and metrics remain healthy.
- No unexpected eviction behavior.

### 15.3 Consolidate Kubelet Tuning by Operational Domain

Instead of separate CRs, keep a single file in Git:

```text
gitops/
  machine-config/
    kubelet/
      worker-kubelet-config.yaml
      infra-kubelet-config.yaml
      odf-kubelet-config.yaml
```

Use GitOps or controlled change management to apply.

### 15.4 Match KubeletConfig with Capacity Planning

Before increasing `maxPods`, calculate:

```text
Pods per node
Average CPU request
Average memory request
System reserved
Eviction threshold
Log volume per pod
Image pull rate
Network policy scale
DNS QPS
API server request rate
```

Do not tune only the kubelet without reviewing the whole cluster.

## 16. Exam / Interview-Level Explanation

### Simple Explanation

`KubeletConfig` is an OpenShift Machine Configuration custom resource used to change kubelet settings for nodes in a selected MachineConfigPool. The Machine Config Operator watches the object, generates a MachineConfig, rolls it into a rendered MachineConfig for the pool, drains/reboots nodes as needed, and applies the kubelet configuration on RHCOS nodes.

### Senior-Level Explanation

In OpenShift 4, node configuration is declarative and managed through MCO. Direct kubelet file edits are unsupported because MCO owns node state and detects drift. `KubeletConfig` provides a supported abstraction over upstream kubelet configuration fields plus OpenShift-specific settings such as `autoSizingReserved`. It targets MachineConfigPools via label selectors, not individual nodes. When reconciled, it produces generated `99-*-generated-kubelet*` MachineConfigs that become part of the rendered pool config. Operationally, each change must be treated as a node rollout because it can trigger drain/reboot and can make nodes unavailable if invalid kubelet settings are passed through. For production, use one consolidated KubeletConfig per pool, test with a canary MCP, monitor MCP status, validate `/etc/kubernetes/kubelet.conf`, and maintain rollback manifests.

### Key Commands to Remember

```bash
oc get kubeletconfig
oc get kubeletconfig <name> -o yaml
oc get mcp --show-labels
oc label mcp worker custom-kubelet=enabled
oc get mc | grep kubelet
oc get mcp -w
oc describe mcp worker
oc describe node <node>
oc debug node/<node>
chroot /host
cat /etc/kubernetes/kubelet.conf
cat /etc/node-sizing.env
journalctl -u kubelet --no-pager
```

## 17. Complete Production-Style Example

This example creates a consolidated worker kubelet config for moderate pod density, system reservation, log rotation, PID safety, and controlled image pulls.

### 17.1 Label the Worker MCP

```bash
oc label mcp worker custom-kubelet=worker-standard --overwrite
```

### 17.2 Create `worker-standard-kubelet.yaml`

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-standard-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: worker-standard
  kubeletConfig:
    maxPods: 250
    podsPerCore: 10
    podPidsLimit: 4096
    containerLogMaxSize: 50Mi
    containerLogMaxFiles: 5
    systemReserved:
      cpu: 1000m
      memory: 2Gi
      ephemeral-storage: 5Gi
    serializeImagePulls: false
    maxParallelImagePulls: 3
    imageGCHighThresholdPercent: 80
    imageGCLowThresholdPercent: 75
```

### 17.3 Apply

```bash
oc apply -f worker-standard-kubelet.yaml
```

### 17.4 Watch

```bash
oc get kubeletconfig worker-standard-kubelet -o yaml
oc get mc | grep kubelet
oc get mcp worker -w
```

### 17.5 Verify

```bash
oc describe node <worker-node> | grep -A15 Allocatable
oc debug node/<worker-node>
chroot /host
cat /etc/kubernetes/kubelet.conf | egrep -i 'maxPods|podsPerCore|podPidsLimit|containerLogMaxSize|maxParallelImagePulls|imageGC|systemReserved'
cat /etc/node-sizing.env || true
```

## 18. Do and Do Not Checklist

### Do

- Use `KubeletConfig` for kubelet tuning.
- Target MCPs using clear labels.
- Use one consolidated config per MCP.
- Test risky changes on a canary pool.
- Watch `oc get mcp -w` after applying.
- Validate actual node files with `oc debug node`.
- Keep rollback YAML files.
- Review PDBs before rollout.
- Treat kubelet changes as production-impacting node changes.

### Do Not

- Do not SSH into RHCOS nodes and manually edit kubelet config.
- Do not create one KubeletConfig per individual field.
- Do not target the broad worker pool if only infra/ODF nodes need changes.
- Do not increase `maxPods` without capacity testing.
- Do not set unsupported fields such as `ClusterDNS` or `CgroupDriver`.
- Do not ignore `MCP Degraded=True`.
- Do not apply kubelet tuning during cluster upgrade unless necessary.
- Do not use aggressive eviction values without understanding filesystem layout.

## 20. Common YAML Mistakes

### Mistake 1: Labeling Node Instead of MCP

Wrong assumption:

```bash
oc label node worker-1 custom-kubelet=enabled
```

Correct:

```bash
oc label mcp worker custom-kubelet=enabled
```

`KubeletConfig.spec.machineConfigPoolSelector` selects MachineConfigPools, not nodes.

### Mistake 2: Wrong Quantity Format

Bad:

```yaml
systemReserved:
  cpu: "1core"
  memory: "2GB"
```

Good:

```yaml
systemReserved:
  cpu: 1000m
  memory: 2Gi
```

### Mistake 3: Too Many Small KubeletConfigs

Bad:

```text
worker-maxpods
worker-pids
worker-logs
worker-qps
```

Good:

```text
worker-kubelet-config
```

### Mistake 4: Targeting Worker and Accidentally Affecting Infra

Bad:

```yaml
machineConfigPoolSelector:
  matchLabels:
    pools.operator.machineconfiguration.openshift.io/worker: ""
```

If infra pool depends on worker configs, it may receive effects too.

Better:

```yaml
machineConfigPoolSelector:
  matchLabels:
    custom-kubelet: worker-only
```

### Mistake 5: Setting Unsupported Kubelet Fields

Avoid trying to override OpenShift-owned settings:

```yaml
kubeletConfig:
  clusterDNS:
  - 10.128.0.10
  cgroupDriver: systemd
```

OpenShift manages those values.

## 21. How to Explain KubeletConfig in an Interview

A strong answer:

> In OpenShift, `KubeletConfig` is the supported custom resource for changing kubelet settings on nodes. It is part of the Machine Configuration API. We target a MachineConfigPool using labels in `spec.machineConfigPoolSelector`, then provide kubelet fields under `spec.kubeletConfig`. The Machine Config Operator converts it into generated kubelet MachineConfigs, renders a new config for the pool, and the Machine Config Daemon applies it node by node. Because kubelet values are passed to upstream kubelet validation, a bad value can make nodes unavailable, so we normally use one consolidated config per MCP, test in a canary pool, monitor MCP rollout, and verify the final `/etc/kubernetes/kubelet.conf` on the node.

Follow-up points:

- KubeletConfig is not for CRI-O; use `ContainerRuntimeConfig` for CRI-O.
- KubeletConfig is not for arbitrary host files; use `MachineConfig` for that.
- KubeletConfig targets MCP labels, not node labels directly.
- Changes usually cause node rollout and reboot/restart behavior.
- `systemReserved` affects `Allocatable` and scheduling.
- `maxPods` and `podsPerCore` must be capacity-tested.
- Invalid kubelet values can degrade or break nodes.
