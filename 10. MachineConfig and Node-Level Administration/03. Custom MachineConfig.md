## 1. What is a Custom MachineConfig?

A **custom MachineConfig** is an OpenShift custom resource used to declare node-level operating system configuration that should be applied by the **Machine Config Operator** to a group of nodes.

In simple words:

> A custom MachineConfig is the OpenShift-supported way to manage selected host OS configuration across nodes without manually SSHing into every node.

A custom MachineConfig can be used to:

- Create or overwrite files under supported host paths such as `/etc` and `/var`.
- Create systemd unit files.
- Add systemd drop-ins.
- Enable, disable, restart, or modify host services.
- Add kernel boot arguments.
- Configure selected RHCOS extensions.
- Update SSH authorized keys for the `core` user.
- Apply node-level configuration consistently to new and existing nodes.

Example use cases:

- Configure `chrony` or NTP settings.
- Add `/etc/containers/registries.conf`-related configuration indirectly through supported OpenShift APIs.
- Add a custom CA file.
- Add a systemd drop-in for a host service.
- Configure journald behavior.
- Enable multipathing.
- Add kernel arguments.
- Configure a custom worker or infra node pool.
- Enforce consistent host files across all worker nodes.

## 2. Why MachineConfig Exists in OpenShift

OpenShift worker and control plane nodes usually run **Red Hat Enterprise Linux CoreOS**. RHCOS is designed to be managed by the cluster, not manually modified like a traditional RHEL server.

Traditional Linux administration pattern:

```bash
ssh node01
vi /etc/some.conf
systemctl restart some-service
repeat on node02 node03 node04...
```

OpenShift pattern:

```bash
oc apply -f 99-worker-custom-config.yaml
oc get mcp
oc describe mcp worker
```

The Machine Config Operator makes node configuration:

- Declarative
- Repeatable
- Auditable
- Cluster-integrated
- Automatically applied to new nodes
- Safer during cluster upgrades
- Less dependent on manual SSH changes

This is important because direct manual changes on OpenShift nodes are generally discouraged. Manual node changes are not durable when a node is replaced, and they can also create configuration drift if they conflict with files managed by the Machine Config Operator.

## 3. Core Architecture

The Machine Config Operator architecture includes several important components.

### 3.1 Machine Config Operator

The **Machine Config Operator**, often called **MCO**, manages operating system and low-level node configuration.

It is responsible for managing configuration related to:

- RHCOS updates
- systemd
- CRI-O
- kubelet
- kernel arguments
- NetworkManager-related host files
- selected OS files
- selected OS extensions
- rendered MachineConfigs
- node reboots required by machine configuration changes

The MCO runs in the `openshift-machine-config-operator` namespace.

Useful commands:

```bash
oc get co machine-config
oc get pods -n openshift-machine-config-operator
oc get ds -n openshift-machine-config-operator
```

### 3.2 Machine Config Controller

The **machine-config-controller** watches MachineConfig and MachineConfigPool resources.

It:

- Detects new or changed MachineConfigs.
- Selects MachineConfigs matching each MachineConfigPool.
- Merges them into rendered MachineConfigs.
- Updates MCP desired configuration.
- Coordinates rollout through the pool.

### 3.3 Machine Config Daemon

The **machine-config-daemon**, or **MCD**, runs on every node as a DaemonSet.

It:

- Compares current node configuration with desired rendered configuration.
- Applies required OS-level changes.
- Drains nodes when required.
- Reboots nodes when required.
- Uncordons nodes after successful update.
- Detects configuration drift.
- Reports node state through node annotations and MCP status.

Important node annotations:

```bash
machineconfiguration.openshift.io/currentConfig
machineconfiguration.openshift.io/desiredConfig
machineconfiguration.openshift.io/state
machineconfiguration.openshift.io/reason
```

### 3.4 Machine Config Server

The **machine-config-server** provides Ignition configuration to new nodes joining the cluster.

When a new node is provisioned, it receives its initial configuration through this flow so that it joins the correct pool and receives the proper rendered configuration.

## 4. MachineConfig vs MachineConfigPool vs Rendered MachineConfig

### 4.1 MachineConfig

A `MachineConfig` is an individual configuration object.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-custom-motd
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
      - path: /etc/motd
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,V2VsY29tZSB0byBPcGVuU2hpZnQK
```

This object says:

- Apply this config to the `worker` role.
- Use Ignition spec version `3.5.0`.
- Write `/etc/motd`.
- File mode is `0644`.
- Replace the file if it already exists.

### 4.2 MachineConfigPool

A `MachineConfigPool`, or **MCP**, represents a group of nodes that should receive the same rendered node configuration.

Default MCPs:

```bash
oc get mcp
```

Typical output:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED
master   rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False
worker   rendered-worker-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False
```

The `master` MCP controls control plane nodes.  
The `worker` MCP controls worker nodes.

Custom MCPs can be created for specialized worker roles, such as:

- `infra`
- `storage`
- `gpu`
- `logging`
- `edge`
- `rt` / real-time workloads

### 4.3 Rendered MachineConfig

A **rendered MachineConfig** is generated by the MCO after merging all matching MachineConfigs for a pool.

Example:

```bash
oc get mc | grep rendered-worker
```

Example output:

```text
rendered-worker-11aabbccddeeff001122334455667788
rendered-worker-99ffeeddccbbaa887766554433221100
```

The node does not apply each MachineConfig independently. Instead, it applies the final rendered MachineConfig generated for its MCP.

## 5. What You Can and Cannot Configure

## 5.1 Supported Configuration Areas

A custom MachineConfig can commonly manage:

### Files

Usually under:

```text
/etc
/var
```

Examples:

```text
/etc/motd
/etc/chrony.conf
/etc/systemd/journald.conf
/etc/containers/policy.json
/var/lib/example/config.yaml
```

### systemd units

You can:

- Create a unit.
- Enable a unit.
- Disable a unit.
- Mask a unit.
- Add drop-in configuration.

### Kernel arguments

Example:

```yaml
spec:
  kernelArguments:
  - loglevel=7
```

### SSH authorized keys

Supported for the `core` user.

### RHCOS extensions

Selected extensions can be added through MachineConfig depending on support for your OpenShift/RHCOS version.

### Kubelet and CRI-O indirectly

For kubelet and CRI-O settings, prefer:

- `KubeletConfig`
- `ContainerRuntimeConfig`

instead of hand-writing the generated MachineConfig directly.

---

## 5.2 Unsupported or Risky Areas

Avoid using custom MachineConfig for:

- Random manual package installation with `dnf` or `yum`.
- Editing files under `/usr` directly.
- Creating arbitrary local Linux users post-installation.
- Large application payload deployment.
- Workload configuration that belongs in Kubernetes objects.
- Tuning that should be handled by the Node Tuning Operator.
- CRI-O or kubelet settings that have dedicated OpenShift custom resources.
- Emergency one-off SSH changes that are not converted back into declarative config.

Important mindset:

> MachineConfig is for host baseline configuration, not for day-to-day application configuration.

## 6. MachineConfig YAML Anatomy

A MachineConfig has these major sections:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files: []
    systemd:
      units: []
  kernelArguments: []
  extensions: []
```

### 6.1 apiVersion

```yaml
apiVersion: machineconfiguration.openshift.io/v1
```

This identifies the OpenShift MachineConfig API.

### 6.2 kind

```yaml
kind: MachineConfig
```

This tells Kubernetes that the object is a MachineConfig.

### 6.3 metadata.name

```yaml
metadata:
  name: 99-worker-example
```

Naming is important because MachineConfigs are merged in lexicographic order.

Common naming patterns:

```text
00-worker-base
01-worker-container-runtime
01-worker-kubelet
50-worker-company-baseline
80-worker-security-hardening
90-worker-custom-service
99-worker-emergency-fix
```

### 6.4 metadata.labels

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

This label decides which pool the MachineConfig targets.

Common values:

```text
master
worker
infra
storage
gpu
```

For a custom pool named `infra`, the MachineConfig label is usually:

```yaml
machineconfiguration.openshift.io/role: infra
```

### 6.5 spec.config.ignition.version

```yaml
spec:
  config:
    ignition:
      version: 3.5.0
```

Current OCP 4.21 documentation recommends creating new MachineConfigs using Ignition specification `3.5.0`.

### 6.6 storage.files

Used to create or overwrite files.

Example:

```yaml
storage:
  files:
  - path: /etc/example.conf
    mode: 0644
    overwrite: true
    contents:
      source: data:text/plain;charset=utf-8;base64,ZXhhbXBsZT10cnVlCg==
```

Notes:

- `path` is the destination path on the node.
- `mode` is normally written as octal in source YAML.
- After the object is stored, OpenShift may display the mode in decimal form.
- `overwrite: true` allows replacement of an existing file.
- `contents.source` often uses a `data:` URL with base64 content.

### 6.7 systemd.units

Used to manage host systemd units.

Example:

```yaml
systemd:
  units:
  - name: example.service
    enabled: true
    contents: |
      [Unit]
      Description=Example custom service
      After=network-online.target

      [Service]
      Type=oneshot
      ExecStart=/usr/local/bin/example.sh
      RemainAfterExit=yes

      [Install]
      WantedBy=multi-user.target
```

### 6.8 systemd drop-ins

Use drop-ins when modifying an existing systemd service.

Example:

```yaml
systemd:
  units:
  - name: crio.service
    dropins:
    - name: 10-custom.conf
      contents: |
        [Service]
        Environment="EXAMPLE=true"
```

Be careful with critical services such as:

- `kubelet.service`
- `crio.service`
- `NetworkManager.service`
- `rpm-ostreed.service`

A bad drop-in can make nodes unavailable.

### 6.9 kernelArguments

Example:

```yaml
spec:
  kernelArguments:
  - loglevel=7
```

Kernel argument changes require reboot because they affect boot-time behavior.

## 7. Naming, Ordering, and Merge Behavior

MachineConfig ordering matters.

The MCO processes MachineConfigs for a pool in lexicographic order by name. The rendered configuration is produced from matching MachineConfigs. Later configs can override earlier fields if they define the same path or field.

Example order:

```text
00-worker
01-worker-container-runtime
01-worker-kubelet
50-worker-baseline
80-worker-security
99-worker-custom
```

Practical guidance:

- Use `99-` only for intentional final overrides.
- Use clear names that include role and purpose.
- Avoid many small MachineConfigs for the same feature.
- Keep related file and systemd changes together when they are logically one change.
- Avoid overwriting files generated by other operators unless documented and supported.

Bad naming:

```text
test
new
final
fix
abc
```

Good naming:

```text
99-worker-chrony-company-ntp
99-infra-custom-journald
80-worker-security-banner
```

## 8. Rollout Lifecycle: What Happens After You Apply a MachineConfig

When you apply a custom MachineConfig, the following usually happens:

1. You create the MachineConfig.
2. The Machine Config Controller detects it.
3. The controller determines which MCP matches the MachineConfig label.
4. The controller renders a new rendered MachineConfig.
5. The MCP status changes to `UPDATING=True`.
6. The Machine Config Daemon on each affected node notices the desired config changed.
7. The MCO cordons/drains one or more nodes depending on `maxUnavailable`.
8. The MCD applies the change.
9. The node reboots if required.
10. The node comes back.
11. The node reports the new current rendered config.
12. The node is uncordoned.
13. The rollout continues to the next node.
14. The MCP eventually returns to `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`.

Check rollout:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig
```

### 8.1 Drain and Reboot Behavior

Most MachineConfig changes require a drain and reboot.

Examples that commonly require reboot:

- File changes
- systemd unit changes
- kernel arguments
- kubelet config generated changes
- CRI-O config generated changes

Some changes can be applied without drain/reboot depending on the type of change, such as supported SSH key changes or certain pull-secret/certificate updates.

### 8.2 maxUnavailable

The MCP controls how many nodes may be unavailable during update.

Check:

```bash
oc get mcp worker -o yaml | grep -A5 maxUnavailable
```

Patch example:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

For production, `maxUnavailable: 1` is safer for small clusters. Larger clusters can use a percentage or higher number after considering workload disruption and PodDisruptionBudgets.

### 8.3 Pausing a MachineConfigPool

Pause worker pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Use pause when:

- Preparing multiple changes before one rollout.
- Preventing immediate reboot during a maintenance window.
- Testing rendered config generation before rollout.

Do not leave MCPs paused accidentally. A paused pool can stop node updates from applying.

## 9. Custom MachineConfigPools

A custom MachineConfigPool is used when a subset of worker nodes needs a different node-level configuration.

Common examples:

- Infra nodes
- Storage nodes
- GPU nodes
- Logging nodes
- Edge nodes
- Real-time kernel nodes
- Nodes with special NIC or hardware requirements

### 9.1 Important Rules

- Custom MCPs are supported for worker-like nodes.
- Custom MCPs for control plane nodes are not supported.
- Custom pools inherit worker pool configuration.
- Worker MachineConfigs are also applied to custom worker-derived pools.
- Custom pool-specific MachineConfigs can override worker configs for the same field/path.
- A node can be managed by only one MCP.
- If a node has `worker` and `infra` labels and an `infra` MCP exists, the custom `infra` MCP manages that node.

### 9.2 Creating an Infra MCP

Example node label:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
```

Example MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp infra
oc get nodes -l node-role.kubernetes.io/infra=
```

### 9.3 Custom MachineConfig for Infra Pool

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-custom-motd
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
      - path: /etc/motd
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,SW5mcmEgbm9kZSBtYW5hZ2VkIGJ5IE1DTwo=
```

This applies only to nodes managed by the `infra` MCP.

## 10. Safe Production Workflow

A senior administrator should never treat MachineConfig as a casual YAML change. It can reboot nodes and affect cluster availability.

Recommended workflow:

### Step 1: Identify target pool

```bash
oc get mcp
oc get nodes --show-labels
```

Decide whether the change belongs to:

- all workers
- control plane nodes
- infra nodes
- storage nodes
- a temporary test pool

### Step 2: Review current health

```bash
oc get co
oc get mcp
oc get nodes
oc get clusterversion
```

Do not apply risky MachineConfigs when:

- MCP is already degraded.
- ClusterOperators are degraded.
- Nodes are NotReady.
- There are pending CSRs for node join.
- etcd or API server is unstable.
- Upgrade is already in progress.

### Step 3: Check workload disruption risk

```bash
oc get pdb -A
oc get pods -A -o wide | grep <node-name>
oc adm drain <node-name> --dry-run=server --ignore-daemonsets
```

Check whether workloads can tolerate node drain.

### Step 4: Use custom pool for testing

Create a small custom MCP with one non-critical worker, apply the MachineConfig there first, then roll out to the larger worker pool after validation.

### Step 5: Generate config with Butane

Prefer Butane for readable source and validation.

### Step 6: Apply during maintenance window

```bash
oc apply -f 99-worker-custom.yaml
watch -n5 oc get mcp
```

### Step 7: Verify node-level result

```bash
oc debug node/<node-name>
chroot /host
cat /etc/motd
systemctl status <service>
exit
exit
```

### Step 8: Keep source YAML in Git

Store both:

- Butane `.bu` source
- Rendered MachineConfig `.yaml`

Use change control for production clusters.

## 11. Creating Custom MachineConfigs with Butane

MachineConfig YAML can be difficult to write directly because file contents usually need to be encoded as data URLs. **Butane** provides a cleaner syntax and converts it into a valid MachineConfig.

### 11.1 Butane Source Example

File: `99-worker-custom-motd.bu`

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-custom-motd
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
  - path: /etc/motd
    mode: 0644
    overwrite: true
    contents:
      inline: |
        Authorized OpenShift worker node.
        Managed by Machine Config Operator.
```

Generate MachineConfig:

```bash
butane 99-worker-custom-motd.bu -o 99-worker-custom-motd.yaml
```

Apply:

```bash
oc apply -f 99-worker-custom-motd.yaml
```

Monitor:

```bash
watch -n5 oc get mcp worker
```

### 11.2 Butane Version

The Butane version should match the OpenShift version and end in `.0`.

Examples:

```yaml
version: 4.16.0
version: 4.17.0
version: 4.18.0
version: 4.21.0
```

If your cluster is OCP 4.16, use `4.16.0`.  
If your cluster is OCP 4.21, use `4.21.0`.

Check cluster version:

```bash
oc get clusterversion
```

## 12.2 Example 2: Configure chrony on Worker Nodes

### Butane Source

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-chrony-company-ntp
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
  - path: /etc/chrony.conf
    mode: 0644
    overwrite: true
    contents:
      inline: |
        server ntp1.example.com iburst
        server ntp2.example.com iburst
        driftfile /var/lib/chrony/drift
        makestep 1.0 3
        rtcsync
        logdir /var/log/chrony
```

Generate and apply:

```bash
butane 99-worker-chrony-company-ntp.bu -o 99-worker-chrony-company-ntp.yaml
oc apply -f 99-worker-chrony-company-ntp.yaml
```

Verify:

```bash
oc debug node/<worker-node>
chroot /host
cat /etc/chrony.conf
chronyc sources -v
exit
exit
```

Important:

- Make sure NTP servers are reachable.
- UDP port 123 must be allowed to external NTP servers.
- Wrong time configuration can break certificates, OAuth, image pulls, and etcd behavior.

## 12.3 Example 3: Add a Custom systemd Service

This example creates a script and a systemd oneshot service.

### Butane Source

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-example-service
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
  - path: /usr/local/bin/example-node-check.sh
    mode: 0755
    overwrite: true
    contents:
      inline: |
        #!/bin/bash
        echo "Custom node check executed at $(date)" >> /var/log/example-node-check.log
systemd:
  units:
  - name: example-node-check.service
    enabled: true
    contents: |
      [Unit]
      Description=Example custom node check
      After=network-online.target

      [Service]
      Type=oneshot
      ExecStart=/usr/local/bin/example-node-check.sh
      RemainAfterExit=yes

      [Install]
      WantedBy=multi-user.target
```

Generate and apply:

```bash
butane 99-worker-example-service.bu -o 99-worker-example-service.yaml
oc apply -f 99-worker-example-service.yaml
```

Verify:

```bash
oc debug node/<worker-node>
chroot /host
systemctl status example-node-check.service
cat /var/log/example-node-check.log
exit
exit
```

Senior-admin warning:

> Do not use custom systemd services to bypass Kubernetes workload management. Use this only for genuine host-level services or one-time host preparation tasks.

```yaml
  config:
    ignition:
      version: 3.5.0
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-rsa AAAA...example-key... user@example
```

Important:

- This is supported for the `core` user.
- Adding arbitrary new users through MachineConfig post-installation is not supported.
- Manage SSH access carefully; cluster nodes should not become general-purpose SSH servers.

## 12.9 Example 9: Prefer KubeletConfig for kubelet Changes

Do **not** manually edit kubelet files through a MachineConfig unless you have a very specific Red Hat-supported reason.

```bash
oc get mc | grep kubelet
oc get kubeletconfig
oc get mcp worker
```

Why this is better:

- The MCO generates the correct MachineConfig.
- kubelet validates upstream kubelet configuration values.
- It is easier to support and revert.

## 14. Troubleshooting Custom MachineConfig Issues

## 14.1 MCP stuck Updating

Symptoms:

```bash
oc get mcp
```

```text
worker   rendered-worker-xxx   False   True   False
```

Check details:

```bash
oc describe mcp worker
```

Common causes:

- Node drain blocked by PodDisruptionBudget.
- Pod cannot be evicted.
- Node cannot reboot.
- Node is NotReady.
- MCD pod has errors.
- MachineConfig contains invalid systemd unit.
- Node is under disk pressure or memory pressure.
- Cluster is already upgrading.

Useful commands:

```bash
oc get nodes
oc describe node <node-name>
oc get pods -A -o wide | grep <node-name>
oc get pdb -A
oc get events -A --sort-by=.lastTimestamp | tail -50
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

---

## 14.2 MCP Degraded

Symptoms:

```text
DEGRADED=True
DEGRADEDMACHINECOUNT > 0
```

Check:

```bash
oc describe mcp worker
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason
```

Common reasons:

- Content mismatch for a managed file.
- File permission mismatch.
- Invalid MachineConfig content.
- Failed systemd unit.
- Node did not reboot correctly.
- MCD failed to apply config.
- Disk or filesystem issue.

Example reason:

```text
content mismatch for file "/etc/mco-test-file"
```

---

## 14.3 Invalid YAML or Bad Ignition

Check server-side validation:

```bash
oc apply --dry-run=server -f 99-worker-custom.yaml
```

Check YAML syntax:

```bash
yamllint 99-worker-custom.yaml
```

Generate using Butane:

```bash
butane --pretty --strict input.bu -o output.yaml
```

Common mistakes:

- Wrong indentation.
- Missing `ignition.version`.
- Wrong base64 in data URL.
- Wrong role label.
- Invalid file mode.
- Writing to unsupported path.
- Duplicating same path across multiple MachineConfigs unintentionally.

---

## 14.4 Wrong Role Label

Problem:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: workers
```

`workers` is wrong if MCP expects `worker`.

Correct:

```yaml
machineconfiguration.openshift.io/role: worker
```

Check matching MachineConfigs:

```bash
oc get mc -l machineconfiguration.openshift.io/role=worker
```

For custom pool:

```bash
oc get mc -l machineconfiguration.openshift.io/role=infra
```

---

## 14.5 Node Does Not Pick Desired Config

Check annotations:

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

If `currentConfig` and `desiredConfig` differ, node is still updating or stuck.

Check MCD logs:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node-name>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

---

## 14.6 Drain Failure

Symptoms in MCD logs or MCP events:

```text
failed to drain node
cannot evict pod
pod disruption budget violation
```

Check:

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data --dry-run=server
oc get pdb -A
oc get pods -A -o wide | grep <node-name>
```

Resolution:

- Fix PDB constraints.
- Scale replicas if needed.
- Move singleton workload.
- Add toleration/node selectors as needed.
- Avoid forcing drain unless you fully understand the impact.

---

## 14.7 Bad systemd Unit

Symptoms:

```text
Failed to start custom.service
MCD degraded
node reboot loop
```

Debug:

```bash
oc debug node/<node-name>
chroot /host
systemctl status custom.service
journalctl -u custom.service -b
systemctl cat custom.service
exit
exit
```

Common mistakes:

- Wrong binary path.
- Missing executable bit.
- SELinux denial.
- Service depends on network before it is available.
- Invalid systemd syntax.
- Unit creates long-running process but uses `Type=oneshot` incorrectly.

---

## 14.8 File Permission Mismatch

If MachineConfig expects mode `0644`, but someone manually changes it:

```bash
chmod 0600 /etc/example.conf
```

MCD can detect drift and degrade the node.

Fix by either:

- Restoring expected mode/content manually.
- Updating the MachineConfig to the desired mode/content.
- Using force reapply only when appropriate and after understanding the root cause.

---

## 15. Configuration Drift

Configuration drift means the node's on-disk state does not match the rendered MachineConfig.

Example:

1. MachineConfig creates `/etc/motd`.
2. Admin manually edits `/etc/motd` on one node.
3. MCD detects file content mismatch.
4. Node becomes `Degraded`.
5. MCP becomes `Degraded`.
6. Node cannot receive further MachineConfig updates until corrected.

Check drift:

```bash
oc describe mcp worker
oc describe node <node-name>
```

Look for:

```text
machineconfiguration.openshift.io/state: Degraded
machineconfiguration.openshift.io/reason: content mismatch for file "/etc/motd"
```

Fix options:

### Option 1: Restore file manually to expected state

```bash
oc debug node/<node-name>
chroot /host
vi /etc/motd
chmod 0644 /etc/motd
exit
exit
```

### Option 2: Update MachineConfig to desired state

If the manual change is actually correct, update the MachineConfig and reapply.

### Option 3: Force reapply current config

Use force reapply only when you understand what will be overwritten and why the drift happened. This is usually an escalation action, not a first response.

## 16. Rollback and Revert Strategy

## 16.1 Revert by Deleting the Custom MachineConfig

If the MachineConfig is no longer required:

```bash
oc delete mc 99-worker-custom-motd
```

Then monitor:

```bash
watch -n5 oc get mcp worker
```

The MCO renders a new config without that MachineConfig and rolls nodes back to the new desired state.

### Important

Deleting a MachineConfig can also trigger node drains and reboots.

If using GitOps or Git:

```bash

oc apply -f 99-worker-custom-motd.yaml
```

## 17. Best Practices for Senior Administrators

### 17.1 Treat MachineConfig as infrastructure code

Keep files in Git:

```text
machine-configs/
  worker/
    99-worker-chrony.bu
    99-worker-chrony.yaml
  infra/
    infra-mcp.yaml
    99-infra-journald.bu
    99-infra-journald.yaml
```

Use pull requests, review, and rollback plans.

### 17.2 Prefer Butane

Butane provides readable syntax and validation. Raw MachineConfig YAML is harder to maintain, especially with base64 file content.

### 17.3 Use custom MCP for risky changes

Do not test kernel arguments, systemd changes, or kubelet-related changes on all workers first.

Recommended:

1. Create test MCP.
2. Move one non-critical node.
3. Apply MachineConfig to test MCP.
4. Validate.
5. Roll out to production MCP.

### 17.4 Never ignore MCP degradation

MCP degraded means the pool cannot safely continue updates.

Always resolve:

```bash
oc describe mcp <pool>
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason
```

### 17.5 Avoid overlapping MachineConfigs

Bad:

```text
99-worker-chrony-a writes /etc/chrony.conf
99-worker-chrony-b also writes /etc/chrony.conf
```

Better:

```text
99-worker-chrony-company-standard writes /etc/chrony.conf
```

### 17.6 Understand dedicated CRs

Use the right API:

| Requirement | Preferred API |
|---|---|
| kubelet maxPods / podPidsLimit | KubeletConfig |
| CRI-O logLevel / overlaySize | ContainerRuntimeConfig |
| Host file under `/etc` | MachineConfig |
| systemd unit/drop-in | MachineConfig |
| kernel args | MachineConfig |
| sysctl/tuned performance profile | Node Tuning Operator / Tuned |
| Operator workload config | Operator-specific CR |

### 17.7 Avoid control plane MachineConfigs unless necessary

Changing `master` pool can reboot control plane nodes. In HA clusters, the MCO rolls through nodes safely, but a bad configuration can still cause serious outage.

Before applying to `master`:

```bash
oc get co
oc get nodes
oc get etcd -n openshift-etcd
oc get mcp master
```

Have console/API access and break-glass procedure ready.

### 17.8 Plan around cluster upgrades

Avoid applying risky custom MachineConfigs during cluster upgrades.

Check:

```bash
oc get clusterversion
oc get co
oc get mcp
```

### 17.9 Document expected reboot

For every MachineConfig change, document:

- Target pool
- Expected nodes
- Expected reboot or no reboot
- Maintenance window
- Rollback command
- Validation command
- Owner
- Git commit

### 17.10 Use `oc debug node`, not permanent SSH

For verification:

```bash
oc debug node/<node-name>
chroot /host
```

SSH can be useful in emergencies, but routine node changes should remain declarative.

## 18. Common Interview and Real-World Questions

### Q1. What is a custom MachineConfig?

A custom MachineConfig is a user-created MachineConfig object that declares host-level configuration for OpenShift nodes. It is applied by the Machine Config Operator to nodes belonging to the matching MachineConfigPool.

### Q2. What happens after applying a MachineConfig?

The MCO renders a new rendered MachineConfig for the target pool. The MCP enters updating state. The MCD on each affected node applies the new configuration, usually drains and reboots the node, then reports success. When all nodes match the desired rendered config, the MCP becomes updated.

### Q3. How does OpenShift decide which nodes receive a MachineConfig?

The MachineConfig has a label such as:

```yaml
machineconfiguration.openshift.io/role: worker
```

The MCP has a `machineConfigSelector` that selects MachineConfigs for that role and a `nodeSelector` that selects nodes managed by the pool.

### Q4. Can a node belong to multiple MCPs?

No. A node can have multiple labels, but it is managed by only one MCP. Custom pools take priority over the default worker pool when matching node labels.

### Q5. Why does applying a MachineConfig reboot nodes?

Many MachineConfig changes affect host OS state, systemd, kernel arguments, kubelet, CRI-O, or files that need a reboot to guarantee consistent node state. The MCO orchestrates this with drain, apply, reboot, and uncordon.

### Q6. How do you know whether a MachineConfig applied successfully?

Check:

```bash
oc get mcp
oc describe mcp <pool>
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig
```

Then verify the actual file or service on the node with `oc debug node`.

### Q7. What is configuration drift?

Configuration drift occurs when a file, systemd unit, or permission managed by MachineConfig is manually changed on the node. The MCD detects the mismatch and can mark the node and MCP as degraded.

### Q8. How do you recover from MCP Degraded due to content mismatch?

1. Identify the degraded node and reason.
2. Compare the file on disk with MachineConfig expected content.
3. Restore the file manually or update the MachineConfig.
4. Wait for MCD to detect recovery or reapply safely.
5. Confirm MCP returns to healthy state.

### Q9. Should kubelet settings be changed through MachineConfig directly?

Usually no. Use `KubeletConfig`. The MCO generates the necessary MachineConfig and integrates the change with supported OpenShift lifecycle behavior.

### Q10. Should CRI-O settings be changed through MachineConfig directly?

Usually no. Use `ContainerRuntimeConfig` for supported CRI-O settings.

### Q11. What is the risk of applying custom MachineConfig to `master`?

It can reboot control plane nodes. If the config is wrong, API server, etcd, scheduler, or controller-manager stability can be affected. Always test, review, and apply during a proper maintenance window.

### Q12. Why use Butane?

Butane provides readable source syntax and validation. It converts a simple YAML-like config into the MachineConfig format expected by OpenShift and Ignition.

## Final Senior-Admin Summary

A custom MachineConfig is powerful because it changes real host operating system state across OpenShift nodes. It is also risky because a bad MachineConfig can drain, reboot, degrade, or even break nodes.

For advanced administration, remember this decision model:

```text
Need to change host file or systemd?        -> MachineConfig
Need kubelet parameter?                     -> KubeletConfig
Need CRI-O runtime parameter?               -> ContainerRuntimeConfig
Need performance/sysctl tuning?             -> Node Tuning Operator
Need app config?                            -> Kubernetes ConfigMap/Secret/Operator CR
Need special subset of workers?             -> Custom MachineConfigPool
Need to test risky node change?             -> One-node custom MCP first
```

The best OpenShift administrators do not manually customize nodes. They define node state declaratively, test through custom pools, monitor MCP health, and keep every MachineConfig in Git with a rollback plan.
