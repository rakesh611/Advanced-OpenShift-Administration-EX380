# Custom systemd Unit through MachineConfig

**Topic:** MachineConfig and Node-Level Administration  
**Audience:** Advanced OpenShift Administration / DO380-style preparation  
**Level:** Senior Linux/OpenShift administrator, ~10 years experience  
**Focus:** How to create, deploy, verify, troubleshoot, and roll back a custom `systemd` unit on OpenShift nodes by using `MachineConfig`.

---

## 1. Executive Summary

In OpenShift 4, cluster nodes usually run **Red Hat Enterprise Linux CoreOS (RHCOS)**. RHCOS is intentionally managed as part of the OpenShift cluster lifecycle. You should not treat nodes like traditional manually configured RHEL servers. Instead of SSHing to each node and editing `/etc/systemd/system/*.service`, you manage node-level operating system configuration declaratively through the **Machine Config Operator (MCO)**.

A **MachineConfig** can be used to:

- create a new `systemd` service,
- enable or disable a service,
- mask an existing service,
- add a `systemd` drop-in to an existing service,
- place supporting files under supported paths such as `/etc` and `/var`,
- apply the configuration consistently to all nodes in a MachineConfigPool.

For custom `systemd` units, the most important idea is this:

> A `MachineConfig` does not simply run a command once. It declares the desired node operating-system configuration. The MCO renders that configuration, rolls it out through the matching MachineConfigPool, and normally drains and reboots affected nodes so the new node state becomes authoritative.

---

## 2. Why Use MachineConfig for systemd Units?

In a normal Linux environment, you might do this:

```bash
sudo vi /etc/systemd/system/my-agent.service
sudo systemctl daemon-reload
sudo systemctl enable --now my-agent.service
```

On OpenShift RHCOS nodes, that approach is operationally unsafe because:

1. **Manual node changes are not declarative.**
   If the node is replaced, the change is lost.

2. **Manual changes can create configuration drift.**
   If the file is managed by MachineConfig and someone modifies it manually, the MCD can mark the node or pool as degraded.

3. **OpenShift upgrades include OS configuration.**
   Node-level configuration must move with the cluster lifecycle.

4. **Consistency matters.**
   A node pool should not have five workers configured one way and three workers configured another way unless that is intentionally modeled by separate MachineConfigPools.

5. **Auditing and GitOps become possible.**
   The YAML definition becomes the source of truth.

Use MachineConfig when the requirement is truly node-level, for example:

- running a small host-level boot-time initialization service,
- applying a host-specific service drop-in,
- enabling/disabling an existing RHCOS service,
- running a host-level agent that cannot be represented cleanly as a Kubernetes DaemonSet,
- integrating with infrastructure requirements that must exist before regular workloads start.

Do **not** use a custom systemd unit just because it feels familiar from RHEL administration. In OpenShift, a DaemonSet is often better for software that monitors nodes, collects logs, exports metrics, or runs application-side helper logic.

## 3. MachineConfig, MCO, MCD, and MCP Relationship

### 3.1 Core Objects

| Component | Meaning |
|---|---|
| `MachineConfig` | Declarative node OS configuration. It can define files, systemd units, kernel args, users, and other Ignition-backed settings. |
| `MachineConfigPool` / MCP | A group of nodes that receive a rendered MachineConfig, usually `master` or `worker`. Custom pools are also possible. |
| Machine Config Operator / MCO | Cluster operator that manages machine configuration lifecycle. |
| Machine Config Controller | Renders MachineConfigs into final rendered configs per pool. |
| Machine Config Daemon / MCD | Runs on each node and applies the desired rendered config to the host. |
| Rendered MachineConfig | Generated MachineConfig like `rendered-worker-xxxxx`. Do not edit it manually. |

### 3.2 Rollout Flow

When you apply a custom `MachineConfig` for worker nodes:

```text
Admin applies MachineConfig
        |
        v
MCO detects new MachineConfig
        |
        v
Machine Config Controller renders a new rendered-worker-xxxxx config
        |
        v
worker MachineConfigPool desiredConfig changes
        |
        v
MCD on each worker sees desiredConfig != currentConfig
        |
        v
MCO/MCD updates nodes one by one based on MCP maxUnavailable
        |
        v
Node is cordoned/drained if needed
        |
        v
Files/systemd units are written to host
        |
        v
Node usually reboots
        |
        v
Node comes back, validates config, uncordons
        |
        v
MCP becomes Updated=True, Degraded=False
```

### 3.3 Important Operational Point

A MachineConfig change is not like applying a ConfigMap to a pod. It can affect the operating system and usually causes node disruption. Plan MachineConfig rollout like a node maintenance event.

## 4. Where systemd Unit Configuration Lives in MachineConfig

A systemd unit is defined under:

```yaml
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: my-service.service
          enabled: true
          contents: |
            [Unit]
            Description=My custom service

            [Service]
            Type=oneshot
            ExecStart=/usr/bin/echo Hello

            [Install]
            WantedBy=multi-user.target
```

### 4.1 Key Fields

| Field | Meaning |
|---|---|
| `name` | systemd unit name. It must include a valid suffix such as `.service`, `.timer`, `.socket`, `.mount`, etc. |
| `enabled` | Whether the unit should be enabled. For a service, the unit normally needs a valid `[Install]` section. |
| `contents` | Full unit file content. This creates or replaces the unit definition under systemd management. |
| `dropins` | Drop-in fragments for an existing unit. Prefer this when only overriding part of an existing service. |
| `masked` | Prevents a unit from being started manually or by dependency. Useful for hard-disabling a service. |

### 4.2 Full Unit vs Drop-in

Use a **full unit** when you are creating a new service:

```yaml
systemd:
  units:
    - name: custom-node-init.service
      enabled: true
      contents: |
        [Unit]
        Description=Custom node init

        [Service]
        Type=oneshot
        ExecStart=/usr/bin/true

        [Install]
        WantedBy=multi-user.target
```

Use a **drop-in** when the unit already exists and you only want to modify a small part of it:

```yaml
systemd:
  units:
    - name: sshd.service
      dropins:
        - name: 10-custom-options.conf
          contents: |
            [Service]
            Environment=EXAMPLE_MANAGED_BY_MACHINECONFIG=true
```

Senior-admin rule:

> Do not copy an entire vendor-managed unit into MachineConfig unless you really intend to own the whole unit definition. Prefer drop-ins for existing services.

## 5. Direct MachineConfig Example: Custom Boot Marker Service

This example creates a small oneshot service on worker nodes. It creates a marker file in `/var/lib/custom-node-banner/initialized` during boot.

This is a safe demonstration service because it does not modify cluster-critical components.

> Adjust the Ignition version according to your OpenShift version. In many OCP 4.16-style labs you will see `3.4.0`. Newer versions may use a newer Ignition version. You can check your cluster with `oc get mc 00-worker -o jsonpath='{.spec.config.ignition.version}'`.

Create `99-worker-custom-node-banner.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-custom-node-banner
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: custom-node-banner.service
          enabled: true
          contents: |
            [Unit]
            Description=Custom node boot marker managed by MachineConfig
            Documentation=man:systemd.service(5)
            Wants=network-online.target
            After=network-online.target
            ConditionPathExists=!/var/lib/custom-node-banner/initialized

            [Service]
            Type=oneshot
            ExecStartPre=/usr/bin/mkdir -p /var/lib/custom-node-banner
            ExecStart=/usr/bin/bash -c 'echo "Custom MachineConfig boot initialization: $(date -Is)" > /var/lib/custom-node-banner/initialized'
            RemainAfterExit=yes

            [Install]
            WantedBy=multi-user.target
```

Apply it:

```bash
oc apply -f 99-worker-custom-node-banner.yaml
```

Monitor rollout:

```bash
oc get mcp
oc describe mcp worker
watch -n5 'oc get mcp worker; oc get nodes'
```

Verify on a worker node:

```bash
NODE=$(oc get nodes -l node-role.kubernetes.io/worker -o name | head -n1)

echo "$NODE"

oc debug "$NODE" -- chroot /host systemctl status custom-node-banner.service --no-pager
oc debug "$NODE" -- chroot /host systemctl is-enabled custom-node-banner.service
oc debug "$NODE" -- chroot /host cat /var/lib/custom-node-banner/initialized
```

Expected result:

```text
custom-node-banner.service is enabled
/var/lib/custom-node-banner/initialized exists
MachineConfigPool worker becomes Updated=True
```

## 6. Butane-Based Example: Recommended Production Workflow

Writing raw MachineConfig YAML is useful for exams and quick labs, but for production you should normally use **Butane**. Butane lets you write readable YAML and generate the MachineConfig/Ignition output.

Create `99-worker-custom-node-banner.bu`:

```yaml
variant: openshift
version: 4.16.0
metadata:
  name: 99-worker-custom-node-banner
  labels:
    machineconfiguration.openshift.io/role: worker
systemd:
  units:
    - name: custom-node-banner.service
      enabled: true
      contents: |
        [Unit]
        Description=Custom node boot marker managed by MachineConfig
        Wants=network-online.target
        After=network-online.target
        ConditionPathExists=!/var/lib/custom-node-banner/initialized

        [Service]
        Type=oneshot
        ExecStartPre=/usr/bin/mkdir -p /var/lib/custom-node-banner
        ExecStart=/usr/bin/bash -c 'echo "Custom MachineConfig boot initialization: $(date -Is)" > /var/lib/custom-node-banner/initialized'
        RemainAfterExit=yes

        [Install]
        WantedBy=multi-user.target
```

Generate the MachineConfig:

```bash
butane --pretty --strict 99-worker-custom-node-banner.bu -o 99-worker-custom-node-banner.yaml
```

Apply it:

```bash
oc apply -f 99-worker-custom-node-banner.yaml
```

Why Butane is better:

- cleaner source YAML,
- easier review in Git,
- validates common mistakes,
- avoids manually building complex Ignition structures,
- better for files, drop-ins, directories, and local file embedding.

## 7. Example: Custom systemd Timer and Service

A timer is useful when you want a periodic host-level action without running a constantly active daemon.

Example requirement:

> Every 10 minutes, write a timestamp to `/var/log/custom-node-heartbeat.log` on each worker node.

Create `99-worker-node-heartbeat.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-node-heartbeat
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: custom-node-heartbeat.service
          contents: |
            [Unit]
            Description=Write custom node heartbeat timestamp

            [Service]
            Type=oneshot
            ExecStart=/usr/bin/bash -c 'echo "$(date -Is) $(hostname) custom heartbeat" >> /var/log/custom-node-heartbeat.log'

        - name: custom-node-heartbeat.timer
          enabled: true
          contents: |
            [Unit]
            Description=Run custom node heartbeat every 10 minutes

            [Timer]
            OnBootSec=2min
            OnUnitActiveSec=10min
            Unit=custom-node-heartbeat.service
            Persistent=true

            [Install]
            WantedBy=timers.target
```

Apply and verify:

```bash
oc apply -f 99-worker-node-heartbeat.yaml

oc get mcp worker

NODE=$(oc get nodes -l node-role.kubernetes.io/worker -o name | head -n1)
oc debug "$NODE" -- chroot /host systemctl status custom-node-heartbeat.timer --no-pager
oc debug "$NODE" -- chroot /host systemctl list-timers --all | grep custom-node-heartbeat
oc debug "$NODE" -- chroot /host tail -n5 /var/log/custom-node-heartbeat.log
```

Production note:

- A timer is often safer than a long-running custom daemon.
- Keep timer actions short and idempotent.
- Avoid writing excessive logs to the host.

## 8. Example: systemd Drop-in for an Existing Unit

A drop-in is normally safer than replacing a full vendor unit.

Example skeleton:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example-dropin
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: example-existing.service
          dropins:
            - name: 10-custom-override.conf
              contents: |
                [Service]
                Environment=MANAGED_BY_MACHINECONFIG=true
```

For a real existing service, first inspect it:

```bash
NODE=$(oc get nodes -l node-role.kubernetes.io/worker -o name | head -n1)
oc debug "$NODE" -- chroot /host systemctl cat <service-name>.service
```

Then create only the minimum drop-in required.

Common drop-in use cases:

- add environment variables,
- override service limits,
- add `ExecStartPre`,
- modify restart behavior,
- adjust ordering dependencies.

Be careful with `ExecStart` overrides. In systemd, overriding `ExecStart` usually requires clearing the old value first:

```ini
[Service]
ExecStart=
ExecStart=/new/command --with --args
```

Do not do this blindly for critical services such as `kubelet.service`, `crio.service`, or `NetworkManager.service`. For kubelet and CRI-O configuration, prefer the supported OpenShift APIs such as `KubeletConfig` and `ContainerRuntimeConfig` unless Red Hat documentation specifically directs otherwise.

## 9. Example: Disable or Mask an Existing Service

### 9.1 Disable Service

Disabling means the service is not enabled to start at boot, but it might still be started manually or by another unit.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-disable-example-service
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: example.service
          enabled: false
```

### 9.2 Mask Service

Masking is stronger. It prevents the unit from being started.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-mask-example-service
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: example.service
          masked: true
```

Senior-admin warning:

> Do not disable or mask core OpenShift node services unless you know the support implications. Disabling the wrong service can make nodes NotReady or unbootable.

## 10. Applying to Master vs Worker Nodes

### Worker Nodes

For workers:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

This targets the `worker` MachineConfigPool.

### Control Plane / Master Nodes

For control plane nodes:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: master
```

Be much more careful on master nodes because a bad MachineConfig can affect API availability, etcd quorum, ingress to control-plane services, upgrades, and recovery options.

Before applying to master nodes:

```bash
oc get co
oc get mcp master
oc get nodes -l node-role.kubernetes.io/master
oc get clusterversion
```

Recommended approach:

1. Test on a non-production cluster.
2. Test on a custom worker pool first if possible.
3. Apply to workers before masters when the requirement allows.
4. Confirm MCP is healthy before making the next change.
5. Keep rollback YAML ready.

## 11. Custom MachineConfigPool Strategy

For production-grade node-level changes, do not always target all workers. Create a custom MCP when only a subset of nodes needs the custom unit.

Example node labels:

```bash
oc label node worker-1.example.com node-role.kubernetes.io/infra=
oc label node worker-2.example.com node-role.kubernetes.io/infra=
```

Example custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Then target the custom pool with:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

This is useful for:

- infra nodes,
- GPU nodes,
- storage nodes,
- edge nodes,
- nodes requiring vendor-specific host agents.

## 12. Rollout Control

### 12.1 Watch MCP Status

```bash
oc get mcp
oc describe mcp worker
```

Important MCP conditions:

| Condition | Meaning |
|---|---|
| `Updated=True` | Pool has fully applied desired rendered config. |
| `Updating=True` | Rollout is in progress. |
| `Degraded=True` | At least one node failed to apply or validate config. |
| `MachineCount` | Total nodes in pool. |
| `UpdatedMachineCount` | Nodes already updated. |
| `ReadyMachineCount` | Nodes ready. |
| `UnavailableMachineCount` | Nodes unavailable during rollout. |

### 12.2 Check Rendered Config

```bash
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
oc get mc | grep rendered-worker
```

### 12.3 Check Node Annotations

```bash
NODE=<node-name>

oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

Typical states:

- `Done`
- `Working`
- `Degraded`

### 12.4 Pause a Pool Before Applying Multiple Changes

You can pause a pool to prevent immediate rollout while preparing several MachineConfigs.

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Apply your MachineConfigs:

```bash
oc apply -f 99-worker-custom-node-banner.yaml
oc apply -f 99-worker-node-heartbeat.yaml
```

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Warning:

- Do not forget paused pools.
- Paused MCPs can block node OS/config rollout and upgrades.
- Use pause intentionally and document it.

## 13. Reboot and Disruption Behavior

For most MachineConfig changes, the MCO drains and reboots the affected nodes. This is normal.

The practical impact is:

- workloads are evicted from a worker node during drain,
- PodDisruptionBudgets can delay or block drain,
- DaemonSet pods are handled differently from normal workload pods,
- one or more nodes can be unavailable depending on `maxUnavailable`,
- a bad unit can cause post-reboot service failure or node readiness issues.

### 13.1 Why a Reboot Happens

A systemd unit change is host OS state. The MCO generally reboots nodes so the entire node state is consistently applied and validated from boot.

### 13.2 Node Disruption Policy

OpenShift supports node disruption policies through the `MachineConfiguration` object. These policies can define whether certain MachineConfig changes require actions such as:

- `Reboot`
- `Drain`
- `None`
- `Reload`
- `Restart`
- `DaemonReload`

Example concept for a systemd unit:

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
  namespace: openshift-machine-config-operator
spec:
  nodeDisruptionPolicy:
    units:
      - name: custom-node-banner.service
        actions:
          - type: DaemonReload
          - type: Restart
            restart:
              serviceName: custom-node-banner.service
```

Production caution:

- Use node disruption policies only when you fully understand the effect.
- If another change in the same rendered config requires reboot, the reboot still wins.
- Do not use no-reboot logic for changes that actually need boot-time validation.

## 14. Production Design Guidelines

### 14.1 Prefer Kubernetes-Native First

Before writing a custom systemd unit, ask:

| Requirement | Better Option |
|---|---|
| Run an agent on every node | DaemonSet |
| Collect logs | OpenShift Logging / Vector / supported logging stack |
| Export metrics | DaemonSet + ServiceMonitor |
| Tune kernel/sysctl | MachineConfig or Node Tuning Operator depending on setting |
| Configure kubelet | `KubeletConfig` |
| Configure CRI-O | `ContainerRuntimeConfig` |
| Configure files under `/etc` or `/var` | MachineConfig |
| Boot-time host initialization | MachineConfig + systemd unit |

Use systemd through MachineConfig when you need host lifecycle integration, not just “run a process somewhere.”

### 14.2 Keep Units Idempotent

A systemd unit managed by MachineConfig should be safe to run more than once.

Good pattern:

```ini
ConditionPathExists=!/var/lib/my-service/initialized
ExecStartPre=/usr/bin/mkdir -p /var/lib/my-service
ExecStart=/usr/bin/bash -c 'do-something && touch /var/lib/my-service/initialized'
```

Bad pattern:

```ini
ExecStart=/usr/bin/bash -c 'append duplicate config every boot'
```

### 14.3 Avoid Blocking Boot

Avoid long-running `oneshot` units before important targets unless necessary.

Dangerous patterns:

```ini
Before=kubelet.service
ExecStart=/usr/bin/curl https://external-site.example.com/big-file
TimeoutStartSec=0
```

Why dangerous:

- external dependency can hang boot,
- kubelet may not start,
- node may stay NotReady,
- MCO rollout can become stuck.

### 14.4 Use Fully Qualified Paths

Systemd does not behave like an interactive shell. Use full paths:

```ini
ExecStart=/usr/bin/bash -c 'echo ok'
```

Do not rely on `$PATH`.

### 14.5 Avoid Unsupported Host Mutations

MachineConfig is supported primarily for writing under `/etc` and `/var`. Do not assume arbitrary writes under `/usr` are safe. RHCOS uses an immutable OS model, and `/usr` is generally managed by the OS image.

### 14.6 Keep Secrets Out of MachineConfig

Do not embed plain-text credentials in MachineConfig unit files. MachineConfigs are cluster-visible resources and may be readable by users with sufficient RBAC.

Better options:

- use Kubernetes Secrets with a DaemonSet,
- use pull secrets only through supported mechanisms,
- integrate with supported node identity mechanisms,
- store only non-sensitive configuration in MachineConfig.

### 14.7 Make Logs Useful but Small

For custom services:

```ini
StandardOutput=journal
StandardError=journal
```

Then inspect with:

```bash
oc debug node/<node> -- chroot /host journalctl -u <unit-name> -b --no-pager
```

Avoid uncontrolled writes to `/var/log`.

## 15. Advanced Example: Running a Containerized Host Agent with systemd

This is an advanced pattern. Prefer a DaemonSet unless the process must run as a host-managed service outside normal Kubernetes workload scheduling.

Example skeleton:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-custom-host-agent
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: custom-host-agent.service
          enabled: true
          contents: |
            [Unit]
            Description=Custom containerized host agent
            Wants=network-online.target
            After=network-online.target

            [Service]
            Type=simple
            Restart=always
            RestartSec=30s
            TimeoutStartSec=120s
            ExecStartPre=-/usr/bin/podman rm -f custom-host-agent
            ExecStart=/usr/bin/podman run --name custom-host-agent --rm --net=host --privileged registry.example.com/infra/custom-host-agent:v1.0
            ExecStop=/usr/bin/podman stop -t 10 custom-host-agent

            [Install]
            WantedBy=multi-user.target
```

Production cautions:

- Use an internal registry or mirrored image.
- Ensure image pull credentials are handled through supported mechanisms.
- Avoid `--privileged` unless truly required.
- Consider SELinux, host networking, cgroups, logging, restart storms, and upgrade behavior.
- A DaemonSet is usually easier to observe, update, secure, and roll back.

## 16. Validation Checklist Before Applying

Before applying a custom systemd MachineConfig, check:

### YAML and MachineConfig

```bash
oc apply --dry-run=server -f 99-worker-custom-node-banner.yaml
```

Check target pool label:

```bash
oc get mcp
oc get nodes --show-labels | grep 'node-role.kubernetes.io/worker'
```

Check existing MachineConfigs:

```bash
oc get mc
```

### Cluster Health

```bash
oc get co
oc get clusterversion
oc get mcp
oc get nodes
```

Do not apply risky MachineConfig changes when:

- ClusterOperators are degraded,
- MCP is already degraded,
- nodes are NotReady,
- upgrade is in progress,
- there are critical workload disruptions,
- PDBs are likely to block drain.

### systemd Unit Syntax

You cannot fully validate the target node service from the API server, but you can test on a similar RHEL/RHCOS node or validate after rollout:

```bash
systemd-analyze verify custom-node-banner.service
```

After rollout on a node:

```bash
oc debug node/<node> -- chroot /host systemd-analyze verify /etc/systemd/system/custom-node-banner.service
```

## 18. Troubleshooting

### 18.1 MCP Stuck Updating

Check:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
```

Common causes:

- node cannot drain due to PodDisruptionBudget,
- node is NotReady,
- MachineConfig has invalid content,
- MCD failed applying config,
- service causes node boot/readiness problem,
- underlying infrastructure issue.

Check MCD logs:

```bash
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide

POD=<machine-config-daemon-pod-on-affected-node>
oc logs -n openshift-machine-config-operator "$POD" -c machine-config-daemon --since=2h
```

### 18.2 MCP Degraded

```bash
oc describe mcp worker
```

Look for messages such as:

- failed to drain node,
- content mismatch,
- failed to update OS to rendered config,
- unexpected on-disk state,
- failed validating against current config.

### 18.3 Unit Exists but Service Failed

The MCO may successfully apply the unit, but the service itself can fail at runtime.

Check:

```bash
oc debug node/<node> -- chroot /host systemctl status <unit>.service --no-pager
oc debug node/<node> -- chroot /host journalctl -u <unit>.service -b --no-pager
```

Common service failures:

| Symptom | Possible Cause |
|---|---|
| `command not found` | Wrong binary path or package not present on RHCOS. |
| `permission denied` | SELinux, file mode, mount option, or wrong user. |
| `dependency failed` | Bad `After=`, `Requires=`, or missing target/service. |
| `start request repeated too quickly` | Restart loop. |
| `unit not found` | Wrong unit name or MachineConfig not applied to that node. |
| `not enabled` | Missing `[Install]` section or `enabled` not set. |

### 18.4 Service Not Enabled

Check whether the unit has `[Install]`:

```bash
oc debug node/<node> -- chroot /host systemctl cat <unit>.service
```

A service with `enabled: true` usually needs:

```ini
[Install]
WantedBy=multi-user.target
```

For timers:

```ini
[Install]
WantedBy=timers.target
```

### 18.5 Wrong Pool Targeted

If the MachineConfig has the wrong label, it will not apply to the expected pool.

Check:

```bash
oc get mc 99-worker-custom-node-banner --show-labels
oc get mcp worker -o yaml | less
```

Correct label for workers:

```yaml
machineconfiguration.openshift.io/role: worker
```

Correct label for masters:

```yaml
machineconfiguration.openshift.io/role: master
```

### 18.6 Configuration Drift

If someone manually edits a file managed by MachineConfig, the MCD can mark the node degraded.

Example bad practice:

```bash
oc debug node/worker-1
chroot /host
vi /etc/systemd/system/custom-node-banner.service
```

Correct approach:

1. Update the MachineConfig YAML in Git.
2. Apply the changed MachineConfig.
3. Let MCO roll out the new rendered config.

If drift already happened:

```bash
oc describe mcp worker
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Then restore the exact expected content or update the MachineConfig properly.

## 19. Rollback Procedure

### 19.1 If You Added a New MachineConfig

Delete it:

```bash
oc delete mc 99-worker-custom-node-banner
```

Watch rollback:

```bash
watch -n5 'oc get mcp worker; oc get nodes'
```

The MCO renders a new config without your custom unit and rolls the pool back. This usually causes another drain/reboot cycle.

### 19.2 If You Modified an Existing MachineConfig

Reapply the previous version from Git:

```bash
oc apply -f previous-good-99-worker-custom-node-banner.yaml
```

### 19.3 Do Not Edit Rendered MachineConfigs

Never do this:

```bash
oc edit mc rendered-worker-xxxxx
```

Rendered configs are generated output. Edit the source MachineConfig instead.

### 19.4 Emergency Worker Recovery

If a worker node is broken because of a bad custom unit:

1. Delete or fix the bad MachineConfig.
2. Wait for other nodes to recover.
3. If a worker cannot return, replace/reprovision the worker node if your platform supports that cleanly.
4. Avoid manual host edits except as a temporary recovery action.

For master/control-plane nodes, use extreme caution and follow Red Hat-supported recovery procedures. A bad MachineConfig on masters can become a cluster availability incident.

## 20. Naming and Ordering Best Practices

MachineConfig names often start with numbers:

```text
00-worker
01-worker-kubelet
99-worker-custom-node-banner
```

General convention:

| Prefix | Meaning |
|---|---|
| `00-` | Base configs. Usually generated/managed by OpenShift. |
| `01-` | Cluster-managed kubelet/container runtime config. |
| `50-` | Optional custom mid-priority configs. |
| `99-` | Late custom overrides. Common for admin-created MachineConfigs. |
| `rendered-*` | Generated final config. Do not edit. |

Use descriptive names:

```text
99-worker-custom-node-banner
99-worker-disable-chronyd
99-infra-vendor-agent
99-master-auditd-dropin
```

Avoid vague names:

```text
test
newmc
fix1
machineconfig-final
```

## 21. Security Considerations

### 21.1 RBAC

Creating MachineConfigs is a cluster-admin-level operation. It can change the OS state of nodes. Limit permissions carefully.

### 21.2 Secrets

MachineConfig content is visible through the Kubernetes API to users with appropriate read access. Do not embed secrets.

Bad:

```ini
Environment=PASSWORD=SuperSecret123
```

Better:

- use supported secret distribution,
- use DaemonSet with Kubernetes Secret volume,
- use external identity/secret mechanism,
- avoid host-level secret handling unless required and approved.

### 21.3 SELinux

RHCOS uses SELinux. A unit might work in a lab and fail in production because of labels, paths, or privilege assumptions.

Check denials:

```bash
oc debug node/<node> -- chroot /host journalctl -t setroubleshoot --no-pager
oc debug node/<node> -- chroot /host ausearch -m avc -ts recent
```

If `ausearch` is unavailable, inspect journal logs:

```bash
oc debug node/<node> -- chroot /host journalctl -b | grep -i denied
```

Do not disable SELinux on RHCOS in production.

### 21.4 Supply Chain

If the unit starts a binary or container image:

- use trusted registries,
- pin versions,
- use digest references where possible,
- mirror images for disconnected clusters,
- validate signatures if your environment requires it.

## 22. Exam and Interview Notes

### 22.1 What the Examiner/Interviewer Expects

You should be able to explain:

1. MachineConfig is the declarative way to change node OS configuration.
2. `systemd.units` is inside `spec.config` because MachineConfig uses Ignition-style configuration.
3. A role label decides which MCP gets the MachineConfig.
4. MCO renders a new config and rolls it out pool by pool.
5. Nodes usually drain and reboot after MachineConfig changes.
6. You verify through `oc get mcp`, node annotations, MCD logs, and `oc debug node`.
7. You roll back by deleting or reverting the source MachineConfig, not the rendered config.
8. For existing services, drop-ins are safer than replacing full units.
9. For app-like agents, DaemonSet may be better than systemd.
10. Manual host edits can cause drift and degraded MCP.

### 22.2 One-Line Definition

> A custom systemd unit through MachineConfig means declaring a systemd service, timer, socket, mount, or drop-in inside a MachineConfig so the Machine Config Operator applies it consistently to all nodes in the targeted MachineConfigPool.

### 22.3 Quick Command Set

```bash
# list pools
oc get mcp

# list machine configs
oc get mc

# apply custom systemd unit
oc apply -f 99-worker-custom-node-banner.yaml

# watch rollout
watch -n5 'oc get mcp worker; oc get nodes'

# check rendered config
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'

# check node current/desired config
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'

# debug systemd on node
oc debug node/<node> -- chroot /host systemctl status custom-node-banner.service --no-pager
oc debug node/<node> -- chroot /host journalctl -u custom-node-banner.service -b --no-pager

# rollback
oc delete mc 99-worker-custom-node-banner
```

## 23. Common Mistakes and Fixes

| Mistake | Result | Fix |
|---|---|---|
| Missing role label | MachineConfig not applied to desired pool | Add `machineconfiguration.openshift.io/role: worker` or `master`. |
| Editing rendered MC | Change lost or unsupported behavior | Edit source MC only. |
| Bad YAML indentation | API rejection or wrong config | Validate with dry-run/server and Butane. |
| Missing `[Install]` section | `enabled: true` may fail | Add `WantedBy=multi-user.target` or correct target. |
| Unit depends on internet | Node boot/update may hang | Mirror dependencies or avoid boot-time external calls. |
| Long-running oneshot | Boot delays or node NotReady | Use `Type=simple` for daemon or timer for periodic task. |
| Manual edit on node | Drift and MCP degraded | Update MachineConfig declaratively. |
| Targeting masters casually | Control plane risk | Test first and use change window. |
| Putting secrets in unit file | Secret exposure | Use Kubernetes Secret/DaemonSet or supported secret mechanism. |
| Replacing full vendor unit | Upgrade fragility | Use drop-ins where possible. |

## 24. Real-World Decision Matrix

| Requirement | Use MachineConfig systemd? | Reason |
|---|---:|---|
| Run log collector on every node | Usually no | DaemonSet is more Kubernetes-native. |
| Add host boot marker | Yes | Boot lifecycle is host-level. |
| Modify existing systemd service setting | Yes, with drop-in | Declarative and pool-wide. |
| Change kubelet config | Usually no | Use `KubeletConfig`. |
| Change CRI-O config | Usually no | Use `ContainerRuntimeConfig` where supported. |
| Start vendor host agent before kubelet | Maybe | Valid if vendor requires host boot integration. |
| One-time app initialization | No | Use Job/init container/application logic. |
| Node-specific debugging command | No | Use `oc debug node`. |
| Disable an unnecessary service | Maybe | Must understand support and dependency impact. |

## 25. End-to-End Lab

### Objective

Create a custom service on worker nodes, verify it, then roll it back.

### Step 1: Check Health

```bash
oc get co
oc get mcp
oc get nodes
```

### Step 2: Create YAML

```bash
cat > 99-worker-custom-node-banner.yaml <<'EOF_YAML'
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-custom-node-banner
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
        - name: custom-node-banner.service
          enabled: true
          contents: |
            [Unit]
            Description=Custom node boot marker managed by MachineConfig
            Wants=network-online.target
            After=network-online.target
            ConditionPathExists=!/var/lib/custom-node-banner/initialized

            [Service]
            Type=oneshot
            ExecStartPre=/usr/bin/mkdir -p /var/lib/custom-node-banner
            ExecStart=/usr/bin/bash -c 'echo "Custom MachineConfig boot initialization: $(date -Is)" > /var/lib/custom-node-banner/initialized'
            RemainAfterExit=yes

            [Install]
            WantedBy=multi-user.target
EOF_YAML
```

### Step 3: Dry Run

```bash
oc apply --dry-run=server -f 99-worker-custom-node-banner.yaml
```

### Step 4: Apply

```bash
oc apply -f 99-worker-custom-node-banner.yaml
```

### Step 5: Watch Rollout

```bash
watch -n5 'oc get mcp worker; oc get nodes'
```

### Step 6: Verify on Node

```bash
NODE=$(oc get nodes -l node-role.kubernetes.io/worker -o name | head -n1)

oc debug "$NODE" -- chroot /host systemctl status custom-node-banner.service --no-pager
oc debug "$NODE" -- chroot /host cat /var/lib/custom-node-banner/initialized
```

### Step 7: Roll Back

```bash
oc delete mc 99-worker-custom-node-banner
watch -n5 'oc get mcp worker; oc get nodes'
```

### Step 8: Confirm Removal

```bash
oc debug "$NODE" -- chroot /host systemctl status custom-node-banner.service --no-pager
```

Depending on how systemd state and files were rendered/removed, the unit should no longer be part of the current rendered MachineConfig after rollback. Always verify through the MCP and rendered config, not only by checking one node.

## 26. Key Takeaways

- MachineConfig is the correct OpenShift-native mechanism for node OS configuration.
- Custom systemd units belong under `spec.config.systemd.units`.
- Role labels decide whether the config targets `worker`, `master`, or a custom MCP.
- MCO renders configs and MCD applies them on each node.
- Most MachineConfig changes cause drain and reboot.
- Use Butane for production readability and validation.
- Prefer drop-ins over replacing existing unit files.
- Prefer DaemonSets over systemd for Kubernetes-style agents.
- Never edit rendered MachineConfigs.
- Avoid manual host edits because they can cause configuration drift.
- Always keep rollback YAML ready before applying risky node-level changes.
