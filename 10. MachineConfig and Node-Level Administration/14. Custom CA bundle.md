# Custom CA Bundle in MachineConfig and Node-Level Administration

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and RHCA/RH280/RH380-level learners with production Linux/Kubernetes experience.  
**Scope:** OpenShift Container Platform 4.x, RHCOS nodes, Machine Config Operator, cluster-wide trust, registry trust, proxy trust, workload trust, troubleshooting, and production runbooks.  
**Assumption:** You already understand Linux CA trust stores, Kubernetes ConfigMaps, OpenShift Operators, MachineConfigPools, and node drain/reboot concepts.

---

## 1. Executive Summary

A **custom CA bundle** in OpenShift is a group of trusted Certificate Authority certificates that the cluster, nodes, platform components, image runtime, Operators, or workloads can use to validate TLS certificates signed by an internal or private PKI.

In real enterprises, this is required for:

- Internal HTTPS proxies performing TLS inspection.
- Private image registries using internal CA-signed certificates.
- Internal artifact repositories such as Nexus, Artifactory, GitLab, Harbor, Quay, or JFrog.
- Disconnected or restricted OpenShift installations.
- Internal APIs consumed by Operators or platform components.
- Corporate PKI where root/intermediate CAs are not in the default RHCOS trust bundle.

From a **MachineConfig and node-level administration** point of view, the custom CA bundle is not only a Kubernetes ConfigMap problem. It eventually affects the RHCOS node trust store, CRI-O, platform component trust, Operator trust, and sometimes application-level trust inside containers.

The most important rule is:

> Do not assume one CA configuration fixes every TLS error in OpenShift. OpenShift has multiple trust domains.

A CA used for image pulls, a CA used by platform Operators, a CA injected into application pods, and a CA placed into the RHCOS host trust store are related but not always identical.

---

## 2. What Is a Custom CA Bundle?

A **CA bundle** is a PEM-formatted file containing one or more CA certificates. These certificates are trusted roots or intermediates. They are not private keys and they are normally not leaf/server certificates.

Example format:

```pem
-----BEGIN CERTIFICATE-----
MIID...
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----
MIIF...
-----END CERTIFICATE-----
```

A custom CA bundle can contain:

- A corporate root CA.
- One or more intermediate CAs.
- A proxy signing CA.
- A private registry CA.
- A disconnected mirror registry CA.

It should not contain:

- Private keys.
- Encrypted private keys.
- Client certificates.
- Random server leaf certificates unless there is a very specific short-term exception.
- Expired CA certificates.
- Duplicate or malformed PEM blocks.

In OpenShift, the phrase **custom CA bundle** usually means a user-provided CA bundle stored in a ConfigMap and referenced by a cluster-scoped configuration object, commonly the `Proxy` object or the `Image` configuration object.

## 3. Why Custom CA Bundle Matters in Advanced Administration

In a small lab, TLS usually works because all endpoints use public CA certificates or cluster-generated certificates. In an enterprise, you frequently see this:

```text
x509: certificate signed by unknown authority
```

or:

```text
certificate verify failed
unable to get local issuer certificate
```

or:

```text
ImagePullBackOff: pinging container registry ... x509: certificate signed by unknown authority
```

A junior admin may try to bypass TLS with insecure flags. A senior OpenShift admin fixes the trust chain correctly.

Custom CA bundle administration is important because it impacts:

- Cluster installation.
- Cluster-wide proxy configuration.
- Image pull and image push behavior.
- MachineConfigPool rollout health.
- Operator installation and marketplace connectivity.
- Disconnected cluster upgrades.
- Builds using BuildConfig.
- Monitoring, logging, registry, authentication, and console Operators.
- Application pod connectivity to internal HTTPS services.
- Security and compliance posture.

In production, incorrect CA management can break upgrades, image pulls, Operator reconciliation, API calls, or node updates.

## 4. Mental Model: Trust Domains in OpenShift

OpenShift has multiple trust domains. This is the most important concept.

| Trust area | Main object/mechanism | Used by | Common symptom when missing |
|---|---|---|---|
| Cluster-wide platform egress trust | `Proxy/cluster.spec.trustedCA` referencing ConfigMap in `openshift-config` | Platform Operators and components that make HTTPS egress calls | Operators show degraded, `x509 unknown authority` |
| RHCOS host trust | Files under `/etc/pki/ca-trust/source/anchors/` managed by MCO | Host services, CRI-O, some node-level clients | Node-level `curl`/CRI-O trust failures |
| Image registry trust | `image.config.openshift.io/cluster.spec.additionalTrustedCA` | Image pulls/pushes, builds, image registry interactions | `ImagePullBackOff`, build pull failure |
| Workload/application trust | Injected ConfigMap with `config.openshift.io/inject-trusted-cabundle=true`, mounted into pod | Application containers | App cannot call internal HTTPS endpoint |
| Service serving certificate trust | ConfigMap annotation `service.beta.openshift.io/inject-cabundle=true` | Pods calling services using OpenShift service serving certs | Pod cannot verify service DNS certificate |
| API/Ingress custom serving certificates | Secrets referenced by API server/IngressController | Clients connecting to API/routes | Browser/API client sees untrusted endpoint |
| Kubelet/MCO/internal cluster certs | Managed by OpenShift/MCO | Internal node/control-plane communication | Node join, kubelet, MCO errors |

Senior-level point:

> A custom CA bundle is not a single switch. You must know which component is failing TLS and which trust store it actually reads.

## 5. How OpenShift Manages Custom CA Bundles Internally

At a high level, the cluster-wide CA flow looks like this:

```text
User CA PEM file
   ↓
ConfigMap in openshift-config
   ↓
Proxy/cluster.spec.trustedCA references the ConfigMap
   ↓
Cluster Network Operator validates and merges trust
   ↓
Merged trusted-ca-bundle is created/managed
   ↓
Machine Config Operator renders node config
   ↓
Machine Config Daemon applies file to RHCOS nodes
   ↓
update-ca-trust / coreos-update-ca-trust runs
   ↓
CRI-O and relevant platform components consume updated trust
```

Important objects involved:

```bash
oc get proxy/cluster -o yaml
oc get cm -n openshift-config
oc get cm -n openshift-config-managed
oc get controllerconfig/machine-config-controller -o yaml
oc get mcp
oc get machineconfignode
oc get mc
```

Important node path:

```text
/etc/pki/ca-trust/source/anchors/openshift-config-user-ca-bundle.crt
```

Important injected workload bundle key:

```text
ca-bundle.crt
```

Important Linux generated bundle path:

```text
/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

## 6. Custom CA Bundle Versus Server Certificate

Many production incidents happen because teams confuse these two:

| Item | Purpose | Stored as | Example |
|---|---|---|---|
| CA certificate | Trust issuer | ConfigMap or host trust anchor | Corporate root CA |
| Server certificate | Proves identity of endpoint | Secret with cert/key | `api.example.com` certificate |
| Client certificate | Proves client identity | Secret/kubeconfig | mTLS client cert |
| CA bundle | Collection of CA certs | PEM bundle | Root + intermediate chain |

A custom CA bundle does **not** replace the certificate used by the OpenShift API or router. It only teaches clients/components to trust certificates signed by that CA.

For example:

- To make the OpenShift API present a custom certificate, configure the API server named certificate.
- To make the router present a custom wildcard certificate, configure the IngressController default certificate.
- To make platform components trust your corporate HTTPS proxy, configure `Proxy/cluster.spec.trustedCA`.
- To make image pulls trust an internal registry, configure image additional trusted CA.

## 7. Preferred Methods to Add Custom CA Trust

### 7.1 Method 1: Add CA During Installation with `additionalTrustBundle`

Use this when you know before installation that the cluster must trust a corporate proxy, mirror registry, or internal PKI.

Example `install-config.yaml` snippet:

```yaml
apiVersion: v1
baseDomain: example.com
metadata:
  name: ocp4
additionalTrustBundle: |
  -----BEGIN CERTIFICATE-----
  <CORPORATE_ROOT_OR_INTERMEDIATE_CA>
  -----END CERTIFICATE-----
```

If you are also using an egress proxy:

```yaml
proxy:
  httpProxy: http://proxy.example.com:8080
  httpsProxy: http://proxy.example.com:8080
  noProxy: .cluster.local,.svc,10.128.0.0/14,10.0.0.0/8
additionalTrustBundle: |
  -----BEGIN CERTIFICATE-----
  <PROXY_SIGNING_CA>
  -----END CERTIFICATE-----
```

Newer installation workflows can also use policy behavior such as referencing the user CA bundle only when proxy is configured or always referencing it, depending on platform and install path.

Production advice:

- Add root and intermediate CAs in correct PEM format.
- Validate the chain before installation.
- Do not paste private keys.
- Keep a copy in source control or secure configuration management.
- Do not rely only on a browser export unless you confirm it is the issuing CA and not only the leaf certificate.

---

### 7.2 Method 2: Add CA to a Running Cluster with `Proxy/cluster.spec.trustedCA`

This is the normal day-2 method for cluster-wide trust.

Create a ConfigMap in `openshift-config`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: custom-ca-bundle
  namespace: openshift-config
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    <CORPORATE_OR_PROXY_CA_CERT>
    -----END CERTIFICATE-----
```

Apply it:

```bash
oc apply -f custom-ca-bundle.yaml
```

Patch the cluster Proxy object:

```bash
oc patch proxy/cluster --type=merge \
  --patch='{"spec":{"trustedCA":{"name":"custom-ca-bundle"}}}'
```

Verify:

```bash
oc get proxy/cluster -o yaml
oc get cm custom-ca-bundle -n openshift-config -o yaml
oc get cm trusted-ca-bundle -n openshift-config -o yaml
oc get cm trusted-ca-bundle -n openshift-config-managed -o yaml
oc get mcp
```

Depending on OpenShift version and node disruption policy behavior, this change can trigger Machine Config rollout activity. Treat it as potentially disruptive and monitor MachineConfigPools.

---

### 7.3 Method 3: Add Registry-Specific CA with `image.config.openshift.io/cluster`

Use this when the TLS problem is specifically image pull, image push, BuildConfig, ImageStream import, or private registry access.

Example:

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=myregistry.example.com..5000=/etc/docker/certs.d/myregistry.example.com:5000/ca.crt \
  --from-file=quay.internal.example.com=/etc/docker/certs.d/quay.internal.example.com/ca.crt
```

Patch the cluster image config:

```bash
oc patch image.config.openshift.io/cluster --type=merge \
  --patch='{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Important domain key rule:

```text
hostname[:port] becomes hostname..port in ConfigMap key
```

Examples:

```text
registry.example.com:5000 → registry.example.com..5000
quay.internal.example.com → quay.internal.example.com
```

This method is usually better than using a generic MachineConfig for registry trust because it integrates with OpenShift image configuration and is understood by cluster components.

---

### 7.4 Method 4: Inject Trusted CA Bundle into Workloads

Use this when an application pod must call an internal HTTPS endpoint signed by your custom CA.

Create an empty ConfigMap with the injection label:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: trusted-ca
  namespace: my-app
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
data: {}
```

Apply:

```bash
oc apply -f trusted-ca.yaml
```

The Cluster Network Operator populates it with a merged CA bundle under:

```text
ca-bundle.crt
```

Mount it into a deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app
        image: registry.access.redhat.com/ubi9/ubi:latest
        command: ["sleep", "infinity"]
        volumeMounts:
        - name: trusted-ca
          mountPath: /etc/pki/ca-trust/extracted/pem
          readOnly: true
      volumes:
      - name: trusted-ca
        configMap:
          name: trusted-ca
          items:
          - key: ca-bundle.crt
            path: tls-ca-bundle.pem
```

Important:

- This does not automatically update every application language runtime.
- Java may need a Java truststore.
- Node.js may need `NODE_EXTRA_CA_CERTS`.
- Python `requests` may need `REQUESTS_CA_BUNDLE`.
- Go applications normally use system trust if built normally, but container base image matters.
- Distroless/scratch images might not have normal CA paths.

### 7.5 Method 5: Direct MachineConfig for Node Trust Store

Use this only when you have a clear node-level requirement not covered by supported cluster config objects.

Typical examples:

- A host-level agent installed on RHCOS needs an internal CA.
- A custom systemd service on the node calls an internal HTTPS endpoint.
- You are doing very controlled low-level platform customization.

Preferred path:

```text
/etc/pki/ca-trust/source/anchors/<name>.crt
```

Example Butane file for worker nodes:

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-custom-ca-anchor
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
  - path: /etc/pki/ca-trust/source/anchors/company-root-ca.crt
    mode: 0644
    overwrite: true
    contents:
      inline: |
        -----BEGIN CERTIFICATE-----
        <COMPANY_ROOT_CA>
        -----END CERTIFICATE-----
systemd:
  units:
  - name: custom-ca-update.service
    enabled: true
    contents: |
      [Unit]
      Description=Update system CA trust after custom CA anchor change
      Wants=network-online.target
      After=network-online.target

      [Service]
      Type=oneshot
      ExecStart=/usr/bin/update-ca-trust extract

      [Install]
      WantedBy=multi-user.target
```

Generate MachineConfig:

```bash
butane 99-worker-custom-ca-anchor.bu -o 99-worker-custom-ca-anchor.yaml
oc apply -f 99-worker-custom-ca-anchor.yaml
```

Verify:

```bash
oc get mcp worker
oc describe mcp worker
oc get mc | grep custom-ca
oc debug node/<worker-node>
chroot /host
ls -l /etc/pki/ca-trust/source/anchors/
trust list | grep -i company
openssl x509 -in /etc/pki/ca-trust/source/anchors/company-root-ca.crt -noout -subject -issuer -dates
```

Production caution:

- Prefer `Proxy.trustedCA` or `Image.additionalTrustedCA` where applicable.
- A generic MachineConfig can trigger node rollout behavior.
- If a node is manually changed outside MachineConfig, MCD can detect configuration drift and mark the node degraded.
- Test in non-production first.

## 8. Machine Config Operator Relationship

The Machine Config Operator manages operating system and node-level configuration for RHCOS nodes. It renders MachineConfigs into a final desired state per MachineConfigPool.

Important components:

| Component | Purpose |
|---|---|
| `machine-config-operator` | Top-level Operator managing MCO stack |
| `machine-config-controller` | Renders configs and coordinates updates |
| `machine-config-daemon` | Runs on each node and applies desired config |
| `machine-config-server` | Serves Ignition/config to nodes |
| `MachineConfig` | Defines OS-level changes |
| `MachineConfigPool` | Groups nodes receiving config |
| `ControllerConfig` | Stores cluster-level data used to render configs |
| `MachineConfigNode` | Per-node update state in newer OCP releases |

When you update a custom CA through cluster config, it can become part of the rendered node configuration. The MCO/MCD then ensures the node gets the expected file content.

A common managed CA file is:

```text
/etc/pki/ca-trust/source/anchors/openshift-config-user-ca-bundle.crt
```

That file is not something you should manually edit on the node. It is managed by cluster configuration and MachineConfig flow.

## 9. Node Disruption and Rollout Behavior

This is where experienced admins pay attention.

Some OpenShift documentation states that modifying the cluster `Proxy` object can initiate a rolling reboot of all nodes. Machine configuration documentation for newer releases also shows node disruption policy behavior for the CA anchor path where the MCO restarts `coreos-update-ca-trust.service` and `crio.service` for the managed CA bundle path.

Operational interpretation:

> Treat custom CA bundle changes as MachineConfig-impacting changes. Plan them like a controlled cluster rollout, then verify the actual behavior on your OpenShift version.

Watch these resources:

```bash
oc get mcp
oc describe mcp master
oc describe mcp worker
oc get nodes
oc get machineconfignode
oc describe machineconfignode/<node>
oc get co machine-config
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=100
```

Possible outcomes:

- MachineConfigPool updates without reboot but with service restart.
- MachineConfigPool updates with drain/reboot.
- Worker pool updates first or based on pool state.
- Master/control-plane pool updates separately.
- Updates pause if pool is paused.
- Updates pause if PDBs block drain.
- Nodes degrade if rendered config cannot apply.

Production best practice:

```bash
oc get mcp
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'   # only when intentionally controlling rollout
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Do not leave MCPs paused unintentionally. A paused MCP can block security and upgrade changes.

## 10. Deep-Dive: Cluster-Wide Proxy `trustedCA`

The cluster-wide `Proxy` object is named `cluster`:

```bash
oc get proxy/cluster -o yaml
```

Relevant fields:

```yaml
spec:
  httpProxy: http://proxy.example.com:8080
  httpsProxy: http://proxy.example.com:8080
  noProxy: .cluster.local,.svc,10.128.0.0/14
  trustedCA:
    name: custom-ca-bundle
```

`trustedCA.name` must reference a ConfigMap in:

```text
openshift-config
```

The ConfigMap must contain:

```yaml
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

The key must be exactly:

```text
ca-bundle.crt
```

Common mistakes:

```yaml
# Wrong key
ca.crt: |

# Wrong namespace
namespace: default

# Wrong object type
kind: Secret

# Wrong content
-----BEGIN PRIVATE KEY-----

# Wrong reference
trustedCA:
  name: missing-configmap
```

Check status:

```bash
oc get proxy/cluster -o jsonpath='{.spec.trustedCA.name}{"\n"}'
oc get proxy/cluster -o jsonpath='{.status.conditions}{"\n"}'
```

Check managed bundle locations:

```bash
oc get cm trusted-ca-bundle -n openshift-config -o yaml
oc get cm trusted-ca-bundle -n openshift-config-managed -o yaml
oc get cm -A | grep -E 'trusted-ca|user-ca|proxy-ca'
```

Different OpenShift versions and components may surface the merged bundle in slightly different namespaces or managed ConfigMaps. The user-provided source ConfigMap belongs in `openshift-config`.

## 11. Deep-Dive: Registry CA Trust

Registry CA trust is its own topic because image pull/push code paths are special.

Symptoms:

```text
Failed to pull image "registry.example.com/app:v1":
x509: certificate signed by unknown authority
```

or:

```text
error pinging docker registry registry.example.com: Get "https://registry.example.com/v2/": x509: certificate signed by unknown authority
```

Recommended OpenShift method:

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=registry.example.com..5000=/path/to/ca.crt

oc patch image.config.openshift.io/cluster --type=merge \
  --patch='{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Verify:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get cm registry-cas -n openshift-config -o yaml
oc get mcp
oc debug node/<node>
chroot /host
find /etc/docker/certs.d -maxdepth 3 -type f -print
find /etc/containers/certs.d -maxdepth 3 -type f -print
```

Notes:

- Image pull trust is not the same as app runtime trust.
- Pull secrets solve authentication, not TLS trust.
- `insecure: true` registry settings should be avoided in production.
- For disconnected environments, registry trust and mirror configuration must be correct before upgrade operations.

## 12. Deep-Dive: Workload CA Injection

A pod does not automatically trust every CA trusted by the RHCOS host. Containers have their own filesystem, base image, libraries, and language trust stores.

To inject the cluster trusted CA into a workload namespace:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: trusted-ca
  namespace: app1
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
data: {}
```

After creation:

```bash
oc get cm trusted-ca -n app1 -o yaml
```

Expected key:

```text
data.ca-bundle.crt
```

Mount into pod:

```yaml
volumes:
- name: trusted-ca
  configMap:
    name: trusted-ca
    items:
    - key: ca-bundle.crt
      path: tls-ca-bundle.pem
containers:
- name: app
  volumeMounts:
  - name: trusted-ca
    mountPath: /etc/pki/ca-trust/extracted/pem
    readOnly: true
```

For UBI/RHEL-like containers, `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem` is commonly used.

For Debian/Ubuntu containers, the usual bundle path might be:

```text
/etc/ssl/certs/ca-certificates.crt
```

For Java:

```text
$JAVA_HOME/lib/security/cacerts
```

For Node.js:

```bash
NODE_EXTRA_CA_CERTS=/path/to/ca-bundle.crt
```

For Python requests:

```bash
REQUESTS_CA_BUNDLE=/path/to/ca-bundle.crt
```

For Git:

```bash
git config --global http.sslCAInfo /path/to/ca-bundle.crt
```

Production advice:

- Do not overwrite application config blindly.
- Know the container base image.
- Know the application language TLS library.
- Use ConfigMap volume mounts or rebuild image trust store depending on lifecycle needs.

## 13. Difference Between `inject-trusted-cabundle` and `inject-cabundle`

These two are frequently confused.

### 13.1 Trusted CA Bundle Injection

```yaml
metadata:
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
```

Purpose:

- Injects merged cluster trusted CA bundle.
- Used for external/internal HTTPS endpoints signed by custom CAs.
- Key: `ca-bundle.crt`.

### 13.2 Service CA Bundle Injection

```yaml
metadata:
  annotations:
    service.beta.openshift.io/inject-cabundle: "true"
```

Purpose:

- Injects OpenShift service serving CA.
- Used to trust service serving certificates generated by OpenShift service-ca Operator.
- Key: `service-ca.crt`.

Do not put both mechanisms on the same ConfigMap. They are managed by different controllers and use different keys. Keep separate ConfigMaps.

## 14. End-to-End Example: Corporate Proxy CA for Running Cluster

Scenario:

- Cluster already running.
- Corporate proxy signs outbound HTTPS traffic.
- Platform Operators fail with `x509 certificate signed by unknown authority`.
- Need to trust proxy CA cluster-wide.

### Step 1: Validate CA file locally

```bash
openssl x509 -in corp-proxy-ca.crt -noout -subject -issuer -dates -fingerprint -sha256
```

Ensure it is a CA:

```bash
openssl x509 -in corp-proxy-ca.crt -noout -text | grep -A3 "Basic Constraints"
```

Expected:

```text
CA:TRUE
```

### Step 2: Create ConfigMap YAML

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: corp-proxy-ca
  namespace: openshift-config
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    <PASTE_CORP_PROXY_CA>
    -----END CERTIFICATE-----
```

### Step 3: Apply

```bash
oc apply -f corp-proxy-ca.yaml
```

### Step 4: Patch Proxy

```bash
oc patch proxy/cluster --type=merge \
  --patch='{"spec":{"trustedCA":{"name":"corp-proxy-ca"}}}'
```

### Step 5: Watch cluster

```bash
watch -n5 'oc get co; echo; oc get mcp; echo; oc get nodes'
```

### Step 6: Verify merged bundle

```bash
oc get cm trusted-ca-bundle -n openshift-config -o yaml | grep -A2 -B2 "BEGIN CERTIFICATE"
oc get cm trusted-ca-bundle -n openshift-config-managed -o yaml | grep -A2 -B2 "BEGIN CERTIFICATE"
```

### Step 7: Verify on node

```bash
NODE=$(oc get node -l node-role.kubernetes.io/worker -o jsonpath='{.items[0].metadata.name}')
oc debug node/$NODE
chroot /host
ls -l /etc/pki/ca-trust/source/anchors/
openssl x509 -in /etc/pki/ca-trust/source/anchors/openshift-config-user-ca-bundle.crt -noout -subject -issuer -dates
trust list | grep -i "corp" -A3 -B3
systemctl status coreos-update-ca-trust.service --no-pager
systemctl status crio --no-pager
exit
exit
```

### Step 8: Check affected Operators

```bash
oc get co
oc describe co image-registry
oc describe co marketplace
oc describe co authentication
oc describe co console
```

## 15. End-to-End Example: Private Registry CA

Scenario:

- Internal registry: `registry.ocp4.example.com:8443`.
- Certificate signed by lab/internal CA.
- Pods fail with `ImagePullBackOff` due to unknown authority.

### Step 1: Export CA

```bash
openssl s_client -showcerts -connect registry.ocp4.example.com:8443 </dev/null 2>/dev/null \
  | awk '/BEGIN CERTIFICATE/,/END CERTIFICATE/ {print}' > registry-chain.pem
```

Inspect:

```bash
openssl x509 -in registry-chain.pem -noout -subject -issuer -dates
```

Make sure you have the CA, not only the leaf certificate.

### Step 2: Create registry CA ConfigMap

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=registry.ocp4.example.com..8443=registry-ca.crt
```

### Step 3: Patch image config

```bash
oc patch image.config.openshift.io/cluster --type=merge \
  --patch='{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

### Step 4: Monitor MCO

```bash
oc get mcp
oc describe mcp worker
oc get co machine-config image-registry
```

### Step 5: Test pull

```bash
oc new-project test-registry-ca
oc run pull-test --image=registry.ocp4.example.com:8443/rhel9/mysql-80 --restart=Never -- sleep 3600
oc describe pod pull-test
oc get pod pull-test -w
```

If still failing:

```bash
oc get events --sort-by=.lastTimestamp -n test-registry-ca
oc describe pod pull-test -n test-registry-ca
oc debug node/<node>
chroot /host
crictl pull registry.ocp4.example.com:8443/rhel9/mysql-80
```

## 16. End-to-End Example: Application Needs Internal HTTPS Trust

Scenario:

- App pod calls `https://api.internal.example.com`.
- Node trust is fine.
- Operator trust is fine.
- App still gets `x509 unknown authority`.

Reason:

> The app container does not automatically inherit RHCOS host trust.

### Step 1: Create injected trusted CA ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: trusted-ca
  namespace: app-prod
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
data: {}
```

```bash
oc apply -f trusted-ca.yaml
oc get cm trusted-ca -n app-prod -o yaml
```

### Step 2: Mount into deployment

```bash
oc set volume deployment/myapp -n app-prod \
  --add \
  --name=trusted-ca \
  --type=configmap \
  --configmap-name=trusted-ca \
  --mount-path=/etc/pki/ca-trust/extracted/pem \
  --read-only=true
```

For applications needing an explicit environment variable:

```bash
oc set env deployment/myapp -n app-prod SSL_CERT_FILE=/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

For Python requests:

```bash
oc set env deployment/myapp -n app-prod REQUESTS_CA_BUNDLE=/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

For Node.js:

```bash
oc set env deployment/myapp -n app-prod NODE_EXTRA_CA_CERTS=/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

### Step 3: Test from pod

```bash
oc rsh deploy/myapp
curl -v https://api.internal.example.com/health
openssl s_client -connect api.internal.example.com:443 -servername api.internal.example.com -verify_return_error
```

## 17. Certificate Validation Before Applying

Never apply an unknown CA bundle without validating it.

### 17.1 Check PEM Format

```bash
grep -c "BEGIN CERTIFICATE" ca-bundle.crt
grep -c "END CERTIFICATE" ca-bundle.crt
```

The counts must match.

### 17.2 Inspect Certificates

If one certificate:

```bash
openssl x509 -in ca-bundle.crt -noout -subject -issuer -dates -fingerprint -sha256
```

If multiple certificates:

```bash
csplit -z -f cert- ca-bundle.crt '/-----BEGIN CERTIFICATE-----/' '{*}'
for c in cert-*; do
  echo "=== $c ==="
  openssl x509 -in "$c" -noout -subject -issuer -dates -fingerprint -sha256
  echo
done
```

### 17.3 Check CA Basic Constraints

```bash
openssl x509 -in ca.crt -noout -text | grep -A4 "Basic Constraints"
```

Expected:

```text
CA:TRUE
```

### 17.4 Test Chain Against Endpoint

```bash
openssl s_client \
  -connect internal.example.com:443 \
  -servername internal.example.com \
  -CAfile ca-bundle.crt \
  -verify_return_error </dev/null
```

Expected:

```text
Verify return code: 0 (ok)
```

### 17.5 Check Expiry

```bash
openssl x509 -in ca.crt -noout -enddate
```

For multiple certificates:

```bash
for c in cert-*; do
  echo "=== $c ==="
  openssl x509 -in "$c" -noout -subject -enddate
done
```

## 19. Common Failure Scenarios and Fixes

### 19.1 `x509: certificate signed by unknown authority` from Operator

Likely cause:

- `Proxy/cluster.spec.trustedCA` not configured.
- ConfigMap key not `ca-bundle.crt`.
- CA missing intermediate.
- Operator pod has not rolled out.
- Operator does not mount injected trust.

Commands:

```bash
oc get proxy/cluster -o yaml
oc get cm -n openshift-config
oc get co
oc describe co <operator>
oc logs -n <operator-namespace> deploy/<operator-deployment>
```

Fix:

- Correct `custom-ca-bundle` ConfigMap.
- Patch `Proxy/cluster`.
- Restart or wait for affected Operator rollout if necessary.

---

### 19.2 ImagePullBackOff with Private Registry

Likely cause:

- You configured proxy trust but not registry trust.
- Wrong ConfigMap key for registry port.
- Missing CA chain.
- Node not yet updated.
- Pull secret issue mixed with TLS issue.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get image.config.openshift.io/cluster -o yaml
oc get cm registry-cas -n openshift-config -o yaml
oc get mcp
```

Fix:

```bash
oc patch image.config.openshift.io/cluster --type=merge \
  --patch='{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

---

### 19.3 App Pod Still Fails After Cluster CA Added

Likely cause:

- Application container does not use host trust.
- CA not mounted inside pod.
- Language runtime uses separate trust store.

Commands:

```bash
oc rsh <pod>
ls -l /etc/pki/ca-trust/extracted/pem/
curl -v https://internal.example.com
python -c 'import requests; print(requests.get("https://internal.example.com").status_code)'
```

Fix:

- Inject trusted CA ConfigMap into app namespace.
- Mount it into pod.
- Set app-specific environment variable.
- For Java, import into Java truststore or mount an application truststore.

---

### 19.4 MCP Degraded After CA Change

Likely cause:

- Bad MachineConfig.
- Invalid file path/mode.
- Node drift due to manual edits.
- MCD cannot apply rendered config.
- PDB/drain issue.

Commands:

```bash
oc get mcp
oc describe mcp worker
oc get machineconfignode
oc describe machineconfignode/<node>
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=200
```

Fix approach:

1. Identify exact degraded reason.
2. If custom MC is bad, create a corrected MC or remove the bad MC.
3. Do not manually edit `/etc/pki` files on node unless recovering with clear intent.
4. Wait for pool reconciliation.
5. If node drift exists, restore file to MachineConfig expected state.

---

### 19.5 Wrong CA Certificate Applied

Symptoms:

- TLS still fails.
- `openssl s_client` chain shows a different issuer than expected.
- The bundle contains the leaf cert but not the issuing CA.

Fix:

```bash
openssl s_client -showcerts -connect endpoint.example.com:443 -servername endpoint.example.com </dev/null
```

Identify issuer:

```bash
openssl x509 -in leaf.crt -noout -issuer -subject
openssl x509 -in intermediate.crt -noout -issuer -subject
```

Add the correct root/intermediate CA bundle.

---

### 19.6 ConfigMap Updated But Components Still Fail

Likely cause:

- Component did not reload mounted ConfigMap.
- Pod needs restart.
- Operator uses environment variable captured at startup.
- Node not updated yet.

Commands:

```bash
oc rollout restart deployment/<name> -n <ns>
oc rollout status deployment/<name> -n <ns>
oc get mcp
oc get pods -n <ns> -o wide
```

Be careful restarting platform Operators manually. Prefer Operator-managed reconciliation unless you know the impact.

## 20. CA Rotation Strategy

A CA bundle is not a one-time task. You need lifecycle management.

### 20.1 Recommended Rotation Pattern

1. Add new CA while keeping old CA.
2. Wait for cluster-wide rollout.
3. Rotate server certificates to be signed by new CA.
4. Validate all clients.
5. Remove old CA after all endpoints stop using it.
6. Monitor MCPs and Operators.

### 20.2 Avoid Big-Bang Rotation

Bad pattern:

```text
Remove old CA → Add new CA → Replace all server certs → Hope everything works
```

Good pattern:

```text
Trust old + new → Roll endpoints → Validate → Remove old
```

### 20.3 Find Expiry

For ConfigMap bundle:

```bash
oc get cm custom-ca-bundle -n openshift-config -o jsonpath='{.data.ca-bundle\.crt}' > ca-bundle.crt
csplit -z -f cert- ca-bundle.crt '/-----BEGIN CERTIFICATE-----/' '{*}'
for c in cert-*; do
  openssl x509 -in "$c" -noout -subject -issuer -enddate
 done
```

For MCO known certificate info:

```bash
oc get controllerconfig/machine-config-controller -o yaml
oc get mcp worker -o yaml
oc get mcp master -o yaml
```

## 21. Security Best Practices

### 21.1 Trust Only What You Need

A CA root is powerful. If you trust a corporate root cluster-wide, any certificate signed by that root might be trusted by platform components.

Use narrower CAs where possible:

- Specific proxy CA for proxy TLS inspection.
- Specific registry CA for registry endpoints.
- Specific app CA for application namespace.

### 21.2 Protect CA Source Files

Even public CA certificates are not secret, but the trust decision is security-sensitive.

Recommended:

- Store CA bundle YAML in GitOps repository.
- Require pull request approval.
- Track fingerprint changes.
- Document owner and expiry.
- Avoid manual `oc edit` in production.

### 21.3 Never Use Insecure Skip Verify as Permanent Fix

Temporary commands like these are diagnostic only:

```bash
curl -k https://endpoint
```

or insecure registry settings.

Do not use them as production design.

### 21.4 Separate Private Keys from CA Bundles

A CA bundle ConfigMap must never include:

```text
-----BEGIN PRIVATE KEY-----
-----BEGIN RSA PRIVATE KEY-----
-----BEGIN ENCRYPTED PRIVATE KEY-----
```

If you see these, stop and investigate.

### 21.5 Audit Changes

```bash
oc get events -A --sort-by=.lastTimestamp | grep -i configmap
oc get cm custom-ca-bundle -n openshift-config -o yaml
oc get proxy/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
```

Use cluster audit logs or GitOps history for production traceability.

## 23. Exam and Interview Notes

For an Advanced OpenShift Administration exam or interview, remember:

1. Custom CA for platform egress uses `Proxy/cluster.spec.trustedCA`.
2. The ConfigMap must be in `openshift-config`.
3. The required data key is `ca-bundle.crt`.
4. Registry trust uses `image.config.openshift.io/cluster.spec.additionalTrustedCA`.
5. Registry ConfigMap keys use `hostname[..port]` style.
6. Workload trust needs `config.openshift.io/inject-trusted-cabundle=true` label and a volume mount.
7. Service serving CA uses `service.beta.openshift.io/inject-cabundle=true` annotation, not the same mechanism.
8. The MCO/MCD handles node-level application of trust changes.
9. Monitor `oc get mcp` after trust changes.
10. Do not manually edit RHCOS trust files unless you are doing controlled recovery or a deliberate MachineConfig-based customization.

Short answer pattern:

```text
For cluster-wide custom CA, create a ConfigMap in openshift-config with key ca-bundle.crt, patch proxy/cluster spec.trustedCA.name to that ConfigMap, then monitor MCP and verify the merged trusted-ca-bundle and node trust store.
```

Registry answer pattern:

```text
For private registry CA, create a ConfigMap in openshift-config where each key is registry hostname[..port] and value is PEM CA, then patch image.config.openshift.io/cluster spec.additionalTrustedCA.name.
```

Workload answer pattern:

```text
For application pods, create an empty ConfigMap with label config.openshift.io/inject-trusted-cabundle=true in the namespace, mount ca-bundle.crt into the container trust path, and configure language-specific trust variables if needed.
```

## 27. Advanced Notes on RHCOS Trust

RHCOS uses the RHEL-style CA trust system. The usual custom anchor directory is:

```text
/etc/pki/ca-trust/source/anchors/
```

The generated extracted bundle is usually under:

```text
/etc/pki/ca-trust/extracted/
```

The command to regenerate extracted trust is:

```bash
update-ca-trust extract
```

On OpenShift nodes, do not run ad-hoc changes as a normal operating model. If you change a node manually, the MCD may detect drift because the live node no longer matches the rendered MachineConfig.

Good pattern:

```text
Declarative ConfigMap / Proxy / Image config / MachineConfig
```

Bad pattern:

```text
ssh node → copy CA file → run update-ca-trust → forget what changed
```

Operators may need trust in different ways:

- OLM pulls bundle/index images: registry trust required.

- Platform Operator calls external endpoint: cluster-wide proxy trust may be required.

```yaml

- Check whether the Operator binary uses system trust.
- Check whether it needs `/etc/ssl/certs` instead of `/etc/pki/ca-trust/extracted/pem`.
- Check if the Operator needs env vars.
- Check container base image.

## 30. FAQ

### Q1. Does `Proxy.trustedCA` mean the cluster must use an HTTP proxy?

No. The `trustedCA` field is part of the cluster Proxy object and is used for custom CA trust. You can use it to provide trust even when your main problem is a custom CA. Follow your OpenShift version documentation for exact behavior.

### Q2. Does cluster-wide custom CA automatically fix my application pod?

Not always. Many application containers need the CA bundle mounted into the container or added to language-specific trust stores.

### Q3. Does registry CA trust fix application curl errors?

No. Registry trust is mainly for image pull/push/build/import paths.

### Q4. Can I put CA bundle in a Secret?

For `Proxy.trustedCA`, use a ConfigMap in `openshift-config` with `ca-bundle.crt`. Some server certificates use Secrets, but CA trust bundle uses ConfigMap.

### Q5. Should I include root CA or intermediate CA?

Usually include the root CA and any required intermediate CA certificates. The exact answer depends on the server chain and your corporate PKI. Validate with `openssl s_client -CAfile`.

### Q6. Why does `curl -k` work but normal `curl` fails?

`-k` disables certificate verification. That proves connectivity, not trust correctness. Fix the CA trust.

### Q7. Why does node `curl` work but pod `curl` fail?

The node and pod use different trust stores. Inject or mount the trusted CA bundle into the pod.

### Q8. Why does pod `curl` work but Java app fails?

Java may use its own `cacerts` truststore. Import the CA or configure Java to use the mounted bundle/truststore.

### Q9. Is it safe to manually copy CA to `/etc/pki/ca-trust/source/anchors` on an OpenShift node?

Not as normal practice. Use OpenShift-supported cluster configuration or MachineConfig. Manual node changes can cause drift and are not durable.

### Q10. Will CA bundle change reboot nodes?

It depends on OpenShift version, the path changed, and node disruption policy. Treat it as a MachineConfig-impacting change and monitor MCPs. In some versions/procedures, documentation describes rolling reboots; newer machine configuration behavior may restart trust/CRI-O services for managed CA paths. Always verify in your cluster.

    name: custom-ca-bundle
```

### 32.3 Registry CA ConfigMap

apiVersion: v1

  name: registry-cas
  namespace: openshift-config

  registry.example.com..5000: |
    -----BEGIN CERTIFICATE-----
    <REGISTRY_CA>
    -----END CERTIFICATE-----

## 33. Important Do and Do Not List

### Do

- Use `Proxy.trustedCA` for cluster-wide platform trust.
- Use `Image.additionalTrustedCA` for private registry trust.
- Use injected ConfigMaps for workload trust.
- Validate CA PEM files before applying.
- Monitor MCPs after cluster trust changes.
- Keep CA changes in GitOps.
- Document CA owner, purpose, fingerprint, and expiry.
- Test in non-production first.

### Do Not

- Do not paste private keys into CA ConfigMaps.
- Do not use `curl -k` as a permanent solution.
- Do not manually change RHCOS nodes as a standard practice.
- Do not confuse service CA injection with trusted CA injection.
- Do not assume node trust automatically updates application runtime trust.
- Do not remove old CA before all endpoints migrate to the new CA.
- Do not leave MCPs paused after a CA rollout.

## 35. Final Senior Admin Takeaway

A custom CA bundle in OpenShift is not just a certificate file. It is part of cluster lifecycle management.

At a senior level, always ask:

```text
Who is failing TLS?
What trust store does that component use?
Is the CA bundle valid and complete?
Which OpenShift object owns this trust path?
Will MCO/MCP rollout be triggered?
How do I verify from the actual failing component?
How do I roll back safely?
```

Once you answer those questions, custom CA bundle troubleshooting becomes predictable instead of guesswork.
