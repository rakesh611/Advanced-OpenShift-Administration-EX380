# SSH Key Injection in MachineConfig and Node-Level Administration

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and Red Hat OpenShift admins with production responsibilities.  
**Scope:** OpenShift Container Platform 4.x / RHCOS nodes / Machine Config Operator / node access and troubleshooting.  
**Goal:** Understand how SSH key injection works, how to implement it safely, how it interacts with MachineConfig, MCP, MCO, MCD, Ignition, and how to troubleshoot it like an experienced OpenShift administrator.

---

## 1. Executive Summary

In OpenShift 4, cluster nodes normally run **Red Hat Enterprise Linux CoreOS (RHCOS)**. RHCOS is intentionally managed differently from a traditional RHEL server. You should not SSH into nodes and manually configure them as a daily administration practice. Instead, OpenShift expects node operating system configuration to be declared through **MachineConfig** and reconciled by the **Machine Config Operator (MCO)**.

**SSH key injection** means adding one or more SSH public keys to the OpenShift node user, normally the default RHCOS user named `core`, so that an administrator can log in to a node using SSH key-based authentication:

```bash
ssh -i ~/.ssh/ocp_breakglass core@<node-ip-or-hostname>
```

In OpenShift node administration, SSH key injection can happen in two main ways:

1. **At installation time** through `install-config.yaml` using the `sshKey` field. The key is passed through Ignition and becomes available for the `core` user on cluster nodes.
2. **After installation** through a `MachineConfig` using:

```yaml
spec:
  config:
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-ed25519 AAAA... admin@example
```

The most important production rule is this:

> MachineConfig-based SSH key changes are supported for the `core` user only. Do not try to create arbitrary Linux users by MachineConfig for SSH access.

Also, in current OpenShift documentation, changes to `spec.config.passwd.users.sshAuthorizedKeys` are treated as a MachineConfig change that can be applied without draining or rebooting the node. Older examples and older cluster versions might show reboot behavior, so always validate on the cluster version you operate.

## 2. Why SSH Exists in OpenShift if `oc debug node` Exists

A mature OpenShift admin should treat SSH as a **break-glass and low-level troubleshooting path**, not the default way to manage nodes.

### 2.1 Preferred access path: `oc debug node`

For normal node troubleshooting, use:

```bash
oc debug node/<node-name>
chroot /host
```

This keeps access inside Kubernetes/OpenShift control, uses cluster authentication and authorization, and avoids permanent direct host administration habits.

Typical examples:

```bash
oc debug node/worker-0.example.com
chroot /host
systemctl status kubelet
journalctl -u kubelet -b
crictl ps -a
```

### 2.2 Why SSH is still needed

SSH is useful when:

- The API server is unavailable.
- The kubelet or CRI-O is broken and `oc debug node` cannot create a debug pod.
- You need early installation debugging.
- You need disaster recovery access.
- You need support collection from a node when cluster-level tooling is impaired.
- You are troubleshooting network paths from the node host itself.
- You need emergency access through a bastion or management network.

### 2.3 Wrong mental model

Do not think:

> “I will SSH into each node and fix it manually.”

Think:

> “I will use SSH only to inspect, recover, or gather evidence, then declare the permanent fix through MachineConfig, Operator configuration, or Kubernetes resources.”

## 3. RHCOS, `core` User, and Immutable Node Management

OpenShift 4 nodes are not ordinary hand-managed Linux servers. RHCOS is designed for:

- Automated provisioning
- Declarative configuration
- Atomic OS updates
- Minimal manual drift
- Operator-driven lifecycle management

The default administrative user on RHCOS is:

```text
core
```

Important points:

- The `core` user exists by default.
- The `core` user normally has no password for SSH login.
- SSH access uses public key authentication.
- You should not create random local users for node login.
- OpenShift MachineConfig supports changing SSH keys only for `core`.
- The permanent source of truth should be MachineConfig, not manual edits under `/home/core/.ssh`.

---

## 4. What “SSH Key Injection” Actually Does

SSH key injection adds one or more public keys to the node so that OpenSSH can authenticate the matching private key.

At the node level, this normally results in keys being available under paths related to the `core` user, such as:

```text
/home/core/.ssh/authorized_keys
/home/core/.ssh/authorized_keys.d/ignition
```

The exact path can depend on whether the key came from installation-time Ignition or MachineConfig/MCD reconciliation. As an administrator, the important concept is:

- **Installation-time key**: delivered through installer/Ignition.
- **Post-install key**: delivered through MachineConfig/MCO/MCD.

OpenSSH decides whether a login is allowed by checking configured authorized key locations for the target user. In OpenShift, the target user is normally `core`.

## 5. Key Components Involved

### 5.1 MachineConfig

`MachineConfig` is an OpenShift custom resource used to configure the host operating system for nodes in a MachineConfigPool.

It can manage things such as:

- Files under `/etc` or `/var`
- systemd units and drop-ins
- kernel arguments
- CRI-O configuration indirectly through `ContainerRuntimeConfig`
- kubelet configuration indirectly through `KubeletConfig`
- SSH authorized keys for `core`

For SSH keys, the key part is:

```yaml
spec:
  config:
    ignition:
      version: 3.5.0
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE admin@example
```

### 5.2 MachineConfigPool

A `MachineConfigPool` groups nodes that receive the same rendered MachineConfig.

Default pools:

```bash
oc get mcp
```

Typical output:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED
master   rendered-master-...                                True      False      False
worker   rendered-worker-...                                True      False      False
```

Common roles:

```text
master
worker
infra
custom worker pools
```

A MachineConfig targets a pool using this label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

### 5.3 Machine Config Operator

The Machine Config Operator is the cluster Operator responsible for managing node operating system configuration. It watches MachineConfig objects, renders new configurations, and coordinates rollout to nodes.

### 5.4 Machine Config Daemon

The Machine Config Daemon runs on every node. It applies rendered configuration to that node and reports status back to the cluster.

For SSH keys, the MCD writes or updates the authorized key content for `core` according to the desired MachineConfig state.

### 5.5 Ignition

Ignition is the first-boot provisioning mechanism used by RHCOS. During installation, Ignition config can create files, users, systemd units, storage layout, and SSH keys.

In OpenShift, MachineConfig embeds Ignition-style configuration under:

```yaml
spec:
  config:
    ignition:
      version: 3.5.0
```

For new MachineConfigs on modern OpenShift, use the Ignition spec version supported by your cluster. Current docs show Ignition spec `3.5.0` for recent OpenShift releases. For Butane, the version should match your OpenShift minor version and end in `.0`, for example `4.16.0`, `4.17.0`, `4.18.0`, or `4.21.0` depending on your cluster.

## 6. Supported and Unsupported Operations

### 6.1 Supported

Supported:

- Add SSH public keys for the `core` user.
- Remove SSH public keys for the `core` user from the MachineConfig-managed key list.
- Rotate SSH public keys for `core`.
- Apply different keys to `master`, `worker`, `infra`, or custom worker pools.
- Use multiple public keys.
- Manage keys declaratively using GitOps if your organization approves it.

### 6.2 Unsupported or bad practice

Avoid or do not do:

- Do not inject a private key into a node.
- Do not create arbitrary users through MachineConfig for SSH access.
- Do not change `name: core` to another user in the MachineConfig SSH section.
- Do not manually edit `/home/core/.ssh/authorized_keys` as the permanent fix.
- Do not use SSH as the normal application/platform administration path.
- Do not store shared private keys on random laptops or bastion hosts.
- Do not remove the only working key before validating the new key.
- Do not assume key removal is successful until tested on the real node path and cluster version.

## 7. Installation-Time SSH Key Injection

During installation, you can provide a public SSH key in `install-config.yaml`:

```yaml
apiVersion: v1
baseDomain: example.com
metadata:
  name: ocp4
sshKey: |
  ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE rakesh@bastion
```

After installation, this key allows:

```bash
ssh -i ~/.ssh/id_ed25519 core@<node-ip>
```

### 7.1 When to configure at installation

Configure installation-time SSH key when:

- You are building production clusters.
- You require disaster recovery access.
- You expect to run support collection or low-level debugging.
- You have a secured bastion/jump host model.

### 7.2 Production advice

For production, do not use a random personal key without tracking. Use one of these patterns:

- A controlled break-glass key stored in a vault.
- Individual named administrator keys managed by MachineConfig/GitOps.
- A bastion-only private key with strict access controls.
- A temporary key with documented removal date.

## 8. Post-Installation SSH Key Injection with MachineConfig

This is the main Day-2 administration method.

### 8.1 Basic worker MachineConfig

Create `99-worker-core-ssh.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-core-ssh
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE1 rakesh@bastion-2026
        - ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABgQCEXAMPLE2 platform-admin@example
```

Apply:

```bash
oc apply -f 99-worker-core-ssh.yaml
```

Monitor:

```bash
oc get mcp worker -w
oc get nodes
```

### 8.2 Basic master MachineConfig

Create `99-master-core-ssh.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-master-core-ssh
  labels:
    machineconfiguration.openshift.io/role: master
spec:
  config:
    ignition:
      version: 3.5.0
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE1 rakesh@bastion-2026
```

Apply:

```bash
oc apply -f 99-master-core-ssh.yaml
```

Monitor:

```bash
oc get mcp master -w
```

### 8.3 Existing `99-worker-ssh` and `99-master-ssh`

Many clusters already have installer-created SSH MachineConfigs, commonly named like:

```text
99-master-ssh
99-worker-ssh
```

Check:

```bash
oc get machineconfig | grep -i ssh
```

View existing keys:

```bash
oc get mc 99-worker-ssh -o yaml
oc get mc 99-master-ssh -o yaml
```

If these objects exist, a conservative admin workflow is:

```bash
oc get mc 99-worker-ssh -o yaml > 99-worker-ssh.backup.yaml
oc get mc 99-master-ssh -o yaml > 99-master-ssh.backup.yaml
```

Then edit carefully, keeping all keys that must remain valid.

### 8.4 Create separate MachineConfig or edit existing one?

Both patterns can work, but choose deliberately.

#### Pattern A: Edit existing SSH MachineConfig

Pros:

- Easy to see all `core` keys in one place.
- Good for rotation.
- Less chance of duplicate keys.

Cons:

- You are editing an installer-created object.
- Mistakes can remove an existing key if you overwrite the list.

#### Pattern B: Create a separate MachineConfig

Pros:

- Cleaner GitOps ownership.
- Easier to delete temporary key by deleting one object.
- Good for emergency temporary access.

Cons:

- Multiple MachineConfigs may make the final rendered key set less obvious.
- You must inspect the rendered config or node to confirm the actual result.

Experienced recommendation:

- For permanent platform keys, manage a single source-of-truth file per pool.
- For short-term break-glass, use a separate clearly named MachineConfig such as `99-worker-temp-breakglass-ssh` and delete it after the incident.
- Always validate the rendered config and actual node file.

Butane is often the better authoring format because it is easier to read and less error-prone than raw Ignition.

### 9.1 Worker Butane file

Create `99-worker-core-ssh.bu`:

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-core-ssh

    machineconfiguration.openshift.io/role: worker
```

## 10. How MCO Applies SSH Key Changes

When you apply a MachineConfig:

1. The Machine Config Controller observes the new or changed MachineConfig.
2. It creates a new rendered MachineConfig for the target pool.
3. The MachineConfigPool status changes.
4. The Machine Config Daemon on each matching node reconciles the desired state.
5. For SSH authorized key changes, current OpenShift documentation states that the change is applied without a node drain or reboot.
6. The node should remain Ready if nothing else is wrong.

Check pool status:

```bash
oc get mcp
```

Detailed pool view:

```bash
oc describe mcp worker
```

Check node annotations:

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

If `currentConfig` equals `desiredConfig`, the node is on the expected rendered MachineConfig.

## 11. Full Operational Procedure: Add SSH Key to Worker Nodes

This is a production-style procedure.

### 11.1 Pre-check cluster state

```bash
oc whoami
oc get clusterversion
oc get co machine-config
oc get mcp
oc get nodes -o wide
oc get mc | grep -i ssh || true
```

Do not proceed if the Machine Config Operator is already degraded unless the SSH key change is required for recovery and you understand the risk.

### 11.2 Generate a new key pair

On your secured admin workstation or bastion:

```bash
ssh-keygen -t ed25519 -C "rakesh@ocp-worker-breakglass-2026-07-03" -f ~/.ssh/ocp_worker_breakglass_ed25519
```

For environments with strict crypto/FIPS requirements, follow your organization’s approved algorithm policy. Many regulated environments prefer RSA 3072/4096 with SHA-2 signatures, but you must validate against your OpenShift/RHEL crypto policy.

Show the public key:

```bash
cat ~/.ssh/ocp_worker_breakglass_ed25519.pub
```

Show fingerprint:

```bash
ssh-keygen -lf ~/.ssh/ocp_worker_breakglass_ed25519.pub
```

### 11.3 Back up existing SSH MachineConfigs

```bash
mkdir -p mc-backup-$(date +%F)
oc get mc -o yaml > mc-backup-$(date +%F)/all-machineconfigs.yaml
oc get mc 99-worker-ssh -o yaml > mc-backup-$(date +%F)/99-worker-ssh.yaml 2>/dev/null || true
oc get mc 99-master-ssh -o yaml > mc-backup-$(date +%F)/99-master-ssh.yaml 2>/dev/null || true
```

### 11.4 Create the MachineConfig

```bash
cat > 99-worker-temp-breakglass-ssh.yaml <<'EOF_MC'
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-temp-breakglass-ssh
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE rakesh@ocp-worker-breakglass-2026-07-03
EOF_MC
```

Validate YAML locally if possible:

```bash
oc apply --dry-run=client -f 99-worker-temp-breakglass-ssh.yaml
```

Apply:

```bash
oc apply -f 99-worker-temp-breakglass-ssh.yaml
```

### 11.5 Monitor rollout

```bash
oc get mcp worker -w
```

In another terminal:

```bash
oc describe mcp worker
oc get nodes
```

### 11.6 Verify on a node using `oc debug`

```bash
NODE=$(oc get nodes -l node-role.kubernetes.io/worker= -o jsonpath='{.items[0].metadata.name}')
echo $NODE
oc debug node/$NODE
```

Inside the debug pod:

```bash
chroot /host
getent passwd core
ls -ld /home/core /home/core/.ssh
ls -l /home/core/.ssh
cat /home/core/.ssh/authorized_keys 2>/dev/null || true
find /home/core/.ssh -maxdepth 2 -type f -print -exec sed -n '1,5p' {} \;
exit
exit
```

### 11.7 Verify actual SSH

Find node IP:

```bash
oc get node $NODE -o wide
```

SSH:

```bash
ssh -i ~/.ssh/ocp_worker_breakglass_ed25519 core@<node-internal-or-external-ip>
```

After login:

```bash
hostname
whoami
sudo -i
systemctl status kubelet --no-pager
journalctl -u sshd -b --no-pager | tail -50
exit
exit
```

## 12. Full Operational Procedure: Rotate SSH Keys Safely

Key rotation must avoid lockout.

### 12.1 Safe rotation rule

Use a two-phase approach:

1. Add the new key while keeping the old key.
2. Validate the new key from the expected bastion/admin location.
3. Remove the old key only after validation.
4. Validate old key no longer works, if removal is required.

### 12.2 Phase 1: Add new key

Example:

```yaml
sshAuthorizedKeys:
- ssh-ed25519 AAAAOLD old-admin@example
- ssh-ed25519 AAAANEW new-admin@example
```

Apply and test:

```bash
oc apply -f 99-worker-ssh.yaml
oc get mcp worker -w
ssh -i ~/.ssh/new_key core@<worker-ip>
```

### 12.3 Phase 2: Remove old key

Update:

```yaml
sshAuthorizedKeys:
- ssh-ed25519 AAAANEW new-admin@example
```

Apply:

```bash
oc apply -f 99-worker-ssh.yaml
oc get mcp worker -w
```

Validate:

```bash
ssh -i ~/.ssh/new_key core@<worker-ip>
ssh -i ~/.ssh/old_key core@<worker-ip>
```

The old key should fail if it has been fully removed from all authorized key sources used by sshd.

### 12.4 Important removal warning

If a key was injected at installation time through Ignition, verify actual node key files and sshd behavior. On some historical versions, install-time keys and MCO-managed keys could be stored in different authorized key locations. Do not declare a key removed until you test the actual SSH path.

Use:

```bash
oc debug node/<node>
chroot /host
sshd -T | grep -i authorizedkeysfile
find /home/core/.ssh -maxdepth 3 -type f -print -exec cat {} \;
```

Then test from your SSH client.

## 13. Applying Keys to Custom MachineConfigPools

Many production clusters have custom pools, for example:

```text
worker
infra
storage
router
gpu
odf
edge
```

A custom pool uses a custom node role label and a MachineConfig selector.

Example node label:

```bash
oc label node worker-3.example.com node-role.kubernetes.io/infra=""
```

Example custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

MachineConfig for infra SSH:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-core-ssh
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.5.0
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE infra-admin@example
```

Apply:

```bash
oc apply -f 99-infra-core-ssh.yaml
oc get mcp infra -w
```

Experienced warning:

- If the custom MCP includes `worker` configs plus custom configs, understand precedence and rendered configuration carefully.
- Do not assume worker keys apply exactly as expected to custom pools unless you verify the rendered config and actual node files.

## 14. Node Drain and Reboot Behavior

For many MachineConfig changes, the MCO drains and reboots nodes. Examples include kernel arguments, many systemd changes, and many file changes.

For SSH key changes under:

```yaml
spec.config.passwd.users.sshAuthorizedKeys
```

current OpenShift documentation identifies this as a change that can be applied without draining or rebooting the node.

However, an experienced administrator should still:

```bash
oc get mcp
oc describe mcp <pool>
oc get nodes
```

Why?

Because the MachineConfig you apply might contain more than only SSH keys. If your YAML also changes files, systemd units, kernel arguments, or OS image content, then the rollout behavior can be different.

### 14.1 Avoid mixing changes

Bad idea:

```yaml
# SSH keys + kernel args + systemd changes in one MachineConfig
```

Good idea:

```text
99-worker-core-ssh          # SSH only
99-worker-custom-sysctl     # sysctl only
99-worker-kernelargs        # kernel args only
```

This makes rollout behavior and rollback easier to reason about.

## 16. Troubleshooting SSH Key Injection

## 16.1 `Permission denied (publickey)`

Common causes:

1. Wrong username.
2. Wrong private key.
3. Public key not applied to the target pool.
4. MachineConfigPool still updating.
5. Node is not in the pool you targeted.
6. Security group/firewall blocks port 22.
7. SSHD configuration differs from expectation.
8. Key algorithm rejected by crypto policy.
9. The key line is malformed.
10. You accidentally inserted a private key instead of public key.

Commands:

```bash
ssh -vvv -i ~/.ssh/key core@<node-ip>
oc get mcp
oc get nodes --show-labels
oc get mc | grep -i ssh
oc describe mcp worker
```

Check target node labels:

```bash
oc get node <node-name> --show-labels
```

If the node is `infra`, but you targeted `worker`, understand your MCP design before proceeding.

---

## 16.2 MachineConfigPool stuck `UPDATING=True`

Check:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
```

Find degraded nodes:

```bash
oc get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\t"}{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}{end}'
```

Check MCD pod on a specific node:

```bash
NODE=<node-name>
MCD_POD=$(oc -n openshift-machine-config-operator get pod -l k8s-app=machine-config-daemon --field-selector spec.nodeName=$NODE -o name)
echo $MCD_POD
oc -n openshift-machine-config-operator logs $MCD_POD -c machine-config-daemon --tail=200
```

---

## 16.3 MachineConfigPool `DEGRADED=True`

Describe pool:

```bash
oc describe mcp worker
```

Check node annotations:

```bash
oc get node <node-name> -o yaml | grep -A5 -B5 machineconfiguration
```

Common reasons:

- Manual drift in files managed by MachineConfig.
- Invalid rendered config.
- MCD cannot write the expected file.
- Previous MachineConfig failure still unresolved.
- Node disk or filesystem issue.
- Conflicting MachineConfigs.

For SSH key injection specifically, common admin mistakes include:

- Wrong `name` under `passwd.users`.
- Bad YAML indentation.
- Key wrapped across multiple lines incorrectly.
- Missing `ignition.version`.
- Target role label does not match the intended MCP.

---

## 16.4 YAML mistakes

Bad:

```yaml
sshAuthorizedKeys:
- ssh-ed25519 AAAA...
  admin@example
```

The key got split into two YAML lines incorrectly.

Good:

```yaml
sshAuthorizedKeys:
- "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE admin@example"
```

Bad:

```yaml
passwd:
users:
- name: core
```

Good:

```yaml
passwd:
  users:
  - name: core
```

Validate before applying:

```bash
oc apply --dry-run=client -f 99-worker-core-ssh.yaml
```

## 16.5 Wrong user

Bad:

```yaml
users:
- name: rakesh
  sshAuthorizedKeys:
  - ssh-ed25519 AAAA...
```

MachineConfig-based SSH key changes are for `core` only.

Good:

```yaml
users:
- name: core
  sshAuthorizedKeys:
  - ssh-ed25519 AAAA...
```

SSH with:

```bash
ssh -i ~/.ssh/key core@<node-ip>
```

Not:

```bash
ssh -i ~/.ssh/key root@<node-ip>
ssh -i ~/.ssh/key rakesh@<node-ip>
```

## 16.6 SSH port blocked

Even if keys are correct, SSH can fail because port 22 is not reachable.

From bastion:

```bash
nc -zv <node-ip> 22
```

Alternative:

```bash
timeout 5 bash -c '</dev/tcp/<node-ip>/22' && echo OK || echo FAIL
```

Check cloud/security/network:

- Security group
- Firewall
- Routing
- VPN
- Bastion ACL
- Node host firewall
- Network segmentation

OpenShift NetworkPolicy does not control host SSH access to nodes. NetworkPolicy controls pod network traffic, not external SSH to node host port 22.

## 16.7 Private key permissions on client

OpenSSH can reject private keys with loose permissions.

Fix:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/ocp_breakglass
```

Test:

```bash
ssh -i ~/.ssh/ocp_breakglass core@<node-ip>
```

## 17. Security Best Practices

### 17.1 Use individual keys when possible

Avoid one shared private key for all administrators.

Better:

```text
rakesh@bastion
admin2@bastion
sre-oncall@vault-issued
```

This improves accountability and rotation.

### 17.2 Use descriptive key comments

Good public key comment:

```text
rakesh@ocp-prod-breakglass-2026-07-03-ticket-CHG12345
```

This helps during audits.

### 17.3 Keep private keys in a controlled location

Use:

- Password manager or vault
- HSM/SSH CA where available
- Bastion with strong access control
- File permission controls
- MFA on the jump host

Avoid:

- Emailing private keys
- Storing private keys in Git
- Putting private keys in ConfigMaps/Secrets for this purpose
- Copying private keys to cluster nodes

### 17.4 Restrict network access to node SSH

Even with key-based SSH, do not expose node port 22 widely.

Recommended:

- Allow SSH only from bastion or management subnet.
- Deny internet-wide node SSH.
- Monitor port 22 access.
- Use short-lived emergency firewall openings if needed.

### 17.5 Audit usage

Check SSH logs:

```bash
oc adm node-logs <node-name> -u sshd --tail=200
```

Inside node:

```bash
journalctl -u sshd -b
last
who
w
```

### 17.6 Avoid permanent emergency keys

If the purpose is break-glass, create a temporary MachineConfig and delete it after use:

```bash
oc delete mc 99-worker-temp-breakglass-ssh
oc get mcp worker -w
```

Then verify the key no longer works.

### 17.7 Do not bypass OpenShift RBAC culture

SSH access bypasses many Kubernetes/OpenShift audit and RBAC workflows. Treat it as privileged infrastructure access.

## 18. Advanced Key Options

OpenSSH authorized key lines can include options before the key, such as:

```text
from="10.10.10.5",no-agent-forwarding,no-port-forwarding ssh-ed25519 AAAA... admin@bastion
```

In YAML:

```yaml
sshAuthorizedKeys:
- 'from="10.10.10.5",no-agent-forwarding,no-port-forwarding ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEXAMPLE admin@bastion'
```

Use carefully.

Options that can be useful:

```text
from="<source-ip-or-cidr>"
no-agent-forwarding
no-port-forwarding
no-X11-forwarding
```

Be careful with:

```text
no-pty
command="..."
```

For emergency node troubleshooting, you usually need an interactive shell, so `no-pty` or forced command restrictions can block your own recovery path.

Always test advanced options on non-production or a single custom pool first.

## 21. Difference Between SSH Key and Core Password

OpenShift also has a MachineConfig procedure for setting a password hash for the `core` user, but that is not the same as SSH key injection.

Key differences:

| Item | SSH key injection | Core password hash |
|---|---|---|
| Purpose | SSH key login | Serial console / BMC access |
| Field | `sshAuthorizedKeys` | `passwordHash` |
| User | `core` | `core` |
| Works with SSH | Yes | No, for the documented purpose |
| Primary use | SSH node access | Console recovery |

Do not confuse these two.

Example password hash config:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: set-core-user-password
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    passwd:
      users:
      - name: core
        passwordHash: "$6$..."
```

Use this only when you specifically need console/BMC access and your security policy allows it.

## 25. Deep-Dive: Rendered MachineConfig Behavior

OpenShift does not directly apply every MachineConfig object independently as a separate transaction. The MCO renders MachineConfigs for a pool into a rendered MachineConfig.

View rendered configs:

```bash
oc get mc | grep rendered-worker
```

Find current rendered config for a node:

```bash
NODE=<node-name>
CURRENT=$(oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}')
echo $CURRENT
oc get mc $CURRENT -o yaml
```

A common advanced troubleshooting step is to compare the intended MachineConfig and rendered MachineConfig:

```bash
oc get mc 99-worker-core-ssh -o yaml > intended.yaml
oc get mc $CURRENT -o yaml > rendered.yaml
```

Then inspect:

```bash
grep -n "sshAuthorizedKeys" -A10 rendered.yaml
```

If the rendered config does not contain your key, check:

- Wrong role label
- Custom MCP selector mismatch
- GitOps reverted your object
- YAML did not apply
- Object name conflict
- You are looking at the wrong node/pool

## 26. Deep-Dive: Configuration Drift

Configuration drift means the node’s on-disk state differs from the MachineConfig-managed desired state.

Manual edits such as this are bad as a permanent fix:

```bash
vi /home/core/.ssh/authorized_keys
```

Why?

- It may not persist across reconciliation or replacement.
- It is not visible in cluster configuration.
- It can trigger degraded state for MCO-managed files.
- It creates inconsistent nodes.
- New nodes will not receive the manual change.

Correct approach:

```bash
oc apply -f 99-worker-core-ssh.yaml
```

Then verify with:

```bash
oc get mcp
oc debug node/<node>
chroot /host
cat /home/core/.ssh/authorized_keys
```

## 27. Deep-Dive: SSH vs Host Network vs Pod Network

SSH to a node is host-level network access:

```text
admin workstation/bastion -> node IP -> TCP/22 -> sshd on host
```

This is different from pod traffic:

```text
pod -> service -> endpoint -> pod
```

Therefore:

- NetworkPolicy does not grant node SSH.
- Service/Route configuration does not expose node SSH.
- Cluster Ingress does not control node SSH.
- Cloud security groups, firewalls, routing, and bastion policies matter.

Troubleshooting examples:

```bash
nc -zv <node-ip> 22
traceroute <node-ip>
ssh -vvv core@<node-ip>
```

On the node:

```bash
sudo ss -lntp | grep ':22'
sudo systemctl status sshd
```

## 28. Deep-Dive: Master Nodes

Be especially careful with control plane nodes.

Do not casually SSH into masters and make changes. Control plane nodes run critical static pods:

- etcd
- kube-apiserver
- kube-controller-manager
- kube-scheduler

Useful read-only inspection commands over SSH:

```bash
sudo -i
crictl ps -a
crictl ps -a | egrep 'etcd|kube-apiserver|kube-controller|kube-scheduler'
journalctl -u kubelet -b --no-pager | tail -200
ls -l /etc/kubernetes/manifests
```

Dangerous actions unless under a documented recovery procedure:

```bash
rm -f /etc/kubernetes/manifests/etcd-pod.yaml
systemctl restart kubelet
rm -rf /var/lib/etcd
reboot
```

Control plane recovery should follow Red Hat procedures and be performed with extreme care.

## 31. Common Bad Practices and Safer Alternatives

| Bad practice | Why bad | Safer alternative |
|---|---|---|
| SSH to every node and edit files | Creates drift | Use MachineConfig |
| Shared private key among many admins | No accountability | Individual keys or SSH CA |
| Keep emergency key forever | Persistent risk | Temporary MachineConfig with expiry |
| Remove old key before testing new key | Lockout risk | Add-test-remove |
| Use root SSH | Not OpenShift model | Use `core`, then sudo if needed |
| Expose node SSH to internet | Attack surface | Bastion-only access |
| Store private key in Git | Credential leak | Vault/password manager |
| Mix SSH change with kernel args | Unclear rollout/reboot | Separate MachineConfigs |
| Ignore MCP degraded state | Future updates blocked | Fix degradation immediately |

## 32. Interview-Style Explanation

A strong senior answer:

> In OpenShift 4, RHCOS nodes are managed through the Machine Config Operator. SSH key injection means declaring SSH public keys for the `core` user through installation Ignition or a Day-2 MachineConfig. Post-installation, I would add keys under `spec.config.passwd.users[].sshAuthorizedKeys` with `name: core`, target the correct MachineConfigPool using `machineconfiguration.openshift.io/role`, apply the manifest, then monitor `oc get mcp`. I would verify the rendered config, node annotations, and actual authorized key files using `oc debug node` or real SSH. I would not create new users or manually edit authorized_keys because that causes drift and is unsupported. For production, I would rotate keys safely using add-test-remove, restrict SSH to a bastion, audit sshd logs, and remove temporary break-glass keys after use.

## 33. Real-World Scenario: Lost Original Private Key

Problem:

```text
Cluster was installed with an SSH key, but the private key is lost.
API access still works.
Need node SSH for recovery/debugging.
```

Solution:

1. Generate a new key pair.
2. Add the new public key through MachineConfig for the required pool.
3. Monitor MCP.
4. Test SSH.
5. Remove or rotate old keys if required and actually verify old key failure.

Commands:

```bash
ssh-keygen -t ed25519 -C "replacement-key-$(date +%F)" -f ~/.ssh/ocp_replacement

```

## 34. Real-World Scenario: Need SSH Only on One Node

MachineConfig targets pools, not individual nodes. If you need SSH only on one node, you have options:

### Option A: Temporary custom MCP

- Label the node with a custom role.
- Create a custom MCP selecting that role.
- Apply MachineConfig to that custom role.

This is clean but operationally heavier.

### Option B: Apply to pool temporarily

- Apply temporary key to worker pool.
- Use it for incident work.
- Remove it quickly.
- Audit usage.

This is simpler but broader.

### Option C: Use `oc debug node`

If API and CRI-O work, prefer `oc debug node` and avoid SSH.

## 35. Real-World Scenario: SSH Works on Workers but Not Masters

Check:

```bash
oc get mc | grep -i ssh
oc get mcp master worker
```

- You applied key to `worker` role only.

```yaml
metadata:

    machineconfiguration.openshift.io/role: master
```

## 36. Real-World Scenario: Key Added but Duplicate Appears

Duplicates can happen if:

- The key exists in installation-time Ignition content.
- The key exists in multiple MachineConfigs.
- You created separate temporary MachineConfigs without cleanup.
- GitOps reintroduced a key.

Check all sources:

```bash
oc get mc -o yaml | grep -n "ssh-ed25519\|ssh-rsa" -A1 -B3
oc get mc | grep -i ssh
oc debug node/<node>
chroot /host
find /home/core/.ssh -maxdepth 3 -type f -print -exec cat {} \;
```

Cleanup source-of-truth manifests, then apply.

## 37. Real-World Scenario: Need to Remove All SSH Access

Be careful. Removing all SSH keys can reduce your disaster recovery options.

Steps:

1. Confirm alternative access exists: `oc debug node`, BMC, serial console, cloud console.
2. Back up existing MachineConfigs.
3. Remove keys from MachineConfig source of truth.
4. Apply.
5. Monitor MCP.
6. Test that SSH fails.
7. Document the change.

Example empty key list is not always the best style. Prefer removing the SSH MachineConfig or managing an explicit approved list. If you keep an explicit list, ensure it reflects your desired state and verify the rendered config.

## 43. Key Takeaways

- SSH key injection in OpenShift should be declarative and MachineConfig-driven.
- The supported user for MachineConfig SSH key updates is `core`.
- Use `sshAuthorizedKeys` under `spec.config.passwd.users`.
- Target nodes through `machineconfiguration.openshift.io/role` and MCP design.
- Prefer `oc debug node` for normal troubleshooting.
- Use SSH as break-glass or low-level recovery access.
- Do not manually edit node files as a permanent fix.
- Rotate keys using add-test-remove.
- Restrict SSH network access to bastions or management networks.
- Verify actual rendered config and node key files.
- Remove temporary access after incidents.
