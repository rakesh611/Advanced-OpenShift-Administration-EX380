## 1. What “Registry Trust Config” Means

In OpenShift, **registry trust config** means configuring the cluster and its nodes to trust the TLS certificate chain of an external or private container image registry.

A registry can be reachable and authenticated, but image pulls can still fail if the node does not trust the registry certificate authority.

Typical error:

```text
Failed to pull image "registry.example.com:5000/app/backend:v1":
rpc error: code = Unknown desc = reading manifest latest in registry.example.com:5000/app/backend:
ping registry registry.example.com:5000: Get "https://registry.example.com:5000/v2/":
tls: failed to verify certificate: x509: certificate signed by unknown authority
```

This is not mainly a Kubernetes Deployment issue. It is a **node-level container runtime trust issue**.

When a pod is scheduled on a node, the kubelet asks CRI-O to pull the image. CRI-O, through the container image libraries, connects to the registry over HTTPS. If the registry certificate is signed by a private corporate CA, self-signed CA, internal PKI, or mirror-registry CA that is not trusted on the node, the image pull fails before authentication or image download can complete.

Registry trust config answers this question:

> “Which custom certificate authorities should OpenShift nodes trust when pulling, pushing, importing, mirroring, or building images from specific image registries?”

## 2. Why Registry Trust Matters in Production OpenShift

In real production OpenShift environments, image registries are rarely only public registries. You commonly see:

- Red Hat registry: `registry.redhat.io`
- Quay: `quay.io`
- Internal Red Hat Quay registry
- JFrog Artifactory
- Sonatype Nexus
- Harbor
- IBM Cloud Container Registry
- AWS ECR, Azure ACR, GCP Artifact Registry
- Disconnected mirror registry
- Local registry for edge or air-gapped sites
- Security-scanned golden-image registry

Many enterprises use an internal PKI. The registry might present a certificate signed by:

- Internal root CA
- Intermediate CA
- Self-signed test CA
- Corporate TLS inspection proxy CA
- Mirror registry generated CA

From a platform-admin perspective, registry trust is critical because it directly affects:

- Pod startup
- Deployment rollouts
- BuildConfig image pulls
- ImageStream imports
- Operator installation
- Cluster upgrades in disconnected environments
- MachineConfig rollout stability
- Developer self-service
- Supply-chain security
- Compliance controls around allowed registries

A single missing CA can block workloads cluster-wide.

## 3. Image Pull Flow at Node Level

A simplified OpenShift image pull flow looks like this:

```text
Pod spec / Deployment / Build / Operator
        |
        v
Kubernetes scheduler places pod on a node
        |
        v
kubelet on that node sees image requirement
        |
        v
kubelet calls CRI-O through CRI
        |
        v
CRI-O uses containers/image libraries
        |
        v
Runtime reads registry policy and registry config
        |
        +--> /etc/containers/registries.conf
        +--> /etc/containers/registries.conf.d/*
        +--> /etc/containers/policy.json
        +--> registry CA trust files / system trust
        |
        v
TLS connection to registry
        |
        +--> CA trusted? yes -> continue
        +--> CA trusted? no  -> x509 error
        |
        v
Authentication using pull secret if required
        |
        v
Manifest fetch
        |
        v
Layer download
        |
        v
Container starts
```

Important point:

> Pull secret and CA trust are different layers. A correct pull secret cannot fix an untrusted TLS certificate. A correct CA cannot fix bad credentials.

## 4. Main Objects and Components

### 4.1 `image.config.openshift.io/cluster`

This is the cluster-wide Image configuration resource.

It controls several image registry behaviors, including:

- Additional trusted CAs for image registry access
- Allowed registries
- Blocked registries
- Insecure registries
- Container runtime search registries

Example command:

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Important fields:

```yaml
spec:
  additionalTrustedCA:
    name: registry-cas
  registrySources:
    allowedRegistries:
    - registry.redhat.io
    - quay.io
    - image-registry.openshift-image-registry.svc:5000
    - registry.example.com:5000
    blockedRegistries:
    - untrusted.example.com
    insecureRegistries:
    - dev-insecure.example.com:5000
    containerRuntimeSearchRegistries:
    - registry.example.com:5000
```

### 4.2 ConfigMap in `openshift-config`

The recommended registry CA configuration uses a ConfigMap in the `openshift-config` namespace.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: registry-cas
  namespace: openshift-config
data:
  registry.example.com: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
  registry-with-port.example.com..5000: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

### 4.3 Machine Config Operator

The **Machine Config Operator (MCO)** manages operating-system-level node configuration in OpenShift 4.x.

It manages or participates in changes related to:

- RHCOS node configuration
- CRI-O configuration
- kubelet configuration
- systemd units
- kernel arguments
- files on disk
- registry-related node configuration
- MachineConfigPool rollout

For registry configuration, the MCO is important because registry-related settings eventually need to be reflected on nodes where CRI-O runs.

### 4.4 Machine Config Daemon

The **Machine Config Daemon (MCD)** runs on each node as part of the MCO stack. It applies rendered machine configuration to the host, performs drift checks, and reports node-level state back to the MCO.

Common MCD states:

```bash
oc get nodes
oc get mcp
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon
```

### 4.5 CRI-O

OpenShift uses **CRI-O** as the Kubernetes container runtime. CRI-O is responsible for pulling images for pods.

For registry trust, CRI-O relies on container image configuration and certificate trust available on the host.

### 4.6 `registries.conf`

Common file:

```text
/etc/containers/registries.conf
```

This controls registry behavior such as:

- Registry mirrors
- Blocked registries
- Insecure registries
- Search registries

### 4.7 `policy.json`

Common file:

```text
/etc/containers/policy.json
```

This file is related to image signature policy and allowed registry behavior.

### 4.8 Global Pull Secret

The global pull secret is authentication-related, not TLS trust-related.

Common secret:

```bash
oc get secret pull-secret -n openshift-config
```

Use it for credentials to registries, not CA trust.

## 5. The Recommended Way: `additionalTrustedCA`

For image registry CA trust, the recommended OpenShift-native method is:

1. Create a ConfigMap in `openshift-config`.
2. Add each registry CA as a key/value pair.
3. Reference the ConfigMap in:

```yaml
image.config.openshift.io/cluster.spec.additionalTrustedCA.name
```

Example:

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=registry.example.com..5000=/path/to/ca.crt

oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

This tells OpenShift:

> “When the cluster contacts this external registry, trust this PEM-encoded CA certificate.”

This is better than manually copying certificates to every node because it is:

- Declarative
- Cluster-managed
- Survives node replacement
- Auditable
- Compatible with MachineConfig/MCO node reconciliation
- Easier to GitOps
- Safer than SSH-based node changes

## 6. ConfigMap Key Format: The Most Common Mistake

The ConfigMap key must match the registry host.

### Registry without port

Registry:

```text
registry.example.com
```

ConfigMap key:

```yaml
data:
  registry.example.com: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

### Registry with port

Registry:

```text
registry.example.com:5000
```

ConfigMap key:

```yaml
data:
  registry.example.com..5000: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

Do **not** use this in the ConfigMap key:

```yaml
registry.example.com:5000: |
```

Use this:

```yaml
registry.example.com..5000: |
```

Reason: in this OpenShift ConfigMap format, the colon in `host:port` is represented as two dots: `host..port`.

### Practical mapping table

| Registry endpoint used in image pull | ConfigMap key |
|---|---|
| `registry.example.com` | `registry.example.com` |
| `registry.example.com:443` | `registry.example.com..443` |
| `registry.example.com:5000` | `registry.example.com..5000` |
| `mirror.ocp4.example.com:8443` | `mirror.ocp4.example.com..8443` |
| `quay.company.local` | `quay.company.local` |

## 7. End-to-End Implementation: Private Registry with Custom CA

Scenario:

```text
Registry: registry.ocp4.example.com:8443
Image:    registry.ocp4.example.com:8443/rhel9/mysql-80:latest
CA file:  /tmp/registry-ca.crt
```

### Step 1: Confirm the failure

Create a test namespace:

```bash
oc new-project registry-trust-test
```

Try to pull an image:

```bash
oc run pull-test \
  --image=registry.ocp4.example.com:8443/rhel9/mysql-80:latest \
  --restart=Never \
  -n registry-trust-test
```

Check events:

```bash
oc describe pod pull-test -n registry-trust-test
```

If trust is missing, you might see:

```text
x509: certificate signed by unknown authority
```

### Step 2: Validate registry certificate manually

From an admin workstation:

```bash
openssl s_client \
  -connect registry.ocp4.example.com:8443 \
  -servername registry.ocp4.example.com \
  -showcerts </dev/null
```

Check:

```bash
openssl x509 -in /tmp/registry-ca.crt -noout -subject -issuer -dates
```

Confirm:

- Certificate is PEM encoded
- It is a CA certificate or CA chain, not only the leaf server certificate
- It is not expired
- The chain matches the registry certificate
- The registry certificate SAN contains the hostname used in image pull

Important:

```text
CA trust fixes unknown authority.
CA trust does not fix hostname mismatch.
```

If the error says the certificate is valid for `registry.internal.local` but you pull from `registry.ocp4.example.com`, fix the registry certificate SAN or use the correct hostname.

### Step 3: Create or update registry CA ConfigMap

For a registry with port `8443`, use key `registry.ocp4.example.com..8443`.

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.ocp4.example.com..8443=/tmp/registry-ca.crt \
  --dry-run=client -o yaml | oc apply -f -
```

Verify:

```bash
oc get cm registry-cas -n openshift-config -o yaml
```

### Step 4: Patch image configuration

```bash
oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Verify:

```bash
oc get image.config.openshift.io/cluster -o yaml | grep -A3 additionalTrustedCA
```

Expected:

```yaml
additionalTrustedCA:
  name: registry-cas
```

### Step 5: Watch MachineConfigPool status

```bash
oc get mcp
```

Useful watch:

```bash
watch -n 5 'oc get mcp && echo && oc get nodes'
```

Look for:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
```

If a pool is updating, wait until it completes before judging the result.

### Step 6: Test again

Delete the old failed pod:

```bash
oc delete pod pull-test -n registry-trust-test --ignore-not-found
```

Create it again:

```bash
oc run pull-test \
  --image=registry.ocp4.example.com:8443/rhel9/mysql-80:latest \
  --restart=Never \
  -n registry-trust-test
```

Check:

```bash
oc get pod pull-test -n registry-trust-test
oc describe pod pull-test -n registry-trust-test
```

If the pod moves beyond image pull and fails for application reasons, the registry trust part is probably fixed.

## 8. Multiple Registries and CA Bundle Management

A single `additionalTrustedCA` reference points to one ConfigMap. To trust multiple registries, put multiple entries in the same ConfigMap.

Example:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.ocp4.example.com..8443=/tmp/ocp4-registry-ca.crt \
  --from-file=quay.corp.example.com=/tmp/quay-corp-ca.crt \
  --from-file=harbor.dev.example.com..5000=/tmp/harbor-dev-ca.crt \
  --dry-run=client -o yaml | oc apply -f -
```

Patch once:

```bash
oc patch image.config.openshift.io/cluster \
  --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

### Updating an existing ConfigMap safely

Export current data first:

```bash
oc get cm registry-cas -n openshift-config -o yaml > registry-cas.backup.yaml
```

Apply updated version:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.ocp4.example.com..8443=/tmp/ocp4-registry-ca.crt \
  --from-file=quay.corp.example.com=/tmp/quay-corp-ca.crt \
  --from-file=new-registry.example.com..5000=/tmp/new-registry-ca.crt \
  --dry-run=client -o yaml | oc apply -f -
```

Watch rollout:

```bash
oc get mcp -w
```

### Do not accidentally replace existing CAs

A common production mistake is creating a new ConfigMap with only the new registry CA, then patching `additionalTrustedCA` to point to it. That removes trust for old private registries.

Safer approach:

1. Export existing ConfigMap.
2. Add new key.
3. Apply the merged ConfigMap.
4. Keep the same ConfigMap name if possible.
5. Validate all registry pulls after rollout.

## 9. How MCO Applies Registry Trust to Nodes

OpenShift registry trust is not just an API object. Eventually, the node that pulls the image must have working trust configuration.

The high-level flow is:

```text
Admin creates ConfigMap in openshift-config
        |
        v
Admin patches image.config.openshift.io/cluster
        |
        v
OpenShift operators detect image configuration change
        |
        v
Rendered node configuration changes
        |
        v
Machine Config Operator coordinates application
        |
        v
Machine Config Daemon applies node-level files/config
        |
        v
CRI-O / containers/image can trust the registry CA
```

### What you must monitor

```bash
oc get co machine-config
oc get mcp
oc describe mcp worker
oc describe mcp master
oc get nodes
```

### What can happen during rollout

Depending on OpenShift version and exact registry-related change, MCO may:

- Render a new machine config
- Mark MCP as updating
- Cordon/drain nodes
- Apply node-level changes
- Reboot nodes for some changes
- Uncordon nodes
- Mark MCP updated

For production, always treat registry trust changes as a potential node-level change and plan a maintenance window, especially on busy clusters.

### MCP `maxUnavailable`

MachineConfigPools control how many nodes can update concurrently.

Check:

```bash
oc get mcp worker -o yaml | grep -A3 maxUnavailable
```

Default behavior commonly updates nodes conservatively. Do not aggressively increase `maxUnavailable` on control-plane pools.

### Configuration drift warning

Do not manually SSH into nodes and change registry trust files unless you are doing emergency diagnosis. Manual changes can cause drift or be overwritten by MCO.

Use declarative OpenShift APIs.

## 10. Node-Level Verification

### Step 1: Pick a node

```bash
oc get nodes
```

### Step 2: Debug into the node

```bash
oc debug node/<node-name>
```

Inside debug shell:

```bash
chroot /host
```

### Step 3: Check registry configuration

```bash
cat /etc/containers/registries.conf
ls -l /etc/containers/registries.conf.d/
```

For allowed/blocked/insecure/mirror settings, inspect:

```bash
cat /etc/containers/registries.conf
cat /etc/containers/registries.conf.d/* 2>/dev/null
cat /etc/containers/policy.json
```

### Step 4: Check registry certificate trust files

Depending on version and rendered configuration, registry-specific certificates are commonly placed in certificate directories consumed by container tools. Check common locations:

```bash
find /etc/docker/certs.d -maxdepth 3 -type f -name '*.crt' -o -name 'ca.crt' 2>/dev/null
find /etc/containers/certs.d -maxdepth 3 -type f -name '*.crt' -o -name 'ca.crt' 2>/dev/null
```

For a registry with port, you might see a directory using the normal registry endpoint form, for example:

```text
/etc/docker/certs.d/registry.ocp4.example.com:8443/ca.crt
```

Do not depend only on file location. The real verification is whether CRI-O/podman can pull successfully.

### Step 5: Test with `podman`

From inside node chroot:

```bash
podman pull registry.ocp4.example.com:8443/rhel9/mysql-80:latest
```

For deeper TLS/debug information:

```bash
podman --log-level=debug pull registry.ocp4.example.com:8443/rhel9/mysql-80:latest
```

Exit:

```bash
exit
exit
```

### Step 6: Test with a Kubernetes pod

```bash
oc run trust-test \
  --image=registry.ocp4.example.com:8443/rhel9/mysql-80:latest \
  --restart=Never \
  -n registry-trust-test

oc describe pod trust-test -n registry-trust-test
```

## 11. Testing Image Pulls Correctly

Many admins test only with `curl` or `openssl`. That is useful but incomplete.

### Correct test sequence

1. DNS resolution:

```bash
getent hosts registry.ocp4.example.com
```

2. TCP reachability:

```bash
curl -vk https://registry.ocp4.example.com:8443/v2/
```

3. Certificate chain:

```bash
openssl s_client -connect registry.ocp4.example.com:8443 \
  -servername registry.ocp4.example.com \
  -showcerts </dev/null
```

4. Runtime pull from node:

```bash
podman pull registry.ocp4.example.com:8443/namespace/image:tag
```

5. Pod pull through kubelet/CRI-O:

```bash
oc run image-pull-test --image=registry.ocp4.example.com:8443/namespace/image:tag --restart=Never
```

### Why `curl -k` is not enough

`curl -k` ignores certificate verification. If `curl -k` works but image pulls fail with x509 errors, trust is still broken.

Use `curl` without `-k` when validating trust:

```bash
curl -v https://registry.ocp4.example.com:8443/v2/
```

Possible good result:

```text
HTTP/1.1 401 Unauthorized
```

A `401 Unauthorized` from `/v2/` can be good because it proves TLS succeeded and the registry is asking for authentication.

Bad TLS result:

```text
SSL certificate problem: self signed certificate in certificate chain
```

## 12. Registry Trust vs Pull Secret vs Registry Policy

These are frequently confused.

| Area | Purpose | Common OpenShift config | Failure symptom |
|---|---|---|---|
| CA trust | Trust registry TLS certificate | `spec.additionalTrustedCA` | `x509: certificate signed by unknown authority` |
| Authentication | Login to registry | Pull secret / global pull secret / namespace secret | `unauthorized`, `authentication required` |
| Authorization | User/service account can access repository | Registry-side permissions | `denied`, `requested access denied` |
| Allowed registry policy | Restrict which registries can be used | `spec.registrySources.allowedRegistries` | Pull blocked by policy |
| Blocked registry policy | Explicitly block registry | `spec.registrySources.blockedRegistries` | Pull blocked by policy |
| Insecure registry | Permit HTTP or invalid TLS | `spec.registrySources.insecureRegistries` | HTTPS/TLS failure unless marked insecure |
| Mirror policy | Redirect source image pulls to mirror | IDMS/ITMS/ICSP | Pull goes to wrong source or mirror not used |

### Example: CA good, pull secret bad

Error:

```text
unauthorized: authentication required
```

Fix:

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.ocp4.example.com:8443 \
  --docker-username=<user> \
  --docker-password=<password> \
  --docker-email=<email> \
  -n <namespace>

oc secrets link default regcred --for=pull -n <namespace>
```

### Example: Pull secret good, CA bad

Error:

```text
x509: certificate signed by unknown authority
```

Fix:

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=registry.ocp4.example.com..8443=/tmp/registry-ca.crt \
  --dry-run=client -o yaml | oc apply -f -

oc patch image.config.openshift.io/cluster --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

## 13. Allowed, Blocked, Insecure, and Search Registries

Registry trust is one piece of registry governance. Advanced administrators also control which registries are allowed or blocked.

### 13.1 Allowed registries

Example:

```yaml
spec:
  registrySources:
    allowedRegistries:
    - registry.redhat.io
    - quay.io
    - image-registry.openshift-image-registry.svc:5000
    - registry.ocp4.example.com:8443
```

Important production warning:

If `allowedRegistries` is defined, registries not listed are blocked. You must include required platform registries such as:

- `registry.redhat.io`
- `quay.io`
- Internal OpenShift registry hostname, if used
- Disconnected mirror registries, if used

Check internal registry hostname:

```bash
oc get image.config.openshift.io/cluster -o jsonpath='{.status.internalRegistryHostname}{"\n"}'
```

### 13.2 Blocked registries

Example:

```yaml
spec:
  registrySources:
    blockedRegistries:
    - docker.io
    - untrusted.example.com
```

Do not block platform-critical registries unless you know all payload content is mirrored and your mirror policy is correct.

### 13.3 Insecure registries

Example:

```yaml
spec:
  registrySources:
    insecureRegistries:
    - dev-registry.example.com:5000
```

Use insecure registries only for labs or temporary non-production scenarios.

An insecure registry means one of these:

- Plain HTTP registry
- HTTPS registry with invalid/untrusted certificate, where verification is intentionally bypassed

Security risk:

- Man-in-the-middle exposure
- Credential leakage risk
- Image tampering risk
- Non-compliance with enterprise supply-chain controls

Preferred fix:

```text
Install a valid registry certificate and configure CA trust.
```

### 13.4 Container runtime search registries

Example:

```yaml
spec:
  registrySources:
    containerRuntimeSearchRegistries:
    - registry.ocp4.example.com:8443
```

This controls short image names like:

```text
ubi9/ubi:latest
```

Instead of fully qualified names like:

```text
registry.access.redhat.com/ubi9/ubi:latest
```

Best practice:

> In production, use fully qualified image references. Avoid relying on short-name search behavior.

## 14. Registry Trust in Disconnected and Mirror Environments

Disconnected OpenShift environments usually rely on mirror registries.

Example pull source:

```text
quay.io/openshift-release-dev/ocp-release@sha256:<digest>
```

Mirror:

```text
mirror.ocp4.example.com:8443/openshift-release-dev/ocp-release@sha256:<digest>
```

You need two separate things:

1. Mirror mapping
2. Mirror registry CA trust

### 14.1 Mirror mapping

Modern OpenShift supports:

- `ImageDigestMirrorSet` / IDMS
- `ImageTagMirrorSet` / ITMS
- `ImageContentSourcePolicy` / ICSP, older/deprecated for new deployments

Example IDMS:

```yaml
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: ocp-release-mirror
spec:
  imageDigestMirrors:
  - source: quay.io/openshift-release-dev/ocp-release
    mirrors:
    - mirror.ocp4.example.com:8443/openshift-release-dev/ocp-release
    mirrorSourcePolicy: NeverContactSource
```

### 14.2 Mirror CA trust

Example:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=mirror.ocp4.example.com..8443=/tmp/mirror-ca.crt \
  --dry-run=client -o yaml | oc apply -f -

oc patch image.config.openshift.io/cluster --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

### 14.3 Common disconnected mistake

Admin configures IDMS correctly but forgets CA trust.

Result:

```text
Image pull goes to the mirror, but fails with x509 unknown authority.
```

Another common mistake:

Admin configures CA trust correctly but forgets mirror mapping.

Result:

```text
Node still tries to contact quay.io or registry.redhat.io, which fails in disconnected network.
```

### 14.4 Mirror verification

On node:

cat /etc/containers/registries.conf

## 15. When to Use MachineConfig Directly

Use the OpenShift Image config API first.

Direct MachineConfig registry trust is usually a special-case tool, not the default.

### Recommended method

Use this for normal image registry CA trust:

```text
ConfigMap in openshift-config + image.config.openshift.io/cluster.spec.additionalTrustedCA
```

### Direct MachineConfig may be used when

- You need a host-level CA for non-image-pull tools running on the node.
- You need to trust a CA for custom host services managed through MachineConfig.
- You are building a controlled custom node role with special OS-level trust requirements.
- You have a break-glass workaround approved by Red Hat support or your platform architecture team.
- You need to seed `/etc/pki/ca-trust` for host-level commands that do not use OpenShift image config.

### Avoid direct MachineConfig when

- The requirement is only “pods cannot pull from private registry.”
- You can use `additionalTrustedCA`.
- You are trying to bypass proper registry certificate management.
- You are tempted to manually SSH into every node.
- You are operating managed OpenShift where MachineConfig changes might be restricted.

### Why direct MachineConfig is risky

MachineConfig changes can:

- Trigger MachineConfigPool rollout
- Drain/reboot nodes depending on change
- Affect all nodes in a pool
- Create degraded MCP if file contents drift
- Interact badly with upgrades if not maintained
- Be overwritten by future rendered configs if unmanaged manual changes are made

## 16. MachineConfig Examples for Registry CA Trust

This section is for advanced node-level administration. Prefer `additionalTrustedCA` unless you have a clear reason.

### 16.1 MachineConfig writing registry CA file directly

Example target:

```text
Registry: registry.ocp4.example.com:8443
Node file: /etc/docker/certs.d/registry.ocp4.example.com:8443/ca.crt
Pool: worker
```

First base64 encode CA:

```bash
base64 -w0 /tmp/registry-ca.crt
```

MachineConfig template:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-registry-ocp4-ca
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/docker/certs.d/registry.ocp4.example.com:8443/ca.crt
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,<BASE64_CA_HERE>
```

Apply:

```bash
oc apply -f 99-worker-registry-ocp4-ca.yaml
oc get mcp worker -w
```

Verify:

```bash
oc debug node/<worker>
chroot /host
ls -l /etc/docker/certs.d/registry.ocp4.example.com:8443/ca.crt
podman pull registry.ocp4.example.com:8443/rhel9/mysql-80:latest
```

### 16.2 Butane-style source template

MachineConfig YAML is hard to write manually. Butane is commonly used to generate MachineConfig.

Template:

```yaml
variant: openshift
version: 4.x.0
metadata:
  name: 99-worker-registry-ocp4-ca
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
  - path: /etc/docker/certs.d/registry.ocp4.example.com:8443/ca.crt
    mode: 0644
    overwrite: true
    contents:
      local: registry-ca.crt
```

Generate:

```bash
butane 99-worker-registry-ocp4-ca.bu -d . -o 99-worker-registry-ocp4-ca.yaml
oc apply -f 99-worker-registry-ocp4-ca.yaml
```

Use the Butane version that matches your OpenShift release.

### 16.3 MachineConfig for OS-level CA trust

This is different from registry-specific trust. It places a CA in the system trust anchor path.

Template:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-corp-root-ca
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/pki/ca-trust/source/anchors/corp-root-ca.crt
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,<BASE64_CA_HERE>
    systemd:
      units:
      - name: update-ca-trust-corp.service
        enabled: true
        contents: |
          [Unit]
          Description=Update system CA trust after installing corporate root CA
          After=network-online.target
          Wants=network-online.target

          [Service]
          Type=oneshot
          ExecStart=/usr/bin/update-ca-trust extract

          [Install]
          WantedBy=multi-user.target
```

Use this only when host-level system trust is genuinely required. For normal image pulls, use `additionalTrustedCA`.

### 16.4 Separate worker and master configs

If you apply only to workers, pods scheduled on control-plane nodes might still fail if your cluster allows workloads on control-plane nodes.

For compact clusters or SNO, target the correct pool:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: master
```

or for worker:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

Check pools:

```bash
oc get mcp
oc get nodes --show-labels
```

## 17. Cluster-Wide Custom PKI vs Registry-Specific Trust

OpenShift has more than one CA trust mechanism.

### 17.1 Registry-specific trust

Use for image registries:

```yaml
image.config.openshift.io/cluster:
  spec:
    additionalTrustedCA:
      name: registry-cas
```

Good for:

- Image pulls
- Image pushes in supported flows
- ImageStream imports
- Builds needing registry trust
- External image registry access

### 17.2 Cluster-wide proxy trusted CA

Use for platform components that need a custom CA for egress connections, commonly with cluster proxy or enterprise PKI.

Example:

```bash
oc create configmap custom-ca \
  -n openshift-config \
  --from-file=ca-bundle.crt=/tmp/corp-ca-bundle.crt

oc patch proxy/cluster --type=merge \
  -p '{"spec":{"trustedCA":{"name":"custom-ca"}}}'
```

This is not the same as registry-specific image pull trust.

### 17.3 Workload application CA injection

Applications may need to trust internal APIs, LDAP, Git, Maven, database, or HTTPS endpoints.

That is application trust, not node image pull trust.

Common pattern:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-trusted-ca
  namespace: app-project
  labels:
    config.openshift.io/inject-trusted-cabundle: "true"
```

Mount the injected bundle into pods if the application supports custom CA files.

### 17.4 Summary

| Requirement | Best mechanism |
|---|---|
| Pod image pull from private registry fails with x509 | `image.config.openshift.io/cluster.spec.additionalTrustedCA` |
| Cluster operators need custom CA for external HTTPS/proxy | `proxy/cluster.spec.trustedCA` |
| Application inside pod needs custom CA | Inject CA bundle ConfigMap or app-specific secret/config |
| Host-level command needs custom CA | MachineConfig system trust, carefully |
| Registry uses HTTP | `insecureRegistries`, avoid in production |

## 19. Troubleshooting Matrix

| Symptom | Likely cause | What to check | Fix |
|---|---|---|---|
| `x509: certificate signed by unknown authority` | CA missing or wrong | `additionalTrustedCA`, ConfigMap key, CA chain | Add correct PEM CA with correct key |
| `certificate is valid for X, not Y` | Hostname/SAN mismatch | `openssl s_client`, cert SAN | Fix registry cert or pull using correct hostname |
| `server gave HTTP response to HTTPS client` | Registry is HTTP | Registry endpoint | Use valid HTTPS or mark insecure for non-prod |
| `unauthorized: authentication required` | Missing/wrong pull secret | Namespace secret, SA pull secret, global pull secret | Create/link pull secret |
| `denied: requested access to the resource is denied` | Registry authorization issue | Registry project permissions | Grant registry repo access |
| `manifest unknown` | Wrong tag/path | Image reference | Correct repository/tag/digest |
| `i/o timeout` | Network/firewall/proxy issue | DNS, route, firewall, proxy | Fix connectivity |
| Works with `curl -k`, fails in pod | Trust still broken | CA trust | Configure CA, test without `-k` |
| Works on one node, fails on another | MCP rollout incomplete or node drift | `oc get mcp`, node debug | Wait/fix degraded node |
| New registry broke old registry pulls | ConfigMap replaced old CAs | Compare backup | Merge all CAs into one ConfigMap |
| Port registry still fails | ConfigMap key wrong | `host..port` format | Replace `:` with `..` in key |
| IDMS configured but x509 remains | Mirror CA missing | Mirror registry CA | Add mirror CA to `additionalTrustedCA` |
| `allowedRegistries` breaks Operators | Required registry omitted | Image config allowed list | Add `registry.redhat.io`, `quay.io`, internal/mirror registries |

## 20. Deep-Dive Failure Scenarios

### Scenario 1: Wrong ConfigMap key for registry with port

Image:

```text
registry.ocp4.example.com:8443/app/frontend:v1
```

Wrong ConfigMap:

```yaml
data:
  registry.ocp4.example.com:8443: |
    -----BEGIN CERTIFICATE-----
```

Correct ConfigMap:

```yaml
data:
  registry.ocp4.example.com..8443: |
    -----BEGIN CERTIFICATE-----
```

Fix:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.ocp4.example.com..8443=/tmp/registry-ca.crt \
  --dry-run=client -o yaml | oc apply -f -
```

### Scenario 2: CA file contains only server certificate

Admin exports the leaf certificate from browser and adds it as CA.

Symptoms:

```text
x509: certificate signed by unknown authority
```

Check:

```bash
openssl x509 -in registry-ca.crt -noout -text | grep -A3 'Basic Constraints'
```

If not CA:

```text
CA:FALSE
```

Fix:

- Get root CA and intermediate CA from PKI team.
- Build correct CA chain file.
- Apply that as ConfigMap value.

### Scenario 3: Registry certificate SAN mismatch

Error:

```text
x509: certificate is valid for harbor.internal.local, not registry.ocp4.example.com
```

CA trust is not the problem. TLS hostname verification is failing.

Fix options:

- Reissue registry certificate with SAN `registry.ocp4.example.com`.
- Pull using `harbor.internal.local` if that is the correct supported hostname.
- Do not use insecure registry as a permanent workaround.

### Scenario 4: Pull secret missing after CA fix

Initial error:

```text
x509: certificate signed by unknown authority
```

After CA fix:

```text
unauthorized: authentication required
```

This means TLS trust is now working and the workflow reached authentication.

Fix:

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.ocp4.example.com:8443 \
  --docker-username=<user> \
  --docker-password=<password> \
  --docker-email=<email> \
  -n app-ns

oc secrets link default regcred --for=pull -n app-ns
```

### Scenario 5: Allowed registries accidentally block internal registry

Config:

```yaml
spec:
  registrySources:
    allowedRegistries:
    - registry.redhat.io
    - quay.io
```

App image:

```text
image-registry.openshift-image-registry.svc:5000/app/backend:latest
```

Problem:

Internal registry is not in allowed list.

Fix:

```bash
INTERNAL=$(oc get image.config.openshift.io/cluster -o jsonpath='{.status.internalRegistryHostname}')
echo $INTERNAL
```

Add it:

```yaml
spec:
  registrySources:
    allowedRegistries:
    - registry.redhat.io
    - quay.io
    - image-registry.openshift-image-registry.svc:5000
```

### Scenario 6: Works with podman on admin laptop but fails on OpenShift

The laptop trusts the CA, but the OpenShift nodes do not.

Fix:

- Configure OpenShift node trust using `additionalTrustedCA`.
- Do not assume laptop trust equals cluster trust.

### Scenario 7: Works on current nodes but fails after node replacement

Someone manually copied CA files to nodes.

When a new node joins, it does not have the manual file.

Fix:

- Remove manual process.
- Use declarative OpenShift config.
- Apply `additionalTrustedCA` or a proper MachineConfig.

### Scenario 8: MCP degraded after custom MachineConfig

Symptoms:

```bash
oc get mcp
```

Shows:

```text
worker   UPDATED=False   UPDATING=False   DEGRADED=True
```

Check:

```bash
oc describe mcp worker
oc get nodes
oc describe node <node>
oc logs -n openshift-machine-config-operator \
  -l k8s-app=machine-config-daemon \
  -c machine-config-daemon --tail=100
```

Common causes:

- Invalid Ignition format
- Bad base64 data URI
- File mode error
- Manual node drift
- File managed by two MachineConfigs
- Systemd unit failure

Fix:

- Correct MachineConfig.
- Avoid overlapping file ownership.
- Prefer `additionalTrustedCA` for registry trust.

## 21. Security Best Practices

### 21.1 Use CA trust, not insecure registries

Bad production pattern:

```yaml
spec:
  registrySources:
    insecureRegistries:
    - registry.corp.example.com:5000
```

Better:

```yaml
spec:
  additionalTrustedCA:
    name: registry-cas
```

### 21.2 Do not trust unnecessary CAs

Only add CA certificates required for known registries.

Avoid dumping a huge enterprise CA bundle into registry trust unless required and reviewed.

### 21.3 Use fully qualified image references

Preferred:

```text
registry.ocp4.example.com:8443/team/app:v1.2.3
```

Avoid:

```text
app:v1.2.3
```

Short names can create ambiguity and risk pulling from unintended registries.

### 21.4 Combine trust with allowed registries

Registry trust says:

```text
This registry certificate is trusted.
```

Allowed registry policy says:

```text
Only these registries may be used.
```

For high-security clusters, use both.

### 21.5 Rotate CA before expiry

Check CA expiry:

```bash
oc get cm registry-cas -n openshift-config -o yaml
oc get cm registry-cas -n openshift-config -o jsonpath='{.data}'
```

Export and inspect:

```bash
oc get cm registry-cas -n openshift-config \
  -o jsonpath='{.data.registry\.ocp4\.example\.com\.\.8443}' > ca.crt

openssl x509 -in ca.crt -noout -dates -subject -issuer
```

### 21.6 Use GitOps for registry trust

Store declarative YAML in Git:

```text
cluster-config/
  image-config/
    registry-cas-configmap.yaml
    image-cluster-patch.yaml
  mirrors/
    idms.yaml
  policies/
    allowed-registries.yaml
```

Protect with:

- Pull request review
- Certificate expiry tracking
- Change tickets
- Automated validation

### 21.7 Do not expose credentials to untrusted registries

Be careful with search registries and global pull secret. Image short-name behavior and public registries can expose credentials or create supply-chain ambiguity.

## 24. Interview-Style Questions

### Q1. What is the difference between registry trust and pull secret?

Registry trust validates the TLS certificate chain of the registry. Pull secret provides credentials to authenticate to the registry. TLS trust happens before or during the HTTPS connection setup; authentication happens after the connection is trusted.

### Q2. Where should registry CA ConfigMap be created?

In the `openshift-config` namespace.

### Q3. Which field references the registry CA ConfigMap?

```yaml
image.config.openshift.io/cluster.spec.additionalTrustedCA.name
```

### Q4. How do you write the ConfigMap key for `registry.example.com:5000`?

```text
registry.example.com..5000
```

### Q5. What error indicates missing CA trust?

```text
x509: certificate signed by unknown authority
```

### Q6. What error indicates hostname mismatch?

```text
x509: certificate is valid for <name1>, not <name2>
```

### Q7. Should you fix x509 errors by adding insecure registry?

Not in production. Install a valid certificate and configure CA trust.

### Q8. Does ImageDigestMirrorSet configure registry trust?

No. IDMS configures mirror mapping. You still need CA trust for the mirror registry if it uses a private CA.

### Q9. Why is manually copying CA to nodes bad?

It is not declarative, does not survive replacement, can drift from MCO-managed state, and is hard to audit.

### Q10. What should you monitor after changing image registry config?

```bash
oc get mcp
oc get nodes
oc get co machine-config
oc describe mcp <pool>
```

## 26. Key Takeaways

1. Registry trust config is node-level TLS trust for image registry access.
2. The recommended OpenShift method is `image.config.openshift.io/cluster.spec.additionalTrustedCA` with a ConfigMap in `openshift-config`.
3. The CA certificate must be PEM encoded.
4. ConfigMap keys use `hostname` or `hostname..port` format.
5. Pull secret fixes authentication, not TLS trust.
6. CA trust fixes unknown authority, not hostname mismatch.
7. Insecure registries should be avoided in production.
8. IDMS/ITMS/ICSP configure mirror mapping, not CA trust.
9. MCO/MCD apply node-level registry configuration and can affect MachineConfigPool rollout.
10. Always verify with both node-level `podman pull` and Kubernetes pod image pull.
11. Do not manually copy CA files to nodes as a permanent fix.
12. Maintain registry trust declaratively and track certificate expiry.
