# Chrony Config in MachineConfig and Node-Level Administration  
## Advanced OpenShift Administration Deep Dive

**Audience:** Senior Linux/OpenShift administrators, SREs, platform engineers, and Red Hat OpenShift exam/practice candidates.  
**Experience level:** Written from a production operations perspective, assuming around 10 years of Linux, networking, Kubernetes, and OpenShift administration experience.  
**Focus:** How to configure, validate, troubleshoot, and safely roll out Chrony/NTP settings on OpenShift nodes by using `MachineConfig`, Butane, MachineConfigPool, and node-level diagnostics.

---

## 1. Executive Summary

In OpenShift, node time synchronization is not a minor Linux setting. It affects certificate validity, OAuth/login behavior, etcd stability, audit logs, Prometheus timestamps, image pulls, TLS handshakes, JWT tokens, node heartbeats, and troubleshooting accuracy.

On Red Hat Enterprise Linux CoreOS (RHCOS), you should not manually SSH to every node and edit `/etc/chrony.conf` as a normal operational method. OpenShift nodes are managed by the **Machine Config Operator (MCO)**. The supported operational pattern is:

1. Write the required `chrony.conf` content.
2. Create a Butane config or raw `MachineConfig`.
3. Target the correct node role or custom MachineConfigPool.
4. Apply the MachineConfig.
5. Let the MCO render and roll out the change.
6. Validate `chronyd`, time source selection, and MachineConfigPool health.
7. Troubleshoot with `oc debug node/<node>` and `chroot /host`.

A senior administrator must understand both sides:

- **Linux side:** `chronyd`, `/etc/chrony.conf`, NTP sources, UDP 123, `chronyc tracking`, `chronyc sources`, `makestep`, `rtcsync`, drift files.
- **OpenShift side:** `MachineConfig`, Butane, Ignition, `MachineConfigPool`, rendered configs, node drain/reboot behavior, MCO degraded state, configuration drift, custom pools, rollout safety.

## 2. Why Chrony Matters in OpenShift

Time synchronization is critical in distributed systems. OpenShift is a Kubernetes platform with many components depending on reasonably accurate clocks.

### 2.1 Components impacted by bad time

| Area | Impact of wrong node time |
|---|---|
| TLS certificates | Certificates can appear `NotBefore` or `Expired` even when valid from the CA perspective. |
| OAuth / API login | Login tokens and session validation can fail unexpectedly. |
| etcd | Distributed consensus relies on timely heartbeats and leases. Severe skew can create instability symptoms. |
| Kubelet | Node status updates, lease renewal, and log timestamps become misleading. |
| Prometheus | Metrics may appear missing, stale, or out of order. |
| Alertmanager | Alerts can fire late, resolve incorrectly, or show confusing timestamps. |
| Image registry | TLS and token-based authentication can fail. |
| Audit logs | Investigation timelines become unreliable. |
| Operators | Operators can report degraded conditions with confusing timestamps. |
| Debugging | `oc logs`, `journalctl`, and event timestamps no longer line up. |

### 2.2 Typical symptoms of time drift

You might suspect bad time synchronization when you see:

- TLS errors such as certificate not yet valid or expired.
- OAuth login failures after node reboot or installation.
- Etcd member instability or unusual leader election behavior.
- Events appearing from the future or far past.
- Prometheus gaps or strange query results.
- ClusterOperator messages whose timestamps do not match real events.
- Nodes intermittently `NotReady` with no obvious resource issue.
- Applications failing token validation across pods running on different nodes.

## 3. Chrony Basics for Senior Administrators

Chrony is the time synchronization implementation commonly used on modern RHEL/RHCOS systems.

It has two main components:

| Component | Purpose |
|---|---|
| `chronyd` | The daemon that synchronizes the system clock. |
| `chronyc` | The CLI used to inspect and control `chronyd`. |

Important files and paths:

| Path | Meaning |
|---|---|
| `/etc/chrony.conf` | Main Chrony configuration file. |
| `/var/lib/chrony/drift` | Drift file recording clock gain/loss rate. |
| `/var/log/chrony` | Chrony log directory if logging is enabled. |
| `/run/chrony-dhcp` | Directory used for NTP sources learned from DHCP, when configured with `sourcedir /run/chrony-dhcp`. |
| `/run/chrony/chronyd.sock` | Local Unix socket used by `chronyc`. |

Important ports:

| Port | Protocol | Purpose |
|---|---|---|
| UDP 123 | NTP | Time synchronization traffic. |
| UDP 323 | chronyc command/monitoring access | Usually local-only; do not expose broadly. |

Important commands:

```bash
chronyc tracking
chronyc sources -v
chronyc sourcestats -v
chronyc activity
timedatectl
systemctl status chronyd
journalctl -u chronyd -b
```

## 4. OpenShift Architecture: Chrony Through MachineConfig

### 4.1 Why not edit `/etc/chrony.conf` manually?

In OpenShift 4, nodes are RHCOS-based and managed through declarative configuration. Directly editing a node can create these problems:

- The change is not repeatable.
- Replacement nodes will not get the change.
- The Machine Config Daemon can detect drift if the file is managed by MCO.
- Cluster updates can overwrite or conflict with manual state.
- You lose auditability and GitOps compatibility.

Correct production mindset:

> Treat node OS configuration as cluster configuration, not as one-off server configuration.

### 4.2 Main OpenShift objects involved

| Object | Purpose |
|---|---|
| `MachineConfig` | Declares OS-level changes: files, systemd units, kernel args, etc. |
| `MachineConfigPool` | Groups nodes that receive rendered MachineConfigs. |
| `MachineConfigNode` | Shows per-node update progress and failure phases in newer OpenShift versions. |
| `MachineConfiguration` | Singleton MCO operator configuration; used for node disruption policies. |
| Butane config | Human-friendly YAML that generates a MachineConfig/Ignition payload. |
| Ignition | Low-level configuration format consumed by RHCOS/MCO. |

### 4.3 How the rollout works

When you apply a new Chrony MachineConfig:

1. The MCO detects the new `MachineConfig`.
2. The render controller creates a new `rendered-<pool>-<hash>` config.
3. The target `MachineConfigPool` enters `UPDATING=True`.
4. The MCO updates nodes according to pool settings such as `maxUnavailable`.
5. By default, many MachineConfig file changes can trigger drain and reboot unless a supported node disruption policy changes the behavior.
6. Nodes return with the new rendered config.
7. The pool becomes `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`.

## 5. Design Decisions Before Writing Chrony Config

Before applying Chrony to OpenShift nodes, decide the time topology.

### 5.1 Option A: All nodes use enterprise NTP servers

Most common production pattern:

```text
master-0 ─┐
master-1 ─┤
master-2 ─┤──> ntp1.corp.example.com, ntp2.corp.example.com
worker-0 ─┤
worker-1 ─┘
```

Recommended when:

- All nodes can reach enterprise NTP.
- You have reliable internal NTP servers.
- You want a simple, uniform config.

### 5.2 Option B: Control plane nodes use upstream NTP; workers use control plane as NTP servers

Useful in disconnected or tightly firewalled environments:

```text
master-0/master-1/master-2 ──> upstream NTP
workers ──> masters as local NTP sources
```

Considerations:

- Control plane nodes must be allowed to serve NTP.
- Workers must be able to reach control plane nodes on UDP 123.
- You must use `allow <worker-subnet>` in master Chrony config.
- You should avoid overloading control plane nodes in very large environments unless this is explicitly designed.

### 5.3 Option C: DHCP-provided NTP

If your infrastructure provides NTP through DHCP, include:

```text
sourcedir /run/chrony-dhcp
```

Without this directive, Chrony might ignore DHCP-provided NTP sources.

### 5.4 Option D: Disconnected or air-gapped cluster

For disconnected clusters, never depend on public NTP pools. Use:

- Internal NTP appliances.
- GPS-backed time sources.
- Data center time servers.
- Management network NTP.
- Bastion-host or infrastructure-host Chrony server.

Example:

```text
server ntp1.disconnected.example.com iburst
server ntp2.disconnected.example.com iburst
```

## 6. Important Chrony Directives

### 6.1 `server`

Use a specific NTP server.

```text
server ntp1.corp.example.com iburst
server ntp2.corp.example.com iburst
```

Use when:

- You have named enterprise NTP servers.
- You want deterministic source selection.
- You do not want pool rotation.

### 6.2 `pool`

Use a pool of NTP servers.

```text
pool 0.rhel.pool.ntp.org iburst
```

Use when:

- Internet access is allowed.
- You want dynamic server selection.
- You are not in a disconnected environment.

For enterprise OpenShift, internal `server` lines are usually preferred over public pools.

### 6.3 `iburst`

```text
server ntp1.corp.example.com iburst
```

`iburst` speeds initial synchronization by sending a burst of packets when the source is unreachable or at startup.

### 6.4 `driftfile`

```text
driftfile /var/lib/chrony/drift
```

Stores the measured rate at which the system clock gains or loses time.

### 6.5 `makestep`

```text
makestep 1.0 3
```

Allows Chrony to step the clock if the offset is larger than 1 second, but only for the first three updates. This is useful at boot, especially for VMs or nodes that were powered off.

Production note:

- Do not allow unlimited time stepping in a steady-state cluster unless you have a strong reason.
- Large time jumps while workloads are running can break applications.

### 6.6 `rtcsync`

```text
rtcsync
```

Enables kernel synchronization of the real-time clock.

### 6.7 `sourcedir`

```text
sourcedir /run/chrony-dhcp
```

Reads additional source definitions from a directory, often used for DHCP-provided NTP servers.

### 6.8 `allow`

```text
allow 10.10.0.0/16
```

Allows clients from the specified network to use this host as an NTP server.

Security note:

- Do not use broad `allow` rules unless required.
- Avoid `allow 0.0.0.0/0` in production.
- Permit only cluster node networks or trusted infrastructure ranges.

### 6.9 `local stratum`

```text
local stratum 10
```

Allows Chrony to serve time even if not synchronized to an upstream source.

Use with extreme caution. This is common in isolated labs but dangerous in production if not designed correctly. It can cause the whole cluster to trust incorrect time.

### 6.10 `cmdallow`, `bindcmdaddress`

These control remote `chronyc` monitoring/command access, normally on UDP 323.

Default local-only behavior is safer. Avoid exposing remote Chrony command access unless required and tightly restricted.

## 7. Recommended Baseline `/etc/chrony.conf` for OpenShift Workers

Example enterprise worker-node config:

```text
server ntp1.corp.example.com iburst
server ntp2.corp.example.com iburst

# Use DHCP-provided NTP sources if the infrastructure provides them.
sourcedir /run/chrony-dhcp

# Record system clock drift.
driftfile /var/lib/chrony/drift

# Allow early boot correction if offset is large.
makestep 1.0 3

# Sync real-time clock from system clock.
rtcsync

# Log directory.
logdir /var/log/chrony
```

For disconnected clusters:

```text
server ntp1.infra.example.com iburst
server ntp2.infra.example.com iburst
driftfile /var/lib/chrony/drift
makestep 1.0 3
rtcsync
logdir /var/log/chrony
```

## 8. Configure Chrony Using Butane

Red Hat recommends using Butane to create a MachineConfig from a human-readable config.

### 8.1 Worker Chrony Butane file

Create `99-worker-chrony.bu`:

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-chrony
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          server ntp1.corp.example.com iburst
          server ntp2.corp.example.com iburst
          sourcedir /run/chrony-dhcp
          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
```

Important details:

| Field | Meaning |
|---|---|
| `variant: openshift` | Tells Butane this is for OpenShift. |
| `version: 4.21.0` | Should match your OpenShift minor version and end in `.0`. Example: OCP 4.21 uses Butane `4.21.0`. |
| `metadata.name` | MachineConfig name after conversion. |
| `machineconfiguration.openshift.io/role: worker` | Targets the worker pool. |
| `path: /etc/chrony.conf` | File delivered to host OS. |
| `mode: 0644` | File permissions in octal in Butane. |
| `overwrite: true` | Replaces existing file content. |
| `inline` | Human-readable Chrony config content. |

Generate the MachineConfig:

```bash
butane 99-worker-chrony.bu -o 99-worker-chrony.yaml
```

Apply to a running cluster:

```bash
oc apply -f 99-worker-chrony.yaml
```

Monitor:

```bash
oc get mcp worker -w
```

### 8.2 Master/control-plane Chrony Butane file

For control plane nodes, use the `master` role label:

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-master-chrony
  labels:
    machineconfiguration.openshift.io/role: master
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          server ntp1.corp.example.com iburst
          server ntp2.corp.example.com iburst
          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
```

Generate and apply:

```bash
butane 99-master-chrony.bu -o 99-master-chrony.yaml
oc apply -f 99-master-chrony.yaml
oc get mcp master -w
```

Production warning:

- Control-plane node reboots are sensitive.
- Apply during a maintenance window.
- Check etcd health before and after.
- Avoid combining Chrony changes with unrelated MachineConfig changes.

## 10. Production Rollout Strategy

### 10.1 Pre-checks

Before changing Chrony:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes -o wide
```

Check if any pool is already degraded:

```bash
oc get mcp
oc describe mcp worker
oc describe mcp master
```

Do not start a Chrony rollout if:

- `master` or `worker` MCP is already degraded.
- There is an ongoing cluster upgrade.
- Nodes are already under pressure.
- Etcd is unhealthy.
- Many pods cannot be rescheduled.
- PodDisruptionBudgets will block drains.
- You do not have confirmed reachable NTP servers.

### 10.2 Validate NTP reachability before applying

From a node:

```bash
oc debug node/<node-name>
chroot /host
```

Inside the host shell:

```bash
getent hosts ntp1.corp.example.com
getent hosts ntp2.corp.example.com
```

If `nc` is available:

```bash
nc -uvz ntp1.corp.example.com 123
```

For UDP, remember that `nc` results can be inconclusive. Better validation is through Chrony after config is active:

```bash
chronyc sources -v
chronyc tracking
```

### 10.3 Roll out workers first

For most production clusters:

1. Apply worker Chrony config first.
2. Wait until worker MCP is updated.
3. Validate several worker nodes.
4. Apply master Chrony config.
5. Validate control plane nodes.

Commands:

```bash
oc apply -f 99-worker-chrony.yaml
oc get mcp worker -w
```

After completion:

```bash
oc get mcp worker
oc get nodes
```

### 10.4 Then roll out control plane

```bash
oc apply -f 99-master-chrony.yaml
oc get mcp master -w
```

Check etcd and API health:

```bash
oc get co etcd kube-apiserver kube-controller-manager kube-scheduler
oc get pods -n openshift-etcd -o wide
```

### 10.5 Use `maxUnavailable` carefully

Check MCP setting:

```bash
oc get mcp worker -o yaml | grep -A5 maxUnavailable
```

A lower `maxUnavailable` is safer but slower. A higher value can create unnecessary workload disruption.

## 11. Using a Custom MachineConfigPool

A custom pool is useful when only a subset of nodes needs a special Chrony configuration, for example:

- Low-latency nodes.
- Edge nodes.
- Infra nodes.
- Disconnected worker zone.
- Nodes in a restricted network segment.
- Nodes using a local GPS time source.

### 11.1 Label nodes

Example:

```bash
oc label node worker-2.example.com node-role.kubernetes.io/edge=
oc label node worker-3.example.com node-role.kubernetes.io/edge=
```

### 11.2 Create a custom MachineConfigPool

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: edge
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - edge
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/edge: ""
```

Apply:

```bash
oc apply -f mcp-edge.yaml
```

### 11.3 Create Chrony config for the custom pool

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-edge-chrony
  labels:
    machineconfiguration.openshift.io/role: edge
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          server edge-ntp1.example.com iburst prefer
          server edge-ntp2.example.com iburst
          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
```

Generate and apply:

```bash
butane 99-edge-chrony.bu -o 99-edge-chrony.yaml
oc apply -f 99-edge-chrony.yaml
oc get mcp edge -w
```

### 11.4 Custom pool conflict warning

If a node belongs to a custom pool, understand precedence carefully. A custom pool can inherit worker configs and also receive custom configs. Avoid defining `/etc/chrony.conf` in multiple MachineConfigs that target overlapping roles unless you intentionally want one to override another.

Best practice:

- Keep one authoritative Chrony MachineConfig per target role/pool.
- Use naming consistently, such as `99-worker-chrony`, `99-master-chrony`, `99-edge-chrony`.
- Store the source Butane files in Git.

## 12. Control Plane as NTP Server for Workers

This is common in disconnected deployments.

### 12.1 Master/control-plane Chrony config

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-master-chrony-server
  labels:
    machineconfiguration.openshift.io/role: master
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          server ntp1.infra.example.com iburst
          server ntp2.infra.example.com iburst

          # Allow worker node network to query NTP from masters.
          allow 10.128.0.0/14
          allow 192.168.100.0/24

          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
```

### 12.2 Worker Chrony client config

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-chrony-client
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          server master-0.ocp4.example.com iburst
          server master-1.ocp4.example.com iburst
          server master-2.ocp4.example.com iburst
          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
```

### 12.3 Network requirements

Workers must reach masters on UDP 123.

Check from worker host network:

```bash
oc debug node/<worker-node>
chroot /host
chronyc sources -v
```

If workers cannot sync:

- Check DNS resolution for master hostnames.
- Check firewall between node networks.
- Check whether control plane nodes are listening on NTP.
- Check `allow` subnet in master Chrony config.
- Check `chronyc clients` on master nodes.

On a master node:

```bash
chronyc clients
ss -lunp | grep :123
```

## 13. Disabling Chrony With MachineConfig

Disabling Chrony is rarely recommended. In most production clusters, every node should have time synchronization.

Valid cases may include:

- A specialized environment where another supported time-sync mechanism is used.
- Lab testing.
- Vendor-provided time synchronization at the hypervisor layer and an explicit architecture decision exists.

Example MachineConfig to disable `chronyd` for a node role:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-disable-chronyd
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    systemd:
      units:
        - name: chronyd.service
          enabled: false
```

Apply:

```bash
oc apply -f 99-worker-disable-chronyd.yaml
oc get mcp worker -w
```

Validation:

```bash
oc debug node/<worker-node>
chroot /host
systemctl is-enabled chronyd
systemctl status chronyd
```

Production warning:

> Do not disable Chrony just to “fix” a bad NTP source. Fix the source, routing, DNS, or firewall issue instead.

## 14. Node Disruption Policy for Chrony Changes

By default, MachineConfig changes commonly cause drain/reboot. Newer OpenShift versions support **node disruption policies** that can reduce disruption for selected config file changes.

For `/etc/chrony.conf`, you can define a policy to restart `chronyd.service` when the file changes instead of rebooting the node.

Example:

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
spec:
  nodeDisruptionPolicy:
    files:
      - path: /etc/chrony.conf
        actions:
          - type: Restart
            restart:
              serviceName: chronyd.service
```

Apply carefully:

```bash
oc apply -f chrony-node-disruption-policy.yaml
```

Check policy status:

```bash
oc get machineconfiguration cluster -o yaml
```

Important senior-admin warnings:

- Test in non-production first.
- The MCO validates policy formatting, but you are responsible for ensuring the action is operationally correct.
- Some MachineConfig changes still require reboots regardless of policy.
- If you combine Chrony changes with other MachineConfig changes, another change may still cause a reboot.
- Do not use node disruption policies to hide unsafe operational practices.

## 15. Pausing MachineConfigPool During Planning

You can pause a MachineConfigPool to stop new rendered configs from being applied immediately.

Pause worker MCP:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Apply MachineConfig while paused:

```bash
oc apply -f 99-worker-chrony.yaml
```

Check that rendered config exists but pool is paused:

```bash
oc get mcp worker
oc describe mcp worker
```

Unpause during maintenance window:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
oc get mcp worker -w
```

Warnings:

- Do not leave pools paused long-term.
- Paused pools might miss important configuration propagation.
- Do not pause during cluster upgrade unless you fully understand upgrade impact.
- Always document who paused the pool, why, and when it must be unpaused.

## 16. Validation After Applying Chrony MachineConfig

### 16.1 Cluster-level validation

```bash
oc get mcp
```

Expected:

```text
NAME     CONFIG                 UPDATED   UPDATING   DEGRADED
master   rendered-master-...    True      False      False
worker   rendered-worker-...    True      False      False
```

Check MachineConfigs:

```bash
oc get mc | grep chrony
oc get mc 99-worker-chrony -o yaml
```

Check rendered config name on nodes:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,CURRENT:.metadata.annotations.machineconfiguration\\.openshift\\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\\.openshift\\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\\.openshift\\.io/state
```

### 16.2 MachineConfigNode validation

If your OpenShift version has `MachineConfigNode` resources:

```bash
oc get machineconfignodes
oc describe machineconfignode <node-name>
```

Look for phases such as:

- UpdatePrepared
- Cordoned
- Drained
- AppliedFilesAndOS
- RebootedNode
- Uncordoned
- Updated
- Resumed
- NodeDegraded

### 16.3 Node-level validation with `oc debug`

```bash
oc debug node/<node-name>
chroot /host
```

Check the file:

```bash
cat /etc/chrony.conf
```

Check service:

```bash
systemctl status chronyd
systemctl is-enabled chronyd
journalctl -u chronyd -b --no-pager
```

Check synchronization:

```bash
chronyc tracking
chronyc sources -v
chronyc sourcestats -v
chronyc activity
timedatectl
```

### 16.4 What good output looks like

`chronyc tracking` should show:

- A valid `Reference ID`.
- Reasonable stratum.
- `Leap status : Normal`.
- Small system time offset.
- Reasonable root delay/dispersion.

`chronyc sources -v` should show at least one selected source:

```text
MS Name/IP address         Stratum Poll Reach LastRx Last sample
===============================================================================
^* ntp1.corp.example.com        2   6   377    42   +123us[ +101us] +/-  10ms
^+ ntp2.corp.example.com        2   6   377    39   -211us[ -220us] +/-  12ms
```

Symbols:

| Symbol | Meaning |
|---|---|
| `^*` | Selected source. |
| `^+` | Good candidate source. |
| `^-` | Acceptable but not selected. |
| `^?` | Unreachable or not enough data. |
| `^x` | False ticker. |
| `^~` | Source has too much variability. |

## 17. Troubleshooting Chrony Config on OpenShift

### 17.1 MCP stuck updating

Check:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
```

Common causes:

- Node drain blocked by PodDisruptionBudget.
- Node not rebooting.
- Node is NotReady.
- MachineConfigPool is paused.
- MCD pod issue on node.
- Bad MachineConfig syntax.
- Node cannot apply file due to OS-level error.

Check MCO pods:

```bash
oc get pods -n openshift-machine-config-operator -o wide
```

Check daemon logs:

```bash
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=200
```

For a specific node, find the MCD pod:

```bash
oc get pod -n openshift-machine-config-operator -o wide | grep <node-name>
oc logs -n openshift-machine-config-operator <mcd-pod-name> -c machine-config-daemon
```

### 17.2 MCP degraded after Chrony change

Check:

```bash
oc describe mcp worker
oc get nodes -o wide
oc get mc 99-worker-chrony -o yaml
```

Common causes:

- Invalid Ignition data URI.
- Bad file path.
- Wrong file mode format in raw MachineConfig.
- Unsupported write path.
- Manual edit caused drift.
- Conflicting MachineConfigs manage the same file.
- Generated rendered config cannot apply cleanly.

### 17.3 Chronyd not running

Inside node debug shell:

```bash
systemctl status chronyd
journalctl -u chronyd -b --no-pager
```

Possible causes:

- Syntax error in `/etc/chrony.conf`.
- `chronyd.service` disabled by another MachineConfig.
- Missing DNS resolution for NTP names does not usually stop the service, but prevents sync.
- Service unit override conflict.

Validate config manually:

```bash
chronyd -Q -f /etc/chrony.conf
```

Note:

- `chronyd -Q` can be used for a one-shot query mode, but use carefully on production nodes.
- Do not run commands that fight with the already-running `chronyd` unless you know the impact.

### 17.4 `chronyc sources` shows `^?`

Example:

```text
^? ntp1.corp.example.com   0   6     0     -     +0ns[ +0ns] +/- 0ns
```

Meaning:

- Source is unreachable, unresolved, blocked, or no valid response yet.

Check:

```bash
getent hosts ntp1.corp.example.com
ping -c 3 ntp1.corp.example.com
ip route get <ntp-ip>
```

UDP 123 check:

```bash
tcpdump -ni any udp port 123
```

If `tcpdump` is not available or not permitted, rely on network/firewall checks and Chrony logs.

### 17.5 DNS problem

If using FQDN NTP sources:

```bash
getent hosts ntp1.corp.example.com
resolvectl status
cat /etc/resolv.conf
```

OpenShift DNS problems on nodes can affect Chrony if NTP sources are hostnames. In restricted environments, using IP addresses for NTP sources can reduce dependency on DNS during early boot.

### 17.6 UDP 123 blocked

Symptoms:

- `chronyc sources -v` shows reach `0`.
- No selected source.
- `journalctl -u chronyd` shows timeout or no response.
- One network segment works, another does not.

Fix:

- Allow outbound UDP 123 from nodes to NTP servers.
- If nodes act as NTP servers, allow inbound UDP 123 from client node networks.
- Check external firewalls, hypervisor security groups, cloud network ACLs, and data center routing.

### 17.7 Large time offset

Symptoms:

- TLS errors.
- `chronyc tracking` shows large offset.
- Logs from different nodes disagree by seconds/minutes.

Check:

```bash
chronyc tracking
timedatectl
```

Immediate correction:

```bash
chronyc makestep
```

In OpenShift, do this only if you understand application impact. For persistent behavior, use:

```text
makestep 1.0 3
```

### 17.8 Manual edit caused configuration drift

If `/etc/chrony.conf` is managed by MachineConfig and someone manually edits it, MCD can mark the node degraded.

Check node annotations:

```bash
oc describe node <node-name> | grep -i machineconfiguration -A5
```

Fix options:

1. Revert the manual file to match MachineConfig.
2. Delete or correct the conflicting MachineConfig.
3. Let MCO roll out the desired rendered config.
4. In severe cases, replace the node.

Never make manual edits your standard fix.

### 17.9 Butane version mismatch

If your cluster is OpenShift 4.21, use:

```yaml
variant: openshift
version: 4.21.0
```

If your cluster is OpenShift 4.16, use:

```yaml
variant: openshift
version: 4.16.0
```

The Butane version should match the OpenShift minor version and end in `.0`.

### 17.10 Wrong MachineConfig role label

If you create:

```yaml
labels:
  machineconfiguration.openshift.io/role: workers
```

Instead of:

```yaml
labels:
  machineconfiguration.openshift.io/role: worker
```

The config will not apply to the default worker pool.

Correct default roles:

```text
master
worker
```

Custom roles must match your custom MCP design.

## 18. Rollback and Recovery

### 18.1 Simple rollback

If the Chrony MachineConfig is the only bad change:

```bash
oc delete mc 99-worker-chrony
oc get mcp worker -w
```

Or if you applied from a file:

```bash
oc delete -f 99-worker-chrony.yaml
oc get mcp worker -w
```

The pool should render a previous config and roll back.

### 18.2 Replace with corrected config

Edit Butane source:

```bash
vi 99-worker-chrony.bu
butane 99-worker-chrony.bu -o 99-worker-chrony.yaml
oc apply -f 99-worker-chrony.yaml
```

Monitor:

```bash
oc get mcp worker -w
```

### 18.3 Emergency node-level recovery

Use only when the cluster cannot recover normally.

```bash
oc debug node/<node-name>
chroot /host
```

Inspect:

```bash
cat /etc/chrony.conf
systemctl status chronyd
journalctl -u chronyd -b
```

If a manual file correction is required to clear an outage, document it and immediately convert the correction into a proper MachineConfig. Otherwise the node can degrade again or replacement nodes will not inherit the fix.

## 19. Security Considerations

### 19.1 Do not expose Chrony command interface broadly

Remote `chronyc` access uses UDP 323. Avoid this unless absolutely required.

Risky pattern:

```text
bindcmdaddress 0.0.0.0
cmdallow 0.0.0.0/0
```

Safer pattern:

```text
bindcmdaddress 10.10.10.5
cmdallow 10.10.20.0/24
```

Even then, prefer local-only monitoring through `oc debug`.

### 19.2 Restrict NTP serving

If a node serves time:

```text
allow 10.128.0.0/14
```

Avoid:

```text
allow 0.0.0.0/0
```

### 19.3 Use trusted time sources

For production:

- Prefer enterprise NTP.
- Prefer at least two independent sources.
- Avoid random public NTP servers in regulated environments.
- Document time source ownership.
- Monitor NTP server health.
- Ensure time servers themselves are synchronized.

### 19.4 Audit and compliance

Keep these in Git:

- Butane source files.
- Generated MachineConfig files, if desired.
- Change records.
- NTP server list.
- Maintenance window approvals.
- Rollback plan.
- Validation output.

## 20. Monitoring and Alerting

### 20.1 What to monitor

At minimum:

- `chronyd` service active on all nodes.
- Selected NTP source exists.
- Time offset within acceptable threshold.
- MCP not degraded.
- Nodes not showing drift-related errors.
- Prometheus and Alertmanager timestamps sane.

### 20.2 Practical checks

You can manually sample nodes:

```bash
for node in $(oc get nodes -o name | sed 's#node/##'); do
  echo "===== $node ====="
  oc debug node/$node -- chroot /host chronyc tracking 2>/dev/null | egrep 'Reference ID|System time|Leap status|Stratum' || true
done
```

Depending on cluster security and image availability, `oc debug` loops can be slow. For production, prefer formal node monitoring or compliance tooling.

### 20.3 Useful alerts

Create alerts for:

- Node time offset above threshold.
- Chrony source unreachable.
- Chrony service down.
- MCP degraded.
- MCO degraded.
- Excessive TLS `not yet valid` or `expired` errors.

### 21.1 GitOps workflow

Recommended repository structure:

```text
openshift-node-config/
├── chrony/
│   ├── base/

│   │   ├── 99-master-chrony.bu

│   │   ├── 99-worker-chrony.yaml
│   │   └── 99-master-chrony.yaml
│   └── overlays/
│       ├── prod/
│       ├── dr/
│       └── edge/
```

Pipeline steps:

```bash
butane chrony/base/99-worker-chrony.bu -o chrony/generated/99-worker-chrony.yaml
butane chrony/base/99-master-chrony.bu -o chrony/generated/99-master-chrony.yaml
oc apply --dry-run=server -f chrony/generated/
```

### 21.2 Pre-production validation

Before production rollout:

- Test on non-prod cluster.
- Test on custom MCP with one canary worker.
- Confirm node returns Ready.
- Confirm `chronyc tracking` is normal.
- Confirm no MCO degraded state.
- Confirm workloads tolerate rollout.

### 21.3 Canary rollout with custom MCP

For critical clusters:

1. Label one worker as `chrony-canary`.
2. Create custom MCP for that node.
3. Apply Chrony config only to that MCP.
4. Validate for 24 hours.
5. Roll out to worker pool.
6. Roll out to master pool.

This pattern is especially useful when:

- Changing from public to private NTP.
- Changing to control-plane-as-NTP-server model.
- Moving NTP across networks.
- Introducing node disruption policy behavior.

## 22. Common Mistakes and How to Avoid Them

| Mistake | Result | Prevention |
|---|---|---|
| Editing `/etc/chrony.conf` manually | Drift, non-repeatable config | Always use MachineConfig. |
| Wrong role label | Config does not apply | Use `worker`, `master`, or correct custom role. |
| Bad Butane version | Conversion or compatibility issue | Match OCP minor version, ending in `.0`. |
| Public NTP in disconnected cluster | No sync | Use internal NTP servers. |
| UDP 123 blocked | Sources show `^?` | Validate firewall/routing. |
| Missing `allow` on NTP server nodes | Clients cannot sync | Add specific trusted subnets. |
| Too broad `allow` | Security exposure | Restrict to node/client networks. |
| Forgetting MCP pause | Changes not applied | Check `oc get mcp -o yaml`. |
| Combining many MachineConfig changes | Hard rollback and more disruption | Keep Chrony changes isolated. |
| Leaving MCP paused | Future config/update problems | Unpause after maintenance. |
| Bad raw data URI | MachineConfig degraded | Prefer Butane. |
| Assuming `nc` proves UDP reachability | False confidence | Use `chronyc sources` and logs. |

## 23. Exam / Interview Style Questions

### Q1. How do you configure Chrony on OpenShift worker nodes?

Use a Butane config that writes `/etc/chrony.conf`, generate a `MachineConfig`, apply it, and monitor the worker MCP.

```bash
butane 99-worker-chrony.bu -o 99-worker-chrony.yaml
oc apply -f 99-worker-chrony.yaml
oc get mcp worker -w
```

Validate:

```bash
oc debug node/<worker>
chroot /host
chronyc tracking
chronyc sources -v
```

### Q2. Why should you not manually edit `/etc/chrony.conf` on RHCOS nodes?

Because OpenShift nodes are managed by the MCO. Manual changes are not declarative, are not applied to replacement nodes, can conflict with rendered MachineConfigs, and can cause configuration drift.

### Q3. What object targets worker nodes?

A `MachineConfig` with:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

### Q4. What happens after applying a MachineConfig?

The MCO renders a new config for the pool, updates nodes according to MCP settings, and by default may drain/reboot affected nodes depending on the change and disruption policy.

### Q5. How do you verify Chrony source selection?

```bash
chronyc sources -v
chronyc tracking
```

Look for `^*` in `chronyc sources`, and `Leap status : Normal` in `chronyc tracking`.

### Q6. What port must be open for NTP?

UDP 123.

### Q7. How do workers use DHCP-provided NTP sources?

Include:

```text
sourcedir /run/chrony-dhcp
```

### Q8. How do you roll back a bad Chrony MachineConfig?

```bash
oc delete mc 99-worker-chrony
oc get mcp worker -w
```

Or fix the Butane file, regenerate, and re-apply.

### Q9. How can you reduce reboot disruption for Chrony file changes?

Use a supported node disruption policy for `/etc/chrony.conf` that restarts `chronyd.service`, but test carefully and avoid combining with changes that still require reboot.

### Q10. How do you identify whether a node has applied the desired rendered config?

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,CURRENT:.metadata.annotations.machineconfiguration\\.openshift\\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\\.openshift\\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\\.openshift\\.io/state
```

## 24. Full Practical Lab: Configure Worker Chrony

### Task

Configure all worker nodes to use:

```text
ntp1.corp.example.com
ntp2.corp.example.com
```

### Step 1: Create Butane file

```bash
cat > 99-worker-chrony.bu <<'EOF'

  name: 99-worker-chrony
```

### Step 4: Apply


## 25. Full Practical Lab: Configure Master as NTP Server and Workers as Clients

### Scenario

- Control plane nodes can reach upstream NTP.
- Worker nodes cannot reach upstream NTP.
- Workers can reach masters on UDP 123.

### Step 1: Master Butane

```bash
cat > 99-master-chrony-server.bu <<'EOF'
variant: openshift
version: 4.21.0
metadata:
  name: 99-master-chrony-server
  labels:
    machineconfiguration.openshift.io/role: master
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          server ntp1.infra.example.com iburst
          server ntp2.infra.example.com iburst

          # Allow worker node subnet.
          allow 10.10.20.0/24

          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
EOF
```

Generate/apply:

```bash
butane 99-master-chrony-server.bu -o 99-master-chrony-server.yaml
oc apply -f 99-master-chrony-server.yaml
oc get mcp master -w
```

### Step 2: Worker Butane

```bash
cat > 99-worker-chrony-client.bu <<'EOF'
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-chrony-client
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          server master-0.ocp4.example.com iburst
          server master-1.ocp4.example.com iburst
          server master-2.ocp4.example.com iburst
          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
EOF
```

Generate/apply:

```bash
butane 99-worker-chrony-client.bu -o 99-worker-chrony-client.yaml
oc apply -f 99-worker-chrony-client.yaml
oc get mcp worker -w
```

### Step 3: Validate masters

```bash
oc debug node/master-0.ocp4.example.com
chroot /host
chronyc tracking
chronyc sources -v
chronyc clients
ss -lunp | grep ':123'
```

### Step 4: Validate workers

```bash
oc debug node/worker-0.ocp4.example.com
chroot /host
chronyc tracking
chronyc sources -v
```

Expected:

- Workers should select one of the master nodes as source.
- Masters should show worker clients in `chronyc clients`.

## 28. Real-World Troubleshooting Flow

Use this flow when someone says: “The Chrony MachineConfig is applied, but time sync is not working.”

### Step 1: Confirm pool health

```bash
oc get mcp
oc describe mcp worker
```

If `DEGRADED=True`, fix MCO/MachineConfig first.

### Step 2: Confirm node received config

```bash
oc debug node/<node>
chroot /host
cat /etc/chrony.conf
```

If file is wrong, inspect MachineConfig targeting and rendered config.

### Step 3: Confirm service

```bash
systemctl status chronyd
journalctl -u chronyd -b --no-pager
```

If service is failed, check config syntax.

### Step 4: Confirm source resolution

```bash
getent hosts ntp1.corp.example.com
```

If DNS fails, fix DNS or use IP sources.

### Step 5: Confirm source reachability

```bash
chronyc sources -v
chronyc activity
```

If source is unreachable, check UDP 123 firewall/routing.

### Step 6: Confirm time status

```bash
chronyc tracking
timedatectl
```

If offset is large, decide whether safe to run:

```bash
chronyc makestep
```

Then fix persistent config if needed.

### Step 7: Confirm no manual drift

```bash
oc describe node <node> | grep -i machineconfiguration -A8
```

If drift is present, revert manual changes or roll out corrected MachineConfig.

## 29. Best Practice Recommendations

1. Use internal, reliable NTP sources for production OpenShift.
2. Do not depend on public NTP in disconnected or regulated environments.
3. Manage `/etc/chrony.conf` only through MachineConfig.
4. Use Butane instead of hand-writing raw data URIs.
5. Keep Chrony changes separate from other MachineConfig changes.
6. Roll out workers before masters unless your topology requires masters first.
7. Use a canary custom MCP for high-risk changes.
8. Avoid disabling Chrony.
9. Avoid broad `allow` and remote command access.
10. Monitor both Chrony health and MCP health.
11. Document NTP topology in your platform runbook.
12. Keep rollback commands ready before applying.
13. Validate time after every node OS update or major cluster upgrade.
14. For edge clusters, define local time-source strategy explicitly.
15. Train operations teams not to manually edit RHCOS nodes.

## 31. Final Senior-Level Takeaway

Chrony configuration in OpenShift is not “just edit `/etc/chrony.conf`.” It is a node lifecycle management task.

A production-grade OpenShift administrator should be able to:

- Design the NTP topology.
- Create Butane-based MachineConfigs.
- Target worker, master, or custom MachineConfigPools.
- Predict MCO rollout impact.
- Validate node-level synchronization.
- Troubleshoot Chrony and MCO together.
- Recover safely from bad MachineConfigs.
- Keep the entire configuration auditable and repeatable.

The strongest operational rule is simple:

> If the setting belongs on every node, it belongs in a declarative OpenShift node configuration, not in manual SSH history.
