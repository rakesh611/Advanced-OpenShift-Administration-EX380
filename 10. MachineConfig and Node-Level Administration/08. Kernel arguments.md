# Kernel Arguments in MachineConfig and Node-Level Administration

**Audience:** Advanced OpenShift Administration / DO380-style learning path  
**Experience level:** Senior Linux, Kubernetes, and OpenShift administrator  
**Scope:** Red Hat OpenShift Container Platform 4.x, Red Hat Enterprise Linux CoreOS (RHCOS), Machine Config Operator (MCO), MachineConfigPool (MCP), day-1 and day-2 node boot-time kernel argument management

---

## 1. Executive Summary

Kernel arguments are boot-time parameters passed to the Linux kernel when an OpenShift node starts. In OpenShift Container Platform, you should not manually edit GRUB or bootloader configuration on RHCOS nodes. Kernel arguments are managed declaratively through `MachineConfig` objects, usually by setting:

```yaml
spec:
  kernelArguments:
    - <kernel-argument>
```

The Machine Config Operator renders the final node configuration, applies it to the target MachineConfigPool, drains affected nodes, applies the boot configuration, reboots nodes, and uncordons them when they return healthy.

As a senior administrator, treat kernel arguments as **cluster lifecycle configuration**, not as an ad-hoc node tweak. A wrong argument can make nodes unbootable, can break storage or networking, and can degrade an MCP. Always test on a small or custom worker pool before production rollout.

---

## 2. What Are Kernel Arguments?

Kernel arguments, also called kernel command-line parameters, are values passed to the Linux kernel by the bootloader. They influence early boot behavior and kernel/runtime behavior before user-space services fully start.

Examples:

```text
loglevel=7
rd.multipath=default
root=/dev/disk/by-label/dm-mpath-root
enforcing=0
intel_iommu=on
iommu=pt
hugepagesz=1G
hugepages=4
default_hugepagesz=1G
```

On a running node, you can see active kernel arguments from:

```bash
cat /proc/cmdline
```

In OpenShift, when using `oc debug node/<node>`, check the host kernel command line with:

```bash
oc debug node/<node-name>
chroot /host
cat /proc/cmdline
```

or without `chroot`:

```bash
cat /host/proc/cmdline
```

## 3. Why Kernel Arguments Matter in OpenShift

In a traditional RHEL server, an administrator might edit `/etc/default/grub`, regenerate GRUB configuration, and reboot. On OpenShift RHCOS, this is not the correct operating model.

OpenShift nodes are managed as part of the cluster. The Machine Config Operator owns OS-level configuration such as:

- Files under supported paths such as `/etc` and `/var`
- systemd units and drop-ins
- CRI-O and kubelet-related machine configuration
- Kernel configuration
- Kernel arguments
- Kernel type, such as real-time kernel in supported scenarios
- Some host-level node lifecycle settings

Kernel arguments are important because they affect areas such as:

| Area | Examples |
|---|---|
| Boot diagnostics | `loglevel=7` |
| Storage discovery | `rd.multipath=default`, root disk path arguments |
| Security behavior | SELinux-related arguments such as `enforcing=0` for debugging only |
| Virtualization and device passthrough | `intel_iommu=on`, `amd_iommu=on`, `iommu=pt` |
| Huge pages and memory behavior | `hugepagesz=1G`, `hugepages=<count>` |
| Low-latency tuning | CPU isolation, tickless kernel, RCU callback placement |
| Hardware workaround | Vendor-specific boot or driver parameters |

A kernel argument is powerful because it applies before normal services start. That is also what makes it risky.

## 4. OpenShift Way vs Traditional Linux Way

### 4.1 Traditional RHEL Approach

On a normal RHEL server, you might do something like:

```bash
vi /etc/default/grub
grub2-mkconfig -o /boot/grub2/grub.cfg
reboot
```

or on UEFI:

```bash
grub2-mkconfig -o /boot/efi/EFI/redhat/grub.cfg
```

### 4.2 OpenShift RHCOS Approach

On OpenShift RHCOS nodes, do **not** manage kernel args this way. Instead, create a `MachineConfig`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 05-worker-kernelarg-example
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - loglevel=7
```

Then apply it:

```bash
oc apply -f 05-worker-kernelarg-example.yaml
```

The MCO handles rendering, rollout, drain, reboot, and verification through MCP status.

## 5. Main OpenShift Objects Involved

### 5.1 MachineConfig

A `MachineConfig` is a declarative object that describes host-level configuration to be applied to nodes in a target role or pool.

For kernel arguments, the important field is:

```yaml
spec:
  kernelArguments:
    - <argument>
```

The MachineConfig API defines `kernelArguments` as a list of kernel arguments to be added.

### 5.2 MachineConfigPool

A `MachineConfigPool` groups nodes that receive a rendered machine configuration. Default pools are:

```text
master
worker
```

A node can have multiple labels such as `node-role.kubernetes.io/worker`, but it should belong to only one MCP. Worker-targeted machine configs also affect custom worker pools unless overridden by custom-pool-specific configuration.

### 5.3 Machine Config Operator

The MCO watches MachineConfig and MCP objects, renders final configs, and coordinates updates.

Major MCO components:

| Component | Purpose |
|---|---|
| `machine-config-operator` | Top-level operator control loop |
| `machine-config-controller` | Renders MachineConfigs and updates MCP desired configuration |
| `machine-config-daemon` | Runs on each node and applies config locally |
| `machine-config-server` | Serves Ignition config during node provisioning/joining |

### 5.4 Rendered MachineConfig

The MCO merges all applicable MachineConfig objects into a rendered config such as:

```text
rendered-worker-5d596d9293ca3ea80c896a1191735bb1
rendered-master-23e785de7587df95a4b517e0647e5ab7
```

The rendered config is what the node actually converges toward.

## 6. How Kernel Arguments Are Applied Internally

When you create a MachineConfig containing `spec.kernelArguments`, the process is generally:

1. You create or update a MachineConfig.
2. The MCO detects the new object.
3. The render controller creates a new rendered MachineConfig for the target pool.
4. The target MCP status changes from `UPDATED=True` to `UPDATING=True`.
5. The MCD on each affected node notices that desired config differs from current config.
6. The node is cordoned.
7. Workloads are drained, respecting MCP `maxUnavailable` and workload disruption constraints.
8. The MCD applies the new machine configuration.
9. The node reboots so the new boot arguments take effect.
10. The node returns Ready.
11. The node is uncordoned.
12. MCP eventually returns to `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`.

The critical point: **kernel arguments require a reboot** because the running kernel command line cannot be changed for the already-booted kernel.

## 7. Day-1 vs Day-2 Kernel Arguments

### 7.1 Day-1 Kernel Arguments

Day-1 means kernel arguments are injected before cluster installation completes. This is used when a kernel setting is needed from the first boot.

Use day-1 when:

- The node cannot boot/install correctly without the argument.
- Low-level storage configuration is required before the OS starts normally.
- Low-level networking is required early.
- The setting must exist before the first OpenShift node boot.

Example day-1 flow:

```bash
./openshift-install create manifests --dir <installation_directory>
```

Create a file under:

```text
<installation_directory>/openshift/99-openshift-machineconfig-master-kargs.yaml
```

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-openshift-machineconfig-master-kargs
  labels:
    machineconfiguration.openshift.io/role: master
spec:
  kernelArguments:
    - loglevel=7
```

For workers, change the role and name:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-openshift-machineconfig-worker-kargs
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - loglevel=7
```

Then continue installation.

### 7.2 Day-2 Kernel Arguments

Day-2 means the cluster is already installed and running. You create a MachineConfig and apply it to the live cluster.

Use day-2 when:

- The cluster can already boot and operate.
- You are adding diagnostics, hardware tuning, performance tuning, or storage adjustments after validation.
- You can tolerate controlled MCO drain/reboot rollout.

Example:

```bash
cat <<'EOF' > 05-worker-kernelarg-loglevel.yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 05-worker-kernelarg-loglevel
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - loglevel=7
EOF

oc apply -f 05-worker-kernelarg-loglevel.yaml
```

## 8. Naming and Ordering Strategy

MachineConfigs are processed by name in lexicographic order. The rendered config is built from applicable MachineConfigs.

Common naming patterns:

```text
05-worker-kernelarg-selinuxpermissive
50-worker-kargs-iommu
80-worker-hugepages-kargs
99-worker-kargs-mpath
```

Practical naming recommendations:

| Prefix | Typical Use |
|---|---|
| `00-` | Base cluster-generated configs |
| `01-` | Cluster-generated kubelet/container runtime configs |
| `05-` | Early simple changes or examples |
| `50-` | Organization-managed custom settings |
| `80-` | Feature-specific node tuning |
| `99-` | Late override-style configs, generated or high-priority custom configs |

For production, use descriptive names:

```text
50-worker-kargs-iommu
50-infra-kargs-hugepages
50-gpu-worker-kargs-pcie
99-master-kargs-mpath
```

Avoid vague names such as:

```text
test
karg
new-config
fix-worker
```

## 9. Targeting Master, Worker, Infra, and Custom Pools

### 9.1 Target Worker Nodes

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

### 9.2 Target Control Plane Nodes

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: master
```

OpenShift documentation still uses the `master` MCP/role label in many examples even though the human-facing term is commonly “control plane”.

### 9.3 Target Custom Worker Pool

For special workloads, create a custom MCP such as `gpu-worker`, `storage-worker`, `lowlatency-worker`, or `infra`.

Example MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Then create MachineConfig for that pool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-infra-kargs-example
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  kernelArguments:
    - loglevel=7
```

Important: Custom pools are supported for workers, not for control plane custom MCPs.

## 11. SELinux Kernel Argument Example: `enforcing=0`

### 11.1 What It Does

```text
enforcing=0
```

This configures SELinux to run in permissive mode. In permissive mode, SELinux policy violations are logged but not denied.

### 11.2 Production Warning

Do not use this in production. Disabling SELinux on RHCOS production nodes is not supported. If SELinux has been disabled on a node, the node must be reprovisioned before being returned to a production cluster.

### 11.3 Example for Lab Only

```bash
cat <<'EOF' > 05-worker-kernelarg-selinuxpermissive.yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 05-worker-kernelarg-selinuxpermissive
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - enforcing=0
EOF

oc apply -f 05-worker-kernelarg-selinuxpermissive.yaml
```

### 11.4 Verify

```bash
oc debug node/<worker-node>
cat /host/proc/cmdline | tr ' ' '\n' | grep enforcing
```

Also check SELinux mode:

```bash
chroot /host getenforce
```

Expected for lab:

```text
Permissive
```

## 12. Multipathing Example

Multipathing is a common reason for kernel arguments on bare metal or SAN-attached nodes.

### 12.1 Worker Multipath MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-kargs-mpath
  labels:
    machineconfiguration.openshift.io/role: "worker"
spec:
  kernelArguments:
    - 'rd.multipath=default'
    - 'root=/dev/disk/by-label/dm-mpath-root'
```

Apply:

```bash
oc apply -f 99-worker-kargs-mpath.yaml
```

### 12.2 Master Multipath MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-master-kargs-mpath
  labels:
    machineconfiguration.openshift.io/role: "master"
spec:
  kernelArguments:
    - 'rd.multipath=default'
    - 'root=/dev/disk/by-label/dm-mpath-root'
```

### 12.3 Verify

```bash
oc debug node/<node>
cat /host/proc/cmdline | tr ' ' '\n' | egrep 'rd.multipath|dm-mpath-root'
```

### 12.4 Senior Admin Notes

Multipath kernel args are high-risk because they can influence the root device path. Validate:

```bash
oc debug node/<node>
chroot /host
findmnt /
lsblk
multipath -ll
```

Use day-1 configuration where storage requires multipathing before first boot.

## 13. IOMMU / Device Passthrough Example

IOMMU settings are commonly used for virtualization, SR-IOV, DPDK, GPU, and PCI passthrough scenarios.

Intel example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-worker-kargs-iommu
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - intel_iommu=on
    - iommu=pt
```

AMD example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-worker-kargs-amd-iommu
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - amd_iommu=on
    - iommu=pt
```

Verify:

```bash
oc debug node/<node>
chroot /host
dmesg | egrep -i 'DMAR|IOMMU|AMD-Vi'
cat /proc/cmdline | tr ' ' '\n' | egrep 'iommu|intel_iommu|amd_iommu'
```

Operational advice:

- Enable BIOS/UEFI virtualization and IOMMU settings first.
- Apply to a custom worker pool if only some nodes need passthrough.
- Coordinate with SR-IOV Network Operator, Node Tuning Operator, and hardware vendor guidance.

## 14. Huge Pages Example

Huge pages can be configured through Kubernetes node resources and performance tuning workflows. Some environments also use kernel arguments.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-worker-kargs-hugepages
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - default_hugepagesz=1G
    - hugepagesz=1G
    - hugepages=4
```

Verify:

```bash
oc debug node/<node>
chroot /host
cat /proc/cmdline | tr ' ' '\n' | grep huge
cat /proc/meminfo | grep -i huge
```

Kubernetes-level check:

```bash
oc describe node <node-name> | egrep -i 'hugepages|Allocatable|Capacity' -A8
```

Senior advice:

- Prefer OpenShift performance/tuning APIs where applicable.
- Do not blindly apply huge pages cluster-wide.
- Reserve enough memory for system and workload needs.
- Validate NUMA topology for NFV, telco, and latency-sensitive workloads.

## 15. Low-Latency and CPU Isolation Arguments

Low-latency workloads may use arguments such as:

```text
isolcpus=
nohz_full=
rcu_nocbs=
irqaffinity=
```

However, in OpenShift, do not casually manage these by raw MachineConfig unless you know the platform design. In many telco/NFV environments, the preferred approach is:

- PerformanceProfile API
- Node Tuning Operator
- CPU Manager policy
- Topology Manager policy
- SR-IOV Operator
- Workload partitioning where supported

Raw kernel args are still useful to understand, but production low-latency tuning should be aligned with Red Hat-supported operator workflows.

Example concept only:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-lowlatency-worker-kargs
  labels:
    machineconfiguration.openshift.io/role: lowlatency
spec:
  kernelArguments:
    - nohz_full=2-15
    - rcu_nocbs=2-15
    - isolcpus=managed_irq,2-15
```

Use only after validating:

```bash
lscpu -e
cat /sys/devices/system/cpu/isolated
cat /proc/cmdline
```

## 16. Real-Time Kernel vs Kernel Arguments

Kernel arguments are not the same as changing the kernel package/type.

To switch to a real-time kernel in supported scenarios, use:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-realtime
  labels:
    machineconfiguration.openshift.io/role: "worker"
spec:
  kernelType: realtime
```

Verify:

```bash
oc debug node/<worker-node>
chroot /host
uname -a
```

You should see indicators such as:

```text
rt
PREEMPT RT
```

Senior notes:

- Real-time kernel support is limited to specific use cases and subscriptions.
- It is generally worker-node focused, especially RAN/telco workloads.
- Do not confuse `kernelType: realtime` with `kernelArguments`.
- Kernel type changes also trigger MCO rollout and reboot.

## 18. Operational Rollout Plan for Production

### 18.1 Pre-Change Checklist

Before applying kernel args:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes -o wide
oc get pdb -A
oc adm top nodes
```

Check MCO health:

```bash
oc get pods -n openshift-machine-config-operator
oc get mcp
oc describe mcp worker
```

Confirm no existing degraded state:

```bash
oc get mcp
oc get co machine-config
```

### 18.2 Test on a Custom Pool

Create a canary custom pool if possible:

```bash
oc label node <node-name> node-role.kubernetes.io/kargs-test=
```

Create MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: kargs-test
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - kargs-test
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/kargs-test: ""
```

Create MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-kargs-test-loglevel
  labels:
    machineconfiguration.openshift.io/role: kargs-test
spec:
  kernelArguments:
    - loglevel=7
```

This limits blast radius.

### 18.3 Control Rollout Speed

Check current `maxUnavailable`:

```bash
oc get mcp worker -o yaml | yq '.spec.maxUnavailable'
```

Patch if needed:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

Use this for worker pools where you want one-at-a-time node reboot.

### 18.4 Pause / Unpause MCP

Pause before staging multiple changes:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Apply MachineConfig changes:

```bash
oc apply -f 50-worker-kargs-example.yaml
```

Unpause to roll out:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Check:

```bash
oc get mcp worker -w
```

Caution: Do not forget a pool in paused state. A paused MCP will not apply new rendered configs until unpaused.

## 20. Removing Kernel Arguments

To remove a kernel argument that you added through a MachineConfig, delete the MachineConfig object or remove the argument from the MachineConfig and apply the change.

### 20.1 Delete MachineConfig

```bash
oc delete mc 05-worker-kernelarg-loglevel
```

Watch rollout:

```bash
oc get mcp worker -w
```

Verify after reboot:

```bash
oc debug node/<worker-node>
cat /host/proc/cmdline | tr ' ' '\n' | grep loglevel
```

### 20.2 Edit MachineConfig

```bash
oc edit mc 05-worker-kernelarg-loglevel
```

Remove the unwanted argument from:

```yaml
spec:
  kernelArguments:
```

Then watch MCP rollout.

### 20.3 Important Removal Notes

- Removing the MachineConfig creates a new rendered config.
- Nodes usually reboot again to apply the kernel command-line removal.
- If the removed argument was required for boot, nodes might fail after reboot.
- Always understand why the argument was added before deleting it.

## 21. Troubleshooting Scenarios

### Scenario 1: MCP Stuck Updating

Symptoms:

```bash
oc get mcp
```

```text
worker   UPDATED=False   UPDATING=True   DEGRADED=False
```

Check nodes:

```bash
oc get nodes
```

Check MCP:

```bash
oc describe mcp worker
```

Check MCD logs:

```bash
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --since=2h
```

Common causes:

- Node drain blocked by PodDisruptionBudget.
- Pod uses local storage and cannot be evicted cleanly.
- Node is already NotReady.
- Workload cannot reschedule due to resource constraints.
- MCP `maxUnavailable` too low and first node is stuck.

Actions:

```bash
oc get pdb -A
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
oc describe node <node>
oc get events -A --sort-by=.lastTimestamp | tail -50
```

Do not force drain blindly in production.

---

### Scenario 2: MCP Degraded After Kernel Argument Change

Symptoms:

```text
worker   UPDATED=False   UPDATING=False   DEGRADED=True
```

Inspect:

```bash
oc describe mcp worker
oc get nodes
oc describe node <problem-node>
```

Check node annotations:

```bash
oc get node <node> -o json | jq '.metadata.annotations | with_entries(select(.key|contains("machineconfiguration")))'
```

Check logs:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --since=2h
```

Possible causes:

- Invalid MachineConfig syntax.
- Conflicting MachineConfigs.
- Node failed to reboot into desired config.
- Kernel argument caused boot failure.
- Node configuration drift.

Rollback:

```bash
oc delete mc <bad-machineconfig-name>
oc get mcp <pool> -w
```

If node does not return, use platform console, BMC/IPMI/iDRAC/iLO, or cloud console to inspect boot failure.

---

### Scenario 3: Argument Not Visible in `/proc/cmdline`

Check whether the MachineConfig exists:

```bash
oc get mc | grep -i karg
```

Check correct role label:

```bash
oc get mc <mc-name> -o yaml
```

Verify label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

Check MCP rendered config changed:

```bash
oc describe mcp worker | egrep -i 'config|rendered|message|reason'
```

Check whether pool is paused:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

If `true`, unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Check node current/desired config:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

If current is not desired, rollout is not complete.

---

### Scenario 4: Drain Blocked

MCO cannot reboot a node if it cannot drain it.

Check events:

```bash
oc get events -A --field-selector involvedObject.kind=Node --sort-by=.lastTimestamp
```

Check PDBs:

```bash
oc get pdb -A
```

Check pods on node:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node-name>
```

Dry-run drain:

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Common fixes:

- Temporarily scale workloads if safe.
- Adjust PDB carefully.
- Add capacity so workloads can move.
- Fix pods stuck terminating.
- Remove broken finalizers only when you understand the impact.

---

### Scenario 5: Node Fails to Boot After Bad Kernel Argument

This is the worst-case scenario.

Possible recovery options:

1. Delete or correct the bad MachineConfig if the cluster control plane is still healthy.
2. Use cloud/provider console to reboot or replace the node.
3. For worker nodes, reprovision the node if faster and safer.
4. For control plane nodes, proceed very carefully and follow Red Hat recovery procedures.
5. If etcd/control plane quorum is at risk, stop and involve Red Hat Support.

Commands if API is healthy:

```bash
oc delete mc <bad-machineconfig>
oc get mcp -w
```

If a worker is unrecoverable:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
oc delete node <node>
```

Then replace through MachineSet, bare-metal host, or infrastructure automation.

## 22. Common Mistakes

### Mistake 1: Editing GRUB Manually on RHCOS

Wrong:

```bash
vi /etc/default/grub
grub2-mkconfig ...
```

Correct:

```bash
oc apply -f <machineconfig>.yaml
```

### Mistake 2: Applying to All Workers Without Testing

Wrong:

```yaml
machineconfiguration.openshift.io/role: worker
```

for an untested risky kernel arg across many worker nodes.

Better:

- Create a custom canary MCP.
- Test one node.
- Validate boot, workload, networking, storage, and logs.
- Roll out to the full pool later.

### Mistake 3: Forgetting MCP Pause State

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

### Mistake 4: Expecting Kernel Arg Without Reboot

Kernel args affect boot. The node must reboot.

### Mistake 5: Using SELinux Permissive in Production

`enforcing=0` is not a production fix. It is a debugging tool and not supported for production RHCOS use.

### Mistake 6: Confusing Kernel Arguments and KubeletConfig

Use `KubeletConfig` for kubelet-level settings. Use `MachineConfig.spec.kernelArguments` for kernel boot-time arguments.

### Mistake 7: Confusing Kernel Arguments and Tuned Profiles

Use Tuned/PerformanceProfile for many runtime tuning scenarios. Use kernel arguments only where boot-time parameters are required.

## 23. Security and Compliance Considerations

Kernel arguments can weaken security if misused.

High-risk examples:

| Argument | Risk |
|---|---|
| `enforcing=0` | SELinux permissive mode; not supported in production |
| `selinux=0` | Disables SELinux; dangerous and unsupported for production |
| `audit=0` | Disables audit subsystem behavior; compliance impact |
| `nosmt` | Security/performance tradeoff; may reduce capacity |
| Debug boot args | May expose sensitive details or alter normal hardening |

Before changing kernel args in regulated environments:

```bash
oc get compliancecheckresult -A
oc get scansettingbinding -A
oc get profiles.compliance.openshift.io -A
```

Also update:

- Change request
- Architecture decision record
- Risk assessment
- Rollback plan
- Security exception if applicable

## 25. Practical Lab: Add, Verify, and Remove a Kernel Argument

### Lab Goal

Add `loglevel=7` to worker nodes, verify it, then remove it.

### Step 1: Check Current State

```bash
oc get clusterversion
oc get co machine-config
oc get mcp
oc get nodes
```

### Step 2: Create MachineConfig

```bash
cat <<'EOF' > 05-worker-kernelarg-loglevel.yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 05-worker-kernelarg-loglevel
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - loglevel=7
EOF
```

### Step 3: Apply

```bash
oc apply -f 05-worker-kernelarg-loglevel.yaml
```

### Step 4: Watch MCP

```bash
oc get mcp worker -w
```

Wait until:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
```

### Step 5: Verify Node Annotation

```bash
NODE=$(oc get nodes -l node-role.kubernetes.io/worker= -o jsonpath='{.items[0].metadata.name}')

echo $NODE
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

### Step 6: Verify Kernel Argument

```bash
oc debug node/$NODE -- chroot /host cat /proc/cmdline
```

If your `oc debug` does not support that direct syntax:

```bash
oc debug node/$NODE
cat /host/proc/cmdline | tr ' ' '\n' | grep '^loglevel=7$'
exit
```

### Step 7: Remove

```bash
oc delete mc 05-worker-kernelarg-loglevel
```

### Step 8: Watch Rollback

```bash
oc get mcp worker -w
```

### Step 9: Verify Removal

```bash
oc debug node/$NODE
cat /host/proc/cmdline | tr ' ' '\n' | grep '^loglevel=7$' || echo 'loglevel=7 removed'
exit
```

## 26. Exam / Interview-Style Questions

### Q1. What object is used to add kernel arguments to OpenShift nodes?

`MachineConfig`, using `spec.kernelArguments`.

### Q2. Does adding a kernel argument require node reboot?

Yes. Kernel command-line arguments are read at boot, so affected nodes must reboot.

### Q3. How do you target only worker nodes?

Use the MachineConfig label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

### Q4. How do you verify the active kernel arguments?

```bash
oc debug node/<node>
cat /host/proc/cmdline
```

### Q5. What happens when a MachineConfig is applied?

The MCO renders a new config, updates MCP desired state, cordons and drains nodes, applies the config, reboots nodes, and uncordons them.

### Q6. How do you reduce rollout disruption?

Use:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

Also use custom pools, canary nodes, maintenance windows, PDB review, and MCP pause/unpause.

### Q7. Why is `enforcing=0` dangerous?

It puts SELinux into permissive mode. This is not supported for production RHCOS nodes and should be used only for lab/debug scenarios.

### Q8. How do you roll back a bad kernel argument?

Delete or edit the MachineConfig that added it:

```bash
oc delete mc <machineconfig-name>
```

Then watch MCP rollout.

### Q9. What if a node does not come back after reboot?

Use infrastructure console/BMC/cloud tools to inspect boot, delete or fix the bad MachineConfig if the API is available, and replace worker nodes if necessary. For control plane boot failures, protect quorum and involve vendor support.

### Q10. Is manually editing `/etc/default/grub` on RHCOS recommended?

No. Use MachineConfig.

## 28. Senior Admin Decision Matrix

| Requirement | Recommended Approach |
|---|---|
| Need boot-time kernel behavior after install | Day-2 MachineConfig with `kernelArguments` |
| Need setting before first node boot | Day-1 MachineConfig injected into install manifests |
| Need kubelet behavior change | `KubeletConfig`, not kernel args |
| Need CRI-O behavior change | `ContainerRuntimeConfig` or supported config method |
| Need low-latency workload tuning | PerformanceProfile / Node Tuning Operator, with kernel args only as supported |
| Need real-time kernel | `spec.kernelType: realtime` in supported worker scenarios |
| Need one hardware-specific node group | Custom MCP |
| Need safe rollout | Canary MCP, `maxUnavailable: 1`, maintenance window |
| Need emergency rollback | Delete/edit MachineConfig and watch MCP |

## 30. Key Takeaways

- Kernel arguments are boot-time parameters and require node reboot.
- In OpenShift, manage them declaratively with `MachineConfig.spec.kernelArguments`.
- Do not manually edit GRUB or bootloader configuration on RHCOS nodes.
- The MCO controls rollout through MachineConfigPool state.
- Always verify with `/host/proc/cmdline` from `oc debug node`.
- Use custom MCPs and canary nodes for risky changes.
- Treat SELinux-disabling arguments as lab/debug-only, not production fixes.
- For performance and low-latency workloads, prefer supported OpenShift tuning APIs where applicable.
- Keep rollback commands ready before applying kernel arguments.
