## 1. What RHCOS node management means

In OpenShift 4, node management does **not** mean logging in to every node and editing files manually like a traditional Linux estate. It means declaring the desired operating system and node configuration through OpenShift APIs and allowing OpenShift operators to converge the nodes to that desired state.

RHCOS node management covers:

- Managing the host operating system configuration.
- Managing kernel arguments.
- Managing systemd units and drop-ins.
- Managing files under writable host paths such as `/etc` and `/var`.
- Managing kubelet settings.
- Managing CRI-O/container runtime settings.
- Managing image registry trust, mirrors, and pull configuration.
- Managing node reboots caused by OS or configuration changes.
- Managing node update rollout through MachineConfigPools.
- Detecting and resolving configuration drift.
- Troubleshooting degraded MachineConfigPools and nodes.

For a senior administrator, the important point is this:

> In OpenShift, RHCOS nodes are treated as cluster-managed infrastructure. The cluster owns the host configuration. You should make persistent node changes through OpenShift APIs, not through manual shell changes.

## 2. Why RHCOS is different from normal RHEL node administration

### 2.1 Traditional RHEL administration model

On a normal RHEL server, administrators commonly do the following:

```bash
ssh root@server
yum install package
systemctl edit service
vi /etc/sysctl.conf
vi /etc/crio/crio.conf
reboot
```

That model works when every server is individually administered or managed by tools such as Ansible. But OpenShift has a different requirement: every node in a pool must remain consistent, upgradeable, and recoverable.

### 2.2 RHCOS administration model

RHCOS is an immutable-style container host based on RHEL technologies and designed specifically for OpenShift. It includes:

- RHEL kernel.
- SELinux enabled by default.
- `kubelet` as the Kubernetes node agent.
- CRI-O as the Kubernetes container runtime.
- Ignition for first-boot provisioning.
- OSTree/rpm-ostree based operating system delivery.
- OpenShift-managed update lifecycle.

The important operational differences are:

| Area | Traditional RHEL | RHCOS in OpenShift |
|---|---|---|
| Package management | `yum` / `dnf` per server | OS image/update managed through OpenShift and MCO |
| Persistent node config | Manual or external config management | MachineConfig, KubeletConfig, ContainerRuntimeConfig, cluster Operators |
| `/usr` | Writable through package manager | Read-only operating system content |
| Node changes | SSH and edit | Declarative API objects |
| Updates | Server-by-server package upgrade | Cluster update and MCO rollout |
| Rollback | Manual package rollback or backup | Atomic deployment model with previous OS deployment available |
| Compliance | Server drift common if unmanaged | MCO detects drift for managed files |

### 2.3 RHCOS filesystem concept

A practical senior-admin view:

```text
/usr       Read-only OS content. Do not modify directly.
/etc       Writable, but persistent cluster changes should come from MachineConfig.
/var       Writable runtime/data area.
/boot      Writable boot area, but should be managed by platform workflows.
/var/lib/containers  Container image and runtime storage.
```

Do not think of RHCOS as “RHEL where I can just install RPMs whenever I want.” Think of it as a node operating system image that OpenShift manages as part of the platform lifecycle.

## 3. RHCOS architecture inside OpenShift

### 3.1 High-level architecture

```text
OpenShift API
   |
   |  MachineConfig / KubeletConfig / ContainerRuntimeConfig / MCP
   v
Machine Config Operator
   |
   |  render desired config
   v
Rendered MachineConfig
   |
   |  assigned to MachineConfigPool
   v
Machine Config Daemon on each node
   |
   |  cordon -> drain -> apply -> reboot -> uncordon
   v
RHCOS node desired state
```

### 3.2 Main node management objects

| Object | Purpose |
|---|---|
| `MachineConfig` | Defines low-level host configuration such as files, systemd units, kernel arguments, SSH keys, and OS image references. |
| `MachineConfigPool` | Groups nodes and controls rollout behavior for machine configs. |
| `KubeletConfig` | Provides supported API for kubelet configuration changes. |
| `ContainerRuntimeConfig` | Provides supported API for CRI-O/container runtime changes. |
| `MachineConfiguration` | Singleton MCO operator configuration object for some MCO-level behavior. Do not confuse it with `MachineConfig`. |
| `Node` | Kubernetes object representing a node host. |
| `Machine` / `MachineSet` | Infrastructure-machine API objects for platforms using Machine API. |

### 3.3 Main node management namespaces

```bash
openshift-machine-config-operator
openshift-machine-api
openshift-cluster-version
openshift-kube-apiserver
openshift-kube-controller-manager
openshift-kube-scheduler
openshift-etcd
```

For RHCOS node management, the most important namespace is:

```bash
openshift-machine-config-operator
```

Check MCO components:

```bash
oc get pods -n openshift-machine-config-operator
```

Typical components:

```text
machine-config-controller
machine-config-daemon
machine-config-operator
machine-config-server
```

## 4. Node management control plane: MCO, MCD, MCS, MCC

The Machine Config Operator is the central control mechanism for RHCOS node configuration. It manages the operating system and node-level settings from roughly the kernel up to the kubelet/container runtime layer.

### 4.1 Machine Config Operator (MCO)

The MCO is responsible for:

- Watching MachineConfig-related resources.
- Rendering final machine configs for pools.
- Coordinating updates across node pools.
- Ensuring nodes are configured to the desired state.
- Managing OS updates as part of OpenShift updates.
- Reporting pool and node degradation.

Check operator status:

```bash
oc get co machine-config
oc describe co machine-config
```

Expected healthy output:

```text
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED
machine-config  4.x.y     True        False         False
```

### 4.2 Machine Config Controller (MCC)

The controller watches configuration objects and renders the effective configuration.

It handles:

- Combining base and custom `MachineConfig` objects.
- Generating `rendered-master-*` and `rendered-worker-*` configs.
- Managing rollout state for MCPs.
- Creating machine configs from KubeletConfig and ContainerRuntimeConfig.

Useful check:

```bash
oc get machineconfig | egrep 'rendered|kubelet|containerruntime'
```

### 4.3 Machine Config Daemon (MCD)

The MCD runs as a daemon on every node. It is the worker process that actually applies the desired configuration locally on the node.

It performs tasks such as:

- Checking current node config.
- Comparing current state with desired rendered config.
- Applying files and systemd units.
- Applying kernel arguments.
- Pivoting or updating OS deployment.
- Rebooting the node when required.
- Reporting state through node annotations and MCP status.
- Detecting configuration drift.

Check MCD pods:

```bash
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide
```

View logs for a specific MCD pod:

```bash
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon
```

### 4.4 Machine Config Server (MCS)

The Machine Config Server provides Ignition configuration to machines joining the cluster.

It is especially important during:

- Node first boot.
- New worker node addition.
- Bootstrap/installation phase.
- Bare-metal or UPI environments.

The MCS is not where you normally make day-to-day changes. It is part of the node provisioning and configuration delivery path.

## 5. MachineConfigPool as the node update boundary

### 5.1 What is a MachineConfigPool?

A `MachineConfigPool` groups nodes by role and determines which machine configs apply to those nodes.

Default pools:

```bash
oc get mcp
```

Typical output:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxx        True      False      False
worker    rendered-worker-yyyyyyyyyyyyyyyyyyyyyyyyyyyy        True      False      False
```

### 5.2 MCP relationship with node labels

Nodes are selected by role labels such as:

```text
node-role.kubernetes.io/master=
node-role.kubernetes.io/worker=
```

Check node labels:

```bash
oc get nodes --show-labels
```

A worker node usually has:

```text
node-role.kubernetes.io/worker=
```

A control plane node usually has:

```text
node-role.kubernetes.io/master=
```

or in newer terminology:

```text
node-role.kubernetes.io/control-plane=
```

OpenShift MCP names may still use `master` for historical/API compatibility.

### 5.3 Why MCPs matter in production

The MCP controls:

- Which nodes receive a config.
- How many nodes can be unavailable during update.
- Whether the pool is paused.
- Whether rollout is degraded.
- Whether the pool is fully updated.

Inspect a pool:

```bash
oc describe mcp worker
```

Important fields:

```text
MACHINECOUNT
READYMACHINECOUNT
UPDATEDMACHINECOUNT
DEGRADEDMACHINECOUNT
UNAVAILABLEMACHINECOUNT
CONFIG
UPDATED
UPDATING
DEGRADED
```

### 5.4 maxUnavailable

`maxUnavailable` controls how many nodes in a pool can be unavailable during a rollout.

View it:

```bash
oc get mcp worker -o yaml | grep -A5 maxUnavailable
```

Patch example:

```bash
oc patch mcp worker --type merge -p '{"spec":{"maxUnavailable":1}}'
```

For production, `maxUnavailable: 1` is conservative and common, especially when workloads have tight capacity or strict PDBs.

### 5.5 Pausing an MCP

You can pause a pool to prevent new machine config changes from rolling out:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":true}}'
```

Resume:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":false}}'
```

Important: pausing is not a long-term solution. A paused MCP can block important platform-managed changes, including some certificate or update-related changes. Use it only during controlled maintenance or canary strategies.

### 5.6 Custom MCPs

You create custom MCPs when a subset of workers needs special host configuration.

Examples:

- Infra nodes.
- Logging nodes.
- Storage nodes.
- GPU nodes.
- Low-latency nodes.
- Security-hardened nodes.
- Nodes with custom registry or kernel settings.

Example: label nodes:

```bash
oc label node worker-3.example.com node-role.kubernetes.io/infra=
oc label node worker-4.example.com node-role.kubernetes.io/infra=
```

Create custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Then create MachineConfig with role `infra`:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

Senior-admin warning: custom MCPs are powerful but can create complicated rollout behavior. Always verify which rendered config a node is using.

## 6. MachineConfig fundamentals

### 6.1 What is a MachineConfig?

A `MachineConfig` is an OpenShift custom resource that defines host-level configuration for RHCOS nodes.

It can configure:

- Files.
- Directories.
- File permissions.
- File ownership.
- Systemd units.
- Systemd drop-ins.
- Kernel arguments.
- SSH authorized keys.
- OS image references.
- Some container runtime and registry-related settings indirectly.

MachineConfig uses Ignition-style configuration under the `spec.config` field.

### 6.2 Basic MachineConfig structure

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files: []
    systemd:
      units: []
```

### 6.3 Naming convention

Common naming style:

```text
00-*.yaml   base/generated configs
01-*.yaml   cluster-provided configs
50-*.yaml   intermediate/custom operator configs
99-*.yaml   admin custom configs
```

For admin-created configs, use names like:

```text
99-worker-custom-motd
99-master-kernel-args
99-infra-crio-log-level
```

### 6.4 Role label is critical

This label determines which pool receives the config:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

If you apply the wrong role, you can accidentally reboot the wrong pool.

Examples:

```yaml
machineconfiguration.openshift.io/role: worker
machineconfiguration.openshift.io/role: master
machineconfiguration.openshift.io/role: infra
```

### 6.5 Rendered MachineConfig

You do not normally edit rendered configs. The MCO generates them by merging all applicable MachineConfig objects for a pool.

List rendered configs:

```bash
oc get mc | grep rendered
```

Check which rendered config a pool is targeting:

```bash
oc get mcp worker -o jsonpath='{.spec.configuration.name}{"\n"}'
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
```

Check which config a node is using:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

Expected steady state:

```text
currentConfig == desiredConfig
state == Done
```

## 7. RHCOS node lifecycle: from boot to steady state

### 7.1 Installation and first boot

At installation time:

1. The installer generates Ignition configs.
2. RHCOS boots.
3. Ignition runs on first boot.
4. The node obtains initial configuration.
5. Kubelet starts.
6. Node joins the cluster.
7. CSR approval occurs automatically or manually depending on environment.
8. The MCD starts managing the node.
9. The node receives its desired rendered config.

### 7.2 Normal steady state

A healthy node should show:

```bash
oc get nodes
```

```text
NAME                    STATUS   ROLES    AGE   VERSION
worker-0.example.com    Ready    worker   20d   v1.xx.x
```

MCP should show:

```bash
oc get mcp
```

```text
UPDATED=True
UPDATING=False
DEGRADED=False
```

Node annotations should show:

```text
currentConfig = desiredConfig
state = Done
```

### 7.3 During configuration update

When a new MachineConfig applies to a pool:

```text
MCP Updating=True
Node desiredConfig changes
MCD starts Working
Node cordoned
Pods drained
Config applied
Node rebooted
Node returns Ready
Node uncordoned
MCD state Done
MCP updated count increases
```

### 7.4 After failed update

If something fails:

```text
MCP Degraded=True
DEGRADEDMACHINECOUNT > 0
Node annotation state=Degraded
MCD logs show reason
Cluster upgrades may be blocked
```

## 8. How changes are applied to RHCOS nodes

### 8.1 Standard change flow

```text
Admin creates/updates MachineConfig
        |
        v
MCO detects change
        |
        v
MCO renders new rendered-<pool>-<hash>
        |
        v
MCP target config changes
        |
        v
MCD on each node sees desired config
        |
        v
MCD cordons and drains node if required
        |
        v
MCD writes files, units, kernel args, OS image changes
        |
        v
MCD reboots node if required
        |
        v
Node returns and reports currentConfig=desiredConfig
```

### 8.2 Why many changes reboot nodes

MachineConfig operates at host OS level. Many host-level changes require a reboot to guarantee a consistent, safe, and repeatable state.

Common reboot-triggering changes:

- Kernel arguments.
- OS image updates.
- Many file changes through MachineConfig.
- Many systemd unit changes.
- Kubelet config changes.
- CRI-O runtime config changes.

### 8.3 Does every change reboot?

Historically, most MachineConfig changes caused drain and reboot. Newer OpenShift versions include node disruption policy capability for selected scenarios, but you should treat reboot as the default assumption unless you have verified the exact version and support status.

Production mindset:

> If you create or modify a MachineConfig, expect a rolling node reboot unless you have confirmed otherwise.

## 9. Node drain, reboot, and disruption behavior

### 9.1 Standard MCO sequence

For most MachineConfig changes, the MCO/MCD sequence is:

```text
1. Cordon
2. Drain
3. Apply
4. Reboot
5. Uncordon
```

This means workloads are evicted and rescheduled before the node reboots.

### 9.2 What can block drain?

Common blockers:

- Strict PodDisruptionBudget.
- Single-replica application with PDB `minAvailable: 1`.
- Pods using local storage.
- Static pods.
- DaemonSets are ignored/handled specially but can still confuse investigations.
- Unhealthy workloads that cannot reschedule.
- Insufficient cluster capacity.
- Broken scheduler or node pressure.

Check pods on a node:

```bash
oc adm manage-node <node> --list-pods
```

Check PDBs:

```bash
oc get pdb -A
```

Check events:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
```

### 9.3 Master/control-plane nodes

Control-plane nodes are more sensitive.

Important considerations:

- Static pods such as etcd and kube-apiserver are not drained like normal workload pods.
- In single-node OpenShift, drain behavior is different because there is no other node to receive workloads.
- Control-plane changes should be planned carefully.
- Always verify cluster operators before and after control-plane MCP changes.

```bash
oc get co
oc get mcp master
oc get nodes
```

### 9.4 Disruption planning

Before applying MachineConfig:

```bash
oc get mcp
oc get nodes
oc get pdb -A
oc adm top nodes
oc get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded
```

During rollout:

```bash
watch 'oc get mcp; echo; oc get nodes'
```

After rollout:

```bash
oc get mcp
oc get co
oc get nodes
```

## 10. Common node-level configuration use cases

### 10.1 Create a file on worker nodes

Example: create `/etc/motd`.

First encode content:

```bash
printf 'Managed by OpenShift MachineConfig\n' | base64 -w0
```

MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-motd
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/motd
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,TWFuYWdlZCBieSBPcGVuU2hpZnQgTWFjaGluZUNvbmZpZwo=
```

Apply:

```bash
oc apply -f 99-worker-motd.yaml
```

Monitor:

```bash
watch oc get mcp worker
```

Verify on a node:

```bash
oc debug node/<worker-node>
chroot /host cat /etc/motd
exit
```

### 10.2 Create a systemd service

Example: create a simple custom systemd service.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example-service
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
      - name: example-node-check.service
        enabled: true
        contents: |
          [Unit]
          Description=Example node check managed by MachineConfig
          After=network-online.target

          [Service]
          Type=oneshot
          ExecStart=/usr/bin/bash -c 'echo MachineConfig service ran at $(date) >> /var/log/example-node-check.log'

          [Install]
          WantedBy=multi-user.target
```

Apply and verify:

```bash
oc apply -f 99-worker-example-service.yaml
oc debug node/<node> -- chroot /host systemctl status example-node-check.service
```

### 10.3 Add a systemd drop-in

Use drop-ins when modifying existing service behavior.

Example skeleton:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-custom-systemd-dropin
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
      - name: example.service
        dropins:
        - name: 10-custom.conf
          contents: |
            [Service]
            Environment="EXAMPLE=true"
```

Warning: do not randomly override OpenShift-managed services. Understand the service dependency and Red Hat support impact first.

### 10.4 Add SSH authorized key for core user

Use this carefully. SSH access should be exceptional, not routine.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-ssh-key
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    passwd:
      users:
      - name: core
        sshAuthorizedKeys:
        - ssh-rsa AAAA... user@example
```

### 10.5 Add kernel argument

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-kargs
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
  - loglevel=7
```

Apply:

```bash
oc apply -f 99-worker-kargs.yaml
```

Verify after reboot:

```bash
oc debug node/<node> -- chroot /host cat /proc/cmdline
```

### 10.6 Configure registries

For registry allow/block/insecure/mirror settings, prefer cluster-level image configuration APIs where supported instead of hand-editing CRI-O files.

Examples to inspect:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

RHCOS nodes receive resulting registry configuration through OpenShift-managed mechanisms.

## 11. KubeletConfig management

### 11.1 Why use KubeletConfig?

Kubelet is the node agent. It controls important behavior such as:

- Pod lifecycle interaction with the node.
- Eviction thresholds.
- Image garbage collection.
- CPU manager behavior.
- Reserved resources.
- System reserved and kube reserved resources.
- Max pods.
- Cgroup behavior.

Do not directly edit kubelet files on the node. Use `KubeletConfig`.

### 11.2 One KubeletConfig per pool strategy

Recommended approach:

- Keep one main `KubeletConfig` per MCP for long-term settings.
- Edit existing CR instead of creating many small CRs.
- Use separate CRs only for temporary changes or different pools.
- Track changes in GitOps.
- Test on custom/canary MCP first.

### 11.3 Example: configure kubelet maxPods

First label MCP:

```bash
oc label machineconfigpool worker custom-kubelet=enabled
```

Create KubeletConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-kubelet-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: enabled
  kubeletConfig:
    maxPods: 250
```

Apply:

```bash
oc apply -f worker-kubelet-config.yaml
```

Monitor:

```bash
oc get mcp worker
oc get mc | grep kubelet
```

### 11.4 Example: reserved resources

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-reserved-resources
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: enabled
  kubeletConfig:
    systemReserved:
      cpu: "500m"
      memory: "1Gi"
    kubeReserved:
      cpu: "500m"
      memory: "1Gi"
```

Use caution. Incorrect reservations can reduce schedulable capacity or cause node pressure.

### 11.5 KubeletConfig troubleshooting

Check generated MachineConfigs:

```bash
oc get mc | grep kubelet
```

Describe KubeletConfig:

```bash
oc describe kubeletconfig <name>
```

Check MCP:

```bash
oc describe mcp worker
```

Check node kubelet after rollout:

```bash
oc debug node/<node>
chroot /host
systemctl status kubelet
journalctl -u kubelet -b --no-pager | tail -100
```

Danger sign:

```text
Invalid kubelet configuration can make nodes unavailable.
```

Always validate values against the OpenShift version and Kubernetes kubelet API for that version.

## 12. ContainerRuntimeConfig management

### 12.1 Why use ContainerRuntimeConfig?

CRI-O is the container runtime used by OpenShift. Runtime-level settings can affect:

- Container log size.
- PIDs limits.
- Overlay storage behavior.
- Default runtime behavior.
- Registry/runtime interaction.
- Runtime security defaults.

Do not directly edit CRI-O configuration on RHCOS nodes. Use supported OpenShift APIs.

### 12.2 One ContainerRuntimeConfig per pool strategy

Recommended approach:

- One `ContainerRuntimeConfig` per pool for long-term runtime settings.
- Avoid multiple overlapping runtime config CRs.
- Use GitOps and peer review.
- Test on canary MCP.
- Monitor CRI-O and kubelet after rollout.

### 12.3 Example ContainerRuntimeConfig

Label MCP:

```bash
oc label machineconfigpool worker custom-crio=enabled
```

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: ContainerRuntimeConfig
metadata:
  name: worker-container-runtime
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-crio: enabled
  containerRuntimeConfig:
    pidsLimit: 4096
    logLevel: info
```

Apply:

```bash
oc apply -f worker-container-runtime.yaml
```

Monitor:

```bash
oc get mcp worker
oc get mc | grep containerruntime
```

Verify:

```bash
oc debug node/<node>
chroot /host
systemctl status crio
journalctl -u crio -b --no-pager | tail -100
```

### 12.4 CRI-O failure pattern

If CRI-O fails after a runtime change:

```text
Node may become NotReady
Pods cannot start
MCD may report degraded
kubelet logs show runtime unavailable
crio logs show config parse or runtime error
```

Commands:

```bash
oc get nodes
oc describe node <node>
oc debug node/<node> -- chroot /host journalctl -u crio -b --no-pager | tail -200
oc debug node/<node> -- chroot /host journalctl -u kubelet -b --no-pager | tail -200
```

Remediation usually means reverting/fixing the `ContainerRuntimeConfig`, then allowing MCO to roll forward to a valid rendered config.

## 13. Kernel arguments and low-level OS tuning

### 13.1 Kernel arguments through MachineConfig

Kernel arguments are managed with `spec.kernelArguments`.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-kernel-args
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
  - audit=1
  - loglevel=7
```

Kernel argument changes require reboot.

Verify:

```bash
oc debug node/<node> -- chroot /host cat /proc/cmdline
```

### 13.2 Common kernel-level use cases

Examples:

- Enable or tune huge pages.
- Set audit options.
- Configure cgroup behavior.
- Configure CPU isolation for low-latency workloads.
- Enable specific hardware-related options.
- Enable FIPS mode at install time, where applicable.

For performance-sensitive configurations, prefer OpenShift-supported operators or profiles where available, such as:

- Node Tuning Operator.
- PerformanceProfile / Performance Addon Operator concepts, depending on OpenShift version and installed components.
- Tuned profiles.

### 13.3 sysctl tuning

Do not randomly write `/etc/sysctl.conf` manually. Use supported methods depending on scope:

- Pod-level safe sysctls in pod spec.
- Node-level sysctls through tuned profiles or supported MachineConfig use cases.
- OpenShift documentation for the exact sysctl and supportability.

A bad sysctl can cause networking, kubelet, or runtime instability.

## 14. SSH, debug access, and why manual changes are risky

### 14.1 Preferred access: oc debug node

Use:

```bash
oc debug node/<node>
chroot /host
```

Examples:

```bash
oc debug node/worker-0.example.com
chroot /host
hostnamectl
rpm-ostree status
journalctl -u kubelet -b --no-pager | tail -100
journalctl -u crio -b --no-pager | tail -100
exit
exit
```

### 14.2 SSH access

SSH to RHCOS nodes is generally not recommended for routine administration. It may be needed when:

- API is unavailable.
- Kubelet is broken.
- `oc debug node` cannot work.
- Red Hat support requests it.
- Bare-metal recovery requires host-level access.

Typical SSH user:

```bash
ssh core@<node>
```

### 14.3 Why manual changes are risky

Manual changes can cause:

- Configuration drift.
- MCP degradation.
- Future update failure.
- Inconsistent nodes in same pool.
- Supportability issues.
- Problems after node replacement.

Example anti-pattern:

```bash
ssh core@worker-1
sudo vi /etc/containers/registries.conf
sudo systemctl restart crio
```

Better pattern:

```bash
oc edit image.config.openshift.io/cluster
# or use supported mirror/config APIs
# then allow OpenShift to roll out the node config
```

### 14.4 Temporary debug vs persistent configuration

| Action | Good for | Persistent? | Recommended? |
|---|---|---:|---|
| `oc debug node` and inspect logs | Troubleshooting | No | Yes |
| SSH and inspect logs | Emergency troubleshooting | No | Sometimes |
| SSH and edit config | Emergency workaround only | Dangerous | Avoid |
| MachineConfig | Persistent host config | Yes | Yes |
| KubeletConfig | Persistent kubelet config | Yes | Yes |
| ContainerRuntimeConfig | Persistent CRI-O config | Yes | Yes |

## 15. Configuration drift detection

### 15.1 What is configuration drift?

Configuration drift means the node’s on-disk configuration no longer matches the MachineConfig that OpenShift believes should be applied.

Example:

1. MachineConfig creates `/etc/example.conf`.
2. Admin manually edits `/etc/example.conf` on one node.
3. MCD detects the file content/permission differs from the rendered config.
4. Node and MCP become degraded.

### 15.2 What drift affects

Drift can affect:

- Files created by MachineConfig.
- File permissions managed by MachineConfig.
- Systemd units managed by MachineConfig.
- Systemd drop-ins managed by MachineConfig.

### 15.3 Symptoms

```bash
oc get mcp
```

```text
DEGRADED=True
DEGRADEDMACHINECOUNT > 0
```

Node annotation:

```bash
oc describe node <node> | grep -A5 machineconfiguration
```

You may see:

```text
machineconfiguration.openshift.io/state: Degraded
```

### 15.4 Troubleshooting drift

Check MCP:

```bash
oc describe mcp worker
```

Check node annotations:

```bash
oc get node <node> -o yaml | grep -A20 machineconfiguration.openshift.io
```

Check MCD logs:

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide \
  | awk '/machine-config-daemon/ && /<node-name>/ {print $1}')

oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon
```

### 15.5 Remediation options

Option 1: Restore the file manually to match MachineConfig.

```bash
oc debug node/<node>
chroot /host
# restore exact content and permissions
exit
exit
```

Option 2: Correct the MachineConfig if the manual change was actually desired.

```bash
oc edit mc <machineconfig>
```

Option 3: Use a force file only when you understand the impact.

A force file causes MCD to reapply the current config and reboot the node. Use it carefully, preferably with Red Hat guidance in production.

Conceptual example:

```bash
oc debug node/<node>
chroot /host
touch /run/machine-config-daemon-force
reboot
```

Check exact path and procedure for your OpenShift version before using this method.

## 17.1 MCP stuck Updating=True

### Symptoms

```bash
oc get mcp
```

```text
worker   UPDATED=False   UPDATING=True   DEGRADED=False
```

### Possible causes

- Rollout still in progress.
- Node reboot taking time.
- Node NotReady after reboot.
- Drain blocked by PDB.
- Insufficient capacity to evict pods.
- MCD pod not running.
- Kubelet or CRI-O issue.

### Investigation

```bash
oc describe mcp worker
oc get nodes
oc get pods -A -o wide | grep <node>
oc get pdb -A
oc get events -A --sort-by=.lastTimestamp | tail -100
```

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Check MCD logs:

```bash

```

### Fix approach

- If drain blocked, fix PDB/workload capacity.
- If node NotReady, inspect kubelet/CRI-O logs.
- If config invalid, revert or correct MachineConfig/KubeletConfig/ContainerRuntimeConfig.
- If node is permanently lost, replace node according to platform procedure.

### Symptoms

```text
DEGRADED=True
DEGRADEDMACHINECOUNT > 0
```

### Common causes

- Invalid MachineConfig syntax.
- Invalid file path/content/permission.
- Invalid systemd unit.
- Invalid kubelet setting.
- Invalid CRI-O setting.
- Configuration drift.
- Failed OS pivot/update.
- Failed reboot.

### Investigation


3. Identify exact error from MCD logs.

- Temporarily adjust PDB if operationally approved.
- Scale workload replicas.
- Add capacity.
- Fix stuck terminating pods.
- Resume MCO rollout.

## 18. Production change-management strategy

### 18.1 Golden rules

1. Never manually edit RHCOS nodes for persistent changes.
2. Never test a new MachineConfig first on all workers in business hours.
3. Always know which MCP will receive the change.
4. Assume MachineConfig changes can reboot nodes.
5. Check PDBs and cluster capacity before applying.
6. Use canary/custom MCPs for risky changes.
7. Keep all MachineConfig/KubeletConfig/ContainerRuntimeConfig in Git.
8. Watch MCP rollout until completion.
9. Do not leave MCPs paused for a long time.
10. Do not edit rendered MachineConfigs.

### 18.2 Recommended workflow

```text
1. Understand requirement.
2. Select supported API: MachineConfig, KubeletConfig, ContainerRuntimeConfig, Tuned, Image config, etc.
3. Build YAML in Git.
4. Review exact MCP selector/role label.
5. Test on non-prod or custom canary MCP.
6. Check cluster health before rollout.
7. Apply change.
8. Watch MCP, nodes, MCD logs.
9. Validate node-level result.
10. Document rollback.
```

### 18.3 Pre-change checklist

```bash
oc get co
oc get clusterversion
oc get nodes
oc get mcp
oc get pdb -A
oc adm top nodes
oc get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded
```

Questions:

- Is the cluster already degraded?
- Are any MCPs updating?
- Are enough nodes available?
- Will PDBs block drain?
- Does the change affect master or worker?
- Is this during a cluster upgrade?
- Is the rollback tested?

### 18.4 Rollback strategy

Rollback usually means one of these:

- Delete the custom MachineConfig.
- Revert the YAML to previous version.
- Correct the KubeletConfig/ContainerRuntimeConfig.
- Restore previous registry/image configuration.

Example:

```bash
oc delete mc 99-worker-bad-change
watch oc get mcp worker
```

Important: deleting a MachineConfig creates another rendered config and may cause another reboot. Plan rollback as another rollout.

### 18.5 Canary rollout strategy

For risky worker changes:

1. Select one or two nodes.
2. Label them for custom role.
3. Create custom MCP.
4. Apply MachineConfig to custom MCP only.
5. Validate.
6. Roll change to larger worker pool.

Example:

```bash
oc label node worker-5.example.com node-role.kubernetes.io/canary=
```

Custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: canary
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - canary
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/canary: ""
  maxUnavailable: 1
```

MachineConfig role:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: canary
```

### 18.6 Change windows

For production:

- Schedule MachineConfig changes in maintenance windows when possible.
- Confirm application redundancy.
- Confirm PDB health.
- Avoid overlapping cluster upgrades and node config changes.
- Avoid applying multiple unrelated MachineConfigs at once.
- Wait for MCP completion before next change.

## 19. Interview and real-world scenario notes

### 19.1 How would you explain RHCOS node management?

A strong answer:

> RHCOS nodes in OpenShift are not managed like normal RHEL servers. Persistent host configuration is managed declaratively through the Machine Config Operator. The MCO renders MachineConfigs for each MachineConfigPool, and the Machine Config Daemon on every node applies the desired config. Most changes are rolled out with cordon, drain, apply, reboot, and uncordon. Kubelet changes should use KubeletConfig, CRI-O changes should use ContainerRuntimeConfig, and manual SSH changes are avoided because they create drift and can degrade the MCP.

### 19.2 Why should we avoid SSH changes?

Because manual changes:

- Are not declarative.
- Are not repeated on replacement nodes.
- Can be overwritten.
- Can cause configuration drift.
- Can degrade the MCP.
- Can block future upgrades.

### 19.3 What happens when you apply a MachineConfig?

Expected answer:

1. MCO detects the new MachineConfig.
2. MCO renders a new config for matching MCP.
3. MCP moves to Updating.
4. MCD on each node applies the desired config.
5. Node is usually cordoned and drained.
6. Config is written.
7. Node reboots if required.
8. Node returns Ready and is uncordoned.
9. Node reports currentConfig equal to desiredConfig.
10. MCP becomes Updated.

### 19.4 What is the difference between MachineConfig and MachineConfigPool?

```text
MachineConfig     = what configuration should be applied
MachineConfigPool = which nodes receive it and how rollout is controlled
```

### 19.5 What is configuration drift?

Configuration drift occurs when a node’s real on-disk state differs from what the applied MachineConfig expects. MCD detects this and marks the node/MCP degraded.

### 19.6 What is rendered MachineConfig?

A rendered MachineConfig is the final merged config generated by MCO from all MachineConfigs applicable to a pool.

Do not edit rendered configs directly.

### 19.7 How do you troubleshoot MCP degraded?

```bash
oc get mcp
oc describe mcp <pool>
oc get nodes
oc describe node <node>
oc get pods -n openshift-machine-config-operator -o wide
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Then identify whether the issue is:

- Drain failure.
- Drift.
- Bad file config.
- Bad systemd unit.
- Bad kubelet config.
- Bad CRI-O config.
- OS pivot/update failure.

### 19.8 What is the safest way to test risky node config?

Use a canary MCP or non-production cluster first. Apply config to a small node pool, validate, then roll out to larger pools.
