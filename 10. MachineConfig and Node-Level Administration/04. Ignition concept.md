# Ignition Concept in MachineConfig and Node-Level Administration

**Track:** Advanced OpenShift Administration  
**Target reader:** Linux/OpenShift administrator with ~10 years of infrastructure experience  
**Focus area:** MachineConfig, RHCOS node bootstrap, Machine Config Operator, node-level configuration, troubleshooting  
**Last updated:** 2026-07-03

---

## 1. Executive Summary

Ignition is the low-level provisioning mechanism used by Red Hat Enterprise Linux CoreOS (RHCOS) and OpenShift to bring a node into the exact required operating-system state during first boot. In OpenShift, Ignition is not just an installation detail. It is also the configuration format embedded inside `MachineConfig` objects, which the Machine Config Operator (MCO) uses to manage node-level operating-system configuration after the cluster is running.

For an experienced administrator, the most important point is this:

> **Ignition configures the node before the node becomes a normal running Linux system. MachineConfig uses Ignition-style configuration to manage the node after installation through the Machine Config Operator.**

Ignition is involved in:

- RHCOS first boot.
- Creating users such as `core`.
- Writing files under `/etc` and `/var`.
- Creating systemd units and drop-ins.
- Disk, filesystem, RAID, and partitioning configuration during installation or node provisioning.
- Node bootstrap into OpenShift.
- The internal format used by `MachineConfig.spec.config`.
- Controlled post-install node changes through MCO and Machine Config Daemon (MCD).

In OpenShift administration, you normally do **not** manually edit RHCOS nodes like traditional RHEL servers. You declare the desired node state through a `MachineConfig`, and the MCO applies that desired state to the correct MachineConfigPool.

---

## 2. Why Ignition Exists

Traditional Linux provisioning often uses tools such as:

- Kickstart
- cloud-init
- Ansible after SSH is available
- Manual shell scripts
- Golden VM templates

RHCOS follows a different model. It is designed to be:

- Immutable or close to immutable.
- Cluster-managed.
- Automatically updated.
- Consistent across nodes.
- Controlled by Kubernetes APIs after cluster bootstrap.

Ignition exists because some configuration must happen **before** a node can safely join the cluster. For example:

- Create the `core` user SSH key.
- Fetch bootstrap configuration.
- Write kubelet configuration.
- Configure trust bundles and certificates.
- Set up disk layout.
- Enable required systemd units.
- Prepare networking or host files needed during early boot.

Ignition runs very early in boot, from the initramfs, before the normal root filesystem is fully active. This makes it suitable for actions that must happen before `systemd` reaches the normal multi-user operating state.

---

## 3. Ignition in One Sentence

**Ignition is a first-boot, declarative, JSON-based machine provisioning engine used by CoreOS/RHCOS to transform a fresh machine into the desired operating-system state.**

Important characteristics:

| Characteristic | Meaning |
|---|---|
| Declarative | You define final state, not step-by-step shell commands. |
| First-boot focused | It is primarily designed to run once during the first boot of the installed system. |
| JSON format | The native Ignition config is JSON. |
| Machine-level | It configures OS-level resources, not Kubernetes workloads. |
| Early boot | Runs in initramfs before the normal OS boot completes. |
| Strict validation | Invalid Ignition can break node boot/provisioning. |
| Used by OpenShift | OpenShift installer and MCO rely on Ignition-style configuration. |

---

## 4. Ignition vs cloud-init vs Kickstart vs MachineConfig

| Tool | When it runs | Main purpose | OpenShift/RHCOS relevance |
|---|---:|---|---|
| Kickstart | During RHEL installation | Install and configure RHEL | Not the normal method for RHCOS nodes. |
| cloud-init | First boot and sometimes later | Cloud VM initialization | Not the primary config method for RHCOS. |
| Ignition | Early first boot | Provision immutable/CoreOS machine | Core mechanism for RHCOS node bootstrap. |
| MachineConfig | After cluster exists | Declare node OS configuration through Kubernetes API | Primary admin method for node-level config in OpenShift. |
| Butane | Before applying config | Human-friendly YAML that generates MachineConfig/Ignition | Recommended way to write complex configs safely. |

The common mistake is thinking MachineConfig and Ignition are separate worlds. They are connected:

- Ignition is the low-level config format and first-boot engine.
- MachineConfig is the OpenShift API object that carries Ignition-style configuration to nodes.
- MCO/MCD applies that configuration safely across pools of nodes.

## 5. Where Ignition Fits in OpenShift Architecture

OpenShift node lifecycle can be understood in two broad phases:

```text
Phase 1: Day-0 / Installation / First boot
-------------------------------------------
install-config.yaml
        |
        v
openshift-install create manifests
        |
        v
openshift-install create ignition-configs
        |
        v
bootstrap.ign / master.ign / worker.ign
        |
        v
RHCOS first boot -> Ignition runs -> node starts kubelet -> joins cluster


Phase 2: Day-2 / Post-install / Ongoing administration
------------------------------------------------------
Admin creates/updates MachineConfig
        |
        v
Machine Config Controller renders config
        |
        v
MachineConfigPool gets new rendered-* config
        |
        v
Machine Config Daemon on each node applies it
        |
        v
Node drain/reboot/service restart as required
```

### Day-0 Ignition

During installation, `openshift-install create ignition-configs` generates files such as:

```text
bootstrap.ign
master.ign
worker.ign
metadata.json
auth/kubeconfig
auth/kubeadmin-password
```

These files are consumed by RHCOS during first boot. On user-provisioned infrastructure, they are often served over HTTP/HTTPS and passed to the node using installer or PXE boot arguments.

### Day-2 MachineConfig

After the cluster is running, administrators usually do not regenerate `worker.ign` or `master.ign`. Instead, they create Kubernetes `MachineConfig` objects. The MCO turns all matching MachineConfigs into a rendered configuration and applies it to the appropriate nodes.

## 6. Important OpenShift Components Related to Ignition

### 6.1 Machine Config Operator

The Machine Config Operator manages system-level changes to RHCOS nodes. It is responsible for updates to areas such as:

- systemd
- CRI-O
- kubelet
- kernel arguments
- NetworkManager-related host configuration
- host files
- operating system image updates
- rendered MachineConfig rollout

You can inspect it with:

```bash
oc get co machine-config
oc get pods -n openshift-machine-config-operator
```

Expected pods include components such as:

```text
machine-config-controller
machine-config-daemon-xxxxx
machine-config-server-xxxxx
machine-config-operator-xxxxx
```

### 6.2 Machine Config Controller

The Machine Config Controller watches MachineConfigs and MachineConfigPools. It combines multiple MachineConfigs into a single rendered config such as:

```text
rendered-worker-7e8a9f...
rendered-master-a31c2b...
```

This rendered config becomes the desired state of the pool.

### 6.3 Machine Config Daemon

The Machine Config Daemon runs on every node as a daemon set. It checks the desired config for the node and applies changes locally.

It can:

- compare current and desired config;
- cordon and drain the node when needed;
- write files;
- manage systemd changes;
- apply kernel arguments;
- reboot the node when required;
- report degraded state if the node cannot be reconciled.

Useful command:

```bash
oc logs -n openshift-machine-config-operator \
  -l k8s-app=machine-config-daemon \
  -c machine-config-daemon --tail=100
```

For a specific daemon pod:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon
oc logs -n openshift-machine-config-operator <mcd-pod-name> -c machine-config-daemon
```

### 6.4 Machine Config Server

The Machine Config Server provides Ignition configuration to nodes during joining/bootstrap. In UPI environments, port `22623` is important for machine config server traffic. If new nodes cannot fetch Ignition/configuration during bootstrap, check load balancer and firewall rules around `22623`.

Common check:

```bash
curl -k https://api.<cluster-name>.<base-domain>:22623/config/worker
curl -k https://api.<cluster-name>.<base-domain>:22623/config/master
```

Depending on cluster stage, auth/cert behavior, and environment, the response can differ, but network reachability to the machine config server path is a key troubleshooting point.

## 7. Native Ignition Config Anatomy

A native Ignition config is JSON. Simplified example:

```json
{
  "ignition": {
    "version": "3.5.0"
  },
  "storage": {
    "files": [
      {
        "path": "/etc/example.conf",
        "mode": 420,
        "overwrite": true,
        "contents": {
          "source": "data:text/plain;charset=utf-8;base64,ZXhhbXBsZT10cnVlCg=="
        }
      }
    ]
  },
  "systemd": {
    "units": [
      {
        "name": "example.service",
        "enabled": true,
        "contents": "[Unit]\nDescription=Example\n[Service]\nType=oneshot\nExecStart=/usr/bin/true\n[Install]\nWantedBy=multi-user.target\n"
      }
    ]
  },
  "passwd": {
    "users": [
      {
        "name": "core",
        "sshAuthorizedKeys": [
          "ssh-rsa AAAA..."
        ]
      }
    ]
  }
}
```

Main sections:

| Section | Purpose |
|---|---|
| `ignition` | Ignition metadata, especially version. |
| `storage.files` | Write files to the node filesystem. |
| `storage.directories` | Create directories. |
| `storage.disks` | Disk partitioning. Usually day-0/new-node sensitive. |
| `storage.filesystems` | Filesystem creation or mounting. |
| `systemd.units` | Create, enable, mask, or modify systemd units. |
| `passwd.users` | Manage users, SSH keys, password hashes. |
| `passwd.groups` | Manage local groups. |

### Mode value warning

Ignition JSON uses integer file modes. For example:

```text
0644 octal = 420 decimal
0600 octal = 384 decimal
0755 octal = 493 decimal
```

When writing Butane YAML, you can use familiar octal style such as `0644`. When writing raw `MachineConfig` YAML manually, you often see the generated decimal value in `spec.config.storage.files[].mode`.

## 8. MachineConfig as an Ignition Wrapper

A MachineConfig stores Ignition-style configuration under `spec.config`.

Basic structure:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example-file
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
      - path: /etc/example.conf
        mode: 420
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,ZXhhbXBsZT10cnVlCg==
```

Key fields:

| Field | Meaning |
|---|---|
| `metadata.name` | Determines ordering. Common convention: `99-worker-*` for custom configs. |
| `metadata.labels.machineconfiguration.openshift.io/role` | Targets a pool role such as `worker` or `master`. |
| `spec.config.ignition.version` | Ignition config spec version supported by OpenShift. |
| `spec.config.storage.files` | Files to write. |
| `spec.config.systemd.units` | systemd units or drop-ins. |
| `spec.config.passwd.users` | Users and SSH keys/password hashes. |
| `spec.kernelArguments` | Kernel arguments managed by MCO. |
| `spec.extensions` | RHCOS extensions, when supported. |

## 9. OpenShift-Supported Ignition Version

For modern OpenShift 4.x, always check the documentation matching your cluster version.

For OpenShift 4.21, Red Hat documentation says OpenShift supports Ignition specification version `3.5`, and new MachineConfigs should be based on Ignition spec `3.5.0`.

Practical rule:

```yaml
spec:
  config:
    ignition:
      version: 3.5.0
```

Do not blindly use the newest upstream Ignition spec if OpenShift does not support it for that OpenShift release. Upstream Ignition may support newer stable specs, but OpenShift validation and MCO behavior are tied to the OpenShift release.

Check your cluster version:

```bash
oc version
oc get clusterversion
```

Check current MachineConfigs:

```bash
oc get mc
oc get mc 00-worker -o yaml | grep -A3 'ignition:'
oc get mc 00-master -o yaml | grep -A3 'ignition:'
```

- Easier syntax.
- Better validation.
- Avoids manual base64 mistakes.
- Avoids decimal/octal mode confusion.

## 11. Ignition During OpenShift Installation

During installation, the installer converts your installation inputs into manifests and Ignition configs.

Typical flow:

```bash
./openshift-install create manifests --dir ocp-install
./openshift-install create ignition-configs --dir ocp-install
```

Result:

```text
ocp-install/
├── auth
│   ├── kubeadmin-password
│   └── kubeconfig
├── bootstrap.ign
├── master.ign
├── metadata.json
└── worker.ign
```

### What each Ignition file is for

| File | Purpose |
|---|---|
| `bootstrap.ign` | Used by the bootstrap node. Starts temporary control plane/bootstrap services. |
| `master.ign` | Used by control plane nodes. |
| `worker.ign` | Used by worker/compute nodes. |
| `metadata.json` | Cluster metadata used by installer. |

### Important installation notes

- Ignition configs are node-role specific.
- Use `master.ign` for control plane nodes.
- Use `worker.ign` for compute nodes.
- Use `bootstrap.ign` only for the bootstrap node.
- Do not casually edit generated `.ign` files directly.
- For install-time customizations, place MachineConfig manifests under the installer `openshift/` directory before generating Ignition configs.
- Generated Ignition assets include time-sensitive certificates. Do not generate them too early and then wait many hours before installing.

### UPI bare-metal/VMware style flow

For user-provisioned infrastructure:

```text
1. Generate install-config.yaml
2. Generate manifests
3. Add any install-time MachineConfig under <install-dir>/openshift/
4. Generate ignition-configs
5. Serve .ign files from HTTP/HTTPS or embed/pass them to installer
6. Boot RHCOS ISO/PXE with correct ignition URL
7. Bootstrap node comes up
8. Masters fetch config and form control plane
9. Workers join after CSRs are approved if required
10. Bootstrap complete
11. Remove bootstrap node from load balancer
```

Example PXE-style kernel argument concept:

```text
coreos.inst.install_dev=/dev/sda \
coreos.inst.ignition_url=http://192.168.1.10:8080/worker.ign
```

## 12. Ignition and MachineConfig During Day-2 Operations

After the cluster is running, you normally manage node-level state through MachineConfig.

Example operations:

- Add a file under `/etc`.
- Configure chrony.
- Add registries configuration.
- Add custom CA bundles.
- Configure journald.
- Add systemd drop-ins.
- Change kubelet settings using `KubeletConfig`.
- Change CRI-O settings using `ContainerRuntimeConfig`.
- Add kernel arguments.
- Enable RHCOS extensions.

Day-2 MachineConfig rollout flow:

```text
oc apply -f 99-worker-custom.yaml
        |
        v
MCC renders new rendered-worker-* config
        |
        v
worker MCP becomes UPDATING=True
        |
        v
MCD on selected node cordons/drains if required
        |
        v
MCD applies config
        |
        v
Node reboots if required
        |
        v
Node returns Ready
        |
        v
Next node updated according to maxUnavailable
```

Watch progress:

```bash
oc get mcp
oc get mcp worker -w
oc describe mcp worker
```

Check node annotations:

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

## 13. MachineConfig Ordering and Render Logic

MachineConfigs are processed in lexicographic order by name. This is why default configs often start with `00-`, generated configs may use other prefixes, and custom administrator configs commonly use `99-`.

Example:

```text
00-worker
01-worker-container-runtime
50-worker-generated-kubelet
99-worker-custom-chrony
99-worker-motd
```

Practical naming convention:

| Prefix | Typical use |
|---|---|
| `00-` | Base configuration delivered by OpenShift. |
| `01-` to `49-` | Platform/operator-generated configuration. |
| `50-` to `89-` | Specialized generated/custom config. |
| `90-` to `99-` | Administrator overrides/custom configs. |

If multiple MachineConfigs write the same file path, later rendered content can override earlier content. Avoid duplicate ownership of the same file across multiple custom MachineConfigs unless you intentionally want an override.

Best practice:

```text
One owner per file path.
One purpose per MachineConfig.
Clear name with role and function.
Keep source Butane YAML in Git.
```

## 14. MachineConfigPool Relationship

A MachineConfigPool groups nodes that receive the same rendered machine configuration.

Default pools:

```bash
oc get mcp
```

Typical output:

```text
NAME     CONFIG                      UPDATED   UPDATING   DEGRADED
master   rendered-master-xxxxx       True      False      False
worker   rendered-worker-yyyyy       True      False      False
```

A MachineConfig targets a pool using this label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

For master/control plane:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: master
```

### Custom pools

Custom MCPs are used when a subset of nodes need different OS-level configuration.

Example scenarios:

- Infra nodes.
- GPU nodes.
- Logging nodes.
- Storage/ODF nodes.
- Low-latency worker nodes.
- Edge or special hardware nodes.

High-level custom MCP flow:

```text
1. Label nodes with a custom role.
2. Create MachineConfigPool selecting those nodes.
3. Create MachineConfig targeting that custom role.
4. Watch custom pool rollout.
```

Example node label:

```bash
oc label node worker-1.example.com node-role.kubernetes.io/infra=
oc label node worker-1.example.com node-role.kubernetes.io/worker-
```

Example MCP skeleton:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Example custom MachineConfig label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

Important: A node should belong to only one MachineConfigPool. Overlapping MCP selectors can create confusion and degraded behavior.

## 17. Practical Example 3: Add a systemd Drop-In

Example: configure an override for a custom service. In real production, only modify services you understand and that are supported for OpenShift node configuration.

Butane:

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-example-systemd-dropin
  labels:
    machineconfiguration.openshift.io/role: worker
systemd:
  units:
  - name: example.service
    enabled: true
    contents: |
      [Unit]
      Description=Example oneshot service managed by MachineConfig
      After=network-online.target

      [Service]
      Type=oneshot
      ExecStart=/usr/bin/bash -c 'echo MachineConfig example > /var/lib/example-service.txt'
      RemainAfterExit=yes

      [Install]
      WantedBy=multi-user.target
```

Generate and apply:

```bash
butane 99-worker-example-systemd-dropin.bu -o 99-worker-example-systemd-dropin.yaml
oc apply -f 99-worker-example-systemd-dropin.yaml
oc get mcp worker -w
```

Verify:

```bash
oc debug node/<worker-node> -- chroot /host systemctl status example.service
oc debug node/<worker-node> -- chroot /host cat /var/lib/example-service.txt
```

Senior-admin note:

> Be careful with custom systemd units. A bad systemd unit can block boot, cause MCD failure, or repeatedly degrade a pool.

## 18. Practical Example 4: Configure chrony Using MachineConfig

Time synchronization is a common real-world node-level configuration task.

Butane:

```yaml
variant: openshift
version: 4.21.0
metadata:
  name: 99-worker-chrony-custom
  labels:
    machineconfiguration.openshift.io/role: worker
storage:
  files:
  - path: /etc/chrony.conf
    mode: 0644
    overwrite: true
    contents:
      inline: |
        server ntp1.example.com iburst
        server ntp2.example.com iburst
        driftfile /var/lib/chrony/drift
        makestep 1.0 3
        rtcsync
        logdir /var/log/chrony
systemd:
  units:
  - name: chronyd.service
    enabled: true
```

Apply:

```bash
butane 99-worker-chrony-custom.bu -o 99-worker-chrony-custom.yaml
oc apply -f 99-worker-chrony-custom.yaml
oc get mcp worker -w
```

Verify:

```bash
oc debug node/<worker-node> -- chroot /host chronyc sources -v
oc debug node/<worker-node> -- chroot /host systemctl status chronyd
```

Production notes:

- Ensure NTP servers are reachable from nodes.
- UDP/123 must be allowed where applicable.
- Apply first to a test/custom MCP before rolling to all workers.

## 20. What You Should and Should Not Manage with Ignition/MachineConfig

### Good candidates

| Use case | Recommended approach |
|---|---|
| `/etc/chrony.conf` | MachineConfig/Butane. |
| `/etc/motd` | MachineConfig/Butane. |
| Custom CA file under `/etc/pki/ca-trust/source/anchors` | Often MachineConfig, depending on purpose. |
| systemd drop-in | MachineConfig/Butane with testing. |
| kernel arguments | MachineConfig/Butane or documented OpenShift mechanism. |
| RHCOS extensions | MachineConfig where supported. |
| Kubelet tuning | Prefer `KubeletConfig` CR. |
| CRI-O tuning | Prefer `ContainerRuntimeConfig` CR. |

### Avoid or be extremely careful

| Use case | Risk |
|---|---|
| Manually editing files on `/host` | Causes config drift. |
| Replacing kubelet systemd unit manually | Can break node lifecycle. |
| Writing random files under `/usr` | RHCOS `/usr` is managed/immutable and not a normal target. |
| Editing generated `00-*` MachineConfigs | Can break upgrade-managed configuration. |
| Applying untested configs to all masters | Can impact API/etcd availability. |
| Disk layout changes on existing nodes | Often install-time/new-node only and high-risk. |
| Overlapping custom MCP selectors | Can cause unclear pool ownership. |

## 21. Ignition, RHCOS Immutability, and `/usr`, `/etc`, `/var`

RHCOS is not managed like traditional mutable RHEL.

General mental model:

| Path | Meaning |
|---|---|
| `/usr` | OS content managed by RHCOS/ostree image. Treat as read-only/platform-managed. |
| `/etc` | Node configuration. MachineConfig commonly writes here. |
| `/var` | Mutable state. MachineConfig may place supported files here. |
| `/run` | Runtime state. Do not use for persistent MachineConfig-managed files. |

If you need to add software or modify OS content, do not treat nodes like yum-managed RHEL servers. Use supported OpenShift mechanisms such as:

- RHCOS extensions where available.
- MachineOSConfig / custom layered images where supported by your version and use case.
- Operators for hardware drivers or specialized node setup.
- Node Tuning Operator for performance tuning.

## 22. Configuration Drift

Configuration drift means the node's actual on-disk state no longer matches the currently applied MachineConfig.

Common causes:

- Admin manually edited a MachineConfig-managed file on the node.
- A script changed permissions of a managed file.
- A troubleshooting change was made inside `oc debug node` and left behind.
- A systemd unit/drop-in managed by MachineConfig was changed manually.
- A third-party tool modified node-level files outside the MCO.

Symptoms:

```bash
oc get mcp
```

Output shows:

```text
DEGRADED=True
```

Check details:

```bash
oc describe mcp worker
oc get nodes
oc describe node <node-name>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Node annotations:

```bash
oc get node <node-name> -o yaml | grep -A5 machineconfiguration.openshift.io
```

Typical recovery approach:

```text
1. Identify drifted file/unit/permission from MCD logs or MCP events.
2. Compare actual node file with MachineConfig desired content.
3. Do not edit random configs repeatedly.
4. Restore the file/permission to match MachineConfig, or update MachineConfig intentionally.
5. Watch MCP return to healthy.
```

Example verification:

```bash
oc debug node/<node-name>
chroot /host
ls -l /etc/example.conf
cat /etc/example.conf
exit
exit
```

If the file is supposed to be MachineConfig-managed, the long-term fix should be through MachineConfig, not manual edits.

## 23. Node Drain, Reboot, and Disruption Behavior

MachineConfig changes can be disruptive. Many changes cause the MCO to:

```text
cordon -> drain -> apply config -> reboot -> uncordon
```

Check rollout:

```bash
oc get mcp worker -w
oc get nodes -w
```

Check drain issues:

```bash
oc describe mcp worker
oc get pods -A --field-selector spec.nodeName=<node-name>
oc get pdb -A
```

Common drain blockers:

- Strict PodDisruptionBudget.
- Static pods on control plane nodes.
- Pods using local storage.
- Unhealthy workloads with no replicas.
- DaemonSet behavior misunderstood.
- Long termination grace periods.

OpenShift can reduce disruption for selected file/systemd/user changes using node disruption policies in supported versions, but you must know exactly what you are doing. Do not assume every MachineConfig change requires or avoids reboot. Always observe MCP behavior.

## 24. Pausing a MachineConfigPool

You can pause an MCP to prevent immediate rollout.

Pause worker pool:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":true}}'
```

Apply MachineConfig while paused:

```bash
oc apply -f 99-worker-change.yaml
oc get mcp worker
```

Unpause:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":false}}'
oc get mcp worker -w
```

Use cases:

- Batch several MachineConfig changes into one rollout.
- Prepare changes during maintenance window.
- Prevent unexpected worker reboots during business hours.

Warnings:

- A paused pool will not apply desired config.
- Do not forget to unpause.
- Long-paused pools can accumulate changes and surprise you later.
- Control plane pool pause should be handled very carefully.

## 25. Troubleshooting: New Node Cannot Fetch Ignition

This is common in UPI/bare-metal/VMware-style installations.

Symptoms:

- RHCOS node boots but does not join cluster.
- Console shows Ignition fetch failure.
- Worker never appears in `oc get nodes`.
- CSR does not appear.
- MachineConfigServer unreachable.

Checklist:

### 25.1 Verify correct Ignition URL

For ISO/coreos-installer:

```bash
coreos-installer install /dev/sda \
  --ignition-url=http://<http-server>/worker.ign
```

For PXE/iPXE, verify:

```text
coreos.inst.ignition_url=http://<http-server>/worker.ign
```

Do not pass `bootstrap.ign` to a worker.

### 25.2 Verify HTTP server

From another machine in same network:

```bash
curl -v http://<http-server>/worker.ign
curl -v http://<http-server>/master.ign
curl -v http://<http-server>/bootstrap.ign
```

### 25.3 Verify API and Machine Config Server load balancer

```bash
nc -zv api.<cluster>.<domain> 6443
nc -zv api.<cluster>.<domain> 22623
curl -k https://api.<cluster>.<domain>:22623/config/worker
```

If `nc` is unavailable, use alternatives:

```bash
curl -vk https://api.<cluster>.<domain>:22623/healthz
openssl s_client -connect api.<cluster>.<domain>:22623 </dev/null
```

### 25.4 Verify DNS

```bash
dig api.<cluster>.<domain>
dig api-int.<cluster>.<domain>
dig *.apps.<cluster>.<domain>
```

### 25.5 Check RHCOS console logs

On failed boot console:

```bash
journalctl --identifier=ignition --all
journalctl -b -u bootkube.service
journalctl -b -u kubelet
```

### 25.6 Common causes

| Cause | Fix |
|---|---|
| Wrong `.ign` file used | Use role-specific Ignition file. |
| HTTP server unreachable | Fix routing/firewall/VLAN. |
| DNS not resolving `api` or `api-int` | Fix DNS records. |
| Port `22623` blocked | Fix firewall/load balancer. |
| Bootstrap removed too early | Keep bootstrap until install completes. |
| Expired/old Ignition assets | Regenerate install assets if installation did not start in time. |
| Wrong NIC or static IP | Fix boot arguments or NetworkManager config. |
| Proxy missing | Configure install proxy correctly. |

## 27. Troubleshooting: MCP Degraded After MachineConfig

Symptoms:

```bash
oc get mcp
```

```text
worker   rendered-worker-xxxxx   False   False   True
```

Step-by-step:

```bash
oc describe mcp worker
oc get nodes
oc describe node <bad-node>
oc get mc | grep rendered-worker
oc get mc rendered-worker-xxxxx -o yaml > rendered-worker.yaml
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Look for messages such as:

```text
content mismatch for file
mode mismatch for file
failed to apply systemd unit
error running rpm-ostree
failed to drain node
```

Recovery depends on cause:

| Cause | Recovery |
|---|---|
| Bad custom MachineConfig | Delete or correct the custom MC. |
| Manual drift | Restore file/permission to desired state or update MC. |
| Bad systemd unit | Fix unit in MC; if node cannot boot, use console/rescue. |
| Bad kernel arg | Remove bad MC; may require node rescue/reinstall if unbootable. |
| Drain failure | Fix workload/PDB issue. |

Delete a bad custom MachineConfig:

```bash
oc delete mc 99-worker-bad-config
oc get mcp worker -w
```

Do not delete default `00-*` or rendered MachineConfigs casually.

## 30. Security Considerations

Ignition and MachineConfig can modify the host OS. Treat them as highly privileged configuration.

Security rules:

- Only cluster admins should create MachineConfigs.
- Store Butane sources in Git with review/approval.
- Do not put plaintext passwords in MachineConfigs.
- If setting a local password hash, use a strong hash and understand exposure risk.
- Avoid embedding secrets directly in node files unless required and approved.
- Be careful with SSH authorized keys for `core`.
- Audit who can modify `machineconfigs.machineconfiguration.openshift.io`.
- Monitor for unexpected MachineConfig changes.

Check RBAC:

```bash
oc auth can-i create machineconfigs.machineconfiguration.openshift.io
oc auth can-i update machineconfigs.machineconfiguration.openshift.io --as=<user>
```

Audit MachineConfigs:

```bash
oc get mc -o wide
oc get mc -o yaml > all-machineconfigs.yaml
```

## 31. Production Best Practices

### 31.1 Always test on a custom pool first

Create a small test MCP with one non-critical worker node. Apply new MachineConfigs there first.

```text
custom-test MCP -> one worker -> validate -> promote to worker pool
```

### 31.2 Use Butane as source of truth

Store this in Git:

```text
machineconfigs/
├── butane/
│   ├── 99-worker-chrony.bu
│   └── 99-worker-motd.bu
└── rendered-yaml/
    ├── 99-worker-chrony.yaml
    └── 99-worker-motd.yaml
```

### 31.3 One MachineConfig per purpose

Good:

```text
99-worker-chrony
99-worker-motd
99-worker-custom-ca
```

Bad:

```text
99-worker-all-random-changes
```

### 31.4 Avoid editing default MachineConfigs

Do not modify:

```text
00-master
00-worker
01-*
rendered-*
```

Create your own named MachineConfig.

### 31.5 Use maintenance windows

MachineConfig changes can reboot nodes. Plan around:

- workload replicas;
- PDBs;
- control plane health;
- worker capacity;
- cluster autoscaler behavior;
- storage quorum;
- infra/router placement.

### 31.6 Monitor during rollout

Use multiple terminals:

```bash
watch -n2 oc get mcp
watch -n2 oc get nodes
oc get pods -A -o wide | grep <node-name>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon -f
```

### 31.7 Keep rollback simple

Rollback often means deleting or correcting the custom MachineConfig.

```bash
oc delete mc 99-worker-problem-change
oc get mcp worker -w
```

But note: not all changes are cleanly reversible, especially disk, filesystem, kernel, or service-level changes.

## 32. Common Exam and Interview Questions

### Q1. What is Ignition in OpenShift?

Ignition is the first-boot provisioning engine used by RHCOS. It applies JSON-based machine configuration early in boot. OpenShift installer generates Ignition files for bootstrap, master, and worker nodes. After installation, OpenShift uses Ignition-style configuration inside MachineConfig objects, applied by the MCO/MCD.

### Q2. Does Ignition run every time a MachineConfig changes?

Not in the same way as first boot. Ignition itself is primarily a first-boot mechanism. In day-2 OpenShift operations, the Machine Config Daemon reads and applies MachineConfig content that uses Ignition-style structure.

### Q3. What is the difference between Ignition and MachineConfig?

Ignition is the low-level machine configuration format and first-boot engine. MachineConfig is the Kubernetes API object used by OpenShift to deliver node OS configuration to pools of nodes.

### Q4. Why use Butane?

Butane lets administrators write readable YAML and generate valid MachineConfig/Ignition output. It reduces mistakes with base64, file modes, and schema validation.

### Q5. What happens after applying a MachineConfig?

The Machine Config Controller renders a new `rendered-*` config. The MachineConfigPool enters updating state. Machine Config Daemon applies the change node by node, draining and rebooting when needed.

### Q6. How do you check if a MachineConfig is applied?

```bash
oc get mcp
oc describe mcp worker
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc debug node/<node> -- chroot /host cat /path/to/file
```

### Q7. What is configuration drift?

Configuration drift occurs when the node's on-disk state differs from the currently applied MachineConfig. The MCD detects this and can mark the node and MCP degraded.

### Q8. Can you manually edit files on an OpenShift node?

Technically yes during debugging, but it is not recommended. Manual edits to MachineConfig-managed files can cause drift. Persistent node-level changes should be declared using MachineConfig or the correct OpenShift CR.

### Q9. Which port is important for Machine Config Server during UPI install?

Port `22623` is used for machine config server traffic. In UPI installs, load balancer/firewall/DNS issues around this port can stop nodes from joining.

### Q10. What is the safest way to roll out node OS changes?

Use Butane, generate MachineConfig, apply first to a custom test MachineConfigPool, validate, then promote to the target pool during a maintenance window.

## 36. Real-World Senior Admin Notes

1. **Never test MachineConfig first on all masters.** A bad config can create an outage.
2. **Do not treat RHCOS like RHEL.** Avoid `dnf install`, manual edits, and unmanaged scripts.
3. **MachineConfig rollout is cluster capacity sensitive.** If your workloads lack replicas or PDBs are too strict, drains can block updates.
4. **Keep generated YAML and Butane source.** During incident recovery, source control matters.
5. **MachineConfig mistakes are recoverable only if the node can still boot or be repaired.** Bad kernel args, bad units, or filesystem mistakes can require console-level recovery or node replacement.
6. **Understand day-0 vs day-2.** Disk partitioning and early network settings often belong in install-time config, not random post-install MachineConfigs.
7. **Watch MCP, not only pods.** The MCP is the main health indicator for node config state.
8. **Use custom MCPs for risky changes.** One canary node is better than a full worker pool outage.
9. **Do not ignore DEGRADED=True.** A degraded MCP means future updates can be blocked.
10. **MCO is part of upgrades.** Bad MachineConfigs can affect cluster upgrades, not just current node state.

## 37. Common Mistakes and Fixes

| Mistake | Symptom | Fix |
|---|---|---|
| Wrong Ignition version | MC rejected or MCD error | Use version supported by your OpenShift release. |
| Used `0644` in raw MC incorrectly | Validation or unexpected mode | Use Butane or decimal mode in raw Ignition. |
| Missing role label | MC created but not applied | Add `machineconfiguration.openshift.io/role`. |
| Applied to `master` accidentally | Control plane reboots | Use correct role; test before apply. |
| Edited node manually | MCP degraded drift | Restore desired state or update MC. |
| Bad systemd unit | Node degraded or boot issue | Fix/delete MC; recover node if needed. |
| PDB blocks drain | MCP stuck Updating | Adjust workload/PDB safely. |
| Overlapping MCP selectors | Pool confusion/degraded | Ensure node belongs to one MCP. |
| Deleted rendered MC | MCO confusion | Do not manually delete rendered configs unless following official cleanup guidance. |
| Used old install Ignition assets | Install failure | Regenerate install assets. |

## 39. Final Summary

Ignition is foundational to OpenShift node management because RHCOS nodes are not meant to be hand-configured like traditional Linux servers. Ignition sets the initial machine state at first boot. MachineConfig carries Ignition-style configuration into the running cluster. The Machine Config Operator renders, rolls out, validates, and protects that desired node state through MachineConfigPools and the Machine Config Daemon.

For advanced OpenShift administration, mastering Ignition means understanding:

- How RHCOS nodes bootstrap.
- How `bootstrap.ign`, `master.ign`, and `worker.ign` are used.
- How MachineConfig wraps Ignition-style config.
- How Butane simplifies MachineConfig creation.
- How MCP rollout, drain, reboot, and drift detection work.
- How to troubleshoot MCO/MCD issues safely.
- How to avoid unmanaged manual changes on nodes.

The senior-admin mindset is simple:

> **Do not configure nodes manually. Declare node state through OpenShift APIs, verify rollout through MCP, and troubleshoot through MCD logs and node annotations.**
