## 1. What is MachineConfigOperator?

The **MachineConfigOperator**, usually called **MCO**, is the OpenShift operator responsible for managing node-level operating system configuration on Red Hat Enterprise Linux CoreOS (**RHCOS**) nodes.

In simple words:

> **MCO is the OpenShift component that keeps node operating system configuration, kubelet configuration, CRI-O configuration, kernel arguments, systemd units, and selected host files in the desired state.**

It is not only a configuration tool. It is part of the OpenShift lifecycle system. It participates in:

- Applying RHCOS operating system updates.
- Applying host-level configuration changes.
- Managing kubelet and CRI-O configuration through supported CRDs.
- Draining and rebooting nodes when required.
- Detecting configuration drift.
- Ensuring newly added nodes receive the correct configuration.
- Blocking upgrades if nodes cannot safely reach the desired configuration.

In Kubernetes, administrators often use SSH, Ansible, shell scripts, or cloud-init to configure nodes. In OpenShift 4, especially on RHCOS, the supported model is different:

> **Do not manually SSH into nodes and edit system configuration as a permanent solution. Use MCO-backed APIs.**

Manual node changes can create drift and cause the node or MachineConfigPool to become `Degraded`.

---

## 2. Why MCO is important in Advanced OpenShift Administration

A beginner sees MCO only when running:

```bash
oc get co machine-config
oc get mcp
```

An experienced OpenShift administrator understands that MCO is one of the most critical operators in the cluster because it touches the foundation of every node.

MCO problems can cause:

- Nodes stuck in `SchedulingDisabled`.
- MachineConfigPool stuck in `Updating=True`.
- MachineConfigPool stuck in `Degraded=True`.
- Cluster upgrades stuck at a percentage such as 80%, 84%, or 95%.
- Worker nodes rebooting unexpectedly after configuration changes.
- Control-plane nodes unable to complete update.
- Workload disruption due to drain/reboot cycles.
- Kubelet or CRI-O configuration not applying.
- Custom MachineConfig syntax errors.
- Configuration drift from manual host modification.
- New nodes joining with old or incorrect configuration.

For advanced administration, MCO must be treated like a node lifecycle controller.

## 3. MCO architecture

MCO runs primarily in the namespace:

```bash
openshift-machine-config-operator
```

Check MCO pods:

```bash
oc get pods -n openshift-machine-config-operator -o wide
```

Typical components:

```text
machine-config-operator
machine-config-controller
machine-config-daemon
machine-config-server
```

Depending on the OpenShift version, additional related components or CRDs might exist, such as `machineconfignodes`, `MachineOSConfig`, or `MachineOSBuild`.

---

### 3.1 machine-config-operator

This is the operator process that manages MCO operands.

Responsibilities:

- Watches cluster configuration.
- Ensures MCO operand deployments and daemonsets exist.
- Reports ClusterOperator status.
- Integrates with the Cluster Version Operator during upgrades.
- Manages operator-level configuration through `MachineConfiguration`.

Check operator status:

```bash
oc get co machine-config
oc describe co machine-config
```

Example healthy output:

```text
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE
machine-config   4.x       True        False         False      10d
```

---

### 3.2 machine-config-controller

The **machine-config-controller** is the brain of the MCO rollout process.

Responsibilities:

- Watches `MachineConfig` objects.
- Watches `MachineConfigPool` objects.
- Renders multiple MachineConfigs into a single rendered MachineConfig per pool.
- Updates pool desired configuration.
- Coordinates node updates with the MachineConfigDaemon.
- Controls rollout based on `maxUnavailable`.
- Tracks pool status such as `UPDATED`, `UPDATING`, and `DEGRADED`.

Check controller logs:

```bash
oc logs -n openshift-machine-config-operator deploy/machine-config-controller
```

Useful during:

- Render failures.
- MCP update not progressing.
- Upgrade stuck.
- MachineConfigPool status mismatch.
- Custom pool selector problems.

---

### 3.3 machine-config-daemon

The **machine-config-daemon**, usually called **MCD**, runs as a DaemonSet on nodes.

Check it:

```bash
oc get ds -n openshift-machine-config-operator machine-config-daemon
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide
```

Responsibilities:

- Runs on each node.
- Reads the desired rendered MachineConfig.
- Compares desired configuration with current node state.
- Cordon/drain/reboot/uncordon when required.
- Applies files, systemd units, kernel arguments, kubelet changes, CRI-O changes, OS image updates.
- Reports node-level MachineConfig state.
- Detects configuration drift.
- Marks node degraded if it cannot reconcile.

For a specific node, find its MCD pod:

```bash
NODE=<node-name>

oc get pod -n openshift-machine-config-operator -o wide \
  -l k8s-app=machine-config-daemon | grep "$NODE"
```

View logs:

```bash
MCD_POD=<machine-config-daemon-pod>

oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon
```

During deep troubleshooting, MCD logs are usually more useful than controller logs.

---

### 3.4 machine-config-server

The **machine-config-server** provides Ignition configuration to nodes during bootstrap or node join.

Responsibilities:

- Serves Ignition configuration for new machines.
- Helps new RHCOS nodes receive initial machine configuration.
- Important during node provisioning, scaling, and replacement.

If new nodes cannot join or cannot fetch Ignition, check:

```bash
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-server
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-server
```

---

### 3.5 High-level architecture flow

```text
Admin creates MachineConfig / KubeletConfig / ContainerRuntimeConfig
        |
        v
machine-config-controller watches API
        |
        v
Controller renders final config for MCP
        |
        v
MachineConfigPool desiredConfig changes
        |
        v
machine-config-daemon on each node notices desiredConfig != currentConfig
        |
        v
MCD cordons/drains node if required
        |
        v
MCD applies files/systemd/kernel/OS/runtime/kubelet changes
        |
        v
Node reboots if required
        |
        v
MCD validates current state
        |
        v
Node currentConfig == desiredConfig
        |
        v
MCP Updated=True, Updating=False, Degraded=False
```

## 5. MachineConfig deep dive

A `MachineConfig` is a declarative object that describes host-level configuration.

It can manage:

- Files under `/etc`, `/var`, and other supported writable paths.
- systemd units and drop-ins.
- Kernel arguments.
- RHCOS extensions.
- OS image URL in rendered configs.
- Some container runtime and kubelet generated configuration.
- SSH authorized keys.
- Registry certificates and trust configuration through generated machine configs.

A basic MachineConfig contains:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
      - path: /etc/example.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,ZXhhbXBsZQo=
```

Key points:

- The label `machineconfiguration.openshift.io/role: worker` targets the worker pool.
- The name ordering matters.
- The `spec.config` section is Ignition-style configuration.
- File content is commonly base64 encoded.
- Most changes cause a rendered MachineConfig change.
- Most rendered MachineConfig changes cause node drain and reboot unless a non-reboot behavior applies or a node disruption policy changes behavior.

---

### 5.1 MachineConfig naming convention

Common naming pattern:

```text
00-worker-...
01-worker-...
50-worker-...
75-worker-...
99-worker-...
```

Examples:

```text
99-worker-chrony
99-worker-custom-ca
75-worker-kernelargs
80-worker-extensions
99-worker-sysctl
```

Why naming matters:

- MachineConfigs are merged in lexicographic order.
- Later configs can override earlier fields in certain cases.
- Generated configs often use `99-...`.
- Bad naming can cause unexpected override behavior.

Practical naming advice:

| Prefix | Use case |
|---:|---|
| `00-` | Base/low-level defaults; usually created by OpenShift |
| `50-` | Mid-level platform configuration |
| `75-` | Team or infra-specific config |
| `80-` | Extensions or feature-specific config |
| `99-` | Final override or custom admin config |

Do not randomly create many `99-*` configs without documentation. In large environments, this becomes difficult to troubleshoot.

---

### 5.2 MachineConfig labels

The most important label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

Common roles:

```text
master
worker
infra
custom pool role
```

Example for infra pool:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

Remember:

- A MachineConfig targets an MCP by role.
- Worker-targeted configs also affect custom worker-derived pools.
- Custom pool configs can override worker configs when fields overlap, depending on OpenShift version behavior.
- Control-plane custom MCPs are not supported.

---

### 5.3 MachineConfig content source

File content can be inline as data URL:

```yaml
contents:
  source: data:text/plain;charset=utf-8;base64,<base64-data>
```

Generate base64:

```bash
echo -n "my-content" | base64 -w0
```

Or:

```bash
base64 -w0 myfile.conf
```

Example:

```bash
cat chrony.conf | base64 -w0
```

---

### 5.4 MachineConfig file modes

Modes are numeric, but pay attention to YAML interpretation.

Common values:

```yaml
mode: 0644
mode: 0600
mode: 0755
```

Best practice:

- Use `0644` for normal config files.
- Use `0600` for sensitive files.
- Use `0755` for executable scripts.
- Avoid world-writable modes.
- Validate generated MachineConfig before applying.

---

### 5.5 MachineConfig overwrite behavior

Example:

```yaml
overwrite: true
```

Meaning:

- If file exists, replace it.
- If file does not exist, create it.
- If you manually change it later, MCD can detect drift.

Be careful with existing files:

- Overwriting kubelet/CRI-O/systemd files manually through MachineConfig can break nodes.
- Prefer `KubeletConfig` for kubelet.
- Prefer `ContainerRuntimeConfig` for CRI-O.
- Prefer drop-in files over replacing complete systemd units.

## 6. MachineConfigPool deep dive

A `MachineConfigPool` groups nodes and controls rollout.

Check pools:

```bash
oc get mcp
```

Example:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
master   rendered-master-xxxx                              True      False      False      3              3                   3                     0
worker   rendered-worker-yyyy                              True      False      False      3              3                   3                     0
```

Important columns:

| Column | Meaning |
|---|---|
| `CONFIG` | Rendered MachineConfig currently desired/current for the pool |
| `UPDATED` | All pool nodes are at desired config |
| `UPDATING` | Some nodes are still applying config |
| `DEGRADED` | At least one node/config is failed or drifted |
| `MACHINECOUNT` | Nodes managed by pool |
| `READYMACHINECOUNT` | Ready nodes in the pool |
| `UPDATEDMACHINECOUNT` | Nodes with currentConfig equal to pool config |
| `DEGRADEDMACHINECOUNT` | Nodes degraded or unreconcilable |

Describe a pool:

```bash
oc describe mcp worker
```

Get YAML:

```bash
oc get mcp worker -o yaml
```

---

### 6.1 Important MCP spec fields

```yaml
spec:
  machineConfigSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: worker
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker: ""
  maxUnavailable: 1
  paused: false
```

Important fields:

| Field | Purpose |
|---|---|
| `machineConfigSelector` | Selects MachineConfigs for the pool |
| `nodeSelector` | Selects nodes managed by the pool |
| `maxUnavailable` | Controls how many nodes can update at once |
| `paused` | Prevents pool from applying new config |
| `configuration` | Desired/current rendered config status |

---

### 6.2 `maxUnavailable`

`maxUnavailable` controls the number or percentage of nodes that can be unavailable during update.

Example:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":2}}'
```

For production:

- Worker pools may use `2`, `10%`, or another value based on capacity.
- Master/control-plane should normally remain conservative.
- Never increase this blindly during business hours.
- Respect workload PodDisruptionBudgets.
- Ensure enough capacity exists to reschedule drained pods.

Check current setting:

```bash
oc get mcp worker -o jsonpath='{.spec.maxUnavailable}{"\n"}'
```

---

### 6.3 Pausing an MCP

Pause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Use cases:

- Batch multiple MachineConfig changes into one rollout.
- Prevent immediate reboot while preparing a maintenance window.
- Stop custom layered image rollout until validation.
- Pause worker pool during sensitive workload periods.

Important warning:

> Do not leave MCPs paused for a long time. Paused pools do not apply new node configuration, including some certificate or trust-related changes. This can later create upgrade or certificate issues.

Check paused status:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

## 7. Rendered MachineConfigs

MCO does not directly apply each individual MachineConfig one by one. It renders them.

A rendered MachineConfig looks like:

```text
rendered-worker-6f7a8b9c...
rendered-master-1a2b3c4d...
```

Check rendered configs:

```bash
oc get mc | grep rendered
```

View a rendered config:

```bash
oc get mc rendered-worker-<hash> -o yaml
```

Find which MachineConfigs were included:

```bash
oc get mc rendered-worker-<hash> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/source}{"\n"}'
```

If the annotation exists, it shows source MachineConfig names.

---

### 7.1 Why rendered configs matter

Rendered configs are the real desired state applied to nodes.

For troubleshooting, compare:

- MCP desired rendered config.
- Node desired rendered config.
- Node current rendered config.
- MCD logs for why current did not reach desired.

Example:

```bash
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
```

Node annotations:

```bash
NODE=<node>

oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

---

### 7.2 Rendered configs are not automatically garbage-collected

Over time, many rendered configs can accumulate.

List unused rendered configs:

```bash
oc adm prune renderedmachineconfigs list --in-use=false --pool-name=worker
```

Dry run prune:

```bash
oc adm prune renderedmachineconfigs --pool-name=worker
```

Prune with confirmation:

```bash
oc adm prune renderedmachineconfigs --pool-name=worker --count=5 --confirm
```

Do not delete rendered MachineConfigs manually unless you fully understand what is in use. Use the supported prune command.

## 8. How MCO applies a node configuration change

Most node-level changes follow this process:

```text
1. New MachineConfig or generated config created
2. MCO renders new rendered MachineConfig
3. MCP desired config changes
4. MCD on selected node notices desiredConfig != currentConfig
5. Node is cordoned
6. Node is drained
7. MCD writes files / changes systemd / applies kernel args / updates OS
8. Node reboots if required
9. Node comes back Ready
10. MCD validates state
11. Node is uncordoned
12. MCP status updates
```

This is why even a small host-level configuration change can cause a node reboot.

---

### 8.1 Cordon

MCO marks the node unschedulable:

```text
SchedulingDisabled
```

Check:

```bash
oc get nodes
```

Manual equivalent:

```bash
oc adm cordon <node>
```

---

### 8.2 Drain

MCO evicts pods from the node.

Manual equivalent:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

Drain can fail because of:

- Strict PodDisruptionBudget.
- Standalone pods without controller.
- Pods with local storage.
- API issues.
- Slow terminating pods.
- Finalizers.
- Static pods on control plane.

Check events:

```bash
oc describe node <node>
oc get events -A --sort-by=.lastTimestamp | tail -100
```

---

### 8.3 Apply

MCD applies the desired configuration.

This may include:

- Writing files.
- Changing file permissions.
- Creating systemd units.
- Creating systemd drop-ins.
- Applying kernel arguments.
- Updating kubelet config.
- Updating CRI-O config.
- Performing rpm-ostree changes.
- Pulling new OS image.
- Installing supported RHCOS extensions.

---

### 8.4 Reboot

Most MachineConfig changes reboot the node.

Check reboot history from node debug:

```bash
oc debug node/<node>
chroot /host
last reboot | head
journalctl -b -u machine-config-daemon
```

---

### 8.5 Uncordon

After successful apply and reboot, MCO uncordons the node.

Manual equivalent:

```bash
oc adm uncordon <node>
```

If a node remains `SchedulingDisabled`, check MCD logs before manually uncordoning. Manual uncordon can hide a failed MCO rollout.

## 9. Node annotations and status tracking

Node annotations are critical for MCO troubleshooting.

Check all MCO annotations:

```bash
oc get node <node> -o json | jq '.metadata.annotations | with_entries(select(.key|contains("machineconfiguration.openshift.io")))'
```

Common annotations:

| Annotation | Meaning |
|---|---|
| `machineconfiguration.openshift.io/currentConfig` | Rendered config currently applied |
| `machineconfiguration.openshift.io/desiredConfig` | Rendered config node should move to |
| `machineconfiguration.openshift.io/state` | MCD state such as `Done`, `Working`, or `Degraded` |
| `machineconfiguration.openshift.io/reason` | Human-readable reason for degraded/working state |

Example:

```bash
NODE=<node>

oc get node "$NODE" -o custom-columns=NAME:.metadata.name,\
STATE:.metadata.annotations.machineconfiguration\\.openshift\\.io/state,\
CURRENT:.metadata.annotations.machineconfiguration\\.openshift\\.io/currentConfig,\
DESIRED:.metadata.annotations.machineconfiguration\\.openshift\\.io/desiredConfig,\
REASON:.metadata.annotations.machineconfiguration\\.openshift\\.io/reason
```

---

### 9.1 MachineConfigNode resource

In newer OpenShift releases, `MachineConfigNode` gives clearer per-node MCO update status.

Check:

```bash
oc get machineconfignodes
oc get machineconfignodes -o wide
oc describe machineconfignode/<node>
```

Example useful command:

```bash
oc get machineconfignodes -o custom-columns=NAME:.metadata.name,POOL:.spec.pool.name,CURRENT:.status.configVersion.current.name,DESIRED:.status.configVersion.desired.name,UPDATED:.status.conditions[?(@.type=="Updated")].status
```

If available in your cluster, prefer this for rollout visibility.

## 10. Configuration drift detection

Configuration drift means:

> The actual on-disk state of a node no longer matches the MachineConfig that MCO believes is applied.

Examples:

- Admin manually edits a MachineConfig-managed file.
- Admin changes permissions on a managed file.
- Admin modifies a systemd unit created by MachineConfig.
- A post-install script modifies `/etc` files managed by MCO.
- Security tooling changes file contents or permissions.
- Someone manually deletes a file created by MachineConfig.

When MCD detects drift:

- It logs an error.
- It creates Kubernetes events.
- It stops further drift detection on that node.
- It marks node degraded.
- It marks MCP degraded.
- The node can stay online, but it cannot be updated safely.

---

### 10.1 How to detect drift

Check MCP:

```bash
oc get mcp
```

If degraded:

```bash
oc describe mcp worker
```

Look for messages like:

```text
content mismatch for file "/etc/example.conf"
```

Check node:

```bash
oc describe node <node>
```

Check MCD logs:

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide \
  -l k8s-app=machine-config-daemon | grep <node> | awk '{print $1}')

oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon
```

Search logs:

```bash
oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon | egrep -i "drift|mismatch|degraded|content"
```

---

### 10.2 Fixing drift

Correct approach:

1. Identify the file/unit/permission that drifted.
2. Compare desired content from rendered MachineConfig.
3. Restore the node file to expected content or change MachineConfig properly.
4. Restart MCD pod only after fixing actual issue if needed.
5. Watch MCP return to healthy.

Do not simply patch node annotations to hide drift. That can lead to worse upgrade failures.

Example flow:

```bash
NODE=<node>
POOL=worker

oc describe mcp "$POOL"
oc describe node "$NODE"

MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide \
  -l k8s-app=machine-config-daemon | grep "$NODE" | awk '{print $1}')

oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon | tail -200
```

Debug node:

```bash
oc debug node/$NODE
chroot /host
```

Restore file or permission:

```bash
chmod 0644 /etc/example.conf
restorecon -v /etc/example.conf
```

Exit debug session and restart MCD pod if required:

```bash
oc delete pod -n openshift-machine-config-operator "$MCD_POD"
```

Watch:

```bash
watch -n5 'oc get mcp; echo; oc get nodes'
```

## 11. Node drain, reboot, and disruption behavior

MCO can perform disruptive actions. Advanced administrators must understand when and why.

Default behavior for most MachineConfig changes:

```text
cordon -> drain -> apply -> reboot -> uncordon
```

But not every change requires a reboot in every version. Some changes can be applied without drain/reboot, and newer versions support **node disruption policies** to reduce unnecessary reboots.

---

### 11.1 Changes often requiring reboot

Common reboot-triggering changes:

- Kernel arguments.
- OS image update.
- RHCOS extension install.
- Many files under `/etc`.
- systemd unit changes.
- Kubelet configuration changes.
- CRI-O configuration changes depending on field/action.
- Custom MachineConfig that alters boot-level behavior.

---

### 11.2 Changes that may not require reboot

Depending on OpenShift version and configuration, some changes may avoid reboot, such as:

- SSH authorized key changes.
- Pull secret changes.
- Certain certificate rotations.
- Some registry configuration changes.
- Changes covered by a node disruption policy.

Always validate behavior in your exact cluster version.

---

### 11.3 Node disruption policy

A **node disruption policy** lets you define what action MCO should perform for selected configuration changes.

Possible actions:

| Action | Meaning |
|---|---|
| `Reboot` | Drain and reboot |
| `None` | Apply change without extra action |
| `Drain` | Cordon and drain |
| `Reload` | Reload service |
| `Restart` | Restart service |
| `DaemonReload` | Reload systemd manager configuration |

Example: restart chronyd when `/etc/chrony.conf` changes.

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
spec:
  nodeDisruptionPolicy:
    files:
    - path: /etc/chrony.conf
      actions:
      - type: Restart
        restart:
          serviceName: chronyd.service
```

Apply by editing:

```bash
oc edit MachineConfiguration cluster -n openshift-machine-config-operator
```

Important:

- MCO validates policy format.
- MCO does not prove your policy is operationally safe.
- `Reboot` and `None` override other actions.
- If a change also requires reboot for another reason, reboot still wins.
- Test on non-production pool first.

## 17. Custom MachineConfigPools

Custom MCPs are useful for worker subgroups.

Examples:

- Infra nodes.
- Logging nodes.
- Storage nodes.
- GPU nodes.
- CNF/low-latency nodes.
- Workload-specific nodes.

Important rules:

- Custom MCPs are supported for worker-derived pools.
- Custom MCPs for control-plane nodes are not supported.
- A node can belong to only one MCP.
- Custom pools inherit worker MachineConfigs.
- Custom pool-specific MachineConfigs can add/override behavior for that custom pool.

---

### 17.1 Create an infra MachineConfigPool

Label nodes:

```bash
oc label node <node1> node-role.kubernetes.io/infra=
oc label node <node2> node-role.kubernetes.io/infra=
```

Create MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

Check:

```bash
oc get mcp
oc get nodes -l node-role.kubernetes.io/infra
```

Create infra-specific MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-example
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.5.0
```

---

### 17.2 Custom MCP troubleshooting

Common mistakes:

- Node label does not match MCP nodeSelector.
- MachineConfig label does not match machineConfigSelector.
- Node has multiple custom pool labels.
- MCP created without including worker configs.
- No nodes selected.
- Pool stuck because one node is NotReady.
- Pool stuck because PDB prevents drain.
- Pool paused.

Commands:

```bash
oc get mcp -o wide
oc describe mcp infra
oc get nodes --show-labels | grep infra
oc get mc -l machineconfiguration.openshift.io/role=infra
oc get mc -l machineconfiguration.openshift.io/role=worker
```

## 18. Production rollout strategy

A 10-year experienced admin does not apply MachineConfigs directly to all production nodes without planning.

Recommended approach:

### 18.1 Preparation

```bash
oc get co
oc get mcp
oc get nodes
oc get pods -A | egrep -i "crash|pending|error"
```

Ensure:

- ClusterOperators healthy.
- MCPs updated and not degraded.
- Nodes ready.
- No ongoing upgrade.
- Workloads have enough replicas.
- PDBs allow drain.
- Maintenance window is approved.
- Backup or rollback plan exists.

---

### 18.2 Use canary pool or small worker subset

For large clusters:

1. Create custom MCP with 1-2 test worker nodes.
2. Apply MachineConfig to custom pool.
3. Validate node behavior.
4. Roll to broader worker pool later.

This avoids taking down all workers due to one bad config.

---

### 18.3 Pause, batch, unpause

For multiple related changes:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
oc apply -f 99-worker-change1.yaml
oc apply -f 99-worker-change2.yaml
oc apply -f 99-worker-change3.yaml
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

This can reduce multiple reboot cycles into one rollout.

Do not leave paused after maintenance.

---

### 18.4 Monitor rollout

```bash
watch -n5 'oc get mcp; echo; oc get nodes'
```

Detailed:

```bash
oc get machineconfignodes -o wide
oc describe mcp worker
oc get events -n openshift-machine-config-operator --sort-by=.lastTimestamp
```

For a node:

```bash
oc describe node <node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

---

### 18.5 Post-validation

Validate:

```bash
oc get mcp
oc get nodes
oc get co machine-config
oc get pods -A | egrep -i "crash|pending|error" || true
```

On node:

## 20. MCP Degraded troubleshooting flow

When `oc get mcp` shows:

```text
DEGRADED=True
```

Use this flow.

---

### Step 1: Identify degraded pool

```bash
oc get mcp
```

Example:

```text
worker   rendered-worker-abc   False   True   True   3   2   2   1
```

Meaning:

- Worker pool is updating.
- Worker pool is degraded.
- One node is degraded.

---

### Step 2: Describe pool

```bash
oc describe mcp worker
```

Look for:

```text
Message:
Reason:
NodeDegraded
RenderDegraded
Failed
```

Common messages:

```text
content mismatch for file "/etc/..."
failed to drain node
failed to update OS
could not find source config
error running rpm-ostree
```

---

### Step 3: Identify bad node

```bash
oc get nodes -o custom-columns=NODE:.metadata.name,\
STATE:.metadata.annotations.machineconfiguration\\.openshift\\.io/state,\
REASON:.metadata.annotations.machineconfiguration\\.openshift\\.io/reason
```

Or:

```bash
oc describe mcp worker | grep -i "Node"
```

---

### Step 4: Check MCD logs

```bash
NODE=<node>
MCD=$(oc get pods -n openshift-machine-config-operator -o wide \
  -l k8s-app=machine-config-daemon | awk -v node="$NODE" '$0 ~ node {print $1}')

oc logs -n openshift-machine-config-operator "$MCD" -c machine-config-daemon --tail=300
```

---

### Step 5: Determine category

| Symptom | Likely cause |
|---|---|
| `content mismatch` | Drift |
| `permission mismatch` | Drift or wrong file mode |
| `failed to drain` | PDB/pod/finalizer/local storage |
| `rpm-ostree` failure | OS update/image/repo issue |
| `unexpected on-disk state` | Manual edits or partial previous update |
| `failed to reboot` | Node/systemd/cloud issue |
| `image pull` error | Registry/mirror/pull secret/proxy |
| `render failed` | Invalid MachineConfig or conflicting configs |

---

### Step 6: Fix based on cause

#### Drift

Restore content/permissions or update MachineConfig properly.

#### Drain blocked

Find blocking pods:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Check PDB:

```bash
oc get pdb -A
```

Check pods on node:

```bash
oc get pods -A --field-selector spec.nodeName=<node> -o wide
```

#### Bad MachineConfig

Delete or fix the bad MachineConfig:

```bash
oc get mc
oc describe mc <bad-mc>
oc delete mc <bad-mc>
```

Then watch rollout.

#### MCD stuck

After fixing root cause:

```bash
oc delete pod -n openshift-machine-config-operator "$MCD"
```

Do not delete MCD pod before understanding cause. It may only restart into the same failure.

## 22. Recovery scenarios

### 22.1 Bad MachineConfig applied to worker nodes

Symptoms:

- Worker MCP degraded.
- Nodes stuck updating or rebooting.
- MCD logs show file/systemd/kernel issue.

Recovery:

```bash
oc get mc
oc describe mc <bad-mc>
oc delete mc <bad-mc>
oc get mcp worker
```

If node remains degraded due to on-disk state, fix drift on node.

---

### 22.2 Bad MachineConfig applied to master nodes

This is serious.

Symptoms:

- Control plane instability.
- API intermittent.
- Master MCP degraded.
- etcd/static pod risk.

Recovery approach:

1. Do not reboot all masters together.
2. Identify bad MachineConfig.
3. Delete or fix bad MachineConfig.
4. Work one master at a time.
5. Ensure etcd quorum remains healthy.
6. Use Red Hat support for production if API/control plane is unstable.

Commands:

```bash
oc get mcp master
oc describe mcp master
oc get nodes -l node-role.kubernetes.io/master
oc get pods -n openshift-etcd -o wide
oc get co etcd kube-apiserver machine-config
```

---

### 22.3 MCP paused accidentally

Symptoms:

- New MachineConfig exists.
- Rendered config changes.
- MCP not rolling out.
- `spec.paused=true`.

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

Fix:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

---

### 22.4 Drain blocked by PDB

Symptoms:

- MCD logs show drain failure.
- Node remains cordoned.
- MCP Updating=True.

Check:

```bash
oc get pdb -A
oc get pods -A --field-selector spec.nodeName=<node>
```

Try dry-run:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Fix:

- Scale application replicas.
- Temporarily relax PDB if approved.
- Fix stuck terminating pods.
- Ensure controllers recreate pods elsewhere.

Do not delete production pods blindly.

---

### 22.5 Node stuck SchedulingDisabled

Check:

```bash
oc get nodes
oc describe node <node>
oc get mcp
```

If MCO still updating, do not manually uncordon immediately.

Find MCD reason:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

If rollout completed but node remained unschedulable due to manual intervention, uncordon:

```bash
oc adm uncordon <node>
```

---

### 22.6 Node NotReady during MCO rollout

Check:

```bash
oc describe node <node>
oc get csr
oc get pods -A --field-selector spec.nodeName=<node>
```

Debug via console/SSH if available through break-glass.

On host:

```bash
systemctl status kubelet
systemctl status crio
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
journalctl -u machine-config-daemon -b --no-pager | tail -200
```

---

### 22.7 Render failure

Symptoms:

- `machine-config` ClusterOperator degraded.
- MCP condition indicates render failure.
- New rendered config not created.

Check:

```bash
oc describe co machine-config
oc logs -n openshift-machine-config-operator deploy/machine-config-controller --tail=300
oc get mc
```

Common causes:

- Invalid MachineConfig YAML.
- Invalid Ignition structure.
- Conflicting file definitions.
- Invalid kernel argument.
- Unsupported field.
- Bad generated config from custom resource.

Fix the source MachineConfig or generated object.

## 23. Best practices

### 23.1 Do not manually modify managed node files

Avoid:

```bash
ssh core@node
sudo vi /etc/chrony.conf
```

Use MachineConfig.

Manual edits can cause drift.

---

### 23.2 Use supported higher-level CRDs

Use:

- `KubeletConfig` for kubelet.
- `ContainerRuntimeConfig` for CRI-O.
- Image configuration APIs for registry trust/mirrors.
- Node Tuning Operator for performance tuning.
- MachineConfig only when the supported API is MachineConfig or no better API exists.

---

### 23.3 Test on canary nodes

Before applying to production workers:

- Create custom MCP.
- Move one node into it.
- Apply change.
- Validate reboot and workload behavior.
- Then promote to worker pool.

---

### 23.4 Keep MachineConfigs in Git

Store:

- `.bu` Butane source file.
- Generated `.yaml`.
- Change reason.
- Rollback instructions.
- Test evidence.

Use GitOps carefully; ensure GitOps does not repeatedly apply broken MachineConfigs.

---

### 23.5 Avoid too many MachineConfigs

Many small configs create operational complexity.

Prefer grouping related files into a clear MachineConfig:

```text
99-worker-ntp
99-worker-security-hardening
99-worker-runtime-tuning
```

Avoid:

```text
99-worker-file1
99-worker-file2
99-worker-file3
...
```

---

### 23.6 Avoid direct master changes

Master MachineConfigs are risky.

Only change control-plane nodes when:

- Required.
- Supported.
- Tested.
- Maintenance window exists.
- etcd quorum is safe.
- Rollback is known.

---

### 23.7 Watch PDBs before rollout

Before MCO rollout:

```bash
oc get pdb -A
```

Check workloads:

```bash
oc get pods -A -o wide | grep <node>
```

If critical apps have single replicas and strict PDBs, MCO drain can block.

---

### 23.8 Monitor after every change

Always monitor:

```bash
watch -n5 'oc get mcp; echo; oc get co machine-config; echo; oc get nodes'
```

Do not close the maintenance task until:

```text
MCP UPDATED=True
MCP UPDATING=False
MCP DEGRADED=False
All nodes Ready
machine-config ClusterOperator Available=True Degraded=False
```

---

### 23.9 Keep rendered configs clean

Occasionally check:

```bash
oc adm prune renderedmachineconfigs list --in-use=false
```

Prune with change control:

```bash
oc adm prune renderedmachineconfigs --count=10 --confirm
```

## 25. Interview and exam notes

### 25.1 Simple explanation

**Question:** What is the MachineConfigOperator?

**Answer:**

MachineConfigOperator manages OpenShift node operating system configuration and updates. It uses MachineConfig and MachineConfigPool resources to apply host-level changes such as files, systemd units, kernel arguments, kubelet config, CRI-O config, and RHCOS updates. The Machine Config Daemon runs on each node, applies the rendered desired configuration, drains and reboots nodes when required, and reports node state back to the cluster.

---

### 25.2 Difference between MachineConfig and MachineConfigPool

| MachineConfig | MachineConfigPool |
|---|---|
| Defines what should be configured | Defines where and how it should be applied |
| Contains files/systemd/kernel args | Selects nodes and MachineConfigs |
| Targeted by role label | Has nodeSelector and machineConfigSelector |
| Gets rendered into final config | Tracks rollout status |

---

### 25.3 What happens after creating a MachineConfig?

1. MCO detects new MachineConfig.
2. Render controller creates new rendered config.
3. MCP desired config changes.
4. MCD on each selected node applies it.
5. Node may be cordoned, drained, rebooted, and uncordoned.
6. MCP status becomes updated when all nodes are at desired config.

---

### 25.4 Why is MCP degraded?

Common reasons:

- Configuration drift.
- Bad MachineConfig.
- Drain failure.
- Node NotReady.
- rpm-ostree failure.
- Kubelet/CRI-O failure.
- Image pull failure.
- Render failure.
- Paused or misconfigured pool.
- MCD cannot apply file/systemd/kernel change.

---

### 25.5 How to troubleshoot MCP degraded?

```bash
oc get mcp
oc describe mcp <pool>
oc get nodes
oc describe node <node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Then fix root cause.

---

### 25.6 Why avoid manual SSH changes?

Manual changes to MCO-managed files create configuration drift. MCO expects node state to match the rendered MachineConfig. If content or permissions differ, MCD can mark the node and MCP degraded.

---

### 25.7 How to safely roll out MachineConfig changes?

- Check cluster health first.
- Use Butane.
- Validate YAML.
- Test on canary/custom MCP.
- Apply during maintenance window.
- Monitor MCP and nodes.
- Fix degraded state immediately.
- Keep configs in Git.

---

### 25.8 What is rendered MachineConfig?

Rendered MachineConfig is the final merged MachineConfig generated by MCO from all MachineConfigs selected for a pool. Nodes apply the rendered config, not individual configs directly.

---

### 25.9 What is configuration drift?

Configuration drift is when actual node disk state differs from the current MachineConfig. Example: an admin manually modifies `/etc/chrony.conf` that was created by MachineConfig. MCD detects this and marks node/MCP degraded.

---

### 25.10 What is `maxUnavailable` in MCP?

`maxUnavailable` controls how many nodes in a MachineConfigPool can be unavailable during update. It limits disruption during MCO rollouts.

## Final practical summary

The MachineConfigOperator is the OpenShift node lifecycle and configuration engine. For advanced administration, remember this rule:

> **If the change touches node OS, kubelet, CRI-O, kernel, systemd, or managed files, think MCO first.**

A good OpenShift administrator knows `oc get mcp`.  
A senior OpenShift administrator knows how to read rendered configs, MCD logs, node annotations, MachineConfigNode status, drain blockers, drift messages, and rollout behavior.

When MCO is healthy, node lifecycle is predictable.  
When MCO is degraded, upgrades stop, nodes stop updating, and the cluster becomes operationally risky.

Treat MachineConfigs like production infrastructure code: test, review, version, apply carefully, monitor, and document rollback.
