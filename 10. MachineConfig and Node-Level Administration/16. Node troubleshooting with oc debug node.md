# Node Troubleshooting with `oc debug node` in OpenShift

**Module:** MachineConfig and Node-Level Administration  
**Level:** Advanced OpenShift Administration / L3 Operations  
**Target experience:** ~10 years Linux, DevOps, Kubernetes, OpenShift administration  
**Focus:** Practical node troubleshooting using `oc debug node`, `chroot /host`, kubelet, CRI-O, MachineConfig/MCD, systemd, journald, networking, storage, and recovery workflows.

---

## 1. Why `oc debug node` Matters

In OpenShift 4, nodes are normally treated as **managed, immutable infrastructure**. For RHCOS nodes, you should not SSH into machines and manually change configuration as a normal operational practice. Node configuration should come from cluster APIs such as:

- `MachineConfig`
- `KubeletConfig`
- `ContainerRuntimeConfig`
- `MachineConfigPool`
- Operators such as MCO, CVO, Network Operator, Storage Operator, and Ingress Operator

Still, real production incidents require direct node inspection. Examples:

- Node is `NotReady`.
- Kubelet is unhealthy.
- CRI-O cannot start pods.
- Pods are stuck in `ContainerCreating`, `ImagePullBackOff`, `CrashLoopBackOff`, or `Terminating`.
- MachineConfigPool is stuck `Updating=True` or `Degraded=True`.
- Node was rebooted but did not rejoin properly.
- DNS, routing, MTU, interface, or OVN issues are suspected on a specific node.
- Disk pressure, inode exhaustion, log growth, or CRI-O storage corruption is suspected.
- A pod works on one node but fails on another.

`oc debug node/<node>` is the OpenShift-native way to open a privileged troubleshooting session on a node without relying on SSH. It creates a temporary privileged debug pod scheduled to the selected node and mounts the host filesystem under `/host`.

The common workflow is:

```bash
oc debug node/<node-name>
chroot /host
```

After `chroot /host`, you are using the node host filesystem as your root filesystem. This allows you to inspect host-level files, services, logs, binaries, network state, CRI-O state, kubelet state, and MachineConfig-rendered files.

## 2. Mental Model: What Happens When You Run `oc debug node`

When you run:

```bash
oc debug node/worker-1.example.com
```

OpenShift creates a temporary debug pod similar to:

```text
worker-1.example.com-debug
```

That pod is:

- Privileged.
- Scheduled specifically on the target node.
- Given access to host namespaces and host filesystem mounts.
- Removed when the debug session exits, unless cleanup fails.
- Intended for diagnostics, not permanent changes.

Inside the debug pod, the node root filesystem is mounted at:

```bash
/host
```

Before chroot:

```bash
ls /
ls /host
```

After chroot:

```bash
chroot /host
```

Your `/` becomes the host root filesystem.

So these commands now inspect the node:

```bash
systemctl status kubelet
journalctl -u kubelet -b
systemctl status crio
journalctl -u crio -b
cat /etc/os-release
rpm-ostree status
crictl ps -a
ip addr
ss -tulpn
findmnt
lsblk
```

Important: `oc debug node` still depends on the cluster API and enough node/runtime functionality to schedule and start the debug pod. If the API is unavailable or CRI-O/kubelet is too broken on that node, `oc debug node` might not work. In that case, SSH or console access might be required as a break-glass method.

## 3. Prerequisites and Access Requirements

You normally need cluster-admin level access or equivalent privileges because node debug requires privileged access.

Check your identity:

```bash
oc whoami
oc auth can-i create pods/exec -A
oc auth can-i create pods -n default
oc auth can-i get nodes
oc auth can-i debug nodes
```

In many environments, only platform administrators should run `oc debug node` because it gives deep host-level access.

Recommended preparation:

```bash
oc get clusterversion
oc get co
oc get nodes -o wide
oc get mcp
oc get mc
oc get pods -A -o wide | grep <node-name>
```

Use a safe namespace before starting debug:

```bash
oc project default
```

or use an admin troubleshooting namespace if your organization has one:

```bash
oc project openshift-debug
```

## 4. Standard Node Debug Entry Procedure

### 4.1 Identify the target node

```bash
oc get nodes -o wide
```

Example:

```text
NAME                    STATUS                     ROLES                  AGE   VERSION
master-0.example.com    Ready                      control-plane,master   80d   v1.30.x
worker-0.example.com    Ready                      worker                 80d   v1.30.x
worker-1.example.com    NotReady                   worker                 80d   v1.30.x
worker-2.example.com    Ready,SchedulingDisabled   worker                 80d   v1.30.x
```

Describe the node first:

```bash
oc describe node worker-1.example.com
```

Look for:

- `Ready`
- `MemoryPressure`
- `DiskPressure`
- `PIDPressure`
- `NetworkUnavailable`
- `Taints`
- `Unschedulable`
- `Events`
- `Capacity`
- `Allocatable`
- `System Info`
- `Container Runtime Version`
- `Kubelet Version`
- MachineConfig annotations:
  - `machineconfiguration.openshift.io/currentConfig`
  - `machineconfiguration.openshift.io/desiredConfig`
  - `machineconfiguration.openshift.io/state`
  - `machineconfiguration.openshift.io/reason`

Quick extraction:

```bash
NODE=worker-1.example.com

oc get node $NODE -o jsonpath='{.status.conditions[*]}' | jq
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 4.2 Start the node debug session

```bash
oc debug node/$NODE
```

Expected output style:

```text
Starting pod/worker-1examplecom-debug ...
To use host binaries, run `chroot /host`
Pod IP: ...
If you don't see a command prompt, try pressing enter.
sh-5.1#
```

### 4.3 Enter the host filesystem

```bash
chroot /host
```

Confirm you are looking at the host:

```bash
hostname
cat /etc/os-release
rpm-ostree status
systemctl is-system-running
```

### 4.4 Exit and cleanup

Exit chroot:

```bash
exit
```

Exit debug pod:

```bash
exit
```

Verify cleanup if needed:

```bash
oc get pods -A | grep debug
```

Delete a stuck debug pod:

```bash
oc delete pod <node-debug-pod-name> -n <namespace>
```

## 5. One-Liner Debug Commands

You can run a command directly without staying inside an interactive shell.

Examples:

```bash
oc debug node/$NODE -- chroot /host hostname
oc debug node/$NODE -- chroot /host systemctl status kubelet
oc debug node/$NODE -- chroot /host journalctl -u kubelet -b --no-pager
oc debug node/$NODE -- chroot /host systemctl status crio
oc debug node/$NODE -- chroot /host journalctl -u crio -b --no-pager
oc debug node/$NODE -- chroot /host crictl ps -a
oc debug node/$NODE -- chroot /host df -hT
oc debug node/$NODE -- chroot /host lsblk
oc debug node/$NODE -- chroot /host ip addr
```

For large log output, redirect locally:

```bash
oc debug node/$NODE -- chroot /host journalctl -u kubelet -b --no-pager > ${NODE}-kubelet.log
oc debug node/$NODE -- chroot /host journalctl -u crio -b --no-pager > ${NODE}-crio.log
```

## 6. Safety Rules for Senior Administrators

`oc debug node` gives powerful access. Treat it like root access to a production node.

### 6.1 Prefer read-only diagnostics first

Safe commands:

```bash
hostnamectl
cat /etc/os-release
rpm-ostree status
systemctl status kubelet
systemctl status crio
journalctl -u kubelet -b --no-pager
journalctl -u crio -b --no-pager
crictl ps -a
crictl pods
ip addr
ip route
ss -tulpn
df -hT
df -ih
lsblk
findmnt
```

Risky commands:

```bash
systemctl restart kubelet
systemctl restart crio
rm -rf /var/lib/containers/storage
nmcli connection down <name>
reboot
shutdown
mount/umount production volumes
editing files under /etc manually
```

### 6.2 Do not permanently hand-edit managed files

OpenShift 4 manages many host files through MachineConfig and Operators. Manual edits can be overwritten or can cause drift/degradation.

Avoid permanent manual changes under:

```text
/etc/kubernetes/
/etc/crio/
/etc/containers/
/etc/systemd/system/kubelet.service.d/
/etc/NetworkManager/
/usr/local/bin/
/var/lib/kubelet/config.json
```

If a permanent change is required, implement it through:

- `MachineConfig`
- `KubeletConfig`
- `ContainerRuntimeConfig`
- Operator configuration CRs
- Day-2 supported OpenShift APIs

### 6.3 Cordon/drain before disruptive action

Before restart, reboot, storage cleanup, or risky node maintenance:

```bash
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data
```

After maintenance:

```bash
oc adm uncordon $NODE
```

Use drain carefully on control-plane nodes and storage nodes. Understand PodDisruptionBudgets, local storage, static pods, DaemonSets, and quorum-sensitive workloads.

## 7. Troubleshooting Flow: From Cluster View to Host View

A strong OpenShift admin does not immediately jump into the node. First compare cluster-level symptoms with host-level evidence.

### 7.1 Cluster-level checks

```bash
oc get co
oc get clusterversion
oc get nodes
oc get mcp
oc get pods -A -o wide | grep $NODE
oc get events -A --sort-by=.lastTimestamp | tail -100
```

For the specific node:

```bash
oc describe node $NODE
oc adm top node $NODE
oc get pods -A --field-selector spec.nodeName=$NODE
```

Check MachineConfig state:

```bash
oc get mcp
oc describe mcp worker
oc get node $NODE -o yaml | egrep 'machineconfiguration.openshift.io/(currentConfig|desiredConfig|state|reason)' -A2
```

Check MCD pod for that node:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon | grep $NODE
```

Get logs:

```bash
MCD_POD=$(oc get pods -n openshift-machine-config-operator -o wide | awk -v node="$NODE" '$0 ~ node && $1 ~ /machine-config-daemon/ {print $1; exit}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=200
```

### 7.2 Host-level checks with debug

```bash
oc debug node/$NODE
chroot /host
```

Then:

```bash
hostnamectl
systemctl is-system-running
systemctl --failed
systemctl status kubelet
systemctl status crio
journalctl -b -p warning..alert --no-pager
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
crictl info
crictl ps -a
crictl pods
```

## 8. Troubleshooting `NotReady` Node

A node becomes `NotReady` when the control plane is not receiving healthy status from kubelet or kubelet reports unhealthy conditions.

### 8.1 Cluster-side checks

```bash
oc get node $NODE
oc describe node $NODE
oc get pods -A --field-selector spec.nodeName=$NODE
```

Look for:

```text
Ready=False
Ready=Unknown
KubeletNotReady
NodeStatusUnknown
container runtime is down
PLEG is not healthy
NetworkPluginNotReady
DiskPressure=True
MemoryPressure=True
PIDPressure=True
```

### 8.2 Host-side checks

```bash
oc debug node/$NODE
chroot /host

systemctl status kubelet --no-pager
journalctl -u kubelet -b --no-pager | tail -300
systemctl status crio --no-pager
journalctl -u crio -b --no-pager | tail -300
crictl info
crictl ps -a
```

### 8.3 Common causes

| Symptom | Possible cause | Check |
|---|---|---|
| `container runtime is down` | CRI-O stopped, failed, hung | `systemctl status crio`, `journalctl -u crio` |
| `PLEG is not healthy` | Kubelet cannot sync pod state from runtime | `journalctl -u kubelet`, `crictl ps -a` |
| `NetworkPluginNotReady` | OVN/SDN CNI issue | network pod logs, `/etc/cni/net.d`, `ip route` |
| `DiskPressure=True` | Full filesystem or inode exhaustion | `df -hT`, `df -ih`, `du` |
| `MemoryPressure=True` | Host memory pressure | `free -m`, `top`, `crictl stats` |
| `PIDPressure=True` | Too many processes | `ps -eLf | wc -l`, `systemctl status` |
| Node `Ready=Unknown` | Kubelet not posting status or network path to API broken | kubelet logs, routing, DNS, API reachability |

### 8.4 Kubelet API connectivity from node

Inside chroot:

```bash
grep -R "server:" /etc/kubernetes/kubeconfig /var/lib/kubelet/kubeconfig 2>/dev/null
curl -k https://api.<cluster-domain>:6443/version
```

If DNS might be broken:

```bash
getent hosts api.<cluster-domain>
nmcli dev show | grep DNS
cat /etc/resolv.conf
```

If routing might be broken:

```bash
ip route
ip addr
ss -tulpn | grep 6443
```

## 9. Troubleshooting Kubelet with `oc debug node`

Kubelet is the node agent. It watches assigned pods, communicates with the API server, calls CRI-O through CRI, mounts volumes, reports node status, and enforces pod lifecycle.

### 9.1 Check kubelet service

```bash
oc debug node/$NODE -- chroot /host systemctl status kubelet --no-pager
```

Interactive:

```bash
oc debug node/$NODE
chroot /host
systemctl status kubelet --no-pager
systemctl cat kubelet
systemctl show kubelet -p FragmentPath -p DropInPaths -p Environment
```

### 9.2 Read kubelet logs

Current boot:

```bash
journalctl -u kubelet -b --no-pager
```

Previous boot:

```bash
journalctl -u kubelet -b -1 --no-pager
```

Follow logs:

```bash
journalctl -u kubelet -f
```

Show warning and above:

```bash
journalctl -u kubelet -b -p warning..alert --no-pager
```

Time-filtered:

```bash
journalctl -u kubelet --since "2 hours ago" --no-pager
journalctl -u kubelet --since "2026-07-03 10:00" --until "2026-07-03 11:00" --no-pager
```

### 9.3 Important kubelet log patterns

Search:

```bash
journalctl -u kubelet -b --no-pager | egrep -i 'error|fail|runtime|pleg|cni|network|eviction|image|mount|volume|certificate|x509|node.*not.*ready|diskpressure|memorypressure|pidpressure'
```

Common patterns:

| Log pattern | Meaning |
|---|---|
| `container runtime is down` | Kubelet cannot communicate with CRI-O |
| `PLEG is not healthy` | Pod lifecycle event generator cannot sync runtime state |
| `NetworkPluginNotReady` | CNI/OVN/SDN not initialized or broken |
| `failed to pull image` | Registry, auth, trust, network, or image issue |
| `x509: certificate has expired` | Certificate or trust issue |
| `eviction manager` | Node pressure eviction due to memory/disk/inodes |
| `failed to mount volume` | CSI/storage/mount problem |
| `node is not ready` | Kubelet health/status problem |

### 9.4 Compare kubelet config

```bash
cat /var/lib/kubelet/config.json | jq .
cat /etc/kubernetes/kubelet.conf 2>/dev/null
ls -l /etc/systemd/system/kubelet.service.d/
systemctl cat kubelet
```

Check for rendered MachineConfig references:

```bash
cat /etc/machine-config-daemon/currentconfig 2>/dev/null | jq .metadata.name
cat /etc/machine-config-daemon/node-annotations.json 2>/dev/null | jq .
```

### 9.5 Temporarily increasing kubelet log level

For short-term troubleshooting only:

```bash
cat > /etc/systemd/system/kubelet.service.d/30-logging.conf <<'EOF_KUBELET_LOG'
[Service]
Environment="KUBELET_LOG_LEVEL=8"
EOF_KUBELET_LOG

systemctl daemon-reload
systemctl restart kubelet
journalctl -u kubelet -f
```

Revert after collecting logs:

```bash
rm -f /etc/systemd/system/kubelet.service.d/30-logging.conf
systemctl daemon-reload
systemctl restart kubelet
```

For persistent changes, use `MachineConfig`/supported OpenShift configuration, not manual host edits.

## 10. Troubleshooting CRI-O with `oc debug node`

CRI-O is the container runtime used by OpenShift 4. Kubelet talks to CRI-O to create pod sandboxes, pull images, start containers, stop containers, and inspect runtime state.

### 10.1 Check CRI-O service

```bash
oc debug node/$NODE -- chroot /host systemctl status crio --no-pager
```

Inside chroot:

```bash
systemctl is-active crio
systemctl status crio --no-pager
journalctl -u crio -b --no-pager | tail -300
```

### 10.2 CRI-O runtime commands

```bash
crictl info
crictl version
crictl pods
crictl ps -a
crictl images
crictl stats
```

Inspect a pod sandbox:

```bash
crictl pods | head
crictl inspectp <pod-sandbox-id> | jq .
```

Inspect a container:

```bash
crictl inspect <container-id> | jq .
crictl logs <container-id>
```

### 10.3 Common CRI-O issues

| Symptom | Likely cause | Check |
|---|---|---|
| Pod stuck `ContainerCreating` | Runtime, CNI, mount, image, storage issue | `journalctl -u crio`, `crictl pods`, kubelet logs |
| `Failed to create pod sandbox` | CNI/runtime/storage problem | kubelet + CRI-O logs |
| Image pull errors | Registry, auth, proxy, CA trust, DNS | `crictl pull`, `/etc/containers/registries.conf`, trust bundle |
| `can't stat lower layer` | Container storage inconsistency | CRI-O logs, `/var/lib/containers/storage` |
| CRI-O not active | Service failure or dependency failure | `systemctl status crio`, `journalctl -xeu crio` |
| Node cannot start debug pod | Runtime on target node broken | SSH/console break-glass may be needed |

### 10.4 Check image pull from node

```bash
crictl pull quay.io/openshift-release-dev/ocp-v4.0-art-dev@sha256:<digest>
```

For your internal registry:

```bash
crictl pull registry.ocp4.example.com:8443/rhel9/mysql-80
```

Check registry configuration:

```bash
cat /etc/containers/registries.conf
ls -R /etc/containers/registries.conf.d/
ls -R /etc/docker/certs.d/ 2>/dev/null
ls -R /etc/pki/ca-trust/source/anchors/
update-ca-trust check 2>/dev/null || true
```

### 10.5 Restarting CRI-O

Restarting CRI-O can impact running workloads. Do this only after assessing risk and preferably after cordon/drain.

```bash
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data
```

Inside node debug/chroot:

```bash
systemctl restart crio
systemctl restart kubelet
systemctl status crio --no-pager
systemctl status kubelet --no-pager
```

After validation:

```bash
oc adm uncordon $NODE
```

## 11. Troubleshooting MachineConfig/MCD Problems from the Node

Machine Config Operator manages operating system and node-level configuration. Machine Config Daemon runs on each node and applies the rendered config.

### 11.1 Cluster-side MCO/MCP checks

```bash
oc get mcp
oc describe mcp worker
oc get mc
oc get nodes
```

Check node annotations:

```bash
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 11.2 MCD pod logs

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon | grep $NODE
```

```bash
MCD_POD=$(oc get pods -n openshift-machine-config-operator -o wide | awk -v node="$NODE" '$0 ~ node && $1 ~ /machine-config-daemon/ {print $1; exit}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=300
```

Search for:

```text
degraded
error
failed to drain
content mismatch
unexpected on-disk state
reboot
pivot
rpm-ostree
kubelet health
```

### 11.3 Host-side MCD files

Inside `oc debug node` + `chroot /host`:

```bash
ls -l /etc/machine-config-daemon/
cat /etc/machine-config-daemon/currentconfig 2>/dev/null | jq .metadata.name
cat /etc/machine-config-daemon/node-annotations.json 2>/dev/null | jq .
```

Check OS state:

```bash
rpm-ostree status
bootupctl status 2>/dev/null || true
journalctl -u rpm-ostreed -b --no-pager | tail -200
```

Check kubelet health because MCD watches kubelet health during updates:

```bash
systemctl status kubelet --no-pager
journalctl -u kubelet -b --no-pager | tail -200
```

### 11.4 Common MCD/MCP scenarios

| Scenario | What to check |
|---|---|
| MCP stuck `Updating=True` | MCD logs, node current/desired config, drain failures |
| MCP `Degraded=True` | `oc describe mcp`, node annotation reason, MCD logs |
| Node currentConfig != desiredConfig | MCD is still applying config or failed |
| Node reboot pending | MCD logs, `rpm-ostree status`, `systemctl status zincati` if present |
| File mismatch | Someone manually edited a managed file |
| Drain failed | PDB, static pods, local storage, unhealthy workload |

### 11.5 Manual host edits and MachineConfig drift

If a file managed by MachineConfig is manually changed, MCD can detect drift and mark the node degraded.

Example symptoms:

```text
unexpected on-disk state validating against rendered-worker-xxxxx
content mismatch for file /etc/...
```

Correct approach:

1. Find the MachineConfig that owns the file.
2. Fix or remove the conflicting manual change.
3. Apply the correct config through MachineConfig.
4. Watch MCP recovery.

Commands:

```bash
oc get mc
oc describe mcp worker
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=500
```

## 12. Troubleshooting Node Disk Pressure

Disk pressure is one of the most common causes of node instability.

### 12.1 Cluster-side symptoms

```bash
oc describe node $NODE | egrep -i 'DiskPressure|eviction|imagefs|nodefs|ephemeral'
oc get events -A --sort-by=.lastTimestamp | egrep -i 'disk|evict|pressure|ephemeral' | tail -50
```

### 12.2 Host-side checks

```bash
oc debug node/$NODE
chroot /host

df -hT
df -ih
lsblk
findmnt
```

Find large directories:

```bash
du -xh /var --max-depth=1 | sort -h
du -xh /var/lib --max-depth=1 | sort -h
du -xh /var/log --max-depth=1 | sort -h
du -xh /var/lib/containers --max-depth=1 | sort -h
du -xh /var/lib/kubelet --max-depth=1 | sort -h
```

Check journald:

```bash
journalctl --disk-usage
```

Check container images:

```bash
crictl images
crictl ps -a
```

### 12.3 What not to delete blindly

Do not blindly run:

```bash
rm -rf /var/lib/containers/storage
rm -rf /var/lib/kubelet
rm -rf /var/log/*
```

These can break workloads, runtime state, mounted volumes, or diagnostic history.

### 12.4 Safer cleanup thinking

First identify the source:

- Container images?
- Dead containers?
- Journald logs?
- Application writing to hostPath?
- EmptyDir usage?
- CSI plugin logs?
- Core dumps?
- Audit logs?

Then remediate using supported methods.

For application workloads:

```bash
oc adm top pod -A
oc get pods -A --field-selector spec.nodeName=$NODE
```

For runtime-level severe corruption, use official recovery procedures and usually cordon/drain first.

## 13. Troubleshooting Node Network Issues

Node-level network issues can appear as:

- Pod-to-pod traffic failure.
- Pod-to-service failure.
- DNS failure.
- Route not accessible from one node.
- Node cannot reach API.
- Node cannot pull images.
- OVN/SDN pods crash on one node.
- MTU mismatch.

### 13.1 Cluster-side checks

```bash
oc get pods -n openshift-ovn-kubernetes -o wide | grep $NODE
oc get pods -n openshift-network-operator
oc get co network
oc describe node $NODE | egrep -i 'NetworkUnavailable|Ready|Message|Reason'
```

For older SDN clusters:

```bash
oc get pods -n openshift-sdn -o wide | grep $NODE
```

### 13.2 Host-side checks

```bash
oc debug node/$NODE
chroot /host

ip addr
ip route
ip rule
ss -tulpn
nmcli dev status
nmcli con show
cat /etc/resolv.conf
getent hosts api.<cluster-domain>
```

Check CNI files:

```bash
ls -l /etc/cni/net.d/
cat /etc/cni/net.d/* 2>/dev/null
```

Check NetworkManager logs:

```bash
journalctl -u NetworkManager -b --no-pager | tail -300
```

Check Open vSwitch/OVN tools if available:

```bash
ovs-vsctl show 2>/dev/null || true
ovn-sbctl show 2>/dev/null || true
```

### 13.3 Use `nsenter` for container namespace troubleshooting

When a container lacks tools like `ip`, `ss`, `tcpdump`, or `curl`, use host tools inside the container network namespace.

Inside `chroot /host`:

```bash
crictl ps
crictl inspect <container-id> | jq '.info.pid'
```

Assume PID is `31150`:

```bash
nsenter -n -t 31150 -- ip addr
nsenter -n -t 31150 -- ip route
nsenter -n -t 31150 -- ss -tulpn
nsenter -n -t 31150 -- curl -vk https://kubernetes.default.svc
```

This is powerful because you are using host binaries while entering the network namespace of a container.

### 13.4 Capture packets from a node

Inside debug/chroot:

```bash
tcpdump -i any -nn host <ip-address>
tcpdump -i any -nn port 6443
tcpdump -i any -nn port 53
```

## 21. Using `oc adm node-logs` vs `oc debug node`

Before opening a debug shell, sometimes `oc adm node-logs` is enough.

Kubelet logs:

```bash
oc adm node-logs $NODE -u kubelet
oc adm node-logs --role=worker -u kubelet
oc adm node-logs --role=master -u kubelet
```

CRI-O logs:

```bash
oc adm node-logs $NODE -u crio
oc adm node-logs --role=worker -u crio
oc adm node-logs --role=master -u crio
```

Advantages of `oc adm node-logs`:

- Faster for log collection.
- Less interactive risk.
- Works well for remote log gathering.
- Good for support bundles.

Use `oc debug node` when you need:

- `systemctl status`
- `crictl` commands
- filesystem inspection
- network inspection
- `nsenter`
- storage/mount inspection
- temporary diagnostic tools
- host-level correlation

## 22. Practical Incident Runbooks

### Runbook 1: Node is `NotReady`

```bash
NODE=<node>

oc get node $NODE
oc describe node $NODE
oc get pods -A --field-selector spec.nodeName=$NODE
oc adm node-logs $NODE -u kubelet --tail=200
oc adm node-logs $NODE -u crio --tail=200

oc debug node/$NODE
chroot /host

systemctl status kubelet --no-pager
systemctl status crio --no-pager
journalctl -u kubelet -b --no-pager | tail -300
journalctl -u crio -b --no-pager | tail -300
crictl info
df -hT
df -ih
ip route
getent hosts api.<cluster-domain>
```

Decision:

- If disk full: identify source and clean safely.
- If CRI-O failed: inspect CRI-O logs and consider controlled restart.
- If kubelet cannot reach API: check network, DNS, proxy, certificates.
- If MCO degraded: check MCD logs and MachineConfig annotations.

---

### Runbook 2: Pods fail only on one node

```bash
NODE=<node>

oc get pods -A -o wide | grep $NODE
oc describe node $NODE
oc get events -A --sort-by=.lastTimestamp | tail -100

oc debug node/$NODE
chroot /host

journalctl -u kubelet -b --no-pager | egrep -i 'fail|error|cni|runtime|mount|image|pull|volume'
journalctl -u crio -b --no-pager | egrep -i 'fail|error|image|pull|network|storage'
crictl ps -a
crictl pods
ip addr
ip route
df -hT
```

Likely causes:

- Node-specific registry trust issue.
- Node-specific disk pressure.
- CNI/OVN issue on that node.
- Runtime storage corruption.
- CSI mount issue.
- Taints or labels causing unexpected scheduling.

---

### Runbook 3: MachineConfigPool stuck updating

```bash
oc get mcp
oc describe mcp worker
oc get nodes

NODE=<affected-node>

oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'

MCD_POD=$(oc get pods -n openshift-machine-config-operator -o wide | awk -v node="$NODE" '$0 ~ node && $1 ~ /machine-config-daemon/ {print $1; exit}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=500

oc debug node/$NODE
chroot /host

rpm-ostree status
systemctl status kubelet --no-pager
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u rpm-ostreed -b --no-pager | tail -200
ls -l /etc/machine-config-daemon/
cat /etc/machine-config-daemon/currentconfig 2>/dev/null | jq .metadata.name
```

Decision:

- Drain issue: resolve PDB/workload blocker.
- Kubelet unhealthy: fix kubelet/runtime issue first.
- File drift: revert manual edit or reapply through MachineConfig.
- rpm-ostree/pivot failure: inspect OS update logs and MCD logs.

---

### Runbook 4: ImagePullBackOff on specific node

```bash
POD=<pod>
NS=<namespace>
NODE=$(oc get pod $POD -n $NS -o jsonpath='{.spec.nodeName}')

oc describe pod $POD -n $NS
oc debug node/$NODE
chroot /host

getent hosts registry.ocp4.example.com
curl -vk https://registry.ocp4.example.com:8443/v2/
crictl pull registry.ocp4.example.com:8443/rhel9/mysql-80
journalctl -u crio -b --no-pager | egrep -i 'pull|registry|x509|unauthorized|timeout|proxy|no such host'
cat /etc/containers/registries.conf
ls -R /etc/containers/registries.conf.d/
ls -R /etc/docker/certs.d/ 2>/dev/null
```

Decision:

- DNS failure: fix node DNS/network.
- x509 failure: configure trusted CA properly through cluster config.
- unauthorized: check imagePullSecret and registry auth.
- timeout: network/proxy/firewall/MTU issue.

---

### Runbook 5: Node disk pressure

```bash
NODE=<node>

oc describe node $NODE | egrep -i 'DiskPressure|eviction|imagefs|nodefs|ephemeral'
oc debug node/$NODE
chroot /host

df -hT
df -ih
journalctl --disk-usage
du -xh /var --max-depth=1 | sort -h
du -xh /var/lib --max-depth=1 | sort -h
du -xh /var/log --max-depth=1 | sort -h
du -xh /var/lib/containers --max-depth=1 | sort -h
du -xh /var/lib/kubelet --max-depth=1 | sort -h
crictl images
crictl ps -a
journalctl -u kubelet -b --no-pager | egrep -i 'eviction|disk|imagefs|nodefs|ephemeral'
```

Decision:

- Application logs on hostPath: fix app/logging design.
- Too many images: review image GC/kubelet behavior.
- Journald growth: review retention policy.
- Container storage corruption: follow official recovery runbook.

## 25. Common Mistakes

### Mistake 1: Running debug from the wrong project and losing track of debug pods

Fix:

```bash
oc project default
oc debug node/$NODE
oc get pods | grep debug
```

### Mistake 2: Forgetting `chroot /host`

Without chroot, you are mostly looking at the debug container environment, not the host root filesystem.

Correct:

```bash
chroot /host
systemctl status kubelet
```

### Mistake 3: Editing managed files manually

Manual edit:

```bash
vi /etc/crio/crio.conf
```

Better:

- Use `ContainerRuntimeConfig` where supported.
- Use `MachineConfig` for host-level files.
- Use cluster config APIs.

### Mistake 4: Restarting kubelet/CRI-O without cordon/drain

Restarting services can disrupt workloads. Assess first.

```bash
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data
```

### Mistake 5: Deleting CRI-O storage blindly

Never do this casually:

```bash
rm -rf /var/lib/containers/storage
```

Use official recovery procedure and only after understanding impact.

### Mistake 6: Treating symptoms from `oc get node` as root cause

`NotReady` is a symptom. Root cause might be:

- Kubelet down.
- CRI-O down.
- API unreachable.
- Disk pressure.
- Certificate issue.
- CNI issue.
- MCO update/drain failure.
- Host OS boot/pivot problem.

## 27. Interview / Real-Time Troubleshooting Questions

### Q1. What does `oc debug node/<node>` do?

It creates a temporary privileged debug pod on the selected node. The host root filesystem is mounted at `/host`. Running `chroot /host` lets you use the host filesystem and host binaries for troubleshooting.

### Q2. Why is `chroot /host` required?

Without `chroot /host`, your root filesystem is the debug container filesystem. With `chroot /host`, `/` becomes the node host filesystem, so commands like `systemctl`, `journalctl`, `crictl`, and file inspection operate against the node.

### Q3. When can `oc debug node` fail?

It can fail when the OpenShift API is unavailable, authentication is broken, scheduling cannot happen, or the target node runtime/kubelet is too broken to start the debug pod. In such cases, SSH or console access may be required as a break-glass option.

### Q4. How do you check kubelet logs from a node?

```bash
oc adm node-logs <node> -u kubelet
```

or:

```bash
oc debug node/<node> -- chroot /host journalctl -u kubelet -b --no-pager
```

### Q5. How do you check CRI-O status?

```bash
oc debug node/<node> -- chroot /host systemctl status crio --no-pager
oc debug node/<node> -- chroot /host journalctl -u crio -b --no-pager
```

### Q6. What should you check when MachineConfigPool is degraded?

Check:

```bash
oc describe mcp <pool>
oc get node <node> -o yaml | grep machineconfiguration.openshift.io -A2
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Then use `oc debug node` to inspect kubelet, rpm-ostree, MCD files, and host state.

### Q7. Why should you avoid manual node changes?

OpenShift 4 nodes are managed by Operators. Manual changes can be overwritten or cause MachineConfig drift and degraded nodes. Persistent changes should be applied through supported APIs such as MachineConfig, KubeletConfig, ContainerRuntimeConfig, or Operator configuration.

### Q8. What is the difference between `oc adm node-logs` and `oc debug node`?

`oc adm node-logs` collects journald logs from nodes. `oc debug node` opens a privileged troubleshooting pod on a specific node and allows broader inspection using host commands and files.

### Q9. What is your first response to a NotReady worker node?

Start from cluster view:

```bash
oc describe node <node>
oc adm node-logs <node> -u kubelet
oc adm node-logs <node> -u crio
```

Then use debug:

```bash
oc debug node/<node>
chroot /host
systemctl status kubelet crio
journalctl -u kubelet -b
journalctl -u crio -b
```

### Q10. How do you troubleshoot pod networking from the node?

Use `crictl inspect` to find the container PID and `nsenter` into its network namespace:

```bash
crictl inspect <container-id> | jq '.info.pid'
nsenter -n -t <pid> -- ip addr
nsenter -n -t <pid> -- ip route
nsenter -n -t <pid> -- ss -tulpn
```

## 28. Production Troubleshooting Mindset

A senior OpenShift administrator should follow this order:

1. **Observe:** `oc get co`, `oc get nodes`, `oc get mcp`, `oc describe node`.
2. **Correlate:** pod placement, node conditions, MCD state, kubelet/CRI-O logs.
3. **Collect evidence:** `oc adm node-logs`, MCD logs, must-gather, host snapshots.
4. **Use `oc debug node`:** inspect host only after cluster-level checks.
5. **Avoid unnecessary mutation:** do not edit managed files or delete runtime data blindly.
6. **Contain impact:** cordon/drain before disruptive remediation.
7. **Fix through supported APIs:** MachineConfig, KubeletConfig, ContainerRuntimeConfig, Operator config.
8. **Validate recovery:** node Ready, MCP Updated, CO Available, workload restored.
9. **Document RCA:** exact symptom, root cause, commands used, impact, fix, prevention.
