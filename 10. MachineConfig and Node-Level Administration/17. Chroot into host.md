# Chroot into Host in OpenShift Node Administration

**Area:** MachineConfig and Node-Level Administration  
**Audience:** Advanced OpenShift Administrators / SREs / Platform Engineers  
**Depth:** Production troubleshooting level for ~10 years Linux, Kubernetes, and OpenShift experience  
**Last reviewed:** 2026-07-03

---

## 1. Executive Summary

In OpenShift, **“chroot into host”** normally means:

```bash
oc debug node/<node-name>
chroot /host
```

This is one of the most important node-level troubleshooting workflows for OpenShift administrators.

`oc debug node/<node-name>` starts a temporary privileged debug pod on the selected node. The node root filesystem is mounted inside that debug pod at `/host`. Running `chroot /host` changes the apparent root directory of your shell from the debug container filesystem to the node filesystem. After that, commands such as `systemctl`, `journalctl`, `crictl`, `rpm-ostree`, `lsblk`, `ip`, `ss`, `cat /etc/...`, and `systemctl cat kubelet` operate against the node environment.

For an experienced administrator, this is not just a command. It is a **controlled break-glass access pattern** for inspecting Red Hat Enterprise Linux CoreOS (RHCOS) nodes without SSH.

Use it mainly for:

- Inspecting kubelet, CRI-O, NetworkManager, systemd, storage, and OS state.
- Reading node logs and configuration.
- Validating MachineConfig, KubeletConfig, ContainerRuntimeConfig, kernel args, RHCOS image state, and systemd units.
- Diagnosing NotReady nodes, CRI-O failures, DNS issues, image pull problems, disk pressure, and MachineConfigPool degradation.

Avoid using it for:

- Permanent node customization.
- Manual editing of files that should be owned by MachineConfig.
- Installing RPMs directly on RHCOS.
- Random restarts of kubelet, CRI-O, NetworkManager, or control-plane static pods.
- “Fixing” one node differently from the rest of the MachineConfigPool.

In OpenShift 4, persistent host-level configuration should normally be managed declaratively through the **Machine Config Operator (MCO)**, `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig`, Node Tuning Operator, NMState, or layered RHCOS image workflows. `chroot /host` is primarily a **diagnostic and emergency access technique**.

## 2. Why This Matters in Advanced OpenShift Administration

OpenShift administrators often troubleshoot at three layers:

```text
Application layer
  Pods, Deployments, Routes, Services, PVCs, NetworkPolicies

Kubernetes/OpenShift control layer
  Operators, API, OAuth, Scheduler, Ingress, Monitoring, MCO, CVO

Node/OS layer
  RHCOS, kubelet, CRI-O, systemd, NetworkManager, kernel, storage, SELinux
```

Most OpenShift issues can be solved from the API using `oc get`, `oc describe`, `oc logs`, `oc adm inspect`, and `oc adm must-gather`. But some problems require node-level visibility:

- Node is `NotReady`.
- Pods are stuck in `ContainerCreating` because CRI-O or storage is failing.
- Image pulls fail only on one node.
- `MachineConfigPool` is `Degraded` or stuck `Updating`.
- Kubelet is reporting certificate, cgroup, DNS, eviction, or disk pressure errors.
- OVS/OVN or node networking is broken.
- The node rebooted unexpectedly.
- A host file created by MachineConfig is missing or has wrong permissions.
- You need `rpm-ostree status` to confirm the booted RHCOS deployment.

In these cases, `oc debug node/<node>` plus `chroot /host` gives you a host-level view while still entering through the Kubernetes/OpenShift control plane.

## 3. Mental Model: What Actually Happens

### 3.1 It Is Not SSH

When you run:

```bash
oc debug node/worker-1.example.com
```

OpenShift does **not** SSH into the node. Instead, it creates a temporary debug pod scheduled onto that node.

The debug pod:

- Runs with elevated privileges.
- Is scheduled specifically on the selected node.
- Mounts the node root filesystem into the pod at `/host`.
- Gives you a shell inside the debug container.
- Is normally removed when the debug session exits.

Before `chroot`:

```text
/       = debug container filesystem
/host   = actual node root filesystem
```

After:

```bash
chroot /host
```

The shell sees:

```text
/       = actual node root filesystem
```

So this command:

```bash
cat /etc/os-release
```

reads the node’s `/etc/os-release`, not the debug container’s file.

### 3.2 Why `chroot /host` Is Needed

Without `chroot`, you can still inspect node files by prefixing `/host`:

```bash
cat /host/etc/os-release
ls /host/etc/kubernetes/
ls /host/var/log/
```

But host binaries and paths are awkward. For example:

```bash
/host/usr/bin/journalctl --directory=/host/var/log/journal
```

After `chroot /host`, you can use normal host paths:

```bash
journalctl -u kubelet -b
systemctl status crio
rpm-ostree status
crictl ps -a
```

This is why most OpenShift node-debug procedures use:

```bash
oc debug node/<node>
chroot /host
```

### 3.3 `chroot` Is Filesystem Root Change, Not Magic

`chroot` changes the root directory for the current process and its children. It does not, by itself, mean you are doing a full SSH login or a full host boot session.

Important distinction:

| Concept | What it changes | OpenShift node-debug relevance |
|---|---|---|
| `chroot /host` | Filesystem root | Lets you use host binaries and paths |
| `nsenter` | Linux namespaces | Useful when entering a process/container namespace |
| `ssh core@node` | Remote login to host | Break-glass when API/kubelet/debug pod path does not work |
| `oc adm node-logs` | API-based log collection | Often safer for journal logs |
| `oc adm must-gather` | Cluster diagnostic bundle | Best first artifact for support cases |

For most OpenShift node administration, `chroot /host` is enough. For deep container namespace investigation, you might combine host tools with `nsenter`.

## 5. Basic Workflow

### 5.1 Start a Debug Session

```bash
oc debug node/worker-1.ocp4.example.com
```

You will enter a shell similar to:

```text
Starting pod/worker-1ocp4examplecom-debug ...
To use host binaries, run `chroot /host`
Pod IP: 10.0.0.25
If you don't see a command prompt, try pressing enter.
sh-5.1#
```

### 5.2 Change Root into the Node Filesystem

```bash
chroot /host
```

Now you are using the host filesystem as `/`.

### 5.3 Verify You Are Looking at the Node

```bash
hostname
cat /etc/os-release
uname -a
rpm-ostree status
systemctl status kubelet --no-pager
```

### 5.4 Exit Cleanly

You normally need to exit twice:

```bash
exit    # leaves chroot
exit    # leaves debug pod
```

If a debug pod remains:

```bash
oc get pods -A | grep debug
oc delete pod <debug-pod-name> -n <namespace>
```

## 6. One-Line Command Patterns

Interactive mode is best for investigation:

```bash
oc debug node/<node-name>
chroot /host
```

For quick commands, you can use one-liners:

```bash
oc debug node/<node-name> -- chroot /host hostname
```

```bash
oc debug node/<node-name> -- chroot /host systemctl status kubelet --no-pager
```

```bash
oc debug node/<node-name> -- chroot /host journalctl -u kubelet -b --no-pager -n 100
```

```bash
oc debug node/<node-name> -- chroot /host rpm-ostree status
```

```bash
oc debug node/<node-name> -- chroot /host crictl ps -a
```

For large output, redirect locally:

```bash
oc debug node/<node-name> -- chroot /host journalctl -u kubelet -b --no-pager > kubelet-${NODE}.log
```

However, for logs, prefer built-in commands where possible:

```bash
oc adm node-logs <node-name> -u kubelet
oc adm node-logs <node-name> -u crio
```

## 7. Relationship with RHCOS Immutability

OpenShift 4 nodes usually run **Red Hat Enterprise Linux CoreOS (RHCOS)**. RHCOS is designed to be managed by OpenShift Operators, especially the Machine Config Operator.

That means:

- Do not treat nodes like traditional manually-managed RHEL servers.
- Do not use SSH as the default administration model.
- Do not manually install packages with `yum` or `dnf` on the host.
- Do not permanently edit MachineConfig-managed files by hand.
- Do not make one worker node different from other workers unless it belongs to a separate MachineConfigPool.

A senior OpenShift admin uses `chroot /host` mostly to **observe, validate, and recover**, not to snowflake-configure nodes.

## 8. Relationship with MachineConfig and MCO

### 8.1 MCO Owns Host-Level Configuration

The Machine Config Operator manages many node OS-level settings:

- systemd units and drop-ins
- CRI-O configuration
- kubelet configuration through `KubeletConfig`
- kernel arguments
- files under `/etc` and other host paths
- registry trust configuration
- SSH keys
- chrony configuration
- RHCOS extensions and layered OS image workflows

When you create or update a `MachineConfig`, the MCO renders a new machine config for the target pool. The Machine Config Daemon on each node applies the new state, often drains the node, applies changes, and reboots the node when required.

### 8.2 `chroot /host` Is Used to Validate MCO Output

Example checks from inside chroot:

```bash
rpm-ostree status
systemctl cat kubelet
systemctl cat crio
ls -l /etc/systemd/system/
ls -l /etc/containers/
cat /etc/containers/registries.conf
cat /etc/containers/policy.json
cat /etc/pki/ca-trust/source/anchors/* 2>/dev/null
cat /etc/chrony.conf
cat /proc/cmdline
```

From outside the node:

```bash
oc get mcp
oc describe mcp worker
oc get mc
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

### 8.3 Manual Edits Can Cause Configuration Drift

If a file or systemd unit is managed by MachineConfig and you manually edit it from a chroot session, the Machine Config Daemon can detect that the actual on-disk state no longer matches the rendered MachineConfig. This is called **configuration drift**.

Symptoms:

```bash
oc get mcp
```

```text
NAME     CONFIG                 UPDATED   UPDATING   DEGRADED
worker   rendered-worker-xxxx   False     False      True
```

Useful checks:

```bash
oc describe mcp worker
oc get nodes
oc describe node <node-name>
```

Find the MCD pod running on the affected node:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node-name>
```

Check MCD logs:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod-name> -c machine-config-daemon
```

Senior-admin rule:

> If the desired final state must survive reboot, upgrade, replacement, or scaling, do it with MachineConfig or another supported Operator path, not with manual `chroot` edits.

## 9. What You Should Inspect from Chroot

### 9.1 Kubelet

```bash
systemctl status kubelet --no-pager
journalctl -u kubelet -b --no-pager -n 200
journalctl -u kubelet --since "1 hour ago" --no-pager
systemctl cat kubelet
cat /etc/kubernetes/kubelet.conf
ls -l /var/lib/kubelet/
```

Common kubelet issues:

- Certificate rotation errors.
- Node registration errors.
- CNI plugin errors.
- Image garbage collection failures.
- Eviction due to disk, memory, or PID pressure.
- Volume mount failures.
- Static pod manifest issues on control-plane nodes.

Cluster-side correlation:

```bash
oc describe node <node-name>
oc get events -A --sort-by=.lastTimestamp | tail -50
oc get csr
oc get pods -A -o wide --field-selector spec.nodeName=<node-name>
```

### 9.2 CRI-O

```bash
systemctl status crio --no-pager
journalctl -u crio -b --no-pager -n 200
crictl info
crictl ps -a
crictl images
crictl pods
```

For failed containers:

```bash
crictl ps -a | head
crictl inspect <container-id>
crictl logs <container-id>
```

For pod sandboxes:

```bash
crictl pods
crictl inspectp <pod-sandbox-id>
```

Check container storage pressure:

```bash
df -h
findmnt
lsblk -f
du -sh /var/lib/containers/storage 2>/dev/null
du -sh /var/log/pods 2>/dev/null
du -sh /var/log/containers 2>/dev/null
```

Be careful with cleanup. Do not randomly delete files under `/var/lib/containers` or `/var/lib/kubelet` on a live production node.

### 9.3 Machine Config State

Inside chroot:

```bash
rpm-ostree status
cat /proc/cmdline
systemctl status zincati --no-pager 2>/dev/null || true
ls -l /etc/machine-config-daemon/ 2>/dev/null || true
```

Outside chroot/API:

```bash
oc get mcp
oc describe mcp master
oc describe mcp worker
oc get node <node> -o yaml | grep -A5 machineconfiguration.openshift.io
oc get co machine-config
```

MCD logs:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node>
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon --since=2h
```

### 9.4 systemd Units

```bash
systemctl --failed
systemctl status kubelet --no-pager
systemctl status crio --no-pager
systemctl status NetworkManager --no-pager
systemctl list-units --type=service --state=running
systemctl cat kubelet
systemctl cat crio
```

Useful journal commands:

```bash
journalctl -b --no-pager -p warning
journalctl -b --no-pager -p err
journalctl -u kubelet -b --no-pager
journalctl -u crio -b --no-pager
journalctl -u NetworkManager -b --no-pager
```

### 9.5 Networking

```bash
ip addr
ip route
ip rule
ss -lntup
nmcli device
nmcli connection show
cat /etc/resolv.conf
hostnamectl
```

For OpenShift SDN/OVN-related node checks, depending on installed tools:

```bash
ovs-vsctl show 2>/dev/null || true
ovs-ofctl show br-ex 2>/dev/null || true
ip link show br-ex 2>/dev/null || true
```

Cluster-side correlation:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide | grep <node>
oc logs -n openshift-ovn-kubernetes <ovnkube-node-pod> -c ovnkube-node --since=1h
oc get network.operator cluster -o yaml
```

### 9.6 Storage and Filesystems

```bash
lsblk -f
blkid
findmnt
df -hT
xfs_info /sysroot 2>/dev/null || true
journalctl -k -b --no-pager | grep -iE 'xfs|nvme|scsi|blk|i/o error|readonly|ext4'
```

For kubelet volume issues:

```bash
ls -l /var/lib/kubelet/pods/
du -sh /var/lib/kubelet/pods/* 2>/dev/null | sort -h | tail
journalctl -u kubelet -b --no-pager | grep -iE 'mount|volume|csi|pvc|permission|denied'
```

Cluster-side correlation:

```bash
oc get pvc -A
oc get pv
oc get storageclass
oc describe pod <pod> -n <namespace>
oc get pods -A -o wide --field-selector spec.nodeName=<node>
```

### 9.7 Control Plane Static Pods

On control-plane nodes, static pod manifests and resources are under host paths such as:

```bash
ls -l /etc/kubernetes/manifests/
ls -l /etc/kubernetes/static-pod-resources/
```

Check static pod containers:

```bash
crictl ps -a | grep -E 'kube-apiserver|kube-controller|kube-scheduler|etcd'
```

Check kubelet logs:

```bash
journalctl -u kubelet -b --no-pager | grep -iE 'static|manifest|kube-apiserver|etcd'
```

Do **not** manually edit static pod manifests unless you are following a documented break-glass recovery procedure. OpenShift control-plane Operators own these files.

## 10. Senior-Level Troubleshooting Workflows

## 10.1 Workflow: Node `NotReady`

Start outside the node:

```bash
oc get nodes
oc describe node <node-name>
oc get pods -A -o wide --field-selector spec.nodeName=<node-name>
oc get mcp
oc get co
```

Look for:

- `Ready=False` or `Ready=Unknown`
- `DiskPressure=True`
- `MemoryPressure=True`
- `PIDPressure=True`
- `NetworkUnavailable=True`
- kubelet heartbeat stopped
- MCO update in progress
- recent reboot

Enter the node:

```bash
oc debug node/<node-name>
chroot /host
```

Check host state:

```bash
hostname
uptime
systemctl status kubelet --no-pager
journalctl -u kubelet -b --no-pager -n 300
systemctl status crio --no-pager
journalctl -u crio -b --no-pager -n 200
df -h
free -m
ss -lntup
```

Interpretation:

| Finding | Likely issue | Next action |
|---|---|---|
| kubelet inactive | node agent down | Inspect logs before restart |
| CRI-O inactive | runtime down | Inspect CRI-O logs and storage |
| disk full | eviction / runtime failures | Identify safe cleanup path |
| cert errors | kubelet/client cert issue | Check CSRs and node certs |
| CNI errors | node network plugin issue | Check OVN/SDN pods and logs |
| MCO updating | expected reboot/update | Check MCP and MCD logs |

Use restarts only after understanding impact:

```bash
systemctl restart kubelet
systemctl restart crio
```

For production worker nodes, cordon/drain first if workloads are impacted:

```bash
oc adm cordon <node-name>
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
```

Be much more careful with control-plane nodes.

---

## 10.2 Workflow: CRI-O Runtime Issue

Symptoms:

- Pods stuck `ContainerCreating`.
- Pods stuck `Terminating` on one node.
- `ImagePullBackOff` only on one node.
- Kubelet logs show runtime errors.
- `oc debug node` may fail if CRI-O is completely broken.

Commands:

```bash
oc debug node/<node>
chroot /host
systemctl status crio --no-pager
journalctl -u crio -b --no-pager -n 300
crictl info
crictl ps -a
crictl images
df -h /var/lib/containers /var/lib/kubelet /var/log
```

Check image pull/auth/trust:

```bash
cat /etc/containers/registries.conf
cat /etc/containers/policy.json 2>/dev/null || true
ls -l /etc/containers/certs.d/ 2>/dev/null || true
ls -l /etc/pki/ca-trust/source/anchors/ 2>/dev/null || true
```

If registry trust is wrong, do not manually copy CA files as a permanent solution. Fix with cluster image configuration, MachineConfig, or documented registry trust configuration path.

## 10.3 Workflow: MachineConfigPool Degraded

Start with:

```bash
oc get mcp
oc describe mcp worker
oc describe node <node>
oc get co machine-config
```

Find MCD pod:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node>
```

Read logs:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --since=4h
```

Enter host to verify file state:

```bash
oc debug node/<node>
chroot /host
```

Check relevant file or unit reported by MCD:

```bash
ls -l <path>
stat <path>
sha256sum <path>
systemctl cat <unit>
```

Typical causes:

- Someone manually edited a MachineConfig-managed file.
- A file permission or SELinux label changed.
- Rendered config applies invalid systemd unit content.
- MachineConfig path conflicts with another config.
- Node reboot failed.
- Disk issue prevented file write.

Correct approach:

1. Identify the rendered MachineConfig expected state.
2. Decide whether the MachineConfig is wrong or the node drifted.
3. If MachineConfig is wrong, create a corrected MachineConfig.
4. If node drifted, restore the expected file content/permission or let MCO reapply after remediation.
5. Avoid repeated manual edits that fight the MCO.

## 10.4 Workflow: Validate Kernel Arguments

From API:

```bash
oc get mc | grep -i kernel
oc describe mcp worker
```

From host:

```bash
oc debug node/<node>
chroot /host
cat /proc/cmdline
rpm-ostree kargs
rpm-ostree status
```

Expected process:

- Kernel arguments should be delivered through MachineConfig.
- Node usually needs reboot to boot with new kernel args.
- Validate with `/proc/cmdline` after reboot.

Do not manually edit bootloader entries as a normal fix.

## 10.5 Workflow: Validate Custom systemd Unit from MachineConfig

From API:

```bash
oc get mc 99-worker-custom-unit -o yaml
oc get mcp worker
```

From host:

```bash
oc debug node/<node>
chroot /host
systemctl status <unit-name> --no-pager
systemctl cat <unit-name>
journalctl -u <unit-name> -b --no-pager
```

Common mistakes:

- Unit file YAML indentation wrong.
- Base64 content wrong.
- Unit enabled but missing dependencies.
- Unit starts before network is ready.
- Script path does not exist or not executable.
- SELinux denial.

Check SELinux/audit clues:

```bash
journalctl -b --no-pager | grep -i denied
ausearch -m AVC -ts recent 2>/dev/null || true
```

## 10.6 Workflow: Registry Trust / Image Pull Issue

Cluster symptoms:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Node checks:

```bash
oc debug node/<node>
chroot /host
journalctl -u crio -b --no-pager | grep -iE 'x509|certificate|registry|pull|unauthorized|denied'
cat /etc/containers/registries.conf
find /etc/containers/certs.d -maxdepth 3 -type f -print 2>/dev/null
trust list | grep -i <registry-or-ca-name> -A2 -B2 2>/dev/null || true
```

Corrective pattern:

- Use supported cluster registry trust configuration.
- Let MCO roll changes across the pool.
- Validate after node update/reboot.
- Avoid manually copying CA files to one node.

## 10.7 Workflow: Disk Pressure

Cluster:

```bash
oc describe node <node> | grep -A10 -i pressure
oc get pods -A -o wide --field-selector spec.nodeName=<node>
```

Host:

```bash
oc debug node/<node>
chroot /host
df -hT
lsblk -f
du -xh /var --max-depth=1 2>/dev/null | sort -h
du -xh /var/lib --max-depth=1 2>/dev/null | sort -h
du -xh /var/log --max-depth=1 2>/dev/null | sort -h
du -xh /var/lib/containers --max-depth=1 2>/dev/null | sort -h
du -xh /var/lib/kubelet --max-depth=1 2>/dev/null | sort -h
journalctl --disk-usage
```

Potential actions:

- Identify runaway logs.
- Check kubelet eviction thresholds.
- Check image garbage collection.
- Check failed pods creating excessive logs.
- Drain and replace node if disk layout is wrong.
- For persistent cluster-wide tuning, use supported config paths.

Avoid:

```bash
rm -rf /var/lib/containers/storage/*
rm -rf /var/lib/kubelet/pods/*
```

Those commands can break the runtime and kubelet state if used carelessly.

## 10.8 Workflow: NetworkManager / Node Network Issue

Host checks:

```bash
oc debug node/<node>
chroot /host
systemctl status NetworkManager --no-pager
journalctl -u NetworkManager -b --no-pager -n 200
nmcli device
nmcli connection show
ip addr
ip route

```

Connectivity checks:

```bash
curl -vk https://api.<cluster>.<base-domain>:6443/version
ss -lntup
```

If DNS is suspected:

```bash
getent hosts api.<cluster>.<base-domain>
getent hosts quay.io
cat /etc/resolv.conf
```

Corrective approach:

- For persistent NetworkManager changes, use supported OpenShift networking configuration, NMState where appropriate, or MachineConfig only when the documented path requires it.
- Do not hand-edit one node’s connection profile and forget to declaratively manage it.

## 11. `chroot /host` vs `toolbox`

RHCOS is minimal. Some common diagnostic tools might not be available directly on the host.

After entering chroot, you can run:

```bash
toolbox
```

The toolbox container provides extra support tools. You can install packages inside the toolbox container for troubleshooting without installing them on the host OS.

Example:

```bash
oc debug node/<node>
chroot /host
toolbox
```

Inside toolbox:

```bash
dnf install -y tcpdump bind-utils strace lsof
```

Important:

- Installing packages inside toolbox does not install them into RHCOS host.
- Toolbox is for diagnostics and data gathering.
- Permanent tooling should be handled through supported images, DaemonSets, or documented RHCOS layering patterns.

## 12. `chroot` vs `nsenter`

Sometimes you need more than the host filesystem. You might need to enter a running container’s network namespace.

Example workflow:

```bash
oc debug node/<node>
chroot /host
crictl ps
crictl inspect <container-id> --output yaml | grep 'pid:'
nsenter -n -t <pid> -- ip addr
nsenter -n -t <pid> -- ss -lntup
```

Meaning:

- `crictl inspect` finds the Linux PID of the container process.
- `nsenter -n -t <pid>` enters that process’s network namespace.
- You can then run host tools such as `ip` or `ss` in that container’s network namespace.

Use this when:

- A pod network issue is not visible from the host namespace alone.
- You need to inspect a container namespace but the application container lacks tools.
- `oc exec` is unavailable or the image is too minimal.

Do not confuse this with `chroot`. They solve different problems.

## 13. Operational Safety Rules

### Rule 1: Prefer Read-Only First

Good:

```bash
journalctl -u kubelet -b
systemctl status crio
cat /proc/cmdline
rpm-ostree status
crictl ps -a
```

Risky:

```bash
vi /etc/kubernetes/kubelet.conf
systemctl restart crio
rm -rf /var/lib/containers/storage
rpm-ostree install something
```

### Rule 2: Use Supported APIs for Permanent Configuration

| Requirement | Preferred path |
|---|---|
| Kubelet settings | `KubeletConfig` |
| CRI-O runtime settings | `ContainerRuntimeConfig` |
| Host files/systemd/kernel args | `MachineConfig` |
| Registry trust | OpenShift image/registry trust config and MCO-managed rollout |
| Node tuning/sysctl/performance | Node Tuning Operator / PerformanceProfile / supported sysctl config |
| Network interface state | NMState / supported network config |
| Extra RPM content | RHCOS image layering / supported extensions |

### Rule 3: Cordon/Drain Before Intrusive Work

For worker nodes:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

After work:

```bash
oc adm uncordon <node>
```

For control-plane nodes, be more careful. Static pods, etcd quorum, API availability, and control plane Operators are involved.

### Rule 4: Avoid Snowflake Nodes

If you manually fix only one node, ask:

- Will the fix survive reboot?
- Will it survive upgrade?
- Will it exist on replacement nodes?
- Will MCO revert or mark it drifted?
- Should this be a MachineConfig instead?

### Rule 5: Capture Evidence Before Fixing

Before restarting or deleting anything:

```bash
oc describe node <node> > node-${node}.describe.txt
oc get pods -A -o wide --field-selector spec.nodeName=<node> > pods-on-${node}.txt
oc adm node-logs <node> -u kubelet > kubelet-${node}.log
oc adm node-logs <node> -u crio > crio-${node}.log
```

Or from chroot:

```bash
journalctl -u kubelet -b --no-pager > /tmp/kubelet.log
journalctl -u crio -b --no-pager > /tmp/crio.log
```

## 14. Common Errors and Fixes

### 14.1 `Error from server (Forbidden)`

Cause:

- User does not have permissions to debug nodes or create privileged debug pods.

Check:

```bash
oc auth can-i get nodes
oc auth can-i create pods
oc auth can-i create pods/exec
```

Fix:

- Use cluster-admin or an approved break-glass role.

---

### 14.2 Debug Pod Cannot Schedule

Possible causes:

- Node is unreachable.
- Node selector in current namespace blocks scheduling.
- Taints or admission controls interfere.
- Runtime on the target node is broken.

Try a debug namespace with empty node selector:

```bash
oc adm new-project debug --node-selector=""
oc debug node/<node-name> --to-namespace=debug
```

If CRI-O or kubelet on the node is broken badly, `oc debug node` might not work. Use `oc adm node-logs` if possible, or SSH break-glass if API/kubelet path is unavailable.

---

### 14.3 `chroot: failed to run command '/bin/sh'`

Possible causes:

- `/host` is not mounted correctly.
- Debug session did not start as expected.
- The node filesystem is damaged.

Check before chroot:

```bash
ls -l /host
ls -l /host/bin /host/usr/bin
cat /host/etc/os-release
```

---

### 14.4 `systemctl` Does Not Behave as Expected

Try:

```bash
systemctl status kubelet --no-pager
journalctl -u kubelet -b --no-pager
```

If systemd bus access is odd, rely on journal files and process checks:

```bash
ps -ef | grep kubelet
journalctl -u kubelet -b --no-pager
crictl ps -a
```

In deep namespace troubleshooting, `nsenter` may help, but use it only when you understand the namespace target.

---

### 14.5 MCP Becomes Degraded After Manual File Edit

Symptoms:

```bash
oc get mcp
oc describe mcp worker
```

MCD logs mention file mismatch, content mismatch, permission mismatch, or unit mismatch.

Fix:

- Restore the file to the rendered MachineConfig state, or
- Correct the MachineConfig so the declared state matches the intended file, then let MCO reconcile.

Do not keep manually editing the same file on each node.

## 15. Example: Safe Read-Only Node Audit

```bash
NODE=worker-1.ocp4.example.com

oc get node $NODE -o wide
oc describe node $NODE | egrep -i 'Ready|Pressure|NetworkUnavailable|machineconfiguration|Taints|Conditions' -A5
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
oc get mcp

oc debug node/$NODE -- chroot /host bash -c '
  echo "===== HOST =====";

  echo "===== NETWORK =====";

```

This gives a quick node health snapshot without changing anything.

- Node is `NotReady`.

## 19. Example: Emergency CRI-O Restart Decision

Do not restart CRI-O casually. It can disrupt pods on that node.

Recommended decision flow:

1. Confirm issue is node-local.
2. Check affected workloads.
3. Cordon the node.
4. Drain if possible.
5. Capture logs.
6. Restart CRI-O.
7. Validate node and pods.
8. Uncordon.

Commands:

```bash
NODE=worker-1.ocp4.example.com

oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data

oc debug node/$NODE
chroot /host
journalctl -u crio -b --no-pager > /tmp/crio-before-restart.log
systemctl restart crio
systemctl status crio --no-pager
exit
exit

oc get node $NODE
oc adm uncordon $NODE
```

If drain is impossible, document why before taking disruptive action.

## 20. Example: Node-Level Debug When Application Image Has No Tools

Application container has no `ip`, `ss`, `curl`, or `tcpdump`. You can use host tools from node debug.

Find pod node:

```bash
oc get pod <pod> -n <namespace> -o wide
```

Debug node:

```bash
oc debug node/<node>
chroot /host
```

Find container:

```bash
crictl ps | grep <pod-or-container-name>
crictl inspect <container-id> --output yaml | grep 'pid:'
```

Enter network namespace:

```bash
nsenter -n -t <pid> -- ip addr
nsenter -n -t <pid> -- ip route
nsenter -n -t <pid> -- ss -lntup
```

This is extremely useful for minimal images such as UBI minimal, distroless, scratch-based images, or locked-down app images.

## 21. Do Not Use Chroot as a Replacement for MachineConfig

Bad production pattern:

```bash
oc debug node/worker-0
chroot /host
vi /etc/sysctl.d/99-custom.conf
sysctl --system
exit
exit

oc debug node/worker-1
chroot /host
vi /etc/sysctl.d/99-custom.conf
sysctl --system
```

Problems:

- Manual drift.
- No audit trail in GitOps.
- Replacement nodes do not get the change.
- Upgrades can overwrite or reject the change.
- MCO may mark MCP degraded.

Good production pattern:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-custom-sysctl-example
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/sysctl.d/99-custom-example.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,bmV0LmlwdjQuaXBfZm9yd2FyZCA9IDEK
```

Then validate with chroot:

```bash
oc get mcp worker -w
oc debug node/<worker>
chroot /host
cat /etc/sysctl.d/99-custom-example.conf
sysctl net.ipv4.ip_forward
```

The exact supported method depends on the setting. For many sysctls, use the Node Tuning Operator or Kubernetes-safe sysctl configuration rather than a raw MachineConfig.

## 24. Interview / Exam-Oriented Explanation

If asked, “What is `chroot /host` in OpenShift?” a strong answer is:

> In OpenShift, `oc debug node/<node>` creates a temporary privileged debug pod on the selected node and mounts the host root filesystem at `/host`. Running `chroot /host` changes the shell’s root directory to the node filesystem, so I can run host binaries and inspect host paths like `/etc/kubernetes`, `/var/lib/kubelet`, `/var/lib/containers`, systemd units, kubelet logs, CRI-O state, kernel args, and rpm-ostree status. I use it mainly for node-level troubleshooting and validation. I avoid making permanent manual changes because RHCOS nodes are Operator-managed, and MachineConfig-managed files can drift and degrade the MCP. Permanent host changes should be done declaratively with MachineConfig, KubeletConfig, ContainerRuntimeConfig, Node Tuning Operator, NMState, or supported RHCOS layering workflows.

## 25. Real-World Senior Admin Notes

### 25.1 Read Logs Before Restarting

Many admins restart `kubelet` or `crio` too early. That destroys the immediate runtime state and can hide the original failure.

Better:

```bash
journalctl -u kubelet -b --no-pager > /tmp/kubelet-before.log
journalctl -u crio -b --no-pager > /tmp/crio-before.log
crictl ps -a > /tmp/crictl-ps-before.txt
systemctl status kubelet --no-pager > /tmp/kubelet-status-before.txt
systemctl status crio --no-pager > /tmp/crio-status-before.txt
```

Then act.

### 25.2 Never Assume One Node Is the Whole Problem

Always compare:

```bash
oc get nodes
oc get pods -A -o wide
oc get mcp
oc get co
```

A kubelet error on one node might be a symptom of:

- cluster DNS issue
- API instability
- certificate signer issue
- CNI rollout problem
- global pull secret change
- MCO rollout
- storage backend outage

### 25.3 Prefer Replacement Over Heroics

In cloud and virtualized environments, if a worker node is badly corrupted and workloads are replicated, the safest fix might be:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

Then replace the machine through Machine API / infrastructure automation.

OpenShift is designed for declarative node replacement. Do not spend hours hand-repairing a snowflake worker if replacement is safer.

### 25.4 Control Plane Is Different

For control-plane nodes:

- Check etcd quorum before disruptive actions.
- Understand static pods.
- Avoid manual changes under `/etc/kubernetes/manifests`.
- Do not restart multiple control-plane services across nodes at the same time.
- Capture must-gather and etcd/control-plane diagnostics where possible.

## 27. Summary

`chroot /host` is a core OpenShift node administration skill. It gives you controlled host-level visibility through an OpenShift debug pod. A senior administrator uses it to inspect and validate, not to permanently snowflake nodes.

Remember the key points:

- `oc debug node/<node>` creates a temporary privileged debug pod on the node.
- The host root filesystem is mounted at `/host`.
- `chroot /host` lets you use host paths and host binaries naturally.
- It is excellent for kubelet, CRI-O, systemd, storage, network, rpm-ostree, and MachineConfig validation.
- RHCOS is Operator-managed; permanent changes should go through supported declarative mechanisms.
- Manual edits can cause MCO configuration drift and `MachineConfigPool` degradation.
- Prefer read-only investigation first, capture evidence, and use cordon/drain before intrusive operations.
- Use SSH only as break-glass when API/kubelet/debug access is unavailable.
