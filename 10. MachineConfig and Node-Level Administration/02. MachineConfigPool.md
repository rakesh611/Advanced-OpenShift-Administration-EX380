# MachineConfigPool in OpenShift: Deep-Dive Guide for Advanced OpenShift Administration

**Topic:** MachineConfigPool  
**Area:** MachineConfig and Node-Level Administration  
**Audience:** Advanced OpenShift Administrator / 10-year Linux, DevOps, Kubernetes, and OpenShift experience level  
**Focus:** Architecture, lifecycle, commands, YAML examples, real-world operations, troubleshooting, and interview/exam readiness

---

## 1. Executive Summary

A **MachineConfigPool**, usually called an **MCP**, is an OpenShift custom resource that groups a set of nodes and a set of MachineConfig objects together. It is one of the most important node-level administration objects in OpenShift 4 because it controls how operating system configuration, kubelet configuration, CRI-O configuration, kernel arguments, systemd units, files, registries, certificates, and node OS updates are rolled out to nodes.

In simple terms:

> **MachineConfigPool = target group of nodes + selected MachineConfigs + rollout policy + observed update status.**

In OpenShift, you normally do not SSH into every node and manually change `/etc` files, systemd units, kubelet settings, or CRI-O configuration. Instead, you create declarative resources such as `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig`, or `MachineOSConfig`, and the **Machine Config Operator** renders and applies those changes to the nodes in the matching MachineConfigPool.

A healthy MCP tells you:

- Which rendered configuration the pool should run.
- Whether all nodes in the pool are updated.
- Whether nodes are currently updating.
- Whether any node is degraded.
- How many nodes are ready, updated, unavailable, or degraded.
- Whether rollout has been paused.
- Which MachineConfigs contributed to the final rendered configuration.

For a senior OpenShift administrator, MCP knowledge is critical for cluster upgrades, node reboots, worker tuning, infra node design, custom pools, kubelet/CRI-O tuning, troubleshooting stuck upgrades, degraded nodes, configuration drift, and safe production change management.

## 2. Why MachineConfigPool Exists

OpenShift 4 manages RHCOS-based nodes as part of the cluster lifecycle. This is different from traditional Linux administration where administrators manually patch and configure servers. In OpenShift, the cluster itself owns much of the node operating system lifecycle.

The Machine Config Operator uses MCPs to answer these questions:

| Question | MCP Role |
|---|---|
| Which nodes should receive this configuration? | `spec.nodeSelector` selects nodes by label. |
| Which MachineConfigs apply to those nodes? | `spec.machineConfigSelector` selects MachineConfigs by label. |
| What is the final merged config? | MCO renders a `rendered-<pool>-<hash>` MachineConfig. |
| How many nodes can update at once? | `spec.maxUnavailable` controls rollout concurrency. |
| Should rollout be temporarily stopped? | `spec.paused` stops generating/applying new desired config. |
| Is the pool healthy? | `status` fields and conditions show current state. |

Without MCPs, OpenShift would not have a clean way to apply different node-level configurations to different node roles such as `master`, `worker`, `infra`, `storage`, `gpu`, or other custom worker-based pools.

## 3. Core Objects Related to MachineConfigPool

### 3.1 MachineConfig

A **MachineConfig** defines the actual OS-level configuration. It can manage things such as:

- Files under `/etc`, `/var`, or other supported paths.
- Systemd units and drop-ins.
- Kernel arguments.
- SSH authorized keys.
- Registries and trusted CA bundles.
- CRI-O or kubelet generated configuration indirectly through higher-level CRs.

Example MachineConfig role label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

This label is very important because MCPs select MachineConfig objects using `spec.machineConfigSelector`.

### 3.2 MachineConfigPool

A **MachineConfigPool** chooses:

1. Which MachineConfigs belong to the pool.
2. Which nodes belong to the pool.
3. How the update rolls out.
4. Whether the pool is healthy or degraded.

Default pools are usually:

```bash
oc get mcp
```

Typical output:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT   AGE
master   rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False      3              3                   3                     0                      30d
worker   rendered-worker-yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy    True      False      False      6              6                   6                     0                      30d
```

### 3.3 Machine Config Operator

The **Machine Config Operator**, or **MCO**, manages the node OS configuration lifecycle. Important components include:

| Component | Purpose |
|---|---|
| `machine-config-operator` | Overall operator control loop. |
| `machine-config-controller` | Watches MachineConfigs, MCPs, KubeletConfig, ContainerRuntimeConfig, and renders final MachineConfigs. |
| `machine-config-daemon` | Runs on each node, applies the desired config, drains/cordons/reboots when required, and detects drift. |
| `machine-config-server` | Serves machine configuration during node boot/provisioning. |

### 3.4 Rendered MachineConfig

The MCO does not apply many separate MachineConfig objects one-by-one to a node. It merges the selected MachineConfigs into a single rendered config:

```text
rendered-worker-5a1d7c9e9f...
rendered-master-8b7f4a1c2d...
rendered-infra-3d2c1b0a9e...
```

You can inspect rendered configs:

```bash
oc get mc | grep rendered
oc get mc rendered-worker-<hash> -o yaml
```

The rendered MachineConfig is the final desired OS state for nodes in that pool.

## 4. Default MachineConfigPools

### 4.1 `master` Pool

The `master` MCP targets control plane nodes.

Typical characteristics:

- Uses node role label: `node-role.kubernetes.io/master`.
- Uses MachineConfig role: `master`.
- Controls critical control plane node configuration.
- Should be handled very carefully.
- `maxUnavailable` should normally remain `1`.
- Avoid unnecessary custom changes.
- Do not create custom MCPs for master nodes.

Example conceptual selector:

```yaml
spec:
  machineConfigSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: master
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/master: ""
```

### 4.2 `worker` Pool

The `worker` MCP targets compute nodes.

Typical characteristics:

- Uses node role label: `node-role.kubernetes.io/worker`.
- Uses MachineConfig role: `worker`.
- Receives most application workload node-level changes.
- Common target for kubelet, CRI-O, registry, certificate, and kernel tuning.
- Custom worker-based pools inherit worker MachineConfigs.

Example conceptual selector:

```yaml
spec:
  machineConfigSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: worker
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker: ""
```

## 5. MCP Selection Logic

MCP selection has two sides:

```text
MachineConfigs  ---> selected by machineConfigSelector
Nodes           ---> selected by nodeSelector
```

### 5.1 `spec.machineConfigSelector`

This field selects MachineConfig objects.

Example:

```yaml
spec:
  machineConfigSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: worker
```

This means: include MachineConfig objects labeled as worker MachineConfigs.

### 5.2 `spec.nodeSelector`

This field selects nodes.

Example:

```yaml
spec:
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker: ""
```

This means: apply the rendered worker configuration to nodes that have the worker node role label.

### 5.3 Why Both Selectors Matter

A common mistake is to create a MachineConfig with the right content but the wrong label. If the MachineConfig label does not match any MCP’s `machineConfigSelector`, it will not be rendered into the desired pool config.

Another common mistake is to label a node but not create a matching MCP. In that case, the node might not be managed as expected, or it might stay in the wrong pool.

Correct mental model:

```text
MachineConfig label decides which rendered config includes the change.
Node label decides which nodes receive that rendered config.
```

## 6. Anatomy of a MachineConfigPool YAML

Example custom MCP for `infra` nodes:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
  paused: false
```

Explanation:

| Field | Meaning |
|---|---|
| `metadata.name` | MCP name, for example `infra`. |
| `metadata.labels` | Useful for selecting the pool from `KubeletConfig` or `ContainerRuntimeConfig`. |
| `spec.machineConfigSelector` | Selects MachineConfigs that contribute to the rendered config. |
| `spec.nodeSelector` | Selects nodes that belong to this MCP. |
| `spec.maxUnavailable` | Number or percentage of nodes that can be unavailable during update. |
| `spec.paused` | Stops new desired config generation and node updates when true. |

Important: for a custom worker-based pool like `infra`, include both `worker` and the custom role in `machineConfigSelector`. That allows the custom pool to inherit worker MachineConfigs while also accepting pool-specific MachineConfigs.

## 7. Custom MachineConfigPools

Custom MCPs are normally used for specialized worker nodes, for example:

- Infra nodes
- Router-only nodes
- Storage nodes
- Logging nodes
- GPU nodes
- Telco/low-latency nodes
- High-memory nodes
- Build nodes
- Dedicated compliance nodes
- Test/canary nodes for MachineConfig rollout

### 7.1 Why Create a Custom MCP?

You create a custom MCP when a subset of worker nodes needs different node-level configuration.

Examples:

| Requirement | Custom MCP Benefit |
|---|---|
| Infra nodes need different kubelet reservation | Create `infra` MCP and target KubeletConfig to it. |
| GPU nodes need special kernel args or drivers | Create `gpu` MCP and apply MachineConfig only there. |
| Storage nodes need different CRI-O overlay size | Create `storage` MCP and target ContainerRuntimeConfig. |
| Canary testing before all workers | Create small `worker-canary` MCP. |
| Dedicated ingress nodes | Create `router` or `infra` MCP and add taints/tolerations. |

### 7.2 Create an Infra MCP: Full Example

#### Step 1: Label the node

```bash
oc label node worker-1.example.com node-role.kubernetes.io/infra=
```

Check roles:

```bash
oc get nodes
```

Output may show:

```text
NAME                   STATUS   ROLES          AGE   VERSION
worker-1.example.com   Ready    infra,worker   30d   v1.xx.x
```

#### Step 2: Optional: remove worker role if it should be infra-only

```bash
oc label node worker-1.example.com node-role.kubernetes.io/worker-
```

Use this carefully. Removing the worker label affects normal workload scheduling because many workloads target worker nodes by default.

#### Step 3: Create MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

#### Step 4: Verify

```bash
oc get mcp
oc describe mcp infra
```

Expected state after reconciliation:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED
infra    rendered-infra-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx     True      False      False
```

## 8. Applying a MachineConfig to a Custom MCP

Example: create a file only on infra nodes.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 51-infra-custom-file
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
        - path: /etc/example-infra-node
          mode: 0644
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8;base64,aW5mcmEtbm9kZQo=
```

Apply:

```bash
oc apply -f 51-infra-custom-file.yaml
```

Watch rollout:

```bash
watch -n 5 'oc get mcp infra && oc get nodes'
```

Verify from the `machine-config-daemon` pod on that node:

```bash
NODE=worker-1.example.com
MCD_POD=$(oc get pod -n openshift-machine-config-operator \
  -l k8s-app=machine-config-daemon \
  --field-selector spec.nodeName=${NODE} \
  -o jsonpath='{.items[0].metadata.name}')

oc rsh -n openshift-machine-config-operator ${MCD_POD} chroot /rootfs cat /etc/example-infra-node
```

Expected output:

```text
infra-node
```

## 9. MCP Rollout Lifecycle

When you create or modify node-level configuration, the lifecycle is generally:

```text
1. Admin creates/updates MachineConfig, KubeletConfig, ContainerRuntimeConfig, or related CR
2. MCO detects the change
3. Machine Config Controller renders a new rendered-<pool>-<hash> MachineConfig
4. MCP desired configuration changes
5. Machine Config Daemon on each selected node notices desiredConfig != currentConfig
6. MCD cordons and drains the node when required
7. MCD applies config
8. Node reboots if required
9. Node returns Ready
10. MCD marks currentConfig = desiredConfig
11. MCP updatedMachineCount increases
12. MCP becomes UPDATED=True, UPDATING=False, DEGRADED=False
```

### 9.1 Node Annotations Used by MCO

Useful node annotations:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Typical annotation values:

| Annotation | Meaning |
|---|---|
| `currentConfig` | Rendered MachineConfig currently applied on node. |
| `desiredConfig` | Rendered MachineConfig node should move to. |
| `state` | Current MCD state, for example `Done`, `Working`, or `Degraded`. |
| `reason` | Error reason if degraded. |

If `currentConfig` and `desiredConfig` are different for a long time, the node is stuck updating or blocked.

## 10. Understanding `oc get mcp` Output

Example:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
worker   rendered-worker-abc123...                          False     True       False      5              4                   3                     0
```

Meaning:

| Column | Meaning |
|---|---|
| `NAME` | MCP name. |
| `CONFIG` | Current rendered config associated with the pool. |
| `UPDATED` | Whether all nodes are updated to desired config. |
| `UPDATING` | Whether rollout is in progress. |
| `DEGRADED` | Whether pool has failed/degraded nodes. |
| `MACHINECOUNT` | Number of nodes selected by MCP. |
| `READYMACHINECOUNT` | Number of ready nodes in pool. |
| `UPDATEDMACHINECOUNT` | Number of nodes already running current desired config. |
| `DEGRADEDMACHINECOUNT` | Number of degraded nodes. |

### 10.1 Healthy MCP

```text
UPDATED=True, UPDATING=False, DEGRADED=False
```

This is the desired steady state.

### 10.2 Updating MCP

```text
UPDATED=False, UPDATING=True, DEGRADED=False
```

This usually means a rollout is happening. Watch node drain/reboot cycles.

### 10.3 Degraded MCP

```text
UPDATED=False, UPDATING=True/False, DEGRADED=True
```

This means at least one node failed to apply config, has drift, cannot reboot correctly, cannot pull an OS image, cannot drain, or hit another MCO/MCD error.

## 11. `maxUnavailable` in MCP

`spec.maxUnavailable` controls how many nodes in the pool can be unavailable during an update.

Example:

```yaml
spec:
  maxUnavailable: 1
```

or:

```yaml
spec:
  maxUnavailable: 20%
```

Important production notes:

- Default is normally `1`.
- For control plane nodes, keep it at `1`.
- A larger value can speed worker rollout but increases workload risk.
- It counts nodes unavailable for any reason, not only MCO-driven updates.
- It respects drain behavior and PodDisruptionBudgets.
- Do not set it to `0` to stop updates; use `spec.paused: true`.

Patch example:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":2}}'
```

Return to safer default:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

Senior admin advice:

> In production, increasing `maxUnavailable` should be treated like a change request. Validate application replicas, PDBs, topology spread, storage behavior, router capacity, monitoring alerts, and maintenance window before increasing it.

## 12. Pausing and Unpausing MCP

Pausing is useful when you want to temporarily stop rollout of new desired MachineConfigs.

Pause worker pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

### 12.1 When to Pause

Good use cases:

- You are preparing multiple related MachineConfig changes and want to roll them together.
- You are investigating a degraded or unstable rollout.
- You are controlling reboot timing during a maintenance window.
- You are using custom layered images and want to prevent immediate node rollout.
- You want to stop worker rollout while control plane updates complete.

### 12.2 Risks of Pausing

Do not leave pools paused indefinitely.

Risks:

- Worker nodes may miss required OS/config updates.
- Cluster upgrades may appear stuck or delayed.
- Security remediations may not reach nodes.
- MCP status can confuse operations teams.
- New MachineConfigs are not rolled out as expected.

Operational best practice:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[*].type
```

Or simply:

```bash
oc get mcp -o yaml | grep -E "name:|paused:"
```

## 13. KubeletConfig and MCP

`KubeletConfig` uses a machine config pool selector to target a pool.

Example: set kubelet reserved resources for infra nodes.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: infra-kubelet-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/infra: ""
  kubeletConfig:
    systemReserved:
      cpu: "500m"
      memory: "1Gi"
    kubeReserved:
      cpu: "500m"
      memory: "1Gi"
```

Important:

- Create one long-lived `KubeletConfig` per MCP where possible.
- Avoid creating many small KubeletConfig objects for the same pool.
- Kubelet changes often trigger node reboot or kubelet restart depending on the change.
- Always verify MCP rollout after applying.

Commands:

```bash
oc get kubeletconfig
oc describe kubeletconfig infra-kubelet-config
oc get mcp infra
```

## 14. ContainerRuntimeConfig and MCP

`ContainerRuntimeConfig` configures CRI-O settings and targets MCPs by selector.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: ContainerRuntimeConfig
metadata:
  name: infra-crio-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/infra: ""
  containerRuntimeConfig:
    logLevel: info
    overlaySize: 8G
```

Use cases:

- Increase overlay size for build-heavy nodes.
- Adjust CRI-O log level.
- Configure runtime options.
- Separate runtime settings for infra/storage/build nodes.

Validation:

```bash
oc get containerruntimeconfig
oc describe containerruntimeconfig infra-crio-config
oc get mcp infra
```

## 15. Relationship Between MCP and Cluster Upgrades

During an OpenShift upgrade, the MCO updates node OS content and node configuration through MCPs.

Typical upgrade behavior:

1. Cluster Version Operator starts upgrade.
2. MCO receives new payload/configuration.
3. New rendered MachineConfigs are created.
4. MCPs begin updating.
5. MCD drains, applies, and reboots nodes.
6. MCPs eventually return to updated state.
7. ClusterOperator `machine-config` becomes Available and not Progressing/Degraded.

Check upgrade impact:

```bash
oc get clusterversion
oc get co machine-config
oc get mcp
oc describe mcp worker
```

Common upgrade stuck reason:

```text
One or more MCPs are not updated or are degraded.
```

If `oc get clusterversion` is stuck at a percentage and `machine-config` ClusterOperator is progressing or degraded, inspect MCPs first.

## 16. Production Change Workflow for MCP Changes

For experienced administrators, every MCP change should follow a controlled workflow.

### 16.1 Pre-checks

```bash
oc get co
oc get mcp
oc get nodes
oc get pods -A | grep -E 'CrashLoopBackOff|Pending|Terminating|Error'
oc adm top nodes
```

Confirm:

- ClusterOperators are healthy.
- MCPs are updated and not degraded.
- Nodes are Ready.
- Workloads have sufficient replicas.
- PDBs will not block drains.
- Storage workloads can tolerate node drain.
- Application owners are informed if needed.

### 16.2 Apply Change

```bash
oc apply -f <machineconfig-or-kubeletconfig-or-crio-config>.yaml
```

### 16.3 Watch MCP

```bash
watch -n 5 'oc get mcp; echo; oc get nodes'
```

### 16.4 Deep Watch Node Annotations

```bash
for n in $(oc get nodes -o name); do
  echo "### $n"
  oc get $n -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{" current\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{" desired\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/state}{" state\n"}'
  echo
 done
```

### 16.5 Post-checks

```bash
oc get mcp
oc get nodes
oc get co machine-config
oc get pods -A | grep -E 'CrashLoopBackOff|Pending|Error'
```

### 16.6 Rollback Strategy

MachineConfig rollback usually means removing or correcting the bad MachineConfig and letting the MCO render a new config.

```bash
oc delete mc <bad-machineconfig>
oc get mcp
```

For KubeletConfig or ContainerRuntimeConfig, either edit the CR back to the previous values or delete the temporary CR.

Important:

- Rollback may trigger another node update/reboot.
- Do not manually edit rendered MachineConfigs.
- Do not manually edit node files to “fix” desired state unless directed by Red Hat support or as an emergency temporary recovery.

## 17. Troubleshooting MCP Issues

### 17.1 First Five Commands

When someone says “MCP is degraded” or “upgrade is stuck,” run:

```bash
oc get mcp
oc describe mcp <pool-name>
oc get nodes
oc get co machine-config
oc get pods -n openshift-machine-config-operator -o wide
```

Then inspect affected node annotations:

```bash
NODE=<node-name>
oc get node $NODE -o yaml | grep -A5 -B5 machineconfiguration.openshift.io
```

### 17.2 Check MCD Logs for a Node

```bash
NODE=<node-name>
MCD_POD=$(oc get pod -n openshift-machine-config-operator \
  -l k8s-app=machine-config-daemon \
  --field-selector spec.nodeName=${NODE} \
  -o jsonpath='{.items[0].metadata.name}')

oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=200
```

### 17.3 Check Controller Logs

```bash
oc logs -n openshift-machine-config-operator deploy/machine-config-controller --tail=200
oc logs -n openshift-machine-config-operator deploy/machine-config-operator --tail=200
```

### 17.4 Describe MCP

```bash
oc describe mcp worker
```

Look for:

- `Message`
- `Reason`
- `Degraded Machine Count`
- `Unavailable Machine Count`
- Events
- Current and desired rendered config

## 18. Common MCP Problems and Fixes

### Problem 1: MCP Stuck Updating

Symptoms:

```text
UPDATED=False
UPDATING=True
DEGRADED=False
```

Possible causes:

- Node is draining slowly.
- PDB blocks eviction.
- Node is rebooting slowly.
- Node cannot pull required OS/update image.
- Node is NotReady.
- MCD pod is not running.
- Another node already unavailable and `maxUnavailable` is blocking next node.

Commands:

```bash
oc get nodes
oc describe node <node>
oc get pdb -A
oc get pods -A --field-selector spec.nodeName=<node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Fix approach:

1. Identify the node stuck in `Working` state.
2. Check drain blockers and PDBs.
3. Check node readiness and kubelet status.
4. Check MCD logs.
5. Resolve workload, node, image, or config issue.
6. Avoid force deletion unless you understand workload impact.

### Problem 2: MCP Degraded Due to Config Drift

Symptoms:

```text
DEGRADED=True
reason mentions content mismatch, file mismatch, mode mismatch, or unexpected on-disk state
```

Cause:

Someone manually changed a file, systemd unit, or permission that is controlled by MachineConfig.

Check:

```bash
oc describe mcp worker
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Fix:

- Restore the file content/permission to match the MachineConfig, or
- Update the MachineConfig intentionally so desired state matches the required on-disk state.

Avoid:

```text
Manual SSH fixes that fight against MachineConfig desired state.
```

### Problem 3: Wrong MachineConfig Label

Symptoms:

- MachineConfig created successfully.
- MCP does not update.
- No rendered config change.

Check:

```bash
oc get mc <name> --show-labels
oc get mcp <pool> -o yaml | yq '.spec.machineConfigSelector'
```

Fix:

```bash
oc label mc <name> machineconfiguration.openshift.io/role=worker --overwrite
```

Or use the correct custom role:

```bash
oc label mc <name> machineconfiguration.openshift.io/role=infra --overwrite
```

### Problem 4: Node Not in Expected MCP

Symptoms:

- Custom MCP has `MACHINECOUNT=0`.
- Node did not get expected config.
- Node role label does not match MCP nodeSelector.

Check:

```bash
oc get nodes --show-labels | grep node-role
oc get mcp infra -o yaml | yq '.spec.nodeSelector'
```

Fix:

```bash
oc label node <node> node-role.kubernetes.io/infra=
```

### Problem 5: Custom MCP Created Incorrectly

Bad example:

```yaml
spec:
  machineConfigSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: infra
```

This selects only infra MachineConfigs and does not inherit worker MachineConfigs.

Better custom worker-based pool:

```yaml
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
```

### Problem 6: Pool Paused and Forgotten

Symptoms:

- New configs are not rolling out.
- Upgrade stuck or delayed.
- `spec.paused: true`.

Check:

```bash
oc get mcp <pool> -o jsonpath='{.spec.paused}{"\n"}'
```

Fix:

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
```

### Problem 7: Bad MachineConfig Breaks Node

Symptoms:

- Node reboots and does not return Ready.
- MCD degraded.
- Systemd unit fails.
- Incorrect file path or invalid config.

Fix approach:

1. Delete or correct bad MachineConfig.
2. Wait for new rendered config.
3. If node is unreachable, recover using console/SSH according to support process.
4. Check `journalctl`, kubelet, CRI-O, and MCD logs.

Useful node-side checks if SSH/debug access is available:

```bash
journalctl -u kubelet -b --no-pager | tail -100
journalctl -u crio -b --no-pager | tail -100
journalctl -u machine-config-daemon -b --no-pager | tail -100
rpm-ostree status
systemctl --failed
```

## 19. MCP and Node Drain Behavior

When the MCO applies many MachineConfig changes, the MCD usually:

1. Cordons the node.
2. Drains workload pods.
3. Applies configuration.
4. Reboots if required.
5. Uncordons after successful update.

Important production considerations:

- PDBs can block drain.
- Single-replica pods can cause service impact.
- Local storage workloads require special planning.
- DaemonSet pods are handled differently during drain.
- Static control plane pods must remain safe on master nodes.
- Router/ingress capacity must be sufficient if infra nodes reboot.
- Storage systems such as ODF/Ceph require careful maintenance handling.

Check drain blockers:

```bash
oc get pdb -A
oc describe node <node>
oc get pods -A --field-selector spec.nodeName=<node> -o wide
```

## 20. Advanced Operational Patterns

### 20.1 Canary MCP

Create a small custom MCP for one or two worker nodes and test MachineConfigs before applying to all workers.

Example:

```text
worker-canary MCP -> one non-critical worker node
```

Workflow:

1. Label one node as canary.
2. Create custom MCP inheriting worker config.
3. Apply MachineConfig with canary role.
4. Observe rollout and workload impact.
5. Promote the change to worker pool after validation.

### 20.2 Infra MCP

Common for routers, registry, monitoring, logging, or infra workloads.

Remember:

- MCP controls node OS configuration.
- Taints and tolerations control scheduling.
- Node labels control role membership.
- MachineSets control infrastructure provisioning on IPI platforms.

Do not confuse these layers.

### 20.3 Storage MCP

Useful when storage nodes need:

- Different kubelet reservations.
- Different eviction thresholds.
- Different CRI-O settings.
- Additional kernel args.
- Separate reboot windows.

### 20.4 GPU MCP

Useful when GPU workers need:

- Driver-related MachineConfigs.
- Runtime configuration.
- Specialized kernel args.
- Taints for GPU workloads.

## 21. Safe MCP Design Principles

1. **Never manually edit rendered MachineConfigs.** They are generated by the MCO.
2. **Use custom MCPs only for worker-based roles.** Do not create custom master pools.
3. **Keep `maxUnavailable: 1` unless you have a tested reason.**
4. **Do not leave MCPs paused.** Track paused state like a production risk.
5. **Use one KubeletConfig per MCP where possible.**
6. **Use one ContainerRuntimeConfig per MCP where possible.**
7. **Keep MachineConfig names ordered and meaningful.** Example: `50-worker-chrony`, `99-worker-kargs`.
8. **Avoid direct SSH changes.** MachineConfig should own node state.
9. **Test disruptive changes on canary nodes.**
10. **Always monitor MCO, MCP, nodes, and application health during rollout.**

## 23. Exam and Interview View

### 23.1 Short Definition

A MachineConfigPool is an OpenShift custom resource that groups nodes by node selector and MachineConfigs by MachineConfig selector. The MCO renders the selected MachineConfigs into one final rendered MachineConfig and rolls it out to nodes in the pool while tracking update and degraded status.

### 23.2 Explain Like a Senior Admin

MachineConfigPool is the operational boundary for node configuration rollout. It decides which nodes receive which OS-level configuration and controls how disruptive changes are applied. When a MachineConfig changes, the MCO creates a new rendered config for the matching pool, and the Machine Config Daemon applies it node by node, often draining and rebooting nodes. MCP status is one of the first places to check during node config changes or stuck cluster upgrades.

### 23.3 Common Interview Questions

#### Q1. What is the difference between MachineConfig and MachineConfigPool?

**MachineConfig** defines the node configuration. **MachineConfigPool** decides which nodes receive which MachineConfigs and tracks rollout status.

#### Q2. What happens when you create a new worker MachineConfig?

The MCO detects it, renders a new `rendered-worker-<hash>` MachineConfig, updates the worker MCP desired configuration, and the MCD applies it to worker nodes according to `maxUnavailable` and drain/reboot rules.

#### Q3. Why is my MachineConfig not applying?

Check the MachineConfig label, MCP `machineConfigSelector`, node label, MCP `nodeSelector`, paused state, MCO logs, and MCP degraded status.

#### Q4. Can I stop MCP updates with `maxUnavailable: 0`?

No. Use `spec.paused: true`.

#### Q5. Should I create a custom MCP for master nodes?

No. Custom pools should be worker-based. Control plane node changes should be handled through the default master pool and with extreme care.

#### Q6. What does `DEGRADED=True` mean?

At least one node in the pool failed to apply the desired config, encountered configuration drift, cannot update, or has another MCD/MCO error. Inspect `oc describe mcp`, node annotations, and MCD logs.

## 24. Real-World Troubleshooting Scenario

### Scenario

Cluster upgrade stuck. `oc get clusterversion` shows upgrade not completed. `oc get co machine-config` shows progressing. `oc get mcp` shows:

```text
NAME     CONFIG                   UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
master   rendered-master-aaa       True      False      False      3              3                   3                     0
worker   rendered-worker-bbb       False     True       True       6              5                   4                     1
```

### Senior Admin Investigation

1. Identify affected pool:

```bash
oc describe mcp worker
```

2. Identify degraded node from message or annotations:

```bash
oc get nodes
for n in $(oc get nodes -o name); do
  echo "### $n"
  oc get $n -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{" "}{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
 done
```

3. Check MCD logs for affected node:

```bash
NODE=<degraded-node>
MCD_POD=$(oc get pod -n openshift-machine-config-operator \
  -l k8s-app=machine-config-daemon \
  --field-selector spec.nodeName=${NODE} \
  -o jsonpath='{.items[0].metadata.name}')

oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=300
```

4. Determine root cause:

Possible examples:

- Config drift in `/etc/chrony.conf`.
- Bad systemd unit in a custom MachineConfig.
- Node cannot drain due to PDB.
- Node NotReady due to kubelet failure.
- Pull secret/registry issue pulling OS image.
- Disk pressure preventing update.

5. Fix based on cause:

- Correct or remove bad MachineConfig.
- Restore drifted file.
- Resolve PDB/drain blocker.
- Fix kubelet/CRI-O/node condition.
- Free disk space.
- Verify image pull access.

6. Watch recovery:

```bash
watch -n 5 'oc get mcp; echo; oc get nodes; echo; oc get co machine-config'
```

## 25. MCP vs MachineSet vs Node Labels vs Taints

These are often confused.

| Object | Layer | Purpose |
|---|---|---|
| `MachineSet` | Infrastructure provisioning | Creates/deletes machines on cloud/platform. |
| `Node` labels | Kubernetes scheduling and selection | Identifies node role or attributes. |
| `MachineConfigPool` | OS/node config management | Applies rendered MachineConfig to selected nodes. |
| `Taint` | Scheduling control | Repels pods unless they tolerate the taint. |
| `KubeletConfig` | Kubelet tuning | Generates MachineConfig for selected MCP. |
| `ContainerRuntimeConfig` | CRI-O tuning | Generates MachineConfig for selected MCP. |

Example:

- MachineSet creates infra nodes.
- Node labels mark them as infra.
- MCP applies infra node OS config.
- Taints prevent normal workloads from scheduling there.
- Tolerations allow routers/monitoring/logging to run there.

## 26. Best-Practice Naming

MachineConfig names are often ordered numerically because order can matter during merge/rendering.

Examples:

```text
50-worker-chrony
50-worker-custom-ca
51-infra-sysctl
60-worker-registries
99-worker-kernel-args
```

Suggested conventions:

| Prefix | Use |
|---|---|
| `00-` to `49-` | Usually reserved/generated/base configs. Avoid unless you know why. |
| `50-` to `79-` | Administrator custom configs. |
| `80-` to `98-` | Special or high-priority custom configs. |
| `99-` | Last override style configs; use carefully. |

Do not rely only on naming to target a pool. The label is what makes the MCP select the MachineConfig.

## 27. What Not To Do

Avoid these mistakes:

```text
1. Do not SSH to every node and manually change files managed by MachineConfig.
2. Do not edit rendered MachineConfigs manually.
3. Do not create custom pools for master nodes.
4. Do not set maxUnavailable high on control plane nodes.
5. Do not leave worker MCP paused after maintenance.
6. Do not apply untested MachineConfig to all workers in production.
7. Do not forget PDB and drain impact.
8. Do not remove a node from a custom MCP unless it will still belong to another valid MCP.
9. Do not use wrong MachineConfig labels.
10. Do not ignore DEGRADED=True during upgrades.
```

## 29. Practical Lab: Create, Apply, Verify, Remove Custom MCP

### 29.1 Create MCP

```bash
oc label node <worker-node> node-role.kubernetes.io/labpool=
```

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: labpool
  labels:
    pools.operator.machineconfiguration.openshift.io/labpool: ""
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - labpool
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/labpool: ""
  maxUnavailable: 1
```

```bash
oc apply -f labpool-mcp.yaml
oc get mcp labpool
```

### 29.2 Apply Custom MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 51-labpool-file
  labels:
    machineconfiguration.openshift.io/role: labpool
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
        - path: /etc/labpool
          mode: 0644
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8;base64,bGFicG9vbAo=
```

```bash
oc apply -f 51-labpool-file.yaml
watch -n 5 'oc get mcp labpool; oc get nodes'
```

### 29.3 Verify File

```bash
NODE=<worker-node>
MCD_POD=$(oc get pod -n openshift-machine-config-operator \
  -l k8s-app=machine-config-daemon \
  --field-selector spec.nodeName=${NODE} \
  -o jsonpath='{.items[0].metadata.name}')

oc rsh -n openshift-machine-config-operator $MCD_POD chroot /rootfs cat /etc/labpool
```

### 29.4 Remove Lab MCP Safely

First, make sure the node still belongs to another valid pool, usually worker:

```bash
oc label node <worker-node> node-role.kubernetes.io/worker=
oc label node <worker-node> node-role.kubernetes.io/labpool-
```

Wait for worker MCP to reconcile:

```bash
oc get mcp
```

Then remove lab config:

```bash
oc delete mc 51-labpool-file
oc delete mcp labpool
```

## 30. Final Senior-Level Takeaways

- MCP is the node configuration rollout boundary in OpenShift.
- Every MachineConfig change eventually shows up through an MCP rollout.
- `machineConfigSelector` selects configs; `nodeSelector` selects nodes.
- Default pools are `master` and `worker`.
- Custom pools should be worker-based and usually inherit worker configs.
- MCP health is critical during upgrades.
- `maxUnavailable` controls rollout concurrency; `paused` stops rollout.
- Degraded MCP usually means MCD error, config drift, failed apply, drain problem, or node issue.
- Use MCPs to operate nodes declaratively, not SSH-based manual configuration.
- In production, treat MCP changes as disruptive infrastructure changes because they can drain and reboot nodes.
