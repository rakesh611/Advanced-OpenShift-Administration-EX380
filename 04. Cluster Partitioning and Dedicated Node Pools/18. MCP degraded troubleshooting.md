# MCP Degraded Troubleshooting in OpenShift

**Topic:** Cluster Partitioning and Dedicated Node Pools  
**Level:** Advanced OpenShift Administration, 10+ years experience  
**Focus:** Troubleshooting `MachineConfigPool` degraded state in real production clusters  
**Applies to:** OpenShift Container Platform 4.x, especially environments using custom/dedicated node pools such as infra, logging, monitoring, storage, GPU, application, or special workload pools

---

## 1. Why MCP degraded troubleshooting matters

In OpenShift, node operating system configuration is not normally managed by manually editing files on each node. It is managed declaratively by the **Machine Config Operator**.

The Machine Config Operator, usually called **MCO**, manages low-level node configuration such as:

- RHCOS operating system updates
- kubelet configuration
- CRI-O configuration
- systemd units and drop-ins
- kernel arguments
- sysctl/kernel tuning through managed files
- registry configuration
- SSH key configuration for the `core` user
- selected NetworkManager configuration
- custom files under supported host paths such as `/etc` and `/var`

A `MachineConfigPool`, usually called **MCP**, groups nodes that must receive the same rendered machine configuration. In default clusters you normally see:

```bash
oc get mcp
```

Example:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
master   rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False      3              3                   3                     0
worker   rendered-worker-yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy    True      False      False      6              6                   6                     0
```

In advanced clusters you often add dedicated pools:

```text
master
worker
infra
logging
monitoring
storage
gpu
app
edge
rt-kernel
```

When an MCP becomes **Degraded**, it means the MCO is blocked from applying the current or desired machine config to at least one node in that pool, or the configuration failed on one or more nodes.

This is serious because:

- cluster upgrades can pause or fail
- node configuration changes stop rolling out
- new node pool changes might not apply
- custom workload isolation can break
- nodes may stay cordoned or stuck in `SchedulingDisabled`
- a dedicated pool can become inconsistent across nodes
- infra/logging/monitoring components might lose HA if their nodes cannot update cleanly

A degraded MCP is not always a total outage. A degraded node can still be `Ready` and running workloads, but it cannot be safely updated until the underlying issue is fixed.

## 2. Core architecture: MCO, MCP, MC, rendered config, and MCD

Before troubleshooting, understand the moving parts.

### 2.1 MachineConfigOperator

The **Machine Config Operator** is the cluster-level operator responsible for machine configuration. Check it with:

```bash
oc get co machine-config
oc describe co machine-config
```

Important fields:

```text
AVAILABLE
PROGRESSING
DEGRADED
MESSAGE
```

If `machine-config` clusteroperator is degraded, there is usually at least one MCP or MCD problem behind it.

---

### 2.2 MachineConfig

A `MachineConfig` is the declarative object that describes OS-level changes for nodes.

Example:

```bash
oc get mc
```

Example output:

```text
00-master
00-worker
01-master-container-runtime
01-worker-container-runtime
99-worker-custom-sysctl
99-infra-chrony
rendered-worker-abc123...
rendered-infra-def456...
```

Human-created or operator-created MachineConfigs are merged into **rendered MachineConfigs**.

---

### 2.3 Rendered MachineConfig

A rendered MachineConfig is the final calculated config for a pool.

Example:

```bash
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
```

Output:

```text
rendered-worker-abc123def456
```

The rendered config is what each node in that MCP should converge to.

---

### 2.4 MachineConfigPool

An MCP maps:

- a group of nodes
- to a set of MachineConfigs
- and controls rollout status

Example:

```bash
oc get mcp worker -o yaml
```

Important sections:

```yaml
spec:
  machineConfigSelector: ...
  nodeSelector: ...
  maxUnavailable: 1
  paused: false
status:
  configuration:
    name: rendered-worker-...
  conditions:
  - type: Updated
  - type: Updating
  - type: Degraded
  machineCount: 6
  readyMachineCount: 6
  updatedMachineCount: 5
  degradedMachineCount: 1
  unavailableMachineCount: 1
```

---

### 2.5 MachineConfigDaemon

The **Machine Config Daemon**, or **MCD**, runs on every node as a DaemonSet pod in the `openshift-machine-config-operator` namespace.

Check it:

```bash
oc get pods -n openshift-machine-config-operator -o wide
```

Example:

```text
machine-config-daemon-2kndf    2/2 Running   worker-1
machine-config-daemon-7xabc    2/2 Running   worker-2
machine-config-daemon-p9qzz    2/2 Running   infra-1
```

The MCD does node-level work:

- validates the current node config
- detects configuration drift
- drains/cordons node when required
- writes files
- updates systemd units
- applies OS updates/pivots
- reboots nodes when needed
- uncordons node after successful update
- reports status back through node annotations and MCP status

## 3. MCP status fields explained deeply

Run:

```bash
oc get mcp
```

Example degraded output:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
worker   rendered-worker-404caf3180818d8ac1f50c32f14b57c3   False     True       True       4              3                   3                     1
```

### 3.1 `UPDATED`

`UPDATED=True` means all targeted nodes are at the current desired rendered config.

If `UPDATED=False`, at least one node is not yet at the desired rendered config.

Common reasons:

- rollout is still progressing
- node is cordoned/draining
- node is rebooting
- MCD failed
- node is unreachable
- PDB prevents drain
- config drift blocks preflight
- invalid MachineConfig prevents apply

---

### 3.2 `UPDATING`

`UPDATING=True` means the pool is actively reconciling toward a desired config.

This is normal during:

- cluster update
- new MachineConfig creation
- KubeletConfig change
- ContainerRuntimeConfig change
- image registry mirror change
- kernel argument change
- custom pool creation
- node label move into another MCP

But if `UPDATING=True` stays for too long, investigate.

---

### 3.3 `DEGRADED`

`DEGRADED=True` means at least one node in that pool failed to apply or reconcile machine configuration.

This is not just an informational warning. It can block cluster upgrades and future machine config rollouts.

---

### 3.4 `MACHINECOUNT`

Total number of nodes selected by the MCP.

If this number is wrong, check:

```bash
oc get nodes --show-labels
oc get mcp <pool> -o yaml
```

Bad node label design can create unexpected MCP membership.

---

### 3.5 `READYMACHINECOUNT`

Number of MCP nodes that are Kubernetes `Ready`.

A node can be `Ready` but still degraded from MCO perspective.

Example:

```text
NodeReady=True
MCP DEGRADED=True
```

This usually means workloads may still run, but MCO cannot safely update that node.

---

### 3.6 `UPDATEDMACHINECOUNT`

Number of nodes already running the MCP current rendered config.

If this is lower than `MACHINECOUNT`, find which nodes are behind:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,ROLE:.metadata.labels.node-role\.kubernetes\.io/worker,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state
```

---

### 3.7 `DEGRADEDMACHINECOUNT`

Number of nodes marked degraded or unreconcilable.

If non-zero, immediately identify the node:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason
```

---

### 3.8 `UNAVAILABLEMACHINECOUNT`

Number of targeted nodes unavailable because they are updating or not `Ready`.

This matters for `maxUnavailable` because the MCO respects pool disruption limits.

## 4. MCP and dedicated node pools

In cluster partitioning, different workload classes often run on dedicated node pools.

Examples:

| Pool | Purpose |
|---|---|
| `infra` | routers, registry, ingress, cluster infra components |
| `logging` | Loki, Elasticsearch, Vector/Fluentd collectors, log storage |
| `monitoring` | Prometheus, Alertmanager, Thanos Querier |
| `storage` | ODF/Ceph, local storage, storage-heavy nodes |
| `gpu` | GPU workloads, NVIDIA GPU Operator nodes |
| `app` | standard user applications |
| `rt-kernel` | low-latency/telco workloads |

A custom MCP normally inherits from the worker pool and then adds pool-specific MachineConfigs.

Example custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

A dedicated pool has its own risk profile:

- An `infra` MCP degradation can affect routers, registry, and ingress capacity.
- A `logging` MCP degradation can affect cluster log ingestion.
- A `monitoring` MCP degradation can affect alert visibility.
- A `storage` MCP degradation can affect ODF placement, quorum, or rebalance stability.
- A `gpu` MCP degradation can block GPU driver/kernel alignment.
- A `rt-kernel` MCP degradation can break performance tuning rollout.

A senior admin does not troubleshoot only the object. They troubleshoot the impact on platform capacity and workload isolation.

## 5. Golden rule: do not randomly patch node annotations

You will find many blog posts suggesting direct patching of node annotations such as:

```text
machineconfiguration.openshift.io/currentConfig
machineconfiguration.openshift.io/desiredConfig
machineconfiguration.openshift.io/state
machineconfiguration.openshift.io/reason
```

Do **not** start there.

Direct annotation patching can make the API status lie while the node on-disk state remains wrong. Use it only when you fully understand the current rendered config, node disk state, MCD state, and recovery objective.

Preferred order:

1. Identify degraded pool.
2. Identify degraded node.
3. Read MCP condition message.
4. Read node annotations.
5. Read MCD logs on that node.
6. Verify current and desired rendered configs.
7. Determine root cause class.
8. Fix source-of-truth or on-disk drift.
9. Let MCO reconcile.
10. Use force file only if appropriate and with reboot expectation.

## 6. One-screen MCP degraded triage commands

Use this first during an incident.

```bash
# 1. Cluster operator health
oc get co machine-config
oc describe co machine-config

# 2. MCP summary
oc get mcp
oc describe mcp

# 3. Identify degraded nodes and reasons
oc get nodes -o custom-columns=NAME:.metadata.name,READY:.status.conditions[-1].type,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig

# 4. Show MCD pods with node placement
oc get pods -n openshift-machine-config-operator -o wide

# 5. Get logs from MCD pod on affected node
NODE=<affected-node>
MCD_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide --no-headers | awk -v n="$NODE" '$7==n {print $1}')
oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon --tail=300

# 6. Events
oc get events -A --sort-by=.lastTimestamp | grep -iE 'machine|mcd|mco|drain|degrad|failed|reboot|config'

# 7. MachineConfigNode status if available in your version
oc get machineconfignodes 2>/dev/null || true
oc describe machineconfignodes <node> 2>/dev/null || true
```

## 7. Production-safe troubleshooting workflow

### Phase 0: Declare the blast radius

Ask:

- Which MCP is degraded?
- Is it `master`, `worker`, or custom pool?
- How many nodes are affected?
- Is a cluster upgrade running?
- Is a MachineConfig rollout running?
- Are nodes cordoned?
- Are critical workloads affected?
- Is etcd healthy if the control-plane pool is involved?

Commands:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pdb -A
oc adm top nodes
```

For control plane MCP issues:

```bash
oc get co kube-apiserver kube-controller-manager kube-scheduler etcd
oc get pods -n openshift-etcd -o wide
oc get nodes -l node-role.kubernetes.io/master
```

Never reboot multiple control-plane nodes at the same time unless you are deliberately following a documented recovery process.

---

### Phase 1: Identify the degraded pool

```bash
oc get mcp
```

Then describe the specific pool:

```bash
oc describe mcp <pool-name>
```

Look for:

```text
Conditions:
  Type:    Degraded
  Status:  True
  Message: ...
```

The `Message` often tells you the node and high-level error.

Example messages you might see:

```text
Node worker-2 is reporting: "unexpected on-disk state validating against rendered-worker-..."
```

```text
failed to drain node worker-3: cannot evict pod as it would violate the pod's disruption budget
```

```text
error running rpm-ostree rebase
```

```text
content mismatch for file /etc/chrony.conf
```

```text
failed to apply kubelet config
```

---

### Phase 2: Identify the exact node

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig
```

Example:

```text
NAME        STATE      REASON                                      CURRENT                    DESIRED
worker-1    Done       <none>                                      rendered-worker-a111       rendered-worker-a111
worker-2    Degraded   content mismatch for file /etc/chrony.conf  rendered-worker-a111       rendered-worker-b222
worker-3    Working    <none>                                      rendered-worker-a111       rendered-worker-b222
```

Interpretation:

- `worker-2` is degraded because `/etc/chrony.conf` does not match expected content.
- It has not moved to desired config.
- Fix the drift or source MachineConfig.

---

### Phase 3: Read MCD logs for affected node

Find the MCD pod on the degraded node:

```bash
NODE=worker-2
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide | grep "$NODE"
```

Get logs:

```bash
MCD_POD=<machine-config-daemon-pod>
oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon --tail=500
```

Previous logs can help if the pod restarted:

```bash
oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon --previous --tail=500
```

Search error patterns:

```bash
oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon --tail=1000 | grep -iE 'error|fail|degrad|drift|mismatch|drain|reboot|pivot|rpm-ostree|kubelet|crio'
```

---

### Phase 4: Inspect node annotations

```bash
NODE=worker-2
oc get node "$NODE" -o jsonpath='{range .metadata.annotations[*]}{.}{"\n"}{end}'
```

More useful:

```bash
oc get node "$NODE" -o jsonpath='current={.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}desired={.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}state={.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}reason={.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Expected healthy state:

```text
current=rendered-worker-b222
desired=rendered-worker-b222
state=Done
reason=
```

Problem state:

```text
current=rendered-worker-a111
desired=rendered-worker-b222
state=Degraded
reason=content mismatch for file /etc/chrony.conf
```

---

### Phase 5: Compare current and desired rendered configs

```bash
CURRENT=$(oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}')
DESIRED=$(oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}')

echo "CURRENT=$CURRENT"
echo "DESIRED=$DESIRED"

oc get mc "$CURRENT" -o yaml > /tmp/current-mc.yaml
oc get mc "$DESIRED" -o yaml > /tmp/desired-mc.yaml

diff -u /tmp/current-mc.yaml /tmp/desired-mc.yaml | less
```

Focus on:

```yaml
spec:
  config:
    ignition:
    storage:
      files:
    systemd:
      units:
  kernelArguments:
  osImageURL:
```

If the desired rendered config includes a bad file, bad systemd unit, invalid kubelet setting, or bad kernel arg, the fix is usually to correct or remove the source MachineConfig/KubeletConfig/ContainerRuntimeConfig, not to manually edit the rendered config.

---

### Phase 6: Find source MachineConfig objects

Rendered configs are generated. Do not edit rendered MachineConfigs directly.

List custom MCs:

```bash
oc get mc | grep -v '^rendered-'
```

Look at labels:

```bash
oc get mc --show-labels
```

A MachineConfig targeted to worker:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

A MachineConfig targeted to infra:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

Find machine configs affecting a pool:

```bash
POOL=infra
oc get mc -l machineconfiguration.openshift.io/role=$POOL
```

Remember custom pools often inherit from worker, so also check:

```bash
oc get mc -l machineconfiguration.openshift.io/role=worker
```

This is very important. A bad worker MachineConfig can also affect custom worker-derived pools like `infra`, `logging`, `monitoring`, `storage`, or `gpu`.

## 8. Root cause category 1: Configuration drift

### 8.1 What is configuration drift?

Configuration drift means the node's actual on-disk state does not match the currently applied MachineConfig.

Examples:

- Someone manually edited `/etc/chrony.conf`
- Someone changed file permissions under `/etc`
- A troubleshooting script modified a managed file
- A systemd drop-in was changed manually
- A third-party operator modified a file owned by MCO
- A node was repaired manually and no longer matches current rendered config

The MCD checks for drift when:

- the node boots
- a managed file or systemd drop-in changes outside MachineConfig
- before a new MachineConfig is applied

If drift is detected, MCO marks the node and MCP degraded.

---

### 8.2 Symptoms

```bash
oc get mcp
```

```text
worker   ... UPDATED=False UPDATING=True DEGRADED=True DEGRADEDMACHINECOUNT=1
```

Node reason:

```bash
oc get node worker-2 -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Possible output:

```text
unexpected on-disk state validating against rendered-worker-xxx: content mismatch for file /etc/chrony.conf
```

---

### 8.3 Confirm file content on node

Use `oc debug`:

```bash
oc debug node/worker-2
chroot /host
```

Then inspect the file:

```bash
ls -l /etc/chrony.conf
sha256sum /etc/chrony.conf
cat /etc/chrony.conf
```

Or run directly:

```bash
oc debug node/worker-2 -- chroot /host cat /etc/chrony.conf
```

---

### 8.4 Compare with MachineConfig expected content

Rendered MachineConfig stores file content often as data URLs/base64.

Example:

```bash
DESIRED=$(oc get node worker-2 -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}')
oc get mc "$DESIRED" -o yaml | less
```

Look under:

```yaml
spec:
  config:
    storage:
      files:
      - path: /etc/chrony.conf
        mode: 420
        contents:
          source: data:text/plain;charset=utf-8;base64,...
```

Decode example:

```bash
oc get mc "$DESIRED" -o jsonpath='{.spec.config.storage.files[?(@.path=="/etc/chrony.conf")].contents.source}' \
| sed 's#data:text/plain;charset=utf-8;base64,##' \
| base64 -d
```

If content differs from node file, you found drift.

---

### 8.5 Fix option A: Restore on-disk file to match MachineConfig

This is usually safest when the MachineConfig is correct and the node was manually changed.

```bash
oc debug node/worker-2
chroot /host
cp -a /etc/chrony.conf /etc/chrony.conf.backup.$(date +%F-%H%M%S)
vi /etc/chrony.conf
chmod 0644 /etc/chrony.conf
exit
exit
```

Then watch:

```bash
oc get mcp worker -w
oc get node worker-2 -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

If MCD does not automatically recover, check logs again.

---

### 8.6 Fix option B: Correct the source MachineConfig

Use this when the MachineConfig is wrong and the node's current manual value is actually the desired value.

Steps:

1. Find the source MC, not the rendered MC.
2. Correct it through GitOps or `oc edit` if emergency.
3. Allow MCO to render a new config.
4. Watch rollout.

```bash
oc get mc --show-labels
oc edit mc 99-worker-chrony
oc get mcp worker -w
```

In mature environments, change the GitOps source and let Argo CD/ACM/ZTP apply the corrected object.

---

### 8.7 Fix option C: Force file

A force file can tell the MCD to bypass usual preflight drift checks and reapply the current MachineConfig.

Path:

```text
/run/machine-config-daemon-force
```

Command:

```bash
oc debug node/worker-2 -- chroot /host touch /run/machine-config-daemon-force
```

Important:

- This can reboot the node.
- Use only after you understand the cause.
- Do not use it blindly to hide real drift.
- Do not apply it to multiple control-plane nodes at once.

Watch:

```bash
oc get mcp worker -w
oc get nodes -w
```

---

## 9. Root cause category 2: Invalid MachineConfig

### 9.1 Typical bad MachineConfig mistakes

Bad MachineConfigs are common in advanced pools.

Examples:

- invalid Ignition version
- malformed base64 data URL
- wrong file path
- unsupported file path
- wrong file mode type
- bad systemd unit syntax
- invalid drop-in name
- invalid kubelet config rendered through KubeletConfig
- kernel argument that prevents boot
- wrong pool label
- conflicting MachineConfigs writing the same file
- worker MC unexpectedly affecting custom pools

---

### 9.2 Identify recently changed MachineConfigs

```bash
oc get mc --sort-by=.metadata.creationTimestamp
```

Show details:

```bash
oc describe mc <machineconfig-name>
oc get mc <machineconfig-name> -o yaml
```

Check who changed it:

```bash
oc get mc <machineconfig-name> -o yaml | grep -A20 managedFields
```

If GitOps is used:

```bash
oc get applications -A | grep -i machine
oc get app -n openshift-gitops
```

---

### 9.3 Validate MachineConfig role label

Wrong:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: workers
```

Correct:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

For custom pool:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

Check:

```bash
oc get mc --show-labels
```

---

### 9.4 Validate file paths

MCO is generally used for supported OS configuration paths such as `/etc` and `/var`.

Good examples:

```text
/etc/chrony.conf
/etc/sysctl.d/99-custom.conf
/etc/systemd/system/example.service.d/10-override.conf
/var/lib/kubelet/config.json
```

Risky or unsupported style examples:

```text
/usr/bin/custom-binary
/boot/custom-file
/random/path/file
```

If you need custom binaries or complex OS layering, evaluate image-based node customization, RPM packaging, or supported operator patterns instead of ad-hoc file injection.

---

### 9.5 Validate file mode

Ignition file mode is decimal integer, not quoted shell-style octal.

For `0644`, use decimal `420`:

```yaml
mode: 420
```

For `0755`, use decimal `493`:

```yaml
mode: 493
```

Bad:

```yaml
mode: "0644"
```

Possibly bad depending on serializer:

```yaml
mode: 0644
```

Safer:

```yaml
mode: 420
```

---

### 9.6 Validate base64 data URL

Example:

```yaml
contents:
  source: data:text/plain;charset=utf-8;base64,c2VydmVyIDEwLjAuMC4xIGlidXJzdAo=
```

Decode:

```bash
echo 'c2VydmVyIDEwLjAuMC4xIGlidXJzdAo=' | base64 -d
```

If decoding fails, MCO/MCD can fail to apply the file.

---

### 9.7 Recovery from bad MachineConfig

If a newly created MC caused the issue:

```bash
oc delete mc <bad-mc>
```

or revert through GitOps.

Then monitor:

```bash
oc get mcp -w
oc get nodes -w
```

If the bad rendered config is already desired on nodes, deleting or fixing the source MC causes the render controller to create a new desired rendered config. MCD should converge nodes to the corrected rendered config.

---

## 10. Root cause category 3: Drain failure

### 10.1 Why drain failures degrade or stall MCP updates

When MCO applies many machine config changes, it needs to:

1. cordon node
2. drain workloads
3. apply config
4. reboot if required
5. uncordon node

If drain fails, the node cannot safely reboot, so the pool can remain stuck updating or degraded.

---

### 10.2 Symptoms

MCP:

```text
UPDATED=False
UPDATING=True
DEGRADED=True or False
```

MCD logs:

```text
failed to drain node
cannot evict pod as it would violate the pod's disruption budget
error when evicting pods
```

Node:

```text
Ready,SchedulingDisabled
```

---

### 10.3 Find pods blocking drain

```bash
NODE=worker-2
oc adm drain "$NODE" --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Check workloads on node:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
```

Check PDBs:

```bash
oc get pdb -A
```

Detailed:

```bash
oc describe pdb -A
```

Look for:

```text
Allowed disruptions: 0
```

---

### 10.4 Fix drain blockers

Common fixes:

- scale application replicas up
- temporarily relax PDB
- fix unhealthy pods so PDB allows eviction
- move singleton workload to another node
- remove local storage dependency if safe
- handle stuck terminating pods
- use maintenance window for critical workloads

Example scale up:


## 14. Root cause category 7: Kernel argument or boot problem

### 14.1 Symptoms

- node does not come back after reboot
- node stuck NotReady
- MCO waits indefinitely
- bare metal console shows boot issue
- custom pool for low-latency, GPU, or storage impacted

### 14.2 Common bad kernel argument scenarios

- GPU-specific kernel argument mismatch

### 14.3 Recovery approach

1. Remove or correct bad source MachineConfig.
2. If node is reachable, allow MCO to reconcile.
3. If node cannot boot, use infrastructure console or rescue workflow.

5. Pause affected pool only if needed to stop further rollout, but do not leave pools paused long-term.

## 15. Root cause category 8: Custom MCP selector and label mistakes

### 15.1 Why this matters in cluster partitioning

Custom MCPs are central to dedicated node pool design. A wrong label or selector can move nodes unexpectedly between pools or leave nodes unmanaged.

Check nodes:

```bash
oc get nodes --show-labels
```

Check MCP selectors:

```bash
oc get mcp <pool> -o yaml
```

---

### 15.2 Correct infra node labeling pattern

A common pattern is dual-labeling infra nodes with worker and infra roles:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
oc label node worker-1 node-role.kubernetes.io/worker=
```

Then create a custom `infra` MCP.

Why keep worker inheritance? Custom worker-derived pools inherit worker MachineConfigs. This is the supported pattern for worker-based custom pools.

---

### 15.3 Dangerous mistake: removing worker role without custom MCP

Bad:

```bash
oc label node worker-1 node-role.kubernetes.io/worker-
oc label node worker-1 node-role.kubernetes.io/infra=
```

If no infra MCP exists, this can leave the node unmanaged by MCO.

Symptoms:

- node not counted in worker MCP
- not counted in infra MCP
- MachineConfig changes not applied
- upgrade inconsistencies

Check:

```bash
oc get mcp
oc get nodes --show-labels
```

---

### 15.4 Dangerous mistake: custom pool overlaps

A node should be managed by only one MCP. Custom pools take priority over worker pool selection when labels match.

If a node has labels for multiple custom pools, you may get unexpected ownership.

Example problem:

```text
node-role.kubernetes.io/infra=
node-role.kubernetes.io/logging=
node-role.kubernetes.io/worker=
```

If both `infra` and `logging` MCPs exist, this design is ambiguous operationally, even if one pool wins selection. Avoid multi-purpose node roles unless intentionally designed.

---

### 15.5 Troubleshoot MCP membership

```bash
for p in $(oc get mcp -o name | cut -d/ -f2); do
  echo "=== MCP: $p ==="
  oc get mcp "$p" -o jsonpath='{.spec.nodeSelector}{"\n"}'
  oc get nodes -l "node-role.kubernetes.io/$p" --no-headers 2>/dev/null || true
  echo
 done
```

Better manual checks:

```bash
oc get mcp infra -o yaml
oc get nodes -l node-role.kubernetes.io/infra -o wide
oc get nodes -l node-role.kubernetes.io/worker -o wide
```

## 16. Root cause category 9: Pool paused too long

### 16.1 What `spec.paused` does

If an MCP is paused:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

MCO does not apply new config changes to that pool until it is unpaused.

This is useful for:

- canary rollout
- emergency stop
- maintenance window control
- preventing a bad config from continuing to additional nodes

But it is dangerous if forgotten.

---

### 16.2 Check paused pools

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status,UPDATING:.status.conditions[?(@.type=="Updating")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status
```

or:

```bash
oc get mcp -o json | jq -r '.items[] | [.metadata.name, (.spec.paused // false)] | @tsv'
```

---

### 16.3 Why long paused pools are risky

If a pool remains paused:

- node config changes do not apply
- upgrade may stall
- certificate rotation changes might not reach nodes
- kubelet client/server compatibility can diverge
- custom pools become inconsistent with worker baseline

Use paused pools only for short, controlled windows.

Unpause:

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
```

## 21. Dedicated pool troubleshooting scenarios

### Scenario 1: Infra MCP degraded after chrony MachineConfig

Symptoms:

```bash
oc get mcp infra
```

```text
infra   rendered-infra-aaa   False   True   True   3   2   2   1
```

Reason:

```text
content mismatch for file /etc/chrony.conf
```

Likely causes:

- infra node was manually modified
- `99-infra-chrony` content differs from actual disk file
- worker chrony config conflicts with infra chrony config

Troubleshooting:

```bash
oc get mc -l machineconfiguration.openshift.io/role=infra
oc get mc -l machineconfiguration.openshift.io/role=worker
oc describe mcp infra
oc get node <infra-node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --tail=300
```

Fix:

- correct source MC if wrong
- restore file if node drifted
- force file only if required and understood

---

### Scenario 2: Logging MCP degraded because drain blocked by PDB

Symptoms:

```text
failed to drain node logging-1: cannot evict pod because it would violate PDB
```

Common in logging pools because log storage or collectors may run with strict disruption budgets.

Check:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=logging-1
oc get pdb -A
oc describe pdb -n openshift-logging <pdb-name>
```

Fix:

- ensure enough replicas
- restore unhealthy pods
- temporarily relax PDB during maintenance
- update one node at a time
- ensure logging storage quorum before drain

---

### Scenario 3: GPU MCP degraded after kernel update

Symptoms:

- GPU workloads fail
- NVIDIA driver pod crashloops
- node reboots but GPU plugin not healthy
- MCP update stuck

Checks:

```bash
oc get mcp gpu
oc get pods -n nvidia-gpu-operator -o wide 2>/dev/null || true
oc debug node/<gpu-node> -- chroot /host uname -r
oc debug node/<gpu-node> -- chroot /host journalctl -u kubelet -b --no-pager | tail -200
```

Likely causes:

- kernel/driver mismatch
- GPU operator DaemonSet not tolerating node taint
- bad kernel argument
- custom MC applied to wrong GPU pool

Fix:

- verify GPU Operator compatibility
- correct kernel args
- stop rollout if multiple GPU nodes are at risk
- restore pool consistency

---

### Scenario 4: Storage MCP degraded because node cannot drain

Symptoms:

- ODF/Ceph pods on node
- PDB blocks drain
- storage pool update stuck

Checks:

```bash
oc get pods -n openshift-storage -o wide
oc get pdb -n openshift-storage
oc describe mcp storage
```

Fix mindset:

- never force-drain storage nodes without understanding quorum and data placement
- verify Ceph health first
- update one storage node at a time
- respect PDB unless an emergency recovery process is approved

---

### Scenario 5: Monitoring MCP degraded because worker MC affected it

Symptoms:

- You changed `99-worker-sysctl`
- `worker`, `infra`, and `monitoring` MCPs all start updating
- monitoring MCP degrades

Reason:

Custom worker-derived pools inherit worker MachineConfigs. A worker-level MC can affect all custom pools.

Check:

```bash
oc get mc -l machineconfiguration.openshift.io/role=worker
oc get mcp
```

Fix:

- do not put specialized tuning into generic worker MC
- move workload-specific tuning into custom pool MC
- keep worker baseline minimal

## 22. Senior-level decision tree

### 22.1 Is MCP degraded during an upgrade?

```bash
oc get clusterversion
oc get co machine-config
oc get mcp
```

If yes:

- do not start additional MachineConfig changes
- identify blocking pool
- identify degraded node
- inspect MCD logs
- fix root cause
- let upgrade continue

---

### 22.2 Is only one node degraded?

Likely:

- node-specific drift
- disk issue
- kubelet/CRI-O issue
- hardware/network issue
- manual file edit

Focus on node logs and on-disk state.

---

### 22.3 Are all nodes in a pool degraded?

Likely:

- bad MachineConfig
- bad KubeletConfig
- bad ContainerRuntimeConfig
- bad pool-level config
- bad worker baseline affecting custom pool

Focus on recent config changes.

---

### 22.4 Are multiple custom pools degraded after one change?

Likely:

- bad worker MachineConfig inherited by custom pools
- cluster update OS image issue
- registry/proxy/CA issue
- common operator-generated MC

Check worker-level MCs and cluster-wide config.

---

### 22.5 Is the node stuck `SchedulingDisabled`?

Check:

```bash
oc describe node <node>
oc get pods -A -o wide --field-selector spec.nodeName=<node>
oc get pdb -A
```

If MCO is still reconciling, do not manually uncordon unless you know MCO is done or stuck due to an unrelated status issue.

---

### 22.6 Is the source config bad or node disk bad?

Ask:

- Does desired rendered config contain the bad setting?
- Does only one node differ from rendered config?
- Did someone manually edit the node?
- Did GitOps recently change MC/KubeletConfig?
- Are MCD logs complaining about content mismatch or apply failure?

If source config is bad, fix source object.  
If node disk is bad, fix node drift.

### Step 5: Classify root cause

| Evidence | Likely root cause |
|---|---|

| one node fails | node-specific drift or host issue |

| pool paused | rollout intentionally blocked or forgotten pause |

- Source config bad: fix/delete MachineConfig, KubeletConfig, ContainerRuntimeConfig, Image config, or GitOps source.
- Node drifted: restore file content/mode to match MC.
- Drain blocked: fix PDB/workload availability.
- Node unhealthy: repair kubelet/CRI-O/disk/network.

Search for systemd unit:

```bash
for mc in $(oc get mc -o name); do
  echo "=== $mc ==="
  oc get "$mc" -o yaml | grep -n "myservice" || true
 done
```

Search for kernel args:

```bash
for mc in $(oc get mc -o name); do
  echo "=== $mc ==="
  oc get "$mc" -o yaml | grep -n "kernelArguments" -A20 || true
 done
```

## 26. Advanced: pool inheritance and override behavior

Custom worker-derived MCPs inherit worker MachineConfigs. This is useful but dangerous.

Example:

```text
worker MC: 99-worker-sysctl
infra MC:  99-infra-router-tuning
```

The infra rendered config includes worker baseline plus infra-specific changes.

If both define the same file path, OpenShift version behavior and render order matter. In modern OpenShift versions, custom pool-targeted MachineConfigs override worker MachineConfigs when they define the same fields. Still, relying on conflicts is poor design.

Best practice:

- keep worker MC generic
- keep infra/logging/monitoring/storage/GPU tuning pool-specific
- use clear naming prefixes
- avoid multiple MCs managing the same file
- document owner and rollback plan

Naming examples:

```text
99-worker-baseline-sysctl
99-infra-router-somaxconn
99-logging-vm-max-map-count
99-monitoring-prometheus-sysctl
99-storage-multipath
99-gpu-nvidia-kargs
```

## 27. Advanced: degraded MCP during cluster upgrade

During OpenShift upgrades, the MCO updates nodes based on each pool's `maxUnavailable`. By default this is commonly `1`, meaning one node per pool at a time.

A degraded MCP can block the cluster upgrade.

### 27.1 Check upgrade status

```bash
oc get clusterversion
oc describe clusterversion
oc get co
oc get mcp
```

Look for messages like:

```text
Unable to apply update: the cluster operator machine-config is degraded
```

or:

```text
pool worker is not ready
```

---

### 27.2 Upgrade-specific priorities

1. Do not introduce new MachineConfigs.
2. Do not delete random rendered configs.
3. Find exact degraded node and reason.
4. Fix the failing node/pool.
5. Let CVO/MCO continue.
6. If multiple pools are degraded, handle control plane first, then infra/storage, then workers, depending on impact.

---

### 27.3 `maxUnavailable` caution

Do not increase control plane `maxUnavailable` to speed up recovery.

Bad idea:

```bash
oc patch mcp master --type=merge -p '{"spec":{"maxUnavailable":3}}'
```

Why dangerous:

- can drain/reboot too many control-plane nodes
- can affect etcd quorum
- can reduce API availability
- can convert a recoverable MCP issue into a platform outage

For worker/custom pools, raising `maxUnavailable` should also be deliberate and based on workload capacity.

## 28. Advanced: when to replace a node instead of repairing

For immutable infrastructure, replacing a broken worker node is often better than spending hours repairing manual drift.

Consider replacement when:

- node is a worker managed by Machine API
- only one node is affected
- workloads are redundant
- node has unknown manual changes
- disk corruption or OS pivot failed badly
- direct recovery would be riskier than replacement

Do not casually replace:

- control plane nodes
- storage nodes with local data
- bare-metal nodes without capacity planning
- GPU nodes with scarce hardware
- nodes running singleton stateful workloads

Replacement mindset:

```text
If the node is cattle, replace it.
If the node is special, diagnose carefully.
```

## 29. Advanced: what not to do

Avoid these mistakes:

```bash
# Do not randomly delete rendered MachineConfigs
oc delete mc rendered-worker-xxxxx

# Do not randomly remove finalizers from MCP/MC/node objects
oc patch ... finalizers ...

# Do not patch currentConfig just to make status green
oc patch node <node> ... currentConfig=desiredConfig

# Do not reboot all masters together
for n in $(oc get nodes -l node-role.kubernetes.io/master -o name); do ... reboot ...; done

# Do not leave MCP paused for days/weeks
oc patch mcp worker -p '{"spec":{"paused":true}}'

# Do not manually edit MCO-managed files as permanent solution
vi /etc/chrony.conf
```

Use emergency actions only with clear rollback and impact understanding.

## 30. Preventing MCP degradation in dedicated node pool design

### 30.1 Use GitOps for MachineConfigs

Every MachineConfig should have:

- owner
- purpose
- target pool
- change ticket
- rollback plan
- test evidence

Recommended Git layout:

```text
clusters/
  prod/
    machine-configs/
      worker/
      infra/
      logging/
      monitoring/
      storage/
      gpu/
```

---

### 30.2 Use canary pools

Before applying a risky MachineConfig to all workers, create a small canary custom MCP.

Example:

```text
worker-canary: 1 node
worker: rest of workers
```

Test:

- node drains
- reboots
- kubelet returns
- workloads schedule
- MCD state returns to Done
- MCP returns Updated=True

Then roll out broadly.

---

### 30.3 Separate baseline and workload-specific configs

Bad:

```text
99-worker-all-tuning
```

This often becomes a dumping ground.

Better:

```text
99-worker-baseline-time
99-worker-baseline-registry
99-infra-router-tuning
99-logging-vm-max-map-count
99-gpu-driver-kargs
```

---

### 30.4 Avoid manual node changes

If you must test manually, immediately convert the change into MachineConfig or revert it.

Manual edits create hidden drift. Hidden drift becomes a future upgrade outage.

---

### 30.5 Validate before applying

For MachineConfigs:

```bash
oc apply --dry-run=server -f mc.yaml
```

For YAML syntax:

```bash
yamllint mc.yaml
```

For base64:

```bash
echo '<base64>' | base64 -d
```

For systemd unit syntax, test in a similar RHEL/RHCOS lab node when possible.

---

### 30.6 Respect PDB and workload HA

MCO updates depend on draining nodes. Dedicated pool design must include enough capacity for drain.

For each pool ask:

- Can one node be unavailable?
- Are PDBs allowing one disruption?
- Are workloads spread across zones/nodes?
- Are replicas greater than one?
- Are storage quorum rules respected?

## 31. Interview-level explanation

If asked in an interview:

> How do you troubleshoot a degraded MCP in OpenShift?

Answer:

```text
First I check the machine-config cluster operator and MCP status using oc get co machine-config and oc get mcp. Then I describe the degraded pool to read the Degraded condition message. After that, I identify the exact node by checking machineconfiguration.openshift.io annotations such as currentConfig, desiredConfig, state, and reason. I locate the machine-config-daemon pod running on that node and inspect its logs.

I classify the issue as configuration drift, invalid MachineConfig, drain/PDB failure, node health issue, kubelet/CRI-O problem, OS pivot issue, paused pool, or custom pool selector problem. If it is drift, I compare the managed file in the rendered MachineConfig with the file on disk and either restore the file or fix the source MachineConfig. If the source config is bad, I fix or remove the source MC/KubeletConfig/ContainerRuntimeConfig and let the MCO render a corrected config. If drain is blocked, I fix PDB or workload availability. I avoid directly patching node annotations unless doing a controlled recovery. Finally I watch the MCP until Updated=True, Updating=False, Degraded=False, and all nodes have currentConfig equal to desiredConfig with state Done.
```

## 33. Full practical lab: simulate and fix configuration drift

> Use only in a lab cluster.

### 33.1 Create a test worker MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-lab-mcp-drift
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/mcp-drift-lab.conf
        mode: 420
        contents:
          source: data:text/plain;charset=utf-8;base64,bGFiX3ZhbHVlPXRydWUK
```

Apply:

```bash
oc apply -f 99-worker-lab-mcp-drift.yaml
oc get mcp worker -w
```

Verify file:

```bash
oc debug node/<worker-node> -- chroot /host cat /etc/mcp-drift-lab.conf
```

Expected:

```text
lab_value=true
```

---

### 33.2 Create drift manually

```bash
oc debug node/<worker-node>
chroot /host
cp -a /etc/mcp-drift-lab.conf /etc/mcp-drift-lab.conf.bak
echo 'lab_value=false' > /etc/mcp-drift-lab.conf
exit
exit
```

Watch:

```bash
oc get mcp worker
oc get node <worker-node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

You should see degraded status or drift reason.

---

### 33.3 Fix drift

```bash
oc debug node/<worker-node>
chroot /host
echo 'lab_value=true' > /etc/mcp-drift-lab.conf
chmod 0644 /etc/mcp-drift-lab.conf
exit
exit
```

Watch recovery:

```bash
oc get mcp worker -w
```

---

### 33.4 Clean up

```bash
oc delete mc 99-worker-lab-mcp-drift
oc get mcp worker -w
```

## 34. Troubleshooting examples by message

### Message: `content mismatch for file /etc/chrony.conf`

Meaning:

- node file differs from rendered MachineConfig

Action:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get mc <desired> -o yaml | grep -n "/etc/chrony.conf" -A20
oc debug node/<node> -- chroot /host cat /etc/chrony.conf
```

Fix:

- restore node file or fix source MC

---

### Message: `failed to drain node`

Meaning:

- MCO cannot evict pods

Action:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node>
oc get pdb -A
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Fix:

- resolve PDB/workload HA blocker

---

### Message: `error running rpm-ostree rebase`

Meaning:

- OS image update/pivot problem

Action:

```bash
oc debug node/<node> -- chroot /host rpm-ostree status
oc debug node/<node> -- chroot /host journalctl -u rpm-ostreed -b --no-pager | tail -300
```

Fix:

- registry/proxy/pull secret/disk/network/OS image issue

---

### Message: `kubelet health failure`

Meaning:

- kubelet did not become healthy after config change

Action:

```bash
oc debug node/<node> -- chroot /host systemctl status kubelet
oc debug node/<node> -- chroot /host journalctl -u kubelet -b --no-pager | tail -300
oc get kubeletconfig
```

Fix:

- correct kubelet config or node issue

---

### Message: `pool is paused`

Meaning:

- MCO will not apply config changes to that pool

Action:

```bash
oc get mcp <pool> -o jsonpath='{.spec.paused}{"\n"}'
```

Fix:

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
```

Only unpause after verifying the config is safe.

## 36. Key takeaways

- MCP degraded means MCO cannot safely reconcile one or more nodes in a pool.
- A degraded node can still be online, but it cannot be updated until fixed.
- In dedicated node pools, worker MachineConfigs may also affect custom pools.
- Always identify the node, current config, desired config, state, and reason.
- MCD logs are the most important evidence source.
- Most issues fall into drift, bad config, drain failure, node health, runtime/kubelet failure, OS pivot failure, paused pool, or selector mistakes.
- Fix source-of-truth first; do not hide problems by patching annotations.
- Use force file carefully and expect reboot.
- Control plane MCP recovery requires extra caution.
- Good pool design, GitOps, canary rollout, and PDB-aware workload placement prevent most MCP degradation incidents.
