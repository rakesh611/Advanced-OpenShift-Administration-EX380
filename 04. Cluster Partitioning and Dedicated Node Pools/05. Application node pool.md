# Application Node Pool in OpenShift

**Topic:** Cluster Partitioning and Dedicated Node Pools  
**Audience:** Advanced OpenShift Administration / 10+ years Linux, Kubernetes, DevOps experience  
**Focus:** Designing, creating, operating, and troubleshooting an **application node pool** in OpenShift Container Platform

---

## 1. What is an Application Node Pool?

An **application node pool** is a dedicated group of OpenShift worker nodes intended primarily for business/user application workloads. It is not a single OpenShift object by itself in a normal standalone OpenShift cluster. It is a **cluster design pattern** built by combining several OpenShift and Kubernetes mechanisms:

- Compute capacity, usually from **MachineSet** or manually provisioned worker nodes
- Node role labels such as `node-role.kubernetes.io/app: ""`
- A custom **MachineConfigPool** such as `app`
- Optional node taints such as `dedicated=app:NoSchedule`
- Workload placement rules such as `nodeSelector`, node affinity, namespace node selectors, tolerations, topology spread constraints, and pod anti-affinity
- Day-2 operations such as drain behavior, upgrades, capacity planning, monitoring, autoscaling, and failure-domain design

In simple words:

> An application node pool is a controlled area of worker capacity where normal application pods should run, isolated from infrastructure, logging, monitoring, storage, GPU, test, or special-purpose workloads.

This pattern is very important in large OpenShift environments because the default `worker` pool often becomes too broad. In a small cluster, all user workloads may run on generic worker nodes. In an enterprise cluster, administrators usually split workers into pools such as:

```text
master / control-plane   -> API server, scheduler, controller-manager, etcd
infra                    -> router, registry, monitoring/logging components if moved there
app                      -> business/user applications
storage                  -> ODF/Ceph/storage daemons
gpu                      -> AI/ML workloads
perf                     -> low-latency or tuned workloads
edge                     -> edge workloads
batch                    -> CI/CD, jobs, reporting, build workloads
```

The **application node pool** is generally the default landing zone for normal application teams.

---

## 2. Why Application Node Pools Matter

Without application node pools, every worker node can become a mixed workload area. That creates operational problems:

- Application pods compete with routers, registry, logging, monitoring, storage daemons, and build workloads.
- Maintenance is harder because all workers may have the same reboot/update behavior.
- Capacity planning becomes unclear: you cannot easily say how much CPU/memory is reserved for applications.
- Application teams may accidentally consume capacity meant for infrastructure.
- A noisy application can impact platform components if infra workloads are not separated.
- Different workload classes cannot receive different kubelet, CRI-O, OS, runtime, or update policies.

A dedicated application node pool gives you:

- **Isolation:** user applications are separated from platform and special-purpose workloads.
- **Predictable capacity:** application teams know available capacity.
- **Controlled scheduling:** only intended pods land on application nodes.
- **Better upgrades:** pool-specific rollout and validation is easier.
- **Governance:** quota, limit range, namespace selectors, and RBAC align with workload placement.
- **Operational clarity:** troubleshooting becomes faster because node purpose is obvious.
- **Scalability:** the pool can scale independently from infra/storage/GPU pools.

## 3. Important Terminology

| Term | Meaning |
|---|---|
| **Node** | A RHCOS/RHEL machine registered in OpenShift as a Kubernetes node. |
| **Worker node** | Node that runs user or platform workloads. |
| **Application node** | Worker node dedicated or preferred for application workloads. |
| **MachineSet** | Machine API object that creates and manages a set of Machines on supported platforms. Similar idea to an autoscaling group template. |
| **Machine** | OpenShift object representing a host/VM managed by Machine API. |
| **MachineConfig** | Defines host-level configuration for nodes, such as files, systemd units, kubelet-related configuration, CRI-O-related configuration, kernel args, and so on. |
| **MachineConfigPool (MCP)** | Groups nodes and MachineConfigs. The MCO applies rendered config to nodes in that pool. |
| **Machine Config Operator (MCO)** | Operator that manages node OS/config lifecycle through MachineConfigs and MCPs. |
| **Node role label** | Label such as `node-role.kubernetes.io/worker`, `node-role.kubernetes.io/infra`, or `node-role.kubernetes.io/app`. It gives a node an operational role. |
| **Taint** | Rule on a node that repels pods unless they have a matching toleration. |
| **Toleration** | Rule in a pod/project that allows scheduling onto tainted nodes. |
| **Node selector** | Simple key/value scheduler rule requiring a pod to run on nodes with matching labels. |
| **Node affinity** | More expressive placement rule than node selector. Supports `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, and `Lt`. |
| **Topology spread constraint** | Scheduler rule to spread pods across topology domains such as hostname, zone, or rack. |
| **PodDisruptionBudget (PDB)** | Limits voluntary disruptions so application replicas remain available during drains/upgrades. |

## 4. Application Node Pool vs Worker Pool vs Infra Pool

### Default worker pool

The default `worker` MCP exists after installation. In a small cluster, application pods normally run there.

### Application pool

An `app` pool is a custom worker-derived pool used for normal user applications. It usually still has the `worker` node role label, plus an additional role label such as `node-role.kubernetes.io/app: ""`.

### Infra pool

An infra pool is for platform infrastructure components such as ingress/router, registry, monitoring, and logging, depending on your architecture. Infra pool design is usually more restrictive because application workloads should not land there.

### Key difference

| Pool | Primary purpose | Typical scheduling policy |
|---|---|---|
| `worker` | Generic compute | Open to normal workloads unless constrained |
| `app` | Business applications | App workloads selected/preferred here |
| `infra` | Platform components | Tainted to keep user apps away |
| `storage` | ODF/Ceph/storage workloads | Strong taints/labels, storage-specific sizing |
| `gpu` | AI/ML workloads | Tainted and selected by GPU workloads |
| `batch` | Jobs/CI/reporting | May use high overcommit and autoscaling |

## 5. Mental Model: Four Layers of an Application Node Pool

Think of an application node pool as four separate layers. Many admins confuse these layers, which causes scheduling and MCP issues.

```text
Layer 1: Infrastructure capacity
         MachineSet / bare-metal host / VM / cloud instance

Layer 2: Node identity
         Labels and taints on the node

Layer 3: Node configuration lifecycle
         MachineConfigPool, MachineConfig, KubeletConfig, ContainerRuntimeConfig

Layer 4: Workload scheduling
         nodeSelector, affinity, toleration, namespace selector, topology spread, PDB
```

A pool is not truly ready until all four layers are aligned.

Example:

- You created nodes but forgot labels: workloads cannot select them.
- You labeled nodes but forgot MCP: MCO may still treat them as generic workers or may not manage them as expected.
- You tainted nodes but forgot tolerations: application pods remain `Pending`.
- You created a project node selector but deployment uses conflicting nodeSelector: pods are rejected or unschedulable.
- You changed MachineSet labels but existing Machines/nodes did not receive labels: only future nodes may be affected.

## 6. Common Use Cases

Use an application node pool when you need:

### 6.1 Production application isolation

Separate production applications from platform services and non-production workloads.

```text
prod-app pool     -> customer-facing workloads
nonprod-app pool  -> dev/test workloads
infra pool        -> routers/registry/monitoring/logging
```

### 6.2 Team-based isolation

Large organizations may create pools by business domain:

```text
app-payments
app-retail
app-data
app-shared
```

This is useful when different teams have different budgets, SLAs, or maintenance windows.

### 6.3 Hardware-based application pools

Some applications need special node properties:

- High memory nodes
- High CPU nodes
- Local NVMe nodes
- GPU nodes
- Low-latency tuned nodes
- Nodes in a specific zone or rack

Example labels:

```text
node-role.kubernetes.io/app=
workload.openshift.io/class=app
hardware-profile=memory-optimized
topology.kubernetes.io/zone=ap-south-1a
```

### 6.4 Compliance and security segmentation

Applications with strict compliance may run on a controlled node pool:

```text
compliance=regulated
pci=true
data-classification=restricted
```

Do not rely only on labels for security boundaries. Labels are scheduling controls, not full security isolation. Combine them with RBAC, SCC/Pod Security Admission controls, NetworkPolicy, egress controls, image policy, secrets management, audit, and monitoring.

### 6.5 Upgrade canary pools

A custom app MCP can be used to validate upgrades on a subset of application nodes before the rest of application capacity is updated.

Example:

```text
app-canary -> 2 nodes, receives update first
app        -> main application capacity
```

## 7. Recommended Labeling Strategy

A clean labeling strategy is critical. Avoid random labels that nobody understands later.

### 7.1 Role label

Use a node role label to show the role in `oc get nodes`:

```bash
oc label node <node-name> node-role.kubernetes.io/app=
```

Output becomes easier to read:

```bash
oc get nodes
```

Example:

```text
NAME        STATUS   ROLES          AGE   VERSION
worker-1    Ready    worker,app     20d   v1.xx.x
worker-2    Ready    worker,app     20d   v1.xx.x
infra-1     Ready    worker,infra   20d   v1.xx.x
```

### 7.2 Scheduling label

Use a stable business label for scheduling. Do not schedule only on `node-role.kubernetes.io/app` if you expect more granular placement later.

Recommended:

```bash
oc label node <node-name> workload.openshift.io/type=app
oc label node <node-name> env=prod
```

Example scheduling label set:

```text
node-role.kubernetes.io/app=
workload.openshift.io/type=app
env=prod
node-pool=app-prod
```

### 7.3 Topology labels

OpenShift/Kubernetes usually provides topology labels such as:

```text
topology.kubernetes.io/region
topology.kubernetes.io/zone
kubernetes.io/hostname
```

Use them for spreading replicas across nodes/zones.

### 7.4 Avoid labels that are too generic

Avoid labels like:

```text
type=app
role=app
pool=app
```

They can conflict with other tooling or become ambiguous. Prefer domain-style labels:

```text
workload.openshift.io/type=app
platform.example.com/node-pool=app-prod
```

## 8. Should You Keep the `worker` Label?

Usually, yes.

For custom worker-derived pools, the node commonly keeps:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/app=
```

The custom MCP selects the `app` label and the machine config selector inherits worker configuration. This is important because custom MCPs are expected to inherit from the worker pool.

Do **not** remove the `worker` label casually. If a node is removed from the worker role and not properly selected by another MCP, it can become unmanaged by the MCO. That means cluster upgrades and machine config changes can behave incorrectly.

Senior rule:

> Add a custom role label first, create/verify the matching custom MCP, then move workloads. Do not strip labels blindly.

## 9. Reference Architecture

Example production cluster partitioning:

```text
Control plane:
  3 master/control-plane nodes

Infra:
  3 infra nodes across 3 zones
  Runs ingress, registry, monitoring/logging as designed

Application:
  6 app nodes across 3 zones
  Runs business application namespaces

Storage:
  3 storage nodes across 3 zones
  Runs OpenShift Data Foundation / Ceph
```

Application node pool design:

```text
MCP: app
Node role label: node-role.kubernetes.io/app=
Scheduling label: workload.openshift.io/type=app
Optional taint: dedicated=app:NoSchedule
Namespace annotation: openshift.io/node-selector=workload.openshift.io/type=app
Default toleration: scheduler.alpha.kubernetes.io/defaultTolerations
Topology spread: topology.kubernetes.io/zone and kubernetes.io/hostname
PDB: protect app availability during drains
ResourceQuota/LimitRange: prevent noisy neighbors
```

## 10. Implementation Workflow

High-level production workflow:

1. Decide node pool purpose, size, zones, hardware, and maintenance policy.
2. Create or clone MachineSets for app nodes, or prepare bare-metal/VM nodes.
3. Add node labels and optional taints.
4. Create a custom `app` MachineConfigPool.
5. Add optional app-specific MachineConfig/KubeletConfig/ContainerRuntimeConfig.
6. Configure namespace/project-level node selectors and tolerations.
7. Configure application deployments with nodeSelector/affinity/topology spread/PDB.
8. Validate scheduling, MCP health, upgrade behavior, and drain behavior.
9. Add monitoring, alerts, capacity dashboards, and runbooks.

## 11. Create an Application Node Pool from Existing Worker Nodes

This is common in labs and smaller environments.

### 11.1 Choose nodes

```bash
oc get nodes -L node-role.kubernetes.io/worker,topology.kubernetes.io/zone
```

Pick nodes that have enough free capacity and ideally exist across zones.

### 11.2 Label nodes

```bash
oc label node worker-1 node-role.kubernetes.io/app=
oc label node worker-1 workload.openshift.io/type=app
oc label node worker-1 node-pool=app-prod

oc label node worker-2 node-role.kubernetes.io/app=
oc label node worker-2 workload.openshift.io/type=app
oc label node worker-2 node-pool=app-prod

oc label node worker-3 node-role.kubernetes.io/app=
oc label node worker-3 workload.openshift.io/type=app
oc label node worker-3 node-pool=app-prod
```

Verify:

```bash
oc get nodes -l node-role.kubernetes.io/app
oc get nodes -l workload.openshift.io/type=app
oc get nodes --show-labels | grep app
```

### 11.3 Create custom MachineConfigPool

Create `mcp-app.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: app
  labels:
    pools.operator.machineconfiguration.openshift.io/app: ""
spec:
  maxUnavailable: 1
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - app
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/app: ""
```

Apply:

```bash
oc apply -f mcp-app.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp app
oc get nodes -l node-role.kubernetes.io/app
```

Expected:

```text
NAME     CONFIG             UPDATED   UPDATING   DEGRADED   MACHINECOUNT
app      rendered-app-...    True      False      False      3
worker   rendered-worker...  True      False      False      N
```

### 11.4 Why `machineConfigSelector` includes `worker` and `app`

The `app` pool should inherit worker machine configs and also allow app-specific machine configs.

- `worker` machine configs apply common worker baseline.
- `app` machine configs apply only to app nodes.
- If both define the same fields, app-specific config should be treated carefully because it can override worker-intended settings.

## 12. Create Application Nodes Using MachineSet

On supported platforms such as AWS, Azure, GCP, vSphere, OpenStack, and others, OpenShift Machine API can manage worker nodes. You can create a dedicated MachineSet for app nodes.

### 12.1 Get existing MachineSets

```bash
oc get machinesets -n openshift-machine-api
```

Example:

```text
cluster-abc-worker-ap-south-1a   2   2   2
cluster-abc-worker-ap-south-1b   2   2   2
cluster-abc-worker-ap-south-1c   2   2   2
```

### 12.2 Export an existing MachineSet as a template

```bash
oc get machineset <existing-worker-machineset> \
  -n openshift-machine-api -o yaml > app-machineset.yaml
```

Edit:

- `metadata.name`
- `spec.selector.matchLabels.machine.openshift.io/cluster-api-machineset`
- `spec.template.metadata.labels.machine.openshift.io/cluster-api-machineset`
- desired replicas
- instance type / flavor if needed
- zone / failure domain if needed
- node labels under `spec.template.spec.metadata.labels`
- taints under `spec.template.spec.taints` if needed

### 12.3 Generic MachineSet label example

Exact provider fields differ by platform, but the node label concept is similar:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: <cluster-id>-app-<zone>
  namespace: openshift-machine-api
spec:
  replicas: 2
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-cluster: <cluster-id>
      machine.openshift.io/cluster-api-machineset: <cluster-id>-app-<zone>
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-cluster: <cluster-id>
        machine.openshift.io/cluster-api-machineset: <cluster-id>-app-<zone>
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/worker: ""
          node-role.kubernetes.io/app: ""
          workload.openshift.io/type: app
          node-pool: app-prod
      taints:
        - key: dedicated
          value: app
          effect: NoSchedule
      providerSpec:
        value:
          # provider-specific configuration here
```

Apply:

```bash
oc apply -f app-machineset.yaml
```

Verify:

```bash
oc get machines -n openshift-machine-api
oc get nodes -l node-role.kubernetes.io/app
oc get mcp app
```

### 12.4 Important MachineSet label behavior

If you edit a MachineSet and add labels later, those labels generally affect new Machines/nodes created from that point onward. Existing Machines/nodes might not automatically receive the new labels. For existing nodes, label them directly or recreate/roll the MachineSet carefully.

Production approach:

1. Create/modify MachineSet template.
2. Scale up new app nodes.
3. Verify labels, taints, and MCP membership.
4. Move workloads gradually.
5. Scale down old generic workers if required.

## 13. Bare Metal or Manually Managed Nodes

In UPI/bare-metal environments, you might not have MachineSets for every node lifecycle task. You still create application node pools by labeling nodes and creating MCPs.

Example:

```bash
oc label node bm-worker-01 node-role.kubernetes.io/app=
oc label node bm-worker-01 workload.openshift.io/type=app
oc label node bm-worker-01 rack=rack-1

oc label node bm-worker-02 node-role.kubernetes.io/app=
oc label node bm-worker-02 workload.openshift.io/type=app
oc label node bm-worker-02 rack=rack-2
```

Then create the `app` MCP as shown earlier.

In bare-metal environments, extra care is needed for:

- BIOS/firmware consistency
- NUMA topology
- NIC bonding/VLANs
- Storage multipath
- MTU consistency
- Kernel arguments
- Time synchronization
- Capacity replacement process
- Manual labeling after reinstall/replacement

## 14. Taints and Tolerations for Application Node Pools

### 14.1 When to taint app nodes

Taint application nodes if you want to prevent random workloads from landing there.

Example:

```bash
oc adm taint nodes -l node-role.kubernetes.io/app dedicated=app:NoSchedule
```

This means only pods with a matching toleration can schedule there.

### 14.2 Toleration in a deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: prod-apps
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      nodeSelector:
        workload.openshift.io/type: app
      tolerations:
        - key: dedicated
          operator: Equal
          value: app
          effect: NoSchedule
      containers:
        - name: frontend
          image: registry.access.redhat.com/ubi9/nginx-120
          resources:
            requests:
              cpu: 200m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 512Mi
```

### 14.3 Toleration only is not enough

A toleration allows a pod to land on tainted nodes, but it does **not** force it to land there.

To dedicate nodes properly, combine:

```text
Taint on node        -> keeps other pods away
Toleration on pod    -> allows intended pods in
Node selector/affinity on pod -> forces intended pods to use those nodes
```

Senior rule:

> Taint controls who is allowed in. Node selector/affinity controls where the allowed pod must go.

## 15. Namespace-Level Placement for App Teams

For application teams, it is often better to enforce placement at namespace/project level instead of asking every developer to add selectors and tolerations manually.

### 15.1 Project with node selector and default toleration

Create `project-prod-apps.yaml`:

```yaml
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: prod-apps
  annotations:
    openshift.io/node-selector: "workload.openshift.io/type=app"
    scheduler.alpha.kubernetes.io/defaultTolerations: >-
      [{"key":"dedicated","operator":"Equal","value":"app","effect":"NoSchedule"}]
```

Apply:

```bash
oc apply -f project-prod-apps.yaml
```

Any new pods in this project get the project selector behavior and can tolerate the app taint.

### 15.2 Add selector to an existing namespace

```bash
oc annotate namespace prod-apps \
  openshift.io/node-selector='workload.openshift.io/type=app' \
  --overwrite
```

Add default toleration:

```bash
oc annotate namespace prod-apps \
  scheduler.alpha.kubernetes.io/defaultTolerations='[{"key":"dedicated","operator":"Equal","value":"app","effect":"NoSchedule"}]' \
  --overwrite
```

### 15.3 Important conflict rule

If a namespace has a project node selector and a pod has a conflicting nodeSelector, the pod might be rejected or remain unscheduled.

Example namespace selector:

```text
workload.openshift.io/type=app
```

Conflicting pod selector:

```yaml
nodeSelector:
  workload.openshift.io/type: infra
```

This is invalid for that project design.

## 16. Workload Placement Patterns

### 16.1 Simple nodeSelector

Use when the rule is simple and strict.

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/type: app
```

Pros:

- Simple
- Easy to troubleshoot
- Good for exam/lab use

Cons:

- No advanced logic
- No soft preference
- All keys must match exactly

### 16.2 Required node affinity

Use when you need expressive matching.

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: workload.openshift.io/type
                    operator: In
                    values:
                      - app
                  - key: env
                    operator: In
                    values:
                      - prod
```

This means the pod can only run on nodes with both labels:

```text
workload.openshift.io/type=app
env=prod
```

### 16.3 Preferred node affinity

Use when app nodes are preferred but not mandatory.

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              preference:
                matchExpressions:
                  - key: workload.openshift.io/type
                    operator: In
                    values:
                      - app
```

This is useful for soft placement, but not for strict isolation.

### 16.4 Pod anti-affinity for HA

Spread replicas across nodes:

```yaml
spec:
  template:
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: frontend
                topologyKey: kubernetes.io/hostname
```

### 16.5 Topology spread constraints

Recommended for HA across zones/nodes:

```yaml
spec:
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: frontend
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: frontend
```

Use `DoNotSchedule` carefully. If you do not have enough zones/nodes, pods can remain Pending.

## 17. Full Example: Production App Deployment on App Node Pool

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: prod-apps
  labels:
    app: payment-api
spec:
  replicas: 6
  selector:
    matchLabels:
      app: payment-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      nodeSelector:
        workload.openshift.io/type: app
      tolerations:
        - key: dedicated
          operator: Equal
          value: app
          effect: NoSchedule
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payment-api
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: payment-api
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: payment-api
                topologyKey: kubernetes.io/hostname
      containers:
        - name: payment-api
          image: image-registry.openshift-image-registry.svc:5000/prod-apps/payment-api:v1
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
            limits:
              cpu: "2"
              memory: 2Gi
```

PDB:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
  namespace: prod-apps
spec:
  minAvailable: 5
  selector:
    matchLabels:
      app: payment-api
```

Why this is production-grade:

- Runs only on app nodes.
- Tolerates app taint.
- Spreads across zones and nodes.
- Uses readiness/liveness probes.
- Uses resource requests/limits.
- Uses a PDB to protect availability during drains/upgrades.

## 18. App-Specific MachineConfig

Use an app-specific MachineConfig only when needed. MachineConfig changes can cause node drain and reboot, so treat them as production-impacting changes.

Example: create a file on app nodes only.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-app-custom-file
  labels:
    machineconfiguration.openshift.io/role: app
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
        - path: /etc/app-node-pool.conf
          mode: 0644
          contents:
            source: data:text/plain;charset=utf-8;base64,YXBwLW5vZGUtcG9vbD10cnVlCg==
```

Apply:

```bash
oc apply -f 99-app-custom-file.yaml
oc get mcp app -w
```

Validate on node:

```bash
oc debug node/<app-node>
chroot /host cat /etc/app-node-pool.conf
```

### 18.1 MachineConfig naming

MachineConfigs are processed lexicographically by name. Prefixes such as `99-` are commonly used for custom configs. Be careful when two configs write the same file or same settings.

### 18.2 Production warning

Before applying MachineConfig to app nodes:

```bash
oc get mcp app
oc get pdb -A
oc adm top nodes
oc get pods -A -o wide | grep <app-node>
```

Check:

- Is the pool healthy?
- Do apps have enough replicas?
- Are PDBs too strict?
- Is there spare capacity for drained pods?
- Is this change approved for the maintenance window?

## 19. App-Specific KubeletConfig

Use `KubeletConfig` when you need pool-specific kubelet tuning.

Example: set max pods and PID limits for app nodes.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: app-kubelet-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/app: ""
  kubeletConfig:
    maxPods: 250
    podPidsLimit: 4096
    containerLogMaxSize: 50Mi
    containerLogMaxFiles: 5
```

Apply:

```bash
oc apply -f app-kubelet-config.yaml
oc get mcp app -w
```

Production notes:

- Higher `maxPods` increases density but also increases pressure on kubelet, CRI-O, CNI, IP allocation, logging, monitoring, and DNS.
- Tune after measuring real workload behavior.
- Do not copy values blindly from another cluster.
- Validate cluster network capacity and service limits.

## 20. App-Specific ContainerRuntimeConfig

Use `ContainerRuntimeConfig` for CRI-O related settings targeted at an MCP.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: ContainerRuntimeConfig
metadata:
  name: app-crio-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/app: ""
  containerRuntimeConfig:
    pidsLimit: 4096
    logLevel: info
```

Apply:

```bash
oc apply -f app-crio-config.yaml
oc get mcp app -w
```

Important:

- Deleting the CR is usually the correct rollback path.
- Removing labels from the MCP might not revert runtime config in the way you expect.
- Keep CRI-O changes minimal and documented.

## 21. Resource Governance for Application Pools

Application node pools should be combined with namespace-level resource governance.

### 21.1 ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: prod-apps-quota
  namespace: prod-apps
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
    services: "20"
    persistentvolumeclaims: "20"
```

### 21.2 LimitRange

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: prod-apps-limits
  namespace: prod-apps
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      default:
        cpu: "1"
        memory: 512Mi
      min:
        cpu: 10m
        memory: 32Mi
      max:
        cpu: "4"
        memory: 8Gi
```

Why this matters:

- Scheduler uses requests, not limits, for placement.
- Missing requests lead to poor capacity planning.
- Too-high requests create artificial Pending pods.
- Too-low requests create noisy neighbor issues.

## 22. Capacity Planning for Application Node Pools

A senior admin should not create node pools only by node count. Plan with real capacity numbers.

### 22.1 Basic formula

```text
Allocatable app CPU = sum(node allocatable CPU) - reserved headroom
Allocatable app memory = sum(node allocatable memory) - reserved headroom
Required app CPU = sum(pod CPU requests) + surge + failure capacity
Required app memory = sum(pod memory requests) + surge + failure capacity
```

### 22.2 Headroom

Keep headroom for:

- Node drain during MCO updates
- Rolling deployments
- HPA scale-out
- Pod rescheduling after node failure
- DaemonSets
- Log/metrics overhead
- Temporary spikes

Common production starting point:

```text
CPU headroom: 20% to 30%
Memory headroom: 20% to 30%
Failure-domain spare capacity: at least one node or one zone impact, depending on SLA
```

Adjust based on actual workload patterns.

### 22.3 N+1 design

If you have 3 app nodes and one node drains, can the remaining 2 nodes run all critical replicas?

Check:

```bash
oc adm top nodes -l workload.openshift.io/type=app
oc adm top pods -A --sort-by=cpu
oc adm top pods -A --sort-by=memory
```

Review scheduled requests:

```bash
oc describe node <app-node> | egrep -A20 "Allocated resources"
```

### 22.4 Zone design

For production, spread app nodes across zones:

```text
app zone-a: 2 nodes
app zone-b: 2 nodes
app zone-c: 2 nodes
```

Then configure app replicas with topology spread constraints.

## 23. Autoscaling Application Node Pools

If Machine API and autoscaling are available, app node pools can scale independently.

### 23.1 MachineAutoscaler concept

A MachineAutoscaler targets a MachineSet and controls min/max replicas.

Generic example:

```yaml
apiVersion: autoscaling.openshift.io/v1beta1
kind: MachineAutoscaler
metadata:
  name: app-zone-a-autoscaler
  namespace: openshift-machine-api
spec:
  minReplicas: 2
  maxReplicas: 6
  scaleTargetRef:
    apiVersion: machine.openshift.io/v1beta1
    kind: MachineSet
    name: <cluster-id>-app-zone-a
```

### 23.2 ClusterAutoscaler

ClusterAutoscaler must be configured for MachineAutoscalers to work.

Check:

```bash
oc get clusterautoscaler -A
oc get machineautoscaler -n openshift-machine-api
```

### 23.3 Autoscaling gotchas

- If pods have strict topology spread constraints, autoscaler may need capacity in the correct zone.
- Taints and node selectors must match the pending pods.
- Max replicas must allow enough capacity for surge and failure.
- Pod requests must be realistic; autoscaling decisions depend on requests.
- Do not use autoscaling as a substitute for capacity governance.

## 24. Upgrade and Maintenance Strategy

### 24.1 MCO behavior

When a machine config change applies, the MCO usually:

1. Cordons the node.
2. Drains workloads.
3. Applies config.
4. Reboots the node if required.
5. Uncordons the node.

The MCP `maxUnavailable` controls how many nodes in that pool can be unavailable at the same time.

### 24.2 App pool maxUnavailable

For production app pools, start conservatively:

```yaml
spec:
  maxUnavailable: 1
```

Use percentages only when you are confident in capacity and PDB behavior.

### 24.3 Pause an MCP

You can pause a pool during sensitive periods, but do not forget to unpause it.

```bash
oc patch mcp app --type merge -p '{"spec":{"paused":true}}'
```

Unpause:

```bash
oc patch mcp app --type merge -p '{"spec":{"paused":false}}'
```

Check:

```bash
oc get mcp app
oc describe mcp app
```

### 24.4 Canary approach

For risky changes:

```text
app-canary MCP -> 1 or 2 nodes
app MCP        -> main production app nodes
```

Apply config to canary first, run validation, then roll out to main app pool.

### 24.5 Drain readiness checklist

Before maintenance:

```bash
oc get mcp app
oc get nodes -l workload.openshift.io/type=app
oc get pdb -A
oc get pods -A -o wide | grep <app-node>
oc adm top nodes -l workload.openshift.io/type=app
```

Check:

- Enough free capacity on remaining app nodes
- PDBs not blocking all drains
- Replicas spread across nodes/zones
- No single-replica critical apps without maintenance approval
- No local-only storage workloads that cannot move
- No pods stuck terminating from previous drains

## 26. Troubleshooting Scenarios

### Scenario 1: Pod is Pending because selector does not match

Symptoms:

```text
0/6 nodes are available: node(s) didn't match Pod's node affinity/selector
```

Check pod selector:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.nodeSelector'
```

Check node labels:

```bash
oc get nodes --show-labels | grep workload.openshift.io/type=app
oc get nodes -l workload.openshift.io/type=app
```

Fix:

```bash
oc label node <node> workload.openshift.io/type=app --overwrite
```

Or fix deployment selector.

---

### Scenario 2: Pod is Pending because taint is not tolerated

Symptoms:

```text
0/6 nodes are available: node(s) had untolerated taint {dedicated: app}
```

Check node taints:

```bash
oc describe node <app-node> | grep -i Taints -A3
```

Check pod tolerations:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.tolerations'
```

Fix deployment:

```yaml
tolerations:
  - key: dedicated
    operator: Equal
    value: app
    effect: NoSchedule
```

Or add default toleration to namespace.

---

### Scenario 3: Pod can run on app nodes but also runs on normal workers

Cause:

- Pod has toleration but no nodeSelector/affinity.
- Toleration allows access to app tainted nodes but does not force placement.

Fix:

Add:

```yaml
nodeSelector:
  workload.openshift.io/type: app
```

or required node affinity.

---

### Scenario 4: Node labeled app but not in app MCP

Check:

```bash
oc get mcp app -o yaml
oc get nodes -l node-role.kubernetes.io/app
oc describe mcp app
```

Common causes:

- MCP nodeSelector does not match node label.
- Label key has typo.
- Label value mismatch.
- MCP not created.
- Node has unexpected custom pool label.

Fix:

```bash
oc label node <node> node-role.kubernetes.io/app= --overwrite
```

Verify:

```bash
oc get mcp app
```

---

### Scenario 5: MCP degraded after MachineConfig change

Check:

```bash
oc get mcp app
oc describe mcp app
oc get machineconfignodes
oc logs -n openshift-machine-config-operator \
  -l k8s-app=machine-config-daemon \
  -c machine-config-daemon --tail=100
```

Common causes:

- Invalid MachineConfig syntax
- File permission issue
- Configuration drift from manual node changes
- Drain blocked by PDB
- Node cannot reboot correctly
- Disk pressure or OS-level problem

Fix approach:

1. Read `oc describe mcp app` condition messages.
2. Identify affected node.
3. Check MCD logs for that node.
4. Correct MachineConfig or revert change.
5. Avoid manual host changes unless instructed by Red Hat support or runbook.

---

### Scenario 6: MCO cannot drain app node

Symptoms:

```text
MCCDrainError
cannot evict pod as it would violate the pod's disruption budget
```

Check:

```bash
oc get pdb -A
oc describe pdb <pdb> -n <ns>
oc get pods -n <ns> -o wide
```

Common causes:

- `minAvailable` too strict
- Only one replica exists
- Pods stuck terminating
- Stateful workload cannot move
- Local storage or node affinity too strict

Fix:

- Scale app replicas.
- Adjust PDB temporarily with approval.
- Add capacity to the app pool.
- Relax strict node affinity/topology constraints if appropriate.

---

### Scenario 7: Project node selector conflict

Symptoms:

```text
pods "x" is forbidden: pod node label selector conflicts with its project node label selector
```

Check namespace annotation:

```bash
oc get ns <ns> -o yaml | grep openshift.io/node-selector -A1
```

Check deployment selector:

```bash
oc get deploy <deploy> -n <ns> -o yaml | yq '.spec.template.spec.nodeSelector'
```

Fix:

- Align pod selector with namespace selector.
- Or update namespace selector if policy allows.

---

### Scenario 8: Existing nodes did not get MachineSet labels

Cause:

MachineSet template label changes may not propagate to existing Machines/nodes.

Check:

```bash
oc get machineset <ms> -n openshift-machine-api -o yaml | yq '.spec.template.spec.metadata.labels'
oc get nodes --show-labels | grep node-pool=app-prod
```

Fix options:

- Label existing nodes directly.
- Roll/recreate Machines under the updated MachineSet during a maintenance window.
- Scale up new MachineSet, migrate workloads, then scale down old nodes.

---

### Scenario 9: Workloads overfill app nodes

Symptoms:

- Frequent CPU throttling
- MemoryPressure
- Evictions
- HPA not helping
- Pods Pending with insufficient CPU/memory

Check:

```bash
oc adm top nodes -l workload.openshift.io/type=app
oc adm top pods -A --sort-by=memory
oc adm top pods -A --sort-by=cpu
oc describe node <node> | egrep -A20 "Allocated resources"
```

Fix:

- Correct resource requests/limits.
- Add nodes or increase MachineSet replicas.
- Split noisy workloads into separate pool.
- Enforce quota/limitrange.
- Review HPA/VPA/KEDA usage.

## 27. Security Considerations

Application node pools improve operational isolation, but they are not a complete security boundary.

Use app node pools together with:

- Namespace RBAC
- SecurityContextConstraints / Pod Security Admission
- NetworkPolicy
- Egress firewall or egress controls
- Image signature/policy controls
- Secret management
- Audit logs
- Resource quotas
- Admission policies
- Separate ingress/egress design
- Separate storage classes where required

Do not assume that because a pod is on an app node, it is secure. Node placement is only one layer.

## 28. Best Practices

### 28.1 Design best practices

- Keep app nodes across at least three failure domains when possible.
- Keep infra and storage workloads out of app pools unless intentionally shared.
- Use labels for identity and taints for exclusivity.
- Use namespace-level selectors for team governance.
- Use topology spread constraints for production apps.
- Use PDBs for critical replicated apps.
- Keep enough spare capacity for drain and node failure.
- Use GitOps for MCP, MachineConfig, MachineSet, quota, and placement policies.

### 28.2 MachineConfig best practices

- Avoid unnecessary MachineConfig changes.
- Test on canary pool first.
- Use clear naming, such as `99-app-*`.
- Keep configs small and documented.
- Never make undocumented manual changes on RHCOS nodes.
- Watch MCP status after every change.

### 28.3 Scheduling best practices

- Use `nodeSelector` for simple strict placement.
- Use node affinity for complex rules.
- Use taints/tolerations for dedicated nodes.
- Combine taints with selectors/affinity for true dedication.
- Avoid over-constraining pods with too many strict rules.
- Validate namespace selector and pod selector compatibility.

### 28.4 Operational best practices

- Monitor app pool separately.
- Track allocatable, requests, limits, actual usage, and evictions.
- Keep runbooks for MCP degraded, drain blocked, Pending pods, and node replacement.
- Practice node replacement before production incidents.
- Keep MachineSet templates updated so replacement nodes get correct labels/taints.

## 30. Interview and Exam-Style Questions

### Q1. Is an application node pool a native OpenShift resource?

In a standard standalone OpenShift cluster, no. It is a design pattern created with worker nodes, labels, MachineConfigPool, taints/tolerations, and workload placement controls. In hosted control plane architectures, the term `NodePool` may refer to a specific resource, but that is a different context.

### Q2. Why create a custom MCP for app nodes?

To manage app nodes as a distinct group for OS/runtime/kubelet configuration, upgrade visibility, node reboot behavior, and pool health. It also prevents confusion when nodes have custom role labels.

### Q3. Can a node belong to multiple MCPs?

No. A node can have multiple labels, but it is managed by only one MCP. Custom pool selection takes priority based on node labels.

### Q4. Does a toleration force a pod onto a tainted node?

No. A toleration only allows the pod to schedule onto a tainted node. Use nodeSelector or node affinity to force placement.

### Q5. Why can a pod remain Pending even when app nodes exist?

Common reasons:

- Missing/mismatched node label
- Missing toleration
- Project node selector conflict
- Insufficient CPU/memory
- Strict topology spread constraints
- PDB/drain-related rescheduling pressure
- Node not Ready or SchedulingDisabled

### Q6. Should you remove the worker label from app nodes?

Usually no. Keep `worker` and add `app`, then create a proper custom MCP that inherits worker config. Removing `worker` without proper MCP design can make nodes unmanaged or incorrectly managed.

### Q7. Why use namespace node selectors?

They enforce default placement for all pods in a project, reducing developer errors and improving governance.

### Q8. What happens when you apply a MachineConfig to an app MCP?

The MCO renders a new config for the pool and usually cordons, drains, applies the config, reboots, and uncordons nodes according to the MCP update policy.

### Q9. What is the safest way to roll out risky app node config?

Use a canary MCP or a small app pool first, validate workloads, then roll out to the main app MCP.

### Q10. What is the best way to dedicate app nodes?

Use all three:

```text
Node label       -> identifies/selects app nodes
Node taint       -> prevents unrelated pods
Pod toleration   -> allows intended pods
Node selector or affinity -> forces intended pods onto app nodes
```

## 31. Practical Lab: End-to-End Application Node Pool

### Objective

Create a dedicated app node pool and run an application only on that pool.

### Step 1: Label nodes

```bash
oc label node worker-1 node-role.kubernetes.io/app=
oc label node worker-1 workload.openshift.io/type=app

oc label node worker-2 node-role.kubernetes.io/app=
oc label node worker-2 workload.openshift.io/type=app
```

### Step 2: Create MCP

```bash
cat <<'YAML' | oc apply -f -
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: app
  labels:
    pools.operator.machineconfiguration.openshift.io/app: ""
spec:
  maxUnavailable: 1
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - app
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/app: ""
YAML
```

### Step 3: Taint nodes

```bash
oc adm taint nodes -l node-role.kubernetes.io/app dedicated=app:NoSchedule
```

### Step 4: Create project

```bash
cat <<'YAML' | oc apply -f -
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: app-demo
  annotations:
    openshift.io/node-selector: "workload.openshift.io/type=app"
    scheduler.alpha.kubernetes.io/defaultTolerations: >-
      [{"key":"dedicated","operator":"Equal","value":"app","effect":"NoSchedule"}]
YAML
```

### Step 5: Deploy test application

```bash
oc -n app-demo create deployment hello --image=registry.access.redhat.com/ubi9/httpd-24
oc -n app-demo scale deployment hello --replicas=2
```

### Step 6: Verify placement

```bash
oc -n app-demo get pods -o wide
oc get nodes -l workload.openshift.io/type=app
oc describe pod -n app-demo -l app=hello | egrep -i "Node-Selectors|Tolerations|Node:"
```

Expected: pods should run on nodes labeled `workload.openshift.io/type=app`.

### Step 7: Troubleshoot if Pending

```bash
oc -n app-demo describe pod <pod>
oc get events -n app-demo --sort-by=.lastTimestamp
oc get nodes -l workload.openshift.io/type=app
oc describe node <app-node> | grep -i Taints -A3
```

## 32. Common Production Anti-Patterns

### Anti-pattern 1: Only labeling nodes

Labels alone do not prevent other pods from landing there.

Better:

```text
Labels + taints + namespace policy + deployment placement
```

### Anti-pattern 2: Only tainting nodes

Taints alone do not force intended pods onto those nodes.

Better:

```text
Taint + toleration + nodeSelector/affinity
```

### Anti-pattern 3: No custom MCP

If you create custom role labels but do not create a custom MCP, node config and upgrade behavior can be confusing.

Better:

```text
One custom MCP per node role that needs independent management
```

### Anti-pattern 4: Too many tiny pools

Every pool adds operational complexity. Do not create a custom pool for every small app unless there is a strong reason.

Better:

```text
Pool by operational requirement, SLA, hardware, compliance, or maintenance boundary
```

### Anti-pattern 5: Strict topology rules without enough nodes

Strict `DoNotSchedule` spread rules can block pods when capacity is missing.

Better:

```text
Validate zone/node count before using strict topology constraints
```

### Anti-pattern 6: No PDBs

Without PDBs, drains can disrupt too many app replicas.

Better:

```text
Define PDBs for critical apps and validate them before upgrades
```

### Anti-pattern 7: Overcommitting memory

CPU can be overcommitted more safely than memory. Memory pressure causes evictions and instability.

Better:

```text
Set realistic memory requests/limits and monitor MemoryPressure/evictions
```

## 33. Design Decision Matrix

| Requirement | Recommended control |
|---|---|
| Show node role in `oc get nodes` | `node-role.kubernetes.io/app` label |
| Force app pods onto app nodes | `nodeSelector` or required node affinity |
| Prevent other pods from using app nodes | Taint app nodes + tolerations for app pods |
| Enforce placement for a whole project | `openshift.io/node-selector` namespace annotation |
| Add default tolerations for a project | `scheduler.alpha.kubernetes.io/defaultTolerations` annotation |
| Manage OS/runtime config separately | Custom `MachineConfigPool` |
| Tune kubelet per pool | `KubeletConfig` targeting MCP label |
| Tune CRI-O per pool | `ContainerRuntimeConfig` targeting MCP label |
| Spread replicas across zones | `topologySpreadConstraints` on `topology.kubernetes.io/zone` |
| Spread replicas across nodes | Pod anti-affinity or topology spread on `kubernetes.io/hostname` |
| Protect apps during drain | PodDisruptionBudget |
| Scale app capacity independently | MachineSet + MachineAutoscaler |
| Validate config before wide rollout | Canary MCP |

## 35. Summary

An **Application Node Pool** in OpenShift is a production-grade cluster partitioning pattern. It gives application workloads a dedicated, governed, and observable compute area. For a senior OpenShift administrator, the key is understanding that a node pool is not only a label or only a MachineConfigPool. It is the combination of capacity, labels, taints, MCP lifecycle, scheduler policy, and operational process.

The most important points are:

- Keep application nodes clearly labeled.
- Use a custom MCP when managing app nodes as a separate role.
- Use taints to repel unwanted pods.
- Use tolerations plus node selectors/affinity for intended pods.
- Use namespace selectors for governance.
- Plan capacity for drain, failure, and scaling.
- Watch MCP health during MachineConfig/Kubelet/CRI-O changes.
- Use PDBs and topology spread for application high availability.
- Keep MachineSet templates updated so replacement nodes join the correct pool.

A well-designed application node pool makes the OpenShift cluster easier to operate, safer to upgrade, and more predictable for application teams.
