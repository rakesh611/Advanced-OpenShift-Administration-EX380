# MachineConfig in Cluster Partitioning and Dedicated Node Pools

**Audience:** Advanced OpenShift Administration / DO380-level administrators  
**Experience level:** Written for administrators with ~10 years of Linux, Kubernetes, DevOps, and platform operations experience  
**Platform focus:** OpenShift Container Platform 4.x, RHCOS-based clusters  
**Main object:** `MachineConfig` from `machineconfiguration.openshift.io/v1`

---

## 1. Why MachineConfig matters in cluster partitioning

In advanced OpenShift administration, cluster partitioning means intentionally dividing the cluster into operational zones or node groups such as:

- control plane nodes
- general worker nodes
- infrastructure nodes
- logging nodes
- monitoring nodes
- storage nodes
- GPU nodes
- low-latency or performance nodes
- application-specific node pools
- edge or special hardware nodes

Most administrators first think about partitioning only from a Kubernetes scheduling point of view: labels, taints, tolerations, node selectors, affinity, topology spread constraints, and project-level placement controls.

That is only half of the story.

Dedicated node pools also need **host-level configuration**. Examples:

- logging nodes might need different disk, journald, CRI-O, or kernel settings
- monitoring nodes might need different kubelet reservations
- GPU nodes might need specific kernel modules, drivers, or device plugin preparation
- storage nodes might need multipath, iSCSI, NVMe, hugepage, or kernel parameters
- infra nodes might need router, registry, and monitoring placement support
- low-latency nodes might need real-time kernel, CPU partitioning, reserved CPUs, and tuned profiles
- compliance pools might need audit, time sync, SSH key, or host-level security configuration

`MachineConfig` is the OpenShift-native way to declare many of those host-level changes.

A simple definition:

> A `MachineConfig` declares operating-system-level configuration that the Machine Config Operator applies to nodes through a MachineConfigPool.

For an experienced admin, the important point is this:

> `MachineConfig` is not workload scheduling. It is node operating system desired state.

You use scheduling primitives to decide **which workloads land on which nodes**. You use `MachineConfig` and `MachineConfigPool` to decide **how those nodes are configured at the OS/runtime level**.

## 2. The mental model

Think of OpenShift node partitioning as four layers.

```text
+-------------------------------------------------------------+
| Workload placement layer                                    |
| labels, taints, tolerations, affinity, topology spread       |
+-------------------------------------------------------------+
| Node pool identity layer                                     |
| node-role labels, MachineConfigPool selectors                |
+-------------------------------------------------------------+
| Host configuration layer                                     |
| MachineConfig, KubeletConfig, ContainerRuntimeConfig, Tuned  |
+-------------------------------------------------------------+
| Infrastructure lifecycle layer                              |
| MachineSet, Machine, bare metal host, cloud instance, VM     |
+-------------------------------------------------------------+
```

`MachineConfig` belongs to the **host configuration layer**.

It answers questions like:

- What files should exist on the node?
- Which systemd units should be enabled, disabled, or modified?
- Which kernel arguments should the node boot with?
- Which RHCOS extensions should be installed?
- Which kernel type should the node run?
- Which OS image should the node boot into when using layered/custom OS images?

It does **not** directly answer:

- Which application pod should run on this node?
- How many replicas should run here?
- Which namespace is allowed to use this node?
- Which users can schedule workloads here?
- How big should the MachineSet be?

Those are handled by scheduling, RBAC, quotas, MachineSets, or higher-level platform policies.

## 3. Core objects and how they relate

### 3.1 MachineConfig

A `MachineConfig` is a declarative OpenShift object that describes node OS configuration.

Common capabilities:

- create or overwrite files under supported host paths
- define systemd units and drop-ins
- change kernel arguments
- enable selected RHCOS extensions
- configure the `core` user SSH keys or password hash
- select kernel type such as default, real-time, or 64k-pages where supported
- point to a custom OS image through `osImageURL` in image-layering scenarios

A `MachineConfig` is selected by a `MachineConfigPool` using labels such as:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

or for a custom pool:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

### 3.2 MachineConfigPool

A `MachineConfigPool` is the grouping and rollout boundary for MachineConfigs.

It decides:

- which nodes belong to the pool
- which MachineConfigs are rendered together for that pool
- how many nodes can be unavailable during rollout
- whether the pool is paused
- whether the pool is updated, updating, or degraded

Default pools usually include:

```text
master
worker
```

Custom pools might include:

```text
infra
logging
monitoring
storage
gpu
worker-perf
app-gold
```

### 3.3 Machine Config Operator

The Machine Config Operator, usually abbreviated as MCO, is the OpenShift operator that reconciles MachineConfig and MachineConfigPool desired state onto RHCOS nodes.

It includes:

- `machine-config-controller`
- `machine-config-daemon`
- `machine-config-server`

At a high level:

1. You create or modify a `MachineConfig`.
2. The MCO renders a new combined MachineConfig for the affected pool.
3. The pool moves to updating state.
4. The Machine Config Daemon on each selected node drains workloads, applies the configuration, and reboots when required.
5. The node returns with the new rendered config.
6. The MCP eventually reports `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`.

### 3.4 MachineSet

A `MachineSet` creates and scales machines or instances. It is infrastructure lifecycle, not host configuration.

Example responsibilities:

- create three infra VMs
- scale GPU worker nodes from 2 to 5
- define cloud instance type
- define zone placement
- define disk size
- apply initial labels or taints through provider specs, where supported

A `MachineSet` can create nodes. A `MachineConfigPool` configures them after they join. A `MachineConfig` defines the OS configuration that the pool applies.

### 3.5 KubeletConfig

A `KubeletConfig` is used for kubelet-level settings. It also targets a MachineConfigPool, but it is a separate custom resource.

Use `KubeletConfig` for kubelet settings such as:

- `maxPods`
- `podsPerCore`
- `systemReserved`
- `kubeReserved`
- image garbage collection thresholds

Do not manually edit kubelet config files through a raw MachineConfig unless Red Hat documentation specifically instructs you to. Prefer the supported CRs.

### 3.6 ContainerRuntimeConfig

A `ContainerRuntimeConfig` configures CRI-O/container runtime behavior for a pool.

Use it for runtime settings such as:

- log size
- overlay size
- default runtime changes when supported
- registry/runtime behavior exposed by the supported API

### 3.7 Tuned and PerformanceProfile

For performance, low latency, CPU isolation, hugepages, and real-time workloads, you often use:

- Node Tuning Operator `Tuned` profiles
- Performance Addon Operator / `PerformanceProfile`
- MachineConfig for kernel type, kernel args, extensions, or supporting files

In real production environments, do not solve every host tuning problem with raw MachineConfig. Use the highest-level supported OpenShift API first.

## 4. What MachineConfig can and cannot do

### 4.1 Good use cases

Use `MachineConfig` for:

- writing host configuration files under supported writable paths
- creating systemd units or systemd drop-ins
- enabling or disabling host services where supported
- adding kernel arguments
- enabling selected RHCOS extensions
- managing SSH keys for the `core` user
- preparing dedicated host pools with node-specific OS settings
- creating consistent configuration for new nodes joining a custom pool
- supporting custom RHCOS image layering scenarios

### 4.2 Poor use cases

Avoid using `MachineConfig` for:

- general application deployment
- workload placement
- namespace-level restrictions
- one-off manual fixes on a single node
- editing `/usr` directly
- installing random RPMs directly on RHCOS nodes
- changing kubelet parameters that should be controlled by `KubeletConfig`
- changing CRI-O parameters that should be controlled by `ContainerRuntimeConfig`
- doing unsupported post-installation FIPS conversion
- bypassing operators that already own the config

### 4.3 Paths and mutability

RHCOS is not managed like a traditional RHEL server.

Important operational assumptions:

- `/usr` is generally read-only and should not be modified directly.
- `/etc`, `/boot`, and `/var` are writable but should be managed declaratively.
- Direct SSH edits might work temporarily but create drift and are not durable.
- New nodes do not inherit your manual SSH changes; they inherit declared MachineConfigs.

A 10-year Linux admin coming from classic RHEL must shift from:

```text
ssh node
vi /etc/somefile
systemctl restart service
```

to:

```text
create declarative config
apply to pool
let MCO roll it safely
verify pool status
```

## 5. MachineConfig anatomy

A minimal MachineConfig looks like this:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
```

Important parts:

| Field | Meaning |
|---|---|
| `apiVersion` | Machine configuration API group and version. |
| `kind` | `MachineConfig`. |
| `metadata.name` | Name. Prefixes matter because MachineConfigs are processed in lexical order. |
| `metadata.labels.machineconfiguration.openshift.io/role` | Role selector used by MachineConfigPool. |
| `spec.config` | Ignition configuration: files, systemd units, passwd entries, etc. |
| `spec.kernelArguments` | Kernel command-line arguments. |
| `spec.kernelType` | Kernel type, for example default or real-time where supported. |
| `spec.extensions` | Supported RHCOS extensions to enable. |
| `spec.osImageURL` | Custom OS image location for certain image-layering use cases. |
| `spec.fips` | FIPS mode control; practically this must be designed at install time, not casually changed after installation. |

## 6. The role label is critical

This label controls which pool can select the MachineConfig:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

Default examples:

```yaml
machineconfiguration.openshift.io/role: master
machineconfiguration.openshift.io/role: worker
```

Custom examples:

```yaml
machineconfiguration.openshift.io/role: infra
machineconfiguration.openshift.io/role: logging
machineconfiguration.openshift.io/role: monitoring
machineconfiguration.openshift.io/role: storage
machineconfiguration.openshift.io/role: gpu
```

A common mistake is creating a MachineConfig without the correct label. The object exists, but no pool consumes it.

Check with:

```bash
oc get mc
oc get mcp
oc describe mcp worker
oc describe mcp infra
```

## 7. Rendered MachineConfigs

The MCO does not apply each individual MachineConfig separately. It renders all selected MachineConfigs for a pool into a single generated MachineConfig.

Example:

```text
00-worker
01-worker-container-runtime
01-worker-kubelet
99-worker-custom-sysctl
99-worker-chrony
```

These become something like:

```text
rendered-worker-6f8a9c5d...
```

The node annotation points to the current and desired rendered config:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

Typical checks:

```bash
oc get mcp
oc describe mcp worker
oc get mc | grep rendered-worker
oc get node -o wide
oc describe node <node> | egrep -i 'machineconfiguration|currentConfig|desiredConfig'
```

Rendered configs are useful for troubleshooting because they show what the MCO actually generated for a pool.

## 8. Lexical ordering and naming strategy

MachineConfigs are processed in lexicographic order by name. That means the name prefix matters.

Common naming patterns:

```text
00-worker-...
01-worker-...
50-worker-...
80-worker-...
99-worker-...
```

A good enterprise pattern:

```text
50-worker-baseline-chrony
60-worker-security-auditd
70-worker-storage-iscsi
80-worker-runtime-custom
99-worker-emergency-override
```

For custom pools:

```text
50-infra-router-sysctl
60-logging-journald
70-storage-multipath
80-gpu-kernel-args
99-monitoring-custom-ca
```

Avoid random names like:

```text
test
abc
new-config
machineconfig1
```

Bad names create future confusion during incident response.

## 9. MachineConfig and custom node pools

### 9.1 Default worker pool

A MachineConfig labeled as `worker` is selected by the worker pool.

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

Important behavior:

- Worker MachineConfigs are baseline for worker nodes.
- Custom worker-derived pools often include the `worker` role in their `machineConfigSelector` so they inherit worker baseline configs.
- A worker MachineConfig can affect custom pools if those pools select the `worker` role.

### 9.2 Custom pool example: infra

Suppose you want infra nodes for routers, registry, and monitoring components.

Node labels:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
oc label node worker-2 node-role.kubernetes.io/infra=
oc label node worker-3 node-role.kubernetes.io/infra=
```

Many real clusters preserve the `worker` label as well, especially for subscription/accounting and compatibility reasons. Then use taints and tolerations to keep normal application workloads away.

Example taint:

```bash
oc adm taint nodes -l node-role.kubernetes.io/infra node-role.kubernetes.io/infra=:NoSchedule
```

Custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Then create MachineConfigs labeled `infra`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-infra-host-banner
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
        - path: /etc/motd.d/infra-node.conf
          mode: 0644
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8,Infra%20node%20-%20managed%20by%20MCO%0A
```

The infra pool receives:

- selected worker baseline MachineConfigs
- selected infra-specific MachineConfigs

That is how you build a dedicated node pool without losing baseline worker configuration.

## 10. Node can have many role labels, but one MCP membership

A node can carry labels like:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
node-role.kubernetes.io/storage=
```

But for MachineConfig rollout purposes, it should belong to only one MCP.

Overlapping MCP selectors create confusion and can degrade pool behavior. In production, design selectors so that a node is intentionally matched by only one MachineConfigPool.

Practical check:

```bash
oc get mcp -o yaml | egrep -n 'name:|nodeSelector|machineConfigSelector|node-role'
oc get nodes --show-labels
```

## 11. MachineConfig rollout lifecycle

When you apply a MachineConfig:

```bash
oc apply -f 60-worker-example.yaml
```

The lifecycle is roughly:

1. API server stores the MachineConfig.
2. MCO detects the change.
3. Render controller creates a new `rendered-<pool>-<hash>` config.
4. MCP status changes to `UPDATING=True`.
5. MCD on selected nodes sees desired config change.
6. Node is cordoned/drained when required.
7. Changes are applied.
8. Node reboots when required.
9. Node returns and reports current config.
10. MCP eventually reports updated.

Watch rollout:

```bash
watch -n 5 'oc get mcp; echo; oc get nodes'
```

Detailed pool status:

```bash
oc describe mcp worker
oc describe mcp infra
```

Node-level status:

```bash
oc describe node <node>
oc adm node-logs <node> -u kubelet
oc adm node-logs <node> -u crio
```

MCO logs:

```bash
oc logs -n openshift-machine-config-operator deploy/machine-config-controller
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon
```

For a specific MCD pod:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon
oc logs -n openshift-machine-config-operator <mcd-pod-name> -c machine-config-daemon
```

## 12. Reboot behavior

Most MachineConfig changes require a reboot because they change host OS state.

Examples that usually require reboot:

- kernel arguments
- kernel type
- OS image changes
- many systemd or file changes
- extension installation

Some changes may be applied without full drain/reboot depending on the exact change and supported node disruption behavior. However, for planning, treat MachineConfig as a potentially disruptive change.

Production rule:

> Never apply MachineConfig changes casually during business hours on a large pool.

Use:

- small `maxUnavailable`
- custom pools
- canary pools
- maintenance windows
- PodDisruptionBudgets awareness
- workload high availability
- monitoring during rollout

## 13. Pausing a MachineConfigPool

You can pause a pool before making multiple changes:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":true}}'
```

Apply several MachineConfigs:

```bash
oc apply -f 50-worker-a.yaml
oc apply -f 60-worker-b.yaml
oc apply -f 70-worker-c.yaml
```

Then unpause:

```bash
oc patch mcp worker --type merge -p '{"spec":{"paused":false}}'
```

Use this carefully.

Benefits:

- avoids multiple consecutive reboots
- lets you batch configuration changes
- provides controlled rollout timing

Risks:

- desired state accumulates but does not apply
- long-paused pools might block cluster updates
- operators might report upgrade risk
- admins might forget the pool is paused

Always check:

```bash
oc get mcp
oc describe mcp worker | grep -i paused -A3 -B3
```

## 14. maxUnavailable strategy

Each MCP can control how many nodes update at once.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  maxUnavailable: 1
```

For small dedicated pools, prefer conservative values.

Recommended starting points:

| Pool type | Suggested `maxUnavailable` |
|---|---:|
| control plane | default / very cautious |
| infra 3 nodes | 1 |
| logging 3 nodes | 1 |
| monitoring 3 nodes | 1 |
| storage 3 nodes | 1, sometimes 0 operationally via pause/control |
| GPU 2 nodes | 1 or maintenance controlled |
| large app workers | percentage or small number after testing |

The right value depends on workload HA, PDBs, replicas, zones, and business risk.

## 15. MachineConfig in dedicated node-pool design

### 15.1 Infra node pool

Purpose:

- routers
- image registry
- monitoring components when desired
- cluster infrastructure workloads

MachineConfig use cases:

- host banner
- logging/audit files
- kernel/network parameters needed by routers
- custom CA files where supported
- CRI-O/container runtime tuning through supported CRs

Typical placement objects:

- node labels: `node-role.kubernetes.io/infra=`
- taint: `node-role.kubernetes.io/infra=:NoSchedule`
- operator tolerations and node placement config
- MCP: `infra`
- MachineConfig role: `infra`

### 15.2 Logging node pool

Purpose:

- LokiStack or Elasticsearch/OpenSearch-style logging backends
- collectors or log storage components
- high disk I/O workloads

MachineConfig use cases:

- journald configuration
- disk-related host configuration
- kernel args where required
- storage client preparation
- persistent host path preparation where documented

Operational warnings:

- logging workloads are I/O heavy
- do not mix with noisy application workloads
- apply MC changes one node at a time
- ensure log stack replication survives node reboots

### 15.3 Monitoring node pool

Purpose:

- Prometheus
- Alertmanager
- Thanos Querier/Receiver where applicable
- metrics-heavy workloads

MachineConfig use cases:

- host-level time sync files
- kernel/network tuning where required
- CA/trust bundle support where documented
- kubelet reservation via `KubeletConfig`, not raw MC

Operational warnings:

- monitoring outage hides other outages
- protect with PDBs and replicas
- do not reboot all monitoring nodes together

### 15.4 Storage node pool

Purpose:

- OpenShift Data Foundation / Ceph
- local storage
- special disk/NVMe nodes
- storage gateways

MachineConfig use cases:

- multipath enablement
- iSCSI initiator settings where documented
- kernel modules or extensions where supported
- udev rules under supported paths
- storage-specific systemd units where approved

Operational warnings:

- storage pools are highly sensitive to reboots
- coordinate with ODF/Ceph health
- check replica health before each node drain
- never make broad MachineConfig changes during degraded storage health

### 15.5 GPU node pool

Purpose:

- AI/ML workloads
- CUDA workloads
- GPU operator-managed workloads

MachineConfig use cases:

- kernel args needed by platform/vendor guidance
- special OS image layering only when supported
- prerequisites that are not owned by GPU Operator

Operational warnings:

- most GPU driver lifecycle should be handled by the NVIDIA GPU Operator or supported vendor operator
- avoid installing drivers manually through MachineConfig
- use custom MCP and canary node before rolling to all GPU nodes

### 15.6 Performance / low-latency pool

Purpose:

- telco/RAN
- packet processing
- latency-sensitive workloads
- CPU-pinned workloads

MachineConfig use cases:

- real-time kernel where supported
- kernel arguments
- extensions
- base files required by performance design

Usually combined with:

- PerformanceProfile
- Node Tuning Operator
- CPU Manager
- Topology Manager
- SR-IOV Operator
- hugepages
- workload-specific RuntimeClass

Do not design low-latency nodes with MachineConfig alone.

## 16. Example: create an infra MachineConfigPool and MachineConfig

### 16.1 Label nodes

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
oc label node worker-2 node-role.kubernetes.io/infra=
oc label node worker-3 node-role.kubernetes.io/infra=
```

Optional taint:

```bash
oc adm taint nodes -l node-role.kubernetes.io/infra node-role.kubernetes.io/infra=:NoSchedule
```

### 16.2 Create the infra MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f infra-mcp.yaml
oc get mcp
```

### 16.3 Create infra-specific host config

Example: write an operational marker file.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 50-infra-operational-marker
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
        - path: /etc/openshift-node-role
          mode: 0644
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8,role=infra%0Aowner=platform-team%0Amanaged_by=machine-config-operator%0A
```

Apply:

```bash
oc apply -f 50-infra-operational-marker.yaml
oc get mcp infra -w
```

Verify on node:

```bash
oc debug node/worker-1
chroot /host
cat /etc/openshift-node-role
exit
exit
```

## 17. Example: systemd drop-in through MachineConfig

Example: add a systemd drop-in to a custom service.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 60-worker-example-systemd-dropin
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.5.0
    systemd:
      units:
        - name: example-node-agent.service
          enabled: true
          contents: |
            [Unit]
            Description=Example Node Agent
            Wants=network-online.target
            After=network-online.target

            [Service]
            Type=oneshot
            ExecStart=/usr/local/bin/example-node-agent.sh
            RemainAfterExit=yes

            [Install]
            WantedBy=multi-user.target
    storage:
      files:
        - path: /usr/local/bin/example-node-agent.sh
          mode: 0755
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8,%23%21%2Fbin%2Fbash%0Aecho%20example%20%3E%20%2Fvar%2Flib%2Fexample-node-agent%0A
```

Notes:

- Use this pattern for supported operational scripts only.
- Avoid building a hidden configuration management system with random scripts.
- Keep scripts idempotent.
- Keep scripts small.
- Prefer operators for long-running agents.

```bash

cat /proc/cmdline
exit
exit
```

Kernel arguments are high impact. Validate them on a canary pool before broad rollout.

## 20. Example: generate MachineConfig with Butane

Writing raw Ignition YAML is error-prone. Butane provides a friendlier syntax and validation.

Example Butane file:

```yaml
variant: openshift
version: 4.20.0
metadata:
  name: 99-worker-custom-chrony
  labels:
    machineconfiguration.openshift.io/role: worker
openshift:
  kernel_arguments:
    - loglevel=7
storage:
  files:
    - path: /etc/chrony.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          pool 0.rhel.pool.ntp.org iburst
          driftfile /var/lib/chrony/drift
          makestep 1.0 3
          rtcsync
          logdir /var/log/chrony
```

Generate MachineConfig:

```bash
butane 99-worker-custom-chrony.bu -o 99-worker-custom-chrony.yaml
```

Apply:

```bash
oc apply -f 99-worker-custom-chrony.yaml
```

Best practice:

- Store the Butane source file in Git.
- Generate the MachineConfig as part of CI or a documented admin workflow.
- Review generated YAML before applying.
- Match the Butane version field to your OpenShift minor version, ending in `.0`, for example `4.20.0` for OpenShift 4.20.

## 21. Canary pool strategy

For production, do not test risky host changes directly on all workers.

A safer design:

```text
worker pool       -> normal worker nodes
worker-canary MCP -> one selected worker node
worker-perf MCP   -> final production performance pool
```

Steps:

1. Select one non-critical worker node.
2. Label it for a canary pool.
3. Create MCP that inherits worker configs plus canary configs.
4. Apply MachineConfig to canary role.
5. Verify reboot, kubelet, CRI-O, workload scheduling, monitoring, logs.
6. Promote the change to the real pool.

Example canary node label:

```bash
oc label node worker-a node-role.kubernetes.io/worker-canary=
```

Example canary MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-canary
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - worker-canary
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-canary: ""
  maxUnavailable: 1
```

Example MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 90-worker-canary-test
  labels:
    machineconfiguration.openshift.io/role: worker-canary
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
        - path: /etc/canary-test
          mode: 0644
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8,canary%20ok%0A
```

## 23. Day-1 vs day-2 MachineConfig

### Day-1

Day-1 means configuration included during cluster installation.

Use cases:

- required kernel arguments before first boot
- disk layout or special early boot requirements
- configuration that must exist before node joins cluster
- bare metal bootstrap-sensitive settings

Day-1 MachineConfigs are placed into installer manifests before cluster creation.

### Day-2

Day-2 means configuration applied after the cluster is running through the MCO.

Use cases:

- most host files
- systemd units
- kernel arguments that can be safely rolled
- pool-specific tuning
- dedicated node pool customizations

Important difference:

- The MCO manages day-2 MachineConfigs as cluster objects.
- Initial Ignition passed directly during install can include changes that MCO does not know about unless they are represented as MachineConfigs.

For long-term manageability, represent host configuration as MachineConfigs whenever possible.

## 24. MachineConfig and cluster upgrades

MachineConfig affects cluster upgrades because the MCO participates in node OS updates.

Before an OpenShift upgrade:

```bash
oc get co machine-config
oc get mcp
oc get nodes
```

You want:

```text
MCP UPDATED=True
MCP UPDATING=False
MCP DEGRADED=False
ClusterOperator machine-config Available=True Progressing=False Degraded=False
```

Avoid upgrading when:

- any MCP is degraded
- a pool is paused without a clear reason
- many nodes have desired config different from current config
- storage or infra pools are mid-rollout
- custom MachineConfigs were recently applied and not validated

Upgrade-safe practice:

1. Reconcile all MCPs.
2. Remove abandoned experimental MachineConfigs.
3. Confirm no paused pools unless intentionally part of upgrade plan.
4. Confirm all nodes are Ready.
5. Confirm no MCO degradation.
6. Review custom configs for unsupported OS assumptions.

## 25. Configuration drift

Configuration drift means the node no longer matches the MachineConfig that the MCO believes should be applied.

Example drift causes:

- admin manually edits a file managed by MachineConfig
- emergency SSH change not committed back to MachineConfig
- script modifies a managed file
- package/operator changes a file owned by MCO config
- file permissions differ from desired state

Symptoms:

```bash
oc get mcp
oc describe mcp <pool>
oc get co machine-config
oc describe node <node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Typical MCO status:

```text
DEGRADED=True
```

Fix strategy:

1. Identify exact node and file/config mismatch.
2. Decide whether the MachineConfig is correct or the manual change is correct.
3. If MachineConfig is correct, restore node file to desired state.
4. If manual change is correct, update MachineConfig declaratively.
5. Wait for MCO to reconcile.
6. Confirm MCP returns to healthy state.

Do not repeatedly force reboot nodes without fixing drift root cause.

## 27. Common problems and fixes

### Problem 1: MachineConfig created but nothing happens

Possible causes:

- wrong role label
- no MCP selects that role
- MCP is paused
- MachineConfig has invalid Ignition
- node selector does not match any node

Checks:

```bash
oc get mc --show-labels
oc get mcp -o yaml
oc get mcp
oc describe mcp <pool>
```

Fix:

- correct `machineconfiguration.openshift.io/role`
- create or fix MCP selector
- unpause MCP if appropriate
- validate MachineConfig YAML

### Problem 2: MCP stuck updating

Possible causes:

- node not Ready
- drain blocked by PDB
- daemon cannot apply config
- reboot issue
- workload disruption policy blocks progress

Checks:

```bash
oc describe mcp <pool>
oc get nodes
oc describe node <node>
oc get pdb -A
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon
```

Fix:

- fix unhealthy node
- resolve blocking PDB/workload issue
- inspect MCD error
- avoid deleting random MCO objects unless directed by support/runbook

### Problem 3: MCP degraded after manual SSH change

Cause:

- file managed by MachineConfig was modified manually

Checks:

```bash
oc describe mcp <pool>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Fix:

- restore file to MachineConfig desired state, or
- update MachineConfig to match intended state

### Problem 4: Custom pool does not inherit worker base config

Cause:

- MCP `machineConfigSelector` only selects custom role and omits `worker`

Risk:

- nodes miss baseline worker MachineConfigs

Fix pattern:

```yaml
machineConfigSelector:
  matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
        - worker
        - infra
```

### Problem 5: Node matched by multiple pools

Cause:

- overlapping MCP node selectors

Fix:

- redesign labels/selectors
- ensure each node intentionally belongs to one MCP
- avoid broad custom selectors that unintentionally match worker nodes

### Problem 6: Applying MachineConfig causes too many reboots

Cause:

- large worker pool
- high `maxUnavailable`
- multiple separate MC changes applied sequentially

Fix:

- pause pool before batch changes
- use `maxUnavailable: 1` for critical pools
- use canary pool
- schedule maintenance window

### Problem 7: Rendered MachineConfigs accumulating

Cause:

- MCO creates rendered configs over time and does not automatically garbage collect all unused rendered configs

Check:

```bash
oc adm prune renderedmachineconfigs list --in-use=false --pool-name=worker
```

Dry run:

```bash
oc adm prune renderedmachineconfigs --pool-name=worker
```

Prune with confirmation:

```bash
oc adm prune renderedmachineconfigs --pool-name=worker --count=2 --confirm
```

Only prune unused rendered configs. Do not delete rendered configs that are currently in use.

## 28. Rollback strategy

MachineConfig rollback usually means changing desired state again, not manually undoing files node by node.

### 28.1 Roll back a simple MachineConfig

If you created a bad MachineConfig:

```bash
oc delete mc 99-worker-bad-config
```

Then monitor:

```bash
oc get mcp worker -w
```

The MCO renders a new desired config without that MachineConfig and rolls nodes again.

### 28.2 Roll back by applying corrected version

```bash
oc apply -f 99-worker-corrected-config.yaml
oc get mcp worker -w
```

### 28.3 Emergency rollback thought process

Ask:

- Is the API available?
- Is the MCO available?
- Is only one pool affected?
- Is only one node affected?
- Can workload capacity tolerate another reboot?
- Is etcd/control plane healthy?
- Does a support case make sense before manual intervention?

For control plane MachineConfig errors, be significantly more conservative. A bad master MachineConfig can affect API availability.

## 29. Security considerations

MachineConfig is cluster-admin level power.

Security risks:

- writing sensitive files to nodes
- enabling insecure systemd units
- weakening SSH access
- changing kernel security flags
- changing container runtime behavior
- creating hidden persistence on all nodes
- accidentally exposing secrets in Git

Security practices:

- restrict who can create/update MachineConfigs
- require peer review
- keep all MachineConfig source in Git
- do not store secrets directly in MachineConfig unless the pattern is explicitly supported and reviewed
- use Kubernetes Secrets/operators where possible
- audit changes
- verify MCO health after changes
- document owner and purpose for every custom MachineConfig

Suggested annotation pattern:

```yaml
metadata:
  annotations:
    platform.example.com/owner: platform-team
    platform.example.com/change-ticket: CHG-12345
    platform.example.com/purpose: infra node operational marker
```

## 30. Production design patterns

### 30.1 Baseline + specialization

Use worker baseline plus custom specialization.

```text
worker MachineConfigs
        +
infra MachineConfigs
        =
rendered-infra
```

This keeps common node behavior consistent while allowing pool-specific tuning.

### 30.2 One pool per operational purpose

Do not overload one pool with unrelated responsibilities.

Bad:

```text
special-pool = logging + GPU + storage + monitoring
```

Good:

```text
logging MCP
storage MCP
gpu MCP
monitoring MCP
```

### 30.3 Canary first

For kernel, OS image, extension, or systemd changes:

```text
canary -> small pool -> full pool
```

### 30.4 Prefer supported higher-level CRs

Use:

- `KubeletConfig` for kubelet
- `ContainerRuntimeConfig` for CRI-O/runtime
- `Tuned` for node tuning
- `PerformanceProfile` for low latency
- storage/GPU operators for vendor lifecycle
- `MachineConfig` for OS config glue and supported host-level changes

### 30.5 Avoid snowflake nodes

If a node needs a manual SSH fix, convert that fix into declared config.

Snowflake node:

```text
only worker-7 has manual /etc change
```

Managed node pool:

```text
all infra nodes have same declared MachineConfig
new infra node receives same config automatically
```

- Confirm disk capacity.

## 35. Interview-level explanation

A strong 10-year-experience explanation:

> In OpenShift, MachineConfig is the declarative host operating system configuration object managed by the Machine Config Operator. It is used to configure RHCOS nodes at the OS level, such as files, systemd units, kernel arguments, kernel type, extensions, and OS image references. MachineConfigs are not applied directly to arbitrary nodes. They are selected by MachineConfigPools using labels, rendered into a pool-specific rendered config, and rolled out by the Machine Config Daemon. In cluster partitioning, we use custom MachineConfigPools to create dedicated node pools like infra, logging, monitoring, storage, GPU, or performance pools. The MCP controls which nodes are in the pool and which MachineConfigs are included. Workload placement is handled separately using labels, taints, tolerations, affinity, and operator placement configs. A production admin must manage MachineConfig carefully because most changes cause node drain and reboot, can block upgrades if degraded, and can affect the entire pool. Best practice is to use GitOps, canary pools, small maxUnavailable, and supported higher-level CRs like KubeletConfig, ContainerRuntimeConfig, Tuned, and PerformanceProfile where appropriate.

## 36. Exam and real-world key points

Remember these points:

1. `MachineConfig` changes OS-level node configuration.
2. `MachineConfigPool` selects nodes and MachineConfigs.
3. MCO renders multiple MachineConfigs into one rendered config per pool.
4. Most MachineConfig changes can cause drain and reboot.
5. A node should be intentionally matched by only one MCP.
6. Custom pools usually inherit worker configs by selecting both `worker` and the custom role.
7. Worker MachineConfigs can apply to custom worker-derived pools if selected by the custom MCP.
8. Use labels and taints for workload isolation; use MachineConfig for host configuration.
9. Use `KubeletConfig` for kubelet tuning, not raw file edits.
10. Use `ContainerRuntimeConfig` for CRI-O/runtime tuning, not unsupported manual edits.
11. Use Butane to generate MachineConfig YAML where possible.
12. Store all MachineConfigs in Git.
13. Avoid manual node changes; they create drift.
14. Check `oc get mcp` before and after every change.
15. Never ignore `DEGRADED=True` on any MCP.
16. Do not upgrade a cluster with unhealthy MCPs unless directed by support.
17. Use canary pools for risky changes.
18. Be careful with control plane MachineConfigs.
19. Prune unused rendered configs only with understanding.
20. Dedicated node pools need both scheduling design and host configuration design.

## 38. Final architecture summary

`MachineConfig` is one of the most powerful OpenShift administration tools because it gives cluster administrators declarative control over the node operating system.

In cluster partitioning, its role is not to isolate pods directly. Its role is to ensure each dedicated node pool has the correct host-level configuration for its purpose.

A mature OpenShift node-pool design looks like this:

```text
Dedicated pool identity:
  node-role labels + MachineConfigPool

Workload isolation:
  taints + tolerations + node selectors + affinity + operator placement

Host configuration:
  MachineConfig + KubeletConfig + ContainerRuntimeConfig + Tuned + PerformanceProfile

Lifecycle and scale:
  MachineSet + autoscaler + infrastructure provider

Operational safety:
  canary + maxUnavailable + maintenance windows + GitOps + rollback plan
```

The difference between a basic admin and an advanced admin is not knowing how to apply a MachineConfig. It is knowing when to apply one, which pool it affects, what will reboot, what might degrade, how to roll back, and how it interacts with the rest of the OpenShift platform.
