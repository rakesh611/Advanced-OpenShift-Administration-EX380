## 1. Executive Summary

In OpenShift, **node role labels** are Kubernetes node labels with a special convention:

```text
node-role.kubernetes.io/<role>
```

Examples:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/master=
node-role.kubernetes.io/control-plane=
node-role.kubernetes.io/infra=
node-role.kubernetes.io/app=
node-role.kubernetes.io/logging=
node-role.kubernetes.io/monitoring=
node-role.kubernetes.io/storage=
node-role.kubernetes.io/gpu=
```

These labels are simple metadata, but in OpenShift administration they become a major design tool. They help answer questions such as:

- Which nodes are normal application workers?
- Which nodes should run routers, registry, monitoring, logging, or other platform components?
- Which nodes should receive a specific MachineConfig?
- Which nodes belong to a custom MachineConfigPool?
- Which nodes should accept a certain class of workload?
- Which nodes should be updated independently from the rest of the worker fleet?
- Which nodes are dedicated, isolated, expensive, GPU-enabled, storage-attached, or security-sensitive?

A senior OpenShift administrator should understand one important principle:

> **A node role label alone does not isolate workloads. It identifies a node. Isolation requires scheduling policy, taints/tolerations, selectors, affinity, and usually a matching MachineConfigPool design.**

For example, this label:

```bash
oc label node worker01 node-role.kubernetes.io/infra=""
```

makes `worker01` appear as an `infra` node, but it does not automatically stop normal application pods from landing there if the node still also has the `worker` role and no taint is applied.

A robust dedicated node-pool design usually combines:

```text
Node role label      -> identifies the node class
MachineSet template  -> makes the label survive node replacement
MachineConfigPool    -> controls OS/kubelet/config lifecycle for that pool
Taint                -> repels unwanted workloads
Toleration           -> allows approved workloads onto tainted nodes
Node selector/affinity -> attracts selected workloads to that pool
PDB/spread rules     -> protects availability during drains and upgrades
Monitoring alerts    -> detects drift and capacity issues
```

## 2. What Are Node Role Labels?

Kubernetes labels are key/value metadata attached to objects. A node role label is a label placed on a `Node` object to describe the node's high-level function.

Generic Kubernetes label example:

```yaml
metadata:
  labels:
    environment: prod
    region: apac
    disk: ssd
```

Node role label example:

```yaml
metadata:
  labels:
    node-role.kubernetes.io/worker: ""
```

The special part is the prefix:

```text
node-role.kubernetes.io/
```

Everything after the slash is treated as the role name.

Examples:

```text
node-role.kubernetes.io/worker
node-role.kubernetes.io/infra
node-role.kubernetes.io/storage
node-role.kubernetes.io/gpu
node-role.kubernetes.io/logging
```

In OpenShift, these labels are visible in the `ROLES` column of:

```bash
oc get nodes
```

Example:

```text
NAME             STATUS   ROLES           AGE   VERSION
master-0         Ready    master          90d   v1.34.x
worker-0         Ready    worker          90d   v1.34.x
infra-0          Ready    infra,worker    40d   v1.34.x
logging-0        Ready    logging         25d   v1.34.x
```

The `ROLES` column is not a separate database field. It is derived from labels whose keys start with `node-role.kubernetes.io/`.

## 3. Why Node Role Labels Matter in OpenShift

In plain Kubernetes, node role labels are mostly a convention for identifying node purpose. In OpenShift, they are more operationally important because they interact with:

1. **Machine API and MachineSets**
2. **MachineConfigPools**
3. **MachineConfig selection**
4. **KubeletConfig selection**
5. **Infrastructure node design**
6. **Cluster operator placement**
7. **Subscription and sizing discussions for infrastructure workloads**
8. **Scheduling boundaries for application teams**
9. **Upgrade rollout behavior**
10. **Troubleshooting and day-2 operations**

A well-designed OpenShift cluster uses node role labels to partition the cluster into understandable operational zones.

Example cluster partitioning:

```text
Control plane nodes
  role: master / control-plane
  purpose: API server, etcd, controller manager, scheduler, platform control plane

Worker nodes
  role: worker
  purpose: general application workloads

Infra nodes
  role: infra
  purpose: routers, registry, monitoring, logging collectors, ingress-related services

Storage nodes
  role: storage
  purpose: ODF/Ceph or storage-heavy services

GPU nodes
  role: gpu
  purpose: AI/ML, batch inference, GPU-enabled workloads

Monitoring nodes
  role: monitoring
  purpose: Prometheus, Alertmanager, Thanos, metrics stack

Logging nodes
  role: logging
  purpose: log collectors, log stores, Elasticsearch/Loki/vector workloads
```

The label itself is small, but the design consequences are large.

## 4. Label Syntax and Meaning

### 4.1 Basic syntax

The standard form is:

```text
node-role.kubernetes.io/<role>=<value>
```

In OpenShift examples, the value is often empty:

```text
node-role.kubernetes.io/infra=
```

or represented in YAML as:

```yaml
node-role.kubernetes.io/infra: ""
```

Kubernetes ignores the value for node role labels. The role comes from the label key after the `/`.

These two forms are commonly equivalent for role display purposes:

```yaml
node-role.kubernetes.io/gpu: ""
```

```yaml
node-role.kubernetes.io/gpu: "gpu"
```

In OpenShift, use the empty string style unless your organization has a reason to standardize otherwise:

```yaml
node-role.kubernetes.io/infra: ""
```

### 4.2 Valid role names

The `<role>` part must follow Kubernetes label key syntax rules.

Good examples:

```text
infra
worker
app
storage
gpu
logging
monitoring
build
ci
edge
rt
```

Avoid role names that are unclear or too environment-specific:

```text
special
misc
team1
newpool
test123
```

Better examples:

```text
app-prod
app-dev
logging
monitoring
storage
gpu
edge
build
```

### 4.3 Role labels are not security boundaries

This is critical.

A node role label does not enforce anything by itself.

It does **not** automatically:

- prevent pods from running on the node
- move workloads to the node
- cordon or drain the node
- apply taints
- create a MachineConfigPool
- change kubelet configuration
- change CPU/memory capacity
- change network policy
- harden the host
- make the node dedicated

It is a marker. You build policy around that marker.

## 5. Common OpenShift Node Roles

### 5.1 `master`

Traditional OpenShift control plane node role:

```text
node-role.kubernetes.io/master=
```

Historically, OpenShift used the `master` role label for control plane nodes. Many OpenShift clusters still show:

```text
ROLES
master
```

Control plane nodes run critical platform services such as:

- API server
- etcd
- scheduler
- controller manager
- control plane static pods

Do not treat control plane nodes as regular worker nodes unless you are working with a supported compact or single-node architecture and understand the scheduling implications.

### 5.2 `control-plane`

Modern Kubernetes uses:

```text
node-role.kubernetes.io/control-plane=
```

OpenShift versions 4.12 and later include both `master` and `control-plane` labels on newly installed control plane nodes. Upgraded clusters from older versions might require manual label alignment if you depend on the `control-plane` label.

Example:

```bash
oc label node master-0 node-role.kubernetes.io/control-plane=""
```

### 5.3 `worker`

Default application-capable node role:

```text
node-role.kubernetes.io/worker=
```

Worker nodes usually run:

- application pods
- user workloads
- platform DaemonSets
- ingress/router pods if infra nodes are not used
- monitoring pods if not moved
- registry pods if not moved

Most default MachineConfig and kubelet configuration for compute nodes starts from the worker pool.

### 5.4 `infra`

Infrastructure node role:

```text
node-role.kubernetes.io/infra=
```

Infra nodes are commonly used for cluster-supporting workloads such as:

- default router / ingress controller
- internal image registry
- monitoring stack
- logging stack
- cluster metrics services
- platform-specific support components

A mature production cluster often separates infra workloads from business application workloads so that a noisy application does not starve critical platform services.

### 5.5 `app`

Application-specific node role:

```text
node-role.kubernetes.io/app=
```

Some organizations prefer to label user workload nodes as `app` instead of relying only on `worker`.

Possible design:

```text
worker role -> broad compute identity
app role    -> user application placement target
```

Example:

```bash
oc label node worker01 node-role.kubernetes.io/app=""
```

Then applications can use:

```yaml
nodeSelector:
  node-role.kubernetes.io/app: ""
```

### 5.6 `logging`

Dedicated logging nodes:

```text
node-role.kubernetes.io/logging=
```

Useful when log processing or log storage is heavy and can impact general applications.

Logging workloads can be CPU, memory, disk, and I/O intensive. Dedicated nodes help protect other workloads from log spikes.

### 5.7 `monitoring`

Dedicated monitoring nodes:

```text
node-role.kubernetes.io/monitoring=
```

Useful for Prometheus, Alertmanager, Thanos, metrics storage, and high-retention observability workloads.

Monitoring workloads are often sensitive to:

- disk I/O
- memory pressure
- restart frequency
- cardinality explosions
- long query bursts

### 5.8 `storage`

Dedicated storage nodes:

```text
node-role.kubernetes.io/storage=
```

Common with OpenShift Data Foundation, Ceph, local storage, or workloads requiring attached disks.

Storage nodes should be designed carefully with:

- failure domains
- disk layout
- network bandwidth
- CPU/memory reservation
- PDBs
- anti-affinity
- taints
- tolerations

### 5.9 `gpu`

GPU node role:

```text
node-role.kubernetes.io/gpu=
```

Used for AI/ML, CUDA, inference workloads, GPU operators, or other accelerator workloads.

GPU nodes are expensive and should nearly always be protected with taints so normal workloads do not consume their CPU/memory capacity accidentally.

Example:

```bash
oc adm taint node gpu01 node-role.kubernetes.io/gpu=:NoSchedule
```

## 6. Node Role Labels vs Normal Node Labels

Node role labels are just labels with a naming convention. But operationally, they are usually treated as higher-level identity labels.

### 6.1 Normal node labels

Examples:

```text
region=apac
zone=apac-1a
disk=ssd
cpu-tier=high
network=low-latency
rack=rack-22
environment=prod
```

These describe physical, logical, or business attributes.

### 6.2 Node role labels

Examples:

```text
node-role.kubernetes.io/infra=
node-role.kubernetes.io/storage=
node-role.kubernetes.io/gpu=
```

These describe the node's cluster function.

### 6.3 Recommended design pattern

Use role labels for broad pool identity:

```text
node-role.kubernetes.io/infra=
```

Use normal labels for detailed scheduling dimensions:

```text
topology.kubernetes.io/zone=ap-south-1a
node.openshift.io/instance-type=m6i.2xlarge
workload-tier=platform
storage-class=nvme
```

Example combined node labels:

```yaml
metadata:
  labels:
    node-role.kubernetes.io/infra: ""
    workload-tier: platform
    topology.kubernetes.io/zone: ap-south-1a
    node-size: large
    disk: ssd
```

This gives you both high-level and detailed placement control.

## 7. Node Role Labels vs Taints, Tolerations, Selectors, and Affinity

This section is the key to real production behavior.

### 7.1 Node role label

A label identifies a node.

```bash
oc label node infra01 node-role.kubernetes.io/infra=""
```

This means:

```text
This node is marked as infra.
```

It does not mean:

```text
Only infra pods can run here.
```

### 7.2 Node selector

A node selector attracts a pod to nodes with matching labels.

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
```

This means:

```text
Schedule this pod only on nodes with the infra role label.
```

### 7.3 Node affinity

Node affinity is a more expressive form of node selector.

Example required affinity:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node-role.kubernetes.io/infra
            operator: Exists
```

This means:

```text
The pod is eligible only on nodes that have the infra role label.
```

Example preferred affinity:

```yaml
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
          - key: node-role.kubernetes.io/infra
            operator: Exists
```

This means:

```text
Prefer infra nodes, but allow other nodes if needed.
```

### 7.4 Taint

A taint repels pods from a node unless they tolerate it.

```bash
oc adm taint node infra01 node-role.kubernetes.io/infra=:NoSchedule
```

This means:

```text
Do not schedule pods here unless they have a matching toleration.
```

### 7.5 Toleration

A toleration allows a pod to pass a taint.

```yaml
spec:
  tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Exists
    effect: NoSchedule
```

This means:

```text
This pod is allowed to run on infra-tainted nodes.
```

Important: a toleration does not attract a pod to a node. It only allows the pod to pass the taint.

### 7.6 Complete dedicated-node formula

For strict placement, use both attraction and repulsion:

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Exists
    effect: NoSchedule
```

And taint the nodes:

```bash
oc adm taint node infra01 node-role.kubernetes.io/infra=:NoSchedule
```

This creates the expected behavior:

```text
Infra workloads can run on infra nodes.
Normal workloads cannot run there unless explicitly tolerated.
```

```text

```

## 10. Adding, Updating, and Removing Node Role Labels

### 10.1 Add a role label

```bash
oc label node <node-name> node-role.kubernetes.io/infra=""
```

Example:

```bash
oc label node worker-0 node-role.kubernetes.io/infra=""
```

Verify:

```bash
oc get node worker-0
```

Expected role column:

```text
worker,infra
```

### 10.2 Add a custom application role

```bash
oc label node worker-1 node-role.kubernetes.io/app=""
```

Verify:

```bash
oc get nodes -l node-role.kubernetes.io/app
```

### 10.3 Remove a role label

To remove a role label, append a dash to the label key:

```bash
oc label node <node-name> node-role.kubernetes.io/worker-
```

Example:

```bash
oc label node infra-0 node-role.kubernetes.io/worker-
```

This removes the `worker` role from that node.

### 10.4 Overwrite a normal label

For normal labels, use `--overwrite` if the key already exists:

```bash
oc label node worker-0 workload-tier=platform --overwrite
```

For node role labels, value is usually empty, so overwriting is less common.

### 10.5 Label multiple nodes

Label all nodes matching a selector:

```bash
oc label nodes -l node-role.kubernetes.io/worker node-role.kubernetes.io/app=""
```

Be careful with bulk operations. Always run a read command first:

```bash
oc get nodes -l node-role.kubernetes.io/worker
```

### 10.6 Recommended safe workflow for production

Before changing node role labels:

```bash
oc get nodes
oc get nodes --show-labels
oc get mcp
oc get pods -A -o wide | grep <node-name>
oc describe node <node-name>
```

Then decide whether to cordon/drain first:

```bash
oc adm cordon <node-name>
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
```

After label changes and policy updates:

```bash
oc adm uncordon <node-name>
```

Do not blindly remove `worker` labels from nodes during business hours without understanding MachineConfigPool membership and workload placement impact.

## 11. Persistence: Node Labels, Machine Labels, and MachineSet Templates

This is a common real-world issue.

### 11.1 Labeling a Node directly

Command:

```bash
oc label node worker-0 node-role.kubernetes.io/infra=""
```

This modifies the Kubernetes `Node` object.

Problem:

```text
If the node is deleted/replaced, the new node might not have this label.
```

Direct node labels are useful for quick testing, emergency fixes, or manual UPI/bare-metal operations, but they are not enough for long-term IPI MachineSet-managed fleets.

### 11.2 Labeling a MachineSet template

For Machine API managed clusters, labels that should survive replacement should be placed in the MachineSet template.

Typical place:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
```

Example MachineSet fragment:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: <cluster-id>-infra-<zone>
  namespace: openshift-machine-api
spec:
  replicas: 2
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machine-role: infra
        machine.openshift.io/cluster-api-machine-type: infra
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
      taints:
      - key: node-role.kubernetes.io/infra
        effect: NoSchedule
```

This means new machines created by the MachineSet create nodes with the infra role label and taint.

### 11.3 Existing MachineSet changes do not always affect existing nodes

If you edit an existing MachineSet template, do not assume existing nodes are immediately relabeled. Existing machines and nodes might not automatically receive template changes. Often you must create new machines, roll nodes, or manually label existing nodes to align current state.

Safe approach:

1. Patch or create the MachineSet template.
2. Create/scale new machines.
3. Confirm new nodes have the expected labels and taints.
4. Move workloads safely.
5. Drain and remove old nodes if required.

### 11.4 Machine labels vs node labels

Machine labels:

```yaml
spec:
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machine-role: infra
        machine.openshift.io/cluster-api-machine-type: infra
```

Node labels:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
```

These are not the same thing.

Machine labels describe Machine API resources. Node labels describe Kubernetes Node objects.

For workload scheduling and MachineConfigPool node selection, you usually care about the **node labels**.

## 12. Node Role Labels and MachineConfigPools

This is where OpenShift differs strongly from generic Kubernetes.

### 12.1 What is a MachineConfigPool?

A MachineConfigPool, or MCP, groups nodes that should receive the same rendered machine configuration.

MCPs control things such as:

- OS-level configuration
- kubelet configuration
- CRI-O configuration
- systemd units
- kernel arguments
- file injection
- RHCOS/RHEL CoreOS update rollout
- node reboot orchestration

Default pools normally include:

```bash
oc get mcp
```

Example:

```text
NAME     CONFIG                         UPDATED   UPDATING   DEGRADED
master   rendered-master-xxxxx          True      False      False
worker   rendered-worker-yyyyy          True      False      False
```

### 12.2 MCP nodeSelector

The MCP uses a node selector to decide which nodes it manages.

Example infra MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

This means:

```text
Manage nodes that have node-role.kubernetes.io/infra="".
Build the rendered config from worker MachineConfigs plus infra-specific MachineConfigs.
```

### 12.3 MachineConfig selector

MachineConfigs are selected using labels such as:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

Example custom MachineConfig for infra nodes:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 51-infra-example
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/example-infra-pool
        mode: 0644
        contents:
          source: data:,infra-pool
```

### 12.4 Why custom MCPs inherit from worker

Custom worker-side pools generally include `worker` in their `machineConfigSelector` so they inherit base worker configuration.

Example:

```yaml
machineConfigSelector:
  matchExpressions:
  - key: machineconfiguration.openshift.io/role
    operator: In
    values:
    - worker
    - infra
```

Without inheriting from worker configuration, custom pools can drift from required base compute node configuration. In OpenShift, custom worker-derived pools are the supported pattern for dedicated compute pool management.

### 12.5 One node, one MCP

A node can be selected by only one MCP. This is a major operational rule.

Example node labels:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

If a custom `infra` MCP exists, the node is managed by the infra MCP, not the generic worker MCP.

If no custom `infra` MCP exists and the node still has the worker role, it is treated as a worker by the Machine Config Operator.

If you remove the worker role and add only infra, but no infra MCP exists, the node can become unmanaged by the Machine Config Operator.

That is a dangerous state.

### 12.6 Check MCP membership

```bash
oc get mcp
```

Describe the MCP:

```bash
oc describe mcp infra
```

Check nodes selected by role:

```bash
oc get nodes -l node-role.kubernetes.io/infra
```

Check rendered config on a node:

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
```

Check desired config:

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

Check MCD pods:

```bash
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide
```

## 13. Dual-Role Nodes vs Pure Dedicated Nodes

### 13.1 Dual-role node

Example:

```text
ROLES: worker,infra
```

Labels:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

This node is both worker and infra by identity.

Advantages:

- Easier transition from worker to infra
- Less risk of node being unmanaged if custom MCP is not ready
- Existing worker MachineConfigs still conceptually apply
- Flexible scheduling if not tainted

Disadvantages:

- General workloads may still schedule there if they target workers
- Role meaning becomes less strict
- Platform teams may assume it is dedicated when it is not
- Requires careful tainting if true isolation is desired

### 13.2 Pure infra node

Example:

```text
ROLES: infra
```

Labels:

```text
node-role.kubernetes.io/infra=
```

No worker label.

Advantages:

- Clear dedicated identity
- Workloads using `worker` selector will not land there
- Better mental model for chargeback and platform separation

Disadvantages:

- Must have a matching custom MCP
- Must ensure operators have placement/toleration rules
- Bad removal sequence can leave node unmanaged
- More operational planning required

### 13.3 Recommended production pattern

For serious dedicated pools:

```text
1. Create MachineSet or node provisioning template with final labels/taints.
2. Create custom MCP before or during pool creation.
3. Keep inheritance from worker MachineConfigs.
4. Apply taint for strict isolation.
5. Configure platform/application workloads with nodeSelector/affinity + toleration.
6. Verify scheduling and MCP health.
7. Remove worker role only after confirming MCP and workload placement behavior.
```

## 14. Designing Dedicated Node Pools

A dedicated node pool is not just a group of machines. It is an operational contract.

A good dedicated node pool design answers:

- What workloads are allowed here?
- What workloads are forbidden here?
- Which team owns capacity?
- Which MachineConfigPool manages the nodes?
- What update/reboot behavior is acceptable?
- What are the minimum replicas per zone?
- What taints protect the nodes?
- What tolerations allow approved pods?
- Are project-level selectors needed?
- Are cluster operator placement settings needed?
- What monitoring alerts detect drift?
- What happens during node replacement?

### 14.1 Minimal node pool design document

For each node pool, document:

```text
Pool name: infra
Role label: node-role.kubernetes.io/infra=""
MachineSet name: <cluster-id>-infra-<zone>
MCP name: infra
Taint: node-role.kubernetes.io/infra=:NoSchedule
Allowed workloads: ingress, registry, monitoring, logging collectors
Forbidden workloads: business applications
Capacity: 3 nodes, one per zone
Instance type: 8 vCPU, 32 GiB RAM
Storage: 200 GiB root disk
Upgrade policy: maxUnavailable=1
Owner: Platform team
```

### 14.2 Role label naming standard

Recommended role labels:

```text
node-role.kubernetes.io/infra
node-role.kubernetes.io/app
node-role.kubernetes.io/logging
node-role.kubernetes.io/monitoring
node-role.kubernetes.io/storage
node-role.kubernetes.io/gpu
node-role.kubernetes.io/build
node-role.kubernetes.io/edge
```

Avoid creating too many roles too early. Every role can become a lifecycle boundary, scheduling boundary, monitoring boundary, and troubleshooting boundary.

### 14.3 Separate role from capability

Bad:

```text
node-role.kubernetes.io/big-memory-ssd-gpu-team-a-prod
```

Better:

```text
node-role.kubernetes.io/gpu=
node-size=large
storage=ssd
environment=prod
team=team-a
```

Use role labels for role. Use ordinary labels for capabilities and ownership.

## 16. Practical Build: Dedicated Application Node Pool

Application pools are useful when you want to keep user workloads away from infra, monitoring, logging, storage, or GPU nodes.

### 16.1 Target state

```text
Role: app
Taint: optional, depending on strictness
MCP: app
Allowed workloads: business apps
Forbidden workloads: infra/logging/monitoring/storage/GPU workloads
```

### 16.2 Label application nodes

```bash
oc label node worker-0 node-role.kubernetes.io/app=""
oc label node worker-1 node-role.kubernetes.io/app=""
oc label node worker-2 node-role.kubernetes.io/app=""
```

Optional: remove worker role after MCP and scheduling design are confirmed:

```bash
oc label node worker-0 node-role.kubernetes.io/worker-
```

In many environments, keeping both `worker` and `app` is acceptable if your platform uses a default node selector that points user workloads to app nodes.

### 16.3 Create app MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: app
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - app
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/app: ""
```

### 16.4 Schedule applications to app nodes

Deployment example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: app-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      nodeSelector:
        node-role.kubernetes.io/app: ""
      containers:
      - name: frontend
        image: registry.example.com/apps/frontend:v1
```

Patch existing deployment:

```bash
oc patch deployment frontend -n app-prod --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"node-role.kubernetes.io/app":""}}}}}'
```

Check rollout:

```bash
oc rollout status deployment/frontend -n app-prod
oc get pods -n app-prod -o wide
```

## 18. Workload Placement Examples

### 18.1 Simple pod with nodeSelector

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-infra-placement
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Exists
    effect: NoSchedule
  containers:
  - name: test
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
```

Apply:

```bash
oc apply -f pod-infra.yaml
oc get pod test-infra-placement -o wide
```

### 18.2 Deployment with required node affinity

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: node-role.kubernetes.io/app
                operator: Exists
      containers:
      - name: backend
        image: registry.example.com/backend:v1
```

### 18.3 Preferred placement with fallback

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reporting
spec:
  replicas: 2
  selector:
    matchLabels:
      app: reporting
  template:
    metadata:
      labels:
        app: reporting
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: node-role.kubernetes.io/app
                operator: Exists
      containers:
      - name: reporting
        image: registry.example.com/reporting:v1
```

This prefers app nodes but does not make them mandatory.

### 18.4 Pod that tolerates infra taint but does not select infra nodes

```yaml
spec:
  tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Exists
    effect: NoSchedule
```

This pod is allowed on infra nodes, but not forced there.

Use this only when fallback scheduling is acceptable.

### 18.5 Pod that selects infra nodes but lacks toleration

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
```

If infra nodes are tainted, this pod will stay Pending because it selects infra nodes but cannot tolerate their taint.

Typical event:

```text
0/6 nodes are available: 3 node(s) had untolerated taint {node-role.kubernetes.io/infra: }, 3 node(s) didn't match Pod's node affinity/selector.
```

## 19. Cluster-Wide and Project-Level Placement Strategy

### 19.1 Cluster-wide default node selector

OpenShift can use a cluster-wide default node selector to constrain newly created pods.

Example Scheduler object pattern:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: node-role.kubernetes.io/app=
```

This can ensure that ordinary user workloads default to application nodes.

Be careful. A cluster-wide default selector can break platform workloads or third-party operators if they are not designed for your placement policy.

### 19.2 Project-level node selector

A namespace/project can have a node selector annotation.

Example:

```bash
oc annotate namespace app-prod openshift.io/node-selector='node-role.kubernetes.io/app='
```

Verify:

```bash
oc get namespace app-prod -o yaml | grep -i node-selector -A2
```

Any pods created in that project must fit the project node selector.

### 19.3 Which level should you use?

Use pod-level placement when:

- only one application needs special placement
- the application owner understands scheduling requirements
- you need precise control in the workload manifest

Use project-level placement when:

- all workloads in a namespace belong to the same placement class
- you want platform-level enforcement for a team/project

Use cluster-wide placement when:

- you have a mature platform policy
- you have tested operator compatibility
- you want all default user workloads constrained away from infra/control/storage/GPU nodes

### 19.4 Avoid conflicting selectors

Example conflict:

Project selector:

```text
node-role.kubernetes.io/app=
```

Pod selector:

```yaml
nodeSelector:
  node-role.kubernetes.io/gpu: ""
```

If no node has both `app` and `gpu`, the pod cannot schedule.

Always troubleshoot Pending pods by checking all placement layers:

```text
Cluster default selector
Project selector
Pod nodeSelector
Pod nodeAffinity
Pod tolerations
Node taints
Node labels
Resource requests
PDB/topology constraints
```

## 20. Node Role Labels During Upgrades and Reboots

### 20.1 MCP rollout behavior

MachineConfigPools roll changes independently.

If you have:

```text
master MCP
worker MCP
infra MCP
storage MCP
gpu MCP
```

OpenShift can roll configuration through each pool according to each pool's status and `maxUnavailable` behavior.

Check:

```bash
oc get mcp
```

Example:

```text
NAME      CONFIG                  UPDATED   UPDATING   DEGRADED
master    rendered-master-xxx     True      False      False
worker    rendered-worker-yyy     True      False      False
infra     rendered-infra-zzz      False     True       False
```

### 20.2 Role labels decide MCP membership

If a node has the wrong role label, it can be managed by the wrong pool or not managed as expected.

Bad cases:

```text
Node should be infra but lacks node-role.kubernetes.io/infra
Node should be worker but worker label was removed accidentally
Node has both app and storage and matches unexpected pool logic
Custom MCP exists but nodeSelector does not match any nodes
MachineConfig targets infra but no infra MCP exists
```

Before changing labels that affect scheduling and MCP membership:

```bash
oc adm cordon <node>
```

After changes:

```bash
oc adm uncordon <node>
```

```bash
oc describe mcp <pool-name>
```

## 21. Troubleshooting Node Role Label Problems

### 21.1 Problem: Node shows `<none>` in ROLES

Check labels:

```bash
oc get node <node-name> --show-labels
```

If no `node-role.kubernetes.io/*` label exists, add the correct role:

```bash
oc label node <node-name> node-role.kubernetes.io/worker=""
```

Then verify:

```bash
oc get nodes
```

### 21.2 Problem: Application pods are running on infra nodes

Check whether infra nodes still have worker label:

```bash
oc get nodes -l node-role.kubernetes.io/infra --show-labels
```

Check taints:

```bash
oc describe node <infra-node> | grep -i taints -A3
```

Fix options:

1. Add infra taint:

```bash
oc adm taint node <infra-node> node-role.kubernetes.io/infra=:NoSchedule
```

2. Remove worker label after MCP is correct:

```bash
oc label node <infra-node> node-role.kubernetes.io/worker-
```

3. Add cluster/project default selector for application nodes.

### 21.3 Problem: Infra workload is Pending

Describe pod:

```bash
oc describe pod <pod> -n <namespace>
```

Look for events like:

```text
node(s) didn't match Pod's node affinity/selector
node(s) had untolerated taint
Insufficient cpu
Insufficient memory
```

Check if infra nodes exist:

```bash
oc get nodes -l node-role.kubernetes.io/infra
```

Check taints:

```bash
oc describe node <infra-node> | grep -i taints -A5
```

If the pod has a selector but no toleration, add toleration.

If the pod has a toleration but no selector, it may schedule elsewhere.

For strict infra placement, use both:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### 21.4 Problem: MCP is degraded after role label change

Check MCP:

```bash
oc get mcp
oc describe mcp <pool-name>
```

Check node current/desired config:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

Check MCD logs:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node-name>
oc logs -n openshift-machine-config-operator <mcd-pod>
```

Common causes:

- node selected by wrong MCP
- custom MCP selector is wrong
- MachineConfig has invalid Ignition content
- node reboot failed
- drain blocked by PDB
- daemon cannot apply file or systemd change
- node has multiple custom role labels and selector behavior is unexpected

### 21.5 Problem: New replacement node does not have expected role label

Check whether the MachineSet template includes node labels:

```bash
oc get machineset <machineset> -n openshift-machine-api -o yaml
```

Look for:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
```

If missing, patch or recreate MachineSet.

Remember: changing an existing MachineSet template might not update existing nodes. It affects future machines created from that template.

### 21.6 Problem: Custom role label exists but no custom MCP exists

Check:

```bash
oc get mcp
oc get nodes --show-labels | grep node-role.kubernetes.io/<role>
```

If the node is intended to be a custom pool, create MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: <role>
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - <role>
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/<role>: ""
```

If it is not intended to be a custom pool, remove the accidental role label.

### 21.7 Problem: Selector syntax is wrong

Common mistake:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: infra
```

But node label is:

```yaml
node-role.kubernetes.io/infra: ""
```

For node selectors, key and value must match. If the node's value is empty, the selector value must be empty.

Correct:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

For affinity, you can avoid value mismatch by using `Exists`:

```yaml
matchExpressions:
- key: node-role.kubernetes.io/infra
  operator: Exists
```

### 21.8 Problem: Too many tiny node roles

Symptoms:

- many MCPs
- hard-to-debug Pending pods
- upgrade complexity
- capacity fragmentation
- small pools unable to absorb failures
- operators requiring custom placement exceptions

Fix:

Consolidate roles. Use normal labels for detailed attributes instead of creating a role for every variation.

## 22. Production Best Practices

### 22.1 Treat role labels as part of platform API

Once application teams rely on a role label, changing or removing it becomes a platform-breaking change.

Use stable names:

```text
infra
app
storage
gpu
logging
monitoring
```

Avoid temporary names:

```text
test
new
pool1
special
```

### 22.2 Use MachineSet templates for persistent labels

For Machine API clusters, put node role labels in MachineSet templates.

Direct node labels are not enough for auto-healing and replacement.

### 22.3 Always pair dedicated labels with taints when isolation matters

Label:

```bash
oc label node infra01 node-role.kubernetes.io/infra=""
```

Taint:

```bash
oc adm taint node infra01 node-role.kubernetes.io/infra=:NoSchedule
```

Workload toleration:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

Workload selector:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

### 22.4 Create a custom MCP for every real custom role

If a node has a long-lived custom role, create a matching MCP.

Example:

```text
node-role.kubernetes.io/infra -> mcp/infra
node-role.kubernetes.io/storage -> mcp/storage
node-role.kubernetes.io/gpu -> mcp/gpu
```

This improves lifecycle control and prevents accidental unmanaged states.

### 22.5 Keep custom MCPs worker-derived

Most custom compute pools should inherit worker MachineConfigs:

```yaml
values:
- worker
- infra
```

This keeps base worker configuration and adds pool-specific changes.

### 22.6 Use one pool per failure/capacity domain only when necessary

Every new MCP adds operational overhead.

Create separate pools when you need different:

- OS-level config
- kubelet config
- kernel arguments
- update schedule
- taint/isolation policy
- hardware class
- ownership/cost model
- compliance boundary

Do not create separate pools only because a team wants a different label.

### 22.7 Watch for capacity fragmentation

Small dedicated pools can cause Pending pods even when the total cluster has free capacity.

Example:

```text
Cluster free CPU: 200 cores
Infra pool free CPU: 0 cores
Router pod selector: infra only
Result: router pod Pending
```

Dedicated pools improve control but reduce scheduling flexibility.

### 22.8 Use zone-aware design

For highly available pools, distribute nodes across zones:

```text
infra-a
infra-b
infra-c
```

Use topology labels:

```text
topology.kubernetes.io/zone=ap-south-1a
topology.kubernetes.io/zone=ap-south-1b
topology.kubernetes.io/zone=ap-south-1c
```

Pair with topology spread constraints or anti-affinity for critical workloads.

### 22.9 Add alerts for label drift

Create monitoring checks for:

- infra nodes missing infra taint
- infra nodes still accepting app workloads
- nodes with `<none>` role
- nodes matching no MCP
- nodes in wrong MCP
- pods Pending due to selectors/taints
- MachineSet template missing required role labels

### 22.10 Document the pool contract

For every role label, document:

```text
Who owns the pool?
What can run there?
What must never run there?
Which MachineSet creates it?
Which MCP manages it?
Which taints protect it?
Which tolerations are allowed?
What is the expected node count per zone?
What is the upgrade behavior?
```

## 23. Common Mistakes and Anti-Patterns

### 23.1 Believing label equals isolation

Wrong assumption:

```text
I labeled a node infra, so apps cannot run there.
```

Correct understanding:

```text
Apps can still run there unless scheduling policy prevents it.
```

Use taints and selectors.

### 23.2 Removing worker label before creating custom MCP

Risky:

```bash
oc label node worker-0 node-role.kubernetes.io/worker-
oc label node worker-0 node-role.kubernetes.io/infra=""
```

If no infra MCP exists, the node might not be managed correctly by the MCO.

Better:

```text
1. Create infra MCP.
2. Label node infra.
3. Verify MCP membership.
4. Move workloads.
5. Remove worker label only if required.
```

### 23.3 Forgetting MachineSet persistence

Bad:

```bash
oc label node infra-0 node-role.kubernetes.io/infra=""
```

Then later node is replaced and new node lacks label.

Better:

```text
Add label to MachineSet template so replacement nodes inherit it.
```

### 23.4 Using value mismatch in nodeSelector

Node label:

```yaml
node-role.kubernetes.io/infra: ""
```

Bad selector:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: infra
```

Good selector:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

Or use affinity `Exists`.

### 23.5 Toleration without selector

A pod with only a toleration can run on tainted nodes, but it is not forced to run there.

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

Add selector if you want placement:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

### 23.6 Selector without toleration

A pod with infra selector but no toleration cannot run on tainted infra nodes.

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

Add toleration:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### 23.7 Creating custom roles for every team

Bad:

```text
node-role.kubernetes.io/team-a
node-role.kubernetes.io/team-b
node-role.kubernetes.io/team-c
node-role.kubernetes.io/team-d
```

This can cause unnecessary MCP sprawl.

Better:

```text
node-role.kubernetes.io/app
team=team-a
team=team-b
```

Use namespaces, RBAC, quotas, and project-level selectors for team isolation where possible.

### 23.8 Labeling control plane nodes for custom pools

Do not create custom worker-derived pools on control plane nodes. Control plane nodes require careful support boundaries.

If you need compact cluster scheduling, use supported OpenShift guidance for that architecture.

## 24. Real-World Architecture Patterns

### 24.1 Small production cluster

```text
3 control plane nodes
3 worker/app nodes
```

Roles:

```text
master/control-plane
worker/app
```

Placement:

- Apps run on worker/app nodes
- Infra workloads may share worker nodes
- Use requests/limits and PDBs carefully

This is simple but less isolated.

### 24.2 Medium production cluster with infra nodes

```text
3 control plane nodes
3 infra nodes
6 app worker nodes
```

Roles:

```text
master/control-plane
infra
app or worker
```

Placement:

- Routers on infra
- Registry on infra
- Monitoring on infra or dedicated monitoring
- User apps on app/worker

This is a common enterprise pattern.

### 24.3 Observability-heavy cluster

```text
3 control plane nodes
3 infra nodes
3 monitoring nodes
3 logging nodes
N app nodes
```

Roles:

```text
infra
monitoring
logging
app
```

Benefits:

- Log spikes do not kill application workloads
- Prometheus memory usage does not starve routers
- Platform workloads are easier to capacity-plan

Tradeoff:

- More pools to manage
- More minimum capacity required
- More scheduling complexity

### 24.4 Storage-heavy OpenShift Data Foundation cluster

```text
3 control plane nodes
3 infra nodes
3 or more storage nodes
N app nodes
```

Roles:

```text
storage
infra
app
```

Storage nodes should be carefully planned with disk and zone topology.

### 24.5 GPU-enabled cluster

```text
3 control plane nodes
3 infra nodes
N app nodes
M gpu nodes
```

Roles:

```text
gpu
app
infra
```

GPU nodes should usually be tainted.

Only GPU-aware workloads and GPU operator components should tolerate the GPU taint.

### 24.6 Edge or telco-style pool

```text
control-plane
worker
edge
rt
```

Possible labels:

```text
node-role.kubernetes.io/edge=
node-role.kubernetes.io/rt=
```

Use cases:

- low-latency workloads
- special kernel arguments
- CPU pinning
- real-time kernel
- SR-IOV
- NUMA-aware placement

Such pools often require custom MCPs and performance profiles.

## 26. Interview and Exam-Level Notes

### 26.1 Core definition

A node role label is a Kubernetes node label with this form:

```text
node-role.kubernetes.io/<role>
```

OpenShift displays these labels in the `ROLES` column of `oc get nodes`.

### 26.2 Key production statement

```text
Node role labels classify nodes. They do not isolate workloads by themselves.
```

Isolation requires:

```text
taints + tolerations + selectors/affinity + correct operator placement
```

### 26.3 Key MachineConfigPool statement

```text
MachineConfigPools select nodes by labels and select MachineConfigs by MachineConfig labels.
```

For custom worker-derived pools:

```yaml
machineConfigSelector:
  matchExpressions:
  - key: machineconfiguration.openshift.io/role
    operator: In
    values:
    - worker
    - infra
nodeSelector:
  matchLabels:
    node-role.kubernetes.io/infra: ""
```

### 26.4 Common exam trap

You label a node as infra:

```bash
oc label node worker01 node-role.kubernetes.io/infra=""
```

But application pods still run there.

Why?

Because the node may still have the worker role and no taint. The label alone did not block scheduling.

### 26.5 Another exam trap

You taint infra node:

```bash
oc adm taint node infra01 node-role.kubernetes.io/infra=:NoSchedule
```

Then router pod becomes Pending.

Why?

Because the router has a node selector for infra but lacks matching toleration, or its operator placement configuration was not updated.

### 26.6 Another exam trap

You create custom `infra` MachineConfig but it does not apply.

Possible causes:

- no infra MCP exists
- MCP `machineConfigSelector` does not include `infra`
- MachineConfig label is wrong
- node lacks `node-role.kubernetes.io/infra`
- node is selected by another MCP
- MCO is degraded

### 26.7 Quick answer for dedicated node pool design

A dedicated OpenShift node pool should include:

```text
1. Node role label
2. Persistent MachineSet node metadata label
3. Optional but recommended custom MachineConfigPool
4. Taint for isolation
5. Workload nodeSelector or affinity
6. Workload toleration
7. Zone-aware replica distribution
8. Monitoring and upgrade validation
```

## 27. Final Takeaway

Node role labels are one of the simplest but most important primitives in OpenShift cluster partitioning.

They answer:

```text
What is this node meant for?
```

But production administration requires deeper thinking:

```text
Who creates the node?
Who manages its OS and kubelet config?
Who can schedule there?
Who is blocked from scheduling there?
What happens when the node is replaced?
What happens during upgrades?
How do operators know to use this pool?
How do we detect drift?
```

A junior admin may stop at:

```bash
oc label node worker01 node-role.kubernetes.io/infra=""
```

A senior OpenShift administrator designs the full lifecycle:

```text
MachineSet -> Node Role Label -> MachineConfigPool -> Taint -> Toleration -> Selector/Affinity -> Operator Placement -> Monitoring -> Upgrade Strategy
```

That complete chain is what makes cluster partitioning reliable in real OpenShift production environments.
