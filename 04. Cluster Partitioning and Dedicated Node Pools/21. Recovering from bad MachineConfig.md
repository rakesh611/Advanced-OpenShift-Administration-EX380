# Recovering from Bad MachineConfig in OpenShift

**Topic:** Cluster Partitioning and Dedicated Node Pools  
**Level:** Advanced OpenShift Administration / Senior Platform Engineer  
**Audience:** OpenShift administrators with production experience  
**Scope:** OpenShift Container Platform 4.x, MachineConfig, MachineConfigPool, Machine Config Operator, dedicated node pools, recovery and rollback strategy

---

## 1. Why this topic matters

A bad `MachineConfig` is one of the most dangerous day-2 administration mistakes in OpenShift because it changes the node operating system layer, not only a Kubernetes object. A bad deployment, route, secret, or config map normally affects one namespace or application. A bad `MachineConfig` can affect every node in a `MachineConfigPool` and can cause node reboots, failed drains, degraded pools, unreachable nodes, broken kubelet behavior, broken CRI-O behavior, bad NetworkManager configuration, kernel argument problems, and blocked cluster upgrades.

In an enterprise OpenShift cluster, `MachineConfig` is commonly used for:

- Kernel arguments
- Systemd units and drop-ins
- CRI-O configuration
- Kubelet configuration through `KubeletConfig`
- Container runtime configuration through `ContainerRuntimeConfig`
- Registry, proxy, pull-secret, and certificate-related node configuration
- File creation or modification under `/etc`, `/var`, and other host paths
- Real-time kernel or performance-related tuning
- Dedicated node pool tuning for infra, logging, monitoring, storage, GPU, telco, or security-sensitive workloads

Because `MachineConfig` changes are applied by the Machine Config Operator and usually involve drain and reboot, recovery must be handled like a platform incident, not like a normal workload troubleshooting task.

## 2. Core mental model

Before recovering, you must understand the control flow.

```text
MachineConfig / KubeletConfig / ContainerRuntimeConfig
                |
                v
        Machine Config Controller
                |
                v
        Rendered MachineConfig
                |
                v
        MachineConfigPool desiredConfig
                |
                v
        Node annotation desiredConfig
                |
                v
        Machine Config Daemon on each node
                |
                v
        Drain -> Apply -> Reboot -> Uncordon
```

### 2.1 Important components

| Component | Namespace / Resource | Responsibility |
|---|---|---|
| Machine Config Operator | `openshift-machine-config-operator` | Owns machine configuration lifecycle |
| Machine Config Controller | MCO controller pod | Renders machine configs and updates MCP desired state |
| Machine Config Daemon | DaemonSet on nodes | Applies config to each node |
| Machine Config Server | MCO component | Serves Ignition config to joining control-plane nodes |
| MachineConfig | Cluster-scoped CR | Describes host-level desired configuration |
| MachineConfigPool | Cluster-scoped CR | Groups nodes that receive the same rendered config |
| Rendered MachineConfig | Generated `rendered-<pool>-<hash>` | Final combined config applied to nodes |
| Node annotations | On each node | Track current, desired, reason, and state |

### 2.2 What makes recovery different from normal Kubernetes recovery

A normal workload object can be rolled back by applying the previous manifest. A `MachineConfig` recovery is different because:

1. The bad config might already be written to the host filesystem.
2. The node might already have rebooted into the bad state.
3. The node might be stuck `NotReady`, `SchedulingDisabled`, or `Degraded`.
4. The MCO might refuse further changes because it detects configuration drift.
5. The MCP might block cluster updates until fixed.
6. Custom MCPs can limit blast radius, but a worker-level config can still impact custom worker-derived pools.

## 3. How MachineConfig affects cluster partitioning

Cluster partitioning means separating node roles and workloads into controlled groups. In OpenShift, this is usually done with:

- Node labels
- Taints and tolerations
- Node selectors
- Affinity rules
- Custom `MachineConfigPool` objects
- Dedicated workload pools such as infra, logging, monitoring, storage, GPU, application, or edge pools

Example node pool design:

```text
master MCP
  - control-plane nodes

worker MCP
  - general application worker nodes

infra MCP
  - router, registry, monitoring, logging infrastructure workloads

storage MCP
  - ODF / Ceph / local-storage nodes

gpu MCP
  - GPU runtime, driver, and accelerator workloads

logging MCP
  - Elasticsearch/Loki/vector/collector-heavy nodes

monitoring MCP
  - Prometheus/Alertmanager/Thanos-heavy nodes
```

A bad `MachineConfig` behaves differently depending on where it is targeted:

| Bad config target | Blast radius |
|---|---|
| `machineconfiguration.openshift.io/role: master` | Control plane risk; highest severity |
| `role: worker` | All normal workers and, depending on version/design, worker-derived custom pools |
| Custom MCP such as `infra` | Limited to nodes selected by that pool |
| Custom MCP with bad selector | Can accidentally capture wrong nodes or no nodes |
| Conflicting worker and custom config | Can produce unexpected rendered output |

For senior administration, the best practice is not only knowing how to recover. The best practice is designing pools so that one bad change does not take down the whole platform.

## 4. What is a bad MachineConfig?

A bad `MachineConfig` is any machine-level desired state that the node cannot safely apply, or that causes the node to become unhealthy after applying.

Common examples:

### 4.1 Invalid YAML or schema

This usually fails before rollout.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-bad-example
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/example.conf
        mode: wrong-value   # bad type
```

### 4.2 Wrong Ignition version

A `MachineConfig` contains an Ignition subset. If the version is wrong or unsupported for your OpenShift release, the MCO can reject or fail processing.

Example area to inspect:

```yaml
spec:
  config:
    ignition:
      version: 3.4.0
```

Always compare this with your cluster version examples and documentation before applying.

### 4.3 Bad base64 content

For file contents, wrong base64 or malformed data URLs are common mistakes.

```yaml
contents:
  source: data:text/plain;charset=utf-8;base64,INVALIDBASE64
```

### 4.4 Bad systemd unit

A syntactically valid `MachineConfig` can still create a broken systemd service.

Example risks:

- Unit starts before required network target
- Service enters crash loop
- Unit overrides kubelet or CRI-O unexpectedly
- Drop-in changes wrong environment variables
- Service blocks boot

### 4.5 Bad CRI-O config

Runtime-level errors can prevent pods from starting.

Symptoms:

- Pods stuck `ContainerCreating`
- `crio` fails to start
- `machine-config-daemon` reports failure after reboot
- Node becomes `NotReady`

### 4.6 Bad kubelet config

Kubelet mistakes can cause severe scheduling and node registration issues.

Examples:

- Too-low `maxPods`
- Bad eviction thresholds
- Invalid reserved resources
- Unsupported kubelet field
- Wrong `systemReserved` or `kubeReserved`

### 4.7 Bad NetworkManager configuration

This is one of the highest-risk categories.

Symptoms:

- Node loses API connectivity
- Node cannot reach SDN/OVN networks
- Node cannot resolve DNS
- Node does not come back after reboot
- SSH or console access required

### 4.8 Bad kernel arguments

Wrong kernel arguments can cause:

- Node boot failure
- Kernel panic
- Device driver failures
- Real-time kernel boot issues
- HugePages or CPU isolation mismatch

### 4.9 Bad custom MCP selector

A wrong selector can move nodes into the wrong pool or create an empty pool.

Example risk:

```yaml
spec:
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

If you label the wrong nodes, the wrong pool receives the wrong rendered config.

### 4.10 Manual file edits causing configuration drift

Even when the original `MachineConfig` was correct, manually editing an MCO-managed file can cause the node and MCP to become degraded.

Examples:

```bash
# Dangerous if file is managed by MachineConfig
sudo vi /etc/chrony.conf
sudo chmod 777 /etc/some-mco-managed-file
sudo rm /etc/systemd/system/some-unit.service
```

If the on-disk file content, permission, or existence differs from the active rendered config, MCD can mark the node degraded.

## 5. Incident symptoms

### 5.1 MCP-level symptoms

```bash
oc get mcp
```

Example:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
master    rendered-master-abc123                             True      False      False      3              3                   3                     0
worker    rendered-worker-def456                             False     True       True       6              4                   4                     1
infra     rendered-infra-aaa111                              False     True       True       3              2                   2                     1
```

Important fields:

| Field | Meaning |
|---|---|
| `UPDATED=True` | Pool has fully applied current rendered config |
| `UPDATING=True` | Pool is rolling out config |
| `DEGRADED=True` | At least one node or pool condition has failed |
| `DEGRADEDMACHINECOUNT` | Number of nodes reporting degraded |
| `READYMACHINECOUNT` | Nodes ready in that pool |
| `UPDATEDMACHINECOUNT` | Nodes that applied target config |

### 5.2 ClusterOperator symptoms

```bash
oc get co machine-config
oc describe co machine-config
```

Possible symptoms:

```text
Degraded=True
Progressing=True
Upgradeable=False
```

If `Upgradeable=False`, cluster upgrade can be blocked until MCP/MCO recovery is complete.

### 5.3 Node annotation symptoms

```bash
NODE=worker-0.example.com

oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

Common values:

```text
Done
Working
Degraded
```

### 5.4 MCD log symptoms

```bash
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon --since=1h
```

For a specific node:

```bash
NODE=worker-0.example.com
MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide \
  -l k8s-app=machine-config-daemon \
  | awk -v n="$NODE" '$0 ~ n {print $1}')

oc logs -n openshift-machine-config-operator "$MCD_POD" --since=2h
```

Common log patterns:

```text
content mismatch for file "/etc/example.conf"
mode mismatch for file "/etc/example.conf"
unexpected on-disk state validating against rendered-worker-xxxxx
failed to update OS to quay.io/openshift-release-dev/...
failed to drain node
error running systemctl daemon-reload
error applying pending config
```

## 6. First response rule: stop the blast radius

When a bad `MachineConfig` is suspected, do not immediately delete random rendered configs or patch node annotations. First determine whether rollout is still in progress and stop further node updates if needed.

### 6.1 Pause the affected MCP

```bash
POOL=worker
oc patch mcp "$POOL" --type=merge -p '{"spec":{"paused":true}}'
```

Check:

```bash
oc get mcp "$POOL" -o jsonpath='{.spec.paused}{"\n"}'
```

Expected:

```text
true
```

### 6.2 Why pausing helps

Pausing the MCP prevents the MCO from applying additional configuration changes to the nodes in that pool. This is useful when only one or a few nodes have consumed the bad rendered config and you need to prevent the remaining nodes from being updated.

### 6.3 Important warning about paused pools

Do not leave MCPs paused permanently. A paused MCP can miss important maintenance changes, certificate rotations, and upgrade-related updates. Use pause as an incident-control tool, then unpause after recovery.

## 7. Recovery decision tree

Use this decision tree in production.

```text
Bad MachineConfig suspected
        |
        v
Is MCP still rolling out?
        |
        +-- Yes --> Pause affected MCP
        |
        v
Can all nodes still reach API?
        |
        +-- Yes --> Use oc, MCD logs, node debug
        |
        +-- No  --> Use console/SSH/bare-metal/cloud access for broken node
        |
        v
Is failure caused by bad desired config or config drift?
        |
        +-- Bad desired config --> Fix/delete bad source MC, allow new rendered config
        |
        +-- Drift from manual edit --> Restore file/permission or use force file
        |
        v
Did node apply bad config and become unhealthy?
        |
        +-- Yes --> Recover node access, fix host/config, reboot carefully
        |
        +-- No  --> Correct MC and resume rollout
        |
        v
Unpause MCP, watch rollout, validate pool and workloads
```

## 8. Golden rule: fix the source object, not the rendered object

The rendered MachineConfig is generated output. In normal recovery, do not edit rendered machine configs directly.

You usually fix one of these source objects:

```bash
oc get mc
oc get kubeletconfig
oc get containerruntimeconfig
```

Then inspect the rendered output:

```bash
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
oc get mc rendered-worker-xxxxx -o yaml
```

### 8.1 Find which MachineConfig contributed to the rendered config

Rendered configs contain references to source configs.

```bash
RENDERED=$(oc get mcp worker -o jsonpath='{.status.configuration.name}')
oc get mc "$RENDERED" -o jsonpath='{range .metadata.annotations}{.}{"\n"}{end}'
```

Better practical inspection:

```bash
oc get mc "$RENDERED" -o yaml | less
```

Look for:

- `machineconfiguration.openshift.io/role`
- files under `spec.config.storage.files`
- systemd units under `spec.config.systemd.units`
- kernel arguments
- generated content from `KubeletConfig`
- generated content from `ContainerRuntimeConfig`

## 9. Scenario 1: Bad MachineConfig created but not yet applied

This is the easiest case.

### 9.1 Symptoms

- MCP might show `UPDATING=True`
- No node has rebooted yet
- Node `currentConfig` still equals old rendered config
- Node `desiredConfig` may point to new rendered config

### 9.2 Immediate action

Pause the pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Find recently created machine configs:

```bash
oc get mc --sort-by=.metadata.creationTimestamp
```

Inspect suspicious object:

```bash
oc get mc 99-worker-bad-example -o yaml
```

Delete or fix the bad source object:

```bash
oc delete mc 99-worker-bad-example
```

or:

```bash
oc edit mc 99-worker-bad-example
```

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Watch:

```bash
watch -n5 'oc get mcp; echo; oc get nodes'
```

### 9.3 Validation

```bash
oc get mcp worker
oc describe mcp worker
oc get co machine-config
```

Expected final state:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
DEGRADEDMACHINECOUNT=0
```

## 10. Scenario 2: Bad MachineConfig applied to one node only

This is common when `maxUnavailable=1`, which is the safest default behavior for many pools.

### 10.1 Symptoms

```bash
oc get mcp worker
oc get nodes
```

Example:

```text
worker    UPDATED=False   UPDATING=True   DEGRADED=True   DEGRADEDMACHINECOUNT=1
```

Only one node may be:

```text
Ready,SchedulingDisabled
NotReady,SchedulingDisabled
Ready but machineconfiguration.openshift.io/state=Degraded
```

### 10.2 Recovery flow

1. Pause the pool.
2. Identify the bad source object.
3. Delete or correct the bad source object.
4. Let MCO render a new desired config.
5. Recover the degraded node.
6. Unpause the pool.
7. Watch rollout.

### 10.3 Commands

Pause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Find degraded node:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason
```

Describe MCP:

```bash
oc describe mcp worker
```

Check MCD logs:

```bash
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon --since=2h | egrep -i 'degraded|error|failed|mismatch|unexpected'
```

Fix source:

```bash
oc delete mc 99-worker-bad-example
```

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Watch:

```bash
watch -n5 'oc get mcp worker; oc get nodes'
```

## 11. Scenario 3: Configuration drift after manual file edit

Configuration drift means the on-disk node state no longer matches the active rendered `MachineConfig`.

### 11.1 Example symptom

```text
Node worker-0 is reporting: "content mismatch for file \"/etc/mco-test-file\""
```

### 11.2 Confirm drift from MCP

```bash
oc describe mcp worker
```

Look for:

```text
Type: NodeDegraded
Reason: 1 nodes are reporting degraded status on sync
Message: content mismatch for file ...
```

### 11.3 Confirm drift from node annotation

```bash
NODE=worker-0.example.com
oc describe node "$NODE" | egrep -A5 'machineconfiguration.openshift.io/(state|reason|currentConfig|desiredConfig)'
```

or:

```bash
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 11.4 Preferred recovery: restore file content and permission

Use `oc debug`:

```bash
NODE=worker-0.example.com
oc debug node/$NODE
```

Inside debug shell:

```bash
chroot /host
```

Compare file:

```bash
ls -l /etc/mco-test-file
cat /etc/mco-test-file
```

Restore the expected content and mode according to the rendered `MachineConfig`.

From outside:

```bash
CURRENT=$(oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}')
oc get mc "$CURRENT" -o yaml | less
```

After correcting the file, restart the MCD pod or wait for it to reconcile:

```bash
oc delete pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon
```

Watch:

```bash
watch -n5 'oc get mcp worker; oc get node worker-0.example.com'
```

### 11.5 Alternative recovery: force file

Use this when you are sure the active rendered config is correct and you want MCD to reapply it.

```bash
NODE=worker-0.example.com
oc debug node/$NODE -- chroot /host touch /run/machine-config-daemon-force
```

Then reboot or allow MCD to proceed:

```bash
oc debug node/$NODE -- chroot /host systemctl reboot
```

Warning: the force file bypasses preflight drift checks and causes a reboot. Do not use it blindly when the active rendered config is itself bad.

## 12. Scenario 4: Node stuck `SchedulingDisabled`

During MachineConfig rollout, the MCO cordons and drains a node. If apply or reboot fails, a node can stay cordoned.

### 12.1 Check node state

```bash
oc get nodes
```

Example:

```text
worker-0   Ready,SchedulingDisabled
```

Check MCD state:

```bash
NODE=worker-0.example.com
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node "$NODE" -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 12.2 Do not simply uncordon immediately

A manual `oc adm uncordon` can hide the symptom but not fix the MachineConfig failure. First resolve the MCO/MCD reason.

Use:

```bash
oc describe mcp worker
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon --since=2h
```

### 12.3 Common causes

- Drain blocked by PodDisruptionBudget
- Static pods or critical workload behavior
- Bad systemd unit
- Failed OS update
- CRI-O/kubelet failure after reboot
- Node not returning from reboot

### 12.4 Recovery

If the source config is bad:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
oc delete mc 99-worker-bad-example
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

If node is healthy after recovery and MCO is no longer working on it:

```bash
oc adm uncordon worker-0.example.com
```

Only uncordon after confirming:

```bash
oc get mcp worker
oc get node worker-0.example.com -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

Expected:

```text
Done
```

## 13. Scenario 5: Bad MachineConfig broke kubelet or CRI-O

### 13.1 Symptoms

```bash
oc get nodes
```

Example:

```text
worker-0   NotReady,SchedulingDisabled
```

Check from node console or SSH:

```bash
sudo systemctl status kubelet
sudo systemctl status crio
sudo journalctl -u kubelet -b --no-pager | tail -100
sudo journalctl -u crio -b --no-pager | tail -100
sudo journalctl -u machine-config-daemon-firstboot -b --no-pager | tail -100
```

### 13.2 Recovery logic

If kubelet/CRI-O is broken because of a bad file written by `MachineConfig`, first remove or fix the bad source `MachineConfig` from the API if the API is still healthy.

```bash
oc delete mc 99-worker-bad-runtime-config
```

If the node cannot communicate with the API, fix enough of the node locally to restore kubelet/CRI-O and API connectivity.

Typical emergency checks on node:

```bash
sudo crio config --default > /tmp/default-crio.conf
sudo systemctl cat crio
sudo systemctl cat kubelet
sudo ls -l /etc/crio /etc/containers /etc/kubernetes/kubelet.conf
```

After API communication returns, let MCO reconcile rather than continuing manual edits.

### 13.3 Restart services only when appropriate

```bash
sudo systemctl daemon-reload
sudo systemctl restart crio
sudo systemctl restart kubelet
```

Then verify:

```bash
oc get node worker-0.example.com
oc describe node worker-0.example.com
oc get mcp worker
```

## 14. Scenario 6: Bad network MachineConfig made node unreachable

This is a high-severity event because `oc debug node` will not work if the node is not reachable by the cluster.

### 14.1 Symptoms

- Node `NotReady`
- SSH unreachable
- Machine console shows network failure
- API cannot contact kubelet
- MCD rollout stuck
- MCP degraded or updating forever

### 14.2 Immediate actions

1. Pause the affected MCP.
2. Delete or fix the bad network `MachineConfig` from the API.
3. Use infrastructure access to recover node networking.

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":true}}'
oc delete mc 99-infra-bad-network
```

### 14.3 Recover through console/SSH

On the node console:

```bash
nmcli con show
nmcli dev status
ip addr
ip route
cat /etc/resolv.conf
journalctl -u NetworkManager -b --no-pager | tail -100
```

If the bad file is under NetworkManager keyfile location, inspect:

```bash
ls -l /etc/NetworkManager/system-connections/
sudo nmcli connection reload
sudo systemctl restart NetworkManager
```

If the node recovers API connectivity, let MCO reconcile the corrected rendered config.

### 14.4 Production warning

Network-related MachineConfigs should never be rolled out first to an entire worker pool. Use a canary pool or a small custom pool before applying to all nodes.

## 15. Scenario 7: Bad kernel arguments or boot failure

### 15.1 Symptoms

- Node does not complete boot
- Kernel panic
- Node disappears from cluster
- Console shows boot errors
- Machine stays unavailable after MCO reboot

### 15.2 Recovery approach

1. Stop further rollout by pausing MCP.
2. Remove or fix bad kernel argument MachineConfig.
3. Recover affected node from console.
4. Reboot into a known-good boot entry if available.
5. Let MCO converge to corrected desired config.

Find kernel argument MachineConfigs:

```bash
oc get mc -o yaml | grep -B5 -A20 kernelArguments
```

Delete bad one:

```bash
oc delete mc 99-worker-bad-kargs
```

If the node cannot boot, use cloud/bare-metal console. On RHCOS, recovery might require selecting a previous boot entry or using platform-specific node replacement. In cloud or machine API environments, replacing an unhealthy worker is often safer than performing risky manual boot repair.

### 15.3 Worker replacement strategy

For replaceable worker nodes:

```bash
oc adm cordon worker-0.example.com
oc adm drain worker-0.example.com --ignore-daemonsets --delete-emptydir-data
```

Then replace the machine through Machine API, cloud automation, or bare-metal automation. New nodes receive the corrected current rendered config.

For control-plane nodes, do not casually delete or rebuild. Follow control-plane recovery procedures and involve vendor support if quorum or etcd health is at risk.

## 16. Scenario 8: Bad MachineConfig in custom dedicated node pool

Assume you have an `infra` MCP.

```bash
oc get mcp infra -o yaml
```

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

A bad `MachineConfig` targeted to `infra`:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

### 16.1 Recovery

Pause only the custom pool:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":true}}'
```

Delete bad custom MC:

```bash
oc delete mc 99-infra-bad-config
```

Unpause:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":false}}'
```

Watch:

```bash
watch -n5 'oc get mcp infra; oc get nodes -l node-role.kubernetes.io/infra='
```

### 16.2 If only infra pool is degraded

Applications on normal workers should continue running if workload placement is designed properly. This is one of the main operational benefits of dedicated node pools.

### 16.3 If infra workloads are affected

Check cluster routers, registry, monitoring, and logging workloads:

```bash
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-image-registry -o wide
oc get pods -n openshift-monitoring -o wide
oc get pods -n openshift-logging -o wide 2>/dev/null || true
```

If router pods were only on degraded infra nodes, external routes might be affected. Use additional infra nodes or temporary worker placement if your operational policy allows it.

## 17. Scenario 9: Bad worker MachineConfig affected custom pools

In many designs, custom worker-derived MCPs include both `worker` and custom role configs. That means a worker-level `MachineConfig` can flow into custom pools.

Example custom pool selector:

```yaml
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
```

This means:

```text
worker MachineConfigs + infra MachineConfigs = rendered-infra-xxxxx
```

### 17.1 Risk

If you create a bad `MachineConfig` with:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

It can impact:

- worker MCP
- infra MCP
- storage MCP
- logging MCP
- monitoring MCP
- GPU MCP
- any custom pool inheriting worker configs

### 17.2 Recovery

Pause all affected pools:

```bash
for p in worker infra storage logging monitoring gpu; do
  oc get mcp "$p" >/dev/null 2>&1 && \
  oc patch mcp "$p" --type=merge -p '{"spec":{"paused":true}}'
done
```

Remove/fix bad worker-level config:

```bash
oc delete mc 99-worker-bad-global-change
```

Unpause in controlled order:

```bash
for p in worker infra monitoring logging storage gpu; do
  oc get mcp "$p" >/dev/null 2>&1 && \
  oc patch mcp "$p" --type=merge -p '{"spec":{"paused":false}}'
  oc wait mcp/$p --for=condition=Updated --timeout=60m || true
done
```

For production, unpause one pool at a time and validate.

## 18. Scenario 10: MCP degraded because rendered config in use was deleted

Rendered MachineConfigs should not be manually deleted while in use.

### 18.1 Symptoms

Possible messages:

```text
could not find MachineConfig rendered-worker-xxxxx
error finding rendered config
```

### 18.2 Recovery approach

1. Identify which rendered config the node or MCP expects.
2. Check whether it still exists.
3. Recreate by restoring source MachineConfigs if possible.
4. If source objects exist, allow render controller to generate new rendered config.
5. If the cluster is stuck, collect must-gather and involve support before manual annotation surgery.

Commands:

```bash
oc get mcp worker -o yaml | egrep 'configuration|rendered'
oc get nodes -o custom-columns=NAME:.metadata.name,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state
oc get mc | grep rendered-worker
```

### 18.3 Do not prune blindly

Use dry-run first:

```bash

```

Only remove unused rendered configs:

```bash
oc adm prune renderedmachineconfigs --pool-name=worker --count=2 --confirm
```

Never delete a rendered config reported as currently in use.

## 20. Inspecting current vs desired config

This is one of the most important troubleshooting steps.

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,POOL:.metadata.labels.node-role\.kubernetes\.io/worker,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason
```

Better script:

```bash
for n in $(oc get nodes -o name | cut -d/ -f2); do
  echo "===== $n ====="
  oc get node "$n" -o jsonpath='current={.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}desired={.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}state={.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}reason={.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
  echo
 done
```

Interpretation:

| currentConfig | desiredConfig | state | Meaning |
|---|---|---|---|
| same | same | Done | Healthy from MCO perspective |
| old | new | Working | Update in progress |
| old | new | Degraded | Failed before/during update |
| new | new | Degraded | Applied target but validation/drift failed |
| missing | any | Degraded | Node/MCD state problem |

## 23. Dangerous recovery methods and when to avoid them

### 23.1 Editing rendered MachineConfig directly

Avoid.

Rendered configs are generated artifacts. Editing them directly can confuse reconciliation and does not fix the source of truth.

### 23.2 Patching node `currentConfig` manually

Avoid unless instructed by vendor support or as a last-resort lab recovery.

Risk:

- Node annotation may not match disk state
- MCD may detect unexpected on-disk state
- Further updates can fail
- You can hide real drift

### 23.3 Deleting rendered MachineConfigs in use

Avoid.

Only prune unused rendered configs using `oc adm prune renderedmachineconfigs` and dry-run first.

### 23.4 Manually editing MCO-managed files

Avoid as a normal practice.

If you must edit during emergency recovery, document exactly what changed and later express the desired state through `MachineConfig`.

### 23.5 Force file on wrong desired config

Avoid.

The force file reapplies the current config. If the current config is bad, force can make the situation worse.

## 24. Using `maxUnavailable` safely

`maxUnavailable` controls how many nodes in a pool can be unavailable during MachineConfig rollout.

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.maxUnavailable}{"\n"}'
```

Set to one for safer rollout:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

For dedicated pools:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"maxUnavailable":1}}'
oc patch mcp storage --type=merge -p '{"spec":{"maxUnavailable":1}}'
oc patch mcp logging --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

Senior guidance:

| Pool | Recommended rollout posture |
|---|---|
| master | Never experiment; schedule maintenance; validate heavily |
| worker | Use `maxUnavailable=1` for risky changes |
| infra | Use at least 3 nodes and `maxUnavailable=1` |
| storage | Very cautious; storage quorum and rebalance impact matter |
| logging | Rolling one node at a time avoids ingestion gaps |
| monitoring | Protect Prometheus/Alertmanager availability |
| GPU | Validate drivers/runtime on canary first |

## 25. Canary MachineConfig rollout pattern

For risky changes, never test first on the whole worker pool.

### 25.1 Create a canary node role

Label one worker:

```bash
oc label node worker-canary-0.example.com node-role.kubernetes.io/mc-canary=
```

### 25.2 Create canary MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: mc-canary
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - mc-canary
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/mc-canary: ""
```

Apply:

```bash
oc apply -f mcp-mc-canary.yaml
```

### 25.3 Target risky MachineConfig to canary

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-mc-canary-test-change
  labels:
    machineconfiguration.openshift.io/role: mc-canary
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/example-canary.conf
        mode: 0644
        contents:
          source: data:text/plain;charset=utf-8;base64,Y2FuYXJ5LXZhbGlkYXRpb249dHJ1ZQo=
```

### 25.4 Validate canary

```bash
oc get mcp mc-canary
oc get node worker-canary-0.example.com
oc debug node/worker-canary-0.example.com -- chroot /host cat /etc/example-canary.conf
```

Only after successful canary testing should you promote the change to the intended pool.

MachineConfig should be handled like infrastructure code.

3. Review rendered effect in non-production.
4. Apply to canary pool.
5. Check MCD logs and node reboot behavior.
6. Apply to target dedicated pool.
7. Apply to broader worker pool only after pool validation.

## 33. Senior admin best practices

### 33.1 Always use custom pools for special workloads

Do not put every node under the default worker pool when workloads have different operational risk.

Recommended:

```text
infra MCP       -> routers, registry, monitoring support components
monitoring MCP  -> Prometheus/Thanos-heavy nodes
logging MCP     -> log collectors/storage nodes
storage MCP     -> ODF/Ceph/local-storage nodes
gpu MCP         -> accelerator and driver-specific nodes
app MCP         -> general business workloads
```

### 33.2 Keep worker-level MachineConfigs minimal

Because worker-level configs can affect custom worker-derived pools, put only truly global settings under the `worker` role.

### 33.3 Prefer pool-specific configs

For infra-only changes:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

For storage-only changes:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: storage
```

### 33.4 Validate MCO health before and after every change

```bash
oc get co machine-config
oc get mcp
```

### 33.5 Never combine too many host-level changes in one MachineConfig

Bad:

```text
one MC changes kernel args + CRI-O + kubelet + systemd + NetworkManager
```

Better:

```text
separate MCs with clear names and rollback boundaries
```

Example naming:

```text
40-worker-chrony-config
50-worker-crio-registry-policy
60-infra-router-sysctl
70-storage-multipath
90-gpu-driver-prereq
```

### 33.6 Use lexicographic ordering intentionally

MachineConfigs are processed by name order. Use numeric prefixes carefully.

Example:

```text
00-worker-base
40-worker-common
80-worker-app-tuning
99-worker-emergency-override
```

Do not create random names that make ordering unclear.

## 34. Interview-level explanation

If asked in an interview: **"How do you recover from a bad MachineConfig?"**

Answer like this:

> First, I check `oc get mcp` and `oc describe co machine-config` to identify the affected pool and whether the MCO is degraded or still progressing. If the rollout is still moving, I immediately pause the affected `MachineConfigPool` to stop the blast radius. Then I inspect node annotations for `currentConfig`, `desiredConfig`, `state`, and `reason`, and check MCD logs for validation, drain, reboot, or content mismatch errors. I fix the source object, such as the bad `MachineConfig`, `KubeletConfig`, or `ContainerRuntimeConfig`, rather than editing rendered configs. If the node is degraded due to drift, I restore the file content and permission to match the active rendered config, or use `/run/machine-config-daemon-force` only when I am sure the current rendered config is correct. After that, I unpause the MCP, watch rollout, confirm `UPDATED=True`, `DEGRADED=False`, `DEGRADEDMACHINECOUNT=0`, and verify workloads. For production, I prevent recurrence using canary pools, `maxUnavailable=1`, GitOps review, and dedicated MCPs for infra, storage, logging, monitoring, GPU, and application nodes.

## 35. Common mistakes

| Mistake | Why it is dangerous |
|---|---|
| Deleting rendered configs manually | Can break nodes still referencing them |
| Force file without understanding desired config | Reapplies possibly bad config |
| Leaving MCP paused permanently | Blocks maintenance/update propagation |
| Applying risky config to `worker` first | Can affect all worker-derived custom pools |
| Ignoring PDBs before rollout | Node drain can hang |
| Manually uncordoning too early | Hides MCO failure state |
| Editing files directly on node | Causes drift unless later expressed via MC |
| Making network changes without console access | Can lock you out of nodes |
| Changing master MachineConfigs casually | Can affect control-plane stability |
| Combining many changes in one MC | Makes rollback and RCA difficult |

## 37. Final production guidance

Recovering from a bad `MachineConfig` is not about one magic command. It is about controlling rollout, identifying whether the problem is bad desired state or configuration drift, fixing the source of truth, safely recovering affected nodes, and validating that every pool is healthy again.

The senior-level mindset is:

```text
Limit blast radius first.
Preserve evidence.
Fix source config, not generated config.
Recover nodes carefully.
Unpause only when ready.
Validate all pools and workloads.
Prevent recurrence with canary pools and GitOps.
```

In a well-designed OpenShift platform, dedicated node pools are not only for scheduling. They are also an operational safety boundary. A bad config in `gpu`, `storage`, `infra`, or `logging` should not take down all application workers. That separation is what turns a potential cluster-wide outage into a controlled pool-level incident.
