# MachineConfig Rollout Troubleshooting in OpenShift

**Context:** Cluster Partitioning and Dedicated Node Pools  
**Audience:** Advanced OpenShift Administration / DO380-level administrators  
**Experience level:** Production runbook style for engineers with ~10 years Linux, Kubernetes, and OpenShift operations experience  
**Scope:** OpenShift Container Platform 4.x, Machine Config Operator (MCO), MachineConfigPool (MCP), custom node pools, dedicated infrastructure/logging/monitoring/GPU/storage/application pools

---

## 1. Why MachineConfig rollout troubleshooting matters

In OpenShift, `MachineConfig` changes are not normal Kubernetes application rollouts. They change the host operating system layer: RHCOS files, systemd units, kubelet configuration, CRI-O configuration, kernel arguments, extensions, certificates, registry trust, SSH keys, and sometimes operating system content.

That means a failed rollout can affect:

- node readiness,
- pod scheduling,
- cluster upgrades,
- custom node pool isolation,
- control plane stability,
- worker pool availability,
- application high availability,
- storage/network/security components running on dedicated nodes.

For a senior OpenShift administrator, the important skill is not only knowing how to create a `MachineConfig`, but knowing how to prove exactly where the rollout is stuck and how to recover safely without making the pool worse.

A MachineConfig rollout problem normally appears as one of these symptoms:

```bash
oc get mcp
```

Example:

```text
NAME           CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
master         rendered-master-xxxxx                              True      False      False      3              3                   3                     0
worker         rendered-worker-yyyyy                              False     True       False      6              5                   5                     0
infra          rendered-infra-zzzzz                               False     True       True       3              2                   2                     1
logging        rendered-logging-aaaaa                             False     False      True       3              2                   2                     1
```

Interpretation:

- `UPDATED=False` means not all nodes in the pool are on the current rendered config.
- `UPDATING=True` means at least one node is currently moving toward the desired config.
- `DEGRADED=True` means MCO/MCD is blocked or a config failed.
- `DEGRADEDMACHINECOUNT>0` means one or more nodes are explicitly degraded.
- `READYMACHINECOUNT` tells how many nodes are updated and schedulable.
- `UPDATEDMACHINECOUNT` tells how many nodes have the pool's current rendered config.

## 2. Mental model: what actually happens during a MachineConfig rollout

A MachineConfig rollout has multiple layers. Troubleshooting becomes easy only when you separate them.

```text
MachineConfig / KubeletConfig / ContainerRuntimeConfig / ImageConfig / Proxy / FeatureSet
        |
        v
Machine Config Controller renders final config
        |
        v
MachineConfigPool points to rendered-<pool>-<hash>
        |
        v
Machine Config Daemon on each selected node notices desired config
        |
        v
Node gets cordoned
        |
        v
Pods are drained, unless update type does not require drain
        |
        v
MCD writes files / units / kubelet config / CRI-O config / OS changes
        |
        v
Node reboots if required
        |
        v
Node returns Ready
        |
        v
MCD verifies on-disk state and marks node Done
        |
        v
MCP counts become Updated=True, Updating=False, Degraded=False
```

In most disruptive MachineConfig changes, the MCO follows this node-level sequence:

1. cordon the node,
2. drain workloads,
3. apply the new host configuration,
4. reboot the node,
5. uncordon the node.

Some changes do not require drain or reboot, such as certain SSH key changes, pull secret updates, or automatic kubelet CA rotation. Still, you must always verify the actual rollout state because the behavior depends on the exact change type and OpenShift version.

## 3. Key components involved in rollout troubleshooting

### 3.1 Machine Config Operator namespace

Most MCO components run in:

```bash
openshift-machine-config-operator
```

Useful checks:

```bash
oc get pods -n openshift-machine-config-operator -o wide
oc get ds -n openshift-machine-config-operator
oc get deploy -n openshift-machine-config-operator
oc get co machine-config
oc describe co machine-config
```

Important components:

| Component | Role in rollout |
|---|---|
| `machine-config-controller` | watches MachineConfigs and pool definitions, renders configs, updates MCP status |
| `machine-config-daemon` | daemonset on nodes; applies config, drains/reboots node, validates state |
| `machine-config-server` | serves Ignition to new nodes joining the cluster |
| `machine-config-operator` | manages the operator components |
| `machine-os-builder` / layered image components | relevant when using custom layered RHCOS / on-cluster image builds |

### 3.2 MachineConfigPool

`MachineConfigPool` decides which nodes receive which rendered config.

Example custom infra pool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Important production rule:

- A node can have multiple node role labels.
- A node must effectively belong to only one MCP for MachineConfig management.
- Custom pools usually inherit worker MachineConfigs because their `machineConfigSelector` includes both `worker` and the custom role.
- Worker MachineConfigs often apply to custom worker-derived pools unless carefully scoped.

This is why a bad worker MachineConfig can unexpectedly roll out to infra, logging, monitoring, storage, GPU, or application node pools.

### 3.3 MachineConfig

A MachineConfig is an Ignition-based host configuration object.

Common uses:

- write host files,
- create systemd units or drop-ins,
- add kernel arguments,
- configure CRI-O registries,
- configure kubelet behavior through generated MachineConfigs,
- set container runtime configuration,
- trust custom registries,
- configure chrony, sysctl, audit, NetworkManager, or other OS-level behavior.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-custom-sysctl
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/sysctl.d/99-infra.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,bmV0LmlwdjQuaXBfZm9yd2FyZCA9IDEK
```

### 3.4 Rendered MachineConfig

The rendered config is the final merged result that MCO applies to the pool.

Check rendered configs:

```bash
oc get mc | grep rendered
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
oc get mc rendered-worker-xxxxx -o yaml
```

Rendered config tells you what MCO thinks the target state should be.

When troubleshooting, always compare:

- pool current rendered config,
- node current config annotation,
- node desired config annotation,
- actual on-disk state.

## 4. Dedicated node pools and why rollouts become complex

Cluster partitioning usually creates custom pools such as:

| Pool | Typical workloads | Rollout risk |
|---|---|---|
| `infra` | router, registry, ingress, internal platform services | route outage, registry pull failures |
| `logging` | Loki/Elasticsearch/Vector/Fluentd | log ingestion interruption, PVC reattachment issues |
| `monitoring` | Prometheus, Alertmanager, Thanos | alerting blind spots, scrape gaps |
| `storage` | ODF/Ceph/Rook, local storage | quorum risk, volume attach/detach delays |
| `gpu` | GPU workloads, device plugin, drivers | driver/kernel mismatch, device plugin failure |
| `app` | business applications | app downtime, PDB blocking drains |
| `perf` / `rt` | low-latency workloads | kernel args, tuned, CPU isolation risk |

MachineConfig rollout troubleshooting is more sensitive in these pools because each pool has a different operational tolerance.

For example:

- In `infra`, draining all router pods at once can break ingress.
- In `logging`, PVC-backed pods can delay drains.
- In `storage`, too much parallel disruption can break quorum.
- In `gpu`, a kernel or driver mismatch can make nodes Ready but unusable for GPU workloads.
- In `monitoring`, alerts might not fire during the exact incident you are troubleshooting.

Therefore, custom MCPs should usually use conservative `maxUnavailable: 1`, especially for infra, storage, logging, and monitoring pools.

## 5. Fast status triage commands

Run these first before changing anything.

### 5.1 Cluster operator health

```bash
oc get co machine-config
oc describe co machine-config
```

Look for:

- `Available=False`,
- `Progressing=True`,
- `Degraded=True`,
- messages mentioning `MCP`, `MCD`, `drain`, `render`, `pivot`, `reboot`, `kubelet`, or `content mismatch`.

### 5.2 MCP overview

```bash
oc get mcp -o wide
oc describe mcp <pool-name>
```

Useful JSONPath:

```bash
oc get mcp <pool-name> \
  -o jsonpath='Pool={.metadata.name}{"\n"}Paused={.spec.paused}{"\n"}Config={.status.configuration.name}{"\n"}Updated={.status.conditions[?(@.type=="Updated")].status}{"\n"}Updating={.status.conditions[?(@.type=="Updating")].status}{"\n"}Degraded={.status.conditions[?(@.type=="Degraded")].status}{"\n"}MachineCount={.status.machineCount}{"\n"}Ready={.status.readyMachineCount}{"\n"}UpdatedMachines={.status.updatedMachineCount}{"\n"}DegradedMachines={.status.degradedMachineCount}{"\n"}'
```

### 5.3 Node annotations

```bash
oc get node <node-name> -o jsonpath='Current={.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}Desired={.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}State={.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}Reason={.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Common node states:

| State | Meaning |
|---|---|
| `Done` | node has applied current desired config |
| `Working` | MCD is applying config |
| `Degraded` | MCD found drift or failed applying config |

### 5.4 MachineConfigDaemon pod for a node

```bash
NODE=<node-name>
MCD_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon \
  -o wide --no-headers | awk -v n="$NODE" '$7==n {print $1}')

echo "$MCD_POD"

oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon --tail=200
```

Follow logs during rollout:

```bash
oc logs -f -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon
```

### 5.5 Events

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
oc get events -n openshift-machine-config-operator --sort-by=.lastTimestamp
oc describe node <node-name>
oc describe mcp <pool-name>
```

### 5.6 MachineConfigNode status, if available

Newer OpenShift versions expose per-node MachineConfig status through `MachineConfigNode`.

```bash
oc get machineconfignodes
oc get machineconfignodes -o wide
oc describe machineconfignode <node-name>
```

Use this when available because it gives a cleaner per-node view of desired config, current config, pool, and update state.

## 6. How to identify exactly which node is blocking the rollout

Start with the degraded or updating pool.

```bash
POOL=infra

oc describe mcp $POOL
```

Then list nodes in that pool. For a role-based pool:

```bash
oc get nodes -l node-role.kubernetes.io/$POOL= -o wide
```

For a worker pool:

```bash
oc get nodes -l node-role.kubernetes.io/worker= -o wide
```

Print MachineConfig annotations for all nodes:

```bash
for n in $(oc get nodes -o name | cut -d/ -f2); do
  echo "==== $n ===="
  oc get node "$n" -o jsonpath='Ready={.status.conditions[?(@.type=="Ready")].status}{"\n"}Current={.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}Desired={.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}State={.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}Reason={.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}{"\n"}'
done
```

Find nodes where:

```text
currentConfig != desiredConfig
```

or:

```text
state = Degraded
```

or:

```text
Ready != True
```

Those nodes are the first troubleshooting targets.

## 7. Rollout failure decision tree

```text
MCP not Updated
|
+-- Is MCP paused?
|     +-- yes: unpause only during maintenance window
|     +-- no: continue
|
+-- Is MCP Degraded?
|     +-- yes: inspect oc describe mcp, node annotations, MCD logs
|     +-- no: continue
|
+-- Are nodes current != desired?
|     +-- yes: identify node state: Working / Degraded / NotReady
|     +-- no: check stale status, controller, or operator health
|
+-- Is node stuck at drain?
|     +-- yes: check PDBs, single replicas, local storage, unhealthy pods, topology spread, capacity
|
+-- Is node stuck after reboot?
|     +-- yes: check kubelet, CRI-O, systemd, kernel args, network, disk, certs
|
+-- Is node degraded due to content mismatch?
|     +-- yes: fix drift or force reapply current config
|
+-- Is rendered config wrong?
|     +-- yes: inspect MC labels, MCP selectors, lexicographic merge, generated KubeletConfig/ContainerRuntimeConfig
|
+-- Is MCO controller unhealthy?
|     +-- yes: inspect operator pods, logs, clusteroperator conditions
```

## 8. Troubleshooting scenario 1: MCP is paused

### Symptom

```bash
oc get mcp
```

shows:

```text
NAME     UPDATED   UPDATING   DEGRADED
infra    False     False      False
```

But nodes do not move to the new rendered config.

Check:

```bash
oc get mcp infra -o jsonpath='{.spec.paused}{"\n"}'
```

If output is:

```text
true
```

then the rollout is intentionally blocked.

### Why it happens

Admins often pause custom pools for canary updates, EUS updates, or maintenance windows. This is normal, but forgetting to unpause creates stale pools.

### Risk

A paused MCP does not apply MachineConfig changes to selected nodes. On long-running paused pools, this can also delay important automatically delivered configuration, including certificate-related updates depending on OpenShift version and component behavior.

### Fix

Unpause during an approved maintenance window:

```bash
oc patch mcp/infra --type=merge --patch '{"spec":{"paused":false}}'
```

Watch:

```bash
watch -n5 'oc get mcp infra; oc get nodes -l node-role.kubernetes.io/infra='
```

### Production note

Unpause one custom pool at a time:

```bash
oc patch mcp/infra --type=merge --patch '{"spec":{"paused":false}}'
# wait until infra complete
oc patch mcp/logging --type=merge --patch '{"spec":{"paused":false}}'
# wait until logging complete
oc patch mcp/monitoring --type=merge --patch '{"spec":{"paused":false}}'
```

Do not unpause all critical pools together unless you have enough cluster capacity and a tested rollback/recovery plan.

## 9. Troubleshooting scenario 2: wrong node selected into wrong pool

### Symptom

- A node receives an unexpected rendered config.
- A custom pool has more or fewer nodes than expected.
- Worker pool count drops unexpectedly after creating custom MCP.
- A node appears to be managed by a pool you did not intend.

Check:

```bash
oc get mcp
oc get nodes --show-labels
oc describe mcp infra
```

### Common causes

1. Node role label typo.
2. MCP `nodeSelector` too broad.
3. Two custom pools select the same node.
4. Node has a stale custom role label.
5. MachineConfig labels do not match intended pool.
6. Worker MachineConfigs are inherited by custom worker-derived pools.

### Validate pool selectors

```bash
oc get mcp infra -o yaml
```

Check:

```yaml
spec:
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
```

### Validate node labels

```bash
oc get node <node-name> --show-labels
```

### Fix wrong node label

Remove stale label:

```bash
oc label node <node-name> node-role.kubernetes.io/infra-
```

Add correct label:

```bash
oc label node <node-name> node-role.kubernetes.io/logging=
```

Then verify:

```bash
oc get mcp
oc describe mcp logging
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

### Senior admin advice

Never label production nodes into a new custom MCP without first checking what rendered config the pool will generate. A node might reboot as soon as MCO detects a new desired config.

Safer pattern:

1. Create MCP.
2. Pause MCP.
3. Label one canary node.
4. Inspect rendered config.
5. Unpause MCP during maintenance.
6. Validate.
7. Move remaining nodes.

## 10. Troubleshooting scenario 3: rendered config is not created or not changing

### Symptom

You create or edit a MachineConfig, but the MCP does not point to a new rendered config.

Check:

```bash
oc get mc
oc get mcp <pool> -o jsonpath='{.status.configuration.name}{"\n"}'
oc describe mcp <pool>
oc logs -n openshift-machine-config-operator deploy/machine-config-controller --tail=200
```

### Common causes

- MachineConfig has wrong role label.
- YAML is accepted by Kubernetes but ignored by desired pool because label selector does not match.
- KubeletConfig or ContainerRuntimeConfig `machineConfigPoolSelector` does not match the target MCP.
- Generated MachineConfig exists, but applies to another pool.
- Controller is degraded.
- Invalid Ignition structure or unsupported field.
- Name/order conflict creates unexpected merged output.

### Check MachineConfig labels

```bash
oc get mc <mc-name> -o jsonpath='{.metadata.labels}{"\n"}'
```

Expected for infra-specific config:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

Expected for worker-wide config:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

### Check generated configs

```bash
oc get mc --sort-by=.metadata.creationTimestamp
oc get mc | grep -E 'kubelet|container-runtime|99|rendered'
```

### Inspect rendered output

```bash
RENDERED=$(oc get mcp infra -o jsonpath='{.status.configuration.name}')
oc get mc "$RENDERED" -o yaml > /tmp/$RENDERED.yaml
```

Search inside rendered config:

```bash
grep -n "99-infra" /tmp/$RENDERED.yaml
grep -n "/etc/sysctl.d" /tmp/$RENDERED.yaml
grep -n "kubelet" /tmp/$RENDERED.yaml
```

### Fix

Correct labels or selectors, then watch for new rendered config:

```bash
oc label mc <mc-name> machineconfiguration.openshift.io/role=infra --overwrite
watch -n5 'oc get mcp infra -o wide'
```

## 11. Troubleshooting scenario 4: rollout stuck during drain

### Symptom

MCP stuck:

```text
UPDATED=False
UPDATING=True
DEGRADED=False or True
```

MCD logs show drain attempts, eviction failures, or timeout messages.

Check node:

```bash
NODE=<node-name>
oc describe node $NODE
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
```

Check MCD logs:

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide --no-headers | awk -v n="$NODE" '$7==n {print $1}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --tail=300 | egrep -i 'drain|evict|pdb|timeout|error|fail'
```

### Common drain blockers

| Blocker | What it looks like | Fix direction |
|---|---|---|
| strict PDB | `Cannot evict pod as it would violate the pod's disruption budget` | increase replicas, relax PDB, fix unavailable pods |
| single replica app with PDB minAvailable 1 | one pod cannot move | scale app to 2+ or adjust PDB temporarily |
| unhealthy replacement pod | eviction waits because replacement cannot become available | fix image, scheduling, PVC, quota, readiness |
| local storage / emptyDir sensitivity | drain waits or app cannot reschedule | ensure app supports restart, use correct drain strategy |
| no spare capacity | pod cannot schedule elsewhere | add capacity or reduce workload pressure |
| topology spread / anti-affinity too strict | replacement pod Pending | relax constraints or add node in required zone/pool |
| storage attach delay | pod stuck ContainerCreating | investigate CSI/ODF/storage events |
| daemonset confusion | daemonsets remain by design | ignore daemonsets unless DS itself is unhealthy |

### PDB analysis

```bash
oc get pdb -A
oc describe pdb -n <namespace> <pdb-name>
oc get pods -n <namespace> -o wide
oc describe pod -n <namespace> <pod-name>
```

Find pods on node with owners:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=$NODE \
  -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,OWNER:.metadata.ownerReferences[0].kind,READY:.status.containerStatuses[*].ready,PHASE:.status.phase'
```

### Safe fix pattern

1. Identify which pod cannot be evicted.
2. Identify controller and PDB.
3. Make the workload drainable.
4. Let MCO continue naturally.

Examples:

Scale deployment temporarily:

```bash
oc scale deploy/<deploy-name> -n <namespace> --replicas=2
```

Relax PDB temporarily:

```bash
oc patch pdb/<pdb-name> -n <namespace> --type=merge -p '{"spec":{"minAvailable":0}}'
```

After rollout, restore original PDB:

```bash
oc patch pdb/<pdb-name> -n <namespace> --type=merge -p '{"spec":{"minAvailable":1}}'
```

### Avoid dangerous shortcuts

Do not manually run aggressive drain commands against an MCO-managed node unless you understand the impact. Manual drain can fight MCO state, disrupt more pods than expected, or bypass application protection. For PDB issues, fix the workload or PDB first.

## 12. Troubleshooting scenario 5: node is NotReady after reboot

### Symptom

MCO applied config and rebooted the node, but node does not return Ready.

Check:

```bash
oc get nodes
oc describe node <node-name>
oc get csr
oc get pods -n openshift-machine-config-operator -o wide
```

If the node is accessible through `oc debug`:

```bash
oc debug node/<node-name>
chroot /host
systemctl status kubelet --no-pager
systemctl status crio --no-pager
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
journalctl -u NetworkManager -b --no-pager | tail -100
rpm-ostree status
exit
exit
```

If `oc debug` is not possible, use cloud console, BMC/iDRAC/iLO, serial console, or SSH if enabled and approved.

### Common causes after reboot

| Cause | Signal | Recovery direction |
|---|---|---|
| bad kubelet config | kubelet fails to start | inspect generated kubelet config, revert bad KubeletConfig |
| bad CRI-O config | crio fails, pods not running | revert ContainerRuntimeConfig or registry config |
| bad kernel arg | node boot issue or service failure | remove MachineConfig adding bad kernel arg |
| invalid systemd unit | boot slow/failure | disable/revert custom unit |
| DNS/proxy breakage | kubelet cannot reach API | fix node network, DNS, proxy, trust bundle |
| disk full | kubelet/crio errors | free space, investigate logs/images |
| certificate problem | kubelet TLS/bootstrap errors | check CSRs, CA rotation, paused pools |
| image pull/pivot failure | rpm-ostree or MCD pivot errors | check registry/network/pull secret |

### Kubelet-focused checks

```bash
oc debug node/<node-name> -- chroot /host bash -c '
  systemctl is-active kubelet
  journalctl -u kubelet -b --no-pager | tail -120
  ls -l /etc/kubernetes/kubelet.conf /var/lib/kubelet/config.json 2>/dev/null
'
```

### CRI-O-focused checks

```bash
oc debug node/<node-name> -- chroot /host bash -c '
  systemctl is-active crio
  journalctl -u crio -b --no-pager | tail -120
  crictl info 2>/dev/null | head -50
'
```

### Network-focused checks

```bash
oc debug node/<node-name> -- chroot /host bash -c '
  ip addr
  ip route
  cat /etc/resolv.conf
  nmcli con show
  curl -k https://api-int.$(oc get dns cluster -o jsonpath={.spec.baseDomain} 2>/dev/null):6443/version || true
'
```

Note: the command above might need adjustment because `oc` is not usually available inside the host chroot.

## 13. Troubleshooting scenario 6: node is Degraded due to configuration drift

### Symptom

```bash
oc get mcp
```

shows `DEGRADED=True` and `DEGRADEDMACHINECOUNT>0`.

`oc describe mcp <pool>` shows a message like:

```text
Node <node> is reporting: "content mismatch for file \"/etc/example.conf\""
```

or:

```text
unexpected on-disk state validating against rendered-worker-xxxxx
```

### What drift means

Configuration drift means the on-disk host state differs from what the currently applied MachineConfig says it should be.

Typical drift sources:

- admin manually edited a MachineConfig-managed file,
- troubleshooting changed a systemd unit directly on the node,
- permissions changed,
- a security hardening script modified `/etc`,
- a vendor agent changed a managed file,
- a previous emergency fix was done outside MCO.

### Confirm from MCP

```bash
oc describe mcp <pool-name>
```

Look for `NodeDegraded`, `content mismatch`, `unexpected mode`, `missing file`, or `unit mismatch`.

### Confirm from node annotation

```bash
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### Inspect file on node

```bash
oc debug node/<node-name>
chroot /host
ls -l /path/from/error
sha256sum /path/from/error
cat /path/from/error
exit
exit
```

### Inspect expected rendered config

```bash
RENDERED=$(oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}')
oc get mc $RENDERED -o yaml > /tmp/$RENDERED.yaml
```

Decode expected file if content is base64:

```bash
grep -n "path: /path/from/error" -A20 /tmp/$RENDERED.yaml
```

If the rendered content source is like:

```yaml
source: data:text/plain;charset=utf-8;base64,SGVsbG8K
```

Decode:

```bash
echo 'SGVsbG8K' | base64 -d
```

### Fix option A: restore file manually to expected content and permissions

```bash
oc debug node/<node-name>
chroot /host
vi /path/from/error
chmod 0644 /path/from/error
chown root:root /path/from/error
systemctl restart machine-config-daemon-host.service 2>/dev/null || true
exit
exit
```

Then wait:

```bash
watch -n5 'oc get mcp <pool-name>; oc get node <node-name>'
```

### Fix option B: force MCD to reapply current config

Use only when you are sure the rendered config is correct and you accept a reboot.

```bash
oc debug node/<node-name>
chroot /host
touch /run/machine-config-daemon-force
systemctl reboot
```

Important: forcing reapply causes node reboot. Use maintenance controls and workload protection.

### Fix option C: revert or supersede the bad MachineConfig

If the MachineConfig itself is wrong:

```bash
oc delete mc <bad-mc-name>
```

or create a corrected higher-order MachineConfig.

Then watch:

```bash
watch -n5 'oc get mcp <pool-name> -o wide'
```

### Senior admin advice

Do not directly edit MCO-managed files on RHCOS nodes except as a temporary emergency action. Permanent host changes must be represented through MachineConfig, KubeletConfig, ContainerRuntimeConfig, Tuned, or the proper OpenShift API.

## 14. Troubleshooting scenario 7: invalid MachineConfig content

### Symptom

MCP becomes degraded after applying a new MachineConfig. MCD logs mention file write errors, systemd errors, invalid path, invalid mode, bad data URL, or failed validation.

### Common mistakes

| Mistake | Example | Impact |
|---|---|---|
| wrong base64 | malformed `source: data:...base64` | MCD cannot decode/apply |
| wrong file mode | `mode: 644` instead of decimal/octal expected by schema handling | permissions wrong or validation issue |
| missing parent directory | writing nested path without directory support | file write failure |
| bad systemd unit | syntax error in unit | service fails, node may degrade |
| wrong role label | intended infra, applied to all workers | unexpected rollout |
| duplicate path in multiple MCs | same file defined more than once | final rendered content not what you expect |
| bad kernel argument | unsupported arg or typo | boot or kubelet issue |
| bad kubelet setting | invalid generated kubelet config | kubelet fails or node NotReady |

### Validate before applying

Use client/server dry run where possible:

```bash
oc apply --dry-run=server -f machineconfig.yaml
```

Render inspection after apply:

```bash
oc get mcp <pool> -o jsonpath='{.status.configuration.name}{"\n"}'
oc get mc rendered-<pool>-<hash> -o yaml
```

### Validate base64

```bash
echo '<base64-string>' | base64 -d
```

### Safer file content creation

```bash
CONTENT=$(cat ./99-custom.conf | base64 -w0)
cat <<EOF2 > mc.yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-custom-file
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/example/99-custom.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,$CONTENT
EOF2
```

### Fix

If config is bad and rollout has started:

1. Stop further damage by pausing affected custom pool if appropriate.
2. Identify whether one or many nodes have applied it.
3. Delete or correct the bad MachineConfig.
4. Unpause and allow MCO to render a corrected config.
5. Recover degraded nodes using drift repair or force reapply if needed.

Pause:

```bash
oc patch mcp/<pool> --type=merge --patch '{"spec":{"paused":true}}'
```

Delete bad MC:

```bash
oc delete mc <bad-mc-name>
```

Unpause:

```bash
oc patch mcp/<pool> --type=merge --patch '{"spec":{"paused":false}}'
```

## 19. Troubleshooting scenario 12: MCP stuck because maxUnavailable/capacity is too restrictive

### Symptom

The rollout progresses very slowly or appears stuck because only one node can update at a time and drains take long.

Check:

```bash
oc get mcp <pool> -o yaml | grep -A3 maxUnavailable
oc get pods -A -o wide | grep <node-name>
oc adm top nodes
oc get pdb -A
```

### Understanding `maxUnavailable`

`maxUnavailable` controls how many nodes in a pool can be unavailable during rollout. Default is commonly `1` for MCPs. This is safe but slower.

### Dedicated pool guidance

| Pool | Suggested approach |
|---|---|
| `master` | keep one at a time; do not aggressively increase |
| `infra` | usually `1`; maintain router/registry redundancy |
| `logging` | usually `1`; storage-backed workloads may drain slowly |
| `monitoring` | usually `1`; protect alerting visibility |
| `storage` | usually `1`; respect quorum and ODF guidance |
| `app` | can be >1 only if apps have redundancy and capacity |
| `gpu` | usually `1`; validate driver/device plugin after each node |

### Temporary increase example

For a large application pool with enough spare capacity:

```bash
oc patch mcp/app --type=merge --patch '{"spec":{"maxUnavailable":2}}'
```

After rollout:

```bash
oc patch mcp/app --type=merge --patch '{"spec":{"maxUnavailable":1}}'
```

### Warning

Do not increase control plane `maxUnavailable` aggressively. For master/control plane nodes, preserve quorum and follow OpenShift guidance.

## 20. Troubleshooting scenario 13: worker MachineConfig unexpectedly affects custom pools

### Symptom

You create:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

and expect it to affect only generic workers, but infra/logging/app custom pools also roll out.

### Why

Custom worker-derived pools often select both `worker` and custom role MachineConfigs:

```yaml
machineConfigSelector:
  matchExpressions:
  - key: machineconfiguration.openshift.io/role
    operator: In
    values:
    - worker
    - infra
```

This means worker-level MachineConfigs are inherited by the custom pool.

### Prevention

For changes that must not hit custom pools:

- create a separate custom pool for generic application workers, or
- label custom pool-specific MachineConfigs only with the custom role, or
- design pool hierarchy carefully before production rollout.

### Troubleshooting commands

```bash
for p in $(oc get mcp -o name | cut -d/ -f2); do
  echo "==== $p ===="
  oc get mcp $p -o jsonpath='{.spec.machineConfigSelector}{"\n"}{.status.configuration.name}{"\n"}'
done
```

Inspect rendered configs for inclusion of a specific file:

```bash
for r in $(oc get mc -o name | grep rendered | cut -d/ -f2); do
  echo "==== $r ===="
  oc get mc $r -o yaml | grep -q '/etc/example.conf' && echo "contains /etc/example.conf"
done
```

## 27. Emergency containment

Sometimes the rollout is actively damaging nodes. The goal is to stop additional nodes from consuming the bad desired config while you repair.

### 27.1 Pause affected custom pool

```bash

```

### 27.2 Identify blast radius

```bash

.metadata.name,
.metadata.labels,
(.metadata.annotations["machineconfiguration.openshift.io/currentConfig"] // "-"),
(.metadata.annotations["machineconfiguration.openshift.io/desiredConfig"] // "-"),
(.metadata.annotations["machineconfiguration.openshift.io/state"] // "-")

```

Simpler:

```bash

oc get nodes -o wide
```


## 28. What not to do

Avoid these common production mistakes:

1. Do not delete random rendered MachineConfigs.
2. Do not manually edit many RHCOS nodes to “make them match”.
3. Do not unpause all custom MCPs at once after a long pause.
4. Do not increase `maxUnavailable` on master/control plane to speed things up.
5. Do not ignore `DEGRADEDMACHINECOUNT=1`; one degraded node can block upgrades.
6. Do not assume `Ready=True` means MachineConfig rollout completed.
7. Do not assume a worker MachineConfig affects only generic workers.
8. Do not manually reboot multiple control plane or storage nodes together.
9. Do not bypass PDBs before understanding application impact.
10. Do not troubleshoot only from `oc get nodes`; always check node annotations and MCD logs.

## 29. Production root cause matrix

| Symptom | Likely root cause | First command | Fix direction |
|---|---|---|---|
| MCP `UPDATED=False`, `UPDATING=False`, `DEGRADED=False` | paused pool | `oc get mcp <p> -o yaml | grep paused` | unpause during window |

## 31. Example end-to-end incident: app MCP stuck draining due to PDB

### Situation

```bash
oc get mcp app
```

shows:

```text
UPDATED=False UPDATING=True DEGRADED=False
```

MCD logs:

```text
Cannot evict pod as it would violate the pod's disruption budget
```

### Step 1: identify node being updated

```bash
for n in $(oc get nodes -l node-role.kubernetes.io/app= -o name | cut -d/ -f2); do
```


### Step 3: identify PDB

```bash
oc get pdb -A
```

```yaml
spec:
  minAvailable: 1
```

```bash
oc scale deploy/payments-api -n payments --replicas=1
```

Senior note: if the app truly requires high availability, keep replicas at 2+ and fix the design instead of reverting to a fragile single replica with strict PDB.

## 32. Example end-to-end incident: GPU pool Ready but GPU workloads fail after rollout

### Situation

MCP says updated:

```bash
oc get mcp gpu
```

But GPU pods stay Pending or device plugin reports no devices.

### Checks

```bash
oc get nodes -l node-role.kubernetes.io/gpu= -o wide
oc describe node <gpu-node> | egrep -i 'nvidia|gpu|allocatable|capacity' -A5
oc get pods -A -o wide | egrep -i 'gpu|nvidia|device'
```

On node:

```bash
oc debug node/<gpu-node> -- chroot /host bash -c '
  uname -r
  lsmod | egrep -i "nvidia|vfio" || true
  journalctl -b --no-pager | egrep -i "nvidia|gpu|driver|kernel" | tail -200
'
```

Possible root causes:

- kernel changed but GPU driver not compatible,
- driver daemonset failed after reboot,
- node labels/taints changed,
- device plugin not running,
- workload RuntimeClass/nodeSelector mismatch,
- GPU operator needs reconciliation.

MachineConfig rollout can be successful at the OS level while workload-specific validation fails. For specialized pools, always validate the pool’s business function, not only MCP status.

## 33. How to design MachineConfigs to reduce rollout incidents

### 33.1 Use pool-specific role labels

For infra-only changes:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

For logging-only changes:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: logging
```

Avoid putting everything under `worker` unless you really intend all worker-derived pools to inherit it.

### 33.2 Use naming order intentionally

MachineConfigs are merged in name order within a role. Use consistent prefixes:

```text
00-worker-base
50-worker-runtime
80-worker-kubelet
99-worker-final-overrides
```

For custom pools:

```text
99-infra-sysctl
99-logging-crio
99-gpu-kernelargs
```

Do not create confusing names like:

```text
test
new-config
final2
abc
```

### 33.3 Keep MachineConfigs small and single-purpose

Bad:

```text
99-worker-everything
```

Good:

```text
99-worker-registry-trust
99-worker-sysctl-forwarding
99-worker-custom-systemd-unit
```

Small MachineConfigs make root cause isolation easier.

### 33.4 Test on canary MCP

Do not test a kernel arg, kubelet config, CRI-O config, or systemd unit on the entire worker fleet first.

### 33.5 Avoid manual host drift

For permanent changes, use OpenShift APIs:

- `MachineConfig` for host files/systemd/kernel args,
- `KubeletConfig` for kubelet,
- `ContainerRuntimeConfig` for CRI-O,
- `Image` config for registry trust/mirrors,
- `Proxy` config for cluster proxy,
- `Tuned` for performance tuning,
- Operators for workload-specific host integration.

## 34. Senior-level troubleshooting checklist

Use this checklist during an incident.

### 34.1 Identify scope

```bash
oc get co
oc get mcp -o wide
oc get nodes -o wide
```

Questions:

- Is only one pool affected?
- Is master/control plane affected?
- Is the issue during upgrade or normal config change?
- Is this a custom pool or default worker pool?
- Are apps down or only rollout stuck?

### 34.2 Identify source change

```bash
oc get mc --sort-by=.metadata.creationTimestamp
oc get kubeletconfig
oc get containerruntimeconfig
oc get image.config.openshift.io/cluster -o yaml
oc get proxy/cluster -o yaml
```

Questions:

- What changed recently?
- Which pool label does it target?
- Did it generate a new rendered config?
- Did it affect more pools than expected?

### 34.3 Identify blocking node

```bash
oc describe mcp <pool>
oc get nodes -l node-role.kubernetes.io/<role>= -o wide
```

Check annotations:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 34.4 Identify phase

| Phase | Evidence |
|---|---|
| render | no new rendered config or controller logs show render error |
| selection | node/pool counts unexpected |
| drain | MCD logs show eviction/drain attempts |
| apply | MCD logs show file/systemd/kubelet/crio errors |
| reboot | node NotReady or reboot errors |
| validation | content mismatch / drift / degraded |
| workload validation | MCP healthy but app/device/storage broken |

### 34.5 Fix minimally

- Fix root cause, not symptoms.
- Pause only affected custom pool if needed.
- Avoid broad worker changes during incident.
- Avoid manual node edits unless necessary.
- Keep notes of every command and timestamp.

### 34.6 Validate completion

```bash
oc get mcp -o wide
oc get co machine-config
oc get nodes
oc get clusterversion
```

Then validate workload function:

```bash
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp | tail -100
```

## 36. Interview / exam-style explanation

If asked to explain MachineConfig rollout troubleshooting as a senior OpenShift administrator, answer like this:

A MachineConfig rollout is controlled by the Machine Config Operator. The controller renders the final config for each MachineConfigPool, and the Machine Config Daemon on each node applies it. For most host-level changes, the node is cordoned, drained, updated, rebooted, and uncordoned. Troubleshooting starts from `oc get mcp` and `oc describe mcp`, then narrows down to the node whose current and desired config annotations differ or whose state is `Degraded`. After that, I check MCD logs on the daemon pod running on that node and determine whether the failure is in render, node selection, drain, apply, reboot, or validation. In dedicated pools, I also verify pool selectors and inherited worker MachineConfigs because worker-level changes can affect custom pools such as infra, logging, monitoring, GPU, and storage. For recovery, I avoid deleting rendered configs or manually editing nodes unless necessary. I fix the root cause: unpause the pool, correct selectors, make workloads drainable, repair config drift, revert bad KubeletConfig/ContainerRuntimeConfig/MachineConfig, or recover node services. Finally, I validate `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`, node Ready status, and workload functionality.

## 37. Real-world best practices

1. Always check MCP status before and after any MachineConfig change.
2. Never apply risky MachineConfigs directly to all workers first.
3. Use canary pools for kernel args, kubelet tuning, CRI-O tuning, and systemd changes.
4. Keep `maxUnavailable` conservative for infra, storage, logging, monitoring, and control plane pools.
5. Validate PDBs before maintenance windows.
6. Do not leave MCPs paused for long periods without tracking.
7. Keep MachineConfigs small, named, documented, and pool-specific.
8. Track every MachineConfig change in GitOps where possible.
9. Treat `DEGRADED=True` as an incident, even if applications are still running.
10. Validate actual pool function after rollout, not only MCP status.

## 39. Final summary

MachineConfig rollout troubleshooting is about identifying the exact failure phase:

```text
render -> select pool -> cordon -> drain -> apply -> reboot -> validate -> workload test
```

For dedicated node pools, most serious incidents come from:

- wrong MCP selectors,
- worker MachineConfigs inherited by custom pools,
- paused pools forgotten after maintenance,
- PDB/capacity drain failures,
- config drift from manual host changes,
- bad kubelet/CRI-O/systemd/kernel configuration,
- node reboot or OS pivot failures.

The senior administrator approach is:

1. read MCP status,
2. identify the exact node,
3. compare current vs desired config,
4. inspect MCD logs,
5. classify the failure phase,
6. fix the root cause safely,
7. validate both MCP health and workload health.
