# Worker Pool Customization in OpenShift

**Topic:** Cluster Partitioning and Dedicated Node Pools  
**Audience:** Advanced OpenShift Administration / DO380-level operations  
**Experience level:** Written for an administrator with around 10 years of Linux, Kubernetes, OpenShift, infrastructure, and production operations experience  
**Focus:** Designing, creating, customizing, operating, troubleshooting, and upgrading dedicated worker pools in Red Hat OpenShift Container Platform 4.x

---

## 1. Executive Summary

Worker pool customization is the practice of dividing OpenShift compute capacity into logical and operationally distinct groups of nodes. These groups can be used for infrastructure workloads, monitoring, logging, storage, GPU workloads, high-memory workloads, latency-sensitive applications, security-sensitive workloads, batch jobs, or tenant-specific workloads.

In OpenShift, the word **pool** can mean different things depending on the layer you are working on:

| Layer | OpenShift/Kubernetes object | Purpose |
|---|---|---|
| Provisioning layer | `MachineSet`, `Machine`, `MachineAutoscaler`, `ClusterAutoscaler` | Creates and scales compute nodes on supported platforms. |
| Configuration layer | `MachineConfigPool`, `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig`, `MachineOSConfig` | Applies host OS, kubelet, CRI-O, kernel, systemd, file, and image-level configuration to nodes. |
| Scheduling layer | Node labels, taints, tolerations, `nodeSelector`, node affinity, topology spread, project node selectors | Decides which workloads can run on which nodes. |
| Operational layer | PDBs, drain behavior, `maxUnavailable`, paused MCPs, upgrade sequencing, monitoring | Controls safe maintenance and upgrade behavior. |

A mature OpenShift administrator must understand that **dedicated node pools are not created by one object only**. A reliable pool design normally combines:

1. A **MachineSet** or manual node provisioning strategy.
2. A **MachineConfigPool** to manage node configuration as a unit.
3. A consistent **node role label** such as `node-role.kubernetes.io/infra`, `node-role.kubernetes.io/logging`, or `node-role.kubernetes.io/app-gold`.
4. Optional **taints** to repel unrelated workloads.
5. Workload-side **tolerations**, `nodeSelector`, or node affinity to attract the right workloads.
6. Pool-specific **kubelet**, **CRI-O**, **kernel**, **systemd**, and **OS file** configuration.
7. Clear operating rules for upgrades, reboots, drains, and troubleshooting.

## 2. Why Customize Worker Pools?

OpenShift clusters often start with a default `worker` pool. That is sufficient for small or simple environments, but production clusters usually need finer partitioning.

Common reasons to customize worker pools:

| Requirement | Why a custom pool helps |
|---|---|
| Infrastructure workload isolation | Routers, registry, monitoring, logging, and operators can be kept away from application workloads. |
| Noisy-neighbor control | Batch, CI/CD, JVM, analytics, and high-I/O workloads can be isolated from latency-sensitive apps. |
| Hardware specialization | GPU, high-memory, high-CPU, local NVMe, RDMA, SR-IOV, or storage nodes need unique labels and configuration. |
| Different kubelet settings | Some pools might need different `maxPods`, eviction thresholds, reserved CPU/memory, or CPU manager policy. |
| Different CRI-O settings | Some workloads need different PID limits, log settings, runtime options, or image behavior. |
| Different OS/kernel tuning | Kernel arguments, sysctl, systemd units, tuned profiles, or custom files can be targeted to a pool. |
| Compliance separation | PCI, regulated, restricted, or internal workloads can be constrained to dedicated hosts. |
| Operational blast-radius control | A bad node-level change can be tested on a small custom pool before applying to all workers. |
| Upgrade sequencing | Different pools can be observed and controlled independently during machine config rollouts. |
| Cost control | Autoscaling can be enabled per machine set or per hardware type. |

A well-designed cluster partitioning model gives the platform team control over **where workloads run**, **how nodes are configured**, **how disruption is managed**, and **how capacity scales**.

## 3. Important Concepts Before Implementation

### 3.1 Default Pools

Every standard OpenShift 4.x cluster starts with at least these MachineConfigPools:

```bash
oc get mcp
```

Typical output:

```text
NAME     CONFIG                                            UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT
master   rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx   True      False      False      3              3
worker   rendered-worker-yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy   True      False      False      3              3
```

The default pools are:

- `master` or control plane pool
- `worker` pool

In OpenShift documentation and object names, the control plane pool is often still represented as `master` in MachineConfigPool objects.

### 3.2 What Is a MachineConfigPool?

A `MachineConfigPool` groups nodes that receive the same rendered machine configuration.

The Machine Config Operator, or MCO, watches MachineConfigPools and applies rendered configurations to matching nodes. A pool is selected through:

- `spec.nodeSelector`: selects nodes by node labels.
- `spec.machineConfigSelector`: selects MachineConfig objects by MachineConfig labels.

A simplified example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: app-gold
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - app-gold
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/app-gold: ""
  maxUnavailable: 1
```

This says:

- Select nodes labeled `node-role.kubernetes.io/app-gold=""`.
- Apply base worker machine configs.
- Also apply MachineConfigs labeled `machineconfiguration.openshift.io/role=app-gold`.
- Update one node at a time.

### 3.3 Custom Pools Inherit from Worker

A custom worker pool normally inherits from the default worker pool. This is very important.

If you create a custom MCP named `infra`, `logging`, `storage`, or `app-gold`, it should normally include both:

```yaml
values:
- worker
- app-gold
```

This means the custom pool receives standard worker configuration plus its own pool-specific configuration.

Do **not** try to create a completely independent custom pool that does not inherit from `worker`. OpenShift's Machine Config Operator model expects custom pools to inherit worker configuration.

### 3.4 A Node Can Belong to Only One MachineConfigPool

A node can have multiple role labels, for example:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

However, for MCO management, a node belongs to only one MachineConfigPool.

If a node matches a custom MCP such as `infra`, the custom MCP takes priority over the generic `worker` MCP. This allows dual-labeled nodes such as `worker,infra` to still be managed by the custom `infra` MCP when that pool exists.

### 3.5 MachineSet Is Not the Same as MachineConfigPool

A common production mistake is confusing **MachineSet** and **MachineConfigPool**.

| Object | Namespace | Main job |
|---|---|---|
| `MachineSet` | `openshift-machine-api` | Creates cloud/virtual machine instances. |
| `Machine` | `openshift-machine-api` | Represents one infrastructure machine. |
| `Node` | cluster-scoped | Kubernetes node registered by kubelet. |
| `MachineConfigPool` | cluster-scoped | Groups nodes for host-level configuration. |
| `MachineConfig` | cluster-scoped | Defines host-level configuration. |

A MachineSet can create nodes with labels and taints, but it does not directly apply OS-level machine configuration. The MachineConfigPool is what controls OS/kubelet/CRI-O/systemd/kernel-level configuration.

### 3.6 Scheduling Isolation Is Not the Same as Configuration Isolation

Labeling a node for scheduling does not automatically create a custom configuration pool.

For example:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
```

This label helps scheduling and node role identification. But unless an `infra` MachineConfigPool exists, the node is still managed as a default worker by the MCO.

Similarly, creating an MCP does not automatically stop user workloads from scheduling on that node. You need taints, selectors, affinity, namespace configuration, or workload policy to control scheduling.

## 4. Worker Pool Customization Design Model

Think of worker pool customization in four dimensions.

### 4.1 Capacity Dimension

Questions:

- How many nodes are required?
- Which zones should contain the pool?
- Should each availability zone have a separate MachineSet?
- Should the pool autoscale?
- Should the pool scale to zero?
- What instance type or hardware profile is needed?
- What storage class constraints exist?
- Are there persistent workloads that require zone-aware placement?

Example pool layout:

| Pool | Nodes | Zones | Purpose |
|---|---:|---|---|
| `worker` | 6 | zone-a, zone-b, zone-c | General apps |
| `infra` | 3 | zone-a, zone-b, zone-c | Router, registry, monitoring operators |
| `logging` | 3 | zone-a, zone-b, zone-c | Loki/Elasticsearch/collector workloads |
| `app-gold` | 6 | zone-a, zone-b, zone-c | Critical production apps |
| `batch` | 0-20 | any | Autoscaled batch jobs |
| `gpu` | 0-4 | selected zones | GPU workloads |

### 4.2 Configuration Dimension

Questions:

- Does this pool need different kubelet configuration?
- Does this pool need different CRI-O configuration?
- Does this pool need specific kernel arguments?
- Does this pool need sysctl tuning?
- Does this pool need custom systemd units?
- Does this pool need a custom layered RHCOS image?
- Should the pool be used as a canary before larger rollout?

Example:

| Pool | Configuration customization |
|---|---|
| `infra` | Higher reserved CPU/memory for platform components; conservative `maxUnavailable`. |
| `logging` | Higher PID limit, disk tuning, larger root disk, maybe special storage layout. |
| `app-gold` | CPU manager, topology manager, reserved CPUs, tuned profile. |
| `batch` | Higher pod density, aggressive overcommit, autoscaling. |
| `gpu` | GPU driver/operator requirements, taints, runtime class, special hardware labels. |

### 4.3 Scheduling Dimension

Questions:

- Which workloads should be allowed onto the pool?
- Which workloads should be prevented?
- Are taints required?
- Do workloads need tolerations?
- Should project-level node selectors be used?
- Should node affinity be required or preferred?
- Should topology spread constraints be enforced?

Example:

```text
infra node taint:
node-role.kubernetes.io/infra=reserved:NoSchedule

logging node taint:
dedicated=logging:NoSchedule

app-gold node taint:
dedicated=app-gold:NoSchedule
```

Application pods must then provide matching tolerations and selectors.

### 4.4 Operations Dimension

Questions:

- How many nodes can reboot at one time?
- What PDBs protect workloads during MCO drains?
- What is the maintenance window?
- How will failed MCO updates be detected?
- How will degraded pools be recovered?
- How will nodes be moved in or out of pools?
- What is the rollback plan?

Example policy:

| Pool | `maxUnavailable` | Maintenance approach |
|---|---:|---|
| `infra` | 1 | Update one node at a time. Check router, registry, monitoring after each wave. |
| `logging` | 1 | Ensure logging quorum before reboot. |
| `app-gold` | 1 | Use PDBs and topology spread. Drain only during approved window. |
| `batch` | 20% | Higher disruption accepted. |
| `gpu` | 1 | Coordinate with long-running ML jobs. |

## 5. Naming and Labeling Standards

A production cluster should have clear naming standards.

### 5.1 Recommended Node Role Labels

Use role labels for pools:

```text
node-role.kubernetes.io/infra=
node-role.kubernetes.io/logging=
node-role.kubernetes.io/monitoring=
node-role.kubernetes.io/storage=
node-role.kubernetes.io/app-gold=
node-role.kubernetes.io/batch=
node-role.kubernetes.io/gpu=
```

The empty value is normal for Kubernetes node role labels.

### 5.2 Recommended Additional Labels

Role labels are useful, but operational labels give more control:

```text
workload.openshift.io/class=infra
workload.openshift.io/tier=gold
platform.example.com/pool=app-gold
platform.example.com/owner=platform-team
topology.kubernetes.io/zone=zone-a
node.kubernetes.io/instance-type=m6i.2xlarge
```

Use role labels for OpenShift pool identity and custom labels for business or scheduling policy.

### 5.3 Label Rules

Good labels:

```text
node-role.kubernetes.io/app-gold=
platform.example.com/pool=app-gold
workload.openshift.io/tier=gold
```

Bad labels:

```text
app=production
team=all
node=fast
special=yes
```

Why the bad labels are bad:

- Too generic.
- Likely to collide with application labels.
- Hard to understand operationally.
- Not clearly owned by the platform team.

## 6. Reference Architecture: Dedicated Worker Pools

### 6.1 Example Target State

```text
OpenShift Cluster
├── Control plane nodes
│   └── MCP: master
│
├── General application workers
│   └── MCP: worker
│
├── Infrastructure nodes
│   ├── MCP: infra
│   ├── Node role: worker,infra
│   ├── Taint: node-role.kubernetes.io/infra=reserved:NoSchedule
│   └── Workloads: ingress router, registry, monitoring, logging operators
│
├── Logging nodes
│   ├── MCP: logging
│   ├── Node role: worker,logging
│   ├── Taint: dedicated=logging:NoSchedule
│   └── Workloads: Loki/Elasticsearch/collector/storage-heavy logging components
│
├── Gold app nodes
│   ├── MCP: app-gold
│   ├── Node role: worker,app-gold
│   ├── Taint: dedicated=app-gold:NoSchedule
│   └── Workloads: critical production applications
│
└── Batch nodes
    ├── MCP: batch
    ├── Node role: worker,batch
    ├── Taint: dedicated=batch:NoSchedule
    └── Workloads: CI/CD, data processing, temporary compute
```

### 6.2 Why Keep the `worker` Label?

For infrastructure-style custom nodes, it is common to keep both labels:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

This dual-label model is practical because:

- The node remains recognizable as a compute node.
- If no custom MCP selects the custom label, the default worker MCP can still manage it.
- OpenShift subscription and platform reporting can identify infra nodes correctly when they are used only for supported infrastructure workloads.
- You avoid accidentally creating unmanaged nodes.

Do not casually remove the `worker` label. If you remove it, make sure a custom MCP selects the remaining role label. A node with only a custom role label and no matching MCP can fall outside normal MCO management.

## 7. End-to-End Implementation: Create a Custom `app-gold` Worker Pool

This section shows a full implementation pattern.

### 7.1 Check Existing Nodes and Pools

```bash
oc get nodes
oc get nodes --show-labels
oc get mcp
oc get mc
```

Useful formatted view:

```bash
oc get nodes -L node-role.kubernetes.io/worker,node-role.kubernetes.io/infra,node-role.kubernetes.io/app-gold,topology.kubernetes.io/zone
```

Check current MachineSets:

```bash
oc get machinesets -n openshift-machine-api
```

Check machines and nodes:

```bash
oc get machines -n openshift-machine-api
oc get nodes -o wide
```

### 7.2 Decide Pool Identity

For this example:

| Item | Value |
|---|---|
| Pool name | `app-gold` |
| Node role label | `node-role.kubernetes.io/app-gold=` |
| Taint | `dedicated=app-gold:NoSchedule` |
| MCP name | `app-gold` |
| MachineConfig role | `app-gold` |
| Workload selector | `nodeSelector: node-role.kubernetes.io/app-gold: ""` |

### 7.3 Create the MachineConfigPool

Create `mcp-app-gold.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: app-gold
  labels:
    pools.operator.machineconfiguration.openshift.io/app-gold: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - app-gold
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/app-gold: ""
  maxUnavailable: 1
```

Apply it:

```bash
oc apply -f mcp-app-gold.yaml
```

Verify:

```bash
oc get mcp app-gold
oc describe mcp app-gold
```

At this point the pool probably has zero nodes until nodes are labeled.

### 7.4 Label Existing Nodes into the Pool

For an existing node:

```bash
oc label node <node-name> node-role.kubernetes.io/app-gold=
```

Example:

```bash
oc label node worker-a-1 node-role.kubernetes.io/app-gold=
```

Verify node labels:

```bash
oc get node worker-a-1 --show-labels
oc get nodes -L node-role.kubernetes.io/app-gold
```

Check MCP membership:

```bash
oc get mcp app-gold
oc describe mcp app-gold
```

The MCO may drain and reboot the node if the rendered config differs from the previous worker configuration.

### 7.5 Apply Taint to Prevent General Workloads

```bash
oc adm taint nodes -l node-role.kubernetes.io/app-gold dedicated=app-gold:NoSchedule
```

Verify:

```bash
oc describe node <node-name> | grep -i taints -A2
```

Expected:

```text
Taints: dedicated=app-gold:NoSchedule
```

### 7.6 Create a Test Namespace and Workload

```bash
oc new-project gold-test
```

Create `gold-app.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gold-nginx
  namespace: gold-test
spec:
  replicas: 2
  selector:
    matchLabels:
      app: gold-nginx
  template:
    metadata:
      labels:
        app: gold-nginx
    spec:
      nodeSelector:
        node-role.kubernetes.io/app-gold: ""
      tolerations:
      - key: dedicated
        operator: Equal
        value: app-gold
        effect: NoSchedule
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: nginx
        image: registry.access.redhat.com/ubi9/nginx-120
        ports:
        - containerPort: 8080
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop:
            - ALL
```

Apply:

```bash
oc apply -f gold-app.yaml
```

Verify placement:

```bash
oc get pods -n gold-test -o wide
oc describe pod -n gold-test -l app=gold-nginx
```

All pods should be scheduled on `app-gold` nodes only.

### 7.7 Test Negative Scheduling

Create a pod without toleration but with `app-gold` selector:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: no-toleration-test
  namespace: gold-test
spec:
  nodeSelector:
    node-role.kubernetes.io/app-gold: ""
  containers:
  - name: test
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
```

Apply:

```bash
oc apply -f no-toleration-test.yaml
```

Check events:

```bash
oc describe pod no-toleration-test -n gold-test
```

You should see scheduling failure because the node has a taint and the pod does not tolerate it.

Delete the test pod:

```bash
oc delete pod no-toleration-test -n gold-test
```

## 8. Creating Custom Pools with MachineSets

For production, you usually want MachineSets to create dedicated nodes automatically with the right labels and taints.

### 8.1 Inspect an Existing MachineSet

```bash
oc get machinesets -n openshift-machine-api
oc get machineset <machineset-name> -n openshift-machine-api -o yaml > base-machineset.yaml
```

Find cluster infrastructure ID:

```bash
oc get infrastructure cluster -o jsonpath='{.status.infrastructureName}{"\n"}'
```

### 8.2 MachineSet Label and Taint Placement

In a MachineSet, node labels and taints are usually placed under:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/app-gold: ""
          platform.example.com/pool: app-gold
      taints:
      - key: dedicated
        value: app-gold
        effect: NoSchedule
```

The provider-specific section varies by platform:

- AWS
- Azure
- Google Cloud
- vSphere
- RHOSP
- Bare metal through Machine API where supported

Do not blindly copy a MachineSet between platforms. Copy from an existing worker MachineSet in the same cluster and modify only the required fields.

### 8.3 Example MachineSet Customization Pattern

General workflow:

```bash
oc get machinesets -n openshift-machine-api
oc get machineset <existing-worker-machineset> -n openshift-machine-api -o yaml > app-gold-machineset.yaml
```

Edit these fields:

```yaml
metadata:
  name: <clusterid>-app-gold-<zone>
  namespace: openshift-machine-api
spec:
  replicas: 1
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-cluster: <clusterid>
      machine.openshift.io/cluster-api-machineset: <clusterid>-app-gold-<zone>
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-cluster: <clusterid>
        machine.openshift.io/cluster-api-machine-role: app-gold
        machine.openshift.io/cluster-api-machine-type: app-gold
        machine.openshift.io/cluster-api-machineset: <clusterid>-app-gold-<zone>
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/worker: ""
          node-role.kubernetes.io/app-gold: ""
          platform.example.com/pool: app-gold
      taints:
      - key: dedicated
        value: app-gold
        effect: NoSchedule
```

Then apply:

```bash
oc apply -f app-gold-machineset.yaml
```

Watch machine creation:

```bash
oc get machines -n openshift-machine-api -w
oc get nodes -w
oc get mcp app-gold -w
```

### 8.4 Zone-Aware MachineSets

For highly available pools, create one MachineSet per zone.

Example:

```text
clusterid-app-gold-zone-a
clusterid-app-gold-zone-b
clusterid-app-gold-zone-c
```

Recommended minimums:

| Pool type | Recommended placement |
|---|---|
| `infra` | At least 3 nodes across 3 zones where possible. |
| `logging` | At least 3 nodes for quorum-based logging stacks. |
| `app-gold` | At least 2 or 3 zones depending on app HA requirement. |
| `batch` | Can be concentrated or autoscaled depending on cost model. |
| `gpu` | Usually limited by hardware availability; document zone constraints. |

Be careful with persistent volumes. Many cloud block volumes are zone-bound. If a workload uses a PVC in zone-a, the pod might not be movable to zone-b unless the storage platform supports that behavior.

## 9. Pool-Specific MachineConfig

### 9.1 MachineConfig Role Label

A MachineConfig is targeted to a pool through its role label:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: app-gold
```

The MCP must include that role in `spec.machineConfigSelector`:

```yaml
machineConfigSelector:
  matchExpressions:
  - key: machineconfiguration.openshift.io/role
    operator: In
    values:
    - worker
    - app-gold
```

If the role label does not match, the MachineConfig will not be rendered into the custom pool.

### 9.2 Example: Add a sysctl File to Only `app-gold` Nodes

Create file content:

```bash
cat > 99-app-gold.conf <<'EOF_SYSCTL'
net.core.somaxconn = 4096
net.ipv4.tcp_tw_reuse = 1
vm.max_map_count = 262144
EOF_SYSCTL
```

Base64 encode:

```bash
base64 -w0 99-app-gold.conf
```

Create `99-app-gold-sysctl.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-app-gold-sysctl
  labels:
    machineconfiguration.openshift.io/role: app-gold
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/sysctl.d/99-app-gold.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,<BASE64_CONTENT>
```

Apply:

```bash
oc apply -f 99-app-gold-sysctl.yaml
```

Watch rollout:

```bash
oc get mcp app-gold -w
oc describe mcp app-gold
```

Verify on node:

```bash
oc debug node/<app-gold-node>
chroot /host
cat /etc/sysctl.d/99-app-gold.conf
sysctl net.core.somaxconn
exit
exit
```

### 9.3 Example: Add a systemd Drop-in

Use MachineConfig to create a systemd unit or drop-in only when absolutely required. Prefer supported OpenShift configuration APIs first.

Example skeleton:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-app-gold-custom-systemd
  labels:
    machineconfiguration.openshift.io/role: app-gold
spec:
  config:
    ignition:
      version: 3.4.0
    systemd:
      units:
      - name: example.service
        enabled: true
        contents: |
          [Unit]
          Description=Example custom service for app-gold nodes
          After=network-online.target

          [Service]
          Type=oneshot
          ExecStart=/usr/local/bin/example-script.sh
          RemainAfterExit=yes

          [Install]
          WantedBy=multi-user.target
```

Production warning:

- Do not change kubelet systemd units casually.
- Do not overwrite OpenShift-managed units unless Red Hat documentation or support guidance says so.
- Prefer `KubeletConfig`, `ContainerRuntimeConfig`, PerformanceProfile, or supported Operator APIs.

### 9.4 MachineConfig Naming and Order

MachineConfigs are processed in lexicographic order by name when rendered. Use a consistent naming pattern:

```text
00-worker
01-worker-container-runtime
50-app-gold-base
90-app-gold-tuning
99-app-gold-final
```

Practical rule:

- Use `50-` for base custom settings.
- Use `90-` for tuning.
- Use `99-` only for final overrides.

Avoid creating many tiny MachineConfigs for one pool. Combine related changes to reduce complexity.

## 10. Pool-Specific KubeletConfig

`KubeletConfig` is the supported way to tune many kubelet settings per pool.

### 10.1 Label the MCP for KubeletConfig Selection

```bash
oc label mcp app-gold custom-kubelet=app-gold
```

Verify:

```bash
oc get mcp app-gold --show-labels
```

### 10.2 Create KubeletConfig

Create `kubeletconfig-app-gold.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: app-gold-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: app-gold
  kubeletConfig:
    maxPods: 250
    podsPerCore: 10
    systemReserved:
      cpu: 1000m
      memory: 2Gi
    kubeReserved:
      cpu: 500m
      memory: 1Gi
```

Apply:

```bash
oc apply -f kubeletconfig-app-gold.yaml
```

Watch:

```bash
oc get kubeletconfig
oc get mc | grep kubelet
oc get mcp app-gold -w
```

### 10.3 Production Notes for KubeletConfig

Important points:

- Create one `KubeletConfig` per MCP where possible.
- Put all desired kubelet changes for that pool in the same CR.
- Do not create one CR per setting.
- Do not exceed platform limits for generated kubelet MachineConfigs.
- Test kubelet changes on a non-production custom pool first.
- Changes commonly cause node drain and reboot.
- Bad kubelet settings can make nodes NotReady.

Common kubelet settings used in pool design:

| Setting | Use case |
|---|---|
| `maxPods` | Increase or decrease pod density. |
| `podsPerCore` | Control density relative to CPU size. |
| `systemReserved` | Reserve resources for OS and system daemons. |
| `kubeReserved` | Reserve resources for Kubernetes components. |
| `evictionHard` | Tune eviction thresholds. |
| `evictionSoft` | Tune soft eviction behavior. |
| `cpuManagerPolicy` | Static CPU pinning for guaranteed workloads. |
| `topologyManagerPolicy` | NUMA-aware workload alignment. |

Always validate exact field support for your OpenShift version before applying.

## 12. Taints, Tolerations, and Node Selectors for Dedicated Pools

### 12.1 Why Labels Alone Are Not Enough

A label attracts workloads only if pods use a selector or affinity. It does not prevent other pods from landing on the node.

A taint repels pods unless they tolerate it.

Use both:

```text
Node label: node-role.kubernetes.io/app-gold=
Node taint: dedicated=app-gold:NoSchedule
Pod selector: node-role.kubernetes.io/app-gold: ""
Pod toleration: dedicated=app-gold:NoSchedule
```

### 12.2 Add a Taint

```bash
oc adm taint nodes -l node-role.kubernetes.io/app-gold dedicated=app-gold:NoSchedule
```

Remove a taint:

```bash
oc adm taint nodes -l node-role.kubernetes.io/app-gold dedicated=app-gold:NoSchedule-
```

### 12.3 Workload Placement with `nodeSelector`

```yaml
spec:
  template:
    spec:
      nodeSelector:
        node-role.kubernetes.io/app-gold: ""
      tolerations:
      - key: dedicated
        operator: Equal
        value: app-gold
        effect: NoSchedule
```

### 12.4 Workload Placement with Required Node Affinity

Node affinity is more expressive than `nodeSelector`.

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: node-role.kubernetes.io/app-gold
                operator: Exists
      tolerations:
      - key: dedicated
        operator: Equal
        value: app-gold
        effect: NoSchedule
```

### 12.5 Preferred Node Affinity

Use preferred affinity when a workload should prefer a pool but can fall back elsewhere.

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: node-role.kubernetes.io/app-gold
                operator: Exists
```

Do not use preferred affinity for strict isolation. Use required affinity or `nodeSelector` plus taints.

### 12.6 Project-Level Node Selector

You can apply a default node selector to a namespace/project:

```bash
oc adm new-project gold-apps --node-selector='node-role.kubernetes.io/app-gold='
```

Or patch an existing namespace:

```bash
oc annotate namespace gold-apps openshift.io/node-selector='node-role.kubernetes.io/app-gold=' --overwrite
```

This is useful for tenant or team-level partitioning.

Be careful: a project-level node selector combines with pod selectors. If they conflict, pods will remain Pending.

## 18. Batch and CI/CD Pool Customization

Batch workloads are usually bursty and cost-sensitive.

Typical design:

```text
node-role.kubernetes.io/batch=
dedicated=batch:NoSchedule
```

Possible settings:

- Higher pod density.
- Autoscaling enabled.
- Lower priority workloads.
- Lower disruption sensitivity.
- Scale-to-zero where supported and safe.
- Separate registry cache considerations.

Example MachineAutoscaler:

```yaml
apiVersion: autoscaling.openshift.io/v1beta1
kind: MachineAutoscaler
metadata:
  name: batch-zone-a
  namespace: openshift-machine-api
spec:
  minReplicas: 0
  maxReplicas: 20
  scaleTargetRef:
    apiVersion: machine.openshift.io/v1beta1
    kind: MachineSet
    name: <clusterid>-batch-zone-a
```

Important:

- ClusterAutoscaler must exist.
- MachineAutoscaler must target a MachineSet.
- Scale-to-zero support depends on platform and design.
- Do not set default installer-created worker MachineSets to zero unless the platform documentation supports the design and you understand the consequences.

## 19. Autoscaling Dedicated Pools

### 19.1 ClusterAutoscaler vs MachineAutoscaler

| Object | Scope | Purpose |
|---|---|---|
| `ClusterAutoscaler` | Cluster-wide | Defines global autoscaling behavior and limits. |
| `MachineAutoscaler` | Per MachineSet | Defines min/max replicas for a MachineSet. |

The ClusterAutoscaler needs MachineAutoscaler resources to know which MachineSets are allowed to scale.

### 19.2 Example MachineAutoscaler for `app-gold`

```yaml
apiVersion: autoscaling.openshift.io/v1beta1
kind: MachineAutoscaler
metadata:
  name: app-gold-zone-a
  namespace: openshift-machine-api
spec:
  minReplicas: 2
  maxReplicas: 6
  scaleTargetRef:
    apiVersion: machine.openshift.io/v1beta1
    kind: MachineSet
    name: <clusterid>-app-gold-zone-a
```

Apply:

```bash
oc apply -f machineautoscaler-app-gold-zone-a.yaml
```

Verify:

```bash
oc get machineautoscaler -n openshift-machine-api
oc describe machineautoscaler app-gold-zone-a -n openshift-machine-api
oc get machineset <clusterid>-app-gold-zone-a -n openshift-machine-api
```

### 19.3 Autoscaling and Taints

If a pool is tainted, pending pods must have matching tolerations. Otherwise, the autoscaler might not scale the desired pool because pods are not considered schedulable onto that MachineSet.

Checklist:

```bash
oc describe pod <pending-pod> -n <namespace>
oc get machineset -n openshift-machine-api --show-labels

```

## 20. Upgrade and Reboot Behavior for Custom Pools

### 20.1 What Happens During MachineConfig Changes

When a MachineConfig, KubeletConfig, ContainerRuntimeConfig, or relevant OS image configuration changes, the MCO renders a new configuration for the affected MCP.

Typical sequence:

1. MCO detects desired configuration change.
2. New rendered MachineConfig is created.
3. MCP status changes to `UPDATING=True`.
4. MCD on selected nodes cordons and drains the node.
5. Machine configuration is applied.
6. Node reboots if required.
7. Node returns Ready.
8. MCP updated count increases.
9. MCP becomes `UPDATED=True` after all nodes converge.

### 20.2 Watch Pool Update

```bash
oc get mcp app-gold -w
```

Detailed view:

```bash
oc describe mcp app-gold
```

Check nodes:

```bash
oc get nodes -l node-role.kubernetes.io/app-gold -o wide
```

Check MCD pods:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon
```

### 20.3 Control Disruption with `maxUnavailable`

For small or critical pools:

```yaml
spec:
  maxUnavailable: 1
```

This means only one node in the pool should be unavailable during MCO-driven updates.

For larger, less critical pools, a percentage may be acceptable, but use caution.

### 20.4 Pausing an MCP

Pause a pool before staging multiple changes:

```bash
oc patch mcp app-gold --type=merge -p '{"spec":{"paused":true}}'
```

Apply your changes:

```bash
oc apply -f 99-app-gold-sysctl.yaml
oc apply -f kubeletconfig-app-gold.yaml
```

Unpause:

```bash
oc patch mcp app-gold --type=merge -p '{"spec":{"paused":false}}'
```

Watch rollout:

```bash
oc get mcp app-gold -w
```

Important:

- A paused MCP does not apply pending machine config changes to nodes until unpaused.
- Do not leave pools paused accidentally.
- Document who paused the pool, why, and when it must be unpaused.

### 20.5 Upgrade Sequencing Strategy

For major upgrades or high-risk machine config changes:

1. Create a small canary custom pool.
2. Move one or two non-critical workers into the canary pool.
3. Apply the MachineConfig or KubeletConfig there first.
4. Observe node readiness, workload behavior, kubelet logs, CRI-O logs, and MCO status.
5. Promote the change to larger pools.
6. Keep `maxUnavailable=1` for critical pools.
7. Validate platform workloads after each pool.

## 21. Troubleshooting Worker Pool Customization

### 21.1 Quick Health Commands

```bash
oc get clusterversion
oc get co machine-config
oc get mcp
oc get nodes
oc get pods -n openshift-machine-config-operator -o wide
```

### 21.2 MCP Not Updating

Check:

```bash
oc describe mcp <pool-name>
oc get mc
oc get nodes --show-labels
```

Common causes:

| Symptom | Likely cause | Fix |
|---|---|---|
| MCP has zero machines | Node selector does not match node labels | Correct node labels or MCP `nodeSelector`. |
| MachineConfig not included | MachineConfig role label does not match MCP selector | Fix `machineconfiguration.openshift.io/role`. |
| Pool stuck `UPDATING=True` | Node drain, reboot, or MCD issue | Check node, MCD logs, PDBs, events. |
| Pool `DEGRADED=True` | Config drift or failed apply | Describe MCP and check MCD logs. |
| Node still in worker MCP | Custom MCP does not exist or selector mismatch | Create/fix custom MCP. |
| Pods Pending | Taint/selector/affinity mismatch | Describe pod events. |
| Workloads landed on wrong pool | Missing taint or selector too broad | Add taint and enforce workload placement. |

### 21.3 Check Which Pool Manages a Node

```bash
oc get node <node-name> --show-labels
oc get mcp -o wide
oc describe mcp worker
oc describe mcp app-gold
```

Look at MCP node counts and selectors.

### 21.4 Check Rendered MachineConfig

```bash
oc get mcp app-gold -o jsonpath='{.status.configuration.name}{"\n"}'
```

Then:

```bash
RENDERED=$(oc get mcp app-gold -o jsonpath='{.status.configuration.name}')
oc get mc "$RENDERED" -o yaml
```

### 21.5 Check MCD Logs

Find the MCD pod on a node:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node-name>
```

Logs:

```bash
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon
```

Previous logs:

```bash
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon --previous
```

### 21.6 Debug Node State

```bash
oc debug node/<node-name>
chroot /host
systemctl status kubelet
systemctl status crio
journalctl -u kubelet -b --no-pager | tail -100
journalctl -u crio -b --no-pager | tail -100
journalctl -u machine-config-daemon -b --no-pager | tail -100
exit
exit
```

### 21.7 Drain Blocked by PDB

Symptoms:

- MCP stuck updating.
- MCD logs show drain errors.
- Node remains cordoned or partially drained.

Check:

```bash
oc get pdb -A
oc describe node <node-name>
oc get pods -A -o wide | grep <node-name>
```

Fix approach:

- Do not delete PDBs blindly.
- Scale workloads or adjust PDBs temporarily with approval.
- Ensure application replicas are spread across nodes/zones.
- Retry after workloads become drainable.

### 21.8 Configuration Drift

Configuration drift occurs when the on-disk node state differs from the MachineConfig-managed desired state.

Common causes:

- Manual edits under `/etc` that are managed by MachineConfig.
- Manual changes to systemd units.
- Manual changes to kubelet or CRI-O config.
- File permissions changed outside MCO.

Check:

```bash
oc describe mcp <pool-name>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Fix:

- Revert manual change to match MachineConfig.
- Or update the MachineConfig to represent the intended state.
- Avoid SSH-based snowflake changes.

### 21.9 Node Not Accepted into Custom MCP

Check labels:

```bash
oc get node <node-name> --show-labels | tr ',' '\n' | grep node-role
```

Check MCP selector:

```bash
oc get mcp app-gold -o yaml
```

Common mistakes:

```yaml
# Wrong: selector expects appgold, node has app-gold
nodeSelector:
  matchLabels:
    node-role.kubernetes.io/appgold: ""
```

```yaml
# Wrong: MachineConfig role is custom-app-gold, MCP selects app-gold
metadata:
  labels:
    machineconfiguration.openshift.io/role: custom-app-gold
```

### 21.10 Pods Pending on Dedicated Pool

```bash
oc describe pod <pod-name> -n <namespace>
```

Look for:

```text
node(s) had untolerated taint
node(s) didn't match Pod's node affinity/selector
Insufficient cpu
Insufficient memory
volume node affinity conflict
```

Fix matrix:

| Event | Fix |
|---|---|
| Untolerated taint | Add correct toleration or remove taint. |
| Node selector mismatch | Correct node label or pod selector. |
| Node affinity mismatch | Fix affinity expression. |
| Insufficient CPU/memory | Add nodes, reduce requests, or autoscale. |
| Volume node affinity conflict | Schedule pod in same zone as PV or use suitable storage. |

### 21.11 Custom Pool with No Nodes

This can be intentional for canary builds or image tests, but usually means labels are missing.

```bash
oc get mcp app-gold
oc get nodes -L node-role.kubernetes.io/app-gold
```

Add label:

```bash
oc label node <node-name> node-role.kubernetes.io/app-gold=
```

### 21.12 Removing a Node from a Custom Pool

Before removing the custom role label, make sure the node still matches another MCP, usually `worker`.

Check:

```bash
oc get node <node-name> --show-labels
```

Remove custom label:

```bash
oc label node <node-name> node-role.kubernetes.io/app-gold-
```

Remove taint if needed:

```bash
oc adm taint node <node-name> dedicated=app-gold:NoSchedule-
```

Watch MCPs:

```bash
oc get mcp -w
```

The node may reboot if moving from one rendered configuration to another.

## 23. Production Best Practices

### 23.1 Keep Pool Count Practical

Too few pools cause poor isolation. Too many pools create operational complexity.

Good starting point:

```text
worker
infra
logging or monitoring if needed
storage if needed
app-critical if needed
batch or gpu if needed
```

Avoid creating a pool for every application team unless there is a strong isolation or compliance requirement.

### 23.2 Use Custom Pools as Change Domains

A pool is also a change domain. If you apply bad kubelet or OS tuning to a small custom pool, the blast radius is limited.

Recommended change promotion:

```text
canary -> app-gold -> general worker -> remaining pools
```

### 23.3 Do Not Manually Edit Managed Host Files

Avoid SSH changes such as:

```bash
vi /etc/kubernetes/kubelet.conf
vi /etc/crio/crio.conf
vi /etc/systemd/system/kubelet.service
```

Use supported OpenShift APIs:

- `MachineConfig`
- `KubeletConfig`
- `ContainerRuntimeConfig`
- Performance Addon Operator / PerformanceProfile where applicable
- Cluster/operator-specific placement APIs

### 23.4 Prefer Declarative GitOps

Store these objects in Git:

```text
machineconfigpools/
machineconfigs/
kubeletconfigs/
containerruntimeconfigs/
machinesets/
machineautoscalers/
namespace-node-selectors/
operator-placement/
```

Use pull requests and peer review for changes that reboot nodes.

### 23.5 Use Taints for Hard Isolation

For true dedicated pools, use taints.

Without taints, a general workload might land on a dedicated node if it has no restrictive selector and scheduler scoring chooses that node.

### 23.6 Use Selectors/Affinity for Attraction

Taints repel. They do not attract.

A pod with only a toleration can run on the tainted node, but it can also run elsewhere unless it has a selector or affinity.

For dedicated placement, use both:

```yaml
nodeSelector:
  node-role.kubernetes.io/app-gold: ""
tolerations:
- key: dedicated
  operator: Equal
  value: app-gold
  effect: NoSchedule
```

### 23.7 Do Not Overuse Project-Level Node Selectors

Project-level node selectors are powerful but can cause confusing Pending pods when combined with workload-level node selectors.

Use them when:

- A namespace should always run on a specific pool.
- You want tenant-level policy.
- Developers should not need to add selectors in every manifest.

Avoid them when:

- Workloads in the namespace need multiple pools.
- Operators create pods with their own strict placement rules.
- Teams frequently move workloads between pools.

### 23.8 Protect Critical Pools with PDBs

MCO updates drain nodes. Workloads should have proper PDBs and replicas.

Example PDB:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: gold-app-pdb
  namespace: gold-test
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: gold-nginx
```

Do not create PDBs that make maintenance impossible. For a single replica workload, `minAvailable: 1` blocks voluntary disruption.

### 23.9 Use Topology Spread for HA

For critical workloads:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: gold-nginx
```

This helps ensure replicas are not concentrated in one zone.

### 23.10 Monitor Pool Health

Create alerts or dashboards for:

- MCP degraded
- MCP updating too long
- Node NotReady
- Node memory pressure
- Node disk pressure
- Node PID pressure
- MCD errors
- Drain failures
- Workload Pending due to taints/selectors
- MachineSet unavailable replicas
- Autoscaler failures

## 24. Common Anti-Patterns

### Anti-Pattern 1: Only Labeling Nodes

```bash
oc label node worker-1 dedicated=gold
```

Problem:

- No MCP isolation.
- No taint.
- No workload enforcement.
- General workloads may still run there.

Better:

- Create MCP.
- Use role label.
- Add taint.
- Add workload selector/toleration.

### Anti-Pattern 2: Removing `worker` Label Without Custom MCP

Problem:

- Node might not be managed by any MCP.
- MCO behavior becomes unsafe or unexpected.

Better:

- Keep `worker` label.
- Add custom role label.
- Create matching custom MCP.

### Anti-Pattern 3: Creating MCP Without Worker Inheritance

Bad:

```yaml
values:
- app-gold
```

Better:

```yaml
values:
- worker
- app-gold
```

### Anti-Pattern 4: Toleration Without Selector

Problem:

A pod with only toleration can run on the dedicated node but is not forced to.

Better:

```yaml
nodeSelector:
  node-role.kubernetes.io/app-gold: ""
tolerations:
- key: dedicated
  operator: Equal
  value: app-gold
  effect: NoSchedule
```

### Anti-Pattern 5: Too Many Tiny MachineConfigs

Problem:

- Hard to troubleshoot.
- Rendered configs become difficult to reason about.
- Rollbacks are messy.

Better:

- Group related settings.
- Use clear names.
- Keep Git history.

### Anti-Pattern 6: No Canary Pool

Problem:

- A bad machine config affects all workers.

Better:

- Test on a small custom pool first.

### Anti-Pattern 7: Ignoring Storage Topology

Problem:

- Pod can be forced to a pool in another zone but PVC is zone-bound.
- Result: `volume node affinity conflict`.

Better:

- Align storage class, MachineSet zones, and pod topology.

### Anti-Pattern 8: Leaving MCP Paused

Problem:

- Important security or configuration updates do not apply.

Better:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status
```

## 25. Advanced Example: Canary Pool for Safe MachineConfig Testing

### 25.1 Goal

Create a small pool for testing MachineConfig changes before applying to production workers.

### 25.2 Create Canary MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1

metadata:
  name: worker-canary
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role

      values:
      - worker
      - worker-canary
```

## 26. Advanced Example: Pool-Specific Performance Tuning

For latency-sensitive applications, worker pool customization often includes:

- Dedicated nodes.
- Static CPU manager policy.
- Topology manager policy.
- Reserved CPUs.
- Huge pages.
- Real-time kernel where supported and required.
- Workload CPU pinning.
- NUMA alignment.

Example concept:

```text
Pool: app-lowlatency
Node labels:
  node-role.kubernetes.io/app-lowlatency=
  workload.openshift.io/latency-sensitive=true
Taint:
  dedicated=app-lowlatency:NoSchedule
KubeletConfig:
  cpuManagerPolicy: static
  topologyManagerPolicy: single-numa-node
Workload:
  Guaranteed QoS
  CPU request == CPU limit
  memory request == memory limit
```

Important:

- CPU manager and topology settings are advanced changes.
- Validate support and exact fields for your OpenShift version.
- Use PerformanceProfile where applicable, especially for telco, CNF, and low-latency workloads.
- A misconfigured performance pool can make workloads unschedulable or degrade node readiness.

## 27. Exam and Interview Style Questions

### Q1. What is the difference between a MachineSet and a MachineConfigPool?

A MachineSet creates machines/nodes on supported infrastructure. A MachineConfigPool groups nodes for OS-level and kubelet/CRI-O-level configuration through the Machine Config Operator. MachineSet is about provisioning. MCP is about configuration management.

### Q2. Does a custom MCP automatically isolate workloads?

No. MCP controls machine configuration, not pod scheduling. For scheduling isolation, use labels, taints, tolerations, selectors, node affinity, namespace node selectors, and topology policies.

### Q3. Why should a custom worker pool include `worker` in `machineConfigSelector`?

Because custom worker pools should inherit the base worker configuration. The custom role then adds pool-specific configuration.

### Q4. Can a node be part of multiple MCPs?

No. A node can have multiple labels but is managed by only one MachineConfigPool. Custom pools take priority when they match.

### Q5. Why are taints required for dedicated pools?

Taints prevent unrelated pods from scheduling onto dedicated nodes unless those pods have matching tolerations. Labels alone do not repel pods.

### Q6. What happens after applying a MachineConfig to a pool?

The MCO renders a new configuration for the MCP. Affected nodes are usually cordoned, drained, updated, and rebooted if required. The rollout follows MCP settings such as `maxUnavailable`.

### Q7. How do you troubleshoot an MCP stuck in Updating?

Check:

```bash
oc describe mcp <pool>
oc get nodes
oc get pods -n openshift-machine-config-operator -o wide
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
oc get pdb -A
oc describe node <node>
```

Look for drain failures, degraded nodes, config drift, bad MachineConfig, PDB blockage, or reboot issues.

### Q8. What is a good use of a canary worker pool?

Testing MachineConfig, KubeletConfig, ContainerRuntimeConfig, or custom layered OS image changes on a small set of nodes before applying to production pools.

## 29. Real-World Troubleshooting Scenarios

### Scenario 1: Custom MCP Shows `MACHINECOUNT=0`

Commands:

```bash
oc get mcp app-gold
oc get nodes -L node-role.kubernetes.io/app-gold
oc get mcp app-gold -o yaml
```

Likely issue:

- Node label does not match MCP `nodeSelector`.

Fix:

```bash
oc label node <node-name> node-role.kubernetes.io/app-gold=
```

### Scenario 2: MachineConfig Applied to All Workers Accidentally

Cause:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

You intended to target only `app-gold`, but used `worker` role.

Fix:

1. Create corrected MachineConfig with role `app-gold`.
2. Remove the wrong MachineConfig.
3. Watch affected MCPs.
4. Validate rollback behavior.

```bash
oc delete mc <wrong-machineconfig-name>
oc get mcp -w
```

### Scenario 3: Pod Has Toleration but Runs on Normal Worker

Cause:

- Toleration does not force placement.
- Missing node selector or node affinity.

Fix:

Add:

```yaml
nodeSelector:
  node-role.kubernetes.io/app-gold: ""
```

### Scenario 4: Pod Has Selector but Is Pending

Cause:

- Node is tainted and pod lacks toleration.

Check:

```bash
oc describe pod <pod> -n <namespace>
```

Fix:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: app-gold
  effect: NoSchedule
```

### Scenario 5: MCO Degraded After Manual Node Change

Cause:

- Configuration drift.

Check:

```bash
oc describe mcp app-gold
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Fix:

- Revert manual change.
- Or represent intended change through MachineConfig.

### Scenario 6: Drain Fails During MCP Update

Cause:

- PDB blocks eviction.
- Static or mirror pods.
- Unhealthy workload replicas.
- DaemonSet or local storage constraints.

Check:

```bash
oc get pdb -A
oc get pods -A -o wide | grep <node-name>
oc describe node <node-name>
```

Fix:

- Restore workload replicas.
- Adjust PDB temporarily with approval.
- Remove unhealthy pods only after impact assessment.

## 32. Key Takeaways

- Worker pool customization is a multi-layer design: provisioning, configuration, scheduling, and operations.
- `MachineSet` creates nodes; `MachineConfigPool` configures nodes; scheduler policies place workloads.
- Custom MCPs should normally inherit from `worker`.
- A node can have multiple labels but can be managed by only one MCP.
- Custom MCPs take priority over the default worker MCP when they match node labels.
- Labels attract workloads only when pods use selectors or affinity.
- Taints repel workloads unless pods tolerate them.
- Tolerations alone do not force placement.
- Use `maxUnavailable`, PDBs, canary pools, and paused MCPs carefully to control disruption.
- Avoid manual node changes; use declarative OpenShift APIs.
- A dedicated pool without monitoring, maintenance policy, and Git-managed configuration is incomplete.
