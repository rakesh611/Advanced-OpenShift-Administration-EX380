# Applying Kernel/sysctl Settings through MachineConfig

**Topic area:** Cluster Partitioning and Dedicated Node Pools  
**Level:** Advanced OpenShift Administration, 10+ years experience  
**Platform focus:** Red Hat OpenShift Container Platform 4.x  
**Main objects:** `MachineConfig`, `MachineConfigPool`, `KubeletConfig`, Machine Config Operator, Node Tuning Operator

---

## 1. Executive Summary

In OpenShift, kernel and sysctl tuning is not something you should handle by manually SSH-ing to each node and editing `/etc/sysctl.conf`, `/etc/sysctl.d/*.conf`, GRUB, or systemd files. OpenShift nodes are managed declaratively. The correct production model is:

1. Partition nodes by role or workload type.
2. Create or use a matching `MachineConfigPool`.
3. Apply host-level operating system configuration through a `MachineConfig` targeted to that pool.
4. Use `KubeletConfig` when you are enabling pod-level unsafe sysctls.
5. Use the Node Tuning Operator when dynamic runtime tuning through TuneD is the better fit.
6. Verify rollout through `oc get mcp`, node annotations, `oc debug node`, Machine Config Daemon logs, and workload behavior.

For dedicated node pools, this is especially important because a sysctl that is useful for one workload can be dangerous for another. For example:

- Elasticsearch/OpenSearch might need `vm.max_map_count`.
- Ingress-heavy or proxy-heavy nodes might need higher connection backlog or port range tuning.
- Logging nodes might need inotify tuning.
- Low-latency/CNF nodes might need kernel arguments, CPU isolation, IRQ balancing, or real-time kernel configuration.
- Storage nodes might need multipath, iSCSI, huge pages, or queue-related tuning.

The mistake many administrators make is applying these settings to the default `worker` pool. In a mature OpenShift environment, you normally do not tune all workers the same way. You isolate tuning by workload domain.

## 2. Kernel Arguments vs sysctl Settings

Kernel tuning in Linux has two major categories.

### 2.1 Kernel arguments

Kernel arguments are boot-time parameters passed to the Linux kernel when the node starts. Examples include parameters that influence CPU, IOMMU, huge pages, SELinux mode, boot behavior, and low-level kernel features.

In OpenShift, boot-time kernel arguments are handled directly in a `MachineConfig` using:

```yaml
spec:
  kernelArguments:
    - <argument>
```

A change to kernel arguments normally requires node reboot because the kernel reads these arguments during boot.

### 2.2 sysctl settings

`sysctl` settings are runtime kernel parameters exposed through `/proc/sys`. They can usually be read and changed using:

```bash
sysctl -a
sysctl net.core.somaxconn
sysctl -w net.core.somaxconn=4096
```

On a traditional RHEL server, persistent sysctl values are usually stored in:

```text
/etc/sysctl.conf
/etc/sysctl.d/*.conf
/run/sysctl.d/*.conf
/usr/lib/sysctl.d/*.conf
```

On OpenShift RHCOS nodes, do not manually edit those files. Use a declarative mechanism:

- `MachineConfig` to place files under `/etc/sysctl.d/` for persistent host-level settings.
- `KubeletConfig` to allow selected unsafe pod sysctls on a selected node pool.
- `Tuned` custom resources through the Node Tuning Operator for TuneD-managed runtime tuning.

## 3. Why MachineConfig Matters in Dedicated Node Pools

`MachineConfig` is the OpenShift way of managing node operating system configuration. The Machine Config Operator applies changes to nodes through machine config pools. A pool represents a set of nodes that should receive the same rendered host configuration.

For cluster partitioning, this matters because different node pools often have different operating system requirements:

| Node pool | Typical workload | Example tuning need |
|---|---|---|
| `worker` | General applications | Keep generic, minimal tuning |
| `infra` | Router, registry, monitoring, logging components | Connection backlog, file watches, queue tuning |
| `logging` | Loki, Elasticsearch/OpenSearch, collectors | `vm.max_map_count`, file descriptors, inotify |
| `monitoring` | Prometheus, Thanos, Alertmanager | mmap, file watches, network buffers |
| `storage` | ODF/Ceph, local storage, iSCSI/multipath | multipath kernel arguments, device tuning |
| `gpu` | GPU workloads | driver/operator-specific tuning, huge pages, IOMMU |
| `cnf` / `lowlatency` | Telco, packet processing | real-time kernel, CPU isolation, IRQ tuning |

The core design principle is simple:

> Apply the smallest required host-level change to the smallest possible node pool.

Do not apply specialized tuning to the global worker pool unless every worker node truly requires it.

## 4. Machine Config Operator Flow

When you create or update a `MachineConfig`, the Machine Config Operator performs a controlled rollout.

Typical flow:

1. You create a `MachineConfig` with a role label such as `machineconfiguration.openshift.io/role: infra`.
2. The MCO render controller combines all applicable machine configs for that pool.
3. A new `rendered-<pool>-<hash>` configuration is created.
4. The target `MachineConfigPool` enters `UPDATING=True`.
5. The Machine Config Daemon on each affected node applies the configuration.
6. For most node OS changes, the node is cordoned, drained, changed, rebooted, and uncordoned.
7. The pool returns to `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`.

Key points for experienced admins:

- Machine configs are rendered in lexicographic order by name.
- Custom worker pools inherit worker machine configs.
- Worker-targeted configs affect all custom pools that inherit from worker.
- Pool-specific configs affect only the pool matching that role label.
- A node should be managed by exactly one MCP.
- A degraded MCP must be fixed before reliable future upgrades.
- A paused MCP does not apply new rendered configs until unpaused.

## 5. Choosing the Right Mechanism

Before applying kernel or sysctl settings, decide which mechanism fits the requirement.

| Requirement | Recommended mechanism | Reason |
|---|---|---|
| Add kernel boot argument | `MachineConfig.spec.kernelArguments` | Kernel reads argument at boot |
| Persist host-level sysctl file | `MachineConfig` writing `/etc/sysctl.d/*.conf` | Declarative OS file management |
| Allow pod to request unsafe namespaced sysctls | `KubeletConfig.kubeletConfig.allowedUnsafeSysctls` | Kubelet must explicitly allow them |
| Tune runtime sysctls with TuneD | Node Tuning Operator `Tuned` CR | Designed for node-level tuning profiles |
| Low latency / real-time tuning | Performance Profile / Node Tuning Operator, sometimes MachineConfig | More complete tuning stack |
| One-off manual emergency check | `oc debug node`, temporary only | Never treat manual changes as persistent |

A strong production rule:

> If the setting must survive node replacement, upgrades, and reboots, it must be declared in the cluster, not manually changed on the host.

## 6. sysctl Categories in OpenShift

OpenShift administrators must distinguish between three sysctl contexts.

### 6.1 Host-level sysctls

These affect the node operating system itself. Examples:

```text
vm.max_map_count
fs.inotify.max_user_watches
fs.inotify.max_user_instances
net.core.somaxconn
net.ipv4.ip_local_port_range
net.ipv4.tcp_tw_reuse
```

Host-level sysctls are usually applied through:

- `/etc/sysctl.d/*.conf` written by `MachineConfig`, or
- `Tuned` profile through the Node Tuning Operator.

### 6.2 Safe pod sysctls

Some sysctls are considered safe for pods because they are namespaced and do not affect other pods or the node globally. These can be used in a pod `securityContext.sysctls` without special unsafe enablement.

Example pod snippet:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: safe-sysctl-example
spec:
  securityContext:
    sysctls:
      - name: net.ipv4.ip_local_port_range
        value: "1024 65535"
  containers:
    - name: app
      image: registry.access.redhat.com/ubi9/ubi-minimal
      command: ["sleep", "3600"]
```

### 6.3 Unsafe pod sysctls

Unsafe sysctls are not allowed by default. If a pod requests an unsafe sysctl and the node's kubelet does not allow it, the pod can be scheduled but fail to start with a status such as `SysctlForbidden`.

Unsafe pod sysctls require kubelet-level allowlisting, normally through `KubeletConfig` scoped to a `MachineConfigPool`.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: allow-unsafe-sysctls-infra
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: infra-sysctl
  kubeletConfig:
    allowedUnsafeSysctls:
      - "net.core.somaxconn"
      - "kernel.msg*"
```

Important distinction:

- Host sysctl value controls the node-level kernel parameter.
- Pod sysctl allowlisting controls whether a pod may request selected sysctls.
- These are related but not the same control plane.

## 7. Dedicated Node Pool Design Pattern

For advanced cluster partitioning, use this pattern:

1. Label the target nodes.
2. Create a custom `MachineConfigPool` for that role.
3. Target workload placement using node selectors, affinity, taints, and tolerations.
4. Apply pool-specific `MachineConfig` objects.
5. Apply pool-specific `KubeletConfig` only if required.
6. Validate rollout and runtime values.

Example target:

```text
Pool: infra
Nodes: worker nodes dedicated to ingress/router/infra workloads
Host tuning:
  net.core.somaxconn = 4096
  vm.max_map_count = 262144
  fs.inotify.max_user_watches = 524288
Kubelet unsafe sysctl allowlisting: only if pods need to set unsafe sysctls themselves
```

## 8. Step-by-Step: Create a Dedicated MCP for sysctl Tuning

### 8.1 Inspect existing nodes and MCPs

```bash
oc get nodes
oc get mcp
oc get mc
```

Example:

```bash
oc get nodes -L node-role.kubernetes.io/worker,node-role.kubernetes.io/infra
```

### 8.2 Label target nodes

For infra nodes:

```bash
oc label node worker-1.example.com node-role.kubernetes.io/infra=
oc label node worker-2.example.com node-role.kubernetes.io/infra=
oc label node worker-3.example.com node-role.kubernetes.io/infra=
```

Keep the worker role unless you know exactly why you are removing it. Custom MCPs normally inherit from worker.

### 8.3 Optional: taint dedicated infra nodes

This prevents normal user workloads from landing on infra nodes unless they tolerate the taint.

```bash
oc adm taint nodes -l node-role.kubernetes.io/infra infra=reserved:NoSchedule
```

Example workload toleration:

```yaml
tolerations:
  - key: infra
    operator: Equal
    value: reserved
    effect: NoSchedule
```

### 8.4 Create the infra MachineConfigPool

Save as `infra-mcp.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f infra-mcp.yaml
oc get mcp infra -w
```

Expected state when ready:

```text
NAME    UPDATED   UPDATING   DEGRADED
infra   True      False      False
```

## 9. Applying Host sysctl Settings through MachineConfig

### 9.1 Recommended file location

Use a dedicated file under `/etc/sysctl.d/`:

```text
/etc/sysctl.d/99-infra-sysctl.conf
```

Avoid editing `/etc/sysctl.conf` directly. A dedicated file is easier to audit, replace, and remove.

### 9.2 Example sysctl file content

```text
# OpenShift managed by MachineConfig: 99-infra-sysctl.conf
# Scope: infra MachineConfigPool only
net.core.somaxconn = 4096
vm.max_map_count = 262144
fs.inotify.max_user_watches = 524288
fs.inotify.max_user_instances = 1024
```

### 9.3 Raw MachineConfig example

Save as `99-infra-sysctl.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-sysctl
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
        - path: /etc/sysctl.d/99-infra-sysctl.conf
          mode: 420
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8;base64,IyBPcGVuU2hpZnQgbWFuYWdlZCBieSBNYWNoaW5lQ29uZmlnOiA5OS1pbmZyYS1zeXNjdGwuY29uZgojIFNjb3BlOiBpbmZyYSBNYWNoaW5lQ29uZmlnUG9vbCBvbmx5Cm5ldC5jb3JlLnNvbWF4Y29ubiA9IDQwOTYKdm0ubWF4X21hcF9jb3VudCA9IDI2MjE0NApmcy5pbm90aWZ5Lm1heF91c2VyX3VzZXJfd2F0Y2hlcyA9IDUyNDI4OApmcy5pbm90aWZ5Lm1heF91c2VyX2luc3RhbmNlcyA9IDEwMjQK
```

Apply:

```bash
oc apply -f 99-infra-sysctl.yaml
oc get mcp infra -w
```

Notes:

- `mode: 420` is decimal for `0644`.
- The file is delivered by Ignition/MCO.
- The MCO generally reboots the affected nodes for this type of file-based OS change.
- After reboot, systemd-sysctl applies the file.

### 9.4 Butane version, easier to maintain

Butane is often cleaner than hand-writing Ignition data URLs.

Save as `99-infra-sysctl.bu`:

```yaml
variant: openshift
version: 4.18.0
metadata:
  name: 99-infra-sysctl
  labels:
    machineconfiguration.openshift.io/role: infra
storage:
  files:
    - path: /etc/sysctl.d/99-infra-sysctl.conf
      mode: 0644
      overwrite: true
      contents:
        inline: |
          # OpenShift managed by MachineConfig: 99-infra-sysctl.conf
          # Scope: infra MachineConfigPool only
          net.core.somaxconn = 4096
          vm.max_map_count = 262144
          fs.inotify.max_user_watches = 524288
          fs.inotify.max_user_instances = 1024
```

Generate the MachineConfig:

```bash
butane 99-infra-sysctl.bu -o 99-infra-sysctl.yaml
oc apply -f 99-infra-sysctl.yaml
oc get mcp infra -w
```

Adjust the Butane `version` to match your OpenShift/RHCOS generation and supported Butane schema in your environment.

## 10. Applying Kernel Arguments through MachineConfig

Use `spec.kernelArguments` when the setting must be passed to the kernel at boot.

Example for a custom low-latency worker pool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-lowlatency-kernelargs
  labels:
    machineconfiguration.openshift.io/role: lowlatency
spec:
  kernelArguments:
    - skew_tick=1
    - nmi_watchdog=0
```

Apply:

```bash
oc apply -f 99-lowlatency-kernelargs.yaml
oc get mcp lowlatency -w
```

Verify on a node:

```bash
NODE=<lowlatency-node-name>
oc debug node/${NODE}
chroot /host
cat /proc/cmdline
```

You should see the configured arguments in the kernel command line.

### Production guidance for kernel arguments

Be careful with kernel arguments because they can affect node boot, CPU behavior, storage, networking, and security. Always test on a canary MCP before applying to a large production pool.

Good rollout model:

1. Create a tiny canary pool with one node.
2. Apply the kernel argument MachineConfig only to the canary role.
3. Reboot and validate workload behavior.
4. Expand to the dedicated pool.
5. Monitor MCP, node readiness, workload latency, and system logs.

## 11. Enabling Unsafe Pod sysctls with KubeletConfig

Do not confuse host sysctl tuning with allowing pods to request sysctls.

If a pod has:

```yaml
securityContext:
  sysctls:
    - name: net.core.somaxconn
      value: "1024"
```

and the sysctl is treated as unsafe, kubelet must allow it on that node pool. Use `KubeletConfig`.

### 11.1 Label the MCP

```bash
oc label machineconfigpool infra custom-kubelet=infra-sysctl
```

### 11.2 Create KubeletConfig

Save as `allow-unsafe-sysctls-infra.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: allow-unsafe-sysctls-infra
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: infra-sysctl
  kubeletConfig:
    allowedUnsafeSysctls:
      - "net.core.somaxconn"
      - "kernel.msg*"
```

Apply:

```bash
oc apply -f allow-unsafe-sysctls-infra.yaml
oc get mcp infra -w
```

### 11.3 Validate generated MachineConfig

```bash
oc get kubeletconfig
oc get mc | grep kubelet
oc describe mcp infra
```

### 11.4 Test with a pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sysctl-test
  namespace: sysctl-test
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
    - key: infra
      operator: Equal
      value: reserved
      effect: NoSchedule
  securityContext:
    sysctls:
      - name: net.core.somaxconn
        value: "1024"
  containers:
    - name: test
      image: registry.access.redhat.com/ubi9/ubi-minimal
      command: ["sleep", "3600"]
```

Verify:

```bash
oc get pod -n sysctl-test
oc describe pod sysctl-test -n sysctl-test
oc rsh -n sysctl-test sysctl-test sysctl net.core.somaxconn
```

If not allowed, you may see `SysctlForbidden` or admission/security warnings depending on the exact sysctl and cluster policy.

## 12. MachineConfig vs Node Tuning Operator for sysctl

OpenShift includes the Node Tuning Operator, which manages node-level tuning through TuneD. For many sysctl settings, especially performance profiles, using `Tuned` CRs is the better administrative interface.

Example `Tuned` profile:

```yaml
apiVersion: tuned.openshift.io/v1
kind: Tuned
metadata:
  name: infra-sysctl
  namespace: openshift-cluster-node-tuning-operator
spec:
  profile:
    - name: infra-sysctl
      data: |
        [main]
        summary=Infra node sysctl tuning
        include=openshift-node
        [sysctl]
        net.core.somaxconn=4096
        vm.max_map_count=262144
        fs.inotify.max_user_watches=524288
  recommend:
    - match:
        - label: node-role.kubernetes.io/infra
      priority: 20
      profile: infra-sysctl
```

Choose `MachineConfig` when:

- You want to manage persistent files under `/etc/sysctl.d/`.
- The setting must be in place early in boot.
- You want the setting tied directly to MCP rendering.
- You are already managing the node pool OS baseline through MachineConfig.
- You need a clean GitOps file artifact for host baseline configuration.

Choose Node Tuning Operator when:

- You are doing performance tuning profiles.
- You need TuneD-managed dynamic tuning.
- You need profile inheritance such as `include=openshift-node`.
- You want node-label-based profile matching.
- You are configuring low latency, CNF, or performance-sensitive nodes.

Avoid applying the same sysctl from both MachineConfig and TuneD unless you understand precedence and reapplication behavior. Duplicate ownership creates confusing troubleshooting scenarios.

## 14. Rollout Control and Maintenance Windows

MachineConfig changes can reboot nodes. For production, do not casually apply them during business hours unless your workload design can tolerate it.

### 14.1 Check pool status first

```bash
oc get mcp
```

Do not start if any pool is already:

```text
UPDATING=True
DEGRADED=True
```

### 14.2 Use `maxUnavailable`

For dedicated pools, set conservative rollout:

```yaml
spec:
  maxUnavailable: 1
```

This limits how many nodes in that MCP are unavailable during rollout.

### 14.3 Pause pool for batching

You can pause an MCP before applying multiple MachineConfig changes:

```bash
oc patch mcp infra --type merge -p '{"spec":{"paused":true}}'
```

Apply your changes:

```bash
oc apply -f 99-infra-sysctl.yaml
oc apply -f 99-infra-other-baseline.yaml
```

Unpause:

```bash
oc patch mcp infra --type merge -p '{"spec":{"paused":false}}'
oc get mcp infra -w
```

Important: paused means the new config will not be rolled out until unpaused.

### 14.4 Validate PDB and workload disruption

Before MCO drains nodes, check whether workloads can move:

```bash
oc get pdb -A
oc get pods -A -o wide | grep <node-name>
oc adm drain <node-name> --dry-run=server --ignore-daemonsets
```

Do not actually drain manually unless you have an operational reason. The MCO normally performs the drain.

## 15. Troubleshooting

### 15.1 MCP stuck in `UPDATING=True`

Check:

```bash
oc get mcp infra
oc describe mcp infra
oc get nodes
oc get node <node> -o yaml | grep -E "currentConfig|desiredConfig|state|reason" -A3
```

Common causes:

- Node reboot taking too long.
- Node cannot drain because of PDB or non-evictable pods.
- Node cannot pull OS update payload.
- Machine Config Daemon error.
- File conflict in MachineConfig.
- Bad Ignition syntax.
- Unsupported path or malformed data URL.

Check MCD logs:

```bash
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --since=30m
```

For a specific node:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node-name>
oc logs -n openshift-machine-config-operator <mcd-pod-name> -c machine-config-daemon
```

### 15.2 MCP `DEGRADED=True`

Check the degraded reason:

```bash
oc describe mcp infra
oc get mcp infra -o yaml
```

Common reasons:

- Manual modification caused configuration drift.
- File content on node does not match rendered config.
- MCD failed to apply a file or systemd unit.
- Node booted but did not converge to desired config.

Fix approach:

1. Read the exact degraded message.
2. Do not randomly delete machine configs.
3. Compare actual node state with rendered desired config.
4. Undo manual host changes if drift exists.
5. Correct the MachineConfig and reapply.

### 15.3 sysctl file exists but value is not active

Check:

```bash
oc debug node/<node>
chroot /host
cat /etc/sysctl.d/99-infra-sysctl.conf
sysctl --system
sysctl <key>
```

Possible causes:

- File syntax error.
- Later sysctl file overrides earlier file.
- TuneD reapplies a different value.
- Setting cannot be changed in current runtime context.
- MachineConfig applied but node has not rebooted yet.
- The value is namespace-specific and you are checking from the wrong namespace/context.

Check ordering:

```bash
ls -l /etc/sysctl.d/ /usr/lib/sysctl.d/ /run/sysctl.d/
grep -R "vm.max_map_count\|somaxconn" /etc/sysctl.d /usr/lib/sysctl.d /run/sysctl.d 2>/dev/null
```

### 15.4 Pod shows `SysctlForbidden`

This is usually not fixed by a host-level sysctl file. Check whether the pod is requesting an unsafe sysctl.

```bash
oc describe pod <pod> -n <namespace>
oc get kubeletconfig
oc get mcp --show-labels
```

Make sure:

- The target MCP has the label used by `KubeletConfig.spec.machineConfigPoolSelector`.
- `allowedUnsafeSysctls` includes the exact sysctl or correct pattern.
- The pod is actually scheduled to nodes in that MCP.
- SCC / Pod Security admission does not block the workload for another reason.

### 15.5 MachineConfig does not affect the intended nodes

Check selectors:

```bash
oc get mcp infra -o yaml
oc get nodes --show-labels
oc get mc 99-infra-sysctl -o yaml
```

You need alignment between:

```yaml
MachineConfig.metadata.labels.machineconfiguration.openshift.io/role
MachineConfigPool.spec.machineConfigSelector
MachineConfigPool.spec.nodeSelector
Node labels
```

For an `infra` pool:

- MC label should be `machineconfiguration.openshift.io/role: infra`.
- MCP `machineConfigSelector` should include `worker` and `infra`.
- MCP `nodeSelector` should match `node-role.kubernetes.io/infra: ""`.
- Nodes should have the infra role label.

### 15.6 Duplicate or conflicting MachineConfigs

List all relevant configs:

```bash
oc get mc | grep infra
oc get mc | grep worker
```

Remember:

- MachineConfigs are processed lexicographically by name.
- Worker configs are inherited by custom worker pools.
- A later config can overwrite the same path.
- Avoid multiple MachineConfigs managing the same file.

Good naming pattern:

```text
50-worker-base-sysctl
80-infra-performance-sysctl
99-infra-sysctl
```

But do not use high numbers as a habit without understanding merge order. Use clear ownership and avoid conflicts.

clusters/

      infra-tuned.yaml

Recommended GitOps practices:

- Keep Butane source files and generated MachineConfigs together.
- Add comments explaining why every sysctl exists.
- Add rollback instructions in the same directory.
- Separate cluster-wide worker configs from pool-specific configs.
- Review MachineConfig changes like OS changes, not like normal app YAML.
- Use canary pools for risky kernel arguments.
- Avoid editing default SCCs for sysctl needs; create custom controls where required.

## 17. Rollback Procedure

### 17.1 Roll back a sysctl MachineConfig

Delete the pool-specific MachineConfig:

```bash
oc delete mc 99-infra-sysctl
oc get mcp infra -w
```

The MCO renders a new config without that file. Depending on the file and disruption policy, affected nodes can reboot.

Verify removal:

```bash
oc debug node/<node>
chroot /host
ls -l /etc/sysctl.d/99-infra-sysctl.conf
sysctl vm.max_map_count
```

If the file is removed but the runtime value still exists, remember that some sysctls do not automatically revert to kernel defaults unless rebooted or explicitly set by another config.

### 17.2 Roll back kernel arguments

Delete or modify the MachineConfig containing the kernel arguments:

```bash
oc delete mc 99-lowlatency-kernelargs
oc get mcp lowlatency -w
```

Verify:

```bash
oc debug node/<node>
chroot /host
cat /proc/cmdline
```

### 17.3 Roll back unsafe sysctl allowlisting

Delete the KubeletConfig:

```bash
oc delete kubeletconfig allow-unsafe-sysctls-infra
oc get mcp infra -w
```

Also remove the MCP label if it is no longer used:

```bash
oc label machineconfigpool infra custom-kubelet-
```

## 19. Interview / Real-World Q&A

### Q1. Why not SSH into an OpenShift node and run `sysctl -w`?

Because it is not persistent, not declarative, not upgrade-safe, and can be overwritten by node reboot, replacement, MCO reconciliation, or TuneD. OpenShift expects node OS state to be managed through Operators and declarative objects.

### Q2. Does a MachineConfig always reboot nodes?

Many MachineConfig changes cause reboot. File changes under `/etc` commonly lead to MCO-controlled drain and reboot unless a node disruption policy changes behavior for supported cases. Kernel argument changes require reboot by nature.

### Q3. If I apply a MachineConfig to `worker`, will custom pools receive it?

Yes, custom worker pools inherit worker configs. This is why broad worker-level tuning can unintentionally affect infra, logging, storage, GPU, or other custom pools.

### Q4. What is the safest way to tune only logging nodes?

Create a logging MCP, label only logging nodes, schedule logging workloads there, and apply logging-specific MachineConfigs or TuneD profiles only to that MCP or node label.

### Q5. How do I know which rendered MachineConfig a node is using?

Use:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

### Q6. What if a sysctl is set in both `/etc/sysctl.d` and TuneD?

Avoid that design. If both manage the same key, final value depends on ordering, reapply behavior, profile application, and reboot/runtime timing. Assign single ownership.

### Q7. Is `allowedUnsafeSysctls` a MachineConfig field?

No. It is kubelet configuration, normally managed through a `KubeletConfig` custom resource. The MCO generates and applies machine config content behind the scenes, but you should not manually edit generated kubelet MachineConfigs.

### Q8. Can I create a custom MCP for control plane nodes?

Custom MCPs are for worker-derived pools. Control plane custom pools are not supported in the same way. Be very careful applying machine configs to master/control-plane nodes.

### Q9. What happens if I manually modify the sysctl file on a node?

The Machine Config Daemon can detect configuration drift. The node or pool can become degraded until the actual host state matches the rendered desired config again.

### Q10. What should I do before applying kernel args in production?

Use a canary pool, validate boot, check `/proc/cmdline`, observe node readiness, run workload smoke tests, and confirm rollback works.

## 20. Advanced Example: Logging Pool with `vm.max_map_count`

Many search/indexing workloads require a higher `vm.max_map_count` than default. Instead of applying it to all workers, isolate it to logging nodes.

### 20.1 Create logging MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: logging
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - logging
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/logging: ""
  maxUnavailable: 1
```

### 20.2 Apply logging sysctl MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-logging-vm-max-map-count
  labels:
    machineconfiguration.openshift.io/role: logging
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
        - path: /etc/sysctl.d/99-logging-vm-max-map-count.conf
          mode: 420
          overwrite: true
          contents:
            source: data:text/plain;charset=utf-8;base64,dm0ubWF4X21hcF9jb3VudCA9IDI2MjE0NAo=
```

The decoded content is:

```text
vm.max_map_count = 262144
```

Apply and watch:

```bash
oc apply -f logging-mcp.yaml
oc apply -f 99-logging-vm-max-map-count.yaml
oc get mcp logging -w
```

Validate:

```bash
oc debug node/<logging-node>
chroot /host
sysctl vm.max_map_count
```

## 22. Common Mistakes

### Mistake 1: Applying pool-specific tuning to all workers

Bad:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
```

This affects worker and custom worker-derived pools.

Better:

```yaml
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
```

### Mistake 2: Creating a node role label without MCP

If you label nodes `infra` but do not create a matching MCP, the node may still be managed as worker or create management ambiguity depending on labels. Dedicated node roles should have matching MCP design.

### Mistake 3: Managing same sysctl in MachineConfig and TuneD

This creates final-value ambiguity and hard-to-debug behavior.

### Mistake 4: Forgetting that kernel arguments require reboot

Kernel arguments are not runtime sysctls. They are boot parameters.

### Mistake 5: Thinking host sysctl automatically allows pod sysctl

A host-level value and a pod-level unsafe sysctl allowlist are different.

### Mistake 6: Editing generated MachineConfigs

Do not edit generated configs such as:

```text
rendered-worker-...
99-worker-generated-kubelet-...
```

Change the source object instead: `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig`, or `Tuned`.

### Mistake 7: Ignoring MCP degraded state

A degraded MCP can block future updates and create upgrade risk. Always fix degraded state before continuing.

## 24. Recommended Production Pattern

For a 10-year-experience OpenShift administrator, the expected approach is not just “create YAML and apply it.” The expected approach is operational ownership:

1. Understand the workload reason for the kernel/sysctl setting.
2. Confirm whether it is host-level, pod-level, or boot-time.
3. Scope it to a dedicated MCP.
4. Use GitOps and peer review.
5. Roll out to canary first.
6. Verify the rendered config and actual node state.
7. Watch application metrics, not only MCP status.
8. Keep a rollback path.
9. Avoid conflicting ownership between MachineConfig, KubeletConfig, and TuneD.
10. Document why each value exists.

The strongest design is:

```text
Workload requirement
        ↓
Dedicated node role label
        ↓
MachineConfigPool
        ↓
MachineConfig / KubeletConfig / Tuned
        ↓
Controlled MCO rollout
        ↓
Verification on node and workload
```
