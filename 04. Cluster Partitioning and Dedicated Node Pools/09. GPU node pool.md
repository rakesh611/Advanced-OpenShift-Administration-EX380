## 1. What is a GPU node pool?

A **GPU node pool** is a dedicated group of OpenShift worker nodes that contain GPU hardware and are reserved for GPU-accelerated workloads such as AI/ML training, inference, video processing, simulation, rendering, scientific computing, or vector-search acceleration.

In OpenShift administration, a GPU node pool is not only a group of machines. It is a complete operational boundary that normally includes:

- Specific worker nodes with GPU-capable instance types or bare-metal servers.
- Labels that identify the nodes as GPU-capable.
- Taints that prevent normal application pods from landing on expensive GPU nodes.
- Tolerations and node selectors or affinity in GPU workloads.
- Optional custom `MachineConfigPool` for node-level tuning and lifecycle control.
- Node Feature Discovery to detect GPU hardware.
- NVIDIA GPU Operator to install and manage the GPU driver stack.
- Monitoring through DCGM exporter metrics.
- Quota and RBAC controls for tenant usage.
- Maintenance procedures for driver rebuilds, OpenShift upgrades, and GPU hardware errors.

A GPU node pool answers this operational question:

> How do I make GPU hardware available to workloads while keeping it isolated, observable, secure, upgradeable, and cost-controlled?

## 2. Why GPU nodes should be partitioned

GPU nodes are not ordinary worker nodes. Treating them like normal workers is one of the most common mistakes in production OpenShift clusters.

### 2.1 Cost isolation

GPU nodes are expensive compared to normal CPU workers. If normal web apps, routers, logging collectors, build pods, or batch jobs are allowed to land on them, they consume CPU, memory, ephemeral storage, and network bandwidth on nodes that were purchased for GPU acceleration.

A GPU pool should normally be tainted so that only GPU workloads or required GPU operator components can schedule there.

### 2.2 Hardware specialization

GPU nodes often have:

- NVIDIA A10, L4, T4, A30, A40, A100, H100, H200, B-series, or cloud GPU variants.
- Special PCIe/NVLink topology.
- Larger memory and CPU allocations.
- High power and cooling requirements.
- Local NVMe scratch storage.
- Faster network interfaces for distributed training.
- Vendor-specific drivers and firmware expectations.

These characteristics make them different from standard OpenShift compute nodes.

### 2.3 Driver and kernel lifecycle

GPU nodes depend on a working chain:

```text
RHCOS kernel
  -> NVIDIA driver
  -> NVIDIA container toolkit
  -> Kubernetes device plugin
  -> GPU feature discovery
  -> DCGM exporter
  -> GPU workload container
```

During OpenShift upgrades, the RHCOS kernel can change. The GPU driver DaemonSet might need to rebuild or reload drivers. If GPU nodes are mixed with general nodes, troubleshooting and maintenance become harder.

### 2.4 Scheduling correctness

A GPU workload must run on a node that:

- Has compatible GPU hardware.
- Has the GPU device plugin running.
- Advertises `nvidia.com/gpu` or MIG resources.
- Has enough free GPU capacity.
- Matches tenant, environment, zone, model, and isolation rules.

A simple `resources.limits.nvidia.com/gpu: 1` is not enough for mature placement. Senior administrators usually combine GPU limits with node labels, taints, affinity, quota, and sometimes topology spread constraints.

### 2.5 Performance isolation

GPU applications are sensitive to:

- CPU starvation.
- Memory pressure.
- PCIe bottlenecks.
- NUMA locality.
- Network bandwidth.
- Storage throughput.
- Noisy neighbors.
- GPU memory fragmentation.
- Long-running kernels.

Partitioning prevents unrelated workloads from degrading GPU jobs.

### 2.6 Security and multi-tenancy

GPU devices are shared host hardware exposed into containers through the device plugin and runtime stack. Tenant isolation must be planned carefully, especially when using GPU sharing methods such as time-slicing.

MIG can provide stronger hardware-level partitioning on supported NVIDIA GPUs. Time-slicing improves utilization but does not provide memory or fault isolation between replicas.

### 2.7 Operational blast-radius control

With a dedicated GPU pool, you can:

- Drain GPU nodes without affecting general apps.
- Upgrade GPU nodes in a controlled sequence.
- Apply GPU-specific kubelet or CRI-O settings.
- Scale GPU capacity independently.
- Use dedicated monitoring and alerting.
- Apply stricter admission and quota rules.

## 3. Where GPU node pools fit in cluster partitioning

A mature OpenShift cluster often uses several logical pools:

| Pool type | Purpose | Example workloads |
|---|---|---|
| Control plane | Kubernetes/OpenShift control plane | API server, etcd, scheduler, controllers |
| Infra node pool | Platform infrastructure | Ingress router, registry, monitoring, logging, GitOps controllers |
| App worker pool | General application workloads | Web apps, APIs, microservices |
| Storage node pool | ODF/Ceph or storage services | OSDs, MONs, MDS, RGW |
| Logging node pool | Log processing and storage | LokiStack, collectors, log gateways |
| Monitoring node pool | Metrics stack | Prometheus, Alertmanager, Thanos, observability |
| GPU node pool | Accelerator workloads | ML training, inference, CUDA jobs, AI workloads |

GPU node pools are usually closer to **specialized workload pools** than generic application pools. They should not be used as the default landing zone for normal pods.

A common production layout:

```text
3 control-plane nodes
3 infra nodes
6 app worker nodes
3 storage nodes
2 monitoring/logging nodes
4 GPU nodes
```

For smaller clusters, GPU nodes might also carry the `worker` role, but they should still be isolated with labels and taints.

## 4. Core OpenShift and Kubernetes building blocks

### 4.1 Node labels

Labels describe node identity or capability.

Examples:

```bash
oc label node worker-gpu-01 node-role.kubernetes.io/gpu=
oc label node worker-gpu-01 node.openshift.io/pool=gpu
oc label node worker-gpu-01 accelerator=nvidia
oc label node worker-gpu-01 gpu.openshift.io/class=training
```

Labels are used by:

- `nodeSelector`
- `nodeAffinity`
- project node selector annotations
- MachineConfigPool node selectors
- monitoring queries
- admin inventory

### 4.2 Taints

Taints repel pods unless the pod has a matching toleration.

Example:

```bash
oc adm taint nodes worker-gpu-01 accelerator=nvidia-gpu:NoSchedule
```

This means normal pods cannot schedule on `worker-gpu-01` unless they tolerate the taint.

### 4.3 Tolerations

A toleration allows a pod to be scheduled on a tainted node.

Example:

```yaml
tolerations:
- key: "accelerator"
  operator: "Equal"
  value: "nvidia-gpu"
  effect: "NoSchedule"
```

Tolerations do not force the pod onto that node. They only allow it. To force or strongly guide scheduling, combine tolerations with `nodeSelector` or `nodeAffinity`.

### 4.4 Node selector

A `nodeSelector` is a simple exact-match placement rule.

```yaml
nodeSelector:
  node-role.kubernetes.io/gpu: ""
```

The pod can run only on nodes with that label.

### 4.5 Node affinity

Node affinity is more expressive than `nodeSelector`.

Example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: gpu.openshift.io/model
          operator: In
          values:
          - a100
          - h100
```

Use affinity when you need multiple allowed values, soft preferences, zone-aware logic, or exclusion rules.

### 4.6 MachineSet

A `MachineSet` creates and manages a group of worker machines on supported infrastructure providers.

For GPU nodes, a MachineSet can define:

- GPU instance type.
- Availability zone.
- Labels applied to new nodes.
- Taints applied to new nodes.
- Replica count.

This is better than manually labeling nodes because replacement nodes inherit the correct labels and taints.

### 4.7 MachineConfigPool

A `MachineConfigPool` groups nodes for RHCOS and node-level configuration lifecycle.

A GPU custom MachineConfigPool is useful when GPU nodes require:

- Different kubelet settings.
- Different CRI-O settings.
- Kernel arguments.
- Special node tuning.
- Controlled update behavior.
- Dedicated reboot sequencing.

Important rule: a node can have multiple role labels, but it should be selected by only one MachineConfigPool. Poor MCP selector design can cause degraded or unexpected upgrade behavior.

### 4.8 NVIDIA GPU Operator

The NVIDIA GPU Operator manages the GPU software stack on OpenShift. It deploys components such as:

- NVIDIA driver DaemonSet.
- NVIDIA container toolkit.
- NVIDIA Kubernetes device plugin.
- GPU Feature Discovery.
- DCGM exporter.
- MIG manager.
- Validator pods.

### 4.9 Node Feature Discovery

Node Feature Discovery detects hardware and system features and labels nodes. For NVIDIA GPUs, NFD detects the NVIDIA PCI vendor ID and applies labels such as:

```text
feature.node.kubernetes.io/pci-10de.present=true
```

`10de` is NVIDIA's PCI vendor ID.

## 5. GPU enablement architecture in OpenShift

A simplified architecture looks like this:

```text
GPU worker node
├── RHCOS host
├── NVIDIA GPU hardware
├── NVIDIA driver loaded on node
├── NVIDIA container toolkit integrated with container runtime
├── NVIDIA device plugin advertises resources to kubelet
├── kubelet reports nvidia.com/gpu capacity to API server
├── scheduler places pods requesting nvidia.com/gpu
├── container receives assigned GPU device
└── DCGM exporter exposes GPU metrics
```

Control flow:

```text
1. Add GPU node to OpenShift.
2. NFD detects hardware and labels the node.
3. GPU Operator sees matching node labels.
4. GPU Operator deploys driver/toolkit/device-plugin/DCGM components.
5. Device plugin registers GPU devices with kubelet.
6. Node capacity shows nvidia.com/gpu.
7. GPU workloads request nvidia.com/gpu.
8. Scheduler places pods only where allocatable GPU exists and placement rules match.
```

A senior administrator should understand that **OpenShift does not magically use GPUs just because the node has GPU hardware**. The node must be discovered, the driver stack must be installed, the device plugin must register resources, and the workload must request the correct extended resource.

## 6. GPU node pool design models

### 6.1 Model 1: Simple GPU workers

Use this for labs or very small clusters.

Characteristics:

- GPU nodes remain ordinary workers.
- Nodes are manually labeled and tainted.
- No custom MachineConfigPool.
- GPU Operator installed cluster-wide.

Pros:

- Easy to set up.
- Good for proof of concept.

Cons:

- Less lifecycle control.
- Manual labels/taints might be lost when nodes are replaced.
- Not ideal for production.

### 6.2 Model 2: Dedicated GPU pool using MachineSet labels and taints

Use this for most production cloud clusters.

Characteristics:

- Separate GPU MachineSet.
- Labels and taints defined in MachineSet template.
- GPU workloads use toleration and node selector or affinity.
- GPU Operator handles the driver stack.

Pros:

- Replacement nodes inherit configuration.
- Autoscaling is possible.
- Clear workload isolation.

Cons:

- Node-level OS tuning still uses the worker MCP unless a custom MCP is added.

### 6.3 Model 3: Dedicated GPU MachineConfigPool

Use this when GPU nodes require different node-level configuration.

Characteristics:

- GPU nodes have a custom role label such as `node-role.kubernetes.io/gpu`.
- Custom MCP selects GPU nodes.
- GPU-specific `MachineConfig`, `KubeletConfig`, or `ContainerRuntimeConfig` can target only GPU nodes.

Pros:

- Strong lifecycle separation.
- Controlled updates and reboots.
- Better for regulated or performance-sensitive clusters.

Cons:

- Requires careful MCP selector design.
- Misconfiguration can degrade the pool.
- Adds operational complexity.

### 6.4 Model 4: Multiple GPU pools by hardware class

Use this when hardware differs significantly.

Example:

```text
gpu-t4-pool      -> low-cost inference/dev
gpu-l4-pool      -> inference/video/AI service
gpu-a100-pool    -> training and large inference
gpu-h100-pool    -> high-end training/LLM workloads
```

Suggested labels:

```text
gpu.openshift.io/vendor=nvidia
gpu.openshift.io/model=a100
gpu.openshift.io/memory=80gb
gpu.openshift.io/class=training
gpu.openshift.io/sharing=none
```

### 6.5 Model 5: MIG-based pool

Use this when supported GPUs such as A100/H100 are partitioned into MIG instances.

Example resources:

```text
nvidia.com/mig-1g.10gb
nvidia.com/mig-2g.20gb
nvidia.com/mig-3g.40gb
```

Good for:

- Multi-tenant inference.
- Small notebooks.
- Predictable partitioned GPU slices.
- Better isolation than time-slicing.

### 6.6 Model 6: Time-sliced GPU pool

Use this for dev/test or small inference tasks where strong isolation is less important.

Characteristics:

- One physical GPU is advertised as multiple replicas.
- Pods receive logical replicas.
- No memory or fault isolation like MIG.

Good for:

- Low-utilization development workloads.
- Notebook experimentation.
- Small jobs that do not require full GPU.

Not ideal for:

- Untrusted tenants.
- Strict latency workloads.
- Production workloads needing fault isolation.

## 7. Labeling strategy for GPU node pools

A weak labeling strategy creates future scheduling problems. A good strategy separates **role**, **capability**, **model**, **tenant**, and **lifecycle**.

### 7.1 Minimum labels

```bash
oc label node <node> node-role.kubernetes.io/gpu=
oc label node <node> node.openshift.io/pool=gpu
oc label node <node> accelerator=nvidia-gpu
```

### 7.2 Recommended production labels

```bash
oc label node <node> node-role.kubernetes.io/gpu=
oc label node <node> node.openshift.io/pool=gpu
oc label node <node> gpu.openshift.io/vendor=nvidia
oc label node <node> gpu.openshift.io/model=a100
oc label node <node> gpu.openshift.io/class=training
oc label node <node> gpu.openshift.io/sharing=none
oc label node <node> gpu.openshift.io/mig-capable=true
oc label node <node> workload.openshift.io/gpu=true
```

### 7.3 Label categories

| Category | Example | Purpose |
|---|---|---|
| Role | `node-role.kubernetes.io/gpu=` | OpenShift/admin role identity |
| Pool | `node.openshift.io/pool=gpu` | Human-readable pool membership |
| Vendor | `gpu.openshift.io/vendor=nvidia` | Vendor-specific targeting |
| Model | `gpu.openshift.io/model=a100` | Hardware-specific scheduling |
| Class | `gpu.openshift.io/class=training` | Workload class alignment |
| Sharing | `gpu.openshift.io/sharing=mig` | Scheduling based on sharing mode |
| Tenant | `tenant=ml-platform` | Dedicated tenant pool |
| Zone | `topology.kubernetes.io/zone=...` | HA and distributed training |

### 7.4 Do not rely only on automatic labels

NFD and GPU Feature Discovery create useful hardware labels, but for production scheduling you should still maintain platform-owned labels.

Why?

- Automatic label names can be too detailed for application teams.
- Hardware labels might change after driver/operator changes.
- Business-level scheduling needs stable abstractions such as `gpu.openshift.io/class=inference`.
- You might want to move workloads between hardware generations without changing every application manifest.

Use automatic labels for discovery and admin verification. Use platform labels for workload contracts.

## 8. Taints and tolerations for GPU isolation

### 8.1 Recommended taint

```bash
oc adm taint nodes <gpu-node> accelerator=nvidia-gpu:NoSchedule
```

This prevents non-GPU workloads from scheduling there.

### 8.2 Alternative taints

```bash
oc adm taint nodes <gpu-node> nvidia.com/gpu=true:NoSchedule
oc adm taint nodes <gpu-node> gpu.openshift.io/dedicated=true:NoSchedule
oc adm taint nodes <gpu-node> dedicated=gpu:NoSchedule
```

Choose a key naming standard and keep it consistent.

### 8.3 Toleration example

```yaml
tolerations:
- key: "accelerator"
  operator: "Equal"
  value: "nvidia-gpu"
  effect: "NoSchedule"
```

### 8.4 Toleration plus node selector

This is the common production pattern:

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/gpu: ""
  tolerations:
  - key: "accelerator"
    operator: "Equal"
    value: "nvidia-gpu"
    effect: "NoSchedule"
```

The toleration allows scheduling onto GPU nodes. The node selector requires GPU nodes.

### 8.5 Why toleration alone is not enough

A pod with only a toleration can still land on non-GPU nodes if it does not request GPU resources or if the scheduler finds another eligible node. A toleration is permission, not placement.

For GPU workloads, always use at least one of:

- `resources.limits.nvidia.com/gpu`
- `nodeSelector`
- `nodeAffinity`
- project node selector

Most production GPU pods use a GPU resource limit plus a node selector or affinity.

### 8.6 Use `NoSchedule`, not usually `NoExecute`

For GPU reservation, `NoSchedule` is usually the safest effect.

| Effect | Behavior | GPU pool recommendation |
|---|---|---|
| `NoSchedule` | Blocks new pods without toleration | Recommended default |
| `PreferNoSchedule` | Soft avoidance | Useful only for soft separation |
| `NoExecute` | Evicts existing pods without toleration | Use carefully; can disrupt workloads |

Use `NoExecute` only when you intentionally want non-tolerating pods evicted.

## 9. MachineSet-based GPU node creation

In cloud-based OpenShift clusters, GPU nodes should usually be created from a separate MachineSet.

### 9.1 Why MachineSet is preferred

If you label and taint a node manually, those settings might be lost when the node is replaced. If labels and taints are part of the MachineSet template, new machines inherit the correct configuration.

### 9.2 Inspect existing MachineSets

```bash
oc get machinesets -n openshift-machine-api
oc get machines -n openshift-machine-api -o wide
```

### 9.3 Create a GPU MachineSet from an existing worker MachineSet

Typical approach:

```bash
oc get machineset <existing-worker-machineset> \
  -n openshift-machine-api \
  -o yaml > gpu-machineset.yaml
```

Edit:

- `metadata.name`
- `spec.selector.matchLabels.machine.openshift.io/cluster-api-machineset`
- `spec.template.metadata.labels.machine.openshift.io/cluster-api-machineset`
- instance type / flavor
- zone
- replicas
- labels
- taints

### 9.4 Generic MachineSet taint and label snippet

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: cluster-gpu-a100-us-east-1a
  namespace: openshift-machine-api
spec:
  replicas: 2
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-machineset: cluster-gpu-a100-us-east-1a
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machineset: cluster-gpu-a100-us-east-1a
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/gpu: ""
          node.openshift.io/pool: gpu
          accelerator: nvidia-gpu
          gpu.openshift.io/vendor: nvidia
          gpu.openshift.io/model: a100
          gpu.openshift.io/class: training
      taints:
      - key: accelerator
        value: nvidia-gpu
        effect: NoSchedule
      providerSpec:
        value:
          # Provider-specific GPU instance settings go here.
          # Example fields differ for AWS, Azure, GCP, vSphere, OpenStack, Bare Metal, etc.
          instanceType: <gpu-instance-type>
```

### 9.5 Scale the GPU MachineSet

```bash
oc scale machineset cluster-gpu-a100-us-east-1a \
  -n openshift-machine-api \
  --replicas=2
```

### 9.6 Verify labels and taints on resulting nodes

```bash
oc get nodes -L node-role.kubernetes.io/gpu,node.openshift.io/pool,accelerator,gpu.openshift.io/model
oc describe node <gpu-node> | egrep -i "Taints|Roles|Labels|nvidia|gpu"
```

## 10. Custom MachineConfigPool for GPU nodes

A custom MachineConfigPool is optional, but it is valuable in advanced environments.

### 10.1 When to create a GPU MCP

Create a custom GPU MCP when you need:

- GPU-specific kubelet tuning.
- GPU-specific CRI-O configuration.
- GPU-specific kernel arguments.
- GPU-specific OS configuration.
- A separate update/reboot strategy.
- Clear lifecycle status for GPU nodes.
- Different `maxUnavailable` settings.

Do not create a custom MCP just because the node has a GPU. For many clusters, MachineSet labels/taints plus GPU Operator are enough.

### 10.2 GPU MCP example

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: gpu
  labels:
    pools.operator.machineconfiguration.openshift.io/gpu: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - gpu
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/gpu: ""
  maxUnavailable: 1
```

Explanation:

- `nodeSelector` selects nodes with `node-role.kubernetes.io/gpu`.
- `machineConfigSelector` includes worker configs and GPU-specific configs.
- `maxUnavailable: 1` updates one GPU node at a time.

### 10.3 GPU-specific MachineConfig example

Use MachineConfig only for OS-level settings that must be applied to GPU nodes. Do **not** install NVIDIA drivers manually with MachineConfig if the NVIDIA GPU Operator is responsible for driver management.

Example placeholder for a GPU-specific file:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-gpu-node-marker
  labels:
    machineconfiguration.openshift.io/role: gpu
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/gpu-node-pool
        mode: 0644
        contents:
          source: data:text/plain;charset=utf-8;base64,R1BVIHBvb2wgbm9kZQo=
```

### 10.4 KubeletConfig for GPU pool

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: gpu-kubelet-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/gpu: ""
  kubeletConfig:
    maxPods: 80
    systemReserved:
      cpu: "2000m"
      memory: "4Gi"
    kubeReserved:
      cpu: "1000m"
      memory: "2Gi"
```

Use this carefully. Lowering `maxPods` on GPU nodes can be useful because GPU workloads are often heavy and fewer pods per node improves operational predictability.

### 10.5 MCP verification commands

```bash
oc get mcp
oc describe mcp gpu
oc get nodes -l node-role.kubernetes.io/gpu=
oc get machineconfig | grep gpu
```

### 10.6 Common MCP mistakes

| Mistake | Result | Fix |
|---|---|---|
| Node selected by more than one custom MCP | Degraded or unpredictable behavior | Ensure selector exclusivity |
| Forgot worker configs in selector | Missing inherited worker config behavior | Include worker and custom role as required |
| Manual changes on RHCOS host | MCD detects drift | Use MachineConfig, do not manually edit managed files |
| `maxUnavailable` too high | Too many GPU nodes reboot together | Set `maxUnavailable: 1` for expensive pools |
| GPU node label added before planning | Node may move pools unexpectedly | Plan labels and MCP before applying broadly |

## 11. Node Feature Discovery and GPU discovery

### 11.1 Purpose

Node Feature Discovery detects hardware features and labels nodes. For GPU nodes, it helps the cluster identify nodes containing NVIDIA PCI devices.

### 11.2 Install NFD Operator

Install the Node Feature Discovery Operator from the OpenShift console or CLI. After installation, create a `NodeFeatureDiscovery` instance.

Verify pods:

```bash
oc get pods -n openshift-nfd
```

### 11.3 Verify NVIDIA PCI label

```bash
oc describe node <gpu-node> | grep feature.node.kubernetes.io/pci-10de.present
```

Expected:

```text
feature.node.kubernetes.io/pci-10de.present=true
```

### 11.4 Verify across all non-control-plane nodes

```bash
oc describe node | egrep 'Name:|Roles:|pci-10de|nvidia'
```

### 11.5 NFD vs GPU Feature Discovery

Do not confuse these two:

| Component | Purpose |
|---|---|
| Node Feature Discovery | General hardware/system discovery; labels nodes with PCI, CPU, kernel, OS features |
| GPU Feature Discovery | NVIDIA-specific GPU labels such as product/model and GPU capabilities |

NFD is usually a prerequisite for the NVIDIA GPU Operator. GPU Feature Discovery is managed as part of the NVIDIA GPU Operator stack.

## 12. NVIDIA GPU Operator deployment

### 12.1 Purpose

The NVIDIA GPU Operator automates the lifecycle of the GPU software stack required for GPU workloads on OpenShift.

It commonly manages:

- Driver container.
- NVIDIA Container Toolkit.
- Device plugin.
- GPU Feature Discovery.
- DCGM exporter.
- Node status exporter.
- MIG manager.
- Operator validator.

### 12.2 Recommended namespace

Use:

```text
nvidia-gpu-operator
```

This is the commonly recommended namespace. If using another namespace, ensure monitoring is enabled as required.

### 12.3 Create namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: nvidia-gpu-operator
```

Apply:

```bash
oc apply -f nvidia-gpu-operator-namespace.yaml
```

### 12.4 Enable cluster monitoring for the namespace


## 13. How GPU resources appear to Kubernetes

### 13.1 Extended resource

The NVIDIA device plugin advertises GPUs as extended resources, typically:

```text
nvidia.com/gpu
```

Check node capacity:

```bash
oc describe node <gpu-node> | egrep -A8 'Capacity|Allocatable|nvidia.com'
```

Example:

```text
Capacity:
  cpu:                64
  memory:             512Gi
  nvidia.com/gpu:     4
Allocatable:
  cpu:                63500m
  memory:             500Gi
  nvidia.com/gpu:     4
```

### 13.2 Requesting GPU in a pod

GPU workloads request GPU resources with `resources.limits`.

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

For Kubernetes GPU scheduling:

- GPU resources are normally specified in `limits`.
- If both `requests` and `limits` are used for GPU, they must be equal.
- You cannot request a GPU without a corresponding limit.
- Standard GPU allocation is whole-device allocation unless MIG or time-slicing is configured.

### 13.3 Scheduler behavior

The Kubernetes scheduler checks:

- Does the node have allocatable `nvidia.com/gpu`?
- Is enough GPU capacity free?
- Does the pod tolerate node taints?
- Does the pod match node selector or node affinity?
- Does the namespace/project selector allow this node?
- Does quota allow the GPU request?

The scheduler does not deeply understand your model performance, CUDA memory needs, or NVLink topology unless you expose that as labels and scheduling rules.

## 14. Scheduling GPU workloads

### 14.1 Minimal GPU pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-test
spec:
  restartPolicy: Never
  containers:
  - name: cuda
    image: nvcr.io/nvidia/cuda:12.4.1-base-ubi9
    command: ["nvidia-smi"]

      limits:
        nvidia.com/gpu: 1
```

This works only if no GPU node taint blocks the pod.

### 14.2 Production GPU pod with isolation

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-test-isolated
  namespace: ml-team-a
spec:
  restartPolicy: Never
  nodeSelector:
    node-role.kubernetes.io/gpu: ""
    gpu.openshift.io/class: training
  tolerations:
  - key: "accelerator"
    operator: "Equal"
    value: "nvidia-gpu"
    effect: "NoSchedule"
  containers:
  - name: cuda
    image: nvcr.io/nvidia/cuda:12.4.1-base-ubi9
    command: ["nvidia-smi"]
    resources:
      limits:
        nvidia.com/gpu: 1
        cpu: "4"
        memory: 16Gi
      requests:
        cpu: "4"
        memory: 16Gi
```

### 14.3 Deployment example for inference

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: image-inference
  namespace: ml-inference
spec:
  replicas: 2
  selector:
    matchLabels:
      app: image-inference
  template:
    metadata:
      labels:
        app: image-inference
    spec:
      nodeSelector:
        node-role.kubernetes.io/gpu: ""
        gpu.openshift.io/class: inference
      tolerations:
      - key: "accelerator"
        operator: "Equal"
        value: "nvidia-gpu"
        effect: "NoSchedule"
      containers:
      - name: server
        image: registry.example.com/ml/image-inference:1.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: "2"
            memory: 8Gi
          limits:
            cpu: "4"
            memory: 16Gi
            nvidia.com/gpu: 1
```

### 14.4 Required node affinity by GPU model

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: gpu.openshift.io/model
          operator: In
          values:
          - a100
          - h100
```

### 14.5 Preferred node affinity

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 90
      preference:
        matchExpressions:
        - key: gpu.openshift.io/model
          operator: In
          values:
          - h100
    - weight: 50
      preference:
        matchExpressions:
        - key: topology.kubernetes.io/zone
          operator: In
          values:
          - zone-a
```

Use preferred affinity when the workload can run on multiple GPU types but performs better on one.

### 14.6 Topology spread for inference replicas

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: ScheduleAnyway
  labelSelector:
    matchLabels:
      app: image-inference
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: image-inference
```

Use this when you need high availability across zones and hosts.

### 14.7 Scheduling anti-patterns

| Anti-pattern | Why it is bad | Better approach |
|---|---|---|
| GPU nodes have no taint | Normal pods consume GPU node capacity | Taint GPU nodes |
| Workload has toleration but no GPU limit | Pod may not actually use GPU scheduling | Set `nvidia.com/gpu` limit |
| Workload has GPU limit but no node selector | It can work, but lacks model/class control | Add node selector/affinity |
| All GPU nodes have same generic label only | Cannot target model/MIG/class | Add model and class labels |
| Time-slicing for untrusted tenants | Weak isolation | Use MIG or separate nodes |
| Multiple teams share pool without quota | Capacity conflict | Enforce ResourceQuota |

## 15. Project-level GPU isolation

OpenShift supports project-level node selectors through namespace/project annotations.

### 15.1 Create GPU project with node selector

```yaml
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: ml-team-a
  annotations:
    openshift.io/node-selector: "node-role.kubernetes.io/gpu=,gpu.openshift.io/class=training"
    scheduler.alpha.kubernetes.io/defaultTolerations: >-
      [{"key":"accelerator","operator":"Equal","value":"nvidia-gpu","effect":"NoSchedule"}]
```

Apply:

```bash
oc apply -f ml-team-a-project.yaml
```

### 15.2 Benefits

- Application teams do not need to repeat node selector and toleration in every manifest.
- Platform team controls placement policy centrally.
- Reduces accidental scheduling onto wrong nodes.

### 15.3 Caution

Project node selectors can conflict with pod-level selectors. If a pod specifies a different selector, it might fail admission or remain unschedulable.

Always document the namespace scheduling contract for application teams.

## 16. ResourceQuota and tenant governance

### 16.1 Why quota matters

GPU capacity is limited and expensive. Without quota, one team can consume all GPUs.

### 16.2 ResourceQuota example

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: gpu-quota
  namespace: ml-team-a
spec:
  hard:
    requests.cpu: "64"
    requests.memory: 256Gi
    limits.cpu: "128"
    limits.memory: 512Gi
    requests.nvidia.com/gpu: "4"
```

Some clusters and admission configurations rely on `requests.nvidia.com/gpu` for extended GPU resource quota. Validate quota behavior in your OpenShift version and policy stack.

### 16.3 Quota verification

```bash
oc describe quota gpu-quota -n ml-team-a
oc get resourcequota -n ml-team-a
```

### 16.4 RBAC governance

Recommended controls:

- Only platform admins can create GPU namespaces.
- Only approved teams receive GPU quota.
- Only approved service accounts can deploy GPU workloads.
- Developers should not be able to modify namespace node selectors or default tolerations.
- Use GitOps to manage GPU project onboarding.

### 16.5 Admission policy ideas

Use policy engines such as Gatekeeper, Kyverno, or OpenShift admission controls to enforce:

- GPU pods must have CPU and memory requests.
- GPU pods must use approved images.
- GPU pods must specify node affinity or use approved GPU namespaces.
- GPU pods cannot use hostPath unless explicitly approved.
- GPU pods cannot run privileged unless part of the GPU Operator.
- Time-sliced pools are not used by production namespaces.

## 17. MIG, time-slicing, and GPU sharing models

### 17.1 Default model: full GPU allocation

By default, Kubernetes schedules GPU resources as whole extended resources.

Example:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

This means the pod gets one GPU device from the node.

### 17.2 MIG: Multi-Instance GPU

MIG allows supported NVIDIA GPUs to be partitioned into multiple hardware-isolated GPU instances.

Example resources:

```text
nvidia.com/mig-1g.10gb
nvidia.com/mig-2g.20gb
nvidia.com/mig-3g.40gb
```

Workload example:

```yaml
resources:
  limits:
    nvidia.com/mig-1g.10gb: 1
```

Use MIG for:

- Multi-tenant inference.
- Notebook environments.
- Small-to-medium GPU workloads.
- Better isolation than time-slicing.
- Predictable GPU memory partitioning.

### 17.3 MIG operational notes

- MIG requires supported hardware.
- MIG mode changes can disrupt running GPU workloads.
- Drain GPU nodes before reconfiguring MIG geometry.
- Use labels to identify MIG configuration.
- Verify allocatable resources after MIG reconfiguration.

Useful verification:

```bash
oc describe node <gpu-node> | grep nvidia.com/mig
oc describe node <gpu-node> | grep nvidia.com/mig.config
```

### 17.4 Time-slicing

Time-slicing advertises multiple logical replicas of a GPU. CUDA workloads are multiplexed on the same underlying device.

Use time-slicing for:

- Development notebooks.
- Low-duty-cycle inference.
- Training demos.
- Non-critical workloads.

Avoid time-slicing for:

- Strict production isolation.
- Untrusted tenants.
- Latency-sensitive workloads.
- Workloads that can consume all GPU memory.

### 17.5 MIG vs time-slicing

| Feature | MIG | Time-slicing |
|---|---|---|
| Hardware isolation | Yes, on supported GPUs | No |
| Memory isolation | Yes | No |
| Fault isolation | Better | Weak |
| Supported hardware | MIG-capable GPUs | Broader NVIDIA support |
| Best use case | Production partitioning | Dev/test utilization |
| Resource names | `nvidia.com/mig-*` | Usually `nvidia.com/gpu` replicas |

### 17.6 Pool design for sharing

Recommended separation:

```text
gpu-prod-full       -> full GPU, no sharing
gpu-prod-mig        -> MIG slices for production inference
gpu-dev-timeslice   -> shared GPUs for notebooks/dev
gpu-research        -> flexible experimental pool
```

Each pool should have different labels, taints, quotas, and policies.

## 19. Autoscaling GPU node pools

### 19.1 Why GPU autoscaling is different

GPU autoscaling must consider:

- High instance cost.
- Long node provisioning time.
- Driver installation time.
- Image pull time for large AI containers.
- Warm-up time for model loading.
- Quota and cloud capacity constraints.
- Zone-specific GPU availability.

Autoscaling GPU nodes is possible, but it is not as fast as scaling normal pods.

### 19.2 MachineAutoscaler

A `MachineAutoscaler` can scale a GPU MachineSet.

Example:

```yaml
apiVersion: autoscaling.openshift.io/v1beta1
kind: MachineAutoscaler
metadata:
  name: gpu-a100-zone-a
  namespace: openshift-machine-api
spec:
  minReplicas: 0
  maxReplicas: 4
  scaleTargetRef:
    apiVersion: machine.openshift.io/v1beta1
    kind: MachineSet
    name: cluster-gpu-a100-us-east-1a
```

### 19.3 ClusterAutoscaler

The cluster autoscaler watches pending pods and scales MachineSets when additional nodes can satisfy those pods.

For GPU workloads, ensure pending pods have:

- GPU resource limits.
- Correct tolerations.
- Correct node selectors or affinity.
- No impossible quota or namespace selector conflicts.

### 19.4 Scale-from-zero considerations

When scaling GPU MachineSets from zero, the autoscaler needs enough information from the MachineSet template to understand future node labels and taints.

Best practices:

- Put labels and taints in the MachineSet template.
- Keep pod node affinity compatible with MachineSet labels.
- Avoid using labels that only appear after GPU Feature Discovery if scaling from zero depends on them.
- Use stable platform labels for scheduling, not only hardware-discovered labels.

### 19.5 Warm pool strategy

For production inference, keep at least one GPU node warm per critical pool.

Reasons:

- GPU node provisioning can take minutes.
- Driver stack readiness can take additional time.
- Model images can be large.
- Cold-start latency might violate SLOs.

Example:

```text
minReplicas: 1 for production inference
minReplicas: 0 for dev/test batch workloads
```

## 20. Upgrade, lifecycle, and maintenance strategy

### 20.1 OpenShift upgrade impact

During OpenShift upgrades:

- RHCOS can be updated.
- Kernel can change.
- MachineConfigPool nodes drain and reboot.
- NVIDIA driver DaemonSet might rebuild driver modules.
- GPU Operator compatibility must be maintained.

### 20.2 Pre-upgrade checklist

Before upgrading OpenShift:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pods -n nvidia-gpu-operator
oc get clusterpolicy -n nvidia-gpu-operator
oc describe clusterpolicy gpu-cluster-policy -n nvidia-gpu-operator
```

Check:

- GPU Operator supports the target OpenShift version.
- Driver version supports the target kernel/RHCOS.
- No MCP is degraded.
- GPU workloads have PDBs where appropriate.
- Long-running training jobs have checkpointing.
- Critical inference services have capacity in other zones/pools.

### 20.3 Upgrade sequencing

Recommended:

1. Validate GPU Operator compatibility.
2. Upgrade non-production GPU pool first if available.
3. Watch GPU MCP update status.
4. Verify driver DaemonSet readiness.
5. Run `nvidia-smi` validation pod.
6. Resume production workload rollout.

### 20.4 Drain strategy

For planned GPU node maintenance:

```bash
oc adm cordon <gpu-node>
oc adm drain <gpu-node> \
  --ignore-daemonsets \
  --delete-emptydir-data \
  --timeout=30m
```

For GPU training jobs, coordinate with application owners. Draining can kill long-running jobs unless they checkpoint or are controlled by resilient job frameworks.

### 20.5 Return node to service

```bash
oc adm uncordon <gpu-node>
oc describe node <gpu-node> | grep -i nvidia
```

Run validation pod:

```bash
oc apply -f nvidia-smi.yaml
oc logs nvidia-smi
oc delete pod nvidia-smi
```

## 21. Security and multi-tenancy considerations

### 21.1 Operator privilege boundary

The GPU Operator deploys privileged components because drivers and device integration require host-level access. This privilege should be limited to the operator namespace and managed by cluster administrators.

Application workloads should not run privileged just because they need a GPU.

### 21.2 SCC considerations

Most GPU application pods should run under standard restricted policies if their image supports non-root execution.

Common issue:

- Many CUDA sample images run as root.
- OpenShift restricted security might block them.
- Do not blindly grant `privileged` or broad SCC.

Better options:

- Use UBI-based CUDA images that support arbitrary UID.
- Build application images for OpenShift restricted security.
- Grant minimal SCC exceptions only when justified.

### 21.3 Tenant separation

Use separate namespaces and quotas:

```text
ml-team-a
ml-team-b
ml-inference-prod
ml-research-dev
```

Each namespace should have:

- ResourceQuota for GPUs.
- CPU/memory quota.
- NetworkPolicy.
- Image policy.
- RBAC boundaries.
- Optional project node selector/toleration.

### 21.4 MIG for stronger isolation

For supported GPUs, MIG is preferred over time-slicing when multiple tenants share a physical GPU because MIG provides hardware-level partitioning of compute and memory resources.

### 21.5 Time-slicing risk

Time-slicing does not provide memory or fault isolation between replicas. A bad or greedy workload can affect other workloads sharing the same physical GPU.

Use time-slicing only when tenants are trusted or workloads are non-critical.

### 21.6 Image security

GPU images are often very large and include Python, CUDA, ML frameworks, and many dependencies.

Controls:

- Use trusted registries.
- Scan images.
- Pin image digests for production.
- Avoid running unknown notebook images on production GPU pools.
- Separate dev notebook pools from production inference pools.

## 23. Storage, networking, and performance design

### 23.1 CPU-to-GPU balance

A GPU workload still needs CPU. Poor CPU allocation can make GPU utilization low.

Recommended:

- Set CPU and memory requests explicitly.
- Avoid tiny CPU requests for GPU jobs.
- Monitor GPU utilization and CPU throttling together.

Bad example:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 1Gi
  limits:
    nvidia.com/gpu: 1
```

Better example:

```yaml
resources:
  requests:
    cpu: "4"
    memory: 16Gi
  limits:
    cpu: "8"
    memory: 32Gi
    nvidia.com/gpu: 1
```

### 23.2 Storage throughput

Training jobs often require fast data access. Bottlenecks can come from:

- Slow object storage reads.
- Shared PVC throughput limits.
- Network file system latency.
- Container image pull time.
- Dataset preprocessing.

Options:

- Local NVMe scratch.
- High-performance RWX storage.
- Object storage caching.
- Data prefetch jobs.
- Dataset sharding.

### 23.3 Local scratch storage

If GPU nodes have local NVMe, you can expose it using:

- Local Storage Operator.
- EmptyDir on high-capacity ephemeral storage.
- HostPath only for trusted workloads and controlled environments.

Avoid uncontrolled hostPath use for tenants.

### 23.4 Networking

Distributed training can be network-sensitive. Consider:

- Zone placement.
- RDMA or high-speed NICs.
- SR-IOV for specialized network workloads.
- Multus secondary networks if required.
- Avoiding cross-zone training traffic when latency matters.

### 23.5 NUMA and topology

For high-end bare metal GPU nodes:

- Understand CPU socket to PCIe/GPU topology.
- Use CPU Manager and Topology Manager only if needed and supported by your workload design.
- Consider PerformanceProfile for latency-sensitive or topology-sensitive workloads.
- Validate with real benchmarks, not assumptions.

### 23.6 Image pull strategy

GPU images can be tens of gigabytes. Strategies:

- Use internal registry mirrors.
- Pre-pull critical images.
- Keep base images consistent.
- Use layered images carefully.
- Avoid frequent rebuilds of huge images.

## 25. Troubleshooting GPU node pools

### 25.1 Problem: GPU node does not show `nvidia.com/gpu`

Symptoms:

```bash
oc describe node <node> | grep nvidia.com/gpu
# no output
```

Possible causes:

- Node does not actually have GPU hardware.
- NFD not installed or not running.
- GPU Operator not installed.
- Driver DaemonSet failed.
- Device plugin DaemonSet failed.
- Node taint prevents GPU Operator operands from running.
- Driver version incompatible.
- Hardware/firmware/BIOS issue.

Checks:

```bash
oc get pods -n openshift-nfd
oc get pods -n nvidia-gpu-operator
oc describe node <node> | grep pci-10de
oc get ds -n nvidia-gpu-operator
oc logs -n nvidia-gpu-operator <device-plugin-pod>
```

### 25.2 Problem: GPU pod remains Pending

Describe pod:

```bash
oc describe pod <pod> -n <ns>
```

Common messages:

```text
Insufficient nvidia.com/gpu
node(s) had untolerated taint
node(s) didn't match Pod's node affinity/selector
exceeded quota
```

Fix by matching the message:

| Message | Likely fix |
|---|---|
| `Insufficient nvidia.com/gpu` | Free GPUs, reduce replicas, add nodes, check allocatable |
| `untolerated taint` | Add toleration or change taint |
| `didn't match node selector` | Fix node labels or pod selectors |
| `exceeded quota` | Increase quota or reduce usage |
| `project node selector conflict` | Fix namespace selector or pod selector |

### 25.3 Problem: GPU Operator pods not scheduled on tainted GPU nodes

If GPU nodes have custom taints, operator operand DaemonSets might need tolerations.

Check:

```bash
oc describe ds nvidia-driver-daemonset-<version> -n nvidia-gpu-operator
oc describe pod <operator-operand-pod> -n nvidia-gpu-operator
```

Fix options:

- Add required tolerations to GPU Operator ClusterPolicy/operator configuration.
- Use taints expected by the operator.
- Avoid taint keys that block operator components without matching tolerations.

### 25.4 Problem: Driver build fails after OpenShift upgrade

Checks:

```bash
oc get mcp
oc get nodes
oc get pods -n nvidia-gpu-operator | grep driver
oc logs -n nvidia-gpu-operator <driver-pod> -c openshift-driver-toolkit-ctr
oc logs -n nvidia-gpu-operator <driver-pod> -c nvidia-driver-ctr
```

Possible causes:

- Unsupported GPU Operator/driver version for target OCP.
- Driver Toolkit image issue.
- Disconnected mirror missing images.
- Proxy blocking image pulls.
- Kernel/driver mismatch.

Actions:

- Verify support matrix.
- Confirm image pull success.
- Check ClusterPolicy driver settings.
- Upgrade GPU Operator if required.
- Roll back or pause workloads if production is impacted.

### 25.5 Problem: Low GPU utilization

Possible causes:

- CPU bottleneck.
- Data loading bottleneck.
- Storage bottleneck.
- Batch size too small.
- Model not optimized.
- Too many replicas with too little work.
- Workload using CPU path instead of CUDA.
- GPU visible but application not using it.

Checks:

```bash
oc adm top pod -n <ns>
# Use Prometheus/DCGM for GPU metrics.
```

Inside pod:

```bash
nvidia-smi
python -c "import torch; print(torch.cuda.is_available())"
```

### 25.6 Problem: GPU memory full but utilization low

This often happens with inference servers or notebooks that load large models but do little compute.

Actions:

- Right-size model replicas.
- Use MIG if supported.
- Use smaller model variants.
- Use batching.
- Improve request routing.
- Avoid placing idle notebooks on production GPUs.

### 25.7 Problem: XID errors

XID errors indicate NVIDIA GPU driver/hardware events.

Actions:

- Check DCGM/XID metrics.
- Drain affected node.
- Run hardware diagnostics.
- Review `nvidia-smi -q` if accessible.
- Check driver logs.
- Escalate to hardware/vendor support if persistent.

### 25.8 Problem: Custom GPU MCP degraded

Checks:

```bash
oc get mcp gpu
oc describe mcp gpu
oc get nodes -l node-role.kubernetes.io/gpu=
oc describe node <gpu-node> | grep -i machineconfiguration
```

Common causes:

- Manual host file modification.
- Invalid MachineConfig.
- Conflicting MCP selectors.
- Drain failure due to PDB or stuck pods.
- Node unreachable.

Fix:

- Correct MachineConfig.
- Remove conflicting selector.
- Resolve drain blocker.
- Avoid manual host edits.

## 26. Real-world design examples

### 26.1 Example A: Small AI inference cluster

Requirement:

- Two L4 GPU nodes.
- Inference workloads only.
- No custom MCP.
- One production namespace.

Design:

```text
Nodes:
  2 x GPU L4 worker nodes
Labels:
  node-role.kubernetes.io/gpu=
  gpu.openshift.io/model=l4
  gpu.openshift.io/class=inference
Taint:
  accelerator=nvidia-gpu:NoSchedule
Namespace:
  ml-inference-prod
Quota:
  requests.nvidia.com/gpu=2
```

Workload uses:

```yaml
nodeSelector:
  gpu.openshift.io/class: inference
tolerations:
- key: accelerator
  value: nvidia-gpu
  effect: NoSchedule
resources:
  limits:
    nvidia.com/gpu: 1
```

### 26.2 Example B: Mixed training and inference cluster

Requirement:

- A100 nodes for training.
- L4 nodes for inference.
- Teams should not accidentally use training GPUs for inference.

Design:

```text
gpu-a100-training pool:
  labels:
    gpu.openshift.io/model=a100
    gpu.openshift.io/class=training
  taint:
    accelerator=nvidia-gpu:NoSchedule

gpu-l4-inference pool:
  labels:
    gpu.openshift.io/model=l4
    gpu.openshift.io/class=inference
  taint:
    accelerator=nvidia-gpu:NoSchedule
```

Namespaces:

```text
ml-training
ml-inference-prod
ml-research-dev
```

Each namespace gets a different node selector and quota.

### 26.3 Example C: MIG for multi-tenant notebooks

Requirement:

- A100 80GB nodes.
- Multiple teams run notebooks.
- Each notebook gets a small GPU slice.

Design:

```text
Pool:
  gpu-a100-mig
Sharing:
  MIG
Labels:
  gpu.openshift.io/model=a100
  gpu.openshift.io/sharing=mig
  gpu.openshift.io/class=notebook
Resources:
  nvidia.com/mig-1g.10gb
Quota per namespace:
  requests.nvidia.com/mig-1g.10gb=2
```

Workload:

```yaml
resources:
  limits:
    nvidia.com/mig-1g.10gb: 1
```

### 26.4 Example D: Dev/test time-sliced GPUs

Requirement:

- Developers need low-cost access.
- Isolation is not strict.
- Production workloads must not run there.

Design:

```text
Pool:
  gpu-dev-timeslice
Labels:
  gpu.openshift.io/sharing=timeslice
  environment=dev
Taint:
  gpu.openshift.io/dev=true:NoSchedule
Policy:
  Only dev namespaces receive toleration.
```

Warning:

Do not place untrusted production tenants on this pool.

### 27.1 Design checklist

- [ ] GPU pool has a clear business purpose.
- [ ] GPU hardware model and memory are documented.
- [ ] Labels identify role, model, class, sharing mode, and tenant if needed.
- [ ] Taints prevent normal workloads from scheduling.

## 28. Interview/exam style notes

### 28.1 Explain GPU node pool in one minute

A GPU node pool is a dedicated set of OpenShift worker nodes with GPU hardware, isolated from normal workloads using labels and taints, enabled using NFD and NVIDIA GPU Operator, and consumed by pods through extended resources such as `nvidia.com/gpu`. Production designs also include quota, monitoring, upgrade strategy, and sometimes a custom MachineConfigPool for GPU-specific node lifecycle.

### 28.2 Key difference: label vs taint

- Label attracts/selects workloads.
- Taint repels workloads.
- Toleration allows a workload to bypass the taint.
- Toleration alone does not force placement.

For GPU nodes, use both:

```text
Label: node-role.kubernetes.io/gpu=
Taint: accelerator=nvidia-gpu:NoSchedule
Pod: nodeSelector + toleration + GPU limit
```

### 28.3 Key difference: MachineSet vs MachineConfigPool

| Object | Main purpose |
|---|---|
| MachineSet | Creates and scales machines/nodes |
| MachineConfigPool | Applies OS/kubelet/CRI-O configuration and controls node update lifecycle |

For GPU pools:

- MachineSet defines GPU instance type, node labels, taints.
- MCP optionally controls GPU node configuration and updates.

### 28.4 Key difference: NFD vs GPU Operator

| Component | Purpose |
|---|---|
| NFD | Detects hardware and labels nodes |
| GPU Operator | Installs and manages NVIDIA driver stack and GPU Kubernetes components |

### 28.5 Why pod is pending with GPU request

Likely reasons:

- No node has allocatable `nvidia.com/gpu`.
- GPU is already allocated.
- Node has taint without matching toleration.
- Node selector or affinity mismatch.
- Namespace/project selector conflict.
- ResourceQuota exceeded.
- GPU Operator/device plugin not ready.

### 28.6 Best production answer

For production, I would create a dedicated GPU MachineSet with GPU instance type, labels, and `NoSchedule` taint. I would install NFD and the NVIDIA GPU Operator, verify `nvidia.com/gpu` capacity, enforce namespace quota, require GPU workloads to use GPU limits plus node affinity, enable DCGM monitoring, and optionally create a GPU MachineConfigPool if GPU nodes need separate kubelet/CRI-O tuning or controlled update behavior.
