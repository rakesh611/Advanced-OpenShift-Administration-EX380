# Workload Placement with Custom Node Pools in OpenShift

**Context:** Cluster Partitioning and Dedicated Node Pools  
**Audience:** Advanced OpenShift Administration / Senior Linux-OpenShift Admin level  
**Scope:** OpenShift Container Platform 4.x, Kubernetes scheduling, custom node pools, MachineSets, MachineConfigPools, labels, taints, tolerations, affinity, topology spread, operator workload placement, and troubleshooting.

---

## 1. Executive Summary

**Workload placement with custom node pools** means intentionally controlling *where pods run* by dividing the cluster into logical or physical groups of nodes and then using scheduler rules to place the right workloads on the right nodes.

In OpenShift, this is not only a scheduler topic. It involves multiple layers:

| Layer | OpenShift/Kubernetes object | Purpose |
|---|---|---|
| Provisioning layer | `MachineSet`, `Machine`, cloud worker pool, bare-metal node inventory | Creates/scales nodes with the right CPU, memory, disk, GPU, zone, or instance type |
| Node identity layer | Node labels such as `node-role.kubernetes.io/infra`, `workload=payments`, `hardware=gpu` | Describes node purpose and capabilities |
| OS/config layer | `MachineConfigPool`, `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig` | Applies node-level configuration to a specific pool |
| Scheduler control layer | `nodeSelector`, node affinity, pod affinity, anti-affinity, topology spread constraints | Determines where workload pods can or should run |
| Exclusion layer | Taints and tolerations | Repels general workloads from dedicated nodes |
| Namespace governance layer | Project node selectors, quotas, limit ranges, RBAC, admission policy | Enforces placement rules at tenant/project level |
| Operator placement layer | Operator-specific `nodeSelector`, `tolerations`, `nodePlacement`, or CR configuration | Moves routers, registry, monitoring, logging, GitOps, pipelines, storage, etc. |

A 10-year experienced OpenShift admin does not treat node pools as only labels. A proper design answers these questions:

1. **Why is this pool needed?** Isolation, performance, licensing, GPU, storage locality, infra billing, compliance, noisy-neighbor control, low latency, or operational separation.
2. **How will nodes be created and maintained?** MachineSet, Machine API, manual/bare-metal node lifecycle, autoscaler, or platform-specific machine pools.
3. **How will only intended workloads land there?** Labels + selectors/affinity + taints/tolerations.
4. **How will OpenShift system workloads be moved safely?** Operator-supported placement configuration, not random pod editing.
5. **How will upgrades and reboots behave?** MachineConfigPool rollout, `maxUnavailable`, PDBs, topology zones, and maintenance windows.
6. **How will placement be verified and troubleshot?** `oc get pods -o wide`, scheduler events, node labels, taints, MCP status, descheduler behavior, and storage topology.

## 2. What Is a Custom Node Pool?

A **custom node pool** is a set of nodes grouped for a specific purpose. In OpenShift, the term can mean slightly different things depending on the layer:

### 2.1 MachineSet / Machine Pool

This is the infrastructure/provisioning view.

Examples:

- AWS MachineSet for infra nodes in `us-east-1a`
- vSphere MachineSet for high-memory workers
- Bare-metal nodes manually labeled as `storage=true`
- Managed OpenShift machine pool in ROSA/OSD

This layer answers: **How are nodes created, scaled, and replaced?**

### 2.2 Node Role / Node Label Pool

This is the Kubernetes/OpenShift scheduling view.

Examples:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
oc label node worker-2 workload=payments
oc label node worker-3 hardware=gpu
oc label node worker-4 storage=odf
```

This layer answers: **How does the scheduler identify the node?**

### 2.3 MachineConfigPool

This is the node OS/configuration lifecycle view.

Examples:

- `worker` MCP
- `master` MCP
- custom `infra` MCP
- custom `gpu` MCP
- custom `low-latency` MCP

This layer answers: **Which nodes receive which MachineConfig, KubeletConfig, kernel arguments, sysctl, CRI-O, or performance settings?**

### 2.4 Workload Placement Pool

This is the application/operator view.

Examples:

- Place routers only on infra nodes.
- Place Elasticsearch/Loki logging pods only on logging nodes.
- Place GPU workloads only on GPU nodes.
- Place database/stateful pods only on storage-optimized nodes.
- Keep payment workloads away from shared application nodes.

This layer answers: **Which pods are allowed or preferred to run on this group?**

## 3. Why Custom Node Pools Matter in Advanced OpenShift Administration

Custom node pools solve real production problems.

### 3.1 Workload Isolation

You isolate workloads when one class of workload should not interfere with another.

Examples:

- Application workloads separated from infra components.
- Logging separated from business apps because log collectors/storage can be I/O-heavy.
- Monitoring separated because Prometheus can be memory-heavy.
- CI/CD runners separated because build workloads are bursty.
- GPU workloads separated because GPU resources are expensive and special.
- Security-sensitive apps separated for compliance.

### 3.2 Resource Predictability

Without placement rules, the scheduler can place pods on any feasible worker node. That is acceptable in simple clusters, but risky in large production clusters.

Problems without custom placement:

- Router pods compete with app pods.
- Monitoring pods land on small workers and hit memory pressure.
- Build pods overload application nodes.
- Database pods land on nodes without proper storage throughput.
- GPU nodes run normal web pods, wasting expensive hardware.

### 3.3 Operational Safety

Custom pools allow controlled node updates and maintenance.

For example:

- Update infra pool separately from app pool.
- Apply kernel/sysctl tuning only to low-latency nodes.
- Reboot GPU pool without impacting all workloads.
- Drain storage nodes carefully with storage-aware procedures.

### 3.4 Licensing and Subscription Awareness

OpenShift infrastructure nodes have special subscription considerations. Nodes running only supported infrastructure components can be treated differently from normal worker nodes. However, if arbitrary user workloads land there, the node becomes a normal worker from a subscription and operations perspective. Therefore, infra nodes must be protected with taints and carefully managed placement.

### 3.5 Hardware-Specific Workloads

Some workloads require specific hardware:

- GPU
- SR-IOV NIC
- NVMe local disk
- High-memory instance type
- CPU generation / AVX flags
- Low-latency tuned kernel profile
- Storage HBA / multipath / iSCSI configuration

Node labels and pool-specific MachineConfig help express those capabilities.

## 4. Scheduler Fundamentals: How OpenShift Decides Pod Placement

OpenShift uses the Kubernetes scheduler. At a high level, scheduling happens in two major phases:

1. **Filtering**: remove nodes that cannot run the pod.
2. **Scoring**: rank feasible nodes and choose the best one.

A pod remains `Pending` when no node passes all required filters.

Typical filters include:

- Node readiness
- Resource requests
- Taints not tolerated by the pod
- Node selectors
- Required node affinity
- Required pod affinity/anti-affinity
- Volume topology constraints
- Host port conflicts
- Pod security/admission failures before scheduling

Typical scoring influences include:

- Resource balance
- Preferred node affinity
- Preferred pod anti-affinity
- Topology spread preference
- Image locality
- plugin-specific scheduler scoring

Important senior-admin principle:

> A taint does not attract pods. It only repels pods that do not tolerate it. To force workloads onto a dedicated pool, combine **node labels/affinity** with **taints/tolerations**.

## 5. Core Placement Mechanisms

## 5.1 Node Labels

Node labels are key-value metadata used by the scheduler and administrators.

Examples:

```bash
oc label node worker-a workload=app
oc label node worker-b workload=infra
oc label node worker-c workload=logging
oc label node worker-d hardware=gpu
oc label node worker-e storage=odf
```

OpenShift node role label examples:

```bash
node-role.kubernetes.io/worker=
node-role.kubernetes.io/master=
node-role.kubernetes.io/infra=
```

Custom labels should be clear and stable:

```bash
workload.openshift.io/pool=payments
workload.openshift.io/pool=logging
hardware.openshift.io/gpu=true
storage.openshift.io/odf=true
topology.kubernetes.io/zone=zone-a
```

Avoid labels that change frequently, such as temporary maintenance status, unless you fully understand rescheduling behavior.

### Verify labels

```bash
oc get nodes --show-labels
oc get nodes -L node-role.kubernetes.io/infra,workload.openshift.io/pool,topology.kubernetes.io/zone
oc describe node <node-name> | egrep -A5 'Labels|Taints'
```

---

## 5.2 nodeSelector

`nodeSelector` is the simplest hard placement rule. The pod can run only on nodes with matching labels.

Example Deployment pinned to application nodes:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      nodeSelector:
        workload.openshift.io/pool: payments
      containers:
      - name: frontend
        image: registry.access.redhat.com/ubi9/nginx-120
        resources:
          requests:
            cpu: 200m
            memory: 256Mi
          limits:
            cpu: 1
            memory: 512Mi
```

Rules:

- All nodeSelector key-value pairs must match.
- A scheduled pod cannot be edited directly to add `nodeSelector`; edit the Deployment/StatefulSet/DaemonSet/Job template.
- If no node matches, pod remains `Pending`.

Useful when:

- Placement requirement is simple.
- One namespace or app must always use one pool.
- You want clear, predictable behavior.

Limitations:

- No OR logic.
- No soft preference.
- No advanced matching operators.

## 5.3 Node Affinity

Node affinity is more expressive than `nodeSelector`.

Two major types:

| Type | Meaning |
|---|---|
| `requiredDuringSchedulingIgnoredDuringExecution` | Hard rule. Pod schedules only if rule matches. If labels change later, pod keeps running. |
| `preferredDuringSchedulingIgnoredDuringExecution` | Soft rule. Scheduler prefers matching nodes but can use others. |

### Required node affinity example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: settlement-api
  namespace: payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: settlement-api
  template:
    metadata:
      labels:
        app: settlement-api
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload.openshift.io/pool
                operator: In
                values:
                - payments
              - key: kubernetes.io/os
                operator: In
                values:
                - linux
      containers:
      - name: settlement-api
        image: quay.io/example/settlement-api:v1
```

### Preferred node affinity example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reporting
spec:
  replicas: 2
  selector:
    matchLabels:
      app: reporting
  template:
    metadata:
      labels:
        app: reporting
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: workload.openshift.io/pool
                operator: In
                values:
                - analytics
          - weight: 20
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - zone-a
      containers:
      - name: reporting
        image: quay.io/example/reporting:v1
```

### Node affinity operators

Common operators:

| Operator | Meaning |
|---|---|
| `In` | Label value must be in list |
| `NotIn` | Label value must not be in list |
| `Exists` | Label key must exist |
| `DoesNotExist` | Label key must not exist |
| `Gt` | Label value is greater than integer |
| `Lt` | Label value is less than integer |

Senior-admin notes:

- Multiple `matchExpressions` inside one `nodeSelectorTerm` are ANDed.
- Multiple `nodeSelectorTerms` are ORed.
- If `nodeSelector` and node affinity are both used, both must be satisfied.
- `IgnoredDuringExecution` means pods are not evicted just because node labels later change.

## 5.4 Taints and Tolerations

Taints repel pods from nodes. Tolerations allow pods to tolerate the taint.

### Effects

| Effect | Behavior |
|---|---|
| `NoSchedule` | New pods without matching toleration are not scheduled there. Existing pods stay. |
| `PreferNoSchedule` | Scheduler tries to avoid the node but may still use it. |
| `NoExecute` | New pods without toleration are not scheduled; existing pods without toleration can be evicted. |

### Taint a dedicated pool

```bash
oc adm taint nodes worker-infra-1 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint nodes worker-infra-2 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint nodes worker-infra-3 node-role.kubernetes.io/infra=reserved:NoSchedule
```

### Remove a taint

```bash
oc adm taint nodes worker-infra-1 node-role.kubernetes.io/infra=reserved:NoSchedule-
```

### Add toleration to workload

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Equal
        value: reserved
        effect: NoSchedule
```

Or tolerate any value for the key:

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

Important:

> A toleration only allows a pod to run on the tainted node. It does not force the pod onto that node. To force placement, also use `nodeSelector` or required node affinity.

### Dedicated pool pattern

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/pool: payments
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
```

Node side:

```bash
oc label node worker-pay-1 workload.openshift.io/pool=payments
oc adm taint node worker-pay-1 dedicated=payments:NoSchedule
```

This means:

- General pods cannot land on payment nodes because of the taint.
- Payment pods can land there because they tolerate the taint.
- Payment pods are forced there because of `nodeSelector`.

## 5.5 Pod Affinity and Anti-Affinity

Pod affinity places pods relative to other pods. Pod anti-affinity keeps pods away from other pods.

### Use cases

| Requirement | Mechanism |
|---|---|
| Place cache near app pods | Pod affinity |
| Spread replicas across nodes | Pod anti-affinity |
| Avoid two replicas on the same node | Required pod anti-affinity with `kubernetes.io/hostname` |
| Avoid two replicas in the same zone | Required/preferred pod anti-affinity with `topology.kubernetes.io/zone` |

### Preferred anti-affinity for high availability

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      nodeSelector:
        workload.openshift.io/pool: payments
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: payment-api
              topologyKey: kubernetes.io/hostname
      containers:
      - name: payment-api
        image: quay.io/example/payment-api:v1
```

Use **preferred** anti-affinity when availability is important but you still want the rollout to continue under constrained capacity.

Use **required** anti-affinity when strict separation is mandatory and you accept that pods may remain `Pending` if there are not enough nodes.

## 5.6 Topology Spread Constraints

Topology spread constraints distribute pods across failure domains such as nodes, zones, or racks.

Example: spread payment API replicas across zones within the payment node pool.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments
spec:
  replicas: 6
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      nodeSelector:
        workload.openshift.io/pool: payments
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment-api
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: payment-api
      containers:
      - name: payment-api
        image: quay.io/example/payment-api:v1
```

Meaning:

- Keep zone skew within 1.
- If zone balance cannot be satisfied, do not schedule.
- Prefer node-level spreading but allow scheduling if perfect balance is not possible.

Senior-admin warnings:

- Nodes missing the `topologyKey` label are ignored for that topology calculation.
- If constraints conflict, pods can remain `Pending`.
- When using node selectors or node affinity, topology spread is calculated only among eligible nodes.
- Make sure the pod template labels match the `labelSelector`; otherwise spread behavior may not represent the intended workload.

## 6. Custom Node Pool Design Patterns

## 6.1 Infra Node Pool

Purpose:

- Ingress router
- Image registry
- Monitoring stack
- Logging components
- GitOps control plane
- Pipelines control plane
- ACS/ACM/Quay components, depending on architecture

Recommended design:

```bash
oc label node infra-1 node-role.kubernetes.io/infra=
oc label node infra-2 node-role.kubernetes.io/infra=
oc label node infra-3 node-role.kubernetes.io/infra=

oc adm taint node infra-1 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint node infra-2 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint node infra-3 node-role.kubernetes.io/infra=reserved:NoSchedule
```

Placement rule for infra workloads:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Equal
  value: reserved
  effect: NoSchedule
```

Production note:

- Use at least three infra nodes when hosting highly available infra components.
- Spread across zones if possible.
- Do not run user workloads on infra nodes unless intentionally designed and licensed.

---

## 6.2 Application Node Pool

Purpose:

- General stateless applications
- Tenant workloads
- Microservices
- Frontend/backend apps

Example:

```bash
oc label node app-1 workload.openshift.io/pool=app
oc label node app-2 workload.openshift.io/pool=app
oc label node app-3 workload.openshift.io/pool=app
```

Namespace selector:

```bash
oc annotate namespace team-a openshift.io/node-selector='workload.openshift.io/pool=app' --overwrite
```

This makes pods in the namespace inherit the project node selector unless otherwise restricted by platform behavior.

## 6.3 Dedicated Business-Critical Pool

Purpose:

- Payment apps
- Banking apps
- High-priority APIs
- Critical production services

Node setup:

```bash
oc label node pay-1 workload.openshift.io/pool=payments
oc label node pay-2 workload.openshift.io/pool=payments
oc label node pay-3 workload.openshift.io/pool=payments

oc adm taint node pay-1 dedicated=payments:NoSchedule
oc adm taint node pay-2 dedicated=payments:NoSchedule
oc adm taint node pay-3 dedicated=payments:NoSchedule
```

Workload setup:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/pool: payments
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
```

Best practice:

- Add PDBs for high availability.
- Use topology spread across zones.
- Use resource requests and limits.
- Avoid broad tolerations like `operator: Exists` unless justified.

## 6.4 Logging Node Pool

Purpose:

- LokiStack / Elasticsearch / logging storage
- Log collectors or aggregators
- High disk I/O workloads

Node labels:

```bash
oc label node log-1 workload.openshift.io/pool=logging
oc label node log-2 workload.openshift.io/pool=logging
oc label node log-3 workload.openshift.io/pool=logging
oc adm taint node log-1 dedicated=logging:NoSchedule
oc adm taint node log-2 dedicated=logging:NoSchedule
oc adm taint node log-3 dedicated=logging:NoSchedule
```

Placement pattern:

```yaml
nodeSelector:
  workload.openshift.io/pool: logging
tolerations:
- key: dedicated
  operator: Equal
  value: logging
  effect: NoSchedule
```

Operational notes:

- Logging storage can be disk- and memory-intensive.
- Use storage classes appropriate for log retention and write throughput.
- DaemonSet-based collectors may need tolerations to run on tainted nodes.
- Do not accidentally block node log collectors from infra or storage pools.

## 6.5 Monitoring Node Pool

Purpose:

- Prometheus
- Alertmanager
- Thanos Querier / receivers depending on architecture
- User workload monitoring components

Node labels:

```bash
oc label node mon-1 workload.openshift.io/pool=monitoring
oc label node mon-2 workload.openshift.io/pool=monitoring
oc label node mon-3 workload.openshift.io/pool=monitoring
oc adm taint node mon-1 dedicated=monitoring:NoSchedule
oc adm taint node mon-2 dedicated=monitoring:NoSchedule
oc adm taint node mon-3 dedicated=monitoring:NoSchedule
```

Monitoring is memory-sensitive. Prometheus usage grows with:

- Number of nodes
- Number of namespaces
- Number of pods
- Metrics cardinality
- Retention period
- Scrape interval
- User workload monitoring enablement

Do not size monitoring nodes like normal small workers in large clusters.

## 6.6 GPU Node Pool

Purpose:

- AI/ML workloads
- CUDA workloads
- GPU-accelerated inference
- Device-plugin-managed workloads

Node labels:

```bash
oc label node gpu-1 hardware.openshift.io/gpu=true
oc label node gpu-1 workload.openshift.io/pool=gpu
oc adm taint node gpu-1 nvidia.com/gpu=present:NoSchedule
```

Workload:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inferencing
spec:
  replicas: 1
  selector:
    matchLabels:
      app: inferencing
  template:
    metadata:
      labels:
        app: inferencing
    spec:
      nodeSelector:
        workload.openshift.io/pool: gpu
      tolerations:
      - key: nvidia.com/gpu
        operator: Equal
        value: present
        effect: NoSchedule
      containers:
      - name: model-server
        image: quay.io/example/model-server:gpu

            nvidia.com/gpu: 1
```

Notes:

- GPU scheduling requires device plugin/operator support.
- Normal pods should be repelled from GPU nodes to avoid wasting expensive hardware.
- GPU workloads usually need limits for extended resources.

## 6.7 Storage Node Pool

Purpose:

- OpenShift Data Foundation / Ceph / local storage
- Stateful applications with storage locality
- NVMe-backed workloads

Node labels:

```bash
oc label node storage-1 workload.openshift.io/pool=storage
oc label node storage-1 cluster.ocs.openshift.io/openshift-storage=
oc adm taint node storage-1 dedicated=storage:NoSchedule
```

Storage-specific notes:

- Storage operators often require their own placement CRs.
- PVC binding can interact with node placement through topology-aware storage.
- `WaitForFirstConsumer` storage classes bind volumes after pod placement decisions.
- A pod can remain `Pending` if its node selector and PVC topology cannot be satisfied together.
- Do not drain storage nodes like normal stateless worker nodes without reviewing storage operator procedures.

## 6.8 Low-Latency / Performance Node Pool

Purpose:

- Telco workloads
- Real-time workloads
- DPDK/SR-IOV workloads
- CPU pinning / hugepages / tuned profiles

Typical components:

- Node Tuning Operator
- PerformanceProfile
- MachineConfigPool
- KubeletConfig
- CPU manager policy
- Topology manager policy
- HugePages
- IRQ balancing settings

Example node labels:

```bash
oc label node rt-1 workload.openshift.io/pool=low-latency
oc label node rt-1 node-role.kubernetes.io/worker-rt=
oc adm taint node rt-1 dedicated=low-latency:NoSchedule
```

Do not apply low-latency kernel and kubelet tuning globally unless every worker node requires it.

## 7. Creating a Custom MachineConfigPool

A custom `MachineConfigPool` is required when a subset of nodes needs dedicated OS-level configuration.

Important OpenShift behavior:

- Default pools are usually `master` and `worker`.
- Custom pools commonly inherit worker configuration.
- A node can have multiple role labels, but it should be selected by only one MachineConfigPool.
- MachineConfig changes can reboot nodes.
- Worker-targeted MachineConfigs also affect custom pools that inherit from worker.

### 7.1 Example: Infra MCP

Label nodes:

```bash
oc label node infra-1 node-role.kubernetes.io/infra=
oc label node infra-2 node-role.kubernetes.io/infra=
oc label node infra-3 node-role.kubernetes.io/infra=
```

Create `infra-mcp.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp infra
oc get nodes -l node-role.kubernetes.io/infra=
```

### 7.2 Example: Pool-specific MachineConfig

Create `99-infra-example-file.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-example-file
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/node-pool-purpose
        mode: 0644
        contents:
          source: data:,infra-node-pool
```

Apply:

```bash
oc apply -f 99-infra-example-file.yaml
oc get mcp infra -w
```

Warning:

MachineConfig changes commonly trigger node drain/reboot cycles. Plan around PDBs, cluster capacity, and maintenance windows.

## 8. Creating Custom Nodes with MachineSets

On Machine API supported platforms, create or clone a MachineSet and add labels/taints to the MachineSet template so new nodes come up correctly.

### 8.1 Find existing MachineSets

```bash
oc get machinesets -n openshift-machine-api
oc get machines -n openshift-machine-api -o wide
```

### 8.2 Add labels and taints in MachineSet template

Example fragment:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: clusterid-payments-zone-a
  namespace: openshift-machine-api
spec:
  replicas: 2
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machineset: clusterid-payments-zone-a
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/worker: ""
          workload.openshift.io/pool: payments
      taints:
      - key: dedicated
        value: payments
        effect: NoSchedule
```

Depending on platform/version, labels may be placed under Machine template metadata or provider-specific fields. Always verify that labels appear on the resulting `Node` object.

### 8.3 Scale MachineSet


### 8.4 MachineSet vs manual node labeling

Manual labeling is acceptable for quick labs, bare-metal nodes, or one-time fixes, but production design should prefer labels and taints being applied automatically by MachineSet, installation automation, GitOps, or cluster lifecycle tooling.

## 9. Namespace-Level Placement Governance

OpenShift supports project/namespace node selectors.

Example:

```bash
oc annotate namespace payments openshift.io/node-selector='workload.openshift.io/pool=payments' --overwrite
```

View:

```bash
oc get namespace payments -o yaml | grep -A3 annotations
```

This helps ensure workloads in a project land only on intended nodes.

### Cluster-wide default node selector

OpenShift can set a cluster-wide default node selector through the `Scheduler` cluster resource.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: workload.openshift.io/pool=app
```

Warning:

Cluster-wide selectors can break platform or operator workloads if not planned carefully. Use with caution. Project selectors are usually safer for tenant isolation.

### Important precedence concept

If a namespace/project selector exists, it can take precedence over the cluster-wide default selector. A pod can fail creation or scheduling when selectors conflict.

## 11. Complete End-to-End Example: Payments Dedicated Node Pool

Goal:

- Create a dedicated pool for payment workloads.
- Prevent general workloads from landing there.
- Force payment namespace workloads to the pool.
- Spread replicas across nodes/zones.

### 11.1 Label nodes

```bash
oc label node worker-pay-a workload.openshift.io/pool=payments
oc label node worker-pay-b workload.openshift.io/pool=payments
oc label node worker-pay-c workload.openshift.io/pool=payments
```

### 11.2 Taint nodes

```bash
oc adm taint node worker-pay-a dedicated=payments:NoSchedule
oc adm taint node worker-pay-b dedicated=payments:NoSchedule
oc adm taint node worker-pay-c dedicated=payments:NoSchedule
```

### 11.3 Annotate namespace

```bash
oc new-project payments
oc annotate namespace payments openshift.io/node-selector='workload.openshift.io/pool=payments' --overwrite
```

### 11.4 Deploy app with toleration and spread

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment-api
      containers:
      - name: payment-api
        image: quay.io/example/payment-api:v1
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: 250m
            memory: 256Mi
          limits:
            cpu: "1"
            memory: 512Mi
```

Because the namespace has a node selector, every pod in this namespace is constrained to `workload.openshift.io/pool=payments`. The pod toleration allows scheduling onto the tainted payment nodes.

### 11.5 Verify placement

```bash
oc get pods -n payments -o wide
oc describe pod -n payments -l app=payment-api
oc get nodes -L workload.openshift.io/pool
oc describe node worker-pay-a | grep -A5 Taints
```

### 11.6 Test isolation

Create a test pod in another namespace without toleration:

```bash
oc new-project general-test
oc run test --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc get pod -o wide
```

The test pod should not land on the payment nodes because it lacks the `dedicated=payments:NoSchedule` toleration.

## 13. Placement with Stateful Workloads and Storage

Stateful workloads require extra care because storage topology can restrict placement.

### 13.1 Common issue

A StatefulSet has:

```yaml
nodeSelector:
  workload.openshift.io/pool: database
```

But its PVC binds to storage available only in another zone or another node group. Result:

```text
0/6 nodes are available: pod has unbound immediate PersistentVolumeClaims, node(s) didn't match Pod's node affinity/selector, volume node affinity conflict
```

### 13.2 Best practices

- Use storage classes designed for the target zones/nodes.
- Understand `volumeBindingMode`:
  - `Immediate`: PVC may bind before pod scheduling.
  - `WaitForFirstConsumer`: scheduler considers pod placement before binding.
- Ensure PV node affinity matches workload node pool labels/topology.
- For local storage, ensure pods target nodes where the local PV exists.
- For ODF/Ceph, follow ODF placement guidance rather than manually moving storage pods.

### 13.3 Verification commands

```bash
oc get sc
oc describe sc <storage-class>
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get pv -o wide
oc describe pv <pv-name>
oc describe pod <pod> -n <ns>
```

## 14. Placement with DaemonSets

DaemonSets are special because they create one pod per eligible node.

Examples:

- Log collector
- Node exporter
- CSI driver
- Network plugin
- Security agent
- Monitoring/node agent

If you taint custom pools, DaemonSet pods may stop landing there unless they have tolerations.

Example DaemonSet toleration:

```yaml
spec:
  template:
    spec:
      tolerations:
      - operator: Exists
```

This tolerates all taints. Use carefully. For security-sensitive environments, define exact tolerations instead.

Limit DaemonSet to a pool:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/pool: logging
```

Senior-admin rule:

> Before tainting a node pool, list all DaemonSets that must still run there: network, DNS, CSI, monitoring, logging, security, and backup agents.

Commands:

```bash
oc get ds -A
oc get ds -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,NODESELECTOR:.spec.template.spec.nodeSelector,TOLERATIONS:.spec.template.spec.tolerations'
```

## 15. Placement and Cluster Autoscaling

When using Machine Autoscaler or Cluster Autoscaler, placement rules affect scaling.

Example problem:

- Pods require `workload.openshift.io/pool=gpu`.
- No GPU nodes exist.
- Autoscaler will scale only if there is a scalable MachineSet that can create nodes with matching labels/taints/resources.

Best practices:

- Ensure MachineSet templates include the labels required by pending pods.
- Ensure taints are compatible with pod tolerations.
- Avoid overly strict affinity that no MachineSet can satisfy.
- Use separate MachineAutoscalers per pool.
- Validate that pending pods contain enough resource requests for autoscaler decisions.

Useful commands:

```bash
oc get machineautoscaler -A
oc get clusterautoscaler -A
oc get machineset -n openshift-machine-api -o yaml | grep -A10 -B5 'workload.openshift.io/pool'
oc describe pod <pending-pod> -n <ns>
```

## 16. Placement and Upgrades / Reboots

MachineConfigPool changes can reboot nodes. This is expected.

During MCP rollout:

1. MCO renders a new config.
2. Machine Config Daemon drains node.
3. OS/config change is applied.
4. Node may reboot.
5. Node returns Ready.
6. MCP progresses until all selected nodes match desired config.

### Verify MCP state

```bash
oc get mcp
oc describe mcp <pool-name>
oc get nodes
oc get co machine-config
```

### Watch rollout

```bash
oc get mcp <pool-name> -w
```

### Check degraded MCP

```bash
oc describe mcp <pool-name>
oc get nodes -o wide
oc adm node-logs <node-name> -u kubelet
oc adm node-logs <node-name> -u crio
oc debug node/<node-name>
```

### Admin considerations

- Keep enough spare capacity before applying MachineConfig.
- Use PDBs carefully; too strict PDBs can block drains.
- Avoid making multiple pool-wide disruptive changes at once.
- Tune MCP `maxUnavailable` only after understanding risk.
- Do not put all replicas of a critical app on one node pool without enough pool capacity.

## 17. Hard Isolation vs Soft Preference

| Requirement | Recommended control |
|---|---|
| Must run only on specific nodes | `nodeSelector` or required node affinity |
| Should prefer specific nodes | Preferred node affinity |
| Keep general workloads away | Taint node + no toleration for general pods |
| Allow only special workloads | Taint + exact tolerations + namespace policy |
| Spread replicas across nodes/zones | Topology spread constraints or pod anti-affinity |
| Move operator workload | Operator CR placement field |
| Per-namespace placement | Project node selector |
| OS-level pool config | MachineConfigPool + MachineConfig/KubeletConfig |

Golden rule:

```text
Dedicated pool = label/affinity for attraction + taint/toleration for protection.
```

## 19. Common Mistakes and Fixes

### Mistake 1: Only adding toleration, no node selector

Problem:

```yaml
 tolerations:
 - key: dedicated
   value: payments
   effect: NoSchedule
```

This allows the pod to run on payment nodes, but does not force it there.

Fix:

```yaml
nodeSelector:
  workload.openshift.io/pool: payments
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoSchedule
```

---

### Mistake 2: Taint effect mismatch

Node taint:

```text
dedicated=payments:NoSchedule
```

Pod toleration:

```yaml
effect: NoExecute
```

This does not match.

Fix:

```yaml
effect: NoSchedule
```

---

### Mistake 3: Label value mismatch

Node:

```text
workload.openshift.io/pool=payment
```

Pod:

```yaml
workload.openshift.io/pool: payments
```

Fix the spelling and standardize label values.

---

### Mistake 4: Removing worker label from custom nodes

Removing `node-role.kubernetes.io/worker` from custom nodes can cause MCO management problems unless a custom MCP is correctly configured.

Safer infra pattern:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

Then use taints/tolerations to prevent user workloads.

---

### Mistake 5: Creating overlapping MachineConfigPools

If a node matches multiple MCP node selectors, the MCO can behave unpredictably or mark pools degraded.

Fix:

- Design mutually exclusive MCP node selectors.
- Verify node labels.
- Ensure each node belongs to only one MCP.

```bash
oc get mcp -o yaml
oc get nodes --show-labels
```

---

### Mistake 6: Moving operator pods by editing Deployment directly

Problem:

```bash
oc edit deployment router-default -n openshift-ingress
```

The operator may revert it.

Fix:

Edit the operator custom resource, such as `IngressController`, image registry config, monitoring config, or logging CR.

---

### Mistake 7: Tainting infra nodes before adding operator tolerations

Result:

- Router pods cannot schedule.
- Registry pods cannot schedule.
- Monitoring pods remain pending.

Fix order:

1. Add node selector and toleration to operator config.
2. Wait for pods to run on target nodes.
3. Apply taint to protect node pool.
4. Verify system pods remain healthy.

---

### Mistake 8: Topology labels missing

Topology spread uses labels like:

```text
topology.kubernetes.io/zone
topology.kubernetes.io/region
kubernetes.io/hostname
```

If nodes lack these labels, spread constraints may not behave as expected.

Fix:

```bash
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
```

---

### Mistake 9: Project node selector conflicts with workload node selector

Namespace selector:

```text
workload.openshift.io/pool=app
```

Deployment selector:

```yaml
nodeSelector:
  workload.openshift.io/pool: payments
```

No node can satisfy both if labels are exclusive.

Fix:

- Align namespace selector with workload requirement.
- Use separate namespaces per placement pool.
- Avoid conflicting cluster default selectors.

## 22. Real Production Design Example

Assume a production OpenShift cluster with 18 worker nodes across three zones.

| Pool | Nodes | Labels | Taints | Workloads |
|---|---:|---|---|---|
| Infra | 3 | `node-role.kubernetes.io/infra=` | `node-role.kubernetes.io/infra=reserved:NoSchedule` | Router, registry, monitoring, GitOps |
| App | 6 | `workload.openshift.io/pool=app` | None or light tenant-specific taints | General apps |
| Payments | 3 | `workload.openshift.io/pool=payments` | `dedicated=payments:NoSchedule` | Payment APIs |
| Logging | 3 | `workload.openshift.io/pool=logging` | `dedicated=logging:NoSchedule` | Loki/Elasticsearch/logging storage |
| Storage | 3 | `workload.openshift.io/pool=storage` | `dedicated=storage:NoSchedule` | ODF/Ceph/local storage |

Recommended governance:

- `payments` namespace has project node selector for payment pool.
- `logging` operator CR uses logging pool selector/toleration.
- Infra operator CRs use infra node selector/toleration.
- General app namespaces use app pool selector.
- DaemonSets that must run everywhere tolerate all required dedicated taints.
- Cluster autoscaler has separate autoscaler definitions for app/payment/logging pools.
- MachineConfigPools exist only where OS/kubelet config differs.

## 23. Mental Model for Exam and Interview Answers

When asked about workload placement with custom node pools, answer in this structure:

1. **Create or identify node pool** using MachineSet/MachinePool/bare-metal inventory.
2. **Label nodes** to identify purpose.
3. **Taint dedicated nodes** to prevent accidental scheduling.
4. **Add nodeSelector or required node affinity** to force intended workloads there.
5. **Add matching tolerations** so intended workloads can use tainted nodes.
6. **Use topology spread/anti-affinity** for HA.
7. **Use project node selectors** for namespace-level governance.
8. **Use operator-supported placement fields** for platform workloads.
9. **Use MachineConfigPool** only when node-level OS/kubelet/runtime tuning differs.
10. **Troubleshoot with pod events, node labels/taints, namespace selector, MCP status, and storage topology.**

Short senior-level answer:

```text
In OpenShift, custom node pools are implemented by combining node provisioning, labels, taints, scheduler constraints, and optionally MachineConfigPools. Labels and node affinity attract or restrict workloads to the pool. Taints repel unrelated workloads. Tolerations allow approved workloads. Project node selectors and operator placement CRs enforce placement at namespace and platform-component level. MachineConfigPools manage pool-specific OS and kubelet configuration, but they must be designed carefully because a node can effectively belong to only one MCP and config changes can reboot nodes.
```

## 25. Final Practical Advice

For production OpenShift, do not design custom node pools with only one mechanism. Use a layered model:

```text
MachineSet creates the right nodes.
Labels identify the pool.
Taints protect the pool.
Selectors/affinity place workloads.
Tolerations allow approved workloads.
Topology spread provides HA.
MachineConfigPool applies node-level tuning.
Operator CRs move platform components safely.
Monitoring and runbooks keep the design operational.
```

This is the difference between a basic Kubernetes placement setup and an enterprise-grade OpenShift cluster partitioning design.
