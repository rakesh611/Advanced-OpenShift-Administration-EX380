# MCP Updating/Paused State in Cluster Partitioning and Dedicated Node Pools

**Audience:** Advanced OpenShift Administrators / Platform Engineers with production experience  
**Scope:** OpenShift Container Platform 4.x, Machine Config Operator, MachineConfigPool lifecycle, custom/dedicated node pools  
**Focus topic:** Understanding, operating, and troubleshooting `MachineConfigPool` `UPDATING` and `paused` states

---

## 1. Executive Summary

In OpenShift, a `MachineConfigPool` (`MCP`) is the operational boundary used by the **Machine Config Operator** (`MCO`) to apply host-level changes to groups of nodes. These changes include updates to RHCOS/RHEL CoreOS configuration, kubelet settings, CRI-O configuration, systemd units, kernel arguments, files under `/etc`, SSH keys, pull secrets, and some OS image changes.

For an experienced administrator, the two most important operational MCP states are:

- `UPDATING=True`
- `spec.paused=true`

They look simple in `oc get mcp`, but they have major production implications.

`UPDATING=True` means the MCO is actively reconciling at least one node in that pool toward the pool's desired rendered machine config. During this time, nodes may be cordoned, drained, rebooted, unavailable, or temporarily not counted as ready.

`spec.paused=true` means the MCP has been intentionally stopped from applying new machine configuration changes to its nodes. This is commonly used during canary updates, controlled maintenance windows, or staged rollouts for dedicated node pools such as infra, logging, monitoring, GPU, storage, or application pools.

A paused MCP is not a harmless cosmetic state. If left paused too long, it can prevent required machine configuration, certificate rotations, OS changes, kubelet changes, and future cluster upgrade progression from reaching the nodes.

---

## 2. Why MCP State Matters in Cluster Partitioning

Cluster partitioning means dividing OpenShift nodes into functional pools such as:

- `master` / control plane pool
- `worker` pool
- `infra` pool
- `logging` pool
- `monitoring` pool
- `storage` pool
- `gpu` pool
- `app` pool
- `special-workload` pool

Each pool can have its own:

- node labels
- node selectors
- taints and tolerations
- MachineConfig objects
- KubeletConfig objects
- ContainerRuntimeConfig objects
- node-level sysctl/kernel tuning
- update timing
- reboot blast radius
- operational policy

This is where `UPDATING` and `paused` become important.

A production cluster may tolerate a worker pool reboot during a normal update, but it might not tolerate simultaneous disruption to:

- logging ingestion nodes
- infra/router nodes
- monitoring stack nodes
- ODF/Ceph storage nodes
- GPU training nodes
- latency-sensitive application nodes

So advanced administrators use custom MCPs to isolate configuration and update behavior.

## 3. Core Concepts

### 3.1 MachineConfig

A `MachineConfig` defines host-level configuration for nodes. It can manage things such as:

- files
- systemd units
- kernel arguments
- CRI-O configuration
- kubelet configuration indirectly through `KubeletConfig`
- SSH authorized keys
- container runtime configuration
- registries and pull-secret-related changes

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example-sysctl
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/sysctl.d/99-custom.conf
        mode: 0644
        contents:
          source: data:text/plain;charset=utf-8;base64,bmV0LmlwdjQuaXBfZm9yd2FyZCA9IDEK
```

### 3.2 Rendered MachineConfig

The MCO combines multiple MachineConfig objects for a pool into a generated object named like:

```text
rendered-worker-<hash>
rendered-infra-<hash>
rendered-storage-<hash>
```

This rendered config becomes the desired target for nodes in that pool.

You should not manually edit or delete rendered MachineConfig objects.

### 3.3 MachineConfigPool

An MCP selects nodes and determines how machine configuration is rolled out.

Example custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Important points:

- The pool selects nodes using `spec.nodeSelector`.
- The pool selects MachineConfigs using `spec.machineConfigSelector`.
- A node can have many labels, but it should belong to only one MCP.
- `maxUnavailable` controls how many nodes the MCO can disrupt at one time.
- `spec.paused` can stop updates for that pool.

## 4. Normal MCO Update Flow

When a change affects an MCP, the MCO usually performs this sequence for each affected node:

```text
MachineConfig / KubeletConfig / CRI-O config changed
        |
        v
MCO renders new rendered-<pool>-<hash>
        |
        v
MCP desired config changes
        |
        v
MCP becomes UPDATED=False, UPDATING=True
        |
        v
MCO selects node according to maxUnavailable
        |
        v
Node is cordoned
        |
        v
Node is drained
        |
        v
MachineConfigDaemon applies files / OS / systemd / kubelet / CRI-O changes
        |
        v
Node reboots if required
        |
        v
Node becomes Ready
        |
        v
Node is uncordoned
        |
        v
MCP updatedMachineCount increases
        |
        v
When all nodes match desired config:
UPDATED=True, UPDATING=False, DEGRADED=False
```

Not every change needs a reboot, but many host-level changes do. Kernel arguments, OS image changes, kubelet changes, CRI-O changes, systemd changes, and many file changes commonly lead to drain/reboot behavior.

## 5. Understanding `oc get mcp`

Typical command:

```bash
oc get mcp
```

Example:

```text
NAME       CONFIG                         UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT   AGE
master     rendered-master-a1b2c3         True      False      False      3              3                   3                     0                      120d
worker     rendered-worker-d4e5f6         False     True       False      6              5                   5                     0                      120d
infra      rendered-infra-aabbcc          True      False      False      3              3                   3                     0                      100d
logging    rendered-logging-112233        True      False      False      3              3                   3                     0                      90d
```

### 5.1 Column Meaning

| Column | Meaning | Production Interpretation |
|---|---|---|
| `CONFIG` | Current rendered config shown for the pool | During update, this may show the config the pool is moving from. After update, it shows the desired config. |
| `UPDATED` | Whether all nodes have the current desired config | `True` means all nodes reached desired config. `False` means at least one node has not. |
| `UPDATING` | Whether the pool is actively reconciling nodes | `True` usually means node drain/apply/reboot/uncordon is in progress or blocked. |
| `DEGRADED` | Whether the pool cannot apply configuration cleanly | `True` needs immediate investigation. |
| `MACHINECOUNT` | Total nodes in pool | Used as baseline. |
| `READYMACHINECOUNT` | Nodes ready and running expected config | Drops during cordon/drain/reboot. |
| `UPDATEDMACHINECOUNT` | Nodes already on desired/current config | Increases as rollout progresses. |
| `DEGRADEDMACHINECOUNT` | Nodes degraded/unreconcilable | Non-zero means node-level problem. |

## 6. Deep Dive: `UPDATING=True`

### 6.1 What `UPDATING=True` Really Means

`UPDATING=True` means the MCO is applying the desired MachineConfigPool configuration to at least one node in that pool.

Common causes:

- new `MachineConfig` created
- existing MachineConfig changed
- new `KubeletConfig` applied
- new `ContainerRuntimeConfig` applied
- cluster version update changed the OS payload
- pull secret change
- SSH key update
- custom pool label changed
- node moved into a different pool
- node is cordoned during MCO reconciliation
- previous update is still completing
- MCD is waiting on reboot
- MCO is blocked by drain/PDB/eviction problems

### 6.2 Normal Updating State

Normal example:

```text
NAME     CONFIG                    UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
worker   rendered-worker-oldhash   False     True       False      3              2                   2                     0
```

Interpretation:

- 3 nodes are in worker pool.
- 2 nodes are ready.
- 2 nodes already updated.
- 1 node is currently being updated.
- No degraded node.
- This is expected during rollout.

### 6.3 Updating But Not Broken

Do not panic just because `UPDATING=True`.

It is normal during:

- OpenShift upgrade
- MCP rollout
- custom MachineConfig deployment
- kubelet tuning rollout
- CRI-O tuning rollout
- OS image change
- custom node pool creation
- node movement between pools

The key is whether it progresses.

Watch it:

```bash
watch -n 10 'oc get mcp'
```

Or:

```bash
oc get mcp worker -w
```

### 6.4 Updating and Potentially Stuck

An MCP is suspicious when:

- `UPDATING=True` for too long
- `UPDATEDMACHINECOUNT` does not increase
- `READYMACHINECOUNT` remains low
- `UNAVAILABLEMACHINECOUNT` remains high
- node remains `SchedulingDisabled`
- node remains `NotReady`
- MCD logs show repeated errors
- `oc describe mcp` shows repeated events
- `DEGRADED=True`
- cluster upgrade is blocked on machine-config

Check:

```bash
oc describe mcp worker
oc get nodes
oc get nodes -l node-role.kubernetes.io/worker=
oc get co machine-config
oc describe co machine-config
```

### 6.5 Node-Level Annotations

Each node managed by MCO normally has annotations similar to:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Example:

```text
currentConfig: rendered-worker-oldhash
desiredConfig: rendered-worker-newhash
state: Working
```

Interpretation:

- Node is not yet at desired config.
- MCD is actively working.
- MCP remains `UPDATING=True` until all nodes converge.

### 6.6 MachineConfigNode Status

In newer OpenShift versions, `MachineConfigNode` can provide granular node update progress.

Commands:

```bash
oc get machineconfignodes
oc describe machineconfignode <node-name>
```

Useful phases include:

- update prepared
- cordoned
- drained
- applied files and OS
- rebooted
- uncordoned
- updated
- resumed
- node degraded

This is very useful when `oc get mcp` only says `UPDATING=True` but does not show where the node is stuck.

## 7. Deep Dive: `spec.paused=true`

### 7.1 What Paused Means

The MCP field is:

```yaml
spec:
  paused: true
```

When this is set, the MCO stops applying changes to the nodes associated with that MCP. It also stops generating a new desired MachineConfig for that pool according to the API behavior.

CLI check:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

List all MCP paused states:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status,UPDATING:.status.conditions[?(@.type=="Updating")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status
```

### 7.2 How to Pause an MCP

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

For a custom pool:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":true}}'
oc patch mcp logging --type=merge -p '{"spec":{"paused":true}}'
oc patch mcp storage --type=merge -p '{"spec":{"paused":true}}'
```

### 7.3 How to Unpause an MCP

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Then watch rollout:

```bash
watch -n 10 'oc get mcp'
```

### 7.4 Paused Is Not the Same as Updated

A paused MCP can still show `UPDATED=True` if all nodes match the old/current rendered config.

Example:

```text
NAME      CONFIG                  UPDATED   UPDATING   DEGRADED
logging   rendered-logging-old    True      False      False
```

But if it is paused and a new cluster-level change exists, it may not move forward. This can create confusion because the pool appears healthy from the `UPDATED` column but is intentionally not receiving new changes.

Always check:

```bash
oc get mcp logging -o yaml | grep -A5 paused
```

Better:

```bash
oc get mcp logging -o jsonpath='{.spec.paused}{"\n"}'
```

## 8. Relationship Between `UPDATING` and `paused`

### 8.1 Case 1: Pool Not Paused and Updating

```text
paused=false
UPDATED=False
UPDATING=True
DEGRADED=False
```

Meaning:

- Normal rollout is happening.
- Watch progress.
- Investigate only if it stalls.

### 8.2 Case 2: Pool Paused Before Change

```text
paused=true
UPDATED=True
UPDATING=False
DEGRADED=False
```

Meaning:

- Pool is stable on old/current config.
- New changes may not be rendered/applied for this pool.
- This is expected if you intentionally paused before maintenance.
- Dangerous if forgotten.

### 8.3 Case 3: Pool Paused During Rollout

```text
paused=true
UPDATED=False
UPDATING=True
DEGRADED=False
```

Meaning:

- Rollout was already in progress or partially applied.
- Some nodes might have new config, others old config.
- Pool might remain split until unpaused.
- This is risky for production consistency.

Avoid pausing in the middle of a rollout unless you are stopping a known bad change and have a rollback plan.

### 8.4 Case 4: Pool Paused and Degraded

```text
paused=true
UPDATED=False
UPDATING=True/False
DEGRADED=True
```

Meaning:

- Pool has a real node/configuration problem.
- Pausing does not fix degradation.
- You must inspect node annotations, MCD logs, events, and rendered configs.

## 9. Why Administrators Pause MCPs

### 9.1 Canary Update

A canary rollout uses a small custom MCP to update a limited set of worker nodes first.

Example strategy:

```text
1. Create worker-canary MCP with 1-2 nodes.
2. Pause normal worker pool.
3. Apply cluster update or MachineConfig change.
4. Allow canary pool to update.
5. Validate apps, networking, storage, logging, and node health.
6. Unpause remaining worker/custom pools in controlled order.
```

### 9.2 Dedicated Node Pool Maintenance

For example, you might pause `storage` because ODF/Ceph recovery is ongoing:

```bash
oc patch mcp storage --type=merge -p '{"spec":{"paused":true}}'
```

After storage is healthy:

```bash
oc patch mcp storage --type=merge -p '{"spec":{"paused":false}}'
```

### 9.3 Avoiding Business-Hour Reboots

You might apply a MachineConfig during the day but keep the MCP paused until a maintenance window.

Example:

```bash
oc patch mcp app --type=merge -p '{"spec":{"paused":true}}'
oc apply -f 99-app-kernelargs.yaml
# Later during approved window:
oc patch mcp app --type=merge -p '{"spec":{"paused":false}}'
```

### 9.4 Protecting Special Hardware Pools

Examples:

- GPU nodes running expensive training workloads
- storage nodes running ODF/Ceph
- infra nodes hosting routers and registry
- monitoring nodes hosting Prometheus/Alertmanager
- logging nodes running Elasticsearch/Loki/Vector/Fluentd

Pausing gives operational control, but only temporarily.

## 10. Production Risks of Paused MCPs

### 10.1 Certificate Rotation Risk

A long-paused MCP can miss automatically rotated certificates. This can break node-level operations such as:

- `oc debug node/<node>`
- `oc logs`
- `oc exec`
- `oc attach`
- kube-apiserver to kubelet communication

This is one of the most serious hidden risks of pausing pools for too long.

### 10.2 Cluster Upgrade Risk

Paused pools can block or complicate cluster upgrades. Even if the control plane finishes, worker/custom MCPs still need to converge.

Leaving MCPs paused after an upgrade can create an unsupported or unsafe operational state.

### 10.3 Configuration Drift Risk

If admins manually change node files while MCPs are paused, later unpausing can reveal drift or overwrite manual changes.

Manual host changes should be avoided. Use MachineConfig, KubeletConfig, ContainerRuntimeConfig, PerformanceProfile, or supported Operators.

### 10.4 Version Skew Risk

Do not intentionally run different MCPs on unrelated OpenShift payload versions for long periods. Staged rollout is acceptable; permanent version mismatch is not a valid design.

### 10.5 Security Patch Delay

If the cluster update includes OS or node-level security fixes, paused MCPs delay those fixes from reaching nodes.

## 11. `maxUnavailable` vs `paused`

### 11.1 `maxUnavailable`

Controls how many nodes can be unavailable during MCP rollout.

Example:

```yaml
spec:
  maxUnavailable: 1
```

For most production pools, especially control plane and storage-related pools, keep this conservative.

### 11.2 Do Not Set `maxUnavailable: 0`

`maxUnavailable` is not the mechanism to stop updates. Use `spec.paused: true` to stop updates.

Correct:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Incorrect design:

```yaml
spec:
  maxUnavailable: 0
```

### 11.3 Practical Recommendation

| Pool | Recommended maxUnavailable | Pause Usage |
|---|---:|---|
| master | 1 | Avoid unless documented control-plane-only update flow requires it; do not create custom control-plane MCPs. |
| worker | 1 or carefully higher | Useful for canary/staged updates. |
| infra | 1 | Pause only for short maintenance windows. |
| logging | 1 | Pause during ingestion-sensitive windows. |
| monitoring | 1 | Pause carefully; watch alerts and Prometheus HA. |
| storage | 1 | Pause carefully; coordinate with ODF/Ceph health. |
| gpu | 1 | Useful to avoid interrupting long-running jobs. |
| app | Depends on replicas/PDBs | Use with app HA planning. |

## 12. Dedicated Node Pool Example: Infra Pool

### 12.1 Label Nodes

```bash
oc label node worker-3 node-role.kubernetes.io/infra=
oc label node worker-4 node-role.kubernetes.io/infra=
oc label node worker-5 node-role.kubernetes.io/infra=
```

Optionally remove generic worker scheduling role from visible role labels only if your platform standard requires it. Be careful; node labels affect MCP membership and workload scheduling.

### 12.2 Create Infra MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

### 12.3 Add Infra-Specific MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-custom-sysctl
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/sysctl.d/99-infra.conf
        mode: 0644
        contents:
          source: data:text/plain;charset=utf-8;base64,bmV0LmNvcmUuc29tYXhjb25uID0gNDA5Ngo=
```

### 12.4 Pause/Unpause Infra Pool

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":true}}'
```

Apply changes, then during maintenance:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":false}}'
watch -n 10 'oc get mcp infra && oc get nodes -l node-role.kubernetes.io/infra='
```

## 13. Troubleshooting Runbook: MCP Updating Too Long

### Step 1: Check High-Level MCP Status

```bash
oc get mcp
oc get co machine-config
oc describe co machine-config
```

Look for:

- `UPDATING=True`
- `DEGRADED=True`
- `DEGRADEDMACHINECOUNT > 0`
- cluster operator message mentioning timeout, drain failure, render failure, or node degraded

### Step 2: Describe the Pool

```bash
oc describe mcp <pool-name>
```

Check:

- conditions
- messages
- events
- degraded machine count
- unavailable machine count
- observed generation
- source MachineConfigs

### Step 3: Identify Nodes in the Pool

```bash
oc get nodes -l node-role.kubernetes.io/<pool-name>=
```

For worker:

```bash
oc get nodes -l node-role.kubernetes.io/worker=
```

For custom pool:

```bash
oc get nodes --show-labels | grep <pool-name>
```

### Step 4: Compare Current and Desired Config

```bash
for n in $(oc get nodes -o name); do
  echo "===== $n ====="
  oc get $n -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{" current\n"}'
  oc get $n -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{" desired\n"}'
  oc get $n -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{" state\n"}'
  oc get $n -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{" reason\n"}'
  echo
 done
```

Expected healthy updating:

```text
currentConfig != desiredConfig
state=Working
```

Expected completed:

```text
currentConfig == desiredConfig
state=Done
```

Problem:

```text
state=Degraded
reason=<error>
```

### Step 5: Check Node Conditions

```bash
oc get nodes
oc describe node <node-name>
```

Look for:

- `NotReady`
- `SchedulingDisabled`
- disk pressure
- memory pressure
- PID pressure
- network unavailable
- kubelet errors
- reboot loop

### Step 6: Check MCO/MCD Pods

```bash
oc get pods -n openshift-machine-config-operator -o wide
```

Important pods:

- `machine-config-operator`
- `machine-config-controller`
- `machine-config-daemon-*`
- `machine-config-server-*`

Logs:

```bash
oc logs -n openshift-machine-config-operator deploy/machine-config-operator
oc logs -n openshift-machine-config-operator deploy/machine-config-controller
```

For a specific node, find the daemon pod:

```bash
oc get pod -n openshift-machine-config-operator -o wide | grep <node-name>
```

Then:

```bash
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon
```

### Step 7: Check Drain Blockers

MCO update can be stuck because the node cannot drain.

Check pods on the node:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node-name>
```

Check PDBs:

```bash
oc get pdb -A
```

Common blockers:

- strict PodDisruptionBudget
- single replica app with PDB `minAvailable: 1`
- local storage pod
- daemonset behavior confusion
- static pods
- terminating pods stuck
- finalizers
- unhealthy workloads preventing eviction

### Step 8: Check Reboot Completion

Sometimes node has applied config but reboot did not complete.

Check node uptime:

```bash
oc debug node/<node-name>
chroot /host uptime
chroot /host journalctl -b -u kubelet --no-pager | tail -100
chroot /host journalctl -b -u crio --no-pager | tail -100
chroot /host journalctl -b -u machine-config-daemon-firstboot --no-pager | tail -100
exit
```

### Step 9: Check Rendered Config

```bash
oc get mc | grep rendered-<pool>
oc describe mc rendered-<pool>-<hash>
```

Compare source MachineConfigs:

```bash
oc get mcp <pool-name> -o yaml
```

Look under:

```yaml
status:
  configuration:
    name: rendered-...
    source:
```

### Step 10: Decide Action

Possible action paths:

| Symptom | Likely Cause | Action |
|---|---|---|
| `UPDATING=True`, counts progressing | Normal rollout | Watch. |
| `UPDATING=True`, node cordoned | MCO updating node | Check MCD logs and wait if progressing. |
| `UPDATING=True`, no progress | Drain, reboot, or MCD issue | Inspect node, PDBs, MCD logs. |
| `DEGRADED=True` | Apply failed or drift | Read node reason and MCD logs. |
| Pool paused | Intentional stop | Confirm change ticket; unpause when ready. |
| Pool paused for days/weeks | Operational risk | Plan immediate controlled unpause. |
| Cluster upgrade blocked | MCP not converged | Fix degraded/paused/updating MCP. |

## 14. Troubleshooting Runbook: MCP Paused Accidentally

### Step 1: Detect Paused Pools

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status,UPDATING:.status.conditions[?(@.type=="Updating")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status
```

### Step 2: Check Age of Pause

Kubernetes does not always clearly show when `spec.paused` was set. Use audit logs/change management/GitOps history if available.

Check MCP YAML:

```bash
oc get mcp <pool> -o yaml
```

Check cluster upgrade history:

```bash
oc get clusterversion
oc describe clusterversion version
```

### Step 3: Check Whether There Are Pending Changes

```bash
oc get mcp <pool> -o yaml | less
oc get mc
oc get kubeletconfig
oc get containerruntimeconfig
```

### Step 4: Plan Safe Unpause

Before unpausing:

```bash
oc get nodes
oc get pods -A | grep -v Running | grep -v Completed
oc get pdb -A
oc get co
```

For storage pools:

```bash
oc get cephcluster -A 2>/dev/null || true
oc get pods -n openshift-storage -o wide 2>/dev/null || true
```

For infra pools:

```bash
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-image-registry -o wide
```

For monitoring pools:

```bash
oc get pods -n openshift-monitoring -o wide
```

### Step 5: Unpause During Maintenance

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
watch -n 10 'oc get mcp <pool>; oc get nodes'
```

### Step 6: Verify Completion

```bash
oc get mcp <pool>
oc describe mcp <pool>
oc get co machine-config
```

Expected:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
DEGRADEDMACHINECOUNT=0
```

## 15. Advanced Scenarios

### 15.1 Applying KubeletConfig to a Dedicated Pool

Label MCP:

```bash
oc label mcp app custom-kubelet=enabled
```

Create KubeletConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: app-kubelet-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: enabled
  kubeletConfig:
    maxPods: 250
    podsPerCore: 10
```

Apply:

```bash
oc apply -f app-kubelet-tuning.yaml
```

Expected:

```text
app MCP becomes UPDATING=True
nodes cordon/drain/reboot one by one based on maxUnavailable
```

If you do not want immediate rollout:

```bash
oc patch mcp app --type=merge -p '{"spec":{"paused":true}}'
oc apply -f app-kubelet-tuning.yaml
# Maintenance window:
oc patch mcp app --type=merge -p '{"spec":{"paused":false}}'
```

### 15.2 Pausing Worker Pool During Control-Plane-Only Update

In some EUS/control-plane-only strategies, worker pools are paused while control plane moves first.

Operational checklist:

```bash
oc get mcp
oc get co
oc adm upgrade
```

Pause non-control-plane pools:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
oc patch mcp infra --type=merge -p '{"spec":{"paused":true}}'
oc patch mcp logging --type=merge -p '{"spec":{"paused":true}}'
oc patch mcp monitoring --type=merge -p '{"spec":{"paused":true}}'
```

After control plane upgrade:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
# Wait until complete, then continue custom pools one by one.
```

Do not forget to unpause all pools.

### 15.3 Bad MachineConfig Rollout

Suppose you apply bad MachineConfig:

```bash
oc apply -f 99-worker-bad.yaml
```

MCP becomes:

```text
worker UPDATED=False UPDATING=True DEGRADED=True
```

Immediate actions:

```bash
oc describe mcp worker
oc get nodes
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

If the MachineConfig is clearly bad:

```bash
oc delete mc 99-worker-bad
```

Then watch:

```bash
watch -n 10 'oc get mcp worker'
```

If node drift remains, fix node state or use supported recovery steps.

### 15.4 Node Moved to New Custom MCP

If you label a worker node for a new custom MCP:

```bash
oc label node worker-6 node-role.kubernetes.io/gpu=
```

Then create `gpu` MCP. The node may transition to the rendered config for `gpu`.

Watch carefully:

```bash
oc get mcp
oc get node worker-6 -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node worker-6 -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

A common mistake is accidentally making a node match multiple custom MCP selectors. This causes unpredictable operational design and should be avoided.

## 17. Common Mistakes and Fixes

### Mistake 1: Forgetting a Pool Paused

Symptom:

```text
Cluster upgrade completed partially, but worker/custom pool did not move.
```

Check:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status
```

Fix:

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
```

### Mistake 2: Expecting `oc get mcp` to Show Paused by Default

Default output does not always show `spec.paused` clearly.

Use custom columns:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status,UPDATING:.status.conditions[?(@.type=="Updating")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status
```

### Mistake 3: Pausing Mid-Rollout Without Understanding Split State

If you pause while some nodes already updated, the pool can remain mixed.

Fix:

- Determine which nodes have which config.
- Decide whether to complete rollout or roll back MachineConfig.
- Avoid long-term split state.

### Mistake 4: Using Manual Host Changes

Manual edits under `/etc`, systemd, CRI-O, or kubelet-managed files can cause configuration drift.

Fix:

- Revert manual changes.
- Use MachineConfig.
- Use KubeletConfig/ContainerRuntimeConfig where appropriate.

### Mistake 5: Changing Control Plane Pool Aggressively

Do not set control plane `maxUnavailable` too high. Control plane updates should be conservative.

### Mistake 6: Creating Custom MCP for Control Plane Nodes

Custom MCPs for control plane nodes are not supported in the normal design. Control plane nodes should remain under the master MCP.

## 18. Interview-Level Explanation

If asked in an interview:

> What is MCP updating state in OpenShift?

Answer:

`UPDATING=True` on a MachineConfigPool means the Machine Config Operator is reconciling one or more nodes in that pool to the desired rendered machine configuration. The rollout can involve cordon, drain, applying files or OS changes, reboot, and uncordon. I check `oc describe mcp`, node annotations for current and desired config, MCD logs, node conditions, PDBs, and the machine-config ClusterOperator to determine whether it is progressing normally or stuck.

> What is MCP paused state?

Answer:

`spec.paused=true` intentionally stops the MCO from applying new machine configuration changes to nodes in that MCP. It is used for canary updates, maintenance windows, and staged rollouts of dedicated node pools. It should be temporary because long-paused pools can miss certificate rotations, delay OS/security updates, and block future upgrade progression.

> How do you pause and unpause?

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

> What is the danger of leaving MCP paused?

A paused MCP can miss important machine configuration, including certificate rotation and upgrade-related node changes. This can break commands that rely on kubelet connectivity and can leave nodes behind during cluster upgrades.

## 19. Production Best Practices

1. **Use custom MCPs intentionally.**  
   Create dedicated pools only when you need separate node configuration, update sequencing, workload isolation, or hardware-specific tuning.

2. **Never pause without a ticket/change window.**  
   Always record why it was paused, who owns it, and when it must be unpaused.

3. **Monitor paused pools.**  
   Create an alert or operational check for `spec.paused=true`.

4. **Keep pause duration short.**  
   Treat a paused MCP as temporary operational debt.

5. **Check cert rotation risk.**  
   Long-paused pools can miss important certificate updates.

6. **Use `maxUnavailable` for rollout speed, not stopping.**  
   Use `spec.paused` to stop rollout.

7. **Use canary pools for risky changes.**  
   Test MachineConfig and kubelet tuning on limited nodes first.

8. **Do not manually edit rendered MachineConfigs.**  
   Change source MachineConfigs instead.

9. **Avoid manual node changes.**  
   Manual changes can cause drift and degraded MCPs.

10. **Validate PDBs before maintenance.**  
    Many stuck MCP rollouts are actually drain/PDB problems.

11. **Unpause in stages.**  
    For large clusters, unpause low-risk pools first, then high-risk pools.

12. **Watch workload availability.**  
    MCP rollout is a node-level operation, but its impact is application-level.

## 21. Real-World Troubleshooting Patterns

### Pattern A: MCP Updating Because Node Is Cordoned

Output:

```text
worker UPDATED=False UPDATING=True DEGRADED=False
```

Node:

```text
worker-2 Ready,SchedulingDisabled
```

Interpretation:

The MCO may have cordoned the node as part of rollout. Check MCD logs and wait if progressing.

### Pattern B: MCP Updating Because PDB Blocks Drain

Symptoms:

- node cordoned
- drain does not complete
- pods remain on node
- MCO logs mention drain failure or eviction failure

Check:

```bash
oc get pdb -A
oc get pods -A -o wide --field-selector spec.nodeName=<node>
```

Fix:

- temporarily scale app
- adjust PDB carefully
- ensure app has enough replicas
- retry rollout by allowing MCO to continue

### Pattern C: MCP Degraded Due to Drift

Symptoms:

```text
DEGRADED=True
DEGRADEDMACHINECOUNT=1
```

Node annotation:

```text
machineconfiguration.openshift.io/state=Degraded
machineconfiguration.openshift.io/reason=content mismatch for file ...
```

Fix:

- restore file content and permissions to match MachineConfig
- or apply corrected MachineConfig
- use force file only with caution because it can reboot the node

### Pattern D: Paused MCP Blocking Upgrade

Symptoms:

```text
oc adm upgrade shows blocked or incomplete update
machine-config ClusterOperator not progressing as expected
```

Check:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status
```

Fix:

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
```

Then watch until all pools are updated.

## 22. Mental Model for 10-Year Experienced Admins

Think of MCPs like controlled host configuration release rings.

```text
MachineConfig = desired host configuration
Rendered MachineConfig = compiled release artifact
MachineConfigPool = release ring / node group
MachineConfigDaemon = node-side agent applying the release
UPDATING=True = release is rolling out
UPDATED=True = release completed
DEGRADED=True = release failed or drift detected
paused=true = release ring is frozen
maxUnavailable = rollout concurrency limit
```

In production, you do not just ask:

```text
Is the MCP updated?
```

You ask:

```text
Which pool?
What changed?
Which rendered config?
Which nodes are affected?
Is it paused?
Is it progressing?
Is it degraded?
What is maxUnavailable?
What workloads are on those nodes?
Are PDBs safe?
Can the business tolerate reboot now?
Will certificate rotation or upgrade be blocked?
```

That is the difference between basic administration and advanced OpenShift operations.
