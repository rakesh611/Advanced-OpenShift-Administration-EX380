# Infra Node Pool in OpenShift

**Topic area:** Cluster Partitioning and Dedicated Node Pools  
**Audience:** Advanced OpenShift Administration / Senior Platform Engineer  
**Perspective:** Production operations, design, troubleshooting, and day-2 administration  
**Applies to:** OpenShift Container Platform 4.x. Examples are written in a version-neutral way, but always confirm exact fields with `oc explain` for your cluster version.

---

## 1. Executive Summary

An **infra node pool** is a dedicated group of OpenShift worker-derived nodes used to run **cluster-supporting infrastructure workloads** instead of user application workloads.

Typical workloads placed on infra nodes include:

- Ingress router / HAProxy IngressController pods
- Integrated OpenShift image registry
- Cluster monitoring stack such as Prometheus, Alertmanager, Thanos Querier
- Cluster aggregated logging / LokiStack / logging collectors, depending on design
- Platform add-ons such as Red Hat Quay, OpenShift Data Foundation, Advanced Cluster Management, Advanced Cluster Security, GitOps, Pipelines, or Service Mesh when they are supporting the cluster and not end-user applications

In real production environments, an infra node pool is not just a label. It is usually a combination of:

1. **Dedicated compute capacity**
   - MachineSet, MachinePool, manually provisioned worker nodes, or cloud/on-prem VMs.

2. **Node role label**
   - `node-role.kubernetes.io/infra=""`

3. **Scheduling isolation**
   - Taints on infra nodes.
   - Matching tolerations on infra workloads.
   - Node selectors or node placement rules on OpenShift Operators.

4. **Optional dedicated MachineConfigPool**
   - Used when infra nodes need different kubelet, CRI-O, operating system, kernel, sysctl, proxy, certificate, or runtime configuration.

5. **Operational policy**
   - Sizing, high availability, upgrades, monitoring, troubleshooting, and clear rules about what is allowed to run there.

The most important production rule is this:

> A taint repels unwanted workloads, but it does not attract required workloads. A node selector attracts selected workloads, but it does not repel everything else. A mature infra pool normally uses both.

## 2. What an Infra Node Pool Really Means

OpenShift installs with two major node roles by default:

- **Control plane nodes**
  - API server
  - etcd
  - controller manager
  - scheduler
  - core control-plane operators

- **Worker nodes**
  - User workloads
  - Router pods by default
  - Registry pods by default if enabled
  - Monitoring components by default
  - Many operator-managed platform pods

An **infra node** is normally a worker node with an additional role label:

```bash
oc label node <node-name> node-role.kubernetes.io/infra=""
```

After labeling, `oc get nodes` usually shows:

```text
NAME                         STATUS   ROLES          AGE   VERSION
worker-0.example.com         Ready    worker         20d   v1.xx.x
infra-0.example.com          Ready    infra,worker   20d   v1.xx.x
infra-1.example.com          Ready    infra,worker   20d   v1.xx.x
infra-2.example.com          Ready    infra,worker   20d   v1.xx.x
```

The dual role `infra,worker` is normal and usually recommended. The infra role communicates that the node is intended for infrastructure workloads; the worker role keeps the node compatible with the Machine Config Operator and general worker inheritance unless you create a dedicated custom MachineConfigPool.

## 3. Infra Node Pool vs Worker Pool vs MachineConfigPool vs MachineSet

Many administrators mix these terms. In interviews, production design reviews, and troubleshooting, you should separate them clearly.

| Concept | What it controls | OpenShift object | Main purpose |
|---|---|---|---|
| Worker node | A node that can run normal workloads | `Node` | General compute |
| Infra node | Worker-derived node reserved for infra workloads | `Node` with `node-role.kubernetes.io/infra=""` | Platform workload isolation |
| MachineSet | VM/node provisioning on Machine API platforms | `MachineSet` in `openshift-machine-api` | Create and scale machines |
| MachineConfigPool | OS/kubelet/CRI-O config rollout group | `MachineConfigPool` | Manage node configuration lifecycle |
| Taint | Repel workloads that do not tolerate it | `Node.spec.taints` | Scheduling isolation |
| Toleration | Allow a pod to run on a tainted node | `Pod.spec.tolerations` or Operator CR | Permit infra workloads |
| Node selector / node placement | Attract workload to selected nodes | Pod spec or Operator CR | Placement targeting |

A senior-level explanation:

> A MachineSet creates the nodes. A node label identifies the nodes. A taint protects the nodes. Operator nodePlacement moves OpenShift infrastructure workloads onto the nodes. A MachineConfigPool manages OS-level configuration for those nodes.

## 4. Why Infra Node Pools Are Used

### 4.1 Isolation of Platform Services

In production, router, registry, monitoring, and logging are not normal application pods. They support every tenant and every application. If user workloads consume all CPU, memory, disk I/O, PID count, or ephemeral storage on generic workers, platform services can become unstable.

Infra node pools reduce this risk by separating platform workloads from user workloads.

### 4.2 More Predictable Cluster Operations

Ingress, monitoring, registry, and logging have very different resource behavior:

- Router pods are network and connection heavy.
- Registry pods are storage and network heavy.
- Monitoring pods are memory, CPU, and disk I/O heavy.
- Logging pods can create high CPU, memory, and storage pressure during bursts.

Dedicated infra nodes make capacity planning easier.

### 4.3 Subscription and Sizing Separation

Red Hat distinguishes between user application worker capacity and infrastructure capacity. Infra nodes can be used for approved cluster-supporting components. Any node that runs non-infrastructure application workloads should be treated as worker capacity for subscription and sizing purposes.

Do not use the infra label as a trick to run business applications without worker entitlement. From an administration perspective, that creates compliance, support, and audit issues.

### 4.4 Operational Blast-Radius Control

A broken application deployment should not evict Prometheus. A badly configured CI pipeline should not starve routers. A noisy tenant should not fill logging storage. Infra node pools help create blast-radius boundaries.

### 4.5 Different Hardware Profiles

Infra workloads may need different machines:

| Workload | Typical pressure | Infra sizing consideration |
|---|---|---|
| Ingress router | CPU, network, connection tracking | More NIC bandwidth, enough CPU, HA across zones |
| Registry | Network, storage backend, memory | Object storage or reliable PV, enough replicas |
| Monitoring | Memory, disk I/O, CPU | Fast disks for Prometheus, larger memory |
| Logging / Loki | Disk, memory, CPU, object storage | Dedicated storage and spread across zones |
| ODF | Disk, network, CPU | Usually its own storage node pool, not mixed casually |

## 5. The Core Design Pattern

A production infra node pool generally follows this pattern:

```text
                ┌────────────────────────────┐
                │ OpenShift Control Plane     │
                │ api / etcd / scheduler      │
                └─────────────┬──────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
┌───────▼────────┐    ┌───────▼────────┐    ┌───────▼────────┐
│ App worker pool │    │ Infra pool      │    │ Special pool    │
│ user apps       │    │ routers         │    │ storage/gpu/etc │
│ deployments     │    │ registry        │    │ workload-specific│
│ jobs            │    │ monitoring      │    │                 │
└────────────────┘    │ logging         │    └────────────────┘
                      └────────────────┘
```

Infra nodes normally have:

```yaml
metadata:
  labels:
    node-role.kubernetes.io/worker: ""
    node-role.kubernetes.io/infra: ""
spec:
  taints:
  - key: node-role.kubernetes.io/infra
    value: reserved
    effect: NoSchedule
```

Infra workloads normally have:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
  operator: Equal
```

Some Operator CRs use `nodePlacement` instead of direct `nodeSelector` and `tolerations` fields. Always verify the exact field path with:

```bash
oc explain <resource>.spec
oc explain <resource>.spec.nodePlacement
oc explain <resource>.spec.template
```

## 6. Infra Node Pool Building Blocks

## 6.1 Node Role Label

The standard infra label is:

```bash
node-role.kubernetes.io/infra=""
```

Apply it with:

```bash
oc label node <node-name> node-role.kubernetes.io/infra=""
```

Verify:

```bash
oc get nodes
oc get nodes -l node-role.kubernetes.io/infra
oc describe node <node-name> | grep -A5 Labels
```

Expected output:

```text
NAME                  STATUS   ROLES          AGE   VERSION
infra-0.example.com   Ready    infra,worker   10d   v1.xx.x
```

### Senior admin note

Do not casually remove the `worker` role label from infra nodes. If a node has only a custom role such as `infra` and no MachineConfigPool selects it properly, Machine Config Operator behavior can become confusing or unsupported. Keep `worker,infra` unless you fully understand the MachineConfigPool design.

---

## 6.2 Taints

A taint on an infra node prevents normal user pods from landing there.

Common taint:

```bash
oc adm taint nodes <node-name> node-role.kubernetes.io/infra=reserved:NoSchedule
```

Verify:

```bash
oc describe node <node-name> | grep -i Taints -A3
```

Expected:

```text
Taints: node-role.kubernetes.io/infra=reserved:NoSchedule
```

Remove the taint if required:

```bash
oc adm taint nodes <node-name> node-role.kubernetes.io/infra=reserved:NoSchedule-
```

### Taint effect comparison

| Effect | Meaning | Infra node usage |
|---|---|---|
| `NoSchedule` | New pods cannot schedule unless they tolerate the taint | Most common for infra nodes |
| `PreferNoSchedule` | Scheduler avoids the node when possible | Weak isolation; rarely enough for production infra isolation |
| `NoExecute` | Evicts existing pods that do not tolerate the taint and blocks new ones | Stronger isolation; use carefully |

Most infra node designs start with `NoSchedule`. Some component examples also add `NoExecute` tolerations because the component should survive or intentionally run on nodes that carry stronger taints.

---

## 6.3 Tolerations

A toleration allows a pod to run on a tainted infra node.

Example:

```yaml
spec:
  tolerations:
  - key: node-role.kubernetes.io/infra
    value: reserved
    effect: NoSchedule
    operator: Equal
```

Important points:

- A toleration does **not** force the pod onto infra nodes.
- A toleration only says, “this pod is allowed to run there.”
- You still need `nodeSelector`, `nodeAffinity`, or an Operator-specific `nodePlacement` field to attract the pod to infra nodes.

---

## 6.4 Node Selector

A node selector attracts a workload to nodes with matching labels.

Example pod-level selector:

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
```

For OpenShift-managed infrastructure workloads, do not usually patch the generated Deployment or DaemonSet directly. Configure the owning Operator CR instead.

Examples:

- IngressController for routers
- Image Registry Operator Config for registry
- Cluster Monitoring ConfigMap for monitoring
- LokiStack or ClusterLogForwarder for logging

---

## 6.5 MachineSet

A MachineSet creates and maintains machines on platforms where the Machine API is available.

Check platform and Machine API availability:

```bash
oc get infrastructure cluster -o jsonpath='{.status.platform}{"\n"}'
oc get machinesets -n openshift-machine-api
oc get machines -n openshift-machine-api
```

On Machine API platforms, infra nodes are commonly created by cloning a worker MachineSet and changing:

- MachineSet name
- labels
- selector labels
- template labels
- instance type / flavor
- zone
- replicas
- taints
- provider-specific values

Core MachineSet identity labels usually look like this:

```yaml
machine.openshift.io/cluster-api-machine-role: infra
machine.openshift.io/cluster-api-machine-type: infra
machine.openshift.io/cluster-api-machineset: <infra-machineset-name>
```

Node labels are usually placed under `spec.template.spec.metadata.labels`:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
```

Taints can also be placed in the MachineSet template so new nodes are born protected:

```yaml
spec:
  template:
    spec:
      taints:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
```

## 6.6 MachineConfigPool

A MachineConfigPool controls how the Machine Config Operator applies node-level configuration.

OpenShift default pools:

```bash
oc get mcp
```

Typical output:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False
worker    rendered-worker-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False
```

When you create a custom infra MachineConfigPool, you might see:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-...                                True      False      False
worker    rendered-worker-...                                True      False      False
infra     rendered-infra-...                                 True      False      False
```

A common infra MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

### Key MCP behavior

- A custom worker-derived pool inherits worker machine configs.
- A custom pool can also receive machine configs targeted only to that pool.
- A node can belong to only one MCP.
- Custom pools take priority over the default worker pool when labels match.
- MachineConfig changes can drain and reboot nodes.
- Configuration drift can mark nodes or pools degraded.

### When to create an infra MCP

Create an infra MCP when infra nodes need different host-level settings from normal workers, such as:

- Different kubelet `maxPods`
- Different kubelet reservations
- Different CRI-O log size
- Registry mirror or trust bundle behavior
- Dedicated kernel arguments
- Different sysctl values
- Extra systemd unit
- Custom file on the RHCOS host
- Different image garbage collection settings
- Infra-only performance or network tuning

Do **not** create a custom MCP just because you created infra nodes. If infra nodes can safely inherit worker configuration, the extra pool may not be necessary. But for long-term mature operations, many teams create one because it gives controlled update and configuration boundaries.

```bash
oc get co
```

```bash

oc get machinesets -n openshift-machine-api
```


```bash
oc get pods -A -o wide | egrep 'router|registry|prometheus|alertmanager|thanos|loki|collector'
```

Check current MachineConfigPools:

```bash
oc get mcp
```

## 7.2 Create Infra Capacity

### Option A: Machine API / IPI style

List worker MachineSets:

```bash
oc get machinesets -n openshift-machine-api
```

Export an existing worker MachineSet:

```bash
oc get machineset <existing-worker-machineset> \
  -n openshift-machine-api \
  -o yaml > infra-machineset.yaml
```

Edit carefully:

```bash
vi infra-machineset.yaml
```

Remove generated fields:

```yaml
metadata:
  creationTimestamp: null
  generation: null
  resourceVersion: null
  uid: null
status: null
```

Change the MachineSet name and labels:

```yaml
metadata:
  name: <infra-machineset-name>
  namespace: openshift-machine-api
  labels:
    machine.openshift.io/cluster-api-cluster: <infrastructure_id>
spec:
  replicas: 3
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-cluster: <infrastructure_id>
      machine.openshift.io/cluster-api-machineset: <infra-machineset-name>
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-cluster: <infrastructure_id>
        machine.openshift.io/cluster-api-machine-role: infra
        machine.openshift.io/cluster-api-machine-type: infra
        machine.openshift.io/cluster-api-machineset: <infra-machineset-name>
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
      taints:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
```

Apply:

```bash
oc apply -f infra-machineset.yaml
```

Watch machines and nodes:

```bash
watch 'oc get machineset,machine -n openshift-machine-api; echo; oc get nodes'
```

### Option B: UPI / manually provisioned nodes

If Machine API is not managing compute nodes, provision the nodes externally, join them as workers, then label them:

```bash
oc label node <node-name> node-role.kubernetes.io/infra=""
```

Then taint them:

```bash
oc adm taint nodes <node-name> node-role.kubernetes.io/infra=reserved:NoSchedule
```

## 7.3 Create an Infra MachineConfigPool

Create `infra-mcp.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp infra
```

Watch rendering:

```bash
watch 'oc get mcp; echo; oc get nodes -l node-role.kubernetes.io/infra'
```

### Important production warning

Creating a new MCP can cause node configuration reconciliation. Depending on the rendered config difference, nodes can drain and reboot. Do this during a maintenance window if these nodes already run critical workloads.

## 7.4 Apply Infra Taints

If taints were not included in the MachineSet, add them manually:

```bash
for node in $(oc get nodes -l node-role.kubernetes.io/infra -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  oc adm taint nodes "$node" node-role.kubernetes.io/infra=reserved:NoSchedule --overwrite
done
```

Verify:

```bash
oc describe nodes -l node-role.kubernetes.io/infra | egrep 'Name:|Roles:|Taints:'
```

## 7.5 Move the Ingress Router to Infra Nodes

Check current IngressController:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

Patch node placement:

```bash
oc patch ingresscontroller default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{
    "spec": {
      "nodePlacement": {
        "nodeSelector": {
          "matchLabels": {
            "node-role.kubernetes.io/infra": ""
          }
        },
        "tolerations": [
          {
            "key": "node-role.kubernetes.io/infra",
            "value": "reserved",
            "effect": "NoSchedule"
          }
        ]
      }
    }
  }'
```

Verify router pods:

```bash
oc get pods -n openshift-ingress -o wide
oc get nodes -l node-role.kubernetes.io/infra
```

Check route availability:

```bash
oc get ingresscontroller default -n openshift-ingress-operator
oc get co ingress
```

### Production considerations for router migration

Before moving routers, check:

- External load balancer target pool
- Firewall rules
- Security groups
- Node ports or host network behavior
- DNS records
- Health checks
- Zone spread
- Router replica count
- Disruption budget

A router running on infra nodes is useless if the external load balancer still sends traffic only to old worker nodes.

## 7.6 Move the Integrated Image Registry

Check current registry config:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Depending on OpenShift version, the Image Registry Operator may support direct `nodeSelector` / `tolerations` or `nodePlacement`. Confirm with:

```bash
oc explain configs.imageregistry.operator.openshift.io.spec
oc explain configs.imageregistry.operator.openshift.io.spec.nodePlacement
```

Example using `nodePlacement` style:

```yaml
apiVersion: imageregistry.operator.openshift.io/v1
kind: Config
metadata:
  name: cluster
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoExecute
```

Example using direct fields:

```yaml
apiVersion: imageregistry.operator.openshift.io/v1
kind: Config
metadata:
  name: cluster
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    value: reserved
    effect: NoSchedule
```

Verify registry pods:

```bash
oc get pods -n openshift-image-registry -o wide
oc get co image-registry
```

### Registry production notes

- Do not move registry blindly if it uses local or zonal persistent storage.
- Verify object storage / PV access from infra nodes.
- Verify pull-through performance.
- Verify image pruning jobs.
- Verify routes if registry is exposed externally.
- Ensure registry replicas match storage backend capabilities.

### Logging production notes

- Logging can be more expensive than expected.
- Keep log retention realistic.
- Do not mix high-volume log storage with small router-only infra nodes.
- Ensure object storage, PVCs, or storage backends are reachable from infra nodes.
- Validate collector placement separately from Loki placement.
- Collectors often run as DaemonSets and may need different placement logic than the log store.

## 8. Dedicated Infra MCP: Advanced Examples

## 8.1 Infra-specific MachineConfig

Example: create a file only on infra nodes.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-example-file
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/example-infra-marker
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,SW5mcmEgbm9kZSBjb25maWd1cmVkCg==
```

Apply:

```bash
oc apply -f 99-infra-example-file.yaml
```

Watch:

```bash
oc get mcp infra -w
```

Verify on node using debug:

```bash
oc debug node/<infra-node-name>
chroot /host
cat /etc/example-infra-marker
exit
exit
```

### Important

Any MachineConfig change can reboot matching nodes. Keep `maxUnavailable` and HA in mind.

## 8.2 Infra KubeletConfig Example

Use this when infra nodes need different kubelet-level settings.

First ensure the MCP has a label you can select:

```bash
oc get mcp infra --show-labels
```

If needed:

```bash
oc label mcp infra pools.operator.machineconfiguration.openshift.io/infra="" --overwrite
```

Example `KubeletConfig`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: infra-kubelet-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/infra: ""
  kubeletConfig:
    maxPods: 250
    systemReserved:
      cpu: 1000m
      memory: 2Gi
    kubeReserved:
      cpu: 500m
      memory: 1Gi
```

Apply:

```bash
oc apply -f infra-kubelet-config.yaml
```

Verify:

```bash
oc get mcp infra
oc describe mcp infra
```

Use with care. Increasing `maxPods` without considering node CPU, memory, PID, CNI scale, and logging volume can create worse outages.

## 8.3 Infra CRI-O / Container Runtime Considerations

Infra workloads such as routers, logging collectors, and monitoring components can generate many logs. You may need container runtime log rotation settings, image garbage collection tuning, or registry mirror configuration. In OpenShift 4.x, use supported MachineConfig or appropriate OpenShift configuration APIs instead of manual edits on `/etc/crio/crio.conf`.

Manual host edits are dangerous because Machine Config Daemon can detect drift and mark the node degraded.

## 9. High Availability Design

## 9.1 Minimum Production Layout

For production, avoid a single infra node.

Recommended baseline:

```text
infra-a   zone-a
infra-b   zone-b
infra-c   zone-c
```

Why three?

- Ingress can survive one zone/node failure.
- Monitoring can maintain HA pairs.
- Logging/storage components can spread replicas.
- MachineConfigPool updates can roll one node at a time.
- Maintenance windows become safer.

## 9.2 Zone-aware MachineSets

On cloud platforms, create one infra MachineSet per zone:

```text
<cluster-id>-infra-us-east-1a
<cluster-id>-infra-us-east-1b
<cluster-id>-infra-us-east-1c
```

This gives better control than one MachineSet with all replicas in one zone.

## 9.3 Router HA

Check router replicas:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o jsonpath='{.spec.replicas}{"\n"}'
```

Set if required:

```bash
oc patch ingresscontroller default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"replicas":3}}'
```

Verify spread:

```bash
oc get pods -n openshift-ingress -o wide
```

If all router pods land on the same infra node, review topology spread, anti-affinity, and resource availability.

## 9.4 Monitoring HA

Check Prometheus and Alertmanager:

```bash
oc get pods -n openshift-monitoring -o wide | egrep 'prometheus|alertmanager|thanos'
```

Confirm that replicas are not all on the same node.

## 9.5 Storage-backed Components

For registry, Prometheus, Loki, or ODF-related components, verify storage topology:

```bash
oc get pvc -A
oc get pv
oc get sc
oc describe pvc <pvc-name> -n <namespace>
```

Common problem:

```text
0/6 nodes are available: pod has unbound immediate PersistentVolumeClaims
```

or

```text
node(s) had volume node affinity conflict
```

This usually means storage topology and infra node placement do not match.

## 10. Capacity Planning for Infra Nodes

There is no universal sizing. Sizing depends on:

- Application traffic
- Number of routes
- TLS termination volume
- Metrics cardinality
- Number of namespaces and pods
- Logging rate
- Registry usage
- Retention settings
- Storage backend
- Zone count
- Failure tolerance

## 10.1 Practical Starting Points

### Small non-production cluster

```text
Infra nodes: 2 or 3
vCPU:        4 each
Memory:      16 GiB each
Disk:        120 GiB+
Use case:    routers, small monitoring, registry if light
```

### Medium production cluster

```text
Infra nodes: 3
vCPU:        8 each
Memory:      32 GiB each
Disk:        200 GiB+ or fast storage for monitoring/logging
Use case:    routers, registry, monitoring, moderate logging
```

### Large production cluster

```text
Separate pools:
- infra-router pool
- infra-monitoring pool
- logging pool
- storage/ODF pool

vCPU/memory/storage sized per workload profile.
```

## 10.2 Why One Big Infra Pool Can Be Bad

Putting router, Prometheus, Loki, registry, ODF, Quay, GitOps, and Pipelines on the same three nodes may technically work, but operationally it creates contention:

- Logging spikes affect router latency.
- Prometheus compaction affects registry performance.
- Registry pulls affect Loki ingestion.
- ODF disk pressure affects everything.

Mature clusters often split infrastructure further:

```text
infra-router
infra-monitoring
infra-logging
infra-storage
infra-cicd
```

Each pool can have its own labels, taints, tolerations, and MachineConfigPool.

## 11. Cluster Partitioning Strategy

Infra node pools are part of a larger cluster partitioning strategy.

## 11.1 Common Pool Types

| Pool | Purpose | Example label | Example taint |
|---|---|---|---|
| `worker` | General apps | `node-role.kubernetes.io/worker` | none |
| `infra` | Platform services | `node-role.kubernetes.io/infra` | `node-role.kubernetes.io/infra=reserved:NoSchedule` |
| `logging` | Heavy log stack | `node-role.kubernetes.io/logging` | `node-role.kubernetes.io/logging=reserved:NoSchedule` |
| `storage` | ODF/Ceph | `cluster.ocs.openshift.io/openshift-storage` | storage-specific taints |
| `gpu` | GPU workloads | `feature.node.kubernetes.io/pci-10de.present=true` | `nvidia.com/gpu=reserved:NoSchedule` |
| `ci` | CI/CD builds | `node-role.kubernetes.io/ci` | `node-role.kubernetes.io/ci=reserved:NoSchedule` |

## 11.2 Label Naming Pattern

Use labels that clearly describe ownership and scheduling intent.

Examples:

```bash
node-role.kubernetes.io/infra=""
node-role.kubernetes.io/logging=""
node-role.kubernetes.io/storage=""
platform.example.com/pool=infra
platform.example.com/tier=system
```

Avoid random labels like:

```bash
type=abc
role=test
node=infra
```

These are hard to audit and easy to misuse.

## 11.3 Taint Naming Pattern

Common:

```bash
node-role.kubernetes.io/infra=reserved:NoSchedule
```

For stricter separation:

```bash
platform.example.com/infra=reserved:NoSchedule
platform.example.com/logging=reserved:NoSchedule
platform.example.com/storage=reserved:NoSchedule
```

Use a standard pattern and document it.

## 13. Troubleshooting Scenarios

## 13.1 Infra Nodes Exist but No Infra Pods Move There

### Symptoms

```bash
oc get nodes
```

Shows infra nodes, but router/registry/monitoring still run on workers.

### Likely cause

You labeled the node but did not configure workload placement.

### Fix

Configure the owning Operator CR:

- `IngressController.spec.nodePlacement`
- Image registry config placement fields
- `cluster-monitoring-config`
- Logging CR placement fields

Remember:

```text
Labeling nodes does not automatically move workloads.
```

---

## 13.2 Pods Pending After Moving to Infra Nodes

### Symptoms

```text
0/9 nodes are available: 3 node(s) had untolerated taint {node-role.kubernetes.io/infra: reserved}
```

### Cause

The workload has a node selector for infra but lacks matching toleration.

### Fix

Add toleration:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
  operator: Equal
```

---

## 13.3 User Pods Running on Infra Nodes

### Cause

Infra nodes are labeled but not tainted, or user namespaces have broad tolerations.

### Fix

Taint infra nodes:

```bash
oc adm taint nodes <infra-node> node-role.kubernetes.io/infra=reserved:NoSchedule --overwrite
```

Audit user workloads for tolerations:

```bash
oc get pods -A -o yaml | grep -B5 -A10 'node-role.kubernetes.io/infra'
```

---

## 13.4 MCP Infra Is Degraded

Check:

```bash
oc describe mcp infra
oc get nodes
oc describe node <infra-node>
oc logs -n openshift-machine-config-operator daemonset/machine-config-daemon -c machine-config-daemon
```

Common causes:

- Manual host file change caused configuration drift.
- Bad MachineConfig syntax.
- Bad systemd unit.
- Node cannot drain because of PDB.
- Node cannot pull required OS update image.
- Disk pressure or image filesystem issue.

Fix depends on the reason. Do not delete MachineConfig blindly until you understand whether the rendered config is active.

---

## 13.5 Infra Nodes Not Counted Correctly in Roles

### Symptom

`oc get nodes` does not show `infra` role.

### Cause

Missing role label or incorrect label syntax.

### Fix

```bash
oc label node <node-name> node-role.kubernetes.io/infra="" --overwrite
```

Then verify:

```bash
oc get nodes
```

---

## 13.6 Router Fails After Moving to Infra Nodes

Check router pods:

```bash
oc get pods -n openshift-ingress -o wide
oc describe pod <router-pod> -n openshift-ingress
```

Check Ingress operator:

```bash
oc get co ingress
oc describe ingresscontroller default -n openshift-ingress-operator
```

Check external traffic:

```bash
oc get svc -n openshift-ingress
oc get endpoints -n openshift-ingress
```

Likely causes:

- Infra nodes not in load balancer backend pool.
- Security group or firewall does not allow traffic.
- Router replicas cannot schedule because taint toleration missing.
- Node selector matches no node.
- Router resource requests exceed infra node capacity.

---

## 13.7 Registry Fails After Moving to Infra Nodes

Check:

```bash
oc get co image-registry
oc get pods -n openshift-image-registry -o wide
oc logs -n openshift-image-registry deploy/image-registry
oc get pvc -n openshift-image-registry
```

Likely causes:

- Storage unavailable from infra node zone.
- Registry config uses unsupported field path for your version.
- Node selector or toleration missing.
- Registry route or service not reachable.
- Pull secret or object storage credentials issue.

---

## 13.8 Monitoring Fails After Moving to Infra Nodes

Check:

```bash
oc get co monitoring
oc get pods -n openshift-monitoring -o wide
oc get events -n openshift-monitoring --sort-by=.lastTimestamp
```

Common issues:

- Prometheus PVC cannot attach in infra node zone.
- Infra nodes do not have enough memory.
- Tolerations missing for one component.
- ConfigMap YAML indentation error.
- Cluster Monitoring Operator rejects unsupported config.

Validate ConfigMap:

```bash
oc get cm cluster-monitoring-config -n openshift-monitoring -o yaml
```

---

## 13.9 DaemonSet Pods Marked Misscheduled After Tainting Infra Nodes

When a `NoSchedule` taint is added, DaemonSet-controlled pods already on the node can show as misscheduled if they do not tolerate the taint. Some DaemonSets are operator-managed, so do not directly edit the DaemonSet unless the product documentation says to do so.

Approach:

1. Identify owner:

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.metadata.ownerReferences}'
```

2. Check whether an Operator CR supports tolerations.
3. Configure tolerations at the supported owner level.
4. Let the Operator reconcile.

## 14. Upgrade and Maintenance Behavior

## 14.1 MachineConfigPool Updates

During cluster updates or MachineConfig changes, the Machine Config Operator updates nodes by pool. It drains nodes, applies configuration, and may reboot nodes.

Check pool status:

```bash
oc get mcp
oc describe mcp infra
```

Set `maxUnavailable` if appropriate:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

For a three-node infra pool, `maxUnavailable: 1` is usually safer than updating too many infra nodes at once.

## 14.2 PodDisruptionBudgets

Check PDBs:

```bash
oc get pdb -A
```

If MCO cannot drain an infra node because PDBs block eviction, MCP updates may pause.

## 14.3 Maintenance Workflow

Safe node maintenance:

```bash
oc adm cordon <infra-node>
oc adm drain <infra-node> --ignore-daemonsets --delete-emptydir-data
# perform maintenance
oc adm uncordon <infra-node>
```

On Machine API platforms, prefer replacing unhealthy machines through MachineSet/Machine API patterns rather than manual host repair when possible.

## 15. Security and Governance

## 15.1 Restrict Who Can Tolerate Infra Taints

Any user who can add tolerations and node selectors to workloads may intentionally or accidentally schedule workloads on infra nodes.

Governance controls:

- Limit RBAC for privileged namespaces.
- Use admission policies where available.
- Review templates and Helm charts.
- Audit workloads with infra tolerations.
- Use namespace-level policies for tenant workloads.

## 15.2 Audit Infra Tolerations

```bash
oc get pods -A -o json | jq -r '
  .items[] |
  select(.spec.tolerations[]? | .key == "node-role.kubernetes.io/infra") |
  [.metadata.namespace, .metadata.name] | @tsv
'
```

If `jq` is not available, use:

```bash
oc get pods -A -o yaml | grep -B8 -A12 'node-role.kubernetes.io/infra'
```

## 15.3 Avoid Running User Workloads on Infra Nodes

Do not allow application namespaces to use:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

or:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
```

unless you intentionally designed a shared platform pool and understand the subscription/support implications.

## 16. Common Production Anti-patterns

## 16.1 Only Labeling Nodes

Bad:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=""
```

Then doing nothing else.

Why bad:

- User workloads can still land there.
- Infra workloads do not automatically move there.

Correct:

- Label infra nodes.
- Taint infra nodes.
- Add nodePlacement to platform workloads.
- Verify pod placement.

---

## 16.2 Removing Worker Label Without MCP Plan

Bad:

```bash
oc label node infra-0 node-role.kubernetes.io/worker-
```

Why bad:

- Can break expected MCO pool selection unless custom MCP is correct.
- Reduces clarity.
- Creates day-2 support complexity.

Better:

```text
Keep worker,infra labels and use taints/tolerations.
```

---

## 16.3 Using Cluster-wide Default Node Selector to Infra

Dangerous:

```yaml
spec:
  defaultNodeSelector: node-role.kubernetes.io/infra=""
```

Why dangerous:

- Can make many pods unschedulable.
- Conflicts with workloads that require master, worker, storage, GPU, or other node roles.
- Affects cluster-wide scheduling expectations.

Use component-level node placement instead.

---

## 16.4 Patching Operator-owned Deployments Directly

Bad:

```bash
oc edit deployment/router-default -n openshift-ingress
```

Why bad:

- Operator may revert your changes.
- Upgrade may overwrite settings.
- Unsupported configuration path.

Correct:

```bash
oc edit ingresscontroller default -n openshift-ingress-operator
```

---

## 16.5 Mixing Heavy Logging and Router-only Infra Nodes

Bad:

```text
3 small infra nodes run router + Prometheus + Loki + registry + Quay + pipelines.
```

Why bad:

- Resource contention.
- Network spikes.
- Disk pressure.
- Harder troubleshooting.

Better:

```text
Separate router/monitoring/logging/storage pools when scale requires it.
```

## 17. Interview-Level Explanation

If asked, “What is an infra node pool in OpenShift?” answer like this:

> An infra node pool is a dedicated set of worker-derived nodes used for OpenShift platform services such as ingress routers, registry, monitoring, and logging. We label those nodes with `node-role.kubernetes.io/infra`, usually keep the `worker` label, protect them with a `NoSchedule` taint, and configure operator-supported node placement so only intended infrastructure workloads run there. If the nodes need different OS or kubelet configuration, we create a custom infra MachineConfigPool that inherits worker configs and adds infra-specific MachineConfigs. In production, we deploy infra nodes across zones, validate storage and load balancer reachability, monitor capacity, and audit that user workloads are not scheduled there.

## 19. Step-by-Step Lab Scenario

This lab creates a basic infra pool from existing workers.

### Step 1: Select nodes

```bash
oc get nodes -o wide
```

Choose three workers:

```text
worker-0
worker-1
worker-2
```

### Step 2: Label nodes

```bash
oc label node worker-0 node-role.kubernetes.io/infra=""
oc label node worker-1 node-role.kubernetes.io/infra=""
oc label node worker-2 node-role.kubernetes.io/infra=""
```

### Step 3: Taint nodes

```bash
oc adm taint nodes worker-0 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint nodes worker-1 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint nodes worker-2 node-role.kubernetes.io/infra=reserved:NoSchedule
```

### Step 4: Create MCP

```bash
cat > infra-mcp.yaml <<'YAML'
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
YAML

oc apply -f infra-mcp.yaml
```

### Step 5: Move router

```bash
oc patch ingresscontroller default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"nodePlacement":{"nodeSelector":{"matchLabels":{"node-role.kubernetes.io/infra":""}},"tolerations":[{"key":"node-role.kubernetes.io/infra","value":"reserved","effect":"NoSchedule"}]}}}'
```

### Step 6: Verify

```bash
oc get nodes
oc get mcp
oc get pods -n openshift-ingress -o wide
```

Expected router node column should show one of:

```text
worker-0
worker-1
worker-2
```

and those nodes should show role:

```text
infra,worker
```

## 20. Troubleshooting Pending Pods: Decision Tree

```text
Pod Pending
│
├── Does nodeSelector match any infra node?
│   ├── No → Fix label or selector
│   └── Yes
│
├── Does pod tolerate infra taint?
│   ├── No → Add toleration through Operator CR
│   └── Yes
│
├── Are resources available on infra nodes?
│   ├── No → Scale infra pool or reduce requests
│   └── Yes
│
├── Is PVC bound and attachable to infra node zone?
│   ├── No → Fix StorageClass/topology/PV
│   └── Yes
│
├── Is MCP updating or node unschedulable?
│   ├── Yes → Wait/fix MCO/drain/cordon issue
│   └── No
│
└── Check events and operator status
```

Useful commands:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
oc describe node <node>
oc get co
oc get mcp
```

## 23. Golden Rules

1. **Infra label alone is not isolation.**
2. **Taint alone does not move workloads.**
3. **Toleration alone does not force placement.**
4. **Use Operator-supported placement fields, not direct patches to generated pods.**
5. **Keep `worker,infra` unless your MCP design is intentional.**
6. **Use at least three infra nodes for production HA where possible.**
7. **Check storage and load balancer reachability before moving registry, monitoring, logging, or routers.**
8. **Do not run user applications on infra nodes if you rely on infra-node subscription treatment.**
9. **Do not manually edit RHCOS host files outside MachineConfig unless troubleshooting under support guidance.**
10. **Audit infra nodes regularly.**
