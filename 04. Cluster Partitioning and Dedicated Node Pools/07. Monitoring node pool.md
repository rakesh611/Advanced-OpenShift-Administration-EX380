## 1. Purpose of a Monitoring Node Pool

A **Monitoring node pool** is a dedicated group of OpenShift worker nodes used mainly for monitoring and observability workloads such as:

- Prometheus
- Alertmanager
- Thanos Querier
- Thanos Ruler
- kube-state-metrics
- openshift-state-metrics
- Metrics Server
- monitoring web console plugin
- selected monitoring Operators or collectors, depending on design

The goal is to isolate monitoring workloads from normal application workloads so that monitoring remains available even when application nodes are under pressure.

In a production cluster, monitoring is not a small side component. Prometheus can be CPU-heavy, memory-heavy, disk-heavy, and network-heavy. It continuously scrapes metrics from cluster components, application endpoints, node exporters, API servers, kubelets, and custom ServiceMonitor or PodMonitor targets. If the monitoring stack runs on general application nodes, then noisy application workloads can directly affect observability.

A dedicated monitoring node pool helps with:

- Predictable monitoring performance
- Stable alerting during application incidents
- Isolation from application CPU and memory spikes
- Dedicated storage for Prometheus and Alertmanager
- Easier troubleshooting of monitoring-related resource pressure
- Controlled upgrades and maintenance windows for observability capacity
- Better capacity planning for large clusters
- Separation of platform workloads from business workloads

A senior administrator should treat monitoring as a **control-plane-adjacent operational workload**, not as an ordinary application. When applications fail, monitoring must still be able to tell you what failed.

## 2. Where Monitoring Fits in Cluster Partitioning

Cluster partitioning means dividing OpenShift nodes into logical pools based on workload type, ownership, hardware profile, security level, or operational function.

A common enterprise layout is:

```text
+------------------------------------------------------------+
|                    OpenShift Cluster                       |
+------------------------------------------------------------+
| Control Plane Nodes | etcd, API server, scheduler, CVO, etc |
+------------------------------------------------------------+
| Infra Node Pool     | router, registry, ingress, logging    |
+------------------------------------------------------------+
| Monitoring Pool     | Prometheus, Alertmanager, Thanos      |
+------------------------------------------------------------+
| Logging Pool        | log collectors, Loki/Elasticsearch     |
+------------------------------------------------------------+
| Storage Pool        | ODF/Ceph or storage-heavy workloads    |
+------------------------------------------------------------+
| App Worker Pool     | business/application workloads         |
+------------------------------------------------------------+
```

The Monitoring node pool is usually created as a custom worker-based pool. It is still made of worker nodes, but the nodes are labeled and optionally tainted so that only monitoring workloads can run there.

Important point: a monitoring node pool is a **scheduling and operational partition**, not a separate Kubernetes cluster. It shares the same API server, same scheduler, same SDN/OVN network, same authentication system, same Operators, and same upgrade flow.

## 3. OpenShift Monitoring Stack Architecture

OpenShift includes a built-in monitoring stack. In OpenShift 4.x, the monitoring stack is managed by the **Cluster Monitoring Operator**.

At a high level:

```text
Cluster Version Operator
        |
        v
Cluster Monitoring Operator
        |
        +--> Prometheus Operator
        |        |
        |        +--> Prometheus
        |        +--> Alertmanager
        |
        +--> Thanos Querier
        +--> kube-state-metrics
        +--> openshift-state-metrics
        +--> node-exporter
        +--> Metrics Server
        +--> Telemeter Client
        +--> monitoring-plugin
```

OpenShift monitoring is logically divided into two areas.

### 3.1 Core Platform Monitoring

Core platform monitoring is installed by default in:

```text
openshift-monitoring
```

It monitors platform components such as:

- API server
- etcd
- kubelets
- scheduler
- controller manager
- OpenShift API server
- OpenShift Controller Manager
- router / HAProxy
- image registry
- CoreDNS
- cluster Operators
- node-exporter metrics
- kube-state metrics
- OpenShift state metrics

Core platform monitoring is configured through:

```text
ConfigMap: cluster-monitoring-config
Namespace: openshift-monitoring
Key:       data.config.yaml
```

Example:

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

### 3.2 User Workload Monitoring

User workload monitoring is optional and runs in:

```text
openshift-user-workload-monitoring
```

It allows user-defined projects to be monitored through objects such as:

- ServiceMonitor
- PodMonitor
- PrometheusRule
- AlertmanagerConfig, depending on enabled features and version

User workload monitoring is configured through:

```text
ConfigMap: user-workload-monitoring-config
Namespace: openshift-user-workload-monitoring
Key:       data.config.yaml
```

Example:

```bash
oc -n openshift-user-workload-monitoring get configmap user-workload-monitoring-config
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

### 3.3 Important Component Difference

For core platform monitoring, the Prometheus config key is:

```yaml
prometheusK8s:
```

For user workload monitoring, the Prometheus config key is:

```yaml
prometheus:
```

This is a common mistake. Many admins copy the wrong key into the wrong ConfigMap and wonder why nothing changes.

## 4. Monitoring Node Pool vs Infra Node Pool vs Worker Node Pool

### 4.1 Worker Node Pool

The default worker pool runs general application workloads. Most user applications, CI/CD jobs, test pods, batch jobs, and developer workloads run here unless constrained otherwise.

Typical labels:

```text
node-role.kubernetes.io/worker=
```

### 4.2 Infra Node Pool

Infra nodes normally host platform infrastructure workloads such as:

- Ingress router
- internal image registry
- logging components
- some Operators
- selected platform services

Typical labels:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

Infra nodes are often tainted to prevent normal application workloads from landing there:

```bash
oc adm taint nodes <infra-node> node-role.kubernetes.io/infra=:NoSchedule
```

### 4.3 Monitoring Node Pool

Monitoring nodes are dedicated to observability workloads. They can be designed in two ways:

#### Option A: Dedicated monitoring worker nodes

Recommended for user workload monitoring and large clusters.

Typical labels:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/monitoring=
monitoring.openshift.io/pool=dedicated
```

Typical taint:

```text
monitoring.openshift.io/dedicated=true:NoSchedule
```

#### Option B: Shared infra + monitoring nodes

Useful for smaller clusters where a separate monitoring pool is too expensive.

Typical labels:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
monitoring.openshift.io/pool=infra-monitoring
```

This design saves hardware but reduces isolation. A router storm, registry issue, or logging spike can affect monitoring.

### 4.4 Important Rule for User Workload Monitoring

For user workload monitoring, do not blindly schedule user workload monitoring components onto control-plane or infrastructure nodes. Use worker-based dedicated monitoring nodes for user workload monitoring unless your OpenShift version and support policy explicitly allow another pattern.

A safe design is:

```text
Dedicated monitoring pool = worker nodes + monitoring labels + monitoring taint
```

Do not remove the worker role label unless you also understand the Machine Config Operator impact and have a custom MachineConfigPool that manages those nodes.

## 5. Core Concepts Required Before Implementation

A monitoring node pool uses multiple OpenShift and Kubernetes mechanisms together. A senior admin must understand how they compound.

### 5.1 Node Labels

Labels are key/value metadata on nodes. The scheduler uses labels to select target nodes.

Example:

```bash
oc label node worker-1 node-role.kubernetes.io/monitoring=
oc label node worker-1 monitoring.openshift.io/pool=dedicated
```

View labels:

```bash
oc get nodes --show-labels
oc get node worker-1 -o jsonpath='{.metadata.labels}' | jq
```

### 5.2 nodeSelector

A `nodeSelector` tells a pod or Operator-managed component: "Run only on nodes matching these labels."

Example:

```yaml
nodeSelector:
  node-role.kubernetes.io/monitoring: ""
```

If no matching node exists, the pod stays `Pending`.

If a matching node exists but has a taint that the pod cannot tolerate, the pod also stays `Pending`.

### 5.3 Taints

A taint repels pods from a node unless the pod has a matching toleration.

Example:

```bash
oc adm taint nodes worker-1 monitoring.openshift.io/dedicated=true:NoSchedule
```

Meaning:

```text
Do not schedule pods here unless they tolerate monitoring.openshift.io/dedicated=true:NoSchedule
```

### 5.4 Tolerations

A toleration allows a pod to schedule onto a tainted node.

Example:

```yaml
tolerations:
- key: monitoring.openshift.io/dedicated
  operator: Equal
  value: "true"
  effect: NoSchedule
```

Toleration does not force scheduling to the node. It only permits scheduling. You still need `nodeSelector` or affinity to attract the pod to the intended node pool.

### 5.5 MachineConfigPool

A MachineConfigPool controls how MachineConfig changes are applied to groups of nodes.

Default pools:

```text
master
worker
```

Custom pools:

```text
infra
monitoring
logging
storage
cnf
```

A custom MCP becomes important when:

- You want a separate reboot/update boundary.
- You apply custom kubelet or OS-level changes to monitoring nodes.
- You want a distinct node role for operational visibility.
- You want monitoring nodes to have dedicated machine configuration.

### 5.6 MachineSet / Machine API

In IPI clusters, MachineSets create and manage worker machines. For a cloud environment, a monitoring pool is usually created by making a new MachineSet with monitoring labels and taints.

For UPI or bare metal clusters, the same effect is achieved by adding labels and taints to existing nodes or by provisioning new hosts and joining them as workers.

### 5.7 Topology Spread Constraints

Monitoring has HA components. Prometheus, Alertmanager, Thanos Ruler, Thanos Querier, Metrics Server, and monitoring-plugin usually run with two replicas in multi-node clusters. You should ensure replicas spread across different nodes, zones, or racks.

If you force all monitoring pods into only one node, you break high availability.

## 6. Production Design Principles

### 6.1 Do Not Make Monitoring Compete with Applications

Application nodes can experience:

- CPU throttling
- memory pressure
- pod eviction
- disk pressure
- network saturation
- image pull storms
- batch job spikes
- CI/CD burst workloads

If Prometheus is on the same nodes, your alerts and dashboards may degrade during the exact incident you need them most.

### 6.2 Use at Least Two Monitoring Nodes

Prometheus and Alertmanager use HA replicas. A single monitoring node is not a production-grade design.

Minimum production design:

```text
2 monitoring nodes across different failure domains
```

Better design:

```text
3 monitoring nodes across 3 zones/racks
```

### 6.3 Keep the Worker Role Label

Do not remove:

```text
node-role.kubernetes.io/worker=
```

from monitoring nodes unless you understand MCO behavior and have created a custom MCP correctly. Many OpenShift components expect worker-based scheduling for compute nodes. A dual-label approach is safer:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/monitoring=
```

### 6.4 Use Both nodeSelector and Tolerations

A clean dedicated pool uses both:

- `nodeSelector` to attract monitoring pods to monitoring nodes
- `taint` to repel non-monitoring pods from monitoring nodes
- `toleration` to allow monitoring pods onto tainted monitoring nodes

Only labels without taints gives weak isolation.

Only taints without nodeSelector gives permission but not placement control.

### 6.5 Be Careful with node-exporter

`node-exporter` is a DaemonSet and collects metrics from every node. It is expected to run on every node. Do not treat node-exporter like Prometheus. If you taint monitoring, infra, or special nodes, ensure node-exporter can still run where required.

### 6.6 Use Persistent Storage for Stateful Monitoring Components

Prometheus, Alertmanager, and Thanos Ruler are stateful components. For HA and data preservation, configure persistent storage.

Without persistent storage, pod recreation can remove local metrics history. That might be acceptable in a lab, but not for production.

### 6.7 Never Edit Operator-Managed Deployments Directly

Do not manually edit:

```bash
oc edit deployment prometheus-operator -n openshift-monitoring
oc edit statefulset prometheus-k8s -n openshift-monitoring
oc edit deployment thanos-querier -n openshift-monitoring
```

Operator reconciliation will revert unsupported changes.

Use the supported ConfigMaps:

```text
cluster-monitoring-config
user-workload-monitoring-config
```

## 7. Sizing and Capacity Planning

Monitoring sizing depends on:

- Number of nodes
- Number of pods
- Number of namespaces
- Number of ServiceMonitor and PodMonitor objects
- Scrape interval
- Metrics cardinality
- Retention period
- Number of alerting and recording rules
- Remote write usage
- Query load from dashboards and APIs
- Persistent volume performance
- User workload monitoring enablement

### 7.1 Why Prometheus Needs Resources

Prometheus stores time-series data. Every unique metric name plus label combination creates a time series.

Example:

```text
http_requests_total{method="GET",status="200",pod="app-1"}
http_requests_total{method="POST",status="500",pod="app-2"}
```

These are separate series.

High-cardinality labels can explode the number of time series:

- request_id
- session_id
- customer_id
- user_id
- transaction_id
- pod UID
- dynamically generated path values

Large series count increases:

- memory usage
- WAL size
- disk I/O
- query latency
- compaction pressure
- CPU usage

### 7.2 Practical Starting Point

For a small-to-medium production cluster, start with at least:

```text
2 or 3 monitoring nodes
```

Each node should have:

```text
CPU:    enough reserved CPU for Prometheus query and scrape spikes
Memory: enough RAM for active series and query load
Disk:   fast persistent storage for Prometheus TSDB
Network: stable low-latency network to scrape cluster targets
```

Avoid under-sizing memory. Prometheus under memory pressure is a painful failure mode because queries slow down, scrapes fail, compaction struggles, and alerts can become unreliable.

### 7.3 Example Sizing Tiers

These are practical planning examples, not universal official numbers.

| Cluster Type | Monitoring Nodes | Typical Use Case |
|---|---:|---|
| Lab / demo | 0 dedicated or 1 dedicated | Learning, non-critical |
| Small production | 2 dedicated | Basic platform monitoring, limited user workload monitoring |
| Medium production | 3 dedicated | HA, user workload monitoring, moderate dashboards |
| Large enterprise | 3+ dedicated | Heavy user workload metrics, remote write, high retention |
| Regulated / critical | 3+ dedicated + remote storage | Auditability, longer retention, strict SLOs |

### 7.4 Storage Planning

Prometheus storage depends on:

```text
samples_per_second × bytes_per_sample × retention_time
```

Practical factors:

- scrape interval: 15s collects more data than 30s
- retention: 15d uses more storage than 24h
- number of targets: more pods means more targets
- cardinality: unbounded labels multiply series
- recording rules: generate additional series

Use `retention` and `retentionSize` together in production when possible:

```yaml
prometheusK8s:
  retention: 15d
  retentionSize: 100GB
```

This prevents Prometheus from filling storage indefinitely.

### 7.5 Disk Performance

Prefer storage with:

- low latency
- good random I/O
- stable write performance
- fast fsync behavior
- predictable performance under compaction

Avoid slow NFS-backed storage for high-scale Prometheus unless it is explicitly validated and supported for your environment. Prometheus TSDB is sensitive to latency and write performance.

## 8. Recommended Label and Taint Strategy

Use labels that clearly express both role and purpose.

### 8.1 Recommended Labels

```bash
oc label node <node> node-role.kubernetes.io/monitoring=
oc label node <node> monitoring.openshift.io/pool=dedicated
oc label node <node> workload.openshift.io/type=monitoring
```

Verify:

```bash
oc get nodes -l node-role.kubernetes.io/monitoring=
oc get nodes -l monitoring.openshift.io/pool=dedicated
```

### 8.2 Recommended Taint

```bash
oc adm taint node <node> monitoring.openshift.io/dedicated=true:NoSchedule
```

Verify:

```bash
oc describe node <node> | grep -i taints -A3
```

### 8.3 Why Not Use Only `node-role.kubernetes.io/infra`?

Using only the infra label for monitoring can be confusing. Infra nodes may also host routers, registry, logging, and other platform workloads. For dedicated monitoring, use a separate monitoring label.

You can combine labels if your design intentionally uses shared infra+monitoring nodes:

```text
node-role.kubernetes.io/infra=
node-role.kubernetes.io/monitoring=
```

But for clean production isolation, keep monitoring separate.

### 8.4 Labeling Existing Nodes

Example with three existing workers:

```bash
for n in worker-1 worker-2 worker-3; do
  oc label node $n node-role.kubernetes.io/monitoring= --overwrite
  oc label node $n monitoring.openshift.io/pool=dedicated --overwrite
  oc label node $n workload.openshift.io/type=monitoring --overwrite
  oc adm taint node $n monitoring.openshift.io/dedicated=true:NoSchedule --overwrite
done
```

Check:

```bash
oc get nodes -L node-role.kubernetes.io/worker,node-role.kubernetes.io/monitoring,monitoring.openshift.io/pool
```

## 9. Building the Monitoring Node Pool

There are two implementation approaches.

### 9.1 Approach 1: Label and Taint Existing Workers

Use this when:

- Cluster already has spare worker nodes
- You are in a lab
- You want quick Day-2 partitioning
- You are doing a migration from shared monitoring to dedicated monitoring

Steps:

```bash
oc get nodes

oc label node worker-1 node-role.kubernetes.io/monitoring=
oc label node worker-1 monitoring.openshift.io/pool=dedicated
oc adm taint node worker-1 monitoring.openshift.io/dedicated=true:NoSchedule
```

Repeat for at least two nodes.

### 9.2 Approach 2: Create a New MachineSet

Use this when:

- Running IPI on AWS, Azure, GCP, vSphere, OpenStack, etc.
- You want autoscaling or Machine API management
- You need specific instance type / disk / zone
- You want clean separation at provisioning time

General process:

```bash
oc get machinesets -n openshift-machine-api
oc get machines -n openshift-machine-api
```

Copy an existing worker MachineSet and modify:

- metadata.name
- spec.selector.matchLabels
- spec.template.metadata.labels
- spec.template.spec.metadata.labels
- providerSpec values such as instance type, zone, disk size
- taints if supported in the MachineSet spec

Example conceptual fields:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/worker: ""
          node-role.kubernetes.io/monitoring: ""
          monitoring.openshift.io/pool: dedicated
      taints:
      - key: monitoring.openshift.io/dedicated
        value: "true"
        effect: NoSchedule
```

The exact providerSpec varies by platform, so copy from an existing worker MachineSet and modify carefully.

### 9.3 Verification After MachineSet Creation

```bash
oc get machineset -n openshift-machine-api
oc get machines -n openshift-machine-api
oc get nodes -l node-role.kubernetes.io/monitoring=
oc describe node <new-monitoring-node>
```

Check labels and taints:

```bash
oc get node <node> --show-labels
oc describe node <node> | grep -i taints -A5
```

## 10. Creating a Custom MachineConfigPool for Monitoring Nodes

A custom MachineConfigPool is optional for simple scheduling partitioning, but recommended for mature production operations.

### 10.1 Why Create a Custom MCP?

Use a custom MCP when you want:

- Separate MCO update status for monitoring nodes
- Monitoring-specific kubelet settings
- Monitoring-specific OS tuning
- Controlled reboots for monitoring nodes
- Cleaner node role management
- Better operational visibility

### 10.2 Important MCP Design Warning

A custom MCP does not replace scheduling labels. It manages machine configuration. Scheduling still depends on labels, taints, tolerations, affinity, and node selectors.

Also, if a node has only a custom role and no worker role, ensure it is still selected by a valid MCP. A safer pattern is dual label:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/monitoring=
```

### 10.3 Example Custom MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: monitoring
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - monitoring
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/monitoring: ""
```

Apply:

```bash
cat <<'EOF_MCP' | oc apply -f -
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: monitoring
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - monitoring
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/monitoring: ""
EOF_MCP
```

Check:

```bash
oc get mcp
oc describe mcp monitoring
```

### 10.4 Example Monitoring-Specific KubeletConfig

Only use this if you have a clear reason. Incorrect kubelet tuning can destabilize nodes.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: monitoring-kubeletconfig
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/monitoring: ""
  kubeletConfig:
    maxPods: 250
```

Before applying, verify your MCP has the expected label:

```bash
oc get mcp monitoring --show-labels
```

### 10.5 Watching MCP Updates

```bash
oc get mcp monitoring -w
oc describe mcp monitoring
oc get nodes -l node-role.kubernetes.io/monitoring=
```

MCO changes can reboot nodes. Plan a maintenance window when modifying machine configuration.

## 11. Moving Core Platform Monitoring to the Monitoring Pool

Core platform monitoring is configured through:

```text
Namespace: openshift-monitoring
ConfigMap: cluster-monitoring-config
```

### 11.1 Create the ConfigMap if Missing

```bash
oc -n openshift-monitoring get configmap cluster-monitoring-config
```

If missing:

```bash
cat <<'EOF' | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
EOF
```

### 11.2 Minimal Core Monitoring Placement Example

This example moves important core monitoring components to the monitoring node pool.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      nodeSelector:
        node-role.kubernetes.io/monitoring: ""
      tolerations:
      - key: monitoring.openshift.io/dedicated
        operator: Equal
        value: "true"
        effect: NoSchedule

    alertmanagerMain:
      nodeSelector:
        node-role.kubernetes.io/monitoring: ""
      tolerations:
      - key: monitoring.openshift.io/dedicated
        operator: Equal
        value: "true"
        effect: NoSchedule

    thanosQuerier:
      nodeSelector:
        node-role.kubernetes.io/monitoring: ""
      tolerations:
      - key: monitoring.openshift.io/dedicated
        operator: Equal
        value: "true"
        effect: NoSchedule
```

Apply:

```bash
oc apply -f cluster-monitoring-config.yaml
```

Or edit directly:

```bash
oc -n openshift-monitoring edit configmap cluster-monitoring-config
```

## 13. Persistent Storage Strategy for Monitoring

### 13.1 Why Persistent Storage Matters

Without persistent storage:

- Prometheus loses local TSDB data when pods are recreated.
- Alertmanager can lose silence and notification state.
- Thanos Ruler can lose state depending on configuration.
- Troubleshooting historical incidents becomes harder.

### 13.2 Core Prometheus PVC Example

```yaml
prometheusK8s:
  volumeClaimTemplate:
    spec:
      storageClassName: fast-block
      resources:
        requests:
          storage: 200Gi
```

### 13.3 User Workload Prometheus PVC Example

```yaml
prometheus:
  volumeClaimTemplate:
    spec:
      storageClassName: fast-block
      resources:
        requests:
          storage: 200Gi
```

### 13.4 Alertmanager PVC Example

```yaml
alertmanagerMain:
  volumeClaimTemplate:
    spec:
      storageClassName: fast-block
      resources:
        requests:
          storage: 20Gi
```

### 13.5 StorageClass Considerations

Check available storage classes:

```bash
oc get sc
```

Important fields:

```bash
oc describe sc <storage-class-name>
```

Consider:

- `volumeBindingMode`
- `allowVolumeExpansion`
- storage backend performance
- zone-awareness
- RWO vs RWX requirements
- backup policy
- snapshot support

Prometheus typically uses RWO volumes per replica.

### 13.6 Volume Binding and Scheduling

If StorageClass uses:

```text
volumeBindingMode: WaitForFirstConsumer
```

then the PVC waits until the scheduler selects a node. This is good for zone-aware storage, but node selectors and taints must be correct. If no node can schedule the pod, the PVC may remain pending.

Troubleshoot:

```bash
oc get pvc -n openshift-monitoring
oc describe pvc <pvc> -n openshift-monitoring
oc describe pod prometheus-k8s-0 -n openshift-monitoring
```

## 14. High Availability and Failure Domain Design

### 14.1 Minimum HA Design

Prometheus runs in HA mode with two replicas in multi-node clusters. Alertmanager and Thanos components also use multiple replicas.

Minimum:

```text
2 monitoring nodes
```

Better:

```text
3 monitoring nodes
```

### 14.2 Zone-Aware Placement

For cloud or multi-rack environments, distribute monitoring nodes across zones:

```text
monitoring-az1
monitoring-az2
monitoring-az3
```

Check zone labels:

```bash
oc get nodes -L topology.kubernetes.io/zone
```

### 14.3 Anti-Affinity and Constraints

OpenShift monitoring components already include HA-oriented scheduling behavior for key components. Your node selectors and taints must not make that impossible.

Bad design:

```text
Only one node has node-role.kubernetes.io/monitoring=
Prometheus requires two replicas on separate nodes
Result: one pod running, one pod pending
```

Good design:

```text
At least two nodes match the monitoring selector
Both tolerate the monitoring taint
Storage is available in both zones
```

### 14.4 Disruption Planning

Before draining monitoring nodes:

```bash
oc get pods -n openshift-monitoring -o wide
oc get pdb -n openshift-monitoring
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

For planned maintenance, drain one monitoring node at a time.

## 15. Topology Spread Constraints

Topology spread constraints help distribute pods across zones, racks, or custom topology domains.

Example conceptual topology label:

```bash
oc label node worker-1 monitoring-zone=zone-a
oc label node worker-2 monitoring-zone=zone-b
oc label node worker-3 monitoring-zone=zone-c
```

Example for user workload Thanos Ruler:

```yaml
thanosRuler:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: monitoring-zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app.kubernetes.io/name: thanos-ruler
```

Use topology spread constraints when:

- you have multiple zones/racks
- you need controlled HA placement
- anti-affinity alone is not enough
- you want predictable cross-failure-domain spread

Do not over-constrain. If nodeSelector, taints, storage topology, anti-affinity, and topology spread constraints cannot all be satisfied, pods remain pending.

## 18. Troubleshooting Monitoring Node Pool Issues

### 18.1 Pod Pending Because Node Selector Does Not Match

Symptoms:

```text
0/10 nodes are available: node(s) didn't match Pod's node affinity/selector
```

Check:

```bash
oc get nodes --show-labels | grep monitoring
oc describe pod <pod> -n openshift-monitoring
```

Fix:

```bash
oc label node <node> node-role.kubernetes.io/monitoring= --overwrite
```

### 18.2 Pod Pending Because Taint Is Not Tolerated

Symptoms:

```text
0/10 nodes are available: node(s) had untolerated taint {monitoring.openshift.io/dedicated: true}
```

Check node taint:

```bash
oc describe node <node> | grep -i taints -A5
```

Fix ConfigMap toleration:

```yaml
tolerations:
- key: monitoring.openshift.io/dedicated
  operator: Equal
  value: "true"
  effect: NoSchedule
```

### 18.3 Only One Prometheus Pod Running

Likely causes:

- only one matching monitoring node
- anti-affinity prevents both replicas on same node
- second node missing label
- storage unavailable in second zone
- node resource shortage

Commands:

```bash
oc get pods -n openshift-monitoring -o wide | grep prometheus
oc describe pod prometheus-k8s-1 -n openshift-monitoring
oc get nodes -l node-role.kubernetes.io/monitoring=
oc get pvc -n openshift-monitoring
```

### 18.4 PVC Pending

Symptoms:

```text
pod has unbound immediate PersistentVolumeClaims
```

Check:

```bash
oc get pvc -n openshift-monitoring
oc describe pvc <pvc> -n openshift-monitoring
oc get sc
oc describe sc <storage-class>
```

Common reasons:

- StorageClass typo
- no dynamic provisioner
- zone mismatch
- insufficient backend capacity
- WaitForFirstConsumer blocked by scheduling constraints

### 18.5 Monitoring Operator Degraded

Check:

```bash
oc get co monitoring
oc describe co monitoring
oc logs -n openshift-monitoring deploy/cluster-monitoring-operator --tail=200
```

Also check events:

```bash
oc get events -n openshift-monitoring --sort-by=.lastTimestamp | tail -100
```

### 18.6 ConfigMap Syntax Error

YAML indentation errors are common.

Check current ConfigMap:

```bash
oc -n openshift-monitoring get cm cluster-monitoring-config -o yaml
```

Validate locally before applying:

```bash
yq e '.data."config.yaml"' cluster-monitoring-config.yaml
```

Common mistake:

```yaml
config.yaml: |
prometheusK8s:
```

Correct:

```yaml
config.yaml: |
  prometheusK8s:
```

### 18.7 Prometheus OOMKilled

Check:

```bash
oc get pod prometheus-k8s-0 -n openshift-monitoring -o yaml | grep -i oom -C3
oc describe pod prometheus-k8s-0 -n openshift-monitoring
oc logs prometheus-k8s-0 -n openshift-monitoring -c prometheus --previous
```

Mitigation:

- increase memory request/limit
- reduce retention
- reduce scrape frequency
- fix high-cardinality metrics
- reduce unnecessary ServiceMonitor/PodMonitor targets
- use remote write for long-term storage

### 18.8 Prometheus Disk Full

Symptoms:

- pod crashloop
- WAL errors
- TSDB compaction failures
- target scraping failures

Check:

```bash
oc describe pod prometheus-k8s-0 -n openshift-monitoring
oc logs prometheus-k8s-0 -n openshift-monitoring -c prometheus --tail=200
oc get pvc -n openshift-monitoring
```

Mitigation:

```yaml
prometheusK8s:
  retention: 7d
  retentionSize: 80GB
```

Or expand PVC if StorageClass allows expansion.

### 18.9 Node Pressure on Monitoring Nodes

Check:

```bash
oc describe node <monitoring-node>
oc adm top node <monitoring-node>
oc adm top pods -A --sort-by=memory | head
oc adm top pods -A --sort-by=cpu | head
```

If non-monitoring pods are running on monitoring nodes, check taints:

```bash
oc get pods -A -o wide | grep <monitoring-node>
oc describe node <monitoring-node> | grep -i taints -A5
```

### 18.10 Misplaced Application Pods on Monitoring Nodes

Cause:

- monitoring nodes not tainted
- application tolerates broad taints
- project-level node selectors are too broad
- cluster default node selector includes monitoring nodes

Find pods:

```bash
oc get pods -A -o wide | grep <monitoring-node>
```

Fix:

```bash
oc adm taint node <node> monitoring.openshift.io/dedicated=true:NoSchedule --overwrite
```

Then evict or reschedule inappropriate pods carefully.

## 19. Common Production Mistakes

### Mistake 1: Creating Only One Monitoring Node

This breaks HA placement for replicated monitoring components.

### Mistake 2: Labeling Nodes but Forgetting Taints

Pods move to monitoring nodes, but application pods can still land there.

### Mistake 3: Tainting Nodes but Forgetting Tolerations

Monitoring pods remain pending.

### Mistake 4: Using the Wrong ConfigMap

Core monitoring uses:

```text
cluster-monitoring-config in openshift-monitoring
```

User workload monitoring uses:

```text
user-workload-monitoring-config in openshift-user-workload-monitoring
```

### Mistake 5: Using `prometheusK8s` in User Workload Config

Wrong:

```yaml
prometheusK8s:
```

Correct for user workload monitoring:

```yaml
prometheus:
```

### Mistake 6: Editing Operator-Managed StatefulSets

Operator reconciliation overwrites unsupported manual edits.

### Mistake 7: Forgetting Storage Topology

Prometheus pod may match a monitoring node in zone A, but PVC may bind to zone B.

### Mistake 8: Over-Constraining Scheduling

Combining too many hard constraints creates pending pods:

```text
nodeSelector + taints + anti-affinity + topology spread + storage topology
```

### Mistake 9: Treating nodeExporter Like Prometheus

nodeExporter must run on every node to collect node-level metrics.

### Mistake 10: Not Monitoring the Monitoring Nodes

Dedicated monitoring nodes also need monitoring. Watch:

- CPU
- memory
- disk pressure
- filesystem usage
- kubelet health
- network latency
- pod restarts
- PVC usage

## 20. Real-World Implementation Scenarios

### 20.1 Small Cluster

Cluster:

```text
3 control-plane nodes
3 worker nodes
```

Recommended:

- Do not create a separate monitoring pool if hardware is limited.
- Use infra nodes only if available.
- Configure persistent storage and resource requests.
- Avoid heavy user workload monitoring.

### 20.2 Medium Enterprise Cluster

Cluster:

```text
3 control-plane nodes
3 infra nodes
3 monitoring nodes
10+ application workers
```

Recommended:

- Dedicated monitoring worker pool
- Dedicated storage class for Prometheus
- Taints and tolerations
- User workload monitoring enabled
- Retention and retentionSize configured
- Topology spread across zones/racks

### 20.3 Large Multi-Team Cluster

Cluster:

```text
3 control-plane nodes
3 infra nodes
3 logging nodes
3 monitoring nodes
30+ app workers
```

Recommended:

- Separate monitoring pool
- Separate logging pool
- Enforce ServiceMonitor governance
- Control high-cardinality metrics
- Use remote write or long-term storage if required
- Define alert ownership model
- Use monitoring RBAC roles
- Review scrape intervals and sample limits

### 20.4 Regulated Environment

Additional controls:

- Longer retention in compliant external system
- Strict RBAC for metrics access
- Alert routing approvals
- Audit of changes to monitoring ConfigMaps
- Backup or snapshot strategy for monitoring storage where appropriate
- Change control for MCP and monitoring pool modifications

## 21. Security and RBAC Considerations

### 21.1 Who Can Change Monitoring Placement?

Core platform monitoring changes usually require cluster-admin.

User workload monitoring can be delegated with appropriate monitoring roles, but placement and infrastructure-level decisions should remain with platform administrators.

### 21.2 Protect Monitoring ConfigMaps

These ConfigMaps affect cluster observability:

```text
openshift-monitoring/cluster-monitoring-config
openshift-user-workload-monitoring/user-workload-monitoring-config
```

Changes can:

- restart monitoring pods
- move pods to different nodes
- change retention
- change resource limits
- affect alerting
- break user workload monitoring

Use GitOps or controlled change process.

### 21.3 Namespace Isolation

Application teams should not have admin access to:

```text
openshift-monitoring
openshift-user-workload-monitoring
```

They should manage monitoring through supported project-level resources such as ServiceMonitor, PodMonitor, and PrometheusRule, depending on cluster policy.

### 21.4 Metrics Data Sensitivity

Metrics can expose sensitive metadata such as:

- namespace names
- pod names
- route names
- service names
- error codes
- endpoint paths
- tenant labels

Use RBAC carefully for query access.

## 24. Interview and Exam-Style Questions

### Q1. What is a Monitoring node pool?

A dedicated set of OpenShift worker nodes used to run monitoring components such as Prometheus, Alertmanager, Thanos, kube-state-metrics, and related observability services. It is created using node labels, taints, tolerations, and optionally a custom MachineConfigPool or MachineSet.

### Q2. Why do we need a dedicated monitoring pool?

To isolate monitoring from application workloads so monitoring remains stable during CPU, memory, disk, or network pressure on application nodes. It improves reliability, capacity planning, and operational visibility.

### Q3. What is the difference between nodeSelector and toleration?

`nodeSelector` attracts or restricts a pod to nodes with matching labels. A toleration allows a pod to run on a node with a matching taint. Toleration alone does not force scheduling.

### Q4. Which ConfigMap controls core platform monitoring placement?

```text
openshift-monitoring/cluster-monitoring-config
```

### Q5. Which ConfigMap controls user workload monitoring placement?

```text
openshift-user-workload-monitoring/user-workload-monitoring-config
```

### Q6. What is the key name for core Prometheus?

```yaml
prometheusK8s:
```

### Q7. What is the key name for user workload Prometheus?

```yaml
prometheus:
```

### Q8. Why should monitoring nodes keep the worker label?

Because they are compute nodes and the default worker MCP can manage them unless a custom MCP is configured. Removing the worker label without a valid custom MCP can create MCO management problems.

### Q9. Should node-exporter be moved only to monitoring nodes?

No. node-exporter is designed to run on every node to collect node-level metrics.

### Q10. Why might Prometheus stay Pending after nodeSelector configuration?

Common causes:

- no node matches the selector
- node has an untolerated taint
- PVC is pending
- storage zone conflicts
- insufficient CPU or memory
- anti-affinity cannot be satisfied

### Q11. What is the minimum number of monitoring nodes for HA?

At least two. Three is better when you have three zones or racks.

### Q12. What happens when you edit monitoring ConfigMaps?

The Cluster Monitoring Operator reconciles the changes. Affected monitoring pods might be redeployed automatically.

### Q13. Why is persistent storage important for Prometheus?

Prometheus is stateful. Persistent storage preserves metrics data across pod restarts and is important for HA and incident investigation.

### Q14. How do you prevent application pods from running on monitoring nodes?

Apply a taint to monitoring nodes:

```bash
oc adm taint node <node> monitoring.openshift.io/dedicated=true:NoSchedule
```

and only give matching tolerations to monitoring components.

### Q15. What is a custom MachineConfigPool used for?

It manages machine configuration for a custom group of nodes. It is useful for separate OS/kubelet tuning, update status, and operational control of monitoring nodes.

## Final Senior Admin Summary

A Monitoring node pool is not just a label on a few nodes. It is a production design decision. You must combine node labels, taints, tolerations, ConfigMap-based monitoring configuration, storage planning, high availability, and MachineConfigPool lifecycle management.

The best production pattern is:

```text
Dedicated worker-based monitoring nodes
+ monitoring role label
+ monitoring taint
+ monitoring component nodeSelectors
+ matching tolerations
+ persistent storage
+ at least two failure domains
+ controlled MCP/MachineSet lifecycle
```

When implemented properly, your observability layer remains healthy during application incidents, noisy workload spikes, and platform maintenance. That is the real value of a dedicated Monitoring node pool.
