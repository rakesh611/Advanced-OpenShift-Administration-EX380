# Custom Kubelet Configuration in OpenShift Dedicated Node Pools

**Topic:** Cluster Partitioning and Dedicated Node Pools  
**Level:** Advanced OpenShift Administration / 10+ years experience  
**Focus:** OpenShift 4.x, Machine Config Operator, MachineConfigPool, KubeletConfig, node pool tuning, production-safe rollout  
**Last updated:** 2026-07-03

---

## 1. Executive Summary

In OpenShift, **custom kubelet configuration** means changing selected kubelet behavior on a group of nodes by creating a `KubeletConfig` custom resource. You normally do this when a dedicated node pool needs different node-level behavior from the default worker pool.

Examples:

- Application worker pool needs higher pod density.
- Logging nodes need larger container log rotation limits.
- Infra nodes need controlled eviction thresholds.
- GPU or special workload nodes need PID limits and kubelet resource tuning.
- Performance-sensitive nodes need carefully reserved CPU or memory boundaries.

In OpenShift 4.x, you should not SSH into a node and directly edit kubelet configuration files. The supported operational model is:

```text
KubeletConfig CR
        |
        v
Machine Config Operator / kubelet-config-controller
        |
        v
Generated MachineConfig
        |
        v
Rendered MachineConfig for selected MachineConfigPool
        |
        v
Machine Config Daemon applies change on each node
        |
        v
Node drain / kubelet config update / reboot / return to service
```

The important point for advanced administration is that kubelet configuration is not only a kubelet topic. It is also an **MCO lifecycle topic**, a **node pool design topic**, a **capacity planning topic**, and a **risk management topic**.

---

## 2. What Is the Kubelet?

The **kubelet** is the node agent that runs on every OpenShift node. It talks to the Kubernetes API server and is responsible for making the node behave according to the desired state.

The kubelet handles tasks such as:

- Registering the node with the cluster.
- Starting, stopping, and monitoring pods.
- Reporting node status and resource capacity.
- Enforcing pod resource requests and limits with the container runtime and Linux cgroups.
- Performing liveness, readiness, and startup probe checks.
- Managing pod lifecycle events.
- Enforcing eviction behavior under memory, disk, inode, and PID pressure.
- Managing container logs and log rotation.
- Cooperating with CRI-O to run containers.
- Publishing allocatable resources such as CPU, memory, ephemeral storage, and maximum pods.

In OpenShift, the kubelet runs as a systemd-managed service on RHCOS nodes. Its configuration is generated and managed by OpenShift components, especially the **Machine Config Operator**.

## 3. Why Custom Kubelet Configuration Matters in Cluster Partitioning

Cluster partitioning means dividing nodes into logical pools for different classes of work. For example:

```text
Cluster
├── master/control-plane nodes
├── default worker nodes
├── infra nodes
├── logging nodes
├── monitoring nodes
├── storage nodes
├── GPU nodes
└── high-density application nodes
```

Each pool can have different requirements.

| Node pool | Typical kubelet tuning need |
|---|---|
| Default worker | Balanced defaults, minimal changes |
| Infra | Stable scheduling, predictable eviction, conservative pod density |
| Logging | Larger log rotation size, disk-pressure awareness |
| Monitoring | Memory and disk pressure tuning, stable eviction behavior |
| GPU | Lower pod density, stricter PID/resource limits |
| High-density app pool | Increased `maxPods`, tuned API QPS/burst |
| Performance pool | CPU Manager, reserved CPUs, Topology Manager, resource isolation |

Custom kubelet configuration gives you a way to align node behavior with workload type.

For a senior OpenShift administrator, the design question is not simply:

> How do I change `maxPods`?

The real question is:

> Which node pool needs different kubelet behavior, how will the MCO roll it out, what can break, how will I verify it, and how will I roll back safely?

## 4. Main OpenShift Objects Involved

### 4.1 `KubeletConfig`

A `KubeletConfig` is an OpenShift custom resource from the `machineconfiguration.openshift.io/v1` API group. It lets you define kubelet parameters for nodes selected through a MachineConfigPool label selector.

Example structure:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-kubelet-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: worker-kubelet-tuning
  kubeletConfig:
    maxPods: 250
    podPidsLimit: 8192
    containerLogMaxSize: 50Mi
```

### 4.2 `MachineConfigPool` / MCP

A `MachineConfigPool` groups nodes that receive the same rendered machine configuration.

Default pools normally include:

```bash
oc get mcp
```

Typical output:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-xxxxx                              True      False      False
worker    rendered-worker-yyyyy                              True      False      False
```

Custom pools can be created for special workloads:

```text
infra
logging
monitoring
gpu
app-highdensity
storage
```

A node can have many labels, but for MCO configuration it should effectively belong to one MCP. Poor MCP selector design can cause unexpected targeting or pool conflicts.

### 4.3 `MachineConfig`

A `MachineConfig` represents host-level changes. When you create a `KubeletConfig`, the MCO generates a kubelet-related `MachineConfig`, for example:

```bash
oc get mc | grep kubelet
```

Example:

```text
99-worker-generated-kubelet-1
```

You usually do not manually edit this generated MachineConfig. You manage the source `KubeletConfig` CR.

### 4.4 Machine Config Operator / MCO

The MCO manages node operating system and node-level configuration, including kubelet, CRI-O, systemd units, files, kernel arguments, and RHCOS updates.

Important MCO components:

| Component | Purpose |
|---|---|
| Machine Config Operator | Top-level operator managing machine configuration lifecycle |
| Machine Config Controller | Renders and coordinates machine configs |
| Kubelet config controller | Converts `KubeletConfig` into generated MachineConfig |
| Machine Config Daemon / MCD | Runs on each node and applies config changes |
| MachineConfigPool | Tracks desired/current config for a node group |

## 5. End-to-End Flow of a Custom Kubelet Change

```text
1. Admin labels an MCP.
2. Admin creates a KubeletConfig that selects that MCP label.
3. MCO validates and processes the KubeletConfig.
4. MCO generates a MachineConfig.
5. Render controller creates a new rendered config for the target MCP.
6. MCP moves to UPDATING=True.
7. MCD cordons/drains one or more nodes depending on maxUnavailable.
8. MCD applies kubelet configuration.
9. Node reboots if required.
10. Node returns Ready.
11. MCP reaches UPDATED=True, UPDATING=False, DEGRADED=False.
```

Senior admin mindset:

- Any kubelet tuning is a rollout event.
- Any rollout can affect workloads.
- PodDisruptionBudgets, daemonsets, static pods, local storage, and long-running workloads can influence drain behavior.
- You should always check MCP status after applying changes.

## 6. Why You Should Not Manually Edit Kubelet Files

Manual edits on OpenShift nodes are operationally dangerous because:

- They are not GitOps-friendly.
- They are not applied to new replacement nodes.
- They can create configuration drift.
- They can mark nodes or MCPs as degraded.
- They may be overwritten or made inconsistent by future machine config changes.
- They make troubleshooting harder because the cluster state no longer matches declarative configuration.

Correct approach:

```bash
oc apply -f kubeletconfig.yaml
```

Incorrect approach:

```bash
ssh core@node
sudo vi /etc/kubernetes/kubelet.conf
sudo systemctl restart kubelet
```

Use debug access for inspection, not for permanent manual changes:

```bash
oc debug node/<node-name>
chroot /host
systemctl status kubelet
```

## 7. Common Kubelet Parameters Used in OpenShift Tuning

Not every upstream kubelet parameter is appropriate for every OpenShift version or environment. The kubelet validates configuration values. Invalid values can cause nodes to become unavailable. Always test in a non-production pool first.

### 7.1 `maxPods`

Controls the maximum number of pods that can run on a node.

Example:

```yaml
kubeletConfig:
  maxPods: 250
```

Use cases:

- Increase pod density on high-capacity application nodes.
- Reduce pod density on GPU or latency-sensitive nodes.
- Keep infra nodes predictable.

Risks:

- More pods means more kubelet API calls.
- More pods means more iptables/nftables/OVN objects.
- More pods means more container logs.
- More pods means more CRI-O workload.
- More pods increases pressure on CPU, memory, ephemeral storage, and PID space.

Production guidance:

- Do not blindly set `maxPods: 500` just because OpenShift examples show it.
- Validate node size, CNI scale, API server load, workload pattern, and monitoring cardinality.
- If you increase pod density, consider `kubeAPIQPS` and `kubeAPIBurst`.

### 7.2 `podsPerCore`

Controls pod density based on CPU cores.

Example:

```yaml
kubeletConfig:
  podsPerCore: 10
  maxPods: 250
```

If both `podsPerCore` and `maxPods` are set, the effective pod limit is the lower result.

Example:

```text
Node CPU cores: 16
podsPerCore: 10
Calculated limit: 160 pods
maxPods: 250
Effective limit: 160 pods
```

Use cases:

- Avoid placing too many pods on smaller nodes.
- Keep pod density proportional to hardware capacity.

### 7.3 `podPidsLimit`

Controls the maximum number of process IDs allowed per pod.

Example:

```yaml
kubeletConfig:
  podPidsLimit: 8192
```

Use cases:

- Prevent fork-bomb behavior inside pods.
- Protect nodes from PID exhaustion.
- Tune for applications that legitimately use many processes.

Risks:

- Too low: Java, build tools, databases, and some monitoring agents can fail.
- Too high: one bad pod can consume excessive PID resources.

### 7.4 `containerLogMaxSize`

Controls the maximum size of a container log file before rotation.

Example:

```yaml
kubeletConfig:
  containerLogMaxSize: 50Mi
```

Use cases:

- Logging nodes or noisy apps that need larger local log files.
- Debug-heavy environments.

Risks:

- Larger log files consume more node filesystem space.
- Can increase disk pressure if workloads log aggressively.

### 7.5 `containerLogMaxFiles`

Controls the number of rotated log files retained per container.

Example:

```yaml
kubeletConfig:
  containerLogMaxFiles: 5
```

Total worst-case local log space per container is roughly:

```text
containerLogMaxSize × containerLogMaxFiles
```

For example:

```text
50Mi × 5 = 250Mi per container
```

This does not mean every container will use that much, but it is important for risk calculation.

### 7.6 `kubeAPIQPS` and `kubeAPIBurst`

These control kubelet client rate limits when talking to the API server.

Example:

```yaml
kubeletConfig:
  maxPods: 250
  kubeAPIQPS: 100
  kubeAPIBurst: 200
```

Use case:

- Higher pod density nodes may need higher kubelet API QPS and burst values.

Risk:

- Increasing these values on many nodes can increase API server load.
- Do not tune only the node side. Also watch API server metrics.

### 7.7 Eviction Settings

The kubelet evicts pods when node resources cross configured pressure thresholds.

Common resources:

- `memory.available`
- `nodefs.available`
- `nodefs.inodesFree`
- `imagefs.available`
- `imagefs.inodesFree`
- `pid.available`

Example:

```yaml
kubeletConfig:
  evictionHard:
    memory.available: "500Mi"
    nodefs.available: "10%"
    nodefs.inodesFree: "5%"
    imagefs.available: "15%"
```

Use cases:

- Protect nodes from becoming unstable.
- Tune disk pressure behavior for logging-heavy nodes.
- Avoid late evictions when memory pressure is already severe.

Risks:

- Too aggressive: unnecessary pod evictions.
- Too relaxed: node instability, kubelet failure, disk full conditions.
- Eviction behavior interacts with QoS classes: `Guaranteed`, `Burstable`, `BestEffort`.

### 7.8 Image Garbage Collection

Kubelet can garbage-collect unused images based on disk usage thresholds.

Example:

```yaml
kubeletConfig:
  imageGCHighThresholdPercent: 85
  imageGCLowThresholdPercent: 75
```

Use cases:

- Nodes with frequent image churn.
- CI/CD or build-heavy workloads.
- Edge clusters with limited disk.

Risks:

- Too aggressive: repeated image pulls, slower pod starts.
- Too relaxed: image filesystem pressure.

### 7.9 CPU Manager and Topology Manager

For performance-sensitive workloads, kubelet supports CPU and topology-aware placement features.

Example:

```yaml
kubeletConfig:
  cpuManagerPolicy: static
  cpuManagerReconcilePeriod: 5s
  topologyManagerPolicy: single-numa-node
```

Use cases:

- Low-latency network functions.
- Telco workloads.
- Workloads requiring exclusive CPUs.
- NUMA-sensitive applications.

Important production note:

For OpenShift performance-sensitive pools, also evaluate the OpenShift performance management stack, such as PerformanceProfile-based configuration where applicable. Do not casually enable CPU Manager or Topology Manager on general worker nodes.

## 8. Designing a Custom Node Pool for Kubelet Tuning

Before creating a `KubeletConfig`, design the target node pool properly.

### 8.1 Example: Infra Node Pool

Node labels:

```bash
oc label node <node1> node-role.kubernetes.io/infra=
oc label node <node2> node-role.kubernetes.io/infra=
oc label node <node3> node-role.kubernetes.io/infra=
```

MachineConfigPool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Important point:

For a custom MCP named `infra`, kubelet or container runtime machine configs that target the custom pool must use the matching custom role name where role selectors are involved.

### 8.2 Label the MCP for KubeletConfig Selection

A common safe pattern is to label the MCP with a dedicated selector label.

```bash
oc label mcp infra custom-kubelet=infra-kubelet-tuning
```

Verify:

```bash
oc get mcp infra --show-labels
```

### 8.3 Create a KubeletConfig for the Pool

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: infra-kubelet-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: infra-kubelet-tuning
  kubeletConfig:
    maxPods: 150
    podPidsLimit: 4096
    containerLogMaxSize: 20Mi
```

Apply:

```bash
oc apply -f infra-kubelet-tuning.yaml
```

Watch:

```bash
watch -n5 'oc get mcp infra'
```

## 9. Complete Lab: High-Density Application Node Pool

### 9.1 Requirement

Create a dedicated application node pool named `app-highdensity` with custom kubelet settings:

- Maximum pods per node: `250`
- Pod PID limit: `8192`
- Container log max size: `30Mi`
- Kubelet API QPS: `100`
- Kubelet API burst: `200`

### 9.2 Label Nodes

```bash
oc label node worker-1.example.com node-role.kubernetes.io/app-highdensity=
oc label node worker-2.example.com node-role.kubernetes.io/app-highdensity=
oc label node worker-3.example.com node-role.kubernetes.io/app-highdensity=
```

### 9.3 Create MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1

metadata:
  name: app-highdensity
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - app-highdensity
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/app-highdensity: ""

```

Apply:

```bash
oc apply -f mcp-app-highdensity.yaml
```

Verify:

```bash
oc get mcp app-highdensity
oc describe mcp app-highdensity
```

### 9.4 Label MCP

```bash
oc label mcp app-highdensity custom-kubelet=app-highdensity-kubelet
```

### 9.5 Create KubeletConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: app-highdensity-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: app-highdensity-kubelet

    maxPods: 250
    podPidsLimit: 8192
    containerLogMaxSize: 30Mi
    kubeAPIQPS: 100
    kubeAPIBurst: 200
```

Apply:

```bash
oc apply -f app-highdensity-kubelet.yaml
```

### 9.6 Watch Rollout

```bash
oc get mcp app-highdensity -w
```

In another terminal:

```bash
oc get nodes -l node-role.kubernetes.io/app-highdensity=
```

Check generated machine config:

```bash
oc get mc | grep kubelet
```

### 9.7 Verify on Node

```bash
oc describe node worker-1.example.com | grep -A20 Allocatable
```

Expected:

```text

```

Check kubelet config from node debug:

```bash

```

Actual file locations can vary by OpenShift version, but node debug inspection is useful for validation.

## 10. Complete Lab: Logging Node Pool

### 10.1 Requirement

Logging nodes handle log collectors, buffering, and log-heavy workloads. Tune them with:

- `containerLogMaxSize: 100Mi`
- `containerLogMaxFiles: 5`
- disk eviction thresholds suitable for local storage protection

### 10.2 MCP Label

```bash
oc label mcp logging custom-kubelet=logging-kubelet
```

### 10.3 KubeletConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: logging-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: logging-kubelet
  kubeletConfig:
    containerLogMaxSize: 100Mi
    containerLogMaxFiles: 5
    evictionHard:
      nodefs.available: "10%"
      nodefs.inodesFree: "5%"
      imagefs.available: "15%"
```

### 10.4 Capacity Warning

If a pod has two containers and each can use:

```text
100Mi × 5 = 500Mi
```

Then one pod can use roughly:

```text
2 × 500Mi = 1Gi local log retention
```

For 100 pods, worst-case local retained container logs could approach:

```text
100Gi
```

Real-world usage may be lower, but this calculation shows why container log settings must be aligned with node filesystem capacity and log shipping reliability.

## 11. Complete Lab: GPU Node Pool

GPU nodes often run fewer pods with heavier resource needs. The goal is usually not maximum density. It is stability and predictable resource behavior.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: gpu-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: gpu-kubelet
  kubeletConfig:
    maxPods: 50
    podPidsLimit: 8192
    containerLogMaxSize: 20Mi
```

Operational notes:

- Use taints and tolerations to keep normal workloads away from GPU nodes.
- Use node selectors or node affinity for GPU workloads.
- Keep `maxPods` conservative.
- Validate GPU Operator compatibility.
- Watch device plugin pods after MCO reboot.

Example taint:

```bash
oc adm taint nodes -l node-role.kubernetes.io/gpu= gpu=true:NoSchedule
```

## 12. Rollout Control and Maintenance Windows

KubeletConfig changes can trigger node drain and reboot. For production clusters, use a rollout plan.

### 12.1 Pre-Change Checklist

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pdb -A
oc get kubeletconfig
oc get mc | grep kubelet
```

Check the target pool:

```bash
oc describe mcp <pool-name>
```

Check degraded operators:

```bash
oc get co | grep -v 'True        False         False'
```

Check pod disruption risks:

```bash
oc get pdb -A
oc get pods -A --field-selector=status.phase!=Running
```

### 12.2 Use `maxUnavailable`

For most production custom pools:

```yaml
spec:
  maxUnavailable: 1
```

This means one node from that MCP should update at a time.

For a large pool, you might use a percentage, but only after understanding workload redundancy.

### 12.3 Pause and Unpause MCP

You can pause a pool before preparing multiple changes:

```bash
oc patch mcp <pool-name> --type=merge -p '{"spec":{"paused":true}}'
```

Apply your changes:

```bash
oc apply -f kubeletconfig.yaml
```

Unpause during the maintenance window:

```bash
oc patch mcp <pool-name> --type=merge -p '{"spec":{"paused":false}}'
```

Watch:

```bash
oc get mcp <pool-name> -w
```

Important:

- Pausing delays application of rendered config to nodes.
- Do not forget to unpause.
- Do not pile up unreviewed config changes.

## 13. Editing vs Creating Multiple KubeletConfig CRs

Recommended pattern:

- Use **one `KubeletConfig` per MCP** containing all intended kubelet changes for that pool.
- Edit the existing CR when adding or modifying settings.
- Create another CR only for another MCP or temporary testing.

Bad pattern:

```text
worker-maxpods
worker-pids
worker-logs
worker-eviction
worker-apiqps
```

Better pattern:

```text
worker-kubelet-tuning
```

Why?

- Easier rollback.
- Fewer generated MachineConfigs.
- Lower risk of hitting generated kubelet MachineConfig limits.
- Cleaner troubleshooting.
- Better GitOps review.

## 14. Rollback Strategy

### 14.1 View Existing KubeletConfig

```bash
oc get kubeletconfig

```

### 14.2 Roll Back One Parameter

Edit the CR:

```bash
oc edit kubeletconfig <name>
```

Remove or change the problematic field.

Example:

```yaml
kubeletConfig:
  maxPods: 150
```

Apply through GitOps or CLI:

```bash
oc apply -f kubeletconfig.yaml
```

### 14.3 Delete KubeletConfig

If you want to remove the entire custom kubelet configuration:

```bash
oc delete kubeletconfig <name>
```

Then monitor:

```bash
oc get mcp <pool-name> -w
```

### 14.4 Deleting Generated MachineConfigs

Do not start by deleting generated MachineConfigs randomly. Manage the source CR first.

If cleanup is required, understand generated names and delete in reverse order when applicable.

Check:

```bash
oc get mc | grep kubelet
```

## 15. Troubleshooting Custom Kubelet Configuration

### 15.1 MCP Stuck in Updating

Check:

```bash
oc get mcp
oc describe mcp <pool-name>
oc get nodes
```

Look for:

- Node not Ready.
- Node cordoned.
- Drain blocked by PDB.
- MCD pod errors.
- Degraded MachineConfigPool condition.

Check MCD logs:

```bash
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=200
```

For a specific node, find the daemon pod:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node-name>
```

Then:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod-name> -c machine-config-daemon
```

### 15.2 MCP Degraded

Check:

```bash
oc describe mcp <pool-name>
oc get nodes
oc describe node <node-name>
```

Common reasons:

- Invalid kubelet configuration.
- Manual file changes causing drift.
- MCD failed to apply config.
- Node reboot failure.
- Drain failure.
- Disk or filesystem issue.

### 15.3 Invalid KubeletConfig

Symptoms:

- `KubeletConfig` condition not successful.
- Generated MachineConfig not created.
- MCP degraded after rollout.
- Kubelet fails to start.

Check:

```bash
oc get kubeletconfig <name> -o yaml
oc describe kubeletconfig <name>
```

Correct the bad value and reapply.

### 15.4 Kubelet Fails After Change

Debug node:

```bash
oc debug node/<node-name>
chroot /host
journalctl -u kubelet -b --no-pager | tail -200
systemctl status kubelet
```

Look for messages related to invalid config fields, type errors, invalid quantities, or unsupported values.

### 15.5 Configuration Drift

Configuration drift means the on-disk state of a node no longer matches the current MachineConfig.

Check:

```bash
oc describe mcp <pool-name>
oc describe node <node-name>
```

Debug:

```bash
oc debug node/<node-name>
chroot /host
journalctl -u machine-config-daemon --no-pager | tail -200
```

Avoid drift by never making permanent manual changes on nodes.

### 15.6 Drain Blocked

Check PDBs:

```bash
oc get pdb -A
```

Check pods on node:

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Common blockers:

- Strict PDB with `minAvailable` too high.
- Single replica app with PDB.
- Pods using local storage.
- Pods without safe eviction behavior.
- Long termination grace periods.

## 16. Important Production Design Rules

### Rule 1: Tune by Pool, Not by Individual Node

Do not tune kubelet differently node by node unless you have a very strong reason. Create a dedicated MCP and apply settings to the pool.

### Rule 2: Keep One KubeletConfig per Pool

This is the cleanest operational model.

### Rule 3: Test on a Small Custom Pool First

Before changing all workers:

```text
worker-test → worker-canary → worker-production
```

### Rule 4: Do Not Increase Pod Density Without Capacity Math

Increasing `maxPods` affects:

- API server load.
- SDN/OVN scale.
- CRI-O load.
- kubelet CPU/memory.
- Node filesystem usage.
- Monitoring metrics volume.
- Log volume.
- Troubleshooting complexity.

### Rule 5: Use Conservative Rollouts

For critical pools:

```yaml
maxUnavailable: 1
```

### Rule 6: Watch MCP and Cluster Operators

```bash
oc get mcp
oc get co
```

A kubelet tuning change is not complete until the MCP is updated and non-degraded.

### Rule 7: Use GitOps for Production

Store these resources in Git:

```text
machineconfigpool-infra.yaml
kubeletconfig-infra.yaml
machineconfigpool-logging.yaml
kubeletconfig-logging.yaml
```

Review every change through pull request.

### Rule 8: Never Tune Blindly During an Incident

During node pressure incidents, kubelet config changes may cause node reboots and make things worse. Use emergency actions first, such as scaling down noisy workloads, freeing disk, fixing log shipping, or cordoning affected nodes.

## 17. KubeletConfig and Dedicated Workload Pools

### 17.1 Infra Pool Example

Goal:

- Moderate pod density.
- Controlled PID limit.
- Smaller log retention.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: infra-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
```

## 18. Relationship with Scheduling Controls

KubeletConfig does not replace scheduling controls. You usually combine it with:

- Node labels.
- Node selectors.
- Taints and tolerations.
- Affinity and anti-affinity.
- Topology spread constraints.
- Resource requests and limits.
- Project-level node selectors.
- Cluster resource quotas.

Example design:

```text
1. Create infra MCP.
2. Label infra nodes.
3. Taint infra nodes.
4. Move routers/registry/monitoring as needed.
5. Apply infra KubeletConfig.
6. Verify MCP rollout.
7. Verify workload placement.
```

Kubelet tuning changes node behavior. Scheduling controls decide which workloads are allowed to land there.

## 20. Interview-Style Questions and Answers

### Q1. How do you customize kubelet settings in OpenShift?

Use a `KubeletConfig` custom resource. Select the target `MachineConfigPool` through `spec.machineConfigPoolSelector`. The Machine Config Operator generates the required MachineConfig and rolls it out to the selected nodes.

### Q2. Should you manually edit kubelet config on OpenShift nodes?

No. Permanent manual edits can cause drift and are not supported as a management model. Use declarative resources such as `KubeletConfig` and `MachineConfig`.

### Q3. What happens after creating a KubeletConfig?

The MCO generates a kubelet MachineConfig, creates a new rendered config for the MCP, and the MCD applies it to nodes. Nodes may be drained and rebooted.

### Q4. How many KubeletConfig CRs should you create?

Operationally, one per target MachineConfigPool is the cleanest practice. Put all kubelet changes for that pool in one CR unless you have a temporary or special reason.

### Q5. What is the risk of increasing `maxPods`?

It increases pressure on kubelet, CRI-O, API server, network plugin, logs, monitoring, and node resources. It must be combined with capacity planning and testing.

### Q6. How do you roll back a bad kubelet config?

Edit or delete the source `KubeletConfig`, then monitor MCP rollout. Do not randomly delete generated MachineConfigs first.

### Q7. Why is MCP status important?

MCP status tells you whether the desired rendered configuration has been applied successfully. `UPDATED=True`, `UPDATING=False`, and `DEGRADED=False` is the healthy end state.

### Q8. What causes MCP degraded after kubelet tuning?

Invalid kubelet config, node drain failure, MCD failure, node reboot issue, configuration drift, or filesystem/systemd problems.

### Q9. How do you target a custom pool?

Create a custom `MachineConfigPool`, label it, and use the same label in `KubeletConfig.spec.machineConfigPoolSelector.matchLabels`.

### Q10. What is the difference between KubeletConfig and ContainerRuntimeConfig?

`KubeletConfig` tunes kubelet behavior. `ContainerRuntimeConfig` tunes CRI-O runtime settings such as log level, overlay size, and default runtime.

## 21. Real-World Scenario: Increase Pod Density Safely

### Situation

The business wants to reduce infrastructure cost by running more pods per node.

### Bad Approach

```yaml
kubeletConfig:
  maxPods: 500
```

Applied directly to all workers without testing.

### Senior Admin Approach

1. Measure current pod density.

```bash
oc get pods -A -o wide | awk '{print $8}' | sort | uniq -c | sort -nr | head
```

2. Check node resource usage.

```bash
oc adm top nodes
```

3. Create a canary MCP with 1-2 nodes.
4. Apply a moderate value first, such as `maxPods: 150` or `200`.
5. Test workload scheduling and restart behavior.
6. Monitor kubelet CPU, memory, API server latency, OVN health, and CRI-O errors.
7. Gradually promote to more nodes.
8. Keep rollback ready.

## 22. Real-World Scenario: Logging Disk Pressure

### Symptoms

```text
NodeHasDiskPressure
Pods evicted
/var/log full
container logs growing quickly
```

### Investigation

```bash
oc describe node <node>
oc adm top nodes
oc debug node/<node>
chroot /host

journalctl -u kubelet -b --no-pager | grep -i eviction
```

### Possible Fixes

- Fix application logging behavior.
- Ensure log collectors are healthy.
- Reduce `containerLogMaxSize` or `containerLogMaxFiles`.
- Tune eviction thresholds.
- Increase node disk size.
- Separate logging-heavy workloads into a dedicated pool.

```yaml
    containerLogMaxSize: 20Mi
    containerLogMaxFiles: 3
    evictionHard:
      nodefs.available: "15%"
      imagefs.available: "20%"
```

## 23. Common Mistakes

### Mistake 1: Labeling Nodes but Not Creating an MCP

Node labels alone do not create a MachineConfigPool.

### Mistake 2: KubeletConfig Selector Does Not Match MCP Label

If this does not match:

```yaml
machineConfigPoolSelector:
  matchLabels:
    custom-kubelet: app
```

With this:

```bash
oc get mcp --show-labels
```

Then no pool is selected.

### Mistake 3: Creating Too Many KubeletConfig CRs

This creates unnecessary generated MachineConfigs and operational complexity.

### Mistake 4: Changing All Workers First

Always test in a canary/custom pool.

### Mistake 5: Ignoring PDBs

A kubelet change may need node drain. PDBs can block drain and leave MCP updating.

### Mistake 6: Increasing Logs Without Disk Planning

Large `containerLogMaxSize` and `containerLogMaxFiles` values can fill disks.

### Mistake 7: Tuning `maxPods` Without API Server Awareness

More pods per node can increase kubelet-to-API-server traffic.

## 28. Final Best Practices

- Use `KubeletConfig`, not manual node edits.
- Target a specific `MachineConfigPool`.
- Label MCPs clearly.
- Use one `KubeletConfig` per pool.
- Keep changes in Git.
- Test with a canary/custom pool first.
- Use conservative `maxUnavailable`.
- Expect node drain/reboot for many machine config changes.
- Monitor `oc get mcp` until completion.
- Validate with `oc describe node` and node debug only when needed.
- Avoid high pod density without API, network, log, and resource planning.
- Treat kubelet tuning as production platform engineering, not as a quick parameter change.
