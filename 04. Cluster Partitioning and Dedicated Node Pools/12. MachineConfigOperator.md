# MachineConfigOperator (MCO) in Cluster Partitioning and Dedicated Node Pools

**Audience:** Advanced OpenShift Administration / DO380-level administrators  
**Experience level:** Written for an administrator with ~10 years of Linux, Kubernetes, DevOps, and OpenShift operations experience  
**Scope:** OpenShift Container Platform 4.x, with emphasis on MachineConfigOperator, MachineConfigPool, custom node pools, cluster partitioning, rollout control, disruption management, and troubleshooting.

---

## 1. Executive Summary

The **MachineConfigOperator (MCO)** is the OpenShift component responsible for managing the operating system configuration of cluster nodes. In OpenShift 4.x, nodes are not treated like traditional hand-managed Linux servers. Instead, the operating system, kubelet, CRI-O, kernel arguments, systemd units, SSH keys, registry configuration, and many host-level settings are managed declaratively through OpenShift APIs.

In cluster partitioning and dedicated node pool design, the MCO is critical because it controls **which node groups receive which host-level configuration**. The MCO applies configuration through **MachineConfigPools (MCPs)**. By creating custom MCPs such as `infra`, `logging`, `monitoring`, `storage`, `gpu`, or `app-highmem`, administrators can apply different host-level settings to different groups of nodes while preserving OpenShift's automated lifecycle management.

A good senior OpenShift administrator must understand this difference:

- **Scheduling controls where pods run.**
  - Labels
  - Taints and tolerations
  - Node selectors
  - Affinity and anti-affinity
  - Topology spread constraints

- **MCO controls how the node OS is configured and updated.**
  - MachineConfig
  - MachineConfigPool
  - KubeletConfig
  - ContainerRuntimeConfig
  - Node disruption policy
  - Rendered machine configs
  - Node drain/reboot lifecycle
  - Configuration drift detection

For dedicated node pools, the MCO is not optional. Without a matching MCP for a custom node role, the node might still run workloads, but from an operating-system management perspective it can be incorrectly managed, over-managed as a generic worker, or in some bad designs become unmanaged.

## 2. Why MachineConfigOperator Matters in Cluster Partitioning

Cluster partitioning means dividing a cluster into logical or physical zones of responsibility. In OpenShift this often means using dedicated node pools for different workload classes:

| Node Pool | Typical Purpose | Why MCO Matters |
|---|---|---|
| `worker` | General application workloads | Baseline OS, kubelet, CRI-O, registry, kernel config |
| `infra` | Routers, registry, monitoring stack, logging stack, platform services | Different kubelet sizing, taints, infra role, sometimes different log/runtime policies |
| `logging` | Elasticsearch/OpenSearch/Loki/Vector/collector workloads | Disk, file descriptor, CRI-O log, kernel, and eviction tuning |
| `monitoring` | Prometheus, Alertmanager, Thanos, observability workloads | Large memory, pod density, log size, storage behavior |
| `storage` | OpenShift Data Foundation / Ceph / local storage | Kernel modules, huge disk I/O, node role consistency, storage-only isolation |
| `gpu` | GPU workloads | Driver/runtime preparation, NFD/GPU operator coordination, special kernel/runtime expectations |
| `app-dedicated` | Critical business apps | Controlled host changes, canary updates, workload isolation |
| `edge` | Remote/latency-sensitive nodes | Smaller batch updates, careful reboot windows, local hardware config |

The MCO lets you say:

> “This host-level configuration applies only to this class of nodes.”

That is the real power of MCP-based partitioning.

## 3. MCO Core Responsibilities

The MachineConfigOperator manages configuration and lifecycle for nodes running Red Hat Enterprise Linux CoreOS (RHCOS) and, in some supported scenarios, RHEL worker nodes. Its responsibilities include:

1. **Applying host-level configuration**
   - Files under `/etc`, `/var`, and other supported paths through Ignition-style configuration
   - Systemd units and drop-ins
   - Kernel arguments
   - SSH authorized keys
   - Registry configuration
   - Kubelet configuration
   - CRI-O/container runtime configuration
   - Some networking-related files and NetworkManager configuration

2. **Rendering desired configuration**
   - Multiple `MachineConfig` objects are merged into one rendered configuration per MCP.
   - Rendered configs are named like `rendered-worker-<hash>` or `rendered-infra-<hash>`.

3. **Rolling out node updates**
   - Cordon node
   - Drain pods
   - Apply files, units, OS image, or runtime changes
   - Reboot when required
   - Uncordon node

4. **Managing OS update integration**
   - MCO participates in OpenShift cluster upgrades by rolling new RHCOS content to nodes.

5. **Detecting configuration drift**
   - The Machine Config Daemon checks whether the node still matches the applied machine config.
   - If a managed file or systemd unit is manually changed, the node or MCP can become `Degraded`.

6. **Coordinating disruption**
   - MCP `maxUnavailable` controls how many nodes in a pool can be updated at one time.
   - Node disruption policies can reduce unnecessary reboot/drain behavior for selected changes.

## 4. MCO Architecture

The MCO runs in the namespace:

```bash
openshift-machine-config-operator
```

Common resources:

```bash
oc get clusteroperator machine-config
oc get pods -n openshift-machine-config-operator
oc get mcp
oc get mc
oc get kubeletconfig
oc get containerruntimeconfig
```

### 4.1 Main Components

| Component | Type | Responsibility |
|---|---|---|
| `machine-config-operator` | Operator/controller | Owns the MCO lifecycle and operand components |
| `machine-config-controller` | Controller | Watches MCPs, MachineConfigs, nodes, rendered configs; coordinates rollout |
| `machine-config-daemon` | DaemonSet | Runs on every managed node and applies the desired config |
| `machine-config-server` | DaemonSet/static bootstrap component | Serves Ignition configs to nodes during bootstrap/joining |
| Render controller | Controller logic | Combines MachineConfigs into rendered MachineConfigs |
| Kubelet config controller | Controller logic | Converts `KubeletConfig` CRs into generated MachineConfigs |
| Container runtime config controller | Controller logic | Converts `ContainerRuntimeConfig` CRs into generated MachineConfigs |
| Node status / MachineConfigNode tracking | Controller/CRD behavior | Tracks current, desired, and update phases per node |

### 4.2 Machine Config Daemon

The **Machine Config Daemon (MCD)** is the part that actually works on the node. It:

- Watches the desired rendered config assigned to the node.
- Compares current node state with desired state.
- Applies file changes.
- Applies systemd changes.
- Applies kernel argument changes.
- Handles OS pivot/update when needed.
- Coordinates kubelet and CRI-O configuration updates.
- Reboots the node when required.
- Reports success, degraded state, and update progress.

Check MCD pods:

```bash
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide
```

Follow logs for one daemon:

```bash
oc logs -n openshift-machine-config-operator <machine-config-daemon-pod> -c machine-config-daemon -f
```

## 5. Important MCO API Objects

### 5.1 MachineConfig

A `MachineConfig` is the declarative object that describes host-level configuration.

Example use cases:

- Add a file to `/etc`.
- Configure a systemd unit.
- Add kernel arguments.
- Configure registries.
- Set SSH keys.
- Prepare node-specific host settings.

Basic structure:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-custom-file
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/example.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,ZXhhbXBsZT10cnVlCg==
```

The important label is:

```yaml
machineconfiguration.openshift.io/role: <pool-role>
```

For example:

```yaml
machineconfiguration.openshift.io/role: worker
machineconfiguration.openshift.io/role: infra
machineconfiguration.openshift.io/role: storage
machineconfiguration.openshift.io/role: logging
```

### 5.2 MachineConfigPool

A `MachineConfigPool` defines two things:

1. **Which MachineConfigs are selected**
2. **Which nodes are managed by the pool**

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
  paused: false
```

This says:

- Select all MachineConfigs labeled `worker` and `infra`.
- Apply the rendered result to nodes labeled `node-role.kubernetes.io/infra=`.
- Update one node at a time.
- Do not pause updates.

### 5.3 Rendered MachineConfig

The MCO does not apply each MachineConfig separately. It merges selected MachineConfigs into a rendered MachineConfig.

Example:

```bash
oc get mc | grep rendered
```

Output example:

```text
rendered-worker-8f61bf839898a4487c3b5263a430e94a
rendered-master-1abc053eec29e6c945670f39d6dc8afa
rendered-infra-a92b9fd9e8f11223344556677889900
```

The node tracks:

- Current config
- Desired config
- Update progress

Check node annotations:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

### 5.4 KubeletConfig

Use `KubeletConfig` when you need to tune kubelet behavior per pool.

Common senior-admin use cases:

- `maxPods`
- `podsPerCore`
- `systemReserved`
- `kubeReserved`
- `evictionHard`
- `evictionSoft`
- `containerLogMaxSize`
- `containerLogMaxFiles`
- `podPidsLimit`

Example for an infra pool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: infra-kubelet-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/infra: ""
  kubeletConfig:
    maxPods: 250
    containerLogMaxSize: 50Mi
    containerLogMaxFiles: 5
    systemReserved:
      cpu: 1000m
      memory: 2Gi
```

Before this works, the MCP must have a matching label:

```bash
oc label mcp infra pools.operator.machineconfiguration.openshift.io/infra=""
```

### 5.5 ContainerRuntimeConfig

Use `ContainerRuntimeConfig` for CRI-O/container runtime settings.

Common use cases:

- Runtime log level
- Overlay storage size
- Default runtime selection
- PIDs limit or runtime-related behavior, depending on version support

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: ContainerRuntimeConfig
metadata:
  name: infra-runtime-tuning
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/infra: ""
  containerRuntimeConfig:
    logLevel: info
    overlaySize: 8G
```

### 5.6 MachineConfiguration

`MachineConfiguration` is an operator-level configuration object. It is used for features such as **node disruption policy**.

Example concept:

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
  namespace: openshift-machine-config-operator
spec:
  nodeDisruptionPolicy:
    files:
    - path: /etc/chrony.conf
      actions:
      - type: Restart
        restart:
          serviceName: chronyd.service
```

This can reduce disruption for specific changes where a full node reboot is unnecessary.

## 6. Default MCPs and Custom MCPs

Every standard OpenShift cluster has two default MCPs:

```bash
oc get mcp
```

Typical output:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx    True      False      False
worker    rendered-worker-yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy    True      False      False
```

### 6.1 `master` MCP

The `master` MCP manages control plane nodes.

Important rules:

- Do not create custom MCPs for control plane nodes.
- Do not experiment with control plane `maxUnavailable` in production.
- Do not use control plane nodes for custom workload partitioning unless you have a supported compact/SNO architecture.
- MCO updates to control plane nodes can directly affect API availability, etcd quorum, operators, and cluster health.

### 6.2 `worker` MCP

The `worker` MCP is the baseline for general compute nodes.

Important behavior:

- Custom worker-based MCPs inherit worker MachineConfigs.
- If you add a MachineConfig labeled `worker`, it also affects custom pools that include `worker` in `machineConfigSelector`.
- Therefore, be careful when applying broad `99-worker-*` MachineConfigs.

### 6.3 Custom MCPs

Custom MCPs are used for dedicated node pools.

Examples:

```bash
infra
logging
monitoring
storage
gpu
app-prod
app-lowlatency
edge
```

Custom MCPs for worker nodes normally include both `worker` and the custom role in `machineConfigSelector`:

```yaml
machineConfigSelector:
  matchExpressions:
  - key: machineconfiguration.openshift.io/role
    operator: In
    values:
    - worker
    - infra
```

This inheritance model is important:

- The custom pool receives baseline worker configuration.
- The custom pool also receives pool-specific configuration.
- Pool-specific MachineConfigs can override matching fields from worker configs in newer OpenShift versions.

## 7. Node Role Labels, MCP Membership, and Dedicated Pools

A node can have multiple labels, for example:

```bash
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

But from the MCO/MCP point of view, a node can be managed by only one MCP.

### 7.1 Example: Worker + Infra Dual Label

Label a node as infra:

```bash
oc label node worker-1.example.com node-role.kubernetes.io/infra=""
```

The node might now have:

```bash
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

If an `infra` MCP exists with a `nodeSelector` matching `node-role.kubernetes.io/infra`, the MCO manages the node using the `infra` MCP.

If no custom `infra` MCP exists, the node is still considered part of the worker MCP from the MCO perspective.

### 7.2 Bad Design: Removing Worker Label Without MCP

Do not do this casually:

```bash
oc label node worker-1.example.com node-role.kubernetes.io/worker-
oc label node worker-1.example.com node-role.kubernetes.io/infra=""
```

If no matching custom MCP exists, the MCO might not manage the node correctly.

Senior rule:

> For every custom node role that requires host-level lifecycle management, create a matching MCP.

## 8. MachineConfig Selection vs Node Selection

A MachineConfigPool has two selector concepts:

### 8.1 `machineConfigSelector`

Selects MachineConfigs.

Example:

```yaml
machineConfigSelector:
  matchExpressions:
  - key: machineconfiguration.openshift.io/role
    operator: In
    values:
    - worker
    - infra
```

Meaning:

> Build the desired rendered config from all MachineConfigs labeled `worker` or `infra`.

### 8.2 `nodeSelector`

Selects nodes.

Example:

```yaml
nodeSelector:
  matchLabels:
    node-role.kubernetes.io/infra: ""
```

Meaning:

> Apply the rendered config to nodes labeled as infra.

### 8.3 Common Mistake

Wrong assumption:

> “If I label a node `infra`, it automatically gets infra MachineConfig.”

Correct understanding:

> The node receives infra MachineConfig only when an MCP selects that node and selects infra MachineConfigs.

## 9. End-to-End Rollout Flow

When you create or modify a MachineConfig:

1. You create a `MachineConfig` object.
2. The MCO render controller detects it.
3. MCO determines which MCP selects it.
4. MCO generates a new rendered MachineConfig.
5. The MCP status changes to `UPDATING=True`.
6. Nodes in that MCP get a new desired config annotation.
7. MCD on each node notices the desired config is different from current config.
8. MCO/MCD perform the update sequence:
   - Cordon
   - Drain
   - Apply
   - Reboot if needed
   - Uncordon
9. Node reports updated.
10. MCP returns to `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`.

Check status:

```bash
oc get mcp
oc describe mcp infra
oc get nodes
oc get machineconfignodes
```

Detailed node config state:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

## 10. MCO and Node Draining

In most disruptive configuration changes, MCO does this:

```text
cordon -> drain -> apply -> reboot -> uncordon
```

### 10.1 Why Drain Happens

Drain is required because the node might reboot or restart critical services. Running workloads must be moved away safely.

During drain:

- Pods managed by Deployments, ReplicaSets, StatefulSets, DaemonSets, etc. are handled according to Kubernetes drain rules.
- Pods protected by PodDisruptionBudgets can block drain.
- Static pods are not drained like normal pods.
- Single-node OpenShift has special handling.

### 10.2 Typical Drain Blockers

| Blocker | Symptom | Fix |
|---|---|---|
| Strict PDB | MCO stuck draining | Relax PDB temporarily or scale replicas |
| Single replica app | Cannot evict safely | Add replicas or schedule maintenance |
| Local storage pod | Eviction blocked | Review storage design and eviction policy |
| Broken workload | Pod termination stuck | Fix finalizers, force delete only if safe |
| Node pressure | Drain slow or stuck | Free resources, repair node health |

Check drain-related MCO logs:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

Check pods on the node:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node>
```

## 11. `maxUnavailable` Strategy

`maxUnavailable` controls how many nodes in an MCP can be unavailable during rollout.

Example:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

For production:

- Keep `master` / control plane very conservative.
- Use `1` for infra, logging, storage, GPU, and critical app pools unless you have strong HA capacity.
- For large homogeneous worker pools, a percentage might be acceptable, but test carefully.

Example:

```yaml
spec:
  maxUnavailable: 1
```

or:

```yaml
spec:
  maxUnavailable: 10%
```

Senior recommendation:

> Dedicated pools usually exist because those nodes are important or special. Do not blindly increase `maxUnavailable` just to finish updates faster.

## 12. Pausing and Unpausing MCPs

Pausing an MCP prevents the MCO from applying new configuration to that pool.

Pause:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":true}}'
```

Unpause:

```bash
oc patch mcp infra --type=merge -p '{"spec":{"paused":false}}'
```

Check:

```bash
oc get mcp infra -o yaml | grep paused -A2
```

### 12.1 When Pausing Is Useful

- Canary rollout planning
- Maintenance window control
- Avoiding immediate reboot during business hours
- Staging a MachineConfig but applying later
- Temporarily protecting a dedicated pool during investigation

### 12.2 When Pausing Is Dangerous

Do not pause MCPs for long periods.

Reasons:

- Important node security updates will not apply.
- OS and kubelet updates can lag behind the cluster version.
- Automatically rotated certificates might not be pushed to nodes.
- Troubleshooting commands such as `oc debug`, `oc logs`, `oc exec`, and `oc attach` can be affected if kubelet-related certificates expire or drift.

Senior rule:

> Pause MCPs only for short, controlled windows and document why they are paused.

Useful audit command:

```bash
oc get mcp -o custom-columns=NAME:.metadata.name,PAUSED:.spec.paused,UPDATED:.status.conditions[?(@.type=="Updated")].status,UPDATING:.status.conditions[?(@.type=="Updating")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status
```

## 13. Creating a Dedicated Infra Node Pool with MCO

This is a common cluster partitioning task.

### 13.1 Label Nodes

```bash
oc label node worker-1.example.com node-role.kubernetes.io/infra=""
oc label node worker-2.example.com node-role.kubernetes.io/infra=""
oc label node worker-3.example.com node-role.kubernetes.io/infra=""
```

Keep the worker label unless your platform design specifically says otherwise.

### 13.2 Add Taint for Workload Isolation

```bash
oc adm taint node worker-1.example.com node-role.kubernetes.io/infra=:NoSchedule
oc adm taint node worker-2.example.com node-role.kubernetes.io/infra=:NoSchedule
oc adm taint node worker-3.example.com node-role.kubernetes.io/infra=:NoSchedule
```

This is scheduling isolation, not MCO isolation. MCO isolation comes from the MCP.

### 13.3 Create Infra MCP

`infra-mcp.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
  paused: false
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp infra
```

### 13.4 Add Infra-Specific MachineConfig

Example: add a simple managed marker file.

Generate base64:

```bash
echo 'pool=infra' | base64 -w0
```

`99-infra-marker.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-marker
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/node-pool
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,cG9vbD1pbmZyYQo=
```

Apply:

```bash
oc apply -f 99-infra-marker.yaml
```

Monitor:

```bash
watch -n5 'oc get mcp infra; oc get nodes -l node-role.kubernetes.io/infra='
```

Verify on node:

```bash
oc debug node/worker-1.example.com
chroot /host
cat /etc/node-pool
exit
exit
```

## 14. Dedicated Storage Node Pool Pattern

Storage nodes are special because they are I/O sensitive and often run stateful workloads such as ODF/Ceph, local storage, or database platforms.

### 14.1 Design Goals

- Isolate storage workloads from general apps.
- Avoid unnecessary host-level changes during peak I/O periods.
- Keep updates controlled with `maxUnavailable: 1`.
- Tune kubelet reservations and eviction thresholds carefully.
- Do not allow random workloads onto storage nodes.

### 14.2 Storage MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: storage
  labels:
    pools.operator.machineconfiguration.openshift.io/storage: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - storage
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/storage: ""
  maxUnavailable: 1
  paused: false
```

### 14.3 Storage Kubelet Tuning Example

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: storage-kubelet-reservation
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/storage: ""
  kubeletConfig:
    systemReserved:
      cpu: 2000m
      memory: 4Gi
    kubeReserved:
      cpu: 1000m
      memory: 2Gi
    evictionHard:
      memory.available: "500Mi"
      nodefs.available: "10%"
      imagefs.available: "15%"
```

Note: Values must be tested for your node size. Do not blindly copy reservations.

## 15. Dedicated Logging Node Pool Pattern

Logging nodes often have high disk throughput, CPU spikes from collectors/indexers, and large container logs.

### 15.1 Logging Pool Goals

- Isolate log aggregation workloads.
- Tune log file retention/size.
- Avoid pod density that starves logging components.
- Manage CRI-O and kubelet settings separately from general workers.

### 15.2 Logging MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: logging
  labels:
    pools.operator.machineconfiguration.openshift.io/logging: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - logging
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/logging: ""
  maxUnavailable: 1
```

### 15.3 Logging KubeletConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: logging-kubelet-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/logging: ""
  kubeletConfig:
    containerLogMaxSize: 100Mi
    containerLogMaxFiles: 10
    maxPods: 150
```

Be careful: increasing log size can increase node disk pressure. Combine this with proper filesystem monitoring and alerting.

## 16. Dedicated GPU Node Pool Pattern

GPU pools require coordination with:

- Node Feature Discovery Operator
- NVIDIA GPU Operator or vendor-specific operator
- Device plugin workloads
- Driver container lifecycle
- Kernel compatibility
- Runtime expectations

### 16.1 GPU MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: gpu
  labels:
    pools.operator.machineconfiguration.openshift.io/gpu: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - gpu
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/gpu: ""
  maxUnavailable: 1
```

### 16.2 GPU Admin Notes

- Do not install GPU drivers manually on RHCOS nodes.
- Prefer supported Operators.
- Avoid unmanaged RPM installation unless using supported image layering or documented vendor approach.
- Coordinate MCO reboots with driver/operator readiness.
- Treat GPU nodes as expensive and disruption-sensitive.

## 17. MachineConfig Naming and Ordering

MachineConfigs are processed in lexicographic order by name when rendered.

Common naming pattern:

```text
00-worker-base
01-worker-container-runtime
50-worker-custom
99-worker-final-override
99-infra-custom
99-storage-custom
```

Senior guidance:

- Use clear numeric prefixes.
- Use role names in the object name.
- Avoid many scattered `99-*` configs that are hard to reason about.
- Keep related changes together where possible.
- Use GitOps so the full desired state is visible.

Example names:

```text
99-infra-chrony
99-infra-kernel-args
99-storage-kubelet-reservation
99-logging-container-logs
99-gpu-runtime-prep
```

## 18. MachineConfig Inheritance and Override Behavior

Custom MCPs generally inherit worker MachineConfigs by including both roles:

```yaml
values:
- worker
- infra
```

This means a `worker` MachineConfig applies to:

- `worker` pool
- `infra` pool
- `storage` pool
- `logging` pool
- other custom worker-based pools

Therefore:

- Put universal settings in `worker` configs.
- Put pool-specific settings in custom-role configs.
- Avoid placing risky or specialized settings in `worker` unless all pools should inherit them.

Example mistake:

```yaml
metadata:
  name: 99-worker-hugepages
  labels:
    machineconfiguration.openshift.io/role: worker
```

If the cluster has `storage`, `logging`, and `gpu` custom pools inheriting worker config, they can all receive this hugepages setting unintentionally.

Better:

```yaml
metadata:
  name: 99-app-hugepages
  labels:
    machineconfiguration.openshift.io/role: app-hugepages
```

## 19. MCO and Cluster Upgrades

During OpenShift upgrades, MCO applies new node OS and configuration content. It rolls through MCPs according to each pool's status and `maxUnavailable`.

### 19.1 Upgrade Flow at Node Level

1. Cluster Version Operator applies new release payload.
2. MCO sees new OS/image/config content.
3. MCPs receive new rendered configs.
4. Nodes update pool by pool.
5. MCD applies new OS/config.
6. Node reboots.
7. Node returns Ready.
8. MCP marks updated.

### 19.2 Custom Pool Upgrade Considerations

Custom pools update independently and can update in parallel with worker/master pools. This can surprise administrators.

For critical pools:

- Review `maxUnavailable` before upgrade.
- Ensure PDBs are healthy.
- Ensure enough replicas exist outside each node.
- Avoid paused pools unless you have a documented maintenance plan.
- Do not keep different pools on different OpenShift versions for extended periods.

## 20. Canary Updates with Custom MCPs

Custom MCPs can be used for canary rollout patterns.

Example design:

```text
worker-canary: 2 nodes
worker: rest of worker fleet
infra: infra nodes
storage: storage nodes
```

Process:

1. Create a custom MCP for canary nodes.
2. Label two worker nodes for the canary MCP.
3. Pause the main worker MCP if needed.
4. Apply new MachineConfig or start upgrade.
5. Let canary nodes update first.
6. Validate applications and node health.
7. Unpause/update the rest.

Example canary MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-canary
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - worker-canary
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-canary: ""
  maxUnavailable: 1
```

Do not create custom MCPs for control plane canary testing. Control plane MCP customization is not supported in that way.

## 21. Node Disruption Policy

By default, many MachineConfig changes cause a node drain and reboot. Newer OpenShift versions support **node disruption policies** to reduce disruption for selected changes.

A node disruption policy defines what action the MCO should take when specific files, units, or SSH keys change.

Actions can include:

- `None`
- `Drain`
- `Reload`
- `Restart`
- `DaemonReload`
- Special internal behavior for selected registry config changes

Example: restart `chronyd` instead of rebooting the entire node for `/etc/chrony.conf` changes.

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
  namespace: openshift-machine-config-operator
spec:
  nodeDisruptionPolicy:
    files:
    - path: /etc/chrony.conf
      actions:
      - type: Restart
        restart:
          serviceName: chronyd.service
```

Senior warning:

> The MCO does not prove that your custom disruption policy is safe. You must understand the service and file behavior yourself.

Use node disruption policy for mature, well-tested changes only.

## 22. Configuration Drift Detection

Configuration drift happens when the on-disk node state does not match the current rendered MachineConfig.

Example drift causes:

- Admin manually edits a file managed by MachineConfig.
- Admin changes permissions of a managed file.
- Admin modifies a systemd unit managed by MCO.
- Emergency break-glass change is not converted back into declarative config.
- A troubleshooting script changes host config.

When drift is detected:

- Node can be marked `Degraded`.
- MCP can be marked `Degraded`.
- Node remains online, but cannot be updated safely.

Check:

```bash
oc get mcp
oc describe mcp <pool>
oc get nodes
oc describe node <node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon
```

### 22.1 Fixing Drift

Preferred fix:

1. Identify the changed file/unit.
2. Restore it to match MachineConfig.
3. Let MCD confirm the state.
4. Confirm MCP returns healthy.

Emergency option:

- Use the MCD force file approach only when you know the risk.
- Expect node reboot.
- Document the incident.

Senior rule:

> Never make permanent node changes manually. Convert them into MachineConfig, KubeletConfig, ContainerRuntimeConfig, or another supported OpenShift API.

## 23. Troubleshooting MCO and MCP Problems

### 23.1 First-Level Health Commands

```bash
oc get co machine-config
oc describe co machine-config
oc get mcp
oc describe mcp worker
oc describe mcp infra
oc get nodes
oc get pods -n openshift-machine-config-operator -o wide
```

### 23.2 Check MCP Status Fields

```bash
oc get mcp -o wide
```

Important columns:

| Field | Meaning |
|---|---|
| `UPDATED` | All nodes have current desired config |
| `UPDATING` | At least one node is moving to desired config |
| `DEGRADED` | One or more nodes/configs failed |
| `MACHINECOUNT` | Total nodes in pool |
| `READYMACHINECOUNT` | Ready nodes in pool |
| `UPDATEDMACHINECOUNT` | Nodes with current config |
| `DEGRADEDMACHINECOUNT` | Nodes degraded |

### 23.3 Check Node Current/Desired Config

```bash
for n in $(oc get nodes -o name); do
  echo "### $n"
  oc get $n -o jsonpath='current={.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}desired={.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}state={.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
  echo
 done
```

### 23.4 Find the MCD Pod for a Node

```bash
NODE=<node-name>
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon | grep "$NODE"
```

Logs:

```bash
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --tail=200
```

### 23.5 MCP Stuck Updating

Possible causes:

| Cause | Investigation | Fix |
|---|---|---|
| Drain blocked by PDB | `oc get pdb -A`, MCD logs | Adjust PDB or replicas |
| Node NotReady | `oc describe node`, kubelet logs | Repair node/kubelet/network/storage |
| MCD degraded | MCD logs | Fix failed config or drift |
| Reboot failed | Node console, MCD logs | Reboot manually only after checking safety |
| Bad MachineConfig | Review rendered config and source MCs | Remove/fix bad MC |
| Paused MCP | `oc get mcp -o yaml` | Unpause after review |
| Certificate or kubelet issue | `oc debug`, MCD/kubelet logs | Check cert rotation and node health |

### 23.6 Check Rendered Config Source

```bash
oc get mcp infra -o jsonpath='{.status.configuration.name}{"\n"}'
oc get mcp infra -o jsonpath='{.status.configuration.source[*].name}{"\n"}'
```

Inspect rendered MachineConfig:

```bash
oc get mc rendered-infra-<hash> -o yaml
```

### 23.7 Prune Old Rendered MachineConfigs

Rendered configs can accumulate. Use supported pruning:

```bash
oc adm prune renderedmachineconfigs --pool-name=worker
oc adm prune renderedmachineconfigs --pool-name=worker --count=2 --confirm
```

Do not delete active rendered MachineConfigs manually.

## 24. MCO vs Machine API vs Scheduler

These are often confused.

| Area | Main Objects | Purpose |
|---|---|---|
| Machine API | `MachineSet`, `Machine`, cloud provider objects | Create/delete/scale infrastructure machines |
| MCO | `MachineConfig`, `MachineConfigPool`, `KubeletConfig`, `ContainerRuntimeConfig` | Configure OS/runtime/kubelet and update nodes |
| Scheduler | Pod spec, node selectors, affinity, taints/tolerations | Decide where pods run |
| Cluster Autoscaler | `ClusterAutoscaler`, `MachineAutoscaler` | Add/remove nodes based on workload demand |

Example:

- Use **MachineSet** to create infra nodes with labels/taints persistently.
- Use **MCP** to manage infra node OS configuration.
- Use **scheduler controls** to place router/registry/monitoring pods on infra nodes.

Do not expect MCO to schedule pods. Do not expect taints to configure OS files.

## 25. Best Practices for Dedicated Node Pools

### 25.1 Create MCP for Every Long-Lived Custom Role

If a node role is permanent, create an MCP:

```text
infra -> infra MCP
storage -> storage MCP
logging -> logging MCP
gpu -> gpu MCP
monitoring -> monitoring MCP
```

### 25.2 Keep Worker Label Unless You Have a Strong Reason

Custom MCPs normally inherit worker configuration. Keeping the worker label helps maintain sane inheritance and platform expectations.

### 25.3 Use MachineSets for Persistent Labels and Taints

Manual node labels and taints can disappear when a machine is replaced. On cloud or Machine API-managed platforms, put labels and taints in the MachineSet template.

### 25.4 Use GitOps for MachineConfig

MachineConfig changes can reboot nodes. Treat them like production infrastructure changes:

- Pull request
- Review
- Maintenance window
- Rollback plan
- Observability
- Post-change validation

### 25.5 Test on Canary Pool

For risky changes:

1. Create canary pool.
2. Apply config to canary.
3. Validate node health and workload behavior.
4. Roll out to production pool.

### 25.6 Avoid Long-Lived Paused MCPs

Paused pools are useful for maintenance windows but dangerous as a permanent state.

### 25.7 Watch PDBs Before MCO Changes

MCO drain honors disruption constraints. Bad PDB design can block node updates.

```bash
oc get pdb -A
oc get pods -A -o wide --field-selector spec.nodeName=<node>
```

### 25.8 Avoid Manual SSH Changes

Manual fixes are sometimes needed in outages, but they must be converted to declarative configuration after the incident.

### 25.9 Use Node Disruption Policy Carefully

Reducing reboots is good. Incorrectly skipping necessary reboots is dangerous.

### 25.10 Keep Pool Sizes HA-Friendly

A pool with one node and `maxUnavailable: 1` means that one pool can go fully unavailable during update. For critical roles, use at least three nodes where possible.

### 26.1 Small Production Cluster

```text
3 master nodes
3 infra nodes
3 worker nodes
3 storage nodes
```

MCPs:

```text

worker
```

Recommended:

- Infra workloads tolerate infra taint.
- Storage workloads tolerate storage taint.
- Monitoring/ingress/registry shifted to infra nodes.
- ODF shifted to storage nodes.

### 26.2 Large Enterprise Cluster

```text
3 master nodes
6 infra nodes
6 monitoring nodes
6 logging nodes
9 storage nodes
50+ app worker nodes
4 GPU nodes
```

MCPs:

```text
master
worker
infra
monitoring
logging
storage
gpu
app-prod
app-nonprod
```

Recommended:

- Canary pool for worker updates.
- Separate rollout calendar for storage and GPU.
- GitOps-managed MachineConfigs.
- Alerting on MCP `Degraded` or `Updating` too long.
- Strict change management for `worker` MachineConfigs because custom pools inherit them.

## 28. Rollback Strategy

There is no casual “undo” button for a bad MachineConfig. The rollback strategy is usually:

1. Remove or correct the bad MachineConfig.
2. MCO renders a new desired config.
3. MCP rolls nodes to the corrected config.
4. Nodes might reboot again.

Example:

```bash
oc delete mc 99-infra-bad-config
oc get mcp infra -w
```

For KubeletConfig or ContainerRuntimeConfig:

```bash
oc delete kubeletconfig infra-kubelet-tuning
oc delete containerruntimeconfig infra-runtime-tuning
```

Important:

- Removing a label from an MCP selector is not always equivalent to reverting generated config.
- For generated configs, delete or edit the owning CR.
- Review rendered configs to confirm desired output.

## 29. Common Interview / Real-World Questions

### Q1. What is the difference between MachineConfig and MachineConfigPool?

`MachineConfig` defines host-level configuration. `MachineConfigPool` defines which MachineConfigs are rendered together and which nodes receive that rendered config.

### Q2. Can one node belong to multiple MCPs?

No. A node can have multiple labels, but it is managed by only one MCP.

### Q3. Why should custom MCPs include `worker` in `machineConfigSelector`?

Because custom worker-based MCPs normally inherit worker baseline configuration. Without worker inheritance, the pool can miss required baseline configuration and become unsupported or unhealthy.

### Q4. Does MCO schedule pods onto infra nodes?

No. MCO manages node configuration. Pod scheduling is controlled by labels, taints, tolerations, selectors, affinity, and scheduler policies.

### Q5. What happens after a MachineConfig change?

MCO renders a new config, updates node desired config, cordons/drains nodes as needed, applies changes, reboots when required, and uncordons nodes.

### Q6. What causes MCP degraded?

Common reasons include bad MachineConfig, failed drain, failed reboot, MCD failure, config drift, invalid kubelet/runtime settings, or node health problems.

### Q7. How do you safely update storage nodes?

Use a dedicated storage MCP, `maxUnavailable: 1`, healthy PDBs, maintenance windows, and validate ODF/Ceph health before and after each node update.

### Q8. Why is a paused MCP risky?

Because node updates, security fixes, OS changes, and automatically rotated certificates might not apply to that pool.

## 32. Practical Lab: Build and Validate an Infra MCP

### Task

Create a dedicated infra MachineConfigPool and apply a pool-specific MachineConfig.

### Steps

1. Label three worker nodes as infra:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=""
oc label node worker-2 node-role.kubernetes.io/infra=""
oc label node worker-3 node-role.kubernetes.io/infra=""
```

2. Create MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
  labels:
    pools.operator.machineconfiguration.openshift.io/infra: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

3. Apply:

```bash
oc apply -f infra-mcp.yaml
```

4. Create pool-specific MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-infra-node-marker
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/infra-node
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,dHJ1ZQo=
```

5. Apply:

```bash
oc apply -f 99-infra-node-marker.yaml
```

6. Monitor:

```bash
oc get mcp infra -w
```

7. Validate on node:

```bash
oc debug node/worker-1
chroot /host
cat /etc/infra-node
```

Expected output:

```text
true
```

8. Confirm MCP health:

```bash
oc get mcp infra
```

Expected:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
```

## 33. Key Takeaways

- The MCO is the OpenShift authority for node OS and host-level configuration.
- MCPs are the foundation of MCO-based cluster partitioning.
- Dedicated node pools need both scheduling isolation and MCO lifecycle management.
- A custom node role should normally have a matching custom MCP.
- Custom worker-based MCPs inherit worker MachineConfigs.
- MachineConfig changes often cause drain and reboot.
- `maxUnavailable` controls rollout concurrency.
- Paused MCPs are powerful but risky if left paused.
- Configuration drift is a serious production hygiene issue.
- Never hand-edit nodes as a permanent solution; use declarative OpenShift APIs.
- Treat MachineConfig changes like production infrastructure changes, not casual YAML changes.
