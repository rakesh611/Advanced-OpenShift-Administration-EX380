## 1. What Is a Special Workload Node Pool?

A **Special Workload Node Pool** is a dedicated group of OpenShift worker nodes reserved for workloads that have non-standard infrastructure, performance, security, licensing, or operational requirements.

It is not always a separate OpenShift API object called `SpecialWorkloadNodePool`. In most self-managed OpenShift clusters, you build this pattern using a combination of:

- Node labels
- Node taints
- Pod tolerations
- Pod `nodeSelector`
- Node affinity
- Pod anti-affinity
- Topology spread constraints
- MachineConfigPool
- MachineConfig
- KubeletConfig
- Tuned / PerformanceProfile
- Compute MachineSets or machine pools
- Operator-specific placement settings
- ResourceQuota and LimitRange
- Monitoring and alerting rules

A special workload pool is usually created when normal worker nodes are too generic for a workload.

Example:

```text
Normal worker pool:
  - Generic stateless applications
  - Standard CPU and memory
  - Default kernel and kubelet settings
  - Shared scheduling capacity

Special workload pool:
  - GPU / AI / ML workloads
  - Low-latency trading or telecom workloads
  - Database workloads needing local NVMe
  - Storage workloads needing high IOPS
  - Security-isolated regulated workloads
  - Network functions using SR-IOV / DPDK
  - High-memory analytics workloads
  - Licensed software bound to dedicated nodes
```

In production, this pool becomes a **controlled failure domain and scheduling domain**. You deliberately decide which pods are allowed to land there, which pods are excluded, how the operating system is configured, and how upgrades are rolled out.

## 2. Why Special Workload Pools Exist

Special workload node pools solve five major production problems.

### 2.1 Isolation

Some workloads must not share nodes with regular application pods.

Reasons include:

- Security compliance
- Noisy-neighbor prevention
- Licensing restrictions
- Hardware access control
- Data locality
- Dedicated performance reservation
- Regulatory boundaries
- Customer or tenant isolation

Example:

```text
AI workload using NVIDIA GPUs:
  Must run only on GPU nodes.
  Generic pods must not consume CPU/memory on GPU nodes.
  GPU device plugin and drivers must be installed only on GPU nodes.
```

### 2.2 Performance Predictability

Regular worker nodes are shared. A latency-sensitive workload may suffer if it lands near CPU-hungry, memory-hungry, or I/O-heavy pods.

Special workload pools allow:

- CPU pinning
- NUMA alignment
- Huge pages
- Real-time kernel
- Isolated CPUs
- Reserved CPUs for platform/system daemons
- Dedicated NICs
- Local SSD / NVMe
- Lower scheduling contention

### 2.3 Hardware Targeting

Some workloads require special hardware:

- GPU
- FPGA
- SmartNIC
- SR-IOV NIC
- High-memory nodes
- Bare-metal nodes
- Local NVMe
- Confidential-computing capable CPUs
- ARM nodes
- Specific CPU instruction sets

The scheduler must know which nodes have that hardware, and the cluster must prevent non-special pods from landing there.

### 2.4 Operational Separation

Special nodes often require different maintenance handling.

Examples:

- Drain one node at a time because GPU jobs are long-running.
- Pause a MachineConfigPool during a critical business window.
- Apply kernel arguments only to special nodes.
- Use separate monitoring dashboards.
- Use separate capacity alerts.
- Upgrade after generic workers are validated.

### 2.5 Cost and Licensing Control

Special nodes are often expensive.

Examples:

- GPU nodes can cost many times more than normal workers.
- Database nodes may use high-cost storage.
- Commercial software may be licensed by CPU socket, core, or host.
- Some workloads are allowed to run only on purchased-license nodes.

A special workload pool protects expensive capacity from accidental use.

## 3. How It Fits into Cluster Partitioning

Cluster partitioning means dividing one OpenShift cluster into logical and operational zones.

A typical advanced production cluster might look like this:

```text
Control Plane Nodes
  - API server
  - etcd
  - scheduler
  - controller manager

Infrastructure Node Pool
  - Ingress router
  - Registry
  - Monitoring
  - Logging
  - GitOps / Pipelines / ACM / ACS depending on design

Application Worker Pool
  - Standard application workloads

Special Workload Node Pool
  - GPU / AI / ML
  - Real-time / telco
  - Database / storage-heavy
  - Security-regulated workloads
  - High-memory analytics
  - Network functions
```

Important distinction:

| Pool Type | Main Purpose | Typical Workloads |
|---|---|---|
| Control plane | Cluster control services | API, etcd, controllers, scheduler |
| Infrastructure | Cluster-supporting services | Router, registry, monitoring, logging |
| Application | General business workloads | Microservices, web apps, APIs |
| Special workload | Non-standard workload requirements | GPU, low latency, database, SR-IOV, compliance |

A special workload node pool should not be created only because a team asks for “dedicated nodes.” It should be justified by a clear requirement:

- Hardware requirement
- Performance requirement
- Compliance requirement
- Licensing requirement
- Operational requirement
- Strong blast-radius requirement

Without a real requirement, you may create unnecessary fragmentation, reduce bin-packing efficiency, and increase operational burden.

## 5. Core OpenShift Building Blocks

A special workload pool is not one single feature. It is a design pattern built from multiple primitives.

### 5.1 Node Labels

Labels describe node characteristics.

Examples:

```bash
oc label node worker-gpu-1 node-role.kubernetes.io/special=
oc label node worker-gpu-1 workload.openshift.io/class=gpu
oc label node worker-gpu-1 hardware.openshift.io/accelerator=nvidia-a100
oc label node worker-gpu-1 topology.kubernetes.io/zone=zone-a
```

Labels answer:

```text
What is this node?
What role does it serve?
What hardware does it have?
Which workloads are allowed to select it?
```

### 5.2 Taints

Taints repel pods unless the pods explicitly tolerate them.

Example:

```bash
oc adm taint nodes worker-gpu-1 workload.openshift.io/special=gpu:NoSchedule
```

This means:

```text
Do not schedule pods on this node unless they tolerate workload.openshift.io/special=gpu:NoSchedule.
```

### 5.3 Tolerations

Tolerations allow a pod to be scheduled onto a tainted node.

Example:

```yaml
tolerations:
  - key: workload.openshift.io/special
    operator: Equal
    value: gpu
    effect: NoSchedule
```

Important: toleration does not force placement. It only permits placement. You still need a `nodeSelector` or node affinity if you want the workload to prefer or require the special nodes.

### 5.4 Node Selector

A `nodeSelector` requires a pod to run only on nodes with matching labels.

```yaml
nodeSelector:
  workload.openshift.io/class: gpu
```

Simple and effective, but less expressive than node affinity.

### 5.5 Node Affinity

Node affinity is more flexible than `nodeSelector`.

Example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: workload.openshift.io/class
              operator: In
              values:
                - gpu
            - key: hardware.openshift.io/accelerator
              operator: In
              values:
                - nvidia-a100
                - nvidia-h100
```

Use affinity when you need:

- Multiple acceptable values
- Required plus preferred rules
- Hardware generation selection
- Zone-aware decisions
- More advanced placement logic

### 5.6 Pod Anti-Affinity

Pod anti-affinity spreads pods apart.

Example use cases:

- Do not place two database replicas on the same node.
- Do not place two GPU inference replicas on the same host.
- Do not co-locate primary and secondary replicas.

### 5.7 Topology Spread Constraints

Topology spread constraints distribute pods across topology domains such as nodes, zones, or racks.

Example:

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: gpu-inference
```

Use this when availability matters and you do not want all replicas landing in one zone.

### 5.8 MachineConfigPool

A MachineConfigPool controls host-level configuration rollout for a selected group of nodes.

Use it when special nodes require different host configuration, such as:

- Kernel arguments
- Kubelet settings
- CRI-O settings
- Systemd units
- Files on the host
- Registries configuration
- OS-level tuning

### 5.9 MachineConfig

A MachineConfig defines OS-level changes applied by the Machine Config Operator.

Examples:

- Add kernel arguments
- Create files
- Configure systemd services
- Configure container runtime behavior

### 5.10 KubeletConfig

A KubeletConfig changes kubelet behavior for nodes selected through a MachineConfigPool selector.

Examples:

- `maxPods`
- CPU manager policy
- Topology manager policy
- Eviction thresholds
- Reserved resources

### 5.11 PerformanceProfile

Used for high-performance node tuning, especially low-latency and telco workloads.

It can configure:

- Reserved CPUs
- Isolated CPUs
- Huge pages
- Real-time kernel
- NUMA topology policy
- Workload hints

## 6. Reference Architecture

A mature special workload architecture separates three concerns:

1. **Node identity**
2. **Node exclusivity**
3. **Workload placement**

### 6.1 Node Identity

Use labels to describe special nodes.

```text
node-role.kubernetes.io/special=
workload.openshift.io/class=gpu
hardware.openshift.io/accelerator=nvidia-a100
```

### 6.2 Node Exclusivity

Use taints to keep general pods away.

```text
workload.openshift.io/special=gpu:NoSchedule
```

### 6.3 Workload Placement

Use tolerations plus node selector or affinity.

```text
Toleration says: I am allowed to run there.
Node selector says: I must run there.
```

A good mental model:

```text
Label = node property
Taint = node protection
Toleration = workload permission
NodeSelector / Affinity = workload targeting
MCP = OS configuration boundary
MachineSet = infrastructure provisioning boundary
Quota / LimitRange = tenant consumption boundary
Monitoring = operational visibility boundary
```

### 6.4 Example Target State

```text
special-gpu-pool
  Nodes:
    worker-gpu-a-1
    worker-gpu-b-1
    worker-gpu-c-1

  Labels:
    node-role.kubernetes.io/special=
    workload.openshift.io/class=gpu
    hardware.openshift.io/accelerator=nvidia-a100

  Taints:
    workload.openshift.io/special=gpu:NoSchedule

  MachineConfigPool:
    special-gpu

  Operators:
    Node Feature Discovery
    NVIDIA GPU Operator

  Allowed projects:
    ai-platform
    model-training
    model-serving

  Denied workloads:
    Generic microservices
    Unbounded batch jobs
    BestEffort pods
```

## 7. Labeling Strategy

Labeling is the foundation of a clean special workload pool.

### 7.1 Use Role Labels Carefully

OpenShift role labels commonly look like this:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
node-role.kubernetes.io/special=
node-role.kubernetes.io/gpu=
```

For a special pool, you may use either a generic `special` role or a more specific role such as `gpu`, `storage`, or `rt`.

Example:

```bash
oc label node worker-special-1 node-role.kubernetes.io/special=
```

Or:

```bash
oc label node worker-gpu-1 node-role.kubernetes.io/gpu=
```

### 7.2 Use Workload Class Labels

Role labels are useful for OpenShift node role grouping. Workload labels are better for scheduling policy.

Recommended:

```bash
oc label node worker-gpu-1 workload.openshift.io/class=gpu
oc label node worker-rt-1 workload.openshift.io/class=realtime
oc label node worker-db-1 workload.openshift.io/class=database
```

### 7.3 Use Hardware Labels

For hardware-specific scheduling:

```bash
oc label node worker-gpu-1 hardware.openshift.io/accelerator=nvidia-a100
oc label node worker-db-1 hardware.openshift.io/storage=local-nvme
oc label node worker-net-1 hardware.openshift.io/sriov=true
oc label node worker-mem-1 hardware.openshift.io/memory-profile=highmem
```

### 7.4 Use Topology Labels

OpenShift and Kubernetes often populate well-known topology labels automatically, depending on platform:

```text
topology.kubernetes.io/zone
topology.kubernetes.io/region
kubernetes.io/hostname
```

For bare metal, you may add additional labels:

```bash
oc label node worker-special-1 topology.example.com/rack=rack-01
oc label node worker-special-2 topology.example.com/rack=rack-02
```

### 7.5 Avoid Ambiguous Labels

Avoid labels like:

```text
type=fast
role=special
team=team1
```

Better:

```text
workload.openshift.io/class=gpu
hardware.openshift.io/accelerator=nvidia-a100
ownership.example.com/cost-center=ai-platform
```

### 7.6 Recommended Label Set

For a GPU special pool:

```bash
oc label node worker-gpu-1 \
  node-role.kubernetes.io/gpu= \
  workload.openshift.io/class=gpu \
  hardware.openshift.io/accelerator=nvidia-a100 \
  workload.openshift.io/dedicated=ai-platform
```

For a database special pool:

```bash
oc label node worker-db-1 \
  node-role.kubernetes.io/database= \
  workload.openshift.io/class=database \
  hardware.openshift.io/storage=local-nvme \
  workload.openshift.io/dedicated=data-platform
```

For a real-time special pool:

```bash
oc label node worker-rt-1 \
  node-role.kubernetes.io/realtime= \
  workload.openshift.io/class=realtime \
  hardware.openshift.io/sriov=true \
  workload.openshift.io/latency=low
```

## 8. Taints and Tolerations Strategy

Labels alone do not protect special nodes. If a generic pod has no node selector, the scheduler may place it on any schedulable worker that has enough resources.

To protect expensive or sensitive nodes, use taints.

### 8.1 Basic Special Pool Taint

```bash
oc adm taint nodes -l workload.openshift.io/class=gpu \
  workload.openshift.io/special=gpu:NoSchedule
```

Meaning:

```text
Only pods with a matching toleration can be scheduled here.
Existing pods remain because NoSchedule affects new scheduling only.
```

### 8.2 NoSchedule vs NoExecute

| Effect | Behavior | Use Case |
|---|---|---|
| `NoSchedule` | New pods without toleration cannot schedule | Most common dedicated pool protection |
| `PreferNoSchedule` | Scheduler tries to avoid the node | Soft preference, weak isolation |
| `NoExecute` | New pods blocked and existing non-tolerating pods evicted | Strong isolation, migration, emergency removal |

For most special pools, start with `NoSchedule`.

Use `NoExecute` carefully because it can evict existing pods.

### 8.3 Toleration for Special Workload

```yaml
tolerations:
  - key: workload.openshift.io/special
    operator: Equal
    value: gpu
    effect: NoSchedule
```

### 8.4 Toleration Alone Is Not Enough

This pod can run on GPU nodes, but it can also run elsewhere if no node selector exists:

```yaml
tolerations:
  - key: workload.openshift.io/special
    operator: Equal
    value: gpu
    effect: NoSchedule
```

This pod must run on GPU nodes:

```yaml
nodeSelector:
  workload.openshift.io/class: gpu
tolerations:
  - key: workload.openshift.io/special
    operator: Equal
    value: gpu
    effect: NoSchedule
```

### 8.5 Taint Naming Convention

Use stable organization-wide keys.

Good:

```text
workload.openshift.io/special=gpu:NoSchedule
workload.openshift.io/special=realtime:NoSchedule
workload.openshift.io/special=database:NoSchedule
```

Avoid:

```text
gpu=true:NoSchedule
special=yes:NoSchedule
devteam=abc:NoSchedule
```

Why? Because many teams and templates will use these fields. Bad naming becomes technical debt.

### 8.6 Apply Toleration Before Taint

When migrating existing nodes into a special pool:

1. Add workload tolerations first.
2. Confirm critical pods can tolerate the taint.
3. Add node taint.
4. Watch scheduling events.

Command:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

## 9. MachineConfigPool Design

A MachineConfigPool is needed when special nodes require host-level configuration different from generic workers.

### 9.1 When You Need a Separate MCP

Create a custom MCP when you need:

- Special kernel arguments
- Real-time kernel configuration
- Huge pages configuration through performance tuning
- Custom kubelet settings
- Custom CRI-O settings
- Node-level files
- Systemd services
- Registry configuration specific to special nodes
- OS-level performance settings
- Separate update rollout behavior

You may not need a separate MCP if the pool only uses labels and taints.

### 9.2 MCP Inheritance Model

Custom worker pools inherit worker MachineConfigs. A custom pool is normally built by selecting both `worker` and the custom role in `machineConfigSelector`.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: special
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - special
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/special: ""
```

This means:

```text
Apply normal worker configuration plus special-specific configuration to nodes labeled node-role.kubernetes.io/special=''.
```

### 9.3 A Node Can Belong to Only One MCP

A node may have multiple Kubernetes labels, but from Machine Config Operator perspective, it should be selected into only one MachineConfigPool.

Bad design:

```text
Node selected by worker MCP and gpu MCP at the same time due to conflicting selectors.
```

Good design:

```text
Node has special role label and the custom MCP selector uniquely selects it.
```

### 9.4 Create Special MachineConfigPool

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: special
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - special
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/special: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f special-mcp.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp special
```

### 9.5 MachineConfig for Special Pool

Example MachineConfig that creates a marker file on special nodes:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 51-special-marker
  labels:
    machineconfiguration.openshift.io/role: special
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
        - path: /etc/node-pool
          mode: 0644
          contents:
            source: data:,special-workload-pool
```

Apply:

```bash
oc apply -f 51-special-marker.yaml
```

Check rollout:

```bash
oc get mcp special -w
oc get nodes -l node-role.kubernetes.io/special=
```

### 9.6 MCP Upgrade Behavior

MCP updates drain and reboot nodes when required. This is extremely important for special pools.

Production recommendations:

- Keep `maxUnavailable: 1` for small or sensitive pools.
- Use PodDisruptionBudgets for critical workloads.
- Avoid large simultaneous reboots on GPU/database/real-time nodes.
- Coordinate maintenance windows.
- Do not manually change MCO-managed files on nodes.
- Watch for `DEGRADED=True`.

Commands:

```bash
oc get mcp
oc describe mcp special
oc get machineconfig
oc get pods -n openshift-machine-config-operator
oc logs -n openshift-machine-config-operator daemonset/machine-config-daemon
```

### 9.7 Pausing a MachineConfigPool

You can pause a MachineConfigPool to stop rollout temporarily.

```bash
oc patch mcp special --type=merge -p '{"spec":{"paused":true}}'
```

Resume:

```bash
oc patch mcp special --type=merge -p '{"spec":{"paused":false}}'
```

Use this carefully. Pausing for too long can delay required security and platform updates.

## 10. Compute MachineSet / Machine Pool Design

In installer-provisioned infrastructure clusters, special worker nodes are commonly created through a separate compute MachineSet.

### 10.1 Why Use a Separate MachineSet

A separate MachineSet gives you:

- Dedicated instance type
- Dedicated disk size
- Dedicated availability zone
- Dedicated labels
- Dedicated taints
- Independent scaling
- Better capacity ownership
- Better replacement behavior

### 10.2 MachineSet-Level Labels

Labels can be placed in the MachineSet template so new nodes automatically join the special pool.

Conceptual snippet:

```yaml
spec:
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machine-role: special
        machine.openshift.io/cluster-api-machine-type: special
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/special: ""
          workload.openshift.io/class: gpu
          hardware.openshift.io/accelerator: nvidia-a100
```

Exact MachineSet format depends on the platform: AWS, Azure, vSphere, GCP, OpenStack, bare metal, or another supported provider.

### 10.3 MachineSet-Level Taints

Some platforms and OpenShift versions allow taints through the MachineSet provider/template configuration. If your platform supports it, define taints at provisioning time.

Conceptual snippet:

```yaml
spec:
  template:
    spec:
      taints:
        - key: workload.openshift.io/special
          value: gpu
          effect: NoSchedule
```

If not supported in your environment, apply taints after nodes are created using automation such as GitOps, Ansible, or a post-provisioning job.

### 10.4 Cloud Instance Selection

For special pools, instance type matters more than for generic workers.

Evaluate:

- CPU architecture
- Core count
- Hyperthreading behavior
- Memory per core
- Local disk availability
- Network bandwidth
- GPU type and count
- NUMA topology
- Availability zone availability
- Quota limits
- Cost

### 10.5 Bare Metal Considerations

For bare metal clusters:

- Hardware inventory must be accurate.
- BIOS settings matter.
- Firmware consistency matters.
- NIC naming consistency matters.
- CPU topology matters.
- Disk mapping matters.
- Out-of-band management should be reliable.

Special bare-metal pools are common in telco, industrial, and high-performance use cases.

## 11. Scheduling Workloads to the Special Pool

A workload should normally include both:

1. A toleration for the special taint
2. A placement rule selecting special nodes

### 11.1 Deployment Example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: special-api
  namespace: special-apps
spec:
  replicas: 3
  selector:
    matchLabels:
      app: special-api
  template:
    metadata:
      labels:
        app: special-api
    spec:
      nodeSelector:
        workload.openshift.io/class: special
      tolerations:
        - key: workload.openshift.io/special
          operator: Equal
          value: special
          effect: NoSchedule
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          command: ["/bin/sh", "-c", "while true; do echo running; sleep 30; done"]
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"
```

### 11.2 Node Affinity Example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: accelerated-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: accelerated-api
  template:
    metadata:
      labels:
        app: accelerated-api
    spec:
      tolerations:
        - key: workload.openshift.io/special
          operator: Equal
          value: gpu
          effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: workload.openshift.io/class
                    operator: In
                    values:
                      - gpu
                  - key: hardware.openshift.io/accelerator
                    operator: In
                    values:
                      - nvidia-a100
                      - nvidia-h100
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          command: ["sleep", "infinity"]
```

### 11.3 StatefulSet Example for Database Pool

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: data-platform
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      nodeSelector:
        workload.openshift.io/class: database
      tolerations:
        - key: workload.openshift.io/special
          operator: Equal
          value: database
          effect: NoSchedule
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: db
              topologyKey: kubernetes.io/hostname
      containers:
        - name: db
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          command: ["sleep", "infinity"]
          resources:
            requests:
              cpu: "2"
              memory: "4Gi"
            limits:
              cpu: "4"
              memory: "8Gi"
```

### 11.4 Topology Spread Example

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: model-serving
```

This prevents all replicas from concentrating in one zone when matching special nodes exist in multiple zones.

## 12. Project-Level Placement Controls

You can control placement at namespace/project level so teams do not need to put node selectors in every manifest.

### 12.1 Namespace Node Selector Annotation

Example:

```bash
oc annotate namespace ai-platform \
  openshift.io/node-selector='workload.openshift.io/class=gpu' \
  --overwrite
```

New pods in that namespace inherit the project-level node selector.

### 12.2 Use with Caution

Project node selectors are powerful but can surprise teams.

Common problem:

```text
Pod has its own node selector for normal workers.
Namespace injects node selector for GPU nodes.
Both must match.
No node has both labels.
Pod remains Pending.
```

Troubleshooting:

```bash
oc describe pod <pod> -n ai-platform
oc get namespace ai-platform -o yaml | grep -A3 node-selector
oc get nodes --show-labels
```

### 12.3 Admission Policy and Governance

For strict environments, consider enforcing workload placement using policy:

- GitOps review
- Kyverno / Gatekeeper-style policies if used in the organization
- OpenShift admission configuration where applicable
- CI checks for manifests
- Namespace templates
- Operator placement defaults

Example governance rule:

```text
Any workload in namespace ai-platform must include:
  - GPU toleration
  - GPU node selector or affinity
  - CPU and memory requests
  - GPU resource request if using GPU
```

## 13. Resource Management

Special pools are usually capacity-constrained. Resource governance is mandatory.

### 13.1 Requests and Limits

Every workload should define requests.

```yaml
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
  limits:
    cpu: "4"
    memory: "8Gi"
```

For GPU:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

For many device plugins, accelerators are requested through limits.

### 13.2 Namespace ResourceQuota

Example:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: ai-platform-quota
  namespace: ai-platform
spec:
  hard:
    requests.cpu: "40"
    requests.memory: 160Gi
    limits.cpu: "80"
    limits.memory: 320Gi
    pods: "50"
    requests.nvidia.com/gpu: "8"
```

### 13.3 LimitRange

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: ai-platform-defaults
  namespace: ai-platform
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: "500m"
        memory: "512Mi"
      default:
        cpu: "2"
        memory: "2Gi"
      min:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "8"
        memory: "32Gi"
```

### 13.4 QoS Classes

Kubernetes QoS class matters during eviction.

| QoS | Condition | Eviction Risk |
|---|---|---|
| Guaranteed | requests = limits for CPU and memory | Lowest |
| Burstable | requests set but not equal to limits | Medium |
| BestEffort | no requests/limits | Highest |

For special workloads, avoid BestEffort pods.

### 13.5 Overcommit Policy

Be conservative with overcommit on special pools.

GPU/real-time/database workloads often need predictable resources. Aggressive overcommit can destroy the reason the pool exists.

Recommended:

```text
Generic app pool:
  Moderate overcommit may be acceptable.

Special workload pool:
  Requests should closely match actual usage.
  Limits should be intentional.
  BestEffort pods should be blocked or discouraged.
```

## 14. Performance Tuning for Special Workloads

Performance tuning should be requirement-driven, not copied blindly.

### 14.1 CPU Manager

CPU Manager static policy can pin Guaranteed pods to exclusive CPUs.

KubeletConfig concept:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: special-cpumanager
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/special: ""
  kubeletConfig:
    cpuManagerPolicy: static
```

Check actual supported fields for your OpenShift version before applying.

### 14.2 Topology Manager

Topology Manager helps align CPU, memory, and device allocations.

Common policies:

```text
none
best-effort
restricted
single-numa-node
```

For high-performance workloads, `restricted` or `single-numa-node` may be required, but they can make scheduling stricter.

### 14.3 Huge Pages

Huge pages are common in:

- DPDK
- Databases
- JVM tuning in some cases
- Real-time workloads
- Network functions

Example workload request:

```yaml
resources:
  requests:
    hugepages-1Gi: 2Gi
    memory: 4Gi
  limits:
    hugepages-1Gi: 2Gi
    memory: 4Gi
```

### 14.4 Reserved and Isolated CPUs

For low-latency pools:

```text
Reserved CPUs:
  Platform services, kubelet, CRI-O, system daemons

Isolated CPUs:
  Application workloads requiring low jitter
```

This is normally handled through PerformanceProfile in supported scenarios.

### 14.5 Tuned Profiles

OpenShift uses tuned profiles for node-level performance tuning.

Special pools may require custom tuned settings for:

- CPU governor
- Kernel scheduler behavior
- Network tuning
- Disk I/O tuning
- Power management

Use caution: wrong tuning can make performance worse or destabilize nodes.

### 14.6 Performance Testing

Before production use, benchmark the pool with representative workloads.

Test:

- CPU latency
- Memory bandwidth
- Network throughput
- Storage IOPS
- Storage latency
- GPU utilization
- Pod startup time
- Drain time
- Recovery time
- Upgrade behavior

## 15. GPU and Accelerator Pools

GPU pools are one of the most common special workload pools.

### 15.1 GPU Pool Components

Typical components:

```text
GPU nodes
Node Feature Discovery Operator
GPU Operator
GPU device plugin
GPU driver stack
GPU monitoring exporter
Taints/labels
AI workload namespaces
Quota for GPU resources
```

### 15.2 GPU Node Labels

Possible labels:

```bash
oc label node worker-gpu-1 node-role.kubernetes.io/gpu=
oc label node worker-gpu-1 workload.openshift.io/class=gpu
oc label node worker-gpu-1 hardware.openshift.io/accelerator=nvidia-a100
```

Node Feature Discovery may add hardware discovery labels automatically.

### 15.3 GPU Node Taint

```bash
oc adm taint node worker-gpu-1 workload.openshift.io/special=gpu:NoSchedule
```

### 15.4 GPU Workload Example

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: gpu-test
  namespace: ai-platform
spec:
  template:
    spec:
      restartPolicy: Never
      nodeSelector:
        workload.openshift.io/class: gpu
      tolerations:
        - key: workload.openshift.io/special
          operator: Equal
          value: gpu
          effect: NoSchedule
      containers:
        - name: cuda-test
          image: nvcr.io/nvidia/cuda:12.4.1-base-ubuntu22.04
          command: ["nvidia-smi"]
          resources:
            limits:
              nvidia.com/gpu: 1
```

Use an image approved for your registry and disconnected environment requirements.

### 15.5 GPU Scheduling Mistakes

Common mistakes:

```text
1. Pod has GPU resource request but no toleration.
   Result: Pending due to taint.

2. Pod has toleration but no GPU resource request.
   Result: It may run but not reserve GPU.

3. Pod has nodeSelector but GPU Operator/device plugin is broken.
   Result: GPU resource not allocatable.

4. Generic workloads tolerate all taints.
   Result: They may land on GPU nodes and waste expensive capacity.
```

Check:

```bash
oc describe node worker-gpu-1 | grep -A20 -i allocatable
oc get pods -n nvidia-gpu-operator
oc describe pod gpu-test -n ai-platform
```

## 16. Real-Time / Low-Latency Pools

Low-latency pools need the most discipline.

### 16.1 Typical Requirements

- Dedicated bare-metal nodes
- Real-time kernel where needed
- CPU isolation
- Reserved CPUs
- Huge pages
- NUMA-aware placement
- SR-IOV NICs
- Power management tuning
- Minimal background noise

### 16.2 PerformanceProfile Concept

Conceptual example:

```yaml
apiVersion: performance.openshift.io/v2
kind: PerformanceProfile
metadata:
  name: realtime-special
spec:
  cpu:
    reserved: "0-3"
    isolated: "4-31"
  nodeSelector:
    node-role.kubernetes.io/realtime: ""
  realTimeKernel:
    enabled: true
  numa:
    topologyPolicy: restricted
  hugepages:
    defaultHugepagesSize: 1G
    pages:
      - size: 1G
        count: 16
```

Always generate and validate PerformanceProfiles according to your OpenShift version and platform guidance.

### 16.3 Low-Latency Workload Requirements

Pods usually need:

- Guaranteed QoS
- Whole CPU requests
- CPU limits equal to requests
- Huge pages where needed
- Node affinity
- Tolerations
- SR-IOV network attachment if needed

Example:

```yaml
resources:
  requests:
    cpu: "4"
    memory: "4Gi"
    hugepages-1Gi: "2Gi"
  limits:
    cpu: "4"
    memory: "4Gi"
    hugepages-1Gi: "2Gi"
```

### 16.4 Real-Time Pool Anti-Patterns

Avoid:

- Running generic monitoring-heavy workloads on low-latency nodes
- Overcommitting CPU
- Using BestEffort pods
- Allowing random DaemonSets without review
- Mixing latency-sensitive and batch workloads
- Applying tuning without measuring before/after

## 17. Storage-Heavy and Database Pools

Database and storage-heavy workloads are sensitive to drain, eviction, and disk pressure.

### 17.1 Design Goals

- Stable node identity
- Predictable storage performance
- Dedicated local/NVMe devices where needed
- Strict anti-affinity for replicas
- PDBs for controlled disruption
- Strong backup and restore procedures

### 17.2 Labels and Taints

```bash
oc label node worker-db-1 node-role.kubernetes.io/database=
oc label node worker-db-1 workload.openshift.io/class=database
oc label node worker-db-1 hardware.openshift.io/storage=local-nvme

oc adm taint node worker-db-1 workload.openshift.io/special=database:NoSchedule
```

### 17.3 StatefulSet Placement

Use:

- `nodeSelector` for database nodes
- Toleration for database taint
- Pod anti-affinity across hostnames
- Topology spread across zones/racks
- PDB to protect quorum

### 17.4 PDB Example

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: db-pdb
  namespace: data-platform
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: db
```

### 17.5 Drain Considerations

Before draining database nodes:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Check:

```bash

oc get pods -n data-platform -o wide
oc describe node <node>
```

Do not force drain stateful production workloads without understanding data safety.

## 20. Autoscaling and Capacity Planning

Special pools are often expensive and capacity-limited. Plan carefully.

### 20.1 Capacity Model

Track:

```text
Node count
CPU allocatable
Memory allocatable
Special resource allocatable, such as GPUs
Actual requested CPU/memory
Actual used CPU/memory
Pod count
DaemonSet overhead
Reserved platform resources
Upgrade surge capacity
Failure-domain capacity
```

### 20.2 Headroom Rule

For production special pools, keep headroom for:

- Node failure
- Maintenance drain
- Rolling upgrades
- Burst scheduling
- DaemonSet growth
- Operator overhead

Example:

```text
3-node GPU pool with 1 GPU per node:
  If all 3 GPUs are constantly allocated, you have no maintenance headroom.
  A drain will either block or disrupt workloads.

Better:
  Run steady-state at 60-75% allocation if high availability matters.
```

### 20.3 Cluster Autoscaler

If using autoscaling, verify:

- Special MachineSets are included correctly.
- Taints are understood by workload pods.
- Pending pods have correct requests.
- Scale-up latency is acceptable.
- Cloud quota supports scale-up.
- Scale-down does not remove nodes with important local state.

### 20.4 Horizontal Pod Autoscaler

HPA works for CPU/memory/custom metrics, but many special workloads scale on external metrics:

- Queue length
- Requests per second
- GPU utilization
- Inference latency
- Kafka lag
- Custom Prometheus metrics

### 20.5 Avoid Autoscaling Anti-Patterns

Avoid:

```text
Scaling GPU workloads only on CPU.
Allowing scale-down of local-storage nodes without data migration.
Using HPA without resource requests.
Ignoring node provisioning time for special hardware.
```

## 22. Upgrade and Day-2 Operations

Special pools need special day-2 handling.

### 22.1 Upgrade Planning

Before upgrade:

```bash
oc adm upgrade
oc get clusterversion
oc get co
oc get mcp
oc get pdb -A
oc get nodes -o wide
```

Check special pool readiness:

```bash
oc get mcp special
oc describe mcp special
oc get pods -A -o wide | grep <special-node>
```

### 22.2 MCP Rollout Strategy

Keep `maxUnavailable` conservative.

```yaml
spec:
  maxUnavailable: 1
```

For very small pools, even one unavailable node may be too disruptive. In that case, ensure workload-level redundancy and PDB design before applying changes.

### 22.3 Draining Special Nodes

Dry run first:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Then actual drain only if safe:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

Uncordon:

```bash
oc adm uncordon <node>
```

### 22.4 Operator Placement Review

Some Operators have their own placement settings. For example:

- Logging operator components
- Monitoring stack
- GPU Operator
- SR-IOV Operator
- OpenShift Virtualization
- OpenShift Data Foundation

Do not assume node labels and taints automatically move all operator-managed pods. Check each Operator CR.

### 22.5 Removing a Special Pool

Safe removal order:

1. Stop scheduling new workloads to the pool.
2. Migrate or scale down workloads.
3. Remove project node selectors or workload affinity.
4. Remove taints.
5. Re-label nodes back to worker if reusing them.
6. Allow MCP reconciliation.
7. Remove custom MachineConfigs.
8. Remove custom MachineConfigPool.
9. Scale down or delete MachineSet if nodes are no longer needed.

Do not delete the MCP while nodes are still selected by it without a migration plan.

## 23. Troubleshooting Runbook

### 23.1 Pod Stuck Pending

Symptoms:

```text
0/6 nodes are available: node(s) had untolerated taint, node(s) didn't match Pod's node affinity/selector.
```

Check pod events:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Check node labels:

```bash
oc get nodes --show-labels | grep special
oc get nodes -l workload.openshift.io/class=gpu
```

Check taints:

```bash
oc describe node <node> | grep -i taints -A5
```

Common root causes:

| Symptom | Likely Cause | Fix |
|---|---|---|
| Untolerated taint | Pod missing toleration | Add matching toleration |
| Node affinity mismatch | Wrong label value | Correct label or affinity |
| Insufficient CPU/memory | Requests too high or pool too small | Adjust requests or add capacity |
| Insufficient GPU | GPU already allocated | Add GPU node or reduce demand |
| Namespace selector conflict | Project node selector conflicts with pod selector | Fix namespace annotation or pod spec |

### 23.2 Pod Scheduled to Wrong Node

Check:

```bash
oc get pod <pod> -n <namespace> -o wide
oc get pod <pod> -n <namespace> -o yaml | grep -A20 -E 'nodeSelector|affinity|tolerations'
```

Likely causes:

- Toleration exists but no node selector.
- Node labels are too broad.
- Pod has preferred affinity, not required affinity.
- Taint is missing from special nodes.
- Generic nodes accidentally have special label.

### 23.3 MCP Degraded

Check:

```bash
oc get mcp
oc describe mcp special
oc get nodes
oc get pods -n openshift-machine-config-operator
oc logs -n openshift-machine-config-operator daemonset/machine-config-daemon
```

Common causes:

- Manual modification to MCO-managed file
- Invalid MachineConfig
- Node failed to reboot
- Node unreachable
- Disk pressure
- Kubelet degraded
- Conflicting configuration

### 23.4 Node Not Joining Special MCP

Check labels:

```bash
oc get node <node> --show-labels
oc get mcp special -o yaml
```

Check MCP selector:

```yaml
spec:
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/special: ""
```

The node must have exactly the label expected by the MCP selector.

### 23.5 Workload Does Not Use GPU

Check allocatable GPU:

```bash
oc describe node <gpu-node> | grep -A20 -i allocatable
```

Check pod resource request:

```bash
oc get pod <pod> -n <namespace> -o yaml | grep -A10 resources
```

Check GPU operator/device plugin pods:

```bash
oc get pods -A | grep -i gpu
oc get pods -A | grep -i nvidia
```

### 23.6 Drain Blocked

Check PDBs:

```bash
oc get pdb -A
oc describe pdb <pdb> -n <namespace>
```

Check blocking pods:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Likely causes:

- PDB prevents eviction
- Standalone pod not managed by controller
- Stateful workload cannot move
- Local storage dependency
- Pod uses emptyDir and command did not allow deletion

### 23.7 Node Pressure

Check:

```bash
oc describe node <node>
oc adm top node <node>
oc debug node/<node>
```

Inside debug shell:

```bash
chroot /host
df -h
free -m
journalctl -u kubelet --no-pager | tail -100
journalctl -u crio --no-pager | tail -100
```

- [ ] Test backup/restore for stateful special workloads.

## 25. Complete Example: Build a Special Workload Node Pool

This example builds a generic `special` pool. You can adapt the names for `gpu`, `database`, `realtime`, or `sriov`.

### 25.1 Current Nodes

```bash
oc get nodes
```

Example:

```text
NAME              STATUS   ROLES    AGE   VERSION
worker-1          Ready    worker   20d   v1.xx
worker-2          Ready    worker   20d   v1.xx
worker-3          Ready    worker   20d   v1.xx
```

### 25.2 Label Nodes

```bash
oc label node worker-2 node-role.kubernetes.io/special=
oc label node worker-2 workload.openshift.io/class=special
```

Verify:

```bash
oc get nodes -L node-role.kubernetes.io/special,workload.openshift.io/class
```

### 25.3 Create MachineConfigPool

Create `special-mcp.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: special
  labels:
    pools.operator.machineconfiguration.openshift.io/special: ""
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - special
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/special: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f special-mcp.yaml
oc get mcp
```

### 25.4 Add Special Pool MachineConfig

Create `51-special-marker.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 51-special-marker
  labels:
    machineconfiguration.openshift.io/role: special
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
        - path: /etc/special-node-pool
          mode: 0644
          contents:
            source: data:,special
```

Apply:

```bash
oc apply -f 51-special-marker.yaml
oc get mcp special -w
```

### 25.5 Taint Special Nodes

```bash
oc adm taint nodes -l workload.openshift.io/class=special \
  workload.openshift.io/special=special:NoSchedule
```

Verify:

```bash
oc describe node worker-2 | grep -i taints -A3
```

### 25.6 Create Namespace

```bash
oc new-project special-apps
```

Optional namespace node selector:

```bash
oc annotate namespace special-apps \
  openshift.io/node-selector='workload.openshift.io/class=special' \
  --overwrite
```

### 25.7 Deploy Test Workload

Create `special-app.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: special-app
  namespace: special-apps
spec:
  replicas: 1
  selector:
    matchLabels:
      app: special-app
  template:
    metadata:
      labels:
        app: special-app
    spec:
      nodeSelector:
        workload.openshift.io/class: special
      tolerations:
        - key: workload.openshift.io/special
          operator: Equal
          value: special
          effect: NoSchedule
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          command: ["/bin/sh", "-c", "while true; do echo special; sleep 30; done"]
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
```

Apply:

```bash
oc apply -f special-app.yaml
```

Verify placement:

```bash
oc get pods -n special-apps -o wide
```

Expected:

```text
Pod should run on worker-2 or another node labeled workload.openshift.io/class=special.
```

### 25.8 Negative Test

Create a generic pod without toleration:

```bash
oc run generic-test -n special-apps \
  --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \
  --command -- sleep infinity
```

If namespace node selector forces it to special nodes but it lacks toleration, it may stay Pending.

Check:

```bash
oc describe pod generic-test -n special-apps
```

You should see scheduling failure related to untolerated taint.

### 25.9 Validate MCP-Level File

Find machine-config-daemon pod on the special node:

```bash
oc get pod -n openshift-machine-config-operator -o wide | grep worker-2
```

Check marker file:

```bash
oc debug node/worker-2
chroot /host
cat /etc/special-node-pool
exit
exit
```

### 25.10 Cleanup

Delete workload:

```bash
oc delete project special-apps
```

Remove taint:

```bash
oc adm taint nodes -l workload.openshift.io/class=special \
  workload.openshift.io/special=special:NoSchedule-
```

Re-label node back to worker-only if needed:

```bash
oc label node worker-2 node-role.kubernetes.io/special-
oc label node worker-2 workload.openshift.io/class-
```

Delete special MachineConfig and MCP after nodes no longer select it:

```bash
oc delete mc 51-special-marker
oc delete mcp special
```

## 26. Interview / Exam-Style Points

### 26.1 What Is the Difference Between Label and Taint?

```text
Label:
  Describes a node.
  Pods can select labels using nodeSelector or affinity.

Taint:
  Protects a node.
  Pods must tolerate taints to schedule there.
```

### 26.2 Does Toleration Force a Pod onto a Node?

No.

A toleration only allows the pod to run on a tainted node. To force placement, use:

- `nodeSelector`
- Required node affinity
- Project node selector

### 26.3 Why Create a Custom MachineConfigPool?

Create a custom MCP when special nodes require different host-level configuration or separate rollout behavior.

Examples:

- GPU driver/runtime tuning
- Kubelet CPU manager settings
- Real-time kernel settings
- Huge pages
- Special systemd services
- Dedicated OS-level files

### 26.4 Can One Node Belong to Multiple MachineConfigPools?

A node can have many labels, but it should be selected by only one MachineConfigPool. Overlapping MCP selectors create operational risk.

### 26.5 What Is the Safest Isolation Pattern?

Use all three:

```text
1. Label special nodes.
2. Taint special nodes.
3. Add toleration plus required node selector/affinity to allowed workloads.
```

### 26.6 Why Is `NoSchedule` Usually Preferred?

`NoSchedule` prevents new non-tolerating pods from landing on the node but does not evict existing pods. It is safer for planned isolation.

`NoExecute` can evict running pods and should be used carefully.

### 26.7 What Causes Pending Pods in Special Pools?

Common causes:

- Missing toleration
- Wrong node selector
- Wrong node label
- Insufficient CPU/memory/GPU
- Conflicting namespace node selector
- PDB or topology constraints too strict
- Special nodes cordoned or NotReady

### 26.8 How Do You Troubleshoot Scheduling?

Start with:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
oc get nodes --show-labels
oc describe node <node>
oc get mcp
```

The pod event usually tells you the scheduler reason.

## Final Senior-Admin Summary

A special workload node pool is a production design pattern for workloads that cannot safely or efficiently run on generic worker nodes. In OpenShift, you build it by combining node labels, taints, tolerations, workload placement rules, MachineConfigPools, machine provisioning, resource governance, and monitoring.

The strongest design is:

```text
Dedicated MachineSet or provisioning group
+ clear node labels
+ protective taints
+ workload tolerations
+ required node selector/affinity
+ custom MCP only when host configuration differs
+ quota/limits/PDBs
+ pool-specific monitoring
+ tested drain and upgrade runbook
```

For a 10-year experienced administrator, the main skill is not just creating labels and taints. The real skill is knowing when to isolate, how much to isolate, how to prevent accidental scheduling, how to preserve upgrade safety, how to monitor capacity, and how to troubleshoot Pending pods or degraded MachineConfigPools under production pressure.
