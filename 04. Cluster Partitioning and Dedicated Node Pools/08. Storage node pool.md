# Storage Node Pool in Cluster Partitioning and Dedicated Node Pools

**Course context:** Advanced OpenShift Administration  
**Audience:** Linux/OpenShift/Kubernetes administrator with around 10 years of infrastructure experience  
**Focus:** Storage node pool design, implementation, validation, operations, troubleshooting, and production patterns

---

## 1. Executive Summary

A **storage node pool** is a dedicated group of OpenShift worker nodes reserved for storage-related services and storage-heavy workloads. In production OpenShift environments, this usually means isolating components such as:

- Red Hat OpenShift Data Foundation (ODF) / Rook-Ceph components
- Ceph OSD, MON, MGR, MDS, RGW, NooBaa, and CSI pods
- Local Storage Operator resources
- CSI node plugins and provisioners
- Storage gateway workloads
- High I/O stateful workloads, when intentionally placed near storage

A storage node pool is not just a label on a node. It is a **cluster partitioning strategy** that combines:

- Node labels
- Taints and tolerations
- MachineSets or manual node lifecycle
- MachineConfigPools
- StorageClass design
- Device planning
- Zone/rack failure-domain planning
- Upgrade and drain strategy
- Monitoring and alerting
- Capacity and performance governance

For an experienced administrator, the important point is this:

> A storage node pool protects storage performance, storage availability, and cluster operational stability by separating storage responsibilities from general application scheduling.

---

## 2. Why Storage Node Pools Exist

OpenShift clusters commonly start with generic worker nodes. This is acceptable for small labs, but it becomes risky in enterprise environments because storage workloads have different operational characteristics from stateless application workloads.

Storage workloads usually require:

- Predictable disk latency
- Consistent CPU and memory availability
- Stable network throughput
- Controlled disruption during upgrades
- Dedicated raw block devices or cloud volumes
- Awareness of failure domains such as zone, rack, host, or storage failure set
- Protection from noisy application workloads
- Careful drain and reboot procedures

Without a storage node pool, the following problems are common:

- Application pods consume CPU or memory needed by OSDs or CSI components.
- Storage pods are scheduled onto nodes without proper disks.
- Generic cluster upgrades reboot too many storage-heavy nodes at an inconvenient time.
- PVC provisioning fails because the scheduler cannot match PV node affinity, pod node affinity, and taints.
- Ceph recovery/backfill competes with normal application traffic.
- DaemonSets such as CSI plugins, DNS, logging agents, or monitoring agents do not tolerate storage taints.
- A node replacement loses required labels because labels were applied manually instead of through MachineSet templates.

A storage pool solves these issues by making the placement model intentional.

## 3. Storage Node Pool vs Other Node Pools

| Pool Type | Primary Purpose | Typical Workloads | Main Risk if Mixed Incorrectly |
|---|---|---|---|
| Control plane | Kubernetes/OpenShift control plane | API server, etcd, controllers, scheduler | Control plane instability |
| Infra pool | Platform infrastructure | Router, registry, monitoring, logging, GitOps, Quay | Platform services compete with apps |
| Application pool | Business workloads | Deployments, StatefulSets, Jobs | Apps compete with platform/storage |
| Logging pool | Log collection and indexing | Loki, Elasticsearch, Vector, Fluentd | Disk and CPU pressure from logs |
| Monitoring pool | Metrics and alerting | Prometheus, Alertmanager, Thanos | Metrics loss during app pressure |
| **Storage pool** | Persistent storage services | ODF, Ceph, Local Storage, CSI, storage gateways | Data availability and I/O performance degradation |

A storage node pool can be implemented as a separate **storage role** or, in ODF subscription-sensitive environments, as dedicated nodes carrying an **infra role plus ODF storage labels and taints**. The exact label model depends on your platform, subscription model, and storage product design.

## 4. Core Design Principles

### 4.1 Keep storage nodes predictable

Storage nodes should be boring and predictable. Avoid running random application workloads on them. Storage nodes should not be used as overflow capacity when application nodes are full.

### 4.2 Treat storage nodes as a failure-domain-aware pool

A three-node storage cluster where all nodes are in the same rack, same hypervisor, same power domain, or same availability zone is not truly resilient. Storage scheduling must account for physical and logical failure domains.

### 4.3 Separate “can schedule here” from “must schedule here”

Labels attract pods. Taints repel pods. For a storage pool, use both:

- **Labels** identify storage-capable nodes.
- **Taints** prevent non-storage workloads from landing there.
- **Tolerations** allow only approved storage components to land there.

### 4.4 Do not rely on manual labels when Machine API is used

If the cluster uses MachineSets, labels and taints should be added to the MachineSet template. If labels are added only to the node object, replacement nodes created after failure might not inherit the correct scheduling identity.

### 4.5 Do not remove the worker role label

Even when creating custom pools, keep the worker role label unless the vendor documentation explicitly says otherwise. Worker inheritance is important for MCO behavior and general node functionality.

### 4.6 Plan maintenance before production

Storage nodes are not regular stateless compute nodes. A reboot, drain, or failed update can trigger storage recovery, data rebalance, degraded redundancy, or application I/O impact.

## 5. Reference Architecture

A strong production pattern looks like this:

```text
                +-------------------------------+
                |        OpenShift Cluster       |
                +-------------------------------+

  +-------------------+  +-------------------+  +-------------------+
  | Control Plane 1   |  | Control Plane 2   |  | Control Plane 3   |
  | etcd/API/etc      |  | etcd/API/etc      |  | etcd/API/etc      |
  +-------------------+  +-------------------+  +-------------------+

  +-------------------+  +-------------------+  +-------------------+
  | Infra Node 1      |  | Infra Node 2      |  | Infra Node 3      |
  | routers/registry  |  | monitoring/logging|  | platform services |
  +-------------------+  +-------------------+  +-------------------+

  +-------------------+  +-------------------+  +-------------------+
  | Storage Node 1    |  | Storage Node 2    |  | Storage Node 3    |
  | OSD/CSI/ODF       |  | OSD/CSI/ODF       |  | OSD/CSI/ODF       |
  | Zone A            |  | Zone B            |  | Zone C            |
  +-------------------+  +-------------------+  +-------------------+

  +-------------------+  +-------------------+  +-------------------+
  | App Node Pool     |  | App Node Pool     |  | App Node Pool     |
  | user workloads    |  | user workloads    |  | user workloads    |
  +-------------------+  +-------------------+  +-------------------+
```

The storage node pool should be sized and placed based on:

- Storage capacity requirement
- Replica count
- Failure domains
- OSD count
- Disk performance profile
- Expected IOPS
- Expected throughput
- Recovery/backfill behavior
- Maintenance window
- Workload read/write pattern

## 6. Label Strategy

A generic storage node pool commonly uses labels such as:

```bash
oc label node <node-name> node-role.kubernetes.io/storage=""
oc label node <node-name> cluster.ocs.openshift.io/openshift-storage=""
```

For ODF-dedicated nodes, Red Hat documentation commonly uses the following important labels and taint pattern:

```yaml
metadata:
  labels:
    node-role.kubernetes.io/worker: ""
    node-role.kubernetes.io/infra: ""
    cluster.ocs.openshift.io/openshift-storage: ""
spec:
  taints:
  - key: node.ocs.openshift.io/storage
    value: "true"
    effect: NoSchedule
```

### Label meanings

| Label | Meaning |
|---|---|
| `node-role.kubernetes.io/worker` | Keeps the node in the worker family and allows worker-based inheritance. Do not remove casually. |
| `node-role.kubernetes.io/storage` | Custom role label for a storage-specific MachineConfigPool or scheduling model. |
| `node-role.kubernetes.io/infra` | Used when storage infrastructure nodes should be treated as infra nodes for platform/subscription design. Validate with your Red Hat subscription guidance. |
| `cluster.ocs.openshift.io/openshift-storage` | Used by ODF placement to identify nodes intended for OpenShift storage components. |
| `topology.kubernetes.io/zone` | Indicates failure zone. Important for topology-aware storage and application placement. |
| `kubernetes.io/hostname` | Used by PV node affinity and anti-affinity decisions. |

### Practical recommendation

For a clean enterprise design, use both a business-readable label and product-specific labels:

```bash
oc label node worker-storage-1 node-role.kubernetes.io/storage=""
oc label node worker-storage-1 workload.openshift.io/pool=storage
oc label node worker-storage-1 cluster.ocs.openshift.io/openshift-storage=""
```

This gives you flexibility:

- MCO can use the role label.
- Storage operators can use the ODF label.
- Platform engineers can filter nodes by `workload.openshift.io/pool=storage`.

## 7. Taint Strategy

A storage node pool should usually be tainted to stop normal workloads from scheduling there.

Example:

```bash
oc adm taint node <node-name> node.ocs.openshift.io/storage=true:NoSchedule
```

Generic custom taint example:

```bash
oc adm taint node <node-name> workload.openshift.io/storage=true:NoSchedule
```

### Taint effects

| Effect | Behavior | Storage Pool Use |
|---|---|---|
| `NoSchedule` | New pods cannot schedule unless they tolerate the taint. | Most common and recommended. |
| `PreferNoSchedule` | Scheduler avoids the node but can still use it. | Weak isolation; not ideal for strict storage pools. |
| `NoExecute` | Existing pods without toleration are evicted. | Dangerous unless carefully planned. |

### Example toleration

```yaml
tolerations:
- key: node.ocs.openshift.io/storage
  operator: Equal
  value: "true"
  effect: NoSchedule
```

### Important warning

After adding a storage taint, some platform DaemonSets might stop running on those nodes unless they have matching tolerations. Common examples include:

- CSI node plugin DaemonSets
- DNS DaemonSets
- Logging collectors
- Monitoring node exporters
- Network-related DaemonSets

Always validate DaemonSet coverage after applying taints.

## 8. MachineSet-Based Storage Nodes

When the Machine API is available, configure storage pool identity at the MachineSet level.

### Why MachineSet templates matter

If you manually label a node created by a MachineSet, a replacement node may not inherit those labels or taints. That creates a hidden production risk:

```text
Node fails -> Machine API creates replacement -> replacement has no storage labels -> ODF pods cannot schedule -> storage capacity/recovery impacted
```

### MachineSet template pattern

Example snippet only; adjust provider-specific fields for AWS, vSphere, OpenStack, Bare Metal, Azure, or GCP.

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: storage-us-east-1a
  namespace: openshift-machine-api
spec:
  replicas: 1
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-machineset: storage-us-east-1a
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machineset: storage-us-east-1a
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/worker: ""
          node-role.kubernetes.io/storage: ""
          cluster.ocs.openshift.io/openshift-storage: ""
          workload.openshift.io/pool: storage
      taints:
      - key: node.ocs.openshift.io/storage
        value: "true"
        effect: NoSchedule
      providerSpec:
        value:
          # Platform-specific provider configuration goes here.
          # Example: instance type, disks, network, zone, image, subnet.
          instanceType: <storage-optimized-instance>
```

### Multi-zone pattern

Use one MachineSet per availability zone:

```text
storage-zone-a MachineSet -> 1 or more storage nodes
storage-zone-b MachineSet -> 1 or more storage nodes
storage-zone-c MachineSet -> 1 or more storage nodes
```

Avoid creating all storage nodes in one failure domain unless the environment is only a lab or non-critical cluster.

## 9. Manual Storage Node Preparation

Manual labeling is acceptable when Machine API is not used or when dealing with user-provisioned infrastructure.

Example:

```bash
# Label node as storage-capable
oc label node worker-3 node-role.kubernetes.io/storage=""
oc label node worker-3 workload.openshift.io/pool=storage
oc label node worker-3 cluster.ocs.openshift.io/openshift-storage=""

# Optional, only when your design intentionally uses infra-role storage nodes
oc label node worker-3 node-role.kubernetes.io/infra=""

# Taint the node to repel non-storage workloads
oc adm taint node worker-3 node.ocs.openshift.io/storage=true:NoSchedule
```

Verify:

```bash
oc get nodes --show-labels | grep storage
oc describe node worker-3 | egrep -i 'Taints|Roles|Labels'
```

## 10. MachineConfigPool for Storage Nodes

A **MachineConfigPool (MCP)** allows you to apply OS-level and kubelet-level configuration to only the storage nodes.

This is useful when storage nodes require:

- Different kubelet reservation
- Different max pods setting
- Different CRI-O settings
- Different sysctl/kernel arguments
- Different network tuning
- Different image pull behavior
- Custom systemd services
- Additional packages through image layering, where supported

### Key concept

Custom MCPs inherit from the worker pool. This means:

- Worker MachineConfigs still apply to the storage pool.
- Storage-specific MachineConfigs can additionally apply to only storage nodes.
- A node should belong to one MCP only.
- Custom MCPs for control plane nodes are not supported.

### Example storage MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: storage
  labels:
    pools.operator.machineconfiguration.openshift.io/storage: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - storage
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/storage: ""
  maxUnavailable: 1
```

Create it:

```bash
oc apply -f storage-mcp.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp storage
oc get nodes -l node-role.kubernetes.io/storage=
```

### Example storage-specific MachineConfig

This is an example skeleton. Do not apply random kernel tuning to production storage nodes without vendor validation.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-storage-custom-sysctl
  labels:
    machineconfiguration.openshift.io/role: storage
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/sysctl.d/99-storage.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,IyBTdG9yYWdlIG5vZGUgdHVuaW5nIGV4YW1wbGUK
```

After applying a MachineConfig, expect the MCO to drain, reboot, and uncordon nodes according to the MCP update strategy.

## 11. KubeletConfig for Storage Pool

Storage nodes may need different kubelet settings from generic workers. For example, you may want more conservative pod density or stronger system reservations.

Example skeleton:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: storage-kubeletconfig
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/storage: ""
  kubeletConfig:
    maxPods: 150
    systemReserved:
      cpu: "2000m"
      memory: "4Gi"
    kubeReserved:
      cpu: "1000m"
      memory: "2Gi"
```

Apply and monitor:

```bash
oc apply -f storage-kubeletconfig.yaml
oc get mcp storage -w
```

Important: kubelet and MachineConfig changes can reboot nodes. For storage nodes, schedule this work carefully.

## 12. StorageClass and Scheduling Interaction

Storage node pool design is incomplete without understanding PVC binding behavior.

### Immediate binding

With `volumeBindingMode: Immediate`, the PV or backend volume can be selected before the consuming pod is scheduled.

This can cause problems when:

- PV node affinity points to a specific node.
- Pod nodeSelector points to another node pool.
- Taints block the pod from the node where the PV exists.

### WaitForFirstConsumer

With `volumeBindingMode: WaitForFirstConsumer`, the scheduler considers the pod placement first and then binds/provisions storage based on where the pod can run.

This is especially important for:

- Local PVs
- Zonal cloud volumes
- Topology-aware storage
- Applications using node affinity

Example StorageClass concept:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-storage-wffc
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Retain
```

For local storage, always inspect PV node affinity:

```bash
oc get pv <pv-name> -o yaml | grep -A20 nodeAffinity
```

## 13. Local Storage Operator on Storage Nodes

The Local Storage Operator is often used to expose local disks as PVs.

### Device discovery checklist

Before deploying local storage:

```bash
oc debug node/<storage-node>
chroot /host
lsblk
blkid
wipefs -n /dev/<device>
ls -l /dev/disk/by-id/
exit
```

Use stable device paths whenever possible:

```text
/dev/disk/by-id/<stable-device-id>
```

Avoid using unstable names like `/dev/sdb` if device ordering can change after reboot.

### LocalVolume example

```yaml
apiVersion: local.storage.openshift.io/v1
kind: LocalVolume
metadata:
  name: local-block-storage
  namespace: openshift-local-storage
spec:
  nodeSelector:
    nodeSelectorTerms:
    - matchExpressions:
      - key: node-role.kubernetes.io/storage
        operator: Exists
  storageClassDevices:
  - storageClassName: local-block
    volumeMode: Block
    fsType: xfs
    devicePaths:
    - /dev/disk/by-id/<device-id-1>
    - /dev/disk/by-id/<device-id-2>
```

If storage nodes are tainted, ensure Local Storage Operator pods and related DaemonSets can tolerate the taint where required.

## 14. OpenShift Data Foundation Placement

ODF is the most common reason for a dedicated storage pool in OpenShift.

### Minimum production idea

For resilient ODF internal mode, plan at least three worker or infrastructure nodes, preferably spread across failure domains. For local-storage-based ODF, nodes should have comparable storage type and size.

### Namespace default node selector issue

If the cluster has a cluster-wide default node selector, the `openshift-storage` namespace may need a blank namespace node selector annotation so ODF is not unintentionally forced to the wrong node pool.

Command:

```bash
oc annotate namespace openshift-storage openshift.io/node-selector=
```

### ODF placement pattern

Typical intent:

```yaml
placement:
  all:
    nodeSelector:
      cluster.ocs.openshift.io/openshift-storage: ""
    tolerations:
    - key: node.ocs.openshift.io/storage
      operator: Equal
      value: "true"
      effect: NoSchedule
```

Actual supported fields can vary by ODF version and component. Always verify with:

```bash
oc explain storagecluster.spec.placement
oc explain storagecluster.spec.placement.all
oc get storagecluster -n openshift-storage -o yaml
```

### ODF dedicated node labels and taints

Common node identity:

```bash
oc label node <node> cluster.ocs.openshift.io/openshift-storage=""
oc adm taint node <node> node.ocs.openshift.io/storage=true:NoSchedule
```

If using infra-labeled ODF nodes according to your support/subscription design:

```bash
oc label node <node> node-role.kubernetes.io/infra=""
```

Do not remove:

```text
node-role.kubernetes.io/worker
```

## 15. CSI Component Placement

CSI has two major classes of components:

### Controller/provisioner components

These usually run as Deployments and handle provisioning, attaching, snapshotting, resizing, and backend API calls.

### Node plugin components

These usually run as DaemonSets and must be present on nodes where workloads using that CSI driver might run.

This is critical in storage node pool design:

```text
A node can only mount/use a CSI-backed PVC if the required CSI node plugin is running on that node.
```

If a node has a taint and the CSI node plugin does not tolerate it, pods on that node may fail volume mount.

Validation commands:

```bash
oc get ds -A | egrep -i 'csi|rbd|cephfs|ebs|cinder|vsphere|azure|gcp'
oc get pods -A -o wide | egrep -i 'csi|rbd|cephfs'
oc describe ds <csi-node-plugin-ds> -n <namespace> | grep -A20 Tolerations
```

Common symptom:

```text
MountVolume.MountDevice failed
failed to find plugin
pod has unbound immediate PersistentVolumeClaims
0/6 nodes are available: node(s) had untolerated taint
```

## 16. Application Workloads and Storage Pools

Most application pods should not run on storage nodes. However, there are exceptions:

- Storage benchmark jobs
- Backup agents
- Storage gateway services
- Data-intensive workloads intentionally colocated with storage
- Recovery or migration jobs

### Application should avoid storage pool

Use node affinity or namespace selectors to target app pools:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/pool: app
```

### Application intentionally uses storage pool

Only do this with explicit approval:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/pool: storage
      tolerations:
      - key: node.ocs.openshift.io/storage
        operator: Equal
        value: "true"
        effect: NoSchedule
```

Never allow application teams to add broad tolerations such as:

```yaml
operator: Exists
```

unless there is a strong governance reason. Broad tolerations bypass isolation.

## 17. Capacity Planning

Storage pool capacity planning has two dimensions:

1. **Raw storage capacity**
2. **Usable application capacity**

For replicated storage, usable capacity is much lower than raw capacity.

Example conceptual model:

```text
Raw capacity:        3 nodes x 4 TB = 12 TB
Replication factor:  3
Approx usable:       12 TB / 3 = 4 TB before overhead and reserve
```

Do not run storage clusters close to 100% capacity. Keep operational headroom for:

- Rebalancing
- Recovery
- Backfill
- Snapshots/clones
- Temporary workload spikes
- Node replacement
- OSD expansion

### Storage capacity checklist

- Raw disk count and size
- Usable capacity after replication/erasure coding
- Failure-domain overhead
- Snapshot growth
- Log growth
- Object bucket growth
- Rebuild time after disk or node failure
- Maintenance reserve
- Performance reserve

## 18. Performance Planning

Storage node performance depends on the slowest layer:

```text
Application -> PVC -> CSI -> Node network -> Storage backend -> Disk/device
```

### Key performance factors

| Factor | Why It Matters |
|---|---|
| Disk type | SSD/NVMe generally provides lower latency than HDD. |
| Disk count | More OSDs/disks can increase parallelism. |
| CPU | Ceph, encryption, compression, and checksumming need CPU. |
| Memory | OSDs and storage daemons need stable memory. |
| Network | Replication and client I/O depend heavily on network throughput. |
| Failure domains | Poor placement can reduce resilience and performance. |
| Noisy neighbors | App pods can steal CPU, memory, and network. |
| Recovery settings | Backfill/recovery can impact normal I/O. |

### Practical tuning rules

- Prefer dedicated disks for storage services.
- Avoid mixing slow and fast disks in the same performance pool unless intentionally tiered.
- Keep storage network latency low and predictable.
- Do not oversubscribe storage nodes like generic app nodes.
- Reserve CPU and memory for system and storage daemons.
- Monitor disk latency, not only disk utilization.
- Benchmark with realistic block sizes and read/write ratios.

## 19. Network Planning for Storage Nodes

Storage traffic can be heavy because replicated storage writes data multiple times.

Important network considerations:

- East-west bandwidth between storage nodes
- Latency between zones/racks
- MTU consistency
- NIC bonding/team configuration
- NetworkPolicy impact
- SDN/OVN overlay overhead
- Storage backend endpoint reachability
- DNS health
- Firewall rules

Useful commands:

```bash
oc get nodes -o wide
oc debug node/<node>
chroot /host
ip addr
ip route
nmcli con show
ethtool <interface>
exit
```

For application symptoms, test from inside the cluster:

```bash
oc run nettest --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk <service-or-route>
getent hosts <service-name>
```

## 20. Upgrade and Maintenance Strategy

Storage nodes require controlled maintenance.

### MCO behavior

During machine configuration updates, nodes in an MCP are drained, updated, rebooted, and uncordoned according to `maxUnavailable`. The default is normally conservative. For storage pools, `maxUnavailable: 1` is usually the safest default.

### Storage node update checklist

Before maintenance:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pods -n openshift-storage -o wide
oc get cephcluster -n openshift-storage -o yaml 2>/dev/null || true
```

Check ODF/Ceph health:

```bash
oc rsh -n openshift-storage deploy/rook-ceph-tools
ceph status
ceph osd tree
ceph health detail
exit
```

During maintenance:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=20m
```

After maintenance:

```bash
oc adm uncordon <node>
oc get nodes
oc get pods -n openshift-storage -o wide
```

Never reboot multiple storage nodes at the same time unless the storage product documentation and current cluster health clearly allow it.

## 21. Scaling Storage Node Pools

Scaling can mean two different things:

### Scale out

Add more storage nodes.

```text
3 storage nodes -> 6 storage nodes
```

Benefits:

- More failure-domain options
- More CPU/memory/network capacity
- More OSD placement options
- Better parallelism

Risks:

- Rebalance traffic
- Incorrect labels/taints
- Device discovery issues
- Uneven capacity if disk sizes differ

### Scale up

Add more disks or larger disks to existing storage nodes.

```text
Each storage node: 3 disks -> 6 disks
```

Benefits:

- More capacity without adding nodes
- Lower node count

Risks:

- Larger failure impact per node
- Longer recovery times
- Possible disk/controller bottlenecks

### Scaling checklist

```bash
oc get nodes -l node-role.kubernetes.io/storage=
oc get pv
oc get pvc -A
oc get storageclass
oc get pods -n openshift-storage -o wide
```

For ODF, always verify storage cluster health before and after scaling.

## 22. Draining Storage Nodes Safely

Storage node drain is more sensitive than app node drain.

### Before drain

Check:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node>
oc get pdb -A
oc get mcp
oc get co
```

For ODF:

```bash
oc rsh -n openshift-storage deploy/rook-ceph-tools
ceph status
ceph osd tree
ceph health detail
exit
```

### Drain command

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=30m
```

### If drain is stuck

Common causes:

- PodDisruptionBudget blocks eviction
- Static/mirror pods
- DaemonSets ignored but still shown
- Finalizers
- Storage operator protection
- Local PV workload cannot move
- StatefulSet has single replica

Debug:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
oc get events -A --sort-by=.lastTimestamp | tail -50
oc describe pod <pod> -n <namespace>
oc get pdb -A
```

Do not force-delete storage pods unless you understand the impact.

## 23. Observability for Storage Node Pools

A storage pool should be monitored at three layers.

### Node layer

- CPU pressure
- Memory pressure
- Disk pressure
- Filesystem usage
- Disk latency
- Network errors/drops
- Reboot count
- Kubelet health
- CRI-O health

### Kubernetes layer

- Pod restarts
- Pending pods
- PVC pending/bound status
- PV reclaim status
- CSI errors
- Scheduler events
- DaemonSet availability
- PDB violations

### Storage backend layer

For ODF/Ceph:

- Ceph health
- OSD up/in status
- PG health
- Recovery/backfill status
- MON quorum

## 24. Security Considerations

Storage nodes are sensitive because they can contain application data.

### Security checklist

- Use least-privilege RBAC for storage administration.
- Restrict who can add tolerations to storage-tainted nodes.
- Restrict who can create privileged pods or hostPath mounts.
- Monitor SCC usage.
- Keep SELinux enforcing unless vendor documentation requires otherwise.
- Encrypt data where required.
- Protect storage admin secrets.
- Use NetworkPolicy where supported and tested.
- Avoid running untrusted workloads on storage nodes.
- Audit node debug usage.

### Dangerous permissions

Be careful with users who can:

- Patch nodes
- Add taints/labels
- Create privileged pods
- Use `hostPath`
- Access `openshift-storage` secrets
- Modify StorageClasses
- Delete PVs or PVCs
- Patch finalizers

A user with these permissions can cause storage outage or data exposure.

## 25. Common Problems and Troubleshooting

### Problem 1: ODF pods are Pending

Check:

```bash
oc get pods -n openshift-storage -o wide
oc describe pod <pod> -n openshift-storage
oc get nodes --show-labels | grep -E 'storage|ocs|infra'
oc describe node <node> | grep -A5 Taints
```

Common causes:

- Missing `cluster.ocs.openshift.io/openshift-storage` label
- Missing toleration for storage taint
- Insufficient CPU/memory
- Wrong namespace node selector
- Node not Ready
- Disk discovery failed
- Zone/failure-domain rules not satisfied

Fix direction:

```bash
oc label node <node> cluster.ocs.openshift.io/openshift-storage=""
oc adm taint node <node> node.ocs.openshift.io/storage=true:NoSchedule
oc annotate namespace openshift-storage openshift.io/node-selector=
```

---

### Problem 2: PVC remains Pending

Check:

```bash
oc get pvc -A
oc describe pvc <pvc> -n <namespace>
oc get storageclass
oc get pv
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common causes:

- StorageClass not found
- Wrong default StorageClass
- Local PV node affinity mismatch
- Immediate binding selected wrong PV
- No available PV capacity
- CSI provisioner not running
- Application pod cannot schedule due to taints

Fix direction:

- Use correct StorageClass.
- Prefer `WaitForFirstConsumer` for local/zonal storage.
- Validate PV node affinity.
- Ensure application pod tolerations and node selectors match the intended node pool.

---

### Problem 3: CSI node plugin missing from storage nodes

Check:

```bash
oc get ds -A | grep -i csi
oc get pods -A -o wide | grep -i csi
oc describe ds <driver-nodeplugin> -n <driver-namespace>
oc describe node <storage-node> | grep -A5 Taints
```

Common cause:

```text
Storage node has taint, but CSI DaemonSet has no matching toleration.
```

Fix direction:

- Add supported toleration configuration for the CSI driver/operator.
- Do not manually edit operator-managed DaemonSets unless vendor documentation supports it.

---

### Problem 4: MachineConfigPool storage is Degraded

Check:

```bash
oc get mcp
oc describe mcp storage
oc get machineconfig
oc get nodes
oc describe node <node>
```

Common causes:

- Bad MachineConfig syntax
- Invalid file content or path
- Node reboot failure
- MCD cannot apply config
- Conflicting MachineConfigs
- Node stuck NotReady

Debug node:

```bash
oc debug node/<node>
chroot /host
journalctl -u machine-config-daemon --no-pager | tail -100
exit
```

Fix direction:

- Roll back bad MachineConfig.
- Wait for MCO reconciliation.
- Do not delete rendered MachineConfigs manually unless directed by support.

---

### Problem 5: Storage node has DiskPressure

Check:

```bash
oc describe node <node> | egrep -i 'DiskPressure|ephemeral|imagefs|nodefs'
oc debug node/<node>
chroot /host
df -h
podman system df
journalctl --disk-usage
exit
```

Common causes:

- Container logs too large
- Image garbage collection not keeping up
- `/var` filling up
- OSD or local disk incorrectly placed on root disk
- Application emptyDir usage

Fix direction:

- Clean unused images carefully.
- Fix log rotation.
- Increase root filesystem if required.
- Ensure storage data disks are separate from OS disk.

## 28. Interview and Real-World Explanation

If asked in an interview, answer like this:

> A storage node pool is a dedicated set of OpenShift worker nodes designed for persistent storage services such as ODF, Ceph, Local Storage, and CSI components. I create it using node labels for attraction, taints for isolation, tolerations for approved storage pods, and usually a custom MachineConfigPool for storage-specific node configuration. If the cluster uses Machine API, I put labels and taints into the MachineSet template so replacement nodes inherit the same identity. For ODF, I make sure storage nodes have the correct ODF labels and storage taint, validate CSI plugin tolerations, and spread nodes across failure domains. I keep `maxUnavailable` conservative because storage nodes should not reboot in bulk. I also validate PVC provisioning, PV node affinity, StorageClass binding mode, and ODF/Ceph health before and after maintenance.

## 29. Exam-Focused Points

For Advanced OpenShift Administration, remember these points:

1. A storage node pool is implemented through labels, taints, tolerations, node selectors, and optionally a custom MCP.
2. Labels alone do not isolate nodes; taints are needed to repel unwanted workloads.
3. Taints alone do not attract storage pods; storage pods need node selectors or affinity.
4. MachineSet templates are better than manual labels for Machine API managed nodes.
5. Keep the worker label on custom worker-derived pools.
6. Custom MCPs inherit worker MachineConfigs.
7. A node belongs to only one MCP; custom pools can take priority over default worker pool selection.
8. ODF commonly uses `cluster.ocs.openshift.io/openshift-storage` and `node.ocs.openshift.io/storage=true:NoSchedule`.
9. Storage taints can break DaemonSets if tolerations are missing.
10. CSI node plugins must run on nodes that need to mount CSI volumes.
11. Local PVs require careful node affinity and `WaitForFirstConsumer` behavior.
12. Never drain or reboot multiple storage nodes blindly.
13. Always check storage health before maintenance.
14. For ODF/local storage, disk type, size, and failure-domain layout matter.
15. PVC Pending issues often come from StorageClass, PV node affinity, taints, tolerations, or node selector mismatch.

## 31. Best Practices

- Use a dedicated storage node pool for production ODF or heavy persistent storage.
- Spread storage nodes across zones/racks/failure domains.
- Keep worker label unless explicitly instructed otherwise.
- Put labels and taints in MachineSet templates when using Machine API.
- Use a custom MCP for storage-specific node configuration.
- Keep `maxUnavailable: 1` unless a tested maintenance process supports more.
- Use `NoSchedule` taints for strong isolation.
- Avoid broad tolerations in application workloads.
- Validate CSI node plugin tolerations after tainting nodes.
- Use stable disk identifiers for local storage.
- Prefer `WaitForFirstConsumer` for topology-sensitive storage.
- Monitor capacity, latency, OSD health, and CSI health.
- Do not run untrusted workloads on storage nodes.
- Test node replacement before production go-live.
- Document drain, reboot, scale, and disk replacement runbooks.

## 32. Anti-Patterns

Avoid these mistakes:

```text
Manual labels on MachineSet-managed nodes only
```

Replacement nodes will lose the labels.

```text
Storage nodes without taints
```

Application workloads can land on storage nodes.

```text
Taints without tolerations
```

Storage and CSI pods can become Pending.

```text
All storage nodes in one zone
```

Zone failure can take storage down.

```text
Removing worker role label
```

Can break expected worker-derived management behavior.

```text
Using root disk for storage data
```

Can cause DiskPressure and node instability.

```text
Draining multiple storage nodes together
```

Can reduce or break data availability.

```text
Ignoring PVC binding mode
```

Can cause pod/PVC scheduling deadlocks.

```text
Giving app teams blanket tolerations
```

Bypasses dedicated pool isolation.

## 33. Simple Mental Model

Remember this model:

```text
Labels      = identify storage nodes
Taints      = protect storage nodes
Tolerations = allow approved storage pods
MCP         = configure storage node OS/kubelet behavior
MachineSet  = preserve labels/taints during node lifecycle
StorageClass= control provisioning and topology behavior
Monitoring  = detect capacity, health, and performance problems
Runbooks    = safely maintain storage without data loss
```

If any layer is missing, the storage node pool is incomplete.

A storage node pool is a production-grade isolation boundary for persistent storage services.
