# Cluster Partitioning Concept in OpenShift

**Topic:** Cluster Partitioning and Dedicated Node Pools  
**Audience:** Advanced OpenShift Administration / 10+ years Linux, Kubernetes, and platform operations experience  
**Focus:** How to design, implement, operate, and troubleshoot logical workload partitions and dedicated node pools in Red Hat OpenShift.

---

## 1. Executive Summary

Cluster partitioning is the practice of dividing one OpenShift cluster into clearly defined compute areas so that different categories of workloads run on the right nodes, with the right lifecycle, isolation, performance profile, cost model, and operational controls.

In OpenShift, cluster partitioning is usually implemented by combining:

- **Node labels** to classify nodes.
- **Taints and tolerations** to repel or allow workloads.
- **Node selectors** to force workloads into a partition.
- **Node affinity and anti-affinity** to express hard or soft placement rules.
- **Topology spread constraints** to distribute replicas across nodes, racks, zones, or custom domains.
- **MachineSets / MachinePools** to create and scale groups of similar nodes.
- **MachineConfigPools** to manage OS and kubelet configuration per node role.
- **Operator-specific node placement** for routers, registry, monitoring, logging, storage, virtualization, and other platform services.
- **Quotas, LimitRanges, PodDisruptionBudgets, priority classes, and autoscaling** to make the partition operationally safe.

A well-partitioned OpenShift cluster is not simply a cluster with labels. It is a platform design where each workload class has an intentional landing zone, ownership model, capacity plan, upgrade behavior, and failure-domain strategy.

---

## 2. What “Cluster Partitioning” Means

Cluster partitioning means logically dividing a single cluster into workload placement zones. Each partition is normally represented by a dedicated node pool or node role.

Examples:

| Partition | Purpose |
|---|---|
| `infra` | Routers, registry, monitoring, logging, platform services |
| `app-general` | Standard stateless application workloads |
| `app-critical` | High-SLA production applications |
| `logging` | Elasticsearch/Loki/collector-heavy workloads |
| `monitoring` | Prometheus, Alertmanager, Thanos, metrics workloads |
| `storage` | ODF/Ceph/storage-heavy workloads |
| `gpu` | AI/ML or GPU workloads |
| `build` | CI/CD build pods and temporary high-churn workloads |
| `secure` | Regulated workloads requiring tighter scheduling control |
| `edge` | Workloads pinned to site-specific or location-specific nodes |
| `realtime` | Low-latency workloads using tuned profiles and CPU isolation |

Partitioning does **not** necessarily mean creating multiple clusters. It means using one cluster while making node groups behave like separate operational pools.

---

## 3. What Cluster Partitioning Is Not

A senior administrator should be clear about this distinction.

Cluster partitioning is **not** the same as:

| Concept | Difference |
|---|---|
| Namespace isolation | Namespaces isolate Kubernetes API objects; they do not automatically isolate compute placement. |
| RBAC | RBAC controls who can do what; it does not decide where pods run. |
| NetworkPolicy | NetworkPolicy controls traffic; it does not reserve nodes. |
| Multi-cluster strategy | Multi-cluster separates control planes; partitioning separates workload placement inside one cluster. |
| Security boundary equivalent to separate clusters | Node partitioning helps reduce blast radius, but hard security isolation might still require separate clusters. |
| Merely adding labels | Labels describe nodes; enforcement requires selectors, affinity, taints, tolerations, admission controls, and governance. |

A common mistake is assuming: “I labeled nodes as infra, so only infra pods will run there.” That is false unless scheduling policy prevents normal user workloads from landing there.

## 4. Why Cluster Partitioning Matters

In a small lab cluster, all workloads might run on worker nodes without major problems. In production, this becomes risky.

Partitioning is used to solve these operational problems:

### 4.1 Noisy Neighbor Control

A heavy application pod can consume CPU, memory, disk I/O, network bandwidth, or PID limits and affect unrelated workloads on the same node.

Examples:

- A logging stack consumes high disk I/O.
- A CI build pod pulls large images and fills image cache.
- A JVM application causes memory pressure and node evictions.
- A batch job consumes all CPU cycles.
- A bad workload creates too many files, sockets, or processes.

Partitioning keeps such workloads away from sensitive workloads.

### 4.2 Platform Stability

OpenShift platform components such as routers, monitoring, logging, and registry are critical to the whole cluster. If user workloads compete with them, platform reliability suffers.

For example:

- If router pods are starved, routes become slow or unavailable.
- If Prometheus is starved, alerting and metrics become unreliable.
- If logging is starved, audit and troubleshooting visibility is reduced.
- If registry is starved, builds and deployments can fail.

This is why many production clusters use dedicated infrastructure nodes.

### 4.3 Performance Consistency

Some workloads need predictable latency, CPU availability, storage throughput, or network throughput.

Examples:

- Telco workloads.
- Financial trading services.
- Database workloads.
- OpenShift Virtualization VM workloads.
- AI/ML inference services.
- High-throughput API gateways.

Partitioning lets administrators choose node types, CPU topology, storage layout, NIC features, and tuning profiles per workload category.

### 4.4 Cost and Subscription Control

OpenShift infrastructure nodes that run only eligible infrastructure workloads can be treated differently from normal application worker nodes from a subscription planning perspective. For this to be safe, administrators must make sure user workloads do not land on those nodes.

### 4.5 Security and Compliance

Certain workloads may require:

- Dedicated hosts.
- Restricted node access.
- Specific encryption or storage configuration.
- No co-location with lower-trust workloads.
- Dedicated ingress path.
- Dedicated egress path.
- Separate logging pipeline.
- Separate runtime configuration.

Partitioning supports compliance design, but it must be combined with RBAC, SCC/Pod Security Admission, NetworkPolicy, audit policy, image policy, and secret management.

### 4.6 Upgrade and Maintenance Control

Different node pools can have different operational handling:

- Drain infra nodes carefully to preserve routers and monitoring.
- Upgrade GPU nodes only after validating drivers.
- Reboot performance-sensitive pools in a controlled window.
- Keep storage nodes under stricter disruption controls.
- Use MachineConfigPools to control OS-level changes per role.

## 5. Core Mental Model

Think of OpenShift cluster partitioning as four layers.

```text
+--------------------------------------------------------------+
| Governance Layer                                             |
| RBAC, quotas, admission, policies, project selectors         |
+--------------------------------------------------------------+
| Scheduling Layer                                             |
| nodeSelector, affinity, taints/tolerations, topology spread  |
+--------------------------------------------------------------+
| Node Pool Layer                                              |
| MachineSets, MachinePools, autoscaling groups, zones         |
+--------------------------------------------------------------+
| Node Configuration Layer                                     |
| MachineConfigPools, kubelet config, tuned profiles, OS config|
+--------------------------------------------------------------+
```

If any layer is missing, the partition may look correct but fail operationally.

Example:

- You create infra nodes with labels but no taint. User pods may still run there.
- You create a taint but forget tolerations for routers. Router pods stay Pending.
- You create node selectors but forget capacity planning. Application pods stay Pending.
- You create a custom role but no MachineConfigPool. Nodes may be unmanaged or managed by the wrong pool.
- You create zone-based partitions but storage is not available in every zone. Pods may fail with volume node affinity errors.

## 6. Partitioning Versus Dedicated Node Pools

The two terms are related but not identical.

### 6.1 Cluster Partitioning

Cluster partitioning is the **architecture** and **policy**.

It answers:

- Which workload classes exist?
- Which workloads can share nodes?
- Which workloads must never share nodes?
- Which nodes are for platform services?
- Which workloads need special hardware?
- Which pools require separate upgrade windows?
- Which pools require separate autoscaling rules?
- Which teams own each pool?

### 6.2 Dedicated Node Pools

Dedicated node pools are the **implementation unit**.

They answer:

- How many nodes are in this pool?
- What instance type or bare-metal profile is used?
- Which labels are applied?
- Which taints are applied?
- Which MachineSet or MachinePool controls them?
- Which MachineConfigPool manages their OS configuration?
- Which autoscaler rules apply?

In short:

```text
Cluster partitioning = design strategy
Dedicated node pool  = concrete compute group used to enforce the strategy
```

## 7. OpenShift-Specific Building Blocks

### 7.1 Node Labels

Labels classify nodes.

Examples:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
oc label node worker-1 workload.openshift.io/class=infra
oc label node worker-2 workload.openshift.io/class=app-critical
oc label node worker-3 hardware.openshift.io/gpu=true
oc label node worker-4 topology.company.com/rack=rack-a
```

Important points:

- Labels are matching keys for node selectors and affinity.
- Labels alone do not prevent workloads from landing on a node.
- Node role labels such as `node-role.kubernetes.io/worker` and `node-role.kubernetes.io/infra` have OpenShift operational meaning.
- Labels added directly to a node may not survive node replacement. For machine-managed clusters, apply labels through MachineSets, MachinePools, or automation.

### 7.2 Taints

Taints repel pods.

Example:

```bash
oc adm taint node worker-infra-1 node-role.kubernetes.io/infra=reserved:NoSchedule
```

Meaning:

- This node refuses normal pods.
- Only pods with a matching toleration can be scheduled there.
- Existing pods can remain if the effect is `NoSchedule`.

Common taint effects:

| Effect | Meaning |
|---|---|
| `NoSchedule` | New pods cannot schedule unless they tolerate the taint. Existing pods remain. |
| `PreferNoSchedule` | Scheduler tries to avoid the node but it is not a hard rule. |
| `NoExecute` | New pods cannot schedule and existing pods can be evicted unless they tolerate it. |

### 7.3 Tolerations

Tolerations allow a pod to run on tainted nodes.

Example:

```yaml
spec:
  tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Equal
      value: reserved
      effect: NoSchedule
```

A toleration does **not** force the pod onto that node. It only permits scheduling there. To force or prefer placement, combine toleration with `nodeSelector` or node affinity.

### 7.4 Node Selectors

A node selector is a hard requirement.

Example:

```yaml
spec:
  nodeSelector:
    workload.openshift.io/class: app-critical
```

This pod can only run on nodes with that exact label.

Use node selectors when:

- The rule is simple.
- The placement requirement is strict.
- You want predictable behavior.

Avoid overusing node selectors when:

- The cluster has many dimensions such as zone, hardware, lifecycle, cost, compliance.
- You need soft preferences.
- You need fallback behavior.

### 7.5 Node Affinity

Node affinity is more expressive than node selectors.

Hard node affinity:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: workload.openshift.io/class
                operator: In
                values:
                  - app-critical
```

Preferred node affinity:

```yaml
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: cost.company.com/tier
                operator: In
                values:
                  - standard
```

Use hard affinity for compliance and strict placement. Use preferred affinity for optimization and cost-aware scheduling.

### 7.6 Pod Affinity and Anti-Affinity

Pod affinity places pods near other pods. Pod anti-affinity keeps pods apart.

Example: keep replicas away from each other on different nodes.

```yaml
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app: payments-api
            topologyKey: kubernetes.io/hostname
```

Use anti-affinity carefully. Hard anti-affinity can make pods Pending if the cluster does not have enough eligible nodes.

### 7.7 Topology Spread Constraints

Topology spread constraints distribute replicas across failure domains such as nodes, zones, racks, or custom topology keys.

Example:

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels:
          app: payments-api
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: ScheduleAnyway
      labelSelector:
        matchLabels:
          app: payments-api
```

This is useful for high availability because it prevents all replicas from landing on the same node or zone.

### 7.8 Project-Wide Node Selectors

OpenShift can constrain all pods in a project to specific nodes using the namespace annotation:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: prod-payments
  annotations:
    openshift.io/node-selector: "workload.openshift.io/class=app-critical"
```

This is powerful for multi-tenant administration because application teams do not need to remember placement rules in every Deployment.

Important behavior:

- Project node selectors are applied to pods in that namespace.
- A project node selector can take precedence over a cluster-wide default node selector.
- A pod can fail admission if its node selector conflicts with the project node selector.

### 7.9 Cluster-Wide Default Node Selector

OpenShift can define a cluster-wide default node selector in the Scheduler object:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: workload.openshift.io/class=app-general
  mastersSchedulable: false
```

Use this carefully. It affects workloads that do not explicitly override placement and can accidentally block system or user pods if node labels are incomplete.

### 7.10 MachineSet

A MachineSet manages machines for a specific infrastructure provider and usually maps to a zone and instance type.

Use MachineSets to define:

- Replica count.
- Instance type.
- Availability zone.
- Provider-specific configuration.
- Node labels at creation time.
- Node taints at creation time.

For example, in AWS you often create one MachineSet per zone for each node pool.

```text
app-critical-us-east-1a
app-critical-us-east-1b
app-critical-us-east-1c
infra-us-east-1a
infra-us-east-1b
infra-us-east-1c
```

### 7.11 MachinePool

In managed OpenShift offerings, such as OpenShift Dedicated or ROSA, administrators often manage compute through MachinePools rather than directly through MachineSets.

MachinePools represent a higher-level abstraction over compute pools and commonly allow:

- Scaling.
- Labels.
- Taints.
- Instance type selection.
- Autoscaling controls.

The exact options depend on the OpenShift platform and service type.

### 7.12 MachineConfigPool

A MachineConfigPool controls how MachineConfig changes are applied to selected nodes.

Use MachineConfigPools for:

- Custom kubelet configuration.
- OS-level configuration.
- Kernel arguments.
- CRI-O configuration.
- File injection.
- Systemd units.
- Tuned/performance-related changes when combined with the right operators.
- Controlled reboot/update behavior per node role.

A node should be managed by exactly one MachineConfigPool.

Example custom MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Senior-level note:

- Do not casually remove the `worker` role label from infra nodes.
- If a node has only a custom role and no matching custom MCP, it can become unmanaged by the Machine Config Operator.
- A dual role such as `worker,infra` is common; taints and tolerations enforce workload placement.

## 8. Common Partitioning Designs

### 8.1 Basic Production Design

```text
Control Plane Nodes
  - Kubernetes API
  - etcd
  - controllers
  - scheduler

Infrastructure Nodes
  - ingress/router
  - registry
  - monitoring
  - logging collectors or aggregators

Application Worker Nodes
  - normal application workloads

Storage Nodes
  - ODF/Ceph/Local Storage workloads
```

This is the most common design for medium production clusters.

### 8.2 Advanced Enterprise Design

```text
control-plane
infra-router
infra-monitoring
infra-logging
app-prod-critical
app-prod-general
app-nonprod
build-ci
storage-odf
gpu-ai
secure-regulated
virtualization
```

This design is used when platform teams need strict control over capacity, maintenance, and workload behavior.

### 8.3 Zone-Aware Partitioning

For highly available clusters, create node pool replicas across zones.

Example:

```text
infra-a   infra-b   infra-c
app-a     app-b     app-c
storage-a storage-b storage-c
```

Benefits:

- Node failure does not remove an entire workload class.
- Zone failure can be tolerated if applications have enough replicas.
- Storage volume placement can match compute placement.
- Routers and monitoring can survive a zone outage.

Mistake to avoid:

```text
All infra nodes in zone-a only
```

If zone-a fails, ingress, registry, monitoring, and logging may fail together.

### 8.4 Security Partitioning

Security partitioning is used when certain workloads need stronger isolation.

Example:

```text
secure nodes:
  labels:
    security.company.com/tier=restricted
  taints:
    security.company.com/restricted=true:NoSchedule

normal app nodes:
  labels:
    security.company.com/tier=standard
```

Workloads in restricted namespaces receive:

- Project node selector.
- Required toleration.
- NetworkPolicy.
- Strict RBAC.
- Strict SCC/Pod Security Admission controls.
- Dedicated egress controls.
- Dedicated monitoring labels.

### 8.5 Performance Partitioning

For low-latency or high-throughput workloads:

```text
performance nodes:
  dedicated CPU topology
  tuned profile
  hugepages
  SR-IOV capable NICs
  CPU manager static policy
  NUMA-aware configuration
  no noisy workloads
```

Do not mix random workloads with performance-sensitive workloads. Even if Kubernetes resource requests look correct, kernel scheduling, interrupt handling, disk I/O, and network I/O can still create noise.

### 8.6 Build and CI Partitioning

Build workloads are often bursty and high churn.

Partitioning them helps prevent:

- Image pull pressure on app nodes.
- Disk pressure from temporary layers.
- CPU starvation.
- Pod churn affecting production apps.
- Security risk from untrusted build steps.

Example:

```text
build nodes:
  labels:
    workload.openshift.io/class=build
  taints:
    workload.openshift.io/build=true:NoSchedule
```

CI workloads tolerate the taint and select the build nodes.

### 8.7 GPU Partitioning

GPU nodes should almost always be partitioned.

Reasons:

- Expensive hardware.
- Specialized drivers.
- Device plugin requirements.
- Different upgrade risk.
- Different autoscaling model.
- Different monitoring requirements.

Example:

```text
gpu nodes:
  labels:
    hardware.openshift.io/gpu=true
    accelerator.company.com/type=nvidia-a100
  taints:
    nvidia.com/gpu=true:NoSchedule
```

GPU workloads must have tolerations, node selectors, and GPU resource requests.

### 8.8 Storage Partitioning

Storage nodes require special care.

For ODF/Ceph or local storage:

- Keep enough nodes across zones.
- Avoid scheduling unrelated high-I/O workloads on storage nodes.
- Monitor disk pressure carefully.
- Respect storage operator placement recommendations.
- Avoid draining too many storage nodes at once.

Storage partitioning mistakes can cause data unavailability, slow recovery, or blocked upgrades.

### 8.9 Monitoring and Logging Partitioning

Monitoring and logging workloads have predictable but heavy resource profiles.

Monitoring:

- Prometheus uses memory and disk heavily.
- Query workloads can spike CPU.
- Retention settings affect storage.
- Alerting depends on monitoring availability.

Logging:

- Collectors run on many nodes.
- Aggregators or stores can consume high CPU, memory, and disk I/O.
- Log bursts can affect application nodes.

For critical clusters, dedicated monitoring/logging node pools are often better than placing these services on general infra nodes.

## 9. Partitioning Enforcement Patterns

### 9.1 Soft Placement

Soft placement means the scheduler prefers a pool but can fall back.

Use cases:

- Cost optimization.
- Non-critical workload preference.
- Gradual migration.
- Best-effort separation.

Example:

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 50
    preference:
      matchExpressions:
        - key: workload.openshift.io/class
          operator: In
          values:
            - app-general
```

Risk:

- Pods may land outside the intended pool when capacity is constrained.

### 9.2 Hard Placement

Hard placement means pods cannot run outside the target pool.

Use cases:

- Security.
- Licensing.
- Hardware requirements.
- Compliance.
- Storage topology.
- Infra nodes.

Example:

```yaml
nodeSelector:
  workload.openshift.io/class: secure
```

Risk:

- Pods stay Pending if the pool has no capacity.

### 9.3 Repel-and-Allow Pattern

This is the standard dedicated pool pattern.

```text
Node:
  label: workload.openshift.io/class=infra
  taint: node-role.kubernetes.io/infra=reserved:NoSchedule

Pod:
  nodeSelector: workload.openshift.io/class=infra
  toleration: node-role.kubernetes.io/infra=reserved:NoSchedule
```

Why both are needed:

- Taint prevents unwanted pods from landing on the node.
- Toleration allows intended pods to land there.
- Node selector or affinity attracts intended pods to that node.

Without the node selector, a pod with a broad toleration can still run elsewhere.

### 9.4 Namespace Default Placement Pattern

Use project node selectors for tenant-level placement.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-prod
  annotations:
    openshift.io/node-selector: "tenant.company.com/team=team-a,environment=prod"
```

This is useful when:

- You operate a shared OpenShift platform.
- Teams should not decide node placement themselves.
- You want namespace-level governance.

### 9.5 Operator Node Placement Pattern

Many OpenShift Operators expose placement configuration in their custom resources.

Examples:

- Ingress Operator: `IngressController` node placement.
- Image Registry Operator: registry deployment placement.
- Cluster Monitoring Operator: monitoring stack placement through `cluster-monitoring-config`.
- Logging Operator: logging component placement.
- OpenShift Data Foundation: storage placement.
- OpenShift Virtualization: virtualization workload placement.

Senior-level rule:

> Do not directly edit operator-managed Deployments unless the documentation explicitly allows it. Configure the owning custom resource instead.

## 10. Example: Infra Node Partition

### 10.1 Goal

Create dedicated infra nodes for router, registry, monitoring, and logging components.

### 10.2 Desired Behavior

- User workloads must not land on infra nodes.
- Infra workloads must be allowed to run on infra nodes.
- Infra nodes should be managed by a custom MCP if they require custom configuration.
- Infra nodes should exist across zones.
- Infra nodes should have enough CPU, memory, disk, and network capacity.

### 10.3 Label Infra Nodes

```bash
oc label node worker-infra-1 node-role.kubernetes.io/infra=
oc label node worker-infra-2 node-role.kubernetes.io/infra=
oc label node worker-infra-3 node-role.kubernetes.io/infra=
```

Optional custom label:

```bash
oc label node worker-infra-1 workload.openshift.io/class=infra
oc label node worker-infra-2 workload.openshift.io/class=infra
oc label node worker-infra-3 workload.openshift.io/class=infra
```

### 10.4 Taint Infra Nodes

```bash
oc adm taint node worker-infra-1 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint node worker-infra-2 node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint node worker-infra-3 node-role.kubernetes.io/infra=reserved:NoSchedule
```

### 10.5 Validate

```bash
oc get nodes -l node-role.kubernetes.io/infra
oc describe node worker-infra-1 | egrep -i 'Roles|Taints|Labels'
```

Expected:

```text
Roles: worker,infra
Taints: node-role.kubernetes.io/infra=reserved:NoSchedule
```

### 10.6 Important OpenShift Detail

Preserve the `worker` label unless you intentionally created a custom MachineConfigPool that manages the infra-only role. A dual `worker,infra` node is normal in OpenShift. The `infra` role communicates the node purpose, while the taint prevents normal user workloads.

## 11. Example: Application-Critical Node Pool

### 11.1 Node Labels and Taints

```bash
oc label node worker-prod-1 workload.openshift.io/class=app-critical
oc label node worker-prod-2 workload.openshift.io/class=app-critical
oc label node worker-prod-3 workload.openshift.io/class=app-critical

oc adm taint node worker-prod-1 workload.openshift.io/app-critical=true:NoSchedule
oc adm taint node worker-prod-2 workload.openshift.io/app-critical=true:NoSchedule
oc adm taint node worker-prod-3 workload.openshift.io/app-critical=true:NoSchedule
```

### 11.2 Namespace Selector

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: prod-payments
  annotations:
    openshift.io/node-selector: "workload.openshift.io/class=app-critical"
```

### 11.3 Deployment Placement

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: prod-payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      tolerations:
        - key: workload.openshift.io/app-critical
          operator: Equal
          value: "true"
          effect: NoSchedule
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payments-api
      containers:
        - name: payments-api
          image: registry.example.com/apps/payments-api:v1.0.0
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "2"
              memory: "2Gi"
```

The namespace selector forces the pod to app-critical nodes. The toleration allows use of tainted app-critical nodes. The topology spread rule distributes replicas across zones.

## 12. Example: MachineSet-Based Node Pool Design

For IPI clusters using the Machine API, prefer defining labels and taints in MachineSets so replacement nodes inherit the same partition identity.

Conceptual MachineSet snippet:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: app-critical-us-east-1a
  namespace: openshift-machine-api
spec:
  replicas: 2
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-machineset: app-critical-us-east-1a
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machineset: app-critical-us-east-1a
    spec:
      metadata:
        labels:
          workload.openshift.io/class: app-critical
          node-role.kubernetes.io/app-critical: ""
      taints:
        - key: workload.openshift.io/app-critical
          value: "true"
          effect: NoSchedule
      providerSpec:
        value:
          # Cloud or platform-specific provider configuration here
```

Why this matters:

- If a node is deleted, the replacement node gets the same labels and taints.
- Autoscaling does not create unpartitioned nodes.
- Drift is reduced.
- Troubleshooting is easier because node identity comes from the machine definition.

## 13. Example: Custom MachineConfigPool for a Dedicated Partition

### 13.1 Use Case

You need a custom kubelet or OS-level configuration for infra nodes.

### 13.2 Create MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values:
          - worker
          - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

## 14. How the Scheduler Evaluates Partitioned Workloads

When a pod is created, the scheduler roughly performs:

1. Identify nodes that are available and schedulable.
2. Remove nodes that do not match the pod node selector.
3. Remove nodes that do not satisfy required node affinity.
4. Remove nodes with taints that the pod does not tolerate.
5. Remove nodes that do not satisfy resource requests.
6. Evaluate volume topology constraints.
7. Evaluate pod affinity, anti-affinity, and topology spread constraints.
8. Score remaining nodes.
9. Bind the pod to the selected node.

In OpenShift, the default scheduler is responsible for choosing a suitable node and creating the pod-to-node binding through the API. Advanced scheduling features let administrators control where pods are required or preferred to run.

## 15. Partitioning Decision Matrix

Use this matrix before creating a node pool.

| Question | Why it matters |
|---|---|
| What workload class is this pool for? | Avoid vague pools that become dumping grounds. |
| Is the placement hard or preferred? | Determines selector/affinity strategy. |
| Should other workloads be repelled? | Determines taint strategy. |
| Which pods tolerate the taint? | Prevents accidental access. |
| Is the pool multi-zone? | Required for HA. |
| Does storage exist in those zones? | Prevents volume node affinity failures. |
| Does it need custom OS/kubelet config? | Determines MCP design. |
| Does it need autoscaling? | Determines MachineAutoscaler/ClusterAutoscaler design. |
| Who owns capacity? | Prevents app/platform team confusion. |
| How is it monitored? | Ensures capacity and SLO visibility. |
| What happens during upgrades? | Determines disruption controls. |
| What workloads are forbidden? | Helps define admission/policy controls. |

## 16. Capacity Planning for Partitions

A dedicated node pool should not be sized by guesswork.

### 16.1 Minimum Inputs

Collect:

- Number of pods.
- CPU requests and limits.
- Memory requests and limits.
- Storage requirements.
- Network throughput.
- Pod density.
- DaemonSet overhead.
- System-reserved and kube-reserved resources.
- Zone distribution.
- Peak usage.
- Growth rate.
- Upgrade surge requirement.
- Failure tolerance requirement.

### 16.2 Capacity Formula

At a basic level:

```text
required_pool_capacity = workload_requests
                       + daemonset_overhead
                       + platform_overhead
                       + upgrade_headroom
                       + failure_headroom
                       + growth_buffer
```

### 16.3 Senior-Level Rule

Do not size the pool only for current steady-state workload. Size for:

- One node down.
- Rolling deployment.
- Cluster upgrade.
- Node drain.
- Logging or monitoring burst.
- HPA scale-out.
- Zone outage if required by SLA.

### 16.4 Example

Application requires:

```text
9 replicas
Each replica requests 1 CPU and 2 Gi memory
3 zones
N+1 node failure tolerance
```

Minimum:

```text
9 CPU and 18 Gi memory for app only
+ DaemonSet overhead
+ system overhead
+ spare capacity for rescheduling if one node drains
+ extra capacity if HPA can scale above 9 replicas
```

If you only allocate exactly 9 CPU, the workload may run normally but fail during maintenance.

## 17. Governance and Tenant Control

Partitioning must be protected from accidental or intentional bypass.

### 17.1 RBAC

Restrict who can:

- Label nodes.
- Taint nodes.
- Edit MachineSets.
- Edit MachineConfigPools.
- Edit namespaces with node selector annotations.
- Create pods with broad tolerations.
- Use privileged SCCs.

Application teams usually should not have permission to add arbitrary tolerations that let them land on infra, storage, or secure nodes.

### 17.2 Quotas and LimitRanges

Dedicated pools can still be exhausted by one namespace.

Use:

- ResourceQuota.
- LimitRange.
- ClusterResourceQuota.
- Default requests.
- Maximum limits.

Example:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: prod-payments-quota
  namespace: prod-payments
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "50"
```

### 17.3 Admission Policy

Use policy controls to prevent:

- Workloads adding infra tolerations without approval.
- Workloads using `nodeName` directly.
- Privileged workloads running in normal pools.
- Missing resource requests.
- Deployments without topology spread or anti-affinity for critical apps.

Possible tools:

- Kubernetes ValidatingAdmissionPolicy.
- Gatekeeper/OPA.
- Kyverno, if approved in your environment.
- OpenShift-native admission and security mechanisms.

### 17.4 Avoid `.spec.nodeName`

A pod can bypass scheduler placement logic if `.spec.nodeName` is directly set. This is usually not appropriate for normal applications.

Restrict this pattern unless used by trusted platform components or controlled troubleshooting.

## 18. Failure Domains and High Availability

Partitioning must support HA, not break it.

### 18.1 Node Failure

If all replicas of an app land on one node, a single node failure can take the app down.

Use:

- Pod anti-affinity.
- Topology spread constraints.
- Multiple nodes per partition.
- PDBs.
- Proper requests.

### 18.2 Zone Failure

If all infra nodes are in one zone, a zone outage can break cluster ingress or monitoring.

Use:

- MachineSets per zone.
- Router replicas across zones.
- Monitoring replicas across zones where supported.
- Storage topology awareness.

### 18.3 Storage Topology

Persistent volumes can constrain where pods run. If a volume is bound in one zone but the pod is forced to another zone, the pod can remain Pending.

Common event:

```text
0/6 nodes are available: volume node affinity conflict
```

Fix:

- Align StorageClass topology with node pool topology.
- Create pools in all required zones.
- Use WaitForFirstConsumer where appropriate.
- Avoid hard node selectors that conflict with PV topology.

### 19.1 Node Pool Creation Flow

Recommended flow:

1. Define workload class and SLA.
2. Decide labels and taints.
3. Create or patch MachineSets/MachinePools.
4. Create custom MachineConfigPool if needed.
5. Configure autoscaling if needed.
6. Configure project node selectors.
7. Configure operator placement for platform workloads.
8. Deploy test workloads.
9. Validate scheduling.

11. Document ownership and runbooks.

Before scaling a pool:


Safe process:

1. Stop new workloads from landing there.
2. Remove namespace selectors or workload selectors pointing to the pool.

5. Remove MachineSet or scale to zero.


Be careful with storage, monitoring, logging, routers, and operator-managed pods.

## 20. Troubleshooting Cluster Partitioning

### 20.1 First Commands

```bash
oc get nodes --show-labels
oc get nodes -L node-role.kubernetes.io/worker,node-role.kubernetes.io/infra,workload.openshift.io/class
oc describe node <node>
oc get pods -A -o wide
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### 20.2 Pending Pod Checklist

If a pod is Pending, check:

1. Does the pod have a nodeSelector?
2. Does any node match the selector?
3. Does the pod have required node affinity?
4. Does any node satisfy affinity?
5. Are target nodes tainted?
6. Does the pod tolerate those taints?
7. Are there enough CPU and memory requests available?
8. Is there a PVC binding issue?
9. Is there a volume node affinity conflict?
10. Is topology spread too strict?
11. Is pod anti-affinity too strict?
12. Is namespace node selector conflicting with pod selector?
13. Is the node cordoned?
14. Is the node under pressure?
15. Is the MCP updating or degraded?

### 20.3 Common Scheduling Events

| Event message pattern | Meaning |
|---|---|
| `node(s) didn't match Pod's node affinity/selector` | Labels/selectors/affinity do not match. |
| `node(s) had untolerated taint` | Pod lacks required toleration. |
| `Insufficient cpu` | Not enough allocatable CPU for requests. |
| `Insufficient memory` | Not enough allocatable memory for requests. |
| `volume node affinity conflict` | PV topology conflicts with selected node. |
| `node(s) were unschedulable` | Nodes are cordoned or otherwise unschedulable. |
| `pod node label selector conflicts with its project node label selector` | Namespace selector conflicts with pod selector. |

### 20.4 Troubleshooting Taints

Check taints:

```bash
oc describe node <node> | grep -i Taints -A3
```

Check pod tolerations:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.tolerations'
```

Add a toleration to a Deployment:

```bash
oc patch deployment <deploy> -n <ns> --type='json' -p='[
  {
    "op":"add",
    "path":"/spec/template/spec/tolerations",
    "value":[
      {
        "key":"node-role.kubernetes.io/infra",
        "operator":"Equal",
        "value":"reserved",
        "effect":"NoSchedule"
      }
    ]
  }
]'
```

### 20.5 Troubleshooting Project Node Selectors

Check namespace annotations:

```bash
oc get namespace <ns> -o yaml | grep -A5 annotations
```

Patch selector:

```bash
oc annotate namespace <ns> openshift.io/node-selector='workload.openshift.io/class=app-critical' --overwrite
```

Remove selector:

```bash
oc annotate namespace <ns> openshift.io/node-selector- 
```

### 20.6 Troubleshooting MCP Issues

```bash
oc get mcp
oc describe mcp <pool>
oc get machineconfig | grep <role>
oc get nodes -l node-role.kubernetes.io/<role>
```

Warning signs:

```text
DEGRADED=True
UPDATING=True for too long
Node not matching expected MCP
Node stuck NotReady after reboot
```

### 20.7 Troubleshooting MachineSet Label Drift

If replacement nodes lose labels, check whether labels were applied only to the Node object and not to the MachineSet template.

```bash
oc get machineset -n openshift-machine-api <machineset> -o yaml | grep -A10 metadata:
```

Patch MachineSet template labels instead of manually fixing only the node.

## 21. Design Anti-Patterns

### 21.1 Label-Only Infra Nodes

Problem:

```text
Node has infra label, but no taint.
```

Result:

```text
User workloads can still land on infra nodes.
```

Fix:

```bash
oc adm taint node <node> node-role.kubernetes.io/infra=reserved:NoSchedule
```

Then configure tolerations for intended infra workloads.

### 21.2 Toleration Without Selector

Problem:

```text
Pod tolerates infra taint but has no nodeSelector.
```

Result:

```text
Pod may run on infra nodes or normal worker nodes.
```

Fix:

Use toleration plus node selector or node affinity.

### 21.3 Hard Anti-Affinity With Too Few Nodes

Problem:

```text
3 replicas require different hostnames, but only 2 eligible nodes exist.
```

Result:

```text
One pod remains Pending.
```

Fix:

- Add nodes.
- Relax anti-affinity to preferred.
- Use topology spread with appropriate `whenUnsatisfiable`.

### 21.4 Single-Zone Dedicated Pool

Problem:

```text
Critical workload partition exists only in one zone.
```

Result:

```text
Zone failure takes down all workloads in that partition.
```

Fix:

Create MachineSets across zones and use topology spread constraints.

### 21.5 Removing Worker Label Without MCP Planning

Problem:

```text
Admin removes worker label and applies custom role label only.
```

Result:

```text
Node may not be managed by the default worker MCP.
```

Fix:

Create a custom MachineConfigPool that selects the custom role, or preserve the worker label and use taints/tolerations for workload control.

### 21.6 Over-Partitioning

Problem:

```text
Too many small node pools.
```

Result:

- Fragmented capacity.
- More Pending pods.
- Poor bin-packing.
- More upgrades to manage.
- Higher cost.
- More operational complexity.

Fix:

Partition only when there is a clear operational, security, cost, or performance reason.

### 21.7 Under-Partitioning

Problem:

```text
Everything runs on generic workers.
```

Result:

- Noisy neighbors.
- Platform instability.
- Weak compliance story.
- Hard maintenance windows.
- Poor troubleshooting.

Fix:

At minimum, separate infrastructure/platform workloads from user application workloads in medium and large production clusters.

The exact configuration depends on OpenShift version and operator API. Always configure the owning operator or custom resource rather than editing managed pods directly.

### 23.1 Ingress Router Placement Concept

IngressController example pattern:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  replicas: 3
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Equal
        value: reserved
        effect: NoSchedule
```

### 23.2 Monitoring Placement Concept

Cluster monitoring is usually controlled through the `cluster-monitoring-config` ConfigMap.

Conceptual example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Equal
          value: reserved
          effect: NoSchedule
    alertmanagerMain:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Equal
          value: reserved
          effect: NoSchedule
```

### 23.3 Logging Placement Concept

Logging placement depends on the logging stack version and CRDs. The design principle is:

```text
collector pods: usually DaemonSet-style, may run broadly
logging store/query/frontend: often dedicated logging or infra nodes
```

Do not assume all logging components should run on the same nodes. Collectors often need node-wide coverage, while storage/query components need dedicated capacity.

### 23.4 Registry Placement Concept

The internal registry can be placed using the Image Registry Operator configuration, depending on version and platform support.

Design principle:

```text
registry pods -> infra nodes
registry storage -> highly available storage
registry route/service -> available during infra node maintenance
```

## 25. Upgrade and Maintenance Strategy

### 25.1 Why Partitions Affect Upgrades

OpenShift upgrades can reboot nodes when MachineConfig changes apply. If a dedicated pool has too few nodes or strict PDBs, upgrades can stall.

### 25.2 Pre-Upgrade Checks

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pdb -A
oc get pods -A --field-selector=status.phase=Pending
```

Check:

- MCPs are healthy.
- No nodes are degraded.
- PDBs will allow eviction.
- Dedicated pools have enough spare capacity.
- Storage pools are healthy.
- Router and monitoring replicas are distributed.

### 25.3 Drain Testing

Before production upgrades, test:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

Then validate whether workloads can move to remaining nodes.

### 25.4 PDB Awareness

A strict PDB can block node drains.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payments-api-pdb
  namespace: prod-payments
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payments-api
```

If replicas are only 2 and `minAvailable` is 2, no voluntary eviction is allowed. That can block maintenance.

## 28. Example End-to-End Design

### 28.1 Requirement

A production OpenShift cluster must support:

- Platform workloads.
- General applications.
- Critical payment applications.
- Logging stack.
- GPU workloads.
- Three availability zones.

|---|---:|---|---|

```text
prod-payments -> app-critical
prod-banking  -> app-critical
dev-general   -> app-general
logging       -> logging
ml-platform   -> gpu
```

### 28.4 Enforcement

- Namespace node selectors for app namespaces.
- Taints on reserved pools.
- Tolerations only in approved workloads.
- OPA/Gatekeeper policy prevents unauthorized tolerations.
- Topology spread constraints for critical apps.
- PDBs for critical apps.
- ResourceQuotas per namespace.
- MachineConfigPools for infra, app-critical, logging, gpu if they require different OS/kubelet configuration.

Expected:

- Infra pods run on infra nodes.
- Critical apps run only on app-critical nodes.
- Logging store runs on logging nodes.
- GPU workloads run only on GPU nodes.
- General apps do not land on reserved pools.
- No critical replicas are concentrated in one zone.

## 29. Exam and Interview-Level Explanation

If asked to explain cluster partitioning in an advanced OpenShift interview, answer like this:

> Cluster partitioning is the design of logical compute segments inside a single OpenShift cluster. We create dedicated node pools for workload classes such as infra, logging, monitoring, storage, GPU, build, and critical applications. The implementation uses labels to identify nodes, taints to repel unauthorized pods, tolerations to allow approved pods, and selectors or affinity to attract the right workloads. In OpenShift, MachineSets or MachinePools create and scale the nodes, and MachineConfigPools manage node-level configuration per role. For production, I also account for zone distribution, resource requests, PDBs, autoscaling, operator-specific node placement, RBAC, admission policies, and upgrade behavior. A good partition design prevents noisy neighbors, protects platform components, improves compliance, and makes maintenance predictable.

## 30. Interview Questions and Strong Answers

### Q1. Why are labels alone not enough for dedicated nodes?

Labels only describe nodes. They do not prevent other pods from scheduling there. To reserve a node pool, use taints to repel normal workloads and tolerations plus selectors or affinity for intended workloads.

### Q2. Why use both taint and nodeSelector?

A taint blocks unwanted pods. A toleration allows a pod to use the node. But toleration does not force placement. A nodeSelector or affinity attracts or forces the pod to the intended node pool.

### Q3. What is the risk of removing the worker label from infra nodes?

If the node no longer matches the worker MCP and no custom MCP selects the new role, the Machine Config Operator might not manage it correctly. In OpenShift, dual `worker,infra` labels are common, and taints/tolerations are used to prevent normal user workloads.

### Q4. How do you ensure replacement nodes keep partition labels?

Apply labels and taints at the MachineSet or MachinePool template level, not only directly on the Node object. Direct node changes can be lost when a node is replaced.

### Q5. How do you troubleshoot a pod that should run on infra nodes but is Pending?

Check pod events, node labels, taints, tolerations, node selector, node affinity, resource availability, namespace node selector, PVC topology, and whether nodes are cordoned or under pressure.

### Q6. When would you choose separate clusters instead of cluster partitioning?

Use separate clusters when isolation requirements exceed what node partitioning can provide, such as strict regulatory boundaries, different platform lifecycle requirements, different cluster administrators, hard blast-radius separation, or incompatible operator/runtime requirements.

### Step 5: Verify Placement

```bash
oc get pods -n prod-critical -o wide
oc describe pod -n prod-critical -l app=critical-nginx
```

Expected:

```text
All pods should run on nodes labeled workload.openshift.io/class=app-critical.
```

### Step 6: Negative Test

Create a normal pod without toleration in another namespace and verify it does not land on app-critical nodes.

```bash
oc new-project normal-test
oc run normal-nginx --image=registry.k8s.io/nginx
oc get pod -o wide
```

If the normal pod lands on app-critical nodes, your taints are missing or incorrect.

## 33. Key Takeaways

- Cluster partitioning is a production architecture practice, not just a Kubernetes scheduling trick.
- Labels identify nodes, but taints protect them.
- Tolerations permit scheduling but do not force placement.
- Use selectors or affinity to attract workloads to the correct pool.
- Use topology spread constraints to avoid single-node or single-zone concentration.
- In OpenShift, MachineSets/MachinePools define compute pools, while MachineConfigPools define node configuration lifecycle.
- Preserve OpenShift node management behavior when creating custom roles.
- Dedicated infra nodes should repel normal user workloads.
- Partitions must be capacity planned, monitored, upgraded, and governed.
- Over-partitioning creates waste; under-partitioning creates instability.
- Production partitioning should be managed through GitOps and policy, not manual node edits.

## 34. Quick Reference Commands

```bash
# Show labels
oc get nodes --show-labels

# Show selected labels as columns
oc get nodes -L workload.openshift.io/class,topology.kubernetes.io/zone

# Label a node
oc label node <node> workload.openshift.io/class=infra

# Remove a label
oc label node <node> workload.openshift.io/class-

# Taint a node
oc adm taint node <node> node-role.kubernetes.io/infra=reserved:NoSchedule

# Remove a taint
oc adm taint node <node> node-role.kubernetes.io/infra=reserved:NoSchedule-

# Check taints
oc describe node <node> | grep -i Taints -A3

# Project node selector
oc annotate namespace <ns> openshift.io/node-selector='workload.openshift.io/class=app-critical' --overwrite

# Remove project node selector
oc annotate namespace <ns> openshift.io/node-selector-

# View pod placement
oc get pods -A -o wide

# Check Pending pods
oc get pods -A --field-selector=status.phase=Pending

# Pod events
oc describe pod <pod> -n <ns>

# MachineSets
oc get machinesets -n openshift-machine-api

# MCP status
oc get mcp
oc describe mcp <pool>

# Drain test
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```
