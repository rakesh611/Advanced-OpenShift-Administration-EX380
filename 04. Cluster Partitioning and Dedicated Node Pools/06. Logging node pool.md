# Logging Node Pool in OpenShift Cluster Partitioning and Dedicated Node Pools

**Audience:** Advanced OpenShift Administration / DO380-style learning  
**Experience level:** Written for an administrator with around 10 years of Linux, DevOps, Kubernetes, and OpenShift experience  
**Focus area:** Cluster partitioning, dedicated node pools, logging workload isolation, scheduling, taints/tolerations, MachineConfigPool, ClusterLogForwarder, and LokiStack placement

---

## 1. Executive Summary

A **logging node pool** is a dedicated group of OpenShift worker nodes reserved for logging-related workloads such as LokiStack, logging gateways, query components, index components, and sometimes receiver-style collectors or log-processing components.

In a production OpenShift cluster, logging is not just another application. Logging has its own operational behavior:

- It receives continuous write traffic from every node and workload.
- It can create heavy CPU, memory, disk, object-storage, and network usage.
- It is often required during outages, incidents, compliance investigations, and upgrades.
- It can become noisy when applications generate excessive logs.
- It needs predictable scheduling and controlled failure domains.

A logging node pool helps isolate this behavior from normal application workloads.

In simple terms:

```text
Application node pool  -> business applications
Infra node pool        -> router, registry, monitoring, platform components
Logging node pool      -> log store, log query, log gateway, log processing components
Storage node pool      -> ODF/Ceph or storage-heavy services
```

A mature OpenShift administrator does not create a logging node pool only by adding labels. A complete design includes:

- Node labels
- Taints
- Tolerations
- Node selectors
- Affinity and anti-affinity
- MachineSets or manual node assignment
- MachineConfigPool when custom OS/kubelet configuration is needed
- Resource requests and limits
- Zone-aware placement
- Drain/upgrade behavior
- Troubleshooting procedures
- Observability of the logging system itself

## 2. What Is a Logging Node Pool?

A **logging node pool** is a logical and sometimes physical partition of worker nodes used for OpenShift logging workloads.

It can be created in several ways:

| Method | Meaning |
|---|---|
| Node labels | Mark selected nodes as logging nodes |
| Taints | Prevent normal workloads from landing on logging nodes |
| Tolerations | Allow logging workloads to run on tainted logging nodes |
| Node selectors | Force logging pods to run only on logging nodes |
| MachineSet | Automatically create logging-labeled worker machines |
| MachineConfigPool | Apply logging-specific OS or kubelet configuration |
| Affinity / anti-affinity | Spread logging components across zones or nodes |

A logging node pool is not a built-in OpenShift object named `LoggingNodePool`. It is an architectural pattern implemented using OpenShift and Kubernetes scheduling primitives.

## 3. Why Logging Needs a Dedicated Pool

### 3.1 Logging Is Write-Heavy

Logging components continuously ingest data. Even when application traffic is normal, log traffic can be high because every container, node service, router, operator, and system component may generate logs.

High-volume applications can suddenly increase log output due to:

- Debug mode accidentally enabled
- CrashLoopBackOff loops
- Application exception storms
- Bad health checks
- Router 4xx/5xx spikes
- Audit log spikes
- Repeated authentication failures
- Noisy sidecars

If logging storage and ingestion components share nodes with business applications, log pressure can indirectly affect application performance.

### 3.2 Logging Is Needed During Incidents

During a cluster incident, you need logs the most. If logging pods are competing with unstable application workloads on the same nodes, the logging system might degrade exactly when you need it.

Dedicated logging nodes help keep the log path alive during:

- Application storms
- Node pressure
- Router failure analysis
- Operator failure analysis
- API server investigation
- Audit/compliance checks
- Storage troubleshooting

### 3.3 Logging Has Different Sizing Requirements

Application nodes are usually sized around application CPU/memory. Logging nodes are sized around:

- Ingestion rate
- Query rate
- Retention period
- Object storage performance
- Burst capacity
- Memory needed for queries
- CPU needed for parsing, filtering, compression, and indexing
- Network throughput between collectors and log store

### 3.4 Logging Can Affect Subscription and Cost Planning

OpenShift infrastructure workloads are often treated differently from user workloads in sizing and subscription discussions. OpenShift documentation includes cluster aggregated logging among infrastructure components that can be moved to infrastructure nodes. If you create a separate logging pool, make sure your organization understands how it is accounted for in your licensing and capacity model.

### 3.5 Operational Boundary

A logging node pool creates a clean operational boundary:

```text
Application team problem?   Check app pool.
Platform issue?             Check infra pool.
Logging ingestion issue?    Check logging pool.
Storage issue?              Check storage pool.
```

This simplifies troubleshooting and capacity ownership.

## 4. OpenShift Logging Architecture Refresher

Modern OpenShift logging commonly uses:

- **Red Hat OpenShift Logging Operator**
- **ClusterLogForwarder** custom resource
- **Collector** pods
- **Loki Operator**
- **LokiStack** custom resource
- **Loki gateway** for authenticated access and multi-tenancy
- **Object storage** for Loki log storage
- Optional external outputs such as Splunk, Kafka, CloudWatch, syslog, HTTP, or S3-compatible targets

A simplified flow:

```text
Application / Node / Audit logs
        |
        v
Collector pods
        |
        v
ClusterLogForwarder pipelines
        |
        +--> LokiStack inside OpenShift
        +--> External SIEM / Splunk / Kafka / Cloud / Object storage
```

### 4.1 Collector

The collector is responsible for gathering log data and forwarding it according to the `ClusterLogForwarder` configuration.

Important advanced point:

> For normal cluster-wide application, infrastructure, and audit log collection, the collector must run on the nodes where logs are produced. Do not blindly restrict collectors only to logging nodes unless you intentionally want to collect logs only from those nodes or you are using a receiver-style design.

In many designs, you dedicate the **log store** to logging nodes, but allow the **collector DaemonSet** to run on all required nodes.

### 4.2 ClusterLogForwarder

`ClusterLogForwarder` defines:

- Service account used by collectors
- Log inputs
- Filters
- Outputs
- Pipelines
- Collector scheduling options
- Collector resource requests/limits

Reserved high-level input types include:

| Input | Purpose |
|---|---|
| `application` | User workload container logs |
| `infrastructure` | OpenShift/system namespace container logs and node journal logs |
| `audit` | API, OAuth, auditd, OVN audit logs |
| `receiver` | HTTP/syslog receiver-style collection |

### 4.3 LokiStack

`LokiStack` provides the in-cluster log store. It can include several components, such as:

- `compactor`
- `distributor`
- `gateway`
- `indexGateway`
- `ingester`
- `querier`
- `queryFrontend`
- `ruler`

These components can be scheduled to the logging node pool using `spec.template.<component>.nodeSelector` and `spec.template.<component>.tolerations`.

## 5. Logging Node Pool Design Models

### Model A: Shared Infra Pool for Logging

In smaller clusters, logging runs on the same pool as other infrastructure components.

```text
infra nodes:
  - router
  - registry
  - monitoring
  - logging
  - GitOps / pipelines / service mesh control plane, if allowed
```

Good for:

- Small production clusters
- Lab clusters
- Cost-sensitive environments
- Low to medium log volume

Risk:

- Monitoring and logging may compete for resources.
- Router traffic spikes can affect logging.
- Log query spikes can affect registry/router/monitoring.

### Model B: Dedicated Logging Pool

Logging has its own nodes.

```text
worker nodes  -> applications
infra nodes   -> router, registry, monitoring
logging nodes -> LokiStack and logging back-end components
```

Good for:

- Medium to large production clusters
- High log volume
- Compliance-driven environments
- Security audit retention
- Heavy log query usage
- Multi-tenant clusters

### Model C: External Logging Store

Collectors run in OpenShift, but the log store is external.

```text
OpenShift collector -> Splunk / Kafka / CloudWatch / Datadog / external Loki / SIEM
```

Good for:

- Enterprises with centralized logging
- Long-term retention outside OpenShift
- Security/SOC pipelines
- Multi-cluster log aggregation

In this model, a logging node pool may not be needed for LokiStack, but you still need collector resource planning on all nodes.

### Model D: Hybrid Recommended Production Pattern

A common mature design:

```text
Collectors             -> run on all required nodes
LokiStack components   -> run on dedicated logging nodes
Object storage         -> external or ODF-backed, depending on platform
Queries/gateway        -> logging nodes
Audit archive          -> external immutable storage
```

This pattern gives full cluster log coverage while isolating the heavy back-end components.

## 6. Core Scheduling Concepts for Logging Node Pools

### 6.1 Node Labels

Labels identify logging nodes.

Example:

```bash
oc label node worker-log-1 node-role.kubernetes.io/logging=""
oc label node worker-log-2 node-role.kubernetes.io/logging=""
oc label node worker-log-3 node-role.kubernetes.io/logging=""
```

Verify:

```bash
oc get nodes -l node-role.kubernetes.io/logging=
oc get nodes --show-labels | grep logging
```

You can also use custom labels:

```bash
oc label node worker-log-1 node-pool= logging
oc label node worker-log-1 workload.openshift.io/logging=true
```

A common enterprise style is:

```yaml
node-role.kubernetes.io/logging: ""
```

or:

```yaml
node-role.kubernetes.io/infra: ""
node-pool: logging
```

### 6.2 Taints

A taint repels pods unless those pods have matching tolerations.

Example:

```bash
oc adm taint nodes worker-log-1 node-role.kubernetes.io/logging=reserved:NoSchedule
oc adm taint nodes worker-log-2 node-role.kubernetes.io/logging=reserved:NoSchedule
oc adm taint nodes worker-log-3 node-role.kubernetes.io/logging=reserved:NoSchedule
```

Verify:

```bash
oc describe node worker-log-1 | grep -i taints -A3
```

A `NoSchedule` taint prevents new pods from landing there unless tolerated.

A `NoExecute` taint also evicts existing pods that do not tolerate it:

```bash
oc adm taint nodes worker-log-1 node-role.kubernetes.io/logging=reserved:NoExecute
```

Use `NoExecute` carefully. In production, first configure tolerations on logging components, then apply the taint.

### 6.3 Tolerations

Tolerations allow pods to run on tainted nodes.

Example toleration:

```yaml
tolerations:
- key: node-role.kubernetes.io/logging
  operator: Equal
  value: reserved
  effect: NoSchedule
```

or with `Exists`:

```yaml
tolerations:
- key: node-role.kubernetes.io/logging
  operator: Exists
  effect: NoSchedule
```

Advanced note:

- A toleration does **not** force a pod onto the logging node.
- It only allows scheduling there.
- Use `nodeSelector` or node affinity to force placement.

### 6.4 Node Selector

A node selector forces pods to run only on nodes with matching labels.

Example:

```yaml
nodeSelector:
  node-role.kubernetes.io/logging: ""
```

For a dedicated logging node pool, LokiStack components usually need both:

```yaml
nodeSelector:
  node-role.kubernetes.io/logging: ""
tolerations:
- key: node-role.kubernetes.io/logging
  operator: Equal
  value: reserved
  effect: NoSchedule
```

### 6.5 Affinity and Anti-Affinity

Affinity and anti-affinity give more expressive scheduling than node selectors.

Use them when you need:

- Zone-aware distribution
- Avoiding multiple replicas on one node
- Keeping related components close
- Separating ingesters across failure domains

Example concept:

```text
Do not place all Loki ingesters in the same zone.
Do not place all queriers on the same worker.
Prefer logging nodes, but tolerate fallback only if required.
```

### 6.6 Topology Awareness

For production, design logging nodes across zones:

```text
zone-a -> logging-node-1
zone-b -> logging-node-2
zone-c -> logging-node-3
```

This avoids losing the logging stack if one zone fails.

## 7. Creating a Logging Node Pool

There are two common approaches:

1. **Manual node labeling** for bare metal, vSphere, or existing nodes
2. **MachineSet-based node pool** for Machine API managed clusters

## 8. Manual Logging Node Pool Creation

### Step 1: Select Candidate Nodes

```bash
oc get nodes -o wide
```

Choose nodes based on:

- CPU capacity
- Memory capacity
- Disk throughput
- Network throughput
- Zone/rack distribution
- Existing workload pressure
- Storage access

### Step 2: Label Nodes

```bash
oc label node worker-log-1 node-role.kubernetes.io/logging=""
oc label node worker-log-2 node-role.kubernetes.io/logging=""
oc label node worker-log-3 node-role.kubernetes.io/logging=""
```

Optional: keep worker role as well:

```bash
oc label node worker-log-1 node-role.kubernetes.io/worker="" --overwrite
```

### Step 3: Taint Nodes

```bash
oc adm taint nodes worker-log-1 node-role.kubernetes.io/logging=reserved:NoSchedule
oc adm taint nodes worker-log-2 node-role.kubernetes.io/logging=reserved:NoSchedule
oc adm taint nodes worker-log-3 node-role.kubernetes.io/logging=reserved:NoSchedule
```

### Step 4: Verify

```bash
oc get nodes -l node-role.kubernetes.io/logging= -o wide
oc describe node worker-log-1 | egrep -i "Roles|Taints|Labels" -A10
```

## 9. MachineSet-Based Logging Node Pool

For cloud or Machine API managed clusters, create a separate MachineSet for logging workers.

A simplified MachineSet pattern:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: cluster-abcde-logging-us-east-1a
  namespace: openshift-machine-api
  labels:
    machine.openshift.io/cluster-api-cluster: cluster-abcde
spec:
  replicas: 1
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-cluster: cluster-abcde
      machine.openshift.io/cluster-api-machineset: cluster-abcde-logging-us-east-1a
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-cluster: cluster-abcde
        machine.openshift.io/cluster-api-machineset: cluster-abcde-logging-us-east-1a
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/worker: ""
          node-role.kubernetes.io/logging: ""
      taints:
      - key: node-role.kubernetes.io/logging
        value: reserved
        effect: NoSchedule
      providerSpec:
        value:
          # Cloud-provider-specific settings go here.
          # Copy from an existing worker MachineSet and adjust instance type,
          # disk, zone, tags, and other provider-specific values.
```

Recommended pattern:

```text
MachineSet per zone:
  logging-zone-a -> 1 or more replicas
  logging-zone-b -> 1 or more replicas
  logging-zone-c -> 1 or more replicas
```

Verify:

```bash
oc get machineset -n openshift-machine-api
oc get machine -n openshift-machine-api | grep logging
oc get nodes -l node-role.kubernetes.io/logging= -o wide
```

## 10. MachineConfigPool for Logging Nodes

A `MachineConfigPool` is needed when logging nodes require different host-level configuration from normal workers.

Examples:

- Different kubelet settings
- Different CRI-O settings
- Additional trusted CA bundles
- Kernel/sysctl tuning
- Dedicated log disk mounts
- Custom systemd units
- Custom image pull or registry configuration

### 10.1 Create Logging MachineConfigPool

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: logging
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - logging
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/logging: ""
```

Apply:

```bash
oc apply -f logging-mcp.yaml
```

Verify:

```bash
oc get mcp
oc describe mcp logging
```

### 10.2 Important MCP Behavior

A custom MachineConfigPool that includes `worker` inherits worker machine configs and can also receive configs targeted only to `logging`.

Be careful:

- A MachineConfigPool update can reboot nodes.
- A bad MachineConfig can degrade the pool.
- If you remove the `worker` role without planning, the Machine Config Operator might not manage the node as expected unless a custom pool is correctly configured.
- A custom pool can override or combine with worker pool configuration.

### 10.3 Example Logging-Specific MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-logging-custom-sysctl
  labels:
    machineconfiguration.openshift.io/role: logging
spec:
  config:
    ignition:
      version: 3.4.0
    storage:
      files:
      - path: /etc/sysctl.d/99-logging.conf
        mode: 0644
        overwrite: true
        contents:
          source: data:text/plain;charset=utf-8;base64,bmV0LmNvcmUuc29tYXhjb25uID0gNDA5NgpuZXQuaXB2NC50Y3BfbWF4X3N5bl9iYWNrbG9nID0gODE5Mgo=
```

This is only an example. Do not apply kernel tuning without testing and vendor guidance.

## 11. Placing LokiStack on the Logging Node Pool

LokiStack is usually the main target for a logging node pool.

### 11.1 Basic LokiStack Placement Pattern

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  # Keep your existing size, storage, tenants, and limits configuration.
  template:
    compactor:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
    distributor:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
    gateway:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
    indexGateway:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
    ingester:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
    querier:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
    queryFrontend:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
    ruler:
      nodeSelector:
        node-role.kubernetes.io/logging: ""
      tolerations:
      - key: node-role.kubernetes.io/logging
        operator: Equal
        value: reserved
        effect: NoSchedule
```

### 11.2 Why Apply Placement to All Loki Components?

If you place only some Loki components on logging nodes, the stack can become split:

```text
ingester      -> logging node
querier       -> application node
gateway       -> infra node
queryFrontend -> random worker
```

That defeats isolation. Apply the same node placement policy consistently to:

- `compactor`
- `distributor`
- `gateway`
- `indexGateway`
- `ingester`
- `querier`
- `queryFrontend`
- `ruler`

### 11.3 Verify LokiStack Placement

```bash
oc get pods -n openshift-logging -o wide
oc get pods -n openshift-logging -o wide | egrep 'loki|gateway|querier|ingester|distributor|compactor'
```

Check node labels:

```bash
oc get node <node-name> --show-labels
```

Check pod scheduling details:

```bash
oc describe pod <loki-pod-name> -n openshift-logging
```

## 12. Collector Placement: Important Production Nuance

This is where many admins make mistakes.

### 12.1 Collector Is Not the Same as Log Store

A logging node pool normally hosts the **log store** and **query** components.

Collectors are different. For standard node-level log collection, collectors need to run where the logs are present.

If you configure this:

```yaml
spec:
  collector:
    nodeSelector:
      node-role.kubernetes.io/logging: ""
```

then collectors are eligible only on logging nodes. That may be correct for receiver-style or limited-scope designs, but it can be wrong for full cluster logging because application logs on application nodes might not be collected.

### 12.2 Recommended Pattern for Full Cluster Logging

For full cluster logging, do not force collectors only onto logging nodes. Instead, allow collectors to run across the nodes that produce logs, and add tolerations so they can also run on tainted logging nodes.

Example:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  collector:
    tolerations:
    - key: node-role.kubernetes.io/logging
      operator: Equal
      value: reserved
      effect: NoSchedule
    resources:
      requests:
        cpu: 100m
        memory: 256Mi
      limits:
        cpu: 500m
        memory: 512Mi
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: default-logstore
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

This means:

```text
Collector DaemonSet -> runs on normal nodes and can also run on tainted logging nodes
LokiStack           -> forced onto logging nodes
```

### 12.3 When Collector NodeSelector Is Acceptable

Collector `nodeSelector` can be valid when:

- You are collecting logs only from selected nodes.
- You are using receiver inputs where external/log-producing systems send logs to collector services.
- You have a specific compliance pipeline on dedicated nodes.
- You intentionally do not need node-local logs from every node.
- You are designing a special hosted control plane or product-supported receiver setup.

Before applying collector `nodeSelector`, ask:

```text
Will this reduce log coverage?
Which nodes will no longer run collector pods?
Do we still collect app, infrastructure, and audit logs from all required nodes?
```

## 13. Service Account and RBAC for Collectors

OpenShift Logging uses RBAC to control what log types a collector may access.

### 13.1 Create Collector Service Account

```bash
oc create sa collector -n openshift-logging
```

### 13.2 Grant Required Roles

Application logs:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector
```

Infrastructure logs:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

Audit logs, only if required:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Verify:

```bash
oc get clusterrolebinding -o wide | grep collect
```

Important:

If `ClusterLogForwarder` references a log type without the required `ClusterRoleBinding`, the logging operator can remove the collector DaemonSet as a protective behavior. This results in no collector pods.

## 14. Full Example: Dedicated Logging Node Pool with LokiStack

This is a realistic high-level implementation sequence.

### 14.1 Label and Taint Nodes

```bash
for NODE in worker-log-1 worker-log-2 worker-log-3; do
  oc label node ${NODE} node-role.kubernetes.io/logging="" --overwrite
  oc adm taint node ${NODE} node-role.kubernetes.io/logging=reserved:NoSchedule --overwrite
done
```

### 14.2 Create MachineConfigPool, if Needed

```bash
cat > logging-mcp.yaml <<'EOF'
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: logging
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - logging
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/logging: ""
