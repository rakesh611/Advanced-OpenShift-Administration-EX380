# Node Reboot Behavior in Cluster Partitioning and Dedicated Node Pools

**Topic:** Node reboot behavior  
**Track:** Advanced OpenShift Administration / DO380-style operations  
**Audience:** OpenShift administrators with Linux, Kubernetes, and production platform experience  
**Focus:** How OpenShift decides when to reboot nodes, how the Machine Config Operator rolls those reboots through MachineConfigPools, and how to design dedicated node pools so reboots do not break workloads.

---

## 1. Executive Summary

In OpenShift, node reboot behavior is not only a Linux operating system topic. It is a platform lifecycle topic controlled mainly by the **Machine Config Operator (MCO)**, **MachineConfigPool (MCP)** objects, node labels, workload scheduling rules, and application disruption controls such as **PodDisruptionBudget (PDB)**.

For a senior administrator, the key point is this:

> A reboot in OpenShift is normally a controlled reconciliation action, not a random host event.

When a node pool receives a new machine configuration, the MCO normally performs this sequence on each affected node:

1. **Cordon** the node so no new workload pods are scheduled there.
2. **Drain** the node so movable pods are evicted and rescheduled elsewhere.
3. **Apply** the host-level configuration.
4. **Reboot** the node if required.
5. **Uncordon** the node after it comes back healthy.

This sequence is why cluster partitioning matters. If infra, logging, monitoring, storage, GPU, and application workloads all share the same worker pool, a single MachineConfig change can create wider application impact. If those workloads are separated into dedicated pools with proper capacity, PDBs, topology spread, taints, tolerations, and controlled `maxUnavailable`, reboots become predictable.

Official Red Hat documentation describes the MCO as the component that manages updates to systemd, CRI-O, kubelet, the kernel, NetworkManager, and other host features, and states that machine configuration changes commonly cause the corresponding nodes to reboot. It also documents that the MCO cordons, drains, applies changes, reboots, and uncordons affected nodes, while respecting the MCP `maxUnavailable` value.

## 2. Why Node Reboot Behavior Matters in Dedicated Node Pools

In a simple lab cluster, node reboot behavior is often seen as:

```bash
oc get nodes
oc get mcp
oc describe mcp worker
```

In production, reboot behavior determines whether these things happen safely:

- Platform upgrades complete inside a maintenance window.
- Router, registry, monitoring, logging, and storage workloads remain available.
- Control plane remains stable while worker nodes update.
- Application replicas are not all evicted from the same zone or pool.
- Stateful workloads do not experience unnecessary failover or data risk.
- GPU or special hardware workloads are not interrupted unexpectedly.
- Security, kernel, sysctl, kubelet, CRI-O, and OS-level changes roll out predictably.

A 10-year-experienced administrator should treat node reboots as a **capacity, scheduling, and risk-management workflow**, not as a simple `systemctl reboot` task.

## 3. Core Objects Involved

### 3.1 Node

A **Node** is the Kubernetes representation of a worker or control plane host. In OpenShift, a node usually runs Red Hat Enterprise Linux CoreOS (RHCOS) and is managed by cluster Operators.

Important node states during reboot-related work:

```text
Ready
Ready,SchedulingDisabled
NotReady
NotReady,SchedulingDisabled
```

Typical meaning:

| State | Meaning |
|---|---|
| `Ready` | Node is healthy and schedulable. |
| `Ready,SchedulingDisabled` | Node is healthy but cordoned; new pods should not be scheduled there. |
| `NotReady` | Node is unavailable, rebooting, unreachable, or kubelet is unhealthy. |
| `NotReady,SchedulingDisabled` | Node is unavailable and also unschedulable. |

### 3.2 MachineConfig

A **MachineConfig** describes host-level configuration that must be applied to nodes. Examples include:

- Kernel arguments.
- Kernel type changes, such as real-time kernel on supported worker nodes.
- Systemd units and drop-ins.
- Files under `/etc` or `/var`.
- Kubelet configuration generated from `KubeletConfig` custom resources.
- CRI-O/container runtime configuration generated from `ContainerRuntimeConfig` custom resources.
- Registry mirror configuration.
- SSH key updates.

Example MachineConfig that changes kernel arguments on workers:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-example-karg
  labels:
    machineconfiguration.openshift.io/role: worker
spec:
  kernelArguments:
    - audit=1
```

Kernel arguments usually require a reboot because the running kernel cannot consume many boot-time parameters without restarting.

### 3.3 Rendered MachineConfig

OpenShift does not apply each MachineConfig independently as a separate script. The MCO renders all matching MachineConfigs for a pool into a single rendered configuration.

Example:

```bash
oc get mc | egrep 'rendered|worker|master'
```

Example output pattern:

```text
rendered-worker-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
rendered-master-yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy
```

The node annotation shows the desired and current config:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

Typical MCD states:

```text
Done
Working
Degraded
```

### 3.4 MachineConfigPool

A **MachineConfigPool** groups nodes that receive the same rendered machine configuration. Default pools are normally:

```text
master
worker
```

Custom worker pools can be created for dedicated workloads, such as:

```text
infra
logging
monitoring
storage
gpu
worker-perf
worker-canary
app-prod
app-nonprod
```

Important MCP fields:

| Field | Purpose |
|---|---|
| `spec.machineConfigSelector` | Selects which MachineConfig objects are rendered into this pool. |
| `spec.nodeSelector` | Selects which nodes belong to this pool. |
| `spec.maxUnavailable` | Controls how many nodes in the pool can be unavailable during update/reboot. |
| `spec.paused` | Stops the MCO from applying new configuration to nodes in the pool. |

Check pools:

```bash
oc get mcp
oc describe mcp worker
oc get mcp worker -o yaml
```

Typical output fields:

```text
NAME     CONFIG                UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
worker   rendered-worker-...   True      False      False      6              6                   6                     0
```

### 3.5 Machine Config Operator

The **Machine Config Operator** is responsible for reconciling the desired host configuration. It includes:

- `machine-config-controller`
- `machine-config-daemon`
- `machine-config-server`

The important operational point is that the **Machine Config Daemon (MCD)** runs on each node. It observes desired config changes, applies them, and reboots the node when required.

Check MCO components:

```bash
oc get co machine-config
oc get pods -n openshift-machine-config-operator
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=100
```

## 4. Default Reboot Flow for MachineConfig Changes

When a MachineConfig change affects a pool, OpenShift usually performs this flow:

```text
MachineConfig / KubeletConfig / ContainerRuntimeConfig changed
        |
        v
MCO renders a new rendered-<pool>-<hash> config
        |
        v
MCP detects desired config != current config
        |
        v
MCO selects nodes up to spec.maxUnavailable
        |
        v
Node is cordoned
        |
        v
Node is drained
        |
        v
MCD applies files, systemd units, OS image, kubelet/CRI-O config, kernel args, etc.
        |
        v
Node reboots if required
        |
        v
Kubelet reconnects and node becomes Ready
        |
        v
MCO uncordons node
        |
        v
MCP moves toward UPDATED=True
```

For a production admin, the most important checkpoints are:

```bash
oc get mcp
oc get nodes
oc describe mcp <pool>
oc get events -A --sort-by=.lastTimestamp | tail -50
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=200
```

## 5. What Triggers Node Reboots?

Not every change reboots a node, but many important host-level changes do.

### 5.1 Common Reboot Triggers

| Change type | Usually reboots? | Why |
|---|---:|---|
| Kernel arguments | Yes | Kernel boot command line changes require restart. |
| Kernel type change | Yes | Node must boot into a different kernel. |
| RHCOS / OS image update | Yes | Node must boot into the updated OS deployment. |
| Some MachineConfig file changes | Often yes by default | MCO default behavior is conservative. |
| Systemd unit changes | Often yes unless policy says otherwise | Unit dependencies and service behavior can require restart/reboot. |
| KubeletConfig changes | Usually disruptive | Kubelet config affects node agent behavior. |
| ContainerRuntimeConfig / CRI-O config | Often disruptive | Runtime changes can require CRI-O restart or node update. |
| Cluster version update with OS payload | Yes | MCO updates host OS/config in update phase. |
| Force file for drift remediation | Yes | Reapplies current machine config and reboots. |
| Manual graceful node restart | Yes | Administrator intentionally reboots host. |

### 5.2 Changes That May Not Reboot

OpenShift documentation identifies some MCO-detected changes that can be applied without draining or rebooting, such as certain SSH key changes, pull secret changes, and kubelet CA rotation. For registry-related changes, behavior depends on the exact registry configuration change; some changes trigger drain without reboot, while specific additions do not require drain.

The important production lesson is:

> Do not assume a MachineConfig change is non-disruptive. Check the exact change type, OpenShift version, MCO behavior, and configured node disruption policy.

### 5.3 Node Disruption Policy

Newer OpenShift versions support **node disruption policies** that let administrators define whether certain MachineConfig changes require:

- `Reboot`
- `None`
- `Drain`
- `Reload`
- `Restart`
- `DaemonReload`
- `Special`

Example: restart `chronyd.service` when `/etc/chrony.conf` changes, instead of rebooting the whole node.

```yaml
apiVersion: operator.openshift.io/v1
kind: MachineConfiguration
metadata:
  name: cluster
  namespace: openshift-machine-config-operator
spec:
  nodeDisruptionPolicy:
    files:
    - path: /etc/chrony.conf
      actions:
      - type: Restart
        restart:
          serviceName: chronyd.service
```

Important cautions:

- Some machine configuration changes always require reboot.
- The MCO validates policy format, but the administrator is responsible for ensuring the policy is operationally correct.
- `Reboot` and `None` override other actions and should not be mixed with other actions for the same rule.
- Policy behavior should be tested in non-production pools first.

## 6. Role of `maxUnavailable`

`spec.maxUnavailable` controls how many nodes in a MachineConfigPool may be unavailable during MCO-driven updates.

Check current value:

```bash
oc get mcp worker -o jsonpath='{.spec.maxUnavailable}{"\n"}'
```

Patch example:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

### 6.1 How `maxUnavailable` Works

If a pool has 10 nodes and `maxUnavailable: 1`, OpenShift updates one node at a time.

If a pool has 10 nodes and `maxUnavailable: 2`, OpenShift can cordon, drain, apply, reboot, and recover two nodes in parallel.

That sounds faster, but it is not always safer.

### 6.2 Production Rule

For the **control plane pool**, keep `maxUnavailable` conservative. In most production clusters, do not increase control plane reboots beyond one node at a time.

For **worker pools**, tune based on:

- Available spare capacity.
- Number of replicas per workload.
- PDB settings.
- Zone spread.
- Stateful workload recovery time.
- Storage attachment/detachment speed.
- Whether the pool hosts critical infra workloads.
- Whether cluster autoscaler can add capacity before disruption.

### 6.3 Dangerous Example

Assume:

- Pool: `logging`
- Nodes: 3
- Elasticsearch/Loki/collector stack with strict PDB
- `maxUnavailable: 2`

A MachineConfig change can make two logging nodes unavailable together. If the logging stack cannot tolerate that, drains may block, or logging availability may degrade.

Better design:

```text
logging MCP: 3 or more nodes
maxUnavailable: 1
PDB: allows one voluntary disruption
Topology spread: across zones
Maintenance window: defined
```

## 7. Role of `spec.paused`

`spec.paused: true` prevents the MCO from applying new machine configuration changes to nodes in that pool.

Pause a pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

Unpause a pool:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

### 7.1 When to Pause a Pool

Use pause carefully for:

- Canary update patterns.
- Maintenance window control.
- Preventing immediate rollout of a risky MachineConfig.
- Building and validating a custom node pool before rollout.
- Avoiding unnecessary back-to-back reboots while preparing multiple related changes.

### 7.2 When Not to Leave a Pool Paused

Do not leave an MCP paused for long periods. Paused pools do not receive new machine config changes, and that can block important rotated certificates or platform-level updates. During upgrades, paused MCPs can also be skipped or delay the cluster reaching a fully updated state.

Senior-admin rule:

> Pausing is a controlled maintenance mechanism, not a permanent configuration state.

## 8. Dedicated Node Pools and Reboot Blast Radius

Cluster partitioning is about reducing blast radius. A reboot event should affect only the workloads that logically belong to that pool.

### 8.1 Infra Node Pool

Infra nodes usually host:

- Ingress router pods.
- Image registry.
- Monitoring components, depending on design.
- Internal platform services.

Reboot concern:

- Router availability can drop if too many infra nodes reboot together.
- Registry availability can be impacted if the registry is not replicated or storage is slow.

Best practice:

- Minimum 3 infra nodes for HA designs.
- `maxUnavailable: 1` for infra MCP.
- Router replicas spread across infra nodes and zones.
- Infra workloads tolerate infra taints.
- App workloads should normally avoid infra nodes.

Example infra MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values: [worker, infra]
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  maxUnavailable: 1
```

Label infra nodes:

```bash
oc label node <node1> node-role.kubernetes.io/infra=
oc label node <node2> node-role.kubernetes.io/infra=
oc label node <node3> node-role.kubernetes.io/infra=
```

Taint example:

```bash
oc adm taint nodes -l node-role.kubernetes.io/infra node-role.kubernetes.io/infra=:NoSchedule
```

### 8.2 Application Node Pool

Application pools host business workloads. For reboot safety:

- Ensure enough replicas exist outside the rebooting node.
- Use `PodDisruptionBudget` correctly.
- Use topology spread constraints or anti-affinity.
- Avoid local-only state unless the workload is designed for it.
- Avoid setting `maxUnavailable` higher than spare capacity.

Example PDB:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-pdb
  namespace: app-prod
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: frontend
```

A PDB is not a magic HA feature. It protects against voluntary evictions, but if you set it too strict, MCO drain can block.

### 8.3 Logging Node Pool

Logging nodes are sensitive because log pipelines often involve persistent storage, buffers, and daemon-style collectors.

Reboot concerns:

- Log ingestion delay.
- Stateful component recovery.
- PVC detach/attach delays.
- Collector backpressure.
- PDB blocking.

Best practice:

- Keep `maxUnavailable: 1`.
- Validate storage recovery before increasing parallelism.
- Ensure logging pods have tolerations for logging taints.
- Use topology spread across zones.
- Monitor ingestion lag before, during, and after reboot.

### 8.4 Monitoring Node Pool

Monitoring nodes can host Prometheus, Alertmanager, Thanos, metrics agents, and observability components.

Reboot concerns:

- Temporary alert gaps.
- Prometheus WAL replay time.
- PVC attach/detach time.
- Alertmanager quorum/replica availability.

Best practice:

- Use multiple monitoring replicas where supported.
- Keep `maxUnavailable: 1`.
- Avoid rebooting all monitoring storage nodes together.
- Silence planned node reboot alerts only for the maintenance window.

### 8.5 Storage Node Pool

Storage pools are often the most sensitive.

Examples:

- OpenShift Data Foundation / Ceph nodes.
- Local Storage Operator nodes.
- NFS-backed nodes.
- Custom storage daemons.

Reboot concerns:

- Storage quorum.
- OSD down/out behavior.
- PVC attachment delays.
- Node-local PV unavailability.
- Data rebalance/recovery storms.

Best practice:

- Never treat storage reboots like stateless app worker reboots.
- Use storage vendor/operator documentation for maintenance mode.
- Keep `maxUnavailable: 1` unless the storage design explicitly supports more.
- Check storage health before and after every node reboot.

Example checks:

```bash
oc get pods -n openshift-storage -o wide
oc get cephcluster -n openshift-storage
oc get storagecluster -n openshift-storage
oc get pv,pvc -A | egrep -i 'Bound|Pending|Lost'
```

### 8.6 GPU Node Pool

GPU nodes often run expensive, long-running, or batch workloads.

Reboot concerns:

- Training jobs may be interrupted.
- GPU operator components may restart.
- Device plugin readiness can lag after reboot.
- Drivers and kernel versions must align.

Best practice:

- Dedicated GPU MCP.
- Taints to prevent non-GPU workloads.
- Lower `maxUnavailable`.
- Drain windows aligned with job scheduler policy.
- Confirm device plugin and GPU operator health after reboot.

Example:

```bash
oc get nodes -l node-role.kubernetes.io/gpu
oc get pods -n nvidia-gpu-operator -o wide
oc describe node <gpu-node> | egrep -i 'nvidia|gpu|allocatable|capacity'
```

### 8.7 Performance / Low-Latency Pool

Performance pools might use:

- Real-time kernel.
- CPU isolation.
- Huge pages.
- Tuned profiles.
- SR-IOV.
- NUMA-aware scheduling.

Reboot concerns:

- Kernel and boot argument changes often require reboot.
- Workloads may need deterministic restart order.
- Network devices and SR-IOV VFs may need validation after boot.

Best practice:

- Use canary node first.
- Validate kernel arguments via `/proc/cmdline`.
- Validate tuned profile and CPU isolation after boot.
- Never mix normal app workloads into performance nodes.

## 9. Custom MachineConfigPool Example for Controlled Reboot Scope

Example: create a dedicated `worker-perf` pool and apply a MachineConfig only to that pool.

### 9.1 Label Nodes

```bash
oc label node worker-a node-role.kubernetes.io/worker-perf=
oc label node worker-b node-role.kubernetes.io/worker-perf=
oc label node worker-c node-role.kubernetes.io/worker-perf=
```

### 9.2 Create MCP

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-perf
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values: [worker, worker-perf]
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-perf: ""
  maxUnavailable: 1
```

Apply:

```bash
oc apply -f worker-perf-mcp.yaml
oc get mcp
```

### 9.3 Create Pool-Specific MachineConfig

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-perf-example
  labels:
    machineconfiguration.openshift.io/role: worker-perf
spec:
  kernelArguments:
    - nosmt
```

Apply:

```bash
oc apply -f 99-worker-perf-example.yaml
oc get mcp worker-perf -w
```

Only nodes in `worker-perf` should move toward the new rendered config and reboot as needed.

### 9.4 Why Include Both `worker` and `worker-perf` in `machineConfigSelector`?

A custom worker pool normally inherits the base worker MachineConfigs and adds custom pool-specific MachineConfigs. That is why the selector commonly includes:

```yaml
values: [worker, worker-perf]
```

This means:

- Base worker configuration still applies.
- Additional `worker-perf` MachineConfigs also apply.
- The node is logically separated from the default worker pool for reboot/update sequencing.

## 10. Manual Node Reboot vs MCO-Driven Reboot

### 10.1 MCO-Driven Reboot

Use this when the reboot is caused by desired config:

- MachineConfig.
- KubeletConfig.
- ContainerRuntimeConfig.
- Cluster update.
- OS image update.

You generally do **not** manually reboot the node. Let MCO manage the sequence.

Monitor:

```bash
oc get mcp -w
oc get nodes -w
oc describe mcp <pool>
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=100
```

### 10.2 Manual Graceful Reboot

Use this for hardware maintenance, troubleshooting, or host-level checks not driven by a MachineConfig.

Recommended sequence:

```bash
NODE=<node-name>

oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --force
oc debug node/$NODE
```

Inside debug shell:

```bash
chroot /host
systemctl reboot
```

After node returns:

```bash
oc adm uncordon $NODE
oc get node $NODE
```

Caution:

- `--delete-emptydir-data` deletes data in `emptyDir` volumes.
- `--force` can delete unmanaged/bare pods.
- `--disable-eviction` bypasses PDB checks and should be a last resort.
- On single-node OpenShift, draining affects cluster API/auth availability because there is nowhere else to reschedule workloads.

## 11. Drain Behavior and Why Drains Fail

The reboot itself is often not the hardest part. The drain is usually the risky part.

### 11.1 What Drain Does

`oc adm drain` evicts pods from a node so controllers can recreate them elsewhere.

It normally ignores DaemonSet pods because DaemonSet pods are expected to run on nodes.

Example dry-run:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

### 11.2 Common Drain Blockers

| Blocker | Symptom | Fix |
|---|---|---|
| Strict PDB | `Cannot evict pod as it would violate the pod's disruption budget` | Add replicas, relax PDB, drain during maintenance, or use last-resort bypass. |
| Single replica app | Drain waits or app downtime occurs | Scale replicas before maintenance. |
| Local storage | Pod cannot move elsewhere | Plan storage-aware maintenance. |
| Unmanaged bare pod | Drain refuses without `--force` | Replace bare pod with Deployment/DaemonSet/StatefulSet. |
| Node selector too strict | Evicted pod has nowhere to run | Add capacity or broaden placement rules. |
| Taints not tolerated | Replacement pod cannot schedule | Add toleration or correct pool design. |
| Resource pressure | Replacement pods Pending | Add capacity or reduce workload before reboot. |
| StatefulSet ordering | Slow reschedule | Validate storage and readiness gates. |

### 11.3 MCO Drain Failure Impact

If the MCO cannot drain a node, it cannot safely proceed to reboot that node for the MachineConfig change. The MCP can remain `UPDATING=True` and possibly become degraded depending on the failure state.

Check:

```bash
oc describe mcp <pool>
oc get pods -A -o wide --field-selector spec.nodeName=<node>
oc get pdb -A
oc get events -A --sort-by=.lastTimestamp | tail -100
```

## 12. Reboot Behavior During Cluster Updates

Cluster updates happen in phases. The CVO updates cluster components, and the MCO handles host-level node updates.

Important distinction:

```text
CVO phase: updates cluster operators and pod-based components.
MCO phase: updates node OS/config and can reboot nodes.
```

During the MCO phase, nodes are cordoned, drained, updated, rebooted, and uncordoned. The number of nodes handled concurrently depends on each MCP's `maxUnavailable`.

### 12.1 Canary Rollout Strategy

For large clusters, create custom MCPs:

```text
worker-canary
worker-batch-a
worker-batch-b
worker-batch-c
```

General flow:

1. Move a small number of nodes to `worker-canary`.
2. Pause other custom worker MCPs.
3. Start cluster update.
4. Let canary nodes update and reboot.
5. Validate workloads.
6. Unpause the next worker pool.
7. Continue one pool at a time.

Example pause:

```bash
oc patch mcp worker-batch-a --type=merge -p '{"spec":{"paused":true}}'
oc patch mcp worker-batch-b --type=merge -p '{"spec":{"paused":true}}'
```

Example unpause:

```bash
oc patch mcp worker-batch-a --type=merge -p '{"spec":{"paused":false}}'
oc get mcp worker-batch-a -w
```

### 12.2 Canary Pool Size

A canary pool should be large enough to test reality, but small enough to evacuate safely.

Bad canary:

```text
1 node, no real workloads, no storage, no router, no monitoring impact
```

Good canary:

```text
A small representative set of nodes that run real but non-critical workloads and match hardware/network/storage characteristics.
```

## 13. Reboot Behavior and Control Plane Nodes

Control plane node reboots are more sensitive.

Key points:

- Do not create custom MCPs from control plane nodes.
- Keep control plane `maxUnavailable` conservative.
- Static pods such as etcd are treated specially.
- In single-node OpenShift, drain behavior is different because workloads cannot be rescheduled elsewhere.
- Always check cluster operators before control plane maintenance.

Pre-check:

```bash
oc get co
oc get nodes -l node-role.kubernetes.io/master
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-apiserver -o wide
```

Control plane safety check:

```bash
oc get co | egrep -v 'True\s+False\s+False'
```

Do not proceed with voluntary reboots if critical operators are already degraded unless you are performing a planned recovery.

## 14. Reboot Behavior and Configuration Drift

Configuration drift means the host on-disk state differs from the MachineConfig-managed desired state.

Examples:

- An admin manually edits a file that MachineConfig owns.
- File permissions differ from the rendered config.
- A systemd drop-in is changed outside MCO.

When drift is detected, the node and MCP can become `Degraded`. A degraded node can remain online, but MCO cannot update it normally.

Check drift:

```bash
oc get mcp
oc describe mcp <pool>
oc describe node <node> | egrep -i 'machineconfiguration|degraded|currentConfig|desiredConfig'
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=200 | egrep -i 'drift|degraded|content mismatch'
```

Fix options:

1. Restore the file/content/permissions to match MachineConfig.
2. Update the MachineConfig to represent the desired state.
3. Use force-file remediation only when you understand the impact.

Force-file remediation can cause a reboot. Do not use it casually during business hours.

## 16. Pre-Reboot Checklist for Dedicated Pools

Before applying a MachineConfig or unpausing a pool, run this checklist.

### 16.1 Cluster Health

```bash
oc get co
oc get mcp
oc get nodes
oc get clusterversion
```

Do not start planned reboots if:

- Cluster operators are degraded.
- MCP is already degraded.
- Nodes are already NotReady.
- API latency is high.
- etcd or storage health is poor.

### 16.2 Workload Capacity

```bash
oc adm top nodes
oc adm top pods -A --sort-by=cpu | head
oc get pods -A | egrep 'Pending|CrashLoopBackOff|ImagePullBackOff|Terminating'
```

Confirm remaining nodes can absorb evicted pods.

### 16.3 PDB Review

```bash
oc get pdb -A
```

Look for strict budgets:

```text
MIN AVAILABLE = replicas
ALLOWED DISRUPTIONS = 0
```

A workload with `ALLOWED DISRUPTIONS=0` can block drains.

### 16.4 Pool Design

```bash
oc get mcp -o wide
oc get nodes --show-labels | egrep 'node-role.kubernetes.io/(infra|logging|monitoring|storage|gpu|worker-perf)'
```

Verify nodes are in the intended pool.

### 16.5 Taints and Tolerations

```bash
oc describe node <node> | grep -i taints -A2
oc get pod <pod> -n <ns> -o yaml | grep -i tolerations -A20
```

If replacement pods cannot tolerate the target pool taints, drain causes Pending pods.

### 16.6 Storage Health

For storage-heavy pools:

```bash
oc get pv,pvc -A
oc get pods -n openshift-storage -o wide
```

Also use storage-specific health commands for ODF/Ceph or your CSI provider.

## 18. Troubleshooting Scenarios

### Scenario 1: MCP Stuck `UPDATING=True`

Symptoms:

```bash
oc get mcp
```

```text
worker   rendered-worker-xxx   False   True   False
```

Steps:

```bash
oc describe mcp worker
oc get nodes
oc get pods -A -o wide | grep <node>
oc get pdb -A
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --tail=200
```

Likely causes:

- Drain blocked by PDB.
- Node NotReady before update.
- Pod cannot terminate.
- Storage detach issue.
- MCD error applying config.
- Kubelet or CRI-O health check failure.

### Scenario 2: Node Reboots but Does Not Return Ready

Steps:

```bash
oc get node <node>
oc describe node <node>
oc get csr
oc get co
```

Access via console/SSH if available:

```bash
journalctl -b -u kubelet --no-pager
journalctl -b -u crio --no-pager
systemctl --failed
rpm-ostree status
```

Likely causes:

- Bad kernel argument.
- Network configuration issue.
- Disk or filesystem issue.
- CRI-O failure.
- Kubelet certificate/API connectivity issue.
- Node cannot pull required images.

### Scenario 3: MachineConfig Change Causes Too Many App Pods Pending

Steps:

```bash
oc get pods -A | grep Pending
oc describe pod <pod> -n <ns>
oc get nodes --show-labels
oc describe node <available-node> | egrep -i 'taints|allocatable|capacity'
```

Likely causes:

- Node selector points only to rebooting pool.
- Taints not tolerated.
- Resource requests too high for remaining nodes.
- PVC zone mismatch.
- Anti-affinity too strict.

Fix:

- Add temporary capacity.
- Reduce `maxUnavailable`.
- Correct tolerations/node selectors.
- Adjust topology spread or anti-affinity.
- Review PDB.

### Scenario 4: MCP Degraded After Manual Host Edit

Symptoms:

```text
NodeDegraded
content mismatch for file ...
```

Steps:

```bash
oc describe mcp <pool>
oc describe node <node>
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --tail=200
```

Fix:

- Revert manual file edit.
- Manage the change through MachineConfig.
- Use force remediation only when necessary and during a maintenance window.

### Scenario 5: Pool Was Paused Too Long

Symptoms:

- Pool does not update.
- Nodes remain on old rendered config.
- Upgrade does not complete cleanly.
- Certificate-related commands fail, such as `oc debug`, `oc logs`, or `oc exec`.

Steps:

```bash
oc get mcp
oc get mcp <pool> -o yaml | egrep 'paused|currentConfig|desiredConfig|maxUnavailable'
oc describe mcp <pool>
```

Fix:

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
oc get mcp <pool> -w
```

## 19. Designing Reboot-Safe Node Pools

### 19.1 Pool Size Guidelines

| Pool type | Minimum practical HA size | Recommended `maxUnavailable` |
|---|---:|---:|
| Control plane | 3 | 1 |
| Infra/router | 3 | 1 |
| Monitoring | 3 if dedicated | 1 |
| Logging | 3 if stateful/HA | 1 |
| Storage | Depends on storage design; often 3+ | 1 |
| GPU | Depends on job tolerance | 1 |
| General app | Depends on app replicas/capacity | 1 or more after testing |
| Canary | Small representative set | 1 |

### 19.2 Scheduling Rules

Use a combination of:

- Node labels.
- Taints and tolerations.
- Node affinity.
- Pod anti-affinity.
- Topology spread constraints.
- PDBs.
- Resource requests/limits.

The reboot workflow is only safe if the scheduler has somewhere correct to place replacement pods.

### 19.3 Capacity Rule

Before rebooting one node, the remaining nodes in that pool or allowed target pools must be able to run the evicted pods.

Simple formula:

```text
Available capacity after N unavailable nodes >= required workload capacity + safety buffer
```

If not true, drains either block or cause Pending pods.

### 19.4 Zone Rule

For multi-zone clusters, avoid rebooting all nodes in a single zone if that zone hosts unique replicas. Use topology spread constraints so replicas are distributed.

Example topology spread:

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: frontend
```

### 19.5 Stateful Workload Rule

For StatefulSets:

- Validate PDB.
- Validate PVC zone and storage class behavior.
- Validate graceful termination.
- Validate startup/readiness probes.
- Avoid parallel node reboots unless the application supports it.

### 21.2 Common Interview Questions

**Q: What happens when you apply a MachineConfig that changes kernel arguments?**

A: The MCO renders a new config for the target MCP. Nodes in that pool are updated according to `maxUnavailable`. Each affected node is cordoned, drained, updated, rebooted, and uncordoned. Kernel argument changes require the node to boot with the new kernel command line.

**Q: How do you prevent all worker nodes from rebooting together?**

A: Use MCP `maxUnavailable`, custom MCPs, canary pools, and possibly pause/unpause pools in stages. Ensure PDBs and capacity allow drains.

**Q: Can you create a custom MCP for control plane nodes?**

A: No. Custom MCPs are for worker nodes. Control plane nodes should not be partitioned into custom MCPs.

**Q: Why can a MachineConfig rollout get stuck?**

A: Common reasons include PDB preventing eviction, a node already unavailable, insufficient capacity, bad taints/tolerations, local storage, failing kubelet/CRI-O, config drift, or MCD failing to apply config.

**Q: What is the difference between cordon and drain?**

A: Cordon marks a node unschedulable for new pods. Drain evicts movable existing pods from the node.

**Q: What is the safest `maxUnavailable` for control plane nodes?**

A: Keep it at 1. Do not update multiple control plane nodes at once in normal production operations.

**Q: What is configuration drift?**

A: Drift occurs when the actual node filesystem or systemd state differs from what the current MachineConfig specifies. MCD can mark the node and MCP degraded until the mismatch is fixed.

## 22. Production Best Practices

1. Treat every MachineConfig change as a possible reboot unless proven otherwise.
2. Never apply risky MachineConfigs directly to all workers without a canary.
3. Keep custom node pools aligned with workload criticality.
4. Use `maxUnavailable: 1` for critical pools unless tested otherwise.
5. Do not increase control plane `maxUnavailable` casually.
6. Avoid leaving MCPs paused for long periods.
7. Review PDBs before maintenance.
8. Ensure remaining nodes have capacity before drains.
9. Use topology spread and anti-affinity for HA applications.
10. Use taints/tolerations to protect infra, storage, monitoring, logging, and GPU pools.
11. Do not manually edit MachineConfig-managed files on nodes.
12. Use `oc debug node/<node>` and `chroot /host` for host-level validation.
13. Monitor `oc get mcp`, `oc get nodes`, MCD logs, and cluster operators during rollout.
14. For storage pools, follow storage-specific maintenance procedures.
15. Document every pool's reboot policy, maintenance window, and owner.

## 24. Mental Model

Think of node reboot behavior like this:

```text
Dedicated node pool design decides blast radius.
MachineConfig decides desired host state.
MCO decides rollout orchestration.
MCP maxUnavailable decides concurrency.
Drain/PDB/capacity decide whether reboot can proceed safely.
Node disruption policy can reduce unnecessary reboot for selected changes.
Observability decides how quickly you detect and fix rollout problems.
```

A strong OpenShift administrator does not ask only, "Will this reboot?"  
A strong OpenShift administrator asks:

```text
Which pool will reboot?
How many nodes can reboot at once?
Can workloads move?
Will PDBs allow eviction?
Is there enough capacity?
Are storage and network dependencies safe?
How do I stop, pause, observe, and recover if anything fails?
```

That is the difference between basic node administration and advanced OpenShift platform operations.
