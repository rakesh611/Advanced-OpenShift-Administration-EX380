# Operator Upgrades in Operator Management
## Advanced OpenShift Administration Guide for Experienced Linux / DevOps / OpenShift Administrators

> **Scope:** This guide explains **Operator upgrades** in OpenShift Operator Management from a senior administrator point of view. It focuses on OLM-managed add-on Operators, upgrade channels, subscriptions, install plans, CSV lifecycle, troubleshooting, disconnected clusters, CRD safety, production change control, and advanced CLI workflows.
>
> **Important distinction:** OpenShift has two major Operator lifecycle areas:
>
> - **Cluster Operators**: Core platform Operators managed by the **Cluster Version Operator (CVO)**. Examples: `kube-apiserver`, `authentication`, `ingress`, `network`, `machine-config`, `operator-lifecycle-manager`.
> - **OLM-based add-on Operators**: Optional Operators installed from Red Hat, certified, community, or custom catalogs and managed by **Operator Lifecycle Manager (OLM)**. Examples: OpenShift Logging, OpenShift Pipelines, OpenShift GitOps, File Integrity Operator, cert-manager Operator, Service Mesh, AMQ, etc.
>
> This document is mainly about **OLM-based Operator upgrades**. Cluster Operator updates are covered only where they interact with Operator upgrades.

## 1. What an Operator Upgrade Really Means

An **Operator upgrade** is not simply a container image update. In OpenShift, an OLM-based Operator upgrade can modify several layers of the cluster:

| Layer | What Can Change | Impact |
|---|---|---|
| Operator bundle | CSV, CRDs, RBAC, Deployments, webhooks, services, roles, permissions | OLM installs or replaces Kubernetes resources |
| Operator controller pod | New image, env vars, args, volumes, resource requests, node scheduling rules | Operator Deployment rolls out |
| APIs | New or updated CRDs, conversion webhooks, validation schemas | Custom Resources may need schema compatibility |
| RBAC | ClusterRoles, Roles, RoleBindings, permissions | Security review required in production |
| Operand reconciliation | Operator may roll or reconfigure managed workloads | Application or platform service impact possible |
| Catalog resolution | Dependencies and constraints may change | Upgrade can be blocked by dependency resolver |
| Cluster compatibility | Operator bundle might define OpenShift version compatibility | Cluster updates can be blocked if Operator is not compatible |

A senior OpenShift administrator should think of an Operator upgrade as a **controlled platform change**. The actual change is usually triggered through the `Subscription`, but the result can affect CRDs, admission webhooks, operands, RBAC, network policies, storage, routes, certificates, and sometimes cluster upgrade readiness.

### Operator upgrade vs application deployment upgrade

A normal application deployment upgrade updates a Deployment, StatefulSet, or DeploymentConfig. An Operator upgrade updates the **controller that owns the application lifecycle**. After the Operator is upgraded, it might reconcile and update operands automatically depending on the Operator design.

Example:

- Upgrading **OpenShift Logging Operator** can change the Operator pod.
- The upgraded Operator may then reconcile the `ClusterLogging` custom resource.
- It may roll Vector, LokiStack, Elasticsearch legacy components, collector DaemonSets, webhooks, or services.
- A successful Operator CSV does not always mean every operand is healthy. Always verify both.

### Three upgrade scopes to separate mentally

#### 1. Operator controller upgrade

This upgrades the Operator itself:

```bash
oc get csv -n <operator-namespace>
oc get deploy -n <operator-namespace>
oc rollout status deploy/<operator-deployment> -n <operator-namespace>
```

#### 2. Operand upgrade

This upgrades workloads managed by the Operator:

```bash
oc get pods -n <operand-namespace>
oc get <custom-resource-kind> -A
oc describe <custom-resource-kind> <name> -n <namespace>
```

#### 3. OpenShift cluster upgrade

This upgrades OpenShift platform components via CVO:

```bash
oc get clusterversion
oc get co
oc adm upgrade
```

OLM-based Operators are not upgraded by CVO, but their compatibility can influence cluster upgrade readiness.

## 2. The OLM Upgrade Control Plane

Operator Lifecycle Manager is responsible for installing, upgrading, and managing the lifecycle of OLM-based Operators. OLM works with catalogs, package metadata, subscriptions, install plans, CSVs, and OperatorGroups.

In a normal OpenShift cluster, important OLM-related namespaces include:

| Namespace | Purpose |
|---|---|
| `openshift-operator-lifecycle-manager` | Core OLM components such as `olm-operator` and `catalog-operator` |
| `openshift-marketplace` | Default Red Hat / certified / community catalog sources and Marketplace Operator |
| `openshift-operators` | Default namespace for globally installed Operators |
| Operator-specific namespaces | Many Red Hat Operators use dedicated namespaces, for example `openshift-logging`, `openshift-gitops-operator`, `openshift-pipelines`, `openshift-file-integrity` |

Check OLM health first:

```bash
oc get co operator-lifecycle-manager
oc get pods -n openshift-operator-lifecycle-manager
oc get pods -n openshift-marketplace
oc get catalogsources -n openshift-marketplace
```

Common OLM control-plane components:

| Component | What It Does |
|---|---|
| `olm-operator` | Manages CSVs, installs resources declared by CSVs, handles CSV transitions |
| `catalog-operator` | Handles subscriptions, dependency resolution, install plans, catalog interactions |
| `packageserver` | Provides PackageManifest API used by console and CLI discovery |
| Marketplace Operator | Manages default catalog sources in `openshift-marketplace` |
| CatalogSource pods | gRPC servers exposing catalog/package/bundle metadata |

### Senior admin mental model

OLM is a **declarative resolver and installer**:

1. Catalog says what versions are available.
2. Subscription says what package/channel/source a namespace wants.
3. Resolver determines the best installable bundle.
4. InstallPlan shows the resources that will be created or updated.
5. CSV represents the installed Operator version and its lifecycle state.
6. Operator pod starts and reconciles operands.

## 3. Core Objects Used During Operator Upgrades

### 3.1 CatalogSource

A `CatalogSource` exposes Operator packages and bundles to OLM.

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource redhat-operators -n openshift-marketplace
```

Typical default sources:

```text
redhat-operators
certified-operators
community-operators
redhat-marketplace
```

A catalog source usually runs a pod in `openshift-marketplace`:

```bash
oc get pods -n openshift-marketplace
oc logs -n openshift-marketplace <catalog-pod>
```

If the CatalogSource is unhealthy, Operator upgrades might not resolve.

### 3.2 PackageManifest

A `PackageManifest` shows available channels, versions, default channel, and install modes.

```bash
oc get packagemanifests -n openshift-marketplace
oc describe packagemanifest <operator-package-name> -n openshift-marketplace
oc get packagemanifest <operator-package-name> -n openshift-marketplace -o yaml
```

Useful filters:

```bash
oc get packagemanifests -n openshift-marketplace | grep -i logging
oc get packagemanifest <pkg> -n openshift-marketplace -o jsonpath='{.status.defaultChannel}{"\n"}'
oc get packagemanifest <pkg> -n openshift-marketplace -o jsonpath='{range .status.channels[*]}{.name}{"\n"}{end}'
```

### 3.3 Subscription

A `Subscription` is the admin declaration that says:

> Install or track this Operator package from this catalog source and channel, with this approval policy.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operator
spec:
  channel: stable
  installPlanApproval: Manual
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Important fields:

| Field | Meaning |
|---|---|
| `spec.name` | Operator package name |
| `spec.channel` | Update channel to track |
| `spec.source` | CatalogSource name |
| `spec.sourceNamespace` | Namespace where CatalogSource exists |
| `spec.installPlanApproval` | `Automatic` or `Manual` |
| `spec.startingCSV` | Optional initial CSV to start from |
| `status.currentCSV` | Current CSV selected by resolver |
| `status.installedCSV` | CSV currently installed |
| `status.installPlanRef` | InstallPlan generated for current operation |
| `status.conditions` | Status such as `ResolutionFailed`, `InstallPlanPending`, etc. |

Commands:

```bash
oc get sub -A
oc get sub -n <operator-namespace>
oc describe sub <subscription-name> -n <operator-namespace>
oc get sub <subscription-name> -n <operator-namespace> -o yaml
```

### 3.4 InstallPlan

An `InstallPlan` is the concrete plan OLM creates to install or upgrade an Operator. It contains the resources that OLM will apply: CRDs, RBAC, Deployments, Services, CSVs, webhooks, etc.

```bash
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
oc get installplan <installplan-name> -n <operator-namespace> -o yaml
```

Important fields:

| Field | Meaning |
|---|---|
| `spec.approval` | `Manual` or `Automatic` |
| `spec.approved` | Whether a manual plan has been approved |
| `spec.clusterServiceVersionNames` | CSVs included in the plan |
| `status.phase` | Overall state, for example `RequiresApproval`, `Installing`, `Complete`, `Failed` |
| `status.conditions` | Detailed reasons and messages |
| `status.bundleLookups` | Bundle unpacking state |
| `status.plan` | Resource-level steps |

Manual approval uses this field:

```bash
oc patch installplan <installplan-name> \
  -n <operator-namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 3.5 ClusterServiceVersion / CSV

A `ClusterServiceVersion` represents one installed Operator version.

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc get csv <csv-name> -n <operator-namespace> -o yaml
```

Important CSV fields:

| Field | Meaning |
|---|---|
| `metadata.name` | Versioned Operator name, often like `operator-name.v1.2.3` |
| `spec.version` | Operator version |
| `spec.replaces` | Previous CSV in upgrade graph |
| `spec.install.spec.deployments` | Operator deployments to create/update |
| `spec.customresourcedefinitions` | Owned and required CRDs |
| `spec.install.spec.permissions` | Namespace RBAC |
| `spec.install.spec.clusterPermissions` | Cluster-wide RBAC |
| `status.phase` | CSV lifecycle phase |
| `status.reason` / `status.message` | Failure or progress detail |

CSV phases you commonly see:

```text
Pending
InstallReady
Installing
Succeeded
Replacing
Deleting
Failed
```

### 3.6 OperatorGroup

An `OperatorGroup` defines the target namespaces an Operator watches and the namespace-scope context for RBAC generation.

```bash
oc get operatorgroup -A
oc describe operatorgroup <name> -n <operator-namespace>
```

Common install modes:

| Install Mode | Meaning |
|---|---|
| `OwnNamespace` | Watches only its own namespace |
| `SingleNamespace` | Watches one selected namespace |
| `MultiNamespace` | Watches multiple selected namespaces |
| `AllNamespaces` | Watches all namespaces; often installed in `openshift-operators` |

OperatorGroup errors can block upgrades, especially when there are multiple OperatorGroups in one namespace or when target namespace configuration is invalid.

### 3.7 OperatorCondition

`OperatorCondition` lets Operators report conditions to OLM, such as whether they are upgradeable. Administrators can override some conditions in special cases, but this should be done with caution.

```bash
oc get operatorcondition -A
oc describe operatorcondition <name> -n <operator-namespace>
```

Use this only after understanding vendor documentation and support implications.

## 4. End-to-End Operator Upgrade Flow

This is the normal OLM Classic upgrade sequence:

```text
CatalogSource updated
        ↓
PackageManifest shows newer bundle in selected channel
        ↓
Subscription detects available update
        ↓
OLM resolver checks dependencies, constraints, and install modes
        ↓
InstallPlan is created
        ↓
If Automatic: OLM approves and executes plan
If Manual: admin must review and approve plan
        ↓
New CSV is created
        ↓
OLM applies required resources: CRDs, RBAC, Services, Webhooks, Deployment, etc.
        ↓
Old CSV enters Replacing / Deleting lifecycle
        ↓
New Operator deployment rolls out
        ↓
New CSV reaches Succeeded
        ↓
Operator starts reconciling operands
        ↓
Admin verifies Operator and operand health
```

### What happens before the InstallPlan appears?

Before an upgrade appears, OLM must satisfy all these checks:

1. Catalog source is healthy.
2. The selected channel contains a newer valid bundle.
3. The newer bundle has a valid upgrade edge from the installed CSV.
4. Dependencies can be resolved.
5. Required APIs/CRDs are available or installable.
6. OperatorGroup target namespace rules are valid.
7. Catalog priority/source selection is unambiguous enough for resolver.

### What happens after InstallPlan approval?

After approval, OLM starts applying resources in a controlled order. Typical resources include:

- New CSV
- CRDs
- ClusterRoles
- ClusterRoleBindings
- Roles
- RoleBindings
- ServiceAccounts
- Services
- Deployments
- Webhook configurations
- Console plugins or UI extensions where relevant
- NetworkPolicies, if shipped in bundle

### What does “Succeeded” mean?

`CSV phase: Succeeded` means OLM successfully installed the Operator resources and the Operator deployment reached required availability from OLM’s perspective.

It does **not always mean**:

- Every operand is upgraded.
- Every managed workload is healthy.
- Every custom resource is reconciled.
- Application traffic is unaffected.
- Data plane migration is complete.

Always verify the operand custom resources and pods separately.

## 5. Upgrade Channels

An **upgrade channel** is a stream of Operator versions. A subscription tracks one channel.

Examples:

```text
stable
fast
candidate
preview
stable-1.10
stable-1.11
v4.14
v4.15
latest
```

Channel naming is Operator-specific. Some Operators use release stability names, while others use minor version streams.

### Common channel strategies

| Channel Type | Typical Meaning | Production Suitability |
|---|---|---|
| `stable` | Recommended production stream | Commonly suitable |
| `fast` | Faster update availability | Use carefully |
| `candidate` | Pre-release or near-release validation | Usually not production |
| `preview` / `alpha` / `beta` | Early feature testing | Lab only unless vendor says otherwise |
| `stable-x.y` | Minor version stream | Good for controlled upgrades |
| `latest` | Latest resolvable version | Useful in labs, risky in strict production |

### Inspect channels

```bash
oc describe packagemanifest <package> -n openshift-marketplace
```

Or:

```bash
oc get packagemanifest <package> -n openshift-marketplace -o jsonpath='{range .status.channels[*]}{.name}{"\n"}{end}'
```

Get default channel:

```bash
oc get packagemanifest <package> -n openshift-marketplace \
  -o jsonpath='{.status.defaultChannel}{"\n"}'
```

Get versions in a channel:

```bash
oc get packagemanifest <package> -n openshift-marketplace -o yaml
```

### Channel change behavior

Changing channel can trigger an upgrade if the selected channel has a newer resolvable bundle.

Example:

```bash
oc patch sub <subscription-name> \
  -n <operator-namespace> \
  --type merge \
  -p '{"spec":{"channel":"stable-1.11"}}'
```

Then monitor:

```bash
oc get sub,csv,installplan -n <operator-namespace>
oc describe sub <subscription-name> -n <operator-namespace>
```

### Do not treat channels like package repositories

A channel is not just a folder of versions. It is normally backed by catalog metadata that defines valid upgrade paths. If the installed CSV does not have a valid upgrade edge to a newer bundle in that channel, no upgrade might appear even if a newer version exists in the catalog.

### Older channel movement

In normal production practice, do not use channel switching as an unsupported downgrade mechanism. Downgrades are usually not guaranteed and can be unsafe because CRDs, stored object versions, and operand state might already have changed.

## 6. Manual vs Automatic Approval

The `Subscription` field `spec.installPlanApproval` controls approval strategy.

```yaml
spec:
  installPlanApproval: Manual
```

or:

```yaml
spec:
  installPlanApproval: Automatic
```

### Automatic approval

With `Automatic`, OLM approves the InstallPlan automatically when a newer resolvable bundle appears in the selected channel.

Good for:

- Labs
- Non-critical dev clusters
- Operators with low risk
- Rapidly patched security components, if organization accepts the risk

Risk:

- New RBAC may be accepted automatically.
- New CRDs or webhooks may be applied automatically.
- Operand behavior might change during business hours.
- In disconnected clusters, a catalog refresh can trigger many upgrades at once.

### Manual approval

With `Manual`, OLM creates a pending InstallPlan but waits for administrator approval.

Good for:

- Production clusters
- Regulated environments
- Operators that manage stateful components
- Operators with broad RBAC
- Operators that manage logging, storage, networking, security, service mesh, GitOps, virtualization, or certificates

Manual approval flow:

```bash
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
oc get installplan <installplan-name> -n <operator-namespace> -o yaml
oc patch installplan <installplan-name> -n <operator-namespace> --type merge -p '{"spec":{"approved":true}}'
```

### Senior admin recommendation

For production, prefer:

```yaml
installPlanApproval: Manual
```

Then use a planned maintenance process:

1. Review release notes.
2. Confirm catalog/image availability.
3. Review InstallPlan resources.
4. Confirm backup/rollback plan.
5. Approve during a change window.
6. Verify Operator and operand health.

## 7. Inspecting the Current Operator State

Before any upgrade, collect the current state.

### 7.1 Find all installed Operators

```bash
oc get csv -A
oc get sub -A
oc get operators -A
```

### 7.2 Inspect a specific Operator

```bash
NS=<operator-namespace>
SUB=<subscription-name>

oc get sub "$SUB" -n "$NS" -o yaml
oc describe sub "$SUB" -n "$NS"
oc get csv -n "$NS"
oc get installplan -n "$NS"
oc get operatorgroup -n "$NS"
oc get events -n "$NS" --sort-by=.lastTimestamp
```

### 7.3 Extract important Subscription fields

```bash
oc get sub "$SUB" -n "$NS" \
  -o jsonpath='name={.metadata.name}{"\n"}channel={.spec.channel}{"\n"}approval={.spec.installPlanApproval}{"\n"}source={.spec.source}{"\n"}sourceNamespace={.spec.sourceNamespace}{"\n"}installedCSV={.status.installedCSV}{"\n"}currentCSV={.status.currentCSV}{"\n"}'
```

### 7.4 Check current CSV version

```bash
CSV=$(oc get sub "$SUB" -n "$NS" -o jsonpath='{.status.installedCSV}')
oc get csv "$CSV" -n "$NS" -o jsonpath='{.metadata.name}{"\n"}{.spec.version}{"\n"}{.status.phase}{"\n"}'
```

### 7.5 Check pending InstallPlans

```bash
oc get installplan -n "$NS" \
  -o custom-columns=NAME:.metadata.name,APPROVAL:.spec.approval,APPROVED:.spec.approved,PHASE:.status.phase,CSV:.spec.clusterServiceVersionNames
```

### 7.6 Check CatalogSource health

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource redhat-operators -n openshift-marketplace
oc get pods -n openshift-marketplace
```

### 7.7 Check Operator deployment rollout

```bash
oc get deploy -n "$NS"
oc rollout status deploy/<operator-deployment> -n "$NS"
oc logs deploy/<operator-deployment> -n "$NS" --tail=100
```

### 7.8 Check custom resources managed by the Operator

First identify CRDs owned by the CSV:

```bash
oc get csv "$CSV" -n "$NS" -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'
```

Then inspect custom resources:

```bash
oc get <custom-resource-kind> -A
oc describe <custom-resource-kind> <name> -n <namespace>
```

## 8. Changing Operator Update Channel

### 8.1 CLI method

Patch the subscription:

```bash
oc patch sub <subscription-name> \
  -n <operator-namespace> \
  --type merge \
  -p '{"spec":{"channel":"<new-channel>"}}'
```

Example:

```bash

  -n openshift-logging \
  --type merge \
  -p '{"spec":{"channel":"stable-6.0"}}'
```

```bash
oc get installplan -n <operator-namespace> -w
```

In another terminal:

```bash
oc describe sub <subscription-name> -n <operator-namespace>
```

Watch CSV:

```bash
oc get csv -n <operator-namespace> -w
```

```bash

```

Find InstallPlan:



```bash
oc patch installplan <installplan-name> \
  -n <operator-namespace> \
```

## 9. Manual Approval by CLI

A common real-world production task is approving a pending Operator upgrade from CLI.

### Step 1: Find pending plans

```bash
oc get installplan -n <operator-namespace>
```

Example output:

```text
NAME            CSV                                APPROVAL   APPROVED
install-abcde   file-integrity-operator.v1.3.0     Manual     false
```

### Step 2: Review the plan

```bash
oc describe installplan install-abcde -n <operator-namespace>
```

Detailed YAML:

```bash
oc get installplan install-abcde -n <operator-namespace> -o yaml
```

Look for:

- `spec.clusterServiceVersionNames`
- `status.phase`
- `status.plan[].resource.kind`
- `status.plan[].resource.name`
- `status.conditions[].message`
- CRDs being added or modified
- ClusterRoles and ClusterRoleBindings
- Webhook configurations
- Deployment changes

### Step 3: Save the plan for audit

```bash
mkdir -p operator-upgrade-audit
oc get installplan install-abcde -n <operator-namespace> -o yaml \
  > operator-upgrade-audit/installplan-install-abcde.yaml
oc get sub <subscription-name> -n <operator-namespace> -o yaml \
  > operator-upgrade-audit/subscription-before.yaml
oc get csv -n <operator-namespace> -o yaml \
  > operator-upgrade-audit/csv-before.yaml
```

### Step 4: Approve

```bash
oc patch installplan install-abcde \
  -n <operator-namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### Step 5: Monitor

```bash
oc get installplan install-abcde -n <operator-namespace> -w
oc get csv -n <operator-namespace> -w
oc get pods -n <operator-namespace> -w
```

### Step 6: Verify final state

```bash
oc get sub,csv,installplan -n <operator-namespace>
oc describe sub <subscription-name> -n <operator-namespace>
oc get events -n <operator-namespace> --sort-by=.lastTimestamp | tail -30
```

## 10. Full Production Operator Upgrade Runbook

Use this runbook for a controlled production Operator upgrade.

### Phase 0: Identify impact

Ask:

- What Operator is being upgraded?
- Which namespace contains the Operator subscription?
- Which operands does it manage?
- Does it manage production workloads?
- Does it own CRDs?
- Does it own admission webhooks?
- Does it own cluster-wide RBAC?
- Does it manage storage, network, logging, security, certificates, or GitOps?
- Is the Operator tied to the next OpenShift cluster upgrade?

Record:

```bash
OP_NS=<operator-namespace>
SUB=<subscription-name>
```

### Phase 1: Capture current state

```bash
mkdir -p upgrade-$SUB-$(date +%F-%H%M)
cd upgrade-$SUB-*

oc get sub "$SUB" -n "$OP_NS" -o yaml > sub-before.yaml
oc get csv -n "$OP_NS" -o yaml > csv-before.yaml
oc get installplan -n "$OP_NS" -o yaml > installplans-before.yaml
oc get operatorgroup -n "$OP_NS" -o yaml > operatorgroups-before.yaml
oc get events -n "$OP_NS" --sort-by=.lastTimestamp > events-before.txt
oc get pods -n "$OP_NS" -o wide > pods-before.txt
```

Capture owned CRDs:

```bash
CSV=$(oc get sub "$SUB" -n "$OP_NS" -o jsonpath='{.status.installedCSV}')
oc get csv "$CSV" -n "$OP_NS" -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}' > owned-crds.txt
```

Capture CRs for owned CRDs:

```bash
while read crd; do
  kind=$(oc get crd "$crd" -o jsonpath='{.spec.names.kind}')
  echo "### $kind" >> crs-before.txt
  oc get "$kind" -A >> crs-before.txt 2>&1 || true
done < owned-crds.txt
```

### Phase 2: Check cluster health

```bash
oc get clusterversion
oc get co
oc get nodes
oc get mcp
oc get pods -A | egrep -v 'Running|Completed'
```

Do not start an Operator upgrade if the cluster is already unstable unless the upgrade is the known fix.

### Phase 3: Check OLM health

```bash
oc get pods -n openshift-operator-lifecycle-manager
oc get pods -n openshift-marketplace
oc get catalogsource -n openshift-marketplace
oc describe sub "$SUB" -n "$OP_NS"
```

Look for conditions:

```text
CatalogSourcesUnhealthy
InstallPlanMissing
InstallPlanPending
InstallPlanFailed
ResolutionFailed
```

### Phase 4: Check available channels and target version

```bash
PKG=$(oc get sub "$SUB" -n "$OP_NS" -o jsonpath='{.spec.name}')
SRC=$(oc get sub "$SUB" -n "$OP_NS" -o jsonpath='{.spec.source}')
SRC_NS=$(oc get sub "$SUB" -n "$OP_NS" -o jsonpath='{.spec.sourceNamespace}')

oc get packagemanifest "$PKG" -n "$SRC_NS" -o yaml > package-manifest.yaml
```

Inspect channels:

```bash
oc describe packagemanifest "$PKG" -n "$SRC_NS"
```

### Phase 5: Confirm approval mode

```bash
oc get sub "$SUB" -n "$OP_NS" -o jsonpath='{.spec.installPlanApproval}{"\n"}'
```

If production and approval is `Automatic`, consider changing it to `Manual` before changing channel:

```bash
oc patch sub "$SUB" -n "$OP_NS" --type merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

### Phase 6: Trigger update

Either catalog refresh already created a pending InstallPlan, or you change the channel:

```bash
oc patch sub "$SUB" -n "$OP_NS" --type merge \
  -p '{"spec":{"channel":"<target-channel>"}}'
```

### Phase 7: Review pending InstallPlan

```bash
oc get installplan -n "$OP_NS"
PLAN=<installplan-name>
oc get installplan "$PLAN" -n "$OP_NS" -o yaml > installplan-review.yaml
oc describe installplan "$PLAN" -n "$OP_NS" > installplan-review.txt
```

Review carefully:

```bash
grep -E "kind:|name:|message:|phase:|approved:|approval:" installplan-review.yaml
```

Look especially for:

- New CRDs
- Changed CRDs
- ClusterRole permission expansion
- ValidatingWebhookConfiguration / MutatingWebhookConfiguration
- APIService
- NetworkPolicy
- SecurityContextConstraints references
- Deployment image changes
- Required APIs

### Phase 8: Approve

```bash
oc patch installplan "$PLAN" -n "$OP_NS" --type merge \
  -p '{"spec":{"approved":true}}'
```

### Phase 9: Monitor OLM objects

```bash
oc get installplan "$PLAN" -n "$OP_NS" -w
oc get csv -n "$OP_NS" -w
```

### Phase 10: Monitor Operator pod

```bash
oc get deploy,pod -n "$OP_NS"
oc rollout status deploy/<operator-deployment> -n "$OP_NS" --timeout=10m
oc logs deploy/<operator-deployment> -n "$OP_NS" --tail=200
```

### Phase 11: Verify operands

This depends on the Operator. Examples:

```bash
oc get pods -n <operand-namespace>
oc get <custom-resource-kind> -A
oc describe <custom-resource-kind> <name> -n <namespace>
oc get events -n <operand-namespace> --sort-by=.lastTimestamp | tail -50
```

For logging:

```bash
oc get clusterlogging -n openshift-logging
oc get lokistack -A
oc get pods -n openshift-logging
```

For file integrity:

```bash
oc get fileintegrities -n openshift-file-integrity
oc get pods -n openshift-file-integrity
```

For pipelines:

```bash
oc get tektonconfig -n openshift-pipelines
oc get pods -n openshift-pipelines
```

### Phase 12: Close change

Capture after-state:

```bash
oc get sub "$SUB" -n "$OP_NS" -o yaml > sub-after.yaml
oc get csv -n "$OP_NS" -o yaml > csv-after.yaml
oc get installplan -n "$OP_NS" -o yaml > installplans-after.yaml
oc get pods -n "$OP_NS" -o wide > pods-after.txt
oc get events -n "$OP_NS" --sort-by=.lastTimestamp > events-after.txt
```

Confirm:

```bash
oc get sub,csv,installplan -n "$OP_NS"
```

Success criteria:

- Subscription reports expected installed/current CSV.
- Latest CSV phase is `Succeeded`.
- InstallPlan phase is `Complete`.
- Operator Deployment is available.
- Operator logs do not show reconcile loops/errors.
- Operand CR status is healthy.
- Operand pods are running and ready.
- No new cluster degradation.

## 11. CSV Upgrade Lifecycle Deep Dive

The CSV is one of the most important upgrade troubleshooting objects.

### Typical CSV upgrade path

```text
old CSV: Succeeded
new CSV: Pending
new CSV: InstallReady
new CSV: Installing
old CSV: Replacing
new CSV: Succeeded
old CSV: Deleting / removed
```

### Important CSV checks

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc get csv <csv-name> -n <operator-namespace> -o jsonpath='{.status.phase}{"\n"}{.status.reason}{"\n"}{.status.message}{"\n"}'
```

### CSV stuck in Pending

Possible reasons:

- Required CRD is missing.
- Required API is unavailable.
- OperatorGroup is invalid.
- Dependency Operator is missing.
- Another CSV owns the same API.
- Namespace has more than one OperatorGroup.
- RBAC cannot be generated.

Check:

```bash
oc describe csv <csv-name> -n <operator-namespace>
oc get operatorgroup -n <operator-namespace>
oc describe operatorgroup <operatorgroup-name> -n <operator-namespace>
oc get crd | grep -i <operator>
oc get events -n <operator-namespace> --sort-by=.lastTimestamp | tail -50
```

### CSV stuck in Installing

Possible reasons:

- Operator Deployment failed.
- ImagePullBackOff.
- SCC/Pod Security admission blocked pod.
- Missing service account.
- Webhook certificate issue.
- Deployment does not become available.

Check:

```bash
oc get deploy,pod -n <operator-namespace>
oc describe deploy <operator-deployment> -n <operator-namespace>
oc describe pod <operator-pod> -n <operator-namespace>
oc logs <operator-pod> -n <operator-namespace>
```

### CSV Failed

Start with:

```bash
oc describe csv <csv-name> -n <operator-namespace>
oc get csv <csv-name> -n <operator-namespace> -o yaml
```

Look at:

```yaml
status:
  phase:
  reason:
  message:
  conditions:
```

Common reasons:

- `InstallComponentFailed`
- `RequirementsNotMet`
- `ComponentUnhealthy`
- `APIServiceResourceIssue`
- `WebhookResourceIssue`
- `UnsupportedOperatorGroup`

### CSV Replacing but old Operator pod still running

This can be normal for a short time. If it stays:

```bash
oc get csv -n <operator-namespace>
oc get deploy -n <operator-namespace>
oc get ownerreferences -o yaml   # not a built-in command; use oc get -o yaml and inspect
oc get events -n <operator-namespace> --sort-by=.lastTimestamp
```

Check whether the old CSV has finalizers or resources that cannot be deleted.

## 12. CRD and Custom Resource Upgrade Safety

CRDs are high risk during Operator upgrades. A CRD upgrade can affect the Kubernetes API server, stored custom resources, validation, conversion, and clients.

### What can go wrong?

- Existing custom resources become invalid under a stricter schema.
- A required field is added to an existing served version.
- Field type changes break stored objects.
- Enum values are removed.
- Default values change unexpectedly.
- Conversion webhook is unavailable.
- CRD version is removed while objects still use it.
- CRD scope changes from namespaced to cluster-scoped or opposite.

### Pre-upgrade CRD inventory

```bash
CSV=$(oc get sub <subscription-name> -n <operator-namespace> -o jsonpath='{.status.installedCSV}')
oc get csv "$CSV" -n <operator-namespace> \
  -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'
```

Back up CRDs:

```bash
mkdir crd-backup
for crd in $(oc get csv "$CSV" -n <operator-namespace> -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'); do
  oc get crd "$crd" -o yaml > crd-backup/$crd.yaml
done
```

Back up CRs:

```bash
mkdir cr-backup
for crd in $(cat owned-crds.txt); do
  kind=$(oc get crd "$crd" -o jsonpath='{.spec.names.kind}')
  oc get "$kind" -A -o yaml > cr-backup/${kind}.yaml 2>/dev/null || true
done
```

### Check stored versions

```bash
oc get crd <crd-name> -o jsonpath='{.status.storedVersions}{"\n"}'
```

If old stored versions exist, removing that version in a CRD can be blocked or dangerous. You might need a storage version migration depending on the resource and Operator guidance.

### Conversion webhook risk

If a CRD uses a conversion webhook, API requests for custom resources can fail when the webhook service is unavailable.

Check:

```bash
oc get crd <crd-name> -o yaml | grep -A20 conversion
oc get validatingwebhookconfiguration,mutatingwebhookconfiguration | grep -i <operator>
oc get svc -A | grep -i <webhook-service>
oc get endpoints -n <namespace> <webhook-service>
```

### OLM v1 CRD safety note

In OLM v1, ClusterExtension upgrades include a CRD upgrade safety preflight model that checks backwards compatibility before allowing some CRD changes. Unsafe CRD changes can block upgrades. Treat bypassing CRD safety as a last-resort operation because it can break stored CRs and API compatibility.

## 13. Operand Impact During Operator Upgrades

A common junior mistake is to verify only this:

```bash
oc get csv -n <operator-namespace>
```

A senior admin also verifies operands.

### Operator vs operand examples

| Operator | Operator Namespace | Operand Examples | Extra Verification |
|---|---|---|---|
| OpenShift Logging | `openshift-logging` | Vector, LokiStack, log collector, UI plugin | log ingestion, collector DaemonSet, storage |
| OpenShift GitOps | `openshift-gitops-operator` | Argo CD instances | ArgoCD CRs, routes, repo-server, application-controller |

| cert-manager | `cert-manager` | cert-manager controller/webhook/cainjector | Certificate issuance, webhook health |
| Service Mesh | `openshift-operators`, `istio-system` | Istiod, gateways, sidecars | mesh CRs, proxy readiness, traffic |

### Operand verification pattern


- StatefulSet rolling updates
- Database schema migrations
- Log storage migrations
- Certificate rotations
- Webhook restarts
- CR status updates
- DaemonSet rollouts across nodes

Use:

```bash

oc rollout status deploy/<name> -n <operand-ns>

oc rollout status statefulset/<name> -n <operand-ns>
```

## 14. Operator Dependencies and Resolution

OLM has a dependency resolver. An Operator bundle can declare required APIs or package dependencies. During upgrade, the resolver must choose a set of bundles that satisfies all constraints.

### Dependency-related symptoms

Subscription conditions may show:

```text
ResolutionFailed
InstallPlanMissing
InstallPlanPending
```

Check:

```bash
oc describe sub <subscription-name> -n <operator-namespace>
oc get sub <subscription-name> -n <operator-namespace> -o yaml
```

Look at:

```yaml
status:
  conditions:
  - type: ResolutionFailed
    status: "True"
    reason: ConstraintsNotSatisfiable
    message: ...
```

### Common dependency failure causes

| Cause | Explanation | Fix |
|---|---|---|
| Required API missing | New bundle requires a CRD/API not present | Install required dependency or correct catalog source |
| Conflicting versions | Another Operator provides incompatible API/version | Align channels or versions |
| Multiple catalogs with same package | Resolver may select unexpected package/source | Specify correct source/sourceNamespace; check catalog priority |
| Package not in selected channel | Channel does not contain target bundle | Select correct channel |
| Invalid upgrade graph | No valid edge from installed CSV to target CSV | Follow supported path, intermediate channel/version |
| OperatorGroup conflict | Target namespace invalid for dependencies | Fix OperatorGroup or install mode |
| Catalog unhealthy | Resolver cannot query catalog | Fix CatalogSource pod/connectivity/image pull |

### Inspect package from a specific catalog

```bash
oc get packagemanifest \
  --selector=catalog=<catalogsource-name> \
  --field-selector metadata.name=<package-name> \
  -n <catalog-namespace> -o yaml
```

### Dependency troubleshooting commands

```bash
oc describe sub <sub> -n <ns>
oc get installplan -n <ns> -o yaml
oc get csv -A | grep -i <dependency>
oc get crd | grep -i <required-api>
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <source> -n openshift-marketplace
```

## 15. Multi-Tenant and Multi-Namespace Upgrade Behavior

Operator upgrades become more complex in multi-tenant clusters.

### One namespace, multiple Operators

If multiple Operators are installed in the same namespace, their subscriptions and install plans can be resolved together. This can be useful for dependencies but can surprise administrators during upgrades.

Production recommendation:

- Install high-risk Operators in dedicated namespaces where supported.
- Avoid mixing unrelated Operators in one namespace.
- Use manual approval for shared Operator namespaces.
- Review all CSVs in the namespace before approving a plan.

```bash
oc get sub,csv,installplan,operatorgroup -n <namespace>
```

### OperatorGroup constraints

You can only have one effective OperatorGroup in many normal install scenarios. Multiple OperatorGroups in the same namespace often break CSV installation.

Check:

```bash
oc get operatorgroup -n <operator-namespace>
oc describe operatorgroup <name> -n <operator-namespace>
```

### AllNamespaces Operators and copied CSVs

Operators installed in `AllNamespaces` mode often create copied CSVs in many namespaces so users can discover that an Operator is available. On very large clusters, copied CSVs can create scale overhead. OpenShift supports disabling copied CSVs through `OLMConfig` in some versions.

Check global Operators:

```bash
oc get csv -n openshift-operators
oc get csv -n openshift
```

Check OLMConfig:

```bash
oc get olmconfig cluster -o yaml
```

### Tenant-safe upgrade planning

Before upgrading a shared Operator:

```bash
oc get <owned-kind> -A
oc get rolebinding,clusterrolebinding -A | grep -i <operator>
oc get projects --show-labels
```

Ask application owners if their CRs use deprecated fields or versions.

## 16. Disconnected / Restricted Network Operator Upgrades

In disconnected environments, Operator upgrades depend on mirrored catalog images and mirrored bundle/operand images.

### Upgrade chain in disconnected clusters

```text
Upstream catalog changes
        ↓
Mirror catalog and images to local registry
        ↓
Update local CatalogSource image/tag/digest
        ↓
CatalogSource pod restarts with new index/catalog
        ↓
PackageManifest exposes new bundles
        ↓
Subscriptions resolve upgrades
        ↓
InstallPlans created
        ↓
Manual or automatic approval
        ↓
Operator and operand images pulled from mirror
```

### Important disconnected checks

```bash
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <local-catalog> -n openshift-marketplace
oc get pods -n openshift-marketplace
```

### CatalogSource image pull failure

Symptoms:

```text
CatalogSourcesUnhealthy
TRANSIENT_FAILURE
ImagePullBackOff
ErrImagePull
unauthorized
no such host
x509: certificate signed by unknown authority
```

Check:

```bash
oc describe catalogsource <catalog> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

### Bundle image pull failure

Sometimes CatalogSource is healthy, but bundle unpack jobs fail because a bundle image is not mirrored or not accessible.

Check jobs/configmaps:

```bash
oc get jobs,configmaps -n openshift-marketplace
oc get pods -n openshift-marketplace | grep -i bundle
oc describe job <job-name> -n openshift-marketplace
oc logs job/<job-name> -n openshift-marketplace
```

### Image pull secret for private catalogs

If a custom catalog or bundle is in a private registry, link pull secret to the relevant service account.

```bash
oc create secret docker-registry <secret-name> \
  --docker-server=<registry> \
  --docker-username=<user> \
  --docker-password=<password> \
  --docker-email=<email> \
  -n openshift-marketplace

oc secrets link <service-account> <secret-name> \
  -n openshift-marketplace \
  --for=pull
```

### Production disconnected best practice

- Use digest-pinned mirrored catalog images where possible.
- Promote catalogs through dev → stage → prod.
- Keep a record of catalog image digests.
- Avoid automatic approval if catalog refresh can expose multiple upgrades.
- Mirror both Operator bundle images and related operand images.
- Validate `relatedImages` are included by the Operator vendor.
- Test upgrades in a disconnected staging cluster before production.

## 17. OLM v1 / ClusterExtension Upgrade Model

OpenShift also includes OLM v1 for cluster extensions. OLM v1 uses a different API model from OLM Classic.

### OLM Classic vs OLM v1

| Area | OLM Classic | OLM v1 |
|---|---|---|
| Primary install object | `Subscription` | `ClusterExtension` |
| Install plan object | `InstallPlan` | Different extension lifecycle model |
| Version targeting | Channel via subscription, optional startingCSV | Channel, exact version, or version range in CR |
| Scope | Namespace-scoped or cluster-wide depending on OperatorGroup | ClusterExtension is cluster-scoped, installs into configured namespace |
| Console support | Managed through console for classic Operators | CLI-oriented in current documented model |
| CRD safety | Classic behavior depends on OLM/Kubernetes/API mechanics | CRD upgrade safety preflight model documented for cluster extensions |

### Example ClusterExtension with channel

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterExtension
metadata:
  name: example-extension
spec:
  namespace: example-namespace
  serviceAccount:
    name: example-installer
  source:
    sourceType: Catalog
    catalog:
      packageName: example-operator
      channels:
        - stable
```

If a channel is used, OLM v1 can update to the latest resolvable release in that channel when catalog updates are available.

### Example ClusterExtension pinned to version

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterExtension
metadata:
  name: example-extension
spec:
  namespace: example-namespace
  serviceAccount:
    name: example-installer
  source:
    sourceType: Catalog
    catalog:
      packageName: example-operator
      version: "1.11.1"
```

When a target version is specified, the extension is pinned until the CR is edited.

### Example version range

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterExtension
metadata:
  name: example-extension
spec:
  namespace: example-namespace
  serviceAccount:
    name: example-installer
  source:
    sourceType: Catalog
    catalog:
      packageName: example-operator
      version: ">=1.11.0 <1.12.0"
```

Version ranges help enforce controlled minor version movement.

### OLM v1 status checks

```bash
oc get clusterextensions
oc describe clusterextension <name>
oc get clusterextension <name> -o yaml
```

Look at:

```yaml
status:
  conditions:
  install:
  activeRevisions:
```

### CRD safety in OLM v1

When a ClusterExtension provides CRDs, OLM v1 can run CRD upgrade safety checks. Unsafe changes can block the upgrade. Examples of dangerous changes include adding a required field to an existing version, removing a field, changing field type, changing defaults, removing enum values, making min/max constraints stricter, changing scope, or removing stored versions.

Do not disable CRD safety unless:

- Vendor documentation explicitly tells you to.
- You have backed up CRDs and CRs.
- You understand stored versions.
- You have tested the exact upgrade in staging.
- You have an approved change and recovery plan.

## 18. Troubleshooting Operator Upgrade Failures

This section is designed like a real support bridge checklist.

---

### 18.1 No upgrade appears

Symptoms:

- Subscription remains `AtLatestKnown` or shows no pending InstallPlan.
- Expected new version is not visible.

Check:

```bash
oc get sub <sub> -n <ns> -o yaml
oc describe sub <sub> -n <ns>
oc describe packagemanifest <package> -n openshift-marketplace
oc get catalogsource -n openshift-marketplace
```

Possible causes:

| Cause | Check | Fix |
|---|---|---|
| Catalog does not contain new version | `oc describe packagemanifest` | Update/mirror catalog |
| Wrong channel | `spec.channel` | Patch subscription channel |
| Wrong source | `spec.source` | Correct Subscription source |
| Invalid upgrade graph | PackageManifest entries / vendor docs | Upgrade through intermediate version/channel |
| Catalog unhealthy | `CatalogSourcesUnhealthy` | Fix CatalogSource pod/connectivity |
| Subscription pinned by startingCSV misconception | `startingCSV` is only initial install | Use channel/version guidance; do not rely on startingCSV for ongoing pinning |

---

### 18.2 InstallPlanPending / RequiresApproval

Symptoms:

```text
InstallPlanPending
status.phase: RequiresApproval
spec.approved: false
```

This is normal for manual approval.

Commands:

```bash
oc get installplan -n <ns>
oc describe installplan <plan> -n <ns>
oc patch installplan <plan> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

Do not approve blindly. Review what will be installed.

---

### 18.3 InstallPlanFailed

Symptoms:

```text
InstallPlanFailed
status.phase: Failed
```

Check:

```bash
oc describe installplan <plan> -n <ns>
oc get installplan <plan> -n <ns> -o yaml
oc get events -n <ns> --sort-by=.lastTimestamp | tail -50
```

Common causes:

- Failed CRD creation/update.
- RBAC conflict.
- Webhook conflict.
- APIService conflict.
- Existing resource owned by another CSV or extension.
- Bundle unpack failed.

Look at `status.conditions[].message` and `status.plan[].status`.

---

### 18.4 ResolutionFailed

Symptoms:

```text
ResolutionFailed
ConstraintsNotSatisfiable
```

Check:

```bash
oc describe sub <sub> -n <ns>
oc get sub <sub> -n <ns> -o yaml
oc get csv -A
oc get crd
oc get packagemanifest <package> -n openshift-marketplace -o yaml
```

Possible fixes:

- Install dependency Operator.
- Change to correct channel.
- Use correct catalog source.
- Remove conflicting old CSV only after confirming it is safe.
- Fix OperatorGroup target namespaces.
- Use vendor-supported upgrade path.

---

### 18.5 CatalogSourcesUnhealthy

Symptoms:

```text
CatalogSourcesUnhealthy
TRANSIENT_FAILURE
ImagePullBackOff
```

Check:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <source> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

Common causes:

- Catalog image not pullable.
- Registry auth missing.
- DNS failure.
- Proxy issue.
- Custom CA issue.
- Mirror registry not reachable.
- Catalog image incompatible/corrupt.

Fix according to event message.

---

### 18.6 Bundle unpack job failing

Symptoms:

- Subscription stuck.
- Jobs in `openshift-marketplace` failing.
- Image pull errors for bundle images.

Check:

```bash
oc get job,pod,configmap -n openshift-marketplace
oc describe job <job> -n openshift-marketplace
oc logs job/<job> -n openshift-marketplace
```

Fix:

- Mirror missing bundle image.
- Fix registry credentials.
- Fix proxy or CA.
- Delete failed bundle unpack job/configmap after correcting image access if documented/appropriate.
- Refresh subscription if it remains stuck.

---

### 18.7 Operator pod ImagePullBackOff

Check:

```bash
oc get pods -n <operator-ns>
oc describe pod <operator-pod> -n <operator-ns>
oc get secret -n <operator-ns>
oc get serviceaccount -n <operator-ns> -o yaml
```

Fix:

- Add image pull secret.
- Verify mirrored Operator image.
- Verify ImageContentSourcePolicy/ImageDigestMirrorSet.
- Fix registry CA.
- Fix proxy.

---

### 18.8 Operator pod CrashLoopBackOff

Check:

```bash
oc logs <pod> -n <operator-ns> --previous
oc logs <pod> -n <operator-ns>
oc describe pod <pod> -n <operator-ns>
```

Common causes:

- Missing config.
- Permission denied.
- Invalid environment variables from Subscription config.
- Webhook certificate issue.
- API version incompatibility.
- Required CRD missing.
- Operand CR has invalid field after upgrade.

Fix depends on logs.

---

### 18.9 CSV stuck Failed due to permission/RBAC

Check:

```bash
oc describe csv <csv> -n <operator-ns>
oc auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa> -n <target-ns>
oc get role,rolebinding,clusterrole,clusterrolebinding | grep -i <operator>
```

Common in scoped Operator installs where the OperatorGroup service account lacks permissions.

---

### 18.10 Webhook errors after upgrade

Symptoms:

```text
failed calling webhook
x509: certificate signed by unknown authority
service not found
no endpoints available for service
context deadline exceeded
```

Check:

```bash
oc get validatingwebhookconfiguration,mutatingwebhookconfiguration | grep -i <operator>
oc get svc -A | grep -i webhook
oc get endpoints -n <namespace> <webhook-service>
oc get pods -n <namespace> -l <webhook-label>
oc logs deploy/<webhook-deployment> -n <namespace>
```

Fix:

- Restore webhook pod availability.
- Fix service selector/endpoints.
- Rotate or restore serving certs.
- Check CA bundle injection.
- Check network policy blocking API server to webhook.

---

### 18.11 CRD update blocked or unsafe

Check:

```bash
oc describe installplan <plan> -n <ns>
oc describe csv <csv> -n <ns>
oc get crd <crd-name> -o yaml
oc get events -n <ns> --sort-by=.lastTimestamp | tail -100
```

Look for:

- Schema validation failure.
- Stored version removal.
- Scope change.
- Conversion webhook failure.
- Existing CRs invalid under new schema.

Fix:

- Follow vendor migration instructions.
- Migrate CRs to supported API version.
- Fix invalid CR fields.
- Ensure conversion webhook is healthy.
- Do not manually force CRD replacement in production unless advised by vendor/support.

---

### 18.12 Subscription stuck after inaccessible bundle image

A known recovery pattern is to refresh the failing subscription after image access is fixed:

```bash
oc get sub,csv -n <namespace>
oc delete subscription <subscription-name> -n <namespace>
oc delete csv <csv-name> -n <namespace>
oc get job,configmap -n openshift-marketplace
oc delete job <job-name> -n openshift-marketplace
oc delete configmap <configmap-name> -n openshift-marketplace
```

Then reinstall the Operator through the catalog.

Use this with care because deleting a CSV can remove Operator controller resources. Understand operand impact before doing this in production.

## 19. Rollback, Downgrade, and Recovery Strategy

### 19.1 There is no universal safe rollback

Operator downgrades are not like rolling back a Deployment. An Operator upgrade may have:

- Changed CRDs.
- Updated stored CR versions.
- Changed operand data format.
- Migrated databases.
- Modified RBAC.
- Rotated certificates.
- Changed finalizers.
- Changed webhooks.

Because of this, a simple downgrade to an older CSV may be unsupported.

### 19.2 What to do before upgrade

Prepare rollback options:

```bash
oc get sub <sub> -n <ns> -o yaml > sub-before.yaml
oc get csv -n <ns> -o yaml > csv-before.yaml
oc get crd <crd> -o yaml > crd-before.yaml
oc get <custom-resource-kind> -A -o yaml > crs-before.yaml
```

For stateful operands:

- Take database backups.
- Snapshot PVCs where supported.
- Export CRs.
- Confirm application-level restore procedure.
- Confirm vendor-supported rollback path.

### 19.3 Practical recovery options

| Situation | Recovery Option |
|---|---|
| InstallPlan pending and not approved | Delete pending InstallPlan or leave unapproved; fix subscription/channel |
| Upgrade started but CSV failed before operand change | Fix failure and let OLM complete; rollback may not be needed |
| Operator pod fails but CRDs unchanged | Patch config, image access, RBAC, proxy/CA issue |
| New Operator breaks operand reconciliation | Consult vendor docs/support; possibly pause/scale Operator temporarily while stabilizing |
| CRD/schema issue | Fix CRs, conversion webhooks, or follow migration guidance |
| Severe production failure | Restore from backup/snapshot; engage Red Hat/vendor support |

### 19.4 Pausing reconciliation

Some Operators support pausing reconciliation through their custom resource. Others do not. Scaling Operator deployment to zero is a last-resort containment action and can make things worse if the Operator manages critical control loops.

Example only after impact review:

```bash
oc scale deploy/<operator-deployment> -n <operator-ns> --replicas=0
```

Restore:

```bash
oc scale deploy/<operator-deployment> -n <operator-ns> --replicas=1
```

Do not do this for core cluster Operators managed by CVO.

## 20. Production Best Practices

### 20.1 Use Manual approval for production

```bash
oc patch sub <sub> -n <ns> --type merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

### 20.2 Separate high-risk Operators

Use dedicated namespaces for Operators that manage important systems:

- Logging
- GitOps
- Pipelines
- Service Mesh
- Storage
- Security/compliance
- Certificates
- Virtualization
- Monitoring extensions

### 20.3 Review RBAC changes

Before approving:

```bash
oc get installplan <plan> -n <ns> -o yaml | grep -A5 -B2 -E 'ClusterRole|ClusterRoleBinding|Role|RoleBinding'
```

### 20.4 Verify CRDs and CRs

```bash
oc get crd | grep -i <operator>
oc get <kind> -A
```

### 20.5 Keep catalogs controlled

Especially in disconnected clusters:

- Mirror tested catalog digests.
- Promote catalog images through environments.
- Avoid uncontrolled floating `latest` tags in production.
- Document catalog source image digests.

### 20.6 Avoid surprise bulk upgrades

If many Subscriptions are automatic, a catalog refresh can trigger many Operator upgrades. Before updating catalog images:

```bash
oc get sub -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,CHANNEL:.spec.channel,APPROVAL:.spec.installPlanApproval,SOURCE:.spec.source
```

Change critical Operators to manual approval.

### 20.7 Check OpenShift upgrade readiness

Before cluster upgrade:

```bash
oc get co
oc get clusterversion
oc adm upgrade
oc get sub -A
oc get csv -A | egrep -v 'Succeeded|Copied'
```

Operators with compatibility limits or un-upgraded bundles can block or complicate the next cluster minor update.

### 20.8 Maintain an Operator inventory

At minimum, track:

| Item | Example |
|---|---|
| Operator package | `cluster-logging` |
| Namespace | `openshift-logging` |
| Subscription | `cluster-logging` |
| Channel | `stable-6.0` |
| Approval | `Manual` |
| Current CSV | `cluster-logging.v6.0.1` |
| Source | `redhat-operators` |
| Operand CRs | `ClusterLogging`, `LokiStack` |
| Owner team | Platform / Observability |
| Maintenance window | Monthly / quarterly |

Generate basic inventory:

```bash
oc get sub -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,PKG:.spec.name,CHANNEL:.spec.channel,APPROVAL:.spec.installPlanApproval,SOURCE:.spec.source,INSTALLED:.status.installedCSV
```

## 22. Interview / Exam-Level Questions

### Q1. What object controls whether an Operator upgrade is manual or automatic?

`Subscription.spec.installPlanApproval`.

### Q2. What object do you patch to approve a pending manual upgrade?

The `InstallPlan`:

```bash
oc patch installplan <plan> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

### Q3. What is the difference between `currentCSV` and `installedCSV`?

- `installedCSV` is the CSV currently installed.
- `currentCSV` is the CSV selected by resolver as current target. During upgrade, these can differ.

### Q4. Why might a newer Operator version exist in the catalog but no upgrade appears?

Possible reasons:

- Subscription tracks a different channel.
- No valid upgrade edge from installed CSV.
- Dependency resolution failed.
- Catalog source unhealthy.
- Wrong catalog source selected.
- Package not available in selected channel.

### Q5. Why is `CSV Succeeded` not enough after an Operator upgrade?

Because `CSV Succeeded` verifies Operator installation, not full operand health. The Operator may still need to reconcile managed workloads, perform migrations, roll pods, or update custom resource status.

### Q6. What are common Subscription conditions during failed upgrades?

```text
CatalogSourcesUnhealthy
InstallPlanMissing
InstallPlanPending
InstallPlanFailed
ResolutionFailed
```

### Q7. Which namespace usually contains default catalog sources?

`openshift-marketplace`.

### Q8. Which namespace contains core OLM controllers?

`openshift-operator-lifecycle-manager`.

### Q9. What is an OperatorGroup used for?

It defines the target namespaces for Operators installed in a namespace and helps OLM generate required RBAC for those target namespaces.

### Q10. Why are disconnected Operator upgrades more complex?

Because you must mirror not only the catalog image but also Operator bundle images and related operand images. Catalog refresh, mirror configuration, registry authentication, proxy, and CA trust all affect upgrade success.

## Final Senior Admin Summary

An Operator upgrade is a platform lifecycle event. Treat it with the same discipline as a cluster change:

1. Know the Operator namespace, Subscription, channel, source, CSV, and operands.
2. Confirm OLM and CatalogSource health.
3. Prefer manual approval in production.
4. Review InstallPlan resources before approval.
5. Watch CSV, Operator deployment, and operand health.
6. Pay special attention to CRDs, webhooks, RBAC, and disconnected image availability.
7. Never assume downgrade is safe.
8. Keep audit artifacts before and after the change.

The experienced OpenShift administrator does not just run `oc patch installplan`; they understand what OLM is about to apply, what APIs may change, what workloads may reconcile, and how to recover if the upgrade fails.
