# OperatorHub in OpenShift Operator Management

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and OpenShift/Kubernetes professionals with production experience.  
**Level:** Deep-dive / 10+ years administration mindset.  
**Scope:** OpenShift OperatorHub, Software Catalog terminology, Operator Lifecycle Manager (OLM), CatalogSources, Subscriptions, InstallPlans, OperatorGroups, security, disconnected environments, troubleshooting, and production best practices.

---

## 1. Version and Terminology Note

In older OpenShift documentation and day-to-day admin language, administrators often say **OperatorHub** when they mean the web console area used to discover and install Operators.

In recent OpenShift releases, Red Hat has renamed parts of the web console navigation:

- **OperatorHub** in the console is now commonly presented as **Software Catalog**.
- The **Operators** navigation area is now commonly presented as **Ecosystem**.
- The API object named **OperatorHub** still exists and is used to configure default catalog sources.
- OLM Classic resources such as `CatalogSource`, `Subscription`, `InstallPlan`, `ClusterServiceVersion`, and `OperatorGroup` are still operationally important.

So, in real administration, you must understand both names:

| Common/Older Name | Newer Console Name / Concept | Practical Meaning |
|---|---|---|
| OperatorHub | Software Catalog | Web UI to discover/install Operators |
| Operators menu | Ecosystem menu | Console navigation area for Operators and related services |
| OperatorHub CR | `operatorhub.config.openshift.io/cluster` | Cluster-level configuration for default catalogs |
| OLM Classic | Operator Lifecycle Manager classic model | Operator installation and upgrade system based on CSVs, Subscriptions, InstallPlans |

## 2. What is OperatorHub?

**OperatorHub** is the OpenShift catalog experience used to discover, inspect, and install Kubernetes Operators into a cluster.

At a high level:

> OperatorHub is not the Operator itself. It is the discovery and catalog layer that shows available Operators from configured catalogs.

An OperatorHub entry usually provides:

- Operator name
- Provider
- Description
- Supported install modes
- Available channels
- Current version
- Upgrade path
- Required APIs
- Provided APIs
- Required permissions
- Installation namespace options
- Documentation and links

In production, OperatorHub is important because it is the entry point for installing platform components such as:

- OpenShift Logging
- OpenShift GitOps
- OpenShift Pipelines
- OpenShift Service Mesh
- OpenShift Data Foundation
- File Integrity Operator
- Compliance Operator
- Advanced Cluster Security
- Serverless
- AMQ, Quay, databases, monitoring tools, storage tools, and many partner Operators

## 3. Why OperatorHub Matters to an Advanced Administrator

For a beginner, OperatorHub is simply a UI page.

For an advanced administrator, OperatorHub is part of a complete Operator supply chain:

```text
Operator image + bundle image
        ↓
Index image / file-based catalog
        ↓
CatalogSource
        ↓
Package / channel / version metadata
        ↓
Subscription
        ↓
InstallPlan
        ↓
ClusterServiceVersion
        ↓
Operator Deployment + RBAC + CRDs + Webhooks
        ↓
Custom Resources managed by the Operator
```

A senior OpenShift administrator must know:

- Which catalog is the source of an Operator
- Whether the Operator is Red Hat supported, vendor supported, or community supported
- Which namespaces the Operator can watch
- Which permissions the Operator requests
- Which CRDs it installs
- How upgrades are approved
- How to pin versions or channels
- How to troubleshoot catalog resolution failures
- How to mirror catalogs for disconnected clusters
- How to disable unsafe or unnecessary catalogs
- How to control Operator availability in multi-tenant clusters

## 4. Main Components Behind OperatorHub

### 4.1 Web Console / Software Catalog

The console provides the human-facing interface.

You can use it to:

- Search for Operators
- Filter by provider or category
- Read Operator metadata
- Install an Operator
- Select update channel
- Select installation namespace
- Select approval strategy
- View installed Operators
- Create Operator-managed custom resources

However, the console does not do magic. When you install an Operator from the console, it creates Kubernetes resources such as:

- `Subscription`
- `OperatorGroup`
- `InstallPlan`
- `ClusterServiceVersion`

### 4.2 Operator Lifecycle Manager

**Operator Lifecycle Manager (OLM)** manages the lifecycle of Operators.

OLM is responsible for:

- Discovering Operators from catalogs
- Resolving dependencies
- Creating install plans
- Installing CRDs
- Creating deployments for Operators
- Creating RBAC required by Operators
- Handling upgrades
- Tracking Operator status through CSVs
- Enforcing namespace-scoped Operator installation rules

OLM runs mainly in the `openshift-operator-lifecycle-manager` namespace.

Useful resources:

```bash
oc get pods -n openshift-operator-lifecycle-manager
oc get deployments -n openshift-operator-lifecycle-manager
oc get csv -A
oc get subscriptions -A
oc get installplans -A
oc get operatorgroups -A
```

Important OLM components usually include:

```text
olm-operator
catalog-operator
package-server-manager
packageserver
```

### 4.3 CatalogSource

A `CatalogSource` tells OLM where to get Operator metadata from.

Default catalog sources usually exist in:

```text
openshift-marketplace
```

Example:

```bash
oc get catalogsource -n openshift-marketplace
```

Typical default catalog sources:

```text
redhat-operators
certified-operators
community-operators
redhat-marketplace
```

Not every cluster has every catalog enabled. This depends on cluster version, installation configuration, marketplace settings, and disconnected configuration.

### 4.4 PackageManifest

A `PackageManifest` is a view of available Operator packages from catalogs.

Useful commands:

```bash
oc get packagemanifest -n openshift-marketplace
oc get packagemanifest -n openshift-marketplace | grep -i logging
oc describe packagemanifest cluster-logging -n openshift-marketplace
```

Package manifests are useful for finding:

- Available channels
- Default channel
- Catalog source
- Package name
- Operator versions
- Install modes

### 4.5 Subscription

A `Subscription` tells OLM:

- Which Operator package to install
- Which channel to follow
- Which catalog source to use
- Which namespace to install into
- Whether upgrades are automatic or manual

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: file-integrity-operator
  namespace: openshift-file-integrity
spec:
  channel: stable
  name: file-integrity-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
```

### 4.6 InstallPlan

An `InstallPlan` is the execution plan generated by OLM.

It contains the actions OLM needs to perform, such as:

- Create CRDs
- Create service accounts
- Create roles and role bindings
- Create cluster roles and cluster role bindings
- Create deployments
- Install or upgrade CSVs

Check install plans:

```bash
oc get installplan -A
oc describe installplan <installplan-name> -n <namespace>
```

For manual approval:

```bash
oc patch installplan <installplan-name> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

### 4.7 ClusterServiceVersion

A `ClusterServiceVersion`, or `CSV`, represents a specific installed Operator version.

It includes:

- Operator metadata
- Owned CRDs
- Required CRDs
- Required permissions
- Install strategy
- Deployment spec
- Status and phase

Useful commands:

```bash
oc get csv -A
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
```

Common CSV phases:

| Phase | Meaning |
|---|---|
| `Pending` | Waiting for dependencies, permissions, or install plan execution |
| `Installing` | OLM is installing resources |
| `Succeeded` | Operator is installed successfully |
| `Failed` | Installation or upgrade failed |
| `Replacing` | Operator is being upgraded/replaced |

### 4.8 OperatorGroup

An `OperatorGroup` defines the namespace scope an Operator watches.

It answers this question:

> Which namespace or namespaces is this Operator allowed to manage?

Example single namespace OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: file-integrity-operator-group
  namespace: openshift-file-integrity
spec:
  targetNamespaces:
  - openshift-file-integrity
```

Important rule:

> Usually, only one OperatorGroup should exist in an Operator installation namespace.

Multiple OperatorGroups in the same namespace can cause installation failure.

## 5. Default Operator Catalogs

OpenShift commonly provides these catalog sources.

### 5.1 Red Hat Operators

```text
redhat-operators
```

Contains Red Hat-provided Operators.

Examples:

- OpenShift Logging
- OpenShift GitOps
- OpenShift Pipelines
- Compliance Operator
- File Integrity Operator
- OpenShift Data Foundation
- Service Mesh

Usually this is the most trusted source for production clusters because these Operators are part of Red Hat's supported ecosystem.

### 5.2 Certified Operators

```text
certified-operators
```

Contains vendor Operators certified for OpenShift.

Examples may include Operators from storage, database, security, observability, and networking vendors.

Support is normally shared between Red Hat and the vendor depending on the component.

### 5.3 Community Operators

```text
community-operators
```

Contains community-provided Operators.

Use carefully in production. Community Operators may not have the same support guarantees as Red Hat Operators.

### 5.4 Red Hat Marketplace

```text
redhat-marketplace
```

Used for Operators delivered through the Red Hat Marketplace ecosystem. Availability depends on cluster version and configuration.

### 5.5 Custom Catalogs

You can create your own catalog source for:

- Internal platform Operators
- Mirrored Operators
- Disconnected clusters
- Version-pinned catalog sets
- Security-approved Operator lists

## 6. OperatorHub API Object

OpenShift has a cluster-scoped API object:

```text
operatorhub.config.openshift.io/cluster
```

Check it:

```bash
oc get operatorhub cluster -o yaml
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: OperatorHub
metadata:
  name: cluster
spec:
  disableAllDefaultSources: false
  sources:
  - name: community-operators
    disabled: true
```

### 6.1 Disable All Default Catalog Sources

In restricted or regulated clusters, you may want to disable all default sources:

```bash
oc patch operatorhub cluster --type merge -p '{"spec":{"disableAllDefaultSources":true}}'
```

Verify:

```bash
oc get operatorhub cluster -o yaml
oc get catalogsource -n openshift-marketplace
```

### 6.2 Disable One Default Catalog Source

Example: disable community operators.

```bash
oc patch operatorhub cluster --type merge -p '{"spec":{"sources":[{"name":"community-operators","disabled":true}]}}'
```

Verify:

```bash
oc get operatorhub cluster -o yaml
oc get catalogsource community-operators -n openshift-marketplace
```

### 6.3 Re-enable a Catalog Source

```bash
oc patch operatorhub cluster --type merge -p '{"spec":{"sources":[{"name":"community-operators","disabled":false}]}}'
```

### 6.4 Why Disable Catalogs?

Production reasons include:

- Reduce unsupported software installation
- Enforce compliance policy
- Avoid accidental installation of community Operators
- Reduce catalog pod resource usage
- Control upgrade exposure
- Use only mirrored internal catalogs
- Prevent internet dependency in restricted clusters

## 7. CatalogSource Deep Dive

A `CatalogSource` defines a catalog server that OLM can query.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: registry.redhat.io/redhat/redhat-operator-index:v4.22
  displayName: Red Hat Operators
  publisher: Red Hat
```

Important fields:

| Field | Meaning |
|---|---|
| `metadata.name` | CatalogSource name used by Subscriptions |
| `metadata.namespace` | Usually `openshift-marketplace` |
| `spec.sourceType` | Commonly `grpc` |
| `spec.image` | Index/catalog image |
| `spec.displayName` | Display name in catalog UI |
| `spec.publisher` | Catalog publisher |
| `spec.updateStrategy` | Controls catalog pod polling/update behavior |

### 7.1 CatalogSource Pod

A catalog source usually creates a pod in `openshift-marketplace`.

```bash
oc get pods -n openshift-marketplace
oc get catalogsource -n openshift-marketplace
oc describe catalogsource redhat-operators -n openshift-marketplace
```

Expected pod examples:

```text
redhat-operators-xxxxx
certified-operators-xxxxx
community-operators-xxxxx
```

### 7.2 CatalogSource Status

Check status:

```bash
oc get catalogsource redhat-operators -n openshift-marketplace -o yaml
```

Look for:

```yaml
status:
  connectionState:
    address: redhat-operators.openshift-marketplace.svc:50051
    lastConnect: ...
    lastObservedState: READY
```

If `lastObservedState` is not `READY`, OLM may not be able to resolve Operators from that catalog.

### 7.3 Common CatalogSource Problems

| Problem | Symptoms | Likely Cause |
|---|---|---|
| Catalog pod not running | `ImagePullBackOff` | Registry auth, proxy, disconnected issue |
| Catalog not visible | No PackageManifest | CatalogSource disabled or broken |
| Install fails | Resolution error | Missing package/channel/dependency |
| Wrong version shown | Unexpected channel | Subscription follows different channel |
| Catalog stale | Old Operator versions | Catalog image not updated or mirrored catalog outdated |

## 8. Operator Package, Channel, and Version Model

### 8.1 Package

A package is the Operator product name.

Example:

```text
cluster-logging
openshift-gitops-operator
file-integrity-operator
compliance-operator
```

Find packages:

```bash
oc get packagemanifest -n openshift-marketplace | grep -i integrity
```

### 8.2 Channel

A channel is an update stream.

Examples:

```text
stable
stable-5.9
stable-6.0
fast
candidate
preview
```

The channel controls which upgrades the Subscription follows.

A production cluster should generally use stable channels unless a vendor explicitly recommends otherwise.

### 8.3 Version

Each Operator version is represented by a CSV.

Example:

```text
file-integrity-operator.v1.3.0
cluster-logging.v6.2.0
```

### 8.4 Channel Head

A Subscription generally tracks the channel head.

Important point:

> The channel head is the latest version in that channel's upgrade graph, not always simply the highest semantic version available across all channels.

This matters when administrators ask:

> Why did my Operator not upgrade to the highest version shown in another channel?

Answer: because your Subscription follows its configured channel and its upgrade graph.

## 9. Installing an Operator from CLI

The web console is useful, but an advanced administrator must be comfortable installing Operators using YAML.

### 9.1 Example: File Integrity Operator

Create namespace:

```bash
oc create namespace openshift-file-integrity
```

Create OperatorGroup:

```bash
cat <<'EOF' | oc apply -f -
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: file-integrity-operator-group
  namespace: openshift-file-integrity
spec:
  targetNamespaces:
  - openshift-file-integrity
EOF
```

Create Subscription:

```bash
cat <<'EOF' | oc apply -f -
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: file-integrity-operator
  namespace: openshift-file-integrity
spec:
  channel: stable
  name: file-integrity-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
EOF
```

Verify:

```bash
oc get subscription -n openshift-file-integrity
oc get installplan -n openshift-file-integrity
oc get csv -n openshift-file-integrity
oc get pods -n openshift-file-integrity
```

### 9.2 Generic Operator Install Flow

```bash
# 1. Find package
oc get packagemanifest -n openshift-marketplace | grep -i <operator>

# 2. Inspect package
oc describe packagemanifest <package-name> -n openshift-marketplace

# 3. Create namespace
oc create namespace <operator-namespace>

# 4. Create OperatorGroup if needed
oc apply -f operatorgroup.yaml

# 5. Create Subscription
oc apply -f subscription.yaml

# 6. Watch install
watch 'oc get subscription,installplan,csv,pods -n <operator-namespace>'
```

### 9.3 Create Subscription from Existing Console Choices

When you install from the console, export the result to understand what was created:

```bash
oc get subscription -n <namespace> -o yaml
oc get operatorgroup -n <namespace> -o yaml
oc get installplan -n <namespace> -o yaml
oc get csv -n <namespace> -o yaml
```

This is very useful for building GitOps-managed Operator installations.

## 10. Operator Installation Modes

Operators declare supported install modes in their CSV.

Common install modes:

| Install Mode | Meaning |
|---|---|
| `OwnNamespace` | Operator watches only its own namespace |
| `SingleNamespace` | Operator watches one selected namespace |
| `MultiNamespace` | Operator watches multiple selected namespaces |
| `AllNamespaces` | Operator watches the whole cluster |

Check install modes:

```bash
oc describe packagemanifest <package-name> -n openshift-marketplace
oc get csv <csv-name> -n <namespace> -o yaml | grep -A20 installModes
```

### 10.1 AllNamespaces Example

Some Operators install into a system namespace and watch all namespaces.

OperatorGroup example:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-operators
  namespace: openshift-operators
spec: {}
```

An empty `spec` can mean all namespaces depending on the Operator and OLM behavior.

### 10.2 SingleNamespace Example

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: my-operator-group
  namespace: my-operator-ns
spec:
  targetNamespaces:
  - my-app-ns
```

### 10.3 OperatorGroup Mistakes

Common mistakes:

- Creating two OperatorGroups in one namespace
- Installing an Operator in a namespace with an incompatible OperatorGroup
- Installing a namespace-scoped Operator into `openshift-operators` accidentally
- Expecting a SingleNamespace Operator to manage all namespaces
- Forgetting that an Operator may not support all install modes

Troubleshoot:

```bash
oc get operatorgroup -A
oc describe operatorgroup <name> -n <namespace>
oc describe csv <csv-name> -n <namespace>
```

## 11. Automatic vs Manual Approval

Subscriptions use:

```yaml
installPlanApproval: Automatic
```

or:

```yaml
installPlanApproval: Manual
```

### 11.1 Automatic Approval

OLM automatically approves install plans and upgrades.

Good for:

- Labs
- Non-production environments
- Low-risk Operators
- Environments with automated testing and rollback strategy

Risk:

- Operator upgrades can happen unexpectedly when catalog content changes.

### 11.2 Manual Approval

OLM creates an InstallPlan, but an administrator must approve it.

Good for:

- Production
- Regulated environments
- Change-controlled clusters
- Operators with high privilege
- Storage, networking, security, service mesh, logging, and cluster-wide Operators

Check pending install plans:

```bash
oc get installplan -A
oc get installplan -n <namespace>
```

Approve:

```bash
oc patch installplan <installplan-name> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

Watch:

```bash
watch 'oc get installplan,csv,pods -n <namespace>'
```

### 11.3 Production Recommendation

For production clusters:

- Use `Manual` for critical Operators.
- Document approval procedure.
- Review release notes before approval.
- Validate upgrade in lower environment first.
- Use GitOps to track Subscription and OperatorGroup manifests.
- Mirror and pin catalog versions where possible.

## 12. OperatorHub and RBAC

Operators often need elevated permissions.

A CSV may request:

- `Role`
- `RoleBinding`
- `ClusterRole`
- `ClusterRoleBinding`
- Service accounts
- Access to CRDs
- Access to secrets/configmaps
- Access to pods, deployments, nodes, storage, network APIs

Before installing an Operator, inspect permissions:

```bash
oc describe packagemanifest <package-name> -n openshift-marketplace
oc get csv <csv-name> -n <namespace> -o yaml
```

Look for:

```yaml
install:
  spec:
    permissions:
    clusterPermissions:
```

### 12.1 Security Questions Before Installing an Operator

Ask:

1. Is this Operator Red Hat supported, certified, or community?
2. Does it request cluster-wide permissions?
3. Does it install admission webhooks?
4. Does it manage secrets?
5. Does it access node-level resources?
6. Does it run privileged pods?
7. Does it use SCCs or SecurityContextConstraints?
8. Does it create CRDs that tenants can use?
9. Does it expose services or routes?
10. Is there a documented upgrade and rollback process?

### 12.2 Tenant Control

In multi-tenant clusters, normal users should not be allowed to install arbitrary Operators.

Recommended controls:

- Restrict who can create `Subscription` objects.
- Restrict who can create `OperatorGroup` objects.
- Disable community catalogs if not approved.
- Use custom catalogs with approved Operators only.
- Use RBAC and admission policy.
- Use GitOps for controlled Operator deployment.
- Use separate namespaces for Operator control planes.

## 13. OperatorHub in Disconnected Environments

Disconnected clusters cannot directly pull catalog images from internet registries.

You must mirror:

- Operator catalog images
- Operator bundle images
- Operator operand images
- Related images referenced by bundles

Typical tools/concepts:

- `oc mirror`
- ImageContentSourcePolicy or ImageDigestMirrorSet / ImageTagMirrorSet depending on version and workflow
- Internal registry
- Mirrored catalog source
- Catalog pruning/filtering

### 13.1 Why Mirroring Is Hard

An Operator can reference many images:

```text
Operator controller image
Operand images
Init container images
Sidecar images
Webhook images
Proxy images
Database/cache images
Related images
```

If any required image is not mirrored, installation may succeed partially but operands fail later.

### 13.2 Custom CatalogSource for Mirrored Catalog

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators-mirror
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: mirror-registry.example.com/olm/redhat-operator-index:v4.22
  displayName: Red Hat Operators Mirror
  publisher: Internal Platform Team
```

Then use it in Subscription:

```yaml
spec:
  source: redhat-operators-mirror
  sourceNamespace: openshift-marketplace
```

### 13.3 Disconnected Checklist

```bash
# Check catalog sources
oc get catalogsource -n openshift-marketplace

# Check catalog pods
oc get pods -n openshift-marketplace

# Check image pull errors
oc get events -A | grep -i image
oc describe pod <pod> -n <namespace>

# Check subscriptions and installplans
oc get sub,ip,csv -A

# Check mirror policies
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get imagecontentsourcepolicy
```

### 13.4 Production Best Practice for Disconnected Clusters

- Disable default internet-backed catalogs.
- Create internal mirrored CatalogSources only.
- Mirror only approved Operators.
- Mirror exact catalog versions for cluster version.
- Test installation in a staging disconnected cluster.
- Keep mirror procedure documented.
- Monitor catalog pod health after mirror updates.
- Validate that related images are included.

## 14. OperatorHub with Proxy and Custom CA

Clusters behind proxy or TLS inspection may have catalog image pull issues.

Check cluster proxy:

```bash
oc get proxy cluster -o yaml
```

Check image pull failures:

```bash
oc get events -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
```

Common symptoms:

```text
ImagePullBackOff
ErrImagePull
x509: certificate signed by unknown authority
connection timed out
proxyconnect tcp
```

Things to verify:

- Cluster-wide proxy configuration
- Trusted CA bundle
- Pull secret
- Registry credentials
- Firewall egress rules
- DNS resolution
- Registry route/certificate
- Mirror configuration

## 15. OperatorHub Troubleshooting Framework

When an Operator installation fails, troubleshoot in layers.

### Layer 1: Catalog Availability

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <source> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

Check:

- Is the CatalogSource present?
- Is the catalog pod running?
- Is the catalog connection ready?
- Is the package visible?

```bash
oc get packagemanifest -n openshift-marketplace | grep -i <operator>
```

### Layer 2: Package and Channel

```bash
oc describe packagemanifest <package-name> -n openshift-marketplace
```

Check:

- Correct package name?
- Correct source?
- Correct source namespace?
- Correct channel?
- Operator supports desired install mode?

### Layer 3: Subscription

```bash
oc get subscription -n <namespace>
oc describe subscription <subscription-name> -n <namespace>
oc get subscription <subscription-name> -n <namespace> -o yaml
```

Check:

- `spec.name`
- `spec.channel`
- `spec.source`
- `spec.sourceNamespace`
- `spec.installPlanApproval`
- Status conditions
- Current CSV
- Installed CSV
- InstallPlan reference

### Layer 4: InstallPlan

```bash
oc get installplan -n <namespace>
oc describe installplan <installplan-name> -n <namespace>
oc get installplan <installplan-name> -n <namespace> -o yaml
```

Check:

- Is it approved?
- Did it fail?
- Which resources are being created?
- Are there permission errors?
- Are CRDs already present but conflicting?

### Layer 5: CSV

```bash
oc get csv -n <namespace>
oc describe csv <csv-name> -n <namespace>
```

Check:

- Phase
- Reason
- Message
- Required APIs
- Owned APIs
- Deployment status
- Permission requirements

### Layer 6: Operator Pods

```bash
oc get pods -n <namespace>
oc describe pod <operator-pod> -n <namespace>
oc logs <operator-pod> -n <namespace>
oc logs deployment/<operator-deployment> -n <namespace>
```

Check:

- CrashLoopBackOff
- ImagePullBackOff
- RBAC denied
- Missing secret
- Webhook certificate issue
- Operand API issue
- SCC/Pod Security issue

### Layer 7: Events

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc get events -A --sort-by=.lastTimestamp | tail -50
```

Events often show the exact reason faster than logs.

## 16. Common OperatorHub Errors and Fixes

### 16.1 Package Not Found

Symptoms:

```text
constraints not satisfiable
no operators found from catalog
```

Check:

```bash
oc get packagemanifest -n openshift-marketplace | grep -i <name>
oc get catalogsource -n openshift-marketplace
```

Fix:

- Correct package name
- Correct catalog source
- Enable required catalog
- Fix broken CatalogSource
- Update mirrored catalog

### 16.2 Channel Not Found

Symptoms:

```text
channel does not exist
```

Check:

```bash
oc describe packagemanifest <package-name> -n openshift-marketplace
```

Fix:

- Use valid channel
- Check OpenShift version compatibility
- Update catalog mirror

### 16.3 InstallPlan Pending Forever

Check:

```bash
oc get installplan -n <namespace>
oc describe installplan <installplan-name> -n <namespace>
```

Possible causes:

- Manual approval required
- Dependency cannot be resolved
- Catalog unavailable
- Permission issue
- Existing conflicting CSV

If manual:

```bash
oc patch installplan <installplan-name> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

### 16.4 CSV Failed

Check:

```bash
oc describe csv <csv-name> -n <namespace>
```

Possible causes:

- Unsupported install mode
- Missing CRD dependency
- RBAC creation failed
- Deployment failed
- Webhook failed
- Image pull failed

### 16.5 Multiple OperatorGroups

Symptoms:

```text
TooManyOperatorGroups
```

Check:

```bash
oc get operatorgroup -n <namespace>
```

Fix:

```bash
oc delete operatorgroup <extra-operatorgroup> -n <namespace>
```

Then restart or recreate Subscription if required.

### 16.6 Catalog Pod ImagePullBackOff

Check:

```bash
oc describe pod <catalog-pod> -n openshift-marketplace
oc get pull-secret -n openshift-config
oc get events -n openshift-marketplace
```

Fix:

- Update global pull secret
- Fix registry credentials
- Configure proxy
- Configure trusted CA
- Fix mirror policy
- Use reachable internal registry

### 16.7 Operator Installed but Custom Resource Fails

This means Operator installation succeeded, but the operand failed.

Check:

```bash
oc get crd | grep -i <operator>
oc get <custom-resource-kind> -A
oc describe <custom-resource-kind> <name> -n <namespace>
oc logs deployment/<operator-deployment> -n <operator-namespace>
```

Common causes:

- Invalid CR spec
- Missing storage class
- Missing secret
- SCC/Pod Security restrictions
- Insufficient resources
- NetworkPolicy blocking traffic
- Operand image not mirrored

## 17. OperatorHub and GitOps

In mature OpenShift environments, Operator installation is usually GitOps-managed.

Recommended Git structure:

```text
cluster-config/
  operators/
    file-integrity/
      namespace.yaml
      operatorgroup.yaml
      subscription.yaml
    compliance/
      namespace.yaml
      operatorgroup.yaml
      subscription.yaml
    logging/
      namespace.yaml
      operatorgroup.yaml
      subscription.yaml
      instance.yaml
```

Benefits:

- Repeatable cluster builds
- Audit trail
- Peer review
- Rollback visibility
- Environment promotion
- Consistency across clusters

### 17.1 GitOps Warning

Do not blindly GitOps every generated OLM object.

Usually manage:

- Namespace
- OperatorGroup
- Subscription
- Operator custom resources

Usually do not manually manage:

- InstallPlan
- CSV
- OLM-generated Roles/Bindings
- Generated Deployments owned by CSV

Why?

Because OLM owns those generated resources and may replace or mutate them during upgrades.

- Confirm source is enabled.
- Confirm UI filters are not hiding it.
- Confirm role permissions.
- Confirm mirrored catalog content.

## 22. Real-World Scenario: Disconnected Operator Install Fails

Problem:

> Subscription exists, InstallPlan created, but pods fail with image pull errors.

Commands:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
oc get catalogsource -n openshift-marketplace
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

Likely causes:

- Operator image not mirrored
- Operand image not mirrored
- Related image missing
- Mirror policy incorrect
- Internal registry certificate not trusted
- Pull secret missing registry credentials
- Catalog points to external registry

Fix approach:

1. Identify missing image from event.
2. Confirm image exists in mirror registry.
3. Confirm mirror policy maps source to mirror.
4. Confirm node can pull from mirror.
5. Confirm pull secret has credentials.
6. Recreate failed pod or let deployment retry.

## 23. OperatorHub Best Practices for Production

### 23.1 Catalog Management

- Disable unnecessary default catalogs.
- Prefer Red Hat-supported Operators for platform-critical functions.
- Use certified Operators only after support ownership is clear.
- Avoid community Operators in production unless internally approved.
- Use mirrored custom catalogs for restricted clusters.
- Pin catalog versions in controlled environments.

### 23.2 Installation Management

- Use GitOps for OperatorGroup and Subscription.
- Use manual approval for production upgrades.
- Use separate namespaces for major Operators.
- Validate install modes before installation.
- Avoid installing many unrelated Operators into one namespace.

### 23.3 Security Management

- Review CSV permissions.
- Watch for cluster-wide RBAC.
- Review webhooks.
- Review SCC requirements.
- Limit who can create Subscriptions.
- Limit who can modify CatalogSources.

### 23.4 Upgrade Management

- Track channel changes.
- Read release notes.
- Test upgrades in non-production.
- Approve InstallPlans through change process.
- Keep rollback/uninstall notes.
- Back up custom resources where applicable.

### 23.5 Observability

Monitor:

```bash
oc get csv -A
oc get subscription -A
oc get installplan -A
oc get pods -n openshift-marketplace
oc get pods -n openshift-operator-lifecycle-manager
```

Alert on:

- CSV failed
- Subscription resolution failure
- Catalog pod down
- Marketplace pod down
- Operator pod CrashLoopBackOff
- Pending manual approval older than change window

## 25. Senior Administrator Mental Model

A strong OpenShift administrator should think about OperatorHub like this:

```text
OperatorHub / Software Catalog = discovery interface
OperatorHub CR = default catalog configuration
CatalogSource = metadata server for Operator packages
PackageManifest = readable package/channel view
Subscription = desired Operator tracking configuration
InstallPlan = generated execution plan
CSV = installed Operator version and status
OperatorGroup = namespace watch scope
```

When something fails, ask:

1. Is the catalog available?
2. Is the package visible?
3. Is the channel valid?
4. Is the Subscription correct?
5. Is the InstallPlan approved and successful?
6. Is the CSV succeeded?
7. Is the Operator pod healthy?
8. Is the custom resource valid?
9. Are all required images pullable?
10. Are RBAC/SCC/webhook dependencies satisfied?

## 27. Quick Interview-Style Questions

### Q1. Is OperatorHub the same as OLM?

No. OperatorHub or Software Catalog is the discovery and installation interface. OLM is the lifecycle controller that installs, upgrades, and manages Operators.

### Q2. What does CatalogSource do?

It points OLM to an Operator catalog/index image and exposes package metadata through a catalog service.

### Q3. What does Subscription do?

It tells OLM which Operator package and channel to track from which catalog source.

### Q4. What does InstallPlan do?

It is the generated plan that creates or updates resources required for an Operator installation or upgrade.

### Q5. What does CSV do?

It represents a specific installed Operator version, including metadata, permissions, CRDs, install strategy, and status.

### Q6. Why use manual approval?

To prevent uncontrolled Operator upgrades in production and allow change review before OLM applies upgrade actions.

### Q7. Why disable community-operators?

To reduce unsupported software risk and enforce platform governance.

### Q8. Why use custom catalogs?

To control approved Operators, support disconnected clusters, pin versions, and reduce supply-chain risk.
