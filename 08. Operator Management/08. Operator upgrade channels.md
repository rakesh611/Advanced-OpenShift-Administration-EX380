## 1. What Are Operator Upgrade Channels?

An **Operator upgrade channel** is a named update stream inside an Operator package. When you install an Operator through Operator Lifecycle Manager, you do not simply install a random container image. You create a **Subscription** that tells OLM:

- Which Operator package to track.
- Which CatalogSource provides that package.
- Which namespace to install it into.
- Which upgrade channel to follow.
- Whether upgrades should be approved automatically or manually.

A channel is similar to a software repository stream. For example:

```text
stable
fast
candidate
preview
alpha
beta
stable-1.12
stable-v1.13
release-2.4
```

A channel contains one or more Operator versions, normally represented by **ClusterServiceVersions** or bundle metadata. OLM uses the channel and the Operator package's upgrade graph to determine whether a newer version is available and how to move from the installed version to the target version.

Simple view:

```text
Operator package: example-operator

Channels:
  stable
    example-operator.v1.0.0 -> example-operator.v1.1.0 -> example-operator.v1.2.0

  fast
    example-operator.v1.0.0 -> example-operator.v1.1.0 -> example-operator.v1.2.0 -> example-operator.v1.3.0

Subscription:
  spec.channel: stable
```

The Subscription above tracks only the `stable` channel. Even if `fast` has a newer version, OLM will not upgrade that Subscription to a version that exists only in `fast` unless the Subscription channel is changed.

## 2. Why Upgrade Channels Matter in Production

For a beginner, channels look like an install-time choice. For a senior administrator, channels are a **production risk-control mechanism**.

They control:

- How quickly an Operator receives updates.
- Whether you consume conservative or early updates.
- Whether upgrades are tied to minor versions.
- Whether the cluster receives bug fixes automatically.
- Whether a broken Operator release can be skipped.
- Whether a disconnected catalog contains a valid upgrade path.
- Whether a CRD schema conversion or controller upgrade happens unexpectedly.

Operators can manage critical platform components such as:

- OpenShift Logging
- OpenShift Service Mesh
- OpenShift GitOps
- OpenShift Data Foundation
- Advanced Cluster Management
- Compliance Operator
- File Integrity Operator
- cert-manager Operator
- External Secrets Operator
- Storage, networking, monitoring, and security integrations

An Operator upgrade is not just a pod image update. It can also modify:

- CRDs
- RBAC
- Webhooks
- Deployments
- ServiceAccounts
- API services
- Conversion strategy
- Default operands
- Finalizers
- Validating or mutating admission behavior
- Cluster-scoped permissions

Because of that, channel choice and approval strategy should be treated as part of the cluster change-management model.

## 3. OLM Objects Involved in Operator Upgrades

### 3.1 CatalogSource

A **CatalogSource** tells OLM where Operator metadata is stored.

Common default CatalogSources in OpenShift classic OLM are in:

```bash
openshift-marketplace
```

Typical catalog names:

```text
redhat-operators
certified-operators
community-operators
redhat-marketplace
```

Check them:

```bash
oc get catalogsource -n openshift-marketplace
```

Example:

```bash
oc get catalogsource redhat-operators -n openshift-marketplace -o yaml
```

A CatalogSource provides packages, channels, bundles, CRDs, CSVs, and dependency metadata.

---

### 3.2 Package

A **package** is the logical Operator product name in a catalog.

Examples:

```text
cluster-logging
openshift-gitops-operator
odf-operator
compliance-operator
file-integrity-operator
servicemeshoperator
```

A package can have multiple channels.

---

### 3.3 Channel

A **channel** is a stream of Operator versions within a package.

Example:

```text
Package: cluster-logging
Channels:
  stable
  stable-5.9
  stable-6.0
```

The channel determines the update stream that a Subscription follows.

---

### 3.4 Bundle / CSV

A **bundle** is a packaged Operator release. In classic OLM, the installed running Operator version is represented on the cluster by a **ClusterServiceVersion**.

Check CSVs:

```bash
oc get csv -A
oc get csv -n <operator-namespace>
```

Example:

```bash
oc get csv -n openshift-operators
```

CSV names normally include versions:

```text
example-operator.v1.2.3
```

---

### 3.5 Subscription

A **Subscription** keeps an Operator installed and updated by tracking a package and channel.

Check Subscriptions:

```bash
oc get subscription -A
```

Short form also works on many clusters:

```bash
oc get sub -A
```

Inspect one:

```bash
oc get subscription <subscription-name> -n <namespace> -o yaml
```

Important fields:

```yaml
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
status:
  currentCSV: example-operator.v1.2.0
  installedCSV: example-operator.v1.1.0
  installPlanRef:
    name: install-abcde
```

Field meaning:

| Field | Meaning |
|---|---|
| `spec.channel` | Channel the Subscription follows |
| `spec.name` | Operator package name |
| `spec.source` | CatalogSource name |
| `spec.sourceNamespace` | Namespace where CatalogSource exists |
| `spec.installPlanApproval` | `Automatic` or `Manual` |
| `spec.startingCSV` | Optional requested starting CSV/version |
| `status.currentCSV` | Latest known CSV according to OLM resolution |
| `status.installedCSV` | Currently installed CSV |
| `status.installPlanRef` | InstallPlan created for install or upgrade |

---

### 3.6 InstallPlan

An **InstallPlan** is OLM's calculated plan for installing or upgrading an Operator.

It contains the resources OLM needs to create, update, or manage.

Check InstallPlans:

```bash
oc get installplan -A
oc get installplan -n <operator-namespace>
```

Inspect:

```bash
oc get installplan <installplan-name> -n <namespace> -o yaml
```

Key fields:

```yaml
spec:
  approved: false
  approval: Manual
status:
  phase: RequiresApproval
```

For manual approval, patch it:

```bash
oc patch installplan <installplan-name> \
  -n <namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

---

### 3.7 OperatorGroup

An **OperatorGroup** defines which namespaces an Operator installed in that namespace watches.

While OperatorGroup is not itself an upgrade channel object, it affects whether an Operator can be installed or upgraded successfully because the CSV install modes and target namespaces must be compatible.

Check OperatorGroups:

```bash
oc get operatorgroup -A
```

Common issue:

```text
CSV Pending: TooManyOperatorGroups
CSV Pending: UnsupportedOperatorGroup
CSV Pending: Cannot modify target namespaces
```

## 4. Core Mental Model

Think of OLM upgrades as a pipeline:

```text
CatalogSource
   |
   | provides packages/channels/bundles/upgrade graph
   v
Package
   |
   | has one or more channels
   v
Channel
   |
   | contains ordered upgrade path
   v
Subscription
   |
   | tracks package + channel
   v
InstallPlan
   |
   | calculated upgrade/install actions
   v
CSV
   |
   | actual installed Operator version
   v
Operator controller pod
   |
   | manages operands / custom resources
   v
Operand workloads
```

A senior admin should separate these layers clearly:

| Layer | Admin question |
|---|---|
| CatalogSource | Where is Operator metadata coming from? |
| Package | Which Operator product am I tracking? |
| Channel | Which update stream am I following? |
| Subscription | What did I ask OLM to install or update? |
| InstallPlan | What changes will OLM apply? |
| CSV | What Operator version is actually installed? |
| Operator pod | Is the controller healthy? |
| Operand | Did the application managed by the Operator remain healthy? |

## 5. How Channels Are Represented

In classic OLM, channel data is catalog metadata. On the cluster, you mostly interact with it through:

- OperatorHub UI
- `PackageManifest` objects
- Subscription resources
- CSVs
- InstallPlans
- CatalogSource pods

Example command to inspect a package:

```bash
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
```

List available package manifests:

```bash
oc get packagemanifest -n openshift-marketplace
```

List channels for a package:

```bash
oc get packagemanifest <package-name> \
  -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{"\n"}{end}'
```

Show default channel:

```bash
oc get packagemanifest <package-name> \
  -n openshift-marketplace \
  -o jsonpath='{.status.defaultChannel}{"\n"}'
```

Show channels with current CSV:

```bash
oc get packagemanifest <package-name> \
  -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{" -> "}{.currentCSV}{"\n"}{end}'
```

Example output:

```text
stable -> example-operator.v1.2.0
fast -> example-operator.v1.3.0
candidate -> example-operator.v1.4.0-rc1
```

Important: `currentCSV` here means the channel head according to catalog metadata, not necessarily what your cluster has installed.

## 6. Common Channel Naming Patterns

Channel names are Operator-specific. There is no single universal naming standard enforced across all Operators.

Common patterns:

### 6.1 Stability-Based Channels

```text
stable
fast
candidate
preview
alpha
beta
```

Typical interpretation:

| Channel | Typical meaning |
|---|---|
| `stable` | Conservative, production-ready update stream |
| `fast` | Faster access to updates, may receive versions before stable |
| `candidate` | Release candidate or pre-stable validation stream |
| `preview` | Early feature preview |
| `alpha` | Experimental, not recommended for production |
| `beta` | More mature than alpha but still not ideal for critical production |

Do not assume every Operator uses the same semantics. Always read the Operator documentation and release notes.

---

### 6.2 Minor-Version Channels

Examples:

```text
stable-1.10
stable-1.11
stable-v1.12
v2.4
release-2.5
```

These channels are common when the Operator or its operand has distinct minor releases.

Example:

```text
stable-1.10 -> only 1.10.z updates
stable-1.11 -> only 1.11.z updates
stable-1.12 -> only 1.12.z updates
```

This allows administrators to receive patch updates without automatically jumping to the next minor release.

---

### 6.3 OpenShift-Version-Specific Channels

Some Operators align with OpenShift versions:

```text
stable-4.14
stable-4.15
stable-4.16
stable-4.17
```

This pattern is used when Operator compatibility depends tightly on OpenShift/Kubernetes API versions.

---

### 6.4 Product Lifecycle Channels

Examples:

```text
eos-1.0
lts
stable-lts
maintenance
```

These indicate long-term support or maintenance streams.

## 7. Subscription and Channel Selection

A Subscription is the admin's declarative request to follow a channel.

Basic Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: openshift-operators
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

This tells OLM:

```text
Install and track package example-operator
from CatalogSource redhat-operators
in namespace openshift-operators
using channel stable
and require manual approval before install or upgrade.
```

### 7.1 What Happens If You Omit the Channel?

In many UI flows, the console defaults to the package's default channel. In declarative YAML, explicitly define `spec.channel` for predictable GitOps behavior.

Good production practice:

```yaml
spec:
  channel: stable-1.12
```

Avoid unclear intent:

```yaml
spec:
  # channel omitted
```

## 8. Automatic vs Manual Upgrade Approval

`installPlanApproval` is one of the most important production fields.

```yaml
spec:
  installPlanApproval: Automatic
```

or:

```yaml
spec:
  installPlanApproval: Manual
```

---

### 8.1 Automatic Approval

With `Automatic`, OLM automatically approves InstallPlans when a newer version is available in the selected channel.

Example:

```yaml
spec:
  channel: stable
  installPlanApproval: Automatic
```

Behavior:

```text
New bundle appears in channel
        |
        v
OLM resolves upgrade
        |
        v
OLM creates InstallPlan
        |
        v
InstallPlan is automatically approved
        |
        v
CSV upgrade begins
```

Advantages:

- Faster security and bug-fix uptake.
- Less admin work.
- Useful for non-critical Operators.
- Useful in dev/test clusters.

Risks:

- Unexpected CRD changes.
- Unexpected webhook behavior.
- Operator controller restart during business hours.
- Operand reconciliation changes.
- Version jumps you did not explicitly review.
- Harder change-control compliance.

Use cases:

- Lab clusters.
- Development clusters.
- Low-risk Operators.
- Operators where rapid security updates are more important than strict maintenance windows.

---

### 8.2 Manual Approval

With `Manual`, OLM creates an InstallPlan, but waits for a human or automation to approve it.

Example:

```yaml
spec:
  channel: stable
  installPlanApproval: Manual
```

Behavior:

```text
New bundle appears in channel
        |
        v
OLM resolves upgrade
        |
        v
OLM creates InstallPlan
        |
        v
InstallPlan waits in RequiresApproval
        |
        v
Admin reviews and approves
        |
        v
CSV upgrade begins
```

Advantages:

- Controlled maintenance windows.
- Easier CAB/change-management compliance.
- Time to read release notes.
- Time to verify CRD/schema changes.
- Safer for cluster-scoped and security-sensitive Operators.

Risks:

- Missed security patches if nobody approves.
- Pending InstallPlans can accumulate.
- Operators may drift behind supported versions.

Production recommendation:

```text
Use Manual for critical, cluster-scoped, security, storage, network, logging, and GitOps Operators.
Use Automatic only when you understand the blast radius.
```

## 9. Operator Upgrade Flow

Detailed OLM upgrade flow:

```text
1. CatalogSource is updated or already contains a newer bundle.
2. OLM watches catalog metadata.
3. Subscription tracks package + channel.
4. OLM compares installedCSV with channel head / upgrade graph.
5. If an upgrade path exists, OLM resolves required resources and dependencies.
6. OLM creates an InstallPlan.
7. If approval is Automatic, OLM approves it.
8. If approval is Manual, admin must approve it.
9. OLM creates or updates resources from the new bundle.
10. New CSV enters Pending / Installing / Succeeded or Failed.
11. Operator deployment rolls out.
12. Old CSV is eventually replaced if upgrade succeeds.
13. Operator reconciles operands.
```

Check Subscription state:

```bash
oc get subscription <sub-name> -n <namespace> -o yaml
```

Useful fields:

```yaml
status:
  currentCSV: example-operator.v1.2.0
  installedCSV: example-operator.v1.1.0
  state: UpgradePending
  conditions:
    - type: InstallPlanPending
```

If:

```text
currentCSV != installedCSV
```

then a newer version might be known to OLM, but it may not yet be installed. Reasons include:

- Manual InstallPlan not approved.
- InstallPlan failed.
- Dependency resolution problem.
- CatalogSource issue.
- CSV failed.
- Webhook/APIService unavailable.
- OperatorGroup incompatibility.

## 10. Upgrade Graph: `replaces`, `skips`, and `skipRange`

A channel is not merely a list of versions. It is an **upgrade graph**.

An upgrade graph defines valid movement between Operator versions.

Example:

```text
v1.0.0 -> v1.1.0 -> v1.2.0 -> v1.3.0
```

OLM must find a valid path from the installed version to a newer candidate.

---

### 10.1 `replaces`

`replaces` defines a direct upgrade edge from one version to the next.

Conceptual example:

```yaml
name: example-operator.v1.2.0
replaces: example-operator.v1.1.0
```

Meaning:

```text
v1.2.0 replaces v1.1.0
```

Graph:

```text
v1.0.0 -> v1.1.0 -> v1.2.0
```

Use `replaces` when every version must be installed in sequence or when you want to preserve incremental installability.

---

### 10.2 `skips`

`skips` lets a version skip over specific earlier versions.

Conceptual example:

```yaml
name: example-operator.v1.3.0
replaces: example-operator.v1.1.0
skips:
  - example-operator.v1.2.0
```

Meaning:

```text
If user is on v1.1.0, go to v1.3.0 and skip bad v1.2.0.
If user is already on v1.2.0, still allow upgrade to v1.3.0 if graph supports it.
```

Common use case:

```text
v1.2.0 was released with a serious bug.
You want new users/upgrades to avoid v1.2.0.
You still need a path for users who already installed v1.2.0.
```

Bad graph design can strand users. Always test upgrade paths from every supported installed version.

---

### 10.3 `skipRange`

`skipRange` uses semantic version constraints to allow skipping multiple versions.

Conceptual example:

```yaml
name: example-operator.v1.5.0
skipRange: ">=1.0.0 <1.5.0"
```

Meaning:

```text
Any installed version matching >=1.0.0 and <1.5.0 can upgrade to v1.5.0.
```

Use cases:

- The Operator supports direct upgrades across many older versions.
- The controller handles all migration logic internally.
- You want to reduce the number of intermediate upgrade steps.

Production caution:

```text
Do not use or trust skipRange blindly for stateful or schema-heavy Operators unless the vendor confirms direct upgrade support.
```

For custom catalogs, ensure skipped versions and upgrade edges are intentional. Removing or pruning bundles can break upgradeability in disconnected environments.

---

### 10.4 File-Based Catalog Channel Entry Example

In file-based catalogs, an `olm.channel` entry defines channel membership and upgrade paths.

Example:

```yaml
---
schema: olm.channel
package: example-operator
name: stable
entries:
  - name: example-operator.v1.0.0
  - name: example-operator.v1.1.0
    replaces: example-operator.v1.0.0
  - name: example-operator.v1.2.0
    replaces: example-operator.v1.1.0
  - name: example-operator.v1.3.0
    replaces: example-operator.v1.2.0
```

Graph:

```text
v1.0.0 -> v1.1.0 -> v1.2.0 -> v1.3.0
```

With skip:

```yaml
---
schema: olm.channel
package: example-operator
name: stable
entries:
  - name: example-operator.v1.0.0
  - name: example-operator.v1.1.0
    replaces: example-operator.v1.0.0
  - name: example-operator.v1.2.0
    replaces: example-operator.v1.1.0
  - name: example-operator.v1.3.0
    replaces: example-operator.v1.1.0
    skips:
      - example-operator.v1.2.0
```

Graph intent:

```text
v1.0.0 -> v1.1.0 -> v1.3.0
                    \-> v1.2.0 may be skipped
```

## 11. Channel Head and Version Resolution

The **head** of a channel is the latest version in that channel according to the catalog metadata.

Example:

```text
stable channel:
  v1.0.0 -> v1.1.0 -> v1.2.0

Channel head: v1.2.0
```

If your Subscription tracks `stable`, OLM tries to move toward the stable channel head, but only through a valid upgrade graph.

Important cases:

### Case 1: Installed version is directly behind

```text
Installed: v1.1.0
Channel head: v1.2.0
Path exists: v1.1.0 -> v1.2.0
Result: upgrade available
```

### Case 2: Installed version is old but path exists

```text
Installed: v1.0.0
Channel head: v1.3.0
Path: v1.0.0 -> v1.1.0 -> v1.2.0 -> v1.3.0
Result: OLM can upgrade sequentially or by valid graph logic
```

### Case 3: Installed version is old and intermediate bundles missing

```text
Installed: v1.0.0
Catalog contains: v1.3.0 only
No skipRange from v1.0.0 to v1.3.0
Result: upgrade may fail or no upgrade path exists
```

This is common in badly pruned disconnected catalogs.

### Case 4: Installed version is not in the new channel graph

```text
Current channel: stable-1.10
Installed: v1.10.7
New channel: stable-1.12
New channel starts at v1.12.0 only
No graph edge from v1.10.7 to v1.12.0
Result: channel switch may not produce valid upgrade
```

Always confirm upgrade path before changing channels in production.

## 12. Installing a Specific Operator Version

Sometimes you do not want the latest version in a channel. You want a specific CSV.

Use `startingCSV`:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: openshift-operators
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  startingCSV: example-operator.v1.1.0
  installPlanApproval: Manual
```

Important production note:

```text
When installing a specific older version, use Manual approval.
Otherwise, OLM may immediately attempt to upgrade to a newer version in the selected channel.
```

Common workflow:

```bash
oc apply -f subscription.yaml
oc get installplan -n openshift-operators
oc describe installplan <installplan-name> -n openshift-operators
oc patch installplan <installplan-name> -n openshift-operators \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

Verify:

```bash
oc get csv -n openshift-operators
oc get subscription example-operator -n openshift-operators -o yaml
```

## 13. Changing an Operator Upgrade Channel

Changing the channel means changing which update stream the Subscription follows.

Example:

```bash
oc patch subscription example-operator \
  -n openshift-operators \
  --type merge \
  -p '{"spec":{"channel":"stable-1.12"}}'
```

Then monitor:

```bash
oc get subscription example-operator -n openshift-operators -o yaml
oc get installplan -n openshift-operators
oc get csv -n openshift-operators
```

### 13.1 Channel Change Is Not a Downgrade Tool

Do not treat channel switching as a rollback mechanism.

Typical vendor/OLM expectation:

```text
Move to newer channels, not older channels.
```

Downgrading an Operator can be dangerous because:

- CRDs may already be upgraded.
- Stored custom resources may use newer schema fields.
- Conversion webhooks may not support reverse migration.
- Operand versions may already be upgraded.
- Finalizers and status fields may differ.
- Controller logic may not be backward compatible.

For rollback, use vendor-supported recovery procedures, restore backups where applicable, and validate CRD/operand state.

## 16. Production Upgrade Strategy

A mature OpenShift Operator upgrade strategy includes technical and operational controls.

### 16.1 Recommended Production Flow

```text
1. Identify installed Operator and current channel.
2. Review available channels and channel heads.
3. Read release notes and known issues.
4. Verify OpenShift version compatibility.
5. Check CRD changes and conversion webhooks.
6. Check operand upgrade behavior.
7. Test in non-production cluster.
8. Ensure backup/export of important CRs.
9. Change channel if needed.
10. Wait for pending InstallPlan.
11. Review InstallPlan resources.
12. Approve during maintenance window.
13. Monitor CSV, Operator deployment, and operands.
14. Validate application/platform functionality.
15. Document result and close change.
```

---

### 16.2 Pre-Upgrade Checks

```bash
# Check Subscription
oc get subscription <sub-name> -n <namespace> -o yaml

# Check current CSV
oc get csv -n <namespace>

# Check Operator pods
oc get pods -n <namespace>

# Check Operator deployment
oc get deployment -n <namespace>

# Check CRDs owned by the Operator
oc get csv <csv-name> -n <namespace> -o jsonpath='{.spec.customresourcedefinitions.owned}' | jq

# Check existing custom resources
oc get <crd-plural> -A

# Check InstallPlans
oc get installplan -n <namespace>

# Check events
oc get events -n <namespace> --sort-by=.lastTimestamp
```


Look for:

- New CSV name
- CRDs added/updated
- ClusterRoles and ClusterRoleBindings
- Deployments
- Webhook configurations
- APIService objects
- Required dependent Operators
- Any unexpected broad RBAC

YAML inspection:

```bash

```

## 17. Disconnected and Restricted Network Considerations

In disconnected OpenShift, Operator upgrade channels become more sensitive because the cluster only sees the catalog content you mirrored.

Typical disconnected flow:

```text
Red Hat catalog / external catalog
        |
        v
oc-mirror or custom mirroring process
        |
        v
Internal registry
        |
        v
CatalogSource points to internal index image
        |
        v
OLM resolves Subscriptions from mirrored metadata
```

Important risks:

- Mirrored catalog may not include required intermediate bundles.
- Upgrade graph may be broken by pruning.
- Bundle images may be missing even though metadata exists.
- CatalogSource may point to the wrong tag.
- Catalog pod may fail to pull image.
- OpenShift version-specific catalog image may not match cluster version.

### 17.1 Disconnected Admin Checks

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalog-name> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

Check Subscription source:

```bash
oc get subscription <sub-name> -n <namespace> \
  -o jsonpath='{.spec.source}{"\n"}{.spec.sourceNamespace}{"\n"}'
```

Check available channels:

```bash
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
```

### 17.2 Golden Rule for Disconnected Upgrade Paths

```text
Mirror not only the target version, but also every bundle and image needed for a valid upgrade path from your currently installed version.
```

If your cluster has:

```text
Installed Operator: v1.0.0
Target Operator: v1.4.0
```

and the graph requires:

```text
v1.0.0 -> v1.1.0 -> v1.2.0 -> v1.3.0 -> v1.4.0
```

then the disconnected catalog must preserve that path or provide a valid `skipRange`/skip graph that allows direct movement.

## 18. Custom Catalogs and File-Based Catalogs

Modern Operator catalogs use the file-based catalog format, usually represented by YAML or JSON declarative config.

Core schemas:

```text
olm.package
olm.channel
olm.bundle
```

### 18.1 `olm.package`

Defines package metadata, including default channel.

Example:

```yaml
---
schema: olm.package
name: example-operator
defaultChannel: stable
```

### 18.2 `olm.channel`

Defines a channel and upgrade paths.

Example:

```yaml
---
schema: olm.channel
package: example-operator
name: stable
entries:
  - name: example-operator.v1.0.0
  - name: example-operator.v1.1.0
    replaces: example-operator.v1.0.0
  - name: example-operator.v1.2.0
    replaces: example-operator.v1.1.0
```

### 18.3 `olm.bundle`

Defines bundle image metadata.

Conceptual example:

```yaml
---
schema: olm.bundle
package: example-operator
name: example-operator.v1.2.0
image: registry.example.com/operators/example-operator-bundle:v1.2.0
properties:
  - type: olm.package
    value:
      packageName: example-operator
      version: 1.2.0
```

### 18.4 Validate Catalogs

```bash
opm validate <catalog-directory>
```

### 18.5 Render Catalog Image

```bash
opm render <catalog-image> -o yaml > index.yaml
```

### 18.6 Build Catalog Image

```bash
opm generate dockerfile <catalog-dir>
podman build -f <catalog-dir>.Dockerfile -t registry.example.com/custom/catalog:v1 .
podman push registry.example.com/custom/catalog:v1
```

### 18.7 Custom CatalogSource Example

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: custom-operators
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: registry.example.com/custom/catalog:v1
  displayName: Custom Operators
  publisher: Platform Team
  updateStrategy:
    registryPoll:
      interval: 30m
```

### 18.8 Advanced Catalog Governance

For enterprise OpenShift:

- Store catalog declarative config in Git.
- Validate every catalog change with `opm validate`.
- Promote catalog images through environments.
- Use immutable tags or digest pinning for production.
- Keep channel policy documented.
- Avoid silently removing bundles that existing clusters may need.
- Test upgrades from every supported installed version.

## 19. Troubleshooting Operator Upgrade Channels

### 19.1 Subscription Shows Upgrade Available but Nothing Happens

Check:

```bash
oc get subscription <sub-name> -n <namespace> -o yaml
oc get installplan -n <namespace>
```

Possible cause:

```text
installPlanApproval: Manual
InstallPlan phase: RequiresApproval
```

Fix:

```bash
oc patch installplan <installplan-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

---

### 19.2 `currentCSV` Is Newer Than `installedCSV`

Example:

```yaml
status:
  currentCSV: example-operator.v1.3.0
  installedCSV: example-operator.v1.2.0
```

Meaning:

```text
OLM has resolved or detected a newer target, but installed version has not caught up.
```

Check:

```bash
oc get installplan -n <namespace>
oc describe installplan <installplan-name> -n <namespace>
oc get csv -n <namespace>
oc describe csv <new-csv> -n <namespace>
```

Common causes:

- Manual approval pending.
- InstallPlan failed.
- CSV stuck in Pending.
- Dependency missing.
- OperatorGroup conflict.
- Required CRD/API unavailable.

---

### 19.3 InstallPlan Stuck in `RequiresApproval`

Expected for Manual approval.

```bash
oc get installplan -n <namespace>
```

Output:

```text
NAME            CSV                         APPROVAL   APPROVED
install-abcde   example-operator.v1.3.0     Manual     false
```

Approve:

```bash
oc patch installplan install-abcde -n <namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

---

### 19.4 InstallPlan Failed

```bash
oc describe installplan <installplan-name> -n <namespace>
```

Check messages:

```bash
oc get installplan <installplan-name> -n <namespace> -o yaml
```

Common reasons:

- Missing CRD dependency.
- Conflicting API owner.
- RBAC creation failure.
- Existing resource conflict.
- Catalog metadata invalid.
- Bundle image not pullable.
- InstallMode not supported in target OperatorGroup.

---

### 19.5 CSV Stuck in Pending

```bash
oc get csv -n <namespace>
oc describe csv <csv-name> -n <namespace>
```

Look for:

```text
RequirementsNotMet
InstallComponentFailed
UnsupportedOperatorGroup
TooManyOperatorGroups
APIServiceResourceIssue
WebhookResourceIssue
```

---

### 19.6 CatalogSource Unhealthy

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalog-name> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

Common causes:

- Index image pull failure.
- Registry authentication issue.
- Disconnected mirror missing image.
- Invalid catalog image.
- Network/proxy issue.
- Catalog pod crashloop.

---

### 19.7 No Available Channels

```bash
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
```

If not found:

```bash
oc get packagemanifest -n openshift-marketplace | grep -i <keyword>
```

Possible causes:

- Wrong package name.
- Wrong CatalogSource.
- CatalogSource not healthy.
- Disabled default OperatorHub sources.
- Disconnected catalog missing package.
- Package exists in different catalog.

### 19.8 Channel Exists but Target Version Missing

Check channel heads:

```bash
oc get packagemanifest <package-name> -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{" -> "}{.currentCSV}{"\n"}{end}'
```

Possible causes:

- Catalog not updated.
- Mirrored catalog older than expected.
- CatalogSource pinned to old image tag.
- Package removed from custom catalog.
- Wrong OpenShift version catalog.

### 19.9 Upgrade Path Broken

Symptoms:

- Subscription does not progress.
- No InstallPlan created.
- Resolver errors.
- OLM logs show constraints/dependency issues.

Check OLM logs:

```bash
oc logs -n openshift-operator-lifecycle-manager deployment/olm-operator
oc logs -n openshift-operator-lifecycle-manager deployment/catalog-operator
oc logs -n openshift-operator-lifecycle-manager deployment/packageserver
```

Also inspect:

```bash
oc get subscription <sub-name> -n <namespace> -o yaml
oc describe subscription <sub-name> -n <namespace>
```

Possible causes:

- Current installed CSV not present in channel graph.
- Intermediate versions pruned from disconnected catalog.
- No `skipRange` allowing direct upgrade.
- Conflicting dependency version.
- Multiple Operators provide the same API.

## 20. Advanced Admin Scenarios

### Scenario 1: You Want Patch Updates but Not Minor Upgrades

Use minor-specific channels when available.

Example:

```yaml
spec:
  channel: stable-1.12
  installPlanApproval: Manual
```

This lets you receive:

```text
1.12.1 -> 1.12.2 -> 1.12.3
```

without automatically moving to:

```text
1.13.0
```

---

### Scenario 2: You Want Faster Fixes in Non-Prod

Use `fast` or equivalent channel in non-prod:

```yaml
spec:
  channel: fast
  installPlanApproval: Automatic
```

Production can remain:

```yaml
spec:
  channel: stable
  installPlanApproval: Manual
```

This allows non-prod to detect issues early.

---

### Scenario 3: You Need to Move from `stable-1.11` to `stable-1.12`

Process:

```bash
# 1. Check current state
oc get subscription <sub-name> -n <namespace> -o yaml

# 2. Confirm available channels
oc get packagemanifest <package-name> -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{" -> "}{.currentCSV}{"\n"}{end}'

# 3. Patch channel
oc patch subscription <sub-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"channel":"stable-1.12"}}'

# 4. Wait for InstallPlan
oc get installplan -n <namespace>

# 5. Review and approve
oc describe installplan <installplan-name> -n <namespace>
oc patch installplan <installplan-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'

# 6. Monitor
oc get subscription,csv,installplan -n <namespace> -w
```

---

### Scenario 4: Operator Upgrade Breaks Operand

Do not immediately delete the Subscription or CSV without understanding the managed resources.

Check:

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc logs deployment/<operator-deployment> -n <operator-namespace>
oc get events -A --sort-by=.lastTimestamp
oc get <operator-cr-kind> -A -o yaml
```

Actions:

- Read Operator release notes.
- Check CR status conditions.
- Check conversion webhooks.
- Check operand pod logs.
- Confirm whether the Operator initiated an operand upgrade.
- Engage vendor support for supported Operators.
- Restore from backup only if necessary and supported.

---

### Scenario 5: GitOps Keeps Reverting Channel

If Argo CD or another GitOps controller manages the Subscription, manual `oc patch` changes may be reverted.

Fix:

```text
Change the Subscription manifest in Git, not only on the live cluster.
```

Check owner/labels:

```bash
oc get subscription <sub-name> -n <namespace> -o yaml
```

Look for:

```yaml
metadata:
  labels:
    app.kubernetes.io/managed-by: gitops
  annotations:
    argocd.argoproj.io/...
```

---

### Scenario 6: Multiple Operators Updated Together

In some namespace layouts, multiple Operators share one namespace and approval behavior may affect how updates are handled operationally.

Production recommendation:

```text
Install critical Operators in dedicated namespaces where supported.
```

Benefits:

- Independent approval.
- Cleaner RBAC boundary.
- Easier troubleshooting.
- Reduced blast radius.
- Clearer GitOps ownership.

---

### Scenario 7: Channel Changed but No Upgrade Happens

Check:

```bash
oc get subscription <sub-name> -n <namespace> -o yaml
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
oc get installplan -n <namespace>
oc logs -n openshift-operator-lifecycle-manager deployment/catalog-operator
```

Common causes:

- New channel has same head version.
- No valid upgrade path from installed CSV.
- Manual InstallPlan pending.
- Catalog not updated.
- Wrong source CatalogSource.
- GitOps reverted change.
- Subscription status not refreshed yet.

## 21. Best Practices

### 21.1 For Production Clusters

Use:

```yaml
installPlanApproval: Manual
```

for critical Operators.

Document:

- Current channel
- Current CSV
- Target channel
- Target CSV
- Change window
- Rollback/recovery plan
- Operand validation plan

---

### 21.2 Prefer Stable Channels for Critical Operators

For production:

```text
stable > fast > candidate > beta > alpha
```

But confirm the vendor's channel meaning.

---

### 21.3 Avoid Uncontrolled Minor Upgrades

Where available, prefer minor-specific stable channels:

```yaml
channel: stable-1.12
```

instead of generic:

```yaml
channel: stable
```

when you need strict lifecycle control.

---

### 21.4 Use Non-Prod as Early Warning

Recommended pattern:

```text
Dev/Test cluster: fast + Automatic or Manual
Stage cluster: stable + Manual
Prod cluster: stable + Manual
```

---

### 21.5 Never Ignore Pending InstallPlans

Pending InstallPlans may indicate:

- Available security update.
- Available bug fix.
- Required compatibility update.
- Stalled upgrade process.

Monitor them:

```bash
oc get installplan -A
```

---

### 21.6 Keep Catalogs Healthy

```bash
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
```

CatalogSource health directly affects Operator installation and upgrades.

---

### 21.7 Treat CRDs as API Contracts

Before Operator upgrades, check whether CRDs change.

```bash
oc get crd | grep -i <operator>
oc get crd <crd-name> -o yaml
```

Pay attention to:

- Versions under `spec.versions`
- Served/storage versions
- Conversion webhooks
- Schema changes
- Deprecated fields
- Required fields

### 21.8 For Disconnected Clusters, Preserve Upgrade Paths

Do not over-prune catalogs.

Bad:

```text
Only mirror latest bundle.
```

Better:

```text
Mirror all bundles required from currently installed version to target version.
```

### 21.9 Do Not Use Channel Switching as Rollback

Rollback should be:

- Vendor-supported.
- Backup-based if needed.
- Tested.
- Aware of CRD/operand state.

### 21.10 Monitor OLM Components

## 22. Interview / Exam Style Questions

### Q1. What is an Operator upgrade channel?

An Operator upgrade channel is a named update stream within an Operator package. A Subscription tracks a specific channel, and OLM uses the channel's upgrade graph to determine install and upgrade targets.

---

### Q2. What happens when `installPlanApproval` is `Manual`?

OLM creates an InstallPlan for install or upgrade, but it does not apply the plan until the administrator approves it by setting:

```yaml
spec:
  approved: true
```

---

### Q3. How do you check which channel an installed Operator uses?

```bash
oc get subscription <sub-name> -n <namespace> \
  -o jsonpath='{.spec.channel}{"\n"}'
```

---

### Q4. How do you list available channels for an Operator package?

```bash
oc get packagemanifest <package-name> \
  -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{"\n"}{end}'
```

---

### Q5. What is the difference between `currentCSV` and `installedCSV`?

`installedCSV` is the CSV currently installed on the cluster. `currentCSV` is the newest CSV known/resolved by OLM for the Subscription. If they differ, an upgrade may be pending, blocked, or waiting for approval.

---

### Q6. Why should production clusters often use Manual approval?

Because Operator upgrades can modify CRDs, RBAC, webhooks, deployments, and operands. Manual approval lets administrators review the InstallPlan and schedule the change.

---

### Q7. Can channel switching be used for rollback?

No. Channel switching should not be treated as rollback. Downgrades may be unsafe because CRDs, stored resources, and operands may already have been upgraded.

---

### Q8. What can break Operator upgrades in disconnected clusters?

Missing intermediate bundles, missing bundle images, invalid catalog metadata, a broken upgrade graph, stale CatalogSource images, or pruned versions required by the upgrade path.

---

### Q9. How do `replaces`, `skips`, and `skipRange` differ?

| Mechanism | Purpose |
|---|---|
| `replaces` | Defines direct upgrade from one specific previous version |
| `skips` | Allows skipping specific problematic versions |
| `skipRange` | Allows skipping a semantic version range when direct upgrade is supported |

---

### Q10. What should you check before approving an Operator upgrade?

Check:

- InstallPlan resources
- New CSV
- CRD changes
- RBAC changes
- Webhooks
- APIService objects
- Operator release notes
- Operand impact
- Backup/recovery plan

---

## 24. Summary

Operator upgrade channels are the control plane for Operator lifecycle velocity. They define which update stream a Subscription follows and work together with OLM's upgrade graph to decide what version can be installed next.

For advanced OpenShift administration:

- A Subscription tracks a package and channel.
- The channel contains upgrade paths and a channel head.
- OLM creates InstallPlans for installs and upgrades.
- `Automatic` approval upgrades without human approval.
- `Manual` approval requires administrator review.
- `currentCSV` shows the newest known target.
- `installedCSV` shows the currently installed Operator version.
- `replaces`, `skips`, and `skipRange` define valid upgrade movement.
- Channel switching should be planned, tested, and usually forward-moving.
- Disconnected catalogs must preserve valid upgrade paths.
- Custom catalogs must be validated and governed like production software artifacts.

A strong OpenShift administrator does not just click **Upgrade**. They understand the Subscription, the channel, the catalog, the graph, the InstallPlan, the CSV, and the operand impact.
