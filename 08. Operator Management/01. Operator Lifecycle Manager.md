## 1. Executive Summary

**Operator Lifecycle Manager (OLM)** is the OpenShift subsystem that installs, upgrades, and manages **application Operators**. It provides a Kubernetes-native way to consume packaged operational automation from catalogs.

In practical terms, OLM answers these questions:

- Where do Operators come from?
- Which version should be installed?
- Which namespace should the Operator run in?
- Which namespaces should the Operator watch?
- Which CRDs, RBAC rules, deployments, and service accounts must be created?
- Should upgrades happen automatically or only after admin approval?
- Are dependencies and APIs satisfied before installation or upgrade?

For an advanced OpenShift administrator, OLM is not just a GUI feature behind **OperatorHub**. It is a full lifecycle control plane built from CRDs, controllers, catalog metadata, dependency resolution, RBAC generation, and upgrade graphs.

The most important OLM Classic flow is:

```text
CatalogSource
     ↓
Package / Channel / Bundle metadata
     ↓
Subscription
     ↓
InstallPlan
     ↓
ClusterServiceVersion (CSV)
     ↓
Operator Deployment + RBAC + CRDs + APIs
```

A senior administrator must understand this flow because most production issues appear as stuck `Subscription`, pending `InstallPlan`, failed `CSV`, unhealthy `CatalogSource`, invalid `OperatorGroup`, catalog image pull failures, or dependency resolution errors.

## 2. Why OLM Exists

Kubernetes gives us primitives such as Deployments, Services, ConfigMaps, Secrets, RBAC, CRDs, and admission controls. But a complex platform component such as logging, storage, service mesh, virtualization, GitOps, monitoring, or database automation needs more than a deployment manifest.

It needs operational knowledge:

- How to install the component safely.
- How to create and upgrade CRDs.
- How to reconcile custom resources.
- How to manage dependencies.
- How to apply RBAC permissions.
- How to upgrade across supported versions.
- How to expose status to administrators.
- How to prevent unsafe upgrades.
- How to operate across one namespace, multiple namespaces, or the whole cluster.

An **Operator** encodes this operational knowledge. **OLM** manages the lifecycle of those Operators.

Without OLM, administrators would manually apply YAML files, track image versions, manage CRDs, update RBAC, and perform upgrades by reading every release note. OLM standardizes this by using catalog metadata and Kubernetes controllers.

## 3. Operator, OLM, OperatorHub, and CVO — Clear Separation

Many administrators confuse these terms. In production, this confusion causes wrong troubleshooting paths.

| Component | Purpose | Example |
|---|---|---|
| **Operator** | Controller that manages an application or platform component | OpenShift Logging Operator, OpenShift GitOps Operator, OpenShift Pipelines Operator |
| **OLM** | Installs, upgrades, and manages application Operators | Creates `Subscription`, `InstallPlan`, `CSV`, RBAC, deployments |
| **OperatorHub** | UI and catalog discovery experience | Web console page to find and install Operators |
| **CatalogSource** | Source of Operator metadata | `redhat-operators`, `certified-operators`, custom mirrored catalog |
| **CVO** | Cluster Version Operator; manages core OpenShift cluster Operators | kube-apiserver, console, authentication, monitoring, ingress |

Important distinction:

- **Core OpenShift cluster Operators** are managed by **Cluster Version Operator (CVO)**.
- **Application / optional Operators** are usually managed by **OLM**.

So if you run:

```bash
oc get co
```

You are checking **ClusterOperators** managed by CVO.

If you run:

```bash
oc get sub,csv,ip -A
```

You are checking **OLM-managed Operators**.

This distinction matters during troubleshooting. For example, `authentication`, `kube-apiserver`, and `network` do not have OLM `Subscription` objects. But `openshift-logging`, `openshift-gitops`, `openshift-pipelines`, and many vendor Operators usually do.

## 4. OLM Architecture

OLM Classic is installed by default in OpenShift 4.x and runs mainly in this namespace:

```bash
openshift-operator-lifecycle-manager
```

Catalog sources usually run in:

```bash
openshift-marketplace
```

### 4.1 Main OLM Components

Check OLM pods:

```bash
oc get pods -n openshift-operator-lifecycle-manager
```

Typical components include:

```text
olm-operator-...
catalog-operator-...
packageserver-...
```

Check marketplace pods:

```bash
oc get pods -n openshift-marketplace
```

Typical catalog pods include:

```text
redhat-operators-...
certified-operators-...
community-operators-...
redhat-marketplace-...
marketplace-operator-...
```

### 4.2 OLM Operator

The **OLM Operator** handles the runtime lifecycle of installed Operators. It watches `ClusterServiceVersion` resources and ensures that the install strategy is executed after requirements are met.

It is responsible for resources such as:

- Operator Deployments
- ServiceAccounts
- Roles and ClusterRoles
- RoleBindings and ClusterRoleBindings
- Some CRDs and API-related resources, depending on the install plan and CSV

### 4.3 Catalog Operator

The **Catalog Operator** handles catalog resolution and installation planning. It watches:

- `CatalogSource`
- `PackageManifest`
- `Subscription`
- `InstallPlan`

It resolves which CSV and supporting resources must be installed or upgraded.

### 4.4 Package Server

The package server exposes package metadata in a Kubernetes API-friendly way. It supports discovery through `PackageManifest` resources.

Example:

```bash
oc get packagemanifests -n openshift-marketplace
oc get packagemanifest <package_name> -n openshift-marketplace -o yaml
```

### 4.5 Marketplace Operator

The **Marketplace Operator** manages default OperatorHub catalog sources in `openshift-marketplace`.

It is important because if you directly edit default `CatalogSource` resources, your changes might be reverted. For persistent changes to default catalog behavior, modify the `OperatorHub` resource or disable default sources and create your own catalog sources.

## 6. OLM Installation and Upgrade Workflow

The normal OLM installation flow is:

```text
1. Admin chooses Operator package from catalog
2. Admin chooses namespace and update channel
3. Admin creates OperatorGroup if required
4. Admin creates Subscription
5. Catalog Operator resolves package, channel, dependencies, and CSV
6. Catalog Operator creates InstallPlan
7. InstallPlan is approved automatically or manually
8. OLM creates required resources
9. CSV moves through phases until Succeeded
10. Operator deployment starts reconciling its custom resources
```

### 6.1 Automatic Install Flow

If `installPlanApproval: Automatic`, OLM approves generated install plans automatically.

```yaml
spec:
  installPlanApproval: Automatic
```

This is easy but less controlled. It is acceptable for lower environments, but production clusters commonly use manual approval for high-impact Operators.

### 6.2 Manual Install Flow

If `installPlanApproval: Manual`, OLM creates an install plan but waits for approval.

```yaml
spec:
  installPlanApproval: Manual
```

The admin reviews the plan:

```bash
oc get installplan -n <operator_namespace>
oc describe installplan <installplan_name> -n <operator_namespace>
```

Approve it:

```bash
oc patch installplan <installplan_name> \
  -n <operator_namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 6.3 Upgrade Flow

Upgrade flow is similar to install flow:

```text
CatalogSource updated
     ↓
New bundle / CSV appears in channel
     ↓
Subscription detects new currentCSV
     ↓
InstallPlan generated
     ↓
Automatic or manual approval
     ↓
New CSV installed
     ↓
Old CSV replaced according to upgrade graph
```

## 7. OperatorGroup Deep Dive

An `OperatorGroup` defines the tenancy boundary for OLM-installed Operators.

It answers:

```text
Which namespaces should this Operator watch?
Where should OLM generate RBAC for this Operator?
Does the Operator support this install mode?
```

### 7.1 Same-Namespace OperatorGroup

Most namespace-scoped Operators use this pattern:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: app-operator-group
  namespace: app-operators
spec:
  targetNamespaces:
    - app-operators
```

This means the Operator runs in `app-operators` and watches `app-operators`.

### 7.2 Global OperatorGroup

A global OperatorGroup watches all namespaces.

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-operators
  namespace: openshift-operators
spec: {}
```

When neither `targetNamespaces` nor `selector` is set, it can represent all namespaces, depending on Operator support.

### 7.3 Operator Install Modes

CSV metadata declares install modes. Common modes:

| Install mode | Meaning |
|---|---|
| `OwnNamespace` | Operator watches its own namespace |
| `SingleNamespace` | Operator watches one selected namespace |
| `MultiNamespace` | Operator watches multiple selected namespaces |
| `AllNamespaces` | Operator watches the whole cluster |

If an Operator does not support the selected OperatorGroup mode, the CSV might fail or remain pending.

### 7.4 Common OperatorGroup Mistakes

#### Mistake 1: No OperatorGroup

Symptom:

```text
CSV Pending
message: no operator group found that is managing this namespace
```

Fix:

```bash
oc get operatorgroup -n <namespace>
```

Create one if absent.

#### Mistake 2: Multiple OperatorGroups in Same Namespace

Symptom:

```text
CSV Pending or Failed
reason: TooManyOperatorGroups
```

Fix:

```bash
oc get operatorgroup -n <namespace>
oc delete operatorgroup <wrong_og> -n <namespace>
```

Keep only one valid OperatorGroup per Operator installation namespace unless documentation says otherwise.

#### Mistake 3: Wrong Target Namespace

Example:

```yaml
spec:
  targetNamespaces:
    - wrong-namespace
```

The Operator installs but watches the wrong namespace, so custom resources appear ignored.

Check CSV annotations:

```bash
oc get csv <csv_name> -n <operator_namespace> -o yaml | grep -A5 olm.targetNamespaces
```

## 8. Subscription Deep Dive

A `Subscription` declares intent to install and track an Operator package from a catalog channel.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operators
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

### 8.1 Important Subscription Fields

| Field | Meaning |
|---|---|
| `spec.name` | Operator package name |
| `spec.channel` | Channel to follow, such as `stable`, `fast`, `stable-1.2` |
| `spec.source` | CatalogSource name |
| `spec.sourceNamespace` | Namespace containing the CatalogSource |
| `spec.installPlanApproval` | `Automatic` or `Manual` |
| `spec.startingCSV` | Optional starting CSV version |
| `status.currentCSV` | Latest resolved CSV known to OLM |
| `status.installedCSV` | CSV currently installed |
| `status.installPlanRef` | Current generated InstallPlan |
| `status.conditions` | Subscription health and resolution state |

### 8.2 View Subscriptions

```bash
oc get sub -A
oc get sub -n <operator_namespace>
oc describe sub <subscription_name> -n <operator_namespace>
oc get sub <subscription_name> -n <operator_namespace> -o yaml
```

### 8.3 Key Subscription Conditions

Common conditions include:

| Condition | Meaning |
|---|---|
| `CatalogSourcesUnhealthy` | One or more required catalog sources are unhealthy |
| `InstallPlanMissing` | Subscription expects an install plan but cannot find one |
| `InstallPlanPending` | Install plan exists but is not approved or not completed |
| `InstallPlanFailed` | Install plan failed to apply resources |
| `ResolutionFailed` | OLM could not resolve dependencies or valid upgrade path |

### 8.4 Subscription Troubleshooting Commands

```bash
NS=<operator_namespace>
SUB=<subscription_name>

oc describe sub $SUB -n $NS
oc get sub $SUB -n $NS -o jsonpath='{.status.conditions}' | jq
oc get sub $SUB -n $NS -o jsonpath='{.status.currentCSV}{"\n"}{.status.installedCSV}{"\n"}'
oc get installplan -n $NS
```

## 9. InstallPlan Deep Dive

An `InstallPlan` is the exact plan OLM will execute to install or upgrade an Operator.

It contains:

- CSV name
- CRDs to create or update
- ServiceAccounts
- Roles and ClusterRoles
- RoleBindings and ClusterRoleBindings
- Deployments
- Webhooks and API services if required
- Status of each planned resource

### 9.1 View InstallPlans

```bash
oc get installplan -A
oc get installplan -n <operator_namespace>
oc describe installplan <installplan_name> -n <operator_namespace>
oc get installplan <installplan_name> -n <operator_namespace> -o yaml
```

### 9.2 Manual Approval

If manual approval is used:

```bash
oc get ip -n <operator_namespace>
```

Look for:

```text
APPROVED   APPROVAL
false      Manual
```

Approve:

```bash
oc patch installplan <installplan_name> \
  -n <operator_namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 9.3 Review What InstallPlan Will Create

```bash
oc get installplan <installplan_name> -n <operator_namespace> -o jsonpath='{range .status.plan[*]}{.resource.kind}{"\t"}{.resource.name}{"\t"}{.status}{"\n"}{end}'
```

This is useful before approving upgrades in production.

### 9.4 InstallPlan Failure Analysis

Check:

```bash
oc describe installplan <installplan_name> -n <operator_namespace>
oc get events -n <operator_namespace> --sort-by=.lastTimestamp
```

Look for:

- RBAC denied
- CRD conflict
- APIService unavailable
- webhook failure
- image pull failure
- namespace termination
- ownership conflict
- missing dependency
- invalid CSV

## 10. ClusterServiceVersion Deep Dive

A `ClusterServiceVersion` or `CSV` represents a specific installed Operator version.

Example name:

```text
openshift-gitops-operator.v1.14.0
cluster-logging.v6.2.0
```

A CSV includes:

- Operator version
- Display name
- Description
- Install strategy
- Required permissions
- Owned CRDs
- Required CRDs
- Owned API services
- Required API services
- Related images
- Install modes
- Replacement / upgrade metadata

### 10.1 View CSVs

```bash
oc get csv -A
oc get csv -n <operator_namespace>
oc describe csv <csv_name> -n <operator_namespace>
oc get csv <csv_name> -n <operator_namespace> -o yaml
```

### 10.2 CSV Phases

Common CSV phases:

| Phase | Meaning |
|---|---|
| `Pending` | Requirements are not satisfied yet |
| `InstallReady` | Requirements are satisfied and installation can start |
| `Installing` | OLM is creating resources |
| `Succeeded` | Operator installation completed |
| `Failed` | Installation failed |
| `Replacing` | CSV is being replaced by a newer version |
| `Deleting` | CSV is being removed |

### 10.3 CSV Troubleshooting

```bash
oc describe csv <csv_name> -n <operator_namespace>
oc get csv <csv_name> -n <operator_namespace> -o jsonpath='{.status.phase}{"\n"}{.status.reason}{"\n"}{.status.message}{"\n"}'
```

Check owned CRDs:

```bash
oc get csv <csv_name> -n <operator_namespace> -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'
```

Check required CRDs:

```bash
oc get csv <csv_name> -n <operator_namespace> -o jsonpath='{range .spec.customresourcedefinitions.required[*]}{.name}{"\n"}{end}'
```

Check install modes:

```bash
oc get csv <csv_name> -n <operator_namespace> -o jsonpath='{range .spec.installModes[*]}{.type}{"="}{.supported}{"\n"}{end}'
```

## 11. CatalogSource and Operator Catalogs

A `CatalogSource` points OLM to Operator metadata.

Default catalogs usually live in:

```bash
openshift-marketplace
```

List them:

```bash
oc get catalogsource -n openshift-marketplace
```

Common default catalogs:

```text
redhat-operators
certified-operators
community-operators
redhat-marketplace
```

### 11.1 CatalogSource Example

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: custom-redhat-operators
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: mirror.registry.example.com/redhat/redhat-operator-index:v4.19
  displayName: Custom Red Hat Operators
  publisher: Platform Team
```

### 11.2 CatalogSource Health

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource redhat-operators -n openshift-marketplace
oc get pods -n openshift-marketplace
```

Check related catalog pod:

```bash
oc get pods -n openshift-marketplace | grep redhat-operators
oc logs <catalog_pod> -n openshift-marketplace
```

### 11.3 CatalogSource Unhealthy Impact

OLM requires catalog sources in a shared global namespace to be healthy for reliable dependency resolution. An unhealthy catalog can block Operator installs or upgrades with `CatalogSourcesUnhealthy`.

Typical causes:

- Catalog index image cannot be pulled.
- Registry authentication failure.
- Proxy or custom CA issue.
- Image tag does not exist.
- Disconnected mirror missing catalog image.
- Catalog pod crashloop.
- Marketplace Operator reverting unsupported changes.

## 12. PackageManifest, Channels, Bundles, and Upgrade Graphs

### 12.1 PackageManifest

A `PackageManifest` gives a catalog-level view of an Operator package.

```bash
oc get packagemanifests -n openshift-marketplace
oc get packagemanifest <package_name> -n openshift-marketplace -o yaml
```

Useful fields:

```text
status.catalogSource
status.catalogSourceNamespace
status.defaultChannel
status.channels[].name
status.channels[].currentCSV
status.channels[].currentCSVDesc
```

Find package channels:

```bash
oc get packagemanifest <package_name> -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{"\t"}{.currentCSV}{"\n"}{end}'
```

### 12.2 Bundle

A bundle is a versioned Operator artifact that includes metadata such as:

- CSV
- CRDs
- Related manifests
- Annotations
- Dependency metadata

### 12.3 Channel

A channel is an update stream.

Examples:

```text
stable
fast
preview
stable-1.12
stable-v1.14
```

Do not assume every Operator uses the same channel naming. Always check package manifests or official documentation.

### 12.4 Upgrade Graph

The upgrade graph defines how OLM moves from one Operator version to another.

Common metadata:

| Field | Meaning |
|---|---|
| `replaces` | New CSV replaces a previous CSV |
| `skips` | New CSV can skip listed CSVs |
| `olm.skipRange` | SemVer range that can be skipped |

In production, upgrade graph issues usually appear as:

```text
constraints not satisfiable
no operators found with matching package/channel
cannot update from installedCSV to currentCSV
```

Manual approval example:

```bash

```


## 14. Manual Approval and Controlled Upgrades

In production, manual approval is often preferred for Operators that affect cluster-wide CRDs, storage, networking, security, service mesh, logging, monitoring, virtualization, GitOps, or admission webhooks.

Manual approval lets administrators review the generated `InstallPlan` before OLM mutates the cluster.

### 14.1 Find Pending InstallPlans

```bash
oc get installplan -A | grep -i false

oc get installplan -A \
  -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,APPROVED:.spec.approved,PHASE:.status.phase,CSV:.spec.clusterServiceVersionNames'
```

### 14.2 Inspect Resource Plan Before Approval

```bash
oc get installplan <ip> -n <ns> \
  -o jsonpath='{range .status.plan[*]}{.resource.kind}{"\t"}{.resource.name}{"\t"}{.status}{"\n"}{end}'
```

### 14.3 Review CSV to Be Installed

```bash
oc get installplan <ip> -n <ns> \
  -o jsonpath='{.spec.clusterServiceVersionNames}{"\n"}'
```

### 14.4 Approve

```bash
oc patch installplan <ip> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

### 14.5 Watch Progress

```bash
watch 'oc get ip,csv,pods -n <ns>'
```

### 14.6 Production Approval Checklist

Before approving an Operator upgrade, verify:

- Maintenance window is approved.
- Operator release notes are reviewed.
- Target OpenShift version is supported.
- Operand version compatibility is known.
- CRD schema changes are understood.
- Webhook/APIService impact is understood.
- Required images are mirrored if disconnected.
- Backups exist for stateful components.
- Rollback or recovery procedure is documented.

## 15. Operator Upgrades, Channel Changes, and Version Control

### 15.1 Check Current and Installed CSV

```bash
oc get sub <sub_name> -n <ns> \
  -o jsonpath='currentCSV={.status.currentCSV}{"\n"}installedCSV={.status.installedCSV}{"\n"}'
```

If `currentCSV` is newer than `installedCSV`, an upgrade is available, pending, or blocked.

### 15.2 Change Channel

```bash
oc patch sub <sub_name> -n <ns> --type merge -p '{"spec":{"channel":"stable-1.14"}}'
```

Then check:

```bash
oc describe sub <sub_name> -n <ns>
oc get installplan -n <ns>
```

### 15.3 Use Manual Approval Before Channel Change

```bash
oc patch sub <sub_name> -n <ns> --type merge -p '{"spec":{"installPlanApproval":"Manual"}}'
```

Then change the channel. This prevents an immediate uncontrolled upgrade.

### 15.4 Starting CSV and Version Pinning

`spec.startingCSV` can specify an initial version during first installation:

```yaml
spec:
  startingCSV: example-operator.v1.2.3
```

Important:

- `startingCSV` is mainly for initial install path selection.
- It is not a long-term pinning mechanism by itself.
- For long-term control, use manual approval and curated catalogs/channels.

### 15.5 Downgrade and Rollback Reality

OLM is designed primarily for forward upgrades based on supported upgrade graphs. Do not assume that installing an older CSV is a supported rollback.

Rollback depends on:

- Operator vendor support.
- CRD schema compatibility.
- Operand data compatibility.
- Conversion webhook behavior.
- Backup and restore strategy.
- Whether the old bundle still exists in the catalog.
- Whether downgrade is explicitly supported.

For stateful Operators, rollback normally requires application-level backup and restore planning.

## 16. Deleting and Cleaning Up Operators

Deleting an Operator is not always the same as deleting everything it created.

### 16.1 Basic OLM Uninstall

```bash
oc delete subscription <sub_name> -n <operator_namespace>
oc delete csv <csv_name> -n <operator_namespace>
```

This usually removes the Operator deployment managed by the CSV.

### 16.2 What Might Remain

After deleting Subscription and CSV, the following might remain:

- CRDs
- Custom resources
- Operand deployments
- PVCs
- Secrets
- ConfigMaps
- Webhooks
- API services
- ClusterRoles and ClusterRoleBindings
- Finalizers
- External cloud resources

### 16.3 Safe Uninstall Order

Recommended production sequence:

```text
1. Read Operator-specific uninstall documentation.
2. Stop or drain affected workloads if required.
3. Delete custom resources managed by the Operator.
4. Wait for operands to clean up.
5. Delete Subscription.
6. Delete CSV.
7. Remove OperatorGroup only if namespace is no longer used by other Operators.
8. Remove CRDs only if no custom resources remain and no other Operator depends on them.
9. Clean PVCs, secrets, and external resources carefully.
```

### 16.4 Identify CRDs Owned by CSV

```bash
oc get csv <csv_name> -n <ns> \
  -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'
```

Check whether CRs still exist:

```bash
oc get <crd_plural> -A
```

Do not delete CRDs blindly in production.

## 17. Disconnected / Restricted Network OLM

In disconnected environments, OLM cannot use default remote OperatorHub content unless you mirror catalogs and related images to an internal registry.

High-level flow:

```text
1. Disable default remote OperatorHub sources.
2. Mirror required Operator catalog and images to an internal registry.
3. Configure image mirror resources.
4. Create local CatalogSource pointing to mirrored catalog image.
5. Install Operators from local CatalogSource.
6. Keep mirror updated using a controlled process.
```

### 17.1 Disable Default Sources

```bash
oc patch OperatorHub cluster --type json \
  -p '[{"op": "add", "path": "/spec/disableAllDefaultSources", "value": true}]'
```

Or:

```bash
oc patch operatorhub cluster -p '{"spec": {"disableAllDefaultSources": true}}' --type=merge
```

Verify:

```bash
oc get operatorhub cluster -o yaml
oc get catalogsource -n openshift-marketplace
```

### 17.2 Mirror with oc-mirror

For modern OpenShift releases, `oc-mirror` v2 is commonly recommended for disconnected content workflows.

Conceptual image set configuration:

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
mirror:
  platform:
    channels:
      - name: stable-4.19
        minVersion: 4.19.0
        maxVersion: 4.19.z
  operators:
    - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.19
      packages:
        - name: example-operator
          channels:
            - name: stable
  additionalImages:
    - name: registry.redhat.io/ubi9/ubi:latest
```

Actual schema and fields can vary by OpenShift and `oc-mirror` version. Always validate with current docs and `oc mirror --help`.

### 17.3 Create Local CatalogSource

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: local-redhat-operators
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: mirror.registry.example.com/redhat/redhat-operator-index:v4.19
  displayName: Local Red Hat Operators
  publisher: Internal Platform Team
```

Apply and verify:

```bash
oc apply -f local-redhat-operators.yaml
oc get catalogsource -n openshift-marketplace
oc describe catalogsource local-redhat-operators -n openshift-marketplace
oc get pods -n openshift-marketplace | grep local-redhat-operators
```


Check pull secret:

## 18. Custom Catalog Management

Custom catalogs are used when an organization wants:

- Only approved Operators.
- Version-controlled Operator supply chain.
- Internal certification.
- Disconnected environments.
- Faster OperatorHub loading.
- Security review before publishing.
- Reduced blast radius from community catalogs.

### 18.1 File-Based Catalogs

File-based catalogs are YAML/JSON catalog metadata. They are easier to edit, compose, and store in Git than older SQLite-based formats.

Common `opm` commands:

```bash
opm render <catalog_image> -o yaml > index.yaml
opm validate <catalog_directory>
opm generate dockerfile <catalog_directory>
podman build -t <registry>/<namespace>/<catalog>:<tag> <catalog_directory>
podman push <registry>/<namespace>/<catalog>:<tag>
```

### 18.2 Filter Catalog Content

Typical reasons to filter:

- Keep only supported Operators.
- Remove community Operators.
- Keep only selected packages.
- Keep only selected channels.
- Remove vulnerable or deprecated versions.

### 18.3 Custom CatalogSource with Private Registry

```bash
oc create secret docker-registry catalog-pull-secret \
  --docker-server=mirror.registry.example.com \
  --docker-username=<user> \
  --docker-password=<password> \
  --docker-email=admin@example.com \
  -n openshift-marketplace
```

Use private registry secrets according to your OpenShift version and catalog configuration.

### 18.4 Catalog Pod Scheduling

For `grpc` catalog sources, you can tune catalog pod placement with `grpcPodConfig`.

```yaml
spec:
  grpcPodConfig:
    nodeSelector:
      node-role.kubernetes.io/infra: ""
    tolerations:
      - key: "node-role.kubernetes.io/infra"
        operator: "Exists"
        effect: "NoSchedule"
```

This is useful when marketplace/catalog pods should run on infra nodes.

## 19. Security, RBAC, SCC, and Multi-Tenancy

OLM can create cluster-scoped resources. That makes it powerful and sensitive.

### 19.1 Operator Installation Permissions

Installing Operators often requires elevated permission because Operators can request:

- CRDs
- ClusterRoles
- ClusterRoleBindings
- APIService resources
- Webhooks
- SCC usage
- Cluster-wide watches

Production principle:

```text
Do not allow random project admins to install arbitrary cluster-scoped Operators.
```

### 19.2 Inspect Operator Permissions

```bash
oc get csv <csv> -n <ns> -o yaml
```

Review:

```text
spec.install.spec.permissions
spec.install.spec.clusterPermissions
spec.customresourcedefinitions.owned
spec.customresourcedefinitions.required
spec.apiservicedefinitions.owned
spec.webhookdefinitions
```

If an Operator requests broad cluster-admin-like permissions, understand why before approval.

### 19.3 OperatorGroup and Tenant Isolation

A namespace-scoped OperatorGroup is safer for tenant isolation:

```yaml
spec:
  targetNamespaces:
    - tenant-a
```

Avoid global watch unless required:

```yaml
spec: {}
```

### 19.4 SCC and Pod Security

Some Operators deploy operands that require special permissions. The Operator itself may run, but managed workloads can fail due to SCC or Pod Security Admission.

Symptoms:

```text
violates PodSecurity
unable to validate against any security context constraint
forbidden: unable to use SCC
```

Check:

```bash
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get sa -n <ns>
oc adm policy who-can use scc/anyuid
```

Apply SCC only when required and approved:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

### 19.5 Supply Chain Controls

Enterprise controls should include:

- Disable unapproved default catalogs if necessary.
- Use curated internal catalogs.
- Mirror images internally.
- Scan Operator and operand images.
- Use image policies and signature verification where applicable.
- Prefer Red Hat-supported or certified Operators for production.
- Track Operator versions in GitOps.

## 22. Common OLM Failure Scenarios and Fixes

### Scenario 1: `CatalogSourcesUnhealthy`

Symptoms:

```text
Subscription condition: CatalogSourcesUnhealthy
Catalog pod ImagePullBackOff
CatalogSource not ready
```

Commands:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalog> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc describe pod <catalog_pod> -n openshift-marketplace
oc logs <catalog_pod> -n openshift-marketplace
```

Common fixes:

- Correct catalog image reference.
- Fix pull secret.
- Add custom CA.
- Fix proxy configuration.
- Mirror missing image.
- Remove or disable broken catalog source.

### Scenario 2: `ResolutionFailed`

Symptoms:

```text
constraints not satisfiable
no operators found with name/package/channel
required API not provided
```

Commands:

```bash
oc describe sub <sub> -n <ns>
oc get packagemanifest <package> -n openshift-marketplace -o yaml
oc get catalogsource -n openshift-marketplace
```

Fixes:

- Correct package name.
- Correct channel name.
- Correct catalog source.
- Ensure dependency Operator is available.
- Use a catalog that contains the required bundle.
- Avoid incompatible channel jumps.

### Scenario 3: `InstallPlanPending`

Symptoms:

```text
InstallPlan exists but approved=false
Subscription shows InstallPlanPending
```

Fix:

```bash
oc get ip -n <ns>
oc describe ip <ip> -n <ns>
oc patch ip <ip> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

Only approve after reviewing the resources.

### Scenario 4: `InstallPlanFailed`

Commands:

```bash
oc describe ip <ip> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc logs deploy/catalog-operator -n openshift-operator-lifecycle-manager
```

Fixes depend on cause:

- Resolve RBAC denial.
- Remove conflicting resources.
- Fix CRD/APIService conflict.
- Fix webhook admission error.
- Fix namespace termination.
- Fix catalog metadata.

### Scenario 5: CSV Stuck in `Pending`

```bash
oc describe csv <csv> -n <ns>
oc get og -n <ns>
oc get crd | grep <required_crd>
```

Common causes:

- No OperatorGroup.
- Multiple OperatorGroups.
- Unsupported install mode.
- Missing required CRD.
- Dependency resolution issue.

### Scenario 6: CSV `Failed`

```bash
oc describe csv <csv> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get deploy,pods -n <ns>
```

Common causes:

- Deployment failed.
- Image pull failure.
- Invalid install strategy.
- RBAC issue.
- Pod security/SCC issue.
- Required API unavailable.

### Scenario 7: Operator Pod ImagePullBackOff

```bash
oc describe pod <pod> -n <ns>
oc get secret -n <ns>
oc get pull-secret -n openshift-config -o yaml
```

Fixes:

- Add registry credentials.
- Mirror operator and operand images.
- Fix ImageDigestMirrorSet/ImageTagMirrorSet.
- Fix disconnected registry certificate trust.

### Scenario 8: Operator Installed but Custom Resource Does Nothing

```bash
oc get og -n <operator_namespace> -o yaml
oc get csv <csv> -n <operator_namespace> -o yaml | grep -A5 olm.targetNamespaces
oc logs deploy/<operator_deployment> -n <operator_namespace>
```

Common causes:

- Custom resource created in wrong namespace.
- OperatorGroup target namespace mismatch.
- Operator supports only selected install modes.
- Missing RBAC for watched namespace.

### Scenario 9: Default Catalog Changes Keep Reverting

Cause: the Marketplace Operator manages default CatalogSources.

Fix:

```bash
oc patch operatorhub cluster -p '{"spec": {"disableAllDefaultSources": true}}' --type=merge
```

Then create a custom CatalogSource with required settings.

### Scenario 10: Upgrade Stuck Because Old CSV Remains

```bash
oc get csv -n <ns>
oc describe sub <sub> -n <ns>
oc describe csv <old_csv> -n <ns>
oc describe csv <new_csv> -n <ns>
```

Common causes:

- Old CSV still owns an API.
- New CSV requirements not met.
- InstallPlan not approved.
- Dependency deadlock.
- Operator condition marks upgrade unsafe.

Fixes:

- Approve pending InstallPlan if valid.
- Resolve dependency Operator first.
- Check Operator documentation for upgrade path.
- Do not manually delete CSVs unless you understand ownership and cleanup impact.

## 24. Best Practices for Enterprise OpenShift

### 24.1 Use Manual Approval for Production

```yaml
installPlanApproval: Manual
```

This prevents surprise upgrades.

### 24.2 Keep Operator Namespace Strategy Clean

Use a dedicated namespace per major Operator unless vendor documentation recommends shared installation.

Examples:

```text
openshift-logging
openshift-gitops
openshift-storage
openshift-cnv
openshift-pipelines
```

### 24.3 Maintain One Valid OperatorGroup Per Operator Namespace

```bash
oc get og -A
```

Avoid multiple OperatorGroups in one namespace.

### 24.4 Use Curated Catalogs

For secure environments:

- Disable default catalogs.
- Mirror only approved Operators.
- Publish internal catalogs.
- Version catalog images.
- Store catalog metadata in Git.

### 24.5 Always Check Operator Documentation

Before installing or upgrading, check:

- Supported OpenShift versions.
- Required channel.
- Install mode.
- Required namespace.
- Required SCC or privileges.
- CRD changes.
- Backup and restore requirements.
- Upgrade path.
- Known issues.

### 24.6 Keep Operator Changes in GitOps

Good GitOps resources:

- Namespace
- OperatorGroup
- Subscription
- CatalogSource
- Image mirror resources
- Operator custom resources

Usually avoid GitOps-managing generated CSVs and InstallPlans unless you have a special reason.

### 24.7 Separate Operator Upgrade from Operand Upgrade

Many Operators separate controller lifecycle from operand/application lifecycle. Upgrading the Operator may or may not upgrade the managed application immediately. Read the Operator release notes.

### 24.8 Backup Before Major Operator Upgrades

For stateful Operators:

- Backup custom resources.
- Backup namespaces.
- Backup persistent data.
- Backup etcd if cluster-level changes are involved.
- Validate restore procedure.

### 24.9 Avoid Blind CSV Deletion

Deleting a CSV can remove the Operator deployment but does not necessarily clean CRDs or operands. It can also break upgrade ownership if done at the wrong time.

### 24.10 Watch for API Deprecation

Operators that use removed Kubernetes APIs might fail on newer OpenShift versions. Verify Operator compatibility before cluster upgrades.

## 25. OLM Classic vs OLM v1 / Extensions

OpenShift includes long-standing OLM Classic APIs and newer OLM v1 / Extensions concepts.

### 25.1 OLM Classic

Core resources:

```text
CatalogSource
PackageManifest
Subscription
InstallPlan
ClusterServiceVersion
OperatorGroup
OperatorCondition
```

This is the model most OpenShift administrators use today for OperatorHub-based installations.

### 25.2 OLM v1 / Extensions

OLM v1 introduces newer APIs and components for extension lifecycle management.

| OLM v1 Concept | Purpose |
|---|---|
| `ClusterCatalog` | Cluster-level catalog source for extension discovery |
| `ClusterExtension` | Desired installation of an extension / Operator-like package |
| `catalogd` | Component that unpacks catalog content for on-cluster clients |
| File-based catalogs | Declarative YAML/JSON catalog metadata |

Example conceptual `ClusterCatalog`:

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterCatalog
metadata:
  name: my-redhat-operators
spec:
  priority: 1000
  source:
    type: Image
    image:
      ref: registry.redhat.io/redhat/redhat-operator-index:v4.19
      pollIntervalMinutes: 10
```

Example conceptual `ClusterExtension`:

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterExtension
metadata:
  name: example-extension
spec:
  namespace: example-operators
  serviceAccount:
    name: example-extension-installer
  source:
    sourceType: Catalog
    catalog:
      packageName: example-operator
      selector:
        matchLabels:
          olm.operatorframework.io/metadata.name: my-redhat-operators
```

### 25.3 Practical Advice

```text
Know OLM Classic deeply because it is widely used in existing clusters.
Understand OLM v1 because newer OpenShift releases are evolving toward extension-focused lifecycle APIs.
Do not mix assumptions between OLM Classic and OLM v1 resources.
```

Classic:

```bash
oc get sub,ip,csv,og -A
```

OLM v1:

```bash
oc get clustercatalog
oc get clusterextension
```

## 27. Interview and Real-World Discussion Points

### 27.1 What happens when you install an Operator from OperatorHub?

```text
OperatorHub helps select a package/channel from a CatalogSource.
A Subscription is created in the target namespace.
The Catalog Operator resolves the package, channel, dependencies, and CSV.
An InstallPlan is generated.
If approved, OLM creates resources defined by the CSV.
The CSV reaches Succeeded when the Operator deployment and requirements are healthy.
```

### 27.2 Difference between Subscription and CSV

```text
Subscription = desired lifecycle tracking configuration.
CSV = concrete installed Operator version.
```

### 27.3 Difference between CatalogSource and PackageManifest

```text
CatalogSource = source of catalog metadata.
PackageManifest = discovered package view generated from catalog metadata.
```

### 27.4 Why use Manual approval?

```text
To prevent unplanned Operator upgrades, review CRD/RBAC/webhook changes, and align changes with maintenance windows.
```

### 27.5 Why does CSV stay Pending?

```text
No OperatorGroup
Multiple OperatorGroups
Unsupported install mode
Missing required API/CRD
Dependency resolution failure
InstallPlan not approved
```

### 27.6 Why are default CatalogSource changes reverted?

```text
The Marketplace Operator manages default OperatorHub catalog sources. For persistent changes, modify OperatorHub configuration, disable default sources, or create custom CatalogSources.
```

### 27.7 How do you install Operators in disconnected OpenShift?

```text
Mirror catalog and related images to internal registry.
Disable default remote sources.
Configure mirror resources and pull secrets.
Create CatalogSource pointing to internal registry.
Install using Subscription from local CatalogSource.
```

### 27.8 Biggest production risk with Operators

```text
Operators can create cluster-scoped APIs, RBAC, webhooks, and controllers. A bad Operator or uncontrolled upgrade can affect the whole cluster. Control catalog source, approval mode, RBAC, and upgrade windows.
```

## Final Senior Admin Notes

For real-world OpenShift administration, remember this practical rule:

```text
If an Operator install or upgrade fails, do not start with pod logs only.
Start from OLM intent and resolution:
CatalogSource → PackageManifest → OperatorGroup → Subscription → InstallPlan → CSV → Operator Pod → Operand CR.
```

Most OLM incidents become simple once you identify which layer is broken.
