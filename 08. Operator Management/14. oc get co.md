# `oc get co` Deep Dive for Advanced OpenShift Administration

**Topic:** Operator Management → Cluster Operators health check and troubleshooting  
**Audience:** Senior OpenShift / Kubernetes administrators, L3 support engineers, SREs  
**Command focus:** `oc get co` / `oc get clusteroperators`  
**OpenShift scope:** OpenShift Container Platform 4.x  
**Last updated:** 2026-07-03

---

## 1. Executive Summary

`oc get co` is one of the most important day-2 administration commands in OpenShift. It displays the status of **ClusterOperator** resources, which represent the health and lifecycle state of core OpenShift platform components such as `authentication`, `console`, `dns`, `etcd`, `ingress`, `kube-apiserver`, `machine-config`, `monitoring`, `network`, `openshift-apiserver`, and others.

In production, an experienced OpenShift administrator does not treat `oc get co` as a simple listing command. It is a **cluster health dashboard from the CLI**. It helps answer these questions quickly:

- Is the cluster healthy?
- Which core operator is degraded?
- Is an upgrade still progressing?
- Which operator is blocking an upgrade?
- Is the issue with the operator itself, its operand, its configuration, or infrastructure?
- Should I troubleshoot OLM resources such as `Subscription` and `CSV`, or should I troubleshoot CVO-managed platform components?

A healthy steady-state cluster normally looks like this:


## 2. What `oc get co` Means

### 2.1 Command Expansion

`co` is the short name for the OpenShift resource:

```text
clusteroperators.config.openshift.io
```

These commands are functionally equivalent:

```bash
oc get co
oc get clusteroperator
oc get clusteroperators
oc get clusteroperators.config.openshift.io
```

A specific operator can be inspected like this:

```bash
oc get co authentication
oc describe co authentication
oc get co authentication -o yaml
oc get clusteroperator/authentication -o json
```

### 2.2 API Group

ClusterOperator objects belong to:

```yaml
apiVersion: config.openshift.io/v1
kind: ClusterOperator
```

They are **cluster-scoped**, not namespace-scoped. That means this is correct:

```bash
oc get co
oc get co network
```

This is not how you query them:

```bash
oc get co -n openshift-network-operator
```

The operator workload might run in a namespace, but the `ClusterOperator` status object itself is cluster-wide.

### 2.3 Why It Exists

Every core OpenShift platform area is operated by a component that reconciles desired state into actual state. The `ClusterOperator` object is the standard status object that tells the rest of the cluster, the Cluster Version Operator, and administrators whether that platform area is healthy.

Examples:

| ClusterOperator | What it represents |
|---|---|
| `authentication` | OAuth server, authentication operator, identity provider rollout |
| `console` | OpenShift web console availability |
| `dns` | Cluster DNS operator and DNS daemonsets |
| `etcd` | etcd cluster health and etcd static pod management |
| `ingress` | Ingress Operator, router deployments, default ingress controller |
| `kube-apiserver` | Kubernetes API server static pods and revisions |
| `machine-config` | MachineConfigController, node OS/config rollout, MCP health |
| `monitoring` | Cluster Monitoring Operator and monitoring stack |
| `network` | Cluster Network Operator and SDN/OVN-Kubernetes components |
| `operator-lifecycle-manager` | OLM core platform components |
| `storage` | Cluster Storage Operator and default storage integrations |

## 3. Cluster Operators vs OLM Operators

This distinction is critical in Operator Management.

### 3.1 Cluster Operators

Cluster Operators are the platform operators that ship with OpenShift. They are installed by default or enabled by cluster capabilities, and they are managed by the **Cluster Version Operator (CVO)**.

You inspect them with:

```bash
oc get co
oc describe co <name>
oc get clusterversion
oc describe clusterversion version
```

They usually do **not** have:

```bash
Subscription
InstallPlan
ClusterServiceVersion
OperatorGroup
```

So, when `oc get co network` is degraded, do not start by looking for a `Subscription` or `CSV` for `network`. You should inspect the `ClusterOperator`, its related objects, its operator deployment/static pods, events, and operand resources.

### 3.2 OLM-managed Operators

Application/add-on operators installed from OperatorHub or catalogs are normally managed by Operator Lifecycle Manager.

You inspect them with:

```bash
oc get sub -A
oc get csv -A
oc get installplan -A
oc get catalogsource -A
oc describe sub <subscription> -n <namespace>
oc describe csv <csv> -n <namespace>
```

Examples:

- OpenShift Logging Operator
- Red Hat OpenShift GitOps Operator
- File Integrity Operator
- Serverless Operator
- Service Mesh Operator
- Pipelines Operator

### 3.3 Important Practical Rule

Use this rule during incidents:

```text
If the problem is with OpenShift platform health, upgrades, control plane, nodes, networking, ingress, DNS, auth, monitoring, or machine config → start with oc get co.

If the problem is with an installed add-on operator from OperatorHub → start with Subscription, CSV, InstallPlan, CatalogSource, and OperatorGroup.
```

However, there is an overlap. Some cluster operators manage platform components related to OLM itself:

```bash
oc get co operator-lifecycle-manager
oc get co operator-lifecycle-manager-catalog
oc get co operator-lifecycle-manager-packageserver
oc get co marketplace
```

If these are degraded, the OperatorHub experience and OLM-based operator installation can fail.

## 4. Understanding the Output Columns

Example:

```bash
$ oc get co
NAME                 VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
authentication       4.14.20   True        False         False      10d
console              4.14.20   True        False         False      10d
kube-apiserver       4.14.20   True        False         False      10d
machine-config       4.14.20   True        False         False      10d
network              4.14.20   True        False         False      10d
```

### 4.1 `NAME`

The ClusterOperator resource name.

Example:

```bash
oc get co network
oc get co ingress
oc get co machine-config
```

The name is not always identical to the namespace where the operator pod runs. For example:

| ClusterOperator | Common operator namespace |
|---|---|
| `network` | `openshift-network-operator` |
| `ingress` | `openshift-ingress-operator` |
| `authentication` | `openshift-authentication-operator` |
| `kube-apiserver` | `openshift-kube-apiserver-operator` |
| `machine-config` | `openshift-machine-config-operator` |
| `monitoring` | `openshift-monitoring` |

### 4.2 `VERSION`

The OpenShift version reported by the operator or its operand status. It usually aligns with the cluster release version, but there can be brief mismatch during upgrades.

Example:

```bash
oc get co machine-config
```

During upgrade, you might see:

```text
machine-config   4.14.20   True   True   False   25m   Working towards 4.14.21
```

Important points:

- Version is reported through `.status.versions`.
- An operator can manage multiple operands and therefore report multiple version tuples.
- The table output displays a simplified version view.
- If the operator is unavailable or not reporting correctly, version might be empty or stale.

Inspect full versions:

```bash
oc get co kube-apiserver -o jsonpath='{range .status.versions[*]}{.name}{"="}{.version}{"\n"}{end}'
```

### 4.3 `AVAILABLE`

`AVAILABLE=True` means the operator considers its managed component functional and available.

Expected steady-state:

```text
AVAILABLE=True
```

Problem patterns:

```text
AVAILABLE=False
AVAILABLE=Unknown
```

A false or unknown availability condition means the operator or one of its operands cannot serve its expected platform function.

Examples:

| Operator | Meaning of `AVAILABLE=False` |
|---|---|
| `authentication` | OAuth server or authentication flow may be broken |
| `console` | Web console may be inaccessible |
| `dns` | Cluster DNS may be unhealthy |
| `etcd` | etcd quorum or static pods might be unhealthy |
| `ingress` | Router/default ingress controller may be unavailable |
| `kube-apiserver` | API server rollout or static pod health issue |
| `machine-config` | MCO/MCP/node config rollout issue |
| `network` | CNI/OVN/SDN operator or network operands unhealthy |

### 4.4 `PROGRESSING`

`PROGRESSING=True` means the operator is moving from one steady state to another.

Normal examples:

- Cluster upgrade in progress
- Configuration change being rolled out
- New revision of static pods being deployed
- MachineConfigPool update rolling through nodes
- Router replicas rolling out after ingress configuration change
- OAuth pods restarting after IDP configuration change

Suspicious examples:

- `PROGRESSING=True` for hours with no visible rollout movement
- `PROGRESSING=True` and `DEGRADED=True`
- `PROGRESSING=True` after failed node rollout
- `PROGRESSING=True` with unavailable operands

Typical command:

```bash
oc get co | grep True
```

Better command:

```bash
oc get co -o custom-columns=NAME:.metadata.name,AVAILABLE:.status.conditions[?\(@.type=="Available"\)].status,PROGRESSING:.status.conditions[?\(@.type=="Progressing"\)].status,DEGRADED:.status.conditions[?\(@.type=="Degraded"\)].status,UPGRADEABLE:.status.conditions[?\(@.type=="Upgradeable"\)].status
```

### 4.5 `DEGRADED`

`DEGRADED=True` is the main red flag in `oc get co`.

It means the operator has detected a persistent condition where the current state does not match the required state. It usually requires administrator investigation.

Examples:

| Operator | Common degraded causes |
|---|---|
| `authentication` | Invalid OAuth config, IDP secret issue, OAuth pods unavailable |
| `console` | Console route unavailable, console deployment failing |
| `dns` | DNS daemonset unavailable on nodes, CoreDNS issue |
| `etcd` | etcd member unhealthy, cert issue, disk latency, quorum problem |
| `image-registry` | Storage misconfiguration, PVC/object storage issue, managementState problem |
| `ingress` | Router pods unavailable, LB/DNS issue, default ingress controller degraded |
| `kube-apiserver` | Static pod revision failing, node issue, cert/config issue |
| `machine-config` | Node degraded, MCP degraded, failed ignition/systemd config, drain failure |
| `monitoring` | Prometheus/operator pod failing, PVC issue, config problem |
| `network` | OVN-Kubernetes/SDN daemonset failing, MTU, node network issue |
| `storage` | CSI driver/operator issue, cloud provider integration issue |

### 4.6 `SINCE`

`SINCE` shows how long the displayed condition has been in its current table-relevant state. Treat it as a quick timeline indicator, not a full incident history.

For detailed timing, inspect condition timestamps:

```bash
oc get co network -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.lastTransitionTime}{"\t"}{.reason}{"\n"}{end}'
```

### 4.7 `MESSAGE`

`MESSAGE` is human-readable context from the operator. It is often the most useful part of the table when something is wrong.

Example:

```text
Degraded=True: NodeInstallerDegraded: 1 nodes are failing on revision 15
```

Do not stop at the table message. Always inspect the full object:

```bash
oc describe co kube-apiserver
oc get co kube-apiserver -o yaml
```

The full object often contains longer messages, reasons, versions, and related objects.

## 5. The Four Important Conditions

ClusterOperator status is mostly interpreted through conditions.

### 5.1 Available

```text
Available=True
```

Means the operator is functional and its managed component is available.

Production interpretation:

| Status | Meaning |
|---|---|
| `True` | Component is serving its required function |
| `False` | At least one required part is non-functional |
| `Unknown` | Operator cannot determine current availability |

### 5.2 Progressing

```text
Progressing=False
```

Means the operator is not actively rolling out changes and is in steady state.

Production interpretation:

| Status | Meaning |
|---|---|
| `False` | Stable / no active rollout |
| `True` | Rolling out, upgrading, applying config, changing state |
| `Unknown` | Cannot determine whether rollout is progressing |

`Progressing=True` is not always bad. It becomes bad when it is stuck, combined with degradation, or blocks cluster upgrade completion.

### 5.3 Degraded

```text
Degraded=False
```

Means the operator has not detected persistent unhealthy state.

Production interpretation:

| Status | Meaning |
|---|---|
| `False` | No persistent degraded condition reported |
| `True` | Operator reports a problem requiring investigation |
| `Unknown` | Operator cannot determine degradation state |

### 5.4 Upgradeable

`Upgradeable` is not always displayed in the default `oc get co` output, but it is extremely important before upgrades.

Check it with:

```bash
oc get co -o custom-columns=NAME:.metadata.name,UPGRADEABLE:.status.conditions[?\(@.type=="Upgradeable"\)].status,REASON:.status.conditions[?\(@.type=="Upgradeable"\)].reason,MESSAGE:.status.conditions[?\(@.type=="Upgradeable"\)].message
```

Meaning:

| Status | Meaning |
|---|---|
| `True` | Operator considers update safe |
| `False` | Operator is blocking or warning against update, commonly minor updates |
| `Unknown` | CVO might allow update, but administrator should inspect message |
| Missing | Treated as not blocking in many cases, but still inspect during strict change windows |

Common examples of `Upgradeable=False`:

- Manual configuration unsupported for next minor release
- Deprecated API usage detected
- Platform-specific prerequisite not met
- Cluster capability or operator-specific precondition failing

## 6. Relationship with Cluster Version Operator

The Cluster Version Operator is responsible for managing the lifecycle of many platform operators and for collecting their status into the overall cluster version status.

Important commands:

```bash
oc get clusterversion
oc describe clusterversion version
oc get clusterversion version -o yaml
oc get co
```

Typical upgrade health check:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pods -A | egrep -v 'Running|Completed'
```

During upgrade, CVO watches ClusterOperators. A single degraded or stuck progressing operator can prevent the upgrade from completing.

Example:

```bash
$ oc get clusterversion
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE   STATUS
version   4.14.21   True        True          40m     Working towards 4.14.22: 600 of 800 done

$ oc get co | egrep 'False|True|Unknown'
```

A senior admin does not only check whether `clusterversion` is progressing. They identify the operator causing it:

```bash
oc get co | awk 'NR==1 || $4=="True" || $5=="True" || $3!="True"'
```

## 7. High-Value `oc get co` Command Patterns

### 7.1 Basic Health

```bash
oc get co
```

### 7.2 Watch Operator Status Live

```bash
watch -n 5 'oc get co'
```

Or:

```bash
oc get co -w
```

### 7.3 Show Only Non-Healthy Operators

```bash
oc get co | awk 'NR==1 || $3!="True" || $4!="False" || $5!="False"'
```

### 7.4 Describe a Specific ClusterOperator

```bash
oc describe co network
```

This shows:

- Conditions
- Messages
- Reasons
- Related objects
- Events if present

### 7.5 Show YAML for Full Troubleshooting

```bash
oc get co network -o yaml
```

### 7.6 Extract Conditions Cleanly

```bash
oc get co network -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\t"}{.lastTransitionTime}{"\n"}{.message}{"\n\n"}{end}'
```

### 7.7 List All Degraded Operators with Reason and Message

```bash
oc get co -o json | jq -r '
  .items[]
  | .metadata.name as $name
  | .status.conditions[]
  | select(.type=="Degraded" and .status=="True")
  | "\($name)\tReason=\(.reason)\tMessage=\(.message)"'
```

### 7.8 List Operators Blocking Upgrade

```bash
oc get co -o json | jq -r '
  .items[]
  | .metadata.name as $name
  | .status.conditions[]?
  | select(.type=="Upgradeable" and .status=="False")
  | "\($name)\tReason=\(.reason)\tMessage=\(.message)"'
```

### 7.9 Show Related Objects

```bash
oc get co ingress -o jsonpath='{range .status.relatedObjects[*]}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

This helps find the namespaces and resources you should inspect next.

### 7.10 Show Version Tuples

```bash
oc get co kube-apiserver -o jsonpath='{range .status.versions[*]}{.name}{"\t"}{.version}{"\n"}{end}'
```

### 7.11 Quick Pre-Upgrade Check

```bash
oc get co
oc get co -o json | jq -r '
  .items[]
  | .metadata.name as $name
  | .status.conditions[]?
  | select((.type=="Degraded" and .status=="True") or (.type=="Upgradeable" and .status=="False") or (.type=="Available" and .status!="True"))
  | "\($name)\t\(.type)=\(.status)\t\(.reason)\t\(.message)"'
```

## 8. Reading `oc describe co <name>` Like an L3 Admin

Example:

```bash
oc describe co authentication
```

Focus on these sections:

```text
Status:
  Conditions:
    Last Transition Time:  ...
    Message:               ...
    Reason:                ...
    Status:                True/False/Unknown
    Type:                  Available/Progressing/Degraded/Upgradeable
  Related Objects:
    Group:                 operator.openshift.io
    Name:                  cluster
    Resource:              authentications
    Group:
    Name:                  openshift-authentication-operator
    Resource:              namespaces
  Versions:
    Name:                  operator
    Version:               4.x.y
```

### 8.1 How to Interpret `Reason`

`Reason` is a machine-friendly CamelCase summary.

Examples:

```text
AsExpected
RouteHealth_FailedGet
NodeInstallerDegraded
RolloutHung
StaticPodsDegraded
OAuthServerDeploymentAvailable
InstallerPodPending
```

The exact reason depends on the operator. Always combine reason with message.

### 8.2 How to Interpret `Message`

`Message` is intended for humans. It often tells you exactly where to look next:

```text
OAuthServerRouteEndpointAccessibleControllerAvailable: Get "https://oauth-openshift.apps.example.com/healthz": dial tcp: lookup oauth-openshift.apps.example.com: no such host
```

From this, an experienced admin immediately checks:

```bash
oc get route -n openshift-authentication
oc get svc,endpoints -n openshift-authentication
oc get pods -n openshift-authentication
oc get dns.operator/default -o yaml
oc get ingresscontroller -n openshift-ingress-operator
```

### 8.3 How to Use Related Objects

`relatedObjects` gives the next troubleshooting map.

Example:

```bash
oc get co image-registry -o jsonpath='{range .status.relatedObjects[*]}{.group}{"/"}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

If it shows:

```text
imageregistry.operator.openshift.io/configs        cluster
/namespaces                                       openshift-image-registry
```

Then inspect:

```bash
oc get configs.imageregistry.operator.openshift.io cluster -o yaml
oc get pods -n openshift-image-registry
oc get pvc -n openshift-image-registry
oc get events -n openshift-image-registry --sort-by=.lastTimestamp
```

## 9. Troubleshooting Workflow for `oc get co`

Use this universal workflow.

### Step 1: Identify unhealthy operators

```bash
oc get co
```

Look for:

```text
AVAILABLE != True
PROGRESSING == True for long time
DEGRADED == True
```

### Step 2: Describe the operator

```bash
oc describe co <operator-name>
```

Read:

- `Available`
- `Progressing`
- `Degraded`
- `Upgradeable`
- `Reason`
- `Message`
- `LastTransitionTime`
- `RelatedObjects`

### Step 3: Inspect the full status

```bash
oc get co <operator-name> -o yaml
```

### Step 4: Find the operator namespace

Use `relatedObjects` or common naming:

```bash
oc get co <operator-name> -o jsonpath='{range .status.relatedObjects[*]}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

Then:

```bash
oc get pods -n <operator-namespace>
oc get events -n <operator-namespace> --sort-by=.lastTimestamp
```

### Step 5: Check operands, not only operator pods

Many ClusterOperators can be healthy as pods but degraded because operands are broken.

Examples:

| ClusterOperator | Operator pod namespace | Operand examples |
|---|---|---|
| `ingress` | `openshift-ingress-operator` | router pods in `openshift-ingress` |
| `authentication` | `openshift-authentication-operator` | OAuth pods in `openshift-authentication` |
| `kube-apiserver` | `openshift-kube-apiserver-operator` | static pods on control plane nodes |
| `network` | `openshift-network-operator` | OVN pods in `openshift-ovn-kubernetes` |
| `dns` | `openshift-dns-operator` | DNS daemonset pods in `openshift-dns` |
| `machine-config` | `openshift-machine-config-operator` | MachineConfigPools, nodes, MCD daemonset |

### Step 6: Check cluster-wide dependencies

```bash
oc get nodes
oc get mcp
oc get clusterversion
oc get events -A --sort-by=.lastTimestamp | tail -100
oc get pods -A | egrep -v 'Running|Completed'
```

### Step 7: Pull logs

Operator logs:

```bash
oc logs -n <operator-namespace> deploy/<operator-deployment> --tail=200
```

Pod logs by label:

```bash
oc logs -n <namespace> -l name=<label> --tail=200
```

Previous crashed container logs:

```bash
oc logs -n <namespace> <pod> --previous
```

### Step 8: Collect must-gather for support/escalation

```bash
oc adm must-gather
```

For operator-specific issues, use relevant must-gather images if documented by Red Hat or the operator vendor.

## 10. Common Operator-Specific Investigations

### 10.1 `authentication` Degraded

Start:

```bash
oc get co authentication
oc describe co authentication
```

Common causes:

- Invalid OAuth configuration
- Broken HTPasswd/LDAP/OIDC secret or config map
- OAuth server route inaccessible
- OAuth deployment unavailable
- Ingress/DNS issue affecting OAuth route
- Certificates or trusted CA issues

Commands:

```bash
oc get oauth cluster -o yaml
oc get pods -n openshift-authentication
oc get pods -n openshift-authentication-operator
oc get route -n openshift-authentication
oc get events -n openshift-authentication --sort-by=.lastTimestamp
oc logs -n openshift-authentication-operator deploy/authentication-operator --tail=200
```

If IDP was recently changed:

```bash
oc get secret -n openshift-config
oc get configmap -n openshift-config
oc describe oauth cluster
```

Production advice:

Do not remove `kubeadmin` or the last working admin identity until you verify login with the new identity provider.

---

### 10.2 `ingress` Degraded

Start:

```bash
oc get co ingress
oc describe co ingress
```

Common causes:

- Router pods unavailable
- Default ingress controller degraded
- Load balancer issue
- Wildcard DNS issue
- Certificate issue
- Node placement issue
- Router cannot bind ports or schedule

Commands:

```bash
oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller default -n openshift-ingress-operator
oc get pods -n openshift-ingress
oc get svc -n openshift-ingress
oc get route -A | head
oc get events -n openshift-ingress --sort-by=.lastTimestamp
oc logs -n openshift-ingress-operator deploy/ingress-operator --tail=200
```

Check route reachability:

```bash
curl -k https://console-openshift-console.apps.<cluster-domain>
```

If wildcard DNS is broken, multiple ClusterOperators may show symptoms, especially `console`, `authentication`, and `ingress`.

---

### 10.3 `network` Degraded

Start:

```bash
oc get co network
oc describe co network
```

Common causes:

- OVN-Kubernetes pods failing
- CNI config issue
- MTU mismatch
- Node network interruption
- Missing or unavailable daemonset pods
- Firewall/security group issue
- SDN migration or configuration issue

Commands for OVN-Kubernetes clusters:

```bash
oc get pods -n openshift-network-operator
oc get pods -n openshift-ovn-kubernetes -o wide
oc get daemonset -n openshift-ovn-kubernetes
oc get network.operator cluster -o yaml
oc get network.config cluster -o yaml
oc get events -n openshift-ovn-kubernetes --sort-by=.lastTimestamp
oc logs -n openshift-network-operator deploy/network-operator --tail=200
```

Node-level checks:

```bash
oc get nodes
oc adm node-logs <node> -u kubelet --tail=100
oc debug node/<node>
```

Inside debug shell:

```bash
chroot /host
ip a
ip route
journalctl -u kubelet -n 100 --no-pager
```

---

### 10.4 `machine-config` Degraded

Start:

```bash
oc get co machine-config
oc describe co machine-config
oc get mcp
```

Common causes:

- MachineConfigPool degraded

## 11. Upgrade-Focused Use of `oc get co`

Before any OpenShift upgrade:

```bash
oc get co
oc get clusterversion
oc get mcp
oc get nodes
oc adm upgrade
```

Do not start an upgrade when:

```text
Any ClusterOperator has DEGRADED=True
Any critical ClusterOperator has AVAILABLE=False
Any MachineConfigPool is degraded
Any node is NotReady
Upgradeable=False exists and the message says the target upgrade is blocked
```

During upgrade:

```bash
watch -n 10 'oc get clusterversion; echo; oc get co; echo; oc get mcp'
```

After upgrade:

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pods -A | egrep -v 'Running|Completed'
```

Expected after upgrade completion:

```text
ClusterVersion: AVAILABLE=True, PROGRESSING=False
ClusterOperators: AVAILABLE=True, PROGRESSING=False, DEGRADED=False
MachineConfigPools: UPDATED=True, UPDATING=False, DEGRADED=False
Nodes: Ready
```

### 11.1 When Upgrade Is Stuck

Find problematic operators:

```bash
oc get co | awk 'NR==1 || $3!="True" || $4!="False" || $5!="False"'
```

Describe the stuck one:

```bash
oc describe co <name>
```

Then correlate with:

```bash
oc describe clusterversion version
oc get mcp
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp | tail -100
```

## 12. Incident Patterns and How to Think

### Pattern 1: `AVAILABLE=True`, `PROGRESSING=False`, `DEGRADED=False`

Healthy steady state.

Action:

```text
No issue from ClusterOperator perspective.
```

### Pattern 2: `AVAILABLE=True`, `PROGRESSING=True`, `DEGRADED=False`

Likely rollout or upgrade.

Action:

```bash
oc describe co <name>
oc get clusterversion
```

Wait if it is recent and progressing. Investigate if stuck.

### Pattern 3: `AVAILABLE=True`, `PROGRESSING=True`, `DEGRADED=True`

Rollout attempted but something failed.

Action:

```bash
oc describe co <name>
oc get pods -n <operator/operand-namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### Pattern 4: `AVAILABLE=False`, `PROGRESSING=False`, `DEGRADED=True`

Component is down and not actively recovering.

Action:

```text
Treat as active incident. Inspect reason/message, operator logs, operand pods, related objects, and dependencies.
```

### Pattern 5: `AVAILABLE=False`, `PROGRESSING=True`, `DEGRADED=True`

Component is down during a failed rollout.

Action:

```text
High priority. Check recent changes, upgrade state, node health, static pods, and operator logs.
```

### Pattern 6: `DEGRADED=False` but application users still report problems

Possibilities:

- Issue is outside ClusterOperator responsibility
- App-specific networking/RBAC/storage/config issue
- OLM add-on operator problem
- External DNS/LB/firewall issue
- Operator has not yet detected condition
- Monitoring blind spot or delayed condition transition

Action:

```bash
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp | tail -100
oc get route -A
oc get svc,endpoints -A
```

## 13. Advanced JSONPath and jq Examples

### 13.1 Compact ClusterOperator Health Report

```bash
oc get co -o json | jq -r '
.items[] | {
  name: .metadata.name,
  available: (.status.conditions[]? | select(.type=="Available") | .status),
  progressing: (.status.conditions[]? | select(.type=="Progressing") | .status),
  degraded: (.status.conditions[]? | select(.type=="Degraded") | .status),
  upgradeable: (.status.conditions[]? | select(.type=="Upgradeable") | .status)
} | [.name, .available, .progressing, .degraded, (.upgradeable // "n/a")] | @tsv'
```

### 13.2 Print All Condition Messages for One Operator

```bash
oc get co network -o json | jq -r '
.status.conditions[] | "TYPE=\(.type)\nSTATUS=\(.status)\nREASON=\(.reason)\nTIME=\(.lastTransitionTime)\nMESSAGE=\(.message)\n---"'
```

### 13.3 Find Long-Running Progressing Operators

```bash
oc get co -o json | jq -r '
.items[]
| .metadata.name as $name
| .status.conditions[]?
| select(.type=="Progressing" and .status=="True")
| "\($name)\t\(.lastTransitionTime)\t\(.reason)\t\(.message)"'
```

### 13.4 Print Related Objects for Every Degraded Operator

```bash
for co in $(oc get co -o json | jq -r '.items[] | select(.status.conditions[]? | select(.type=="Degraded" and .status=="True")) | .metadata.name'); do
  echo "### $co"
  oc get co "$co" -o jsonpath='{range .status.relatedObjects[*]}{.group}{"/"}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
  echo
done
```

### 13.5 Pre-Change Gate Script

Use this before upgrades, infra changes, machine config changes, ingress changes, or authentication changes:

```bash
#!/usr/bin/env bash
set -euo pipefail

bad=$(oc get co -o json | jq -r '
.items[]
| .metadata.name as $name
| .status.conditions[]?
| select(
    (.type=="Available" and .status!="True") or
    (.type=="Progressing" and .status=="True") or
    (.type=="Degraded" and .status=="True") or
    (.type=="Upgradeable" and .status=="False")
  )
| "\($name) \(.type)=\(.status) Reason=\(.reason) Message=\(.message)"')

if [[ -n "$bad" ]]; then
  echo "ClusterOperator gate failed:"
  echo "$bad"
  exit 1
fi

echo "ClusterOperator gate passed."
```

## 14. What `oc get co` Does Not Tell You

`oc get co` is powerful, but it is not everything.

It does not directly show:

- Every failing application pod
- Every OLM `Subscription` failure
- Every `CSV` issue
- Every `InstallPlan` issue
- Every node-level kernel/network problem
- Every external load balancer issue
- Every DNS record problem outside the cluster
- Every storage backend outage
- Root cause by itself

It is a starting point. The command tells you **which platform area is reporting a problem**, not always the exact root cause.

For full diagnosis, combine it with:

```bash
oc describe co <name>
oc get clusterversion
oc get mcp
oc get nodes
oc get pods -A
oc get events -A
oc logs
oc adm node-logs
oc adm must-gather
```

## 16. Common Mistakes

### Mistake 1: Troubleshooting ClusterOperators as OLM Subscriptions

Wrong approach:

```bash
oc get sub -A | grep network
oc get csv -A | grep kube-apiserver
```

Correct approach:

```bash
oc describe co network
oc get pods -n openshift-network-operator
oc get pods -n openshift-ovn-kubernetes
```

### Mistake 2: Ignoring `MESSAGE`

Bad habit:

```text
network is degraded. Restart network operator.
```

Better habit:

```text
Read reason/message, related objects, operator logs, operand daemonsets, node status, and recent changes.
```

### Mistake 3: Restarting Operator Pods Blindly

Restarting an operator pod rarely fixes configuration, node, certificate, storage, or external dependency issues. It can hide evidence.

Better:

```bash
oc describe co <name>
oc logs -n <namespace> deploy/<operator> --tail=300
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### Mistake 4: Assuming `Progressing=True` Is Always Bad

During upgrade or rollout, progressing is expected. The question is:

```text
Is it progressing normally, or stuck?
```

Check timestamps, messages, pods, revisions, and rollout movement.

### Mistake 5: Checking Only Operator Pods

The operator pod can be running while its operand is broken.

Example:

```text
ingress-operator pod Running
router pods CrashLoopBackOff
ClusterOperator ingress Degraded=True
```

Always inspect both operator and operand.

## 17. Exam and Interview Perspective

For advanced OpenShift administration, you should be able to explain `oc get co` like this:

> `oc get co` lists ClusterOperator resources, which are cluster-scoped status objects for core OpenShift platform operators. These operators are managed by the Cluster Version Operator, not by OLM Subscriptions or CSVs. The key columns are Available, Progressing, Degraded, Since, and Message. In steady state, I expect Available=True, Progressing=False, and Degraded=False for all operators. During upgrade or config rollout, Progressing=True can be normal, but long-running progressing or any degraded condition requires investigation using `oc describe co`, full YAML conditions, relatedObjects, operator logs, operand pods, events, nodes, MCPs, and clusterversion status.

Interview follow-up answer:

> If an operator is degraded, I first read `oc describe co <operator>` to understand the condition reason and message. Then I use `relatedObjects` to identify relevant namespaces/resources, check operator and operand pods, inspect events and logs, correlate with recent changes, and verify cluster dependencies like nodes, machine config pools, ingress, DNS, storage, and API health. I do not troubleshoot CVO-managed ClusterOperators using OLM objects unless the degraded operator is itself related to OLM, such as marketplace or packageserver.
