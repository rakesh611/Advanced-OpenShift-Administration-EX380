# OperatorGroup in OpenShift Operator Management

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and Kubernetes/OpenShift operators with production experience.  
**Focus:** Practical, deep understanding of `OperatorGroup` in Operator Lifecycle Manager (OLM), including install scoping, RBAC generation, CSV membership, multitenancy, security, troubleshooting, and real-world administration patterns.

---

## 1. Executive Summary

An `OperatorGroup` is an OLM-managed Kubernetes custom resource that defines **where Operators installed in a namespace are allowed to operate** and **where OLM should generate the RBAC needed by those Operators**.

In simple words:

> A `Subscription` says **which Operator package to install**.  
> An `InstallPlan` says **what resources will be created for that install or upgrade**.  
> A `ClusterServiceVersion` says **what the installed Operator needs and provides**.  
> An `OperatorGroup` says **which namespace scope that Operator is allowed to manage**.

For an experienced OpenShift administrator, the most important point is this:

> The namespace where you install an Operator must contain exactly one valid `OperatorGroup`, and the Operator CSV must support the scope selected by that `OperatorGroup`.

If this relationship is wrong, Operator installation can remain pending, the CSV can fail, RBAC might not be created as expected, or OLM can block the installation because of API ownership conflicts.

---

## 2. Why OperatorGroup Exists

OpenShift Operators are not just normal application pods. They extend cluster behavior. Many Operators:

- create CRDs,
- watch custom resources,
- reconcile workload resources,
- create service accounts,
- create roles and role bindings,
- manage operands in one or more namespaces,
- sometimes need cluster-wide permissions.

Without a scoping object, every Operator installation would either need full cluster permissions or custom manual RBAC. That is unsafe and hard to operate at scale.

`OperatorGroup` solves several administration problems:

1. **Namespace scoping**
   - Determines whether an Operator watches only its own namespace, one target namespace, multiple namespaces, or all namespaces.

2. **OLM RBAC generation**
   - OLM uses the `OperatorGroup` target namespaces when creating or copying RBAC objects required by the Operator CSV.

3. **Operator membership**
   - OLM determines which CSVs belong to an `OperatorGroup`.

4. **Multitenant control**
   - Platform admins can create Operator installation namespaces and target scopes for different teams.

5. **API ownership conflict prevention**
   - OLM tracks APIs provided by Operators and prevents conflicting OperatorGroups from managing the same APIs in intersecting namespace scopes.

6. **Delegated Operator installation**
   - With `spec.serviceAccountName`, an admin can restrict Operators installed under an OperatorGroup to the permissions of a pre-approved service account.

## 3. Where OperatorGroup Fits in the OLM Workflow

Typical OLM installation flow:

```text
CatalogSource
     |
     v
PackageManifest
     |
     v
Subscription
     |
     v
InstallPlan
     |
     v
ClusterServiceVersion
     |
     v
Operator Deployment + RBAC + CRDs/API Services
```

`OperatorGroup` is not a package source and does not select the Operator version. It sits beside this flow and controls the namespace scope.

```text
Namespace: my-operator-ns
 ├── OperatorGroup
 ├── Subscription
 ├── InstallPlan
 ├── ClusterServiceVersion
 ├── Operator Deployment
 ├── ServiceAccount
 ├── Role / RoleBinding
 └── Other OLM-created resources
```

OLM checks the `OperatorGroup` in the same namespace where the CSV will be installed. If the namespace has no valid OperatorGroup, or more than one OperatorGroup, OLM cannot correctly determine the Operator scope.

---

## 4. Key Rule: One OperatorGroup Per Installation Namespace

A namespace used for OLM Operator installation should have **exactly one** `OperatorGroup`.

Check all OperatorGroups:

```bash
oc get operatorgroup -A
oc get og -A
```

Check a specific namespace:

```bash
oc get operatorgroup -n <namespace>
oc describe operatorgroup -n <namespace> <operatorgroup-name>
```

If there is more than one OperatorGroup in the same namespace, CSVs in that namespace can fail with:

```text
TooManyOperatorGroups
```

If there is no OperatorGroup, the `InstallPlan` might not generate the CSV and may show messages similar to an invalid OperatorGroup or missing OperatorGroup condition.

Production rule:

> Never create multiple OperatorGroups in the same Operator installation namespace. Treat one namespace as one OperatorGroup scope domain.

## 5. OperatorGroup API Overview

Modern OpenShift 4 uses:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
```

Common fields:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: example-operatorgroup
  namespace: example-operators
spec:
  targetNamespaces:
  - example-app
```

Important `spec` fields:

| Field | Purpose | Admin Notes |
|---|---|---|
| `spec.targetNamespaces` | Explicit list of target namespaces | Most common for single-namespace scoped installs |
| `spec.selector` | Selects target namespaces by namespace labels | Avoid for new designs unless required; multi-namespace selector scoping is not recommended in current docs |
| `spec.serviceAccountName` | Service account used to constrain Operator install permissions | Useful for delegated/non-cluster-admin Operator installation |
| `spec.staticProvidedAPIs` | Tells OLM not to update `olm.providedAPIs` automatically | Advanced conflict-prevention use case |
| `spec.upgradeStrategy` | Controls CSV replacement behavior | Default is safest; fail-forward tech preview is risky |

Important `status` fields:

| Field | Purpose |
|---|---|
| `status.namespaces` | Resolved target namespaces |
| `status.conditions` | OperatorGroup status conditions |
| `status.serviceAccountRef` | Resolved service account reference when `serviceAccountName` is used |
| `status.lastUpdated` | Last status update timestamp |

Important annotations:

| Annotation | Meaning |
|---|---|
| `olm.providedAPIs` | GVKs provided by active member CSVs |
| `olm.operatorGroup` | OperatorGroup name added to member CSVs |
| `olm.operatorNamespace` | OperatorGroup namespace added to member CSVs |
| `olm.targetNamespaces` | Comma-separated target namespace list added to source CSV and projected to Operator deployment |

Older upstream material can show slightly different annotation naming, but when operating OpenShift, inspect your actual CSV YAML from the cluster.

## 6. OperatorGroup Target Namespace Models

An OperatorGroup can target namespaces in three main ways.

### 6.1 Explicit Single Namespace

This is the safest and most common tenant pattern.

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: team-a-og
  namespace: team-a
spec:
  targetNamespaces:
  - team-a
```

Meaning:

- Operator is installed in `team-a`.
- OLM generates RBAC for `team-a`.
- The Operator should watch only `team-a`.
- CSV must support `OwnNamespace` or `SingleNamespace` depending on package metadata and install mode.

Use this for:

- namespace-scoped Operators,
- developer self-service,
- test/dev environments,
- Operators designed to manage resources only inside one project.

### 6.2 Operator Namespace Separate from Target Namespace

This pattern keeps Operator pods and service accounts hidden from tenant namespaces.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-operators
---
apiVersion: v1
kind: Namespace
metadata:
  name: team-a
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: team-a-operatorgroup
  namespace: team-a-operators
spec:
  targetNamespaces:
  - team-a
```

Meaning:

- Operator workload runs in `team-a-operators`.
- Operator watches/manages `team-a`.
- Tenant users might see copied CSV information in `team-a`, but not necessarily the Operator pod itself.

Use this for stronger separation:

- tenant cannot manage Operator deployment,
- platform team owns Operator lifecycle,
- tenant only creates custom resources in their project.

### 6.3 Global OperatorGroup

A global OperatorGroup targets all namespaces by omitting both `spec.targetNamespaces` and `spec.selector`.

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-operatorgroup
  namespace: global-operators
```

Meaning:

- `status.namespaces` contains an empty string `""`.
- The consuming Operator interprets this as all namespaces.
- CSV must support `AllNamespaces`.

OpenShift has a default global Operator namespace:

```text
openshift-operators
```

For many all-namespace Operator installs through the console, OpenShift installs the Operator in `openshift-operators`.

Production recommendation:

> Avoid putting every global Operator into the default `openshift-operators` namespace if you need strict lifecycle separation. Use custom global Operator namespaces for groups of Operators that should share install plans and update policies.

### 6.4 Label Selector Based OperatorGroup

Example:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: prod-selector-og
  namespace: prod-operators
spec:
  selector:
    matchLabels:
      environment: prod
```

Meaning:

- OLM resolves namespaces with label `environment=prod`.
- Those namespaces become the target set.

Important production warning:

> Current OpenShift documentation warns that listing multiple namespaces in `spec.targetNamespaces` or using `spec.selector` is not recommended, because support for more than one target namespace in an OperatorGroup is likely to be removed in a future release.

Use selectors only when you fully understand Operator support and product lifecycle implications.

## 7. InstallModes: The CSV Must Support the OperatorGroup Scope

Every OLM Operator package has CSV metadata. The CSV declares which install modes it supports.

Install modes:

| InstallModeType | Meaning |
|---|---|
| `OwnNamespace` | Operator can manage the namespace where it is installed |
| `SingleNamespace` | Operator can manage one namespace |
| `MultiNamespace` | Operator can manage more than one namespace |
| `AllNamespaces` | Operator can manage all namespaces |

Relationship between OperatorGroup and CSV:

```text
OperatorGroup target namespace set
        +
CSV installModes support
        =
CSV can become active member of OperatorGroup
```

If unsupported, the CSV can fail with:

```text
UnsupportedOperatorGroup
```

Example scenario:

```text
Operator supports only AllNamespaces
OperatorGroup targets only team-a
Result: CSV fails with UnsupportedOperatorGroup
```

Another scenario:

```text
Operator supports only SingleNamespace
OperatorGroup is global
Result: CSV fails with UnsupportedOperatorGroup
```

Check package install modes before installing:

```bash
oc get packagemanifest <operator-package-name> \
  -n openshift-marketplace \
  -o yaml
```

Filter relevant sections:

```bash
oc get packagemanifest <operator-package-name> \
  -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{"CHANNEL: "}{.name}{"\n"}{range .currentCSVDesc.installModes[*]}{.type}{": "}{.supported}{"\n"}{end}{"\n"}{end}'
```

Check the installed CSV:

```bash
oc get csv -n <operator-namespace>
oc get csv -n <operator-namespace> <csv-name> -o yaml
```

Look for:

```yaml
spec:
  installModes:
  - type: OwnNamespace
    supported: true
  - type: SingleNamespace
    supported: true
  - type: MultiNamespace
    supported: false
  - type: AllNamespaces
    supported: false
```

## 8. CSV Membership

A CSV is a member of an OperatorGroup when:

1. the CSV exists in the same namespace as the OperatorGroup, and
2. the CSV install modes support the OperatorGroup target namespace set.

Example:

```text
Namespace: elastic-operators
  OperatorGroup: elastic-og
  CSV: elasticsearch-operator.vX.Y.Z
```

If the CSV supports the scope of `elastic-og`, it becomes an active member.

Once the CSV becomes a member:

- OLM annotates it with OperatorGroup metadata,
- OLM generates/copies RBAC according to target namespaces,
- OLM can create copied CSVs in target namespaces,
- OLM updates `olm.providedAPIs` on the OperatorGroup,
- OLM checks API conflicts with other OperatorGroups.

Inspect annotations:

```bash
oc get csv -n <operator-namespace> <csv-name> -o yaml | grep -A20 annotations:
```

Useful JSONPath:

```bash
oc get csv -n <operator-namespace> <csv-name> \
  -o jsonpath='{.metadata.annotations.olm\.operatorGroup}{"\n"}{.metadata.annotations.olm\.targetNamespaces}{"\n"}'
```

## 9. The `olm.targetNamespaces` Annotation

OLM writes target namespace information to member CSVs using `olm.targetNamespaces`.

Example annotation:

```yaml
metadata:
  annotations:
    olm.operatorGroup: team-a-og
    olm.operatorNamespace: team-a
    olm.targetNamespaces: team-a
```

For a global OperatorGroup, the target namespace signal is effectively empty string `""`.

Why this matters:

- The Operator container can consume this value through the Downward API.
- Many Operators use this value to configure `WATCH_NAMESPACE`.
- If the Operator implementation does not correctly handle this value, it can watch the wrong scope or fail.

Common Operator deployment pattern:

```yaml
env:
- name: WATCH_NAMESPACE
  valueFrom:
    fieldRef:
      fieldPath: metadata.annotations['olm.targetNamespaces']
```

As an admin, if the Operator is not watching the expected namespace, inspect:

```bash
oc get csv -n <operator-namespace> <csv-name> -o yaml
oc get deployment -n <operator-namespace>
oc get deployment -n <operator-namespace> <operator-deployment> -o yaml | grep -A20 WATCH_NAMESPACE
```

## 10. Copied CSVs

When an OperatorGroup targets namespaces, OLM can create copied CSVs in those namespaces.

Purpose:

> A copied CSV tells users in a target namespace that an Operator is available and watching resources created there.

Example:

```bash
oc get csv -A | grep <operator-name>
```

You might see:

```text
openshift-operators   my-operator.v1.2.3   Succeeded
team-a                my-operator.v1.2.3   Copied
team-b                my-operator.v1.2.3   Copied
```

Important points:

- The real/source CSV is in the Operator installation namespace.
- Copied CSVs have reason/status like `Copied`.
- Copied CSVs are not the actual installation owner.
- `olm.targetNamespaces` is stripped from copied CSVs to avoid leaking target scope details between tenants.
- Copied CSVs are deleted when the source CSV is removed or when the OperatorGroup no longer targets that namespace.

Disable copied CSVs cluster-wide:

```yaml
apiVersion: operators.coreos.com/v1
kind: OLMConfig
metadata:
  name: cluster
spec:
  features:
    disableCopiedCSVs: true
```

Re-enable:

```yaml
apiVersion: operators.coreos.com/v1
kind: OLMConfig
metadata:
  name: cluster
spec:
  features:
    disableCopiedCSVs: false
```

Operational note:

> Do not troubleshoot copied CSVs as if they are independent Operator installs. Always find the source CSV and source OperatorGroup.

## 11. RBAC Deep Dive

### 11.1 What OLM Does with RBAC

When a CSV becomes an active member of an OperatorGroup, OLM reads the CSV permission requirements and creates the needed RBAC.

The CSV can declare:

```yaml
spec:
  install:
    spec:
      permissions:
      - serviceAccountName: my-operator
        rules:
        - apiGroups: [""]
          resources: ["pods"]
          verbs: ["get", "list", "watch"]
      clusterPermissions:
      - serviceAccountName: my-operator
        rules:
        - apiGroups: ["example.com"]
          resources: ["widgets"]
          verbs: ["*"]
```

OLM uses OperatorGroup scope to decide where namespaced RBAC should exist.

### 11.2 Generated OperatorGroup ClusterRoles

When an OperatorGroup is created, OLM creates aggregate cluster roles with names similar to:

```text
olm.og.<operatorgroup-name>-admin-<hash>
olm.og.<operatorgroup-name>-edit-<hash>
olm.og.<operatorgroup-name>-view-<hash>
```

Find them:

```bash
oc get clusterroles | grep <operatorgroup-name>
```

These roles use labels for aggregation. Typical labels include:

```text
olm.opgroup.permissions/aggregate-to-admin: <operatorgroup-name>
olm.opgroup.permissions/aggregate-to-edit: <operatorgroup-name>
olm.opgroup.permissions/aggregate-to-view: <operatorgroup-name>
```

### 11.3 CRD/API Resource RBAC Aggregation

For APIs provided by the Operator, OLM can generate admin/edit/view style cluster roles for the custom resources, for example:

```text
<kind>.<group>-<version>-admin
<kind>.<group>-<version>-edit
<kind>.<group>-<version>-view
```

Expected verbs:

| Role Type | Common Verbs |
|---|---|
| admin | `*` |
| edit | `create`, `update`, `patch`, `delete` |
| view | `get`, `list`, `watch` |

This is why developers with namespace roles can often interact with Operator custom resources after the Operator is installed.

### 11.4 Service Account Boundaries

`spec.serviceAccountName` on an OperatorGroup lets an admin restrict Operator installation/upgrade privileges.

Example:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: restricted-og
  namespace: tenant-operators
spec:
  serviceAccountName: operator-installer
  targetNamespaces:
  - tenant-a
```

Meaning:

- OLM attempts to install/upgrade member Operators using the permission boundary of `operator-installer`.
- If the Operator asks for permissions outside that service account's RBAC, installation fails.
- This helps prevent user privilege escalation through Operator installation.

Create a restricted service account pattern:

```bash
oc new-project tenant-operators
oc create serviceaccount operator-installer -n tenant-operators
```

Grant limited permissions, for example:

```bash
oc adm policy add-role-to-user admin \
  system:serviceaccount:tenant-operators:operator-installer \
  -n tenant-a
```

Then create OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: tenant-a-og
  namespace: tenant-operators
spec:
  serviceAccountName: operator-installer
  targetNamespaces:
  - tenant-a
```

Important security note:

> CRDs and APIServices are cluster-scoped API extension resources. OLM still handles some extension resources with high privileges. Do not blindly allow non-admins to install arbitrary Operators. Audit the Operator CSV and InstallPlan.

## 12. `olm.providedAPIs` and API Ownership

`OperatorGroup` uses the `olm.providedAPIs` annotation to track which APIs are provided by active member CSVs.

Example:

```yaml
metadata:
  annotations:
    olm.providedAPIs: Widget.v1.example.com,Gadget.v1.example.com
```

Format:

```text
<Kind>.<version>.<group>
```

Example:

```text
Prometheus.v1.monitoring.coreos.com
Alertmanager.v1.monitoring.coreos.com
```

OLM uses this to detect conflicts.

Two OperatorGroups conflict when:

1. their target namespace sets intersect, and
2. their provided API sets intersect.

Example conflict:

```text
OperatorGroup A targets namespace team-a and provides Widget.v1.example.com
OperatorGroup B targets namespace team-a and provides Widget.v1.example.com
Result: InterOperatorGroupOwnerConflict risk
```

Reason:

> Two Operators would compete to own/reconcile the same API in the same namespace.

Common failure reason:

```text
InterOperatorGroupOwnerConflict
```

Troubleshooting:

```bash
oc get operatorgroup -A -o yaml | grep -B5 -A10 olm.providedAPIs
oc get csv -A | grep -i failed
oc describe csv -n <namespace> <csv-name>
```

## 13. Static OperatorGroups

A static OperatorGroup is created with:

```yaml
spec:
  staticProvidedAPIs: true
```

Example:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: monitoring-api-guard
  namespace: monitoring-operators
  annotations:
    olm.providedAPIs: Prometheus.v1.monitoring.coreos.com,ServiceMonitor.v1.monitoring.coreos.com
spec:
  staticProvidedAPIs: true
  targetNamespaces:
  - monitoring
```

Meaning:

- OLM does not modify `olm.providedAPIs`.
- Admin pre-declares APIs that this OperatorGroup protects.
- Useful when preventing resource contention before active CSVs exist.

Failure to watch for:

```text
CannotModifyStaticOperatorGroupProvidedAPIs
```

Use static OperatorGroups only when you understand API ownership and conflict behavior.

## 14. `upgradeStrategy`

The OperatorGroup API includes `spec.upgradeStrategy`.

Supported values include:

```text
Default
TechPreviewUnsafeFailForward
```

### 14.1 Default

Default strategy is safest. OLM normally proceeds from a healthy/succeeded CSV state to replacement.

### 14.2 TechPreviewUnsafeFailForward

This allows OLM to move forward from some failed states when a newer catalog update becomes available.

Warning:

> This is unsafe and can cause unexpected behavior or unrecoverable data loss if used without deep understanding of the Operators managed in that namespace.

Production guidance:

- Keep default unless Red Hat support or vendor guidance specifically directs otherwise.
- Never enable fail-forward casually on critical stateful Operators.
- Test in non-production first.

Example only:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: risky-fail-forward-og
  namespace: test-operators
spec:
  targetNamespaces:
  - test
  upgradeStrategy: TechPreviewUnsafeFailForward
```

## 15. Common Installation Patterns

### Pattern 1: Default All-Namespace Install

Used by many console installs.

```text
Operator namespace: openshift-operators
OperatorGroup: global-operators
Scope: all namespaces
```

Check:

```bash
oc get og -n openshift-operators
oc get csv -n openshift-operators
```

Pros:

- easy,
- console-friendly,
- good for cluster-level Operators.

Cons:

- many Operators share namespace,
- shared install plans/update behavior can become confusing,
- less lifecycle isolation.

Use for:

- cluster-wide Operators,
- simple labs,
- Operators designed for global scope.

### Pattern 2: Custom Global Operator Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: storage-operators
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: storage-global-og
  namespace: storage-operators
```

Pros:

- global scope,
- better lifecycle separation than `openshift-operators`,
- useful for grouping dependencies.

Use for:

- ODF-related Operators,
- monitoring/security platform Operators,
- platform-owned global services.

### Pattern 3: Single Namespace Tenant Install

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: team-a-og
  namespace: team-a
spec:
  targetNamespaces:
  - team-a
```

Pros:

- simple,
- good for namespace-scoped Operators,
- suitable for delegated application teams.

Cons:

- Operator pod lives in same namespace,
- tenant admins might have more visibility/control.

### Pattern 4: Separate Operator Namespace and Tenant Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-operators
---
apiVersion: v1
kind: Namespace
metadata:
  name: team-a
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: team-a-og
  namespace: team-a-operators
spec:
  targetNamespaces:
  - team-a
```

Pros:

- cleaner separation,
- Operator lifecycle owned by platform team,
- tenant only consumes custom resources.

Cons:

- more objects to manage,
- must ensure Operator supports SingleNamespace not only OwnNamespace.

### Pattern 5: Restricted Delegated Install

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: restricted-team-a-og
  namespace: team-a-operators
spec:
  serviceAccountName: operator-installer
  targetNamespaces:
  - team-a
```

Pros:

- prevents privilege escalation,
- allows controlled self-service,
- good for regulated environments.

Cons:

- requires careful RBAC design,
- many Operator installs fail until permissions are tuned.

## 16. Complete CLI Example: Install a Single-Namespace Operator

This is a generic workflow. Replace package/channel/catalog names with your Operator details.

### 16.1 Inspect available Operator

```bash
oc get packagemanifests -n openshift-marketplace | grep -i <operator>
```

Inspect install modes:

```bash
oc get packagemanifest <operator-package> \
  -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{"CHANNEL: "}{.name}{"\n"}{range .currentCSVDesc.installModes[*]}{.type}{": "}{.supported}{"\n"}{end}{"\n"}{end}'
```

### 16.2 Create namespace

```bash
oc new-project app-operators
```

### 16.3 Create OperatorGroup

```bash
cat <<'EOF' | oc apply -f -
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: app-operators-og
  namespace: app-operators
spec:
  targetNamespaces:
  - app-operators
EOF
```

### 16.4 Create Subscription

```bash
cat <<'EOF' | oc apply -f -
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: app-operators
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
EOF
```

### 16.5 Review InstallPlan

```bash
oc get installplan -n app-operators
oc describe installplan -n app-operators <installplan-name>
```

Approve if manual:

```bash
oc patch installplan <installplan-name> \
  -n app-operators \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 16.6 Verify CSV

```bash
oc get csv -n app-operators
oc describe csv -n app-operators <csv-name>
```

Expected:

```text
Phase: Succeeded
```

### 16.7 Verify OperatorGroup status

```bash
oc get operatorgroup app-operators-og \
  -n app-operators \
  -o yaml
```

Look for:

```yaml
status:
  namespaces:
  - app-operators
```

### 18.1 Daily Health Checks

```bash
oc get og -A
oc get csv -A
oc get subscription -A
oc get installplan -A
```

Find failed CSVs:

```bash
oc get csv -A | egrep -i 'failed|pending|replacing'
```

Find OperatorGroup conflicts:

```bash
oc get csv -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,PHASE:.status.phase,REASON:.status.reason
```

### 18.2 Inspect OperatorGroup Scope

```bash
oc get og -n <operator-namespace> <og-name> -o yaml
```

Key checks:

```bash
oc get og -n <operator-namespace> <og-name> \
  -o jsonpath='{.spec.targetNamespaces}{"\n"}{.spec.selector}{"\n"}{.status.namespaces}{"\n"}'
```

### 18.3 Inspect CSV Annotations

```bash
oc get csv -n <operator-namespace> <csv-name> \
  -o jsonpath='{.metadata.annotations.olm\.operatorGroup}{"\n"}{.metadata.annotations.olm\.targetNamespaces}{"\n"}{.status.phase}{"\n"}{.status.reason}{"\n"}'
```

### 18.4 Inspect Generated RBAC

```bash
oc get clusterroles | grep <operatorgroup-name>
oc get role,rolebinding -n <target-namespace> | grep <operator-or-csv-name>
oc get clusterrole,clusterrolebinding | grep <operator-or-csv-name>
```

### 18.5 Inspect InstallPlan Permission Changes

```bash
oc describe installplan -n <operator-namespace> <installplan-name>
oc get installplan -n <operator-namespace> <installplan-name> -o yaml
```

For production upgrades, especially with manual approval:

- check requested ClusterRoles,
- check new CRDs,
- check service account changes,
- check webhook/APIService changes,
- check vendor release notes.

## 19. Troubleshooting Runbooks

### Problem 1: CSV Fails with `TooManyOperatorGroups`

Symptoms:

```bash
oc get csv -n <ns>
```

Shows failed CSV.

```bash
oc describe csv -n <ns> <csv>
```

Reason:

```text
TooManyOperatorGroups
```

Cause:

- More than one OperatorGroup exists in the CSV namespace.

Verify:

```bash
oc get operatorgroup -n <ns>
```

Fix:

1. Decide the correct OperatorGroup.
2. Delete the extra OperatorGroup.
3. Watch CSV recover.

```bash
oc delete operatorgroup <wrong-og> -n <ns>
oc get csv -n <ns> -w
```

Production caution:

> Do not randomly delete OperatorGroups in namespaces with production Operators. Check target scope and provided APIs first.

---

### Problem 2: CSV Fails with `UnsupportedOperatorGroup`

Symptoms:

```text
CSV phase: Failed
Reason: UnsupportedOperatorGroup
```

Cause:

- Operator CSV install modes do not support the OperatorGroup target namespace set.

Example:

```text
CSV supports SingleNamespace only.
OperatorGroup is global.
```

Verify OperatorGroup:

```bash
oc get og -n <ns> -o yaml
```

Verify CSV install modes:

```bash
oc get csv -n <ns> <csv> -o yaml | grep -A20 installModes
```

Fix options:

- Change OperatorGroup scope to match supported install mode.
- Install the Operator in a different namespace with correct OperatorGroup.
- Choose a different Operator version/channel that supports required scope.
- Use console install mode supported by the Operator.

---

### Problem 3: InstallPlan Does Not Create CSV

Symptoms:

```bash
oc get installplan -n <ns>
oc describe installplan -n <ns> <installplan>
```

Messages may indicate invalid OperatorGroup.

Common causes:

- no OperatorGroup in namespace,
- multiple OperatorGroups,
- wrong/nonexistent `spec.serviceAccountName`,
- service account lacks required permissions.

Verify:

```bash
oc get og -n <ns>
oc get sa -n <ns>
oc describe installplan -n <ns> <installplan>
```

Fix:

```bash
oc apply -f operatorgroup.yaml
oc create sa <service-account> -n <ns>
```

Then re-check:

```bash
oc get installplan -n <ns> -w
```

---

### Problem 4: CSV Fails with `InterOperatorGroupOwnerConflict`

Symptoms:

```text
Reason: InterOperatorGroupOwnerConflict
```

Cause:

- Two OperatorGroups have overlapping target namespaces and provide overlapping APIs.

Verify provided APIs:

```bash
oc get og -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{" -> "}{.metadata.annotations.olm\.providedAPIs}{" targets="}{.status.namespaces}{"\n"}{end}'
```

Fix options:

- Remove duplicate Operator install.
- Change target namespace scope so OperatorGroups do not intersect.
- Use only one owner for that API in that namespace.
- Uninstall conflicting Operator cleanly.

---

### Problem 5: Operator Shows `Copied` in Namespace

Symptoms:

```bash
oc get csv -n team-a
```

Shows:

```text
my-operator.v1.2.3   Copied
```

Meaning:

- Operator is installed somewhere else.
- It is available to `team-a`.
- The source CSV is in the Operator installation namespace.

Find source:

```bash
oc get csv -A | grep my-operator
```

Look for `Succeeded`, not `Copied`.

---

### Problem 6: Tenant User Cannot Install Operator

Symptoms:

- User can create `Subscription` but install does not progress.
- User has `edit` or `admin` in namespace but cannot create OperatorGroup.

Explanation:

- OpenShift grants RBAC for `Subscription` to namespace `edit`/`admin` users.
- RBAC is not automatically granted for `OperatorGroup`.
- This prevents ordinary users from escalating privileges by creating an arbitrary OperatorGroup.

Admin fix:

- Pre-create an OperatorGroup.
- Optionally bind it to a restricted service account.
- Allow user to create Subscriptions only within that boundary.

---

### Problem 7: Operator Watches Wrong Namespace

Checks:

```bash
oc get og -n <operator-ns> -o yaml
oc get csv -n <operator-ns> <csv> -o yaml | grep -A10 olm.targetNamespaces
oc get deployment -n <operator-ns> <deployment> -o yaml | grep -A20 WATCH_NAMESPACE
```

Possible causes:

- Wrong OperatorGroup `targetNamespaces`.
- Operator does not consume `olm.targetNamespaces`.
- Operator has hardcoded watch namespace.
- Operator image bug.
- Operator installed with wrong install mode.

Fix:

- Correct OperatorGroup and reinstall if needed.
- Check vendor documentation for supported install modes.
- Verify deployment environment variables.
- Avoid modifying generated deployment directly; OLM may reconcile it back.

---

### Problem 8: OperatorGroup Uses Selector but Namespace Not Targeted

Verify namespace labels:

```bash
oc get ns --show-labels
```

Verify OperatorGroup selector:

```bash
oc get og -n <operator-ns> <og-name> -o yaml
```

Check status:

```bash
oc get og -n <operator-ns> <og-name> -o jsonpath='{.status.namespaces}{"\n"}'
```

Fix:

```bash
oc label namespace <target-ns> environment=prod
```

Caution:

> Selector-based multi-namespace scoping is not recommended for new production designs because future support is uncertain.

## 20. OperatorGroup and Multitenancy

OpenShift multitenancy is not just namespace separation. Operators complicate tenancy because CRDs are cluster-scoped.

Important constraints:

1. **CRDs are global**
   - Two tenants cannot safely run incompatible versions of the same CRD.

2. **API ownership matters**
   - OLM prevents two OperatorGroups from managing the same API in intersecting namespaces.

3. **Operator pods may run outside tenant namespace**
   - This can be good for separation, but must be documented.

4. **Copied CSVs are only visibility markers**
   - They are not separate Operator installations.

5. **Different versions of same Operator can be limited**
   - Same Operator family with incompatible APIs cannot always be installed in parallel.

Production multitenancy design:

```text
Cluster
 ├── Platform global Operators
 │    └── custom global namespaces
 ├── Tenant A
 │    ├── team-a
 │    └── team-a-operators
 ├── Tenant B
 │    ├── team-b
 │    └── team-b-operators
 └── Shared services
      └── platform-owned Operators
```

Recommended:

- one Operator installation namespace per tenant or per Operator group,
- one OperatorGroup per install namespace,
- avoid multi-namespace target lists,
- avoid selector OperatorGroups unless strongly justified,
- pre-approve Operators and channels,
- use manual install plan approval,
- inspect RBAC changes during upgrades.

## 21. Security Best Practices

### 21.1 Do Not Treat Operators Like Normal Apps

Operators can:

- create workloads,
- modify secrets/configmaps,
- manage networking,
- create webhooks,
- install CRDs,
- affect many namespaces.

Always inspect the CSV and InstallPlan.

```bash
oc get csv -n <ns> <csv> -o yaml
oc get installplan -n <ns> <installplan> -o yaml
```

### 21.2 Use Manual Approval for Sensitive Operators

```yaml
spec:
  installPlanApproval: Manual
```

Why:

- permission changes become reviewable,
- cluster-scoped changes are visible,
- upgrades do not surprise production.

### 21.3 Use `serviceAccountName` for Delegated Installs

```yaml
spec:
  serviceAccountName: restricted-installer
```

This helps prevent users from using OLM as a privilege escalation path.

### 21.4 Separate Global Operators

Instead of putting all global Operators in `openshift-operators`, create custom global namespaces:

```text
monitoring-operators
storage-operators
security-operators
platform-operators
```

Benefits:

- easier troubleshooting,
- clearer ownership,
- less shared update-plan coupling,
- safer lifecycle control.

### 21.5 Avoid Scope Changes Without Impact Analysis

Changing `targetNamespaces` affects:

- RBAC generation,
- copied CSVs,
- watched namespaces,
- API conflicts,
- tenant visibility.

Before changing:

```bash
oc get og -n <ns> <og> -o yaml > before-og.yaml
oc get csv -n <ns> -o yaml > before-csv.yaml
oc get role,rolebinding -A | grep <operator-name>
```

## 22. Production Design Recommendations

For a 10-year-experience OpenShift administrator, the reliable design is usually:

### 22.1 For Cluster-Level Operators

Use either:

```text
openshift-operators
```

or custom global namespace:

```text
<domain>-operators
```

Example:

```text
storage-operators
security-operators
monitoring-operators
```

Use a global OperatorGroup by omitting `targetNamespaces` and `selector`.

### 22.2 For Tenant-Level Operators

Use:

```text
<tenant>-operators
```

as install namespace and:

```text
<tenant>
```

as target namespace.

Example:

```yaml
spec:
  targetNamespaces:
  - team-a
```

### 22.3 For Dev/Test Labs

Single namespace install is acceptable:

```yaml
metadata:
  namespace: dev
spec:
  targetNamespaces:
  - dev
```

### 22.4 For Self-Service

Pre-create:

- namespace,
- OperatorGroup,
- constrained service account,
- approved CatalogSource access,
- RBAC for Subscription only,
- manual approval workflow.

### 22.5 Avoid

- multiple OperatorGroups in one namespace,
- unrelated global Operators sharing lifecycle in one namespace,
- selectors for broad tenant selection,
- multi-target OperatorGroups unless vendor explicitly supports it,
- blindly approving InstallPlans,
- editing OLM-owned deployments manually.

## 23. OperatorGroup vs Related OLM Resources

| Resource | Scope | Main Purpose |
|---|---|---|
| `CatalogSource` | Namespace | Provides Operator catalog/index data |
| `PackageManifest` | Namespace/API view | Shows available packages/channels |
| `Subscription` | Namespace | Requests an Operator package/channel |
| `InstallPlan` | Namespace | Lists resources OLM will create/update |
| `ClusterServiceVersion` | Namespace | Installed Operator metadata and lifecycle state |
| `OperatorGroup` | Namespace with target scope | Defines namespace scope and RBAC boundary |
| `OperatorCondition` | Namespace | Lets Operator communicate condition/upgrade state to OLM |

Mental shortcut:

```text
CatalogSource = where Operator comes from
Subscription = what Operator you want
InstallPlan = what will be installed
CSV = what is installed
OperatorGroup = where it is allowed to operate
```

## 24. Exam and Interview Focus Points

You should be able to answer these quickly.

### Q1. What is an OperatorGroup?

An OLM resource that defines the target namespace scope for Operators installed in its namespace and allows OLM to generate required RBAC for those member Operators.

### Q2. How many OperatorGroups should exist in an Operator installation namespace?

Exactly one.

### Q3. What happens if there are two OperatorGroups in one namespace?

CSV can fail with `TooManyOperatorGroups`.

### Q4. What happens if the Operator does not support the OperatorGroup scope?

CSV can fail with `UnsupportedOperatorGroup`.

### Q5. How do you create a global OperatorGroup?

Omit both `spec.targetNamespaces` and `spec.selector`.

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-og
  namespace: global-operators
```

### Q6. What is `olm.targetNamespaces`?

A CSV annotation containing the OperatorGroup target namespace selection. It is commonly projected to Operator pods so the Operator knows what namespace(s) to watch.

### Q7. What is a copied CSV?

A CSV copy placed in a target namespace to show that an Operator installed elsewhere is available there.

### Q8. Why can two OperatorGroups conflict?

Because their target namespace sets and provided API sets intersect, causing possible competing ownership of the same API in the same namespace.

### Q9. What field restricts Operator install permissions?

```yaml
spec:
  serviceAccountName: <service-account>
```

### Q10. Why is multi-namespace target scoping risky?

Current OpenShift documentation warns that multiple target namespaces or selector-based scoping is not recommended because support for more than one target namespace is likely to be removed in a future release.

## 26. Golden Rules

1. **One OperatorGroup per Operator installation namespace.**
2. **Match OperatorGroup scope with CSV installModes.**
3. **Use global OperatorGroup only for Operators that support `AllNamespaces`.**
4. **Use single target namespace for most tenant-scoped Operators.**
5. **Avoid multi-namespace target lists and selectors for new production designs.**
6. **Do not treat copied CSVs as real installations.**
7. **Review InstallPlans before approving production upgrades.**
8. **Use `serviceAccountName` for delegated Operator installation.**
9. **Avoid dumping all global Operators into `openshift-operators` if lifecycle isolation matters.**
10. **Troubleshoot from OperatorGroup → InstallPlan → CSV → Deployment/RBAC.**

## 28. Final Mental Model

Think of `OperatorGroup` as the **scope contract** between the cluster administrator, OLM, and the Operator.

```text
OperatorGroup = "This installation namespace may run Operators that manage this target namespace set, with this permission boundary."
```

If the contract matches the CSV, OLM installs and manages the Operator cleanly.

If the contract does not match, OLM protects the cluster by blocking or failing the CSV.

For advanced OpenShift administration, mastering `OperatorGroup` means mastering the boundary between:

- platform control and tenant self-service,
- global Operators and namespace Operators,
- Operator installation and Operator consumption,
- RBAC generation and privilege escalation prevention,
- safe multitenancy and API ownership conflicts.
