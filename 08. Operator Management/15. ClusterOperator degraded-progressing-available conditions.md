# ClusterOperator `Degraded`, `Progressing`, and `Available` Conditions

**Area:** Operator Management  
**Level:** Advanced OpenShift Administration / 10+ years production operations  
**Focus:** How to read, interpret, troubleshoot, and operationalize `ClusterOperator` conditions in OpenShift Container Platform 4.x

---

## 1. Why ClusterOperator conditions matter

In OpenShift 4, platform components are not managed as static services that an administrator manually installs and patches one by one. They are managed by **cluster Operators**. These Operators own major parts of the control plane and platform foundation: API servers, authentication, console, ingress, DNS, network, machine configuration, monitoring, image registry, storage-related components, and more.

The resource that exposes the health and rollout state of those platform Operators is:

```bash
oc get clusteroperators
oc get co
```

A `ClusterOperator` is a `config.openshift.io/v1` resource that holds the status of a core or optional OpenShift component managed by the **Cluster Version Operator (CVO)**. Each cluster Operator uses this object to publish its state to the rest of the cluster.

The three conditions administrators check most often are:

```text
Available
Progressing
Degraded
```

The normal steady-state target is:

```text
Available=True
Progressing=False
Degraded=False
```

That does **not** mean every platform pod has never restarted, every operand is perfect, or every future update is safe. It means the operator is currently reporting that its managed component is available, not rolling out toward a new state, and not persistently failing to match its required state.

---

## 2. ClusterOperator is not the same as an OLM Operator

This distinction is very important in interviews, EX280/DO380-style troubleshooting, and production incidents.

### 2.1 ClusterOperator

A `ClusterOperator` represents an OpenShift platform component managed by the CVO.

Examples:

```bash
oc get co authentication
oc get co console
oc get co ingress
oc get co network
oc get co kube-apiserver
oc get co machine-config
oc get co monitoring
```

These operators are part of the OpenShift release payload and participate in OpenShift cluster upgrades.

### 2.2 OLM-managed Operator

An OLM-managed Operator is installed through OperatorHub / Subscription / InstallPlan / CSV.

Examples:

```bash
oc get sub -A
oc get installplan -A
oc get csv -A
```

Examples of add-on Operators:

- OpenShift GitOps Operator
- OpenShift Pipelines Operator
- OpenShift Logging Operator
- cert-manager Operator for Red Hat OpenShift
- File Integrity Operator
- Local Storage Operator

These might expose their own CR status conditions, CSV phase, deployment health, and sometimes an `OperatorCondition`, but they are not the same object as `ClusterOperator`.

### 2.3 Practical rule

Use this split:

```text
Platform component health       -> oc get co
OLM add-on installation health  -> oc get csv, sub, installplan, catalogsource
Application/operator workload   -> pods, deployments, CR status, events, logs
```

## 3. Object anatomy of a ClusterOperator

Inspect one operator in YAML:

```bash
oc get co authentication -o yaml
```

Important fields:

```yaml
apiVersion: config.openshift.io/v1
kind: ClusterOperator
metadata:
  name: authentication
status:
  conditions:
  - type: Available
    status: "True"
    lastTransitionTime: "..."
    reason: AsExpected
    message: All is well
  - type: Progressing
    status: "False"
    lastTransitionTime: "..."
    reason: AsExpected
    message: All is well
  - type: Degraded
    status: "False"
    lastTransitionTime: "..."
    reason: AsExpected
    message: All is well
  - type: Upgradeable
    status: "True"
    reason: AsExpected
    message: All is well
  versions:
  - name: operator
    version: 4.x.y
  relatedObjects:
  - group: ""
    resource: namespaces
    name: openshift-authentication
```

### 3.1 `status.conditions`

`status.conditions` describes the state of the Operator's managed and monitored components.

Each condition contains:

| Field | Meaning |
|---|---|
| `type` | The aspect being reported, such as `Available`, `Progressing`, `Degraded`, or `Upgradeable`. |
| `status` | `True`, `False`, or `Unknown`. |
| `reason` | Short CamelCase machine-readable reason. Useful for searching docs, bugs, and logs. |
| `message` | Human-readable explanation. This is often the most useful troubleshooting clue. |
| `lastTransitionTime` | Time when this condition last changed status. Use it to determine whether the condition is fresh or stale. |

### 3.2 `status.relatedObjects`

`relatedObjects` lists objects that are interesting or related to the Operator. This usually includes:

- the Operator configuration object,
- the Operator namespace,
- operand namespaces,
- API services,
- deployments,
- daemon sets,
- custom resources that drive the component.

Use it when you do not know which namespace or resource family to inspect.

```bash
oc get co ingress -o jsonpath='{range .status.relatedObjects[*]}{.group}{"\t"}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

### 3.3 `status.versions`

`versions` shows operator and operand version tuples. During upgrades, this matters because the CVO expects operators to report that they have achieved the desired version before the upgrade can move forward.

```bash
oc get co kube-apiserver -o jsonpath='{range .status.versions[*]}{.name}{"="}{.version}{"\n"}{end}'
```

## 4. The normal ClusterOperator health model

The most important production mental model is:

```text
Available   = Can the component serve its function?
Progressing = Is it intentionally moving from one state/version/config to another?
Degraded    = Has it persistently failed to reach or maintain required state?
```

These conditions are **not mutually exclusive**.

An operator can be:

```text
Available=True, Progressing=True, Degraded=False
```

That usually means the component is usable while a rollout or configuration change is in progress.

An operator can also be:

```text
Available=True, Progressing=False, Degraded=True
```

That means the component is still available, but the Operator has detected a persistent problem that needs investigation.

Do not read the columns as one single status. Read them as three independent signals.

---

## 5. `Available` condition in depth

### 5.1 Meaning

`Available=True` means the Operator reports that its managed component is functional and available in the cluster.

`Available=False` means at least one required part of the operand is non-functional, and administrator intervention might be required.

### 5.2 Practical interpretation

Ask:

```text
Can this platform function currently serve requests or perform its purpose?
```

Examples:

| ClusterOperator | What `Available=True` roughly means |
|---|---|
| `authentication` | OAuth/authentication service is reachable and functional. |
| `console` | Web console backend/route is functional. |
| `ingress` | Ingress controllers are serving routes according to desired configuration. |
| `dns` | DNS operands are available enough for cluster DNS service. |
| `network` | CNI/network components are available. |
| `kube-apiserver` | OpenShift-managed kube-apiserver static pods are functional. |
| `machine-config` | MCO/MCD/MCP state is functional enough for node config management. |
| `monitoring` | Core monitoring stack is available. |

The exact threshold depends on the operator. For example, one operator might require all replicas ready; another might consider the component available when a minimum quorum or at least one daemonset pod is available. Always inspect the `message` and operator-specific resources.

### 5.3 Common causes of `Available=False`

Common production causes include:

- required operand pods are not ready,
- operator deployment itself is down,
- static pods are failing on one or more control-plane nodes,
- APIService is unavailable,
- ingress route cannot be reached,
- required service endpoints are missing,
- TLS serving certificates are invalid or not mounted,
- image pull failures,
- node pressure, taints, scheduling failure, or drained nodes,
- PDBs blocking rollout or drains,
- persistent volume/storage failure,
- missing cloud credentials or infrastructure permissions,
- broken DNS, proxy, or trust bundle configuration.

### 5.4 How serious is `Available=False`?

Treat `Available=False` as high priority, especially for:

```text
kube-apiserver
openshift-apiserver
authentication
ingress
network
dns
etcd
machine-config
monitoring
```

Impact depends on the component:

- `kube-apiserver=False` can affect cluster API availability.
- `authentication=False` can block new logins, even if existing tokens still work.
- `ingress=False` can affect routes and external application access.
- `monitoring=False` might not break workloads, but reduces observability and alerting.
- `image-registry=False` might affect builds/pushes, not necessarily running pods.

### 5.5 First commands for `Available=False`

```bash
# See all operators and identify abnormal ones
oc get co

# Inspect the affected operator
oc get co <operator-name> -o yaml
oc describe co/<operator-name>

# Extract only Available condition
oc get co <operator-name> -o jsonpath='{range .status.conditions[?(@.type=="Available")]}status={.status}{"\n"}reason={.reason}{"\n"}message={.message}{"\n"}lastTransitionTime={.lastTransitionTime}{"\n"}{end}'

# Check the operator and operand namespaces from relatedObjects
oc get co <operator-name> -o jsonpath='{range .status.relatedObjects[*]}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

## 6. `Progressing` condition in depth

### 6.1 Meaning

`Progressing=True` means the Operator is actively rolling out new code, propagating configuration changes, upgrading operands, or otherwise moving from one steady state to another.

It is not the same as "the Operator reconciliation loop is running." Operators continuously reconcile. `Progressing=True` is used when the Operator is moving toward a changed desired state.

### 6.2 Normal reasons for `Progressing=True`

`Progressing=True` can be normal during:

- cluster version upgrade,
- operator rollout,
- operand deployment rollout,
- config change,
- certificate rotation,
- machine config rollout,
- ingress controller change,
- network configuration migration,
- image registry storage configuration change,
- monitoring stack rollout,
- API server static pod revision rollout.

### 6.3 When `Progressing=True` is healthy

Healthy example:

```text
Available=True
Progressing=True
Degraded=False
```

This often means the old version is still serving while the new version/config is rolling out.

Example scenarios:

- ingress operator rolling out router pods after config change,
- monitoring operator updating Prometheus/Alertmanager/Thanos pods,
- kube-apiserver operator rolling out new static pod revision,
- machine-config operator applying a new MachineConfigPool update.

### 6.4 When `Progressing=True` is a problem

`Progressing=True` becomes a problem when it stays true much longer than expected and the `message` indicates blocked rollout.

Common causes:

- deployment rollout stuck,
- daemonset not available on some nodes,
- image pull failure,
- PDB preventing eviction,
- node not ready,
- MCP update paused or degraded,
- static pod revision stuck,
- pending CSR after node replacement,
- operands waiting for unavailable APIService/CRD,
- storage or PVC binding issue,
- canary check failing,
- network connectivity checks failing,
- new config invalid but not yet reported as degraded.

### 6.5 Useful commands for `Progressing=True`

```bash
# Check cluster upgrade status
oc get clusterversion
oc get clusterversion version -o yaml
oc adm upgrade

# Check the progressing operator condition
oc get co <operator-name> -o jsonpath='{range .status.conditions[?(@.type=="Progressing")]}status={.status}{"\n"}reason={.reason}{"\n"}message={.message}{"\n"}lastTransitionTime={.lastTransitionTime}{"\n"}{end}'

# Check operator namespace pods
oc get pods -n <operator-namespace> -o wide
oc get deploy -n <operator-namespace>
oc get ds -n <operator-namespace>

# Check events
oc get events -A --sort-by=.lastTimestamp | tail -100
```

### 6.6 Progressing during upgrades

During a cluster upgrade, `Progressing=True` is expected for some ClusterOperators. The CVO applies release manifests in ordered stages called **Runlevels**. It waits for operators in a runlevel to become `Available=True`, `Degraded=False`, and to report the desired version before proceeding to the next runlevel.

Therefore, a single stuck operator can hold the upgrade.

Useful commands:

```bash
# Overall update condition
oc get clusterversion version
oc describe clusterversion version

# CVO logs
oc logs -n openshift-cluster-version deploy/cluster-version-operator --since=2h

# Operators not in healthy target state
oc get co --no-headers | awk '$3 != "True" || $4 != "False" || $5 != "False" {print}'
```

## 7. `Degraded` condition in depth

### 7.1 Meaning

`Degraded=True` means the Operator has observed, over a period of time, that the current state does not match the required state.

Important points:

- It represents a **persistent** observation, not a momentary blip.
- The time threshold can vary by component.
- Operators should not rapidly flap in and out of `Degraded` for short transient changes.
- Normal cluster update activity should usually be represented by `Progressing`, not `Degraded`.
- A degraded condition often indicates that administrator investigation is required.

### 7.2 `Degraded=True` does not always mean outage

This is a senior-admin distinction.

Example:

```text
Available=True
Progressing=False
Degraded=True
```

This means the component is available, but something is wrong or out of desired state. User workloads might still run normally.

Examples:

- one replica is failing but enough replicas remain available,
- optional route check is failing,
- one operand namespace resource is misconfigured,
- an operator cannot complete a secondary task,
- a canary or health check is failing intermittently but service is still reachable,
- cluster has a condition that blocks safe upgrade but not current workload traffic.

Do not ignore it. But do not automatically declare a full outage either.

### 7.3 Common causes of `Degraded=True`

Common causes include:

- invalid cluster-level configuration,
- missing or malformed secret/configmap,
- route, DNS, or ingress canary failure,
- APIService unavailable,
- operand pod crashlooping,
- daemonset missing pods on some nodes,
- static pod revision failure,
- certificate/key mismatch,
- expired or untrusted certificate,
- cloud API permission problem,
- storage class/PV/PVC issue,
- MachineConfigPool degraded,
- failed node drain or reboot,
- CNI rollout failure,
- unreachable registry or image pull secret issue,
- proxy or trusted CA misconfiguration,
- network connectivity check failure,
- configuration drift due to manual edits.

### 7.4 First commands for `Degraded=True`

```bash
# List degraded operators
oc get co --no-headers | awk '$5 == "True" {print}'

# Get degraded message
oc get co <operator-name> -o jsonpath='{range .status.conditions[?(@.type=="Degraded")]}status={.status}{"\n"}reason={.reason}{"\n"}message={.message}{"\n"}lastTransitionTime={.lastTransitionTime}{"\n"}{end}'

# Full describe often formats multiline messages well
oc describe co/<operator-name>

# Related objects can point to the exact namespace or config object
oc get co <operator-name> -o jsonpath='{range .status.relatedObjects[*]}{.group}{"\t"}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

### 7.5 Read `reason` and `message` carefully

Do not stop at:

```text
DEGRADED=True
```

The useful data is usually here:

```yaml
reason: IngressControllersDegraded
message: The "default" ingress controller reports Degraded=True: ...
```

or:

```yaml
reason: MachineConfigPoolsDegraded
message: One or more machine config pools are degraded...
```

or:

```yaml
reason: APIServices_Unavailable
message: APIServices are unavailable: ...
```

Treat the `reason` as the error class and the `message` as the incident clue.

## 8. Condition combination matrix

Use this matrix in real operations.

| Available | Progressing | Degraded | Meaning | Action |
|---|---|---|---|---|
| True | False | False | Healthy steady state. | No action. Continue monitoring. |
| True | True | False | Healthy rollout/config change in progress. | Watch rollout. Check upgrade/config context. |
| True | False | True | Service is available but persistent issue exists. | Investigate. Not always outage. Do not ignore. |
| True | True | True | Service available, rollout in progress, but persistent issue exists. | Investigate carefully. Upgrade/config may be blocked. |
| False | True | False | Component unavailable while rollout is happening. | Check rollout, pods, events, PDBs, nodes. Severity depends on component. |
| False | False | True | Broken steady state. | High priority. Read message, inspect operands, logs, related objects. |
| False | True | True | Component unavailable, rollout stuck or failing. | Incident-level for critical operators. Escalate if control-plane-facing. |
| Unknown | Any | Any | Operator cannot confidently report status. | Check API availability, operator pod, CVO, status update path. |

### 8.1 Most common healthy state

```text
Available=True Progressing=False Degraded=False
```

### 8.2 Most common upgrade state

```text
Available=True Progressing=True Degraded=False
```

### 8.3 Most common incident state

```text
Available=False Progressing=True Degraded=True
```

This usually means the component is trying to move to a required state but failing and is no longer available.

### 8.4 Most misunderstood state

```text
Available=True Progressing=False Degraded=True
```

This is often treated as "fine" by junior admins because the component is available. A senior admin treats it as a warning that can become a bigger problem, especially before upgrades.

## 9. `oc get co` output explained

Example:

```bash
oc get co
```

Example output:

```text
NAME                    VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
authentication          4.14.20   True        False         False      12d
console                 4.14.20   True        False         False      12d
ingress                 4.14.20   True        False         True       30m     The default ingress controller reports Degraded=True...
machine-config          4.14.20   True        True          False      18m     Working towards rendered-worker-...
```

Column meaning:

| Column | Meaning |
|---|---|
| `NAME` | ClusterOperator resource name. |
| `VERSION` | Version reported by the operator. During upgrades, check status.versions for detail. |
| `AVAILABLE` | Value of condition type `Available`. |
| `PROGRESSING` | Value of condition type `Progressing`. |
| `DEGRADED` | Value of condition type `Degraded`. |
| `SINCE` | Age of the last relevant condition transition shown by the CLI. |
| `MESSAGE` | Operator condition message, often shortened in table output. |

For serious troubleshooting, always use YAML or describe because table output can truncate messages.

```bash
oc describe co ingress
oc get co ingress -o yaml
```

## 10. Fast health checks

### 10.1 Show only unhealthy operators

```bash
oc get co --no-headers | awk '$3 != "True" || $4 != "False" || $5 != "False" {print}'
```

### 10.2 Show not available operators

```bash
oc get co --no-headers | awk '$3 != "True" {print}'
```

### 10.3 Show progressing operators

```bash
oc get co --no-headers | awk '$4 == "True" {print}'
```

### 10.4 Show degraded operators

```bash
oc get co --no-headers | awk '$5 == "True" {print}'
```

### 10.5 Get all condition messages in readable format

```bash
for co in $(oc get co -o name); do
  echo "===== $co ====="
  oc get "$co" -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{"\n"}{.message}{"\n\n"}{end}'
done
```

### 10.6 Custom columns

```bash
oc get co -o custom-columns='NAME:.metadata.name,AVAILABLE:.status.conditions[?(@.type=="Available")].status,PROGRESSING:.status.conditions[?(@.type=="Progressing")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status,VERSION:.status.versions[?(@.name=="operator")].version'
```

## 11. Troubleshooting workflow used by senior OpenShift admins

### Step 1: Confirm cluster-wide view

```bash
oc get co
oc get clusterversion
oc get nodes
```

Look for patterns:

- Is one operator affected or many?
- Are control-plane operators affected together?
- Are network/dns/ingress affected together?
- Are many operators progressing because of an upgrade?
- Is machine-config updating nodes?
- Are nodes NotReady?

### Step 2: Identify the first failing condition

```bash
oc describe co/<operator-name>
oc get co <operator-name> -o yaml
```

Look at:

- `type`
- `status`
- `reason`
- `message`
- `lastTransitionTime`

Do not troubleshoot only from the table row.

### Step 3: Find related namespaces and resources

```bash
oc get co <operator-name> -o jsonpath='{range .status.relatedObjects[*]}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

Then inspect those resources:

```bash
oc get all -n <namespace>
oc get pods -n <namespace> -o wide
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### Step 4: Separate operator failure from operand failure

An operator has two sides:

```text
Operator controller pod  -> the brain
Operand resources        -> what the operator manages
```

Example:

```text
openshift-ingress-operator deployment/ingress-operator
openshift-ingress         router-default pods
```

If the operator pod is down, the controller cannot reconcile. If the operator pod is healthy but operands are failing, the Operator will usually report degraded/progressing based on operand state.

Commands:

```bash
oc get pods -n <operator-namespace> -o wide
oc logs -n <operator-namespace> deploy/<operator-deployment> --since=1h

oc get pods -n <operand-namespace> -o wide
oc describe pod <pod> -n <operand-namespace>
oc logs <pod> -n <operand-namespace> --since=1h
```

### Step 5: Check events

Events often reveal scheduling, mount, image, and admission problems faster than logs.

```bash
oc get events -A --sort-by=.lastTimestamp | tail -150
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common event clues:

```text
FailedScheduling
FailedMount
BackOff
ImagePullBackOff
ErrImagePull
FailedCreate
FailedAttachVolume
Unhealthy
Killing
Preempting
```

### Step 6: Check nodes and MCPs

Many operator symptoms are actually node symptoms.

```bash
oc get nodes
oc describe node <node>
oc get mcp
oc describe mcp master
oc describe mcp worker
```

If `machine-config` is progressing or degraded:

```bash
oc get mcp -o wide
oc get machineconfig
oc get nodes -o wide
oc adm node-logs <node> -u kubelet --tail=200
oc adm node-logs <node> -u crio --tail=200
```

### Step 7: Check API aggregation

Some operators depend on aggregated APIs.

```bash
oc get apiservices | grep -v True
oc describe apiservice <apiservice-name>
```

If an APIService is unavailable, check the backing service, endpoints, certificates, and pods.

### Step 8: Check upgrade state

```bash
oc adm upgrade
oc get clusterversion version -o yaml
oc logs -n openshift-cluster-version deploy/cluster-version-operator --since=2h
```

Look for:

- accepted release,
- failing preconditions,
- blocked runlevel,
- operator version not updated,
- `Upgradeable=False`,
- payload image pull/extraction failure,
- manifest apply failure.

### Step 9: Gather support data when needed

```bash
oc adm must-gather
```

For a focused collection, inspect key namespaces and objects:

```bash
oc adm inspect clusteroperator/<operator-name>
oc adm inspect ns/<namespace>
oc adm inspect clusterversion/version
```

Package evidence before escalation:

```bash
tar cvaf must-gather-$(date +%F-%H%M).tar.gz must-gather.local.*
```

## 12. Operator-specific troubleshooting patterns

## 12.1 `authentication` ClusterOperator

### Typical abnormal states

```text
authentication Available=False Progressing=True Degraded=True
authentication Available=True  Progressing=False Degraded=True
```

### Common causes

- OAuth server pods not ready.
- OAuth route inaccessible.
- Ingress/router issue.
- Identity provider misconfiguration.
- Bad htpasswd secret, LDAP bind issue, OIDC config issue.
- Missing or broken certificates.
- API server or route dependency failure.

### Commands

```bash
oc get co authentication -o yaml
oc describe co/authentication

oc get pods -n openshift-authentication -o wide
oc get pods -n openshift-authentication-operator -o wide
oc logs -n openshift-authentication-operator deploy/authentication-operator --since=1h

oc get oauth cluster -o yaml
oc get route -n openshift-authentication
oc get events -n openshift-authentication --sort-by=.lastTimestamp
```

### Senior-admin note

If `authentication` is down, existing kubeconfigs or tokens might still work for some time, but new logins can fail. Do not test only with your current session. Test a fresh login path if safe.

## 12.2 `console` ClusterOperator

### Common causes

- Console deployment not ready.
- Console route failing.
- Authentication dependency failing.
- Ingress/DNS problem.
- Console config error.

### Commands

```bash
oc get co console -o yaml
oc get pods -n openshift-console -o wide
oc logs -n openshift-console deploy/console --since=1h
oc get route -n openshift-console
oc get console.operator.openshift.io cluster -o yaml
```

### Senior-admin note

Console failure does not always mean API failure. During incidents, prefer CLI/API verification:

```bash
oc whoami
oc get --raw='/readyz?verbose'
oc get co
```

## 12.3 `ingress` ClusterOperator

### Common causes

- Router pods not available.
- IngressController degraded.
- Load balancer unreachable.
- Wildcard DNS broken.
- Default certificate invalid.
- Canary route failing.
- Node scheduling/taint issue.

### Commands

```bash
oc get co ingress -o yaml
oc describe co/ingress

oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller default -n openshift-ingress-operator

oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-ingress-operator -o wide
oc logs -n openshift-ingress-operator deploy/ingress-operator --since=1h

oc get svc -n openshift-ingress
oc get route -A | head
```

### Practical check

From outside the cluster:

```bash
curl -vk https://console-openshift-console.apps.<cluster-domain>
```

From inside the cluster:

```bash
oc run curl-test --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk https://console-openshift-console.openshift-console.svc
```

- DNS daemonset pods not available.
- Node-level networking problem.
- CoreDNS config issue.

## 12.5 `network` ClusterOperator

### Common causes

- CNI pods failing.
- OVN-Kubernetes control plane issues.
- Node network daemonset not running.
- MTU mismatch.
- Network diagnostics failing.
- Node-to-node connectivity broken.
- Cloud/network security group issue.

### Commands

```bash
oc get co network -o yaml
oc describe co/network
oc get network.operator cluster -o yaml
oc get network.config cluster -o yaml

oc get pods -n openshift-network-operator -o wide
oc logs -n openshift-network-operator deploy/network-operator --since=1h

oc get pods -n openshift-ovn-kubernetes -o wide
oc get ds -n openshift-ovn-kubernetes
oc get events -n openshift-ovn-kubernetes --sort-by=.lastTimestamp
```

### Senior-admin note

## 13. ClusterOperator conditions and upgrades

ClusterOperator conditions are central to OpenShift upgrades.

The CVO:

1. watches the `ClusterVersion` resource,
2. retrieves and validates the desired release payload,
3. applies release manifests,
4. updates cluster operators in logical stages,
5. waits for operators to report healthy state and target versions.

During upgrade, watch:

```bash
watch 'oc get clusterversion; echo; oc get co'
```

### 13.1 Normal upgrade behavior

You might see:

```text
Progressing=True
```

on multiple operators.

That is normal if:

```text
Available=True
Degraded=False
```

and messages indicate rollout progress.

### 13.2 Abnormal upgrade behavior

Concerning signs:

```text
Available=False
Degraded=True
Progressing=True for a long time
ClusterVersion Failing=True
Upgradeable=False before upgrade
```

Commands:

```bash
oc describe clusterversion version
oc logs -n openshift-cluster-version deploy/cluster-version-operator --since=2h
oc get co --no-headers | awk '$3 != "True" || $4 != "False" || $5 != "False" {print}'
```

### 13.3 Do not force upgrades casually

OpenShift can provide force options for exceptional cases, but forcing an update around failed verification, `Upgradeable=False`, or degraded core operators can create a harder outage.

Before forcing anything, collect:

```bash
oc get clusterversion version -o yaml
oc get co -o yaml
oc adm must-gather
```

Then validate with vendor documentation or support process.

## 14. How to find root cause when many ClusterOperators are bad

When many operators are degraded or unavailable, avoid troubleshooting alphabetically. Find the common dependency.

### 14.1 Dependency-first triage

Start with:

```bash
oc get nodes
oc get co etcd kube-apiserver openshift-apiserver authentication network dns ingress machine-config
oc get mcp
```

### 14.2 Common dependency chains

#### Network problem

```text
network degraded
  -> dns degraded/unavailable
  -> ingress degraded
  -> authentication/console unavailable
  -> monitoring degraded
```

#### Ingress problem

```text
ingress degraded
  -> console unavailable
  -> authentication route check degraded
  -> apps routes fail
```

#### API server problem

```text
kube-apiserver degraded/unavailable
  -> operators cannot update status reliably
  -> many ClusterOperators Unknown/Degraded
  -> controllers lag
```

#### Machine config problem

```text
machine-config progressing/degraded
  -> nodes reboot/drain/fail
  -> daemonsets unavailable
  -> ingress/network/dns/monitoring affected
```

#### Storage problem

```text
storage/PVC issue
  -> monitoring unavailable
  -> image-registry unavailable
  -> logging/other stateful operators affected
```

### 14.3 Root-cause rule

If several operators fail together, the first root cause is usually one of:

```text
nodes
network
DNS
ingress
API server
etcd
machine-config
storage
proxy/CA/registry access
```

Not every degraded operator is the root cause.


```promql

```

```promql
cluster_operator_conditions{condition="Progressing",status="true"} == 1
```

Production alerting idea:

```text
Critical: Available=False for critical operators for more than 5-10 minutes
Warning: Degraded=True for any operator for more than 10-30 minutes
```

Adjust thresholds by environment. For example, `machine-config Progressing=True` during upgrade can last much longer than `console Progressing=True`.

## 17. Production runbook: ClusterOperator degraded

Use this as an on-call flow.

### 17.1 Situation

Alert:

```text
ClusterOperatorDegraded
```

### 17.2 Immediate triage

```bash
oc get co
oc get co --no-headers | awk '$5 == "True" {print}'
oc get nodes
oc get clusterversion
```

### 17.3 Identify detail

```bash
OP=<operator-name>
oc describe co/$OP
oc get co $OP -o yaml
```

Record:

```text
operator:
Available:
Progressing:
Degraded:
reason:
message:
lastTransitionTime:
cluster version:
upgrade in progress: yes/no
nodes healthy: yes/no
```

### 17.4 Determine blast radius

Ask:

```text
Is the component Available=False?
Is user traffic affected?
Is API/auth/ingress/network affected?
Is this blocking an upgrade?
Is this a single operator or many?
```

### 17.5 Inspect related objects

```bash
oc get co $OP -o jsonpath='{range .status.relatedObjects[*]}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

### 17.6 Inspect pods, events, logs

```bash
oc get pods -n <namespace> -o wide
oc get events -n <namespace> --sort-by=.lastTimestamp
oc logs -n <namespace> deploy/<operator-deployment> --since=1h
```

### 17.7 Check dependencies

```bash
oc get nodes
oc get mcp
oc get apiservices | grep -v True
oc get csr
oc get pv,pvc -A | grep -E 'Pending|Lost|Released'
```

### 17.8 Decide action

Safe actions usually include:

- fix invalid config,
- restore missing secret/configmap if known,
- fix DNS/LB/certificate issue,
- approve valid pending CSRs,
- unpause/fix MCP if appropriate,
- fix image pull/proxy/registry access,
- resolve node NotReady or disk pressure,
- remove broken manual changes from CVO-managed resources only through supported configuration APIs.

Avoid unsafe actions:

- deleting random control-plane pods repeatedly,
- editing generated manifests,
- removing finalizers blindly,
- force-upgrading without understanding `Upgradeable=False`,
- manually modifying static pod manifests,
- deleting etcd members without a recovery plan,
- patching ClusterOperator status manually.

### 17.9 Collect evidence

```bash
oc adm must-gather
oc adm inspect clusteroperator/$OP
oc adm inspect clusterversion/version
oc adm inspect ns/<operator-namespace>
oc adm inspect ns/<operand-namespace>
```

## 20. Advanced interpretation patterns

### 20.1 `Available=True` is not equal to perfect

It means the component is serving its purpose according to that operator's availability criteria. It can still be degraded.

### 20.2 `Progressing=False` is not equal to no reconciliation

Operators always reconcile. `Progressing=False` means no active move from one steady state to another is being reported.

### 20.3 `Degraded=False` is not equal to no warnings anywhere

Some issues might exist in pods, events, logs, or optional components without crossing the operator's degraded threshold.

### 20.4 `Unknown` deserves attention

`Unknown` can indicate the operator cannot determine state or cannot publish status. Check operator pod health, API availability, RBAC, and CVO.

### 20.5 `lastTransitionTime` helps separate new incident from old noise

A condition that transitioned two minutes ago during a change window is different from a condition that has been degraded for six days.

### 20.6 `message` is human-readable, not stable automation API

Use `type/status/reason` for automation decisions. Use `message` for human diagnosis.

### 20.7 Do not patch ClusterOperator status

ClusterOperator status is reported by the operator. Patching it manually hides symptoms and does not fix root cause. The operator will usually overwrite it anyway.

## 22. Common interview/exam explanations

### Q1. What does `ClusterOperator Degraded=True` mean?

It means the operator has persistently observed that the current state of its managed component does not match the required state. It is not necessarily an immediate outage if `Available=True`, but it requires investigation because the component is not fully healthy or not fully matching desired state.

### Q2. What does `Progressing=True` mean?

It means the operator is actively moving from one steady state to another, such as rolling out a new version, applying configuration, rotating certificates, or updating operands. It can be normal during upgrades or config changes.

### Q3. What does `Available=False` mean?

It means the operator reports that at least one required part of its operand is non-functional. For critical operators such as kube-apiserver, authentication, ingress, network, or DNS, this can be service-impacting.

### Q4. Can an operator be Available and Degraded at the same time?

Yes. `Available=True` means the component can still serve its function. `Degraded=True` means a persistent problem exists. This is a warning state and may block upgrades or become an outage later.

### Q5. During upgrade, what conditions does CVO wait for?

The CVO waits for operators in a runlevel to report `Available=True`, `Degraded=False`, and the desired version in the `ClusterOperator` resource before moving to the next runlevel.

### Q6. Where do you start troubleshooting?

Start with:

```bash
oc get co
oc describe co/<operator>
oc get co <operator> -o yaml
```

Then read `reason`, `message`, and `lastTransitionTime`, inspect related objects, pods, events, logs, nodes, MCPs, and dependencies.

## 23. Real-world examples

### Example 1: Ingress degraded but available

```text
ingress Available=True Progressing=False Degraded=True
```

- Routes might still work.
- Operator has detected a persistent ingress-related problem.
- Could be canary route failure, one ingress controller degraded, certificate issue, DNS/LB problem, or router pod issue.

```text
machine-config Available=True Progressing=True Degraded=False
```

Interpretation:

- MCO is applying new machine configuration.
- Nodes may be cordoned/drained/rebooted one by one.
- Normal during upgrades, but duration depends on node count and workload drain behavior.

Workflow:

```bash

oc get nodes
oc get pdb -A
```

### Example 3: Authentication unavailable after IDP change

```text
authentication Available=False Progressing=True Degraded=True
```

Interpretation:

- OAuth/authentication stack is failing after configuration change.

## 24. What not to do

Avoid these common mistakes:

1. **Do not patch `ClusterOperator` status manually.**  
   It is a symptom, not the root cause.

2. **Do not delete random platform pods repeatedly.**  
   If the operator is failing to reconcile, pods will come back with the same issue.

3. **Do not edit generated resources directly.**  
   Use supported config APIs such as `ingress.operator`, `oauth`, `image.config`, `proxy.config`, `network.operator`, etc.

4. **Do not force upgrades around unresolved degraded critical operators.**  
   You can turn a recoverable degraded state into a major outage.

5. **Do not treat `Available=True Degraded=True` as healthy.**  
   It is available but not clean.

6. **Do not chase every degraded operator independently when many are failing.**  
   Find the shared dependency.

7. **Do not ignore old degraded conditions before maintenance.**  
   Old warnings often become upgrade blockers.

## 27. Final senior-admin summary

Read `ClusterOperator` conditions like this:

```text
Available=True      -> the platform function is serving its purpose
Progressing=True    -> it is intentionally moving to a new version/config/state
Degraded=True       -> it has persistently failed to match desired state
```

The best OpenShift administrators do not only run `oc get co`. They read the condition `reason`, condition `message`, `lastTransitionTime`, `relatedObjects`, operator logs, operand state, events, nodes, MCPs, and CVO state. They also understand dependency chains: a broken network, DNS, ingress, API server, etcd, machine-config, or storage layer can make many unrelated operators look unhealthy.

For production, the clean target before upgrades and maintenance is:

```text
All required ClusterOperators Available=True
All required ClusterOperators Degraded=False
No unexpected long-running Progressing=True
Nodes Ready
MCPs Updated
ClusterVersion not failing
```
