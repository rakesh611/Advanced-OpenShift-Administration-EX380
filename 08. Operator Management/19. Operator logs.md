# Operator Logs in Operator Management for Advanced OpenShift Administration

**Audience:** Advanced OpenShift administrators, OpenShift/Kubernetes platform engineers, SREs, L3 support engineers  
**Experience level:** Written from a 10-year production operations mindset  
**Scope:** OpenShift 4.x, Operator Lifecycle Manager, Cluster Operators, Operator pod logs, catalog logs, install/upgrade troubleshooting, support data collection

---

## 1. What “Operator Logs” Means in OpenShift

In OpenShift, **Operator logs** are the runtime logs generated by the pods or containers that run Operator controller logic.

An Operator is not only an application pod. It is a controller that watches cluster resources, compares desired state with actual state, and performs reconciliation. When something goes wrong with installation, upgrade, reconciliation, operand creation, RBAC, webhooks, CRDs, certificates, image pulls, or dependency resolution, the Operator logs usually show the real technical reason.

In production, Operator logs are used to answer questions like:

- Why is an Operator not installing?
- Why is a `ClusterServiceVersion` stuck in `Pending`, `InstallReady`, `Installing`, or `Failed`?
- Why is a `Subscription` not creating an `InstallPlan`?
- Why is an operand custom resource not creating pods, services, routes, PVCs, or secrets?
- Why is a Cluster Operator `Degraded`, `Progressing`, or `Unavailable`?
- Why is an upgrade blocked?
- Why is an Operator repeatedly restarting?
- Why is a webhook rejecting resources?
- Why are CRDs present but the Operator is not reconciling objects?

A senior administrator must not check Operator logs randomly. The correct approach is to identify which lifecycle layer is failing, then collect logs from the correct component.

## 2. Two Major Operator Categories in OpenShift

OpenShift has two broad categories of Operators, and their logs are investigated differently.

### 2.1 Cluster Operators

**Cluster Operators** are core OpenShift platform Operators required for cluster functionality. Examples include:

- `kube-apiserver`
- `kube-controller-manager`
- `kube-scheduler`
- `authentication`
- `console`
- `ingress`
- `network`
- `machine-config`
- `image-registry`
- `monitoring`
- `dns`
- `etcd`
- `cloud-controller-manager`
- `operator-lifecycle-manager`

They are visible through:

```bash
oc get clusteroperators
oc get co
```

Cluster Operators are managed by the **Cluster Version Operator**. They normally do **not** have a user-created `Subscription` object.

You troubleshoot them using:

```bash
oc get co
oc describe co <cluster-operator-name>
oc get pods -n <operator-namespace>
oc logs -n <operator-namespace> <operator-pod-name>
oc adm must-gather
```

Example:

```bash
oc describe co authentication
oc get pods -n openshift-authentication-operator
oc logs -n openshift-authentication-operator deploy/authentication-operator
```

### 2.2 OLM-managed Application Operators

Application Operators are installed through OperatorHub or custom catalogs and are managed by **Operator Lifecycle Manager**.

They usually have these resources:

- `Subscription`
- `InstallPlan`
- `ClusterServiceVersion` / `CSV`
- `CatalogSource`
- `OperatorGroup`
- Operator Deployment / Pod
- Operand custom resources

You troubleshoot them using this chain:

```text
CatalogSource → PackageManifest → Subscription → InstallPlan → CSV → Operator Pod → Operand CR → Operand Pods
```

Example:

```bash
oc get sub -n <operator-namespace>
oc describe sub <subscription-name> -n <operator-namespace>
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc get pods -n <operator-namespace>
oc logs -n <operator-namespace> <operator-pod-name>
```

## 3. Why Operator Logs Are Important

Operator logs are important because most Operator failures are not visible from pod status alone.

For example, a pod can show `Running`, but the Operator may still fail to reconcile because of:

- Missing RBAC permissions
- Invalid custom resource spec
- CRD version mismatch
- Admission webhook failure
- Certificate validation failure
- Registry authentication failure
- API server timeout
- Network policy blocking API access
- Catalog source connectivity issue
- Dependency resolution failure
- Owner reference conflict
- Finalizer stuck
- Namespace mismatch
- Operand image pull failure
- Unsupported cluster version
- Operand pod security violation
- SCC restriction
- Storage class/PVC binding failure

A junior admin often stops at:

```bash
oc get pods
```

A senior admin goes further:

```bash
oc describe sub <name> -n <ns>
oc describe ip <name> -n <ns>
oc describe csv <name> -n <ns>
oc logs deploy/<operator-deployment> -n <ns> --since=30m
oc get events -n <ns> --sort-by=.lastTimestamp
```

## 4. Operator Log Sources

Operator-related logs can come from multiple places.

### 4.1 Operator Pod Logs

These are the main logs generated by the Operator controller.

```bash
oc logs -n <namespace> <pod-name>
```

For a deployment-managed Operator:

```bash
oc logs -n <namespace> deploy/<operator-deployment-name>
```

For all containers in the pod:

```bash
oc logs -n <namespace> <pod-name> --all-containers=true
```

For a specific container:

```bash
oc logs -n <namespace> <pod-name> -c <container-name>
```

For previous crashed container logs:

```bash
oc logs -n <namespace> <pod-name> -c <container-name> --previous
```

### 4.2 OLM Component Logs

OLM itself has components that manage Operator lifecycle.

Common namespaces:

```bash
openshift-operator-lifecycle-manager
openshift-marketplace
```

Useful commands:

```bash
oc get pods -n openshift-operator-lifecycle-manager
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator
oc logs -n openshift-operator-lifecycle-manager deploy/packageserver
```

Depending on the version and cluster, deployments or pod names can vary. Always check actual names:

```bash
oc get deploy -n openshift-operator-lifecycle-manager
oc get pods -n openshift-operator-lifecycle-manager -o wide
```

### 4.3 CatalogSource Pod Logs

CatalogSource pods serve Operator metadata over gRPC. If an Operator does not appear, a `Subscription` cannot resolve dependencies, or an `InstallPlan` is not created, catalog logs are important.

Common namespace:

```bash
openshift-marketplace
```

Commands:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalogsource-name> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc logs -n openshift-marketplace <catalog-pod-name>
```

Example:

```bash
oc describe catalogsource redhat-operators -n openshift-marketplace
oc get pods -n openshift-marketplace | grep redhat-operators
oc logs -n openshift-marketplace <redhat-operators-pod>
```

### 4.4 Cluster Operator Logs

Cluster Operators usually run in `openshift-*` namespaces.

Examples:

```bash
oc get pods -n openshift-kube-apiserver-operator
oc logs -n openshift-kube-apiserver-operator deploy/kube-apiserver-operator

oc get pods -n openshift-ingress-operator
oc logs -n openshift-ingress-operator deploy/ingress-operator

oc get pods -n openshift-machine-config-operator
oc logs -n openshift-machine-config-operator deploy/machine-config-operator
```

### 4.5 Operand Logs

An Operator manages operands. The Operator log tells you what the controller tried to do. Operand logs tell you what happened inside the managed application.

Example: OpenShift Logging Operator manages LokiStack, collector, gateway, console plugin, and other operands depending on version and configuration.

You may need both:

```bash
oc logs -n openshift-logging deploy/cluster-logging-operator
oc logs -n openshift-logging <loki-or-collector-pod>
```

### 4.6 Events

Events are not logs, but they are essential during Operator troubleshooting.

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc describe pod <pod-name> -n <namespace>
oc describe csv <csv-name> -n <namespace>
```

Events often show:

- Failed image pull
- Scheduling failure
- SCC denial
- Secret missing
- ConfigMap missing
- PVC unbound
- Probe failure
- Admission webhook rejection
- RBAC forbidden message

## 5. Finding the Correct Operator Namespace

A major production mistake is checking logs in the wrong namespace.

### 5.1 For Cluster Operators

Start with:

```bash
oc get co
```

Then inspect the failing Cluster Operator:

```bash
oc describe co <name>
```

Look for:

- `Available`
- `Progressing`
- `Degraded`
- `Upgradeable`
- Message
- Reason
- Related objects

Example:

```bash
oc describe co ingress
```

Then find related namespaces:

```bash
oc get ns | grep ingress
oc get pods -A | grep ingress
```

Typical namespace:

```bash
openshift-ingress-operator
```

### 5.2 For OLM-managed Operators

List installed Operators:

```bash
oc get operators
oc get operators -A
```

List subscriptions across all namespaces:

```bash
oc get sub -A
```

Find CSVs:

```bash
oc get csv -A
```

Find pods:

```bash
oc get pods -A | grep -i <operator-keyword>
```

Find deployments:

```bash
oc get deploy -A | grep -i <operator-keyword>
```

## 6. Basic Operator Log Commands

### 6.1 View Current Logs

```bash
oc logs -n <namespace> <pod-name>
```

### 6.2 Follow Logs Live

```bash
oc logs -f -n <namespace> <pod-name>
```

### 6.3 View Logs from Deployment

```bash
oc logs -n <namespace> deploy/<deployment-name>
```

### 6.4 View Logs from Specific Container

```bash
oc logs -n <namespace> <pod-name> -c <container-name>
```

### 6.5 View Previous Crashed Container Logs

```bash
oc logs -n <namespace> <pod-name> -c <container-name> --previous
```

This is critical for `CrashLoopBackOff`.

### 6.6 Limit Log Output by Time

```bash
oc logs -n <namespace> <pod-name> --since=10m
oc logs -n <namespace> <pod-name> --since=1h
```

### 6.7 Limit Log Output by Lines

```bash
oc logs -n <namespace> <pod-name> --tail=100
oc logs -n <namespace> <pod-name> --tail=500
```

### 6.8 Add Timestamps

```bash
oc logs -n <namespace> <pod-name> --timestamps
```

### 6.9 Collect Logs from All Containers

```bash
oc logs -n <namespace> <pod-name> --all-containers=true
```

### 6.10 Save Operator Logs to File

```bash
oc logs -n <namespace> <pod-name> --all-containers=true --timestamps > operator.log
```

For previous logs:

```bash
oc logs -n <namespace> <pod-name> --all-containers=true --previous --timestamps > operator-previous.log
```

## 7. Senior-Level Operator Troubleshooting Flow

Use this sequence in real production incidents.

### Step 1: Check Cluster Health

```bash
oc get clusterversion
oc get co
oc get nodes
oc get mcp
```

If multiple Cluster Operators are degraded, the issue may be platform-wide, not specific to one Operator.

### Step 2: Identify Operator Type

Ask:

```text
Is this a Cluster Operator or an OLM-managed application Operator?
```

For Cluster Operator:

```bash
oc get co
oc describe co <name>
```

For OLM-managed Operator:

```bash
oc get sub -A
oc get csv -A
oc get installplan -A
```

### Step 3: Check Subscription

```bash
oc get sub -n <namespace>
oc describe sub <subscription-name> -n <namespace>
```

Check:

- `CatalogSourcesUnhealthy`
- `InstallPlanMissing`
- `InstallPlanPending`
- `InstallPlanFailed`
- `ResolutionFailed`
- `currentCSV`
- `installedCSV`
- `installPlanRef`
- `state`
- `reason`
- `message`

### Step 4: Check InstallPlan

```bash
oc get installplan -n <namespace>
oc describe installplan <installplan-name> -n <namespace>
```

Check:

- Approved or not
- Phase
- Bundle lookup status
- Resource creation failures
- CRD conflicts
- RBAC creation errors
- ServiceAccount errors

### Step 5: Check CSV

```bash
oc get csv -n <namespace>
oc describe csv <csv-name> -n <namespace>
```

Check:

- Phase
- Reason
- Message
- Requirements
- Install strategy
- Related images
- Owned CRDs
- Required CRDs
- Deployment status
- Events

### Step 6: Check Operator Pod

```bash
oc get pods -n <namespace> -o wide
oc describe pod <operator-pod> -n <namespace>
oc logs <operator-pod> -n <namespace> --all-containers=true --timestamps
```

If restarting:

```bash
oc logs <operator-pod> -n <namespace> --all-containers=true --previous --timestamps
```

### Step 7: Check Operand CR

```bash
oc get <custom-resource-kind> -n <namespace>
oc describe <custom-resource-kind> <name> -n <namespace>
oc get <custom-resource-kind> <name> -n <namespace> -o yaml
```

Look at:

```yaml
status:
  conditions:
```

### Step 8: Check Operand Pods

```bash
oc get pods -n <operand-namespace>
oc describe pod <operand-pod> -n <operand-namespace>
oc logs <operand-pod> -n <operand-namespace> --all-containers=true
```

### Step 9: Check Events

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc get events -A --sort-by=.lastTimestamp | tail -50
```

### Step 10: Collect Must-Gather

```bash
oc adm must-gather
```

For Operator-specific or product-specific must-gather images, use vendor documentation if available.

## 8. Understanding Log Patterns

Operator logs often contain controller-runtime style messages. You may see terms like:

```text
reconcile
reconciling
controller
watch
cache
leader election
resource version
forbidden
conflict
not found
webhook
finalizer
owner reference
condition
status update
```

### 8.1 Reconcile Loop

Most Operators run reconciliation loops.

A typical flow:

```text
Watch event received
Read custom resource
Compare desired state with actual state
Create/update/delete dependent resources
Update status.conditions
Requeue if needed
```

Example log style:

```text
Reconciling ClusterLogging instance
Creating deployment collector
Updating status condition Ready=False
Requeue after 30s
```

A repeating reconcile error usually means the Operator is continuously trying to fix something but cannot.

### 8.2 Forbidden / RBAC Errors

Example:

```text
secrets is forbidden: User "system:serviceaccount:ns:operator-sa" cannot create resource "secrets" in API group "" in namespace "app-ns"
```

Meaning:

- Operator ServiceAccount lacks RBAC.
- CSV may not have installed correct roles.
- OperatorGroup target namespace may be wrong.
- Manual RBAC modification may have broken permissions.

Check:

```bash
oc get sa -n <operator-namespace>
oc get rolebinding,clusterrolebinding -A | grep <operator-sa>
oc auth can-i create secrets --as system:serviceaccount:<ns>:<sa> -n <target-ns>
```

### 8.3 Conflict Errors

Example:

```text
Operation cannot be fulfilled on deployments.apps "example": the object has been modified
```

Meaning:

- Multiple controllers are modifying the same object.
- User or GitOps tool is fighting the Operator.
- Reconcile loop should normally retry.

Check:

```bash
oc get deployment <name> -n <ns> -o yaml
oc get events -n <ns> --sort-by=.lastTimestamp
```

### 8.4 Not Found Errors

Example:

```text
configmaps "operator-config" not found
```

Meaning:

- Required ConfigMap/Secret is missing.
- Operator expected a generated resource that was deleted.
- InstallPlan did not complete.
- Namespace mismatch.

Check:

```bash
oc get cm,secret -n <ns>
oc describe csv <csv> -n <ns>
```

### 8.5 Image Pull Errors

Image pull issues usually appear in events, but Operator logs may also reference failed deployments.

Check:

```bash
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get secret -n <ns> | grep pull
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

Common causes:

- Private registry credentials missing
- Disconnected mirror misconfigured
- Wrong image tag
- Proxy issue
- CA trust issue
- Registry unavailable

### 8.6 Webhook Errors

Example:

```text
failed calling webhook "validate.example.io": service "webhook-service" not found
```

Meaning:

- Webhook service missing
- Webhook pod down
- TLS certificate invalid
- CA bundle mismatch
- Network/DNS issue

Check:

```bash
oc get validatingwebhookconfiguration,mutatingwebhookconfiguration | grep -i <operator>
oc describe validatingwebhookconfiguration <name>
oc get svc,endpoints,pods -n <webhook-namespace>
oc logs -n <webhook-namespace> <webhook-pod>
```

### 8.7 Finalizer Errors

Example:

```text
failed to remove finalizer
```

Meaning:

- Operator is trying to clean resources before deletion.
- Dependent resources may be stuck.
- External dependency may be unavailable.

Check:

```bash
oc get <resource> <name> -n <ns> -o yaml | grep -A5 finalizers
oc describe <resource> <name> -n <ns>
```

Do not remove finalizers blindly in production unless you understand what cleanup will be skipped.

### 8.8 Leader Election Logs

Operators often use leader election when multiple replicas exist.

Example:

```text
attempting to acquire leader lease
successfully acquired lease
leader election lost
```

Usually normal unless frequent leadership loss correlates with API latency, network instability, or pod restarts.

Check:

```bash
oc get lease -A | grep -i <operator>
oc get pods -n <ns> -o wide
oc describe pod <operator-pod> -n <ns>
```

### 8.9 API Timeout or Rate Limit Errors

Example:

```text
context deadline exceeded
client rate limiter Wait returned an error
etcdserver: request timed out
```

Possible causes:

- API server overloaded
- etcd latency
- Network issue
- Operator watching too many namespaces/resources
- Large number of CRs
- Broken watch cache

Check:

```bash
oc get co kube-apiserver etcd
oc adm top pods -A
oc adm top nodes
oc get --raw /readyz?verbose
```

## 9. Operator Logs and OLM Resource Relationship

A strong admin correlates Operator logs with OLM status.

### 9.1 Subscription

A `Subscription` tracks a channel in a package and keeps CSVs updated.

Useful commands:

```bash
oc get sub -n <ns>
oc describe sub <sub-name> -n <ns>
oc get sub <sub-name> -n <ns> -o yaml
```

Important fields:

```yaml
spec:
  channel:
  installPlanApproval:
  name:
  source:
  sourceNamespace:
status:
  currentCSV:
  installedCSV:
  installPlanRef:
  conditions:
```

If `Subscription` shows `ResolutionFailed`, check:

```bash
oc describe sub <sub-name> -n <ns>
oc get catalogsource -n <sourceNamespace>
oc describe catalogsource <source> -n <sourceNamespace>
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator
```

### 9.2 InstallPlan

An `InstallPlan` is the calculated set of resources needed to install or upgrade an Operator.

Useful commands:

```bash
oc get ip -n <ns>
oc describe ip <installplan-name> -n <ns>
oc get ip <installplan-name> -n <ns> -o yaml
```

If manual approval is used:

```bash
oc patch installplan <installplan-name> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

Check logs:

```bash
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator --since=30m
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator --since=30m
```

### 9.3 ClusterServiceVersion

A CSV represents a specific installed Operator version.

Useful commands:

```bash
oc get csv -n <ns>
oc describe csv <csv-name> -n <ns>
oc get csv <csv-name> -n <ns> -o yaml
```

Important CSV phases:

```text
Pending
InstallReady
Installing
Succeeded
Failed
Replacing
Deleting
```

Important CSV troubleshooting areas:

- Requirements not met
- APIService unavailable
- CRD conflict
- Deployment missing
- Deployment unavailable
- ServiceAccount missing
- Permission denied
- Webhook unavailable
- Install strategy failure

### 9.4 OperatorGroup

An `OperatorGroup` defines the target namespaces an Operator watches.

Useful commands:

```bash
oc get operatorgroup -n <ns>
oc describe operatorgroup <name> -n <ns>
oc get operatorgroup <name> -n <ns> -o yaml
```

Common issue:

```text
Operator installed in namespace A, but expected to manage namespace B.
```

Check Operator logs for namespace watching messages.

## 10. Cluster Operator Log Troubleshooting

Cluster Operators expose high-level health through `oc get co`.

Example:

```bash
oc get co
```

Output example:

```text
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
ingress          4.x       True        False         True       20m     The "default" ingress controller reports Degraded=True
```

### 10.1 Investigate a Degraded Cluster Operator

```bash
oc describe co ingress
```

Check:

- Conditions
- Message
- Reason
- Related objects
- Versions

Then locate pods:

```bash
oc get pods -A | grep ingress-operator
oc get pods -n openshift-ingress-operator
```

Check logs:

```bash
oc logs -n openshift-ingress-operator deploy/ingress-operator --since=1h --timestamps
```

Check operand namespace:

```bash
oc get pods -n openshift-ingress
oc describe ingresscontroller default -n openshift-ingress-operator
```

### 10.2 Cluster Operator Condition Meaning

| Condition | Meaning | Log Action |
|---|---|---|
| `Available=False` | Operator or operand is not healthy enough to serve | Check Operator pod logs and operand pods |
| `Progressing=True` | Operator is applying changes or upgrade | Check logs for rollout, version, desired/current state |
| `Degraded=True` | Operator found a fault | `oc describe co`, then logs from related namespace |
| `Upgradeable=False` | Cluster update is blocked | Check message, Operator logs, and CVO status |

### 10.3 CVO Logs

When an upgrade is stuck, check Cluster Version Operator logs:

```bash
oc get pods -n openshift-cluster-version
oc logs -n openshift-cluster-version deploy/cluster-version-operator --since=2h --timestamps
oc describe clusterversion version
```

Check:

```bash
oc get clusterversion
oc describe clusterversion version
oc get co
```

CVO logs help identify which Cluster Operator blocks an upgrade.

## 12. Operator Logs During Installation Failure

### Scenario

Operator installation fails from OperatorHub.

### Troubleshooting

```bash
NS=<operator-namespace>

oc get sub -n $NS
oc describe sub <subscription> -n $NS

oc get ip -n $NS
oc describe ip <installplan> -n $NS

oc get csv -n $NS
oc describe csv <csv> -n $NS

oc get pods -n $NS
oc get events -n $NS --sort-by=.lastTimestamp
```

Then check OLM logs:

```bash
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator --since=30m --timestamps
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator --since=30m --timestamps
```

If catalog issue:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalog> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc logs -n openshift-marketplace <catalog-pod>
```

### Common Root Causes

| Symptom | Likely Cause | Where to Check |
|---|---|---|
| `ResolutionFailed` | Dependency, package, channel, catalog issue | Subscription, catalog-operator logs |
| `InstallPlanPending` | Manual approval required | InstallPlan |
| `InstallPlanFailed` | Resource creation failure | InstallPlan, OLM logs, events |
| CSV `Pending` | Requirements not met | CSV describe |
| CSV `Failed` | Install strategy failed | CSV describe, OLM logs |
| Operator pod `ImagePullBackOff` | Registry/auth/mirror issue | Pod describe, events |
| Operator pod `CrashLoopBackOff` | Runtime/config/cert issue | Previous pod logs |

## 13. Operator Logs During Upgrade Failure

### 13.1 Automatic Approval Upgrade

If approval is automatic, OLM creates and approves the InstallPlan automatically.

Check:

```bash
oc get sub -n <ns>
oc get ip -n <ns>
oc get csv -n <ns>
oc describe sub <sub> -n <ns>
oc describe csv <new-csv> -n <ns>
```

Check logs:

```bash
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator --since=2h --timestamps
oc logs -n <operator-namespace> deploy/<operator-deployment> --since=2h --timestamps
```

### 13.2 Manual Approval Upgrade

If approval is manual:

```bash
oc get installplan -n <ns>
oc describe installplan <ip> -n <ns>
```

Approve:

```bash
oc patch installplan <ip> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

Then monitor:

```bash
watch 'oc get csv -n <ns>; oc get pods -n <ns>'
```

### 13.3 CSV Replacement Issues

Sometimes old CSV and new CSV conflict.

Check:

```bash
oc get csv -n <ns>
oc describe csv <old-csv> -n <ns>
oc describe csv <new-csv> -n <ns>
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator --since=1h
```

## 15. Operator Logs and RBAC Troubleshooting

RBAC errors are common in namespaced Operators.

### 15.1 Typical Log

```text
User "system:serviceaccount:my-operator:my-operator-controller-manager" cannot list resource "pods" in API group "" in namespace "target-ns"
```

### 15.2 Investigation

```bash
oc get sa -n my-operator
oc get role,rolebinding -n target-ns
oc get clusterrole,clusterrolebinding | grep my-operator
```

Check permission:

```bash
oc auth can-i list pods \
  --as system:serviceaccount:my-operator:my-operator-controller-manager \
  -n target-ns
```

For cluster-scoped resource:

```bash
oc auth can-i list nodes \
  --as system:serviceaccount:my-operator:my-operator-controller-manager
```

### 15.3 Common Causes

- OperatorGroup targets wrong namespace
- CSV missing required permission
- Manual RBAC deletion
- Namespace recreated without RoleBinding
- Operator installed in single namespace but expected to watch all namespaces
- ServiceAccount name changed

## 16. Operator Logs and SCC / Pod Security

OpenShift enforces security through SCC and Kubernetes pod security admission labels.

### 16.1 Typical Event

```text
Error creating: pods "example" is forbidden: unable to validate against any security context constraint
```

### 16.2 Check Events

```bash
oc get events -n <ns> --sort-by=.lastTimestamp
oc describe pod <pod> -n <ns>
```

### 16.3 Check Operator Logs

```bash
oc logs -n <operator-ns> deploy/<operator-deployment> --since=1h | grep -i forbidden
```

### 16.4 Fix Approach

Do not randomly assign `anyuid` or `privileged` SCC. First identify the required security context.

Check:

```bash
oc get pod <pod> -n <ns> -o yaml | grep -A20 securityContext
oc get sa -n <ns>
```

If product documentation requires a specific SCC:

```bash
oc adm policy add-scc-to-user <scc-name> -z <serviceaccount> -n <namespace>
```

For exam/lab environments, you may be asked to use `anyuid`:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

In production, follow vendor documentation and security policy.

## 26. Log Collection Script for Operator Troubleshooting

Use this as a safe starting point. Adjust namespace and names.

```bash
#!/bin/bash
set -euo pipefail

NS="${1:-}"
OPERATOR_DEPLOY="${2:-}"

if [ -z "$NS" ] || [ -z "$OPERATOR_DEPLOY" ]; then
  echo "Usage: $0 <operator-namespace> <operator-deployment>"
  exit 1
fi

OUT="operator-debug-${NS}-${OPERATOR_DEPLOY}-$(date +%F-%H%M%S)"
mkdir -p "$OUT"

echo "Collecting OLM resources..."
oc get sub -n "$NS" -o yaml > "$OUT/subscriptions.yaml" || true
oc get installplan -n "$NS" -o yaml > "$OUT/installplans.yaml" || true
oc get csv -n "$NS" -o yaml > "$OUT/csvs.yaml" || true
oc get operatorgroup -n "$NS" -o yaml > "$OUT/operatorgroups.yaml" || true

echo "Collecting namespace resources..."
oc get all -n "$NS" -o wide > "$OUT/all.txt" || true
oc get events -n "$NS" --sort-by=.lastTimestamp > "$OUT/events.txt" || true
oc get pods -n "$NS" -o yaml > "$OUT/pods.yaml" || true
oc get deploy -n "$NS" -o yaml > "$OUT/deployments.yaml" || true

echo "Collecting Operator logs..."
oc logs -n "$NS" deploy/"$OPERATOR_DEPLOY" --all-containers=true --timestamps --since=4h > "$OUT/operator-current.log" || true
oc logs -n "$NS" deploy/"$OPERATOR_DEPLOY" --all-containers=true --timestamps --previous > "$OUT/operator-previous.log" || true

echo "Collecting OLM logs..."
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator --timestamps --since=4h > "$OUT/olm-operator.log" || true
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator --timestamps --since=4h > "$OUT/catalog-operator.log" || true
oc logs -n openshift-operator-lifecycle-manager deploy/packageserver --timestamps --since=4h > "$OUT/packageserver.log" || true

echo "Collecting cluster operator status..."
oc get co -o yaml > "$OUT/clusteroperators.yaml" || true
oc get clusterversion -o yaml > "$OUT/clusterversion.yaml" || true

tar czf "$OUT.tar.gz" "$OUT"
echo "Created $OUT.tar.gz"
```

Run:

```bash
chmod +x collect-operator-debug.sh
./collect-operator-debug.sh <operator-namespace> <operator-deployment>
```

## 28. Production Best Practices

### 28.1 Always Capture Before Restarting

Before restarting Operator pods, collect:

```bash
oc logs --previous
oc describe pod
oc get events
oc describe csv
oc describe sub
```

Restarting may remove useful failure context.

### 28.2 Use Time Windows

During incidents, reduce noise:

```bash
oc logs -n <ns> deploy/<operator> --since=30m --timestamps
```

### 28.3 Correlate with Change Time

Ask:

```text
What changed before the logs started showing errors?
```

Check:

- Operator upgrade
- Cluster upgrade
- Catalog update
- GitOps sync
- Certificate rotation
- Pull secret update
- Proxy change
- NetworkPolicy change
- StorageClass change
- Node reboot
- Namespace deletion/recreation

### 28.4 Do Not Edit Operator-managed Objects Blindly

If a resource has owner references controlled by an Operator, manual changes may be reverted.

Check:

```bash
oc get <resource> <name> -n <ns> -o yaml | grep -A10 ownerReferences
```

Fix the source custom resource, not only the generated resource.

### 28.5 Avoid Random Pod Deletion

Deleting Operator pods may trigger recovery, but it can also hide the real cause. Use it only after collecting logs.

### 28.6 Watch Status Conditions

Most Operators expose conditions in custom resources:

```bash
oc get <kind> <name> -n <ns> -o yaml | yq '.status.conditions'
```

If `yq` is unavailable:

```bash
oc get <kind> <name> -n <ns> -o yaml | grep -A30 conditions:
```

### 28.7 Understand Operator Ownership

Operator ownership chain:

```text
Subscription owns upgrade intent
InstallPlan owns install action
CSV owns Operator deployment metadata
Operator deployment runs controller
Custom Resource defines operand desired state
Operand resources implement actual workload
```

Troubleshooting logs without understanding this chain leads to wrong conclusions.

## 29. Common Mistakes

### Mistake 1: Checking Only Operand Logs

Operand logs show application failure, but Operator logs show why the application was configured that way.

### Mistake 2: Checking Only Operator Logs

Operator logs may show it created a Deployment successfully, but pod events may show SCC, PVC, or image pull failure.

### Mistake 3: Ignoring `oc describe csv`

For OLM-managed Operators, CSV status often gives the cleanest lifecycle error.

### Mistake 4: Confusing Cluster Operators with OLM Operators

Cluster Operators normally do not have `Subscription` objects. Do not waste time searching for a subscription for core platform Operators.

### Mistake 5: Not Using `--previous`

For `CrashLoopBackOff`, current logs may be empty. Use:

```bash
oc logs <pod> -n <ns> --previous
```

### Mistake 6: Ignoring CatalogSource Health

If dependency resolution fails, catalog health matters as much as the target Operator.

### Mistake 7: Deleting Finalizers Without Understanding

Removing finalizers may orphan external resources or leave broken state.

### Mistake 8: Not Checking Events

Many Operator-related failures are clearer in events than logs.

## 30. Exam and Interview-Oriented Summary

For Advanced OpenShift Administration, explain Operator logs like this:

```text
Operator logs are the controller logs generated by Operator pods. They show reconciliation activity, lifecycle errors, RBAC failures, webhook problems, certificate issues, and operand creation failures. In OpenShift, I first identify whether the issue is with a CVO-managed Cluster Operator or an OLM-managed application Operator. For Cluster Operators, I start with oc get co and oc describe co, then inspect logs from the related openshift-* operator namespace. For OLM-managed Operators, I follow the lifecycle chain: Subscription, InstallPlan, CSV, Operator pod, custom resource, and operand pods. I also check CatalogSource health and OLM component logs such as catalog-operator and olm-operator. For CrashLoopBackOff, I use oc logs --previous. For support cases, I collect oc adm must-gather along with specific Operator logs, events, CSV, subscription, install plan, and catalog source YAML.
```

## 32. Final Senior-Level Mindset

Operator logs are not just text output. They are the operational record of the reconciliation engine.

When troubleshooting Operators, always correlate:

```text
Desired state → OLM lifecycle state → Operator reconcile logs → Kubernetes events → Operand status → Cluster health
```

The best OpenShift administrators do not simply ask, “What does the pod log say?” They ask:

```text
Which controller owns this resource?
What was the desired state?
What did OLM install?
What did the CSV create?
What did the Operator reconcile?
What did Kubernetes reject?
What did the operand report?
What changed recently?
```

That is how Operator logs should be used in real Advanced OpenShift Administration.
