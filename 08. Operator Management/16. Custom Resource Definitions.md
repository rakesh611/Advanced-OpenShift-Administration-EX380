## 1. Executive Summary

A **Custom Resource Definition (CRD)** extends the Kubernetes/OpenShift API by adding a new resource type. After a CRD is created, the cluster API server exposes a new REST endpoint under `/apis/<group>/<version>/...`, and users can create objects of that new type just like they create Pods, Deployments, Routes, Secrets, or ConfigMaps.

In Operator Management, CRDs are extremely important because Operators usually work like this:

1. The Operator package installs one or more CRDs.
2. Users create **Custom Resources (CRs)** based on those CRDs.
3. The Operator watches those CRs.
4. The Operator reconciles real infrastructure or Kubernetes objects to match the desired state described in the CR.

For example:

| Operator | CRD | Custom Resource | What the Operator Does |
|---|---|---|---|
| OpenShift Logging Operator | `ClusterLogForwarder` / `ClusterLogging` | `ClusterLogForwarder` CR | Builds log pipelines |
| Loki Operator | `LokiStack` | `LokiStack` CR | Deploys Loki components |
| cert-manager Operator | `Certificate`, `Issuer`, `ClusterIssuer` | Certificate CR | Issues and renews certs |
| File Integrity Operator | `FileIntegrity` | FileIntegrity CR | Monitors node file integrity |
| Prometheus Operator | `ServiceMonitor`, `PrometheusRule` | ServiceMonitor CR | Configures monitoring discovery and alerts |

Think of a CRD as the **API contract**. Think of a CR as the **desired state document**. Think of the Operator as the **controller that makes reality match the desired state**.

For an experienced OpenShift administrator, CRDs are not just YAML objects. They affect:

- API discovery
- RBAC
- OLM dependency resolution
- Operator upgrades
- schema compatibility
- application lifecycle
- etcd storage
- backup/restore
- troubleshooting
- multi-tenancy
- cluster security

A bad CRD upgrade can break an Operator. A missing CRD can block a CSV. A wrong schema can reject user resources. A broken conversion webhook can make existing resources unreadable. A dangling finalizer can block CR deletion. A broad RBAC rule on a CRD can expose sensitive platform configuration.

## 2. What Problem CRDs Solve

Kubernetes provides built-in resources such as:

- `Pod`
- `Service`
- `Deployment`
- `ConfigMap`
- `Secret`
- `Ingress`
- `PersistentVolumeClaim`
- `RoleBinding`

But real platforms need more domain-specific objects:

- `KafkaCluster`
- `PostgresCluster`
- `BackupSchedule`
- `LokiStack`
- `ServiceMonitor`
- `ArgoCD`
- `TektonPipeline`
- `ImageDigestMirrorSet`
- `FileIntegrity`
- `MachineConfig`
- `OperatorGroup`

Instead of asking users to manually create 20 Deployments, 10 Services, ConfigMaps, PVCs, Roles, NetworkPolicies, and Secrets, a CRD allows the platform to expose a clean declarative API:

```yaml
apiVersion: database.example.com/v1
kind: PostgresCluster
metadata:
  name: finance-db
  namespace: finance
spec:
  replicas: 3
  storage:
    size: 200Gi
  backup:
    enabled: true
    schedule: "0 2 * * *"
```

The user declares **what** they want. The Operator decides **how** to create it, update it, monitor it, repair it, and report status.

This is why CRDs are central to Operators.

## 3. CRD vs CR vs Operator

### 3.1 CRD: Custom Resource Definition

The CRD defines the API type itself.

Example:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.platform.example.com
spec:
  group: platform.example.com
  scope: Namespaced
  names:
    plural: backups
    singular: backup
    kind: Backup
    shortNames:
    - bkp
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
```

This tells the API server:

> “Expose a new resource called `backups.platform.example.com` with kind `Backup`.”

After that, the API server accepts:

```bash
oc get backups
oc get backup
oc explain backup.spec
oc create -f backup.yaml
```

### 3.2 CR: Custom Resource

The CR is an actual object created from the CRD.

```yaml
apiVersion: platform.example.com/v1
kind: Backup
metadata:
  name: nightly-db-backup
  namespace: prod
spec:
  schedule: "0 1 * * *"
  retentionDays: 14
```

This is the desired state.

### 3.3 Operator

The Operator is a controller that watches the CR and acts on it.

For example, when it sees:

```yaml
spec:
  schedule: "0 1 * * *"
  retentionDays: 14
```

it may create:

- CronJob
- Secret
- ServiceAccount
- RoleBinding
- PVC
- backup job
- status condition

### 3.4 Simple Analogy

| Concept | Analogy |
|---|---|
| CRD | Form template / API contract |
| CR | Filled form / desired request |
| Operator | Skilled engineer who reads the request and performs work |
| Status | Engineer’s progress report |
| Finalizer | Cleanup checklist before deletion |
| Schema | Rules that validate form fields |

## 4. Where CRDs Fit in OpenShift Operator Management

OpenShift ships with many Operators and Operator-managed APIs. Some are cluster operators that manage the OpenShift platform itself. Others are installed through OperatorHub using OLM.

In Operator Management, CRDs appear in these areas:

### 4.1 OLM-managed Operators

When you install an Operator from OperatorHub, OLM usually creates:

- `Subscription`
- `InstallPlan`
- `ClusterServiceVersion` / CSV
- Operator Deployment
- ServiceAccount
- Roles / ClusterRoles
- RoleBindings / ClusterRoleBindings
- CRDs owned by the Operator
- Sometimes webhooks, services, and related objects

The CRD is usually installed before the Operator starts serving its domain logic.

### 4.2 ClusterServiceVersion Metadata

The CSV declares:

- CRDs the Operator **owns**
- CRDs the Operator **requires**
- install modes
- RBAC permissions
- deployment strategy
- owned API descriptions shown in the console

This is why a CSV can fail if a required CRD is missing.

### 4.3 OperatorHub UI

In the OpenShift web console, the **Installed Operators** page often shows CRDs as “Provided APIs”. When you click an Operator, you usually see custom resource kinds that the Operator exposes.

Example:

- Installed Operator: File Integrity Operator
- Provided API: `FileIntegrity`
- User creates a `FileIntegrity` custom resource

### 4.4 OpenShift Native APIs Are Also Often CRD-based

OpenShift itself uses many API extensions. Some are CRDs, while others are aggregated APIs or native API groups. Examples you commonly inspect as an admin:

```bash
oc api-resources | grep operator
oc get crd | grep openshift
oc get crd | grep monitoring
oc get crd | grep loki
```

## 5. CRD API Anatomy

A CRD object has this broad structure:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: <plural>.<group>
spec:
  group: <api-group>
  scope: Namespaced | Cluster
  names:
    plural: <plural-name>
    singular: <singular-name>
    kind: <KindName>
    listKind: <KindName>List
    shortNames:
    - <short>
    categories:
    - <category>
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
    subresources:
      status: {}
      scale: {}
    additionalPrinterColumns: []
status:
  conditions: []
  acceptedNames: {}
  storedVersions: []
```

### 5.1 `metadata.name`

CRD name must be:

```text
<plural>.<group>
```

Example:

```yaml
metadata:
  name: backups.platform.example.com
```

If `spec.names.plural` is `backups` and `spec.group` is `platform.example.com`, then `metadata.name` must be:

```text
backups.platform.example.com
```

Wrong example:

```yaml
metadata:
  name: backup.platform.example.com   # wrong if plural is backups
```

This causes validation failure.

### 5.2 `spec.group`

API group is the logical namespace for the API.

Examples:

```text
monitoring.coreos.com
operators.coreos.com
logging.openshift.io
loki.grafana.com
machineconfiguration.openshift.io
platform.example.com
```

Good API group names should be DNS-style and owned by your organization.

Avoid generic groups like:

```text
apps.com
operator.io
example.com
```

unless you really control and intend them.

### 5.3 `spec.scope`

Two choices:

```yaml
scope: Namespaced
```

or:

```yaml
scope: Cluster
```

Namespaced CRs live in a namespace:

```bash
oc get backups -n finance
```

Cluster-scoped CRs are global:

```bash
oc get clusterbackups
```

### 5.4 `spec.names`

Example:

```yaml
names:
  plural: backups
  singular: backup
  kind: Backup
  listKind: BackupList
  shortNames:
  - bkp
  categories:
  - all
```

This controls CLI behavior:

```bash
oc get backups
oc get backup
oc get bkp
oc get all
```

Be careful with categories. Adding a CRD to `all` can make `oc get all` noisy.

### 5.5 `spec.versions`

Example:

```yaml
versions:
- name: v1alpha1
  served: true
  storage: false
- name: v1beta1
  served: true
  storage: false
- name: v1
  served: true
  storage: true
```

Important fields:

| Field | Meaning |
|---|---|
| `name` | Version name such as `v1alpha1`, `v1beta1`, `v1` |
| `served` | API server accepts requests for this version |
| `storage` | API server stores objects in etcd using this version |
| `schema` | OpenAPI v3 validation schema |
| `subresources` | Enables `/status` and `/scale` |
| `additionalPrinterColumns` | Extra columns in `oc get` |

Only one version can have:

```yaml
storage: true
```

Multiple versions can have:

```yaml
served: true
```

### 5.6 `status.conditions`

Common CRD conditions:

| Condition | Meaning |
|---|---|
| `Established` | API endpoint is ready |
| `NamesAccepted` | Resource names do not conflict |
| `Terminating` | CRD is being deleted |

Check:

```bash
oc describe crd backups.platform.example.com
oc get crd backups.platform.example.com -o jsonpath='{.status.conditions}' | jq
```

## 6. How the Kubernetes API Server Handles CRDs

When you create a CRD, the API server dynamically registers a new API endpoint. You do not deploy a new API server for basic CRDs.

For a namespaced CRD:

```yaml
spec:
  group: platform.example.com
  names:
    plural: backups
  scope: Namespaced
  versions:
  - name: v1
```

The API path becomes:

```text
/apis/platform.example.com/v1/namespaces/<namespace>/backups
```

For a cluster-scoped CRD:

```text
/apis/platform.example.com/v1/clusterbackups
```

### 6.1 CRD Storage

CR instances are stored in etcd by the Kubernetes API server. The Operator does not usually store CR objects itself. It watches them through the API.

Important consequence:

- CRDs and CRs are part of cluster state.
- They must be considered in backup/restore.
- Large CR objects increase API server and etcd pressure.
- CRDs should not be used as a high-volume event database.

### 6.2 CRD Is Not the Controller

A CRD only creates the API. It does not automatically create Pods, Services, Routes, PVCs, or cloud resources.

This command may succeed:

```bash
oc apply -f backup-cr.yaml
```

But nothing useful happens unless a controller/Operator watches that CR.

### 6.3 What Happens When the Operator Is Down

If the Operator pod is down:

- Existing CRDs remain registered.
- Users can still create/update/delete CRs if RBAC allows it.
- Status may become stale.
- Desired state might not be reconciled.
- Deletion can hang if finalizers require the Operator to perform cleanup.

Check:

```bash
oc get pods -n <operator-namespace>
oc logs deploy/<operator-deployment> -n <operator-namespace>
oc get <custom-resource-kind> -A
```

## 7. Namespaced vs Cluster-scoped CRDs

Choosing scope is a major design and operations decision.

### 7.1 Namespaced CRD

Example:

```yaml
spec:
  scope: Namespaced
```

Users create CRs in namespaces:

```bash
oc create -f backup.yaml -n finance
oc get backups -n finance
```

Good for:

- tenant-owned resources
- application-level resources
- namespace-level self-service
- dev/test/prod isolation
- RBAC delegation

Examples:

- `ServiceMonitor` in a namespace
- `KafkaTopic` in a namespace
- `Backup` for one app namespace

### 7.2 Cluster-scoped CRD

Example:

```yaml
spec:
  scope: Cluster
```

Users create CRs globally:

```bash
oc get clusterissuers
oc get ingresscontrollers.operator.openshift.io
```

Good for:

- cluster-wide configuration
- infrastructure configuration
- global policies
- cluster-level Operators

Examples:

- `ClusterIssuer`
- `IngressController`
- `ImageDigestMirrorSet`
- `ClusterLogForwarder` in newer cluster-scoped designs

### 7.3 Admin Decision Matrix

| Requirement | Prefer Namespaced | Prefer Cluster-scoped |
|---|---:|---:|
| Tenant self-service | Yes | No |
| Namespace RBAC delegation | Yes | No |
| Global cluster config | No | Yes |
| One object controls many namespaces | Maybe | Yes |
| Sensitive infrastructure setting | No | Yes |
| Easy project cleanup | Yes | No |
| Multi-tenant isolation | Yes | Usually no |

### 7.4 Common Mistake

Creating cluster-scoped CRDs for tenant workloads makes RBAC and multi-tenancy harder. Users may need cluster-level permissions, which platform teams usually do not want to grant.

```bash
oc get crd
```

Filter by group:

```bash
oc get crd | grep monitoring.coreos.com
oc get crd | grep operators.coreos.com
oc get crd | grep logging
```

### 8.2 List API Resources

```bash
oc api-resources
```

Filter:

```bash
oc api-resources | grep -i backup
oc api-resources --api-group=platform.example.com
oc api-resources --namespaced=true
oc api-resources --namespaced=false
```

Useful output columns:

```text
NAME      SHORTNAMES   APIVERSION                  NAMESPACED   KIND
backups   bkp          platform.example.com/v1      true         Backup
```

### 8.3 Explain a Custom Resource

```bash
oc explain backup
oc explain backup.spec
oc explain backup.spec.schedule
```

If schema is well-defined, `oc explain` becomes useful. If the CRD has a poor schema, `oc explain` will be weak or nearly useless.

### 8.4 Get CRD Details

```bash
oc describe crd backups.platform.example.com
```

Important fields:

- Group
- Kind
- Names
- Scope
- Versions
- Served/storage version
- Conditions
- Stored versions
- Printer columns

### 8.5 Get Custom Resources

```bash
oc get backups -n finance
oc get backup nightly-db-backup -n finance -o yaml
oc get backups -A
```

### 8.6 Use Fully Qualified Resource Name

When names conflict:

```bash
oc get backups.platform.example.com -A
```

This avoids ambiguity.

### 8.7 Raw API Discovery

```bash
oc get --raw /apis | jq
oc get --raw /apis/platform.example.com/v1 | jq
```

This helps when CLI discovery is stale or confusing.

## 9. Schema Validation and Structural Schemas

In `apiextensions.k8s.io/v1`, CRDs should define an OpenAPI v3 schema.

Example:

```yaml
schema:
  openAPIV3Schema:
    type: object
    required:
    - spec
    properties:
      spec:
        type: object
        required:
        - schedule
        properties:
          schedule:
            type: string
          retentionDays:
            type: integer
            minimum: 1
            maximum: 365
```

### 9.1 Why Schema Matters

Schema controls:

- API validation
- field pruning
- `oc explain`
- server-side apply behavior
- compatibility checks during upgrade
- safe CRD evolution

Without schema discipline, you get fragile APIs.

### 9.2 Example Validation Failure

CR:

```yaml
apiVersion: platform.example.com/v1
kind: Backup
metadata:
  name: bad-backup
spec:
  retentionDays: -1
```

Expected error:

```text
spec.retentionDays: Invalid value: -1: spec.retentionDays in body should be greater than or equal to 1
```

### 9.3 Required Fields

```yaml
required:
- spec
properties:
  spec:
    type: object
    required:
    - schedule
```

This means `.spec.schedule` must exist.

### 9.4 Enum Fields

```yaml
mode:
  type: string
  enum:
  - Full
  - Incremental
  - Snapshot
```

Good for fields where only certain values are valid.

### 9.5 Numeric Bounds

```yaml
retentionDays:
  type: integer
  minimum: 1
  maximum: 365
```

### 9.6 String Pattern

```yaml
schedule:
  type: string
  pattern: '^(@(hourly|daily|weekly)|([0-9*/,-]+\s+){4}[0-9*/,-]+)$'
```

Be careful. Overly strict patterns can block legitimate future use cases.

### 9.7 Object Fields

```yaml
storage:
  type: object
  required:
  - size
  properties:
    size:
      type: string
      pattern: '^[0-9]+(Gi|Mi|Ti)$'
    storageClassName:
      type: string
```

### 9.8 Array Fields

```yaml
targets:
  type: array
  items:
    type: object
    required:
    - name
    - namespace
    properties:
      name:
        type: string
      namespace:
        type: string
```

### 9.9 Preserve Unknown Fields

In modern CRDs, unknown fields are generally pruned unless explicitly preserved in schema. This means if a user sends an unsupported field, the API server may remove it rather than store it.

Example user CR:

```yaml
spec:
  schedule: "0 1 * * *"
  unsupportedField: true
```

If the schema does not allow `unsupportedField`, it may not persist.

Check stored object:

```bash
oc get backup nightly-db-backup -n finance -o yaml
```

### 9.10 Structural Schema Concept

A structural schema means the schema follows Kubernetes rules that allow the API server to understand object structure reliably. This is important for:

- pruning
- defaulting
- validation
- server-side apply
- CRD upgrades

Production CRDs should always use clean structural schemas.

## 10. CEL Validation Rules

Kubernetes supports validation rules using Common Expression Language (CEL) in CRD schemas.

Example:

```yaml
x-kubernetes-validations:
- rule: "self.retentionDays <= 365"
  message: "retentionDays must be 365 or less"
```

More useful example:

```yaml
properties:
  spec:
    type: object
    properties:
      minReplicas:
        type: integer
        minimum: 1
      maxReplicas:
        type: integer
        minimum: 1
    x-kubernetes-validations:
    - rule: "self.maxReplicas >= self.minReplicas"
      message: "maxReplicas must be greater than or equal to minReplicas"
```

### 10.1 Why CEL Is Useful

OpenAPI schema handles simple validation:

- type
- minimum
- maximum
- pattern
- enum
- required

CEL handles relationship-based validation:

- `maxReplicas >= minReplicas`
- immutable fields after creation
- field dependency rules
- conditional requirements

### 10.2 Immutable Field Example

```yaml
x-kubernetes-validations:
- rule: "self == oldSelf"
  message: "This field is immutable"
```

Used carefully, CEL can reduce the need for validating webhooks.

### 10.3 Admin Warning

Complex CEL rules can confuse users if messages are poor. Always provide meaningful `message` fields.

Bad message:

```text
rule failed
```

Good message:

```text
maxReplicas must be greater than or equal to minReplicas
```

## 11. CRD Versioning: served, storage, conversion

CRD versioning is one of the most important advanced topics.

### 11.1 Version Names

Common patterns:

| Version | Meaning |
|---|---|
| `v1alpha1` | Experimental, may break |
| `v1beta1` | More stable, but still may change |
| `v1` | Stable public API |

### 11.2 `served`

```yaml
served: true
```

The API server accepts requests for this version.

Example:

```bash
oc get backups.v1.platform.example.com
```

or object:

```yaml
apiVersion: platform.example.com/v1
```

If `served: false`, users cannot use that version through the API, but old stored objects may still exist internally until migrated.

### 11.3 `storage`

```yaml
storage: true
```

This version is used to persist objects in etcd.

Only one version can be storage at a time.

### 11.4 Multiple Version Example

```yaml
versions:
- name: v1alpha1
  served: true
  storage: false
  schema:
    openAPIV3Schema:
      type: object
- name: v1beta1
  served: true
  storage: true
  schema:
    openAPIV3Schema:
      type: object
```

Users can create both:

```yaml
apiVersion: platform.example.com/v1alpha1
```

and:

```yaml
apiVersion: platform.example.com/v1beta1
```

But etcd stores the object in the storage version.

### 11.5 `status.storedVersions`

Check stored versions:

```bash
oc get crd backups.platform.example.com -o jsonpath='{.status.storedVersions}'
```

Example:

```text
["v1alpha1","v1beta1"]
```

This means objects have historically been stored in those versions.

### 11.6 Version Migration

Changing storage version does not always automatically rewrite every existing object immediately. Existing objects may remain stored in older versions until read/write migration or storage version migration happens.

Common admin approach:

```bash
for ns in $(oc get ns -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  oc get backups -n "$ns" -o name 2>/dev/null | while read obj; do
    oc get "$obj" -n "$ns" -o yaml | oc apply -f -
  done
done
```

Use caution. For large clusters, do this with proper planning.

### 11.7 Conversion Strategy: None

```yaml
conversion:
  strategy: None
```

With `None`, conversion is only basic API version conversion. The schema between versions must be compatible enough that the same object shape works.

### 11.8 Conversion Strategy: Webhook

```yaml
conversion:
  strategy: Webhook
  webhook:
    conversionReviewVersions:
    - v1
    clientConfig:
      service:
        namespace: backup-operator-system
        name: backup-conversion-webhook
        path: /convert
        port: 443
      caBundle: <base64-ca>
```

A conversion webhook transforms objects between versions.

Example transformation:

`v1alpha1`:

```yaml
spec:
  schedule: daily
```

`v1`:

```yaml
spec:
  schedule:
    type: Cron
    expression: "0 1 * * *"
```

### 11.9 Conversion Webhook Risks

If the conversion webhook is broken:

- API reads may fail.
- `oc get` may fail.
- Operator reconciliation may fail.
- CRD upgrades may fail.
- Users may be unable to list or update CRs.

Common errors:

```text
conversion webhook for platform.example.com/v1 failed
service "backup-conversion-webhook" not found
x509: certificate signed by unknown authority
context deadline exceeded
```

Troubleshoot:

```bash
oc get svc -n backup-operator-system
oc get endpoints backup-conversion-webhook -n backup-operator-system
oc get pods -n backup-operator-system
oc logs deploy/backup-operator-controller-manager -n backup-operator-system
oc describe crd backups.platform.example.com
```

## 12. Status and Scale Subresources

### 12.1 Status Subresource

Enable:

```yaml
subresources:
  status: {}
```

This creates a `/status` endpoint.

Normal users update desired state:

```text
PUT /apis/platform.example.com/v1/namespaces/finance/backups/nightly-db-backup
```

The Operator updates observed state:

```text
PUT /apis/platform.example.com/v1/namespaces/finance/backups/nightly-db-backup/status
```

### 12.2 Why `/status` Matters

It separates:

| Field | Owner |
|---|---|
| `.spec` | User / GitOps / admin |
| `.status` | Controller / Operator |

Users should not manually edit `.status` in normal operations.

Example status:

```yaml
status:
  phase: Ready
  lastBackupTime: "2026-07-03T01:00:00Z"
  conditions:
  - type: Ready
    status: "True"
    reason: BackupCompleted
    message: Latest backup completed successfully
    lastTransitionTime: "2026-07-03T01:05:00Z"
```

### 12.3 RBAC for Status

Operators often need permission like:

```yaml
- apiGroups:
  - platform.example.com
  resources:
  - backups/status
  verbs:
  - get
  - patch
  - update
```

If missing, Operator logs may show:

```text
backups.platform.example.com "nightly-db-backup" is forbidden: User "system:serviceaccount:..." cannot update resource "backups/status"
```

### 12.4 Scale Subresource

The `/scale` subresource lets HPA and `oc scale` work with a custom resource.

Example:

```yaml
subresources:
  scale:
    specReplicasPath: .spec.replicas
    statusReplicasPath: .status.replicas
    labelSelectorPath: .status.selector
```

Then:

```bash
oc scale myapps.platform.example.com frontend --replicas=5 -n prod
```

or HPA can target it if the CRD supports scale properly.

### 12.5 Scale Subresource Requirements

- `.spec.replicas` must exist and be integer.
- `.status.replicas` should be updated by the controller.
- `.status.selector` should represent target pod labels if used by autoscaling.

## 14. Finalizers, Owner References, and Garbage Collection

### 14.1 Finalizers

A finalizer blocks deletion until cleanup is complete.

Example CR:

```yaml
metadata:
  finalizers:
  - backups.platform.example.com/finalizer
```

When a user deletes the CR:

```bash
oc delete backup nightly-db-backup -n finance
```

Kubernetes sets:

```yaml
metadata:
  deletionTimestamp: "2026-07-03T10:00:00Z"
```

but does not remove the object until finalizers are cleared.

The Operator should:

1. detect deletion timestamp
2. clean external resources
3. remove finalizer

### 14.2 Stuck Finalizer

If the Operator is down or buggy, deletion may hang:

```bash
oc get backup nightly-db-backup -n finance -o yaml | grep -A5 finalizers
```

Emergency removal:

```bash
oc patch backup nightly-db-backup -n finance --type=merge -p '{"metadata":{"finalizers":[]}}'
```

Warning: removing finalizers can orphan external resources.

### 14.3 Owner References

Operators often create child resources with owner references pointing to the CR.

Example child Deployment:

```yaml
metadata:
  ownerReferences:
  - apiVersion: platform.example.com/v1
    kind: Backup
    name: nightly-db-backup
    uid: <uid>
```

When the CR is deleted, Kubernetes garbage collection can delete owned child objects.

### 14.4 Cross-namespace Owner Reference Problem

Kubernetes owner references are namespace-sensitive:

- Namespaced object can own namespaced objects in the same namespace.
- Cluster-scoped owner can own cluster-scoped and namespaced dependents.
- Cross-namespace owner references are not valid for garbage collection.

Operators should handle cross-namespace cleanup explicitly.

## 16. CRDs Inside OLM: CSV, Subscription, InstallPlan, OperatorGroup

### 16.1 OLM Objects Review

| Object | Purpose |
|---|---|
| `CatalogSource` | Source of Operator metadata/bundles |
| `Subscription` | User intent to install/track an Operator channel |
| `InstallPlan` | Concrete plan of resources OLM will create/update |
| `ClusterServiceVersion` | Metadata and installation definition for one Operator version |
| `OperatorGroup` | Defines target namespaces for an Operator |
| `CRD` | API types owned/required by the Operator |

### 16.2 Installation Flow

Typical flow:

1. Admin creates OperatorGroup.
2. Admin creates Subscription.
3. OLM resolves dependencies.
4. OLM creates InstallPlan.
5. InstallPlan creates CRDs, RBAC, ServiceAccounts, Deployments, CSV.
6. CSV moves through phases.
7. Operator pod starts.
8. Users create CRs.
9. Operator reconciles CRs.

### 16.3 CSV Phases

Check:

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
```

Common phases:

| Phase | Meaning |
|---|---|
| `Pending` | Waiting for requirements |
| `InstallReady` | Ready to install |
| `Installing` | Creating resources |
| `Succeeded` | Operator installed successfully |
| `Failed` | Install or requirement failed |
| `Replacing` | Being replaced by newer CSV |

### 16.4 CRDs in InstallPlan

```bash
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
```

Look for CRD resources in the plan.

Example:

```text
Resource: backups.platform.example.com
Kind: CustomResourceDefinition
Status: Created
```

### 16.5 CRD and OperatorGroup Relationship

OperatorGroup affects which namespaces the Operator watches. It does not change whether a CRD is cluster-scoped or namespaced.

Important distinction:

| Concept | Controls |
|---|---|
| CRD `.spec.scope` | Whether CR instances are namespaced or cluster-scoped |
| OperatorGroup | Which namespaces the Operator is configured to watch |
| RBAC | Who can create/read/update/delete CRs |

A namespaced CRD can exist cluster-wide, but the Operator may only watch a subset of namespaces.

## 17. Owned CRDs vs Required CRDs

In CSV metadata, Operators can declare CRDs as:

- **owned**
- **required**

### 17.1 Owned CRDs

Owned CRDs are provided by the Operator.

Example concept:

```yaml
customresourcedefinitions:
  owned:
  - name: backups.platform.example.com
    version: v1
    kind: Backup
    displayName: Backup
    description: Backup config managed by Backup Operator
```

This means:

- The Operator owns this API.
- OLM may install or upgrade the CRD as part of the Operator.
- The OpenShift console can show it as a Provided API.

### 17.2 Required CRDs

Required CRDs are dependencies.

Example:

```yaml
customresourcedefinitions:
  required:
  - name: servicemonitors.monitoring.coreos.com
    version: v1
    kind: ServiceMonitor
```

This means:

- The Operator expects this CRD to already exist or be provided by another Operator.
- OLM dependency resolution may block installation if the requirement is not satisfied.

### 17.3 Practical Example

A database Operator may own:

```text
postgresclusters.database.example.com
backups.database.example.com
```

It may require:

```text
servicemonitors.monitoring.coreos.com
prometheusrules.monitoring.coreos.com
```

because it integrates with Prometheus Operator.

### 17.4 Troubleshooting Required CRD Failure

CSV message may show:

```text
requirements not met: no operators found providing ServiceMonitor.monitoring.coreos.com/v1
```

Check:

```bash
oc get crd servicemonitors.monitoring.coreos.com
oc get csv -A | grep prometheus
oc describe csv <csv> -n <operator-ns>
```

Fix by installing the dependency Operator or choosing a compatible Operator channel.

## 18. CRD Upgrade Behavior in OLM

CRD upgrades are sensitive because CRDs are cluster-level APIs that may have many existing CRs.

### 18.1 Single Owner Case

If a CRD is owned by a single CSV, OLM can upgrade that CRD as part of the Operator upgrade.

### 18.2 Multiple Owner Case

If multiple CSVs own the same CRD, OLM applies safer checks. The new CRD must be backward compatible with existing serving versions and existing CR instances must validate against the new schema.

This avoids breaking another Operator or existing CRs.

### 18.3 Why Existing CRs Matter

Suppose old schema allowed:

```yaml
spec:
  retentionDays: 999
```

New schema says:

```yaml
retentionDays:
  maximum: 365
```

Existing CRs with `999` may block the CRD upgrade because they would be invalid under the new schema.

### 18.4 Admin Pre-upgrade Check

Before upgrading an Operator:

```bash
oc get subscription -n <operator-ns>
oc get csv -n <operator-ns>
oc get installplan -n <operator-ns>
oc get crd <crd-name> -o yaml > crd-before.yaml
oc get <custom-resource> -A -o yaml > crs-before.yaml
```

Look for:

- deprecated API versions
- invalid CR values
- old storage versions
- conversion webhook dependencies
- multiple CSVs owning same CRD

### 18.5 Manual Approval Strategy

For production Operators, prefer manual InstallPlan approval when CRD upgrades are risky:

```yaml
spec:
  installPlanApproval: Manual
```

Then:

```bash
oc get installplan -n <operator-ns>
oc describe installplan <name> -n <operator-ns>
oc patch installplan <name> -n <operator-ns> --type merge -p '{"spec":{"approved":true}}'
```

### 18.6 CRD Upgrade Failure Symptoms

```text
InstallPlanFailed
error validating existing CRs against new CRD schema
risk of data loss
requirements not met
no operators found providing required API
```

### 18.7 Safe Upgrade Sequence

1. Read Operator release notes.
2. Export current CRDs and CRs.
3. Check stored versions.
4. Validate existing CRs against expected new schema if possible.
5. Ensure dependency Operators are healthy.
6. Approve InstallPlan during maintenance window.
7. Watch CSV phase.
8. Watch Operator logs.
9. Confirm CR status conditions.
10. Keep rollback/restore plan ready.

## 19. Production CRD Design Patterns

Even if you are not writing Operators, knowing good CRD design helps you judge Operator quality.

### 19.1 Spec/Status Split

Good:

```yaml
spec:
  replicas: 3
  storage:
    size: 100Gi
status:
  readyReplicas: 3
  conditions:
  - type: Ready
    status: "True"
```

Bad:

```yaml
spec:
  replicas: 3
  readyReplicas: 3   # observed state inside spec: bad design
```

### 19.2 Conditions Pattern

Use Kubernetes-style conditions:

```yaml
status:
  conditions:
  - type: Available
    status: "True"
    reason: MinimumReplicasAvailable
    message: Deployment has minimum availability
    lastTransitionTime: "2026-07-03T10:00:00Z"
```

Recommended condition fields:

- `type`
- `status`
- `reason`
- `message`
- `lastTransitionTime`
- `observedGeneration`

### 19.3 Observed Generation

`metadata.generation` increments when spec changes.

Controller should set:

```yaml
status:
  observedGeneration: 7
```

If:

```text
status.observedGeneration < metadata.generation
```

then the Operator has not reconciled the latest spec.

Check:

```bash
oc get backup nightly-db-backup -n finance -o jsonpath='{.metadata.generation}{"\n"}{.status.observedGeneration}{"\n"}'
```

### 19.4 Idempotent Reconciliation

A good Operator can run reconciliation repeatedly without causing damage.

Good behavior:

- If Deployment exists and is correct, do nothing.
- If Deployment exists but drifted, patch it.
- If Service is missing, recreate it.
- If CR is deleted, clean up safely.

### 19.5 Defaulting

Good CRDs/Operators provide reasonable defaults.

Example user CR:

```yaml
spec:
  size: small
```

Stored/defaulted CR:

```yaml
spec:
  size: small
  replicas: 1
  retentionDays: 7
```

Defaulting may be implemented through schema defaults or webhooks.

### 19.6 Backward Compatibility

Good CRD evolution:

- Add optional fields.
- Do not remove served versions abruptly.
- Do not narrow validation in a way that invalidates existing CRs without migration.
- Keep old fields until users migrate.
- Use conversion webhooks for shape changes.
- Document deprecations.

### 19.7 Meaningful Status

Bad status:

```yaml
status:
  phase: Error
```

Good status:

```yaml
status:
  phase: Degraded
  conditions:
  - type: Ready
    status: "False"
    reason: StorageClassNotFound
    message: StorageClass fast-ssd does not exist
```

### 19.8 GitOps-friendly CRDs

Good CRDs work well with Argo CD / GitOps:

- deterministic defaults
- no constant mutation of spec
- status separated
- stable field order not required
- clear health status
- predictable finalizers

## 20. Production Anti-patterns

### 20.1 Using CRDs as a Database

Bad:

- storing every metric sample as a CR
- storing every log event as a CR
- creating thousands of CRs per minute

This overloads API server and etcd.

Use proper databases, object stores, message queues, or monitoring backends.

### 20.2 No Schema

A CRD with loose schema allows invalid data and makes upgrades dangerous.

Bad:

```yaml
schema:
  openAPIV3Schema:
    type: object
    x-kubernetes-preserve-unknown-fields: true
```

Use only when truly needed.

### 20.3 Everything Cluster-scoped

Cluster-scoped APIs are harder to delegate safely.

Prefer namespaced CRDs for tenant-owned workloads.

### 20.4 Operator Mutates `.spec`

The user owns `.spec`. Operator owns `.status`.

If the Operator constantly mutates `.spec`, GitOps tools may constantly fight it.

### 20.5 Breaking Version Changes

Bad upgrade:

- remove `v1beta1` while users still use it
- change field type from string to object without conversion
- make optional field required without default/migration
- add stricter enum that invalidates existing values

### 20.6 No Finalizer Cleanup Plan

If a CR creates cloud resources or cluster-scoped resources, deletion must clean them up. But finalizers must not hang forever without clear status.

### 20.7 Poor RBAC Boundaries

Do not grant application teams broad permissions like:

```yaml
apiGroups:
- "*"
resources:
- "*"
verbs:
- "*"
```

Use least privilege.

## 22. Troubleshooting CRD Problems

### Problem 1: `no matches for kind` Error

Error:

```text
error: resource mapping not found for name: "example" namespace: "test" from "cr.yaml": no matches for kind "Backup" in version "platform.example.com/v1"
```

Meaning:

- CRD not installed
- wrong API group/version/kind
- API discovery cache stale
- CRD not established yet

Check:

```bash
oc get crd | grep backup
oc api-resources | grep -i backup
oc get crd backups.platform.example.com
oc describe crd backups.platform.example.com
```

Fix:

```bash
oc apply -f crd.yaml
# or install the Operator that owns the CRD
```

If recently installed:

```bash
sleep 10
oc api-resources | grep -i backup
```

### Problem 2: CRD Exists but Not Established

Check:

```bash
oc describe crd <crd-name>
```

Look for:

```text
Type: Established
Status: False
```

Possible causes:

- naming conflict
- invalid schema
- API server issue
- CRD being terminated

Check API server events/logs if needed:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -50
oc get pods -n openshift-kube-apiserver
```

### Problem 3: Names Not Accepted

Condition:

```text
NamesAccepted=False
```

Possible cause:

- another resource already uses same plural/singular/kind/shortName in same API group
- invalid naming

Check:

```bash
oc describe crd <crd-name>
oc api-resources | grep <name>
```

Fix CRD names.

### Problem 4: Schema Validation Rejects CR

Error:

```text
spec.retentionDays: Invalid value: 999: must be less than or equal to 365
```

Check schema:

```bash
oc get crd backups.platform.example.com -o yaml | less
oc explain backup.spec.retentionDays
```

Fix CR YAML.

### Problem 5: Unknown Field Disappears

User applies:

```yaml
spec:
  schedule: "0 1 * * *"
  myCustomField: enabled
```

Then sees field missing:

```bash
oc get backup test -o yaml
```

Cause:

- CRD schema prunes unknown fields.

Fix:

- Use supported fields.
- Update CRD schema if you own the Operator/API.
- Do not rely on unknown fields.

### Problem 6: CR Stuck Terminating

Check:

```bash
oc get <resource> <name> -n <ns> -o yaml
```

Look for:

```yaml
metadata:
  deletionTimestamp: ...
  finalizers:
  - example.com/finalizer
```

Check Operator:

```bash
oc get pods -n <operator-ns>
oc logs deploy/<operator-deployment> -n <operator-ns>
```

If emergency:

```bash
oc patch <resource> <name> -n <ns> --type=merge -p '{"metadata":{"finalizers":[]}}'
```

Warning: this may orphan resources.

### Problem 7: Cannot Delete CRD

CRD deletion can hang if CR instances exist or finalizers are present.

Check CRs:

```bash
oc get <resource> -A
```

Delete CRs first:

```bash
oc delete <resource> --all -A
```

Then delete CRD:

```bash
oc delete crd <crd-name>
```

Warning: deleting a CRD deletes all CRs for that type. Treat as destructive.

### Problem 8: Conversion Webhook Failing

Symptoms:

```bash
oc get <resource> -A
```

fails with:

```text
conversion webhook failed
service not found
x509 certificate error
context deadline exceeded
```

Check:

```bash
oc get crd <crd-name> -o yaml | yq '.spec.conversion'
oc get svc -n <webhook-namespace>
oc get endpoints -n <webhook-namespace> <webhook-service>
oc get pods -n <webhook-namespace>
oc logs -n <webhook-namespace> deploy/<operator-or-webhook-deploy>
```

Fix:

- restore webhook service
- fix endpoints
- fix CA bundle
- restart Operator/webhook
- rollback broken Operator version if necessary

### Problem 9: `oc explain` Does Not Show Fields

Cause:

- incomplete schema
- non-structural schema
- CRD lacks field descriptions

Check:

```bash
oc get crd <crd-name> -o yaml | less
```

If third-party Operator, report to vendor. If internal Operator, improve schema.

### Problem 10: API Server Slow After Installing Operator

Possible causes:

- Operator creates too many CRs
- CR objects are too large
- too many watches
- bad controller reconciliation loops
- massive status updates

Check:

```bash
oc get --raw /metrics | grep apiserver_request_total | grep <group>
oc get crd <crd-name> -o yaml
oc get <resource> -A --no-headers | wc -l
```

Also inspect Operator logs for rapid reconcile loops.


Possible causes:

- CSV did not declare owned CRD metadata properly.
- Console cache delay.
- Operator installed with unsupported install mode.
- OLM/console issue.

### Problem 6: Operator Watches Wrong Namespace

CRD exists and CR is created, but Operator ignores it.

Check OperatorGroup:

```bash
oc get operatorgroup -n <operator-ns> -o yaml
```

Check Operator env vars:

```bash
oc get deploy <operator-deploy> -n <operator-ns> -o yaml | grep -A5 WATCH_NAMESPACE
```

Fix:

- Install Operator with correct OperatorGroup.
- Use supported install mode.
- Reinstall Operator if necessary.

### Problem 7: CRD Upgrade Blocked by Existing Invalid CRs

Check all CRs:

```bash
oc get <resource> -A -o yaml > all-crs.yaml
```

Find invalid values based on new schema. Fix CRs before approving upgrade.

Example:

```bash
oc patch backup old-backup -n finance --type merge -p '{"spec":{"retentionDays":365}}'
```

Then retry/approve InstallPlan.

### Problem 8: CRD Deleted Accidentally

Symptoms:

```bash
oc get <resource>
```

returns:

```text
the server doesn't have a resource type "<resource>"
```

Impact:

- CRs for that CRD are deleted from API storage when CRD is deleted.
- Operator may crash or degrade.
- OLM may recreate CRD if still managed, but CR instances may be lost unless restored.

Response:

1. Stop further changes.
2. Check audit logs if enabled.
3. Check etcd/cluster backup availability.
4. Reinstall/reconcile Operator only if appropriate.
5. Restore CRs from GitOps or backup.

## 24. Backup, Restore, Migration, and Disaster Recovery

### 24.1 What to Back Up

For Operator-managed workloads, back up:

- CRDs
- CRs
- Operator namespace objects
- Secrets used by CRs
- ConfigMaps used by CRs
- PVC data if applicable
- external resources if Operator manages them

### 24.2 Export CRD

```bash
oc get crd backups.platform.example.com -o yaml > backups-crd.yaml
```

### 24.3 Export All CRs

```bash
oc get backups.platform.example.com -A -o yaml > backups-crs.yaml
```

### 24.4 Export by Namespace

```bash
oc get backups -n finance -o yaml > finance-backups.yaml
```

### 24.5 Restore Order

Usually:

1. Install CRDs first.
2. Install Operator and RBAC.
3. Restore Secrets/ConfigMaps.
4. Restore CRs.
5. Restore PVC/application data.
6. Watch reconciliation.

### 24.6 GitOps Recommendation

For production, store intended CRs in Git:

```text
clusters/
  prod/
    operators/
      logging/
        subscription.yaml
        operatorgroup.yaml
        clusterlogforwarder.yaml
      monitoring/
        servicemonitors.yaml
```

Do not rely only on live cluster state.

### 24.7 Disaster Recovery Warning

Restoring CRs can trigger Operators to recreate resources. Understand side effects:

- database restore jobs may run
- cloud load balancers may be created
- certificates may be reissued
- storage volumes may be provisioned
- external DNS records may change

Always test restore in non-production.

## 25. Security and Governance

### 25.1 CRDs Are API Surface Area

Every CRD expands the cluster API. It introduces:

- new permissions
- new data objects
- new watch streams
- new audit events
- new controller behavior

Treat CRDs as platform APIs.

### 25.2 Restrict CRD Creation

Only trusted admins and OLM should create CRDs.

Check who can create CRDs:

```bash
oc adm policy who-can create customresourcedefinitions.apiextensions.k8s.io
```

### 25.3 Audit CR Changes

Custom resources may contain sensitive configuration.

Examples:

- issuer references
- backup targets
- registry mirrors
- cluster policies
- endpoints
- tenant configuration

Avoid storing secret values directly in CRs. Use Secret references.

Bad:

```yaml
spec:
  password: redhat123
```

Good:

```yaml
spec:
  credentialsSecretRef:
    name: backup-credentials
```

### 25.4 RBAC Least Privilege

Give teams only the CR permissions they need.

Example view-only:

```bash
oc adm policy add-role-to-user view alice -n finance
```

But note: default `view` may or may not include specific CRD permissions depending on aggregation labels and Operator RBAC. For custom roles, explicitly define CR resources.

### 25.5 Aggregated ClusterRoles

Some Operators create ClusterRoles with labels like:

```yaml
rbac.authorization.k8s.io/aggregate-to-view: "true"
rbac.authorization.k8s.io/aggregate-to-edit: "true"
rbac.authorization.k8s.io/aggregate-to-admin: "true"
```

This can add CRD permissions into default roles.

Review:

```bash
oc get clusterrole -l rbac.authorization.k8s.io/aggregate-to-view=true
oc get clusterrole <role> -o yaml
```

### 25.6 Admission Control

For sensitive CRDs, consider:

- validating admission policies
- validating webhooks
- namespace policies
- RBAC controls
- GitOps review process

### 25.7 Supply Chain Trust

Before installing an Operator that creates CRDs:

- verify source CatalogSource
- verify vendor support
- read permissions requested by CSV
- check install modes
- review CRDs and webhooks
- understand upgrade policy

Commands:

```bash
oc describe packagemanifest <operator-package> -n openshift-marketplace
oc get csv <csv> -n <operator-ns> -o yaml
oc describe installplan <installplan> -n <operator-ns>
```

## 26. Performance and Scale Considerations

### 26.1 Number of CRDs

Many CRDs increase API discovery size. This can affect:

- CLI discovery
- controllers with broad discovery
- API server memory
- console resource discovery

Check count:

```bash
oc get crd --no-headers | wc -l
```

### 26.2 Number of CR Instances

High CR count can impact list/watch performance.

```bash
oc get <resource> -A --no-headers | wc -l
```

### 26.3 Object Size

Large CRs are bad. Avoid embedding:

- huge configs
- certificates chains when Secret reference is better
- logs
- metrics
- large templates
- binary data

### 26.4 Status Update Frequency

Operators should not update status too frequently. Every update writes to etcd and notifies watchers.

Bad:

- status update every second for every CR
- status includes rapidly changing metrics

Good:

- status changes only when meaningful state changes
- metrics go to Prometheus, not CR status

### 26.5 Watch Scope

Operators should watch only necessary namespaces/resources.

Bad:

- cluster-wide watch for tenant-only Operator without need

Good:

- namespaced watch when installed for one namespace
- filtered watches and predicates in controller logic

### 26.6 API Priority and Fairness

Heavy CRD usage can consume API server capacity. In severe cases, admin operations may see latency. Monitor API metrics and Operator behavior.

## 27. Example: Production-grade CRD Manifest

Below is a simplified but production-style CRD example.

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.platform.example.com
  labels:
    app.kubernetes.io/name: backup-operator
    app.kubernetes.io/part-of: platform-services
spec:
  group: platform.example.com
  scope: Namespaced
  names:
    plural: backups
    singular: backup
    kind: Backup
    listKind: BackupList
    shortNames:
    - bkp
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        required:
        - spec
        properties:
          apiVersion:
            type: string
          kind:
            type: string
          metadata:
            type: object
          spec:
            type: object
            required:
            - schedule
            - targetRef
            properties:
              schedule:
                type: string
                description: Cron schedule for backup execution.
              retentionDays:
                type: integer
                minimum: 1
                maximum: 365
                default: 7
                description: Number of days to retain successful backups.
              suspend:
                type: boolean
                default: false
                description: If true, scheduled backup execution is suspended.
              targetRef:
                type: object
                required:
                - name
                properties:
                  name:
                    type: string
                    description: Name of the target application or database.
                  namespace:
                    type: string
                    description: Namespace of the target. Defaults to the Backup namespace if omitted.
              storage:
                type: object
                properties:
                  storageClassName:
                    type: string
                  size:
                    type: string
                    pattern: '^[0-9]+(Mi|Gi|Ti)$'
                    default: 10Gi
            x-kubernetes-validations:
            - rule: "!has(self.retentionDays) || self.retentionDays <= 365"
              message: "retentionDays must be 365 or less"
          status:
            type: object
            properties:
              phase:
                type: string
                enum:
                - Pending
                - Running
                - Ready
                - Degraded
                - Failed
              observedGeneration:
                type: integer
                format: int64
              lastBackupTime:
                type: string
                format: date-time
              conditions:
                type: array
                items:
                  type: object
                  required:
                  - type
                  - status
                  properties:
                    type:
                      type: string
                    status:
                      type: string
                      enum:
                      - "True"
                      - "False"
                      - Unknown
                    reason:
                      type: string
                    message:
                      type: string
                    lastTransitionTime:
                      type: string
                      format: date-time
                    observedGeneration:
                      type: integer
                      format: int64
    subresources:
      status: {}
    additionalPrinterColumns:
    - name: Phase
      type: string
      jsonPath: .status.phase
    - name: Schedule
      type: string
      jsonPath: .spec.schedule
    - name: Retention
      type: integer
      jsonPath: .spec.retentionDays
    - name: LastBackup
      type: date
      jsonPath: .status.lastBackupTime
    - name: Age
      type: date
      jsonPath: .metadata.creationTimestamp
```

Apply:

```bash
oc apply -f backup-crd.yaml
```

Verify:

```bash
oc get crd backups.platform.example.com
oc api-resources | grep backups
oc explain backup.spec
```

```yaml
  name: nightly-db-backup
  namespace: finance

  schedule: "0 1 * * *"
  retentionDays: 14
```


The Operator sees the CR and performs:

1. Validate referenced target.
2. Add finalizer.
3. Create ServiceAccount.
4. Create Role/RoleBinding.
5. Create PVC if needed.
6. Create CronJob for scheduled backup.
7. Update status condition.

```yaml
status:
  observedGeneration: 1
  phase: Ready
  conditions:
  - type: Ready
    status: "True"
    reason: ReconcileSucceeded
    message: Backup schedule is configured
    observedGeneration: 1
    lastTransitionTime: "2026-07-03T10:00:00Z"
```

```yaml
status:
  observedGeneration: 2
  phase: Degraded
```

## 30. Interview and Real-world Scenario Questions

### Q1. What is the difference between CRD and CR?

A CRD defines a new API type. A CR is an instance of that type.

Example:

- CRD: `backups.platform.example.com`
- CR: `nightly-db-backup`

### Q2. Does creating a CRD automatically deploy workloads?

No. A CRD only extends the API. An Operator/controller must watch CRs and create workloads.

### Q3. Why does a CR remain unchanged even after editing spec?

Possible causes:

- Operator down
- Operator not watching namespace
- RBAC missing
- validation rejected update
- reconciliation error
- finalizer/deletion state

### Q4. What happens if a CRD is deleted?

The API type is removed and all CR instances of that type are deleted from the API. This is destructive.

### Q5. Why use `/status` subresource?

It separates user-owned desired state from controller-owned observed state and allows separate RBAC for status updates.

### Q6. What is `storage: true` in CRD versions?

It marks the version used for storing objects in etcd. Only one version can be the storage version.

### Q7. What is a conversion webhook?

A webhook used by the API server to convert custom resources between API versions when object schemas differ.

### Q8. What is the difference between owned and required CRDs in a CSV?

Owned CRDs are provided by the Operator. Required CRDs are dependencies that must be present/provided by another Operator.

### Q9. Why can an Operator upgrade fail because of CRDs?

Because the new CRD schema/version may not be backward compatible or existing CRs may fail validation under the new schema.

### Q10. How do you check whether a user can create a custom resource?

```bash
oc auth can-i create <resource> -n <namespace> --as <user>
```

## Final Notes for Senior OpenShift Administrators

In real production OpenShift environments, CRDs are where platform API design, Operator lifecycle, RBAC, etcd storage, GitOps, and application automation meet.

When troubleshooting an Operator, do not only check whether the Operator pod is running. Always inspect the full chain:

```text
CatalogSource → Subscription → InstallPlan → CSV → CRD → CR → Operator logs → Child resources → Status conditions
```

For CRD-related incidents, remember these senior-level rules:

1. **CRD exists does not mean controller works.**
2. **CR exists does not mean reconciliation succeeded.**
3. **Status is the Operator’s truth report.**
4. **Finalizers explain many stuck deletions.**
5. **RBAC explains many silent reconciliation failures.**
6. **CRD upgrades can be more dangerous than Operator pod upgrades.**
7. **Never delete a CRD casually in production.**
8. **Back up CRDs and CRs before Operator upgrades.**
9. **Use manual InstallPlan approval for critical Operators.**
10. **Treat CRDs as production APIs, not just YAML.**
