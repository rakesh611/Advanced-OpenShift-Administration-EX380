# Operator Rollback Concept in OpenShift Operator Management

**Audience:** Advanced OpenShift Administration / DO380-level study  
**Experience level:** Written for an administrator with ~10 years of Linux, Kubernetes, OpenShift, DevOps, and production operations experience  
**Scope:** OLM-managed application Operators, not Cluster Version Operator-managed OpenShift platform Operators  

---

## 1. Executive Summary

Operator rollback in OpenShift means returning an Operator-managed component to an earlier working state after an Operator upgrade causes failure, instability, incompatibility, or an unsupported change.

In OpenShift, this is **not the same as rolling back a Deployment** with `oc rollout undo`. An Operator rollback is more complex because an Operator is not just a pod image. It is managed by **Operator Lifecycle Manager (OLM)** and is represented by objects such as:

- `Subscription`
- `ClusterServiceVersion` or `CSV`
- `InstallPlan`
- `CatalogSource`
- `OperatorGroup`
- `CustomResourceDefinition` or `CRD`
- `CustomResource` or `CR`
- Operand workloads created by the Operator

The most important production rule is:

> **You do not roll back only the Operator pod. You must understand whether the operand, CRD schema, custom resources, data, and external systems can also move backward safely.**

A rollback can be simple when the upgrade failed before the new Operator became active. It can be risky or unsupported when the new Operator already migrated CRDs, changed custom resources, upgraded databases, changed storage layouts, or modified external systems.

---

## 2. Operator Rollback vs Application Rollback

### 2.1 Normal application rollback

For a normal OpenShift workload, rollback usually means:

```bash
oc rollout history deployment/myapp -n app-ns
oc rollout undo deployment/myapp -n app-ns
```

This works because a Deployment rollout is mostly about ReplicaSets and container image revisions.

### 2.2 Operator rollback

For an Operator, rollback might involve:

- Removing or replacing the current `Subscription`.
- Removing the current `CSV`.
- Reinstalling a previous Operator CSV from a catalog.
- Pinning the Subscription to a previous version with `startingCSV` and `Manual` approval.
- Restoring custom resources.
- Restoring operand data.
- Verifying CRD compatibility.
- Following product-specific rollback steps.

This is why rollback must be planned before the upgrade.

## 3. Key OLM Objects Involved in Rollback

OLM manages Operators using several custom resources. Understanding them is mandatory before rollback.

| Object | Short Name | Rollback Relevance |
|---|---:|---|
| `CatalogSource` | `catsrc` | Provides Operator package metadata, versions, channels, and upgrade graph. Rollback requires the old version to still exist in a catalog. |
| `Subscription` | `sub` | Tracks a package and channel. It tells OLM what Operator should be kept up to date. Automatic approval can immediately upgrade again after rollback. |
| `InstallPlan` | `ip` | The calculated list of resources OLM creates or updates to install/upgrade a CSV. Manual approval gives admin control before upgrade. |
| `ClusterServiceVersion` | `csv` | Represents a specific installed Operator version. Deleting the CSV usually removes the Operator deployment/pods, but not necessarily CRDs/CRs. |
| `OperatorGroup` | `og` | Defines the namespaces watched by Operators in the namespace. Wrong OperatorGroup scope can break reinstall or rollback. |
| `CRD` | `crd` | Defines the API schema for operands. CRD downgrade is one of the highest rollback risks. |
| `CR` | custom resource | Desired state consumed by the Operator. The older Operator might not understand fields written by the newer Operator. |

OLM is designed to install, update, and manage Operators and their lifecycle. In OLM, a `Subscription` keeps CSVs up to date by tracking a package channel, and an `InstallPlan` describes the resources created to install or upgrade a CSV. A CSV represents a specific version of a running Operator and contains metadata, install strategy, RBAC, owned APIs, required APIs, and related technical information.

## 4. What Rollback Really Means

There are several meanings of rollback. Do not mix them.

### 4.1 Rollback of the Operator controller only

This means going from:

```text
my-operator.v1.5.0  --->  my-operator.v1.4.2
```

This changes the Operator controller version.

### 4.2 Rollback of the operand

This means the actual application managed by the Operator goes backward, for example:

```text
Database operand 14.8  --->  Database operand 14.7
```

The operand is the real service: database, storage system, logging stack, monitoring stack, service mesh, etc.

### 4.3 Rollback of the CRD/API schema

This means API definitions go backward.

Example risk:

```yaml
spec:
  newFeatureEnabled: true
```

If the old Operator/CRD does not know `newFeatureEnabled`, reconciliation might fail, the field might be pruned, or the object might be rejected depending on schema and versioning behavior.

### 4.4 Rollback of persistent data

This means data migrations must be reversed or restored from backup.

Examples:

- Database schema migration
- Storage metadata migration
- Index format change
- Encryption key format change
- CR status/state migration
- External cloud resource changes

This is normally the hardest part.

## 5. Important Concept: OLM Is Forward-Upgrade Oriented

OLM primarily works with an **upgrade graph**. A catalog defines which bundle can upgrade to which other bundle. Common graph mechanisms are:

- `replaces`
- `skips`
- `skipRange`

Example graph:

```text
my-operator.v1.0.0 -> my-operator.v1.0.1 -> my-operator.v1.0.2
```

OLM knows how to move forward along this graph. Rollback is not normally a graph operation. It is usually an administrative recovery action.

The Operator Framework documentation states that update graphs are defined in file-based catalogs through `olm.channel` entries, and the catalog is the source of truth for upgrade edges. It also warns that `skipRange` can make skipped versions no longer installable through `spec.startingCSV`.

Practical meaning:

- If the old Operator version is not present or installable in any enabled catalog, OLM cannot install it.
- If a `skipRange` pruned the previous version from the graph, pinning to that version might not work.
- If the catalog always exposes only the newest head of a channel, you may need a custom or mirrored catalog that still contains the target version.

## 6. Why Operator Rollback Is Risky

### 6.1 The Operator may have changed CRDs

An upgrade can add:

- New CRD versions
- New required fields
- New validation rules
- Conversion webhooks
- New status fields
- New finalizers
- New RBAC rules

Older Operators may not reconcile newer CR shapes.

### 6.2 The Operator may have migrated the operand

Examples:

- Database Operator upgrades database major version.
- Logging Operator migrates index format.
- Storage Operator upgrades Ceph components.
- Service mesh Operator upgrades control plane and sidecars.

Even if the old Operator starts, the operand may not support downgrade.

### 6.3 Automatic approval can re-upgrade immediately

If the Subscription is still set to:

```yaml
installPlanApproval: Automatic
```

then OLM may immediately create and approve a new InstallPlan to move back to the channel head.

For rollback control, use:

```yaml
installPlanApproval: Manual
```

### 6.4 Channel head behavior matters

If the channel head is `v1.5.0`, and you reinstall `v1.4.2` while still subscribed to the same channel, OLM may detect `v1.5.0` as the desired latest version.

### 6.5 Deleting the Operator does not delete everything

Uninstalling an OLM-managed Operator removes the Operator deployment and pods, but it does not automatically remove all resources managed by that Operator, including CRDs and CRs. This is intentional, because deleting CRDs could delete all custom resources and cause data loss.

### 6.6 Product support matters

Some Red Hat Operators have documented product-specific rollback procedures. Others do not support downgrade. Always check product documentation and Red Hat support policies for production clusters.

## 7. Supported, Risky, and Unsupported Rollback Scenarios

### 7.1 Usually safer: upgrade not approved yet

If approval is manual and the new InstallPlan has not been approved, rollback is not needed. You simply stop the upgrade.

Check:

```bash
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
```

If the InstallPlan is not approved, do not approve it.

Optionally remove it if appropriate:

```bash
oc delete installplan <installplan-name> -n <operator-namespace>
```

Then keep the Subscription pinned or change the channel.

### 7.2 Usually recoverable: failed install before CSV succeeded

If the new CSV failed and the old CSV still exists, OLM might not have fully replaced the old Operator. Inspect both CSVs.

```bash
oc get csv -n <operator-namespace>
oc describe csv <new-csv-name> -n <operator-namespace>
oc describe csv <old-csv-name> -n <operator-namespace>
```

If the old CSV is still `Succeeded`, focus on fixing or removing the failed upgrade attempt.

### 7.3 Risky: new CSV succeeded but operand not migrated

If the Operator upgraded successfully but operand rollout failed, you might be able to reinstall the older Operator, but confirm:

- Did the CRD change?
- Did the CR spec change?
- Did the operand image change?
- Did data migration begin?
- Does product documentation support downgrade?

### 7.4 High risk: operand data migrated

If storage/database/schema migration occurred, rollback normally requires product-specific restore steps.

Examples:

- Restore application backup.
- Restore PVC snapshot.
- Restore database dump.
- Restore external system configuration.
- Set product-specific rollback flag.

### 7.5 Generally unsupported: OpenShift cluster Operators

This document focuses on OLM-managed application Operators. Many OpenShift platform components are managed by the **Cluster Version Operator (CVO)** and represented by `ClusterOperator` resources.

Examples:

```bash
oc get co
```

Do not try to roll back CVO-managed platform Operators by deleting their pods, CSVs, or deployments. They usually do not have normal OLM `Subscription` objects.

## 8. Golden Rule Before Any Operator Upgrade

Before approving or triggering any Operator upgrade, collect a rollback baseline.

```bash
NS=<operator-namespace>
PKG=<package-name>

mkdir -p rollback-baseline-$PKG

oc get sub,csv,installplan,operatorgroup -n $NS -o yaml > rollback-baseline-$PKG/olm-objects.yaml
oc get packagemanifest $PKG -n openshift-marketplace -o yaml > rollback-baseline-$PKG/packagemanifest.yaml
oc get pods,deploy,rs,svc,route,cm,secret,pvc -n $NS -o wide > rollback-baseline-$PKG/workloads.txt
oc get events -n $NS --sort-by=.lastTimestamp > rollback-baseline-$PKG/events.txt
```

For CRs owned by the Operator, export them too.

Find owned APIs from CSV:

```bash
CSV=$(oc get sub -n $NS <subscription-name> -o jsonpath='{.status.installedCSV}')
oc get csv $CSV -n $NS -o yaml > rollback-baseline-$PKG/current-csv.yaml
```

Check owned CRDs:

```bash
oc get csv $CSV -n $NS -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'
```

Export CRs for each owned CRD:

```bash
for CRD in $(oc get csv $CSV -n $NS -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'); do
  KIND=$(oc get crd $CRD -o jsonpath='{.spec.names.plural}')
  GROUP=$(oc get crd $CRD -o jsonpath='{.spec.group}')
  echo "Exporting $KIND.$GROUP"
  oc get $KIND.$GROUP -A -o yaml > rollback-baseline-$PKG/${KIND}.${GROUP}.yaml || true
done
```

Also take product-specific backups, such as database dumps, object storage backups, and PVC snapshots.

## 9. How to Inspect Current Operator State

### 9.1 List Operators in a namespace

```bash
oc get sub,csv,installplan,operatorgroup -n <operator-namespace>
```

### 9.2 Check Subscription fields

```bash
oc get sub <subscription-name> -n <operator-namespace> -o yaml
```

Important fields:

```yaml
spec:
  channel: stable
  installPlanApproval: Manual
  name: <package-name>
  source: redhat-operators
  sourceNamespace: openshift-marketplace
status:
  currentCSV: <newest-known-csv>
  installedCSV: <installed-csv>
  state: AtLatestKnown
```

`currentCSV` is the newest version OLM knows for the Subscription. `installedCSV` is the version installed on the cluster.

### 9.3 Check CSV status

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
```

Common CSV phases:

```text
Pending
InstallReady
Installing
Succeeded
Replacing
Deleting
Failed
```

### 9.4 Check InstallPlans

```bash
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
```

Look for:

```yaml
spec:
  approved: false
  clusterServiceVersionNames:
  - <target-csv>
status:
  phase: RequiresApproval
```

### 9.5 Check available versions and channels

```bash
oc describe packagemanifest <package-name> -n openshift-marketplace
```

Or:

```bash
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
```

For multiple catalogs with the same package, specify the catalog:

```bash
oc get packagemanifest \
  --selector=catalog=<catalogsource-name> \
  --field-selector metadata.name=<package-name> \
  -n openshift-marketplace -o yaml
```

This avoids installing from the wrong catalog.

## 10. Rollback Decision Tree

Use this before touching anything.

```text
Operator upgraded?
|
+-- No, pending InstallPlan only
|   +-- Do not approve InstallPlan
|   +-- Delete or leave pending InstallPlan based on policy
|   +-- Keep Subscription Manual
|
+-- Yes, new CSV failed
|   +-- Is old CSV still Succeeded?
|   |   +-- Yes: remove failed upgrade objects or fix dependency
|   |   +-- No: proceed to controlled reinstall / support case
|
+-- Yes, new CSV Succeeded
    +-- Did operand/data migrate?
        +-- No / unknown: inspect CRDs, CRs, pods, events, logs
        +-- Yes: use product-specific rollback or restore backup
    +-- Is previous CSV available in catalog?
        +-- Yes: controlled reinstall to previous version may be possible
        +-- No: use mirrored/custom catalog or vendor support
```

## 11. Controlled Rollback Runbook: Reinstall Previous Operator Version

> Use this only after confirming that the product supports rollback or that the failure is limited to the Operator layer.

### 11.1 Define variables

```bash
NS=<operator-namespace>
SUB=<subscription-name>
PKG=<package-name>
CATALOG=<catalogsource-name>
CATALOG_NS=openshift-marketplace
CHANNEL=<channel-name>
TARGET_CSV=<previous-csv-name>
```

Example:

```bash
NS=my-operator-ns
SUB=my-operator
PKG=my-operator
CATALOG=redhat-operators
CATALOG_NS=openshift-marketplace
CHANNEL=stable-1.4
TARGET_CSV=my-operator.v1.4.2
```

### 11.2 Freeze automatic upgrades

Patch the Subscription to manual approval if it still exists:

```bash
oc patch sub $SUB -n $NS --type=merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

Confirm:

```bash
oc get sub $SUB -n $NS -o jsonpath='{.spec.installPlanApproval}{"\n"}'
```

### 11.3 Capture current state

```bash
mkdir -p rollback-$PKG-before
oc get sub,csv,installplan,operatorgroup -n $NS -o yaml > rollback-$PKG-before/olm.yaml
oc get events -n $NS --sort-by=.lastTimestamp > rollback-$PKG-before/events.txt
oc get pods -n $NS -o wide > rollback-$PKG-before/pods.txt
oc get packagemanifest $PKG -n $CATALOG_NS -o yaml > rollback-$PKG-before/packagemanifest.yaml
```

### 11.4 Verify target CSV exists in catalog

```bash
oc get packagemanifest $PKG -n $CATALOG_NS -o yaml | grep -A3 -B3 "$TARGET_CSV"
```

If the target CSV is not present, do not continue with standard rollback. You may need:

- Older mirrored index image.
- Custom `CatalogSource` containing the previous bundle.
- Vendor-supported downgrade procedure.
- Restore from backup.

### 11.5 Delete current Subscription

```bash
oc delete sub $SUB -n $NS
```

Deleting the Subscription stops OLM from tracking the package/channel for updates.

### 11.6 Delete the current CSV

Find current CSV:

```bash
oc get csv -n $NS
```

Delete the upgraded CSV:

```bash
oc delete csv <current-csv-name> -n $NS
```

Important:

- Do **not** delete CRDs unless you are intentionally uninstalling the product and understand data loss impact.
- Do **not** delete CRs unless product documentation says so.
- Do **not** delete PVCs unless restoring from backup or product documentation requires it.

### 11.7 Recreate Subscription pinned to previous CSV

Create `rollback-subscription.yaml`:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: my-operator
  namespace: my-operator-ns
spec:
  channel: stable-1.4
  installPlanApproval: Manual
  name: my-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  startingCSV: my-operator.v1.4.2
```

Apply it:

```bash
oc apply -f rollback-subscription.yaml
```

### 11.8 Inspect and approve only the rollback InstallPlan

```bash
oc get installplan -n $NS
oc describe installplan <installplan-name> -n $NS
```

Confirm the InstallPlan references the target CSV:

```bash
oc get installplan <installplan-name> -n $NS \
  -o jsonpath='{.spec.clusterServiceVersionNames}{"\n"}'
```

Approve:

```bash
oc patch installplan <installplan-name> -n $NS --type=merge \
  -p '{"spec":{"approved":true}}'
```

### 11.9 Verify Operator rollback

```bash
oc get sub,csv,installplan -n $NS
oc get pods -n $NS -o wide
oc describe csv $TARGET_CSV -n $NS
```

Expected CSV phase:

```text
Succeeded
```

Check logs:

```bash
oc logs -n $NS deploy/<operator-deployment-name> --tail=200
```

### 11.10 Verify operand health

```bash
oc get pods -n <operand-namespace> -o wide
oc get events -n <operand-namespace> --sort-by=.lastTimestamp
oc get <custom-resource-kind> -n <operand-namespace> -o yaml
```

Then test service behavior, not only pod status:

```bash
oc get route -n <operand-namespace>
oc get svc,endpoints -n <operand-namespace>
curl -k https://<route-host>
```

## 12. Rollback Runbook: Failed Subscription / Failed Bundle Pull

Sometimes rollback is not needed. The Subscription is stuck because OLM cannot pull a bundle image or resolve a catalog.

Symptoms:

```text
ImagePullBackOff
Back-off pulling image
rpc error: code = Unknown
bundle image not accessible
installplan failed
```

Recovery pattern:

```bash
NS=<operator-namespace>

oc get sub,csv,installplan -n $NS
oc describe sub <subscription-name> -n $NS
oc describe installplan <installplan-name> -n $NS
```

If the catalog/bundle problem is fixed, refresh the failed subscription:

```bash
oc delete sub <subscription-name> -n $NS
oc delete csv <csv-name> -n $NS
```

Then recreate the Subscription.

This pattern is documented by Red Hat as a way to refresh a failing Subscription after correcting inaccessible bundle images.

## 13. Rollback Prevention: Use Manual Approval

For serious production clusters, especially with stateful Operators, use `Manual` approval.

```yaml
spec:
  installPlanApproval: Manual
```

Benefits:

- You can inspect the InstallPlan before the upgrade.
- You can detect RBAC changes.
- You can detect CRD changes.
- You can schedule maintenance.
- You can confirm backups exist.
- You avoid surprise upgrades from channel head changes.

InstallPlan inspection:

```bash
oc get installplan -n <operator-namespace>
oc get installplan <installplan-name> -n <operator-namespace> -o yaml
```

Approve only after review:

```bash
oc patch installplan <installplan-name> -n <operator-namespace> --type=merge \
  -p '{"spec":{"approved":true}}'
```

Red Hat documentation notes that manual approval gives administrators the opportunity to verify permission changes and take necessary steps before updating.

## 14. How to Inspect What an Upgrade Will Change

Before approving an InstallPlan:

```bash
oc get installplan <installplan-name> -n <operator-namespace> -o yaml
```

Look for:

```yaml
spec:
  clusterServiceVersionNames:
  - <new-csv>
status:
  plan:
  - resolving: ...
    resource:
      group: apiextensions.k8s.io
      kind: CustomResourceDefinition
      name: example.example.com
  - resource:
      group: rbac.authorization.k8s.io
      kind: ClusterRole
  - resource:
      group: apps
      kind: Deployment
```

Risk signals:

- New CRD or CRD update
- New ClusterRole permissions
- New webhooks
- New APIService
- New cluster-scoped resources
- Operand image major version change
- Finalizer or conversion webhook changes

## 15. CRD and Custom Resource Rollback Checks

### 15.1 Check CRD stored versions

```bash
oc get crd <crd-name> -o jsonpath='{.status.storedVersions}{"\n"}'
```

If the new Operator stored objects in a new API version, an old Operator may not work safely.

### 15.2 Check CRD served versions

```bash
oc get crd <crd-name> -o jsonpath='{range .spec.versions[*]}{.name}{" served="}{.served}{" storage="}{.storage}{"\n"}{end}'
```

### 15.3 Check conversion strategy

```bash
oc get crd <crd-name> -o jsonpath='{.spec.conversion.strategy}{"\n"}'
```

If conversion uses a webhook, rollback can break if the old Operator does not run the required webhook service.

### 15.4 Compare CR manifests before and after upgrade

```bash
oc get <crd-plural>.<group> -A -o yaml > cr-after-upgrade.yaml
```

Compare against pre-upgrade backup:

```bash
diff -u cr-before-upgrade.yaml cr-after-upgrade.yaml
```

Look for:

- New spec fields
- Removed fields
- New finalizers
- Status changes that indicate migration
- OwnerReferences changes
- New labels/annotations used by the Operator

---

## 16. Operator Rollback and Finalizers

Operators often add finalizers to custom resources.

Example:

```yaml
metadata:
  finalizers:
  - example.com/finalizer
```

If you roll back to an older Operator that does not handle a newer finalizer, CR deletion can hang.

Check finalizers:

```bash
oc get <kind> <name> -n <namespace> -o jsonpath='{.metadata.finalizers}{"\n"}'
```

Avoid removing finalizers manually unless you understand what cleanup they protect. Removing a finalizer can orphan cloud resources, storage, DNS entries, certificates, or external database objects.

---

## 17. Operator Rollback and RBAC

A newer Operator version may require new permissions. During rollback, older RBAC may be restored, but leftover resources may still require permissions the older Operator does not have.

Check Operator service account:

```bash
oc get deploy -n <operator-namespace>
oc get deploy <operator-deployment> -n <operator-namespace> -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

Check RBAC:

```bash
oc get role,rolebinding -n <operator-namespace>
oc get clusterrole,clusterrolebinding | grep -i <operator-name>
```

Test permissions:

```bash
oc auth can-i get <resource> --as=system:serviceaccount:<ns>:<sa> -n <target-ns>
oc auth can-i update <resource> --as=system:serviceaccount:<ns>:<sa> -n <target-ns>
```

## 18. Operator Rollback in Disconnected Environments

Disconnected environments require extra planning because old bundles might not be available.

Before upgrade, save:

- Current index image reference
- Target bundle image digest
- CatalogSource YAML
- ImageContentSourcePolicy / ImageDigestMirrorSet / ImageTagMirrorSet
- Pull secret state
- Mirrored registry path

Commands:

```bash
oc get catalogsource -n openshift-marketplace -o yaml
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
```

If rollback requires an older version, ensure the mirrored catalog still contains that version.

Do not assume the latest mirrored index image contains every old bundle.

## 19. CatalogSource Priority and Duplicate Packages

If multiple catalogs contain the same package, OLM resolver behavior can surprise you. A package can be selected from an unexpected catalog unless you specify the source carefully.

Check packages:

```bash
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
```

Use selector:

```bash
oc get packagemanifest \
  --selector=catalog=<catalogsource-name> \
  --field-selector metadata.name=<package-name> \
  -n openshift-marketplace -o yaml
```

Subscription must specify:

```yaml
spec:
  source: <catalogsource-name>
  sourceNamespace: openshift-marketplace
```

## 20. Operator Rollback and OperatorGroup Scope

OperatorGroup controls which namespaces the Operator watches.

Check:

```bash
oc get operatorgroup -n <operator-namespace> -o yaml
```

Common rollback issue:

- Original Operator was installed cluster-wide.
- Rollback Subscription is created in a namespace with different OperatorGroup scope.
- Operator installs but does not reconcile existing CRs.

Verify:

```yaml
spec:
  targetNamespaces:
  - <namespace>
```

or cluster-wide OperatorGroup depending on install mode.

For `AllNamespaces` install mode, many Operators are installed in `openshift-operators`. For `SingleNamespace`, the Operator usually watches only the selected namespace.

---

## 21. Special Case: Web Console Rollback Pattern

For some Operators, the web console allows selecting channel and version metadata during installation. If installing a non-latest version, manual approval is usually required.

General pattern:

1. Open **Operators → Installed Operators**.
2. Select the Operator.
3. Uninstall Operator.
4. Reinstall from OperatorHub.
5. Select the older channel/version if available.
6. Use Manual approval.
7. Approve only the intended InstallPlan.
8. Verify CSV becomes `Succeeded`.

Remember: web console uninstall removes the Operator deployment and pods, but not necessarily CRDs, CRs, dashboards, navigation items, off-cluster resources, or operand data.

---

## 22. Product-Specific Rollback Is the Source of Truth

Some Operators document special rollback steps. For example, Red Hat Advanced Cluster Security documentation includes an Operator rollback procedure that deletes the OLM Subscription and CSV, determines the rollback version, updates rollback configuration, changes the deployment image, verifies readiness, and reinstalls the Operator on the rolled-back channel.

That type of product-specific process is more authoritative than a generic OLM reinstall procedure.

For stateful Operators, always check product documentation for:

- Supported downgrade versions
- Data migration rollback support
- Required backups
- Required CR edits
- Required image tags
- Channel restrictions
- Version-specific limitations

## 23. Difference Between Delete Subscription, Delete CSV, and Delete CRD

### 23.1 Delete Subscription

```bash
oc delete sub <subscription-name> -n <operator-namespace>
```

Effect:

- Stops OLM from tracking that package/channel.
- Does not necessarily remove the running Operator immediately.
- Prevents automatic re-upgrade from that Subscription.

### 23.2 Delete CSV

```bash
oc delete csv <csv-name> -n <operator-namespace>
```

Effect:

- Removes the installed Operator version.
- Typically removes Operator deployment/pods managed by the CSV.
- Does not automatically remove CRDs/CRs.

### 23.3 Delete CRD

```bash
oc delete crd <crd-name>
```

Effect:

- Deletes the API definition.
- Deletes all custom resources of that CRD.
- Can cause irreversible data/control-plane loss.

Do not delete CRDs during rollback unless the product documentation explicitly says so or this is a full uninstall with backups confirmed.

## 24. Rollback Verification Checklist

After rollback, verify at four layers.

### 24.1 OLM layer

```bash
oc get sub,csv,installplan -n <operator-namespace>
oc describe csv <target-csv> -n <operator-namespace>
```

Expected:

```text
CSV phase: Succeeded
```

## 25. Common Rollback Problems and Fix Direction

| Problem | Likely Cause | Fix Direction |
|---|---|---|
| Old CSV not installable | Target version missing from catalog or pruned by skipRange | Use older/custom catalog or vendor support |
| Rollback succeeds then upgrades again | Subscription still Automatic or channel head newer | Set Manual approval, pin channel/version, inspect InstallPlans |
| CSV stuck Pending | Dependency missing, CRD conflict, OperatorGroup issue | Describe CSV and InstallPlan; check required APIs |
| CSV Failed | RBAC, webhook, bad image, unsupported CRD state | Check CSV events and operator logs |
| Operator pod Running but operand broken | Operand data/schema not downgraded | Follow product-specific restore/rollback |
| CR deletion stuck | Finalizer handled only by newer Operator | Reinstall compatible Operator or follow cleanup procedure |
| Old Operator cannot parse CR | CR spec contains new fields | Restore older CR manifest or edit unsupported fields carefully |
| InstallPlan references wrong version | Wrong channel/catalog/source | Recreate Subscription with correct source/channel/startingCSV |
| Catalog pod unhealthy | Marketplace/catalog issue | Check `openshift-marketplace` pods and CatalogSource status |

## 27. Example: Generic Operator Rollback Lab

### Situation

You upgraded `example-operator` from `v1.2.0` to `v1.3.0`. After upgrade, the Operator pod is running but operand reconciliation fails. Product team confirms rollback to `v1.2.0` is supported and data was not migrated.

### Step 1: Inspect

```bash
oc get sub,csv,installplan -n example-operator
oc describe sub example-operator -n example-operator
oc get csv -n example-operator
```

### Step 2: Freeze upgrades

```bash
oc patch sub example-operator -n example-operator --type=merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

### Step 3: Confirm previous version is available

```bash
oc get packagemanifest example-operator -n openshift-marketplace -o yaml | grep -A5 -B5 'example-operator.v1.2.0'
```

### Step 4: Delete current Subscription and CSV

```bash
oc delete sub example-operator -n example-operator
oc delete csv example-operator.v1.3.0 -n example-operator
```

### Step 5: Create pinned Subscription

```bash
cat <<'EOF_SUB' | oc apply -f -
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operator
spec:
  channel: stable-1.2
  installPlanApproval: Manual
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  startingCSV: example-operator.v1.2.0
EOF_SUB
```

### Step 6: Approve intended InstallPlan

```bash
oc get installplan -n example-operator
oc get installplan <ip-name> -n example-operator \
  -o jsonpath='{.spec.clusterServiceVersionNames}{"\n"}'

oc patch installplan <ip-name> -n example-operator --type=merge \
  -p '{"spec":{"approved":true}}'
```

### Step 7: Verify

```bash
oc get sub,csv,installplan -n example-operator
oc get pods -n example-operator -o wide
oc logs -n example-operator deploy/example-operator --tail=200
```

## 28. Exam and Interview Notes

### Question: Can I use `oc rollout undo` for Operator rollback?

No. `oc rollout undo` can roll back a Deployment rollout, but OLM will reconcile Operator state through CSV and Subscription. If you manually change only the Operator deployment image, OLM may revert it.

### Question: What is the safest rollback?

The safest rollback is avoiding the bad upgrade by using Manual InstallPlan approval, reviewing the InstallPlan, and not approving it.

### Question: What object tells OLM which Operator package/channel to track?

`Subscription`.

### Question: What object represents a specific Operator version?

`ClusterServiceVersion` or `CSV`.

### Question: What object lists resources OLM will create during install/upgrade?

`InstallPlan`.

### Question: Why can deleting CRD be dangerous?

Deleting a CRD deletes all custom resources for that API. This can destroy desired state and trigger data loss.

### Question: Why can rollback fail even if the old Operator pod starts?

Because the operand data, CRD schema, CR spec, finalizers, or external resources may already have been changed by the newer Operator.

### Question: Why use Manual approval?

Manual approval gives administrators a control point to inspect permissions, CRDs, and other resources before the update is applied.

## 29. Production Best Practices

1. Use Manual approval for critical/stateful Operators.
2. Install unrelated Operators in separate namespaces when independent upgrade control is required.
3. Read product-specific release notes before upgrade.
4. Capture OLM object YAML before upgrade.
5. Export CRs before upgrade.
6. Back up operand data before upgrade.
7. Test rollback in a non-production cluster.
8. Keep older catalog/index images available in disconnected environments.
9. Avoid deleting CRDs during rollback.
10. Verify business-level health, not only CSV `Succeeded`.
11. Use Red Hat Support for stateful product rollbacks.
12. Document exact channel, CSV, catalog, and image digest before every production upgrade.

## 31. Mental Model for a 10-Year OpenShift Admin

Think of Operator rollback as a layered recovery problem:

```text
Layer 1: OLM metadata
  Subscription, InstallPlan, CSV, CatalogSource, OperatorGroup

Layer 2: Operator controller
  Operator deployment, service account, RBAC, webhooks

Layer 3: Kubernetes API extension
  CRDs, conversion, validation, stored versions

Layer 4: Desired state
  Custom resources, finalizers, labels, annotations

Layer 5: Operand runtime
  Deployments, StatefulSets, DaemonSets, Services, Routes, PVCs

Layer 6: Data and external systems
  Databases, storage, object buckets, cloud resources, certificates
```

A rollback is safe only when all affected layers can return to a compatible state.

## 33. Final Practical Advice

For exam and real production troubleshooting, remember this simple rule:

> **Rollback starts with OLM objects, but success depends on operand compatibility and data safety.**

Before upgrade, make rollback possible. After a failed upgrade, do not panic-delete CRDs or PVCs. First inspect `Subscription`, `CSV`, `InstallPlan`, catalog versions, CRDs, custom resources, Operator logs, and operand health. Then decide whether generic OLM reinstall is enough or whether product-specific restore is required.
