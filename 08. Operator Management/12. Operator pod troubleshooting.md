# Operator Pod Troubleshooting in OpenShift

**Audience:** Advanced OpenShift Administration / DO380-style troubleshooting  
**Experience level:** Written for an administrator with ~10 years of Linux, Kubernetes, DevOps, and OpenShift operations experience  
**Scope:** OLM-managed Operator pods, OLM control-plane pods, CatalogSource pods, bundle unpack jobs, CSV-owned Deployments, Cluster Operators, and real production troubleshooting patterns

---

## 1. What “Operator pod troubleshooting” really means

In OpenShift, an Operator problem is often visible as a pod problem, but the root cause might be in a higher-level lifecycle object. A normal application pod is usually controlled by a Deployment, StatefulSet, DaemonSet, or Job. An Operator pod is usually controlled by one of the following layers:

```text
Subscription
  -> InstallPlan
      -> ClusterServiceVersion (CSV)
          -> Deployment / ServiceAccount / RBAC / CRDs / Webhooks / APIService
              -> ReplicaSet
                  -> Operator Pod
```

For catalog-related failures, the chain is different:

```text
CatalogSource
  -> CatalogSource registry pod / gRPC service
      -> PackageManifest availability
          -> Subscription resolution
              -> InstallPlan
                  -> Bundle unpack Job
                      -> CSV
                          -> Operator Deployment
```

For OpenShift built-in platform Operators, the chain is controlled by the Cluster Version Operator (CVO):

```text
ClusterVersion / ClusterOperator
  -> Operand namespace
      -> Operator Deployment / DaemonSet / static pod / controller
          -> Operator Pod
```

The important first step is to identify **which type of Operator you are troubleshooting**.

| Operator category | Managed by | Main objects | Typical namespaces |
|---|---|---|---|
| OpenShift platform Cluster Operators | CVO | `ClusterOperator`, `ClusterVersion`, Deployments, DaemonSets, static pods | `openshift-*` namespaces |
| OLM-managed application Operators | OLM Classic | `Subscription`, `InstallPlan`, `CSV`, `OperatorGroup`, `CatalogSource` | `openshift-operators`, custom Operator namespace, product-specific namespace |
| OLM control-plane components | OpenShift / OLM | `olm-operator`, `catalog-operator`, `packageserver`, cluster operator objects | `openshift-operator-lifecycle-manager` |
| Catalog source pods | Catalog Operator / Marketplace Operator | `CatalogSource`, registry pod, service | `openshift-marketplace` or custom catalog namespace |
| OLM v1 extensions | OLM v1 | `ClusterExtension`, `ClusterCatalog` | cluster-scoped resources and OLM v1 namespaces |

In most enterprise cases, “Operator pod troubleshooting” means answering these questions:

1. Is the pod actually the failing component, or is it only a symptom of a bad Subscription, CSV, InstallPlan, CatalogSource, OperatorGroup, registry, SCC, RBAC, scheduling, or network condition?
2. Is this a platform Operator or an OLM-managed add-on Operator?
3. Is the failure happening before installation, during installation, during upgrade, during reconciliation, or after an uninstall/reinstall?
4. Can the pod be safely deleted/recreated, or will OLM/CVO recreate the same broken state?
5. Is the issue local to one Operator, one namespace, one node, all catalog sources, or the whole OLM control plane?

## 2. Fast incident workflow

Use this when production is degraded and you need a quick triage path.

### 2.1 Start with cluster health

```bash
oc get clusterversion
oc get clusteroperators
oc get nodes
oc get mcp
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Look for:

- `Available=False`, `Progressing=True`, or `Degraded=True` in `oc get clusteroperators`.
- Nodes in `NotReady`, `SchedulingDisabled`, or pressure conditions.
- MachineConfigPools stuck in `Updating=True` or `Degraded=True`.
- API, authentication, image registry, DNS, network, or CVO problems. Many Operator pods fail when the platform below them is unhealthy.

### 2.2 Check OLM control plane

```bash
oc get pods -n openshift-operator-lifecycle-manager -o wide
oc get pods -n openshift-marketplace -o wide
oc get catalogsource -A
oc get sub,csv,installplan,operatorgroup -A
```

Expected high-level pattern:

- `olm-operator`, `catalog-operator`, and package server components should be healthy.
- `marketplace-operator` should be healthy.
- Default catalog pods such as Red Hat, certified, community, and marketplace catalogs should be running unless disabled intentionally.
- A broken catalog pod can block Operator discovery and upgrades.

### 2.3 Identify the exact failed pod and owner

```bash
NS=<operator_namespace>
POD=<operator_pod_name>

oc get pod "$POD" -n "$NS" -o wide
oc describe pod "$POD" -n "$NS"
oc get pod "$POD" -n "$NS" -o jsonpath='{.metadata.ownerReferences[*].kind}{"/"}{.metadata.ownerReferences[*].name}{"\n"}'
```

If the owner is a ReplicaSet, follow it back to the Deployment:

```bash
RS=$(oc get pod "$POD" -n "$NS" -o jsonpath='{.metadata.ownerReferences[0].name}')
oc get rs "$RS" -n "$NS" -o jsonpath='{.metadata.ownerReferences[*].kind}{"/"}{.metadata.ownerReferences[*].name}{"\n"}'
```

Then map the Deployment back to the CSV:

```bash
oc get csv -n "$NS" -o json | jq -r '.items[] | [.metadata.name, (.spec.install.spec.deployments[]?.name // "")] | @tsv' | column -t
```

If `jq` is not available:

```bash
oc get csv -n "$NS" -o yaml | less
```

Search for the Deployment name under:

```yaml
spec:
  install:
    spec:
      deployments:
```

### 2.4 Get the lifecycle status first, then pod details

For OLM-managed Operators:

```bash
oc get sub,csv,installplan,operatorgroup -n "$NS"
oc describe sub <subscription_name> -n "$NS"
oc describe csv <csv_name> -n "$NS"
oc describe installplan <installplan_name> -n "$NS"
oc describe operatorgroup <operatorgroup_name> -n "$NS"
```

For Cluster Operators:

```bash
oc get co <cluster_operator_name> -o yaml
oc describe co <cluster_operator_name>
oc get pods -n <operator_namespace> -o wide
oc logs -n <operator_namespace> deploy/<operator_deployment> --all-containers --tail=200
```

### 2.5 Capture logs correctly

```bash
oc logs pod/$POD -n "$NS" --all-containers --tail=200
oc logs pod/$POD -n "$NS" --all-containers --previous --tail=200
oc logs deploy/<deployment_name> -n "$NS" --all-containers --tail=200
```

If the pod has multiple containers and `oc logs` asks for a container name:

```bash
oc get pod "$POD" -n "$NS" -o jsonpath='{.spec.containers[*].name}{"\n"}'
oc logs pod/$POD -n "$NS" -c <container_name> --tail=200
oc logs pod/$POD -n "$NS" -c <container_name> --previous --tail=200
```

## 3. Core OLM objects you must understand before troubleshooting pods

### 3.1 Subscription

A `Subscription` tells OLM which package, channel, source, and approval strategy to track.

Important fields:

```yaml
spec:
  channel: stable
  name: <package_name>
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic | Manual
  config:
    env: []
    resources: {}
    nodeSelector: {}
    tolerations: []
    affinity: {}
```

Important status fields:

```bash
oc get sub <name> -n <ns> -o yaml
oc describe sub <name> -n <ns>
```

Look for:

- `status.currentCSV`
- `status.installedCSV`
- `status.installPlanRef`
- `status.conditions`
- `CatalogSourcesUnhealthy`
- `InstallPlanMissing`
- `InstallPlanPending`
- `InstallPlanFailed`
- `ResolutionFailed`

If `installPlanApproval` is `Manual`, the Operator pod will not be created until the pending InstallPlan is approved.

```bash
oc get installplan -n <ns>
oc patch installplan <installplan_name> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

### 3.2 InstallPlan

An `InstallPlan` is OLM’s calculated execution plan for installing or upgrading a CSV and related objects.

```bash
oc get installplan -n <ns>
oc describe installplan <name> -n <ns>
oc get installplan <name> -n <ns> -o yaml
```

Check:

- Is it approved?
- Did it fail while creating CRDs, RBAC, Deployments, webhooks, or APIService objects?
- Is the failure caused by missing API versions?
- Is there a bundle unpack Job failing in `openshift-marketplace`?
- Is there an immutable field change during upgrade?

### 3.3 ClusterServiceVersion

A `ClusterServiceVersion` is the key object that describes how OLM should run an Operator. It includes the deployment spec, permissions, CRDs owned/required, webhooks, APIs, version, and install strategy.

```bash
oc get csv -n <ns>
oc describe csv <csv_name> -n <ns>
oc get csv <csv_name> -n <ns> -o yaml
```

Check:

- `status.phase`
- `status.reason`
- `status.message`
- `status.requirementStatus`
- `spec.install.spec.deployments`
- `spec.install.spec.permissions`
- `spec.install.spec.clusterPermissions`
- `spec.customresourcedefinitions.owned`
- `spec.customresourcedefinitions.required`
- webhook/APIService definitions

Common CSV phases:

| Phase | Meaning |
|---|---|
| `Pending` | Requirements not met yet. Could be waiting for CRDs, APIService, RBAC, OperatorGroup, or dependency resolution. |
| `InstallReady` | Requirements are met and install strategy can run. |
| `Installing` | OLM is creating resources. |
| `Succeeded` | Operator install strategy completed. Pod might still fail later due to runtime issues. |
| `Failed` | OLM hit an unrecoverable install error. Check `reason` and `message`. |
| `Replacing` | Upgrade is replacing an older CSV. |

### 3.4 OperatorGroup

An `OperatorGroup` defines the namespace scope that an Operator watches. A CSV must be compatible with the OperatorGroup in its namespace.

```bash
oc get operatorgroup -n <ns>
oc describe operatorgroup <name> -n <ns>
oc get operatorgroup <name> -n <ns> -o yaml
```

Common OperatorGroup-related failures:

| Reason | Meaning | Action |
|---|---|---|
| `NoOperatorGroup` | CSV namespace has no OperatorGroup. | Create the correct OperatorGroup or reinstall through the software catalog. |
| `TooManyOperatorGroups` | More than one OperatorGroup exists in the namespace. | Keep only one OperatorGroup per namespace. |
| `UnsupportedOperatorGroup` | CSV install modes do not support the selected namespace scope. | Change install mode/namespace or use an Operator version that supports the desired scope. |
| `InterOperatorGroupOwnerConflict` | Another OperatorGroup already owns the provided APIs. | Remove conflicting install or redesign tenancy. |
| `CannotModifyStaticOperatorGroupProvidedAPIs` | Static OperatorGroup cannot be modified to include new APIs. | Adjust static API ownership intentionally. |

### 3.5 CatalogSource

A `CatalogSource` provides Operator packages and channels to OLM.

```bash
oc get catalogsource -A
oc describe catalogsource <name> -n <source_namespace>
oc get catalogsource <name> -n <source_namespace> -o yaml
```

Important status area:

```yaml
status:
  connectionState:
    address: <catalog-service>:50051
    lastConnect: ...
    lastObservedState: READY | TRANSIENT_FAILURE | CONNECTING | SHUTDOWN
    reason: ...
```

If the catalog pod is in `ImagePullBackOff`, OLM might not discover packages from that source. If the package is not visible, the Subscription can show `CatalogSourcesUnhealthy` or `ResolutionFailed`.

## 4. Operator pod states and what they usually mean

### 4.1 `Pending`

A `Pending` Operator pod usually means scheduling or volume setup did not complete.

Check:

```bash
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp | tail -50
oc get node --show-labels
oc describe node <node>
oc get quota,limitrange -n <ns>
```

Common causes:

- Node selector does not match any node.
- Project-level node selector conflicts with Subscription config.
- Required node affinity is too restrictive.
- Taints exist but the Operator pod has no matching toleration.
- Insufficient CPU or memory.
- PVC not bound.
- Missing Secret or ConfigMap volume.
- MachineConfigPool/node upgrade disruption.
- PodSecurity/SCC admission failure before pod creation.

Typical scheduler event:

```text
0/6 nodes are available: 3 node(s) didn't match Pod's node affinity/selector, 3 node(s) had taint that the pod didn't tolerate.
```

Fix pattern:

1. Confirm whether placement was intentional.
2. Check the `Subscription.spec.config` placement fields.
3. Check project node selector.
4. Check node labels and taints.
5. Patch the Subscription, not the generated Deployment, when OLM owns the Deployment.

Example Subscription patch for toleration:

```bash
oc patch sub <sub_name> -n <ns> --type merge -p '
{
  "spec": {
    "config": {
      "tolerations": [
        {
          "key": "dedicated",
          "operator": "Equal",
          "value": "operators",
          "effect": "NoSchedule"
        }
      ]
    }
  }
}'
```

Example Subscription patch for node selector:

```bash
oc patch sub <sub_name> -n <ns> --type merge -p '
{
  "spec": {
    "config": {
      "nodeSelector": {
        "node-role.kubernetes.io/infra": ""
      }
    }
  }
}'
```

### 4.2 `ImagePullBackOff` / `ErrImagePull`

This is one of the most common Operator installation failures.

There are three different image-pull paths:

| Image type | Where it fails | Example symptom |
|---|---|---|
| Catalog index image | CatalogSource pod | Catalog pod in `openshift-marketplace` is `ImagePullBackOff`. |
| Bundle image | Bundle unpack Job | Failing Job in `openshift-marketplace`; Subscription stuck. |
| Operator controller image | Operator Deployment pod | CSV may install, but controller pod cannot start. |

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.containers[*]}{.name}{" => "}{.image}{"\n"}{end}'
oc get events -n <ns> --sort-by=.lastTimestamp | tail -50
oc get pullsecret -n openshift-config
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

Common event messages:

```text
unauthorized: access to the requested resource is not authorized
x509: certificate signed by unknown authority
dial tcp: lookup registry.example.com: no such host
manifest unknown
no matching manifest for linux/amd64 in the manifest list entries
```

Root causes:

- Private registry credentials missing.
- Wrong pull secret namespace.
- Disconnected mirror not configured.
- Wrong digest or tag in mirrored catalog.
- Registry DNS not resolvable from nodes.
- Corporate proxy/CA not trusted.
- Architecture mismatch.
- Catalog references upstream images not available in restricted network.

For a private CatalogSource image, reference the pull secret in `CatalogSource.spec.secrets`:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: my-operator-catalog
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: registry.example.com/operators/my-index:v4.20
  displayName: My Operator Catalog
  publisher: My Org
  secrets:
  - my-registry-pull-secret
```

Create a pull secret in the same namespace as the CatalogSource:

```bash
oc create secret docker-registry my-registry-pull-secret \
  --docker-server=registry.example.com \
  --docker-username=<user> \
  --docker-password=<password> \
  --docker-email=<email> \
  -n openshift-marketplace
```

For a controller image pull failure, inspect the ServiceAccount used by the Operator pod:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
oc get sa <serviceaccount> -n <ns> -o yaml
oc get secret -n <ns>
```

Patch image pull secret only when appropriate:

```bash
oc secrets link <serviceaccount> <pull_secret> --for=pull -n <ns>
```

For disconnected clusters, confirm your mirror configuration and that all referenced catalog, bundle, and operator images are mirrored. Do not assume mirroring the catalog image alone is enough; the catalog points to bundles, and bundles point to operator images.

### 4.3 `CrashLoopBackOff`

A `CrashLoopBackOff` Operator pod means the container started and exited repeatedly.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc logs pod/<pod> -n <ns> --all-containers --previous --tail=200
oc logs pod/<pod> -n <ns> --all-containers --tail=200
oc get pod <pod> -n <ns> -o yaml
oc get deploy <deployment> -n <ns> -o yaml
```

Check `lastState`:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{range .status.containerStatuses[*]}{.name}{" state="}{.state}{" last="}{.lastState}{" restarts="}{.restartCount}{"\n"}{end}'
```

Common root causes:

- Required environment variables missing.
- Secret or ConfigMap content invalid.
- Operator cannot talk to the Kubernetes API.
- RBAC denies watch/list/update on resources.
- CRD conversion webhook is unavailable.
- Controller panic caused by unexpected custom resource spec.
- Leader election errors.
- TLS certificate expired or not trusted.
- Proxy configuration missing.
- OOM kill due to low memory limit.
- Operator binary incompatible with current Kubernetes/OpenShift version.

Look for logs like:

```text
failed to get rest config
forbidden: User "system:serviceaccount:..." cannot list resource ...
leader election lost
x509: certificate signed by unknown authority
panic: runtime error
OOMKilled
```

Fix pattern:

1. Read previous logs first; current logs may only show startup retry.
2. Confirm whether the crash happens before manager startup or during reconciliation.
3. Check whether the Operator is failing on a specific custom resource.
4. Check RBAC using `oc auth can-i` with the Operator ServiceAccount.
5. Check Secret/ConfigMap references and mounted files.
6. Check memory limits and OOM events.
7. Validate compatibility with the OpenShift version and Operator channel.

RBAC test example:

```bash
SA=$(oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}')
oc auth can-i list pods --as system:serviceaccount:<ns>:$SA -n <target_ns>
oc auth can-i get <resource>.<api_group> --as system:serviceaccount:<ns>:$SA -A
```

### 4.4 `CreateContainerConfigError`

This usually means Kubernetes could not build the container runtime config.

Common causes:

- Missing Secret.
- Missing ConfigMap.
- Wrong key in Secret/ConfigMap.
- Invalid env var reference.
- Invalid volume mount.
- Projected service account token problem.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get secret,configmap -n <ns>
oc get pod <pod> -n <ns> -o yaml
```

Events commonly show exactly which Secret/ConfigMap/key is missing.

Fix pattern:

- Recreate or correct the missing object.
- If the missing object should be created by another Operator, troubleshoot that Operator first.
- If OLM should create it from the CSV, inspect `CSV.status.message` and `InstallPlan` resources.

### 4.5 `RunContainerError`

This happens after the image is pulled but before the process starts successfully.

Common causes:

- Invalid command/args.
- Entrypoint missing.
- Permission denied on executable.
- Volume mount path conflict.
- SecurityContext/SCC denial.
- Read-only root filesystem conflict.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o yaml
oc adm policy who-can use scc/<scc_name>
```

### 4.6 `Running` but not `Ready`

The container is alive, but the readiness probe is failing.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc logs pod/<pod> -n <ns> --all-containers --tail=200
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.containers[*]}{.name}{"\nreadiness="}{.readinessProbe}{"\nliveness="}{.livenessProbe}{"\n"}{end}'
```

Common causes:

- Manager health endpoint not listening.
- Metrics endpoint TLS/cert issue.
- Webhook server cannot start.
- Controller waiting for CRDs or APIService.
- Operator cannot connect to dependencies.
- Startup is slow and readiness timeout is too aggressive.

Do not simply remove probes from an OLM-managed Deployment. The CSV owns the Deployment and OLM might revert manual changes.

### 4.7 `Completed` or `Error` bundle unpack Jobs

During install/upgrade, OLM creates bundle unpack Jobs. These are often in `openshift-marketplace`.

```bash
oc get jobs,pods -n openshift-marketplace
oc describe job <job_name> -n openshift-marketplace
oc logs job/<job_name> -n openshift-marketplace
```

Common causes:

- Bundle image not pullable.
- Bundle malformed.
- Missing registry access.
- Unsupported manifest/API version.
- Network/proxy/CA problem.
- Job hit active deadline.

If a failed bundle image was inaccessible and you later fixed mirroring/registry access, a failing subscription may need to be refreshed by cleaning the related Subscription, CSV, Job, and ConfigMap and then reinstalling the Operator. Do this during a maintenance window and only after confirming the correct bundle image is available.

### 4.8 `OOMKilled`

Check:

```bash
oc describe pod <pod> -n <ns> | grep -A5 -B5 OOM
oc get pod <pod> -n <ns> -o jsonpath='{range .status.containerStatuses[*]}{.name}{" lastState="}{.lastState}{"\n"}{end}'
oc adm top pod <pod> -n <ns>
oc adm top pod -n <ns>
```

Root causes:

- Operator cache is too large because it watches all namespaces.
- Too many CR instances.
- Too many watched resources.
- Memory limits too low.
- Bug or memory leak.
- Upgrade introduced higher memory usage.

Fix pattern:

- Prefer vendor-supported resource tuning through `Subscription.spec.config.resources` if supported.
- Consider namespace-scoped install instead of all-namespaces install when supported.
- Reduce CR fan-out or reconcile storm.
- Open vendor support case if memory grows continuously.

Example resource patch:

```bash
oc patch sub <sub_name> -n <ns> --type merge -p '
{
  "spec": {
    "config": {
      "resources": {
        "requests": {
          "cpu": "100m",
          "memory": "256Mi"
        },
        "limits": {
          "cpu": "500m",
          "memory": "1Gi"
        }
      }
    }
  }
}'
```

### 4.9 `Evicted`

Evicted Operator pods indicate node pressure, not necessarily Operator defects.

```bash
oc describe pod <pod> -n <ns>
oc describe node <node>
oc adm top node
oc get events -A --sort-by=.lastTimestamp | grep -i -E 'evict|pressure|disk|memory'
```

Fix node pressure first. If the Operator is critical, consider placing it on infra nodes with appropriate requests, tolerations, and priority class, following your cluster design.

## 5. Troubleshooting OLM control-plane pods

OLM control-plane health matters because it creates and updates Operator resources.

Check:

```bash
oc get pods -n openshift-operator-lifecycle-manager -o wide
oc get deploy -n openshift-operator-lifecycle-manager
oc logs deploy/olm-operator -n openshift-operator-lifecycle-manager --all-containers --tail=200
oc logs deploy/catalog-operator -n openshift-operator-lifecycle-manager --all-containers --tail=200
oc get apiservice | grep -i package
oc get clusteroperators | grep -E 'operator-lifecycle|marketplace|olm'
```

If `catalog-operator` is unhealthy:

- Subscriptions might not resolve.
- InstallPlans might not be created.
- CatalogSource status might not update.
- Bundle unpack Jobs might not run correctly.

If `olm-operator` is unhealthy:

- CSV install strategies might not execute.
- Deployments/RBAC from CSVs might not be reconciled.
- CSV status might be stale.

If `packageserver` is unhealthy:

- Web console Operator catalog may not show packages correctly.
- `PackageManifest` API may be degraded.
- OperatorHub discovery can appear broken even when installed Operators keep running.

Advanced checks:

```bash
oc get apiservice v1.packages.operators.coreos.com -o yaml
oc describe apiservice v1.packages.operators.coreos.com
oc get endpoints -n openshift-operator-lifecycle-manager
oc get svc -n openshift-operator-lifecycle-manager
```

Look for:

- `FailedDiscoveryCheck`
- no endpoints
- service selector mismatch
- certificate/CA bundle errors
- package server pods not ready

Avoid restarting OLM components blindly. Capture logs and events first. If you delete a pod, Kubernetes recreates it, but you may lose crash evidence unless logs are centralized.

## 6. Troubleshooting CatalogSource pods

CatalogSource pods are not the Operator itself. They serve metadata to OLM over gRPC. If a catalog pod fails, installation and upgrade resolution can fail.

### 6.1 Basic catalog checks

```bash
oc get catalogsource -A
oc describe catalogsource <catsrc> -n <catsrc_ns>
oc get pods -n <catsrc_ns> -o wide
oc get svc -n <catsrc_ns>
oc logs pod/<catalog_pod> -n <catsrc_ns> --tail=200
```

If the CatalogSource status shows connection failure:

```bash
oc get catsrc <catsrc> -n <catsrc_ns> -o yaml
```

Check:

```yaml
status:
  connectionState:
    address:
    lastObservedState:
    reason:
```

### 6.2 Catalog pod `ImagePullBackOff`

Check the image:

```bash
oc get catsrc <catsrc> -n <catsrc_ns> -o jsonpath='{.spec.image}{"\n"}'
oc describe pod <catalog_pod> -n <catsrc_ns>
```

Fix areas:

- Registry credentials.
- Mirror registry content.
- `CatalogSource.spec.secrets`.
- Node trust for registry CA.
- DNS/proxy from nodes to registry.

### 6.3 Catalog pod blocked by pod security admission

OpenShift 4.20 defaults the CatalogSource security mode to `legacy`, but restricted enforcement is important for future compatibility. For older SQLite-based catalogs, pod security can block catalog pods in stricter namespaces.

Check:

```bash
oc get catsrc <catsrc> -n <ns> -o yaml | grep -A5 grpcPodConfig
oc get ns <ns> -o yaml | grep -E 'pod-security|scc.podSecurityLabelSync' -A5 -B5
oc describe pod <catalog_pod> -n <ns>
```

Example explicit legacy mode:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: my-catsrc
  namespace: my-ns
spec:
  sourceType: grpc
  grpcPodConfig:
    securityContextConfig: legacy
  image: my-image:latest
```

Use `restricted` where your catalog supports it. Use `legacy` only when required and understood.

### 6.4 Catalog pod scheduling override

Catalog source pods can be controlled with scheduling settings. Useful for infra-node placement or restricted clusters.

Check:

```bash
oc get catsrc <catsrc> -n <ns> -o yaml
oc describe pod <catalog_pod> -n <ns>
```

Look for:

- `nodeSelector`
- `tolerations`
- `priorityClassName`
- namespace node selector

### 6.5 Package not visible from catalog

```bash
oc get packagemanifest -n openshift-marketplace | grep -i <operator>
oc get packagemanifest <package_name> -n openshift-marketplace -o yaml
```

If package is missing:

- Catalog pod might not be ready.
- Package is not in that catalog/channel.
- Wrong `source` or `sourceNamespace` in Subscription.
- Catalog mirror does not include the package.
- PackageManifest API/package server is unhealthy.

## 7. Troubleshooting Subscription and InstallPlan issues that prevent Operator pods

### 7.1 `InstallPlanPending`

If approval is manual:

```bash
oc get installplan -n <ns>
oc describe installplan <ip> -n <ns>
oc patch installplan <ip> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

If approval is automatic but pending persists:

- Catalog resolution may be stuck.
- Required APIs might be missing.
- Another failed Subscription in the same namespace might block resolution.
- Catalog source may be unhealthy.

### 7.2 `ResolutionFailed`

```bash
oc describe sub <sub> -n <ns>
oc get sub -n <ns> -o yaml
oc get csv -n <ns>
oc get catsrc -A
```

Common causes:

- Package/channel not found.
- Required CRD/API not available.
- Conflicting CSV already exists.
- Deleted Subscription left an unassociated CSV.
- Multiple Subscriptions in one namespace create an unsatisfiable set.
- Operator version incompatible with OpenShift/Kubernetes API level.

A key rule: Subscriptions in the same namespace are resolved together. One broken Subscription can block others in that namespace.

### 7.3 Deleted Subscription left CSV behind

Symptom:

```text
constraints not satisfiable ... clusterserviceversion ... exists and is not referenced by a subscription
```

Fix choice:

- If you want to upgrade/reinstall: delete the old CSV after confirming CRD/CR impact.
- If you do not want the Operator: delete the new Subscription.

Commands:

```bash
oc get sub,csv -n <ns>
oc delete csv <old_csv> -n <ns>
```

Be careful: deleting a CSV usually removes the Operator deployment, but it does not always remove CRDs or custom resources.

### 7.4 `InstallPlanFailed`

```bash
oc describe installplan <ip> -n <ns>
oc get installplan <ip> -n <ns> -o yaml
oc get events -n <ns> --sort-by=.lastTimestamp | tail -100
```

Look for failed resource creation:

- CRD already exists and is owned by another Operator.
- Webhook config conflicts.
- APIService conflicts.
- RBAC creation denied.
- Immutable field on Deployment update.
- Unsupported API version in bundle.

If failure is due to an immutable field during upgrade, manual editing of the Deployment is usually not enough; OLM continues to apply the CSV strategy. The durable fix is normally a corrected Operator bundle/CSV version from the vendor, or a supported uninstall/reinstall path.

## 8. CSV failure reasons and pod impact

### 8.1 `NoOperatorGroup`

Symptom:

```bash
oc describe csv <csv> -n <ns>
# Reason: NoOperatorGroup
```

Root cause: CSV namespace has no OperatorGroup.

Fix:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: <name>
  namespace: <ns>
spec:
  targetNamespaces:
  - <ns>
```

Apply:

```bash
oc apply -f operatorgroup.yaml
```

### 8.2 `TooManyOperatorGroups`

```bash
oc get operatorgroup -n <ns>
```

Keep only one OperatorGroup in the namespace. Do not delete randomly; confirm which one matches the installed Operators.

### 8.3 `UnsupportedOperatorGroup`

Check CSV install modes:

```bash
oc get csv <csv> -n <ns> -o yaml | grep -A20 installModes
```

If the Operator supports only `OwnNamespace`, do not install it as `AllNamespaces`. If it supports `AllNamespaces`, cluster-wide install is possible, but RBAC scope and memory footprint might be larger.

### 8.4 Required CRD/API missing

Check requirement status:

```bash
oc get csv <csv> -n <ns> -o yaml | less
```

Search:

```text
requirementStatus
```

If a required CRD is missing, check whether another dependency Operator should be installed first.

### 8.5 `field is immutable`

Common during upgrades when the new CSV changes an immutable part of an existing Deployment, such as selector labels.

Symptoms:

```text
Deployment.apps "x" is invalid: spec.selector: Invalid value: field is immutable
```

Operational approach:

1. Do not force-edit generated resources first.
2. Check vendor release notes/known issues.
3. Confirm upgrade path and channel.
4. If vendor documents reinstall, plan a maintenance window.
5. Capture CSV, InstallPlan, Deployment YAML before deleting anything.

## 9. RBAC and ServiceAccount troubleshooting

Operator pods almost always run with a dedicated ServiceAccount created by OLM from the CSV permissions.

Find the ServiceAccount:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
oc get sa <sa> -n <ns> -o yaml
```

Inspect CSV permissions:

```bash
oc get csv <csv> -n <ns> -o yaml | less
```

Search:

```text
permissions:
clusterPermissions:
serviceAccountName:
```

Check effective permissions:

```bash
oc auth can-i list pods \
  --as system:serviceaccount:<operator_ns>:<sa> \
  -n <target_ns>

oc auth can-i update <resource>.<api_group> \
  --as system:serviceaccount:<operator_ns>:<sa> \
  -n <target_ns>

oc auth can-i get <cluster_resource>.<api_group> \
  --as system:serviceaccount:<operator_ns>:<sa> \
  --all-namespaces
```

Common RBAC log messages:

```text
forbidden: User "system:serviceaccount:..." cannot list resource "..." in API group "..."
failed to list *v1.Pod: pods is forbidden
cannot update resource "status"
```

Fix options:

- Prefer upgrading to a corrected Operator version if the CSV is wrong.
- Prefer vendor-documented RBAC fixes.
- Avoid manual edits to OLM-owned Roles/RoleBindings unless you understand that OLM may reconcile them.
- If you add temporary RBAC, document it and remove it after the vendor fix.

Temporary example:

```bash
oc create role <role_name> --verb=get,list,watch --resource=<resource> -n <target_ns>
oc adm policy add-role-to-user <role_name> system:serviceaccount:<operator_ns>:<sa> -n <target_ns>
```

For cluster-scoped permissions:

```bash
oc create clusterrole <role_name> --verb=get,list,watch --resource=<resource>.<api_group>
oc adm policy add-cluster-role-to-user <role_name> system:serviceaccount:<operator_ns>:<sa>
```

Use cluster-wide permissions carefully.

## 10. SCC and Pod Security Admission troubleshooting

OpenShift uses Security Context Constraints (SCC) and Kubernetes Pod Security Admission labels. Operator pods can fail because their security context is not allowed.

Symptoms:

```text
Error creating: pods "..." is forbidden: unable to validate against any security context constraint
would violate PodSecurity "restricted:latest"
container has runAsNonRoot and image will run as root
allowPrivilegeEscalation != false
```

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp | tail -100
oc get ns <ns> -o yaml | grep -E 'pod-security|scc.podSecurityLabelSync' -A5 -B5
oc get sa <sa> -n <ns> -o yaml
oc adm policy who-can use scc/anyuid
oc adm policy who-can use scc/privileged
```

Operational rule:

- Do not grant `privileged` or `anyuid` to an Operator ServiceAccount just because the pod failed.
- First verify vendor requirements.
- Check whether the Operator supports restricted mode.
- Use the least-privileged SCC required.
- Prefer installing certified Operators through supported channels because OLM-managed RBAC/SCC expectations are defined in the CSV and product docs.

If a vendor explicitly requires `anyuid`:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <operator_ns>
```

Document the exception:

```bash
oc annotate sa <serviceaccount> -n <operator_ns> \
  security.openshift.io/justification='Required by <vendor/operator/version>; reviewed on <date>'
```

## 11. Networking, DNS, proxy, and certificates

Operator pods normally need to reach:

- Kubernetes API server.
- OpenShift API resources and CRDs.
- Internal services/webhooks.
- External registries during install/upgrade if images are not mirrored.
- Cloud provider APIs for cloud/storage/network Operators.
- Product endpoints managed by the Operator.

### 11.1 Check DNS and service endpoints

```bash
oc get svc,endpoints,endpointslice -n <ns>
oc get networkpolicy -n <ns>
oc get egressfirewall -A 2>/dev/null || true
```

Run a debug pod in the same namespace if policy allows:

```bash
oc run net-debug -n <ns> --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside:

```bash
curl -k https://kubernetes.default.svc
getent hosts kubernetes.default.svc
getent hosts <service>.<namespace>.svc
curl -vk https://<service>.<namespace>.svc:<port>/healthz
```

Minimal images often do not include `nc` or `telnet`. Use `curl`, `getent`, `bash` TCP redirection, or install tools only in disposable debug pods where allowed.

### 11.2 Proxy issues

Symptoms:

```text
connection refused
proxyconnect tcp: x509: certificate signed by unknown authority
i/o timeout
dial tcp: lookup ... no such host
```

Check cluster proxy:

```bash
oc get proxy/cluster -o yaml
```

OLM-managed Operators can inherit cluster-wide proxy settings, and many support override through `Subscription.spec.config.env`.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operator
spec:
  config:
    env:
    - name: HTTP_PROXY
      value: http://proxy.example.com:8080
    - name: HTTPS_PROXY
      value: http://proxy.example.com:8080
    - name: NO_PROXY
      value: .cluster.local,.svc,10.0.0.0/8,api-int.example.com
```

### 11.3 Custom CA issues

Symptoms:

```text
x509: certificate signed by unknown authority
certificate signed by unknown authority
unable to verify the first certificate
```

Check:

```bash
oc get configmap -n openshift-config
oc get proxy/cluster -o yaml
oc describe pod <pod> -n <ns>
oc logs pod/<pod> -n <ns> --all-containers --tail=200
```

For some OLM-managed Operators, a trusted CA can be injected and mounted using `Subscription.spec.config` volumes and volume mounts. For many images, mounting at `/etc/ssl/certs` is required so the system trust store can be used. Follow the specific Operator documentation because trust paths vary by image base.

## 12. Webhook and APIService troubleshooting

Operators often install admission webhooks, conversion webhooks, or aggregated API services. A pod can be running, but the API path can still be broken.

### 12.1 Admission webhook failure

Symptoms:

```text
failed calling webhook
context deadline exceeded
service not found
no endpoints available for service
x509: certificate signed by unknown authority
```

Commands:

```bash
oc get validatingwebhookconfiguration,mutatingwebhookconfiguration | grep -i <operator>
oc get validatingwebhookconfiguration <name> -o yaml
oc get mutatingwebhookconfiguration <name> -o yaml
oc get svc,endpoints -n <operator_ns>
oc logs deploy/<operator_deployment> -n <operator_ns> --all-containers --tail=200
```

Check:

- Webhook service exists.
- Endpoints exist.
- Pod is Ready.
- `caBundle` is correct.
- Certificate secret exists and is mounted.
- NetworkPolicy does not block API server to webhook service.

Emergency mitigation is sometimes setting webhook `failurePolicy: Ignore`, but this weakens admission control and should be used only with vendor guidance or during controlled incident response.

### 12.2 APIService failure

```bash
oc get apiservice | grep -i <operator>
oc describe apiservice <apiservice_name>
oc get svc,endpoints -n <operator_ns>
oc logs deploy/<api_server_deployment> -n <operator_ns> --all-containers --tail=200
```

Common APIService conditions:

- `MissingEndpoints`
- `ServiceNotFound`
- `FailedDiscoveryCheck`
- TLS verification failure

If an APIService is unavailable, `kubectl/oc` discovery can slow down or fail for related API groups. Fix the serving pod, service, endpoints, or certificate.

## 13. Upgrade-specific Operator pod troubleshooting

Operator pod failures during upgrade are often different from day-2 runtime failures.

### 13.1 Before approving an upgrade

```bash
oc get sub <sub> -n <ns> -o yaml
oc get installplan -n <ns>
oc describe installplan <pending_ip> -n <ns>
oc get csv -n <ns>
oc get crd | grep -i <operator>
```

Review:

- New CSV version.
- Required permissions.
- New CRDs or CRD versions.
- Webhook/APIService changes.
- Deprecated API usage.
- Channel compatibility with your OpenShift version.
- Release notes and known issues.

Manual approvals are safer in production because they let administrators review permission and behavior changes before the pod is replaced.

### 13.2 Upgrade stuck with old and new CSVs

```bash
oc get csv -n <ns>
oc describe csv <new_csv> -n <ns>
oc describe csv <old_csv> -n <ns>
oc get deploy -n <ns>
```

Common reasons:

- New CSV failed.
- New Deployment could not become Ready.
- Immutable field error.
- New CRD conversion problem.
- Required API missing.
- OperatorGroup conflict.

Do not delete the old CSV until you understand whether it is still serving live workloads.

### 13.3 Operator pod starts but operands fail after upgrade

The Operator controller can be healthy while managed workloads fail. Check custom resources:

```bash
oc get crd | grep -i <operator>
oc api-resources | grep -i <operator>
oc get <custom_resource_kind> -A
oc describe <custom_resource_kind> <name> -n <operand_ns>
oc logs deploy/<operator_deployment> -n <operator_ns> --all-containers --tail=300
```

Look for reconcile errors in logs and `.status.conditions` on custom resources.

## 14. Reinstall and uninstall troubleshooting

Failed uninstall/reinstall is common when CRDs or custom resources remain.

### 14.1 Proper uninstall order

General safe order:

1. Remove or scale down operand custom resources as documented by the Operator.
2. Confirm operands are gone or intentionally retained.
3. Delete Subscription.
4. Delete CSV.
5. Remove leftover InstallPlans only if needed.
6. Remove OperatorGroup if namespace is dedicated and no longer needed.
7. Remove CRDs only when product documentation says it is safe and you understand all CR instances will be removed.

Commands:

```bash
oc get sub,csv,installplan,operatorgroup -n <ns>
oc delete sub <sub> -n <ns>
oc delete csv <csv> -n <ns>
oc get crd | grep -i <operator>
oc get namespaces | grep Terminating
```

### 14.2 Namespace stuck `Terminating`

Do not force-delete a namespace first. Find blocking resources.

```bash
oc get ns <ns> -o yaml
oc api-resources --verbs=list --namespaced -o name | xargs -n 1 oc get -n <ns> --ignore-not-found
oc get crd | grep -i <operator>
```

Check finalizers:

```bash
oc get <resource> <name> -n <ns> -o yaml | grep -A20 finalizers
```

Only remove finalizers when you know the controller responsible for cleanup is gone and the cleanup side effects are acceptable.

## 16. Evidence collection for support or RCA

Before deleting or patching resources, capture evidence.

```bash
mkdir -p operator-rCA

oc get clusterversion -o yaml > operator-rCA/clusterversion.yaml
oc get clusteroperators -o yaml > operator-rCA/clusteroperators.yaml
oc get nodes -o wide > operator-rCA/nodes.txt
oc get events -A --sort-by=.lastTimestamp > operator-rCA/events-all.txt

NS=<operator_namespace>
POD=<operator_pod_name>

oc get sub,csv,installplan,operatorgroup -n "$NS" -o yaml > operator-rCA/olm-objects-$NS.yaml
oc get pod "$POD" -n "$NS" -o yaml > operator-rCA/pod-$POD.yaml
oc describe pod "$POD" -n "$NS" > operator-rCA/pod-$POD-describe.txt
oc logs pod/$POD -n "$NS" --all-containers --tail=500 > operator-rCA/pod-$POD-logs.txt 2>&1
oc logs pod/$POD -n "$NS" --all-containers --previous --tail=500 > operator-rCA/pod-$POD-previous-logs.txt 2>&1

oc adm inspect ns/$NS --dest-dir=operator-rCA/inspect-$NS
oc adm must-gather --dest-dir=operator-rCA/must-gather

tar czf operator-pod-rca-$(date +%F-%H%M).tar.gz operator-rCA
```

Useful RCA fields:

- Time issue started.
- Change immediately before failure: OpenShift upgrade, Operator upgrade, registry/mirror change, proxy change, cert rotation, node maintenance, CR change.
- Exact pod status and restart count.
- CSV phase/reason/message.
- Subscription conditions.
- InstallPlan status.
- CatalogSource connection state.
- Events from namespace and node.
- Previous logs.
- Node pressure and kubelet/CRI-O logs if node-specific.

## 18. Real-world troubleshooting scenarios

### Scenario 1: Operator installation stuck; no Operator pod created

Symptoms:

```bash
oc get sub,csv,installplan -n openshift-logging
# Subscription exists, CSV missing or Pending, no operator pod
```

Approach:

```bash
oc describe sub <sub> -n openshift-logging
oc get installplan -n openshift-logging
oc describe installplan <ip> -n openshift-logging
oc get catalogsource -A
oc describe catalogsource redhat-operators -n openshift-marketplace
oc get pods -n openshift-marketplace
```

Likely causes:

- Manual InstallPlan not approved.
- CatalogSource unhealthy.
- Package/channel not available.
- Bundle unpack Job failed.
- Required API missing.

Fix:

- Approve pending InstallPlan if manual.
- Fix catalog source image pull/connectivity.
- Correct package/channel/source.
- Fix mirror registry and refresh failing subscription if bundle was inaccessible.

### Scenario 2: Catalog pod `ImagePullBackOff`

Symptoms:

```bash
oc get pods -n openshift-marketplace
# my-catalog-xxxxx 0/1 ImagePullBackOff
```

Approach:

```bash
oc describe pod my-catalog-xxxxx -n openshift-marketplace
oc get catsrc my-catalog -n openshift-marketplace -o yaml
oc get secret -n openshift-marketplace
```

Root cause examples:

- Catalog image in private registry.
- Secret not referenced in CatalogSource.
- Registry CA not trusted by nodes.
- Disconnected mirror path wrong.

Fix:

```bash
oc create secret docker-registry my-registry-pull-secret ... -n openshift-marketplace
oc patch catsrc my-catalog -n openshift-marketplace --type merge -p '{"spec":{"secrets":["my-registry-pull-secret"]}}'
```

### Scenario 3: Operator pod `CrashLoopBackOff` after upgrade

Symptoms:

```bash
oc get pods -n <ns>
oc get csv -n <ns>
# new CSV Succeeded or Installing, pod crashlooping
```

Approach:

```bash
oc logs pod/<pod> -n <ns> --previous --all-containers --tail=300
oc describe pod <pod> -n <ns>
oc describe csv <new_csv> -n <ns>
oc get sub <sub> -n <ns> -o yaml
```

Likely causes:

- New version requires new permissions.
- New version expects a Secret/ConfigMap/env var.
- New version incompatible with existing CR spec.
- New version has a bug.
- Memory limit too low.

Fix:

- Check release notes.
- Verify new CSV permissions and ServiceAccount access.
- Validate CR instances.
- Patch Subscription config if resource/proxy/env settings are supported.
- Rollback is not always straightforward in OLM; use supported channel/version procedure.

### Scenario 4: Operator pod `Pending` only on infra nodes

Symptoms:

```text
0/3 nodes are available: node(s) had taint {node-role.kubernetes.io/infra: }, that the pod didn't tolerate
```

Approach:

```bash
oc describe pod <pod> -n <ns>
oc get sub <sub> -n <ns> -o yaml
oc describe node <infra_node>
oc get ns <ns> -o yaml | grep node-selector -A3 -B3
```

Fix:

Patch Subscription toleration and node selector:

```bash
oc patch sub <sub> -n <ns> --type merge -p '
{
  "spec": {
    "config": {
      "nodeSelector": {
        "node-role.kubernetes.io/infra": ""
      },
      "tolerations": [
        {
          "key": "node-role.kubernetes.io/infra",
          "operator": "Exists",
          "effect": "NoSchedule"
        }
      ]
    }
  }
}'
```

### Scenario 5: CSV `UnsupportedOperatorGroup`

Symptoms:

```bash
oc describe csv <csv> -n <ns>
# Reason: UnsupportedOperatorGroup
```

Approach:

```bash
oc get operatorgroup -n <ns> -o yaml
oc get csv <csv> -n <ns> -o yaml | grep -A20 installModes
```

Fix:

- If CSV supports only `OwnNamespace`, install it in own namespace mode.
- If you need all namespaces, choose an Operator/channel that supports `AllNamespaces`.
- Avoid multiple OperatorGroups in the same namespace.

### Scenario 6: Operator pod cannot list resources in target namespace

Symptoms in logs:

```text
forbidden: User "system:serviceaccount:operator-ns:operator-sa" cannot list resource "foos" in API group "example.com" in namespace "app-ns"
```

Approach:

```bash
oc auth can-i list foos.example.com --as system:serviceaccount:operator-ns:operator-sa -n app-ns
oc get csv <csv> -n operator-ns -o yaml | less
oc get rolebinding,clusterrolebinding -A | grep operator-sa
```

Likely causes:

- Operator installed namespace-scoped but CR is in another namespace.
- OperatorGroup target namespace mismatch.
- CSV RBAC bug.
- RoleBinding deleted manually.

Fix:

- Correct OperatorGroup/install mode.
- Recreate OLM-owned resources by letting CSV reconcile.
- Reinstall if ownership is corrupted.
- Add temporary RBAC only with change control.

## 19. Production best practices

1. Use manual approval for important production Operators.
2. Review InstallPlans before approving upgrades.
3. Keep one OperatorGroup per Operator namespace unless you fully understand the impact.
4. Do not edit OLM-generated Deployments directly unless it is a temporary break-glass action.
5. Prefer `Subscription.spec.config` for supported pod placement, env, resources, tolerations, and affinity.
6. Mirror catalog, bundle, and Operator images for disconnected clusters.
7. Validate catalog health before planned Operator upgrades.
8. Capture evidence before deleting pods, CSVs, or Subscriptions.
9. Keep Operator namespaces clean: avoid mixing unrelated Operators with different scope needs.
10. Monitor Operator pod restarts, CSV phases, Subscription conditions, and CatalogSource status.
11. Document all manual RBAC/SCC exceptions.
12. Never force-delete CRDs or namespaces during business hours without understanding finalizers and custom resources.
13. Treat webhook failures as high-risk because they can block unrelated workloads.
14. Test channel changes and upgrades in a non-production cluster.
15. Maintain a runbook per critical Operator, including uninstall/reinstall and backup/restore behavior.

```text
|
+-- Is it a ClusterOperator? 
|   |
|   +-- yes -> oc get co, inspect platform operator namespace, check CVO/MCO/node/API health

|

|   |
|   +-- Pending              -> scheduling, node selector, taints, quota, volumes
|   +-- ImagePullBackOff     -> registry, mirror, pull secret, CA, DNS, proxy
|   +-- CrashLoopBackOff     -> previous logs, env, secret, RBAC, API, cert, memory
|   +-- CreateConfigError    -> missing Secret/ConfigMap/key/volume
|   +-- Running NotReady     -> readiness probe, webhook, dependency, cert
|   +-- OOMKilled/Evicted    -> resources or node pressure
|
+-- Is OLM healthy?
|   |
|   +-- no -> troubleshoot olm-operator/catalog-operator/packageserver/marketplace
|   +-- yes -> troubleshoot Operator-specific lifecycle and pod runtime
|
+-- Is catalog healthy?
|   |
|   +-- no -> fix CatalogSource pod, registry, gRPC state, package visibility
|   +-- yes -> fix Subscription/CSV/InstallPlan/OperatorGroup or pod runtime
```
