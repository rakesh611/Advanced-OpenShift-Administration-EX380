# Manual vs Automatic Approval in Operator Management

**Audience:** Advanced OpenShift Administration / DO380-style administration  
**Experience level:** Written for administrators with around 10 years of Linux, Kubernetes, and OpenShift operations experience  
**Main objects:** `Subscription`, `InstallPlan`, `ClusterServiceVersion`, `CatalogSource`, `OperatorGroup`  
**Primary control field:** `spec.installPlanApproval` in the `Subscription`

---

## 1. Executive Summary

In OpenShift Operator Management, **Manual vs Automatic approval** controls how Operator Lifecycle Manager, or **OLM**, applies an `InstallPlan` generated from a `Subscription`.

A `Subscription` tells OLM:

> “Install this Operator package from this `CatalogSource`, track this update channel, and keep the Operator aligned with that channel.”

OLM then resolves the required Operator bundle, dependencies, CRDs, RBAC, service accounts, deployments, webhooks, and other resources. It records the resolved action as an `InstallPlan`.

The approval strategy decides whether that `InstallPlan` is executed automatically or waits for a human or automation gate.

```yaml
spec:
  installPlanApproval: Automatic   # OLM approves generated install plans automatically
```

or:

```yaml
spec:
  installPlanApproval: Manual      # OLM waits until the install plan is approved
```

At senior administrator level, this is not only a UI choice. It is a **release governance control**. It affects outage risk, maintenance windows, GitOps workflow, security review, CRD lifecycle, RBAC changes, workload compatibility, and platform change management.

---

## 2. Where Approval Fits in the OLM Workflow

OLM uses several custom resources to install and update Operators.

```text
CatalogSource
    |
    | exposes package metadata, channels, bundles, CSVs
    v
PackageManifest / catalog metadata
    |
    | selected by administrator or GitOps manifest
    v
Subscription
    |
    | OLM resolves desired Operator version and dependencies
    v
InstallPlan
    |
    | approved automatically or manually
    v
ClusterServiceVersion (CSV)
    |
    | creates Operator deployment, RBAC, CRDs, webhooks, etc.
    v
Operator pod runs and manages operands
```

### Important objects

| Object | Role in approval flow |
|---|---|
| `CatalogSource` | Provides Operator metadata and update graph. |
| `Subscription` | Defines the package, channel, source, namespace, and approval strategy. |
| `InstallPlan` | Generated plan containing resources OLM will create or update. |
| `ClusterServiceVersion` / `CSV` | Represents one installed Operator version. |
| `OperatorGroup` | Defines which namespaces the Operator can target. |

The important lifecycle is:

1. Admin creates a `Subscription`.
2. OLM checks the catalog and resolves the correct Operator bundle.
3. OLM creates an `InstallPlan`.
4. The `InstallPlan` is either automatically approved or waits for approval.
5. After approval, OLM creates or updates resources.
6. The target `CSV` eventually reaches `Succeeded`, or it fails and requires troubleshooting.

---

## 3. Core Difference: Manual vs Automatic

| Area | Automatic approval | Manual approval |
|---|---|---|
| `Subscription` field | `spec.installPlanApproval: Automatic` | `spec.installPlanApproval: Manual` |
| Initial install | Install plan is approved automatically. | Install plan is created but waits for approval. |
| Future updates | New versions in the selected channel are applied automatically. | New versions create pending install plans. |
| Change control | Low friction, less human control. | High control, needs review/approval. |
| Best for | Low-risk Operators, test/dev clusters, lab environments. | Production, regulated environments, critical Operators. |
| Risk | Surprise update, CRD/RBAC changes, app behavior changes. | Delayed security fixes if pending plans are ignored. |
| Operational model | OLM-driven continuous update. | Admin/SRE-driven controlled update. |

## 4. Key Fields You Must Understand

### 4.1 `Subscription.spec.installPlanApproval`

This is the field most administrators think of when they say “manual or automatic approval.”

Example automatic subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operator
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
```

Example manual subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operator
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

If the field is omitted, many Operators default to automatic behavior, but you should not rely on implicit defaults in production GitOps. Explicit is better.

### 4.2 `InstallPlan.spec.approval`

This records the approval policy on the generated `InstallPlan`.

```yaml
spec:
  approval: Manual
```

or:

```yaml
spec:
  approval: Automatic
```

### 4.3 `InstallPlan.spec.approved`

This boolean determines whether the plan is allowed to run.

```yaml
spec:
  approved: false
```

For manual approval, the generated plan normally starts with:

```yaml
spec:
  approval: Manual
  approved: false
```

After approval:

```yaml
spec:
  approval: Manual
  approved: true
```

For automatic approval, the generated plan normally appears as:

```yaml
spec:
  approval: Automatic
  approved: true
```

### 4.4 `Subscription.status.installplan.name`

The subscription status commonly points to the related install plan.

```bash
oc get subscription <subscription-name> -n <namespace> \
  --template='{{.status.installplan.name}}{{"\n"}}'
```

### 4.5 `Subscription.status.installedCSV` and `currentCSV`

Useful fields when checking upgrade state:

```bash
oc get subscription <subscription-name> -n <namespace> -o yaml
```

Look for:

```yaml
status:
  installedCSV: example-operator.v1.2.0
  currentCSV: example-operator.v1.3.0
```

Interpretation:

- `installedCSV` is the version currently installed.
- `currentCSV` is the version OLM is trying to move toward or has resolved as current from the subscription stream.
- If they differ and the approval strategy is `Manual`, there might be a pending `InstallPlan`.

## 5. Automatic Approval in Depth

### 5.1 What happens during initial install

When you create a `Subscription` with automatic approval:

```yaml
installPlanApproval: Automatic
```

OLM performs these actions:

1. Reads the package and channel from the catalog.
2. Resolves the latest bundle in the selected channel.
3. Creates an `InstallPlan`.
4. Marks the plan as approved automatically.
5. Creates the required resources.
6. Creates or updates the target `ClusterServiceVersion`.
7. Starts the Operator deployment.
8. Marks the CSV as `Succeeded` when installation succeeds.

Typical command view:

```bash
oc get installplan -n example-operator
```

Example output:

```text
NAME            CSV                         APPROVAL    APPROVED
install-wzg94   example-operator.v1.2.0     Automatic   true
```

### 5.2 What happens during an update

If a newer version becomes available in the same selected channel:

```text
example-operator.v1.2.0 -> example-operator.v1.3.0
```

OLM creates a new `InstallPlan` and automatically approves it. The update starts without an administrator clicking **Approve** or patching anything.

This is convenient but risky in production. Operators are not just stateless applications. They can change:

- CRDs
- conversion webhooks
- validating/mutating webhooks
- RBAC rules
- controller behavior
- operand reconciliation logic
- default values
- upgrade jobs
- storage behavior
- API compatibility assumptions

### 5.3 Advantages of automatic approval

Automatic approval is useful when:

- You are running a lab, sandbox, or training cluster.
- You want fast adoption of bug fixes.
- The Operator is low-risk and does not control critical infrastructure.
- You have strong automated tests around the Operator and operands.
- You are using disposable environments.
- You want minimal manual administration.

### 5.4 Disadvantages of automatic approval

Automatic approval can create production issues when:

- The Operator manages stateful workloads such as storage, databases, backup, logging, or service mesh.
- An update changes CRDs or webhooks in a way that affects running workloads.
- An update requires new cloud IAM permissions.
- An update triggers operand upgrades immediately.
- A new version is pulled during business hours.
- Your SRE team does not know a change has started.
- A catalog refresh introduces a version you have not tested.

### 5.5 Where automatic approval is usually acceptable

Automatic approval can be acceptable for:

- Dev/test clusters
- Short-lived demo clusters
- Training clusters
- Non-critical utility Operators
- Operators with low blast radius
- Internal platforms with strong CI validation

Even then, monitor subscriptions and CSVs.

```bash
oc get subscriptions -A
oc get installplans -A
oc get csv -A
```

## 6. Manual Approval in Depth

### 6.1 What happens during initial install

When you create a `Subscription` with manual approval:

```yaml
installPlanApproval: Manual
```

OLM still resolves the package and creates an `InstallPlan`, but the plan is not executed until approved.

Example:

```bash
oc get installplan -n example-operator
```

Output:

```text
NAME            CSV                         APPROVAL   APPROVED
install-tsz2g   example-operator.v1.2.0     Manual     false
```

Until you approve the plan:

- The CSV might remain pending.
- The Operator deployment might not be created.
- The Operator APIs might not become available.
- The console may show the subscription as upgrading or requiring approval.

### 6.2 Approving manually from CLI

Find the plan:

```bash
oc get installplan -n example-operator
```

Review it:

```bash
oc describe installplan install-tsz2g -n example-operator
```

Approve it:

```bash
oc patch installplan install-tsz2g \
  -n example-operator \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

Watch the result:

```bash
watch 'oc get installplan,csv,pods -n example-operator'
```

### 6.3 Approving manually from web console

Typical path:

```text
Administrator perspective
  -> Operators
  -> Installed Operators
  -> Select Operator
  -> Subscription tab
  -> Upgrade Status / requires approval
  -> Preview Install Plan
  -> Approve
```

Before clicking **Approve**, review the listed resources.

### 6.4 What to review before approval

Do not approve blindly in production. Review the install plan and target CSV.

```bash
oc get installplan install-tsz2g -n example-operator -o yaml
```

Check:

- Target CSV version.
- CRDs being created or modified.
- ClusterRoles and ClusterRoleBindings.
- ServiceAccounts.
- Webhook configurations.
- Deployments.
- APIService resources.
- Required permissions.
- Any related operand upgrade notes from vendor documentation.

Useful commands:

```bash
# Show install plan details
oc describe installplan install-tsz2g -n example-operator

# Show CSV details
oc get csv -n example-operator
oc describe csv example-operator.v1.3.0 -n example-operator

# Inspect required permissions from CSV
oc get csv example-operator.v1.3.0 -n example-operator -o yaml | less
```

### 6.5 What happens during a future update

When a new version appears in the selected channel, OLM creates another `InstallPlan` with `approved: false`.

```text
NAME            CSV                         APPROVAL   APPROVED
install-k7f2m   example-operator.v1.3.0     Manual     false
```

No update happens until approval.

This gives you time to:

- Read release notes.
- Test in lower environments.
- Check CRD and API compatibility.
- Check RBAC and SCC changes.
- Confirm backup and restore plans.
- Schedule a maintenance window.
- Notify application teams.

## 7. Manual Approval Is a Change-Control Gate, Not a Rollback Strategy

A common mistake is thinking:

> “If I use Manual approval, I can easily roll back.”

That is not correct.

Manual approval delays moving forward. It does not automatically provide rollback.

After you approve and OLM installs a newer CSV:

- The old CSV might be replaced.
- CRDs might already be upgraded.
- Webhooks might already be changed.
- Operators might upgrade operands.
- Operand data formats might change.
- Downgrading might not be supported.

Treat approval as a **pre-change checkpoint**, not a rollback mechanism.

Before approving a critical Operator update, have:

- Backup of workloads and custom resources.
- Storage snapshot or application backup where relevant.
- Export of important CRs.
- Clear rollback documentation from the Operator vendor.
- Maintenance window.
- Monitoring and alert suppression plan if needed.

Example backup of custom resources:

```bash
oc get <custom-resource-kind> -A -o yaml > before-operator-upgrade-crs.yaml
```

Example export of subscription and CSV state:

```bash
oc get subscription,csv,installplan -n example-operator -o yaml > before-operator-upgrade-olm-state.yaml
```

## 8. Version Pinning with `startingCSV` and Manual Approval

If you want to install a specific Operator version, use `startingCSV` with manual approval.

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operator
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  startingCSV: example-operator.v1.2.0
  installPlanApproval: Manual
```

Why this matters:

- `startingCSV` says which CSV you want to start from.
- `Manual` prevents OLM from immediately moving beyond that version if a later version is already available in the channel.
- You approve only the plan you actually want.

Senior admin warning:

Do not use `startingCSV` as your only version-control mechanism. If the channel has a later version and automatic approval is enabled, OLM can continue forward according to the channel update graph.

For stable production pinning:

- Use manual approval.
- Use controlled catalog content in disconnected or mirrored environments when possible.
- Promote catalog index images through dev, stage, and prod.
- Approve install plans only after validation.

## 9. Namespace Co-location Caveat

Operator approval is not always isolated when many Operators share the same namespace.

In the OpenShift web console flow, installing an Operator with Manual approval can cause Operators installed in the same namespace to function with Manual approval behavior and be updated together. Therefore, if you need independent upgrade control, install Operators into separate namespaces where supported.

Practical example:

```text
openshift-operators namespace:
  - operator-a
  - operator-b
  - operator-c
```

If all are installed globally in `openshift-operators`, update behavior and dependency resolution can become coupled.

Better production pattern when independent control matters:

```text
operator-a-system namespace:
  - operator-a

operator-b-system namespace:
  - operator-b

operator-c-system namespace:
  - operator-c
```

This is especially important for:

- Logging Operators
- Storage Operators
- Networking Operators
- Security Operators
- Service mesh Operators
- Database Operators

## 10. Cloud Credential and Workload Identity Considerations

For clusters using cloud provider token authentication or workload identity mechanisms, manual approval becomes more important.

Examples:

- AWS STS
- Microsoft Entra Workload ID / Federated Identity
- Google Cloud Workload Identity

Why?

A new Operator version can require new cloud permissions. If automatic approval is enabled, the Operator might upgrade before the administrator updates IAM policies or cloud role permissions.

Production workflow:

1. Detect pending Operator update.
2. Review new CSV permissions.
3. Review vendor documentation for new cloud IAM requirements.
4. Update cloud role or credential configuration if required.
5. Approve install plan.
6. Validate Operator and operand health.

---

## 11. Disconnected / Restricted Network Environments

In disconnected OpenShift clusters, approval strategy interacts with catalog promotion.

Usually, disconnected environments use a mirrored catalog:

```text
Red Hat catalog -> mirror registry -> cluster CatalogSource
```

Automatic approval in disconnected environments means:

- Updates are automatic only after the mirrored catalog is updated and the cluster sees the newer bundle.
- If the catalog is promoted to production, OLM can update Operators automatically.

Manual approval in disconnected environments means:

- You can promote the catalog first.
- Then approve Operator updates in a controlled window.

Recommended production pattern:

```text
Dev catalog mirror -> test updates -> stage catalog mirror -> prod catalog mirror -> manual approval in prod
```

This separates **catalog availability** from **installation approval**.

## 13. Changing Approval Strategy After Installation

You can patch an existing `Subscription`.

### 13.1 Change from Automatic to Manual

```bash
oc patch subscription <subscription-name> \
  -n <namespace> \
  --type merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

This affects future install plans. It does not undo an update that is already approved and running.

### 13.2 Change from Manual to Automatic

```bash
oc patch subscription <subscription-name> \
  -n <namespace> \
  --type merge \
  -p '{"spec":{"installPlanApproval":"Automatic"}}'
```

Be careful. If pending updates exist, OLM might proceed after reconciliation. Review pending plans first.

Check pending plans:

```bash
oc get installplan -n <namespace> \
  -o custom-columns=NAME:.metadata.name,CSV:.spec.clusterServiceVersionNames,APPROVAL:.spec.approval,APPROVED:.spec.approved
```

## 14. Update Channel and Approval Strategy

A subscription tracks a channel:

```yaml
spec:
  channel: stable
```

Channel examples vary by Operator:

```text
stable
fast
candidate
stable-4.16
stable-v1
v1.2
v1.3
```

When you change to a newer channel:

- With `Automatic`, the update starts automatically.
- With `Manual`, OLM creates a pending plan that must be approved.

CLI patch example:

```bash
oc patch subscription <subscription-name> \
  -n <namespace> \
  --type merge \
  -p '{"spec":{"channel":"stable-v2"}}'
```

Then check:

```bash
oc get subscription <subscription-name> -n <namespace> -o yaml
oc get installplan -n <namespace>
oc get csv -n <namespace>
```

Senior admin warning:

Changing channels is not the same as rollback. OpenShift documentation warns that installed Operators cannot simply be changed to an older channel than the current channel. Plan forward movement carefully.

## 15. Operational Decision Matrix

### Use Automatic when:

- Cluster is non-production.
- Operator is low impact.
- Operator does not manage critical state.
- Fast fixes matter more than maintenance-window control.
- You have strong monitoring and easy rebuild.
- Updates have been validated elsewhere.

### Use Manual when:

- Production cluster.
- Regulated or change-controlled environment.
- Operator manages storage, networking, security, logging, monitoring, backup, identity, service mesh, or databases.
- Operator update can change CRDs or webhooks.
- Operator update can change RBAC or cloud IAM permissions.
- Maintenance windows are required.
- Application teams must validate operands after update.
- GitOps promotion is used.

### Simple rule for production

```text
Default to Manual for production.
Use Automatic only when the blast radius is understood and accepted.
```

## 16. Advanced Admin Workflow for Production Approval

A mature production process should look like this.

### Phase 1: Detect

```bash
oc get subscriptions -A
oc get installplans -A
oc get csv -A
```

Find pending manual install plans:

```bash
oc get installplans -A \
  -o custom-columns=NAMESPACE:.metadata.namespace,NAME:.metadata.name,CSV:.spec.clusterServiceVersionNames,APPROVAL:.spec.approval,APPROVED:.spec.approved \
  | grep Manual \
  | grep false
```

### Phase 2: Review

```bash
NS=<namespace>
PLAN=<installplan-name>

oc describe installplan "$PLAN" -n "$NS"
oc get installplan "$PLAN" -n "$NS" -o yaml > review-installplan.yaml
```

Check target CSV:

```bash
oc get installplan "$PLAN" -n "$NS" \
  -o jsonpath='{.spec.clusterServiceVersionNames[*]}{"\n"}'
```

Then:

```bash
CSV=<target-csv>
oc describe csv "$CSV" -n "$NS"
oc get csv "$CSV" -n "$NS" -o yaml > review-csv.yaml
```

### Phase 3: Risk check

Review:

- Does the CSV request broader permissions?
- Are new CRDs installed?
- Are existing CRDs changed?
- Are webhooks added or modified?
- Is an operand upgrade triggered?
- Does the vendor require pre-upgrade steps?
- Is the cluster version supported?
- Is the Operator channel correct?
- Is there enough capacity for new pods?
- Are Pod Security / SCC requirements changing?
- Are proxy, disconnected, or registry mirror settings compatible?

### Phase 4: Backup

At minimum:

```bash
oc get subscription,csv,installplan -n "$NS" -o yaml > olm-state-before.yaml
oc get all -n "$NS" -o yaml > namespace-workloads-before.yaml
```

For Operators managing CRDs:

```bash
oc api-resources --api-group=<operator-api-group>
oc get <kind> -A -o yaml > operator-custom-resources-before.yaml
```

### Phase 5: Approve

```bash
oc patch installplan "$PLAN" -n "$NS" \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### Phase 6: Monitor

```bash
watch "oc get installplan,csv,pods -n $NS"
```

Check events:

```bash
oc get events -n "$NS" --sort-by=.lastTimestamp
```

Check Operator logs:

```bash
oc logs -n "$NS" deployment/<operator-deployment-name>
```

### Phase 7: Validate operands

Operator installation succeeding is not enough. Validate the workloads the Operator manages.

Examples:

```bash
oc get <custom-resource-kind> -A
oc describe <custom-resource-kind> <name> -n <namespace>
oc get pods -n <operand-namespace>
oc get routes -A
oc get pvc -A
```

## 17. GitOps Considerations

Manual approval and GitOps need careful design because `InstallPlan` names are generated, for example:

```text
install-abcde
install-k7f2m
install-tsz2g
```

A pure static manifest cannot usually predefine the generated install plan name.

### Common GitOps pattern

Store the `Subscription` as code:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operator
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

Then approve through one of these controlled methods:

- Manual CLI command after review.
- CI/CD pipeline step.
- Argo CD sync hook Job.
- Custom approval controller.
- Policy engine workflow.

### Example approval Job pattern

Use with caution and only when your pipeline has already reviewed the version.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: approve-example-operator-installplan
  namespace: example-operator
spec:
  template:
    spec:
      restartPolicy: Never
      serviceAccountName: installplan-approver
      containers:
        - name: approve
          image: registry.redhat.io/openshift4/ose-cli:latest
          command:
            - /bin/bash
            - -c
            - |
              set -euo pipefail
              PLAN=$(oc get installplan -n example-operator \
                -o jsonpath='{.items[?(@.spec.approved==false)].metadata.name}')
              if [ -n "$PLAN" ]; then
                oc patch installplan "$PLAN" -n example-operator \
                  --type merge \
                  -p '{"spec":{"approved":true}}'
              fi
```

The service account needs permission to get and patch install plans in that namespace.

Example Role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: installplan-approver
  namespace: example-operator
rules:
  - apiGroups: ["operators.coreos.com"]
    resources: ["installplans"]
    verbs: ["get", "list", "watch", "patch"]
```

Example RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: installplan-approver
  namespace: example-operator
subjects:
  - kind: ServiceAccount
    name: installplan-approver
    namespace: example-operator
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: installplan-approver
```

Senior admin warning:

Do not create an automation that approves every pending install plan in production without checking target version, maintenance window, and risk category. That defeats the purpose of manual approval.

## 18. Troubleshooting Manual and Automatic Approval

### 18.1 Subscription stuck in `Upgrade available` or `requires approval`

Check install plans:

```bash
oc get installplan -n <namespace>
```

If you see:

```text
APPROVAL   APPROVED
Manual     false
```

The update is waiting for approval.

Approve after review:

```bash
oc patch installplan <installplan-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 18.2 No install plan created

Check subscription:

```bash
oc describe subscription <subscription-name> -n <namespace>
```

Check common problems:

- Wrong package name in `spec.name`.
- Wrong `CatalogSource` name.
- Wrong `sourceNamespace`.
- CatalogSource pod failing.
- CatalogSource image pull error.
- Disconnected registry mirror issue.
- Invalid channel name.
- OperatorGroup missing or invalid.
- Dependency resolution failure.

Commands:

```bash
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
oc describe catalogsource <catalogsource-name> -n openshift-marketplace
oc describe operatorgroup -n <namespace>
oc get packagemanifest -n openshift-marketplace | grep -i <operator>
```

### 18.3 InstallPlan approved but CSV not succeeding

Check CSV:

```bash
oc get csv -n <namespace>
oc describe csv <csv-name> -n <namespace>
```

Check pods:

```bash
oc get pods -n <namespace>
oc describe pod <operator-pod> -n <namespace>
oc logs <operator-pod> -n <namespace>
```

Check events:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common causes:

- Image pull failure.
- Missing pull secret.
- Invalid proxy or trusted CA configuration.
- RBAC denied.
- Pod Security/SCC violation.
- Webhook failure.
- CRD conflict.
- OperatorGroup conflict.
- Node scheduling problem.
- ResourceQuota or LimitRange blocking pod creation.

### 18.4 Automatic approval caused unexpected update

Immediate steps:

```bash
oc get subscription <subscription-name> -n <namespace> -o yaml
oc get installplan -n <namespace>
oc get csv -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Then:

1. Identify the new CSV.
2. Check Operator logs.
3. Check operand health.
4. Review CRD changes.
5. Confirm whether rollback is supported by vendor.
6. Consider patching future strategy to Manual:

```bash
oc patch subscription <subscription-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

### 18.5 Manual approval but update never proceeds after approval

Check whether the patch worked:

```bash
oc get installplan <installplan-name> -n <namespace> -o yaml | grep -A5 approved
```

Check install plan status:

```bash
oc describe installplan <installplan-name> -n <namespace>
```

Check OLM/catalog operator pods:

```bash
oc get pods -n openshift-operator-lifecycle-manager
oc logs -n openshift-operator-lifecycle-manager deployment/olm-operator
oc logs -n openshift-operator-lifecycle-manager deployment/catalog-operator
```

Possible causes:

- OLM controller issue.
- Dependency resolution issue.
- CatalogSource unavailable.
- Conflicting CSV in namespace.
- Required API not available.
- Failed resource creation.

### 18.6 Multiple pending install plans

List pending plans:

```bash
oc get installplans -A \
  -o custom-columns=NAMESPACE:.metadata.namespace,NAME:.metadata.name,CSV:.spec.clusterServiceVersionNames,APPROVAL:.spec.approval,APPROVED:.spec.approved
```

Approve one namespace at a time after review.

Avoid this in production unless you fully understand the blast radius:

```bash
for ns in $(oc get installplan -A --no-headers | awk '$4=="false" {print $1}' | sort -u); do
  oc get installplan -n "$ns"
done
```

Bulk approval can be useful in labs, but it is dangerous in production.

## 19. Security and Compliance View

Manual approval is often required by change-management processes because Operator updates can alter cluster-level security posture.

Review these before approving:

### 19.1 RBAC changes

```bash
oc get csv <csv-name> -n <namespace> -o yaml | grep -A50 permissions:
```

Look for:

- New cluster-wide permissions.
- Permissions to secrets.
- Permissions to security-sensitive resources.
- New admission webhooks.
- New APIService registrations.

### 19.2 CRD changes

```bash
oc get crd | grep -i <operator>
oc describe crd <crd-name>
```

Changing CRDs can affect:

- Validation schemas.
- Stored versions.
- Conversion webhooks.
- Existing custom resources.
- API clients and automation.

### 19.3 Webhook changes

```bash
oc get validatingwebhookconfiguration,mutatingwebhookconfiguration | grep -i <operator>
```

Webhook failures can block unrelated workload creation if the webhook is broad and has strict failure behavior.

### 19.4 Cloud IAM changes

For cloud Operators, check whether the new version needs additional permissions. Approving without IAM updates can leave the Operator degraded.

## 20. Best Practices for 10-Year Experienced Administrators

### 20.1 Production defaults

Use this default posture:

```text
Production: Manual
Non-production: Automatic or Manual depending on test strategy
Critical infrastructure Operators: Manual
Stateful/data Operators: Manual
Security Operators: Manual
Networking Operators: Manual
Cloud IAM-sensitive Operators: Manual
```

### 20.2 Separate Operators by operational ownership

Avoid installing many unrelated Operators into one namespace if you need independent lifecycle control.

### 20.3 Promote catalogs, not just YAML

In mature environments:

```text
Vendor catalog -> internal mirror -> dev -> stage -> prod
```

Do not let production discover untested catalog content directly if strict control is required.

### 20.4 Keep approval visible

Create monitoring around pending install plans.

Example Prometheus idea:

```text
Alert when InstallPlan approved=false for more than X hours/days
```

Even without a custom alert, run regular checks:

```bash
oc get installplans -A | grep Manual | grep false
```

### 20.5 Always document approval

For critical Operators, record:

- Old CSV.
- New CSV.
- Subscription channel.
- InstallPlan name.
- Approval time.
- Approver.
- Release notes reviewed.
- Backup completed.
- Validation results.

### 20.6 Do not approve based only on “Succeeded” in console

`CSV Succeeded` means the Operator installed successfully. It does not guarantee that every operand is healthy.

Always check operand-specific resources.

### 20.7 Be careful with automatic approval during cluster upgrades

Cluster upgrades and Operator upgrades can happen close together. Keep critical Operators on Manual if you want to sequence changes:

```text
1. Upgrade OpenShift z-stream or minor version.
2. Validate cluster operators and nodes.
3. Promote compatible Operator catalog.
4. Approve add-on Operator updates.
5. Validate operands.
```

## 21. Exam and Interview Focus Points

For Advanced OpenShift Administration, you should be able to answer these clearly.

### Question: What controls manual vs automatic approval?

Answer:

```yaml
spec:
  installPlanApproval: Manual
```

or:

```yaml
spec:
  installPlanApproval: Automatic
```

in the `Subscription` object.

### Question: What object do you approve?

Answer:

You approve the generated `InstallPlan`, normally by setting:

```yaml
spec:
  approved: true
```

### Question: How do you find the pending install plan?

```bash
oc get installplan -n <namespace>
```

or from the subscription:

```bash
oc get subscription <subscription-name> -n <namespace> \
  --template='{{.status.installplan.name}}{{"\n"}}'
```

### Question: How do you approve from CLI?

```bash
oc patch installplan <installplan-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### Question: What happens with automatic approval when a new version appears in the channel?

Answer:

OLM creates and approves an install plan automatically, so the Operator update starts without administrator approval.

### Question: Why use manual approval?

Answer:

To control update timing, review CRDs/RBAC/webhooks/IAM changes, validate release notes, and align with maintenance windows.

### Question: Is manual approval a rollback mechanism?

Answer:

No. It is a pre-update gate. Once approved, CRDs, webhooks, operands, and data might change. Rollback depends on the Operator/vendor support.

## 22. Common Real-World Scenarios

### Scenario 1: Logging Operator in production

Recommended:

```yaml
installPlanApproval: Manual
```

Reason:

Logging Operators can affect collectors, log pipelines, storage, schemas, and integrations with external systems such as Loki, Elasticsearch, or SIEM tools.

### Scenario 2: Local Storage Operator

Recommended:

```yaml
installPlanApproval: Manual
```

Reason:

Storage Operators are high-risk because they can impact persistent volumes and node-level storage configuration.

### Scenario 3: Demo Operator in lab

Recommended:

```yaml
installPlanApproval: Automatic
```

Reason:

Low business risk and faster setup.

### Scenario 4: Operator needs cloud credentials

Recommended:

```yaml
installPlanApproval: Manual
```

Reason:

A new Operator version might require updated IAM permissions before it can work correctly.

### Scenario 5: GitOps-controlled platform

Recommended:

```yaml
installPlanApproval: Manual
```

Reason:

You want to separate declaration of desired subscription from approval of a specific resolved update.

## 24. Deep Mental Model

Think of `Subscription` as the **desired tracking relationship**:

```text
package + channel + catalog + namespace + approval policy
```

Think of `InstallPlan` as the **resolved executable change**:

```text
These exact resources will be created or updated to install this exact CSV.
```

Think of `Manual approval` as:

```text
Resolve now, execute later after approval.
```

Think of `Automatic approval` as:

```text
Resolve now, execute immediately.
```

In senior operations, the main question is not:

> “Which option is easier?”

The real question is:

> “Who should control the timing and risk of Operator changes: OLM automatically, or the platform operations process?”

For most production OpenShift clusters, the safest answer is:

```text
Let OLM resolve updates, but let administrators approve execution.
```

That means `Manual`.

---

## 25. Final Recommendations

1. Use **Manual approval** for production and critical Operators.
2. Use **Automatic approval** only where the risk is low or fully automated validation exists.
3. Always review the target CSV and install plan before approving.
4. Do not confuse manual approval with rollback.
5. Keep Operators in separate namespaces when independent lifecycle control matters.
6. Use `startingCSV` plus `Manual` when you need to start at a specific version.
7. Avoid broad bulk approval in production.
8. Monitor pending install plans so security fixes are not forgotten.
9. For cloud workload identity or STS-based clusters, prefer or require Manual approval because permission changes may be needed before update.
10. Treat Operator updates like platform changes, not simple application redeployments.
