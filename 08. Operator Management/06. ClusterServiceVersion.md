## 1. What is ClusterServiceVersion?

A **ClusterServiceVersion**, commonly called **CSV**, is a namespaced custom resource used by **Operator Lifecycle Manager (OLM Classic)** to represent one specific installed version of an Operator.

In simple language:

> A CSV is the installed Operator version record that tells OLM what the Operator is, what version it is, what permissions it needs, what CRDs or APIs it owns, what dependencies it requires, and how to deploy the Operator controller.

The object kind is:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: ClusterServiceVersion
```

Even though the name starts with **Cluster**, a CSV object is **namespaced**. You normally find it in the namespace where the Operator is installed, for example:

```bash
oc get csv -n openshift-operators
oc get csv -n openshift-logging
oc get csv -n openshift-storage
```

A CSV is not the same as a `ClusterOperator`.

| Object | Managed by | Purpose |
|---|---|---|
| `ClusterServiceVersion` | OLM Classic | Represents an installed OLM-managed application Operator version |
| `ClusterOperator` | Cluster Version Operator (CVO) | Represents core OpenShift platform Operators such as kube-apiserver, authentication, console, ingress, monitoring |
| `Subscription` | OLM Catalog Operator | Tracks a package/channel and triggers install or upgrade |
| `InstallPlan` | OLM Catalog Operator | Lists the resources OLM must create for install or upgrade |

A senior admin should think of the CSV as the **runtime contract** between the Operator package and OLM.

## 2. Where CSV fits in Operator Management

When you install an Operator from the OpenShift web console or CLI, you are normally not creating a CSV directly. You usually create a `Subscription`.

Typical flow:

```text
CatalogSource
   ↓
PackageManifest / package metadata
   ↓
Subscription
   ↓
InstallPlan
   ↓
ClusterServiceVersion
   ↓
Operator Deployment + ServiceAccount + RBAC + CRDs/API Services
   ↓
Operator Pod starts reconciling custom resources
```

Example:

```bash
oc get catalogsource -n openshift-marketplace
oc get packagemanifest
oc get subscription -n openshift-operators
oc get installplan -n openshift-operators
oc get csv -n openshift-operators
oc get deploy -n openshift-operators
```

The CSV appears after OLM resolves the requested package version and begins installing the Operator.

## 3. CSV as an operator package, not just a YAML file

A CSV is like a package manifest in Linux package management.

For example:

| Linux package world | OLM world |
|---|---|
| RPM package metadata | CSV metadata |
| Package version | `spec.version` |
| Dependency metadata | `required` CRDs/APIServices |
| Post-install objects | install strategy resources |
| Required permissions | `permissions` / `clusterPermissions` |
| Package upgrade path | `replaces`, `skips`, skip ranges, catalog graph |
| Installed package database | CSV objects in namespace |

So, when you see:

```bash
oc get csv -n openshift-operators
```

You are effectively seeing installed OLM Operator versions.

Example output:

```text
NAME                                      DISPLAY                    VERSION   REPLACES                                  PHASE
elasticsearch-operator.v5.8.15            OpenShift Elasticsearch    5.8.15    elasticsearch-operator.v5.8.14            Succeeded
cluster-logging.v6.2.1                    Red Hat OpenShift Logging  6.2.1     cluster-logging.v6.2.0                    Succeeded
```

The CSV is more than display information. It also contains the installation strategy and the permissions OLM will create.

## 4. Important OpenShift objects related to CSV

### 4.1 CatalogSource

A `CatalogSource` provides Operator catalog content.

Example:

```bash
oc get catalogsource -n openshift-marketplace
```

Common catalog sources:

```text
redhat-operators
certified-operators
community-operators
redhat-marketplace
```

A catalog contains packages, channels, bundles, CRDs, and CSV definitions.

---

### 4.2 PackageManifest

A `PackageManifest` is a discovery view of packages available from catalog sources.

Example:

```bash
oc get packagemanifest | grep -i logging
oc describe packagemanifest cluster-logging
```

You use it to identify package name, channels, default channel, catalog source, and install modes.

---

### 4.3 Subscription

A `Subscription` says:

> Install this package from this catalog source and keep it on this channel.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: cluster-logging
  namespace: openshift-logging
spec:
  channel: stable-6.2
  installPlanApproval: Manual
  name: cluster-logging
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

The Subscription does not directly deploy the Operator pod. It drives OLM to create an InstallPlan and eventually a CSV.

---

### 4.4 InstallPlan

An `InstallPlan` is the resolved list of objects OLM will create.

Example:

```bash
oc get installplan -n openshift-logging
oc describe installplan <installplan-name> -n openshift-logging
```

For manual approval:

```bash
oc patch installplan <installplan-name> \
  -n openshift-logging \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

The InstallPlan usually references one or more CSV names:

```yaml
spec:
  clusterServiceVersionNames:
  - cluster-logging.v6.2.1
```

---

### 4.5 OperatorGroup

An `OperatorGroup` defines the namespace scope for Operators in a namespace.

Example:

```bash
oc get operatorgroup -n openshift-operators
oc describe operatorgroup <name> -n openshift-operators
```

An OperatorGroup decides whether the Operator watches:

- only its own namespace,
- one selected namespace,
- multiple selected namespaces,
- or all namespaces.

CSV install mode must support the OperatorGroup scope. If the CSV does not support the OperatorGroup scope, CSV installation can fail with an unsupported OperatorGroup reason.

---

### 4.6 OperatorCondition

OLM creates an `OperatorCondition` for each CSV it reconciles. Operators can use it to communicate conditions back to OLM.

Example:

```bash
oc get operatorcondition -n <operator-namespace>
oc describe operatorcondition <name> -n <operator-namespace>
```

This is more common in advanced troubleshooting and Operator authoring scenarios.

---

## 5. CSV lifecycle flow

A normal CSV lifecycle looks like this:

```text
1. User creates Subscription
2. Catalog Operator resolves desired package/version/channel
3. Catalog Operator creates InstallPlan
4. InstallPlan is approved automatically or manually
5. OLM creates CSV and required resources
6. OLM checks dependencies and OperatorGroup compatibility
7. OLM creates ServiceAccount, Roles, RoleBindings, ClusterRoles, ClusterRoleBindings, Deployments
8. Operator Deployment becomes available
9. CSV phase becomes Succeeded
10. Operator starts reconciling its custom resources
```

You can observe this flow with:

```bash
watch -n2 'oc get sub,installplan,csv,deploy,pod -n <operator-namespace>'
```

For example:

```bash
watch -n2 'oc get sub,ip,csv,deploy,pod -n openshift-logging'
```

## 6. CSV namespace behavior

A CSV is namespaced. The namespace is important because OLM uses it to decide where to install the Operator controller and where to place related resources.

Common patterns:

### 6.1 Cluster-wide Operator namespace

Many Red Hat Operators are installed into product-specific namespaces:

```text
openshift-logging
openshift-storage
openshift-cnv
openshift-nmstate
openshift-gitops-operator
```

Or into the generic namespace:

```text
openshift-operators
```

### 6.2 All namespaces mode

If an Operator is installed for **All namespaces**, the main CSV usually exists in the installation namespace, often:

```text
openshift-operators
```

OLM can also create **copied CSVs** in target namespaces so users can see that the Operator is available there.

### 6.3 Single namespace mode

If installed in one project, the CSV usually exists in that project:

```bash
oc get csv -n my-operator-project
```

### 6.4 Multiple namespace mode

Some Operators support watching multiple namespaces. This is controlled by OperatorGroup target namespaces and CSV install modes.

## 7. CSV YAML anatomy

A simplified CSV looks like this:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: ClusterServiceVersion
metadata:
  name: example-operator.v1.2.3
  namespace: example-operators
  annotations:
    capabilities: Seamless Upgrades
spec:
  displayName: Example Operator
  description: Example Operator manages ExampleApp resources.
  version: 1.2.3
  maturity: stable

  provider:
    name: Example Corp

  maintainers:
  - name: Platform Team
    email: platform@example.com

  installModes:
  - type: OwnNamespace
    supported: true
  - type: SingleNamespace
    supported: true
  - type: MultiNamespace
    supported: false
  - type: AllNamespaces
    supported: true

  install:
    strategy: deployment
    spec:
      permissions:
      - serviceAccountName: example-operator
        rules:
        - apiGroups: [""]
          resources: ["pods", "services"]
          verbs: ["get", "list", "watch"]

      clusterPermissions:
      - serviceAccountName: example-operator
        rules:
        - apiGroups: ["example.com"]
          resources: ["exampleapps", "exampleapps/status"]
          verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

      deployments:
      - name: example-operator-controller-manager
        spec:
          replicas: 1
          selector:
            matchLabels:
              app: example-operator
          template:
            metadata:
              labels:
                app: example-operator
            spec:
              serviceAccountName: example-operator
              containers:
              - name: manager
                image: registry.example.com/example-operator@sha256:...
                command:
                - /manager

  customresourcedefinitions:
    owned:
    - name: exampleapps.example.com
      version: v1
      kind: ExampleApp
      displayName: Example App
      description: Represents an example application.
    required: []

status:
  phase: Succeeded
  reason: InstallSucceeded
  message: install strategy completed with no errors
```

Important parts:

| Section | Meaning |
|---|---|
| `metadata.name` | Unique CSV name, usually includes Operator version |
| `metadata.namespace` | Namespace where the Operator is installed |
| `spec.version` | Operator version |
| `spec.displayName` | UI display name |
| `spec.installModes` | Supported Operator scopes |
| `spec.install.strategy` | Usually `deployment` |
| `spec.install.spec.permissions` | Namespaced RBAC |
| `spec.install.spec.clusterPermissions` | Cluster-wide RBAC |
| `spec.install.spec.deployments` | Operator controller Deployment template |
| `spec.customresourcedefinitions.owned` | CRDs owned by this Operator |
| `spec.customresourcedefinitions.required` | CRDs this Operator depends on |
| `status.phase` | Current CSV phase |
| `status.reason` | Short reason |
| `status.message` | Human-readable status/troubleshooting message |

## 8. Deep explanation of important CSV spec fields

### 8.1 `metadata.name`

Example:

```yaml
metadata:
  name: cluster-logging.v6.2.1
```

Best practice:

```text
<operator-package-name>.v<semantic-version>
```

Why version in name?

Because each CSV represents a specific version. During upgrades, the new CSV replaces the previous CSV.

---

### 8.2 `spec.displayName`

Used by the web console and OperatorHub display.

Example:

```yaml
spec:
  displayName: Red Hat OpenShift Logging
```

This is not the package name. It is the human-friendly name.

---

### 8.3 `spec.description`

Explains what the Operator does.

Example:

```yaml
description: |
  The Example Operator manages lifecycle operations for ExampleApp custom resources.
```

This appears in UI and helps admins understand the Operator before installation.

---

### 8.4 `spec.version`

Example:

```yaml
version: 1.2.3
```

This is the Operator version. It usually follows semantic versioning.

Important:

- CSV name and `spec.version` should align.
- Upgrade graph resolution uses package metadata, channels, and CSV version/replacement information.
- A new Operator release normally creates a new CSV.

---

### 8.5 `spec.release`

Some CSVs can use a `release` field to distinguish packaging builds for the same Operator version.

Example:

```yaml
spec:
  version: 1.2.3
  release: "1"
```

Use case:

```text
same Operator functionality version, but different bundle packaging metadata
```

Examples:

```text
example-operator-v1.2.3-1
example-operator-v1.2.3-2
example-operator-v1.2.3-rc.1
```

As an OpenShift administrator, you normally inspect this field rather than modifying it.

---

### 8.6 `spec.provider`

Example:

```yaml
provider:
  name: Red Hat
```

This tells who publishes the Operator.

---

### 8.7 `spec.maintainers`

Example:

```yaml
maintainers:
- name: Platform Engineering
  email: platform@example.com
```

Used mainly for catalog and UI metadata.

---

### 8.8 `spec.keywords`

Example:

```yaml
keywords:
- logging
- observability
- loki
```

Used for search/discovery.

---

### 8.9 `spec.maturity`

Example:

```yaml
maturity: stable
```

Possible maturity values often include:

```text
planning
pre-alpha
alpha
beta
stable
mature
inactive
deprecated
```

Do not confuse this with Operator capability level.

---

### 8.10 `metadata.annotations.capabilities`

Example:

```yaml
metadata:
  annotations:
    capabilities: Seamless Upgrades
```

Common capability levels:

```text
Basic Install
Seamless Upgrades
Full Lifecycle
Deep Insights
Auto Pilot
```

Meaning:

| Capability | Practical meaning |
|---|---|
| Basic Install | Operator installs and starts |
| Seamless Upgrades | Operator supports upgrades |
| Full Lifecycle | Operator can manage full lifecycle of operands |
| Deep Insights | Operator exposes metrics/events/status insights |
| Auto Pilot | Operator can automate operational decisions |

For admin work, treat capability level as useful metadata, not a guarantee that production upgrades are risk-free.

---

### 8.11 `spec.installModes`

Example:

```yaml
installModes:
- type: OwnNamespace
  supported: true
- type: SingleNamespace
  supported: true
- type: MultiNamespace
  supported: false
- type: AllNamespaces
  supported: true
```

Install modes tell OLM which OperatorGroup scopes the Operator supports.

| Install mode | Meaning |
|---|---|
| `OwnNamespace` | Operator watches the namespace where it is installed |
| `SingleNamespace` | Operator watches one selected namespace |
| `MultiNamespace` | Operator watches multiple selected namespaces |
| `AllNamespaces` | Operator watches the whole cluster |

If the OperatorGroup target scope does not match a supported install mode, CSV installation can fail.

Example check:

```bash
oc get csv <csv-name> -n <ns> -o jsonpath='{.spec.installModes}{"\n"}'
oc get operatorgroup -n <ns> -o yaml
```

---

### 8.12 `spec.install.strategy`

Most CSVs use:

```yaml
install:
  strategy: deployment
```

This means OLM installs the Operator by creating one or more Kubernetes Deployments.

The Deployment template is inside:

```yaml
spec:
  install:
    spec:
      deployments:
      - name: ...
        spec:
          ...
```

A CSV can deploy multiple Deployments, though most Operators use one controller-manager Deployment.

---

### 8.13 `spec.install.spec.deployments`

This section is similar to a normal Kubernetes Deployment.

Example:

```yaml
install:
  strategy: deployment
  spec:
    deployments:
    - name: example-operator-controller-manager
      spec:
        replicas: 1
        template:
          spec:
            serviceAccountName: example-operator
            containers:
            - name: manager
              image: registry.example.com/example-operator@sha256:...
```

OLM uses this template to create or update the Operator controller Deployment.

Common admin checks:

```bash
oc get csv <csv> -n <ns> -o jsonpath='{.spec.install.spec.deployments[*].name}{"\n"}'

oc get deploy -n <ns>

oc describe deploy <deployment-name> -n <ns>
```

---

### 8.14 `spec.install.spec.permissions`

This defines **namespaced RBAC**.

Example:

```yaml
permissions:
- serviceAccountName: example-operator
  rules:
  - apiGroups: [""]
    resources: ["pods", "services", "configmaps"]
    verbs: ["get", "list", "watch"]
```

OLM creates:

```text
ServiceAccount
Role
RoleBinding
```

This gives the Operator access inside the namespace.

---

### 8.15 `spec.install.spec.clusterPermissions`

This defines **cluster-wide RBAC**.

Example:

```yaml
clusterPermissions:
- serviceAccountName: example-operator
  rules:
  - apiGroups: ["example.com"]
    resources: ["exampleapps", "exampleapps/status"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
```

OLM creates:

```text
ServiceAccount
ClusterRole
ClusterRoleBinding
```

This is security-sensitive.

A senior admin should always inspect this before approving Operators in sensitive clusters:

```bash
oc get csv <csv> -n <ns> -o yaml | less
```

Or focused view:

```bash
oc get csv <csv> -n <ns> -o jsonpath='{.spec.install.spec.clusterPermissions}' | jq
```

If you do not have `jq`:

```bash
oc get csv <csv> -n <ns> -o yaml | sed -n '/clusterPermissions:/,/deployments:/p'
```

---

### 8.16 `spec.customresourcedefinitions.owned`

Owned CRDs are APIs provided by this Operator.

Example:

```yaml
customresourcedefinitions:
  owned:
  - name: exampleapps.example.com
    version: v1
    kind: ExampleApp
    displayName: Example App
    description: Example application managed by Example Operator.
```

This tells OLM and users:

```text
This Operator owns and reconciles ExampleApp custom resources.
```

Admin checks:

```bash
oc get csv <csv> -n <ns> \
  -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\t"}{.kind}{"\t"}{.version}{"\n"}{end}'
```

Then check CRDs:

```bash
oc get crd | grep example.com
```

---

### 8.17 `spec.customresourcedefinitions.required`

Required CRDs are dependencies.

Example:

```yaml
customresourcedefinitions:
  required:
  - name: certificates.cert-manager.io
    version: v1
    kind: Certificate
```

Meaning:

```text
This Operator needs another API to exist before it can work properly.
```

If a required CRD is missing, the CSV can remain in `Pending` or fail requirement checks.

---

### 8.18 `spec.apiservicedefinitions.owned`

Some Operators expose aggregated API services through Kubernetes API aggregation.

Example:

```yaml
apiservicedefinitions:
  owned:
  - group: packages.operators.coreos.com
    version: v1
    kind: PackageManifest
    name: packagemanifests
```

This is more advanced than normal CRDs. If APIService availability is broken, `oc api-resources` can show discovery errors.

Admin checks:

```bash
oc get apiservice
oc describe apiservice <name>
oc get csv <csv> -n <ns> -o yaml | sed -n '/apiservicedefinitions:/,/customresourcedefinitions:/p'
```

---

### 8.19 `spec.webhookdefinitions`

Operators can ship admission webhooks.

Example types:

```text
validating admission webhook
mutating admission webhook
conversion webhook
```

Admin impact:

- OLM can manage webhook lifecycle.
- Bad webhook availability can block resource creation.
- Expired or broken webhook certificates can cause admission failures.
- Network policy or service issues can break webhook calls.

Troubleshooting:

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc describe validatingwebhookconfiguration <name>
oc get svc,endpoints -n <operator-namespace>
oc logs deploy/<operator-deployment> -n <operator-namespace>
```

---

### 8.20 `spec.relatedImages`

Example:

```yaml
relatedImages:
- name: operand
  image: registry.example.com/example-operand@sha256:...
```

This is important for disconnected environments because catalog mirroring tools use it to identify images that must be mirrored.

Admin note:

```text
Prefer digest-pinned images in production bundles.
```

---

### 8.21 `spec.replaces`

Example:

```yaml
replaces: example-operator.v1.2.2
```

This means:

```text
This CSV replaces the older CSV named example-operator.v1.2.2.
```

Used in upgrade graph resolution.

---

### 8.22 `spec.skips`

Example:

```yaml
skips:
- example-operator.v1.2.0
- example-operator.v1.2.1
```

This tells catalog graph creation to skip listed versions during upgrades.

---

### 8.23 `metadata.annotations.olm.skipRange`

Example:

```yaml
metadata:
  annotations:
    olm.skipRange: '>=1.0.0 <1.2.3'
```

This allows upgrade graph behavior where a new bundle can replace a range of older versions.

As an admin, you inspect this when upgrades do not follow the path you expected.

---

### 8.24 `metadata.annotations.olm.targetNamespaces`

Example:

```yaml
metadata:
  annotations:
    olm.targetNamespaces: ns1,ns2
```

OLM uses this annotation to communicate the OperatorGroup target namespaces into the Operator deployment.

Many Operators read this environment variable or annotation indirectly to know what namespace scope they should watch.

## 9. CSV status, phases, reasons, and conditions

The `status` section is the first place to troubleshoot a CSV.

Command:

```bash
oc get csv <csv-name> -n <namespace> -o yaml
```

Focused:

```bash
oc get csv <csv-name> -n <namespace> -o jsonpath='{.status.phase}{"\n"}{.status.reason}{"\n"}{.status.message}{"\n"}'
```

### 9.1 Common CSV phases

| Phase | Meaning | Admin action |
|---|---|---|
| `Pending` | CSV accepted but install strategy not attempted, often due to unmet requirements | Check requirements, OperatorGroup, CRDs, InstallPlan |
| `InstallReady` | Requirements are met; install strategy ready to run | Usually wait or inspect OLM logs if stuck |
| `Installing` | OLM is creating resources or waiting for deployment readiness | Check Deployment, Pod, events, image pulls, SCC, RBAC |
| `Succeeded` | OLM created required resources and Operator is installed | Normal state |
| `Failed` | Install strategy failed | Inspect status reason/message and OLM logs |
| `Unknown` | OLM could not determine state | Check OLM controller health and logs |

List phases:

```bash
oc get csv -A
```

Example:

```text
NAMESPACE            NAME                         DISPLAY              VERSION   REPLACES   PHASE
openshift-logging    cluster-logging.v6.2.1       OpenShift Logging    6.2.1                Succeeded
```

### 9.2 Important status fields

```yaml
status:
  phase: Failed
  reason: UnsupportedOperatorGroup
  message: operatorgroup targets multiple namespaces but CSV does not support MultiNamespace
```

Important fields:

| Field | Meaning |
|---|---|
| `status.phase` | High-level lifecycle phase |
| `status.reason` | Machine-readable short reason |
| `status.message` | Human-readable detailed message |
| `status.requirementStatus` | Dependency and requirement status |
| `status.conditions` | Historical condition transitions |

### 9.3 Requirement status

Example command:

```bash
oc get csv <csv-name> -n <namespace> -o jsonpath='{.status.requirementStatus}' | jq
```

Without `jq`:

```bash
oc get csv <csv-name> -n <namespace> -o yaml | sed -n '/requirementStatus:/,/lastTransitionTime:/p'
```

This section can show whether required CRDs, service accounts, roles, deployments, or APIs are present.

### 9.4 Events

Always check namespace events:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

For OLM namespace:

```bash
oc get events -n openshift-operator-lifecycle-manager --sort-by=.lastTimestamp
```

## 10. RBAC and security impact of CSV

CSV is one of the most important security objects in Operator management because it declares what permissions the Operator needs.

### 10.1 Why CSV RBAC matters

An Operator is a controller. A controller usually has continuous access to Kubernetes APIs.

If CSV grants wide permissions, the Operator can potentially:

- list secrets,
- create pods,
- modify workloads,
- create cluster roles,
- watch all namespaces,
- modify CRDs,
- manage admission webhooks,
- affect cluster-wide resources.

Before approving a high-privilege Operator, inspect:

```bash
oc get csv <csv> -n <ns> -o yaml | sed -n '/permissions:/,/deployments:/p'
```

And:

```bash
oc get csv <csv> -n <ns> -o yaml | sed -n '/clusterPermissions:/,/deployments:/p'
```

### 10.2 Namespaced permissions vs cluster permissions

| CSV section | Kubernetes objects created | Scope |
|---|---|---|
| `permissions` | Role, RoleBinding | Namespace |
| `clusterPermissions` | ClusterRole, ClusterRoleBinding | Cluster-wide |

### 10.3 ServiceAccount used by Operator

Get ServiceAccount from CSV:

```bash
oc get csv <csv> -n <ns> \
  -o jsonpath='{range .spec.install.spec.deployments[*]}{.name}{" => "}{.spec.template.spec.serviceAccountName}{"\n"}{end}'
```

Then check bindings:


### 10.4 Production security review checklist

Before approving an Operator in production:

```text
[ ] Is the Operator from a trusted catalog?
[ ] Is it Red Hat supported / certified / internal?
[ ] Which namespace will it be installed in?
[ ] Does it install cluster-wide or namespaced?
[ ] Does the CSV request cluster-admin-like permissions?
[ ] Does it read or write Secrets?
[ ] Does it create CRDs or APIService objects?
[ ] Does it install webhooks?
[ ] Does it run privileged containers?
[ ] Does it need SCC permissions?
[ ] Are relatedImages digest-pinned and mirrored for disconnected clusters?
[ ] Is installPlanApproval Manual for controlled environments?
[ ] Is there a documented rollback/uninstall process?
```

## 14. Copied CSVs

When an Operator is installed cluster-wide or for selected namespaces, OLM may create copied CSVs in namespaces where the Operator is available.

Copied CSVs are simplified copies used to show users that an Operator is active for their namespace.

Example:

```bash
oc get csv -A | grep Copied
```

Typical phases:

```text
Succeeded   main installed CSV
Copied      copied CSV in target namespace
```

Important:

- Do not troubleshoot copied CSVs as if they are the main installed CSV.
- The main CSV is usually in the Operator installation namespace.
- Copied CSVs help namespace users discover available APIs.

Disable copied CSVs only if you understand the UI and operational impact.

## 15. CSV upgrades and replacement behavior

A new Operator version usually means a new CSV.

Example:

```text
example-operator.v1.2.2
example-operator.v1.2.3
```

The new CSV may contain:

```yaml
replaces: example-operator.v1.2.2
```

Upgrade flow:

```text
1. CatalogSource receives newer bundle
2. Subscription detects newer version in selected channel
3. InstallPlan is created
4. InstallPlan is approved
5. New CSV is created
6. New Operator Deployment/RBAC is applied
7. Old CSV is replaced
8. New CSV becomes Succeeded
```

### 15.1 Watch an upgrade

```bash
NS=<operator-namespace>

watch -n2 "oc get sub,installplan,csv,deploy,pod -n $NS"
```

### 15.2 Manual update strategy

For production clusters, prefer:

```yaml
installPlanApproval: Manual
```

This allows you to inspect the InstallPlan before approving.

### 15.3 Common upgrade risks

| Risk | Symptom |
|---|---|
| RBAC changed | InstallPlan shows new ClusterRole/Role changes |
| CRD schema changed | CR creation/update starts failing |
| Webhook changed | Admission errors |
| Deployment immutable field changed | CSV fails with immutable field error |
| Missing related image in disconnected registry | ImagePullBackOff |
| OperatorGroup scope mismatch | UnsupportedOperatorGroup |
| Required dependency not present | Pending / requirements not met |

### 15.4 Inspect what an upgrade will change

```bash
oc describe installplan <installplan> -n <ns>
```

For full manifest detail:

```bash
oc get installplan <installplan> -n <ns> -o yaml
```

Search plan resources:

```bash
oc get installplan <installplan> -n <ns> -o yaml | grep -E "kind:|name:|ClusterRole|ClusterRoleBinding|CustomResourceDefinition|ClusterServiceVersion"
```

## 16. Uninstall behavior

Uninstalling an OLM-managed Operator usually requires two actions:

```text
1. Delete Subscription
2. Delete CSV
```

Example:

```bash
NS=openshift-nmstate

oc delete subscription kubernetes-nmstate-operator -n $NS

oc get csv -n $NS

oc delete csv kubernetes-nmstate-operator.v4.21.0 -n $NS
```

Important:

```text
Deleting the Subscription prevents OLM from reinstalling/upgrading the Operator.
Deleting the CSV removes OLM-created resources such as RBAC and deployments.
OLM does not automatically delete owned CRDs, APIService objects, or custom resources because that could cause data loss.
```

Before deleting CRDs:

```bash
oc get csv <csv> -n <ns> \
  -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'

oc get <custom-resource-kind> -A
```

Back up CRs if needed:

```bash
oc get <kind> -A -o yaml > <kind>-backup.yaml
```

Never delete CRDs blindly in production. Removing a CRD deletes all custom resources of that type.

### 18.1 Standard troubleshooting flow

Use this order:

```text
2. InstallPlan
3. CSV
```

### 18.2 CSV stuck in Pending

Symptoms:

```text
PHASE: Pending
MESSAGE: one or more requirements couldn't be found
```

Possible causes:

| Cause | Check | Fix |
|---|---|---|
| Missing required CRD | `oc get crd <name>` | Install dependency Operator or correct catalog |
| Missing APIService | `oc get apiservice` | Fix dependency API service |
| No OperatorGroup | `oc get operatorgroup -n <ns>` | Create OperatorGroup |
| OperatorGroup unsupported | Compare OperatorGroup with `installModes` | Use supported install mode |
| Catalog resolution issue | `oc describe sub` | Fix Subscription/CatalogSource |
| Manual InstallPlan not approved | `oc get installplan` | Approve InstallPlan |

Commands:

```bash
oc get csv <csv> -n <ns> -o yaml | sed -n '/requirementStatus:/,/conditions:/p'

oc describe csv <csv> -n <ns>
```

### 18.4 CSV Failed with UnsupportedOperatorGroup

```text

```


- choose an Operator-supported installation mode,
- reinstall Operator in correct namespace/scope,

### 18.5 CSV Installing but deployment not ready

Symptoms:


Common causes:

| Cause | Symptom |
|---|---|
| Image pull issue | `ImagePullBackOff`, `ErrImagePull` |
| SCC/security issue | `CreateContainerError`, admission denied |
| Missing secret/configmap | Pod events show missing volume/env |
| Node scheduling issue | `Pending`, taints/tolerations |
| Resource quota | `exceeded quota` |
| Webhook/API issue | Deployment or pod admission failures |
| Readiness probe failing | Pod running but not ready |

```text
field is immutable
```


### 18.7 CSV Succeeded but Operator not working

CSV `Succeeded` only means OLM installed the Operator resources successfully. It does not always mean the Operator is correctly reconciling operands.

Check:

Possible causes:

| Cause | Example |
|---|---|
| Operand CR invalid | CR status shows validation/reconcile errors |
| Missing storage class | Operand PVC pending |
| SCC issue for operand | Operand pod rejected |
| Network policy issue | Operand components cannot connect |
| Image missing in mirror registry | Operand ImagePullBackOff |
| Missing secret | Operand reconcile fails |
| Webhook failure | CR cannot be created/updated |

## 19. Production best practices

### 19.1 Use manual approval for important Operators

For production:

```yaml
installPlanApproval: Manual
```

This gives you a change-control point.

### 19.2 Inspect InstallPlan before approving

```bash
oc describe installplan <installplan> -n <ns>
oc get installplan <installplan> -n <ns> -o yaml
```

Look for:

```text
CRD changes
ClusterRole changes
ClusterRoleBinding changes
Webhook changes
APIService changes
CSV version change
Deployment image change
```

### 19.3 Keep Operators in dedicated namespaces

Good:

```text
openshift-logging
openshift-storage
openshift-cnv
my-product-operators
```

Avoid installing many unrelated Operators in one namespace unless you understand OperatorGroup colocation behavior.

### 19.4 Do not manually edit vendor CSVs as a permanent fix

Manual CSV edits can be overwritten by upgrades and can drift from catalog state.

Better:

```text
Use Subscription config if supported
Use documented Operator CR configuration
Use supported override mechanisms
Use vendor advisory/fix
Use a custom catalog only when you own the packaging process
```

### 19.5 Understand CRD retention before uninstall

Before removing a CSV, know what CRDs and CRs are owned:

```bash
oc get csv <csv> -n <ns> \
  -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\n"}{end}'
```

Back up CRs:

```bash
oc get <kind> -A -o yaml > backup.yaml
```

### 19.6 Watch APIService and webhook health

Operators that install APIServices or webhooks can affect the cluster beyond their namespace.

Checklist:

```bash
oc get apiservice | grep False
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc get endpoints -A | grep <operator-name>
```

### 19.7 Track Operator upgrade windows

For business-critical Operators:

```text
Plan maintenance window
Review release notes
Review InstallPlan
Take backups of CRs
Confirm storage backups
Approve InstallPlan
Watch CSV and operands
Validate application health
```

## 20. Exam and interview notes

### 20.1 One-line definition

A CSV is a namespaced OLM custom resource that represents one installed version of an Operator and contains its metadata, install strategy, required permissions, owned APIs, dependencies, and current installation status.

### 20.2 CSV vs Subscription

| CSV | Subscription |
|---|---|
| Represents installed Operator version | Represents intent to install/track package/channel |
| Created by OLM from InstallPlan | Created by admin/user |
| Has phase `Succeeded`, `Pending`, etc. | Has conditions like `ResolutionFailed`, `InstallPlanPending` |
| Contains install strategy and RBAC | Contains package, channel, source, approval strategy |
| Delete CSV to remove installed Operator resources | Delete Subscription to stop future installs/upgrades |

### 20.3 CSV vs InstallPlan

| CSV | InstallPlan |
|---|---|
| Installed version object | Plan of resources to create |
| Shows current Operator status | Shows install/upgrade resources and approval |
| OLM reconciles it | Catalog Operator creates it |
| Has Operator Deployment template | Has resource manifests in plan |

### 20.4 CSV vs CRD

| CSV | CRD |
|---|---|
| Describes/install Operator | Defines a Kubernetes API type |
| Namespaced | Cluster-scoped |
| Managed by OLM | Often owned by Operator |
| Can reference owned CRDs | Does not install Operator |

### 20.5 Common exam command patterns

```bash
oc get csv -A
oc get csv -n <ns>
oc describe csv <csv> -n <ns>
oc get sub,installplan,csv -n <ns>
oc get operatorgroup -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator
```

### 20.6 What to check if Operator installation fails

```text
1. Subscription conditions
2. InstallPlan approved or not
3. CSV phase/reason/message
4. OperatorGroup exists and matches installModes
5. Required CRDs/APIServices
6. CatalogSource health
7. Operator deployment/pod status
8. Events
9. OLM logs
```

## Final senior-admin takeaway

A CSV is the **most important runtime object to inspect after a Subscription and InstallPlan** when troubleshooting OLM-managed Operators.

For real production administration, do not only check whether the CSV is `Succeeded`. Also verify:

```text
Operator pod readiness
Operand CR status
CRD/API availability
Webhook health
RBAC scope
Catalog health
Upgrade path
Events and OLM logs
```

A CSV tells you what OLM installed, what it expected, what it owns, what it depends on, and why installation or upgrade is stuck.
