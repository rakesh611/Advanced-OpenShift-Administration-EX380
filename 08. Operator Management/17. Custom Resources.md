# Custom Resources in Operator Management — Advanced OpenShift Administration Guide

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and OpenShift Operator support engineers with production responsibility.  
**Experience level:** Written from a 10-year operations perspective.  
**Focus area:** Operator Management, Operator Lifecycle Manager (OLM), Custom Resources (CRs), CustomResourceDefinitions (CRDs), troubleshooting, upgrades, RBAC, and day-2 operations.

---

## 1. Executive Summary

In OpenShift, **Custom Resources (CRs)** are the primary way users and administrators configure applications managed by Operators. A CR is not just a YAML file. It is an API object stored in etcd, served through the Kubernetes API server, validated by a CRD schema, watched by an Operator controller, and continuously reconciled into real infrastructure such as Deployments, StatefulSets, Services, Routes, ConfigMaps, Secrets, Jobs, storage objects, monitoring objects, or cluster-scoped resources.

For an OpenShift administrator, understanding CRs is important because most modern OpenShift platform components are managed through Operators. Instead of manually editing low-level Kubernetes objects, you often manage a high-level CR such as:

```yaml
kind: LokiStack
kind: FileIntegrity
kind: NMState
kind: KubeDescheduler
kind: ServiceMeshControlPlane
kind: ArgoCD
kind: QuayRegistry
kind: OpenShiftAPIServer
kind: IngressController
kind: ImageRegistry
```

The Operator reads the CR and makes the cluster match the desired state. If the CR is wrong, the Operator may fail, keep reconciling unsuccessfully, mark status conditions as degraded, or create broken operand workloads.

A senior OpenShift administrator must know how to answer these questions quickly:

- Which CRD provides this CR kind?
- Which Operator owns or reconciles this CR?
- Is the CR namespaced or cluster-scoped?
- Which namespace should the CR be created in?
- Is the CR accepted by the API server but rejected by the Operator logic?
- Are `.spec`, `.status`, `.metadata.generation`, `.status.observedGeneration`, and `.status.conditions` aligned?
- Did an OLM upgrade change the CRD schema or required fields?
- Are finalizers blocking deletion?
- Is RBAC preventing the Operator from watching or updating the CR?
- Is the Operator watching the namespace where the CR exists?
- Is the CR valid for the installed Operator version and channel?

This guide explains Custom Resources deeply from an Operator Management perspective.

## 2. What Is a Custom Resource?

A **Custom Resource** is an extension of the Kubernetes API. Kubernetes already has built-in resources such as `Pod`, `Service`, `Deployment`, `Secret`, and `ConfigMap`. A Custom Resource adds a new API type to the cluster.

Example:

```yaml
apiVersion: example.com/v1
kind: AppCluster
metadata:
  name: production
  namespace: app-prod
spec:
  replicas: 3
  version: "1.2.0"
  storage:
    size: 20Gi
```

After its CRD is installed, the API server treats this object like any other Kubernetes object:

```bash
oc get appcluster
oc describe appcluster production
oc get appcluster production -o yaml
oc delete appcluster production
oc explain appcluster.spec
```

The important point is this:

> A CR stores desired state. The Operator converts that desired state into actual cluster resources.

Without a controller or Operator watching it, a CR is usually just data stored in the Kubernetes API. The power comes from the controller that continuously reconciles it.

## 3. CR vs CRD vs Operator vs Operand

These terms are often mixed up. In production troubleshooting, confusing them causes wrong diagnosis.

| Term | Full Name | Meaning | Example |
|---|---|---|---|
| CR | Custom Resource | An instance of a custom API | `LokiStack logging-loki` |
| CRD | CustomResourceDefinition | Defines a new API type | `lokistacks.loki.grafana.com` |
| Operator | Controller that manages lifecycle | Loki Operator pod | `deployment/loki-operator-controller-manager` |
| Operand | The application managed by the Operator | Loki gateway, distributor, compactor pods | Loki components |
| CSV | ClusterServiceVersion | OLM metadata object for installed Operator | `loki-operator.vX.Y.Z` |
| Subscription | OLM desired install/update stream | Subscribe to package/channel | `loki-operator` stable channel |
| InstallPlan | OLM plan to install or upgrade resources | CRDs/RBAC/CSV to apply | `install-xxxxx` |
| OperatorGroup | Defines install/watch scope | Own namespace/all namespaces | `openshift-operators` OperatorGroup |

### Practical mental model

```text
CatalogSource
    ↓
Subscription
    ↓
InstallPlan
    ↓
CSV
    ↓
CRD installed
    ↓
User creates CR
    ↓
Operator watches CR
    ↓
Operator creates/manages operand resources
```

## 4. Why Custom Resources Matter in Operator Management

Operators are built around Kubernetes API extensibility. Instead of asking an administrator to manually create many objects, the Operator exposes a high-level API.

For example, instead of manually creating:

- ServiceAccounts
- Roles and RoleBindings
- Deployments
- StatefulSets
- Services
- Routes
- ConfigMaps
- Secrets
- PersistentVolumeClaims
- NetworkPolicies
- PodDisruptionBudgets
- PrometheusRules

The administrator creates one CR:

```yaml
apiVersion: example.com/v1
kind: AppCluster
metadata:
  name: app-prod
spec:
  replicas: 3
  storageSize: 50Gi
  tls:
    enabled: true
```

The Operator then creates and maintains all required lower-level resources.

This is why CRs are central to OpenShift day-2 operations:

- Installation may be OLM-driven, but configuration is often CR-driven.
- Upgrade behavior may depend on CR spec fields.
- Failure status is usually visible in the CR `.status.conditions`.
- Deletion may be blocked by CR finalizers.
- Backup/restore planning must include CRs and their dependent resources.
- Multi-tenancy depends on where CRs are allowed and where Operators watch.

## 5. Anatomy of a Custom Resource

A CR has the same top-level Kubernetes object structure as built-in resources.

```yaml
apiVersion: example.com/v1
kind: AppCluster
metadata:
  name: production
  namespace: app-prod
  labels:
    app.kubernetes.io/managed-by: app-operator
  annotations:
    support.example.com/ticket: INC123456
spec:
  replicas: 3
  version: "1.2.0"
status:
  phase: Ready
  observedGeneration: 4
  conditions:
  - type: Available
    status: "True"
    reason: ComponentsReady
    message: All components are available
    lastTransitionTime: "2026-07-03T10:00:00Z"
```

### 5.1 `apiVersion`

The `apiVersion` contains the API group and version:

```yaml
apiVersion: example.com/v1
```

Format:

```text
<api-group>/<version>
```

Examples:

```yaml
apiVersion: operators.coreos.com/v1alpha1
apiVersion: loki.grafana.com/v1
apiVersion: nmstate.io/v1
apiVersion: route.openshift.io/v1
apiVersion: apps/v1
```

The API group prevents naming conflicts. Two different vendors can define a `Cluster` kind if they use different API groups.

### 5.2 `kind`

The `kind` is the object type:

```yaml
kind: AppCluster
```

The kind is normally CamelCase. The CRD maps this kind to plural and singular API resource names.

Example:

```text
Kind: AppCluster
Plural resource: appclusters
Singular resource: appcluster
CRD name: appclusters.example.com
```

### 5.3 `metadata`

Metadata contains Kubernetes object identity and control fields.

Important metadata fields:

| Field | Purpose |
|---|---|
| `name` | Object name |
| `namespace` | Required for namespaced CRs |
| `labels` | Selection, grouping, ownership, policy matching |
| `annotations` | Extra non-identifying metadata |
| `generation` | Incremented when desired state changes |
| `resourceVersion` | Storage version for optimistic concurrency |
| `finalizers` | Block deletion until cleanup completes |
| `ownerReferences` | Garbage-collection ownership relationship |
| `deletionTimestamp` | Object is in deletion state |

### 5.4 `spec`

The `spec` is the user-defined desired state.

Example:

```yaml
spec:
  replicas: 3
  storage:
    size: 20Gi
  tls:
    enabled: true
```

As an administrator, you normally edit `.spec`, not `.status`.

```bash
oc edit appcluster production -n app-prod
oc patch appcluster production -n app-prod --type merge -p '{"spec":{"replicas":5}}'
```

### 5.5 `status`

The `status` is normally written by the Operator, not by the user. It represents observed state.

Important fields:

| Field | Meaning |
|---|---|
| `phase` | Simple high-level state, if implemented |
| `conditions` | Detailed readiness/degraded/progressing state |
| `observedGeneration` | Last `.metadata.generation` reconciled by the Operator |
| component statuses | Per-component readiness or error details |

A healthy CR usually has:

```text
metadata.generation == status.observedGeneration
Available=True or Ready=True
Degraded=False
Progressing=False or Reconciling=False
```

Not all Operators use exactly the same condition names. Always inspect the specific CR.

## 6. Anatomy of a CustomResourceDefinition

A CRD defines the API itself.

Simplified example:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: appclusters.example.com
spec:
  group: example.com
  scope: Namespaced
  names:
    plural: appclusters
    singular: appcluster
    kind: AppCluster
    shortNames:
    - ac
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              replicas:
                type: integer
                minimum: 1
              version:
                type: string
          status:
            type: object
            x-kubernetes-preserve-unknown-fields: true
    subresources:
      status: {}
      scale:
        specReplicasPath: .spec.replicas
        statusReplicasPath: .status.replicas
```

### Important CRD fields

| CRD field | Meaning |
|---|---|
| `metadata.name` | Must be `<plural>.<group>` |
| `spec.group` | API group |
| `spec.scope` | `Namespaced` or `Cluster` |
| `spec.names.kind` | Kind used in YAML |
| `spec.names.plural` | Resource name used by CLI/API |
| `spec.names.shortNames` | Optional CLI aliases |
| `spec.versions[].name` | API versions such as `v1alpha1`, `v1beta1`, `v1` |
| `spec.versions[].served` | Whether API server serves this version |
| `spec.versions[].storage` | Version stored in etcd |
| `schema.openAPIV3Schema` | Validation schema |
| `subresources.status` | Enables status updates separately |
| `subresources.scale` | Enables HPA-like scale interface |
| `additionalPrinterColumns` | Columns shown in `oc get` |
| `conversion` | Optional version conversion strategy/webhook |

## 7. Namespaced vs Cluster-Scoped Custom Resources

CRDs can define either namespaced or cluster-scoped CRs.

### 7.1 Namespaced CR

```yaml
spec:
  scope: Namespaced
```

Created inside a namespace/project:

```bash
oc get appclusters -n app-prod
oc create -f appcluster.yaml -n app-prod
```

Use cases:

- Tenant applications
- Namespace-specific logging
- Namespace-local app instances
- Project-scoped service instances

### 7.2 Cluster-scoped CR

```yaml
spec:
  scope: Cluster
```

Created without a namespace:

```bash
oc get image.config.openshift.io cluster
oc get ingresscontroller -n openshift-ingress-operator
```

Strictly speaking, cluster-scoped resources do not belong to a namespace. Some OpenShift APIs use a cluster-scoped CR with the fixed name `cluster`, for example certain `config.openshift.io` resources.

Use cases:

- Cluster-wide configuration
- Cluster-wide networking
- Cluster-wide monitoring
- Storage platform configuration
- Global security policy

### 7.3 Common admin mistake

Creating a CR in the wrong namespace is one of the most common Operator problems.

Example symptoms:

```text
CR exists but no operand pods are created
CR status never changes
Operator logs show no reconcile event
CSV is healthy but application is missing
```

Check where the Operator is installed and what namespaces it watches:

```bash
oc get operatorgroup -A
oc get csv -A
oc get deployments -A | grep -i operator
oc logs deployment/<operator-deployment> -n <operator-namespace>
```

## 8. OperatorGroup and CR Watch Scope

In OLM-managed Operators, the **OperatorGroup** defines the target namespaces for an Operator installation.

Important idea:

> Installing an Operator in namespace `openshift-operators` does not automatically mean it watches every namespace unless the OperatorGroup and CSV install modes support that scope.

Check OperatorGroup:

```bash
oc get operatorgroup -n <operator-namespace> -o yaml
```

Look for:

```yaml
spec:
  targetNamespaces:
  - app-prod
```

or all-namespaces mode:

```yaml
spec: {}
```

depending on how the OperatorGroup is configured.

Check CSV install modes:

```bash
oc get csv <csv-name> -n <operator-namespace> -o yaml | yq '.spec.installModes'
```

Common install modes:

| Install mode | Meaning |
|---|---|
| `OwnNamespace` | Operator watches its own namespace |
| `SingleNamespace` | Operator watches one selected namespace |
| `MultiNamespace` | Operator watches multiple selected namespaces |
| `AllNamespaces` | Operator watches all namespaces |

### Troubleshooting scope mismatch

If CRs are not reconciled:

```bash
oc get <cr-resource> -A
oc get operatorgroup -n <operator-ns> -o yaml
oc get csv -n <operator-ns>
oc describe csv <csv> -n <operator-ns>
oc logs deployment/<operator> -n <operator-ns> --tail=100
```

Look for messages such as:

```text
namespace not watched
unsupported install mode
no OperatorGroup found
too many OperatorGroups
failed to determine watch namespace
```

## 9. CR Lifecycle in OLM-Based Operator Management

The CR is created after the Operator and CRD are installed.

### 9.1 Installation lifecycle

```text
1. CatalogSource provides Operator metadata.
2. Subscription selects package, channel, and source.
3. OLM resolves dependencies.
4. InstallPlan is generated.
5. InstallPlan is approved automatically or manually.
6. CSV is created.
7. CRDs and RBAC are installed.
8. Operator deployment becomes available.
9. User creates CR.
10. Operator reconciles CR into operand resources.
```

### 9.2 Upgrade lifecycle

```text
1. New bundle appears in subscribed channel.
2. Subscription detects newer CSV.
3. OLM creates upgrade InstallPlan.
4. InstallPlan updates CSV, CRDs, RBAC, deployment, and managed bundle resources.
5. Operator starts new version.
6. Operator reconciles existing CRs.
7. CR status updates according to new controller logic.
```

### 9.3 Deletion lifecycle

```text
1. User deletes CR.
2. API server marks CR with deletionTimestamp.
3. Operator sees deletion event.
4. Operator performs cleanup.
5. Operator removes finalizer.
6. API server deletes CR.
7. Dependent resources may be deleted by ownerReferences or Operator cleanup logic.
```

If the Operator is removed before CRs are deleted, finalizers can leave CRs stuck in `Terminating`.

## 10. Reconciliation: The Heart of Custom Resources

Operators use the reconciliation pattern.

### Reconciliation loop

```text
Watch CR events
    ↓
Read current CR spec
    ↓
Read current cluster state
    ↓
Compare desired vs actual
    ↓
Create/update/delete dependent resources
    ↓
Update CR status
    ↓
Repeat continuously
```

The Operator does not just act once. It keeps enforcing desired state.

If a user manually changes an Operator-managed Deployment, the Operator may revert it.

Example:

```bash
oc scale deployment app-backend --replicas=10 -n app-prod
```

If the CR says `replicas: 3`, the Operator may scale it back to 3.

Correct method:

```bash
oc patch appcluster production -n app-prod --type merge -p '{"spec":{"replicas":10}}'
```

Senior admin rule:

> If a resource is Operator-managed, change the CR first. Edit lower-level generated objects only when you understand whether the Operator will overwrite your change.

## 11. Desired State vs Observed State

A CR has desired state in `.spec` and observed state in `.status`.

### Desired state

```yaml
spec:
  replicas: 3
  storage:
    size: 100Gi
```

### Observed state

```yaml
status:
  observedGeneration: 7
  conditions:
  - type: Ready
    status: "False"
    reason: WaitingForPVC
    message: PVC app-data is still Pending
```

### Important fields

```bash
oc get <resource> <name> -n <ns> -o jsonpath='{.metadata.generation}{"\n"}{.status.observedGeneration}{"\n"}'
```

If `.metadata.generation` is higher than `.status.observedGeneration`, the Operator has not yet fully processed the latest spec change.

Possible causes:

- Operator pod down
- Operator is crashlooping
- Operator lacks RBAC
- Operator is not watching the namespace
- Reconcile is stuck on dependency
- Webhook failure
- API server or etcd issue
- CR is invalid from business-logic perspective

## 12. CR Status Conditions

Many Operators report health through `.status.conditions`.

Example:

```yaml
status:
  conditions:
  - type: Available
    status: "True"
    reason: ComponentsAvailable
    message: All components are running
  - type: Progressing
    status: "False"
    reason: ReconcileComplete
    message: Reconciliation completed
  - type: Degraded
    status: "False"
    reason: NoError
    message: No degraded components detected
```

Common condition fields:

| Field | Meaning |
|---|---|
| `type` | Condition name, such as Ready, Available, Degraded |
| `status` | `True`, `False`, or `Unknown` |
| `reason` | Machine-readable reason |
| `message` | Human-readable explanation |
| `lastTransitionTime` | When condition last changed |
| `observedGeneration` | Generation this condition refers to, if implemented |

### Useful commands

```bash
oc get <resource> <name> -n <ns> -o yaml | yq '.status.conditions'
```

Without `yq`:

```bash
oc get <resource> <name> -n <ns> -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

Watch status:

```bash
watch -n 3 "oc get <resource> <name> -n <ns> -o jsonpath='{.status.conditions}'"
```

## 14. Relationship Between CSV and CRDs

A CSV contains metadata about the Operator. It declares APIs the Operator owns and APIs it requires.

### 14.1 Owned APIs

Owned APIs are usually CRDs installed and managed as part of the Operator bundle.

Check owned CRDs:

```bash
oc get csv <csv-name> -n <operator-ns> -o yaml | yq '.spec.customresourcedefinitions.owned'
```

Without `yq`:

```bash
oc get csv <csv-name> -n <operator-ns> -o jsonpath='{range .spec.customresourcedefinitions.owned[*]}{.name}{"\t"}{.kind}{"\t"}{.version}{"\n"}{end}'
```

### 14.2 Required APIs

Required APIs are APIs that must exist for this Operator to work. They may be provided by another Operator.

```bash
oc get csv <csv-name> -n <operator-ns> -o yaml | yq '.spec.customresourcedefinitions.required'
```

If required APIs are missing, CSV installation may fail or stay pending.

### 14.3 CRD ownership and upgrade implications

OLM tracks which CSV owns a CRD. During upgrades, OLM must ensure CRD changes are safe. Backward-incompatible schema changes can block or break upgrades.

As an administrator, before upgrading important Operators, check:

```bash
oc get subscription -A
oc get installplan -A
oc get csv -A
oc describe csv <csv> -n <ns>
oc get crd <owned-crd> -o yaml
```

Look for:

- API version changes
- Removed fields
- New required fields
- Conversion webhook changes
- CRD status conditions
- Existing CRs using deprecated versions

## 15. CRD Versioning and CR API Versions

A CRD can serve multiple versions.

Example:

```yaml
spec:
  versions:
  - name: v1alpha1
    served: true
    storage: false
  - name: v1beta1
    served: true
    storage: false
  - name: v1
    served: true
    storage: true
```

### Version fields

| Field | Meaning |
|---|---|
| `served: true` | API server accepts requests for this version |
| `storage: true` | Objects are stored in etcd using this version |
| `served: false` | Version is no longer available through API |

### Check versions

```bash
oc get crd <crd-name> -o jsonpath='{range .spec.versions[*]}{.name}{" served="}{.served}{" storage="}{.storage}{"\n"}{end}'
```

### Operational impact

If an Operator upgrade stops serving an old API version, existing automation may fail:

```bash
error: no matches for kind "AppCluster" in version "example.com/v1alpha1"
```

Fix by updating manifests to the served API version:

```yaml
apiVersion: example.com/v1
kind: AppCluster
```

### Senior admin practice

Before upgrading an Operator:

```bash
oc get crd <crd-name> -o yaml | yq '.spec.versions'
oc get <resource> -A -o yaml | grep apiVersion
```

Also check release notes and upgrade notes for CR migration requirements.

## 16. CRD Schema Validation

Modern CRDs use OpenAPI v3 schema validation.

Example:

```yaml
schema:
  openAPIV3Schema:
    type: object
    properties:
      spec:
        type: object
        required:
        - replicas
        properties:
          replicas:
            type: integer
            minimum: 1
            maximum: 10
```

If the CR violates schema validation, the API server rejects it before the Operator sees it.

Example error:

```text
The AppCluster "production" is invalid: spec.replicas: Invalid value: 0: spec.replicas in body should be greater than or equal to 1
```

### Schema validation vs Operator validation

There are two layers of validation:

| Layer | Who validates? | When? | Example |
|---|---|---|---|
| CRD schema | API server | On create/update | `replicas` must be integer |
| Operator logic | Operator controller | During reconcile | StorageClass must exist |

A CR can be accepted by the API server but still fail reconciliation.

Example:

```yaml
spec:
  storageClassName: does-not-exist
```

API server may accept it because it is a string, but the Operator later reports:

```text
StorageClass does-not-exist not found
```

## 17. Unknown Fields and Pruning

CRD schemas can control whether unknown fields are preserved or pruned.

If the schema does not allow unknown fields, extra fields may be rejected or silently pruned depending on CRD configuration and Kubernetes behavior.

Example mistake:

```yaml
spec:
  replica: 3     # wrong field; expected replicas
```

Possible outcomes:

- API server rejects the field.
- Field is pruned and ignored.
- Operator never sees the intended setting.

Always verify applied object:

```bash
oc apply -f cr.yaml
oc get <resource> <name> -n <ns> -o yaml
```

Do not assume what you applied is exactly what was stored.

## 18. Defaulting and Mutating Webhooks

Some Operators install admission webhooks that mutate or validate CRs.

### Mutating webhook

Adds or modifies fields during admission.

Example:

```yaml
spec:
  replicas: 1
```

may become:

```yaml
spec:
  replicas: 1
  updateStrategy: RollingUpdate
```

### Validating webhook

Rejects invalid CRs based on advanced rules.

Example:

```text
admission webhook "validate.example.com" denied the request: unsupported storage mode for production profile
```

### Troubleshooting webhook failures

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc describe validatingwebhookconfiguration <name>
oc get pods -A | grep webhook
oc logs deployment/<webhook-deployment> -n <operator-ns>
```

Common webhook symptoms:

```text
failed calling webhook
service not found
x509: certificate signed by unknown authority
context deadline exceeded
no endpoints available for service
```

Fix path:

```bash
oc get svc -n <webhook-ns>
oc get endpoints -n <webhook-ns>
oc get secret -n <webhook-ns>
oc logs -n <webhook-ns> deployment/<webhook>
oc describe apiservice | grep -i failed -A5
```

## 19. Additional Printer Columns

CRDs can define additional columns shown by `oc get`.

Example CRD snippet:

```yaml
additionalPrinterColumns:
- name: Ready
  type: string
  jsonPath: .status.conditions[?(@.type=="Ready")].status
- name: Age
  type: date
  jsonPath: .metadata.creationTimestamp
```

Then:

```bash
oc get appclusters -A
```

might show:

```text
NAMESPACE   NAME          READY   AGE
app-prod    production    True    2d
```

If columns show empty values, inspect full YAML:

```bash
oc get appcluster production -n app-prod -o yaml
```

## 20. Subresources: `status` and `scale`

### 20.1 Status subresource

A CRD can enable a separate status subresource:

```yaml
subresources:
  status: {}
```

This lets the Operator update `.status` without modifying `.spec`.

Status update endpoint:

```text
/apis/<group>/<version>/namespaces/<ns>/<resource>/<name>/status
```

RBAC must allow it:

```yaml
resources:
- appclusters/status
verbs:
- get
- update
- patch
```

If missing, Operator logs may show:

```text
cannot update resource "appclusters/status" in API group "example.com"
```

### 20.2 Scale subresource

A CRD can expose scaling fields:

```yaml
subresources:
  scale:
    specReplicasPath: .spec.replicas
    statusReplicasPath: .status.replicas
```

Then scaling may work:

```bash
oc scale appcluster production --replicas=5 -n app-prod
```

This is not universal. Only CRDs with a scale subresource support it.

## 21. Finalizers in Custom Resources

Finalizers prevent deletion until cleanup is complete.

Example:

```yaml
metadata:
  finalizers:
  - app.example.com/finalizer
```

### Normal deletion

```text
User deletes CR
API server sets deletionTimestamp
Operator sees deletion
Operator deletes external/internal resources
Operator removes finalizer
CR disappears
```

### Stuck deletion

Symptoms:

```bash
oc get <resource> <name> -n <ns> -o yaml | grep -A5 finalizers
oc get <resource> <name> -n <ns> -o jsonpath='{.metadata.deletionTimestamp}'
```

If deletionTimestamp exists and finalizer remains for a long time, deletion is blocked.

Common causes:

- Operator is not running
- Operator was uninstalled before CR deletion
- Operator lacks RBAC for cleanup
- External dependency unavailable
- Operand namespace/resource already deleted manually
- Bug in finalizer logic

### Emergency finalizer removal

Use only after understanding impact:

```bash
oc patch <resource> <name> -n <ns> --type json -p='[{"op":"remove","path":"/metadata/finalizers"}]'
```

For cluster-scoped CR:

```bash
oc patch <resource> <name> --type json -p='[{"op":"remove","path":"/metadata/finalizers"}]'
```

Warning:

> Removing finalizers manually can orphan resources, leave cloud assets running, leak storage, or break future installs. Use it as a controlled recovery action, not a normal deletion method.

## 22. OwnerReferences and Garbage Collection

Operators may set ownerReferences on generated resources.

Example:

```yaml
metadata:
  ownerReferences:
  - apiVersion: example.com/v1
    kind: AppCluster
    name: production
    uid: abcdef12-3456-7890
    controller: true
```

This allows Kubernetes garbage collection to delete child resources when the owner CR is deleted.

Check ownerReferences:

```bash
oc get deployment app-backend -n app-prod -o yaml | yq '.metadata.ownerReferences'
```

Without `yq`:

```bash
oc get deployment app-backend -n app-prod -o jsonpath='{.metadata.ownerReferences}'
```

Important notes:

- Namespaced owner cannot own cluster-scoped dependent objects.
- Cross-namespace ownerReferences are restricted.
- Some Operators use labels instead of ownerReferences.
- Some cleanup is performed manually by finalizers.

## 27. Troubleshooting Custom Resource Problems

### 27.1 Problem: `no matches for kind`

Error:

```text
error: resource mapping not found for name: "production" namespace: "app-prod" from "appcluster.yaml": no matches for kind "AppCluster" in version "example.com/v1"
```

Causes:

- CRD not installed
- Wrong `apiVersion`
- Wrong kind
- Operator installation failed before CRD creation
- CRD version no longer served
- You are connected to the wrong cluster

Commands:

```bash
oc get crd | grep -i appcluster
oc api-resources --api-group=example.com
oc get csv -A
oc get installplan -A
oc get subscription -A
```

Fix:

- Install or repair Operator.
- Use correct API version from `oc api-resources` or `oc explain`.
- Approve pending InstallPlan if manual approval is used.

---

### 27.2 Problem: CR is created but nothing happens

Symptoms:

```text
CR exists
No pods/services/PVCs are created
Status is empty
Events are empty or old
```

Causes:

- Operator not running
- Operator not watching CR namespace
- Wrong namespace for CR
- Wrong CR kind/version
- Operator crashed before reconcile
- RBAC issue prevents watch/list
- CR name does not match expected singleton name

Commands:

```bash
oc get pods -n <operator-ns>
oc logs deployment/<operator> -n <operator-ns> --tail=200
oc get operatorgroup -n <operator-ns> -o yaml
oc get csv -n <operator-ns>
oc describe csv <csv> -n <operator-ns>
oc get <resource> -A
```

Fix path:

1. Confirm Operator pod is running.
2. Confirm CSV phase is `Succeeded`.
3. Confirm OperatorGroup scope includes the CR namespace.
4. Confirm CR is in the namespace expected by the Operator.
5. Check Operator logs for reconcile activity.
6. Check RBAC with `oc auth can-i` as the Operator ServiceAccount.

---

### 27.3 Problem: CR status shows Degraded

Example:

```yaml
status:
  conditions:
  - type: Degraded
    status: "True"
    reason: InvalidConfiguration
    message: storageClassName fast-storage does not exist
```

Commands:

```bash
oc get <resource> <name> -n <ns> -o yaml
oc describe <resource> <name> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc logs deployment/<operator> -n <operator-ns> --tail=200
```

Fix:

- Correct invalid spec field.
- Create missing dependency.
- Restore missing Secret/ConfigMap/PVC.
- Fix permissions.
- Check product-specific documentation.

---

### 27.4 Problem: CR status does not update after spec change

Check generation:

```bash
oc get <resource> <name> -n <ns> -o jsonpath='generation={.metadata.generation}{" observed="}{.status.observedGeneration}{"\n"}'
```

If generation is greater than observedGeneration:

```text
Operator has not processed the latest desired state.
```

Commands:

```bash
oc get pods -n <operator-ns>
oc logs deployment/<operator> -n <operator-ns> --tail=200
oc get events -n <operator-ns> --sort-by=.lastTimestamp
oc auth can-i update <resource>/status --as=system:serviceaccount:<operator-ns>:<operator-sa> -n <cr-ns>
```

Possible fix:

- Restart Operator pod if stuck and supported.
- Fix RBAC.
- Fix webhook/backend dependency.
- Resolve API server issues.

Restart example:

```bash
oc rollout restart deployment/<operator-deployment> -n <operator-ns>
```

Use restart carefully. Logs should be captured first in production incidents.

---

### 27.5 Problem: CR stuck Terminating

Commands:

```bash
oc get <resource> <name> -n <ns> -o yaml | yq '.metadata.finalizers, .metadata.deletionTimestamp'
oc logs deployment/<operator> -n <operator-ns> --tail=200
oc get events -n <ns> --sort-by=.lastTimestamp
```

Common causes:

- Operator removed before CR
- Cleanup dependency unavailable
- RBAC denied finalizer update
- Operator bug
- External object deletion failed

Controlled recovery:

```bash
oc patch <resource> <name> -n <ns> --type json -p='[{"op":"remove","path":"/metadata/finalizers"}]'
```

Before removing finalizer, document:

- What finalizer was removed
- Why cleanup failed
- Which resources may be orphaned
- Manual cleanup performed
- Business approval if production-impacting

---

### 27.6 Problem: Admission webhook blocks CR changes

Error:

```text
Error from server (InternalError): error when creating "cr.yaml": Internal error occurred: failed calling webhook
```

Commands:

```bash
oc get validatingwebhookconfiguration | grep -i <operator>
oc get mutatingwebhookconfiguration | grep -i <operator>
oc describe validatingwebhookconfiguration <name>
oc get svc -A | grep -i webhook
oc get endpoints -n <webhook-ns> <webhook-service>
oc logs deployment/<webhook-deployment> -n <webhook-ns>
```

Common causes:

- Webhook service has no endpoints
- TLS certificate expired or invalid
- Webhook pod crashlooping
- NetworkPolicy blocks API server to webhook
- Operator upgrade partially completed

Fix:

- Restore webhook deployment/service/endpoints.
- Check certificate Secret.
- Check Operator CSV and InstallPlan.
- Temporarily disabling webhook is a last resort and must be risk-approved.

## 28. Custom Resources and Operator Upgrades

CRs are sensitive during Operator upgrades.

### Upgrade risks

- New Operator version changes CRD schema.
- Old CR fields become deprecated.
- New required fields are introduced.
- Conversion webhook changes fail.
- Existing CRs cannot be reconciled by new version.
- CR status conditions change names or meaning.
- Operand upgrade requires CR spec changes.

### Before upgrade

```bash
oc get subscription -n <operator-ns> <sub> -o yaml
oc get csv -n <operator-ns>
oc get installplan -n <operator-ns>
oc get crd <crd-name> -o yaml > crd-before.yaml
oc get <resource> -A -o yaml > crs-before.yaml
oc get pods -n <operator-ns>
oc logs deployment/<operator> -n <operator-ns> --tail=200 > operator-before.log
```

### Manual approval strategy

For critical Operators, manual InstallPlan approval is safer.

```bash
oc patch subscription <sub-name> -n <operator-ns> --type merge -p '{"spec":{"installPlanApproval":"Manual"}}'
```

Approve upgrade after review:

```bash
oc get installplan -n <operator-ns>
oc describe installplan <installplan> -n <operator-ns>
oc patch installplan <installplan> -n <operator-ns> --type merge -p '{"spec":{"approved":true}}'
```

### After upgrade

```bash
oc get csv -n <operator-ns>
oc describe csv <new-csv> -n <operator-ns>
oc get <resource> -A
oc get <resource> <name> -n <ns> -o yaml
oc get pods -A | grep -i <operand>
oc logs deployment/<operator> -n <operator-ns> --tail=200
```

Check:

```text
CSV phase = Succeeded
Operator pod running
CR observedGeneration updated
CR Degraded=False
Operand pods ready
No repeating reconcile errors
```

## 29. Custom Resources and Backup/Restore

A platform backup must include CRDs and CRs. But restore order matters.

### Correct restore order

```text
1. Restore namespaces/projects.
2. Restore CRDs or reinstall Operators that provide CRDs.
3. Restore RBAC required by Operators.
4. Restore CRs.
5. Restore Secrets/ConfigMaps/PVCs as required.
6. Let Operators reconcile.
7. Verify status and operands.
```

If CRs are restored before CRDs exist, restore fails with:

```text
no matches for kind
```

If CRs are restored before Operators are running, CRs may be accepted but not reconciled.

### Backup checklist

```bash
oc get crd -o yaml > crds.yaml
oc get <resource> -A -o yaml > custom-resources.yaml
oc get subscription -A -o yaml > subscriptions.yaml
oc get csv -A -o yaml > csvs.yaml
oc get operatorgroup -A -o yaml > operatorgroups.yaml
```

For production, use a supported backup solution such as OADP/Velero where appropriate, and always follow product-specific backup instructions for stateful Operators.

## 30. Custom Resources and GitOps

CRs are excellent GitOps objects because they define desired state.

### GitOps principles for CRs

- Store CR YAML in Git.
- Avoid manual `oc edit` in production except emergency.
- Use overlays for dev/test/prod.
- Pin Operator channels intentionally.
- Use manual approvals for sensitive Operator upgrades.
- Keep CRD lifecycle separate from application CR lifecycle when possible.
- Do not let GitOps delete CRDs accidentally.

### Recommended repository structure

```text
clusters/
  prod/
    operators/
      loki/
        subscription.yaml
        operatorgroup.yaml
      file-integrity/
        subscription.yaml
    custom-resources/
      loki/
        lokistack.yaml
      file-integrity/
        fileintegrity.yaml
  dev/
    operators/
    custom-resources/
```

### GitOps sync waves

For Argo CD or OpenShift GitOps, apply in order:

```text
Namespace
OperatorGroup
Subscription
CRD readiness wait
Custom Resource
Dependent app config
```

Do not apply a CR before its CRD exists.

## 31. Custom Resources and Multi-Tenancy

CRs can expose powerful operations. A tenant who can create a CR may indirectly create pods, PVCs, routes, services, secrets, or even cluster-impacting workloads depending on the Operator.

### Multi-tenancy questions

Before allowing users to create CRs:

- What does the Operator create when this CR is created?
- Can the CR create privileged pods?
- Can it mount host paths?
- Can it create cluster-scoped resources?
- Can it reference Secrets from other namespaces?
- Can it consume large storage or CPU?
- Does it bypass standard deployment controls?
- Does it create Routes or external exposure?
- Does it support namespace isolation?

### RBAC pattern

Give users access only to the CRs they need:

```bash
oc create role appcluster-viewer \
  --verb=get,list,watch \
  --resource=appclusters.example.com \
  -n app-prod

oc adm policy add-role-to-user appcluster-viewer alice -n app-prod
```

For edit access:

```bash
oc create role appcluster-editor \
  --verb=get,list,watch,create,update,patch,delete \
  --resource=appclusters.example.com \
  -n app-prod
```

Do not casually grant `cluster-admin` to solve CR permission issues.

## 32. Custom Resources and Security

### 32.1 CRs may cause privileged workloads

Some Operators create privileged pods or request special SCCs. The CR itself may look harmless, but the Operator may translate it into powerful resources.

Example risk fields:

```yaml
spec:
  hostNetwork: true
  privileged: true
  nodeSelector:
    node-role.kubernetes.io/master: ""
  tolerations:
  - operator: Exists
  storage:
    hostPath: /var/lib/data
```

Always understand the Operator behavior before delegating CR creation.

### 32.2 Secrets in CR specs

Some CRs reference Secrets:

```yaml
spec:
  credentialsSecret:
    name: database-creds
```

Best practices:

- Do not put secret values directly inside CR specs unless documentation requires it.
- Prefer Secret references.
- Limit who can read CRs if CRs expose sensitive status or connection data.
- Check whether the Operator copies Secrets to other namespaces.

### 32.3 Status may leak information

CR status sometimes includes URLs, usernames, endpoint names, certificate messages, or backend error strings.

Control access:

```bash
oc auth can-i get <resource> -n <ns> --as=<user>
```


## 36. Best Practices for Production OpenShift Administration

### 36.1 Treat CRs as platform API contracts

A CR is not casual YAML. It is a contract between admin/user and Operator.

Before applying changes:

```bash
oc explain <resource>.spec
oc apply -f cr.yaml --dry-run=server
oc diff -f cr.yaml
```

### 36.2 Do not manually modify Operator-owned objects unless necessary

Generated Deployments, Services, StatefulSets, and ConfigMaps may be overwritten.

Correct approach:

```text
Change CR spec → Operator reconciles generated resources
```

### 36.3 Use manual InstallPlan approval for critical Operators

Especially for:

- Storage Operators
- Logging Operators
- Service Mesh Operators
- GitOps Operators
- Security Operators
- Cluster-wide networking Operators

### 36.4 Capture CRs before upgrades

```bash
oc get <resource> -A -o yaml > before-upgrade-crs.yaml
oc get crd <crd> -o yaml > before-upgrade-crd.yaml
```

### 36.5 Watch status after every change

```bash
watch "oc get <resource> <name> -n <ns> -o jsonpath='{.status.conditions}'"
```

### 36.6 Understand finalizers before deleting

Do not remove finalizers blindly.

### 36.7 Document CR ownership

Maintain a platform inventory:

| Operator | Namespace | CRD | CRs | Owner team | Criticality |
|---|---|---|---|---|---|
| Loki Operator | openshift-operators-redhat | lokistacks.loki.grafana.com | logging-loki | Platform | High |
| File Integrity Operator | openshift-file-integrity | fileintegrities.fileintegrity.openshift.io | worker-fileintegrity | Security | Medium |

### 36.8 Use labels consistently

```yaml
metadata:
  labels:
    app.kubernetes.io/name: appcluster
    app.kubernetes.io/instance: production
    app.kubernetes.io/managed-by: app-operator
    environment: prod
    owner: platform
```

### 36.9 Keep CR manifests in Git

Manual changes should be temporary and backported to Git.

## 38. Example: Full Troubleshooting Walkthrough

Problem:

```text
User created AppCluster CR, but no pods are running.
```

### Step 1: Confirm CRD exists

```bash
oc get crd | grep appcluster
```

Output:

```text
appclusters.example.com   2026-07-03T09:00:00Z
```

### Step 2: Confirm CR exists

```bash
oc get appclusters -A
```

Output:

```text
NAMESPACE   NAME         READY   AGE
app-prod    production   False   20m
```

### Step 3: Inspect CR status

```bash
oc get appcluster production -n app-prod -o yaml
```

Status:

```yaml
status:
  observedGeneration: 1
  conditions:
  - type: Ready
    status: "False"
    reason: MissingSecret
    message: Required secret database-creds not found
```

### Step 4: Verify missing Secret

```bash
oc get secret database-creds -n app-prod
```

Output:

```text
Error from server (NotFound): secrets "database-creds" not found
```

### Step 5: Create required Secret

```bash
oc create secret generic database-creds \
  --from-literal=username=appuser \
  --from-literal=password='REDACTED' \
  -n app-prod
```

### Step 6: Watch reconciliation

```bash
watch "oc get appcluster production -n app-prod"
```

### Step 7: Verify operands

```bash
oc get pods -n app-prod
oc get svc -n app-prod
oc get events -n app-prod --sort-by=.lastTimestamp
```

Root cause:

```text
The CR was valid at API level but invalid at application level because the referenced Secret was missing.
```

Corrective action:

```text
Add pre-flight validation in GitOps pipeline to ensure required Secrets exist before CR sync.
```

## 39. Exam and Interview-Level Key Points

For Advanced OpenShift Administration, remember these points:

1. A CRD defines a new API type; a CR is an instance of that type.
2. Operators watch CRs and reconcile desired state into real resources.
3. OLM installs CRDs through Operator bundles and CSVs.
4. CRs are usually created after the Operator and CRDs are installed.
5. `oc api-resources`, `oc get crd`, and `oc explain` are essential discovery commands.
6. A CR may be namespaced or cluster-scoped depending on CRD scope.
7. OperatorGroup controls the namespace scope for many OLM-managed Operators.
8. `.spec` is desired state; `.status` is observed state.
9. `metadata.generation` and `status.observedGeneration` help detect whether the Operator has reconciled the latest change.
10. `.status.conditions` are usually the best place to find why a CR is degraded.
11. API server validation and Operator reconciliation validation are different.
12. Admission webhooks can mutate or reject CRs.
13. Finalizers can block deletion until the Operator performs cleanup.
14. RBAC must include access to the main resource, `/status`, and sometimes `/finalizers`.
15. CRD versioning matters during Operator upgrades.
16. Manual InstallPlan approval is safer for critical Operators.
17. Do not edit Operator-generated resources unless you understand reconciliation behavior.
18. Store CR manifests in Git and apply them in the correct order.
19. Backup/restore must include CRDs, CRs, Operator metadata, and dependent resources.
20. Before uninstalling an Operator, understand what happens to CRs, finalizers, CRDs, and operands.

## 40. Quick Troubleshooting Matrix

| Symptom | Likely Cause | First Commands |
|---|---|---|
| `no matches for kind` | CRD missing or wrong API version | `oc get crd`, `oc api-resources` |
| CR exists but no pods | Operator not watching namespace | `oc get operatorgroup`, `oc logs operator` |
| CR status empty | Operator not reconciling | `oc get pods -n operator-ns`, `oc logs` |
| `Degraded=True` | Invalid spec or dependency issue | `oc get cr -o yaml`, `oc get events` |
| Generation not observed | Operator stuck/down | Check `generation`, `observedGeneration`, logs |
| Delete stuck | Finalizer blocked | Check `metadata.finalizers`, operator logs |
| Webhook error | Webhook service/pod/TLS issue | `oc get validatingwebhookconfiguration`, endpoints |
| Upgrade stuck | InstallPlan/CSV/CRD issue | `oc get installplan`, `oc describe csv` |
| Permission denied in logs | Operator RBAC missing | `oc auth can-i --as=system:serviceaccount...` |
| CR accepted but app broken | Operator-level validation failed | CR status, events, operand pods |

## 41. Practical Command Bundle

Replace variables and run during CR troubleshooting.

```bash
RESOURCE=<resource-plural>
CR_NAME=<cr-name>
CR_NS=<cr-namespace>
OP_NS=<operator-namespace>
OP_DEPLOY=<operator-deployment>

oc api-resources | grep -i "$RESOURCE"
oc get crd | grep -i "$RESOURCE"
oc get "$RESOURCE" -A
oc get "$RESOURCE" "$CR_NAME" -n "$CR_NS" -o yaml
oc describe "$RESOURCE" "$CR_NAME" -n "$CR_NS"
oc get events -n "$CR_NS" --sort-by=.lastTimestamp
oc get pods -n "$OP_NS"
oc logs deployment/"$OP_DEPLOY" -n "$OP_NS" --tail=300
oc get csv -n "$OP_NS"
oc get operatorgroup -n "$OP_NS" -o yaml
```

Generation check:

```bash
oc get "$RESOURCE" "$CR_NAME" -n "$CR_NS" \
  -o jsonpath='generation={.metadata.generation}{" observedGeneration="}{.status.observedGeneration}{"\n"}'
```

Conditions:

```bash
oc get "$RESOURCE" "$CR_NAME" -n "$CR_NS" \
  -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

Finalizers:

```bash
oc get "$RESOURCE" "$CR_NAME" -n "$CR_NS" \
  -o jsonpath='finalizers={.metadata.finalizers}{" deletionTimestamp="}{.metadata.deletionTimestamp}{"\n"}'
```

## 44. Summary

Custom Resources are the operational interface of many OpenShift Operators. A CR defines desired state; the Operator watches it, reconciles it, updates status, and manages the lifecycle of operands. For basic administration, it may be enough to apply a sample CR. For advanced administration, you must understand API discovery, CRD schema, OperatorGroup scope, CSV ownership, RBAC, status conditions, finalizers, webhooks, upgrades, and backup/restore ordering.

A 10-year-level OpenShift administrator does not troubleshoot only pods. They trace the full control plane path:

```text
CR YAML
  → API server validation
  → CRD schema
  → admission webhooks
  → etcd storage
  → Operator watch
  → reconcile logic
  → generated operands
  → CR status conditions
  → OLM lifecycle and upgrades
```

When you understand this path, Operator problems become much easier to isolate and fix.
