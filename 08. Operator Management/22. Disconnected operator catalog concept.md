## 1. Executive Summary

A **disconnected Operator catalog** is a local, internally reachable copy of Operator metadata and required Operator images that allows **Operator Lifecycle Manager (OLM)** to discover, install, and upgrade Operators without accessing internet-based registries such as `registry.redhat.io`, `quay.io`, or other external sources.

In a connected OpenShift cluster, OLM reads remote catalog sources managed by OperatorHub. In a disconnected cluster, those remote sources are not reachable, so the administrator must:

1. Decide which Operator catalogs and packages are required.
2. Mirror the catalog image, bundle images, Operator images, and related operand images into an internal registry.
3. Apply generated mirror mapping resources such as `ImageDigestMirrorSet` and `ImageTagMirrorSet`.
4. Create or apply a `CatalogSource` pointing to the mirrored catalog image.
5. Disable default remote OperatorHub sources to avoid failed image pulls.
6. Install and upgrade Operators only from local catalog sources.

The key idea is simple:

> OLM does not need the internet. OLM needs a healthy `CatalogSource`, reachable bundle images, reachable Operator images, valid image pull credentials, and complete dependency metadata.

## 2. What Is a Disconnected Operator Catalog?

A disconnected Operator catalog is a **catalog source backed by a mirrored index/catalog image** stored in an internal registry. It contains metadata that tells OLM:

- Which Operator packages exist.
- Which channels are available.
- Which Operator versions exist in those channels.
- Which CSVs, CRDs, permissions, webhooks, deployments, APIs, and related images are needed.
- Which upgrade graph OLM should follow.

It is not only a list of Operator names. It is a structured metadata source used by OLM’s resolver.

Example disconnected catalog source:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators-disconnected
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: mirror-registry.example.com/ocp4/redhat/redhat-operator-index:v4.20
  displayName: Red Hat Operators - Disconnected
  publisher: Platform Team
  updateStrategy:
    registryPoll:
      interval: 30m
```

Here, OLM no longer reads the internet-hosted catalog. It reads the internal image:

```text
mirror-registry.example.com/ocp4/redhat/redhat-operator-index:v4.20
```

## 3. Why This Matters in Enterprise OpenShift

Disconnected Operator catalogs are common in:

- Defense and government environments.
- Banking and regulated financial systems.
- Manufacturing and industrial networks.
- Telecom private cloud environments.
- Internal datacenters with no outbound internet.
- Production clusters where internet access is prohibited by policy.
- Clusters that require deterministic, approved, vulnerability-scanned software sources.

For a senior administrator, the disconnected catalog is not only an installation topic. It affects:

- Platform governance.
- Change control.
- Security scanning.
- Operator upgrade planning.
- Registry sizing.
- Certificate management.
- OLM troubleshooting.
- Cluster lifecycle management.
- Disaster recovery.

In connected clusters, OperatorHub feels like a marketplace. In disconnected clusters, OperatorHub becomes a **curated internal software supply chain**.

## 4. Connected vs Disconnected Operator Installation

### 4.1 Connected Cluster Flow

```text
OpenShift Console / CLI
        |
        v
OperatorHub / PackageManifest
        |
        v
Default CatalogSource in openshift-marketplace
        |
        v
External catalog image on registry.redhat.io / quay.io
        |
        v
OLM resolver
        |
        v
Subscription -> InstallPlan -> CSV -> Operator Deployment
        |
        v
Operator pulls images from external registry
```

In this flow, the cluster can pull catalog, bundle, Operator, and operand images from remote registries.

### 4.2 Disconnected Cluster Flow

```text
Internet-connected mirror host
        |
        | oc mirror / oc adm catalog mirror
        v
Internal mirror registry
        |
        v
Generated cluster resources
  - CatalogSource
  - ImageDigestMirrorSet
  - ImageTagMirrorSet
        |
        v
Disconnected OpenShift cluster
        |
        v
OLM reads local CatalogSource
        |
        v
Subscription -> InstallPlan -> CSV -> Operator Deployment
        |
        v
Operator and operands pull only from internal registry
```

The disconnected cluster does not reach out to the internet during normal operation.

## 5. Core Components

### 5.1 Operator Lifecycle Manager

OLM installs, upgrades, and manages OLM-based application Operators.

OLM works with:

- `CatalogSource`
- `PackageManifest`
- `Subscription`
- `InstallPlan`
- `ClusterServiceVersion`
- `OperatorGroup`

OLM is responsible for resolving the correct Operator version and applying the resources declared by the Operator bundle.

### 5.2 OperatorHub

OperatorHub is the discovery layer in the OpenShift console. It does not install Operators by itself. It shows Operator metadata from available catalog sources.

If the catalog source is unhealthy, Operators disappear from OperatorHub or show incomplete metadata.

### 5.3 CatalogSource

A `CatalogSource` tells OLM where catalog metadata is served from. For image-based catalogs, a pod is created in the catalog source namespace, commonly `openshift-marketplace`, and serves the catalog over gRPC.

### 5.4 Index / Catalog Image

A catalog image contains Operator metadata. In modern OpenShift, Red Hat-provided catalogs use the file-based catalog format.

Examples:

```text
registry.redhat.io/redhat/redhat-operator-index:v4.20
registry.redhat.io/redhat/certified-operator-index:v4.20
```

After mirroring, the same logical content might exist as:

```text
mirror-registry.example.com/ocp4/redhat/redhat-operator-index:v4.20
mirror-registry.example.com/ocp4/redhat/certified-operator-index:v4.20
```

### 5.5 Bundle Image

A bundle image represents one installable version of an Operator. It includes CSV, CRDs, RBAC, deployment specs, webhooks, and metadata.

### 5.6 Operator Image

This is the actual controller image that runs as the Operator deployment.

### 5.7 Operand Images

Operands are the applications/components managed by the Operator. Example: a database Operator may deploy database pods; a logging Operator may deploy collectors, gateways, or storage components.

A disconnected setup fails if the catalog is mirrored but the operand images are not mirrored.

## 6. End-to-End Architecture

```text
                CONNECTED SIDE
+------------------------------------------------+
| Internet-connected mirror host / bastion        |
|                                                |
|  Pulls from:                                   |
|  - registry.redhat.io                          |
|  - quay.io                                     |
|  - vendor registries                           |
|                                                |
|  Runs:                                         |
|  - oc mirror --v2                              |
|  - oc adm catalog mirror                       |
+-------------------------+----------------------+
                          |
                          | push / archive transfer
                          v
+------------------------------------------------+
| Internal mirror registry                        |
|                                                |
| Stores:                                        |
|  - catalog images                              |
|  - bundle images                               |
|  - Operator images                             |
|  - operand images                              |
|  - release images if cluster updates included  |
+-------------------------+----------------------+
                          |
                          | pull only from internal registry
                          v
                DISCONNECTED SIDE
+------------------------------------------------+
| OpenShift cluster                               |
|                                                |
|  openshift-marketplace:                        |
|    CatalogSource pod                           |
|                                                |
|  OLM:                                          |
|    resolves subscriptions                      |
|    creates install plans                       |
|    deploys CSV resources                       |
|                                                |
|  Nodes:                                        |
|    CRI-O pulls mirrored images                 |
|                                                |
+------------------------------------------------+
```

The mirror registry becomes critical infrastructure. If it is unavailable, new Operator installs, upgrades, pod rescheduling, node replacement, and disaster recovery can fail.

## 7. How OLM Uses Catalogs Internally

When an administrator installs an Operator from a disconnected catalog, the following happens:

1. `CatalogSource` pod starts in `openshift-marketplace`.
2. The pod serves catalog metadata over gRPC.
3. OLM builds `PackageManifest` data from available catalog sources.
4. Administrator creates a `Subscription`.
5. OLM resolves the package, channel, version, dependencies, and required APIs.
6. OLM creates an `InstallPlan`.
7. If approval is `Manual`, the admin approves the `InstallPlan`.
8. OLM unpacks the selected bundle image.
9. OLM creates or updates the `ClusterServiceVersion`.
10. OLM applies CRDs, RBAC, deployments, webhooks, and other bundle content.
11. The Operator deployment starts.
12. The Operator creates or manages operands when custom resources are created.

Important point:

> A healthy catalog source only proves that metadata is available. It does not prove all runtime images are reachable.

## 8. Disconnected Catalog Image Flow

### 8.1 Normal Connected Pull

```text
Node -> registry.redhat.io/redhat/redhat-operator-index:v4.20
Node -> registry.redhat.io/openshift4/ose-operator-bundle@sha256:...
Node -> registry.redhat.io/openshift4/ose-some-operator@sha256:...
```

### 8.2 Disconnected Pull

```text
Node -> mirror-registry.example.com/ocp4/redhat/redhat-operator-index:v4.20
Node -> mirror-registry.example.com/ocp4/openshift4/ose-operator-bundle@sha256:...
Node -> mirror-registry.example.com/ocp4/openshift4/ose-some-operator@sha256:...
```

### 8.3 How the Cluster Knows About Mirrors

OpenShift uses mirror configuration resources such as:

- `ImageDigestMirrorSet` for digest-based references.
- `ImageTagMirrorSet` for tag-based references.
- `ImageContentSourcePolicy` in older workflows.

These resources tell the cluster image runtime where to pull equivalent images from.

Example concept:

```yaml
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: operator-mirror-set
spec:
  imageDigestMirrors:
  - source: registry.redhat.io/openshift4
    mirrors:
    - mirror-registry.example.com/ocp4/openshift4
```

If a bundle references:

```text
registry.redhat.io/openshift4/ose-logging-operator@sha256:abc123
```

The node runtime can try:

```text
mirror-registry.example.com/ocp4/openshift4/ose-logging-operator@sha256:abc123
```

## 9. Image Types You Must Understand

A common mistake is thinking that mirroring the catalog image is enough. It is not.

### 9.1 Catalog Image

Used by the `CatalogSource` pod.

Failure symptom:

```text
CatalogSource TRANSIENT_FAILURE
catalog pod ImagePullBackOff
```

### 9.2 Bundle Image

Used by OLM bundle unpacking.

Failure symptom:

```text
bundle unpack job fails
InstallPlan fails
Subscription remains pending
```

### 9.3 Operator Controller Image

Used by the Operator deployment.

Failure symptom:

```text
CSV Pending / Failed
operator deployment ImagePullBackOff
```

### 9.4 Operand Image

Used by workloads created by the Operator.

Failure symptom:

```text
Operator installed successfully
Custom resource created
Operand pods fail with ImagePullBackOff
```

This is why disconnected-compatible Operators must list all required images in metadata such as `relatedImages`, and why administrators must test not only installation but also actual operand creation.

## 10. Important OpenShift Resources

### 10.1 OperatorHub

Cluster-level resource that controls default catalog sources.

Check it:

```bash
oc get operatorhub cluster -o yaml
```

Disable default sources:

```bash
oc patch OperatorHub cluster --type json \
  -p '[{"op": "add", "path": "/spec/disableAllDefaultSources", "value": true}]'
```

Alternative merge patch:

```bash
oc patch operatorhub cluster \
  -p '{"spec": {"disableAllDefaultSources": true}}' \
  --type=merge
```

### 10.2 CatalogSource

Check catalog sources:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource redhat-operators-disconnected -n openshift-marketplace
```

Important status fields:

```text
status.connectionState.lastObservedState
status.connectionState.message
status.registryService.serviceName
status.registryService.port
```

Common states:

```text
READY / healthy
TRANSIENT_FAILURE
ImagePullBackOff on catalog pod
```

### 10.3 PackageManifest

`PackageManifest` is generated from catalog sources and shown to users as available Operators.

```bash
oc get packagemanifest -n openshift-marketplace
oc get packagemanifest cluster-logging -n openshift-marketplace -o yaml
```

### 10.4 Subscription

A `Subscription` tells OLM which Operator package/channel/source to track.

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: cluster-logging
  namespace: openshift-logging
spec:
  channel: stable
  installPlanApproval: Manual
  name: cluster-logging
  source: redhat-operators-disconnected
  sourceNamespace: openshift-marketplace
```

### 10.5 InstallPlan

An `InstallPlan` contains the resources OLM plans to create or update.

```bash
oc get installplan -n openshift-logging
oc describe installplan <installplan-name> -n openshift-logging
```

Approve manual install plan:

```bash
oc patch installplan <installplan-name> \
  -n openshift-logging \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 10.6 ClusterServiceVersion

CSV represents the installed Operator version.

```bash
oc get csv -n openshift-logging
oc describe csv <csv-name> -n openshift-logging
```

Important CSV phases:

```text
Pending
InstallReady
Installing
Succeeded
Failed
Replacing
Deleting
```

### 10.7 ImageDigestMirrorSet

Used for digest-based image mirror mappings.

```bash
oc get imagedigestmirrorset
oc get idms
```

### 10.8 ImageTagMirrorSet

Used for tag-based image mirror mappings.

```bash
oc get imagetagmirrorset
oc get itms
```

## 11. oc-mirror v2 Concept

`oc-mirror` v2 is the preferred modern mirroring workflow for disconnected OpenShift environments. It uses a declarative configuration file to define what content must be mirrored.

It can mirror:

- OpenShift release payloads.
- Operator catalogs.
- Operator packages.
- Helm charts.
- Additional images.

High-level workflow:

```text
1. Create ImageSetConfiguration.
2. Run oc mirror --v2.
3. Push images to mirror registry or create archive.
4. Apply generated cluster resources.
5. Create/use local CatalogSource.
6. Repeat as needed for updates.
```

### 11.1 Why oc-mirror v2 Matters

For experienced administrators, the important improvements are:

- Declarative image selection.
- Incremental mirroring using cache/workspace.
- Generated `CatalogSource`, `ImageDigestMirrorSet`, and `ImageTagMirrorSet` resources.
- Better control of what is mirrored.
- Better support for fully disconnected workflows.
- Safer deletion model instead of automatic pruning.

### 11.2 Basic Command Pattern

Mirror directly to a registry:

```bash
oc mirror --v2 \
  --config imageset-config.yaml \
  docker://mirror-registry.example.com:8443
```

Use explicit auth file:

```bash
oc mirror --v2 \
  --config imageset-config.yaml \
  --authfile ./pull-secret.json \
  docker://mirror-registry.example.com:8443
```

Use workspace and cache:

```bash
oc mirror --v2 \
  --config imageset-config.yaml \
  --authfile ./pull-secret.json \
  --workspace file://./workspace \
  --cache-dir ./cache \
  docker://mirror-registry.example.com:8443
```

## 12. ImageSetConfiguration Deep Dive

The `ImageSetConfiguration` is the source of truth for mirroring.

### 12.1 Example: Minimal Operator Catalog Mirror

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
mirror:
  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
    packages:
    - name: cluster-logging
      channels:
      - name: stable
    - name: compliance-operator
      channels:
      - name: stable
```

This mirrors only selected packages and channels from the Red Hat Operator catalog.

### 12.2 Example: Include Version Range

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
mirror:
  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
    packages:
    - name: compliance-operator
      channels:
      - name: stable
        minVersion: "1.5.0"
        maxVersion: "1.7.0"
```

Use version ranges carefully. If you mirror only one version and later need rollback or upgrade, OLM might not have a valid upgrade path.

### 12.3 Example: Full Catalog Mirror

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
mirror:
  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
    full: true
```

This is easier operationally but requires much more storage and time.

### 12.4 Example: Operators Plus Additional Images

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
mirror:
  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
    packages:
    - name: cluster-logging
      channels:
      - name: stable
  additionalImages:
  - name: registry.redhat.io/ubi9/ubi:latest
  - name: registry.redhat.io/openshift4/ose-cli:latest
```

Use `additionalImages` for images that are not pulled through Operator bundle metadata but are still required by your operational process.

### 12.5 Good ImageSet Design

For production, maintain separate files:

```text
imagesets/
  base-platform.yaml
  logging-stack.yaml
  security-stack.yaml
  storage-stack.yaml
  dev-tools.yaml
```

But apply generated cluster resources carefully so mirror policies do not conflict.

### 12.6 Common Mistake

Bad practice:

```yaml
mirror:
  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
    packages:
    - name: my-operator
```

This mirrors only the package head for channels depending on filter behavior. It might not include all older versions you need for deterministic upgrades/rollback.

Better practice:

```yaml
mirror:
  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
    packages:
    - name: my-operator
      channels:
      - name: stable
        minVersion: "1.2.0"
        maxVersion: "1.4.3"
```

Or mirror a full package/channel if storage allows.

## 13. CatalogSource Deep Dive

### 13.1 What Happens When You Create a CatalogSource

When you create a `CatalogSource` of type `grpc` with `spec.image`, the Catalog Operator creates a pod that serves catalog content.

Example:

```bash
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
oc get svc -n openshift-marketplace
```

Typical objects:

```text
CatalogSource: redhat-operators-disconnected
Pod:           redhat-operators-disconnected-xxxxx
Service:       redhat-operators-disconnected
Port:          50051/gRPC
```

OLM connects to the gRPC service to read catalog metadata.

### 13.2 CatalogSource YAML

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators-disconnected
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: mirror-registry.example.com/ocp4/redhat/redhat-operator-index:v4.20
  displayName: Red Hat Operators - Disconnected
  publisher: Platform Engineering
  updateStrategy:
    registryPoll:
      interval: 30m
```

### 13.3 Important Fields

| Field | Meaning |
|---|---|
| `metadata.name` | Source name used by `Subscription.spec.source` |
| `metadata.namespace` | Usually `openshift-marketplace` for global catalog availability |
| `spec.sourceType` | Usually `grpc` |
| `spec.image` | Mirrored catalog image |
| `spec.displayName` | Name visible in console |
| `spec.publisher` | Publisher shown in console |
| `spec.updateStrategy.registryPoll.interval` | How often catalog source checks for image updates |

### 13.4 Tag vs Digest for CatalogSource Image

Using a tag:

```yaml
image: mirror-registry.example.com/ocp4/redhat/redhat-operator-index:v4.20
```

Pros:

- Simple.
- Easy to update by pushing a new tag.

Cons:

- Less deterministic.
- Catalog content can change while tag remains same.

Using a digest:

```yaml
image: mirror-registry.example.com/ocp4/redhat/redhat-operator-index@sha256:<digest>
```

Pros:

- Deterministic.
- Better for audited production clusters.

Cons:

- Requires updating the CatalogSource image digest for each catalog refresh.

Recommendation:

- Use tags in labs and lower environments.
- Use digests in regulated production environments.

## 14. OperatorHub Default Source Disablement

In a disconnected cluster, default remote sources should usually be disabled.

```bash
oc patch OperatorHub cluster --type json \
  -p '[{"op": "add", "path": "/spec/disableAllDefaultSources", "value": true}]'
```

Check:

```bash
oc get operatorhub cluster -o yaml
oc get catalogsource -n openshift-marketplace
```

Why disable them?

- Prevents catalog pods from trying to pull external catalog images.
- Reduces noise in `openshift-marketplace`.
- Avoids `ImagePullBackOff` and `TRANSIENT_FAILURE` from unreachable internet registries.
- Ensures users select only approved internal catalogs.

A disconnected cluster should normally show only your internal catalog sources, such as:

```text
NAME                              DISPLAY
redhat-operators-disconnected     Red Hat Operators - Disconnected
certified-operators-disconnected  Certified Operators - Disconnected
custom-platform-catalog           Internal Platform Operators
```

## 15. IDMS and ITMS Deep Dive

### 15.1 ImageDigestMirrorSet

`ImageDigestMirrorSet` handles digest-based image pull redirection.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: redhat-operator-mirror
spec:
  imageDigestMirrors:
  - source: registry.redhat.io/openshift4
    mirrors:
    - mirror-registry.example.com/ocp4/openshift4
```

Used when images are referenced like:

```text
registry.redhat.io/openshift4/ose-example@sha256:abcd...
```

### 15.2 ImageTagMirrorSet

`ImageTagMirrorSet` handles tag-based image pull redirection.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: ImageTagMirrorSet
metadata:
  name: redhat-operator-tag-mirror
spec:
  imageTagMirrors:
  - source: registry.redhat.io/redhat
    mirrors:
    - mirror-registry.example.com/ocp4/redhat
```

Used when images are referenced like:

```text
registry.redhat.io/redhat/redhat-operator-index:v4.20
```

### 15.3 Why Digest-Based References Are Better

Digest references are immutable:

```text
image@sha256:<digest>
```

Tags are mutable:

```text
image:v4.20
```

For production disconnected clusters, digest-based mirroring is safer because it gives better reproducibility.

### 15.4 Verify Mirror Sets

```bash
oc get idms,itms
oc describe idms <name>
oc describe itms <name>
```

Check cluster image config:

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Watch machine config pools after mirror changes:

```bash
oc get mcp
oc describe mcp worker
```

## 16. Pull Secrets and Registry Trust

A disconnected registry usually requires:

- Authentication credentials.
- Custom CA trust if using an internal CA.
- Correct pull secret configuration.
- Correct DNS resolution from every node.

### 16.1 Global Pull Secret

Check global pull secret:

```bash
oc get secret/pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq
```

Update global pull secret carefully:

```bash
oc set data secret/pull-secret -n openshift-config \
  --from-file=.dockerconfigjson=merged-pull-secret.json
```

Warning:

- Updating the global pull secret can cause node-level effects.
- Test in non-production first.
- Make sure the merged file preserves existing registry credentials.

### 16.2 Pull Secret for CatalogSource

If the mirrored catalog registry requires credentials, create a secret in `openshift-marketplace`:

```bash
oc create secret generic mirror-registry-pull \
  -n openshift-marketplace \
  --from-file=.dockerconfigjson=mirror-auth.json \
  --type=kubernetes.io/dockerconfigjson
```

Then reference it in `CatalogSource`:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators-disconnected
  namespace: openshift-marketplace
spec:
  sourceType: grpc
```

## 20. Operator Upgrade Behavior in Disconnected Catalogs

Operator upgrades in a disconnected environment depend entirely on the catalog versions you mirrored.

### 20.1 Automatic Approval

If `installPlanApproval: Automatic`, OLM upgrades when a newer valid version appears in the local catalog.

Problem:

- If the platform team refreshes the disconnected catalog without change control, Operators might upgrade unexpectedly.

### 20.2 Manual Approval

If `installPlanApproval: Manual`, OLM creates an `InstallPlan` but waits for admin approval.

Recommended for production disconnected clusters:

```yaml
installPlanApproval: Manual
```

### 20.3 Upgrade Requires Mirrored Path

Example:

```text
Installed: 1.2.0
Available in catalog: 1.5.0
Missing from catalog: 1.3.0, 1.4.0
```

Depending on the Operator upgrade graph, OLM may or may not upgrade directly. Some Operators require stepping through intermediate versions.

Best practice:

- Mirror full channel or approved version range.
- Validate upgrade path in staging.
- Use manual approval.
- Keep old catalog image digest until upgrade validation is complete.

### 20.4 Rollback Reality

OLM is upgrade-oriented, not generic rollback-oriented. A disconnected catalog helps only if older bundle metadata and images still exist in the registry, but downgrade may not be supported by the Operator.

Rollback planning should include:

- Backup custom resources.
- Backup operand data.
- Keep previous catalog image.
- Keep previous mirrored images.
- Understand Operator-specific downgrade support.

## 21. Catalog Filtering Strategy

### 21.1 Full Catalog Mirror

Pros:

- Simple.
- Fewer missing dependency issues.
- Good for shared enterprise mirror registry.

Cons:

- Large storage requirement.
- Longer mirror time.
- More vulnerability scanning noise.
- More software exposed in internal OperatorHub.

### 21.2 Package-Level Mirror

Pros:

- Smaller.
- Easier governance.
- Only approved Operators are visible.

Cons:

- Must explicitly include dependencies.
- Higher risk of missing operand images or dependent packages.
- Requires stronger lifecycle discipline.

### 21.3 Channel-Level Mirror

Pros:

- Good balance between size and upgrade flexibility.
- Keeps only approved channel.

Cons:

- Still need version path planning.

### 21.4 Version-Range Mirror

Pros:

- Best for change-controlled environments.
- Keeps exact approved versions.

Cons:

- Can break upgrades if upgrade graph requires versions outside the range.
- Requires more testing.

### 21.5 Recommended Enterprise Pattern

For production:

```text
Mirror selected packages + selected channels + approved min/max range.
Use manual InstallPlan approval.
Promote catalog content from dev -> test -> prod.
Pin production catalog by digest when strict reproducibility is required.
```

## 22. Dependency and relatedImages Concepts

### 22.1 Bundle Dependencies

An Operator bundle may require:

- CRDs.
- APIs provided by another Operator.
- Specific Kubernetes/OpenShift versions.
- Certain RBAC permissions.
- Webhook configurations.

OLM resolves metadata dependencies from the catalog.

### 22.2 oc-mirror Filtering Limitation

When filtering Operator catalogs, do not assume the tool will infer every dependency you require. If an Operator requires another package, include it explicitly in your ImageSetConfiguration.

Example:

```yaml
mirror:
  operators:
  - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
    packages:
    - name: dependent-operator
      channels:
      - name: stable
    - name: main-operator
      channels:
      - name: stable
```

### 22.3 relatedImages

`relatedImages` should list extra images required by the Operator or operands.

Example bundle metadata concept:

```yaml
relatedImages:
- name: operand-image
  image: registry.redhat.io/example/operand@sha256:...
```

Disconnected compatibility heavily depends on accurate `relatedImages` metadata.

If a third-party Operator does not list all required images, mirroring might succeed but the Operator can still fail when it deploys operands.

### 22.4 Senior Admin Validation

Do not stop testing at:

```bash
oc get csv
```

Also test:

1. Create the Operator custom resource.
2. Ensure operand pods start.
3. Confirm no pod pulls from internet registries.
4. Check Operator logs for missing images.
5. Check events in operand namespaces.

## 23. Production Design Patterns

### 23.1 Central Enterprise Mirror Registry

```text
One HA internal registry serves multiple OpenShift clusters.
```

Pros:

- Central governance.
- Easier scanning.
- Easier cache reuse.

Cons:

- Registry becomes a major dependency.
- Requires HA and backup.

### 23.2 Per-Environment Registries

```text
Dev registry -> test registry -> prod registry
```

Pros:

- Strong promotion model.
- Better isolation.

Cons:

- More storage.
- More operational overhead.

### 23.3 Catalog Promotion Model

```text
External source
   -> mirror staging registry
   -> scan images
   -> approve images
   -> promote to production registry
   -> update production CatalogSource
```

### 23.4 Immutable Catalog Releases

Use catalog image digests:

```text
redhat-operator-index@sha256:<digest>
```

Maintain a release record:

```text
Catalog release: platform-catalog-2026-07
OCP version: 4.20
Included packages:
  - compliance-operator stable 1.6.0-1.7.0
  - cluster-logging stable 6.2.0-6.3.0
Registry: mirror-registry.example.com
Approved by: CAB-12345
```

### 23.5 Separate Vendor Catalogs

Do not mix everything into one uncontrolled catalog. Separate:

```text
redhat-operators-disconnected
certified-operators-disconnected
internal-operators
vendor-security-operators
```

This improves troubleshooting and governance.

- Wrong catalog source image.
- Operator package not mirrored.
- Catalog pod unhealthy.
- Disabled source.

- Manual approval pending.
- Unsupported install mode.

### 25.6 Check CSV

```bash
oc get csv -n <namespace>

```

Look for:

- Failed requirements.
- Pending install strategy.
- Deployment not available.
- Webhook issues.

## 26. Common Failure Scenarios

### 26.1 CatalogSource TRANSIENT_FAILURE

Symptoms:

```text
oc get catalogsource -n openshift-marketplace
LAST OBSERVED STATE: TRANSIENT_FAILURE
```

Possible causes:

- Catalog pod not running.
- Catalog image pull failure.
- gRPC service not reachable.
- Invalid catalog image.
- Catalog pod crashed.
- NetworkPolicy blocks connection.

Fix path:

```bash
oc get pods -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
oc describe catalogsource <catalog> -n openshift-marketplace
```

### 26.2 Catalog Pod ImagePullBackOff

Possible causes:

- Mirror registry unreachable.
- Wrong image path.
- Missing pull secret.
- Missing CA trust.
- Image was not mirrored.
- Tag does not exist.

Fix path:

```bash
oc describe pod <catalog-pod> -n openshift-marketplace
oc get secret -n openshift-marketplace
oc get image.config.openshift.io/cluster -o yaml
curl -vk https://mirror-registry.example.com:8443/v2/
```

### 26.3 Operator Not Visible in OperatorHub

Possible causes:

- Package not mirrored.
- Wrong channel filtered.
- Catalog source unhealthy.
- User is viewing wrong project/scope.
- Default sources disabled but local source missing.

Fix path:

```bash
oc get packagemanifest -n openshift-marketplace | grep <operator>
oc get catalogsource -n openshift-marketplace
```

### 26.4 Subscription Stuck Pending

Possible causes:

- Manual InstallPlan not approved.
- No valid upgrade path.
- Missing dependencies.
- Unhealthy catalog source.
- Wrong `source` or `sourceNamespace`.

Fix path:

```bash
oc describe sub <sub> -n <ns>
oc get installplan -n <ns>
oc describe installplan <ip> -n <ns>
```

### 26.5 InstallPlan Failed

Possible causes:

- Bundle image cannot pull.
- RBAC creation failed.
- CRD conflict.
- Unsupported install mode.
- Existing stale CSV from previous failed install.

Fix path:

```bash
oc describe installplan <ip> -n <ns>
oc get jobs -n openshift-marketplace
oc get events -n <ns> --sort-by=.lastTimestamp
```

### 26.6 CSV Failed

Possible causes:

- Operator deployment cannot pull image.
- Required APIs missing.
- Webhook/cert issue.
- RBAC issue.
- Deployment not available.

Fix path:

```bash
oc describe csv <csv> -n <ns>
oc get deploy,pods -n <ns>
oc logs deploy/<operator-deployment> -n <ns>
```

### 26.7 Operator Installed, Operand Fails

This is very common in disconnected clusters.

Possible causes:

- Operand image not mirrored.
- `relatedImages` incomplete.
- Operator uses hardcoded external image.
- Custom resource points to external image.
- Operand namespace lacks pull secret.

Fix path:

```bash
oc get pods -n <operand-namespace>
oc describe pod <operand-pod> -n <operand-namespace>
oc logs deploy/<operator> -n <operator-namespace>
oc get events -n <operand-namespace> --sort-by=.lastTimestamp
```

### 26.8 Wrong Catalog Used

A Subscription must reference the disconnected source:

```yaml
source: redhat-operators-disconnected
sourceNamespace: openshift-marketplace
```

If it references old/default sources:

```yaml
source: redhat-operators
```

then OLM may try to use a remote/default catalog or an unhealthy source.

### 26.9 Stale Failed Subscription

Sometimes OLM remains stuck after an image pull failure. Recovery can require deleting Subscription, CSV, failing jobs, and retrying after fixing the mirror.

```bash
oc get sub,csv -n <namespace>
oc delete sub <subscription-name> -n <namespace>
oc delete csv <csv-name> -n <namespace>
oc get jobs -n openshift-marketplace
oc delete job <failed-job> -n openshift-marketplace
```

Then recreate the Subscription.

## 27. Security, Compliance, and Governance

### 27.1 Treat Catalogs as Software Supply Chain

Disconnected catalogs define what software can enter your cluster. Govern them like production code.

Recommended controls:

- Git-controlled ImageSetConfiguration.
- Change approval for catalog updates.
- Image scanning before promotion.
- Registry access controls.
- Signed image verification where supported.
- Audit of package/channel/version changes.
- Separate dev/test/prod catalog promotion.

### 27.2 Avoid Uncontrolled Full Catalogs in Production

A full catalog exposes many installable Operators. Even if RBAC restricts installation, it increases governance and vulnerability management overhead.

Better:

```text
Approved catalog with selected packages and selected versions.
```

### 27.3 Registry Security

Mirror registry should have:

- TLS with trusted CA.
- Authentication enabled.
- Role-based access.
- Storage monitoring.
- Backup/restore plan.
- HA design for production.
- Vulnerability scanning.
- Immutable tags or digest-based promotion if possible.

### 27.4 Pull Secret Hygiene

Avoid one giant shared credential if your organization requires segmentation. Use namespace/service-account credentials when possible, but remember that OLM, catalog pods, Operator deployments, and operands might run in different namespaces.

## 28. Performance and Scale Considerations

### 28.1 Registry Performance

Large disconnected environments can have many clusters pulling from the same mirror registry. Plan for:

- High availability.
- Adequate IOPS.
- Adequate bandwidth.
- Garbage collection windows.
- Backup windows.
- Storage growth.

### 28.2 Catalog Size

Full catalogs are large and slower to mirror. Filtered catalogs are smaller but require better dependency management.

### 28.3 Polling Interval

Catalog source polling interval controls how often catalog source checks for newer image content.

```yaml
updateStrategy:
  registryPoll:
    interval: 30m
```

For production, do not rely only on polling. Use controlled catalog updates and explicit validation.

### 28.4 Multiple CatalogSources

Multiple catalog sources are normal, but too many unhealthy sources make troubleshooting noisy. Remove unused ones.

## Final Senior-Admin Mental Model

In a disconnected OpenShift environment, an Operator catalog is not just a UI item. It is the entry point of a controlled software supply chain.

A working disconnected catalog requires four things:

```text
1. Catalog metadata is available locally.
2. All referenced images are mirrored locally.
3. Cluster image runtime knows mirror mappings.
4. OLM resources point to the local source.
```

When troubleshooting, follow the pull chain:

```text
CatalogSource image
  -> bundle image
  -> Operator deployment image
  -> operand images
```

Most disconnected Operator failures are caused by one of these being missing, unreachable, unauthenticated, or not trusted.
