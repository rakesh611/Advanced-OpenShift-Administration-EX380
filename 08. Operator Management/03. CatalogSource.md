# CatalogSource in Operator Management — Advanced OpenShift Administration

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and Red Hat exam/lab practitioners with strong Linux/Kubernetes background.  
**Scope:** OpenShift Container Platform 4.x, Operator Lifecycle Manager (OLM Classic), OperatorHub, custom catalogs, disconnected environments, troubleshooting, and production operations.  
**Important version note:** In OpenShift 4.18 and later, **OLM v1** is also available and uses **ClusterCatalog** for catalog management. **CatalogSource** remains the key catalog API for **OLM Classic** workflows, subscriptions, OperatorHub catalog sources, and many existing production clusters.

---

## 1. Executive Summary

A **CatalogSource** is an OLM resource that tells OpenShift **where Operator metadata comes from**.

In practical production terms:

- OperatorHub does not magically know every Operator.
- OperatorHub is populated from one or more **catalogs**.
- A catalog is normally delivered as a **catalog/index image**.
- A **CatalogSource** points OLM to that catalog image.
- OLM starts a catalog pod, exposes it through a service, queries it over gRPC, and uses that metadata to resolve Operator installations and upgrades.

Think of it like this:

```text
Catalog image in registry
        |
        v
CatalogSource CR
        |
        v
Catalog pod + Service on port 50051
        |
        v
OLM catalog-operator / package server / resolver
        |
        v
PackageManifest visible in OperatorHub
        |
        v
Subscription -> InstallPlan -> CSV -> Operator deployment
```

For a senior administrator, CatalogSource is not just an install object. It is a **control point** for:

- Which Operators users can discover
- Which Operator versions are installable
- Which upgrade channels are visible
- Whether disconnected clusters can install Operators
- How trusted or untrusted third-party Operators enter the cluster
- How Operator upgrades are controlled, mirrored, pinned, filtered, and audited

## 2. Core OLM Objects Related to CatalogSource

Before going deep into CatalogSource, understand the nearby OLM objects.

| Object | API | Purpose |
|---|---|---|
| `CatalogSource` | `operators.coreos.com/v1alpha1` | Points OLM Classic to an Operator catalog source. Usually a gRPC catalog image. |
| `PackageManifest` | `packages.operators.coreos.com/v1` | Read-only/discovery view of packages available from catalog sources. OperatorHub uses this. |
| `Subscription` | `operators.coreos.com/v1alpha1` | Requests installation or upgrade of an Operator from a specific catalog source/channel. |
| `InstallPlan` | `operators.coreos.com/v1alpha1` | OLM-generated plan describing resources to create/update for an Operator installation. |
| `ClusterServiceVersion` / `CSV` | `operators.coreos.com/v1alpha1` | Metadata and deployment spec for an installed Operator version. |
| `OperatorGroup` | `operators.coreos.com/v1` | Defines the namespace scope in which an Operator watches and operates. |
| `ClusterCatalog` | `olm.operatorframework.io/v1` | OLM v1 catalog API introduced for the newer OLM architecture. Not the same as CatalogSource. |

## 3. What Is a CatalogSource?

A **CatalogSource** represents a source of Operator metadata that OLM can query to discover Operators and their dependencies.

In OpenShift, the most common CatalogSource type is:

```yaml
spec:
  sourceType: grpc
  image: registry.redhat.io/redhat/redhat-operator-index:v4.19
```

That means:

1. OLM reads the `CatalogSource` object.
2. OLM pulls/runs the catalog image.
3. The catalog image serves Operator metadata through a gRPC API.
4. OLM queries the gRPC endpoint to list packages, channels, bundles, CSVs, CRDs, dependencies, and upgrade graphs.
5. OperatorHub and OLM subscriptions use that data.

A CatalogSource does **not** install an Operator by itself. It only makes Operator metadata available. Installation happens through a `Subscription` and `InstallPlan`.

## 4. Why CatalogSource Matters in Real Administration

A beginner sees CatalogSource as “that YAML used to add an Operator catalog.”

A senior OpenShift administrator sees it as:

- A **software supply-chain entry point**
- A **cluster-wide governance object**
- A **disconnected environment dependency**
- A **version control point** for Operators
- A **security boundary** for approved Operator content
- A **troubleshooting root cause** when OperatorHub is empty or installations fail
- A **performance object** because large catalogs consume memory and catalog pod resources
- An **upgrade control object** because catalog refresh controls available Operator versions

In enterprise clusters, you normally do not allow every upstream catalog directly. You curate catalogs, mirror content, filter packages, pin images, and expose only approved Operators.

## 6. Namespace Scope of CatalogSource

The namespace of a CatalogSource matters.

### 6.1 Cluster-wide catalog source

For normal OpenShift OperatorHub usage, create the CatalogSource in:

```text
openshift-marketplace
```

Example:

```yaml
metadata:
  name: internal-redhat-operators
  namespace: openshift-marketplace
```

This makes the catalog broadly available through OperatorHub and common OLM workflows.

### 6.2 Namespace-scoped catalog source

A CatalogSource can also be created in another namespace:

```yaml
metadata:
  name: app-team-catalog
  namespace: app-team-a
```

Then subscriptions must point to that namespace:

```yaml
spec:
  source: app-team-catalog
  sourceNamespace: app-team-a
```

This is useful when a team needs a private catalog, but it is less common for centralized platform administration.

## 8. Catalog Metadata Model

CatalogSource exposes catalog metadata. That metadata is built from Operator packaging objects.

### 8.1 Package

A package is the top-level Operator name.

Example:

```text
local-storage-operator
openshift-gitops-operator
odf-operator
cluster-logging
```

### 8.2 Channel

A channel is an upgrade stream.

Examples:

```text
stable
stable-5.9
stable-4.16
fast
candidate
```

Channels define which versions are related and how upgrades happen.

### 8.3 Bundle

A bundle represents one installable Operator version. It usually contains:

- CSV
- CRDs
- RBAC
- Deployment spec
- Related images
- Annotations
- Properties

### 8.4 CSV

The `ClusterServiceVersion` describes how to run the Operator and what APIs it owns or requires.

### 8.5 Upgrade graph

OLM uses catalog metadata to understand valid upgrades:

```text
v1.0.0 -> v1.1.0 -> v1.2.0
```

If a bundle is missing from the graph or channel, upgrades might not appear even if the image exists in the registry.

## 9. File-Based Catalogs vs Legacy SQLite Catalogs

Modern OpenShift catalogs use **file-based catalog** format.

### 9.1 File-based catalog

File-based catalogs are plain text, usually JSON or YAML. They are easier to:

- Inspect
- Validate
- Filter
- Compose
- Store in Git
- Automate through CI/CD
- Mirror into disconnected registries

Typical file-based catalog content includes:

```text
catalog/
  ├── my-operator/
  │   ├── package.yaml
  │   ├── channel.yaml
  │   └── bundles.yaml
  └── another-operator/
      └── ...
```

### 9.2 Legacy SQLite catalogs

Older OLM catalogs used SQLite database format. This format is deprecated in modern OpenShift releases. You may still see it in legacy environments, but for new work use file-based catalogs.

Operational recommendation:

```text
New catalog work: file-based catalog
Old inherited catalog: migrate to file-based catalog
Disconnected curated catalog: file-based catalog + oc-mirror workflow
```

## 11. Production-Style CatalogSource Example

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: corp-approved-operators
  namespace: openshift-marketplace
  labels:
    platform.example.com/catalog-tier: approved
spec:
  sourceType: grpc
  image: registry.example.com/openshift/corp-approved-operator-index:v4.19-2026-07-03
  displayName: Corporate Approved Operators
  publisher: Platform Engineering
  priority: 100
  secrets:
    - corp-registry-pull-secret
  grpcPodConfig:
    securityContextConfig: restricted
    priorityClassName: system-cluster-critical
    nodeSelector:
      node-role.kubernetes.io/infra: ""
    tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
    memoryTarget: 512Mi
  updateStrategy:
    registryPoll:
      interval: 30m
```

### Field explanation

| Field | Meaning |
|---|---|
| `sourceType: grpc` | Run or query a gRPC catalog server. Most common type. |
| `image` | Catalog/index image containing Operator metadata. |
| `displayName` | Friendly name shown in OperatorHub. |
| `publisher` | Publisher shown in UI/CLI. |
| `priority` | Higher value is preferred by OLM dependency resolution. |
| `secrets` | Pull secrets for private catalog image access. |
| `grpcPodConfig.securityContextConfig` | Controls security context behavior for the catalog pod. |
| `grpcPodConfig.nodeSelector` | Schedules catalog pod on selected nodes. |
| `grpcPodConfig.tolerations` | Lets catalog pod tolerate tainted nodes. |
| `grpcPodConfig.priorityClassName` | Gives scheduling priority to the catalog pod. |
| `grpcPodConfig.memoryTarget` | Tunes memory target for large catalog servers. |
| `updateStrategy.registryPoll.interval` | Polls for new catalog image content. |

## 12. Important CatalogSource Spec Fields

### 12.1 `spec.sourceType`

Common values:

```text
grpc
configmap
internal
```

Most production OpenShift usage is:

```yaml
sourceType: grpc
```

A gRPC CatalogSource can work in two ways:

```yaml
# Common: OLM runs a catalog image as a pod
spec:
  sourceType: grpc
  image: quay.io/example/catalog:latest
```

```yaml
# Less common: OLM connects to an existing gRPC endpoint
spec:
  sourceType: grpc
  address: catalog.example.svc:50051
```

Using `address` is uncommon because the administrator must manage the external catalog server lifecycle.

### 12.2 `spec.image`

This is the catalog image.

Examples:

```yaml
image: registry.redhat.io/redhat/redhat-operator-index:v4.19
```

```yaml
image: registry.example.com/mirror/redhat-operator-index@sha256:abc123...
```

Using a tag is convenient for automatic refresh. Using a digest is better for immutability and auditability.

### 12.3 Tag vs digest behavior

A practical rule:

| Image reference | Behavior |
|---|---|
| `:tag` | Easier polling/refresh. Risk: tag can move. |
| `@sha256:digest` | Immutable and reproducible. Requires changing YAML to move to new content. |

Production advice:

- Use digest pinning for strict change control.
- Use versioned tags for controlled internal catalogs.
- Avoid `latest` in production.
- For disconnected clusters, align catalog image versions with mirrored content.

### 12.4 `spec.displayName`

Shown in OperatorHub and CLI output.

```yaml
displayName: Corporate Approved Operators
```

### 12.5 `spec.publisher`

Shows who publishes the catalog.

```yaml
publisher: Platform Engineering
```

### 12.6 `spec.priority`

Catalog priority affects OLM dependency resolution. Higher value means the catalog is preferred over lower-priority catalogs. If priorities are equal, catalog names can be used as a tie-breaker.

Example:

```yaml
priority: 100
```

Use this when you have overlapping packages in multiple catalogs and want OLM to prefer your curated catalog.

### 12.7 `spec.secrets`

Used for private registry access.

```yaml
spec:
  secrets:
    - corp-registry-pull-secret
```

Create a secret in the same namespace:

```bash
oc create secret docker-registry corp-registry-pull-secret \
  --docker-server=registry.example.com \
  --docker-username='<user>' \
  --docker-password='<password>' \
  --docker-email='admin@example.com' \
  -n openshift-marketplace
```

### 12.8 `spec.updateStrategy.registryPoll.interval`

Controls catalog image polling.

```yaml
updateStrategy:
  registryPoll:
    interval: 30m
```

Use this carefully. Frequent polling is not always needed in production, especially if catalog promotion is controlled through GitOps.

### 12.9 `spec.grpcPodConfig.securityContextConfig`

Common values:

```text
restricted
legacy
```

Example:

```yaml
grpcPodConfig:
  securityContextConfig: restricted
```

Use `restricted` for modern catalog images compatible with restricted Pod Security Admission. Use `legacy` only when working with old catalog images that cannot run under restricted settings.

### 12.10 `spec.grpcPodConfig.nodeSelector`

Schedule catalog pods on specific nodes:

```yaml
grpcPodConfig:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
```

### 12.11 `spec.grpcPodConfig.tolerations`

Allow scheduling on tainted infra nodes:

```yaml
grpcPodConfig:
  tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
```

### 12.12 `spec.grpcPodConfig.priorityClassName`

Give the catalog pod higher scheduling priority:

```yaml
grpcPodConfig:
  priorityClassName: system-cluster-critical
```

Use carefully. Do not mark every custom catalog as critical.

### 12.13 `spec.grpcPodConfig.affinity`

Use node affinity or anti-affinity for placement:

```yaml
grpcPodConfig:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: node-role.kubernetes.io/infra
                operator: Exists
```

### 12.14 `spec.grpcPodConfig.memoryTarget`

For large catalogs, tune memory:

```yaml
grpcPodConfig:
  memoryTarget: 1Gi
```

This helps large catalog servers avoid memory pressure. Combine it with cluster monitoring and resource observation.

## 13. CatalogSource Status Fields

Use:

```bash
oc describe catalogsource <name> -n <namespace>
```

Look for:

```text
Status:
  Connection State:
    Address:              example-catalog.openshift-marketplace.svc:50051
    Last Connect:         ...
    Last Observed State:  READY
  Registry Service:
    Service Name:         example-catalog
    Service Namespace:    openshift-marketplace
    Port:                 50051
    Protocol:             grpc
```

Common `Last Observed State` values:

| State | Meaning |
|---|---|
| `READY` | OLM can connect to the catalog. |
| `TRANSIENT_FAILURE` | OLM cannot currently connect to the gRPC catalog endpoint. |
| Empty/missing | Catalog pod or service may not be created, or reconciliation has not completed. |

`TRANSIENT_FAILURE` is one of the most common CatalogSource symptoms. It is not the root cause by itself. It means the catalog connection is failing. The root cause may be image pull, crash, bad catalog, DNS, service endpoint, network, proxy, CA, or scheduling.

## 14. How OperatorHub Uses CatalogSource

OperatorHub displays Operators by querying package metadata available from CatalogSources.

Flow:

```text
CatalogSource exists
  -> catalog pod runs
  -> package metadata available
  -> PackageManifest appears
  -> OperatorHub displays package
```

Check PackageManifests:

```bash
oc get packagemanifest -n openshift-marketplace
```

Find a package:

```bash
oc get packagemanifest -n openshift-marketplace | grep -i logging
```

Inspect one package:

```bash
oc get packagemanifest cluster-logging -n openshift-marketplace -o yaml
```

Useful JSONPath:

```bash
oc get packagemanifest cluster-logging -n openshift-marketplace \
  -o jsonpath='{.status.defaultChannel}{"\n"}'
```

List channels:

```bash
oc get packagemanifest cluster-logging -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{"\n"}{end}'
```

List versions:

```bash
oc get packagemanifest cluster-logging -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}Channel: {.name}{"\n"}{range .entries[*]}  {.name}{"\n"}{end}{end}'
```

## 15. Installing an Operator from a CatalogSource

CatalogSource only exposes metadata. To install, create an OperatorGroup and Subscription.

Example namespace:

```bash
oc new-project demo-operators
```

OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: demo-operators-og
  namespace: demo-operators
spec:
  targetNamespaces:
    - demo-operators
```

Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: demo-operators
spec:
  channel: stable
  name: example-operator
  source: corp-approved-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

Check:

```bash
oc get subscription -n demo-operators
oc get installplan -n demo-operators
oc get csv -n demo-operators
```

Approve manual InstallPlan:

```bash
oc patch installplan <installplan-name> -n demo-operators \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

## 16. CatalogSource and Operator Upgrades

Operator upgrade availability depends on catalog metadata.

For an installed Operator, OLM checks:

- Subscription package name
- Subscription channel
- CatalogSource referenced by `source` and `sourceNamespace`
- Available bundles in that channel
- Upgrade graph constraints
- Required APIs and dependencies
- InstallPlan approval mode

Example Subscription:

```yaml
spec:
  channel: stable-5.9
  installPlanApproval: Manual
  name: cluster-logging
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

If a newer bundle exists in the catalog but not in the selected channel, OLM will not upgrade to it. If the channel has the new bundle but dependencies cannot be resolved, InstallPlan creation or CSV upgrade can fail.

### Common upgrade confusion

| Symptom | Likely cause |
|---|---|
| New version exists upstream but not visible | Catalog image not refreshed or mirrored. |
| New version visible in another channel | Subscription channel is pinned to older channel. |
| InstallPlan not created | Resolver cannot satisfy dependencies. |
| InstallPlan created but pending | Manual approval required. |
| CSV stuck replacing | Operator deployment, CRD, webhook, RBAC, or APIService issue. |

## 17. Disabling Default Catalog Sources

In restricted, secure, or curated environments, you may disable default catalogs.

Disable all default sources:

```bash
oc patch OperatorHub cluster --type json \
  -p '[{"op": "add", "path": "/spec/disableAllDefaultSources", "value": true}]'
```

Alternative merge patch:

```bash
oc patch operatorhub cluster --type merge \
  -p '{"spec":{"disableAllDefaultSources":true}}'
```

Verify:

```bash
oc get operatorhub cluster -o yaml
oc get catalogsources -n openshift-marketplace
```

Disable only selected sources:

```yaml
apiVersion: config.openshift.io/v1
kind: OperatorHub
metadata:
  name: cluster
spec:
  sources:
    - name: community-operators
      disabled: true
    - name: redhat-marketplace
      disabled: true
```

Use this in production when you want to allow Red Hat supported catalogs but block community catalogs.

## 19. Disconnected Environment Workflow

In disconnected OpenShift environments, the cluster cannot pull default catalog images from Red Hat or public registries.

High-level workflow:

```text
Internet-connected workstation
  -> mirror OpenShift release images and Operator catalog images
  -> push to internal mirror registry
  -> configure cluster image mirror policies/trust
  -> disable default OperatorHub sources
  -> create CatalogSource pointing to mirrored catalog image
  -> verify PackageManifests
  -> install Operators from mirrored catalog
```

Key points:

- Mirroring catalog metadata is not enough.
- Operators must also reference required operand images correctly.
- For a disconnected-capable Operator, `relatedImages` should include required images.
- Digest-based references are safer for disconnected use.
- Keep catalog image, bundle images, and related operand images in sync.

Example disconnected control commands:

```bash
# Disable default internet-backed sources
oc patch operatorhub cluster --type merge \
  -p '{"spec":{"disableAllDefaultSources":true}}'

# Create your mirrored catalog source
oc apply -f mirrored-catalogsource.yaml

# Confirm catalog pod runs from internal registry
oc get pods -n openshift-marketplace -o wide
oc describe pod -n openshift-marketplace <catalog-pod>

# Confirm packages appear
oc get packagemanifest -n openshift-marketplace
```

## 20. Building a File-Based Catalog Image

A simplified workflow for building a custom catalog image:

```bash
# Render an existing catalog to inspect it
opm render registry.redhat.io/redhat/redhat-operator-index:v4.19 > catalog.json

# Validate file-based catalog directory
opm validate ./catalog

# Generate Dockerfile for catalog image
opm generate dockerfile ./catalog

# Build and push catalog image
podman build -f catalog.Dockerfile -t registry.example.com/olm/custom-index:v1 .
podman push registry.example.com/olm/custom-index:v1
```

Then create a CatalogSource:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: custom-index
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: registry.example.com/olm/custom-index:v1
  displayName: Custom Index
  publisher: Platform Team
```

Production catalog build recommendations:

- Store FBC content in Git.
- Validate with `opm validate` in CI.
- Use signed images if your organization requires image signing.
- Promote catalog images through dev -> test -> prod registries.
- Avoid editing production catalogs manually.
- Record catalog image digest in change tickets.

## 21. Filtering Catalogs for Enterprise Use

Enterprise teams often create a curated catalog instead of exposing everything.

Reasons:

- Reduce attack surface
- Reduce OperatorHub noise
- Avoid unsupported community Operators
- Control versions for compliance
- Prevent accidental installation of huge or privileged Operators
- Ensure disconnected mirroring includes all required images

Example allowed catalog policy:

```text
Allowed:
  - openshift-gitops-operator
  - local-storage-operator
  - odf-operator
  - cluster-logging
  - compliance-operator

Blocked:
  - unapproved community Operators
  - Operators requiring unsupported APIs
  - Operators requiring privileged access without approval
```

Recommended process:

```text
Request -> security review -> platform review -> test install -> mirror -> add to curated catalog -> publish -> GitOps apply CatalogSource
```

## 23. TLS, Proxy, and Custom CA Considerations

CatalogSource failures often come from registry trust issues.

Common environments:

- Corporate proxy
- Man-in-the-middle TLS inspection
- Private registry with custom CA
- Disconnected mirror registry
- Registry route with self-signed certificate

Troubleshooting checklist:

```bash
oc get proxy cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
oc get configmap -n openshift-config
oc describe pod <catalog-pod> -n openshift-marketplace
```

Look for:

```text
x509: certificate signed by unknown authority
proxyconnect tcp
connection refused
i/o timeout
no route to host
```

For private CAs, ensure the cluster trusts the CA through OpenShift image/registry trust configuration. For Operators that need custom CA bundles, also consider Operator-specific trusted CA injection patterns.

## 24. Security Considerations

CatalogSource controls installable software metadata. Treat it as a privileged supply-chain object.

### 24.1 Risks

| Risk | Explanation |
|---|---|
| Untrusted Operator | Operators can request broad RBAC and cluster privileges. |
| Malicious catalog image | Catalog metadata can point to malicious bundle images. |
| Tag drift | A mutable tag can silently change catalog content. |
| Over-broad catalogs | Users can install Operators that were never reviewed. |
| Disconnected mismatch | Metadata exists but operand images are missing. |
| Old catalog image | Uses removed Kubernetes APIs or insecure runtime assumptions. |

### 24.2 Controls

Recommended controls:

- Disable unneeded default catalogs.
- Prefer Red Hat supported or vendor-certified content.
- Mirror and curate catalogs internally.
- Pin production catalog images by digest or controlled version tags.
- Use `installPlanApproval: Manual` for sensitive Operators.
- Restrict who can create `Subscription`, `OperatorGroup`, and `CatalogSource` resources.
- Monitor catalog pods and OLM namespaces.
- Review CSV permissions before approving InstallPlans.
- Keep catalog images aligned with OpenShift minor version.

### 24.3 RBAC governance

Check who can create CatalogSources:

```bash
oc auth can-i create catalogsources.operators.coreos.com --all-namespaces
```

Check for a user:

```bash
oc auth can-i create catalogsources.operators.coreos.com \
  --as user@example.com \
  -n openshift-marketplace
```

In production, only platform administrators should manage cluster-wide CatalogSources.

## 25. Scheduling Catalog Pods

Catalog pods can be scheduled like other pods, but OLM creates them from CatalogSource configuration.

Use `grpcPodConfig`:

```yaml
grpcPodConfig:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
  priorityClassName: system-cluster-critical
```

### When to place catalog pods on infra nodes

Good cases:

- Large enterprise cluster
- Dedicated infra nodes exist
- You run routers, registry, monitoring, logging, and OLM support workloads on infra
- You want to reduce noise on app worker nodes

Avoid overusing `system-cluster-critical` for every custom catalog. If many pods claim critical priority, priority loses meaning.

## 26. Performance and Scale

Large catalogs can consume noticeable memory and CPU.

Symptoms:

```text
Catalog pod OOMKilled
Catalog pod CrashLoopBackOff
PackageManifest slow or missing
OperatorHub slow to load
OLM resolver latency
```

Commands:

```bash
oc adm top pod -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

Tuning options:

```yaml
grpcPodConfig:
  memoryTarget: 1Gi
```

Operational recommendations:

- Use curated catalogs instead of huge all-in-one catalogs.
- Avoid unnecessary duplicate catalogs.
- Use reasonable polling intervals.
- Watch memory and restarts.
- Validate catalog content before publishing.
- Keep old catalogs cleaned up.

## 27. Lifecycle of a CatalogSource

### 27.1 Create

```bash
oc apply -f catalogsource.yaml
```

OLM creates catalog pod and service.

### 27.2 Refresh

If polling is configured and the image tag moves, OLM can refresh catalog content.

```yaml
updateStrategy:
  registryPoll:
    interval: 30m
```

### 27.3 Update

Change the image reference:

```bash
oc patch catalogsource corp-approved-operators \
  -n openshift-marketplace \
  --type merge \
  -p '{"spec":{"image":"registry.example.com/olm/corp-index:v2"}}'
```

### 27.4 Delete

```bash
oc delete catalogsource corp-approved-operators -n openshift-marketplace
```

Installed Operators usually continue running after catalog deletion, but new installs and upgrades from that source fail. Existing Subscriptions referencing the deleted source will have resolution problems.

## 30. Troubleshooting Matrix

| Symptom | Likely cause | Checks | Fix |
|---|---|---|---|
| CatalogSource `TRANSIENT_FAILURE` | gRPC endpoint unreachable | `oc describe catsrc`, pod logs, service/endpoints | Fix pod/image/network/service issue |
| Catalog pod `ImagePullBackOff` | Registry auth, wrong image, CA, mirror missing | `oc describe pod` events | Correct image, pull secret, CA, mirror |
| Catalog pod `CrashLoopBackOff` | Bad catalog image, invalid FBC, incompatible server | pod logs, `opm validate` | Rebuild/validate catalog |
| OperatorHub empty | Default sources disabled or catalog pods failing | `oc get catsrc`, `oc get packagemanifest` | Enable/add working catalogs |
| Package missing | Package not included or wrong catalog version | `opm render`, `packagemanifest` | Use correct/updated catalog |
| New Operator version missing | Catalog not refreshed or wrong channel | Subscription/channel/catalog image | Update catalog image/channel |
| InstallPlan pending | Manual approval | `oc get installplan` | Approve InstallPlan |
| Subscription fails resolution | Missing dependencies/APIs | `oc describe sub`, OLM logs | Add dependency catalog/package |
| Private catalog cannot pull | Missing secret or wrong namespace | pod events | Create secret in CatalogSource namespace and reference it |
| Default CatalogSource edits revert | Managed by Marketplace Operator | annotations, operatorhub config | Disable default source and create custom source |
| Catalog pod unschedulable | taints/nodeSelector/resource pressure | `oc describe pod` | Fix `grpcPodConfig`, resources, nodes |

## 31. Common Real-World Scenarios

### Scenario 1: OperatorHub shows no Operators

Commands:

```bash
oc get operatorhub cluster -o yaml
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
oc get packagemanifest -n openshift-marketplace | head
```

Possible root causes:

- `disableAllDefaultSources: true`
- Catalog pods failing
- Proxy/registry problem
- Package server problem
- Disconnected cluster without mirrored catalogs

Fix path:

1. Confirm whether default sources are intentionally disabled.
2. Check catalog pods.
3. Check catalog source status.
4. Add mirrored/custom CatalogSource if disconnected.
5. Confirm PackageManifests appear.

### Scenario 2: CatalogSource is READY but Operator install fails

CatalogSource readiness only means OLM can query metadata. Installation can still fail because of:

- Missing OperatorGroup
- Wrong channel
- Manual InstallPlan not approved
- CSV deployment issue
- Required CRD/API unavailable
- Webhook/APIService issue
- Operand image pull issue
- SCC/security restrictions

Commands:

```bash
oc get sub,ip,csv -n <namespace>
oc describe sub <name> -n <namespace>
oc describe installplan <name> -n <namespace>
oc describe csv <name> -n <namespace>
```

### Scenario 3: Disconnected install shows bundle but Operator pod image pull fails

Catalog metadata is mirrored, but operand images are missing.

Check CSV related images:

```bash
oc get csv <csv-name> -n <namespace> -o yaml | grep -A20 relatedImages
```

Fix:

- Mirror related images.
- Ensure image mirror policies are correct.
- Confirm registry authentication and trust.

### Scenario 4: Custom catalog package not visible

Check catalog content locally:

```bash
opm render registry.example.com/olm/custom-index:v1 | grep -i <package-name>
opm validate ./catalog
```

Check cluster:

```bash
oc describe catalogsource custom-index -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
oc get packagemanifest -n openshift-marketplace | grep -i <package-name>
```

Possible fixes:

- Rebuild catalog image.
- Correct package/channel metadata.
- Push correct tag.
- Update CatalogSource image field.
- Restart catalog pod only after confirming image reference and content.

## 34. CatalogSource vs OperatorHub

OperatorHub is the UI/discovery experience. CatalogSource is the backend source of truth for OLM Classic catalog metadata.

```text
OperatorHub = user-facing catalog browser
CatalogSource = cluster API object pointing to catalog content
```

If OperatorHub is empty, troubleshoot CatalogSources and PackageManifests first.

## 35. CatalogSource vs ClusterCatalog in OLM v1

OpenShift 4.18 introduced OLM v1 as generally available alongside OLM Classic. In OLM v1, catalog management uses `ClusterCatalog` rather than OLM Classic `CatalogSource`.

### 35.1 OLM Classic

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: registry.redhat.io/redhat/redhat-operator-index:v4.19
```

### 35.2 OLM v1

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterCatalog
metadata:
  name: my-redhat-operators
spec:
  priority: 1000
  source:
    type: Image
    image:
      ref: registry.redhat.io/redhat/redhat-operator-index:v4.19
      pollIntervalMinutes: 10
```

### 35.3 Operational difference

| Area | OLM Classic | OLM v1 |
|---|---|---|
| Catalog API | `CatalogSource` | `ClusterCatalog` |
| Install API | `Subscription`, `InstallPlan`, `CSV` | Newer extension APIs such as `ClusterExtension` |
| Catalog transport | gRPC catalog pod/service | catalogd unpacks and serves catalog content |
| Existing production usage | Very common | Increasing in newer OCP versions |
| Admin exam/lab relevance | Very high | Version-dependent |

Senior advice: know both. Many clusters and exams still heavily use OLM Classic CatalogSource. Newer platform architecture discussions increasingly mention OLM v1 ClusterCatalog.

## 36. Best Practices

### 36.1 Production CatalogSource best practices

- Use curated internal catalogs for production.
- Disable untrusted default sources if not needed.
- Avoid `latest` tags.
- Pin images by digest when strict auditability is required.
- Use GitOps for CatalogSource changes.
- Keep catalog images aligned with OpenShift minor versions.
- Validate FBC content before publishing.
- Test Operator installs in a non-production cluster first.
- Use manual InstallPlan approval for sensitive Operators.
- Monitor catalog pod health.
- Keep registry trust and proxy configuration documented.

### 36.2 Disconnected best practices

- Mirror catalogs using supported OpenShift mirroring workflows.
- Confirm related images are mirrored.
- Test install and upgrade offline.
- Avoid direct public registry references in production disconnected clusters.
- Maintain a repeatable mirror update process.
- Record catalog image digest and mirror date.

### 36.3 Security best practices

- Restrict who can create or update CatalogSources.
- Review CSV permissions before Operator approval.
- Prefer vendor-supported Operators.
- Maintain an allowlist of approved packages.
- Use image signature verification where required.
- Remove stale catalogs.
- Keep `community-operators` disabled unless explicitly approved.

## 38. Interview-Ready Explanation

A strong senior-level explanation:

> A CatalogSource is the OLM Classic resource that registers an Operator catalog with OpenShift. In most OpenShift 4.x clusters, it points to a catalog/index image and uses `sourceType: grpc`. OLM runs that image as a catalog pod, exposes it through a service, and queries it over gRPC to discover packages, channels, bundles, CSVs, CRDs, and dependency metadata. OperatorHub and `PackageManifest` are populated from these catalog sources. A Subscription later references the catalog source using `source` and `sourceNamespace` to install or upgrade an Operator. In production, CatalogSource management is important for supply-chain security, disconnected operations, version pinning, catalog curation, and upgrade governance. In newer OpenShift versions, OLM v1 also introduces ClusterCatalog, but CatalogSource remains fundamental for OLM Classic workflows.

## 40. Common Mistakes

| Mistake | Why it hurts | Correct approach |
|---|---|---|
| Creating CatalogSource in wrong namespace | OperatorHub or Subscription cannot find it | Use `openshift-marketplace` or correct `sourceNamespace` |
| Using wrong package name in Subscription | Resolver cannot find package | Check `PackageManifest` name |
| Using wrong channel | Install/upgrade not available | Inspect channels in PackageManifest |
| Forgetting pull secret | Catalog pod `ImagePullBackOff` | Create secret in CatalogSource namespace and reference it |
| Assuming CatalogSource installs Operator | Nothing installed | Create Subscription and OperatorGroup |
| Editing default CatalogSource directly | Marketplace Operator reverts changes | Disable default and create custom source |
| Using `latest` tag | Uncontrolled catalog changes | Use version tag or digest |
| Mirroring catalog only | Operator operand images fail | Mirror related images too |
| Ignoring `TRANSIENT_FAILURE` | OperatorHub/installs broken | Check pod, service, endpoints, logs |
| Leaving community catalogs enabled in regulated prod | Unapproved Operators visible | Disable or curate catalogs |

## 41. Senior Admin Mental Model

When troubleshooting Operator installation, ask in this order:

```text
1. Is the CatalogSource present?
2. Is the catalog pod running?
3. Is the catalog service reachable?
4. Is CatalogSource status READY?
5. Does PackageManifest show the package?
6. Does the package have the expected channel/version?
7. Does Subscription reference the right source/sourceNamespace/channel?
8. Was an InstallPlan created?
9. Is InstallPlan approved?
10. Did CSV install successfully?
11. Did the Operator deployment become available?
12. Can operand images pull and run?
```

This sequence prevents random guessing.

## 42. Final Takeaway

A CatalogSource is the **catalog entry point for OLM Classic**. It decides what Operator metadata is visible and installable in OpenShift. In daily operations, it connects registries, OperatorHub, package manifests, subscriptions, install plans, and CSVs.

For advanced OpenShift administration, master CatalogSource in five dimensions:

1. **Architecture:** catalog image -> catalog pod -> gRPC service -> OLM resolver.
2. **Operations:** create, update, verify, delete, and monitor CatalogSources.
3. **Security:** curate, mirror, pin, restrict, and audit Operator sources.
4. **Troubleshooting:** diagnose `TRANSIENT_FAILURE`, image pulls, missing packages, and failed upgrades.
5. **Version awareness:** understand OLM Classic `CatalogSource` and OLM v1 `ClusterCatalog` differences.

If you can confidently explain and troubleshoot this chain, you are operating at a senior OpenShift administrator level.
