## 1. Executive Summary

Operator dependency troubleshooting is the process of identifying why OLM cannot install, upgrade, or reconcile an Operator because the dependency graph is not solvable or the resources selected by the resolver cannot be created successfully.

In simple terms:

> **A Subscription says what Operator you want. A CatalogSource says what Operator versions are available. OLM resolves a compatible set of CSVs, CRDs, APIs, packages, and versions. The InstallPlan applies the solution. The CSV becomes the running Operator version.**

When dependency troubleshooting is required, the failure is usually not inside the application pod first. It is usually in one of these layers:

| Layer | Typical Problem |
|---|---|
| CatalogSource | Catalog pod unhealthy, image pull error, stale index, wrong source namespace, catalog missing package |
| Package/channel | Package exists but selected channel has no valid upgrade path or no version satisfying dependency |
| Subscription | Wrong package name, wrong channel, wrong source, manual InstallPlan not approved, old status |
| Resolver | `ResolutionFailed`, `ConstraintsNotSatisfiable`, missing API provider, package/version conflict |
| InstallPlan | Plan not approved, failed bundle unpack, CRD/RBAC creation failure |
| CSV | Requirements not met, OperatorGroup unsupported, deployment failure, APIService failure |
| OperatorGroup | Missing, multiple in same namespace, install mode mismatch, target namespace conflict |
| CRD/API | Required CRD not provided, CRD upgrade blocked by incompatible existing custom resources |
| Disconnected environment | Catalog mirrored but bundle or related images missing; proxy/CA/registry policy issue |

The key is to **follow the OLM chain**, not randomly delete objects:

```text
CatalogSource -> PackageManifest -> Subscription -> InstallPlan -> CSV -> Operator Deployment -> CRDs/APIs
```

## 2. Where Operator Dependency Troubleshooting Fits

In OpenShift, most add-on platform capabilities are delivered as Operators:

- OpenShift Logging
- OpenShift GitOps
- OpenShift Pipelines
- File Integrity Operator
- Compliance Operator
- Service Mesh Operators
- External Secrets Operators
- Storage Operators
- Database Operators
- Monitoring integrations
- Security and policy Operators

An enterprise cluster usually has many Operators installed in shared namespaces such as:

- `openshift-operators`
- `openshift-logging`
- `openshift-storage`
- `openshift-gitops-operator`
- custom tenant namespaces

Dependency troubleshooting becomes important when:

- An Operator installation is stuck.
- An upgrade is not generating a new InstallPlan.
- A Subscription shows `ResolutionFailed`.
- Multiple Operators in the same namespace stop upgrading.
- A catalog update breaks previously working installations.
- A disconnected cluster cannot resolve or unpack a bundle.
- One Operator requires another Operator, CRD, APIService, or package version.
- A vendor changes catalog location or package naming.
- A channel switch breaks the upgrade path.

A senior administrator should think of this as **package dependency resolution plus Kubernetes API safety**.

OLM is more conservative than many package managers because Operators are continuously running controllers. If OLM installs an incompatible dependency set, one controller might remove or change APIs used by another controller. OLM therefore tries to avoid installing or upgrading a set of Operators that cannot work together.

## 3. OLM Dependency Resolution Mental Model

### 3.1 The Core Idea

OLM does not simply install the latest image tag. It resolves a set of constraints.

A requested Operator might say:

```text
I provide API A.
I require API B.
I require package prometheus version >0.27.0.
I must be installed in a namespace with a compatible OperatorGroup.
I belong to package X and channel stable.
```

OLM looks at all visible catalogs and asks:

```text
Can I find a valid set of Operator bundles that satisfies all required APIs, package versions, channel constraints, existing installed CSVs, and namespace rules?
```

If yes, OLM creates or updates an InstallPlan.

If no, the Subscription usually reports:

```yaml
conditions:
- type: ResolutionFailed
  status: "True"
  reason: ConstraintsNotSatisfiable
  message: ...
```

### 3.2 Dependency Resolution Is Namespace-Scoped

One of the most important senior-level details:

> **OLM resolves Subscriptions as a set within a namespace.**

This means one failing Subscription can block other Subscriptions in the same namespace because the resolver attempts to produce a consistent solution set for that namespace.

For example, in namespace `openshift-operators`:

```text
sub-a requires provider-x <2.0
sub-b requires provider-x >=2.1
```

Both can individually look valid, but together they can be impossible. The namespace-level solution fails.

### 3.3 OLM Uses Catalog Metadata, Not Live Guessing

OLM does not inspect random internet repositories. It uses metadata from visible CatalogSources.

If a dependency is missing from the catalog, OLM cannot resolve it even if you know the image exists somewhere.

### 3.4 OLM Resolves APIs and Packages

OLM dependency resolution is built from two major ideas:

1. **Properties** — what an Operator bundle provides, such as a GVK or package version.
2. **Constraints / dependencies** — what an Operator bundle requires, such as a required GVK or package version range.

Example:

```yaml
properties:
- type: olm.package
  value:
    packageName: example-operator
    version: 1.2.3
- type: olm.gvk
  value:
    group: cache.example.com
    version: v1
    kind: CacheCluster
```

Example dependency:

```yaml
dependencies:
- type: olm.gvk
  value:
    group: monitoring.coreos.com
    version: v1
    kind: ServiceMonitor
- type: olm.package
  value:
    packageName: prometheus
    version: ">0.27.0"
```

### 3.5 Runtime Dependency vs OLM Dependency

Do not confuse these:

| Type | Meaning | Example |
|---|---|---|
| OLM dependency | Required for installation/upgrade resolution | Operator requires `ServiceMonitor.monitoring.coreos.com/v1` |
| Runtime dependency | Required after Operator is running | Operator pod cannot connect to database |
| Kubernetes dependency | Required resource missing | ServiceAccount, Role, CRD, APIService, Deployment |
| External dependency | Registry, proxy, DNS, object storage, license server | Bundle image cannot be pulled |

A `ResolutionFailed` problem is usually an **OLM dependency** issue, not an application runtime issue.

## 4. Important OLM Objects Involved

### 4.1 CatalogSource

A `CatalogSource` is a source of Operator metadata. In OpenShift, default Red Hat catalogs normally live in:

```text
openshift-marketplace
```

Common CatalogSources:

```bash
oc get catalogsource -n openshift-marketplace
```

Example:

```text
NAME                  DISPLAY               TYPE   PUBLISHER   AGE
redhat-operators      Red Hat Operators      grpc   Red Hat      20d
certified-operators   Certified Operators    grpc   Red Hat      20d
community-operators   Community Operators    grpc   Red Hat      20d
```

A CatalogSource provides:

- Package names
- Channels
- CSV metadata
- CRDs and APIs provided by bundles
- Dependency metadata
- Upgrade graph information

If the CatalogSource is unhealthy, dependency resolution can fail even if the Subscription is correct.

### 4.2 PackageManifest

A `PackageManifest` is the discovered package view from a catalog.

Use it to answer:

- Does the Operator exist?
- Which catalog provides it?
- Which channels exist?
- Which channel is default?
- Which CSV is current in each channel?
- Which install modes are supported?

Commands:

```bash
oc get packagemanifests -n openshift-marketplace | grep -i <operator>
oc describe packagemanifest <package-name> -n openshift-marketplace
oc get packagemanifest <package-name> -n openshift-marketplace -o yaml
```

When multiple catalogs provide the same package name, always filter by catalog:

```bash
oc get packagemanifest \
  --selector=catalog=<catalogsource-name> \
  --field-selector metadata.name=<package-name> \
  -n openshift-marketplace -o yaml
```

### 4.3 Subscription

A `Subscription` declares intent:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-namespace
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
```

Important fields:

| Field | Meaning |
|---|---|
| `spec.name` | Package name |
| `spec.channel` | Update channel |
| `spec.source` | CatalogSource name |
| `spec.sourceNamespace` | Namespace containing CatalogSource |
| `spec.installPlanApproval` | `Automatic` or `Manual` |
| `status.currentCSV` | Newest CSV known by OLM for this subscription |
| `status.installedCSV` | CSV currently installed |
| `status.installPlanRef` | InstallPlan generated for this Subscription |
| `status.conditions` | Most important troubleshooting signal |

### 4.4 InstallPlan

An `InstallPlan` is the resolved set of Kubernetes resources OLM will create.

It can contain:

- CSVs
- CRDs
- ServiceAccounts
- Roles / ClusterRoles
- RoleBindings / ClusterRoleBindings
- Deployments
- APIService objects
- Webhook configurations

Commands:

```bash
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
oc get installplan <installplan-name> -n <operator-namespace> -o yaml
```

Common phases:

```text
RequiresApproval
Installing
Complete
Failed
```

### 4.5 ClusterServiceVersion

A `ClusterServiceVersion` or CSV represents a specific installed Operator version.

Commands:

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc get csv <csv-name> -n <operator-namespace> -o yaml
```

Important CSV areas:

- `metadata.name`
- `spec.version`
- `spec.install.modes`
- `spec.customresourcedefinitions.owned`
- `spec.customresourcedefinitions.required`
- `spec.apiservicedefinitions.owned`
- `spec.apiservicedefinitions.required`
- `spec.install.spec.deployments`
- `status.phase`
- `status.reason`
- `status.message`
- `status.requirementStatus`

### 4.6 OperatorGroup

An `OperatorGroup` defines where an Operator watches and where OLM generates RBAC.

Commands:

```bash
oc get operatorgroup -n <operator-namespace>
oc describe operatorgroup <name> -n <operator-namespace>
```

Important points:

- A namespace should normally have exactly one OperatorGroup for OLM-managed Operators.
- The Operator’s CSV must support the selected install mode.
- An OperatorGroup targets one namespace, multiple namespaces, or all namespaces.
- If the target namespace set is unsupported, CSV installation can fail.

### 4.7 CRDs and APIs

Dependencies are often expressed as required APIs.

Commands:

```bash
oc get crd | grep -i <api-or-kind>
oc api-resources | grep -i <kind>
oc get apiservice | grep -i <group-or-version>
```

A common dependency problem is:

```text
Operator A requires GVK X, but no installed or installable Operator provides X.
```

## 5. What Is an Operator Dependency?

An Operator dependency is a requirement declared by an Operator bundle so OLM can ensure another API, Operator package, version, or generic property exists before installing or upgrading.

### 5.1 API / GVK Dependency

The most common form.

Example:

```yaml
dependencies:
- type: olm.gvk
  value:
    group: monitoring.coreos.com
    version: v1
    kind: ServiceMonitor
```

Meaning:

```text
This Operator requires a provider of ServiceMonitor.monitoring.coreos.com/v1.
```

In OpenShift, the Prometheus Operator usually provides monitoring APIs like `ServiceMonitor`, but availability depends on cluster version, catalog, and namespace/operator design.

### 5.2 Package Dependency

Example:

```yaml
dependencies:
- type: olm.package
  value:
    packageName: prometheus
    version: ">0.27.0"
```

Meaning:

```text
This Operator requires the prometheus package with version greater than 0.27.0.
```

### 5.3 Generic Constraint

Example:

```yaml
properties:
- type: olm.constraint
  value:
    failureMessage: 'requires a certified provider'
    cel:
      rule: 'properties.exists(p, p.type == "certified")'
```

Meaning:

```text
The resolver must select a bundle whose properties satisfy this rule.
```

### 5.4 CSV Required CRD Dependency

Older style dependency may appear inside CSV:

```yaml
spec:
  customresourcedefinitions:
    required:
    - name: service.monitors.monitoring.coreos.com
      version: v1
      kind: ServiceMonitor
```

### 5.5 Dependency Is Not Always a Separate Operator

A dependency can be satisfied by:

- An Operator already installed in the namespace solution set
- A new Operator from a visible catalog
- A CRD/API provided by another selected CSV
- A package version selected through catalog metadata

But if the required provider is not available in any visible catalog, OLM cannot invent it.

## 6. How OLM Resolves Dependencies

### 6.1 High-Level Flow

```text
1. User creates Subscription.
2. Catalog Operator reads Subscription.
3. Catalog Operator queries CatalogSources.
4. Resolver builds dependency problem.
5. Resolver selects candidate CSVs/bundles.
6. Catalog Operator creates InstallPlan.
7. Admin approves InstallPlan if Manual.
8. OLM creates CRDs/RBAC/CSV/Deployment.
9. CSV reaches Succeeded if requirements are met.
```

### 6.2 Resolver Input

OLM considers:

- Existing CSVs in the namespace
- Existing Subscriptions in the namespace
- Package and channel requested by Subscription
- CatalogSource and source namespace
- Bundle properties
- Bundle dependencies
- Provided APIs
- Required APIs
- Package version ranges
- Catalog priority
- Channel ordering
- Update graph
- Install mode compatibility through OperatorGroup

### 6.3 Resolver Output

The resolver produces an InstallPlan.

Example logic:

```text
Subscription requests package X channel stable.
X latest channel head requires package Y >=1.5.
Catalog has Y 1.6.
InstallPlan includes X CSV and Y CSV.
```

If impossible:

```text
Subscription requests package X channel stable.
X requires package Y >=2.0.
Catalog only has Y 1.8.
ResolutionFailed.
```

### 6.4 Why One Bad Subscription Can Block Others

All Subscriptions in the same namespace are part of a resolver set.

Think of it like a `requirements.txt` file:

```text
operator-a==1.0
operator-b>=2.0
operator-c requires operator-a>=2.0
```

The whole set is impossible. OLM reports failures and might not progress other installs in that namespace until the impossible constraint is fixed.

### 6.5 OLM Does Not Compare Versions Like Humans

For update channels, OLM follows the update graph. A channel head is not always the highest semver number. The catalog graph determines what is “latest” in a channel.

This matters when troubleshooting:

- Broken `replaces` chain
- Missing intermediate bundle
- Incorrect `skips` or `skipRange`
- Channel switch with no upgrade path
- Custom catalog built incorrectly

## 7. Dependency Types: `olm.gvk`, `olm.package`, `olm.constraint`

### 7.1 `olm.gvk`

Used when an Operator requires a Kubernetes API by group/version/kind.

Example:

```yaml
dependencies:
- type: olm.gvk
  value:
    group: example.com
    version: v1
    kind: ExampleDatabase
```

Troubleshooting question:

```text
Who provides ExampleDatabase.example.com/v1?
```

Commands:

```bash
oc api-resources | grep -i ExampleDatabase
oc get crd | grep -i exampledatabase
oc get csv -A -o yaml | grep -B5 -A15 "ExampleDatabase"
```

### 7.2 `olm.package`

Used when an Operator requires another package/version.

Example:

```yaml
dependencies:
- type: olm.package
  value:
    packageName: prometheus
    version: ">=0.37.0 <1.0.0"
```

Troubleshooting questions:

```text
Does that package exist in the visible catalog?
Does the selected catalog provide a version in the required range?
Is the package in a channel that OLM can select?
Is another installed CSV from the same package causing conflict?
```

Commands:

```bash
oc get packagemanifest prometheus -n openshift-marketplace -o yaml
oc get packagemanifest prometheus \
  --selector=catalog=redhat-operators \
  -n openshift-marketplace -o yaml
```

### 7.3 `olm.constraint`

Used for more complex rules.

Constraint types can include:

- `gvk`
- `package`
- `cel`
- `all`
- `any`
- `not`

Example:

```yaml
schema: olm.bundle
name: red.v1.0.0
properties:
- type: olm.constraint
  value:
    failureMessage: Required dependency is not available
    any:
      constraints:
      - gvk:
          group: blue.example.com
          version: v1
          kind: Blue
      - package:
          name: blue-operator
          versionRange: '>=1.0.0'
```

Troubleshooting question:

```text
Which part of the constraint is impossible?
```

### 7.4 Dependency Best Practice From Admin View

As an administrator, you might not author the Operator, but you must understand vendor metadata quality.

Good dependency metadata:

- Requires exact APIs needed.
- Uses minimum version when a feature is needed but API version did not change.
- Avoids unnecessarily tight maximum version ranges.
- Provides clear failure messages for generic constraints.

Bad dependency metadata:

- Requires package versions too narrowly.
- Uses package dependency when API dependency would be safer.
- Missing required GVKs.
- Declares a GVK but catalog provider does not provide it.
- Broken update graph.

## 8. Common Symptoms

### 8.1 Subscription Shows `ResolutionFailed`

Command:

```bash
oc describe sub <subscription> -n <namespace>
```

Example:

```text
Conditions:
  Type:    ResolutionFailed
  Status:  True
  Reason:  ConstraintsNotSatisfiable
  Message: constraints not satisfiable: ...
```

Meaning:

```text
OLM cannot find a valid dependency solution for the namespace.
```

### 8.2 Subscription Has No InstallPlan

```bash
oc get sub <subscription> -n <namespace> -o yaml
```

Look for:

```yaml
status:
  installPlanRef: null
```

Possible causes:

- CatalogSource unhealthy
- Package not found
- Wrong source/sourceNamespace
- Early catalog-operator processing error
- Resolver cannot solve dependencies
- Subscription is malformed

### 8.3 InstallPlan Requires Manual Approval

```bash
oc get installplan -n <namespace>
```

Example:

```text
NAME            CSV                         APPROVAL   APPROVED
install-abcde   example-operator.v1.2.3     Manual     false
```

Fix:

```bash
oc patch installplan install-abcde -n <namespace> \
  --type merge -p '{"spec":{"approved":true}}'
```

### 8.4 InstallPlan Failed

```bash
oc describe installplan <name> -n <namespace>
```

Possible causes:

- CRD already exists with incompatible ownership
- RBAC denied
- APIService creation failure
- Bundle unpack job failed
- Image pull error
- Invalid bundle metadata

### 8.5 CSV Stuck in Pending / Failed

```bash
oc describe csv <csv> -n <namespace>
```

Look for:

- `status.phase`
- `status.reason`
- `status.message`
- `status.requirementStatus`

Possible causes:

- Missing required API
- OperatorGroup mismatch
- Deployment unavailable
- Webhook/APIService issue
- CRD ownership conflict
- Pod security / SCC issue

### 8.6 CatalogSource Unhealthy

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <name> -n openshift-marketplace
oc get pods -n openshift-marketplace
```

Possible causes:

- Catalog image cannot be pulled
- Registry unreachable
- Proxy/CA issue
- Pod scheduling issue
- Catalog pod crash
- Wrong `securityContextConfig`
- Bad custom catalog image

### 8.7 Orphan CSV Blocks Reinstallation

Symptom message often includes:

```text
clusterserviceversion <operator>.v1.0.0 exists and is not referenced by a subscription
```

Meaning:

```text
A CSV remains from an old Subscription, but no Subscription owns it now. New Subscription cannot simply associate with it.
```

Common fix:

```bash
oc delete csv <old-csv> -n <namespace>
```

Only do this after checking CRDs, custom resources, and impact.

## 9. Golden Troubleshooting Flow

Use this every time.

### Step 1: Identify Namespace and Package

```bash
NS=<operator-namespace>
PKG=<package-name>
SUB=<subscription-name>
```

Find all related objects:

```bash
oc get sub,ip,csv,operatorgroup -n $NS
```

### Step 2: Read Subscription Status

```bash
oc get sub $SUB -n $NS -o yaml
oc describe sub $SUB -n $NS
```

Focus on:

```yaml
spec:
  channel:
  name:
  source:
  sourceNamespace:
  installPlanApproval:
status:
  currentCSV:
  installedCSV:
  installPlanRef:
  conditions:
```

Interpretation:

| Observation | Meaning |
|---|---|
| No status | Catalog Operator may not be processing the Subscription |
| `CatalogSourcesUnhealthy` | Catalog layer issue |
| `ResolutionFailed` | Dependency solver failed |
| `InstallPlanPending` | Manual approval or unresolved plan |
| `InstallPlanFailed` | Plan generated but failed to execute |
| `currentCSV != installedCSV` | Upgrade available or stuck |

### Step 3: Inspect InstallPlan

```bash
IP=$(oc get sub $SUB -n $NS -o jsonpath='{.status.installPlanRef.name}')
echo $IP
oc get installplan $IP -n $NS -o yaml
oc describe installplan $IP -n $NS
```

Check:

- `spec.approved`
- `spec.approval`
- `spec.clusterServiceVersionNames`
- `status.phase`
- `status.conditions`
- `status.plan[].status`
- Failed resource name/kind

### Step 4: Inspect CSV

```bash
oc get csv -n $NS
oc describe csv <csv-name> -n $NS
oc get csv <csv-name> -n $NS -o yaml
```

Check:

- Required CRDs
- Owned CRDs
- Install modes
- Requirement status
- Deployment status
- Related images

### Step 5: Inspect OperatorGroup

```bash
oc get og -n $NS -o yaml
```

Check:

- Is there exactly one OperatorGroup?
- Does it target expected namespace(s)?
- Does CSV support that install mode?
- Does the CSV have `olm.targetNamespaces` annotation?

### Step 6: Inspect CatalogSource

```bash
SRC=$(oc get sub $SUB -n $NS -o jsonpath='{.spec.source}')
SRCNS=$(oc get sub $SUB -n $NS -o jsonpath='{.spec.sourceNamespace}')
echo $SRC $SRCNS
oc get catalogsource $SRC -n $SRCNS -o yaml
oc describe catalogsource $SRC -n $SRCNS
oc get pods -n $SRCNS | grep $SRC
```

Check:

- `status.connectionState.lastObservedState`
- Registry service
- Pod readiness
- Image pull
- Catalog pod logs

### Step 7: Confirm Package and Channel

```bash
oc get packagemanifest $PKG -n openshift-marketplace -o yaml
```

Filter by catalog:

```bash
oc get packagemanifest \
  --selector=catalog=$SRC \
  --field-selector metadata.name=$PKG \
  -n openshift-marketplace -o yaml
```

Check:

- Does package exist?
- Does channel exist?
- Is the channel head expected?
- Does install mode match OperatorGroup?
- Does the package exist in multiple catalogs?

### Step 8: Read Catalog Operator Logs

```bash
oc logs -n openshift-operator-lifecycle-manager deployment/catalog-operator --tail=200
```

Search around Subscription name, namespace, package, InstallPlan name.

### Step 9: Decide Fix Safely

Do not start by deleting CRDs or CSVs. Choose based on evidence:

| Root Cause | Safer Fix |
|---|---|
| Wrong Subscription source/channel | Patch or recreate Subscription |
| Manual InstallPlan pending | Approve InstallPlan |
| CatalogSource unhealthy | Fix catalog image, registry, proxy, CA, scheduling |
| Orphan CSV | Delete orphan CSV after impact review |
| Duplicate package in namespace | Remove duplicate Subscription/CSV |
| Missing dependency provider | Install provider Operator or use catalog containing provider |
| Broken update graph | Correct catalog or switch supported channel/source |
| Disconnected missing images | Mirror full catalog and bundle/related images |
| OperatorGroup mismatch | Recreate correct OperatorGroup/namespace plan |

## 11. Troubleshooting `ResolutionFailed`

### 11.1 Meaning

`ResolutionFailed` means OLM could not compute a valid dependency solution for the Subscription set in the namespace.

Example:

```yaml
conditions:
- type: ResolutionFailed
  status: "True"
  reason: ConstraintsNotSatisfiable
  message: 'constraints not satisfiable: ...'
```

### 11.2 First Commands

```bash
oc describe sub <sub> -n <ns>
oc get sub <sub> -n <ns> -o yaml
oc get sub -n <ns>
oc get csv -n <ns>
oc get installplan -n <ns>
```

### 11.3 Decode Message

Resolution messages are long, but they usually contain useful hints.

Look for phrases:

| Phrase | Meaning |
|---|---|
| `requires` | Subscription or bundle requires a package/API |
| `originates from package` | Package conflict or duplicate package candidate |
| `exists and is not referenced by a subscription` | Orphan CSV problem |
| `no operators found` | Missing package/provider in catalog |
| `not found in channel` | Wrong channel or broken graph |
| `constraints not satisfiable` | Dependency set impossible |
| `CatalogSourcesUnhealthy` | Catalog layer blocking resolution |

### 11.4 Root-Cause Questions

Ask in order:

1. Is the requested package present in the selected CatalogSource?
2. Is the requested channel present?
3. Is the CatalogSource healthy?
4. Is an old CSV already installed from the same package?
5. Is there a Subscription for the old CSV?
6. Does another Subscription in the namespace require a conflicting version?
7. Does the selected bundle require an API that no catalog provides?
8. Does a different catalog provide a better match?
9. Is the cluster disconnected and missing mirrored metadata/images?
10. Is the OperatorGroup compatible with the install mode?

### 11.5 Common Fixes

#### Fix Wrong Source or Channel

```bash
oc patch sub <sub> -n <ns> --type merge -p '{"spec":{"channel":"stable","source":"redhat-operators","sourceNamespace":"openshift-marketplace"}}'
```

Be careful: channel changes can change upgrade path and dependency selection.

#### Fix Orphan CSV

```bash
oc get csv -n <ns>
oc delete csv <orphan-csv> -n <ns>
```

Only after checking impact.

#### Fix Bad Catalog

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalog> -n openshift-marketplace
oc get pods -n openshift-marketplace
```

Patch image or restore correct catalog:

```bash
oc patch catalogsource <catalog> -n openshift-marketplace --type merge \
  -p '{"spec":{"image":"registry.example.com/my-index:v4.19"}}'
```

#### Fix Missing Dependency Provider

Install the provider Operator or use a catalog that contains it.

```bash
oc get packagemanifests -n openshift-marketplace | grep -i <provider>
```

## 12. Troubleshooting `ConstraintsNotSatisfiable`

### 12.1 Meaning

`ConstraintsNotSatisfiable` is usually the reason under `ResolutionFailed`.

It means:

```text
The requested Subscription set cannot be satisfied by the available bundle metadata and existing namespace state.
```

### 12.2 Example: Orphan CSV

Message:

```text
constraints not satisfiable: @existing/my-ns/example-operator.v1.0.0
and redhat-operators/openshift-marketplace/stable/example-operator.v1.1.0
originate from package example-operator,
subscription example-operator requires example-operator.v1.1.0,
clusterserviceversion example-operator.v1.0.0 exists and is not referenced by a subscription
```

Interpretation:

```text
An old CSV exists, but the Subscription does not own it. OLM cannot select both old and new CSVs from the same package.
```

Fix options:

- If upgrade is desired, delete old CSV and let OLM install the selected CSV.
- If old version must remain, delete the new Subscription.

### 12.3 Example: Required Package Version Missing

Message:

```text
constraints not satisfiable: subscription app-operator requires db-operator >=2.0.0, no operators found satisfying package db-operator >=2.0.0
```

Check:

```bash
oc get packagemanifest db-operator -n openshift-marketplace -o yaml
```

Fix:

- Add/update catalog containing required version.
- Change to a supported Operator version/channel that requires available dependency.
- Mirror correct catalog in disconnected environment.

### 12.4 Example: Two Operators Require Conflicting Provider Versions

```text
operator-a requires provider >=1.0 <2.0
operator-b requires provider >=2.0
```

Fix options:

- Move Operators to separate namespaces if supported.
- Choose compatible channels.
- Upgrade/downgrade one Operator to a compatible stream.
- Ask vendor for supported dependency matrix.

### 12.5 Example: Required GVK Not Provided

```text
requires gvk monitoring.coreos.com/v1, Kind=ServiceMonitor, no bundle provides it
```

Check:

```bash
oc api-resources | grep -i servicemonitor
oc get crd | grep -i servicemonitor
oc get packagemanifests -n openshift-marketplace | grep -i prometheus
```

Fix:

- Install provider Operator.
- Enable catalog containing provider.
- Select an Operator channel that does not require that API.
- Use correct OpenShift version/catalog for the operator.

## 13. Troubleshooting Missing Required API / GVK

### 13.1 Typical CSV Requirement Output

```text
requirements not met: no operators found in package ... providing required API
```

Or in CSV:

```yaml
status:
  phase: Pending
  reason: RequirementsNotMet
  requirementStatus:
  - group: monitoring.coreos.com
    kind: ServiceMonitor
    name: servicemonitors.monitoring.coreos.com
    status: NotPresent
    version: v1
```

### 13.2 Required API Checklist

1. Identify exact GVK.
2. Check whether CRD/APIService exists.
3. Check whether an installed CSV owns it.
4. Check whether a visible catalog can provide it.
5. Check whether the provider’s install mode is compatible.
6. Check whether provider is blocked by its own dependencies.

### 13.3 Commands

```bash
# Search CRDs
oc get crd | grep -i <kind-or-group>

# Search API resources
oc api-resources | grep -i <kind>

# Search APIService, useful for aggregated APIs
oc get apiservice | grep -i <group>

# Find CSVs that own/require the API
oc get csv -A -o yaml | grep -B10 -A20 "kind: <Kind>"
```

### 13.4 Common Mistake

Do not manually create a CRD just to satisfy OLM unless you fully understand the lifecycle impact.

Why?

- OLM tracks ownership.
- The provider Operator may expect a specific CRD schema.
- Future upgrades can fail.
- CRD schema mismatch can break custom resources.

A manual CRD can make installation appear to progress but fail later in reconciliation.

### 13.5 Correct Fix Pattern

Preferred:

```text
Install or restore the Operator that owns/provides the required API.
```

Example:

```bash
oc get packagemanifests -n openshift-marketplace | grep -i <provider>
oc apply -f provider-subscription.yaml
```

Then confirm:

```bash
oc get csv -n <provider-ns>
oc get crd | grep -i <required-api>
```

## 14. Troubleshooting Package and Version Conflicts

### 14.1 What Is a Package Conflict?

A package conflict occurs when OLM cannot select a single valid CSV for a package in a namespace.

Common causes:

- Two Subscriptions request the same package with different channels.
- Existing CSV from same package is not referenced by a Subscription.
- A dependency requires a version range incompatible with installed CSV.
- Catalog has multiple providers and OLM preference selects unexpected one.
- Channel head requires dependencies unavailable in the cluster.

### 14.2 Check Same Package in Namespace

```bash
oc get sub -n <ns> -o custom-columns=NAME:.metadata.name,PACKAGE:.spec.name,CHANNEL:.spec.channel,SOURCE:.spec.source
oc get csv -n <ns>
```

Look for:

```text
multiple CSVs with same package family
old CSV without matching Subscription
multiple Subscriptions for same spec.name
```

### 14.3 Check Package Versions and Channels

```bash
oc get packagemanifest <pkg> -n openshift-marketplace -o json \
  | jq '.status.channels[] | {name: .name, currentCSV: .currentCSV}'
```

### 14.4 Fix Duplicate Subscriptions

If two Subscriptions request same package:

```bash
oc delete sub <duplicate-sub> -n <ns>
```

Then inspect CSVs:

```bash
oc get csv -n <ns>
```

If an unwanted CSV remains:

```bash
oc delete csv <unwanted-csv> -n <ns>
```

### 14.5 Fix Version Range Conflict

If Operator A requires Provider `<2.0` and Operator B requires Provider `>=2.0`, you must choose a compatible matrix.

Possible actions:

- Upgrade Operator A to a channel supporting Provider `>=2.0`.
- Downgrade or change Operator B channel.
- Move one Operator to another namespace if supported and if dependency scope allows.
- Use separate clusters for incompatible platform add-ons.
- Get vendor-supported version matrix.

Do not force patch CSV dependency metadata in production. It will be overwritten and unsupported.

## 15. Troubleshooting Orphaned CSV Problems

### 15.1 What Is an Orphan CSV?

An orphan CSV is a CSV left behind after its Subscription was deleted.

Example:

```bash
oc delete sub example-operator -n example-ns
# CSV might remain
oc get csv -n example-ns
```

If a new Subscription is created later, OLM might not associate it with the old CSV.

### 15.2 Symptom

```text
clusterserviceversion example-operator.v1.0.0 exists and is not referenced by a subscription
```

### 15.3 Why It Blocks

The resolver sees:

- Existing CSV from package `example-operator`
- New Subscription requiring a CSV from same package
- Package constraint: within a namespace, no two Operators should come from the same package

So the resolver cannot select both.

### 15.4 Safe Remediation

#### Step 1: Check Custom Resources

```bash
oc get crd | grep -i example
oc api-resources | grep -i example
```

Check CRs:

```bash
oc get <custom-resource> -A
```

#### Step 2: Backup CRs

```bash
oc get <custom-resource> -A -o yaml > backup-example-crs.yaml
```

#### Step 3: Delete Orphan CSV

```bash
oc delete csv example-operator.v1.0.0 -n example-ns
```

#### Step 4: Recreate or Let Subscription Reconcile

```bash
oc get sub -n example-ns
oc get installplan -n example-ns
oc get csv -n example-ns
```

### 15.5 When Not to Delete CSV Immediately

Do not delete immediately if:

- The Operator manages critical stateful workloads.
- CRDs have finalizers controlled by the Operator.
- The Operator performs backup/restore or storage lifecycle operations.
- You do not know which CRs exist.
- A vendor uninstall procedure exists and must be followed.

## 16. Troubleshooting CatalogSource Dependency Problems

### 16.1 CatalogSource Health Directly Affects Resolution

If the CatalogSource is unhealthy, OLM might not trust the available package data. Resolution can stop with `CatalogSourcesUnhealthy`.

Check:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalog> -n openshift-marketplace
oc get pods -n openshift-marketplace
```

### 16.2 Important CatalogSource Status Fields

```yaml
status:
  connectionState:
    address: redhat-operators.openshift-marketplace.svc:50051
    lastObservedState: READY
    lastConnect: "..."
  registryService:
    serviceName: redhat-operators
    serviceNamespace: openshift-marketplace
```

Interpretation:

| State | Meaning |
|---|---|
| `READY` | Catalog gRPC connection is established |
| `CONNECTING` | OLM is trying to connect |
| `TRANSIENT_FAILURE` | Temporary connection failure; often image/pod/network issue |

### 16.3 Catalog Pod Not Running

```bash
oc get pods -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

Common causes:

| Pod State | Cause |
|---|---|
| `ImagePullBackOff` | Registry unreachable, auth, mirror missing, pull secret issue |
| `CrashLoopBackOff` | Bad index image or catalog server crash |
| `Pending` | Scheduling constraints, taints, insufficient resources |
| `Running but not Ready` | gRPC server not healthy |

### 16.4 Wrong Catalog Namespace

In OpenShift, cluster-wide catalogs are normally in `openshift-marketplace`.

If a Subscription points to a namespaced CatalogSource, it must reference the correct source namespace:

```yaml
spec:
  source: my-catalog
  sourceNamespace: my-operator-ns
```

For a global OpenShift catalog:

```yaml
spec:
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

### 16.5 Package Exists in Unexpected Catalog

Problem:

```bash
oc describe packagemanifest <pkg> -n openshift-marketplace
```

may show a package from an unexpected catalog if multiple catalogs provide the same package name.

Always verify catalog explicitly:

```bash
oc get packagemanifest \
  --selector=catalog=<catalogsource> \
  --field-selector metadata.name=<pkg> \
  -n openshift-marketplace -o yaml
```

### 16.6 Catalog Priority Effects

CatalogSource has a `spec.priority` field. Higher-priority catalogs are preferred during dependency resolution. Also, options in the same catalog as the dependent Operator are preferred.

This matters when:

- A custom catalog and Red Hat catalog both provide a dependency.
- A stale custom catalog has higher priority.
- A vendor catalog provides a dependency with a narrower version set.

Check priority:

```bash
oc get catalogsource -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,PRIORITY:.spec.priority,IMAGE:.spec.image
```

### 16.7 Fix Bad Custom Catalog

Patch image:

```bash
oc patch catalogsource my-catalog -n openshift-marketplace --type merge \
  -p '{"spec":{"image":"registry.example.com/olm/my-catalog:v4.19-2026-07"}}'
```

Or delete invalid catalog if not needed:

```bash
oc delete catalogsource my-catalog -n openshift-marketplace
```

Be careful: deleting a catalog can affect future upgrades for Operators installed from that catalog.

## 19. Troubleshooting OperatorGroup Dependency Problems

### 19.1 Why OperatorGroup Matters

An OperatorGroup decides target namespaces and RBAC. CSV membership depends on OperatorGroup compatibility.

If the CSV does not support the install mode selected by the OperatorGroup, installation fails.

### 19.2 Check OperatorGroup Count

```bash
oc get og -n <ns>
```

Problem:

```text
No OperatorGroup
```

or:

```text
Multiple OperatorGroups
```

Both can break CSV installation.

### 19.3 Install Mode Types

| Install Mode | Meaning |
|---|---|
| `OwnNamespace` | Operator watches its own namespace |
| `SingleNamespace` | Operator watches one namespace |
| `MultiNamespace` | Operator watches multiple namespaces |
| `AllNamespaces` | Operator watches all namespaces |

Check supported install modes:

```bash
oc describe packagemanifest <pkg> -n openshift-marketplace
```

Or CSV:

```bash
oc get csv <csv> -n <ns> -o json | jq '.spec.installModes'
```

### 19.4 Common OperatorGroup Problems

| Problem | Symptom | Fix |
|---|---|---|
| No OperatorGroup | CSV Pending | Create valid OperatorGroup |
| Multiple OperatorGroups | CSV Failed/Pending | Keep one correct OperatorGroup |
| OperatorGroup all-namespaces but CSV does not support `AllNamespaces` | CSV unsupported install mode | Use namespace-scoped install |
| Operator requires all namespaces but OperatorGroup targets one namespace | CSV unsupported install mode | Install in `openshift-operators` or supported namespace |
| Wrong target namespace | Operator cannot watch expected CRs | Recreate OperatorGroup correctly |

### 19.5 Example OperatorGroup for Own Namespace

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: example-og
  namespace: example-operators
spec:
  targetNamespaces:
  - example-operators
```

Apply:

```bash
oc apply -f operatorgroup.yaml
```

### 19.6 Example Global OperatorGroup

Usually `openshift-operators` already has a global OperatorGroup.

Check:

```bash
oc get og -n openshift-operators -o yaml
```

A global OperatorGroup typically has no `spec.targetNamespaces`, meaning all namespaces.

## 20. Troubleshooting CRD Upgrade Dependency Problems

### 20.1 CRDs Are Cluster-Scoped

CRDs are cluster-scoped resources. If multiple Operators depend on the same CRD, CRD upgrades can affect the whole cluster.

### 20.2 OLM CRD Upgrade Safety

OLM upgrades a CRD immediately if it is owned by one CSV. If multiple CSVs own a CRD, OLM applies compatibility checks. Existing served versions must remain, and existing custom resources must validate against the new schema.

### 20.3 Symptoms

- InstallPlan stuck or failed while applying CRD.
- CSV stuck replacing old version.
- API validation errors for existing CRs.
- Operator upgrade blocked after CRD schema change.

### 20.4 Commands

```bash
oc get crd <crd-name> -o yaml
oc get <custom-resource-kind> -A -o yaml
oc describe ip <installplan> -n <ns>
oc describe csv <csv> -n <ns>
```

### 20.5 Common Root Causes

| Root Cause | Explanation |
|---|---|
| New CRD removed existing served version | Existing clients/CRs still use old version |
| Existing CRs fail new schema validation | OLM blocks unsafe CRD change |
| CRD owned by multiple CSVs | Upgrade waits for compatibility across owners |
| Manual CRD edit | Ownership/schema drift from bundle metadata |
| Finalizers on CRs | Old Operator not available to clean resources |

### 20.6 Safe Fixes

- Follow vendor upgrade path.
- Upgrade through supported intermediate Operator versions.
- Backup and validate CRs.
- Convert CRs to supported API versions.
- Avoid manual CRD deletion unless vendor support instructs it.
- In severe cases, engage Red Hat/vendor support before deleting CRDs.

## 21. Troubleshooting Disconnected / Air-Gapped Dependency Problems

### 21.1 Why Disconnected Clusters Fail Differently

In connected clusters, OLM can pull catalog and bundle images from external registries.

In disconnected clusters, all required content must be mirrored:

- Catalog index image
- Operator bundle images
- Operator related images
- Operand images
- Base images referenced by jobs or init containers

If the catalog says a bundle exists but the bundle image is not mirrored, dependency resolution might succeed but unpack/install fails.

### 21.2 Common Disconnected Symptoms

```text
CatalogSource unhealthy
ImagePullBackOff for catalog pod
Bundle unpack job failed
Back-off pulling image
no such host
x509: certificate signed by unknown authority
manifest unknown
unauthorized
```

### 21.3 Check CatalogSource Image

```bash
oc get catalogsource <catalog> -n openshift-marketplace -o yaml | grep image:
```

### 21.4 Check ImageContentSourcePolicy / IDMS / ITMS

Depending on OpenShift version and configuration:

```bash
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

### 21.5 Check Pull Secret

```bash
oc get secret/pull-secret -n openshift-config -o yaml
```

Do not print secrets in shared logs. Use controlled admin access.

### 21.6 Check Proxy and CA

```bash
oc get proxy/cluster -o yaml
oc get configmap -n openshift-config trusted-ca-bundle -o yaml
```

### 21.7 Bundle Unpack Failure Flow

```bash
oc get pods -n openshift-marketplace | grep -i bundle
oc describe pod <bundle-unpack-pod> -n openshift-marketplace
oc logs <bundle-unpack-pod> -n openshift-marketplace
```

If image pull fails:

1. Identify exact image pullspec.
2. Confirm it exists in mirror registry.
3. Confirm pull secret access.
4. Confirm cluster mirror rules rewrite the source registry to mirror.
5. Confirm custom CA trust.
6. Rebuild/mirror catalog correctly.

### 21.8 Disconnected Best Practice

Use a complete catalog mirroring process and test by installing the Operator in a non-production disconnected cluster first.

Validate:

```bash
oc get catalogsource -n openshift-marketplace
oc get packagemanifest -n openshift-marketplace | grep -i <operator>
oc apply -f test-subscription.yaml
oc get ip,csv -n <test-ns>
```

## 22. Troubleshooting Namespace-Scoped Resolver Problems

### 22.1 The Namespace Is the Dependency Boundary

OLM resolves all Subscriptions in a namespace together.

Example namespace:

```bash
oc get sub -n platform-operators
```

```text
NAME                 PACKAGE              CHANNEL
logging              cluster-logging      stable
service-mesh         servicemeshoperator  stable
kiali                kiali-ossm           stable
jaeger               jaeger-product       stable
```

If one Subscription has impossible constraints, others might also stop progressing.

### 22.2 Diagnose Whole Namespace

```bash
oc get sub -n <ns>
oc get csv -n <ns>
oc get ip -n <ns>
oc get og -n <ns>
```

Read all Subscription conditions:

```bash
oc get sub -n <ns> -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .status.conditions[*]}{"  "}{.type}{" "}{.reason}{" "}{.message}{"\n"}{end}{"\n"}{end}'
```

### 22.3 Fix One Bad Subscription First

Do not treat every failing Subscription as separate. Identify the root conflict.

Typical root conflicts:

- One orphan CSV.
- One unhealthy CatalogSource.
- One duplicate package Subscription.
- One provider dependency unavailable.
- One custom catalog with bad priority.

Fixing one object can unblock all Subscriptions in the namespace.

## 23. Advanced Catalog and Update Graph Analysis

### 23.1 Why Update Graph Matters

OLM follows catalog graph metadata, not simple numeric version comparison.

Important metadata:

- `replaces`
- `skips`
- `skipRange`
- channel head
- default channel

### 23.2 Broken Upgrade Path Symptoms

- Subscription sees no upgrade even though a newer bundle exists.
- InstallPlan generated for unexpected intermediate version.
- Channel switch does not progress.
- Resolver cannot find a unique replacement.
- Custom catalog has package but no usable channel head.

### 23.3 Inspect PackageManifest Channel Heads

```bash
oc get packagemanifest <pkg> -n openshift-marketplace -o json \
  | jq '.status.channels[] | {name: .name, currentCSV: .currentCSV}'
```

### 23.4 Inspect Catalog With `opm`

On an admin workstation with `opm`:

```bash
opm render <index-image> > catalog-render.yaml
```

Search package:

```bash
grep -n "package: <pkg>" catalog-render.yaml
```

Search bundle:

```bash
grep -n "name: <csv-or-bundle-name>" catalog-render.yaml
```

With `jq` if JSON output is used:

```bash
opm render <index-image> -o json \
  | jq 'select(.schema == "olm.bundle" and .package == "<pkg>") | {name, package, properties}'
```

### 23.5 Catalog Priority Troubleshooting

If two catalogs provide the same dependency:

```bash
oc get catalogsource -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,PRIORITY:.spec.priority,IMAGE:.spec.image
```

A higher priority custom catalog can accidentally override a newer Red Hat catalog.

### 23.6 Version Deadlock

Example:

```text
Operator A v1 provides API A and requires API B.
Operator B v1 provides API B and requires API A.
A v2 provides A2 and requires B2.
B v2 provides B2 and requires A2.
```

If only one upgrades, dependency breaks. OLM tries to update compatible sets together, but the catalog must contain valid metadata and paths.

### 23.7 Catalog Rebuild Requirements

When maintaining custom catalogs:

- Include all required dependency bundles.
- Include full upgrade graph or valid skip ranges.
- Keep packages from same vendor aligned.
- Rebuild catalog for target OpenShift/Kubernetes versions.
- Test install and upgrade, not only package discovery.
- Validate in disconnected mirror.

```bash
oc logs -n openshift-operator-lifecycle-manager deployment/olm-operator --tail=500 > olm-debug-$NS/olm-operator.log
```

### 24.4 Decision Tree

```text
Subscription has CatalogSourcesUnhealthy?
  -> Fix catalog first.

Subscription has ResolutionFailed?
  -> Decode constraints message.
  -> Check orphan CSV, duplicate package, missing provider, version conflict.

Subscription has InstallPlanPending?
  -> Check manual approval.

InstallPlan has Failed?
  -> Check failed resource/bundle unpack job.

CSV exists but not Succeeded?
  -> Check CSV requirements, OperatorGroup, deployment, APIService.

Operator deployment running but operand broken?
  -> Move to runtime Operator troubleshooting.
```

### 24.5 Safe Change Rules

Before deleting anything:

```bash
oc get sub,ip,csv,og -n $NS
oc get crd | grep -i <operator>
oc api-resources | grep -i <operator>
oc get <operator-cr-kind> -A
```

Backup custom resources:

```bash
oc get <operator-cr-kind> -A -o yaml > backup-<kind>.yaml
```

Avoid:

- Deleting CRDs first.
- Editing CSV dependency metadata.
- Deleting all InstallPlans blindly.
- Deleting Operator namespace with CR finalizers still present.
- Installing same package twice in same namespace.

## 26. Real-World Failure Scenarios

### Scenario 1: Logging Operator Upgrade Blocked by Unhealthy Catalog

#### Symptom

```text
Subscription cluster-logging has CatalogSourcesUnhealthy=True
```

#### Diagnosis

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource redhat-operators -n openshift-marketplace
oc get pods -n openshift-marketplace
```

Catalog pod is `ImagePullBackOff`.

#### Root Cause

Cluster cannot pull updated Red Hat index image due to disconnected mirror issue.

#### Fix

- Mirror correct catalog index image.
- Update ICSP/IDMS/ITMS if required.
- Verify pull secret and CA.
- Restart or patch CatalogSource.

### Scenario 2: New Subscription Fails After Old Subscription Deleted

#### Symptom

```text
clusterserviceversion my-operator.v1.0.0 exists and is not referenced by a subscription
```

#### Diagnosis

```bash
oc get sub -n my-ns
oc get csv -n my-ns
```

CSV exists but no Subscription owns it.

#### Fix

```bash
oc delete csv my-operator.v1.0.0 -n my-ns
```

Then recreate/allow Subscription to resolve.

### Scenario 3: Dependency Package Version Too New for Catalog

#### Symptom

```text
operator-a requires package provider >=2.0.0, but no candidates found
```

#### Diagnosis

```bash
oc get packagemanifest provider -n openshift-marketplace -o yaml
```

Catalog only has provider v1.8.

#### Fix

- Update catalog.
- Use correct OpenShift-compatible catalog tag.
- Select older channel of operator-a that supports provider v1.8.

### Scenario 4: Custom Catalog Overrides Red Hat Catalog

#### Symptom

A dependency resolves to an old bundle from custom catalog.

#### Diagnosis

```bash
oc get catalogsource -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,PRIORITY:.spec.priority,IMAGE:.spec.image
oc get packagemanifest <dependency> --selector=catalog=<custom-catalog> -n openshift-marketplace -o yaml
oc get packagemanifest <dependency> --selector=catalog=redhat-operators -n openshift-marketplace -o yaml
```

#### Root Cause

Custom catalog priority higher than Red Hat catalog.

#### Fix

- Lower custom catalog priority.
- Remove stale package from custom catalog.
- Use correct source in Subscription.

### Scenario 5: OperatorGroup AllNamespaces Unsupported

#### Symptom

CSV stuck with unsupported install mode.

#### Diagnosis

```bash
oc get og -n my-ns -o yaml
oc get csv <csv> -n my-ns -o json | jq '.spec.installModes'
```

OperatorGroup targets all namespaces, but CSV supports only `OwnNamespace`.

#### Fix

Use a namespace-scoped OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: my-og
  namespace: my-ns
spec:
  targetNamespaces:
  - my-ns
```

### Scenario 6: Bundle Unpack Job Fails in Disconnected Cluster

#### Symptom

```text
InstallPlanFailed
bundle unpacking failed
manifest unknown
```

#### Diagnosis

```bash
oc get pods -n openshift-marketplace | grep bundle
oc describe pod <bundle-pod> -n openshift-marketplace
```

#### Root Cause

Catalog was mirrored, but bundle image was not available in mirror registry.

#### Fix

Re-mirror catalog and related images completely.

### Scenario 7: CRD Upgrade Blocked by Existing Invalid CR

#### Symptom

InstallPlan fails while applying CRD update.

#### Diagnosis

```bash
oc describe ip <ip> -n <ns>
oc get crd <crd> -o yaml
oc get <custom-resource> -A -o yaml
```

Existing CR has fields invalid under new schema.

#### Fix

- Convert/fix existing CRs.
- Follow vendor migration guide.
- Re-run upgrade.

### Scenario 8: Single Bad Subscription Blocks Namespace

#### Symptom

Multiple Subscriptions in `openshift-operators` show failures.

#### Diagnosis

```bash
oc get sub -n openshift-operators
oc get sub -n openshift-operators -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .status.conditions[*]}{"  "}{.type}{" "}{.reason}{" "}{.message}{"\n"}{end}{"\n"}{end}'
```

One Subscription has orphan CSV conflict.

#### Fix

Fix the one root conflict; other Subscriptions then progress.

## 27. Best Practices

### 27.1 Installation Best Practices

- Use supported Red Hat or vendor channels.
- Keep Operator catalogs aligned with OpenShift version.
- Prefer default Red Hat catalogs unless custom catalog is required.
- Do not install same package twice in same namespace.
- Use separate namespaces for Operators with different scopes where supported.
- Use manual approval for critical production Operators.
- Review InstallPlan before approving major upgrades.

### 27.2 Catalog Best Practices

- Keep custom catalogs updated.
- Use catalog priority intentionally.
- Test custom catalogs before production.
- Include dependencies in mirrored catalogs.
- Do not remove old bundles required for upgrade graph unless skip/skipRange is correct.
- Use versioned catalog images, not `latest`, in production.

### 27.3 Subscription Best Practices

- Always specify correct `source` and `sourceNamespace`.
- Use a known channel, not assumed default.
- Use `Manual` approval for high-risk Operators.
- Track `currentCSV` and `installedCSV` during upgrades.
- Avoid deleting Subscription without understanding CSV/CRD cleanup.

### 27.4 OperatorGroup Best Practices

- One OperatorGroup per namespace.
- Match OperatorGroup target with supported install modes.
- Use `openshift-operators` for cluster-scoped/all-namespace Operators when appropriate.
- Use dedicated namespaces for namespaced Operators.
- Do not casually change OperatorGroup target after Operators are installed.

### 27.5 Troubleshooting Best Practices

- Read Subscription conditions first.
- Check CatalogSource health early.
- Check all Subscriptions in the namespace, not only one.
- Check orphan CSVs before changing channels.
- Check PackageManifest from the exact catalog.
- Check InstallPlan plan resources and bundle jobs.
- Do not delete CRDs first.
- Backup custom resources before uninstall/reinstall.
- Use must-gather for persistent/production incidents.

### 27.6 Disconnected Best Practices

- Mirror full catalog and related images.
- Test bundle unpacking.
- Validate mirror rules.
- Validate pull secret and CA trust.
- Keep catalog images aligned to OpenShift/Kubernetes version.
- Document registry dependencies for every Operator.

## 28. Interview and Exam-Oriented Questions

### Q1. What is `ResolutionFailed` in OLM?

`ResolutionFailed` means OLM cannot find a valid dependency solution for one or more Subscriptions in the namespace. Common causes include missing provider API, version conflicts, orphan CSVs, duplicate package Subscriptions, unhealthy catalogs, or wrong package/channel/source.

### Q2. Why can one failing Subscription block others in the same namespace?

OLM resolves all Subscriptions in a namespace as one set. If any Subscription introduces unsatisfiable constraints, the resolver might fail the whole namespace solution.

### Q3. What is an orphan CSV?

An orphan CSV is a ClusterServiceVersion left behind after its Subscription is deleted. It can block a new Subscription for the same package because OLM sees an existing CSV not referenced by a Subscription.

### Q4. How do you check which InstallPlan belongs to a Subscription?

```bash
oc get sub <sub> -n <ns> -o jsonpath='{.status.installPlanRef.name}{"\n"}'
```

### Q5. How do you approve a manual InstallPlan?

```bash
oc patch installplan <ip> -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

### Q6. What is the difference between `currentCSV` and `installedCSV`?

`currentCSV` is the newest CSV known by OLM for the Subscription. `installedCSV` is the CSV currently installed on the cluster. If they differ, an upgrade may be pending, stuck, or waiting for approval.

### Q7. What is `olm.gvk` dependency?

It declares that an Operator requires a Kubernetes API identified by group/version/kind. OLM must find an installed or installable provider for that GVK.

### Q8. What is `olm.package` dependency?

It declares dependency on an Operator package and version or version range.

### Q9. What should you check if Subscription has no InstallPlan?

Check Subscription status, CatalogSource health, package/channel existence, source/sourceNamespace, catalog operator logs, and resolver failure messages.

### Q10. Why should you not delete CRDs first while troubleshooting Operators?

CRDs are cluster-scoped and can contain production custom resources. Deleting CRDs deletes or endangers all CRs of that type and can break finalizers, dependent controllers, and data lifecycle.

### Q11. How does CatalogSource priority affect dependency resolution?

Higher-priority catalogs are preferred when multiple catalogs can satisfy a dependency. OLM also prefers options from the same catalog as the dependent Operator.

### Q12. How do you identify missing required APIs in a CSV?

```bash
oc describe csv <csv> -n <ns>
oc get csv <csv> -n <ns> -o json | jq '.status.requirementStatus'
```

### Q13. What causes bundle unpacking errors?

Common causes are missing bundle image, registry authentication issue, proxy or CA failure, invalid bundle metadata, or disconnected mirror incompleteness.

### Q14. What is the role of OperatorGroup in dependency troubleshooting?

OperatorGroup determines target namespaces and RBAC generation. If the CSV does not support the OperatorGroup’s install mode, the CSV can fail even when dependency resolution succeeds.

### Q15. How do you check if a package exists in a specific catalog?

```bash
oc get packagemanifest \
  --selector=catalog=<catalogsource> \
  --field-selector metadata.name=<package> \
  -n openshift-marketplace -o yaml
```

## Final Senior-Level Takeaway

Operator dependency troubleshooting is not guesswork. Treat OLM as a resolver-driven package manager for continuously running Kubernetes controllers.

Always move in this order:

```text
Subscription -> InstallPlan -> CSV -> OperatorGroup -> CatalogSource -> PackageManifest -> CRD/API -> Logs
```

The best administrators do not fix Operator dependency issues by deleting everything. They identify the unsatisfied constraint, understand which object introduced it, and make the smallest safe change that restores a valid dependency solution.
