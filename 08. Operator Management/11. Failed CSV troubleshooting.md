# Failed CSV Troubleshooting in Operator Management

**Audience:** Advanced OpenShift Administration / senior Linux-OpenShift administrators  
**Experience target:** 10+ years production operations mindset  
**Scope:** OLM Classic / CSV-based Operators in OpenShift 4.x  
**Main object:** `ClusterServiceVersion` / `csv`  

---

## 1. Executive Summary

A **Failed CSV** means Operator Lifecycle Manager, usually called **OLM**, could not complete the installation or upgrade of an Operator version represented by a `ClusterServiceVersion` object.

A CSV failure is rarely a single-object problem. In real production troubleshooting, the CSV is usually the visible failure point of a larger chain:

```text
CatalogSource
   ↓
Package / Channel / Bundle metadata
   ↓
Subscription
   ↓
InstallPlan
   ↓
ClusterServiceVersion
   ↓
CRDs / APIService / RBAC / ServiceAccount / Deployment / Webhooks
   ↓
Operator Pod
   ↓
Operand resources managed by the Operator
```

A senior admin does not start by deleting the CSV. A senior admin first answers these questions:

1. Did OLM resolve the correct package, channel, and version?
2. Did the `Subscription` create or reference the expected `InstallPlan`?
3. Did the `InstallPlan` install successfully?
4. Did OLM create the CSV and all resources declared by the CSV?
5. Did the Operator pod start and become available?
6. Is the failure caused by catalog, image, RBAC, OperatorGroup, CRD/APIService, webhook, proxy, network, SCC/security, or an Operator bug?

## 2. What Is a CSV?

A `ClusterServiceVersion`, abbreviated as **CSV**, is the OLM object that represents one installed version of an Operator.

Example:

```bash
oc get csv -n openshift-logging
```

Example output:

```text
NAME                                      DISPLAY                    VERSION   REPLACES                                  PHASE
cluster-logging.v6.2.1                   Red Hat OpenShift Logging  6.2.1     cluster-logging.v6.2.0                   Succeeded
loki-operator.v6.2.1                     Loki Operator              6.2.1     loki-operator.v6.2.0                     Succeeded
my-operator.v1.4.0                       My Operator                1.4.0     my-operator.v1.3.9                       Failed
```

The CSV contains important metadata and installation instructions, such as:

- Operator name, version, description, icons, labels, links.
- Owned and required CRDs.
- Required APIs.
- Install strategy.
- Deployments to create.
- Service accounts.
- RBAC permissions.
- Webhook definitions.
- Related images.
- Replacement chain information.

In practical terms:

```text
Subscription decides what version should be installed.
InstallPlan lists what OLM must create.
CSV describes how that Operator version must run.
OLM reconciles the CSV until the Operator is installed or fails.
```

## 3. CSV Phases You Must Understand

Check CSV phases:

```bash
oc get csv -n <operator-namespace>
```

Common CSV phases:

| Phase | Meaning | Admin action |
|---|---|---|
| `Pending` | CSV exists but required dependencies are not ready yet | Check required APIs, CRDs, OperatorGroup, Subscription, InstallPlan |
| `InstallReady` | OLM has enough information to install | Check whether install progresses |
| `Installing` | OLM is creating resources from the CSV | Watch events, InstallPlan, deployments |
| `Succeeded` | Operator version installed successfully | Confirm pods and operator-owned CRs |
| `Replacing` | CSV is being replaced by a newer CSV | Check upgrade path and old/new CSV relationship |
| `Failed` | OLM hit an unrecoverable install/upgrade condition | Read `status.reason`, `status.message`, events, OLM logs |
| `Deleting` | CSV deletion is in progress | Check finalizers and owned resources if stuck |

A CSV can fail quickly, or it can remain in another phase while the real problem appears in related resources. Never look at only the `PHASE` column.

## 4. Fast Triage Command Set

Set variables first:

```bash
NS=<operator-namespace>
CSV=<csv-name>
SUB=<subscription-name>
```

### 4.1 List the OLM objects in the namespace

```bash
oc get sub,csv,installplan,operatorgroup -n $NS
```

Short names:

```bash
oc get sub,csv,ip,og -n $NS
```

### 4.2 Inspect CSV status

```bash
oc get csv $CSV -n $NS -o yaml
```

Useful focused views:

```bash
oc get csv $CSV -n $NS -o jsonpath='{.status.phase}{"\n"}'
oc get csv $CSV -n $NS -o jsonpath='{.status.reason}{"\n"}'
oc get csv $CSV -n $NS -o jsonpath='{.status.message}{"\n"}'
```

With `jq`:

```bash
oc get csv $CSV -n $NS -o json | jq '.status'
```

### 4.3 Describe CSV and read events

```bash
oc describe csv $CSV -n $NS
```

Namespace events:

```bash
oc get events -n $NS --sort-by=.lastTimestamp
```

Filter warning events:

```bash
oc get events -n $NS --sort-by=.lastTimestamp | egrep -i 'warning|failed|error|forbidden|backoff|csv|installplan|subscription|resolution'
```

### 4.4 Inspect Subscription

```bash
oc get sub -n $NS
oc describe sub $SUB -n $NS
oc get sub $SUB -n $NS -o yaml
```

Focused status:

```bash
oc get sub $SUB -n $NS -o jsonpath='{.status.currentCSV}{"\n"}'
oc get sub $SUB -n $NS -o jsonpath='{.status.installedCSV}{"\n"}'
oc get sub $SUB -n $NS -o jsonpath='{.status.installPlanRef.name}{"\n"}'
oc get sub $SUB -n $NS -o json | jq '.status.conditions'
```

### 4.5 Inspect InstallPlan

```bash
IP=$(oc get sub $SUB -n $NS -o jsonpath='{.status.installPlanRef.name}')
oc get installplan $IP -n $NS -o yaml
oc describe installplan $IP -n $NS
```

List all install plans:

```bash
oc get installplan -n $NS
```

Check whether manual approval is blocking the install:

```bash
oc get installplan -n $NS -o custom-columns=NAME:.metadata.name,APPROVED:.spec.approved,PHASE:.status.phase
```

Approve manual install plan if required:

```bash
oc patch installplan $IP -n $NS --type merge -p '{"spec":{"approved":true}}'
```

### 4.6 Inspect OperatorGroup

```bash
oc get operatorgroup -n $NS
oc describe operatorgroup -n $NS
oc get operatorgroup -n $NS -o yaml
```

### 4.7 Inspect CatalogSource

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalogsource-name> -n openshift-marketplace
oc get pods -n openshift-marketplace
```

### 4.8 Inspect OLM control plane logs

OLM components run in `openshift-operator-lifecycle-manager`:

```bash
oc get pods -n openshift-operator-lifecycle-manager
```

Logs:

```bash
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator
oc logs -n openshift-operator-lifecycle-manager deploy/packageserver
```

Search recent errors:

```bash
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator --since=30m | egrep -i 'error|fail|csv|installplan|forbidden|operatorgroup'
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator --since=30m | egrep -i 'error|fail|resolution|catalog|bundle|installplan'
```

### 4.9 Inspect the Operator workload

Find resources created by the Operator CSV:

```bash
oc get deploy,rs,pod,sa,role,rolebinding,clusterrole,clusterrolebinding,svc -n $NS
```

Check pods:

```bash
oc get pods -n $NS
oc describe pod <operator-pod> -n $NS
oc logs <operator-pod> -n $NS
oc logs <operator-pod> -n $NS --previous
```

## 5. Senior Troubleshooting Rule: Diagnose from Outside to Inside

Use this order:

```text
1. Namespace and OperatorGroup
2. CatalogSource health
3. Subscription conditions
4. InstallPlan phase and approval
5. CSV status.reason and status.message
6. Events in operator namespace
7. OLM operator and catalog-operator logs
8. Resources created by CSV
9. Operator Deployment and Pod
10. Operator application logs
11. Operand custom resources
```

Why this order matters:

- If the catalog is broken, deleting the CSV will not help.
- If the subscription cannot resolve dependencies, recreating the Operator pod will not help.
- If the InstallPlan is pending manual approval, debugging the operator container is a waste of time.
- If the OperatorGroup is missing or wrong, the CSV may never install correctly.
- If RBAC is denied by a scoped OperatorGroup service account, the InstallPlan message usually tells you exactly which permission is missing.
- If the operator pod is CrashLooping, the CSV failure may only be a symptom of image, config, SCC, webhook, certificate, or API connectivity issues.

## 6. Common Failed CSV Reasons and How to Fix Them

## 6.1 `NoOperatorGroup`

### Symptom

CSV status shows:

```yaml
status:
  phase: Failed
  reason: NoOperatorGroup
```

### Meaning

The namespace where the Operator is being installed does not contain an `OperatorGroup`.

### Why it happens

- Operator installed manually with YAML but OperatorGroup was not created.
- Namespace was recreated without recreating the OperatorGroup.
- OperatorHub install partially failed.
- GitOps applied `Subscription` before `OperatorGroup`.

### Diagnosis

```bash
oc get operatorgroup -n $NS
oc get csv -n $NS
oc describe csv $CSV -n $NS
```

### Fix

For single-namespace install:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: <operatorgroup-name>
  namespace: <operator-namespace>
spec:
  targetNamespaces:
  - <operator-namespace>
```

Apply:

```bash
oc apply -f operatorgroup.yaml
```

Then watch:

```bash
oc get csv -n $NS -w
```

### Senior admin note

Do not create multiple OperatorGroups in one namespace unless you know exactly why. Multiple OperatorGroups in the same namespace commonly cause OLM confusion and CSV failure.

---

## 6.2 `UnsupportedOperatorGroup`

### Symptom

CSV status shows:

```yaml
status:
  phase: Failed
  reason: UnsupportedOperatorGroup
```

### Meaning

The Operator does not support the install mode defined by the OperatorGroup.

### Example

Operator supports only `OwnNamespace`, but the OperatorGroup targets all namespaces.

### Diagnosis

Check CSV-supported install modes:

```bash
oc get csv $CSV -n $NS -o json | jq '.spec.installModes'
```

Example output:

```json
[
  {"type":"OwnNamespace","supported":true},
  {"type":"SingleNamespace","supported":true},
  {"type":"MultiNamespace","supported":false},
  {"type":"AllNamespaces","supported":false}
]
```

Check OperatorGroup target:

```bash
oc get operatorgroup -n $NS -o yaml
```

### Fix

Match the OperatorGroup to a supported install mode.

Single namespace:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: my-operatorgroup
  namespace: my-operator-ns
spec:
  targetNamespaces:
  - my-operator-ns
```

Global install:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-operators
  namespace: openshift-operators
```

No `spec.targetNamespaces` means cluster-wide watch.

### Important

Changing an existing OperatorGroup can affect all Operators installed in that namespace. In production, always check:

```bash
oc get csv -n $NS
oc get sub -n $NS
oc get operatorgroup -n $NS -o yaml
```

## 6.3 Multiple OperatorGroups in One Namespace

### Symptom

CSV fails or never progresses. Events may mention ambiguous OperatorGroups or unsupported group selection.

### Diagnosis

```bash
oc get operatorgroup -n $NS
```

If more than one OperatorGroup exists in the same namespace, suspect this immediately.

### Fix

Keep one correct OperatorGroup per Operator installation namespace unless the platform design explicitly requires otherwise.

Example cleanup:

```bash
oc delete operatorgroup <wrong-og-name> -n $NS
```

Then re-check CSV:

```bash
oc get csv -n $NS -w
```

### Senior admin warning

Deleting the wrong OperatorGroup can break other Operators in the namespace. First map ownership:

```bash
oc get csv -n $NS
oc describe operatorgroup <og-name> -n $NS
```

## 6.4 `InterOperatorGroupOwnerConflict`

### Symptom

CSV status reason:

```text
InterOperatorGroupOwnerConflict
```

### Meaning

There is a conflict between OperatorGroups regarding provided APIs. In simple terms, OLM has detected that Operators or OperatorGroups would overlap in a way that can make API ownership unsafe.

### Common causes

- Two Operators provide the same API in overlapping target namespaces.
- Two versions of the same Operator are installed in conflicting scopes.
- One Operator is installed globally and another namespace-scoped installation tries to own the same APIs.
- A previous failed CSV remains and still owns/provides APIs.

### Diagnosis

```bash
oc get operatorgroup -A
oc get csv -A | grep -i <operator-or-api-name>
oc get csv -A -o custom-columns=NS:.metadata.namespace,CSV:.metadata.name,PHASE:.status.phase,VERSION:.spec.version
```

Check provided APIs:

```bash
oc get csv $CSV -n $NS -o json | jq '.metadata.annotations["olm.providedAPIs"], .spec.customresourcedefinitions.owned'
```

Check OperatorGroup annotations:

```bash
oc get operatorgroup -n $NS -o yaml | grep -i provided -A3 -B3
```

### Fix strategy

1. Identify which Operator should own the API.
2. Remove duplicate or stale CSVs only after confirming they are not active.
3. Avoid installing the same API-owning Operator globally and namespace-scoped at the same time.
4. Reinstall with a clean and correct OperatorGroup scope.

Example:

```bash
oc delete sub <old-subscription> -n <old-ns>
oc delete csv <old-csv> -n <old-ns>
```

### Senior admin warning

This is a high-risk cleanup area. Before deleting CSVs, capture:

```bash
oc get sub,csv,installplan,operatorgroup -A > olm-inventory.txt
oc get crd | grep -i <api-name> > crd-check.txt
```

## 6.5 `CannotModifyStaticOperatorGroupProvidedAPIs`

### Symptom

CSV fails with:

```text
CannotModifyStaticOperatorGroupProvidedAPIs
```

### Meaning

The OperatorGroup has static provided APIs and OLM cannot modify them as required by the CSV.

### Common causes

- OperatorGroup annotation `olm.providedAPIs` is pinned/static.
- Upgrade introduces new owned APIs but the OperatorGroup cannot be updated.
- Manual OperatorGroup modifications conflict with new CSV metadata.

### Diagnosis

```bash
oc get operatorgroup -n $NS -o yaml
oc get csv $CSV -n $NS -o yaml | less
```

Look for:

```yaml
metadata:
  annotations:
    olm.providedAPIs: ...
```

### Fix strategy

- Review whether the OperatorGroup was intentionally made static.
- Compare old and new CSV owned APIs.
- If safe, update or recreate the OperatorGroup according to supported install design.
- If the Operator is vendor-supported, check vendor upgrade notes before editing ownership annotations.

## 6.6 Immutable Deployment Field Error

### Symptom

CSV message may include text similar to:

```text
field is immutable
```

or:

```text
Deployment.apps "<operator-deployment>" is invalid: spec.selector: Invalid value: field is immutable
```

### Meaning

The new CSV install strategy is trying to patch a Kubernetes `Deployment` field that cannot be changed after creation.

### Common immutable fields

- `spec.selector`
- Some volume claim template fields in StatefulSets
- Certain labels tied to selectors

### Why it happens

- Operator author changed selector labels between versions.
- Manual edit changed the existing deployment.
- Old deployment exists from previous install and conflicts with new CSV.
- Upgrade path is broken in the bundle metadata.

### Diagnosis

```bash
oc get deploy -n $NS
oc describe deploy <operator-deployment> -n $NS
oc get deploy <operator-deployment> -n $NS -o yaml > current-deploy.yaml
oc get csv $CSV -n $NS -o yaml > failed-csv.yaml
```

Check CSV install strategy:

```bash
oc get csv $CSV -n $NS -o json | jq '.spec.install.spec.deployments'
```

### Fix options

#### Option A: Vendor-correct fix

Upgrade to a newer Operator version where the CSV uses a new deployment name or a corrected upgrade path.

#### Option B: Controlled recreation

If vendor docs allow it and the Operator is stateless:

```bash
oc delete deploy <operator-deployment> -n $NS
```

Then let OLM recreate it.

#### Option C: Clean reinstall

For lab or non-critical environments:

```bash
oc delete sub <subscription> -n $NS
oc delete csv <csv> -n $NS
```

Then reinstall.

### Senior admin warning

Do not delete an Operator deployment blindly for stateful Operators. The Operator deployment is usually stateless, but the operands may not be. Understand what the Operator controls before cleanup.

## 6.7 InstallPlan Failed: RBAC Forbidden

### Symptom

InstallPlan shows:

```text
is forbidden: User "system:serviceaccount:<ns>:<sa>" cannot create resource "clusterroles" at the cluster scope
```

CSV may fail because OLM could not create a required component.

### Meaning

The OperatorGroup is using a scoped service account, but that service account lacks permissions required by the Operator CSV.

### Common cause

A cluster admin intentionally restricted non-cluster-admin Operator installation by setting:

```yaml
spec:
  serviceAccountName: scoped
```

in the OperatorGroup.

### Diagnosis

```bash
oc get operatorgroup -n $NS -o yaml
oc get installplan -n $NS
oc describe installplan $IP -n $NS
```

Check the exact denied resource:

```bash
oc get installplan $IP -n $NS -o json | jq '.status.conditions'
```

### Fix

Grant only the missing permission to the scoped service account, or install the Operator with a properly privileged installation path.

Example permission test:

```bash
oc auth can-i create clusterroles --as=system:serviceaccount:$NS:<serviceaccount-name>
oc auth can-i create deployments -n $NS --as=system:serviceaccount:$NS:<serviceaccount-name>
```

### Senior admin approach

Do not immediately grant `cluster-admin`. Build the minimum RBAC required by the CSV, unless the vendor explicitly requires cluster-wide privileges.

## 6.8 Manual InstallPlan Approval Blocking CSV Progress

### Symptom

Subscription exists, InstallPlan exists, but CSV is not installed or remains pending.

InstallPlan shows:

```text
APPROVED=false
```

### Diagnosis

```bash
oc get installplan -n $NS
oc describe installplan <installplan-name> -n $NS
oc get sub $SUB -n $NS -o yaml | grep installPlanApproval -A2
```

### Fix

Approve the InstallPlan:

```bash
oc patch installplan <installplan-name> -n $NS --type merge -p '{"spec":{"approved":true}}'
```

Watch:

```bash
oc get installplan,csv -n $NS -w
```

### Senior admin note

Manual approval is often intentional in production. Before approving, check what resources will be installed:

```bash
oc get installplan <installplan-name> -n $NS -o json | jq '.status.plan[] | {name: .resource.name, kind: .resource.kind, group: .resource.group, version: .resource.version}'
```

## 6.9 Subscription `ResolutionFailed`

### Symptom

Subscription conditions show:

```text
Type: ResolutionFailed
Reason: ConstraintsNotSatisfiable
```

or events mention:

```text
constraints not satisfiable
```

### Meaning

The Catalog Operator cannot resolve a valid set of packages, versions, and dependencies.

### Common causes

- Wrong channel.
- Required dependency Operator is missing.
- Required API cannot be provided.
- Multiple catalog heads exist for the same channel.
- Old CSV exists but is not referenced by a subscription.
- Channel or package metadata is broken in a custom catalog.
- CatalogSource is stale or unhealthy.

### Diagnosis

```bash
oc describe sub $SUB -n $NS
oc get events -n $NS --sort-by=.lastTimestamp | grep -i ResolutionFailed
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator --since=30m | grep -i ResolutionFailed
```

Check package and channel:

```bash
oc get sub $SUB -n $NS -o jsonpath='{.spec.name}{"\n"}{.spec.channel}{"\n"}{.spec.source}{"\n"}{.spec.sourceNamespace}{"\n"}'
```

Check stale CSVs:

```bash
oc get csv -A | grep -i <package-name>
oc get sub -A | grep -i <package-name>
```

### Fix strategy

1. Correct package name, channel, source, and source namespace.
2. Ensure the catalog source is healthy.
3. Remove stale unreferenced CSV only after confirming no active subscription owns it.
4. Recreate subscription if it is stuck after bundle/image access is corrected.
5. If using a custom catalog, rebuild and publish a correct catalog graph.

### Example Subscription

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: my-operator
  namespace: my-operator-ns
spec:
  channel: stable
  installPlanApproval: Automatic
  name: my-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

## 6.10 CatalogSource Unhealthy

### Symptom

Subscription condition:

```text
CatalogSourcesUnhealthy
```

CatalogSource describe shows:

```text
Last Observed State: TRANSIENT_FAILURE
```

Catalog pod may show:

```text
ImagePullBackOff
CrashLoopBackOff
```

### Diagnosis

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalogsource> -n openshift-marketplace
oc get pods -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
```

Check image pull problems:

```bash
oc get pods -n openshift-marketplace | grep -i backoff
oc describe pod <catalog-pod> -n openshift-marketplace | egrep -i 'pull|image|denied|unauthorized|x509|timeout|dns|proxy'
```

### Common causes

- Index image unavailable.
- Pull secret missing.
- Proxy not configured correctly.
- Disconnected mirror missing catalog image.
- DNS cannot resolve registry.
- Registry certificate not trusted.
- Catalog image architecture mismatch.

### Fix examples

If disconnected, verify mirror and ImageContentSourcePolicy / ImageDigestMirrorSet / ImageTagMirrorSet configuration, depending on OpenShift version and environment policy.

Check registry access from a debug pod:

```bash
oc run tmp-curl -n openshift-marketplace --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk https://<registry>/v2/
```

Check cluster pull secret:

```bash
oc get secret/pull-secret -n openshift-config -o yaml
```

### Senior admin note

If catalog is unhealthy, CSV troubleshooting is secondary. Fix catalog resolution first.

## 6.11 Bundle Image Pull Failure

### Symptom

Subscription or marketplace job fails with messages like:

```text
ImagePullBackOff
Back-off pulling image "...operator-bundle@sha256:..."
rpc error: code = Unknown desc = error pinging docker registry
```

### Meaning

OLM resolved the Operator metadata, but the bundle image cannot be pulled.

### Diagnosis

```bash
oc get jobs -n openshift-marketplace
oc get pods -n openshift-marketplace
oc describe pod <bundle-unpack-pod> -n openshift-marketplace
oc logs <bundle-unpack-pod> -n openshift-marketplace
```

Look for:

```text
no such host
connection refused
timeout
x509: certificate signed by unknown authority
unauthorized
manifest unknown
```

### Fix

- Correct mirror registry content.
- Correct pull secret.
- Correct proxy or no-proxy.
- Add trusted CA bundle.
- Use a valid catalog/bundle digest.
- Refresh failing subscription after confirming image accessibility.

Controlled refresh pattern:

```bash
oc get sub,csv -n $NS
oc delete sub <subscription-name> -n $NS
oc delete csv <csv-name> -n $NS
# Recreate subscription after image access is fixed
oc apply -f subscription.yaml
```

## 6.12 Operator Pod CrashLoopBackOff After CSV Installation

### Symptom

CSV may be `Failed`, or CSV may remain non-succeeded because the operator Deployment is not available.

```bash
oc get pods -n $NS
```

Shows:

```text
<operator-pod>   0/1   CrashLoopBackOff
```

### Diagnosis

```bash
oc describe pod <operator-pod> -n $NS
oc logs <operator-pod> -n $NS
oc logs <operator-pod> -n $NS --previous
oc get deploy <operator-deployment> -n $NS -o yaml
```

Check environment and args from CSV:

```bash
oc get csv $CSV -n $NS -o json | jq '.spec.install.spec.deployments[].spec.template.spec.containers[] | {name, image, command, args, env}'
```

### Common causes

- Missing required secret or config map.
- Invalid proxy settings.
- Bad operand namespace configuration.
- Operator expects a CRD/API that is not available.
- Certificate or webhook error.
- Permission denied inside container.
- SCC/security context incompatibility.
- Image architecture mismatch.
- Operator bug.

### Fix strategy

1. Read the previous logs first.
2. Check missing config/secrets.
3. Check service account permissions.
4. Check API discovery errors.
5. Check certificates and webhooks.
6. Check SCC/security context.
7. Compare with vendor install docs.

## 6.13 ImagePullBackOff for Operator Deployment

### Symptom

Operator pod is not starting:

```text
ImagePullBackOff
ErrImagePull
```

### Diagnosis

```bash
oc describe pod <operator-pod> -n $NS
oc get csv $CSV -n $NS -o json | jq '.spec.install.spec.deployments[].spec.template.spec.containers[].image'
oc get secret -n $NS
oc get sa -n $NS
oc describe sa <operator-sa> -n $NS
```

### Common causes

- Operator image not mirrored.
- Pull secret missing in namespace/service account.
- Registry authentication failure.
- Registry TLS certificate not trusted.
- Wrong image tag or digest.

### Fix examples

Link pull secret to service account:

```bash
oc secrets link <operator-serviceaccount> <pull-secret> -n $NS --for=pull
```

Check pull secret:

```bash
oc get sa <operator-serviceaccount> -n $NS -o yaml
```

## 6.14 APIService or CRD Problems

### Symptom

CSV fails while creating or waiting for API resources.

Possible messages:

```text
waiting for install components to report healthy
could not find the requested resource
APIService not available
```

### Diagnosis

Check owned and required CRDs:

```bash
oc get csv $CSV -n $NS -o json | jq '.spec.customresourcedefinitions'
```

Check CRDs:

```bash
oc get crd | grep -i <operator-or-api-name>
oc describe crd <crd-name>
```

Check APIServices:

```bash
oc get apiservice | grep -i <operator-or-api-name>
oc describe apiservice <apiservice-name>
```

Check API discovery:

```bash
oc api-resources | grep -i <kind-or-group>
oc get --raw /apis | jq .
```

### Common causes

- CRD already exists but is owned by another CSV.
- CRD version conversion webhook is broken.
- APIService points to a service with no endpoints.
- APIService CA bundle invalid.
- Required API removed due to Kubernetes/OpenShift version upgrade.
- Operator bundle uses deprecated/removed APIs.

### Fix strategy

- Resolve CRD ownership conflict.
- Fix service endpoints for APIService.
- Fix webhook certificates.
- Use an Operator version compatible with the current OpenShift version.
- Avoid manually editing CRDs unless vendor support approves.

## 6.15 Webhook Problems

### Symptom

CSV fails or Operator installation blocks when webhook-related resources are created.

Common errors:

```text
failed calling webhook
x509: certificate signed by unknown authority
service not found
no endpoints available for service
connection refused
```

### Diagnosis

```bash
oc get validatingwebhookconfiguration,mutatingwebhookconfiguration | grep -i <operator>
oc describe validatingwebhookconfiguration <name>
oc describe mutatingwebhookconfiguration <name>
oc get svc,endpoints -n $NS
oc get pods -n $NS
```

### Fix strategy

- Confirm webhook service exists.
- Confirm endpoints exist.
- Confirm serving certificate is valid.
- Confirm CA bundle is injected or configured correctly.
- Restart operator pod only after root cause is fixed.

### Emergency admin note

Disabling or deleting webhook configurations may unblock the API server but can bypass validation or mutation. Treat that as emergency mitigation, not a permanent fix.

## 6.16 SCC / Security Context Failure

### Symptom

Operator pod fails admission or starts with permission problems.

Possible messages:

```text
would violate PodSecurity
unable to validate against any security context constraint
permission denied
runAsUser forbidden
```

### Diagnosis

```bash
oc describe pod <operator-pod> -n $NS
oc get sa -n $NS
oc adm policy who-can use scc anyuid
oc get csv $CSV -n $NS -o json | jq '.spec.install.spec.deployments[].spec.template.spec.securityContext'
```

### Fix strategy

- Prefer vendor-recommended SCC/RBAC settings.
- Avoid assigning privileged SCC unless required.
- For lab-only cases, anyuid might be used, but production should follow least privilege.

Example:

```bash
oc adm policy add-scc-to-user anyuid -z <operator-serviceaccount> -n $NS
```

Production note: document the reason and get security approval for SCC changes.

## 6.17 Proxy / Disconnected Cluster Failure

### Symptom

CSV fails because bundle, catalog, or operator images cannot be reached.

Possible messages:

```text
proxyconnect tcp
no such host
i/o timeout
x509: certificate signed by unknown authority
connection refused
```

### Diagnosis

Check cluster proxy:

```bash
oc get proxy cluster -o yaml
```

Check trusted CA:

```bash
oc get configmap -n openshift-config
oc get image.config.openshift.io/cluster -o yaml
```

Check subscription config overrides:

```bash
oc get sub $SUB -n $NS -o yaml
```

Debug DNS and registry:

```bash
oc run net-debug -n $NS --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk https://<registry>/v2/
getent hosts <registry>
```

### Fix strategy

- Correct cluster-wide proxy.
- Correct noProxy list for internal registries/services.
- Configure trusted registry CA.
- Ensure mirror registry has catalog, bundle, and related images.
- Confirm ImageDigestMirrorSet / ImageTagMirrorSet policy is correct for the environment.

## 6.18 Stale CSV Not Referenced by Subscription

### Symptom

Events may mention:

```text
clusterserviceversion <name> exists and is not referenced by a subscription
```

### Meaning

A CSV from an older install or failed upgrade remains in the namespace, but no active Subscription owns or references it. This can block dependency resolution.

### Diagnosis

```bash
oc get sub,csv -n $NS
oc get csv -n $NS -o custom-columns=NAME:.metadata.name,PHASE:.status.phase,VERSION:.spec.version
oc get sub -n $NS -o yaml | egrep 'currentCSV|installedCSV|startingCSV|name:|channel:'
```

Across cluster:

```bash
oc get csv -A | grep -i <operator-package>
oc get sub -A | grep -i <operator-package>
```

### Fix

If the CSV is truly stale and no Subscription references it:

```bash
oc delete csv <stale-csv> -n $NS
```

Then wait for resolution:

```bash
oc get sub,csv,installplan -n $NS -w
```

### Senior admin warning

Before deleting, confirm whether any operands depend on that Operator version.

## 7. CSV Troubleshooting Decision Tree

Use this as your production mental flow:

```text
CSV Failed?
│
├─ Check CSV status.reason/status.message
│  ├─ NoOperatorGroup → create correct OperatorGroup
│  ├─ UnsupportedOperatorGroup → align install mode and targetNamespaces
│  ├─ InterOperatorGroupOwnerConflict → resolve API ownership overlap
│  ├─ CannotModifyStaticOperatorGroupProvidedAPIs → review static provided APIs
│  └─ Other/empty → inspect events and OLM logs
│
├─ Check Subscription conditions
│  ├─ CatalogSourcesUnhealthy → fix CatalogSource/index image
│  ├─ InstallPlanPending → approve or verify manual workflow
│  ├─ InstallPlanFailed → inspect InstallPlan condition message
│  └─ ResolutionFailed → fix package/channel/dependency/stale CSV/catalog graph
│
├─ Check InstallPlan
│  ├─ approved=false → approve if expected
│  ├─ phase=Failed + forbidden → fix OperatorGroup service account RBAC
│  ├─ phase=Failed + image/bundle error → fix bundle image access
│  └─ phase=Complete but CSV failed → inspect CSV resources and operator pod
│
├─ Check CatalogSource
│  ├─ TRANSIENT_FAILURE → inspect catalog pod/network/image
│  ├─ ImagePullBackOff → fix registry/pull secret/mirror/CA
│  └─ healthy → continue
│
├─ Check Operator Deployment/Pod
│  ├─ ImagePullBackOff → fix operator image pull
│  ├─ CrashLoopBackOff → inspect logs and config
│  ├─ Pending → node scheduling/resource/security issue
│  └─ Running but not ready → readiness probe, webhook, API, config
│
└─ Check CRDs/APIService/Webhooks
   ├─ CRD conflict → resolve ownership/version conflict
   ├─ APIService unavailable → fix backing service/endpoints/CA
   ├─ webhook broken → fix service/cert/endpoints
   └─ deprecated API → use compatible Operator version
```


### 9.6 CSV required CRDs

```bash

```

```bash
oc get csv $CSV -n $NS -o json | jq -r '.spec.install.spec.deployments[].spec.template.spec.containers[] | "\(.name) \(.image)"'
```

```bash

```

### 9.10 Find stale CSVs without obvious matching subscription

```bash
for ns in $(oc get ns -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  csvs=$(oc get csv -n $ns --no-headers 2>/dev/null | awk '{print $1}')
  subs=$(oc get sub -n $ns -o json 2>/dev/null | jq -r '.items[]? | [.status.currentCSV,.status.installedCSV,.spec.startingCSV] | .[]?' | sort -u)
  for csv in $csvs; do
    echo "$subs" | grep -qx "$csv" || echo "Possible stale CSV: $ns/$csv"
  done
done
```

## Scenario 1: Operator Installation Fails Immediately

### Situation

You install an Operator in namespace `tools-operators`. CSV becomes `Failed`.

### Check

```bash
oc get csv -n tools-operators
oc get csv <csv> -n tools-operators -o jsonpath='{.status.reason}{"\n"}{.status.message}{"\n"}'
```

Output:

```text
NoOperatorGroup
csv created in namespace with no operatorgroup
```

### Fix

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: tools-operators
  namespace: tools-operators
spec:
  targetNamespaces:
  - tools-operators
```

Apply:

```bash
oc apply -f og.yaml
oc get csv -n tools-operators -w
```

### Root cause

GitOps applied Subscription but not OperatorGroup.

### Prevention

In Argo CD or GitOps, sync OperatorGroup before Subscription.

## Scenario 2: InstallPlan Failed with Forbidden Error

### Situation

Tenant admin installs Operator using a scoped OperatorGroup. InstallPlan fails.

### Check

```bash
oc describe installplan <ip> -n scoped
```

Error:

```text
clusterroles.rbac.authorization.k8s.io is forbidden:
User "system:serviceaccount:scoped:scoped" cannot create resource "clusterroles" at the cluster scope
```

### Root cause

Operator requires cluster-scoped RBAC, but scoped service account does not have permission.

### Fix options

Option 1: Grant required permission if approved.

```bash
oc create clusterrole scoped-operator-extra --verb=create,get,list,watch,update,patch --resource=clusterroles.rbac.authorization.k8s.io
oc adm policy add-cluster-role-to-user scoped-operator-extra -z scoped -n scoped
```

Option 2: Install the Operator using a cluster-admin-approved namespace and OperatorGroup.

### Prevention

Audit CSV permissions before allowing tenant installation:

```bash
oc get packagemanifest <package> -n openshift-marketplace -o yaml
```

## Scenario 3: Subscription ResolutionFailed After Upgrade

### Situation

Operator was upgraded but now Subscription has `ResolutionFailed`.

### Check

```bash
oc describe sub <sub> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp | grep -i ResolutionFailed
```

Possible message:

```text
constraints not satisfiable ... clusterserviceversion <old-csv> exists and is not referenced by a subscription
```

### Root cause

Stale CSV from previous install blocks dependency resolution.

### Fix

Confirm ownership:

```bash
oc get sub,csv -n <ns>
oc get sub <sub> -n <ns> -o yaml | egrep 'currentCSV|installedCSV|startingCSV'
```

Delete stale CSV only if safe:

```bash
oc delete csv <old-unreferenced-csv> -n <ns>
```

Watch recovery:

```bash

```

## Scenario 4: CatalogSource TRANSIENT_FAILURE

## Scenario 5: CSV Failed Due to Immutable Deployment Selector

### Situation

Upgrade from Operator `v1.2.0` to `v1.3.0` fails.

CSV message:

```text
Deployment.apps "my-operator-controller-manager" is invalid: spec.selector: Invalid value: field is immutable
```

### Root cause

New CSV changed the Deployment selector. Kubernetes does not allow selector mutation.

### Fix

Best fix: install vendor-corrected version.

If vendor approves deployment recreation:

```bash

oc get csv -n <ns> -w
```

If lab environment:

```bash
oc delete sub <sub> -n <ns>
oc delete csv <failed-csv> -n <ns>
oc apply -f subscription.yaml
```

## 11. Do Not Do These Things Blindly

Avoid these actions unless you understand the impact:

```bash
oc delete csv <csv>
oc delete crd <crd>
oc delete operatorgroup <og>
oc delete deployment <operator-deployment>
oc delete validatingwebhookconfiguration <webhook>
oc delete apiservice <apiservice>
oc adm policy add-cluster-role-to-user cluster-admin -z <sa> -n <ns>
```

Why:

- Deleting CSV can uninstall or orphan Operator-managed resources.
- Deleting CRD can delete custom resources or break operands.
- Deleting OperatorGroup can break all Operators in that namespace.
- Deleting webhooks can bypass admission controls.
- Granting cluster-admin hides the real RBAC issue and creates security risk.

## 12. Safe Remediation Patterns

## 12.1 Restart OLM components

Usually not required. Use only if OLM controller appears stuck and no object-level issue exists.

```bash
oc rollout restart deploy/olm-operator -n openshift-operator-lifecycle-manager
oc rollout restart deploy/catalog-operator -n openshift-operator-lifecycle-manager
```

Watch:

```bash
oc get pods -n openshift-operator-lifecycle-manager -w
```

## 12.2 Refresh failing subscription

Use when bundle/image access was broken and is now fixed.

```bash
oc get sub,csv -n $NS
oc delete sub <subscription-name> -n $NS
oc delete csv <csv-name> -n $NS
oc apply -f subscription.yaml
```

## 12.3 Move from wrong channel to correct channel

```bash
oc patch sub <subscription-name> -n $NS --type merge -p '{"spec":{"channel":"stable"}}'
```

Then monitor:

```bash
oc describe sub <subscription-name> -n $NS
oc get installplan,csv -n $NS -w
```

## 12.4 Change approval strategy

Automatic to Manual:

```bash
oc patch sub <subscription-name> -n $NS --type merge -p '{"spec":{"installPlanApproval":"Manual"}}'
```

Manual to Automatic:

```bash
oc patch sub <subscription-name> -n $NS --type merge -p '{"spec":{"installPlanApproval":"Automatic"}}'
```

## 12.5 Reinstall Operator cleanly

Use this mostly for labs, failed initial installs, or vendor-approved cleanup.

```bash
oc get sub,csv,installplan,operatorgroup -n $NS
oc delete sub <subscription-name> -n $NS
oc delete csv <csv-name> -n $NS
oc delete installplan <installplan-name> -n $NS
```

Do not delete CRDs unless vendor docs explicitly tell you to and you have backed up custom resources.

## 13. How to Read CSV YAML Like a Senior Admin

Example:

```bash
oc get csv $CSV -n $NS -o yaml
```

Important sections:

```yaml
metadata:
  name: my-operator.v1.2.3
  namespace: my-operator-ns
  annotations:
    alm-examples: ...
    capabilities: ...
    categories: ...
    certified: "true"
    olm.skipRange: ...

spec:
  version: 1.2.3
  replaces: my-operator.v1.2.2
  installModes:
  - type: OwnNamespace
    supported: true
  - type: SingleNamespace
    supported: true
  - type: MultiNamespace
    supported: false
  - type: AllNamespaces
    supported: true
  customresourcedefinitions:
    owned: []
    required: []
  install:
    strategy: deployment
    spec:
      deployments: []
      permissions: []
      clusterPermissions: []

status:
  phase: Failed
  reason: UnsupportedOperatorGroup
  message: ...
```

### What to look for

| CSV field | Why it matters |
|---|---|
| `spec.version` | Confirms actual Operator version |
| `spec.replaces` | Shows upgrade chain |
| `metadata.annotations.olm.skipRange` | Shows upgrade skip range if used |
| `spec.installModes` | Must match OperatorGroup scope |
| `spec.customresourcedefinitions.owned` | APIs this Operator owns |
| `spec.customresourcedefinitions.required` | APIs that must exist before install |
| `spec.install.spec.permissions` | Namespace-scoped RBAC required |
| `spec.install.spec.clusterPermissions` | Cluster-scoped RBAC required |
| `spec.install.spec.deployments` | Operator deployments/images/env/security context |
| `status.phase` | Current lifecycle phase |
| `status.reason` | Primary failure category |
| `status.message` | Human-readable failure detail |
| `status.conditions` | Timeline and condition-specific info |
| `status.requirementStatus` | Dependency status and missing requirements |

## 14. Relationship Between CSV and OperatorGroup

An OperatorGroup defines the namespaces that Operators in the same namespace should watch.

### Single namespace OperatorGroup

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: app-operatorgroup
  namespace: app-operators
spec:
  targetNamespaces:
  - app-operators
```

### Operator in one namespace watching another namespace

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: team1-operatorgroup
  namespace: team1-operator
spec:
  targetNamespaces:
  - team1
```

### Global OperatorGroup

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-operatorgroup
  namespace: openshift-operators
```

### Key troubleshooting point

CSV install modes and OperatorGroup target scope must be compatible.

Example mismatch:

```text
CSV supports OwnNamespace only.
OperatorGroup targets all namespaces.
Result: UnsupportedOperatorGroup.
```

## 15. Relationship Between CSV and Subscription

A Subscription tracks a package and channel.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: file-integrity-operator
  namespace: openshift-file-integrity
spec:
  channel: stable
  installPlanApproval: Automatic
  name: file-integrity-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

Important Subscription fields:

| Field | Meaning |
|---|---|
| `spec.name` | Operator package name |
| `spec.channel` | Update channel |
| `spec.source` | CatalogSource name |
| `spec.sourceNamespace` | CatalogSource namespace |
| `spec.installPlanApproval` | Automatic or Manual approval |
| `spec.startingCSV` | Optional starting version |
| `status.currentCSV` | CSV selected by resolver |
| `status.installedCSV` | CSV currently installed |
| `status.installPlanRef` | InstallPlan created for this subscription |
| `status.conditions` | Health and resolution status |

If Subscription is wrong, CSV may fail or never appear.

## 16. Relationship Between CSV and InstallPlan

An InstallPlan is the calculated list of resources OLM will create to install or upgrade a CSV.

Check:

| Field | Meaning |

## 19. Exam and Lab Tips

For Red Hat style exams and practical labs:

1. Always check the namespace first.
2. Confirm there is exactly one correct OperatorGroup in the install namespace.
3. Confirm Subscription fields: `name`, `channel`, `source`, `sourceNamespace`, `installPlanApproval`.
4. If approval is Manual, approve the InstallPlan.
5. Use `oc describe sub`, `oc describe installplan`, and `oc describe csv`.
6. If CSV is Failed, read `status.reason` and `status.message`; do not guess.
7. For operator pod issues, check `oc describe pod` before logs because image pull, SCC, scheduling, and probe failures appear in events.
8. For disconnected clusters, check catalog and bundle image pull before debugging CSV internals.
9. Remember that OpenShift default cluster Operators are managed by CVO, not by OLM Subscriptions. Application Operators installed from OperatorHub are managed by OLM.
10. Do not delete CRDs in an exam unless explicitly required.

## 21. Root Cause Matrix

| Symptom | Likely root cause | First command | Fix direction |
|---|---|---|---|
| CSV `Failed`, reason `NoOperatorGroup` | Missing OperatorGroup | `oc get og -n $NS` | Create correct OperatorGroup |
| CSV `Failed`, reason `UnsupportedOperatorGroup` | Install mode mismatch | `oc get csv $CSV -o json | jq '.spec.installModes'` | Fix OperatorGroup scope |
| CSV `Failed`, reason `InterOperatorGroupOwnerConflict` | API ownership conflict | `oc get csv -A` | Remove conflicting install/stale CSV |
| InstallPlan `approved=false` | Manual approval pending | `oc get ip -n $NS` | Approve InstallPlan |
| Subscription `ResolutionFailed` | Dependency/channel/catalog issue | `oc describe sub $SUB -n $NS` | Fix package/channel/dependencies/stale CSV |
| Subscription `CatalogSourcesUnhealthy` | Bad catalog | `oc describe catsrc -n openshift-marketplace` | Fix catalog pod/image/registry |
| Catalog pod `ImagePullBackOff` | Index image pull failure | `oc describe pod -n openshift-marketplace` | Fix pull secret/mirror/CA/proxy |
| Bundle unpack pod fails | Bundle image unreachable | `oc get pods -n openshift-marketplace` | Fix bundle image access |
| Operator pod `ImagePullBackOff` | Operator image pull failure | `oc describe pod <pod> -n $NS` | Fix image/pull secret/mirror |
| Operator pod `CrashLoopBackOff` | Runtime config/API/RBAC bug | `oc logs <pod> --previous -n $NS` | Fix config/RBAC/API/vendor issue |
| InstallPlan forbidden | Scoped OperatorGroup SA lacks RBAC | `oc describe ip $IP -n $NS` | Grant minimum RBAC or use proper install path |
| APIService unavailable | Webhook/API backend broken | `oc describe apiservice <name>` | Fix service/endpoints/cert |
| Webhook x509 error | CA/cert mismatch | `oc describe validatingwebhookconfiguration` | Fix cert/CA injection |
| Immutable deployment field | Bad upgrade/deployment selector change | `oc describe csv $CSV -n $NS` | Vendor fix or controlled recreate |

## 22. Production Best Practices

1. Use dedicated namespaces for Operators when appropriate.
2. Keep one OperatorGroup per Operator namespace unless the design is intentional.
3. Use Manual approval for critical Operators in production.
4. Review InstallPlan before approving upgrades.
5. Monitor CSV phases and Subscription conditions.
6. Keep catalogs healthy and mirrored in disconnected clusters.
7. Avoid manually editing CSVs. They are reconciled by OLM.
8. Avoid deleting CRDs during Operator cleanup unless you want to remove all custom resources and vendor docs approve it.
9. Keep GitOps order correct: Namespace → OperatorGroup → Subscription → Custom Resources.
10. Capture OLM object YAML before remediation.
11. Use least privilege for scoped Operator installation.
12. Validate Operator compatibility with OpenShift version before upgrade.
13. Do not mix global and namespace-scoped installs of the same API-owning Operator without vendor support.
14. Maintain a rollback plan for Operator upgrades.
15. For disconnected clusters, mirror catalog, bundle, operator, and operand images—not only the catalog index image.

Correct order:

```text
1. Namespace
2. OperatorGroup
3. Subscription
4. Manual InstallPlan approval, if required
5. Operator custom resources
6. Operand validation
```

## 24. Monitoring Failed CSVs

### Prometheus-style operational idea

OLM exposes metrics for OLM-managed resources in OpenShift monitoring. In production, you should alert on abnormal CSVs and failed install plans.

Useful operational checks:

```bash
oc get csv -A | grep -v Succeeded
oc get installplan -A | grep -i failed
oc get sub -A -o json | jq '.items[] | {namespace: .metadata.namespace, name: .metadata.name, conditions: .status.conditions}'
```

### Simple cron-style check

```bash
oc get csv -A --no-headers | awk '$NF != "Succeeded" {print strftime(), $0}'
```

## 25. When to Escalate to Vendor Support

Escalate when:

- CSV fails due to immutable deployment fields introduced by vendor bundle.
- Operator upgrade graph is broken.
- Required APIs are missing despite correct catalog and dependencies.
- Operator pod crash loop is caused by vendor code.
- Webhook certificates are generated incorrectly by the Operator.
- CRD conversion webhook blocks API server operations.
- Deleting/recreating CSV may affect production operands.
- Disconnected catalog metadata appears inconsistent.

Include:

```bash
oc adm must-gather
oc get sub,csv,installplan,operatorgroup -n $NS -o yaml
oc get events -n $NS --sort-by=.lastTimestamp
oc logs -n openshift-operator-lifecycle-manager deploy/olm-operator --since=4h
oc logs -n openshift-operator-lifecycle-manager deploy/catalog-operator --since=4h
oc get pods,deploy,svc,endpoints -n $NS -o yaml
```

## 26. Interview-Grade Explanation

If asked in an interview, explain it like this:

> A Failed CSV means OLM could not complete installation or upgrade of an Operator version. I do not troubleshoot it by deleting the CSV first. I start from the OLM dependency chain: CatalogSource, Subscription, InstallPlan, OperatorGroup, then CSV status, events, and OLM logs. The most important fields are `status.phase`, `status.reason`, `status.message`, Subscription conditions, and InstallPlan conditions. Common causes are missing or wrong OperatorGroup, unsupported install mode, dependency resolution failure, unhealthy CatalogSource, pending manual InstallPlan, RBAC denial with scoped OperatorGroup service account, image pull or disconnected registry issues, stale CSV conflicts, CRD/APIService conflicts, webhook/certificate problems, and operator pod crashes. The fix depends on the exact reason: create or correct OperatorGroup, approve InstallPlan, fix catalog or image mirror, grant minimum RBAC, remove stale CSV safely, or use a vendor-corrected Operator version.

## 28. Final Senior Admin Mindset

When a CSV fails, think like a package manager, Kubernetes admin, and platform SRE at the same time.

OLM is not just deploying a pod. It is resolving dependencies, creating RBAC, installing CRDs, reconciling API ownership, managing upgrade graphs, and deploying a controller that may itself manage more workloads.

The winning troubleshooting method is:

```text
Read status.
Read events.
Read InstallPlan.
Read Subscription.
Read OperatorGroup.
Read CatalogSource.
Read OLM logs.
Read operator pod logs.
Fix the first broken dependency.
Avoid destructive cleanup until ownership is clear.
```

That is the difference between basic `oc get pods` troubleshooting and advanced OpenShift Operator administration.
