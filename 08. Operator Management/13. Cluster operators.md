# Cluster Operators in OpenShift Operator Management

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, L3 support engineers, and Red Hat exam/interview preparation candidates with around 10 years of Linux/DevOps/OpenShift experience.

**Scope:** This guide explains **Cluster Operators** in OpenShift Container Platform 4.x in deep operational detail. It focuses on architecture, health states, commands, upgrade behavior, troubleshooting, real-world failure patterns, and senior-level operational practices.

---

## 1. What are Cluster Operators?

In OpenShift, **Cluster Operators** are platform-level operators responsible for managing core OpenShift components such as authentication, networking, ingress, DNS, image registry, monitoring, machine configuration, console, etcd, Kubernetes API server, and other control-plane services.

A **ClusterOperator** object is not the same thing as a user-installed Operator from OperatorHub. It is a cluster-scoped status object under the API group:

```yaml
apiVersion: config.openshift.io/v1
kind: ClusterOperator
```

The `ClusterOperator` resource reports the health and version state of a core or optional OpenShift component managed by the **Cluster Version Operator** (CVO). Operators use this object to publish their state to the rest of the cluster.

In daily administration, when you run:

```bash
oc get clusteroperators
oc get co
```

you are looking at the health summary of platform operators, not application operators.

---

## 2. Why Cluster Operators matter for advanced administration

A senior OpenShift administrator must understand Cluster Operators because they are the quickest way to answer these operational questions:

- Is the cluster healthy?
- Is an upgrade blocked?
- Which platform component is failing?
- Is the issue in networking, authentication, ingress, storage, monitoring, image registry, etcd, or machine configuration?
- Is a degraded operator causing real workload impact, or is it only a warning state?
- Which namespace, deployment, daemon set, CR, config object, or operand should be inspected next?
- Is the cluster stuck in `Progressing=True` because of a real rollout, node issue, missing image, DNS problem, certificate issue, or operator reconciliation problem?

For advanced OpenShift administration, `oc get co` is often the first command after login.

---

## 3. Cluster Operators vs OLM Operators

OpenShift uses the word **Operator** in multiple contexts. This is important because many admins confuse **Cluster Operators** with **OLM-installed Operators**.

| Area | Cluster Operators | OLM / OperatorHub Operators |
|---|---|---|
| Purpose | Manage OpenShift platform components | Manage add-on applications or platform extensions |
| Lifecycle owner | Cluster Version Operator | Operator Lifecycle Manager / OLM v1 / Subscription / ClusterExtension depending on version and installation method |
| Status object | `ClusterOperator` under `config.openshift.io/v1` | `ClusterServiceVersion`, `Subscription`, `InstallPlan`, `OperatorCondition`, `ClusterExtension`, etc. |
| Example | `authentication`, `network`, `ingress`, `kube-apiserver`, `machine-config` | OpenShift GitOps, Service Mesh, Compliance Operator, File Integrity Operator, Local Storage Operator |
| Upgrade path | Tied to OpenShift release payload | Tied to catalog/channel/subscription or extension lifecycle |
| Command | `oc get co` | `oc get csv`, `oc get sub`, `oc get ip`, `oc get clusterextension` |
| Admin action | Troubleshoot platform health and upgrades | Install/upgrade/remove add-on operators |

**Key point:**

`oc get co` does not show every installed Operator. It shows platform operators that report cluster health to the CVO.

## 4. Main architecture

At a high level:

```text
OpenShift release payload
        |
        v
Cluster Version Operator (CVO)
        |
        | applies manifests and watches status
        v
Cluster Operators
        |
        | reconcile platform components
        v
Operands / managed components
        |
        | publish state
        v
ClusterOperator status
```

The **Cluster Version Operator** is the top-level orchestrator for platform lifecycle. During normal operation, it compares the desired state from the release payload with in-cluster resources and reconciles differences. During upgrades, it applies manifests in ordered stages called **Runlevels**.

Cluster Operators then manage their own domain. For example:

- `authentication` manages OAuth and authentication-related components.
- `network` manages cluster networking components.
- `ingress` manages ingress controllers and router components.
- `dns` manages cluster DNS.
- `machine-config` manages node OS configuration, kubelet config, CRI-O config, systemd units, kernel arguments, and RHCOS node updates.
- `kube-apiserver` manages Kubernetes API server static pod rollout.
- `etcd` manages etcd member health, certs, backups-related status, and quorum-sensitive behavior.
- `image-registry` manages the internal OpenShift image registry.

Each Cluster Operator publishes status through a `ClusterOperator` resource.

## 6. The `ClusterOperator` object structure

A `ClusterOperator` object mainly contains `metadata`, `spec`, and `status`.

Example command:

```bash
oc get clusteroperator authentication -o yaml
```

Simplified structure:

```yaml
apiVersion: config.openshift.io/v1
kind: ClusterOperator
metadata:
  name: authentication
spec: {}
status:
  conditions:
  - type: Available
    status: "True"
    reason: AsExpected
    message: OAuth server is available
    lastTransitionTime: "2026-07-03T10:15:00Z"
  - type: Progressing
    status: "False"
    reason: AsExpected
    message: OAuth server is not progressing
  - type: Degraded
    status: "False"
    reason: AsExpected
    message: OAuth server is not degraded
  - type: Upgradeable
    status: "True"
    reason: AsExpected
    message: Cluster is upgradeable
  relatedObjects:
  - group: operator.openshift.io
    resource: authentications
    name: cluster
  - group: ""
    resource: namespaces
    name: openshift-authentication
  versions:
  - name: operator
    version: 4.x.y
```

The most important fields for troubleshooting are:

| Field | Meaning |
|---|---|
| `.status.conditions` | Health and lifecycle condition list |
| `.status.conditions[].type` | Condition name such as `Available`, `Progressing`, `Degraded`, `Upgradeable` |
| `.status.conditions[].status` | `True`, `False`, or `Unknown` |
| `.status.conditions[].reason` | Short machine-readable reason |
| `.status.conditions[].message` | Human-readable troubleshooting message |
| `.status.conditions[].lastTransitionTime` | When the condition last changed |
| `.status.relatedObjects` | Related resources to inspect next |
| `.status.versions` | Operator and operand versions currently reported as available |

## 7. Understanding ClusterOperator conditions

### 7.1 `Available`

`Available=True` means the operator and its managed component are functional enough to serve their intended purpose.

Healthy example:

```text
AVAILABLE=True
```

Problem example:

```text
AVAILABLE=False
```

`Available=False` is serious. It usually means at least one required operand is not functional and admin intervention is needed.

Common causes:

- Pods are crash looping.
- Deployments are unavailable.
- Static pods failed to roll out.
- API connectivity is broken.
- Required secrets or config maps are missing.
- Certificates are expired or invalid.
- Required nodes are not ready.
- Storage is missing or broken.
- Cloud provider API integration failed.

### 7.2 `Progressing`

`Progressing=True` means the operator is actively moving from one steady state to another.

This can be normal during:

- Cluster upgrade
- Config change
- Deployment rollout
- Static pod revision rollout
- MachineConfig rollout
- Node reboot cycle
- Image pull or payload change

But `Progressing=True` for a long time may indicate a stuck rollout.

Example:

```bash
oc get co machine-config
```

```text
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED
machine-config   4.x.y     True        True          False
```

This may be normal if nodes are rebooting. It is abnormal if it remains stuck because one node cannot drain, reboot, or apply the rendered MachineConfig.

### 7.3 `Degraded`

`Degraded=True` means the operator has observed a persistent mismatch between current state and required state.

Important senior-admin interpretation:

- `Degraded=True` does **not always mean user applications are down**.
- If `Available=True` and `Degraded=True`, the component is still available but needs investigation.
- If `Available=False` and `Degraded=True`, the component is failing and likely has user or platform impact.
- Operators should not normally report `Degraded=True` during ordinary upgrade transitions; persistent infrastructure problems often cause degraded states.

Examples:

```text
authentication   True   False   True
```

This means authentication is available but degraded. Users might still log in, but something requires attention.

```text
ingress          False  True    True
```

This is more serious. Routes may be unavailable or router pods may not be serving traffic.

### 7.4 `Upgradeable`

`Upgradeable=True` means the operator reports that its current state is safe for cluster updates.

`Upgradeable=False` is especially important before minor version upgrades.

Examples:

```bash
oc get co -o custom-columns=NAME:.metadata.name,UPGRADEABLE:.status.conditions[?\(@.type=="Upgradeable"\)].status,MESSAGE:.status.conditions[?\(@.type=="Upgradeable"\)].message
```

If an operator reports `Upgradeable=False`, read the message carefully. It usually tells you what must be fixed before upgrade.

Common causes:

- Unsupported configuration
- Deprecated API usage
- Removed cluster capability conflicts
- Storage backend not configured correctly
- Cloud credential mode issues
- Operator-specific precondition failures
- Incomplete previous upgrade

```text

```

## 9. Useful commands for Cluster Operators

### 9.1 List all Cluster Operators

```bash
oc get clusteroperators
oc get co
```

### 9.2 Describe one operator

```bash
oc describe co authentication
oc describe co ingress
oc describe co network
oc describe co machine-config
```

### 9.3 Get YAML

```bash
oc get co authentication -o yaml
```

### 9.4 Get only conditions

```bash
oc get co authentication -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

### 9.5 Show degraded operators only

```bash
oc get co | awk 'NR==1 || $5=="True"'
```

Better JSON-based approach:

```bash
oc get co -o json | jq -r '
  .items[] |
  .metadata.name as $name |
  (.status.conditions[] | select(.type=="Degraded" and .status=="True")) |
  "\($name): \(.reason) - \(.message)"
'
```

### 9.6 Show unavailable operators

```bash
oc get co -o json | jq -r '
  .items[] |
  .metadata.name as $name |
  (.status.conditions[] | select(.type=="Available" and .status!="True")) |
  "\($name): Available=\(.status) reason=\(.reason) message=\(.message)"
'
```

### 9.7 Show progressing operators

```bash
oc get co -o json | jq -r '
  .items[] |
  .metadata.name as $name |
  (.status.conditions[] | select(.type=="Progressing" and .status=="True")) |
  "\($name): \(.reason) - \(.message)"
'
```

### 9.8 Show upgrade blockers

```bash
oc get co -o json | jq -r '
  .items[] |
  .metadata.name as $name |
  (.status.conditions[] | select(.type=="Upgradeable" and .status=="False")) |
  "\($name): Upgradeable=False reason=\(.reason) message=\(.message)"
'
```

### 9.9 Show related objects for an operator

```bash
oc get co ingress -o json | jq -r '.status.relatedObjects[] | [.group, .resource, .namespace, .name] | @tsv'
```

### 9.10 Show operator versions

```bash
oc get co kube-apiserver -o json | jq '.status.versions'
```

### 9.11 Get cluster version status

```bash
oc get clusterversion
oc get clusterversion version -o yaml
oc describe clusterversion version
```

### 9.12 Check upgrade recommendations

```bash
oc adm upgrade
oc adm upgrade --include-not-recommended
```

### 9.13 Check CVO pod and logs

```bash
oc get pods -n openshift-cluster-version
oc logs -n openshift-cluster-version deployment/cluster-version-operator
```

### 9.14 Gather support data

```bash
oc adm must-gather
```

For a focused must-gather, depending on component, use a component-specific image or collect targeted resources manually.

## 10. How to troubleshoot a degraded Cluster Operator

Use this flow as a senior-admin checklist.

### Step 1: Confirm overall cluster health

```bash
oc get co
oc get clusterversion
oc get nodes
oc get mcp
```

Look for:

- Operators with `Available=False`
- Operators with `Progressing=True` for a long time
- Operators with `Degraded=True`
- Nodes in `NotReady`
- MachineConfigPools in `UPDATING=True` or `DEGRADED=True`
- ClusterVersion `Progressing=True` or `Failing=True`

### Step 2: Pick the most fundamental failing component first

Troubleshooting order matters. Fix foundational components before dependent ones.

Recommended priority:

1. `etcd`
2. `kube-apiserver`
3. `kube-controller-manager`
4. `kube-scheduler`
5. `machine-config`
6. `network`
7. `dns`
8. `ingress`
9. `authentication`
10. `image-registry`, `monitoring`, `console`, `marketplace`, etc.

Example: If `network` and `ingress` are degraded, fix `network` first. Router pods depend on networking.

### Step 3: Read the condition message

```bash
oc describe co <operator-name>
```

or:

```bash
oc get co <operator-name> -o json | jq '.status.conditions'
```

Do not ignore the message. It usually tells you the first failing resource.

### Step 4: Inspect related objects

```bash
oc get co <operator-name> -o json | jq '.status.relatedObjects'
```

The related objects usually point to:

- Operator namespace
- Operand namespace
- Operator config CR
- Managed deployment, daemon set, or resource
- Cluster-scoped config object

### Step 5: Find the operator namespace

Common examples:

| Operator | Common namespace |
|---|---|
| `authentication` | `openshift-authentication`, `openshift-authentication-operator` |
| `console` | `openshift-console`, `openshift-console-operator` |
| `ingress` | `openshift-ingress`, `openshift-ingress-operator` |
| `network` | `openshift-network-operator`, `openshift-ovn-kubernetes` |
| `dns` | `openshift-dns`, `openshift-dns-operator` |
| `image-registry` | `openshift-image-registry` |
| `monitoring` | `openshift-monitoring` |
| `machine-config` | `openshift-machine-config-operator` |
| `kube-apiserver` | `openshift-kube-apiserver`, `openshift-kube-apiserver-operator` |
| `etcd` | `openshift-etcd`, `openshift-etcd-operator` |

### Step 6: Inspect pods

```bash
oc get pods -n <namespace> -o wide
oc get deploy,ds,sts -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Look for:

- `CrashLoopBackOff`
- `ImagePullBackOff`
- `ErrImagePull`
- `Pending`
- `CreateContainerConfigError`
- `RunContainerError`
- `OOMKilled`
- Unready containers
- Failed mounts
- Failed scheduling
- Permission/SCC failures
- Node affinity or taint issues

### Step 7: Check logs

```bash
oc logs -n <namespace> deployment/<operator-deployment>
oc logs -n <namespace> <pod-name> -c <container-name>
oc logs -n <namespace> <pod-name> --previous
```

For daemon sets:

```bash
oc logs -n <namespace> ds/<daemonset-name> --all-containers=true --tail=100
```

### Step 8: Check operands, not only operator pods

A Cluster Operator may be healthy as a pod but degraded because its **operand** is broken.

Example:

- Ingress Operator pod is running, but router deployment is unavailable.
- Machine Config Operator pod is running, but one node cannot apply MachineConfig.
- Authentication Operator pod is running, but OAuth deployment is unavailable.
- Network Operator pod is running, but OVN daemonset is unhealthy.

Always inspect both:

```text
operator controller pod + managed operand pods/resources
```

### Step 9: Check cluster-wide dependencies

Many operator failures are secondary symptoms. Check:

```bash
oc get nodes
oc get csr
oc get mcp
oc get pvc -A
oc get pv
oc get events -A --sort-by=.lastTimestamp | tail -100
oc adm top nodes
oc adm top pods -A
```

### Step 10: Gather evidence before changing anything

For production:

```bash
oc adm must-gather
oc get co -o yaml > clusteroperators.yaml
oc get clusterversion version -o yaml > clusterversion.yaml
oc get nodes -o wide > nodes.txt
oc get mcp -o wide > mcp.txt
```

Do this before deleting pods, patching config, forcing upgrades, removing finalizers, or editing static-pod resources.

## 11. Deep dive: important Cluster Operators

## 11.1 Cluster Version Operator: `version`

The CVO is responsible for applying OpenShift release payload manifests and tracking the desired OpenShift version.

Commands:

```bash
oc get clusterversion
oc describe clusterversion version
oc get co version
oc get pods -n openshift-cluster-version
oc logs -n openshift-cluster-version deployment/cluster-version-operator
```

Important fields:

```bash
oc get clusterversion version -o json | jq '.status.conditions'
oc get clusterversion version -o json | jq '.status.history'
oc get clusterversion version -o json | jq '.status.desired'
```

Common problems:

- Upgrade payload image cannot be pulled.
- Update path unavailable or not recommended.
- ClusterOperator reports `Upgradeable=False`.
- ClusterOperator stuck in `Progressing=True`.
- CVO cannot apply a manifest due to validation or API issue.
- API server or etcd instability prevents reconciliation.

Important practice:

Do not directly edit the `ClusterVersion` object manually. Use `oc adm upgrade` or the web console to manage upgrades.

---

## 11.2 Machine Config Operator: `machine-config`

The Machine Config Operator manages node-level OS and kubelet-related configuration. It is one of the most important Cluster Operators because node updates and many cluster upgrades depend on it.

Commands:

```bash
oc get co machine-config
oc describe co machine-config
oc get mcp
oc describe mcp master
oc describe mcp worker
oc get mc
oc get nodes
oc get pods -n openshift-machine-config-operator
oc logs -n openshift-machine-config-operator deployment/machine-config-operator
```

Important resources:

- `MachineConfig`
- `MachineConfigPool`
- `KubeletConfig`
- `ContainerRuntimeConfig`
- rendered MachineConfigs
- MCD pods on nodes

Common failure patterns:

### MCP stuck updating

```bash
oc get mcp
```

Symptoms:

```text
UPDATED=False
UPDATING=True
DEGRADED=False
```

Possible causes:

- Node is rebooting slowly.
- Node cannot drain due to PodDisruptionBudget.
- Pod stuck terminating.
- Workload without enough replicas blocks drain.
- Node has local storage pods.
- Node unreachable.

Useful commands:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
oc describe node <node>
oc get pods -A --field-selector spec.nodeName=<node>
oc get pdb -A
```

### MCP degraded

```text
DEGRADED=True
```

Possible causes:

- Invalid MachineConfig.
- File content conflict.
- Kubelet config invalid.
- CRI-O config invalid.
- Node failed to apply rendered config.
- Node filesystem or disk issue.

Useful commands:

```bash
oc describe mcp worker
oc get node <node> -o yaml | grep -A5 machineconfiguration.openshift.io
oc debug node/<node>
```

Inside debug node shell:

```bash
chroot /host
journalctl -u machine-config-daemon -b
journalctl -u kubelet -b
journalctl -u crio -b
```

Senior advice:

Never blindly delete rendered MachineConfigs. Understand which custom MachineConfig caused the rendered output and fix the source object.

## 11.3 Network Operator: `network`

The Network Operator manages cluster networking. In most recent OpenShift clusters, this is commonly OVN-Kubernetes, but environments can vary.

Commands:

```bash
oc get co network
oc describe co network
oc get network.operator.openshift.io cluster -o yaml
oc get network.config.openshift.io cluster -o yaml
oc get pods -n openshift-network-operator
oc get pods -n openshift-ovn-kubernetes -o wide
oc get ds -n openshift-ovn-kubernetes
```

Common failure patterns:

- OVN control plane pods unavailable.
- OVN node pods crash looping.
- Node network configuration issue.
- MTU mismatch.
- Cluster network CIDR or service network misconfiguration.
- Host firewall/security group blocks required traffic.
- DNS issues appear as network symptoms.
- Node not ready due to CNI failure.

Useful checks:

```bash
oc get nodes
oc describe node <node>
oc get pods -n openshift-ovn-kubernetes -o wide
oc logs -n openshift-ovn-kubernetes ds/ovnkube-node -c ovn-controller --tail=100
oc logs -n openshift-ovn-kubernetes ds/ovnkube-node -c ovnkube-node --tail=100
```

Connectivity test example:

```bash
oc run net-test --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc rsh net-test
curl -k https://kubernetes.default.svc
```

Senior advice:

When `network` is degraded, many other operators can become degraded as secondary impact. Fix networking before troubleshooting higher-level symptoms such as console, ingress, monitoring, and authentication.

## 11.4 DNS Operator: `dns`

The DNS Operator manages cluster DNS components.

Commands:

```bash
oc get co dns
oc describe co dns
oc get pods -n openshift-dns -o wide
oc get ds -n openshift-dns
oc logs -n openshift-dns ds/dns-default -c dns
```

Common failure patterns:

- DNS pods not running on all nodes.
- Node-level network issue.
- CoreDNS crash loop.
- ConfigMap issue.
- DNS forwarding problem.
- External DNS server unreachable.

Test DNS from a pod:

```bash
oc run dns-test --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc rsh dns-test
getent hosts kubernetes.default.svc
getent hosts openshift.default.svc
```

If `getent` is unavailable, use tools available in the image or install debug utilities in a temporary troubleshooting image allowed by your environment.

## 11.5 Ingress Operator: `ingress`

The Ingress Operator manages OpenShift router/ingress controller resources.

Commands:

```bash
oc get co ingress
oc describe co ingress
oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller default -n openshift-ingress-operator
oc get pods -n openshift-ingress -o wide
oc get deploy -n openshift-ingress
oc logs -n openshift-ingress-operator deployment/ingress-operator
```

Common failure patterns:

- Router pods not scheduled.
- Router deployment unavailable.
- Load balancer not provisioned.
- Wildcard DNS not pointing to router/load balancer.
- Certificate or default certificate issue.
- Node selector or toleration issue.
- Router cannot bind ports because hostNetwork or permissions fail.

Route testing:

```bash
oc get route -A
curl -kv https://<route-host>
```

Check router canonical hostname and load balancer:

```bash
oc get svc -n openshift-ingress
oc describe svc router-default -n openshift-ingress
```

Senior advice:

If routes fail but `ingress` is healthy, check DNS and external load balancer first. If `ingress` is degraded, inspect the `IngressController` message and router deployment availability.

## 11.6 Authentication Operator: `authentication`

The Authentication Operator manages OAuth and authentication availability.

Commands:

```bash
oc get co authentication
oc describe co authentication
oc get oauth cluster -o yaml
oc get pods -n openshift-authentication
oc get pods -n openshift-authentication-operator
oc logs -n openshift-authentication-operator deployment/authentication-operator
oc logs -n openshift-authentication deployment/oauth-openshift
```

Common failure patterns:

- OAuth pods unavailable.
- Identity provider secret missing or malformed.
- OAuth config invalid.
- Route/DNS/ingress problem affects login.
- OAuth serving cert or CA issue.
- LDAP/HTPasswd/GitHub/OIDC provider unreachable.
- Authentication operator degraded after editing OAuth CR.

HTPasswd example checks:


## 12. Cluster Operators and upgrades

Cluster Operators are central to OpenShift upgrades.

During an upgrade:

1. Admin initiates upgrade using web console or `oc adm upgrade`.
2. The CVO resolves the target release image.
3. The CVO validates the release image.
4. The CVO extracts manifests.
5. The CVO applies manifests in ordered Runlevels.
6. Cluster Operators reconcile their components.
7. Cluster Operators report `Progressing=True` while updating.
8. The CVO waits for operators in each Runlevel to become stable.
9. Machine Config Operator eventually updates node OS/config and reboots nodes.
10. ClusterVersion reports completion when control plane is updated, while nodes might still be updating depending on phase and version behavior.

The CVO waits for operators in a Runlevel to satisfy:

```text
Available=True
Degraded=False
desired version reported in status.versions
```

### Pre-upgrade checklist

```bash
oc get co
oc get clusterversion
oc adm upgrade
oc get nodes
oc get mcp
oc get csr
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Before upgrade, the ideal state is:

```text
All ClusterOperators: Available=True, Progressing=False, Degraded=False
ClusterVersion: Available=True, Progressing=False
All MCPs: UPDATED=True, UPDATING=False, DEGRADED=False
All nodes: Ready
No pending CSRs
```

### Upgrade blockers

Common upgrade blockers:

- `Upgradeable=False` on one or more Cluster Operators.
- Incomplete MachineConfig rollout.
- Degraded control-plane operator.
- Unavailable API server or etcd.
- Disconnected registry mirror missing release image.
- Cluster cannot retrieve update graph.
- Unsupported/deprecated configuration.
- Admin changed unsupported internal resources.

Command:

```bash
oc get co -o json | jq -r '
  .items[] |
  .metadata.name as $name |
  (.status.conditions[] | select(.type=="Upgradeable" and .status=="False")) |
  "\($name): \(.reason) - \(.message)"
'
```

## 13. Troubleshooting stuck `Progressing=True`

### Step 1: Check whether upgrade is active

```bash
oc get clusterversion
oc describe clusterversion version
```

If ClusterVersion is progressing, operator progression may be normal.

### Step 2: Check duration

```bash
oc get co <operator-name>
```

Look at `SINCE`.

A few minutes can be normal. Several hours requires investigation.

### Step 3: Read the message

```bash
oc describe co <operator-name>
```

### Step 4: Check rollout resources

For deployment-based operators:

```bash
oc get deploy -n <namespace>
oc rollout status deploy/<name> -n <namespace>
oc describe deploy/<name> -n <namespace>
```

For daemon sets:

```bash
oc get ds -n <namespace>
oc describe ds/<name> -n <namespace>
```

For static pods:

```bash
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-etcd -o wide
```

For machine-config:

```bash
oc get mcp
oc describe mcp worker
oc describe node <node>
```

### Step 5: Identify blocking resource

Common blockers:

- Node not ready.
- Pod cannot schedule.
- Image cannot pull.
- PDB blocks drain.
- PVC pending.
- Cert secret missing.
- Invalid config map.
- Static pod installer failing.
- One replica unavailable.

## 14. Troubleshooting `Degraded=True`

Use this process:

```bash
OP=<operator-name>
oc describe co $OP
oc get co $OP -o json | jq '.status.conditions'
oc get co $OP -o json | jq '.status.relatedObjects'
```

Then:

1. Identify condition `type=Degraded`.
2. Read `reason` and `message`.
3. Inspect related namespace.
4. Inspect operator pod logs.
5. Inspect operand pods/resources.
6. Check events.
7. Check dependencies.
8. Avoid unsupported manual edits.

Example:

```bash
oc get co ingress -o json | jq -r '
.status.conditions[] | select(.type=="Degraded") | .reason + " - " + .message
'
```

## 18. Real-world failure scenarios

## Scenario 1: `authentication` degraded after HTPasswd change

Symptoms:

```bash
oc get co authentication
```

```text
authentication   True   False   True
```

Check:

```bash
oc describe co authentication
oc get oauth cluster -o yaml

oc get pods -n openshift-authentication
```

Likely causes:

- Secret name in OAuth CR is wrong.

- Correct the secret in `openshift-config`.
- Correct OAuth CR reference.
- Let operator reconcile.

## Scenario 2: `ingress` degraded and routes not reachable

Symptoms:



- Fix invalid MachineConfig.

## Scenario 4: `image-registry` degraded on bare metal or vSphere

## Scenario 5: `network` degraded and pods cannot communicate

Check:

- Node network issue.
- MTU mismatch.

- Then re-check DNS, ingress, authentication, and monitoring.

## 20. Common mistakes by administrators

### Mistake 1: Troubleshooting only pods, not ClusterOperator status

Pods may be running, but operator can still be degraded because the operand state is wrong.

### Mistake 2: Deleting operator pods repeatedly

Deleting pods can restart controllers but rarely fixes the root cause. Always read condition messages first.

### Mistake 3: Ignoring `relatedObjects`

`relatedObjects` often directly points to the relevant namespace or CR.

### Mistake 4: Treating every `Degraded=True` as outage

`Available=True` with `Degraded=True` means investigate, but not always immediate outage.

### Mistake 5: Upgrading with degraded operators

Upgrades should start from a clean baseline unless there is a documented reason and support guidance.

### Mistake 6: Editing generated resources

Avoid editing generated deployments, config maps, rendered MachineConfigs, static pod manifests, or CVO-managed resources directly unless documentation tells you to.

### Mistake 7: Troubleshooting dependent operators first

If `network` is broken, `ingress`, `monitoring`, `console`, and `authentication` may all report symptoms. Fix foundation first.


## 23. Exam and interview notes

### Must-know command

```bash
oc get co
```

### Must-know healthy state

```text
AVAILABLE=True
PROGRESSING=False
DEGRADED=False
```

### Must-know concepts

- Cluster Operators manage OpenShift platform components.
- `ClusterOperator` is a status resource under `config.openshift.io/v1`.
- CVO manages platform lifecycle and uses ClusterOperator status during upgrades.
- OLM Operators are different from Cluster Operators.
- `Degraded=True` does not always mean outage if `Available=True`.
- `Upgradeable=False` can block minor upgrades.
- `relatedObjects` tells you where to troubleshoot next.
- `machine-config` is critical for node updates and upgrades.
- `etcd` and `kube-apiserver` are foundational; troubleshoot them before dependent operators.

### Interview-style answer

> Cluster Operators are OpenShift platform operators managed by the Cluster Version Operator. They reconcile core cluster components such as authentication, networking, ingress, DNS, image registry, monitoring, machine configuration, etcd, and API servers. Their health is exposed through `ClusterOperator` resources in `config.openshift.io/v1`, visible with `oc get co`. The key conditions are `Available`, `Progressing`, `Degraded`, and `Upgradeable`. During upgrades, the CVO applies release manifests in Runlevels and waits for Cluster Operators to report `Available=True`, `Degraded=False`, and the desired version before moving forward. For troubleshooting, I start with `oc get co`, inspect `oc describe co <name>`, read conditions and messages, inspect `relatedObjects`, then check the operator namespace, operand resources, events, and logs.

## 26. Best practices

1. Use `oc get co` as the first platform health command.
2. Read condition messages before restarting anything.
3. Use `relatedObjects` to locate the correct namespace and CR.
4. Troubleshoot foundational operators first: `etcd`, `kube-apiserver`, `machine-config`, `network`, `dns`.
5. Do not directly edit generated resources.
6. Avoid deleting static pods manually unless following documented recovery.
7. Keep all Cluster Operators healthy before upgrades.
8. Treat `Upgradeable=False` as a pre-upgrade blocker.
9. Collect must-gather before risky production changes.
10. Document recurring operator degradation and create preventive alerts/runbooks.

## 28. Final summary

Cluster Operators are the operational heartbeat of OpenShift. They expose the health, rollout, degradation, and upgrade readiness of core platform components through `ClusterOperator` resources. For a senior OpenShift administrator, the key is not just knowing `oc get co`, but understanding how to interpret conditions, follow `relatedObjects`, correlate operator and operand health, prioritize foundational failures, and avoid unsupported manual changes.

A clean OpenShift cluster should normally show:

```text
Available=True
Progressing=False
Degraded=False
```

When something is wrong, start with:

```bash
oc get co
oc describe co <operator>
oc get co <operator> -o json | jq '.status.conditions, .status.relatedObjects, .status.versions'
```

Then move from ClusterOperator status to related namespaces, operator pods, managed operands, events, logs, and dependencies.
