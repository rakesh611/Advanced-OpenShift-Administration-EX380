## 1. Executive Summary

An **InstallPlan** is the OLM-generated execution plan that tells OpenShift exactly which Kubernetes resources must be created or updated to install or upgrade an Operator. It is not normally created manually by an administrator. It is created by OLM after an administrator or authorized user creates a `Subscription`.

Think of it like this:

```text
Subscription = intent
InstallPlan  = calculated execution plan
CSV          = installed Operator version and metadata
Operator pod = actual running controller
CRDs         = APIs introduced by the Operator
RBAC         = permissions required by the Operator
```

In production, `InstallPlan` is important because it is the point where you can review and control what OLM is about to do before an Operator installation or upgrade changes cluster state.

For a senior OpenShift administrator, InstallPlan knowledge is essential for:

- Controlled Operator upgrades
- Manual approval workflows
- Change windows
- Troubleshooting stuck Operator installations
- Debugging catalog and dependency resolution issues
- Understanding why an Operator did not install even though the `Subscription` exists
- Validating which resources OLM will create before allowing the change

## 2. Where InstallPlan Fits in Operator Management

Operator management in OpenShift is handled mainly by **Operator Lifecycle Manager** for OLM-based add-on Operators. OLM handles Operator installation, update, dependency resolution, RBAC creation, CRD management, and lifecycle tracking.

A normal OLM Classic installation path looks like this:

```text
User / Admin
    |
    v
OperatorHub / Software Catalog
    |
    v
CatalogSource
    |
    v
Package + Channel + Bundle metadata
    |
    v
Subscription
    |
    v
InstallPlan
    |
    v
ClusterServiceVersion
    |
    v
CRDs / RBAC / ServiceAccount / Deployment / Operator Pod
    |
    v
Custom Resources managed by Operator
```

The InstallPlan is the bridge between **intent** and **execution**.

## 3. Core Definition

An `InstallPlan` is a Kubernetes custom resource with API group:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: InstallPlan
```

It describes the resources OLM must create to install or upgrade an Operator to a specific version. That specific version is represented by a `ClusterServiceVersion` or CSV.

A simple definition:

> InstallPlan is the OLM-generated list of resources required to install or upgrade an Operator version.

A more practical administrator definition:

> InstallPlan is the pending or approved change request generated by OLM from a Subscription. It contains the resources OLM will apply, the target CSV version, the approval status, and execution status.

## 4. OLM Classic Workflow

OLM Classic commonly uses these objects:

| Object | Purpose |
|---|---|
| `CatalogSource` | Provides Operator metadata from an index/catalog image. |
| `PackageManifest` | Shows available Operator packages and channels discovered from catalogs. |
| `Subscription` | Declares intent to install or track an Operator package/channel. |
| `InstallPlan` | Describes calculated resources to install or upgrade the Operator. |
| `ClusterServiceVersion` | Represents a specific installed Operator version. |
| `OperatorGroup` | Defines target namespaces and RBAC scope for the Operator. |
| `CustomResourceDefinition` | Adds Kubernetes APIs required by the Operator. |

Typical OLM Classic sequence:

```text
1. Admin selects Operator from software catalog.
2. OpenShift creates a Subscription.
3. OLM resolves package, channel, version, dependencies, and required APIs.
4. OLM creates an InstallPlan.
5. If approval is Automatic, OLM approves it.
6. If approval is Manual, admin must approve it.
7. OLM creates resources listed in the InstallPlan.
8. CSV moves through Pending / Installing / Succeeded or Failed.
9. Operator Deployment and pods become available.
```

## 5. Relationship Between OperatorHub, CatalogSource, Subscription, InstallPlan, CSV, and OperatorGroup

### 5.1 OperatorHub / Software Catalog

The web console page where administrators discover and install Operators. It is a user-facing interface.

### 5.2 CatalogSource

A `CatalogSource` points OLM to a catalog image that contains Operator metadata.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: registry.redhat.io/redhat/redhat-operator-index:v4.22
  displayName: Red Hat Operators
  publisher: Red Hat
```

If the catalog source is unhealthy, InstallPlans may not be generated or may fail dependency resolution.

### 5.3 Subscription

A `Subscription` is the admin's intent to install an Operator and follow a channel.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-namespace
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

Important fields:

| Field | Meaning |
|---|---|
| `spec.name` | Operator package name. |
| `spec.channel` | Update stream, such as `stable`, `fast`, `candidate`, or versioned channel. |
| `spec.source` | CatalogSource name. |
| `spec.sourceNamespace` | Namespace where the CatalogSource exists. |
| `spec.installPlanApproval` | `Automatic` or `Manual`. |
| `spec.startingCSV` | Optional starting version. Useful for controlled installs. |

### 5.4 InstallPlan

The `InstallPlan` is created by the Subscription. It lists the resources OLM will create.

### 5.5 CSV

The `ClusterServiceVersion` represents a specific Operator version, including install strategy, permissions, owned APIs, required APIs, related images, and deployment specs.

### 5.6 OperatorGroup

The `OperatorGroup` controls install scope and target namespaces. It affects whether the CSV can be installed.

## 6. InstallPlan API Object Deep Dive

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: InstallPlan
metadata:
  name: install-abcde
  namespace: openshift-logging
  ownerReferences:
  - apiVersion: operators.coreos.com/v1alpha1
    kind: Subscription
    name: cluster-logging
spec:
  approval: Manual
  approved: false
  clusterServiceVersionNames:
  - cluster-logging.v6.0.0
  generation: 1
status:
  phase: RequiresApproval
  catalogSources:
  - redhat-operators
  conditions:
  - type: Resolved
    status: "True"
  plan:
  - resolving: cluster-logging.v6.0.0
    resource:
      group: operators.coreos.com
      version: v1alpha1
      kind: ClusterServiceVersion
      name: cluster-logging.v6.0.0
      sourceName: redhat-operators
      sourceNamespace: openshift-marketplace
    status: NotPresent
```

### 6.1 Metadata Fields

| Field | Meaning |
|---|---|
| `metadata.name` | Generated name, usually `install-xxxxx`. |
| `metadata.namespace` | Namespace where the Subscription exists. |
| `ownerReferences` | Often points to the Subscription that created it. |
| `creationTimestamp` | Useful for finding newest pending plans. |

### 6.2 Spec Fields

| Field | Meaning |
|---|---|
| `spec.approval` | Approval strategy copied from Subscription: `Automatic` or `Manual`. |
| `spec.approved` | Whether this plan has been approved. Patch this to `true` for manual approval. |
| `spec.clusterServiceVersionNames` | Target CSV names to install. |
| `spec.generation` | Internal generation used by OLM. |

### 6.3 Status Fields

| Field | Meaning |
|---|---|
| `status.phase` | Overall InstallPlan phase. |
| `status.conditions` | Detailed condition messages. |
| `status.catalogSources` | Catalog sources used during resolution. |
| `status.plan` | Resource list OLM will create or has created. |
| `status.bundleLookups` | Bundle unpacking and lookup status in many OLM versions. |

### 6.4 `status.plan` Resource List

This is the most important part for review.

Common resources inside an InstallPlan:

- `ClusterServiceVersion`
- `CustomResourceDefinition`
- `ServiceAccount`
- `Role`
- `RoleBinding`
- `ClusterRole`
- `ClusterRoleBinding`
- `Deployment`
- `Service`
- `WebhookConfiguration`
- `APIService`

A senior admin should inspect these before approving an important production Operator upgrade.

## 7. InstallPlan Lifecycle Phases

Common InstallPlan phases include:

| Phase | Meaning | Admin Action |
|---|---|---|
| `None` / empty | OLM has not fully populated status yet. | Wait and inspect Subscription. |
| `Planning` | OLM is resolving resources. | Check catalog health if stuck. |
| `RequiresApproval` | Manual approval is required. | Review and approve if acceptable. |
| `Installing` | OLM is creating resources. | Monitor CSV and pods. |
| `Complete` | InstallPlan completed successfully. | Verify Operator status. |
| `Failed` | OLM failed to install resources. | Inspect conditions, events, CSV, catalogs. |

Typical manual approval flow:

```text
InstallPlan created
    |
    v
phase: RequiresApproval
spec.approved: false
    |
    | admin reviews plan
    v
spec.approved: true
    |
    v
phase: Installing
    |
    v
phase: Complete
```

## 8. Automatic vs Manual Approval

The approval strategy is configured in the Subscription:

```yaml
spec:
  installPlanApproval: Automatic
```

or:

```yaml
spec:
  installPlanApproval: Manual
```

### 8.1 Automatic Approval

With `Automatic`, OLM approves InstallPlans automatically.

Advantages:

- Less operational overhead
- Good for non-critical Operators
- Faster security and bug-fix updates
- Useful in development or test clusters

Risks:

- Operator updates can happen without a maintenance window
- CRD schema changes might affect workloads
- Operator pod restarts can happen during business hours
- New RBAC permissions may be granted automatically

### 8.2 Manual Approval

With `Manual`, OLM creates the InstallPlan but does not execute it until approved.

Advantages:

- Change control
- Maintenance window alignment
- Review of RBAC and CRDs before applying
- Better production governance
- Safer for storage, logging, service mesh, security, and cluster-wide Operators

Risks:

- Pending updates can be forgotten
- Security patches can be delayed
- Too many pending plans can create operational noise

### 8.3 Production Recommendation

For production clusters:

| Operator Type | Suggested Approval |
|---|---|
| Logging / Loki / Elasticsearch legacy | Manual |
| Service Mesh | Manual |
| Storage / ODF / CSI | Manual |
| Security / Compliance / File Integrity | Manual |
| GitOps / Pipelines | Manual or Automatic depending on risk |
| Small app namespace-scoped Operator | Automatic may be acceptable |
| Lab / exam environment | Use whatever task requires; know both. |

## 9. Installing an Operator Using InstallPlan Flow

Example: Install an Operator with manual approval.

### 9.1 Create Namespace

```bash
oc new-project openshift-example-operator
```

### 9.2 Create OperatorGroup

For a namespace-scoped Operator:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: example-operator-group
  namespace: openshift-example-operator
spec:
  targetNamespaces:
  - openshift-example-operator
```

Apply:

```bash
oc apply -f operatorgroup.yaml
```

For all-namespaces installation, the OperatorGroup might look like:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-operators
  namespace: openshift-operators
spec: {}
```

### 9.3 Create Subscription

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: openshift-example-operator
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

Apply:

```bash
oc apply -f subscription.yaml
```

### 9.4 Watch InstallPlan

```bash
oc get installplan -n openshift-example-operator
```

Expected example:

```text
NAME            CSV                       APPROVAL   APPROVED
install-abcde   example-operator.v1.2.3   Manual     false
```

### 9.5 Review InstallPlan

```bash
oc describe installplan install-abcde -n openshift-example-operator
```

or:

```bash
oc get installplan install-abcde -n openshift-example-operator -o yaml
```

### 9.6 Approve InstallPlan

```bash
oc patch installplan install-abcde \
  -n openshift-example-operator \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 9.7 Verify CSV

```bash
oc get csv -n openshift-example-operator
```

Expected:

```text
NAME                      DISPLAY            VERSION   REPLACES   PHASE
example-operator.v1.2.3   Example Operator   1.2.3                Succeeded
```

### 9.8 Verify Operator Pod

```bash
oc get pods -n openshift-example-operator
```

## 10. Upgrading an Operator Using InstallPlan Flow

An Operator upgrade is also performed through a new InstallPlan.

Upgrade triggers:

- New bundle appears in the subscribed channel
- Admin changes Subscription channel to a newer channel
- Admin changes catalog image and it exposes newer packages
- `startingCSV` / channel constraints allow a newer CSV

### 10.1 Check Current Subscription

```bash
oc get sub -n <operator-namespace>
```

```bash
oc describe sub <subscription-name> -n <operator-namespace>
```

Important status fields:

```yaml
status:
  currentCSV: example-operator.v1.2.4
  installedCSV: example-operator.v1.2.3
  installPlanRef:
    name: install-fghij
```

Meaning:

| Field | Meaning |
|---|---|
| `currentCSV` | Newest version known to OLM for this Subscription. |
| `installedCSV` | Version currently installed. |
| `installPlanRef` | Current InstallPlan for install or upgrade. |

If `currentCSV` differs from `installedCSV`, an upgrade might be pending or in progress.

### 10.2 Find Pending Upgrade Plan

```bash
oc get installplan -n <operator-namespace>
```

Example:

```text
NAME            CSV                       APPROVAL   APPROVED
install-fghij   example-operator.v1.2.4   Manual     false
```

### 10.3 Review Plan Before Upgrade

```bash
oc get installplan install-fghij -n <operator-namespace> -o yaml
```

Look for:

- New CSV version
- New CRDs or changed CRDs
- New cluster roles
- New cluster role bindings
- Webhooks
- API services
- Deployment changes
- Related images

### 10.4 Approve During Maintenance Window

```bash
oc patch installplan install-fghij \
  -n <operator-namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 10.5 Watch CSV Upgrade

```bash
watch -n 5 'oc get csv -n <operator-namespace>'
```

```bash
oc describe csv <new-csv-name> -n <operator-namespace>
```

## 11. How OLM Resolves Dependencies

Before creating an InstallPlan, OLM performs dependency resolution. This is similar to package managers such as `yum`, `dnf`, or `rpm` dependency resolution.

OLM evaluates:

- Package name
- Channel
- Available bundle versions
- Replaces / skipRange graph
- Required APIs
- Provided APIs
- CRD ownership
- Existing CSVs
- OperatorGroup scope
- CatalogSource health
- Namespace placement
- Install mode support

### 11.1 Required APIs and Provided APIs

An Operator bundle can declare:

- APIs it **provides**
- APIs it **requires**

If Operator A requires an API provided by Operator B, OLM might install both, or fail if the dependency cannot be resolved.

### 11.2 Common Resolution Failure Reasons

| Failure | Meaning |
|---|---|
| Package not found | Wrong `spec.name`, wrong catalog, disabled catalog, or disconnected mirror missing package. |
| Channel not found | Wrong `spec.channel`. |
| No replacement path | Upgrade graph does not allow transition. |
| Required API missing | Dependency Operator not available. |
| CRD conflict | Another Operator owns or provides conflicting APIs. |
| Catalog unhealthy | OLM refuses resolution because catalog data is unreliable. |
| Unsupported OperatorGroup | CSV install modes do not match namespace scope. |

## 12. OperatorGroup Impact on InstallPlan

InstallPlan execution depends heavily on a valid `OperatorGroup`.

An InstallPlan namespace must normally have exactly one valid OperatorGroup.

Problem cases:

| Problem | Result |
|---|---|
| No OperatorGroup | CSV might not be generated or remains pending. |
| Multiple OperatorGroups | InstallPlan can continue attempting but CSV generation fails. |
| Wrong service account in OperatorGroup | RBAC generation fails. |
| CSV does not support target namespace mode | CSV fails with unsupported OperatorGroup condition. |

### 12.1 Check OperatorGroups

```bash
oc get operatorgroup -n <operator-namespace>
```

```bash
oc describe operatorgroup <operatorgroup-name> -n <operator-namespace>
```

### 12.2 Example Error

```text
attenuated service account query failed - more than one operator group(s) are managing this namespace count=2
```

Fix:

```bash
oc get operatorgroup -n <namespace>
oc delete operatorgroup <extra-operatorgroup> -n <namespace>
```

Then allow OLM to reconcile again.

## 13. Namespace and Scope Behavior

Operator installation mode affects how OLM creates RBAC and where the Operator watches resources.

Common install modes:

| Mode | Meaning |
|---|---|
| `OwnNamespace` | Operator watches its own namespace. |
| `SingleNamespace` | Operator watches one selected namespace. |
| `MultiNamespace` | Operator watches multiple selected namespaces. |
| `AllNamespaces` | Operator watches all namespaces. |

The CSV must support the selected mode. If the Subscription and OperatorGroup imply a mode the CSV does not support, installation fails.

### 13.1 All Namespaces Pattern

Usually installed in:

```text
openshift-operators
```

OperatorGroup:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: global-operators
  namespace: openshift-operators
spec: {}
```

### 13.2 Single Namespace Pattern

Usually installed in a dedicated namespace:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: app-operator-group
  namespace: app-operator-ns
spec:
  targetNamespaces:
  - app-operator-ns
```

## 14. Inspecting InstallPlans with `oc`

### 14.1 List All InstallPlans

```bash
oc get installplan -A
```

Short alias also works:

```bash
oc get ip -A
```

### 14.2 List InstallPlans in Namespace

```bash
oc get installplan -n <namespace>
```

Example:

```bash
oc get installplan -n openshift-logging
```

### 14.3 Show YAML

```bash
oc get installplan <installplan-name> -n <namespace> -o yaml
```

### 14.4 Describe InstallPlan

```bash
oc describe installplan <installplan-name> -n <namespace>
```

### 14.5 Find Pending Manual Plans

```bash
oc get installplan -A \
  -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,CSV:.spec.clusterServiceVersionNames[*],APPROVAL:.spec.approval,APPROVED:.spec.approved,PHASE:.status.phase'
```

### 14.6 Find Plans Requiring Approval

```bash
oc get installplan -A -o json | jq -r '
  .items[] |
  select(.spec.approval=="Manual" and .spec.approved==false) |
  [.metadata.namespace, .metadata.name, (.spec.clusterServiceVersionNames|join(",")), .status.phase] |
  @tsv'
```

### 14.7 Get InstallPlan from Subscription

```bash
oc get sub <subscription-name> -n <namespace> \
  -o jsonpath='{.status.installPlanRef.name}{"\n"}'
```

Then:

```bash
IP=$(oc get sub <subscription-name> -n <namespace> -o jsonpath='{.status.installPlanRef.name}')
oc get installplan "$IP" -n <namespace> -o yaml
```

## 15. Approving a Pending InstallPlan

### 15.1 Correct Way

Patch `spec.approved` on the InstallPlan:

```bash
oc patch installplan <installplan-name> \
  -n <namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 15.2 Example

```bash
oc patch installplan install-7tx2k \
  -n openshift-file-integrity \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 15.3 Verify

```bash
oc get installplan install-7tx2k -n openshift-file-integrity
```

```bash
oc get csv -n openshift-file-integrity
```

```bash
oc get pods -n openshift-file-integrity
```

### 15.4 Do Not Confuse These Actions

| Action | Result |
|---|---|
| Patch InstallPlan `spec.approved: true` | Approves existing pending InstallPlan. |
| Change Subscription `installPlanApproval` to `Automatic` | Affects future behavior, but does not always approve an already pending plan in the way you expect. |
| Delete InstallPlan | OLM may regenerate another plan, but this is not the normal approval method. |
| Delete Subscription | Stops tracking Operator and can affect upgrades. |

## 16. Reading InstallPlan Status Like a Senior Admin

When reviewing an InstallPlan, do not only check `APPROVED=true`. Check the full plan.

### 16.1 Important Checks

```bash
oc get installplan <ip> -n <ns> -o yaml
```

Review:

```yaml
spec:
  approval: Manual
  approved: false
  clusterServiceVersionNames:
  - some-operator.v1.2.3
status:
  phase: RequiresApproval
  catalogSources:
  - redhat-operators
  conditions:
  - type: Resolved
    status: "True"
  plan:
  - resource:
      kind: ClusterServiceVersion
      name: some-operator.v1.2.3
    status: NotPresent
```

### 16.2 Questions to Ask Before Approval

1. Is this the expected Operator version?
2. Is this coming from the expected CatalogSource?
3. Does the plan create new CRDs?
4. Does it create cluster-wide RBAC?
5. Does it install webhooks or APIService resources?
6. Does it replace a critical Operator version?
7. Is this being done during a valid maintenance window?
8. Are dependent workloads ready for the Operator upgrade?
9. Does the Operator support this OpenShift version?
10. Is the catalog from a trusted source?

### 16.3 Extract Resource Kinds from Plan

```bash
oc get installplan <ip> -n <ns> -o json | jq -r '.status.plan[].resource.kind' | sort | uniq -c
```

Example output:

```text
1 ClusterServiceVersion
3 CustomResourceDefinition
1 Deployment
2 ClusterRole
2 ClusterRoleBinding
1 ServiceAccount
```

### 16.4 Extract Cluster-Wide RBAC

```bash
oc get installplan <ip> -n <ns> -o json | jq -r '
  .status.plan[] |
  select(.resource.kind=="ClusterRole" or .resource.kind=="ClusterRoleBinding") |
  .resource.kind + " " + .resource.name'
```

## 17. Common InstallPlan Conditions and Subscription Conditions

InstallPlan problems often appear in the related `Subscription` conditions.

Common Subscription condition types:

| Condition | Meaning |
|---|---|
| `CatalogSourcesUnhealthy` | One or more catalog sources needed for resolution are unhealthy. |
| `InstallPlanMissing` | Subscription expected an InstallPlan but cannot find it. |
| `InstallPlanPending` | InstallPlan exists but is pending, often waiting for manual approval. |
| `InstallPlanFailed` | InstallPlan failed to execute. |
| `ResolutionFailed` | OLM could not resolve package, channel, version, or dependencies. |

Check them:

```bash
oc describe sub <subscription-name> -n <namespace>
```

or:

```bash
oc get sub <subscription-name> -n <namespace> -o yaml
```

## 18. Troubleshooting InstallPlan Problems

### 18.1 Problem: InstallPlan Stuck in `RequiresApproval`

Symptoms:

```bash
oc get ip -n <ns>
```

```text
NAME            CSV                    APPROVAL   APPROVED
install-abcde   my-operator.v1.0.0     Manual     false
```

Cause:

- Subscription uses `installPlanApproval: Manual`
- Admin has not approved the InstallPlan

Fix:

```bash
oc patch installplan install-abcde -n <ns> --type merge -p '{"spec":{"approved":true}}'
```

Verify:

```bash
oc get csv -n <ns>
oc get pods -n <ns>
```

---

### 18.2 Problem: Subscription Exists but No InstallPlan Created

Check Subscription:

```bash
oc describe sub <sub-name> -n <ns>
```

Check PackageManifest:

```bash
oc get packagemanifest | grep -i <operator-name>
```

Check CatalogSource:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <catalog-name> -n openshift-marketplace
```

Check OLM pods:


## 23. Backup, Audit, and Rollback Reality

### 23.1 InstallPlan Is Not a Rollback Tool

InstallPlan moves forward in the update graph. It is not a full rollback mechanism.

Rolling back an Operator may require:

- Confirming catalog has downgrade path
- Deleting and recreating Subscription with `startingCSV`
- Restoring CRDs or CRs carefully
- Following vendor-specific rollback procedure
- Restoring etcd backup in severe cases

### 23.2 CRD Downgrade Risk

CRDs are cluster-scoped. Once upgraded, stored custom resources might use fields or versions not supported by an older Operator.

This is why manual InstallPlan review is critical for Operators managing important APIs.

### 23.3 Audit InstallPlan Approval

Check Kubernetes audit logs if enabled, or inspect object metadata:

```bash
oc get installplan <ip> -n <ns> -o yaml
```

For GitOps or change control, record:

- InstallPlan name
- Namespace
- Subscription
- Target CSV
- Approver
- Time approved
- Maintenance window
- Resulting CSV phase

## 27. Exam and Interview Notes

### 27.1 Exam-Style Points

You should be able to:

- Create a `Subscription` with `installPlanApproval: Manual` or `Automatic`.
- Find the generated InstallPlan.
- Approve a manual InstallPlan.
- Verify CSV phase is `Succeeded`.
- Troubleshoot when Operator pod does not appear.
- Check `CatalogSource` status.
- Check `OperatorGroup` scope.
- Understand that default cluster Operators are managed by CVO, not OLM Subscriptions.

### 27.2 Common Exam Command Pattern

```bash
oc get sub -n <ns>
oc get ip -n <ns>
oc patch ip <ip-name> -n <ns> --type merge -p '{"spec":{"approved":true}}'
oc get csv -n <ns>
oc get pods -n <ns>
```

### 27.3 Interview Questions

#### Q1. What is an InstallPlan?

An InstallPlan is an OLM-generated resource that lists the Kubernetes resources required to install or upgrade an Operator to a specific CSV version.

#### Q2. Do admins manually create InstallPlans?

Normally no. Admins create Subscriptions; OLM creates InstallPlans.

#### Q3. How do you approve a manual InstallPlan?

Patch `spec.approved` to `true`:

```bash
oc patch installplan <name> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

#### Q4. What is the difference between Subscription and InstallPlan?

A Subscription declares intent to install or track an Operator channel. An InstallPlan is the resolved execution plan generated from that intent.

#### Q5. Why would an InstallPlan not be generated?

Possible causes include unhealthy CatalogSource, wrong package/channel, disabled OperatorHub sources, disconnected mirror missing content, or dependency resolution failure.

#### Q6. Why is manual approval useful?

It allows review of RBAC, CRDs, webhooks, API services, target CSV version, and change timing before OLM changes cluster state.

#### Q7. What happens after an InstallPlan is approved?

OLM creates the resources listed in the plan and installs or upgrades the Operator CSV in the Subscription namespace.

#### Q8. Can an InstallPlan be used for rollback?

No. It is an install/upgrade execution plan, not a rollback mechanism.

## 28. Best Practices

### 28.1 Production Best Practices

- Use `Manual` approval for critical Operators.
- Review InstallPlan resources before approval.
- Check cluster health before approval.
- Validate Operator compatibility with OpenShift version.
- Approve during maintenance windows.
- Keep catalogs healthy.
- Avoid installing many unrelated Operators in the same namespace.
- Use dedicated namespaces for important Operators when supported.
- Track Subscription, CSV, and InstallPlan state in change records.
- Monitor pending InstallPlans with alerts.

### 28.2 Security Best Practices

- Review ClusterRoles and ClusterRoleBindings in the InstallPlan.
- Avoid untrusted catalogs in production.
- Disable unused default catalogs if your organization requires strict supply-chain control.
- Use disconnected mirrored catalogs for regulated environments.
- Keep pull secrets secure.
- Validate related images in Operator bundles.

### 28.3 Troubleshooting Best Practices

- Start with Subscription conditions.
- Then inspect InstallPlan status.
- Then inspect CSV.
- Then check OperatorGroup.
- Then check CatalogSource.
- Then check OLM logs.
- Do not randomly delete OLM resources without understanding ownership.

### 28.4 Namespace Best Practices

- Ensure only one OperatorGroup exists in the Operator namespace.
- Match OperatorGroup scope with CSV-supported install modes.
- Use `openshift-operators` for global Operators if appropriate.
- Use dedicated namespaces for complex Operators.

## 30. Key Takeaways

- `InstallPlan` is generated by OLM from a `Subscription`.
- It contains the resolved resources required to install or upgrade an Operator.
- Manual approval requires patching `spec.approved: true` on the InstallPlan.
- `Subscription` is intent; `InstallPlan` is execution plan; `CSV` is installed Operator version.
- A pending InstallPlan is not always a problem; it might simply be waiting for manual approval.
- InstallPlan troubleshooting usually starts with Subscription conditions and then moves to InstallPlan, CSV, OperatorGroup, CatalogSource, and OLM logs.
- In production, manual InstallPlan approval is a powerful change-control mechanism.
- InstallPlan is not a rollback tool; plan Operator upgrades carefully.
- Catalog health and OperatorGroup correctness are two of the most common causes of InstallPlan/CSV problems.

## Appendix C: Safe Production Approval Script Template

This script shows a guarded way to review and approve a single InstallPlan. Customize it for your environment.

```bash
#!/usr/bin/env bash
set -euo pipefail

NS="${1:?Usage: $0 <namespace> <installplan>}"
IP="${2:?Usage: $0 <namespace> <installplan>}"

echo "Namespace: $NS"
echo "InstallPlan: $IP"

echo "\nCurrent InstallPlan summary:"
oc get installplan "$IP" -n "$NS" \
  -o custom-columns='NAME:.metadata.name,CSV:.spec.clusterServiceVersionNames[*],APPROVAL:.spec.approval,APPROVED:.spec.approved,PHASE:.status.phase'

echo "\nResources in plan:"
oc get installplan "$IP" -n "$NS" -o json | jq -r '
.status.plan[]
| [.resource.kind, .resource.name, .resource.sourceName, .status]
| @tsv'

echo "\nCluster-wide RBAC in plan:"
oc get installplan "$IP" -n "$NS" -o json | jq -r '
.status.plan[]
| select(.resource.kind=="ClusterRole" or .resource.kind=="ClusterRoleBinding")
| [.resource.kind, .resource.name]
| @tsv'

read -r -p "Approve this InstallPlan? Type YES: " CONFIRM

if [[ "$CONFIRM" == "YES" ]]; then
  oc patch installplan "$IP" -n "$NS" --type merge -p '{"spec":{"approved":true}}'
  echo "Approved. Watch CSV status with: oc get csv -n $NS -w"
else
  echo "Not approved."
fi
```
