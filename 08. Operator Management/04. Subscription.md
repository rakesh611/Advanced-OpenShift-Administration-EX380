## 1. What is a Subscription?

In OpenShift Operator management, a **Subscription** is a namespaced OLM custom resource that tells Operator Lifecycle Manager:

> “Install this Operator package from this catalog, track this channel, and handle its install/upgrade using this approval policy.”

A Subscription is the administrator's declarative intent to install and keep an Operator updated. It connects the following items:

- The **Operator package name** you want to install.
- The **CatalogSource** where OLM can find operator metadata.
- The **channel** that defines the update stream.
- The **approval strategy** for InstallPlans.
- Optionally, the **starting CSV** version.
- Optionally, runtime configuration for the Operator deployment via `spec.config`.

A Subscription does **not** directly run the Operator container. Instead, it drives the OLM workflow. OLM uses the Subscription to generate an InstallPlan, install the CSV, create RBAC, deploy the operator controller pod, and later track updates.

Think of Subscription as the **package manager subscription record** for an Operator. If Linux package management is your analogy:

| Linux package manager concept | OLM equivalent |
|---|---|
| Repository metadata | CatalogSource |
| Package name | Operator package name |
| Repository stream | Channel |
| Transaction plan | InstallPlan |
| Installed package metadata | ClusterServiceVersion |
| Package subscription / tracking rule | Subscription |

## 2. Where Subscription fits in OLM architecture

OLM is the component that manages installation, upgrade, and lifecycle of Operators. In a normal OpenShift cluster, OLM uses several custom resources.

High-level flow:

```text
OperatorHub / PackageManifest
        |
        v
CatalogSource  --->  package/channel/bundle metadata
        |
        v
Subscription  --->  admin intent: install package X from source Y, channel Z
        |
        v
InstallPlan  --->  generated execution plan; may need approval
        |
        v
ClusterServiceVersion  --->  installed Operator metadata and deployment spec
        |
        v
Operator Deployment / RBAC / CRDs / Webhooks / APIService
        |
        v
Operator reconciles operands through Custom Resources
```

Two controllers are important:

1. **Catalog Operator**
   - Watches CatalogSources, PackageManifests, Subscriptions, and InstallPlans.
   - Resolves what needs to be installed or updated.
   - Creates InstallPlans from Subscriptions.

2. **OLM Operator**
   - Executes approved InstallPlans.
   - Installs and manages ClusterServiceVersions.
   - Creates or updates RBAC, CRDs, deployments, webhooks, and related resources.

As a senior administrator, you should not troubleshoot Subscription alone. You must inspect the full chain:

```text
CatalogSource -> PackageManifest -> Subscription -> InstallPlan -> CSV -> Deployment/Pod/Logs
```

## 3. Subscription is not a Red Hat account subscription

OpenShift has two different meanings of the word **subscription**:

1. **Red Hat product subscription**
   - Commercial entitlement, support, licensing, account-level subscription.
   - Related to Red Hat Customer Portal, pull secrets, support cases, etc.

2. **OLM Subscription**
   - Kubernetes custom resource: `Subscription.operators.coreos.com/v1alpha1`.
   - Used by Operator Lifecycle Manager to install and update Operators.

This document is about the second one: **OLM Subscription**.

## 4. Core OLM objects around Subscription

### 4.1 CatalogSource

A `CatalogSource` is where OLM gets operator metadata.

Examples:

```bash
oc get catalogsource -n openshift-marketplace
```

Common default CatalogSources:

```text
redhat-operators
certified-operators
community-operators
redhat-marketplace
```

A Subscription refers to one CatalogSource:

```yaml
spec:
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

### 4.2 PackageManifest

A `PackageManifest` is a cluster-visible view of available operator packages from catalogs.

```bash
oc get packagemanifests -n openshift-marketplace
oc describe packagemanifest <operator-package-name> -n openshift-marketplace
```

Use it to verify:

- Package name
- Available channels
- Default channel
- Available versions
- Supported install modes
- Catalog name

### 4.3 OperatorGroup

An `OperatorGroup` defines the target namespaces an Operator will watch and where OLM creates RBAC.

For namespaced operators, a proper OperatorGroup must exist in the same namespace as the Subscription.

Example:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: app-operatorgroup
  namespace: app-operators
spec:
  targetNamespaces:
    - app-operators
```

Important production rule:

> Normally, only one OperatorGroup should exist in an operator installation namespace.

### 4.4 Subscription

The `Subscription` selects the package, catalog, channel, and approval strategy.

### 4.5 InstallPlan

OLM creates an InstallPlan from the Subscription.

```bash
oc get installplan -n <operator-namespace>
oc describe installplan <installplan-name> -n <operator-namespace>
```

If approval is `Manual`, the InstallPlan remains unapproved until an admin approves it.

### 4.6 ClusterServiceVersion

A `ClusterServiceVersion` represents an installed Operator version.

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
```

A healthy installed Operator normally has CSV phase:

```text
Succeeded
```

## 5. Complete lifecycle flow

When you create a Subscription, the lifecycle typically works like this:

1. Admin creates namespace.
2. Admin ensures an OperatorGroup exists.
3. Admin creates Subscription.
4. Catalog Operator resolves package metadata from CatalogSource.
5. Catalog Operator creates an InstallPlan.
6. If `installPlanApproval: Automatic`, OLM approves and executes it automatically.
7. If `installPlanApproval: Manual`, admin reviews and approves it.
8. OLM creates or updates CRDs, RBAC, Deployments, Services, Webhooks, APIService, etc.
9. OLM creates a ClusterServiceVersion.
10. CSV reaches `Succeeded` if all requirements are met.
11. Operator pod starts running.
12. Subscription status shows installed and current CSV information.
13. Later, when catalog metadata changes and a newer bundle exists in the selected channel, OLM creates another InstallPlan.
14. Automatic approval installs the update immediately; manual approval waits for admin review.

Operationally:

```text
Subscription = desired tracking state
InstallPlan  = transaction to reach desired state
CSV          = installed operator version state
```

## 6. Subscription API anatomy

API group and kind:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
```

Subscription is a namespaced object:

```bash
oc api-resources | grep -i subscription
oc get subscriptions -A
```

Short names can vary by cluster, but commonly you can use:

```bash
oc get sub -A
```

The most important parts are:

```yaml
metadata:
  name: <subscription-name>
  namespace: <operator-install-namespace>
spec:
  channel: <channel-name>
  name: <operator-package-name>
  source: <catalogsource-name>
  sourceNamespace: <catalogsource-namespace>
  installPlanApproval: Automatic | Manual
  startingCSV: <optional-csv-name>
  config: <optional-operator-deployment-customization>
status:
  currentCSV: <csv-olm-is-progressing-to>
  installedCSV: <csv-currently-installed>
  installPlanRef: <latest-installplan-reference>
  state: <subscription-state>
  reason: <state-reason>
  conditions: <condition-list>
  catalogHealth: <catalog-health-view>
```

## 7. Basic Subscription YAML

Example using placeholders:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: openshift-operators
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

Meaning:

- Install operator package `example-operator`.
- Use the `stable` channel.
- Pull metadata from CatalogSource `redhat-operators` in namespace `openshift-marketplace`.
- Create InstallPlans but require manual approval before installation or upgrade.

## 8. Field-by-field deep dive

### 8.1 `metadata.name`

```yaml
metadata:
  name: example-operator
```

This is the name of the Subscription object. It does not have to be exactly the package name, but in production it is best to keep it close to the package name for clarity.

Good:

```yaml
metadata:
  name: file-integrity-operator
```

Bad:

```yaml
metadata:
  name: test1
```

Why naming matters:

- Easier incident troubleshooting.
- Easier GitOps inventory.
- Easier audit and compliance checks.
- Easier cleanup.

### 8.2 `metadata.namespace`

```yaml
metadata:
  namespace: openshift-operators
```

This is the namespace where the Subscription is created and where the Operator is installed.

Common patterns:

| Install pattern | Typical namespace |
|---|---|
| Cluster-wide operator | `openshift-operators` or vendor-recommended namespace |
| Red Hat platform operator | Vendor-recommended `openshift-*` namespace |
| Namespaced application operator | Dedicated namespace such as `myapp-operators` |
| Isolated tenant operator | Tenant-specific operator namespace |

Important:

- The Subscription namespace is not always the namespace where operands run.
- The OperatorGroup controls target namespaces.
- Many operators create operands in separate namespaces through their custom resources.

### 8.3 `spec.name`

```yaml
spec:
  name: example-operator
```

This is the **operator package name** as known by the catalog.

Do not guess it from the UI display name. Verify it:

```bash
oc get packagemanifests -n openshift-marketplace | grep -i example
oc describe packagemanifest example-operator -n openshift-marketplace
```

If `spec.name` is wrong, OLM cannot resolve the package.

### 8.4 `spec.source`

```yaml
spec:
  source: redhat-operators
```

This is the CatalogSource name.

Check available sources:

```bash
oc get catalogsource -n openshift-marketplace
```

A package with the same name might exist in multiple catalogs. For example, a community package and a certified package can have similar names. In production, explicitly select the correct catalog.

### 8.5 `spec.sourceNamespace`

```yaml
spec:
  sourceNamespace: openshift-marketplace
```

This is the namespace where the CatalogSource exists.

Default catalog namespace is normally:

```text
openshift-marketplace
```

In disconnected clusters, custom catalog sources might exist in another namespace, for example:

```text
openshift-marketplace
olm
operator-registry
custom-catalogs
```

Never assume. Verify:

```bash
oc get catalogsource -A
```

### 8.6 `spec.channel`

```yaml
spec:
  channel: stable
```

The channel is the update stream. It decides which operator versions OLM can select.

Examples of channel styles:

```text
stable
fast
candidate
preview
stable-1.2
stable-1.3
v4.16
v4.17
```

Channel names are operator-specific. There is no universal rule that every operator has `stable`.

Verify channels:

```bash
oc describe packagemanifest <operator-name> -n openshift-marketplace
```

Or inspect YAML:

```bash
oc get packagemanifest <operator-name> -n openshift-marketplace -o yaml
```

### 8.7 `spec.installPlanApproval`

```yaml
spec:
  installPlanApproval: Manual
```

Allowed values:

```text
Automatic
Manual
```

This controls whether OLM automatically approves generated InstallPlans.

| Value | Behavior |
|---|---|
| `Automatic` | OLM installs or upgrades without admin approval when an InstallPlan is generated. |
| `Manual` | OLM creates InstallPlans but waits until an admin approves them. |

Production recommendation:

- Use `Manual` for critical infrastructure operators.
- Use `Automatic` for development or low-risk operators only after risk review.
- Use `Manual` when cloud credentials, permissions, CRD changes, or API changes need review.

### 8.8 `spec.startingCSV`

```yaml
spec:
  startingCSV: example-operator.v1.2.3
```

This tells OLM which CSV version to start from.

Important behavior:

- `startingCSV` is not a permanent pin by itself.
- If a newer version exists in the selected channel and approval is Automatic, OLM can continue upgrading along the channel.
- To intentionally start at a specific version and prevent immediate upgrade, use `startingCSV` with `installPlanApproval: Manual` and do not approve later InstallPlans until ready.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operators
spec:
  channel: stable-1.2
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  startingCSV: example-operator.v1.2.3
  installPlanApproval: Manual
```

### 8.9 `spec.config`

`spec.config` customizes parts of the Operator pod/deployment that OLM manages.

Common use cases:

- Add environment variables.
- Configure proxy variables.
- Add node selectors.
- Add tolerations.
- Add resource requests and limits.
- Add annotations.
- Add affinity or anti-affinity.
- Mount volumes, secrets, or config maps.

Example:

```yaml
spec:
  config:
    env:
      - name: HTTP_PROXY
        value: http://proxy.example.com:8080
      - name: HTTPS_PROXY
        value: http://proxy.example.com:8443
      - name: NO_PROXY
        value: .cluster.local,.svc,10.0.0.0/8
    resources:
      requests:
        cpu: 100m
        memory: 256Mi
      limits:
        cpu: 500m
        memory: 512Mi
    nodeSelector:
      node-role.kubernetes.io/infra: ""
    tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

Be careful:

- `spec.config` configures the Operator workload managed by OLM, not necessarily the application operands managed by that Operator.
- Some fields are effectively immutable or difficult to change safely after installation.
- Use it only when required by your platform design.

## 9. Automatic vs Manual approval

### 9.1 Automatic approval

Example:

```yaml
spec:
  installPlanApproval: Automatic
```

Behavior:

1. OLM creates an InstallPlan.
2. OLM automatically approves it.
3. Operator install or upgrade proceeds immediately.

Advantages:

- Less operational overhead.
- Good for labs and non-production.
- Faster patch adoption.
- Useful for low-risk operators.

Risks:

- Operator updates may introduce new CRDs, RBAC, permissions, webhooks, or behavior changes.
- Upgrade can happen at an unexpected time after catalog refresh.
- A bad operator version can impact platform services.
- Multi-operator dependency resolution can create unexpected upgrade chains.

### 9.2 Manual approval

Example:

```yaml
spec:
  installPlanApproval: Manual
```

Behavior:

1. OLM creates an InstallPlan.
2. InstallPlan remains unapproved.
3. Admin reviews the InstallPlan.
4. Admin approves it.
5. OLM executes installation or upgrade.

Advantages:

- Change control friendly.
- Supports maintenance windows.
- Allows RBAC/CRD review.
- Safer for production.
- Useful for regulated environments.

Risks:

- Operators can remain outdated if nobody approves updates.
- Security fixes can be delayed.
- Requires monitoring for pending InstallPlans.

### 9.3 Senior admin rule

For production clusters:

```text
Default to Manual unless there is a strong operational reason for Automatic.
```

Use Automatic only when:

- You trust the operator lifecycle.
- You have tested it in lower environments.
- The operator is non-critical.
- You have strong observability and rollback procedures.
- The vendor explicitly recommends it for your use case.

## 10. startingCSV and version control

`startingCSV` is one of the most misunderstood fields.

### 10.1 What it does

It tells OLM the first CSV version to install from the selected channel.

Example:

```yaml
startingCSV: my-operator.v2.4.1
```

### 10.2 What it does not do

It does not permanently freeze the Operator at that version.

If your channel contains newer versions and your approval strategy allows upgrades, OLM can progress to newer CSVs.

### 10.3 How to avoid immediate upgrade

Use:

```yaml
startingCSV: my-operator.v2.4.1
installPlanApproval: Manual
```

Then approve only the InstallPlan you want.

### 10.4 When to use startingCSV

Use `startingCSV` when:

- You need to install a specific tested version.
- You are restoring a known environment.
- You are matching a certified platform baseline.
- You are performing phased upgrades.
- You are avoiding a problematic latest release.

Avoid it when:

- You simply want the latest version in a channel.
- You do not know the exact CSV name.
- The version is no longer in the catalog.

### 10.5 How to find CSV names

```bash
oc describe packagemanifest <operator-name> -n openshift-marketplace
```

Or:

```bash
oc get packagemanifest <operator-name> -n openshift-marketplace -o yaml | less
```

Look for channel entries and bundle names.

## 11. Channels and update streams

A channel is an update path maintained by the operator publisher.

### 11.1 Common channel examples

```text
stable
fast
candidate
preview
alpha
beta
stable-1.0
stable-1.1
stable-v4.17
```

### 11.2 Channel selection strategy

For production:

- Prefer `stable`, `stable-x.y`, or vendor-recommended production channel.
- Avoid `alpha`, `beta`, `preview`, or `candidate` unless explicitly required.
- Match application lifecycle requirements.
- Check supported OpenShift versions.
- Check upgrade graph and skip ranges if vendor documents them.

### 11.3 Changing channels

Changing a channel can cause OLM to detect a newer CSV and create an InstallPlan.

Example patch:

```bash
oc patch subscription <subscription-name> \
  -n <operator-namespace> \
  --type merge \
  -p '{"spec":{"channel":"stable-1.3"}}'
```

Then check:

```bash
oc get subscription <subscription-name> -n <operator-namespace> -o yaml
oc get installplan -n <operator-namespace>
oc get csv -n <operator-namespace>
```

Production advice:

- Do not switch channels during business hours without a change window.
- Review release notes before changing channels.
- In Manual mode, review the generated InstallPlan before approval.
- Avoid downgrading. OLM does not treat downgrade paths as normal operator lifecycle operations.

## 12. OperatorGroup relationship

A Subscription needs an appropriate OperatorGroup in the same namespace.

### 12.1 Why OperatorGroup matters

OperatorGroup defines which namespaces the Operator targets.

OLM uses it to:

- Determine install mode compatibility.
- Generate RBAC.
- Inject target namespace information into CSVs.
- Decide whether an operator can be installed in that namespace.

### 12.2 Install modes

Operators can support one or more install modes:

| Install mode | Meaning |
|---|---|
| `OwnNamespace` | Operator watches only its own namespace. |
| `SingleNamespace` | Operator watches one selected namespace. |
| `MultiNamespace` | Operator watches multiple selected namespaces. |
| `AllNamespaces` | Operator watches all namespaces in the cluster. |

Verify install modes:

```bash
oc describe packagemanifest <operator-name> -n openshift-marketplace
```

### 12.3 AllNamespaces pattern

For many cluster-wide operators, OpenShift uses:

```text
openshift-operators
```

This namespace normally has a default global OperatorGroup.

Check:

```bash
oc get operatorgroup -n openshift-operators
oc describe operatorgroup global-operators -n openshift-operators
```

### 12.4 SingleNamespace pattern

Example:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: my-operatorgroup
  namespace: my-operators
spec:
  targetNamespaces:
    - my-operators
```

Subscription in the same namespace:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: my-operator
  namespace: my-operators
spec:
  channel: stable
  name: my-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

### 12.5 Common OperatorGroup mistakes

#### Mistake 1: No OperatorGroup

Symptom:

```text
CSV stays Pending
InstallPlan created but CSV cannot succeed
```

Check:

```bash
oc get operatorgroup -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
```

Fix:

Create the appropriate OperatorGroup.

#### Mistake 2: Multiple OperatorGroups in same namespace

Symptom:

```text
TooManyOperatorGroups
```

Fix:

Keep only one OperatorGroup in that namespace.

#### Mistake 3: OperatorGroup target namespace not matching supported install modes

Symptom:

```text
UnsupportedOperatorGroup
```

Fix:

Check operator install modes and create compatible OperatorGroup.

## 13. InstallPlan relationship

A Subscription does not directly install resources. It causes OLM to generate an InstallPlan.

### 13.1 View InstallPlans

```bash
oc get installplan -n <operator-namespace>
```

Example output:

```text
NAME            CSV                         APPROVAL    APPROVED
install-abc12   example-operator.v1.2.3     Manual      false
```

### 13.2 Describe InstallPlan

```bash
oc describe installplan install-abc12 -n <operator-namespace>
```

Look for:

- CSV to be installed.
- CRDs to be created or updated.
- ClusterRoles and Roles.
- ClusterRoleBindings and RoleBindings.
- Deployments.
- Webhooks.
- APIService.
- Status conditions.
- Failure messages.

### 13.3 Approve InstallPlan

```bash
oc patch installplan install-abc12 \
  -n <operator-namespace> \
  --type merge \
  -p '{"spec":{"approved":true}}'
```

### 13.4 Production review checklist before approval

Before approving a production InstallPlan, review:

- New or changed CRDs.
- New API versions introduced.
- RBAC escalation.
- ClusterRole and ClusterRoleBinding changes.
- Webhook additions or changes.
- APIService additions.
- Operator image digest.
- Required permissions for cloud credentials.
- Release notes and known issues.
- Impact on custom resources.
- Upgrade path compatibility.
- Backup requirements.

## 14. ClusterServiceVersion relationship

A CSV is the installed operator version object.

### 14.1 Check CSV

```bash
oc get csv -n <operator-namespace>
```

Healthy example:

```text
NAME                         DISPLAY             VERSION   REPLACES                     PHASE
example-operator.v1.2.3      Example Operator    1.2.3     example-operator.v1.2.2      Succeeded
```

### 14.2 Describe CSV

```bash
oc describe csv example-operator.v1.2.3 -n <operator-namespace>
```

Important fields:

- `Phase`
- `Reason`
- `Message`
- `Install Modes`
- `Owned CRDs`
- `Required CRDs`
- `APIServiceDefinitions`
- `Install Strategy`
- `Permissions`
- `Cluster Permissions`

### 14.3 CSV phases

Common phases:

| Phase | Meaning |
|---|---|
| `Pending` | Waiting for requirements or install plan execution. |
| `InstallReady` | Requirements resolved; ready to install. |
| `Installing` | OLM is installing resources. |
| `Succeeded` | Operator version installed successfully. |
| `Failed` | Installation failed. |
| `Replacing` | New CSV replacing old CSV. |
| `Deleting` | CSV deletion in progress. |

### 14.4 Subscription status vs CSV status

Subscription tells you what OLM wants and tracks.
CSV tells you whether the actual operator version is installed successfully.

Useful command:

```bash
oc get subscription <subscription-name> -n <operator-namespace> \
  -o jsonpath='{.status.installedCSV}{"\n"}{.status.currentCSV}{"\n"}{.status.state}{"\n"}{.status.reason}{"\n"}'
```

Interpretation:

| Field | Meaning |
|---|---|
| `installedCSV` | CSV currently installed by the Subscription. |
| `currentCSV` | CSV the Subscription is progressing toward. |
| `installPlanRef` | Latest InstallPlan reference. |
| `state` | Current Subscription state. |
| `reason` | Reason for current state. |

## 15. CatalogSource relationship

A Subscription depends on a healthy CatalogSource.

### 15.1 Check CatalogSource

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource redhat-operators -n openshift-marketplace
```

### 15.2 Check catalog pods

```bash
oc get pods -n openshift-marketplace
```

CatalogSources usually create registry pods. If those pods are failing, Subscriptions depending on that catalog may not resolve.

### 15.3 Common CatalogSource problems

- Catalog pod ImagePullBackOff.
- Mirrored catalog image missing in disconnected cluster.
- CatalogSource namespace wrong in Subscription.
- Package not present in selected catalog.
- Same package present in multiple catalogs, wrong one selected.
- Catalog metadata outdated.
- Marketplace disabled or default sources disabled.

### 15.4 Subscription status catalogHealth

Subscription status can include catalog health information. Inspect it:

```bash
oc get subscription <subscription-name> -n <operator-namespace> -o yaml
```

Look at:

```yaml
status:
  catalogHealth:
  - catalogSourceRef:
      name: redhat-operators
      namespace: openshift-marketplace
    healthy: true
```

If `healthy: false`, troubleshoot the CatalogSource and catalog pod first.

## 16. Production-grade installation workflow

A senior OpenShift administrator should not install Operators by random clicking. Use a controlled workflow.

### 16.1 Pre-install checklist

Verify the following before creating a Subscription:

```text
[ ] Operator is supported on this OpenShift version.
[ ] Operator package name is confirmed.
[ ] CatalogSource name and namespace are confirmed.
[ ] Channel is confirmed and appropriate for environment.
[ ] Install mode is confirmed.
[ ] OperatorGroup exists or will be created.
[ ] Target namespaces are correct.
[ ] Approval strategy is selected intentionally.
[ ] startingCSV is required or intentionally omitted.
[ ] Cloud credential mode is understood if applicable.
[ ] Required secrets/config maps exist.
[ ] Resource requirements are understood.
[ ] Scheduling constraints are planned if required.
[ ] Disconnected mirror catalog is tested if applicable.
[ ] Release notes and known issues are reviewed.
[ ] Backup/rollback plan exists for critical operators.
```

### 16.2 Install namespace

Create namespace:

```bash
oc create namespace my-operators
```

For OpenShift-managed operators, use vendor-recommended namespace. Do not invent namespaces for platform operators unless documentation allows it.

### 16.3 OperatorGroup

Create OperatorGroup if needed:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: my-operators-og
  namespace: my-operators
spec:
  targetNamespaces:
    - my-operators
```

Apply:

```bash
oc apply -f operatorgroup.yaml
```

### 16.4 Subscription

Create Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: my-operator
  namespace: my-operators
spec:
  channel: stable
  name: my-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

Apply:

```bash
oc apply -f subscription.yaml
```

### 16.5 Verify

```bash
oc get subscription -n my-operators
oc get installplan -n my-operators
oc get csv -n my-operators
oc get pods -n my-operators
```

If manual:

```bash
oc describe installplan <installplan-name> -n my-operators
oc patch installplan <installplan-name> -n my-operators --type merge -p '{"spec":{"approved":true}}'
```

Wait:

```bash
watch 'oc get sub,ip,csv,pods -n my-operators'
```

## 20. Using spec.config for operator pod customization

`spec.config` is advanced. It modifies the Operator workload generated by OLM.

### 20.1 Resource requests and limits

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-operators
spec:
  channel: stable
  name: example-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
  config:
    resources:
      requests:
        cpu: 100m
        memory: 256Mi
      limits:
        cpu: 500m
        memory: 512Mi
```

Use case:

- Prevent operator pods from running without requests.
- Satisfy namespace LimitRange.
- Control noisy operator resource consumption.

### 20.2 NodeSelector

```yaml
spec:
  config:
    nodeSelector:
      node-role.kubernetes.io/infra: ""
```

Use case:

- Run operator pods on infra nodes.
- Separate platform workloads from application nodes.

### 20.3 Tolerations

```yaml
spec:
  config:
    tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

Use with matching node taints.

### 20.4 Affinity

```yaml
spec:
  config:
    affinity:
      nodeAffinity:
        requiredDuringSchedulingIgnoredDuringExecution:
          nodeSelectorTerms:
            - matchExpressions:
                - key: node-role.kubernetes.io/infra
                  operator: Exists
```

Use case:

- Strong placement control.
- Ensure operator runs only on selected nodes.

### 20.5 Environment variables

```yaml
spec:
  config:
    env:
      - name: MY_OPERATOR_SETTING
        value: "true"
```

Use case:

- Operator-specific environment variables.
- Proxy variables.
- Feature flags if documented by vendor.

Do not randomly inject undocumented environment variables.

### 20.6 Proxy configuration

Example:

```yaml
spec:
  config:
    env:
      - name: HTTP_PROXY
        value: http://proxy.example.com:8080
      - name: HTTPS_PROXY
        value: http://proxy.example.com:8443
      - name: NO_PROXY
        value: .cluster.local,.svc,127.0.0.1,localhost,10.128.0.0/14,172.30.0.0/16
```

Important:

- Cluster-wide proxy may already inject proxy settings.
- Operator-specific proxy override should be documented and tested.
- Wrong `NO_PROXY` can break API server or service access.

### 20.7 Volumes and volumeMounts

Example:

```yaml
spec:
  config:
    volumes:
      - name: custom-ca
        configMap:
          name: custom-ca-bundle
    volumeMounts:
      - name: custom-ca
        mountPath: /etc/pki/ca-trust/source/anchors
        readOnly: true
```

Use case:

- Custom CAs.
- Vendor-required config files.

Be careful:

- Mount paths must not conflict with the operator image layout.
- Some operators do not expect additional volumes.
- Test before production.

### 20.8 Annotations

```yaml
spec:
  config:
    annotations:
      backup.velero.io/backup-volumes: custom-data
```

Use case:

- Backup tooling.
- Security scanning.
- Internal metadata.

### 20.9 Practical caution

Do not use `spec.config` as a workaround for poor operator design. Use it when:

- Vendor documentation requires it.
- Platform policy requires scheduling/resource controls.
- You have tested behavior during upgrade.

## 21. Disconnected / air-gapped environment considerations

In disconnected OpenShift, Subscriptions still work, but they must point to a mirrored catalog.

### 21.1 Connected cluster Subscription

```yaml
spec:
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

### 21.2 Disconnected cluster Subscription

Example:

```yaml
spec:
  source: redhat-operators-disconnected
  sourceNamespace: openshift-marketplace
```

The catalog image must be mirrored and reachable by the cluster.

### 21.3 Disconnected checklist

```text
[ ] Operator catalog image mirrored.
[ ] Operator bundle images mirrored.
[ ] Related images mirrored.
[ ] ImageContentSourcePolicy / ImageDigestMirrorSet configured as required.
[ ] Pull secret has credentials for mirror registry.
[ ] CatalogSource points to mirrored index/catalog image.
[ ] Catalog pod is running.
[ ] Package appears in PackageManifest.
[ ] Subscription source/sourceNamespace points to the mirrored CatalogSource.
```

### 21.4 Troubleshooting disconnected Subscription

Check catalog:

```bash
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
oc describe catalogsource <catalog-name> -n openshift-marketplace
```

Check package availability:

```bash
oc get packagemanifests -n openshift-marketplace | grep -i <operator>
```

Check image pulls:

```bash
oc get events -n <operator-namespace> --sort-by=.lastTimestamp
oc describe pod <pod-name> -n <operator-namespace>
```

Common issue:

```text
Subscription is correct, but InstallPlan fails because a related image was not mirrored.
```

In that case, inspect operator bundle related images and mirror configuration.

## 22. GitOps approach

A production platform should manage Operators declaratively.

### 22.1 Recommended Git structure

```text
clusters/
  prod-a/
    operators/
      logging/
        namespace.yaml
        operatorgroup.yaml
        subscription.yaml
      file-integrity/
        namespace.yaml
        operatorgroup.yaml
        subscription.yaml
      service-mesh/
        namespace.yaml
        operatorgroup.yaml
        subscription.yaml
```

### 22.2 Sync order

Apply in this order:

1. Namespace
2. OperatorGroup
3. CatalogSource if custom
4. Subscription
5. Wait for CSV Succeeded
6. Operand custom resources

In Argo CD, use sync waves:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "10"
```

Example ordering:

| Resource | Sync wave |
|---|---:|
| Namespace | `0` |
| OperatorGroup | `5` |
| Subscription | `10` |
| Custom Resources | `20` |

### 22.3 Manual approval and GitOps

Manual InstallPlans are operationally safer, but they require an approval step.

Approaches:

1. Manual human approval using `oc patch` after review.
2. Controlled pipeline approves InstallPlans after policy checks.
3. Use Automatic in lower environments and Manual in production.
4. Use notifications for pending InstallPlans.

### 22.4 GitOps anti-patterns

Avoid:

- Creating Subscription and operand CR in the same sync wave.
- Relying on the web console for production state.
- Using Automatic approval for critical operators without change control.
- Installing many unrelated operators into one namespace without understanding dependency resolution.
- Hardcoding channels without lifecycle review.

## 23. Uninstall behavior

Deleting a Subscription does not always remove everything you expect.

### 23.1 Standard CLI uninstall

1. Identify current CSV:

```bash
oc get subscription <subscription-name> -n <operator-namespace> -o yaml | grep currentCSV
```

Or:

```bash
CSV=$(oc get subscription <subscription-name> -n <operator-namespace> -o jsonpath='{.status.currentCSV}')
echo $CSV
```

2. Delete Subscription:

```bash
oc delete subscription <subscription-name> -n <operator-namespace>
```

3. Delete CSV:

```bash
oc delete csv $CSV -n <operator-namespace>
```

### 23.2 What remains after uninstall?

Often remaining resources include:

- Custom resources created by users.
- CRDs.
- Operand workloads.
- PVCs.
- Secrets and ConfigMaps.
- External cloud resources.
- Finalizers.

Production warning:

> Deleting an Operator does not necessarily delete the applications or infrastructure it managed.

Always read operator-specific uninstall documentation.

### 23.3 Cleanup order

General safe order:

1. Delete or scale down operands using operator CRs.
2. Wait for operator to clean managed resources.
3. Delete custom resources.
4. Delete Subscription.
5. Delete CSV.
6. Delete CRDs only if no longer required.
7. Delete namespace if dedicated and empty.

## 25. Common failure scenarios and fixes

### 25.1 Wrong package name

Symptom:

```text
No InstallPlan created
Subscription does not progress
```

Check:

```bash
oc get packagemanifests -n openshift-marketplace | grep -i <name>
```

Fix:

Use exact package name from PackageManifest.

### 25.2 Wrong CatalogSource

Symptom:

```text
Package not found
Catalog unhealthy
No resolution
```

Check:

```bash
oc get catalogsource -A
oc get packagemanifest <operator-name> -n openshift-marketplace -o yaml
```

Fix:

Correct `spec.source` and `spec.sourceNamespace`.

### 25.3 CatalogSource unhealthy

Symptom:

```yaml
status:
  catalogHealth:
  - healthy: false
```

Check:

```bash
oc get pods -n openshift-marketplace
oc describe catalogsource <catalog-name> -n openshift-marketplace
```

Fix:

- Fix catalog image pull.
- Fix mirror registry access.
- Fix CatalogSource image.
- Restore marketplace source.

### 25.4 Missing OperatorGroup

Symptom:

```text
CSV Pending
No compatible OperatorGroup
```

Check:

```bash
oc get operatorgroup -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
```

Fix:

Create compatible OperatorGroup.

### 25.5 Multiple OperatorGroups

Symptom:

```text
TooManyOperatorGroups
```

Fix:

Remove extra OperatorGroups. Keep one per operator installation namespace.

### 25.6 Unsupported install mode

Symptom:

```text
UnsupportedOperatorGroup
```

Example cause:

- Operator supports `SingleNamespace`, but OperatorGroup targets all namespaces.
- Operator supports `AllNamespaces`, but you attempted unsupported MultiNamespace.

Fix:

Check install modes and adjust OperatorGroup.

### 25.7 InstallPlan pending approval

Symptom:

```text
InstallPlan APPROVED=false
Subscription appears stuck
```

Fix:

```bash
oc patch installplan <name> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

### 25.8 Dependency resolution failed

Symptom:

```text
ConstraintsNotSatisfiable
```

Possible causes:

- Required CRD not available.
- Conflicting CSV owns the same CRD.
- Incompatible operator versions in same namespace.
- Dependency not present in catalog.

Fix:

- Inspect InstallPlan and CSV messages.
- Check required APIs.
- Avoid conflicting operators in same namespace.
- Use correct channel and catalog.
- Install required dependency operator if documented.

### 25.9 CSV failed

Symptom:

```text
CSV Phase: Failed
```

Check:

```bash
oc describe csv <csv-name> -n <operator-namespace>
oc get events -n <operator-namespace> --sort-by=.lastTimestamp
oc get pods -n <operator-namespace>
oc logs deploy/<operator-deployment> -n <operator-namespace>
```

Fix depends on reason:

- RBAC issue: inspect service account and roles.
- ImagePullBackOff: fix registry access.
- CrashLoopBackOff: inspect logs and config.
- Webhook/APIService issue: check service, CA, endpoints.
- LimitRange/ResourceQuota issue: add resource requests or increase quota.

### 25.10 ImagePullBackOff in disconnected cluster

Symptom:

```text
ImagePullBackOff
ErrImagePull
```

Fix:

- Mirror missing operator or related images.
- Update mirror config.
- Fix pull secret.
- Validate catalog uses mirrored references.

### 25.11 ResourceQuota blocks operator

Symptom:

```text
exceeded quota
failed quota
```

Fix:

- Add resource requests in Subscription `spec.config.resources` if required.
- Increase namespace ResourceQuota.
- Use dedicated operator namespace.

### 25.12 LimitRange requires requests

Symptom:

```text
must specify cpu request
must specify memory request
```

Fix:

Set `spec.config.resources` in Subscription or adjust LimitRange.

### 25.13 Subscription updated but operator pod not changing

Possible reasons:

- Field is immutable.
- OLM does not apply the change to existing deployment as expected.
- CSV needs replacement.
- Operator manages its own deployment after install.

Fix:

- Read operator documentation.
- Check CSV install strategy.
- Test in non-production.
- Avoid relying on mutable Subscription config after initial install.

### 25.14 Subscription deleted but operator still visible

Cause:

Deleting Subscription alone does not always delete CSV and operator resources.

Fix:

Delete CSV after Subscription:

```bash
oc delete csv <csv-name> -n <operator-namespace>
```

### 25.15 CRDs remain after uninstall

This is normal for many operators.

Fix:

Only delete CRDs after ensuring no custom resources or dependent applications remain.

```bash
oc get crd | grep -i <operator>
```

## 26. Production best practices

### 26.1 Use Manual approval for critical operators

Critical examples:

- Logging
- Service Mesh
- GitOps
- Storage / ODF
- Monitoring extensions
- Security/compliance operators
- Networking operators
- Database operators

### 26.2 Keep operator namespaces clean

Avoid putting unrelated operators into the same namespace unless the vendor recommends it.

Benefits:

- Cleaner RBAC.
- Fewer dependency conflicts.
- Easier troubleshooting.
- Easier uninstall.
- Easier GitOps ownership.

### 26.3 Always verify package metadata before install

```bash
oc describe packagemanifest <operator-name> -n openshift-marketplace
```

Check:

- Catalog
- Channel
- Version
- Install modes

### 26.4 Use vendor-recommended namespaces

Some Red Hat operators expect specific namespaces, for example:

```text
openshift-logging
openshift-storage
openshift-gitops-operator
openshift-file-integrity
```

Do not change namespace unless documentation allows.

### 26.5 Avoid Automatic in production without monitoring

If you use Automatic:

- Monitor CSV changes.
- Monitor operator pod restarts.
- Monitor CRD changes.
- Have rollback or mitigation plan.
- Track catalog update windows.

### 26.6 Monitor pending InstallPlans

```bash
oc get installplan -A | awk '$4 == "false" {print}'
```

Better:

```bash
oc get installplan -A -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,CSV:.spec.clusterServiceVersionNames[*],APPROVAL:.spec.approval,APPROVED:.spec.approved'
```

### 26.7 Track installed Operator versions

```bash
oc get csv -A
```

Custom view:

```bash
oc get csv -A -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,VERSION:.spec.version,PHASE:.status.phase'
```

### 26.8 Keep Operator lifecycle separate from operand lifecycle

Operator installation is not the same as application deployment.

Example:

- Installing Logging Operator does not mean logging storage is configured.
- Installing ODF Operator does not mean StorageCluster exists.
- Installing GitOps Operator does not mean Argo CD instance is configured.

Subscription installs the Operator. Custom Resources configure the operand.

### 26.9 Review RBAC before approval

Operators often need powerful permissions.

Before approving InstallPlan:

```bash
oc get installplan <name> -n <namespace> -o yaml
```

Look for ClusterRoles and ClusterRoleBindings.

### 26.10 Treat CRD upgrades carefully

CRD upgrades can affect:

- API versions.
- Validation schemas.
- Conversion webhooks.
- Existing custom resources.
- Backup and restore.

Before upgrade:

```bash
oc get crd | grep -i <operator>
oc get <custom-resource-kind> -A
```

Back up critical custom resources:

```bash
oc get <resource> -A -o yaml > backup.yaml
```

### 26.11 Use lower environments

Promote operator updates through:

```text
dev -> test -> staging -> production
```

Track:

- Subscription channel.
- CSV version.
- Operand CR versions.
- Known issues.
- Rollback approach.

## 28. Interview-level explanation

### 28.1 Simple explanation

A Subscription is an OLM resource that subscribes a namespace to an Operator package from a CatalogSource. It specifies the channel and approval strategy. OLM uses it to create InstallPlans and install or upgrade the Operator through CSVs.

### 28.2 Senior explanation

A Subscription is the lifecycle tracking object for an OLM-managed Operator. It binds an operator package name to a CatalogSource and update channel, then allows OLM to resolve the desired bundle and produce InstallPlans. The InstallPlan execution results in a CSV, which owns the operator deployment, CRDs, RBAC, webhooks, and related resources. In production, the Subscription approval strategy controls change management: Automatic approves updates immediately, while Manual creates a pending InstallPlan for administrator review. Subscription health must be interpreted together with CatalogSource health, OperatorGroup compatibility, InstallPlan status, and CSV phase.

### 28.3 30-second answer

> In OpenShift, a Subscription is a namespaced OLM custom resource used to install and update Operators. It tells OLM which operator package to install, from which CatalogSource, through which channel, and whether InstallPlans should be approved automatically or manually. It does not directly run the Operator; it drives OLM to create an InstallPlan, install a CSV, and deploy the Operator. For production, I normally use Manual approval, review the InstallPlan for CRD/RBAC changes, then approve it during a maintenance window.

## 29. Command cheat sheet

### List Subscriptions

```bash
oc get subscription -A
oc get sub -A
```

### Describe Subscription

```bash
oc describe subscription <subscription-name> -n <namespace>
```

### Get Subscription YAML

```bash
oc get subscription <subscription-name> -n <namespace> -o yaml
```

### List packages

```bash
oc get packagemanifests -n openshift-marketplace
```

### Inspect package

```bash
oc describe packagemanifest <operator-name> -n openshift-marketplace
```

### List CatalogSources

```bash
oc get catalogsource -A
```

### List OperatorGroups

```bash
oc get operatorgroup -A
```

### List InstallPlans

```bash
oc get installplan -A
```

### Approve InstallPlan

```bash
oc patch installplan <installplan-name> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

### List CSVs

```bash
oc get csv -A
```

### Watch install status

```bash
watch 'oc get sub,ip,csv,pods -n <operator-namespace>'
```

### Get installed and current CSV

```bash
oc get subscription <subscription-name> -n <namespace> \
  -o jsonpath='{.status.installedCSV}{"\n"}{.status.currentCSV}{"\n"}'
```

### Patch approval strategy

```bash
oc patch subscription <subscription-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"installPlanApproval":"Manual"}}'
```

### Patch channel

```bash
oc patch subscription <subscription-name> -n <namespace> \
  --type merge \
  -p '{"spec":{"channel":"stable-1.3"}}'
```

### Delete Subscription and CSV

```bash
CSV=$(oc get subscription <subscription-name> -n <namespace> -o jsonpath='{.status.currentCSV}')
oc delete subscription <subscription-name> -n <namespace>
oc delete csv "$CSV" -n <namespace>
```

## Final senior-admin takeaway

A Subscription is small YAML, but it controls a large production lifecycle. A wrong channel, wrong catalog, wrong OperatorGroup, or careless Automatic approval can create serious platform risk. Treat Subscription changes like package repository and lifecycle changes on a critical Linux system: verify source, version stream, dependencies, transaction plan, and rollback path before execution.
