# RWO, RWX, ROX in OpenShift Storage and Backup Awareness

**Audience:** Advanced OpenShift Administration / DO380-level storage operations  
**Experience level:** Designed for administrators with ~10 years of Linux, DevOps, Kubernetes, and OpenShift experience  
**Focus:** PersistentVolume access modes, workload placement, CSI behavior, backup/restore impact, troubleshooting, and production design decisions

---

## 1. Executive Summary

In OpenShift, **RWO**, **RWX**, and **ROX** are PersistentVolume access modes. They describe how a PersistentVolume can be mounted by nodes in the cluster.

| Short Name | Full Name | Meaning | Typical Storage Type | Common Use Case |
|---|---|---|---|---|
| `RWO` | `ReadWriteOnce` | Read-write mount by **one node** at a time | Block storage such as EBS, vSphere disk, Ceph RBD, iSCSI, FC, LVM/local PV | Databases, single-writer apps, StatefulSets |
| `RWX` | `ReadWriteMany` | Read-write mount by **many nodes** at the same time | Shared filesystem such as NFS, CephFS, Azure File, AWS EFS, ODF CephFS | Shared uploads, HA web content, shared app data |
| `ROX` | `ReadOnlyMany` | Read-only mount by **many nodes** at the same time | NFS, CephFS, object-backed file gateway, read-only exported filesystem | Shared static content, reference data, model files, golden data |

The most important production point is this:

> **Access mode is a scheduling and mount capability. It is not a complete application-level data-safety model.**

For example, `RWX` means multiple nodes can mount the volume read-write, but it does **not** mean your application is safe to perform concurrent writes. The application, filesystem, and storage backend must still support correct locking, consistency, and concurrency.

## 2. Where Access Modes Fit in the OpenShift Storage Model

OpenShift uses the Kubernetes PersistentVolume framework:

- **PersistentVolume (PV):** Cluster-level storage object representing real storage.
- **PersistentVolumeClaim (PVC):** Namespace-scoped request for storage by an application or developer.
- **StorageClass:** Defines dynamic provisioning behavior, backend driver, reclaim policy, expansion behavior, binding mode, and driver-specific parameters.
- **CSI driver:** Storage plugin that handles dynamic provisioning, attach, mount, expansion, snapshots, and sometimes cloning.

A typical flow is:

1. Admin creates or installs a storage backend and StorageClass.
2. User creates a PVC with size, access mode, and StorageClass.
3. OpenShift binds the PVC to an existing PV or dynamically provisions a new PV.
4. Pod references the PVC.
5. Kubelet and CSI node plugin mount the volume onto the selected node.
6. Container mounts the volume path into the container filesystem.

Example PVC request:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  namespace: production
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-rwo
  resources:
    requests:
      storage: 20Gi
```

The access mode requested by the PVC must be supported by the StorageClass/backend. If no matching PV can be created or found, the PVC remains `Pending`.

---

## 3. Critical Mental Model: Node-Level, Not Container-Level

A common misunderstanding is:

> “RWO means only one pod can use the PVC.”

That is not exactly correct.

`ReadWriteOnce` means the volume can be mounted read-write by **one node** at a time. Multiple pods can use the same RWO PVC **if they run on the same node** and if the platform/backend allows the mount pattern.

That distinction matters during:

- Deployment scaling
- Rolling updates
- StatefulSet failover
- Node drain
- Zone-aware scheduling
- Backup jobs
- Multi-attach troubleshooting

For true **single-pod** semantics, Kubernetes has `ReadWriteOncePod` (`RWOP`). This is different from `RWO`. `RWOP` is intended when only one pod in the entire cluster should be able to use the PVC read-write.

## 4. Access Mode Comparison in Detail

## 4.1 ReadWriteOnce (`RWO`)

### Definition

`RWO` means:

> The volume can be mounted as read-write by a single node at a time.

It is the most common access mode for block storage.

### Typical Backends

Common RWO-capable storage includes:

- AWS EBS CSI
- Google Persistent Disk CSI
- Azure Disk CSI
- VMware vSphere CSI
- OpenShift Data Foundation Ceph RBD
- iSCSI
- Fibre Channel
- Local Storage Operator PVs
- LVM Storage / LVMS-style local block volumes

### Production Use Cases

Use `RWO` for workloads that need a private disk:

- PostgreSQL
- MySQL/MariaDB
- MongoDB single replica or per-replica disks
- Redis persistence
- Kafka broker data directories
- Elasticsearch/OpenSearch node data
- Prometheus TSDB
- Quay database component
- Application data where only one replica should write

### Good Workload Pattern

For RWO, prefer **StatefulSet** over Deployment when the application has identity and persistent data.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: database
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: registry.redhat.io/rhel8/mysql-80
          volumeMounts:
            - name: mysql-data
              mountPath: /var/lib/mysql/data
  volumeClaimTemplates:
    - metadata:
        name: mysql-data
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: fast-rwo
        resources:
          requests:
            storage: 20Gi
```

Each replica receives its own PVC:

```bash
oc get pvc -n database
```

Expected style of output:

```text
mysql-data-mysql-0   Bound   pvc-...   20Gi   RWO   fast-rwo
mysql-data-mysql-1   Bound   pvc-...   20Gi   RWO   fast-rwo
mysql-data-mysql-2   Bound   pvc-...   20Gi   RWO   fast-rwo
```

This is correct because every database replica has its own disk.

### Bad Workload Pattern

This is dangerous:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shared-rwo-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: shared-rwo-app
  template:
    metadata:
      labels:
        app: shared-rwo-app
    spec:
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi
          command: ["sleep", "infinity"]
          volumeMounts:
            - name: data
              mountPath: /data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: one-rwo-pvc
```

Why this is risky:

- If all replicas land on one node, they might start.
- If a replica schedules on another node, attach/mount might fail.
- During rolling updates, OpenShift may create a new pod before the old pod fully releases the volume.
- During node failure, detach/attach can take time.
- On cloud block storage, the volume is usually attached to only one node.

Common error patterns:

```text
Multi-Attach error for volume "pvc-..." Volume is already exclusively attached to one node
```

or:

```text
Unable to attach or mount volumes: timed out waiting for the condition
```

### RWO and StatefulSet Behavior

A StatefulSet does not magically make RWO shared. It makes the design correct by giving each replica its own PVC. For example:

- `mysql-0` uses `mysql-data-mysql-0`
- `mysql-1` uses `mysql-data-mysql-1`
- `mysql-2` uses `mysql-data-mysql-2`

This matches the RWO model.

### RWO and Node Drain

During maintenance:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

For RWO workloads:

1. Pod is evicted from old node.
2. Volume must detach from old node.
3. Pod schedules to new node.
4. Volume attaches and mounts to new node.

Issues can occur if:

- Old node is unreachable.
- Cloud provider detach is slow.
- CSI attacher sees stale attachment metadata.
- PodDisruptionBudget blocks eviction.
- Workload has strict topology constraints.

Useful commands:

```bash
oc get pods -A -o wide | grep <pvc-or-app>
oc describe pod <pod> -n <namespace>
oc describe pvc <pvc> -n <namespace>
oc get volumeattachment
oc describe volumeattachment <name>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### RWO and Topology

Many block storage providers are zone-bound. A disk created in zone `a` cannot attach to a node in zone `b`.

Check StorageClass:

```bash
oc get sc <storageclass> -o yaml
```

Important fields:

```yaml
volumeBindingMode: WaitForFirstConsumer
allowedTopologies:
  - matchLabelExpressions:
      - key: topology.kubernetes.io/zone
        values:
          - zone-a
```

`WaitForFirstConsumer` delays provisioning until a pod is scheduled, allowing the scheduler to consider node topology before the PV is created.

### RWO Backup Awareness

For RWO databases, never assume filesystem snapshot equals application-consistent backup.

Backup options:

1. **CSI snapshot:** Fast, crash-consistent unless application quiescing is added.
2. **Database-native dump:** `pg_dump`, `mysqldump`, `mariabackup`, `xtrabackup`, etc.
3. **Filesystem-level backup:** Works best when app is stopped or quiesced.
4. **Velero/OADP with CSI snapshots:** Good for cluster-aware backup workflows, but application consistency still needs planning.

Recommended for production databases:

- Use database-native backup for logical recovery.
- Use CSI snapshots for fast rollback or crash-consistent volume restore.
- Test restore regularly.
- Do not call a snapshot a backup unless it is copied outside the failure domain.

### RWO Admin Checklist

```bash
# PVC access mode
oc get pvc -n <ns>

# Bound PV details
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.volumeName}{"\n"}'
oc get pv <pv> -o yaml

# Which node is using it
oc get pod -n <ns> -o wide

# Attach status
oc get volumeattachment

# StorageClass behavior
oc get sc <sc> -o yaml

# CSI driver objects
oc get csidriver
oc get csinode
```

## 4.2 ReadWriteMany (`RWX`)

### Definition

`RWX` means:

> The volume can be mounted as read-write by many nodes at the same time.

This usually requires shared filesystem storage.

### Typical Backends

Common RWX-capable storage includes:

- NFS
- CephFS
- OpenShift Data Foundation CephFS
- AWS EFS CSI
- Azure File CSI
- Some enterprise NAS platforms through CSI drivers
- GlusterFS in older environments

Block disks are normally not RWX unless exposed through a clustered filesystem or special storage layer that supports multi-node read-write safely.

### Production Use Cases

Use `RWX` for:

- Shared web uploads
- Shared CMS media directories
- Shared reports/export directories
- CI/CD shared cache
- Read-write shared application files
- OpenShift image registry in HA mode, if using a suitable shared backend
- Application data where multiple pods need simultaneous read/write access

### Good Workload Pattern

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-content
  namespace: web
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: ocs-storagecluster-cephfs
  resources:
    requests:
      storage: 50Gi
```

Deployment using the shared PVC:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-content
  namespace: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-content
  template:
    metadata:
      labels:
        app: web-content
    spec:
      containers:
        - name: nginx
          image: registry.access.redhat.com/ubi9/nginx-120
          volumeMounts:
            - name: content
              mountPath: /opt/app-root/src/content
      volumes:
        - name: content
          persistentVolumeClaim:
            claimName: shared-content
```

All replicas can run on different nodes and mount the same PVC.

### RWX Does Not Mean Write-Safe

RWX only says the storage can be mounted read-write by many nodes. It does not solve:

- Application-level file locking
- Race conditions
- Split-brain writes
- Corruption from non-cluster-aware applications
- Cache coherency problems
- Database transaction consistency

Bad idea:

> Running three independent MySQL pods writing to the same RWX directory.

Good idea:

> Running three web pods reading and writing user-uploaded files on a shared filesystem, assuming the application handles file naming and locking correctly.

### RWX Performance Considerations

RWX often has different performance behavior from RWO block storage.

Watch for:

- Metadata-heavy workloads: many small files, frequent stat/list operations
- Lock-heavy workloads
- High concurrent writes
- Latency-sensitive databases
- Cross-zone network latency
- NFS server bottlenecks
- CephFS MDS saturation
- EFS throughput mode limits

Commands:

```bash
# Check PVC and PV
oc get pvc -n <ns>
oc get pv <pv> -o yaml

# Check pod placement
oc get pod -n <ns> -o wide

# Check application-level write behavior
oc rsh -n <ns> <pod-a>
oc rsh -n <ns> <pod-b>
```

Test from multiple pods:

```bash
# Pod A
hostname > /shared/pod-a.txt

# Pod B
cat /shared/pod-a.txt
hostname > /shared/pod-b.txt

# Pod A
cat /shared/pod-b.txt
```

### RWX and Permissions in OpenShift

OpenShift runs containers with restricted security defaults. Random UIDs are common. Shared filesystems must allow the container UID or group to write.

Common symptoms:

```text
Permission denied
Read-only file system
Operation not permitted
```

Useful checks:

```bash
oc rsh <pod>
id
ls -ld /mount/path
touch /mount/path/test
```

Security context example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rwx-app
spec:
  template:
    spec:
      securityContext:
        fsGroup: 1000710000
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi
          command: ["sleep", "infinity"]
          volumeMounts:
            - name: shared
              mountPath: /shared
      volumes:
        - name: shared
          persistentVolumeClaim:
            claimName: shared-content
```

Notes:

- `fsGroup` may help with group ownership on supported backends.
- NFS root-squash can prevent root-owned writes.
- SELinux labeling behavior differs by backend and OpenShift version.
- Some CSI drivers support mount options that affect UID/GID mapping.
- Do not solve all storage permission issues by using privileged pods. Fix ownership and SCC design properly.

### RWX Backup Awareness

RWX backup is tricky because many pods can write at the same time.

For consistent backups:

1. Identify all writers.
2. Stop or quiesce writes.
3. Take snapshot or backup.
4. Resume writes.
5. Validate restore.

For simple static content, file-level backup may be enough. For active shared application data, coordinate with the application.

Possible backup approaches:

- CSI snapshot if the CSI driver supports snapshots for the RWX backend.
- File-level backup using backup agents.
- Application-aware export.
- Storage-native replication.
- OADP/Velero for Kubernetes objects plus volume data.

Important:

> A RWX snapshot taken while multiple pods are writing is usually crash-consistent at best unless the application is quiesced.

### RWX Admin Checklist

```bash
# Confirm RWX request
oc get pvc -n <ns>

# Confirm backend driver
oc get pv <pv> -o jsonpath='{.spec.csi.driver}{"\n"}'

# Confirm all pods mounting it
oc get pods -n <ns> -o wide
oc describe pod <pod> -n <ns> | grep -A20 Volumes

# Test write from multiple pods
oc rsh -n <ns> <pod1> 'date >> /shared/test.txt'
oc rsh -n <ns> <pod2> 'cat /shared/test.txt'

# Check events
oc get events -n <ns> --sort-by=.lastTimestamp
```

## 4.3 ReadOnlyMany (`ROX`)

### Definition

`ROX` means:

> The volume can be mounted read-only by many nodes at the same time.

It is useful when many workloads need the same data but should not modify it.

### Typical Backends

ROX can be provided by:

- NFS read-only export
- CephFS read-only mount capability
- Preloaded shared filesystem
- Static PV with read-only backend export
- Storage backend snapshots mounted as read-only volumes, depending on provider

### Production Use Cases

Use `ROX` for:

- Static website content
- Shared software binaries
- Golden configuration bundles
- Machine learning model artifacts
- Reference datasets
- Compliance policy bundles
- Read-only reports
- Shared documentation
- Data distributed to many pods without write access

### Example ROX PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: reference-data
  namespace: analytics
spec:
  accessModes:
    - ReadOnlyMany
  storageClassName: shared-rox
  resources:
    requests:
      storage: 100Gi
```

Pod mount:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: analytics-reader
  namespace: analytics
spec:
  containers:
    - name: reader
      image: registry.access.redhat.com/ubi9/ubi
      command: ["sleep", "infinity"]
      volumeMounts:
        - name: reference
          mountPath: /mnt/reference
          readOnly: true
  volumes:
    - name: reference
      persistentVolumeClaim:
        claimName: reference-data
        readOnly: true
```

### ROX Important Nuance

Do not rely only on `accessModes: ReadOnlyMany` for write protection in every situation.

Use layered protection:

1. PV/PVC access mode: `ReadOnlyMany`
2. Pod volume reference: `readOnly: true`
3. Container `volumeMounts`: `readOnly: true`
4. Backend export/mount configured read-only
5. Application user permissions prevent writes

A strong ROX design ensures read-only behavior at the Kubernetes layer and at the storage backend.

### ROX Backup Awareness

ROX is usually easiest to back up because workloads should not write to it.

Backup patterns:

- Backup the source/golden dataset before publishing.
- Rebuild ROX volume from artifact repository when possible.
- Use object storage or Git as source of truth for static content.
- Use CSI snapshot if supported.
- Use checksum validation after restore.

Example checksum validation:

```bash
oc rsh -n analytics analytics-reader -- sha256sum /mnt/reference/model.bin
```

### ROX Admin Checklist

```bash
# Confirm access mode
oc get pvc reference-data -n analytics

# Confirm pod mounts as read-only
oc describe pod analytics-reader -n analytics | grep -A20 Mounts

# Test write should fail
oc rsh -n analytics analytics-reader -- touch /mnt/reference/should-fail

# Check backend export if using NFS
showmount -e <nfs-server>
```

## 5. Access Modes vs Volume Modes

Do not confuse **accessModes** with **volumeMode**.

### accessModes

Defines mount sharing capability:

```yaml
accessModes:
  - ReadWriteOnce
```

### volumeMode

Defines how the volume is presented:

```yaml
volumeMode: Filesystem
```

or:

```yaml
volumeMode: Block
```

### Filesystem Mode

Most common. The volume is formatted and mounted as a filesystem.

```yaml
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Filesystem
```

### Block Mode

The raw block device is exposed into the container.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: raw-block-pvc
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Block
  storageClassName: fast-block
  resources:
    requests:
      storage: 10Gi
```

Pod using block device:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: block-pod
spec:
  containers:
    - name: app
      image: registry.access.redhat.com/ubi9/ubi
      command: ["sleep", "infinity"]
      volumeDevices:
        - name: blockvol
          devicePath: /dev/xvda
  volumes:
    - name: blockvol
      persistentVolumeClaim:
        claimName: raw-block-pvc
```

Block mode is usually RWO and used by specialized applications that manage their own filesystem or raw device layout.

## 6. Storage Backend Capability Matrix

| Backend | RWO | RWX | ROX | Notes |
|---|---:|---:|---:|---|
| AWS EBS | Yes | No | Limited / driver-specific | Block disk, zone-bound |
| AWS EFS | Yes | Yes | Yes | Shared filesystem |
| Azure Disk | Yes | No | Limited / driver-specific | Block disk |
| Azure File | Yes | Yes | Yes | SMB/NFS-style shared storage depending config |
| vSphere CSI | Yes | Usually no | Limited | Block disk; topology matters |
| ODF Ceph RBD | Yes | No | Often read-only capability depends design | Block storage |
| ODF CephFS | Yes | Yes | Yes | Shared filesystem |
| NFS | Yes | Yes | Yes | Depends export options |
| iSCSI | Yes | No | Yes in some cases | Block protocol |
| Fibre Channel | Yes | No | Yes in some cases | Block protocol |
| Local PV | Yes | No | Usually no | Node-bound storage |

Always verify your actual StorageClass and CSI driver documentation. CSI behavior is driver-specific.

## 7. How Binding Works with Access Modes

For static PVs, access mode participates in matching.

Example static PV:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-rwx-pv
spec:
  capacity:
    storage: 100Gi
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 192.168.10.20
    path: /exports/appdata
```

PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: appdata
  namespace: app
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 50Gi
```

The PVC can bind because:

- PV capacity is sufficient.
- Access mode matches.
- StorageClass/selector constraints match or are absent.

If the PVC asks for `ReadWriteMany` but only RWO PVs exist, it remains `Pending`.

Check:

```bash
oc describe pvc appdata -n app
```

Look for events such as:

```text
no persistent volumes available for this claim and no storage class is set
```

or:

```text
waiting for a volume to be created, either by external provisioner ... or manually created by system administrator
```

## 8. Dynamic Provisioning and Access Modes

With dynamic provisioning, the StorageClass provisioner decides whether it can satisfy the requested access mode.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-rwo
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete
```

PVC requesting RWX from this class may fail or remain pending because AWS EBS does not normally provide RWX filesystem sharing.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: wrong-access-mode
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: fast-rwo
  resources:
    requests:
      storage: 10Gi
```

Typical fix:

- Use an RWX-capable StorageClass such as EFS, CephFS, Azure File, or NFS.
- Or redesign the app so each replica has its own RWO PVC.

## 9. Choosing the Right Access Mode

## 9.1 Decision Tree

Ask these questions:

### Question 1: Does more than one pod need to write to the same files at the same time?

- Yes: consider `RWX`.
- No: use `RWO` for private app data.

### Question 2: Does more than one node need to read the same data without writing?

- Yes: consider `ROX`.
- No: `RWO` is probably enough.

### Question 3: Is the workload a database?

- Normal single-instance database: `RWO`.
- Clustered database with each member having its own disk: StatefulSet + RWO PVC per replica.
- Database sharing one directory across replicas: avoid unless the database explicitly supports it.

### Question 4: Do you need HA replicas with shared uploads?

- Usually `RWX`.
- Alternative: store uploads in object storage instead of filesystem.

### Question 5: Is data a versioned artifact?

- Prefer image layer, object storage, Git, ConfigMap, or ROX volume.

## 10. Practical Design Patterns

## 10.1 Database StatefulSet with RWO

Best for:

- PostgreSQL
- MySQL
- Redis
- Kafka

Pattern:

```text
StatefulSet replica 0 -> PVC 0 -> RWO PV 0
StatefulSet replica 1 -> PVC 1 -> RWO PV 1
StatefulSet replica 2 -> PVC 2 -> RWO PV 2
```

Benefits:

- Clear data ownership
- Predictable identity
- Safer failover
- Easier backup per replica

## 10.2 Web Farm with RWX

Best for:

- Multiple web pods sharing media directory
- Legacy apps expecting shared filesystem

Pattern:

```text
Pod A -> shared RWX PVC
Pod B -> shared RWX PVC
Pod C -> shared RWX PVC
```

Risks:

- Shared filesystem bottleneck
- Lock contention
- Permission problems
- Concurrent writes

## 10.3 Static Content with ROX

Best for:

- Model files
- Static website build output
- Compliance bundles
- Shared read-only data

Pattern:

```text
Build pipeline publishes data -> ROX volume or read-only export -> many pods consume
```

Benefits:

- Simple consistency
- Safe sharing
- Easy cache distribution

## 10.4 Object Storage Instead of RWX

Sometimes the best RWX design is no RWX filesystem.

For uploads, reports, artifacts, and backups, consider:

- S3-compatible object storage
- OpenShift Data Foundation NooBaa / Multicloud Object Gateway
- External object storage
- Application-level object storage integration

Benefits:

- Better horizontal scalability
- Avoids POSIX locking issues
- Better cross-region backup patterns
- Easier lifecycle policies

## 11. Backup and Restore Deep Dive by Access Mode

## 11.1 Backup Principles

A good OpenShift backup includes:

1. Kubernetes objects: Deployments, StatefulSets, Services, Routes, ConfigMaps, Secrets, RBAC, Operators, CRs.
2. Persistent data: PVC contents, snapshots, file backups, database dumps.
3. External dependencies: DNS, load balancer, external DB, object storage, identity provider.
4. Restore procedure: Tested, documented, automated where possible.

Snapshots are useful, but:

> A snapshot is not automatically a full backup strategy.

If the snapshot exists only on the same storage system, it may not protect against storage backend failure, accidental deletion, ransomware, or site-level disaster.

## 11.2 CSI VolumeSnapshot Basics

A CSI snapshot workflow normally uses:

- `VolumeSnapshotClass`
- `VolumeSnapshot`
- `VolumeSnapshotContent`
- Source PVC
- Restored PVC using `dataSource`

Example snapshot:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-data-snap-001
  namespace: database
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: mysql-data-mysql-0
```

Check:

```bash
oc get volumesnapshot -n database
oc describe volumesnapshot mysql-data-snap-001 -n database
```

Restore to a new PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-restore
  namespace: database
spec:
  storageClassName: fast-rwo
  dataSource:
    name: mysql-data-snap-001
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

Check:

```bash
oc get pvc mysql-data-restore -n database
```

## 11.3 RWO Backup Strategy

Recommended for databases:

```text
Application quiesce or database backup mode
        ↓
CSI snapshot or database-native backup
        ↓
Copy backup outside cluster/storage fault domain
        ↓
Validate restore into separate namespace
```

Example MySQL logical backup job pattern:

```bash
oc exec -n database mysql-0 -- \
  mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --all-databases > mysql-backup.sql
```

For filesystem snapshot consistency:

- Flush database buffers.
- Pause writes if supported.
- Take snapshot.
- Resume writes.
- Verify snapshot restore.

## 11.4 RWX Backup Strategy

For RWX, coordinate all writers.

Options:

- Scale app to zero briefly.
- Put app in maintenance/read-only mode.
- Use application-level locking.
- Use storage-native consistent snapshot features.
- Use file backup with changed-file tracking.

Example safe maintenance flow:

```bash
oc scale deploy/web-content -n web --replicas=0
oc create -f snapshot-shared-content.yaml
oc wait volumesnapshot/shared-content-snap -n web --for=jsonpath='{.status.readyToUse}'=true --timeout=5m
oc scale deploy/web-content -n web --replicas=3
```

This is disruptive but simple. For production, use app-aware quiescing.

## 11.5 ROX Backup Strategy

ROX backup should focus on source-of-truth recovery.

Example:

- Store static content in Git or artifact repository.
- Publish to ROX backend.
- Validate checksums.
- Rebuild ROX volume during disaster recovery.

For ROX, restore testing is usually easier because no live writers should be changing files.

## 12. Restore Considerations

## 12.1 Restore to Same Access Mode

Usually restore to the same access mode as the original PVC:

```text
RWO source -> RWO restore
RWX source -> RWX restore
ROX source -> ROX restore
```

Changing access mode during restore depends on:

- CSI driver capability
- StorageClass capability
- Snapshot/clone support
- Filesystem compatibility
- Backend export mode

Do not assume you can snapshot an RWO block volume and restore it as RWX shared filesystem. That normally requires migration, not just restore.

## 12.2 Restore to Different Namespace

You can often restore a snapshot to another PVC in the same namespace. Cross-namespace restore depends on the backup tool, snapshot content handling, and permissions.

Common pattern:

```text
production namespace snapshot -> restore-test namespace restored PVC -> validation pod
```

Validation pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: restore-check
  namespace: restore-test
spec:
  containers:
    - name: check
      image: registry.access.redhat.com/ubi9/ubi
      command: ["sleep", "infinity"]
      volumeMounts:
        - name: data
          mountPath: /restore
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: mysql-data-restore
```

## 12.3 Restore Validation Commands

```bash
oc get pvc -n restore-test
oc get pod -n restore-test -o wide
oc rsh -n restore-test restore-check
ls -lah /restore
du -sh /restore
find /restore -maxdepth 2 -type f | head
```

For databases, start an isolated database pod and run application-specific checks.

## 13. Troubleshooting Scenarios

## 13.1 PVC Stuck in Pending

Symptoms:

```bash
oc get pvc -n app
```

```text
NAME       STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
app-data   Pending                                      fast-rwo
```

Check:

```bash
oc describe pvc app-data -n app
oc get sc
oc get sc fast-rwo -o yaml
oc get events -n app --sort-by=.lastTimestamp
```

Common causes:

- Requested `RWX` from RWO-only StorageClass.
- No default StorageClass and PVC did not specify one.
- StorageClass provisioner unavailable.
- Topology constraints cannot be satisfied.
- Quota blocks PVC creation.
- Requested size exceeds backend limit.
- CSI driver not healthy.

Fix examples:

```bash
# Patch PVC only works for some fields; often recreate is cleaner.
oc delete pvc app-data -n app

# Recreate with correct StorageClass/access mode.
oc apply -f pvc-correct.yaml
```

## 13.2 Multi-Attach Error with RWO

Symptoms:

```text
Multi-Attach error for volume "pvc-..." Volume is already exclusively attached to one node and can't be attached to another
```

Check:

```bash
oc get pod -n <ns> -o wide
oc describe pod <pod> -n <ns>
oc get volumeattachment
oc describe volumeattachment <name>
oc get node
```

Common causes:

- Deployment has multiple replicas sharing one RWO PVC.
- Old pod stuck terminating.
- Node is NotReady and volume detach is delayed.
- RollingUpdate creates replacement before old pod releases disk.

Fix options:

- Use StatefulSet with one PVC per replica.
- Set Deployment replicas to 1.
- Use `Recreate` strategy for single RWO PVC.
- Fix stuck terminating pod/node.
- Wait for CSI detach.

Deployment strategy for single RWO PVC:

```yaml
spec:
  strategy:
    type: Recreate
```

## 13.3 RWX Permission Denied

Symptoms:

```text
touch: cannot touch '/shared/test': Permission denied
```

Check:

```bash
oc rsh -n <ns> <pod>
id
ls -ld /shared
mount | grep shared
```

Common causes:

- NFS export ownership does not match OpenShift random UID.
- Root squash blocks root writes.
- `fsGroup` not applied or unsupported.
- Backend ACL denies write.
- SCC/securityContext mismatch.

Fix options:

- Set correct ownership on export path.
- Use group-writable directory.
- Configure `fsGroup` where supported.
- Use storage backend parameters for UID/GID mapping.
- Avoid privileged workaround unless truly required.

## 13.4 ROX Volume Allows Write Attempt

Symptoms:

- App starts but write fails.
- Or app unexpectedly writes because backend not truly read-only.

Check:

```bash
oc describe pod <pod> -n <ns>
oc get pv <pv> -o yaml
oc rsh <pod> -- mount | grep <mount>
oc rsh <pod> -- touch /mnt/reference/test
```

Fix:

Use all three:

```yaml
persistentVolumeClaim:
  claimName: reference-data
  readOnly: true
```

and:

```yaml
volumeMounts:
  - name: reference
    mountPath: /mnt/reference
    readOnly: true
```

and backend read-only export/mount policy.

## 13.5 Snapshot Not Ready

Check:

```bash
oc get volumesnapshot -A
oc describe volumesnapshot <name> -n <ns>
oc get volumesnapshotclass
oc get volumesnapshotcontent
```

Common causes:

- CSI driver does not support snapshots.
- Wrong `VolumeSnapshotClass` driver.
- Snapshot controller/operator issue.
- PVC source not bound.
- Backend error.
- Permission/RBAC issue.

## 15. Exam and Interview-Level Questions

### Q1. A Deployment with 3 replicas uses one RWO PVC. What can go wrong?

The pod replicas may not all schedule successfully. RWO allows read-write mount by one node. If replicas land on different nodes, attach/mount can fail with multi-attach errors. Use one replica, `Recreate` strategy, StatefulSet with per-replica PVCs, or an RWX backend if shared data is required.

### Q2. Does RWO mean only one pod?

No. RWO means one node. Multiple pods on the same node may access the same RWO volume. For single-pod enforcement, use `ReadWriteOncePod` where supported.

### Q3. Is RWX good for databases?

Usually no. RWX means multi-node read-write mount, not database concurrency safety. Use database clustering architecture with per-member RWO disks unless the database explicitly supports shared storage.

### Q4. Why is my PVC Pending when I request RWX?

The requested StorageClass may not support RWX. Check the StorageClass provisioner and events. Use an RWX-capable backend such as CephFS, NFS, EFS, or Azure File.

### Q5. Is ROX enough to secure read-only data?

No. Use ROX plus `readOnly: true` in the pod volume and volumeMount, and enforce read-only at the storage backend.

### Q6. Can I restore an RWO snapshot as RWX?

Usually no. A block volume snapshot restored as a block/filesystem volume normally remains tied to a compatible StorageClass and access pattern. Converting RWO block data to RWX shared filesystem is a migration operation.

### Q7. Why does RWX write fail with Permission denied in OpenShift?

OpenShift restricted SCC commonly runs containers with arbitrary UIDs. The shared filesystem path may not be writable by that UID or group. Fix ownership, group permissions, fsGroup, export options, or backend ACLs.

## 19. Real-World Design Recommendations

### Recommendation 1: Use RWO for databases by default

Databases usually need strong consistency and private storage. Use StatefulSet with one RWO PVC per replica.

### Recommendation 2: Use RWX only when true sharing is required

RWX is powerful but can become a bottleneck or corruption risk if the app does not handle concurrency.

### Recommendation 3: Use ROX for shared immutable data

ROX is excellent for data that many pods need to read but should not modify.

### Recommendation 4: Do not confuse storage HA with application HA

A highly available storage backend does not automatically make a single database pod highly available. Application architecture still matters.

### Recommendation 5: Test backup and restore per access mode

A backup strategy that works for RWO database volumes may not work for RWX shared filesystems. Restore tests must match workload type.

### Recommendation 6: Validate StorageClass capabilities before giving it to teams

Document:

- Supported access modes
- Expansion support
- Snapshot support
- Clone support
- Topology behavior
- Reclaim policy
- Performance tier
- Backup policy

Example internal catalog:

| StorageClass | Backend | Access Modes | Snapshot | Expansion | Best For |
|---|---|---|---|---|---|
| `fast-rwo` | Ceph RBD / cloud block | RWO | Yes | Yes | DB, StatefulSet |
| `shared-rwx` | CephFS / NFS / EFS | RWX/ROX | Driver-specific | Driver-specific | Shared app files |
| `archive-rox` | NFS read-only | ROX | No / external | No | Reference data |

## 21. Key Takeaways

- `RWO` = read-write by one node. Best for single-writer private storage.
- `RWX` = read-write by many nodes. Best for shared filesystems, not automatically safe for databases.
- `ROX` = read-only by many nodes. Best for immutable shared content.
- RWO does not mean one pod; it means one node. Use `RWOP` for single-pod semantics where supported.
- Access mode must be supported by the storage backend and CSI driver.
- Dynamic provisioning fails or waits if the requested mode cannot be satisfied.
- Backup strategy must consider writer count and application consistency.
- RWX requires careful permission, locking, and performance design.
- ROX should be enforced at both Kubernetes and backend levels.
- Always test restore, not just backup creation.
