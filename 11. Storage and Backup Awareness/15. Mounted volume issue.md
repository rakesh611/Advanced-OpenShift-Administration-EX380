## 1. What is a Mounted Volume Issue?

A **mounted volume issue** means a workload has requested a storage volume, but OpenShift cannot correctly attach, stage, publish, mount, or use that volume inside the container.

In simple words:

> The PVC may exist, the PV may be bound, and the pod may be scheduled, but the volume is not usable inside the container.

This commonly appears as:

- Pod stuck in `ContainerCreating`
- Pod stuck in `Pending`
- Pod restarting because the application cannot read or write data
- `oc describe pod` showing `FailedMount`
- `oc describe pod` showing `FailedAttachVolume`
- `Multi-Attach error`
- `MountVolume.SetUp failed`
- `Unable to attach or mount volumes`
- `permission denied`
- `read-only file system`
- `no such file or directory`
- `timed out waiting for the condition`

A mounted volume issue is different from a simple **PVC Pending** issue. A PVC Pending issue means the claim has not yet successfully bound to storage. A mounted volume issue often happens after the PVC is already `Bound`, but the pod still cannot consume it.

## 2. Why This Topic Matters for Advanced OpenShift Administrators

For a senior OpenShift administrator, storage failures are high-impact because they affect stateful workloads such as:

- Databases
- Message queues
- CI/CD tools
- Container registries
- Monitoring stacks
- Logging stacks
- Backup tools
- Stateful microservices
- OpenShift Virtualization VMs
- AI/ML workloads using shared datasets

A volume mount problem can block application startup, create data loss risk, delay disaster recovery, and cause prolonged outage if the administrator fixes the wrong layer.

An experienced administrator must know how to answer these questions quickly:

1. Is the PVC bound?
2. Is the pod scheduled?
3. Is the volume attached to the correct node?
4. Is there a stale attachment on another node?
5. Is the CSI driver healthy?
6. Is kubelet able to mount the device?
7. Is the storage backend healthy?
8. Is the application failing because of permissions?
9. Is this a Kubernetes/OpenShift issue or a storage array/export issue?
10. Is it safe to force delete a pod, remove a taint, delete a `VolumeAttachment`, or detach a disk manually?

## 3. Volume Mount Lifecycle in OpenShift

Understanding the lifecycle is mandatory. Do not troubleshoot only from the pod level.

A typical persistent volume mount lifecycle looks like this:

```text
Application Deployment/StatefulSet
        |
        v
Pod references PVC
        |
        v
PVC binds to PV or dynamic provisioner creates PV
        |
        v
Scheduler places pod on a node
        |
        v
Attachable storage is attached to the node
        |
        v
CSI Node plugin stages the volume on the node
        |
        v
Kubelet publishes/mounts the volume into the pod directory
        |
        v
Container runtime starts container
        |
        v
Application reads/writes to mountPath
```

Important phases:

### 3.1 Provision

Dynamic provisioning creates a PV from a PVC using a `StorageClass`.

```text
PVC -> StorageClass -> CSI provisioner -> backend volume -> PV
```

If this fails, PVC usually remains `Pending`.

### 3.2 Bind

The PVC is matched to a PV.

```bash
oc get pvc -n <namespace>
oc get pv
```

Expected:

```text
STATUS: Bound
```

### 3.3 Schedule

The scheduler selects a node for the pod. With topology-aware storage, scheduling and provisioning can be connected. For example, `volumeBindingMode: WaitForFirstConsumer` delays binding until a pod is scheduled.

```bash
oc get pod -n <namespace> -o wide
```

### 3.4 Attach

For attachable block storage, OpenShift/Kubernetes creates a `VolumeAttachment` object and the CSI controller attaches the volume to the node.

```bash
oc get volumeattachment
oc describe volumeattachment <name>
```

NFS and many RWX filesystems usually do not use the same attach flow as cloud block devices or Ceph RBD.

### 3.5 Stage

The CSI node plugin prepares the device on the node. This may include device discovery, filesystem checks, formatting when appropriate, and staging under kubelet paths.

### 3.6 Publish / Mount

Kubelet mounts the volume into the pod path under `/var/lib/kubelet/pods/<pod-uid>/volumes/...` and exposes it to the container at the configured `mountPath`.

### 3.7 Application Access

The container process reads and writes using its user ID, group ID, SELinux label, filesystem permissions, and mount flags.

## 4. Key Objects Involved

### 4.1 Pod

The pod references a PVC under `.spec.volumes` and mounts it under `.spec.containers[].volumeMounts`.

```bash
oc get pod <pod> -n <namespace> -o yaml
oc describe pod <pod> -n <namespace>
```

Look for:

- `volumes`
- `volumeMounts`
- `mountPath`
- `subPath`
- `readOnly`
- pod events
- node name

### 4.2 PVC

The PVC is the namespace-scoped request for storage.

```bash
oc get pvc -n <namespace>
oc describe pvc <pvc> -n <namespace>
```

Check:

- Status
- Capacity
- Access modes
- StorageClass
- Volume name
- Events
- Conditions

### 4.3 PV

The PV is cluster-scoped storage backing the PVC.

```bash
oc get pv
oc describe pv <pv>
```

Check:

- Reclaim policy
- Claim reference
- Access modes
- Volume mode
- CSI driver
- Backend volume handle
- Node affinity
- Mount options
- Capacity

### 4.4 StorageClass

The StorageClass defines the dynamic provisioning behavior.

```bash
oc get sc
oc describe sc <storageclass>
```

Check:

- Provisioner
- Parameters
- `volumeBindingMode`
- `allowVolumeExpansion`
- `reclaimPolicy`
- mount options

### 4.5 VolumeAttachment

`VolumeAttachment` represents attach/detach state for attachable CSI volumes.

```bash
oc get volumeattachment
oc describe volumeattachment <volumeattachment-name>
```

Check:

- Attached status
- Node name
- PV name
- Attach error
- Detach error

### 4.6 CSI Driver Objects

```bash
oc get csidriver
oc get csinode
oc describe csinode <node>
```

Check whether the node has registered the expected CSI driver.

### 4.7 CSI Operator and Pods

Common namespaces:

```bash
oc get pods -A | grep -i csi
oc get co | grep -i storage
oc get co | grep -i csi
```

Depending on the platform, CSI components may run in namespaces such as:

- `openshift-cluster-csi-drivers`
- `openshift-storage`
- vendor-specific operator namespace

### 4.8 Node and Kubelet

The final mount operation is performed by kubelet on the node.

```bash
oc get node
oc describe node <node>
oc debug node/<node>
chroot /host
journalctl -u kubelet --since "1 hour ago"
```

## 5. Common Symptoms

### 5.1 Pod Stuck in ContainerCreating

```bash
oc get pod -n app
```

Example:

```text
NAME        READY   STATUS              RESTARTS   AGE
mysql-0     0/1     ContainerCreating   0          12m
```

This often indicates image pull, CNI, or volume setup. Confirm using `oc describe pod`.

### 5.2 Pod Stuck in Pending

```text
NAME        READY   STATUS    RESTARTS   AGE
app-0       0/1     Pending   0          10m
```

Could be:

- PVC Pending
- topology conflict
- insufficient resources
- node selector mismatch
- taints/tolerations
- volume node affinity conflict

### 5.3 FailedMount Event

```text
Warning  FailedMount  kubelet  MountVolume.SetUp failed for volume "data": permission denied
```

Usually node-level mount, backend export, filesystem, permission, or config issue.

### 5.4 FailedAttachVolume Event

```text
Warning  FailedAttachVolume  attachdetach-controller  AttachVolume.Attach failed for volume "pvc-..."
```

Usually CSI controller, cloud API, storage backend, stale attachment, or access mode issue.

### 5.5 Multi-Attach Error

```text
Multi-Attach error for volume "pvc-..." Volume is already exclusively attached to one node and can't be attached to another
```

Usually RWO volume already attached to another node, often after node failure, pod reschedule, or force deletion.

### 5.6 Application Starts but Cannot Write

Container runs, but logs show:

```text
Permission denied
Read-only file system
No space left on device
Operation not permitted
```

This is often not an attach problem. It is usually permissions, SELinux, readOnly mount, quota, filesystem full, or wrong application path.

## 6. Most Common Error Messages

### 6.1 `Unable to attach or mount volumes`

Generic kubelet event. Always inspect the full event text.

```bash
oc describe pod <pod> -n <namespace>
```

### 6.2 `MountVolume.SetUp failed`

The volume reached kubelet setup but mount failed.

Possible causes:

- NFS export denied
- missing secret/configmap
- invalid `subPath`
- permission issue
- filesystem issue
- wrong mount option
- stale mount path
- CSI node plugin problem

### 6.3 `FailedAttachVolume`

Attach failed before kubelet could mount.

Possible causes:

- CSI controller unhealthy
- storage backend API failure
- stale attachment
- node not found in cloud/storage backend
- volume already attached elsewhere
- zone/topology mismatch

### 6.4 `Multi-Attach error`

The volume cannot be attached to more than one node in write mode.

Common with:

- RWO block storage
- StatefulSet reschedule
- node crash
- forced pod deletion
- cloud disk detach delay

### 6.5 `permission denied`

Could be from:

- NFS export permissions
- filesystem ownership
- SELinux labeling
- SCC UID restrictions
- fsGroup not applied
- root-squash
- application running as random UID

### 6.6 `read-only file system`

Could be from:

- `readOnly: true` in volumeMount
- ROX access mode
- backend mounted read-only after filesystem error
- snapshot/clone mounted read-only depending on backend behavior
- NFS export read-only
- storage backend protection mode

### 6.7 `no such file or directory`

Could be from:

- invalid `subPath`
- missing ConfigMap/Secret key
- wrong hostPath/local path
- backend export path missing
- application writing to path not created

### 6.8 `volumeMode mismatch`

Filesystem volume mounted as block or block volume mounted as filesystem.

Check:

```bash
oc get pv <pv> -o jsonpath='{.spec.volumeMode}{"\n"}'
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.volumeMode}{"\n"}'
```

### 6.9 `timed out waiting for the condition`

Could indicate attach, mount, or CSI operation timeout. Look at CSI controller, CSI node plugin, kubelet, and backend health.

## 7. First 10-Minute Triage Workflow

Use this workflow during a live incident.

### Step 1: Identify the failing pod and node

```bash
NS=<namespace>
POD=<pod-name>

oc get pod $POD -n $NS -o wide
oc describe pod $POD -n $NS
```

Important fields:

- Status
- Node
- Events
- PVC names
- FailedMount/FailedAttachVolume messages

### Step 2: Check PVC status

```bash
oc get pvc -n $NS
oc describe pvc <pvc-name> -n $NS
```

If PVC is `Pending`, troubleshoot provisioning/binding first.

If PVC is `Bound`, continue to mount/attach troubleshooting.

### Step 3: Check PV details

```bash
PV=$(oc get pvc <pvc-name> -n $NS -o jsonpath='{.spec.volumeName}')
echo $PV
oc describe pv $PV
oc get pv $PV -o yaml
```

Look for:

- CSI driver
- volumeHandle
- accessModes
- volumeMode
- nodeAffinity
- mountOptions
- reclaimPolicy

### Step 4: Check pod events sorted by time

```bash
oc get events -n $NS --sort-by=.lastTimestamp | tail -50
```

For cluster-wide related events:

```bash
oc get events -A --sort-by=.lastTimestamp | grep -E "FailedMount|FailedAttach|Multi-Attach|pvc|volume|CSI|MountVolume"
```

### Step 5: Check VolumeAttachment

```bash
oc get volumeattachment | grep $PV
```

If found:

```bash
VA=<volumeattachment-name>
oc describe volumeattachment $VA
oc get volumeattachment $VA -o yaml
```

Look for:

```text
status.attached: true/false
status.attachError
status.detachError
spec.nodeName
spec.source.persistentVolumeName
```

### Step 6: Check CSI health

```bash
oc get csidriver
oc get csinode
oc get pods -A | grep -i csi
oc get co
```

For OpenShift Data Foundation:

```bash
oc get pods -n openshift-storage
oc get cephcluster -n openshift-storage
oc get storagecluster -n openshift-storage
```

### Step 7: Check kubelet logs on the node

```bash
NODE=<node-name>
oc debug node/$NODE
chroot /host
journalctl -u kubelet --since "1 hour ago" | grep -Ei "mount|volume|csi|pvc|attach|detach|permission|denied|failed"
```

### Step 8: Check actual mount state on node

Inside `oc debug node/<node>` and `chroot /host`:

```bash
findmnt | grep -i kubelet
findmnt | grep <pvc-or-volume-id>
mount | grep <pvc-or-volume-id>
lsblk
blkid
```

### Step 9: Check application permissions

```bash
oc rsh -n $NS $POD
id
mount | grep <mountPath>
ls -ld <mountPath>
touch <mountPath>/test-write
```

If pod is not running, create a temporary debug pod with the same PVC only when safe.

### Step 10: Decide the fault domain

Classify into one of these:

```text
PVC provisioning/binding issue
Attach/detach issue
CSI controller issue
CSI node plugin issue
Kubelet mount issue
Backend storage issue
Node OS issue
Application permission issue
Manifest/config issue
Backup/restore mismatch
```

## 9. Root Cause Categories

### Category 1: PVC or PV Misconfiguration

Examples:

- Wrong PVC name in pod
- PVC in wrong namespace
- Wrong `storageClassName`
- Wrong access mode
- Wrong volume mode
- Wrong capacity request
- Static PV claimRef mismatch
- PV node affinity conflict

### Category 2: StorageClass / Provisioner Issue

Examples:

- Provisioner not installed
- CSI controller down
- Wrong parameters
- Missing secret for CSI provisioner
- Backend quota exhausted
- Unsupported access mode
- `WaitForFirstConsumer` behavior misunderstood

### Category 3: Attach/Detach Issue

Examples:

- RWO volume already attached to another node
- Cloud disk detach delay
- Node crashed
- Stale `VolumeAttachment`
- Storage backend thinks disk is still mapped
- Attach limit reached on node

### Category 4: Kubelet Mount Issue

Examples:

- Filesystem check failure
- mount binary/helper missing
- invalid mount option
- stale mount path
- node plugin not responding
- node pressure
- kubelet bug or restart needed

### Category 5: Backend Storage Issue

Examples:

- NFS server down
- Ceph OSD down
- storage network issue
- export permission denied
- cloud API throttling
- storage array LUN offline
- backend volume deleted manually

### Category 6: Security / Permission Issue

Examples:

- Random UID cannot write
- missing `fsGroup`
- root-squash on NFS
- SELinux denial
- SCC prevents required user/group
- application expects root-owned directory

### Category 7: Manifest Issue

Examples:

- wrong `mountPath`
- wrong `subPath`
- missing ConfigMap/Secret
- `readOnly: true`
- duplicate volume names
- path collision with existing container files

### Category 8: Backup/Restore Issue

Examples:

- Restored pod points to missing PVC
- Restored PV references old backend volume ID
- Snapshot restored to PVC with wrong access mode
- App restored without quiescing database
- PVC restored into namespace with missing StorageClass
- Data owner/group differs after restore

## 10. PVC Bound but Pod Cannot Mount

This is one of the most common real-world cases.

### 10.1 Confirm PVC is Bound

```bash
oc get pvc -n <ns>
```

Example:

```text
NAME      STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS
mysql     Bound    pvc-22334455-aaaa-bbbb-cccc-123456789abc   10Gi       RWO            thin-csi
```

### 10.2 Check Pod Events

```bash
oc describe pod <pod> -n <ns>
```

Look at the bottom:

```text
Events:
  Warning FailedMount  kubelet  Unable to attach or mount volumes...
```

### 10.3 Check if the Pod Moved to Another Node

```bash
oc get pod <pod> -n <ns> -o wide
oc get volumeattachment | grep <pv-name>
```

If the PV is attached to a different node than the current pod, suspect stale attachment or multi-attach.

### 10.4 Check Access Mode

```bash
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.accessModes}{"\n"}'
oc get pv <pv> -o jsonpath='{.spec.accessModes}{"\n"}'
```

If `ReadWriteOnce`, the volume can be mounted read-write by one node at a time.

### 10.5 Check Node Affinity

```bash
oc get pv <pv> -o yaml | grep -A20 nodeAffinity
```

If PV has node affinity and pod is scheduled elsewhere, the pod may fail scheduling or mounting depending on the scenario.

### 10.6 Check CSI Node Plugin on the Target Node

```bash
oc get pods -A -o wide | grep -i csi | grep <node-name>
```

A CSI daemonset pod should generally be running on the node for that driver.

### 10.7 Check Kubelet Logs

```bash
oc debug node/<node>
chroot /host
journalctl -u kubelet --since "1 hour ago" | grep -Ei "FailedMount|MountVolume|pvc|csi|permission|denied"
```

## 11. PVC Pending vs Mounted Volume Issue

### 11.1 PVC Pending

PVC Pending means OpenShift has not successfully bound storage.

```text
PVC -> Pending -> no usable PV yet
```

Common causes:

- No default StorageClass
- Wrong StorageClass
- Provisioner unavailable
- Access mode not supported
- Storage backend quota full
- `WaitForFirstConsumer` and no pod exists yet
- Static PV not matching PVC

### 11.2 Mounted Volume Issue

Mounted volume issue often means:

```text
PVC -> Bound -> pod references PVC -> mount fails
```

Common causes:

- Multi-attach
- CSI node plugin issue
- kubelet issue
- backend unavailable
- permission denied
- invalid mount options
- volumeMode mismatch
- stale node attachment

### 11.3 Quick Differentiation

```bash
oc get pvc -n <ns>
oc describe pod <pod> -n <ns>
```

If PVC is `Pending`, focus on PVC/PV/StorageClass/provisioner.

If PVC is `Bound` and pod has `FailedMount` or `FailedAttachVolume`, focus on attach/mount path.

## 12. Access Mode Problems: RWO, RWX, ROX, RWOP

Access modes describe how a volume can be used.

### 12.1 ReadWriteOnce — RWO

```text
Mounted read-write by a single node
```

Important: Multiple pods can sometimes use the same RWO volume if they are on the same node, depending on the storage/plugin behavior. But the volume cannot be mounted read-write across multiple nodes.

Common issue:

```text
Stateful pod rescheduled from node1 to node2, but volume is still attached to node1.
```

Result:

```text
Multi-Attach error
```

### 12.2 ReadWriteMany — RWX

```text
Mounted read-write by many nodes
```

Common backends:

- NFS
- CephFS
- AWS EFS
- Azure File
- some vSphere CNS configurations

Common issue:

```text
Application requires shared write access but PVC is RWO.
```

Fix:

- Use RWX-capable StorageClass
- Redesign workload if backend does not support RWX

### 12.3 ReadOnlyMany — ROX

```text
Mounted read-only by many nodes
```

Common issue:

```text
Application tries to write to ROX mount.
```

Result:

```text
read-only file system
```

### 12.4 ReadWriteOncePod — RWOP

```text
Mounted read-write by only one pod
```

Use only when supported by your OpenShift version and storage driver. In older OpenShift releases this has had Technology Preview status. Verify support for your specific cluster version and storage driver before production use.

### 12.5 Access Modes Are Not Complete Runtime Enforcement

Access modes are used for matching and describing capabilities, but storage backend behavior matters at runtime. A volume can match a PVC and still fail during mount if the backend cannot satisfy the actual usage pattern.

## 13. Multi-Attach Error

### 13.1 Meaning

A Multi-Attach error means the same volume is already attached to one node and OpenShift is trying to attach it to another node.

Example:

```text
Multi-Attach error for volume "pvc-123" Volume is already exclusively attached to one node and can't be attached to another
```

### 13.2 Common Scenario

```text
mysql-0 was running on worker-1
worker-1 crashed or became NotReady
OpenShift created mysql-0 on worker-2
Volume is still attached to worker-1
Attach to worker-2 fails
```

### 13.3 Commands

```bash
oc get pod -n <ns> -o wide
oc get pvc -n <ns>
PV=$(oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.volumeName}')
oc get volumeattachment | grep $PV
oc describe volumeattachment <name>
```

Check which node owns the attachment:

```bash
oc get volumeattachment <name> -o jsonpath='{.spec.nodeName}{"\n"}'
oc get volumeattachment <name> -o jsonpath='{.status.attached}{"\n"}'
```

### 13.4 Safe Fix Flow

1. Confirm old node status:

```bash
oc get node <old-node>
oc describe node <old-node>
```

2. Confirm whether old pod still exists:

```bash
oc get pod -n <ns> -o wide | grep <app>
```

3. If old node is healthy, do not force detach. Investigate why the pod was rescheduled.

4. If old node is dead or powered off, use supported recovery method for non-graceful shutdown or backend detach.

5. For critical workloads, confirm application-level data consistency before forcing anything.

### 13.5 What Not to Do Immediately

Do not blindly delete `VolumeAttachment` as the first action. If the backend still has the disk attached to a running node, manual deletion can create split-brain or data corruption risk.

### 13.6 When Force Deleting Pod Is Used

If a pod is stuck terminating on a dead node and holding an RWO volume, force deletion may be required after confirming the node is really down.

```bash
oc delete pod <pod> -n <ns> --force --grace-period=0
```

Use this carefully. For databases, confirm there is no active process still writing to the volume.

## 14. Node Failure and Non-Graceful Shutdown

A non-graceful node shutdown is a classic reason for mounted volume issues.

### 14.1 Problem

When a node crashes, OpenShift may not immediately know whether the node is truly powered off. For RWO volumes, the storage system may still consider the volume attached to that node.

Result:

```text
New pod cannot mount the same RWO PVC on a different node.
```

### 14.2 Symptoms

```bash
oc get node
```

```text
worker-1   NotReady
```

Pod events:

```text
Multi-Attach error
Unable to attach or mount volumes
```

### 14.3 Recovery Principle

Before telling OpenShift/storage to detach a volume from a failed node, confirm the node is actually down or fenced.

For bare metal or VM environments, this may mean:

- Confirm VM powered off in hypervisor
- Confirm physical server powered off through iLO/iDRAC/IPMI
- Confirm storage path is inactive
- Confirm no kubelet is still writing

### 14.4 Out-of-Service Taint

For non-graceful node shutdown handling, Kubernetes/OpenShift supports using an out-of-service taint to allow volume detach behavior for shutdown nodes when the feature is available and supported by the platform/version.

Typical upstream command pattern:

```bash
oc adm taint nodes <node-name> node.kubernetes.io/out-of-service=nodeshutdown:NoExecute
```

Use only after confirming the node is really shutdown/powered off.

### 14.5 Remove Taint After Node Recovery

When the node is healthy again and you are ready to return it to service:

```bash
oc adm taint nodes <node-name> node.kubernetes.io/out-of-service-
```

### 14.6 Important Senior Admin Warning

Never use force detach or out-of-service taint casually. The goal is to prevent two nodes from writing to the same RWO filesystem at the same time.

## 17. NFS Mounted Volume Issues

NFS is common for RWX workloads, but many mount failures are caused by export, network, UID/GID, or root-squash problems.

### 17.1 Common NFS Errors

```text
mount.nfs: access denied by server while mounting
mount.nfs: Connection timed out
mount.nfs: No route to host
permission denied
read-only file system
stale file handle
```

### 17.2 Check PV

```bash
oc get pv <pv> -o yaml
```

Look for:

```yaml
spec:
  nfs:
    server: <nfs-server>
    path: <export-path>
  mountOptions:
  - nfsvers=4.1
```

### 17.3 Test From Node

Use node debug:

```bash
oc debug node/<node>
chroot /host
showmount -e <nfs-server>
mount -t nfs -o vers=4.1 <nfs-server>:<path> /mnt
```

If `showmount` is unavailable, test network first:

```bash
ping <nfs-server>
nc -zv <nfs-server> 2049
```

If `nc` is unavailable on node image, use available tools or a temporary diagnostic pod with proper network access.

### 17.4 Check Export on NFS Server

On NFS server:

```bash
exportfs -v
cat /etc/exports
systemctl status nfs-server
```

Common export problems:

- worker node IP not allowed
- wrong subnet
- root-squash blocks root writes
- export is read-only
- path does not exist
- firewall blocks 2049
- NFSv3/NFSv4 mismatch

### 17.5 NFS Permission with OpenShift Random UID

OpenShift normally runs containers with arbitrary high UIDs unless SCC allows otherwise. If the NFS directory is owned by a fixed UID and lacks group write, the pod may mount successfully but application write fails.

Check inside pod:

```bash
id
ls -ld /data
touch /data/test
```

Fix patterns:

- Set directory group ownership to a shared GID
- Use `fsGroup` if supported and appropriate
- Use proper NFS export options
- Avoid giving broad `anyuid` unless required and approved
- Prefer application images that support arbitrary UID

### 17.6 Stale File Handle

Usually occurs when exported directory or underlying filesystem changed while clients still had handles.

Recovery:

1. Confirm NFS server export is stable.
2. Restart affected pods if safe.
3. Unmount stale mount on node only if no active workload is using it.
4. Investigate backend storage changes.

## 20. Filesystem, fsType, and volumeMode Issues

### 20.1 volumeMode

PVC/PV can use:

```yaml
volumeMode: Filesystem
```

or:

```yaml
volumeMode: Block
```

Filesystem is default if unspecified.

### 20.2 Filesystem Volume

Mounted using `volumeMounts`:

```yaml
volumeMounts:
- name: data
  mountPath: /var/lib/mysql
```

### 20.3 Raw Block Volume

Used with `volumeDevices`, not `volumeMounts`:

```yaml
volumeDevices:
- name: data
  devicePath: /dev/xvda
```

### 20.4 Common Mistake

Using a block PVC like a filesystem PVC:

```yaml
volumeMode: Block
```

but in pod:

```yaml
volumeMounts:
- mountPath: /data
```

Correct for raw block:

```yaml
volumeDevices:
- devicePath: /dev/data
```

### 20.5 fsType Issues

Some PVs or StorageClasses specify filesystem type such as:

- `xfs`
- `ext4`

Problems:

- unsupported filesystem type
- corrupted filesystem
- device already formatted unexpectedly
- wrong mount option for fsType

Node checks:

```bash
lsblk -f
blkid
xfs_repair -n <device>   # dry-run only; do not repair mounted filesystem
fsck -n <device>         # dry-run only; use carefully
```

### 20.6 Warning About Formatting

Never manually format a device backing a PV unless you are absolutely sure it is the correct new/empty volume. Formatting the wrong PV destroys data.

## 21. Security Context, SCC, SELinux, and Permission Issues

OpenShift security is stricter than vanilla Kubernetes in many environments.

### 21.1 Typical Symptom

Pod starts but application logs show:

```text
mkdir: cannot create directory: Permission denied
cannot write to /data
permission denied opening file
```

### 21.2 Check Runtime User

```bash
oc rsh <pod> -n <ns>
id
```

Example:

```text
uid=1000710000 gid=0(root) groups=0(root),1000710000
```

### 21.3 Check Mount Directory

```bash
ls -ld /data
stat /data
```

### 21.4 SCC Check

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

### 21.5 fsGroup

A pod security context can request group ownership behavior:

```yaml
securityContext:
  fsGroup: 1001
```

However, behavior depends on storage plugin and filesystem. Some drivers apply it differently or slowly on large volumes.

### 21.6 SELinux

On OpenShift/RHCOS, SELinux labeling matters. A volume may be mounted but still inaccessible if labels or mount behavior conflict with container confinement.

Node-level investigation:

```bash
oc debug node/<node>
chroot /host
ausearch -m avc -ts recent 2>/dev/null || true
journalctl --since "1 hour ago" | grep -i denied
```

### 21.7 NFS and SELinux

NFS plus SELinux plus arbitrary UID can be confusing. Separate the issue:

1. Is the volume mounted?
2. Can node mount it?
3. Can container user write?
4. Is denial from Unix permission, NFS export, or SELinux?

### 21.8 anyuid SCC

`anyuid` can solve some legacy application issues, but it should not be the first fix for every storage permission problem.

Command:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

Use only when justified. Prefer images that support arbitrary UID and proper group permissions.

### 21.9 Recommended Permission Pattern

For OpenShift-friendly images and volumes:

```bash
chgrp -R 0 /data
chmod -R g+rwX /data
```

Application image directories should generally be group-writable and not require a fixed UID.

## 22. Secret, ConfigMap, Projected, and subPath Volume Issues

Not all mounted volume issues involve PVCs. Secrets, ConfigMaps, projected volumes, and `subPath` can also fail.

### 22.1 Missing Secret

Pod event:

```text
MountVolume.SetUp failed for volume "app-secret": secret "mysecret" not found
```

Check:

```bash
oc get secret -n <ns>
oc describe pod <pod> -n <ns>
```

Fix:

```bash
oc create secret generic mysecret --from-literal=password=redhat -n <ns>
```

### 22.2 Missing ConfigMap

```text
configmap "app-config" not found
```

Check:

```bash
oc get cm -n <ns>
```

### 22.3 Optional Secret/ConfigMap

If the volume can be optional:

```yaml
volumes:
- name: config
  configMap:
    name: app-config
    optional: true
```

### 22.4 subPath Error

Common event:

```text
failed to prepare subPath for volumeMount
no such file or directory
```

Example problem:

```yaml
volumeMounts:
- name: config
  mountPath: /etc/app/app.conf
  subPath: app.conf
```

But ConfigMap does not have key `app.conf`.

Check:

```bash
oc get cm app-config -n <ns> -o yaml
```

### 22.5 subPath Update Behavior

When using `subPath` with ConfigMap/Secret, updates may not be reflected the same way as a normal ConfigMap/Secret volume mount. Rolling the pod is usually required.

### 23.1 Check Pod YAML

```yaml
readOnly: true
```

### 23.2 Check PV/PVC Access Mode


ROX means read-only many.

Look for `ro` vs `rw`.

### 23.4 Check Backend Export

## 24. Mount Path, Directory, and Application-Level Issues

Sometimes the volume is mounted correctly, but the application is wrong.

### 24.1 Wrong mountPath

Example:

```yaml
volumeMounts:
- mountPath: /var/lib/mysql-data
```

But the MySQL image expects:

```text
/var/lib/mysql
```

Result: application writes to container ephemeral filesystem instead of PVC, or fails on startup.

### 24.2 Mount Hides Image Directory

If a volume is mounted over a path that already has files in the image, those files are hidden by the mount.

Example:

```yaml
mountPath: /usr/share/nginx/html
```

If PVC is empty, default Nginx files from image are hidden.

Fix:

- Initialize PVC with initContainer
- Use ConfigMap for static content
- Mount into subdirectory
- Build image with entrypoint that handles empty volume

### 24.3 Directory Does Not Exist

Kubernetes usually creates the mount path, but application-specific subdirectories may not exist.

Use initContainer:

```yaml
initContainers:
- name: init-data-dir
  image: registry.access.redhat.com/ubi9/ubi-minimal
  command: ["sh", "-c", "mkdir -p /data/app && chmod -R g+rwX /data"]
  volumeMounts:
  - name: data
    mountPath: /data
```

### 24.4 Application Lock Files

After unclean shutdown, databases may leave lock files.

Examples:

- PostgreSQL `postmaster.pid`
- MySQL/MariaDB InnoDB recovery needed
- Elasticsearch lock files
- Kafka log recovery

Do not assume every startup failure is Kubernetes mount failure.

## 25. Backup and Restore Awareness

Mounted volume issues often appear after backup and restore.

### 25.1 What Gets Backed Up?

A complete application backup usually needs:

- Kubernetes manifests
- PVC data
- Secrets
- ConfigMaps
- ServiceAccounts
- RBAC
- Routes/Ingress
- Operators/custom resources
- Database consistency state

If only YAML is restored but PVC data is missing, pods may fail or start empty.

If only PVC data is restored but app metadata is missing, pod may reference wrong PVC or wrong mount path.

### 25.2 Restore Order Matters

Recommended order:

1. Namespace/project
2. RBAC and service accounts
3. Secrets and ConfigMaps
4. Operators/CRDs if needed
5. StorageClass availability
6. PVC restore or snapshot restore
7. Workload controllers
8. Routes/services
9. Post-restore validation

### 25.3 Common Restore-Related Mount Failures

- PVC restored but StorageClass does not exist
- PV restored with old backend volume handle
- PVC references unavailable PV
- access mode not supported in target cluster
- volume snapshot class missing
- restored secret for CSI driver missing
- restored pod starts before PVC is ready
- namespace UID/GID range changed, causing permission denied

### 25.4 Verify After Restore

```bash
oc get pvc -n <ns>
oc get pv
oc describe pod <pod> -n <ns>
oc rsh <pod> -n <ns> -- ls -ld <mountPath>
oc rsh <pod> -n <ns> -- sh -c 'touch <mountPath>/restore-test && rm <mountPath>/restore-test'
```

## 26. Snapshot-Based Restore and Mounted Volume Issues

CSI snapshots are commonly used in backup/restore workflows, but they do not automatically guarantee application consistency.

### 26.1 Snapshot Objects

Common objects:

```bash
oc get volumesnapshot -n <ns>
oc get volumesnapshotclass
oc get volumesnapshotcontent
```

### 26.2 Restore Snapshot to New PVC

Typical PVC restore pattern:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restored-data
  namespace: app
spec:
  storageClassName: <snapshot-compatible-storageclass>
  dataSource:
    name: app-data-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

### 26.3 Common Snapshot Restore Mount Problems

- snapshot not ready to use
- snapshot class does not match driver
- target PVC smaller than snapshot source
- target StorageClass incompatible
- application tries to mount old PVC name
- restored filesystem has old UID/GID ownership
- database requires crash recovery
- snapshot is crash-consistent, not application-consistent

### 26.4 Check Snapshot Readiness

```bash
oc get volumesnapshot -n <ns>
oc describe volumesnapshot <snapshot> -n <ns>
```

Look for:

```text
Ready To Use: true
```

### 26.5 Mount Restored PVC Safely

For critical data, first mount restored PVC to a recovery/debug pod in read-only mode if supported.

```yaml
volumeMounts:
- name: restored
  mountPath: /restore
  readOnly: true
```

Validate data before replacing production PVC.

## 27. Application-Consistent Backup Considerations

### 27.1 Crash-Consistent vs Application-Consistent

A crash-consistent snapshot captures storage at a point in time without necessarily flushing application buffers.

Application-consistent backup coordinates with the application before snapshot:

- flush writes
- pause IO
- lock tables
- checkpoint database
- freeze filesystem when appropriate
- resume after snapshot

### 27.2 Why It Matters for Mounted Volume Issues

After restore, app may fail to start due to:

- unclean database state
- partial transactions
- corrupted write-ahead logs
- missing companion PVC snapshot
- inconsistent multi-volume application state

### 27.3 Multi-PVC Applications

Applications with multiple PVCs need coordinated snapshots.

Examples:

- database data PVC + WAL PVC
- VM root disk + data disk
- app data PVC + index PVC

If each PVC is snapshotted at a different time, restore may mount successfully but application may be logically inconsistent.

### 27.4 Recommended Pattern

For databases:

1. Use database-native backup when possible.
2. Use CSI snapshot as additional layer.
3. Quiesce or checkpoint before snapshot.
4. Verify restore regularly.
5. Keep runbook for post-restore recovery.

## 28. Safe Recovery Actions

### 28.1 Restart the Pod

Safe for stateless or app-approved workloads:

```bash
oc delete pod <pod> -n <ns>
```

For Deployment, ReplicaSet recreates pod. For StatefulSet, same identity returns.

### 28.2 Rollout Restart

```bash
oc rollout restart deploy/<deployment> -n <ns>
oc rollout restart statefulset/<statefulset> -n <ns>
```

### 28.3 Cordon and Drain Node

If one node has mount problems:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

Be careful with local storage and RWO volumes.

### 28.4 Restart CSI Node Pod

If CSI node plugin on one node is bad:

```bash
oc delete pod <csi-node-pod> -n <csi-namespace>
```

DaemonSet should recreate it.

### 28.5 Restart Kubelet

Only when justified and during incident-controlled action:

```bash
oc debug node/<node>
chroot /host
systemctl restart kubelet
```

This can disrupt pods on the node.

### 28.6 Force Delete Stuck Pod

Only after checking data safety:

```bash
oc delete pod <pod> -n <ns> --force --grace-period=0
```

### 28.7 Use Out-of-Service Taint for Dead Node

Only after confirming node is powered off:

```bash
oc adm taint nodes <node> node.kubernetes.io/out-of-service=nodeshutdown:NoExecute
```

### 28.8 Create Temporary Debug Pod with PVC

Only if the PVC is not actively used elsewhere or if it supports the required access mode.

For RWO, ensure it runs on same node or no other pod uses it.

## 29. Dangerous Actions to Avoid

### 29.1 Do Not Delete PV Randomly

Deleting a PV can trigger backend deletion depending on reclaim policy.

Check first:

```bash
oc get pv <pv> -o jsonpath='{.spec.persistentVolumeReclaimPolicy}{"\n"}'
```

### 29.2 Do Not Remove Finalizers Blindly

Finalizers protect resources from unsafe deletion.

Avoid:

```bash
oc patch pvc <pvc> -n <ns> -p '{"metadata":{"finalizers":null}}' --type=merge
```

unless you fully understand impact.

### 29.3 Do Not Delete VolumeAttachment Blindly

Deleting a `VolumeAttachment` without backend detach can cause data corruption risk.

### 29.4 Do Not Force Detach from a Live Node

If the old node is still alive and writing, force detach can corrupt filesystem/application data.

### 29.5 Do Not Format Unknown Devices

Never run `mkfs` on a device unless it is confirmed empty and intended for new PV use.

### 29.6 Do Not Use anyuid as Universal Fix

`anyuid` can hide permission problems and weaken security posture.

### 29.7 Do Not Assume Snapshot Equals Valid Backup

Snapshots must be tested by restore. A snapshot that cannot restore or mount is not a backup.

## 30. Production Incident Runbook

### 30.1 Incident Input

Collect:

```text
Namespace:
Application:
Pod name:
PVC name:
Node name:
StorageClass:
Business impact:
Recent changes:
Backup available:
```

### 30.2 Commands to Capture Evidence

```bash
NS=<namespace>
POD=<pod>

mkdir -p /tmp/volume-incident-$NS-$POD

oc get pod $POD -n $NS -o wide > /tmp/volume-incident-$NS-$POD/pod-wide.txt
oc describe pod $POD -n $NS > /tmp/volume-incident-$NS-$POD/pod-describe.txt
oc get pod $POD -n $NS -o yaml > /tmp/volume-incident-$NS-$POD/pod.yaml
oc get pvc -n $NS -o wide > /tmp/volume-incident-$NS-$POD/pvc-wide.txt
oc get events -n $NS --sort-by=.lastTimestamp > /tmp/volume-incident-$NS-$POD/events.txt
```

For each PVC:

```bash
PVC=<pvc>
PV=$(oc get pvc $PVC -n $NS -o jsonpath='{.spec.volumeName}')
oc describe pvc $PVC -n $NS > /tmp/volume-incident-$NS-$POD/pvc-$PVC-describe.txt
oc get pvc $PVC -n $NS -o yaml > /tmp/volume-incident-$NS-$POD/pvc-$PVC.yaml
oc describe pv $PV > /tmp/volume-incident-$NS-$POD/pv-$PV-describe.txt
oc get pv $PV -o yaml > /tmp/volume-incident-$NS-$POD/pv-$PV.yaml
oc get volumeattachment | grep $PV > /tmp/volume-incident-$NS-$POD/volumeattachment-$PV.txt || true
```

### 30.3 Determine Fault Domain

Use events:

```text
FailedScheduling -> scheduler/topology/PVC pending
FailedAttachVolume -> attach/controller/backend
FailedMount -> kubelet/node/backend/permission/config
Application log permission denied -> security/path/app
```

### 30.4 Storage Backend Health

For ODF:

```bash
oc get pods -n openshift-storage
oc get storagecluster -n openshift-storage
oc get cephcluster -n openshift-storage
```

For NFS:

```bash
showmount -e <nfs-server>
nc -zv <nfs-server> 2049
```

For cloud/block storage:

- check CSI controller logs
- check cloud console/API for disk attachment
- check node attach limits
- check zone/topology

### 30.6 Closure Checklist

Before closing incident:

- Pod is Running/Ready
- Application can read/write expected mount path
- No repeated FailedMount/FailedAttach events
- PVC/PV status normal
- VolumeAttachment normal or removed when pod deleted
- CSI pods healthy
- Storage backend healthy
- Application owner confirms functionality
- Backup/restore state validated if data was impacted

## 33. Interview and Real-World Scenario Questions

### Question 1

A pod is stuck in `ContainerCreating`. PVC is `Bound`. Events show `FailedMount`. What will you check?

**Answer:**

- `oc describe pod`
- PVC/PV details
- node where pod is scheduled
- kubelet logs on that node
- CSI node plugin pod on that node
- backend storage connectivity
- mount options
- permissions/SELinux if mount succeeds but app fails

### Question 2

PVC is RWO. Pod moved from worker-1 to worker-2 and now shows Multi-Attach. What is the safe approach?

**Answer:**

- Confirm whether worker-1 is alive or dead
- Check old pod status
- Check `VolumeAttachment`
- Do not force detach if old node may still write
- If node is truly powered off, use supported non-graceful shutdown recovery or backend detach process
- Then allow pod to attach on worker-2

### Question 3

NFS PV mounts but app cannot write. What could be wrong?

**Answer:**

- NFS export is read-only
- root-squash
- directory ownership does not allow OpenShift random UID
- missing group write
- SELinux denial
- app writes to wrong directory
- volumeMount has `readOnly: true`

### Question 4

What is the difference between `FailedAttachVolume` and `FailedMount`?

**Answer:**

`FailedAttachVolume` usually means the volume could not be attached to the node by the attach/detach controller or CSI controller. `FailedMount` usually means kubelet or CSI node plugin could not mount or publish the volume on the node or into the pod.

### Question 5

After restoring from snapshot, the PVC is Bound but database pod crashes. Is it a mount issue?

**Answer:**

Maybe not. If the volume mounts and database logs show recovery/corruption/permission errors, the issue may be application consistency, ownership, database recovery, or incomplete multi-PVC snapshot coordination.

## 34. Best Practices

### 34.1 Design Best Practices

- Use the correct access mode for workload design.
- Use RWX only with backends designed for shared write access.
- Prefer StatefulSet for stable identity stateful workloads.
- Avoid sharing one RWO PVC across replicas on different nodes.
- Use topology-aware StorageClasses correctly.
- Use OpenShift-friendly container images that support arbitrary UID.
- Define resource requests to help scheduling.
- Document StorageClass capabilities.

### 34.2 Operational Best Practices

- Monitor CSI pods and storage operators.
- Monitor PVC Pending and pod FailedMount events.
- Keep runbooks for backend-specific detach/recover operations.
- Test node failure behavior for stateful workloads.
- Validate backup restore regularly.
- Keep application owners involved before force detach or filesystem repair.
- Capture evidence before remediation.

### 34.3 Security Best Practices

- Avoid broad SCC changes unless required.
- Use least privilege SCC.
- Prefer group-write permissions over fixed UID requirements.
- Validate SELinux denials before disabling security controls.
- Protect storage backend credentials.

### 34.4 Backup Best Practices

- Do not rely only on YAML backup for stateful apps.
- Test restore, not just backup creation.
- Coordinate snapshots for multi-volume apps.
- Use application-native backup for databases.
- Keep restore documentation with exact PVC names and StorageClasses.

### 34.5 Change Management Best Practices

Before changing storage-related objects, capture:

```bash
oc get pvc,pv -o yaml
oc get sc -o yaml
oc get volumeattachment -o yaml
oc get pod <pod> -n <ns> -o yaml
```

For production, never change PV reclaim policy, finalizers, or backend volume mapping without approval and rollback plan.

## 35. Summary

A mounted volume issue in OpenShift is not only a PVC problem. It can involve the full chain:

```text
Pod -> PVC -> PV -> StorageClass -> CSI controller -> VolumeAttachment -> CSI node -> kubelet -> node OS -> storage backend -> application permissions
```

A senior administrator should troubleshoot in layers:

1. Check pod events.
2. Confirm PVC/PV binding.
3. Identify node and access mode.
4. Check VolumeAttachment for attachable CSI volumes.
5. Check CSI controller and node plugin health.
6. Check kubelet logs and node mount state.
7. Check backend storage health.
8. Check application UID/GID, SELinux, SCC, and write permissions.
9. Consider backup/restore consistency if issue appeared after restore.
10. Use safe recovery actions and avoid force operations unless the risk is understood.

The most important production rule:

> Do not force detach, delete VolumeAttachment, remove finalizers, or format devices until you have confirmed the old writer is gone and data safety is understood.
