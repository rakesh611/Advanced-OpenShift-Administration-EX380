## 1. Executive Summary

A **PersistentVolumeClaim (PVC)** is a namespace-scoped request for persistent storage. In OpenShift, developers usually create PVCs, and the platform automatically binds them to **PersistentVolumes (PVs)** either by dynamic provisioning through a **StorageClass** or by matching an already available static PV.

A PVC is not the physical disk itself. It is a Kubernetes/OpenShift API object that says:

> “I need storage with this size, access mode, volume mode, and storage class.”

The actual storage can come from many backends:

- Red Hat OpenShift Data Foundation / Ceph RBD / CephFS
- AWS EBS
- Azure Disk / Azure File
- Google Persistent Disk
- VMware vSphere CSI
- OpenStack Cinder / Manila
- NFS
- Local Storage Operator
- LVM Storage / TopoLVM
- Other supported CSI drivers

For advanced administration, PVC knowledge is critical because most stateful application outages are not caused by YAML syntax alone. They are usually caused by one or more of the following:

- Wrong StorageClass
- PVC stuck in `Pending`
- Topology or zone mismatch
- Missing default StorageClass
- Unsupported access mode, especially `ReadWriteMany`
- Volume attach or mount failure
- Node failure with attached RWO volume
- SCC / UID / filesystem permission issue
- Storage quota exhaustion
- Backend storage full
- Failed PVC expansion
- Deleted PVC causing unexpected data loss
- Snapshot not equivalent to a real off-cluster backup
- Restore into a namespace where StorageClass, SCC, secrets, or application identity differ

A senior OpenShift administrator should understand the full path from **PVC YAML → StorageClass → CSI provisioner → PV → backend disk/share → kubelet mount → container path → backup/restore lifecycle**.

## 2. Why PVC Matters in OpenShift Administration

OpenShift is built on Kubernetes, but enterprise OpenShift storage administration has extra operational concerns:

1. **Multi-tenant projects**  
   Each team or application usually works inside its own namespace/project. PVCs are namespaced, so a PVC belongs to one project.

2. **Cluster-wide PV resources**  
   PVs are cluster-scoped. Once a PV is bound to a PVC, it effectively becomes dedicated to that PVC namespace until released.

3. **CSI driver lifecycle**  
   Most modern OpenShift storage integrations use CSI. Admins must monitor CSI controller pods, node plugins, sidecars, StorageClasses, and backend connectivity.

4. **Backup and disaster recovery**  
   PVC data is usually business-critical. Stateful apps such as databases, message brokers, CI systems, artifact repositories, registries, and monitoring stacks depend on PVCs.

5. **Production safety**  
   Deleting a PVC can delete the underlying disk if the PV reclaim policy is `Delete`. This is one of the most common serious mistakes in Kubernetes/OpenShift operations.

6. **Scheduling dependency**  
   Storage is now part of scheduling. A pod might not run because storage cannot be provisioned in the selected zone or on the selected node.

7. **Application identity and permissions**  
   OpenShift runs containers with randomized UIDs by default. A mounted PVC may fail because the container process cannot write to the filesystem.

## 3. Core Storage Objects

### 3.1 PersistentVolumeClaim (PVC)

A PVC is a user request for persistent storage.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  namespace: app-prod
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-csi
  resources:
    requests:
      storage: 20Gi
```

This says:

- Create or find storage for namespace `app-prod`
- Name the claim `app-data`
- Need `20Gi`
- Need `ReadWriteOnce`
- Use StorageClass `fast-csi`

### 3.2 PersistentVolume (PV)

A PV represents the actual storage resource inside Kubernetes/OpenShift.

It can be:

- Dynamically created by a CSI provisioner
- Manually created by an administrator
- Backed by cloud disk, NFS export, Ceph volume, local disk, LUN, etc.

PVs are **cluster-scoped** objects.

### 3.3 StorageClass

A StorageClass defines how dynamic storage should be created.

It includes:

- CSI provisioner name
- Backend parameters
- Reclaim policy
- Volume binding mode
- Expansion support
- Optional mount options

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-csi
provisioner: csi.example.com
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
parameters:
  type: ssd
  fsType: xfs
```

### 3.4 CSI Driver

CSI means **Container Storage Interface**. It standardizes how container platforms communicate with storage backends.

A CSI deployment usually includes:

- Controller plugin
- Node plugin / daemonset
- External provisioner
- External attacher
- External resizer
- Snapshotter components
- Driver-specific secrets and configuration

### 3.5 VolumeSnapshot

A VolumeSnapshot captures the state of a PVC at a point in time, if the CSI driver supports snapshots.

Important point:

> A snapshot is not automatically a complete disaster recovery backup. If it stays on the same storage backend, it may be lost with that backend.

### 3.6 OADP

**OpenShift API for Data Protection (OADP)** is Red Hat’s OpenShift backup and restore solution based on Velero. It can back up Kubernetes objects and persistent volumes using supported snapshot or filesystem backup methods.

## 4. PVC Architecture Flow

High-level flow:

```text
Application YAML
   |
   | references PVC name
   v
PersistentVolumeClaim
   |
   | uses storageClassName
   v
StorageClass
   |
   | calls provisioner
   v
CSI Controller / External Provisioner
   |
   | creates backend volume
   v
PersistentVolume
   |
   | bound to PVC
   v
Pod scheduled
   |
   | CSI node plugin attaches/mounts volume
   v
Container path, for example /var/lib/mysql
```

When a pod starts, OpenShift does not mount the PVC object directly. The pod references the PVC. Kubernetes resolves the PVC to a PV. Then kubelet and the CSI node plugin handle attach and mount operations on the worker node.

## 5. PVC Object Deep Dive

A PVC has three main sections:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: example-pvc
  namespace: example-ns
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Filesystem
  storageClassName: standard
  resources:
    requests:
      storage: 10Gi
status:
  phase: Bound
```

### 5.1 `metadata.name`

Name of the PVC inside the namespace.

Rules:

- Must be unique inside the namespace
- Used by pods as `claimName`
- Should be meaningful: `mysql-data`, `jenkins-home`, `registry-storage`, `prometheus-db`

### 5.2 `metadata.namespace`

PVCs are namespace-scoped.

A pod can only mount PVCs from its own namespace. You cannot directly mount a PVC from namespace `A` into a pod running in namespace `B`.

### 5.3 `spec.accessModes`

Defines how the volume can be mounted.

Common values:

- `ReadWriteOnce` / `RWO`
- `ReadOnlyMany` / `ROX`
- `ReadWriteMany` / `RWX`
- `ReadWriteOncePod` / `RWOP`

Access mode support depends on the storage backend.

### 5.4 `spec.resources.requests.storage`

The requested capacity.

Example:

```yaml
resources:
  requests:
    storage: 50Gi
```

Important points:

- This is a request, not a limit.
- A PVC may bind to a larger static PV if it satisfies the request.
- With dynamic provisioning, the backend normally creates a volume of the requested size.
- Shrinking PVCs is generally not supported.

### 5.5 `spec.storageClassName`

Defines which StorageClass should satisfy the PVC.

Cases:

```yaml
storageClassName: fast
```

Use the `fast` StorageClass.

```yaml
storageClassName: ""
```

Do not use dynamic provisioning. Bind only to a matching PV that has no StorageClass or explicitly compatible class behavior.

```yaml
# storageClassName omitted
```

Use the default StorageClass, if one exists.

### 5.6 `spec.volumeMode`

Defines how the volume is exposed:

```yaml
volumeMode: Filesystem
```

or

```yaml
volumeMode: Block
```

`Filesystem` is the common choice for most applications. `Block` is used when the application manages the raw block device itself.

### 5.7 `spec.selector`

Used mostly with static PV binding.

Example:

```yaml
selector:
  matchLabels:
    app: oracle
    tier: gold
```

This forces the PVC to bind only to a PV with matching labels.

### 5.8 `spec.volumeName`

Used to bind a PVC to a specific PV.

Example:

```yaml
volumeName: pv-prod-db-001
```

Useful during controlled restore, migration, or manual PV reuse.

### 5.9 `spec.dataSource`

Used for cloning or restoring from a snapshot.

Example from snapshot:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restored-data
spec:
  storageClassName: odf-rbd
  dataSource:
    name: mysql-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

### 5.10 `status.phase`

Common phases:

- `Pending`
- `Bound`
- `Lost`

`Pending` means the claim is not yet satisfied. `Bound` means a PV is assigned. `Lost` means the PV backing the claim is missing or unavailable from the API perspective.

## 6. PV and PVC Lifecycle

PVC lifecycle:

```text
PVC created
   |
   v
Pending
   |
   | matching PV found OR dynamic PV provisioned
   v
Bound
   |
   | Pod uses PVC
   v
Mounted into workload
   |
   | PVC deleted
   v
PV released
   |
   | reclaim policy decides backend behavior
   v
Deleted / Retained / manual cleanup
```

### 6.1 Pending

PVC is waiting for one of the following:

- Default StorageClass exists
- Specified StorageClass exists
- CSI provisioner works
- Backend has capacity
- A matching static PV exists
- Pod scheduling occurs when `WaitForFirstConsumer` is used

### 6.2 Bound

PVC has a matching PV.

Check:

```bash
oc get pvc -n app-prod
oc get pv
oc describe pvc app-data -n app-prod
```

### 6.3 Mounted

A pod is using the PVC.

Check:

```bash
oc get pod -n app-prod -o wide
oc describe pod <pod> -n app-prod
oc get volumeattachment
```

### 6.4 Released

PVC was deleted, but PV remains. This usually happens with `Retain` reclaim policy.

Check:

```bash
oc get pv | grep Released
```

### 6.5 Failed or Lost

The backing storage may be gone, inaccessible, or incorrectly reclaimed.

Investigate:

```bash
oc describe pvc <pvc> -n <ns>
oc describe pv <pv>
oc get events -n <ns> --sort-by=.lastTimestamp
```

## 7. Dynamic Provisioning

Dynamic provisioning is the normal enterprise pattern in modern OpenShift.

Instead of manually creating PVs, the administrator provides StorageClasses. Users create PVCs, and OpenShift automatically provisions storage.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
  namespace: database
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: odf-rbd
  resources:
    requests:
      storage: 20Gi
```

Dynamic provisioning flow:

```text
PVC created
  -> StorageClass selected
  -> CSI provisioner receives request
  -> Backend volume created
  -> PV object created
  -> PV bound to PVC
```

### 7.1 Benefits

- No need to pre-create PVs
- Better self-service
- Standardized storage tiers
- Easier quota management
- Good GitOps integration
- Consistent application deployment

### 7.2 Risks

- Wrong default StorageClass can create storage on the wrong backend
- `Delete` reclaim policy can remove data when PVC is deleted
- Misconfigured CSI driver can block all new PVCs
- Capacity exhaustion may appear first as PVC `Pending`
- Zone-aware storage can block scheduling if binding mode is wrong

## 8. Static Provisioning

Static provisioning means the admin creates PVs manually.

Use cases:

- Existing NFS export
- Existing LUN
- Migration from old storage
- Pre-created cloud disk
- Strict control of storage asset naming
- Retained PV reuse after restore

Example static NFS PV:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-web-001
  labels:
    app: web
    env: prod
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs-static
  nfs:
    server: 192.168.10.50
    path: /exports/web
```

Matching PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: web-content
  namespace: web-prod
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: nfs-static
  selector:
    matchLabels:
      app: web
      env: prod
  resources:
    requests:
      storage: 10Gi
```

### 8.1 Static Binding Rules

The PVC and PV must match:

- Capacity must be equal or greater than request
- Access mode must be compatible
- Volume mode must match
- StorageClass must match
- Selector labels must match, if used

### 8.2 Static Provisioning Production Notes

For 10-year-level operations, static PVs require disciplined documentation:

- Backend path or volume ID
- Owner namespace
- Application owner
- Reclaim policy
- Backup policy
- Encryption policy
- Mount options
- Expected access mode
- Cleanup procedure

Never create anonymous static PVs without knowing who owns the backend data.

## 9. StorageClass and PVC Relationship

The StorageClass is the most important object behind dynamic PVC provisioning.

Check available classes:

```bash
oc get storageclass
oc describe storageclass <name>
```

Example output fields:

```text
Name:                  odf-rbd
IsDefaultClass:        Yes
Provisioner:           openshift-storage.rbd.csi.ceph.com
ReclaimPolicy:         Delete
VolumeBindingMode:     Immediate
AllowVolumeExpansion:  True
```

### 9.1 Key StorageClass Fields

#### `provisioner`

The CSI driver that provisions the volume.

Examples:

```text
ebs.csi.aws.com
csi.vsphere.vmware.com
pd.csi.storage.gke.io
openshift-storage.rbd.csi.ceph.com
openshift-storage.cephfs.csi.ceph.com
topolvm.io
```

#### `reclaimPolicy`

Controls what happens to the PV and backend storage after PVC deletion.

Common values:

```yaml
reclaimPolicy: Delete
```

or

```yaml
reclaimPolicy: Retain
```

#### `volumeBindingMode`

Controls when binding/provisioning happens.

```yaml
volumeBindingMode: Immediate
```

or

```yaml
volumeBindingMode: WaitForFirstConsumer
```

For zone-aware storage, `WaitForFirstConsumer` is often safer because provisioning waits until the scheduler knows where the pod can run.

#### `allowVolumeExpansion`

Allows PVC expansion after creation.

```yaml
allowVolumeExpansion: true
```

This does not mean every backend supports it. The CSI driver and backend must also support resize.

#### `mountOptions`

Optional mount flags, backend dependent.

Example:

```yaml
mountOptions:
  - noatime
  - nodiratime
```

Use carefully. Bad mount options can prevent mounting.

### 9.2 Default StorageClass

A default StorageClass is used when a PVC omits `storageClassName`.

Check default:

```bash
oc get sc
```

Default classes usually show:

```text
(default)
```

Set default:

```bash
oc annotate storageclass fast-csi storageclass.kubernetes.io/is-default-class="true"
```

Remove default:

```bash
oc annotate storageclass old-class storageclass.kubernetes.io/is-default-class- --overwrite
```

### 9.3 Multiple Default StorageClasses

Multiple default StorageClasses can cause unpredictable provisioning behavior. In production, keep only one default unless there is a very deliberate migration window.

## 10. Access Modes

Access modes describe how a volume may be mounted.

| Access Mode | Short | Meaning | Common Backend |
|---|---:|---|---|
| `ReadWriteOnce` | RWO | Read-write by a single node | EBS, Azure Disk, vSphere, RBD |
| `ReadOnlyMany` | ROX | Read-only by many nodes | NFS, CephFS |
| `ReadWriteMany` | RWX | Read-write by many nodes | NFS, CephFS, Azure File, ODF CephFS |
| `ReadWriteOncePod` | RWOP | Read-write by only one pod | CSI drivers with support |

### 10.1 `ReadWriteOnce` Does Not Mean One Pod Only

This is a common misunderstanding.

`ReadWriteOnce` usually means the volume can be mounted read-write by one node. Multiple pods on the same node might be able to use it, depending on the workload and driver behavior.

For strict single-pod semantics, use `ReadWriteOncePod` where supported.

### 10.2 `ReadWriteMany`

RWX is required for workloads where many pods across nodes must write the same data.

Examples:

- Shared web content
- Some CI/CD shared workspaces
- Shared media uploads
- Legacy applications expecting shared filesystem

Do not assume block storage supports RWX. Most cloud block disks do not.

### 10.3 `ReadOnlyMany`

Good for shared read-only content:

- Static content
- Reference data
- Model files
- Configuration bundles

### 10.4 Access Mode Troubleshooting

Check PVC request:

```bash
oc get pvc <pvc> -n <ns> -o yaml | yq '.spec.accessModes'
```

Check PV capability:

```bash
oc get pv <pv> -o yaml | yq '.spec.accessModes'
```

Check StorageClass/backend documentation if requested mode is unsupported.

## 11. Volume Modes: Filesystem vs Block

### 11.1 Filesystem Mode

Default and most common.

```yaml
volumeMode: Filesystem
```

The volume is formatted with a filesystem and mounted into the container.

Example pod mount:

```yaml
volumeMounts:
  - name: data
    mountPath: /var/lib/mysql
```

Use for:

- MySQL
- PostgreSQL
- Jenkins
- Nexus
- GitLab
- Prometheus
- Web uploads
- General application data

### 11.2 Block Mode

Raw block volume.

```yaml
volumeMode: Block
```

The container receives a block device.

Example:

```yaml
volumeDevices:
  - name: data
    devicePath: /dev/xvda
```

Use for:

- Databases that manage raw devices
- Specialized storage engines
- Virtualization scenarios
- Performance-sensitive workloads with direct block access

### 11.3 Important Difference

Filesystem mode uses `volumeMounts`.  
Block mode uses `volumeDevices`.

Wrong usage causes pod admission or mount errors.

## 12. PVC with Pods, Deployments, and StatefulSets

### 12.1 Pod Using PVC

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pvc-test
  namespace: app-test
spec:
  containers:
    - name: nginx
      image: registry.k8s.io/nginx
      volumeMounts:
        - name: web-data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: web-data
      persistentVolumeClaim:
        claimName: web-content
```

### 12.2 Deployment Using PVC

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: app-test
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: registry.k8s.io/nginx
          volumeMounts:
            - name: web-data
              mountPath: /usr/share/nginx/html
      volumes:
        - name: web-data
          persistentVolumeClaim:
            claimName: web-content
```

### 12.3 Deployment with RWO PVC Warning

If a Deployment uses one RWO PVC and you scale it to multiple replicas, pods may fail if scheduled on different nodes.

Symptoms:

```text
Multi-Attach error for volume
Volume is already exclusively attached to one node
```

Better options:

- Use `replicas: 1`
- Use StatefulSet with per-pod PVCs
- Use RWX storage
- Use application-level replication instead of shared disk

## 13. StatefulSet `volumeClaimTemplates`

StatefulSets are designed for stateful applications.

Example:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: database
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: registry.redhat.io/rhel8/mysql-80
          volumeMounts:
            - name: mysql-data
              mountPath: /var/lib/mysql/data
  volumeClaimTemplates:
    - metadata:
        name: mysql-data
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: odf-rbd
        resources:
          requests:
            storage: 20Gi
```

This creates PVCs like:

```text
mysql-data-mysql-0
mysql-data-mysql-1
mysql-data-mysql-2
```

Each replica gets its own PVC.

### 13.1 Why StatefulSet PVCs Are Safer for Databases

- Stable pod identity
- Stable network identity
- Stable storage identity
- One PVC per replica
- Better rolling update behavior
- Safer than sharing one PVC across many database pods

### 13.2 Important Deletion Behavior

Deleting a StatefulSet does not necessarily delete PVCs automatically. This protects data from accidental deletion.

Always check:

```bash
oc get pvc -n database
```

## 14. Reclaim Policy and Data Retention

The PV reclaim policy controls backend data lifecycle after PVC deletion.

### 14.1 `Delete`

When the PVC is deleted:

- PVC is removed
- PV is deleted
- Backend storage is usually deleted
- Data is lost unless separately backed up

This is common for dynamically provisioned volumes.

### 14.2 `Retain`

When the PVC is deleted:

- PVC is removed
- PV remains in `Released`
- Backend data remains
- Admin must manually reclaim or reuse the PV

Use `Retain` for important data when deletion safety is more important than automation.

### 14.3 Change PV Reclaim Policy

```bash
oc patch pv <pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
```

or:

```bash
oc patch pv <pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Delete"}}'
```

### 14.4 Safe Delete Procedure for Production PVC

Before deleting any production PVC:

```bash
oc get pvc <pvc> -n <ns> -o wide
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.volumeName}{"\n"}'
oc get pv <pv> -o jsonpath='{.spec.persistentVolumeReclaimPolicy}{"\n"}'
oc describe pv <pv>
```

Then confirm:

- Is there a recent backup?
- Is there a snapshot?
- Is the snapshot stored off the same failure domain?
- Does the application owner approve deletion?
- Does the PV reclaim policy match the intended outcome?

### 14.5 Reusing Retained PV

Typical controlled flow:

```bash
oc patch pv <pv> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
oc delete pvc <old-pvc> -n <old-ns>
oc patch pv <pv> --type=json -p='[{"op":"remove","path":"/spec/claimRef"}]'
```

Then create a new PVC with:

```yaml
spec:
  volumeName: <pv>
```

Be very careful. Rebinding a PV with old data to the wrong namespace can expose sensitive data.

## 15. PVC Expansion and Resize

PVC expansion lets you increase requested capacity.

### 15.1 Requirements

- StorageClass must have `allowVolumeExpansion: true`
- CSI driver must support expansion
- Backend must have capacity
- Filesystem expansion may require pod restart or remount depending on driver/filesystem
- Shrinking is not supported in normal Kubernetes/OpenShift PVC workflow

Check StorageClass:

```bash
oc get sc <sc-name> -o yaml | grep allowVolumeExpansion
```

### 15.2 Expand PVC

Example from 10Gi to 20Gi:

```bash
oc patch pvc app-data -n app-prod -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

Watch:

```bash
oc get pvc app-data -n app-prod -w
oc describe pvc app-data -n app-prod
```

### 15.3 Filesystem Resize Pending

You may see:

```text
FileSystemResizePending
```

This means backend volume expansion happened, but filesystem resize still needs to complete on the node. Restarting or recreating the pod may finish the filesystem resize depending on the driver.

### 15.4 Failed Resize Recovery

If resize is stuck:

```bash
oc describe pvc <pvc> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc describe pv <pv>
oc get pods -n openshift-cluster-csi-drivers
```

Common causes:

- Backend quota exceeded
- StorageClass does not allow expansion
- CSI resizer sidecar issue
- Requested size exceeds backend limits
- Filesystem cannot expand
- Node-side resize failed

### 15.5 Never Try to Shrink by Editing PVC Smaller

Shrinking is not supported. If you need a smaller volume:

1. Create a new smaller PVC
2. Copy data at application/filesystem level
3. Validate application
4. Cut over
5. Delete old PVC only after confirmed backup

## 16. PVC Cloning

PVC cloning creates a new PVC from an existing PVC, if the CSI driver supports it.

Use cases:

- Test copy of production data
- Fast duplicate environment
- Pre-upgrade validation
- Data migration

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-clone
  namespace: database
spec:
  storageClassName: odf-rbd
  dataSource:
    name: mysql-data
    kind: PersistentVolumeClaim
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

Important rules:

- Source PVC and target PVC are usually expected in the same namespace unless advanced cross-namespace data sources are supported and enabled.
- Target PVC size must be equal or greater than source PVC.
- Driver must support clone.
- Application consistency still matters. A clone of a live database may not be transaction-consistent unless the app is quiesced or storage supports crash-consistent semantics acceptable to the workload.

## 17. Volume Snapshots

A VolumeSnapshot is a snapshot request for a PVC.

Objects involved:

- `VolumeSnapshotClass`
- `VolumeSnapshot`
- `VolumeSnapshotContent`
- Source PVC
- CSI snapshotter

### 17.1 VolumeSnapshotClass Example

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-snapclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: csi.example.com
deletionPolicy: Delete
```

### 17.2 Create Snapshot

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-data-snap-001
  namespace: database
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: mysql-data
```

Check:

```bash
oc get volumesnapshot -n database
oc describe volumesnapshot mysql-data-snap-001 -n database
oc get volumesnapshotcontent
```

### 17.3 Restore Snapshot to New PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-restored
  namespace: database-restore
spec:
  storageClassName: odf-rbd
  dataSource:
    name: mysql-data-snap-001
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

### 17.4 Snapshot Deletion Policy

`VolumeSnapshotClass.deletionPolicy` controls what happens to the backend snapshot when the snapshot object is deleted.

Common values:

- `Delete`
- `Retain`

Use `Retain` when you need manual safety. Use `Delete` when lifecycle automation is preferred.

### 17.5 Snapshot Is Not Always a Backup

A snapshot is commonly stored on the same storage system. If the storage backend fails completely, the snapshot may be lost too.

For real backup, ensure data is copied to another failure domain, object storage, backup system, or remote cluster.

## 18. PVC Backup and Restore Awareness

PVC backup is more than copying Kubernetes YAML.

A real application backup should include:

- Namespace resources
- Deployments / StatefulSets
- Services / Routes
- ConfigMaps
- Secrets
- ServiceAccounts
- RoleBindings
- PVC data
- VolumeSnapshots or filesystem backup data
- Image references
- Operator CRs, if applicable
- Database dump or application-level backup, if required
- Restore order and validation steps

### 18.1 Backup Types

| Backup Type | Captures | Pros | Cons |
|---|---|---|---|
| YAML only | Kubernetes objects | Fast, GitOps friendly | No PVC data |
| CSI snapshot | Block/filesystem snapshot | Fast restore | Driver/backend dependent; may be same failure domain |
| Filesystem backup | Files from mounted PVC | Portable | Slower for large data |
| Application dump | Logical app data | App-consistent | Needs app-specific process |
| Storage replication | Backend-level copy | Good DR | Complex, storage-specific |
| OADP backup | K8s objects + PV options | OpenShift integrated | Needs configuration and testing |

### 18.2 What Happens If You Back Up Only YAML?

You can recreate the PVC object, but not the data.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
spec:
  resources:
    requests:
      storage: 20Gi
```

This recreates an empty disk unless restored from snapshot/backup.

### 18.3 Stateful Application Backup Principle

For databases, use at least one of:

- Database-native backup: `mysqldump`, `pg_dump`, `pg_basebackup`, RMAN, etc.
- CSI snapshot with quiescing
- OADP with backup hooks
- Storage-level snapshot integrated with database freeze/thaw

Crash-consistent snapshots may be acceptable for some workloads but not all.

## 19. OADP, Velero, Restic, Kopia, and CSI Snapshots

OADP is commonly used for OpenShift application backup and restore.

### 19.1 OADP Can Handle

- Kubernetes resources
- Namespace-scoped application resources
- Internal images, depending on configuration
- PV backup using supported methods
- CSI snapshot backups
- Filesystem backup using Restic or Kopia, depending on OADP version/configuration

### 19.2 Backup Storage Location

You need object storage such as:

- OpenShift Data Foundation object bucket
- AWS S3
- Azure Blob
- Google Cloud Storage
- S3-compatible object storage
- IBM Cloud Object Storage S3

### 19.3 CSI Snapshot Backup

Requires:

- CSI snapshot-capable storage
- VolumeSnapshotClass
- OADP configuration enabling CSI support
- Compatible OADP/Velero version

### 19.4 Filesystem Backup

Filesystem backup walks the mounted volume filesystem and copies file data to object storage.

Useful when:

- CSI snapshots are not supported
- Cross-provider migration is needed
- Backup must be portable
- Storage backend snapshot is not available

Trade-offs:

- Slower than snapshots
- Higher I/O load
- Requires enough time window

```yaml
  storageLocation: default
  ttl: 720h0m0s
```

Actual OADP configuration varies by environment and OADP version.

## 20. Application-Consistent Backup Strategy

A senior admin should distinguish between:

### 20.1 Crash-Consistent Backup

Similar to pulling power from a server and capturing disk state.

May be okay for:

- Some journaling filesystems
- Some replicated databases
- Stateless-like caches
- Apps that can recover from journals

Risky for:

- Single-instance databases
- Message queues
- Write-heavy systems
- Applications with in-memory state not flushed to disk

### 20.2 Application-Consistent Backup

Application is prepared before backup.

Examples:

- Flush tables with read lock in MySQL
- Checkpoint PostgreSQL
- Freeze filesystem with `fsfreeze`
- Pause writes
- Run app-specific pre-hook
- Resume writes after snapshot

### 20.3 Backup Hook Pattern

Before snapshot:

```bash
# Example only; use workload-specific command
mysql -e 'FLUSH TABLES WITH READ LOCK;'
```

After snapshot:

```bash
mysql -e 'UNLOCK TABLES;'
```

In reality, long locks can impact production. Coordinate with DBAs and application owners.

### 20.4 Restore Validation

A backup is not valid until restored and tested.

Validate:

- PVC restored
- Pod starts
- Files are present
- Database integrity check passes
- App login works
- Route/Service works
- Secrets are valid
- Ownership/permissions are correct
- Performance is acceptable

## 21. OpenShift Security Context, SCC, and PVC Permissions

OpenShift often runs containers with randomized UIDs. This is more secure but can create PVC permission problems.

### 21.1 Common Error

```text
permission denied
mkdir: cannot create directory
chown: changing ownership: Operation not permitted
```

### 21.2 Check Pod Security Context

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.securityContext'
oc get pod <pod> -n <ns> -o yaml | yq '.spec.containers[].securityContext'
```

### 21.3 Check SCC

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
oc get scc
```

### 21.4 Fix Patterns

#### Use `fsGroup` where allowed

```yaml
securityContext:
  fsGroup: 1000720000
```

#### Use an init container to set permissions

This may require elevated SCC depending on the image and operation.

#### Use storage backend ownership controls

For NFS, configure export permissions, UID/GID mapping, or root squash behavior carefully.

#### Avoid unnecessary `anyuid`

Do not blindly assign `anyuid` SCC to solve every PVC permission issue. It may work quickly but can violate security standards.

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

Use only when justified and documented.

### 21.5 NFS and OpenShift UID Issues

With NFS, common issues include:

- `root_squash`
- Directory not writable by arbitrary UID
- Wrong SELinux context on NFS server
- UID/GID mismatch
- Export not reachable from worker nodes

For OpenShift-compatible NFS directories, permissions often need to allow the project UID range or group write through supplemental groups.

## 23. Topology, Zones, and `WaitForFirstConsumer`

Storage provisioning and pod scheduling must agree on topology.

### 23.1 Problem with Immediate Binding

If a PVC is provisioned immediately in zone `A`, but the pod is scheduled or constrained to zone `B`, the pod cannot attach the volume.

Symptoms:

```text
0/6 nodes are available: node(s) had volume node affinity conflict
```

### 23.2 `WaitForFirstConsumer`

With `WaitForFirstConsumer`, volume provisioning waits until a pod using the PVC is scheduled. This allows the scheduler to choose a node first, then storage is created in the correct topology.

StorageClass example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: zone-aware-block
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
allowVolumeExpansion: true
```

### 23.3 Check PV Node Affinity

```bash
oc get pv <pv> -o yaml | yq '.spec.nodeAffinity'
```

### 23.4 Check Pod Scheduling Constraints

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.nodeSelector'
oc get pod <pod> -n <ns> -o yaml | yq '.spec.affinity'
oc describe pod <pod> -n <ns>
```

## 24. Local Storage and LVM Storage Considerations

Local storage is different from network storage.

### 24.1 Local Storage Characteristics

- Very low latency
- Tied to a specific node
- Not automatically replicated
- Node failure can make data unavailable
- Good for workloads with application-level replication

### 24.2 LVM Storage / TopoLVM

LVM Storage uses local disks and can dynamically provision local PVs.

Important production warning:

> Local storage does not provide automatic storage-level replication across nodes. You need application-level replication, backup, or DR strategy.

### 24.3 Local PV Scheduling

Local PVs have node affinity. A pod using a local PV must run on the node where the disk exists.

Check:

```bash
oc get pv <local-pv> -o yaml | yq '.spec.nodeAffinity'
```

### 24.4 When to Use Local Storage

Good candidates:

- Elasticsearch/OpenSearch with replicas
- Kafka with replication
- Cassandra
- Ceph/ODF internals
- High-performance cache with rebuild capability

Poor candidates:

- Single-instance database without backup
- Critical app expecting automatic failover
- Apps with no restore procedure

## 27. PVC Troubleshooting Runbook

### 27.1 PVC Stuck in Pending

Symptoms:

```bash
oc get pvc -n app-prod
```

```text
NAME       STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
app-data   Pending                                      fast-csi
```

Run:

```bash
oc describe pvc app-data -n app-prod
oc get events -n app-prod --sort-by=.lastTimestamp
oc get sc fast-csi -o yaml
oc get pods -A | grep -i csi
```

Common causes:

| Cause | Evidence | Fix |
|---|---|---|
| StorageClass missing | `storageclass.storage.k8s.io not found` | Correct `storageClassName` |
| No default StorageClass | PVC omitted `storageClassName` | Set default SC or specify SC |
| Backend full | Provisioning failed events | Add capacity / clean backend |
| Unsupported access mode | Provisioning failure | Use correct backend/class |
| Quota exceeded | ResourceQuota event | Increase quota / reduce request |
| WaitForFirstConsumer | PVC waits until pod exists | Create pod using PVC |
| CSI provisioner down | No provisioning | Fix CSI operator/pods |
| Topology conflict | Node affinity errors | Use correct binding mode / scheduling |

### 27.2 Pod Stuck in ContainerCreating Due to PVC

Check:

```bash
oc describe pod <pod> -n <ns>
oc describe pvc <pvc> -n <ns>
oc describe pv <pv>
oc get volumeattachment
```

Common errors:

```text
Unable to attach or mount volumes
MountVolume.MountDevice failed
Multi-Attach error
permission denied
node(s) had volume node affinity conflict
```

### 27.3 Multi-Attach Error

Cause:

- RWO volume already attached to another node
- Deployment scaled with single RWO PVC
- Old pod still terminating
- Node failure left attachment stale

Commands:

```bash
oc get pod -n <ns> -o wide
oc get volumeattachment | grep <pv-or-volume-id>
oc describe volumeattachment <name>
```

Fix options:

- Scale deployment to 1
- Wait for detach
- Force delete stuck pod only after confirming node state
- Move to RWX storage if app needs multiple replicas sharing one volume
- Use StatefulSet with one PVC per replica

### 27.4 Permission Denied on Mounted PVC

Check pod logs:

```bash
oc logs <pod> -n <ns>
```

Check SCC:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

Debug:

```bash
oc rsh <pod> -n <ns>
id
ls -ld <mount-path>
touch <mount-path>/test
```

Fix:

- Correct ownership on volume
- Use `fsGroup` if permitted
- Adjust NFS export permissions
- Use supported container image that works with arbitrary UID
- Assign appropriate SCC only if required

### 27.5 PVC Bound but Pod Cannot Mount

Possible causes:

- CSI node plugin not running on selected node
- Node cannot reach storage backend
- Bad mount options
- Filesystem corruption
- Backend volume unavailable
- SELinux or permission issue
- Volume already attached elsewhere

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get pods -A -o wide | grep -i csi
oc debug node/<node>
```

### 27.6 PVC Expansion Stuck

Check:

```bash
oc describe pvc <pvc> -n <ns>
oc get pvc <pvc> -n <ns> -o yaml | yq '.status.conditions'
oc get sc <sc> -o yaml | grep allowVolumeExpansion
```

Possible causes:

- StorageClass expansion disabled
- Driver does not support resize
- Backend capacity exhausted
- Filesystem resize pending
- Pod needs restart
- Requested impossible size

### 27.7 Released PV Cannot Bind to New PVC

Cause:

- Old `claimRef` still exists

Check:

```bash
oc get pv <pv> -o yaml | yq '.spec.claimRef'
```

Fix carefully:

```bash
oc patch pv <pv> --type=json -p='[{"op":"remove","path":"/spec/claimRef"}]'
```

Then create a PVC with matching `volumeName`.

### 27.8 PVC Deletion Stuck Terminating

Check finalizers:

```bash
oc get pvc <pvc> -n <ns> -o yaml | yq '.metadata.finalizers'
```

Common finalizer:

```text
kubernetes.io/pvc-protection
```

This protects in-use PVCs from deletion.

Find pods using PVC:

```bash
oc get pods -n <ns> -o json | jq -r '
  .items[] |
  select(.spec.volumes[]? .persistentVolumeClaim.claimName == "<pvc>") |
  .metadata.name'
```

Do not remove finalizers casually. First remove workloads using the PVC.

## 28. Common Production Incidents and Fixes

### Incident 1: Developer Created PVC Without StorageClass

Problem:

```text
PVC Pending, no persistent volumes available, no storage class is set
```

Fix:

```bash
oc get sc
oc patch pvc <pvc> -n <ns> -p '{"spec":{"storageClassName":"standard"}}'
```

Note: Some PVC spec fields are immutable after creation depending on state. If patch fails, recreate the PVC with correct class.

### Incident 2: Default StorageClass Changed Accidentally

Impact:

- New PVCs provision on wrong backend
- Performance/cost/security issues

Fix:

```bash
oc get sc
oc annotate sc wrong storageclass.kubernetes.io/is-default-class- --overwrite
oc annotate sc correct storageclass.kubernetes.io/is-default-class="true" --overwrite
```

Then review recently created PVCs.

### Incident 3: Deleted PVC Removed Production Data

Cause:

- PV reclaim policy was `Delete`
- No backup tested

Preventive control:

- Use `Retain` for critical classes
- Use backup policy labels
- Restrict PVC deletion through RBAC/admission
- Require backup verification before deletion

### Incident 4: Database Deployment Scaled to 3 with One RWO PVC

Symptoms:

```text
Multi-Attach error
```

Fix:

- Scale to 1 immediately
- Convert to StatefulSet with per-replica PVCs
- Use database replication, not shared disk

### Incident 5: PVC Bound but App Cannot Write

Symptoms:

```text
permission denied
```

Fix:

- Check UID inside container
- Fix image to support arbitrary UID
- Use `fsGroup` if allowed
- Fix NFS permissions
- Avoid unnecessary root/anyuid

### Incident 6: PVC Pending with `WaitForFirstConsumer`

This may be normal until a pod uses it.

Check:

```bash
oc describe pvc <pvc> -n <ns>
```

Message may indicate waiting for first consumer.

Create the workload that references the PVC.

### Incident 7: Restore Created PVC but App Still Fails

Possible causes:

- Secrets not restored
- UID permissions changed
- Route/Service missing
- App expected old hostname
- StorageClass name differs in target cluster
- Snapshot restored crash-consistently but app needs logical recovery
- Operator CR not restored correctly

## 29. Performance and Capacity Planning

### 29.1 Capacity Planning Questions

For each PVC-backed app, ask:

- What is current used capacity?
- What is daily growth rate?
- What is retention period?
- Is expansion supported?
- Is online expansion supported?
- What happens at 80%, 90%, 95% usage?
- Is there a quota?
- Is there a backup window?
- How long does restore take?

### 29.2 Storage Tiering

Define clear tiers:

| Tier | Example | Use Case |
|---|---|---|
| gold | SSD / high IOPS | Database, critical apps |
| silver | balanced | App data, CI tools |
| bronze | low-cost | Archives, non-prod |
| shared-rwx | CephFS/NFS | Shared content |
| local-fast | NVMe local | Replicated high-performance apps |

### 29.3 IOPS and Throughput

PVC size may influence performance on some backends. For example, cloud disks often scale IOPS/throughput with disk size or configured class.

Admin checklist:

```bash
oc get pvc -A
oc get sc
oc describe sc <sc>
oc adm top pod -A
```

Also check backend dashboards for latency, queue depth, IOPS, and throughput.

### 29.4 Filesystem Choice

Common filesystems:

- `xfs`
- `ext4`

OpenShift RHCOS commonly uses XFS on host filesystems, but PVC filesystem depends on the storage class and driver parameters.

Filesystem choice can affect:

- Expansion behavior
- Performance
- Metadata-heavy workloads
- Snapshot behavior
- Repair procedures

### 29.5 Overprovisioning Risk

Storage backends may thin-provision. Kubernetes may show requested capacity as available, but backend physical pool may run out.

Monitor both:

- Kubernetes PVC requests
- Backend physical pool usage

## 31. Best Practices

### 31.1 PVC Design

- Always specify `storageClassName` for production workloads unless default behavior is intentional.
- Use meaningful PVC names.
- Use StatefulSet `volumeClaimTemplates` for replicated stateful workloads.
- Avoid one RWO PVC across multiple Deployment replicas.
- Use RWX only when the backend supports it and the application really needs shared writes.
- Avoid using storage as a substitute for application clustering.

### 31.2 StorageClass Design

- Maintain clear storage tiers.
- Use `WaitForFirstConsumer` for topology-aware storage.
- Enable `allowVolumeExpansion` only where supported and tested.
- Choose `Retain` for critical data classes if deletion safety is required.
- Avoid multiple default StorageClasses.
- Document backend mapping and expected performance.

### 31.3 Backup Design

- Do not treat snapshots as complete backups unless they are copied to a separate failure domain.
- Test restores regularly.
- Use application-aware backup for databases.
- Keep backup manifests and restore procedures in Git.
- Monitor backup jobs.
- Document RPO and RTO for each app.

### 31.4 Security

- Do not blindly use `anyuid` SCC.
- Prefer images compatible with arbitrary UID.
- Manage NFS permissions carefully.
- Protect PVC deletion with RBAC and process controls.
- Encrypt storage where supported.
- Keep tenant isolation in mind during PV reuse.

### 31.5 Operations

- Before deleting PVC, check reclaim policy.
- Before resizing PVC, check StorageClass and backend support.
- Before migrating storage, validate restore in non-prod.
- Monitor backend capacity, not only Kubernetes objects.
- Keep CSI driver versions aligned with OpenShift support matrix.

## 32. Interview and Real-World Scenario Questions

### Q1. What is the difference between PV and PVC?

PV is the cluster storage resource. PVC is a namespace-scoped request for that storage. Users create PVCs; admins or CSI provisioners provide PVs.

### Q2. Why is PVC stuck in Pending?

Possible reasons:

- No matching PV
- Missing StorageClass
- No default StorageClass
- CSI provisioner issue
- Backend capacity issue
- Unsupported access mode
- ResourceQuota exceeded
- Waiting for first consumer
- Topology conflict

### Q3. What happens when PVC is deleted?

It depends on the PV reclaim policy. With `Delete`, the PV and backend storage are usually deleted. With `Retain`, the PV and data remain for manual reclamation.

### Q4. Can two pods use the same PVC?

Yes, depending on access mode and scheduling. With RWO, multiple pods may use it only if allowed by backend and generally on the same node. For multi-node shared writes, use RWX storage.

### Q5. Why should StatefulSet use `volumeClaimTemplates`?

Each pod gets stable, independent storage. This avoids multiple replicas fighting over one PVC and supports stable identity.

### Q6. Is VolumeSnapshot a backup?

Not always. It is a point-in-time copy, often on the same storage backend. For backup, copy data/snapshots to another failure domain or use OADP/filesystem backup.

### Q7. Why does OpenShift show permission denied on PVC mount?

OpenShift often runs containers with arbitrary UIDs. The mounted filesystem may not be writable by that UID/GID. Fix image permissions, use `fsGroup`, adjust backend permissions, or use appropriate SCC only when justified.

### Q8. Can PVC be resized smaller?

Normally no. Expansion is supported if StorageClass and CSI driver allow it; shrinking requires migration to a new smaller PVC.

### Q9. What is `WaitForFirstConsumer`?

It delays volume binding/provisioning until a pod using the PVC is scheduled. This helps choose the correct zone/node topology.

### Q10. How do you restore a PVC from snapshot?

Create a new PVC with `dataSource` pointing to the `VolumeSnapshot`, ensure StorageClass compatibility, mount it to a restored workload, then validate application data.

## 33. Quick Command Cheat Sheet

```bash
# List PVCs in all namespaces
oc get pvc -A

oc get pvc -n <namespace>

oc describe pvc <pvc> -n <namespace>

oc annotate sc <sc> storageclass.kubernetes.io/is-default-class="true" --overwrite

oc annotate sc <sc> storageclass.kubernetes.io/is-default-class- --overwrite

# Expand PVC
oc patch pvc <pvc> -n <namespace> -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'

# Watch PVC
oc get pvc <pvc> -n <namespace> -w

# Check PVC events
oc get events -n <namespace> --sort-by=.lastTimestamp

# Patch PV reclaim policy to Retain
oc patch pv <pv> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'

oc get volumesnapshot -A

oc describe volumesnapshot <snapshot> -n <namespace>

oc get volumesnapshotclass
```

## Final Senior Admin Reminder

PVC administration is not only about creating storage. It is about protecting application data throughout its full lifecycle:

```text
Provision -> Bind -> Mount -> Secure -> Monitor -> Expand -> Snapshot -> Back up -> Restore -> Reclaim
```

Before touching production PVCs, always know:

1. Which application owns the PVC?
2. Which PV and backend volume does it map to?
3. Which reclaim policy applies?
4. Is there a tested backup?
5. Can the application tolerate crash-consistent restore?
6. What is the recovery plan if the operation fails?

A strong OpenShift administrator treats PVCs as production data assets, not just Kubernetes YAML objects.
