## 1. What is a PV?

A **PersistentVolume (PV)** is a cluster-level Kubernetes/OpenShift API object that represents a piece of storage available to workloads. It can represent storage from NFS, iSCSI, Fibre Channel, Ceph RBD, CephFS, AWS EBS, Azure Disk, Google Persistent Disk, VMware vSphere, local disk, LVM, or any storage backend exposed through a **Container Storage Interface (CSI)** driver.

In simple words:

> A PV is storage already known to the cluster. A PVC is a user request for that storage. A Pod consumes the PVC, not usually the PV directly.

A PV is similar to a node in the compute world:

| Compute side | Storage side |
|---|---|
| Node provides CPU and memory | PV provides storage capacity |
| Pod requests CPU/memory | PVC requests storage |
| Scheduler places Pod on node | PV controller binds PVC to PV |
| Node lifecycle affects workload | PV lifecycle affects persistent data |

Important characteristics:

- A PV is **cluster-scoped**, not namespace-scoped.
- A PVC is **namespace-scoped**.
- After a PV is bound to a PVC, that PV is effectively dedicated to that claim.
- A PV can be created manually by an administrator or dynamically by a storage provisioner.
- PVs are independent of Pod lifecycle; deleting a Pod should not delete the application data.

## 2. Why PV exists in OpenShift

Containers are ephemeral by nature. A container filesystem is recreated when the container is recreated. That is acceptable for stateless workloads, but not acceptable for databases, message queues, registries, CI/CD workspaces, monitoring systems, object gateways, and many enterprise applications.

Without PVs, every application team would need to know storage backend details such as:

- NFS server address and export path
- iSCSI target IQN and LUN ID
- Ceph pool and image name
- vSphere datastore and disk UUID
- AWS volume ID
- Azure disk URI
- Filesystem type
- Mount options
- Zone and topology placement
- Snapshot capability
- Expansion capability
- Backup integration

That is not scalable.

The PV framework separates responsibilities:

| Role | Responsibility |
|---|---|
| Storage admin | Provides storage backend and storage classes |
| Cluster admin | Configures CSI drivers, StorageClasses, quotas, monitoring, backup policies |
| Developer | Requests storage using PVC |
| OpenShift control plane | Binds PVC to PV and coordinates lifecycle |
| Kubelet / CSI node plugin | Mounts, formats, attaches, and exposes storage to Pods |

This abstraction allows developers to request storage without knowing the backend implementation.

## 3. PV, PVC, StorageClass, CSI, and Pod relationship

The storage flow is usually:

```text
Application Pod
    |
    | uses volumeMount
    v
PersistentVolumeClaim (PVC) - namespace-scoped request
    |
    | bound to
    v
PersistentVolume (PV) - cluster-scoped storage object
    |
    | provisioned by / backed by
    v
Storage backend via CSI driver, NFS, local disk, cloud disk, ODF, etc.
```

### Key objects

#### PersistentVolume

A PV describes actual storage available to the cluster.

Examples:

- `nfs.server: 192.168.10.50`
- `nfs.path: /exports/app01`
- `csi.driver: ebs.csi.aws.com`
- `local.path: /mnt/local-storage/disk1`
- `capacity.storage: 100Gi`
- `accessModes: [ReadWriteOnce]`
- `persistentVolumeReclaimPolicy: Retain`

#### PersistentVolumeClaim

A PVC is a request from a namespace.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
  namespace: production
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  storageClassName: fast-block
```

The user is saying:

> I need 20Gi storage, RWO access, from the `fast-block` storage class.

#### StorageClass

A StorageClass defines dynamic provisioning behavior.

It answers questions such as:

- Which CSI driver provisions the volume?
- What storage tier is used?
- Is volume expansion allowed?
- What reclaim policy is used?
- Is binding immediate or delayed until Pod scheduling?
- Which topology/zone is allowed?

#### CSI driver

CSI is the modern plugin interface between Kubernetes/OpenShift and external storage systems.

A CSI driver usually provides:

- Dynamic volume provisioning
- Attach/detach
- Node staging and publishing
- Mounting
- Filesystem creation
- Expansion
- Snapshot support
- Clone support
- Topology awareness

#### Pod

A Pod consumes storage through a PVC:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: production
spec:
  containers:
    - name: web
      image: registry.access.redhat.com/ubi9/nginx-120
      volumeMounts:
        - name: web-content
          mountPath: /usr/share/nginx/html
  volumes:
    - name: web-content
      persistentVolumeClaim:
        claimName: web-content-pvc
```

The Pod does not normally reference the PV name directly.

## 4. PV lifecycle in production

A PV passes through several lifecycle phases.

```text
Provisioning -> Available -> Bound -> Released -> Reclaimed / Deleted / Failed
```

### 4.1 Provisioning

Provisioning can be:

| Provisioning type | Description |
|---|---|
| Static | Admin manually creates the backend storage and PV object |
| Dynamic | PVC triggers CSI provisioner to create backend storage and PV automatically |

### 4.2 Available

The PV exists and is free.

```bash
oc get pv
```

Example:

```text
NAME      CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS
pv-nfs01  10Gi       RWX            Retain           Available           nfs-static
```

### 4.3 Bound

A PVC has claimed the PV.

```text
NAME      CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM              STORAGECLASS
pv-nfs01  10Gi       RWX            Retain           Bound    app/data-pvc       nfs-static
```

Once bound, a PV cannot be used by another PVC unless released and reclaimed correctly.

### 4.4 Released

The PVC was deleted, but the PV still remembers the old claim.

```text
STATUS: Released
CLAIM: old-namespace/old-pvc
```

This often happens with `Retain` reclaim policy.

A `Released` PV is not automatically available for a new PVC because old data may still exist.

### 4.5 Failed

The cluster attempted reclamation and failed.

Examples:

- Backend volume deletion failed
- CSI driver could not delete the disk
- Cloud credentials were invalid
- Storage API unavailable
- Finalizer could not complete

## 5. PV object anatomy

A common static NFS PV:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-app01
  labels:
    storage-tier: standard
    app: app01
spec:
  capacity:
    storage: 20Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs-static
  mountOptions:
    - hard
    - nfsvers=4.2
  nfs:
    server: 192.168.10.50
    path: /exports/app01
```

### Important fields

#### `metadata.name`

Unique PV name at cluster scope.

Use meaningful names:

```text
pv-<backend>-<app/env>-<number>
pv-nfs-prod-mysql-001
pv-local-worker03-db-001
pv-odf-rbd-prod-001
```

#### `metadata.labels`

Labels help with selection and operational ownership.

Useful labels:

```yaml
labels:
  env: prod
  owner: platform-team
  storage-tier: gold
  backup-policy: daily
  data-classification: confidential
```

#### `spec.capacity.storage`

Advertised capacity of the PV.

Important:

- PVC can bind to a PV larger than requested.
- A 10Gi PVC can bind to a 20Gi PV if all other criteria match.
- Capacity value does not always enforce backend quotas unless the backend enforces them.

#### `spec.volumeMode`

Defines how the volume is exposed:

- `Filesystem`
- `Block`

Default is `Filesystem` if omitted.

#### `spec.accessModes`

Defines supported access mode capability:

- `ReadWriteOnce`
- `ReadOnlyMany`
- `ReadWriteMany`
- `ReadWriteOncePod`

#### `spec.persistentVolumeReclaimPolicy`

Defines what happens when the PVC is deleted:

- `Retain`
- `Delete`
- `Recycle` deprecated and should not be used

#### `spec.storageClassName`

Class name used for matching with PVCs.

Important cases:

```yaml
storageClassName: fast
```

Means only PVCs requesting `fast` can bind.

```yaml
storageClassName: ""
```

Means classless PV. Only PVCs explicitly requesting no class can bind.

#### `spec.mountOptions`

Mount options passed to the mount operation.

Examples:

```yaml
mountOptions:
  - hard
  - nfsvers=4.2
  - noatime
```

Bad mount options can cause mount failure. Kubernetes does not deeply validate every mount option before runtime.

#### Backend-specific field

Examples:

```yaml
nfs:
  server: 192.168.10.50
  path: /exports/app01
```

```yaml
local:
  path: /mnt/local-storage/disk1
nodeAffinity:
  required:
    nodeSelectorTerms:
      - matchExpressions:
          - key: kubernetes.io/hostname
            operator: In
            values:
              - worker-03
```

```yaml
csi:
  driver: ebs.csi.aws.com
  volumeHandle: vol-0123456789abcdef
  fsType: xfs
```

## 6. Static provisioning vs dynamic provisioning

### Static provisioning

In static provisioning, the storage administrator creates storage first, then creates a PV object manually.

Flow:

```text
Storage admin creates NFS export / LUN / disk
Cluster admin creates PV YAML
Developer creates PVC
PVC binds to matching PV
Pod consumes PVC
```

Use static provisioning when:

- Using NFS exports manually created by storage team
- Using existing storage that must be reused
- Migrating legacy data into OpenShift
- Using local PVs
- Storage backend lacks a dynamic provisioner
- You need strict naming or manual lifecycle control
- Exam/lab task explicitly asks to create a PV

Advantages:

- Full control
- Easy to understand
- Good for labs and legacy environments
- Useful for Retain workflows

Disadvantages:

- Manual and slow
- Human error prone
- Not self-service
- Difficult at scale
- Reuse requires careful data wiping

### Dynamic provisioning

In dynamic provisioning, a user creates a PVC and the provisioner creates the backend volume and PV automatically.

Flow:

```text
Developer creates PVC with storageClassName
CSI provisioner creates backend volume
CSI provisioner creates PV object
PVC binds to PV
Pod consumes PVC
```

Use dynamic provisioning when:

- Running production platforms at scale
- Storage backend supports CSI
- Developers need self-service storage
- You need automation and consistency
- StatefulSets create per-replica PVCs

Advantages:

- Self-service
- Scalable
- Less manual YAML
- Integrated with snapshots/expansion/topology depending on CSI driver

Disadvantages:

- Requires working CSI driver
- Wrong StorageClass defaults can cause data loss or cost issues
- `Delete` reclaim policy may remove backend disks when PVCs are deleted
- Troubleshooting requires CSI knowledge

## 7. Access modes in depth

Access modes describe how a PV can be mounted.

| Access mode | Abbreviation | Meaning |
|---|---:|---|
| `ReadWriteOnce` | RWO | Read-write by a single node |
| `ReadOnlyMany` | ROX | Read-only by many nodes |
| `ReadWriteMany` | RWX | Read-write by many nodes |
| `ReadWriteOncePod` | RWOP | Read-write by only one Pod in the cluster; CSI only |

### 7.1 ReadWriteOnce (RWO)

RWO means the volume can be mounted read-write by one node at a time.

Important nuance:

- RWO is node-level, not always Pod-level.
- Multiple Pods on the same node may use the same RWO PVC, depending on workload and backend behavior.
- If Pods move to different nodes, attach/mount conflicts can occur.

Typical use cases:

- MySQL
- PostgreSQL
- MongoDB single replica volume
- Redis persistence
- Application data tied to one Pod

Common backends:

- AWS EBS
- Azure Disk
- GCP Persistent Disk
- VMware vSphere block volumes
- Ceph RBD
- LVM/local block

### 7.2 ReadWriteMany (RWX)

RWX means the volume can be mounted read-write by multiple nodes.

Typical use cases:

- Shared web content
- CI/CD shared workspace
- Shared uploads directory
- Application clusters requiring shared filesystem
- Some legacy applications

Common backends:

- NFS
- CephFS
- Gluster-like systems in older environments
- Some enterprise NAS systems
- OpenShift Data Foundation CephFS

Warning:

RWX solves shared mount access, not application-level locking. If multiple Pods write to the same files, the application must handle concurrency, locking, and corruption risk.

### 7.3 ReadOnlyMany (ROX)

ROX means many nodes can mount the volume read-only.

Use cases:

- Shared static content
- Reference datasets
- Model files
- Configuration bundles
- Read-only artifacts

### 7.4 ReadWriteOncePod (RWOP)

RWOP is stricter than RWO. It ensures the PVC is mounted read-write by only one Pod across the cluster.

Use cases:

- Workloads that must never have two active writers
- Strong single-writer guarantees
- CSI-backed database volumes

Practical warning:

RWOP requires CSI support. Do not assume every storage class supports it.

### 7.5 Access mode does not equal filesystem permission

Access mode is a scheduling and attachment/mount capability. It does not replace Linux permissions, SELinux labels, application locking, or backend export policy.

Example:

A PV declared as `ReadOnlyMany` is not a complete guarantee that the backend export itself is read-only unless the backend is configured that way.

## 8. Volume modes: Filesystem vs Block

A PV can be exposed as a filesystem or raw block device.

### 8.1 Filesystem mode

Most common mode.

```yaml
volumeMode: Filesystem
```

The volume is mounted as a directory inside the container.

Example:

```yaml
volumeMounts:
  - name: data
    mountPath: /var/lib/mysql
```

Use cases:

- Web content
- Application files
- Database data directory
- Logs
- Backups

Filesystem types commonly seen:

- `xfs`
- `ext4`

In RHEL/OpenShift environments, XFS is commonly preferred for enterprise Linux storage, but application and backend requirements should decide.

### 8.2 Block mode

```yaml
volumeMode: Block
```

The volume is exposed as a raw block device.

Pod uses `volumeDevices`, not `volumeMounts`.

Example:

```yaml
volumeDevices:
  - name: block-data
    devicePath: /dev/xvda
```

Use cases:

- Databases that manage their own storage layout
- High-performance workloads
- Specialized storage engines
- Virtualization workloads
- Applications that expect raw device access

Warnings:

- Application must know how to use raw block device.
- Backup tools must understand block-level consistency.
- Filesystem commands such as `df -h` may not show expected output inside container.

## 9. Reclaim policies

The reclaim policy controls what happens to the PV and backend storage after the bound PVC is deleted.

### 9.1 Retain

```yaml
persistentVolumeReclaimPolicy: Retain
```

Behavior:

- PVC is deleted.
- PV moves to `Released`.
- Backend storage remains.
- Data remains.
- Admin must manually reclaim, wipe, reuse, or delete.

Use Retain for:

- Production databases
- Critical data
- Compliance workloads
- Manual recovery scenarios
- Migration use cases
- Exam/lab tasks where data must remain after PVC deletion

Example:

```bash
oc patch pv pv-prod-db-001 -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
```

Manual reclaim flow:

```bash
oc get pv pv-prod-db-001
oc delete pvc db-data -n prod
oc get pv pv-prod-db-001
# PV should show Released

# Verify backend data manually before deleting or reusing
# Then either create backup, wipe data, or create a new PV pointing to same backend path/disk.
```

### 9.2 Delete

```yaml
persistentVolumeReclaimPolicy: Delete
```

Behavior:

- PVC is deleted.
- PV is deleted.
- Backend storage asset is usually deleted by the provisioner.

Use Delete for:

- Temporary environments
- Dev/test workloads
- Disposable CI volumes
- Ephemeral data with no retention requirement
- Dynamically provisioned volumes where deletion is expected

Warning:

For production, `Delete` can be dangerous if users delete PVCs accidentally. Use RBAC, backup, admission controls, and clear storage class naming.

### 9.3 Recycle

`Recycle` is deprecated and should not be used.

Old behavior was a basic scrub of data. Modern clusters should use dynamic provisioning or manual cleanup with Retain.

## 10. Binding logic and matching rules

PVC-to-PV binding is handled by the control plane.

A PVC can bind to a PV when these match:

- Requested capacity is less than or equal to PV capacity
- Access mode is compatible
- StorageClass matches
- Volume mode matches
- Selector labels match, if used
- PV is Available

### 10.1 Capacity matching

PVC:

```yaml
resources:
  requests:
    storage: 5Gi
```

PV:

```yaml
capacity:
  storage: 10Gi
```

This can bind because 10Gi satisfies 5Gi.

But the reverse cannot bind:

- PVC requests 20Gi
- PV provides 10Gi

### 10.2 StorageClass matching

PVC:

```yaml
storageClassName: nfs-static
```

PV:

```yaml
storageClassName: nfs-static
```

This can bind.

If the PVC requests `fast-block` and the PV has `nfs-static`, it will not bind.

### 10.3 Classless PV/PVC

For a classless static PV:

PV:

```yaml
storageClassName: ""
```

PVC:

```yaml
storageClassName: ""
```

This is important in clusters with a default StorageClass. If you omit `storageClassName` in a PVC, admission may inject the default class. To request no class, explicitly use an empty string.

### 10.4 Selector matching

PV:

```yaml
metadata:
  labels:
    app: reports
    tier: archive
```

PVC:

```yaml
selector:
  matchLabels:
    app: reports
    tier: archive
```

The PVC only binds to PVs with matching labels.

### 10.5 Pre-binding with `volumeName`

PVC:

```yaml
spec:
  volumeName: pv-nfs-prod-001
```

This tells the control plane to bind to a specific PV, if valid.

### 10.6 Pre-binding with `claimRef`

PV:

```yaml
spec:
  claimRef:
    namespace: prod
    name: db-data
```

This reserves the PV for a specific PVC.

Use this carefully. Wrong claimRef is a common cause of PVC Pending issues.

## 11. StorageClass awareness

Even though this file focuses on PV, a senior OpenShift admin must always understand the StorageClass behind dynamically provisioned PVs.

Example StorageClass:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-rwo
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"
provisioner: csi.example.com
parameters:
  type: ssd
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

Important fields:

| Field | Why it matters |
|---|---|
| `provisioner` | CSI driver used to create PV |
| `parameters` | Backend-specific options like disk type, pool, zone, filesystem |
| `reclaimPolicy` | Default reclaim policy for dynamically created PVs |
| `allowVolumeExpansion` | Whether PVC size can be increased |
| `volumeBindingMode` | Whether PV is created immediately or after Pod scheduling |
| `mountOptions` | Mount behavior for volumes |

### 11.1 `Immediate` vs `WaitForFirstConsumer`

#### Immediate

PV is provisioned as soon as PVC is created.

Risk:

- In topology-aware environments, a disk may be created in a zone where the Pod cannot run.

#### WaitForFirstConsumer

PV provisioning waits until a Pod uses the PVC. This allows scheduler topology decisions to influence where the volume is created.

Recommended for:

- Cloud block storage
- Local storage
- Zone-aware CSI drivers
- Multi-zone clusters

## 12. CSI driver role in modern OpenShift storage

Modern OpenShift storage relies heavily on CSI.

CSI separates Kubernetes from storage vendor implementation. Instead of embedding storage plugins inside Kubernetes, storage vendors provide CSI drivers.

CSI components commonly include:

| Component | Role |
|---|---|
| CSI controller plugin | Provision, delete, attach, detach, snapshot, expand |
| CSI node plugin | Mount, unmount, stage, publish volumes on nodes |
| External provisioner | Watches PVCs and creates PVs |
| External attacher | Handles volume attachment where required |
| External resizer | Handles expansion |
| External snapshotter | Handles VolumeSnapshot objects |
| Storage backend API | Actual disk/filesystem creation and management |

### What happens when a Pod starts with a PVC

```text
1. Pod references PVC.
2. PVC is already bound or triggers dynamic provisioning.
3. Scheduler selects a node, considering storage topology if needed.
4. Attach/detach controller or CSI attacher attaches volume if backend requires attachment.
5. Kubelet calls CSI node plugin.
6. CSI node plugin stages volume.
7. Filesystem may be formatted if empty and Filesystem mode is used.
8. Volume is mounted into the Pod.
9. Container sees path or block device.
```

### CSI troubleshooting namespaces

CSI drivers usually run in platform namespaces such as:

```bash
oc get pods -A | grep -i csi
oc get csidriver
oc get storageclass
```

For OpenShift Data Foundation or vendor storage, also check the operator namespace:

```bash
oc get co
oc get pods -n openshift-storage
oc get csv -A | grep -i storage
```

## 13. Common PV backends

### 13.1 NFS

Characteristics:

- Common for RWX
- Simple and widely understood
- Good for shared files
- Performance depends on network and NFS server
- Backup can happen at NAS level or application level

Pros:

- Easy static PVs
- Supports RWX
- Good for labs and shared web content

Cons:

- Single NFS server can become bottleneck/SPOF if not HA
- File locking issues can affect applications
- Permission and UID/GID problems are common
- Not ideal for high-performance databases unless designed carefully

### 13.2 Ceph RBD

Characteristics:

- Block storage
- Usually RWO
- Good for databases
- Snapshot/clone capable depending on CSI integration

Typical in OpenShift Data Foundation for block volumes.

### 13.3 CephFS

Characteristics:

- Distributed filesystem
- RWX capable
- Useful for shared application data
- Snapshot support depends on deployment and CSI capabilities

### 13.4 Cloud block storage

Examples:

- AWS EBS
- Azure Disk
- Google Persistent Disk

Characteristics:

- Usually RWO
- Zone-aware
- Dynamic provisioning common
- Expansion and snapshot usually supported
- Attach/detach delays can affect failover time

### 13.5 VMware vSphere

Characteristics:

- CSI-backed vSphere volumes
- Enterprise virtualization storage
- Often RWO block volumes
- Datastore policy and topology matter

### 13.6 Local PV

Characteristics:

- Storage tied to a specific node
- High local performance
- No automatic node-level HA
- Requires node affinity
- Good for specific high-performance or edge workloads

Use only when the application handles replication or data loss risk is accepted.

### 13.7 LVM Storage / LVMS

Characteristics:

- Useful for local dynamic provisioning on bare metal or edge-style deployments
- RWO oriented
- Node-local constraints apply
- Good for compact clusters and single-node OpenShift use cases

## 14. NFS static PV example

### 14.1 Prepare NFS server

On NFS server:

```bash
mkdir -p /exports/landing
chmod 0777 /exports/landing
chown -R nfsnobody:nfsnobody /exports/landing
```

Example `/etc/exports`:

```text
/exports/landing 10.0.0.0/24(rw,sync,no_root_squash)
```

Export:

```bash
exportfs -rav
exportfs -v
```

From an OpenShift node, validate:

```bash
showmount -e <nfs-server>
mount -t nfs <nfs-server>:/exports/landing /mnt
```

### 14.2 Create PV

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: landing-pv
  labels:
    app: landing
    storage: nfs
spec:
  capacity:
    storage: 1Gi
  volumeMode: Filesystem
  accessModes:
    - ReadOnlyMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs-static
  mountOptions:
    - hard
    - nfsvers=4.2
  nfs:
    server: 192.168.100.10
    path: /exports/landing
```

Apply:

```bash
oc apply -f landing-pv.yaml
oc get pv landing-pv
```

### 14.3 Create PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: landing-pvc
```

## 15. Local PV example and warnings

Local PVs expose storage physically attached to a node.

### Why local PV is risky

If the node dies, the PV is unavailable. Kubernetes cannot magically move local disk data to another node.

Use local PV only when:

- Application replicates data itself
- Workload is node-specific
- Edge/SNO design accepts the risk
- Performance requirement justifies locality
- Backup is clearly designed

### Example local PV

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-pv-worker03-db01
spec:
  capacity:
    storage: 100Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-storage
  local:
    path: /mnt/local-storage/db01
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - worker03.example.com
```

Important:

- `nodeAffinity` is mandatory for local PVs.
- The Pod using this PVC must be scheduled on the same node.
- Do not use local PV for random multi-replica shared workloads.

Validate:

```bash
oc get pv local-pv-worker03-db01 -o yaml
oc get pvc -A | grep local-pv-worker03-db01
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
```

## 17. Pre-binding PV to PVC

Pre-binding is useful when a specific PV must be consumed by a specific PVC.

### 17.1 PVC uses `volumeName`

```yaml
apiVersion: v1

metadata:
  name: app-data
  namespace: prod

    - ReadWriteMany
```

### 17.2 PV uses `claimRef`

```yaml
apiVersion: v1

metadata:
  name: pv-prod-app-data-001

  capacity:
    storage: 50Gi
  accessModes:
```

## 18. StatefulSet and PV behavior

StatefulSets usually use `volumeClaimTemplates`.

Example:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: db
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: registry.redhat.io/rhel9/mysql-80
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: fast-rwo
        resources:
          requests:
            storage: 20Gi
```

This creates PVCs such as:

```text
data-mysql-0
data-mysql-1
data-mysql-2
```

Each replica gets its own PVC and usually its own PV.

Important operational behavior:

- Scaling down StatefulSet does not automatically delete PVCs.
- Deleting StatefulSet does not necessarily delete PVCs.
- PVC retention behavior must be understood before cleanup.
- Recreating a StatefulSet with the same name can reuse existing PVCs.

Validate:

```bash
oc get sts -n db
oc get pvc -n db
oc get pv | grep db
```

## 19. PV security in OpenShift

Storage security is not only about Kubernetes YAML. It includes:

- Namespace isolation
- RBAC for PVC create/delete
- SCC restrictions
- SELinux labeling
- Linux UID/GID permissions
- NFS export policy
- Storage backend ACLs
- Encryption at rest
- Encryption in transit
- Snapshot access
- Backup repository access
- Reclaim policy
- Data sanitization

### 19.1 Namespace boundary

PVCs are namespace-scoped. A Pod in namespace `app1` cannot directly reference a PVC in namespace `app2`.

However, PVs are cluster-scoped. A misconfigured Available PV can be claimed by a PVC from another namespace if it matches.

For sensitive static PVs:

- Use `claimRef` to reserve the PV.
- Use unique `storageClassName`.
- Use label selectors.
- Use RBAC to control PVC creation.
- Use Retain for production data.

### 19.2 RBAC controls

Check who can create PVCs:

```bash
oc auth can-i create persistentvolumeclaims -n prod --as <user>
oc auth can-i delete persistentvolumeclaims -n prod --as <user>
oc auth can-i create persistentvolumes --as <user>
```

Usually:

- Developers can create PVCs in their namespaces.
- Only cluster admins can create PVs.
- Storage admin roles should be tightly controlled.

### 19.3 Sensitive data leakage risk

Risk scenario:

1. PV uses Retain.
2. PVC is deleted.
3. PV becomes Released.
4. Admin clears claimRef without wiping data.
5. Another namespace claims the PV.
6. New application sees old data.

Safe process:

```text
Released PV -> verify owner -> backup if required -> wipe/sanitize backend -> remove old claimRef -> mark Available or create new PV
```

Never reuse retained PV storage without data sanitization.

## 20. SELinux, SCC, fsGroup, permissions, and mount problems

OpenShift runs containers with strong security defaults. Storage permissions often fail because the storage backend was prepared for root or fixed UIDs, while OpenShift runs Pods with randomized UIDs.

### 20.1 Common symptom

Pod starts but application logs show:

```text
Permission denied
cannot create directory
failed to write file
operation not permitted
```

Check:

```bash
oc logs <pod> -n <ns>
oc describe pod <pod> -n <ns>
oc rsh <pod> -n <ns> id
oc rsh <pod> -n <ns> ls -ld <mount-path>
```

### 20.2 Random UID behavior

OpenShift often runs containers with a random high UID from a namespace UID range.

Inside Pod:

```bash
id
```

Example:

```text
uid=1000790000 gid=0(root) groups=0(root),1000790000
```

If the mounted directory is owned by `root:root` and mode `0755`, the app may not write.

### 20.3 Fixing NFS permissions

For shared NFS test/lab:

```bash
chmod -R 0777 /exports/app
```

For production, prefer group-based permissions:

```bash
chgrp -R 0 /exports/app
chmod -R g+rwX /exports/app
```

Many Red Hat container images are designed to work with group `0` writable directories.

### 20.4 `fsGroup`

Example:

```yaml
securityContext:
  fsGroup: 2000
```

This can help with volume ownership, depending on backend and driver support.

Warning:

- `fsGroup` behavior differs by volume type and CSI driver.
- Large volume recursive ownership changes can delay Pod startup.

### 20.5 SCC and privileged storage operations

Some workloads request root, hostPath, or privileged behavior. In OpenShift, SCC controls this.

Example check:

```bash
oc describe pod <pod> -n <ns> | grep -i scc
oc get scc
```

Granting broad SCC like `privileged` or `anyuid` should be done only when justified.

Example:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

Do not use SCC as the first fix for storage permissions. First verify UID/GID, backend permissions, SELinux, and image expectations.

### 20.6 SELinux considerations

SELinux can deny access when labels are incompatible, especially for hostPath/local path usage.

Check node logs:

```bash
oc debug node/<node-name>
chroot /host
ausearch -m avc -ts recent
journalctl -t setroubleshoot --since "1 hour ago"
```

For NFS, SELinux booleans and context handling depend on host configuration and workload pattern. Avoid unsupported manual changes on RHCOS nodes unless you understand MachineConfig-based persistence.

## 21. Capacity planning and performance

A senior admin should not treat PV capacity as just `Gi` in YAML. Storage design impacts application stability.

### 21.1 Questions before choosing PV backend

Ask:

1. Is the workload stateful or stateless?
2. Does it need RWO or RWX?
3. Does it need low latency or high throughput?
4. Does it need snapshots?
5. Does it need online expansion?
6. Does it need encryption?
7. What is the RPO/RTO?
8. What is expected growth per day/month?
9. How many replicas write concurrently?
10. What happens if the node or zone fails?
11. Is backup crash-consistent or application-consistent?
12. Are there compliance retention requirements?

### 21.2 Capacity metrics to monitor

Monitor at least:

- PVC requested capacity
- Actual filesystem usage
- Inode usage
- Backend pool usage
- Thin pool usage
- Snapshot usage
- Volume expansion failures
- PV Pending/Released/Failed counts
- CSI provisioner errors
- Attach/detach latency
- Mount failures

Commands:

```bash
oc get pvc -A
oc get pv
oc adm top pod -A
oc rsh <pod> df -h
oc rsh <pod> df -i
```

### 21.3 Performance dimensions

| Dimension | Meaning |
|---|---|
| IOPS | Small random read/write operations |
| Throughput | Large sequential read/write bandwidth |
| Latency | Time per storage operation |
| Queue depth | Parallel IO capability |
| fsync latency | Critical for databases |
| Metadata performance | Important for many small files |
| Network latency | Important for NFS/Ceph/cloud storage |

### 21.4 Backend choice examples

| Workload | Recommended pattern |
|---|---|
| PostgreSQL | RWO block, fast SSD, snapshot + logical backup |
| MySQL | RWO block, careful fsync latency, app-consistent backup |
| Shared web files | RWX NFS/CephFS |
| CI workspace | RWX if shared; RWO per worker if isolated |
| Logging stack | StorageClass recommended by vendor/operator |
| Monitoring | Reliable RWO or ODF-backed storage |
| VM disks | CSI block storage with virtualization support |
| Edge/SNO | LVM/local storage with clear backup plan |

## 22. Backup and restore awareness

PV backup is one of the most misunderstood OpenShift topics.

A PV object is not the data. The PV object is metadata. The backend disk/filesystem contains the data.

### 22.1 What must be backed up?

For a stateful application, backup must include:

| Layer | Examples |
|---|---|
| Kubernetes objects | Namespace, Deployment, StatefulSet, Service, Route, Secret, ConfigMap, PVC |
| PV metadata | PV object, reclaim policy, volume handle, labels |
| Storage data | Files/database contents inside backend volume |
| Application consistency | DB flush, quiesce, transaction logs, backup hooks |
| Security material | Secrets, TLS certs, encryption keys |
| Operator CRs | Custom resources that define the app |

Backing up only YAML does not back up database data.

Backing up only disk data does not guarantee application can be restored cleanly.

### 22.2 Crash-consistent vs application-consistent

#### Crash-consistent backup

Snapshot captures the volume at a point in time without coordinating with the application.

Good for:

- Filesystems with journaling
- Some resilient applications
- Non-critical dev workloads

Risk:

- Database may require recovery
- In-flight transactions may be lost
- Multi-volume apps may be inconsistent

#### Application-consistent backup

Application is quiesced or backup-aware commands are run.

Examples:

- `pg_dump` or PostgreSQL base backup
- MySQL `FLUSH TABLES WITH READ LOCK` or backup tool
- MongoDB backup commands
- Velero/OADP backup hooks
- Filesystem freeze for some workloads

Use this for production databases.

### 22.3 Backup architecture patterns

#### Pattern A: Application-native backup

Example:

- PostgreSQL dumps to object storage
- MySQL backup to S3-compatible bucket
- MongoDB Ops Manager backup

Pros:

- Application-consistent
- Portable across clusters
- Good for logical restore

Cons:

- Restore may be slower
- Requires app-specific knowledge

#### Pattern B: CSI snapshots

CSI creates point-in-time volume snapshots.

Pros:

- Fast
- Storage-integrated
- Good for quick restore/clones

Cons:

- Depends on CSI driver
- May be crash-consistent unless hooks used
- Snapshot may remain in same failure domain unless moved/exported

#### Pattern C: OADP/Velero with CSI snapshots or filesystem backup

OADP protects Kubernetes resources and can integrate with PV backup mechanisms.

Pros:

- OpenShift-aware
- Namespace/application-level backup
- Useful for migration and DR

Cons:

- Requires correct configuration
- Not all volume types behave the same
- Backup hooks and restore ordering matter

#### Pattern D: Storage-array backup

Enterprise storage handles snapshots/replication.

Pros:

- Powerful and mature
- Good for large environments

Cons:

- Kubernetes metadata may not be included
- Restore coordination with PVC/PV objects is required

### 22.4 RPO and RTO

| Term | Meaning | PV implication |
|---|---|---|
| RPO | How much data loss is acceptable | Backup frequency, replication, WAL/archive logs |
| RTO | How long restore can take | Snapshot restore speed, app startup, data size |

Example:

- RPO 24h: nightly backup may be enough.
- RPO 5m: need frequent snapshots, logs, replication, or app-native continuous backup.
- RTO 15m: restore must be automated and tested.

### 22.5 Backup validation

A backup is not successful until restore is tested.

Validate:

```bash
# Restore into test namespace
oc get all -n restore-test
oc get pvc -n restore-test
oc get pv | grep restore-test
oc logs -n restore-test deploy/<app>
oc exec -n restore-test <pod> -- <app-health-command>
```

For databases:

```bash
# Example only; use application-specific validation
oc rsh -n restore-test <db-pod>
mysql -e 'select count(*) from important_table;'
psql -c 'select count(*) from important_table;'
```

## 23. Snapshots, clones, and OADP

### 23.1 VolumeSnapshot

A `VolumeSnapshot` is a request for a point-in-time snapshot of a PVC.

Objects involved:

| Object | Purpose |
|---|---|
| `VolumeSnapshotClass` | Defines snapshot driver and deletion policy |
| `VolumeSnapshot` | User request for snapshot |
| `VolumeSnapshotContent` | Cluster-level snapshot object |
| PVC restore | New PVC can be created from snapshot |

Example VolumeSnapshot:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-data-snap-001
  namespace: db
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: mysql-data
```

Check:

```bash
oc get volumesnapshot -n db
oc describe volumesnapshot mysql-data-snap-001 -n db
oc get volumesnapshotcontent
```

### 23.2 Restore PVC from snapshot

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-restore
  namespace: db-restore
spec:
  storageClassName: fast-rwo
  dataSource:
    name: mysql-data-snap-001
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

### 23.3 Volume clone

A clone duplicates an existing PVC into a new PVC, when supported by the CSI driver.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-clone
  namespace: db
spec:
  storageClassName: fast-rwo
  dataSource:
    name: mysql-data
    kind: PersistentVolumeClaim
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

### 23.4 OADP awareness

OpenShift API for Data Protection (OADP) is commonly used for application backup and restore. For PV data, OADP can use CSI snapshots and file-system backup approaches depending on configuration and version.

An OADP-aware admin should verify:

```bash
oc get dpa -A
oc get backupstoragelocation -A
oc get volumesnapshotclass
oc get backup -A
oc get restore -A
```

Backup planning checklist:

- Is the application namespace included?
- Are PVCs included?
- Is CSI snapshot enabled?
- Does the StorageClass support snapshots?
- Is there a VolumeSnapshotClass?
- Is the snapshot deletion policy correct?
- Are backups copied to remote object storage?
- Are Secrets included and protected?
- Are restore hooks needed?
- Has restore been tested?

## 24. PV expansion

PV expansion usually starts by editing the PVC request size, not the PV directly.

Example:

```bash
oc patch pvc mysql-data -n db -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'
```

Watch:

```bash
oc get pvc mysql-data -n db -w
oc describe pvc mysql-data -n db
```

### Requirements

- StorageClass has `allowVolumeExpansion: true`.
- CSI driver supports expansion.
- Dynamic provisioning is typically used.
- Requested size must increase, not decrease.

### Shrinking is not supported

You cannot reduce a PVC from 100Gi to 50Gi using normal Kubernetes/OpenShift volume expansion.

To shrink:

1. Create smaller PVC.
2. Copy data carefully.
3. Validate application.
4. Switch workload.
5. Delete old PVC only after backup and validation.

### Filesystem resize

Depending on driver and filesystem, expansion may complete:

- Online while Pod is running
- After Pod restart
- After filesystem resize operation

Check PVC conditions:

```bash
oc get pvc mysql-data -n db -o yaml | yq '.status.conditions'
```

## 26.3 PV stuck Released

### Cause

PVC was deleted and reclaim policy is `Retain`.

### Safe resolution

1. Identify old claim:

```bash
oc get pv <pv-name> -o yaml | yq '.spec.claimRef'
```

2. Confirm data owner and retention requirement.
3. Back up data if needed.
4. Wipe backend if reusing.
5. Remove old claimRef only after data is handled.

Patch example:

```bash
oc patch pv <pv-name> --type json -p '[{"op":"remove","path":"/spec/claimRef"}]'
```

Warning:

Do not remove claimRef and reuse a PV containing sensitive old data.

## 26.4 PV/PVC terminating forever

### Symptoms

```bash
oc get pvc -n app
```

```text
app-data   Terminating
```

Check finalizers:

```bash
oc get pvc app-data -n app -o yaml | yq '.metadata.finalizers'
oc get pv <pv-name> -o yaml | yq '.metadata.finalizers'
```

Common finalizers:

```text
kubernetes.io/pvc-protection
kubernetes.io/pv-protection
external-provisioner.volume.kubernetes.io/finalizer
```

### Safe approach

1. Check if Pod still uses PVC:

```bash
oc get pods -n app -o yaml | grep -B5 -A5 app-data
```

2. Scale down workload:

```bash
oc scale deploy/<name> -n app --replicas=0
oc scale sts/<name> -n app --replicas=0
```

3. Check CSI backend deletion status.
4. Remove finalizers only as a last resort after confirming no live dependency.

Emergency finalizer removal:

```bash
oc patch pvc app-data -n app --type json -p '[{"op":"remove","path":"/metadata/finalizers"}]'
```

Warning:

Manual finalizer removal can orphan backend storage or cause data loss.

## 26.5 Multi-attach error

### Symptoms

```text
Multi-Attach error for volume "pvc-..." Volume is already exclusively attached to one node and cannot be attached to another
```

Common with RWO block storage.

### Causes

- Pod rescheduled to another node while old attachment remains
- Node NotReady
- Force delete caused stale attachment
- Cloud/storage backend detach delay
- Application has multiple replicas using same RWO PVC

### Fix

```bash
oc get pods -n app -o wide
oc get volumeattachment
oc describe volumeattachment <name>
oc get node
```

Actions:

- Ensure only one Pod uses the RWO PVC.
- Wait for detach if node is healthy.
- Investigate stuck VolumeAttachment.
- Resolve node NotReady.
- Do not blindly delete VolumeAttachment unless you understand backend state.

## 26.6 Permission denied after mount

Check:

```bash
oc rsh <pod> -n app id
oc rsh <pod> -n app ls -ld /data
oc logs <pod> -n app
```

Fix strategy:

- Set backend directory group writable.
- Use group `0` for Red Hat images where appropriate.
- Use `fsGroup` if supported.
- Avoid running as root unless necessary.
- Avoid broad SCC changes unless justified.

- Rotate logs.

## 27. Real-world incident scenarios

### Scenario 1: Production database PVC accidentally deleted

#### Situation

- PVC `mysql-data` deleted in namespace `prod`.
- PV reclaim policy is `Delete`.
- CSI provisioner deletes backend disk.

#### Impact

Data loss unless backup/snapshot exists.

#### Prevention

- Use Retain for critical storage classes or patch critical PVs.
- Restrict PVC delete permissions in production.
- Use OADP/Velero backups.
- Use database-native backups.
- Enable snapshot schedules if available.
- Add admission policy to prevent deleting PVCs with label `critical=true`.

#### Recovery

- Stop application.
- Identify latest backup/snapshot.
- Restore PVC.
- Restore database.
- Validate data.
- Run RCA.

---

### Scenario 2: PVC Pending after creating static PV

#### Situation

PVC:

```yaml
storageClassName: ""
accessModes:
  - ReadWriteMany
resources:
  requests:
    storage: 5Gi
```

PV:

```yaml
storageClassName: nfs-static
accessModes:
  - ReadWriteMany
capacity:
  storage: 5Gi
```

#### Problem

StorageClass mismatch. PVC asks for classless PV, but PV has `nfs-static`.

#### Fix

Either update PVC to use `nfs-static` or recreate PV/PVC consistently.

---

### Scenario 3: NFS PV bound but Pod cannot write

#### Situation

PVC Bound, Pod Running, app logs show permission denied.

#### Root cause

OpenShift random UID cannot write to NFS export owned by root with `0755`.

#### Fix

On NFS server:

```bash
chgrp -R 0 /exports/app
chmod -R g+rwX /exports/app
```

Or set appropriate POSIX ACLs.

---

### Scenario 4: Local PV workload stuck Pending

#### Situation

PVC bound to local PV on `worker-03`, but Pod has nodeSelector for `worker-05`.

#### Root cause

PV node affinity conflicts with Pod scheduling constraints.

#### Fix

- Remove incorrect nodeSelector.
- Schedule Pod to node where local PV exists.
- Use topology-aware scheduling.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc describe pv <pv>
```

---

### Scenario 5: StatefulSet scaled to 3 but all replicas use same PVC

#### Situation

Deployment or StatefulSet manually configured all replicas with one RWO PVC.

#### Problem

Only one node can mount the RWO volume read-write.

#### Fix

- For StatefulSet, use `volumeClaimTemplates`.
- For shared data, use RWX backend.
- For database clustering, use separate PVC per replica.

## 28. Production best practices

### 28.1 Naming standards

Use predictable names.

```text
StorageClass:
  sc-<backend>-<tier>-<access>-<region>
  sc-odf-gold-rwo
  sc-cephfs-shared-rwx
  sc-nfs-standard-rwx

PV:
  pv-<backend>-<env>-<app>-<id>
  pv-nfs-prod-reports-001

PVC:
  <app>-<purpose>
  mysql-data
  uploads-shared
  prometheus-data
```

### 28.2 Label everything

For PVs:

```yaml
labels:
  env: prod
  app: payments
  owner: platform
  backup-policy: gold
  data-classification: confidential
```

For PVCs:

```yaml
labels:
  app: payments
  backup: enabled
  critical: "true"
```

### 28.3 Use separate StorageClasses by policy

Do not use one generic `standard` class for everything.

Create policy-based classes:

| StorageClass | Purpose |
|---|---|
| `gold-rwo-retain` | Critical DB volumes |
| `silver-rwo-delete` | Normal app data |
| `shared-rwx-retain` | Shared file data |
| `ci-temp-delete` | CI temporary volumes |
| `local-rwo-retain` | Local high-performance workloads |

### 28.4 Choose reclaim policy deliberately

| Environment | Suggested default |
|---|---|
| Production critical | Retain |
| Production non-critical | Depends on backup maturity |
| Development | Delete |
| CI/CD temporary | Delete |
| Migration | Retain |

### 28.5 Use quotas

Prevent uncontrolled PVC growth.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: storage-quota
  namespace: app
spec:
  hard:
    requests.storage: 500Gi
    persistentvolumeclaims: "20"
```

StorageClass-specific quota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: fast-storage-quota
  namespace: app
spec:
  hard:
    fast-rwo.storageclass.storage.k8s.io/requests.storage: 200Gi
```

### 28.6 Protect production PVC deletion

Options:

- RBAC: limit delete permission.
- Admission control: block PVC deletion with critical labels.
- Backup policy: require backup label for production PVC.
- Reclaim policy: use Retain.
- Change management: deletion requires approval.

### 28.7 Test restore regularly

Minimum restore test schedule:

| Environment | Restore test frequency |
|---|---|
| Critical production | Monthly or quarterly |
| Regulated workloads | As required by compliance |
| Standard production | Quarterly or twice yearly |
| Dev/test | As needed |

### 28.8 Avoid hostPath in production

`hostPath` directly mounts node filesystem paths into Pods. It is dangerous and not portable.

Use local PV, CSI, NFS, or supported storage operators instead.

### 28.9 Do not assume RWX means safe concurrent writes

RWX allows multiple mounts. It does not make your application cluster-safe.

Applications must handle:

- File locking
- Write ordering
- Concurrent updates
- Cache consistency
- Split-brain behavior

### 28.10 Document storage ownership

For every production PVC, document:

- Namespace
- Application owner
- Business owner
- StorageClass
- Backend
- Reclaim policy
- Backup policy
- RPO/RTO
- Expansion process
- Restore process
- Data classification

## 29. Interview and exam style questions

### Q1. What is the difference between PV and PVC?

A PV is a cluster-scoped storage resource. A PVC is a namespace-scoped request for storage. Pods consume PVCs; the control plane binds PVCs to suitable PVs.

### Q2. Why is a PV stuck in Released state?

Usually because the bound PVC was deleted and the PV has `Retain` reclaim policy. The PV still contains old data and claim reference. Admin must manually reclaim it.

### Q3. Can one PV bind to multiple PVCs?

No. After a PV is bound to a PVC, it cannot be bound to another PVC at the same time.

### Q4. What is the difference between RWO and RWX?

RWO allows read-write mount by a single node. RWX allows read-write mount by multiple nodes, if the backend supports it.

### Q5. Why is PVC Pending even though PV exists?

Common reasons:

- StorageClass mismatch
- Access mode mismatch
- PVC requests more capacity than PV offers
- VolumeMode mismatch
- PV already bound or released
- PVC selector does not match PV labels
- claimRef reserves PV for another PVC

### Q6. What happens when PVC is deleted and reclaim policy is Delete?

The PV object and backend storage are typically deleted by the provisioner, if the backend supports deletion and finalizers complete successfully.

### Q7. What happens when PVC is deleted and reclaim policy is Retain?

The PV remains, backend data remains, and PV moves to Released. Manual admin action is required.

### Q8. How do you expand a PVC?

Ensure StorageClass allows expansion and CSI driver supports it, then increase `.spec.resources.requests.storage` on the PVC.

### Q9. Can PV be shrunk?

No. Shrinking PV/PVC is not supported through normal Kubernetes/OpenShift volume expansion.

### Q10. What is `WaitForFirstConsumer`?

It delays dynamic provisioning and binding until a Pod uses the PVC, allowing scheduling topology such as zone or node constraints to be considered.

### Q11. Why is local PV not highly available?

Because data is tied to one node's local disk. If the node fails, the data is unavailable unless the application or backup system provides replication/recovery.

### Q12. What is the correct backup strategy for a database PV?

Use application-consistent database backup and/or CSI snapshots with quiesce hooks. Also back up Kubernetes resources, secrets, PVC metadata, and test restore regularly.

## 31. Summary

A PersistentVolume is not just a YAML object. In production OpenShift administration, a PV represents a contract between the cluster, workload, CSI driver, storage backend, security model, and backup strategy.

Senior-level PV understanding means you can answer these questions quickly:

- Who owns this data?
- Which PVC is bound to this PV?
- What backend stores the actual bytes?
- Is the reclaim policy safe?
- Can the volume be expanded?
- Can it be snapshotted?
- Is it RWO or RWX?
- Is the application safe for shared writes?
- What happens if the node, zone, CSI driver, or storage backend fails?
- Can we restore this application within the required RTO/RPO?
- Are permissions, SELinux, SCC, and UID/GID correctly handled?
- Is there a tested backup and restore process?

For advanced OpenShift administration, PV knowledge is not only storage knowledge. It is platform reliability, security, disaster recovery, and operational discipline.
