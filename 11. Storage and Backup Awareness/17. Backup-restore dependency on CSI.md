## 1. Executive Summary

In OpenShift, backup and restore of stateful workloads depends heavily on **how the application stores data** and **which backup method you use**.

For stateless objects such as Deployments, Services, Routes, ConfigMaps, Secrets, RBAC, and Operators, a backup tool can mostly back up Kubernetes/OpenShift API objects without needing CSI.

For persistent data inside PVCs, CSI becomes important because OpenShift itself does not know how to copy storage-array blocks, cloud disks, Ceph images, vSphere volumes, or vendor storage snapshots. OpenShift delegates those operations to a CSI driver.

The key point:

> **If your backup strategy uses native volume snapshots, the PVC must be backed by a CSI driver that supports the Kubernetes VolumeSnapshot API.**

CSI dependency is not only about taking the snapshot. Restore also depends on CSI because a restored PVC is normally provisioned from a `VolumeSnapshot` or from data that originated from a CSI snapshot. If the destination cluster does not have the right CSI driver, compatible `StorageClass`, compatible `VolumeSnapshotClass`, and matching storage backend capabilities, restore can fail or produce a PVC stuck in `Pending`.

For OpenShift administrators, the most important operational understanding is this:

| Backup/Restore Method | CSI Dependency | What It Means |
|---|---:|---|
| Kubernetes object backup only | Low | Backs up API resources, not actual PVC data. |
| Filesystem backup using node agent / Restic / Kopia style backup | Medium | Does not require CSI snapshot support, but depends on mounted volume access and node-agent permissions. |
| Native CSI snapshot backup | High | Requires CSI driver snapshot support, snapshot CRDs/controller, `VolumeSnapshotClass`, and backend snapshot support. |
| OADP/Velero CSI Data Mover | Very High | Requires CSI snapshots first, then data movement to object storage using DataUpload/DataDownload workflows. |
| Cross-cluster restore from CSI snapshots | Very High | Requires source and destination compatibility, object-store backup metadata, CSI driver, StorageClass mapping, and restore support. |

## 2. Why CSI Matters in Backup and Restore

### 2.1 What CSI Does

CSI, or **Container Storage Interface**, is the standard interface used by Kubernetes and OpenShift to communicate with external storage systems.

A CSI driver allows OpenShift to perform operations such as:

- Dynamically provision a volume.
- Attach a volume to a node.
- Mount a filesystem into a pod.
- Expand a volume.
- Clone a volume, if supported.
- Snapshot a volume, if supported.
- Restore a volume from a snapshot, if supported.

Without CSI, OpenShift can still manage some storage through older mechanisms, but modern backup and restore workflows depend on CSI because Kubernetes native volume snapshots are CSI-only.

### 2.2 Why Kubernetes Cannot Snapshot Any PVC by Itself

A PVC is only an abstraction. OpenShift knows that an application requested storage, but it does not automatically know how the actual backend implements snapshotting.

For example:

- AWS EBS creates EBS snapshots.
- Azure Disk creates managed disk snapshots.
- VMware vSphere creates CNS/FCD-related snapshots depending on the driver and storage policy.
- OpenShift Data Foundation uses Ceph RBD or CephFS snapshot mechanisms.
- NetApp Trident uses ONTAP snapshot technology.
- Portworx, Dell, Pure, HPE, IBM, and other storage vendors have their own mechanisms.

The CSI driver translates Kubernetes snapshot requests into backend-specific snapshot operations.

### 2.3 Backup Tool View

When OADP/Velero sees a PVC during backup, it must decide how to protect the PVC data. Possible choices include:

1. Skip volume data and back up only the PVC object.
2. Back up the filesystem by reading files from the mounted volume.
3. Ask the CSI layer to create a snapshot.
4. Ask CSI to create a snapshot and then move the snapshot data to object storage.

Only options 3 and 4 are native snapshot-based backup paths, and both are CSI-dependent.

## 3. Backup Types and CSI Dependency Levels

### 3.1 Kubernetes/OpenShift Resource Backup

This includes:

- Namespace
- Deployment
- StatefulSet
- DaemonSet
- Service
- Route
- ConfigMap
- Secret
- ServiceAccount
- RoleBinding
- NetworkPolicy
- Operator custom resources
- PVC object metadata

This backup type does **not** necessarily protect actual persistent volume data. It can recreate a PVC object, but not automatically restore the storage content unless the backup also includes PV data protection.

**CSI dependency:** Low.

Example:

```bash
velero backup create app-meta-backup \
  --include-namespaces app-prod
```

This may protect application metadata, but unless volume backup is enabled, the database/data directory inside the PVC is not protected.

### 3.2 Filesystem Backup

Filesystem backup reads files from a mounted volume and writes them to backup storage. In Velero/OADP terminology, this is often associated with node-agent based file backup using uploaders such as Restic or Kopia, depending on version and configuration.

This approach is useful when:

- CSI snapshot is unavailable.
- Storage is NFS/EFS-like and does not support Kubernetes CSI snapshot API.
- You need portable file-level backup.
- Snapshot restore is not supported on the target cluster.

**CSI dependency:** Medium.

It may not require CSI snapshot support, but it still depends on Kubernetes volume mount behavior, node access, SCC/security permissions, and data consistency handling.

Common limitation:

- It reads from the live filesystem, so consistency may be weaker than a frozen/quiesced snapshot unless the application is stopped or quiesced.

### 3.3 CSI Snapshot Backup

CSI snapshot backup creates a Kubernetes `VolumeSnapshot` for a PVC. The snapshot controller binds it to a `VolumeSnapshotContent`. The CSI snapshotter sidecar asks the storage backend to create a real snapshot.

**CSI dependency:** High.

Requirements:

- PVC must be backed by CSI PV.
- CSI driver must support snapshot operations.
- Snapshot CRDs must exist.
- CSI snapshot controller must be running.
- CSI driver snapshot sidecar must be installed with the driver.
- Correct `VolumeSnapshotClass` must exist.
- `VolumeSnapshotClass.driver` must match the PVC's StorageClass provisioner.
- Storage backend must allow snapshot creation.

### 3.4 CSI Snapshot + Data Mover Backup

This method first creates a CSI snapshot and then moves snapshot data to remote object storage. This is important for disaster recovery because many CSI snapshots are stored in or near the storage backend. If the cluster or storage backend is lost, a local snapshot may not be sufficient.

**CSI dependency:** Very High.

Additional requirements:

- OADP/Velero CSI plugin.
- Node agent enabled.
- Backup repository configured.
- Object storage accessible.
- DataUpload/DataDownload resources functioning.
- Temporary volumes can be provisioned from snapshots.
- Adequate SCC/security permissions for node agent, depending on platform.

## 4. CSI Snapshot Architecture in OpenShift

### 4.1 Main Components

OpenShift CSI snapshot architecture has these major pieces:

```text
User / Backup Tool
      |
      v
VolumeSnapshot API
      |
      v
CSI Snapshot Controller
      |
      v
VolumeSnapshotContent
      |
      v
CSI external-snapshotter sidecar
      |
      v
CSI Driver Controller Plugin
      |
      v
Storage Backend Snapshot
```

### 4.2 CSI Snapshot Controller

The snapshot controller watches `VolumeSnapshot` and `VolumeSnapshotContent` objects.

Its responsibilities include:

- Binding `VolumeSnapshot` to `VolumeSnapshotContent`.
- Creating `VolumeSnapshotContent` for dynamically provisioned snapshots.
- Managing deletion behavior based on `deletionPolicy`.
- Updating snapshot status.

In OpenShift, the CSI Snapshot Controller Operator installs and manages the snapshot controller.

Useful command:

```bash
oc get pods -n openshift-cluster-storage-operator
```

Look for snapshot-controller related pods and operator health.

### 4.3 CSI external-snapshotter Sidecar

The CSI driver vendor provides the `csi-external-snapshotter` sidecar as part of the CSI driver deployment.

It watches `VolumeSnapshotContent` and triggers CSI calls such as:

- `CreateSnapshot`
- `DeleteSnapshot`

Important point:

> OpenShift provides the snapshot controller, but the CSI driver/vendor provides the snapshotter sidecar and actual backend snapshot implementation.

If the snapshot controller exists but the CSI driver does not support snapshots, `VolumeSnapshot` still fails.

### 4.4 Storage Backend

The actual snapshot is created in the storage platform, not inside OpenShift.

Examples:

- Ceph RBD snapshot
- CephFS snapshot
- AWS EBS snapshot
- Azure Disk snapshot
- vSphere CNS snapshot
- ONTAP snapshot
- Portworx snapshot

Kubernetes objects are only control-plane representations of backend state.

## 5. Core Objects: StorageClass, PVC, PV, VolumeSnapshotClass, VolumeSnapshot, VolumeSnapshotContent

### 5.1 StorageClass

A `StorageClass` defines how PVCs are dynamically provisioned.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ocs-storagecluster-ceph-rbd
provisioner: openshift-storage.rbd.csi.ceph.com
parameters:
  clusterID: openshift-storage
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: Immediate
```

Important field:

```yaml
provisioner: openshift-storage.rbd.csi.ceph.com
```

This must match the CSI driver responsible for the volume.

### 5.2 PVC

A PVC requests storage from a `StorageClass`.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
  namespace: mysql-prod
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: ocs-storagecluster-ceph-rbd
  resources:
    requests:
      storage: 20Gi
```

Check PVC:

```bash
oc get pvc -n mysql-prod
oc describe pvc mysql-data -n mysql-prod
```

### 5.3 PV

A PV is the actual cluster object representing the backend volume.

For CSI volumes, inspect:

```bash
oc get pv <pv-name> -o yaml
```

Look for:

```yaml
spec:
  csi:
    driver: openshift-storage.rbd.csi.ceph.com
    volumeHandle: ...
```

If `spec.csi` is absent and the PV is backed by NFS, hostPath, local volume, in-tree plugin, or older FlexVolume, native CSI snapshot backup will not work.

### 5.4 VolumeSnapshotClass

A `VolumeSnapshotClass` tells Kubernetes which CSI driver and backend parameters to use for snapshot creation.

Example:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ocs-rbd-snapshotclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Delete
```

Important fields:

| Field | Meaning |
|---|---|
| `driver` | CSI driver used for snapshot operations. Must match PVC/PV CSI driver. |
| `deletionPolicy` | `Delete` removes backend snapshot when snapshot object is deleted. `Retain` keeps backend snapshot. |
| `parameters` | Storage-vendor-specific snapshot options. |
| default annotation | Used when a `VolumeSnapshot` does not specify a class. |

Check snapshot classes:

```bash
oc get volumesnapshotclass
oc get volumesnapshotclass -o yaml
```

### 5.5 VolumeSnapshot

A `VolumeSnapshot` is a namespaced request to snapshot a PVC.

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-data-snap-001
  namespace: mysql-prod
spec:
  volumeSnapshotClassName: ocs-rbd-snapshotclass
  source:
    persistentVolumeClaimName: mysql-data
```

Check status:

```bash
oc get volumesnapshot -n mysql-prod
oc describe volumesnapshot mysql-data-snap-001 -n mysql-prod
```

Useful JSONPath:

```bash
oc get volumesnapshot mysql-data-snap-001 -n mysql-prod \
  -o jsonpath='{.status.readyToUse}{"\n"}'
```

Expected:

```text
true
```

### 5.6 VolumeSnapshotContent

A `VolumeSnapshotContent` is cluster-scoped and represents the actual backend snapshot binding.

```bash
oc get volumesnapshotcontent
oc describe volumesnapshotcontent <name>
```

Important fields:

```yaml
spec:
  deletionPolicy: Delete
  driver: openshift-storage.rbd.csi.ceph.com
  source:
    snapshotHandle: ...
  volumeSnapshotRef:
    name: mysql-data-snap-001
    namespace: mysql-prod
status:
  readyToUse: true
```

A common admin mistake is checking only `VolumeSnapshot` and forgetting `VolumeSnapshotContent`. For deep troubleshooting, always inspect both.

## 6. How CSI Snapshot Backup Works

### 6.1 Normal Flow

When a backup tool creates a CSI snapshot, the flow is:

```text
1. Backup tool detects PVC.
2. Backup tool creates VolumeSnapshot for that PVC.
3. Snapshot controller creates/binds VolumeSnapshotContent.
4. CSI external-snapshotter calls CSI driver CreateSnapshot.
5. Storage backend creates real snapshot.
6. CSI driver returns snapshot handle.
7. VolumeSnapshot status becomes readyToUse=true.
8. Backup tool records snapshot metadata.
```

### 6.2 What Is Actually Backed Up?

Native CSI snapshot backup usually protects:

- The Kubernetes metadata needed to understand the snapshot.
- The relationship between PVC and snapshot.
- The backend snapshot reference.

But where the actual snapshot data lives depends on the backend.

For example:

- A cloud snapshot might live in the cloud provider snapshot service.
- An ODF snapshot might live in the Ceph backend.
- A vSphere snapshot might live in vSphere/CNS-backed storage.

This has huge disaster-recovery implications.

### 6.3 Why Local Snapshots Are Not Always DR

A storage snapshot is not automatically a complete off-cluster backup.

If the snapshot lives in the same failure domain as the original volume, then cluster loss, storage backend loss, ransomware, accidental deletion, or region failure may still destroy both data and snapshots.

For DR-grade protection, use one or more of:

- CSI Data Mover to object storage.
- Storage backend replication.
- Cloud snapshot copy to another region/account.
- Off-cluster backup repository.
- Application-level dump plus object storage.
- Database-native backup and WAL/binlog shipping.

## 7. How CSI Snapshot Restore Works

### 7.1 Restore as New PVC

Restoring from a snapshot usually creates a new PVC whose `dataSource` references the `VolumeSnapshot`.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-restore
  namespace: mysql-prod
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  dataSource:
    name: mysql-data-snap-001
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

Flow:

```text
1. User or restore controller creates PVC with dataSource=VolumeSnapshot.
2. CSI provisioner sees PVC request.
3. CSI driver creates a new volume from snapshot.
4. PV is provisioned and bound.
5. Pod mounts restored PVC.
```

### 7.2 Restore Is Usually Not In-Place

Most Kubernetes/OpenShift snapshot restore workflows create a **new PVC**. They do not overwrite the existing PVC in place.

Operational approach:

1. Scale down application.
2. Create restored PVC from snapshot.
3. Update Deployment/StatefulSet to use restored PVC, or recreate StatefulSet PVC names carefully.
4. Validate data.
5. Remove old PVC only after confirmation.

### 7.3 Restore Requires Compatible CSI Driver

A snapshot restore is not just a YAML operation. The destination CSI driver must understand the snapshot handle and be able to create a volume from it.

Restore can fail if:

- Destination cluster lacks the same CSI driver.
- `StorageClass` name changed.
- `VolumeSnapshotClass` driver mismatch exists.
- Snapshot handle is meaningful only in the source cluster/backend.
- Backend snapshot was deleted because `deletionPolicy: Delete` removed it.
- Snapshot belongs to a different region, zone, account, or storage system.
- Access mode or volume mode is unsupported.
- Requested restored PVC size is smaller than original.

## 8. OADP / Velero Dependency on CSI

### 8.1 OADP Overview

OADP, OpenShift API for Data Protection, is Red Hat's OpenShift data protection solution built around Velero and plugins. It can protect OpenShift/Kubernetes resources and persistent data depending on configuration.

For CSI-aware backups, OADP uses Velero CSI integration and snapshot/data-movement workflows.

### 8.2 OADP Backup Decision for PVCs

At a high level, when OADP/Velero processes PVCs:

```text
PVC found
  |
  +--> If CSI snapshot backup enabled and PVC supports CSI snapshot:
  |       create VolumeSnapshot
  |
  +--> If snapshotMoveData=true / data mover enabled:
  |       create DataUpload and move snapshot data to object storage
  |
  +--> If filesystem backup enabled/annotated/defaulted:
  |       read mounted files through node agent
  |
  +--> If no volume backup method applies:
          only PVC metadata is backed up
```

### 8.3 Important OADP/Velero Fields

Example backup manifest:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: mysql-prod-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
  - mysql-prod
  storageLocation: default
  snapshotMoveData: true
  defaultVolumesToFsBackup: false
  csiSnapshotTimeout: 10m0s
  itemOperationTimeout: 4h0m0s
  ttl: 720h0m0s
```

Important fields:

| Field | Meaning |
|---|---|
| `includedNamespaces` | Namespace to protect. |
| `snapshotMoveData` | Enables movement of CSI snapshot data to remote object storage in supported OADP/Velero versions. |
| `defaultVolumesToFsBackup` | Uses filesystem backup path by default when true. |
| `csiSnapshotTimeout` | Timeout for CSI snapshot creation. |
| `itemOperationTimeout` | Timeout for data mover operations such as DataUpload/DataDownload. |

### 8.4 VolumeSnapshotClass Label for OADP

Some OADP/Velero CSI workflows require the `VolumeSnapshotClass` to be discoverable by label.

Common label:

```yaml
metadata:
  labels:
    velero.io/csi-volumesnapshot-class: "true"
```

or depending on documented version:

```yaml
metadata:
  labels:
    metadata.labels.velero.io/csi-volumesnapshot-class: "true"
```

Because label requirements can vary by OADP/Velero version, always verify against your installed OADP version documentation and your cluster's existing `VolumeSnapshotClass` examples.

Check labels:

```bash
oc get volumesnapshotclass --show-labels
```

Patch example:

```bash
oc label volumesnapshotclass ocs-rbd-snapshotclass \
  velero.io/csi-volumesnapshot-class=true --overwrite
```

### 8.5 Backup CR Status

Check backup:

```bash
oc get backup -n openshift-adp
oc describe backup mysql-prod-backup -n openshift-adp
```

Velero CLI, if available:

```bash
velero backup describe mysql-prod-backup --details
velero backup logs mysql-prod-backup
```

Common statuses:

| Status | Meaning |
|---|---|
| `Completed` | Backup completed successfully. |
| `PartiallyFailed` | Some items failed, often PVC/snapshot/hooks/data movement. |
| `Failed` | Backup failed. |
| `InProgress` | Backup still running. |

## 9. CSI Data Mover Dependency

### 9.1 Why Data Mover Exists

Native CSI snapshots may remain inside the storage backend. If the backend is lost, the snapshot may be lost.

Data Mover solves this by moving snapshot data to backup storage, normally object storage.

Simplified flow:

```text
PVC
  |
  v
CSI VolumeSnapshot
  |
  v
Temporary access to snapshot/volume
  |
  v
DataUpload
  |
  v
Object storage / backup repository
```

Restore flow:

```text
Object storage / backup repository
  |
  v
DataDownload
  |
  v
Temporary restored volume
  |
  v
PVC available to application
```

### 9.2 DataUpload

`DataUpload` represents the movement of snapshot data from the cluster/storage side to the backup repository.

Check:

```bash
oc get datauploads -A
oc describe dataupload <name> -n openshift-adp
```

Useful JSONPath:

```bash
oc get datauploads -A \
  -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,PHASE:.status.phase,NODE:.status.node,BYTES:.status.progress.bytesDone,TOTAL:.status.progress.totalBytes
```

Expected successful phase:

```text
Completed
```

### 9.3 DataDownload

`DataDownload` represents the movement of backed-up data from object storage back to the restored volume.

Check:

```bash
oc get datadownloads -A
oc describe datadownload <name> -n openshift-adp
```

Expected successful phase:

```text
Completed
```

### 9.4 BackupRepository

A backup repository stores data movement metadata and data chunks depending on the uploader.

Check:

```bash
oc get backuprepositories -A
oc describe backuprepository <name> -n openshift-adp
```

### 9.5 Data Mover Failure Domains

Data Mover depends on more components than plain snapshots:

- CSI snapshot creation must work.
- Temporary PVC creation from snapshot must work.
- Node agent must be running on suitable nodes.
- Node agent must have required permissions/SCC.
- Object storage must be reachable.
- Backup repository must be initialized and writable.
- Timeouts must be sufficient for volume size and network speed.
- Restore cluster must support creating the target volume.

This is why Data Mover failures often show as `PartiallyFailed` backups even though Kubernetes resource backup succeeded.

## 10. Crash Consistency vs Application Consistency

### 10.1 Crash-Consistent Snapshot

A crash-consistent snapshot is like pulling the power plug from a server and preserving disk state at that instant.

It generally includes:

- Data already written to disk.
- Filesystem metadata at that point.

It may exclude:

- Application memory buffers.
- Unflushed database pages.
- Cached writes.
- In-flight transactions.

Many CSI snapshots are crash-consistent by default when a pod is actively writing to the volume.

### 10.2 Application-Consistent Backup

An application-consistent backup coordinates with the application before snapshotting.

Examples:

- MySQL: `FLUSH TABLES WITH READ LOCK`, backup lock, or database-native backup.
- PostgreSQL: `pg_start_backup`/`pg_basebackup`, checkpoint/WAL handling, or operator-supported backup.
- MongoDB: `fsyncLock` or operator-supported backup.
- VM: guest agent filesystem freeze.
- Generic app: pre-hook to stop writes and post-hook to resume writes.

### 10.3 OpenShift Admin Rule

For important databases:

> Do not assume CSI snapshot alone is application-consistent. Use application hooks, database-native backup, or operator-supported backup workflows.

Example safe high-level flow:

```text
1. Put app/database in backup-safe state.
2. Confirm writes are flushed/quiesced.
3. Take CSI snapshot.
4. Resume application writes.
5. Validate snapshot readiness.
6. Optionally move snapshot data to remote object storage.
7. Periodically test restore.
```

## 11. Storage Provider Differences

### 11.1 OpenShift Data Foundation

OpenShift Data Foundation commonly provides CSI drivers for:

- Ceph RBD block volumes.
- CephFS shared filesystem volumes.

Snapshot behavior can vary between RBD and CephFS.

Admin considerations:

- Check correct `VolumeSnapshotClass` for RBD vs CephFS.
- Use correct `StorageClass` for application PVC.
- Ensure snapshot count limits and cleanup policies are understood.
- Ensure application consistency for active workloads.
- For DR, do not rely only on local Ceph snapshots unless backend replication/DR exists.

### 11.2 Cloud Block Storage

Examples:

- AWS EBS CSI
- Azure Disk CSI
- Google Persistent Disk CSI
- IBM VPC Block CSI

Admin considerations:

- Snapshots may be region/zone/account scoped.
- Restore might require same cloud account/project/region or configured copy.
- IAM permissions are critical.
- Snapshot charges may apply.
- Cross-cluster restore requires storage and credentials alignment.

### 11.3 vSphere CSI

Admin considerations:

- CSI driver support and vSphere version matter.
- Storage policy compatibility matters.
- Snapshot limitations may depend on volume type and platform version.
- Restored PVC may stay pending if topology or storage policy cannot satisfy placement.

### 11.4 NFS / EFS / Non-CSI Filesystems

Many NFS-style volumes do not support Kubernetes CSI VolumeSnapshot API, or the driver may not implement snapshots.

Admin options:

- Use filesystem backup.
- Use storage-array-native backup outside OpenShift.
- Use application backup.
- Use rsync/backup job to object storage.
- Use storage vendor CSI if snapshot support exists.

### 11.5 Local Volumes

Local PVs are node-bound and usually poor candidates for portable CSI snapshot backup unless provided through a CSI driver with snapshot capabilities.

Risk:

- Node failure can equal data loss if replication is not handled elsewhere.
- Restore scheduling can fail due to node affinity.

## 12. Day-2 Admin Prechecks Before Backup

### 12.1 Confirm PVCs and StorageClasses

```bash
oc get pvc -A
oc get sc
```

For a specific app:

```bash
NS=mysql-prod
oc get pvc -n $NS -o wide
oc describe pvc -n $NS
```

### 12.2 Confirm PVC Is CSI-Backed

```bash
PVC=mysql-data
NS=mysql-prod
PV=$(oc get pvc $PVC -n $NS -o jsonpath='{.spec.volumeName}')
oc get pv $PV -o yaml | egrep -A20 '^  csi:|csi:'
```

Expected:

```yaml
csi:
  driver: ...
  volumeHandle: ...
```

If `spec.csi` is missing, CSI snapshot backup will not work.

### 12.3 Match StorageClass Provisioner to VolumeSnapshotClass Driver

```bash
SC=$(oc get pvc $PVC -n $NS -o jsonpath='{.spec.storageClassName}')
oc get sc $SC -o jsonpath='{.provisioner}{"\n"}'
oc get volumesnapshotclass -o custom-columns=NAME:.metadata.name,DRIVER:.driver,DELETIONPOLICY:.deletionPolicy
```

The `StorageClass.provisioner` should match the appropriate `VolumeSnapshotClass.driver`.

### 12.4 Confirm Snapshot CRDs

```bash
oc get crd | grep snapshot.storage.k8s.io
```

Expected CRDs include:

```text
volumesnapshotclasses.snapshot.storage.k8s.io
volumesnapshotcontents.snapshot.storage.k8s.io
volumesnapshots.snapshot.storage.k8s.io
```

## 14. Common Failure Scenarios and Root Cause Analysis

### Scenario 1: `VolumeSnapshot` Stuck Not Ready

Symptoms:

```bash
oc get volumesnapshot -n app
```

Output:

```text
NAME        READYTOUSE   SOURCEPVC   AGE
app-snap    false        app-pvc     20m
```

Check:

```bash
oc describe volumesnapshot app-snap -n app
oc get volumesnapshotcontent
oc describe volumesnapshotcontent <name>
```

Possible causes:

- CSI driver does not support snapshots.
- `VolumeSnapshotClass.driver` mismatch.
- Snapshot sidecar missing.
- Storage backend error.
- Credentials/IAM problem.
- PVC is not CSI-backed.
- Timeout.

Fix:

1. Validate PVC's PV has `spec.csi.driver`.
2. Validate `VolumeSnapshotClass.driver` matches.
3. Check CSI controller logs.
4. Check storage backend quota/health.
5. Test with a small PVC.

---

### Scenario 2: No `VolumeSnapshotClass`

Symptoms:

```text
failed to get snapshot class
no default VolumeSnapshotClass found
```

Check:

```bash
oc get volumesnapshotclass
```

Fix:

Create a matching class:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-snapclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: <csi-driver-name>
deletionPolicy: Delete
```

Apply:

```bash
oc apply -f volumesnapshotclass.yaml
```

Important:

- Use the actual CSI driver name from the StorageClass provisioner or PV `spec.csi.driver`.
- Do not create multiple default `VolumeSnapshotClass` objects for the same driver.

---

### Scenario 3: Driver Mismatch

Symptoms:

```text
failed to check and update snapshot content: failed to take snapshot of the volume
snapshot class driver does not match PVC driver
```

Check:

```bash
oc get sc <sc-name> -o jsonpath='{.provisioner}{"\n"}'
oc get volumesnapshotclass <vsc-name> -o jsonpath='{.driver}{"\n"}'
```

Fix:

Use/create a `VolumeSnapshotClass` whose `driver` matches the CSI driver that provisioned the PVC.

---

### Scenario 4: PVC Is NFS or Non-CSI

Symptoms:

- Backup logs say PVC does not support CSI snapshots.
- No `spec.csi` in PV.

Check:

```bash
PV=$(oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.volumeName}')
oc get pv $PV -o yaml
```

If the PV uses `nfs:` or another non-CSI source, CSI snapshots will not work.

Fix options:

- Use filesystem backup.
- Use NFS backend-native snapshot outside OpenShift.
- Migrate workload to CSI-backed storage.
- Use application-native backup.

---

### Scenario 5: Backup Completed but Restore Has Empty Data

Possible causes:

- Only Kubernetes object metadata was backed up.
- PVC data was not backed up.
- Volume backup annotation was missing.
- `defaultVolumesToFsBackup` disabled and CSI snapshot failed/skipped.
- DataUpload failed but backup was treated as partially successful.

Check:

```bash
oc describe backup <backup> -n openshift-adp
velero backup describe <backup> --details
velero backup logs <backup>
oc get datauploads -A
```

Fix:

- Confirm actual volume backup method.
- Ensure CSI snapshots or filesystem backup is enabled.
- Do test restores regularly.

---

### Scenario 6: OADP Backup `PartiallyFailed`

Symptoms:

```bash
oc get backup -n openshift-adp
```

Output:

```text
NAME                PHASE             ERRORS   WARNINGS
mysql-prod-backup   PartiallyFailed   1        3
```

Check:

```bash
oc describe backup mysql-prod-backup -n openshift-adp
oc logs deploy/velero -n openshift-adp
oc get datauploads -A
oc get volumesnapshot -A
```

Common causes:

- Snapshot timeout.
- DataUpload timeout.
- VolumeSnapshotClass missing label.
- Object storage unavailable.
- Node agent permission issue.
- PVC in unsupported volume mode.
- Driver could snapshot one PVC but not another.

Fix:

- Inspect exact failed item.
- Check `VolumeSnapshot` status.
- Check `DataUpload` status.
- Increase timeout if data is large and throughput is low.
- Validate node-agent SCC and logs.

---

### Scenario 7: Restore PVC Stuck Pending

Symptoms:

```bash
oc get pvc -n app-restore
```

Output:

```text
NAME          STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
mysql-data    Pending                                      ocs-rbd
```

Check:

```bash
oc describe pvc mysql-data -n app-restore
oc get events -n app-restore --sort-by=.lastTimestamp | tail -50
```

Possible causes:

- StorageClass missing on target.
- CSI driver missing.
- Snapshot reference invalid.
- Topology/zone mismatch.
- Requested size too small.
- Backend cannot create volume from snapshot.
- DataDownload failed.

Fix:

- Create matching StorageClass.
- Restore into compatible cluster/backend.
- Map StorageClass names if supported by restore tool.
- Check `datadownloads`.
- Check CSI provisioner logs.

---

### Scenario 8: Snapshot Deleted but Backend Snapshot Needed

Cause:

`VolumeSnapshotClass.deletionPolicy: Delete` means deleting the `VolumeSnapshot` can delete the backend snapshot.

Check:

```bash
oc get volumesnapshotclass -o custom-columns=NAME:.metadata.name,DRIVER:.driver,POLICY:.deletionPolicy
```

Production consideration:

- Use `Delete` when snapshot lifecycle is fully managed and cleanup is desired.
- Use `Retain` when you need backend snapshot retention after Kubernetes object deletion.
- But with `Retain`, you must document cleanup to avoid orphaned snapshots and cost growth.

---

### Scenario 9: Restore Works but Application Fails to Start

Possible causes:

- Snapshot was crash-consistent but application needed recovery.
- Database files are inconsistent.
- Secret/config mismatch.
- UID/GID or SELinux context issue.
- Restored PVC mounted into wrong path.
- StatefulSet PVC name mismatch.
- Operator reconciliation overwrote restored state.

Fix:

- Check application logs.
- Run database recovery tools.
- Validate mount path.
- Validate SCC/securityContext.
- Restore secrets/configs with PVC data.
- For operator-managed apps, use operator-supported restore method.

---

### Scenario 10: Cross-Cluster Restore Fails

Possible causes:

- CSI snapshot handle is not portable.
- Destination does not have source backend access.
- StorageClass names differ.
- OADP versions incompatible.
- Data Mover repository inaccessible.
- Cloud credentials missing.
- Object storage bucket reachable but repository metadata incompatible.

Fix:

- Prefer Data Mover or filesystem backup for portability.
- Test restore into target cluster before disaster.
- Align OADP versions and backup format compatibility.
- Validate BackupStorageLocation.
- Use StorageClass mapping where supported.

## 16. Design Patterns for Production Backup/Restore

### 16.1 Do Not Treat Snapshots as Complete Backups Automatically

A snapshot is point-in-time volume state. It may not be:

- Application-consistent.
- Off-cluster.
- Cross-region.
- Ransomware-safe.
- Long-term retained.
- Portable across clusters.

A production backup design should answer:

- Where is the data stored?
- Who can delete it?
- Is it immutable?
- Can it survive cluster loss?
- Can it survive storage backend loss?
- Can it be restored to another cluster?
- How often is restore tested?

### 16.2 Use Layered Protection

For critical applications:

```text
Layer 1: Application-native backup
Layer 2: CSI snapshots for fast local rollback
Layer 3: Data Mover/object storage for disaster recovery
Layer 4: Cross-region or offsite replication
Layer 5: Periodic restore test and checksum validation
```

### 16.3 Keep Metadata and Data Together

A PVC alone is not enough. A database secret alone is not enough. A snapshot alone is not enough.

Back up together:

- Namespace resources.
- PVC data.
- Secrets.
- ConfigMaps.
- Routes/Services.
- ServiceAccounts/RBAC.
- Operator CRs.
- NetworkPolicies.
- Image references.
- External dependencies information.

### 16.4 Separate Fast Rollback and DR Backup

Fast rollback:

- Local CSI snapshot.
- Short retention.
- Fast restore as new PVC.
- Same cluster/backend.

DR backup:

- Data Mover or application backup to object storage.
- Longer retention.
- Restore to alternate cluster.
- Tested independently.

### 16.5 Define Retention Carefully

`deletionPolicy: Delete` is clean but risky if admins delete snapshot objects accidentally.

`deletionPolicy: Retain` protects backend snapshots but creates orphan/cost risk.

Recommended:

- For automated short-lived snapshots: `Delete`.
- For manual break-glass snapshots: `Retain` with documented cleanup.
- For compliance backup: use immutable object storage or backend retention lock, not just Kubernetes object retention.

### 16.6 Version Compatibility

Before upgrading OADP/Velero or CSI drivers:

- Read upgrade notes.
- Take filesystem backup of critical workloads if moving between incompatible data mover versions.
- Test backup and restore after upgrade.
- Validate `VolumeSnapshotClass` labels and defaults.
- Validate node-agent settings.

### 16.7 Multi-Volume Applications

For apps with multiple PVCs, separate snapshots may not be exactly simultaneous unless volume group snapshots are supported and enabled.

Examples:

- Database data PVC + WAL PVC.
- Application upload PVC + metadata DB PVC.
- VM disks with multiple PVCs.

Options:

- Application-level quiesce across all volumes.
- VolumeGroupSnapshot if supported and production-ready for your version/provider.
- Database-native backup.
- Stop application briefly during snapshot.

## 17. Exam and Interview Notes

### 17.1 One-Line Answer

Backup/restore depends on CSI when PVC data is protected using native snapshots because only CSI drivers can implement Kubernetes `VolumeSnapshot` operations; without CSI snapshot support, OpenShift can back up metadata but cannot create or restore storage-backend snapshots for that PVC.

### 17.2 Interview-Ready Explanation

In OpenShift, CSI abstracts storage provider operations. For snapshot-based backup, OADP/Velero creates Kubernetes `VolumeSnapshot` objects. The snapshot controller binds them to `VolumeSnapshotContent`, and the CSI snapshotter sidecar calls the CSI driver to create the actual backend snapshot. Restore creates a new PVC from the snapshot, so the destination also needs a compatible CSI driver and StorageClass. If the CSI driver does not support snapshots, if the `VolumeSnapshotClass` driver does not match the PVC's StorageClass provisioner, or if the snapshot exists only in the source backend, backup or restore fails. For disaster recovery, Data Mover can move CSI snapshot data to object storage, but that adds dependencies on node-agent, object storage, DataUpload/DataDownload, and repository health.

### 17.3 Common Exam Traps

| Trap | Correct Thinking |
|---|---|
| PVC exists, so data is backed up | False. PVC object metadata is not the same as volume data. |
| Any PVC can be snapshotted | False. Kubernetes VolumeSnapshot is CSI-only. |
| StorageClass and VolumeSnapshotClass can use different drivers | Usually false for dynamic snapshots; driver must match. |
| Snapshot restore overwrites existing PVC | Usually false; restore creates a new PVC. |
| Snapshot is always application-consistent | False; usually crash-consistent unless app is quiesced. |
| Local snapshot is full DR | False; if backend is lost, local snapshot may be lost. |
| OADP Data Mover avoids CSI | False; it starts from CSI snapshots. |
| NFS PV can always use CSI snapshot | False; only if backed by CSI driver with snapshot support. |

## Final Operational Message

For an advanced OpenShift administrator, the most important mindset is:

> **A backup is not valid because the Backup CR says `Completed`; it is valid only after a restore test proves that Kubernetes metadata, PVC data, CSI driver behavior, application consistency, and target-cluster storage compatibility all work together.**

CSI is the bridge between OpenShift and real storage. If the bridge is missing, unsupported, mismatched, or not tested, snapshot-based backup/restore will fail exactly when you need it most.
