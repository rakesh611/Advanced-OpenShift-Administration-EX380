## 1. Executive Summary

Access modes define **how a PersistentVolume can be mounted by workloads**. In OpenShift and Kubernetes, access modes are specified in PVs and PVCs and are used during binding and scheduling decisions.

The four common access modes are:

| Access Mode | CLI Short Name | Meaning |
|---|---:|---|
| `ReadWriteOnce` | `RWO` | The volume can be mounted read-write by a single node. Multiple pods may use it only when they are on that same node and the backend allows it. |
| `ReadWriteOncePod` | `RWOP` | The volume can be mounted read-write by only one pod in the cluster. This is the strictest single-writer mode. |
| `ReadOnlyMany` | `ROX` | The volume can be mounted read-only by many nodes. |
| `ReadWriteMany` | `RWX` | The volume can be mounted read-write by many nodes. |

The most important production rule:

> **Access mode is not the same as application data safety.**  
> It tells Kubernetes/OpenShift what the storage claims to support. It does not magically make a non-cluster-aware database safe for multi-writer access.

For advanced administration, access modes affect:

- PVC binding
- Dynamic provisioning
- Pod scheduling
- Multi-attach errors
- StatefulSet design
- Deployment rolling updates
- Backup and restore approach
- Volume snapshot compatibility
- Disaster recovery design
- Storage backend selection
- Security context and SELinux behavior
- Performance and latency expectations

## 2. Why Access Modes Matter

In simple labs, a PVC is often created, a pod mounts it, and everything works. In production, access modes become critical because they decide whether a workload can scale, restart, migrate, or recover safely.

A wrong access mode can cause:

- PVC stuck in `Pending`
- Pod stuck in `ContainerCreating`
- Pod stuck in `Pending`
- `Multi-Attach error`
- Mount timeout
- Read/write permission errors
- Split-brain database corruption
- Failed rolling deployments
- StatefulSet replicas stuck
- Backup inconsistency
- Restore failure due to unavailable storage class or access mode
- Application downtime during node failure

Example production situation:

You deploy a Deployment with 3 replicas using a single `ReadWriteOnce` PVC on AWS EBS. OpenShift may schedule replicas across different worker nodes. Only one node can attach that EBS volume. Result: one pod runs, the others fail with attach/mount errors.

Correct design options:

1. Use one PVC per replica through StatefulSet `volumeClaimTemplates`.
2. Use a true RWX backend such as CephFS, NFS, EFS, Azure File, Manila, or vSAN File Service.
3. Use object storage instead of shared filesystem storage.
4. Redesign the application to avoid shared mutable files.

## 3. Storage Mental Model in OpenShift

OpenShift uses the Kubernetes PersistentVolume framework.

Important objects:

| Object | Scope | Purpose |
|---|---|---|
| `PersistentVolume` | Cluster-scoped | Represents actual storage available to the cluster. |
| `PersistentVolumeClaim` | Namespace-scoped | Developer/application request for storage. |
| `StorageClass` | Cluster-scoped | Defines dynamic provisioning behavior and backend driver. |
| `CSI Driver` | Cluster/backend integration | Talks to real storage system. |
| `VolumeSnapshotClass` | Cluster-scoped | Defines snapshot driver behavior. |
| `VolumeSnapshot` | Namespace-scoped | Request for point-in-time snapshot of a PVC. |
| `Pod` | Namespace-scoped | Mounts PVC as a volume. |

Flow:

```text
Application needs storage
        |
        v
PVC requests size + access mode + storageClassName
        |
        v
StorageClass / CSI provisioner creates PV dynamically
        |
        v
PVC binds to PV
        |
        v
Pod references PVC
        |
        v
Kubelet + CSI node plugin attach/mount volume on node
```

For static provisioning:

```text
Admin creates PV manually
        |
        v
Developer creates PVC
        |
        v
Binder matches PVC to suitable PV
        |
        v
Pod mounts PVC
```

## 4. What Are Access Modes?

Access modes describe **volume capability**.

They answer:

- Can this volume be mounted read-write?
- Can it be mounted read-only?
- Can it be mounted from more than one node?
- Is it limited to one pod?
- Can many pods across many nodes use it?

Access modes appear in both PV and PVC specs:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: thin-csi
```

The PVC is saying:

> I need a volume of at least 10Gi, provisioned by `thin-csi`, and I need it to support `ReadWriteOnce`.

For a statically created PV:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-pv-001
spec:
  capacity:
    storage: 20Gi
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 192.168.10.50
    path: /exports/app1
```

The PV is saying:

> This backend export supports read-write mounts from many nodes.

## 5. The Four Access Modes

### 5.1 ReadWriteOnce - RWO

```yaml
accessModes:
  - ReadWriteOnce
```

Meaning:

```text
Read-write by one node.
```

Important nuance:

- RWO means **one node**, not always one pod.
- Multiple pods can use the same RWO PVC if they are scheduled on the same node.
- Many block storage backends support RWO, for example AWS EBS, Azure Disk, vSphere block volumes, local volumes, and many CSI block drivers.
- RWO is common for databases with one writer pod, such as PostgreSQL, MySQL, MongoDB single-primary, Elasticsearch data nodes, Redis persistence, etc.

Best for:

- Single-instance databases
- StatefulSet where each replica gets its own PVC
- Apps that do not need shared writes
- Block storage backends

Not best for:

- Shared upload directories across many replicas
- Multi-node shared application content
- Multiple Deployment replicas writing to the same path

---

### 5.2 ReadWriteOncePod - RWOP

```yaml
accessModes:
  - ReadWriteOncePod
```

Meaning:

```text
Read-write by exactly one pod in the cluster.
```

RWOP is stricter than RWO.

RWO allows multiple pods on one node to mount the same PVC. RWOP prevents that and gives a stronger single-writer guarantee at Kubernetes level.

Best for:

- Databases that must have exactly one writer pod
- Legacy applications that cannot tolerate two writers
- Leader-only storage
- Critical stateful workloads where accidental second mount is dangerous

Important points:

- RWOP is supported for CSI volumes.
- It should be the only access mode on the PV/PVC.
- It is useful when RWO is not strict enough.
- It helps avoid accidental same-node multi-pod mounts.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes:
    - ReadWriteOncePod
  resources:
    requests:
      storage: 20Gi
  storageClassName: fast-csi
```

---

### 5.3 ReadOnlyMany - ROX

```yaml
accessModes:
  - ReadOnlyMany
```

Meaning:

```text
Read-only by many nodes.
```

Best for:

- Shared static content
- Golden datasets
- Model files
- Reference data
- Read-only configuration bundles
- Shared libraries
- Distribution of preloaded content to many pods

Important:

- ROX means the volume can be mounted by many nodes in read-only mode.
- It does not mean the storage backend is globally immutable.
- Admins should ensure the backend export, filesystem permission, or application mount options truly prevent writes.

Example use case:

A machine learning inference platform needs to mount a 200Gi model repository on many nodes, but no pod should write to it.

---

### 5.4 ReadWriteMany - RWX

```yaml
accessModes:
  - ReadWriteMany
```

Meaning:

```text
Read-write by many nodes.
```

Best for:

- Shared web content
- Media uploads shared by multiple app replicas
- CI/CD workspace sharing when appropriate
- Read-write shared configuration repositories
- Apps requiring many pods across many nodes to write to a shared path

Common backends:

- NFS
- CephFS / OpenShift Data Foundation file storage
- AWS EFS
- Azure File
- GCP Filestore
- OpenStack Manila
- vSphere vSAN File Service
- SMB/CIFS

Critical warning:

> RWX does not make the application cluster-safe.

Many applications cannot safely handle concurrent writes even if the filesystem supports RWX. You still need application-level locking, database semantics, or a shared filesystem designed for your workload.

## 6. Access Modes vs Volume Mount ReadOnly Flag

Access mode is specified in PVC/PV.

The pod mount can also specify `readOnly`.

Example:

```yaml
volumes:
  - name: app-data
    persistentVolumeClaim:
      claimName: app-data-pvc
      readOnly: true
```

This means:

- PVC/PV access mode describes what is possible.
- Pod-level `readOnly: true` says this pod wants to mount the claim read-only.
- A PVC with `ReadWriteMany` can be mounted read-only by a specific pod.
- A PVC with `ReadOnlyMany` should not be mounted read-write.

Do not confuse:

```yaml
spec:
  accessModes:
    - ReadOnlyMany
```

with:

```yaml
persistentVolumeClaim:
  claimName: data
  readOnly: true
```

The first is storage claim capability.  
The second is pod mount behavior.

## 7. Access Modes vs StorageClass

A `StorageClass` does not directly say `RWO` or `RWX` in a standard field. Instead, it points to a provisioner/CSI driver and parameters that determine what kind of volume is created.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ocs-storagecluster-ceph-rbd
provisioner: openshift-storage.rbd.csi.ceph.com
parameters:
  clusterID: openshift-storage
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: Immediate
```

This class usually provisions Ceph RBD block volumes, commonly used with RWO.

Another class:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ocs-storagecluster-cephfs
provisioner: openshift-storage.cephfs.csi.ceph.com
parameters:
  clusterID: openshift-storage
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: Immediate
```

This class provisions CephFS volumes, commonly used with RWX.

As an admin, do not only read PVC accessModes. Also check:

```bash
oc get sc
oc describe sc <storageclass>
oc get csidrivers
oc get sc <storageclass> -o yaml
```

## 8. Access Modes vs VolumeMode: Filesystem and Block

PVCs can request a volume mode:

```yaml
volumeMode: Filesystem
```

or:

```yaml
volumeMode: Block
```

### 8.1 Filesystem

The storage is formatted with a filesystem and mounted into the container path.

Example:

```yaml
volumeMounts:
  - name: data
    mountPath: /var/lib/mysql
```

Most application PVCs use `Filesystem`.

### 8.2 Block

The volume is exposed as a raw block device.

Example:

```yaml
volumeDevices:
  - name: data
    devicePath: /dev/xvda
```

Used by:

- Specialized databases
- Virtualization
- Storage engines that manage their own filesystem
- Performance-sensitive applications

Access mode and volume mode are separate decisions.

Example:

```yaml
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Block
```

This means:

> Give me a raw block device that can be mounted read-write by one node.

## 9. How PV and PVC Binding Works

The binder matches PVCs to PVs based on several criteria.

Important matching factors:

- Requested capacity
- Access mode
- `storageClassName`
- `volumeMode`
- Selector labels, if used
- Existing `claimRef`, if any

Example PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: claim1
  namespace: app1
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: nfs-rwx
  resources:
    requests:
      storage: 10Gi
```

This PVC needs:

- At least 10Gi
- RWX capability
- StorageClass `nfs-rwx`

If no dynamic provisioner exists and no matching PV exists, it stays `Pending`.

Check:

```bash
oc get pvc -n app1
oc describe pvc claim1 -n app1
oc get pv
```

Common event:

```text
no persistent volumes available for this claim and no storage class is set
```

or:

```text
waiting for a volume to be created, either by external provisioner
```

or:

```text
storageclass.storage.k8s.io "rwx-storage" not found
```

## 10. Dynamic Provisioning Behavior

Dynamic provisioning creates a PV automatically when a PVC is created.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
  namespace: prod
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-block
  resources:
    requests:
      storage: 50Gi
```

The CSI provisioner receives this request and creates a backend volume.

Important admin checks:

```bash
oc get pvc -n prod
oc get pv
oc describe pvc mysql-data -n prod
oc describe pv <pv-name>
oc get events -n prod --sort-by=.lastTimestamp
```

Dynamic provisioning can fail if:

- StorageClass does not exist
- CSI provisioner is unhealthy
- Requested access mode is unsupported
- Requested size is unsupported
- Zone topology cannot satisfy request
- Quota is exceeded in cloud/provider
- Credentials are wrong
- Backend storage pool is full
- `volumeBindingMode` and pod scheduling constraints conflict

## 11. Real-World Storage Backend Mapping

This table is intentionally practical. Always confirm with your actual CSI driver documentation and OpenShift support matrix.

| Backend Type | Common Access Mode | Typical Use |
|---|---|---|
| AWS EBS | RWO / RWOP | Databases, one pod per volume |
| AWS EFS | RWX / ROX / RWO | Shared filesystem |
| Azure Disk | RWO / RWOP | Databases, app data |
| Azure File | RWX / ROX / RWO | Shared files |
| GCP Persistent Disk | RWO / ROX, some RWX modes depending disk type | Block storage |
| GCP Filestore | RWX / ROX / RWO | Shared filesystem |
| vSphere CNS block | RWO / RWOP | Databases, VM disks, block storage |
| vSphere vSAN File Service | RWX | Shared filesystem |
| NFS | RWX / ROX / RWO | Shared files, labs, legacy apps |
| Ceph RBD | RWO / RWOP | Block volumes |
| CephFS | RWX / ROX / RWO | Shared filesystem |
| Local PV | RWO / RWOP | High-performance node-local workloads |
| LVM Storage | RWO / RWOP | Local block storage |
| iSCSI / Fibre Channel | Usually RWO; raw block RWX in some cases | Enterprise SAN |
| SMB/CIFS | RWX / ROX / RWO | Windows/shared file workloads |

Senior admin rule:

> Do not assume a backend supports RWX because the application needs RWX. Select the backend based on access mode, latency, locking semantics, backup support, and recovery requirements.

## 12. OpenShift Data Foundation Access Mode Thinking

OpenShift Data Foundation commonly exposes multiple storage classes. Names may vary by installation, but typical examples are:

```bash
oc get sc
```

Possible output:

```text
NAME                                   PROVISIONER
ocs-storagecluster-ceph-rbd             openshift-storage.rbd.csi.ceph.com
ocs-storagecluster-cephfs               openshift-storage.cephfs.csi.ceph.com
openshift-storage.noobaa.io             openshift-storage.noobaa.io/obc
```

Typical mapping:

| ODF Component | Storage Type | Common Mode | Workload |
|---|---|---|---|
| Ceph RBD | Block | RWO / RWOP | Databases, VM disks, StatefulSets |
| CephFS | Shared filesystem | RWX | Shared files, multi-replica apps |
| NooBaa / MCG | Object storage | Not PVC access mode | S3-compatible object workloads |

Important distinction:

- For block-style stateful apps, use Ceph RBD.
- For shared filesystem needs, use CephFS.
- For object-style data, use S3/ObjectBucketClaim, not RWX PVC.

## 13. Access Modes and Workload Controllers

### 13.1 Deployment

A Deployment is usually for stateless or horizontally scalable apps.

Risky design:

```text
Deployment replicas: 3
PVC: one RWO claim
```

Problem:

- Replicas can land on different nodes.
- RWO volume can attach to only one node.
- Rolling updates can create an old pod and a new pod at the same time.
- Multi-attach errors may occur.

Safer Deployment design:

- Use RWX if all replicas must share the same files.
- Use separate PVCs if each replica needs independent storage.
- Use object storage for shared assets.
- Use `strategy: Recreate` for a single RWO PVC.

Example:

```yaml
strategy:
  type: Recreate
```

### 13.2 StatefulSet

StatefulSet is the preferred controller for many stateful workloads.

It supports `volumeClaimTemplates`:

```yaml
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes:
        - ReadWriteOnce
      storageClassName: fast-block
      resources:
        requests:
          storage: 20Gi
```

For 3 replicas, OpenShift creates:

```text
data-app-0
data-app-1
data-app-2
```

Each pod gets its own PVC.

This is ideal for:

- PostgreSQL cluster
- Kafka
- Elasticsearch
- Cassandra
- MongoDB replica set
- Redis cluster

### 13.3 DaemonSet

DaemonSets run one pod per node.

Avoid a single shared RWO PVC with DaemonSet.

Common patterns:

- Use hostPath only for node-level agents when appropriate.
- Use local logs/ephemeral storage.
- Use per-node local PV.
- Send data to remote backend instead of shared PVC.

### 13.4 CronJob and Job

Jobs can safely use RWO if only one pod runs at a time.

For concurrent jobs:

- Use RWX if sharing is required.
- Use one PVC per job.
- Use object storage.
- Add locking.

## 14. RWO Deep Dive

### 14.1 What RWO Really Means

RWO is often misunderstood.

RWO does not mean:

```text
Only one pod can mount this volume.
```

RWO means:

```text
The volume can be mounted read-write by a single node.
```

If two pods using the same RWO PVC are scheduled on the same node, Kubernetes may allow both to mount it.

This can be dangerous for:

- Databases
- Apps without file locking
- Apps that assume exclusive access

Use RWOP when strict one-pod access is required.

---

### 14.2 RWO with Deployment

Bad example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: mysql
          image: registry.redhat.io/rhel8/mysql-80
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql/data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: mysql-data
```

If `mysql-data` is RWO, two MySQL pods using the same datadir can corrupt data.

Better options:

- Use replicas 1.
- Use `strategy: Recreate`.
- Use StatefulSet with one PVC per replica.
- Use database-native replication.
- Use an operator such as Crunchy Postgres, Percona, MongoDB, etc.

---

### 14.3 RWO and Multi-Attach Error

Common error:

```text
Multi-Attach error for volume "pvc-xxxx"
Volume is already exclusively attached to one node and can't be attached to another
```

Diagnosis:

```bash
oc get pod -n <ns> -o wide
oc describe pod <pod> -n <ns>
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get pv <pv-name> -o yaml
oc get volumeattachment
oc describe volumeattachment <name>
```

Typical causes:

- Old pod still running on another node.
- Node crashed and volume attachment is stale.
- Rolling update created replacement pod before old pod terminated.
- Deployment has more than one replica.
- Stateful app is using Deployment instead of StatefulSet.
- CSI driver or cloud provider detach is slow.
- Node drain was not clean.

Resolution approach:

1. Confirm which pod/node still uses the volume.
2. Do not force detach unless you understand data risk.
3. Scale workload down.
4. Wait for volume detach.
5. If the node is permanently gone, follow provider/CSI guidance for safe detach.
6. For critical databases, validate filesystem and application consistency before starting.

## 15. RWOP Deep Dive

### 15.1 Why RWOP Exists

RWO was historically used for single-writer workloads. But RWO is node-scoped. Multiple pods on the same node may still mount the same PVC.

RWOP solves that by limiting the volume to a single pod.

Use RWOP when:

- You need strong single-writer behavior.
- A second pod touching the same volume can corrupt data.
- You want to prevent accidental same-node duplicate pod access.
- You are running a sensitive database or storage engine.

---

### 15.2 RWOP Example

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: critical-db-data
  namespace: prod-db
spec:
  accessModes:
    - ReadWriteOncePod
  storageClassName: fast-csi
  resources:
    requests:
      storage: 100Gi
```

Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: critical-db
  namespace: prod-db
spec:
  containers:
    - name: db
      image: registry.redhat.io/rhel8/postgresql-13
      volumeMounts:
        - name: data
          mountPath: /var/lib/pgsql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: critical-db-data
```

---

### 15.3 RWOP Migration Thinking

Changing an existing PVC from RWO to RWOP is not a casual edit.

Recommended approach:

1. Confirm CSI driver supports RWOP.
2. Stop the workload.
3. Take backup/snapshot.
4. Set PV reclaim policy to `Retain` if deleting/recreating the PVC is required.
5. Recreate PVC with RWOP and bind to retained PV if supported.
6. Restart workload.
7. Validate application and mount status.

Do not try this during an incident without a rollback plan.

## 16. ROX Deep Dive

ROX is underused but useful.

Example use cases:

- Shared training dataset
- Shared read-only documentation
- Shared binaries
- Shared static web content
- Golden configuration
- AI model repository

PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: model-repo
  namespace: ai-prod
spec:
  accessModes:
    - ReadOnlyMany
  storageClassName: shared-file
  resources:
    requests:
      storage: 500Gi
```

Pod:

```yaml
volumes:
  - name: model-repo
    persistentVolumeClaim:
      claimName: model-repo
      readOnly: true
```

Mount:

```yaml
volumeMounts:
  - name: model-repo
    mountPath: /models
    readOnly: true
```

Operational tip:

For ROX content, define an update pipeline:

```text
Build content -> publish to staging volume/object storage -> validate checksum -> promote to read-only production volume
```

## 17. RWX Deep Dive

### 17.1 What RWX Gives You

RWX allows many nodes to mount the same volume read-write.

This is required when multiple pods on different nodes need the same writable filesystem path.

Examples:

- WordPress uploads directory
- Shared CMS content
- Legacy application shared files
- Multi-replica web app with shared media directory
- Shared reports directory
- CI artifacts directory

---

### 17.2 What RWX Does Not Give You

RWX does not guarantee:

- Database safety
- Distributed locking correctness
- Low latency
- High IOPS
- POSIX semantics on every backend
- No stale cache behavior
- No split-brain behavior
- Application-level consistency

RWX is a storage capability, not an application correctness model.

Bad use case:

```text
Run 3 MySQL pods sharing one RWX datadir.
```

Correct use case:

```text
Run 3 web pods sharing one RWX uploads directory.
```

---

### 17.3 RWX and Performance

RWX backends are often network filesystems.

Expect:

- Higher latency than local/block storage
- Metadata operation bottlenecks
- Lock contention
- Lower random write IOPS than block storage
- Backend dependency on network health
- More visible impact from DNS, MTU, firewall, and storage network issues

Admin checks:

```bash
oc rsh <pod>
df -hT
mount
time dd if=/dev/zero of=/mnt/data/testfile bs=1M count=1024 oflag=direct
time find /mnt/data -type f | wc -l
```

Use proper performance tools for production. Do not rely only on `dd`.

## 20. Troubleshooting Access Mode Problems

### 20.1 PVC Stuck Pending

Symptoms:

```bash
oc get pvc -n app
```

Output:

```text
NAME       STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
data       Pending                                      shared-file
```

Check:

```bash
oc describe pvc data -n app
```

Possible causes:

| Cause | Explanation | Fix |
|---|---|---|
| StorageClass missing | PVC references a non-existing class | Correct `storageClassName` |
| Unsupported access mode | Backend cannot provision requested mode | Use correct storage class |
| No provisioner | StorageClass has invalid/unavailable provisioner | Fix CSI/operator |
| Quota exceeded | Backend/cloud quota reached | Increase quota/free capacity |
| Topology conflict | Volume cannot be created in scheduled zone | Check `volumeBindingMode` and node affinity |
| Static PV mismatch | No PV with matching size/mode/class | Create matching PV |

---

### 20.2 Pod Stuck ContainerCreating

Check:

```bash
oc describe pod <pod> -n <ns>
```

Common event:

```text
Unable to attach or mount volumes
```

or:

```text
MountVolume.MountDevice failed
```

Possible causes:

- Volume already attached to another node
- Node CSI plugin down
- Backend unreachable
- Permission issue
- Wrong NFS export
- SELinux labeling problem
- Network/firewall issue
- Stale volume attachment

---

### 20.3 Multi-Attach Error

Error:

```text
Multi-Attach error for volume "pvc-xxxx"
```

Check pods using PVC:

```bash
PVC=<pvc-name>
NS=<namespace>

oc get pods -n $NS -o jsonpath='{range .items[*]}{.metadata.name}{" "}{range .spec.volumes[*]}{.persistentVolumeClaim.claimName}{" "}{end}{"\n"}{end}' | grep "$PVC"
```

Check pod placement:

```bash
oc get pod -n $NS -o wide
```

Fix options:

- Scale Deployment to 1.
- Change strategy to `Recreate`.
- Convert to StatefulSet with PVC per replica.
- Use RWX backend if shared writes are truly required.
- Wait for detach after pod deletion/node recovery.
- Avoid force deletion unless the old node is confirmed dead and data safety is understood.

---

### 20.4 Permission Denied After Mount

Symptoms:

```text
Permission denied
cannot create directory
read-only file system
```

Check:

```bash
oc rsh <pod>
id
mount
ls -ld <mount-path>
```

OpenShift-specific areas:

- SCC restrictions
- `runAsUser`
- `fsGroup`
- SELinux label
- Root-squash on NFS
- Backend export permissions
- `readOnly: true` in pod spec
- ROX access mode

Possible fix pattern:

```yaml
securityContext:
  fsGroup: 1000670000
```

But do not blindly set arbitrary IDs. Match OpenShift namespace UID ranges and application requirements.

---

### 20.5 RWX Requested but Backend Only Supports RWO

Symptom:

```text
failed to provision volume with StorageClass "fast-block": invalid access mode ReadWriteMany
```

Fix:

- Use shared filesystem storage class.
- Examples: CephFS, NFS, EFS, Azure File, Filestore, Manila.
- Change application design to per-replica PVC.
- Use object storage.

---

### 20.6 RWO PVC Used by Deployment with RollingUpdate

Symptom:

- New pod cannot start during rollout.
- Old pod still holds volume.
- Multi-attach error.

Fix:

```yaml
spec:
  strategy:
    type: Recreate
```

or use StatefulSet.

## 21. Backup and Restore Awareness

Access mode impacts backup design because it influences how many pods write to the same volume and how consistent the data can be at snapshot time.

### 21.1 Backup Methods in OpenShift

Common OpenShift application backup approaches:

| Method | Protects | Notes |
|---|---|---|
| OADP/Velero resource backup | Kubernetes/OpenShift objects | YAML/resource metadata |
| CSI snapshot | PVC point-in-time snapshot | Requires CSI snapshot support |
| Native cloud snapshot | Cloud block volumes | Provider-specific |
| File-system backup / node agent / restic/kopia-style data copy | File contents | Useful when snapshots unsupported or for file volumes |
| Application-native backup | Database/application data | Best for databases |
| Storage-array replication | Backend-level DR | Depends on storage platform |

### 21.2 Access Mode and Backup Consistency

| Access Mode | Backup Concern |
|---|---|
| RWO | Usually one writer, easier to quiesce. Still need app consistency for databases. |
| RWOP | Best Kubernetes-level single-writer guarantee. Good for critical single-writer apps. |
| ROX | Usually safe to snapshot/copy because pods should not write. Validate source update process. |
| RWX | Harder consistency because many pods may write concurrently. Need quiesce, app locks, or application-level backup. |

### 21.3 Snapshot Is Not Always Application-Consistent

A CSI snapshot is usually crash-consistent unless the application is quiesced.

For filesystems and databases, consider:

- Pre-backup hook
- Post-backup hook
- `fsfreeze` where appropriate
- Database flush/lock
- Database-native dump
- Operator-provided backup CR
- Read replica backup
- Maintenance window

Examples:

PostgreSQL:

```text
Prefer pg_basebackup, pg_dump, WAL archiving, or operator-managed backup.
```

MySQL:

```text
Prefer mysqldump, mysqlbackup, xtrabackup, or operator-managed backup.
```

MongoDB:

```text
Prefer mongodump or replica-set-aware snapshot strategy.
```

### 21.4 RWX Backup Risk

RWX volumes may be written by many pods. During backup:

- Pod A writes file1.
- Pod B updates file2.
- Pod C deletes directory3.
- Backup process reads a moving target.

Result:

- Inconsistent backup
- Partial files
- Application-level corruption
- Restore with missing metadata

Mitigation:

1. Stop writers temporarily.
2. Scale deployment to zero or read-only mode.
3. Use application maintenance mode.
4. Use app-level locking.
5. Use storage snapshot with quiesce.
6. Use versioned object storage instead of shared filesystem.
7. Separate mutable and immutable data.

---

### 21.5 OADP Planning by Access Mode

For RWO/RWOP block volumes:

```text
CSI snapshot is often a good option if supported by the CSI driver.
```

For RWX file volumes:

```text
CSI snapshot support depends on backend. File-system backup may be needed.
```

For NFS:

```text
Native CSI snapshot might not exist depending on how NFS is provisioned. File-system backup may be required.
```

For ODF CephFS:

```text
Check ODF/OADP support for CephFS snapshots and Data Mover behavior in your installed version.
```

For databases:

```text
Application-native backup is usually safer than raw volume snapshot alone.
```

---

### 21.6 Restore Awareness

After restore, verify:

```bash
oc get pvc -n <ns>
oc get pv
oc describe pvc <pvc> -n <ns>
oc get pod -n <ns>
oc describe pod <pod> -n <ns>
```

Common restore issues:

| Issue | Cause | Fix |
|---|---|---|
| PVC Pending | StorageClass missing in target cluster | Map/change storage class |
| Access mode unsupported | Target backend differs from source | Use compatible backend or restore to different class |
| Pod cannot mount | Volume attachment/permission/SELinux issue | Check pod events, CSI, SCC |
| App corrupt | Snapshot not app-consistent | Use app-native restore |
| RWX restore fails | File backend not available | Restore to equivalent RWX backend |
| PV retained with old claimRef | Static PV reuse issue | Clear claimRef carefully |

## 23. Security, SCC, SELinux, fsGroup, and Permissions

OpenShift adds strong security defaults compared to vanilla Kubernetes.

Storage issues are often misdiagnosed as access mode issues when they are actually permission/security context problems.

### 23.1 Random UID Behavior

OpenShift commonly runs containers with arbitrary UIDs unless SCC allows otherwise.

An image expecting to write as root may fail:

```text
Permission denied
```

Check:

```bash
oc rsh <pod> id
oc rsh <pod> ls -ld /data
```

Fix options:

- Use an OpenShift-compatible image.
- Set correct file permissions in image.
- Use `fsGroup` if appropriate.
- Use init containers carefully.
- Avoid granting `anyuid` SCC unless required and approved.

---

### 23.2 fsGroup

`fsGroup` can help writable mounted volumes by assigning group ownership/permissions.

Example:

```yaml
spec:
  securityContext:
    fsGroup: 1000670000
```

But in large volumes, recursive ownership changes can slow pod startup. Some CSI drivers support policies to reduce this impact.

---

### 23.3 SELinux

SELinux labels protect containers and host resources.

Possible symptoms:

```text
permission denied
operation not permitted
```

Checks:

```bash
oc describe pod <pod> -n <ns>
oc logs <pod> -n <ns>
```

Node-level investigation:

```bash
oc debug node/<node>
chroot /host
ausearch -m avc -ts recent
```

Only use node debugging when necessary and permitted.

---

### 23.4 NFS Root Squash

With NFS, `root_squash` maps root to anonymous user.

If the container runs as root and tries to write to NFS, it may fail.

Fix options:

- Export with correct UID/GID ownership.
- Use non-root UID matching export permissions.
- Use supplemental groups if allowed.
- Avoid insecure broad permissions unless lab-only.
- Understand `root_squash` security impact before changing.

---

## 24. Performance and Availability Considerations

### 24.1 RWO Block Storage

Pros:

- Good latency
- Good database fit
- Easier consistency model
- Often supports snapshots

Cons:

- Single-node attachment
- Failover requires detach/attach
- Multi-attach errors during node failure
- Not shared across replicas

### 24.2 RWX File Storage

Pros:

- Shared across nodes
- Good for common files
- Enables multi-replica app writes

Cons:

- Network filesystem latency
- Metadata bottlenecks
- Backend availability critical
- Harder backup consistency
- Application locking required

### 24.3 Local PV

Pros:

- Very fast
- Good for high-performance workloads
- No network storage latency

Cons:

- Tied to one node
- Node failure impacts data availability
- Requires application replication
- Backup/restore planning is critical

## 26. Anti-Patterns

### Anti-Pattern 1: Multiple Database Pods Sharing One RWX Datadir

Bad:

```text
3 MySQL pods -> same RWX PVC -> /var/lib/mysql
```

Why bad:

- MySQL data directory is not designed for concurrent writers.
- RWX filesystem does not provide database clustering.

Correct:

- MySQL operator
- StatefulSet with one PVC per replica
- Database replication
- App-native backup

---

### Anti-Pattern 2: Deployment with Replicas > 1 Using One RWO PVC

Bad:

```text
Deployment replicas=3
PVC accessMode=RWO
```

Correct:

- RWX if sharing required
- StatefulSet if each replica needs own data
- Scale replicas to 1
- Use Recreate strategy

---

### Anti-Pattern 3: Assuming Access Mode Enforces Read-Only at Application Level

Bad assumption:

```text
PV says ROX, so application can never write.
```

Reality:

- Backend and mount options matter.
- Pod mount `readOnly: true` matters.
- Filesystem/export permissions matter.

---

### Anti-Pattern 4: Snapshotting Busy RWX Volumes Without Quiesce

Bad:

```text
Take raw snapshot while multiple pods are writing.
```

Correct:

- Maintenance mode
- Scale down writers
- Use app hooks
- Use app-native backup
- Validate restore

---

### Anti-Pattern 5: Granting anyuid for Every Storage Permission Problem

Bad:

```bash
oc adm policy add-scc-to-user anyuid -z default -n app
```

Correct:

- Diagnose UID/GID/SELinux/NFS permissions.
- Use least privilege.
- Fix image permissions.
- Use correct SCC only when justified.

## 27. Migration and Change Management

### 27.1 Changing Access Mode Is Not Always Editable

PVC fields are limited after binding. You usually cannot simply patch access modes on a bound PVC and expect backend behavior to change.

Safer process:

1. Identify source PVC and PV.
2. Back up data.
3. Stop application.
4. Create new PVC with desired access mode and compatible StorageClass.
5. Copy data.
6. Update workload to use new claim.
7. Validate.
8. Retain old volume until rollback window expires.

---

### 27.2 RWO to RWX Migration

Example scenario:

```text
Single web pod with RWO uploads -> scale to multiple replicas requiring shared uploads
```

Process:

1. Create RWX PVC.
2. Scale app down or enable maintenance.
3. Copy data from RWO PVC to RWX PVC.
4. Update Deployment to mount RWX PVC.
5. Scale app up.
6. Validate concurrent writes.
7. Update backup policy.
8. Decommission old PVC after retention period.

Data copy pod pattern:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: data-copy
  namespace: app-prod
spec:
  restartPolicy: Never
  containers:
    - name: copy
      image: registry.access.redhat.com/ubi9/ubi
      command: ["/bin/bash", "-c"]
      args:
        - |
          set -euo pipefail
          cp -a /old/. /new/
          echo "copy complete"
      volumeMounts:
        - name: old
          mountPath: /old
        - name: new
          mountPath: /new
  volumes:
    - name: old
      persistentVolumeClaim:
        claimName: old-rwo-pvc
    - name: new
      persistentVolumeClaim:
        claimName: new-rwx-pvc
```

This only works if both volumes can be mounted to the same pod/node according to backend rules.

---

### 27.3 RWX to RWO Migration

Use when moving from shared files to per-replica or database-native storage.

Process:

1. Analyze data ownership.
2. Split data by replica/tenant/app component.
3. Create separate RWO PVCs.
4. Copy relevant data.
5. Update app config.
6. Validate consistency.
7. Update backup and restore runbooks.

## 28. Exam and Interview Notes

### 28.1 Must-Know Definitions

- RWO: read-write by one node
- RWOP: read-write by one pod
- ROX: read-only by many nodes
- RWX: read-write by many nodes

### 28.2 Must-Know Commands

```bash
oc get sc
oc get pvc -A
oc get pv
oc describe pvc <pvc> -n <ns>
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get volumeattachment
```

### 28.3 Typical Exam-Style Mistakes

- Requesting RWX from a block-only StorageClass
- Using one RWO PVC with many Deployment replicas
- Forgetting `storageClassName`
- Wrong namespace for PVC
- Mounting wrong claim name
- Ignoring pod events
- Not checking access mode in `oc get pv`
- Thinking RWO means one pod
- Forgetting `readOnly: true` for ROX use
- Using NFS path/server incorrectly
- Forgetting SCC/permission issues after storage mounts

### 28.4 Interview Answer: RWO vs RWOP

Good answer:

> RWO allows a volume to be mounted read-write by a single node. Multiple pods on that same node may still use it, depending on backend and scheduling. RWOP restricts the volume to a single pod across the cluster and is better for strict single-writer workloads, provided the CSI driver supports it.

### 28.5 Interview Answer: RWX for Database?

Good answer:

> RWX only means the filesystem can be mounted read-write by many nodes. It does not make a database safe for multiple concurrent writers. Databases need clustering/replication protocols or one PVC per replica. For most databases, I would use RWO/RWOP per pod with StatefulSet or an operator, not a shared RWX datadir.

```bash
    - name: data
      persistentVolumeClaim:
        claimName: rwo-data
EOF
```

Observe:

```bash
oc get pod -o wide
oc describe pod writer-2
```

Depending on scheduling and backend:

- It may run if scheduled on same node.
- It may fail if scheduled on another node.
- It may show multi-attach events.

This demonstrates why RWO is node-scoped, not strictly pod-scoped.

## 30. Cheat Sheet

### 30.1 Fast Definitions

```text
RWO  = ReadWriteOnce      = read-write by one node
RWOP = ReadWriteOncePod   = read-write by one pod
ROX  = ReadOnlyMany       = read-only by many nodes
RWX  = ReadWriteMany      = read-write by many nodes
```

### 30.2 Workload Selection

| Requirement | Recommended Mode |
|---|---|
| One database pod | RWO or RWOP |
| Strict single writer | RWOP |
| StatefulSet with per-replica disks | RWO or RWOP |
| Shared uploads across web replicas | RWX |
| Shared read-only model/content | ROX |
| Local high-performance storage | RWO/RWOP with local PV |
| Many pods need same writable files | RWX |
| Many pods need same database data directory | Usually wrong design |

### 30.3 Troubleshooting Flow

```text
PVC Pending?
  -> oc describe pvc
  -> check StorageClass
  -> check access mode support
  -> check CSI provisioner
  -> check quota/capacity/topology

Pod ContainerCreating?
  -> oc describe pod
  -> check FailedMount/FailedAttachVolume
  -> check volumeattachment
  -> check node/CSI logs
  -> check backend reachability

Multi-Attach?
  -> check old pod/node
  -> check Deployment strategy
  -> check replicas
  -> wait safe detach
  -> use StatefulSet/RWX/Recreate as appropriate

Permission denied?
  -> check UID/GID
  -> check SCC
  -> check fsGroup
  -> check SELinux
  -> check NFS export/root_squash
```

### 30.4 Backup Rules

```text
RWO/RWOP:
  Easier to reason about. Use CSI snapshot plus app consistency.

ROX:
  Usually safe if truly read-only. Validate publishing workflow.

RWX:
  Many possible writers. Use quiesce, hooks, app locks, or file-level backup.

Database:
  Prefer application-native backup or operator-managed backup.
```

### 30.5 Senior Admin Golden Rules

1. RWO means one node, not one pod.
2. RWOP means one pod and is safer for strict single-writer workloads.
3. RWX enables sharing, but it does not guarantee application correctness.
4. ROX should still be enforced with mount flags and backend permissions.
5. StorageClass determines backend behavior; access mode only requests capability.
6. Check pod events before guessing.
7. For databases, storage snapshot alone may not be application-consistent.
8. A PVC can bind only to a compatible PV.
9. Dynamic provisioning fails if the driver cannot satisfy access mode.
10. Always test restore, not just backup.
