# VolumeSnapshotClass in OpenShift — Advanced Storage and Backup Awareness

**Audience:** Advanced OpenShift Administrators, Kubernetes Platform Engineers, SREs, Backup/DR Engineers  
**Experience level:** 10+ years Linux/DevOps/OpenShift administration  
**Focus area:** Storage and Backup Awareness  
**API group:** `snapshot.storage.k8s.io/v1`  
**Core object:** `VolumeSnapshotClass`

---

## 1. Executive Summary

`VolumeSnapshotClass` is the **cluster-level policy object** that tells OpenShift/Kubernetes **how snapshots should be created for CSI-backed persistent volumes**.

It is similar in concept to `StorageClass`, but instead of describing how to provision a new `PersistentVolume`, it describes how to create a **snapshot** of an existing CSI volume.

In production OpenShift administration, `VolumeSnapshotClass` is important for:

- Storage backup design
- Application rollback
- PVC restore testing
- Disaster recovery workflows
- Backup operator integration
- CSI driver validation
- Storage backend lifecycle control
- Snapshot retention behavior
- Troubleshooting snapshot failures

A `VolumeSnapshotClass` does **not** itself create a backup. It defines the snapshot behavior. A user or backup tool creates a `VolumeSnapshot`, and the snapshot controller plus CSI driver use the selected `VolumeSnapshotClass` to create the real backend snapshot.

---

## 2. Why VolumeSnapshotClass Exists

Before CSI snapshots, storage snapshots were usually handled outside Kubernetes:

- Storage array CLI
- Cloud console
- Vendor backup tool
- Manual LUN or disk snapshot
- VM-level snapshot
- File-level backup

This created problems:

- Kubernetes did not know that a snapshot existed.
- Backup tools had to talk directly to each storage backend.
- Restore workflows were not portable.
- Developers could not request snapshots using Kubernetes-native APIs.
- Admins could not define reusable snapshot policies in cluster objects.

CSI volume snapshots solve this by giving Kubernetes/OpenShift standard snapshot APIs:

| Object | Scope | Purpose |
|---|---:|---|
| `VolumeSnapshotClass` | Cluster | Defines snapshot type/policy/driver |
| `VolumeSnapshot` | Namespace | User request to snapshot a PVC |
| `VolumeSnapshotContent` | Cluster | Actual bound snapshot resource, similar to `PV` |

`VolumeSnapshotClass` is the admin-controlled bridge between Kubernetes snapshot requests and the storage backend snapshot capability.

---

## 3. Simple Analogy: StorageClass vs VolumeSnapshotClass

| Area | StorageClass | VolumeSnapshotClass |
|---|---|---|
| Main job | Creates new PVs | Creates snapshots of existing PVs |
| User object | PVC | VolumeSnapshot |
| Backend action | `CreateVolume` | `CreateSnapshot` |
| Controller object | PV | VolumeSnapshotContent |
| CSI driver field | `provisioner` | `driver` |
| Lifecycle policy | `reclaimPolicy` | `deletionPolicy` |
| Typical admin owner | Cluster/storage admin | Cluster/storage/backup admin |

Think like this:

```text
StorageClass         = how to create storage
VolumeSnapshotClass  = how to create snapshots of that storage
PVC                  = request for storage
VolumeSnapshot       = request for snapshot
PV                   = actual provisioned volume
VolumeSnapshotContent = actual provisioned snapshot object
```

|---|---|---:|---|
| `VolumeSnapshotClass` | Cluster admin / storage operator | Cluster | Defines snapshot behavior |

| `VolumeSnapshotContent` | Snapshot controller dynamically, or admin manually | Cluster | Represents real backend snapshot |
| Backend snapshot | CSI driver / storage system | Outside Kubernetes | Real point-in-time snapshot |

## 5. OpenShift CSI Snapshot Architecture

OpenShift uses Kubernetes CSI snapshot APIs with OpenShift-managed operators and controllers.

Important components:

### 5.1 CSI Snapshot Controller Operator

The CSI Snapshot Controller Operator is installed by OpenShift and runs in:

```bash
openshift-cluster-storage-operator
```

It installs/manages the snapshot controller and snapshot CRDs.

Useful checks:

```bash
oc get co storage
oc get pods -n openshift-cluster-storage-operator
oc get crd | grep snapshot.storage.k8s.io
```

Expected snapshot CRDs:

```text
volumesnapshotclasses.snapshot.storage.k8s.io
volumesnapshotcontents.snapshot.storage.k8s.io
volumesnapshots.snapshot.storage.k8s.io
```

### 5.2 Snapshot controller

The snapshot controller watches:

- `VolumeSnapshot`
- `VolumeSnapshotContent`

It handles:

- Binding `VolumeSnapshot` to `VolumeSnapshotContent`
- Dynamic creation of `VolumeSnapshotContent`
- Deletion lifecycle based on `deletionPolicy`
- Status updates such as `readyToUse`

### 5.3 CSI external snapshotter sidecar

The CSI driver vendor provides the `csi-external-snapshotter` sidecar with the CSI driver.

The sidecar watches `VolumeSnapshotContent` and calls CSI operations against the storage backend:

```text
CreateSnapshot
DeleteSnapshot
```

Very important: OpenShift may provide the snapshot controller, but **the CSI driver must support snapshots**. If the CSI driver does not implement snapshot capability, `VolumeSnapshotClass` alone will not help.

## 6. VolumeSnapshotClass API Definition

A basic `VolumeSnapshotClass` looks like this:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-example-snapclass
driver: example.csi.driver.com
deletionPolicy: Delete
parameters: {}
```

Main fields:

| Field | Required | Meaning |
|---|---:|---|
| `apiVersion` | Yes | Snapshot API group/version |
| `kind` | Yes | `VolumeSnapshotClass` |
| `metadata.name` | Yes | Class name used by `VolumeSnapshot` |
| `driver` | Yes | CSI driver that handles snapshot creation |
| `deletionPolicy` | Yes | What happens to backend snapshot when snapshot object is deleted |
| `parameters` | No | Driver-specific snapshot options |

---

## 7. Field-by-Field Deep Dive

## 7.1 `metadata.name`

Example:

```yaml
metadata:
  name: ocs-storagecluster-rbdplugin-snapclass
```

This is the name users reference in `VolumeSnapshot`:

```yaml
spec:
  volumeSnapshotClassName: ocs-storagecluster-rbdplugin-snapclass
```

Admin guidance:

- Use clear names.
- Include storage backend or driver type.
- Include policy intent if multiple classes exist.

Example naming convention:

```text
<backend>-<driver>-<policy>-snapclass
```

Examples:

```text
odf-rbd-delete-snapclass
odf-rbd-retain-snapclass
vsphere-retain-snapclass
aws-ebs-delete-snapclass
```

---

## 7.2 `driver`

Example:

```yaml
driver: openshift-storage.rbd.csi.ceph.com
```

The `driver` field must match the CSI driver responsible for the source PVC's storage backend.

You can inspect StorageClasses:

```bash
oc get storageclass
oc describe storageclass <storageclass-name>
```

Look for:

```yaml
provisioner: <csi-driver-name>
```

For snapshots, the `VolumeSnapshotClass.driver` should align with the CSI provisioner used by the source PVC.

Example:

```bash
oc get sc ocs-storagecluster-ceph-rbd -o yaml | grep provisioner
```

Example output:

```yaml
provisioner: openshift-storage.rbd.csi.ceph.com
```

Then the matching snapshot class should use:

```yaml
driver: openshift-storage.rbd.csi.ceph.com
```

### Common mistake

Using a snapshot class for a different CSI driver.

Example mistake:

```text
PVC created by:  openshift-storage.rbd.csi.ceph.com
SnapshotClass:   openshift-storage.cephfs.csi.ceph.com
```

Result:

- Snapshot stays unready.
- Events show driver mismatch or unsupported source.
- Snapshot controller cannot provision the expected backend snapshot.

---

## 7.3 `deletionPolicy`

Allowed values:

```text
Delete
Retain
```

This controls what happens when the `VolumeSnapshot` is deleted.

### `Delete`

```yaml
deletionPolicy: Delete
```

When the `VolumeSnapshot` is deleted:

- `VolumeSnapshotContent` is deleted.
- The physical backend snapshot is deleted.

Good for:

- Temporary snapshots
- Dev/test rollback
- Short-lived backup workflows
- CI/CD pre-upgrade checkpoints
- Avoiding orphaned storage costs

Risk:

- Deleting the Kubernetes snapshot object removes the actual backend snapshot.
- Not ideal for long-term retention unless another backup system has copied the data elsewhere.

### `Retain`

```yaml
deletionPolicy: Retain
```

When the `VolumeSnapshot` is deleted:

- `VolumeSnapshotContent` remains.
- The backend physical snapshot remains.

Good for:

- Compliance retention
- Manual DR control
- Forensic snapshots
- Long-lived protected recovery points
- Admin-managed storage retention

Risk:

- Orphaned snapshots can accumulate.
- Backend storage consumption can grow.
- Manual cleanup is required.
- Users may think data is deleted while backend copies still exist.

### Production recommendation

| Use case | Recommended policy |
|---|---|
| Developer temporary snapshot | `Delete` |
| Backup tool-managed snapshot | Depends on tool design |
| Compliance snapshot | `Retain` |
| Before risky application change | `Delete` or `Retain`, based on rollback window |
| DR recovery point | `Retain` |
| Cost-sensitive cloud volumes | Usually `Delete`, with external backup copy |

---

## 7.4 `parameters`

Example:

```yaml
parameters:
  snapshot-type: crash-consistent
  retention: short
```

`parameters` is a key-value map passed to the CSI driver. Kubernetes does not interpret these values. They are opaque to Kubernetes.

Important:

- Supported parameters depend entirely on the CSI driver.
- Not every CSI driver requires parameters.
- Wrong parameters may be ignored or may cause snapshot creation failure.
- Always check vendor documentation for valid keys.

Examples of possible vendor-specific use cases:

- Snapshot type
- Snapshot location
- Consistency mode
- Encryption option
- Backend pool
- Tags/labels
- Snapshot group or profile

Do not blindly copy parameters from another storage platform.

## 8. Default VolumeSnapshotClass

You can mark a `VolumeSnapshotClass` as default using this annotation:

```yaml
metadata:
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
```

Example:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: odf-rbd-default-snapclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Delete
```

If a `VolumeSnapshot` does not specify `volumeSnapshotClassName`, Kubernetes/OpenShift tries to select a default class matching the CSI driver of the PVC's StorageClass.

Example snapshot without explicit class:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-snapshot
  namespace: database
spec:
  source:
    persistentVolumeClaimName: mysql-data
```

### Default class caution

You should have only one default `VolumeSnapshotClass` per CSI driver.

If multiple default snapshot classes exist for the same CSI driver, snapshot creation can fail because the controller cannot determine which class to use.

Production advice:

- Prefer explicit `volumeSnapshotClassName` in automation.
- Use default class only where developer simplicity is required.
- Audit default classes regularly.

Commands:

```bash
oc get volumesnapshotclass -o custom-columns=NAME:.metadata.name,DRIVER:.driver,DELETEPOLICY:.deletionPolicy,DEFAULT:.metadata.annotations.snapshot\.storage\.kubernetes\.io/is-default-class
```

## 10. Restore PVC from VolumeSnapshot

A snapshot is useful only if you can restore it.

Create a new PVC using the snapshot as a data source:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-restore
  namespace: database
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  dataSource:
    name: mysql-data-snap-001
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

Apply:

```bash
oc apply -f mysql-restore-pvc.yaml
```

Verify:

```bash
oc get pvc mysql-data-restore -n database
oc describe pvc mysql-data-restore -n database
```

Use restored PVC in a deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql-restore-test
  namespace: database
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mysql-restore-test
  template:
    metadata:
      labels:
        app: mysql-restore-test
    spec:
      containers:
      - name: mysql
        image: registry.redhat.io/rhel8/mysql-80
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql/data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: mysql-data-restore
```

## 11. Application Consistency vs Crash Consistency

A storage snapshot is usually **point-in-time** at the storage layer. That does not always mean the application data is fully consistent.

### 11.1 Crash-consistent snapshot

A crash-consistent snapshot is like pulling the power cable from a server and taking disk state at that instant.

It may be acceptable for:

- Stateless apps
- Some journaling file systems
- Some databases with proper WAL/journal replay
- Dev/test rollback

But it can be risky for:

- Active databases
- Message queues
- Multi-volume applications
- Applications with in-memory buffers
- Apps requiring write ordering

### 11.2 Application-consistent snapshot

Application consistency requires coordination before snapshot:

- Stop writes
- Flush buffers
- Quiesce database
- Freeze filesystem
- Ensure transaction logs are consistent
- Then snapshot
- Resume application

Example MySQL safe-ish process:

```bash
# Example only; adapt for production database method
oc exec -n database deploy/mysql -- mysql -uroot -p$MYSQL_ROOT_PASSWORD -e "FLUSH TABLES WITH READ LOCK;"
# Create snapshot quickly
# Then unlock
oc exec -n database deploy/mysql -- mysql -uroot -p$MYSQL_ROOT_PASSWORD -e "UNLOCK TABLES;"
```

For production databases, prefer database-native backup tools or backup operators with pre/post hooks.

### 11.3 OpenShift practical advice

Before taking a snapshot of a PVC used by a running pod:

```bash
oc scale deploy/<app> -n <namespace> --replicas=0
# take snapshot
oc scale deploy/<app> -n <namespace> --replicas=<original-count>
```

This reduces risk of unwritten/cached data being excluded from the snapshot.

For stateful apps, consider:

- Database backup hooks
- Operator-supported backup CRs
- Velero/OpenShift API for Data Protection integration
- App-specific quiesce commands
- Multi-volume consistency planning

## 12. VolumeSnapshotClass and OpenShift Data Foundation

In OpenShift Data Foundation environments, snapshot classes are often created by the storage operator.

Typical ODF-related snapshot classes may look similar to:

```text
ocs-storagecluster-rbdplugin-snapclass
ocs-storagecluster-cephfsplugin-snapclass
```

Exact names depend on ODF version and configuration.

Useful commands:

```bash
oc get volumesnapshotclass
oc get volumesnapshotclass -o yaml
oc get sc
oc get sc -o custom-columns=NAME:.metadata.name,PROVISIONER:.provisioner,DEFAULT:.metadata.annotations.storageclass\.kubernetes\.io/is-default-class
```

For RBD block storage, source PVCs usually map to an RBD CSI provisioner. For CephFS file storage, source PVCs usually map to a CephFS CSI provisioner.

Do not use an RBD snapshot class for a CephFS PVC, or a CephFS snapshot class for an RBD PVC.

## 13. RBAC and Security Considerations

### 13.1 Resource scopes

| Resource | Scope | Typical permission owner |
|---|---:|---|
| `VolumeSnapshotClass` | Cluster | Cluster admin/storage admin |
| `VolumeSnapshotContent` | Cluster | Cluster admin/storage controller |
| `VolumeSnapshot` | Namespace | Developer/app admin/backup tool |

### 13.2 Why this matters

A user who can create snapshots can potentially create copies of application data.

That data may include:

- Database records
- Secrets stored inside application volumes
- Customer files
- Application logs
- Exported reports
- Configuration data

Snapshot creation is therefore a data access concern, not only a storage concern.

### 13.3 Check API resources

```bash
oc api-resources | grep -i snapshot
```

Example output:

```text
volumesnapshotclasses              snapshot.storage.k8s.io/v1   false   VolumeSnapshotClass
volumesnapshotcontents             snapshot.storage.k8s.io/v1   false   VolumeSnapshotContent
volumesnapshots                    snapshot.storage.k8s.io/v1   true    VolumeSnapshot
```

### 13.4 Check permissions

Can a user create snapshots in a namespace?

```bash
oc auth can-i create volumesnapshots.snapshot.storage.k8s.io -n database --as alice
```

Can a user manage snapshot classes?

```bash
oc auth can-i create volumesnapshotclasses.snapshot.storage.k8s.io --as alice
```

In most production clusters:

- Developers may be allowed to create `VolumeSnapshot` in their own namespace.
- Developers should not manage `VolumeSnapshotClass`.
- Developers should not manage `VolumeSnapshotContent`.
- Backup operators get dedicated RBAC.

## 14. Backup and DR Design Considerations

### 14.1 Snapshot is not always backup

A storage snapshot is not automatically a full backup.

A snapshot may depend on:

- Same storage backend
- Same cluster
- Same availability zone
- Same cloud account
- Same storage pool
- Same encryption keys

If the storage backend fails, local snapshots may fail with it.

For real backup/DR, ask:

| Question | Why it matters |
|---|---|
| Is the snapshot stored on the same backend? | Same failure domain risk |
| Is it replicated off-cluster? | DR readiness |
| Can it restore to another cluster? | Migration/DR requirement |
| Is data application-consistent? | Database reliability |
| Is snapshot encrypted? | Compliance |
| Who can delete it? | Ransomware/insider risk |
| Is retention automated? | Cost/control |
| Are restores tested? | Backup without restore test is incomplete |

### 14.2 When VolumeSnapshotClass is enough

Good use cases:

- Short rollback before upgrade
- Developer test snapshot
- Restore same app into same namespace or test namespace
- Backup operator temporary snapshot before object-store upload
- Fast local recovery

### 14.3 When you need more than VolumeSnapshotClass

You need a complete backup solution when requiring:

- Cross-cluster restore
- Offsite backup
- Long-term retention
- Object storage export
- Encrypted immutable backups
- Namespace/application metadata backup
- Multi-resource restore
- Scheduled backups
- Compliance reporting

Common OpenShift ecosystem options include:

- OpenShift API for Data Protection / Velero-based workflows
- ODF backup/DR capabilities
- Storage vendor backup operators
- Database-native backups
- Enterprise backup platforms integrated with CSI snapshots

## 15. Troubleshooting VolumeSnapshotClass Issues

## 15.1 Snapshot remains `readyToUse: false`

Check snapshot:

```bash
oc describe volumesnapshot <snapshot-name> -n <namespace>
```

Check content:

```bash
oc get volumesnapshotcontent
oc describe volumesnapshotcontent <content-name>
```

Check events:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Possible causes:

- CSI driver does not support snapshots.
- Wrong `VolumeSnapshotClass.driver`.
- Missing `VolumeSnapshotClass`.
- No default `VolumeSnapshotClass` and snapshot did not specify one.
- Backend snapshot quota exceeded.
- Source PVC is not bound.
- CSI snapshotter sidecar is not running.
- Storage backend credentials/config are broken.
- Backend snapshot creation is slow.

---

## 15.2 Error: no default VolumeSnapshotClass

Symptoms:

```text
failed to get snapshot class
could not find requested VolumeSnapshotClass
no default VolumeSnapshotClass found
```

Check:

```bash
oc get volumesnapshotclass
```

Fix option 1: specify class explicitly:

```yaml
spec:
  volumeSnapshotClassName: odf-rbd-delete-snapclass
```

Fix option 2: configure default class:

```bash
oc annotate volumesnapshotclass odf-rbd-delete-snapclass \
  snapshot.storage.kubernetes.io/is-default-class="true"
```

---

## 15.3 Error: multiple default VolumeSnapshotClasses

Symptoms:

```text
multiple default VolumeSnapshotClasses were found
```

Check:

```bash
oc get volumesnapshotclass -o yaml | grep -B5 -A5 'is-default-class'
```

Fix:

```bash
oc annotate volumesnapshotclass <wrong-class> \
  snapshot.storage.kubernetes.io/is-default-class-
```

Then keep only one default per CSI driver.

---

## 15.4 Driver mismatch

Check source PVC StorageClass:

```bash
PVC=mysql-data
NS=database
SC=$(oc get pvc $PVC -n $NS -o jsonpath='{.spec.storageClassName}')
echo $SC
oc get sc $SC -o jsonpath='{.provisioner}{"\n"}'
```

Check VolumeSnapshotClass driver:

```bash
oc get volumesnapshotclass <snapclass> -o jsonpath='{.driver}{"\n"}'
```

They should match logically.

---

## 15.5 SnapshotContent stuck with finalizer

Check finalizers:

```bash
oc get volumesnapshot <snapshot-name> -n <namespace> -o yaml | grep -A5 finalizers
oc get volumesnapshotcontent <content-name> -o yaml | grep -A5 finalizers
```

Do not remove finalizers casually. Finalizers protect against deleting API objects while backend resources still exist.

Last-resort cleanup only after confirming no dependent PVC, snapshot, or backend operation exists:

```bash
oc patch volumesnapshot <snapshot-name> -n <namespace> \
  --type=merge -p '{"metadata":{"finalizers":null}}'
```

For content:

```bash
oc patch volumesnapshotcontent <content-name> \
  --type=merge -p '{"metadata":{"finalizers":null}}'
```

Production warning:

Removing finalizers can orphan backend snapshots or break restore references. Always check storage backend state before force cleanup.

---

## 15.6 Backend snapshot quota exceeded

Symptoms may include:

```text
snapshot limit reached
maximum snapshots per volume exceeded
quota exceeded
ResourceExhausted
```

Check:

```bash
oc describe volumesnapshot <snapshot> -n <namespace>
oc describe volumesnapshotcontent <content>
```

Actions:

- Delete old snapshots.
- Check `deletionPolicy` behavior.
- Clean retained backend snapshots manually if required.
- Review storage backend limits.
- For vSphere, check configured maximum snapshots per block volume.

---

## 15.7 CSI snapshotter sidecar issue

Find CSI driver pods:

```bash
oc get pods -A | grep -i csi
```

Check containers:

```bash
oc get pod <csi-controller-pod> -n <csi-namespace> -o jsonpath='{.spec.containers[*].name}{"\n"}'
```

Look for snapshotter container names such as:

```text
csi-snapshotter
snapshotter
```

Check logs:

```bash
oc logs <csi-controller-pod> -n <csi-namespace> -c csi-snapshotter
```

Also check CSI driver controller logs:

```bash
oc logs <csi-controller-pod> -n <csi-namespace> -c <driver-container-name>
```

## 19. Common Interview and Exam Questions

### Q1. What is VolumeSnapshotClass?

`VolumeSnapshotClass` is a cluster-scoped snapshot policy object. It defines the CSI driver, deletion behavior, and optional backend-specific parameters used when dynamically creating snapshots of PVCs.

### Q2. Is VolumeSnapshotClass namespaced?

No. It is cluster-scoped, like `StorageClass`.

### Q3. What are required fields?

- `driver`
- `deletionPolicy`

Plus normal Kubernetes fields such as `apiVersion`, `kind`, and `metadata.name`.

### Q4. What is the difference between VolumeSnapshot and VolumeSnapshotContent?

`VolumeSnapshot` is a namespaced user request. `VolumeSnapshotContent` is a cluster-scoped representation of the actual provisioned backend snapshot.

### Q5. What happens with `deletionPolicy: Delete`?

Deleting the `VolumeSnapshot` deletes the `VolumeSnapshotContent` and the underlying backend snapshot.

### Q6. What happens with `deletionPolicy: Retain`?

Deleting the `VolumeSnapshot` keeps the `VolumeSnapshotContent` and the physical backend snapshot.

### Q7. Can any PVC be snapshotted?

No. The PVC must be backed by a CSI driver that supports volume snapshots.

### Q8. Can NFS PVs be snapshotted using VolumeSnapshotClass?

Only if the NFS storage is managed through a CSI driver that implements snapshot support. Traditional static NFS PVs do not automatically support CSI snapshots.

### Q9. Does VolumeSnapshotClass create scheduled backups?

No. It defines snapshot behavior. Scheduling requires another tool, operator, CronJob, or backup platform.

### Q10. Is a snapshot a complete disaster recovery backup?

Not necessarily. A snapshot may remain on the same storage backend and failure domain. DR usually requires off-cluster/offsite copy, retention, encryption, and restore testing.

## 20. Real Production Mistakes

### Mistake 1: Treating snapshots as backups

Snapshots are often local to the storage backend. If the backend fails, the snapshots may fail too.

### Mistake 2: No restore testing

A snapshot policy without restore testing is incomplete.

### Mistake 3: Wrong deletion policy

Using `Delete` for compliance snapshots can destroy required data. Using `Retain` everywhere can create cost and cleanup problems.

### Mistake 4: Driver mismatch

A snapshot class must match the CSI driver of the source PVC.

### Mistake 5: Snapshotting active databases without quiescing

This can create crash-consistent but not application-consistent recovery points.

### Mistake 6: Giving broad snapshot permissions

Snapshot access can become data exfiltration access.

### Mistake 7: Multiple defaults per driver

This can break snapshot creation when no explicit class is specified.

## 21. Best Practices

1. Keep one clear `VolumeSnapshotClass` per CSI driver and policy type.
2. Use explicit `volumeSnapshotClassName` in production automation.
3. Use `Delete` for temporary snapshots and `Retain` only where required.
4. Validate CSI driver snapshot support before promising backup capability.
5. Test restore regularly.
6. Do not snapshot busy databases without quiesce/application hooks.
7. Restrict RBAC for snapshot creation and snapshot class management.
8. Monitor retained snapshots and backend capacity.
9. Document which snapshot classes are approved for production.
10. Integrate snapshots into a larger backup/DR strategy if off-cluster recovery is required.

## 22. Quick Troubleshooting Matrix

| Symptom | Likely cause | Check | Fix |
|---|---|---|---|
| `VolumeSnapshot` not ready | Backend still creating snapshot | `oc describe volumesnapshot` | Wait/check backend |
| Snapshot class not found | Wrong name | `oc get volumesnapshotclass` | Correct `volumeSnapshotClassName` |
| No snapshot created | No default class | Events | Specify class or set default |
| Driver mismatch | Wrong snapshot class | Compare SC provisioner and snapshot driver | Use matching class |
| Snapshot delete does not remove backend snapshot | `Retain` policy | `oc get volumesnapshotcontent` | Manual cleanup if intended |
| Restore PVC pending | Snapshot not ready or SC issue | PVC events | Wait/fix SC/driver |
| Permission denied | RBAC missing | `oc auth can-i` | Add namespace role |
| Snapshot stuck deleting | Finalizer/backend issue | YAML finalizers, CSI logs | Fix backend; finalizer removal last resort |
| Quota exceeded | Too many backend snapshots | Snapshot events/backend UI | Delete old snapshots/increase quota |
| Snapshot API missing | CRDs/controller missing | `oc get crd` | Check cluster storage operator |

## 23. Mental Model for 10-Year Admins

For an experienced OpenShift administrator, the correct mental model is:

```text
VolumeSnapshotClass is not the backup.
It is the snapshot policy interface between Kubernetes and the CSI backend.

VolumeSnapshot is the request.
VolumeSnapshotContent is the bound cluster object.
CSI snapshotter is the executor.
Storage backend is where the real snapshot exists.
Restore testing proves the design.
```

When troubleshooting, always walk the chain:

```text
PVC -> StorageClass -> CSI Driver -> VolumeSnapshotClass -> VolumeSnapshot -> VolumeSnapshotContent -> CSI sidecar -> Storage backend
```

## 25. One-Line Definition

`VolumeSnapshotClass` is a cluster-scoped CSI snapshot policy that defines which storage driver creates a snapshot, what backend-specific parameters are used, and whether the physical snapshot is deleted or retained when the Kubernetes snapshot object is removed.
