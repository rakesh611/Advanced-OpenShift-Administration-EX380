# Storage Performance Basics in OpenShift

**Track:** Advanced OpenShift Administration  
**Area:** Storage and Backup Awareness  
**Audience:** OpenShift/Kubernetes administrators with Linux, virtualization, DevOps, and production support experience  
**Focus:** Practical storage performance fundamentals, observability, troubleshooting, and backup impact analysis

---

## 1. Why storage performance matters in OpenShift

In OpenShift, application performance is not only CPU, memory, and network. A stateful workload can look healthy from a pod point of view while still failing users because the storage layer is slow. Common examples are:

- A database pod is `Running`, but queries are slow.
- A CI/CD system is online, but builds are slow because artifact writes are slow.
- Prometheus is up, but query latency increases because block storage is saturated.
- A pod starts slowly because PVC attach or mount takes too long.
- Backups succeed, but they overload the production storage backend.
- Restore works, but recovery time is too long for the business RTO.

A 10-year-level administrator should not treat storage as only `PVC Bound` or `PVC Pending`. The real operational question is:

> Is the selected storage type suitable for the workload’s latency, throughput, IOPS, access mode, consistency, backup, restore, and failure-domain requirements?

OpenShift abstracts storage through PV, PVC, StorageClass, CSI drivers, and Operators, but abstraction does not remove physical limits. The application still depends on disks, arrays, object stores, network paths, multipath, storage controllers, CSI sidecars, kubelet volume operations, filesystem behavior, and backup tools.

## 2. Important OpenShift storage terms

### 2.1 PV

A **PersistentVolume** is a cluster-level storage resource. It represents real storage from a backend such as ODF/Ceph, vSphere, SAN, iSCSI, FC, NFS, AWS EBS, Azure Disk, Azure Files, EFS, GCE PD, Cinder, or local storage.

Key performance-related PV fields:

```yaml
spec:
  capacity:
    storage: 100Gi
  accessModes:
  - ReadWriteOnce
  volumeMode: Filesystem
  persistentVolumeReclaimPolicy: Delete
  storageClassName: fast-block
  csi:
    driver: <csi-driver-name>
```

Important point: capacity alone does not tell performance. A 1 TiB slow NFS volume can be slower than a 100 GiB SSD-backed block volume.

### 2.2 PVC

A **PersistentVolumeClaim** is a namespace-level request for storage. Application teams usually create PVCs. The PVC asks for capacity, access mode, volume mode, and StorageClass.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: prod-db
spec:
  accessModes:
  - ReadWriteOnce
  volumeMode: Filesystem
  storageClassName: fast-block
  resources:
    requests:
      storage: 200Gi
```

For performance, the important question is not only whether the PVC is bound. Ask:

- Which StorageClass provisioned it?
- Which CSI driver created it?
- Is it block, file, object-backed, or local?
- What access mode does it use?
- What node or zone is it attached to?
- Is the backend already saturated?
- Is the workload doing random I/O, sequential I/O, sync writes, or metadata-heavy operations?

### 2.3 StorageClass

A **StorageClass** is the platform contract between the application and the storage backend. Kubernetes describes StorageClass as the parameters for a class of storage from which PVs can be dynamically provisioned.

A StorageClass can represent:

- Performance tier, such as `bronze`, `silver`, `gold`, `nvme`, or `archive`.
- Access pattern, such as RWO block or RWX file.
- Backup policy, such as snapshot-enabled or non-snapshot-enabled.
- Encryption policy.
- Availability zone or topology rules.
- Filesystem and mount options.
- Vendor-specific disk type, replication, pool, or QoS settings.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-block
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"
provisioner: csi.example.com
parameters:
  type: ssd
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

Performance-relevant fields:

| Field | Why it matters |
|---|---|
| `provisioner` | Decides which CSI/storage backend creates the volume. |
| `parameters` | Backend-specific performance tier, disk type, pool, replication, filesystem, encryption, etc. |
| `allowVolumeExpansion` | Controls whether PVC size can be increased later. Expansion can solve capacity pressure, not always IOPS pressure. |
| `volumeBindingMode` | `WaitForFirstConsumer` helps schedule storage close to the pod topology. |
| `mountOptions` | Can affect latency, reliability, caching, and failure behavior. Invalid options can cause mount failure. |
| `allowedTopologies` | Restricts where volumes can be provisioned. Wrong topology can cause scheduling or attach issues. |
| `reclaimPolicy` | Operational lifecycle; not direct performance, but important for recovery and data protection. |

## 3. Storage performance language every OpenShift admin must know

### 3.1 Latency

**Latency** is how long one I/O operation takes.

Typical unit: milliseconds or microseconds.

Why it matters:

- Databases are very sensitive to latency, especially for WAL/redo logs and sync commits.
- Small synchronous writes can be slow even when throughput looks high.
- User-facing applications feel latency before they feel raw throughput limits.

Example:

```text
4 KB random write latency: 1 ms = excellent for many database workloads
4 KB random write latency: 20 ms = may be painful for transaction-heavy workloads
4 KB random write latency: 100 ms = severe storage/backend problem or queueing
```

Latency increases when:

- Storage backend is saturated.
- Queue depth is too high.
- Network path is congested.
- Sync writes wait for replication/acknowledgement.
- Backend cache is full.
- Snapshot/COW overhead increases.
- Filesystem metadata operations are heavy.
- Node CPU is saturated and kubelet/CSI operations are delayed.

### 3.2 IOPS

**IOPS** means I/O operations per second.

Small random reads/writes are usually measured by IOPS. For example:

- Database indexes.
- Key-value stores.
- Prometheus TSDB blocks and WAL activity.
- Small file workloads.
- Many container image layer reads.

Important formula:

```text
Throughput = IOPS × block size
```

Example:

```text
10,000 IOPS × 4 KB = about 40 MB/s
10,000 IOPS × 1 MB = about 10 GB/s
```

So IOPS alone is not enough. Always ask the block size.

### 3.3 Throughput

**Throughput** is the amount of data read or written per second.

Typical unit: MB/s or GB/s.

Throughput-heavy workloads:

- Backup jobs.
- Restore jobs.
- Container image registry garbage collection.
- Data warehouse loads.
- Large media/object processing.
- Sequential file reads/writes.

A storage backend can have good throughput but poor small-write latency. That means it can copy large files fast but still perform badly for a transactional database.

### 3.4 Queue depth

**Queue depth** is how many I/O operations are waiting or in flight.

A higher queue depth can improve throughput for capable storage, but it can also hide latency problems. When queues grow, average latency rises.

In Linux, you often see this through:

```bash
iostat -xz 2
```

Important fields:

| Field | Meaning |
|---|---|
| `r/s`, `w/s` | Reads/writes per second. |
| `rkB/s`, `wkB/s` | Read/write throughput. |
| `await` | Average I/O wait time. |
| `aqu-sz` | Average queue size. |
| `%util` | Device busy percentage. High value can mean saturation, but interpret carefully with modern storage. |

### 3.5 Block size

Block size changes the meaning of a performance result.

Common examples:

| Block size | Workload pattern |
|---|---|
| 4 KB | Database random I/O, metadata, small writes. |
| 8 KB | PostgreSQL page size. |
| 16 KB | MySQL/InnoDB page size. |
| 64 KB - 256 KB | Mixed application file I/O. |
| 1 MB+ | Sequential backup/restore/copy workload. |

Never compare a 4 KB random-write test with a 1 MB sequential-write test as if they measure the same thing.

### 3.6 Random vs sequential I/O

**Random I/O** touches many locations on disk. It is harder for many storage systems.

**Sequential I/O** reads/writes large continuous ranges. It is usually easier for disks and storage arrays.

Examples:

| Workload | Pattern |
|---|---|
| PostgreSQL OLTP | Random reads, WAL sequential writes, sync writes. |
| MySQL OLTP | Random reads/writes, redo log writes. |
| Backup stream | Mostly sequential reads and writes. |
| Image registry pull | Many layer reads, mixed pattern. |
| NFS home directory with many small files | Metadata-heavy random I/O. |

### 3.7 Sync vs async writes

A write is **synchronous** when the application waits until data is safely committed before continuing.

Databases often use sync writes for durability:

- PostgreSQL WAL with `fsync`.
- MySQL InnoDB redo logs.
- etcd writes.
- Journaling filesystems.

Sync writes are latency-sensitive. Adding more throughput does not always fix sync-write latency.

### 3.8 Read/write ratio

Always ask whether the workload is:

- Read-heavy.
- Write-heavy.
- Balanced.
- Metadata-heavy.
- Sync-write-heavy.
- Restore-heavy.
- Backup-heavy.

Storage tuning without knowing the read/write ratio is guesswork.

### 3.9 Cache effects

Caches exist in many places:

- Application cache.
- Linux page cache.
- Filesystem cache.
- Storage controller cache.
- Ceph/ODF cache.
- Cloud provider storage cache.
- Object-store gateway cache.

A benchmark can look excellent because it is reading from cache, not real storage. Use direct I/O tests when you need backend behavior:

```bash
fio --direct=1 ...
```

But direct I/O does not represent every application. Many applications intentionally benefit from page cache. Test both direct and realistic application behavior.

## 4. The OpenShift storage I/O path

A write from an application inside a pod can pass through many layers:

```text
Application process
  -> container mount namespace
    -> mounted PVC path
      -> filesystem or raw block device
        -> kubelet volume manager
          -> CSI node plugin
            -> Linux kernel block/NFS/Ceph/iSCSI/FC stack
              -> node NIC/HBA/multipath/device mapper
                -> network or SAN fabric
                  -> storage backend/controller/OSDs/object gateway
                    -> physical SSD/HDD/NVMe/cloud disk
```

For troubleshooting, this means the issue can be in any of these layers:

| Layer | Example issue |
|---|---|
| Application | Too many fsyncs, small writes, no batching, bad DB config. |
| Pod/container | CPU throttling, memory pressure, wrong mount path, logs filling disk. |
| PVC/PV | Wrong StorageClass, wrong access mode, undersized volume, no expansion. |
| Kubelet | Volume mount delay, stale mount, node pressure. |
| CSI | Attach failure, slow provision, driver pod unhealthy. |
| Node OS | High iowait, multipath issue, network drops, filesystem errors. |
| Network | Packet loss, MTU mismatch, congestion, storage VLAN problem. |
| Backend | Pool full, OSD down, array cache exhausted, cloud disk throttling. |
| Backup system | Snapshot storm, repository bottleneck, object-store throttling. |

A senior admin avoids jumping directly to “storage is slow”. First isolate where the delay is introduced.

## 5. Storage types and performance behavior

OpenShift can use several storage categories. Each category has a different performance profile.

### 5.1 Ephemeral storage

Ephemeral storage is local transient storage tied to the pod/node lifecycle. It is used for:

- Container writable layers.
- Logs.
- `emptyDir` volumes.
- Scratch space.
- Temporary caches.

Important behavior:

- It does not survive pod rescheduling to another node.
- It is shared with node OS, kubelet, container runtime, and other pods.
- It is not a durable backup target.
- It can cause pod eviction if node ephemeral storage is exhausted.
- It can be fast, but it does not provide persistent-storage guarantees.

Use ephemeral storage for:

- Build scratch space.
- Temporary cache.
- Non-critical temporary files.

Do not use it for:

- Databases requiring durability.
- Backup repositories.
- Business data.

Example request/limit:

```yaml
resources:
  requests:
    ephemeral-storage: 2Gi
  limits:
    ephemeral-storage: 10Gi
```

### 5.2 Block storage

Block storage gives the pod a disk-like volume. It is commonly used through RWO PVCs.

Examples:

- ODF RBD block.
- AWS EBS.
- Azure Disk.
- GCE Persistent Disk.
- vSphere CNS block volumes.
- SAN/iSCSI/FC backed CSI volumes.

Good for:

- Databases.
- Prometheus/metrics storage.
- Elasticsearch-like workloads, when supported.
- Loki components that require block only when architecture supports it.
- Single-writer transactional workloads.
- Low-latency workloads.

Performance strengths:

- Usually better latency than shared file storage.
- Good for random I/O.
- Good for filesystems owned by one pod at a time.
- Better fit for database WAL/redo workloads.

Limitations:

- Usually RWO, so one node can mount it read-write.
- Pod mobility depends on detach/attach time.
- Multi-AZ behavior depends on backend and topology.
- Not suitable when many pods need simultaneous write access to the same path.

### 5.3 File storage

File storage exposes a shared filesystem.

Examples:

- NFS.
- CephFS / ODF file.
- AWS EFS.
- Azure Files.
- NetApp/Trident file storage.

Good for:

- RWX shared content.
- User uploads shared by multiple replicas.
- Jenkins shared workspaces or artifact areas, depending on workload.
- Read-mostly shared content.
- Applications that require POSIX-like shared file access.

Performance strengths:

- Multiple pods can mount the same PVC with RWX.
- Easier for shared content.
- Good for read-many workloads if backend is sized correctly.

Limitations:

- Metadata-heavy workloads can be slow.
- Small-file workloads can become bottlenecked.
- Network latency matters.
- Locking semantics matter.
- Not always recommended for databases, monitoring, or logging backends.
- NFS behavior depends heavily on server implementation, export options, network, and client mount options.

### 5.4 Object storage

Object storage is accessed through APIs, not normal filesystem PV mounts.

Examples:

- S3.
- NooBaa/ODF Multicloud Object Gateway.
- Ceph RGW.
- Azure Blob.
- Google Cloud Storage.
- OpenStack Swift.

Good for:

- Backup repositories.
- Image registry, especially scaled/HA registry designs.
- Logs/archives.
- Application media objects.
- Large immutable objects.
- Cross-region retention.

Performance strengths:

- Scales well for large object workloads.
- Good durability and off-cluster backup target.
- Good for backup/restore streams.

Limitations:

- Not POSIX filesystem storage.
- Higher per-operation latency than local/block storage.
- Applications need object API support.
- Small object workloads can be inefficient.
- List operations and metadata operations can become expensive.

### 5.5 Local persistent volumes

Local persistent volumes use disks physically attached to a node.

Good for:

- Very low latency.
- High IOPS.
- Workloads that handle their own replication.
- Distributed databases.
- Kafka-style local-disk workloads, if architecture supports it.
- Performance-sensitive workloads where pod must stay near data.

Strengths:

- Avoids network storage latency.
- Can use NVMe/SSD performance directly.
- Predictable if node hardware is dedicated.

Limitations:

- Data is tied to the node.
- Pod cannot freely move to any node unless application replication handles it.
- Node failure can mean volume unavailable.
- Backup and restore planning becomes critical.
- Scheduling must respect topology.

Common StorageClass setting:

```yaml
volumeBindingMode: WaitForFirstConsumer
```

This helps provision/bind the volume only after the scheduler knows where the consuming pod should run.

## 6. Access modes and performance impact

### 6.1 ReadWriteOnce

`ReadWriteOnce` means the volume can be mounted read-write by a single node. It is commonly used for block volumes.

Best fit:

- Databases.
- StatefulSets where each replica has its own PVC.
- Metrics storage.
- Single-writer applications.

Performance note:

RWO block storage is often the best default choice for latency-sensitive stateful workloads.

### 6.2 ReadWriteMany

`ReadWriteMany` means the volume can be mounted read-write by multiple nodes.

Best fit:

- Shared uploads.
- Shared content repositories.
- Read/write shared filesystem applications.

Performance note:

RWX usually means file storage or object-backed behavior. It is convenient, but convenience does not guarantee low latency. RWX file systems often pay extra cost for metadata, locking, network round trips, and consistency.

### 6.3 ReadOnlyMany

`ReadOnlyMany` means multiple nodes can mount read-only.

Best fit:

- Shared static content.
- Reference datasets.
- Read-only configuration/data.

Performance note:

ROX can scale well for read-only workloads, but backend caching and client behavior matter.

### 6.4 ReadWriteOncePod

`ReadWriteOncePod` restricts access to a single pod. This is useful when strict single-pod write ownership is needed.

Performance note:

It is not a performance booster by itself. It is a stronger access guarantee that can prevent accidental multi-writer patterns.

## 7. Volume mode: Filesystem vs Block

### 7.1 Filesystem mode

Most PVCs use:

```yaml
volumeMode: Filesystem
```

The volume is formatted with a filesystem such as XFS or ext4 and mounted into the pod.

Good for:

- Most applications.
- Databases using filesystem paths.
- Web applications.
- Middleware.

Performance considerations:

- Filesystem metadata matters.
- Mount options can matter.
- `fsGroup` ownership changes can slow pod startup on large volumes.
- Many small files can cause metadata bottlenecks.

### 7.2 Block mode

Raw block mode uses:

```yaml
volumeMode: Block
```

The application receives a raw block device instead of a mounted filesystem.

Good for:

- Specialized databases.
- Virtual machines.
- Applications that manage their own filesystem or block layout.

Example pod volume device:

```yaml
volumeDevices:
- name: data
  devicePath: /dev/xvda
volumes:
- name: data
  persistentVolumeClaim:
    claimName: raw-block-pvc
```

Performance considerations:

- Avoids filesystem overhead.
- Application must know how to use the block device safely.
- Backup tools must support raw block semantics.

## 8. StorageClass design for performance tiers

A mature OpenShift platform should not expose only one default StorageClass for every workload. Instead, define clear storage classes based on workload requirements.

Example model:

| StorageClass | Backend | Access | Use case | Performance expectation |
|---|---|---|---|---|
| `bronze-file-rwx` | NFS/CephFS/EFS | RWX | Shared low-criticality files | Moderate latency, shared access. |
| `silver-block-rwo` | Standard SSD block | RWO | General stateful apps | Balanced IOPS/latency. |
| `gold-block-rwo` | Fast SSD/NVMe/cloud premium disk | RWO | Databases, monitoring | Low latency, higher IOPS. |
| `local-nvme` | Local PV | RWO/RWOP | Distributed systems | Very low latency, node-local. |
| `backup-object` | S3/object | API/OBC | Backup/archive | High durability, off-cluster. |

### 8.1 Example StorageClass review commands

```bash
oc get storageclass
oc describe storageclass <storageclass-name>
oc get storageclass <storageclass-name> -o yaml
```

Check:

```bash
oc get sc -o custom-columns=NAME:.metadata.name,PROVISIONER:.provisioner,DEFAULT:.metadata.annotations.storageclass\.kubernetes\.io/is-default-class,RECLAIM:.reclaimPolicy,BINDING:.volumeBindingMode,EXPAND:.allowVolumeExpansion
```

### 8.2 StorageClass questions for production readiness

For every StorageClass, document:

- Backend name and owner.
- Supported access modes.
- Supported volume modes.
- Snapshot support.
- Clone support.
- Expansion support.
- Encryption behavior.
- Default reclaim policy.
- Expected IOPS/throughput/latency range.
- Failure domain.
- Backup policy.
- Restore process.
- Maximum volume size.
- Maximum number of volumes per node.
- Topology restrictions.
- Whether it is approved for databases.
- Whether it is approved for OpenShift monitoring/logging/registry.

## 9. Matching workload to storage

### 9.1 PostgreSQL

Recommended starting point:

- RWO block storage.
- Low latency.
- Snapshot-capable CSI driver.
- Separate WAL/data volumes only if you understand backend behavior.
- Avoid RWX file storage for primary data unless the database/vendor explicitly supports it.

Performance-sensitive areas:

- WAL `fsync` latency.
- Checkpoint behavior.
- Random reads for indexes.
- Write amplification during vacuum/checkpoints.
- Backup reads during production hours.

Useful database-side checks:

```sql
SELECT * FROM pg_stat_bgwriter;
SELECT * FROM pg_stat_database;
```

### 9.2 MySQL/MariaDB

Recommended starting point:

- RWO block storage.
- Low latency for redo logs.
- Adequate memory to reduce random reads.
- Avoid metadata-heavy shared filesystems.

Performance-sensitive areas:

- `innodb_flush_log_at_trx_commit` behavior.
- Redo log write latency.
- Buffer pool miss rate.
- Flush storms.

### 9.3 Prometheus

Recommended starting point:

- RWO block storage.
- Fast local or block storage.
- Capacity planned for retention and cardinality.
- Avoid slow RWX file storage for production metrics.

Performance-sensitive areas:

- WAL writes.
- Compaction.
- Query fan-out.
- High cardinality metrics.
- Retention and block compaction.

### 9.4 Image registry

Storage choice depends on registry topology.

- Non-HA registry can use storage that does not require RWX, but storage must provide consistency suitable for registry operations.
- Scaled/HA registry usually needs object storage or supported shared storage, depending on platform and version.
- Object storage is usually the preferred architecture for scalable registry use.

Performance-sensitive areas:

- Image push throughput.
- Image pull latency.
- Many small layer metadata operations.
- Garbage collection.
- Backend read-after-write consistency.

### 9.5 Jenkins / CI workspaces

Recommended starting point:

- For shared workspaces: RWX file storage sized for metadata operations.
- For high-speed temporary builds: local/ephemeral scratch plus artifact upload to object storage.
- For durable controller data: RWO block or vendor-supported storage.

Performance-sensitive areas:

- Many small files.
- Git checkout metadata operations.
- Artifact writes.
- Concurrent builds.

### 9.6 Logging

Storage design depends on logging stack architecture.

General principles:

- Use the storage type recommended by the logging operator/vendor.
- Avoid unsupported NFS/file backends for log stores that require block/object.
- Plan for write-heavy ingestion and retention.
- Use object storage when the logging architecture is object-store based.

Performance-sensitive areas:

- Ingestion write path.
- Indexing/compaction.
- Query reads.
- Retention deletion.

### 9.7 Backup repository

Recommended starting point:

- Object storage for backup repository whenever possible.
- Off-cluster and preferably off-failure-domain storage.
- Avoid storing backups only on the same storage system as production PVCs.

Performance-sensitive areas:

- Full backup scan time.
- Incremental backup changed-data rate.
- Compression/dedup CPU cost.
- Object-store request rate and throughput.
- Restore parallelism.

## 10. Observability: what to check first

### 10.1 Cluster-level storage inventory

```bash
oc get sc
oc get pv
oc get pvc -A
oc get volumeattachments
oc get csidrivers
oc get pods -A | grep -i csi
```

Better formatted:

```bash
oc get pvc -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,STATUS:.status.phase,SC:.spec.storageClassName,MODE:.spec.volumeMode,ACCESS:.spec.accessModes[*],SIZE:.spec.resources.requests.storage,VOLUME:.spec.volumeName
```

### 10.2 PVC deep check

```bash
oc describe pvc <pvc-name> -n <namespace>
oc get pvc <pvc-name> -n <namespace> -o yaml
```

Look for:

- `Pending` state.
- Events from provisioner.
- Requested StorageClass.
- Access mode mismatch.
- Volume mode mismatch.
- Resize condition.
- Bound PV name.

### 10.3 PV deep check

```bash
oc describe pv <pv-name>
oc get pv <pv-name> -o yaml
```

Look for:

- CSI driver.
- Volume handle.
- Reclaim policy.
- Node affinity/topology.
- Capacity.
- Access modes.
- Mount options.

### 10.4 CSI driver health

CSI components vary by vendor, but many run controller and node pods.

Common checks:

```bash
oc get pods -A | grep -i csi
oc get deployment,statefulset,daemonset -A | grep -i csi
oc get events -A | grep -i csi
oc get volumeattachments
```

Check logs:

```bash
oc logs -n <csi-namespace> <csi-controller-pod> -c <container-name>
oc logs -n <csi-namespace> <csi-node-pod> -c <container-name>
```

Common CSI symptoms:

| Symptom | Possible cause |
|---|---|
| PVC stuck Pending | Provisioner cannot create volume, bad StorageClass, quota, topology issue. |
| Pod stuck ContainerCreating | Attach or mount problem. |
| Multi-attach error | RWO volume attached to another node. |
| Slow mount | Backend slow, filesystem check, large ownership change, network/storage issue. |
| VolumeAttachment stuck | CSI/controller/backend cannot detach/attach. |

### 10.5 Node-level checks

Start with node debug:

```bash
oc debug node/<node-name>
chroot /host
```

Inside the host:

```bash
lsblk -f
findmnt
mount | grep kubelet
df -hT
journalctl -u kubelet --since "1 hour ago"
```

If available:

```bash
iostat -xz 2
pidstat -d 2
sar -d 2
vmstat 2
```

Network checks for network storage:

```bash
ip addr
ip route
ss -s
ethtool <interface>
nmcli dev status
```

For iSCSI/FC/multipath environments, if tools are installed and supported:

```bash
multipath -ll
lsblk
udevadm settle
```

Do not install random packages on RHCOS nodes in production. Use approved debug procedures and support tools.

### 10.6 OpenShift monitoring

OpenShift includes a platform monitoring stack based on Prometheus and related components. You can use the web console Observe section, dashboards, alerts, and PromQL.

PVC capacity metrics commonly available from kubelet:

```promql
kubelet_volume_stats_capacity_bytes
kubelet_volume_stats_available_bytes
kubelet_volume_stats_used_bytes
kubelet_volume_stats_inodes
kubelet_volume_stats_inodes_used
```

Capacity percentage:

```promql
100 * kubelet_volume_stats_used_bytes / kubelet_volume_stats_capacity_bytes
```

Inode usage percentage:

```promql
100 * kubelet_volume_stats_inodes_used / kubelet_volume_stats_inodes
```

Node disk activity examples:

```promql
rate(node_disk_reads_completed_total[5m])
rate(node_disk_writes_completed_total[5m])
rate(node_disk_read_bytes_total[5m])
rate(node_disk_written_bytes_total[5m])
rate(node_disk_io_time_seconds_total[5m])
```

Approximate average read latency:

```promql
rate(node_disk_read_time_seconds_total[5m]) / rate(node_disk_reads_completed_total[5m])
```

Approximate average write latency:

```promql
rate(node_disk_write_time_seconds_total[5m]) / rate(node_disk_writes_completed_total[5m])
```

Important caution:

- `kubelet_volume_stats_*` is mostly capacity/inode visibility, not full storage performance.
- Node disk metrics can be difficult to map back to one PVC, especially with network storage or shared devices.
- Backend-specific dashboards are usually needed for true storage latency, IOPS, and throughput.

### 10.7 ODF / Ceph monitoring

For OpenShift Data Foundation, use the Data Foundation dashboard and backend metrics. Useful areas:

- Cluster health.
- Capacity utilization.
- IOPS.
- Latency.
- Throughput.
- Recovery/rebalancing status.
- OSD health.
- Pool usage.

Typical checks:

```bash
oc -n openshift-storage get storagecluster
oc -n openshift-storage get cephcluster
oc -n openshift-storage get pods
oc -n openshift-storage get cephblockpool
```

## 11. Benchmarking storage correctly

Benchmarking is useful only when it matches the real workload.

### 11.1 Benchmark rules

Follow these rules:

1. Test from inside a pod using the same StorageClass as the application.
2. Test from the same namespace/security constraints if possible.
3. Use a test file larger than memory if measuring backend storage instead of cache.
4. Record block size, read/write mix, direct I/O setting, runtime, number of jobs, and iodepth.
5. Run tests long enough to avoid burst-cache-only results.
6. Do not run destructive write tests on production data PVCs.
7. Run tests during maintenance windows if backend impact is unknown.
8. Compare against baseline from a known-good time.
9. Test backup and restore separately from application I/O.
10. Do not compare different storage classes without documenting all parameters.

### 11.2 Example fio pod

Use an approved fio-capable image from your internal registry. Example pattern:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: fio-pvc
  namespace: storage-test
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: fast-block
  resources:
    requests:
      storage: 20Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: fio
  namespace: storage-test
spec:
  restartPolicy: Never
  containers:
  - name: fio
    image: <approved-fio-image>
    command: ["sleep", "infinity"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: fio-pvc
```

Run:

```bash
oc apply -f fio.yaml
oc rsh -n storage-test pod/fio
```

### 11.3 Sequential throughput test

```bash
fio --name=seq-write \
  --directory=/data \
  --rw=write \
  --bs=1M \
  --size=8G \
  --numjobs=1 \
  --iodepth=16 \
  --direct=1 \
  --runtime=120 \
  --time_based \
  --group_reporting
```

Measures large sequential write throughput.

### 11.4 Random read IOPS test

```bash
fio --name=rand-read \
  --directory=/data \
  --rw=randread \
  --bs=4k \
  --size=8G \
  --numjobs=4 \
  --iodepth=32 \
  --direct=1 \
  --runtime=120 \
  --time_based \
  --group_reporting
```

Measures small random read IOPS.

### 11.5 Random write latency test

```bash
fio --name=rand-write-lat \
  --directory=/data \
  --rw=randwrite \
  --bs=4k \
  --size=8G \
  --numjobs=1 \
  --iodepth=1 \
  --direct=1 \
  --runtime=120 \
  --time_based \
  --group_reporting
```

This is closer to latency-sensitive small-write behavior.

### 11.6 Sync write / fsync-style test

```bash
fio --name=sync-write \
  --directory=/data \
  --rw=write \
  --bs=8k \
  --size=4G \
  --numjobs=1 \
  --iodepth=1 \
  --direct=1 \
  --fsync=1 \
  --runtime=120 \
  --time_based \
  --group_reporting
```

This is useful for database durability-style behavior.

### 11.7 Metadata-heavy small-file test

```bash
mkdir -p /data/smallfiles
for i in $(seq 1 10000); do echo test > /data/smallfiles/file-$i; done
time find /data/smallfiles -type f | wc -l
time rm -rf /data/smallfiles
```

This is not a perfect benchmark, but it quickly exposes RWX/NFS/CephFS metadata pain.

### 11.8 Interpreting fio output

Look at:

| fio field | Meaning |
|---|---|
| `IOPS` | Operations per second. |
| `BW` | Bandwidth/throughput. |
| `clat` | Completion latency. |
| `lat percentiles` | Tail latency, often more important than average. |
| `99.00th`, `99.90th` | High-tail latency; important for user-facing workloads. |
| `cpu` | CPU overhead. |

Do not only read average latency. Tail latency matters because applications experience stalls.

## 12. Common storage performance bottlenecks

### 12.1 Wrong storage type

Symptoms:

- Database moved to RWX file storage and becomes slow.
- Prometheus on shared filesystem shows high query and compaction latency.
- Registry on unsupported/shared backend has consistency or performance issues.

Fix:

- Match workload to block/file/object/local storage requirements.
- Use RWO block for latency-sensitive single-writer workloads.
- Use RWX file only when shared filesystem semantics are required.
- Use object storage for backups and scalable registry/log/archive patterns.

### 12.2 Backend saturation

Symptoms:

- Many workloads slow at the same time.
- Node `iowait` increases.
- ODF/Ceph latency increases.
- Cloud disk hits IOPS or throughput limit.
- Storage array shows high controller utilization.

Fix:

- Move heavy workloads to a faster tier.
- Add backend capacity/performance.
- Reduce backup concurrency.
- Separate noisy workloads.
- Use QoS if backend supports it.
- Review replication/recovery/backfill status.

### 12.3 Noisy neighbor

Symptoms:

- One namespace backup job slows another namespace database.
- CI build storm impacts monitoring storage.
- Batch job causes high backend write latency.

Fix:

- Separate storage classes/pools for critical workloads.
- Schedule backups off-peak.
- Limit backup parallelism.
- Use ResourceQuota and workload controls.
- Use backend QoS or per-volume limits if supported.

### 12.4 Network storage problems

Symptoms:

- NFS/Ceph/iSCSI performance drops during network congestion.
- Retransmits or packet loss.
- Mounts become stale or slow.
- Latency spikes during backup.

Fix:

- Check storage VLAN/network path.
- Validate MTU end-to-end.
- Check NIC errors/drops.
- Check bond/LACP configuration.
- Validate DNS for storage endpoints.
- Check firewall/security group rules.

### 12.5 Filesystem metadata bottleneck

Symptoms:

- Many small file operations are slow.
- `ls`, `find`, `git checkout`, or `npm install` is slow.
- Throughput tests look fine, but application is slow.

Fix:

- Use local scratch for build temporary data.
- Reduce small file count.
- Use artifact packaging.
- Use a backend designed for metadata-heavy workloads.
- Avoid using general-purpose NFS for high-concurrency metadata workloads unless validated.

### 12.6 fsGroup recursive ownership changes

Symptoms:

- Pod starts slowly after mounting a large PVC.
- Pod stuck in `ContainerCreating` for a long time.
- Kubelet logs show ownership/permission work.

Cause:

Security context `fsGroup` can trigger recursive permission changes depending on volume type and policy.

Check pod security context:

```bash
oc get pod <pod> -n <namespace> -o yaml | grep -A20 securityContext
```

Possible mitigation:

- Use `fsGroupChangePolicy: OnRootMismatch` where supported.
- Pre-create correct ownership in image or init process.
- Avoid huge file counts in mounted volume root.
- Use storage driver features that handle ownership efficiently.

Example:

```yaml
securityContext:
  fsGroup: 1000710000
  fsGroupChangePolicy: OnRootMismatch
```

### 12.7 Volume expansion misunderstanding

Expanding PVC size can help when the volume is full or when the backend ties performance to volume size. But it may not improve performance if:

- Backend IOPS are fixed.
- Pool is saturated.
- Application writes are sync-latency-bound.
- Network is bottlenecked.
- StorageClass parameters remain the same.

Check:

```bash
oc get sc <storageclass> -o yaml | grep allowVolumeExpansion
oc patch pvc <pvc-name> -n <namespace> -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'
oc describe pvc <pvc-name> -n <namespace>
```

Remember: shrinking PVs is not supported. Plan carefully.

### 12.8 Snapshot overhead

Snapshots are useful, but they can affect performance depending on backend implementation.

Possible symptoms:

- Writes slow after many snapshots.
- Snapshot deletion causes backend load.
- Restore from snapshot is quick initially but later copy-on-write overhead appears.
- Snapshot storm during backup window impacts production.

Fix:

- Limit snapshot frequency.
- Retain only required snapshots.
- Avoid taking many snapshots of heavily written volumes simultaneously.
- Use application-consistent hooks.
- Move backups to separate failure domain; do not rely only on same-backend snapshots.

### 12.9 Backend near-full condition

Storage systems often degrade before they are 100% full.

Symptoms:

- Writes slow.
- Rebalancing/recovery active.
- OSDs or pools nearfull.
- PVC expansion fails because backend has no capacity.

Fix:

- Add capacity before emergency thresholds.
- Clean unused PVCs/PVs/snapshots.
- Review retention.
- Move cold data to object/archive.
- Avoid filling ODF/Ceph pools near maximum thresholds.

## 13. Troubleshooting workflow: pod is running but storage is slow

### Step 1: Define the symptom

Ask:

- Which namespace/application?
- Which operation is slow: read, write, startup, backup, restore, attach, mount, query?
- When did it start?
- Is it constant or only during backup/peak hours?
- Is one pod affected or many?
- Which PVC and StorageClass?
- Did the pod move nodes?
- Was there a recent cluster upgrade, storage change, snapshot, backup, or node reboot?

Commands:

```bash
oc get pod -n <ns> -o wide
oc describe pod <pod> -n <ns>
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get pv <pv> -o yaml
```

### Step 2: Confirm storage class and backend

```bash
PVC=<pvc-name>
NS=<namespace>
PV=$(oc get pvc $PVC -n $NS -o jsonpath='{.spec.volumeName}')
oc get pvc $PVC -n $NS -o wide
oc get pv $PV -o jsonpath='{.spec.storageClassName}{"\n"}{.spec.csi.driver}{"\n"}{.spec.csi.volumeHandle}{"\n"}'
oc describe sc $(oc get pvc $PVC -n $NS -o jsonpath='{.spec.storageClassName}')
```

Interpretation:

- If it is RWX file storage and workload is database-like, suspect mismatch.
- If it is local PV and pod moved or node degraded, check node locality.
- If it is cloud block, check provider IOPS/throughput limits.
- If it is ODF, check Ceph health and recovery.

### Step 3: Check pod resource pressure

A storage symptom can be caused by CPU throttling or memory pressure.

```bash
oc adm top pod -n <ns>
oc adm top node
oc describe pod <pod> -n <ns> | egrep -i "thrott|oom|evict|pressure|limit|request"
```

Check container CPU throttling from metrics if available:

```promql
rate(container_cpu_cfs_throttled_seconds_total{namespace="<ns>",pod="<pod>"}[5m])
```

If application CPU is throttled, I/O completion and application processing can look like storage latency.

### Step 4: Check node iowait and disk metrics

```bash
oc debug node/<node-name>
chroot /host
vmstat 2
iostat -xz 2
```

Interpretation:

- High `wa` in `vmstat` suggests CPU waiting on I/O.
- High `await` suggests storage latency.
- High `%util` with high queue suggests device saturation.
- Low device metrics but slow app may indicate network storage path or application issue.

### Step 5: Check storage backend

For ODF/Ceph:

```bash
oc -n openshift-storage get pods
oc -n openshift-storage get cephcluster
oc -n openshift-storage get storagecluster
```

In toolbox if available:

```bash
ceph -s
ceph health detail
ceph osd df
```

For NFS:

```bash
mount | grep nfs
nfsstat -m
```

Also check the NFS server side: CPU, disk, network, export options, and logs.

For cloud volumes:

- Check cloud disk IOPS/throughput limits.
- Check whether performance scales with disk size.
- Check burst credit behavior if applicable.
- Check zone attachment and detach/attach events.

### Step 6: Check backup/snapshot activity

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
oc get pods -A | egrep -i 'velero|oadp|backup|kopia|restic'
oc get schedules -A 2>/dev/null
oc get backup -A 2>/dev/null
```

Ask whether a backup window overlaps the incident. A backup can produce large sequential reads and object writes while production databases are doing random sync writes.

### Step 7: Run a controlled comparison

Create a temporary PVC using the same StorageClass and run a short non-destructive benchmark. Compare:

- Same StorageClass, same node.
- Same StorageClass, different node.
- Different StorageClass, same node.
- Same workload outside backup window.

This helps isolate backend vs node vs application.

## 14. Troubleshooting workflow: PVC Pending and performance-related causes

PVC Pending is not a performance result, but it often reveals wrong storage design.

Check:

```bash
oc describe pvc <pvc> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get sc <sc-name> -o yaml
```

Common causes:

| Cause | Symptom | Fix |
|---|---|---|
| No default StorageClass | PVC has no `storageClassName` and remains Pending. | Set `storageClassName` or configure default SC. |
| Wrong access mode | PVC requests RWX but SC supports only RWO. | Use correct RWX-capable SC or change app design. |
| Topology issue | WaitForFirstConsumer waits for pod; pod cannot schedule. | Check pod scheduling, node selectors, taints, zones. |
| Capacity exhausted | Provisioner cannot create volume. | Add backend capacity or reduce request. |
| CSI unhealthy | Provisioning events show CSI errors. | Fix CSI controller/node pods and backend. |
| Quota | Namespace quota blocks PVC. | Adjust quota or PVC size. |

`WaitForFirstConsumer` is not always a problem. It can be correct behavior for topology-aware storage. The PVC may remain Pending until a pod exists that uses it.

## 15. Troubleshooting workflow: slow pod startup due to storage

Symptoms:

- Pod stuck in `ContainerCreating`.
- Events show mount/attach delays.
- Application starts slowly after rescheduling.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get volumeattachments
oc describe volumeattachment <name>
oc logs -n <csi-namespace> <csi-node-pod>
oc logs -n <csi-namespace> <csi-controller-pod>
```

Common causes:

| Cause | Explanation |
|---|---|
| Multi-attach | RWO volume still attached to old node. |
| Slow detach | Cloud/storage backend is slow to detach. |
| Node not ready | Volume cannot detach cleanly. |
| Filesystem check | Large or dirty filesystem may delay mount. |
| fsGroup ownership | Recursive chown on large volume. |
| CSI node plugin issue | Node plugin cannot mount volume. |
| Network storage unreachable | NFS/Ceph/iSCSI endpoint issue. |

Fix approach:

1. Confirm pod node and previous pod node.
2. Confirm VolumeAttachment object.
3. Check CSI logs.
4. Check kubelet logs on target node.
5. Check backend attachment state.
6. Avoid force detach unless you understand data corruption risk.

## 16. Backup and storage performance awareness

Backups are I/O workloads. They are not free.

### 16.1 Backup performance dimensions

| Dimension | Meaning |
|---|---|
| RPO | How much data loss is acceptable. |
| RTO | How quickly restore must complete. |
| Backup window | Time allowed to run backup without harming production. |
| Read load | Backup reads production PVCs or snapshots. |
| Write load | Backup writes to repository/object store. |
| Metadata load | File-level backup scans many files. |
| Network load | Data moves across cluster/storage/object network. |
| CPU load | Compression, encryption, deduplication. |
| Backend load | Snapshots, clones, reads, object uploads. |

### 16.2 Snapshot is not automatically a full backup

A CSI snapshot captures a point-in-time state of a volume and can be used to create a new PVC. However:

- Snapshot support depends on the CSI driver.
- Snapshots often live on the same storage backend as the source volume.
- Same-backend snapshots do not protect against backend loss.
- Crash-consistent snapshots may need application recovery.
- Application-consistent snapshots need quiesce/freeze/pre-post hooks.
- Snapshots can add copy-on-write overhead depending on backend.

For real backup, copy backup data or snapshots to a separate failure domain, often object storage.

### 16.3 Crash-consistent vs application-consistent backup

Crash-consistent backup:

- Similar to pulling power from a server and capturing disk state.
- Filesystem/database may recover using journal/WAL/redo logs.
- Faster and simpler.
- Not always sufficient for complex apps.

Application-consistent backup:

- Application is quiesced, flushed, locked, or put into backup mode.
- Database/application confirms data is in a consistent state.
- Safer restore.
- More operational complexity.
- Can briefly impact writes.

### 16.4 Backup methods and performance impact

| Method | Performance behavior |
|---|---|
| CSI snapshot | Usually fast snapshot creation; backend may pay later on writes/deletes. |
| File-level backup | Can be slow for many small files; high metadata overhead. |
| Restic/Kopia-style backup | Flexible, but scans and uploads can consume CPU/network/storage. |
| Database dump | Application-level consistency; can be CPU and read intensive. |
| Storage replication | Good RPO, but not a replacement for logical backup. |
| Object-store backup | Good off-cluster target; restore speed depends on object store/network/parallelism. |

### 16.5 Backup scheduling rules

Good practices:

- Do not run all namespace backups at the same minute.
- Stagger large PVC backups.
- Limit concurrency.
- Avoid heavy backups during business peak.
- Track backup duration trend.
- Test restore regularly.
- Measure restore throughput, not only backup success.
- Exclude caches and rebuildable data.
- Use application hooks for databases.
- Monitor backend latency during backup windows.

### 16.6 Backup performance troubleshooting

If backup is slow, check:

```bash
oc get pods -A | egrep -i 'backup|velero|oadp|restic|kopia'
oc logs -n <backup-namespace> <backup-pod>
oc get volumesnapshot -A
oc get pvc -A
```

Questions:

- Is backup file-level or snapshot-based?
- How many PVCs are scanned?
- Is object storage throttling?
- Are there many small files?
- Is compression/encryption CPU-bound?
- Is the source PVC on slow RWX storage?
- Is backend recovery/rebalancing active?
- Is network bandwidth saturated?

### 16.7 Restore performance awareness

Restore is often slower or more business-critical than backup.

Measure:

- Time to create PVC from snapshot.
- Time to copy data from object repository.
- Time for database recovery/replay.
- Time for application warm-up.
- Time to validate data.
- Time to update routes/services/DNS if needed.

Restore bottlenecks:

- Object-store read throughput.
- PVC provisioning time.
- CSI clone/snapshot restore time.
- Database WAL replay time.
- Image pulls after namespace rebuild.
- Secret/config dependency ordering.

## 17. Practical tuning levers

### 17.1 Application-level tuning

Often the biggest improvement comes from application behavior.

Examples:

- Batch small writes.
- Reduce unnecessary fsyncs.
- Tune database checkpoint intervals.
- Increase database cache/buffer pool.
- Avoid writing temporary files to persistent storage.
- Move caches to `emptyDir` if data is rebuildable.
- Compress large files before writing to network storage if CPU allows.
- Avoid millions of tiny files on shared filesystems.

### 17.2 Kubernetes/OpenShift-level tuning

- Use correct StorageClass.
- Use StatefulSet with one PVC per replica for databases.
- Avoid sharing one RWX volume for write-heavy replicas unless app supports it.
- Use topology-aware binding.
- Use node/pod affinity for local storage workloads.
- Set proper CPU/memory requests to avoid throttling.
- Use `fsGroupChangePolicy` where appropriate.
- Use PVC expansion before filesystem becomes critically full.
- Separate critical workloads by namespace, node pool, or storage tier.
- Use PodDisruptionBudgets for stateful apps.

### 17.3 Node-level tuning

Be careful: OpenShift nodes are managed. Use supported methods such as MachineConfig, PerformanceProfile, or documented vendor procedures.

Areas that can matter:

- NIC speed and errors.
- Storage network MTU.
- Multipath configuration.
- Kernel/device queue settings.
- CPU isolation for performance-sensitive workloads.
- RHCOS disk layout.
- Container runtime disk pressure.

Do not manually change node settings in an unsupported way and expect them to survive reboot or MachineConfig reconciliation.

### 17.4 Backend tuning

Backend-specific examples:

- Add SSD/NVMe capacity.
- Separate pools for DB vs archive workloads.
- Tune Ceph recovery/backfill limits carefully.
- Add OSDs or rebalance.
- Use correct cloud disk type.
- Increase provisioned IOPS/throughput.
- Check storage controller cache and battery/health.
- Use QoS policies.
- Separate backup repository from production data path.

## 19. Scenario-based learning

### Scenario 1: Database became slow after migration to RWX

Situation:

- PostgreSQL moved from RWO block to RWX file storage.
- Pod is running.
- Queries are slow.
- `fio` sequential throughput looks acceptable.

Likely issue:

- Database is latency-sensitive and metadata/sync-write-sensitive.
- RWX file storage adds network, locking, and metadata overhead.

Action:

```bash
oc get pvc -n db
oc describe pvc postgres-data -n db
oc get pv <pv> -o yaml
```

Fix:

- Move primary database data to RWO block storage.
- Use database-native replication for HA.
- Use RWX only for shared non-database files.

### Scenario 2: Backup slows production every night

Situation:

- App slow from 01:00 to 02:00.
- Backup job starts at 01:00.
- Storage backend latency increases.

Likely issue:

- Backup reads PVCs heavily and writes to object repository.
- Backend is saturated or network is saturated.

Action:

```bash
oc get pods -A | egrep -i 'backup|velero|oadp|restic|kopia'
oc get volumesnapshot -A
```

Fix:

- Stagger schedules.
- Reduce concurrency.
- Move backup repository traffic to appropriate network/object backend.
- Use snapshots plus offload instead of direct file scan where supported.
- Exclude caches/temp data.

### Scenario 3: PVC Pending with local storage

Situation:

- PVC uses local PV StorageClass.
- PVC is Pending.
- Admin thinks storage failed.

Likely issue:

- `volumeBindingMode: WaitForFirstConsumer` waits for a pod before binding.

Action:

```bash
oc describe pvc <pvc> -n <ns>
oc get sc <sc> -o yaml | grep volumeBindingMode
oc get pod -n <ns> -o wide
```

Fix:

- Create consuming pod.
- Check pod scheduling constraints.
- Check node labels and local PV availability.

### Scenario 4: Pod startup takes 20 minutes after mounting PVC

Situation:

- Pod stuck in `ContainerCreating`.
- PVC is bound.
- Large number of files in volume.
- Security context uses `fsGroup`.

Likely issue:

- Recursive ownership/permission change during mount.

Action:

```bash
oc describe pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o yaml | grep -A30 securityContext
journalctl -u kubelet --since "30 minutes ago"
```

Fix:

- Use `fsGroupChangePolicy: OnRootMismatch` where supported.
- Reduce files under mounted path.
- Pre-set ownership.
- Review SCC/security context design.

### Scenario 5: ODF latency spike after node failure

Situation:

- ODF/Ceph backend reports recovery.
- Applications slow after storage node failure.
- PVCs still mounted.

Likely issue:

- Recovery/backfill competes with client I/O.

Action:

```bash
oc -n openshift-storage get pods
oc -n openshift-storage get cephcluster
# In toolbox if available:
ceph -s
ceph health detail
ceph osd df
```

Fix:

- Allow recovery but monitor impact.
- Avoid starting heavy backups during recovery.
- Add capacity or repair failed OSD/node.
- Tune recovery only according to vendor guidance.

## 20. Golden rules for storage performance in OpenShift

1. `PVC Bound` means storage is allocated, not that it is fast.
2. Capacity, IOPS, throughput, and latency are different dimensions.
3. Use RWO block for most latency-sensitive single-writer workloads.
4. Use RWX file storage only when the application really requires shared writes.
5. Use object storage for backup/archive/registry-style scalable object workloads where supported.
6. Do not place every workload on the default StorageClass.
7. Benchmark with workload-like patterns, not only large sequential writes.
8. Measure tail latency, not only average latency.
9. Backups and snapshots can impact production storage.
10. Same-backend snapshot is not the same as off-cluster backup.
11. Expansion fixes capacity pressure; it does not automatically fix latency.
12. Storage issues can be caused by CPU throttling, memory pressure, network, CSI, or application behavior.
13. Document each StorageClass as a platform contract.
14. Test restore, not only backup.
15. Keep storage, application, platform, and backup owners aligned.

## 24. Quick interview/exam-style points

- StorageClass is cluster-scoped; PVC is namespace-scoped.
- Dynamic provisioning uses StorageClass and a provisioner/CSI driver to create PVs on demand.
- `WaitForFirstConsumer` delays binding until a pod needs the PVC, which helps topology-aware provisioning.
- RWO is usually best for single-writer block workloads.
- RWX requires shared-capable storage and may have higher latency.
- Object storage is not a normal mounted filesystem; apps use APIs or object bucket claims/integration.
- CSI snapshots require a CSI driver that supports snapshots and a VolumeSnapshotClass.
- Snapshots are point-in-time volume states; backup strategy must consider failure domain.
- PVC expansion requires StorageClass expansion support and backend support; shrinking is not supported.
- `kubelet_volume_stats_*` helps capacity/inode monitoring, not complete performance diagnosis.
- Use backend metrics for real IOPS/latency/throughput.
- Slow storage symptoms can be caused by CPU throttling, memory pressure, network, CSI, or app design.

## 26. Final admin mindset

Storage performance in OpenShift is a full-stack topic. A good administrator understands PV/PVC/StorageClass syntax, but a senior administrator understands workload behavior, backend limits, CSI operations, node-level symptoms, metrics, backup impact, restore time, and failure domains.

When troubleshooting, use this order:

```text
Workload pattern -> PVC/SC/backend mapping -> pod/node health -> CSI events/logs -> backend metrics -> backup/snapshot activity -> controlled benchmark -> corrective action
```

The best production storage design is not the fastest storage everywhere. It is the right storage tier for each workload, with documented performance expectations, backup guarantees, restore tests, monitoring, and ownership.
