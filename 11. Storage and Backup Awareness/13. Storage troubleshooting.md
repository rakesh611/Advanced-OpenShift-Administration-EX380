# Storage Troubleshooting in OpenShift: Advanced Administration Runbook

**Area:** Storage and Backup Awareness  
**Audience:** Advanced OpenShift Administrators, SREs, Platform Engineers  
**Experience level:** Written for an administrator with around 10 years of Linux, virtualization, networking, Kubernetes, and OpenShift exposure  
**Focus:** Practical troubleshooting of PV, PVC, StorageClass, CSI, VolumeAttachment, local storage, NFS, iSCSI, cloud storage, OpenShift Data Foundation, snapshots, expansion, backup readiness, and node-level storage issues.

---

## 1. What “storage troubleshooting” means in OpenShift

Storage troubleshooting in OpenShift is the process of identifying why an application cannot provision, attach, mount, read, write, resize, snapshot, restore, or release storage safely.

In a real production cluster, storage issues rarely belong to one layer only. A single symptom such as a pod stuck in `ContainerCreating` can involve:

- A PVC stuck in `Pending`.
- A StorageClass pointing to the wrong CSI provisioner.
- A CSI controller that cannot talk to the backend array or cloud API.
- A CSI node plugin missing from a worker node.
- A `VolumeAttachment` stuck after a node crash.
- Access mode mismatch such as trying to mount an RWO block volume from two nodes.
- Backend storage exhaustion.
- Network/firewall issues between node and storage server.
- Incorrect NFS export permissions.
- iSCSI session or multipath failure.
- ODF/Ceph health problem.
- SELinux, filesystem, inode, or node disk-pressure issue.
- Backup/snapshot expectation mismatch.

A senior OpenShift administrator does not start by deleting objects randomly. The correct approach is to walk the storage path from application to backend and prove where the chain breaks.

## 2. OpenShift storage mental model

Before troubleshooting, understand the request path.

```text
Application Pod
   |
   | references volumeMount + volume
   v
PersistentVolumeClaim (PVC) - namespaced request
   |
   | binds to
   v
PersistentVolume (PV) - cluster-scoped storage object
   |
   | created manually or dynamically through
   v
StorageClass
   |
   | provisioner field points to
   v
CSI Controller / external-provisioner / external-attacher / resizer / snapshotter
   |
   | creates/attaches storage on
   v
Storage backend: ODF/Ceph, vSphere, AWS EBS, Azure Disk/File, NFS, iSCSI, FC, local disk, etc.
   |
   | mounted on the worker node by
   v
CSI Node Plugin + kubelet + OS mount stack
   |
   v
Container filesystem path
```

### Key objects

| Object | Scope | Purpose | Common troubleshooting use |
|---|---:|---|---|
| `StorageClass` | Cluster | Defines provisioner, reclaim policy, binding mode, expansion, backend parameters | Check default class, provisioner name, topology, expansion support |
| `PVC` | Namespace | User/application request for storage | Check `Pending`, `Bound`, resize conditions, events |
| `PV` | Cluster | Actual volume resource | Check claimRef, reclaim policy, node affinity, backend handle |
| `Pod` | Namespace | Mounts the PVC | Check scheduling, attach, mount, permission, fsGroup events |
| `VolumeAttachment` | Cluster | Attach/detach intent for CSI volumes | Check stuck attach/detach, stale attachment after node failure |
| `CSIDriver` | Cluster | CSI driver capabilities | Check driver registration and behavior |
| `CSINode` | Cluster | CSI drivers installed on each node | Check whether node plugin is registered on affected node |
| `VolumeSnapshotClass` | Cluster | Snapshot driver policy | Check snapshot driver and deletion policy |
| `VolumeSnapshot` | Namespace | User request for snapshot | Check readiness and snapshot content binding |
| `VolumeSnapshotContent` | Cluster | Actual backend snapshot object | Check snapshot handle and deletion behavior |

## 3. Golden rule: classify the failure before fixing

When storage breaks, first classify the issue into one of these categories:

1. **Provisioning failure**: PVC remains `Pending`; no PV created or no suitable PV exists.
2. **Binding failure**: PV exists but does not bind to PVC.
3. **Scheduling/topology failure**: pod cannot be scheduled to a node where the volume can exist or attach.
4. **Attach failure**: volume cannot attach to the selected node.
5. **Mount failure**: volume attaches but kubelet/CSI cannot mount it into the pod.
6. **Permission failure**: application sees `Permission denied`, read-only filesystem, wrong ownership, SELinux issue.
7. **Runtime I/O failure**: application starts but read/write is slow, hangs, or fails.
8. **Resize failure**: PVC expansion stuck or filesystem not resized.
9. **Snapshot/restore failure**: snapshot not ready, restore PVC stuck, app consistency not achieved.
10. **Cleanup failure**: PVC/PV/pod stuck terminating due to finalizer, stale attachment, or backend deletion problem.
11. **Backend failure**: ODF/Ceph, NFS, iSCSI, cloud storage, SAN, or vSphere backend issue.
12. **Node-level failure**: kubelet, CRI-O, mount table, device paths, multipath, disk pressure, or kernel logs show issue.

This classification prevents blind troubleshooting.

## 5. Storage troubleshooting decision tree

### 5.1 PVC is `Pending`

Start here:

```bash
oc describe pvc -n <ns> <pvc>
oc get sc
oc describe sc <sc>
oc get events -n <ns> --sort-by=.lastTimestamp
```

Common event messages and meaning:

| Event/message | Likely cause | What to check |
|---|---|---|
| `no persistent volumes available for this claim` | Static provisioning mismatch | PV capacity, accessModes, storageClassName, volumeMode, selector |
| `storageclass.storage.k8s.io "x" not found` | PVC references missing StorageClass | PVC `spec.storageClassName`; `oc get sc` |
| `waiting for first consumer to be created before binding` | `WaitForFirstConsumer` binding mode | Create pod; check pod scheduling constraints |
| `failed to provision volume with StorageClass` | CSI provisioner/backend failure | CSI controller logs, backend quota/credentials/network |
| `exceeded quota` | Namespace ResourceQuota blocks PVC count/storage | `oc describe quota -n <ns>` |
| `access mode not supported` | Requested access mode unsupported by backend | RWO/RWX/ROX vs storage provider capabilities |
| `volume mode not supported` | Filesystem/Block mismatch | PVC `volumeMode`; StorageClass/backend support |
| `insufficient storage` | Backend capacity exhausted | Backend pool/cloud quota/ODF health |

#### PVC pending command pack

```bash
NS=<namespace>
PVC=<pvc-name>

oc get pvc -n $NS $PVC -o yaml
oc describe pvc -n $NS $PVC
oc get events -n $NS --field-selector involvedObject.name=$PVC --sort-by=.lastTimestamp

SC=$(oc get pvc -n $NS $PVC -o jsonpath='{.spec.storageClassName}')
echo "StorageClass=$SC"
oc describe sc $SC

oc get quota -n $NS
oc describe quota -n $NS
oc get limitrange -n $NS
```

#### Static PV binding checks

For static PVs, PVC and PV must match on:

- `storageClassName`
- `accessModes`
- capacity request less than or equal to PV capacity
- `volumeMode` (`Filesystem` or `Block`)
- selector labels, if PVC uses `spec.selector`
- PV not already bound through `claimRef`

```bash
oc get pv -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,SC:.spec.storageClassName,CAP:.spec.capacity.storage,ACCESS:.spec.accessModes,VOLMODE:.spec.volumeMode,CLAIM:.spec.claimRef.name
```

A PV with an old `claimRef` may not bind to a new PVC even if it looks available. Do not patch `claimRef` unless you know the data ownership and reclaim workflow.

### 5.2 Pod stuck in `Pending`

A storage issue can appear as a scheduler issue.

```bash
oc describe pod -n <ns> <pod>
oc get pvc -n <ns>
oc get pv <pv> -o yaml | egrep -A20 'nodeAffinity|claimRef|storageClassName'
oc describe node <node>
```

Common causes:

- PVC is still `Pending`.
- StorageClass uses `WaitForFirstConsumer`, but pod has impossible node selectors, affinity, taints, or resource requests.
- Local PV has `nodeAffinity` to a node where the pod cannot run.
- StatefulSet uses a PVC template but storage backend cannot provision more volumes.
- Namespace quota blocks generated PVCs, especially with StatefulSets or generic ephemeral volumes.

For local storage:

```bash
oc get pv -o wide | grep local
oc get pv <local-pv> -o yaml | yq '.spec.nodeAffinity'
oc get pod -n <ns> <pod> -o yaml | yq '.spec.nodeSelector,.spec.affinity,.spec.tolerations'
```

Production rule: never “fix” local PV scheduling by removing PV node affinity. The data exists on a specific node.

### 5.3 Pod stuck in `ContainerCreating`

This is the classic attach/mount failure state.

```bash
oc describe pod -n <ns> <pod>
oc get pvc -n <ns>
oc get pv
oc get volumeattachment | grep <pv-or-volume-handle>
oc get events -n <ns> --sort-by=.lastTimestamp | tail -50
```

Look for events like:

- `FailedAttachVolume`
- `FailedMount`
- `Multi-Attach error`
- `MountVolume.MountDevice failed`
- `Unable to attach or mount volumes`
- `timed out waiting for the condition`
- `rpc error: code = Internal desc = ...`
- `permission denied`
- `read-only file system`
- `stale file handle`
- `context deadline exceeded`

#### Attach vs mount

| Failure stage | Where to look | Typical responsible layer |
|---|---|---|
| Attach | `VolumeAttachment`, CSI controller logs, cloud/SAN backend | CSI external-attacher + backend |
| Mount device | kubelet logs, CSI node plugin logs, OS device/multipath | CSI node plugin + node OS |
| Bind mount into pod | kubelet logs, SCC/fsGroup/SELinux, mount options | kubelet + container runtime + security context |

#### VolumeAttachment checks

```bash
oc get volumeattachment
oc get volumeattachment <name> -o yaml
oc describe volumeattachment <name>
```

Check:

- `.spec.nodeName`
- `.spec.source.persistentVolumeName`
- `.status.attached`
- `.status.attachError.message`
- `.status.detachError.message`

If a node died ungracefully, a stale `VolumeAttachment` can block reattach. Do not delete `VolumeAttachment` as a first action. Confirm node status, workload ownership, backend attachment state, and whether the CSI driver supports force-detach or non-graceful shutdown handling.

---

### 5.4 Multi-Attach error

Typical message:

```text
Multi-Attach error for volume "pvc-..." Volume is already exclusively attached to one node and can't be attached to another
```

Most common causes:

- RWO PVC used by pods scheduled on different nodes.
- Rolling update creates new pod on a different node while old pod is terminating slowly.
- Node crashed and backend still thinks volume is attached to old node.
- Stateful workload is scaled incorrectly with one RWO claim.
- Application needs RWX but is using RWO storage.

#### Diagnose

```bash
PVC=<pvc>
NS=<ns>
PV=$(oc get pvc -n $NS $PVC -o jsonpath='{.spec.volumeName}')

echo $PV
oc get pod -A -o wide | grep $PVC
oc get volumeattachment -o yaml | grep -B5 -A15 $PV
oc describe pv $PV
```

#### Fix options

| Situation | Correct fix |
|---|---|
| Deployment replicas share one RWO PVC | Use RWX storage or one PVC per replica |
| StatefulSet replica uses wrong shared claim | Use `volumeClaimTemplates` |
| Old pod stuck terminating | Drain/check node; allow clean detach; force only after confirming data safety |
| Node down permanently | Follow non-graceful node shutdown/storage vendor force-detach process |
| App really needs shared write | Use RWX backend such as CephFS, NFS, EFS, Azure File, or another supported file storage |

Bad fix: changing the PVC from RWO to RWX in YAML. PVC access mode is not simply a permission flag; the backend must support that access pattern.

## 6. StorageClass troubleshooting

`StorageClass` is often the root cause of provisioning issues.

```bash
oc get sc
oc describe sc <name>
oc get sc -o yaml
```

Important fields:

```yaml
provisioner: csi.example.com
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
parameters:
  type: gp3
mountOptions:
  - discard
allowedTopologies: []
```

### 6.1 Default StorageClass issues

Check default annotation:

```bash
oc get sc -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.annotations.storageclass\.kubernetes\.io/is-default-class}{"\n"}{end}'
```

A PVC with no `storageClassName` uses the default StorageClass. Problems happen when:

- No default StorageClass exists.
- More than one default exists.
- Default points to a backend not available on the platform.
- Developers expected static binding but dynamic default provisioning happened.

To mark a class default:

```bash
oc annotate storageclass <sc-name> storageclass.kubernetes.io/is-default-class=true --overwrite
```

To remove default:

```bash
oc annotate storageclass <sc-name> storageclass.kubernetes.io/is-default-class- --overwrite
```

### 6.2 `Immediate` vs `WaitForFirstConsumer`

| Binding mode | Behavior | Troubleshooting angle |
|---|---|---|
| `Immediate` | PV is provisioned as soon as PVC is created | Can create volume in wrong zone/topology before pod scheduling |
| `WaitForFirstConsumer` | Provision/bind waits until pod scheduling decision | PVC pending may be normal until pod exists |

For topology-aware storage, `WaitForFirstConsumer` is usually safer because scheduler considers pod constraints and storage topology together.

### 6.3 Reclaim policy confusion

| Policy | Behavior after PVC deletion | Production risk |
|---|---|---|
| `Delete` | Backend volume normally deleted | Accidental PVC delete can destroy data |
| `Retain` | PV/data retained; manual cleanup required | PV stuck `Released`, manual recovery required |

Check:

```bash
oc get pv -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,RECLAIM:.spec.persistentVolumeReclaimPolicy,CLAIM:.spec.claimRef.name,SC:.spec.storageClassName
```

For critical databases, decide reclaim policy intentionally. Many teams use `Retain` for manually protected data and `Delete` for ephemeral or reproducible workloads.

## 7. PVC/PV lifecycle troubleshooting

### 7.1 PVC phases

| PVC phase | Meaning | Action |
|---|---|---|
| `Pending` | Not bound to PV | Check StorageClass/provisioner/static PV matching/events |
| `Bound` | Bound to PV | Check pod attach/mount if app still failing |
| `Lost` | Bound PV missing | Investigate PV deletion/backend state immediately |

### 7.2 PV phases

| PV phase | Meaning | Action |
|---|---|---|
| `Available` | Free PV | Can bind to matching PVC |
| `Bound` | Bound to PVC | Normal if claim is active |
| `Released` | PVC deleted, data may remain | Follow reclaim process; do not blindly reuse |
| `Failed` | Automatic reclamation failed | Inspect events/backend/finalizers |

### 7.3 Released PV recovery with Retain policy

When a PVC using a `Retain` PV is deleted, the PV becomes `Released` but still has a `claimRef`.

Safe recovery pattern:

1. Confirm the data owner and application.
2. Confirm backend volume still exists.
3. Ensure no pod is using it.
4. Back up data if possible.
5. Create a new PV pointing to the same backend handle or carefully clear claimRef only if you know the original workflow.

Example inspection:

```bash
oc get pv <pv> -o yaml
oc describe pv <pv>
```

Patching claimRef is risky:

```bash
# Only after validation and change approval
oc patch pv <pv> --type=json -p='[{"op":"remove","path":"/spec/claimRef"}]'
```

Do not use this during an exam or production incident unless the scenario explicitly requires it and you understand data ownership.

## 8. CSI troubleshooting deep dive

CSI is the standard storage interface used by modern OpenShift storage providers.

### 8.1 CSI components

Typical components:

| Component | Runs as | Function |
|---|---|---|
| CSI controller plugin | Deployment/StatefulSet | Provision, delete, attach, detach, snapshot, resize |
| CSI node plugin | DaemonSet | Mount/unmount volumes on each worker node |
| external-provisioner | Sidecar | Watches PVC and creates volumes |
| external-attacher | Sidecar | Manages `VolumeAttachment` operations |
| external-resizer | Sidecar | Handles volume expansion |
| external-snapshotter | Sidecar/controller | Handles snapshots |
| livenessprobe | Sidecar | Health checks CSI plugin |

### 8.2 Find CSI pods

```bash
oc get pods -A | egrep -i 'csi|driver|provisioner|attacher|snapshot|resizer'
oc get ds -A | egrep -i 'csi|driver'
oc get deploy -A | egrep -i 'csi|driver|provisioner|attacher|snapshot|resizer'
```

Common namespaces:

- `openshift-cluster-csi-drivers`
- `openshift-storage`
- storage-vendor namespaces
- `kube-system` in some non-OpenShift Kubernetes distributions

### 8.3 Check CSI driver registration

```bash
oc get csidriver
oc describe csidriver <driver-name>
oc get csinode <node-name> -o yaml
```

If a pod on node `worker-2` cannot mount a volume, check whether the CSI node driver is registered on `worker-2`:

```bash
oc get csinode worker-2 -o yaml | grep -A20 drivers
```

If the driver is missing on one node:

```bash
oc get ds -A | grep csi
oc describe ds -n <csi-namespace> <csi-node-daemonset>
oc get pod -n <csi-namespace> -o wide | grep worker-2
oc logs -n <csi-namespace> <csi-node-pod> --all-containers --tail=200
```

### 8.4 CSI controller logs

For provisioning/attach/delete/resize/snapshot issues:

```bash
oc logs -n <csi-ns> deploy/<csi-controller-deployment> --all-containers --tail=300
```

If there are multiple replicas:

```bash
for p in $(oc get pod -n <csi-ns> -l app=<label> -o name); do
  echo "### $p"
  oc logs -n <csi-ns> $p --all-containers --tail=100
 done
```

Look for:

- backend API authentication failure
- cloud quota exceeded
- pool full
- invalid parameter in StorageClass
- topology/zone mismatch
- volume already exists
- volume not found
- timeout / context deadline exceeded
- permission denied
- failed to delete volume
- failed to expand volume

### 8.5 CSI node plugin logs

For mount/unmount/device issues:

```bash
oc get pod -n <csi-ns> -o wide | grep <node-name>
oc logs -n <csi-ns> <csi-node-pod> --all-containers --tail=300
```

Look for:

- device path not found
- filesystem type unsupported
- mount option invalid
- `permission denied`
- `stale file handle`
- `transport endpoint is not connected`
- iSCSI login failed
- multipath device not ready
- read-only mount
- SELinux relabel timeout or error
- mount timeout

## 9. Node-level storage troubleshooting

When Kubernetes events are not enough, debug the node.

### 9.1 Enter node debug shell

```bash
oc debug node/<node-name>
chroot /host
```

From inside `chroot /host`:

```bash
hostname
uptime
df -h
df -ih
lsblk -f
findmnt
mount | egrep -i 'kubelet|pvc|nfs|iscsi|ceph|rbd|csi'
dmesg -T | tail -100
journalctl -u kubelet --no-pager -n 300
journalctl -u crio --no-pager -n 200
```

### 9.2 Kubelet storage paths

On OpenShift nodes, kubelet stores pod volume data under paths similar to:

```text
/var/lib/kubelet/pods/<pod-uid>/volumes/
/var/lib/kubelet/plugins/
/var/lib/kubelet/plugins_registry/
/var/lib/kubelet/plugins/kubernetes.io/csi/
```

Useful commands:

```bash
findmnt | grep kubelet
ls -l /var/lib/kubelet/plugins_registry/
ls -l /var/lib/kubelet/plugins/
```

Be careful. Do not delete kubelet plugin or pod volume directories manually unless directed by vendor support or a documented recovery procedure.

### 9.3 Node disk pressure vs application storage issue

Node disk pressure affects scheduling and pod startup even if PV backend is fine.

```bash
oc describe node <node-name> | egrep -A5 'Conditions|DiskPressure|MemoryPressure|PIDPressure'
oc adm top node <node-name>
```

On node:

```bash
df -h
df -ih
du -xh /var/lib/containers 2>/dev/null | sort -h | tail -20
du -xh /var/log 2>/dev/null | sort -h | tail -20
journalctl --disk-usage
```

Common causes:

- container logs filling `/var/log`
- image layers filling `/var/lib/containers`
- application writing to ephemeral filesystem instead of mounted PVC
- too many small files consuming inodes
- runaway emptyDir usage

### 9.4 Filesystem and inode issue inside pod

```bash
oc rsh -n <ns> <pod>
df -h
df -ih
mount
id
ls -ld <mount-path>
touch <mount-path>/testfile
```

If app fails but `touch` works, issue is likely application-level path, user, permission, or database lock. If `touch` fails, check storage permissions, read-only mount, quota, or backend state.

## 10. Permission, ownership, SELinux, and SCC issues

Storage can mount successfully but still be unusable by the application.

### 10.1 Symptoms

- Application logs: `Permission denied`
- Database init container fails
- Pod runs as random UID and cannot write
- NFS export root squashing prevents chown
- Volume is mounted read-only
- SELinux denies hostPath/local path access
- `fsGroup` relabel takes too long on large volumes

### 10.2 Diagnose from pod

```bash
oc rsh -n <ns> <pod>
id
whoami
mount | grep <mount-path>
ls -ld <mount-path>
ls -ln <mount-path>
touch <mount-path>/write-test
```

Check pod security context:

```bash
oc get pod -n <ns> <pod> -o yaml | yq '.spec.securityContext,.spec.containers[].securityContext'
```

Check SCC admission:

```bash
oc adm policy who-can use scc anyuid
oc adm policy who-can use scc privileged
oc get pod -n <ns> <pod> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

### 10.3 Fix patterns

| Problem | Preferred fix |
|---|---|
| App needs writable directory | Set correct image permissions; use init container if allowed |
| App hardcodes UID 0 | Prefer image fix; if unavoidable, bind suitable SCC to service account |
| NFS root squash blocks chown | Pre-create export directory with correct UID/GID; avoid relying on root chown |
| fsGroup slow on huge file count | Use driver support, `fsGroupChangePolicy`, or pre-set ownership |
| hostPath/local SELinux issue | Use supported storage; avoid hostPath for normal apps |

Example anyuid binding, only when justified:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

Do not grant `privileged` or `anyuid` casually. Storage failures are often fixed better by correcting volume ownership or image design.

## 11. NFS troubleshooting

NFS is common in labs and enterprise OpenShift environments for RWX workloads, but it introduces network, export, UID/GID, and locking issues.

### 11.1 Typical NFS symptoms

- PVC bound but pod mount fails.
- `permission denied` on mount.
- `stale file handle`.
- Pod hangs during I/O.
- Application cannot write due to UID/GID mismatch.
- `root_squash` prevents root from changing ownership.
- NFS server firewall blocks nodes.
- Export allows master but not worker subnets.

### 11.2 Server-side checks

On NFS server:

```bash
exportfs -v
showmount -e localhost
systemctl status nfs-server
ss -tulpn | egrep '2049|111|mountd|nlockmgr'
firewall-cmd --list-all
```

Check export path:

```bash
ls -ld /exports/app1
ls -ln /exports/app1
getfacl /exports/app1
```

Example export:

```text
/exports/app1 10.0.0.0/24(rw,sync,no_subtree_check,no_root_squash)
```

Production note: `no_root_squash` can be risky. Prefer correct UID/GID ownership and a security-reviewed export policy.

### 11.3 Node-side NFS checks

From debug node:

```bash
oc debug node/<worker>
chroot /host

showmount -e <nfs-server>
mount -t nfs <nfs-server>:/exports/app1 /mnt
mount | grep nfs
touch /mnt/test
umount /mnt
```

If `showmount` or manual mount fails from node, the issue is not OpenShift PVC logic. Fix network, DNS, firewall, export, or NFS server.

### 11.4 PVC/PV NFS example

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-app-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 10.0.0.10
    path: /exports/app1
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nfs-app-pvc
  namespace: app
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 10Gi
  volumeName: nfs-app-pv
```

Troubleshooting checks:

```bash
oc describe pv nfs-app-pv
oc describe pvc -n app nfs-app-pvc
oc describe pod -n app <pod>
```

## 12. iSCSI troubleshooting

iSCSI failures are usually at the node-to-target layer.

### 12.1 Common symptoms

- PVC/PV exists but pod mount fails.
- iSCSI login timeout.
- LUN not found.
- CHAP authentication failure.
- Multipath device not ready.
- Device appears on one node but not another.
- Firewall blocks TCP 3260.

### 12.2 Node checks

```bash
oc debug node/<worker>
chroot /host

rpm -q iscsi-initiator-utils
cat /etc/iscsi/initiatorname.iscsi
systemctl status iscsid
iscsiadm -m discovery -t sendtargets -p <target-ip>
iscsiadm -m session
lsblk -f
multipath -ll 2>/dev/null
journalctl -u iscsid --no-pager -n 200
dmesg -T | egrep -i 'iscsi|scsi|multipath|blk|io error' | tail -100
```

### 12.3 Network checks

```bash
nc -vz <target-ip> 3260
# If nc is not available:
```

## 16. Local storage troubleshooting

Local storage uses disks attached to specific nodes. It is fast and simple but tied to node availability.

### 16.1 Key facts

- Local PVs are node-local.
- Workloads are bound to nodes that hold the storage.
- Local volumes are not suitable for every HA workload unless the application or storage layer handles replication.
- Local PVs commonly use PV `nodeAffinity`.
- Local storage is not the same as RWX shared storage.

### 16.2 Checks

```bash

oc get localvolumeset -A
oc get pv | grep local
oc get sc | grep local
```

```bash

```

Node debug:

```bash
oc debug node/<node>
chroot /host
lsblk -f
blkid
findmnt
ls -l /dev/disk/by-id/
```

### 16.3 Common local storage failures

| Symptom | Cause | Fix |
|---|---|---|
| No local PV created | Disk mounted/partitioned/not discovered | Provide clean unmounted disk; check LocalVolume/LocalVolumeSet |
| Pod cannot schedule | PV nodeAffinity conflicts with pod constraints | Adjust pod scheduling, not PV nodeAffinity |
| Device missing after reboot | Non-persistent device path | Use `/dev/disk/by-id` and stable serials |
| Data unavailable after node failure | Local disk tied to failed node | Recover node/disk or restore from backup/replica |
| Duplicate PVs for same disk | Reused storage class/device config | Clean up safely; avoid multiple SC names for same device |

## 17. Volume expansion troubleshooting

### 17.1 Requirements

To expand a PVC:

- StorageClass must have `allowVolumeExpansion: true`.
- CSI driver/backend must support resize.
- PVC must request a larger size than current size.
- Shrinking is not supported.
- Filesystem expansion may require pod restart depending on driver/filesystem.

Check:

```bash
oc describe sc <sc>
oc get pvc -n <ns> <pvc> -o yaml
oc describe pvc -n <ns> <pvc>
```

Patch PVC:

```bash
oc patch pvc <pvc> -n <ns> -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

Watch:

```bash
oc get pvc -n <ns> <pvc> -w
oc describe pvc -n <ns> <pvc>
```

Inside pod:

```bash
oc rsh -n <ns> <pod> df -h <mount-path>
```

### 17.2 Common expansion failures

| Symptom | Cause | Fix |
|---|---|---|
| PVC edit rejected | StorageClass expansion disabled | Enable expansion or create new PVC/migrate data |
| PVC stuck `Resizing` | Backend resize slow/failed | Check CSI resizer logs/backend quota |
| Filesystem size unchanged | Node filesystem resize pending | Restart pod if required; check kubelet/CSI node logs |
| User tried smaller size | Shrink unsupported | Create new smaller PVC and copy data |

## 18. VolumeSnapshot troubleshooting

Snapshots are important for backup awareness but are not automatically application-consistent.

### 18.1 Snapshot objects

```bash
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

A snapshot path:

```text
PVC -> VolumeSnapshot -> VolumeSnapshotContent -> backend snapshot
```

### 18.2 Check snapshot readiness

```bash
oc describe volumesnapshot -n <ns> <snapshot>
oc get volumesnapshot -n <ns> <snapshot> -o yaml
oc get volumesnapshotcontent <content-name> -o yaml
```

Important fields:

- `status.readyToUse`
- `status.error`
- `status.boundVolumeSnapshotContentName`
- `spec.volumeSnapshotClassName`
- `spec.source.persistentVolumeClaimName`

### 18.3 Common snapshot failures

| Symptom | Cause | Check/fix |
|---|---|---|
| No VolumeSnapshotClass | CSI snapshot support missing | Install/configure supported CSI snapshot driver/class |
| Snapshot not ready | Backend snapshot failed | Snapshot controller/CSI logs/backend capacity |
| Restore PVC pending | Restore SC/access mode unsupported | PVC events, StorageClass, backend support |
| App data inconsistent | Snapshot taken while app writing | Quiesce app, DB backup hooks, fsfreeze/operator integration |
| Snapshot deleted backend data unexpectedly | DeletionPolicy set to Delete | Review VolumeSnapshotClass deletionPolicy |

### 18.4 Example snapshot

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: app-snap-001
  namespace: app
spec:
  volumeSnapshotClassName: <snapshot-class>
  source:
    persistentVolumeClaimName: app-pvc
```

Restore to new PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-restore-pvc
  namespace: app
spec:
  storageClassName: <storage-class>
  dataSource:
    name: app-snap-001
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

Never restore over the same live database path without an application-aware recovery plan.

## 19. Backup and restore troubleshooting awareness

Storage backup is not only “take snapshot.” For OpenShift workloads, you normally need both:

1. **Kubernetes object backup**: Deployments, StatefulSets, Services, Routes, ConfigMaps, Secrets, PVC definitions, CRs.
2. **Persistent data backup**: PV snapshot, array snapshot, object copy, database dump, replication, or backup operator.

### 19.1 Crash-consistent vs application-consistent

| Type | Meaning | Risk |
|---|---|---|
| Crash-consistent | Snapshot captures disk as if machine crashed | Filesystem usually recoverable, database may need replay |
| Application-consistent | App/database is quiesced/flushed before snapshot | Safer for databases and stateful systems |

For databases, prefer operator-native backup or pre/post hooks:

- PostgreSQL: `pg_dump`, base backup, WAL archiving, operator backup.
- MySQL/MariaDB: logical dump, xtrabackup, flush/lock strategy.
- MongoDB: `mongodump`, filesystem snapshots with proper quiesce, replica-aware backup.
- Elasticsearch/OpenSearch: repository snapshot API.
- Kafka: replication plus topic-level backup strategy.

### 19.2 Restore validation checklist

A backup is not valid until restore is tested.

```bash
# Restore to new namespace
oc new-project restore-test

# Restore objects
# Restore PVC/snapshot/data

# Validate app
oc get pods,pvc,route,svc -n restore-test
oc logs -n restore-test deploy/<app>
oc rsh -n restore-test <pod> df -h
curl -k <route-url>
```

Validation questions:

- Did PVC bind to expected StorageClass?
- Did restored volume mount successfully?
- Is app data present?
- Are Secrets/ConfigMaps restored?
- Are Routes/Services correct?
- Is database internally consistent?
- Are credentials valid after restore?
- Is the restore isolated from production?

## 20. PVC/PV stuck terminating

### 20.1 Diagnose finalizers

```bash
oc get pvc -n <ns> <pvc> -o yaml | yq '.metadata.finalizers'
oc get pv <pv> -o yaml | yq '.metadata.finalizers'
oc describe pvc -n <ns> <pvc>
oc describe pv <pv>
```

Common finalizers:

- `kubernetes.io/pvc-protection`
- `kubernetes.io/pv-protection`
- CSI external-provisioner finalizer
- snapshot finalizers

A finalizer exists to prevent unsafe deletion. Do not remove finalizers until you know why cleanup is stuck.

### 20.2 Why PVC deletion hangs

- Pod still references PVC.
- CSI driver cannot delete backend volume.
- PV has reclaim policy `Retain`.
- Snapshot/content depends on volume.
- Backend API unavailable.
- Namespace terminating with objects blocked.

### 20.3 Safe cleanup pattern

```bash
NS=<ns>
PVC=<pvc>

oc get pods -n $NS -o yaml | grep -B5 -A5 $PVC
oc get pvc -n $NS $PVC -o yaml
PV=$(oc get pvc -n $NS $PVC -o jsonpath='{.spec.volumeName}')
oc get pv $PV -o yaml
oc get volumeattachment | grep $PV
```

Only after confirming no pod uses the PVC and backend state is safe, consider finalizer removal.

High-risk command:

```bash
# Dangerous: only after validation
oc patch pvc <pvc> -n <ns> --type=json -p='[{"op":"remove","path":"/metadata/finalizers"}]'
```

For production, capture must-gather before manual finalizer removal.

## 21. Performance troubleshooting

Storage may work but be too slow.

### 21.1 Symptoms

- Pod starts slowly when volume has many files.
- Database latency increases.
- Application I/O timeout.
- `fsGroup` relabel takes very long.
- ODF reports slow ops.
- NFS operations hang.
- Node load high with iowait.

### 21.2 Application-level checks

```bash
oc rsh -n <ns> <pod>
df -h
df -ih
time sh -c 'dd if=/dev/zero of=/mount/test bs=1M count=256 conv=fdatasync'
time sh -c 'dd if=/mount/test of=/dev/null bs=1M'
rm -f /mount/test
```

Use `dd` carefully; do not run destructive or heavy benchmarks on production storage during peak time.

### 21.3 Node-level checks

```bash
oc debug node/<node>
chroot /host

top
iostat -xz 1 5 2>/dev/null
vmstat 1 5
pidstat -d 1 5 2>/dev/null
dmesg -T | egrep -i 'blk|nvme|scsi|io error|reset|timeout' | tail -100
```

If tools are missing on RHCOS, use debug toolbox/ephemeral debug methods approved in your environment.

### 21.4 ODF/Ceph performance checks

```bash

ceph health detail
ceph osd perf
ceph osd df tree
ceph df
```

Performance issue patterns:

| Pattern | Meaning |
|---|---|
| high OSD utilization | uneven data distribution or small cluster |
| nearfull OSDs | backfill/recovery and writes affected |
| slow ops | backend/network/disk latency |
| degraded PGs | data recovery underway or blocked |
| network packet loss | Ceph replication latency increases |

## 22. Events and logs: how to read them like a senior admin

### 22.1 Event order matters

```bash
oc get events -n <ns> --sort-by=.lastTimestamp
```

Read from oldest relevant error to newest. A pod may show repeated `FailedMount`, but the first event often contains the real reason.

### 22.2 Common Kubernetes storage event messages

| Event | Meaning |
|---|---|
| `ProvisioningFailed` | CSI provisioner/backend failed to create volume |
| `ExternalProvisioning` | Waiting for CSI external provisioner |
| `WaitForFirstConsumer` | Waiting for pod scheduling before provisioning |
| `FailedScheduling` | Scheduler cannot place pod, possibly due to storage topology |
| `FailedAttachVolume` | Volume attach failed |
| `FailedMount` | Mount stage failed on node |
| `FileSystemResizePending` | PVC expanded but filesystem resize pending |
| `VolumeResizeFailed` | Backend or driver resize failed |

### 22.3 Log collection command set

```bash
# Namespace events
oc get events -n <ns> --sort-by=.lastTimestamp > events-<ns>.txt

# Pod description
oc describe pod -n <ns> <pod> > pod-<pod>.describe.txt
```

## 24. Common real-world incident scenarios

### Scenario 1: PVC pending after creating app

**Symptoms**

```bash
oc get pvc -n app
# app-data   Pending
```

**Diagnosis**

```bash
oc describe pvc -n app app-data
oc get sc
oc describe sc <sc>
```

**Likely findings**

- StorageClass missing.
- No default StorageClass.
- Provisioner pod down.
- Quota exceeded.
- `WaitForFirstConsumer` and no pod yet.

**Fix**

- Correct `storageClassName`.
- Create pod if `WaitForFirstConsumer`.
- Fix quota.
- Fix CSI provisioner/backend.

---

### Scenario 2: Pod stuck `ContainerCreating` with `FailedMount`

**Diagnosis**

```bash
oc describe pod -n app <pod>
oc get pvc -n app
oc get pv <pv> -o yaml
oc logs -n <csi-ns> <csi-node-pod> --all-containers --tail=300
journalctl -u kubelet --no-pager -n 300
```

**Likely causes**

- Node plugin missing.
- NFS permission denied.
- iSCSI session failure.
- Backend device not visible.
- SELinux/permission issue.
- Invalid mount option.

**Fix**

Depends on event message. Validate backend connectivity from the node before changing Kubernetes objects.

---

### Scenario 3: Multi-Attach during rollout

**Diagnosis**

```bash
oc get pods -n app -o wide
oc get pvc -n app
oc get volumeattachment | grep <pv>
oc describe pod -n app <new-pod>
```

**Fix**

- For Deployment with one RWO PVC: set strategy `Recreate`, or redesign with RWX/StatefulSet.
- For StatefulSet: ensure each replica uses its own PVC from `volumeClaimTemplates`.
- For node crash: follow force-detach/non-graceful shutdown procedure.

---

### Scenario 4: App says permission denied on mounted PVC

**Diagnosis**

```bash
oc rsh -n app <pod> id
oc rsh -n app <pod> ls -ld /data
oc get pod -n app <pod> -o yaml | yq '.spec.securityContext,.spec.containers[].securityContext'
oc logs -n app <pod>
```

**Fix**

- Correct UID/GID ownership on volume.
- Use image that supports arbitrary UID.
- Use `fsGroup` if appropriate.
- Pre-create NFS export with correct permissions.
- Use SCC only when required and approved.

---

### Scenario 5: PVC resize stuck

**Diagnosis**

```bash
oc describe pvc -n app data
oc describe sc <sc>
oc logs -n <csi-ns> deploy/<csi-controller> --all-containers --tail=300
```

**Fix**

- Enable `allowVolumeExpansion` if supported.
- Ensure backend capacity/quota.
- Restart pod if filesystem resize pending and driver requires it.
- Do not attempt shrink.

---

### Scenario 6: ODF PVC provisioning fails

**Diagnosis**

```bash
oc get pods -n openshift-storage
oc get cephcluster -n openshift-storage
oc get storagecluster -n openshift-storage
oc get events -n openshift-storage --sort-by=.lastTimestamp | tail -100
oc logs -n openshift-storage deploy/rook-ceph-operator --tail=300
oc logs -n openshift-storage deploy/rook-ceph-mgr-a --tail=300
```

Toolbox:

```bash
oc rsh -n openshift-storage deploy/rook-ceph-tools
ceph -s
ceph health detail
ceph df
```

**Fix**

Depends on health condition: restore OSD/MON/MDS health, free capacity, fix node/storage device, or collect ODF must-gather and escalate.

| Pod pending | Pod events | PVC/PV nodeAffinity | Scheduler constraints | Fix pod scheduling or storage class |
| ContainerCreating | Pod events | VolumeAttachment | CSI node/kubelet/backend | Fix attach/mount/backend connectivity |
| Multi-Attach | Pod placement | VolumeAttachment | Backend attachment | Use correct access mode/force-detach safely |
| Permission denied | Pod logs | SecurityContext/SCC | NFS/export/ownership/SELinux | Fix UID/GID/fsGroup/export/image |
| Slow startup | Pod events | PVC file count | kubelet logs/fsGroup | Optimize ownership/relabel/file count |
| Resize stuck | PVC conditions | StorageClass | CSI resizer/backend | Enable expansion/check quota/restart pod |
| Snapshot not ready | VolumeSnapshot | VolumeSnapshotContent | snapshotter/backend | Fix class/driver/backend/app quiesce |
| PVC terminating | PVC finalizers | PV/VolumeAttachment | CSI delete/backend | Remove users, fix backend, then cleanup |
| ODF health error | StorageCluster/CephCluster | ODF pods | Ceph toolbox/must-gather | Restore Ceph health/escalate |

---

## 28. Senior admin best practices

1. **Always read events first.** Events usually tell you whether the issue is provisioning, attach, mount, permission, or scheduling.
2. **Never delete storage objects blindly.** PV/PVC deletion can destroy data depending on reclaim policy and CSI behavior.
3. **Understand access modes.** RWO is not RWX. Changing YAML does not make block storage shareable.
4. **Use `WaitForFirstConsumer` intentionally.** It prevents topology mistakes but makes PVC pending look normal until a pod exists.
5. **Treat finalizers as safety mechanisms.** Remove them only after proving data state.
6. **For ODF, check Ceph health.** Kubernetes may show PVC symptoms while Ceph is the root cause.
7. **Validate from the node.** If NFS/iSCSI cannot mount from node, OpenShift cannot fix it.
8. **Separate backup from snapshot.** A snapshot without app quiesce may not be application-consistent.
9. **Record exact timestamps.** Storage backend teams need timestamp, node, volume handle, PVC, PV, and CSI logs.
10. **Test restore regularly.** Backup confidence comes from restore validation, not successful backup jobs.

## 30. Final quick checklist

When storage breaks, answer these questions in order:

```text
1. Is the pod Pending, ContainerCreating, Running with errors, or Terminating?
2. Is the PVC Pending, Bound, Lost, or Terminating?
3. Which PV is bound?
4. Which StorageClass and CSI provisioner are used?
5. Is binding Immediate or WaitForFirstConsumer?
6. Is the access mode correct for the workload?
7. Is there a VolumeAttachment? Is it attached? Any attachError?
8. Is the CSI controller healthy?
9. Is the CSI node plugin healthy on the selected node?
10. What does kubelet say on that node?
11. Can the node reach/mount/login to the backend storage?
12. Is backend storage healthy and not full?
13. Are permissions, SCC, fsGroup, SELinux, and UID/GID correct?
14. Are snapshots/backups application-consistent or only crash-consistent?
15. Is any cleanup blocked by finalizers, active pods, or backend deletion?
```

If you can answer these 15 questions, you can troubleshoot most OpenShift storage incidents like a senior platform administrator.
