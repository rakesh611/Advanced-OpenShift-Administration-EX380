# PVC Pending Issue in OpenShift

**Area:** Storage and Backup Awareness  
**Level:** Advanced OpenShift Administration  
**Audience:** OpenShift / Kubernetes administrators with production operations experience  
**Focus:** Deep diagnosis and recovery of `PersistentVolumeClaim` objects stuck in `Pending`

---

## 1. What This Guide Covers

A `PVC Pending` issue means a `PersistentVolumeClaim` has been created, but Kubernetes/OpenShift has not successfully bound it to a usable `PersistentVolume`.

In production OpenShift, this is not only a storage problem. It can involve:

- `PersistentVolumeClaim` specification
- `PersistentVolume` availability
- `StorageClass` configuration
- CSI driver health
- dynamic provisioning
- static provisioning
- topology and availability zones
- node scheduling
- local storage constraints
- OpenShift Data Foundation / Ceph health
- cloud provider quota or API errors
- snapshot or clone restore problems
- access mode mismatch
- storage capacity mismatch
- stale `claimRef`
- broken provisioner credentials
- pod scheduling constraints

From a senior administrator perspective, the mistake is to troubleshoot only the PVC. A pending PVC is often a symptom of a broken storage control path, scheduler decision, CSI sidecar, topology rule, or backend storage state.

---

## 2. Core Mental Model

### 2.1 PVC, PV, StorageClass, and CSI Relationship

A PVC is a request for storage. It asks for capacity, access mode, volume mode, and optionally a `StorageClass`.

A PV is the actual cluster storage object. It may represent NFS, iSCSI, Fibre Channel, Ceph RBD, CephFS, vSphere disk, AWS EBS, Azure Disk, local disk, LVM volume, or another backend.

A StorageClass defines how dynamic provisioning should happen. It points to a provisioner such as a CSI driver.

A CSI driver performs storage lifecycle actions such as:

- create volume
- delete volume
- attach volume
- detach volume
- stage volume
- publish volume
- expand volume
- snapshot volume, if supported

In simple terms:

```text
PVC request
   |
   |-- static provisioning path --> bind to existing matching PV
   |
   |-- dynamic provisioning path --> StorageClass -> CSI provisioner -> backend volume -> PV -> PVC bound
```

When the PVC stays `Pending`, something in that chain did not complete.

---

## 3. What `Pending` Actually Means

A PVC has common phases:

```text
Pending  -> not yet bound to a PV
Bound    -> successfully bound to a PV
Lost     -> bound PV no longer exists or is no longer usable
```

A PVC in `Pending` does not always mean failure.

For example, with `volumeBindingMode: WaitForFirstConsumer`, a PVC may remain pending until a pod consumes it. This is normal for topology-aware storage classes because OpenShift waits to know where the pod can run before provisioning a volume in the correct zone, node, or topology segment.

The key question is:

> Is the PVC pending because OpenShift is intentionally waiting, or because provisioning/binding failed?

## 4. First 5-Minute Triage

Run these commands first.

```bash
# List PVCs in the namespace
oc get pvc -n <namespace>

# Wide output gives volume, capacity, access mode, storage class, age
oc get pvc -n <namespace> -o wide

# Describe the PVC. Events are the most important part.
oc describe pvc <pvc-name> -n <namespace>

# Check namespace events sorted by time
oc get events -n <namespace> --sort-by=.lastTimestamp

# Check all storage classes
oc get storageclass

# Show storage class details
oc describe storageclass <storageclass-name>

# Check PV inventory
oc get pv

# Check pods using the claim
oc get pod -n <namespace> -o wide

# Find pods referencing the PVC
oc get pod -n <namespace> -o yaml | grep -B5 -A8 "claimName: <pvc-name>"
```

A senior admin does not start by deleting objects. First, read events.

Common PVC event messages include:

```text
waiting for first consumer to be created before binding
no persistent volumes available for this claim and no storage class is set
storageclass.storage.k8s.io "x" not found
failed to provision volume with StorageClass "x"
pod has unbound immediate PersistentVolumeClaims
0/6 nodes are available: pod has unbound immediate PersistentVolumeClaims
failed to provision volume with StorageClass: rpc error
provisioning failed: no available topology found
claim Selector is not supported
volume node affinity conflict
exceeded quota
```

## 5. Decision Tree

Use this flow instead of random trial and error.

```text
PVC Pending
|
|-- Step 1: Does PVC specify a storageClassName?
|     |
|     |-- No / nil -> Is there a default StorageClass?
|     |       |-- No -> PVC will wait for static PV or remain pending
|     |       |-- Yes -> default SC should be injected
|     |
|     |-- storageClassName: "" -> dynamic provisioning disabled intentionally
|     |
|     |-- named SC -> Does that StorageClass exist?
|
|-- Step 2: Is StorageClass dynamic or static path?
|     |
|     |-- Dynamic -> check provisioner, CSI pods, backend, quotas, topology
|     |
|     |-- Static -> check PV match: size, accessModes, volumeMode, class, selector, phase, claimRef
|
|-- Step 3: Is volumeBindingMode WaitForFirstConsumer?
|     |
|     |-- Yes -> Is there a pod consuming the PVC?
|              |-- No -> Pending is expected
|              |-- Yes -> check pod scheduling constraints and topology
|
|-- Step 4: Is the requested mode supported?
|     |
|     |-- RWX requested on block/local storage? likely unsupported
|     |-- Block requested but PV/SC supports Filesystem only? mismatch
|
|-- Step 5: Are CSI/operator/backend components healthy?
|     |
|     |-- CSI controller logs
|     |-- CSI node plugin pods
|     |-- ClusterOperator status
|     |-- ODF/Ceph health or cloud API status
|
|-- Step 6: Is the issue restore/snapshot/clone related?
|     |
|     |-- check dataSource, snapshot class, source PVC status, driver snapshot support
```

## 6. Common Root Causes and Fixes

## 6.1 No Default StorageClass

### Symptom

```bash
oc get pvc -n app
```

Example:

```text
NAME      STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
data      Pending                                      <none>         5m
```

PVC event:

```text
no persistent volumes available for this claim and no storage class is set
```

### Why It Happens

The PVC did not specify `storageClassName`, and the cluster has no default StorageClass. Without a default class, OpenShift cannot dynamically provision storage unless the claim explicitly references a valid StorageClass.

### Check

```bash
oc get storageclass
```

If no class has `(default)`, then new PVCs without `storageClassName` may remain pending unless a matching static PV exists.

### Fix Option 1: Set a Default StorageClass

```bash
oc patch storageclass <sc-name> \
  -p '{"metadata": {"annotations": {"storageclass.kubernetes.io/is-default-class": "true"}}}'
```

Then recreate the PVC if the default class was not injected earlier.

```bash
oc delete pvc <pvc-name> -n <namespace>
oc apply -f pvc.yaml
```

### Fix Option 2: Specify StorageClass in PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  namespace: app
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: gp3-csi
  resources:
    requests:
      storage: 10Gi
```

### Senior Admin Note

Do not blindly set a default StorageClass in a multi-storage cluster. For example, if you have `ocs-storagecluster-ceph-rbd`, `ocs-storagecluster-cephfs`, `gp3-csi`, and `lvms-vg1`, the default choice affects every application that omits `storageClassName`.

## 6.2 `storageClassName: ""` Disables Dynamic Provisioning

### Symptom

PVC remains pending even though a default StorageClass exists.

```yaml
spec:
  storageClassName: ""
```

### Why It Happens

An empty string means: do not use any StorageClass. The PVC will only bind to a static PV with no storage class.

This is commonly used for static NFS PVs, exam labs, legacy storage, or manually pre-created PVs.

### Check

```bash
oc get pvc <pvc-name> -n <namespace> -o yaml | grep storageClassName
```

### Fix

If dynamic provisioning is intended, remove the empty value and specify a real StorageClass.

```yaml
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
```

If static provisioning is intended, create a matching PV with no `storageClassName` or with `storageClassName: ""`, depending on your YAML convention.

---

## 6.3 StorageClass Does Not Exist

### Symptom

PVC event:

```text
storageclass.storage.k8s.io "fast-storage" not found
```

### Check

```bash
oc get storageclass
oc get pvc <pvc-name> -n <namespace> -o yaml | grep storageClassName
```

### Fix

Correct the PVC StorageClass name.

```yaml
storageClassName: <valid-storage-class>
```

If the application is deployed by Helm or an Operator, update values or custom resource fields instead of manually editing generated PVCs.

Example Helm override:

```bash
helm upgrade <release> <chart> \
  -n <namespace> \
  --set persistence.storageClass=ocs-storagecluster-ceph-rbd
```

### Senior Admin Note

StorageClass names are case-sensitive and cluster-specific. A chart value that works in AWS might fail on vSphere, bare metal, or OpenShift Data Foundation.

---

## 6.4 Multiple Default StorageClasses

### Symptom

PVCs without `storageClassName` bind to an unexpected backend, or administrators see alerts about multiple defaults.

### Check

```bash
oc get storageclass -o custom-columns=NAME:.metadata.name,DEFAULT:.metadata.annotations.storageclass\.kubernetes\.io/is-default-class,PROVISIONER:.provisioner
```

### Fix

Keep only one default unless there is a deliberate migration window.

```bash
oc patch storageclass <old-default> \
  -p '{"metadata": {"annotations": {"storageclass.kubernetes.io/is-default-class": "false"}}}'

oc patch storageclass <new-default> \
  -p '{"metadata": {"annotations": {"storageclass.kubernetes.io/is-default-class": "true"}}}'
```

### Senior Admin Note

Changing the default StorageClass does not automatically change existing PVCs. It affects new PVCs that omit `storageClassName`.

## 6.5 `WaitForFirstConsumer` Is Working as Designed

### Symptom

PVC event:

```text
waiting for first consumer to be created before binding
```

The PVC is `Pending`, but no pod is using it yet.

### Why It Happens

A StorageClass with `volumeBindingMode: WaitForFirstConsumer` delays provisioning until a pod uses the PVC. This allows the scheduler to choose a node first, so storage can be created in the correct zone, topology segment, or node-local location.

### Check

```bash
oc describe storageclass <sc-name> | grep -i VolumeBindingMode
```

Example:

```text
VolumeBindingMode: WaitForFirstConsumer
```

Check whether a pod consumes the PVC:

```bash
oc get pod -n <namespace> -o yaml | grep -B5 -A8 "claimName: <pvc-name>"
```

### Fix

Create or fix the pod/deployment/statefulset that consumes the PVC.

Example pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pvc-consumer
  namespace: app
spec:
  containers:
    - name: app
      image: registry.access.redhat.com/ubi9/ubi
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: app-data
```

After the pod is created, watch PVC and pod events:

```bash
oc get pvc,pod -n app -w
```

### Senior Admin Note

Do not change `WaitForFirstConsumer` to `Immediate` just to make the PVC bind quickly. On topology-aware storage, immediate binding can create a volume in a zone where the pod cannot run, resulting in a different production failure.

## 6.6 `WaitForFirstConsumer` + `nodeName` Misuse

### Symptom

PVC stays pending even though a pod exists.

Pod YAML has:

```yaml
spec:
  nodeName: worker-1.example.com
```

PVC event may still say:

```text
waiting for first consumer to be created before binding
```

### Why It Happens

When `nodeName` is set directly, the scheduler is bypassed. For `WaitForFirstConsumer`, Kubernetes needs the scheduler to participate in volume binding. Bypassing the scheduler can leave the PVC pending.

### Fix

Use node selector, affinity, or topology-aware scheduling instead of `nodeName`.

```yaml
spec:
  nodeSelector:
    kubernetes.io/hostname: worker-1.example.com
```

Or use node affinity:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: kubernetes.io/hostname
                operator: In
                values:
                  - worker-1.example.com
```

## 6.7 Static PV Does Not Match PVC

### Symptom

PVC is pending with event:

```text
no persistent volumes available for this claim
```

PV exists, but binding does not happen.

### Match Conditions

For static binding, these must align:

| Requirement | PVC | PV |
|---|---|---|
| Capacity | requested storage | PV capacity must be equal or greater |
| Access mode | `ReadWriteOnce`, `ReadWriteMany`, etc. | PV must support requested mode |
| Volume mode | `Filesystem` or `Block` | must match |
| StorageClass | class name or empty class | must match |
| Selector | PVC label selector | PV labels must match |
| PV phase | must be `Available` | not `Bound`, `Released`, or `Failed` |
| claimRef | should be empty unless pre-bound correctly | stale claimRef blocks reuse |

### Check

```bash
oc get pv
oc describe pvc <pvc-name> -n <namespace>
oc describe pv <pv-name>
```

Useful JSONPath checks:

```bash
oc get pvc <pvc-name> -n <namespace> \
  -o jsonpath='{.spec.storageClassName}{"\n"}{.spec.accessModes}{"\n"}{.spec.resources.requests.storage}{"\n"}{.spec.volumeMode}{"\n"}'

oc get pv <pv-name> \
  -o jsonpath='{.spec.storageClassName}{"\n"}{.spec.accessModes}{"\n"}{.spec.capacity.storage}{"\n"}{.spec.volumeMode}{"\n"}{.status.phase}{"\n"}'
```

### Example Mismatch: PVC Requests Too Much

PVC:

```yaml
resources:
  requests:
    storage: 100Gi
```

PV:

```yaml
capacity:
  storage: 50Gi
```

This will not bind.

### Fix

Create a PV with enough capacity or reduce the PVC request if acceptable.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-app-pv
spec:
  capacity:
    storage: 100Gi
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: ""
  nfs:
    server: 192.168.10.20
    path: /exports/app
```

## 6.8 Access Mode Mismatch

### Symptom

PVC requests `ReadWriteMany`, but only block/local/RWO storage is available.

PVC:

```yaml
accessModes:
  - ReadWriteMany
```

StorageClass is backed by EBS, Azure Disk, vSphere block disk, LVM, or local storage.

### Why It Happens

Not every storage backend supports every access mode.

Typical pattern:

| Backend | Common Access Mode |
|---|---|
| AWS EBS | RWO |
| Azure Disk | RWO |
| vSphere CNS block | RWO |
| Ceph RBD | RWO |
| Local/LVM | RWO |
| NFS | RWX |
| CephFS | RWX |
| Azure File | RWX |
| Manila | RWX |

### Check

```bash
oc get storageclass
oc describe storageclass <sc-name>
oc get pv -o wide
```

### Fix

Use a RWX-capable StorageClass for shared filesystem workloads.

Example with CephFS:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-data
  namespace: app
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: ocs-storagecluster-cephfs
  resources:
    requests:
      storage: 20Gi
```

### Senior Admin Note

Do not force RWX by changing YAML only. The backend must actually support multi-node read-write semantics. Otherwise, the PVC may remain pending or the pod may later fail at mount time.

---

## 6.9 VolumeMode Mismatch: `Filesystem` vs `Block`

### Symptom

A PV exists, but PVC does not bind.

PVC:

```yaml
volumeMode: Block
```

PV:

```yaml
volumeMode: Filesystem
```

### Why It Happens

Kubernetes matches PVCs and PVs by volume mode. A block claim will not bind to a filesystem PV.

### Check

```bash
oc get pvc <pvc-name> -n <namespace> -o jsonpath='{.spec.volumeMode}{"\n"}'
oc get pv <pv-name> -o jsonpath='{.spec.volumeMode}{"\n"}'
```

If omitted, `Filesystem` is the default.

### Fix

Use matching `volumeMode` on PVC and PV, or use a StorageClass/driver that supports the requested mode.

## 6.10 PV Is `Released` Because of Old ClaimRef

### Symptom

PV exists and looks suitable, but PVC remains pending.

```bash
oc get pv
```

Example:

```text
NAME        CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM
app-pv      10Gi       RWO            Retain           Released   old-ns/old-pvc
```

### Why It Happens

With `Retain` reclaim policy, when a PVC is deleted, the PV may remain in `Released` state and keep a `claimRef` to the old PVC. It is not automatically available for a new claim.

### Check

```bash
oc get pv <pv-name> -o yaml | grep -A8 claimRef
```

### Fix

Only do this after confirming the backend data should be reused or manually cleaned.

```bash
oc patch pv <pv-name> --type=json -p='[{"op":"remove","path":"/spec/claimRef"}]'
```

Then check:

```bash
oc get pv <pv-name>
```

The PV should move to `Available`, and a matching PVC can bind.

### Data Safety Warning

Never remove `claimRef` on a retained PV unless you understand the data ownership. You can accidentally attach another application to old production data.

## 6.11 PVC Selector Prevents Dynamic Provisioning

### Symptom

PVC has a selector:

```yaml
selector:
  matchLabels:
    storage-tier: gold
```

PVC stays pending even though StorageClass exists.

### Why It Happens

PVC selectors are mainly for selecting static PVs by labels. Many dynamic provisioners do not support PVC selectors. The selector may prevent provisioning or limit binding to only PVs with matching labels.

### Check

```bash
oc get pvc <pvc-name> -n <namespace> -o yaml | grep -A8 selector
oc get pv --show-labels
```

### Fix

For dynamic provisioning, remove the selector unless your storage solution explicitly supports it.

For static provisioning, label the PV correctly.

```bash
oc label pv <pv-name> storage-tier=gold
```

## 6.12 CSI Driver or Provisioner Is Down

### Symptom

PVC event:

```text
failed to provision volume with StorageClass "x"
```

or:

```text
waiting for a volume to be created, either by external provisioner "x" or manually created by system administrator
```

### Check StorageClass Provisioner

```bash
oc get storageclass <sc-name> -o yaml
```

Look at:

```yaml
provisioner: ebs.csi.aws.com
```

or:

```yaml
provisioner: openshift-storage.rbd.csi.ceph.com
```

### Check CSI Driver Objects

```bash
oc get csidriver
oc get clustercsidriver
```

### Check Cluster Operators

```bash
oc get co
oc get co storage
```

Depending on platform, also check relevant operators:

```bash
oc get co | egrep 'storage|csi|cloud|machine|authentication|kube-controller-manager'
```

### Check CSI Pods

Common namespaces:

```bash
oc get pods -n openshift-cluster-csi-drivers
oc get pods -n openshift-storage
oc get pods -n openshift-local-storage
oc get pods -n openshift-storage-operator
```

Find CSI pods cluster-wide:

```bash
oc get pods -A | egrep -i 'csi|provisioner|attacher|resizer|snapshot|ceph|rook|odf|lvm|local'
```

### Check Logs

```bash
oc logs -n <csi-namespace> <csi-controller-pod> -c csi-provisioner --tail=100
oc logs -n <csi-namespace> <csi-controller-pod> --all-containers --tail=200
```

For CSI daemonset node plugin:

```bash
oc logs -n <csi-namespace> ds/<csi-node-daemonset> --all-containers --tail=100
```

### Fix

Depends on failure:

| Failure | Fix |
|---|---|
| CSI controller pod CrashLoopBackOff | inspect logs, config, credentials, operator status |
| CSI provisioner cannot call backend API | fix cloud credentials / backend endpoint / firewall |
| CSI node plugin missing on nodes | check daemonset tolerations, node selectors, SCC, taints |
| Operator degraded | inspect ClusterOperator conditions and operator logs |
| Provisioner name typo in custom StorageClass | correct StorageClass and recreate PVC |

### Senior Admin Note

For PVC Pending, the `csi-provisioner` container is often more useful than application pod logs. Application pods only tell you they cannot mount; the provisioner tells you why the PV was never created.

## 6.13 Backend Storage Capacity Exhausted

### Symptom

PVC event:

```text
failed to provision volume: insufficient storage
```

or provider-specific messages:

```text
no space left on device
pool full
exceeded quota
not enough free extents
resource exhausted
```

### Check

For generic cluster:

```bash
oc describe pvc <pvc-name> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

For OpenShift Data Foundation:

```bash
oc get storagecluster -n openshift-storage
oc get cephcluster -n openshift-storage
oc get cephblockpool -n openshift-storage
oc get cephfilesystem -n openshift-storage
oc get pods -n openshift-storage
```

If the rook toolbox is available:

```bash
oc rsh -n openshift-storage deploy/rook-ceph-tools
ceph status
ceph df
ceph osd df tree
```

For LVM Storage:

```bash
oc get lvmcluster -A
oc get pods -n openshift-storage | grep -i lvm
oc get nodes -o wide
```

For cloud storage:

- check cloud volume quota
- check account/subscription limits
- check availability-zone-specific capacity
- check encryption/KMS permission
- check storage API errors in CSI logs

### Fix

| Backend | Corrective Action |
|---|---|
| ODF/Ceph pool full | add capacity, recover OSDs, clean old volumes after confirming reclaim policy |
| LVM no free extents | add disk/device, expand volume group, rebalance workload |
| Cloud quota exceeded | increase quota or delete unused volumes/snapshots |
| Local storage exhausted | add local disks and update local volume configuration |
| Thin pool full | expand thin pool or reduce usage |

### Senior Admin Note

Capacity issues can be namespace-level or backend-level. A ResourceQuota failure is different from a storage pool full condition. PVC events identify which layer rejected the request.

## 6.14 Namespace ResourceQuota Blocks PVC

### Symptom

PVC creation or provisioning fails with quota-related event.

Examples:

```text
exceeded quota
requests.storage exceeded
persistentvolumeclaims exceeded
```

### Check

```bash
oc get resourcequota -n <namespace>
oc describe resourcequota -n <namespace>
```

Check namespace storage usage:

```bash
oc get pvc -n <namespace>
oc describe quota <quota-name> -n <namespace>
```

### Fix

Increase quota or reduce request.

Example quota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: storage-quota
  namespace: app
spec:
  hard:
    persistentvolumeclaims: "10"
    requests.storage: 500Gi
```

Patch example:

```bash
oc patch resourcequota storage-quota -n app --type=merge \
  -p '{"spec":{"hard":{"requests.storage":"500Gi","persistentvolumeclaims":"10"}}}'
```

### Senior Admin Note

ResourceQuota normally blocks object admission or updates. If an Operator is retrying PVC creation, the application may show pending or degraded even though the PVC object may not exist yet. Always check both PVC objects and events.

## 6.15 Pod Has Unbound Immediate PersistentVolumeClaims

### Symptom

Pod is pending:

```text
0/5 nodes are available: pod has unbound immediate PersistentVolumeClaims
```

PVC is pending.

### Why It Happens

The pod references a PVC that uses immediate binding, but the PVC is not bound. The scheduler cannot schedule the pod because storage is unresolved.

### Check

```bash
oc describe pod <pod-name> -n <namespace>
oc describe pvc <pvc-name> -n <namespace>
oc get storageclass <sc-name> -o yaml
```

### Fix

Fix the PVC root cause:

- missing StorageClass
- dynamic provisioner failed
- no matching static PV
- quota issue
- access mode mismatch
- backend capacity issue

Do not troubleshoot CPU/memory scheduling first unless PVC has already bound.

---

## 6.16 Pod Scheduling Constraints Block `WaitForFirstConsumer`

### Symptom

PVC uses `WaitForFirstConsumer`. A pod exists, but PVC remains pending.

Pod event examples:

```text
0/6 nodes are available: node(s) didn't match Pod's node affinity/selector
0/6 nodes are available: untolerated taint
0/6 nodes are available: insufficient cpu
0/6 nodes are available: volume node affinity conflict
```

### Why It Happens

With delayed binding, PVC provisioning depends on a valid pod scheduling decision. If the pod cannot be scheduled anywhere, the scheduler cannot choose topology for the volume.

### Check

```bash
oc describe pod <pod-name> -n <namespace>
oc get nodes --show-labels
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
oc describe storageclass <sc-name>
```

Check pod constraints:

```bash
oc get pod <pod-name> -n <namespace> -o yaml | egrep -A20 'nodeSelector|affinity|tolerations|topologySpreadConstraints'
```

### Fix

Correct one of these:

- node selector labels
- node affinity
- tolerations
- resource requests
- topology spread constraints
- pod anti-affinity
- storage topology labels
- availability zone mismatch

### Senior Admin Note

In this case, PVC Pending is caused by scheduling, not by the storage backend. The storage system is waiting for the scheduler to make a valid placement decision.

## 6.17 Local Storage / LVM Storage / TopoLVM Pending Issues

### Symptom

PVC using local or LVM-backed storage remains pending.

StorageClass may look like:

```text
lvms-vg1
local-storage
```

Events may mention:

```text
waiting for first consumer
no available volume found
no nodes match
not enough allocatable capacity
```

### Why It Happens

Local storage is tied to a specific node or device. It is not globally accessible like network storage. The scheduler and provisioner must align pod placement with available local capacity.

### Check

```bash
oc get storageclass
oc describe storageclass <local-or-lvm-sc>
oc get nodes -o wide
oc get pods -A | egrep -i 'local|lvm|topolvm'
oc get pv -o wide
```

For LVM Storage Operator:

```bash
oc get lvmcluster -A
oc describe lvmcluster -n openshift-storage
oc get pods -n openshift-storage | grep -i lvm
```

Check node labels and taints:

```bash
oc get nodes --show-labels
oc describe node <node-name>
```

### Fix

- ensure the pod can schedule to nodes that have local/LVM capacity
- remove incorrect node selectors
- add tolerations if storage nodes are tainted
- add disks to eligible nodes
- ensure local storage operator discovered devices
- ensure PVs are `Available`
- use `WaitForFirstConsumer` for topology-aware local provisioning

### Senior Admin Note

Local storage is excellent for performance-sensitive workloads but weak for portability. A node failure can make local PV-backed workloads unavailable unless the application has replication at the application layer.

## 6.18 OpenShift Data Foundation / Ceph PVC Pending

### Symptom

PVC using ODF classes is pending:

```text
ocs-storagecluster-ceph-rbd
ocs-storagecluster-cephfs
openshift-storage.rbd.csi.ceph.com
openshift-storage.cephfs.csi.ceph.com
```

Events may show:

```text
failed to provision volume
rados: ret=-28, No space left on device
failed to get connection
pool full
ceph cluster is not healthy
```

### Check ODF Health

```bash
oc get storagecluster -n openshift-storage
oc describe storagecluster -n openshift-storage
oc get pods -n openshift-storage
oc get cephcluster -n openshift-storage
```

Check CSI controller logs:

```bash
oc get pods -n openshift-storage | egrep 'csi|rbd|cephfs'

oc logs -n openshift-storage <rbd-csi-controller-pod> --all-containers --tail=200
oc logs -n openshift-storage <cephfs-csi-controller-pod> --all-containers --tail=200
```

If toolbox exists:

```bash
oc rsh -n openshift-storage deploy/rook-ceph-tools
ceph -s
ceph df
ceph health detail
```

### RBD vs CephFS Decision

| Workload Need | ODF Class |
|---|---|
| Single-node read/write block-style volume | `ocs-storagecluster-ceph-rbd` |
| Shared RWX filesystem | `ocs-storagecluster-cephfs` |

### Fix

| Issue | Fix |
|---|---|
| Ceph full/nearfull | add storage, remove unused volumes safely, recover OSDs |
| OSD down | repair node/disk/network, check rook/ceph pods |
| Wrong class for RWX | use CephFS class |
| CSI controller unhealthy | inspect logs, restart only after understanding root cause |
| Encryption/KMS issue | check KMS secret/config and CSI logs |

### Senior Admin Note

Do not delete ODF PVCs or PVs casually. ODF stores cluster services and application data. Understand reclaim policies and Ceph object mapping before cleanup.

```text
csi.vsphere.vmware.com
```

PVC event:


| Cloud Issue | Fix |
|---|---|

## 6.20 Snapshot Restore or Clone PVC Pending

### Symptom

PVC created from snapshot or clone stays pending.

Example PVC from snapshot:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restored-data
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  dataSource:
    name: app-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

### Common Causes

- source snapshot is not ready
- `VolumeSnapshotClass` missing or wrong
- CSI driver does not support restore
- target PVC size smaller than source snapshot
- restore StorageClass incompatible with snapshot backend
- snapshot exists in different namespace
- data source reference typo
- CSI snapshot controller unhealthy

### Check

```bash
oc get volumesnapshot -n <namespace>
oc describe volumesnapshot <snapshot-name> -n <namespace>
oc get volumesnapshotclass
oc get volumesnapshotcontent
oc describe pvc <pvc-name> -n <namespace>
oc get pods -A | grep -i snapshot
```

Check snapshot readiness:

```bash
oc get volumesnapshot <snapshot-name> -n <namespace> \
  -o jsonpath='{.status.readyToUse}{"\n"}{.status.restoreSize}{"\n"}'
```

### Fix

- wait until snapshot is `readyToUse: true`
- use correct `VolumeSnapshotClass`
- create target PVC in same namespace as snapshot, unless supported workflow says otherwise
- request target size greater than or equal to restore size
- use same compatible CSI backend
- check snapshot controller and CSI snapshotter logs

### Backup Awareness Note

Snapshot restore is not only a PVC operation. It depends on snapshot APIs, snapshot controller, CSI snapshotter sidecars, backend snapshot support, and application consistency. A restored PVC may bind successfully but still contain crash-consistent application data unless the backup workflow quiesced the application.

## 7. Production Troubleshooting Playbooks

## 7.1 Playbook: Generic PVC Pending

```bash
NS=<namespace>
PVC=<pvc-name>

oc get pvc $PVC -n $NS -o wide
oc describe pvc $PVC -n $NS
oc get events -n $NS --sort-by=.lastTimestamp | tail -50

SC=$(oc get pvc $PVC -n $NS -o jsonpath='{.spec.storageClassName}')
```

Then branch:

- no SC -> default/static PV issue
- SC missing -> typo or missing driver/operator

- no matching PV -> check static PV match

## 8. Advanced Event Interpretation

## 8.1 `waiting for first consumer`

Meaning:

```text
StorageClass uses WaitForFirstConsumer. Need pod scheduling context.
```

Action:

```bash
oc get pod -n <ns>
oc describe pod <pod> -n <ns>
```

If no pod exists, create the consumer.

---

## 8.2 `no persistent volumes available and no storage class is set`

Meaning:

```text
No dynamic provisioning path and no matching static PV.
```

Action:

```bash
oc get sc
oc get pv
oc get pvc <pvc> -n <ns> -o yaml
```

Fix by setting a StorageClass or creating a matching static PV.

---

## 8.3 `storageclass not found`

Meaning:

```text
PVC references a StorageClass that does not exist.
```

Action:

```bash
oc get sc
oc patch pvc <pvc> -n <ns> --type=merge -p '{"spec":{"storageClassName":"<valid-sc>"}}'
```

In many cases, because PVC spec fields are partly immutable after creation, the clean fix is to recreate the PVC if no data exists yet.

## 8.4 `failed to provision volume`

Meaning:

```text
Dynamic provisioner attempted backend volume creation and failed.
```

Action:

```bash
oc describe pvc <pvc> -n <ns>
oc describe sc <sc>
oc logs -n <csi-ns> <csi-controller-pod> --all-containers --tail=200
```

Fix depends on backend message.

---

## 8.5 `volume node affinity conflict`

Meaning:

```text
PV is tied to topology/node that does not match where pod is scheduled.
```

Action:

```bash
oc describe pv <pv>

oc get nodes --show-labels
```

Fix node affinity, pod placement, topology labels, or recreate volume in correct topology.

## 11. Backup and Restore Awareness

A PVC pending problem during restore is common after disaster recovery, migration, Velero restore, OADP restore, snapshot restore, or application clone.

### 11.1 Restore-Time PVC Pending Causes

| Cause | Example |
|---|---|
| StorageClass missing in target cluster | source used `gp3`, target has `ocs-storagecluster-ceph-rbd` |
| Default StorageClass different | restored PVC binds to wrong backend |
| Static PV not restored | PVC asks for old PV name that does not exist |
| PV has old node affinity | restored local PV points to non-existing node |
| SnapshotClass missing | PVC from snapshot cannot restore |
| Source snapshot not ready | snapshot restore claim waits/fails |
| Access mode unsupported in target | RWX claim restored onto RWO backend |
| Retain PV claimRef stale | old PV not reusable |
| Namespace ResourceQuota lower in target | restored PVC rejected or pending |
| CSI driver not installed in target | provisioner unavailable |

### 11.2 Migration Checklist

Before restoring applications:

```bash
oc get storageclass
oc get csidriver
oc get volumesnapshotclass
oc get resourcequota -A
oc get pv
```

Map source classes to target classes:

```text
source gp2             -> target gp3-csi
source managed-premium -> target managed-csi
source ceph-rbd        -> target ocs-storagecluster-ceph-rbd
source nfs-client      -> target cephfs or nfs-client
```

### 11.3 Stateful Application Restore Rule

For databases and stateful applications:

1. Restore namespace metadata.
2. Restore secrets/configmaps/service accounts.
3. Restore PVCs/PVs or snapshots.
4. Wait for PVCs to bind.
5. Start StatefulSets/Deployments.
6. Validate application consistency.
7. Validate service endpoints and routes.

Starting pods before PVCs bind leads to noisy pod pending events and can hide the actual storage failure.

## 13. What Not To Do

Do not do these in production:

```bash
# Bad: deleting PVC without understanding reclaim policy
oc delete pvc data -n prod

# Bad: removing finalizers blindly
oc patch pvc data -n prod -p '{"metadata":{"finalizers":null}}' --type=merge

# Bad: deleting PV with Retain/Delete confusion
oc delete pv pvc-xxxx

# Bad: changing application YAML without checking storage class and events
oc edit deployment app

# Bad: restarting CSI pods randomly before collecting logs
oc delete pod <csi-pod> -n <csi-ns>
```

Why these are dangerous:

- PVC deletion can trigger backend volume deletion if reclaim policy is `Delete`.
- Removing finalizers can orphan storage or cause data loss.
- Deleting PVs may remove the only cluster reference to backend storage.
- Restarting CSI pods may erase useful failure context.
- Editing generated PVCs from Operators/Helm may be reverted.

## 15. Exam and Interview Notes

For OpenShift administration exams and real interviews, explain PVC Pending like this:

> A PVC remains Pending when the control plane cannot bind it to a matching PV or dynamically provision a PV through the requested StorageClass. I first check PVC events, StorageClass, default class, binding mode, PV match conditions, CSI provisioner health, backend capacity, access mode support, and pod scheduling constraints if `WaitForFirstConsumer` is used.

Key commands to remember:

```bash
oc describe pvc <pvc> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get sc
oc describe sc <sc>
oc get pv
oc describe pv <pv>
oc get pods -A | grep -i csi
oc logs -n <csi-ns> <csi-controller-pod> --all-containers --tail=200
```

Key concepts:

- PVC is namespaced; PV is cluster-scoped.
- Bound PV/PVC is one-to-one.
- `storageClassName: ""` disables dynamic provisioning.
- `WaitForFirstConsumer` can make Pending normal until a pod exists.
- `nodeName` can break delayed binding because it bypasses scheduler behavior.
- Access mode must be supported by backend.
- Static PV match requires size, class, access mode, volume mode, selector, and phase alignment.
- Retained PVs may need old `claimRef` cleanup.
- CSI logs are essential for dynamic provisioning failures.

## 16. Quick Reference Table

| PVC/POD Message | Most Likely Cause | First Check | Fix Direction |
|---|---|---|---|
| `waiting for first consumer` | WFFC mode | pod exists? pod schedulable? | create/fix consumer pod |
| `no storage class is set` | no SC/default/static PV | `oc get sc`, `oc get pv` | specify SC or create PV |
| `storageclass not found` | typo/missing SC | `oc get sc` | correct class/recreate PVC |
| `failed to provision volume` | CSI/backend failure | CSI logs | fix backend/provisioner |
| `pod has unbound immediate PVC` | PVC unresolved before scheduling | describe PVC | fix PVC root cause |
| `volume node affinity conflict` | topology mismatch | describe PV/pod/node | fix scheduling/topology |
| `exceeded quota` | namespace quota | describe quota | increase quota/reduce request |
| PV `Released` | stale claimRef | describe PV | remove claimRef after data validation |
| RWX PVC pending | backend does not support RWX | describe SC | use RWX-capable class |
| restore PVC pending | snapshot/SC mismatch | describe snapshot/PVC | fix dataSource/snapshot class/SC |

## 17. Final Troubleshooting Method

Use this exact order in production:

1. Read PVC events.
2. Check StorageClass name and default behavior.
3. Check `volumeBindingMode`.
4. Check whether a pod consumes the PVC.
5. If static provisioning, compare PVC and PV match fields.
6. If dynamic provisioning, check CSI provisioner logs.
7. Check backend capacity and health.
8. Check pod scheduling constraints for WFFC.
9. Check access mode and volume mode support.
10. Check restore/snapshot/clone data source if applicable.
11. Back up YAML before destructive remediation.
12. Fix the root cause, then recreate only when required.

A strong OpenShift administrator treats PVC Pending as a control-plane workflow failure, not just a storage object status.
