## 1. Executive Summary

A **CSI driver** is the storage integration layer that allows Kubernetes and OpenShift to consume external storage systems through a standard API. CSI stands for **Container Storage Interface**.

In OpenShift, a CSI driver is usually delivered and managed through an **Operator**. It normally contains:

- A **controller component** that provisions, deletes, attaches, detaches, snapshots, and resizes volumes.
- A **node component** that runs on each worker node and stages/publishes/mounts volumes for pods.
- Multiple Kubernetes CSI sidecars such as `external-provisioner`, `external-attacher`, `external-snapshotter`, `external-resizer`, `node-driver-registrar`, and `livenessprobe`.

For an advanced OpenShift administrator, CSI is important because most production stateful workload issues eventually touch one of these areas:

- PVC stuck in `Pending`
- PV created but pod cannot mount it
- `Multi-Attach` error
- snapshot not becoming `readyToUse`
- PVC expansion stuck
- wrong `StorageClass`
- topology/zone mismatch
- CSI driver pod crash
- storage backend credential issue
- backup appears successful but restore fails

CSI is not only a storage feature. It is a day-2 operations topic that connects Kubernetes API objects, OpenShift Operators, cloud or SAN/NAS backends, node-level mounts, kubelet behavior, security, and backup design.

## 2. What Is a CSI Driver?

A **CSI driver** is a plugin that implements the Container Storage Interface specification for a storage backend.

Examples of storage backends:

- AWS EBS
- Azure Disk
- Azure File
- Google Persistent Disk
- VMware vSphere CNS
- OpenStack Cinder
- OpenStack Manila
- Red Hat OpenShift Data Foundation / Ceph RBD / CephFS
- LVM Storage
- NFS/SMB third-party CSI drivers
- Enterprise SAN/NAS arrays such as NetApp, Dell, Pure, HPE, Hitachi, IBM, etc.

The Kubernetes/OpenShift control plane does not need to know every storage vendor's internal API. Instead, it talks to the CSI driver, and the CSI driver talks to the backend storage system.

### Simple definition

```text
PVC/PV/Pod request in OpenShift
        ↓
Kubernetes storage controllers and CSI sidecars
        ↓
CSI driver
        ↓
Storage backend API
        ↓
Real disk/share/LUN/volume/snapshot
```

### Real-world analogy

Think of OpenShift as a data center operations platform. A user asks for a 100Gi disk by creating a PVC. OpenShift does not manually log in to a storage array. It asks the CSI driver. The CSI driver knows how to create a LUN, cloud disk, Ceph RBD image, NFS share, or virtual disk in the backend storage system.

## 3. Why CSI Exists

Before CSI, Kubernetes had many **in-tree volume plugins** compiled directly into Kubernetes source code. That model created problems:

- Storage vendors had to contribute plugin code into Kubernetes core.
- Kubernetes releases were tied to storage driver updates.
- Vendor-specific bug fixes depended on Kubernetes release cycles.
- The core Kubernetes codebase became harder to maintain.
- New storage features were slow to deliver.

CSI solved this by moving storage vendor logic out of the Kubernetes core and into separately deployed drivers.

### Benefits of CSI

| Benefit | Explanation |
|---|---|
| Vendor independence | Storage providers can build and release drivers outside Kubernetes core. |
| Faster bug fixes | CSI driver updates can happen without changing Kubernetes itself. |
| Standard API | Kubernetes/OpenShift can use a common model for provisioning, attach, mount, snapshots, resize, and clone. |
| Rich storage features | Snapshots, cloning, volume expansion, topology-aware provisioning, and ephemeral CSI volumes become possible depending on the driver. |
| Operator-based lifecycle | In OpenShift, many CSI drivers are managed by Operators for installation, upgrades, and reconciliation. |

## 4. CSI in OpenShift vs Plain Kubernetes

OpenShift is Kubernetes plus enterprise platform components such as Operators, SCC, cluster operators, integrated monitoring, authentication, and curated Red Hat support boundaries.

In plain Kubernetes, you often deploy a CSI driver manually using manifests or Helm. In OpenShift, many CSI drivers are installed or managed using **CSI Driver Operators**.

### OpenShift-specific points

- Many platform CSI drivers are deployed in the namespace:

```bash
openshift-cluster-csi-drivers
```

- The snapshot controller is managed by the OpenShift cluster storage/operator layer.
- OpenShift may install a default CSI driver, driver Operator, and StorageClass depending on platform type.
- OpenShift enforces Security Context Constraints, so node-level CSI pods often need privileged permissions.
- OpenShift cluster operators report health through `oc get co`.
- CSI issues may show up under operators such as:

```bash
oc get co storage
oc get co csi-snapshot-controller
```

Depending on the OpenShift version and platform, supported CSI drivers and features differ. Always check the exact OpenShift documentation for your version and storage backend.

## 5. Core CSI Architecture

A CSI deployment normally has two major parts:

1. **Controller plugin**
2. **Node plugin**

### 5.1 Controller Plugin

The controller plugin usually runs as a `Deployment` or `StatefulSet`.

It handles cluster-level operations such as:

- Create volume
- Delete volume
- Attach volume
- Detach volume
- Create snapshot
- Delete snapshot
- Expand volume
- Create volume from snapshot
- Create clone from PVC

The controller plugin usually contains:

- CSI driver container
- `external-provisioner`
- `external-attacher`
- `external-snapshotter`
- `external-resizer`
- `livenessprobe`

Example controller pod inspection:

```bash
oc get pods -n openshift-cluster-csi-drivers
oc describe pod <csi-controller-pod> -n openshift-cluster-csi-drivers
oc logs <csi-controller-pod> -c csi-driver -n openshift-cluster-csi-drivers
oc logs <csi-controller-pod> -c csi-provisioner -n openshift-cluster-csi-drivers
oc logs <csi-controller-pod> -c csi-attacher -n openshift-cluster-csi-drivers
```

### 5.2 Node Plugin

The node plugin usually runs as a `DaemonSet`, one pod per node.

It handles node-level operations such as:

- Register driver with kubelet
- Stage volume on node
- Publish volume into pod path
- Unpublish volume
- Unstage volume
- Expand filesystem on node
- Mount block device or filesystem

The node plugin usually contains:

- CSI driver container
- `node-driver-registrar`
- `livenessprobe`

Example node plugin inspection:

```bash
oc get ds -n openshift-cluster-csi-drivers
oc get pods -n openshift-cluster-csi-drivers -o wide
oc logs <csi-node-pod> -c csi-driver -n openshift-cluster-csi-drivers
oc logs <csi-node-pod> -c csi-node-driver-registrar -n openshift-cluster-csi-drivers
```

### 5.3 Important CSI Sidecars

| Sidecar | Runs In | Main Job |
|---|---|---|
| `external-provisioner` | Controller | Watches PVCs and calls `CreateVolume` / `DeleteVolume`. |
| `external-attacher` | Controller | Watches `VolumeAttachment` and calls `ControllerPublishVolume` / `ControllerUnpublishVolume`. |
| `external-snapshotter` | Controller | Handles snapshot create/delete operations with snapshot APIs. |
| `external-resizer` | Controller | Handles PVC expansion and calls expansion operations. |
| `node-driver-registrar` | Node | Registers CSI driver with kubelet on each node. |
| `livenessprobe` | Controller/Node | Helps Kubernetes restart unhealthy CSI pods. |

### 5.4 CSI RPC Calls You Should Recognize

| CSI Operation | Meaning |
|---|---|
| `CreateVolume` | Backend creates a new disk/share/volume. |
| `DeleteVolume` | Backend deletes the volume. |
| `ControllerPublishVolume` | Attach volume to a node. |
| `ControllerUnpublishVolume` | Detach volume from a node. |
| `NodeStageVolume` | Prepare volume on the node, often mount to a staging path. |
| `NodePublishVolume` | Mount or bind-mount volume into the pod path. |
| `NodeUnpublishVolume` | Remove volume from pod path. |
| `NodeUnstageVolume` | Remove volume from staging path. |
| `CreateSnapshot` | Create backend snapshot. |
| `DeleteSnapshot` | Delete backend snapshot. |
| `ControllerExpandVolume` | Expand backend volume size. |
| `NodeExpandVolume` | Expand filesystem or node-visible volume. |

### 5.5 Important Paths on Nodes

CSI drivers commonly interact with kubelet paths such as:

```text
/var/lib/kubelet/plugins/<driver-name>/
/var/lib/kubelet/plugins_registry/
/var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~csi/
/var/lib/kubelet/pods/<pod-uid>/volume-subpaths/
```

On OpenShift nodes, inspect carefully using `oc debug node`:

```bash
oc debug node/<node-name>
chroot /host
mount | grep csi
findmnt | grep kubelet
ls -l /var/lib/kubelet/plugins
ls -l /var/lib/kubelet/plugins_registry
```

Do not delete kubelet volume paths manually unless you are following a vendor or Red Hat recovery procedure. Manual cleanup can corrupt mounts or break pod volume state.

- `provisioner`
- `parameters`
- `reclaimPolicy`
- `allowVolumeExpansion`


A cluster-scoped representation of actual storage.

```bash
oc get pv

```

Cluster-scoped object that tells Kubernetes how to interact with a CSI driver.

```bash
oc get csidriver
```

## 7. PVC-to-Pod Mount Flow

When a developer creates a PVC and uses it in a pod, many things happen behind the scenes.

### Step-by-step flow

```text
1. User creates PVC
2. PVC references a StorageClass
3. external-provisioner watches PVC
4. external-provisioner calls CSI CreateVolume
5. Storage backend creates actual volume
6. external-provisioner creates PV
7. PVC binds to PV
8. Pod is scheduled
9. attach/detach controller creates VolumeAttachment if driver needs attach
10. external-attacher calls ControllerPublishVolume
11. kubelet asks CSI node plugin to stage volume
12. kubelet asks CSI node plugin to publish volume into pod path
13. Container sees mounted volume
```

### What to check at each stage

| Stage | Command |
|---|---|
| PVC request | `oc describe pvc <pvc> -n <ns>` |
| StorageClass | `oc describe sc <sc>` |
| PV object | `oc get pv; oc describe pv <pv>` |
| Provisioner logs | `oc logs <controller-pod> -c csi-provisioner` |
| Attach status | `oc get volumeattachment` |
| Attacher logs | `oc logs <controller-pod> -c csi-attacher` |
| Node plugin logs | `oc logs <node-pod> -c csi-driver` |
| Kubelet logs | `oc adm node-logs <node> -u kubelet` |
| Mount state | `oc debug node/<node>; chroot /host; findmnt` |

## 8. StorageClass Deep Dive

A `StorageClass` is the main policy object that controls dynamic provisioning.

### Example StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-csi
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: example.csi.vendor.com
parameters:
  type: ssd
  fsType: xfs
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
mountOptions:
  - noatime
```

### 8.1 `provisioner`

The `provisioner` value must match the CSI driver name.

Example:

```bash
oc get sc -o custom-columns=NAME:.metadata.name,PROVISIONER:.provisioner
oc get csidriver
```

If the StorageClass provisioner does not match any installed CSI driver, PVCs will stay `Pending`.

### 8.2 `parameters`

Parameters are backend-specific.

Examples:

- disk type
- IOPS tier
- filesystem type
- storage pool
- datastore
- availability zone
- encrypted volume setting
- NFS share client rules
- secret references

Never assume parameters are portable across CSI drivers. A StorageClass for AWS EBS is not compatible with Azure Disk or vSphere.

### 8.3 `reclaimPolicy`

Controls what happens to the PV/backend volume when the PVC is deleted.

| Policy | Meaning | Production Use |
|---|---|---|
| `Delete` | Delete PV and backend volume. | Good for disposable app data. Dangerous for critical data if used casually. |
| `Retain` | Keep PV and backend volume. | Safer for critical workloads, manual recovery, forensic analysis. |

For backup-critical applications, understand the reclaim policy before deleting a PVC.

### 8.4 `allowVolumeExpansion`

Allows PVC size increase.

```yaml
allowVolumeExpansion: true
```

Expansion depends on:

- StorageClass allowing expansion
- CSI driver supporting expansion
- backend supporting expansion
- volume mode and filesystem support
- pod/node behavior

### 8.5 `volumeBindingMode`

| Mode | Behavior |
|---|---|
| `Immediate` | Provision volume as soon as PVC is created. |
| `WaitForFirstConsumer` | Wait until a pod using the PVC is scheduled, then provision based on node/topology. |

For zonal block storage, `WaitForFirstConsumer` is usually safer because the scheduler can align pod placement and volume topology.

### 8.6 Default StorageClass

Check default class:

```bash
oc get sc
oc get sc -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.annotations.storageclass\.kubernetes\.io/is-default-class}{"\n"}{end}'
```

Set default:

```bash
oc annotate storageclass <sc-name> storageclass.kubernetes.io/is-default-class=true --overwrite
```

Remove default from another class:

```bash
oc annotate storageclass <old-sc> storageclass.kubernetes.io/is-default-class- --overwrite
```

Be careful: multiple default StorageClasses can cause unpredictable behavior for new PVCs without `storageClassName`.

## 9. Access Modes and Volume Modes

### 9.1 Access Modes

| Access Mode | Meaning | Typical Backend |
|---|---|---|
| `ReadWriteOnce` / `RWO` | One node can mount read-write. Multiple pods on same node may use it. | Cloud block disks, RBD, vSphere disk. |
| `ReadOnlyMany` / `ROX` | Many nodes can mount read-only. | NFS, CephFS, some snapshots/clones. |
| `ReadWriteMany` / `RWX` | Many nodes can mount read-write. | NFS, CephFS, Azure File, Manila, EFS. |
| `ReadWriteOncePod` / `RWOP` | One pod only can mount read-write. | CSI-supported drivers in newer Kubernetes versions. |

### 9.2 Volume Modes

| Volume Mode | Meaning |
|---|---|
| `Filesystem` | Volume is formatted and mounted as a filesystem. Default for most PVCs. |
| `Block` | Raw block device is exposed to the pod. Useful for databases or specialized apps. |

Example raw block PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: raw-block-pvc
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Block
  resources:
    requests:
      storage: 20Gi
  storageClassName: fast-csi
```

Pod using raw block:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: block-test
spec:
  containers:
    - name: app
      image: registry.access.redhat.com/ubi9/ubi
      command: ["sleep", "3600"]
      volumeDevices:
        - name: data
          devicePath: /dev/xvda
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: raw-block-pvc
```

## 10. Dynamic vs Static Provisioning

### 10.1 Dynamic Provisioning

Dynamic provisioning means the CSI driver creates the backend volume automatically when a PVC is created.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-csi
  resources:
    requests:
      storage: 10Gi
```

Dynamic provisioning is the common OpenShift model.

### 10.2 Static Provisioning

Static provisioning means an administrator creates a PV that points to an existing backend volume.

Useful when:

- importing old data
- recovering retained volumes
- using pre-created SAN/NAS resources
- restoring from storage-level backup outside Kubernetes

Example CSI static PV skeleton:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: static-csi-pv
spec:
  capacity:
    storage: 100Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: static-csi
  csi:
    driver: example.csi.vendor.com
    volumeHandle: backend-volume-id-12345
    fsType: xfs
```

Static PVs are powerful but risky. The `volumeHandle` must point to the correct backend object. Wrong mapping can expose wrong data to a project.

## 11. Volume Binding Mode and Topology

Topology-aware provisioning is critical for cloud and virtualized storage.

### 11.1 Why topology matters

A volume may exist only in one zone, region, datastore, failure domain, or storage pool. If a pod is scheduled to a node that cannot access that volume, the mount fails.

Examples:

- AWS EBS volume in `ap-south-1a` cannot attach to node in `ap-south-1b`.
- Azure Disk has zone constraints.
- vSphere datastore accessibility depends on host cluster/datastore configuration.
- Local/LVM volumes are tied to a node or volume group.

### 11.2 Immediate vs WaitForFirstConsumer

With `Immediate`, the volume is provisioned before pod scheduling. The scheduler later has to find a node that matches the volume's topology.

With `WaitForFirstConsumer`, provisioning waits until pod scheduling. This allows scheduler and CSI provisioner to choose a volume location compatible with the selected node.

### 11.3 Useful troubleshooting commands

```bash
oc describe pvc <pvc> -n <ns>
oc describe pod <pod> -n <ns>
oc get pv <pv> -o yaml | grep -A20 nodeAffinity
oc get nodes --show-labels | grep topology
oc get sc <sc> -o yaml | grep volumeBindingMode
```

Common topology event examples:

```text
0/6 nodes are available: node(s) had volume node affinity conflict
volume node affinity conflict
waiting for first consumer to be created before binding
```

## 12. CSI Snapshots and Backup Awareness

CSI snapshots are a key part of OpenShift backup awareness, but they are not a complete backup strategy by themselves.

### 12.1 What is a VolumeSnapshot?

A `VolumeSnapshot` is a point-in-time copy of a volume's state, represented through Kubernetes/OpenShift snapshot APIs.

It involves:

- `VolumeSnapshotClass`
- `VolumeSnapshot`
- `VolumeSnapshotContent`
- CSI snapshot controller
- CSI external snapshotter sidecar
- backend storage snapshot object

### 12.2 Snapshot flow

```text
1. Admin creates VolumeSnapshotClass
2. User creates VolumeSnapshot for a PVC
3. Snapshot controller watches VolumeSnapshot
4. Snapshot controller binds VolumeSnapshot to VolumeSnapshotContent
5. external-snapshotter calls CSI CreateSnapshot
6. Storage backend creates real snapshot
7. VolumeSnapshot status becomes readyToUse: true
```

### 12.3 VolumeSnapshotClass example

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: fast-csi-snapclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: example.csi.vendor.com
deletionPolicy: Delete
parameters:
  snapshotType: crash-consistent
```

### 12.4 VolumeSnapshot example

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: app-data-snapshot-001
  namespace: app-prod
spec:
  volumeSnapshotClassName: fast-csi-snapclass
  source:
    persistentVolumeClaimName: app-data
```

Check:

```bash
oc get volumesnapshot -n app-prod
oc describe volumesnapshot app-data-snapshot-001 -n app-prod
oc get volumesnapshotcontent
```

### 12.5 Snapshot consistency levels

Not all snapshots are equal.

| Consistency Type | Meaning | Risk |
|---|---|---|
| Crash-consistent | Similar to pulling power from a VM/server. Filesystem may recover, app may need replay. | Usually okay for some filesystems, risky for databases without journaling/application handling. |
| Filesystem-consistent | Filesystem buffers are flushed/frozen. | Better, but app-level transactions may still be inconsistent. |
| Application-consistent | Application is quiesced, transaction logs flushed, then snapshot taken. | Best for databases and critical apps. |

CSI itself usually provides crash-consistent backend snapshots unless combined with application hooks or backup tooling.

### 12.6 Snapshot is not equal to backup

A CSI snapshot is often stored in the same storage backend. If the backend fails, the snapshot may also be lost.

A production backup design should answer:

- Is the snapshot stored outside the primary failure domain?
- Can it survive storage backend deletion?
- Can it be copied to object storage?
- Is it encrypted?
- Is it immutable?
- Is it tested through restore drills?
- Does it include Kubernetes objects as well as volume data?
- Are secrets/configmaps/routes/operators/custom resources included?
- What is the RPO and RTO?

### 12.7 When snapshots are useful

- Before application upgrade
- Before database schema migration
- Before risky configuration change
- Before deleting/recreating StatefulSet
- Dev/test rollback
- Backup product integration
- Fast restore to another PVC

### 12.8 When snapshots are not enough

- Disaster recovery across sites
- Ransomware protection
- Full cluster rebuild
- Long-term retention
- Compliance backup
- Cross-cloud migration
- Application-consistent database backups unless proper hooks are used

## 13. Restore from Snapshot

A snapshot can be restored by creating a new PVC with `dataSource` pointing to the `VolumeSnapshot`.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-restored
  namespace: app-prod
spec:
  storageClassName: fast-csi
  dataSource:
    name: app-data-snapshot-001
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

Important restore rules:

- Restored PVC size must be equal to or larger than snapshot source size.
- StorageClass must be compatible with the snapshot driver.
- Snapshot must be `readyToUse: true`.
- Application should be stopped or carefully reconfigured before switching PVCs.
- For StatefulSets, PVC names are tied to pod identity; plan restore carefully.

Check snapshot readiness:

```bash
oc get volumesnapshot <snap> -n <ns> -o jsonpath='{.status.readyToUse}{"\n"}'
```

## 14. PVC Cloning

PVC cloning creates a new PVC from an existing PVC.

### Clone example

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-clone
  namespace: app-prod
spec:
  storageClassName: fast-csi
  dataSource:
    name: app-data
    kind: PersistentVolumeClaim
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

### Clone requirements commonly include

- Source PVC must be `Bound`.
- Source and target usually need to be in the same namespace.
- StorageClass compatibility is required.
- Target size must be equal to or larger than source.
- CSI driver must support cloning.

### Snapshot vs clone

| Feature | Snapshot | Clone |
|---|---|---|
| Source | PVC -> snapshot object | PVC -> PVC |
| Use case | Backup/restore point | Copy data for test/dev |
| Retention | Can be retained independently depending on policy | Clone is a live PVC |
| API objects | VolumeSnapshot, VolumeSnapshotContent | PVC only with dataSource |

## 15. Volume Expansion

Volume expansion allows increasing PVC size after creation.

### Expansion example

Original PVC:

```yaml
resources:
  requests:
    storage: 10Gi
```

Patch to 20Gi:

```bash
oc patch pvc app-data -n app-prod -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

Watch status:

```bash
oc get pvc app-data -n app-prod -w
oc describe pvc app-data -n app-prod
```

### Expansion flow

```text
1. Admin/user increases PVC requested storage
2. external-resizer detects change
3. CSI driver expands backend volume
4. PV capacity updates
5. kubelet performs NodeExpandVolume if filesystem expansion is needed
6. PVC status becomes normal after filesystem resize
```

### Common expansion issues

| Symptom | Possible Cause |
|---|---|
| PVC size not increasing | `allowVolumeExpansion` is false. |
| Controller expansion done but filesystem not resized | Pod/node needs remount or kubelet node expansion pending. |
| Expansion event shows unsupported | CSI driver or backend does not support expansion. |
| Application still sees old size | Filesystem resize pending or pod needs restart depending on driver/filesystem. |

Check:

```bash
oc describe sc <sc>
oc describe pvc <pvc> -n <ns>
oc get pv <pv> -o yaml | grep -A10 capacity
oc logs <csi-controller-pod> -c csi-resizer -n openshift-cluster-csi-drivers
oc adm node-logs <node> -u kubelet | grep -i expand
```

Never shrink a PVC. Kubernetes supports increasing requested storage, not shrinking existing volumes.

## 16. Inline Ephemeral CSI Volumes

CSI inline ephemeral volumes are temporary volumes defined directly inside a pod spec. They follow the pod lifecycle.

Use cases:

- scratch storage
- temporary secrets from external systems
- short-lived test volumes
- special vendor-provided runtime storage

They are not a replacement for PVCs when data must survive pod deletion.

Example skeleton:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ephemeral-csi-test
spec:
  containers:
    - name: app
      image: registry.access.redhat.com/ubi9/ubi
      command: ["sleep", "3600"]
      volumeMounts:
        - name: ephemeral-data
          mountPath: /data
  volumes:
    - name: ephemeral-data
      csi:
        driver: example.csi.vendor.com
        volumeAttributes:
          size: "1Gi"
```

Support depends on the CSI driver and OpenShift version.

## 17. Security, SCC, RBAC, and Credentials

CSI drivers are security-sensitive because they may:

- run privileged pods
- mount host paths
- use bidirectional mount propagation
- talk to backend storage APIs
- hold credentials for cloud or storage arrays
- create/delete production volumes
- attach/detach disks to nodes

### 17.1 Controller credentials

Controller pods often need backend credentials to create/delete/attach/detach volumes.

Best practices:

- Store credentials in OpenShift `Secret` objects.
- Restrict secret access to CSI controller service accounts.
- Run controller pods on infra nodes where possible.
- Use cloud IAM roles/workload identity when supported.
- Rotate credentials periodically.
- Monitor failed authentication events in CSI logs.

### 17.2 Node plugin privileges

Node plugins often require:

- privileged SCC
- hostPath access
- mount propagation
- access to `/var/lib/kubelet`
- device access for block volumes

Check SCC usage:

```bash
oc get pod <csi-node-pod> -n openshift-cluster-csi-drivers -o yaml | grep openshift.io/scc
oc adm policy who-can use scc/privileged
```

### 17.3 RBAC

CSI sidecars need permissions to watch/update resources such as:

- PVCs
- PVs
- Pods
- Nodes
- CSINodes
- VolumeAttachments
- VolumeSnapshots
- VolumeSnapshotContents
- Events
- Secrets, if StorageClass parameters reference secrets

Troubleshoot RBAC:

```bash
oc auth can-i get secrets --as system:serviceaccount:<ns>:<sa> -n <secret-ns>
oc auth can-i update persistentvolumes --as system:serviceaccount:<ns>:<sa>
oc describe clusterrole <role>
oc describe clusterrolebinding <binding>
```

### 17.4 Namespace separation

Application teams should usually not have direct access to CSI driver namespaces or backend credentials.

Recommended separation:

| Responsibility | Team |
|---|---|
| StorageClass creation | Platform/storage admin |
| PVC creation | Application team |
| SnapshotClass creation | Platform/storage admin |
| Snapshot creation | App team or backup operator, depending on policy |
| Backend credential management | Platform/storage/security admin |
| Backup policy | Platform/SRE/application owner |

## 19. Backup Design: What CSI Does and Does Not Do

CSI provides storage primitives. A backup solution must orchestrate those primitives safely.

### 19.1 CSI can provide

- volume provisioning
- attach/detach
- mount/unmount
- snapshots
- restore from snapshot
- clone
- resize

### 19.2 CSI does not automatically provide

- application-consistent backup
- cross-cluster restore workflow
- long-term retention
- object storage copy
- encryption policy by itself
- immutable backup
- Kubernetes object backup
- application dependency mapping
- scheduled backup policy
- restore validation

### 19.3 Production backup layers

A strong OpenShift backup design usually includes:

1. **Kubernetes object backup**
   - Deployments
   - StatefulSets
   - ConfigMaps
   - Secrets
   - Routes
   - Services
   - Operators and CRs
   - RBAC

2. **Persistent volume data backup**
   - CSI snapshots
   - file-level backup
   - database-native backup
   - storage replication
   - object storage copy

3. **Application consistency hooks**
   - pre-backup quiesce
   - freeze filesystem
   - flush database logs
   - post-backup unfreeze

4. **Restore process**
   - restore objects
   - restore PVCs
   - validate mounts
   - validate app health
   - run data integrity checks

### 19.4 Database backup warning

For databases such as MySQL, PostgreSQL, MongoDB, Oracle, or MariaDB, do not depend only on crash-consistent CSI snapshots unless the application owner accepts that risk.

Better patterns:

- database-native dump or physical backup
- WAL/binlog/archive log backup
- pre/post hooks to quiesce writes
- operator-native backup if using a database Operator
- snapshot plus transaction log replay
- regular restore drills

### 19.5 RPO and RTO

| Term | Meaning | CSI Relevance |
|---|---|---|
| RPO | Maximum acceptable data loss. | Snapshot schedule influences RPO. |
| RTO | Maximum acceptable recovery time. | Snapshot restore speed influences RTO. |

Example:

```text
RPO = 15 minutes means you need backup/snapshot frequency that can limit data loss to 15 minutes.
RTO = 30 minutes means the restore process must bring the application back within 30 minutes.
```

## 23. Common Failure Scenarios

### Scenario 1: PVC stuck in Pending

Symptoms:

```bash
oc get pvc -n app-prod
# NAME       STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
# app-data   Pending                                      fast-csi
```

Possible causes:

- StorageClass does not exist.
- StorageClass provisioner does not match installed CSI driver.
- CSI provisioner pod is down.
- Backend credentials invalid.
- Backend capacity exhausted.
- Namespace ResourceQuota blocks PVC storage request.
- `WaitForFirstConsumer` and no pod is using the PVC yet.
- Topology cannot be satisfied.

Commands:

```bash
oc describe pvc app-data -n app-prod
oc get sc fast-csi -o yaml
oc get pods -n openshift-cluster-csi-drivers
oc logs <controller-pod> -c csi-provisioner -n openshift-cluster-csi-drivers
oc describe quota -n app-prod
```

### Scenario 2: Pod stuck ContainerCreating due to mount failure

Symptoms:

```text
MountVolume.MountDevice failed
NodePublishVolume failed
permission denied
mount failed: exit status 32
```

Possible causes:

- CSI node plugin not running on that node.
- Kubelet cannot reach CSI socket.
- Backend volume not attached.
- Filesystem issue.
- Wrong mount options.
- SELinux/SCC issue.
- Node kernel module missing.
- NFS/Ceph endpoint unreachable.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get pods -n openshift-cluster-csi-drivers -o wide | grep <node>
oc logs <csi-node-pod> -c csi-driver -n openshift-cluster-csi-drivers
oc adm node-logs <node> -u kubelet | grep -i mount
oc debug node/<node>
```

### Scenario 3: Multi-Attach error

Symptoms:

```text
Multi-Attach error for volume "pvc-xxxx" Volume is already used by pod(s) ...
```

Possible causes:

- RWO volume attached to one node, pod rescheduled to another.
- Old node NotReady and detach did not complete.
- Storage backend has stale attachment.
- Stateful workload scaled incorrectly.

Commands:

```bash
oc get pod -A -o wide | grep <pvc-or-app>
oc get volumeattachment
oc describe volumeattachment <name>
oc get nodes
oc describe node <old-node>
```

Safe handling:

1. Confirm old pod is terminated.
2. Confirm old node state.
3. Check backend attachment.
4. Let attach/detach controller reconcile if possible.
5. Force detach only using documented storage vendor/Red Hat procedure.

### Scenario 4: Snapshot not ready

Symptoms:

```bash
oc get volumesnapshot -n app-prod
# READYTOUSE false
```

Possible causes:

- CSI driver does not support snapshots.
- Missing VolumeSnapshotClass.
- Wrong snapshot driver name.
- Snapshot controller unhealthy.
- External snapshotter sidecar missing.
- Backend snapshot failed.
- Source PVC is not bound.

Commands:

```bash
oc describe volumesnapshot <snap> -n app-prod
oc get volumesnapshotclass
oc get volumesnapshotcontent
oc get co csi-snapshot-controller
oc logs <controller-pod> -c csi-snapshotter -n openshift-cluster-csi-drivers
```

### Scenario 5: Restore PVC from snapshot fails

Possible causes:

- Snapshot not ready.
- Restore PVC size smaller than snapshot source.
- Wrong StorageClass.
- SnapshotClass driver and StorageClass provisioner mismatch.
- Backend snapshot deleted but Kubernetes object still exists.

Commands:

```bash
oc get volumesnapshot <snap> -n <ns> -o yaml
oc describe pvc <restore-pvc> -n <ns>
oc describe volumesnapshotcontent <vsc>
```

### Scenario 6: PVC expansion stuck

Possible causes:

- StorageClass does not allow expansion.
- CSI driver does not support expansion.
- Backend quota reached.
- Node expansion pending.
- Filesystem does not support online resize.
- Pod needs restart depending on driver/filesystem.

Commands:

```bash
oc describe sc <sc>
oc describe pvc <pvc> -n <ns>
oc logs <controller-pod> -c csi-resizer -n openshift-cluster-csi-drivers
oc adm node-logs <node> -u kubelet | grep -i expand
```

### Scenario 7: StorageClass default confusion

Symptoms:

- PVC without `storageClassName` gets wrong backend.
- Multiple StorageClasses are marked default.
- Application lands on slow/incorrect storage.

Commands:

```bash
oc get sc
oc get sc -o yaml | grep -B5 -A5 is-default-class
```

Fix:

```bash
oc annotate sc <wrong-default> storageclass.kubernetes.io/is-default-class- --overwrite
oc annotate sc <correct-default> storageclass.kubernetes.io/is-default-class=true --overwrite
```

### Scenario 8: Volume stuck Terminating due to finalizer

Symptoms:

```bash
oc get pvc -n app-prod
# app-data Terminating
```

Possible causes:

- Pod still using PVC.
- PV protection finalizer waiting.
- CSI driver cannot delete backend volume.
- Snapshot or clone dependency exists.

Commands:

```bash
oc get pod -n app-prod -o wide | grep app-data
oc describe pvc app-data -n app-prod
oc get pv <pv> -o yaml | grep finalizers -A5
oc logs <controller-pod> -c csi-provisioner -n openshift-cluster-csi-drivers
```

Do not remove finalizers casually. Removing a finalizer can orphan backend storage or hide a failed delete operation.

## 24. Performance and Reliability Considerations

### 24.1 Match storage backend to workload

| Workload | Preferred Storage Pattern |
|---|---|
| Stateless web app | No PVC or small RWX if shared files needed. |
| Database | Low-latency RWO block storage, tested IOPS. |
| Shared content | RWX storage such as CephFS/NFS/Azure File/EFS/Manila. |
| Logging | High throughput storage, retention policy, careful expansion. |
| CI/CD workspace | Ephemeral or dynamic PVC, cleanup policy. |
| AI/ML data | High throughput RWX/object storage, cache design. |

### 24.2 Filesystem choice

Common filesystems:

- XFS
- ext4

Consider:

- online resize support
- application requirements
- mount options
- journaling behavior
- performance under many small files
- storage backend recommendation

### 24.3 IOPS and throughput

PVC size alone does not guarantee performance.

Check backend-specific rules:

- cloud disk IOPS may depend on size/type
- shared file systems may throttle metadata operations
- Ceph pools need sufficient OSD resources
- vSphere datastore latency affects all volumes
- NFS server network and export settings matter

### 24.4 High availability

For critical CSI drivers:

- Controller deployments should have HA replicas if supported.
- Leader election should be enabled for sidecars.
- Node DaemonSet must run on all eligible worker nodes.
- Driver pods should tolerate required taints.
- Monitor CSI pods and storage backend health.

### 24.5 Monitoring signals

Monitor:

- PVC pending count
- PV failed/released count
- CSI pod restarts
- provisioning latency
- attach latency
- mount failures
- snapshot failure count
- backend capacity
- backend latency
- cloud API throttling

## 26. Best Practices

### 26.1 StorageClass best practices

- Use clear names such as `gold-rwo`, `silver-rwx`, `odf-rbd`, `odf-cephfs`, `vsphere-thin-csi`.
- Do not keep multiple default StorageClasses unless intentionally supported and understood.
- Use `WaitForFirstConsumer` for topology-sensitive block storage.
- Enable expansion only where tested.
- Use `Retain` for highly critical manual-recovery workloads where accidental delete risk is high.
- Document every StorageClass parameter.

### 26.2 PVC best practices

- Always specify `storageClassName` for production apps.
- Avoid relying on cluster default for critical workloads.
- Size volumes based on application growth and backend performance behavior.
- Set quotas to prevent namespace-level storage abuse.
- Monitor PVC usage from inside the pod and from backend.

### 26.3 Snapshot best practices

- Treat snapshots as fast restore points, not always as full backups.
- Use application hooks for databases.
- Test restore regularly.
- Document `VolumeSnapshotClass` deletion policy.
- Use naming with timestamp and application context.

Example naming:

```text
mysql-prod-data-2026-07-03-pre-upgrade
app1-content-2026-07-03-before-release-42
```

### 26.4 Security best practices

- Restrict access to CSI namespaces.
- Do not give application teams access to backend credentials.
- Audit who can create/delete snapshots.
- Audit who can delete PVC/PV objects.
- Use encryption at rest where supported.
- Rotate storage backend credentials.

### 26.5 Troubleshooting best practices

- Start with events, not guesses.
- Trace PVC -> PV -> VolumeAttachment -> CSI logs -> kubelet -> backend.
- Do not delete finalizers unless you understand the backend impact.
- Do not manually detach volumes without confirming pod/node state.
- Always collect logs before destructive recovery steps.

## 27. Interview / Exam Style Questions

### Q1. What is the role of a CSI driver in OpenShift?

A CSI driver allows OpenShift to provision, attach, mount, snapshot, clone, and expand persistent storage from an external backend using a standard interface.

### Q2. What is the difference between the CSI controller plugin and node plugin?

The controller plugin handles cluster-level operations such as volume creation, deletion, attach, detach, snapshot, and resize. The node plugin runs on each node and handles staging/publishing/mounting volumes into pods.

### Q3. Which sidecar provisions volumes from PVCs?

`external-provisioner`.

### Q4. Which object is used to track attach/detach status?

`VolumeAttachment`.

### Q5. Why is `WaitForFirstConsumer` useful?

It delays volume provisioning until pod scheduling so topology-sensitive storage can be created in a location compatible with the selected node.

### Q6. Is a CSI snapshot a complete backup?

No. A CSI snapshot is a point-in-time storage snapshot. It may not include Kubernetes objects, may not be application-consistent, and may live in the same failure domain as the original volume.

### Q7. How do you restore a PVC from a snapshot?

Create a new PVC with `dataSource` referencing the `VolumeSnapshot`.

### Q8. What do you check when PVC is stuck Pending?

Check PVC events, StorageClass, provisioner name, CSI controller pods, namespace quota, backend capacity, and topology constraints.

### Q9. What causes Multi-Attach errors?

Usually an RWO volume is still attached to one node while a pod tries to use it on another node, often after node failure or rescheduling.

### Q10. Why do CSI node pods often need privileged permissions?

They need host access for device handling, mount operations, kubelet plugin registration, and bidirectional mount propagation.

- StorageClass used
- Access mode
- Volume mode
- Expansion support
- Snapshot support
- Backup schedule
- Restore procedure
- RPO/RTO
- Application-consistency method
- Owner/team contact
- Backend storage mapping
