# Snapshot-based Restore in OpenShift

**Area:** Storage and Backup Awareness  
**Level:** Advanced OpenShift Administration / 10+ years production operations perspective  
**Focus:** CSI `VolumeSnapshot` restore, PVC recovery, workload cutover, application consistency, OADP integration, troubleshooting, and production-grade runbooks

---

## 1. What is Snapshot-based Restore?

**Snapshot-based restore** is the process of recovering persistent application data from a previously captured point-in-time storage snapshot.

In OpenShift and Kubernetes, this usually means:

1. A PVC is snapshotted using a CSI `VolumeSnapshot`.
2. The snapshot becomes `readyToUse`.
3. A **new PVC** is created with `spec.dataSource` pointing to that `VolumeSnapshot`.
4. The CSI driver provisions a new backend volume pre-populated with snapshot data.
5. The application is reattached, redeployed, or cut over to the restored PVC.

A key production point:

> In the standard Kubernetes CSI snapshot workflow, restore usually means **provision a new PVC from a snapshot**, not directly overwrite the existing PVC in place.

Some storage systems have backend-native “revert” operations, but the portable Kubernetes/OpenShift pattern is **restore as a new claim** and then perform an application cutover.

---

## 2. Why Snapshot-based Restore Matters

For an OpenShift administrator, snapshot-based restore is important because it provides a fast recovery option for stateful workloads.

Common use cases:

- Recover from accidental file deletion.
- Roll back failed application upgrades.
- Recover a database volume before a bad schema migration.
- Clone production-like data into a test namespace.
- Restore VM disks in OpenShift Virtualization.
- Reduce RTO for stateful applications.
- Validate backups without impacting the original workload.
- Provide a safety point before risky changes.

Snapshot restore is usually faster than file-level backup restore because it uses storage-backend capabilities such as copy-on-write, cloning, or backend snapshot metadata.

However, snapshots are **not automatically a full backup strategy**. If the snapshot remains on the same storage array, same cluster, same failure domain, or same thin pool, it may not protect against storage backend failure, ransomware, accidental snapshot deletion, or site loss.

## 3. Important Terminology

| Term | Meaning |
|---|---|
| `PersistentVolumeClaim` / PVC | Namespace-scoped request for storage used by a pod. |
| `PersistentVolume` / PV | Cluster-scoped volume object bound to a PVC. |
| `StorageClass` | Defines dynamic provisioning behavior for PVCs. |
| CSI driver | Storage plugin implementing Container Storage Interface operations. |
| `VolumeSnapshotClass` | Snapshot equivalent of `StorageClass`; defines driver and snapshot deletion behavior. |
| `VolumeSnapshot` | Namespace-scoped request for a snapshot of a PVC. |
| `VolumeSnapshotContent` | Cluster-scoped object representing the actual backend snapshot. |
| `readyToUse` | Snapshot status indicating it is ready for restore. |
| `restoreSize` | Minimum/suggested size reported by the snapshot for restored PVC creation. |
| `snapshotHandle` | Backend snapshot identifier known to the CSI driver. |
| Crash-consistent | Snapshot resembles disk state after sudden power loss. |
| Application-consistent | Application has flushed data and metadata before snapshot capture. |
| OADP | OpenShift API for Data Protection, Red Hat’s supported Velero-based backup/restore solution. |

---

## 4. Mental Model: Snapshot Restore is Storage Recovery, Not Full Application Recovery

A snapshot restore recovers **volume data**. It does not automatically recover everything that makes an application work.

A full application recovery may also require:

- Deployments, StatefulSets, Services, Routes, Ingress, ConfigMaps, Secrets.
- ServiceAccounts, SCC/RBAC bindings, NetworkPolicies.
- Operators and custom resources.
- Database credentials and application config.
- Correct DNS/Route behavior.
- Image pull secrets.
- Correct namespace labels, quotas, and LimitRanges.
- Recreated PVC references in workload manifests.

For this reason, snapshot-based restore should be treated as one layer in a broader data protection plan.

## 6. Snapshot Creation Lifecycle

Before understanding restore, understand snapshot creation.

### 6.1 Dynamic snapshot creation

A user creates a `VolumeSnapshot`:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: app-data-snap-2026-07-03
  namespace: app-prod
spec:
  volumeSnapshotClassName: ocs-storagecluster-rbdplugin-snapclass
  source:
    persistentVolumeClaimName: app-data
```

The snapshot controller:

1. Watches the `VolumeSnapshot`.
2. Creates a matching `VolumeSnapshotContent`.
3. Binds `VolumeSnapshot` and `VolumeSnapshotContent` one-to-one.
4. The CSI snapshotter asks the CSI driver to create the backend snapshot.
5. The driver records the backend `snapshotHandle`.
6. Status becomes `readyToUse: true` when the snapshot can be restored.

Check status:

```bash
oc get volumesnapshot -n app-prod
oc describe volumesnapshot app-data-snap-2026-07-03 -n app-prod
oc get volumesnapshotcontent
```

Useful JSONPath:

```bash
oc get volumesnapshot app-data-snap-2026-07-03 -n app-prod \
  -o jsonpath='{.status.readyToUse}{"\n"}'

oc get volumesnapshot app-data-snap-2026-07-03 -n app-prod \
  -o jsonpath='{.status.restoreSize}{"\n"}'

oc get volumesnapshot app-data-snap-2026-07-03 -n app-prod \
  -o jsonpath='{.status.boundVolumeSnapshotContentName}{"\n"}'
```

## 7. Restore Lifecycle

Snapshot restore is driven by a new PVC that references the snapshot as a data source.

### 7.1 Restore PVC example

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-restore-20260703
  namespace: app-prod
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  dataSource:
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: app-data-snap-2026-07-03
```

When this PVC is created:

```text
PVC with dataSource
   |
   v
External provisioner notices dataSource=VolumeSnapshot
   |
   v
CSI CreateVolume called with VolumeContentSource=snapshot
   |
   v
Storage backend creates new volume from snapshot
   |
   v
PV created and bound
   |
   v
Pod can mount restored PVC
```

### 7.2 Important restore behavior

- The restored PVC is a new object.
- The restored backend volume is independent of the source PVC.
- Deleting the original PVC does not automatically delete the restored PVC.
- Deleting the snapshot does not normally delete an already restored PVC.
- The restored PVC must use a compatible `StorageClass` and CSI driver.
- The restored PVC size should normally be equal to or greater than the snapshot `restoreSize`. Some drivers or products require the exact same size first, then expansion after restore.
- The restored volume mode must be compatible with the original snapshot, unless the cluster and snapshot content explicitly permit volume mode conversion.

## 8. Snapshot-based Restore vs Backup Restore

| Area | Snapshot-based restore | Traditional backup restore |
|---|---|---|
| Speed | Usually fast | Usually slower |
| Data movement | Often backend-local | Usually reads/writes backup data |
| Failure-domain protection | Often same backend unless exported | Can be off-cluster/off-site |
| Granularity | Volume-level | File/object/app-level depending on tool |
| App manifests | Not restored by raw VolumeSnapshot | Usually restored by OADP/Velero-style tools |
| Best use | Fast rollback, clone, pre-change safety | Disaster recovery, long-term retention |
| Risk | Same storage failure domain | Backup repository integrity required |

Production recommendation:

> Use snapshots for fast local recovery, but use OADP/data mover/object storage/replication for real backup and disaster recovery.

## 10. Basic Restore Runbook: Single PVC

Scenario:

- Namespace: `app-prod`
- Original PVC: `app-data`
- Snapshot: `app-data-snap-2026-07-03`
- Restored PVC: `app-data-restore-20260703`
- StorageClass: `ocs-storagecluster-ceph-rbd`

### Step 1: Verify snapshot

```bash
oc get volumesnapshot app-data-snap-2026-07-03 -n app-prod
oc describe volumesnapshot app-data-snap-2026-07-03 -n app-prod
```

Confirm:

```text
readyToUse: true
```

### Step 2: Check restore size

```bash
oc get volumesnapshot app-data-snap-2026-07-03 -n app-prod \
  -o jsonpath='{.status.restoreSize}{"\n"}'
```

Use this value for the restored PVC size unless your CSI driver documentation says otherwise.

### Step 3: Create restored PVC

```bash
cat <<'EOF' | oc apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-restore-20260703
  namespace: app-prod
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  dataSource:
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: app-data-snap-2026-07-03
EOF
```

### Step 4: Wait for restored PVC to bind

```bash
oc get pvc app-data-restore-20260703 -n app-prod -w
oc describe pvc app-data-restore-20260703 -n app-prod
```

Expected:

```text
STATUS: Bound
```

### Step 5: Mount restored PVC into validation pod

```bash
cat <<'EOF' | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: restore-validator
  namespace: app-prod
spec:
  restartPolicy: Never
  containers:
    - name: validator
      image: registry.access.redhat.com/ubi9/ubi:latest
      command: ["/bin/bash", "-c", "sleep 3600"]
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: restored-data
          mountPath: /restore
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  volumes:
    - name: restored-data
      persistentVolumeClaim:
        claimName: app-data-restore-20260703
EOF
```

Check pod:

```bash
oc wait --for=condition=Ready pod/restore-validator -n app-prod --timeout=120s
oc rsh -n app-prod restore-validator ls -lah /restore
```

### Step 6: Validate data

Examples:

```bash
oc rsh -n app-prod restore-validator find /restore -maxdepth 2 -type f | head
oc rsh -n app-prod restore-validator du -sh /restore
oc rsh -n app-prod restore-validator cat /restore/version.txt
```

### Step 7: Cut over application

How you cut over depends on the workload type:

- Deployment: change pod template to use restored PVC.
- StatefulSet: restore each ordinal PVC carefully or recreate with existing restored PVCs.
- Operator-managed database: use operator-supported restore method first if available.
- VM: use OpenShift Virtualization snapshot/restore workflow if it is a VM disk.

### Step 8: Clean validation pod

```bash
oc delete pod restore-validator -n app-prod
```

Do not delete the restored PVC until the application owner confirms recovery is complete.

## 11. Deployment Restore Pattern

A Deployment using a manually referenced PVC is the easiest restore scenario.

Original deployment volume:

```yaml
volumes:
  - name: app-data
    persistentVolumeClaim:
      claimName: app-data
```

Patch to restored PVC:

```bash
oc scale deployment/myapp -n app-prod --replicas=0

oc patch deployment/myapp -n app-prod --type=json \
  -p='[
    {"op":"replace","path":"/spec/template/spec/volumes/0/persistentVolumeClaim/claimName","value":"app-data-restore-20260703"}
  ]'

oc scale deployment/myapp -n app-prod --replicas=1
oc rollout status deployment/myapp -n app-prod
```

Important:

- Ensure the volume index is correct before patching.
- Prefer GitOps update instead of manual patch in production.
- For RWO storage, ensure the old pod is fully terminated before the new pod mounts the restored claim.

Safer manual edit:

```bash
oc edit deployment/myapp -n app-prod
```

Then change:

```yaml
claimName: app-data-restore-20260703
```

## 12. StatefulSet Restore Pattern

StatefulSets need extra care because PVCs are usually generated from `volumeClaimTemplates`.

PVC names follow this pattern:

```text
<volumeClaimTemplate-name>-<statefulset-name>-<ordinal>
```

Example:

```text
data-postgres-0
data-postgres-1
data-postgres-2
```

### 12.1 Why StatefulSet restore is tricky

`volumeClaimTemplates` are mostly immutable after creation. You usually cannot simply patch the StatefulSet template to point to another PVC name like a Deployment.

For a 10-year-experience administrator, the safe restore decision depends on the workload:

1. Is it a single-replica StatefulSet?
2. Is it a replicated database with its own replication/recovery mechanism?
3. Is the operator responsible for backup/restore?
4. Are all PVCs restored from the same consistent point?
5. Are PVC names expected by the StatefulSet controller?

### 12.2 Single-replica StatefulSet restore approach

Assume:

```text
StatefulSet: postgres
PVC: data-postgres-0
Snapshot: data-postgres-0-snap
Restored PVC temporary name: data-postgres-0-restore
```

High-level steps:

1. Scale StatefulSet to 0.
2. Restore snapshot into a new PVC.
3. Validate restored PVC.
4. Preserve old PVC by renaming is not possible directly; Kubernetes object names are immutable.
5. Choose a cutover strategy:
   - Recreate StatefulSet with a different claim reference if manually controlled.
   - Delete old PVC and recreate a PVC with the original expected name from the snapshot.
   - Use operator-supported recovery if operator-managed.

### 12.3 Recreate expected PVC name from snapshot

This is a common emergency pattern when the StatefulSet expects `data-postgres-0`.

**Warning:** Do not do this unless you have a confirmed snapshot and a rollback plan.

```bash
oc scale sts/postgres -n db-prod --replicas=0
oc wait --for=delete pod/postgres-0 -n db-prod --timeout=120s

# Preserve old PVC by making sure PV reclaim policy and backups are understood.
oc get pvc data-postgres-0 -n db-prod -o yaml > old-data-postgres-0-pvc.yaml
oc get pv $(oc get pvc data-postgres-0 -n db-prod -o jsonpath='{.spec.volumeName}') -o yaml > old-data-postgres-0-pv.yaml

# Delete old PVC only after approval.
oc delete pvc data-postgres-0 -n db-prod
```

Recreate PVC with the same expected name from snapshot:

```bash
cat <<'EOF' | oc apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-postgres-0
  namespace: db-prod
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 100Gi
  dataSource:
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: data-postgres-0-snap
EOF
```

Wait:

```bash
oc get pvc data-postgres-0 -n db-prod -w
```

Start workload:

```bash
oc scale sts/postgres -n db-prod --replicas=1
oc rollout status sts/postgres -n db-prod
```

### 12.4 Multi-replica StatefulSet warning

For databases such as PostgreSQL, MySQL, MongoDB, Kafka, Cassandra, Elasticsearch, and Redis Cluster, do not blindly restore all PVCs from independent snapshots unless you understand consistency across replicas.

Often better options:

- Use the database/operator-native backup and restore mechanism.
- Restore one primary volume and rebuild replicas.
- Use a VolumeGroupSnapshot if the CSI driver and OpenShift version support it.
- Quiesce the application and snapshot all PVCs at the same logical point.
- Restore into an isolated namespace first, verify, then cut over.

## 13. Application Consistency

### 13.1 Crash-consistent vs application-consistent

A storage snapshot can capture disk blocks at a point in time, but the application may still have:

- Dirty pages in memory.
- Unflushed database transactions.
- Partially written files.
- WAL/binlog/redo logs still being written.
- Multiple PVCs not captured at exactly the same instant.

That means a raw volume snapshot is often **crash-consistent**, not necessarily **application-consistent**.

Crash-consistent means:

> The restored data looks like the system lost power at that moment.

Application-consistent means:

> The application was prepared for backup: writes paused, buffers flushed, database checkpoint completed, filesystem frozen if needed, and then snapshot captured.

### 13.2 How to make snapshots more consistent

Common approaches:

#### Option A: Scale down workload

```bash
oc scale deployment/myapp -n app-prod --replicas=0
# create snapshot
oc scale deployment/myapp -n app-prod --replicas=1
```

Pros:

- Simple.
- Good for many file-based apps.

Cons:

- Causes downtime.
- Not suitable for all databases or HA systems.

#### Option B: Application quiesce hooks

Examples:

- PostgreSQL: `pg_start_backup` / `pg_backup_start` style workflows, checkpoint, WAL archiving, or operator backup.
- MySQL/MariaDB: `FLUSH TABLES WITH READ LOCK`, filesystem freeze, or backup lock depending on version/engine.
- MongoDB: `fsyncLock`/`fsyncUnlock` only with care; better use database-native backup.
- Filesystem: `fsfreeze` if supported and safe.

#### Option C: Operator-native backup

Many stateful Operators provide supported backup/restore flows. Prefer them when available because they understand application semantics.

Examples:

- Crunchy Postgres Operator backup/restore.
- Percona operators.
- MongoDB Enterprise/Community operator workflows.
- AMQ/Kafka operator-supported backup guidance.
- OpenShift Virtualization VM snapshots with guest-agent-assisted freeze.

#### Option D: OADP with hooks

Use OADP/Velero backup hooks to run pre/post commands around backup.

Example idea:

```text
pre-hook:  put app into read-only mode / flush DB
snapshot:  CSI snapshot taken
post-hook: resume writes
```

## 15. PostgreSQL Example: Restore Considerations

For PostgreSQL, a crash-consistent volume snapshot may recover using WAL replay, but that depends on:

- WAL and data directory consistency.
- Whether WAL is on the same PVC or another PVC.
- Whether all related volumes were snapped together.
- Whether PostgreSQL was cleanly stopped or checkpointed.

Safer approaches:

1. Use PostgreSQL operator backup/restore.
2. Stop PostgreSQL cleanly, snapshot, restart.
3. Ensure WAL volume and data volume are captured consistently.
4. Restore to isolated namespace and run integrity checks before cutover.

Validation commands inside PostgreSQL pod may include:

```bash
pg_isready
psql -c 'select now();'
psql -c '\l'
```

If restore fails with corruption or missing WAL, do not repeatedly start the database against the same restored PVC. Preserve evidence, clone another restore PVC from the same snapshot, and troubleshoot carefully.

## 16. Multi-volume Restore and VolumeGroupSnapshot

Applications often use multiple PVCs:

```text
Database data PVC
Database WAL/log PVC
Search index PVC
Object cache PVC
```

If each PVC is snapshotted separately, the restore point may not be logically consistent.

### 16.1 Problem with independent snapshots

Example:

```text
10:00:00 - data PVC snapshot starts
10:00:03 - transaction commits
10:00:05 - log PVC snapshot starts
```

The restored data and logs may represent different points in time.

### 16.2 VolumeGroupSnapshot concept

A `VolumeGroupSnapshot` groups multiple PVCs using a label selector and requests snapshots for the group.

Conceptual flow:

```text
PVC data       label group=mydb
PVC wal        label group=mydb
PVC index      label group=mydb
      \          |          /
       \         |         /
        VolumeGroupSnapshot
              |
              v
   Individual VolumeSnapshots
              |
              v
   Restore each PVC from its matching snapshot
```

### 16.3 Example group snapshot class

```yaml
apiVersion: groupsnapshot.storage.k8s.io/v1beta1
kind: VolumeGroupSnapshotClass
metadata:
  name: odf-rbd-groupsnapclass
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Delete
```

### 16.4 Label PVCs

```bash
oc label pvc db-data -n db-prod snapshot-group=mydb
oc label pvc db-wal  -n db-prod snapshot-group=mydb
```

### 16.5 Create group snapshot

```yaml
apiVersion: groupsnapshot.storage.k8s.io/v1beta1
kind: VolumeGroupSnapshot
metadata:
  name: mydb-groupsnap-20260703
  namespace: db-prod
spec:
  volumeGroupSnapshotClassName: odf-rbd-groupsnapclass
  source:
    selector:
      matchLabels:
        snapshot-group: mydb
```

### 16.6 Restore from group snapshot

A group snapshot usually produces individual `VolumeSnapshot` objects. Restore each required PVC using those individual snapshot names:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data-restore
  namespace: db-prod
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 100Gi
  dataSource:
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: snapshot-for-db-data
```

Repeat for `db-wal-restore`, `db-index-restore`, and other volumes.

### 16.7 Production warning

A group snapshot improves multi-volume crash consistency, but it still does not automatically make the application logically consistent unless application writes are quiesced or the application can recover from crash-consistent storage state.

## 17. OADP and Snapshot-based Restore

OADP provides backup and restore for OpenShift applications using Velero-based components. It can protect:

- Kubernetes/OpenShift objects.
- Namespaced resources.
- Internal images depending on configuration.
- PV data using snapshots, Restic, Kopia, or data mover approaches depending on OADP version and configuration.

### 17.1 Raw CSI snapshots vs OADP

| Requirement | Raw `VolumeSnapshot` | OADP |
|---|---|---|
| Restore only PVC data | Yes | Yes |
| Restore Deployments/Services/Routes | No | Yes |
| Namespace-level backup | Manual | Yes |
| Object storage repository | No by itself | Yes |
| Hooks | Manual/custom | Supported through backup hooks |
| Scheduling | Manual/Cron/custom | Backup schedules available |
| Cross-cluster recovery | Limited/backend-specific | Better suited |

### 17.2 When to use raw snapshots

Use raw snapshots when:

- You need a quick pre-change restore point.
- You are troubleshooting one PVC.
- You need to clone data for test.
- You are practicing storage operations.
- The application manifests are already managed by GitOps.

### 17.3 When to use OADP

Use OADP when:

- You need namespace/application restore.
- You need scheduled backups.
- You need backup metadata in object storage.
- You need restore into another cluster.
- You need application resources plus volume data.
- You need a more auditable backup system.

### 17.4 OADP restore mental model

```text
Backup CR
   |
   +-- Kubernetes objects stored in backup location
   |
   +-- PV data handled by snapshot/restic/kopia/data mover

Restore CR
   |
   +-- Recreates Kubernetes objects
   |
   +-- Recreates PVCs and binds restored data
   |
   +-- Restores app namespace/resources
```

OADP still needs careful validation. Restoring application YAML does not guarantee application-level consistency unless the backup was taken consistently.

## 18. OpenShift Virtualization Snapshot Restore

OpenShift Virtualization has its own VM snapshot objects and workflows. VM snapshots can include:

- VM specification and metadata.
- CSI-backed VM disks.
- DataVolume/PVC disk state.

For online VM snapshots, guest-agent integration can help freeze/thaw the filesystem. This is more application-aware than a blind PVC snapshot, but the actual guarantee still depends on guest OS, agent health, workload, and storage backend behavior.

For VM workloads, prefer the OpenShift Virtualization snapshot/restore workflow rather than manually snapshotting VM PVCs unless you have a specific low-level recovery requirement.

## 19. Important Storage Backend Caveats

### 19.1 OpenShift Data Foundation / Ceph RBD

When restoring RBD snapshots, consider:

- Restore storage class should be compatible with the original pool.
- Encryption compatibility matters.
- RBD snapshots and clones can increase backend dependency chains.
- Long-lived snapshots may increase space usage.
- Deleting snapshots may not immediately reclaim expected capacity.
- Watch Ceph health and pool capacity.

### 19.2 File storage / RWX volumes

For RWX volumes, restore support depends on the CSI driver.

Questions to ask:

- Does the CSI driver support snapshots for RWX volumes?
- Is snapshot restore supported for the same access mode?
- Are restored file permissions preserved?
- Are SELinux labels and ownership valid after restore?
- Is the restored PVC mounted by multiple pods safely?

### 19.3 Thin-provisioned storage

Thin-provisioned backends need monitoring.

Risks:

- Snapshot growth due to copy-on-write changes.
- Pool exhaustion.
- Restore provisioning failure.
- Snapshot deletion delays.
- Performance degradation during heavy clone/restore operations.

### 19.4 Local storage

Local PVs generally have limited snapshot/restore portability. If snapshots are node-local, they may not protect against node failure.

### 19.5 Cloud storage

Cloud CSI snapshots may be region/zone-bound. Restoring into another zone or region may need provider-specific snapshot copy or restore behavior.

## 20. Access Modes and Restore

Access modes matter during restore.

| Access mode | Restore consideration |
|---|---|
| RWO | Old pod must release old/new volume before mount; common for block storage. |
| RWX | Multiple pods may mount restored PVC, but app-level consistency still matters. |
| ROX | Useful for read-only restore validation. |
| RWOP | Only one pod can use PVC cluster-wide; ensure strict cutover. |

If your original PVC is `ReadWriteOnce`, do not expect old and new pods to concurrently mount the same claim. The restored PVC is separate, but each claim still follows its own access mode rules.

## 21. Volume Mode and Restore

PVCs can use:

```yaml
volumeMode: Filesystem
```

or:

```yaml
volumeMode: Block
```

Restore volume mode should normally match the source snapshot.

Filesystem example:

```yaml
spec:
  volumeMode: Filesystem
```

Block example:

```yaml
spec:
  volumeMode: Block
```

Block-mode restores are common for VM disks and some high-performance databases. Not every backup/data movement path supports block and filesystem equally, so validate with your storage/OADP version.

## 22. Namespace and Cross-namespace Restore

A standard `VolumeSnapshot` is namespace-scoped. A PVC data source normally references a snapshot in the same namespace.

For cross-namespace scenarios:

- Prefer OADP restore into target namespace.
- Use storage backend copy/export/import if supported.
- Use pre-provisioned `VolumeSnapshotContent` only with cluster-admin-level care.
- Validate RBAC and data exposure risks.

Do not casually expose production snapshots to development namespaces. Snapshots may contain secrets, customer data, tokens, database credentials, and regulated information.

## 23. Security and RBAC

Snapshot permissions should be controlled.

Useful API groups:

```text
snapshot.storage.k8s.io
```

Resources:

```text
volumesnapshots
volumesnapshotcontents
volumesnapshotclasses
```

Typical separation:

| Role | Permission |
|---|---|
| App developer | Create/list/get `VolumeSnapshot` in own namespace if allowed. |
| Namespace admin | Restore PVCs from approved snapshots. |
| Storage admin | Manage `VolumeSnapshotClass` and backend policy. |
| Cluster admin | Manage `VolumeSnapshotContent`, recovery imports, retained snapshots. |

Example role for namespace snapshot users:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: snapshot-user
  namespace: app-prod
rules:
  - apiGroups: ["snapshot.storage.k8s.io"]
    resources: ["volumesnapshots"]
    verbs: ["get", "list", "watch", "create", "delete"]
  - apiGroups: [""]
    resources: ["persistentvolumeclaims"]
    verbs: ["get", "list", "watch", "create"]
```

Bind it:

```bash
oc adm policy add-role-to-user snapshot-user alice -n app-prod
```

Production rule:

> Do not give broad `VolumeSnapshotContent` permissions to application teams. It is cluster-scoped and can expose backend snapshot handles.

## 24. DeletionPolicy: Delete vs Retain

`VolumeSnapshotClass` controls deletion behavior:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-snapclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: example.csi.driver
deletionPolicy: Delete
```

### 24.1 Delete

If `deletionPolicy: Delete`:

- Deleting `VolumeSnapshot` can delete the underlying storage snapshot.
- Good for short-term snapshots.
- Lower risk of orphaned backend snapshots.

### 24.2 Retain

If `deletionPolicy: Retain`:

- Deleting `VolumeSnapshot` retains `VolumeSnapshotContent` and backend snapshot.
- Useful for disaster recovery workflows or manual imports.
- Requires cleanup discipline.
- Can create hidden storage consumption.

Check policy:

```bash
oc get volumesnapshotclass -o custom-columns=NAME:.metadata.name,DRIVER:.driver,POLICY:.deletionPolicy
```

## 25. Production Restore Checklist

Before restore:

```text
[ ] Incident/change ticket created.
[ ] Application owner confirms desired restore point.
[ ] Snapshot exists and is readyToUse=true.
[ ] restoreSize checked.
[ ] CSI driver and StorageClass compatibility confirmed.
[ ] Namespace quota has enough storage request capacity.

[ ] Secrets/config compatibility checked.

[ ] Rollback plan ready.
[ ] Validation commands prepared.
[ ] Old PVC preservation plan defined.
```

During restore:

```text
[ ] Create restored PVC from VolumeSnapshot.
[ ] Wait for PVC Bound.
[ ] Mount restored PVC in validation pod or isolated workload.
[ ] Validate data.
[ ] Scale down original workload if needed.
[ ] Cut over workload to restored PVC.
[ ] Watch rollout and logs.
[ ] Run application health checks.
```

After restore:

```text
[ ] Confirm business/application validation.
[ ] Keep old PVC until retention window expires.
[ ] Record snapshot, restored PVC, PV, and backend IDs.
[ ] Clean temporary validation pods.
[ ] Clean unneeded snapshots according to policy.
[ ] Update GitOps manifests if manual changes were made.
[ ] Document root cause and prevention.
```

## 27. Troubleshooting Snapshot Restore

### 27.1 PVC stuck Pending

Symptoms:

```bash
oc get pvc -n app-prod
```

Shows:

```text
STATUS: Pending
```

Check:

```bash
oc describe pvc app-data-restore-20260703 -n app-prod
oc get events -n app-prod --sort-by=.lastTimestamp
```

Common causes:

- Wrong `storageClassName`.
- Snapshot not `readyToUse`.
- Snapshot in different namespace.
- Restore size too small.
- CSI driver does not support restore from snapshot.
- Quota exceeded.
- Backend capacity exhausted.
- Topology/zone mismatch.
- Missing external provisioner or CSI controller issue.

Fix examples:

```bash
oc get volumesnapshot -n app-prod
oc describe volumesnapshot app-data-snap-2026-07-03 -n app-prod
oc describe quota -n app-prod
oc get sc
```

---

### 27.2 Error: dataSource not found

Cause:

- Snapshot name is wrong.
- Snapshot is in another namespace.
- API group/kind typo.

Correct form:

```yaml
dataSource:
  apiGroup: snapshot.storage.k8s.io
  kind: VolumeSnapshot
  name: app-data-snap-2026-07-03
```

---

### 27.3 Snapshot not ready

Check:

```bash
oc describe volumesnapshot <snapshot> -n <namespace>
oc get volumesnapshotcontent
```

Common causes:

- CSI snapshotter not healthy.
- Snapshot class driver mismatch.
- Source PVC not bound.
- Storage backend snapshot failed.
- Backend pool full.
- Volume mode not supported.

Check CSI pods:

```bash
oc get pods -A | grep -i csi
oc logs -n <csi-namespace> <csi-controller-pod> -c csi-snapshotter
oc logs -n <csi-namespace> <csi-controller-pod> -c csi-provisioner
```

---

### 27.4 Restore PVC bound but pod cannot mount

Check pod events:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common causes:

- RWO volume already attached elsewhere.
- Node affinity/topology conflict.
- CSI node plugin issue.
- Filesystem corruption.
- SELinux/permission issue.
- Incorrect `volumeMode`.

Check volume attachments:

```bash
oc get volumeattachment
```

---

### 27.5 Restored app starts with old/wrong config

Snapshot restore only restored data. Check:

```bash
oc get configmap,secret -n app-prod
oc describe deployment/myapp -n app-prod
oc set env deployment/myapp --list -n app-prod
```

You may have restored data from time T1 but config from time T2. That mismatch can break applications.

---

### 27.6 Restore successful but database inconsistent

Symptoms:

- Database crash loop.
- WAL/redo/binlog errors.
- Missing transaction logs.
- Corruption messages.

Actions:

1. Stop the workload to avoid further writes.
2. Preserve logs.
3. Do not delete the restored PVC.
4. Restore a second copy from the same snapshot for forensic testing.
5. Use database recovery tools.
6. Consider restoring from application-consistent backup instead.

---

### 27.7 VolumeSnapshotContent stuck terminating

Check finalizers:

```bash
oc get volumesnapshotcontent <name> -o yaml
```

Do not remove finalizers blindly. Finalizers protect against deleting objects while backend cleanup or references still exist.

Only after confirming there are no active references:

```bash
oc patch volumesnapshotcontent <name> --type=merge -p '{"metadata":{"finalizers":null}}'
```

Use this only as a last resort.

## 29. Restore Decision Tree

```text
Need to recover data?
 |
 +-- Is it a single PVC app?
 |      |
 |      +-- yes -> Restore snapshot to new PVC -> validate -> patch workload
 |      +-- no  -> continue
 |
 +-- Is it StatefulSet/operator DB?
 |      |
 |      +-- operator has restore feature? -> use operator-supported restore
 |      +-- no -> restore into isolated namespace first
 |
 +-- Multiple PVCs must match same point in time?
 |      |
 |      +-- yes -> use VolumeGroupSnapshot or app quiesce + coordinated snapshots
 |      +-- no  -> individual PVC restore may be acceptable
 |
 +-- Need full namespace/resources too?
 |      |
 |      +-- yes -> use OADP restore
 |      +-- no  -> raw VolumeSnapshot restore is enough
 |
 +-- Need site-loss protection?
        |
        +-- yes -> snapshots alone are not enough; use OADP/data mover/offsite backup
```

## 30. Real Production Example: Failed Upgrade Rollback

Scenario:

- Application `payments-api` uses PVC `payments-data`.
- Upgrade caused data format issue.
- Snapshot exists from before upgrade.
- Need fast rollback.

### Step 1: Freeze current state for investigation

```bash
oc scale deploy/payments-api -n payments --replicas=0
```

Optional: snapshot broken current state too:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: payments-data-broken-after-upgrade
  namespace: payments
spec:
  volumeSnapshotClassName: ocs-storagecluster-rbdplugin-snapclass
  source:
    persistentVolumeClaimName: payments-data
```

### Step 2: Restore pre-upgrade snapshot

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: payments-data-preupgrade-restore
  namespace: payments
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 50Gi
  dataSource:
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: payments-data-before-upgrade
```

### Step 3: Validate restored data

```bash
oc run restore-check -n payments --image=registry.access.redhat.com/ubi9/ubi:latest \
  --restart=Never --command -- sleep 3600
```

For a real validation pod, mount the restored PVC using YAML as shown earlier.

### Step 4: Roll back deployment image/config

```bash
oc rollout undo deployment/payments-api -n payments
```

### Step 5: Patch PVC reference

```bash
oc edit deployment/payments-api -n payments
```

Change:

```yaml
claimName: payments-data-preupgrade-restore
```

### Step 6: Start and verify

```bash
oc scale deploy/payments-api -n payments --replicas=3
oc rollout status deploy/payments-api -n payments
oc logs deploy/payments-api -n payments --tail=100
```

## 31. Performance and Capacity Considerations

### 31.1 Restore speed

Restore speed depends on:

- Storage backend snapshot implementation.
- Full copy vs clone-on-write behavior.
- Volume size.
- Changed data since snapshot.
- Backend load.
- Network and node attach latency.
- Filesystem check/replay time.
- Application startup recovery time.

### 31.2 RTO reality

A snapshot may restore quickly, but application RTO includes:

```text
Time to identify correct snapshot
+ time to create PVC
+ time to bind and attach volume
+ time to validate data
+ time to cut over workload
+ time for app/database recovery
+ time for business validation
```

Do not advertise storage snapshot time as full application recovery time.

### 31.3 Capacity risk

Snapshots consume space as data changes. On copy-on-write systems, heavy writes after snapshot creation may increase snapshot space usage.

Monitor:

- Backend pool usage.
- Snapshot count.
- Snapshot age.
- Clone dependency chains.
- Restore storm impact.
- Namespace storage quota.

## 32. GitOps Considerations

Manual restore operations can drift from Git.

If workloads are managed by Argo CD/OpenShift GitOps:

- Patch Git manifests, not only live cluster resources.
- Or temporarily pause sync during emergency restore.
- Record restored PVC name in Git.
- Avoid Argo CD reverting your emergency PVC reference.

Example risk:

```text
Admin patches deployment to use restored PVC.
Argo CD syncs original manifest.
Application switches back to bad PVC.
```

Mitigation:

```bash
argocd app suspend <app>
# or update Git immediately and sync intentionally
```

Use your organization’s approved GitOps process.

## 35. Exam / Interview Style Points

If asked, “How do you restore data from a VolumeSnapshot in OpenShift?” answer like this:

1. Confirm CSI snapshot support and `VolumeSnapshotClass`.
2. Verify the snapshot is `readyToUse`.
3. Create a new PVC using `spec.dataSource` pointing to the `VolumeSnapshot`.
4. Wait for the restored PVC to become `Bound`.
5. Validate the data by mounting the restored PVC in a test pod or isolated workload.
6. Scale down or stop the affected workload.
7. Patch/recreate the workload to use the restored PVC.
8. Start application and validate health.
9. Keep old PVC until rollback window expires.
10. Clean up temporary resources and document the restore.

Short YAML to remember:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restored-pvc
spec:
  storageClassName: <storage-class>
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: <same-or-larger-size>
  dataSource:
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: <snapshot-name>
```

## 36. Common Mistakes

| Mistake | Impact | Better practice |
|---|---|---|
| Assuming snapshot restore modifies original PVC | No restore happens to existing workload | Create new PVC and cut over workload. |
| Restoring before `readyToUse=true` | PVC may stay pending/fail | Wait for snapshot readiness. |
| Wrong StorageClass | Provisioning failure | Use compatible CSI driver/storage class. |
| Size too small | PVC rejected or stuck | Use restoreSize or same source size. |
| Ignoring app consistency | Corrupt database restore | Quiesce app or use app-native backup. |
| Independent snapshots for multi-PVC DB | Logical inconsistency | Use VolumeGroupSnapshot or DB backup. |
| Deleting old PVC immediately | No rollback | Preserve old PVC until validation. |
| Manual patch under GitOps | GitOps reverts restore | Update Git/suspend sync. |
| Giving broad snapshot permissions | Data exposure | Use namespace-scoped RBAC. |
| Treating snapshots as DR backups | Site/storage failure risk | Export/copy backups off-cluster. |

## 38. Snapshot Restore with a Test Namespace

For safer validation, restore to a test namespace.

Important limitation: a normal PVC data source references a `VolumeSnapshot` in the same namespace. To validate in another namespace, use one of these options:

- Use OADP restore into a different namespace.
- Create a controlled copy/export through storage backend features.
- Use pre-provisioned `VolumeSnapshotContent` with admin control.
- Clone after restore if supported and allowed.
- Restore in original namespace and mount read-only validation pod if acceptable.

Never copy production data into a lower-security namespace without approval.

## 39. Snapshot Restore and Disaster Recovery

Snapshots help with local recovery but are not enough for disaster recovery unless they are replicated or moved out of the failure domain.

A complete DR design should answer:

- Are snapshots stored on the same array or replicated offsite?
- Can snapshots survive namespace deletion?
- Can snapshots survive cluster deletion?
- Can you restore to a different OpenShift cluster?
- Are the required `StorageClass` and CSI driver available in the target cluster?
- Are encryption keys available?
- Are application manifests backed up?
- Are routes/DNS/secrets restored safely?
- What is the tested RTO/RPO?

Recommended layered model:

```text
Layer 1: Local CSI snapshots for fast rollback
Layer 2: OADP backups for namespace/application recovery
Layer 3: Data mover/object storage/offsite copy for disaster recovery
Layer 4: Application-native backups for databases
Layer 5: Regular restore drills
```

## 40. Final Practical Summary

Snapshot-based restore in OpenShift is a powerful day-2 administration skill. The core idea is simple: create a new PVC from a `VolumeSnapshot` and point the application to it. The hard part is doing that safely in production.

A senior OpenShift administrator should always think beyond the YAML:

- Is the snapshot ready?
- Is it crash-consistent or application-consistent?
- Is the storage class compatible?
- Is the application single-volume or multi-volume?
- Is the workload Deployment, StatefulSet, Operator-managed database, or VM?
- Is GitOps going to revert manual changes?
- Is this a local rollback or a real DR restore?
- How will the data be validated?
- How will we roll back if the restore is bad?

The best restore is not the one that merely creates a PVC. The best restore is the one that brings the application back safely, predictably, and with evidence that the recovered data is correct.
