# Application-Consistent Backup in OpenShift

**Topic:** Storage and Backup Awareness  
**Audience:** Advanced OpenShift Administration / 10+ years Linux, DevOps, Kubernetes, OpenShift experience  
**Focus:** How to design, take, validate, restore, and troubleshoot application-consistent backups for stateful workloads on Red Hat OpenShift.

---

## 1. What is an Application-Consistent Backup?

An **application-consistent backup** is a backup where the application data is captured in a clean, recoverable, transactionally valid state.

In simple terms:

> The backup is not only a copy of files or PVC blocks. It is a copy taken after the application has flushed pending writes, completed or rolled back transactions, and reached a state from which it can recover without corruption or logical data loss.

For OpenShift administrators, this means you must think beyond `oc get pvc`, `VolumeSnapshot`, or OADP `Backup` status. A snapshot can be technically successful but still not be application-consistent.

Example:

- A PostgreSQL PVC snapshot taken while dirty pages are still in memory might be crash-consistent, not application-consistent.
- A MySQL backup taken without `FLUSH TABLES WITH READ LOCK`, backup lock, or a proper database-native backup tool can restore with corruption or missing transactions.
- A multi-PVC application can be inconsistent if PVC-A is snapped at 10:00:01 and PVC-B at 10:00:07 while writes are active.
- A Kubernetes object backup can restore Deployments, Services, Routes, ConfigMaps, and Secrets, but the application may still fail if the database files are not internally consistent.

Application consistency is achieved by coordinating the backup tool with the application.

## 2. Backup Consistency Levels

Understanding backup consistency levels is critical in production OpenShift environments.

| Consistency Level | Meaning | Example | Risk |
|---|---|---|---|
| File-level copy | Files are copied while app is running | `tar`, rsync, file-system backup | High risk for databases |
| Crash-consistent | Same as sudden power loss; storage captures blocks at a point in time | CSI snapshot without app hook | Usually recoverable for journaling DBs, but not ideal |
| File-system consistent | File system buffers are flushed/frozen | `fsfreeze` before snapshot | Better, but app memory may still contain unflushed state |
| Application-consistent | Application flushes transactions and enters safe backup mode | PostgreSQL checkpoint, MySQL backup lock, MongoDB fsync lock, app-specific quiesce | Preferred for production |
| Business-consistent | Multiple services/data stores captured at same logical business point | App + DB + message queue + object store coordinated | Required for complex enterprise apps |

### Key point for OpenShift

OpenShift storage snapshots are normally **storage-level** operations. They do not automatically understand your database transactions, application caches, queues, or distributed system state.

To make backups application-consistent, you usually need one or more of the following:

- Velero/OADP backup hooks
- Database-native backup tools
- CSI snapshots with pre/post hooks
- Application quiesce logic
- Operator-provided backup CRs
- Scheduled maintenance windows
- Write pause / read-only mode
- Multi-component backup orchestration
- Restore testing

## 3. Where Application-Consistent Backup Fits in OpenShift

OpenShift application backup commonly protects two categories of data:

### 3.1 Kubernetes and OpenShift objects

Examples:

- Namespace
- Deployment
- StatefulSet
- DaemonSet
- Service
- Route
- Ingress
- ConfigMap
- Secret
- ServiceAccount
- RoleBinding
- NetworkPolicy
- PVC object
- Operator custom resources
- ImageStreams

These are stored in the Kubernetes API server and etcd.

Application backup tools such as **OADP**, which is based on **Velero**, can back up application resources at namespace granularity and filter resources by namespace, label, or type.

### 3.2 Persistent application data

Examples:

- Database files on PVC
- Uploaded user files
- Logs that must be retained
- Search indexes
- Message queue data
- Object cache state
- Application-generated content

This data usually lives on PersistentVolumes.

OADP can protect PV data by using:

- CSI or cloud-native storage snapshots
- File System Backup using Restic or Kopia, depending on OADP version and configuration
- Storage provider integrations

However, none of these alone guarantees application consistency unless application writes are coordinated.

## 4. Application-Consistent vs OpenShift Cluster Backup

Do not confuse these two backup types.

### 4.1 Cluster backup

Cluster backup usually means backing up OpenShift control plane state, especially `etcd`.

It is used for:

- Control plane disaster recovery
- etcd quorum loss recovery
- Recovering cluster state after major failure

It is not an application-aware backup strategy.

### 4.2 Application backup

Application backup means backing up workloads and their data.

It is used for:

- Restoring a namespace
- Recovering a deleted application
- Migrating an application to another cluster
- Recovering from application data corruption
- Disaster recovery for business services

For application-consistent backup, focus on application data, transaction state, PVCs, related objects, and restore validation.

## 5. Core Components Used in OpenShift Application Backups

### 5.1 OADP

**OADP** stands for **OpenShift API for Data Protection**.

It provides OpenShift-supported APIs and operator-managed components for application backup and restore. OADP uses Velero underneath.

Important OADP resources:

| Resource | Purpose |
|---|---|
| `DataProtectionApplication` | Main OADP configuration CR |
| `Backup` | Defines what to back up |
| `Restore` | Defines what to restore |
| `Schedule` | Defines recurring backups |
| `BackupStorageLocation` | Object storage destination for backup metadata and archives |
| `VolumeSnapshotLocation` | Snapshot location for provider-native snapshots |

### 5.2 Velero

Velero performs the backup and restore workflow.

It can:

- Back up Kubernetes objects into object storage
- Snapshot PVs through cloud/CSI plugins
- Run backup hooks
- Run restore hooks
- Schedule recurring backups
- Restore resources into same or different namespaces
- Remap namespaces during restore

### 5.3 CSI snapshots

CSI snapshots use Kubernetes resources:

| Resource | Meaning |
|---|---|
| `VolumeSnapshot` | User request to snapshot a PVC |
| `VolumeSnapshotContent` | Actual snapshot object bound to the snapshot |
| `VolumeSnapshotClass` | Defines driver, deletion policy, and snapshot parameters |

CSI snapshots are storage-system snapshots. They are fast and efficient, but application consistency depends on pre-snapshot quiescing.

### 5.4 File System Backup: Restic / Kopia

File System Backup copies file contents from mounted volumes to object storage.

Use it when:

- Storage snapshot is unavailable
- Snapshot support is not configured
- The storage backend does not support CSI snapshots
- You need portability across storage providers

Considerations:

- Usually slower than snapshots
- More I/O intensive
- Requires node-agent or similar data movement components
- Application consistency still needs hooks or native application backup logic

### 5.5 Database-native backup tools

For serious production databases, native tools are usually preferred.

Examples:

| Application | Native backup approach |
|---|---|
| PostgreSQL | `pg_dump`, `pg_basebackup`, WAL archiving, `pg_start_backup`/backup API depending on version |
| MySQL/MariaDB | `mysqldump`, `mysqlbackup`, Percona XtraBackup, backup locks |
| MongoDB | `mongodump`, filesystem snapshot with `fsyncLock`, Ops Manager/Cloud Manager backup |
| Redis | `BGSAVE`, AOF persistence handling |
| Elasticsearch/OpenSearch | Repository snapshot API |
| Kafka | Replication + topic export + operator-aware backup, not simple PVC snapshot only |

For databases, a PVC snapshot alone is often not enough for guaranteed consistency.

## 6. The Main Principle: Quiesce, Capture, Resume

Application-consistent backup normally follows this sequence:

```text
1. Prepare / validate application health
2. Quiesce application writes
3. Flush application buffers to disk
4. Optionally freeze file system
5. Take backup or snapshot
6. Unfreeze file system
7. Resume writes
8. Validate backup status
9. Test restore
```

This is the most important mental model.

### Quiesce

Quiescing means temporarily making the application safe for backup.

Examples:

- Put app in maintenance mode
- Stop background workers
- Pause message consumers
- Disable writes
- Flush database transactions
- Lock tables briefly
- Trigger checkpoint
- Drain queues
- Stop cron jobs

### Capture

Capture means taking the backup.

Examples:

- OADP `Backup` CR
- Velero backup
- CSI `VolumeSnapshot`
- Storage array snapshot
- Restic/Kopia file backup
- Database dump/base backup

### Resume

Resume means safely restoring normal operation.

Examples:

- Unlock database
- Unfreeze file system
- Re-enable writes
- Resume consumers
- Restart background workers
- Exit maintenance mode

## 7. Why Crash-Consistent Backup Is Not Enough

A crash-consistent backup is similar to pulling the power cable from a server and copying the disk.

Modern databases can often recover from crash consistency using WAL, redo logs, journals, or transaction logs. But this is not guaranteed to satisfy business requirements.

Problems with crash-consistent backups:

- Uncommitted transactions may be rolled back
- Recently acknowledged writes might be missing if not flushed
- Multi-volume state may not match
- Application cache and DB state may diverge
- Message queue offset and DB transaction state may mismatch
- Search indexes may not match source database
- Restored app may require lengthy recovery
- Data corruption may appear only after restore

For enterprise OpenShift environments, crash consistency may be acceptable for low-risk stateless or cache workloads, but it is weak for databases and transactional systems.

## 8. OpenShift Backup Architecture for Application-Consistent Workloads

A production-grade architecture usually contains these layers:

```text

  ├── Quiesce API / maintenance mode
  ├── Pre-backup command
  ├── Post-backup command
  └── Health validation

  ├── Native backup command
  ├── Transaction checkpoint
  ├── WAL/binlog/archive handling

  ├── Namespace objects
  ├── Secrets and ConfigMaps
  ├── Routes and Services
  ├── StatefulSets and PVCs
  └── RBAC/SCC/NetworkPolicy

Data Protection Layer
  ├── OADP Operator
  ├── Velero server
  ├── Backup CR
  ├── Restore CR
  ├── Schedule CR
  ├── Backup hooks
  └── Restore hooks

Storage Layer
  ├── CSI driver
  ├── VolumeSnapshotClass
  ├── VolumeSnapshot
  ├── Object storage
  └── Snapshot backend / Restic / Kopia
```

## 9. Application-Consistent Backup Decision Matrix

| Workload Type | Recommended Backup Method | Application Consistency Method |
|---|---|---|
| Stateless web app | OADP object backup | No special quiesce needed |
| Web app with uploaded files | OADP + PV backup | Pause writes or app maintenance mode |
| PostgreSQL | Native DB backup + OADP metadata | Checkpoint/WAL/base backup logic |
| MySQL/MariaDB | Native dump/XtraBackup + OADP metadata | Backup lock / flush / binary log handling |
| MongoDB | Native dump or fsyncLock + snapshot | Replica-aware backup preferred |
| Redis | RDB/AOF-aware backup | `BGSAVE` / AOF fsync handling |
| Elasticsearch/OpenSearch | Snapshot repository API | Use cluster snapshot API, not raw PVC snapshot |
| Kafka | Replication/operator strategy | Avoid relying only on PVC snapshots |
| Single PVC file server | CSI snapshot or FSB | `fsfreeze` or app write pause |
| Multi-PVC app | Coordinated backup workflow | Quiesce all components before snapshots |
| Operator-managed app | Operator backup CR if available | Use vendor/operator-supported method |

## 11. What Not to Assume

Do not assume:

- A successful `Backup` CR means the application is consistent.
- A bound `VolumeSnapshot` means the database can recover cleanly.
- Restoring YAML objects means the app will be usable.
- All storage classes support snapshots.
- All CSI drivers support volume snapshots.
- All PVCs in a multi-volume app are snapped at the same logical time.
- Operators can be backed up like normal Deployments.
- Secrets copied to a new cluster will always work.
- Routes will work after cross-cluster restore without DNS/TLS review.
- Storage snapshot retention equals backup retention.

## 13. Example DataProtectionApplication Concept

Exact fields vary by OADP version and provider, but conceptually a DPA defines:

- Backup location
- Object storage bucket
- Provider plugin
- Credentials
- Snapshot configuration
- Node agent / file system backup settings
- Velero resource requests/limits

Example skeleton:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: ocp-app-backups
          prefix: prod-cluster-a
        config:
          region: us-east-1
          s3ForcePathStyle: "true"
          s3Url: https://s3.example.com
        credential:
          name: cloud-credentials
          key: cloud
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
    nodeAgent:
      enable: true
      uploaderType: kopia
```

> Always validate the supported DPA schema for your OADP version before applying production YAML.

## 14. CSI VolumeSnapshotClass Example

A `VolumeSnapshotClass` tells Kubernetes which CSI driver to use for snapshots.

Example for a CSI driver:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ocs-storagecluster-rbdplugin-snapclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Retain
parameters:
  clusterID: openshift-storage
  csi.storage.k8s.io/snapshotter-secret-name: rook-csi-rbd-provisioner
  csi.storage.k8s.io/snapshotter-secret-namespace: openshift-storage
```

### `deletionPolicy: Retain` vs `Delete`

| Policy | Meaning | Production Consideration |
|---|---|---|
| `Delete` | Deletes backend snapshot when `VolumeSnapshotContent` is deleted | Good for short retention and automated cleanup |
| `Retain` | Keeps backend snapshot after Kubernetes object deletion | Safer for DR, but requires manual lifecycle management |

For regulated environments, `Retain` is often safer, but it can create orphaned snapshots if not managed.

```yaml
  name: app1-backup-001

  includedNamespaces:
    - app1-prod
```

Apply:

```bash

```

Check:

```bash

velero backup logs app1-backup-001
```

This creates a backup, but by itself it is usually **not application-consistent** unless the application was quiesced or backup hooks were configured.

## 16. Backup Hooks: The Most Common App-Consistency Mechanism

Velero/OADP backup hooks let you run commands inside application pods before and after backup processing.

Use hooks for:

- Flushing DB buffers
- Triggering checkpoints
- Freezing file systems
- Locking writes
- Stopping workers
- Putting app into maintenance mode
- Running app-specific backup scripts
- Unfreezing/unlocking after snapshot

Two common ways to define hooks:

1. Pod annotations
2. Backup CR `hooks` section

---

## 17. Pod Annotation Hook Example

Example: freeze and unfreeze a file system before/after backup.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: file-app
  namespace: app1-prod
spec:
  replicas: 1
  selector:
    matchLabels:
      app: file-app
  template:
    metadata:
      labels:
        app: file-app
      annotations:
        pre.hook.backup.velero.io/container: app
        pre.hook.backup.velero.io/command: '["/bin/sh", "-c", "fsfreeze --freeze /data"]'
        pre.hook.backup.velero.io/timeout: 30s
        pre.hook.backup.velero.io/on-error: Fail
        post.hook.backup.velero.io/container: app
        post.hook.backup.velero.io/command: '["/bin/sh", "-c", "fsfreeze --unfreeze /data"]'
        post.hook.backup.velero.io/timeout: 30s
        post.hook.backup.velero.io/on-error: Fail
    spec:
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi
          command: ["/bin/sh", "-c", "sleep infinity"]
          volumeMounts:
            - name: data
              mountPath: /data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: file-app-pvc
```

Important:

- `fsfreeze` requires privileges/capabilities that many restricted pods do not have.
- On OpenShift, SCC restrictions may block this unless the pod is allowed appropriate privileges.
- Freezing a busy filesystem for too long can stall application I/O.
- Prefer application-native quiesce commands for databases.

## 18. Backup CR Hook Example

You can define hooks inside the `Backup` CR.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app1-consistent-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app1-prod
  snapshotVolumes: true
  hooks:
    resources:
      - name: app1-pre-post-hooks
        includedNamespaces:
          - app1-prod
        labelSelector:
          matchLabels:
            app: app1
        pre:
          - exec:
              container: app
              command:
                - /bin/sh
                - -c
                - /opt/app/bin/pre-backup.sh
              onError: Fail
              timeout: 60s
        post:
          - exec:
              container: app
              command:
                - /bin/sh
                - -c
                - /opt/app/bin/post-backup.sh
              onError: Fail
              timeout: 60s
```

This is better than annotations when backup logic should be controlled by the backup administrator rather than embedded into application manifests.

## 19. PostgreSQL Application-Consistent Backup Patterns

### Pattern A: Native logical backup

Use `pg_dump` or `pg_dumpall`.

Good for:

- Smaller databases
- Schema/data portability
- Migration between versions
- Selective restore

Example:

```bash
oc exec -n postgres-prod sts/postgres -- \
  bash -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" > /backup/app.dump'
```

Then back up the `/backup` PVC or upload dump to object storage.

Pros:

- Application-consistent
- Portable
- Easy to validate

Cons:

- Slow for large databases
- Restore can be slow
- May not capture roles/tablespaces unless handled

### Pattern B: Physical backup with WAL

Use:

- `pg_basebackup`
- WAL archiving
- Point-in-time recovery design

Better for:

- Large production databases
- PITR requirement
- Lower RPO

### Pattern C: Snapshot with PostgreSQL checkpoint

A simplified hook approach:

```yaml
pre:
  - exec:
      container: postgres
      command:
        - /bin/bash
        - -c
        - |
          psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "CHECKPOINT;"
      onError: Fail
      timeout: 60s
```

This improves crash recovery but is not always equal to a full PostgreSQL-native backup strategy.

For enterprise PostgreSQL, use operator-supported backup if the DB is managed by an Operator such as Crunchy, CloudNativePG, or another vendor-supported operator.

## 20. MySQL / MariaDB Application-Consistent Backup Patterns

### Pattern A: Logical dump

```bash
oc exec -n mysql-prod deploy/mysql -- \
  bash -c 'mysqldump --single-transaction --routines --triggers --events -u root -p"$MYSQL_ROOT_PASSWORD" appdb > /backup/appdb.sql'
```

`--single-transaction` is useful for InnoDB tables because it creates a consistent snapshot without locking all tables for the full dump duration.

### Pattern B: Backup lock / flush table lock + snapshot

For snapshot-based backup, a simplified flow is:

```text
1. Stop app writes or put app in maintenance mode
2. Flush tables
3. Acquire backup lock or read lock
4. Take storage snapshot
5. Release lock
6. Resume writes
```

Example pre-hook concept:

```bash
mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "FLUSH TABLES WITH READ LOCK; DO SLEEP(20);"
```

But this example is dangerous if the command session exits too soon or sleeps while another process takes the snapshot asynchronously. In production, use a carefully tested script that holds the lock until the snapshot is completed or use a native hot backup tool such as Percona XtraBackup or MySQL Enterprise Backup.

### Better approach

Use a script with lock coordination:

```text
pre-backup.sh  -> acquire lock, write lock state file, keep session alive
snapshot       -> OADP/CSI snapshot
post-backup.sh -> release lock safely
```

## 21. MongoDB Application-Consistent Backup Patterns

Recommended approaches:

- `mongodump` for logical backup
- MongoDB Ops Manager / Cloud Manager where available
- Replica set secondary backup
- Filesystem snapshot only with proper `fsyncLock`/quiesce design

Example logical dump:

```bash
oc exec -n mongo-prod sts/mongodb -- \
  bash -c 'mongodump --archive=/backup/mongo.archive --gzip'
```

Snapshot approach concept:

```text
1. Use replica set
2. Prefer snapshot from secondary
3. Run fsyncLock
4. Take snapshot
5. Run fsyncUnlock
```

Avoid taking random PVC snapshots of a busy MongoDB primary without app coordination.

## 22. Redis Application-Consistent Backup Patterns

Redis depends on configuration:

- RDB snapshot persistence
- AOF persistence
- Both
- Neither

Example pre-backup:

```bash
redis-cli BGSAVE
```

Then wait until save completes:

```bash
redis-cli INFO persistence | grep rdb_bgsave_in_progress
```

For AOF:

```bash
redis-cli BGREWRITEAOF
```

Application-consistent Redis backup usually means ensuring the persistence file is complete before the PVC backup or copying the generated RDB/AOF file to object storage.

## 23. Elasticsearch / OpenSearch

Do not rely on raw PVC snapshots as the primary backup method for Elasticsearch/OpenSearch clusters.

Use the built-in snapshot API with a supported repository:

- S3-compatible repository
- Azure repository
- GCS repository
- Shared filesystem repository where supported

Concept:

```bash
curl -X PUT "http://elasticsearch:9200/_snapshot/prod_repo/snapshot_001?wait_for_completion=true"
```

Why:

- Cluster metadata matters
- Shard state matters
- Index consistency matters
- Multiple nodes/PVCs must be coordinated

Back up OpenShift objects separately with OADP.

## 24. Kafka and Event Streaming Workloads

Kafka backup is not usually solved with simple PVC snapshots.

Challenges:

- Distributed logs across brokers
- Replication state
- Topic configuration
- Consumer offsets
- In-flight producer writes
- ZooKeeper/KRaft metadata
- Operator-managed resources

Better strategies:

- Multi-broker replication
- MirrorMaker 2 / Cluster Linking equivalent
- Topic configuration export
- Consumer group offset handling
- Operator-supported backup method
- Disaster recovery cluster design

PVC snapshots can be part of a recovery strategy, but do not treat them as sufficient application-consistent backup unless validated by the Kafka platform/vendor guidance.

## 25. Multi-PVC Applications

Multi-PVC consistency is a major advanced topic.

Example:

```text
Stateful app:
  pvc-data
  pvc-wal
  pvc-index
  pvc-config
```

If snapshots are taken independently, each PVC may represent a slightly different point in time.

Risks:

- WAL ahead of data
- Data ahead of index
- Metadata mismatch
- App refuses to start
- Silent logical corruption

Recommended approaches:

1. Quiesce the whole application.
2. Ensure all writes are stopped.
3. Flush all components.
4. Snapshot all PVCs as close together as possible.
5. Resume writes only after snapshots are complete.
6. Perform restore tests.

For true group consistency, verify whether your storage platform and OpenShift/Kubernetes version support coordinated group snapshots. Do not assume it.

## 26. StatefulSet-Specific Backup Considerations

StatefulSets need careful handling because they use stable identity.

Check:

```bash
oc get sts -n app1-prod
oc get pvc -n app1-prod
oc get pods -n app1-prod -o wide
```

Important objects:

- StatefulSet definition
- Headless Service
- PVCs created from `volumeClaimTemplates`
- ConfigMaps
- Secrets
- PodDisruptionBudget
- ServiceAccount
- NetworkPolicy

Restore concerns:

- PVC names must match expected pod ordinal names
- Headless service must exist
- DNS identity matters
- Restored pod may start before data is ready
- Init containers may need restore logic

Example PVC name pattern:

```text
data-postgres-0
data-postgres-1
data-postgres-2
```

Do not casually rename StatefulSet PVCs during restore.

## 27. Operator-Managed Applications

Operator-managed applications require extra care.

Examples:

- Databases managed by Operators
- OpenShift Data Foundation
- AMQ Streams / Kafka
- OpenShift GitOps
- Service Mesh
- Elasticsearch/OpenSearch
- Cloud Pak workloads

Rules:

1. Check vendor/operator backup documentation first.
2. Do not assume backing up Deployments and PVCs is enough.
3. Avoid blindly backing up/restoring Operators themselves with application data.
4. Back up custom resources that represent desired application state.
5. Use operator-native backup CRs if available.
6. Restore in the documented order.

Common restore order:

```text
1. Install required Operators on target cluster
2. Restore required CRDs if supported/required
3. Restore namespace metadata/RBAC/secrets/config
4. Restore application CRs
5. Restore PVC data
6. Let Operator reconcile
7. Validate health
```

## 28. Designing a Production Backup Policy

A mature backup policy defines:

| Area | Example Decision |
|---|---|
| Scope | Namespace, labels, PVCs, Secrets, Routes |
| Consistency | Crash, file-system, application, business |
| RPO | Maximum acceptable data loss, e.g. 15 minutes |
| RTO | Maximum restore time, e.g. 1 hour |
| Frequency | Hourly, daily, weekly |
| Retention | 7 daily, 4 weekly, 12 monthly |
| Location | Same cluster, same region, different region |
| Encryption | At rest and in transit |
| Immutability | Object lock / WORM if required |
| Access | Backup admin RBAC, namespace self-service |
| Validation | Scheduled restore tests |
| Audit | Backup logs, restore evidence |

---

## 29. RPO and RTO in OpenShift Backup

### RPO: Recovery Point Objective

RPO answers:

> How much data can the business afford to lose?

Examples:

| RPO | Backup Strategy |
|---|---|
| 24 hours | Daily backup |
| 1 hour | Hourly backup or snapshot |
| 5 minutes | Continuous WAL/binlog/object replication |
| Near-zero | Synchronous replication / HA architecture |

### RTO: Recovery Time Objective

RTO answers:

> How quickly must the service be restored?

Examples:

| RTO | Restore Strategy |
|---|---|
| 8 hours | Manual restore acceptable |
| 1 hour | Automated restore runbook |
| 15 minutes | Warm standby / pre-provisioned cluster |
| Near-zero | Active-active or active-passive failover |

OpenShift backup is not a substitute for HA. Backup restores data after loss; HA keeps service running during failures.

## 32. Example: PostgreSQL Backup with Native Dump + OADP

Scenario:

- Namespace: `finance-prod`
- PostgreSQL pod: `postgres-0`
- Backup PVC mounted at `/backup`
- OADP backs up Kubernetes objects and backup dump PVC

### CronJob to generate DB dump

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postgres-logical-backup
  namespace: finance-prod
spec:
  schedule: "30 1 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: registry.redhat.io/rhel9/postgresql-15
              command:
                - /bin/bash
                - -c
                - |
                  set -euo pipefail
                  export PGPASSWORD="$POSTGRES_PASSWORD"
                  pg_dump -h postgres -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" \
                    > /backup/${POSTGRES_DB}-$(date +%F-%H%M%S).dump
                  find /backup -name "*.dump" -mtime +7 -delete
              envFrom:
                - secretRef:
                    name: postgres-secret
              volumeMounts:
                - name: backup
                  mountPath: /backup
          volumes:
            - name: backup
              persistentVolumeClaim:
                claimName: postgres-backup-pvc
```

### OADP backup after dump window

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: finance-prod-oadp-daily
  namespace: openshift-adp
spec:
  schedule: "0 2 * * *"
  template:
    includedNamespaces:
      - finance-prod
    snapshotVolumes: true
    ttl: 168h0m0s
```

This approach separates database consistency from Kubernetes object backup.

## 34. Restore Hooks

Restore hooks run during restore or after restore to prepare the application.

Examples:

- Run database recovery command
- Fix file permissions
- Rebuild indexes
- Import a database dump
- Run schema migration
- Disable scheduled jobs during restore
- Re-enable app after validation

Conceptual example:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: postgres-restore
  namespace: openshift-adp
spec:
  backupName: postgres-backup
  hooks:
    resources:
      - name: postgres-restore-hook
        includedNamespaces:
          - postgres-restore
        labelSelector:
          matchLabels:
            app: postgres
        postHooks:
          - exec:
              container: postgres
              command:
                - /bin/bash
                - -c
                - /opt/backup/post-restore-validate.sh
              waitTimeout: 5m
              execTimeout: 10m
              onError: Fail
```

Validate exact restore hook syntax for your Velero/OADP version.

## 37. Troubleshooting Backup Failures

### 37.1 Backup stuck in progress

Check:

```bash
oc get backup -n openshift-adp
velero backup describe <backup-name> --details
velero backup logs <backup-name>
oc get pods -n openshift-adp
oc logs -n openshift-adp deploy/velero
```

Possible causes:

- Object storage unavailable
- Credentials invalid
- CSI snapshot stuck
- Hook command hanging
- Pod not found by label selector
- Restic/Kopia node-agent issue
- API server throttling

### 37.2 Hook failed

Check:

```bash
velero backup logs <backup-name> | grep -i hook
oc logs -n <app-ns> <pod-name>
oc describe pod -n <app-ns> <pod-name>
```

Common causes:

- Command path wrong
- Container name wrong
- Shell not present in image
- Permission denied
- SCC blocks required capability
- Timeout too short
- Script returns non-zero
- App credentials missing

Fix:

- Test command manually with `oc exec`
- Use full path
- Add `/bin/sh -c` if shell expansion is required
- Increase timeout
- Mount backup script via ConfigMap
- Use a purpose-built backup sidecar

### 37.3 Snapshot not created

Check:

```bash
oc get volumesnapshot -A
oc describe volumesnapshot -n <ns> <snapshot-name>
oc get volumesnapshotcontent
oc get volumesnapshotclass
oc describe pvc -n <ns> <pvc-name>
oc get sc
```

Common causes:

- No default `VolumeSnapshotClass`
- Wrong CSI driver name
- CSI driver does not support snapshots
- Missing snapshotter secret
- Snapshot controller issue
- Storage backend error
- PVC not bound

### 37.4 Backup partially failed

Check details:

```bash
velero backup describe <backup-name> --details
velero backup logs <backup-name> | egrep -i 'error|warn|fail|skip'
```

Possible reasons:

- Forbidden resource due to RBAC
- Excluded API resource
- Unavailable CRD
- Unsupported resource
- PV snapshot failure
- Timeout
- Object storage issue

### 37.5 Restore completed but app not working

Check:

```bash
oc get pods,pvc,svc,route -n <restore-ns>
oc get events -n <restore-ns> --sort-by=.lastTimestamp
oc logs -n <restore-ns> deploy/<app>
oc describe pod -n <restore-ns> <pod>
```

Common causes:

- Secret missing or stale
- Route hostname conflict
- ImagePullBackOff
- PVC restored but data inconsistent
- StorageClass missing on target cluster
- SCC/RBAC missing
- NetworkPolicy blocking traffic
- Operator not installed
- CRD missing
- Database recovery required

## 38. Security Considerations

Backups often contain sensitive data.

Protect:

- Kubernetes Secrets
- Database contents
- TLS private keys
- OAuth tokens
- Pull secrets
- Application credentials
- Customer data
- PII or regulated data

Security checklist:

```text
Encrypt backup object storage
Use TLS to object storage
Restrict backup bucket access
Use least-privilege credentials
Rotate backup credentials
Enable object lock/immutability where required
Audit backup and restore operations
Protect Velero/OADP namespace
Do not expose backup logs with secrets
Validate restore access controls
Separate prod and non-prod backup buckets
```

OpenShift RBAC matters. Backup administrators can often access sensitive namespace data through backup archives, so treat backup permissions as privileged access.

## 39. Storage Backend Considerations

### 39.1 OpenShift Data Foundation / Ceph RBD

Usually good for block PV snapshots.

Check:

```bash
oc get sc
oc get volumesnapshotclass
oc get pods -n openshift-storage
```

Consider:

- RBD snapshots are efficient
- Application consistency still needs hooks
- Ceph health must be clean
- Retention policy must avoid snapshot sprawl

### 39.2 CephFS / RWX volumes

RWX volumes can be mounted by multiple pods.

Extra risk:

- Multiple writers
- Hooks may need to run on several pods
- Freezing one pod does not stop other writers

For RWX application consistency:

```text
1. Stop all writers
2. Confirm no active writes
3. Flush/sync
4. Snapshot or file-system backup
5. Resume writers
```

### 39.3 NFS

NFS-backed PVs are common but snapshot support depends on backend.

Consider:

- NFS itself does not guarantee Kubernetes CSI snapshots unless provided by storage backend/driver
- File-level backup may be used
- Application writes must be paused
- Permissions and UID/GID restore issues are common

### 39.4 Cloud block storage

Examples:

- AWS EBS
- Azure Disk
- Google Persistent Disk

Consider:

- Fast snapshot operations
- Snapshot is storage-level
- Multi-disk consistency varies
- Restore to another zone/region may need special handling

## 40. Backup of Secrets and ConfigMaps

Secrets are critical for restore.

Examples:

- DB password
- TLS certificate
- API token
- Pull secret
- OAuth client secret

But restored Secrets can be problematic:

- Token may be expired
- Certificate CN/SAN may not match new route
- External system credential may be environment-specific
- ServiceAccount tokens are usually auto-generated and should not be blindly reused

Best practice:

```text
Back up application Secrets, but review environment-specific Secrets during cross-cluster restore.
Use External Secrets/Vault/GitOps where possible.
Avoid hardcoding cluster-specific credentials.
```

## 41. Route, DNS, and TLS Restore Issues

Routes are OpenShift-specific objects and often included in app backups.

Problems during restore:

- Same hostname already exists
- DNS points to old cluster
- TLS cert does not match target route
- Edge/reencrypt passthrough settings differ
- Ingress controller domain differs

Before cross-cluster restore:

```bash
oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}{"\n"}'
oc get route -n app-prod
```

After restore, update route hostnames if needed:

```bash
oc patch route app -n app-restore --type merge -p '{"spec":{"host":"app-restore.apps.dr.example.com"}}'
```

## 42. GitOps and Backup

GitOps does not replace backup.

GitOps can restore:

- YAML manifests
- Helm values
- Kustomize overlays
- Argo CD Applications

GitOps cannot automatically restore:

- Runtime database data
- User-uploaded files
- Dynamically generated Secrets unless synced from secret manager
- PV contents
- Message queue state

Best design:

```text
GitOps restores desired state.
OADP/storage/native tools restore runtime state.
Application validation confirms business state.
```

Sometimes you should exclude noisy or unsafe resources.

Examples:

- Pods generated by controllers
- ReplicaSets if Deployments recreate them
- Events
- Temporary Jobs
- Operator runtime pods
- Certain cluster-scoped resources

Use exclusions carefully. Excluding the wrong object can break restore.

## 52. Exam and Interview Style Points

### Question: What is application-consistent backup?

Answer:

> It is a backup captured after the application has been placed into a consistent state, usually by flushing transactions, pausing writes, locking or checkpointing data, and then taking the backup or snapshot before resuming normal operations.

### Question: Is a CSI VolumeSnapshot application-consistent?

Answer:

> Not automatically. A CSI snapshot is storage-level. It can be crash-consistent, but application consistency requires app-aware quiescing such as database checkpoints, backup locks, or Velero/OADP hooks.

### Question: How can OADP help with application consistency?

Answer:

> OADP uses Velero and supports backup hooks that run commands before and after backup operations. These hooks can flush buffers, freeze filesystems, lock databases, or put apps into maintenance mode.

### Question: What is the difference between etcd backup and OADP backup?

Answer:

> etcd backup protects cluster control plane state for cluster disaster recovery. OADP protects application resources and persistent data at application or namespace level.

### Question: Why are restore tests mandatory?

Answer:

> Because backup success only proves data was captured. Restore testing proves the application can actually come back healthy, with valid data, working credentials, networking, routes, and storage.

## 54. Recommended Production Pattern

For most enterprise OpenShift environments:

```text
1. Use GitOps for desired application manifests.
2. Use OADP for namespace resources and PV protection.
3. Use CSI snapshots where supported for fast PV recovery.
4. Use database-native backups for critical databases.
5. Use Velero/OADP hooks for quiesce/resume.
6. Store backups in encrypted object storage.
7. Replicate backups to another region/site.
```

```text
Native DB backup + WAL/binlog/archive strategy + OADP metadata backup
```

```text

```

## 56. Final Summary

Application-consistent backup in OpenShift is not a single command. It is a coordinated process between the application, database, Kubernetes objects, OADP/Velero, CSI storage, object storage, and restore validation.

The most important rule:

> A storage snapshot captures blocks. An application-consistent backup captures a recoverable business service state.

For a senior OpenShift administrator, the real responsibility is to design backups that can be restored under pressure, with clear RPO/RTO, tested runbooks, secured backup storage, and application-aware consistency controls.
