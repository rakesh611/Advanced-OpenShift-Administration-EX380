## 1. What OpenShift Logging Provides

OpenShift Logging is the platform-level logging solution for collecting, routing, storing, querying, and visualizing log data from an OpenShift Container Platform cluster.

In a production OpenShift environment, logs are needed for many different operational goals:

- Application debugging
- Cluster troubleshooting
- Security investigation
- Audit evidence
- Compliance retention
- Incident response
- SRE observability
- Developer self-service
- Capacity and cost analysis
- Integration with enterprise SIEM tools such as Splunk, QRadar, Sentinel, Elastic, Datadog, Kafka, or cloud-native logging services

OpenShift Logging does **not** mean only one centralized log store. In modern OpenShift, logging is best understood as a **log routing architecture**:

```text
Sources  ->  Collector  ->  Pipelines  ->  Outputs
Pods         Vector         Filters        LokiStack
Nodes        DaemonSet      Routing        Splunk
Audit                      Pruning        Kafka
Receivers                  Drop rules      S3
                                          Syslog
                                          OTLP
                                          Cloud services
```

The key point for an advanced administrator is this:

> OpenShift Logging is not just a log viewer. It is a controlled log movement system with RBAC, tenancy, filtering, routing, buffering, output security, storage design, and operational SLO impact.

## 2. Modern OpenShift Logging Architecture at a Glance

A complete OpenShift Logging 6.x deployment can contain three main operator-managed layers:

```text
+----------------------------------------------------------------------------------+
|                            OpenShift Container Platform                           |
|                                                                                  |
|  +----------------------+       +----------------------+       +----------------+ |
|  | Application Pods     |       | Infra Components     |       | Audit Sources  | |
|  | stdout/stderr        |       | node journal, OCP    |       | API/OAuth/OVN  | |
|  +----------+-----------+       +----------+-----------+       +--------+-------+ |
|             |                              |                            |         |
|             +------------------------------+----------------------------+         |
|                                            |                                      |
|                          +-----------------v------------------+                   |
|                          | Vector Collector DaemonSet          |                   |
|                          | One collector pod per node          |                   |
|                          | Reads, enriches, transforms, sends  |                   |
|                          +-----------------+------------------+                   |
|                                            |                                      |
|                         ClusterLogForwarder pipelines                            |
|                                            |                                      |
|        +----------------------+------------+-------------+----------------+       |
|        |                      |                          |                |       |
| +------v------+       +-------v-------+          +-------v------+  +------v-----+ |
| | LokiStack   |       | Splunk/HTTP   |          | Kafka/Syslog |  | S3 archive | |
| | in-cluster  |       | external SIEM |          | stream bus   |  | compliance | |
| +------+------+       +---------------+          +--------------+  +------------+ |
|        |                                                                         |
| +------v----------------+                                                        |
| | Console Logs UI       |                                                        |
| | via COO + UIPlugin    |                                                        |
| +-----------------------+                                                        |
+----------------------------------------------------------------------------------+
```

A full architecture normally includes:

| Layer | Main Resource | Managed By | Purpose |
|---|---|---|---|
| Collection and forwarding | `ClusterLogForwarder` | Red Hat OpenShift Logging Operator | Defines what to collect, how to process it, and where to send it |
| Collector runtime | Vector `DaemonSet` | Red Hat OpenShift Logging Operator | Runs on nodes and reads log files/journals/audit sources |
| Storage | `LokiStack` | Loki Operator | Stores logs in a horizontally scalable Loki deployment |
| Visualization | `UIPlugin` | Cluster Observability Operator | Adds Observe → Logs to the OpenShift web console |
| Object storage | S3-compatible bucket, AWS S3, Azure, GCS, ODF/NooBaa/Ceph RGW, Swift | Storage platform + Loki Operator | Durable chunk/index storage for Loki |
| RBAC | ServiceAccount + ClusterRoleBindings | OpenShift RBAC | Controls which log types the collector can read |
| Monitoring | Prometheus metrics + alerts | OpenShift Monitoring | Tracks collector, Loki, and operator health |

## 3. OpenShift Logging 5 vs Logging 6 Architecture Shift

A 10-year-experience administrator must be clear about the architecture shift from older OpenShift Logging versions.

### 3.1 Older model

Older deployments often used:

```text
ClusterLogging CR
ClusterLogForwarder CR
Fluentd collector
Elasticsearch log store
Kibana visualization
```

### 3.2 Modern Logging 6 model

Current architecture uses:

```text
ClusterLogForwarder CR only for collection/forwarding configuration
Vector collector
LokiStack for managed log storage
Cluster Observability Operator UIPlugin for console visualization
```

### 3.3 Major differences

| Area | Older Logging 5.x-style architecture | Logging 6.x architecture |
|---|---|---|
| Collector | Fluentd or Vector, depending on version/configuration | Vector collector |
| Main API | `logging.openshift.io` resources such as `ClusterLogging` and older `ClusterLogForwarder` | `observability.openshift.io/v1` `ClusterLogForwarder` |
| Managed store | Elasticsearch | LokiStack |
| Visualization | Kibana / old logging console plugin | Cluster Observability Operator `UIPlugin` |
| Main design goal | Centralized cluster logging stack | Flexible routing, LokiStack, external outputs, OpenTelemetry alignment |
| Storage model | Full-text indexing in Elasticsearch | Loki label/index model with object storage-backed chunks |
| Cost profile | Higher indexing/storage overhead | More efficient for many log workloads when labels are controlled |

### 3.4 Why this matters in operations

Many real production failures happen because administrators mix old and new mental models:

- Creating a `ClusterLogging` CR in a Logging 6-only setup.
- Expecting Fluentd pods when the collector is Vector.
- Looking for Kibana when visualization is now through COO/UIPlugin.
- Forgetting the collector service account permissions required by the new `ClusterLogForwarder` model.
- Assuming Loki behaves like Elasticsearch full-text search.
- Adding too many Loki labels and causing high-cardinality performance problems.

For advanced administration, always identify the version and architecture first:

```bash
oc get csv -A | egrep 'cluster-logging|loki|observability'
oc get clusterlogforwarder -A
oc get lokistack -A
oc get uiplugin -A
oc get pods -n openshift-logging
```

## 4. Core Architecture Components

### 4.1 Red Hat OpenShift Logging Operator

The Red Hat OpenShift Logging Operator manages log collection and forwarding.

It reconciles the `ClusterLogForwarder` CR and creates/updates collector resources such as:

- Collector `DaemonSet`
- Collector `ServiceAccount` usage
- ConfigMaps and generated Vector configuration
- Collector services for receiver inputs
- Collector network policies, if configured
- Resource requests/limits, tolerations, node selectors
- Collector status conditions

The operator does **not** store logs by itself. Storage is handled by LokiStack or external systems.

### 4.2 Vector Collector

Vector is the log collector deployed as a `DaemonSet`. In practical terms:

- One collector pod runs on each eligible node.
- It tails container log files.
- It reads infrastructure and audit sources when authorized.
- It enriches records with Kubernetes metadata.
- It applies parsing, filtering, pruning, multiline exception detection, and rate limits.
- It forwards to one or more outputs.

Vector is a critical per-node component. If it fails on one node, logs from workloads on that node may stop flowing, while other nodes can continue.

### 4.3 ClusterLogForwarder

`ClusterLogForwarder` is the central configuration object for collection, filtering, and forwarding.

Typical structure:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
  - name: selected-apps
    type: application
    application:
      selector:
        matchLabels:
          app: payments
  filters:
  - name: drop-debug
    type: drop
    drop:
    - test:
      - field: .level
        matches: debug
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: app-to-loki
    inputRefs:
    - selected-apps
    filterRefs:
    - drop-debug
    outputRefs:
    - default-lokistack
```

Think of the `ClusterLogForwarder` as a routing graph:

```text
inputRefs -> filterRefs -> outputRefs
```

### 4.4 Loki Operator

The Loki Operator manages the `LokiStack` custom resource. It deploys and reconciles Loki components such as:

- Gateway
- Distributor / ingestion path components
- Ingester
- Querier
- Query frontend
- Compactor
- Ruler, if enabled
- Supporting services, network policies, secrets, config, service accounts

The Loki Operator is responsible for the in-cluster log store, not the node collector.

### 4.5 LokiStack

`LokiStack` describes the managed Loki deployment.

It includes configuration for:

- Size profile
- Storage backend
- Storage schema
- Tenancy mode
- Retention rules
- TLS/object storage configuration
- Tolerations/node selectors
- Replication-related settings
- Network policy behavior
- Gateway exposure

Example simplified `LokiStack`:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  size: 1x.extra-small
  storage:
    schemas:
    - version: v13
      effectiveDate: "2026-07-01"
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: ocs-storagecluster-ceph-rbd
  tenants:
    mode: openshift-logging
```

### 4.6 Cluster Observability Operator

The Cluster Observability Operator manages visualization integration for logs in the OpenShift console.

It uses a `UIPlugin` resource to add log querying features under:

```text
OpenShift Console -> Observe -> Logs
```

Example:

```yaml
apiVersion: observability.openshift.io/v1alpha1
kind: UIPlugin
metadata:
  name: logging
spec:
  type: Logging
  logging:
    lokiStack:
      name: logging-loki
    logsLimit: 50
    timeout: 30s
    schema: otel
```

### 4.7 LogFileMetricExporter

`LogFileMetricExporter` can be used to expose metrics related to log files. This is useful for detecting node log file growth, rotation issues, and collector visibility problems.

In strict network environments, it can also require explicit network policy configuration.

## 5. End-to-End Log Flow

### 5.1 Container log flow

Most application logs start from container `stdout` and `stderr`.

```text
Application writes stdout/stderr
        |
        v
CRI-O writes container log files on node
        |
        v
Kubelet/container runtime symlinks logs under node log paths
        |
        v
Vector collector pod tails logs from host-mounted paths
        |
        v
Vector enriches with Kubernetes metadata
        |
        v
ClusterLogForwarder pipeline applies filters/routing
        |
        v
Output: LokiStack / Splunk / Kafka / S3 / Syslog / OTLP / HTTP
```

Important admin point:

> OpenShift Logging normally collects container logs from node log files, not by running inside every application pod.

That is why the collector is a node-level `DaemonSet` and why node permissions, hostPath mounts, SELinux context, and RBAC matter.

### 5.2 Infrastructure log flow

Infrastructure logs include OpenShift and Kubernetes system components. They usually come from:

- Containers in `openshift-*` namespaces
- Containers in `kube-*` namespaces
- Some node journal sources
- Cluster platform component logs

```text
OpenShift component / node service
        |
        v
container logs or journald
        |
        v
Vector collector
        |
        v
infrastructure input
        |
        v
pipeline -> output
```

### 5.3 Audit log flow

Audit logs are security-sensitive and high-volume. They can include:

- Kubernetes API audit logs
- OpenShift API audit logs
- OAuth-related audit logs
- Node `auditd` logs
- OVN/network audit logs

```text
API server / OAuth / node auditd / OVN
        |
        v
Audit files or audit streams
        |
        v
Vector collector with collect-audit-logs permission
        |
        v
audit input
        |
        v
optional prune/drop filters
        |
        v
secure output such as SIEM or archive
```

Audit logs should be treated differently from normal application logs:

- Higher sensitivity
- Higher compliance importance
- Higher storage cost risk
- More strict access control
- Often routed to immutable or long-term archive
- Often pruned before leaving the cluster

### 5.4 Receiver input flow

Receiver inputs allow the collector to accept log data over a network protocol. Supported receiver models include HTTP and syslog for specific supported use cases.

```text
Supported in-cluster product / hosted control plane source
        |
        v
HTTP or syslog receiver service created by Logging Operator
        |
        v
Vector collector
        |
        v
pipeline -> output
```

Receiver inputs are not a generic replacement for a central syslog server. They are intended for specific supported scenarios.

## 6. Log Sources: Application, Infrastructure, Audit, and Receivers

`ClusterLogForwarder` recognizes three reserved high-level built-in inputs:

```text
application
infrastructure
audit
```

It can also define custom inputs and receiver inputs.

### 6.1 Application logs

Application logs are logs generated by user workloads.

Examples:

- Java/Spring Boot app logs
- Python service logs
- NGINX access logs written to stdout
- Node.js application errors
- Microservice business logs
- Custom application container logs

Application input can select by:

- Namespace
- Container name patterns
- Pod labels
- Include/exclude rules
- Rate limits
- Maximum message size tuning

Example: collect only application logs from specific namespaces:

```yaml
spec:
  inputs:
  - name: finance-apps
    type: application
    application:
      includes:
      - namespace: finance-prod
      - namespace: finance-uat
```

Example: collect only pods with a label:

```yaml
spec:
  inputs:
  - name: high-priority-apps
    type: application
    application:
      selector:
        matchLabels:
          priority: high
```

### 6.2 Infrastructure logs

Infrastructure logs are from OpenShift/Kubernetes platform components.

Common sources:

- `openshift-*` namespaces
- `kube-*` namespaces
- `default` infrastructure namespace patterns
- Node journal logs

Example: infrastructure input with selected source:

```yaml
spec:
  inputs:
  - name: infra-containers-only
    type: infrastructure
    infrastructure:
      sources:
      - container
```

Example: node journal logs only:

```yaml
spec:
  inputs:
  - name: node-journal-only
    type: infrastructure
    infrastructure:
      sources:
      - node
```

### 6.3 Audit logs

Audit input can include multiple sources:

```text
kubeAPI
openshiftAPI
auditd
ovn
```

Example:

```yaml
spec:
  inputs:
  - name: api-audit-only
    type: audit
    audit:
      sources:
      - kubeAPI
      - openshiftAPI
```

### 6.4 Receiver inputs

Receiver input example for HTTP audit format:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
  - name: http-audit-receiver
    type: receiver
    receiver:
      type: http
      port: 8443
      http:
        format: kubeAPIAudit
  outputs:
  - name: audit-http-out
    type: http
    http:
      url: https://audit-receiver.example.com:443/logs
  pipelines:
  - name: received-audit-to-http
    inputRefs:
    - http-audit-receiver
    outputRefs:
    - audit-http-out
```

Operational note:

- Receiver inputs create services.
- Network policies may need explicit allowance.
- TLS and authentication must be designed carefully.
- Treat receiver ports as platform entry points.

## 7. Collector Architecture: Vector on Every Node

### 7.1 Collector deployment model

The collector is normally deployed as a `DaemonSet`.

```text
worker-1 -> collector pod
worker-2 -> collector pod
worker-3 -> collector pod
master-1 -> collector pod, if scheduled/tolerated
master-2 -> collector pod, if scheduled/tolerated
master-3 -> collector pod, if scheduled/tolerated
```

Why a `DaemonSet`?

- Logs are written locally on each node.
- A central pod cannot directly read all node-local files.
- Per-node collectors reduce cross-node dependency.
- Failure is isolated per node.

Check collector pods:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

Expected pattern:

```text
One collector pod per eligible node
```

### 7.2 Collector responsibilities

The collector performs these functions:

1. **Read** container log files, journal sources, and audit files.
2. **Parse** log records into internal fields.
3. **Enrich** records with Kubernetes metadata.
4. **Classify** records as `application`, `infrastructure`, or `audit`.
5. **Apply input-level constraints** such as namespace/container selectors and rate limits.
6. **Apply filters** such as drop, prune, parse, multiline exception detection, or label enrichment.
7. **Batch and buffer** records for output delivery.
8. **Forward** to configured output sinks.
9. **Expose metrics** for Prometheus scraping.

### 7.3 Why collector RBAC matters

The collector cannot read all log categories by default. It needs explicit permissions through predefined cluster roles:

```text
collect-application-logs
collect-infrastructure-logs
collect-audit-logs
```

This design prevents accidental collection of sensitive categories such as audit logs.

Create collector service account:

```bash
oc create sa collector -n openshift-logging
```

Grant permissions:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Verify:

```bash
oc get clusterrolebinding -o wide | grep collector
```

### 7.4 Protective failure behavior

If a `ClusterLogForwarder` references a log type that the service account is not authorized to collect, the operator can remove or stop the collector deployment to avoid insecure partial collection.

Example problem:

```yaml
pipelines:
- name: audit-pipeline
  inputRefs:
  - audit
  outputRefs:
  - default-lokistack
```

But the service account has only:

```text
collect-application-logs
collect-infrastructure-logs
```

Result:

- `ClusterLogForwarder` authorization condition fails.
- Collector may be removed/stopped.
- All log collection may stop, not only audit collection.

This is why production change process should always be:

```text
1. Add RBAC first
2. Verify ClusterRoleBinding
3. Update ClusterLogForwarder
4. Verify status
5. Verify collector pods
6. Verify log flow
```

### 7.5 Collector scheduling

The collector can be tuned with:

- `nodeSelector`
- `tolerations`
- Resource requests/limits
- Max unavailable during rollout
- Network policy rule set

Example resources:

```yaml
spec:
  collector:
    resources:
      requests:
        cpu: 100m
        memory: 736Mi
      limits:
        cpu: 500m
        memory: 1Gi
```

Example rollout tuning:

```yaml
spec:
  collector:
    maxUnavailable: 10%
```

Example toleration for infra nodes:

```yaml
spec:
  collector:
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
```

### 7.6 Collector failure modes

| Failure | Symptoms | Likely Cause |
|---|---|---|
| No collector pods | `oc get pods` empty | CLF auth/valid condition failed, operator failed, namespace issue |
| Collector crashloop | Pod restarts repeatedly | Invalid generated config, memory limit too low, output TLS/auth failure edge case |
| Logs missing from one node | Only workloads on one node affected | Collector pod failed on that node, node disk issue, file permission issue |
| Logs delayed | Old logs appear late | Backpressure, slow output, 429 from Loki, network bottleneck |
| High collector memory | OOMKilled collector | Multiline detection, huge messages, high volume, slow sink |
| Output errors only | Collector running but sink empty | TLS, auth, endpoint, DNS, NetworkPolicy, receiver-side rate limit |

## 8. ClusterLogForwarder Architecture

`ClusterLogForwarder` is the most important resource for day-to-day OpenShift Logging administration.

### 8.1 Conceptual model

```text
ClusterLogForwarder
  |
  +-- serviceAccount: identity used by collector
  |
  +-- inputs: where logs come from
  |
  +-- filters: how records are modified or dropped
  |
  +-- outputs: where logs go
  |
  +-- pipelines: which inputs connect to which filters and outputs
  |
  +-- collector: operational behavior of collector pods
```

### 8.2 Inputs

Inputs define log source selection.

Built-in reserved input names:

```yaml
inputRefs:
- application
- infrastructure
- audit
```

Custom inputs allow selection:

```yaml
inputs:
- name: nginx-prod
  type: application
  application:
    selector:
      matchLabels:
        app: nginx
    includes:
    - namespace: prod
```

### 8.3 Filters

Filters transform or drop records.

Common filter types:

| Filter | Purpose |
|---|---|
| `drop` | Drop entire log records based on field tests |
| `prune` | Remove or keep specific fields |
| `detectMultilineException` | Combine stack traces / multiline exceptions into one record |
| `parse` | Parse structured data such as JSON where supported |
| `openshiftLabels` | Add labels/metadata for routing or downstream use |

Example drop filter:

```yaml
filters:
- name: drop-debug
  type: drop
  drop:
  - test:
    - field: .level
      matches: debug
```

Example prune filter:

```yaml
filters:
- name: prune-audit-heavy-fields
  type: prune
  prune:
    in:
    - .audit.requestObject
    - .audit.responseObject
    - .audit.managedFields
```

Example multiline exception detection:

```yaml
filters:
- name: detect-java-stacktraces
  type: detectMultilineException
```

### 8.4 Outputs

Outputs define destinations.

Common output types include:

- `lokiStack` for in-cluster managed LokiStack
- `loki` for an external Loki endpoint
- `splunk`
- `kafka`
- `syslog`
- `http`
- `otlp`
- `s3`
- `cloudwatch`
- `googleCloudLogging`
- `azureMonitor` where still available, noting deprecation/removal timelines must be checked before use

Example LokiStack output:

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    authentication:
      token:
        from: serviceAccount
    target:
      name: logging-loki
      namespace: openshift-logging
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

Example Splunk output:

```yaml
outputs:
- name: splunk-prod
  type: splunk
  splunk:
    authentication:
      token:
        secretName: splunk-token
        key: hecToken
    url: https://splunk.example.com:8088
```

Example Kafka output:

```yaml
outputs:
- name: kafka-audit
  type: kafka
  kafka:
    url: tls://kafka.example.com:9093/audit-topic
    authentication:
      sasl:
        mechanism: SCRAM-SHA-512
        username:
          secretName: kafka-secret
          key: username
        password:
          secretName: kafka-secret
          key: password
```

Example S3 archive output:

```yaml
outputs:
- name: audit-archive-s3
  type: s3
  s3:
    url: https://s3.us-east-1.amazonaws.com
    bucket: openshift-audit-archive
    keyPrefix: cluster-a/prod/audit
    authentication:
      type: awsAccessKey
      awsAccessKey:
        keyId:
          secretName: s3-secret
          key: access_key_id
        keySecret:
          secretName: s3-secret
          key: secret_access_key
```

### 8.5 Pipelines

Pipelines connect inputs, filters, and outputs.

Example:

```yaml
pipelines:
- name: apps-to-loki
  inputRefs:
  - application
  filterRefs:
  - drop-debug
  outputRefs:
  - default-lokistack

- name: audit-to-s3-and-splunk
  inputRefs:
  - audit
  filterRefs:
  - prune-audit-heavy-fields
  outputRefs:
  - audit-archive-s3
  - splunk-prod
```

Important behavior:

- A pipeline can send the same log record to multiple outputs.
- If one output fails, other outputs can continue independently.
- Filters are applied in the order specified in `filterRefs`.
- A record dropped by an early filter will not reach later filters or outputs in that pipeline.

### 8.6 Status conditions

Always inspect status conditions after changes:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Important conditions include:

```text
Authorized
Valid
Ready
```

A practical check:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

## 9. LokiStack Architecture

LokiStack is the managed Loki deployment used by OpenShift Logging.

### 9.1 Loki design concept

Loki is different from Elasticsearch.

Elasticsearch commonly indexes much more of the log content. Loki is designed around:

- Labels for indexing streams
- Log chunks stored in object storage
- Querying with LogQL
- Separating ingestion and query paths
- Multi-tenancy through a gateway model

Think of Loki as:

```text
Labels identify log streams.
Chunks store actual log content.
Object storage holds durable data.
Queries use labels first, then filter log lines.
```

### 9.2 LokiStack component view

A simplified LokiStack architecture:

```text
                 +----------------------------+
                 | OpenShift Console / LogQL  |
                 +-------------+--------------+
                               |
                               v
+-------------------+   +------+-------+   +----------------+
| Vector collectors |-->| Loki Gateway |-->| Distributor    |
+-------------------+   +------+-------+   +-------+--------+
                               |                   |
                               |                   v
                               |           +-------+--------+
                               |           | Ingester       |
                               |           +-------+--------+
                               |                   |
                               |                   v
                               |           +-------+--------+
                               |           | Object Storage |
                               |           | S3/ODF/GCS/etc |
                               |           +-------+--------+
                               |
                               v
                       +-------+--------+
                       | Query Frontend |
                       +-------+--------+
                               |
                               v
                       +-------+--------+
                       | Querier        |
                       +-------+--------+
                               |
                               v
                       +-------+--------+
                       | Compactor      |
                       +----------------+
```

Exact components and names can vary by LokiStack size and version, but the functional paths are important.

### 9.3 Write path

```text
Vector collector
   -> LokiStack gateway
      -> distributor
         -> ingester
            -> chunk/index/object storage
```

Important admin checks:

```bash
oc get pods -n openshift-logging | grep loki
oc get lokistack -n openshift-logging
oc describe lokistack logging-loki -n openshift-logging
```

### 9.4 Query path

```text
User / console / API client
   -> LokiStack gateway
      -> query frontend
         -> querier
            -> ingesters for recent data
            -> object storage for persisted chunks/index
```

Important query performance factors:

- Time range
- Label selectivity
- Number of streams matched
- Log volume in selected range
- Query pattern, especially regex and line filters
- Object storage latency
- Querier CPU/memory
- Query frontend configuration
- Cardinality of labels

### 9.5 Compaction and retention

The compactor is responsible for index/chunk maintenance and retention-related cleanup depending on configuration.

Retention can be configured at different levels depending on the LokiStack feature set:

- Global retention
- Tenant-level retention
- Stream-based retention rules
- Object bucket lifecycle policies

Production note:

> Do not rely on “we created a bucket” as a retention strategy. Explicitly design retention in LokiStack and/or object storage lifecycle policy.

### 9.6 Ruler

The ruler evaluates rules against log streams, such as alerting rules. Enabling rule evaluation increases CPU and memory requirements.

Use the ruler carefully in high-volume environments:

- Minimize expensive LogQL expressions.
- Avoid wide time ranges.
- Avoid high-cardinality label matches.
- Align evaluation intervals with real incident needs.

## 10. Storage Architecture

### 10.1 Loki storage model

LokiStack usually depends on two types of storage:

1. **Object storage** for chunks/index data.
2. **Persistent volumes** for some Loki components depending on the deployment size and internal state requirements.

Common object storage options:

- AWS S3
- S3-compatible storage
- OpenShift Data Foundation object storage / NooBaa / Ceph RGW
- Google Cloud Storage
- Azure Blob Storage
- Swift

### 10.2 Object storage secret

S3-compatible example:

```bash
oc create secret generic logging-loki-s3 \
  -n openshift-logging \
  --from-literal=bucketnames="openshift-logs" \
  --from-literal=endpoint="https://s3.example.com" \
  --from-literal=access_key_id="<access-key>" \
  --from-literal=access_key_secret="<secret-key>" \
  --from-literal=forcepathstyle="true"
```

Corresponding LokiStack:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  size: 1x.extra-small
  storage:
    secret:
      name: logging-loki-s3
      type: s3
    schemas:
    - version: v13
      effectiveDate: "2026-07-01"
  storageClassName: ocs-storagecluster-ceph-rbd
  tenants:
    mode: openshift-logging
```

### 10.3 ODF object bucket example

ObjectBucketClaim example:

```yaml
apiVersion: objectbucket.io/v1alpha1
kind: ObjectBucketClaim
metadata:
  name: loki-bucket-odf
  namespace: openshift-logging
spec:
  generateBucketName: loki-bucket-odf
  storageClassName: openshift-storage.noobaa.io
```

Then create the Loki object storage secret using bucket details from the generated ConfigMap and Secret.

### 10.4 Storage design checklist

For production, validate:

- Bucket exists and is reachable from Loki pods.
- TLS CA is trusted if object store uses private CA.
- IAM/access keys have required bucket permissions.
- Object lifecycle policies do not delete data earlier than Loki retention expects.
- Bucket versioning/lifecycle settings match compliance needs.
- NetworkPolicy/AdminNetworkPolicy permits object store egress.
- Object store latency is acceptable.
- Bucket size/cost monitoring exists.
- StorageClass for Loki PVCs has enough capacity/performance.

### 10.5 Storage anti-patterns

Avoid:

- Using demo size in production.
- Leaving retention undefined forever.
- Treating Loki as a long-term legal archive without designing object lifecycle and access controls.
- Using high-cardinality labels that explode index size.
- Placing object storage behind unreliable proxies.
- Sharing buckets across clusters without clear prefixes/tenancy.
- Enabling verbose audit logging without cost estimation.

## 12. Security and RBAC Architecture

### 12.1 Security layers

OpenShift Logging security includes multiple layers:

```text
OpenShift RBAC
  -> collector service account permissions
  -> namespace access control
  -> LokiStack gateway tenancy
  -> output authentication secrets
  -> TLS for in-cluster and external outputs
  -> NetworkPolicy/AdminNetworkPolicy
  -> audit log sensitivity controls
```

### 12.2 Collector service account

The collector service account identity is defined in the `ClusterLogForwarder`:

```yaml
spec:
  serviceAccount:
    name: collector
```

The service account requires explicit cluster role bindings.

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### 12.3 Output secrets

External outputs frequently require secrets:

- Splunk HEC token
- Kafka SASL username/password
- TLS client cert/key
- S3 access key
- Cloud provider credentials
- OTLP bearer token/basic auth

Example Splunk secret:

```bash
oc create secret generic splunk-token \
  -n openshift-logging \
  --from-literal=hecToken='<token>'
```

### 12.4 TLS to LokiStack

When forwarding to LokiStack, always include the CA block so the collector can verify the LokiStack gateway certificate.

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    authentication:
      token:
        from: serviceAccount
    target:
      name: logging-loki
      namespace: openshift-logging
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

Symptoms of missing/wrong CA:

- `ClusterLogForwarder` may show Ready.
- Collector logs show certificate verification failures.
- LokiStack receives no logs.

### 12.5 Audit logs are sensitive

Audit logs can contain:

- Usernames
- Service account names
- Object names
- Namespace names
- Request metadata
- Admission details
- Authorization decisions
- Sometimes request/response objects depending on audit policy

Best practice:

- Do not send raw audit logs to broad developer-visible stores.
- Route audit logs separately.
- Prune heavy/sensitive fields before external SaaS forwarding.
- Use dedicated long-term archive/SIEM outputs.
- Limit query access.

## 13. Multi-Tenancy and Access Control

### 13.1 Why tenancy matters

In a shared OpenShift cluster, logs can reveal sensitive data:

- Application payload snippets
- Internal URLs
- Secrets accidentally printed by apps
- Customer identifiers
- Pod/service names
- Security events
- Deployment timings

Logging access must follow namespace and role boundaries.

### 13.2 LokiStack tenant modes

In OpenShift Logging, LokiStack can operate in OpenShift-aware modes such as `openshift-logging`.

Example:

```yaml
spec:
  tenants:
    mode: openshift-logging
```

The gateway participates in access control so users query logs according to OpenShift authorization.

### 13.3 Administrator vs developer access

| User Type | Typical Access |
|---|---|
| Cluster administrator | Cluster-wide logs, including infrastructure and possibly audit logs |
| Namespace admin | Application logs in owned namespaces |
| Developer | Application logs in namespaces where they have permissions |
| Security team | Audit logs and selected platform logs |
| External SIEM | Dedicated forwarded stream, not necessarily direct cluster UI access |

### 13.4 Common access mistakes

- Giving too many users access to audit logs.
- Forwarding all logs to a shared external index without namespace controls.
- Adding high-cardinality labels based on user or request IDs.
- Treating log access as separate from Kubernetes RBAC.
- Letting application teams query infrastructure logs unnecessarily.

## 14. Pipelines, Filters, and Routing Patterns

### 14.1 Basic all-to-Loki pattern

```yaml
pipelines:
- name: all-apps-to-loki
  inputRefs:
  - application
  - infrastructure
  outputRefs:
  - default-lokistack
```

Use for:

- Small/medium clusters
- Basic troubleshooting
- Learning labs
- Development clusters

Avoid for:

- Regulated production where audit must go separately
- Very high-volume clusters without filtering
- Cost-sensitive external output architecture

### 14.2 Split application and audit pattern

```yaml
pipelines:
- name: apps-to-loki
  inputRefs:
  - application
  outputRefs:
  - default-lokistack

- name: audit-to-siem
  inputRefs:
  - audit
  filterRefs:
  - prune-audit-heavy-fields
  outputRefs:
  - splunk-prod
```

Use for:

- Production clusters
- Security separation
- Compliance

### 14.3 Dual output pattern

```yaml
pipelines:
- name: audit-to-splunk-and-s3
  inputRefs:
  - audit
  outputRefs:
  - splunk-prod
  - audit-archive-s3
```

Use when:

- SIEM needs searchable audit events.
- S3 archive is required for long-term retention.

### 14.4 Noise control pattern

```yaml
filters:
- name: drop-debug
  type: drop
  drop:
  - test:
    - field: .level
      matches: debug

pipelines:
- name: apps-no-debug-to-loki
  inputRefs:
  - application
  filterRefs:
  - drop-debug
  outputRefs:
  - default-lokistack
```

### 14.5 Namespace isolation pattern

```yaml
inputs:
- name: payments-prod
  type: application
  application:
    includes:
    - namespace: payments-prod

- name: shared-dev
  type: application
  application:
    includes:
    - namespace: dev-a
    - namespace: dev-b

pipelines:
- name: payments-to-splunk
  inputRefs:
  - payments-prod
  outputRefs:
  - splunk-prod

- name: dev-to-loki
  inputRefs:
  - shared-dev
  outputRefs:
  - default-lokistack
```

### 14.6 Filter ordering best practice

Recommended order:

```text
1. parse structured data
2. drop unwanted records
3. prune fields
4. detect/enrich/label as needed
5. output routing
```

Why?

- Parsing first exposes structured fields.
- Dropping early reduces work.
- Pruning after dropping avoids unnecessary transformations.
- Labels last avoid adding routing metadata to logs that will be dropped.

## 15. Common Output Architectures

### 15.1 In-cluster troubleshooting store only

```text
Vector -> LokiStack -> OpenShift Console
```

Best for:

- Platform troubleshooting
- Developer self-service
- Short-term operational visibility

Not enough for:

- Long-term legal compliance by itself
- Enterprise SIEM correlation unless integrated
- Cross-cluster centralized analytics unless external aggregation is added

### 15.2 SIEM-forwarding architecture

```text
Vector -> ClusterLogForwarder -> Splunk/QRadar/Sentinel/Elastic/Datadog
```

Best for:

- Security operations
- Compliance
- Cross-platform correlation
- Existing enterprise logging standards

Design notes:

- Use filters to avoid sending noisy debug logs.
- Use separate indexes by cluster/env/log type.
- Make audit routing explicit.
- Monitor external endpoint rate limits.
- Treat token/cert rotation as operational process.

### 15.3 Kafka fan-out architecture

```text
Vector -> Kafka -> downstream consumers
```

Best for:

- Central data platform ingestion
- Multiple downstream tools
- Decoupling OpenShift from slow consumers
- Event-driven log processing

Risks:

- Kafka partition/topic design matters.
- Backpressure can still affect collectors.
- Ordering and topic strategy require planning.
- TLS/SASL cert expiration can break ingestion.

### 15.4 Archive-first architecture

```text
Vector -> S3-compatible archive
```

Best for:

- Cost-effective long-term retention
- Audit/compliance archive
- Batch analytics

Limitations:

- Not ideal for fast troubleshooting.
- Querying requires external tooling.
- Object layout/keyPrefix design matters.

### 15.5 Hybrid architecture

```text
application logs -> LokiStack, short retention
infrastructure logs -> LokiStack + SIEM
raw audit logs -> S3 archive
security-relevant audit subset -> Splunk
```

This is the pattern I would expect in a mature enterprise OpenShift platform.

## 16. Sizing and Capacity Planning

### 16.1 What drives log platform sizing

Do not size logging by node count alone.

Important drivers:

- GB/day ingestion rate
- Burst rate
- Audit log volume
- Retention period
- Query time range
- Number of concurrent users
- Dashboard refresh rate
- Alert rule count
- Number of tenants
- Cardinality of labels
- Object storage latency
- Collector CPU/memory
- External sink throughput

### 16.2 Initial LokiStack sizing

General approach:

```text
Small clusters: start with a small supported LokiStack size.
Larger clusters: start with a medium supported size.
SNO/edge: use the minimum supported edge profile.
After 24+ hours: measure actual ingestion and resize.
```

Example metric for collector-sent bytes to Loki:

```promql
sum by (component_name) (
  rate(vector_component_sent_bytes_total{component_type="loki", component_kind="sink"}[5m])
)
```

Convert bytes/sec to GB/day:

```text
GB/day = bytes_per_second * 86400 / 1073741824
```

Example:

```text
5,242,880 bytes/sec
= 5,242,880 * 86,400 / 1,073,741,824
≈ 421 GB/day
```

### 16.3 Capacity planning formula

For object storage:

```text
Required storage ~= daily ingestion GB * retention days * compression/overhead factor
```

Example:

```text
Daily ingestion: 300 GB/day
Retention: 30 days
Raw volume: 9 TB
Add safety factor: 1.3
Plan: ~12 TB object storage budget
```

### 16.4 Audit log multiplier

Audit logs can be unexpectedly high-volume.

High audit volume is common when:

- Many controllers reconcile frequently.
- Many CI/CD pipelines create/delete objects.
- API audit profile is verbose.
- Admission webhooks mutate/validate heavily.
- Operators generate frequent API calls.
- A workload repeatedly fails and restarts.

Never enable broad audit forwarding to expensive storage without measuring.

### 16.5 Label cardinality planning

Loki performance depends heavily on labels.

Good labels:

```text
namespace
pod
container
log_type
cluster_id
environment
```

Dangerous labels:

```text
request_id
trace_id
user_id
session_id
pod_uid for every query pattern
full URL
IP address
error message
exception text
```

High cardinality causes:

- Too many streams
- High index overhead
- Slow queries
- Higher memory usage
- Ingestion pressure

### 16.6 Query cost planning

Bad query:

```logql
{log_type="application"} |~ "error|timeout|failed"
```

Better query:

```logql
{kubernetes_namespace_name="payments-prod", log_type="application"} |~ "(?i)error|timeout|failed"
```

Best operational habit:

> Start with selective labels, then filter text.

## 17. Reliability, Backpressure, and Failure Domains

### 17.1 Failure domains

| Component | Failure Impact |
|---|---|
| One collector pod | Logs from that node delayed/lost depending on buffer and rotation |
| All collectors | Cluster-wide log collection stops |
| Loki gateway | Ingestion/query access to Loki impacted |
| Ingesters | Writes and recent queries impacted |
| Object storage | Durable write/query path impacted |
| Querier/query frontend | Queries fail but ingestion may continue |
| External SIEM | Forwarding to that output fails; other outputs may continue |
| COO/UIPlugin | Console visualization unavailable, collection may continue |

### 17.2 Backpressure

Backpressure happens when downstream cannot accept logs as fast as collectors send them.

Causes:

- Loki rate limits
- External Splunk HEC throttling
- Kafka broker issue
- Network latency
- DNS failure
- Object storage slowness
- TLS handshake failures
- Too many large messages

Symptoms:

- Collector logs show retries or 429.
- Output lag increases.
- Collector memory/CPU rises.
- Logs appear late.
- Some records are dropped if rate limits/buffers are exceeded.

### 17.3 At-most-once vs at-least-once thinking

Not every output has the same delivery guarantees. Understand your sink and collector settings.

For compliance-critical audit logs:

- Prefer durable external systems.
- Use archive outputs.
- Monitor drops/retries.
- Avoid small buffers.
- Avoid aggressive drop filters unless policy-approved.

For high-volume debug logs:

- Dropping under pressure may be acceptable.
- Rate limits are useful.
- Short retention is enough.

### 17.4 Rolling updates

Collector changes can trigger rolling restarts of collector pods.

Before changing `ClusterLogForwarder` in production:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml > clf-backup-$(date +%F).yaml
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

After change:

```bash
oc apply -f clf.yaml
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -w
```

## 18. Network Architecture

### 18.1 Network paths

OpenShift Logging may require these flows:

```text
Collector -> LokiStack gateway
Collector -> external outputs
Collector -> Kafka/Splunk/S3/HTTP/Syslog/OTLP
Loki components -> object storage
Console/plugin -> LokiStack gateway/query path
Prometheus -> collector/Loki metrics endpoints
```

### 18.2 Collector network policy

In restrictive network environments, define collector network policy behavior.

Example:

```yaml
spec:
  collector:
    networkPolicy:
      ruleSet: RestrictIngressEgress
```

Or:

```yaml
spec:
  collector:
    networkPolicy:
      ruleSet: AllowAllIngressEgress
```

Use `RestrictIngressEgress` in mature production environments when you know all ports/destinations.

Use `AllowAllIngressEgress` carefully, usually to restore logging in a restricted cluster while troubleshooting.

### 18.3 AdminNetworkPolicy impact

If cluster-wide AdminNetworkPolicy blocks pod egress, logging can fail even when the collector config is valid.

Check:

```bash
oc get networkpolicy -A | grep -i logging
oc get adminnetworkpolicy
oc get baselineadminnetworkpolicy
```

### 18.4 DNS and proxy

For external outputs, verify:

```bash
oc debug -n openshift-logging deploy/cluster-logging-operator -- nslookup splunk.example.com
```

Or run a temporary pod in a namespace allowed by network policy:

```bash
oc run net-test -n openshift-logging --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside:

```bash
curl -vk https://splunk.example.com:8088
curl -vk https://s3.example.com
```

### 18.5 TLS CA chain

Common TLS failures:

```text
certificate verify failed
self-signed certificate in certificate chain
unknown authority
hostname mismatch
expired certificate
```

Fix approach:

1. Identify which connection fails.
2. Get the server certificate chain.
3. Put the CA bundle in a ConfigMap or Secret as required by the output type.
4. Reference it in the `ClusterLogForwarder` output or LokiStack storage config.
5. Restart/reconcile and verify collector logs.

### 20.7 Create ClusterLogForwarder

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  managementState: Managed
  serviceAccount:
    name: collector
  collector:
    resources:
      requests:
        cpu: 200m
        memory: 736Mi
      limits:
        cpu: 1
        memory: 1Gi
    networkPolicy:
      ruleSet: RestrictIngressEgress

  inputs:
  - name: prod-apps
    type: application
    application:
      includes:
      - namespace: payments-prod
      - namespace: orders-prod
      - namespace: customer-prod
      tuning:
        rateLimitPerContainer:
          maxRecordsPerSecond: 500

  - name: audit-api-only
    type: audit
    audit:
      sources:
      - kubeAPI
      - openshiftAPI

  filters:
  - name: drop-debug
    type: drop
    drop:
    - test:
      - field: .level
        matches: debug

  - name: prune-audit-heavy-fields
    type: prune
    prune:
      in:
      - .audit.requestObject
      - .audit.responseObject
      - .audit.managedFields

  - name: detect-stacktraces
    type: detectMultilineException

  outputs:
  - name: lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt

  - name: splunk-security
    type: splunk
    splunk:
      authentication:
        token:
          secretName: splunk-token
          key: hecToken
      url: https://splunk.example.com:8088
      index: openshift_prod

  - name: audit-s3-archive
    type: s3
    s3:
      url: https://s3.example.com
      bucket: openshift-audit-prod
      keyPrefix: cluster-a/audit
      authentication:
        type: awsAccessKey
        awsAccessKey:
          keyId:
            secretName: audit-s3-secret
            key: access_key_id
          keySecret:
            secretName: audit-s3-secret
            key: secret_access_key

  pipelines:
  - name: prod-apps-to-loki
    inputRefs:
    - prod-apps
    filterRefs:
    - detect-stacktraces
    - drop-debug
    outputRefs:
    - lokistack

  - name: infrastructure-to-loki-and-splunk
    inputRefs:
    - infrastructure
    outputRefs:
    - lokistack
    - splunk-security

  - name: audit-to-security-and-archive
    inputRefs:
    - audit-api-only
    filterRefs:
    - prune-audit-heavy-fields
    outputRefs:
    - splunk-security
    - audit-s3-archive
```

## 22. Common Failure Scenarios and Fixes

### 22.1 `ClusterLogForwarder` Ready=True but no logs in Loki

Likely causes:

- Missing `tls.ca` block for LokiStack output.
- Collector cannot verify Loki gateway certificate.
- Collector logs show certificate verification failure.

Fix:

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

Then:

```bash
oc apply -f clf.yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

### 22.2 Collector pods missing

Check:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Likely causes:

- Missing service account.
- Missing ClusterRoleBinding for requested log type.
- Invalid CLF spec.
- Operator reconciliation failure.

Fix sequence:

```bash
oc create sa collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-application-logs system:serviceaccount:openshift-logging:collector
oc adm policy add-cluster-role-to-user collect-infrastructure-logs system:serviceaccount:openshift-logging:collector
oc adm policy add-cluster-role-to-user collect-audit-logs system:serviceaccount:openshift-logging:collector
oc apply -f clusterlogforwarder.yaml
```

### 22.3 Audit logs not collected

Likely causes:

- `collect-audit-logs` not bound.
- Pipeline does not include `audit` or custom audit input.
- Audit input source selection excludes desired source.
- Filters drop/prune too aggressively.

Check:

```bash
oc get clusterrolebinding -o wide | grep collect-audit
oc get clusterlogforwarder instance -n openshift-logging -o yaml | grep -A20 audit
```

### 22.4 Only some namespace logs missing

Likely causes:

- Application input includes/excludes namespace incorrectly.
- Label selector mismatch.
- Workload is writing logs to file inside container, not stdout/stderr.
- Logs are multiline and not being reconstructed as expected.
- Developer querying with wrong label names/schema.

Check pod labels:

```bash
oc get pod -n <namespace> --show-labels
```

Check application emits stdout/stderr:

```bash
oc logs -n <namespace> <pod>
```

If `oc logs` works but centralized logs do not, focus on collector/CLF path.

If `oc logs` itself shows nothing, the application is not writing to container stdout/stderr.

### 22.5 Loki pods pending

Likely causes:

- Not enough CPU/memory.
- PVC cannot bind.
- Wrong StorageClass.
- NodeSelector/toleration mismatch.
- ODF/storage not ready.

Check:

```bash
oc get pods -n openshift-logging | grep loki
oc describe pod -n openshift-logging <pending-pod>
oc get pvc -n openshift-logging
oc describe pvc -n openshift-logging <pvc>
oc get sc
```

### 22.6 Loki ingestion 429 Too Many Requests

Likely causes:

- Initial backlog flush.
- LokiStack too small.
- Burst ingestion too high.
- A noisy application.
- Audit logs too verbose.

Fix:

- Wait briefly if during initial deployment.
- Measure GB/day.
- Resize LokiStack.
- Add rate limits for noisy inputs.
- Drop/prune unnecessary logs.
- Move audit/archive logs to separate pipeline.

### 22.7 Query is slow or times out

Likely causes:

- Query too broad.
- Time range too large.
- High cardinality labels.
- Object storage latency.
- Querier CPU/memory saturation.
- Too many dashboard refreshes.

Fix:

- Use namespace/log type labels.
- Reduce time range.
- Avoid broad regex.
- Add/adjust LokiStack size.
- Review label strategy.

### 22.8 External Splunk not receiving logs

Check:

```bash
oc get secret splunk-token -n openshift-logging -o yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 | grep -i splunk
```

Likely causes:

- Wrong HEC URL or port.
- Wrong token secret/key.
- TLS CA problem.
- NetworkPolicy blocks egress.
- Splunk index not configured.
- Splunk HEC disabled.
- Proxy/firewall issue.

### 22.9 Kafka output stalled

Likely causes:

- Broker DNS unavailable.
- SASL mechanism mismatch.
- TLS cert expired.
- Topic missing or ACL denied.
- Broker requires port in URL.
- Kafka cluster overloaded.

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 | egrep -i 'kafka|sasl|broker|topic|tls'
```

### 22.10 No Logs tab in console

Likely causes:

- Cluster Observability Operator not installed.
- `UIPlugin` not created.
- UIPlugin references wrong LokiStack name.
- Browser/console plugin not refreshed.

Check:

```bash
oc get csv -A | grep -i observability
oc get uiplugin logging -o yaml
oc get lokistack -A
```

## 23. Operational Best Practices

### 23.1 Design principles

1. Separate application, infrastructure, and audit pipelines.
2. Do not route everything everywhere.
3. Keep Loki labels low-cardinality.
4. Use LokiStack for short-term troubleshooting.
5. Use SIEM/archive for long-term compliance and security.
6. Prune audit fields before sending outside the cluster unless policy requires raw logs.
7. Rate-limit noisy applications.
8. Monitor collector drops and output errors.
9. Treat logging changes as production-impacting platform changes.
10. Keep a rollback copy of `ClusterLogForwarder`.

### 23.2 GitOps recommendation

Store these in Git:

```text
namespaces
operator subscriptions
object storage secret templates, not raw secrets
LokiStack CR
ClusterLogForwarder CR
UIPlugin CR
LogFileMetricExporter CR
NetworkPolicy/AdminNetworkPolicy exceptions
alerting rules
runbooks
```

Use sealed secrets, external secrets, or Vault-style integration for sensitive credentials.

### 23.3 Change checklist

Before changing logging:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml > backup-clf.yaml
oc get lokistack logging-loki -n openshift-logging -o yaml > backup-lokistack.yaml
oc get pods -n openshift-logging -o wide
```

After changing:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Validation queries:

```logql
{log_type="application"}
{log_type="infrastructure"}
{log_type="audit"}
```

### 23.4 Retention strategy

Example retention model:

| Log Type | Short-term Loki | Long-term Archive | SIEM |
|---|---:|---:|---:|
| Application | 7-14 days | Optional | Error/security subset |
| Infrastructure | 14-30 days | Optional | Important cluster events |
| Audit | Short, restricted | 90-365+ days | Yes |
| Debug/noisy logs | Very short or dropped | No | No |

### 23.5 Naming standards

Use descriptive names:

```text
inputs:
  prod-apps
  audit-api-only
  openshift-infra

filters:
  drop-debug
  prune-audit-heavy-fields
  detect-stacktraces

outputs:
  lokistack
  splunk-security
  audit-s3-archive

pipelines:
  prod-apps-to-loki
  infrastructure-to-loki-and-splunk
  audit-to-security-and-archive
```

Avoid names like:

```text
test
out1
new-pipe
foo
```

### 23.6 Documentation standards

Every production `ClusterLogForwarder` should have comments or companion documentation explaining:

- Why each input exists
- Why each filter exists
- Which business/security team owns each output
- Retention expectation
- Data sensitivity
- Cost impact
- Runbook for failures

## 24. Interview and Real-World Admin Notes

### 24.1 How to explain architecture in an interview

A strong answer:

> In current OpenShift Logging, collection and forwarding are controlled by the Red Hat OpenShift Logging Operator through the `ClusterLogForwarder` resource. The collector is Vector, deployed as a DaemonSet, so it can read node-local container logs, infrastructure logs, and audit logs when the collector service account has the required cluster roles. Logs are routed through inputs, optional filters, and pipelines to outputs such as LokiStack, Splunk, Kafka, Syslog, S3, HTTP, or OTLP. If we use in-cluster storage, the Loki Operator manages a LokiStack, which stores data in object storage and exposes logs through a gateway with OpenShift-aware tenancy. If we need console visualization, the Cluster Observability Operator deploys a UIPlugin that adds Observe → Logs in the web console.

### 24.2 Senior-admin points to mention

- Logging 6 replaced the older Elasticsearch/Kibana/Fluentd-centered architecture.
- `ClusterLogForwarder` is now the central CR for collection and forwarding.
- RBAC must be granted before referencing log types.
- Audit logs need separate design due to sensitivity and volume.
- Loki label cardinality is a major performance concern.
- Object storage is part of the critical path for Loki.
- `Ready=True` on CLF does not always prove end-to-end delivery; always check collector logs and sink data.
- NetworkPolicy/AdminNetworkPolicy can silently break forwarding.
- External outputs need TLS, auth, DNS, firewall, and rate-limit monitoring.

### 24.3 Troubleshooting story example

Scenario:

```text
Application team says logs are not visible in Observe -> Logs.
```

Experienced admin workflow:

```bash
# 1. Is app writing logs?
oc logs -n payments-prod deploy/payment-api --tail=20

# 2. Does CLF include namespace?
oc get clusterlogforwarder instance -n openshift-logging -o yaml | less

# 3. Are collectors running on the node where pod is scheduled?
oc get pod -n payments-prod -o wide
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide

# 4. Is CLF healthy?
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

# 5. Are collector logs showing errors?
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100

# 6. Is Loki healthy?
oc get lokistack -A
oc get pods -n openshift-logging | grep loki

# 7. Query with selective labels.
# In console / LogQL:
{kubernetes_namespace_name="payments-prod"}
```

Conclusion depends on findings:

- If `oc logs` empty, app logging problem.
- If collector missing, platform logging problem.
- If CLF auth false, RBAC problem.
- If TLS error, CA/output config problem.
- If query too broad, user query pattern problem.

## Final Summary

OpenShift Logging architecture should be understood as a production-grade log routing and storage system:

```text
Application / Infrastructure / Audit / Receiver logs
        -> Vector collector DaemonSet
        -> ClusterLogForwarder inputs, filters, pipelines
        -> LokiStack and/or external outputs
        -> OpenShift console visualization through COO/UIPlugin
```

For advanced administration, focus on:

- Correct architecture identification
- Collector RBAC
- `ClusterLogForwarder` status
- Vector collector health
- LokiStack readiness and storage
- Output TLS/auth/network connectivity
- Audit log separation
- Label cardinality
- Query performance
- Storage retention and cost
- Clear runbooks and GitOps-managed configuration
