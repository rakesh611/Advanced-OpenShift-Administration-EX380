## 1. Executive Summary

Audit logs are one of the most important security telemetry streams in OpenShift. They answer operational and forensic questions such as:

- Who created or deleted a resource?
- Which user changed a `RoleBinding`, `ClusterRoleBinding`, `SecurityContextConstraints`, `NetworkPolicy`, or `Secret`?
- Which service account made a suspicious API call?
- Which API request failed with `403 Forbidden` or `401 Unauthorized`?
- Which workload triggered a Pod Security Admission audit violation?
- Was a change initiated by a human user, controller, operator, CI/CD pipeline, or compromised service account?

In OpenShift Logging, audit logs are treated as a separate log type from application and infrastructure logs. They are sensitive, high-volume, and usually have stricter access, retention, and forwarding requirements.

Key points for senior administrators:

1. **Audit log generation is controlled by the OpenShift API server audit configuration.**
2. **Audit log forwarding is controlled by OpenShift Logging and `ClusterLogForwarder`.**
3. **Audit logs are not automatically stored in the logging backend by default.** You must explicitly forward them.
4. **The collector service account must have `collect-audit-logs` before you add `audit` to a pipeline.** If you add audit input without the correct RBAC, the operator can stop the collector DaemonSet as a protective behavior.
5. **Audit logs are security records, not normal developer logs.** Treat them like privileged data.
6. **For compliance, forward audit logs to durable external storage, SIEM, or immutable archive.** Do not rely only on short-retention in-cluster storage.

## 2. What Are Audit Logs?

Audit logs are chronological records of security-relevant activity in the cluster. In Kubernetes/OpenShift, the most important audit stream comes from API server requests.

A Kubernetes/OpenShift audit event can show:

- The user or service account that made the request.
- The groups the identity belonged to.
- The source IP address.
- The user agent, such as `oc`, `kubectl`, `helm`, `argocd`, a controller, or an operator.
- The request verb, such as `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`, or `deletecollection`.
- The target API resource, namespace, name, API group, and API version.
- The request URI.
- The response code, such as `200`, `201`, `403`, `404`, `409`, or `500`.
- Authorization decision and reason.
- Authentication-related annotations.
- Optional request body and response body, depending on audit level/profile.

In simple terms:

> Application logs tell you what the application did. Infrastructure logs tell you what the platform components did. Audit logs tell you who asked the platform to do something.

---

## 3. Audit Logs vs Application Logs vs Infrastructure Logs

| Log Type | Primary Source | Main Consumer | Typical Use | Sensitivity |
|---|---|---|---|---|
| Application logs | User application containers | Developers, app SREs | Debug app behavior | Medium to high, depending on app data |
| Infrastructure logs | OpenShift components, node journal, system namespaces | Platform SREs | Troubleshoot cluster components | High |
| Audit logs | API servers, node `auditd`, OVN audit | Security, compliance, platform admins | Forensics, compliance, API activity review | Very high |

Audit logs are different because they often contain identities, authorization decisions, request paths, object references, and sometimes request/response payloads. They can expose sensitive metadata even when request bodies are not logged.

Examples of sensitive audit records:

- A user reading a `Secret` object.
- A CI service account creating privileged workloads.
- A cluster admin granting `cluster-admin` to another user.
- An operator modifying security-sensitive cluster resources.
- An unauthorized user repeatedly receiving `403` responses.
- OAuth login failures for important users.

## 4. OpenShift Audit Log Sources

OpenShift Logging recognizes the reserved audit input type `audit`. In Logging 6.x, audit sources can include:

| Audit Source | Meaning | Why It Matters |
|---|---|---|
| `kubeAPI` | Kubernetes API server audit logs | Core Kubernetes API calls such as pods, secrets, configmaps, deployments, roles, rolebindings, namespaces |
| `openshiftAPI` | OpenShift API server audit logs | OpenShift-specific APIs such as routes, users, groups, image streams, builds, projects |
| `auditd` | Node audit daemon logs | Host-level Linux audit events from nodes |
| `ovn` | Open Virtual Network audit logs | Network-related audit information from OVN-Kubernetes |

If you use the reserved `audit` input without selecting sources, the collector attempts to gather all supported audit sources.

### Senior-admin interpretation

In production, you rarely treat all audit sources the same way. A common design is:

- Send `kubeAPI` and `openshiftAPI` to SIEM for API forensics.
- Send `auditd` to security data lake or host security tooling.
- Send `ovn` to network security monitoring.
- Send a reduced/filtered copy to in-cluster LokiStack for short-term troubleshooting.
- Send the raw or near-raw stream to immutable external storage for compliance.

## 5. Audit Event Anatomy

A typical Kubernetes/OpenShift API audit event is JSON.

Example shape:

```json
{
  "kind": "Event",
  "apiVersion": "audit.k8s.io/v1",
  "level": "Metadata",
  "auditID": "cfce8a0b-b5f5-4365-8c9f-79c1227d10f9",
  "stage": "ResponseComplete",
  "requestURI": "/api/v1/namespaces/default/secrets/my-secret",
  "verb": "get",
  "user": {
    "username": "system:serviceaccount:ci:deploy-bot",
    "groups": [
      "system:serviceaccounts",
      "system:serviceaccounts:ci",
      "system:authenticated"
    ]
  },
  "sourceIPs": ["10.128.0.12"],
  "userAgent": "oc/4.x kubernetes/$Format",
  "objectRef": {
    "resource": "secrets",
    "namespace": "default",
    "name": "my-secret",
    "apiVersion": "v1"
  },
  "responseStatus": {
    "metadata": {},
    "code": 200
  },
  "requestReceivedTimestamp": "2026-07-03T10:30:00.000000Z",
  "stageTimestamp": "2026-07-03T10:30:00.030000Z",
  "annotations": {
    "authorization.k8s.io/decision": "allow",
    "authorization.k8s.io/reason": "RBAC: allowed by RoleBinding ..."
  }
}
```

Important fields:

| Field | Meaning | Admin Use |
|---|---|---|
| `auditID` | Unique ID for the audited request | Correlate related stages for same request |
| `stage` | Lifecycle stage of the request | Usually filter on `ResponseComplete` for completed calls |
| `verb` | API action | Detect writes, deletes, secret reads |
| `user.username` | Actor identity | Human user or service account |
| `user.groups` | RBAC groups | Understand access path |
| `sourceIPs` | Client IP chain | Track source of API request |
| `userAgent` | Client tool/controller | Identify `oc`, controllers, GitOps, Helm, scripts |
| `objectRef` | Target resource | Identify affected resource |
| `responseStatus.code` | HTTP result | Detect failed access or successful modification |
| `annotations.authorization.k8s.io/decision` | Authorization result | `allow` or `forbid`/deny-related decisions |
| `requestObject` | Request body if logged | High-value but sensitive and high-volume |
| `responseObject` | Response body if logged | Very sensitive and potentially huge |

## 6. Audit Event Lifecycle and Stages

Kubernetes audit events can be emitted at different stages of request processing.

Common stages:

| Stage | Meaning | Practical Use |
|---|---|---|
| `RequestReceived` | API server received request before deeper processing | Very noisy; often omitted |
| `ResponseStarted` | Response headers sent; used mostly for long-running requests such as `watch` | Useful for watches/streams |
| `ResponseComplete` | Request completed and response body finished | Most useful for completed action analysis |
| `Panic` | Request processing panicked | Critical troubleshooting signal |

For most operational searches, start with:

```bash
jq 'select(.stage == "ResponseComplete")'
```

If you include `RequestReceived`, volume increases significantly and many events may not yet have final response status.

## 7. Audit Policy Levels

Audit level controls how much information is captured in an event.

| Level | Captures | Does Not Capture | Typical Use |
|---|---|---|---|
| `None` | Nothing; matching event is dropped | Everything | Suppress noisy low-value events |
| `Metadata` | Metadata such as user, verb, resource, timestamps, status | Request and response bodies | Default production-friendly level |
| `Request` | Metadata + request body | Response body | Write investigation, change tracking |
| `RequestResponse` | Metadata + request body + response body | Nothing for applicable requests | Deep debugging; use carefully |

### Production guidance

- Use `Metadata` for most events.
- Use `Request` only for selected write operations or short-term incident investigation.
- Use `RequestResponse` rarely because response bodies can be large and sensitive.
- Never blindly enable maximum audit detail across a large production cluster without capacity planning.

## 8. OpenShift API Server Audit Profiles

OpenShift exposes high-level audit profiles through the cluster `APIServer` configuration.

Check current configuration:

```bash
oc get apiserver cluster -o yaml
```

Edit profile:

```bash
oc edit apiserver cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  audit:
    profile: Default
```

Supported profiles commonly include:

| Profile | Meaning | Recommended Use |
|---|---|---|
| `Default` | Logs metadata for read and write requests; default production profile | Normal production baseline |
| `WriteRequestBodies` | Logs request bodies for write requests such as `create`, `update`, `patch`, `delete`, `deletecollection` | Temporary deeper change investigation |
| `AllRequestBodies` | Logs request bodies for many read and write requests | Short-lived troubleshooting only |
| `None` | Disables audit logging | Avoid in production unless a very specific, approved reason exists |

### Example: temporarily increase audit detail for investigation

```yaml
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  audit:
    profile: WriteRequestBodies
```

After changing the profile, verify rollout of API server revisions:

```bash
oc get kubeapiserver -o=jsonpath='{range .items[0].status.conditions[?(@.type=="NodeInstallerProgressing")]}{.reason}{"\n"}{.message}{"\n"}'
```

Expected final reason:

```text
AllNodesAtLatestRevision
```

### Custom rules by group

OpenShift also allows custom audit rules for groups.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  audit:
    customRules:
    - group: system:authenticated:oauth
      profile: WriteRequestBodies
    - group: system:authenticated
      profile: Default
    profile: Default
```

Important:

- Custom rules are evaluated top-to-bottom.
- First matching rule wins.
- Do not set top-level profile to `None` if you expect custom rules to work.
- Sensitive resources can still be restricted to metadata-only behavior by platform policy.

## 9. Two Different Layers: Audit Generation vs Audit Forwarding

This is one of the most important concepts.

### Layer 1: Audit generation

Controlled by OpenShift/Kubernetes API server audit configuration.

This decides:

- Which API requests are audited.
- Which audit level is used.
- Whether request or response bodies are captured.
- Whether audit logging is disabled.

Primary object:

```bash
oc get apiserver cluster -o yaml
```

### Layer 2: Audit forwarding

Controlled by Red Hat OpenShift Logging.

This decides:

- Whether generated audit logs are collected by the logging collector.
- Which audit sources are collected.
- Which filters are applied.
- Which destinations receive the audit logs.
- Whether logs go to LokiStack, Splunk, Kafka, syslog, CloudWatch, S3, Elasticsearch, or another endpoint.

Primary object:

```bash
oc get clusterlogforwarder.observability.openshift.io -A
```

### Why this matters

Changing `ClusterLogForwarder` does not change what the API server generates. It only changes what the collector forwards. Similarly, changing `APIServer` audit profile does not automatically send audit logs to Loki/SIEM. You need both layers configured correctly.

## 10. Where Audit Logs Live on OpenShift Nodes

On OpenShift control plane nodes, audit logs are exposed through node log paths such as:

- `kube-apiserver/`
- `openshift-apiserver/`
- `oauth-apiserver/`
- `oauth-server/`

You typically do not SSH into nodes to read these. Use `oc adm node-logs`.

OpenShift administrators should understand both:

1. **Direct node-level retrieval** for troubleshooting and support.
2. **Centralized forwarding** through OpenShift Logging for long-term visibility and retention.

## 12. Filtering Audit Logs with `jq`

Audit logs are JSON lines. `jq` is essential.

### Filter by user

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.user.username == "admin")'
```

### Filter by service account

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.user.username == "system:serviceaccount:ci:deploy-bot")'
```

### Filter write operations

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.verb | IN("create", "update", "patch", "delete", "deletecollection"))'
```

### Filter failed authorization events

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.responseStatus.code == 403)'
```

### Filter unauthorized requests

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.responseStatus.code == 401)'
```

### Filter secret access

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.resource == "secrets")'
```

### Filter RoleBinding and ClusterRoleBinding changes

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select((.objectRef.resource == "rolebindings" or .objectRef.resource == "clusterrolebindings") and (.verb | IN("create", "update", "patch", "delete")))'
```

### Filter SCC-related changes

```bash
oc adm node-logs <node> --path=openshift-apiserver/audit.log \
| jq 'select(.objectRef.resource == "securitycontextconstraints")'
```

### Filter a specific namespace

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.objectRef.namespace == "production")'
```

### Filter by user agent

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.userAgent | test("argocd|helm|oc|kubectl"; "i"))'
```

### Show compact high-value fields

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq -r '
  select(.stage == "ResponseComplete") |
  [.requestReceivedTimestamp,
   .user.username,
   .verb,
   .objectRef.namespace,
   .objectRef.resource,
   .objectRef.name,
   .responseStatus.code,
   .userAgent] | @tsv'
```

### Detect possible Pod Security Admission audit violations

```bash
oc adm node-logs <node> --path=kube-apiserver/audit.log \
| jq 'select(.annotations."pod-security.kubernetes.io/audit-violations" != null)'
```

## 13. Collecting Audit Logs with Must-Gather

Audit logs are not always included in a normal must-gather collection because they can be large and sensitive.

Collect audit logs explicitly:

```bash
oc adm must-gather -- /usr/bin/gather_audit_logs
```

Use cases:

- Red Hat support case.
- Security incident review.
- Pod Security Admission violation investigation.
- Unknown RBAC or authentication issue.
- API server behavior investigation.

Security handling:

- Store must-gather output securely.
- Treat the archive as sensitive.
- Do not upload to public ticketing systems or shared drives.
- Scrub or encrypt before transferring outside your organization.

## 14. OpenShift Logging Architecture for Audit Logs

OpenShift Logging uses a collector that runs on cluster nodes, normally as a DaemonSet. The collector reads configured log sources and forwards them through pipelines defined by `ClusterLogForwarder`.

### Conceptual flow

```text
API server / auditd / OVN
        |
        v
Node audit files / journal / component logs
        |
        v
OpenShift Logging collector, usually Vector
        |
        v
ClusterLogForwarder inputs -> filters -> outputs -> pipelines
        |
        +--> LokiStack for short-term search
        +--> SIEM for security analytics
        +--> S3/object storage for archive
        +--> Kafka for streaming
        +--> Splunk/Elastic/CloudWatch/Datadog/etc.
```

### Reserved log input types

`ClusterLogForwarder` recognizes high-level input references:

```yaml
inputRefs:
- application
- infrastructure
- audit
```

For audit logs, use:

```yaml
inputRefs:
- audit
```

or define a named audit input with selected sources.

## 15. Collector Permissions and RBAC

In Logging 6.x, collector permissions are explicit. Create a service account and grant the exact log collection roles needed.

### Create collector service account

```bash
oc create sa collector -n openshift-logging
```

### Grant audit log collection permission

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### If you also collect application and infrastructure logs

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

### Verify cluster role bindings

```bash
oc get clusterrolebinding -o wide | grep collect
```

### Critical order of operations

Correct order:

```text
1. Create service account.
2. Grant collect-audit-logs.
3. Create or update ClusterLogForwarder with audit input.
4. Verify status and collector pods.
```

Wrong order:

```text
1. Add audit to ClusterLogForwarder.
2. Forget collect-audit-logs.
3. Collector authorization fails.
4. Log collection can stop.
```

This behavior is intentional. The operator avoids running a collector with unauthorized or partial access to requested log types.

## 16. Enable Audit Log Forwarding to LokiStack

This example forwards audit logs to an in-cluster LokiStack.

> Adjust `target.name`, `target.namespace`, and CA config map names according to your LokiStack deployment.

### Example `ClusterLogForwarder`

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: audit-to-loki
    inputRefs:
    - audit
    outputRefs:
    - lokistack
```

Apply:

```bash
oc apply -f audit-to-loki.yaml
```

Verify readiness:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Look for:

```text
Ready=True
observability.openshift.io/Authorized=True
observability.openshift.io/Valid=True
```

Verify collector pods:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
```

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

## 17. Forward Only Selected Audit Sources

You may not want every audit source in the same pipeline. Use named inputs.

### Example: only API audit logs, not node `auditd`

```yaml
apiVersion: observability.openshift.io/v1

  name: instance
  namespace: openshift-logging

  serviceAccount:
    name: collector
  inputs:
  - name: api-audit-only
    type: audit
    audit:
      sources:
      - kubeAPI
      - openshiftAPI
  outputs:
  - name: lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging

  - name: api-audit-to-loki

    - api-audit-only

    - lokistack
```

## 18. Forward Audit Logs to External Systems

Audit logs are often forwarded outside the cluster for retention and security analytics.

Common destinations:

| Destination | Use Case |
|---|---|
| SIEM | Detection, correlation, alerting, investigation |
| S3/object storage | Long-term archive and compliance retention |
| Kafka | Streaming pipeline to multiple consumers |
| Splunk | Security operations and search |
| Elasticsearch/OpenSearch | Search and analytics |
| Syslog | Legacy SOC ingestion |
| CloudWatch | AWS-native monitoring |
| Datadog | SaaS observability/security |
| HTTP endpoint | Custom collector or webhook-style pipeline |

### Pattern: short-term Loki + long-term archive

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: lokistack-short-retention
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  - name: siem-splunk
    type: splunk
    splunk:
      url: https://splunk-hec.example.com:8088
      authentication:
        token:
          secretName: splunk-hec-token
          key: token
  pipelines:
  - name: audit-to-loki-and-siem
    inputRefs:
    - audit
    outputRefs:
    - lokistack-short-retention
    - siem-splunk
```

### Pattern: compliance archive and monitoring split

```yaml
pipelines:
- name: audit-to-archive-and-monitoring
  inputRefs:
  - audit
  outputRefs:
  - s3-compliance-archive
  - security-monitoring
```

Senior design point: when sending to two outputs, plan for independent failure handling. One destination may fail while another continues receiving records.

## 19. API Audit Filtering with `kubeAPIAudit`

The `kubeAPIAudit` filter is used to reduce audit event volume and event size. It uses a Kubernetes audit-policy-like structure.

### Why filter audit logs?

Audit logs can be extremely noisy because controllers constantly call the API. Without filtering, storage and SIEM ingestion costs can become high.

Use filtering to:

- Remove low-value `get`, `list`, and `watch` noise.
- Keep writes to sensitive resources.
- Keep denied requests.
- Keep RBAC changes.
- Reduce request/response body capture.
- Keep compliance-relevant events while dropping operational noise.

### Important behavior

Rules are evaluated in order. The first matching rule applies.

Audit levels:

```text
None             Drop event
Metadata         Keep metadata only
Request          Keep metadata + request body
RequestResponse  Keep metadata + request body + response body
```

### Example `kubeAPIAudit` filter

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  filters:
  - name: security-audit-policy
    type: kubeAPIAudit
    kubeAPIAudit:
      omitStages:
      - RequestReceived
      rules:
      # Keep RBAC changes with request body.
      - level: Request
        verbs:
        - create
        - update
        - patch
        - delete
        resources:
        - group: rbac.authorization.k8s.io
          resources:
          - roles
          - rolebindings
          - clusterroles
          - clusterrolebindings

      # Keep Secret access metadata, but avoid logging bodies.
      - level: Metadata
        resources:
        - group: ""
          resources:
          - secrets

      # Keep SCC changes.
      - level: Request
        verbs:
        - create
        - update
        - patch
        - delete
        resources:
        - group: security.openshift.io
          resources:
          - securitycontextconstraints

      # Drop noisy watch requests from known system components.
      - level: None
        verbs:
        - watch
        userGroups:
        - system:nodes

      # Catch-all: metadata for everything else.
      - level: Metadata
  outputs:
  - name: lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: filtered-audit-to-loki
    inputRefs:
    - audit
    filterRefs:
    - security-audit-policy
    outputRefs:
    - lokistack
```

### Recommended rule strategy

A practical production policy is:

1. Omit `RequestReceived` unless specifically needed.
2. Preserve denied/forbidden requests.
3. Preserve all RBAC changes.
4. Preserve all authentication/OAuth-related anomalies.
5. Preserve `Secret` access metadata, not bodies.
6. Preserve SCC, admission, project, namespace, network policy, route, image, and operator changes.
7. Drop known noisy watches from trusted controllers only after validating you will not lose required compliance data.
8. Use a final catch-all rule.

## 20. Prune and Drop Filters for Audit Logs

### Drop filter

A `drop` filter removes entire records when conditions match.

Example: drop noisy successful read-only requests from a specific service account:

```yaml
filters:
- name: drop-noisy-reader
  type: drop
  drop:
  - test:
    - field: .user.username
      matches: '^system:serviceaccount:monitoring:readonly-bot$'
    - field: .verb
      matches: '^(get|list|watch)$'
    - field: .responseStatus.code
      matches: '^200$'
```

### Prune filter

A `prune` filter removes selected fields from records.

Example: remove Kubernetes annotations and labels before forwarding to a third-party endpoint:

```yaml
filters:
- name: prune-sensitive-metadata
  type: prune
  prune:
    in:
    - .kubernetes.annotations
    - .kubernetes.labels
```

### Required field warning

Do not try to prune required fields such as:

- `.log_type`
- `.log_source`
- `.message`
- `.kubernetes.namespace_name`
- `.kubernetes.pod_name`
- `.kubernetes.container_name`
- `.level`

The operator can mark the configuration invalid if required fields are pruned.

### Filter ordering

Recommended order:

```text
1. kubeAPIAudit or drop filters to reduce complete records.
2. prune filters to remove sensitive fields from remaining records.
3. labels/enrichment filters last.
```

Drop first, prune second. Dropping first reduces processing work.

## 21. Security and Compliance Design

Audit logs are high-value security records. Design around confidentiality, integrity, availability, and retention.

### Confidentiality

- Restrict access to audit logs.
- Avoid exposing audit logs to project developers by default.
- Do not place audit logs in the same tenant/query path as normal app logs unless access controls are correct.
- Treat `Request` and `RequestResponse` level logs as sensitive because they can include object payloads.
- Mask/prune sensitive fields before sending to third-party SaaS, if required by policy.

### Integrity

- Forward logs to a system where cluster admins cannot silently tamper with historical records.
- Prefer immutable object storage, WORM, legal hold, or SIEM with tamper-evident controls for compliance use cases.
- Ensure time synchronization across cluster nodes.
- Preserve `auditID`, timestamps, user identity, and source IP fields.

### Availability

- Do not depend only on ephemeral node files.
- Do not depend only on in-cluster LokiStack for regulatory retention.
- Monitor collector health and output failures.
- Capacity-plan for spikes during incidents, upgrades, and controller loops.

### Retention

Typical patterns:

| Retention Tier | Destination | Purpose |
|---|---|---|
| 7–30 days | LokiStack | Quick troubleshooting |
| 90–180 days | SIEM/search | Security investigation |
| 1–7 years | Object storage/archive | Compliance and audit requirements |

Actual retention depends on your organization, regulatory framework, and data classification.

## 22. Retention, Storage, and Cost Planning

Audit logs can be more expensive than application logs because:

- API servers generate many events.
- Controllers continuously read/watch/list resources.
- Request and response bodies increase event size.
- Security teams often require longer retention.
- SIEM ingestion is commonly priced by volume.

### Capacity planning inputs

Collect the following before deciding retention:

- Number of nodes.
- Number of namespaces.
- Number of pods/controllers/operators.
- API request rate.
- Current audit profile.
- Whether request bodies are enabled.
- Number of destinations.
- Compression support in output system.
- Required retention period.
- Expected incident spike volume.

### Cost-reduction methods

- Omit `RequestReceived` stage.
- Keep metadata for most events.
- Use request bodies only for selected high-value writes.
- Drop known low-value watches only after approval.
- Route detailed logs to cheaper archive, summarized logs to expensive SIEM.
- Use pipeline splitting: raw to archive, filtered to SIEM.
- Use object storage lifecycle policies.

### Example routing design

```text
Raw audit logs      -> S3 immutable archive, 1 year retention
Filtered audit logs -> SIEM, 180 days retention
Small subset        -> LokiStack, 14 days retention
```

## 23. Performance Considerations

Audit logging affects multiple components:

| Component | Impact |
|---|---|
| API server | More CPU, memory, and I/O when audit detail increases |
| Node storage | More writes and rotation pressure |
| Collector | More CPU/memory for parsing, filtering, batching, forwarding |
| Network | More egress traffic to external outputs |
| Loki/SIEM | More ingestion, indexing, and query cost |

### High-risk settings

Be careful with:

- `AllRequestBodies` cluster-wide.
- `RequestResponse` on broad resource sets.
- Long retention in high-cardinality Loki labels.
- Sending full audit stream to multiple expensive outputs.
- Missing rate/buffer tuning under high load.

### Collector resource tuning

You can tune collector resources in `ClusterLogForwarder`.

Example:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    resources:
      requests:
        memory: 1Gi
        cpu: 200m
      limits:
        memory: 2Gi
        cpu: 1000m
```

Actual values depend on cluster size and log volume. Monitor before and after changes.

### Rollout strategy

For large clusters, avoid restarting all collectors at once.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    maxUnavailable: 10%
```

## 25. Troubleshooting Audit Log Forwarding

### Symptom: collector pods disappear after adding audit input

Likely cause: missing `collect-audit-logs` role binding.

Check:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Fix:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Then re-check collector pods:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
```

### Symptom: `ClusterLogForwarder` `Authorized=False`

Cause: service account lacks required log collection role for one or more input types.

Check service account name:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml | yq '.spec.serviceAccount.name'
```

Check bindings:

```bash
oc get clusterrolebinding -o wide | grep collector
```

Fix required roles:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### Symptom: `Ready=True` but no logs in LokiStack

Possible causes:

- Missing or wrong `tls.ca` for LokiStack gateway.
- Wrong LokiStack target name/namespace.
- Tenant/access mismatch.
- Collector cannot reach gateway due to network policy.
- Output authentication issue.
- Querying wrong log type/tenant in console.

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
```

Check LokiStack:

```bash
oc get lokistack -A
oc get pods -n openshift-logging | grep loki
```

Check services:

```bash
oc get svc -n openshift-logging | grep loki
```

### Symptom: no audit records but app/infrastructure logs work

Check:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Confirm:

```yaml
pipelines:
- inputRefs:
  - audit
```

Then confirm audit source generation at node level:

```bash
oc adm node-logs --role=master --path=kube-apiserver/ | head
```

If node-level audit logs exist but not in log store, the problem is in collection/forwarding, not generation.

### Symptom: audit volume too high

Actions:

1. Review audit profile:

```bash
oc get apiserver cluster -o yaml | yq '.spec.audit'
```

2. Avoid broad `AllRequestBodies`.
3. Add `kubeAPIAudit` filter.
4. Omit `RequestReceived`.
5. Split raw archive and filtered SIEM streams.
6. Review noisy controllers/user agents.

### Symptom: SIEM ingestion cost spike

Analyze top users and verbs:

```bash
jq -r '[.user.username, .verb] | @tsv' kube-audit.log \
| sort | uniq -c | sort -nr | head -30
```

Top resources:

```bash
jq -r '[.objectRef.apiGroup // "core", .objectRef.resource, .verb] | @tsv' kube-audit.log \
| sort | uniq -c | sort -nr | head -30
```

Top user agents:

```bash
jq -r '.userAgent // "-"' kube-audit.log \
| sort | uniq -c | sort -nr | head -30
```

## 27. Interview and Exam Notes

### Common questions

**Q1. Are audit logs stored by OpenShift Logging by default?**  
No. You must configure `ClusterLogForwarder` to forward audit logs to a storage/output.

**Q2. What RBAC is required for the collector to collect audit logs?**  
The collector service account must be bound to `collect-audit-logs`.

**Q3. What happens if you add `audit` to `inputRefs` without permission?**  
The `ClusterLogForwarder` becomes unauthorized and the operator can remove/stop the collector DaemonSet to avoid unauthorized partial collection.

**Q4. What are the common audit sources?**  
`kubeAPI`, `openshiftAPI`, `auditd`, and `ovn`.

**Q5. What is the difference between `APIServer` audit profile and `ClusterLogForwarder` audit input?**  
`APIServer` controls what audit events are generated and at what level. `ClusterLogForwarder` controls collection, filtering, and forwarding.

**Q6. Which audit level includes request and response bodies?**  
`RequestResponse`.

**Q7. Which audit level includes request body but not response body?**  
`Request`.

**Q8. Which stage is usually most useful for completed API calls?**  
`ResponseComplete`.

**Q9. Which command gathers audit logs for support?**

```bash
oc adm must-gather -- /usr/bin/gather_audit_logs
```

**Q10. Which command lists Kubernetes API server audit logs?**

```bash
oc adm node-logs --role=master --path=kube-apiserver/
```

## 29. Common Mistakes

### Mistake 1: Confusing generated audit logs with forwarded audit logs

You might see logs with `oc adm node-logs`, but they will not appear in Loki/SIEM unless forwarding is configured.

### Mistake 2: Adding `audit` input before RBAC

Always bind `collect-audit-logs` first.

### Mistake 3: Sending audit logs to the same place as developer logs

Audit logs require stricter access control.

### Mistake 4: Enabling request/response bodies without capacity planning

This can cause large storage, CPU, memory, and SIEM cost impact.

### Mistake 5: Over-filtering audit logs

Dropping too much can break forensic and compliance value. Validate with security/compliance teams before removing event classes.

### Mistake 6: Keeping audit logs only in-cluster

If the cluster is compromised or deleted, audit evidence can be lost. Forward to external durable storage.

### Mistake 7: Ignoring OAuth audit logs

Authentication failures and login attempts are often visible in OAuth audit streams, not only kube-apiserver logs.

### Mistake 8: No documented rollback

If you temporarily set `WriteRequestBodies` or `AllRequestBodies`, document the rollback command and scheduled end time.

## Appendix C: Senior Admin Mental Model

Think of audit logs as a chain of custody for cluster API activity:

```text
Identity -> API request -> Authorization/admission -> Resource action -> Audit event -> Collector -> Filter -> Secure destination -> Retention/search
```

Every production design should answer:

1. Are audit events generated at the right level?
2. Are they collected from the right sources?
3. Are they forwarded to the right destinations?
4. Are they protected from unauthorized readers?
5. Are they retained long enough?
6. Can security teams search them quickly?
7. Can we prove they were not silently modified or lost?
8. Can we reduce cost without losing forensic value?
