# Missing Logs Troubleshooting in OpenShift Logging

**Audience:** Advanced OpenShift Administration / OpenShift Logging operations  
**Experience level:** 10+ years Linux, Kubernetes, OpenShift, SRE, platform operations  
**Focus:** Missing application, infrastructure, audit, event, LokiStack, Vector collector, and external forwarded logs  
**Modern stack covered:** Red Hat OpenShift Logging 6.x with `ClusterLogForwarder` API `observability.openshift.io/v1`, Vector collector, LokiStack, and external outputs  
**Legacy notes included:** Fluentd and Elasticsearch where still seen in older clusters

---

## 1. What “missing logs” really means

In OpenShift, “missing logs” is not one problem. It can mean many different failure points:

| Symptom | Most likely layer |
|---|---|
| `oc logs` also shows nothing | Application/container logging problem |
| `oc logs` shows logs, but Observe → Logs does not | Collection, forwarding, Loki, query, RBAC, tenant, or time-range issue |
| Logs appear for some namespaces but not one namespace | `ClusterLogForwarder` input selector, namespace classification, RBAC, filter, or query issue |
| Logs appear for some nodes only | Collector DaemonSet scheduling, node health, journal/container log path, taint/toleration, resource issue |
| Logs reach Loki but not external SIEM | Pipeline/output problem, external auth, TLS, network, rate limit, topic/index/tenant mismatch |
| Old logs disappeared | Retention, compaction, object storage lifecycle, Loki short-term storage expectation |
| Audit logs missing | Audit input not configured, missing `collect-audit-logs`, audit policy, wrong tenant/query |
| Kubernetes events missing | Event Router not installed or not producing logs |

The correct approach is to prove where the log disappeared in the pipeline, not to restart everything.

## 2. OpenShift Logging log flow: where logs can disappear

A simplified end-to-end path:

```text
Application stdout/stderr
        |
        v
CRI-O container log file on node
/var/log/pods/... and /var/log/containers/...
        |
        v
Vector collector DaemonSet pod on each node
        |
        v
ClusterLogForwarder input selection
application / infrastructure / audit / custom inputs
        |
        v
Filters
(drop, prune, parse, label, rate limit)
        |
        v
Outputs
LokiStack / Kafka / Splunk / HTTP / syslog / Elasticsearch / CloudWatch / S3 / Azure / GCP / OTLP
        |
        v
Query or visualization layer
OpenShift Observe -> Logs / Grafana / Splunk / SIEM / LogQL / external search
```

For troubleshooting, always walk the path left to right:

1. Did the workload produce logs?
2. Did the node write the container logs?
3. Is a collector running on that node?
4. Is `ClusterLogForwarder` valid, authorized, and ready?
5. Does the configured input actually select this namespace, pod, container, or log type?
6. Is any filter dropping it?
7. Is the output reachable and accepting writes?
8. Is Loki/external storage ingesting, indexing, and retaining the logs?
9. Is the query looking at the correct tenant, labels, namespace, log type, and time range?

## 3. Golden rules for senior troubleshooting

### 3.1 Do not begin with pod restarts

Restarting collectors can hide evidence. First capture:

```bash
oc get clusterlogforwarder -A -o wide
oc get pods -n openshift-logging -o wide
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -50
oc get lokistack -A
oc get csv -A | egrep -i 'logging|loki|observability'
```

Then inspect the current state.

### 3.2 Always define the missing log precisely

Before debugging, write down:

```text
Namespace:
Pod:
Container:
Node:
Expected time range:
Log type: application / infrastructure / audit / event
Expected destination: Observe -> Logs / LokiStack / Splunk / Kafka / external SIEM
Example missing message text:
```

Use that information in every command.

### 3.3 Compare source of truth with destination

For application logs, source of truth is usually `oc logs`:

```bash
NS=myapp
POD=myapp-abc123
CONTAINER=mycontainer

oc -n $NS logs $POD -c $CONTAINER --since=30m --timestamps | tail -50
```

If the message is not in `oc logs`, OpenShift Logging cannot collect it through the standard container log path.

### 3.4 Never add `audit` to `inputRefs` before granting RBAC

In Logging 6.x, the collector service account must have the correct `ClusterRoleBinding` before the log type is referenced. If a `ClusterLogForwarder` references a log type that the service account is not authorized to collect, the Operator can remove the collector DaemonSet as a protective action. This can stop all collection.

## 4. Quick triage command set

Use this first in a production incident.

```bash
# 1. Confirm logging resources
oc get ns openshift-logging
oc get clusterlogforwarder -A
oc get lokistack -A
oc get pods -n openshift-logging -o wide

# 2. Check ClusterLogForwarder status conditions
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

# If the CLF has a different name or namespace:
oc get clusterlogforwarder -A
oc get clusterlogforwarder <name> -n <namespace> \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

# 3. Check collector pods
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m --tail=200

# Some older or mixed clusters might use different labels:
oc get pods -n openshift-logging --show-labels | egrep -i 'collector|vector|fluentd'
oc logs -n openshift-logging -l component=collector --since=30m --tail=200

# 4. Check operator logs
oc get pods -n openshift-logging | egrep -i 'operator|logging|loki'
oc logs -n openshift-logging -l name=cluster-logging-operator --since=30m --tail=200

# 5. Check Loki components
oc get pods -n openshift-logging | egrep -i 'loki|gateway|ingester|querier|distributor|compactor|index'
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -80
```

If you see no collector pods, jump to section **8. Collector not running**.

## 5. Confirm the application is actually producing collectable logs

### 5.1 Check current and previous container logs

```bash
NS=myapp
POD=$(oc -n $NS get pod -l app=myapp -o jsonpath='{.items[0].metadata.name}')

oc -n $NS logs $POD --all-containers=true --since=30m --timestamps | tail -100
oc -n $NS logs $POD --all-containers=true --previous --timestamps | tail -100
```

If logs are only visible with `--previous`, the current container restarted and the expected messages belonged to a previous container instance. Logging might still have collected them, but your query time range and pod UID labels must match.

### 5.2 Check multi-container pods

A very common mistake is querying the wrong container.

```bash
oc -n $NS get pod $POD -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{end}'

for c in $(oc -n $NS get pod $POD -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{end}'); do
  echo "===== $c ====="
  oc -n $NS logs $POD -c $c --since=30m --timestamps | tail -20
done
```

### 5.3 Check if the application logs to a file inside the container

OpenShift Logging normally collects container stdout/stderr, infrastructure logs, and audit sources. It does not automatically collect arbitrary files inside an application container such as:

```text
/app/logs/app.log
/var/log/myapp/app.log
/tmp/app-debug.log
```

If the application writes only to a file, you have options:

1. Change the application to log to stdout/stderr.
2. Use a sidecar pattern to tail the file to stdout.
3. Forward logs from the application directly to an external endpoint.
4. Use an application-native logging library or OpenTelemetry/log exporter.

Best practice for containers: write application logs to stdout/stderr and let the platform collect them.

### 5.4 Check timestamps

A query may look empty because the UI time range is wrong.

```bash
oc -n $NS logs $POD --all-containers=true --since=2h --timestamps | tail -20
oc debug node/$(oc -n $NS get pod $POD -o jsonpath='{.spec.nodeName}') -- chroot /host date -u
```

If the log timestamp is outside your UI query window, expand the query to 6h or 24h and re-check.

## 6. Determine whether this is application, infrastructure, audit, or event data

OpenShift Logging separates log types.

### 6.1 Application logs

Application logs are logs from user workloads. However, workloads in infrastructure namespaces can be classified differently.

Check namespace:

```bash
oc get ns $NS --show-labels
```

A workload deployed in namespaces matching platform patterns such as `openshift-*`, `kube-*`, or `default` can be treated as infrastructure container logs rather than normal application logs.

### 6.2 Infrastructure logs

Infrastructure logs include:

- OpenShift and Kubernetes component container logs.
- Node journal logs.
- Platform namespaces such as `openshift-*`, `kube-*`, and `default`.

Useful checks:

```bash
oc adm node-logs <node-name> -u crio --tail=100
oc adm node-logs <node-name> -u kubelet --tail=100
oc get pods -A -o wide | grep <node-name>
```

### 6.3 Audit logs

Audit logs include Kubernetes API, OpenShift API, auditd, and OVN audit sources depending on configuration. Audit logs are sensitive and are not automatically stored unless you configure forwarding for them.

Check if audit is in any pipeline:

```bash
oc get clusterlogforwarder -A -o yaml | grep -n "audit" -C 4
```

Check RBAC:

```bash
oc get clusterrolebinding -o wide | grep collect-audit-logs
```

### 6.4 Kubernetes events

Kubernetes events are not the same as application logs. If you expect cluster events in logging, confirm Event Router is installed and producing container logs.

```bash
oc get pods -n openshift-logging | grep -i event
oc logs -n openshift-logging deploy/eventrouter --since=30m --tail=100
```

If there is no Event Router deployment, events might only be visible through the Kubernetes API:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
```

## 7. ClusterLogForwarder health and configuration

### 7.1 Identify the active ClusterLogForwarder resources

Modern Logging versions can use `ClusterLogForwarder` resources with different names and namespaces. Do not assume only `openshift-logging/instance` exists.

```bash
oc get clusterlogforwarder -A
oc get clusterlogforwarder -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{"\n"}{end}'
```

For each relevant forwarder:

```bash
CLF_NS=openshift-logging
CLF_NAME=instance

oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml
oc describe clusterlogforwarder $CLF_NAME -n $CLF_NS
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

### 7.2 Understand the important status conditions

Expected conditions:

| Condition | Expected | Meaning |
|---|---:|---|
| `observability.openshift.io/Authorized` | `True` | Collector service account has required log-type RBAC |
| `observability.openshift.io/Valid` | `True` | CR schema and semantic validation passed |
| `Ready` | `True` | Operator reconciled resources needed for collector deployment |

If `Authorized=False`, the collector service account is missing one or more `ClusterRoleBinding` objects.

If `Valid=False`, there is likely a bad input reference, output reference, filter reference, unsupported field, malformed secret reference, wrong output type, or invalid pipeline definition.

### 7.3 Check service account and RBAC

Find the service account used by the forwarder:

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS \
  -o jsonpath='{.spec.serviceAccount.name}{"\n"}'
```

Expected service account:

```bash
oc get sa -n $CLF_NS
```

Grant permissions based on the log types used:

```bash
SA=collector

# Application logs
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:$CLF_NS:$SA

# Infrastructure logs
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:$CLF_NS:$SA

# Audit logs: grant before adding audit to inputRefs
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:$CLF_NS:$SA
```

Verify:

```bash
oc get clusterrolebinding -o wide | grep "system:serviceaccount:$CLF_NS:$SA"
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

### 7.4 Check pipelines

A pipeline is the routing logic that connects inputs, optional filters, and outputs.

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS \
  -o jsonpath='{range .spec.pipelines[*]}{"PIPELINE: "}{.name}{"\nINPUTS: "}{.inputRefs}{"\nFILTERS: "}{.filterRefs}{"\nOUTPUTS: "}{.outputRefs}{"\n\n"}{end}'
```

Common mistakes:

- `application` logs are not included in `inputRefs`.
- A custom input is used, but the namespace is not included.
- A pipeline references an output name that does not exist.
- A pipeline references a filter that drops the message.
- Audit is referenced without RBAC.
- Only audit/infrastructure logs are routed to Loki, while application logs are routed elsewhere.
- Logs are intentionally routed to external storage but the admin checks only Observe → Logs.

## 8. Collector not running

### 8.1 Symptom

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
# No resources found
```

### 8.2 Common causes

1. `ClusterLogForwarder` has `Authorized=False`.
2. `ClusterLogForwarder` has `Valid=False`.
3. Logging Operator is not running.
4. Operator reconciliation failed.
5. Wrong namespace/name assumptions.
6. Node selector, taints, tolerations, or scheduling constraints prevent collectors.
7. Resource requests cannot be satisfied.

### 8.3 Check CLF conditions first

```bash
oc get clusterlogforwarder -A
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

If unauthorized, fix RBAC. If invalid, fix the message in `.status.conditions`.

### 8.4 Check collector DaemonSet

```bash
oc get ds -n openshift-logging
oc describe ds -n openshift-logging | sed -n '/collector/,$p' | head -120
```

If DaemonSet exists but pods are missing:

```bash
oc get nodes
oc describe node <node-name> | egrep -i 'taint|memorypressure|diskpressure|pidpressure|networkunavailable|unschedulable' -A5
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -100
```

### 8.5 Check scheduling and resources

```bash
oc get pods -n openshift-logging -o wide | grep -i collector
oc describe pod -n openshift-logging <collector-pod>
```

Look for:

- `Insufficient cpu`
- `Insufficient memory`
- `node(s) had taint ... that the pod didn't tolerate`
- `node selector mismatch`
- image pull errors
- SCC/security admission errors
- `CrashLoopBackOff`
- `OOMKilled`

### 8.6 Remediation patterns

Fix authorization:

```bash
SA=$(oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o jsonpath='{.spec.serviceAccount.name}')

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:$CLF_NS:$SA
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:$CLF_NS:$SA
```

Increase collector resources if it is OOMKilled or CPU-starved:

```bash
oc patch clusterlogforwarder $CLF_NAME -n $CLF_NS --type=merge \
  -p '{"spec":{"collector":{"resources":{"requests":{"cpu":"200m","memory":"256Mi"},"limits":{"cpu":"1000m","memory":"1Gi"}}}}}'
```

Re-check:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -w
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

## 9. Logs are in `oc logs` but not in Observe → Logs or Loki

This is the most common “missing logs” case.

### 9.1 Verify the pod node and collector on the same node

```bash
NS=myapp
POD=myapp-abc123
NODE=$(oc -n $NS get pod $POD -o jsonpath='{.spec.nodeName}')
echo $NODE

oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide | grep "$NODE"
```

There should be a collector pod on the same node. If not, troubleshoot DaemonSet scheduling.

### 9.2 Check the exact namespace/container selection

Dump CLF inputs:

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | sed -n '/inputs:/,/outputs:/p'
```

If custom application input is used, verify includes/excludes:

```yaml
spec:
  inputs:
  - name: selected-apps
    type: application
    application:
      includes:
      - namespace: myapp
        container: app
      excludes:
      - namespace: noisy-ns
```

Important behavior:

- `includes.namespace` limits collection to matching namespaces.
- `includes.container` limits collection to matching containers.
- `excludes` takes precedence over `includes`.
- Label selectors must match pod labels, not necessarily Deployment labels unless those labels are present on the pod template.

Check actual pod labels:

```bash
oc -n $NS get pod $POD --show-labels
oc -n $NS get pod $POD -o jsonpath='{.metadata.labels}' | python3 -m json.tool
```

### 9.3 Check if namespace is classified as infrastructure

If your application runs in `openshift-*`, `kube-*`, or `default`, it might be selected under `infrastructure` instead of `application`.

Search both log types in the UI or confirm CLF input:

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | grep -n "infrastructure" -C 5
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | grep -n "application" -C 5
```

### 9.4 Check filters that drop logs

Dump filters:

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | sed -n '/filters:/,/outputs:/p'
```

Look for `drop` filters:

```yaml
filters:
- name: drop-debug
  type: drop
  drop:
  - test:
    - field: .message
      matches: "debug|healthcheck"
```

Common mistakes:

- Regex too broad, e.g. `error|warn|info` intended to keep but implemented as drop.
- Dropping an entire namespace such as `myapp`.
- Dropping by `.kubernetes.namespace_name` but using the wrong field path for the selected data model.
- Applying filter to all pipelines instead of only one.
- Filter order causes parsed fields to be unavailable when the drop test runs.

Temporarily remove the filter from the pipeline for a controlled test:

```bash
oc edit clusterlogforwarder $CLF_NAME -n $CLF_NS
```

Then generate a known test log:

```bash
oc -n $NS exec deploy/myapp -- /bin/sh -c 'echo MISSING_LOG_TEST_$(date -u +%Y%m%dT%H%M%SZ)'
```

If the test appears after removing the filter, the filter is the cause.

### 9.5 Check input/output rate limits

Rate limits can intentionally drop records.

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | grep -n "rateLimit\|maxRecordsPerSecond" -C 5
```

If `inputs[].application.tuning.rateLimitPerContainer.maxRecordsPerSecond` is too low, logs above that rate are dropped per container.

If `outputs[].rateLimit.maxRecordsPerSecond` is too low, logs above that rate are dropped per collector pod.

Check metrics from Prometheus if available:

```promql
rate(observability_log_forwarder_output_rate_limited_total[5m])
```

If this metric increases, your configuration is causing dropped logs.

## 10. Vector collector troubleshooting

OpenShift Logging uses Vector as the modern collector. Vector usually tells you the exact sink, transform, or source that is failing.

### 10.1 Check collector logs

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m --tail=300
```

Search for:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=1h \
  | egrep -i 'error|warn|failed|retry|429|403|401|certificate|tls|timeout|refused|rate|dropped|parse|invalid'
```

### 10.2 Enable debug logging temporarily

```bash
oc annotate clusterlogforwarder $CLF_NAME -n $CLF_NS \
  observability.openshift.io/log-level=debug --overwrite

oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Reset afterward:

```bash
oc annotate clusterlogforwarder $CLF_NAME -n $CLF_NS \
  observability.openshift.io/log-level=info --overwrite
```

Do not leave `debug` or `trace` enabled in production because it increases collector log volume and can affect performance.

### 10.3 Common Vector messages and meaning

| Message pattern | Likely cause | Action |
|---|---|---|
| `429 Too Many Requests` | Loki or external destination is rate limiting | Wait for backlog or tune Loki/CLF rate limits |
| `certificate verify failed` | Missing or wrong CA bundle | Fix `spec.outputs[].tls.ca` |
| `connection refused` | Endpoint/service down, wrong port, NetworkPolicy | Test service and network path |
| `no such host` | DNS or wrong endpoint | Check service/route/DNS |
| `401` / `403` | Token, secret, service account, tenant auth | Validate credentials and RBAC |
| `failed to encode` / `parse` | Bad output format or unsupported field | Check output type and format |
| `buffer` / `retrying` | Destination unavailable or slow | Check output health and network |
| `rate_limited` / dropped metric increasing | CLF rate limit too strict | Increase/remove rate limit |

### 10.4 Check generated configuration indirectly

The Operator generates Vector configuration from the `ClusterLogForwarder`. Do not hand-edit generated collector config. Instead, validate the source CR:

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml
oc describe clusterlogforwarder $CLF_NAME -n $CLF_NS
oc get events -n $CLF_NS --field-selector involvedObject.name=$CLF_NAME
```

If the generated collector behaves unexpectedly, inspect:

```bash
oc get cm -n openshift-logging | egrep -i 'collector|vector|logging'
oc get secret -n openshift-logging | egrep -i 'collector|vector|logging|loki|splunk|kafka'
```

Avoid modifying generated resources unless Red Hat Support explicitly instructs you.

## 11. LokiStack ingestion troubleshooting

### 11.1 Confirm LokiStack exists and is healthy

```bash
oc get lokistack -A
oc describe lokistack logging-loki -n openshift-logging
oc get pods -n openshift-logging | egrep -i 'loki|gateway|distributor|ingester|querier|index|compactor|ruler'
```

Check component health:

```bash
oc get pods -n openshift-logging -o wide | egrep -i 'loki|gateway|ingester|distributor|querier|compactor|index'
oc get events -n openshift-logging --sort-by=.lastTimestamp | egrep -i 'loki|warning|failed|error|mount|pvc|secret|object|s3|throttle' | tail -100
```

### 11.2 Check Loki object storage configuration

LokiStack depends on object storage. If object storage is wrong or unavailable, logs might not persist or queries might fail.

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml | sed -n '/storage:/,/tenants:/p'
oc get secret -n openshift-logging | grep -i loki
oc get pvc -n openshift-logging | grep -i loki
```

Common causes:

- Missing object storage secret.
- Wrong S3 endpoint, access key, secret key, bucket name, or `forcepathstyle`.
- Object storage TLS/certificate issue.
- Bucket lifecycle policy deleting objects earlier than expected.
- NetworkPolicy blocking object storage egress.
- Proxy configuration mismatch.

### 11.3 Check Loki gateway and CA bundle

For in-cluster LokiStack output, the collector usually talks to the Loki gateway and needs the proper CA bundle.

```bash
oc get cm logging-loki-gateway-ca-bundle -n openshift-logging -o yaml
oc get svc -n openshift-logging | grep -i loki
oc get route -n openshift-logging | grep -i loki
```

A typical `lokiStack` output should include something like:

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    authentication:
      token:
        from: serviceAccount
    target:
      name: logging-loki
      namespace: openshift-logging
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

If collector logs show certificate verification errors, add or correct `tls.ca`.

### 11.4 Loki 429 rate limit errors

Symptoms in collector logs:

```text
429 Too Many Requests
Ingestion rate limit exceeded
Retrying after error
```

Possible causes:

- Initial backlog after enabling logging.
- Loki was unavailable and collectors are catching up.
- A noisy namespace or pod emits very large messages.
- LokiStack size is too small for ingestion volume.
- Loki ingestion limits are too low.
- A single stream exceeds per-stream rate limits.

First, check whether it is transient:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m \
  | grep -c '429\|Too Many Requests\|rate limit'
```

If persistent, inspect and tune Loki limits:

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml | sed -n '/limits:/,/managementState:/p'
```

Example tuning:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  limits:
    global:
      ingestion:
        ingestionBurstSize: 16
        ingestionRate: 8
```

Also consider scaling LokiStack size from `1x.demo` to a production size such as `1x.extra-small`, `1x.small`, or `1x.medium` depending on log volume.

### 11.5 Loki query has no results but ingestion is working

Check:

- UI time range.
- Correct tenant: application, infrastructure, audit.
- Correct namespace label name for your data model.
- Whether the log was pruned or relabeled.
- Whether retention already removed it.
- Whether object storage lifecycle deleted data.
- Whether the user has RBAC to see that namespace’s logs.

Test with broad query first:

```logql
{log_type="application"}
```

Then narrow gradually:

```logql
{log_type="application", kubernetes_namespace_name="myapp"}
```

Depending on Logging version and selected data model, label names may differ. Inspect an actual returned log from a broad query before building narrow queries.

## 12. External forwarding troubleshooting

External outputs include Splunk, Kafka, HTTP, syslog, Elasticsearch, OTLP, CloudWatch, S3, Azure Monitor, Google Cloud Logging, and external Loki.

### 12.1 Validate output configuration

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | sed -n '/outputs:/,/pipelines:/p'
```

Check:

- Output name matches `pipeline.outputRefs`.
- URL/host/port is correct.
- Secret name and key names are correct.
- CA bundle is correct.
- Proxy settings are correct.
- Compression type is supported by that destination.
- Output format is supported by receiver.
- Kafka topic exists or auto-create is enabled.
- Splunk HEC token is valid and points to the correct index.
- Elasticsearch version and URL path are correct.
- Syslog receiver accepts selected RFC format and transport.

### 12.2 Test network from inside the cluster

Create a temporary test pod in a namespace that has similar egress restrictions as the collector. If collector runs in `openshift-logging`, test there.

```bash
oc run curl-test -n openshift-logging --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
getent hosts splunk.example.com
curl -vk https://splunk.example.com:8088/services/collector/health
```

If `curl` fails from a debug pod, the collector will also fail unless NetworkPolicy allows it differently.

### 12.3 Check authentication secrets

```bash
oc get secret -n $CLF_NS
oc describe secret <secret-name> -n $CLF_NS
```

Decode only in a secure admin session:

```bash
oc get secret <secret-name> -n $CLF_NS -o jsonpath='{.data}' | python3 -m json.tool
```

For key existence, you do not need to print secret values.

### 12.4 Common HTTP status codes

| Code | Meaning | Typical fix |
|---:|---|---|
| 400 | Bad payload, unsupported format, wrong endpoint | Verify format and API path |
| 401 | Invalid token/basic auth | Fix secret/token |
| 403 | Authenticated but forbidden, tenant/index/topic denied | Fix destination-side authorization |
| 404 | Wrong endpoint path | Fix URL/path |
| 413 | Payload too large | Reduce `maxWrite`, tune receiver limit, reduce multiline/large messages |
| 429 | Rate limited | Tune destination quota, CLF rate, Loki ingestion limits |
| 500/502/503 | Destination unhealthy or proxy issue | Check destination and network/proxy |

### 12.5 Kafka-specific checks

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m \
  | egrep -i 'kafka|rdkafka|sasl|ssl|broker|topic|authorization'
```

Check:

- Bootstrap broker list.
- TLS CA and client cert/key if used.
- SASL mechanism and username/password.
- Topic existence.
- ACLs for producer.
- Broker DNS resolution from the cluster.
- NetworkPolicy egress to broker ports.

### 12.6 Splunk-specific checks

Check collector errors:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m \
  | egrep -i 'splunk|hec|401|403|429|invalid|token|ack|index'
```

Validate:

- HEC token enabled.
- Correct HEC URL, usually `https://host:8088/services/collector`.
- Index exists and token can write to it.
- TLS CA is trusted.
- Splunk index-time field extraction expectations.
- Firewall/proxy allows OpenShift egress.

## 13. NetworkPolicy and AdminNetworkPolicy issues

A restrictive cluster network policy can make logs appear missing even when CLF is correct.

### 13.1 Symptoms

- Collector logs show connection timeouts.
- Collector logs show DNS failure or TCP connect failure.
- Loki components cannot talk to each other.
- External SIEM endpoint cannot be reached.
- Metrics scraping alerts fire.
- Collector or LogFileMetricExporter pods exist but cannot communicate.

### 13.2 Check policies

```bash
oc get networkpolicy -A | egrep -i 'logging|loki|collector|default-deny'
oc get adminnetworkpolicy -A 2>/dev/null
oc get baselineadminnetworkpolicy -A 2>/dev/null
```

### 13.3 Configure collector network policy through CLF

For quick isolation during troubleshooting, you can allow all ingress/egress for collector-managed traffic:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    networkPolicy:
      ruleSet: AllowAllIngressEgress
```

For production, use the most restrictive policy that still allows required outputs, metrics, DNS, and receiver inputs.

### 13.4 Configure Loki network policies

If using LokiStack network policies, verify `spec.networkPolicies.ruleSet`:

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml | grep -n "networkPolicies" -A10
```

Example:

```yaml
spec:
  networkPolicies:
    ruleSet: RestrictIngressEgress
```

If this breaks ingestion or querying, validate allow rules for:

- Collector to Loki gateway/distributor.
- Loki components to each other.
- Loki to object storage.
- Loki to DNS.
- Monitoring to scrape metrics.
- UI/Gateway query path.

## 14. Node-level log path troubleshooting

If only logs from one node are missing, focus on that node.

### 14.1 Identify affected node

```bash
NS=myapp
POD=myapp-abc123
NODE=$(oc -n $NS get pod $POD -o jsonpath='{.spec.nodeName}')
echo $NODE
```

### 14.2 Check collector on that node

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide | grep "$NODE"
```

If absent, troubleshoot DaemonSet scheduling.

### 14.3 Check node pressure

```bash
oc describe node $NODE | egrep -i 'Ready|MemoryPressure|DiskPressure|PIDPressure|NetworkUnavailable|Taints' -A5
oc adm top node $NODE
```

Disk pressure can cause log rotation, pod eviction, and collector instability.

### 14.4 Inspect container log files on node

Use `oc debug node` carefully:

```bash
oc debug node/$NODE

# Inside debug shell:
chroot /host
ls -lh /var/log/containers | grep myapp
ls -lh /var/log/pods | grep myapp
journalctl -u crio --since "30 min ago" | tail -100
journalctl -u kubelet --since "30 min ago" | tail -100
exit
exit
```

If files are not present on the node, the problem is below OpenShift Logging.

### 14.5 Check log rotation and disk usage

```bash
oc debug node/$NODE -- chroot /host df -h /var /var/log
oc debug node/$NODE -- chroot /host du -sh /var/log/containers /var/log/pods 2>/dev/null
```

High disk usage can rotate logs before the collector reads them.

## 15. Missing audit logs

Audit logs require special care.

### 15.1 Confirm audit is configured in CLF

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | grep -n "audit" -C 5
```

A pipeline should include:

```yaml
pipelines:
- name: audit-to-secure-store
  inputRefs:
  - audit
  outputRefs:
  - secure-output
```

### 15.2 Confirm audit RBAC exists before inputRefs

```bash
SA=$(oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o jsonpath='{.spec.serviceAccount.name}')
oc get clusterrolebinding -o wide | grep collect-audit-logs | grep "system:serviceaccount:$CLF_NS:$SA"
```

If missing:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:$CLF_NS:$SA
```

Then verify CLF status.

### 15.3 Check audit source selection

If custom audit sources are defined, ensure the missing source is included:

```yaml
inputs:
- name: audit-input
  type: audit
  audit:
    sources:
    - kubeAPI
    - openshiftAPI
    - auditd
    - ovn
```

If you include only `kubeAPI`, you will not get `auditd` or `ovn` audit records.

### 15.4 Audit logs and compliance warning

OpenShift Logging is commonly used for operational aggregation. For compliance-grade audit retention, forward audit logs to secure external storage such as SIEM, immutable object storage, or a controlled archive. Do not assume short-term Loki retention satisfies regulatory audit retention.

## 16. Missing infrastructure logs

Infrastructure logs include node journal logs and containers in infrastructure namespaces.

### 16.1 Verify pipeline includes infrastructure

```bash
oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o yaml | grep -n "infrastructure" -C 5
```

### 16.2 Verify RBAC

```bash
SA=$(oc get clusterlogforwarder $CLF_NAME -n $CLF_NS -o jsonpath='{.spec.serviceAccount.name}')
oc get clusterrolebinding -o wide | grep collect-infrastructure-logs | grep "system:serviceaccount:$CLF_NS:$SA"
```

If missing:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:$CLF_NS:$SA
```

### 16.3 Check source selection

If you configured infrastructure sources explicitly, confirm both are included if needed:

```yaml
inputs:
- name: infra-input
  type: infrastructure
  infrastructure:
    sources:
    - node
    - container
```

If only `node` is configured, infrastructure container logs can be absent. If only `container` is configured, node journal logs can be absent.

## 17. Missing logs due to retention or storage lifecycle

### 17.1 Understand Loki retention expectation

OpenShift’s LokiStack configuration is optimized for recent troubleshooting and short-term log access. It is not a long-term archive by default.

### 17.2 Check LokiStack retention configuration

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml | sed -n '/retention:/,/storage:/p'
```

Look for global or tenant-specific retention:

```yaml
spec:
  limits:
    global:
      retention:
        days: 20
    tenants:
      application:
        retention:
          days: 7
      infrastructure:
        retention:
          days: 5
      audit:
        retention:
          days: 1
```

A tenant-specific rule can delete audit/application logs earlier than expected.

### 17.3 Check object storage lifecycle

Even if Loki retention says 20 days, object storage lifecycle policy can delete objects independently.

Check:

- S3 lifecycle rules.
- ODF NooBaa bucket policy.
- Cloud object versioning and expiration.
- Bucket quota.
- Object lock/retention policy.
- Compactor errors.

### 17.4 Query time range

Always test with a known recent log and a broad time window:

```bash
oc -n myapp exec deploy/myapp -- /bin/sh -c 'echo RETENTION_TEST_$(date -u +%s)'
```

Then query last 15 minutes. If recent logs appear but old logs do not, the issue is likely retention or lifecycle, not ingestion.

## 18. Missing logs due to OpenShift console or RBAC

Sometimes logs are present but the user cannot see them.

### 18.1 Test as cluster-admin

```bash
oc whoami
oc auth can-i get pods/log -n myapp
```

If a developer cannot see logs but cluster-admin can, this is access control, not logging ingestion.

### 18.2 Check project access

```bash
oc adm policy who-can get pods/log -n myapp
oc get rolebinding -n myapp
```

### 18.3 Observe → Logs tenant mismatch

In the console, select the correct log type:

- `application` for user workload logs.
- `infrastructure` for platform and node logs.
- `audit` for audit logs.

Also expand the time range. Many “missing log” incidents are actually “wrong time range + wrong tenant”.

## 19. Missing logs after upgrade or migration

### 19.1 Common upgrade issues

- Old `logging.openshift.io/v1` style assumptions remain in scripts.
- Fluentd/Elasticsearch commands used against Vector/LokiStack.
- CLF API group changed to `observability.openshift.io/v1` in Logging 6.x.
- `ClusterLogging` and `ClusterLogForwarder` architecture changed.
- Default labels and data model changed.
- Old Kibana queries do not match Loki labels.
- External destinations changed TLS requirements.
- Operator channel upgraded but CR not migrated correctly.

### 19.2 Post-upgrade validation

```bash
oc get csv -A | egrep -i 'logging|loki|observability'
oc get crd | egrep -i 'clusterlogforwarder|lokistack|logfilemetricexporter'
oc api-resources | egrep -i 'clusterlogforwarder|lokistack|logging'
oc get clusterlogforwarder -A -o yaml
oc get lokistack -A -o yaml
oc get pods -n openshift-logging -o wide
```

### 19.3 Validate labels before reusing old queries

Run a broad query and inspect one actual log record. Build queries from labels that exist now, not from labels that existed in the old Elasticsearch/Kibana deployment.

## 20. Legacy Fluentd and Elasticsearch notes

Older OpenShift Logging versions used Fluentd and Elasticsearch. If you still operate legacy clusters, missing logs often come from a different set of causes.

### 20.1 Fluentd checks

```bash
oc get pods -n openshift-logging | grep -i fluentd
oc logs -n openshift-logging -l component=fluentd --since=30m --tail=200
oc get ds -n openshift-logging | grep -i fluentd
```

Look for:

- Buffer queue increasing.
- Output errors.
- Elasticsearch 429/403/503.
- TLS verification errors.
- Fluentd pod OOMKilled.
- Node taints preventing DaemonSet.

### 20.2 Elasticsearch checks

```bash
oc get elasticsearch -n openshift-logging
oc get pods -n openshift-logging | grep -i elastic
oc logs -n openshift-logging <elasticsearch-pod> --since=30m --tail=200
```

Common missing-log causes:

- Cluster health red/yellow.
- Disk watermark reached.
- Index set to read-only after flood-stage watermark.
- Shard allocation failure.
- JVM heap pressure.
- Write rejections.
- Index lifecycle/deletion policy.

### 20.3 Legacy remediation examples

Check read-only index block:

```bash
# Example only. Use the correct ES service/auth for your environment.
curl -k -u user:pass https://elasticsearch:9200/_all/_settings?pretty | grep read_only -C 2
```

If disk pressure caused read-only blocks, add storage or delete old indices first, then remove the block. Do not blindly clear blocks while disk is still full.

## 23. Known-good baseline ClusterLogForwarder to LokiStack

This baseline forwards application and infrastructure logs to an in-cluster LokiStack. Add audit only after granting `collect-audit-logs`.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  collector:
    resources:
      requests:
        cpu: 200m
        memory: 256Mi
      limits:
        cpu: 1000m
        memory: 1Gi
    networkPolicy:
      ruleSet: AllowAllIngressEgress
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: apps-and-infra-to-loki
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

```bash

  system:serviceaccount:openshift-logging:collector

  system:serviceaccount:openshift-logging:collector
```

Verify:

## 27. Common root causes and fast fixes

| Root cause | Evidence | Fix |
|---|---|---|
| App logs to file, not stdout | `oc logs` empty | Change app logging, sidecar tail, or direct forward |
| Wrong container | Logs visible only under another container | Query correct container or all containers |
| Collector absent | No collector pods | Fix CLF status/RBAC/validation/scheduling |
| Missing `collect-*` RBAC | `Authorized=False` | Add proper `ClusterRoleBinding` |
| Invalid CLF | `Valid=False` | Fix CR message, input/output/filter refs |
| Custom input excludes namespace | CLF `includes/excludes` mismatch | Correct input selector |
| Label selector mismatch | Pod labels do not match CLF selector | Fix pod labels or selector |
| Drop filter too broad | Filter matches missing logs | Adjust/remove drop filter |
| Rate limit drops records | rate-limited metric increases | Increase/remove rate limit |
| TLS CA missing | `certificate verify failed` | Add `tls.ca` config |
| External auth failure | 401/403 in collector logs | Fix token/secret/ACL/index/topic |
| Network blocked | timeout/refused/no route | Fix NetworkPolicy/AdminNetworkPolicy/firewall |
| Loki 429 | 429 errors | Wait for backlog or tune Loki limits/size |
| Retention expired | Recent logs work, old logs absent | Adjust Loki retention/object lifecycle |
| Wrong tenant/time range | Logs present under different type/time | Query correct log type/time/labels |
| UI RBAC issue | Admin can see logs, user cannot | Fix project/log access RBAC |

## 28. Advanced admin notes

### 28.1 “Ready=True” does not always mean logs are delivered

`Ready=True` means the Operator reconciled the CLF successfully. It does not prove every external output is accepting writes. For example, a missing TLS CA can still cause collector delivery failure while CLF is ready. Always inspect collector logs.

### 28.2 “No logs in Loki” might be a query problem

Loki is label-driven. A too-specific query can look like data loss. Start broad, inspect labels, then narrow. Avoid copying old Elasticsearch/Kibana field names blindly.

### 28.3 Multiple pipelines duplicate logs

A single input can be sent to multiple outputs. If one output fails, another output can still work. Missing logs in Splunk do not prove Loki ingestion failed.

### 28.4 Excludes beat includes

If a namespace/container matches both include and exclude, it is excluded. This causes many silent “missing log” cases.

### 28.5 Rate limits drop, Loki 429 retries

CLF input/output rate limits can drop logs intentionally. Loki 429 ingestion errors can be retried by the collector and may recover after backlog clears. Treat them differently.

### 28.6 Audit is expensive and sensitive

Audit logs can be high volume and sensitive. Route them deliberately, prune carefully, and store them according to compliance requirements.

### 28.7 Generated resources are not your source of truth

Edit `ClusterLogForwarder`, `LokiStack`, and supported CRs. Do not manually edit collector DaemonSets, generated ConfigMaps, or operator-managed resources unless directed by support.

## 29. Exam/interview style troubleshooting flow

For a practical OpenShift admin exam or senior interview, answer missing logs like this:

```text
1. I first prove whether the app produced logs with oc logs.
2. If source logs exist, I identify the pod node and verify a collector pod is running on that node.
3. I check ClusterLogForwarder conditions: Authorized, Valid, Ready.
4. I verify the service account and collect-* ClusterRoleBindings for the log type.
5. I inspect inputs and pipelines to confirm the namespace/container/log type is selected.
6. I inspect filters and rate limits to ensure records are not dropped intentionally.
7. I check collector logs for TLS, auth, network, and 429 errors.
8. I validate LokiStack or the external sink health.
9. I confirm query tenant, labels, RBAC, and time range.
10. I generate a controlled test log and trace it end to end.
```

This is the expected senior-level method: isolate the stage, prove evidence, fix the narrowest cause.

## 31. Final summary

Missing logs in OpenShift Logging usually come from one of seven areas:

1. The application did not write to stdout/stderr.
2. The collector is not running on the node.
3. `ClusterLogForwarder` is invalid or unauthorized.
4. Inputs/selectors/filters/rate limits intentionally exclude or drop logs.
5. Output delivery fails due to TLS, auth, network, or destination rate limits.
6. LokiStack/storage/retention/query layer hides or removes logs.
7. User RBAC, tenant, time range, or label query is wrong.

The fastest safe troubleshooting path is:

```text
oc logs -> node -> collector -> CLF status -> input/filter/pipeline -> output -> Loki/external sink -> query/RBAC/time
```

Once you follow that chain, “missing logs” becomes a deterministic pipeline issue instead of guesswork.
