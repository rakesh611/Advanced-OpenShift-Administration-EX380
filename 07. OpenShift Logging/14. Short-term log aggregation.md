# Short-term Log Aggregation in OpenShift Logging

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and Linux/DevOps engineers with production experience.  
**Focus:** Red Hat OpenShift Logging 6.x style architecture using **Vector**, **ClusterLogForwarder**, **LokiStack**, object storage, retention, reliability, and troubleshooting.  
**Generated:** 2026-07-03  

---

## 1. Executive Summary

**Short-term log aggregation** in OpenShift means collecting logs from pods, nodes, control-plane components, and optionally audit sources into a centralized log store for **fast operational troubleshooting** over a limited retention window.

In modern OpenShift Logging, this is commonly implemented with:

- **Red Hat OpenShift Logging Operator** for log collection and forwarding.
- **Vector** as the supported collector implementation in Logging 6.x.
- **ClusterLogForwarder** as the main API for selecting log inputs, filters, outputs, and pipelines.
- **Loki Operator** for managing the in-cluster **LokiStack** log store.
- **Cluster Observability Operator** and the OpenShift console **Observe > Logs** UI for log visualization.
- **Object storage** such as S3, S3-compatible storage, OpenShift Data Foundation, Azure, GCS, or Swift as the Loki backing store.

The important mindset is this:

> OpenShift Logging with LokiStack is not a long-term compliance archive. It is a short-term, operational log aggregation layer designed for recent troubleshooting, incident response, and day-to-day platform visibility.

Red Hat documentation describes LokiStack in OpenShift Logging as a short-term log store optimized for very recent queries and states that Loki sizing is tested and supported for short-term storage up to a maximum of 30 days. For long-term retention or long-range queries, use an external logging, SIEM, archive, or compliance platform.

---

## 2. What “Short-term Log Aggregation” Means

Short-term log aggregation is the practice of collecting logs centrally for a small operational window, usually something like:

- 1 to 3 days for noisy development clusters.
- 7 to 14 days for normal production troubleshooting.
- Up to 30 days where supported, sized, and cost-justified.

It is designed to answer questions like:

- Why did this pod restart today?
- Which node started showing kubelet errors after the last maintenance?
- Did the ingress/router return 503 responses during the incident window?
- What application error happened around the time Prometheus fired an alert?
- Did the API server, OAuth server, or scheduler report warnings during a control-plane issue?
- Which namespace is producing excessive logs?
- Are Loki ingestion limits being hit?
- Did a recent deployment increase log volume?

It is **not** primarily designed to answer questions like:

- Show me all audit activity for the last 1 year.
- Keep immutable logs for 7 years for compliance.
- Store logs as a certified SIEM evidence repository.
- Query multi-terabyte log history over long time ranges every day.
- Guarantee that every log line is permanently stored under all failure scenarios.

For those requirements, the platform should forward logs to external systems such as Splunk, Kafka, Elasticsearch/OpenSearch, SIEM, cloud-native log platforms, or object-storage-based archives.

## 3. Why Short-term Logging Exists in OpenShift

OpenShift is a distributed platform. A single application request can touch:

- Application pods.
- Sidecars.
- Services.
- Routes and ingress controllers.
- Service mesh components, if used.
- Nodes.
- Kubelet.
- CRI-O.
- API server.
- OAuth server.
- Scheduler.
- Controller manager.
- OVN-Kubernetes.
- Storage CSI drivers.
- Image registry.
- Operators.

Without aggregation, troubleshooting requires jumping between nodes and namespaces using commands like:

```bash
oc logs
oc adm node-logs
journalctl
oc get events
oc describe pod
```

That works for simple cases, but it fails at production scale because logs are distributed, ephemeral, rotated, and often needed after the pod or node state has already changed.

Short-term aggregation gives administrators a central place to search recent logs while keeping cost, performance, and retention under control.

## 4. OpenShift Logging 6.x Component Model

In older OpenShift Logging versions, administrators often thought in terms of a monolithic “cluster logging stack.” In Logging 6.x, the responsibilities are separated more clearly.

| Component | Responsibility |
|---|---|
| Red Hat OpenShift Logging Operator | Deploys and manages log collection and forwarding based on `ClusterLogForwarder`. |
| Vector collector | Runs as collector pods, normally as a DaemonSet, and reads logs from nodes. |
| ClusterLogForwarder | Defines inputs, filters, outputs, and pipelines. |
| Loki Operator | Deploys and manages LokiStack storage components. |
| LokiStack | Stores and indexes logs for short-term querying. |
| Object storage | Stores Loki chunks and index data. |
| Cluster Observability Operator | Provides OpenShift console log visualization plugin. |
| OpenShift console | Provides Observe > Logs query experience. |

Logging 6.x also moved the forwarding API to the `observability.openshift.io` API group and made Vector the supported collection service.

## 5. High-level Data Flow

A simplified short-term aggregation flow looks like this:

```text
Application stdout/stderr
        |
        v
CRI-O writes container logs on each node
        |
        v
Vector collector DaemonSet tails node log files and selected sources
        |
        v
Vector enriches records with Kubernetes metadata
        |
        v
ClusterLogForwarder pipeline applies selection, filters, transforms, and routing
        |
        v
LokiStack gateway receives logs with OpenShift auth and tenancy
        |
        v
Loki distributor / ingester / index gateway / compactor / querier components
        |
        v
Object storage + local PVC/WAL/index/cache storage
        |
        v
OpenShift console Observe > Logs or LogQL clients query recent logs
```

The key operational idea is that the collector runs close to the node where logs are generated, while the log store centralizes recent logs for searching.

## 6. Log Sources in OpenShift

OpenShift Logging commonly groups logs into these major categories:

### 6.1 Application Logs

Application logs are produced by user workloads. These are usually logs written to container `stdout` and `stderr`.

Examples:

```text
payment-api namespace pod logs
nginx access logs written to stdout
Java application exceptions
Node.js application console output
Python application traceback output
```

Application logs are the highest-volume source in many clusters because application teams control log verbosity.

### 6.2 Infrastructure Logs

Infrastructure logs come from platform components and node-level services.

Examples:

```text
openshift-* namespace component logs
kube-* namespace component logs
router logs
registry logs
operator logs
node-related system logs
OVN-Kubernetes logs
```

Infrastructure logs are critical for platform SRE troubleshooting.

### 6.3 Audit Logs

Audit logs capture security-sensitive API activity from components such as Kubernetes API server, OpenShift API server, and OAuth-related flows.

Audit logs are special because:

- They can be high-volume.
- They contain sensitive metadata.
- They are often required for compliance.
- They are not stored by default unless explicitly configured.
- OpenShift Logging is not a SIEM and should not be treated as the only secure audit archive.

For compliance-grade audit requirements, forward audit logs to an external SIEM or secure archive.

## 7. Why Loki Is Used for Short-term Aggregation

Loki is designed differently from Elasticsearch-style systems.

Traditional full-text log stores index a lot of log content during ingestion. That gives powerful search, but indexing large log volumes can be expensive in CPU, memory, and storage.

Loki stores log data as compressed chunks and indexes a smaller set of labels. Query-time parsing is used for deeper analysis. This makes Loki attractive for Kubernetes/OpenShift environments where labels such as namespace, pod, container, node, and log type are natural query selectors.

The trade-off is important:

| Area | Loki Behavior |
|---|---|
| Ingestion | Efficient when label cardinality is controlled. |
| Querying | Fast when queries use selective labels and short time ranges. |
| Long history | Not the main OpenShift Logging use case. |
| Full-text search | Possible, but expensive if performed across broad time ranges and many streams. |
| Cost model | Better when log labels are stable and retention is short. |

For OpenShift, the goal is recent troubleshooting, not unlimited historical search.

## 8. Short-term vs Long-term Logging Design

| Requirement | Short-term OpenShift Logging | Long-term External Logging |
|---|---|---|
| Primary use | Troubleshooting recent incidents | Compliance, security, analytics, long history |
| Typical retention | 1-30 days | Months to years |
| Query pattern | Recent, narrow time windows | Historical, cross-system, compliance queries |
| Storage | LokiStack + object storage | SIEM, Splunk, OpenSearch, archive buckets, Kafka pipelines |
| Admin goal | Fast operational visibility | Durable record retention and governance |
| Risk if overloaded | Query slowness, ingestion throttling, storage pressure | Higher cost, index growth, governance complexity |

A mature platform often uses both:

```text
LokiStack = fast recent troubleshooting
External SIEM/archive = long-term governance and security retention
```

## 10. Required Collector Permissions

Modern `ClusterLogForwarder` deployments require explicit RBAC permission for the collector service account.

Example:

```bash
oc create sa collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector

# Add only if audit collection is required and approved.
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Important production rule:

> Grant the RBAC role before adding the corresponding log type to `ClusterLogForwarder.inputRefs`.

If the collector service account is not authorized for a log type referenced in the pipeline, the operator can stop the collector deployment to avoid insecure or partial collection.

Verification:

```bash
oc get clusterrolebinding -o wide | grep collect
oc get sa collector -n openshift-logging
```

## 11. LokiStack Storage Model

LokiStack requires two broad storage layers:

### 11.1 Object Storage

Object storage stores log chunks and index-related data.

Supported storage families include:

- AWS S3.
- S3-compatible storage.
- OpenShift Data Foundation object storage.
- Azure storage.
- Google Cloud Storage.
- Swift.

For S3-compatible storage, a secret typically looks like this:

```bash
oc create secret generic logging-loki-s3 \
  -n openshift-logging \
  --from-literal=bucketnames="<bucket_name>" \
  --from-literal=endpoint="<s3_endpoint_url>" \
  --from-literal=access_key_id="<access_key>" \
  --from-literal=access_key_secret="<secret_key>" \
  --from-literal=forcepathstyle="true"
```

For OpenShift Data Foundation, the object bucket is usually created with an `ObjectBucketClaim`, and the resulting bucket endpoint, access key, and secret key are used to create the Loki object storage secret.

### 11.2 Persistent Volumes

Loki components also use PVCs for local working data such as:

- Write-ahead logs.
- Index gateway storage.
- Ruler storage if enabled.
- Caches and local component state.

That means a healthy short-term logging setup depends on both:

```text
Object storage availability
+ Kubernetes PVC availability
+ network connectivity between Loki components and object storage
```

## 12. Example LokiStack for Short-term Aggregation

The following example is a practical starting point. Adjust size, storage class, retention, and replication for your environment.

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.small
  replicationFactor: 2
  storage:
    schemas:
    - version: v13
      effectiveDate: "<yyyy-mm-dd>"
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: <block_storage_class_for_loki_pvcs>
  tenants:
    mode: openshift-logging
  limits:
    global:
      retention:
        days: 14
      ingestion:
        ingestionRate: 8
        ingestionBurstSize: 16
    tenants:
      application:
        retention:
          days: 7
      infrastructure:
        retention:
          days: 14
      audit:
        retention:
          days: 3
```

Notes:

- `tenants.mode: openshift-logging` integrates LokiStack with OpenShift log tenancy.
- `size` should be selected based on daily ingest volume and query concurrency.
- `retention` should match your operational troubleshooting need, not arbitrary “keep everything” behavior.
- Use `v13` schema for forward compatibility in modern deployments.
- In production, consider object storage lifecycle policies for cost-effective pruning.
- For upgrades, schema `effectiveDate` must be planned carefully, usually as a future UTC date.

## 13. Example ClusterLogForwarder to LokiStack

This example forwards application and infrastructure logs to the in-cluster LokiStack.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: default-logstore
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

Critical details:

- `tls.ca` is mandatory for LokiStack gateway certificate verification.
- The `target.name` must exactly match the LokiStack CR name.
- The collector service account must have RBAC for every log type listed in `inputRefs`.
- Add `audit` only after granting `collect-audit-logs`.

Verification:

```bash
oc apply -f clusterlogforwarder.yaml

oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=50
```

Expected conditions:

```text
observability.openshift.io/Authorized = True
observability.openshift.io/Valid      = True
Ready                                 = True
```

## 15. Retention Strategy

Short-term logging retention should be driven by incident response needs and cluster capacity.

### 15.1 Common Retention Patterns

| Environment | Application Logs | Infrastructure Logs | Audit Logs in Loki | External Archive |
|---|---:|---:|---:|---|
| Lab | 1-3 days | 1-3 days | Usually disabled | No |
| Dev/Test | 3-7 days | 3-7 days | Disabled or 1 day | Optional |
| Production standard | 7-14 days | 14 days | 1-3 days | Yes |
| Regulated production | 7-14 days | 14-30 days | 1-7 days | Mandatory SIEM/archive |

### 15.2 Stream-based Retention

LokiStack can define retention globally, per tenant, or per stream selector.

Example:

```yaml
spec:
  limits:
    global:
      retention:
        days: 14
      streams:
      - days: 3
        priority: 1
        selector: '{kubernetes_namespace_name=~"dev-.+"}'
      - days: 1
        priority: 2
        selector: '{kubernetes_container_name="debug-sidecar"}'
    tenants:
      application:
        retention:
          days: 7
      infrastructure:
        retention:
          days: 14
      audit:
        retention:
          days: 3
```

Use stream-based retention to reduce cost from noisy namespaces, debug containers, test environments, or known high-volume components.

### 15.3 Object Storage Lifecycle Policies

For cost-effective pruning, configure lifecycle policies directly on the object storage bucket where supported.

Reasons:

- Deletion is handled by the object store.
- Loki does less internal delete work.
- Cost and lifecycle governance are centralized.
- Object storage teams can audit retention behavior.

Important:

> If neither object storage lifecycle retention nor LokiStack retention is configured, logs can remain in the bucket indefinitely and eventually consume the object storage budget or quota.

## 16. Sizing Short-term Aggregation

Sizing is not only about number of nodes. It depends mainly on:

- Daily log ingestion volume.
- Retention days.
- Query concurrency.
- Query time range.
- Label cardinality.
- Number of tenants.
- Audit log volume.
- Burst behavior during incidents.
- Object storage performance.
- PVC performance for Loki components.

### 16.1 LokiStack Size Families

Red Hat uses `1x.<size>` style sizing. Typical supported sizes include:

| Size | Approximate data transfer profile | Query profile | Typical use |
|---|---:|---:|---|
| `1x.demo` | Demo only | Demo only | Labs, not production |
| `1x.pico` | Around 50 GB/day | Low QPS | Very small clusters |
| `1x.extra-small` | Around 100 GB/day | Low QPS | Small production or dev |
| `1x.small` | Around 500 GB/day | Medium QPS | Standard production |
| `1x.medium` | Around 2 TB/day | Higher QPS | Larger production |

Always confirm exact supported sizing for your OpenShift Logging version because resource requests and support limits can change between releases.

### 16.2 Capacity Formula

A simple first-pass estimate:

```text
Estimated raw retention volume = daily ingest volume x retention days
```

Example:

```text
100 GB/day x 14 days = 1.4 TB raw log volume before compression, metadata, replication, object-store overhead, and growth margin
```

Then add safety margin:

```text
Recommended planning volume = estimated volume x 1.3 to 2.0
```

Use a larger margin where:

- Audit logs are enabled.
- Applications produce JSON stack traces.
- Debug logging is common.
- Incidents cause log storms.
- Query bursts occur during business hours.
- Development teams frequently deploy noisy workloads.

### 16.3 Watch These Metrics

At minimum, monitor:

```text
Loki ingestion rate
Loki 429 errors
Loki distributor/ingester errors
Loki object storage request failures
Loki query duration
Loki query frontend queueing
Loki compactor status
Collector pod restarts
Collector delivery errors
Collector memory pressure
PVC usage and pending PVCs
Object bucket growth
```

## 17. Label Cardinality and Query Performance

Loki performance depends heavily on labels. Labels should help narrow queries, but they must not explode into millions of unique streams.

Good labels:

```text
namespace
pod
container
node
log_type
cluster
application
component
```

Dangerous labels:

```text
request_id
trace_id
session_id
user_id
order_id
ip_address
full URL path with IDs
random UUID
error message
stack trace content
```

Bad label cardinality creates too many streams, which increases memory pressure, index size, ingestion overhead, and query cost.

Production rule:

> Use labels for stable dimensions. Use log content parsing for high-cardinality fields.

Example good query pattern:

```logql
{log_type="application", kubernetes_namespace_name="payments"} |= "ERROR"
```

Example risky query pattern:

```logql
{request_id="8f66f7f2-9e7e-4c4a-9c58-..."}
```

Search for request IDs inside log content instead of promoting them to labels.

## 18. Filtering and Noise Control

Short-term logging fails when every application logs everything forever.

You should reduce volume close to the source or in the forwarding pipeline.

Common filtering strategies:

- Drop debug logs in production.
- Drop health-check access logs.
- Exclude noisy namespaces.
- Exclude test containers.
- Keep infrastructure logs longer than dev application logs.
- Route audit logs separately.
- Send critical security logs to SIEM.
- Send bulk logs to low-cost archive.

Example conceptual pipeline design:

```text
application logs from production namespaces -> LokiStack, 7-14 days
application logs from dev namespaces        -> LokiStack, 1-3 days
infrastructure logs                         -> LokiStack, 14-30 days
security/audit logs                         -> SIEM/archive, plus optional short Loki retention
```

Do not solve log noise only by increasing Loki size. Fix application logging behavior and pipeline selection.

## 19. Ingestion Rate Limits and 429 Errors

Loki protects itself with ingestion limits. If Vector sends too much data too quickly, Loki can return HTTP `429 Too Many Requests`.

Typical symptoms in collector logs:

```text
429 Too Many Requests
Ingestion rate limit exceeded
Per stream rate limit exceeded
Retrying after error
```

Important interpretation:

- A few `429` errors during initial backlog ingestion can be normal.
- Persistent `429` errors mean ingestion volume, burst size, or stream design needs attention.
- If average log generation is below the limit, retry behavior may eventually catch up.
- If new log generation continuously exceeds the limit, backlog and data loss risk increase.

Possible actions:

1. Identify noisy namespaces or containers.
2. Drop unnecessary logs.
3. Reduce debug verbosity.
4. Increase LokiStack size if justified.
5. Tune ingestion limits carefully.
6. Split routing for high-volume logs to an external system.

Example limit configuration:

```yaml
spec:
  limits:
    global:
      ingestion:
        ingestionRate: 8
        ingestionBurstSize: 16
```

Do not blindly raise limits. If object storage, network, or ingester resources cannot handle the load, higher limits just move the bottleneck.

## 20. Reliability and Failure Modes

Short-term logging should be designed for graceful degradation.

### 20.1 Collector Failure

Symptoms:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Common causes:

- Missing ClusterRoleBinding.
- Invalid ClusterLogForwarder CR.
- Output TLS CA misconfiguration.
- NetworkPolicy blocking egress.
- Memory pressure on collector pods.
- Node filesystem issues.
- Permission issue reading log files.

### 20.2 Loki Gateway / TLS Failure

Symptoms:

```text
certificate verify failed
self-signed certificate in certificate chain
connection refused
no logs reaching Loki although ClusterLogForwarder says Ready
```

Check:

```bash
oc get cm logging-loki-gateway-ca-bundle -n openshift-logging -o yaml
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Ensure:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

### 20.3 Object Storage Failure

Symptoms:

```text
S3 timeout
AccessDenied
NoSuchBucket
SignatureDoesNotMatch
connection reset by peer
slow queries
chunks upload failure
```

Check:

```bash
oc get secret logging-loki-s3 -n openshift-logging -o yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=ingester --tail=100
oc logs -n openshift-logging -l app.kubernetes.io/component=compactor --tail=100
```

Validate:

- Endpoint URL.
- Bucket name.
- Region.
- Access key.
- Secret key.
- TLS trust.
- Firewall/proxy rules.
- Object storage lifecycle policy.
- Object store quota.

### 20.4 PVC Failure

Symptoms:

```bash
oc get pvc -n openshift-logging
oc get pods -n openshift-logging | grep -i pending
```

Common causes:

- StorageClass unavailable.
- Zone mismatch.
- Quota exhausted.
- PVC stuck terminating.
- Node or zone failure.

Useful commands:

```bash
oc get pvc -n openshift-logging
oc describe pvc <pvc-name> -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp
```

If a PVC is stuck terminating due to `kubernetes.io/pv-protection`, only remove finalizers when you understand the data-loss impact:

```bash
oc patch pvc <pvc_name> -n openshift-logging \
  -p '{"metadata":{"finalizers":null}}'
```

### 20.5 Query Slowness

Symptoms:

```text
Log UI timeout
queries take too long
query frontend queue grows
high querier CPU/memory
object storage read latency high
```

Fix approach:

1. Narrow the time range.
2. Add selective labels.
3. Avoid broad text search across all namespaces.
4. Reduce label cardinality.
5. Increase Loki size if needed.
6. Check object storage latency.
7. Check query frontend and querier logs.

Bad query:

```logql
{log_type="application"} |= "error"
```

Better query:

```logql
{log_type="application", kubernetes_namespace_name="payments"} |= "error"
```

Even better during incident:

```logql
{log_type="application", kubernetes_namespace_name="payments", kubernetes_container_name="api"} |= "error"
```

- Review query latency complaints.
- Confirm retention is working.
- Confirm object lifecycle rules are active.

### Monthly

- Recalculate log volume and retention cost.
- Review audit log routing.
- Review application teams using debug logging.
- Validate upgrade channel compatibility.
- Test restore/recovery assumptions for object storage access.
- Review NetworkPolicy rules for collector and Loki traffic.

## 23. Advanced Design Patterns

### 23.1 Dual-destination Pattern

Use LokiStack for recent troubleshooting and external storage for long-term retention.

```text
application + infrastructure -> LokiStack, 7-14 days
application + infrastructure -> external archive, 30-90 days if needed
audit                       -> SIEM/archive, long-term
audit                       -> LokiStack, optional 1-3 days
```

### 23.2 Cost-control Pattern

```text
production namespaces -> 14 days
shared services       -> 14 days
dev/test namespaces   -> 1-3 days
noisy debug workloads -> drop or 1 day
health-check logs     -> drop
```

### 23.3 Security Pattern

```text
audit logs -> SIEM
OAuth/API/security-sensitive infra logs -> SIEM + LokiStack
normal app logs -> LokiStack
sensitive fields -> prune before forwarding externally
```

### 23.4 Multi-team Platform Pattern

Use RBAC and tenancy so teams can query logs they are allowed to see. Avoid giving broad log access to every developer. Namespace-level visibility should match organizational access policies.

## 24. Troubleshooting Scenarios

### Scenario 1: ClusterLogForwarder Ready but No Logs in UI

Likely causes:

- Missing or incorrect `tls.ca` block.
- Collector cannot reach Loki gateway.
- Output target name or namespace is wrong.
- Collector is retrying delivery.
- UI plugin or LokiStack tenancy issue.

Commands:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
oc get cm logging-loki-gateway-ca-bundle -n openshift-logging
oc get lokistack logging-loki -n openshift-logging -o yaml
```

Fix:

- Add the correct CA bundle.
- Correct the target name and namespace.
- Check NetworkPolicy and service connectivity.

### Scenario 2: Collector DaemonSet Missing

Likely cause:

- `ClusterLogForwarder.inputRefs` includes a log type for which the service account lacks RBAC.

Commands:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get clusterrolebinding -o wide | grep collect
```

Fix:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

Add audit RBAC only if audit is in `inputRefs`.

### Scenario 3: Loki 429 Errors

Likely causes:

- Log storm.
- Initial backlog.
- High-volume audit logs.
- Too many noisy applications.
- Insufficient LokiStack size.
- Per-stream limit exceeded.

Commands:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 | grep -i '429\|rate'
oc logs -n openshift-logging -l app.kubernetes.io/component=ingester --tail=200 | grep -i 'rate\|limit'
```

Fix sequence:

1. Identify noisy source.
2. Reduce log verbosity.
3. Add filters or shorter retention.
4. Tune ingestion limits if justified.
5. Increase LokiStack size if sustained volume requires it.

### Scenario 4: Logs Retained Forever in Bucket

Likely causes:

- No bucket lifecycle policy.
- No LokiStack retention.
- Retention configured for streams but object storage lifecycle not configured.

Fix:

- Add object lifecycle policy for the bucket.
- Add LokiStack retention if lifecycle policy is unavailable.
- Confirm supported retention window.

### Scenario 5: Queries Are Slow

Likely causes:

- Broad time range.
- Broad selectors.
- Full-text search across too many streams.
- High label cardinality.
- Object storage latency.
- Undersized querier/query-frontend.

Fix:

- Start with namespace, pod, container, log type, and short time range.
- Avoid searching all application logs for generic strings.
- Review labels and cardinality.
- Check query frontend and querier resource pressure.

## 25. Best Practices for 10-year Experienced Administrators

1. **Treat LokiStack as an operational cache, not a compliance archive.**  
   Keep it lean and fast.

2. **Control log volume before scaling infrastructure.**  
   Debug logs and health-check spam should not dictate platform cost.

3. **Use retention tiers.**  
   Dev logs rarely need the same retention as production infrastructure logs.

4. **Forward audit logs externally.**  
   LokiStack can help with recent investigation, but SIEM/archive should handle compliance.

5. **Always configure object lifecycle or Loki retention.**  
   No retention means unbounded bucket growth.

6. **Keep labels stable and low-cardinality.**  
   Bad labels are one of the fastest ways to damage Loki performance.

7. **Verify ClusterLogForwarder status after every change.**  
   `Authorized`, `Valid`, and `Ready` should be `True`.

8. **Do not ignore 429 errors if persistent.**  
   Occasional backlog retry is different from sustained ingestion overload.

9. **Test failure modes.**  
   Simulate object storage unavailability, collector restart, and noisy namespace bursts in non-production.

10. **Document ownership.**  
   Decide who owns app log verbosity, platform retention, SIEM forwarding, bucket lifecycle, and incident query access.

## 30. Final Takeaway

Short-term log aggregation in OpenShift is about **speed, focus, and operational usefulness**.

A good design gives platform teams enough recent log history to troubleshoot incidents quickly without turning the OpenShift cluster into an expensive, slow, long-term logging warehouse.

The production-grade pattern is:

```text
Vector + ClusterLogForwarder + LokiStack = recent troubleshooting
External SIEM/archive/object storage     = long-term compliance and historical retention
Retention + filtering + low-cardinality labels = sustainable logging
```
