## 1. Executive Summary

In older OpenShift Logging deployments, the default logging stack was commonly described as **EFK**:

- **E** = Elasticsearch as the internal log store
- **F** = Fluentd as the node-level collector
- **K** = Kibana as the visualization/search UI

In current OpenShift Logging direction, Elasticsearch is a **legacy concept**. The modern Red Hat-managed stack is based on:

- **Vector** for collection and forwarding
- **LokiStack** for Red Hat-managed log storage
- **Cluster Observability Operator (COO) UI plugin** for log visualization

For an advanced administrator, Elasticsearch remains important because many production clusters still have historical Logging 5.x deployments, brownfield upgrades, Kibana dashboards, existing operational runbooks, external Elasticsearch forwarding, or migration projects from Elasticsearch to LokiStack.

The key operational idea is simple:

> Elasticsearch in OpenShift Logging was designed as a **short-term troubleshooting log store**, not as a long-term SIEM, compliance archive, or unlimited search platform.

## 2. Version and Support Reality

### Legacy stack

Older OpenShift Logging used:

```text
Node logs / container logs / audit logs
        ↓
Fluentd DaemonSet
        ↓
Internal Elasticsearch log store
        ↓
Kibana UI
```

### Current stack direction

OpenShift Logging 6.x moves away from Elastic-based managed storage and visualization:

```text
Node logs / container logs / audit logs
        ↓
Vector collector
        ↓
LokiStack
        ↓
OpenShift Observe → Logs / COO logging UI plugin
```

### Practical support meaning

For a senior OpenShift administrator:

| Area | Legacy Elasticsearch Logging | Modern Logging Direction |
|---|---|---|
| Collector | Fluentd | Vector |
| Log store | Elasticsearch | LokiStack |
| Visualization | Kibana | OpenShift console / COO UI plugin |
| Main API | `logging.openshift.io/v1` with `ClusterLogging` and `ClusterLogForwarder` | `observability.openshift.io` ClusterLogForwarder model in Logging 6 |
| New deployment recommendation | Do not design new managed logging around Elasticsearch | Use LokiStack or external enterprise log platform |
| Long-term storage | Not recommended as internal default | Use external storage/SIEM/log analytics platform |

## 3. Why Elasticsearch Is Called Legacy in OpenShift Logging

Elasticsearch became legacy in OpenShift Logging because Red Hat moved the managed logging storage and visualization stack away from Elastic products. Operationally, this was driven by several realities:

1. **High resource consumption**  
   Elasticsearch indexes log content at ingestion time. This gives strong search capability, but it costs CPU, memory, disk I/O, and storage.

2. **Storage sensitivity**  
   Elasticsearch is based on Lucene. It is sensitive to storage latency and file system behavior. Unsupported storage, especially NFS-style storage, can cause corruption or instability.

3. **Short-term design**  
   The internal OpenShift Elasticsearch deployment was optimized and tested for short-term retention, commonly around seven days. Long-term retention was expected to be handled outside the cluster.

4. **Operational complexity**  
   Administrators had to understand shards, replicas, index rollover, disk watermarks, JVM pressure, memory requests, persistent volumes, Kibana index patterns, and collector backpressure.

5. **Modern OpenShift Logging architecture**  
   LokiStack is preferred for Red Hat-managed short-term log storage, and Vector is the supported collector direction in the newer logging architecture.

## 4. Legacy EFK Architecture

A classic OpenShift Logging 5.x deployment using Elasticsearch looked like this:

```text
+------------------------------------------------------------+
|                    OpenShift Cluster                       |
|                                                            |
|  +----------------+       +-----------------------------+  |
|  | Worker Node 1  |       | Worker Node 2               |  |
|  |                |       |                             |  |
|  | /var/log/...   |       | /var/log/...                |  |
|  | journald       |       | journald                    |  |
|  | container logs |       | container logs              |  |
|  | Fluentd Pod    |       | Fluentd Pod                 |  |
|  +-------+--------+       +-------------+---------------+  |
|          |                              |                  |
|          +--------------+---------------+                  |
|                         |                                  |
|                         v                                  |
|              +---------------------+                       |
|              | Elasticsearch SVC   |                       |
|              +----------+----------+                       |
|                         |                                  |
|          +--------------+---------------+                  |
|          |              |               |                  |
|          v              v               v                  |
|   +-------------+ +-------------+ +-------------+          |
|   | ES Data Pod | | ES Data Pod | | ES Data Pod |          |
|   | PVC 1       | | PVC 2       | | PVC 3       |          |
|   +-------------+ +-------------+ +-------------+          |
|                         |                                  |
|                         v                                  |
|                 +---------------+                          |
|                 | Kibana Route  |                          |
|                 +---------------+                          |
|                                                            |
+------------------------------------------------------------+
```

### Main characteristics

- A collector pod runs on every node.
- Logs are normalized and forwarded to the internal Elasticsearch service.
- Elasticsearch stores logs in indices.
- Kibana reads from Elasticsearch and provides search/visualization.
- OpenShift RBAC controls which logs a user can see.
- Internal Elasticsearch is not intended to be a regulatory archive.

## 5. Core Components

### 5.1 Red Hat OpenShift Logging Operator / Cluster Logging Operator

The logging operator manages the logging stack components. In the legacy model, it watches the `ClusterLogging` custom resource and reconciles collector, log store, and visualization components.

Important legacy object:

```bash
oc get clusterlogging -n openshift-logging
oc get clusterlogging instance -n openshift-logging -o yaml
```

### 5.2 OpenShift Elasticsearch Operator

The Elasticsearch Operator manages the Elasticsearch cluster used by legacy OpenShift Logging. It creates and manages:

- Elasticsearch custom resource
- Elasticsearch deployments
- Elasticsearch services
- Secrets and certificates
- Persistent volume claims
- Index management jobs/cronjobs

Useful commands:

```bash
oc get elasticsearch -n openshift-logging
oc describe elasticsearch elasticsearch -n openshift-logging
oc get pods -n openshift-logging -l component=elasticsearch
```

### 5.3 Fluentd Collector

In the older stack, Fluentd runs as a DaemonSet and collects:

- Container logs from `/var/log/containers/*.log`
- Node and system logs from journald
- Optional audit logs from `/var/log/audit/audit.log`

Useful commands:

```bash
oc get daemonset -n openshift-logging
oc get pods -n openshift-logging -l component=collector
oc logs -n openshift-logging ds/collector
```

Depending on the OpenShift Logging version, collector labels and names can vary. Always check actual resources:

```bash
oc get pods -n openshift-logging --show-labels
```

### 5.4 Elasticsearch Log Store

Elasticsearch stores log events as documents. OpenShift Logging historically divided logs into source types such as:

- `app`
- `infra`
- `audit`

It uses indices, shards, and replicas to distribute and protect data.

### 5.5 Kibana

Kibana was the legacy UI for searching and visualizing Elasticsearch logs. Users typically created index patterns such as:

- `app`
- `infra`
- `audit`

User permissions determine which logs are visible.

## 6. Data Flow: From Pod Log to Searchable Document

### Step-by-step flow

1. Application writes to `stdout` or `stderr`.
2. CRI-O stores container logs on the node.
3. Fluentd tails container log files.
4. Fluentd enriches records with Kubernetes metadata.
5. Fluentd forwards logs to the configured output.
6. The default output sends logs to internal Elasticsearch.
7. Elasticsearch indexes logs into app/infra/audit indices.
8. Kibana queries Elasticsearch.
9. RBAC limits user visibility.

### Example enriched log document fields

A log event can include fields similar to:

```yaml
@timestamp: "2026-07-03T10:15:30.123Z"
message: "User login successful"
log_type: application
kubernetes:
  namespace_name: payments
  pod_name: api-7f88c9f9f9-abcde
  container_name: api
  labels:
    app: payments-api
level: info
```

### Important point

Elasticsearch does not merely store raw lines. It indexes fields so users can search, filter, and aggregate log events.

## 7. Log Types: Application, Infrastructure, and Audit

### 7.1 Application logs

Application logs come from user workloads running in normal application namespaces.

Examples:

```text
Namespace: payments
Pod: payments-api-xxx
Container log: stdout/stderr
Index category: app
```

Developers normally see only application logs from projects where they have access.

### 7.2 Infrastructure logs

Infrastructure logs come from platform components and nodes, including namespaces such as:

- `openshift-*`
- `kube-*`
- `default`

Examples:

```text
openshift-apiserver
openshift-authentication
openshift-ingress
kube-apiserver
node journal logs
```

These are generally administrator-focused logs.

### 7.3 Audit logs

Audit logs include:

- Kubernetes API server audit logs
- OpenShift API server audit logs
- Node audit logs from `/var/log/audit/audit.log`

Important legacy behavior:

> Audit logs are not stored in the internal Elasticsearch log store by default because the internal store is not considered secure/compliance-grade audit storage.

To send audit logs to internal Elasticsearch, a `ClusterLogForwarder` pipeline must explicitly include `audit` and the `default` output.

Example:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  pipelines:
    - name: audit-to-default
      inputRefs:
        - audit
      outputRefs:
        - default
```

Use this only when it matches your organization security and compliance requirements.

## 8. Elasticsearch Concepts You Must Know

### 8.1 Document

A document is one log event stored in Elasticsearch.

Example:

```json
{
  "@timestamp": "2026-07-03T10:15:30Z",
  "message": "GET /api/orders 200",
  "kubernetes": {
    "namespace_name": "orders",
    "pod_name": "orders-api-abcde"
  }
}
```

### 8.2 Index

An index is a logical collection of documents.

In legacy OpenShift Logging, logs are grouped into indices or aliases such as:

```text
app
infra
audit
```

Behind the scenes, rollover indices can look like:

```text
app-000001
app-000002
infra-000001
audit-000001
```

### 8.3 Shard

A shard is a piece of an index. Elasticsearch splits an index into primary shards and distributes them across data nodes.

OpenShift-specific point:

```text
Number of primary shards for index templates = number of Elasticsearch data nodes
```

This has a sizing impact. More data nodes can mean more primary shards for newly created indices, which affects CPU, memory, and disk overhead.

### 8.4 Replica

A replica is a copy of a primary shard. Replicas provide resilience if a node fails.

### 8.5 Cluster health

Elasticsearch cluster health commonly appears as:

| Health | Meaning |
|---|---|
| `green` | All primary and replica shards are assigned |
| `yellow` | Primary shards are assigned, but some replicas are unassigned |
| `red` | One or more primary shards are unassigned; data/search impact likely |

Check health:

```bash
ES_POD=$(oc get pod -n openshift-logging -l component=elasticsearch -o jsonpath='{.items[0].metadata.name}')
oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cluster/health?pretty'
```

### 8.6 Ingest-heavy workload

Logging is write-heavy. Elasticsearch must continuously receive, parse, index, replicate, and flush logs.

The biggest operational pressure points are:

- CPU during indexing
- JVM heap pressure
- Disk I/O
- Persistent volume latency
- Shard count
- Retention period
- Log volume spikes
- Collector buffering/backpressure

## 10. ClusterLogging CR for Legacy Elasticsearch

A typical legacy `ClusterLogging` CR defines:

- `managementState`
- `logStore`
- `collection`
- `visualization`

Example:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogging
metadata:
  name: instance
  namespace: openshift-logging
spec:
  managementState: Managed
  logStore:
    type: elasticsearch
    elasticsearch:
      nodeCount: 3
      redundancyPolicy: SingleRedundancy
      storage:
        storageClassName: gp2
        size: 200G
      resources:
        requests:
          cpu: "1"
          memory: 16Gi
        limits:
          memory: 16Gi
    retentionPolicy:
      application:
        maxAge: 7d
      infrastructure:
        maxAge: 7d
      audit:
        maxAge: 1d
  visualization:
    type: kibana
    kibana:
      replicas: 1
  collection:
    type: fluentd
```

### Field explanation

| Field | Meaning |
|---|---|
| `managementState: Managed` | Operator actively reconciles resources |
| `logStore.type: elasticsearch` | Use Elasticsearch as internal log store |
| `nodeCount: 3` | Three Elasticsearch data nodes |
| `redundancyPolicy` | Controls shard replica behavior |
| `storage` | PVC settings for each ES data node |
| `retentionPolicy` | Log retention by source type |
| `visualization.type: kibana` | Deploy Kibana legacy UI |
| `collection.type: fluentd` | Use Fluentd collector |

### `Managed` vs `Unmanaged`

| State | Meaning |
|---|---|
| `Managed` | Operator reconciles desired state |
| `Unmanaged` | Operator stops reconciling most changes; useful during certain migrations or support workflows |
| `Removed` | Component removal behavior, depending on version |

During migration, docs commonly use a temporary patch like:

```bash
oc -n openshift-logging patch clusterlogging/instance \
  -p '{"spec":{"managementState":"Unmanaged"}}' \
  --type=merge
```

## 11. ClusterLogForwarder with Elasticsearch

`ClusterLogForwarder` controls where logs are sent.

### 11.1 Default internal Elasticsearch output

In legacy logging, `default` means the internal log store declared in `ClusterLogging`.

Example: send application and infrastructure logs to internal Elasticsearch:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  pipelines:
    - name: app-and-infra-to-default
      inputRefs:
        - application
        - infrastructure
      outputRefs:
        - default
```

### 11.2 Send audit logs to default internal Elasticsearch

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  pipelines:
    - name: audit-to-default
      inputRefs:
        - audit
      outputRefs:
        - default
```

Use this carefully. Audit logs often require stricter storage, retention, access control, and compliance rules.

### 11.3 Forward logs to external Elasticsearch

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  outputs:
    - name: external-elasticsearch
      type: elasticsearch
      url: https://elasticsearch.example.com:9200
      secret:
        name: external-elasticsearch-secret
  pipelines:
    - name: app-to-external-es
      inputRefs:
        - application
      outputRefs:
        - external-elasticsearch
```

Secret example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: external-elasticsearch-secret
  namespace: openshift-logging
type: Opaque
stringData:
  username: elastic_user
  password: strong_password
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----
```

Exact secret keys can vary by output type and logging version. Always confirm against the version-specific OpenShift Logging documentation.

### 11.4 Important naming rule in legacy mode

In older logging workflows, the `ClusterLogForwarder` named `instance` in the `openshift-logging` namespace had special legacy behavior. Do not create random duplicate CLFs in the same namespace unless your logging version supports multi log forwarding and the operator is configured for it.

## 12. Kibana Legacy Visualization

Kibana was used to search and visualize Elasticsearch data.

### Access model

Users access Kibana through OpenShift OAuth. The same OpenShift identity is used, and access depends on OpenShift RBAC.

Typical access path:

```text
OpenShift Web Console → Application Launcher → Logging → Kibana
```

### Index patterns

Common index patterns:

| User type | Index pattern |
|---|---|
| Developer | `app` |
| Cluster admin | `app`, `infra`, `audit` |

Time field:

```text

```

### Why logs may not show in Kibana

Common reasons:

1. No index pattern created.
2. Wrong index pattern selected.
3. Time range is wrong.
4. User lacks RBAC permission.
5. Audit logs were never forwarded to internal Elasticsearch.

7. Elasticsearch is unhealthy.
8. Index rollover/retention already deleted old data.

```bash

```

## 13. Retention, Rollover, and Index Management

Retention controls how long logs remain in Elasticsearch.

Example:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogging
metadata:
  name: instance
  namespace: openshift-logging
spec:
  logStore:
    type: elasticsearch
    retentionPolicy:
      application:
        maxAge: 7d
      infrastructure:
        maxAge: 7d
      audit:
        maxAge: 1d
```

### Rollover concept

Elasticsearch does not usually write forever into one index. It rolls over to a new index when certain conditions are met.

Common rollover triggers include:

- Index age exceeds configured max age.
- Index size becomes too large.
- Document count becomes too high.

After rollover, old indices are deleted based on the retention policy.

### Default behavior

If no retention policy is configured, old docs historically defaulted to deletion after approximately seven days in OpenShift Logging-managed Elasticsearch.

### Check index management cronjobs

```bash
oc get cronjob -n openshift-logging | grep elasticsearch
```

Example names can include:

```text
elasticsearch-im-app
elasticsearch-im-infra
elasticsearch-im-audit
```

### Verify indices

```bash
ES_POD=$(oc get pod -n openshift-logging -l component=elasticsearch -o jsonpath='{.items[0].metadata.name}')

oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cat/indices?v'
```

### Senior admin advice

Retention is not only a compliance decision. It is a capacity decision.

Increasing retention from 7 days to 30 days might require:

- Larger PVCs
- More data nodes
- Faster storage
- More memory
- More CPU
- Better shard management
- External archiving strategy

## 14. Storage Design

Elasticsearch storage is one of the most important design decisions.

### 14.1 Persistent storage is expected

Production Elasticsearch requires persistent storage. Each Elasticsearch data node uses its own volume.

Example:

```yaml
spec:
  logStore:
    type: elasticsearch
    elasticsearch:
      nodeCount: 3
      storage:
        storageClassName: gp2
        size: 200G
```

### 14.2 Avoid unsupported storage

Do not use NFS-backed volumes for Elasticsearch data. Elasticsearch/Lucene expects file system behavior that NFS does not reliably provide for this workload.

Avoid:

```text
NFS
NAS-backed unsupported volumes
Gluster-style unsupported NAS paths
Raw block volumes for local volume use cases
```

Preferred storage traits:

- Low latency
- High IOPS
- Stable filesystem semantics
- Persistent volumes with good throughput
- Storage class appropriate for database/search workloads

### 14.3 emptyDir is non-production

Example:

```yaml
spec:
  logStore:
    type: elasticsearch
    elasticsearch:
      nodeCount: 3
      storage: {}
```

This can create ephemeral storage behavior. If the pod restarts or is redeployed, data can be lost.

Use only for labs, demos, or temporary non-production troubleshooting.

### 14.4 PVC troubleshooting

Check PVC status:

```bash
oc get pvc -n openshift-logging
oc describe pvc <pvc-name> -n openshift-logging
```

Check storage class:

```bash
oc get sc
oc describe sc <storage-class>
```

Common PVC issues:

| Symptom | Likely cause |
|---|---|
| PVC Pending | No default storage class, wrong storage class, insufficient PV capacity |
| Pod Pending | PVC not bound, node selector/toleration issue |
| Slow indexing | Storage latency/IOPS bottleneck |
| Red cluster | Lost PV, node failure, shard allocation failure |

## 15. Sizing and Performance

### 15.1 Memory

Elasticsearch is memory-intensive. Legacy OpenShift deployments commonly used three Elasticsearch nodes with large memory requests. For production, avoid under-sizing.

Typical senior-admin rule:

```text
Do not treat Elasticsearch like a lightweight stateless pod.
It behaves more like a distributed database/search engine.
```

Check resource requests:

```bash
oc get pod -n openshift-logging -l component=elasticsearch \
  -o custom-columns=NAME:.metadata.name,CPU_REQ:.spec.containers[*].resources.requests.cpu,MEM_REQ:.spec.containers[*].resources.requests.memory
```

### 15.2 Example resource tuning

```yaml
spec:
  logStore:
    type: elasticsearch
    elasticsearch:
      resources:
        requests:
          cpu: "1"
          memory: 16Gi
        limits:
          memory: 16Gi
      proxy:
        resources:
          requests:
            memory: 100Mi
          limits:
            memory: 100Mi
```

### 15.3 Requests and limits

For Elasticsearch, memory request and limit are often kept equal to reduce scheduling surprises and help the pod get the memory it expects.

Example:

```yaml
resources:
  requests:
    cpu: "8"
    memory: 32Gi
  limits:
    memory: 32Gi
```

### 15.4 CPU

CPU pressure appears as:

- Increased ingest latency
- Fluentd buffering
- Search slowness
- JVM GC pressure
- Kibana timeout
- Delayed shard recovery

Check CPU:

```bash
oc adm top pod -n openshift-logging
oc adm top node
```

### 15.5 Disk

Elasticsearch disk pressure is dangerous. If nodes approach disk watermarks, shard allocation and writes can degrade or stop.

Check disk from Elasticsearch:

```bash
oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cat/allocation?v'
```

Check PVC capacity:

```bash
oc get pvc -n openshift-logging
```

### 15.6 Query load

Heavy Kibana queries over long time ranges can affect ingestion. Avoid allowing broad, expensive wildcard queries during incidents.

Good operational habits:

- Narrow time range.
- Filter by namespace/pod/container.
- Avoid wide regex searches.
- Use short retention internally.
- Forward long-term logs externally.

## 16. High Availability and Redundancy Policies

Elasticsearch uses replicas to protect data.

Legacy OpenShift Logging allowed redundancy policies such as:

| Policy | Behavior | Use case |
|---|---|---|
| `FullRedundancy` | Replicates primary shards to every data node | Highest safety, highest disk, lower performance |
| `MultipleRedundancy` | Replicates to about half the data nodes | Balance between safety and performance |
| `SingleRedundancy` | One replica copy | Common production baseline with at least two data nodes |
| `ZeroRedundancy` | No replica copies | Better performance, but data loss risk if node/PV fails |

Example:

```yaml
spec:
  logStore:
    type: elasticsearch
    elasticsearch:
      nodeCount: 3
      redundancyPolicy: SingleRedundancy
```

### HA rule

A highly available Elasticsearch deployment requires at least three Elasticsearch nodes, preferably spread across different worker nodes or failure domains.

### Anti-affinity and node placement

Use dedicated infrastructure nodes when possible:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=""
oc label node worker-2 node-role.kubernetes.io/infra=""
oc label node worker-3 node-role.kubernetes.io/infra=""
```

Then schedule logging workloads appropriately using supported `ClusterLogging` fields for node selectors and tolerations in your version.

### Failure domain thinking

Do not place all ES pods on one physical host. For real HA, spread across:

- Nodes
- Racks
- Zones
- Storage failure domains

## 17. Security and RBAC

### 17.1 User log visibility

OpenShift Logging integrates with OpenShift RBAC.

General behavior:

- Developers can see logs for projects where they have access.
- Cluster admins can see app, infra, and audit logs.
- Infra/audit visibility requires broader permissions.

Check permission:

```bash
oc auth can-i get pods --subresource=log -n <project>
```

### 17.2 Elasticsearch route exposure

By default, internal Elasticsearch is not exposed outside the cluster. If needed, an administrator can create a re-encrypt route and access it using an OpenShift token and CA certificate.

Extract CA:

```bash
oc project openshift-logging
oc extract secret/elasticsearch --to=. --keys=admin-ca
```

Create re-encrypt route example:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: elasticsearch
  namespace: openshift-logging
spec:
  to:
    kind: Service
    name: elasticsearch
  tls:
    termination: reencrypt
    destinationCACertificate: |
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----
```

Verify:

```bash
token=$(oc whoami -t)
routeES=$(oc get route elasticsearch -n openshift-logging -o jsonpath='{.spec.host}')

curl -k -H "Authorization: Bearer ${token}" \
  "https://${routeES}/_cluster/health?pretty"
```

### 17.3 Audit log warning

The internal OpenShift Elasticsearch store is not a secure compliance archive for audit logs. For regulated environments, forward audit logs to a dedicated SIEM or compliant external log platform.

### 17.4 Secrets and certificates

Check secrets:

```bash
oc get secret -n openshift-logging | grep -E 'elastic|kibana|collector'
```

Do not copy Elasticsearch internal certificates casually. Treat them as sensitive cluster credentials.

## 20. Rolling Restart Procedure

A rolling restart might be needed after certain config changes or node maintenance.

### Safe operational idea

1. Check cluster health.
2. Stop or reduce new ingestion if required.
3. Flush/sync data.
4. Disable unnecessary shard movement during restart.
5. Restart one ES node at a time.
6. Wait for health to return to green/yellow.
7. Re-enable allocation.
8. Restore collection.

### Commands

Change project:

```bash
oc project openshift-logging
```

Get ES pods:

```bash
oc get pods -l component=elasticsearch
```

Optionally stop collector ingestion temporarily:

```bash
oc -n openshift-logging patch daemonset/collector \
  -p '{"spec":{"template":{"spec":{"nodeSelector":{"logging-infra-collector":"false"}}}}}'
```

Synced flush:

```bash
oc exec <any-es-pod> -c elasticsearch -- \
  es_util --query='_flush/synced' -XPOST
```

Limit allocation movement:

```bash
oc exec <any-es-pod> -c elasticsearch -- \
  es_util --query='_cluster/settings' -XPUT \
  -d '{ "persistent": { "cluster.routing.allocation.enable" : "primaries" } }'
```

Restart deployment one by one:

```bash
oc rollout restart deployment/<elasticsearch-deployment-name> -n openshift-logging
oc rollout status deployment/<elasticsearch-deployment-name> -n openshift-logging
```

Check health:

```bash
oc exec <any-es-pod> -c elasticsearch -- \
  es_util --query='_cluster/health?pretty'
```

Re-enable allocation:

```bash
oc exec <any-es-pod> -c elasticsearch -- \
  es_util --query='_cluster/settings' -XPUT \
  -d '{ "persistent": { "cluster.routing.allocation.enable" : "all" } }'
```

Restore collector:

```bash
oc -n openshift-logging patch daemonset/collector \
  -p '{"spec":{"template":{"spec":{"nodeSelector":{"logging-infra-collector":"true"}}}}}'
```

Important: actual collector node selector strategy might differ in your cluster. Confirm current DaemonSet spec before patching.

## 21. Common Failure Scenarios

### Scenario 1: Elasticsearch pod OOMKilled

Symptoms:

```bash
oc get pod -n openshift-logging
oc describe pod <es-pod> -n openshift-logging | grep -i oom
```

Likely causes:

- Memory request/limit too low
- High query load
- Too many shards
- Retention too long
- Log volume spike
- Proxy memory too low in large clusters

Fix approach:

1. Check memory usage.
2. Check JVM pressure in logs.
3. Reduce query load.
4. Reduce retention if needed.
5. Increase ES/proxy memory through `ClusterLogging` CR.
6. Ensure nodes have enough allocatable memory.

### Scenario 2: Cluster health yellow

Likely causes:

- Replica shards unassigned
- Node count too low for redundancy policy
- Disk allocation rules preventing replicas
- Recently restarted node

Commands:

```bash
oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cat/shards?v'

oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cluster/allocation/explain?pretty'
```

Fix approach:

- Wait if recovery is in progress.
- Check disk space.
- Check node availability.
- Validate redundancy policy.
- Confirm PVCs are healthy.

### Scenario 3: Cluster health red

This is serious.

Possible causes:

- Primary shard unassigned
- PV lost or corrupted
- Data node down
- Disk full
- Failed recovery

Actions:

1. Check which primary shard is unassigned.
2. Check data node pods and PVCs.
3. Check events for storage/node failures.
4. Avoid deleting PVCs unless you intentionally accept data loss.
5. Engage Red Hat Support for production.

### Scenario 4: No application logs in Kibana

Check pipeline:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Check collector:

```bash
oc logs -n openshift-logging -l component=collector --tail=200
```

Check app index:

```bash
oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cat/indices/app*?v'
```

Common reasons:

- Collector not running on nodes
- Wrong CLF pipeline
- ES unavailable
- Index pattern missing
- Time range wrong
- Application not writing to stdout/stderr

### Scenario 5: Audit logs missing

Expected unless explicitly forwarded.

Check CLF:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Look for:

```yaml
inputRefs:
  - audit
outputRefs:
  - default
```

### Scenario 6: PVC pending

```bash
oc get pvc -n openshift-logging
oc describe pvc <pvc> -n openshift-logging
oc get sc
```

Fix:

- Correct `storageClassName`
- Ensure storage operator is healthy
- Ensure PV capacity exists
- Validate topology constraints

### Scenario 7: Kibana index pattern cannot be created

Check if documents exist:

```bash
oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cat/indices?v'
```

Check time range and aliases:

```bash
oc exec -n openshift-logging "$ES_POD" -c elasticsearch -- \
  es_util --query='_cat/aliases?v'
```

## 22. Backup, Recovery, and Data Protection Reality

### 22.1 Internal ES is short-term

The internal Elasticsearch log store was intended for short-term operational troubleshooting, not as the only copy of critical audit/security data.

### 22.2 Snapshot strategy

Elasticsearch supports snapshot/restore concepts, but OpenShift Logging-managed Elasticsearch has version-specific support boundaries. For production, do not invent an unsupported backup method.

Better approach:

- Forward critical logs to external SIEM/log storage.
- Use compliant long-term storage outside the OpenShift cluster.
- Keep OpenShift internal logging retention short.
- Treat internal ES loss as operational impact, not compliance data loss.

### 22.3 PVC backup caution

Backing up individual Elasticsearch PVCs without cluster-aware coordination is risky. Elasticsearch data consistency spans shards and cluster state. A raw volume backup might not restore cleanly.

### 22.4 Disaster recovery design

For high-value logs:

```text
OpenShift collector
   ├── Internal short-term store for troubleshooting
   └── External SIEM / log lake / enterprise Elasticsearch / Splunk / Kafka / cloud logging
```

This is safer than relying only on internal ES.

## 23. Migration from Elasticsearch to LokiStack

### 23.1 Why migrate

Migration is required for current OpenShift Logging direction because managed Elasticsearch and Kibana are no longer the future stack.

Modern target:

```text
Vector → LokiStack → COO/OpenShift Observe Logs
```

### 23.2 Important migration reality

A typical migration does **not** move historical Elasticsearch data into LokiStack automatically.

Common practical model:

- Old logs remain in Elasticsearch and are viewed through Kibana while retained.
- New logs go to LokiStack and are viewed in OpenShift console logging UI.
- After confidence and retention expiry, Elasticsearch/Kibana are removed.

### 23.3 High-level migration flow

1. Install/verify Loki Operator.
2. Deploy LokiStack with object storage.
3. Migrate visualization from Kibana to COO UI plugin.
4. Switch collection from Fluentd to Vector if not already done.
5. Update `ClusterLogging` or new API configuration to use LokiStack.
6. Run Elasticsearch and Loki in parallel temporarily if needed.
7. Validate new logs in Loki.
8. Preserve or detach old ES/Kibana resources only if required.
9. Delete old `ClusterLogging`, ES, Kibana, and CRDs when safe.

### 23.4 Example migration patch from legacy docs

Temporarily set `ClusterLogging` unmanaged:

```bash
oc -n openshift-logging patch clusterlogging/instance \
  -p '{"spec":{"managementState":"Unmanaged"}}' \
  --type=merge
```

Remove owner references if preserving Elasticsearch/Kibana temporarily:

```bash
oc -n openshift-logging patch elasticsearch/elasticsearch \
  -p '{"metadata":{"ownerReferences":[]}}' \
  --type=merge

oc -n openshift-logging patch kibana/kibana \
  -p '{"metadata":{"ownerReferences":[]}}' \
  --type=merge
```

Update `ClusterLogging` to LokiStack in 5.x-style migration:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogging
metadata:
  name: instance
  namespace: openshift-logging
spec:
  managementState: Managed
  logStore:
    type: lokistack
    lokistack:
      name: logging-loki
  collection:
    type: vector
```

### 23.5 Logging 6.x API direction

In Logging 6.x, log collection and forwarding configuration moves to the `observability.openshift.io` API group, and Vector is the supported collector implementation.

Before any production migration, check:

```bash
oc get clusterversion
oc get csv -A | grep -Ei 'logging|loki|observability'
oc api-resources | grep -Ei 'clusterlogforwarder|clusterlogging|lokistack|uiplugin'
```

### 23.6 Migration validation checklist

Validate before deleting Elasticsearch:

```bash
# Are new app logs visible in Observe → Logs?
# Are infrastructure logs visible to admins?
# Are audit logs forwarded to the required external destination?
# Are retention rules configured in LokiStack or external store?
# Are alerts/dashboards updated?
# Are old Kibana dashboards exported if needed?
# Are SOPs updated for Vector/Loki commands?
```

## 24. Best Practices for Senior OpenShift Administrators

### 24.1 Do not build new production logging on legacy ES

For new OpenShift Logging deployments, use LokiStack or forward to an external enterprise logging platform.

### 24.2 Keep internal retention short

Use internal logging for operational troubleshooting. Forward long-term logs externally.

Recommended design:

```text
Internal store: 3-7 days for fast troubleshooting
External store: 30/90/180/365+ days as per compliance
```

### 24.3 Separate audit logs

Do not casually store audit logs in internal ES. Audit logs should go to a secure, compliant destination.

### 24.4 Use fast persistent storage

Avoid unsupported storage. Treat ES like a stateful distributed data service.

### 24.5 Monitor logging itself

Logging is a platform service. Monitor:

- ES health
- Collector errors
- PVC usage
- Pod restarts
- OOM kills
- Kibana availability
- Index rollover jobs
- Log ingestion latency

### 24.6 Avoid direct manual edits to managed resources

Change supported settings through the supported CRs. Direct edits to operator-managed resources can be overwritten or unsupported.

### 24.7 Use labels and namespaces properly

When troubleshooting logs, filter by:

- namespace
- pod
- container
- node
- log type
- timestamp range

### 24.8 Plan migrations as projects

Elasticsearch-to-Loki migration is not just an operator update. It affects:

- Dashboards
- Queries
- Retention
- RBAC
- Alerts
- SOPs
- External SIEM pipelines
- Audit/compliance workflows
- Developer self-service log access

## 25. Interview and Exam-Oriented Notes

### Q1. What was Elasticsearch used for in legacy OpenShift Logging?

Elasticsearch was the default internal log store. It indexed application, infrastructure, and optionally audit logs so they could be queried and visualized in Kibana.

### Q2. Why is Elasticsearch considered legacy now?

Because modern OpenShift Logging moved Red Hat-managed storage to LokiStack and visualization to the OpenShift/COO logging UI. Elasticsearch/Kibana are not the direction for new managed logging deployments.

### Q3. What are app, infra, and audit logs?

- `application`: user workload container logs
- `infrastructure`: platform and node logs
- `audit`: Kubernetes/OpenShift API and node audit logs

### Q4. Are audit logs stored in internal Elasticsearch by default?

No. In legacy OpenShift Logging, audit logs are not sent to internal Elasticsearch by default because the internal store is not designed as secure compliance-grade audit storage.

### Q5. What is the default output in ClusterLogForwarder?

In legacy logging, `default` points to the internal log store defined by the `ClusterLogging` CR, usually Elasticsearch.

### Q6. What is a shard?

A shard is a piece of an Elasticsearch index. OpenShift-managed index templates set primary shards based on the number of Elasticsearch data nodes.

### Q7. What does yellow cluster health mean?

Primary shards are available, but one or more replica shards are not assigned.

### Q8. What does red cluster health mean?

One or more primary shards are unassigned. This can cause data/search impact and should be treated as a serious incident.

### Q9. Why is NFS not supported for Elasticsearch storage?

Elasticsearch relies on Lucene and requires file system behavior that NFS does not reliably provide for this workload. It can lead to corruption and instability.

### Q10. What is the migration target from Elasticsearch?

LokiStack for storage, Vector for collection, and Cluster Observability Operator/OpenShift console for visualization.

Elasticsearch in OpenShift Logging is no longer the strategic managed logging backend, but a senior OpenShift administrator must still understand it deeply for brownfield support, upgrades, incident response, and migration planning.

A good admin does not only know how to deploy it. A good admin understands:

- why it consumes resources,
- how shards and replicas affect availability,
- why storage choice matters,
- why audit logs require special care,
- how retention impacts cluster stability,
- how to read cluster health,
- how to troubleshoot collector-to-Elasticsearch flow,
- and how to migrate safely to LokiStack without losing operational visibility.
