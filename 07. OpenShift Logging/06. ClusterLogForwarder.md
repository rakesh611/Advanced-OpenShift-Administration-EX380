# ClusterLogForwarder in OpenShift Logging — Advanced Administration Guide

**Audience:** Advanced OpenShift Administrators, OpenShift Platform Engineers, SREs, DevOps Engineers  
**Experience target:** ~10 years Linux / Kubernetes / OpenShift administration  
**Focus:** Red Hat OpenShift Logging 6.x style configuration using `ClusterLogForwarder`  
**Primary API:** `observability.openshift.io/v1`  

---

## 1. What is ClusterLogForwarder?

`ClusterLogForwarder` is the OpenShift Logging custom resource that defines **what logs are collected**, **how logs are filtered or transformed**, and **where logs are forwarded**.

In practical administration terms, it is the routing engine for OpenShift logs.

It answers these questions:

- Should application logs be collected?
- Should infrastructure logs be collected?
- Should audit logs be collected?
- Which namespaces, pods, labels, containers, or sources should be included or excluded?
- Should noisy logs be dropped?
- Should JSON logs be parsed?
- Should fields such as annotations, labels, or sensitive data be pruned?
- Should logs go to in-cluster LokiStack, external Loki, Splunk, Kafka, Elasticsearch, HTTP, syslog, CloudWatch, S3, Google Cloud Logging, Azure Monitor, or OTLP?
- Should different log classes go to different systems?
- Should delivery prioritize speed or durability?

A senior OpenShift administrator should think of `ClusterLogForwarder` as **policy-driven log routing**.

## 2. Modern API version note

OpenShift Logging has changed significantly across versions.

### Legacy style

Older examples often use:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
```

or depend on:

```yaml
kind: ClusterLogging
```

This is common in OpenShift Logging 5.x examples and older OpenShift 4.x documentation.

### Modern Logging 6.x style

Current OpenShift Logging 6.x uses:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
```

Important changes in Logging 6.x:

- The log collection and forwarding configuration is centered around `ClusterLogForwarder`.
- The old `ClusterLogging.logging.openshift.io` and old `ClusterLogForwarder.logging.openshift.io` resources are not the modern API model.
- In-cluster log storage is handled by `LokiStack`, managed by the Loki Operator.
- Visualization is handled by the Cluster Observability Operator through a logging UI plugin.
- The current collector implementation is Vector-based.

For real production work, always confirm the installed CRD and fields with:

```bash
oc api-resources | grep -i clusterlogforwarder
oc explain clusterlogforwarders.observability.openshift.io.spec
oc explain clusterlogforwarders.observability.openshift.io.spec.outputs
oc explain clusterlogforwarders.observability.openshift.io.spec.filters
oc explain clusterlogforwarders.observability.openshift.io.spec.pipelines
```

## 3. Where ClusterLogForwarder fits in OpenShift Logging architecture

A typical modern OpenShift Logging deployment includes these components:

| Component | Responsibility |
|---|---|
| Red Hat OpenShift Logging Operator | Manages log collection and forwarding resources |
| `ClusterLogForwarder` | Defines collection sources, filters, outputs, pipelines, collector tuning, and service account identity |
| Vector collector | Runs on nodes and collects/forwards logs according to `ClusterLogForwarder` |
| Loki Operator | Manages in-cluster LokiStack log storage |
| `LokiStack` | Stores logs inside the cluster, usually for operational troubleshooting |
| Cluster Observability Operator | Enables OpenShift web console log visualization |
| `UIPlugin` | Adds Observe → Logs view in the OpenShift console |

High-level flow:

```text
Application Pods / Node Journals / Audit Logs
                  |
                  v
        Vector Collector DaemonSet
                  |
                  v
        ClusterLogForwarder policy
      inputs -> filters -> pipelines -> outputs
                  |
                  v
LokiStack / Splunk / Kafka / Elasticsearch / S3 / HTTP / Syslog / OTLP / Cloud
```

The collector normally runs as a **DaemonSet**, meaning one collector pod runs on each node so it can read local node log files and journal sources.

## 4. Why ClusterLogForwarder matters in enterprise OpenShift

Without controlled log forwarding, organizations usually face one of these problems:

1. **Too much data**  
   All logs go everywhere. Storage cost increases, queries become slow, and useful signals are buried under noise.

2. **Too little data**  
   Only application logs are visible, while infrastructure or audit logs are missing during incidents.

3. **Wrong data in wrong place**  
   Developers get access to sensitive audit logs, or regulated logs leave the cluster without filtering.

4. **Poor retention design**  
   High-volume troubleshooting logs are stored in expensive systems for too long, while audit logs are not retained long enough.

5. **No separation of stakeholders**  
   SRE, developer, security, and compliance teams all need different log views.

`ClusterLogForwarder` solves this by allowing multiple pipelines:

```text
application logs      -> LokiStack for developers
infrastructure logs   -> Splunk / Elasticsearch for SRE
security audit logs   -> S3 / SIEM for long-term compliance
high-volume app logs  -> filtered before expensive storage
```

## 5. Core ClusterLogForwarder object structure

A `ClusterLogForwarder` generally has these important sections:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector

  inputs:
  - name: my-input
    type: application
    application:
      includes:
      - namespace: my-project

  filters:
  - name: my-filter
    type: drop
    drop:
    - test:
      - field: .level
        matches: debug

  outputs:
  - name: my-output
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt

  pipelines:
  - name: my-pipeline
    inputRefs:
    - my-input
    filterRefs:
    - my-filter
    outputRefs:
    - my-output
```

### Important fields

| Field | Purpose |
|---|---|
| `spec.serviceAccount.name` | Service account used by collector pods |
| `spec.inputs` | Optional custom log source definitions |
| `spec.filters` | Optional log transformation/drop/prune logic |
| `spec.outputs` | Destination definitions |
| `spec.pipelines` | Binds inputs, filters, and outputs |
| `status.conditions` | Shows `Authorized`, `Valid`, and `Ready` state |

## 6. ServiceAccount and RBAC: the most important production rule

The collector does not automatically get permission to read every log type. You must create a service account and grant explicit cluster roles.

### Create collector service account

```bash
oc create sa collector -n openshift-logging
```

### Grant application log permission

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector
```

### Grant infrastructure log permission

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

### Grant audit log permission

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### Why ordering matters

Grant RBAC **before** referencing that log type in `inputRefs`.

For example, if this pipeline references `audit`:

```yaml
pipelines:
- name: audit-to-s3
  inputRefs:
  - audit
  outputRefs:
  - s3-audit
```

then the collector service account must already have:

```bash
collect-audit-logs
```

If you reference a log type without authorization, the Logging Operator can remove the collector DaemonSet as a protective action. The result is severe: **cluster-wide log collection stops** until the RBAC or CR validation issue is fixed.

### Verify RBAC

```bash
oc get clusterrolebinding -o wide | grep collector
oc get clusterrolebinding -o wide | grep collect
```

Check the service account used by the CLF:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.spec.serviceAccount.name}{"\n"}'
```

Check authorization status:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions[?(@.type=="observability.openshift.io/Authorized")].message}{"\n"}'
```

Expected example:

```text
permitted to collect log types: [application audit infrastructure]
```

## 7. Built-in input types

`ClusterLogForwarder` supports reserved high-level input references. These can be used directly in `pipelines.inputRefs`.

### 7.1 `application`

Collects logs from user-deployed application workloads.

Typical sources:

```text
/var/log/containers/*.log
```

Use cases:

- Developer troubleshooting
- Application debugging
- App performance analysis
- App error-rate investigation
- Team-specific log routing

Example pipeline:

```yaml
pipelines:
- name: app-logs-to-loki
  inputRefs:
  - application
  outputRefs:
  - default-lokistack
```

### 7.2 `infrastructure`

Collects infrastructure and OpenShift component logs.

Typical sources:

- OpenShift control plane components
- `openshift-*` namespaces
- `kube-*` namespaces
- Node journal logs
- Container runtime logs
- System services

Use cases:

- API server troubleshooting
- Operator failure analysis
- Node issue diagnosis
- Cluster upgrade debugging
- SRE operational monitoring

Example pipeline:

```yaml
pipelines:
- name: infra-to-loki
  inputRefs:
  - infrastructure
  outputRefs:
  - default-lokistack
```

### 7.3 `audit`

Collects security-sensitive audit logs.

Audit sources may include:

| Source | Meaning |
|---|---|
| `kubeAPI` | Kubernetes API server audit logs |
| `openshiftAPI` | OpenShift API server audit logs |
| `auditd` | Node audit daemon logs |
| `ovn` | OVN network audit logs |

Use cases:

- Compliance
- Security investigations
- API activity tracking
- Privileged action review
- SIEM integration

Example pipeline:

```yaml
pipelines:
- name: audit-to-security-store
  inputRefs:
  - audit
  outputRefs:
  - s3-audit
```

Important: OpenShift Logging is not a complete SIEM by itself. For regulated audit retention, forward audit logs to a secure external or immutable storage system.

## 8. Custom inputs

Custom inputs allow more precise selection than the broad built-in `application`, `infrastructure`, and `audit` input refs.

### 8.1 Filter application logs by namespace and container

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
  - name: payment-api-logs
    type: application
    application:
      includes:
      - namespace: payment-prod
        container: payment-api
      excludes:
      - namespace: payment-prod
        container: debug-sidecar*
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: payment-api-to-loki
    inputRefs:
    - payment-api-logs
    outputRefs:
    - default-lokistack
```

Important behavior:

```text
excludes takes precedence over includes
```

So if a container matches both include and exclude, it is excluded.

### 8.2 Filter application logs by pod labels

```yaml
inputs:
- name: prod-critical-apps
  type: application
  application:
    selector:
      matchLabels:
        environment: prod
        criticality: high
```

With match expressions:

```yaml
inputs:
- name: selected-apps
  type: application
  application:
    selector:
      matchExpressions:
      - key: env
        operator: In
        values:
        - prod
        - qa
      - key: tier
        operator: NotIn
        values:
        - experimental
```

Valid selector operators:

- `In`
- `NotIn`
- `Exists`
- `DoesNotExist`

### 8.3 Filter infrastructure or audit by source

Example: collect only selected audit sources.

```yaml
inputs:
- name: api-audit-only
  type: audit
  audit:
    sources:
    - kubeAPI
    - openshiftAPI
```

Example: collect selected infrastructure sources.

```yaml
inputs:
- name: node-infra-only
  type: infrastructure
  infrastructure:
    sources:
    - node
```

Use this when you want to reduce volume or send different source categories to different destinations.

## 9. Receiver inputs

Receiver inputs allow the collector to act as a server that receives logs over a network protocol.

Supported receiver input types include:

| Receiver type | Purpose |
|---|---|
| `http` | Receives audit logs over HTTP |
| `syslog` | Receives infrastructure logs over syslog |

Important constraints:

- Receiver inputs are not meant as a general-purpose log ingestion gateway for arbitrary products.
- They are supported for logs originating from Red Hat-supported products installed on the same cluster, or hosted control plane scenarios.
- Receiver ports must be between `1024` and `65535`.
- The Operator creates a Service for each configured receiver input.
- Service naming normally follows `<clusterlogforwarder-name>-<input-name>`.

Example HTTP audit receiver:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
  - name: http-audit-receiver
    type: receiver
    receiver:
      type: http
      port: 8443
      http:
        format: kubeAPIAudit
  outputs:
  - name: external-http
    type: http
    http:
      url: https://log-gateway.example.com/audit
  pipelines:
  - name: received-audit-to-http
    inputRefs:
    - http-audit-receiver
    outputRefs:
    - external-http
```

Verify receiver service:

```bash
oc get svc -n openshift-logging
```

## 10. Outputs

Outputs define where logs are sent.

Common output types include:

| Output type | Typical use case |
|---|---|
| `lokiStack` | Red Hat managed in-cluster LokiStack |
| `loki` | External Loki endpoint |
| `splunk` | Splunk HEC integration |
| `elasticsearch` | External Elasticsearch cluster |
| `kafka` | Streaming pipeline / event bus |
| `http` | Generic HTTP endpoint / webhook / custom receiver |
| `syslog` | Traditional syslog/SIEM forwarding |
| `cloudwatch` | AWS CloudWatch Logs |
| `s3` | Long-term archival / compliance storage |
| `googleCloudLogging` | Google Cloud Logging |
| `azureMonitor` | Azure Monitor Logs; check deprecation status in your installed docs |
| `otlp` | OpenTelemetry Protocol forwarding |

### 10.1 LokiStack output

Use `lokiStack` for the in-cluster Red Hat managed LokiStack.

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    authentication:
      token:
        from: serviceAccount
    target:
      name: logging-loki
      namespace: openshift-logging
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

Important:

- `lokiStack.target.name` must match your `LokiStack` CR name.
- If the LokiStack is in another namespace, set `target.namespace` correctly.
- Include the `tls.ca` block when using the LokiStack gateway certificate.
- Missing or incorrect CA configuration can produce a situation where `ClusterLogForwarder` shows `Ready=True`, but logs do not arrive.

### 10.2 External Loki output

Use `loki` for an external Loki deployment.

```yaml
outputs:
- name: external-loki
  type: loki
  loki:
    url: https://loki.example.com:3100
    proxyURL: http://proxy.example.com:8080
    authentication:
      bearerToken:
        secretName: loki-token
        key: token
  tls:
    ca:
      configMapName: external-loki-ca
      key: ca-bundle.crt
```

Use this when the Loki system is not managed as an OpenShift `LokiStack`.

### 10.3 Splunk output

Example Splunk HEC output:

```yaml
outputs:
- name: splunk-prod
  type: splunk
  splunk:
    url: https://splunk-hec.example.com:8088
    authentication:
      token:
        secretName: splunk-hec-token
        key: token
```

Example secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: splunk-hec-token
  namespace: openshift-logging
type: Opaque
stringData:
  token: "REPLACE_WITH_SPLUNK_HEC_TOKEN"
```

Use cases:

- Enterprise SOC/SIEM
- Existing centralized logging platforms
- Application team dashboards
- Security correlation searches

### 10.4 Kafka output

Kafka is useful when logs must be streamed to downstream consumers.

```yaml
outputs:
- name: kafka-prod
  type: kafka
  kafka:
    brokers:
    - tls://kafka-1.example.com:9093
    - tls://kafka-2.example.com:9093
    topic: openshift-logs
    authentication:
      sasl:
        mechanism: SCRAM-SHA-512
        username:
          secretName: kafka-secret
          key: username
        password:
          secretName: kafka-secret
          key: password
  tls:
    ca:
      configMapName: kafka-ca
      key: ca.crt
```

Production notes:

- For Kafka and syslog URLs, ensure port numbers are explicitly present.
- Use TLS for cross-network or production delivery.
- Use topic strategy carefully; too many dynamic topics can hurt Kafka administration.

### 10.5 HTTP output

HTTP output is useful for custom gateways or vendor collectors.

```yaml
outputs:
- name: http-gateway
  type: http
  http:
    url: https://logs.example.com/ingest
    method: POST
    format: ndjson
    authentication:
      bearerToken:
        secretName: http-token
        key: token
  tls:
    ca:
      configMapName: http-ca
      key: ca.crt
```

Notes:

- `format: ndjson` can reduce memory footprint for some receivers.
- Use `insecureSkipVerify: true` only for temporary testing, never as a production default.

### 10.6 Syslog output

```yaml
outputs:
- name: syslog-siem
  type: syslog
  syslog:
    url: tls://siem-syslog.example.com:6514
    rfc: RFC5424
    facility: local0
    severity: informational
  tls:
    ca:
      configMapName: syslog-ca
      key: ca.crt
```

Use cases:

- Traditional SIEM
- Security operations center
- External log archival appliances

### 10.7 S3 output

Use S3 or S3-compatible object storage for long-term retention.

```yaml
outputs:
- name: s3-audit-archive
  type: s3
  s3:
    bucket: openshift-audit-logs
    region: ap-south-1
    keyPrefix: clusters/prod-cluster/audit/%Y/%m/%d/
    authentication:
      type: accessKey
      accessKey:
        keyId:
          secretName: aws-secret
          key: aws_access_key_id
        keySecret:
          secretName: aws-secret
          key: aws_secret_access_key
```

Use cases:

- Long-term compliance archive
- Security investigation retention
- Data lake ingestion
- Low-cost storage tiering

### 10.8 OTLP output

OTLP is useful when your organization is standardizing on OpenTelemetry.

```yaml
outputs:
- name: otel-collector
  type: otlp
  otlp:
    url: https://otel-collector.example.com:4318/v1/logs
    authentication:
      bearerToken:
        secretName: otel-token
        key: token
```

Important:

- OTLP uses the OpenTelemetry data model.
- Field names and structure differ from the ViaQ style used by many traditional OpenShift Logging outputs.
- Align downstream queries, dashboards, and retention policies with the selected data model.

## 11. Pipelines

Pipelines connect inputs, filters, and outputs.

A pipeline is where you say:

```text
Take these logs -> apply these filters -> send to these destinations
```

Example:

```yaml
pipelines:
- name: app-errors-to-splunk
  inputRefs:
  - application
  filterRefs:
  - drop-debug
  - prune-noisy-fields
  outputRefs:
  - splunk-prod
```

### Pipeline behavior

| Behavior | Explanation |
|---|---|
| Multiple inputs | Logs from all referenced inputs flow into the pipeline |
| Multiple outputs | Each output receives a copy of the matching records |
| Optional filters | Filters run before output delivery |
| Filter order matters | Earlier filters can drop records before later filters see them |
| Missing pipeline means dropped logs | If no pipeline references a log type, that log type is not collected/forwarded |
| Output failure isolation | Failure of one output does not necessarily stop forwarding to other outputs |

### Good naming examples

```yaml
pipelines:
- name: apps-prod-to-lokistack
- name: audit-to-s3-archive
- name: infra-to-splunk
- name: payment-errors-to-kafka
```

Bad naming examples:

```yaml
- name: pipeline1
- name: test
- name: logs
```

In production, names should explain intent.

## 12. Filters

Filters transform, enrich, parse, prune, or drop records as they pass through a pipeline.

Common filter types:

| Filter | Purpose |
|---|---|
| `drop` | Drop entire log records based on conditions |
| `prune` | Remove fields from records |
| `parse` | Parse JSON messages into structured fields |
| `openshiftLabels` | Add labels to outbound records |
| `detectMultilineException` | Combine stack traces into one event |
| `kubeAPIAudit` | Reduce/filter Kubernetes API audit events |

### 12.1 Drop filter

Drop filters are used to reduce volume.

Example: drop debug-level logs.

```yaml
filters:
- name: drop-debug
  type: drop
  drop:
  - test:
    - field: .level
      matches: debug
```

Example: drop logs from a noisy namespace.

```yaml
filters:
- name: drop-noisy-namespace
  type: drop
  drop:
  - test:
    - field: .kubernetes.namespace_name
      matches: noisy-dev-namespace
```

Example: drop health check messages.

```yaml
filters:
- name: drop-health-checks
  type: drop
  drop:
  - test:
    - field: .message
      matches: ".*GET /healthz.*"
```

A record is dropped when a test passes. Use regular expressions carefully. A poorly written regex can accidentally drop important logs.

### 12.2 Prune filter

Prune filters remove fields to reduce payload size or protect sensitive data.

Example: remove annotations and labels:

```yaml
filters:
- name: prune-k8s-metadata
  type: prune
  prune:
    in:
    - .kubernetes.annotations
    - .kubernetes.labels
```

Example: keep only selected fields:

```yaml
filters:
- name: keep-minimal-fields
  type: prune
  prune:
    notIn:
    - .message
    - .level
    - .log_type
    - .log_source
    - .kubernetes.namespace_name
    - .kubernetes.pod_name
    - .kubernetes.container_name
```

Do not prune required fields such as:

- `.log_type`
- `.log_source`
- `.message`
- `.kubernetes.namespace_name`
- `.kubernetes.pod_name`
- `.kubernetes.container_name`
- `.level`

If you remove required fields, the CR can become invalid or the output may not work correctly.

### 12.3 Parse filter

The parse filter attempts to parse JSON messages and add structured content.

```yaml
filters:
- name: parse-json
  type: parse
```

Use this when applications write JSON strings to stdout/stderr.

Example application log:

```json
{"level":"error","service":"payment","trace_id":"abc123","message":"payment failed"}
```

After parsing, downstream systems can query structured fields more easily.

### 12.4 Multiline exception detection

Many applications emit stack traces across multiple lines. Without multiline handling, one exception can become dozens of log records.

```yaml
filters:
- name: detect-stacktraces
  type: detectMultilineException
```

Pipeline usage:

```yaml
pipelines:
- name: apps-to-loki
  inputRefs:
  - application
  filterRefs:
  - detect-stacktraces
  outputRefs:
  - default-lokistack
```

Supported languages include common stack trace formats such as Java, JavaScript, Ruby, Python, Go, PHP, and Dart.

Production caution:

- Multiline detection can increase CPU and memory usage.
- Test before enabling cluster-wide.
- Consider enabling only for selected high-value namespaces.

### 12.5 kubeAPIAudit filter

The `kubeAPIAudit` filter reduces audit volume and controls audit detail level.

Audit levels:

| Level | Meaning |
|---|---|
| `None` | Drop the event |
| `Metadata` | Keep metadata only; no request/response bodies |
| `Request` | Keep metadata and request body |
| `RequestResponse` | Keep metadata, request body, and response body |

Example concept:

```yaml
filters:
- name: reduce-audit-noise
  type: kubeAPIAudit
  kubeAPIAudit:
    omitResponseCodes:
    - 404
    - 409
    rules:
    - level: None
      verbs:
      - get
      - list
      - watch
      users:
      - system:serviceaccount:openshift-monitoring:prometheus-k8s
    - level: Metadata
```

Use cases:

- Drop high-volume read-only audit noise
- Retain write operations
- Reduce response body retention
- Keep security-relevant metadata

Senior admin warning: audit filtering is a compliance decision, not only a platform tuning decision. In regulated environments, align this with security and legal requirements.

## 13. Complete baseline: application and infrastructure logs to LokiStack

This is a practical starting configuration.

### 13.1 Create RBAC

```bash
oc create sa collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

### 13.2 Create ClusterLogForwarder

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle

  - name: default-logstore
```

```bash
oc apply -f clusterlogforwarder.yaml
```

## 14. Complete production-style example: split logs by audience

Scenario:

- Developers need application logs in LokiStack.
- SRE team needs infrastructure logs in Splunk.
- Security team needs audit logs in S3.
- Debug logs should not be sent to Splunk/S3.
- Kubernetes annotations should be pruned before external forwarding.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
  annotations:
    observability.openshift.io/log-level: info
spec:
  serviceAccount:
    name: collector

  inputs:
  - name: prod-apps
    type: application
    application:
      selector:
        matchLabels:
          environment: prod

  filters:
  - name: drop-debug
    type: drop
    drop:
    - test:
      - field: .level
        matches: debug

  - name: prune-external-metadata
    type: prune
    prune:
      in:
      - .kubernetes.annotations
      - .kubernetes.labels

  outputs:
  - name: lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt

  - name: splunk-infra
    type: splunk
    splunk:
      url: https://splunk-hec.example.com:8088
      authentication:
        token:
          secretName: splunk-hec-token
          key: token

  - name: s3-audit
    type: s3
    s3:
      bucket: openshift-audit-archive
      region: ap-south-1
      keyPrefix: prod-cluster/audit/%Y/%m/%d/
      authentication:
        type: accessKey
        accessKey:
          keyId:
            secretName: aws-secret
            key: aws_access_key_id
          keySecret:
            secretName: aws-secret
            key: aws_secret_access_key

  pipelines:
  - name: prod-apps-to-loki
    inputRefs:
    - prod-apps
    filterRefs:
    - drop-debug
    outputRefs:
    - lokistack

  - name: infra-to-splunk
    inputRefs:
    - infrastructure
    filterRefs:
    - drop-debug
    - prune-external-metadata
    outputRefs:
    - splunk-infra

  - name: audit-to-s3
    inputRefs:
    - audit
    filterRefs:
    - prune-external-metadata
    outputRefs:
    - s3-audit
```

Required RBAC for this example:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

## 15. Tuning delivery, durability, and throughput

Large OpenShift clusters can generate huge log volumes. You must tune collection and forwarding deliberately.

### 15.1 Input tuning

Input tuning controls how much data is accepted from containers.

```yaml
inputs:
- name: application-tuned
  type: application
  application:
    tuning:
      container:
        maxMessageSize: 16Ki
        rateLimitPerContainer:
          maxRecordsPerSecond: 1000
```

Important fields:

| Field | Meaning |
|---|---|
| `maxMessageSize` | Maximum merged message size; larger records can be dropped |
| `rateLimitPerContainer.maxRecordsPerSecond` | Per-container record rate limit |

Use cases:

- Prevent one bad pod from overwhelming the collector
- Control runaway debug logging
- Protect log store from high-volume loops

### 15.2 Output tuning

Output tuning controls delivery characteristics.

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    tuning:
      deliveryMode: AtLeastOnce
      compression: gzip
      maxWrite: 3Mi
      minRetryDuration: 2
      maxRetryDuration: 300
```

Key fields:

| Field | Meaning |
|---|---|
| `deliveryMode: AtLeastOnce` | Prioritizes durability; may create duplicate logs after crash/retry |
| `deliveryMode: AtMostOnce` | Prioritizes throughput; logs can be lost during failure |
| `compression` | Compresses data before sending if supported |
| `maxWrite` | Maximum payload size per send |
| `minRetryDuration` | Minimum retry delay after delivery failure |
| `maxRetryDuration` | Maximum retry delay after delivery failure |

### 15.3 Choosing delivery mode

| Requirement | Suggested mode |
|---|---|
| Compliance/audit retention | `AtLeastOnce` |
| Security archive | `AtLeastOnce` |
| Cost-sensitive high-volume debug logs | `AtMostOnce` or aggressive drop/rate limit |
| Developer short-term troubleshooting | Usually default or `AtMostOnce` depending on business criticality |
| Financial/regulated workloads | `AtLeastOnce`, external durable sink, explicit retention policy |

Important: `AtLeastOnce` can duplicate logs after retry. Downstream systems should handle deduplication if exact counting matters.

## 16. Collector resource sizing

You can configure collector CPU and memory through `spec.collector.resources`.

Example patch:

```bash
oc patch clusterlogforwarder instance -n openshift-logging \
  --type=merge \
  -p '{"spec":{"collector":{"resources":{"requests":{"cpu":"100m","memory":"256Mi"},"limits":{"cpu":"500m","memory":"512Mi"}}}}}'
```

Example YAML:

```yaml
spec:
  collector:
    resources:
      requests:
        cpu: 100m
        memory: 256Mi
      limits:
        cpu: 500m
        memory: 512Mi
```

Sizing considerations:

- Number of nodes
- Number of pods per node
- Average log rate per pod
- Peak log bursts during incidents or restarts
- Number of outputs
- Whether multiline detection is enabled
- Whether JSON parsing is enabled
- Whether delivery is durable
- Network latency to external outputs
- TLS overhead
- Compression overhead

Symptoms collector is undersized:

- Collector restarts
- Logs delayed or missing
- CPU throttling
- Memory OOMKilled
- Backpressure errors
- Persistent retry logs
- `429 Too Many Requests` from LokiStack or external sink

## 18. Troubleshooting ClusterLogForwarder

### 18.1 Collector pods missing

Symptom:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
No resources found
```

Likely causes:

- Missing RBAC for referenced log type
- Invalid `ClusterLogForwarder` spec
- Bad output configuration
- Secret missing
- ConfigMap missing
- Operator reconciliation failure

Check:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc describe clusterlogforwarder instance -n openshift-logging

oc get events -n openshift-logging --sort-by=.lastTimestamp
```

Fix:

- If `Authorized=False`, add the missing `collect-*` role.
- If `Valid=False`, read the `message` field and fix YAML.
- If output secret is missing, create the secret in the same namespace as the `ClusterLogForwarder`.

### 18.2 CLF is Ready but logs do not appear in LokiStack

Common cause:

- Missing or wrong `tls.ca` block for LokiStack gateway.

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Look for certificate errors such as:

```text
certificate verify failed: self-signed certificate in certificate chain
```

Fix LokiStack output:

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    authentication:
      token:
        from: serviceAccount
    target:
      name: logging-loki
      namespace: openshift-logging
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

### 18.3 `Authorized=False`

Check:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions[?(@.type=="observability.openshift.io/Authorized")].message}{"\n"}'
```

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \

```

### 18.4 `Valid=False`

Check the validation message:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions[?(@.type=="observability.openshift.io/Valid")].message}{"\n"}'
```

Common validation problems:

- Output referenced in pipeline does not exist
- Filter referenced in pipeline does not exist
- Input referenced in pipeline does not exist
- Wrong field name
- Wrong API version
- Missing required output field
- Invalid port format
- Secret referenced but not found
- Trying to prune required fields

### 18.5 429 Too Many Requests

Symptom:

```text
429 Too Many Requests
```

Likely causes:

- LokiStack cannot ingest as fast as collector sends
- Initial backlog flush
- Sink temporarily unavailable and then restored
- Cluster log rate exceeds LokiStack sizing

Actions:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
oc get lokistack -n openshift-logging
oc describe lokistack logging-loki -n openshift-logging
oc adm top pods -n openshift-logging
```

Fix options:

- Wait for backlog to clear if it is initial deployment.
- Increase LokiStack size if persistently saturated.
- Add input rate limits.
- Drop noisy logs.
- Reduce labels/cardinality.
- Increase collector resources.
- Use external durable storage for high-volume archives.

### 18.6 Output authentication failure

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100 | egrep -i 'auth|401|403|token|denied|forbidden'
```

Common causes:

- Secret in wrong namespace
- Wrong secret key name
- Token expired
- TLS handshake failure
- External endpoint blocks cluster egress
- NetworkPolicy blocks egress
- Proxy required but not configured

## 20. Security best practices

### 20.1 Use least privilege RBAC

Only grant the collector log types it really needs.

Example:

- Application-only forwarding: grant only `collect-application-logs`.
- No audit pipeline: do not grant `collect-audit-logs`.
- Audit enabled: grant `collect-audit-logs` before editing pipeline.

### 20.2 Protect secrets

External outputs often need secrets:

- Splunk HEC token
- Kafka SASL password
- Cloud credentials
- HTTP bearer token
- Elasticsearch basic auth
- Loki tenant token

Best practices:

```bash
oc get secret -n openshift-logging
oc describe secret <name> -n openshift-logging
```

- Keep secrets in the same namespace as the `ClusterLogForwarder`.
- Use sealed secrets, External Secrets Operator, Vault, or cloud secret integration where possible.
- Rotate tokens periodically.
- Avoid embedding credentials directly in YAML.

### 20.3 Encrypt logs in transit

Use TLS for external outputs.

Avoid this in production:

```yaml
tls:
  insecureSkipVerify: true
```

Prefer this:

```yaml
tls:
  ca:
    configMapName: external-ca
    key: ca.crt
```

### 20.4 Prune sensitive metadata

Kubernetes labels and annotations can contain sensitive values.

Example:

```yaml
filters:
- name: prune-sensitive-k8s-fields
  type: prune
  prune:
    in:
    - .kubernetes.annotations
    - .kubernetes.labels
```

### 20.5 Handle audit logs separately

Audit logs should usually go to a controlled destination:

```text
audit -> immutable archive / SIEM / compliance store
```

Do not casually expose audit logs to all developer-facing systems.

## 21. Performance and scale design

### 21.1 Main drivers of log volume

- Number of nodes
- Number of pods
- Application logging verbosity
- Restart loops
- Debug flags left enabled
- Sidecars emitting frequent logs
- Audit policy detail level
- API-heavy controllers
- CI/CD workloads
- Service mesh proxies
- Network observability components

### 21.2 Main drivers of collector CPU/memory

- Multiline exception detection
- JSON parsing
- Regex-heavy drop filters
- Many outputs
- TLS handshakes
- Compression
- Durable delivery
- Very large log messages
- High label cardinality

### 21.3 Reducing storage cost

Use a layered strategy:

```text
1. Fix noisy applications first
2. Apply namespace/container/label input selection
3. Drop low-value records
4. Prune heavy fields
5. Rate-limit abusive containers
6. Send only high-value data to expensive systems
7. Archive compliance logs to cheaper object storage
```

### 21.4 Avoid high-cardinality label design

For Loki and LokiStack, labels are powerful but dangerous.

Avoid using values like these as stream labels:

- request ID
- trace ID
- user ID
- session ID
- pod UID
- exact URL path with IDs
- transaction ID

High cardinality can hurt ingestion, indexing, and query performance.

Good labels:

- namespace
- app
- environment
- cluster
- log type
- team

### 23.1 Basic developer logging

Use when:

- Regulations restrict data movement.
- PII must not leave a boundary.

## 25. Exam and interview explanation

### Simple definition

`ClusterLogForwarder` is an OpenShift Logging custom resource used to configure log collection and forwarding. It defines input sources, optional filters, output destinations, and pipelines that connect them.

### Advanced definition

`ClusterLogForwarder` is the policy layer for OpenShift log routing. The Logging Operator reads the CR, creates or updates the collector configuration, and deploys collector pods that collect application, infrastructure, audit, or receiver logs. The CR can filter, parse, prune, label, rate-limit, tune delivery, and forward log streams to one or more destinations such as LokiStack, Splunk, Kafka, Elasticsearch, HTTP, syslog, S3, CloudWatch, or OTLP.

### 30-second interview answer

In OpenShift Logging, `ClusterLogForwarder` controls how logs move through the platform. It defines inputs such as application, infrastructure, and audit logs; filters such as drop, prune, parse, multiline, or audit filters; outputs such as LokiStack, Splunk, Kafka, Elasticsearch, HTTP, syslog, S3, CloudWatch, or OTLP; and pipelines that bind all of them together. In Logging 6.x it uses `observability.openshift.io/v1`. The collector service account must have explicit RBAC like `collect-application-logs`, `collect-infrastructure-logs`, or `collect-audit-logs`, otherwise the collector can be removed and log collection stops. Day-2 checks include `status.conditions`, collector pod health, output connectivity, TLS CA configuration, and collector logs.

## 27. Common mistakes and fixes

| Mistake | Impact | Fix |
|---|---|---|
| Using old `logging.openshift.io/v1` YAML on Logging 6.x | CR rejected or wrong behavior | Use `observability.openshift.io/v1` |
| Referencing `audit` without RBAC | Collector DaemonSet removed / no log collection | Add `collect-audit-logs` first |
| Missing LokiStack TLS CA block | CLF may show Ready but no logs reach LokiStack | Add `tls.ca.configMapName` and `key` |
| Secret in wrong namespace | Output auth fails | Put secret in same namespace as CLF |
| Output name typo in pipeline | `Valid=False` | Match `outputRefs` to `outputs[].name` |
| Filter name typo in pipeline | `Valid=False` | Match `filterRefs` to `filters[].name` |
| Too many labels in Loki | Slow queries and high ingestion cost | Reduce label cardinality |
| Enabling multiline globally without sizing | High CPU/memory | Enable selectively and increase resources |
| Leaving debug collector logging enabled | More noise and overhead | Reset log level to `info` |
| No pipeline for a log type | Logs dropped/not collected | Add pipeline referencing that input |

```text
  bind inputs + filters + outputs
```

For advanced administration, the key is not only creating YAML. The key is designing a reliable, secure, cost-aware log routing architecture.

A strong production design answers:

- Who needs the logs?
- Which logs are required?
- Which logs are too noisy?
- Which logs are sensitive?
- Which destination is authoritative?
- What retention is needed?
- What happens when the destination is down?
- How much log loss is acceptable?
- How do we prove forwarding is healthy?
- How do we avoid breaking the collector with bad RBAC or invalid specs?

If you can answer those questions and express them cleanly in `ClusterLogForwarder`, you can manage OpenShift Logging at an advanced enterprise level.
