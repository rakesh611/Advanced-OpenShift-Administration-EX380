# Diagnosing Logging Pipeline Issues in OpenShift Logging

**Audience:** Advanced OpenShift administrators, OpenShift SREs, platform engineers, and L3 support engineers with production responsibility.  
**Context:** Red Hat OpenShift Logging 6.x style architecture using `ClusterLogForwarder` API `observability.openshift.io/v1`, Vector collector, LokiStack, and optional external outputs such as Splunk, Kafka, Elasticsearch, HTTP, CloudWatch, S3, Syslog, and OTLP.

---

## 1. What “logging pipeline issue” means

A logging pipeline issue means logs are generated by workloads or OpenShift components, but they do not reliably reach the expected destination, are delayed, duplicated, malformed, dropped, or cannot be queried by the intended users.

A complete OpenShift logging path normally looks like this:

```text
Application / node / audit log source
        |
        v
Node log files or receiver input
        |
        v
Vector collector pod managed by OpenShift Logging Operator
        |
        v
ClusterLogForwarder inputs -> filters -> pipelines -> outputs
        |
        v
LokiStack gateway / external sink / SIEM / Kafka / Splunk / HTTP endpoint
        |
        v
Query layer: OpenShift Observe -> Logs, LogQL, external tool, or downstream SIEM
```

When troubleshooting, do not start by changing configuration. First identify the failing stage.

Typical symptoms:

| Symptom | Likely failing area |
|---|---|
| No collector pods | `ClusterLogForwarder` authorization or validation issue |
| Collector pods running but no logs in Loki | Output TLS, Loki gateway, RBAC, tenant, Loki ingestion, or pipeline mismatch |
| Application logs missing only for one namespace | input selectors, namespace exclusion, RBAC, workload not writing to stdout/stderr |
| Infrastructure logs missing | missing `collect-infrastructure-logs` role, wrong inputRefs, node/journal collection issue |
| Audit logs missing | missing `collect-audit-logs`, audit input not configured, audit logs not stored by default |
| Logs delayed | destination throttling, Loki rate limit, collector backlog, resource pressure, object storage latency |
| `429 Too Many Requests` | Loki ingestion limit or temporary backlog flush |
| `certificate verify failed` | missing or wrong `tls.ca` block in output configuration |
| Logs visible for admin but not developer | LokiStack tenancy/RBAC/UI plugin/query schema issue |
| Logs forwarded to external sink but not local Loki | pipeline outputRefs, multi-output split, destination-specific failures |
| Query times out | poor labels, large time range, regex-heavy LogQL, slow object storage, undersized LokiStack |

## 2. Modern OpenShift Logging architecture you must understand

### 2.1 Main components

In current Red Hat OpenShift Logging 6.x deployments, focus on these resources:

| Component | Purpose | Namespace commonly used |
|---|---|---|
| Red Hat OpenShift Logging Operator | Manages collector and forwarding resources | `openshift-logging` |
| Loki Operator | Manages `LokiStack` | `openshift-logging` or operator namespace depending installation |
| `ClusterLogForwarder` | Defines what logs are collected, filtered, and forwarded | often `openshift-logging`, but multiple CLFs are supported |
| Vector collector | Tails logs and forwards to outputs | runs as collector pods, usually daemonset style |
| `LokiStack` | Short-term in-cluster log store | usually `openshift-logging` |
| Cluster Observability Operator + `UIPlugin` | Enables Observe -> Logs UI | `openshift-operators` / cluster-scoped UI plugin |
| `LogFileMetricExporter` | Exposes produced-log metrics | `openshift-logging` |

The important change from older OpenShift Logging versions is that you should not troubleshoot only the legacy `ClusterLogging` object. In Logging 6.x, the operational center is usually:

```bash
oc get clusterlogforwarder.observability.openshift.io -A
oc get lokistack.loki.grafana.com -A
oc get pods -n openshift-logging
```

### 2.2 Pipeline model

A `ClusterLogForwarder` has four logical blocks:

```text
inputs  ->  filters  ->  pipelines  ->  outputs
```

- **Inputs** select log sources such as `application`, `infrastructure`, `audit`, or custom receiver inputs.
- **Filters** drop, prune, transform, parse, or detect multiline exceptions.
- **Pipelines** connect inputRefs, optional filterRefs, and outputRefs.
- **Outputs** define destinations such as `lokiStack`, `loki`, `splunk`, `kafka`, `http`, `syslog`, `elasticsearch`, `cloudwatch`, `s3`, or `otlp`.

A pipeline issue is usually one of these:

1. The input does not select the log stream.
2. The collector service account is not authorized for the selected input.
3. A filter drops or changes records unexpectedly.
4. The output cannot be reached or authenticated.
5. Loki or the external sink accepts the connection but throttles, rejects, or silently stores data in a different tenant/index/topic.
6. Logs are stored correctly but the query/UI/RBAC path hides them.

## 3. Golden troubleshooting rule: prove each hop

Use this sequence every time:

```text
1. Is the source producing logs?
2. Is the collector deployed on the node where the source runs?
3. Is the ClusterLogForwarder valid and authorized?
4. Does the pipeline select this source?
5. Is the output reachable and trusted?
6. Is the destination accepting ingestion?
7. Are logs queryable with the right tenant, labels, time range, and permissions?
8. Is there backlog, rate limiting, or query-performance issue?
```

Do not jump directly to Loki or Splunk. Many issues are caused earlier by missing RBAC, invalid CLF status, selectors, TLS CA blocks, or filters.

```json
  }
]
```

## 5. Diagnosing `ClusterLogForwarder` status

### 5.1 `Authorized=False`

This means the collector service account does not have the required `ClusterRoleBinding` for one or more log types referenced by `inputRefs`.

Common required roles:

| Required log type | Required role |
|---|---|
| application logs | `collect-application-logs` |
| infrastructure logs | `collect-infrastructure-logs` |
| audit logs | `collect-audit-logs` |
| write to LokiStack | `logging-collector-logs-writer` |

Check service account:

```bash
oc get sa $SA -n $NS
```

Check ClusterRoleBindings for that service account:

```bash
oc get clusterrolebinding -o json | jq -r \
'.items[] |
 select(.subjects[]? | .kind=="ServiceAccount" and .name=="'"$SA"'" and .namespace=="'"$NS"'") |
 [.metadata.name, .roleRef.name] | @tsv'
```

Fix missing application, infrastructure, and Loki writer roles:

```bash
oc adm policy add-cluster-role-to-user logging-collector-logs-writer \
  system:serviceaccount:$NS:$SA

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:$NS:$SA

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:$NS:$SA
```

If collecting audit logs:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:$NS:$SA
```

Important production warning: if you add `audit` to `inputRefs` before granting `collect-audit-logs`, the Operator can remove the entire collector DaemonSet. That causes all log collection to stop until RBAC is corrected.

### 5.2 `Valid=False`

This means the CLF schema or semantic configuration is invalid.

Check detailed message:

```bash
oc get clf $CLF -n $NS -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{"  "}{.message}{"\n"}{end}'
```

Common causes:

- `inputRefs` references an input name that does not exist.
- `outputRefs` references an output name that does not exist.
- wrong `apiVersion` or old CR syntax copied from Logging 5.x examples.
- output type-specific required fields missing.
- invalid secret/configMap reference.
- wrong namespace for the service account.
- filter referenced in pipeline but not defined.

### 5.3 `Ready=True` but no logs

This is a common trap. `Ready=True` means the Operator reconciled the object and can deploy resources. It does not guarantee that the collector can successfully deliver logs to the destination.

Immediately check collector logs:

```bash
oc logs -n $NS -l app.kubernetes.io/component=collector --tail=200 | egrep -i \
'error|warn|certificate|tls|denied|unauthorized|forbidden|429|retry|failed|timeout|connection|backoff'
```

Most common reasons:

- missing `tls.ca` for LokiStack gateway.
- LokiStack gateway unavailable.
- external endpoint DNS/network blocked.
- invalid token/secret.
- destination accepts connection but rejects payload.
- selector/filter excludes logs.
- query uses wrong labels or time range.

## 6. Diagnosing collector pod issues

### 6.1 No collector pod exists

Command:

```bash
oc get pods -n $NS -l app.kubernetes.io/component=collector
```

Output:

```text
No resources found in openshift-logging namespace.
```

Likely causes:

1. `ClusterLogForwarder` is unauthorized.
2. `ClusterLogForwarder` is invalid.
3. Logging Operator reconciliation failed.
4. Wrong namespace/name when multiple CLFs exist.

Troubleshoot:

```bash
oc get clf -A
oc get clf $CLF -n $NS -o jsonpath='{.status.conditions}' | python3 -m json.tool
oc describe clf $CLF -n $NS
oc logs -n $NS deployment/cluster-logging-operator --tail=200
oc get events -n $NS --sort-by=.lastTimestamp | tail -80
```

Fix RBAC or validation first. After correction, the Operator should recreate the collector DaemonSet automatically.

### 6.2 Collector pods pending

Check scheduling:

```bash
oc get pods -n $NS -l app.kubernetes.io/component=collector -o wide
oc describe pod -n $NS <collector-pod>
```

Common causes:

- taints not tolerated.
- insufficient CPU/memory on nodes.
- node selector does not match.
- image pull failure.
- SCC/security context issue.
- namespace quota blocks pod creation.

Commands:

```bash
oc adm top node
oc get nodes --show-labels
oc describe node <node>
oc get quota -n $NS
oc get limitrange -n $NS
```

### 6.3 Collector pods crash or restart

```bash
oc get pods -n $NS -l app.kubernetes.io/component=collector
oc describe pod -n $NS <collector-pod>
oc logs -n $NS <collector-pod> --previous
oc logs -n $NS <collector-pod> --tail=200
```

Look for:

- OOMKilled.
- config parse error.
- TLS/certificate error.
- output authentication error.
- disk read permission error.
- panic/bug after upgrade.
- unsupported modification of collector DaemonSet or collector config.

For resource pressure, tune collector resources in CLF rather than directly editing the DaemonSet:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    resources:
      requests:
        cpu: 200m
        memory: 736Mi
      limits:
        cpu: 1000m
        memory: 1Gi
```

Do not manually edit the generated collector DaemonSet in production. The Operator will reconcile it back, and unsupported changes complicate upgrades and support.

## 7. Diagnosing source-side issues

Before blaming logging, prove that the source actually produces logs.

### 7.1 Application workload logs

```bash
APP_NS=myapp
POD=$(oc get pod -n $APP_NS -o jsonpath='{.items[0].metadata.name}')
oc logs -n $APP_NS $POD --tail=50
oc logs -n $APP_NS $POD --all-containers --tail=50
```

If `oc logs` shows nothing, OpenShift Logging cannot collect what the container does not write to stdout/stderr.

Check container logging pattern:

- application logs to stdout/stderr: good.
- application writes only to `/var/log/app.log` inside container: not collected unless sidecar or app redirects to stdout.
- multiline stack traces: may need multiline exception detection.
- high-cardinality JSON payloads: may need pruning/filtering before Loki.

### 7.2 Infrastructure logs

Infrastructure logs generally include OpenShift and Kubernetes platform namespace logs and node/service logs selected by the infrastructure input.

Check CLF inputRefs:

```bash
oc get clf $CLF -n $NS -o jsonpath='{.spec.pipelines[*].inputRefs}'
```

Check service account has infrastructure role:

```bash
oc get clusterrolebinding -o json | jq -r \
'.items[] |
 select(.roleRef.name=="collect-infrastructure-logs") |
 .metadata.name'
```

### 7.3 Audit logs

Audit logs are sensitive and not stored by default. You must explicitly configure forwarding and grant audit collection permission.

Correct sequence:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:$NS:$SA

oc edit clf $CLF -n $NS
# add audit to inputRefs only after RBAC exists
```

Example pipeline including audit:

```yaml
spec:
  pipelines:
  - name: all-to-loki
    inputRefs:
    - application
    - infrastructure
    - audit
    outputRefs:
    - lokistack-out
```

If audit was added first and collectors disappeared, remove `audit` from `inputRefs` or add the missing RBAC, then wait for reconciliation.

## 8. Diagnosing input selector mistakes

Inputs can include or exclude namespaces, containers, labels, infrastructure sources, and audit sources. Selector bugs are common because the pipeline looks healthy but intentionally selects zero records.

Check inputs:

```bash
oc get clf $CLF -n $NS -o jsonpath='{.spec.inputs}' | python3 -m json.tool
```

Common mistakes:

- namespace name typo.
- `includes` and `excludes` conflict.
- label selector does not match pods.
- selecting pods by deployment label that changed during rollout.
- excluding `openshift-*` namespaces unintentionally.
- selecting only one container in a multi-container pod.

Validate labels:

```bash
oc get ns --show-labels | grep <namespace>
oc get pods -n <namespace> --show-labels
oc get pod -n <namespace> <pod> -o jsonpath='{.metadata.labels}' | python3 -m json.tool
```

Example targeted application input:

```yaml
spec:
  inputs:
  - name: frontend-prod
    type: application
    application:
      includes:
      - namespace: prod-frontend
        container: app
      selector:
        matchLabels:
          app: frontend
  pipelines:
  - name: frontend-to-loki
    inputRefs:
    - frontend-prod
    outputRefs:
    - lokistack-out
```

Diagnostic test: temporarily create a broader input in a non-production CLF or staging cluster to confirm whether the issue is selector-related. In production, avoid broadening audit or high-volume namespace collection without capacity review.

## 9. Diagnosing filter issues

Filters are powerful but can silently remove or reshape records.

Check filters and pipeline references:

```bash
oc get clf $CLF -n $NS -o jsonpath='{.spec.filters}' | python3 -m json.tool
oc get clf $CLF -n $NS -o jsonpath='{.spec.pipelines}' | python3 -m json.tool
```

Typical filter problems:

| Filter behavior | Risk |
|---|---|
| drop filter | Records disappear by design |
| prune filter | Required Loki labels/fields removed |
| multiline exception detection | Higher CPU/memory and changed event boundaries |
| JSON parsing/transform | Malformed payloads produce unexpected fields |
| audit reduction | Security team expects full audit but only summary is forwarded |

For LokiStack, do not prune required stream labels. Required labels commonly include namespace, pod, and container identity. Removing required metadata can break ingestion, tenancy, or queryability.

### 9.1 Multiline exception detection

Multiline detection joins stack traces into a single log record. It is useful for Java, Python, Go, Ruby, PHP, JS, Dart, etc., but it can increase CPU and memory usage.

Example:

```yaml
spec:
  filters:
  - name: detect-exceptions
    type: detectMultilineException
  pipelines:
  - name: apps-to-loki
    inputRefs:
    - application
    filterRefs:
    - detect-exceptions
    outputRefs:
    - lokistack-out
```

If collector CPU spikes after enabling it, either increase collector resources, narrow the input scope, or remove the filter for high-volume namespaces.

## 10. Diagnosing output issues

### 10.1 LokiStack output

A common LokiStack output looks like this:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: lokistack-out
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: infra-app-logs
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - lokistack-out
```

Critical checks:

```bash
oc get lokistack logging-loki -n openshift-logging
oc get cm -n openshift-logging logging-loki-gateway-ca-bundle -o yaml
oc get svc -n openshift-logging | grep -i loki
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 | grep -i certificate
```

If you see:

```text
certificate verify failed: self-signed certificate in certificate chain
```

Fix `spec.outputs[].tls.ca`. The collector may not trust the LokiStack gateway certificate unless the CA bundle is explicitly referenced.

### 10.2 External HTTP/Splunk/Elasticsearch/Kafka/Syslog output

For external destinations, isolate four layers:

```text
DNS -> network path -> TLS trust/authentication -> destination protocol acceptance
```

Run a temporary debug pod from a namespace that has similar network restrictions:

```bash
oc -n openshift-logging run net-debug --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside the pod:

```bash
curl -vk https://splunk.example.com:8088/services/collector/health
curl -vk https://elastic.example.com:9200/
getent hosts kafka.example.com
```

If tools are missing, install only in disposable debug pods where allowed:

```bash
dnf -y install bind-utils nc openssl
```

TLS checks:

```bash
openssl s_client -connect splunk.example.com:8088 -showcerts </dev/null
```

Authentication checks:

- verify secret name and key names.
- verify token has not expired or rotated.
- verify Splunk HEC token is enabled and assigned to correct index.
- verify Kafka SASL/SSL mechanism and CA/client certs.
- verify Elasticsearch version and index pattern.
- verify external firewall allows worker node egress.

### 10.3 Multiple outputs

A pipeline can duplicate records to multiple outputs:

```yaml
pipelines:
- name: app-to-local-and-siem
  inputRefs:
  - application
  outputRefs:
  - lokistack-out
  - splunk-prod
```

If one output fails, inspect whether the collector retries that output while still delivering to others. A failing slow output can increase memory/backpressure depending buffering and tuning.

## 11. Diagnosing LokiStack issues

### 11.1 Loki pod health

```bash
oc get pods -n openshift-logging | grep loki
oc get lokistack logging-loki -n openshift-logging -o yaml
oc describe lokistack logging-loki -n openshift-logging
```

Check individual component logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=gateway --tail=100
oc logs -n openshift-logging -l app.kubernetes.io/component=distributor --tail=100
oc logs -n openshift-logging -l app.kubernetes.io/component=ingester --tail=100
oc logs -n openshift-logging -l app.kubernetes.io/component=querier --tail=100
oc logs -n openshift-logging -l app.kubernetes.io/component=query-frontend --tail=100
oc logs -n openshift-logging -l app.kubernetes.io/component=compactor --tail=100
```

Labels can vary by version. If these selectors return nothing, list labels:

```bash
oc get pods -n openshift-logging --show-labels | grep loki
```

### 11.2 Loki ingestion errors

Search collector and Loki logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=500 | egrep -i '429|rate|limit|retry|loki|push|error'
oc logs -n openshift-logging -l app.kubernetes.io/component=ingester --tail=500 | egrep -i '429|rate|limit|error|reject'
oc logs -n openshift-logging -l app.kubernetes.io/component=distributor --tail=500 | egrep -i '429|rate|limit|error|reject'
```

### 11.3 `429 Too Many Requests`

This happens when ingestion exceeds Loki limits. It can be normal during first deployment or after connectivity is restored, because collectors flush a backlog.

If it clears after a few minutes, no action may be needed.

If it persists:

1. Identify noisy namespaces/pods.
2. Add filtering or reduce log verbosity.
3. Increase LokiStack capacity/sizing.
4. Adjust ingestion limits carefully.

Example LokiStack limit tuning:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  limits:
    global:
      ingestion:
        ingestionBurstSize: 16
        ingestionRate: 8
```

Guidance:

- `ingestionBurstSize` is a hard burst size limit in MB per distributor replica.
- `ingestionRate` is a softer MB/sec limit.
- Increasing limits without object storage and CPU capacity can move the bottleneck elsewhere.
- Long-term fix is often reducing noisy logs or sizing Loki correctly.

### 11.4 Object storage issues

Loki depends heavily on object storage. If object storage is slow or unavailable, ingestion and query performance can degrade.

Check object storage secret and Loki conditions:

```bash
oc get secret -n openshift-logging
oc describe lokistack logging-loki -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp | grep -i loki
```

Symptoms:

- ingester/distributor errors.
- compactor errors.
- query timeouts.
- high latency in Loki metrics.
- object store 403/AccessDenied.
- DNS/connectivity failure to S3-compatible endpoint.

For S3-compatible stores, verify:

- endpoint URL.
- bucket exists.
- region/signature settings.
- access key/secret key.
- TLS CA trust.
- required object storage permissions.

## 12. Diagnosing query and UI issues

Sometimes logs are ingested correctly but users cannot see them.

### 12.1 No Observe -> Logs tab

Check Cluster Observability Operator and UIPlugin:

```bash
oc get csv -A | grep -i observability
oc get uiplugin.observability.openshift.io logging -o yaml
```

A `UIPlugin` similar to this enables the Logs UI:

```yaml
apiVersion: observability.openshift.io/v1alpha1
kind: UIPlugin
metadata:
  name: logging
spec:
  type: Logging
  logging:
    lokiStack:
      name: logging-loki
    logsLimit: 50
    timeout: 30s
    schema: otel
```

If the UI tab is missing, the pipeline may still be working. Query via CLI/API or inspect Loki/collector logs before assuming ingestion failure.

### 12.2 Admin sees logs, developer does not

Likely RBAC/tenancy issue.

Check user permissions:

```bash
oc auth can-i get pods/log -n <app-namespace> --as=<user>
oc auth can-i view -n <app-namespace> --as=<user>
oc auth can-i get pods -n <app-namespace> --as=<user>
```

For LokiStack tenancy, users generally see logs based on namespace access. Grant the correct namespace role instead of giving broad cluster-admin:

```bash
oc adm policy add-role-to-user view <user> -n <app-namespace>
```

### 12.3 Wrong query labels

Depending on data model and version, label names may differ. In newer OpenTelemetry-oriented paths, attributes such as `k8s.namespace.name` can be persisted with transformed names like `k8s_namespace_name`.

Start with broad queries:

```logql
{log_type="application"}
{log_type="infrastructure"}
```

Then narrow:

```logql
{kubernetes_namespace_name="myapp"}
{k8s_namespace_name="myapp"}
{log_type="application"} |= "error"
```

If a query times out, reduce time range first. Then remove regex and high-cardinality filters.

## 13. Diagnosing query performance issues

Loki is optimized for recent, label-based log retrieval. It is not a full-text indexed Elasticsearch replacement. Poor query patterns can make healthy systems look broken.

Better query approach:

```text
Good:  select labels first -> narrow time -> simple string filter
Bad:   huge time range -> regex across all logs -> no namespace/app label
```

Examples:

```logql
# Better
{kubernetes_namespace_name="payments", kubernetes_pod_name=~"api-.*"} |= "timeout"

# Expensive
{log_type="application"} |~ ".*timeout.*exception.*failed.*"
```

Check Loki query logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=query-frontend --tail=200 | grep metrics.go
oc logs -n openshift-logging -l app.kubernetes.io/component=querier --tail=200 | grep metrics.go
```

Improve performance:

- Use latest compatible Loki Operator.
- Use recommended LokiStack schema version.
- Use fast, reliable object storage.
- Prefer simple filters over regex.
- Avoid high-cardinality labels.
- Use labels that describe long-lived infrastructure, apps, namespaces, clusters, and environments.
- Reduce query time range.
- Increase LokiStack size only after proving resource saturation.

## 14. NetworkPolicy and AdminNetworkPolicy issues

Restrictive network policies can block collector-to-Loki or collector-to-external-sink traffic.

Check policies:

```bash
oc get networkpolicy -A | egrep 'logging|loki|collector|default-deny'
oc get adminnetworkpolicy 2>/dev/null || true
oc get egressfirewall -A 2>/dev/null || true
```

Collector needs egress to:

- LokiStack gateway service, if using in-cluster Loki.
- external outputs, if forwarding out of cluster.
- Kubernetes API where required.
- DNS.

Debug from a pod:

```bash
oc -n openshift-logging run net-debug --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside:

```bash
getent hosts logging-loki-gateway-http.openshift-logging.svc
curl -vk https://logging-loki-gateway-http.openshift-logging.svc:8080/
```

If your cluster uses default-deny or AdminNetworkPolicy, configure allowed ingress/egress via supported CLF network policy rule sets or platform network policy rules rather than manually patching generated resources.

## 15. Resource pressure and noisy workloads

Logging failures often start as capacity issues.

Check collector resource pressure:

```bash
oc adm top pods -n openshift-logging
oc describe pod -n openshift-logging <collector-pod> | egrep -i 'oom|killed|evict|memory|cpu|warning'
```

Find noisy pods by produced logs metrics if LogFileMetricExporter is enabled:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=logfilesmetricexporter
```

PromQL examples may vary by version, but useful patterns include checking produced bytes/lines by namespace, pod, or container in the OpenShift Metrics UI.

Operational fixes:

- reduce application log level from debug to info/warn.
- avoid printing huge JSON payloads, secrets, stack traces in loops, or health-check logs.
- add CLF input selectors to avoid unnecessary namespaces.
- use filters to drop known-noisy messages.
- scale/sizing LokiStack and object storage appropriately.
- separate audit/security retention to external durable store.

## 16. External destination troubleshooting matrix

| Output | Check first | Common error | Fix |
|---|---|---|---|
| Splunk HEC | URL, token, index | 401/403, index not found | rotate token, enable HEC, correct index |
| Kafka | broker DNS, topic, SASL/TLS | connection refused, auth failed | fix brokers, CA, SASL mechanism, topic ACL |
| Elasticsearch | version, URL, credentials | 401, mapping/index failure | correct version, index pattern, auth |
| HTTP | method, headers, TLS | 4xx/5xx | validate endpoint accepts JSON/NDJSON |
| Syslog | protocol/port, firewall | dropped UDP/no ACK | prefer TCP/TLS, verify rsyslog listener |
| S3 | bucket, IAM, endpoint | AccessDenied/NoSuchBucket | fix policy, region, endpoint, secret |
| OTLP | endpoint path/protocol | 404/415/unimplemented | verify OTLP HTTP/gRPC and schema |
| External Loki | tenant/labels/TLS | 401/429 | tenant header, limits, CA, auth |

```bash
oc logs -n $NS -l app.kubernetes.io/component=collector --tail=1000 | egrep -i \
```

## 18. Advanced diagnostic workflow by symptom

### 18.1 Symptom: “No logs from any namespace”

Run:

```bash
oc get clf -A
oc get clf $CLF -n $NS -o jsonpath='{.status.conditions}' | python3 -m json.tool
oc get pods -n $NS -l app.kubernetes.io/component=collector
oc logs -n $NS -l app.kubernetes.io/component=collector --tail=200
oc get lokistack -A
oc get pods -n $NS | grep loki
```

Likely fixes:

- grant missing collector RBAC.
- fix invalid CLF.
- restore collector DaemonSet by correcting `Authorized`/`Valid`.
- add LokiStack TLS CA block.
- fix Loki gateway/object storage.

### 18.2 Symptom: “Only audit logs missing”

Run:

```bash
oc get clf $CLF -n $NS -o yaml | grep -n audit -C 5
oc get clusterrolebinding -o json | jq -r '.items[] | select(.roleRef.name=="collect-audit-logs") | .metadata.name'
oc get clf $CLF -n $NS -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Likely fixes:

- grant `collect-audit-logs` before adding `audit` input.
- confirm pipeline includes `audit`.
- send audit to durable external store if retention/compliance is required.

### 18.3 Symptom: “CLF Ready True but Loki empty”

Run:

```bash
oc logs -n $NS -l app.kubernetes.io/component=collector --tail=500 | egrep -i 'certificate|tls|loki|429|error|retry|failed'
oc get cm -n $NS | grep gateway-ca
oc get clf $CLF -n $NS -o yaml | grep -n 'tls:' -A8
```

Likely fixes:

- add correct `tls.ca`.
- fix Loki target name/namespace.
- fix service account token auth.
- check LokiStack gateway and distributor/ingester logs.

### 18.4 Symptom: “Only some app namespaces missing”

Run:

```bash
oc logs -n <app-ns> <pod> --tail=50
oc get pods -n <app-ns> --show-labels
oc get clf $CLF -n $NS -o yaml | sed -n '/inputs:/,/outputs:/p'
```

Likely fixes:

- correct namespace/container/label selector.
- remove conflicting excludes.
- verify app writes to stdout/stderr.
- verify user query uses correct namespace label.

### 18.5 Symptom: “Logs are delayed”

Run:

```bash
oc logs -n $NS -l app.kubernetes.io/component=collector --tail=500 | egrep -i '429|retry|backoff|buffer|timeout'
oc adm top pods -n $NS
oc get events -n $NS --sort-by=.lastTimestamp | tail -50
```

Likely fixes:

- wait for initial backlog if temporary.
- reduce noisy logs.
- tune Loki ingestion limits with capacity review.
- increase collector resources.
- check object storage latency.
- check external sink response time.

### 18.6 Symptom: “Queries are slow or timeout”

Run:

```bash
oc logs -n $NS -l app.kubernetes.io/component=query-frontend --tail=200 | grep metrics.go
oc logs -n $NS -l app.kubernetes.io/component=querier --tail=200 | grep metrics.go
```

Likely fixes:

- reduce time range.
- filter by namespace/app labels first.
- avoid heavy regex.
- improve object storage.
- review LokiStack sizing/schema.
- avoid high-cardinality labels.

## 19. Production-safe remediation principles

1. **Fix declarative resources, not generated pods.** Edit `ClusterLogForwarder`, `LokiStack`, `UIPlugin`, or supported CRs. Do not patch generated collector DaemonSets directly.
2. **Treat audit logs carefully.** They are sensitive and not stored by default; forward to compliant external storage if required.
3. **Do not increase Loki limits blindly.** Prove whether the problem is burst, sustained throughput, object storage, or noisy apps.
4. **Keep pipeline small and intentional.** Each extra output doubles delivery work for matching records.
5. **Use narrow inputs for expensive destinations.** Send all logs to local Loki only when capacity allows; send only required logs to SIEM.
6. **Document tenant and access model.** Many “missing logs” incidents are actually user RBAC or query schema issues.
7. **Capture evidence before changes.** Save CLF YAML, collector logs, Loki conditions, and events before modifying production.

## 21. Interview and real-world explanation

When asked “How do you diagnose OpenShift logging pipeline issues?”, answer like this:

> I troubleshoot the pipeline hop by hop. First I verify the source produces logs with `oc logs`. Then I check the `ClusterLogForwarder` conditions: `Authorized`, `Valid`, and `Ready`. If `Authorized` is false, I fix the collector service account ClusterRoleBindings. If `Valid` is false, I fix the CLF schema or references. Then I verify collector pods are running on nodes and inspect Vector collector logs for TLS, authentication, network, 429, or retry errors. For LokiStack, I check gateway, distributor, ingester, object storage, and rate-limit conditions. If ingestion is healthy but users cannot see logs, I check UIPlugin, RBAC/tenancy, label schema, and query time range. I avoid manually editing generated DaemonSets and make changes only through supported CRs such as ClusterLogForwarder and LokiStack.

## 22. Hands-on lab scenario

### Scenario

Developers report that logs for namespace `payments-prod` are missing from Observe -> Logs. Infrastructure logs are visible. The CLF shows `Ready=True`.

### Diagnosis

1. Confirm source:

```bash
oc logs -n payments-prod deploy/payments-api --tail=20
```

2. Check CLF status:

```bash
oc get clf instance -n openshift-logging -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

3. Check inputs:

```bash
oc get clf instance -n openshift-logging -o yaml | sed -n '/inputs:/,/outputs:/p'
```

4. Check labels:

```bash
oc get pods -n payments-prod --show-labels
```

5. Check collector errors:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m | egrep -i 'payments|error|drop|retry|failed'
```

### Finding

The CLF input has:

```yaml
selector:
  matchLabels:
    app: payment-api
```

But pods have:

```text
app=payments-api
```

### Fix

Update selector:

```yaml
selector:
  matchLabels:
    app: payments-api
```

Apply and verify:

```bash
oc apply -f clf.yaml
oc get clf instance -n openshift-logging -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Run LogQL:

```logql
{log_type="application"} |= "payments"
```

## 24. Final mental model

For a senior OpenShift administrator, logging troubleshooting is not “check Loki only.” It is a pipeline investigation:

```text
source -> collector scheduling -> collector RBAC -> CLF validity -> filter behavior -> output connectivity -> destination ingestion -> query/RBAC/UI
```

Most real incidents fall into five buckets:

1. **Authorization failure:** CLF references logs the service account cannot collect.
2. **Validation/config failure:** input/output/filter references are wrong.
3. **TLS/network failure:** collector cannot reach or trust destination.
4. **Capacity/rate failure:** destination throttles or object storage is slow.
5. **Query/access failure:** logs exist, but the user, labels, schema, or time range hides them.

If you follow this order and collect evidence at each hop, you can diagnose OpenShift Logging pipeline failures quickly without random restarts or unsupported manual patches.
