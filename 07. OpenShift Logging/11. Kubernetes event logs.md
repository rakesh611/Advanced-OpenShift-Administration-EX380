**Focus:** Kubernetes Events as operational logs inside Red Hat OpenShift Logging  
**Level:** 10+ years Linux / DevOps / OpenShift administration  
**File:** Single Markdown study and operations guide

---

## 1. Executive Summary

In OpenShift, **Kubernetes Events** are not the same thing as application logs, infrastructure logs, or audit logs. Events are Kubernetes API objects that describe significant state changes or failures inside the cluster, such as image pull failures, scheduling failures, failed mounts, probe failures, pod sandbox creation errors, node pressure, operator reconciliation problems, and workload lifecycle transitions.

For day-to-day troubleshooting, events are usually viewed with:

```bash
oc get events -A --sort-by='.lastTimestamp'
oc describe pod <pod-name> -n <namespace>
oc get events -n <namespace> --field-selector type=Warning
```

However, native Kubernetes Events are **short-lived**. They are stored in the Kubernetes API server backing store and are purged based on event TTL. In OpenShift, this retention is controlled through the `KubeAPIServer` custom resource using `spec.eventTTLMinutes`, with valid values documented as `5` to `180` minutes in current Red Hat documentation.

In OpenShift Logging, events become searchable as logs only when they are exported or converted into log records. Historically, Red Hat documented the **Event Router** pattern: a pod watches Kubernetes Events from all projects and writes them to `STDOUT`; the OpenShift Logging collector then collects the Event Router pod logs and forwards them to the configured logging backend. In modern OpenShift Logging 6.x, the central object is `ClusterLogForwarder`, which selects log inputs such as `application`, `infrastructure`, `audit`, and receiver-based inputs, and sends them to outputs such as LokiStack, Splunk, Kafka, syslog, Elasticsearch, HTTP, OTLP, and cloud logging services.

For production administration, treat Kubernetes Events as **high-signal but best-effort operational evidence**. They are excellent for troubleshooting, incident reconstruction, and detecting cluster behavior, but they are not a replacement for audit logs, metrics, application logs, or compliance-grade evidence.

## 2. What Are Kubernetes Events?

A Kubernetes Event is a report of something that happened somewhere in the cluster. It usually represents a change, warning, or operational action related to another Kubernetes object.

Examples:

- A pod could not be scheduled.
- A container image could not be pulled.
- A volume could not be mounted.
- A liveness probe failed.
- A pod was killed due to memory pressure.
- A node became unreachable.
- A controller created or deleted a replica.
- An operator reconciled or failed to reconcile a resource.

Kubernetes Events are API resources. They are stored and retrieved through the Kubernetes API, not from `/var/log/containers` directly.

### 2.1 Event vs log

| Item | Kubernetes Event | Container / Application Log | Audit Log | Metric |
|---|---|---|---|---|
| Primary purpose | Describe cluster state changes | Application or process output | Record API activity | Numeric time-series measurement |
| Source | kubelet, scheduler, controllers, operators, CSI/CNI, admission, etc. | Container stdout/stderr | kube-apiserver, openshift-apiserver, node auditd, OVN audit | Prometheus exporters |
| Storage by default | Kubernetes API / etcd with TTL | Node log files | Audit files / logging pipeline | Prometheus / Thanos |
| Retention | Short | Depends on log stack | Depends on audit/log retention | Depends on metrics retention |
| Best for | “Why did this object change/fail?” | “What did the process print?” | “Who did what through API?” | “How much/how often/how long?” |
| Compliance use | Weak / supplemental | Depends | Stronger | Supplemental |

### 2.2 Events are best-effort evidence

Do not design a compliance or forensic process that depends only on Kubernetes Events. Events are intentionally lightweight and short-lived. Messages, reasons, timing, and repeated event behavior can change across Kubernetes versions and components.

Use events to answer operational questions such as:

- Why is the pod stuck in `Pending`?
- Why is the pod restarting?
- Why did the deployment fail to roll out?
- Why did the PVC not bind?
- Which node experienced pressure?
- What did the scheduler say?
- What did the kubelet report?
- Which operator emitted warnings?

Use audit logs to answer security questions such as:

- Who created the deployment?
- Who changed the route?
- Who deleted the secret?
- Which service account performed the API request?
- Was the request allowed or denied?

## 3. Kubernetes Event Object Model

A Kubernetes Event is attached to another object, often called the involved object or regarding object.

Important fields commonly seen in event records:

| Field | Meaning |
|---|---|
| `metadata.name` | Event object name |
| `metadata.namespace` | Namespace where the event is stored |
| `involvedObject.kind` | Kind of object the event is about, for example `Pod`, `Node`, `Deployment`, `PVC` |
| `involvedObject.name` | Object name |
| `involvedObject.namespace` | Object namespace |
| `reason` | Short machine-readable reason, for example `FailedScheduling`, `FailedMount`, `Unhealthy` |
| `message` | Human-readable explanation |
| `type` | Usually `Normal` or `Warning` |
| `source.component` | Older source component field, for example `kubelet`, `default-scheduler` |
| `reportingComponent` | Newer component field, for example `kubernetes.io/kubelet` |
| `firstTimestamp` | First time the event was observed in older event format |
| `lastTimestamp` | Last time the event was observed in older event format |
| `eventTime` | Event time in newer event format |
| `count` | Number of repeated occurrences |
| `series` | Repeated event series data in newer event format |

### 3.1 Normal vs Warning

`Normal` does not always mean “not useful.” Normal events show lifecycle progress such as scheduled, pulled image, created container, started container, successful attach, and successful scaling.

`Warning` usually deserves attention. Warning events commonly indicate:

- scheduling failures
- image pull failures
- volume mount failures
- probe failures
- node pressure
- network sandbox errors
- admission failures
- resource quota failures
- operator reconciliation problems

### 3.2 Repeated events and count

Kubernetes often aggregates repeated events. For example, a failing liveness probe might appear as one event with a high `count` rather than thousands of separate event objects.

This is important during incident reconstruction. If you sort only by the latest timestamp, an old issue that is still repeating can appear at the bottom or top depending on the command and sort field. Always check `count`, first time, last time, and message.

## 4. Why Kubernetes Event Logs Matter in OpenShift

For an experienced OpenShift administrator, Kubernetes Events are one of the fastest diagnostic signals because they are generated by the same control-plane and node components that make cluster decisions.

Events help during:

1. **Application troubleshooting**
   - `CrashLoopBackOff`
   - `ImagePullBackOff`
   - failed probes
   - failed ConfigMap or Secret references
   - missing service accounts

2. **Scheduling analysis**
   - insufficient CPU or memory
   - taints and tolerations mismatch
   - node affinity mismatch
   - topology spread constraints
   - node selector mismatch
   - PVC binding delays

3. **Storage troubleshooting**
   - PVC pending
   - volume attach failure
   - volume mount failure
   - CSI driver errors
   - storage class issues
   - `WaitForFirstConsumer` behavior

4. **Network troubleshooting**
   - pod sandbox creation failures
   - CNI plugin errors
   - Multus attachment failures
   - DNS-related readiness failures

5. **Node health analysis**
   - node not ready
   - memory pressure
   - disk pressure
   - PID pressure
   - pod eviction

6. **Operator and platform analysis**
   - ClusterOperator degradation
   - Operator Lifecycle Manager events
   - CSV install failure
   - subscription or install plan issues
   - operand deployment failures

7. **Incident timeline creation**
   - when a pod started failing
   - when scheduling started failing
   - when node pressure began
   - when image registry access broke
   - when rollout behavior changed

## 5. OpenShift Logging Architecture and Event Logs

### 5.1 Native OpenShift Logging categories

OpenShift Logging commonly deals with these major log categories:

- `application`
- `infrastructure`
- `audit`
- receiver-based inputs such as HTTP or syslog in newer Logging versions

Kubernetes Events are not simply another file under `/var/log/containers` until some component writes them as log output. That is why event export is required when you want historical event search in a log backend.

### 5.2 Modern OpenShift Logging 6.x flow

A simplified modern flow:

```text
Container stdout/stderr, node logs, audit logs
        |
        v
OpenShift Logging collector, usually Vector in Logging 6.x
        |
        v
ClusterLogForwarder pipelines
        |
        v
LokiStack / external Loki / Splunk / Kafka / syslog / HTTP / OTLP / Cloud logging / Elasticsearch
```

For Kubernetes Events using Event Router:

```text
Kubernetes API Events
        |
        | watch/list/get
        v
Event Router pod
        |
        | writes JSON to STDOUT
        v
/var/log/containers/eventrouter*.log on node
        |
        v
OpenShift Logging collector
        |
        v
ClusterLogForwarder pipeline
        |
        v
LokiStack or external log destination
```

### 5.3 Why Event Router works

The Event Router is a watcher. It connects to the Kubernetes API, watches event objects, formats them, and prints them to its own container standard output.

Once it does that, OpenShift Logging treats those lines like any other container log line from the Event Router pod. If the Event Router runs in `openshift-logging`, it is typically categorized as infrastructure logging because it runs in an OpenShift-prefixed namespace.

### 5.4 Current-version caution

Red Hat documented Event Router in earlier OpenShift Logging documentation. Recent OpenShift Logging 6.x documentation focuses on `ClusterLogForwarder`, Vector, LokiStack, inputs, outputs, receivers, and pipelines. Before deploying Event Router in a production cluster, confirm the support status and image version for your exact OpenShift and OpenShift Logging version.

Practical production rule:

- For **lab and troubleshooting training**, Event Router is a useful pattern.
- For **production**, confirm support with Red Hat documentation for your installed version or use a supported Red Hat/product-integrated receiver/exporter path.
- For **compliance**, use audit logs, not events alone.

## 6. Native Event Viewing Commands

### 6.1 Cluster-wide recent events

```bash
oc get events -A --sort-by='.lastTimestamp'
```

If your event objects use newer fields and `lastTimestamp` is empty, sort by creation timestamp:

```bash
oc get events -A --sort-by='.metadata.creationTimestamp'
```

### 6.2 Events in one namespace

```bash
oc get events -n myapp --sort-by='.lastTimestamp'
```

### 6.3 Only warning events

```bash
oc get events -A --field-selector type=Warning --sort-by='.lastTimestamp'
```

### 6.4 Events for one pod

```bash
oc get events -n myapp \
  --field-selector involvedObject.kind=Pod,involvedObject.name=web-7c9d6f8b6f-r2x4m \
  --sort-by='.lastTimestamp'
```

### 6.5 Describe object with related events

```bash
oc describe pod web-7c9d6f8b6f-r2x4m -n myapp
```

The `Events:` section at the end of `oc describe` is often the quickest root-cause signal.

### 6.6 Watch events live

```bash
oc get events -n myapp --watch
```

If your `oc` version supports the Kubernetes `events` subcommand:

```bash
oc events -n myapp --watch
oc events -A --types=Warning
```

### 6.7 JSON view for automation

```bash
oc get events -A -o json | jq -r '
  .items[] |
  [
    .metadata.namespace,
    .type,
    .reason,
    .involvedObject.kind,
    .involvedObject.name,
    .message
  ] | @tsv'
```

### 6.8 Top warning reasons

```bash
oc get events -A --field-selector type=Warning -o json | jq -r '
  .items[].reason' | sort | uniq -c | sort -nr
```

### 6.9 Events by component

```bash
oc get events -A -o json | jq -r '
  .items[] |
  [
    (.source.component // .reportingComponent // "unknown"),
    .type,
    .reason
  ] | @tsv' | sort | uniq -c | sort -nr
```

### 6.10 Events for nodes

```bash
oc get events -A \
  --field-selector involvedObject.kind=Node \
  --sort-by='.lastTimestamp'
```

## 7. Event Retention and etcd Impact in OpenShift

Kubernetes Events are stored in etcd through the API server and are purged by TTL. OpenShift lets you control this with the `KubeAPIServer` custom resource.

### 7.1 Check current event TTL

```bash
oc get cm config -n openshift-kube-apiserver \
  -o jsonpath='{.data.config\.yaml}' | \
  jq -r '.apiServerArguments["event-ttl"][0]'
```

### 7.2 Change event TTL

Example: set event TTL to 60 minutes.

```bash
oc patch kubeapiserver/cluster \
  --type=merge \
  -p='{"spec": {"eventTTLMinutes": 60 }}'
```

Wait for the API server rollout:

```bash
oc adm wait-for-stable-cluster
```

### 7.3 Production warning

Increasing event TTL increases how long events remain available through the Kubernetes API, but it also increases etcd storage pressure and API server watch/list load. On large clusters, high-volume event storms can contribute to control-plane pressure.

Better production pattern:

```text
Keep Kubernetes event TTL reasonable
        +
Export events to a log/observability backend
        +
Use retention controls in the external backend
```

## 8. Deploying Event Router Pattern

> **Important:** This section explains the Event Router pattern commonly used in OpenShift Logging training and older documented deployments. Validate the supported image and procedure for your installed OpenShift Logging version before production use.

### 8.1 Create Event Router manifest

Save as `eventrouter.yaml`:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: eventrouter
  namespace: openshift-logging
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: event-reader
rules:
- apiGroups: [""]
  resources: ["events"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["events.k8s.io"]
  resources: ["events"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: event-reader-binding
subjects:
- kind: ServiceAccount
  name: eventrouter
  namespace: openshift-logging
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: event-reader
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: eventrouter
  namespace: openshift-logging
data:
  config.json: |-
    {
      "sink": "stdout"
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: eventrouter
  namespace: openshift-logging
  labels:
    component: eventrouter
    logging-infra: eventrouter
    provider: openshift
spec:
  replicas: 1
  selector:
    matchLabels:
      component: eventrouter
      logging-infra: eventrouter
      provider: openshift
  template:
    metadata:
      labels:
        component: eventrouter
        logging-infra: eventrouter
        provider: openshift
    spec:
      serviceAccountName: eventrouter
      containers:
      - name: kube-eventrouter
        image: registry.redhat.io/openshift-logging/eventrouter-rhel8:v0.4
        imagePullPolicy: IfNotPresent
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 256Mi
        volumeMounts:
        - name: config-volume
          mountPath: /etc/eventrouter
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop:
            - ALL
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      volumes:
      - name: config-volume
        configMap:
          name: eventrouter
```

Apply it:

```bash
oc apply -f eventrouter.yaml
```

### 8.2 Verify Event Router pod

```bash
oc get pods -n openshift-logging -l component=eventrouter
```

Expected:

```text
NAME                           READY   STATUS    RESTARTS   AGE
eventrouter-xxxxxxxxxx-yyyyy   1/1     Running   0          1m
```

### 8.3 Check Event Router logs

```bash
oc logs -n openshift-logging deploy/eventrouter
```

You should see JSON event records similar to:

```json
{
  "verb": "ADDED",
  "event": {
    "metadata": {
      "name": "example.17abc",
      "namespace": "myapp",
      "creationTimestamp": "2026-07-03T10:00:00Z"
    },
    "involvedObject": {
      "kind": "Pod",
      "namespace": "myapp",
      "name": "web-7c9d6f8b6f-r2x4m"
    },
    "reason": "FailedScheduling",
    "message": "0/3 nodes are available: insufficient memory.",
    "type": "Warning"
  }
}
```

### 8.4 Why deploy it in `openshift-logging`?

Deploying Event Router in `openshift-logging` is useful because:

- the namespace is OpenShift infrastructure namespace
- logs are normally collected as infrastructure logs
- platform administrators can manage RBAC centrally
- the collector can pick up the pod stdout logs
- it avoids mixing cluster-wide event export with an application team namespace

## 9. Forwarding Event Router Logs with ClusterLogForwarder

### 9.1 Service account and RBAC for collector

Create collector service account:

```bash
oc create sa logging-collector -n openshift-logging
```

Grant writer role for LokiStack:

```bash
oc adm policy add-cluster-role-to-user logging-collector-logs-writer \
  -z logging-collector -n openshift-logging
```

Grant infrastructure log collection permission:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  -z logging-collector -n openshift-logging
```

If you also collect application logs:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  -z logging-collector -n openshift-logging
```

If you also collect audit logs:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging
```

**Important:** Do not add an input type in `ClusterLogForwarder` unless the collector service account has the matching cluster role. Missing RBAC can break log collection.

### 9.2 Example CLF to forward infrastructure logs to LokiStack

Because Event Router is running in `openshift-logging`, its container stdout logs are normally part of infrastructure logs.

Save as `clf-eventrouter-infra.yaml`:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: lokistack-out
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        key: service-ca.crt
        configMapName: logging-loki-gateway-ca-bundle
  pipelines:
  - name: eventrouter-infra-to-loki
    inputRefs:
    - infrastructure
    outputRefs:
    - lokistack-out
```

Apply:

```bash
oc apply -f clf-eventrouter-infra.yaml
```

### 9.3 Verify CLF status

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Look for conditions such as:

```text
Ready=True
```

Also check collector pods:

```bash
oc get pods -n openshift-logging
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Labels differ by Logging version, so if the selector does not work:

```bash
oc get pods -n openshift-logging --show-labels
```

## 10. Searching Event Logs in Loki / Console

### 10.1 Console approach

In the OpenShift web console:

1. Go to **Observe**.
2. Open **Logs**.
3. Select infrastructure logs.
4. Filter by namespace `openshift-logging`.
5. Filter by pod or container containing `eventrouter`.
6. Search inside the JSON message for event reasons such as:
   - `FailedScheduling`
   - `FailedMount`
   - `Unhealthy`
   - `BackOff`
   - `ImagePullBackOff`
   - `Evicted`

### 10.2 Loki LogQL examples

Label names differ depending on OpenShift Logging version, output data model, and Loki tenant. Adapt these examples after checking actual labels.

Find Event Router records:

```logql
{kubernetes_namespace_name="openshift-logging"} |= "eventrouter"
```

Warnings only:

```logql
{kubernetes_namespace_name="openshift-logging"} |= "\"type\":\"Warning\""
```

Scheduling failures:

```logql
{kubernetes_namespace_name="openshift-logging"} |= "FailedScheduling"
```

Image pull failures:

```logql
{kubernetes_namespace_name="openshift-logging"} |~ "Failed|ErrImagePull|ImagePullBackOff|BackOff"
```

PVC and mount issues:

```logql
{kubernetes_namespace_name="openshift-logging"} |~ "FailedMount|FailedAttachVolume|ProvisioningFailed|Volume"
```

Node pressure / eviction:

```logql
{kubernetes_namespace_name="openshift-logging"} |~ "Evicted|NodeNotReady|MemoryPressure|DiskPressure|PIDPressure"
```

### 10.3 Recommended parsing strategy

Event Router records are JSON. If your log backend supports JSON parsing, parse fields such as:

- `event.type`
- `event.reason`
- `event.message`
- `event.involvedObject.kind`
- `event.involvedObject.namespace`
- `event.involvedObject.name`
- `event.source.component`
- `event.reportingComponent`
- `event.count`

This allows useful dashboards:

- warning events by reason
- warning events by namespace
- warning events by node
- top noisy workloads
- scheduler failures by namespace
- storage failures by storage class
- image pull failures by registry
- operator failures by operator namespace

## 11. Event Troubleshooting Playbooks

## 11.1 Pod stuck in Pending

### Step 1: Check pod

```bash
oc get pod -n myapp
oc describe pod -n myapp <pod>
```

### Step 2: Check events

```bash
oc get events -n myapp \
  --field-selector involvedObject.kind=Pod,involvedObject.name=<pod> \
  --sort-by='.lastTimestamp'
```

### Common reasons

| Event reason | Meaning | Admin action |
|---|---|---|
| `FailedScheduling` | Scheduler cannot place pod | Check CPU/memory requests, taints, affinity, node selector, topology spread |
| `FailedCreate` | Controller cannot create pod | Check quota, SCC, admission, image policy |
| `FailedMount` | Volume cannot mount | Check PVC/PV, CSI driver, node, secret/configmap volume |
| `FailedAttachVolume` | Volume attach failed | Check cloud provider/CSI attach, access mode, stale attachment |
| `NotTriggerScaleUp` | Autoscaler did not scale | Check autoscaler limits and node group constraints |

### Deep checks

```bash
oc get quota -n myapp
oc describe quota -n myapp
oc get limitrange -n myapp
oc get nodes -o wide
oc describe node <node>
oc get pvc -n myapp
oc describe pvc -n myapp <pvc>
```

## 11.3 CrashLoopBackOff

Events show restart/backoff behavior, but application logs usually show the actual process error.

### Check events

```bash
oc describe pod -n myapp <pod>
```

Look for:

- `BackOff`
- `Killing`
- `Unhealthy`
- probe failures
- OOM-related messages

### Check current and previous logs

```bash
oc logs -n myapp <pod> -c <container>
oc logs -n myapp <pod> -c <container> --previous
```

### Check container status

```bash
oc get pod -n myapp <pod> -o json | jq '.status.containerStatuses[] | {
  name,
  restartCount,
  state,
  lastState
}'
```

### Common root causes

| Symptom | Likely issue |
|---|---|
| exit code non-zero | App crash or bad entrypoint |
| `OOMKilled` | Memory limit too low or memory leak |
| liveness probe failure | Probe too aggressive or app unhealthy |
| config file missing | ConfigMap/Secret mount/env issue |
| permission denied | SCC, UID, file permissions, volume ownership |

## 11.4 FailedMount / PVC Pending

### Check PVC


### Check pod events

```bash

```

### Check storage class


### Common OpenShift cases

| Event/message | Meaning | Action |
|---|---|---|
| `waiting for first consumer` | StorageClass uses `WaitForFirstConsumer` | Check pod scheduling constraints |

## 11.5 Liveness and readiness probe failures

### Events

```bash
oc describe pod -n myapp <pod> | sed -n '/Events:/,$p'
```

Look for:

- `Unhealthy`
- `Readiness probe failed`
- `Liveness probe failed`
- `Startup probe failed`

### Check probe configuration

```bash
oc get pod -n myapp <pod> -o json | jq '.spec.containers[] | {
  name,
  livenessProbe,
  readinessProbe,
  startupProbe
}'
```

### Debug from inside cluster

```bash
oc rsh -n myapp <pod>
curl -vk http://127.0.0.1:<port>/<path>
```

If the container lacks tools:

```bash
oc debug -n myapp pod/<pod> --image=registry.access.redhat.com/ubi9/ubi
```

### Common fixes

- Add `startupProbe` for slow-starting apps.
- Increase `initialDelaySeconds`.
- Increase `timeoutSeconds`.
- Use correct path and port.
- Do not point readiness to a dependency that has occasional latency unless intended.
- Do not make liveness too strict; it causes restart storms.

## 11.6 Node pressure and evictions

### Events

```bash
oc get events -A --field-selector involvedObject.kind=Node \
  --sort-by='.lastTimestamp'
```

### Check node

```bash
oc describe node <node>
oc adm top node
oc adm top pod -A --sort-by=memory
```

### Look for

- `MemoryPressure`
- `DiskPressure`
- `PIDPressure`
- `NodeNotReady`
- `Evicted`
- image filesystem pressure
- container filesystem pressure

### Admin response

1. Identify noisy pods.
2. Check requests/limits.
3. Check ephemeral storage usage.
4. Check image garbage collection.
5. Check kubelet and CRI-O logs.
6. Cordon/drain if node is unhealthy.
7. Add capacity if pressure is legitimate.

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

## 12. Event Logs vs Audit Logs in OpenShift

This distinction is critical for senior administrators.

### 12.1 Example: user creates a deployment

Audit log can show:

```text
user: alice
verb: create
resource: deployments
namespace: myapp
responseStatus: 201
```

Event log can show:

```text
Scaled up replica set web-xxxx to 3
Created pod web-xxxx-yyyy
Successfully assigned pod to worker-1
Pulled image
Started container
```

### 12.2 Example: user deletes a secret

Audit log can show who deleted the secret.

Events might not provide enough detail, or might only show secondary failures later, such as pods failing because a secret no longer exists.

### 12.3 Production rule

Use both:

```text
Audit logs = who/what API action
Events     = what cluster components observed afterward
App logs   = what process experienced
Metrics    = how much/how often/how long
```

## 13. Alerting from Event Logs

Do not alert on every Warning event. Kubernetes can produce noisy warnings during normal rollouts, node reboots, autoscaling, and transient registry/network issues.

### 13.1 Good event alert candidates

- sustained `FailedScheduling`
- repeated `FailedMount`
- repeated `FailedCreatePodSandBox`
- many `ImagePullBackOff` events across namespaces
- repeated `NodeNotReady`
- many `Evicted` events
- OLM install failures
- storage provisioning failures
- admission failures affecting many namespaces

### 13.2 Poor alert candidates

- one-off `Unhealthy` event during rollout
- occasional image pull retry that later succeeds
- old repeated event with no current impact
- namespace-specific warning with no production severity
- normal scaling events

### 13.3 Alert design

Instead of alerting on a single log line, aggregate by time window:

```text
IF warning events with reason FailedScheduling > 20 in 10 minutes
GROUP BY namespace, reason
THEN notify platform team
```

Or:

```text
IF unique namespaces with ImagePullBackOff > 5 in 15 minutes
THEN suspect registry or pull-secret issue
```

## 14. Noise Control and Event Storm Management

Large clusters can generate very high event volumes. Event storms can come from:

- broken deployments creating many pods
- failing probes every few seconds
- invalid image references
- storage provisioner failures
- CNI failures
- cluster autoscaler loops
- many operators reconciling failed resources
- GitOps repeatedly applying invalid manifests

### 14.1 Identify noisy namespaces

```bash
oc get events -A --field-selector type=Warning -o json | jq -r '
  .items[].metadata.namespace' | sort | uniq -c | sort -nr | head
```

### 14.2 Identify noisy reasons

```bash
oc get events -A --field-selector type=Warning -o json | jq -r '
  .items[].reason' | sort | uniq -c | sort -nr | head
```

### 14.3 Identify noisy objects

```bash
oc get events -A --field-selector type=Warning -o json | jq -r '
  .items[] |
  [.metadata.namespace, .involvedObject.kind, .involvedObject.name, .reason] | @tsv' |
  sort | uniq -c | sort -nr | head -30
```

### 14.4 Remediation approach

1. Stop the generating workload if it is causing control-plane pressure.
2. Fix root cause.
3. Reduce bad rollout loops from GitOps or CI/CD.
4. Adjust probe settings.
5. Fix missing secrets/configmaps.
6. Fix invalid PVC/storage definitions.
7. Avoid increasing event TTL as the first response to event loss.
8. Export events to an external backend for longer history.

## 15. Security and RBAC Considerations

Event export is cluster-wide visibility. A cluster-wide event watcher can see object names, namespaces, messages, and sometimes sensitive operational hints.

### 15.1 RBAC required

Event Router or a custom event exporter generally requires:

```yaml
verbs:
- get
- list
- watch
resources:
- events
```

At cluster scope, this means it can watch events across namespaces.

### 15.2 Sensitive data caution

Events should not contain secret values, but they can reveal:

- namespace names
- workload names
- image names
- registry hostnames
- node names
- failure messages
- storage backend hints
- network attachment names
- operator names

Treat cluster-wide event logs as platform-sensitive data.

### 15.3 Multi-tenancy

In multi-tenant OpenShift clusters:

- application teams should see their own namespace events
- platform teams may see cluster-wide events
- external SIEM pipelines should apply access controls
- LokiStack tenancy and RBAC should be configured carefully
- avoid exposing all event logs to all users

## 16. Performance Considerations

### 16.1 API server impact

An event exporter watches the API server. Normally a single efficient watch is acceptable, but multiple poorly designed exporters can add load.

Best practices:

- run one cluster-level event exporter
- avoid polling loops with frequent full-list calls
- use watches where possible
- set resource requests and limits
- monitor API server latency
- monitor etcd database size

### 16.2 Collector impact

Event Router writes events to stdout. The logging collector then reads them like other container logs. High event volume increases collector throughput and backend ingestion.

Watch:

```bash
oc adm top pod -n openshift-logging
oc get pods -n openshift-logging
oc logs -n openshift-logging deploy/eventrouter --tail=100
```

### 16.3 Backend impact

Events can have high cardinality fields:

- pod names
- event names
- object UIDs
- messages
- image names
- node names

Do not turn every dynamic field into an indexed label in Loki. Prefer labels for stable fields and keep high-cardinality details in the log body.

Good label candidates:

- cluster
- namespace
- type
- reason
- involved kind
- reporting component

Bad label candidates:

- full message
- pod UID
- event object name
- image digest
- exact error string

## 17. Advanced Correlation Workflow

When troubleshooting production incidents, correlate events with logs, metrics, and audit entries.

### 17.1 Example: Deployment rollout failure

```bash
oc rollout status deploy/web -n myapp
oc describe deploy/web -n myapp
oc describe rs -n myapp -l app=web
oc get pods -n myapp -l app=web
oc get events -n myapp --sort-by='.lastTimestamp'
oc logs -n myapp deploy/web --all-containers --tail=200
```

Correlation:

| Signal | What it tells you |
|---|---|
| Deployment status | Rollout condition |
| ReplicaSet events | Pod creation issue |
| Pod events | Scheduling, image, mount, probe issue |
| Container logs | App startup failure |
| Metrics | CPU/memory pressure |
| Audit logs | Who changed the deployment |

### 17.2 Example: PVC pending after deployment

```bash
oc get pvc -n myapp
oc describe pvc -n myapp data
oc describe pod -n myapp <pod>
oc get events -n myapp --sort-by='.lastTimestamp'
oc get sc
oc get pv
```

Possible conclusions:

- StorageClass missing.
- PVC requests unsupported access mode.
- Dynamic provisioner down.
- `WaitForFirstConsumer` waiting for pod scheduling.
- Pod scheduling blocked by node selector/affinity.
- CSI backend credentials broken.

### 17.3 Example: cluster-wide image pull issue

```bash
oc get events -A --field-selector type=Warning -o json | jq -r '
  .items[] | select(.reason | test("Pull|BackOff|Failed")) |
  [.metadata.namespace, .involvedObject.name, .reason, .message] | @tsv'
```

Then check:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get secret -A | grep -i pull
oc get pods -n openshift-image-registry
oc get co image-registry
oc get co authentication
```

## 18. Useful Event Reasons Cheat Sheet

| Reason | Area | Meaning |
|---|---|---|
| `Scheduled` | Scheduler | Pod assigned to node |
| `FailedScheduling` | Scheduler | Scheduler could not place pod |
| `Pulled` | Kubelet | Image already pulled or successfully pulled |
| `Pulling` | Kubelet | Image pull started |
| `Failed` | Kubelet / runtime | Generic failure, read message |
| `BackOff` | Kubelet | Backoff after repeated failure |
| `Created` | Kubelet | Container created |
| `Started` | Kubelet | Container started |
| `Killing` | Kubelet | Container being killed |
| `Unhealthy` | Kubelet | Probe failed |
| `FailedMount` | Storage/kubelet | Volume mount failed |
| `FailedAttachVolume` | Storage/controller | Volume attach failed |
| `ProvisioningFailed` | Storage/CSI | Dynamic provisioning failed |
| `ExternalProvisioning` | Storage | Waiting for external provisioner |
| `FileSystemResizeRequired` | Storage | FS resize needed |
| `Evicted` | Kubelet | Pod evicted due to pressure or policy |
| `NodeNotReady` | Node controller | Node readiness problem |
| `FailedCreatePodSandBox` | Runtime/CNI | Pod network sandbox failure |
| `FailedCreate` | Controller/admission | Controller failed to create object |

| `SuccessfulDelete` | Controller | Object successfully deleted |
| `ScalingReplicaSet` | Deployment | Deployment scaled ReplicaSet |

Always read the `message`; the same reason can have different root causes.

## 20. Troubleshooting Event Router Itself

### 20.1 Pod not running

```bash
oc get pods -n openshift-logging -l component=eventrouter
oc describe pod -n openshift-logging -l component=eventrouter
```

Check for:

- image pull errors
- SCC/security context errors
- missing service account
- missing config map
- scheduling errors

### 20.2 RBAC failure

Symptoms in logs:

```text
forbidden: User "system:serviceaccount:openshift-logging:eventrouter" cannot list resource "events"
```

Fix:

```bash
oc get clusterrole event-reader -o yaml
oc get clusterrolebinding event-reader-binding -o yaml
oc auth can-i list events --as system:serviceaccount:openshift-logging:eventrouter -A
oc auth can-i watch events --as system:serviceaccount:openshift-logging:eventrouter -A
```

### 20.3 No logs from Event Router

```bash
oc logs -n openshift-logging deploy/eventrouter
```

Generate a test event:

```bash
oc new-project event-test
oc create deployment bad --image=no-such-registry/no-such-image:v1 -n event-test
oc get events -n event-test
oc logs -n openshift-logging deploy/eventrouter --tail=50
```

### 20.4 Logs exist in Event Router but not in Loki

Check collector:

```bash
oc get pods -n openshift-logging
oc get clusterlogforwarder instance -n openshift-logging -o yaml
oc describe clusterlogforwarder instance -n openshift-logging
```

Check CLF includes `infrastructure` input and collector service account has `collect-infrastructure-logs`.

Check LokiStack:

```bash
oc get lokistack -A
oc get pods -n openshift-logging | grep loki
oc get route -n openshift-logging
```

### 20.5 Events too noisy

Temporarily scale down Event Router if it is overloading the logging backend:

```bash
oc scale deployment/eventrouter -n openshift-logging --replicas=0
```

Scale back:

```bash
oc scale deployment/eventrouter -n openshift-logging --replicas=1
```

Then fix the noisy source.

## 21. Production Best Practices

1. **Do not rely on default event retention for incidents.** Export events if you need historical analysis.
2. **Keep event TTL reasonable.** Increasing TTL is not a substitute for a log backend.
3. **Use Event Router or supported exporter carefully.** Validate support for your OpenShift Logging version.
4. **Run one cluster-wide exporter.** Avoid duplicate watchers.
5. **Deploy in an infrastructure namespace.** `openshift-logging` is a logical location for platform-managed event export.
6. **Use least privilege RBAC.** Grant only `get`, `list`, and `watch` on events.
7. **Protect event logs.** They reveal workload names, node names, image names, and failure details.
8. **Do not label high-cardinality fields in Loki.** Keep dynamic details in the log body.
9. **Alert on aggregated patterns, not single event lines.** Reduce noise.
10. **Correlate with audit logs.** Events tell what happened; audit logs tell who requested it.
11. **Correlate with metrics.** Events explain state changes; metrics prove impact.
12. **Check actual message text.** Same reason can hide different root causes.
13. **Build dashboards by namespace, reason, type, component, and involved kind.**
14. **Review warning spikes after upgrades.** CNI, CSI, and operators may change event patterns.
15. **Document event playbooks for L1/L2/L3 support.** Events are excellent triage signals.

## 22. Senior Admin Interview / Exam Notes

### 22.1 Important statements

- Kubernetes Events are API objects, not normal log files.
- Events are short-lived and should be treated as best-effort supplemental data.
- `oc describe` shows related events and is often the fastest troubleshooting command.
- Event Router watches events and writes them to stdout so the logging collector can collect them.
- In OpenShift Logging 6.x, `ClusterLogForwarder` defines inputs, outputs, pipelines, and filters.
- Built-in CLF input types include `application`, `infrastructure`, and `audit`; newer documentation also describes receiver inputs.
- Event Router logs from `openshift-logging` are usually collected through the infrastructure input.
- Audit logs and event logs solve different problems.
- Increasing event TTL affects etcd size and control-plane behavior.
- Loki label cardinality matters; do not label event messages or UIDs.

### 22.2 Fast command set

```bash
# all recent events
oc get events -A --sort-by='.lastTimestamp'

# warnings only
oc get events -A --field-selector type=Warning --sort-by='.lastTimestamp'

# pod-focused events
oc describe pod <pod> -n <ns>

# top warning reasons
oc get events -A --field-selector type=Warning -o json | jq -r '.items[].reason' | sort | uniq -c | sort -nr

# event router logs
oc logs -n openshift-logging deploy/eventrouter

# event TTL check
oc get cm config -n openshift-kube-apiserver -o jsonpath='{.data.config\.yaml}' | jq -r '.apiServerArguments["event-ttl"][0]'

# collector forwarder status
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

## 23. Common Mistakes

| Mistake | Why it is bad | Better approach |
|---|---|---|
| Treating events as audit logs | Events usually do not prove who performed an action | Use audit logs for identity/API evidence |
| Waiting hours before checking events | Native events may be purged | Export events to logging backend |
| Alerting on every warning event | Too noisy | Alert on rate and impact patterns |
| Increasing event TTL too high | Adds etcd pressure | Export to external log store |
| Running many event exporters | Adds API watch/list load | Run one managed exporter |
| Indexing event message as Loki label | High cardinality | Keep message in log body |
| Ignoring `count` | Repeated issue may be hidden | Check count and timestamps |
| Looking only at pod logs | Scheduling/storage failures happen before app starts | Check `oc describe` and events |
| Ignoring namespace of involved object | Event Router runs in one namespace but reports all namespaces | Parse `event.involvedObject.namespace` |
| Forgetting collector RBAC | CLF input without role can break collection | Bind required cluster roles first |

## 26. Final Takeaway

For advanced OpenShift administration, Kubernetes Events are one of the most valuable real-time troubleshooting signals. They explain what the platform observed while scheduling, starting, mounting, probing, scaling, and reconciling workloads. OpenShift Logging gives you the ability to retain and search those signals only after they are exported into the logging pipeline, commonly through the Event Router pattern or another supported event exporter.

Use events for fast operational diagnosis, use logs for process output, use metrics for behavior over time, and use audit logs for security accountability. A mature OpenShift platform uses all four together.
