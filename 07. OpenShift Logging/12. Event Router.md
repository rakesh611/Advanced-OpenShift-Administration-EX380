# Event Router in OpenShift Logging — Advanced Administration Guide

**Audience:** Advanced OpenShift administrators, SREs, platform engineers, and RHCA/DO380-style learners with production operations experience.  
**Scope:** Event Router in Red Hat OpenShift Logging, Kubernetes event collection, forwarding, troubleshooting, security, and production readiness.  
**Version context checked:** Red Hat OpenShift Logging 6.5 and OpenShift Logging 5.x/older EFK behavior where relevant.

---

## 1. Executive Summary

The **Event Router** is a small OpenShift Logging component that watches Kubernetes/OpenShift **Events** from the cluster API and writes them as JSON records to the Event Router pod’s `STDOUT`. After that, the normal OpenShift Logging collector pipeline, usually **Vector** in modern releases, collects the Event Router container logs and forwards them to the configured logging backend such as **LokiStack**, external Loki, Splunk, Kafka, Elasticsearch, HTTP, CloudWatch, S3-compatible storage, or another supported destination.

In simple terms:

```text
Kubernetes / OpenShift Events
        ↓ watch/list/get through Kubernetes API
Event Router pod in openshift-logging
        ↓ writes each event to STDOUT as JSON
Node log collector, usually Vector
        ↓ ClusterLogForwarder pipelines, filters, outputs
LokiStack / external log backend / SIEM / archive
```

For a senior OpenShift administrator, Event Router is important because normal Kubernetes events are **short-lived** and best-effort. They are excellent for troubleshooting pod scheduling, image pulls, probe failures, quota failures, PVC binding, node pressure, admission failures, operator actions, route/certificate issues, and controller activity, but they are not designed as a durable historical log store. Event Router bridges that gap by turning event streams into log records that can be stored, searched, retained, and correlated with application, infrastructure, and audit logs.

---

## 2. What Event Router Is

The Event Router is a cluster-level event watcher. It runs as a pod, normally in the `openshift-logging` namespace, and uses a service account with permission to read Events across the cluster.

It does the following:

1. Connects to the Kubernetes API server.
2. Watches event objects.
3. Receives event changes such as `ADDED`, `MODIFIED`, and sometimes repeated event updates.
4. Converts each event into a JSON log line.
5. Writes that JSON line to `STDOUT`.
6. Relies on the OpenShift Logging collector to pick up the container log and forward it.

It does **not** directly store logs.  
It does **not** replace audit logs.  
It does **not** replace Prometheus alerts.  
It does **not** create Kubernetes events.  
It only observes existing events and exposes them to the logging pipeline.

---

## 3. Why Event Router Exists

Kubernetes events are useful but temporary. They are designed as operational hints, not long-term evidence. A senior administrator normally checks them with commands like:

```bash
oc get events -A --sort-by=.lastTimestamp
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --field-selector involvedObject.name=<pod-name>
```

This is enough during active troubleshooting. It is not enough when:

- A pod failed yesterday and the event has already expired.
- A developer asks why a deployment was unavailable overnight.
- Security wants evidence of failed image pulls or suspicious workload activity.
- SREs need to correlate events with metrics and logs during an incident.
- Storage teams need historical PVC attach/mount/fail events.
- Platform teams need to identify noisy controllers or misbehaving workloads.
- Compliance teams require retention of cluster operational events.

Event Router solves this by converting transient events into log records.

## 4. Events vs Logs vs Audit Logs

Understanding the distinction is critical in production.

| Signal type | Source | Purpose | Example | Retention behavior |
|---|---|---|---|---|
| Kubernetes Events | API objects created by controllers, kubelet, scheduler, operators, etc. | Operational state changes and warnings | `FailedScheduling`, `BackOff`, `FailedMount`, `Pulled`, `Created`, `Killing` | Short-lived and best-effort |
| Application logs | Container `STDOUT`/`STDERR` | App runtime behavior | Java exception, HTTP request log | Retained by logging backend |
| Infrastructure logs | Node, container runtime, OpenShift component logs | Platform operations | kubelet, CRI-O, SDN/OVN, operator logs | Retained by logging backend |
| Audit logs | API server, OAuth, Kubernetes API audit records | Security and API activity trail | user created secret, service account patched role | Sensitive, usually routed separately |
| Metrics | Prometheus/Thanos samples | Numeric state over time | CPU usage, restart count, API latency | Retained by metrics stack |

Event Router converts **Events** into **log records**. These records become searchable in the logging backend, but their meaning remains event-centric.

## 5. Event Router in Modern OpenShift Logging Architecture

Modern OpenShift Logging uses a collector deployed by the Red Hat OpenShift Logging Operator through `ClusterLogForwarder` configuration. In OpenShift Logging 6.x, the `ClusterLogForwarder` API is under:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
```

The common production components are:

- **Red Hat OpenShift Logging Operator** — manages logging collector and forwarding resources.
- **Vector collector** — DaemonSet that collects and forwards logs from nodes.
- **ClusterLogForwarder** — defines inputs, filters, outputs, and pipelines.
- **Loki Operator / LokiStack** — common Red Hat-managed log store and query layer.
- **Event Router** — manually deployed pod that writes Kubernetes events to `STDOUT`.

High-level flow:

```text
+-------------------------+
| kube-apiserver          |
| Event API               |
+-----------+-------------+
            |
            | get/list/watch events
            v
+-------------------------+
| Event Router Deployment |
| ns: openshift-logging   |
| SA: eventrouter         |
+-----------+-------------+
            |
            | JSON to STDOUT
            v
+-------------------------+
| Node container log file |
| /var/log/containers/... |
+-----------+-------------+
            |
            | collector reads container logs
            v
+-------------------------+
| Vector collector        |
| DaemonSet               |
+-----------+-------------+
            |
            | CLF pipeline
            v
+-------------------------+
| LokiStack / SIEM / etc. |
+-------------------------+
```

Older OpenShift Logging stacks used Fluentd and Elasticsearch/Kibana. In that model, Event Router records were typically indexed as infrastructure logs. In modern deployments, you should think of Event Router output as part of the collector pipeline and verify how your backend labels it, normally as infrastructure logs because the pod runs in an `openshift-*` system namespace.

## 6. Key Production Use Cases

### 6.1 Pod Lifecycle Troubleshooting

Events show scheduling, pulling, creating, starting, stopping, and restart behavior.

Useful event reasons include:

- `Scheduled`
- `Pulling`
- `Pulled`
- `Created`
- `Started`
- `Killing`
- `BackOff`
- `Failed`
- `FailedMount`
- `FailedScheduling`
- `Unhealthy`

Common real-world examples:

```text
Warning  FailedScheduling  0/6 nodes are available: insufficient cpu
Warning  FailedMount       MountVolume.SetUp failed for volume
Warning  BackOff           Back-off restarting failed container
Warning  Failed            Failed to pull image
Normal   Pulled            Successfully pulled image
```

### 6.2 Storage and PVC Troubleshooting

Event Router is extremely useful for persistent volume issues.

You can investigate:

- PVC pending state.
- PV binding failures.
- CSI attach errors.
- Mount failures.
- Topology mismatch.
- StorageClass problems.
- Permission failures on NFS or CSI-backed storage.

Example event reasons:

```text
FailedBinding
ProvisioningFailed
ExternalProvisioning
FailedMount
FailedAttachVolume
VolumeResizeFailed
```

### 6.3 Networking and Route Troubleshooting

Events can expose problems around:

- Service endpoint changes.
- Ingress/router issues.
- Certificate or route problems.
- Pod readiness failures due to network dependency failures.

Event Router does not replace `oc describe route`, router logs, or OVN logs, but it gives historical context.

### 6.4 Operator and Cluster Component Troubleshooting

Operators create events when reconciling resources, detecting invalid configuration, or reporting degraded state.

This helps during:

- Operator upgrades.
- CSV install failures.
- Operand rollout failures.
- Certificate rotation.
- SCC/security context rejections.
- ImageContentSourcePolicy or pull secret issues.

### 6.5 Security and Compliance Context

Event logs are not audit logs, but they help answer operational-security questions such as:

- Which workloads repeatedly failed to pull images?
- Which namespaces generated repeated forbidden/security context errors?
- Were there suspicious workloads causing node pressure?
- Were pods repeatedly created and killed?
- Were workloads trying to mount unavailable or unauthorized storage?

Use Event Router logs together with audit logs for complete evidence.

## 7. What an Event Router Log Record Looks Like

A typical Event Router output is a JSON object similar to this:

```json
{
  "verb": "ADDED",
  "event": {
    "metadata": {
      "name": "example-pod.17b6d8e3eaa2a1b2",
      "namespace": "app-prod",
      "uid": "a1234567-1111-2222-3333-b1234567890c",
      "resourceVersion": "123456789",
      "creationTimestamp": "2026-07-03T07:10:31Z"
    },
    "involvedObject": {
      "kind": "Pod",
      "namespace": "app-prod",
      "name": "example-pod-6f7c5f7c9d-jx8nm",
      "uid": "d1234567-1111-2222-3333-b1234567890d",
      "apiVersion": "v1",
      "resourceVersion": "123456000"
    },
    "reason": "FailedScheduling",
    "message": "0/6 nodes are available: 3 Insufficient cpu, 3 node(s) had untolerated taint",
    "source": {
      "component": "default-scheduler"
    },
    "firstTimestamp": "2026-07-03T07:10:31Z",
    "lastTimestamp": "2026-07-03T07:10:31Z",
    "count": 1,
    "type": "Warning"
  }
}
```

Important fields:

| Field | Meaning |
|---|---|
| `verb` | Watch action, such as `ADDED` or `MODIFIED` |
| `event.metadata.namespace` | Namespace where the event object exists |
| `event.involvedObject.kind` | Object type involved in the event, such as `Pod`, `Deployment`, `Job`, `Node`, `PersistentVolumeClaim` |
| `event.involvedObject.name` | Name of the affected object |
| `event.reason` | Short machine-friendly reason, such as `BackOff` or `FailedScheduling` |
| `event.message` | Human-readable details |
| `event.source.component` | Component that emitted the event, such as scheduler, kubelet, job-controller |
| `event.type` | Usually `Normal` or `Warning` |
| `event.count` | Number of times the same event was observed/repeated |
| `firstTimestamp` / `lastTimestamp` | Time window for repeated event occurrences |

In your log backend, the whole JSON line might be stored under a `.message`, `.log`, or parsed JSON field depending on collector/output configuration.

## 8. Installation Requirements

Before deploying Event Router, confirm:

```bash
oc whoami
oc auth can-i create serviceaccount -n openshift-logging
oc auth can-i create clusterrole
oc auth can-i create clusterrolebinding
oc get ns openshift-logging
oc get pods -n openshift-logging
```

Required components:

1. OpenShift cluster access.
2. `cluster-admin` or equivalent privileges.
3. Red Hat OpenShift Logging Operator installed.
4. A valid log collector pipeline.
5. Pull access to the Event Router image.
6. A logging backend or external output if you need retention/search.

Recommended namespace:

```text
openshift-logging
```

Do not deploy Event Router into a random application namespace unless you have a clear reason. Deploying it into `openshift-logging` makes ownership, RBAC, log classification, and operational troubleshooting simpler.

## 9. Event Router Objects

A standard Event Router deployment contains:

| Object | Purpose |
|---|---|
| `ServiceAccount/eventrouter` | Identity used by the Event Router pod |
| `ClusterRole/event-reader` | Allows reading/watching event objects |
| `ClusterRoleBinding/event-reader-binding` | Binds cluster event-read permission to the service account |
| `ConfigMap/eventrouter` | Contains `config.json`; commonly `{"sink":"stdout"}` |
| `Deployment/eventrouter` | Runs the Event Router pod |

Minimum required RBAC:

```yaml
rules:
- apiGroups: [""]
  resources: ["events"]
  verbs: ["get", "list", "watch"]
```

This is cluster-wide read access to core `v1` Event resources. It does not grant permission to read pods, secrets, configmaps, or other workload objects.

## 10. Production-Ready Deployment YAML

Save the following as `eventrouter.yaml`.

> Adjust the image tag according to your supported OpenShift Logging version and your disconnected registry strategy. For connected clusters, Red Hat documentation commonly references `registry.redhat.io/openshift-logging/eventrouter-rhel9:v0.4`.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: eventrouter
  namespace: openshift-logging
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: event-reader
rules:
- apiGroups: [""]
  resources:
  - events
  verbs:
  - get
  - list
  - watch
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: event-reader-binding
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: event-reader
subjects:
- kind: ServiceAccount
  name: eventrouter
  namespace: openshift-logging
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: eventrouter
  namespace: openshift-logging
data:
  config.json: |
    {
      "sink": "stdout"
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: eventrouter
  namespace: openshift-logging
  labels:
    app.kubernetes.io/name: eventrouter
    app.kubernetes.io/component: eventrouter
    app.kubernetes.io/part-of: openshift-logging
    component: eventrouter
    logging-infra: eventrouter
    provider: openshift
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: eventrouter
      component: eventrouter
      logging-infra: eventrouter
      provider: openshift
  template:
    metadata:
      labels:
        app.kubernetes.io/name: eventrouter
        app.kubernetes.io/component: eventrouter
        app.kubernetes.io/part-of: openshift-logging
        component: eventrouter
        logging-infra: eventrouter
        provider: openshift
    spec:
      serviceAccountName: eventrouter
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: kube-eventrouter
        image: registry.redhat.io/openshift-logging/eventrouter-rhel9:v0.4
        imagePullPolicy: IfNotPresent
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 256Mi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop:
            - ALL
        volumeMounts:
        - name: config-volume
          mountPath: /etc/eventrouter
          readOnly: true
      volumes:
      - name: config-volume
        configMap:
          name: eventrouter
```

Apply it:

```bash
oc apply -f eventrouter.yaml
```

Verify objects:

```bash
oc get sa eventrouter -n openshift-logging
oc get clusterrole event-reader
oc get clusterrolebinding event-reader-binding
oc get cm eventrouter -n openshift-logging
oc get deploy eventrouter -n openshift-logging
oc get pods -n openshift-logging -l component=eventrouter
```

Check logs:

```bash
POD=$(oc get pod -n openshift-logging -l component=eventrouter -o jsonpath='{.items[0].metadata.name}')
oc logs -n openshift-logging "$POD" --tail=20
```

Pretty-print event records if `jq` is available:

```bash
oc logs -n openshift-logging "$POD" --tail=5 | jq .
```

## 11. Deployment Using OpenShift Template Style

Some official examples use an OpenShift `Template` so that `IMAGE`, `CPU`, `MEMORY`, and `NAMESPACE` are parameters.

Typical flow:

```bash
oc process -f eventrouter-template.yaml \
  -p NAMESPACE=openshift-logging \
  -p IMAGE=registry.redhat.io/openshift-logging/eventrouter-rhel9:v0.4 \
  -p CPU=100m \
  -p MEMORY=128Mi \
| oc apply -n openshift-logging -f -
```

The template approach is useful when:

- You maintain environment-specific images.
- You mirror images to a disconnected registry.
- You keep deployment manifests in GitOps.
- You want parameterized CPU/memory settings.

For GitOps, a plain manifest is often simpler because it avoids `oc process` at runtime.

## 12. Disconnected / Restricted Network Deployment

In disconnected clusters, do not reference `registry.redhat.io` directly from the workload manifest unless image mirroring and ImageContentSourcePolicy/ImageDigestMirrorSet configuration makes it resolvable.

Recommended process:

1. Mirror the Event Router image into your internal registry.
2. Pin by digest where possible.
3. Update `image:` in the Deployment.
4. Confirm pull secret availability.
5. Confirm node access to the internal registry.

Example:

```yaml
image: registry.example.com/openshift-logging/eventrouter-rhel9@sha256:<digest>
```

Verification:

```bash
oc describe pod -n openshift-logging -l component=eventrouter | egrep -i 'image|pull|failed|backoff'
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -20
```

If the pod is in `ImagePullBackOff`, check:

```bash
oc get secret -n openshift-logging
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagecontentsourcemirrorpolicy
oc debug node/<node-name>
```

Inside a debug node session, validate registry DNS/connectivity as appropriate for your environment.

## 13. ClusterLogForwarder Integration

Event Router only writes events to its container log. Collection and forwarding are controlled by the logging collector and `ClusterLogForwarder`.

In OpenShift Logging 6.x, a basic collector setup includes:

```bash
oc create sa collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector

# Add audit only if your CLF includes audit logs.
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Because Event Router is normally deployed in `openshift-logging`, its container logs normally flow as infrastructure logs. Therefore, your pipeline must collect `infrastructure` logs if you expect Event Router output to reach LokiStack or another backend.

Example `ClusterLogForwarder` to send application and infrastructure logs to a LokiStack:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: apps-and-infra-to-loki
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

Apply:

```bash
oc apply -f clusterlogforwarder.yaml
```

Verify:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=50
```

Expected conditions:

```text
Authorized=True
Valid=True
Ready=True
```

If `Authorized=False`, the collector service account does not have one or more required `collect-*-logs` cluster roles.

## 14. Targeting Only Event Router Logs

In large clusters, infrastructure logs can be high-volume. You may want a dedicated Event Router pipeline to send only event logs to a SIEM or long-term archive.

There are two common approaches.

### Approach A: Collect Infrastructure and Filter in Backend

Forward infrastructure logs to Loki/Splunk/Elasticsearch and filter by labels/fields such as:

```text
namespace = openshift-logging
pod/container/deployment contains eventrouter
container name = kube-eventrouter
component = eventrouter
logging-infra = eventrouter
```

This is easiest but may send more data than required.

### Approach B: Use Custom Input / Selector Where Supported

If your logging version supports custom inputs for namespaces/pods/labels, create an input that selects only the Event Router pod labels.

Conceptual example:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: eventrouter-forwarder
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
  - name: eventrouter-only
    type: infrastructure
    infrastructure:
      includes:
      - namespace: openshift-logging
        container: kube-eventrouter
  outputs:
  - name: event-archive
    type: kafka
    kafka:
      brokers:
      - kafka-1.example.com:9092
      topic: openshift-events
  pipelines:
  - name: eventrouter-to-kafka
    inputRefs:
    - eventrouter-only
    outputRefs:
    - event-archive
```

The exact selector schema varies by OpenShift Logging version. Always validate against your installed CRD:

```bash
oc explain clusterlogforwarder.spec.inputs --recursive | less
oc get crd clusterlogforwarders.observability.openshift.io -o yaml | less
```

## 15. Querying Event Router Logs

### 15.1 CLI Query from Event Router Pod

```bash
POD=$(oc get pod -n openshift-logging -l component=eventrouter -o jsonpath='{.items[0].metadata.name}')
oc logs -n openshift-logging "$POD" --since=30m | jq -r '
  select(.event.type=="Warning") |
  [.event.metadata.namespace,
   .event.involvedObject.kind,
   .event.involvedObject.name,
   .event.reason,
   .event.message] | @tsv'
```

Find all failed scheduling events:

```bash
oc logs -n openshift-logging "$POD" --since=2h \
| jq -r 'select(.event.reason=="FailedScheduling")'
```

Find PVC-related events:

```bash
oc logs -n openshift-logging "$POD" --since=4h \
| jq -r 'select(.event.involvedObject.kind=="PersistentVolumeClaim")'
```

Find warning events by namespace:

```bash
oc logs -n openshift-logging "$POD" --since=1h \
| jq -r 'select(.event.type=="Warning") | .event.metadata.namespace' \
| sort | uniq -c | sort -nr
```

### 15.2 Loki / LogQL Examples

The exact label names depend on your OpenShift Logging version and output format. Common labels/fields may include namespace, pod, container, log type, or Kubernetes metadata.

Start broad:

```logql
{namespace="openshift-logging"} |= "eventrouter"
```

or:

```logql
{kubernetes_namespace_name="openshift-logging"} |= "FailedScheduling"
```

Warning events:

```logql
{kubernetes_namespace_name="openshift-logging"} |= "\"type\":\"Warning\""
```

BackOff events:

```logql
{kubernetes_namespace_name="openshift-logging"} |= "BackOff"
```

PVC issues:

```logql
{kubernetes_namespace_name="openshift-logging"} |= "PersistentVolumeClaim" |= "Warning"
```

If JSON parsing is enabled/available:

```logql
{kubernetes_namespace_name="openshift-logging"}
| json
| event_type="Warning"
```

Because logging schemas vary, begin by finding a raw Event Router line and inspect actual labels before building dashboards.

### 15.3 OpenShift Console

In the OpenShift web console:

1. Go to **Observe → Logs**.
2. Select the appropriate log type, commonly **Infrastructure**.
3. Filter for `openshift-logging` namespace.
4. Search for `eventrouter`, `FailedScheduling`, `BackOff`, `FailedMount`, or `Warning`.
5. Open a raw event record and inspect labels/fields used by your backend.

## 16. Common Event Reasons and Admin Interpretation

| Reason | Type | Common source | Admin meaning |
|---|---|---|---|
| `FailedScheduling` | Warning | Scheduler | Resource shortage, taints/tolerations, affinity, topology, PVC binding, node selector issue |
| `BackOff` | Warning | kubelet | Container repeatedly failing or image pull backoff |
| `Failed` | Warning | kubelet/controller | Generic failure; read message carefully |
| `FailedMount` | Warning | kubelet | Volume mount failure, secret/configmap missing, CSI/NFS issue |
| `FailedAttachVolume` | Warning | attach/detach controller | CSI attach problem or zone/node mismatch |
| `Unhealthy` | Warning | kubelet | Liveness/readiness/startup probe failure |
| `Killing` | Normal | kubelet | Container termination due to rollout, eviction, probe, delete, preemption |
| `Pulled` | Normal | kubelet | Image pull successful |
| `Created` | Normal | kubelet | Container created |
| `Started` | Normal | kubelet | Container started |
| `Scheduled` | Normal | Scheduler | Pod assigned to node |
| `Evicted` | Warning | kubelet | Node pressure eviction |
| `NodeNotReady` | Warning | node controller | Node health problem |
| `ProvisioningFailed` | Warning | CSI/external provisioner | Dynamic PV provisioning failed |
| `ReconcileFailed` | Warning | Operator/controller | Operator failed to reconcile a resource |

## 17. Troubleshooting Decision Tree

### 17.1 Event Router Pod Is Not Running

Check deployment and pod status:

```bash
oc get deploy eventrouter -n openshift-logging
oc get pods -n openshift-logging -l component=eventrouter -o wide
oc describe pod -n openshift-logging -l component=eventrouter
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -30
```

Common causes:

| Symptom | Likely cause | Fix |
|---|---|---|
| `ImagePullBackOff` | Registry/auth/mirror issue | Check image, pull secret, mirror config |
| `CreateContainerConfigError` | ConfigMap missing or bad volume | Recreate `ConfigMap/eventrouter` |
| `CrashLoopBackOff` | Bad config or API access problem | Check `oc logs --previous` |
| `Forbidden` in logs | RBAC missing | Verify ClusterRoleBinding |
| Pod unscheduled | node selector, taint, resource shortage | Inspect scheduler event messages |

### 17.2 Event Router Runs But Shows No Logs

Check if cluster events exist:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -20
```

Check Event Router output:

```bash
POD=$(oc get pod -n openshift-logging -l component=eventrouter -o jsonpath='{.items[0].metadata.name}')
oc logs -n openshift-logging "$POD" --tail=50
```

Check RBAC:

```bash
oc auth can-i list events --as=system:serviceaccount:openshift-logging:eventrouter -A
oc auth can-i watch events --as=system:serviceaccount:openshift-logging:eventrouter -A
oc auth can-i get events --as=system:serviceaccount:openshift-logging:eventrouter -A
```

Expected:

```text
yes
yes
yes
```

If not, inspect:

```bash
oc get clusterrole event-reader -o yaml
oc get clusterrolebinding event-reader-binding -o yaml
```

### 17.3 Event Router Logs Exist But Are Not in Loki/SIEM

Check collector permissions:

```bash
oc get clusterrolebinding -o wide | egrep 'collect-application|collect-infrastructure|collect-audit'
```

Check `ClusterLogForwarder` status:

```bash
oc get clusterlogforwarder -A
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Check collector pods:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Common causes:

| Symptom | Likely cause | Fix |
|---|---|---|
| `Authorized=False` | Missing `collect-infrastructure-logs` or other role | Bind required role before applying CLF input |
| Collector DaemonSet removed | CLF requested unauthorized log type | Fix service account RBAC then reapply CLF |
| Logs visible in Event Router pod but absent in backend | Pipeline excludes infrastructure logs | Add `infrastructure` input or custom input |
| TLS/certificate error | Output CA config missing/wrong | Fix `tls.ca` config |
| 429 errors | Loki/output rate limit | Tune Loki limits or output rate limits |
| Backend auth failure | Token/secret issue | Check output secret and collector logs |

### 17.4 Too Many Event Logs

High event volume can happen during:

- Cluster upgrades.
- Large rollouts.
- Image registry outages.
- Broken probes causing restart storms.
- Storage outages.
- Node pressure or mass evictions.
- Misconfigured operators.
- CrashLooping workloads across many namespaces.

Actions:

```bash
# Top warning reasons from current eventrouter pod logs
oc logs -n openshift-logging "$POD" --since=1h \
| jq -r 'select(.event.type=="Warning") | .event.reason' \
| sort | uniq -c | sort -nr | head

# Top noisy namespaces
oc logs -n openshift-logging "$POD" --since=1h \
| jq -r '.event.metadata.namespace' \
| sort | uniq -c | sort -nr | head

# Top involved objects
oc logs -n openshift-logging "$POD" --since=1h \
| jq -r '[.event.involvedObject.namespace, .event.involvedObject.kind, .event.involvedObject.name] | @tsv' \
| sort | uniq -c | sort -nr | head
```

Fix the root cause first. Filtering should not hide active incidents unless you intentionally route only high-value events to expensive storage.

## 18. Filtering and Cost Control

Event logs are useful, but normal events can be noisy. In production, separate high-signal warnings from routine normal events.

### 18.1 Backend-Level Filtering

Keep everything in short-term Loki, but dashboards focus on:

- `event.type="Warning"`
- Important reasons such as `FailedScheduling`, `FailedMount`, `BackOff`, `Unhealthy`, `Evicted`
- Production namespaces
- Critical cluster namespaces

### 18.2 ClusterLogForwarder Drop Filters

OpenShift Logging supports `drop` filters to remove entire log records based on field matches. Actual field paths depend on parsed log structure and output format. Always inspect a sample record first.

Conceptual example for dropping known noise:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  filters:
  - name: drop-low-value-events
    type: drop
    drop:
    - test:
      - field: .message
        matches: '"type":"Normal"'
      - field: .message
        matches: '"reason":"Pulled"|"reason":"Created"|"reason":"Started"'
  pipelines:
  - name: infra-to-loki-filtered
    inputRefs:
    - infrastructure
    filterRefs:
    - drop-low-value-events
    outputRefs:
    - default-lokistack
```

Validate carefully. A wrong filter can drop useful incident data.

### 18.3 Output Rate Limits

If forwarding Event Router logs to an expensive destination like Splunk or CloudWatch, use output rate limits when supported:

```yaml
outputs:
- name: expensive-siem
  type: http
  http:
    url: https://siem.example.com/ingest
  rateLimit:
    maxRecordsPerSecond: 1000
```

Important: rate limiting drops records when exceeded. Monitor collector metrics and backend ingestion errors.

## 19. Performance Considerations

Event Router itself is lightweight, but it can increase log collector and backend load because it converts every watched event into a log line.

Production considerations:

1. **API watch load** — Event Router watches events from the API server. This is normally low overhead, but still a cluster-wide watch.
2. **Collector load** — Event Router output becomes container log input. On the node running Event Router, the collector reads more logs.
3. **Backend ingestion** — Loki/Splunk/Elasticsearch/Kafka can receive many extra records during incidents.
4. **Storage cost** — Normal events can be high-volume and low-value for long-term storage.
5. **Dashboard cardinality** — Avoid turning high-cardinality fields such as pod names, event names, or UIDs into Loki labels unless you understand the impact.
6. **Upgrade storms** — Cluster upgrades and operator rollouts can create many events.
7. **Broken workload storms** — A misconfigured namespace can generate constant `BackOff`, `FailedMount`, or `FailedScheduling` events.

Recommended starting resource requests:

```yaml
requests:
  cpu: 100m
  memory: 128Mi
limits:
  cpu: 500m
  memory: 256Mi
```

Scale vertically if the pod is CPU throttled or memory constrained. Event Router is normally one replica because multiple replicas can duplicate event logs.

## 20. Availability and Duplicate Event Behavior

Do not casually scale Event Router above one replica.

Why:

- Each replica watches the same event stream.
- Multiple replicas can produce duplicate log records.
- Duplicates increase backend cost and confuse incident timelines.

Recommended:

```yaml
replicas: 1
```

For availability, rely on Deployment self-healing. If the node fails, the pod is recreated elsewhere. A short gap in event logging is acceptable for most clusters because Event Router is observability support, not a control-plane component.

For strict compliance needs, discuss architecture with Red Hat support and your logging/security team before adding replicas or custom collectors.

## 21. Security Considerations

Event Router uses read-only permissions against Events, but events can contain sensitive operational metadata.

Examples of potentially sensitive event content:

- Image registry paths.
- Namespace names that reveal project names.
- Workload names that reveal application names.
- Error messages containing hostnames or endpoint names.
- PVC names and storage details.
- Admission or security policy failure messages.
- Internal service names.

Hardening recommendations:

1. Run in `openshift-logging`.
2. Use a dedicated service account.
3. Grant only `get`, `list`, and `watch` on `events`.
4. Do not grant broad `view`, `edit`, or `cluster-admin` to Event Router.
5. Run as non-root.
6. Drop Linux capabilities.
7. Disable privilege escalation.
8. Use `RuntimeDefault` seccomp profile.
9. Avoid privileged SCC.
10. Use namespace/network policies according to your cluster’s logging design.
11. Apply retention and access controls in Loki/SIEM.
12. Treat Event Router logs as operationally sensitive.

RBAC verification:

```bash
oc auth can-i list events -A --as=system:serviceaccount:openshift-logging:eventrouter
oc auth can-i get pods -A --as=system:serviceaccount:openshift-logging:eventrouter
oc auth can-i get secrets -A --as=system:serviceaccount:openshift-logging:eventrouter
```

Expected:

```text
yes
no
no
```

## 25. Event Router and Alerting

Event Router logs can support log-based alerting, but be careful. Events are best-effort and may change. For critical SLOs, prefer metrics-based alerts. Use event-log alerts for additional context or for specific operational symptoms.

Good alert candidates:

- High rate of `FailedScheduling` in production namespaces.
- Repeated `FailedMount` events.
- Repeated `ImagePullBackOff`/pull failures.
- Node `Evicted` events.
- Multiple `Unhealthy` probe failures for critical apps.
- Operator reconciliation warnings.

Avoid alerting on:

- Every `Normal` event.
- Every image pull.
- One-off `BackOff` events during normal deployment rollout.
- High-cardinality pod-name labels.

Example alert logic concept:

```text
If Warning events with reason FailedScheduling > threshold for 10 minutes
AND namespace is production
THEN notify platform SRE
```

Use log-based alerts together with Prometheus alerts such as:

- Pod crashloop alerts.
- Node pressure alerts.
- KubeDeploymentReplicasMismatch.
- KubePodNotReady.
- KubePersistentVolumeFillingUp.
- API server latency alerts.

## 29. Common Mistakes

| Mistake | Impact | Correct approach |
|---|---|---|
| Deploying Event Router but no CLF pipeline collects infrastructure logs | Event Router pod shows logs, backend does not | Include infrastructure input or custom eventrouter input |
| Missing collector RBAC | Collector DaemonSet may not run or CLF is not Authorized | Bind `collect-infrastructure-logs` before using infrastructure input |
| Scaling Event Router to multiple replicas | Duplicate event logs | Keep `replicas: 1` |
| Treating Event Router as audit logging | Incomplete security trail | Use audit logs for API audit, Event Router for event context |
| Storing all normal events forever | High cost and low signal | Filter, route, or apply different retention |
| Using old CLF API from older docs | CR rejected | Validate installed CRD API version |
| Pulling image directly in disconnected cluster | ImagePullBackOff | Mirror image and update manifest |
| Over-permissioning Event Router SA | Security risk | Only `get/list/watch` events |
| Not checking raw labels in Loki | Broken queries/dashboards | Inspect actual log labels/fields first |
| Dropping fields needed by backend | Failed ingestion or unusable records | Test filters in non-prod |

## 30. Interview / Exam-Level Explanation

If asked, explain Event Router like this:

> Event Router is a manually deployed OpenShift Logging component that watches Kubernetes events from the API server and writes them to its pod `STDOUT` as JSON. The normal logging collector, such as Vector, then collects those container logs and forwards them through the `ClusterLogForwarder` pipeline to LokiStack or another backend. It is useful because Kubernetes events are short-lived and best-effort, while production teams need historical visibility for scheduling failures, image pull issues, storage mount problems, probe failures, node pressure, and operator reconciliation events. It requires a service account with cluster-wide read access to events only, normally runs in `openshift-logging`, and should usually run as one replica to avoid duplicate event records.

Key points to remember:

- Manual deployment.
- Recommended namespace: `openshift-logging`.
- Writes to `STDOUT`.
- Collector forwards it.
- Needs `get/list/watch` on Events.
- Not part of the Logging Operator image bundle.
- Useful for historical event troubleshooting.
- Not a replacement for audit logs.
- Do not over-scale replicas.
- Verify CLF, collector RBAC, and backend visibility.

## 34. Best Practices from a Senior Admin View

1. **Deploy Event Router only after logging pipeline is healthy.** Otherwise, you will see pod logs locally but not in the backend.
2. **Keep Event Router separate from application teams.** Own it as a platform component.
3. **Use infrastructure log routing.** Since it runs in `openshift-logging`, include infrastructure in your CLF pipeline.
4. **Do not treat Events as ground truth alone.** Correlate with pod logs, node logs, metrics, and audit logs.
5. **Keep one replica.** Avoid duplicate event records.
6. **Use labels consistently.** They make backend filtering much easier.
7. **Mirror images in restricted clusters.** Avoid runtime dependency on external registries.
8. **Create saved searches.** `FailedScheduling`, `BackOff`, `FailedMount`, `Unhealthy`, and `Evicted` are high-value.
9. **Control retention by value.** Store warnings longer than normal lifecycle events if cost matters.
10. **Watch noisy namespaces.** Event storms usually point to real platform or workload problems.
11. **Validate after upgrades.** CLF APIs and collector behavior may change between major logging versions.
12. **Document field mappings.** Loki/Splunk/OTLP schemas differ; dashboards must match actual labels.

## 36. Final Takeaway

Event Router is small, but operationally powerful. It captures the cluster’s event stream and makes it searchable in your logging platform. For advanced OpenShift administration, it is most valuable when you use it to preserve short-lived troubleshooting evidence, correlate event storms with metrics and logs, and build production-ready visibility into scheduling, storage, image pull, probe, node, and operator issues.

Use it with discipline:

```text
Event Router for operational event history.
Audit logs for API/security evidence.
Metrics for alerting and SLOs.
Application/infrastructure logs for runtime diagnosis.
```

That separation is what makes an OpenShift observability design reliable at enterprise scale.
