## 1. What Are Node Logs in OpenShift?

In OpenShift, **node logs** are logs generated by the underlying node operating system and node-level platform services. These logs usually come from **journald** and files under `/var/log` on Red Hat Enterprise Linux CoreOS (RHCOS) or supported RHEL compute nodes.

Node logs are not the same as logs printed by application containers. They represent the health and behavior of the node itself: kubelet, CRI-O, systemd, NetworkManager, kernel, storage services, Machine Config Daemon, time synchronization, Open vSwitch/OVN components, and other host-level processes.

From a platform administrator's view, node logs answer questions such as:

- Why did a node become `NotReady`?
- Why are pods stuck in `ContainerCreating`?
- Why is CRI-O failing to start containers?
- Why did kubelet evict pods?
- Why is the node reporting disk pressure, memory pressure, or PID pressure?
- Why did a MachineConfig update fail?
- Why is node networking unstable?
- Why are control plane static pods restarting?
- Why is a worker node not joining the cluster?

In modern OpenShift Logging, node journal logs are normally treated as part of the **infrastructure** log stream.

## 2. Why Node Logs Matter for Advanced Administration

A beginner usually starts with:

```bash
oc get pods -A
oc describe pod <pod>
oc logs <pod>
```

An advanced administrator goes deeper:

```bash
oc get nodes
oc describe node <node>
oc adm node-logs <node> -u kubelet
oc adm node-logs <node> -u crio
oc debug node/<node>
chroot /host
journalctl -b -u kubelet
journalctl -b -u crio
journalctl -k
```

Node logs are critical because many OpenShift failures are not application failures. They originate below Kubernetes:

| Problem | Common Root Cause Visible in Node Logs |
|---|---|
| Pod stuck in `ContainerCreating` | CRI-O, image pull, storage mount, CNI failure |
| Node `NotReady` | kubelet crash, network issue, disk full, certificate issue |
| Pods evicted | kubelet eviction manager, memory pressure, disk pressure |
| Upgrade stuck | MachineConfigDaemon, rpm-ostree, reboot failure |
| Route/service issues | OVN, Open vSwitch, NetworkManager, DNS, node network |
| Control plane degraded | static pod restart, etcd issue, API server logs, kubelet |
| Image pull failures | CRI-O, registry trust, proxy, DNS, auth secret issue |
| PVC mount failures | kubelet, CSI driver, multipath, iSCSI, Fibre Channel, NFS |

For L3/SRE-level troubleshooting, node logs are often the difference between treating the symptom and finding the root cause.

## 3. Node Logs vs Application, Infrastructure, and Audit Logs

OpenShift Logging generally groups logs into three major categories:

| Log Type | Source | Examples |
|---|---|---|
| Application logs | User workload containers | `stdout`/`stderr` from app pods in user namespaces |
| Infrastructure logs | Platform containers and node journal logs | `openshift-*`, `kube-*`, `default` namespace containers, journald node logs |
| Audit logs | Security/audit event streams | Kubernetes API audit, OpenShift API audit, `auditd`, OVN audit |

Important distinction:

- **Node logs** are usually part of the **infrastructure** stream.
- **Node audit daemon logs** are part of the **audit** stream.
- **Control plane component container logs** may also appear as infrastructure logs because they run in infrastructure namespaces.
- **Application container logs** are not node logs, even though the raw files physically exist on the node under container runtime paths.

Practical example:

```yaml
pipelines:
  - name: infra-pipeline
    inputRefs:
      - infrastructure
    outputRefs:
      - default-lokistack
```

This pipeline can include both:

1. Infrastructure namespace container logs.
2. Node journald logs.

If you only want node journal logs and not infrastructure container logs, use a custom infrastructure input with `sources: [node]` where supported by your Logging API version.

## 4. Where Node Logs Come From

Node logs mainly come from the following layers.

### 4.1 Operating System Layer

OpenShift 4 nodes commonly run **Red Hat Enterprise Linux CoreOS**. RHCOS is designed to be immutable and managed by Operators, especially the Machine Config Operator. Host-level logs include:

- systemd service logs
- kernel ring buffer logs
- NetworkManager logs
- chrony/time synchronization logs
- boot logs
- rpm-ostree logs
- SELinux AVC messages
- node filesystem and mount messages

Typical commands:

```bash
journalctl -b
journalctl -b -p warning
journalctl -k
journalctl --since "1 hour ago"
```

### 4.2 Kubernetes Node Agent Layer

The kubelet is the main Kubernetes node agent. It manages pod lifecycle, communicates with the API server, calls CRI-O for container operations, invokes CNI networking, and manages volume mounts.

Typical kubelet logs show:

- node registration
- certificate rotation
- pod admission
- image pull failures
- container runtime errors
- volume mount failures
- eviction decisions
- node pressure conditions
- pod sandbox creation failures

Command:

```bash
journalctl -b -u kubelet
```

### 4.3 Container Runtime Layer

OpenShift uses CRI-O as the container runtime. CRI-O logs help troubleshoot:

- container start/stop failures
- image pull failures
- registry authentication issues
- storage driver issues
- pod sandbox creation
- runtime hooks
- seccomp/AppArmor/SELinux-related runtime errors

Command:

```bash
journalctl -b -u crio
```

### 4.4 Network Layer

Depending on the OpenShift networking stack, node logs may include:

- NetworkManager logs
- OVN-Kubernetes node logs
- Open vSwitch logs
- DNS resolution issues
- interface and routing problems
- MTU mismatch symptoms
- CNI plugin errors

Common commands:

```bash
journalctl -b -u NetworkManager
journalctl -b | grep -i ovn
journalctl -b | grep -i ovs
```

Also check platform pods:

```bash
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node -c ovn-controller
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node -c ovnkube-node
```

### 4.5 Machine Configuration Layer

The Machine Config Daemon runs on nodes and applies OS-level configuration rendered by the Machine Config Operator.

Common issues visible in logs:

- rendered MachineConfig mismatch
- degraded node due to manual file drift
- failed rpm-ostree update
- reboot required but blocked
- node stuck updating
- failed drain during upgrade

Command:

```bash
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -c machine-config-daemon
```

From node:

```bash
journalctl -b | grep -i machine-config
```

## 5. Important Node Log Locations

### 5.1 journald

Most node service logs are in journald.

```bash
journalctl -b
journalctl -b -u kubelet
journalctl -b -u crio
journalctl -b -u NetworkManager
journalctl -b -p err
```

Useful flags:

| Flag | Meaning |
|---|---|
| `-b` | Logs from current boot |
| `-b -1` | Logs from previous boot |
| `-u <unit>` | Filter by systemd unit |
| `-p err` | Show errors and above |
| `-f` | Follow logs live |
| `--since` | Time-based filter |
| `--until` | End time filter |
| `-o short-precise` | Timestamp with precision |
| `-o json` | JSON output |

Examples:

```bash
journalctl -b -u kubelet --since "30 min ago"
journalctl -b -p warning --no-pager
journalctl -b -1 -u crio
journalctl -k --since "today"
```

### 5.2 `/var/log`

Node log files can also exist under `/var/log`.

Common paths:

```text
/var/log/messages
/var/log/audit/audit.log
/var/log/containers/
/var/log/pods/
/var/log/openshift-apiserver/
/var/log/kube-apiserver/
/var/log/oauth-apiserver/
/var/log/ovn/
```

Not every path exists on every node. Control plane nodes have additional API-related logs. Worker nodes usually do not have API server logs.

### 5.3 Container Log Symlinks

Kubernetes-style container logs are exposed under:

```text
/var/log/containers/
```

These are usually symlinks into pod/container runtime log locations.

Example:

```bash
ls -l /var/log/containers/
```

Container logs are physically present on the node, but logically they are **application** or **infrastructure container** logs depending on namespace and workload type.

### 5.4 Audit Logs

Audit logs may exist at paths such as:

```text
/var/log/audit/audit.log
/var/log/kube-apiserver/audit.log
/var/log/openshift-apiserver/audit.log
/var/log/oauth-apiserver/audit.log
```

Do not mix them conceptually with normal node infrastructure logs. They are handled as audit logs and typically require stricter retention, access control, and forwarding policy.

## 6. How OpenShift Logging Collects Node Logs

OpenShift Logging deploys a collector as a **DaemonSet**, so a collector pod runs on each node. The collector reads logs from local node sources, enriches them with metadata, transforms them if configured, and forwards them to one or more outputs.

Modern deployments use:

- **Red Hat OpenShift Logging Operator** to manage log collection resources.
- **Vector collector** as the preferred collector.
- **ClusterLogForwarder** to define inputs, outputs, filters, and pipelines.
- **LokiStack** as the preferred in-cluster log store, when local storage is needed.

High-level flow:

```text
Node journald / /var/log
        |
        v
Collector DaemonSet pod on the same node
        |
        v
Parse / enrich / filter / transform
        |
        v
LokiStack / Kafka / Splunk / Elasticsearch / Cloud logging / HTTP / Syslog / OTLP
```

For node journal logs, the relevant input is normally:

```yaml
inputRefs:
  - infrastructure
```

Or a custom infrastructure input selecting only the node source:

```yaml
inputs:
  - name: node-journal-only
    type: infrastructure
    infrastructure:
      sources:
        - node
```

API details can vary by Logging release, so always verify with:

```bash
oc explain clusterlogforwarders.observability.openshift.io.spec.inputs
oc explain clusterlogforwarders.observability.openshift.io.spec.inputs.infrastructure
```

## 7. Vector Collector and Node Logs

### 7.1 What Vector Does

Vector is the modern log collector used by OpenShift Logging. It is responsible for:

- reading journald and container log sources
- adding Kubernetes metadata
- applying filters and transformations
- buffering and batching events
- forwarding logs to configured outputs
- exposing metrics for health and throughput

For node logs, Vector usually reads journald entries and maps them into structured log records.

### 7.2 Why Vector Is Preferred

Vector is preferred over legacy Fluentd in newer OpenShift Logging releases because it is designed for high-performance observability pipelines. From an operational perspective, Vector usually gives better resource efficiency, lower overhead, and a forward-looking feature path.

### 7.3 Collector Placement

The collector runs as a DaemonSet:

```bash
oc get ds -n openshift-logging
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

You should normally see one collector pod per schedulable node where logging is enabled.

Check which node each collector is running on:

```bash
oc get pods -n openshift-logging \
  -l app.kubernetes.io/component=collector \
  -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,STATUS:.status.phase
```

### 7.4 Collector Logs

Collector logs are not the same as collected logs. Collector logs show whether the collector itself is healthy.

```bash
oc logs -n openshift-logging \
  -l app.kubernetes.io/component=collector \
  --tail=100
```

Check a specific collector on a specific node:

```bash
oc get pods -n openshift-logging -o wide | grep <node-name>
oc logs -n openshift-logging <collector-pod-name> --tail=100
```

Common collector errors:

- cannot read source files
- journald access permission issue
- output TLS verification failure
- Loki 429 rate limit
- Kafka authentication failure
- output endpoint DNS failure
- invalid ClusterLogForwarder configuration
- missing RBAC for selected log type

## 8. ClusterLogForwarder and Node Log Forwarding

`ClusterLogForwarder` defines what logs are selected, optionally filtered/transformed, and where they are sent.

Core sections:

```yaml
spec:
  serviceAccount:
    name: logcollector
  inputs:
    - name: node-journal-only
      type: infrastructure
      infrastructure:
        sources:
          - node
  outputs:
    - name: default-lokistack
      type: lokiStack
      lokiStack:
        target:
          name: logging-loki
          namespace: openshift-logging
        authentication:
          token:
            from: serviceAccount
  pipelines:
    - name: node-logs-to-loki
      inputRefs:
        - node-journal-only
      outputRefs:
        - default-lokistack
```

### 8.1 Built-in Inputs

Common built-in input references:

```yaml
inputRefs:
  - application
  - infrastructure
  - audit
```

For node logs, `infrastructure` is the key input.

### 8.2 Custom Infrastructure Input

To avoid mixing node journal logs with infrastructure container logs, create a custom infrastructure input selecting only `node`:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logcollector
  inputs:
    - name: node-journal-only
      type: infrastructure
      infrastructure:
        sources:
          - node
  outputs:
    - name: default-lokistack
      type: lokiStack
      lokiStack:
        target:
          name: logging-loki
          namespace: openshift-logging
        authentication:
          token:
            from: serviceAccount
      tls:
        ca:
          configMapName: logging-loki-gateway-ca-bundle
          key: service-ca.crt
  pipelines:
    - name: node-journal-to-loki
      inputRefs:
        - node-journal-only
      outputRefs:
        - default-lokistack
```

Validate supported fields in your cluster:

```bash
oc explain clusterlogforwarder.spec.inputs.infrastructure
```

### 8.3 Pipeline Design

For production, avoid sending every log to every destination. Separate pipelines by audience and retention:

| Pipeline | Input | Output | Audience |
|---|---|---|---|
| `node-ops` | node infrastructure logs | LokiStack | SRE / platform team |
| `node-security` | auditd / audit logs | SIEM | Security team |
| `infra-apps` | infra namespace containers | Loki/Kafka | Platform operators |
| `apps` | application logs | Tenant-specific output | App teams |

## 9. RBAC and Service Account Permissions

Modern OpenShift Logging requires explicit permissions for the collector service account to collect selected log types.

Typical service account:

```bash
oc create sa logcollector -n openshift-logging
```

Grant infrastructure log collection permission:

```bash
oc adm policy add-cluster-role-to-user \
  collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:logcollector
```

If collecting application logs:

```bash
oc adm policy add-cluster-role-to-user \
  collect-application-logs \
  system:serviceaccount:openshift-logging:logcollector
```

If collecting audit logs:

```bash
oc adm policy add-cluster-role-to-user \
  collect-audit-logs \
  system:serviceaccount:openshift-logging:logcollector
```

Check status:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Expected condition examples:

```json
[
  {
    "type": "observability.openshift.io/Authorized",
    "status": "True",
    "message": "permitted to collect log types: [infrastructure]"
  },
  {
    "type": "observability.openshift.io/Valid",
    "status": "True"
  },
  {
    "type": "Ready",
    "status": "True"
  }
]
```

If `Authorized=False`, the collector service account is missing a required role binding. The collector DaemonSet might not be created or may be removed by the Operator.

## 10. Inspecting Node Logs Without Central Logging

Central logging is useful, but advanced troubleshooting often starts directly from the node log source.

Use these methods in order:

1. `oc adm node-logs` if API is healthy.
2. `oc debug node/<node>` if you need host inspection.
3. SSH as `core` only when API/kubelet path is unavailable or emergency access is required.
4. `must-gather` and `sosreport` for support-grade evidence.

Recommended starting point:

```bash
oc get nodes
oc describe node <node>
oc adm node-logs <node> -u kubelet --tail=100
oc adm node-logs <node> -u crio --tail=100
```

## 11. Using `oc adm node-logs`

`oc adm node-logs` retrieves journald unit logs and files from `/var/log` on nodes through the OpenShift API path.

### 11.1 Get kubelet Logs from a Node

```bash
oc adm node-logs <node-name> -u kubelet
```

Follow kubelet logs:

```bash
oc adm node-logs <node-name> -u kubelet -f
```

Get recent kubelet logs:

```bash
oc adm node-logs <node-name> -u kubelet --tail=200
```

### 11.2 Get CRI-O Logs

```bash
oc adm node-logs <node-name> -u crio
```

### 11.3 Get Logs by Role

Control plane nodes:

```bash
oc adm node-logs --role=master -u kubelet
```

Worker nodes:

```bash
oc adm node-logs --role=worker -u crio
```

> Note: Many newer OpenShift commands and labels use `control-plane`, but `master` role labels remain common in OpenShift clusters. Check actual node labels with `oc get nodes --show-labels`.

### 11.4 List Files Under `/var/log` Path

List API server logs on control plane nodes:

```bash
oc adm node-logs --role=master --path=openshift-apiserver
```

Read a specific file:

```bash
oc adm node-logs --role=master --path=openshift-apiserver/audit.log
```

### 11.5 Troubleshoot Previous Boot

`oc adm node-logs` focuses on current accessible logs. For previous boot analysis, use `oc debug node` and `journalctl -b -1`, or SSH if necessary.

## 12. Using `oc debug node`

Use `oc debug node/<node>` when you need deeper host-level access.

```bash
oc debug node/<node-name>
```

Inside the debug pod:

```bash
chroot /host
```

Now you are operating against the host filesystem.

Examples:

```bash
journalctl -b -u kubelet --no-pager
journalctl -b -u crio --no-pager
journalctl -b -p err --no-pager
journalctl -k --no-pager
ls -lh /var/log
ls -lh /var/log/containers | head
```

Check disk usage:

```bash
df -h
find /var/log -type f -size +100M -exec ls -lh {} \;
```

Check container runtime status:

```bash
systemctl status crio
systemctl status kubelet
crictl ps -a
crictl images
```

Check node network:

```bash
ip addr
ip route
nmcli con show
resolvectl status || cat /etc/resolv.conf
```

Exit safely:

```bash
exit
exit
```

Do not make manual host changes unless you fully understand the MachineConfig implications. On RHCOS, persistent host configuration must usually be managed through MachineConfig, Operators, or supported OpenShift APIs.

## 13. Using SSH When the API Is Down

SSH is not the preferred normal method for OpenShift 4 nodes, but it is sometimes necessary when:

- API server is unavailable.
- kubelet is broken.
- `oc debug node` cannot schedule.
- node cannot communicate with the control plane.
- bootstrap/control plane installation failed.

Example:

```bash
ssh core@<node-fqdn>
sudo journalctl -b -u kubelet -f
sudo journalctl -b -u crio -f
sudo journalctl -b -p err
```

Control plane API audit file example:

```bash
sudo tail -f /var/log/openshift-apiserver/audit.log
```

Use SSH carefully. Do not patch files manually as a long-term fix. Manual changes can cause MachineConfig drift and make the node degraded.

## 15. Node Logs for Control Plane Troubleshooting

Control plane failures often require correlation among:

- cluster operators
- static pods
- kubelet logs
- CRI-O logs
- API server logs
- etcd logs
- node system logs

Start with cluster health:

```bash
oc get clusterversion
oc get co
oc get nodes
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-etcd -o wide
```

Then inspect node logs on affected control plane node:

```bash
oc adm node-logs <master-node> -u kubelet --tail=300
oc adm node-logs <master-node> -u crio --tail=300
```

Check static pod containers:

```bash
oc logs -n openshift-kube-apiserver <kube-apiserver-pod> -c kube-apiserver
oc logs -n openshift-etcd <etcd-pod> -c etcd
```

If API server is unstable, inspect from node:

```bash
oc debug node/<master-node>
chroot /host
journalctl -b -u kubelet --no-pager
journalctl -b -u crio --no-pager
ls -lh /etc/kubernetes/manifests
ls -lh /var/log/kube-apiserver
ls -lh /var/log/openshift-apiserver
```

Common control plane signs in node logs:

| Log Pattern | Meaning |
|---|---|
| `failed to create pod sandbox` | CNI/runtime issue affecting static pods |
| `certificate has expired` | Cert rotation or time sync issue |
| `connection refused` to etcd | etcd unavailable or API static pod dependency issue |
| `no space left on device` | Disk pressure affecting static pod writes |
| `node is not ready` | kubelet/node status issue |
| `failed to sync pod` | kubelet cannot reconcile pod state |

## 16. Node Logs for Worker Node Troubleshooting

Worker node issues usually show up as:

- application pods not starting
- CNI failures
- image pull failures
- volume mount failures
- node pressure
- node flapping Ready/NotReady
- high CPU/memory load
- disk saturation

Basic workflow:

```bash
oc get nodes
oc describe node <worker-node>
oc get pods -A -o wide | grep <worker-node>
oc adm node-logs <worker-node> -u kubelet --tail=300
oc adm node-logs <worker-node> -u crio --tail=300
```

Look for kubelet events:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -50
```

Common kubelet log messages:

| Pattern | Likely Meaning |
|---|---|
| `Eviction manager` | Resource pressure causing pod eviction |
| `ImagePullBackOff` / `ErrImagePull` | Registry/auth/DNS/proxy issue |
| `MountVolume.SetUp failed` | Storage or CSI issue |
| `failed to create pod sandbox` | Network plugin or CRI-O issue |
| `PLEG is not healthy` | Runtime/kubelet sync issue |
| `NodeHasDiskPressure` | Disk capacity or image/container log growth |

## 17. Node Logs for CRI-O and Kubelet Issues

### 17.1 Pod Sandbox Failure

Symptoms:

## 21. Audit Logs vs Node Logs

Audit logs are security-relevant records. Some are stored on nodes, but they are not handled the same way as normal infrastructure node logs.

Audit sources can include:

- Kubernetes API server audit logs
- OpenShift API server audit logs
- Linux `auditd` logs
- OVN audit logs, if enabled

Typical files:

```text
/var/log/audit/audit.log
/var/log/kube-apiserver/audit.log
/var/log/openshift-apiserver/audit.log
```

ClusterLogForwarder audit input:

```yaml
pipelines:
  - name: audit-to-siem
    inputRefs:
      - audit
    outputRefs:
      - external-siem
```

Do not send audit logs casually to a general-purpose developer log store. They may contain sensitive information and usually require:

- restricted access
- long retention
- tamper-resistant storage
- SIEM integration
- encryption in transit
- encryption at rest
- clear compliance ownership

## 22. Forwarding Only Node Infrastructure Logs

A common advanced requirement is:

> Forward only node journal logs to the SRE Loki tenant, but do not include all infrastructure container logs.

Example:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logcollector
  inputs:
    - name: node-only
      type: infrastructure
      infrastructure:
        sources:
          - node
  outputs:
    - name: loki-node
      type: lokiStack
      lokiStack:
        target:
          name: logging-loki
          namespace: openshift-logging
        authentication:
          token:
            from: serviceAccount
      tls:
        ca:
          configMapName: logging-loki-gateway-ca-bundle
          key: service-ca.crt
  pipelines:
    - name: node-only-pipeline
      inputRefs:
        - node-only
      outputRefs:
        - loki-node
```

Apply:

```bash
oc apply -f node-only-clf.yaml
```

Verify:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=50
```

## 24. Forwarding Node Logs to External Systems

OpenShift Logging can forward logs to external systems such as:

- external Loki
- Kafka
- Splunk HEC
- Elasticsearch
- HTTP endpoint
- cloud logging systems
- syslog-compatible destinations
- OTLP receiver, depending on version/support status

### 24.1 Kafka Example for Node Logs

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logcollector
  inputs:
    - name: node-only
      type: infrastructure
      infrastructure:
        sources:
          - node
  outputs:
    - name: kafka-node-output
      type: kafka
      kafka:
        url: tls://kafka.example.com:9093/node-logs
        topic: openshift-node-logs
  pipelines:
    - name: node-to-kafka
      inputRefs:
        - node-only
      outputRefs:
        - kafka-node-output
```

### 24.2 Splunk HEC Design

For Splunk:

- Use a dedicated index for node/infrastructure logs.
- Do not mix app logs and node logs unless your operational model requires it.
- Add source type mapping.
- Use TLS.
- Use token from Secret.
- Control event volume aggressively.

Conceptual pipeline:

```text
node journald -> Vector collector -> ClusterLogForwarder -> Splunk HEC -> node_ops index
```

### 24.3 Syslog

Syslog forwarding is common for enterprise SIEM/log aggregation, but be careful with format, TLS, and volume. Some syslog receiver features are limited to supported scenarios and specific product integrations depending on your Logging version.

## 25. Filtering and Reducing Noise

Node logs can be noisy. A production cluster can generate large amounts of journald data, especially during upgrades, node pressure, network instability, or image pull storms.

### 25.1 Filter by Source

Best practice: do not forward all log types to all destinations.

Use separate pipelines:

```yaml
pipelines:
  - name: node-ops
    inputRefs:
      - node-only
    outputRefs:
      - sre-loki

  - name: audit-security
    inputRefs:
      - audit
    outputRefs:
      - security-siem
```

### 25.2 Drop Noisy Content

Depending on Logging version, filters can drop or prune records. Use this carefully. Dropping logs can reduce cost, but it can also remove evidence needed for incident review.

Examples of logs you may consider filtering:

- repeated health-check noise
- known benign warnings
- verbose debug output accidentally enabled
- duplicate messages from non-critical services

Never blindly drop:

- kubelet errors
- CRI-O errors
- kernel OOM messages
- audit logs
- certificate errors
- authentication failures
- MachineConfig errors
- storage mount errors

### 25.3 Rate Limiting

Rate limiting protects your logging backend from storms. However, aggressive rate limiting can hide important symptoms during incidents.

Use rate limiting when:

- a noisy node overwhelms Loki or Kafka
- app teams accidentally generate massive logs
- network reconnect causes backlog flush
- storage cost must be controlled

But alert when rate limiting occurs.

## 26. Retention, Storage, and Capacity Planning

Node logs are essential for incident response. Retention must match your operational needs.

Suggested retention model:

| Log Category | Typical Retention | Reason |
|---|---:|---|
| Node infrastructure logs | 7–30 days | Operational troubleshooting |
| Control plane infrastructure logs | 14–45 days | Upgrade and incident analysis |
| Audit logs | 90–365+ days | Compliance and investigation |
| Application logs | Based on app/SLA | Developer and business needs |

### 26.1 Sizing Considerations

Node log volume depends on:

- number of nodes
- pod churn rate
- image pull frequency
- network instability
- kubelet verbosity
- audit policy
- number of Operators
- upgrade activity
- infrastructure component health

High-risk volume events:

- cluster upgrades
- large node scale-up/scale-down
- registry outage
- DNS outage
- CNI failure
- storage backend outage
- image pull storm
- CrashLoopBackOff storm
- audit policy set too verbose

### 26.2 Loki Cardinality Warning

When forwarding to Loki, be careful with labels. Labels should help query logs but must not create extreme cardinality.

Good labels:

```text
log_type
kubernetes_host
namespace
container_name
```

Risky labels:

```text
pod UID
request ID
full error string
container ID
highly dynamic IP/port pairs
```

High cardinality can hurt Loki ingestion and query performance.

## 27. Security and Compliance Considerations

Node logs may contain sensitive data:

- hostnames
- internal IP addresses
- service names
- registry URLs
- certificate errors
- usernames or service account names
- SELinux denials
- authentication failures
- audit records
- kernel/device information

Security practices:

1. Restrict access to infrastructure and audit logs.
2. Separate tenant application logs from node logs.
3. Use TLS for forwarding.
4. Use Secrets for output credentials.
5. Rotate log forwarding credentials.
6. Avoid forwarding audit logs to low-security stores.
7. Avoid exposing node logs to application teams unless required.
8. Mask or prune sensitive fields only after compliance review.
9. Keep audit logs immutable where required.
10. Monitor collector failures as a security visibility gap.

RBAC example for viewing logs depends on OpenShift console/logging tenancy. Do not grant broad cluster-admin access just to view logs. Create proper roles for SRE/security users.

## 28. Performance Impact of Node Log Collection

Node log collection is not free. Collector pods consume CPU, memory, network bandwidth, and disk buffer resources.

### 28.1 Tune Collector Resources

Example:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    resources:
      requests:
        memory: 736Mi
      limits:
        cpu: 500m
        memory: 1Gi
```

Always validate resource fields on your cluster:

```bash
oc explain clusterlogforwarder.spec.collector.resources
```

### 28.2 Watch Collector Health

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc top pods -n openshift-logging
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

### 28.3 Backpressure

Backpressure occurs when outputs cannot receive logs as fast as collectors produce them.

Symptoms:

- collector memory increases
- output retry messages
- 429 from Loki
- Kafka timeout/retry
- logs delayed in UI
- dropped events if configured for at-most-once delivery

Actions:

- check backend health
- increase backend capacity
- reduce log volume
- tune batching/retry where supported
- separate pipelines by priority
- avoid sending audit and noisy infrastructure logs to same constrained backend

## 29. Collector Troubleshooting

### 29.1 Check ClusterLogForwarder Status

```bash
oc get clusterlogforwarder -n openshift-logging
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Important conditions:

| Condition | Expected | Meaning |
|---|---|---|
| `Authorized` | `True` | Service account can collect selected log types |
| `Valid` | `True` | CLF syntax and semantics are valid |
| `Ready` | `True` | Operator reconciled resources successfully |

### 29.2 Collector Pod Missing

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
```

If no pods exist:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Likely causes:

- missing `collect-infrastructure-logs` role
- invalid output configuration
- invalid input/filter/pipeline reference
- Operator degraded
- namespace/resource issue

### 29.3 Collector Running but No Node Logs

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Verify:

- pipeline includes `infrastructure` or node-only custom input
- service account has `collect-infrastructure-logs`
- output is reachable
- TLS CA is correct
- collector pods exist on nodes
- logs exist in journald on target node

Generate a test node log message from a debug node carefully:

```bash
oc debug node/<node>
chroot /host
logger "openshift node log test from $(hostname)"
```

Then search in your logging backend for the message.

### 29.4 TLS Errors

Common collector log:

```text
certificate verify failed: self-signed certificate in certificate chain
```

Fix:

- add correct `tls.ca` config
- verify destination certificate chain
- ensure service CA ConfigMap exists
- rotate/re-extract CA if changed

### 29.5 Loki 429 Errors

Common collector log:

```text
429 Too Many Requests
```

Meaning:

- Loki is rate limiting ingestion.
- Backlog flush may be happening after initial deployment or outage recovery.

Actions:

- wait briefly if caused by initial backlog
- check LokiStack health
- increase Loki capacity
- reduce log volume
- tune retention and labels
- split pipelines

### 29.6 Enable Collector Debug Logging

```bash
oc annotate clusterlogforwarder instance -n openshift-logging \
  observability.openshift.io/log-level=debug --overwrite

oc logs -n openshift-logging \
  -l app.kubernetes.io/component=collector \
  --tail=100
```

Reset after troubleshooting:

```bash
oc annotate clusterlogforwarder instance -n openshift-logging \
  observability.openshift.io/log-level=info --overwrite
```

Do not leave debug logging enabled in production unless you have a specific reason.

## 31. Interview and Real-World Scenario Questions

### Q1. A node is `NotReady`. Which logs do you check first?

Answer:

```bash
oc describe node <node>
oc adm node-logs <node> -u kubelet --tail=300
oc adm node-logs <node> -u crio --tail=300
oc debug node/<node>
chroot /host
journalctl -b -p err
```

Focus on kubelet health, CRI-O health, disk pressure, memory pressure, network connectivity, and certificate issues.

### Q2. Pods are stuck in `ContainerCreating`. What node logs matter?

Answer:

- kubelet logs for pod sync and volume/CNI errors
- CRI-O logs for runtime and image errors
- OVN/CNI logs for sandbox creation failure
- CSI logs for mount failure

Commands:

```bash
oc describe pod <pod> -n <ns>
oc adm node-logs <node> -u kubelet --tail=300
oc adm node-logs <node> -u crio --tail=300
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --tail=100
```

### Q3. ClusterLogForwarder is `Ready=True`, but no logs appear in Loki. What next?

Answer:

Check collector logs and output TLS/connectivity:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Possible causes include output TLS CA error, Loki rate limiting, backend unavailable, wrong tenant, missing label/query, or pipeline not selecting infrastructure logs.

### Q4. What is the difference between node logs and audit logs?

Answer:

Node logs are operational host/service logs, usually part of infrastructure logging. Audit logs are security-relevant records of API/auditd/OVN activity and should be forwarded, retained, and protected separately.

### Q5. Why should application teams not get unrestricted node logs?

Answer:

Node logs can expose hostnames, internal IP addresses, registry details, authentication failures, system errors, and security-relevant information. Access should follow least privilege.

### Q6. What is the fastest way to check kubelet logs on all control plane nodes?

```bash
oc adm node-logs --role=master -u kubelet --tail=100
```

### Q7. How do you prove node journald logs are being collected?

Generate a test host log:

```bash
oc debug node/<node>
chroot /host
logger "node-log-test $(hostname) $(date --iso-8601=seconds)"
```

Then search the infrastructure log stream in Loki/OpenShift console.

A good OpenShift administrator correlates four layers:

```text
Cluster state      -> oc get/describe/co/events
Workload state     -> pod logs/events/status
Node state         -> kubelet/crio/journal/kernel logs
Logging pipeline   -> collector/CLF/output/backend status
```

For node-level incidents, always build a timeline:

1. When did the symptom start?
2. Which node was affected?
3. What changed before the issue? Upgrade, MachineConfig, workload rollout, network/storage event?
4. What do kubelet and CRI-O say at that timestamp?
5. Did the logging collector capture the same event centrally?
6. Is there a related cluster operator degraded condition?
7. Is the issue isolated to one node, one role, one zone, or all nodes?

That timeline-based approach is what separates basic command execution from advanced OpenShift administration.
