## 1. What Vector Does in OpenShift Logging

Vector is the log collector and forwarder used by modern Red Hat OpenShift Logging. It runs on cluster nodes, reads log sources, enriches events with Kubernetes metadata, applies pipeline logic, and sends logs to configured outputs such as LokiStack, Kafka, syslog, Elasticsearch-compatible endpoints, HTTP endpoints, OTLP receivers, Splunk HEC, or cloud logging services depending on the supported OpenShift Logging version and output type.

In practical OpenShift administration, Vector is responsible for the following:

- Reading container logs from node filesystem paths.
- Reading infrastructure logs, node logs, and selected audit logs when configured and authorized.
- Adding Kubernetes metadata such as namespace, pod, container, labels, node, and log type.
- Applying `ClusterLogForwarder` input selection.
- Applying filters such as drop, prune, multiline, audit policy filtering, and parsing.
- Routing logs through pipelines to one or more outputs.
- Retrying output writes when destinations are unavailable.
- Buffering logs according to the collector/output tuning model.
- Exposing metrics that OpenShift Monitoring can scrape for alerting.

A senior administrator should think of Vector as a distributed data plane. The Red Hat OpenShift Logging Operator is the control plane that creates and reconciles the Vector workload from `ClusterLogForwarder` and related resources.

### High-level flow

```text
Application / infra / audit log files
        |
        v
Vector collector pod on each node
        |
        |-- read source
        |-- enrich metadata
        |-- filter / transform
        |-- route through pipeline
        |-- buffer / retry
        v
LokiStack / Kafka / Syslog / HTTP / OTLP / Splunk / Cloud output
```

### Why Vector troubleshooting is different from Fluentd troubleshooting

Legacy OpenShift Logging deployments used Fluentd and Elasticsearch/Kibana. Modern Logging 6.x uses Vector as the supported collector and separates collection/forwarding, storage, and visualization into separate operators and APIs. This changes the troubleshooting workflow:

| Old style | Modern style |
|---|---|
| `ClusterLogging` controlled most logging stack behavior | `ClusterLogForwarder` is central for collection and forwarding |
| Fluentd collector | Vector collector |
| Elasticsearch managed log store | LokiStack is the primary Red Hat-managed log store |
| Kibana visualization | OpenShift console logging plugin via Cluster Observability Operator |
| Fluentd buffer/error patterns | Vector component metrics, delivery tuning, output errors, and backpressure |

## 2. Modern Logging Architecture: Logging 6.x View

A modern OpenShift Logging 6.x deployment normally has these parts:

```text
+-------------------------------+
| Red Hat OpenShift Logging     |
| Operator                      |
| - owns collector/forwarding   |
| - reconciles Vector workload  |
+---------------+---------------+
                |
                v
+-------------------------------+
| ClusterLogForwarder           |
| observability.openshift.io/v1 |
| - serviceAccount              |
| - inputs                      |
| - filters                     |
| - outputs                     |
| - pipelines                   |
| - tuning / scheduling         |
+---------------+---------------+
                |
                v
+-------------------------------+
| Vector Collector              |
| usually DaemonSet-style       |
| one collector pod per node    |
+---------------+---------------+
                |
                v
+-------------------------------+
| Outputs                       |
| - LokiStack                   |
| - Kafka                       |
| - syslog                      |
| - http                        |
| - otlp                        |
| - external systems            |
+-------------------------------+
```

### Main troubleshooting layers

When logs are missing, delayed, duplicated, malformed, or not reaching outputs, isolate the fault by layer:

1. **API layer** — CRD exists? correct API group? `ClusterLogForwarder` accepted?
2. **Operator layer** — operator running? CSV healthy? reconciliation errors?
3. **RBAC layer** — service account has collect and write permissions?
4. **Collector workload layer** — Vector DaemonSet/pods running on all required nodes?
5. **Source layer** — log files exist and are readable?
6. **Pipeline layer** — inputRefs, filterRefs, outputRefs, names, namespaces, and labels correct?
7. **Configuration layer** — generated Vector config valid and matches expectation?
8. **Output layer** — Loki/external endpoint reachable, authenticated, authorized, and accepting payload format?
9. **Runtime layer** — buffers, retries, backpressure, CPU, memory, disk, node pressure?
10. **Consumer layer** — logs exist but UI/tenant/query/RBAC hides them?

Do not start by changing YAML randomly. First decide where in the flow the data stops.

## 3. Vector Troubleshooting Mindset

A 10-year-experience approach is not “restart the pods and check again.” A senior workflow is:

1. **Define the symptom clearly.**
   - No collector pods?
   - Collector pods running but no logs?
   - Application logs missing only from one namespace?
   - Audit logs missing?
   - Loki logs visible but external SIEM missing?
   - High error alert?
   - Log delay/backlog?
   - Duplicates after node restart?

2. **Map symptom to pipeline stage.**
   - Source problem: logs not produced or not readable.
   - Selection problem: input does not include namespace/container/log type.
   - Filter problem: records dropped or pruned.
   - Routing problem: pipeline points to wrong output.
   - Output problem: endpoint/TLS/auth/network/retry.
   - Query/RBAC problem: logs are stored but user cannot see them.

3. **Check status before logs.**
   - Custom resource status often tells you validation or reconciliation issues.
   - Pod logs tell runtime issues.
   - Metrics tell volume/error/backpressure issues.

4. **Use one known-good test log.**
   - Create a test pod in a known namespace.
   - Emit a unique string.
   - Search that exact string in Loki/output.
   - This removes guessing.

5. **Do not ignore RBAC.**
   - In Logging 6, log collection permissions are explicit.
   - Missing collect roles can break collector deployment.

6. **Treat `Ready=True` carefully.**
   - A `ClusterLogForwarder` can pass API validation but the collector can still fail to connect to Loki or an external endpoint.

7. **Never assume UI absence means collection failure.**
   - Logs might be present in Loki but hidden by tenant, time range, namespace, label, or RBAC.

## 5. Fast Triage Checklist

Use this during an incident.

```bash
# 1. Confirm cluster and namespace
oc whoami
oc project openshift-logging

# 2. Check operators
oc get csv -n openshift-logging
oc get subscription -n openshift-logging
oc get installplan -n openshift-logging

# 3. Check logging CRDs
oc api-resources | egrep -i 'clusterlogforwarder|lokistack|logfile|uiplugin'

# 4. Check ClusterLogForwarder objects
oc get clusterlogforwarder -A
oc get clf -A 2>/dev/null || true

# 5. Describe ClusterLogForwarder
oc describe clusterlogforwarder <name> -n <namespace>
oc get clusterlogforwarder <name> -n <namespace> -o yaml

# 6. Check collector workloads
oc get ds,deploy,pods -n openshift-logging -o wide
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -80

# 7. Check collector logs
oc logs -n openshift-logging <collector-pod> --all-containers --tail=200
oc logs -n openshift-logging <collector-pod> --all-containers --previous --tail=200

# 8. Check service account and RBAC
oc get sa -n openshift-logging
oc get clusterrole | egrep 'collect-.*-logs|logging-collector-logs-writer'
oc auth can-i get pods/log --as=system:serviceaccount:openshift-logging:<collector-sa> -A

# 9. Check LokiStack/output health if using Loki
oc get lokistack -A
oc describe lokistack <name> -n openshift-logging
oc get pods -n openshift-logging | grep -i loki

# 10. Check alerts
oc get prometheusrule -A | grep -i log
oc get servicemonitor -A | grep -i log
```

### First decision tree

```text
Are collector pods missing?
  -> Check CLF validation, RBAC, operator reconciliation, node scheduling.

Collector pods running but logs missing?
  -> Check input selection, filters, source files, collector logs, output errors.

Only one output missing?
  -> Check that output pipeline, auth, TLS, endpoint, network, and format.

Only one namespace/app missing?
  -> Check input includes/excludes, labels, namespace tenant/RBAC, app actually logs.

Logs delayed?
  -> Check output throttling, backpressure, buffer usage, CPU/memory, network latency.

Duplicates?
  -> Check delivery mode, collector restarts, output retry behavior, downstream dedupe.
```

## 6. Version and API Discovery

OpenShift Logging changed significantly across releases. Your first job is to identify which API you are troubleshooting.

### Check OpenShift and Logging versions

```bash
oc version
oc get clusterversion
oc get csv -n openshift-logging
oc get subscription -n openshift-logging -o yaml
```

### Check API group

```bash
oc api-resources | grep -i clusterlogforwarder
```

You may see:

```text
clusterlogforwarders   clf   observability.openshift.io/v1
```

or old style:

```text
clusterlogforwarders   clf   logging.openshift.io/v1
```

### Modern Logging 6 example skeleton

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: collector
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
  pipelines:
  - name: default-pipeline
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

### Legacy Logging 5 style reminder

Legacy examples may use:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
```

Do not mix fields blindly between API groups. Use:

```bash
oc explain clusterlogforwarder.spec --api-version=observability.openshift.io/v1
oc explain clusterlogforwarder.spec.outputs --api-version=observability.openshift.io/v1
oc explain clusterlogforwarder.spec.pipelines --api-version=observability.openshift.io/v1
```

If `oc explain` output does not match your YAML, you are probably using documentation for a different Logging version.

## 7. Operator Health Troubleshooting

Vector is usually deployed and configured by the Red Hat OpenShift Logging Operator. If the operator is unhealthy, the collector may not be reconciled.

### Check CSV

```bash
oc get csv -n openshift-logging
oc describe csv -n openshift-logging $(oc get csv -n openshift-logging -o name | grep -i logging | head -1)
```

Look for:

```text
Phase: Succeeded
Reason: InstallSucceeded
```

Problem signs:

```text
Phase: Failed
InstallCheckFailed
RequirementsNotMet
ImagePullBackOff
```

### Check subscription and install plan

```bash
oc get subscription -n openshift-logging -o wide
oc describe subscription cluster-logging -n openshift-logging
oc get installplan -n openshift-logging
oc describe installplan <installplan-name> -n openshift-logging
```

Common issues:

| Symptom | Likely cause | Fix |
|---|---|---|
| Subscription stuck | install plan requires approval | Approve install plan or set automatic approval |
| CSV failed | missing dependency | Install required operator such as Loki Operator or COO if needed |
| ImagePullBackOff | disconnected registry/mirror issue | Check ImageContentSourcePolicy/ImageDigestMirrorSet, pull secrets |
| Operator pod crash | invalid permissions, bad upgrade, resource issue | Check operator logs and events |

### Check operator pod logs

```bash
oc get pods -n openshift-logging | grep -i logging
oc logs -n openshift-logging deploy/cluster-logging-operator --tail=300
```

If deployment name differs:

```bash
oc get deploy -n openshift-logging
oc logs -n openshift-logging deployment/<operator-deployment-name> --tail=300
```

Look for:

```text
reconcile failed
failed to generate collector config
invalid ClusterLogForwarder
serviceaccount not found
forbidden
cannot create daemonset
secret not found
configmap not found
unsupported output type
```

### Check events

```bash
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -100
```

Events often reveal:

- SCC denial.
- ServiceAccount missing.
- Secret missing.
- ConfigMap invalid.
- Pull secret failure.
- Node scheduling failure.
- DaemonSet update blocked.

## 8. ClusterLogForwarder Troubleshooting

`ClusterLogForwarder` is the main object that tells the Logging Operator what logs to collect, how to process them, and where to send them.

### List all CLFs

```bash
oc get clusterlogforwarder -A
oc get clf -A 2>/dev/null || true
```

### Inspect status

```bash
oc describe clusterlogforwarder <name> -n <namespace>
oc get clusterlogforwarder <name> -n <namespace> -o yaml
```

Check:

```yaml
status:
  conditions:
  - type: Ready
    status: "True"
  - type: Valid
    status: "True"
```

Problem signs:

```yaml
status: "False"
reason: ValidationFailure
message: outputRefs not found
message: filterRefs not found
message: serviceAccount not found
message: secret not found
message: unsupported compression type
```

### Verify names match exactly

Pipeline references are string-based. These mistakes are very common:

```yaml
outputs:
- name: loki-output

pipelines:
- outputRefs:
  - loki-ouput    # typo: missing t
```

Check with:

```bash
oc get clf <name> -n <namespace> -o jsonpath='{.spec.outputs[*].name}{"\n"}'
oc get clf <name> -n <namespace> -o jsonpath='{.spec.pipelines[*].outputRefs}{"\n"}'
oc get clf <name> -n <namespace> -o jsonpath='{.spec.inputs[*].name}{"\n"}'
oc get clf <name> -n <namespace> -o jsonpath='{.spec.pipelines[*].inputRefs}{"\n"}'
```

### Validate inputRefs

Built-in input refs are commonly:

```text
application
infrastructure
audit
```

Custom input names must match `spec.inputs[].name`.

Example mistake:

```yaml
inputs:
- name: app-logs
  application:
    includes:
    - namespace: payment

pipelines:
- name: pipeline1
  inputRefs:
  - application    # collects all application logs, not only app-logs
```

Correct:

```yaml
pipelines:
- name: pipeline1
  inputRefs:
  - app-logs
```

### Validate filter order

Filters are applied in the order referenced by the pipeline.

```yaml
pipelines:
- name: app-pipeline
  inputRefs:
  - application
  filterRefs:
  - drop-debug
  - prune-fields
  outputRefs:
  - loki
```

If a drop filter removes an event, later filters never see it. For production troubleshooting, temporarily remove suspicious filters or create a second pipeline to a test output.

### Check whether CLF generation created collector workload

```bash
oc get ds,deploy,pods -n openshift-logging --show-labels | grep -i collector
```

If CLF is valid but no collector exists:

- Check operator logs.
- Check service account exists.
- Check RBAC bindings.
- Check namespace and API group.
- Check whether management state is unmanaged.
- Check if workload is created in a different namespace for multi-forwarder deployments.

## 9. Collector ServiceAccount and RBAC Troubleshooting

Modern OpenShift Logging requires explicit permissions for the collector service account. Without correct roles, the collector may fail to read logs or write to LokiStack.

### Typical roles

Common roles include:

```text
collect-application-logs
collect-infrastructure-logs
collect-audit-logs
logging-collector-logs-writer
```

Use only the roles needed for the log types and outputs you configure.

### Example service account setup

```bash
oc create sa logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user logging-collector-logs-writer \
  -z logging-collector -n openshift-logging

# Add only if audit logs are collected
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging
```

### Verify service account referenced by CLF

```bash
oc get clf <name> -n <namespace> -o jsonpath='{.spec.serviceAccount.name}{"\n"}'
oc get sa <service-account-name> -n <namespace>
```

### Check cluster role bindings

```bash
oc get clusterrolebinding | egrep 'collect-application-logs|collect-infrastructure-logs|collect-audit-logs|logging-collector-logs-writer'
```

More targeted:

```bash
SA=logging-collector
NS=openshift-logging
oc get clusterrolebinding -o yaml | grep -B5 -A10 "system:serviceaccount:${NS}:${SA}"
```

### Use `oc auth can-i`

```bash
SA=logging-collector
NS=openshift-logging

oc auth can-i get pods/log \
  --as=system:serviceaccount:${NS}:${SA} -A

oc auth can-i get namespaces \
  --as=system:serviceaccount:${NS}:${SA}

oc auth can-i get pods \
  --as=system:serviceaccount:${NS}:${SA} -A
```

For Loki writing, permissions depend on LokiStack tenancy and operator-created roles. Check:

```bash
oc auth can-i create logs \
  --as=system:serviceaccount:${NS}:${SA} -n openshift-logging
```

If this command does not map cleanly in your version, inspect the role:

```bash
oc get clusterrole logging-collector-logs-writer -o yaml
```

### Common RBAC mistakes

| Mistake | Symptom | Fix |
|---|---|---|
| CLF references wrong SA | collector not created or unauthorized | Correct `spec.serviceAccount.name` |
| SA created in wrong namespace | `serviceaccount not found` | Create SA in same namespace as CLF or adjust reference |
| audit input configured without audit role | collector failure / no audit logs | Add `collect-audit-logs` role before enabling audit input |
| writer role missing for LokiStack | collection works but Loki writes fail | Add `logging-collector-logs-writer` |
| binding created to user instead of SA | permissions ineffective | Use `-z <sa> -n <namespace>` |

## 10. Vector DaemonSet and Pod Troubleshooting

Vector typically runs as a collector pod on nodes so it can read node-local log files.

### Check workload distribution

```bash
oc get ds -n openshift-logging -o wide
oc get pods -n openshift-logging -o wide | grep -i collector
oc get nodes
```

Expected:

```text
DESIRED = number of schedulable nodes that match collector scheduling
CURRENT = DESIRED
READY   = DESIRED
AVAILABLE = DESIRED
```

### DaemonSet not scheduling on all nodes

Check:

```bash
oc describe ds <collector-ds> -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -100
```

Common causes:

- Node taints not tolerated.
- Node selector does not match.
- Insufficient CPU/memory.
- SCC/security policy denial.
- Image pull failure.
- HostPath mount restricted.
- ClusterLogForwarder scheduling config excludes nodes.

### Node taint issue

```bash
oc describe node <node> | grep -A5 Taints
```

If infra/master nodes have taints and you need collection there, configure tolerations in the supported CLF/collector scheduling stanza for your version.

### Pod pending

```bash
oc describe pod <collector-pod> -n openshift-logging
```

Look for:

```text
0/6 nodes are available: insufficient memory
node(s) had taint that the pod didn't tolerate
pod has unbound immediate PersistentVolumeClaims
```

### Pod crash looping

```bash
oc logs <collector-pod> -n openshift-logging --all-containers --tail=300
oc logs <collector-pod> -n openshift-logging --all-containers --previous --tail=300
oc describe pod <collector-pod> -n openshift-logging
```

Common crash causes:

- Invalid generated Vector config.
- Secret/CA mount missing.
- File permission issue.
- Unsupported output setting.
- Memory limit too low.
- Collector cannot initialize source/sink.

### Image pull failure

```bash
oc describe pod <collector-pod> -n openshift-logging | egrep -i 'image|pull|backoff|denied|unauthorized'
```

Check disconnected cluster mirrors:

```bash
oc get imagedigestmirrorset
oc get imagecontentsourcepolicy
oc get secret -n openshift-logging
oc get pullsecret -n openshift-config
```

### SCC/security issue

Vector collector needs access to node log paths. If pod is blocked:

```bash
oc describe pod <collector-pod> -n openshift-logging | egrep -i 'scc|security|forbidden|hostpath|privileged'
```

Do not manually bind random privileged SCC unless Red Hat documentation or support directs it. First inspect operator-managed SCC and service account:

```bash
oc get scc | grep -i log
oc get sa <collector-sa> -n openshift-logging -o yaml
oc adm policy who-can use scc/<scc-name>
```

## 11. Generated Vector Configuration Troubleshooting

The Logging Operator converts `ClusterLogForwarder` into a Vector configuration. If behavior does not match the CR, inspect the generated config.

### Find config maps/secrets

```bash
oc get cm -n openshift-logging | grep -i vector
oc get cm -n openshift-logging | grep -i collector
oc get secret -n openshift-logging | grep -i collector
```

### Dump candidate ConfigMaps

```bash
oc get cm -n openshift-logging <configmap-name> -o yaml
```

Inside a collector pod:

```bash
oc rsh -n openshift-logging <collector-pod>
ls -l /etc/vector 2>/dev/null || true
find / -maxdepth 4 -iname '*vector*' 2>/dev/null | head
```

Then inspect likely config paths:

```bash
cat /etc/vector/vector.toml 2>/dev/null || true
cat /etc/vector/vector.yaml 2>/dev/null || true
```

### What to look for in generated config

- Source definitions for application, infrastructure, audit.
- Correct file path includes.
- Kubernetes metadata transform/source.
- Filter transforms matching CLF filters.
- Sink sections for each output.
- TLS settings and CA paths.
- Retry and batch/buffer settings.
- Endpoint URL and protocol.
- Tenant/auth headers for Loki.

### Compare CR to generated config

```bash
oc get clf <name> -n <namespace> -o yaml > /tmp/clf.yaml
oc get cm <collector-configmap> -n openshift-logging -o yaml > /tmp/vector-config.yaml
```

Compare logically:

```text
CLF output name -> Vector sink exists?
CLF input name -> Vector source/transform exists?
CLF filter -> Vector transform exists?
CLF pipeline -> source -> transform -> sink chain exists?
TLS secret -> mounted path exists?
```

### Debug-level logging

Some OpenShift Logging releases support setting collector log level via annotation on `ClusterLogForwarder`. Check your exact API:

```bash
oc explain clusterlogforwarder.metadata.annotations
oc explain clusterlogforwarder.spec --api-version=observability.openshift.io/v1
```

If supported by your version, temporarily increase to debug or trace for one incident window, collect logs, then revert. Avoid leaving trace enabled in production because it can generate heavy logs and expose sensitive operational metadata.

## 12. Log Source Troubleshooting

Vector cannot forward what it cannot read.

### Application container logs

Container runtime logs are usually under node paths such as:

```text

```

## 13. Pipeline, Filter, and Routing Troubleshooting

A `ClusterLogForwarder` pipeline is the route:

```text
inputRefs -> filterRefs -> outputRefs
```

If logs are missing, inspect this chain carefully.

### Basic pipeline example

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: collector
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
  pipelines:
  - name: app-infra-to-loki
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

### Symptom: only one namespace missing

Check includes/excludes:

```bash
oc get clf <name> -n <namespace> -o yaml | sed -n '/inputs:/,/outputs:/p'
```

Example namespace include:

```yaml
inputs:
- name: payment-app
  application:
    includes:
    - namespace: payment
```

If your app is in `payments` but config says `payment`, nothing is collected for that namespace.

### Symptom: labels not matching

Check pod and namespace labels:

```bash
oc get ns <namespace> --show-labels
oc get pods -n <namespace> --show-labels
```

If CLF input selects labels, confirm exact key/value. Label matching is case-sensitive.

### Symptom: logs disappear after adding filter

Temporarily bypass the filter by adding a parallel debug pipeline:

```yaml
pipelines:
- name: app-normal
  inputRefs:
  - application
  filterRefs:
  - drop-noisy
  outputRefs:
  - prod-siem

- name: app-debug-bypass
  inputRefs:
  - application
  outputRefs:
  - debug-loki
```

If `debug-loki` receives logs but `prod-siem` does not, the problem is filter/output-specific.

### Drop filter troubleshooting

Typical mistakes:

- Regex too broad.
- Field path wrong.
- Matching `.message` when actual field is `.message.message` or another structured key.
- Dropping all logs because condition handles missing field incorrectly.

Test with small examples and exact strings.

### Prune filter troubleshooting

Prune filters can break downstream outputs if required fields are removed. Avoid removing these essential fields unless documentation for your output explicitly allows it:

```text
.log_type
.log_source
.message
.hostname
.kubernetes.*
```

For SIEM outputs, keep enough context:

```text
kubernetes.namespace_name
kubernetes.pod_name
kubernetes.container_name
kubernetes.host
level
message
timestamp
```

### Multiline troubleshooting

Multiline logs are common for Java, Python, Go panic traces, and application exceptions.

Common symptoms:

- Stack traces split into many events.
- Multiple exceptions merged into one huge event.
- Downstream rejects large events.
- High memory due to large multiline buffers.

Troubleshooting steps:

1. Confirm multiline filter is actually referenced by pipeline.
2. Test pattern using a known sample log.
3. Check output `maxWrite` or downstream payload size limit.
4. Watch collector memory.
5. Check for logs without expected start pattern causing unbounded grouping.

## 16. TLS, CA, and Certificate Troubleshooting

TLS is one of the most common causes of “CLF Ready but no logs arrive.” API validation can succeed even if runtime TLS cannot connect.

### Common TLS errors

```text
certificate signed by unknown authority
x509: certificate is valid for X, not Y
certificate has expired or is not yet valid
tls: failed to verify certificate
remote error: tls: bad certificate
handshake failure
unknown ca
```

### Check secret exists

```bash
oc get secret -n <clf-namespace>
oc describe secret <secret-name> -n <clf-namespace>
```

### Check expected keys

Common key names:

```text
ca-bundle.crt
tls.crt
tls.key
username
password
token
```

Exact keys depend on output type and CLF spec.

```bash
oc get secret <secret-name> -n <namespace> -o jsonpath='{.data}'
```

Decode CA/cert:

```bash
oc get secret <secret-name> -n <namespace> -o jsonpath='{.data.ca-bundle\.crt}' | base64 -d > /tmp/ca.crt
openssl x509 -in /tmp/ca.crt -noout -subject -issuer -dates
```

For client cert:

```bash
oc get secret <secret-name> -n <namespace> -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/tls.crt
openssl x509 -in /tmp/tls.crt -noout -subject -issuer -dates -ext subjectAltName
```

### Check endpoint certificate SAN

From a debug pod or admin host:

```bash
openssl s_client -connect <host>:<port> -servername <host> -showcerts </dev/null
```

Check:

- Certificate chain is complete.
- CA matches configured CA.
- SAN includes the exact hostname used in CLF URL.
- Certificate is not expired.
- Intermediate CA is included if required.

### Hostname mismatch example

CLF output:

```yaml
url: https://logs.example.com:443/ingest
```

Certificate SAN:

```text
DNS:siem.internal.example.com
```

This fails because `logs.example.com` is not in SAN. Fix by:

- Using the SAN hostname in URL, or
- Reissuing certificate with correct SAN, or
- Configuring a proper ingress/LB certificate.

Do not disable TLS verification in production unless explicitly approved and documented as a temporary emergency workaround.

## 18. Buffer, Backpressure, and Delivery Troubleshooting

Vector has to handle output failures and downstream slowness. When output is slow, backpressure starts. Depending on delivery mode and buffer settings, this can lead to delay, disk use, duplicates, or dropped logs.

### Delivery modes

Common tuning concept:

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    tuning:
      deliveryMode: AtLeastOnce
      compression: gzip
      maxWrite: 10M
      minRetryDuration: 5s
      maxRetryDuration: 20s
```

Conceptually:

| Mode | Meaning | Trade-off |
|---|---|---|
| `AtLeastOnce` | tries to resend logs after crash/restart if already read but not delivered | better durability, possible duplicates |
| `AtMostOnce` | does not try to recover logs lost during crash | higher throughput, possible log loss |

### Backpressure symptoms

- Logs arrive late.
- Collector CPU high.
- Collector memory high.
- Collector filesystem usage grows.
- Output errors increase.
- Alerts fire for collector error rate or disk/buffer usage.
- Downstream shows 429/503.

### Check collector pod resource usage

```bash
oc adm top pod -n openshift-logging
oc adm top pod -n openshift-logging --containers
oc adm top node
```

### Check node disk

```bash
oc debug node/<node>
chroot /host
df -h
find /var/lib -maxdepth 3 -type d -iname '*vector*' -print
find /var/lib -maxdepth 4 -type f -size +100M 2>/dev/null | head
```

Exact buffer paths are version/config dependent. Use `find` carefully; avoid expensive full filesystem scans on production nodes during incidents.

### Check collector logs for backpressure

```bash
oc logs -n openshift-logging <collector-pod> --all-containers --tail=1000 | \
  egrep -i 'backpressure|buffer|retry|rate|dropped|discard|throttle|429|503|timeout|failed to send'
```

### Downstream throttling patterns

| Output response | Meaning | Action |
|---|---|---|
| 429 | rate limited | reduce log volume, increase downstream limit, tune batch/retry |
| 413 | payload too large | reduce `maxWrite`, split multiline, reduce batch size |
| 500/503 | downstream unavailable | fix output, expect retry/backpressure |
| timeout | network/downstream slow | check latency/firewall/load balancer |
| connection reset | LB/proxy/server closing | tune keepalive/LB timeout or endpoint capacity |

### Reduce log pressure quickly

During an incident, reduce volume safely:

1. Exclude noisy namespaces temporarily.
2. Drop known noisy debug messages.
3. Stop forwarding infra logs to external SIEM if not required.
4. Keep audit logs if compliance requires them.
5. Add resource requests/limits if collector is CPU throttled.
6. Scale downstream capacity.
7. Adjust delivery/tuning only after understanding durability requirements.

Example temporary drop filter concept:

```yaml
filters:
- name: drop-healthz
  type: drop
  drop:
  - test:
    - field: .message
      matches: ".*healthz.*"
```

Validate syntax with `oc explain` for your version before applying.

## 19. Performance and Resource Troubleshooting

Vector is efficient, but high log volume can still overload CPU, memory, disk, network, or downstream services.

### Key questions

- How many nodes are collecting logs?
- Which namespaces generate most logs?
- Are logs mostly small lines or huge stack traces?
- Are filters expensive?
- Is multiline enabled?
- Is output compressed?
- Is downstream slow or rate-limiting?
- Is collector CPU throttled?
- Are node disks near full?

### Check CPU/memory

```bash
oc adm top pod -n openshift-logging --containers
oc adm top node
```

Check pod limits:

```bash
oc get pod <collector-pod> -n openshift-logging -o jsonpath='{.spec.containers[*].resources}{"\n"}'
oc describe pod <collector-pod> -n openshift-logging | sed -n '/Containers:/,/Conditions:/p'
```

### CPU throttling check through PromQL

In OpenShift console Observe > Metrics:

```promql
rate(container_cpu_cfs_throttled_seconds_total{namespace="openshift-logging"}[5m])
```

Or by pod:

```promql
sum by (pod, container) (rate(container_cpu_usage_seconds_total{namespace="openshift-logging"}[5m]))
```

### Memory pressure

```promql
container_memory_working_set_bytes{namespace="openshift-logging"}
```

If pods OOM:

```bash
oc describe pod <collector-pod> -n openshift-logging | egrep -i 'oom|killed|reason|exit code'
oc logs <collector-pod> -n openshift-logging --previous --all-containers --tail=200
```

### High log volume sources

Use LogFileMetricExporter if deployed, or check top talkers through Loki queries/metrics. A practical manual method:

```bash
oc adm top pod -A | sort -k3 -h | tail
```

For app-level log volume, look for noisy deployments:

```bash
for ns in $(oc get ns -o jsonpath='{.items[*].metadata.name}'); do
  oc get pods -n $ns --no-headers 2>/dev/null | wc -l | xargs echo $ns
 done
```

This counts pods, not log volume, but helps start investigation.

### Performance best practices

- Avoid forwarding all application logs to all outputs unless required.
- Use namespace/pod selection to reduce unnecessary volume.
- Avoid expensive filters on high-volume streams.
- Keep multiline patterns precise.
- Use compression for network-heavy outputs if CPU allows.
- Tune `maxWrite` to match downstream payload limits.
- Avoid very high-cardinality labels in Loki.
- Do not use logging as a substitute for application metrics/traces.

## 23. Common Error Messages and Meaning

### `certificate signed by unknown authority`

Meaning:

- Collector does not trust output certificate.

Fix:

- Add correct CA bundle in secret.
- Reference it properly in CLF output TLS section.
- Ensure intermediate CA is included.

### `x509: certificate is valid for X, not Y`

Meaning:

- URL hostname does not match certificate SAN.

Fix:

- Use correct hostname or reissue certificate.

### `401 Unauthorized`

Meaning:

- Missing/wrong token, username/password, or auth header.

Fix:

- Check secret keys, service account token, output auth config.

### `403 Forbidden`

Meaning:

- Auth succeeded but lacks permission.

Fix:

- Check Loki writer role, Kafka ACL, Splunk token index permission, SIEM authorization.

### `429 Too Many Requests`

Meaning:

- Downstream throttling/rate limiting.

Fix:

- Reduce log rate, tune batching/retry, increase downstream quota/capacity.

### `413 Payload Too Large`

Meaning:

- Batch/event exceeds output limit.

Fix:

- Reduce `maxWrite`, reduce multiline event size, reduce batch size, tune downstream limit.

### `connection refused`

Meaning:

- Host reachable but port closed or service not listening.

Fix:

- Check port, endpoint, service, firewall, target listener.

### `no such host`

Meaning:

- DNS resolution failed.

Fix:

- Check DNS, proxy, service name, CoreDNS, search domains.

### `i/o timeout`

Meaning:

- Network path blocked or target not responding.

Fix:

- Check firewall, route, NetworkPolicy, proxy, endpoint health.

### `outputRefs not found`

Meaning:

- Pipeline references missing output name.

Fix:

- Correct output name in `outputRefs`.

### `filterRefs not found`

Meaning:

- Pipeline references missing filter name.

Fix:

- Correct `filterRefs` or define filter.

### `serviceaccount not found`

Meaning:

- CLF references a missing SA.

Fix:

- Create SA in CLF namespace or correct name.

### `forbidden: User system:serviceaccount... cannot ...`

Meaning:

- Collector SA lacks permission.

Fix:

- Add required cluster role binding.

## 24. Production Incident Runbooks

### Runbook 1: No logs visible anywhere

```text
Goal: Find whether collection, forwarding, storage, or UI is broken.
```

Commands:

```bash
oc get csv -n openshift-logging
oc get clf -A
oc describe clf <name> -n <namespace>
oc get pods -n openshift-logging -o wide
oc logs -n openshift-logging <collector-pod> --all-containers --tail=300

```

Decision:

- No collector pods -> operator/CLF/RBAC/scheduling issue.
- Collector pods crash -> config/secret/TLS/resource issue.
- Collector logs show output errors -> output/network/TLS/auth issue.
- Collector healthy and Loki healthy -> UI/query/RBAC/time range issue.

### Runbook 2: Only one namespace missing

```bash
NS=payment
oc logs -n $NS deploy/<deploy-name> --tail=20
oc get ns $NS --show-labels
oc get pods -n $NS --show-labels
oc get clf <name> -n <namespace> -o yaml | sed -n '/inputs:/,/outputs:/p'
oc get clf <name> -n <namespace> -o yaml | sed -n '/filters:/,/pipelines:/p'
```

Check:

- Namespace included?
- Namespace excluded?
- Label selector correct?
- Container name correct?
- Drop filter matching?
- User has RBAC to view namespace logs?

### Runbook 3: Loki logs missing but external SIEM receives logs

This means source and collector mostly work. Focus on Loki output.

```bash
oc get clf <name> -n <namespace> -o yaml | grep -A40 -i loki
oc describe lokistack <name> -n openshift-logging
oc logs -n openshift-logging <collector-pod> --all-containers --tail=500 | egrep -i 'loki|401|403|429|500|503|tls|timeout'
oc get clusterrolebinding -o yaml | grep -B5 -A10 logging-collector-logs-writer
```

Likely causes:

- Loki writer RBAC missing.
- Wrong LokiStack target name/namespace.
- TLS CA missing.
- LokiStack not ready.
- Tenant/RBAC/UI issue.

### Runbook 4: External SIEM missing but Loki receives logs

This means collector source and app pipeline probably work. Focus on external output.

```bash
oc get clf <name> -n <namespace> -o yaml | sed -n '/outputs:/,/pipelines:/p'
oc logs -n openshift-logging <collector-pod> --all-containers --tail=1000 | \
  egrep -i 'siem|http|syslog|kafka|splunk|error|retry|tls|timeout|401|403|429|413'
```

Test network:

```bash
oc run -n openshift-logging net-debug --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside:

```bash
getent hosts <siem-host>
bash -c '</dev/tcp/<siem-host>/<port>' && echo OK || echo FAIL
```

Likely causes:

- Firewall.
- DNS.
- TLS CA.
- Auth token.
- SIEM endpoint path.
- Payload too large.
- Rate limiting.

### Runbook 5: CollectorHighErrorRate firing

```bash
oc get alerts -A 2>/dev/null || true
oc get pods -n openshift-logging -o wide | grep -i collector
oc logs -n openshift-logging <collector-pod> --all-containers --tail=1500 > /tmp/collector.log
cat /tmp/collector.log | egrep -i 'error|failed|retry|dropped|discard|tls|timeout|429|503|401|403|413' | tail -100
oc adm top pod -n openshift-logging --containers
```

Classify error:

| Error family | Next step |
|---|---|
| TLS | Check CA/SAN/secret |
| 401/403 | Check auth/RBAC/secret |
| 429 | Rate limit/backpressure |
| 413 | Payload too large |
| timeout | Network/output capacity |
| config parse | CLF/generated config |
| OOM/restart | Resource tuning/log volume |

### Runbook 6: Logs delayed by minutes/hours

```bash
oc adm top pod -n openshift-logging --containers
oc logs -n openshift-logging <collector-pod> --all-containers --tail=1000 | \
  egrep -i 'buffer|backpressure|retry|429|timeout|rate|throttle'
```

Check downstream:

- Loki distributor/ingester health.
- Kafka broker lag/throttle.
- SIEM ingestion status.
- HTTP endpoint response times.

Mitigation:

1. Reduce noisy logs.
2. Increase collector CPU/memory if throttled.
3. Fix downstream capacity.
4. Tune retry/batch/compression.
5. Decide whether durability or throughput is more important.

### Runbook 7: Duplicate logs after collector restart

Likely expected with at-least-once delivery during crash/retry. Confirm:

```bash
oc get clf <name> -n <namespace> -o yaml | grep -A10 tuning
oc get pods -n openshift-logging | grep -i collector
oc get events -n openshift-logging --sort-by=.lastTimestamp | grep -i collector | tail
```

If duplicates are unacceptable:

- Consider downstream deduplication.
- Use unique event IDs if app can provide them.
- Discuss trade-off before changing delivery to at-most-once.

## 25. Deep-Dive Scenarios

### Scenario A: `ClusterLogForwarder` Ready=True but no logs in Loki

Possible because CR validation checks object syntax, not every runtime connection.

Steps:

```bash
oc describe clf <name> -n <namespace>
oc get pods -n openshift-logging -o wide | grep -i collector
oc logs -n openshift-logging <collector-pod> --all-containers --tail=500 | egrep -i 'loki|tls|error|warn|retry|401|403|429|503|timeout'
oc describe lokistack <name> -n openshift-logging
oc get svc -n openshift-logging | grep -i loki
```

Likely root causes:

- Missing Loki TLS CA.
- Wrong LokiStack target name/namespace.
- `logging-collector-logs-writer` role missing.
- LokiStack not ready.
- NetworkPolicy blocking collector-to-Loki traffic.
- UIPlugin not connected to LokiStack.
- Querying wrong tenant/time range.

### Scenario B: Audit logs broke entire collector deployment

In Logging 6, missing RBAC for a configured input can cause severe collector failure.

Steps:

```bash
oc get clf <name> -n <namespace> -o yaml | grep -A30 audit
oc get clusterrolebinding -o yaml | grep -B5 -A10 collect-audit-logs
oc logs -n openshift-logging deployment/cluster-logging-operator --tail=300
oc get ds,pods -n openshift-logging
```

Fix:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z <collector-sa> -n <clf-namespace>
```

Then let operator reconcile:

```bash
oc get pods -n openshift-logging -w
```

### Scenario C: External syslog receives quoted messages after Fluentd-to-Vector migration

Symptoms:

- SIEM parser worked with Fluentd.
- After migrating to Vector, syslog message format differs.
- Events reach syslog but parsing fails.

Troubleshooting:

```bash
oc logs -n openshift-logging <collector-pod> --all-containers --tail=300 | grep -i syslog
```

Actions:

- Check syslog RFC/enrichment fields supported by your CLF version.
- Adjust downstream parser.
- Create a test pipeline to validate message format.
- Avoid assuming Fluentd and Vector serialize exactly the same.

### Scenario D: High collector memory during Java stack traces

Likely causes:

- Multiline merging too much.
- Very large exception events.
- Output slow, buffers growing.
- Downstream 413 or 429.

Steps:

```bash
oc adm top pod -n openshift-logging --containers
oc logs -n openshift-logging <collector-pod> --all-containers --tail=1000 | egrep -i 'multiline|buffer|413|429|memory|dropped|retry'
oc get clf <name> -n <namespace> -o yaml | grep -A80 -i multiline
```

Fix options:

- Tighten multiline start pattern.
- Limit noisy namespace logs.
- Reduce output batch size.
- Increase collector memory only after reducing avoidable noise.
- Fix downstream payload limits.

### Scenario E: Application logs visible to cluster-admin but not developer

This is likely not Vector. It is RBAC/tenant/query behavior.

Check:

```bash
oc auth can-i get pods/log -n <namespace> --as=<developer-user>
oc auth can-i view loki logs -n <namespace> --as=<developer-user> 2>/dev/null || true
oc get rolebinding -n <namespace>
oc get clusterrolebinding | grep <developer-user>
```

Fix:

- Grant appropriate project role such as `view` if policy allows.
- Verify console selected correct project/time range.
- Confirm logs are under application tenant.

### Scenario F: Collector pods run only on workers, not masters/control-plane nodes

If infra/audit/control-plane logs are needed, check taints and tolerations.

```bash
oc get nodes -o wide
oc describe node <master-node> | grep -A5 Taints
oc describe ds <collector-ds> -n openshift-logging | grep -A20 Tolerations
```

Fix:

- Configure collector tolerations/scheduling using the supported CLF fields for your Logging version.
- Do not patch operator-managed DaemonSet directly unless emergency and documented; operator may revert it.

## 27. Best Practices

### Configuration best practices

- Use one clear `ClusterLogForwarder` per responsibility where supported.
- Keep input, filter, output, and pipeline names simple and consistent.
- Document every filter and why it exists.
- Keep audit pipelines separate from application pipelines where possible.
- Use namespace/container includes to reduce noise.
- Avoid broad regex drop filters without testing.
- Keep source, filter, and output changes in Git.
- Use controlled rollout windows for logging changes.

### RBAC best practices

- Create a dedicated collector service account.
- Bind only required collect roles.
- Add `collect-audit-logs` only if collecting audit logs.
- Review role bindings after upgrades.
- Do not use cluster-admin as collector service account.

### TLS best practices

- Use CA bundles, not `insecureSkipVerify`, in production.
- Monitor certificate expiry.
- Ensure SAN matches CLF URL hostname.
- Include intermediate CA if needed.
- Store secrets in the same namespace expected by CLF.

### Performance best practices

- Keep log volume under control at application level.
- Do not log high-cardinality noisy debug data in production.
- Avoid forwarding all logs to all destinations.
- Use compression where network is bottleneck and CPU headroom exists.
- Tune batch size for downstream limits.
- Watch collector CPU/memory after enabling multiline or complex filters.

### Operations best practices

- Create a known-good log generator namespace for testing.
- Keep runbooks for Loki, Kafka, syslog, and SIEM outputs.
- Monitor collector alerts and downstream ingestion metrics.
- Test logging after OpenShift upgrades.
- Test certificate renewal before expiry.
- Keep a rollback copy of last known-good CLF YAML.

## 28. Interview and Real-World Troubleshooting Questions

### Q1. `ClusterLogForwarder` is Ready=True, but no logs appear in Loki. What do you check?

Answer:

- Collector pod logs for Loki/TLS/auth errors.
- LokiStack Ready condition.
- Loki services and pods.
- Collector service account writer role.
- TLS CA configuration.
- NetworkPolicy between collector and Loki.
- Console time range, tenant, namespace, and RBAC.

### Q2. Why might `AtLeastOnce` delivery cause duplicate logs?

Answer:

Because if Vector reads logs and crashes/restarts before confirming delivery, it can resend records to avoid loss. This improves durability but can produce duplicates. Downstream deduplication may be needed for strict audit/analytics use cases.

### Q3. What happens if you configure audit input without audit RBAC?

Answer:

The collector service account lacks permission to read audit logs. In modern Logging versions, required collect roles must be bound before adding corresponding input types. Missing roles can prevent successful collector deployment or cause collection failure.

### Q4. Application logs are visible with `oc logs`, but not in SIEM. Why?

Answer:

Possible reasons include:

- CLF input does not include namespace/container.
- Filter drops them.
- Pipeline does not route to SIEM output.
- SIEM output has TLS/auth/network error.
- SIEM rejects payload due to schema or size.
- Downstream parser fails even though events arrive.

### Q5. How do you prove whether problem is source, collector, or output?

Answer:

Generate a unique test log, verify with `oc logs`, check collector pod logs/metrics, and then search the exact string in each output. If it exists in pod logs but not collector output, source/selection/filter is suspect. If it reaches Loki but not SIEM, external output is suspect.

### Q6. What is the biggest migration gotcha from Fluentd to Vector?

Answer:

Assuming behavior and output formatting are identical. Vector has different configuration generation, metrics, buffering behavior, and can serialize some outputs differently. Downstream parsers and filters should be tested.

## Final Senior Admin Summary

Vector troubleshooting in OpenShift Logging is not only about checking collector pod logs. The correct production method is to trace the log event path from source to output:

```text
pod stdout/stderr
  -> node log file
  -> Vector source
  -> metadata enrichment
  -> CLF input selection
  -> filters/transforms
  -> pipeline route
  -> output sink
  -> downstream storage/SIEM
  -> UI/query/RBAC
```

Most real incidents fall into one of these buckets:

1. **RBAC missing** for application, infrastructure, audit, or Loki writer access.
2. **CLF reference mismatch** in input/filter/output names.
3. **TLS/CA/hostname problem** with Loki or external output.
4. **Network or DNS block** from collector pods/nodes to output.
5. **Downstream throttling** causing retry, buffer growth, and delayed logs.
6. **Filter/selector mistake** silently dropping expected logs.
7. **Resource pressure** from high log volume, multiline events, or slow outputs.
8. **UI/RBAC confusion** where logs exist but are not visible to the user.

A good OpenShift administrator proves each layer with commands, metrics, and a known test log. A great administrator prevents repeat incidents by controlling log volume, validating CLF changes, monitoring collector alerts, testing external outputs, and documenting every pipeline and filter.
