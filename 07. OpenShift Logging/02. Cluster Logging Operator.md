## 1. Executive Summary

The **Cluster Logging Operator**, now documented as the **Red Hat OpenShift Logging Operator**, is the OpenShift operator responsible for managing **log collection and log forwarding**. In current Logging 6.x architecture, it does **not** manage Elasticsearch, Kibana, or the logging UI. Its primary job is to watch the `ClusterLogForwarder` custom resource and reconcile the required collector workload, usually a **Vector-based DaemonSet**, so logs can be collected from each node and forwarded to one or more destinations.

In a production OpenShift cluster, you should think of the operator as the control plane for the logging pipeline:

```text
Pods / Nodes / Audit files
        |
        v
Vector collector DaemonSet, managed by Red Hat OpenShift Logging Operator
        |
        v
ClusterLogForwarder pipelines: inputs -> filters -> outputs
        |
        +--> LokiStack, managed by Loki Operator
        +--> Splunk / Kafka / Elasticsearch / HTTP / Syslog / S3 / CloudWatch / other supported outputs
```

A 10-year experienced administrator should not treat logging as a simple "install operator and check logs" task. The real work is:

- designing log routing for developers, SREs, and security teams;
- granting the correct RBAC before enabling each log type;
- preventing high-volume workloads from overwhelming storage;
- separating short-term troubleshooting logs from long-term compliance logs;
- understanding operator reconciliation so manual changes are not overwritten;
- troubleshooting collector readiness, TLS, output authentication, rate limiting, and missing logs.

## 2. Naming: Cluster Logging Operator vs Red Hat OpenShift Logging Operator

In many clusters, commands and deployment names still use the older naming style:

```bash
oc get deployment -n openshift-logging cluster-logging-operator
oc get csv -n openshift-logging
```

In current documentation and OperatorHub, the product is referred to as:

```text
Red Hat OpenShift Logging Operator
```

The operator subscription is usually named:

```text
cluster-logging
```

The deployment is commonly:

```text
cluster-logging-operator
```

So, in real support cases, these names are often used interchangeably:

| Term | Meaning |
|---|---|
| Cluster Logging Operator | Common/legacy operational name |
| Red Hat OpenShift Logging Operator | Current product/operator name |
| `cluster-logging-operator` | Operator deployment name in `openshift-logging` |
| `cluster-logging` | Common Subscription/CSV identity |
| CLO | Common shorthand for Cluster Logging Operator |

Important: in Logging 6.x, the operator manages **collection and forwarding**, not the full old Elasticsearch/Kibana stack.

## 3. OpenShift Logging Architecture

Modern OpenShift Logging is split across distinct responsibilities.

### 3.1 Main components

| Component | Managed by | Purpose |
|---|---|---|
| Vector collector | Red Hat OpenShift Logging Operator | Collects logs from nodes and forwards them |
| `ClusterLogForwarder` | Red Hat OpenShift Logging Operator | Defines inputs, filters, outputs, and pipelines |
| LokiStack | Loki Operator | In-cluster log storage and multi-tenant query layer |
| Logging UI plugin | Cluster Observability Operator | Adds log visualization to OpenShift web console |
| External log stores | External systems / admins | Splunk, Kafka, Elasticsearch, S3, CloudWatch, etc. |

### 3.2 Full architecture flow

```text
+--------------------------------------------------------------+
|                      OpenShift Cluster                        |
|                                                              |
|  +-------------------+        +----------------------------+  |
|  | Application Pods  |        | OpenShift / kube services   |  |
|  | stdout / stderr   |        | node + infra logs           |  |
|  +---------+---------+        +--------------+-------------+  |
|            |                                 |                |
|            | container log files             | journal/files   |
|            v                                 v                |
|  +--------------------------------------------------------+   |
|  | Vector collector DaemonSet                             |   |
|  | - one pod per node                                     |   |
|  | - reads application, infrastructure, audit logs         |   |
|  | - normalizes records                                   |   |
|  | - applies filters/rate limits                          |   |
|  +-------------------------+------------------------------+   |
|                            |                                  |
|                            v                                  |
|  +--------------------------------------------------------+   |
|  | ClusterLogForwarder CR                                 |   |
|  | inputs -> filters -> outputs                           |   |
|  +------------+-------------------+-----------------------+   |
|               |                   |                           |
|               v                   v                           |
|        +-------------+      +-------------+                    |
|        | LokiStack   |      | External SIEM|                   |
|        | short-term  |      | Splunk/Kafka |                   |
|        +-------------+      +-------------+                    |
+--------------------------------------------------------------+
```

### 3.3 Why this split matters

Older administrators often expect one operator to deploy everything: collector, Elasticsearch, Kibana, Curator, and dashboards. That was closer to the older Logging 4.x/5.x mental model. Modern Logging 6.x separates responsibilities:

- **Logging Operator:** collection and forwarding.
- **Loki Operator:** log storage.
- **Cluster Observability Operator:** visualization.

This split improves lifecycle management but requires administrators to know which operator owns which failure domain.

## 4. What the Operator Actually Does

The Red Hat OpenShift Logging Operator performs reconciliation. It watches supported logging custom resources and ensures the actual cluster objects match the desired state.

### 4.1 Primary responsibilities

The operator manages:

- collector DaemonSet generation;
- collector configuration generation;
- collector ServiceAccount usage;
- RBAC validation for requested log inputs;
- input, filter, output, and pipeline validation;
- TLS and authentication references for outputs;
- collector restarts when configuration changes;
- status conditions on `ClusterLogForwarder`;
- metrics and health signals used by OpenShift Monitoring;
- safe removal of the collector when authorization or validation fails.

### 4.2 What it does not manage in Logging 6.x

The operator does not own:

- Loki storage pods and object storage configuration;
- LokiStack schema and retention;
- OpenShift web console logging UI plugin;
- external Splunk/Kafka/Elasticsearch/S3 systems;
- arbitrary custom Vector configuration;
- unsupported manual modification of the generated collector DaemonSet.

If you manually edit the collector DaemonSet or generated config, the operator can revert your changes during reconciliation.

## 5. Logging 5.x vs Logging 6.x Architecture Change

This is one of the most important advanced topics because many production clusters were installed before Logging 6.x.

### 5.1 Logging 5.x model

Typical Logging 5.x resources:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogging
metadata:
  name: instance
  namespace: openshift-logging
```

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
```

Older model characteristics:

- `ClusterLogging` controlled collector, log store, and visualization choices.
- Fluentd was historically used as a collector.
- Elasticsearch and Kibana existed in many deployments.
- Vector became the recommended/supported collector before Logging 6.x.
- Elasticsearch, Kibana, and Fluentd were deprecated before their removal from the modern stack.

### 5.2 Logging 6.x model

Modern resource:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
```

Logging 6.x characteristics:

- `ClusterLogging` and old `ClusterLogForwarder.logging.openshift.io` concepts are replaced by the new `ClusterLogForwarder.observability.openshift.io` API.
- Vector is the supported collector implementation.
- LokiStack is the supported Red Hat-managed in-cluster log store.
- Elasticsearch and Kibana are not the managed OpenShift Logging storage/visualization path in Logging 6.x.
- UI visualization is handled through Cluster Observability Operator and the logging UI plugin.

### 5.3 Practical upgrade impact

During upgrade/migration, you must check for old resources:

```bash
oc get clusterlogging -A
oc get clusterlogforwarder.logging.openshift.io -A
oc get clusterlogforwarder.observability.openshift.io -A
oc get elasticsearch -n openshift-logging
oc get kibana -n openshift-logging
```

A production migration should include:

1. inventory of old collector, store, and forwarding resources;
2. confirmation that Fluentd is no longer used;
3. migration of storage from Elasticsearch to LokiStack or external destination;
4. migration of forwarding rules to the new API;
5. validation of collector RBAC for every log type;
6. deletion of old resources only after the new collector is healthy.

Never delete old logging resources blindly in a live production cluster. First confirm that new pipelines are forwarding all required log types.

## 8. Collector ServiceAccount and RBAC Model

This is one of the most common places where advanced administrators make mistakes.

### 8.1 Why the ServiceAccount matters

The collector pod reads sensitive log data from nodes and cluster components. OpenShift protects this with RBAC. The `ClusterLogForwarder` must reference a ServiceAccount:

```yaml
spec:
  serviceAccount:
    name: logging-collector
```

That ServiceAccount must have permission for every log type included in `inputRefs`.

### 8.2 Create collector ServiceAccount

```bash
oc create sa logging-collector -n openshift-logging
```

### 8.3 Grant permissions for application and infrastructure logs

```bash
oc adm policy add-cluster-role-to-user logging-collector-logs-writer \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  -z logging-collector -n openshift-logging
```

### 8.4 Grant audit log permissions only when required

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging
```

Audit logs are highly sensitive and can be high-volume. In many enterprises, audit logs should be forwarded to a security-controlled destination instead of developer-facing storage.

### 8.5 Verify RBAC

```bash
oc get clusterrolebinding -o wide | egrep 'logging-collector|collect-application|collect-infrastructure|collect-audit|logs-writer'
```

### 8.6 Critical sequencing rule

Grant RBAC **before** adding the log type to `ClusterLogForwarder`.

Wrong sequence:

```text
Add audit to ClusterLogForwarder -> no collect-audit-logs binding -> collector removed/fails
```

Correct sequence:

```text
Grant collect-audit-logs -> update ClusterLogForwarder inputRefs -> verify Authorized=True
```

## 9. ClusterLogForwarder Deep Dive

`ClusterLogForwarder` is the central desired-state object for log routing.

### 9.1 Basic structure

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  inputs: []
  filters: []
  outputs: []
  pipelines: []
```

### 9.2 Key concepts

| Section | Meaning |
|---|---|
| `serviceAccount` | Identity used by collector pods |
| `inputs` | What logs to collect |
| `filters` | What to drop, prune, parse, label, or transform |
| `outputs` | Where logs go |
| `pipelines` | How inputs connect to filters and outputs |

### 9.3 Pipeline mental model

```text
inputRefs -> filterRefs -> outputRefs
```

Example:

```yaml
pipelines:
- name: app-to-loki
  inputRefs:
  - application
  filterRefs:
  - drop-debug
  outputRefs:
  - default-lokistack
```

This means:

```text
collect application logs -> drop debug logs -> send remaining records to LokiStack
```

### 9.4 Full production-style example

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector

  inputs:
  - name: production-apps
    type: application
    application:
      includes:
      - namespace: production
      tuning:
        rateLimitPerContainer:
          maxRecordsPerSecond: 500

  filters:
  - name: drop-debug
    type: drop
    drop:
    - test:
      - field: .level
        matches: debug

  - name: prune-sensitive-audit-fields
    type: prune
    prune:
      in:
      - .audit.requestObject
      - .audit.responseObject
      - .audit.managedFields

  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt

  - name: security-s3
    type: s3
    s3:
      url: https://s3.example.com/audit-logs
      authentication:
        accessKey:
          key: access_key_id
          secretName: audit-s3-secret
        secretKey:
          key: access_key_secret
          secretName: audit-s3-secret

  pipelines:
  - name: production-apps-to-loki
    inputRefs:
    - production-apps
    filterRefs:
    - drop-debug
    outputRefs:
    - default-lokistack

  - name: infrastructure-to-loki
    inputRefs:
    - infrastructure
    outputRefs:
    - default-lokistack

  - name: audit-to-security-archive
    inputRefs:
    - audit
    filterRefs:
    - prune-sensitive-audit-fields
    outputRefs:
    - security-s3
```

### 9.5 Status conditions

Check readiness:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Important conditions:

| Condition | Expected | Meaning |
|---|---|---|
| `observability.openshift.io/Authorized` | `True` | ServiceAccount has RBAC for requested log types |
| `observability.openshift.io/Valid` | `True` | CR passes schema and semantic validation |
| `Ready` | `True` | Operator can reconcile resources for collector deployment |

If `Authorized=False`, check RBAC first. If `Valid=False`, check YAML structure, output type, missing secrets, invalid references, unsupported field combinations, or API version mismatch.

## 10. Collector Runtime: Vector DaemonSet

### 10.1 Why DaemonSet?

A collector must run on every node because container log files and some node-level log sources are node-local. A Deployment would not guarantee per-node collection.

```text
worker-1 -> collector pod reads worker-1 logs
worker-2 -> collector pod reads worker-2 logs
master-1 -> collector pod reads master-1 infrastructure/audit sources, if scheduled and authorized
```

### 10.2 Verify collector pods

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc get ds -n openshift-logging
```

Expected:

```text
one collector pod per schedulable node selected by the operator configuration
```

### 10.3 Collector log checks

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

For a specific pod:

```bash
POD=$(oc get pod -n openshift-logging -l app.kubernetes.io/component=collector -o jsonpath='{.items[0].metadata.name}')
oc logs -n openshift-logging "$POD" --tail=100
```

### 10.4 Collector responsibilities

The collector:

- tails container log files;
- reads infrastructure log sources;
- reads audit sources when authorized and configured;
- normalizes log records;
- enriches records with Kubernetes metadata;
- applies configured filters;
- handles TLS and authentication to outputs;
- buffers and retries where supported;
- exposes operational metrics.

### 10.5 Checkpoints

Collectors maintain checkpoints so they know how far they have read from log files. During migrations or path changes, incorrect checkpoint handling can cause duplicate log processing or gaps. In upgrades, always review Red Hat guidance for Vector checkpoint migration.

## 11. Log Types: Application, Infrastructure, Audit

### 11.1 Application logs

Application logs come from user workloads. These are usually pod stdout/stderr logs from non-infrastructure namespaces.

Use cases:

- developer troubleshooting;
- application error tracking;
- SRE incident analysis;
- business transaction debugging.

Reserved input:

```yaml
inputRefs:
- application
```

Custom application input:

```yaml
inputs:
- name: payment-apps
  type: application
  application:
    includes:
    - namespace: payments
```

### 11.2 Infrastructure logs

Infrastructure logs include logs from OpenShift and Kubernetes components, node services, and system namespaces.

Reserved input:

```yaml
inputRefs:
- infrastructure
```

Use cases:

- cluster operator troubleshooting;
- kubelet or CRI-O issues;
- SDN/OVN diagnostics;
- control plane incident review.

### 11.3 Audit logs

Audit logs are security-sensitive API audit records.

Reserved input:

```yaml
inputRefs:
- audit
```

Use cases:

- compliance;
- investigation of privileged activity;
- change tracking;
- identity and authorization analysis.

Operational warning:

- Audit logs can be very large.
- Audit logs may contain sensitive object data.
- Audit logs should usually go to security-controlled storage.
- Use prune filters before external forwarding when appropriate.

## 12. Outputs and Destinations

Outputs define where logs are sent.

### 12.1 Common output types

| Output | Typical use |
|---|---|
| `lokiStack` | In-cluster short-term troubleshooting store |
| `splunk` | Enterprise SIEM/observability |
| `kafka` | Streaming pipeline / downstream processors |
| `elasticsearch` | External Elasticsearch, not Red Hat-managed legacy store |
| `syslog` | Network/security appliances |
| `http` | Custom log ingestion endpoint |
| `s3` | Compliance archive / cold storage |
| `cloudwatch` | AWS-native logging |
| `azureMonitor` | Azure-native logging |
| `googleCloudLogging` | Google Cloud logging |
| `otlp` | OpenTelemetry-based observability pipeline |

### 12.2 Output design principles

Do not send everything everywhere. Design outputs by audience:

| Audience | Recommended pattern |
|---|---|
| Developers | Application logs to LokiStack or team-specific external sink |
| SRE | Application + infrastructure logs to query-optimized store |
| Security | Audit logs to SIEM or immutable archive |
| Compliance | Pruned audit logs to long-term object storage |
| FinOps | Rate-limited and filtered logs to paid SaaS output |

### 12.3 Multi-output example

```yaml
pipelines:
- name: apps-to-loki-and-splunk
  inputRefs:
  - application
  outputRefs:
  - default-lokistack
  - splunk-prod
```

This duplicates records to both outputs. That can be useful but doubles egress and processing cost.

## 13. Filters, Pruning, Drop Rules, and Rate Limits

Filters are the policy engine of your logging pipeline.

### 13.1 Drop filter

Use drop filters to remove whole records.

Example: drop debug logs.

```yaml
filters:
- name: drop-debug
  type: drop
  drop:
  - test:
    - field: .level
      matches: debug
```

Example: drop logs from a noisy namespace.

```yaml
filters:
- name: drop-marketplace
  type: drop
  drop:
  - test:
    - field: .kubernetes.namespace_name
      matches: openshift-marketplace
```

### 13.2 Prune filter

Use prune filters to remove fields but keep the record.

Example:

```yaml
filters:
- name: prune-audit-heavy-fields
  type: prune
  prune:
    in:
    - .audit.requestObject
    - .audit.responseObject
    - .audit.managedFields
```

### 13.3 Filter order

Filters are applied in the order referenced by the pipeline:

```yaml
filterRefs:
- drop-debug
- prune-sensitive-fields
```

Recommended order:

1. parse structured logs if needed;
2. drop unwanted records early;
3. prune fields from remaining records;
4. add labels/routing metadata last.

### 13.4 Rate limits

Input rate limit example:

```yaml
inputs:
- name: limited-prod-apps
  type: application
  application:
    includes:
    - namespace: production
    tuning:
      rateLimitPerContainer:
        maxRecordsPerSecond: 500
```

Output rate limit example:

```yaml
outputs:
- name: limited-splunk
  type: splunk
  splunk:
    url: https://splunk.example.com:8088
    authentication:
      token:
        key: token
        secretName: splunk-secret
  rateLimit:
    maxRecordsPerSecond: 1000
```

Important: when rate limits are exceeded, excess records are dropped. Rate limiting is a protection mechanism, not lossless backpressure.

## 14. LokiStack Integration

### 14.1 Role of LokiStack

LokiStack is the supported Red Hat-managed in-cluster log store in modern OpenShift Logging. It is managed by the Loki Operator, not by the Logging Operator.

The Logging Operator sends logs to LokiStack through a `lokiStack` output.

### 14.2 Example LokiStack output

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    target:
      name: logging-loki
      namespace: openshift-logging
    authentication:
      token:
        from: serviceAccount
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

### 14.3 Important TLS requirement

When forwarding to LokiStack with a service-signed gateway certificate, include the CA bundle:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

If this is missing, `ClusterLogForwarder` can appear ready while the collector fails to deliver logs due to certificate verification issues.

### 14.4 Loki is not long-term archival by default

LokiStack in OpenShift Logging is optimized for recent troubleshooting queries. For long retention, legal hold, or historical analytics, forward to external long-term storage such as object storage, SIEM, or a dedicated logging platform.

## 15. External Forwarding Patterns

### 15.1 Splunk pattern

```yaml
outputs:
- name: splunk-prod
  type: splunk
  splunk:
    url: https://splunk.example.com:8088
    authentication:
      token:
        secretName: splunk-token
```

Use for:

- enterprise SIEM;
- security monitoring;
- app team dashboards;
- centralized search.

Watch for:

- HEC token validity;
- TLS CA chain;
- ingestion limits;
- HTTP 429 responses;
- index routing rules.

### 15.2 Kafka pattern

```yaml
outputs:
- name: kafka-prod
  type: kafka
  kafka:
    brokers:
    - kafka-1.example.com:9092
    - kafka-2.example.com:9092
    topic: openshift-logs
```

Use for:

- streaming pipelines;
- decoupling cluster logging from consumers;
- high-throughput centralized ingestion.

Watch for:

- broker connectivity;
- TLS/SASL configuration;
- topic partitions;
- consumer lag;
- log ordering expectations.

### 15.3 S3/archive pattern

Use object storage for compliance archive. Combine with prune filters to reduce sensitive or oversized fields.

```yaml
pipelines:
- name: audit-to-s3
  inputRefs:
  - audit
  filterRefs:
  - prune-sensitive-audit-fields
  outputRefs:
  - audit-archive-s3
```

## 16. Operator Reconciliation Behavior

### 16.1 Reconciliation loop

The operator repeatedly compares desired state to actual state:

```text
ClusterLogForwarder spec
        |
        v
Operator validates RBAC and config
        |
        v
Generates collector config + DaemonSet
        |
        v
Kubernetes schedules collector pods
        |
        v
Status conditions updated
```

### 16.2 What gets overwritten

Manual changes to generated objects can be reverted, including:

- collector DaemonSet edits;
- collector environment variable edits;
- collector ConfigMap edits;
- unsupported volume mounts;
- image changes;
- unsupported tuning not exposed through CR fields.

### 16.3 Managed vs Unmanaged

Some operators support `managementState`. If you set the logging operator to unmanaged to make unsupported manual changes, you are moving outside normal support and update behavior. Use this only for temporary diagnostic work and restore managed state as soon as possible.

### 16.4 Why the collector disappears

In Logging 6.x, the operator may remove the collector DaemonSet when it detects unsafe or unauthorized configuration. The most common cause is a `ClusterLogForwarder` that references a log type without the required ServiceAccount ClusterRoleBinding.

Example:

```yaml
pipelines:
- name: all-logs
  inputRefs:
  - application
  - infrastructure
  - audit
```

But the ServiceAccount has only:

```text
collect-application-logs
collect-infrastructure-logs
```

Result:

```text
Authorized=False
collector DaemonSet removed or not created
all log collection stopped
```

Fix:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging
```

Then verify:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

## 17. Security and Compliance Considerations

### 17.1 Least privilege

Grant only the log collection roles required:

| Log type | Role |
|---|---|
| Application | `collect-application-logs` |
| Infrastructure | `collect-infrastructure-logs` |
| Audit | `collect-audit-logs` |
| LokiStack write | `logging-collector-logs-writer` |

### 17.2 Audit log sensitivity

Audit logs may include:

- usernames;
- API paths;
- request objects;
- response objects;
- object metadata;
- service account activity;
- RBAC changes;
- secret access events, depending on audit policy.

Use separate pipelines and restricted destinations for audit logs.

### 17.3 Do not expose all logs to all users

In multi-tenant clusters, application logs should respect namespace boundaries. Avoid cluster-wide log access unless needed by platform/SRE/security teams.

Check log viewer RBAC:

```bash
oc get clusterrolebinding -o json | \
  jq -r '.items[] | select(.roleRef.name=="cluster-logging-application-view") | {name: .metadata.name, subjects: .subjects}'
```

For namespace-specific access:

```bash
oc get rolebinding -n <namespace> -o json | \
  jq -r '.items[] | select(.roleRef.name=="cluster-logging-application-view") | {name: .metadata.name, subjects: .subjects}'
```

### 17.4 TLS everywhere

For external outputs, validate:

- CA certificate is trusted;
- secret names and keys match exactly;
- endpoint hostname matches certificate SAN/CN;
- proxy or firewall is not intercepting TLS;
- mTLS requirements are met where configured.

## 18. Sizing and Performance Engineering

### 18.1 Logging sizing is workload-dependent

Log volume depends on:

- number of nodes;
- number of pods;
- application log verbosity;
- audit policy;
- container restart loops;
- error storms;
- operator reconciliation loops;
- external output latency;
- retention requirements;
- filtering strategy.

A small cluster with noisy apps can produce more logs than a large but quiet cluster.

### 18.2 Key performance risks

| Risk | Impact |
|---|---|
| Debug logs enabled in production | High ingestion cost |
| Audit logs sent to short-term store only | Compliance gap |
| Slow external output | Collector retries/backpressure |
| Missing rate limits | Storage or SaaS ingestion overload |
| Too aggressive rate limits | Dropped records |
| No filters | Expensive storage and noisy search |
| Large JSON logs | Increased CPU, memory, and network |

### 18.3 Practical sizing workflow

1. Start with application and infrastructure logs.
2. Measure ingestion rate for at least 24 hours.
3. Identify top noisy namespaces and containers.
4. Apply input selectors and drop filters.
5. Add audit logs only after RBAC and destination planning.
6. Separate short-term Loki retention from long-term archive.
7. Monitor collector CPU, memory, retries, dropped records, and output errors.

### 18.4 High-volume app handling

For noisy namespaces:

```yaml
inputs:
- name: noisy-app-limited
  type: application
  application:
    includes:
    - namespace: noisy-prod
    tuning:
      rateLimitPerContainer:
        maxRecordsPerSecond: 100
```

For unnecessary debug logs:

```yaml
filters:
- name: drop-debug-and-trace
  type: drop
  drop:
  - test:
    - field: .level
      matches: "debug|trace"
```

## 20. Troubleshooting Playbook

### 20.1 Symptom: No collector pods

Check:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Common causes:

| Cause | Fix |
|---|---|
| Missing ServiceAccount | Create SA and update CLF |
| Missing ClusterRoleBinding | Grant log-type RBAC |
| Invalid CLF YAML | Fix `Valid=False` message |
| Operator not running | Check CSV and operator pod logs |
| Wrong namespace | Use `openshift-logging` |

### 20.2 Symptom: `Authorized=False`

Check requested log types:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{range .spec.pipelines[*]}{.inputRefs[*]}{"\n"}{end}' | sort -u
```

Check bindings:

```bash
oc get clusterrolebinding -o wide | grep logging-collector
```

Fix missing roles:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging
```

### 20.3 Symptom: `Ready=True` but no logs in LokiStack

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
```

Common causes:

| Cause | Fix |
|---|---|
| Missing `tls.ca` for LokiStack | Add CA configMap/key block |
| Wrong LokiStack name | Match `oc get lokistack -A` |
| Wrong LokiStack namespace | Correct target namespace |
| Missing `logging-collector-logs-writer` | Grant writer role |
| Loki gateway unavailable | Check LokiStack pods and routes/services |
| 429 from Loki | Wait for backlog, tune rate, scale storage if needed |

### 20.4 Symptom: Certificate verification failed

Example log:

```text
certificate verify failed: self-signed certificate in certificate chain
```

Fix for LokiStack service CA:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

For external destinations:

- create a ConfigMap or Secret with CA bundle;
- reference it correctly in the output TLS section;
- confirm the endpoint certificate chain is complete;
- confirm hostname matches certificate SAN.

### 20.5 Symptom: 429 Too Many Requests

Meaning:

```text
Destination is throttling or cannot ingest as fast as collector sends.
```

Actions:

1. Check whether this is initial backlog after install.
2. Check LokiStack or external destination capacity.
3. Add or tune rate limits.
4. Drop noisy logs.
5. Increase destination ingestion capacity if required.

### 20.6 Symptom: Some namespaces missing logs

Check input selectors:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Common causes:

- custom input includes only selected namespaces;
- namespace labels do not match selector;
- pod labels do not match selector;
- pipeline does not reference the intended input;
- developer is querying wrong tenant/log type in UI;
- RBAC does not allow user to view that namespace's logs.

### 20.7 Symptom: External output authentication failure

Check:

```bash
oc get secret <secret-name> -n openshift-logging -o yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
```

Common mistakes:

- secret in wrong namespace;
- wrong key name inside secret;
- expired token;
- wrong Splunk HEC endpoint;
- Kafka SASL mechanism mismatch;
- CA chain missing;
- firewall or proxy blocking.

### 20.8 Enable debug logging temporarily

```bash
oc annotate clusterlogforwarder instance -n openshift-logging \
  observability.openshift.io/log-level=debug --overwrite

oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Reset afterward:

```bash
oc annotate clusterlogforwarder instance -n openshift-logging \
  observability.openshift.io/log-level=info --overwrite
```

Do not leave debug enabled permanently in production because it increases log volume.

## 22. Disaster Recovery and Backup Considerations

### 22.1 What to back up

For logging configuration backup:

- `ClusterLogForwarder` resources;
- LokiStack resources;
- output authentication secrets;
- TLS CA ConfigMaps/Secrets;
- Operator Subscriptions;
- OperatorGroups;
- role bindings for collector ServiceAccount;
- UIPlugin resources if used.

### 22.2 What not to rely on as backup

Do not treat the in-cluster logging store as your only audit/compliance backup. LokiStack in OpenShift Logging is designed for recent troubleshooting, not as a general-purpose long-term archive.

### 22.3 Recovery sequence

1. Restore operators/subscriptions.
2. Restore LokiStack/object storage configuration if using in-cluster storage.
3. Restore collector ServiceAccount and RBAC.
4. Restore secrets and CA bundles.
5. Restore `ClusterLogForwarder`.
6. Verify collector pods.
7. Verify logs appear in target destinations.

## 23. Production Best Practices

### 23.1 Design with separate pipelines

Avoid one huge pipeline for everything.

Better:

```text
application -> LokiStack / developer tool
infrastructure -> SRE observability store
audit -> SIEM / archive
```

### 23.2 Treat audit logs separately

Do not casually mix audit logs with developer-facing application logs.

### 23.3 Always validate RBAC before changing inputRefs

Checklist before adding `audit`:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging

oc get clusterrolebinding -o wide | grep collect-audit-logs
```

Then update CLF.

### 23.4 Include TLS CA for LokiStack

Do not omit:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

### 23.5 Control noisy logs early

Use input selectors and drop filters before logs reach expensive storage.

### 23.6 Use rate limits carefully

Rate limits protect systems but can drop logs. Alert on dropped records.

### 23.7 Never manually edit generated collector DaemonSet

Make supported changes through `ClusterLogForwarder` or operator-supported CR fields.

### 23.8 Keep operator versions aligned

Use compatible major/minor channels for:

- Red Hat OpenShift Logging Operator;
- Loki Operator;
- Cluster Observability Operator when used.

### 23.9 Document log ownership

For every pipeline, document:

- business owner;
- log type;
- output;
- retention;
- security classification;
- escalation owner;
- whether records are filtered, pruned, or rate-limited.

## 24. Real Interview/L3 Support Scenarios

### Scenario 1: Collector pods disappeared after adding audit logs

**Question:** You added `audit` to `inputRefs`, and now all collector pods are gone. What happened?

**Answer:** The collector ServiceAccount likely lacks the `collect-audit-logs` ClusterRoleBinding. In Logging 6.x, if the CLF requests a log type without authorization, the operator marks `Authorized=False` and can remove the collector DaemonSet to avoid insecure or partial collection.

Fix:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging

oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

### Scenario 2: `Ready=True`, but no logs in Observe → Logs

**Likely causes:**

- LokiStack output TLS CA missing;
- wrong LokiStack name/namespace;
- LokiStack not healthy;
- collector cannot write to LokiStack;
- UI plugin issue;
- user lacks log view permissions;
- selected wrong tenant/log type in UI.

Commands:

```bash
oc get lokistack -A
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

### Scenario 3: Splunk team says logs stopped

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=300 | egrep -i 'splunk|error|429|tls|certificate|timeout|refused'
oc get secret splunk-token -n openshift-logging
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Likely root causes:

- expired HEC token;
- Splunk endpoint changed;
- TLS CA changed;
- output rate limit reached;
- Splunk throttling;
- firewall/proxy issue;
- pipeline no longer references Splunk output.

### Scenario 4: Developers cannot see logs for their namespace

Check:

```bash
oc auth can-i get pods/log -n <namespace> --as=<user>
oc get rolebinding -n <namespace>
oc get clusterrolebinding | grep cluster-logging-application-view
```

Also check whether `ClusterLogForwarder` actually collects that namespace.

### Scenario 5: Logging cost suddenly increased

Investigate:

```bash
oc adm top pods -n openshift-logging
oc get pods -A --sort-by=.metadata.creationTimestamp | tail
oc get events -A --sort-by=.lastTimestamp | tail -50
```

Look for:

- crash loops generating stack traces;
- debug logging accidentally enabled;
- audit verbosity changes;
- new namespace with chatty workload;
- operator reconciliation loops;
- external destination retry storms.

Mitigate with:

- fixing noisy workload;
- drop filters;
- namespace-specific inputs;
- rate limits;
- shorter retention for short-term store;
- separate archive pipeline.

### 26.5 Basic ClusterLogForwarder to LokiStack

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: lokistack-out
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: app-infra-to-loki
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - lokistack-out
```

### 26.6 Add audit pipeline to external archive

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  filters:
  - name: prune-audit-heavy-fields
    type: prune
    prune:
      in:
      - .audit.requestObject
      - .audit.responseObject
      - .audit.managedFields
  outputs:
  - name: audit-archive
    type: s3
    s3:
      url: https://s3.example.com/audit-logs
      authentication:
        accessKey:
          key: access_key_id
          secretName: audit-s3-secret
        secretKey:
          key: access_key_secret
          secretName: audit-s3-secret
  pipelines:
  - name: audit-to-archive
    inputRefs:
    - audit
    filterRefs:
    - prune-audit-heavy-fields
    outputRefs:
    - audit-archive
```

Remember to grant `collect-audit-logs` before applying this.

## Final Notes for Advanced Administrators

For experienced OpenShift administrators, the most important point is this:

```text
The Logging Operator is not just an installer. It is a policy-enforcing reconciliation controller for log collection and forwarding.
```

A stable production logging deployment depends on:

- correct RBAC for requested log types;
- valid `ClusterLogForwarder` pipelines;
- healthy Vector collector pods on nodes;
- trusted TLS and valid credentials for outputs;
- storage and destination capacity planning;
- careful handling of audit logs;
- respecting operator-managed objects;
- treating LokiStack as short-term troubleshooting storage unless you explicitly design otherwise.

When troubleshooting, always follow the order:

```text
Operator CSV -> ClusterLogForwarder conditions -> RBAC -> collector pods -> collector logs -> output health -> destination query
```

That sequence will solve most real-world OpenShift Logging incidents faster than randomly restarting pods.
