## 1. What “Loki troubleshooting” means in OpenShift Logging

In OpenShift Logging, **Loki troubleshooting** means diagnosing failures across the complete log pipeline:

```text
container / node / audit source
        ↓
collector DaemonSet, usually Vector
        ↓
ClusterLogForwarder pipeline
        ↓
LokiStack gateway
        ↓
Loki distributor
        ↓
Loki ingester + WAL PVC
        ↓
object storage chunks/index
        ↓
querier / query-frontend / index-gateway
        ↓
OpenShift Observability UI / Logs tab / LogQL client
```

A senior administrator should not troubleshoot Loki as only a pod problem. Most incidents are caused by one of the following:

- Missing or wrong object storage configuration.
- Missing block storage for Loki internal PVCs.
- `ClusterLogForwarder` invalid or unauthorized.
- Collector DaemonSet removed by the operator because the CR is invalid.
- TLS CA missing in the LokiStack output.
- Object storage certificate, proxy, DNS, or permission problems.
- Loki receiving more data than the configured size can process.
- Bad labels causing high cardinality and slow queries.
- NetworkPolicies blocking collector-to-gateway or Loki-to-object-storage traffic.
- Retention configured in LokiStack but object storage lifecycle or delete permission missing.
- Incorrect expectations: Loki in OpenShift Logging is designed primarily as **short-term log storage for troubleshooting**, not as a long-term compliance archive or SIEM.

## 2. Current OpenShift Logging model

Modern OpenShift Logging is operator-driven and usually includes three main parts:

| Layer | Component | Purpose |
|---|---|---|
| Log store | **Loki Operator** + `LokiStack` | Deploys and manages Loki components and their storage integration. |
| Collection/forwarding | **Red Hat OpenShift Logging Operator** + `ClusterLogForwarder` | Deploys collectors and defines what logs go where. |
| Visualization | **Cluster Observability Operator** / OpenShift web console Logs UI | Allows users to search and visualize logs, usually through the OpenShift console. |

Important operational points:

- Install and configure the **Loki Operator** before configuring the Red Hat OpenShift Logging Operator.
- The Loki Operator and Red Hat OpenShift Logging Operator should use the same major/minor channel, for example `stable-6.4` for both.
- LokiStack requires both:
  - block storage through a `StorageClass` for internal PVCs such as WAL, index cache, and compactor working space;
  - object storage, such as S3-compatible, AWS S3, Azure, GCS, ODF, or Swift, for actual log chunks and indexes.
- OpenShift Logging Loki sizing is tested for short-term storage, with a maximum supported retention expectation of around 30 days.

## 3. LokiStack architecture in OpenShift

A LokiStack deployment normally contains these Loki components:

| Component | Main job | Common symptoms when broken |
|---|---|---|
| `gateway` | Authenticated API entry point for writes and queries. Enforces OpenShift tenant access. | Collector cannot push logs, UI cannot query, 401/403/5xx, TLS errors. |
| `distributor` | Receives pushed logs and distributes them to ingesters. | 429 errors, push failures, high CPU, overload. |
| `ingester` | Stores recent logs in memory/WAL and flushes chunks to object storage. | WAL PVC issues, CrashLoopBackOff, high memory, missing recent logs, flush errors. |
| `querier` | Reads log chunks and index data during queries. | Slow queries, timeout, high CPU/memory, object-store read errors. |
| `query-frontend` | Queues, splits, and schedules queries. | Long queue time, UI timeouts, slow LogQL. |
| `index-gateway` | Serves index data efficiently. | Index lookup slowness, query errors, cache/PVC issues. |
| `compactor` | Compacts index/chunks and enforces retention where configured. | Retention not working, old data not deleted, object storage delete errors. |
| `ruler` | Evaluates Loki recording/alerting rules when configured. | Log-based alerts not firing, rule evaluation errors. |

The key difference from Elasticsearch-based logging is that Loki indexes labels, not full text. This is good for cost and scale, but query design and label cardinality matter heavily.

## 5. Golden rule: troubleshoot by log path

Always identify the broken segment:

```text
Source → Collector → ClusterLogForwarder → Loki gateway → distributor → ingester → object storage → query path → UI/RBAC
```

Ask these questions in order:

1. Are application/node/audit logs being produced?
2. Is the collector DaemonSet running on nodes?
3. Is `ClusterLogForwarder` `Authorized=True`, `Valid=True`, and `Ready=True`?
4. Can the collector reach the LokiStack gateway?
5. Is TLS trusted by the collector?
6. Is Loki accepting pushes or returning 429/401/403/5xx?
7. Are ingesters healthy and able to flush to object storage?
8. Is object storage reachable, writable, readable, and delete-capable?
9. Can query components read index/chunks?
10. Is the user allowed to view that tenant/namespace/log type?
11. Is the query efficient enough for the selected time range?

This flow prevents wasting time checking the UI while ingestion is broken, or checking collectors while object storage is silently dropping chunks.

## 7. Operator and version troubleshooting

### 7.1 Symptoms

- LokiStack CR does not reconcile.
- CRDs are missing.
- Pods are not created after applying valid CRs.
- Operator pod is `CrashLoopBackOff`.
- `Subscription` shows upgrade/install errors.
- Logging Operator creates no collector.
- Loki Operator and Logging Operator are on mismatched channels.

### 7.2 Commands

```bash
oc get subscription -A | grep -Ei 'loki|logging'
oc get csv -A | grep -Ei 'loki|logging'
oc get pods -A | grep -Ei 'loki-operator|cluster-logging-operator'
oc describe subscription <sub> -n <ns>
oc describe csv <csv> -n <ns>
oc get installplan -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp | tail -100
```

Check operator logs:

```bash
oc logs -n openshift-operators-redhat deploy/loki-operator-controller-manager --tail=200
oc logs -n openshift-logging deploy/cluster-logging-operator --tail=200
```

Names can vary. Discover first:

```bash
oc get deploy -A | grep -Ei 'loki|logging'
```

### 7.3 Root causes

| Symptom | Likely cause | Fix |
|---|---|---|
| LokiStack CRD missing | Loki Operator not installed or failed | Fix Subscription/CSV first. |
| Logging CRD missing | Logging Operator not installed | Install correct operator/channel. |
| LokiStack not reconciling | Operator down or lacks permissions | Check operator deployment and CSV. |
| Version mismatch | Loki Operator and Logging Operator on different major/minor versions | Align channels, for example both `stable-6.4`. |
| Operator installed but pods not created | Invalid CR or missing prerequisites | Check CR `status.conditions`, events, and operator logs. |

## 8. LokiStack CR troubleshooting

The `LokiStack` CR is the desired state for Loki. If it is wrong, downstream troubleshooting becomes noisy.

### 8.1 Inspect the CR

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml
oc describe lokistack logging-loki -n openshift-logging
oc explain lokistack.spec
oc explain lokistack.spec.storage
oc explain lokistack.spec.template
```

### 8.2 Minimal production-style fields to verify

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.small
  storage:
    schemas:
    - effectiveDate: "2024-04-01"
      version: v13
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: gp3-csi
  tenants:
    mode: openshift-logging
```

Check these items:

| Field | Why it matters |
|---|---|
| `managementState: Managed` | Operator manages the deployment. If unmanaged, operator stops reconciling. |
| `size` | Determines resource sizing and throughput expectations. |
| `storage.secret.name` | References the object storage credentials secret. |
| `storage.secret.type` | Must match backend type, such as `s3`, `azure`, `gcs`, or `swift`. |
| `storage.schemas[].version` | Schema version affects query and storage behavior; `v13` is recommended in current docs. |
| `storageClassName` | Used for internal block-storage PVCs, not object storage. |
| `tenants.mode` | Controls tenancy model; OpenShift logging uses tenant separation for application, infrastructure, and audit logs. |

### 8.3 Common CR mistakes

| Mistake | Impact | Fix |
|---|---|---|
| `storageClassName` set to object storage name | Loki PVCs fail or bind incorrectly | Use a real Kubernetes StorageClass for block storage. |
| Object storage secret missing | Pods may run but ingestion/query fails | Create secret in `openshift-logging`. |
| Wrong object storage `type` | Loki cannot configure backend | Match provider type. |
| Wrong bucket/endpoint/region | Push/query errors, storage logs show failure | Validate object store endpoint from Loki pod. |
| No retention configured anywhere | Old logs stay in bucket indefinitely | Configure object lifecycle and/or Loki retention. |
| Over-small size such as demo in production | 429, slow queries, overload | Increase LokiStack size and/or reduce ingestion. |

## 9. Storage troubleshooting

LokiStack storage is the most important troubleshooting area.

### 9.1 Two storage types

OpenShift LokiStack needs two separate storage layers:

```text
1. Block storage / StorageClass
   Used for Loki internal PVCs: WAL, index cache, compactor workspace.

2. Object storage
   Used for actual log chunks and indexes.
```

Do not confuse them. `spec.storageClassName` is for PVCs. Object storage is configured through the secret referenced by `spec.storage.secret.name`.

### 9.2 Block storage failure symptoms

- Loki pods stuck in `Pending`.
- PVCs stuck in `Pending`.
- Events show `no persistent volumes available`, `waiting for first consumer`, `storageclass not found`, or CSI provisioning errors.
- Ingester/index-gateway/compactor pods do not start.

Commands:

```bash
oc get pvc -n openshift-logging
oc describe pvc <pvc> -n openshift-logging
oc get storageclass
oc get pods -n openshift-logging -o wide
oc describe pod <pending-pod> -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -80
```

Fix approach:

1. Verify a default or named StorageClass exists.
2. Verify `spec.storageClassName` matches it exactly.
3. Check CSI provisioner pods.
4. Check node scheduling constraints.
5. Check quota in `openshift-logging`.
6. Check PV topology/zone constraints.
7. Check if PVC finalizers are stuck during cleanup.

### 9.3 Object storage failure symptoms

- LokiStack appears `Ready`, but no logs are stored.
- Collector pushes successfully for some time, but queries return missing data.
- Ingester logs show flush errors.
- Querier logs show object read errors.
- Compactor logs show retention delete failures.
- TLS errors to S3-compatible endpoint.
- NetworkPolicy blocks object storage access.
- Bucket grows forever even after retention rules.

Commands:

```bash
oc get secret -n openshift-logging
oc get secret logging-loki-s3 -n openshift-logging -o yaml
oc get lokistack logging-loki -n openshift-logging -o jsonpath='{.spec.storage.secret.name}{"\n"}'
oc get lokistack logging-loki -n openshift-logging -o jsonpath='{.spec.storage.secret.type}{"\n"}'
```

Check Loki component logs:

```bash
for p in $(oc get pod -n openshift-logging -o name | grep loki); do
  echo "===== $p ====="
  oc logs -n openshift-logging $p --all-containers --tail=100 | egrep -i 's3|bucket|object|flush|x509|certificate|access denied|timeout|forbidden|no such host|connection refused' || true
done
```

### 9.4 S3 permission checks

For S3-compatible object storage, verify that the access key can:

- list bucket objects;
- put objects;
- get objects;
- delete expired objects if Loki retention/compactor needs to delete;
- get and put object tags if retention/lifecycle tagging is used.

Production symptom: `Ready=True` but old logs never delete. Often the missing permission is `DeleteObject`, or retention is configured in Loki but object storage lifecycle is not configured.

### 9.5 CA bundle and object storage TLS

If using MinIO, ODF, NetApp StorageGRID, or internal S3 with private CA, make sure Loki trusts the object storage CA. Symptoms include:

```text
x509: certificate signed by unknown authority
certificate verify failed
self-signed certificate in certificate chain
```

Check:

```bash
oc get configmap -n openshift-logging | grep -i ca
oc describe lokistack logging-loki -n openshift-logging
oc logs -n openshift-logging <ingester-pod> --tail=200 | grep -Ei 'x509|certificate|tls'
```

## 10. Loki pod troubleshooting by component

### 10.1 General pod triage

```bash
oc get pods -n openshift-logging -o wide
oc get pod <pod> -n openshift-logging -o yaml
oc describe pod <pod> -n openshift-logging
oc logs <pod> -n openshift-logging --all-containers --tail=200
oc logs <pod> -n openshift-logging --all-containers --previous --tail=200
```

Interpret status:

| Pod status | Meaning | First checks |
|---|---|---|
| `Pending` | Scheduling or PVC issue | `describe pod`, PVC, node selectors, taints, quotas. |
| `ContainerCreating` | Image, mount, secret, PVC, CNI issue | `describe pod`, events. |
| `CrashLoopBackOff` | Process starts then exits | logs `--previous`, config, secret, object storage, TLS. |
| `ImagePullBackOff` | Registry/image issue | pull secret, catalog source, disconnected mirror. |
| `Running` but not ready | Readiness probe failing | component logs, service endpoints. |

### 10.2 Gateway troubleshooting

Gateway is the front door for writes and queries.

Symptoms:

- Collector logs show 401/403/5xx.
- Logs UI cannot query.
- Users can see one tenant but not another.
- TLS handshake errors.
- NetworkPolicy blocks traffic.

Commands:

```bash
oc get svc -n openshift-logging | grep gateway
oc get endpoints -n openshift-logging | grep gateway
oc get route -n openshift-logging
oc logs -n openshift-logging <gateway-pod> --tail=200
oc describe pod -n openshift-logging <gateway-pod>
```

Checks:

- Does the gateway service have endpoints?
- Are gateway pods ready?
- Does collector output reference the correct LokiStack name/namespace?
- Is the service CA configured in `ClusterLogForwarder`?
- Does the collector service account use token authentication from service account?
- Are users authorized for the tenant/namespace they are querying?

### 10.3 Distributor troubleshooting

Distributor accepts log pushes and sends them to ingesters.

Symptoms:

- High CPU.
- 429 rate limits.
- Push errors.
- Ingestion delay.

Commands:

```bash
oc logs -n openshift-logging <distributor-pod> --tail=200 | egrep -i 'rate|limit|429|push|error|tenant'
oc adm top pod -n openshift-logging | grep distributor
```

Actions:

- Confirm if 429 is temporary backlog or sustained overload.
- Reduce noisy logs with filters/rate limits.
- Increase LokiStack size if production volume exceeds sizing.
- Fix high-cardinality labels if stream count is exploding.

### 10.4 Ingester troubleshooting

Ingester handles recent logs and WAL.

Symptoms:

- Recent logs missing.
- WAL PVC full or mount errors.
- CrashLoopBackOff.
- Flush to object storage fails.
- Memory pressure.

Commands:

```bash
oc logs -n openshift-logging <ingester-pod> --tail=300 | egrep -i 'wal|flush|chunk|s3|bucket|error|panic|oom|rate|limit|x509'
oc describe pod -n openshift-logging <ingester-pod>
oc get pvc -n openshift-logging | grep -i ingester
oc adm top pod -n openshift-logging | grep ingester
```

Common causes:

| Cause | Evidence | Fix |
|---|---|---|
| Object storage write denied | `AccessDenied`, `Forbidden`, `PutObject` errors | Fix bucket policy/secret. |
| TLS issue | `x509`, certificate errors | Add correct CA. |
| WAL PVC issue | mount or disk errors | Fix PVC/StorageClass/node. |
| OOM | pod restarted, previous logs, OOMKilled | Increase size/resources, reduce ingestion. |
| Too much ingestion | rate limit, high CPU/memory | Filter/rate-limit logs, scale LokiStack size. |

### 10.5 Querier and query-frontend troubleshooting

Symptoms:

- UI query timeout.
- Long time range query never returns.
- Query works for 5 minutes but not 24 hours.
- Query works by namespace but not free-text across all logs.
- High `queue_time` in query frontend logs.

Commands:

```bash
oc logs -n openshift-logging <query-frontend-pod> --tail=200 | grep metrics.go
oc logs -n openshift-logging <querier-pod> --tail=200 | grep metrics.go
oc adm top pod -n openshift-logging | egrep 'querier|query-frontend|index-gateway'
```

Look for these fields in `metrics.go` lines:

```text
duration
queue_time
chunk_refs_fetch_time
store_chunks_download_time
```

Interpretation:

| Field high | Meaning |
|---|---|
| `queue_time` | Query frontend is backed up or not enough query capacity. |
| `chunk_refs_fetch_time` | Index lookup is expensive; labels/time range may be poor. |
| `store_chunks_download_time` | Object storage or cache is slow. |
| `duration` | Overall query is too heavy or backend slow. |

Actions:

- Narrow time range.
- Add label selectors such as namespace/app/container.
- Avoid broad regex across all streams.
- Check object storage latency.
- Check index-gateway health.
- Check query component CPU/memory.
- Review label cardinality.

### 10.6 Index-gateway troubleshooting

Symptoms:

- Queries slow even when object storage is healthy.
- Index-related errors.
- PVC/cache issues.

Commands:

```bash
oc logs -n openshift-logging <index-gateway-pod> --tail=200 | egrep -i 'index|cache|error|timeout|object|s3'
oc get pvc -n openshift-logging | grep -i index
oc adm top pod -n openshift-logging | grep index
```

Fixes:

- Validate PVCs.
- Validate object store read latency.
- Reduce query breadth.
- Ensure schema version and migration state are correct.

### 10.7 Compactor troubleshooting

Symptoms:

- Retention not deleting old logs.
- Object store bucket grows forever.
- Compactor crash loops.
- Delete requests fail.

Commands:

```bash
oc logs -n openshift-logging <compactor-pod> --tail=300 | egrep -i 'compact|retention|delete|s3|bucket|forbidden|access|error'
oc describe pod -n openshift-logging <compactor-pod>
oc get lokistack logging-loki -n openshift-logging -o yaml | grep -A30 -i retention
```

Common causes:

- Retention not configured in object storage lifecycle or LokiStack.
- S3 user missing delete permissions.
- Object storage does not support expected lifecycle/tag behavior.
- Compactor PVC/workspace issue.
- NetworkPolicy blocks object storage.

### 10.8 Ruler troubleshooting

Symptoms:

- Log-based alerts do not fire.
- Rules fail to load.
- Ruler pod fails.
- RBAC missing for LokiStack rules.

Commands:

```bash
oc get pods -n openshift-logging | grep ruler
oc logs -n openshift-logging <ruler-pod> --tail=200
oc get lokistack -n openshift-logging -o yaml | grep -A50 -i ruler
```

Fixes:

- Check rule CRs and tenant configuration.
- Check Ruler component readiness.
- Check RBAC for log-based alerting rules.
- Check query performance; alert rules are also LogQL queries.

## 11. Collector and ClusterLogForwarder troubleshooting

In many incidents, Loki is healthy but no logs arrive because collection or forwarding is broken.

### 11.1 Check ClusterLogForwarder status

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Expected:

```json
[
  {
    "type": "observability.openshift.io/Authorized",
    "status": "True",
    "message": "permitted to collect log types: [application infrastructure]"
  },
  {
    "type": "observability.openshift.io/Valid",
    "status": "True"
  },
  {
    "type": "Ready",
    "status": "True"
  }
]
```

Meaning:

| Condition | Expected | Meaning if false |
|---|---|---|
| `Authorized` | `True` | Collector service account lacks required `ClusterRoleBinding` for one or more log types. |
| `Valid` | `True` | CR has structural or semantic error. |
| `Ready` | `True` | Operator could not reconcile the CR or create collector resources. |

### 11.2 Collector pod missing

Symptom:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
No resources found in openshift-logging namespace.
```

Likely cause:

- `ClusterLogForwarder` invalid or unauthorized.
- Missing RBAC for one of the requested `inputRefs`.
- For example, CR includes `audit` but SA lacks `collect-audit-logs`.

Resolution:


## 12. TLS and certificate troubleshooting

### 12.1 Collector to LokiStack gateway TLS

Symptom:

```text
certificate verify failed
self-signed certificate in certificate chain
```

Cause:

The collector does not trust the LokiStack gateway certificate. The gateway uses OpenShift service-serving CA, so `ClusterLogForwarder` must reference the correct CA bundle.

Fix:

```yaml
outputs:
- name: lokistack-out
  type: lokiStack
  lokiStack:
    target:
      name: logging-loki
      namespace: openshift-logging
    authentication:
      token:
        from: serviceAccount
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

Verify:

```bash
oc get cm logging-loki-gateway-ca-bundle -n openshift-logging -o yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100 | grep -Ei 'x509|certificate|tls'
```

### 12.2 Loki to object storage TLS

Symptoms:

```text
x509: certificate signed by unknown authority
TLS handshake timeout
certificate verify failed
```

Check:

```bash
oc logs -n openshift-logging <ingester-pod> --tail=200 | grep -Ei 'x509|certificate|tls|s3|object'
oc logs -n openshift-logging <querier-pod> --tail=200 | grep -Ei 'x509|certificate|tls|s3|object'
```

Fix approach:

- Confirm endpoint URL in object storage secret.
- Confirm CA bundle config for LokiStack object storage.
- Confirm DNS resolution from Loki pods.
- Confirm proxy settings if cluster-wide proxy is used.
- Confirm NetworkPolicy permits egress to object storage/proxy.

## 15. 429 rate-limit troubleshooting

### 15.1 What 429 means

`429 Too Many Requests` means logs are being sent faster than Loki or the destination sink can process them. This can be normal during:

- initial deployment, when collectors flush old accumulated logs;
- recovery after Loki or object storage was unavailable;
- a sudden application log storm;
- a too-small LokiStack size for current ingestion volume.

Collector retry/backoff can clear temporary backlog automatically. Sustained 429 requires tuning or reducing volume.

### 15.2 Evidence

Collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 | grep -i '429\|too many\|rate'
```

Loki logs:

```bash
oc logs -n openshift-logging <distributor-pod> --tail=200 | grep -Ei '429|rate|limit'
oc logs -n openshift-logging <ingester-pod> --tail=200 | grep -Ei '429|rate|limit'
```

Example style of error:

```text
rpc error: code = Code(429) desc = entry with timestamp ... ignored, reason: 'Per stream rate limit exceeded ...'
```

### 15.3 Decision tree

```text
429 seen?
  ↓
Is this just after installation or outage recovery?
  ├─ yes → observe backlog; verify it clears.
  └─ no  → sustained overload.
          ↓
Is one namespace/app noisy?
  ├─ yes → filter/rate-limit/drop debug logs for that source.
  └─ no  → check global ingestion volume vs LokiStack size.
          ↓
Are labels too granular?
  ├─ yes → reduce stream label cardinality.
  └─ no  → resize LokiStack / improve object storage / tune collector payload.
```

### 15.4 Fix options

1. **Wait if temporary**  
   Initial backlog can clear without intervention if incoming new logs are below Loki capacity.

2. **Reduce noisy logs**  
   Use `ClusterLogForwarder` filters to drop debug/noisy messages or only include required namespaces.

3. **Configure rate limits before expensive output**  
   Rate-limit high-volume applications before they overload Loki or external sinks.

4. **Tune output payload**  
   For LokiStack outputs, check max payload settings and retry timing. Default max write payload for LokiStack outputs is documented as `3Mi` when unspecified.

5. **Resize LokiStack**  
   If production volume is higher than the chosen LokiStack size, move from demo/pico/extra-small to a suitable size.

6. **Fix bad labels**  
   High cardinality creates too many streams and can trigger per-stream or global limits.

## 16. Query and UI troubleshooting

### 16.1 Symptoms

- Logs UI opens but query returns nothing.
- Query returns data for 5 minutes but not 24 hours.
- Query times out.
- Query works for cluster-admin but not project user.
- Query works by namespace but not free text.
- `query-frontend` shows high queue time.
- Object storage read latency is high.

### 16.2 First checks

```bash
oc get pods -n openshift-logging | grep -Ei 'query|querier|frontend|gateway|index'
oc logs -n openshift-logging <query-frontend-pod> --tail=200
oc logs -n openshift-logging <querier-pod> --tail=200
oc logs -n openshift-logging <index-gateway-pod> --tail=200
oc logs -n openshift-logging <gateway-pod> --tail=200
```

### 16.3 Query performance metrics

Loki emits `metrics.go` log lines for query execution. Look for:

```text
duration
queue_time
chunk_refs_fetch_time
store_chunks_download_time
```

Practical interpretation:

| High value | Meaning | Operational fix |
|---|---|---|
| `queue_time` | Query frontend is overloaded | More query capacity, fewer broad queries, reduce concurrency pressure. |
| `chunk_refs_fetch_time` | Index lookup is expensive | Better label selectors, reduce time range, check index-gateway. |
| `store_chunks_download_time` | Object store/cache read slow | Check object store latency, network, cache, PVC. |
| `duration` | Query overall too expensive | Narrow query, improve labels, inspect backend resource pressure. |

### 16.4 Good vs bad LogQL style

Bad broad query:

```logql
{log_type="application"} |= "Exception"
```

Better query:

```logql
{kubernetes_namespace_name="payments", kubernetes_container_name="api"} |= "Exception"
```

Bad high-cost regex:

```logql
{log_type="application"} |~ ".*timeout.*|.*failed.*|.*exception.*"
```

Better:

```logql
{kubernetes_namespace_name="payments"} |= "timeout"
```

Operational guidance:

- Always start with tenant/namespace/app/container labels.
- Keep time ranges small during incident triage.
- Avoid cluster-wide free-text searches unless necessary.
- Avoid regex until label narrowing is done.
- Educate developers that Loki is label-first, not full-text-index-first.

### 16.5 User can see no logs

Separate access problem from data problem:

```bash
# As cluster-admin, check if logs exist for the namespace.
# Then check user's project access.
oc auth can-i get pods -n <namespace> --as=<user>
oc auth can-i get pods/log -n <namespace> --as=<user>
```

If cluster-admin sees logs but user does not, troubleshoot RBAC/tenant access. If nobody sees logs, troubleshoot ingestion/storage/query path.

## 17. Label and cardinality troubleshooting

Loki uses labels as the index and stream partition key. This is the heart of Loki performance.

### 17.1 Good labels

Good labels are:

- low cardinality;
- long-lived;
- useful for query filtering;
- infrastructure-oriented.

Examples:

```text
cluster
namespace
application
container
log_type
environment
region
```

### 17.2 Bad labels

Avoid labels with high cardinality:

```text
request_id
trace_id
user_id
session_id
pod_uid
full HTTP path with IDs
IP address in high-churn environments
timestamp
error message
```

These create too many streams and hurt ingestion and query performance.

### 17.3 Detect cardinality symptoms

Symptoms:

- 429 per-stream or global rate limits.
- Query performance degrades sharply.
- Ingester memory high.
- Distributor CPU high.
- Too many tiny streams.

Checks:

```bash
oc logs -n openshift-logging <distributor-pod> --tail=300 | grep -Ei 'cardinality|stream|rate|limit'
oc logs -n openshift-logging <ingester-pod> --tail=300 | grep -Ei 'stream|series|rate|limit|memory'
```

### 17.4 ClusterLogForwarder label configuration

For LokiStack output, stream labels can be configured through `lokiStack.labelKeys` depending on data model.

Conceptual example:

```yaml
outputs:
- name: lokistack-out
  type: lokiStack
  lokiStack:
    target:
      name: logging-loki
      namespace: openshift-logging
    labelKeys:
      application:
        ignoreGlobal: false
        labelKeys:
        - kubernetes.namespace_name
        - kubernetes.container_name
      infrastructure:
        ignoreGlobal: false
        labelKeys:
        - kubernetes.namespace_name
      audit:
        ignoreGlobal: false
        labelKeys: []
```

Use the exact field names supported by your installed logging version. Confirm with:

```bash
oc explain clusterlogforwarder.spec.outputs.lokiStack
oc explain clusterlogforwarder.spec.outputs.lokiStack.labelKeys
```

## 18. Retention and compactor troubleshooting

### 18.1 Understand retention layers

Retention can be enforced at:

1. Object storage lifecycle policy.
2. LokiStack retention configuration.
3. Stream-based retention rules.

For cost-effective deletion, object storage lifecycle is often preferred. LokiStack retention is useful when object storage lifecycle is unavailable or when stream/tenant-specific retention is required.

### 18.2 Symptoms

- Logs older than expected are still queryable.
- Bucket size grows forever.
- Compactor logs show delete failure.
- Retention configured but no deletion occurs.
- Audit logs retained incorrectly.

### 18.3 Check LokiStack retention config

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml | sed -n '/limits:/,/storage:/p'
```

Example per-tenant concept:

```yaml
spec:
  limits:
    global:
      retention:
        days: 20
    tenants:
      application:
        retention:
          days: 7
      infrastructure:
        retention:
          days: 5
      audit:
        retention:
          days: 1
```

### 18.4 Check compactor logs

```bash
oc logs -n openshift-logging <compactor-pod> --tail=300 | \
  egrep -i 'retention|delete|compact|s3|bucket|forbidden|access|error'
```

### 18.5 Common retention root causes

| Symptom | Cause | Fix |
|---|---|---|
| Retention configured but bucket grows | Object storage user cannot delete | Add delete permissions. |
| Old logs never deleted | No object lifecycle and no Loki retention | Configure one of them. |
| Delete errors in compactor | Missing S3 `DeleteObject` or network issue | Fix IAM/network. |
| Retention too long | Tenant/global precedence misunderstood | Review tenant-specific rules. |
| Audit retention wrong | Audit pipeline/tenant misconfigured | Verify `inputRefs: audit` and tenant access. |

## 19. NetworkPolicy troubleshooting

NetworkPolicy is a common cause in hardened clusters.

### 19.1 Traffic that must work

```text
collector pods → LokiStack gateway
Loki components → each other
Loki components → object storage endpoint
Loki components → cluster DNS
Loki components → proxy, if cluster-wide proxy is used
users/UI → gateway/query path through OpenShift console integration
```

### 19.2 Symptoms

- Collector `connection refused`, `timeout`, or `no route to host`.
- Loki cannot reach S3/ODF/MinIO/Swift.
- Everything works until NetworkPolicy is enabled.
- Object store works outside cluster but not from Loki pods.
- Cluster-wide proxy configured but traffic to proxy blocked.

### 19.3 Commands

```bash
oc get networkpolicy -n openshift-logging
oc describe networkpolicy -n openshift-logging
oc get egressnetworkpolicy -A 2>/dev/null || true
oc get netnamespace 2>/dev/null || true
```

Test connectivity from a debug pod in the same namespace:

```bash
oc run net-debug -n openshift-logging --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
curl -vk https://<object-storage-endpoint>
curl -vk https://<loki-gateway-service>:8080
getent hosts <object-storage-host>
```

If the image lacks tools, install temporarily only in a disposable debug pod if allowed by your environment.

### 19.4 Known pattern

When Loki Operator network policies are enabled with S3-compatible storage, Swift, or cluster-wide proxy, verify that egress to object storage or proxy is explicitly allowed. Otherwise Loki may look healthy but fail to flush/query chunks.

## 20. Scheduling, node pressure, and HA troubleshooting

### 20.1 Symptoms

- Loki pods pending.
- Pods scheduled on overloaded worker nodes.
- Ingester OOM or CPU throttling.
- Query components slow during cluster load.
- Node drain causes disruption.
- PVC zone mismatch.

### 20.2 Commands

```bash
oc get pods -n openshift-logging -o wide
oc adm top pods -n openshift-logging
oc adm top nodes
oc describe pod <pod> -n openshift-logging
oc get nodes --show-labels
oc describe node <node>
oc get pdb -n openshift-logging
```

### 20.3 Infra node placement

For production, you can schedule Loki components to infra nodes using `nodeSelector` and `tolerations` in `LokiStack.spec.template`.

Example pattern:

```yaml
spec:
  template:
    ingester:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
    querier:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
```

Confirm fields:

```bash
oc explain lokistack.spec.template
oc explain lokistack.spec.template.ingester
```

### 20.4 Anti-affinity and failure tolerance

Loki Operator sets preferred pod anti-affinity for Loki components. For stricter HA, required anti-affinity can spread pods across nodes, but ensure enough nodes exist. If you enforce required anti-affinity on a small cluster, pods may remain pending.

Check pending pod event:

```bash
oc describe pod <pending-loki-pod> -n openshift-logging | sed -n '/Events:/,$p'
```

Look for:

```text
0/3 nodes are available: pod didn't match pod anti-affinity rules
node(s) had taint that the pod didn't tolerate
node(s) didn't match Pod's node affinity/selector
```

```bash
for p in $(oc get pods -n openshift-logging -o name); do
  safe=$(echo $p | tr '/:' '__')
  oc logs -n openshift-logging $p --all-containers --tail=500 > loki-debug/${safe}.log 2>&1 || true
  oc logs -n openshift-logging $p --all-containers --previous --tail=500 > loki-debug/${safe}.previous.log 2>&1 || true
done

tar -cvaf loki-debug.tar.gz loki-debug
```

- Last configuration change.
- Whether issue affects ingestion, query, UI, or retention.

## 24. Interview and real-world scenario questions

### Q1. LokiStack shows Ready but no logs are visible. What do you check?

Answer:

1. `ClusterLogForwarder` conditions: `Authorized`, `Valid`, `Ready`.
2. Collector pod existence and logs.
3. Gateway CA in `ClusterLogForwarder` output.
4. Loki gateway/distributor/ingester logs.
5. Object storage secret, endpoint, CA, and permissions.
6. PVC status.
7. Query tenant and user RBAC.

### Q2. Why can LokiStack be Ready even when logs are silently dropped?

Answer:

Readiness can indicate the CR reconciled and components are deployed, but runtime dependencies such as object storage credentials, CA trust, object storage permissions, or NetworkPolicy may still fail during ingestion or flush. Always check component logs and object store connectivity.

### Q3. Collector DaemonSet disappeared after adding audit logs. Why?

Answer:

The `ClusterLogForwarder` requested `audit` input, but the collector service account lacks `collect-audit-logs`. When the forwarder is unauthorized or invalid, the operator can remove the collector DaemonSet. Fix RBAC, then verify status conditions.

### Q4. How do you troubleshoot 429 Too Many Requests?

Answer:

Check collector, distributor, and ingester logs. Determine whether 429 is temporary backlog after install/outage or sustained overload. If temporary, observe retry/backoff. If sustained, reduce noisy logs, configure filters/rate limits, reduce high-cardinality labels, improve object storage, or resize LokiStack.

### Q5. What is the difference between block storage and object storage in LokiStack?

Answer:

Block storage through `storageClassName` is used for internal PVCs such as WAL, index cache, and compactor workspace. Object storage stores actual log chunks and indexes and is configured by the object storage secret referenced in `spec.storage.secret`.

### Q6. Why do broad LogQL queries perform badly?

Answer:

Loki indexes labels, not every word in the log body. A broad query across all streams forces Loki to inspect many chunks. Queries should first narrow by labels such as namespace, app, container, tenant, or environment.

### Q7. Retention is configured but bucket size keeps growing. What is likely wrong?

Answer:

Object storage lifecycle might not be configured, Loki retention might not match the streams, compactor might be failing, or the S3 credentials might lack delete/tagging permissions required for retention cleanup.

### Q8. User cannot see logs but cluster-admin can. What is the likely cause?

Answer:

RBAC/tenant access issue. Validate the user’s access to the namespace and log type. Application logs are usually namespace-scoped; infrastructure and audit logs require higher privileges.

### Q9. Loki pods are pending after enabling required anti-affinity. Why?

Answer:

The cluster may not have enough eligible nodes to satisfy the required anti-affinity and node selector/toleration rules. Check pod events for scheduling failures.

### Q10. Why is `tls.ca` important in ClusterLogForwarder for LokiStack?

Answer:

The LokiStack gateway uses a certificate signed by the OpenShift service-serving CA. The collector must trust that CA. Without the CA reference, the CR can appear ready but runtime forwarding fails with certificate verification errors.

## 25. Best practices checklist

### Design

- Use LokiStack for short-term troubleshooting logs, not as the only long-term compliance store.
- Forward audit logs to an external, secure, long-term store if required.
- Choose LokiStack size based on real ingestion after at least 24 hours of measurement.
- Keep Loki Operator and Logging Operator on matching major/minor channels.
- Use a reliable object store with low latency.
- Keep object storage lifecycle policies aligned with retention needs.

### Storage

- Validate both block storage and object storage before deployment.
- Do not confuse `storageClassName` with object storage.
- Ensure object storage credentials can list, put, get, and delete objects as needed.
- Configure CA trust for private object storage endpoints.
- Monitor bucket growth and compactor health.

### Collection

- Always check `ClusterLogForwarder.status.conditions`.
- Grant collector RBAC before adding the related `inputRefs`.
- Include `tls.ca` for in-cluster LokiStack forwarding.
- Keep collector debug/trace temporary.
- Drop or rate-limit noisy logs before they reach Loki.

### Query

- Teach users label-first LogQL.
- Avoid broad regex across all application logs.
- Use short time ranges during incidents.
- Watch query-frontend and querier `metrics.go` logs.
- Keep labels low-cardinality and long-lived.

### Security

- Review tenant access carefully.
- Use NetworkPolicy, but explicitly allow required Loki traffic.
- Be careful with infrastructure/audit log access.
- Rotate object storage credentials safely.

### Operations

- Keep runbooks for 429, missing collector, storage failure, UI timeout, and retention failure.
- Collect must-gather before major changes in production incidents.
- Monitor Loki pods, PVCs, object storage, and collector errors.
- Document last changes to `LokiStack`, `ClusterLogForwarder`, NetworkPolicy, and object storage.

## Final senior-admin summary

When Loki troubleshooting in OpenShift, do not start with only `oc logs` of a Loki pod. Start by identifying which segment of the log path is broken:

```text
source → collector → forwarder → gateway → distributor → ingester → object storage → query path → UI/RBAC
```

For 80% of production issues, the answer is found in these commands:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get lokistack logging-loki -n openshift-logging -o yaml
oc get pods,pvc,svc,endpoints -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -100
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
```

Then branch into storage, TLS, RBAC, rate-limit, query, or NetworkPolicy troubleshooting based on the first real error.
