# OpenShift Logging: Log Retention — Advanced Administration Deep Dive

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and L3 operations engineers with production Kubernetes/OpenShift experience.  
**Focus:** Retention design, LokiStack retention, object storage lifecycle, source-node retention, audit/infrastructure/application differences, verification, troubleshooting, and legacy Elasticsearch comparison.  
**Primary scope:** Red Hat OpenShift Logging 6.x with Vector, `ClusterLogForwarder`, and `LokiStack`. Legacy Elasticsearch/Fluentd behavior is included for migration awareness.

---

## 1. What “log retention” really means in OpenShift

Log retention is the policy and mechanism that decides **how long logs remain searchable or stored** before they are pruned, deleted, expired, or moved to another system.

In OpenShift, retention is not a single switch. It exists at multiple layers:

```text
Application / node generates logs
        |
        v
Node-level local log files and journald
        |
        v
Vector collector reads and forwards logs
        |
        v
ClusterLogForwarder decides destinations and filters
        |
        v
LokiStack stores logs in object storage and local PVC-backed working data
        |
        v
Object storage lifecycle, Loki retention, or external SIEM retention deletes old data
```

A senior OpenShift administrator must separate these layers:

| Layer | Responsible component | Retention meaning | Main risk if misconfigured |
|---|---|---|---|
| Container log files on node | Kubelet / CRI-O | Local rotated pod log files | Node disk pressure, missing logs before collector reads them |
| Journald / node system logs | systemd-journald | Local node journal retention and rate limiting | Dropped node logs, noisy system logs filling disk |
| Collector buffering | Vector | Temporary buffering/retry, not archival retention | Backpressure, dropped/late logs |
| Forwarding selection | `ClusterLogForwarder` | Which logs are sent to which output | Logs never arrive at store; retention cannot help |
| LokiStack | Loki Operator / Loki components | Queryable retention for streams/tenants | Bucket grows forever, old logs still queryable, or needed logs deleted too early |
| Object storage | S3/GCS/Azure/ODF/Swift lifecycle | Physical object deletion/expiration | High cost, compliance gap, or premature deletion |
| External log platform | Splunk/Elastic/CloudWatch/SIEM | Enterprise long-term retention | Compliance and forensics gaps |

**Important operational rule:** Retention applies only to logs that are successfully collected and stored. If a `ClusterLogForwarder` pipeline does not include `audit`, for example, no audit retention policy in Loki can preserve audit logs because those logs never reach Loki.

## 2. Modern OpenShift Logging 6.x architecture and retention ownership

In current OpenShift Logging 6.x, log collection and forwarding are managed through the newer `observability.openshift.io/v1` `ClusterLogForwarder` API. Vector is the supported collector implementation. Loki replaces Elasticsearch as the supported managed log store, and the OpenShift console/observability UI replaces the old Kibana-based experience.

At a high level:

```text
[Node log sources]
  /var/log/containers/*.log
  /var/log/pods/*
  journald
  audit files
        |
        v
[Vector collector DaemonSet]
        |
        v
[ClusterLogForwarder pipelines]
        |
        +--> LokiStack output
        +--> Kafka / Splunk / HTTP / syslog / cloud outputs
        +--> Multiple destinations if required

[LokiStack]
  Gateway        - tenant-aware authenticated access
  Distributor    - receives writes
  Ingester       - buffers and writes chunks
  Querier        - reads chunks/indexes
  Query frontend - query acceleration
  Compactor      - compaction and retention-related deletion work
  Ruler          - alerting/rule evaluation where enabled
        |
        v
[Object storage]
  S3 / S3-compatible / ODF RGW / Azure / GCS / Swift
```

For retention, the key point is this:

- `ClusterLogForwarder` controls **what gets collected and sent**.
- `LokiStack.spec.limits.*.retention` controls **stream/tenant retention intent**.
- Object storage lifecycle controls **provider-side physical expiration**.
- S3 permissions such as delete/tag operations determine whether old objects can actually be removed.
- External systems must have their own independent retention policy.

## 3. Types of logs and typical retention intent

OpenShift Logging classifies logs into three main types.

### 3.1 Application logs

Application logs are produced by user workloads in regular application namespaces. Examples:

```text
payment-api-7cc9bdf5bc-jkx7p payment-api INFO request_id=abc status=200 latency_ms=45
inventory-worker-65f8d7cfc9-bx2f2 worker ERROR failed to reserve item sku=123
```

Common retention goals:

- Short troubleshooting: 3 to 7 days
- Production incident analysis: 7 to 14 days
- Regulated application logs: often forwarded externally for 30, 90, 180, or 365+ days

Application logs are usually the largest volume source, so retention design must include namespace-level and noisy workload policies.

### 3.2 Infrastructure logs

Infrastructure logs come from OpenShift and Kubernetes namespaces such as `openshift-*`, `kube-*`, `default`, and node/system services.

Examples:

```text
openshift-apiserver operator reconciliation messages
kubelet.service logs
CRI-O logs
router / ingress controller logs
monitoring stack logs
machine-config-daemon logs
```

Common retention goals:

- Platform troubleshooting: 7 to 14 days
- Upgrade investigation: keep at least the upgrade window plus a buffer
- High-volume router/access logs: sometimes shorter or sent to a dedicated backend

### 3.3 Audit logs

Audit logs contain security-relevant API activity. Examples:

```text
user=alice verb=create resource=secrets namespace=prod
system:serviceaccount:ci:pipeline verb=patch resource=deployments namespace=frontend
```

Common retention goals:

- Local short-term investigation: 7 to 30 days
- Compliance/security: usually external SIEM/object archive for 90 days to multiple years

Audit logs are sensitive and often high-volume. Treat local Loki retention as fast operational search, not as your only compliance archive.

## 4. Retention strategy: local troubleshooting vs long-term compliance

A good production strategy usually has two retention tiers:

```text
Tier 1: On-cluster LokiStack
  Purpose: fast troubleshooting, recent queries, developer/SRE visibility
  Typical retention: 3-30 days depending on size and support limits

Tier 2: External archive/SIEM/log platform
  Purpose: compliance, security investigation, enterprise analytics
  Typical retention: 30 days to several years
```

Do not design on-cluster Loki as your only long-term compliance repository. OpenShift’s Loki deployment is optimized for recent troubleshooting queries. For long retention and heavy historical search, forward to an external log store or archival system.

## 5. The four retention control planes

### 5.1 Source-node retention

OpenShift nodes store local logs before and during collection. Two important sources are container log files and journald.

#### Container log files

Container logs are written on the node and rotated by kubelet. In OpenShift, kubelet behavior can be managed with a `KubeletConfig` CR. For example, OpenShift supports setting `containerLogMaxSize` in a `KubeletConfig` to control the maximum container log file size before rotation.

Example:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: set-worker-container-log-size
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: set-worker-container-log-size
  kubeletConfig:
    containerLogMaxSize: 50Mi
```

Operational notes:

- This is **node-local rotation**, not centralized retention.
- If container logs rotate too aggressively before Vector reads them, you can lose logs.
- If container logs rotate too slowly or are too large, nodes can hit disk pressure.
- Apply `KubeletConfig` carefully because it rolls through Machine Config Pools and can reboot nodes.

#### Journald logs

OpenShift node-level service logs use systemd-journald. You can manage journald settings by writing `/etc/systemd/journald.conf` through MachineConfig/Butane.

Example conceptual settings:

```ini
Compress=yes
Storage=persistent
MaxRetentionSec=1month
SystemMaxUse=8G
SystemKeepFree=20%
SystemMaxFileSize=10M
RateLimitIntervalSec=30s
RateLimitBurst=10000
```

Operational notes:

- `MaxRetentionSec` limits local journal age.
- `SystemMaxUse` caps local journal disk usage.
- Rate limiting can drop logs during bursts.
- Increasing node-local retention does not increase Loki retention.

### 5.2 Collector and forwarding retention

The collector is not the retention system. Vector is responsible for reading logs and forwarding them through pipelines.

`ClusterLogForwarder` determines:

- Which log types are collected: `application`, `infrastructure`, `audit`
- Which outputs receive the logs
- Which filters/pruning are applied
- What service account identity the collector uses

Example minimal LokiStack forwarding pipeline:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: app-infra-to-loki
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

Before adding log types, bind collector permissions:

```bash
oc create sa collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Advanced warning:

- If you add `audit` to `inputRefs` without the `collect-audit-logs` binding, the operator can remove the collector DaemonSet as a protective failure state.
- If the collector cannot validate the LokiStack gateway certificate because `tls.ca` is missing, the `ClusterLogForwarder` might appear `Ready`, but logs can fail at runtime.

### 5.3 LokiStack retention

LokiStack retention is configured in the `LokiStack` custom resource under `spec.limits`.

Retention can be:

- Global: applies to all tenants/log streams unless overridden.
- Per-tenant: applies to `application`, `infrastructure`, or `audit` tenant.
- Stream-based: applies to streams matching a LogQL label selector.

The OpenShift tenant names are:

```text
application
infrastructure
audit
```

Example global retention:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.small
  replicationFactor: 1
  storageClassName: gp3-csi
  storage:
    schemas:
    - effectiveDate: "2026-07-01"
      version: v13
    secret:
      name: logging-loki-s3
      type: s3
  tenants:
    mode: openshift-logging
  limits:
    global:
      retention:
        days: 14
```

Example per-tenant retention:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.small
  replicationFactor: 1
  storageClassName: gp3-csi
  storage:
    schemas:
    - effectiveDate: "2026-07-01"
      version: v13
    secret:
      name: logging-loki-s3
      type: s3
  tenants:
    mode: openshift-logging
  limits:
    global:
      retention:
        days: 14
    tenants:
      application:
        retention:
          days: 7
      infrastructure:
        retention:
          days: 14
      audit:
        retention:
          days: 30
```

Example stream-based retention:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.small
  replicationFactor: 1
  storageClassName: gp3-csi
  storage:
    schemas:
    - effectiveDate: "2026-07-01"
      version: v13
    secret:
      name: logging-loki-s3
      type: s3
  tenants:
    mode: openshift-logging
  limits:
    global:
      retention:
        days: 14
        streams:
        - selector: '{log_type="infrastructure"}'
          days: 7
          priority: 1
        - selector: '{kubernetes_namespace_name=~"dev|test|sandbox"}'
          days: 3
          priority: 2
    tenants:
      application:
        retention:
          days: 7
          streams:
          - selector: '{kubernetes_namespace_name="prod"}'
            days: 14
            priority: 10
          - selector: '{kubernetes_namespace_name=~"dev|qa|test"}'
            days: 3
            priority: 5
      infrastructure:
        retention:
          days: 14
      audit:
        retention:
          days: 30
```

In this model:

- Most application logs are kept 7 days.
- Production application logs are kept 14 days.
- Dev/test/qa application logs are kept 3 days.
- Infrastructure logs default to 14 days, but specific infrastructure streams may be kept 7 days.
- Audit logs are kept 30 days locally.

### 5.4 Object storage lifecycle retention

LokiStack stores actual log chunks and indexes in object storage. Object storage lifecycle policies are usually the most cost-effective way to remove old objects.

Examples:

- AWS S3 lifecycle expiration
- Azure Blob lifecycle management
- Google Cloud Storage lifecycle rules
- ODF NooBaa/RGW lifecycle rules where supported
- S3-compatible vendor lifecycle policies

Recommended design:

```text
LokiStack retention:       controls queryable stream/tenant retention intent
Object storage lifecycle:  controls provider-side expiry/delete policy
External archive:          controls compliance retention
```

Important:

- If neither bucket lifecycle nor LokiStack retention is configured, logs can remain in object storage indefinitely.
- If object storage lifecycle is shorter than LokiStack retention, data may disappear before Loki expects it, causing query gaps or errors.
- If object storage lifecycle is much longer than LokiStack retention, old data may remain physically stored and cost money even if no longer desired.
- If LokiStack is expected to delete expired objects, the object storage credentials must allow deletion.

## 6. Required object storage permissions for retention

For S3-compatible storage, LokiStack needs permissions to list, put, get, delete, and tag objects. Retention-related deletion depends especially on delete and tagging permissions.

Minimum conceptual permission set:

```text
s3:ListBucket          - list bucket contents
s3:PutObject           - write chunks/indexes
s3:GetObject           - read chunks/indexes
s3:DeleteObject        - delete expired chunks/objects
s3:GetObjectTagging    - read tags used for lifecycle/retention handling
s3:PutObjectTagging    - write tags used for lifecycle/retention handling
```

Example AWS IAM policy skeleton:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-openshift-loki-bucket"
      ]
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:DeleteObject",
        "s3:GetObjectTagging",
        "s3:PutObjectTagging"
      ],
      "Resource": [
        "arn:aws:s3:::my-openshift-loki-bucket/*"
      ]
    }
  ]
}
```

Common production mistake:

```text
LokiStack retention is configured correctly.
LokiStack status is Ready.
Queries work.
But old logs are never deleted.
```

Possible cause:

```text
The S3 credential can write/read logs but cannot delete old objects.
The compactor cannot remove expired chunks.
The bucket keeps growing.
```

## 7. LokiStack schema and retention

Use schema `v13` for new deployments unless Red Hat documentation for your exact OpenShift Logging version says otherwise.

Example:

```yaml
spec:
  storage:
    schemas:
    - effectiveDate: "2026-07-01"
      version: v13
```

Advanced notes:

- Do not remove old schema entries from existing deployments without understanding migration impact.
- Schema effective dates are UTC-sensitive.
- When adding a new schema, use a future effective date.
- Retention troubleshooting should include checking the schema because retention, compaction, and object layout are related to how Loki stores chunks and indexes.

## 8. Designing a production retention policy

### 8.1 Start with business requirements

Ask these questions before editing YAML:

1. Which log classes are required for compliance?
2. Which namespaces are production-critical?
3. What is the incident investigation window?
4. How long do developers need self-service log access?
5. What is the expected ingestion rate per day?
6. What is the maximum supported local retention for your LokiStack size/version?
7. Which logs must be sent to external SIEM or archive?
8. Which logs contain sensitive data and require pruning or restricted access?
9. What is the object storage budget?
10. Who owns bucket lifecycle policies: platform team, storage team, or cloud team?

### 8.2 Example enterprise policy

| Log class | Local Loki retention | External retention | Notes |
|---|---:|---:|---|
| Dev application logs | 3 days | Optional | Reduce noise and cost |
| QA/staging application logs | 7 days | Optional | Useful for release debugging |
| Production application logs | 14 days | 30-90+ days if required | Use stream selectors by namespace |
| Infrastructure logs | 14 days | 30-90 days | Important for upgrades and outages |
| Audit logs | 30 days local | 180-365+ days in SIEM/archive | Sensitive; restrict access |
| Router/access logs | 3-7 days local | 30+ days external if needed | Often very high volume |
| Debug/noisy namespaces | 1-3 days | Usually none | Control cost |

### 8.3 Translate requirements into CR design

Example retention CR snippet:

```yaml
spec:
  limits:
    global:
      retention:
        days: 14
    tenants:
      application:
        retention:
          days: 7
          streams:
          - selector: '{kubernetes_namespace_name=~"prod-.+"}'
            days: 14
            priority: 10
          - selector: '{kubernetes_namespace_name=~"dev-.+|test-.+|sandbox-.+"}'
            days: 3
            priority: 5
          - selector: '{kubernetes_namespace_name="loadtest"}'
            days: 1
            priority: 20
      infrastructure:
        retention:
          days: 14
      audit:
        retention:
          days: 30
```

Design explanation:

- `global.retention.days: 14` acts as a general fallback.
- `application.retention.days: 7` overrides global for application tenant.
- `prod-*` gets longer application retention.
- Dev/test/sandbox gets shorter retention.
- `loadtest` gets highest-priority shortest retention because it is noisy.
- Audit remains 30 days locally, but still should be forwarded to external SIEM if compliance requires longer.

## 9. Capacity planning for retention

Retention is a storage equation. You cannot safely choose `30d` without estimating ingestion.

### 9.1 Basic formula

```text
raw_GB_per_day = events_per_second × average_event_bytes × 86400 / 1024^3
stored_GB_per_day = raw_GB_per_day × compression_factor
required_GB = stored_GB_per_day × retention_days × safety_factor
```

Typical assumptions:

```text
compression_factor = 0.3 to 0.7, depending on log structure
safety_factor = 1.2 to 1.5
```

### 9.2 Example calculation

Assume:

```text
5,000 events/sec
600 bytes/event average
7-day retention
0.4 compression factor
1.3 safety factor
```

Calculation:

```text
raw_GB_per_day = 5000 × 600 × 86400 / 1024^3
               ≈ 241 GB/day

stored_GB_per_day = 241 × 0.4
                  ≈ 96 GB/day

required_GB = 96 × 7 × 1.3
            ≈ 874 GB
```

This is only object storage estimation. LokiStack also requires block storage PVCs for WAL, caches, and compactor working data.

### 9.3 Measure real ingestion

After deployment, measure actual ingestion for at least 24 hours before finalizing retention.

Useful checks:

```bash
# LokiStack pods
oc get pods -n openshift-logging

# Collector pods
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector

# LokiStack CR
oc get lokistack logging-loki -n openshift-logging -o yaml

# PVCs used by LokiStack
oc get pvc -n openshift-logging
```

In a mature environment, monitor:

- bytes ingested per tenant
- logs per second
- object storage growth per day
- compactor errors
- query latency
- 429/rate-limit events
- collector retries and drops
- high-cardinality labels

## 10. Retention and query behavior

Retention has two user-visible effects:

1. Old logs should no longer appear in queries after retention expiry.
2. Object storage should eventually stop growing from expired data.

Do not expect deletion to happen exactly at midnight or exactly at `N` days. Retention cleanup is asynchronous. Compaction, marker processing, object storage lifecycle jobs, provider delays, and cache behavior can create delay.

Practical verification method:

```text
1. Confirm retention CR is applied.
2. Confirm compactor/ruler/retention-related components are healthy.
3. Query a range older than the retention period.
4. Check object storage object count/size trend after cleanup window.
5. Check compactor logs for delete/permission errors.
```

Example commands:

```bash
# Show configured limits
oc get lokistack logging-loki -n openshift-logging -o yaml | sed -n '/limits:/,/managementState:/p'

# Explain retention fields from the CRD
oc explain lokistack.spec.limits.global.retention
oc explain lokistack.spec.limits.tenants.application.retention

# Check LokiStack pods
oc get pods -n openshift-logging | egrep 'loki|compactor|ruler|gateway|querier|ingester'

# Check compactor logs; adjust selector/pod names to your deployment
oc logs -n openshift-logging -l app.kubernetes.io/component=compactor --tail=200

# Check collector status
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

# Check collector logs
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

## 11. Advanced stream selectors

Loki retention stream selectors use LogQL-style label matchers.

Common labels in OpenShift logging streams include labels such as:

```text
log_type
kubernetes_namespace_name
kubernetes_pod_name
kubernetes_container_name
kubernetes_host
```

Examples:

```yaml
# Keep infrastructure logs 7 days
- selector: '{log_type="infrastructure"}'
  days: 7
  priority: 1

# Keep all namespaces starting with prod- for 14 days
- selector: '{kubernetes_namespace_name=~"prod-.+"}'
  days: 14
  priority: 10

# Keep one noisy container for 1 day
- selector: '{kubernetes_namespace_name="payments", kubernetes_container_name="debug-sidecar"}'
  days: 1
  priority: 20

# Keep OpenShift cluster monitoring logs for 7 days
- selector: '{kubernetes_namespace_name="openshift-monitoring"}'
  days: 7
  priority: 5
```

Guidelines:

- Prefer namespace and log type selectors over pod-name selectors because pod names change.
- Avoid excessive fine-grained retention rules unless business value is clear.
- Use priorities to resolve overlaps intentionally.
- Keep retention policies easy to explain during incident reviews.
- Document every exception with owner, reason, and expiry date.

## 12. Retention and high-cardinality labels

Retention rules operate on streams, and streams are defined by label sets. High-cardinality labels create many streams and can hurt query and retention performance.

Avoid making labels from values such as:

```text
request_id
trace_id
session_id
user_id
order_id
random UUID
full URL with query string
pod UID where not necessary
```

Better approach:

- Keep high-cardinality values inside the log body, not as Loki labels.
- Use labels for stable dimensions: namespace, app, container, log type, environment.
- Use application-level structured logging for search fields if your external backend supports indexing.

Retention design should not compensate for uncontrolled label cardinality. Fix label design first.

## 13. Audit log retention pattern

Audit logs deserve special handling.

Recommended pattern:

```text
Local LokiStack:
  audit retention = 7-30 days for fast incident investigation

External SIEM/archive:
  audit retention = compliance-defined period
  access control = security team only
  immutability/WORM = if required
```

Example `ClusterLogForwarder` sending audit logs to Loki and an external sink:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  - name: external-siem
    type: http
    url: https://siem.example.com/openshift/audit
    secret:
      name: siem-token
  pipelines:
  - name: audit-to-loki-and-siem
    inputRefs:
    - audit
    outputRefs:
    - default-lokistack
    - external-siem
```

Operational controls:

- Use RBAC to restrict who can read audit logs.
- Consider pruning sensitive fields before sending to broad-access destinations.
- Ensure external SIEM retention is independently verified.
- Confirm audit log forwarding after API server upgrades or logging upgrades.

## 14. Infrastructure log retention pattern

Infrastructure logs are essential for platform operations. They answer questions such as:

- Why did a node go NotReady?
- Did MCO reboot nodes during a change?
- Why did the ingress router reject traffic?
- Why did an operator degrade?
- What happened during an upgrade?

Recommended local retention:

```text
Small/non-prod cluster: 7 days
Production cluster: 14 days
Critical platform / slow change windows: 14-30 days
```

Example:

```yaml
spec:
  limits:
    tenants:
      infrastructure:
        retention:
          days: 14
          streams:
          - selector: '{kubernetes_namespace_name="openshift-monitoring"}'
            days: 7
            priority: 5
          - selector: '{kubernetes_namespace_name="openshift-ingress"}'
            days: 7
            priority: 5
```

Router and monitoring logs can be high volume. Keep them long enough for incident response but short enough to control cost.

## 15. Application log retention pattern

Application retention should be namespace-driven and aligned with environment criticality.

Example namespace labels:

```text
prod-payments
prod-core
stage-payments
dev-payments
sandbox-team-a
loadtest
```

Example policy:

```yaml
spec:
  limits:
    tenants:
      application:
        retention:
          days: 7
          streams:
          - selector: '{kubernetes_namespace_name=~"prod-.+"}'
            days: 14
            priority: 10
          - selector: '{kubernetes_namespace_name=~"stage-.+"}'
            days: 7
            priority: 8
          - selector: '{kubernetes_namespace_name=~"dev-.+|sandbox-.+"}'
            days: 3
            priority: 5
          - selector: '{kubernetes_namespace_name="loadtest"}'
            days: 1
            priority: 20
```

This is a practical balance:

- Developers still have recent logs.
- Production gets a longer troubleshooting window.
- Load test noise is controlled.
- External systems can handle long-term application audit/compliance needs.

## 16. Legacy Elasticsearch retention comparison

Older OpenShift Logging deployments used Elasticsearch and Kibana. Retention was configured differently.

Example legacy `ClusterLogging` retention policy:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogging
metadata:
  name: instance
  namespace: openshift-logging
spec:
  managementState: Managed
  logStore:
    type: elasticsearch
    retentionPolicy:
      application:
        maxAge: 1d
      infra:
        maxAge: 7d
      audit:
        maxAge: 7d
    elasticsearch:
      nodeCount: 3
```

Legacy behavior:

- Retention used `maxAge` per source.
- Elasticsearch rolled over indices and deleted rolled-over indices after the retention age.
- Default retention was commonly 7 days when no retention policy was configured in older Elasticsearch-based logging.
- The Elasticsearch CR was operator-managed; retention changes had to be made through `ClusterLogging`, not by editing the generated `Elasticsearch` CR directly.

Modern difference:

| Area | Legacy Elasticsearch | Modern LokiStack |
|---|---|---|
| Store | Elasticsearch indices | Loki chunks/indexes in object storage |
| Collector | Fluentd historically | Vector in Logging 6.x |
| API | `logging.openshift.io/v1` | `observability.openshift.io/v1` for forwarding, `loki.grafana.com/v1` for LokiStack |
| Retention | `ClusterLogging.spec.logStore.retentionPolicy` | `LokiStack.spec.limits.*.retention` plus object storage lifecycle |
| UI | Kibana | OpenShift Observability UI / console plugin |
| Long-term storage | External recommended | External recommended |

Migration note:

Do not copy old Elasticsearch retention YAML into a LokiStack deployment. The APIs and retention model are different.

## 18. Troubleshooting retention issues

### Problem 1: Bucket keeps growing forever

Symptoms:

```text
LokiStack Ready=True
Queries work
Retention configured
Object storage cost keeps increasing
Old objects remain
```

Likely causes:

```text
No object storage lifecycle rule
No LokiStack retention block
Missing s3:DeleteObject permission
Missing object tagging permissions
Compactor unhealthy
Retention cleanup delay misunderstood
```

Checks:

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml | grep -A50 retention
oc logs -n openshift-logging -l app.kubernetes.io/component=compactor --tail=300
```

Fix:

- Add retention to `LokiStack`.
- Add object storage lifecycle rule.
- Grant delete/tag permissions.
- Fix compactor scheduling/resources.

### Problem 2: Old logs still appear after retention period

Possible causes:

- Cleanup is asynchronous; wait for compaction/lifecycle processing.
- Retention rule does not match the stream labels.
- A higher-priority stream rule gives longer retention.
- Tenant-level rule overrides global rule.
- Query cache or frontend behavior briefly returns stale results.
- Bucket lifecycle is longer and Loki retention is not deleting as expected.

Checks:

```bash
oc get lokistack logging-loki -n openshift-logging -o yaml | sed -n '/limits:/,/storage:/p'
oc logs -n openshift-logging -l app.kubernetes.io/component=compactor --tail=300
```

Review the exact labels on the logs you query. Your selector must match actual stream labels.

### Problem 3: Needed logs disappeared too soon

Possible causes:

- Object storage lifecycle shorter than Loki retention.
- Stream selector matched too broadly.
- Higher-priority short-retention rule matched production logs.
- Logs were never forwarded to Loki.
- Node-local logs rotated before collector picked them up.

Fix:

- Align bucket lifecycle with Loki retention.
- Add safer namespace selector patterns.
- Use explicit production rules with higher priority.
- Confirm `ClusterLogForwarder` inputRefs and RBAC.
- Check collector errors/backpressure.

### Problem 4: Audit logs not retained

Possible causes:

- `audit` missing from `ClusterLogForwarder.inputRefs`.
- Collector service account lacks `collect-audit-logs`.
- Pipeline sends audit only to external output, not Loki.
- Audit retention rule exists but no audit tenant data is present.

Checks:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
oc get clusterrolebinding -o wide | grep collect-audit-logs
```

### Problem 5: Retention configured but compactor cannot delete

Symptoms:

```text
AccessDenied
403 Forbidden
operation error S3: DeleteObject
NoSuchBucket or invalid endpoint
x509 certificate signed by unknown authority
```

Fix:

- Add `s3:DeleteObject`.
- Add object tagging permissions.
- Fix endpoint/region/forcepathstyle.
- Configure CA bundle for private object storage.
- Confirm network egress to object storage.

### Problem 6: Logs missing during high-volume bursts

Possible causes:

- Journald rate limiting.
- Container log rotation too aggressive.
- Vector backpressure.
- Loki ingestion limits.
- Network or object storage latency.

Fix:

- Tune journald rate limits carefully.
- Increase `containerLogMaxSize` only if node disk capacity allows.
- Scale LokiStack size appropriately.
- Reduce noisy logs at source.
- Add filters to drop debug noise before storing.

## 19. Retention anti-patterns

Avoid these designs:

### Anti-pattern 1: “Keep everything for 90 days in on-cluster Loki”

Why it fails:

- Expensive object storage growth
- Slow long-range queries
- Unsupported or untested local retention window depending on version/size
- Operational blast radius inside the cluster

Better:

- Keep 7-30 days locally.
- Forward long-term logs externally.

### Anti-pattern 2: Object lifecycle shorter than Loki retention

Example:

```text
LokiStack audit retention = 30 days
S3 lifecycle expiration = 7 days
```

Result:

```text
Audit logs vanish after 7 days from object storage even though Loki expects 30 days.
```

### Anti-pattern 3: No delete permission

Example:

```text
S3 policy allows PutObject/GetObject/ListBucket but denies DeleteObject.
```

Result:

```text
Loki ingests and queries correctly, but bucket never shrinks.
```

### Anti-pattern 4: Retention exceptions with no owner

Bad:

```yaml
- selector: '{kubernetes_namespace_name="some-old-test"}'
  days: 30
```

Better:

```yaml
# Owner: Team A
# Reason: release validation until 2026-08-31
# Remove after: 2026-09-01
- selector: '{kubernetes_namespace_name="release-validation"}'
  days: 30
  priority: 10
```

### Anti-pattern 5: Retention as a substitute for log hygiene

Do not use retention alone to solve noisy logs. Fix logging level, sampling, structured fields, and application behavior.

### 20.2 Production-style per-tenant retention

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.small
  replicationFactor: 1
  storageClassName: gp3-csi
  storage:
    schemas:
    - effectiveDate: "2026-07-01"
      version: v13
    secret:
      name: logging-loki-s3
      type: s3
  tenants:
    mode: openshift-logging
  limits:
    global:
      retention:
        days: 14
    tenants:
      application:
        retention:
          days: 7
          streams:
          - selector: '{kubernetes_namespace_name=~"prod-.+"}'
            days: 14
            priority: 10
          - selector: '{kubernetes_namespace_name=~"dev-.+|test-.+|sandbox-.+"}'
            days: 3
            priority: 5
          - selector: '{kubernetes_namespace_name="loadtest"}'
            days: 1
            priority: 20
      infrastructure:
        retention:
          days: 14
      audit:
        retention:
          days: 30
```

## 22. Example interview/L3 troubleshooting questions

### Q1. Why is `ClusterLogForwarder` not enough to configure retention?

Because `ClusterLogForwarder` controls collection, filtering, and forwarding. Retention is enforced by the destination store, such as LokiStack or an external log platform, and by object storage lifecycle policies.

### Q2. Why can logs stay forever in the bucket even when Loki is working?

Because ingestion and query permissions can work with `PutObject` and `GetObject`, but deletion requires `DeleteObject`. If no bucket lifecycle exists and Loki cannot delete expired objects, the bucket continues to grow.

### Q3. Why should audit logs usually be forwarded externally?

Audit logs are sensitive, security-relevant, and often have compliance retention requirements longer than the local troubleshooting window. Local Loki is best for fast recent investigation, while external SIEM/archive handles long-term retention and access control.

### Q4. What is the difference between `application`, `infrastructure`, and `audit` tenants?

They are logical log categories used by OpenShift Logging. Application logs come from user workloads, infrastructure logs come from OpenShift/Kubernetes/system namespaces and node services, and audit logs record API/security-relevant actions.

### Q5. Why can a retention selector fail silently?

It may not match the actual stream labels. For example, selecting `{namespace="prod"}` will not work if the actual label is `kubernetes_namespace_name="prod"`.

### Q6. Why should you avoid pod-name selectors for retention?

Pod names change during rollouts and rescheduling. Namespace, container, app, and log type selectors are usually more stable.

### Q7. How do you validate whether logs are missing because of retention or forwarding?

First check `ClusterLogForwarder` status and collector logs. If the log type was never collected or forwarded, retention is irrelevant. Then check LokiStack retention, compactor logs, and query boundaries.

## 24. Senior admin best practices

1. Treat local Loki retention as an operational troubleshooting window, not your full compliance strategy.
2. Configure both LokiStack retention and object storage lifecycle intentionally.
3. Confirm delete/tag permissions before trusting retention.
4. Keep audit logs local for recent investigation and external for compliance.
5. Use namespace-based and tenant-based retention policies; avoid fragile pod-name rules.
6. Keep stream selectors simple and documented.
7. Tune noisy workloads at the source instead of relying only on retention.
8. Monitor object storage growth daily after changes.
9. Test retention after real time passes; deletion is asynchronous.
10. Back up all logging CRs before editing.
11. Align retention with upgrade and incident investigation windows.
12. Use GitOps for retention policies, with code review and owner metadata.
13. Validate `ClusterLogForwarder` RBAC before adding new log types.
14. Do not edit operator-generated resources directly unless documentation explicitly supports it.
15. Revisit retention after every major OpenShift Logging upgrade.

## 27. Final takeaway

Log retention in OpenShift is a **platform design decision**, not just a YAML field. A strong design connects five things:

```text
What logs are collected
Where logs are forwarded
How long Loki keeps them queryable
When object storage physically deletes them
Where long-term compliance logs live
```

For advanced administration, always validate the full chain: source node → Vector collector → `ClusterLogForwarder` → LokiStack → object storage lifecycle → external archive. Most real production incidents happen because one link in that chain was assumed instead of verified.
