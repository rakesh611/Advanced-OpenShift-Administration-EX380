# SIEM Integration in OpenShift Logging

**Audience:** Advanced OpenShift Administration / OpenShift platform engineer with ~10 years of Linux, DevOps, Kubernetes, and security operations experience  
**Scope:** Red Hat OpenShift Logging 6.x style configuration using `ClusterLogForwarder` API `observability.openshift.io/v1`  
**Goal:** Understand how OpenShift logs are collected, filtered, secured, and forwarded to SIEM platforms such as Splunk, QRadar, Elastic/Sentinel-like HTTP collectors, ArcSight/syslog collectors, Kafka-based log gateways, and long-term compliance archives.

---

## 1. What SIEM integration means in OpenShift

**SIEM** stands for **Security Information and Event Management**. In an enterprise OpenShift environment, SIEM integration means sending security-relevant and operational log events from OpenShift to an external security analytics platform where teams can perform:

- Threat detection
- Audit trail analysis
- Compliance reporting
- Incident investigation
- Correlation with firewall, IAM, endpoint, cloud, and network telemetry
- Long-term retention and legal hold
- Alerting based on suspicious activity

OpenShift Logging itself is **not a SIEM**. It collects, processes, stores, visualizes, and forwards logs. The SIEM is usually an external system that performs correlation, detection, alerting, and retention according to security policy.

In practical terms, SIEM integration in OpenShift Logging is implemented through the **ClusterLogForwarder** custom resource. The log collector runs on cluster nodes, reads selected log sources, applies filters if required, and forwards the records to one or more external destinations.

---

## 2. Why OpenShift clusters need SIEM integration

A production OpenShift cluster is a high-value control plane. If an attacker compromises OpenShift, they can potentially:

- Create privileged pods
- Mount host paths
- Access secrets
- Modify RBAC
- Change routes
- Exfiltrate container images
- Disable monitoring
- Create persistence through workloads or operators
- Abuse service account tokens
- Modify admission, network, or security policies

Because of this, security teams usually require OpenShift logs to be forwarded to a centralized SIEM. Local cluster storage alone is not enough because a compromised cluster might lose or alter local logs. Forwarding logs out of the cluster gives security teams an independent evidence trail.

Typical enterprise reasons:

| Requirement | Why SIEM helps |
|---|---|
| Compliance | PCI-DSS, ISO 27001, SOC 2, HIPAA-like controls, internal audit requirements |
| Security detection | Detect privilege escalation, suspicious API calls, failed authentication, abnormal pod creation |
| Central retention | Store audit logs outside the OpenShift cluster for months or years |
| Investigation | Correlate OpenShift events with firewall, EDR, identity provider, cloud, and network logs |
| Separation of duties | Developers may see app logs, but security owns audit logs |
| Tamper resistance | External SIEM/archive reduces dependency on cluster-local log storage |

## 3. OpenShift Logging architecture for SIEM forwarding

At a high level:

```text
+-----------------------------+
| OpenShift Cluster            |
|                             |
|  Pods / Nodes / API Server  |
|      |                      |
|      v                      |
|  Log files / journald /     |
|  audit sources              |
|      |                      |
|      v                      |
|  OpenShift Logging Collector|
|  DaemonSet, usually Vector  |
|      |                      |
|      v                      |
|  ClusterLogForwarder        |
|  inputs -> filters ->       |
|  pipelines -> outputs       |
+-------------+---------------+
              |
              | TLS / HTTPS / Syslog / Kafka / Cloud API
              v
+---------------------------------------------+
| External SIEM / Log Gateway / Archive        |
| Splunk, QRadar, Elastic, ArcSight, Kafka,    |
| Sentinel gateway, CloudWatch, S3, etc.       |
+---------------------------------------------+
```

The important OpenShift objects are:

| Component | Purpose |
|---|---|
| **Red Hat OpenShift Logging Operator** | Deploys and manages the log collector resources. |
| **ClusterLogForwarder** | Defines what logs to collect, how to filter them, and where to send them. |
| **Collector DaemonSet** | Runs collector pods on nodes to read and forward logs. |
| **ServiceAccount** | Identity used by collector pods. |
| **ClusterRoleBinding** | Grants collector permission to read application, infrastructure, or audit logs. |
| **Secret / ConfigMap** | Stores SIEM tokens, usernames, passwords, CA bundles, TLS material, or cloud credentials. |
| **NetworkPolicy** | Controls egress from collector pods to SIEM endpoints when restrictive networking is enabled. |

## 4. Important change in newer OpenShift Logging

In modern Red Hat OpenShift Logging 6.x, `ClusterLogForwarder` uses this API:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
```

Older tutorials often show:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
```

That older API is common in OpenShift Logging 5.x and older documentation. For current advanced administration, always check your installed operator version and CRD:

```bash
oc get crd | grep -i clusterlogforwarder
oc explain clusterlogforwarder.spec
oc api-resources | grep -i clusterlogforwarder
```

For OpenShift Logging 6.x, prefer `observability.openshift.io/v1` unless your cluster clearly runs the legacy API.

## 5. Log sources relevant to SIEM

OpenShift Logging commonly works with three built-in log input types.

### 5.1 Application logs

Application logs are container logs generated by user workloads. They usually come from pod `stdout` and `stderr`.

Examples:

- Java application exceptions
- Nginx access logs
- Spring Boot application logs
- Database container logs
- Business application security logs
- Login failure messages from applications

SIEM use cases:

- Application attack detection
- Failed login correlation
- Suspicious user behavior
- API abuse detection
- WAF-to-application correlation
- Error spikes after deployment

OpenShift input reference:

```yaml
inputRefs:
  - application
```

### 5.2 Infrastructure logs

Infrastructure logs come from OpenShift and Kubernetes components, node journals, and system namespaces.

Examples:

- Kubelet logs
- CRI-O logs
- SDN/OVN logs
- Router logs
- Machine Config Operator logs
- Ingress operator logs
- OpenShift control plane component logs

SIEM use cases:

- Node-level suspicious behavior
- Repeated control plane errors
- Router/ingress anomalies
- Cluster component restarts
- Node authorization issues
- Privileged workload activity indicators

OpenShift input reference:

```yaml
inputRefs:
  - infrastructure
```

### 5.3 Audit logs

Audit logs are the most important SIEM source for OpenShift security monitoring. They record security-relevant API and system events.

Typical audit sources include:

| Audit source | Meaning |
|---|---|
| `kubeAPI` | Kubernetes API server audit logs |
| `openshiftAPI` | OpenShift API server audit logs |
| `auditd` | Node audit daemon logs |
| `ovn` | Open Virtual Network audit logs |

OpenShift input reference:

```yaml
inputRefs:
  - audit
```

Audit logs are sensitive and high-volume. Treat them differently from developer application logs. In many environments, audit logs should go directly to the SIEM or immutable archive, not to a shared developer-facing log store.

## 6. Common SIEM integration patterns

### Pattern 1: Direct SIEM forwarding

The collector sends logs directly to the SIEM endpoint.

```text
OpenShift Collector -> Splunk HEC / QRadar Syslog / Elastic HTTP / Cloud SIEM API
```

Best for:

- Simple architecture
- Low to medium volume
- SIEM endpoint reachable from cluster
- SIEM supports backpressure and HA

Risk:

- If the SIEM endpoint is slow or unavailable, logs might be delayed or dropped depending on tuning and delivery mode.

### Pattern 2: Forward through a log gateway

The collector sends logs to an intermediate gateway such as rsyslog, Vector, Fluent Bit, Logstash, or OpenTelemetry Collector.

```text
OpenShift Collector -> Log Gateway -> SIEM
```

Best for:

- Format transformation
- Multi-SIEM routing
- Token isolation
- Centralized TLS termination
- Site-to-site routing
- Air-gapped or restricted networks

### Pattern 3: Kafka buffering layer

OpenShift sends logs to Kafka, and SIEM consumers pull from Kafka topics.

```text
OpenShift Collector -> Kafka -> SIEM Consumer / Logstash / Custom Parser
```

Best for:

- Large-scale clusters
- Multi-cluster environments
- Replay capability
- Decoupling OpenShift from SIEM availability
- Multiple consumers: SIEM, data lake, analytics, archive

### Pattern 4: Dual-path audit forwarding

Audit logs go to both real-time SIEM and long-term archive.

```text
OpenShift audit logs -> SIEM for detection
                     -> S3/object storage for retention
```

Best for:

- Compliance-heavy environments
- Separation of real-time monitoring and long-term retention
- Immutable evidence storage

## 7. Supported output types useful for SIEM

Common `ClusterLogForwarder` output types useful for SIEM integration:

| Output type | Common SIEM use |
|---|---|
| `splunk` | Splunk HTTP Event Collector integration |
| `syslog` | QRadar, ArcSight, rsyslog, syslog-ng, legacy SIEM collectors |
| `http` | Generic HTTPS ingestion endpoint, custom collector, webhook gateway |
| `kafka` | Buffered enterprise event streaming before SIEM ingestion |
| `elasticsearch` | External Elasticsearch-compatible log analytics systems |
| `cloudwatch` | AWS-native logging/security analytics pipeline |
| `s3` | Long-term archive and data lake integration |
| `otlp` | OpenTelemetry-based log gateway; check support status before production use |

Important production point: do not choose output type based only on what is easiest to configure. Choose it based on reliability, parsing quality, retention requirements, network topology, authentication, and SIEM ingestion limits.

## 8. Prerequisites before configuring SIEM forwarding

### 8.1 Confirm operator and namespace

```bash
oc get ns openshift-logging
oc get operators -A | grep -i logging
oc get pods -n openshift-logging
```

### 8.2 Confirm CRD and API version

```bash
oc get crd | grep -i clusterlogforwarder
oc explain clusterlogforwarder.spec
```

### 8.3 Confirm SIEM endpoint connectivity

From an OpenShift debug pod or temporary test pod:

```bash
oc run net-test -n openshift-logging --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc exec -n openshift-logging net-test -- curl -vk https://splunk.example.com:8088/services/collector/health
oc delete pod net-test -n openshift-logging
```

For syslog TCP/TLS:

```bash
oc run net-test -n openshift-logging --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc exec -n openshift-logging net-test -- bash -c 'timeout 5 bash -c "</dev/tcp/syslog.example.com/6514" && echo reachable || echo failed'
oc delete pod net-test -n openshift-logging
```

If the image does not have `nc` or `telnet`, use Bash `/dev/tcp`, `curl`, or install troubleshooting tools in a temporary debug image.

## 9. Collector identity and RBAC

The collector must have explicit permission to read each log type. This is a critical production and exam point.

Create a collector service account:

```bash
oc create sa collector -n openshift-logging
```

Grant application log access:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector
```

Grant infrastructure log access:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

Grant audit log access:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Verify:

```bash
oc get clusterrolebinding -o wide | grep -E 'collect-application|collect-infrastructure|collect-audit'
```

Very important: grant RBAC **before** referencing that log type in `ClusterLogForwarder`. If the CR requests a log type that the collector service account is not authorized to collect, the operator can remove the collector DaemonSet as a protective action, stopping cluster log collection.

## 10. Secret and certificate design

SIEM forwarding often needs credentials and TLS material.

Common secret examples:

| Integration | Secret content |
|---|---|
| Splunk HEC | HEC token |
| Generic HTTP | username/password or token/header material |
| Syslog TLS | CA certificate, client certificate/key if required by gateway design |
| Kafka SASL | username/password and CA certificate |
| Elasticsearch | username/password, CA certificate, custom headers |
| Cloud outputs | cloud access keys, IAM role references, STS configuration |

Create secrets in the same namespace where the `ClusterLogForwarder` runs, commonly `openshift-logging`.

Example CA secret:

```bash
oc -n openshift-logging create secret generic siem-ca \
  --from-file=ca-bundle.crt=/path/to/siem-ca.crt
```

Example Splunk token secret:

```bash
oc -n openshift-logging create secret generic splunk-hec-secret \
  --from-literal=hecToken='<SPLUNK_HEC_TOKEN>'
```

Security recommendations:

- Never hardcode tokens in YAML committed to Git.
- Use sealed secrets, External Secrets Operator, Vault, or another approved secret-management workflow.
- Rotate SIEM tokens periodically.
- Use separate tokens per cluster or environment.
- Use TLS with CA validation.
- Avoid `insecureSkipVerify: true` outside temporary testing.
- Restrict egress from collector pods to approved SIEM endpoints only.

## 11. Example 1: Forward application and infrastructure logs to Splunk HEC

Use this when Splunk is the SIEM or central logging platform.

### 11.1 Create Splunk HEC token secret

```bash
oc -n openshift-logging create secret generic splunk-hec-secret \
  --from-literal=hecToken='<SPLUNK_HEC_TOKEN>'
```

### 11.2 ClusterLogForwarder for Splunk

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: siem-forwarder
  namespace: openshift-logging
spec:
  managementState: Managed
  serviceAccount:
    name: collector
  outputs:
    - name: splunk-hec
      type: splunk
      splunk:
        url: https://splunk.example.com:8088
        authentication:
          token:
            secretName: splunk-hec-secret
            key: hecToken
        index: '{.log_type||"openshift"}'
        source: '{.log_source||"openshift"}'
        indexedFields:
          - .log_type
          - .log_source
          - .kubernetes.namespace_name
        tuning:
          compression: gzip
      tls:
        ca:
          secretName: siem-ca
          key: ca-bundle.crt
  pipelines:
    - name: app-and-infra-to-splunk
      inputRefs:
        - application
        - infrastructure
      outputRefs:
        - splunk-hec
```

Apply:

```bash
oc apply -f clf-splunk.yaml
```

Verify:

```bash
oc get clusterlogforwarder siem-forwarder -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

### 11.3 Splunk field strategy

Recommended fields to index or make searchable:

| Field | Why it matters |
|---|---|
| `.log_type` | application, infrastructure, audit separation |
| `.log_source` | container, node, kubeAPI, auditd, ovn, etc. |
| `.kubernetes.namespace_name` | tenant/project analysis |
| `.kubernetes.pod_name` | workload investigation |
| `.kubernetes.container_name` | container-level root cause |
| `.hostname` | node-level correlation |
| `.level` | severity-based searching |

Be careful with indexed fields. Indexing too many fields increases SIEM storage and ingestion cost.

## 12. Example 2: Forward audit logs to Splunk with pruning

Audit logs are security-sensitive and can be very large. Before forwarding them to a SIEM, you might prune high-volume fields while keeping forensic value.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: audit-siem-forwarder
  namespace: openshift-logging
spec:
  managementState: Managed
  serviceAccount:
    name: collector
  filters:
    - name: prune-audit-heavy-fields
      type: prune
      prune:
        in:
          - .audit.requestObject
          - .audit.responseObject
          - .audit.managedFields
  outputs:
    - name: splunk-audit
      type: splunk
      splunk:
        url: https://splunk.example.com:8088
        authentication:
          token:
            secretName: splunk-hec-secret
            key: hecToken
        index: openshift_audit
        source: '{.log_source||"audit"}'
        indexedFields:
          - .log_type
          - .log_source
          - .audit.verb
          - .audit.user.username
      tls:
        ca:
          secretName: siem-ca
          key: ca-bundle.crt
  pipelines:
    - name: audit-to-splunk
      inputRefs:
        - audit
      filterRefs:
        - prune-audit-heavy-fields
      outputRefs:
        - splunk-audit
```

Before applying this, make sure audit RBAC exists:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Useful SIEM detections from OpenShift audit logs:

| Suspicious behavior | What to search for |
|---|---|
| Privilege escalation | RoleBinding/ClusterRoleBinding creation, SCC changes |
| Secret access | `get`, `list`, `watch` on secrets |
| Service account abuse | TokenRequest, secret mount, unusual service account usage |
| Privileged workload | Pods using privileged SCC, hostPath, hostNetwork, hostPID |
| Network weakening | NetworkPolicy delete/update |
| Persistence | CronJob, DaemonSet, Operator, Deployment creation in unusual namespace |
| Defense evasion | Deleting logs, disabling monitoring, modifying logging resources |
| Suspicious exec | `pods/exec`, `pods/attach`, `pods/portforward` |

## 13. Example 3: Forward logs to a syslog-based SIEM over TLS

Many enterprise SIEMs, including QRadar/ArcSight-style deployments, ingest syslog. Use TLS syslog when possible.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: syslog-siem-forwarder
  namespace: openshift-logging
spec:
  managementState: Managed
  serviceAccount:
    name: collector
  outputs:
    - name: qradar-syslog
      type: syslog
      syslog:
        url: tls://qradar-syslog.example.com:6514
        rfc: RFC5424
        facility: local0
        severity: informational
        appName: openshift-{.log_type||"unknown"}
        procId: '{.kubernetes.namespace_name||"cluster"}'
        msgId: '{.log_source||"openshift"}'
        payloadKey: '{.message}'
        enrichment: KubernetesMinimal
        tuning:
          deliveryMode: AtLeastOnce
      tls:
        ca:
          secretName: siem-ca
          key: ca-bundle.crt
  pipelines:
    - name: infra-and-audit-to-syslog-siem
      inputRefs:
        - infrastructure
        - audit
      outputRefs:
        - qradar-syslog
```

Apply:

```bash
oc apply -f clf-syslog-siem.yaml
```

Verify on OpenShift:

```bash
oc get clusterlogforwarder syslog-siem-forwarder -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Verify on SIEM/syslog receiver:

- Confirm TCP/TLS listener on port `6514`
- Confirm client certificate policy if mutual TLS is required
- Confirm RFC format expected by SIEM parser: `RFC3164` or `RFC5424`
- Confirm facility mapping
- Confirm source host and app name parsing
- Confirm event payload remains structured enough for detection rules

Production recommendation: use `RFC5424` where possible because it is more structured than legacy `RFC3164`.

## 14. Example 4: Forward selected namespace logs to a generic HTTPS SIEM gateway

Use this when the SIEM has a custom HTTPS collector or when you send to an intermediate log gateway.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: http-siem-forwarder
  namespace: openshift-logging
spec:
  managementState: Managed
  serviceAccount:
    name: collector
  inputs:
    - name: payment-app-logs
      type: application
      application:
        includes:
          - namespace: payment-prod
          - namespace: payment-dr
        excludes:
          - namespace: payment-dev
  outputs:
    - name: https-siem-gateway
      type: http
      http:
        url: https://siem-gateway.example.com/openshift/logs
        timeout: 300
        headers:
          X-Cluster-Name: ocp-prod-01
          X-Environment: production
        authentication:
          username:
            secretName: http-siem-basic-auth
            key: username
          password:
            secretName: http-siem-basic-auth
            key: password
      tls:
        ca:
          secretName: siem-ca
          key: ca-bundle.crt
  pipelines:
    - name: payment-apps-to-siem
      inputRefs:
        - payment-app-logs
      outputRefs:
        - https-siem-gateway
```

Create the basic auth secret:

```bash
oc -n openshift-logging create secret generic http-siem-basic-auth \
  --from-literal=username='<USER>' \
  --from-literal=password='<PASSWORD>'
```

This pattern is useful when:

- A central security team owns the SIEM gateway
- All clusters must send to a common endpoint
- The gateway normalizes OpenShift fields into the organization’s event schema
- You need to hide SIEM tokens from individual clusters

## 15. Example 5: Forward logs to Kafka before SIEM

Kafka is useful when log volume is high or the SIEM cannot safely absorb direct burst traffic from multiple clusters.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: kafka-siem-forwarder
  namespace: openshift-logging
spec:
  managementState: Managed
  serviceAccount:
    name: collector
  outputs:
    - name: kafka-security-topic
      type: kafka
      kafka:
        url: tls://kafka-bootstrap.logging-gateway.example.com:9093/openshift-security
        authentication:
          sasl:
            username:
              secretName: kafka-sasl-secret
              key: username
            password:
              secretName: kafka-sasl-secret
              key: password
        topic: '{.log_type||"openshift"}'
      tls:
        ca:
          secretName: kafka-ca
          key: ca-bundle.crt
  pipelines:
    - name: audit-and-infra-to-kafka
      inputRefs:
        - audit
        - infrastructure
      outputRefs:
        - kafka-security-topic
```

Kafka design recommendations:

- Use separate topics for audit, infrastructure, and application logs.
- Use replication factor appropriate for security retention requirements.
- Define retention long enough to replay during SIEM outages.
- Monitor consumer lag.
- Secure Kafka with TLS and SASL.
- Validate message size limits for large audit events.
- Avoid mixing confidential audit logs with low-trust consumers.

## 16. Filtering strategy before sending to SIEM

Filtering is where experienced administrators save money and reduce noise without destroying forensic value.

### 16.1 Drop filter

Use drop filters to remove low-value records.

Example: drop debug logs from application logs before sending to expensive SIEM storage.

```yaml
filters:
  - name: drop-debug
    type: drop
    drop:
      - test:
          - field: .level
            matches: debug
```

Use cases:

- Drop debug noise
- Drop health-check access logs
- Drop logs from non-production namespaces
- Drop known noisy sidecars

Be careful: dropping too aggressively can remove evidence needed during incident response.

### 16.2 Prune filter

Use prune filters to remove sensitive or high-volume fields while keeping the log record.

Example:

```yaml
filters:
  - name: prune-sensitive-audit-fields
    type: prune
    prune:
      in:
        - .audit.requestObject
        - .audit.responseObject
        - .kubernetes.annotations
```

Use cases:

- Reduce audit log payload size
- Remove sensitive object content
- Remove noisy annotations
- Prevent PII leaving the cluster
- Meet data-sovereignty requirements

Important: do not remove required fields such as log type, message, namespace, pod, container, or severity fields needed by the logging pipeline and SIEM parser.

### 16.3 Namespace-based filtering

Forward only selected namespaces:

```yaml
inputs:
  - name: prod-app-logs
    type: application
    application:
      includes:
        - namespace: app-prod
        - namespace: app-dr
      excludes:
        - namespace: app-dev
```

### 16.4 Label-based filtering

Forward only security-critical workloads:

```yaml
inputs:
  - name: pci-workloads
    type: application
    application:
      selector:
        matchLabels:
          compliance: pci
```

Use this for:

- PCI workloads
- Internet-facing apps
- Authentication services
- Payment services
- Privileged automation namespaces

## 17. Rate limiting and high-volume protection

A SIEM integration must handle noisy workloads. Otherwise, one bad application can increase ingestion cost or cause forwarding backpressure.

Example input and output rate limiting:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: rate-limited-siem-forwarder
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
    - name: limited-app-logs
      type: application
      application:
        tuning:
          rateLimitPerContainer:
            maxRecordsPerSecond: 100
  outputs:
    - name: limited-splunk
      type: splunk
      splunk:
        url: https://splunk.example.com:8088
        authentication:
          token:
            secretName: splunk-hec-secret
            key: hecToken
      rateLimit:
        maxRecordsPerSecond: 1000
  pipelines:
    - name: limited-apps-to-splunk
      inputRefs:
        - limited-app-logs
      outputRefs:
        - limited-splunk
```

Operational warning: rate limits can drop logs. Monitor collector metrics and SIEM ingestion counters. Rate limiting should be a controlled protection mechanism, not a hidden data-loss mechanism.

## 18. Multi-destination forwarding

One pipeline can send the same log stream to multiple outputs. This is useful when different teams have different needs.

```yaml
pipelines:
  - name: audit-to-siem-and-archive
    inputRefs:
      - audit
    filterRefs:
      - prune-audit-heavy-fields
    outputRefs:
      - splunk-audit
      - s3-compliance-archive
```

Design examples:

| Log type | Destination 1 | Destination 2 |
|---|---|---|
| Application | LokiStack for developers | Splunk for production security alerts |
| Infrastructure | Elasticsearch/Loki for SRE | SIEM for suspicious cluster behavior |
| Audit | SIEM for detection | S3/object storage for immutable retention |

Important: each output works independently. If one output has issues, check whether the other outputs are still receiving logs.

## 19. Field normalization for SIEM

A SIEM is only useful if logs are normalized well enough to search and correlate.

Recommended OpenShift fields for SIEM parsing:

| Field | Purpose |
|---|---|
| `cluster_id` or custom cluster label | Identify source cluster |
| `.log_type` | application, infrastructure, audit |
| `.log_source` | container, node, kubeAPI, openshiftAPI, auditd, ovn |
| `.hostname` | Node correlation |
| `.kubernetes.namespace_name` | Tenant/project context |
| `.kubernetes.pod_name` | Workload context |
| `.kubernetes.container_name` | Container context |
| `.kubernetes.labels` | Application/team/compliance classification |
| `.level` | Severity |
| `.message` | Main event payload |
| `.audit.user.username` | User identity for audit events |
| `.audit.verb` | API action such as create, update, delete, get |
| `.audit.objectRef.resource` | Kubernetes resource type |
| `.audit.objectRef.namespace` | Target namespace |
| `.audit.sourceIPs` | Client/source IP |

Recommended labels to add at workload level:

```yaml
metadata:
  labels:
    app.kubernetes.io/name: payment-api
    app.kubernetes.io/part-of: payment-platform
    environment: production
    owner: payments-team
    compliance: pci
```

Good labels make SIEM queries and dashboards much better.

## 20. Security hardening for SIEM integration

### 20.1 Use TLS everywhere

Use HTTPS, TLS syslog, or TLS Kafka. Avoid plaintext syslog UDP for sensitive logs.

Bad for production:

```yaml
url: udp://siem.example.com:514
```

Better:

```yaml
url: tls://siem.example.com:6514
```

### 20.2 Validate certificates

Use CA bundles:

```yaml
tls:
  ca:
    secretName: siem-ca
    key: ca-bundle.crt
```

Avoid this except for temporary testing:

```yaml
tls:
  insecureSkipVerify: true
```

### 20.3 Restrict network egress

Collector pods should reach only required SIEM endpoints.

Check generated or existing policies:

```bash
oc get networkpolicy -n openshift-logging
oc describe networkpolicy -n openshift-logging
```

### 20.4 Use least privilege

Do not grant audit log collection unless required. But when required, grant it explicitly and protect the destination.

### 20.5 Protect audit logs separately

Audit logs should have:

- Dedicated SIEM index/source type
- Restricted access
- Longer retention
- Tamper-resistant archival
- Separate alert rules
- Stronger change control for filters

### 20.6 Separate environments

Use different SIEM indexes or tokens for:

- Production
- DR
- UAT
- Development
- Shared services
- Regulated workloads

Never mix production audit logs and development logs without clear source tagging.

## 21. Reliability design

Experienced administrators plan for SIEM outages.

Questions to ask before production rollout:

1. What happens if SIEM is unavailable for 30 minutes?
2. What happens if SIEM throttles ingestion?
3. Is log loss acceptable for application logs?
4. Is log loss acceptable for audit logs?
5. Do we need Kafka or object storage as a buffer/archive?
6. What is the maximum daily ingestion volume?
7. Are large audit events accepted by the SIEM parser?
8. Are SIEM tokens rotated without downtime?
9. Are collector pods resource-limited correctly?
10. Are alerts configured for output errors?

Recommended production pattern for critical clusters:

```text
Audit logs -> Kafka or SIEM direct + S3 archive
Infrastructure logs -> SIEM + short-term operations log store
Application logs -> application-specific destination, filtered before SIEM
```

## 23. Troubleshooting matrix

| Symptom | Likely cause | What to check |
|---|---|---|
| No collector pods | Missing RBAC for referenced input type | `oc get clusterlogforwarder -o yaml`, status conditions, clusterrolebindings |
| `Authorized=False` | ServiceAccount lacks required collect role | Add `collect-application-logs`, `collect-infrastructure-logs`, or `collect-audit-logs` |
| `Valid=False` | YAML/schema problem | `status.conditions[].message`, `oc explain` |
| `Ready=True` but SIEM has no logs | Network, TLS, auth, SIEM parser, or endpoint issue | Collector logs, curl test, SIEM receiver logs |
| Certificate verify failed | Missing/wrong CA bundle | Check `tls.ca.secretName` and CA chain |
| HTTP 401/403 | Wrong token/basic credentials | Verify Secret key names and SIEM token scope |
| Connection refused | Wrong host/port or firewall | Test from pod, check firewall and listener |
| Logs delayed | Backpressure, retries, SIEM slow | Collector metrics, SIEM ingestion queue |
| Missing audit logs | Audit input not configured or RBAC missing | `inputRefs: audit`, `collect-audit-logs` binding |
| Unexpected cost increase | Too many logs, debug noise, audit volume | Add drop/prune/rate limits; split indexes |
| Syslog parsed incorrectly | Wrong RFC or payload format | Compare RFC3164 vs RFC5424; check SIEM parser |
| Kafka failures | SASL/TLS/topic/message size issue | Kafka broker logs, collector logs, topic ACLs |

## 24. High-value SIEM detection ideas for OpenShift

### 24.1 RBAC changes

Alert on:

- ClusterRoleBinding creation
- RoleBinding to `cluster-admin`
- SCC-related role changes
- Service account token access

Example logic:

```text
log_type=audit AND verb IN (create, update, patch, delete) AND resource IN (rolebindings, clusterrolebindings, roles, clusterroles)
```

### 24.2 Privileged workload creation

Alert on:

- `hostNetwork: true`
- `hostPID: true`
- `hostPath` volumes
- privileged containers
- added capabilities
- `runAsUser: 0`

### 24.3 Secret access

Alert on:

```text
log_type=audit AND resource=secrets AND verb IN (get, list, watch)
```

Tune for:

- CI/CD service accounts
- backup jobs
- known controllers
- normal operator behavior

### 24.4 Exec into pods

Alert on:

```text
log_type=audit AND resource=pods/exec
```

High priority when:

- Executed in production namespace
- Executed by unusual user
- Executed against database, payment, identity, or security pods

### 24.5 Logging pipeline tampering

Alert on changes to:

- `ClusterLogForwarder`
- Logging operator subscription
- collector service account
- logging secrets
- network policies in `openshift-logging`

Example:

```text
log_type=audit AND namespace=openshift-logging AND verb IN (delete, patch, update)
```

### 24.6 Image and deployment anomalies

Alert on:

- Workloads using unapproved registries
- Image tag `latest` in production
- New DaemonSet in non-system namespace
- Pods with suspicious command shells
- Unexpected CronJobs

### Architecture

- [ ] Separate pipelines for application, infrastructure, and audit logs.
- [ ] Dedicated audit log destination or index.
- [ ] External archive for audit/compliance logs if required.

- [ ] Collector pods running on all required nodes.

- [ ] Rate limiting reviewed and monitored.
- [ ] Test logs validated after deployment.

- [ ] Retention defined by log type.
- [ ] Namespace inclusion/exclusion documented.

## 28. Advanced administrator notes

1. **Do not forward everything blindly.** A mature design routes different log types to different destinations.
2. **Audit logs are not normal logs.** They require stronger retention, access control, and change management.
3. **RBAC order matters.** Create service account and cluster role bindings before adding log types to pipelines.
4. **`Ready=True` does not always mean SIEM delivery is successful.** Always check collector logs and SIEM-side ingestion.
5. **TLS CA mistakes are common.** The collector must trust the SIEM endpoint certificate chain.
6. **SIEM parsing matters as much as forwarding.** A successful TCP connection is not enough; fields must parse correctly.
7. **High-cardinality fields cost money.** Be careful with Splunk indexed fields and label-heavy records.
8. **Use dedicated indexes.** Separate app, infra, and audit logs to simplify access control and retention.
9. **Test during upgrades.** Logging APIs, collector behavior, and output validation can change across operator versions.
10. **Treat ClusterLogForwarder as security-critical infrastructure.** Monitor changes to it through audit rules.

## 29. Interview-style questions

### Q1. Is OpenShift Logging a SIEM?

No. OpenShift Logging collects, processes, stores, visualizes, and forwards logs. A SIEM performs security correlation, detection, alerting, compliance reporting, and long-term investigation workflows. OpenShift integrates with SIEM by forwarding logs using `ClusterLogForwarder`.

### Q2. Which OpenShift logs are most important for SIEM?

Audit logs are usually the most important because they show API activity and security-relevant actions. Infrastructure logs are also important for node and control-plane behavior. Application logs are important when applications emit authentication, authorization, transaction, or security events.

### Q3. Why should audit logs be forwarded outside the cluster?

Because audit logs are sensitive evidence. If the cluster is compromised, relying only on cluster-local log storage is risky. External SIEM or immutable archive improves forensic reliability and separation of duties.

### Q4. What happens if you reference `audit` in `ClusterLogForwarder` without RBAC?

The collector service account is not authorized. In modern OpenShift Logging, the operator can remove the collector DaemonSet as a protective action, stopping log collection until the required `collect-audit-logs` binding is added.

### Q5. Splunk vs syslog output: when to use which?

Use `splunk` output for Splunk HEC because it supports Splunk-specific metadata such as index, source, indexed fields, and HEC token authentication. Use `syslog` for SIEMs or collectors that expect RFC3164/RFC5424 syslog, such as QRadar/ArcSight/rsyslog-based gateways.

### Q6. Why use Kafka between OpenShift and SIEM?

Kafka decouples OpenShift from SIEM availability, handles bursts, allows replay, supports multiple consumers, and is useful in multi-cluster high-volume environments.

### Q7. What is the difference between drop and prune filters?

A drop filter removes entire log records. A prune filter keeps the record but removes selected fields. Use drop for low-value noise and prune for sensitive or large fields.

### Q8. What should be checked when logs are not reaching SIEM?

Check `ClusterLogForwarder` conditions, collector pods, collector logs, service account RBAC, Secret key names, TLS CA, network reachability, SIEM token validity, SIEM listener health, parser errors, and rate limits.

## 32. Final takeaway

For an advanced OpenShift administrator, SIEM integration is not just “send logs to Splunk.” It is a security architecture decision.

A strong design answers:

- Which logs are security-relevant?
- Who is allowed to collect them?
- Which fields should be preserved or removed?
- Which SIEM/index/archive receives each log type?
- How is TLS and authentication handled?
- What happens during SIEM outage or throttling?
- How do we prove logs are still flowing?
- How do we detect tampering with the logging pipeline itself?

In production, the best pattern is usually:

```text
Application logs       -> developer/SRE log store + selective SIEM forwarding
Infrastructure logs    -> SRE visibility + SIEM correlation
Audit logs             -> dedicated SIEM index + immutable archive
ClusterLogForwarder    -> managed as security-critical infrastructure
```
