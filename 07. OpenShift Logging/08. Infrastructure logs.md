## 1. What are Infrastructure Logs?

In OpenShift Logging, **infrastructure logs** are logs generated by the **cluster platform itself**, not by normal user applications and not by audit subsystems. They represent the operational behavior of the OpenShift cluster, nodes, control plane components, operators, platform services, and system daemons.

Infrastructure logs usually include two major streams:

1. **Infrastructure container logs**
   - Logs from pods running in platform namespaces such as:
     - `openshift-*`
     - `kube-*`
     - `default`
   - Examples:
     - `openshift-apiserver`
     - `openshift-kube-apiserver`
     - `openshift-authentication`
     - `openshift-ingress`
     - `openshift-monitoring`
     - `openshift-machine-config-operator`
     - `openshift-cluster-version`
     - `openshift-image-registry`
     - `openshift-logging`
     - `openshift-operators-redhat`

2. **Node journal logs**
   - Logs from host-level system services on OpenShift nodes.
   - Examples:
     - `kubelet`
     - `crio`
     - `NetworkManager`
     - `systemd`
     - `chronyd`
     - node-level operating system messages
     - OpenShift node service messages

A simple way to remember:

```text
Infrastructure logs = OpenShift platform pod logs + node operating system journal logs
```

They answer questions like:

- Why did a node become `NotReady`?
- Why did kubelet restart a pod?
- Why is the ingress router returning errors?
- Why is the API server slow or restarting?
- Why is the Machine Config Daemon draining or rebooting nodes?
- Why are cluster operators degraded?
- Why is CRI-O failing to start containers?
- Why are logging collectors dropping or failing to ship logs?

## 2. Why Infrastructure Logs Matter in Real Production

For a 10-year-experience OpenShift administrator, infrastructure logs are not just “logs to view after failure.” They are an operational signal used for:

### 2.1 Cluster Reliability

Infrastructure logs show the health of platform services before metrics become critical. For example:

- kubelet repeatedly reports image pull or volume mount failures.
- Machine Config Daemon reports pending node reboot.
- Ingress router reports backend connection failures.
- API server logs show repeated request timeout or watch cache errors.
- CRI-O logs show container runtime storage problems.

### 2.2 Incident Root Cause Analysis

Metrics tell you **what** is wrong. Infrastructure logs often tell you **why**.

Example:

```text
Alert: KubeNodeNotReady
Metric symptom: node readiness changed to false
Infrastructure log root cause:
  kubelet cannot communicate with container runtime
  CRI-O socket unavailable
  disk pressure reported by eviction manager
```

### 2.3 Platform Upgrade Troubleshooting

During OpenShift upgrades, infrastructure logs help analyze:

- Cluster Version Operator progression
- operator reconciliation errors
- Machine Config Pool rollout
- node drain failures
- static pod revision rollout
- API server/operator degradation

### 2.4 Security and Change Awareness

Infrastructure logs are not a replacement for audit logs, but they help identify platform behavior around:

- operator installation
- failed authentication service behavior
- router reloads
- pod admission failures
- SCC/security context denial symptoms
- node-level service issues

### 2.5 SRE and SLA/SLO Operations

Senior administrators use infrastructure logs to support SLOs such as:

- API availability
- ingress availability
- node availability
- logging pipeline health
- platform operator health

## 3. OpenShift Log Categories: Application vs Infrastructure vs Audit

OpenShift Logging separates cluster logs into logical categories.

| Log Type | Meaning | Typical Source | Example Use Case |
|---|---|---|---|
| `application` | User workload container logs | Pods in non-platform namespaces | Developer troubleshooting |
| `infrastructure` | Platform and node operational logs | `openshift*`, `kube*`, `default` pods and node journal | SRE/platform troubleshooting |
| `audit` | Security/API audit records | kube-apiserver, openshift-apiserver, auditd, OVN | Compliance and security review |

### 3.1 Application Logs

Application logs come from normal user workloads. Example namespaces:

```text
finance-prod
hr-dev
payment-app
customer-portal
```

### 3.2 Infrastructure Logs

Infrastructure logs come from platform namespaces and node services. Example namespaces:

```text
openshift-apiserver
openshift-authentication
openshift-console
openshift-ingress
openshift-monitoring
openshift-kube-apiserver
openshift-machine-config-operator
openshift-logging
kube-system
kube-public
default
```

### 3.3 Audit Logs

Audit logs are security-sensitive API and node audit logs. They are separate from infrastructure logs because they usually have different retention, access control, compliance, and cost requirements.

Important distinction:

```text
API server normal container log       -> infrastructure
API server audit event log            -> audit
Ingress router access/error log       -> infrastructure
Application stdout/stderr             -> application
Kubelet service journal log           -> infrastructure
Node auditd log                       -> audit
```

## 4. Infrastructure Log Sources

In current OpenShift Logging 6.x `ClusterLogForwarder`, infrastructure input supports two main source types:

```yaml
infrastructure:
  sources:
    - node
    - container
```

### 4.1 `node` Source

`node` means journal logs from OpenShift cluster nodes.

Typical services:

```text
kubelet
crio
NetworkManager
systemd
chronyd
rpm-ostreed
machine-config-daemon-related host activity
kernel/system messages
```

Typical issues found here:

- node pressure
- CRI-O failures
- kubelet eviction decisions
- CNI/network setup failures
- node reboot/shutdown events
- systemd service restart loops
- disk/filesystem errors
- container runtime storage problems

### 4.2 `container` Source

`container` means container logs from OpenShift infrastructure namespaces.

Infrastructure container logs are collected from pods running in namespaces such as:

```text
default
kube*
openshift*
```

Typical components:

| Namespace | Example Component | Why Logs Matter |
|---|---|---|
| `openshift-apiserver` | OpenShift API server | API errors, admission behavior |
| `openshift-kube-apiserver` | Kubernetes API server | API failures, watch/cache issues |
| `openshift-authentication` | OAuth server | Login/authentication issues |
| `openshift-ingress` | Router pods | Route/backend/TLS problems |
| `openshift-monitoring` | Prometheus/Alertmanager | Monitoring stack failures |
| `openshift-machine-config-operator` | MCO/MCD | Node config rollout/reboot issues |
| `openshift-cluster-version` | Cluster Version Operator | Upgrade status/errors |
| `openshift-image-registry` | Internal registry | Push/pull/storage failures |
| `openshift-logging` | Collector/Loki/Logging Operator | Logging pipeline health |
| `openshift-dns` | DNS pods | DNS resolution failures |
| `openshift-network-*` | Network plugin pods | SDN/OVN/CNI failures |

### 4.3 Default Behavior

If you use the reserved input reference:

```yaml
inputRefs:
  - infrastructure
```

OpenShift Logging collects both:

```text
infrastructure.container + infrastructure.node
```

unless you define a custom infrastructure input with only specific sources.

## 5. End-to-End Architecture

Infrastructure log flow:

```text
[Node journal]                 [Platform pods]
     |                              |
     | journald                     | /var/log/containers/*.log
     |                              |
     +--------------+---------------+
                    |
                    v
          OpenShift Logging Collector
          usually Vector, deployed as DaemonSet
                    |
                    v
       normalization / enrichment / filtering
                    |
                    v
         ClusterLogForwarder pipelines
                    |
          +---------+----------+-----------+
          |                    |           |
          v                    v           v
      LokiStack             Kafka       Splunk/HTTP/S3/etc.
```

### 5.1 Main Components

| Component | Purpose |
|---|---|
| Red Hat OpenShift Logging Operator | Manages log collection and forwarding resources |
| Loki Operator | Manages LokiStack log store |
| LokiStack | OpenShift-managed Loki log store, usually for short-term troubleshooting |
| Collector | DaemonSet on every node; reads container logs and node logs |
| ClusterLogForwarder | Main CR that defines inputs, filters, outputs, and pipelines |
| ServiceAccount | Identity used by collector to collect/write logs |
| ClusterRoleBindings | Grant collector permission to collect selected log types |

### 5.2 Where Infrastructure Logs Are Read From

OpenShift/Kubernetes container logs are normally available through CRI log files on nodes, commonly under:

```text
/var/log/containers/*.log
/var/log/pods/...
```

Node logs come from `journald`.

The collector DaemonSet runs on every node and mounts the required host paths to read these logs.

### 5.3 Data Enrichment

Raw container runtime logs alone only include limited metadata. The collector enriches records with Kubernetes/OpenShift metadata such as:

```text
namespace
pod name
container name
node name
labels
annotations
log_type
log_source
```

For infrastructure logs, useful fields often include:

```text
.log_type = infrastructure
.log_source = container | node
.hostname
.kubernetes.namespace_name
.kubernetes.pod_name
.kubernetes.container_name
.message
```

Field names can vary depending on data model, output type, and OpenShift Logging version. In older ViaQ style output you commonly see fields such as `.kubernetes.namespace_name`; in OpenTelemetry model you should expect OTLP semantic fields.

## 6. How the Collector Handles Infrastructure Logs

### 6.1 Collector Deployment Model

The collector runs as a **DaemonSet**, meaning one collector pod is scheduled per eligible node. This is essential because logs are local to each node.

Check collector pods:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

View collector DaemonSet:

```bash
oc get ds -n openshift-logging
oc describe ds -n openshift-logging -l app.kubernetes.io/component=collector
```

### 6.2 Collector Responsibilities

For infrastructure logs, the collector:

1. Reads node journal entries.
2. Reads platform namespace container logs.
3. Adds metadata.
4. Classifies records with `log_type=infrastructure`.
5. Marks source as `log_source=node` or `log_source=container`.
6. Applies input tuning, filters, and transformations.
7. Sends records to configured outputs.
8. Reports health through collector pod logs and `ClusterLogForwarder` status.

### 6.3 Collector Failure Impact

If the collector fails on one node:

- Logs from that node may not be forwarded.
- Other nodes continue forwarding.
- Cluster-wide logging may look partially healthy unless you check all collector pods.

Always validate:

```bash
oc get pods -n openshift-logging -o wide
oc get clusterlogforwarder -A
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

## 7. RBAC and Collector Service Account Requirements

In current OpenShift Logging, the collector needs explicit permission for each log type it collects.

For infrastructure logs, bind:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

For application logs as well:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector
```

For audit logs:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Create service account if needed:

```bash
oc project openshift-logging
oc create serviceaccount collector
```

Verify bindings:

```bash
oc get clusterrolebinding -o wide | grep collect
```

Expected style:

```text
collect-infrastructure-logs   ClusterRole/collect-infrastructure-logs   system:serviceaccount:openshift-logging:collector
collect-application-logs      ClusterRole/collect-application-logs      system:serviceaccount:openshift-logging:collector
```

### 7.1 Common RBAC Mistake

If your `ClusterLogForwarder` references:

```yaml
inputRefs:
  - infrastructure
```

but the service account does **not** have `collect-infrastructure-logs`, the collector may not deploy correctly or log collection can be disabled/invalid depending on validation state.

Rule:

```text
Every inputRef log type must have matching collector permission.
```

## 8. Minimal Infrastructure Log Forwarding to LokiStack

This example forwards application and infrastructure logs to an in-cluster LokiStack.

> Adjust the LokiStack name if your LokiStack is not named `logging-loki`.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
    - name: default-lokistack
      type: lokiStack
      lokiStack:
        authentication:
          token:
            from: serviceAccount
        target:
          name: logging-loki
          namespace: openshift-logging
      tls:
        ca:
          configMapName: logging-loki-gateway-ca-bundle
          key: service-ca.crt
  pipelines:
    - name: default-logstore
      inputRefs:
        - application
        - infrastructure
      outputRefs:
        - default-lokistack
```

Apply:

```bash
oc apply -f clf-infra-lokistack.yaml
```

Check status:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'

oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Check collector pods:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

### 8.1 Important LokiStack TLS CA Requirement

When forwarding to the in-cluster LokiStack gateway, include:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

Without the correct CA block, the `ClusterLogForwarder` may appear `Ready`, but collectors can fail delivery with certificate verification errors.

## 11. Forward Infrastructure Logs to External Systems

Many enterprises do not keep infrastructure logs only in in-cluster LokiStack. Common pattern:

```text
Short-term operational troubleshooting -> LokiStack
Long-term analytics/compliance          -> Splunk / Elasticsearch / Kafka / S3 / CloudWatch / HTTP
```

### 11.1 Forward Infrastructure Logs to Splunk

Example skeleton:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
    - name: splunk-infra
      type: splunk
      splunk:
        url: https://splunk-hec.example.com:8088
        authentication:
          token:
            secretName: splunk-hec-token
            key: hecToken
      tls:
        ca:
          secretName: splunk-ca
          key: ca-bundle.crt
  pipelines:
    - name: infra-to-splunk
      inputRefs:
        - infrastructure
      outputRefs:
        - splunk-infra
```

Create token secret example:

```bash
oc create secret generic splunk-hec-token \
  -n openshift-logging \
  --from-literal=hecToken='<YOUR_HEC_TOKEN>'
```

### 11.2 Forward Infrastructure Logs to Kafka

Kafka is useful when you want buffering and downstream processing.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
    - name: kafka-infra
      type: kafka
      kafka:
        url: tls://kafka-bootstrap.logging.example.com:9093/topic/openshift-infra
      tls:
        ca:
          secretName: kafka-ca
          key: ca.crt
  pipelines:
    - name: infra-to-kafka
      inputRefs:
        - infrastructure
      outputRefs:
        - kafka-infra
```

### 11.3 Forward Infrastructure Logs to HTTP Endpoint

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
    - name: http-infra
      type: http
      http:
        url: https://log-gateway.example.com/openshift/infra
        headers:
          X-Cluster: prod-ocp
      tls:
        ca:
          secretName: http-ca
          key: ca.crt
  pipelines:
    - name: infra-to-http
      inputRefs:
        - infrastructure
      outputRefs:
        - http-infra
```

### 11.4 Dual Forwarding Pattern

Send infrastructure logs to LokiStack and Splunk:

```yaml
pipelines:
  - name: infra-to-loki-and-splunk
    inputRefs:
      - infrastructure
    outputRefs:
      - default-lokistack
      - splunk-infra
```

Benefits:

- SREs use LokiStack for fast local troubleshooting.
- Enterprise monitoring/SOC uses Splunk or SIEM pipeline.
- Local storage retention can be short; external retention can be long.

## 12. Filtering, Pruning, and Reducing Infrastructure Log Volume

Infrastructure logs can become noisy. Examples:

- router access logs
- kubelet repeated sync messages
- operator reconcile loops
- debug logs from platform components
- health check messages
- high-volume monitoring component logs

### 12.1 Drop Filter Concept

A `drop` filter removes matching records before forwarding.

Example: drop low-value debug level records.

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  filters:
    - name: drop-debug
      type: drop
      drop:
        - test:
            - field: .level
              matches: debug
  outputs:
    - name: default-lokistack
      type: lokiStack
      lokiStack:
        authentication:
          token:
            from: serviceAccount
        target:
          name: logging-loki
          namespace: openshift-logging
      tls:
        ca:
          configMapName: logging-loki-gateway-ca-bundle
          key: service-ca.crt
  pipelines:
    - name: infra-filtered
      inputRefs:
        - infrastructure
      filterRefs:
        - drop-debug
      outputRefs:
        - default-lokistack
```

### 12.2 Drop by Namespace

Example: drop logs from a noisy infra namespace.

```yaml
filters:
  - name: drop-noisy-namespace
    type: drop
    drop:
      - test:
          - field: .kubernetes.namespace_name
            matches: openshift-noisy-operator
```

Pipeline:

```yaml
pipelines:
  - name: infra-filtered
    inputRefs:
      - infrastructure
    filterRefs:
      - drop-noisy-namespace
    outputRefs:
      - default-lokistack
```

### 12.3 Drop by Message Pattern

Example:

```yaml
filters:
  - name: drop-health-checks
    type: drop
    drop:
      - test:
          - field: .message
            matches: ".*healthz.*"
```

Be careful. Dropping by message patterns can hide important events if the regex is too broad.

### 12.4 Prune Filter Concept

A `prune` filter removes low-value fields while keeping the record.

Example: remove annotations.

```yaml
filters:
  - name: remove-annotations
    type: prune
    prune:
      in:
        - .kubernetes.annotations
```

Use pruning to reduce payload size while retaining operational meaning.

### 12.5 Fields You Should Usually Keep

For infrastructure logs, keep:

```text
.log_type
.log_source
.message
.hostname
.kubernetes.namespace_name
.kubernetes.pod_name
.kubernetes.container_name
.level
.timestamp
```

Dropping these can make troubleshooting very difficult.

## 13. Rate Limits, Message Size, and Delivery Tuning

Infrastructure logs can spike during failures. Examples:

- node reboot storm
- router backend outage
- API server instability
- operator crashloop
- network plugin errors
- storage attach/detach issues

### 13.1 Input Rate Limit Example

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
    - name: tuned-infrastructure
      type: infrastructure
      infrastructure:
        tuning:
          container:
            maxMessageSize: 16Ki
            rateLimitPerContainer:
              maxRecordsPerSecond: 1000
  outputs:
    - name: default-lokistack
      type: lokiStack
      lokiStack:
        authentication:
          token:
            from: serviceAccount
        target:
          name: logging-loki
          namespace: openshift-logging
        tuning:
          deliveryMode: AtLeastOnce
          compression: gzip
          maxWrite: 3Mi
          minRetryDuration: 2
          maxRetryDuration: 300
      tls:
        ca:
          configMapName: logging-loki-gateway-ca-bundle
          key: service-ca.crt
  pipelines:
    - name: tuned-infra-to-loki
      inputRefs:
        - tuned-infrastructure
      outputRefs:
        - default-lokistack
```

### 13.2 Rate Limit Trade-off

| Setting | Benefit | Risk |
|---|---|---|
| Low rate limit | Controls cost and protects collector | Drops logs during incidents |
| High rate limit | Preserves more data | More CPU/memory/network/storage |
| Small message size | Prevents huge records | Truncates important stack traces |
| AtLeastOnce delivery | Better durability | More buffering/resource pressure |
| Compression gzip | Saves network/storage bandwidth | Extra CPU overhead |

### 13.3 Senior Admin Recommendation

For production:

1. Start with conservative default collection.
2. Measure actual log rate.
3. Identify top noisy namespaces/components.
4. Apply prune before drop where possible.
5. Drop only proven low-value records.
6. Keep incident-relevant records even if noisy.
7. Forward long-term copy to external storage if required.

## 14. Querying Infrastructure Logs in Loki / LogQL

The exact labels depend on data model and LokiStack label configuration, but common useful dimensions include:

```text
log_type="infrastructure"
log_source="container"
log_source="node"
kubernetes_namespace_name="openshift-ingress"
kubernetes_pod_name="..."
kubernetes_container_name="..."
hostname="..."
```

### 14.1 All Infrastructure Logs

```logql
{log_type="infrastructure"}
```

### 14.2 Node Journal Logs Only


## 16. Troubleshooting Infrastructure Log Collection

### 16.1 No Infrastructure Logs in UI

Check whether infrastructure pipeline exists:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Look for:

```yaml
pipelines:
  - inputRefs:
      - infrastructure
```

If no pipeline includes `infrastructure`, logs are intentionally dropped/not collected.

### 16.2 Check RBAC

```bash
oc get clusterrolebinding -o wide | grep collect-infrastructure-logs
```

If missing:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

### 16.3 Check Collector Pods

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

Problems:

| Symptom | Likely Cause |
|---|---|
| No collector pods | Invalid CLF, missing RBAC, operator issue |
| Collector CrashLoopBackOff | bad config, resource limit, permission issue |
| Collector pending | scheduling/toleration/node selector issue |
| Collector running only on some nodes | taints, node selector, daemonset scheduling problem |

### 16.4 Check CLF Status

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Look for condition types such as:

```text
Ready
Valid
Reconciled
```

Read messages carefully. CLF status is usually the fastest place to find validation errors.

### 16.5 Enable Debug Logging Temporarily

Add annotation:

```yaml
metadata:
  annotations:
    observability.openshift.io/log-level: debug
```

Example patch:

```bash
oc patch clusterlogforwarder instance -n openshift-logging --type=merge -p \
  '{"metadata":{"annotations":{"observability.openshift.io/log-level":"debug"}}}'
```

Review logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
```

Reset to info:

```bash
oc patch clusterlogforwarder instance -n openshift-logging --type=merge -p \
  '{"metadata":{"annotations":{"observability.openshift.io/log-level":"info"}}}'
```

Do not leave debug enabled in production longer than necessary.

### 16.6 Validate Node Journal Has Data

```bash
oc adm node-logs <node> --tail=50
oc adm node-logs <node> -u kubelet --tail=50
oc adm node-logs <node> -u crio --tail=50
```

If `oc adm node-logs` shows data but Loki does not, issue is likely collector/forwarder/output, not source generation.

## 17. Troubleshooting Infrastructure Log Forwarding

### 17.1 LokiStack Certificate Error

Collector log example:

```text
certificate verify failed: self-signed certificate in certificate chain
x509: certificate signed by unknown authority
```

Fix: ensure CLF output contains the CA bundle:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

### 17.2 LokiStack Target Name Wrong

Check LokiStack:

```bash
oc get lokistack -n openshift-logging
```

Your CLF must match:

```yaml
lokiStack:
  target:
    name: logging-loki
    namespace: openshift-logging
```

### 17.3 External Endpoint Connectivity

Test from a debug pod in `openshift-logging` or a temporary namespace with similar egress permissions.

```bash
oc run tmp-curl -n openshift-logging --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk https://splunk-hec.example.com:8088/services/collector
```

For restricted clusters, also check:

```bash
oc get networkpolicy -n openshift-logging
oc get egressfirewall -A
oc get dns.operator/default -o yaml
```

### 17.4 HTTP 401/403 from External Destination

Likely causes:

- wrong token
- token secret in wrong namespace
- wrong secret key name
- destination role does not allow ingestion
- proxy rewrites headers

Check secret exists:

```bash
oc get secret -n openshift-logging
oc describe secret <secret> -n openshift-logging
```

Do not print secret values in shared terminals.

### 17.5 Rate Limit / Dropped Logs

Symptoms:

```text
rate limit exceeded
dropping events
buffer full
request too large
payload too large
```

Actions:

1. Check collector logs.
2. Check output limits.
3. Increase output capacity.
4. Tune `rateLimit`, `maxWrite`, `maxMessageSize`.
5. Drop/prune noisy logs.
6. Use Kafka or durable external pipeline for high volume.

### 17.6 No Logs for Specific Namespace

Remember infrastructure classification:

```text
openshift*, kube*, default => infrastructure
other namespaces          => application
```

If you are looking for logs from `my-prod-app`, they are not infrastructure logs; they are application logs.

## 18. Production Design Patterns

### 18.1 Standard Enterprise Pattern

```text
Application logs      -> team-specific destination + optional Loki
Infrastructure logs   -> SRE/platform Loki + enterprise analytics
Audit logs            -> dedicated secure compliance archive/SIEM
```

Example:

```yaml
pipelines:
  - name: infra-to-loki
    inputRefs:
      - infrastructure
    outputRefs:
      - default-lokistack

  - name: infra-to-splunk
    inputRefs:
      - infrastructure
    outputRefs:
      - splunk-infra

  - name: audit-to-s3
    inputRefs:
      - audit
    filterRefs:
      - prune-sensitive-fields
    outputRefs:
      - s3-compliance
```

### 18.2 Separate Node and Container Infrastructure Logs

```yaml
inputs:
  - name: infra-node
    type: infrastructure
    infrastructure:
      sources:
        - node
  - name: infra-container
    type: infrastructure
    infrastructure:
      sources:
        - container
pipelines:
  - name: node-to-sre
    inputRefs:
      - infra-node
    outputRefs:
      - sre-loki
  - name: infra-container-to-analytics
    inputRefs:
      - infra-container
    outputRefs:
      - enterprise-splunk
```

Use this when:

- Node logs are security/platform-only.
- Platform pod logs are shared with wider SRE team.
- You need different retention/cost policies.

### 18.3 Short-Term Loki, Long-Term External Archive

```text
LokiStack retention: short-term troubleshooting
External S3/Splunk/Elasticsearch retention: 30/90/180/365 days depending policy
```

OpenShift-managed LokiStack is best treated as an operational troubleshooting store, not a full enterprise SIEM or long-term archive.

### 18.4 Multi-Cluster Logging Pattern

For multiple clusters:

```text
Cluster A infrastructure logs -> central Kafka/Splunk topic/index with cluster label
Cluster B infrastructure logs -> same central backend with cluster label
Cluster C infrastructure logs -> same central backend with cluster label
```

Add labels to pipelines if supported by your output design:

```yaml
pipelines:
  - name: infra-to-central
    inputRefs:
      - infrastructure
    labels:
      cluster: prod-east
      environment: production
    outputRefs:
      - central-splunk
```

Benefits:

- global incident correlation
- central SRE dashboards
- cross-cluster upgrade analysis
- unified retention

## 19. Security, Access Control, and Compliance

### 19.1 Who Should Read Infrastructure Logs?

Typically:

| Team | Access |
|---|---|
| Platform SRE | Full infrastructure logs |
| App developers | Their application logs only, not full infrastructure logs |
| Security team | Infrastructure + audit logs as required |
| Compliance team | Audit archive, possibly selected infrastructure logs |
| Vendor support | Time-limited, scoped access only |

### 19.2 Loki Access Role

OpenShift Logging provides roles such as:

```text
cluster-logging-infrastructure-view
cluster-logging-application-view
cluster-logging-audit-view
```

Grant infrastructure view carefully:

```bash
oc adm policy add-cluster-role-to-user cluster-logging-infrastructure-view <user-or-group>
```

Prefer groups:

```bash
oc adm groups new sre-platform-team
oc adm groups add-users sre-platform-team alice bob
oc adm policy add-cluster-role-to-group cluster-logging-infrastructure-view sre-platform-team
```

### 19.3 Sensitive Data in Infrastructure Logs

Infrastructure logs may contain:

- URLs
- route hostnames
- backend service names
- namespace names
- user names in certain platform messages
- certificate/TLS errors
- internal IP addresses
- tokens accidentally printed by misconfigured components

Best practices:

1. Do not grant infrastructure logs to everyone.
2. Use prune filters where safe.
3. Keep audit logs separate.
4. Mask/tokenize at external SIEM if required.
5. Restrict retention according to policy.
6. Use TLS for all external forwarding.
7. Rotate destination credentials.


### 20.3 Collector Resource Sizing

Check current usage:

```bash
oc adm top pods -n openshift-logging
oc describe pod -n openshift-logging -l app.kubernetes.io/component=collector
```

Watch during incidents/upgrades:

```bash
watch 'oc adm top pods -n openshift-logging'
```

### 20.4 LokiStack Considerations

For infrastructure logs, LokiStack pressure appears as:

- ingestion rate limit errors
- distributor/ingester CPU high
- query timeout
- object storage latency
- compactor issues
- high cardinality label problems

Avoid using high-cardinality fields as Loki labels, such as:

```text
pod UID
container ID
request ID
full URL path
user agent
random IDs
```

Better labels:

```text
log_type
log_source
namespace
node/hostname
container
cluster
```

### 20.5 Retention Strategy

Recommended approach:

| Log Stream | LokiStack | External Store |
|---|---:|---:|
| Infrastructure | 3-14 days | 30-180 days |
| Application | 3-14 days | team-dependent |
| Audit | minimal or none locally | policy-driven secure archive |

Exact retention depends on business policy, regulatory requirements, storage budget, and incident investigation needs.

## 22. Interview / Exam Style Questions

### Q1. What are infrastructure logs in OpenShift?

Infrastructure logs are logs from OpenShift platform components and node services. They include container logs from `openshift*`, `kube*`, and `default` namespaces and journal logs from cluster nodes.

### Q2. Are audit logs infrastructure logs?

No. Audit logs are a separate log type. API server audit records, node auditd logs, and OVN audit logs are classified as `audit`, not `infrastructure`.

### Q3. What are valid infrastructure sources in `ClusterLogForwarder`?

```yaml
sources:
  - node
  - container
```

`node` means node journal logs. `container` means infrastructure namespace container logs.

### Q4. What happens if no pipeline references `infrastructure`?

Infrastructure logs are not forwarded. In OpenShift Logging 6.x, if a log type is not included in a pipeline, it is dropped/not collected for that forwarder path.

### Q5. Which ClusterRole is required to collect infrastructure logs?

```text
collect-infrastructure-logs
```

Bind it to the collector service account:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

### Q6. What is the difference between `log_type` and `log_source`?

`log_type` describes the high-level category such as `infrastructure`, `application`, or `audit`. `log_source` describes the source within that category, such as `node` or `container` for infrastructure logs.

### Q7. Why include the LokiStack CA bundle in CLF?

The collector must verify the LokiStack gateway certificate. Without the CA block, forwarding can fail with TLS verification errors even if the CLF status appears ready.

### Q8. Which logs are useful for node NotReady troubleshooting?

Infrastructure node journal logs, especially kubelet, CRI-O, systemd, NetworkManager, and kernel/system messages.

### Q9. Which logs are useful for route 503 troubleshooting?

Infrastructure container logs from `openshift-ingress`, plus service/endpoints information in the affected application namespace.

### Q10. Should developers get full infrastructure log access?

Usually no. Developers should typically access their application logs. Infrastructure logs should be limited to platform/SRE/security teams because they can expose platform internals and sensitive operational data.

## Final Senior Admin Takeaway

Infrastructure logs are the platform administrator's operational black box recorder. For production OpenShift, you should treat them as a first-class SRE signal alongside metrics, alerts, events, must-gather, and cluster operator status.

The most important practical points are:

1. Include `infrastructure` in a `ClusterLogForwarder` pipeline or those logs will not be forwarded.
2. Grant `collect-infrastructure-logs` to the collector service account.
3. Understand the two infrastructure sources: `node` and `container`.
4. Keep node journal logs and platform pod logs available during incidents.
5. Use LokiStack for fast troubleshooting, but use external storage for long retention.
6. Tune volume carefully; never drop logs blindly during production incidents.
7. Restrict infrastructure log access to platform/SRE/security teams.
8. Always verify collector health before assuming a component produced no logs.
