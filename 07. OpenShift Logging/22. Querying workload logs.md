# Querying Workload Logs in OpenShift Logging

**Audience:** Advanced OpenShift administrators, SREs, platform engineers, and OpenShift Logging operators with ~10 years of Linux/Kubernetes/OpenShift experience.  
**Focus:** How to query application/workload logs in OpenShift using `oc logs`, OpenShift web console log views, and centralized OpenShift Logging with LokiStack/LogQL.  
**Platform context:** Red Hat OpenShift Logging 6.x / LokiStack-based logging, with notes for legacy ViaQ-style labels and newer OTLP/OpenTelemetry-style labels.

---

## 1. What “querying workload logs” means

In OpenShift, **workload logs** usually means logs produced by user workloads: Deployments, DeploymentConfigs, StatefulSets, DaemonSets, Jobs, CronJobs, Pods, and containers running in application namespaces.

There are two different log-query paths that an administrator must understand:

| Query path | Typical tool | Data source | Best use case | Limitation |
|---|---|---|---|---|
| **Live resource logs** | `oc logs`, web console pod logs | Current or previous container log files on the node | Immediate pod/container debugging | Tied to pod/container lifecycle; not a long-term search engine |
| **Centralized workload logs** | Observe → Logs, LokiStack, LogQL, external log backend | Logs collected by Vector/OpenShift Logging and stored in LokiStack or forwarded externally | Search across namespaces, pods, time ranges, labels, and historical incidents | Depends on collector health, RBAC, retention, label schema, and storage/query performance |

A senior OpenShift admin should not treat these as the same thing. `oc logs` answers: **“What is this pod/container writing now or just before restart?”** Centralized logging answers: **“What happened across the workload estate over time?”**

---

## 2. End-to-end workload log flow

For a normal application container, the flow is:

```text
Application process
  ↓ writes stdout/stderr
Container runtime / CRI log file on node
  ↓ tailed by OpenShift Logging collector, normally Vector
ClusterLogForwarder application input
  ↓ optional input selection / filters / parsing / drop / prune
Output: LokiStack, external Loki, Elasticsearch, Splunk, Kafka, CloudWatch, S3, etc.
  ↓
Query layer: OpenShift Observe → Logs, Loki API / LogQL, external SIEM, external dashboard
```

Important details:

1. OpenShift Logging is designed to collect application, infrastructure, and audit logs.
2. Workload/application logs are selected through the `application` input type in `ClusterLogForwarder`.
3. `application` logs exclude infrastructure namespaces and can be narrowed by namespace, container, and pod labels.
4. LokiStack in Red Hat OpenShift Logging is primarily a short-term troubleshooting store, not a replacement for a long-term compliance archive.
5. Access to centralized logs is controlled separately from normal pod access. A user might be able to view a namespace but still lack Loki log-query permission, depending on RBAC and tenant configuration.

## 3. Core components involved in workload log querying

### 3.1 `oc logs`

`oc logs` queries resource logs directly through the Kubernetes/OpenShift API. It does not require OpenShift Logging to be installed. It is the fastest path for pod-level debugging.

Use it when:

- A pod is currently running.
- A pod is crash-looping and you need the previous container log.
- You need to verify whether the application is writing to stdout/stderr.
- You need a quick tail from one workload before checking centralized logging.

### 3.2 Red Hat OpenShift Logging Operator

The Red Hat OpenShift Logging Operator manages log collection and forwarding. In Logging 6.x, `ClusterLogForwarder` is the central configuration object for log collection, filtering, and routing.

### 3.3 Vector collector

The collector tails node-local container log files, enriches records with Kubernetes/OpenShift metadata, applies selected filters, and sends records to outputs.

### 3.4 `ClusterLogForwarder`

`ClusterLogForwarder` defines:

- **Inputs:** what logs to collect.
- **Filters:** how to transform, drop, parse, or prune logs.
- **Outputs:** where logs go.
- **Pipelines:** how inputs, filters, and outputs are connected.
- **Service account:** the identity used by the collector.

For workload logs, the key input is `application`.

### 3.5 Loki Operator and LokiStack

The Loki Operator manages the LokiStack log store. LokiStack provides storage, query, tenancy, and the gateway integration used by OpenShift Logging.

### 3.6 Cluster Observability Operator logging UI plugin

The logging UI plugin surfaces logs in the OpenShift console, typically under **Observe → Logs**. It lets users apply filters, run queries, set time ranges, configure refresh rates, and expand individual log records.

## 4. Querying live workload logs with `oc logs`

### 4.1 Basic pod log query

```bash
oc logs pod/<pod_name> -n <namespace>
```

Example:

```bash
oc logs pod/api-7c8d7c67d8-q9m2x -n payments
```

Use this when you already know the pod name.

### 4.2 Query logs from a Deployment

```bash
oc logs deploy/<deployment_name> -n <namespace>
```

Example:

```bash
oc logs deploy/payments-api -n payments
```

This is useful when you know the workload but not the current replica pod name. For multiple replicas, prefer label selectors when you need all matching pods.

### 4.3 Query logs using labels

```bash
oc logs -l app=payments-api -n payments
```

For all containers in matching pods:

```bash
oc logs -l app=payments-api -n payments --all-containers=true
```

Follow logs from matching pods:

```bash
oc logs -f -l app=payments-api -n payments --all-containers=true
```

### 4.4 Multi-container pod logs

List containers:

```bash
oc get pod <pod_name> -n <namespace> -o jsonpath='{.spec.containers[*].name}{"\n"}'
```

Query a specific container:

```bash
oc logs pod/<pod_name> -n <namespace> -c <container_name>
```

Query init container logs:

```bash
oc logs pod/<pod_name> -n <namespace> -c <init_container_name>
```

### 4.5 CrashLoopBackOff / previous container logs

When a container restarts, the current log might not contain the failure. Use `--previous`:

```bash
oc logs pod/<pod_name> -n <namespace> -c <container_name> --previous
```

Typical crash-loop workflow:

```bash
oc get pod -n payments
oc describe pod <pod_name> -n payments
oc logs pod/<pod_name> -n payments -c app --previous --tail=200
oc get events -n payments --sort-by=.lastTimestamp
```

### 4.6 Time-bounded live logs

Last 10 minutes:

```bash
oc logs deploy/payments-api -n payments --since=10m
```

Last 2 hours:

```bash
oc logs deploy/payments-api -n payments --since=2h
```

Only last 100 lines:

```bash
oc logs deploy/payments-api -n payments --tail=100
```

Add timestamps:

```bash
oc logs deploy/payments-api -n payments --timestamps=true --tail=200
```

Follow live logs:

```bash
oc logs -f deploy/payments-api -n payments --tail=50
```

### 4.7 Jobs and CronJobs

Query a Job:

```bash
oc logs job/<job_name> -n <namespace>
```

Find pods created by a Job:

```bash
oc get pods -n <namespace> -l job-name=<job_name>
oc logs -n <namespace> -l job-name=<job_name> --all-containers=true
```

For CronJobs, identify the generated Job first:

```bash
oc get jobs -n <namespace> --sort-by=.metadata.creationTimestamp
oc logs job/<generated_job_name> -n <namespace>
```

### 4.8 When `oc logs` is not enough

Use centralized logging when:

- The pod was deleted.
- You need to search multiple replicas or namespaces.
- You need logs from a previous time window.
- You need text search or label filtering across many workloads.
- You need to correlate app logs with infrastructure or audit events.
- You need retention beyond the current container log file.

## 5. Verifying centralized workload logging is installed

Before querying centralized workload logs, verify the stack.

### 5.1 Check Logging Operator resources

```bash
oc get csv -n openshift-logging
oc get clusterlogforwarder -A
oc get lokistack -A
oc get uiplugin -A
```

Expected pattern in a common setup:

```text
openshift-logging   clusterlogforwarder/instance
openshift-logging   lokistack/logging-loki
```

### 5.2 Check `ClusterLogForwarder` outputs

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{range .spec.outputs[*]}{.name}{"\t"}{.type}{"\n"}{end}'
```

Example:

```text
default-lokistack    lokiStack
splunk-prod          splunk
```

This tells you whether application logs go to LokiStack, Splunk, or another destination.

### 5.3 Check pipelines

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{range .spec.pipelines[*]}{.name}{"\n  inputs: "}{.inputRefs}{"\n  outputs: "}{.outputRefs}{"\n"}{end}'
```

Healthy example:

```text
application-logs
  inputs: [application]
  outputs: [default-lokistack]
infrastructure-logs
  inputs: [infrastructure]
  outputs: [default-lokistack]
audit-logs
  inputs: [audit]
  outputs: [default-lokistack splunk-prod]
```

For workload log querying, make sure at least one pipeline includes either:

```text
inputRefs: [application]
```

or a named application input such as:

```text
inputRefs: [payments-app-logs]
```

### 5.4 Check `ClusterLogForwarder` status

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Look for:

```text
Authorized=True
Valid=True
Ready=True
```

If `Authorized=False`, the collector service account probably lacks collection permission. If `Valid=False`, the CR spec has a validation problem. If `Ready=False`, the Operator has not successfully reconciled the deployment.

### 5.5 Check collector pods

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
```

Normally, you expect one collector pod per node.

Check collector errors:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 \
  | grep -i "error\|failed\|certificate\|connection\|denied\|unauthorized"
```

### 5.6 Check LokiStack readiness

```bash
oc get lokistack -n openshift-logging
oc get lokistack logging-loki -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Look for a `Ready=True` condition.

### 5.7 Verify logs are visible in console

In the OpenShift console:

```text
Observe → Logs
```

Select the workload/application log type or schema mode, set a recent time range, and verify that recent log entries appear.

## 6. Configuring workload log collection

### 6.1 Minimal application-log pipeline to LokiStack

Example `ClusterLogForwarder` for application logs:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: application-logs
    inputRefs:
    - application
    outputRefs:
    - default-lokistack
```

The `tls.ca` block is important for in-cluster LokiStack forwarding because the LokiStack gateway uses the OpenShift service-serving CA.

### 6.2 Collector service account permissions

Create the collector service account:

```bash
oc create sa logging-collector -n openshift-logging
```

Grant application log collection permission:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:logging-collector
```

If collecting infrastructure logs too:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:logging-collector
```

If collecting audit logs too:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:logging-collector
```

Do not add `audit` to `inputRefs` before granting `collect-audit-logs`. In recent Logging versions, requesting unauthorized log types can cause the Operator to remove the collector DaemonSet as a protective behavior.

### 6.3 Collect application logs only from selected namespaces

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  inputs:
  - name: payments-workload-logs
    type: application
    application:
      includes:
      - namespace: payments
      - namespace: checkout
      excludes:
      - namespace: payments-dev
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: selected-apps
    inputRefs:
    - payments-workload-logs
    outputRefs:
    - default-lokistack
```

Use input-level selection when you want to reduce collection volume before logs enter the pipeline.

### 6.4 Collect application logs by pod labels

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  inputs:
  - name: prod-critical-apps
    type: application
    application:
      selector:
        matchLabels:
          tier: backend
        matchExpressions:
        - key: env
          operator: In
          values:
          - prod
          - qa
  pipelines:
  - name: prod-critical-pipeline
    inputRefs:
    - prod-critical-apps
    outputRefs:
    - default-lokistack
```

This is useful when teams consistently label workloads, for example:

```yaml
labels:
  app: payments-api
  env: prod
  tier: backend
  owner: payments-team
```

## 7. RBAC for querying centralized workload logs

Centralized logs have their own access model.

### 7.1 Cluster roles for reading logs

Common roles:

| Role | Purpose |
|---|---|
| `cluster-logging-application-view` | Read application/workload logs |
| `cluster-logging-infrastructure-view` | Read infrastructure logs |
| `cluster-logging-audit-view` | Read audit logs |

### 7.2 Namespace-scoped application log access

Grant a user access to workload logs in one namespace:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: allow-read-workload-logs
  namespace: payments
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-logging-application-view
subjects:
- kind: User
  apiGroup: rbac.authorization.k8s.io
  name: appuser1
```

Apply:

```bash
oc apply -f allow-read-workload-logs.yaml
```

Check who can read application logs in a namespace:

```bash
oc get rolebinding -n payments -o json | \
  jq -r '.items[] | select(.roleRef.name=="cluster-logging-application-view") | {name: .metadata.name, subjects: .subjects}'
```

### 7.3 Cluster-wide application log access

Use carefully:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: logging-all-application-logs-reader
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-logging-application-view
subjects:
- kind: Group
  apiGroup: rbac.authorization.k8s.io
  name: sre-team
```

Check cluster-wide application log readers:

```bash
oc get clusterrolebinding -o json | \
  jq -r '.items[] | select(.roleRef.name=="cluster-logging-application-view") | {name: .metadata.name, subjects: .subjects}'
```

### 7.4 Tenant mode

Check tenant mode:

```bash
oc get lokistack logging-loki -n openshift-logging \
  -o jsonpath='{.spec.tenants.mode}{"\n"}'
```

Common value:

```text
openshift-logging
```

In tenant-aware mode, users query application logs based on their namespace access. If users can query nothing, validate both normal project access and log-specific access.

## 8. Querying workload logs in the OpenShift web console

### 8.1 UI location

Use:

```text
OpenShift Console → Observe → Logs
```

Typical workflow:

1. Select the log type or schema mode.
2. Set time range, for example last 5 minutes, 30 minutes, or 2 hours.
3. Filter by namespace, pod, container, deployment, or text.
4. Expand records to inspect metadata.
5. Switch to a LogQL-like query when precise filtering is required.

### 8.2 Logging UI plugin example

A typical `UIPlugin` for logging:

```yaml
apiVersion: observability.openshift.io/v1alpha1
kind: UIPlugin
metadata:
  name: logging
spec:
  type: Logging
  logging:
    lokiStack:
      name: logging-loki
    logsLimit: 50
    timeout: 30s
    schema: otel
```

Schema options commonly include:

| Schema | Meaning |
|---|---|
| `otel` | Use OpenTelemetry-style attributes |
| `viaq` | Use legacy ViaQ-compatible attributes |
| `select` | Let the user select query mode in UI |

In mixed or upgraded environments, use `select` during transition so admins can confirm which label model is currently effective.

## 9. LogQL fundamentals for workload logs

Loki uses **LogQL**. A basic log query has:

```text
{label_selector} | pipeline_filters
```

Examples:

```logql
{log_type="application"}
```

```logql
{log_type="application", kubernetes_namespace_name="payments"}
```

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
```

The exact labels depend on whether the environment uses ViaQ compatibility labels or OTLP/OpenTelemetry labels.

### 9.1 ViaQ-style / compatibility label examples

Common examples:

```logql
{log_type="application"}
```

```logql
{log_type="application", kubernetes_namespace_name="payments"}
```

```logql
{log_type="application", kubernetes_namespace_name="payments", kubernetes_pod_name=~"payments-api-.*"}
```

```logql
{log_type="application", kubernetes_namespace_name="payments", kubernetes_container_name="app"}
```

### 9.2 OTLP/OpenTelemetry-style label examples

Loki persists OTLP attribute names by lowercasing them and replacing characters such as `.`, `/`, and `-` with `_`. For example:

```text
k8s.namespace.name → k8s_namespace_name
k8s.pod.name       → k8s_pod_name
k8s.container.name → k8s_container_name
openshift.log.type → openshift_log_type
```

Examples:

```logql
{openshift_log_type="application"}
```

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
```

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_deployment_name="payments-api"}
```

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_container_name="app"}
```

### 9.3 Always discover labels first

Never blindly assume labels in production. Confirm labels in one of these ways:

- Use the OpenShift Observe → Logs UI label browser/dropdowns.
- Expand a log record and inspect metadata.
- Query a broad recent window and inspect available labels.
- Check whether the UI plugin is using `otel`, `viaq`, or `select` mode.
- Check whether console labels are enabled for OTLP-based querying.

## 10. Workload log query cookbook

### 10.1 All application logs in a recent time window

ViaQ-style:

```logql
{log_type="application"}
```

OTLP-style:

```logql
{openshift_log_type="application"}
```

Use a short time range first, for example last 5 or 15 minutes.

### 10.2 All logs from one namespace

ViaQ-style:

```logql
{log_type="application", kubernetes_namespace_name="payments"}
```

OTLP-style:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
```

### 10.3 Logs from one Deployment

ViaQ-style, if the deployment label/field exists:

```logql
{log_type="application", kubernetes_namespace_name="payments"} |= "payments-api"
```

OTLP-style with deployment label:

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_deployment_name="payments-api"}
```

If the deployment label is not available, use pod name regex:

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_pod_name=~"payments-api-.*"}
```

### 10.4 Logs from one pod

ViaQ-style:

```logql
{log_type="application", kubernetes_namespace_name="payments", kubernetes_pod_name="payments-api-7c8d7c67d8-q9m2x"}
```

OTLP-style:

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_pod_name="payments-api-7c8d7c67d8-q9m2x"}
```

### 10.5 Logs from one container

ViaQ-style:

```logql
{log_type="application", kubernetes_namespace_name="payments", kubernetes_container_name="app"}
```

OTLP-style:

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_container_name="app"}
```

### 10.6 Search for error text

```logql
{openshift_log_type="application", k8s_namespace_name="payments"} |= "ERROR"
```

Case-insensitive regex when needed:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"} |~ "(?i)error|exception|panic|fatal"
```

Prefer exact text filters like `|= "ERROR"` before regex because they are cheaper.

### 10.7 Exclude noisy health checks

```logql
{openshift_log_type="application", k8s_namespace_name="payments"} != "/healthz" != "/readyz"
```

### 10.8 JSON logs: filter by JSON fields

If the application emits JSON logs:

```json
{"level":"error","trace_id":"abc123","msg":"payment authorization failed","status":503}
```

Query:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
  |= "payment"
  | json
  | level="error"
```

Filter by HTTP status:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
  |= "status"
  | json
  | status >= 500
```

Filter by trace/request ID:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
  |= "abc123"
  | json
  | trace_id="abc123"
```

Optimization rule: apply a cheap line filter before `| json` when possible.

### 10.9 logfmt logs

For logs like:

```text
level=error method=POST path=/pay status=503 duration_ms=1200
```

Query:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
  |= "status="
  | logfmt
  | status >= 500
```

### 10.10 NGINX-style logs with pattern parser

```logql
{openshift_log_type="application", k8s_namespace_name="edge"}
  |= "HTTP"
  | pattern `<ip> - - <_> "<method> <path> <_>" <status> <size> <_>`
  | status >= 500
```

### 10.11 Count error logs by pod

```logql
sum by (k8s_pod_name) (
  count_over_time({openshift_log_type="application", k8s_namespace_name="payments"} |~ "(?i)error|exception|panic" [5m])
)
```

### 10.12 Error rate by deployment

```logql
sum by (k8s_deployment_name) (
  rate({openshift_log_type="application", k8s_namespace_name="payments"} |~ "(?i)error|exception|fatal" [5m])
)
```

### 10.13 Top noisy pods

```logql
topk(10,
  sum by (k8s_pod_name) (
    rate({openshift_log_type="application", k8s_namespace_name="payments"}[5m])
  )
)
```

### 10.14 Find logs from pods scheduled on a node

```logql
{openshift_log_type="application", k8s_node_name="worker-2.example.com"}
```

This is useful when a node has disk pressure, network issues, or runtime problems.

### 10.15 Find stdout versus stderr

Depending on schema and metadata availability:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
  | json
  | log_iostream="stderr"
```

Or inspect expanded log metadata in the UI to confirm whether stream metadata appears as `stream`, `log_iostream`, or another field.

## 11. Performance rules for LogQL workload queries

### 11.1 Start narrow

Bad:

```logql
{openshift_log_type="application"} |~ ".*timeout.*"
```

Better:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"} |= "timeout"
```

Best when labels exist:

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_deployment_name="payments-api"} |= "timeout"
```

### 11.2 Use labels for stable identity

Good labels:

- namespace
- deployment
- statefulset
- daemonset
- pod
- container
- node
- environment
- cluster
- service name

Poor labels:

- request ID
- user ID
- session ID
- full URL path with IDs
- error message text
- timestamp
- pod UID as a primary query dimension

High-cardinality labels increase index size and hurt query performance.

### 11.3 Filter early

Efficient order:

```logql
{labels} |= "cheap-string" | json | structured_field="value"
```

Less efficient:

```logql
{labels} | json | structured_field="value"
```

Worst pattern:

```logql
{labels} |~ ".*huge.*regex.*" | json
```

### 11.4 Prefer exact line filters over regex

Prefer:

```logql
|= "ERROR"
```

Use regex only when you actually need it:

```logql
|~ "(?i)error|exception|panic|fatal"
```

### 11.5 Keep time windows realistic

For active incidents:

- Start with last 5–15 minutes.
- Expand to 1 hour if needed.
- Avoid multi-day broad regex queries unless absolutely necessary.
- For long-term queries, use an external log store designed and sized for long retention.

### 11.6 Understand LokiStack’s intended retention role

In Red Hat OpenShift Logging, LokiStack is supported as a short-term log store for fast troubleshooting. For long-term compliance, SIEM, and multi-month search, forward to an external destination such as Splunk, S3, Elasticsearch/OpenSearch, Kafka pipeline, or a dedicated enterprise log platform.

## 12. Troubleshooting: workload logs missing from centralized logging

Use this runbook when `oc logs` shows application output but Observe → Logs or Loki queries do not.

### 12.1 Confirm the app writes to stdout/stderr

```bash
oc logs deploy/<deployment> -n <namespace> --tail=50
```

If this shows nothing, the app might be writing to an internal file instead of stdout/stderr. OpenShift Logging normally collects container stdout/stderr logs, not arbitrary application files inside the container unless you implement a sidecar or custom forwarding pattern.

### 12.2 Confirm the namespace is application scope

Application logs are normally from user-created namespaces. Workloads in namespaces such as `openshift-*`, `kube-*`, or `default` can be classified as infrastructure logs depending on logging rules.

If your app runs in an infrastructure namespace, query `infrastructure` logs instead of `application`, or move the app to a proper application namespace.

### 12.3 Confirm `ClusterLogForwarder` has application input

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{range .spec.pipelines[*]}{.name}{" inputs="}{.inputRefs}{" outputs="}{.outputRefs}{"\n"}{end}'
```

You need `application` or a named application input in a pipeline.

### 12.4 Confirm the collector has permission to collect application logs

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions[?(@.type=="observability.openshift.io/Authorized")].message}{"\n"}'
```

Expected:

```text
permitted to collect log types: [application ...]
```

If missing, grant:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:<collector_service_account>
```

### 12.5 Confirm collector pods are running on all nodes

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

If a node has no collector pod, check taints, tolerations, node selectors, resource pressure, and DaemonSet status.

### 12.6 Check collector logs

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 \
  | grep -i "error\|failed\|denied\|unauthorized\|certificate\|timeout\|rate"
```

Common causes:

| Symptom | Likely issue |
|---|---|
| `certificate verify failed` | Missing or wrong LokiStack gateway CA in output TLS config |
| `permission denied` / `unauthorized` | Missing collector ClusterRoleBinding or token auth issue |
| `connection refused` / timeout | LokiStack gateway/network/DNS issue |
| repeated backpressure | Output too slow, Loki overloaded, external destination slow |
| dropped records | Drop filters, rate limits, max line size, or output rejection |

### 12.7 Confirm LokiStack is ready

```bash
oc get lokistack logging-loki -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Check Loki pods:

```bash
oc get pods -n openshift-logging | grep -i loki
```

### 12.8 Confirm UI plugin is enabled

```bash
oc get uiplugin logging -o yaml
```

Check console plugins:

```bash
oc get console.operator.openshift.io cluster -o jsonpath='{.spec.plugins}{"\n"}'
```

If GitOps manages the Console Operator, ensure the logging plugin is included in the desired GitOps state, otherwise it might be removed on sync.

### 12.9 Confirm user has log-query access

For namespace-scoped access:

```bash
oc get rolebinding -n <namespace> -o json | \
  jq -r '.items[] | select(.roleRef.name=="cluster-logging-application-view") | {name: .metadata.name, subjects: .subjects}'
```

For cluster-wide access:

```bash
oc get clusterrolebinding -o json | \
  jq -r '.items[] | select(.roleRef.name=="cluster-logging-application-view") | {name: .metadata.name, subjects: .subjects}'
```

### 12.10 Confirm time range and timestamp correctness

Problems that look like “missing logs”:

- UI time range is too narrow.
- Browser timezone differs from cluster timezone.
- Node clocks are skewed.
- Application writes incorrect timestamps in JSON logs.
- Query uses local time assumption while Loki stores timestamps in UTC.

Check node time synchronization if timestamps are suspicious.

### 12.11 Confirm filters are not dropping logs

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.spec.filters}' | python3 -m json.tool
```

Look for:

- `drop` filters matching namespace/message/level.
- `prune` filters removing fields needed for querying.
- rate limits.
- parse/multiline filters changing records.

### 12.12 Confirm retention has not expired

```bash
oc get lokistack logging-loki -n openshift-logging \
  -o jsonpath='{.spec.limits.global.retention}' | python3 -m json.tool
```

If you search beyond retention, logs are gone from LokiStack. Check external archives if configured.

## 14. Troubleshooting: Loki query is slow or times out

### 14.1 Reduce query scope

Start with:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"}
```

Then add deployment/pod/container labels.

### 14.2 Reduce time range

Use last 5 minutes, then expand.

### 14.3 Avoid broad regex

Bad:

```logql
{openshift_log_type="application"} |~ ".*Exception.*timeout.*"
```

Better:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"} |= "Exception" |= "timeout"
```

### 14.4 Parse after line filtering

Bad:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"} | json | level="error"
```

Better:

```logql
{openshift_log_type="application", k8s_namespace_name="payments"} |= "error" | json | level="error"
```

### 14.5 Check object storage and Loki metrics

Loki query speed depends heavily on object storage performance and Loki component health. Check object storage errors/latency and Loki resource pressure.

Example S3 request metric query:

```promql
sum by(status, container, operation) (
  label_replace(
    rate(loki_s3_request_duration_seconds_count{namespace="openshift-logging"}[5m]),
    "status", "${1}xx", "status_code", "([0-9]).."
  )
)
```

## 15. Multiline exceptions and stack traces

Many Java, Python, Go, Ruby, Node.js, PHP, and Dart exceptions span multiple lines. Without multiline handling, each line can become a separate log record, making queries noisy.

Enable multiline exception detection with a filter:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  filters:
  - name: detect-exceptions
    type: detectMultilineException
  pipelines:
  - name: application-logs
    inputRefs:
    - application
    filterRefs:
    - detect-exceptions
    outputRefs:
    - default-lokistack
```

Use this carefully. It can increase collector CPU/memory requirements, especially in high-volume clusters.

## 16. Structured logging recommendations for application teams

To make workload logs queryable at scale, application teams should emit structured logs.

Recommended JSON fields:

```json
{
  "timestamp": "2026-07-03T10:15:30.123Z",
  "level": "error",
  "service": "payments-api",
  "env": "prod",
  "trace_id": "abc123",
  "span_id": "def456",
  "request_id": "req-987",
  "method": "POST",
  "path": "/api/v1/payments",
  "status": 503,
  "duration_ms": 1280,
  "msg": "payment authorization failed"
}
```

Best practices:

- Write logs to stdout/stderr, not only to files.
- Use JSON or logfmt for machine-queryable logs.
- Keep one event per log line.
- Include severity, service name, request ID, trace ID, and business operation.
- Do not log secrets, tokens, passwords, private keys, or full PII.
- Avoid huge stack traces or payload dumps in normal paths.
- Use labels for stable workload identity, not unique request values.

## 17. Security and governance

### 17.1 Do not over-grant log access

Application logs often contain sensitive data. Avoid granting `cluster-logging-application-view` to `system:authenticated` unless your organization explicitly accepts that risk.

Prefer namespace-level `RoleBinding` for developers and team-specific groups.

### 17.2 Treat audit logs separately

Audit logs can reveal usernames, request URIs, object names, and security-relevant metadata. Do not mix broad developer access to application logs with audit log access.

### 17.3 Filter or prune sensitive fields

Use application-side redaction first. Use collector-side `drop` and `prune` filters as a second layer, especially when forwarding to third-party systems.

Example: prune noisy annotations:

```yaml
spec:
  filters:
  - name: prune-annotations
    type: prune
    prune:
      in:
      - .kubernetes.annotations
```

### 17.4 Long-term retention

For compliance, forward logs externally. LokiStack is best for short-term troubleshooting. Use external destinations for:

- 90-day / 180-day / 1-year retention
- Legal hold
- Immutable archive
- SIEM correlation
- Cross-cluster reporting

## 18. Practical incident workflow

Scenario: Users report intermittent 503 from `payments-api`.

### Step 1: Confirm workload status

```bash
oc get deploy,pods,svc,route -n payments
oc get events -n payments --sort-by=.lastTimestamp | tail -50
```

### Step 2: Check current pod logs

```bash
oc logs deploy/payments-api -n payments --since=10m --tail=200 --timestamps=true
```

### Step 3: Check previous crash logs

```bash
for p in $(oc get pod -n payments -l app=payments-api -o name); do
  echo "### $p"
  oc logs "$p" -n payments --previous --tail=100 2>/dev/null || true
done
```

### Step 4: Query centralized logs for errors

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_deployment_name="payments-api"}
  |~ "(?i)error|exception|panic|fatal|503|timeout"
```

### Step 5: If logs are JSON, query status field

```logql
{openshift_log_type="application", k8s_namespace_name="payments", k8s_deployment_name="payments-api"}
  |= "status"
  | json
  | status >= 500
```

### Step 6: Count failures by pod

```logql
sum by (k8s_pod_name) (
  count_over_time(
    {openshift_log_type="application", k8s_namespace_name="payments", k8s_deployment_name="payments-api"}
    |~ "503|timeout|connection refused" [5m]
  )
)
```

### Step 7: Correlate with platform signals

Check:

```bash
oc describe pod <bad_pod> -n payments
oc adm top pod -n payments
oc adm top node
oc get events -n payments --sort-by=.lastTimestamp
```

Then query infrastructure logs for the node if needed.

## 20. Interview-ready explanation

**Question:** How do you query workload logs in OpenShift?

**Answer:**

In OpenShift, I separate workload log querying into two paths. For immediate pod-level debugging, I use `oc logs` against the Pod, Deployment, Job, or label selector. That helps me inspect current logs, previous crashed container logs with `--previous`, specific containers with `-c`, time windows with `--since`, and live streams with `-f`.

For centralized querying, I use OpenShift Logging. Application containers write stdout/stderr, the collector tails container logs from nodes, enriches them with Kubernetes metadata, and forwards them through `ClusterLogForwarder` pipelines to LokiStack or an external destination. Then I query through Observe → Logs or LogQL. I start with a narrow label selector such as namespace, deployment, pod, and container, then add line filters or JSON parsing. I also verify RBAC because reading centralized application logs requires roles like `cluster-logging-application-view`.

If logs are missing, I check whether the application writes stdout/stderr, whether the `ClusterLogForwarder` includes the `application` input, whether the collector service account has `collect-application-logs`, whether collector pods are running on all nodes, whether LokiStack is Ready, whether the user has log-query access, and whether the query uses the correct ViaQ or OTLP label schema.

## 21. Senior-admin field notes

1. Always compare `oc logs` with centralized query results during troubleshooting. If `oc logs` has data but Loki does not, the issue is collection, forwarding, storage, RBAC, retention, or query labels.
2. Query labels are not universal. OpenShift Logging 6.x environments can expose OTLP labels, ViaQ compatibility labels, or both depending on configuration and upgrade path.
3. Do not start incidents with a broad regex over all application logs. Start with namespace, deployment, pod, and a small time window.
4. Loki query performance is often a storage and label-design problem, not only a CPU problem.
5. Namespace-scoped log access is safer than cluster-wide access.
6. LokiStack is not your SIEM. Forward to external systems for long-term compliance and multi-cluster analytics.
7. Filters are powerful but dangerous. A `drop` filter can make logs disappear exactly when you need them.
8. For Java/Python/Go stack traces, multiline exception detection can improve readability but must be sized and monitored.
9. Application teams must own log quality. Platform teams can provide the pipeline, but bad application logs remain hard to query.
10. During upgrades, document the active query schema (`viaq`, `otel`, or `select`) for your SREs and developers.
