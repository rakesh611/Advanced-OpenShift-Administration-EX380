# OpenShift Logging: Log Storage Sizing — Advanced Administration Guide

**Audience:** Advanced OpenShift Administrators, Platform Engineers, SREs, and L3 Support Engineers  
**Experience level:** Written for an engineer with around 10 years of Linux, Kubernetes, DevOps, and OpenShift administration experience  
**Scope:** Red Hat OpenShift Logging with LokiStack, Vector collectors, retention planning, capacity calculation, operational validation, and production troubleshooting  
**Last updated:** 2026-07-03

---

## 1. What “log storage sizing” means in OpenShift Logging

In OpenShift Logging, **log storage sizing** is the process of estimating and validating how much storage, CPU, memory, and query capacity are required to collect, store, retain, and query logs from an OpenShift cluster.

For a senior administrator, storage sizing is not only “how many GB or TB do I need?” It includes:

- How many logs are generated per day.
- Which log categories are collected: application, infrastructure, audit.
- How long logs must be retained.
- Whether logs are stored locally in LokiStack, forwarded externally, or both.
- Whether the platform is used for short-term troubleshooting or long-term compliance/audit retention.
- Query behavior: short recent searches vs long historical searches.
- Peak ingestion rate, not only daily average.
- Object storage lifecycle and retention enforcement.
- LokiStack size class and component resources.
- Collector buffering and backpressure behavior.
- Growth, application verbosity, namespace onboarding, and audit policy changes.

In real production clusters, wrong sizing causes symptoms such as:

- Missing logs.
- Delayed log visibility.
- Loki ingestion rate-limit errors.
- Query timeouts.
- Object bucket growth without pruning.
- Collector memory pressure.
- Loki ingester restarts.
- Slow Observe → Logs UI.
- Unplanned object storage cost.
- Compliance gaps because retention is shorter than expected.

## 2. Current OpenShift Logging architecture relevant to sizing

Modern Red Hat OpenShift Logging separates the logging stack into distinct layers:

```text
Application / node / audit log sources
        |
        v
Vector collector DaemonSet
        |
        +--> LokiStack inside OpenShift
        |
        +--> External log systems: Splunk, Kafka, Elasticsearch, syslog, cloud logging, etc.
```

### 2.1 Main components

| Layer | Component | Sizing impact |
|---|---|---|
| Collection | Vector collector | CPU, memory, network, buffering, source read throughput |
| Storage | LokiStack | Ingestion capacity, query capacity, local PVC/disk requests, memory, CPU |
| Object storage | S3-compatible, AWS S3, Azure Blob, GCS, Swift, ODF/Ceph RGW | Main long-lived log data capacity |
| Visualization | OpenShift Observability UI / Grafana / LogQL clients | QPS, query range, query parallelism |
| Alerting / rules | Loki ruler | Extra CPU/memory and retention/rule evaluation load |
| External forwarding | Splunk/Elastic/Kafka/SIEM | May reduce in-cluster retention need, but increases collector/network load |

### 2.2 Important modern design point

Red Hat positions LokiStack in OpenShift Logging as a **short-term troubleshooting log store**, not a long-term enterprise archive. For long-term retention or large historical queries, use an external log store/SIEM/archive design.

A practical rule:

```text
OpenShift LokiStack = recent troubleshooting window
External SIEM/archive = long-term search, compliance, security analytics, audit history
```

## 3. Log categories that affect storage sizing

OpenShift logs are usually divided into three major groups.

### 3.1 Application logs

Application logs come from containers and are usually read from:

```text
/var/log/containers/*.log
```

Application logs are often the biggest and least predictable category.

Examples:

- Java/Spring Boot DEBUG logs.
- NGINX access logs.
- API gateway logs.
- Application JSON logs.
- Database sidecar logs.
- Service mesh proxy logs.
- CI/CD job logs.

Production risk:

```text
One noisy application can produce more logs than the rest of the cluster combined.
```

### 3.2 Infrastructure logs

Infrastructure logs include node, runtime, systemd/journald, kubelet, CRI-O, OpenShift control plane, router, SDN/OVN, and operator logs.

These are usually more stable than application logs but can spike during:

- Node pressure.
- Cluster upgrades.
- CNI issues.
- Image pull failures.
- API server instability.
- Operator crash loops.
- Repeated pod scheduling failures.

### 3.3 Audit logs

Audit logs are highly important for security and compliance. They can grow quickly depending on audit policy and API activity.

Common drivers:

- Large number of users or service accounts.
- High CI/CD automation activity.
- Controllers repeatedly reconciling resources.
- Security tools polling the API server.
- Verbose audit policy.
- Multi-tenant clusters with many namespaces.

Audit logs require special care because compliance teams often demand longer retention than LokiStack is designed for. In many enterprises, audit logs should be forwarded to an external SIEM or immutable object archive.

## 4. Storage sizing dimensions

Do not size logging only by number of nodes or pods. Size by **actual log production and query behavior**.

### 4.1 Primary sizing variables

| Variable | Meaning | Why it matters |
|---|---|---|
| `GB_per_day` | Total logs ingested per day | Main capacity driver |
| `retention_days` | Number of days logs are retained | Main object storage multiplier |
| `peak_MBps` | Peak ingestion rate | Determines whether Loki/collectors can keep up |
| `QPS` | Queries per second | Affects querier/frontend capacity |
| `query_range` | How far back users query | Longer ranges require more CPU/memory |
| `ruler_enabled` | Loki ruler/rules enabled or not | Adds CPU/memory overhead |
| `tenant_count` | application/infrastructure/audit and multi-tenancy | Affects limits, fairness, and query behavior |
| `label_cardinality` | Number of unique label combinations | Affects index and query performance |
| `growth_factor` | Expected growth over next 6–12 months | Prevents early resize |
| `safety_margin` | Buffer for spikes and operational mistakes | Prevents outages during noisy periods |

### 4.2 Recommended capacity formula

Use this formula for object storage planning:

```text
Base storage = GB_per_day × retention_days

Planned storage = Base storage × overhead_factor × growth_factor × safety_margin
```

Typical values:

```text
overhead_factor: 1.10 to 1.30
growth_factor: 1.20 to 2.00
safety_margin: 1.20 to 1.50
```

For conservative enterprise planning:

```text
Planned storage = GB_per_day × retention_days × 1.3 × 1.5
```

This gives room for index overhead, object metadata, burst days, temporary duplication, future workload growth, and operational mistakes.

### 4.3 Conversion formula from bytes/second to GB/day

If Prometheus returns log ingestion in bytes/second:

```text
GB/day = bytes_per_second × 86400 ÷ 1073741824
```

Example:

```text
5,242,880 bytes/sec × 86400 ÷ 1073741824 = about 421 GB/day
```

That example is important because 5 MB/sec does not sound large, but it becomes more than 400 GB per day.

## 5. Red Hat LokiStack size classes

Red Hat uses `1x.<size>` style sizing for LokiStack. The `1x` part is not something you arbitrarily increase; the size class determines the performance profile.

Typical OpenShift Logging 6.x LokiStack sizing classes:

| LokiStack size | Approximate data transfer target | Approximate QPS target | Typical usage |
|---|---:|---:|---|
| `1x.demo` | Demo only | Demo only | Lab/demo only, not production |
| `1x.pico` | ~50 GB/day | 1–25 QPS | SNO/edge/minimum viable deployment |
| `1x.extra-small` | ~100 GB/day | 1–25 QPS | Small clusters, light logging |
| `1x.small` | ~500 GB/day | 25–50 QPS | Medium production clusters |
| `1x.medium` | ~2 TB/day | 25–75 QPS | Large/high-volume production clusters |

Resource requests increase significantly as the size class grows. In OpenShift Logging 6.5 documentation, the current published sizing table shows approximate total requests such as:

| Size | CPU request | Memory request | Disk request | CPU with ruler | Memory with ruler | Disk with ruler |
|---|---:|---:|---:|---:|---:|---:|
| `1x.pico` | ~7 vCPU | ~17 Gi | ~590 Gi | ~8 vCPU | ~18 Gi | ~910 Gi |
| `1x.extra-small` | ~14 vCPU | ~31 Gi | ~430 Gi | ~16 vCPU | ~35 Gi | ~750 Gi |
| `1x.small` | ~34 vCPU | ~67 Gi | ~430 Gi | ~42 vCPU | ~83 Gi | ~750 Gi |
| `1x.medium` | ~54 vCPU | ~139 Gi | ~590 Gi | ~70 vCPU | ~171 Gi | ~910 Gi |

> Always confirm the exact table for your installed Red Hat OpenShift Logging version because Operator resource profiles can change between releases.

## 6. Initial sizing before installation

Before installation, you cannot accurately predict exact log volume. Node count and pod count are weak predictors because one verbose pod can generate huge daily logs, while hundreds of quiet pods may generate very little.

Use this practical starting approach:

| Cluster type | Initial LokiStack size |
|---|---|
| Single-node OpenShift / edge / lab | `1x.pico` |
| Small cluster, up to around 10 nodes | `1x.extra-small` |
| Medium or large cluster, more than around 10 nodes | `1x.medium` initially, then downsize/upsize after measurement if required |
| Known high-volume application platform | Start at least `1x.small`, often `1x.medium` |
| Compliance/security-heavy audit logging | Prefer external SIEM/archive for audit, keep Loki short-term |

### 6.1 Pre-installation checklist

Before creating LokiStack, answer these questions:

```text
1. How many days of in-cluster troubleshooting logs are required?
2. Are audit logs required in Loki, or only forwarded externally?
3. Which namespaces are noisy?
4. Are application teams allowed to log DEBUG/TRACE in production?
5. Is service mesh logging enabled?
6. Are ingress/access logs collected?
7. Will logs also be forwarded to Splunk/Elastic/SIEM?
8. Does object storage have lifecycle expiration?
9. What is the expected query pattern: last 15 minutes or last 30 days?
10. How many admins/dev teams query logs during incidents?
```

## 7. Post-installation sizing using real metrics

The correct production method is:

```text
Install with a reasonable baseline → collect real metrics → calculate GB/day → adjust LokiStack size and storage.
```

Wait at least 24 hours after installation. For better accuracy, use 7 days of data if the workload has weekday/weekend patterns.

### 7.1 PromQL: current Loki sink throughput

Use this query in the OpenShift web console under **Observe → Metrics**:

```promql
sum by (component_name) (
  rate(vector_component_sent_bytes_total{component_type="loki", component_kind="sink"}[5m])
)
```

This gives bytes/second sent by Vector to Loki.

### 7.2 PromQL: total bytes/second

```promql
sum(
  rate(vector_component_sent_bytes_total{component_type="loki", component_kind="sink"}[5m])
)
```

### 7.3 PromQL: 24-hour average bytes/second

```promql
avg_over_time(
  sum(rate(vector_component_sent_bytes_total{component_type="loki", component_kind="sink"}[5m]))[24h:5m]
)
```

If your Prometheus does not accept that nested expression directly, graph the 5-minute query over 24 hours and use average/visual inspection.

### 7.4 PromQL: peak ingestion over 24 hours

```promql
max_over_time(
  sum(rate(vector_component_sent_bytes_total{component_type="loki", component_kind="sink"}[5m]))[24h:5m]
)
```

Sizing should consider both:

```text
average GB/day for capacity
peak MB/sec for ingestion stability
```

### 7.5 Manual conversion

If Prometheus returns:

```text
8,388,608 bytes/sec
```

Then:

```text
8,388,608 × 86400 ÷ 1073741824 = 675 GB/day approximately
```

That exceeds `1x.small` target capacity and points toward `1x.medium`, unless filtering/drop policies reduce the rate.

## 8. Worked sizing examples

### 8.1 Example 1: Small production cluster

Observed ingestion:

```text
75 GB/day
```

Retention:

```text
7 days
```

Base storage:

```text
75 × 7 = 525 GB
```

Add overhead, growth, and safety:

```text
525 × 1.3 × 1.3 = 887 GB
```

Recommended object storage bucket:

```text
1 TB minimum
```

Recommended LokiStack size:

```text
1x.extra-small
```

Reasoning:

- Daily ingestion is below 100 GB/day.
- 7-day retention is short.
- Query load is probably low.
- 1 TB bucket gives breathing room.

### 8.2 Example 2: Medium cluster with 500 GB/day

Observed ingestion:

```text
500 GB/day
```

Retention:

```text
14 days
```

Base storage:

```text
500 × 14 = 7000 GB = 7 TB
```

Planned storage:

```text
7 TB × 1.3 × 1.5 = 13.65 TB
```

Recommended object storage:

```text
14–15 TB minimum
```

Recommended LokiStack size:

```text
1x.small minimum
```

Consider `1x.medium` if:

- Query range is often 7–14 days.
- Many dashboards auto-refresh.
- Ruler is enabled.
- Peak ingestion goes far above average.
- Audit logs are included.

### 8.3 Example 3: Large platform cluster

Observed ingestion:

```text
1.5 TB/day
```

Retention:

```text
30 days
```

Base storage:

```text
1.5 × 30 = 45 TB
```

Planned storage:

```text
45 × 1.3 × 1.5 = 87.75 TB
```

Recommended object storage:

```text
90–100 TB minimum
```

Recommended LokiStack size:

```text
1x.medium
```

Architecture recommendation:

```text
Keep LokiStack for short-term troubleshooting.
Forward compliance/security logs to an external SIEM or archive.
Avoid using in-cluster Loki as the only long-term historical log store.
```

### 8.4 Example 4: Audit-heavy cluster

Daily volume:

```text
Application:     80 GB/day
Infrastructure: 40 GB/day
Audit:          180 GB/day
Total:          300 GB/day
```

Retention requirement:

```text
Application troubleshooting: 7 days
Infrastructure: 14 days
Audit compliance: 180 days
```

Bad design:

```text
Store all logs in LokiStack for 180 days.
```

Better design:

```text
LokiStack:
  Application: 7 days
  Infrastructure: 14 days
  Audit: 3–7 days for quick troubleshooting

External SIEM/archive:
  Audit: 180 days or more
```

Reasoning:

- LokiStack is not designed as the long-term compliance archive.
- Audit logs are usually more valuable in SIEM/security analytics.
- Retention policies should match log value and query pattern.

## 9. Retention sizing

Retention is the biggest storage multiplier.

```text
100 GB/day × 7 days  = 700 GB
100 GB/day × 30 days = 3 TB
100 GB/day × 180 days = 18 TB
```

That is before overhead, growth, and safety margin.

### 9.1 Retention by log type

Use different retention policies where possible.

| Log type | Typical Loki retention | External retention |
|---|---:|---:|
| Application logs | 3–14 days | Optional, based on business need |
| Infrastructure logs | 7–30 days | Optional/central ops archive |
| Audit logs | 1–7 days in Loki | 90–365+ days in SIEM/archive |
| Security event logs | 1–7 days in Loki | SIEM/archive required |
| Debug/trace logs | Hours to a few days | Usually not retained long term |

### 9.2 Why retention must be explicitly configured

If neither object storage lifecycle expiration nor LokiStack retention is configured, logs can continue accumulating and eventually fill object storage or increase cost unexpectedly.

Best practice order:

```text
1. Prefer object storage lifecycle expiration for cost-efficient deletion.
2. Use LokiStack retention when object storage lifecycle is unavailable or when stream-based rules are required.
3. Document retention requirements by log type and tenant.
```

### 9.3 Example LokiStack retention configuration

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  managementState: Managed
  size: 1x.small
  storage:
    schemas:
    - effectiveDate: "2024-01-01"
      version: v13
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: gp3-csi
  tenants:
    mode: openshift-logging
  limits:
    global:
      retention:
        days: 14
        streams:
        - days: 3
          priority: 1
          selector: '{log_type="infrastructure"}'
        - days: 7
          priority: 2
          selector: '{kubernetes_namespace_name=~"prod-.+"}'
```

Notes:

- Use `schema v13` for new deployments unless your vendor/version guidance says otherwise.
- Match selectors carefully. A wrong selector means retention does not affect the intended streams.
- Global retention and tenant/stream retention should be documented.
- For compliance, verify retention with real object storage lifecycle and SIEM policy.

## 10. Object storage sizing

LokiStack stores log data in object storage. Supported backends include S3-compatible stores and common cloud object stores.

Common choices:

- AWS S3.
- Azure Blob.
- Google Cloud Storage.
- S3-compatible object storage.
- OpenShift Data Foundation / Ceph RGW.
- Swift.

### 10.1 Object storage sizing formula

```text
Object storage required = Daily ingest × retention × overhead × growth × safety
```

Example:

```text
Daily ingest: 250 GB/day
Retention: 14 days
Overhead: 1.25
Growth: 1.5
Safety: 1.2

250 × 14 × 1.25 × 1.5 × 1.2 = 7,875 GB
```

Recommendation:

```text
Provision at least 8 TB, preferably 10 TB if growth is expected.
```

### 10.2 Object storage performance considerations

Capacity alone is not enough. Check:

```text
- PUT request rate
- GET request rate
- LIST operation behavior
- Object lifecycle expiration
- Bucket quota
- Network path between OpenShift and object store
- TLS/certificate trust
- Object storage latency
- Throttling limits
- Multi-AZ/zone availability
```

Poor object storage performance can appear as Loki query slowness, compactor issues, or ingestion backpressure.

### 10.3 Object storage lifecycle

For production, create lifecycle rules such as:

```text
Delete objects older than N days.
Abort incomplete multipart uploads.
Expire non-current versions if bucket versioning is enabled.
Clean temporary prefixes if used by the backend.
```

Important:

```text
Retention in LokiStack and lifecycle in the bucket must not conflict.
```

For example, if Loki retention is 14 days but bucket lifecycle deletes at 7 days, users will see missing logs for the 7–14 day window.

## 11. Local disk/PVC sizing for LokiStack

Do not confuse two different storage types:

```text
Object storage capacity = long-lived log data
LokiStack local disk/PVCs = working data, WAL/cache/temporary/index-related component storage
```

The Red Hat LokiStack size table includes **total disk requests** for the Loki components. These disk requests are not the same as object bucket capacity.

Operationally, verify:

```bash
oc get pvc -n openshift-logging
oc get pv | grep openshift-logging
oc describe pvc -n openshift-logging <pvc-name>
oc adm top pods -n openshift-logging
```

Check for:

```text
- Pending PVCs
- Wrong StorageClass
- Insufficient worker node disk
- StorageClass not supporting required access mode
- Disk pressure on logging nodes
- Loki pods stuck due to volume attach/mount issues
```

## 12. Collector sizing and filtering

Vector collectors run as DaemonSet pods and read logs from each node.

Collector sizing matters because every byte must first be read, parsed, enriched, and sent to output.

### 12.1 Collector resource check

```bash
oc -n openshift-logging get pods -o wide
oc -n openshift-logging get daemonset
oc adm top pods -n openshift-logging
oc -n openshift-logging logs <collector-pod-name> --tail=200
```

### 12.2 Collector CPU/memory resources

In the `ClusterLogForwarder` API, collector resources can be tuned under `spec.collector.resources`.

Example:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    resources:
      requests:
        cpu: 200m
        memory: 1Gi
      limits:
        cpu: 1000m
        memory: 2Gi
```

Tune collectors when you see:

```text
- Collector OOMKilled
- Delayed log forwarding
- Backpressure warnings
- High CPU on collector pods
- Rate-limit retry loops
- Dropped/late logs during peak periods
```

### 12.3 Filtering before storage

The cheapest log is the log you do not store.

Apply filtering to:

- Drop debug logs from noisy namespaces.
- Exclude health-check access logs.
- Exclude known useless sidecar logs.
- Route high-volume logs to cheaper external storage.
- Keep only required fields where transformation is supported.

Practical examples of logs to consider dropping or shortening:

```text
- HTTP 200 health probe logs
- Kubernetes readiness/liveness probe access logs
- DEBUG logs in production
- Repeated stack traces from known crash loops
- High-frequency service mesh access logs where not required
```

### 12.4 Namespace-based filtering strategy

Use labels and naming conventions:

```text
prod-*       → retain 7–14 days
nonprod-*    → retain 1–3 days
security-*   → forward to SIEM
ci-*         → short retention or external cheap storage
```

## 13. Query sizing: QPS and query range

Storage capacity answers “can I keep the logs?” Query sizing answers “can users search the logs fast enough?”

Query load increases with:

```text
- More users querying Observe → Logs
- Grafana dashboards with frequent auto-refresh
- Alert rules using LogQL
- Long time ranges such as 7, 14, or 30 days
- Expensive regex filters
- High-cardinality labels
- Broad queries without namespace/pod/container filters
```

### 13.1 Good query behavior

Encourage users to query like this:

```text
{log_type="application", kubernetes_namespace_name="payments"}
```

Then filter:

```text
|= "error"
```

Avoid starting with a broad query like:

```text
{log_type="application"} |= "error"
```

across 30 days during an incident unless the system is sized for it.

### 13.2 Query range policy

Recommended practice:

| User need | Query range |
|---|---:|
| Live troubleshooting | 5–30 minutes |
| Incident investigation | 1–6 hours |
| Recent regression | 24–72 hours |
| Weekly trend | External analytics preferred |
| Monthly compliance search | SIEM/archive preferred |

### 13.3 Ruler impact

The Loki ruler evaluates alerting rules and retention-related processing. Enable it only when needed and size for the extra CPU/memory. Rules multiply load by:

```text
number of tenants × number of rules × data volume × evaluation frequency
```

## 14. Ingestion rate limits and burst sizing

A cluster can have acceptable average daily ingestion but still fail during bursts.

Example:

```text
Average: 200 GB/day
Peak during incident: 30 MB/sec for 20 minutes
```

This can trigger rate-limit errors even though daily storage is fine.

### 14.1 Symptoms of ingestion bottleneck

```text
- HTTP 429 from Loki
- "Ingestion rate limit exceeded"
- Collector retry messages
- Logs visible late
- Ingester CPU high
- Distributor warnings
- Backpressure in collector logs
```

### 14.2 LokiStack ingestion limit example

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  limits:
    global:
      ingestion:
        ingestionRate: 16
        ingestionBurstSize: 32
```

Meaning:

```text
ingestionRate      = soft MB/sec style limit
ingestionBurstSize = hard burst size limit for large pushes
```

Use higher values carefully. Increasing limits without increasing CPU/memory/object storage performance can simply move the bottleneck elsewhere.

## 15. Cardinality and label sizing

Loki performs best when labels are controlled. High cardinality creates index pressure and slow queries.

### 15.1 High-cardinality labels to avoid

Do not use labels such as:

```text
request_id
trace_id
span_id
user_id
session_id
transaction_id
pod_uid if unnecessary
container_id if unnecessary
full URL with query string
client IP as label
```

These values change too frequently and explode stream count.

### 15.2 Better approach

Keep them in log body, not labels:

```json
{
  "level": "error",
  "trace_id": "abc123",
  "message": "payment failed"
}
```

Search using LogQL parsing/filtering instead of indexing every unique value as a label.

### 15.3 Good labels

Generally useful labels:

```text
log_type
kubernetes_namespace_name
kubernetes_pod_name
kubernetes_container_name
app
component
environment
cluster
```

Even these should be reviewed if they generate too many unique streams.

## 16. Production sizing workflow

Use this as a field runbook.

### Step 1: Identify logging objective

```text
Is Loki used for:
- troubleshooting only?
- central platform logs?
- developer self-service logs?
- audit/security logs?
- compliance retention?
```

If compliance retention is required, design external archive/SIEM first.

### Step 2: Decide log categories

```text
application: yes/no
infrastructure: yes/no
audit: yes/no
```

Do not collect audit logs into Loki by default unless you have a reason and capacity.

### Step 3: Choose initial size

```text
SNO/edge       → 1x.pico
small cluster  → 1x.extra-small
medium/large   → 1x.small or 1x.medium
```

### Step 4: Provision object storage

Calculate:

```text
estimated_GB_day × retention_days × 1.3 × growth_factor
```

Add lifecycle policy.

### Step 5: Deploy LokiStack and ClusterLogForwarder

Verify:

```bash
oc get pods -n openshift-logging
oc get lokistack -n openshift-logging
oc get clusterlogforwarder -n openshift-logging
oc get pvc -n openshift-logging
```

### Step 6: Observe real ingestion for 24 hours

Use PromQL:

```promql
sum(rate(vector_component_sent_bytes_total{component_type="loki", component_kind="sink"}[5m]))
```

### Step 7: Convert to GB/day

```text
GB/day = bytes/sec × 86400 ÷ 1073741824
```

### Step 8: Compare with size table

```text
≤50 GB/day       → 1x.pico may be enough
≤100 GB/day      → 1x.extra-small
≤500 GB/day      → 1x.small
≤2 TB/day        → 1x.medium
>2 TB/day        → reduce logs, split architecture, external log platform, vendor review
```

### Step 9: Validate query behavior

Test:

```text
last 15 minutes
last 1 hour
last 6 hours
last 24 hours
retention boundary search
```

### Step 10: Tune filters, retention, and limits

Reduce storage before simply adding capacity.

## 17. Resizing LokiStack

If measured ingestion exceeds your selected size, update the LokiStack CR.

Example:

```bash
oc -n openshift-logging patch lokistack logging-loki --type=merge -p '{"spec":{"size":"1x.small"}}'
```

Or edit manually:

```bash
oc -n openshift-logging edit lokistack logging-loki
```

Change:

```yaml
spec:
  size: 1x.small
```

Important operational notes:

```text
- Resizing can cause rolling restarts of Loki components.
- Plan during maintenance windows for production clusters.
- Confirm node capacity before increasing size.
- Check pending pods and PVCs after resize.
- Validate ingestion and query metrics after resize.
```

Verification:

```bash
oc -n openshift-logging get pods -w
oc -n openshift-logging get lokistack logging-loki -o yaml
oc -n openshift-logging get events --sort-by=.lastTimestamp | tail -50
```

## 18. External forwarding and sizing impact

Many enterprises forward logs to external systems.

Example outputs:

```text
Splunk
Kafka
Elasticsearch/OpenSearch
Syslog
Cloud logging
SIEM
```

### 18.1 Important sizing point

Forwarding logs externally does not eliminate collection cost. Vector still reads, processes, and sends logs.

If you send logs to both Loki and Splunk:

```text
Collector output traffic roughly doubles.
```

If you apply different filters per output, sizing depends on each pipeline.

### 18.2 Recommended enterprise pattern

```text
LokiStack:
  recent platform/application troubleshooting logs

External SIEM:
  audit/security/compliance logs

External archive/object storage:
  long-term immutable retention

Kafka:
  fan-out buffer for multiple consumers
```

### 18.3 When to avoid storing in Loki

Avoid or reduce Loki storage for:

```text
- High-volume access logs needed only for analytics
- Audit logs requiring 180+ days retention
- Security logs already handled by SIEM
- CI logs with low operational value after a few days
- Debug/trace logs from non-production workloads
```

## 19. Troubleshooting storage sizing problems

### 19.1 Problem: Logs are missing

Possible causes:

```text
- Collector cannot read source logs
- Collector RBAC missing
- Pipeline not selecting correct input
- Loki rate limiting
- Object storage issue
- Retention/lifecycle deleting earlier than expected
- Query selector is wrong
- Time range is wrong
- Clock/timezone issue
```

Commands:

```bash
oc -n openshift-logging get pods -o wide
oc -n openshift-logging get clusterlogforwarder -o yaml
oc -n openshift-logging logs <collector-pod> --tail=200
oc -n openshift-logging logs <loki-distributor-or-gateway-pod> --tail=200
oc -n openshift-logging get events --sort-by=.lastTimestamp | tail -100
```

### 19.2 Problem: Object storage is filling too fast

Check:

```text
- Is retention configured?
- Is bucket lifecycle configured?
- Are audit logs unexpectedly collected?
- Did one namespace start DEBUG logging?
- Did service mesh/access logs increase?
- Is there duplicate forwarding into Loki?
- Did application deployment create a log loop?
```

PromQL:

```promql
sum by (component_name) (
  rate(vector_component_sent_bytes_total{component_type="loki", component_kind="sink"}[5m])
)
```

Operational actions:

```text
1. Identify noisy namespace/app.
2. Apply filters or lower application verbosity.
3. Shorten retention for low-value streams.
4. Confirm object lifecycle expiration.
5. Increase bucket capacity only after reducing waste.
```

### 19.3 Problem: Loki returns 429 rate-limit errors

Look for messages like:

```text
Ingestion rate limit exceeded
Per stream rate limit exceeded
Too Many Requests
```

Actions:

```text
1. Identify whether this is temporary burst or constant overload.
2. Check current bytes/sec and peak bytes/sec.
3. Reduce noisy logs if possible.
4. Increase LokiStack size if sustained volume exceeds size class.
5. Tune ingestionRate/ingestionBurstSize only after understanding bottleneck.
6. Check object storage latency and Loki pod CPU/memory.
```

### 19.4 Problem: Queries are slow

Check:

```text
- Query time range too large
- Regex-heavy query
- Broad tenant/log_type query
- High-cardinality labels
- Under-sized querier/frontend
- Object storage latency
- Too many dashboard refreshes
```

Better query pattern:

```logql
{log_type="application", kubernetes_namespace_name="payments"} |= "error"
```

Avoid:

```logql
{log_type="application"} |~ ".*error.*"
```

across many days.

### 19.5 Problem: Collector pods OOMKilled

Check:

```bash
oc -n openshift-logging get pods
oc -n openshift-logging describe pod <collector-pod>
oc -n openshift-logging logs <collector-pod> --previous --tail=200
oc adm top pod -n openshift-logging
```

Actions:

```text
- Increase collector memory.
- Reduce log volume.
- Filter early.
- Check external output slowness.
- Check network and DNS to output backends.
```

### 19.6 Problem: PVC pending for LokiStack

Check:

```bash
oc -n openshift-logging get pvc
oc -n openshift-logging describe pvc <pvc-name>
oc get sc
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -50
```

Common causes:

```text
- Wrong StorageClass
- Storage quota exhausted
- Zone mismatch
- WaitForFirstConsumer scheduling issue
- Worker node capacity shortage
- Storage backend degraded
```

## 20. Advanced production recommendations

### 20.1 Separate retention by value

Do not retain all logs equally.

```text
Critical security/audit logs → SIEM/archive, long retention
Application error logs       → moderate retention
Access/health logs           → short retention or drop
Debug logs                   → very short retention
```

### 20.2 Use external storage for long-term logs

If the requirement says:

```text
90 days
180 days
1 year
7 years
legal hold
immutable archive
security analytics
```

then LokiStack should not be the only storage system.

### 20.3 Set application logging standards

Platform teams should define:

```text
- Default production log level: INFO or WARN
- DEBUG allowed only temporarily
- JSON structured logs preferred
- No secrets in logs
- No high-cardinality labels
- Access log sampling where acceptable
- Health-check log suppression
```

### 20.4 Create namespace onboarding policy

For each namespace/project, define:

```text
owner
application criticality
expected log volume
retention requirement
SIEM forwarding requirement
PII/security classification
allowed log level
```

### 20.5 Monitor log volume as an SLO

Create internal alerts such as:

```text
- Total logging ingestion > 80% of LokiStack size target
- Object bucket > 80% capacity or budget threshold
- Collector restarts > 0
- Loki 429 errors > threshold
- Query latency above threshold
- Daily log volume increased > 50% from baseline
```

## 22. Design patterns

### 22.1 Small internal OpenShift cluster

```text
Nodes: 3–10
Log volume: <100 GB/day
Retention: 7 days
LokiStack: 1x.extra-small
Object storage: 1–2 TB
Audit: forward externally if required
```

### 22.2 Medium production application platform

```text
Nodes: 10–50
Log volume: 100–500 GB/day
Retention: 7–14 days
LokiStack: 1x.small
Object storage: 5–15 TB
External forwarding: audit/security logs
```

### 22.3 Large multi-tenant platform

```text
Nodes: 50+
Log volume: 500 GB/day–2 TB/day
Retention: 7–30 days in Loki for selected logs
LokiStack: 1x.medium
Object storage: tens of TB
External SIEM/archive: mandatory for audit/compliance
Governance: namespace log policies required
```

### 22.4 Regulated environment

```text
LokiStack: short troubleshooting window only
Audit/security: SIEM + immutable archive
Retention: defined by compliance team
Bucket lifecycle: enforced and audited
Access control: strict tenant separation
Log redaction: required
```

## 23. Common sizing mistakes

### Mistake 1: Sizing by node count only

Wrong:

```text
20 nodes means 1 TB is enough.
```

Correct:

```text
Measure actual GB/day and peak MB/sec.
```

### Mistake 2: Ignoring audit logs

Audit logs can exceed application logs in busy clusters.

### Mistake 3: No retention policy

Without retention or lifecycle policy, object storage can grow indefinitely.

### Mistake 4: Treating Loki as a SIEM archive

LokiStack in OpenShift Logging is for short-term troubleshooting, not long-term compliance analytics.

### Mistake 5: Allowing DEBUG logs permanently

A single DEBUG deployment can break sizing assumptions.

### Mistake 6: Not accounting for query load

A bucket may have enough capacity, but queries may still fail due to insufficient CPU/memory/QPS sizing.

### Mistake 7: Increasing ingestion limits without increasing capacity

Raising limits can hide rate-limit errors but cause CPU, memory, object storage, or query failures later.

### Mistake 8: High-cardinality labels

Putting request IDs or user IDs into labels damages Loki performance.

### Mistake 9: No growth factor

Clusters grow. Applications become more verbose. Incidents produce more logs. Always include growth.

## 24. Interview and senior admin talking points

Use these points in an advanced OpenShift admin interview:

```text
1. I size logging from observed GB/day, not pod count.
2. Retention multiplied by daily ingest gives the base object storage requirement.
3. I add overhead, growth, and safety margin before provisioning storage.
4. LokiStack is best for short-term troubleshooting; long-term compliance logs should go to SIEM/archive.
5. I measure Vector-to-Loki throughput using Prometheus metrics.
6. I validate both average daily ingestion and peak ingestion bursts.
7. I tune retention by stream/tenant/log type instead of keeping all logs equally.
8. I avoid high-cardinality labels in Loki.
9. I monitor ingestion rate, 429 errors, collector restarts, object bucket growth, and query latency.
10. I prefer reducing noisy logs before blindly increasing storage.
```

## 26. Senior-level final recommendation

For production OpenShift Logging, use this decision model:

```text
1. Start with the smallest safe LokiStack size for the cluster class.
2. Measure actual ingestion after at least 24 hours.
3. Convert bytes/sec to GB/day.
4. Select LokiStack size based on daily volume and QPS.
5. Size object storage as daily volume × retention × overhead × growth × safety.
6. Use explicit retention and bucket lifecycle.
7. Keep Loki retention short, usually 7–30 days maximum depending on support/version guidance.
8. Forward audit/security/compliance logs to SIEM/archive.
9. Reduce noisy logs at source or with filters.
10. Revisit sizing after major application onboarding, audit policy changes, service mesh enablement, or cluster upgrades.
```

The best OpenShift administrators do not treat logging storage as a one-time installation parameter. They run it as an ongoing capacity management process with dashboards, alerts, retention governance, and regular review with application and security teams.
