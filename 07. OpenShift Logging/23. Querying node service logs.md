# Querying Node Service Logs in OpenShift Logging

**Audience:** Advanced OpenShift Administration / DO380-style Day-2 operations  
**Experience level:** Senior Linux, Kubernetes, and OpenShift administrator with ~10 years of production experience  
**Primary tools:** `oc adm node-logs`, `oc debug node`, `journalctl`, `oc adm must-gather`, `oc adm inspect`  
**Scope:** OpenShift Container Platform 4.x, RHCOS-based nodes, node-level service and journal log troubleshooting

---

## 1. What “querying node service logs” means

In OpenShift, **node service logs** are the logs generated by services running directly on cluster nodes, usually managed by **systemd** and recorded in the **systemd journal**. These logs are different from normal application container logs that you query with `oc logs`, Loki, or the OpenShift web console.

Node service logs are useful when troubleshooting problems below the application layer, for example:

- Kubelet failures
- Node `NotReady` conditions
- Container runtime issues
- Static pod startup problems
- Control plane component symptoms
- Machine Config Operator changes
- CRI-O, kubelet, networking, DNS, certificate, and image pull issues
- Node boot and reboot problems
- Drain, cordon, eviction, and pressure-related issues

The primary OpenShift command for querying node service logs from the cluster API is:

```bash
oc adm node-logs
```

The most common form is:

```bash
oc adm node-logs --role=master -u kubelet
oc adm node-logs --role=worker -u kubelet
```

For a specific node:

```bash
oc adm node-logs <node-name> -u kubelet
```

Conceptually, this is similar to running `journalctl -u kubelet` on the node, but it is accessed through OpenShift/Kubernetes APIs rather than requiring SSH into the host.

## 2. Why senior OpenShift admins care about node service logs

A beginner usually starts troubleshooting with:

```bash
oc get pods -A
oc logs <pod>
oc describe pod <pod>
```

A senior OpenShift administrator knows that many failures are **node-originated**, not application-originated.

For example:

| Symptom | Often visible in | Why node service logs matter |
|---|---|---|
| Pod stuck in `ContainerCreating` | Pod events | Kubelet or CRI-O logs show mount, image, CNI, or runtime errors |
| Node `NotReady` | `oc get nodes` | Kubelet logs show API connectivity, certificate, cgroup, or runtime issues |
| Image pull fails intermittently | Pod events | CRI-O or kubelet logs show registry/auth/network timeout details |
| Static pod degraded | ClusterOperator status | Node journal shows kubelet managing static pods and failing containers |
| MachineConfigPool updating forever | MCP status | Kubelet, rpm-ostree, pivot, or MCD logs explain reboot/update failures |
| Network policy or OVN issue | Pod connectivity tests | OVN and node-level logs may show flow or daemon problems |
| Node pressure eviction | Pod status and events | Kubelet logs show eviction thresholds and resource pressure decisions |
| API degraded | ClusterOperator status | Control plane node service logs help distinguish API pod issue vs node issue |

In production, node service logs answer questions like:

- Did the kubelet restart?
- Did CRI-O fail to create the sandbox?
- Did the node reboot during an update?
- Did the node lose API connectivity?
- Did the runtime fail to mount a volume?
- Did SELinux, cgroups, DNS, or certificate validation cause the issue?
- Did Machine Config Daemon reboot the node intentionally?
- Did pods fail because of node-level pressure rather than application failure?

## 3. Node service logs vs other OpenShift logs

| Log type | Main command | Source | Best for |
|---|---|---|---|
| Application pod logs | `oc logs` | Container stdout/stderr | App runtime, app exceptions, pod-level logs |
| Previous container logs | `oc logs --previous` | Previous container instance | CrashLoopBackOff investigation |
| Events | `oc get events`, `oc describe` | Kubernetes API events | Scheduling, image pull, mount, admission, probe events |
| Operator logs | `oc logs -n <operator-ns>` | Operator pod logs | Operator reconciliation and controller issues |
| Node service logs | `oc adm node-logs` | Node journald/systemd logs | Kubelet, CRI-O, host service, node runtime issues |
| Host file logs under `/var/log` | `oc adm node-logs --path=...` | Node filesystem | Audit logs, control plane log files, host logs |
| Full support bundle | `oc adm must-gather` | Cluster-wide data | Support cases and broad diagnostics |
| Node debug shell | `oc debug node/<node>` | Debug pod with host mounted at `/host` | Deep node investigation without direct SSH |
| SSH logs | `ssh core@<node> journalctl ...` | Direct host access | Last resort when API/kubelet path is unavailable |

A strong admin does not rely on one log source. The real workflow is to correlate:

```text
ClusterOperator condition -> Node condition -> Events -> Pod status -> Kubelet/CRI-O logs -> must-gather
```

## 4. Architecture behind `oc adm node-logs`

When you run:

```bash
oc adm node-logs <node-name> -u kubelet
```

OpenShift queries node logs through privileged node log access. The command retrieves logs from supported node log backends, normally the systemd journal, and can also access paths under `/var/log`.

Important architecture points:

1. **It is not querying Loki by default.**  
   `oc adm node-logs` is a node diagnostic command, not a Loki query command.

2. **It depends on cluster API availability.**  
   If the API is down or unreachable, `oc adm node-logs` might not work.

3. **It requires privileged access.**  
   Node logs can contain sensitive data, tokens, paths, hostnames, certificate messages, command output, and infrastructure details.

4. **It is usually better than SSH for normal Day-2 work.**  
   OpenShift nodes are RHCOS-based and intended to be managed by Operators, not manually administered over SSH.

5. **It can query systemd units.**  
   The `-u` or `--unit` flag selects services such as `kubelet`, `crio`, or other systemd units.

6. **It can query `/var/log` paths.**  
   With `--path`, you can inspect files under the node’s `/var/log` directory.

## 5. Prerequisites

Before querying node service logs, verify these prerequisites.

### 5.1 Login and permissions

You normally need cluster-admin or equivalent node log permission:

```bash
oc whoami
oc auth can-i get nodes/log
oc adm policy who-can --all-namespaces get nodes/log
```

Expected result for a privileged admin:

```bash
yes
```

If the user does not have permission, you might see errors similar to:

```text
Error from server (Forbidden): nodes/log is forbidden
```

### 5.2 OpenShift CLI installed

```bash
oc version
```

Best practice: use an `oc` client version close to the cluster version.

### 5.3 API availability

Because `oc adm node-logs` goes through the OpenShift/Kubernetes API path, verify the API is functional:

```bash
oc whoami --show-server
oc get clusterversion
oc get nodes
```

If the API is not functional, use SSH only as a fallback, for example:

```bash
ssh core@<node>.<cluster_name>.<base_domain> sudo journalctl -b -u kubelet
```

### 5.4 Node names and roles

```bash
oc get nodes -o wide
oc get nodes --show-labels
```

Common node role labels:

```text
node-role.kubernetes.io/master
node-role.kubernetes.io/worker
node-role.kubernetes.io/infra
```

In newer terminology, `master` nodes are often called **control plane** nodes, but the role label and many command examples still use `master`.

## 6. Basic command syntax

General syntax:

```bash
oc adm node-logs [node-name] [options]
```

Common patterns:

```bash
# Kubelet logs from all control plane nodes
oc adm node-logs --role=master -u kubelet

# Kubelet logs from all worker nodes
oc adm node-logs --role=worker -u kubelet

# Kubelet logs from one specific node
oc adm node-logs worker-0.example.com -u kubelet

# CRI-O logs from one node
oc adm node-logs worker-0.example.com -u crio

# Multiple units
oc adm node-logs worker-0.example.com -u kubelet -u crio

# Tail last 100 lines
oc adm node-logs worker-0.example.com -u kubelet --tail=100

# Logs since relative time
oc adm node-logs worker-0.example.com -u kubelet --since=1h

# Logs before/after a time window
oc adm node-logs worker-0.example.com -u kubelet \
  --since='2026-07-03T09:00:00Z' \
  --until='2026-07-03T09:30:00Z'

# Grep inside node service logs
oc adm node-logs worker-0.example.com -u kubelet -g 'eviction|pressure|failed|error'

# JSON output for parsing
oc adm node-logs worker-0.example.com -u kubelet -o json
```

## 7. Important `oc adm node-logs` options

| Option | Meaning | Example |
|---|---|---|
| `<node-name>` | Query one node | `oc adm node-logs worker-0 -u kubelet` |
| `--role=<role>` | Query nodes by role | `--role=master`, `--role=worker` |
| `-l`, `--selector` | Query nodes by label | `-l node-role.kubernetes.io/infra=` |
| `-u`, `--unit` | Query systemd unit logs | `-u kubelet`, `-u crio` |
| `--tail=<n>` | Return last `n` lines | `--tail=200` |
| `--since=<time>` | Logs after relative or ISO time | `--since=2h` |
| `--until=<time>` | Logs before relative or ISO time | `--until='2026-07-03T10:00:00Z'` |
| `-g`, `--grep` | Regex filter | `-g 'error|failed'` |
| `--case-sensitive=false` | Case-insensitive filter | `--case-sensitive=false -g error` |
| `--boot=<offset>` | Select current or previous boot | `--boot=0`, `--boot=-1` |
| `-o`, `--output` | Format service logs | `-o short`, `-o json`, `-o cat` |
| `--path=<path>` | Read `/var/log/<path>` | `--path=openshift-apiserver/audit.log` |
| `--unify` | Interleave/sort multi-node output | `--unify=true` |
| `--raw` | Avoid transformation | `--raw=true` |

### Senior admin note

Use time filtering aggressively in production. Pulling full logs from many nodes creates noise and can delay troubleshooting.

Bad first command in a large cluster:

```bash
oc adm node-logs --role=worker -u kubelet
```

Better:

```bash
oc adm node-logs <suspect-node> -u kubelet --since=30m --tail=500
```

Best when you know the incident window:

```bash
oc adm node-logs <suspect-node> -u kubelet \
  --since='2026-07-03T08:55:00Z' \
  --until='2026-07-03T09:10:00Z' \
  -g 'error|fail|evict|pressure|timeout|certificate|cni|mount'
```

## 8. Which systemd units to query

The exact units can vary by OpenShift version and node role, but these are common investigation targets.

| Unit | Why query it |
|---|---|
| `kubelet` | Pod lifecycle, node readiness, volume mount, image pull, eviction, CNI, static pod management |
| `crio` | Container runtime, pod sandbox creation, image handling, runtime errors |
| `rpm-ostreed` | RHCOS OS update and image pivot symptoms |
| `NetworkManager` | Node network interface, DNS, routes, bonding, VLAN, DHCP symptoms |
| `chronyd` | Time sync, certificate validation, token expiry, clock skew |
| `sshd` | Emergency access audit and SSH troubleshooting |
| `kubelet.service` | Same unit name style when using `journalctl` directly on node |
| `machine-config-daemon` related logs | Usually collected from MCD pod logs, but node reboot/update symptoms also appear in journal |

To discover units directly on a node, use a debug session:

```bash
oc debug node/<node-name>
chroot /host
systemctl list-units --type=service --state=running
systemctl list-unit-files | grep -E 'kubelet|crio|ostree|NetworkManager|chrony'
```

## 9. Querying kubelet logs

The kubelet is one of the most important node services in OpenShift. It is responsible for:

- Registering the node with the cluster
- Reporting node status
- Starting and stopping pods through CRI-O
- Managing static pods on control plane nodes
- Applying pod resource limits and cgroup configuration
- Running probes
- Mounting volumes
- Reporting image pull and container lifecycle errors
- Enforcing eviction decisions

### 9.1 Kubelet logs from all control plane nodes

```bash
oc adm node-logs --role=master -u kubelet --tail=200
```

Use this when:

- API server static pods are failing
- Control plane operator is degraded
- Control plane node is restarting static pods
- You are investigating kube-apiserver, kube-controller-manager, scheduler, or etcd pod lifecycle symptoms

### 9.2 Kubelet logs from all worker nodes

```bash
oc adm node-logs --role=worker -u kubelet --tail=200
```

Use this when:

- Multiple workloads fail across workers
- Pods are stuck in `ContainerCreating`
- Cluster-wide node pressure is suspected
- Network or storage daemonsets are causing broad failures

### 9.3 Kubelet logs from one node

```bash
NODE=worker-0.example.com
oc adm node-logs $NODE -u kubelet --since=1h --tail=1000
```

Use this when:

- A specific node is `NotReady`
- A pod is failing only on one node
- A node rebooted
- A node has disk, memory, PID, or network pressure

### 9.4 Follow kubelet logs directly through debug shell

`oc adm node-logs` is best for API-based collection. For interactive investigation:

```bash
oc debug node/<node-name>
chroot /host
journalctl -b -f -u kubelet.service
```

This is useful when you are reproducing a problem live, such as creating a pod and watching kubelet react.

## 10. Querying CRI-O logs

CRI-O is the OpenShift container runtime. Kubelet talks to CRI-O to create pod sandboxes and containers.

Common symptoms that require CRI-O logs:

- `FailedCreatePodSandBox`
- `ContainerCreating` stuck
- Runtime timeout
- Image pull problem after kubelet handoff
- Storage driver issues
- SELinux runtime labeling symptoms
- Pod sandbox network namespace creation failures
- Runtime crash or restart

Commands:

```bash
# CRI-O logs from a specific node
oc adm node-logs <node-name> -u crio --since=1h --tail=500

# CRI-O logs from worker nodes
oc adm node-logs --role=worker -u crio --since=30m

# Filter CRI-O errors
oc adm node-logs <node-name> -u crio --since=2h \
  -g 'error|failed|timeout|sandbox|image|storage|overlay|selinux'
```

Correlate CRI-O with kubelet:

```bash
oc adm node-logs <node-name> -u kubelet -u crio --since=1h --tail=1000
```

Senior workflow:

1. `oc describe pod <pod>` to find event reason.
2. Identify node with `oc get pod -o wide`.
3. Query kubelet logs on that node.
4. Query CRI-O logs on same node for the exact timestamp.
5. Compare event timestamp, kubelet message, CRI-O message.

Example:

```bash
POD=myapp-abc123
NS=prod
NODE=$(oc get pod $POD -n $NS -o jsonpath='{.spec.nodeName}')

echo $NODE
oc describe pod $POD -n $NS
oc adm node-logs $NODE -u kubelet --since=30m -g 'myapp|sandbox|failed|error'
oc adm node-logs $NODE -u crio --since=30m -g 'myapp|sandbox|failed|error'
```

## 11. Querying logs by node role

### 11.1 Control plane nodes

```bash
oc adm node-logs --role=master -u kubelet --since=1h
```

Use for:

- Control plane static pod lifecycle
- API server symptoms
- Scheduler/controller-manager pod restarts
- Etcd pod startup from kubelet perspective
- Control plane node update or reboot investigation

### 11.2 Worker nodes

```bash
oc adm node-logs --role=worker -u kubelet --since=1h
oc adm node-logs --role=worker -u crio --since=1h
```

Use for:

- Workload scheduling and runtime issues
- CNI and volume mount problems
- Node pressure and evictions
- Image pull/runtime failures

### 11.3 Infra nodes

If infra nodes are labeled separately:

```bash
oc get nodes -l node-role.kubernetes.io/infra=
oc adm node-logs -l node-role.kubernetes.io/infra= -u kubelet --since=1h
```

Use for:

- Router pod issues
- Registry pod issues
- Monitoring/logging infra workload problems
- Ingress and infrastructure service placement issues

## 12. Querying logs by node label selector

Sometimes roles are not enough. Use selectors when troubleshooting a node pool, zone, hardware type, or infra group.

```bash
oc get nodes --show-labels
```

Examples:

```bash
# Nodes in a zone
oc adm node-logs -l topology.kubernetes.io/zone=ap-south-1a -u kubelet --since=1h

# Nodes with a custom pool label
oc adm node-logs -l node.openshift.io/os_id=rhcos -u kubelet --since=1h

# Infra-labeled nodes
oc adm node-logs -l node-role.kubernetes.io/infra= -u crio --since=2h
```

This is very useful in large clusters because failures are often localized to:

- One availability zone
- One rack
- One vSphere cluster
- One bare-metal hardware batch
- One MachineConfigPool
- One network segment
- One storage backend path

## 13. Querying logs by time window

### 13.1 Relative time

```bash
oc adm node-logs <node-name> -u kubelet --since=10m
oc adm node-logs <node-name> -u kubelet --since=2h
oc adm node-logs <node-name> -u crio --since=1d
```

### 13.2 Absolute time

Use ISO/RFC3339-style timestamps when possible:

```bash
oc adm node-logs <node-name> -u kubelet \
  --since='2026-07-03T04:00:00Z' \
  --until='2026-07-03T04:30:00Z'
```

### 13.3 Incident timeline method

When handling production incidents, create a timeline:

```text
09:01 - Alert fired: NodeNotReady
09:02 - Pod evictions started
09:03 - API latency increased
09:05 - Node recovered
```

Then query narrow windows:

```bash
oc adm node-logs <node> -u kubelet \
  --since='2026-07-03T03:25:00Z' \
  --until='2026-07-03T03:40:00Z'
```

Remember time zones. OpenShift components, Prometheus, and journald outputs may not all be viewed in your local time zone. Convert carefully.

## 14. Filtering logs with grep

Use `-g` to reduce noise:

```bash
oc adm node-logs <node-name> -u kubelet --since=1h -g 'error|failed|timeout'
```

Case-insensitive:

```bash
oc adm node-logs <node-name> -u kubelet --since=1h \
  -g 'error|failed|timeout' \
  --case-sensitive=false
```

Useful regex patterns:

```bash
# General failures
-g 'error|failed|failure|timeout|refused|denied|panic|fatal'

# Pod sandbox and runtime
-g 'sandbox|CreatePodSandbox|RunPodSandbox|StopPodSandbox|runtime|crio'

# Image pull
-g 'pull|image|registry|unauthorized|x509|certificate|manifest|timeout'

# Storage and volume
-g 'mount|volume|pvc|csi|attach|detach|filesystem|permission denied'

# Network and CNI
-g 'cni|network|ovn|dns|resolve|route|iptables|nft|mtu'

# Eviction and pressure
-g 'evict|pressure|threshold|memory|disk|pid|ephemeral'

# Certificate and auth
-g 'certificate|x509|expired|token|unauthorized|forbidden|tls'
```

Senior warning: grep can hide context. When you find a matching line, re-run with a broader time window and without grep around the timestamp.

## 15. Querying previous boot logs

Node reboot analysis is common during updates or failures. Use `--boot`:

```bash
# Current boot
oc adm node-logs <node-name> -u kubelet --boot=0 --tail=200

# Previous boot
oc adm node-logs <node-name> -u kubelet --boot=-1 --tail=500
```

Use cases:

- Node rebooted unexpectedly
- MachineConfigPool update caused reboot
- Kubelet failed before reboot
- Kernel/panic-like symptoms suspected
- CRI-O restarted repeatedly before node became unavailable

Also check node events and MachineConfigPool:

```bash
oc get nodes
oc describe node <node-name>
oc get mcp
oc describe mcp worker
```

## 16. Output formats

Common output formats:

```bash
# Default readable output
oc adm node-logs <node> -u kubelet --tail=50

# Short output
oc adm node-logs <node> -u kubelet -o short --tail=50

# Message only, useful for grep/scripting
oc adm node-logs <node> -u kubelet -o cat --tail=50

# JSON output, useful for parsing
oc adm node-logs <node> -u kubelet -o json --tail=50

# Unix timestamp style
oc adm node-logs <node> -u kubelet -o short-unix --tail=50
```

For automation, JSON is useful:

```bash
oc adm node-logs <node> -u kubelet -o json --since=1h > kubelet-node.json
```

For quick human triage, default or short output is usually easier.

## 17. Reading files under `/var/log` with `--path`

`oc adm node-logs` can also inspect host files under `/var/log`.

List available log paths:

```bash
oc adm node-logs --role=master --path=/
```

List a subdirectory:

```bash
oc adm node-logs --role=master --path=openshift-apiserver
```

Read a specific file:

```bash
oc adm node-logs --role=master --path=openshift-apiserver/audit.log
```

Common examples:

```bash
# OpenShift API server audit log on control plane nodes
oc adm node-logs --role=master --path=openshift-apiserver/audit.log

# See available files under /var/log on worker nodes
oc adm node-logs --role=worker --path=/

# Query path from a specific node
oc adm node-logs <node-name> --path=openshift-apiserver/audit.log
```

Important distinction:

```bash
-u kubelet
```

queries node service logs from journald/systemd, while:

```bash
--path=openshift-apiserver/audit.log
```

reads a file under `/var/log`.

## 18. Control plane static pod troubleshooting

OpenShift control plane components run as static pods on control plane nodes. Kubelet manages these pods directly from manifests on the host.

Control plane symptoms:

```bash
oc get co
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-controller-manager -o wide
oc get pods -n openshift-kube-scheduler -o wide
```

If a static pod is crashing on one control plane node:

```bash
NODE=<control-plane-node>
oc adm node-logs $NODE -u kubelet --since=1h \
  -g 'kube-apiserver|etcd|static|mirror|failed|error'
```

Then correlate with pod logs:

```bash
oc logs -n openshift-kube-apiserver <apiserver-pod> -c kube-apiserver --previous
oc logs -n openshift-etcd <etcd-pod> -c etcd --previous
```

Senior note:

- `oc logs` shows container logs.
- `oc adm node-logs -u kubelet` shows kubelet’s view of static pod lifecycle.
- Audit logs are usually file logs under `/var/log/openshift-apiserver/audit.log`.

## 19. Node `NotReady` troubleshooting workflow

### 19.1 Identify affected node

```bash
oc get nodes
oc describe node <node-name>
```

Look for:

```text
Ready=False
Ready=Unknown
NetworkUnavailable=True
MemoryPressure=True
DiskPressure=True
PIDPressure=True
Kubelet stopped posting node status
```

### 19.2 Query kubelet logs

```bash
oc adm node-logs <node-name> -u kubelet --since=2h --tail=1000
```

Filter:

```bash
oc adm node-logs <node-name> -u kubelet --since=2h \
  -g 'NotReady|node status|PLEG|runtime|timeout|certificate|connection refused|eviction|pressure'
```

### 19.3 Query CRI-O logs

```bash
oc adm node-logs <node-name> -u crio --since=2h --tail=1000
```

### 19.4 Check node resource usage

```bash
oc adm top node <node-name>
oc describe node <node-name> | egrep -A5 'Conditions|Allocated resources|Events'
```

### 19.5 Check machine config state

```bash
oc get mcp
oc describe mcp worker
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node-name> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
```

### 19.6 If API path fails

If the API cannot reach the node log endpoint, use `oc debug` if possible:

```bash
oc debug node/<node-name>
chroot /host
journalctl -b -u kubelet.service --no-pager
journalctl -b -u crio.service --no-pager
```

If API itself is unavailable, SSH is a last resort:

```bash
ssh core@<node> sudo journalctl -b -u kubelet.service --no-pager
ssh core@<node> sudo journalctl -b -u crio.service --no-pager
```

## 20. Pod stuck in `ContainerCreating`

### 20.1 Start from pod status

```bash
oc get pod <pod> -n <ns> -o wide
oc describe pod <pod> -n <ns>
```

Look for events:

```text
FailedMount
FailedCreatePodSandBox
FailedPullImage
Failed to setup network
MountVolume.SetUp failed
context deadline exceeded
```

### 20.2 Get node name

```bash
NODE=$(oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeName}')
echo $NODE
```

### 20.3 Query kubelet and CRI-O

```bash
oc adm node-logs $NODE -u kubelet --since=1h \
  -g '<pod>|mount|sandbox|network|failed|error|timeout'

oc adm node-logs $NODE -u crio --since=1h \
  -g '<pod>|sandbox|runtime|failed|error|timeout'
```

### 20.4 Decision tree

| Event reason | Next node logs to query | Likely area |
|---|---|---|
| `FailedMount` | Kubelet | CSI, PVC, NFS, permissions, mount propagation |
| `FailedCreatePodSandBox` | Kubelet + CRI-O | CNI, runtime, SELinux, network namespace |
| `ImagePullBackOff` | Kubelet + CRI-O | Registry, pull secret, DNS, certificates |
| `CreateContainerError` | Kubelet + CRI-O | Entrypoint, security context, runtime config |
| `Evicted` | Kubelet | Memory, disk, PID pressure |
| `NodeLost` | Kubelet + node status | Node outage, network partition, reboot |

## 21. Image pull troubleshooting

Image pull problems can appear in pod events, kubelet logs, and CRI-O logs.

### 21.1 Pod event view

```bash
oc describe pod <pod> -n <ns> | sed -n '/Events:/,$p'
```

### 21.2 Node log view

```bash
NODE=$(oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeName}')

oc adm node-logs $NODE -u kubelet --since=1h \
  -g 'pull|image|registry|unauthorized|forbidden|x509|certificate|manifest|timeout|resolve'

oc adm node-logs $NODE -u crio --since=1h \
  -g 'pull|image|registry|unauthorized|forbidden|x509|certificate|manifest|timeout|resolve'
```

### 21.3 Common root causes

| Log clue | Meaning | Fix direction |
|---|---|---|
| `unauthorized` | Pull secret/auth issue | Check imagePullSecret, service account, registry auth |
| `x509: certificate signed by unknown authority` | Registry CA not trusted | Add trusted CA to cluster image config |
| `manifest unknown` | Image/tag missing | Check image name and tag |
| `context deadline exceeded` | Network or registry timeout | Check DNS, proxy, firewall, registry health |
| `no such host` | DNS resolution problem | Check node DNS, NetworkManager, proxy, DNS operator |

## 22. Volume mount and PVC troubleshooting

When a pod is stuck because of storage, kubelet logs are critical.

### 22.1 Start with PVC and pod

```bash
oc get pvc -n <ns>

oc describe pod <pod> -n <ns>
```

### 22.2 Query kubelet for mount errors

```bash
NODE=$(oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeName}')
```


### 22.4 Common root causes

| Kubelet message area | Possible cause |
|---|---|
| `MountVolume.SetUp failed` | Bad path, permission, secret, configmap, CSI mount error |
| `timeout waiting for volume attach` | CSI attach controller/backend issue |
| `permission denied` | NFS export, SELinux, fsGroup, SCC/security context issue |
| `stale file handle` | NFS backend/export issue |
| `multi-attach error` | RWO volume attached to another node |

## 28. OpenShift Logging stack vs node service logs

OpenShift Logging usually collects and stores logs such as:

- Application logs
- Infrastructure logs
- Audit logs, depending on configuration

However, not every node-level journal entry is necessarily available in Loki or another log store. `oc adm node-logs` remains important because it gives direct node service visibility.

### 28.1 When to use Loki/OpenShift Logging

Use Loki/OpenShift Logging when:

- You need historical, aggregated logs
- You need namespace/app filtering
- You need log correlation across workloads
- You need developer-facing query access
- You need dashboards or long-term retention

### 28.2 When to use `oc adm node-logs`

Use `oc adm node-logs` when:

- You need node-level kubelet/CRI-O/systemd logs
- The issue is tied to one node
- The issue happened recently
- You need precise boot/unit filtering
- The logging collector may itself be broken
- Pods are not starting, so app logs are not available

### 28.3 When to use `must-gather`

Use `must-gather` when:

- You need a complete support bundle
- The problem spans many components
- You need to preserve evidence before remediation
- You are opening a Red Hat support case
- The issue includes operators, CRs, events, service logs, and cluster state

For logging-specific support data:

```bash
oc adm must-gather --image=$(oc -n openshift-logging get deployment.apps/cluster-logging-operator \
  -o jsonpath='{.spec.template.spec.containers[?(@.name == "cluster-logging-operator")].image}')
```

## 32. Troubleshooting command failures

### 32.1 Forbidden

Error:

```text
Error from server (Forbidden): nodes/log is forbidden
```

Check:

```bash
oc auth can-i get nodes/log
oc adm policy who-can --all-namespaces get nodes/log
```

Fix direction:

- Use a cluster-admin account.
- Grant only the minimum required access in production.
- Remember node logs may contain sensitive information.

### 32.2 API unavailable

Symptoms:

```text
Unable to connect to the server
EOF
connection refused
TLS handshake timeout
```

Check:

```bash
oc whoami --show-server
oc get --raw='/readyz?verbose'
oc get nodes
```

Fallback:

```bash
ssh core@<node> sudo journalctl -b -u kubelet.service
```

### 32.3 No logs returned

Possible causes:

- Wrong unit name
- Wrong node role selector
- Time filter too narrow
- Logs rotated or not present for that boot
- Node unreachable
- Unit not running on that node role

Checks:

```bash
oc get nodes --show-labels
oc adm node-logs <node> --path=/
oc debug node/<node> -- chroot /host systemctl list-units --type=service | grep -Ei 'kubelet|crio'
```

### 32.4 Too much output

Use:

```bash
--tail=200
--since=30m
-g 'error|failed|timeout'
```

Example:

```bash
oc adm node-logs --role=worker -u kubelet --since=30m --tail=500 \
  -g 'error|failed|timeout|evict|pressure'
```

### 32.5 Mixed output from multiple nodes

When querying multiple nodes, output may be interleaved or prefixed. For clean analysis, save per node:

```bash
mkdir -p node-logs
for n in $(oc get nodes -o name | cut -d/ -f2); do
  oc adm node-logs "$n" -u kubelet --since=2h > "node-logs/${n}-kubelet.log"
done
```

Compressed collection:

```bash
mkdir -p node-logs
for n in $(oc get nodes -o name | cut -d/ -f2); do
  oc adm node-logs "$n" -u kubelet --since=2h | gzip > "node-logs/${n}-kubelet.log.gz"
done
```

## 33. Practical senior-level playbooks

### 33.1 Playbook: pod cannot start

```bash
NS=<namespace>
POD=<pod>

oc get pod $POD -n $NS -o wide
oc describe pod $POD -n $NS

NODE=$(oc get pod $POD -n $NS -o jsonpath='{.spec.nodeName}')
echo "Node: $NODE"

oc adm node-logs $NODE -u kubelet --since=1h \
  -g "$POD|failed|error|mount|sandbox|image|network|timeout"

oc adm node-logs $NODE -u crio --since=1h \
  -g "$POD|failed|error|sandbox|image|runtime|timeout"
```

Interpretation:

- If pod events show `FailedMount`, focus on kubelet and CSI.
- If events show `FailedCreatePodSandBox`, focus on kubelet, CRI-O, and CNI.
- If events show image pull, focus on kubelet, CRI-O, registry, DNS, certificates, and pull secrets.

### 33.2 Playbook: one node is NotReady

```bash
NODE=<node>

oc get node $NODE
oc describe node $NODE

oc adm node-logs $NODE -u kubelet --since=2h --tail=1000
oc adm node-logs $NODE -u crio --since=2h --tail=1000
oc adm node-logs $NODE -u NetworkManager --since=2h --tail=500
```

Filter version:

```bash
oc adm node-logs $NODE -u kubelet --since=2h \
  -g 'NotReady|node status|PLEG|runtime|timeout|certificate|connection|pressure|evict'
```

### 33.3 Playbook: worker pool degraded after update

```bash
oc get mcp
oc describe mcp worker
oc get nodes

for n in $(oc get nodes -l node-role.kubernetes.io/worker= -o name | cut -d/ -f2); do
  echo "===== $n ====="
  oc adm node-logs $n -u kubelet --since=4h \
    -g 'reboot|drain|cordon|ready|not ready|machineconfig|error|failed'
```

### 33.4 Playbook: image pull fails only on some nodes

```bash
NS=<namespace>
APP_LABEL=<label-selector>

oc get pods -n $NS -l $APP_LABEL -o wide

for n in $(oc get pods -n $NS -l $APP_LABEL -o jsonpath='{range .items[*]}{.spec.nodeName}{"\n"}{end}' | sort -u); do

  oc adm node-logs $n -u kubelet --since=1h \
```

## 37. Security and compliance considerations

Node logs can expose sensitive data. Treat them like privileged operational data.

Possible sensitive content:

- Internal hostnames
- Node IPs
- Registry names
- Image paths
- Service account token errors
- Certificate paths and identities
- Usernames
- API request details
- Audit events
- Infrastructure topology
- Failure messages containing secrets or URLs

Best practices:

- Do not share raw logs publicly.
- Redact tokens, passwords, internal FQDNs, and IPs before external sharing.
- Use support cases for vendor sharing.
- Restrict `nodes/log` permission.
- Store diagnostic bundles in controlled locations.
- Rotate or delete temporary log archives after incident closure.


## 40. Interview-level explanation

A strong answer in an interview:

> In OpenShift, node service logs are queried using `oc adm node-logs`. This is mainly used to inspect node-level journald/systemd logs such as kubelet and CRI-O logs. It is different from `oc logs`, which reads container stdout/stderr. I use `oc adm node-logs` when pods are stuck in `ContainerCreating`, nodes become `NotReady`, image pulls fail, volumes do not mount, or CRI-O/CNI/runtime issues are suspected. I first identify the affected pod and node with `oc get pod -o wide`, inspect events using `oc describe`, then query kubelet and CRI-O logs on that node with a narrow `--since` window. For control plane issues, I query `--role=master -u kubelet` because kubelet manages static pods. If API access is unavailable, I use `oc debug node` or SSH as a last resort and run `journalctl` directly. For support cases, I collect `must-gather` as well.

## 42. Common mistakes

### Mistake 1: Using `oc logs` for node service issues

Wrong:

```bash
oc logs node/<node-name>
```

Correct:

```bash
oc adm node-logs <node-name> -u kubelet
```

### Mistake 2: Querying all worker logs without filters

Wrong:

```bash
oc adm node-logs --role=worker -u kubelet
```

Better:

```bash
oc adm node-logs <node-name> -u kubelet --since=30m --tail=500
```

### Mistake 3: Forgetting CRI-O

Kubelet may only say that runtime failed. CRI-O often contains lower-level detail.

```bash
oc adm node-logs <node-name> -u crio --since=1h
```

### Mistake 4: Ignoring timestamps

Always align:

- Pod event timestamp
- Kubelet log timestamp
- CRI-O log timestamp
- Alert timestamp
- Node reboot timestamp

### Mistake 5: SSH first

OpenShift Day-2 operation should normally start with `oc` tools. Use SSH when the API or kubelet path is broken.

## 43. Production-ready log collection script

```bash
#!/usr/bin/env bash
set -euo pipefail

SINCE="${SINCE:-2h}"
OUTDIR="${OUTDIR:-node-service-logs-$(date +%Y%m%d-%H%M%S)}"
UNITS=(kubelet crio NetworkManager chronyd)

mkdir -p "$OUTDIR"

oc get nodes -o wide > "$OUTDIR/nodes.txt"
oc get co > "$OUTDIR/clusteroperators.txt"
oc get mcp > "$OUTDIR/machineconfigpools.txt" || true
oc get events -A --sort-by=.lastTimestamp > "$OUTDIR/events.txt" || true

for node in $(oc get nodes -o name | cut -d/ -f2); do
  mkdir -p "$OUTDIR/$node"
  echo "Collecting logs from $node"
  oc describe node "$node" > "$OUTDIR/$node/describe-node.txt" || true

  for unit in "${UNITS[@]}"; do
    echo "  unit=$unit"
    oc adm node-logs "$node" -u "$unit" --since="$SINCE" \
      > "$OUTDIR/$node/${unit}.log" 2> "$OUTDIR/$node/${unit}.err" || true
    gzip -f "$OUTDIR/$node/${unit}.log" || true
  done

done

tar czf "${OUTDIR}.tar.gz" "$OUTDIR"
echo "Created ${OUTDIR}.tar.gz"
```

Run:

```bash
chmod +x collect-node-service-logs.sh
SINCE=1h ./collect-node-service-logs.sh
```

Use with care because node logs may contain sensitive data.

## 45. Best-practice troubleshooting flow

Use this as your mental model:

```text
1. Confirm symptom
   oc get co
   oc get nodes
   oc get pods -A

2. Scope the blast radius
   One pod? One namespace? One node? One zone? Whole cluster?

3. Identify affected node
   oc get pod -o wide
   oc describe node

4. Check Kubernetes events
   oc describe pod
   oc get events --sort-by=.lastTimestamp

5. Query node service logs
   oc adm node-logs <node> -u kubelet --since=<window>
   oc adm node-logs <node> -u crio --since=<window>

6. Query component/operator logs
   oc logs -n <operator-namespace> <pod>

7. Use debug node if needed
   oc debug node/<node>
   chroot /host
   journalctl -u kubelet

8. Collect must-gather for support
   oc adm must-gather

9. Remediate using supported OpenShift methods
   Avoid unmanaged host changes unless break-glass is required.
```

## 47. Key takeaways

- `oc adm node-logs` is the main OpenShift command for node service logs.
- It is different from `oc logs`; it targets node-level systemd/journald and `/var/log` sources.
- Kubelet logs are the first place to inspect pod lifecycle, node readiness, eviction, mount, probe, and static pod management issues.
- CRI-O logs are essential for runtime, image, sandbox, SELinux, and container creation errors.
- Use `--since`, `--until`, `--tail`, and `-g` to reduce noise.
- For control plane symptoms, query `--role=master -u kubelet`.
- For workload runtime symptoms, query the exact node from `oc get pod -o wide`.
- Use `oc debug node` for interactive node troubleshooting.
- Use SSH only when API-based methods are not functional.
- Use `must-gather` for broad, support-grade evidence collection.
- Treat node logs as sensitive operational data.
