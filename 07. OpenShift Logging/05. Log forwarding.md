## 1. What is Log Forwarding?

**Log forwarding** in OpenShift Logging is the process of collecting logs from OpenShift cluster nodes, applications, platform components, audit sources, or supported receiver inputs, then routing those logs to one or more destinations.

In practical terms, log forwarding answers four production questions:

1. **What logs should be collected?**
   - Application logs?
   - Infrastructure logs?
   - Audit logs?
   - Only selected namespaces?
   - Only selected pod labels?

2. **What should happen before logs leave the cluster?**
   - Drop noisy logs.
   - Prune sensitive fields.
   - Parse JSON payloads.
   - Detect multiline exceptions.
   - Apply labels.
   - Rate-limit high-volume sources.

3. **Where should logs go?**
   - In-cluster LokiStack.
   - External Loki.
   - Splunk.
   - Kafka.
   - Syslog server.
   - HTTP endpoint.
   - Amazon S3.
   - CloudWatch.
   - Google Cloud Logging.
   - Azure Monitor.
   - OTLP / OpenTelemetry Collector.

4. **Who is allowed to collect those logs?**
   - OpenShift Logging uses RBAC-protected service accounts and cluster roles. The collector cannot collect everything automatically unless you explicitly grant permissions.

In OpenShift Logging 6.x, the main object used to configure log forwarding is:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
```

The `ClusterLogForwarder` CR tells the OpenShift Logging Operator how to deploy and configure the log collector, normally Vector, and how to route logs through inputs, filters, outputs, and pipelines.

## 2. Why Log Forwarding Matters in Enterprise OpenShift

In small labs, logs are often viewed with:

```bash
oc logs pod/<pod-name>
```

In enterprise OpenShift, that is not enough. A production cluster may have hundreds or thousands of pods, many namespaces, audit requirements, security policies, and multiple teams. Logs must be collected, filtered, routed, stored, secured, and retained properly.

### Enterprise reasons for log forwarding

| Requirement | Why log forwarding helps |
|---|---|
| Application troubleshooting | Developers need logs from their own namespaces without cluster-admin access. |
| SRE operations | Platform teams need node, operator, control plane, ingress, registry, monitoring, and network component logs. |
| Security investigations | Audit logs must be collected, protected, and often exported to a SIEM. |
| Compliance | Audit and security logs may require long-term immutable retention. |
| Cost control | Not every debug or health-check log should go to expensive storage. |
| Multi-tool environments | Different teams may use Loki, Splunk, Kafka, S3, CloudWatch, or external observability platforms. |
| Data sovereignty | Sensitive fields may need pruning before logs leave the cluster. |
| Separation of duties | Application, infrastructure, and audit logs often have different access and retention rules. |

A mature OpenShift administrator does not think of log forwarding only as “send logs somewhere.” The production mindset is:

> Collect only what is required, enrich or filter it safely, route it to the right destination, secure it in transit, monitor delivery health, and design for failure.

## 3. OpenShift Logging Architecture Refresher

A modern OpenShift Logging stack commonly includes:

```text
+--------------------------------------------------------------+
|                 OpenShift Container Platform                 |
|                                                              |
|  +-------------------+      +------------------------------+ |
|  | Application Pods  |      | OpenShift Infra Components   | |
|  | stdout/stderr     |      | kubelet, CRI-O, router, etc. | |
|  +---------+---------+      +---------------+--------------+ |
|            |                                |                |
|            v                                v                |
|  +--------------------------------------------------------+   |
|  | Node log files / journald / audit log sources          |   |
|  +--------------------------------------------------------+   |
|                            |                                 |
|                            v                                 |
|  +--------------------------------------------------------+   |
|  | Vector collector DaemonSet                             |   |
|  | - Runs on nodes                                        |   |
|  | - Reads container, infra, audit, receiver logs          |   |
|  | - Applies filters                                      |   |
|  | - Sends to configured outputs                          |   |
|  +----------------------+---------------------------------+   |
|                         |                                     |
|                         v                                     |
|  +--------------------------------------------------------+   |
|  | Outputs                                                |   |
|  | LokiStack / Splunk / Kafka / Syslog / S3 / HTTP / OTLP |   |
|  +--------------------------------------------------------+   |
|                                                              |
|  Managed by: Red Hat OpenShift Logging Operator              |
+--------------------------------------------------------------+
```

### Key point

The collector is not configured manually like a normal Vector deployment. You declare your intended routing in `ClusterLogForwarder`, and the Operator reconciles the collector configuration.

## 4. Log Forwarding Data Flow

The forwarding flow is:

```text
Log Source
  |
  v
Input
  |
  v
Filter(s)
  |
  v
Pipeline
  |
  v
Output(s)
```

More realistically:

```text
Application containers       Infrastructure components       Audit sources
        |                              |                         |
        +--------------+---------------+-------------------------+
                       |
                       v
             Vector collector on each node
                       |
                       v
        ClusterLogForwarder routing configuration
                       |
       +---------------+-------------------+----------------+
       |                                   |                |
       v                                   v                v
    LokiStack                            Splunk            S3
 short-term ops                         SIEM/ops      compliance archive
```

### Inputs

Inputs decide **which logs enter** the pipeline.

Examples:

```yaml
inputRefs:
- application
- infrastructure
- audit
```

Or custom input:

```yaml
inputs:
- name: payment-prod
  type: application
  application:
    includes:
    - namespace: payments-prod
```

### Filters

Filters decide **what transformation or reduction happens**.

Examples:

- Drop noisy logs.
- Remove annotations.
- Parse JSON.
- Add labels.
- Join multiline stack traces.

### Outputs

Outputs decide **where logs are sent**.

Examples:

- `lokiStack`
- `loki`
- `splunk`
- `kafka`
- `syslog`
- `http`
- `s3`
- `cloudwatch`
- `googleCloudLogging`
- `otlp`

### Pipelines

Pipelines bind inputs, filters, and outputs:

```yaml
pipelines:
- name: app-logs-to-loki
  inputRefs:
  - application
  filterRefs:
  - drop-debug
  outputRefs:
  - default-lokistack
```

## 5. Important Components

### 5.1 Red Hat OpenShift Logging Operator

The Logging Operator manages log collection and forwarding. It watches `ClusterLogForwarder` custom resources and creates or updates the collector workload.

Main responsibilities:

- Deploy collector pods.
- Generate collector configuration.
- Validate `ClusterLogForwarder` spec.
- Enforce supported configuration.
- Manage collector lifecycle.
- Report status conditions.

### 5.2 Vector collector

Vector is the log collector used by OpenShift Logging. It typically runs as a DaemonSet so it can collect logs from every node.

Vector responsibilities:

- Tail container log files.
- Read infrastructure logs.
- Read audit logs when permitted.
- Receive supported HTTP/syslog receiver logs.
- Parse and transform records.
- Forward logs to outputs.
- Retry delivery when supported.
- Apply rate limits and tuning.

### 5.3 ClusterLogForwarder

The `ClusterLogForwarder` CR is the central configuration object for log forwarding.

It defines:

- Collector service account.
- Inputs.
- Filters.
- Outputs.
- Pipelines.
- Collector resources.
- Tuning.
- Annotations such as collector log level.

### 5.4 LokiStack

`LokiStack` is the Red Hat managed Loki-based log store. It is managed by the Loki Operator and commonly used for in-cluster log storage and OpenShift console log viewing.

Important distinction:

| Output type | Meaning |
|---|---|
| `lokiStack` | Red Hat managed LokiStack with OpenShift tenancy/auth integration. |
| `loki` | External Loki endpoint outside the Red Hat managed LokiStack integration. |

### 5.5 Cluster Observability Operator / Console plugin

Modern OpenShift observability can expose logs through the console, especially when using LokiStack and the log observability UI plugin.

## 6. ClusterLogForwarder Overview

A simple `ClusterLogForwarder` looks like this:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: default-logstore
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

This means:

- Use the `collector` service account.
- Send application and infrastructure logs to LokiStack.
- Authenticate to LokiStack using the service account token.
- Trust the LokiStack gateway CA bundle.
- Do not collect audit logs unless audit permission and audit input are configured.

## 7. API Version and Model Changes

### 7.1 Current model

Current OpenShift Logging 6.x examples use:

```yaml
apiVersion: observability.openshift.io/v1

```

### 7.2 Older model

Older OpenShift Logging releases used examples like:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
```

and often used a singleton CR named `instance` in the `openshift-logging` namespace.

### 7.3 Practical admin advice

On real clusters, always confirm the installed CRD:

```bash
oc api-resources | grep -i clusterlogforwarder
oc explain clusterlogforwarder
oc explain clusterlogforwarder.spec
```

Check the actual API group:

```bash
oc get crd clusterlogforwarders.observability.openshift.io
oc get crd clusterlogforwarders.logging.openshift.io
```

If you copy YAML from the wrong version, admission validation may fail.

## 8. Log Types: Application, Infrastructure, Audit, Receiver

OpenShift Logging divides logs into major types.

### 8.1 Application logs

Application logs are container logs from user workloads.

Examples:

- Logs written to stdout/stderr by app containers.
- Logs from user-created namespaces.
- Java, Node.js, Python, Go, PHP, Ruby application logs.

Reserved input reference:

```yaml
inputRefs:
- application
```

Application logs normally exclude OpenShift infrastructure namespaces.

### 8.2 Infrastructure logs

Infrastructure logs come from platform and node components.

Examples:

- Containers in `openshift-*`, `kube-*`, and selected platform namespaces.
- Node journald logs.
- Router, registry, monitoring, operator logs.
- CRI-O and kubelet-related logs.

Reserved input reference:

```yaml
inputRefs:
- infrastructure
```

### 8.3 Audit logs

Audit logs contain security-relevant events.

Examples:

- Kubernetes API server audit logs.
- OpenShift API server audit logs.
- OAuth/audit-related events.
- Node auditd logs.
- OVN audit logs.

Reserved input reference:

```yaml
inputRefs:
- audit
```

Audit logs are sensitive. Do not casually send them to developer-accessible tools.

### 8.4 Receiver logs

Receiver inputs allow the collector to listen for logs over supported protocols.

Examples:

- HTTP receiver for supported audit log sources.
- Syslog receiver for supported infrastructure/journal-style logs.

Example skeleton:

```yaml
inputs:
- name: syslog-receiver
  type: receiver
  receiver:
    type: syslog
    port: 10514
```

Important notes:

- Receiver support is limited to supported use cases.
- Ports must be between `1024` and `65535`.
- NetworkPolicy, TLS, and service exposure must be designed carefully.

## 9. Collector Identity and RBAC

OpenShift Logging does not allow a collector to read all logs automatically. You must create a service account and bind the correct cluster roles.

### 9.1 Create collector service account

```bash
oc create sa collector -n openshift-logging
```

### 9.2 Grant application log collection permission

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector
```

### 9.3 Grant infrastructure log collection permission

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

### 9.4 Grant audit log collection permission

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### 9.5 Verify bindings

```bash
oc get clusterrolebinding | grep collector
oc adm policy who-can collect applicationlogs
```

The exact `who-can` command can vary by resource and cluster version, so the most reliable method is checking the `ClusterLogForwarder` status conditions after applying the CR.

### 9.6 Very important behavior

If your `ClusterLogForwarder` references a log type that the service account is not authorized to collect, the Operator can remove the entire collector DaemonSet as a protective failure behavior. That means all collection can stop, not only the unauthorized log type.

Production rule:

> Grant RBAC first, then add the log type to `inputRefs`.

Bad order:

```text
Add audit to CLF -> no collect-audit-logs binding -> collector removed -> logging outage
```

Good order:

```text
Create service account -> bind collect-audit-logs -> add audit input -> verify status
```

## 10. ClusterLogForwarder Structure

A full `ClusterLogForwarder` has these major sections:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
  annotations:
    observability.openshift.io/log-level: info
spec:
  serviceAccount:
    name: collector

  collector:
    resources:
      requests:
        cpu: 100m
        memory: 256Mi
      limits:
        cpu: 500m
        memory: 512Mi

  inputs:
  - name: selected-apps
    type: application
    application:
      includes:
      - namespace: app-prod

  filters:
  - name: drop-debug
    type: drop
    drop:
    - test:
      - field: .level
        matches: debug

  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt

  pipelines:
  - name: selected-apps-to-loki
    inputRefs:
    - selected-apps
    filterRefs:
    - drop-debug
    outputRefs:
    - default-lokistack
```

### Section summary

| Section | Purpose |
|---|---|
| `serviceAccount` | Identity used by collector pods. |
| `collector` | Collector resource requests/limits and runtime settings. |
| `inputs` | Custom log selections or receivers. |
| `filters` | Drop, prune, parse, label, multiline, audit policy filters. |
| `outputs` | Destinations. |
| `pipelines` | Routing logic connecting inputs, filters, and outputs. |

## 11. Inputs in Detail

Inputs select log records before pipeline filtering.

### 11.1 Built-in input references

You can reference these directly in pipelines:

```yaml
inputRefs:
- application
- infrastructure
- audit
```

These are reserved names. You do not need to define them under `spec.inputs` unless you need custom selection.

### 11.2 Custom application input by namespace

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  inputs:
  - name: payment-prod-logs
    type: application
    application:
      includes:
      - namespace: payments-prod
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: payment-prod-to-loki
    inputRefs:
    - payment-prod-logs
    outputRefs:
    - default-lokistack
```

### 11.3 Include and exclude namespace/container

```yaml
inputs:
- name: app-selected
  type: application
  application:
    includes:
    - namespace: app-prod
      container: "api"
    excludes:
    - namespace: app-prod
      container: "sidecar-debug*"
```

Important:

- `excludes` takes precedence over `includes`.
- Use input filtering for namespace/container selection when possible.
- Do not collect everything and drop later if the selection can be done at input level.

### 11.4 Select by pod labels

```yaml
inputs:
- name: frontend-prod
  type: application
  application:
    selector:
      matchLabels:
        app: frontend
        env: prod
```

With expressions:

```yaml
inputs:
- name: qa-or-prod
  type: application
  application:
    selector:
      matchExpressions:
      - key: env
        operator: In
        values:
        - prod
        - qa
      - key: temporary
        operator: DoesNotExist
        values: []
```

Valid operators:

- `In`
- `NotIn`
- `Exists`
- `DoesNotExist`

### 11.5 Infrastructure input source selection

Infrastructure logs can include container and node sources.

Example:

```yaml
inputs:
- name: infra-node-only
  type: infrastructure
  infrastructure:
    sources:
    - node
```

Example use case:

- Send node journal logs to the platform SRE tool.
- Send infrastructure container logs to LokiStack.
- Keep them separate for troubleshooting.

### 11.6 Audit input source selection

Audit logs can include multiple sources such as API server, OpenShift API, auditd, and OVN.

Example:

```yaml
inputs:
- name: api-audit-only
  type: audit
  audit:
    sources:
    - kubeAPI
    - openshiftAPI
```

Use this when security wants only API audit logs in one archive and network/auditd logs elsewhere.

### 11.7 Receiver input example: syslog

```yaml
inputs:
- name: syslog-receiver
  type: receiver
  receiver:
    type: syslog
    port: 10514
```

The Operator creates a service for the receiver. Check it:

```bash
oc get svc -n openshift-logging
```

Expected pattern:

```text
<clusterlogforwarder-name>-<input-name>
```

## 12. Filters in Detail

Filters transform, enrich, parse, or remove records after input selection and before output delivery.

### 12.1 Supported filter types

Common filter types include:

| Filter | Purpose |
|---|---|
| `drop` | Drop whole records based on field tests. |
| `prune` | Remove or keep selected fields. |
| `parse` | Parse structured JSON from message payload. |
| `openshiftLabels` | Add OpenShift labels under the log record. |
| `detectMultilineException` | Combine stack traces into one record. |
| `kubeAPIAudit` | Apply Kubernetes audit policy-like filtering. |

### 12.2 Drop filter

Drop logs from a noisy namespace:

```yaml
filters:
- name: drop-marketplace
  type: drop
  drop:
  - test:
    - field: .kubernetes.namespace_name
      matches: openshift-marketplace
```

Reference it in a pipeline:

```yaml
pipelines:
- name: app-infra-to-loki
  inputRefs:
  - application
  - infrastructure
  filterRefs:
  - drop-marketplace
  outputRefs:
  - default-lokistack
```

### 12.3 Drop filter AND/OR logic

Inside one `test`, conditions behave like AND:

```yaml
filters:
- name: drop-debug-from-dev
  type: drop
  drop:
  - test:
    - field: .kubernetes.namespace_name
      matches: dev-.*
    - field: .level
      matches: debug
```

Meaning:

```text
Drop if namespace matches dev-* AND level matches debug.
```

Multiple `test` blocks behave like OR:

```yaml
filters:
- name: drop-multiple
  type: drop
  drop:
  - test:
    - field: .kubernetes.namespace_name
      matches: test-.*
  - test:
    - field: .message
      matches: "health check"
```

Meaning:

```text
Drop if namespace matches test-* OR message contains health check.
```

### 12.4 Prune filter

Remove large or sensitive fields:

```yaml
filters:
- name: remove-noisy-fields
  type: prune
  prune:
    in:
    - .kubernetes.annotations
    - .kubernetes.labels."pod-template-hash"
```

Keep only selected fields:

```yaml
filters:
- name: keep-minimum
  type: prune
  prune:
    notIn:
    - .message
    - .kubernetes.namespace_name
    - .kubernetes.pod_name
    - .kubernetes.container_name
    - .level
    - .log_type
    - .log_source
```

Use `notIn` carefully. If you remove fields that downstream systems require for labels or tenancy, queries and access control can break.

### 12.5 Parse filter

If an application writes JSON as text to stdout, use parse:

Application log line:

```json
{"level":"error","service":"payment","request_id":"abc123","msg":"payment failed"}
```

Filter:

```yaml
filters:
- name: parse-json
  type: parse
```

This allows downstream filters to operate on structured fields.

### 12.6 Multiline exception filter

Java/Python/Go stack traces often span multiple lines. Without multiline detection, each line becomes a separate log record.

```yaml
filters:
- name: multiline-errors
  type: detectMultilineException
```

Pipeline:

```yaml
pipelines:
- name: app-errors-to-loki
  inputRefs:
  - application
  filterRefs:
  - multiline-errors
  outputRefs:
  - default-lokistack
```

Supported languages include common stack trace formats such as Java, JavaScript, Ruby, Python, Go, PHP, and Dart.

Production warning:

- Multiline detection can increase CPU and memory usage.
- Use it only for workloads that need it.
- Test with real log volume before enabling cluster-wide.

### 12.7 kubeAPIAudit filter

The `kubeAPIAudit` filter reduces Kubernetes API audit volume and controls audit detail.

Example:

```yaml
filters:
- name: api-audit-policy
  type: kubeAPIAudit
  kubeAPIAudit:
    omitStages:
    - RequestReceived
    rules:
    - level: RequestResponse
      resources:
      - group: ""
        resources:
        - pods
    - level: Metadata
      resources:
      - group: ""
        resources:
        - secrets
        - configmaps
    - level: Metadata
```

Use audit filtering with security approval. Do not drop audit events blindly.

### 12.8 Recommended filter ordering

Best practice ordering:

```text
parse -> drop -> prune -> label -> output
```

However, if a drop filter does not need parsed fields, drop first:

```text
drop noisy namespace -> parse JSON -> prune sensitive fields -> output
```

Goal:

- Drop early to reduce processing.
- Parse before filtering on structured app fields.
- Prune before expensive external outputs.
- Add labels after final transformations.

## 13. Outputs in Detail

Outputs define destinations.

### 13.1 Common output types

| Output type | Destination |
|---|---|
| `lokiStack` | Red Hat managed in-cluster LokiStack. |
| `loki` | External Loki endpoint. |
| `splunk` | Splunk HTTP Event Collector. |
| `kafka` | Apache Kafka topic. |
| `syslog` | External syslog receiver over UDP/TCP/TLS. |
| `http` | Generic HTTP or HTTPS endpoint. |
| `s3` | Amazon S3 or compatible object storage. |
| `cloudwatch` | Amazon CloudWatch Logs. |
| `googleCloudLogging` | Google Cloud Logging. |
| `elasticsearch` | External Elasticsearch. |
| `otlp` | OpenTelemetry Protocol endpoint. |
| `azureMonitor` | Azure Monitor Logs; deprecated and planned for removal/obsolescence. |

### 13.2 Output naming

Use descriptive names:

```yaml
outputs:
- name: loki-short-term
- name: splunk-security
- name: s3-audit-archive
- name: kafka-platform-bus
```

Avoid names like:

```yaml
- name: output1
- name: test
- name: abc
```

Good output names make troubleshooting much easier.

### 13.3 Output independence

When one pipeline sends the same logs to multiple outputs, the collector duplicates the stream. If one output fails, other outputs can continue independently. However, persistent failure of one output can still consume resources, generate retries, and increase collector pressure.

## 14. Pipelines in Detail

Pipelines are the routing rules.

A pipeline includes:

```yaml
pipelines:
- name: <pipeline-name>
  inputRefs:
  - <input-name-or-built-in-log-type>
  filterRefs:
  - <filter-name>
  outputRefs:
  - <output-name>
```

### 14.1 Pipeline example: application to LokiStack

```yaml
pipelines:
- name: apps-to-loki
  inputRefs:
  - application
  outputRefs:
  - default-lokistack
```

### 14.2 Pipeline example: infrastructure to Kafka

```yaml
pipelines:
- name: infra-to-kafka
  inputRefs:
  - infrastructure
  outputRefs:
  - kafka-platform
```

### 14.3 Pipeline example: audit to S3 and Splunk

```yaml
pipelines:
- name: audit-to-archive-and-siem
  inputRefs:
  - audit
  filterRefs:
  - prune-sensitive-runtime-fields
  outputRefs:
  - s3-audit-archive
  - splunk-security
```

### 14.4 Important pipeline rule

If you do not define a pipeline for a log type, logs of that type are not collected/forwarded.

Example:

```yaml
pipelines:
- name: app-only
  inputRefs:
  - application
  outputRefs:
  - default-lokistack
```

This forwards only application logs. Infrastructure and audit logs are not forwarded.

## 15. Forwarding to LokiStack

`lokiStack` is the most common destination for OpenShift Logging when using the Red Hat managed in-cluster log store.

### 15.1 Prerequisites

- Loki Operator installed.
- `LokiStack` CR created, for example `logging-loki`.
- Red Hat OpenShift Logging Operator installed.
- Collector service account created.
- Required `ClusterRoleBinding` objects created.
- LokiStack gateway CA bundle available.

### 15.2 RBAC

```bash
oc create sa collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

Add audit only if needed:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### 15.3 Complete LokiStack forwarding example

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: app-and-infra-to-loki
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

Apply:

```bash
oc apply -f clf-lokistack.yaml
```

Verify:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
```

### 15.4 Why `tls.ca` is important

For LokiStack, the collector must trust the LokiStack gateway certificate. If the CA bundle is missing or wrong, the `ClusterLogForwarder` can appear `Ready`, but logs may not reach LokiStack.

Common error:

```text
certificate verify failed: self-signed certificate in certificate chain
```

Fix:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

### 15.5 LokiStack labels that must not be pruned

For LokiStack output, these Kubernetes fields are important stream labels and should not be pruned:

```text
.kubernetes.container_name
.kubernetes.namespace_name
.kubernetes.pod_name
```

If they are missing, LokiStack may set them to empty strings, which reduces query usefulness and can hurt stream organization.

## 20. Forwarding to HTTP / Webhook / Custom Receiver

HTTP output is useful for custom collectors, gateways, webhooks, and vendor ingestion endpoints.

### 20.1 HTTP JSON output

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: http-forwarder
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector
  outputs:
  - name: http-collector
    type: http
    http:
      url: https://logs-gateway.example.com/ingest
      method: POST
  pipelines:
  - name: apps-to-http
    inputRefs:
    - application
    outputRefs:
    - http-collector
```

### 20.2 HTTP NDJSON output

OpenShift Logging 6.5 supports HTTP output as newline-delimited JSON using `format: ndjson`.

```yaml
outputs:
- name: http-ndjson
  type: http
  http:
    url: https://logs-gateway.example.com/ingest
    method: POST
    format: ndjson
```

NDJSON can reduce receiver memory pressure because the receiver can process records line by line rather than waiting for a full JSON array.

### 20.3 HTTP production advice

- Prefer HTTPS.
- Use bearer token or basic auth if supported.
- Store credentials in Secrets.
- Use `format: ndjson` if the receiver supports it.
- Confirm retry behavior and idempotency on the receiver side.
- Rate-limit if the receiver has ingestion quotas.


## 27. Multi-Destination Log Routing

Enterprise OpenShift logging often requires different paths for different consumers.

### 27.1 Example architecture

```text
Application logs -> LokiStack for developers and SREs
Infrastructure logs -> LokiStack + Kafka platform bus
Audit logs -> S3 immutable archive + Splunk security
PCI app logs -> Splunk PCI index
Noisy debug logs -> dropped before external forwarding
```

### 27.2 Full multi-destination example

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: enterprise-forwarder
  namespace: openshift-logging
spec:
  serviceAccount:
    name: collector

  inputs:
  - name: pci-apps
    type: application
    application:
      selector:
        matchLabels:
          compliance: pci

  filters:
  - name: drop-debug
    type: drop
    drop:
    - test:
      - field: .level
        matches: debug
  - name: prune-annotations
    type: prune
    prune:
      in:
      - .kubernetes.annotations

  outputs:
  - name: loki-short-term
    type: lokiStack
    lokiStack:
      authentication:
        token:
          from: serviceAccount
      target:
        name: logging-loki
        namespace: openshift-logging
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt

  - name: splunk-security
    type: splunk
    splunk:
      url: https://splunk-sec.example.com:8088
      authentication:
        token:
          secretName: splunk-sec-token
          key: hecToken
      index: security

  - name: kafka-platform
    type: kafka
    kafka:
      brokers:
      - kafka.example.com:9092
      topic: openshift-platform-logs

  - name: s3-audit
    type: s3
    s3:
      bucket: openshift-audit-archive
      region: us-east-1
      keyPrefix: audit/

  pipelines:
  - name: normal-apps-to-loki
    inputRefs:
    - application
    filterRefs:
    - drop-debug
    - prune-annotations
    outputRefs:
    - loki-short-term

  - name: infra-to-loki-and-kafka
    inputRefs:
    - infrastructure
    filterRefs:
    - prune-annotations
    outputRefs:
    - loki-short-term
    - kafka-platform

  - name: pci-apps-to-security
    inputRefs:
    - pci-apps
    outputRefs:
    - splunk-security

  - name: audit-to-archive-and-security
    inputRefs:
    - audit
    outputRefs:
    - s3-audit
    - splunk-security
```

### 27.3 Design caution

The `pci-apps` input is a subset of `application`. If you also forward all `application` logs elsewhere, PCI logs may be duplicated. That might be intended, but you should design and document it.

## 28. Rate Limiting and Delivery Tuning

Rate limiting prevents a high-volume source or output from overwhelming the collector or destination.

### 28.1 Input rate limit per container

```yaml
inputs:
- name: high-volume-prod
  type: application
  application:
    includes:
    - namespace: production
    tuning:
      rateLimitPerContainer:
        maxRecordsPerSecond: 500
```

### 28.2 Output rate limit

```yaml
outputs:
- name: expensive-splunk
  type: splunk
  splunk:
    url: https://splunk.example.com:8088
    authentication:
      token:
        secretName: splunk-secret
        key: token
  rateLimit:
    maxRecordsPerSecond: 500
```

### 28.3 Important rate-limit behavior

When rate limits are exceeded, logs are dropped. Rate limiting is not queueing forever. It is a protection mechanism.

Monitor rate-limit metrics such as:

```text
observability_log_forwarder_output_rate_limited_total
```

### 28.4 Tuning message size

```yaml
inputs:
- name: application
  type: application
  application:
    tuning:
      container:
        maxMessageSize: 16Ki
        rateLimitPerContainer:
          maxRecordsPerSecond: 1000
```

If messages exceed `maxMessageSize`, they can be dropped. This is important for large stack traces or applications that write large JSON blobs.

### 28.5 Output tuning

Output tuning can include:

- Compression.
- Maximum write size.
- Retry duration.

Example:

```yaml
outputs:
- name: loki-short-term
  type: lokiStack
  lokiStack:
    authentication:
      token:
        from: serviceAccount
    target:
      name: logging-loki
      namespace: openshift-logging
  tuning:
    compression: gzip
    maxWrite: 3Mi
    minRetryDuration: 2
    maxRetryDuration: 300
```

Use only supported tuning fields for the output type on your OpenShift Logging version. Always confirm with:

```bash
oc explain clusterlogforwarder.spec.outputs.tuning
oc explain clusterlogforwarder.spec.outputs.<output_type>
```

## 30. NetworkPolicy and Egress Design

In restricted clusters, collector pods may not be able to reach external outputs unless NetworkPolicy allows egress.

### 30.1 Things to check

```bash
oc get networkpolicy -A
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc get svc -n openshift-logging
```

### 30.2 Test egress from a debug pod

Because collector pods may not have troubleshooting tools, use a temporary pod in the same namespace if allowed:

```bash
oc run net-test -n openshift-logging --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside:

```bash
curl -vk https://splunk.example.com:8088
curl -vk https://loki.example.com:3100/ready
```

If `nc` is unavailable:

```bash
bash -c 'echo > /dev/tcp/splunk.example.com/8088'
```

or install/debug with a toolbox image approved by your environment.

### 30.3 Egress design

Allow only required destinations:

| Destination | Typical port |
|---|---:|
| Splunk HEC | 8088 |
| External Loki | 3100 |
| Kafka | 9092 / 9093 |
| Syslog TLS | 6514 |
| Syslog TCP | 514 or custom |
| HTTPS HTTP output | 443 |
| S3/Cloud APIs | 443 |
| OTLP HTTP | 4318 |
| OTLP gRPC | 4317 |

### 30.4 Proxy environments

If your cluster requires egress through a proxy:

- Confirm cluster-wide proxy configuration.
- Confirm destination supports proxy usage.
- For external Loki, use `proxyURL` where supported.
- Ensure `NO_PROXY` does not accidentally bypass or block required routes.

## 31. Resource Sizing and Performance

The collector runs on nodes and competes for node resources. High log volume can consume CPU, memory, network, and disk I/O.

### 31.1 Set collector resources

```bash
oc patch clusterlogforwarder instance -n openshift-logging \
  --type=merge \
  -p '{"spec":{"collector":{"resources":{"requests":{"cpu":"100m","memory":"256Mi"},"limits":{"cpu":"500m","memory":"512Mi"}}}}}'
```

Example YAML:

```yaml
spec:
  collector:
    resources:
      requests:
        cpu: 100m
        memory: 256Mi
      limits:
        cpu: 500m
        memory: 512Mi
```

### 31.2 Performance drivers

| Driver | Impact |
|---|---|
| Number of pods per node | More files to tail. |
| Log lines per second | More CPU/network. |
| Message size | More memory and bandwidth. |
| Multiline detection | More CPU/memory. |
| JSON parsing | More CPU. |
| Number of outputs | More network and retries. |
| TLS/compression | More CPU but less bandwidth. |
| Slow destination | More retries/backpressure. |

### 31.3 Monitor collector pods

```bash
oc adm top pods -n openshift-logging
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc describe pod -n openshift-logging -l app.kubernetes.io/component=collector
```

Look for:

- OOMKilled.
- High restarts.
- CPU throttling.
- Error logs.
- Backoff messages.
- TLS errors.
- 429 responses.

## 32. Reliability, Backpressure, and Log Loss

Log forwarding is not magic. If destinations are slow, unavailable, or rate-limited, some logs may be delayed or dropped depending on configuration and conditions.

### 32.1 Common failure modes

| Failure | Effect |
|---|---|
| Destination TLS error | Logs not delivered to that output. |
| Destination returns 429 | Collector retries, may backlog. |
| Destination down | Retries/backpressure. |
| Collector OOM | Collection interruption. |
| Rate limit exceeded | Logs dropped. |
| Max message size exceeded | Large log records dropped. |
| Missing RBAC | Collector DaemonSet removed / not running. |
| NetworkPolicy blocks egress | Delivery failure. |

### 32.2 Design for reliability

- Use separate pipelines for critical audit logs.
- Avoid sending every debug log to expensive or fragile systems.
- Use rate limits intentionally.
- Keep collector resources adequate.
- Monitor output errors.
- Use durable destinations for compliance logs.
- Do not assume `Ready=True` means every destination is receiving logs; always verify actual delivery.

## 34. Troubleshooting Runbook

### 34.1 Problem: No collector pods

Check:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Likely causes:

- Missing service account.
- Missing cluster role binding.
- Invalid `ClusterLogForwarder` spec.
- Unauthorized `inputRefs` such as `audit` without `collect-audit-logs`.

Fix:

```bash
oc create sa collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

If audit is referenced:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### 34.2 Problem: `Ready=True` but no logs in LokiStack

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Look for:

```text
certificate verify failed
self-signed certificate in certificate chain
```

Fix LokiStack CA:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

### 34.3 Problem: 429 Too Many Requests

Symptom:

```text
429 Too Many Requests
```

Meaning:

- Destination is throttling.
- Initial backlog flush is too aggressive.
- LokiStack or external sink is undersized.

Actions:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector | grep 429
oc adm top pods -n openshift-logging
```

Fix options:

- Wait if it is initial backlog.
- Increase destination capacity.
- Reduce log volume.
- Add filters.
- Add rate limits intentionally.
- Tune LokiStack size.

### 34.4 Problem: TLS handshake errors

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector | grep -i tls
```

Fix:

- Verify CA config map.
- Verify secret keys.
- Verify server certificate CN/SAN.
- Verify URL hostname matches certificate.
- Verify intermediate CA chain.

### 34.5 Problem: External destination unreachable

Test from namespace:

```bash
oc run net-test -n openshift-logging --rm -it \
  --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Then:

```bash
curl -vk https://destination.example.com:443
```

Check:

- DNS.
- Firewall.
- Proxy.
- NetworkPolicy.
- Egress firewall.
- Route table.
- Destination listener.

### 34.6 Problem: Logs duplicated

Likely cause:

- Same source referenced by multiple pipelines.
- Custom input overlaps with `application` built-in input.

Example:

```yaml
pipelines:
- name: all-apps
  inputRefs:
  - application
- name: pci-apps
  inputRefs:
  - pci-apps
```

If `pci-apps` is a subset of `application`, those logs appear in both destinations.

Fix:

- Decide if duplication is expected.
- Exclude PCI namespaces from generic app input.
- Use separate custom inputs.

### 34.7 Problem: Missing specific namespace logs

Check namespace and labels:

```bash
oc get ns --show-labels
oc get pods -n <namespace> --show-labels
```

Check input selectors:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Common mistakes:

- Wrong namespace pattern.
- Label mismatch.
- Exclude overrides include.
- App writes logs to file instead of stdout/stderr.
- Pod not running on expected node.

### 34.8 Problem: Large Java stack traces split into many records

Fix:

```yaml
filters:
- name: multiline
  type: detectMultilineException
pipelines:
- name: apps-to-loki
  inputRefs:
  - application
  filterRefs:
  - multiline
  outputRefs:
  - default-lokistack
```

Watch collector CPU/memory after enabling.

### 34.9 Problem: LogFileMetricExporter dashboard empty

Create the exporter:

```yaml
apiVersion: logging.openshift.io/v1alpha1
kind: LogFileMetricExporter
metadata:
  name: instance
  namespace: openshift-logging
spec:
  nodeSelector: {}
  resources:
    limits:
      cpu: 500m
      memory: 256Mi
    requests:
      cpu: 200m
      memory: 128Mi
  tolerations: []
```

Apply:

```bash
oc apply -f log-file-metric-exporter.yaml
```

Verify:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=logfilesmetricexporter
```

## 35. Production Design Patterns

### 35.1 Pattern: Short-term operational logs + long-term audit archive

```text
Application + infrastructure -> LokiStack, 7-30 days
Audit -> S3 immutable archive, 1-7 years
Critical audit/security -> Splunk SIEM
```

Why:

- LokiStack gives fast troubleshooting.
- S3 reduces long-term cost.
- Splunk provides security analytics.

### 35.2 Pattern: Team-specific forwarding

```text
team-a namespace -> team-a Splunk index
team-b namespace -> team-b Loki tenant/tool
platform logs -> SRE LokiStack
```

Why:

- Separation of access.
- Lower noise.
- Cost ownership by team.

### 35.3 Pattern: Kafka as central log bus

```text
OpenShift collectors -> Kafka -> SIEM / data lake / analytics / alerting
```

Why:

- Decouples OpenShift from many consumers.
- Supports multiple downstream systems.
- Allows replay if retention is configured.

Caution:

- Kafka must be sized and monitored.
- If Kafka is unavailable and buffers fill, logs can be delayed or dropped.

### 35.4 Pattern: Compliance-first audit pipeline

```text
Audit input -> minimal filtering -> TLS -> immutable S3 -> restricted access
```

Why:

- Security evidence integrity.
- Least privilege.
- Lower risk of accidental deletion.

### 35.5 Pattern: Cost-control filter layer

```text
Drop health checks
Drop debug from non-prod
Prune annotations
Rate-limit noisy containers
Forward only high-value logs to expensive sinks
```

Why:

- Logging cost can grow faster than compute cost.
- Debug logs often dominate volume.
- Annotations and labels can be large.

## 36. Security and Compliance Best Practices

### 36.1 Least privilege

Grant only required collector roles:

| Need | Role |
|---|---|
| App logs | `collect-application-logs` |
| Infra logs | `collect-infrastructure-logs` |
| Audit logs | `collect-audit-logs` |

Do not bind `collect-audit-logs` unless audit logs are required.

### 36.2 Separate audit logs

Audit logs should usually have:

- Separate pipeline.
- Separate destination.
- Separate retention policy.
- Restricted access.
- Stronger encryption and immutability.

### 36.3 Protect credentials

- Store output tokens in Secrets.
- Rotate tokens.
- Restrict who can read `openshift-logging` secrets.
- Avoid committing raw secrets to Git.

### 36.4 Prune sensitive fields

Use `prune` before sending logs to third-party SaaS providers.

Examples to consider:

```text
.kubernetes.annotations
.kubernetes.labels containing internal IDs
structured.customer_email
structured.token
structured.authorization
```

### 36.5 Avoid leaking secrets in application logs

No log forwarder can fully fix bad application logging. Enforce application logging standards:

- Do not log passwords.
- Do not log bearer tokens.
- Do not log full request headers.
- Mask PII.
- Use structured logging.

### 36.6 Use TLS everywhere

For external outputs, prefer HTTPS/TLS and validate CA properly. Do not disable certificate validation in production.

## 37. Common Mistakes

### Mistake 1: Adding audit input before RBAC

Bad:

```yaml
inputRefs:
- audit
```

without:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

Result: collector may be removed or not deployed.

### Mistake 2: Missing LokiStack CA

Symptom:

```text
Ready=True, but no logs in LokiStack
```

Fix:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

### Mistake 3: Confusing `loki` and `lokiStack`

Use:

```yaml
type: lokiStack
```

for Red Hat managed LokiStack.

Use:

```yaml
type: loki
```

for external Loki.

### Mistake 4: Overusing labels in Loki

High-cardinality labels hurt Loki performance.

Bad label ideas:

- Request ID.
- User ID.
- Pod UID.
- Full URL.
- Error message.

Good label ideas:

- Namespace.
- App.
- Container.
- Log type.
- Environment.

### Mistake 5: Forwarding everything to Splunk

This often causes high cost. Filter, split, and rate-limit.

### Mistake 6: Assuming logs written to files are collected

OpenShift standard application logging expects stdout/stderr. If an app writes to `/var/log/app.log` inside the container, the collector normally does not collect it unless the app also emits to stdout/stderr or a supported custom approach is used.

### Mistake 7: Using old API examples blindly

Always check:

```bash
oc explain clusterlogforwarder
```

and verify API group.

### Mistake 8: Forgetting NetworkPolicy

In restricted clusters, collector egress may be blocked.

### Mistake 9: Too much multiline detection

Multiline is helpful, but cluster-wide usage on huge workloads can increase CPU/memory consumption.

### Mistake 10: Not testing with real volume

A config that works with 10 log lines per second may fail at 20,000 lines per second.

## 38. Interview and Real-World Scenario Questions

### Q1. What is `ClusterLogForwarder`?

`ClusterLogForwarder` is the OpenShift Logging custom resource used to define log collection and forwarding. It specifies the collector service account, log inputs, optional filters, outputs, and pipelines that route selected logs to one or more destinations.

### Q2. What is the difference between input, filter, output, and pipeline?

- Input selects logs.
- Filter transforms or drops logs.
- Output defines destination.
- Pipeline connects inputs, filters, and outputs.

### Q3. What happens if you reference audit logs without `collect-audit-logs`?

The collector service account is unauthorized. The Operator can remove the collector DaemonSet or refuse to run it, stopping log collection until RBAC is corrected.

### Q4. How do you forward only one namespace to Splunk?

Create a custom application input using `includes.namespace`, configure a Splunk output, and create a pipeline referencing that input and output.

### Q5. How do you reduce log cost?

- Use input selectors.
- Drop noisy logs.
- Prune large metadata fields.
- Rate-limit high-volume sources.
- Use cheap archive storage for long-term retention.
- Avoid forwarding debug logs to expensive systems.

### Q6. What is the difference between `loki` and `lokiStack` output?

`lokiStack` targets a Red Hat managed LokiStack with OpenShift Logging authentication and tenancy. `loki` targets an external Loki endpoint.

### Q7. Why can `Ready=True` still have no logs in LokiStack?

The CR can be valid and the collector deployed, but delivery can fail due to TLS CA errors, destination errors, NetworkPolicy, or rate limiting. Always check collector logs and destination ingestion.

### Q8. How do you collect multiline Java stack traces?

Use the `detectMultilineException` filter and reference it in the application pipeline.

### Q9. How do you handle PII before logs leave the cluster?

Use application logging standards to avoid generating PII, then use `prune` filters to remove sensitive fields before external forwarding.

### Q10. What is the best design for audit logs?

Forward audit logs through a dedicated pipeline to a secure destination such as S3 immutable archive and/or a SIEM. Use TLS, least privilege, restricted access, and carefully approved filtering.

For a 10-year-experience OpenShift administrator, log forwarding is not only a YAML task. It is an operational design problem involving RBAC, tenancy, security, cost, performance, retention, and failure handling.

The most important production rules are:

2. **Use input selectors to avoid collecting unnecessary logs.**
3. **Use filters to drop noise and prune sensitive data.**
4. **Separate app, infra, and audit pipelines.**
5. **Use `lokiStack` for Red Hat managed LokiStack and `loki` for external Loki.**
6. **Always configure TLS CA correctly for secure outputs.**
7. **Monitor collector status, logs, rate limits, and destination ingestion.**
8. **Design audit forwarding as security evidence, not developer troubleshooting data.**
