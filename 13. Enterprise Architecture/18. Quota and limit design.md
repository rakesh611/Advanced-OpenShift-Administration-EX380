# 1. What quota and limit design means

Quota and limit design is the enterprise architecture discipline of deciding **how much CPU, memory, storage, object count, and ephemeral capacity each OpenShift project is allowed to consume**, and how individual containers and pods are constrained inside those projects.

In OpenShift, this design is implemented mainly through:

| Area | Object | Scope | Purpose |
|---|---|---|---|
| Namespace/project aggregate control | `ResourceQuota` | One namespace/project | Limits total consumption inside a project |
| Per-container, per-pod, and per-PVC defaults/constraints | `LimitRange` | One namespace/project | Sets default requests/limits and min/max boundaries |
| Multi-project aggregate control | `ClusterResourceQuota` | Multiple projects selected by label/annotation | Shares one quota budget across several projects |
| Visibility for project admins | `AppliedClusterResourceQuota` | Project view | Shows cluster quotas applied to a project |
| Default onboarding governance | Project request template | Cluster-level project creation flow | Injects standard quota/LimitRange/network policy/RBAC into new projects |

A good quota and limit design answers questions like:

- How much CPU and memory can the `payment-prod` namespace consume?
- What default CPU/memory request should be applied when a developer forgets to specify resources?
- Should production apps be allowed to run BestEffort pods?
- How many pods, services, secrets, routes, config maps, PVCs, and load balancers can one project create?
- Can a developer accidentally create 500 PVCs or 1,000 pods?
- How much storage can a team consume across all dev namespaces?
- How do quotas align with cluster capacity, cost allocation, autoscaling, and SLOs?

# 2. Why quota and limit design matters in enterprise OpenShift

In a small lab cluster, missing quotas usually cause inconvenience. In an enterprise production cluster, missing quotas can cause outages, noisy-neighbor incidents, unexpected cloud cost, failed deployments, failed autoscaling, and unstable worker nodes.

## 2.1 Enterprise risks without quota and limit design

| Risk | Example |
|---|---|
| Noisy neighbor | One namespace consumes too much CPU/memory and affects other tenants |
| Scheduler pressure | Pods without requests make capacity planning inaccurate |
| Node instability | Memory-heavy workloads without limits cause eviction/OOM scenarios |
| Cost explosion | Dynamic PVCs, LoadBalancer services, and high pod counts create hidden cost |
| Failed autoscaling | HPA cannot scale correctly if CPU requests are missing or unrealistic |
| Failed deployments | Quota is too tight for rolling updates, so deployments get stuck |
| Security exposure | Unlimited object creation allows abuse or accidental API object sprawl |
| Poor chargeback | Platform team cannot map usage to business units or cost centers |
| Production instability | Dev/test workloads can consume capacity needed by production |

## 2.2 Enterprise goals

A mature quota and limit architecture should provide:

1. **Fairness** — each team receives a controlled share of shared cluster capacity.
2. **Predictability** — scheduling and scaling decisions are based on real requests.
3. **Availability** — production namespaces keep enough headroom for rolling updates and failover.
4. **Cost control** — storage, object count, and cloud-integrated resources are bounded.
5. **Security** — tenants cannot exhaust API objects or create unlimited resources.
6. **Governance** — every namespace follows a standard baseline.
7. **Self-service** — developers can deploy safely without opening tickets for every object.
8. **Observability** — platform teams can alert before quota exhaustion.
9. **Scalability** — quota objects and multi-project quota selectors do not overload API admission paths.
10. **Auditability** — quota changes are reviewed, versioned, and traceable.

# 3. Core OpenShift and Kubernetes objects

## 3.1 ResourceQuota

`ResourceQuota` limits aggregate resource consumption in a namespace/project.

It can control:

- CPU requests
- CPU limits
- Memory requests
- Memory limits
- Storage requests
- Ephemeral storage requests/limits
- PVC count
- Pod count
- Service count
- Secret count
- ConfigMap count
- Route count
- ReplicationController/Deployment-related object count
- Resource count by API group using `count/<resource>.<group>` syntax

Example:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-prod-standard
  namespace: payment-prod
spec:
  hard:
    requests.cpu: "12"
    limits.cpu: "24"
    requests.memory: 48Gi
    limits.memory: 96Gi
    pods: "120"
    services: "30"
    secrets: "100"
    configmaps: "100"
    persistentvolumeclaims: "20"
    requests.storage: 500Gi
```

Important behavior:

- Quota is enforced at API admission time.
- If a create/update request would exceed quota, it is rejected.
- Quota tracks objects that exist in API server storage.
- Quota is not a replacement for node capacity planning.
- Quota is not a replacement for application performance testing.

## 3.2 LimitRange

`LimitRange` sets default and allowed minimum/maximum resource values in a namespace.

It can:

- Set default CPU/memory requests for containers.
- Set default CPU/memory limits for containers.
- Set minimum and maximum CPU/memory per container or pod.
- Set maximum request-to-limit ratio.
- Set minimum/maximum storage request per PVC.

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-prod-standard
  namespace: payment-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 200m
      memory: 256Mi
    default:
      cpu: 1
      memory: 1Gi
    min:
      cpu: 50m
      memory: 64Mi
    max:
      cpu: 4
      memory: 8Gi
    maxLimitRequestRatio:
      cpu: "10"
      memory: "4"
```

## 3.3 ClusterResourceQuota

`ClusterResourceQuota` is OpenShift-specific and applies a shared quota budget across multiple projects selected by labels and/or annotations.

Example:

```yaml
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata:
  name: crq-team-payments-nonprod
spec:
  selector:
    labels:
      matchLabels:
        cost-center: payments
        environment-class: nonprod
  quota:
    hard:
      requests.cpu: "40"
      limits.cpu: "80"
      requests.memory: 160Gi
      limits.memory: 320Gi
      pods: "400"
      persistentvolumeclaims: "80"
      requests.storage: 2Ti
```

Use it when a team owns many namespaces and you want one aggregate quota across all of them.

## 3.4 AppliedClusterResourceQuota

`AppliedClusterResourceQuota` gives project-level visibility into ClusterResourceQuotas that apply to that project.

Useful command:

```bash
oc describe appliedclusterresourcequota -n <project>
```

This helps project admins understand why a namespace might be blocked even when its local `ResourceQuota` still has space.

# 4. Requests, limits, scheduler behavior, and runtime behavior

Quota and limit design cannot be understood without understanding requests and limits.

## 4.1 Requests

A **request** is the amount of resource Kubernetes/OpenShift uses for scheduling.

Example:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi
```

Meaning:

- The scheduler places the pod on a node that has enough allocatable capacity for the request.
- Requests are the main signal for capacity planning.
- Requests influence Quality of Service class.
- HPA CPU utilization is calculated against CPU request.

If requests are too low:

- Cluster looks underutilized on paper.
- Too many pods can be scheduled.
- Nodes may suffer pressure later.
- HPA may scale aggressively because usage/request ratio appears high.

If requests are too high:

- Pods may remain Pending.
- Cluster appears full even when actual usage is low.
- Cost increases because capacity is reserved but unused.

## 4.2 Limits

A **limit** is the maximum resource a container is allowed to use at runtime.

Example:

```yaml
resources:
  limits:
    cpu: "2"
    memory: 2Gi
```

Meaning:

- CPU limits can throttle CPU usage.
- Memory limits can cause container termination when memory usage exceeds the limit.
- Limits protect nodes and other tenants.
- Limits can also hurt performance if set too low.

## 4.3 CPU behavior

CPU is compressible.

If a container hits its CPU limit:

- It is throttled.
- It is usually not killed.
- Latency-sensitive applications may suffer.
- Java, API gateways, and high-throughput services may show high response time even when average CPU looks acceptable.

Senior-level design point:

> CPU limit design should be stricter in shared dev/test environments and more carefully tuned in latency-sensitive production environments. For critical production workloads, avoid blindly setting very low CPU limits. Use monitoring, load testing, and throttling metrics.

## 4.4 Memory behavior

Memory is not compressible in the same way as CPU.

If a container exceeds its memory limit:

- It can be OOMKilled.
- The pod may restart depending on restart policy.
- Application availability can be affected.

Senior-level design point:

> Memory requests should represent normal steady-state working set. Memory limits should allow expected burst/headroom, but not unlimited growth.

## 4.5 Quality of Service classes

Kubernetes assigns pod QoS classes:

| QoS class | Condition | Enterprise meaning |
|---|---|---|
| Guaranteed | CPU and memory requests equal limits for all containers | Highest predictability, useful for critical workloads |
| Burstable | Some requests/limits set but not equal | Common production default |
| BestEffort | No CPU/memory requests or limits | Usually not acceptable for production |

Enterprise recommendation:

- Production: mostly `Burstable`, sometimes `Guaranteed` for critical stateful/latency-sensitive workloads.
- Non-production: `Burstable` with conservative defaults.
- Sandbox: small requests/limits and strict object quotas.

# 5. ResourceQuota design

## 5.1 ResourceQuota purpose

A `ResourceQuota` sets the maximum aggregate consumption inside one project.

Think of it as:

> “This namespace may consume up to X requested CPU, Y memory, Z storage, and N objects.”

## 5.2 ResourceQuota categories

### 5.2.1 Compute quota

Controls CPU and memory requests/limits.

```yaml
spec:
  hard:
    requests.cpu: "8"
    limits.cpu: "16"
    requests.memory: 32Gi
    limits.memory: 64Gi
```

Use compute quota to:

- Prevent one namespace from consuming all schedulable CPU/memory.
- Force teams to think about sizing.
- Support chargeback/showback.
- Ensure HPA max replica planning.

### 5.2.2 Storage quota

Controls total storage requested by PVCs.

```yaml
spec:
  hard:
    persistentvolumeclaims: "20"
    requests.storage: 500Gi
```

Storage quota prevents:

- Unlimited PVC creation.
- Accidental large PVC requests.
- Storage backend exhaustion.
- Cost growth in cloud storage.

### 5.2.3 StorageClass-specific quota

Use this when you have multiple storage classes with different cost/performance profiles.

Example:

```yaml
spec:
  hard:
    fast-ssd.storageclass.storage.k8s.io/requests.storage: 200Gi
    standard.storageclass.storage.k8s.io/requests.storage: 1Ti
    fast-ssd.storageclass.storage.k8s.io/persistentvolumeclaims: "10"
    standard.storageclass.storage.k8s.io/persistentvolumeclaims: "50"
```

Design use cases:

- Limit premium SSD consumption.
- Allow larger standard storage usage.
- Separate database storage from general-purpose storage.

### 5.2.4 Object count quota

Controls number of API objects.

```yaml
spec:
  hard:
    pods: "100"
    services: "30"
    secrets: "100"
    configmaps: "100"
    persistentvolumeclaims: "20"
    count/routes.route.openshift.io: "20"
```

Use object quotas to prevent:

- API object sprawl.
- Thousands of Secrets or ConfigMaps.
- Excessive Services or Routes.
- Accidental loops in CI/CD creating objects.

### 5.2.5 Ephemeral storage quota

Controls local ephemeral storage used by containers, logs, writable layers, and emptyDir-backed storage.

```yaml
spec:
  hard:
    requests.ephemeral-storage: 50Gi
    limits.ephemeral-storage: 100Gi
```

Use this for:

- Logging-heavy applications.
- Build workloads.
- Temporary processing workloads.
- CI namespaces.
- Apps writing to container filesystem.

## 5.3 ResourceQuota design decision table

| Question | Design decision |
|---|---|
| Is this namespace production? | Larger quota, stricter requests, monitored limits |
| Is it dev/test? | Smaller quota, more overcommit, stricter object count |
| Is it sandbox? | Very small compute/storage quota and automatic cleanup |
| Does the app use HPA? | Quota must support max replica count plus rollout surge |
| Does the app use PVCs? | Include PVC count and storage quota |
| Does the app create routes dynamically? | Include route count quota |
| Does CI/CD create short-lived objects? | Include object count and cleanup policies |
| Is the app latency-sensitive? | Avoid overly tight CPU limits; monitor throttling |
| Is the app memory-sensitive? | Use realistic memory request and safe limit |
| Is this a platform namespace? | Usually no tenant quota; manage separately with strict change control |

## 5.4 Quota calculation method

For each namespace:

```text
Namespace request quota = sum(max planned replicas × per-pod requests) + rollout headroom + failure headroom
Namespace limit quota   = sum(max planned replicas × per-pod limits)   + rollout headroom
```

For production:

```text
Quota should support:
- steady-state replicas
- HPA max replicas
- rolling update maxSurge
- emergency hotfix deployment
- sidecars
- init containers
- observability agents if injected
```

Example:

Application `payment-api`:

```text
Replicas: 6
HPA max: 20
CPU request per pod: 500m
Memory request per pod: 768Mi
CPU limit per pod: 2
Memory limit per pod: 2Gi
maxSurge: 25% => 5 extra pods at max HPA scale
Sidecar overhead: 100m CPU, 128Mi memory per pod
```

Per pod request:

```text
CPU request = 500m + 100m = 600m
Memory request = 768Mi + 128Mi = 896Mi
```

Quota request for HPA + surge:

```text
Max pods during rollout = 20 + 5 = 25
CPU requests = 25 × 600m = 15 CPU
Memory requests = 25 × 896Mi = 22,400Mi ≈ 22Gi
```

Add 20% operational buffer:

```text
CPU request quota ≈ 18 CPU
Memory request quota ≈ 27Gi
```

A reasonable namespace quota might be:

```yaml
requests.cpu: "18"
requests.memory: 28Gi
limits.cpu: "60"
limits.memory: 64Gi
pods: "80"
```

# 6. LimitRange design

## 6.1 LimitRange purpose

`LimitRange` controls resource defaults and boundaries for containers, pods, and PVCs inside a project.

It answers:

- What happens when a developer forgets to set CPU/memory requests?
- What is the minimum allowed container size?
- What is the maximum allowed container size?
- Can a container request 50Gi memory in a small dev namespace?
- Can a PVC request 10Ti by mistake?
- What request-to-limit ratio is acceptable?

## 6.2 Why LimitRange is required with ResourceQuota

If a namespace has CPU/memory quota and a pod does not specify CPU/memory requests or limits, pod admission may fail depending on the quota keys configured.

A LimitRange solves this by injecting default requests/limits.

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-container-limits
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
```

Now a pod without explicit resources receives defaults.

## 6.3 Production LimitRange pattern

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 200m
      memory: 256Mi
    default:
      cpu: 1
      memory: 1Gi
    min:
      cpu: 50m
      memory: 64Mi
    max:
      cpu: 4
      memory: 8Gi
    maxLimitRequestRatio:
      cpu: "10"
      memory: "4"
  - type: Pod
    max:
      cpu: 8
      memory: 16Gi
  - type: PersistentVolumeClaim
    min:
      storage: 1Gi
    max:
      storage: 200Gi
```

Design explanation:

- `defaultRequest` gives every container schedulable footprint.
- `default` prevents unlimited resource use.
- `min` prevents meaningless tiny requests.
- `max` prevents huge containers without review.
- `maxLimitRequestRatio` prevents a container from requesting 100m CPU but limiting at 8 CPU.
- PVC min/max prevents accidental tiny or huge volumes.

## 6.4 Dev/test LimitRange pattern

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-nonprod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 50m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
    min:
      cpu: 25m
      memory: 64Mi
    max:
      cpu: 2
      memory: 4Gi
    maxLimitRequestRatio:
      cpu: "20"
      memory: "6"
  - type: PersistentVolumeClaim
    min:
      storage: 1Gi
    max:
      storage: 50Gi
```

## 6.5 Sandbox LimitRange pattern

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-sandbox
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 25m
      memory: 64Mi
    default:
      cpu: 250m
      memory: 256Mi
    min:
      cpu: 10m
      memory: 32Mi
    max:
      cpu: 1
      memory: 1Gi
  - type: PersistentVolumeClaim
    min:
      storage: 1Gi
    max:
      storage: 10Gi
```

## 6.6 LimitRange design mistakes

| Mistake | Impact |
|---|---|
| Very high default limits | Every pod consumes quota quickly |
| Very low memory defaults | Apps OOMKill unexpectedly |
| No default requests | Scheduling and HPA become unreliable |
| No max container size | One app can request huge resources |
| Same limits for all namespaces | Production and sandbox needs are different |
| CPU limit too low for latency app | CPU throttling and slow responses |
| Memory limit equal to normal usage | Frequent OOMKills during traffic spikes |

# 7. ClusterResourceQuota design

## 7.1 Purpose

`ClusterResourceQuota` allows a shared quota across many projects.

Example use cases:

- One business unit owns many namespaces.
- One developer can create multiple self-service projects.
- One team has separate `dev`, `test`, `stage`, and feature namespaces.
- You want to prevent total non-production consumption from exceeding a team budget.

## 7.2 Selection model

ClusterResourceQuota selects projects using:

- Labels
- Annotations
- Both labels and annotations

Example namespace labels:

```yaml
metadata:
  labels:
    cost-center: payments
    environment-class: nonprod
    owner-team: payments-platform
```

ClusterResourceQuota:

```yaml
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata:
  name: crq-payments-nonprod
spec:
  selector:
    labels:
      matchLabels:
        cost-center: payments
        environment-class: nonprod
  quota:
    hard:
      requests.cpu: "40"
      limits.cpu: "100"
      requests.memory: 160Gi
      limits.memory: 400Gi
      pods: "500"
      persistentvolumeclaims: "100"
      requests.storage: 5Ti
```

## 7.3 When to use ClusterResourceQuota

Use it when:

- You need team-level or business-unit-level quota.
- Namespaces are created dynamically.
- Project-level quotas alone cannot control aggregate consumption.
- You operate a multi-tenant platform.
- You have self-service namespace creation.

Avoid or use carefully when:

- It selects too many active namespaces.
- Labeling is inconsistent.
- Multiple ClusterResourceQuotas overlap without clear policy.
- Teams cannot understand where quota exhaustion is happening.

## 7.4 ClusterResourceQuota and performance consideration

ClusterResourceQuota participates in admission decisions. A quota that selects a very large number of active projects can increase contention during object creation.

Enterprise rule:

> Prefer several targeted ClusterResourceQuotas over one massive quota selecting hundreds of busy projects.

Recommended pattern:

| Scope | Example selector |
|---|---|
| Business unit non-prod | `cost-center=payments, environment-class=nonprod` |
| Business unit prod | `cost-center=payments, environment-class=prod` |
| Shared dev sandbox | `environment-class=sandbox` |
| CI projects | `workload-type=ci` |

## 7.5 Viewing ClusterResourceQuota usage

```bash
oc get clusterresourcequota
oc describe clusterresourcequota crq-payments-nonprod
oc describe appliedclusterresourcequota -n payment-dev
```

# 8. Enterprise quota architecture model

A strong enterprise quota architecture has multiple layers.

```text
Enterprise Capacity Policy
        ↓
Cluster Capacity Plan
        ↓
Environment Tier Model
        ↓
Business Unit / Team Quota
        ↓
Namespace ResourceQuota
        ↓
Namespace LimitRange
        ↓
Application Requests and Limits
        ↓
Monitoring, Alerts, Review, Chargeback
```

## 8.1 Layer 1: Enterprise capacity policy

Defines global rules:

- Production receives reserved capacity.
- Non-production can be overcommitted more aggressively.
- Sandbox namespaces have strict default limits.
- Storage classes have cost tiers.
- Every namespace must have owner, cost center, environment, and lifecycle labels.
- All quotas are managed by GitOps.

## 8.2 Layer 2: Cluster capacity plan

Maps physical/virtual/cloud capacity:

```text
Total worker allocatable CPU
Total worker allocatable memory
Reserved capacity for platform components
Reserved capacity for node drain/upgrade
Reserved capacity for failure domain loss
Allowed overcommit ratio
Quota budget per environment
```

Example:

```text
Cluster allocatable CPU: 600 cores
Cluster allocatable memory: 2.4 TiB
Platform reserve: 15%
Upgrade/drain reserve: 15%
Emergency buffer: 10%
Tenant usable CPU: 600 × 0.60 = 360 cores
Tenant usable memory: 2.4 TiB × 0.60 = 1.44 TiB
```

## 8.3 Layer 3: Environment tier model

| Tier | Purpose | Quota behavior |
|---|---|---|
| Prod critical | Revenue/SLO critical | Conservative memory overcommit, tested limits, enough rollout headroom |
| Prod standard | Normal production apps | Controlled overcommit, strict object/storage quota |
| Stage/pre-prod | Production-like validation | Similar shape to prod but smaller |
| Test/QA | Functional/performance testing | Moderate quota, scheduled scale-down possible |
| Dev | Developer iteration | Smaller quota, higher CPU overcommit |
| Sandbox | Experimentation | Very strict quota, short lifecycle |
| CI/CD | Build/test automation | Ephemeral storage and object quotas important |

## 8.4 Layer 4: Team quota model

For large enterprises, assign quota budgets to teams or business units.

Example:

```text
Payments BU:
- Production budget: 80 CPU request, 320Gi memory request
- Non-production budget: 60 CPU request, 240Gi memory request
- Storage budget: 10Ti standard, 2Ti premium
```

Implement with:

- ClusterResourceQuota for aggregate team quota.
- ResourceQuota for namespace-level quota.
- LimitRange for per-workload guardrails.

## 8.5 Layer 5: Namespace-level quota

Each namespace gets a specific quota based on workload criticality.

Examples:

- `payment-api-prod`
- `payment-api-stage`
- `payment-api-dev`
- `payment-api-ci`

Each namespace has tailored:

- CPU request/limit quota
- Memory request/limit quota
- Pod quota
- PVC/storage quota
- Route/service/object quota
- LimitRange defaults

# 9. Namespace/project tiering model

## 9.1 Recommended enterprise labels

Every project should have labels like:

```yaml
metadata:
  labels:
    environment: prod
    environment-class: production
    owner-team: payments
    cost-center: cc-1042
    application: payment-api
    data-classification: internal
    support-tier: tier-1
    lifecycle: active
```

These labels help with:

- Quota selection
- ClusterResourceQuota selection
- Cost reporting
- NetworkPolicy selection
- Backup policy selection
- Monitoring routing
- Compliance reporting

## 9.2 Tier examples

### Production critical namespace

```yaml
metadata:
  labels:
    environment: prod
    environment-class: production
    support-tier: tier-1
    quota-tier: prod-critical
```

Typical properties:

- Larger CPU/memory request quota.
- Memory limits based on load testing.
- CPU limits carefully reviewed.
- High pod count to allow HPA and rollouts.
- Storage quota sized for retention and growth.
- Alerts at 70%, 80%, and 90% usage.

### Non-production namespace

```yaml
metadata:
  labels:
    environment: dev
    environment-class: nonprod
    support-tier: tier-3
    quota-tier: nonprod-standard
```

Typical properties:

- Smaller quota.
- Strong default limits.
- More aggressive CPU overcommit.
- Lower PVC size maximum.
- Automated cleanup.

### Sandbox namespace

```yaml
metadata:
  labels:
    environment: sandbox
    environment-class: sandbox
    quota-tier: sandbox
    lifecycle: temporary
```

Typical properties:

- Very small quota.
- Short TTL.
- Strict object count.
- No premium storage.
- No external routes unless approved.

# 10. Production namespace design with quotas and limits

Production quota design must support availability, rollout, scaling, and failure recovery.

## 10.1 Production requirements

For each production namespace, collect:

1. Quota must allow HPA maximum replicas.

9. Quotas must be GitOps-managed.
10. Exceptions must expire or be reviewed periodically.

# 12. Storage quota design

Storage quota is often missed, but it is one of the biggest cost and risk areas.

## 12.1 What to control

Control:

- Number of PVCs
- Total requested storage
- Storage per PVC through LimitRange
- StorageClass-specific usage
- Premium storage usage
- Snapshot/backup impact where relevant

## 12.2 Storage quota example

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-storage-standard
spec:
  hard:
    persistentvolumeclaims: "20"
    requests.storage: 1Ti
    standard.storageclass.storage.k8s.io/requests.storage: 800Gi
    premium.storageclass.storage.k8s.io/requests.storage: 200Gi
    standard.storageclass.storage.k8s.io/persistentvolumeclaims: "15"
    premium.storageclass.storage.k8s.io/persistentvolumeclaims: "5"
```

## 12.3 PVC LimitRange example

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-pvc-size
spec:
  limits:
  - type: PersistentVolumeClaim
    min:
      storage: 1Gi
    max:
      storage: 200Gi
```

## 12.4 Design questions

Before granting storage quota, ask:

- Is the workload stateful?
- What StorageClass is required?
- What is the IOPS/throughput requirement?
- What is the data growth rate?
- What is the retention period?
- Is backup/snapshot required?
- Is encryption required?
- Is cross-zone replication required?
- What is the restore procedure?
- Is the volume expansion policy approved?

## 12.5 Storage anti-patterns

| Anti-pattern | Problem |
|---|---|
| Unlimited PVC count | Storage backend exhaustion |
| Unlimited premium storage | High cost |
| Huge max PVC in every namespace | Accidental large allocation |
| No per-StorageClass quota | Teams consume expensive classes silently |
| No storage monitoring | Quota exhaustion discovered during incident |
| Same quota for DB and stateless app | Poor cost/performance alignment |

# 15. CPU and memory overcommit design

Overcommit means granting more quota than physical allocatable capacity because not all workloads peak at the same time.

## 15.1 CPU overcommit

CPU is generally overcommitted more safely than memory.

Example:

```text
Cluster usable CPU: 300 cores
Allowed CPU request quota total: 600 cores
CPU request overcommit ratio: 2:1
```

Common pattern:

| Environment | CPU request overcommit idea |
|---|---:|
| Prod critical | 1:1 to 1.5:1 |
| Prod standard | 1.5:1 to 2:1 |
| Non-prod | 2:1 to 4:1 |
| Sandbox | 4:1 or more, with strict limits |

Use real monitoring before choosing ratios.

## 15.2 Memory overcommit

Memory overcommit is riskier because memory pressure causes eviction or OOM.

Common pattern:

| Environment | Memory request overcommit idea |
|---|---:|
| Prod critical | 1:1 to 1.2:1 |
| Prod standard | 1:1 to 1.5:1 |
| Non-prod | 1.5:1 to 2:1 |
| Sandbox | Higher only if risk is accepted |

## 15.3 Limit-to-request ratio

Example:

```text
CPU request: 250m
CPU limit: 2
CPU ratio: 8:1
```

High ratios can be acceptable for bursty workloads, but they make capacity planning harder.

Recommended rough guidance:

| Workload | CPU limit/request ratio | Memory limit/request ratio |
|---|---:|---:|
| Latency-sensitive API | 2–4 | 1.5–3 |
| Batch job | 4–10 | 2–4 |
| Dev workload | 5–20 | 2–6 |
| Database | Carefully tested | Carefully tested |
| JVM app | Carefully tested | 1.5–3, aligned with heap/non-heap |

## 15.4 Why request accuracy matters

Requests drive:

- Scheduling
- Cluster autoscaler decisions
- HPA CPU utilization denominator
- Capacity reports
- Chargeback/showback
- Quota consumption
- Upgrade planning
- Node sizing

Bad requests create bad architecture.

# 16. Quota design for HPA, VPA, and autoscaling

## 16.1 HPA and quota

HPA scales replicas, but quota can block new pods.

If quota does not allow HPA max replicas:

- Deployment may scale only partially.
- Pods may remain Pending or fail admission.
- Application may not meet load.

Design formula:

```text
Required quota = HPA max replicas × per-pod request + rollout surge + buffer
```

## 16.2 HPA CPU behavior

HPA CPU utilization uses CPU requests as a reference.

Example:

```text
Pod CPU request: 100m
Actual usage: 200m
HPA sees: 200%
```

If request is too low, HPA may over-scale.
If request is too high, HPA may under-scale.

## 16.3 Rolling update and quota

For a Deployment:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 25%
```

At max scale, extra surge pods consume extra quota.

Example:

```text
HPA max replicas: 20
maxSurge: 25%
Extra pods: 5
Quota must allow at least 25 pods worth of requests/limits
```

## 16.4 VPA and quota

VPA can recommend or update requests.

Quota impact:

- VPA may increase pod requests.
- Increased requests consume more quota.
- Pods may be blocked if namespace quota is too low.
- VPA recommendations should be reviewed against namespace budgets.

Design recommendation:

- Use VPA recommendation mode first.
- Review quota impact before enabling auto mode for critical workloads.
- Avoid VPA fighting with HPA on the same metric without careful design.

## 16.5 Cluster autoscaler interaction

Cluster autoscaler reacts to unschedulable pods that cannot fit on existing nodes.

Quota can block pod creation before scheduling. In that case, cluster autoscaler may not help because the pod never becomes schedulable/pending due to quota rejection.

Design point:

> Quota exhaustion and node capacity exhaustion are different failure modes. Monitor both.

# 17. Quota design with node sizing and capacity planning

Quota cannot be designed in isolation. It must align with node sizing.

## 17.1 Capacity planning inputs

Collect:

- Worker node count
- Worker node allocatable CPU/memory
- MachineConfigPool layout
- Infra node separation
- Storage backend capacity
- Platform component overhead
- Logging/monitoring overhead
- Upgrade drain requirement
- Failure domain requirement
- Cluster autoscaler limits
- Business unit demand
- Growth forecast

## 17.2 Capacity formula

```text
Tenant usable capacity = total allocatable - platform reserve - upgrade reserve - failure reserve - emergency buffer
```

Then allocate:

```text
Prod guaranteed budget
+ Stage budget
+ Non-prod shared budget
+ Sandbox budget
+ CI/CD budget
<= Tenant usable capacity × approved overcommit ratio
```

## 17.3 Node drain and upgrade headroom

During OpenShift upgrades or node maintenance, pods are drained and rescheduled.

Quota design must support:

- Extra pods during rollouts
- Rescheduling during node maintenance
- Zone failure if applicable
- Temporary duplicate workloads

If quota is too tight, maintenance can fail indirectly because new pods cannot be admitted.

## 17.4 Infra components

Do not apply tenant quota blindly to system namespaces such as:

- `openshift-*`
- `kube-*`
- `default`
- platform operator namespaces
- logging/monitoring namespaces
- ingress/router namespaces
- registry namespaces

Platform namespaces need a separate platform capacity policy.

# 23. Troubleshooting quota and limit issues

## 23.1 Pod rejected due to quota

Symptom:

```text
Error creating: pods "app-xxxxx" is forbidden: exceeded quota
```

Check:

```bash
oc describe quota -n <project>
oc get quota -n <project> -o yaml
oc get pods -n <project>
oc describe deployment <deployment> -n <project>
```

Common causes:

- CPU request quota full.
- Memory request quota full.
- Pod count quota full.
- PVC quota full.
- HPA scaled up and consumed quota.
- Rolling update surge exceeded quota.

Fix options:

- Reduce replicas.
- Reduce requests after validation.
- Clean unused objects.
- Increase quota through approval.
- Tune maxSurge.
- Tune HPA max replicas.

## 23.2 Pod rejected due to missing requests/limits

Symptom:

```text
failed quota: must specify requests.cpu, requests.memory
```

Check:

```bash
oc describe quota -n <project>
oc describe limitrange -n <project>
oc get pod <pod> -n <project> -o yaml
```

Fix:

- Add resources to deployment.
- Add or correct LimitRange defaults.

Example patch:

```bash
oc set resources deployment/myapp \
  --requests=cpu=200m,memory=256Mi \
  --limits=cpu=1,memory=1Gi \
  -n myproject
```

## 23.3 Pod Pending due to insufficient node resources

This is not necessarily quota.

Symptom:

```text
0/10 nodes are available: Insufficient cpu, Insufficient memory
```

Check:

```bash
oc describe pod <pod> -n <project>
oc adm top nodes
oc get nodes
oc describe node <node>
```

Explanation:

- Quota allowed pod creation.
- Scheduler cannot find a node with enough allocatable capacity.
- Need node capacity, lower requests, topology review, or autoscaler action.

## 23.4 OOMKilled due to memory limit

Check:

```bash
oc get pod <pod> -n <project>
oc describe pod <pod> -n <project>
oc logs <pod> -n <project> --previous
```

Possible fixes:

- Increase memory limit.
- Tune app memory usage.
- Tune JVM heap.
- Review memory leak.
- Increase memory request if steady usage is high.

## 23.5 CPU throttling due to CPU limit

Symptoms:

- High latency.
- Low average CPU but slow app.
- Throttling metrics high.

Check:

```bash
oc adm top pod -n <project>
oc describe pod <pod> -n <project>
```

Possible fixes:

- Increase CPU limit.
- Remove CPU limit only if enterprise policy allows.
- Increase CPU request.
- Use performance testing.
- Separate latency-sensitive workload onto dedicated node pool.

## 23.6 PVC rejected due to storage quota

Symptom:

```text
persistentvolumeclaims is forbidden: exceeded quota
```

Check:

```bash
oc describe quota -n <project>
oc get pvc -n <project>
oc describe pvc <pvc> -n <project>
```

Fix:

- Delete unused PVCs.
- Reduce requested size.
- Request quota increase.
- Use correct StorageClass.

## 23.7 ClusterResourceQuota exhaustion

Symptom:

- Local ResourceQuota appears available.
- New objects still fail.
- Error references cluster quota.

Check:

```bash
oc describe appliedclusterresourcequota -n <project>
oc describe clusterresourcequota <name>
```

Fix:

- Identify other namespaces consuming shared quota.
- Clean unused resources.
- Adjust team-level quota.
- Split ClusterResourceQuota if selector is too broad.

# 25. Common anti-patterns

## 25.1 No quotas in shared cluster

Impact:

- Any team can consume all resources.
- Cost control is weak.
- Troubleshooting noisy neighbors becomes reactive.

## 25.2 Quota without LimitRange

Impact:

- Pods missing requests/limits may be rejected.
- Developers get confusing errors.
- Defaults are inconsistent.

## 25.3 Same quota everywhere

Impact:

- Production may be under-provisioned.
- Sandbox may be over-provisioned.
- Cost and risk are not aligned with business criticality.

## 25.4 Too tight production quota

Impact:

- Rolling deployments fail.
- HPA cannot scale.
- Incident response is slowed.

## 25.5 Excessive CPU limits

Impact:

- Latency issues due to throttling.
- Poor performance despite available node CPU.

## 25.6 No object count quota

Impact:

- CI/CD loops can create many objects.
- API server and etcd pressure increases.

## 25.7 No storage quota

Impact:

- Storage backend fills up.
- Premium storage cost increases.
- Teams create oversized PVCs.

## 25.8 Large ClusterResourceQuota selector

Impact:

- Admission contention.
- Harder troubleshooting.
- Many active namespaces compete for one budget.

## 25.9 Quotas managed manually

Impact:

- Drift.
- No audit trail.
- Emergency changes are forgotten.
- Multi-cluster inconsistency.

## 25.10 Ignoring application behavior

Impact:

- JVM apps OOMKill due to wrong heap sizing.
- Batch jobs fail due to low ephemeral storage.
- APIs throttle due to low CPU limits.
- Databases suffer due to generic defaults.

# 27. Runbooks

## 27.1 Runbook: New production namespace quota

1. Collect app sizing.
2. Validate environment tier.
3. Confirm HPA max replicas.
4. Confirm deployment strategy and surge.
5. Confirm sidecars/init containers.
6. Confirm storage class and PVC requirements.
7. Calculate CPU/memory request quota.
8. Calculate CPU/memory limit quota.
9. Add object count quota.
10. Add storage quota.
11. Add ephemeral storage quota if needed.
12. Add LimitRange.
13. Commit YAML to Git.
14. Apply through GitOps.
15. Verify with `oc describe quota`.
16. Create alerts.
17. Review after production traffic.

## 27.2 Runbook: Quota exceeded during deployment

```bash
oc describe quota -n <project>
oc get events -n <project> --sort-by=.lastTimestamp
oc describe deployment <name> -n <project>
oc get rs -n <project>
oc get pods -n <project>
```

Decision tree:

```text
Is pod count quota full?
  → Reduce old ReplicaSets, tune rollout, or increase pod quota.

Is requests.cpu full?
  → Check HPA/maxSurge, reduce requests only if safe, or increase quota.

Is requests.memory full?
  → Check memory sizing, reduce replicas only if safe, or increase quota.

Is ClusterResourceQuota full?
  → Check other selected namespaces.

Is object count full?
  → Clean unused resources or increase object quota.
```

## 27.3 Runbook: OOMKilled application

```bash
oc describe pod <pod> -n <project>
oc logs <pod> -n <project> --previous
oc get pod <pod> -n <project> -o yaml | grep -A20 resources
oc adm top pod <pod> -n <project>
```

Actions:

- Verify memory limit.
- Compare with observed usage.
- Check application logs.
- Tune application memory.
- Increase memory limit if justified.
- Increase memory request if steady-state usage increased.

## 27.4 Runbook: CPU throttling suspected

```bash
oc adm top pod -n <project>
oc describe pod <pod> -n <project>
```

Monitoring checks:

- CPU throttled seconds
- Request vs actual usage
- Limit vs actual usage
- Latency/error rate correlation

Actions:

- Increase CPU limit.
- Increase CPU request.
- Tune thread pools.
- Consider dedicated nodes for latency-sensitive apps.

## 27.5 Runbook: Storage quota exceeded

```bash
oc describe quota -n <project>
oc get pvc -n <project>
oc describe pvc <pvc> -n <project>
```

Actions:

- Delete unused PVCs.
- Resize only if StorageClass supports it and approval exists.
- Move to lower-cost StorageClass if suitable.
- Increase quota with approval.

# 28. Interview and exam-focused notes

## 28.1 Simple explanation

`ResourceQuota` controls total resource consumption in a project. `LimitRange` controls default and allowed resource values for pods, containers, and PVCs inside a project.

## 28.2 Key difference

| ResourceQuota | LimitRange |
|---|---|
| Aggregate namespace/project limit | Per-object default and min/max control |
| Controls total CPU/memory/storage/object count | Controls individual container/pod/PVC requests and limits |
| Prevents namespace from consuming too much | Prevents bad individual resource specs |
| Example: max 10 pods | Example: each container max 2 CPU |

## 28.3 Important commands

```bash
oc create quota compute-quota \
  --hard=requests.cpu=2,limits.cpu=4,requests.memory=2Gi,limits.memory=4Gi,pods=10 \
  -n demo

oc get quota -n demo
oc describe quota compute-quota -n demo

oc get limitrange -n demo
oc describe limitrange -n demo

oc create clusterresourcequota team-quota \
  --project-label-selector=owner-team=payments \
  --hard=pods=100 \
  --hard=requests.cpu=20 \
  --hard=requests.memory=80Gi

oc describe appliedclusterresourcequota -n demo
```

## 28.4 Common exam/lab errors

| Error | Cause | Fix |
|---|---|---|
| Pod forbidden due to quota | ResourceQuota exceeded | Check `oc describe quota` |
| Must specify requests.cpu | Quota requires request but pod lacks it | Add resources or LimitRange default |
| Pod Pending insufficient CPU | Node capacity issue, not quota | Check node allocatable and pod request |
| PVC forbidden | PVC count or storage quota exceeded | Check PVC quota |
| HPA not scaling fully | Quota blocks new pods | Increase quota or reduce max replicas |
| Deployment rollout stuck | maxSurge exceeds quota | Increase quota or tune strategy |

## 28.5 Senior interview answer

In enterprise OpenShift, I do not design quotas only as YAML values. I start from cluster allocatable capacity, platform reserve, upgrade headroom, failure-domain assumptions, environment tiering, application SLOs, and HPA/rollout behavior. Then I map business-unit quota using ClusterResourceQuota where needed, namespace quota using ResourceQuota, and per-container defaults using LimitRange. I include CPU, memory, storage, ephemeral storage, object count, and route/service/PVC limits. I manage all of this with GitOps, monitor quota usage, alert at thresholds, and periodically review actual utilization against requested capacity.

## Final senior-level summary

Quota and limit design is not just an administrative task. It is an enterprise architecture control plane for capacity, reliability, security, cost, and multi-tenancy.

A mature OpenShift platform uses:

- `ResourceQuota` to control total namespace consumption.
- `LimitRange` to enforce safe defaults and per-object boundaries.
- `ClusterResourceQuota` to manage aggregate team-level consumption.
- Namespace labels to connect quota with ownership, cost center, and environment.
- GitOps to manage quota lifecycle.
- Monitoring to detect exhaustion before production impact.
- Review workflows to keep quotas aligned with real workload behavior.

For a 10+ years experienced OpenShift administrator, the key skill is not only creating quota YAML. The key skill is designing quota as part of enterprise capacity architecture, rollout safety, autoscaling, governance, and operational reliability.
