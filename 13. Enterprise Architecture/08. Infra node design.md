# Infra Node Design in Enterprise Architecture for Advanced OpenShift Administration

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and architects with production experience  
**Level:** 10+ years Linux/DevOps/OpenShift/Kubernetes operations  
**Scope:** OpenShift Container Platform 4.x, with examples aligned to current Red Hat OpenShift 4.22 documentation  
**Main idea:** Infra nodes are dedicated OpenShift nodes used to run platform-supporting workloads such as ingress/router, registry, monitoring, logging, GitOps, ACM, ACS, ODF, Quay, Pipelines, and service mesh control-plane components. They are designed to separate platform services from business application workloads.

---

## 1. What is an Infra Node?

An **infra node** is a compute node labeled for infrastructure workloads instead of normal application workloads.

In OpenShift, infra nodes are commonly labeled as:

```bash
node-role.kubernetes.io/infra=""
```

In cloud or virtualization environments where the Machine API is available, infra nodes are usually created from dedicated `MachineSet` objects. The MachineSet template normally labels the resulting node as infra and may add a taint so that normal user workloads cannot land there.

Example node role output:

```bash
oc get nodes
```

Expected style:

```text
NAME                         STATUS   ROLES          AGE   VERSION
master-0                     Ready    control-plane  20d   v1.x
worker-0                     Ready    worker         20d   v1.x
infra-0                      Ready    infra,worker   10d   v1.x
infra-1                      Ready    infra,worker   10d   v1.x
infra-2                      Ready    infra,worker   10d   v1.x
```

The `infra,worker` dual role is normal and recommended in many OpenShift 4 designs. The `infra` label communicates the subscription and placement intent. The `worker` label keeps the node managed by the default worker MachineConfigPool unless you deliberately create a custom infra MachineConfigPool.

## 2. Why Infra Node Design Matters in Enterprise Architecture

A production OpenShift cluster is not only application pods. It also runs critical platform services:

- ingress/router pods
- internal image registry
- monitoring stack
- Alertmanager
- Thanos Querier
- metrics components
- logging collectors and storage components
- GitOps controllers
- ACM hub components
- ACS central/scanner/sensor components
- service mesh control-plane components
- Quay registry components
- ODF/Ceph components, where appropriate

If these components run randomly on worker nodes, they compete with business applications for CPU, memory, network, storage I/O, and maintenance windows.

Infra node design gives the platform team a clean separation:

```text
Control Plane Nodes  -> Kubernetes/OpenShift API, etcd, controllers, scheduler
Infra Nodes          -> routers, registry, monitoring, logging, platform operators
Worker Nodes         -> end-user/business applications
Storage Nodes        -> optional dedicated ODF/Ceph or storage-heavy workloads
Special Nodes        -> GPU, high-performance, telco, edge, batch, database, etc.
```

The enterprise goal is not only cost optimization. A proper infra node design improves:

- availability of ingress traffic
- stability of cluster monitoring
- registry performance
- troubleshooting clarity
- capacity accounting
- maintenance isolation
- upgrade predictability
- subscription sizing discipline
- compliance separation between platform and app workloads
- operational ownership between platform, app, security, and network teams

## 3. Official OpenShift Infra Node Concept

OpenShift allows infrastructure machine sets to create machines that host infrastructure components such as:

- default router
- integrated container image registry
- cluster metrics
- monitoring components

Infra machines are not counted toward the total number of OpenShift subscriptions required for the environment, provided only eligible infrastructure workloads run on them.

Common eligible infrastructure workloads include:

- Kubernetes and OpenShift control plane services
- default router
- integrated image registry
- HAProxy-based Ingress Controller
- cluster metrics and monitoring services
- user-defined project monitoring components
- cluster aggregated logging
- Red Hat Quay
- Red Hat OpenShift Data Foundation
- Red Hat Advanced Cluster Management for Kubernetes
- Red Hat Advanced Cluster Security for Kubernetes
- Red Hat OpenShift GitOps
- Red Hat OpenShift Pipelines
- Red Hat OpenShift Service Mesh

Important rule:

> If a node runs business application pods or other non-infrastructure workloads, it becomes a worker node from a sizing and subscription perspective.

## 4. Infra Node Design Principles

### 4.1 Separate platform workloads from application workloads

The first design principle is separation of concern.

Infra workloads are platform workloads. They should not be affected by a noisy application deployment, a bad HPA event, an overloaded namespace, or a misconfigured application rollout.

Example problem without infra nodes:

```text
Application pods consume worker CPU
↓
Router pods also run on those workers
↓
Ingress latency increases
↓
All application teams complain because routes are slow
↓
Root cause looks like network problem, but actual issue is node resource contention
```

With infra nodes:

```text
Application overload impacts worker nodes
Router pods remain isolated on infra nodes
Monitoring still collects metrics
Registry remains available
Cluster operations remain stable
```

### 4.2 Use at least three infra nodes for production

For most production clusters, use **three infra nodes**. This allows:

- router pods to spread across failure domains
- monitoring components to survive node maintenance
- registry and logging components to have better availability
- one infra node to be drained while two remain active
- multi-AZ or multi-rack design

A two-infra-node design is possible for smaller environments, but it reduces maintenance flexibility. A one-infra-node design is not production-grade for shared enterprise platforms.

### 4.3 Use labels for placement and taints for protection

A label says:

```text
This node is suitable for infra workloads.
```

A taint says:

```text
Do not schedule normal workloads here unless they explicitly tolerate this node.
```

Typical infra label:

```bash
node-role.kubernetes.io/infra=""
```

Typical infra taint:

```bash
node-role.kubernetes.io/infra=reserved:NoSchedule
```

Apply it with:

```bash
oc adm taint nodes <infra-node-name> node-role.kubernetes.io/infra=reserved:NoSchedule
```

The platform component must then use a matching `nodeSelector` and `tolerations`.

### 4.4 Preserve the `worker` role unless you know why you are removing it

OpenShift commonly creates infra nodes with both `infra` and `worker` roles. This is not a mistake.

Recommended enterprise approach:

```text
Keep labels: infra,worker
Add taint: node-role.kubernetes.io/infra=reserved:NoSchedule
Move platform workloads using nodeSelector + tolerations
Prevent application workloads using taints
```

Do not remove the `worker` label casually. A node with a label other than `master/control-plane` or `worker` is not handled by the default MachineConfigPool unless a custom MCP is created. Removing `worker` often creates upgrade and configuration management surprises.

### 4.5 Design infra nodes as platform capacity, not spare worker capacity

Infra nodes are not a dumping ground for leftover VMs. They are part of the platform control architecture.

They need capacity planning for:

- number of routes
- ingress request rate
- TLS termination load
- registry pull/push volume
- monitoring metrics cardinality
- Prometheus retention
- Alertmanager load
- logging throughput
- GitOps sync frequency
- ACM managed cluster count
- ACS scan volume
- ODF/Ceph I/O, if placed there
- upgrade surge and rescheduling events

## 5. Infra Node Workload Placement Model

Infra node placement usually uses this pattern:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
```

For components that use the `nodePlacement` structure:

```yaml
nodePlacement:
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    value: reserved
    effect: NoSchedule
```

Different OpenShift Operators use different CR schemas. Always verify the exact field for the specific component and OpenShift version.

## 6. Infra Node Architecture Patterns

## 6.1 Small production cluster

Example:

```text
3 control-plane nodes
3 worker nodes
3 infra nodes
```

Use case:

- normal enterprise production
- moderate route count
- central monitoring
- internal registry
- limited logging

Design:

```text
master/control-plane: 3 nodes
infra:                3 nodes
worker:               3+ nodes
```

Recommended placement:

- IngressController on infra nodes
- image registry on infra nodes
- OpenShift monitoring on infra nodes
- logging collector DaemonSets everywhere, but logging back-end on infra/storage nodes
- GitOps/ACM/ACS operators on infra nodes where supported

## 6.2 Multi-zone cloud or virtualization cluster

Example:

```text
Zone A: infra-0, worker-a...
Zone B: infra-1, worker-b...
Zone C: infra-2, worker-c...
```

Design target:

```text
1 infra MachineSet per zone
1+ replica per infra MachineSet
router replicas spread across zones
external load balancer targets infra nodes only
monitoring uses anti-affinity where supported
```

Benefits:

- zone failure does not remove all routers
- maintenance can happen one zone at a time
- registry and monitoring components can be spread
- load balancer can target a stable infra node pool

## 6.3 Large enterprise platform

For large clusters, one infra pool might not be enough. Split infrastructure capacity by function.

Example labels:

```bash
node-role.kubernetes.io/infra=""
infra-role=ingress
infra-role=monitoring
infra-role=registry
infra-role=logging
```

Example node pools:

```text
infra-ingress     -> routers, external/internal ingress controllers
infra-monitoring  -> Prometheus, Alertmanager, Thanos, metrics components
infra-registry    -> internal image registry, Quay
infra-logging     -> Loki/Elasticsearch/OpenSearch/logging back-end, if used
storage           -> ODF/Ceph, if separated from infra
```

All infra nodes should still carry the infra role label if they are intended to count as infrastructure nodes:

```bash
node-role.kubernetes.io/infra=""
```

Then add more specific labels for scheduling:

```bash
oc label node infra-ingress-0 infra-role=ingress
oc label node infra-monitoring-0 infra-role=monitoring
```

Example IngressController placement:

```yaml
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
        infra-role: ingress
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
```

## 6.4 Bare-metal or UPI cluster

In user-provisioned infrastructure environments, especially when the cluster platform type is `none`, the Machine API might not be available. In that case, you normally:

1. Provision physical or virtual machines outside OpenShift.
2. Add them as worker nodes.
3. Label them as infra nodes.
4. Taint them.
5. Move platform workloads.
6. Update the external load balancer to target router pods on infra nodes.

Example:

```bash
oc label node worker-bm-03 node-role.kubernetes.io/infra=""
oc adm taint nodes worker-bm-03 node-role.kubernetes.io/infra=reserved:NoSchedule
```

Bare-metal design needs special attention to:

- static IPs or stable DHCP reservations for router nodes
- external load balancer pool membership
- wildcard DNS for `*.apps.<cluster-domain>`
- NIC bonding
- VLAN separation
- storage network bandwidth
- rack-level failure domains
- out-of-band management access

## 6.5 VMware vSphere design

For vSphere, infra nodes are usually created by a dedicated infra MachineSet or by cloning/modifying an existing worker MachineSet.

Design recommendations:

- place infra VMs across different ESXi hosts
- use DRS anti-affinity rules where possible
- keep infra VM sizing consistent
- avoid datastore contention with app/database VMs
- ensure router nodes are reachable from the external load balancer
- use infra MachineSets for repeatable provisioning where Machine API is supported
- use dedicated resource pools if the organization uses vSphere resource governance

## 7. MachineSet-Based Infra Node Creation

## 7.1 Check whether Machine API is available

```bash
oc get infrastructure cluster -o jsonpath='{.status.platform}{"\n"}'
oc get machinesets -n openshift-machine-api
```

If the platform is `none`, advanced Machine API features are not available. If MachineSets exist and are healthy, you can use the Machine API approach.

## 7.2 Discover existing worker MachineSets

```bash
oc get machinesets -n openshift-machine-api
```

Example:

```text
NAME                                 DESIRED   CURRENT   READY   AVAILABLE
ocp4-worker-us-east-1a               2         2         2       2
ocp4-worker-us-east-1b               2         2         2       2
ocp4-worker-us-east-1c               2         2         2       2
```

Export one worker MachineSet as a starting point:

```bash
oc get machineset ocp4-worker-us-east-1a \
  -n openshift-machine-api \
  -o yaml > infra-us-east-1a.yaml
```

Clean generated fields:

```bash
# Remove fields such as status, uid, resourceVersion, generation, creationTimestamp, managedFields.
```

Change the name and labels:

```yaml
metadata:
  name: ocp4-infra-us-east-1a
  namespace: openshift-machine-api
  labels:
    machine.openshift.io/cluster-api-machine-role: infra
    machine.openshift.io/cluster-api-machine-type: infra
spec:
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-machineset: ocp4-infra-us-east-1a
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machine-role: infra
        machine.openshift.io/cluster-api-machine-type: infra
        machine.openshift.io/cluster-api-machineset: ocp4-infra-us-east-1a
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
      taints:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
```

Create it:

```bash
oc create -f infra-us-east-1a.yaml
```

Verify:

```bash
oc get machineset -n openshift-machine-api
oc get machines -n openshift-machine-api
oc get nodes -l node-role.kubernetes.io/infra=
oc describe node <infra-node-name> | egrep -i 'roles|taints|labels'
```

## 7.3 Recommended MachineSet layout

For a three-zone cloud cluster:

```text
infra-a MachineSet -> zone A -> replicas: 1
infra-b MachineSet -> zone B -> replicas: 1
infra-c MachineSet -> zone C -> replicas: 1
```

For higher ingress or monitoring load:

```text
infra-a MachineSet -> zone A -> replicas: 2
infra-b MachineSet -> zone B -> replicas: 2
infra-c MachineSet -> zone C -> replicas: 2
```

For bare-metal or non-Machine API environments, use manual node labeling and external infrastructure automation instead of MachineSets.

## 8. Manual Infra Node Creation

Use this approach when:

- Machine API is not available
- cluster was installed with platform type `none`
- you are using bare metal without MachineSets
- nodes are provisioned by an external CMDB/VMware/Ansible process

Label node:

```bash
oc label node <node-name> node-role.kubernetes.io/infra=""
```

Taint node:

```bash
oc adm taint node <node-name> node-role.kubernetes.io/infra=reserved:NoSchedule
```

Verify:

```bash
oc get nodes
oc describe node <node-name> | grep -i Taints -A3
oc get nodes -l node-role.kubernetes.io/infra=
```

Remove taint if needed:

```bash
oc adm taint node <node-name> node-role.kubernetes.io/infra=reserved:NoSchedule-
```

Remove label if needed:

```bash
oc label node <node-name> node-role.kubernetes.io/infra-
```

## 9. MachineConfigPool Design for Infra Nodes

A MachineConfigPool controls RHCOS-level configuration for selected nodes.

You do **not** always need a custom infra MCP.

Use default worker MCP when:

- infra nodes still have `worker` label
- no infra-specific OS-level config is needed
- you want simple upgrades
- you only need scheduling isolation

Create custom infra MCP when:

- you remove the `worker` role from infra nodes
- infra nodes need specific OS/kernel/kubelet config
- infra nodes require different sysctl, chrony, CRI-O, or file configuration
- you need a separate reboot/update rollout policy

Example infra MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Apply:

```bash
oc create -f infra-mcp.yaml
```

Verify:

```bash
oc get mcp
oc get machineconfig | grep infra
oc describe mcp infra
```

Important design note:

```text
Custom MCPs inherit worker MachineConfigs when configured with worker + infra selector.
Changes to worker pool can still affect infra pool.
Dedicated infra MachineConfigs should use:
machineconfiguration.openshift.io/role: infra
```

Example infra-only MachineConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 51-infra-custom
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
      - path: /etc/infra-node-purpose
        mode: 0644
        contents:
          source: data:,infra
```

## 10. Moving OpenShift Router / Ingress to Infra Nodes

The router is one of the most important infra workloads. It handles application traffic through OpenShift Routes.

Check current IngressController:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

Edit:

```bash
oc edit ingresscontroller default -n openshift-ingress-operator
```

Add node placement:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
```

Verify router pods:

```bash
oc get pods -n openshift-ingress -o wide
oc get node <router-node-name>
```

Expected node role:

```text
ROLES
infra,worker
```

Enterprise architecture notes:

- External load balancers should target infra nodes that run router pods.
- DNS wildcard `*.apps.<cluster-domain>` should point to the load balancer VIP/FQDN.
- For bare metal, ensure infra nodes have stable addresses or stable load balancer backends.
- For internal/external traffic separation, create separate IngressControllers and place them on different infra node pools.

Example dedicated external router:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: external
  namespace: openshift-ingress-operator
spec:
  domain: apps.example.com
  replicas: 3
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
        infra-role: ingress-external
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
```

Example dedicated internal router:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: internal
  namespace: openshift-ingress-operator
spec:
  domain: internal.apps.example.com
  replicas: 3
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
        infra-role: ingress-internal
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
```

## 11. Moving the Internal Image Registry to Infra Nodes

Check registry status:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
oc get pods -n openshift-image-registry -o wide
```

Edit:

```bash
oc edit configs.imageregistry.operator.openshift.io/cluster
```

Example placement:

```yaml
apiVersion: imageregistry.operator.openshift.io/v1
kind: Config
metadata:
  name: cluster
spec:
  managementState: Managed
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    value: reserved
    effect: NoSchedule
```

Verify:

```bash
oc get pods -n openshift-image-registry -o wide
oc describe node <registry-pod-node> | grep node-role.kubernetes.io/infra
```

Registry design considerations:

- Use object storage where supported for better durability.
- Avoid placing a high-throughput registry on small infra nodes.
- Registry traffic can be heavy during mass deployments, CI/CD bursts, and upgrades.
- In disconnected clusters, registry/mirror design is more important than simple pod placement.
- If the registry uses PVC-backed storage, understand zone affinity and storage class behavior.

## 13. Moving Operator-Managed Components

Some Operator Lifecycle Manager workloads can be moved by editing the `Subscription` CR:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-namespace
spec:
  config:
    nodeSelector:
      node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
```

However, not every Operator supports moving all operand pods the same way. Some Operators require a product-specific custom resource field.

Enterprise approach:

```text
Operator pod placement         -> often Subscription spec.config
Operand/application placement  -> product-specific CR field
DaemonSet placement            -> depends on operator ownership
Control-plane placement        -> often restricted or product-specific
```

Always verify:

```bash
oc get subscription -A
oc get csv -A
oc get pods -n <operator-namespace> -o wide
oc explain <kind>.spec
```

## 14. Infra Node Sizing

Red Hat provides infrastructure node sizing guidance based on cluster density testing where monitoring and default ingress were moved to infra nodes.

Reference sizing table:

| Worker nodes | Cluster density / namespaces | Infra node CPU cores | Infra node memory |
|---:|---:|---:|---:|
| 27 | 500 | 4 | 24 GB |
| 120 | 1000 | 8 | 48 GB |
| 252 | 4000 | 16 | 128 GB |
| 501 | 4000 | 32 | 128 GB |

General recommendation:

```text
Use three infra nodes per production cluster.
```

Important sizing notes:

- Treat official sizing as a starting point, not a final answer.
- Prometheus can be memory-heavy.
- Router usage depends on route count, TLS termination, request rate, and connection patterns.
- Registry usage depends on image pull/push rate and storage backend.
- Logging can dominate CPU, memory, disk, and network if placed on infra nodes.
- ACM hub, ACS, GitOps, Service Mesh, and ODF can require additional dedicated sizing.

Practical enterprise sizing model:

```text
Base infra capacity
+ ingress request capacity
+ route count growth
+ monitoring cardinality growth
+ registry throughput
+ logging throughput
+ operator/control workload growth
+ upgrade headroom
+ node failure headroom
= final infra node design
```

## 14.1 Sizing examples

### Small production

```text
3 infra nodes
4 vCPU each
24 GB RAM each
```

Suitable for:

- modest number of namespaces
- default monitoring
- default ingress
- internal registry with moderate use

### Medium enterprise

```text
3 infra nodes
8 vCPU each
48 GB RAM each
```

Suitable for:

- many teams
- more routes
- user workload monitoring enabled
- GitOps and ACS agents
- moderate logging

### Large enterprise

```text
3 to 9+ infra nodes
16-32 vCPU each
64-128+ GB RAM each
Separate pools for ingress, monitoring, registry, logging, and hub services
```

Suitable for:

- high namespace density
- heavy Prometheus load
- large GitOps fleet
- ACM hub cluster
- ACS central
- high traffic ingress
- central logging back-end

## 15. Network Design for Infra Nodes

Infra nodes are often the entry point for external traffic.

Key network components:

```text
Client
  ↓
DNS wildcard: *.apps.cluster.example.com
  ↓
External Load Balancer / Cloud LB / F5 / HAProxy / MetalLB
  ↓
Router pods on infra nodes
  ↓
Service
  ↓
Application pod on worker node
```

## 15.1 Load balancer design

For production:

- LB backend pool should include router-capable infra nodes.
- Health checks should target router health endpoints or relevant ports.
- Router pods should be spread across infra nodes.
- Do not leave old worker nodes in the router LB pool after moving routers to infra nodes.
- For cloud LBs, ensure security groups/NACLs allow ingress to infra nodes.
- For bare metal, ensure F5/HAProxy/keepalived/MetalLB design is stable.

## 15.2 DNS design

Typical records:

```text
api.cluster.example.com       -> API load balancer
api-int.cluster.example.com   -> internal API load balancer
*.apps.cluster.example.com    -> router/ingress load balancer
```

When routers move to infra nodes, DNS usually does not change if the load balancer VIP remains the same. The load balancer backend pool changes.

## 15.3 Ingress sharding

For large environments, create multiple IngressControllers:

```text
default ingress    -> common apps
internal ingress   -> internal-only routes
external ingress   -> public apps
pci ingress        -> PCI namespace selector
dev ingress        -> development route selector
```

Placement can be controlled with infra labels:

```bash
oc label node infra-0 infra-role=ingress-external
oc label node infra-1 infra-role=ingress-external
oc label node infra-2 infra-role=ingress-external
```

Then the IngressController uses:

```yaml
nodePlacement:
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
      infra-role: ingress-external
```

## 16. Storage Design for Infra Nodes

Infra nodes may host storage-consuming components:

- image registry
- monitoring Prometheus PVCs
- Alertmanager data
- logging stack
- Quay registry
- ACS Central database
- ACM observability
- ODF/Ceph components, if designed that way

Storage design questions:

1. Is the component stateless or stateful?
2. Does it require local disk, block storage, file storage, or object storage?
3. Is storage zone-aware?
4. Can the component tolerate node drain?
5. Does storage follow the pod across nodes?
6. What is the IOPS requirement?
7. Is backup required?
8. Does the component need encryption at rest?
9. Does the storage class use `WaitForFirstConsumer`?
10. Will nodeSelector conflict with storage topology?

Example problem:

```text
Prometheus PVC is bound to zone A
Prometheus pod has nodeSelector for infra-role=monitoring
Only infra monitoring nodes are in zone B/C
Pod remains Pending due to volume node affinity conflict
```

Design fix:

```text
Place monitoring infra nodes across storage zones
Use proper StorageClass topology
Ensure StatefulSet replicas have valid placement options
```

## 17. Security and Compliance Design

Infra nodes are high-value platform nodes.

Security controls:

- prevent user workloads with taints
- restrict who can edit infra MachineSets
- restrict who can label/taint nodes
- restrict who can change IngressController, registry, and monitoring placement
- monitor infra nodes separately
- alert if user namespaces schedule pods on infra nodes
- use RBAC separation for platform admins vs project admins
- use audit logs for node label, taint, MachineSet, and operator CR changes
- apply consistent patch/upgrade windows
- keep router certificates and wildcard cert lifecycle controlled
- ensure registry trust and pull-secret design is secure

Useful check for non-platform pods on infra nodes:

```bash
for n in $(oc get nodes -l node-role.kubernetes.io/infra= -o name | cut -d/ -f2); do
  echo "### $n"
  oc get pods -A -o wide --field-selector spec.nodeName=$n
 done
```

Then inspect namespaces. Application namespaces should normally not run on infra nodes.

## 18. Upgrade and Maintenance Design

Infra nodes must be maintained carefully because they run shared platform services.

Before maintenance:

```bash
oc get clusterversion
oc get clusteroperators
oc get mcp
oc get nodes
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-monitoring -o wide
oc get pods -n openshift-image-registry -o wide
```

Graceful node maintenance pattern:

```bash
oc adm cordon <infra-node>
oc adm drain <infra-node> \
  --ignore-daemonsets \
  --delete-emptydir-data \
  --grace-period=60 \
  --timeout=10m

# perform maintenance / reboot

oc adm uncordon <infra-node>
```

Check recovery:

```bash
oc get nodes
oc get pods -A -o wide --field-selector spec.nodeName=<infra-node>
oc get clusteroperators
```

Router-specific considerations:

- Ensure enough router replicas exist before draining.
- Check load balancer health before and after drain.
- Use PodDisruptionBudgets where supported.
- Drain one infra node at a time.
- Confirm route traffic still works.

Monitoring-specific considerations:

- Prometheus restart can take time depending on WAL and retention.
- Alertmanager quorum and availability should be checked.
- If monitoring is unavailable, platform troubleshooting becomes harder.

Registry-specific considerations:

- Registry outage can block new deployments if images must be pulled from the internal registry.
- CI/CD pipelines can fail during registry disruption.
- Check storage attachment before deleting registry pods.

## 19. Infra Node Autoscaling

Infra nodes can be autoscaled with MachineAutoscaler in Machine API-supported environments, but this must be designed carefully.

Autoscaling is useful for:

- bursty ingress workloads
- GitOps/CI platform components
- non-stateful infra workloads

Autoscaling is risky for:

- monitoring with PVCs
- registry with local/PVC storage
- logging back-ends
- ODF/Ceph
- workloads needing stable load balancer backend registration

Recommended approach:

```text
Use fixed-size infra node pools for core services.
Use autoscaling only for clearly stateless or horizontally scalable infra pools.
```

Do not autoscale infra nodes blindly just because worker nodes autoscale.

## 22. Troubleshooting Infra Node Issues

## 22.1 Infra pod stuck Pending

Common causes:

- nodeSelector does not match any node
- node has taint but pod lacks toleration
- PVC zone affinity conflict
- insufficient CPU or memory
- PodDisruptionBudget blocks movement
- topology spread or anti-affinity prevents placement
- operator does not support requested placement field

Commands:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
oc get nodes --show-labels | grep infra
oc describe node <infra-node>
```

Look for messages like:

```text
0/6 nodes are available: 3 node(s) didn't match Pod's node affinity/selector, 3 node(s) had untolerated taint.
```

## 22.2 Router did not move to infra node

Check:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get pods -n openshift-ingress -o wide
oc describe pod <router-pod> -n openshift-ingress
oc get nodes -l node-role.kubernetes.io/infra=
```

Possible issues:

- `nodePlacement` placed under wrong YAML level
- toleration missing
- infra node label typo
- router replica count greater than schedulable infra nodes with host port constraints
- LB still targeting old worker nodes

## 22.3 Registry did not move

Check:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
oc get pods -n openshift-image-registry -o wide
oc logs -n openshift-image-registry deployment/image-registry
```

Possible issues:

- wrong field for OpenShift version
- PVC topology conflict
- registry operator degraded
- missing toleration
- infra node insufficient resources

## 22.4 Monitoring did not move

Check:

```bash
oc get configmap cluster-monitoring-config -n openshift-monitoring -o yaml
oc get pods -n openshift-monitoring -o wide
oc get clusteroperator monitoring
oc describe pod <monitoring-pod> -n openshift-monitoring
```

Possible issues:

- invalid YAML inside `config.yaml`
- missing tolerations for one component
- Prometheus PVC stuck in one zone
- operator has not reconciled yet
- component needs pod deletion to be recreated

## 22.5 Infra node shows `SchedulingDisabled`

Check:

```bash
oc get node <node>
oc describe node <node>
```

Uncordon:

```bash
oc adm uncordon <node>
```

## 22.6 MachineConfigPool degraded

Check:

```bash
oc get mcp
oc describe mcp infra
oc get nodes
oc logs -n openshift-machine-config-operator daemonset/machine-config-daemon -c machine-config-daemon
```

Common causes:

- bad MachineConfig
- rendered config mismatch
- node failed to reboot
- custom MCP selector conflict
- removed worker label without correct MCP

## 23. Anti-Patterns

Avoid these designs:

### Anti-pattern 1: Infra label without taint

Problem:

```text
Application pods can still schedule on infra nodes.
```

Correct design:

```bash
oc adm taint nodes <node> node-role.kubernetes.io/infra=reserved:NoSchedule
```

### Anti-pattern 2: Removing worker label too early

Problem:

```text
MCO may not manage the node unless a custom MCP exists.
```

Correct design:

```text
Keep infra,worker labels and use taints/tolerations.
Create custom MCP only when required.
```

### Anti-pattern 3: Single infra node

Problem:

```text
Router, registry, or monitoring becomes a single maintenance and failure point.
```

Correct design:

```text
Use three infra nodes for production.
```

### Anti-pattern 4: Moving router but not updating load balancer

Problem:

```text
Traffic still goes to old worker nodes or unhealthy backends.
```

Correct design:

```text
Ensure LB backend pool targets active router infra nodes.
```

### Anti-pattern 5: Cluster-wide default node selector to infra

Problem:

```text
Normal pods may become unschedulable.
Some platform pods may conflict with existing selectors.
```

Correct design:

```text
Use component-specific nodePlacement or namespace/project node selectors.
```

### Anti-pattern 6: Placing heavy monitoring, logging, registry, ingress, and ODF on tiny infra nodes

Problem:

```text
Infra nodes become bottlenecks and platform services become unstable.
```

Correct design:

```text
Size each infra pool based on workload profile.
Separate high-I/O and high-memory services when required.
```

### Anti-pattern 7: Assuming all Operators support infra placement

Problem:

```text
Some Operator or operand pods ignore Subscription nodeSelector or require product-specific fields.
```

Correct design:

```text
Check Operator documentation and CR schema.
Validate actual pod placement.
```

## 25. Interview and Real-World Explanation

A strong 10-year-experience answer:

> In production OpenShift, I design infra nodes as a dedicated platform services layer. I normally create three infra nodes across zones or racks, label them with `node-role.kubernetes.io/infra`, preserve the worker role unless I need a custom MCP, and apply a `NoSchedule` taint so business workloads cannot land there. Then I move router, registry, monitoring, and supported platform operators using node selectors and tolerations. I also align load balancer backend pools, storage topology, monitoring capacity, and upgrade runbooks with the infra node design. For large environments, I split infra pools by function, such as ingress, monitoring, registry, logging, and ACM/ACS/GitOps, because ingress is network-heavy, Prometheus is memory-heavy, registry is storage/network-heavy, and logging can be I/O-heavy. My validation is not just `oc get nodes`; I verify actual pod placement, taints, tolerations, MachineSet health, MCP health, cluster operators, route availability, registry pull/push behavior, and alerting health.

```bash
for n in <node-a> <node-b> <node-c>; do
```

### Step 4: Verify infra nodes

```bash
oc get nodes -l node-role.kubernetes.io/infra=
```

```bash
oc edit ingresscontroller default -n openshift-ingress-operator
```

Add:

```yaml
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
```

```yaml
spec:

    value: reserved
    effect: NoSchedule
```

## 27. Final Design Summary

Infra node design is a platform architecture decision, not just an `oc label node` task.

A good design answers:

```text
Which platform workloads should run on infra nodes?
How many infra nodes are required?
Which zones/racks should they span?
How are labels and taints enforced?
How do router, registry, and monitoring move safely?
How does the load balancer know about router infra nodes?
How are storage topology and PVCs handled?
How are MachineSets and MCPs managed?
How do upgrades and reboots happen without outage?
How do we prove that no user workloads are running on infra nodes?
```

For an advanced OpenShift administrator, the expected mindset is:

```text
Design infra nodes for isolation, availability, scaling, troubleshooting, subscription clarity, and operational safety.
Do not treat infra nodes as spare workers.
```
