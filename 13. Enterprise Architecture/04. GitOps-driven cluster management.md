# GitOps-driven Cluster Management in Enterprise Architecture

**Audience:** Advanced OpenShift Administration / Senior OpenShift Platform Engineer / 10+ years infrastructure experience  
**Focus:** Enterprise architecture, OpenShift GitOps, Argo CD, ACM hub-spoke operations, cluster configuration, security, governance, drift control, and day-2 operations  
**File type:** Single Markdown study guide  

---

## 1. Executive Summary

GitOps-driven cluster management means managing OpenShift cluster configuration, platform add-ons, security policy, application delivery, and operational standards through declarative files stored in Git. Git becomes the **source of truth**, and tools such as **Red Hat OpenShift GitOps**, **Argo CD**, and **Red Hat Advanced Cluster Management for Kubernetes** continuously reconcile the actual cluster state with the desired state declared in repositories.

For an enterprise OpenShift administrator, GitOps is not only a deployment method. It is an operating model for managing many clusters safely, repeatedly, and auditably. Instead of applying changes manually with `oc apply`, console edits, or one-time shell scripts, platform teams define desired state as code, review it through pull requests, validate it through CI, and let controllers apply it consistently.

In a mature enterprise architecture, GitOps usually manages:

- Cluster bootstrap configuration
- Namespace/project standards
- RBAC and team access
- ResourceQuota and LimitRange
- NetworkPolicy
- Operator subscriptions
- Ingress/router configuration
- Cluster monitoring configuration
- Compliance policies
- Security controls
- Application deployments
- Environment-specific overlays
- Disaster recovery manifests
- Day-2 operational drift correction

The biggest value is not automation alone. The real value is **governed automation**: every change is reviewed, versioned, traceable, reversible, and continuously reconciled.

## 2. What GitOps-driven Cluster Management Means

GitOps-driven cluster management is the practice of declaring cluster state in Git and using a reconciliation engine to apply and maintain that state on one or more OpenShift clusters.

A simple definition:

> GitOps-driven cluster management is a declarative operating model where Git stores the intended cluster configuration and controllers continuously compare, apply, and correct the live OpenShift state.

In traditional administration, an engineer executes commands:

```bash
oc create namespace payments
oc adm policy add-role-to-user edit alice -n payments
oc apply -f networkpolicy.yaml
oc apply -f quota.yaml
```

In GitOps-driven administration, the engineer commits YAML files:

```text
clusters/prod/apps/payments/namespace.yaml
clusters/prod/apps/payments/rbac.yaml
clusters/prod/apps/payments/networkpolicy.yaml
clusters/prod/apps/payments/quota.yaml
```

Then Argo CD/OpenShift GitOps reconciles those manifests into the cluster.

The difference is architectural:

| Area | Traditional admin model | GitOps-driven model |
|---|---|---|
| Source of truth | Human memory, tickets, scripts, live cluster | Git repository |
| Change process | Manual command execution | Pull request + review + merge |
| Audit | Shell history, cluster events, ticket notes | Git history + PR approval + Argo CD sync history |
| Drift handling | Detected manually | Continuously detected by controller |
| Rollback | Manual rework | Git revert + sync |
| Multi-cluster consistency | Difficult | Template/generator based |
| Compliance evidence | Manual collection | Git, policy, sync, and audit records |

## 3. Why GitOps Matters in Enterprise OpenShift Architecture

Enterprise OpenShift environments usually contain multiple clusters across development, testing, staging, production, disaster recovery, edge, and cloud regions. Manual administration does not scale well across such environments.

GitOps solves several enterprise problems.

### 3.1 Consistency Across Clusters

Large organizations often run many clusters:

```text
hub-cluster
├── dev-cluster-01
├── test-cluster-01
├── stage-cluster-01
├── prod-cluster-01
├── prod-cluster-02
└── dr-cluster-01
```

Without GitOps, every cluster slowly becomes different. One cluster has a missing NetworkPolicy, another has a different quota, another has a manually changed OAuth setting, and another has an old Operator channel.

GitOps reduces configuration snowflakes by declaring common standards once and applying them repeatedly.

### 3.2 Auditability

Every enterprise production change should answer:

- Who changed it?
- Why was it changed?
- Who approved it?
- What exact configuration changed?
- Which clusters received the change?
- When was it applied?
- Can it be rolled back?

GitOps answers these through Git commit history, pull requests, branch protection, Argo CD sync history, and cluster audit logs.

### 3.3 Faster Recovery

If a cluster is lost or rebuilt, GitOps helps restore desired platform configuration quickly:

1. Install or bootstrap OpenShift.
2. Install OpenShift GitOps/ACM tooling.
3. Register the cluster.
4. Apply the root/bootstrap application.
5. Let the reconciler restore cluster configuration and platform add-ons.

This does not replace etcd backup, persistent volume backup, or application data recovery. GitOps restores **configuration state**, not all runtime data.

### 3.4 Separation of Duties

GitOps enables role separation:

| Role | Responsibility |
|---|---|
| Platform architect | Defines repository model and cluster standards |
| OpenShift admin | Maintains cluster configuration and add-ons |
| Security team | Reviews policy, RBAC, NetworkPolicy, SCC usage |
| Developer team | Owns application manifests and overlays |
| Release manager | Controls promotion between environments |
| SRE team | Observes health, drift, and rollback |

### 3.5 Reduced Manual Error

Manual cluster commands are powerful but risky. A command run against the wrong namespace or cluster can cause outage. GitOps does not eliminate risk, but it moves risk into reviewable code before the change reaches the cluster.

## 4. Core GitOps Principles

A mature GitOps model follows four practical principles.

### 4.1 Declarative Configuration

Everything that can be expressed declaratively should be stored as YAML, Helm values, Kustomize overlays, or policy definitions.

Examples:

- `Namespace`
- `RoleBinding`
- `ResourceQuota`
- `LimitRange`
- `NetworkPolicy`
- `Subscription`
- `OperatorGroup`
- `MachineConfig`
- `ConfigMap`
- `Secret` references
- `Deployment`
- `Route`
- `ServiceMonitor`
- `Application`
- `ApplicationSet`
- ACM `Policy`

### 4.2 Versioned and Immutable History

Changes are made through commits. A commit provides a durable record of what changed.

Good commit message:

```text
platform: add default quota and network policy for payments namespace
```

Poor commit message:

```text
fix yaml
```

For enterprise teams, commit messages should map to tickets, change records, or incident IDs:

```text
CHG0042187: update prod ingress certificate secret reference
INC0037819: rollback payments HPA maxReplicas to 10
```

### 4.3 Automated Reconciliation

A GitOps controller watches Git and the cluster. When Git and cluster state differ, the controller shows `OutOfSync` and can sync manually or automatically.

For critical cluster configuration, many organizations use:

- Automatic sync for low-risk baseline resources
- Manual sync for high-risk production changes
- Sync windows for restricted change periods
- Sync waves for ordered rollout
- Prune protection for sensitive resources

### 4.4 Drift Detection and Correction

Drift means the live cluster state no longer matches Git.

Example drift:

```bash
oc scale deployment payments-api --replicas=10 -n payments
```

If Git says replicas should be `3`, Argo CD detects the difference. With self-heal enabled, it restores the desired value.

Drift is not always bad. During incident handling, temporary manual changes may be required. The important point is that drift should be visible, controlled, and resolved.

## 5. Key Components in OpenShift GitOps Architecture

### 5.1 Git Repository

Git stores the desired state. Enterprise teams usually separate repositories by concern:

```text
gitops-platform-config
├── clusters
├── bootstrap
├── operators
├── namespaces
├── policies
├── networking
├── security
└── observability

gitops-apps
├── payments
├── inventory
├── crm
└── shared-services
```

Some enterprises use a mono-repo, others use multiple repos. Both can work. The decision depends on team boundaries, compliance rules, and ownership.

### 5.2 CI System

CI validates changes before merge.

Common validation checks:

```bash
yamllint .
kubeconform -summary manifests/
kustomize build overlays/prod
helm template chart/ -f values-prod.yaml
conftest test manifests/ --policy policy/
oc apply --dry-run=server -f rendered.yaml
```

CI should not directly deploy to production clusters in a mature GitOps model. CI should validate and update Git. The GitOps controller should deploy.

### 5.3 OpenShift GitOps Operator

Red Hat OpenShift GitOps provides Argo CD as an Operator-managed service inside OpenShift. It is commonly installed in the `openshift-gitops` namespace. The Operator manages Argo CD components such as the API server, repo server, application controller, Dex/SSO integration, Redis, and route.

Important components:

| Component | Purpose |
|---|---|
| `argocd-server` | API and UI |
| `argocd-repo-server` | Fetches Git/Helm/Kustomize content and renders manifests |
| `argocd-application-controller` | Compares desired and live state, performs sync |
| `argocd-redis` | Cache/state coordination |
| `dex` or OpenShift OAuth integration | Authentication |
| `Application` CR | Represents one deployable desired-state unit |
| `ApplicationSet` CR | Generates multiple Applications from templates |
| `AppProject` CR | Security and tenancy boundary |

### 5.4 Argo CD Application

An `Application` maps a Git source to a destination cluster and namespace.

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-dev
  namespace: openshift-gitops
spec:
  project: platform-apps
  source:
    repoURL: https://git.example.com/platform/gitops-apps.git
    targetRevision: main
    path: payments/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Key fields:

| Field | Meaning |
|---|---|
| `source.repoURL` | Git repository URL |
| `source.targetRevision` | Branch, tag, or commit |
| `source.path` | Directory containing manifests/chart/kustomization |
| `destination.server` | Target Kubernetes API server |
| `destination.namespace` | Target namespace |
| `project` | AppProject security boundary |
| `syncPolicy` | How sync is performed |

### 5.5 ApplicationSet

`ApplicationSet` generates many Argo CD Applications from one template. It is very important in multicluster OpenShift architecture.

Use cases:

- Deploy same baseline add-ons to every cluster
- Deploy environment-specific overlays
- Deploy cluster-specific configuration from a cluster inventory file
- Deploy applications to only clusters with matching labels
- Manage hub-spoke clusters through cluster generators

Example ApplicationSet using cluster generator:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-baseline
  namespace: openshift-gitops
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            platform.example.com/baseline: enabled
  template:
    metadata:
      name: '{{name}}-baseline'
    spec:
      project: cluster-config
      source:
        repoURL: https://git.example.com/platform/cluster-config.git
        targetRevision: main
        path: clusters/{{name}}/baseline
      destination:
        server: '{{server}}'
        namespace: openshift-gitops
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

### 5.6 AppProject

`AppProject` provides security boundaries around Applications.

It controls:

- Which repositories are allowed
- Which destination clusters are allowed
- Which destination namespaces are allowed
- Which resource kinds are allowed or denied
- Which users/groups can sync or update applications

Example:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: platform-config
  namespace: openshift-gitops
spec:
  description: Platform-owned cluster configuration
  sourceRepos:
    - https://git.example.com/platform/cluster-config.git
  destinations:
    - namespace: '*'
      server: https://kubernetes.default.svc
  clusterResourceWhitelist:
    - group: '*'
      kind: '*'
  namespaceResourceWhitelist:
    - group: '*'
      kind: '*'
```

For application teams, do not grant broad cluster-scoped permissions unless required.

## 6. Enterprise Reference Architecture

A typical enterprise GitOps architecture for OpenShift looks like this:

```text
Developers / Platform Engineers
        |
        v
Pull Request + Review + CI Validation
        |
        v
Git Repository: Desired State
        |
        v
OpenShift GitOps / Argo CD
        |
        +-------------------+-------------------+
        |                   |                   |
        v                   v                   v
 dev cluster           stage cluster          prod cluster
        |                   |                   |
        v                   v                   v
Namespaces, RBAC, Operators, NetworkPolicy, Apps, Monitoring, Policies
```

For multicluster governance, Red Hat Advanced Cluster Management often sits beside GitOps:

```text
               Git Repositories
                     |
                     v
          Hub Cluster / Management Plane
        +--------------------------------+
        | OpenShift GitOps / Argo CD     |
        | ACM Cluster Management         |
        | ACM Governance Policies        |
        | Observability                  |
        +--------------------------------+
             |          |          |
             v          v          v
       spoke-dev   spoke-stage   spoke-prod
```

### 6.1 Control Plane Cluster

Some enterprises dedicate a management or hub cluster to platform operations. It hosts:

- Red Hat Advanced Cluster Management
- OpenShift GitOps
- Observability tools
- Central policy dashboards
- Cluster inventory
- Optional secret management integration

This avoids mixing management tooling with business workloads.

### 6.2 Managed / Spoke Clusters

Spoke clusters run actual workloads. GitOps applies desired state to these clusters either directly from a central Argo CD or through a local Argo CD instance per cluster.

### 6.3 Repository Source of Truth

The repository design should match ownership.

Common split:

```text
platform-cluster-config     # owned by platform team
security-policies           # owned by security/platform governance
application-config          # owned by app teams
cluster-inventory           # owned by platform operations
```

### 6.4 CI Validation Layer

CI should block bad manifests before Argo CD sees them.

Validation examples:

- YAML syntax
- Kubernetes schema
- Kustomize render
- Helm render
- OpenShift dry run
- OPA/Conftest policy checks
- Image registry allowlist
- Required labels
- Namespace naming standards
- No privileged workloads unless approved

### 6.5 Reconciliation Layer

Argo CD continuously compares Git and cluster state.

Important concepts:

| Concept | Meaning |
|---|---|
| Desired state | Manifests from Git |
| Live state | Objects currently in the cluster |
| Sync | Apply desired state to live cluster |
| OutOfSync | Git and live state differ |
| Healthy | Resources are operationally healthy |
| Degraded | Resource exists but is unhealthy |
| Prune | Delete resources no longer in Git |
| Self-heal | Automatically correct live drift |

## 7. GitOps Patterns for Cluster Management

### 7.1 App of Apps Pattern

The App of Apps pattern uses a parent Argo CD Application to deploy child Applications.

Example:

```text
bootstrap/root-app.yaml
        |
        v
cluster-addons-app.yaml
namespaces-app.yaml
network-policy-app.yaml
rbac-app.yaml
monitoring-app.yaml
```

Parent Application:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-bootstrap
  namespace: openshift-gitops
spec:
  project: platform-config
  source:
    repoURL: https://git.example.com/platform/cluster-config.git
    targetRevision: main
    path: bootstrap/root
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

The root directory contains child Application YAMLs.

Advantages:

- Easy bootstrap
- Simple hierarchy
- Good for small to medium setups
- Works well for platform-owned add-ons

Risks:

- Parent app can become too powerful
- Mistakes in child Application definitions can affect many areas
- Requires strict review controls

Use it carefully, especially when child Applications can target cluster-scoped resources.

### 7.2 ApplicationSet Pattern

ApplicationSet is better for large multicluster environments because it generates Applications dynamically.

Example use case:

```text
Deploy logging add-on to all clusters labeled logging=enabled.
```

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: logging-addon
  namespace: openshift-gitops
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            logging: enabled
  template:
    metadata:
      name: '{{name}}-logging'
    spec:
      project: cluster-addons
      source:
        repoURL: https://git.example.com/platform/addons.git
        targetRevision: main
        path: logging/overlays/{{metadata.labels.environment}}
      destination:
        server: '{{server}}'
        namespace: openshift-logging
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

Advantages:

- Scales well across many clusters
- Supports cluster label selection
- Reduces repeated Application YAML
- Useful for cluster add-ons and environment overlays

### 7.3 One Argo CD per Cluster

Each cluster has its own Argo CD instance.

```text
cluster-dev   -> local Argo CD -> local workloads
cluster-stage -> local Argo CD -> local workloads
cluster-prod  -> local Argo CD -> local workloads
```

Advantages:

- Failure isolation
- Local cluster autonomy
- Smaller blast radius
- Better for disconnected or restricted networks

Disadvantages:

- More Argo CD instances to operate
- More upgrade/backup overhead
- Harder central visibility without additional tooling

### 7.4 Central Argo CD Managing Many Clusters

A hub Argo CD instance manages multiple target clusters.

```text
hub Argo CD
├── dev cluster
├── stage cluster
└── prod cluster
```

Advantages:

- Central visibility
- Central policy for sync and access
- Easier platform-wide control

Disadvantages:

- Larger blast radius
- Network connectivity requirements from hub to spokes
- Central credentials become highly sensitive
- Requires strict AppProject isolation

### 7.5 Hybrid Pattern

Many enterprises use both:

- Central GitOps for baseline cluster configuration and governance
- Local GitOps for application teams or restricted environments

Example:

```text
Hub GitOps:
  - baseline RBAC
  - quotas
  - network policies
  - operator subscriptions
  - compliance policies

Local cluster GitOps:
  - team applications
  - namespace-level configurations
  - environment-specific application overlays
```

This pattern gives central control with local flexibility.

## 8. Repository Design for Enterprise GitOps

Repository design is one of the most important architecture decisions. Poor repository design causes confusion, ownership conflict, merge problems, and insecure workflows.

### 8.1 Platform Repository Example

```text
cluster-config/
├── README.md
├── bootstrap/
│   ├── hub/
│   │   └── root-application.yaml
│   └── spoke/
│       └── root-application.yaml
├── clusters/
│   ├── dev-ocp01/
│   │   ├── kustomization.yaml
│   │   ├── baseline/
│   │   ├── operators/
│   │   ├── networking/
│   │   ├── security/
│   │   └── namespaces/
│   ├── stage-ocp01/
│   └── prod-ocp01/
├── components/
│   ├── namespaces/
│   ├── rbac/
│   ├── quotas/
│   ├── networkpolicies/
│   ├── monitoring/
│   ├── logging/
│   └── operators/
└── policies/
    ├── baseline-security/
    ├── compliance/
    └── allowed-registries/
```

### 8.2 Application Repository Example

```text
payments-gitops/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── route.yaml
│   └── kustomization.yaml
├── overlays/
│   ├── dev/
│   │   ├── kustomization.yaml
│   │   └── patch-replicas.yaml
│   ├── stage/
│   └── prod/
└── README.md
```

### 8.3 Environment Branch vs Directory Model

There are two common approaches.

#### Branch-per-environment

```text
main      -> dev
stage     -> stage
prod      -> prod
```

Advantages:

- Promotion by merge/cherry-pick
- Clear branch protection

Disadvantages:

- Environment drift between branches
- Harder to compare full environment differences
- Merge conflicts can become painful

#### Directory-per-environment

```text
overlays/dev
overlays/stage
overlays/prod
```

Advantages:

- All environments visible in one branch
- Easier review of differences
- Good with Kustomize overlays

Disadvantages:

- Requires stricter CODEOWNERS and path-based approvals
- A bad merge to main can affect multiple environments if not protected

For platform cluster configuration, directory-per-cluster is often clearer. For application promotion, either model can work.

### 8.4 Recommended Enterprise Repository Rules

Use these rules in production:

1. Protect the main branch.
2. Require pull request reviews.
3. Require CI validation before merge.
4. Use CODEOWNERS for security/platform directories.
5. Do not store plain-text secrets.
6. Keep generated files out unless intentionally versioned.
7. Use tags or release branches for production baselines.
8. Document rollback procedures.
9. Use clear naming conventions.
10. Review cluster-scoped changes separately.

Example `CODEOWNERS`:

```text
/clusters/prod-*/              @platform-admins @security-team
/policies/                     @security-team
/components/networkpolicies/   @network-security-team
/components/operators/         @platform-admins
/apps/payments/                @payments-team @platform-admins
```

## 9. Cluster Bootstrap Workflow

Cluster bootstrap is the process of turning a newly installed OpenShift cluster into an enterprise-ready managed cluster.

### 9.1 Bootstrap Stages

```text
OpenShift installed
   |
   v
Install GitOps Operator
   |
   v
Create Argo CD instance / use default instance
   |
   v
Configure repository credentials
   |
   v
Apply root Application
   |
   v
Root Application creates child Applications/ApplicationSets
   |
   v
Cluster baseline is reconciled
```

### 9.2 Bootstrap Items

Typical cluster bootstrap resources:

- OpenShift GitOps Operator
- Argo CD instance
- Argo CD RBAC
- AppProjects
- Repository credentials
- Root Application
- Namespace baselines
- Operator subscriptions
- Monitoring configuration
- Logging configuration
- Image registry policy
- NetworkPolicy defaults
- SecurityContextConstraints bindings where approved
- OAuth/identity provider configuration
- MachineConfig and node tuning
- Cluster observability integration

### 9.3 Installing OpenShift GitOps Operator Declaratively

Example Operator subscription:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-gitops-operator
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  upgradeStrategy: Default
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  channel: latest
  installPlanApproval: Automatic
  name: openshift-gitops-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
```

In many OpenShift versions, the Operator creates a default Argo CD instance in the `openshift-gitops` namespace. Always verify the exact behavior for your installed version.

### 9.4 Root Application Example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-root
  namespace: openshift-gitops
spec:
  project: platform-config
  source:
    repoURL: https://git.example.com/platform/cluster-config.git
    targetRevision: main
    path: clusters/prod-ocp01
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-gitops
  syncPolicy:
    automated:
      prune: false
      selfHeal: true
    syncOptions:
      - ApplyOutOfSyncOnly=true
```

For production cluster root apps, be careful with `prune: true`. Accidentally removing a directory from Git can delete live resources.

## 10. Managing Cluster-scoped Resources with GitOps

Cluster-scoped resources require special attention because they can affect the entire cluster.

Examples:

- `ClusterRole`
- `ClusterRoleBinding`
- `SecurityContextConstraints`
- `MachineConfig`
- `OAuth`
- `IngressController`
- `ImageContentSourcePolicy` / `ImageDigestMirrorSet`
- `CatalogSource`
- `Subscription`
- `ConsoleNotification`
- `APIServer`
- `Proxy`
- `Scheduler`
- `Project` template configuration

### 10.1 Risks

Bad cluster-scoped GitOps changes can:

- Lock users out
- Break authentication
- Reconfigure node-level settings
- Restart nodes via MachineConfig
- Break image pulls
- Expose workloads through incorrect ingress settings
- Grant excessive privileges

### 10.2 Controls

Use strict controls:

- Separate AppProject for cluster-scoped resources
- Separate repository path
- Mandatory security/platform approval
- CI dry-run validation
- Sync windows for production
- Manual sync for high-risk resources
- Disable automatic prune for critical root apps
- Use sync waves for ordered dependencies
- Use backup/export before dangerous changes

Example production AppProject restriction:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: prod-cluster-config
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://git.example.com/platform/prod-cluster-config.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: '*'
  clusterResourceWhitelist:
    - group: rbac.authorization.k8s.io
      kind: ClusterRole
    - group: rbac.authorization.k8s.io
      kind: ClusterRoleBinding
    - group: operators.coreos.com
      kind: Subscription
    - group: operators.coreos.com
      kind: OperatorGroup
    - group: machineconfiguration.openshift.io
      kind: MachineConfig
```

In real production, do not blindly whitelist `*/*` unless the AppProject is strictly limited to a trusted platform repository and admin group.

## 11. Namespace / Project Management with GitOps

OpenShift Projects are Kubernetes namespaces with additional OpenShift annotations and lifecycle integration.

### 11.1 Namespace Baseline

Example namespace baseline:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  labels:
    environment: prod
    app.kubernetes.io/part-of: payments
    platform.example.com/network-default-deny: "true"
  annotations:
    openshift.io/display-name: Payments Production
```

### 11.2 ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: payments-prod-quota
  namespace: payments-prod
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
    services: "20"
    secrets: "50"
    configmaps: "50"
    persistentvolumeclaims: "20"
```

### 11.3 LimitRange

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: payments-default-limits
  namespace: payments-prod
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 256Mi
      default:
        cpu: 500m
        memory: 512Mi
      min:
        cpu: 10m
        memory: 64Mi
      max:
        cpu: "2"
        memory: 2Gi
```

### 11.4 RBAC

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payments-devs-edit
  namespace: payments-prod
subjects:
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: payments-developers
roleRef:
  kind: ClusterRole

```

### 11.5 Default Deny NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1

  namespace: payments-prod

  podSelector: {}
```

## 13. Managing Security with GitOps

Security configuration is one of the best use cases for GitOps because it requires consistency and auditability.

### 13.1 RBAC as Code

RBAC should be stored in Git and reviewed by security/platform owners.

Avoid direct manual grants such as:

```bash
oc adm policy add-cluster-role-to-user cluster-admin bob
```

Prefer reviewed manifests:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: approved-platform-admins
subjects:
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: platform-admins
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: cluster-admin
```

### 13.2 SCC Bindings

OpenShift SecurityContextConstraints are sensitive. Do not casually grant `anyuid`, `hostnetwork`, or `privileged`.

Example controlled SCC binding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: allow-anyuid-for-approved-sa
  namespace: legacy-app-prod
subjects:
  - kind: ServiceAccount
    name: legacy-runtime
    namespace: legacy-app-prod
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: system:openshift:scc:anyuid
```

Review checklist:

- Why does the app require this SCC?
- Is it namespace-limited?
- Is it service-account-limited?
- Has the image been reviewed?
- Is there a migration plan to restricted security?

### 13.3 Secrets Management

Do not store plain-text secrets in Git.

Common patterns:

| Pattern | Description |
|---|---|
| Sealed Secrets | Encrypted Secret stored in Git, decrypted by controller |
| External Secrets Operator | Pulls secrets from external vault/provider |
| HashiCorp Vault integration | Dynamic/semi-dynamic secret delivery |
| SOPS + KMS/GPG | Encrypted YAML files stored in Git |
| OpenShift Pipelines secret injection | CI injects secret references, not values |

Bad:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-password
data:
  password: cGFzc3dvcmQxMjM=
```

Base64 is encoding, not encryption.

Better pattern with ExternalSecret:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-password
  namespace: payments-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: enterprise-vault
    kind: ClusterSecretStore
  target:
    name: db-password
  data:
    - secretKey: password
      remoteRef:
        key: prod/payments/db
        property: password
```

### 13.4 Git Repository Credentials

Repository credentials used by Argo CD are highly sensitive.

Best practices:

- Use read-only deploy keys where possible.
- Avoid personal access tokens tied to individual users.
- Rotate credentials regularly.
- Scope token access to required repositories only.
- Store credentials in OpenShift Secrets, not Git.
- Use separate credentials for platform and app repos.

### 13.5 AppProject Security

AppProjects are essential for preventing privilege escalation.

Dangerous AppProject:

```yaml
sourceRepos:
  - '*'
destinations:
  - namespace: '*'
    server: '*'
clusterResourceWhitelist:
  - group: '*'
    kind: '*'
```

Use this only for tightly controlled admin-owned projects. Never give application teams this level of access.

Safer application team AppProject:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments-team
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://git.example.com/apps/payments-gitops.git
  destinations:
    - namespace: payments-dev
      server: https://kubernetes.default.svc
    - namespace: payments-test
      server: https://kubernetes.default.svc
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
    - group: apps
      kind: Deployment
    - group: ""
      kind: Service
    - group: route.openshift.io
      kind: Route
    - group: networking.k8s.io
      kind: NetworkPolicy
```

## 14. GitOps with Red Hat Advanced Cluster Management

Red Hat Advanced Cluster Management for Kubernetes, commonly called ACM or RHACM, extends GitOps-driven cluster management for multicluster environments.

ACM helps with:

- Cluster lifecycle
- Managed cluster inventory
- Placement decisions
- Governance policies
- Compliance visibility
- Application distribution
- Observability across clusters

OpenShift GitOps handles desired-state reconciliation. ACM adds cluster inventory, placement, governance, and enterprise multicluster control.

### 14.1 Hub-spoke Model

```text
ACM Hub Cluster
├── ManagedCluster: dev-ocp01
├── ManagedCluster: stage-ocp01
├── ManagedCluster: prod-ocp01
└── ManagedCluster: dr-ocp01
```

The hub cluster maintains knowledge of managed clusters. Policies and placements decide where configurations apply.

### 14.2 Policy-based Governance

ACM policies can ensure clusters comply with required configuration.

Example policy use cases:

- Ensure audit logging is configured
- Ensure allowed registries are configured
- Ensure namespace has required labels
- Ensure Operator is installed
- Ensure privileged SCC usage is limited
- Ensure default ingress certificate exists
- Ensure monitoring config exists

### 14.3 Policy Placement

ACM uses placement concepts to decide where policies apply.

Example idea:

```text
Policy: require-default-deny-networkpolicy
Placement: clusters with environment=prod
Binding: attach policy to placement
```

### 14.4 GitOps + ACM Pattern

A strong enterprise pattern:

```text
Git
 |
 v
ACM Policy / Placement definitions
 |
 v
Hub cluster
 |
 v
Policies distributed to managed clusters
 |
 v
Clusters become compliant or report violation
```

Another pattern:

```text
ACM cluster inventory labels
      |
      v
ApplicationSet cluster generator
      |
      v
Argo CD Applications generated for matching clusters
```

### 14.5 Example ACM Policy Concept

A policy can enforce a namespace baseline:

```yaml
apiVersion: policy.open-cluster-management.io/v1
kind: Policy
metadata:
  name: policy-namespace-baseline
  namespace: policies
spec:
  remediationAction: enforce
  disabled: false
  policy-templates:
    - objectDefinition:
        apiVersion: policy.open-cluster-management.io/v1
        kind: ConfigurationPolicy
        metadata:
          name: require-platform-namespace
        spec:
          remediationAction: enforce
          severity: medium
          object-templates:
            - complianceType: musthave
              objectDefinition:
                apiVersion: v1
                kind: Namespace
                metadata:
                  name: platform-tools
                  labels:
                    owner: platform
```

In production, choose `inform` first, observe impact, then move to `enforce` after validation.

## 15. Sync Policies and Operational Behavior

Argo CD sync policy determines how changes are applied.

### 15.1 Manual Sync

Manual sync requires an operator or authorized user to approve the sync.

Use manual sync for:

- Production cluster-scoped changes
- Authentication/OAuth changes
- MachineConfig changes
- Ingress controller changes
- High-risk Operator upgrades
- Large database application changes

### 15.2 Automated Sync

Automated sync applies changes when Git changes are detected.

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
```

Use automated sync for:

- Dev/test applications
- Namespace baselines
- Low-risk config maps
- Standard NetworkPolicy baselines
- Common team onboarding templates

### 15.3 Prune

Prune deletes resources that exist in the cluster but no longer exist in Git.

Powerful but dangerous.

Use prune carefully for:

- Namespaced application resources
- Generated environments
- Temporary dev namespaces

Be careful or disable prune for:

- Namespaces
- PersistentVolumeClaims
- ClusterRoleBinding
- OAuth
- MachineConfig
- Critical production resources

### 15.4 Self Heal

Self-heal corrects live drift back to Git.

Useful for:

- Preventing manual changes
- Enforcing baseline config
- Maintaining compliance

Risk:

- During incidents, emergency manual changes may be reverted unexpectedly.

Mitigation:

- Use sync windows
- Temporarily disable auto-sync with documented approval
- Commit emergency change to Git quickly

### 15.5 Sync Options

Common sync options:

```yaml
syncOptions:
  - CreateNamespace=true
  - ApplyOutOfSyncOnly=true
  - PruneLast=true
  - ServerSideApply=true
```

Meaning:

| Option | Purpose |
|---|---|
| `CreateNamespace=true` | Create destination namespace if missing |
| `ApplyOutOfSyncOnly=true` | Apply only changed resources |
| `PruneLast=true` | Prune after other resources are healthy |
| `ServerSideApply=true` | Use Kubernetes server-side apply behavior |

Do not add sync options blindly. Test them with your resource types and OpenShift version.

## 16. Sync Waves and Hooks

Sync waves control ordering. This is important when managing cluster configuration.

### 16.1 Sync Wave Example

Namespace first:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

Quota after namespace:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: payments-quota
  namespace: payments-prod
  annotations:
    argocd.argoproj.io/sync-wave: "1"
```

Deployment later:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: payments-prod
  annotations:
    argocd.argoproj.io/sync-wave: "5"
```

### 16.2 Suggested Waves for Cluster Add-ons

| Wave | Resource type |
|---|---|
| -10 | CRDs if manually managed |
| -5 | Namespaces |
| 0 | OperatorGroup, Subscription |
| 5 | Operator custom resources |
| 10 | RBAC and service accounts |
| 20 | Workloads |
| 30 | Routes, ServiceMonitors, alerts |

### 16.3 Hooks

Hooks run at specific sync phases:

- `PreSync`
- `Sync`
- `PostSync`
- `SyncFail`
- `PostDelete`

Example PreSync Job:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: precheck-payments
  namespace: payments-prod
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: precheck
          image: registry.access.redhat.com/ubi9/ubi
          command:
            - /bin/bash
            - -c
            - echo "Running pre-sync validation"
```

Use hooks carefully. Hooks should not become hidden deployment scripts that bypass declarative management.

## 17. Kustomize and Helm in GitOps

### 17.1 Kustomize

Kustomize is excellent for environment overlays.

Base:

```text
base/
├── deployment.yaml
├── service.yaml
├── route.yaml
└── kustomization.yaml
```

Overlay:

```text
overlays/prod/
├── kustomization.yaml
├── patch-replicas.yaml
└── patch-resources.yaml
```

Example overlay:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
patches:
  - path: patch-replicas.yaml
  - path: patch-resources.yaml
images:
  - name: quay.io/example/payments-api
    newTag: v1.4.7
```

### 17.2 Helm

Helm is useful for packaged applications and Operators that publish charts.

Argo CD can deploy Helm charts with values:

```yaml
source:
  repoURL: https://charts.example.com/platform
  chart: payments-api
  targetRevision: 1.2.3
  helm:
    valueFiles:
      - values-prod.yaml
```

### 17.3 Kustomize vs Helm

| Requirement | Better fit |
|---|---|
| Environment overlays | Kustomize |
| Packaged reusable app | Helm |
| Simple YAML patches | Kustomize |
| Complex templating | Helm |
| Third-party chart deployment | Helm |
| Platform baseline config | Kustomize/plain YAML |

Avoid over-templating. Too much templating makes reviews difficult.

## 18. Image Promotion in GitOps

GitOps separates image build from deployment.

Typical flow:

```text
Developer pushes code
   |
   v
CI builds image
   |
   v
CI pushes image to registry
   |
   v
CI updates GitOps repo with image tag/digest
   |
   v
Argo CD deploys new desired state
```

### 18.1 Tag vs Digest

Tag example:

```yaml
image: quay.io/example/payments-api:v1.4.7
```

Digest example:

```yaml
image: quay.io/example/payments-api@sha256:abc123...
```

For production, digest pinning is safer because tags can be moved.

### 18.2 Promotion Model

```text
Dev image validated
   |
   v
Update dev overlay
   |
   v
Promote same image digest to stage overlay
   |
   v
Promote same digest to prod overlay
```

The image should not be rebuilt separately for each environment. Build once, promote the same artifact.

## 19. Drift Management

Drift is a normal operational concern. GitOps makes drift visible.

### 19.1 Types of Drift

| Drift type | Example |
|---|---|
| Manual hotfix | Engineer scales deployment manually |
| Controller mutation | Operator adds default fields |
| Admission mutation | Mutating webhook changes pods |
| Runtime status | Kubernetes adds status fields |
| External secret refresh | Secret value changes outside Git |
| HPA change | HPA adjusts replicas |

### 19.2 Ignore Differences

Some differences should be ignored. Example: replicas managed by HPA.

Application ignore difference example:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

Use ignore rules carefully. Do not hide real drift.

### 19.3 Drift Response Procedure

When Argo CD shows `OutOfSync`:

1. Check diff.
2. Identify whether drift is expected.
3. If expected, update Git or ignore rule.
4. If unexpected, investigate who/what changed it.
5. Sync or self-heal.
6. Record incident/change if production.

Commands:

```bash
argocd app diff payments-prod
argocd app get payments-prod
oc get events -n payments-prod --sort-by=.lastTimestamp
oc adm node-logs <node> --role=master
```

OpenShift audit logs may be needed for sensitive drift investigation.

- Inter-namespace allow policies
- Egress policies
- Routes
- IngressController configuration
- Service mesh configuration

Allow application pods to connect to MySQL in another namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-payments-to-mysql
  namespace: database-prod
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
    - Ingress

            matchLabels:
              app.kubernetes.io/name: payments-prod

            matchLabels:
              app: payments-api

          port: 3306
```

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments-api
  namespace: payments-prod
spec:
  host: payments.apps.prod.example.com
```

```yaml
apiVersion: operator.openshift.io/v1
```

The actual TLS secret should be delivered securely through an approved secrets mechanism.

## 21. GitOps and Node-level / Machine Configuration

OpenShift node-level configuration often uses `MachineConfig` and `MachineConfigPool`.

- Kernel arguments
- Chrony configuration
- CRI-O config
- Registry trust configuration
- File drops under `/etc`

Controls:

- Manual sync for MachineConfig apps

## 23. Disaster Recovery and Backup Considerations

GitOps improves recovery, but it is not a complete backup solution.

### 23.1 What GitOps Can Restore

GitOps can restore:

- YAML-defined cluster configuration
- Namespace structure
- RBAC
- NetworkPolicy
- Operator subscriptions
- Application deployment manifests
- Routes/services/config maps
- Monitoring rules
- Policy definitions

### 23.2 What GitOps Cannot Restore Alone

GitOps cannot restore by itself:

- etcd data not represented in Git
- Persistent volume data
- Database contents
- Runtime-generated secrets not stored externally
- Image registry contents if registry is lost
- Cluster certificates unless managed externally
- Manual changes never committed to Git

### 23.3 DR Architecture

A strong DR model includes:

- Git repository backup/mirroring
- Container registry backup/replication
- External secrets backup
- OpenShift etcd backup
- Persistent volume backup/snapshot
- GitOps bootstrap procedure
- Documented cluster rebuild runbook

### 23.4 Recovery Runbook Example

```text
1. Provision replacement OpenShift cluster.
2. Restore/validate identity provider and certificates.
3. Install OpenShift GitOps Operator.
4. Configure Git credentials.
5. Apply root Application for target cluster.
6. Wait for baseline Applications to sync.
7. Restore persistent data from backup.
8. Validate Operators and CRDs.
9. Validate routes and DNS.
10. Run application smoke tests.
11. Confirm monitoring and alerts.
```

## 24. Change Management Workflow

GitOps must integrate with enterprise change management.

### 24.1 Standard Change Flow

```text
Engineer creates branch
   |
   v
Modify YAML/Kustomize/Helm values
   |
   v
Run local validation
   |
   v
Open pull request
   |
   v
CI validates manifests and policy
   |
   v
Peer/security/platform approval
   |
   v
Merge to protected branch
   |
   v
Argo CD detects change
   |
   v
Manual or automatic sync
   |
   v
Post-change validation
```

### 24.2 Emergency Change Flow

During incidents:

1. Make minimum necessary live change only if required.
2. Record the command and reason.
3. Immediately create Git PR to capture desired state.
4. Merge after expedited review.
5. Let GitOps reconcile.
6. Remove temporary exception after incident.

Important principle:

> Emergency manual changes should become Git changes quickly, otherwise GitOps will either revert them or leave undocumented drift.

## 26. Multi-tenancy Design

OpenShift is often shared by many teams. GitOps must respect multi-tenancy.

### 26.1 Tenant Isolation

Use:

- Separate namespaces/projects
- ResourceQuota
- LimitRange
- NetworkPolicy
- RBAC groups
- AppProjects
- Separate Git repository or path ownership
- Separate Argo CD Applications per team/app

### 26.2 Do Not Give Teams Unlimited AppProject Permissions

If a team can create Applications targeting any namespace and any resource kind, they can escalate privileges.

Example risk:

```yaml
kind: ClusterRoleBinding
roleRef:
  name: cluster-admin
subjects:
  - kind: User
    name: developer1
```

If AppProject allows this, GitOps becomes a privilege escalation path.

### 26.3 Safe Tenant AppProject

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: inventory-team
  namespace: openshift-gitops
spec:
  sourceRepos:
    - https://git.example.com/apps/inventory-gitops.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: inventory-dev
    - server: https://kubernetes.default.svc
      namespace: inventory-test
  clusterResourceWhitelist: []
  namespaceResourceBlacklist:
    - group: rbac.authorization.k8s.io
      kind: RoleBinding
```

Depending on your model, you might allow teams to manage RoleBindings only to pre-approved roles, or not at all.

## 27. GitOps for Compliance and Governance

### 27.1 Compliance Requirements

Common enterprise controls:

- No privileged pods unless approved
- No workloads running as root unless approved
- All namespaces have owner labels
- All production namespaces have default deny NetworkPolicy
- All apps have resource requests and limits
- All routes use TLS
- Images come from approved registries
- Cluster audit policy is enabled
- Operators use approved channels
- Secrets are not stored in Git

### 27.2 Policy-as-Code

Use policy-as-code in CI and cluster governance.

CI policy examples:

- Block plain-text Secret manifests
- Block `privileged: true`
- Require resource requests
- Require labels
- Require approved registries

Runtime governance examples:

- ACM Policy
- Gatekeeper/OPA
- Kyverno if allowed by enterprise standard
- OpenShift admission controls

### 27.3 Example Conftest Rule Idea

Plain language policy:

```text
Deny any Deployment container without resources.requests.cpu and resources.requests.memory.
```

This catches problems before merge.

Evidence sources:

- Pull request approvals
- Commit history
- CI validation logs
- Argo CD sync history
- ACM policy compliance reports
- OpenShift audit logs
- Change request IDs in commit messages

## 28. Promotion Strategy

### 28.1 Environment Promotion

Typical promotion:

```text
Dev -> Test -> Stage -> Prod
```

In GitOps:

```text
Update dev overlay
Validate
Promote same image digest to test overlay
Validate
Promote same digest to stage overlay
Validate
Promote same digest to prod overlay
```

### 28.2 Pull Request Promotion

A production promotion PR should show:

- Image digest/tag change
- Replica/resource changes
- Config changes
- Database migration hooks if any
- Rollback plan
- Test evidence

### 28.3 Rollback

Rollback should be done by reverting Git.

```bash
git revert <commit-id>
git push
```

Then sync the application.

Avoid using only `oc rollout undo` in a GitOps-managed deployment. If Git still says new version, Argo CD may reapply it.

## 30. Troubleshooting GitOps in OpenShift

### 30.1 Application OutOfSync

Check:

```bash
argocd app get <app-name>
argocd app diff <app-name>
oc get application <app-name> -n openshift-gitops -o yaml
```

Common causes:

- Manual changes
- Mutating webhook changes
- HPA replica changes
- Operator defaulting fields
- Missing ignoreDifferences
- Helm template difference

### 30.2 Sync Failed

Check:

```bash
argocd app sync <app-name>
argocd app history <app-name>
oc describe application <app-name> -n openshift-gitops
oc get events -A --sort-by=.lastTimestamp
```

Common causes:

- RBAC permission denied
- Namespace missing
- CRD not installed yet
- Invalid YAML
- Admission policy denied resource
- SCC restriction
- ResourceQuota exceeded
- Image pull error

### 30.3 Permission Denied

Error example:

```text
User "system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller" cannot create resource ...
```

Fix approach:

1. Identify exact resource and API group.
2. Identify Argo CD service account.
3. Check AppProject restrictions.
4. Check Kubernetes RBAC.
5. Grant minimum required permission.

Commands:

```bash
oc auth can-i create deployment \
  --as system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller \
  -n payments-prod

oc auth can-i create clusterrole \
  --as system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
```

### 30.4 CRD Missing

Error:

```text
no matches for kind "ServiceMonitor" in version "monitoring.coreos.com/v1"
```

Cause:

- CRD not installed yet
- Operator not ready
- Sync ordering issue

Fix:

- Install Operator first
- Use sync waves
- Split Operator install and CR creation into separate Applications

### 30.5 Namespace Does Not Exist

Error:

```text
namespaces "payments-prod" not found
```

Fix options:

- Add Namespace manifest
- Use `CreateNamespace=true`
- Ensure namespace app syncs before workload app

### 30.6 ResourceQuota Exceeded

Error:

```text
exceeded quota: payments-prod-quota
```

Fix:

- Review requested resources
- Adjust app resources
- Increase quota through Git PR if approved
- Avoid manual quota edits

### 30.7 SCC Denied

Error:

```text
would violate PodSecurity "restricted" or SecurityContextConstraints
```

Fix:

- Run image as non-root if possible
- Set proper `securityContext`
- Use approved service account
- Add SCC binding only after review

### 30.8 Git Repository Unreachable

Check:

```bash
oc logs deployment/openshift-gitops-repo-server -n openshift-gitops
oc get secret -n openshift-gitops | grep repo
```

Common causes:

- Bad Git credentials
- Expired token
- TLS trust issue
- Proxy issue
- DNS/network issue
- Repository moved or renamed

### 30.9 ApplicationSet Not Generating Apps

Check:

```bash
oc get applicationset -n openshift-gitops
oc describe applicationset <name> -n openshift-gitops
oc logs deployment/openshift-gitops-applicationset-controller -n openshift-gitops
```

Common causes:

- Cluster secret labels do not match selector
- Template variable wrong
- Destination cluster not registered
- AppProject does not allow destination
- Git path does not exist

## 33. Common Anti-patterns

### 33.1 Storing Plain Secrets in Git

Base64 is not secure. Do not store Kubernetes Secrets with real values in Git.

### 33.2 Giving Argo CD Unlimited Access to Everything

It is easy but dangerous. Use AppProjects and RBAC boundaries.

### 33.3 Using GitOps for Everything Without Risk Classification

Not all resources should auto-sync with prune enabled. Classify resources by risk.

### 33.4 Manual Console Changes in Production

Manual changes cause drift and weaken auditability. Use Git PRs.

### 33.5 No CI Validation

Bad YAML should fail before it reaches Argo CD.

### 33.6 Too Much Templating

Heavy Helm templating or complex generators can make reviews hard. Keep configuration understandable.

### 33.7 One Giant Application for Everything

A single huge Argo CD Application is hard to troubleshoot and risky to sync. Split by responsibility and blast radius.

### 33.8 Auto-prune on Critical Cluster Resources

Deleting a directory by mistake can delete important resources. Use prune carefully.

### 33.9 No Break-glass Process

Production incidents need a controlled emergency path. Define it before an incident.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prod-ocp01-root
  namespace: openshift-gitops
spec:
  project: prod-cluster-config
  source:
    repoURL: https://git.example.com/platform/enterprise-gitops.git
```

```yaml
      - CreateNamespace=false
      - PruneLast=true
```

## 36. Senior Engineer Interview Notes

### Question: What is GitOps-driven cluster management?

Answer:

GitOps-driven cluster management is a declarative operations model where cluster desired state is stored in Git and continuously reconciled to OpenShift clusters by tools like OpenShift GitOps and Argo CD. It covers not only application deployment but also cluster configuration, operators, namespaces, RBAC, quotas, network policies, and governance. The key benefits are auditability, consistency, drift detection, rollback, and multicluster scalability.

### Question: How do you manage multiple clusters with GitOps?

Answer:

Use a hub-spoke model with OpenShift GitOps and often ACM. Cluster inventory and labels define which clusters receive which configuration. ApplicationSet can generate Applications for clusters based on selectors. ACM policies can enforce compliance across managed clusters. Repository structure should separate common components from cluster-specific overlays.

### Question: How do you secure Argo CD in OpenShift?

Answer:

Secure it with OpenShift OAuth/SSO, least-privilege AppProjects, restricted repository credentials, RBAC, TLS trust, namespace isolation, network policies, and review-controlled Git access. Avoid broad `*/*` permissions except for tightly controlled platform-admin projects. Do not store plain secrets in Git.

### Question: What is drift and how do you handle it?

Answer:

Drift is the difference between desired state in Git and live cluster state. Argo CD detects drift and can self-heal. The response depends on whether drift is expected. For expected controller mutations, use `ignoreDifferences`. For emergency manual changes, commit the change to Git quickly or let GitOps revert it. For unauthorized drift, investigate audit logs and sync back to desired state.

### Question: What resources should not be auto-pruned?

Answer:

Be very careful with namespaces, PVCs, cluster-scoped RBAC, MachineConfig, OAuth, ingress configuration, and critical production resources. Auto-prune is useful for controlled application resources, but dangerous for high-impact platform resources.

### Question: How do you avoid CRD timing issues?

Answer:

Install Operators and CRDs before applying custom resources. Use sync waves or separate Applications. Verify Operator readiness before custom resources sync. For production, keep Operator installation and CR creation as separate controlled phases.

## 38. Troubleshooting Scenarios

### Scenario 1: App is OutOfSync because HPA changed replicas

Symptom:

```text
Deployment replicas differ: Git says 3, live says 8.
```

Cause:

HPA modified replicas.

Solution:

Ignore `/spec/replicas` for that Deployment or avoid storing fixed replicas when HPA controls scaling.

### Scenario 2: Operator custom resource fails because CRD is missing

Symptom:

```text
no matches for kind "ClusterLogging"
```

Cause:

Cluster Logging Operator CRD not installed yet.

Solution:

Separate Operator installation and custom resource application. Use sync waves.

### Scenario 3: Argo CD cannot create Route

Symptom:

```text
routes.route.openshift.io is forbidden
```

Cause:

AppProject or RBAC does not allow Route creation.

Solution:

Update AppProject namespace resource whitelist or grant proper RBAC to the Argo CD service account.

### Scenario 4: Production manual hotfix keeps getting reverted

Symptom:

Engineer scales deployment manually; Argo CD reverts it.

Cause:

Self-heal enabled.

Solution:

Commit hotfix to Git or temporarily pause auto-sync using approved break-glass process.

### Scenario 5: ApplicationSet does not create Applications for new cluster

Symptom:

New cluster registered but no generated app.

Cause possibilities:

- Cluster secret missing required label
- Selector mismatch
- Cluster not registered in Argo CD
- Template variable error
- AppProject destination denied

Solution:

Check ApplicationSet status, controller logs, cluster secret labels, and AppProject permissions.

## 39. Best Practices Summary

1. Treat Git as the source of truth.
2. Use pull requests for every production change.
3. Validate manifests in CI before merge.
4. Use AppProjects for tenancy and least privilege.
5. Avoid plain-text secrets in Git.
6. Use ApplicationSet for multicluster scale.
7. Use ACM policies for governance and compliance.
8. Use sync waves for ordered cluster configuration.
9. Use auto-sync selectively based on risk.
10. Use prune carefully, especially for cluster-scoped resources.
11. Monitor Argo CD health and sync failures.
12. Document drift response and break-glass procedures.
13. Test bootstrap and DR regularly.
14. Keep repository structure simple and reviewable.
15. Separate platform configuration from application configuration when ownership differs.
