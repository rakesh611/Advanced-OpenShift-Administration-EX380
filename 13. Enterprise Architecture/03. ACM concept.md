## 1. Why ACM Exists in Enterprise OpenShift Architecture

In a small OpenShift environment, one cluster might be enough. A team installs OpenShift, creates projects, configures routes, manages RBAC, deploys applications, monitors the cluster, and performs upgrades manually or with a small automation layer.

In an enterprise environment, this model breaks quickly.

Large organizations usually run many OpenShift or Kubernetes clusters across different locations and platforms:

- Production clusters
- Non-production clusters
- DR clusters
- Edge clusters
- Single-node OpenShift clusters
- Cloud clusters on AWS, Azure, GCP, or IBM Cloud
- On-premises clusters on VMware, bare metal, OpenStack, or private cloud
- Dedicated clusters for security zones, business units, regulatory workloads, latency-sensitive applications, or customer-specific isolation

Without a multi-cluster management layer, every cluster becomes its own island. Administrators log in separately to each console, manually compare configuration, manually check compliance, manually apply patches, and manually deploy common resources. This creates configuration drift, inconsistent security posture, slow incident response, and poor fleet visibility.

**ACM solves this enterprise problem.**

ACM provides a central management plane for OpenShift and Kubernetes clusters. It gives platform teams one place to manage cluster lifecycle, policy compliance, application placement, observability, and search across the fleet.

Think of ACM as the **enterprise control tower** for multi-cluster OpenShift.

It does not replace OpenShift. It does not replace Kubernetes. It does not replace GitOps. Instead, it coordinates and governs many clusters from a central hub.

### Enterprise problem without ACM

```text
Admin laptop
   |-- login cluster-dev-1
   |-- login cluster-dev-2
   |-- login cluster-prod-1
   |-- login cluster-prod-2
   |-- login cluster-dr-1
   |-- login edge-sno-1
   |-- login edge-sno-2
   |-- manually compare configs
   |-- manually validate compliance
   |-- manually deploy policies
   |-- manually check upgrade status
```

This model does not scale.

### Enterprise model with ACM

```text
                       +---------------------------+
                       |        ACM Hub Cluster     |
                       |---------------------------|
                       | Cluster lifecycle          |
                       | Governance policies        |
                       | Placement decisions        |
                       | GitOps integration         |
                       | Observability              |
                       | Search                     |
                       +-------------+-------------+
                                     |
        +----------------------------+----------------------------+
        |                            |                            |
+-------+--------+          +--------+-------+            +-------+--------+
| Managed Cluster |          | Managed Cluster |            | Managed Cluster |
| Dev             |          | Prod            |            | Edge / SNO       |
+-----------------+          +----------------+            +----------------+
```

The hub becomes the control point for fleet visibility and fleet governance.

## 2. What ACM Is

**Red Hat Advanced Cluster Management for Kubernetes** is a Red Hat product for managing multiple Kubernetes and OpenShift clusters from a central hub cluster.

At a high level, ACM provides these capabilities:

1. **Cluster lifecycle management**  
   Create, import, upgrade, detach, destroy, and organize clusters.

2. **Cluster fleet governance**  
   Define policies once and apply them across selected clusters.

3. **Application lifecycle management through GitOps integration**  
   Register selected managed clusters with OpenShift GitOps / Argo CD and deploy applications based on placement decisions.

4. **Observability**  
   Collect and view fleet-level metrics and cluster health.

5. **Search**  
   Search Kubernetes resources across many clusters from one console.

6. **Security and access control**  
   Use RBAC, cluster sets, credentials, certificates, and policy frameworks to secure management operations.

7. **Business continuity**  
   Back up and restore hub resources, support active-passive hub patterns, and recover fleet management state.

### Simple definition

ACM is a centralized multi-cluster management platform for OpenShift and Kubernetes.

### Architect-level definition

ACM is a hub-and-spoke management control plane that uses Kubernetes APIs, custom resources, controllers, agents, placement decisions, policy propagation, GitOps integration, and observability pipelines to manage the lifecycle, configuration, security posture, and operational visibility of many clusters across hybrid cloud and edge environments.

### L3 operations definition

ACM is the tool you use when you do not want to SSH, log in, or manually configure 20, 50, or 500 clusters one by one.

## 3. ACM vs OpenShift vs MCE vs GitOps vs RHACS

Many administrators confuse ACM with other OpenShift platform components. In enterprise architecture, you must understand the boundaries clearly.

| Component | Main Purpose | What It Does | What It Does Not Replace |
|---|---|---|---|
| OpenShift Container Platform | Container platform | Runs applications, operators, routes, builds, workloads, networking, storage | Does not centrally manage many clusters by itself |
| ACM | Multi-cluster management | Manages fleet lifecycle, governance, placement, observability, search | Does not run application workloads directly except on hub itself |
| MCE | Cluster lifecycle engine | Provides cluster lifecycle functions used by ACM or standalone OpenShift | Does not provide full ACM governance/observability features by itself |
| OpenShift GitOps / Argo CD | Declarative app/config deployment | Syncs Git-defined resources to clusters | Does not decide full enterprise fleet governance alone |
| RHACS / ACS | Security scanning and runtime security | Vulnerability, compliance, runtime detection, network graph | Does not manage cluster lifecycle |
| ODF | Storage platform | Provides persistent storage, object storage, Ceph-based storage | Does not manage cluster fleet |
| Quay | Enterprise image registry | Stores and scans images | Does not govern clusters |

### Key relationship

```text
OpenShift = where workloads run
ACM       = how many clusters are managed
MCE       = cluster lifecycle engine used by ACM
GitOps    = how desired state is continuously applied
RHACS     = security visibility and runtime protection
ODF       = storage layer
Quay      = image registry
```

A mature enterprise platform usually combines these tools:

```text
                 +------------------------------+
                 | Platform Management Layer     |
                 | ACM + GitOps + ACS + Quay     |
                 +---------------+--------------+
                                 |
        +------------------------+------------------------+
        |                        |                        |
+-------+--------+       +-------+--------+       +-------+--------+
| OCP Cluster A  |       | OCP Cluster B  |       | OCP Cluster C  |
| Apps + ODF     |       | Apps + ODF     |       | Apps + ODF     |
+----------------+       +----------------+       +----------------+
```

## 4. Core ACM Architecture

ACM follows a hub-and-spoke architecture.

The main components are:

- **Hub cluster**
- **Managed clusters**
- **MulticlusterHub custom resource**
- **Multicluster Engine**
- **Klusterlet agent**
- **ManagedCluster custom resource**
- **ManagedClusterSet and ClusterSetBinding**
- **Placement and PlacementDecision**
- **Governance policy framework**
- **Application / GitOps integration**
- **Search service**
- **Observability service**
- **Backup and restore components**

### High-level architecture

```text
                         +-----------------------------------+
                         |            ACM Hub Cluster         |
                         |-----------------------------------|
                         | multiclusterhub-operator          |
                         | multiclusterhub CR                |
                         | multicluster engine               |
                         | cluster-manager                   |
                         | placement controller              |
                         | governance policy controllers     |
                         | search API/collector              |
                         | observability / Thanos            |
                         | GitOps integration                |
                         +----------------+------------------+
                                          |
                    Registration, work, status, policy, metrics
                                          |
        +---------------------------------+--------------------------------+
        |                                 |                                |
+-------+--------+                +-------+--------+               +-------+--------+
| Managed Cluster |                | Managed Cluster |               | Managed Cluster |
| OpenShift prod  |                | OpenShift dev   |               | Edge/SNO        |
| klusterlet      |                | klusterlet      |               | klusterlet      |
| add-ons         |                | add-ons         |               | add-ons         |
+-----------------+                +-----------------+               +----------------+
```

### ACM control flow

ACM uses a Kubernetes-controller model. You create or modify a custom resource on the hub. Controllers watch that desired state, calculate decisions, propagate work to managed clusters, then collect status back to the hub.

Example:

1. Admin creates a `Policy` on the hub.
2. Admin creates a `Placement` to choose clusters.
3. Admin binds the policy to the placement using `PlacementBinding`.
4. ACM creates replicated policy resources for selected clusters.
5. Policy add-ons on managed clusters evaluate compliance.
6. Compliance status is reported back to the hub.
7. The governance dashboard shows compliant or non-compliant status.

This is the same Kubernetes operator pattern you already know from OpenShift, but applied at fleet scale.

## 5. Hub Cluster, Managed Cluster, and Local Cluster

### Hub cluster

The **hub cluster** is the OpenShift cluster where ACM is installed.

It contains the central ACM control plane. It stores ACM CRDs, cluster inventory, policies, placement decisions, search data, observability components, credentials, and backup configuration.

The hub cluster should be treated as a **critical management platform**, not as a normal application cluster.

Recommended enterprise approach:

- Use a dedicated OpenShift cluster as ACM hub.
- Do not run heavy business applications on the hub.
- Use infrastructure nodes if required.
- Protect hub etcd with backup.
- Enable hub backup and restore.
- Restrict admin access.
- Monitor hub health aggressively.
- Use high availability architecture.
- Keep hub version within supported compatibility for managed clusters.

### Managed cluster

A **managed cluster** is a Kubernetes or OpenShift cluster imported into ACM or created from ACM.

After a cluster becomes managed, ACM can:

- View its health.
- Apply governance policies.
- Register it with GitOps.
- Use it in placement decisions.
- Search its resources.
- Collect observability data.
- Run cluster lifecycle actions depending on how it was created or imported.

### Local cluster

The **local-cluster** is the hub cluster managing itself.

When local-cluster is enabled, the hub is also registered as a managed cluster. This allows policies and placements to target the hub itself.

Use this carefully. Applying broad policies to `local-cluster` can affect the hub control plane. For example, an enforced policy that changes authentication, SCC, networking, or operator subscriptions on the hub might break ACM itself.

### Hub vs managed cluster comparison

| Area | Hub Cluster | Managed Cluster |
|---|---|---|
| Main role | Central management plane | Runs workloads and reports to hub |
| ACM installed? | Yes | No full ACM install; agent/add-ons only |
| Klusterlet | Optional/local-cluster | Yes |
| Policy source | Root policy lives here | Replicated policy evaluated here |
| Placement | Calculated here | Selected by placement |
| Observability | Receives/stores fleet metrics | Sends metrics to hub |
| GitOps | Integrates with OpenShift GitOps | Application deployment target |
| Criticality | Very high | Depends on workload |

## 7. Klusterlet and Managed Cluster Registration

When ACM manages a cluster, the managed cluster runs an agent called **klusterlet**.

The klusterlet is responsible for connecting the managed cluster to the hub and allowing ACM to manage resources, report status, and run add-ons.

### Registration model

```text
Hub cluster:
  ManagedCluster CR
  Import secret
  Cluster namespace
  Add-on configuration
  Work resources
  Policy status

Managed cluster:
  Klusterlet
  Registration agent
  Work agent
  Add-on agents
  Policy controllers
  Search collector
  Observability endpoint operator
```

### Import flow for an existing cluster

1. Admin starts cluster import from ACM console or CLI.
2. ACM creates a namespace on the hub for that managed cluster.
3. ACM generates import manifests or an import secret.
4. Admin applies import YAML on the target cluster.
5. The klusterlet is installed on the managed cluster.
6. The managed cluster registers with the hub.
7. The hub accepts the cluster.
8. Add-ons are deployed.
9. Cluster status becomes `Available`.

### Example commands to inspect imported clusters

```bash
oc get managedcluster
oc get managedcluster -o wide
oc describe managedcluster <cluster-name>

oc get ns | grep <cluster-name>
oc get klusterletaddonconfig -n <cluster-name>
oc get managedclusteraddon -n <cluster-name>
```

### On the managed cluster

```bash
oc get pods -n open-cluster-management-agent
oc get pods -n open-cluster-management-agent-addon
oc get klusterlet
oc describe klusterlet klusterlet
```

### Important registration states

| State | Meaning |
|---|---|
| `Available=True` | Hub can communicate with managed cluster |
| `Available=False` | Cluster is unreachable, agent broken, or certificates/network issue |
| `Joined=True` | Cluster registration accepted |
| Add-on `Available=True` | Add-on running correctly |
| Add-on `Degraded=True` | Add-on has an issue |

### Common import failure causes

- Managed cluster cannot reach hub API or hub route.
- Proxy settings are missing or wrong.
- Custom CA is not trusted.
- Import token expired.
- Cluster name mismatch.
- Klusterlet pods are failing.
- RBAC or SCC issue on managed cluster.
- NetworkPolicy/firewall blocks traffic.
- Hub certificate changed and managed cluster has stale trust.

## 8. Cluster Lifecycle Management

ACM is not only for importing existing clusters. It can also create and manage clusters across supported providers.

Cluster lifecycle includes:

- Create cluster
- Import cluster
- Detach cluster
- Destroy cluster
- Upgrade cluster
- Scale some cluster types
- Hibernate/resume supported clusters
- Manage cluster pools
- Discover clusters
- Manage host inventory for bare metal or edge scenarios

### Common lifecycle models

#### 1. Import existing OpenShift cluster

Used when the cluster already exists.

```text
Existing OCP cluster ---> imported into ACM ---> becomes managed cluster
```

Use this for:

- Existing production clusters
- Customer-managed clusters
- Clusters created outside ACM
- Lab clusters
- Cloud clusters created manually

#### 2. Provision cluster from ACM

Used when ACM creates the cluster.

```text
ACM hub ---> provider credentials ---> create new OpenShift cluster
```

Possible provider types vary by version and support matrix, but common patterns include:

- AWS
- Azure
- GCP
- VMware vSphere
- OpenStack
- Bare metal / assisted installation
- Hosted control plane environments
- On-premises infrastructure

#### 3. Cluster pool and cluster claim

A `ClusterPool` pre-creates clusters and keeps them ready. A `ClusterClaim` allows a user or automation to claim one cluster quickly.

This is useful for:

- Developer self-service
- Training labs
- Temporary test environments
- CI/CD ephemeral clusters

```text
ClusterPool: dev-pool, size=5
  |-- cluster-a ready
  |-- cluster-b ready
  |-- cluster-c ready

Developer creates ClusterClaim ---> gets one ready cluster
```

#### 4. Hosted control planes

Hosted control planes separate the OpenShift control plane from worker nodes. This can reduce management overhead for large fleets or edge clusters. In ACM/MCE architecture, hosted control plane support is an important model for scale and edge use cases.

### Important cluster lifecycle resources

#### ManagedCluster

Represents a cluster that the hub knows about.

```bash
oc get managedcluster
oc describe managedcluster <name>
```

#### ClusterDeployment

Usually used for clusters provisioned through Hive-style workflows.

```bash
oc get clusterdeployment -A
oc describe clusterdeployment <name> -n <namespace>
```

#### ClusterImageSet

Defines OpenShift release images available for cluster creation.

```bash
oc get clusterimageset
```

#### ClusterCurator

Used for cluster lifecycle tasks such as upgrades in some workflows.

```bash
oc get clustercurator -A
```

#### KlusterletAddonConfig

Controls add-ons enabled for a managed cluster.

```bash
oc get klusterletaddonconfig -A
```

#### ManagedClusterAddOn

Shows status of add-ons on each managed cluster.

```bash
oc get managedclusteraddon -A
```

## 9. ManagedClusterSet, ClusterSetBinding, Placement, and PlacementDecision

This is one of the most important ACM concepts for enterprise architecture.

ACM must decide **which clusters** receive a policy, application, or GitOps registration. It does this with cluster grouping and placement resources.

### ManagedClusterSet

A `ManagedClusterSet` groups managed clusters.

Example cluster sets:

- `prod-clusters`
- `nonprod-clusters`
- `edge-clusters`
- `pci-clusters`
- `banking-clusters`
- `delhi-region`
- `dr-clusters`

A managed cluster can be assigned to a cluster set.

```bash
oc get managedclusterset
oc get managedcluster --show-labels
```

Conceptual example:

```text
ManagedClusterSet: prod-clusters
  - prod-delhi-01
  - prod-mumbai-01
  - prod-hyderabad-01

ManagedClusterSet: nonprod-clusters
  - dev-delhi-01
  - qa-delhi-01
```

### ManagedClusterSetBinding

A `ManagedClusterSetBinding` makes a cluster set available inside a namespace.

Why this matters:

- ACM resources such as policies and placements are often namespace-scoped.
- A namespace must be bound to a cluster set before it can place resources onto clusters from that set.

Example:

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta2
kind: ManagedClusterSetBinding
metadata:
  name: prod-clusters
  namespace: platform-governance
spec:
  clusterSet: prod-clusters
```

### Placement

A `Placement` selects clusters based on cluster sets, labels, claims, predicates, or other rules.

Example: select production clusters in India.

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta1
kind: Placement
metadata:
  name: prod-india-placement
  namespace: platform-governance
spec:
  clusterSets:
    - prod-clusters
  predicates:
    - requiredClusterSelector:
        labelSelector:
          matchLabels:
            environment: prod
            region: india
```

### PlacementDecision

A `PlacementDecision` is created by the placement controller. It shows which clusters were selected.

```bash
oc get placement -A
oc get placementdecision -A
oc describe placement prod-india-placement -n platform-governance
```

Example output concept:

```text
Placement: prod-india-placement
PlacementDecision:
  - prod-delhi-01
  - prod-mumbai-01
```

### Why placement is powerful

Instead of hard-coding cluster names in every policy or application, you label clusters and let ACM decide dynamically.

Example:

```bash
oc label managedcluster prod-delhi-01 environment=prod region=india compliance=pci
oc label managedcluster prod-mumbai-01 environment=prod region=india compliance=pci
oc label managedcluster dev-delhi-01 environment=dev region=india
```

Then use placements:

```text
All prod India clusters        -> environment=prod, region=india
All PCI clusters               -> compliance=pci
All edge clusters              -> cluster-type=edge
All clusters except DR         -> role!=dr
```

This is a core enterprise architecture pattern.

### Placement troubleshooting

If a policy or GitOpsCluster is not applying to a cluster, always check placement first.

```bash
oc get placement -A
oc describe placement <placement> -n <namespace>
oc get placementdecision -n <namespace>
oc get managedcluster --show-labels
oc get managedclusterset
oc get managedclustersetbinding -n <namespace>
```

Common causes:

- Cluster not in the expected cluster set.
- Cluster set not bound to the namespace.
- Label selector does not match cluster labels.
- Placement is in a different namespace from the consuming resource.
- Cluster has taints or conditions that prevent selection.
- Cluster is not `Available`.

## 10. Governance and Policy Management

Governance is one of ACM's strongest enterprise features.

In a production fleet, you need to guarantee that every cluster follows enterprise standards:

- Required namespaces exist.
- Required operators are installed.
- OAuth/identity providers are configured.
- Image registry sources are restricted.
- Insecure cluster settings are blocked.
- Certificates are valid.
- Etcd encryption is enabled.
- Network policies exist.
- SCC/RBAC rules are controlled.
- Compliance baselines are continuously checked.

Doing this manually for many clusters is not practical. ACM policies solve this.

### Governance architecture

```text
Hub cluster
  |
  | Root Policy
  | Placement
  | PlacementBinding
  | Policy propagator
  |
  +--> Managed cluster namespace on hub
          |
          | Replicated Policy
          |
          +--> Managed cluster
                  |
                  | Governance policy framework
                  | Configuration policy controller
                  | Certificate policy controller
                  | Operator policy controller
                  | Compliance status
```

### Policy objects

A typical ACM policy setup contains:

1. `Policy`
2. `Placement`
3. `PlacementBinding`

The policy defines **what** should be checked or enforced.
The placement defines **where** it should apply.
The placement binding connects the two.

### Inform vs Enforce

ACM policies commonly use two remediation modes:

| Mode | Behavior | Use Case |
|---|---|---|
| `inform` | Report non-compliance only | Audit, safe rollout, initial baseline |
| `enforce` | Automatically remediate drift | Mandatory enterprise controls |

A senior admin should never directly enforce a complex policy across production without testing.

Recommended rollout:

```text
1. Create policy in inform mode.
2. Apply to dev cluster set.
3. Review non-compliance.
4. Fix false positives.
5. Apply to non-prod.
6. Change to enforce where safe.
7. Apply to production in phases.
```

### Example: Namespace policy

This policy ensures a namespace exists on selected clusters.

```yaml
apiVersion: policy.open-cluster-management.io/v1
kind: Policy
metadata:
  name: policy-namespace-platform-tools
  namespace: platform-governance
spec:
  remediationAction: enforce
  disabled: false
  policy-templates:
    - objectDefinition:
        apiVersion: policy.open-cluster-management.io/v1
        kind: ConfigurationPolicy
        metadata:
          name: create-platform-tools-namespace
        spec:
          remediationAction: enforce
          severity: medium
          object-templates:
            - complianceType: musthave
              objectDefinition:
                apiVersion: v1
                kind: Namespace
                metadata:
                  name: platform-tools
```

Placement:

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta1
kind: Placement
metadata:
  name: placement-prod
  namespace: platform-governance
spec:
  clusterSets:
    - prod-clusters
  predicates:
    - requiredClusterSelector:
        labelSelector:
          matchLabels:
            environment: prod
```

PlacementBinding:

```yaml
apiVersion: policy.open-cluster-management.io/v1
kind: PlacementBinding
metadata:
  name: binding-policy-namespace-platform-tools
  namespace: platform-governance
placementRef:
  apiGroup: cluster.open-cluster-management.io
  kind: Placement
  name: placement-prod
subjects:
  - apiGroup: policy.open-cluster-management.io
    kind: Policy
    name: policy-namespace-platform-tools
```

### Example: Ensure etcd encryption is configured

Conceptual policy target:

```yaml
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  encryption:
    type: aescbc
```

This type of policy is high impact. Test carefully before enforcing.

### Example: Ensure an Operator is installed

Operator policies are useful for ensuring required operators exist across clusters, such as:

- OpenShift GitOps
- Compliance Operator
- File Integrity Operator
- Local Storage Operator
- ODF Operator
- OpenShift Pipelines
- Quay Bridge Operator

Conceptual example:

```yaml
apiVersion: policy.open-cluster-management.io/v1beta1
kind: OperatorPolicy
metadata:
  name: install-openshift-gitops
spec:
  remediationAction: enforce
  severity: medium
  complianceType: musthave
  subscription:
    name: openshift-gitops-operator
    namespace: openshift-operators
    channel: latest
    source: redhat-operators
    sourceNamespace: openshift-marketplace
```

Always verify the exact API version and supported fields for your ACM version.

### Policy compliance states

| State | Meaning |
|---|---|
| Compliant | Desired state exists or rule passes |
| NonCompliant | Desired state missing or rule fails |
| Pending | Evaluation pending |
| Unknown | Cluster unreachable or policy controller issue |
| Disabled | Policy disabled |

### Policy troubleshooting commands

```bash
oc get policy -A
oc describe policy <policy-name> -n <namespace>
oc get placement -A
oc get placementbinding -A
oc get placementdecision -A

oc get policy -n <managed-cluster-namespace>
oc describe policy <replicated-policy> -n <managed-cluster-namespace>

oc get pods -n open-cluster-management-agent-addon
oc logs -n open-cluster-management-agent-addon deploy/governance-policy-framework
```

### Governance best practices

- Use `inform` first.
- Use labels and placement, not static cluster names.
- Group policies into policy sets.
- Separate baseline, security, platform, app, and compliance policies.
- Avoid enforcing destructive changes without a rollback plan.
- Do not target local-cluster casually.
- Use GitOps to manage policy YAML.
- Use policy exceptions only with documented approval.
- Track policy compliance as an SRE KPI.

### Common governance use cases

| Use Case | Policy Type |
|---|---|
| Namespace must exist | ConfigurationPolicy |
| Operator must be installed | OperatorPolicy |
| Required RBAC must exist | ConfigurationPolicy |
| SCC must be restricted | SCC policy / ConfigurationPolicy |
| Etcd encryption enabled | ConfigurationPolicy |
| Image registry source allowed | ConfigurationPolicy |
| Certificate expiry check | CertificatePolicy |
| CIS baseline | Policy set / Compliance integration |
| Gatekeeper constraints | Gatekeeper policy |

## 11. Application Lifecycle and GitOps Integration

Modern ACM application lifecycle is closely connected with **OpenShift GitOps**, which is Red Hat's supported Argo CD distribution.

The best enterprise pattern is:

```text
Git repository = source of truth
OpenShift GitOps / Argo CD = sync engine
ACM Placement = cluster selection engine
ACM Governance = compliance guardrail
```

ACM should not become a place where administrators manually click-deploy applications. Mature organizations use GitOps and let ACM decide where applications should go.

### Application flow with ACM and GitOps

```text
Git repo
  |
  | Application manifests / Helm / Kustomize
  v
OpenShift GitOps / Argo CD on hub or management cluster
  |
  | GitOpsCluster + Placement
  v
Selected managed clusters from ACM
  |
  v
Applications deployed to target namespaces
```

### GitOpsCluster concept

A `GitOpsCluster` resource can register a group of managed clusters with an OpenShift GitOps instance based on ACM placement decisions.

Conceptual example:

```yaml
apiVersion: apps.open-cluster-management.io/v1beta1
kind: GitOpsCluster
metadata:
  name: prod-gitops-clusters
  namespace: openshift-gitops
spec:
  argoServer:
    cluster: local-cluster
    argoNamespace: openshift-gitops
  placementRef:
    apiVersion: cluster.open-cluster-management.io/v1beta1
    kind: Placement
    name: prod-placement
    namespace: openshift-gitops
```

The exact YAML can vary by ACM and OpenShift GitOps version, but the concept remains:

```text
Placement selects clusters.
GitOpsCluster registers those clusters into Argo CD.
Argo CD deploys apps to those clusters.
```

### Why this is powerful

Suppose you label clusters:

```bash
oc label managedcluster prod-delhi-01 environment=prod region=india app-zone=payments
oc label managedcluster prod-mumbai-01 environment=prod region=india app-zone=payments
```

Then the placement selects:

```text
environment=prod AND region=india AND app-zone=payments
```

When a new cluster is added with matching labels, ACM can include it in placement decisions. GitOps can then register it and deploy applications, depending on your automation design.

### Recommended repository structure

```text
platform-gitops/
  clusters/
    prod-delhi-01/
    prod-mumbai-01/
  policies/
    baseline/
    security/
    operators/
  applications/
    payments/
      base/
      overlays/
        dev/
        qa/
        prod/
  placements/
    prod-india.yaml
    nonprod-india.yaml
  argocd/
    applicationsets/
```

### ACM plus ApplicationSet pattern

An advanced pattern is using Argo CD ApplicationSet with cluster generators or Git generators, while ACM controls which clusters are registered and governed.

```text
ACM controls cluster inventory and placement.
Argo CD ApplicationSet controls app instantiation.
Git controls desired state.
```

### Common application lifecycle mistakes

- Deploying apps manually from the ACM console in production.
- Not using Git as source of truth.
- Hard-coding cluster names instead of using labels and placement.
- Registering every cluster to every Argo CD instance.
- Giving Argo CD cluster-admin everywhere without scoping.
- Not separating platform config from application config.
- Ignoring namespace/RBAC prerequisites before app sync.
- Not coordinating governance policies and GitOps sync.

### Senior-admin recommendation

Use ACM for **where** and **compliance**, use GitOps for **what** and **desired state**.

```text
ACM      = which clusters and whether they are compliant
GitOps   = what resources should exist
OpenShift = runtime platform
```

## 12. Observability Architecture

ACM observability gives fleet-level visibility across managed clusters.

A single OpenShift cluster already has monitoring through Prometheus, Alertmanager, and the OpenShift console. But in an enterprise fleet, you need cross-cluster views.

Questions ACM observability helps answer:

- Which clusters are unhealthy?
- Which clusters are under high CPU or memory pressure?
- Which clusters have unavailable nodes?
- Are there control plane issues across regions?
- Which clusters are close to capacity?
- Are there repeating alerts across many clusters?
- Which clusters need attention before business impact?

### Observability components

The observability architecture commonly includes:

- `multicluster-observability-operator` on hub
- `MultiClusterObservability` custom resource
- Thanos components on hub
- Object storage for metrics
- `observability-endpoint-operator` on managed clusters
- Metrics collector on managed clusters
- Grafana dashboards or ACM console views
- Alerting integration

### High-level flow

```text
Managed cluster Prometheus
      |
      | metrics collection
      v
observability endpoint operator
      |
      | sends metrics
      v
ACM hub observability service
      |
      | Thanos + object storage
      v
Fleet dashboards, alerts, health views
```

### Object storage requirement

ACM observability usually requires object storage for long-term metrics storage.

Possible storage backends depend on environment and supportability:

- AWS S3
- Azure Blob
- Google Cloud Storage
- ODF object bucket
- S3-compatible object storage

For on-prem environments, ODF Multicloud Object Gateway or another supported S3-compatible object store is common.

### MultiClusterObservability example

Conceptual example:

```yaml
apiVersion: observability.open-cluster-management.io/v1beta2
kind: MultiClusterObservability
metadata:
  name: observability
spec:
  observabilityAddonSpec:
    enableMetrics: true
  retentionConfig:
    retentionResolutionRaw: 5d
    retentionResolution5m: 14d
    retentionResolution1h: 30d
  storageConfig:
    metricObjectStorage:
      name: thanos-object-storage
      key: thanos.yaml
```

Always verify exact API version and fields for your ACM release.

### What to monitor on the hub

Hub health is critical. Monitor:

- ACM operator status
- MulticlusterHub status
- MCE status
- Hub etcd health
- Hub API health
- Search components
- Policy controller status
- Observability ingestion
- Thanos store/query/receive components
- Object storage availability
- Certificate expiry
- Managed cluster availability
- Add-on health

### Common observability issues

| Symptom | Possible Cause |
|---|---|
| No metrics from managed cluster | Add-on not enabled, network issue, endpoint operator failing |
| Thanos pods failing | Object storage secret/config issue |
| Query slow | Too much metric cardinality, undersized hub, object storage latency |
| Data gaps | Managed cluster disconnected, collector restart, object store issue |
| Alerts missing | Alert routing or rule configuration issue |
| Hub resource pressure | Observability not sized correctly |

### Observability troubleshooting commands

On hub:

```bash
oc get multiclusterobservability
oc describe multiclusterobservability observability

oc get pods -n open-cluster-management-observability
oc get pods -n open-cluster-management-addon-observability
oc get secret -n open-cluster-management-observability

oc get managedclusteraddon -A | grep observability
```

On managed cluster:

```bash
oc get pods -n open-cluster-management-addon-observability
oc logs -n open-cluster-management-addon-observability <pod-name>
oc get pods -n openshift-monitoring
```

## 14. Security, RBAC, Credentials, and Certificates

ACM is a high-value control plane. If an attacker compromises ACM hub admin access, they might be able to influence many clusters.

Therefore, ACM security must be designed carefully.

### Security principles

1. Treat the hub as a privileged management cluster.
2. Use least privilege RBAC.
3. Separate platform admin, security admin, app team, and view-only roles.
4. Use external identity providers.
5. Protect cloud/provider credentials.
6. Protect import tokens and kubeconfigs.
7. Use custom CA trust correctly.
8. Audit all hub actions.
9. Avoid broad cluster-admin access through GitOps or policies.
10. Use network controls around hub API and routes.

### ACM RBAC areas

RBAC exists at multiple layers:

| Layer | Example |
|---|---|
| OpenShift hub RBAC | Who can manage ACM resources on hub |
| ACM console roles | Who can view or operate managed clusters |
| ManagedClusterSet RBAC | Which users can access which cluster sets |
| Namespace RBAC | Who can manage policies in a namespace |
| Managed cluster RBAC | What agents or GitOps can do on target cluster |
| Cloud credential RBAC | Who can create/update provider credentials |

### Cluster set security model

Cluster sets help divide fleet responsibility.

Example:

```text
ClusterSet: banking-prod
  Admin group: platform-banking-admins
  View group: banking-auditors

ClusterSet: telecom-prod
  Admin group: platform-telecom-admins
  View group: telecom-auditors
```

This prevents every platform team from managing every cluster.

### Credential management

ACM can store credentials for providers such as cloud platforms or infrastructure providers.

These credentials are sensitive because they might allow cluster provisioning or infrastructure changes.

Best practices:

- Store credentials only in required namespaces.
- Use least-privilege cloud IAM roles.
- Rotate credentials regularly.
- Avoid shared personal accounts.
- Use service principals or service accounts.
- Protect backup containing secrets.
- Encrypt etcd on hub.
- Audit secret access.

### Certificate trust

ACM commonly needs certificate trust for:

- Hub API endpoint
- Hub routes
- Managed cluster API endpoints
- Proxy servers
- Private registries
- Object storage endpoints
- LDAP/OIDC endpoints
- Disconnected mirror registries

Common certificate issues:

- Managed cluster cannot trust hub certificate.
- Proxy uses TLS inspection and breaks trust.
- Object storage has custom CA.
- Registry uses self-signed certificate.
- Certificate rotation not propagated.

### Audit considerations

Enable and review:

- Hub OpenShift audit logs
- ACM policy changes
- RBAC changes
- Secret access
- Cluster lifecycle operations
- GitOps sync actions
- Provider credential updates
- Managed cluster detach/destroy events

### Network controls

The managed cluster must be able to communicate with the hub as required. In restricted environments, define exactly which endpoints are allowed.

At a high level:

```text
Managed cluster agent ---> Hub API / hub routes
Managed cluster metrics ---> Hub observability endpoint
Hub ---> Provider APIs during cluster creation
Hub ---> Object storage for observability/backup
Hub ---> Git repositories if GitOps runs on hub
Hub ---> Registry/catalog sources
```

Exact ports and endpoints depend on deployment mode and version. Always confirm using the product documentation and your network architecture.

## 15. Business Continuity, Backup, and Hub Disaster Recovery

The ACM hub contains critical fleet management state.

If the hub is lost, managed clusters continue running workloads, but centralized management, governance, search, observability, and lifecycle operations can be lost until the hub is restored.

### What happens if hub goes down?

Managed clusters do not immediately stop running applications. Applications continue on managed clusters because their Kubernetes control planes are independent.

But these functions are affected:

- Central policy visibility
- New policy propagation
- Search
- Observability dashboards
- Cluster lifecycle operations
- GitOps cluster registration updates
- Central governance reporting
- Managed cluster import/detach actions

### Hub backup scope

ACM backup should protect resources such as:

- ManagedCluster resources
- Cluster namespaces
- Policies
- Placements
- PlacementBindings
- Cluster sets
- Cluster credentials/secrets
- GitOps integration resources
- Observability configuration
- ACM configuration
- Selected hub resources needed for restore

### Active-passive hub pattern

```text
             Normal operation

+------------------+          +------------------+
| Active ACM Hub   |  backup  | Passive ACM Hub  |
| Region A         +--------->| Region B         |
+--------+---------+          +------------------+
         |
         | manages
         v
+------------------+
| Managed Clusters |
+------------------+
```

During disaster:

```text
+------------------+          +------------------+
| Failed Hub       | restore  | New Active Hub   |
| Region A         |--------->| Region B         |
+------------------+          +--------+---------+
                                      |
                                      | reactivates management
                                      v
                              +------------------+
                              | Managed Clusters |
                              +------------------+
```

### Important DR considerations

- Test hub restore before production disaster.
- Protect object storage used for backup.
- Secure backup secrets.
- Ensure passive hub version compatibility.
- Document managed cluster reattachment behavior.
- Validate policies after restore.
- Validate GitOps registration after restore.
- Validate observability ingestion after restore.
- Keep DNS and certificates ready for failover.

## 16. Enterprise Architecture Patterns

### Pattern 1: Single hub for small to medium enterprise

```text
+----------------+
| ACM Hub        |
+-------+--------+
        |
        +--- dev clusters
        +--- qa clusters
        +--- prod clusters
        +--- dr clusters
```

Use when:

- Cluster count is moderate.
- One platform team manages all clusters.
- Network latency is acceptable.
- Regulatory separation does not require multiple hubs.

Pros:

- Simple design.
- Lower operational overhead.
- Central visibility.

Cons:

- Hub becomes central dependency.
- Scaling limit depends on hub sizing and component capacity.
- Regional isolation might be weak.

### Pattern 2: Regional hubs

```text
                +----------------------+
                | Global operations     |
                | reporting / process   |
                +----------+-----------+
                           |
        +------------------+------------------+
        |                                     |
+-------+--------+                    +-------+--------+
| ACM Hub India  |                    | ACM Hub Europe |
+-------+--------+                    +-------+--------+
        |                                     |
   India clusters                         Europe clusters
```

Use when:

- Large number of clusters.
- Regional compliance requirements.
- Latency between regions is high.
- Teams are regionally aligned.

Pros:

- Better regional autonomy.
- Lower latency.
- Smaller blast radius.

Cons:

- Requires higher-level reporting or global hub strategy.
- Policies must be synchronized across hubs.
- More operational overhead.

### Pattern 3: Hub per business unit

```text
+----------------------+     +----------------------+
| Banking ACM Hub      |     | Retail ACM Hub       |
+----------+-----------+     +----------+-----------+
           |                            |
   banking clusters              retail clusters
```

Use when:

- Business units require strong isolation.
- Compliance boundaries are strict.
- Separate platform teams exist.

Pros:

- Clear ownership.
- Strong separation.
- Smaller failure domains.

Cons:

- Duplicate platform effort.
- Policy drift across business units unless centrally managed.

### Pattern 4: Edge fleet with ACM

```text
                    +---------------------+
                    | Central ACM Hub      |
                    +----------+----------+
                               |
      +------------------------+------------------------+
      |                        |                        |
+-----+------+          +------+-----+           +------+-----+
| Edge SNO 1 |          | Edge SNO 2 |           | Edge SNO N |
+------------+          +------------+           +------------+
```

Use when:

- Many edge locations.
- Single-node OpenShift.
- Retail, telecom, manufacturing, defense, remote sites.

Important design points:

- Intermittent connectivity is common.
- Policies should tolerate temporary disconnection.
- Local workloads must continue without hub.
- Observability retention and bandwidth must be planned.
- Upgrade waves must be controlled carefully.

### Pattern 5: Disconnected regulated environment

```text
                +--------------------------+
                | Disconnected ACM Hub      |
                +-------------+------------+
                              |
          +-------------------+-------------------+
          |                                       |
+---------+----------+                 +----------+---------+
| Disconnected OCP   |                 | Disconnected OCP   |
| prod               |                 | dr                 |
+--------------------+                 +--------------------+

Supporting services:
- Mirror registry
- Internal Git
- Internal object storage
- Internal DNS
- Internal NTP
- Internal CA
- Internal identity provider
```

Use when:

- Internet access is not allowed.
- Defense, government, banking, or regulated enterprise environment.
- All catalogs, images, releases, and Git repositories are internal.

Critical requirements:

- Mirror OpenShift release images.
- Mirror operator catalogs.
- Mirror ACM/MCE operator images.
- Configure imageContentSources or IDMS/ITMS depending on OCP version.
- Configure trusted CA bundles.
- Use internal object storage for observability and backup.
- Use internal Git for GitOps.
- Use OpenShift Update Service for disconnected upgrades where needed.

### Pattern 6: Global hub / multi-hub fleet

For very large environments, a single hub might not be sufficient. A global view across multiple hubs may be needed.

```text
                  +-----------------------+
                  | Multicluster Global   |
                  | Hub / global view     |
                  +-----------+-----------+
                              |
        +---------------------+---------------------+
        |                                           |
+-------+--------+                         +--------+-------+
| Regional Hub A |                         | Regional Hub B |
+-------+--------+                         +--------+-------+
        |                                           |
   Managed clusters                            Managed clusters
```

Use when:

- Organization has very large cluster count.
- Multiple hubs are required for scale or governance.
- Executives or central SRE team need global posture visibility.

## 17. Disconnected and Restricted Network Design

Disconnected ACM architecture is more complex than connected architecture.

You must plan every dependency.

### Required internal services

| Service | Why Needed |
|---|---|
| Mirror registry | Store OpenShift, ACM, MCE, operator, and app images |
| Internal Git | GitOps source of truth |
| Internal object storage | Observability and backup |
| Internal DNS | Cluster API, apps, registry, object storage |
| Internal NTP/chrony | Time sync for certs and tokens |
| Internal CA | Trust for registry, Git, object storage, proxies |
| LDAP/OIDC | Enterprise authentication |
| Proxy if needed | Controlled outbound connectivity |

### Disconnected upgrade flow

A typical disconnected upgrade flow includes:

1. Mirror release images.
2. Mirror operator catalog.
3. Update catalog sources.
4. Update image registry trust.
5. Use policies to configure managed clusters.
6. Use OpenShift Update Service or supported update channels.
7. Upgrade clusters in waves.
8. Validate health after each wave.

### Common disconnected failures

- CatalogSource cannot pull image.
- Registry certificate not trusted.
- Pull secret missing registry credentials.
- ImageDigestMirrorSet or ImageContentSourcePolicy mismatch.
- GitOps cannot access internal Git certificate.
- Observability cannot access object storage.
- Managed cluster import fails due to hub route DNS.
- Proxy excludes missing for cluster internal domains.
- NTP mismatch causes TLS/token issues.

### Senior-admin checklist

```text
[ ] Mirror registry reachable from hub and managed clusters
[ ] Pull secret includes mirror registry credentials
[ ] Custom CA installed on hub and managed clusters
[ ] CatalogSource pods healthy
[ ] ACM operator installed from mirrored catalog
[ ] MCE operator installed and healthy
[ ] Hub routes resolvable from managed clusters
[ ] Object storage reachable and trusted
[ ] Git repository reachable and trusted
[ ] OpenShift release images mirrored
[ ] Upgrade graph available if using OSUS
[ ] Policies tested in inform mode
[ ] Backup tested
```

## 18. Day-2 Operations with ACM

Day-2 operations are the daily activities after clusters are installed.

ACM is especially useful for Day-2 operations.

### Common Day-2 tasks

- Import new clusters.
- Apply baseline policies.
- Deploy required operators.
- Check compliance posture.
- Register clusters with GitOps.
- Upgrade clusters in waves.
- Monitor fleet health.
- Search for resources during incidents.
- Rotate credentials.
- Detach retired clusters.
- Restore hub resources after disaster.

### Cluster onboarding workflow

```text
1. Cluster created or discovered.
2. Import into ACM.
3. Label cluster with environment, region, owner, compliance, platform.
4. Add cluster to ManagedClusterSet.
5. Bind cluster set to governance namespace.
6. Baseline policies apply in inform mode.
7. Fix non-compliance.
8. Enable enforce mode for safe policies.
9. Register with GitOps placement.
10. Enable observability.
11. Add to upgrade wave.
12. Handover to operations dashboard.
```

### Example cluster labels

```bash
oc label managedcluster prod-delhi-01 environment=prod
oc label managedcluster prod-delhi-01 region=india
oc label managedcluster prod-delhi-01 datacenter=delhi-dc1
oc label managedcluster prod-delhi-01 owner=payments
oc label managedcluster prod-delhi-01 compliance=pci
oc label managedcluster prod-delhi-01 upgrade-wave=wave-2
oc label managedcluster prod-delhi-01 cluster-type=standard
```

```text
wave-0 = lab / canary
wave-1 = dev
wave-2 = qa
wave-3 = low-risk prod
wave-4 = critical prod
wave-5 = DR clusters
```

Use labels and placements:

```yaml
matchLabels:

```

Then apply upgrade policies or lifecycle actions to one wave at a time.

### Fleet compliance process

```text
Daily:
  - Review non-compliant policies
  - Check unavailable clusters
  - Check degraded add-ons
  - Check hub health
  - Check observability ingestion

Weekly:
  - Review exceptions
  - Review cluster labels
  - Review RBAC changes
  - Review backup status
  - Review upgrade readiness

Monthly:
  - Test restore
  - Review certificate expiry
  - Review disconnected mirror status
  - Review compliance trend
```

## 19. Troubleshooting Runbook

This section is written like a real L3 operations checklist.

### Issue 1: Managed cluster shows `Unknown` or `Unavailable`

Check from hub:

```bash
oc get managedcluster
oc describe managedcluster <cluster-name>
oc get managedclusteraddon -n <cluster-name>
oc get ns <cluster-name>
```

Check agent resources:

```bash
oc get manifestwork -n <cluster-name>
oc get appliedmanifestwork -A | grep <cluster-name>
```

On managed cluster:

```bash
oc get pods -n open-cluster-management-agent
oc get pods -n open-cluster-management-agent-addon
oc logs -n open-cluster-management-agent deploy/klusterlet-registration-agent
oc logs -n open-cluster-management-agent deploy/klusterlet-work-agent
```

Possible causes:

- Hub API route unreachable.
- Managed cluster DNS cannot resolve hub endpoint.
- Firewall blocks traffic.
- Proxy configuration missing.
- Certificate trust problem.
- Klusterlet registration token expired.
- Agent pod crashlooping.
- Hub was restored and managed cluster needs reactivation.

### Issue 2: Policy not reaching managed cluster

Check policy resources:

```bash
oc get policy -A
oc describe policy <policy> -n <namespace>
oc get placement -n <namespace>
oc get placementbinding -n <namespace>
oc get placementdecision -n <namespace>
```

Check cluster selection:

```bash
oc get managedcluster --show-labels
oc get managedclusterset
oc get managedclustersetbinding -n <namespace>
```

Common causes:

- Placement does not select any clusters.
- ClusterSetBinding missing.
- Policy and PlacementBinding in different namespace.
- Cluster label mismatch.
- Policy disabled.
- Managed cluster unavailable.
- Governance add-on degraded.

### Issue 3: Policy is non-compliant but resource exists

Check:

```bash
oc describe policy <policy> -n <namespace>
oc get policy <replicated-policy> -n <cluster-namespace> -o yaml
```

On managed cluster, verify object exactly:

```bash
oc get <resource> <name> -n <namespace> -o yaml
```

Possible causes:

- `complianceType` mismatch: `musthave`, `mustonlyhave`, or `mustnothave`.
- YAML field mismatch.
- Namespace mismatch.
- API version mismatch.
- Defaulted fields differ from expected fields.
- Object exists but not with required values.

### Issue 4: PlacementDecision is empty

Check:

```bash
oc describe placement <placement> -n <namespace>
oc get managedcluster --show-labels
oc get managedclustersetbinding -n <namespace>
```

Possible causes:

- No clusters match labels.
- Cluster set not bound.
- Placement references wrong cluster set.
- Managed clusters are unavailable.
- Taints/tolerations issue.

### Issue 5: GitOpsCluster not registering clusters

Check:

```bash
oc get gitopscluster -A
oc describe gitopscluster <name> -n <namespace>
oc get placement -n <namespace>
oc get placementdecision -n <namespace>
oc get managedclusteraddon -A | grep managed-serviceaccount
```

Check OpenShift GitOps:

```bash
oc get pods -n openshift-gitops
oc get argocd -A
oc logs -n openshift-gitops deploy/openshift-gitops-application-controller
```

Common causes:

- OpenShift GitOps operator not installed.
- Placement not selecting clusters.
- ManagedServiceAccount add-on not enabled.
- Argo CD RBAC issue.
- Cluster secret not created.
- Certificate trust issue.
- Namespace mismatch between GitOpsCluster and Placement.

### Issue 6: Observability not showing data

Check hub:

```bash
oc get multiclusterobservability
oc describe multiclusterobservability observability
oc get pods -n open-cluster-management-observability
oc get managedclusteraddon -A | grep observability
```

Check object storage secret:

```bash
oc get secret -n open-cluster-management-observability
oc describe secret thanos-object-storage -n open-cluster-management-observability
```

Check managed cluster:

```bash
oc get pods -n open-cluster-management-addon-observability
oc logs -n open-cluster-management-addon-observability <collector-pod>
```

Common causes:

- Object storage unreachable.
- Object storage credential wrong.
- CA not trusted.
- Add-on disabled.
- Managed cluster Prometheus unavailable.
- Network policy/firewall blocking metrics path.
- Hub resource pressure.

### Issue 7: ACM operator installed but MulticlusterHub not ready

Check:

```bash
oc get csv -n open-cluster-management
oc get mch -A
oc describe mch multiclusterhub -n open-cluster-management
oc get pods -n open-cluster-management
oc get pods -n multicluster-engine
```

Common causes:

- Subscription channel mismatch.
- CatalogSource issue.
- Pull secret issue.
- Image registry not reachable.
- Resource limits too low.
- Storage class missing.
- Required CRDs not installed.
- In disconnected environment, images not mirrored.

### Issue 8: Cannot detach or delete managed cluster

Check finalizers:

```bash
oc get managedcluster <cluster-name> -o yaml
oc get ns <cluster-name> -o yaml
```

Check cluster lifecycle resources:

```bash
oc get clusterdeployment -A | grep <cluster-name>
oc get manifestwork -n <cluster-name>
oc get managedclusteraddon -n <cluster-name>
```

Be careful with finalizer removal. Only remove finalizers manually when you understand the cleanup impact.

### Issue 9: Search not returning expected resources

Check:

```bash
oc get pods -n open-cluster-management
oc get managedclusteraddon -A | grep search
oc get pods -n open-cluster-management-agent-addon
```

Possible causes:

- Search add-on degraded.
- RBAC prevents visibility.
- Managed cluster unavailable.
- Search indexing delay.
- Resource type not collected.

### Issue 10: Hub restored but managed clusters not reconnecting

Check:


## 21. Example Enterprise Lab Scenario

This example shows how ACM concepts fit together.

### Requirement

An enterprise has four OpenShift clusters:

| Cluster | Environment | Region | Compliance | Purpose |
|---|---|---|---|---|
| `dev-delhi-01` | dev | india | standard | Development |
| `qa-delhi-01` | qa | india | standard | Testing |
| `prod-delhi-01` | prod | india | pci | Production |
| `prod-mumbai-01` | prod | india | pci | Production DR/HA |

Platform team wants:

- All clusters imported into ACM.
- Production clusters grouped separately.
- Baseline namespace created on all clusters.
- PCI policy applied only to production PCI clusters.
- Production clusters registered with OpenShift GitOps.
- Observability enabled for all clusters.

### Step 1: Label clusters

```bash
oc label managedcluster dev-delhi-01 environment=dev region=india compliance=standard
oc label managedcluster qa-delhi-01 environment=qa region=india compliance=standard
oc label managedcluster prod-delhi-01 environment=prod region=india compliance=pci
oc label managedcluster prod-mumbai-01 environment=prod region=india compliance=pci
```

### Step 2: Create cluster sets

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta2
kind: ManagedClusterSet
metadata:
  name: prod-clusters
---
apiVersion: cluster.open-cluster-management.io/v1beta2
kind: ManagedClusterSet
metadata:
  name: nonprod-clusters
```

### Step 3: Bind cluster set to governance namespace

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta2
kind: ManagedClusterSetBinding
metadata:
  name: prod-clusters
  namespace: platform-governance
spec:
  clusterSet: prod-clusters
```

### Step 4: Create placement for PCI production clusters

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta1
kind: Placement
metadata:
  name: placement-prod-pci-india
  namespace: platform-governance
spec:
  clusterSets:
    - prod-clusters
  predicates:
    - requiredClusterSelector:
        labelSelector:
          matchLabels:
            environment: prod
            region: india
            compliance: pci
```

### Step 5: Create baseline namespace policy

```yaml
apiVersion: policy.open-cluster-management.io/v1
kind: Policy
metadata:
  name: policy-platform-baseline
  namespace: platform-governance
spec:
  remediationAction: enforce
  disabled: false
  policy-templates:
    - objectDefinition:
        apiVersion: policy.open-cluster-management.io/v1
        kind: ConfigurationPolicy
        metadata:
          name: create-platform-baseline-namespace
        spec:
          remediationAction: enforce
          severity: low
          object-templates:
            - complianceType: musthave
              objectDefinition:
                apiVersion: v1
                kind: Namespace
                metadata:
                  name: platform-baseline
```

### Step 6: Bind policy to placement

```yaml
apiVersion: policy.open-cluster-management.io/v1
kind: PlacementBinding
metadata:
  name: bind-platform-baseline-prod
  namespace: platform-governance
placementRef:
  apiGroup: cluster.open-cluster-management.io
  kind: Placement
  name: placement-prod-pci-india
subjects:
  - apiGroup: policy.open-cluster-management.io
    kind: Policy
    name: policy-platform-baseline
```

### Step 7: Verify

```bash
oc get placementdecision -n platform-governance
oc get policy -n platform-governance
oc describe policy policy-platform-baseline -n platform-governance
```

On selected managed clusters:

```bash
oc get ns platform-baseline
```

### Architecture result

```text
ACM Hub
  |
  | placement-prod-pci-india
  | policy-platform-baseline
  |
  +--> prod-delhi-01
  +--> prod-mumbai-01

Non-prod clusters are not selected by this specific placement.
```

## 22. Interview and Real-World Questions

### Q1. What is ACM in OpenShift?

ACM is Red Hat's multi-cluster management platform. It provides centralized cluster lifecycle, governance, application placement through GitOps integration, observability, search, and security controls across OpenShift and Kubernetes clusters.

### Q2. What is a hub cluster?

The hub cluster is the OpenShift cluster where ACM is installed. It stores ACM resources and runs controllers that manage the fleet.

### Q3. What is a managed cluster?

A managed cluster is an OpenShift or Kubernetes cluster that is imported into or created by ACM. It runs klusterlet and add-ons so the hub can manage it.

### Q4. What is klusterlet?

Klusterlet is the agent installed on managed clusters. It handles registration, work execution, and communication with the hub.

### Q5. What is MCE?

MCE, or multicluster engine, provides cluster lifecycle management capabilities. It can run standalone or as part of ACM.

### Q6. What is ManagedClusterSet?

A ManagedClusterSet is a logical grouping of managed clusters. It is used for isolation, RBAC, and placement.

### Q7. What is Placement?

Placement is an ACM resource that selects managed clusters based on cluster sets, labels, and conditions. It produces PlacementDecision resources.

### Q8. Why is PlacementDecision important?

PlacementDecision shows the actual clusters selected by a Placement. It is critical for troubleshooting policies and GitOps integration.

### Q9. What is ACM governance?

Governance is ACM's policy framework for checking and enforcing desired cluster configuration across the fleet.

### Q10. What is inform mode?

Inform mode reports non-compliance but does not change the managed cluster.

### Q11. What is enforce mode?

Enforce mode automatically remediates drift by creating or modifying resources to match the policy.

### Q12. How does ACM integrate with GitOps?

ACM uses placement to select clusters and GitOpsCluster resources to register selected managed clusters with OpenShift GitOps/Argo CD. Argo CD then deploys applications from Git.

### Q13. Does ACM replace Argo CD?

No. ACM does not replace Argo CD. ACM selects and governs clusters. Argo CD syncs application desired state from Git.

### Q14. Does ACM replace RHACS?

No. ACM provides governance and management. RHACS provides container security, vulnerability management, compliance scanning, and runtime security.

### Q15. What happens if ACM hub is down?

Managed clusters continue running workloads, but central management, policy propagation, observability, search, and lifecycle operations are impacted until the hub is restored.

### Q16. How do you troubleshoot a managed cluster showing unavailable?

Check `ManagedCluster` status on hub, add-on status, klusterlet pods on managed cluster, network connectivity, DNS, proxy, certificates, and registration agent logs.

### Q17. Why is a policy not applying to a cluster?

Most common causes are missing ClusterSetBinding, Placement selector mismatch, cluster labels missing, cluster unavailable, policy disabled, or governance add-on degraded.

### Q18. Why is observability not showing metrics?

Possible causes include object storage issue, observability add-on disabled, endpoint operator failure, network blockage, Prometheus issue on managed cluster, or CA trust problem.

### Q19. How do you organize clusters in enterprise ACM?

Use labels and ManagedClusterSets by environment, region, compliance, owner, upgrade wave, and platform type.

### Q20. What is the safest way to roll out governance policies?

Start with `inform` mode on dev clusters, fix false positives, promote to non-prod, then enforce safe policies in production using phased placements.

## 23. Best Practices for Senior OpenShift Administrators

### Hub design

- Use a dedicated hub cluster.
- Size the hub for cluster count and enabled features.
- Do not run heavy application workloads on the hub.
- Use HA control plane and worker nodes.
- Protect hub etcd.
- Enable hub backup and restore.
- Monitor hub aggressively.
- Keep ACM/MCE versions supported.

### Cluster onboarding

- Define naming standards.
- Label every cluster consistently.
- Assign clusters to correct cluster sets.
- Enable required add-ons only.
- Validate governance status before production use.
- Register with GitOps only after baseline policies pass.

### Governance

- Store policies in Git.
- Use `inform` before `enforce`.
- Use policy sets for organization.
- Avoid huge monolithic policies.
- Use small, readable policies.
- Separate baseline, security, operator, and application policies.
- Track compliance trend.
- Document exceptions.

### GitOps

- Use Git as source of truth.
- Use ACM placement for cluster selection.
- Scope Argo CD permissions carefully.
- Avoid manual console drift.
- Separate app GitOps from platform GitOps.
- Review sync waves and dependencies.

### Observability

- Plan object storage capacity.
- Control metric cardinality.
- Monitor ingestion lag.
- Tune retention.
- Use alerts for hub and managed cluster health.
- Review dashboards regularly.

### Security

- Use enterprise identity provider.
- Avoid shared admin accounts.
- Limit cluster-admin.
- Rotate provider credentials.
- Encrypt etcd.
- Protect backups.
- Use audit logs.
- Review RBAC quarterly.
- Secure hub ingress/API.

### Disconnected

- Mirror all required images.
- Validate CatalogSources.
- Configure trusted CA bundles.
- Test import in disconnected mode.
- Use internal Git and object storage.
- Test upgrades before production.

### Operations

- Use upgrade waves.
- Maintain runbooks.
- Test hub restore.
- Review managed cluster add-on status daily.
- Use labels for automation.
- Avoid manual finalizer removal unless necessary.
- Keep documentation current.
