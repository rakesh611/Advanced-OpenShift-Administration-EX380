## 1. Executive Summary

A **hub-spoke architecture** is a multicluster enterprise architecture where one or more central management clusters, called **hub clusters**, manage many workload clusters, called **spoke clusters** or **managed clusters**.

In OpenShift enterprise environments, the hub-spoke model is commonly implemented with:

- **Red Hat Advanced Cluster Management for Kubernetes (RHACM / ACM)**
- **multicluster engine for Kubernetes (MCE)**
- **Open Cluster Management (OCM)** concepts such as `ManagedCluster`, `Klusterlet`, `Placement`, `ManagedClusterSet`, and `ManifestWork`
- **OpenShift GitOps / Argo CD** for declarative application and platform configuration
- **Policy framework** for security and compliance governance
- **Observability** for fleet-wide visibility
- **Submariner or external networking patterns** for multicluster service connectivity when required

The hub-spoke pattern separates **central control** from **local workload execution**.

The hub does not normally run all production business workloads. Instead, it acts as the command, control, governance, visibility, and automation layer. Spoke clusters run application workloads close to business units, regions, environments, data centers, cloud accounts, edge sites, or customers.

For a senior OpenShift administrator, hub-spoke architecture is not only about installing ACM. It is about designing a secure, scalable, reliable, auditable, and maintainable fleet operating model.

## 2. What Hub-Spoke Architecture Means

### Simple Definition

A **hub-spoke architecture** is a topology where a central system coordinates many distributed systems.

In OpenShift:

```text
                     +------------------------+
                     |      Hub Cluster       |
                     |  ACM / MCE / GitOps    |
                     |  Governance / Search   |
                     |  Observability         |
                     +-----------+------------+
                                 |
        -----------------------------------------------------
        |                |                 |                |
+-------+------+ +-------+------+ +--------+------+ +-------+------+
| Spoke Cluster| | Spoke Cluster| | Spoke Cluster | | Spoke Cluster|
|   Dev        | |   QA         | |   Production  | |   Edge       |
+--------------+ +--------------+ +---------------+ +--------------+
```

The hub cluster provides centralized management. Spoke clusters remain independent Kubernetes/OpenShift clusters that run workloads and local control planes.

### Enterprise Definition

In enterprise architecture, hub-spoke means:

- Centralized governance
- Decentralized workload execution
- Standardized platform configuration
- Distributed failure boundaries
- Consistent policy enforcement
- Fleet-wide visibility
- Controlled day-2 operations
- Automated cluster lifecycle management
- Separation between platform team and application teams

### Practical OpenShift Meaning

In OpenShift administration, the hub-spoke model allows a platform team to answer questions like:

- Which clusters are running OpenShift 4.14, 4.15, 4.16, or newer?
- Which clusters are non-compliant with security policy?
- Which clusters have missing ingress certificates?
- Which clusters are missing monitoring configuration?
- Which production clusters need upgrade?
- Which clusters belong to the banking, telecom, retail, or edge environment?
- Which clusters should receive a specific application deployment?
- Which clusters can be managed by a certain operations team?

## 3. Why Enterprises Use Hub-Spoke for OpenShift

### 3.1 Multicluster Reality

Large organizations rarely run a single OpenShift cluster. They normally run many clusters because of:

- Environment separation: dev, test, staging, production
- Business unit separation
- Regional or country-specific requirements
- Disaster recovery requirements
- Cloud provider separation
- On-premises and public cloud hybrid strategy
- Edge locations
- Security boundaries
- Data residency rules
- Performance and latency requirements
- Upgrade ring strategy

Without a hub-spoke model, each cluster becomes an isolated island. Operations teams then manage every cluster manually using different kubeconfigs, different scripts, different policies, and different procedures. That approach does not scale.

### 3.2 Centralized Governance Without Centralized Workloads

The hub-spoke design allows a platform team to centrally define standards while allowing workloads to remain distributed.

Examples:

- All production clusters must have audit log forwarding enabled.
- All clusters must use approved image registries.
- All namespaces must have resource quotas.
- All clusters must have trusted CA bundles configured.
- All clusters must reject privileged workloads except approved namespaces.
- All clusters must enforce NetworkPolicy defaults.

The hub becomes the control center for governance, not the single place where every application runs.

### 3.3 Better Failure Isolation

A single huge OpenShift cluster can become a large blast radius. Hub-spoke allows failures to be isolated.

Example:

- A broken production deployment in `prod-east` does not directly break `prod-west`.
- A cloud provider network issue in AWS does not directly break on-premises workloads.
- A regional DNS issue does not necessarily break all clusters.
- A failed upgrade can be isolated to a small upgrade ring.

### 3.4 Consistent Day-2 Operations

Day-2 operations include:

- Upgrade
- Certificate rotation
- Policy enforcement
- Application rollout
- Backup validation
- Monitoring
- Troubleshooting
- Access control review
- Compliance reporting
- Capacity review

A hub-spoke architecture provides a consistent operating model for all these activities.

| Term | Meaning |

| Spoke cluster | Workload cluster managed by the hub. Also called managed cluster. |
| Managed cluster | A cluster imported into ACM or created by ACM/MCE and managed from the hub. |
| Klusterlet | Agent installed on a managed cluster that connects the managed cluster to the hub. |
| Cluster manager | OCM control-plane component running on the hub side. |
| MultiClusterHub | ACM custom resource used to install/manage ACM hub components. |
| MultiClusterEngine | MCE custom resource used for cluster lifecycle capabilities. |
| ManagedCluster | Hub-side custom resource representing a spoke cluster. |

| Placement | Resource used to select target clusters based on labels, claims, sets, and other rules. |
| PlacementDecision | Output resource showing which clusters were selected by a Placement. |

| ClusterClaim | Metadata reported by a managed cluster to the hub, often used for placement decisions. |
| Add-on | Additional capability deployed to managed clusters, such as observability, GitOps, or Submariner. |
| Global Hub | Higher-level management layer used to manage multiple hub clusters. |

## 5. Logical Architecture

### 5.1 High-Level Logical View

```text
+----------------------------------------------------------------------------------+
|                                  Enterprise Users                                 |
| Platform Admins | SRE | Security | Compliance | App Teams | Operations | Auditors |
+-----------------------------------------+----------------------------------------+
                                          |
                                          v
+----------------------------------------------------------------------------------+
|                                   Hub Cluster                                    |
|----------------------------------------------------------------------------------|
| OpenShift Console Plugin | ACM Console | Search | Governance | Observability      |
| Cluster Lifecycle | MCE | GitOps Integration | Policy Framework | RBAC              |
| MultiClusterHub | MultiClusterEngine | Cluster Manager | Placement Controller       |
+------------------+----------------------+----------------------+------------------+
                   |                      |                      |
                   v                      v                      v
        +----------+----------+ +---------+----------+ +---------+----------+
        | Managed Cluster A   | | Managed Cluster B  | | Managed Cluster C  |
        | Dev / QA            | | Prod / Region 1    | | Prod / Region 2    |
        | Klusterlet          | | Klusterlet         | | Klusterlet         |
        | App Workloads       | | App Workloads      | | App Workloads      |
        +---------------------+ +--------------------+ +--------------------+
```

### 5.2 Management Plane vs Workload Plane

A good enterprise design clearly separates the **management plane** and the **workload plane**.

#### Management Plane

Runs on the hub cluster:

- ACM console
- MCE
- Cluster lifecycle controllers
- Governance controllers
- Placement controllers
- Search components
- Observability components
- GitOps integration controllers
- Cluster inventory and compliance data

#### Workload Plane

Runs on spoke clusters:

- Application namespaces
- Application deployments
- Local ingress/router
- Local registry pull configuration
- Local monitoring stack
- Local storage classes
- Local node autoscaling
- Local SCC/RBAC enforcement
- Local network policies

### 5.3 Hub Is Not a Replacement for Spoke Control Planes

Each spoke cluster has its own Kubernetes/OpenShift API server, scheduler, controller manager, etcd, ingress, monitoring, and operators. The hub does not replace those local control planes.

The hub provides fleet-level orchestration and desired-state management.

## 6. Hub Cluster Responsibilities

The hub cluster is the most important component in the architecture. It is not just another OpenShift cluster. It is a management control plane for the fleet.

### 6.1 Main Responsibilities

The hub is responsible for:

1. Cluster inventory
2. Cluster lifecycle management
3. Cluster import and detach
4. Policy definition and compliance reporting
5. Placement and targeting
6. Fleet-wide search
7. Observability aggregation
8. Application deployment orchestration
9. GitOps integration
10. Add-on management
11. Central RBAC for fleet operations
12. Audit and compliance visibility
13. Upgrade coordination
14. Managed cluster health status
15. Multicluster troubleshooting entry point

### 6.2 What Should Run on the Hub

Recommended workloads on the hub:

- ACM/MCE operators and components
- OpenShift GitOps controller, if used centrally
- External Secrets or secret integration components, if part of platform control
- Observability stack required by ACM
- Policy automation tools
- Platform automation jobs
- Lightweight dashboards
- Integration components for ITSM, CMDB, ticketing, or SIEM

### 6.3 What Should Not Run on the Hub

Avoid running heavy business workloads on the hub unless the hub is intentionally designed as a local managed cluster too.

Avoid:

- High-volume customer-facing workloads
- Large databases unrelated to hub operations
- Uncontrolled CI build workloads
- Non-platform application workloads
- Experimental workloads
- Heavy batch jobs

Reason: Hub stability is fleet stability. If the hub becomes unstable, you lose central visibility and control.

### 6.4 Hub Cluster Sizing Considerations

Hub sizing depends on:

- Number of managed clusters
- Number of resources indexed by Search
- Number of policies
- Observability volume
- Retention period
- Number of users
- GitOps workload
- Frequency of policy evaluation
- Number of add-ons

For enterprise design, treat the hub as a critical shared service.

Plan for:

- Dedicated worker nodes for management workloads
- Infrastructure node placement where supported
- Fast storage for observability/search components
- Proper etcd performance
- Load-balanced API endpoint
- Backup and restore
- Upgrade windows
- Monitoring and alerting

## 7. Spoke Cluster Responsibilities

A spoke cluster is a managed workload cluster. It can be a full OpenShift cluster in a data center, public cloud, private cloud, lab, edge location, or hosted control plane environment.

### 7.1 Main Responsibilities

A spoke cluster is responsible for:

- Running application workloads
- Enforcing local Kubernetes/OpenShift policies
- Running local operators
- Providing local ingress and service routing
- Providing local persistent storage
- Providing local monitoring and logging
- Running the klusterlet agent
- Applying work sent from the hub
- Reporting status and compliance back to the hub
- Running add-ons such as observability or GitOps agents

### 7.2 Spoke Cluster Independence

A key advantage of hub-spoke architecture is that a spoke should continue running existing workloads even if hub connectivity is temporarily lost.

If the hub is unavailable:

- Existing workloads should continue running on the spoke.
- Local OpenShift API should continue working.
- Local admins should still be able to manage the cluster directly.
- New hub-driven policy/application updates will not be delivered until connectivity returns.
- Compliance status and observability updates may become stale.

### 7.3 Spoke Cluster Types

Common spoke types:

| Type | Description |
|---|---|
| Development spoke | Used by developers and CI/CD pipelines. |
| QA spoke | Used for test validation. |
| Production spoke | Runs critical applications. |
| Edge spoke | Small or remote cluster close to devices/users. |
| Regional spoke | Cluster serving one geographic region. |
| Cloud spoke | Cluster running in AWS, Azure, GCP, IBM Cloud, etc. |
| On-prem spoke | Cluster running in customer data center. |
| Hosted control plane spoke | Workload nodes are separated from hosted control plane components. |
| Local cluster | Hub cluster also imported as a managed cluster. |

## 8. Red Hat ACM and Open Cluster Management Components

### 8.1 Red Hat Advanced Cluster Management

Red Hat Advanced Cluster Management for Kubernetes provides enterprise multicluster management for Kubernetes and OpenShift fleets.

In hub-spoke architecture, ACM commonly provides:

- Cluster lifecycle
- Application lifecycle
- Governance
- Observability
- Search
- Cluster inventory
- Multicluster RBAC integration
- Policy management
- GitOps integration
- Global hub capabilities

### 8.2 multicluster engine for Kubernetes

The multicluster engine provides cluster lifecycle management capabilities.

It is responsible for features such as:

- Creating clusters
- Importing existing clusters
- Managing cluster credentials
- Detaching clusters
- Managing cluster pools where supported
- Hosted control plane integration
- Cluster lifecycle APIs

In modern ACM installations, MCE is included as part of the ACM installation.

### 8.3 Open Cluster Management Foundation

Open Cluster Management provides the core hub-agent model.

Conceptually:

```text
Hub side:    Cluster Manager / Registration / Work controllers
Spoke side:  Klusterlet / Registration agent / Work agent
```

The managed cluster runs an agent that connects back to the hub. This is important because many enterprise networks do not allow inbound connections from central management systems into production clusters. Outbound-from-spoke communication is usually easier to approve through firewalls.

### 8.4 Klusterlet

The klusterlet is installed on each managed cluster.

It handles:

- Registration with hub
- Authentication to hub
- Receiving work from hub
- Applying work locally
- Reporting status
- Running add-on controllers

Typical namespaces include variations such as:

```bash
open-cluster-management
open-cluster-management-agent
open-cluster-management-agent-addon
```

Actual namespace names can vary by product version and add-on.

### 8.5 ManagedCluster Resource

On the hub cluster, every spoke is represented as a `ManagedCluster`.

Example commands:

```bash
oc get managedclusters
oc describe managedcluster <cluster-name>
oc get managedcluster <cluster-name> -o yaml
```

Important status fields:

- `ManagedClusterConditionAvailable`
- Joined/accepted status
- URL/API information
- Cluster labels
- Cluster claims
- Add-on status

### 8.6 ManagedClusterAddOn

Add-ons extend spoke capabilities.

Example:

```bash
oc get managedclusteraddon -A
oc describe managedclusteraddon <addon-name> -n <managed-cluster-name>
```

Common add-ons:

- Observability
- Search collector
- Application manager
- GitOps
- Submariner
- Managed service account

## 9. Control Plane Flow: How Hub and Spokes Communicate

### 9.1 Basic Communication Pattern

The common pattern is:

```text
Spoke Klusterlet  --->  Hub API Server
Spoke Add-ons     --->  Hub API Server / Observability endpoint
Hub Controllers   --->  Hub local resources representing desired state
Spoke Agents      --->  Pull desired work and apply locally
```

This is a **hub-agent** model.

The hub stores desired state. The spoke agent retrieves and reconciles it.

### 9.2 Why Pull-Based Communication Matters

Pull-based communication is useful because:

- Production clusters often sit behind firewalls.
- Central systems may not be allowed to initiate direct inbound traffic to all clusters.
- Spoke clusters can reconnect after network interruption.
- The model resembles Kubernetes node/kubelet behavior.
- Local reconciliation remains possible even when central control is temporarily disrupted.

### 9.3 Registration Flow

Typical registration process:

1. Hub cluster has ACM/MCE installed.
2. Administrator creates/imports a managed cluster.
3. Import command or manifest is generated.
4. Manifest is applied on the spoke cluster.
5. Klusterlet starts on the spoke.
6. Spoke requests registration with the hub.
7. Hub administrator accepts or approves the managed cluster.
8. Hub creates or updates `ManagedCluster` status.
9. Add-ons are deployed/enabled as required.
10. Hub begins managing the spoke.

### 9.4 Work Distribution Flow

Typical work distribution:

```text
Admin/GitOps creates policy/application on hub
              |
              v
Placement selects target clusters
              |
              v
Hub creates ManifestWork or policy work objects
              |
              v
Klusterlet/work agent on spoke reads work
              |
              v
Spoke applies Kubernetes resources locally
              |
              v
Status is reported back to hub
```

### 9.5 Status Reporting

Spokes report:

- Cluster health
- Add-on health
- Policy compliance
- Work application status
- Metrics, if observability is enabled
- Cluster claims and labels
- Application status

### 9.6 Failure Behavior

| Failure | Expected Impact |
|---|---|
| Hub unavailable | Existing spoke workloads continue; new central changes stop. |
| Spoke API unavailable | Hub shows cluster unavailable or stale. |
| Klusterlet down | Managed cluster cannot receive work or report status. |
| Network blocked from spoke to hub | Cluster becomes unavailable from hub perspective. |
| Observability storage issue | Metrics aggregation can fail while cluster management may still work. |
| Policy controller issue | Compliance status may become stale or incorrect. |

## 10. Cluster Lifecycle Management

Cluster lifecycle means creating, importing, managing, upgrading, scaling, hibernating, resuming, detaching, and destroying clusters.

### 10.1 Create vs Import

#### Create Cluster from Hub

The hub provisions a new cluster using supported infrastructure integration.

Use cases:

- Standardized production cluster creation
- Cloud cluster factory model
- Cluster-as-a-service
- Temporary clusters
- Developer self-service clusters

#### Import Existing Cluster

A cluster already exists and is imported into hub management.

Use cases:

- Existing OpenShift estate
- Acquired business unit clusters
- Clusters created by another team
- Edge clusters deployed earlier
- Migration into central governance

### 10.2 Cluster Import Best Practices

Before importing a cluster, verify:

```bash
oc whoami
oc cluster-info
oc get clusterversion
oc get nodes
oc get co
oc get authentication.operator cluster -o yaml
oc get proxy/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
```

Check:

- Cluster health is good.
- API is reachable from admin workstation.
- Spoke can reach hub API.
- Required trust bundle is configured.
- Pull secret can access required images.
- Proxy settings are known.
- DNS resolution works.
- Time synchronization is correct.
- Cluster name follows naming standard.

### 10.3 Cluster Naming Standard

A strong enterprise naming standard is important.

Example:

```text
<business-unit>-<environment>-<region>-<sequence>
```

Examples:

```text
bank-prod-in-01
bank-prod-in-02
retail-dev-aws-usw2-01
edge-store-delhi-001
telco-ran-west-003
```

Recommended labels:

```bash
oc label managedcluster bank-prod-in-01 environment=prod
oc label managedcluster bank-prod-in-01 region=india
oc label managedcluster bank-prod-in-01 provider=onprem
oc label managedcluster bank-prod-in-01 business-unit=banking
oc label managedcluster bank-prod-in-01 criticality=tier1
oc label managedcluster bank-prod-in-01 compliance=pci
```

### 10.4 Cluster Upgrade Strategy

Never upgrade all clusters at once.

Use upgrade rings:

```text
Ring 0: Lab / sandbox
Ring 1: Dev
Ring 2: QA / staging
Ring 3: Non-critical production
Ring 4: Critical production
Ring 5: Edge / special sites
```

Upgrade flow:

1. Confirm hub version supports target spoke version.
2. Confirm operators are compatible.
3. Confirm storage CSI compatibility.
4. Confirm CNI compatibility.
5. Confirm node firmware and OS requirements.
6. Upgrade lab clusters first.
7. Validate monitoring, ingress, DNS, registry, storage, and authentication.
8. Upgrade dev and QA.
9. Run application smoke tests.
10. Upgrade production in controlled batches.

Useful commands:

```bash
oc get managedclusters
oc get clusterversion -A
oc get co
oc adm upgrade
oc adm upgrade --to=<version>
oc get mcp
oc get nodes
oc get events -A --sort-by=.lastTimestamp
```

### 10.5 Cluster Detach vs Destroy

| Action | Meaning |
|---|---|
| Detach | Remove cluster from hub management but keep cluster running. |
| Destroy | Delete the cluster infrastructure if it was created by hub/lifecycle tooling. |
| Decommission | Formal enterprise process including backup, DNS cleanup, monitoring cleanup, CMDB update, and access removal. |

Do not confuse detach with destroy.

### 10.6 Cluster Lifecycle Governance

A production-grade platform should maintain:

- Cluster owner
- Business owner
- Environment type
- Support team
- Criticality
- Data classification
- Compliance scope
- Upgrade ring
- Backup policy
- DR tier
- Location/region
- Cloud provider/account
- Expiry date for temporary clusters

These attributes can be represented through labels, annotations, CMDB integration, or Git inventory.

## 11. GitOps and Application Lifecycle in Hub-Spoke

### 11.1 Why GitOps Fits Hub-Spoke

GitOps is a natural fit because hub-spoke architecture needs consistent, repeatable, auditable configuration.

Git becomes the source of truth for:

- Cluster configuration
- Policies
- Namespace templates
- Operator subscriptions
- RBAC
- NetworkPolicies
- Quotas and LimitRanges
- Applications
- Environment-specific overlays
- Placement rules

### 11.2 Common GitOps Models

#### Model 1: Central Argo CD on Hub

```text
Git Repo ---> Argo CD on Hub ---> Target Spoke Clusters
```

Pros:

- Centralized control
- Easier audit
- Single place for app sync status
- Good for platform configuration

Cons:

- Hub becomes more critical
- Network/authentication to all spokes must be designed carefully
- Large scale may require sharding or multiple Argo CD instances

#### Model 2: Argo CD on Each Spoke

```text
Git Repo ---> Argo CD on each Spoke ---> Local Cluster
```

Pros:

- Local autonomy
- Better failure isolation
- Spoke can continue syncing even if hub is disconnected
- Good for application teams

Cons:

- More Argo CD instances to manage
- Requires consistent bootstrap
- More operational overhead

#### Model 3: Hybrid GitOps

```text
Hub Argo CD: platform baseline, governance, operators
Spoke Argo CD: app team workloads
```

This is often the best enterprise model.

### 11.3 Repository Structure

Example structure:

```text
gitops-platform/
├── clusters/
│   ├── bank-prod-in-01/
│   │   ├── kustomization.yaml
│   │   ├── labels.yaml
│   │   └── overlays/
│   ├── bank-prod-in-02/
│   └── retail-dev-aws-usw2-01/
├── cluster-sets/
│   ├── prod-india.yaml
│   ├── dev.yaml
│   └── edge.yaml
├── policies/
│   ├── security/
│   ├── compliance/
│   ├── operators/
│   ├── networking/
│   └── monitoring/
├── placements/
│   ├── prod-india-placement.yaml
│   ├── dev-placement.yaml
│   └── edge-placement.yaml
├── operators/
│   ├── openshift-gitops/
│   ├── cert-manager/
│   ├── logging/
│   └── odf/
└── apps/
    ├── frontend/
    ├── backend/
    └── database/
```

### 11.4 GitOps Promotion Flow

```text
Dev branch ---> Dev clusters
Release branch ---> QA clusters
Tag v1.2.3 ---> Staging clusters
Approved release ---> Production clusters
```

Use labels and placement rules to target clusters.

Example labels:

```yaml
environment: prod
region: india
business-unit: banking
criticality: tier1
```

### 11.5 GitOps Best Practices

- Use pull requests for all platform changes.
- Require security approval for policy changes.
- Use signed commits or protected branches.
- Separate app repos from platform repos.
- Avoid storing raw secrets in Git.
- Use Sealed Secrets, External Secrets, Vault, or cloud secret managers.
- Use overlays for environment-specific differences.
- Keep cluster inventory declarative.
- Use progressive rollout for critical changes.
- Keep break-glass procedures outside GitOps automation but audited.

## 12. Governance and Policy Management

Governance is one of the strongest reasons to use hub-spoke architecture.

### 12.1 Governance Goals

Governance answers:

- Are clusters compliant?
- Which clusters violate security rules?
- Which clusters need remediation?
- Which clusters are missing required operators?
- Which clusters have drifted from desired state?
- Which teams changed something outside GitOps?

### 12.2 Policy Types

Common policy categories:

| Category | Examples |
|---|---|
| Security | Disable privileged pods, enforce SCC restrictions, restrict hostPath. |
| RBAC | Require least privilege, detect cluster-admin bindings. |
| Networking | Require default deny NetworkPolicy, restrict ingress. |
| Image security | Allow only approved registries, require image signature checks. |
| Compliance | PCI, HIPAA, CIS-like controls, internal standards. |
| Operator baseline | Ensure required operators are installed. |
| Logging | Ensure audit and app logs are forwarded. |
| Monitoring | Ensure user workload monitoring is enabled. |
| Certificates | Ensure custom CAs and ingress certs exist. |
| Quotas | Ensure namespace quotas and LimitRanges exist. |

### 12.3 Inform vs Enforce

Policies can be used in two major modes:

#### Inform Mode

The policy reports non-compliance but does not fix it.

Use for:

- Sensitive production systems
- Audit visibility
- Change advisory review
- Early rollout
- Detection-only controls

#### Enforce Mode

The policy attempts to remediate drift automatically.

Use for:

- Mandatory baseline configuration
- Low-risk objects
- Standard namespace controls
- Operator installation
- Known-safe compliance controls

### 12.4 Policy Placement

A policy is only useful when correctly targeted.

Example:

```text
Policy: require-default-deny-networkpolicy
Placement: all clusters where environment=prod
Binding: policy attached to placement
```

### 12.5 Governance Example

Goal: All production clusters must have a default deny ingress NetworkPolicy in application namespaces.

Flow:

1. Define policy in Git.
2. Define placement for `environment=prod`.
3. Bind policy to placement.
4. Hub evaluates target clusters.
5. Policy is distributed to spokes.
6. Spoke reports compliant or non-compliant.
7. Security team reviews compliance dashboard.

### 12.6 Policy Design Rules

For enterprise use:

- Start in `inform` mode.
- Test on non-production clusters.
- Use narrow placement first.
- Avoid broad `enforce` policies without testing.
- Document business owner and risk.
- Store policies in Git.
- Use labels for targeting.
- Keep policy names clear.
- Use namespaces to group policies.
- Review policy violation noise.

### 12.7 Common Governance Anti-Pattern

Bad:

```text
Apply every policy to every cluster immediately in enforce mode.
```

Better:

```text
Apply baseline policies gradually using rings and labels.
Start inform-only.
Move to enforce only after validation.
```

## 13. Identity, RBAC, and Multitenancy

### 13.1 Identity Architecture

Enterprise hub-spoke architecture must define identity for:

- Hub administrators
- Spoke administrators
- Application teams
- Security team
- Auditors
- Automation service accounts
- GitOps controllers
- CI/CD pipelines

### 13.2 Central Identity Provider

Common identity providers:

- LDAP
- Active Directory
- OpenID Connect
- SAML via enterprise SSO
- GitHub/GitLab for smaller environments

OpenShift OAuth is configured per cluster. Enterprises often standardize OAuth across clusters using GitOps or ACM policy.

### 13.3 Hub RBAC vs Spoke RBAC

There are two RBAC scopes:

#### Hub RBAC

Controls what users can do in ACM:

- View clusters
- Create clusters
- Import clusters
- Manage policies
- View compliance
- Access search
- Manage placements
- Manage cluster sets

#### Spoke RBAC

Controls what users can do inside a managed cluster:

- Manage namespaces
- Deploy apps
- View logs
- Manage routes
- Create secrets
- Bind SCC
- Administer nodes/operators

### 13.4 ManagedClusterSet RBAC

ManagedClusterSets are important for multitenancy.

Example design:

```text
ManagedClusterSet: banking-prod
  Clusters: bank-prod-in-01, bank-prod-in-02
  Admin team: banking-platform-admins

ManagedClusterSet: retail-dev
  Clusters: retail-dev-aws-01, retail-dev-aws-02
  Admin team: retail-dev-platform-admins
```

This allows delegated administration without giving every team access to every cluster.

### 13.5 Service Accounts for Automation

Automation identities should be:

- Dedicated
- Least privilege
- Rotated
- Audited
- Scoped to cluster sets or namespaces
- Not shared between teams
- Stored in secret managers

Examples:

```text
gitops-platform-sa
policy-deployer-sa
cluster-import-sa
observability-reader-sa
backup-operator-sa
```

### 13.6 Break-Glass Access

Every enterprise platform should define break-glass access.

Rules:

- Break-glass should be disabled or tightly controlled by default.
- Access should be time-limited.
- Usage must generate alerts.
- Credentials must be rotated after use.
- Root/admin access must be audited.
- Break-glass process must work even if SSO is down.

## 14. Networking Architecture

Networking is one of the hardest parts of hub-spoke architecture.

### 14.1 Required Connectivity

At minimum, a managed cluster must be able to reach the hub API endpoint for management communication.

Typical requirement:

```text
Spoke cluster nodes/pods ---> Hub API endpoint TCP 6443
```

Depending on features, additional endpoints may be required:

- Observability endpoint
- Image registry
- Object storage
- Git repositories
- Identity provider
- Proxy
- DNS
- NTP
- Red Hat registry
- Mirror registry
- Logging/SIEM endpoint

### 14.2 Network Zones

A common enterprise design:

```text
Management Zone:
  Hub cluster
  GitOps
  Monitoring aggregation
  SIEM integration
  Bastion/jump hosts

Production Zone:
  Production spoke clusters
  Production ingress
  Production storage

Development Zone:
  Dev and QA spokes

Edge Zone:
  Edge spokes with intermittent connectivity

DMZ:
  External-facing ingress or API gateways
```

### 14.3 DNS Design

DNS must be planned for:

- Hub API
- Hub console
- Spoke API endpoints
- Spoke ingress wildcard domains
- Internal services
- Mirror registries
- Git endpoints
- Observability endpoints

Example:

```text
api.hub.ocp.example.com
console-openshift-console.apps.hub.ocp.example.com
api.prod-in-01.ocp.example.com
*.apps.prod-in-01.ocp.example.com
registry.mirror.example.com
gitops.example.com
```

### 14.4 Proxy Design

Many enterprise clusters use HTTP/HTTPS proxies.

Important checks:

```bash
oc get proxy/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
oc get configmap trusted-ca -n openshift-config -o yaml
oc get cm -n openshift-config-managed | grep trusted
```

Proxy must allow:

- Hub API access from spokes
- Registry image pulls
- Git repository access
- Object storage access for observability
- Red Hat registry or mirror registry
- Identity provider access

### 14.5 Multicluster Service Networking

Hub-spoke management does not automatically mean applications can talk across clusters.

For application-to-application communication between clusters, use one of these patterns:

1. API gateway
2. External load balancer
3. Service mesh multicluster
4. Submariner
5. DNS-based service discovery
6. Message queue/event bus
7. Database replication layer
8. Cloud-native private link or transit gateway

### 14.6 Submariner

Submariner can provide direct networking and service discovery between managed clusters when required.

Use cases:

- Cross-cluster service discovery
- East-west service connectivity
- Active-active applications
- DR failover
- Shared backend service access

Be careful with:

- Overlapping pod/service CIDRs
- Firewall rules
- MTU
- NAT traversal
- Gateway node placement
- Latency
- Security boundaries

### 14.7 NetworkPolicy in Hub-Spoke

NetworkPolicy should be managed as part of baseline governance.

Recommended production baseline:

- Default deny ingress per application namespace
- Default deny egress where practical
- Allow DNS
- Allow required service-to-service traffic
- Allow monitoring scrape only from monitoring namespace
- Allow ingress controller to application pods
- Allow GitOps/controller namespaces where required

### 15.1 Observability Goals

Fleet observability should answer:

- Which clusters are healthy?
- Which clusters are unavailable?
- Which clusters have high CPU or memory pressure?
- Which clusters have failing operators?
- Which clusters are non-compliant?
- Which workloads are degraded?
- Which nodes are NotReady?
- Which clusters have certificate expiry risk?
- Which clusters have storage capacity issues?

### 15.2 Layers of Observability

```text
Layer 1: Local OpenShift monitoring on every cluster
Layer 2: ACM observability aggregation on hub
Layer 3: Enterprise monitoring/SIEM integration
Layer 4: Business service dashboards
```

### 15.3 Local Cluster Monitoring

- Platform operations
- Security compliance

- Application SLOs
- DR readiness

Retention should be based on business need.

Examples:

## 16. Security Architecture

### 16.1 Security Principles

Hub-spoke architecture should follow these principles:

- Least privilege
- Defense in depth
- Zero trust between clusters
- No shared admin credentials
- Strong identity federation
- Certificate trust management
- Explicit network allowlists
- GitOps auditability
- Policy-as-code
- Secrets externalization
- Break-glass control
- Continuous compliance

### 16.2 Hub as a High-Value Target

The hub can influence many clusters, so it must be protected as a critical security asset.

Protect the hub with:

- Strict admin RBAC
- MFA/SSO
- Dedicated infrastructure nodes
- Network segmentation
- Audit log forwarding
- Regular backup
- Vulnerability management
- Short-lived automation tokens
- Restricted console/API access
- SIEM integration
- Image scanning
- Policy review process

### 16.3 Spoke Security Baseline

Every spoke should have baseline security controls:

- OAuth configured with enterprise IdP
- Kubeadmin removed or disabled after setup, where appropriate
- SCC reviewed
- Privileged workloads restricted
- NetworkPolicy enforced
- Image registry allowlist
- Audit logs forwarded
- Secrets encryption reviewed
- etcd backup configured
- Certificate expiry monitored
- Node SSH access restricted
- Compliance policies applied

### 16.4 Certificate Trust

Hub-spoke architecture requires careful certificate trust.

Check:

```bash
oc get proxy/cluster -o yaml
oc get configmap -n openshift-config
oc get secret -n open-cluster-management
oc get secret -n open-cluster-management-agent
openssl s_client -connect api.hub.example.com:6443 -showcerts
```

Certificate issues commonly affect:

- Cluster import
- Klusterlet registration
- Proxy communication
- GitOps repository access
- Image pulls
- Observability endpoints
- LDAP/OIDC integrations

### 16.5 Secrets Management

Do not store sensitive kubeconfigs, cloud credentials, or registry passwords in plain Git.

Use:

- External Secrets Operator
- HashiCorp Vault
- CyberArk
- AWS Secrets Manager
- Azure Key Vault
- Google Secret Manager
- Sealed Secrets for limited use cases
- OpenShift secret encryption at rest

### 16.6 Audit Logging

Audit logging should cover:

- Hub API actions
- ACM policy changes
- Cluster import/detach
- RBAC changes
- GitOps sync actions
- Break-glass access
- Spoke API activity
- Policy remediation events

Forward audit logs to enterprise SIEM.

## 17. Disaster Recovery and Business Continuity

### 17.1 Hub Failure Impact

If the hub fails:

- Existing spoke workloads continue.
- New hub-driven changes stop.
- Fleet visibility is reduced.
- Policy status becomes stale.
- Centralized GitOps may stop, depending on design.
- Cluster lifecycle operations stop.

Therefore, hub backup and restore are critical.

### 17.2 Hub Backup Scope

Back up:

- ACM/MCE custom resources
- Policies
- Placements
- ManagedCluster resources
- Cluster credentials/secrets
- GitOps configuration
- Observability configuration
- Search configuration
- Operator subscriptions
- RBAC
- Namespace metadata
- Integration secrets

Do not rely only on etcd snapshot if your restore process is not tested.

### 17.3 Spoke Cluster Backup

Each spoke needs its own backup strategy.

Back up:

- Application namespaces
- Persistent volumes
- Cluster-scoped resources
- CRDs and custom resources
- Operator state
- Secrets
- Routes/Ingress
- ConfigMaps
- NetworkPolicies
- RBAC

Use application-consistent backup for databases.

### 17.4 DR Patterns

| Pattern | Description |
|---|---|
| Hub restore | Restore hub from backup after failure. |
| Standby hub | Maintain another hub ready for takeover. |
| Multi-hub | Split fleet across multiple hubs. |
| Global hub | Higher-level hub manages multiple hubs. |
| Spoke reimport | Reattach spokes to rebuilt hub. |
| GitOps rebuild | Use Git to reconstruct hub state. |

### 17.5 DR Testing

Test regularly:

- Restore hub backup
- Reconnect managed clusters
- Validate policies
- Validate GitOps sync
- Validate observability
- Validate RBAC
- Validate cluster lifecycle functions
- Validate certificate trust
- Validate emergency access

## 18. Scaling Design Considerations

### 18.1 Scaling Dimensions

Scaling is not only number of clusters.

Consider:

- Number of clusters
- Number of namespaces per cluster
- Number of resources indexed by search
- Number of policies
- Number of placement decisions
- Number of applications
- Number of GitOps sync operations
- Metrics volume
- Alert volume
- Number of users
- Number of automation events

### 18.2 Label Strategy at Scale

Labels become critical at scale.

Recommended cluster labels:

```yaml
environment: dev|qa|stage|prod
region: india|us-east|eu-west
provider: aws|azure|gcp|onprem|edge
business-unit: banking|retail|telco|shared
criticality: tier1|tier2|tier3
compliance: pci|hipaa|internal|none
upgrade-ring: ring0|ring1|ring2|ring3
owner: platform-team-a
network-zone: dmz|internal|restricted
```

### 18.3 Placement at Scale

Avoid manually listing clusters in every policy or app.

Bad:

```yaml
clusters:
  - cluster1
  - cluster2
  - cluster3
```

Better:

```yaml
clusterSelector:
  matchLabels:
    environment: prod
    region: india
```

### 18.4 Policy Scale

Too many policies can create noise.

Organize policies:

```text
baseline-security
baseline-networking
baseline-monitoring
baseline-operators
prod-only-security
pci-compliance
edge-baseline
```

### 18.5 Observability Scale

Metrics are expensive.

Control:

- Retention
- Metric allowlists
- Custom metrics
- Scrape intervals
- Dashboard cardinality
- Label cardinality
- Remote write destinations

### 18.6 GitOps Scale

For many clusters:

- Use ApplicationSets
- Use cluster generators
- Shard Argo CD if needed
- Avoid one giant app managing everything
- Use sync waves
- Use health checks
- Limit automated prune for dangerous resources
- Separate platform and application sync

### 19.1 Hub Cluster HA

The hub itself should be a highly available OpenShift cluster.

Requirements:

- 3 control plane nodes
- Reliable etcd
- Highly available API load balancer
- Highly available ingress
- Redundant storage
- Node anti-affinity for critical pods
- Proper PDBs
- Monitoring and alerting
- Backups

### 19.2 Hub Component Placement

Use node placement and tolerations where supported.

Example design:

```text
infra nodes:
  router
  registry
  monitoring
  logging
  ACM components where supported

worker nodes:
  general workloads

dedicated management nodes:
  GitOps
  observability
  search
```

### 19.3 Spoke HA

Production spokes should have:

- 3 control plane nodes
- At least 3 worker nodes where possible
- Multi-zone worker spread
- Storage replication
- Highly available ingress

## 20. Global Hub and Multi-Hub Architecture

### 20.1 Why Multiple Hubs

One hub may not be enough for very large enterprises.

Reasons for multiple hubs:

- Scale limits
- Regional autonomy
- Data residency
- Separate security zones
- Mergers/acquisitions
- Independent business units
- Production vs non-production separation
- Edge fleet separation
- Different platform teams

### 20.2 Multi-Hub Pattern

```text
                         +----------------------+
                         |      Global Hub      |
                         | Fleet summary /     |
                         | policy status /     |
                         | multi-hub view      |
                         +----------+-----------+
                                    |
              ------------------------------------------------
              |                       |                      |
+-------------+-------------+ +-------+-------------+ +------+--------------+
| Regional Hub India        | | Regional Hub US     | | Edge Hub           |
| Manages India spokes      | | Manages US spokes   | | Manages edge sites |
+-------------+-------------+ +-------+-------------+ +------+--------------+
              |                       |                      |
       Spoke clusters          Spoke clusters          Edge clusters
```

### 20.3 Hub Placement Strategy

Possible strategies:

| Strategy | Description |
|---|---|
| Regional hubs | One hub per geography. |
| Environment hubs | Separate dev/test/prod hubs. |
| Business unit hubs | Each BU has its own hub. |
| Security-zone hubs | Separate hubs for restricted and general clusters. |
| Edge hubs | Dedicated hubs for edge locations. |

### 20.4 Multi-Hub Challenges

- Policy duplication
- GitOps repository design
- RBAC consistency
- Reporting consistency
- Backup complexity
- Version compatibility
- Operational ownership
- Cluster migration between hubs
- Global search and compliance view

### 20.5 When to Use Global Hub

Use Global Hub when:

- You manage multiple ACM hubs.
- Leadership needs fleet-wide status.
- Compliance needs aggregate reporting.
- Regions operate independently but require central visibility.
- Scale exceeds one hub's comfortable operating boundary.

## 21. Enterprise Design Patterns

### 21.1 Pattern: Central Governance, Local Workloads

Use hub for policy and visibility. Run workloads only on spokes.

Best for:

- Large enterprises
- Strict separation
- Regulated environments

### 21.2 Pattern: Platform Hub + Shared Services Cluster

Use one hub for management and separate shared services cluster for tools.

```text
Hub: ACM/MCE/Governance
Shared services spoke: Jenkins, Nexus, SonarQube, GitLab runners
Production spokes: business apps
```

Best for:

- Cleaner hub
- Better resource isolation
- Safer management plane

### 21.3 Pattern: Ring-Based Rollouts

Use cluster labels and placements to roll out changes gradually.

```text
upgrade-ring=ring0 -> lab
upgrade-ring=ring1 -> dev
upgrade-ring=ring2 -> qa
upgrade-ring=ring3 -> prod non-critical
upgrade-ring=ring4 -> prod critical
```

Best for:

- Upgrades
- Policy rollout
- Operator updates
- Security changes

### 21.4 Pattern: Hub-Driven Baseline Bootstrap

When a new cluster joins, hub automatically applies:

- OAuth configuration
- RBAC baseline
- Monitoring config
- Logging config
- NetworkPolicy defaults
- Quotas
- Required operators
- Trusted CA bundle
- Image registry policy

### 21.5 Pattern: Cluster-as-a-Service

Application teams request clusters through a workflow.

Flow:

```text
Request -> Approval -> Cluster creation -> Import -> Baseline policies -> Handover
```

Integrate with:

- ServiceNow/Jira
- Ansible Automation Platform
- GitOps repo
- CMDB
- Cost management

### 21.6 Pattern: Edge Hub-Spoke

Edge clusters may have intermittent connectivity.

Design for:

- Local autonomy
- Delayed sync
- Lightweight policies
- Local image registry/cache
- Minimal observability payload
- Remote upgrade windows
- Hardware replacement process

## 22. Anti-Patterns and Common Mistakes

### 22.1 Running Everything on the Hub

Bad:

```text
Hub runs ACM + CI/CD + databases + customer apps + test workloads.
```

Impact:

- Resource contention
- Hub instability
- Fleet management outage
- Security risk

### 22.2 No Label Strategy

Without labels, placement becomes manual and error-prone.

Bad:

```text
Policy targets manually selected clusters.
```

Better:

```text
Policy targets clusters by labels and ManagedClusterSets.
```

### 22.3 Direct Manual Changes Everywhere

If admins manually change every cluster, drift becomes impossible to control.

Better:

- GitOps
- Policies
- Templates
- Automation
- Audit

### 22.4 Enforce Policies Too Early

Moving directly to enforce mode can break workloads.

Better:

1. Inform mode
2. Non-prod test
3. Pilot production cluster
4. Ring rollout
5. Enforce after approval

### 22.5 Ignoring Network and Proxy Requirements

Cluster import and add-ons often fail because of:

- Proxy blocking hub API
- Missing CA bundle
- DNS failure
- Registry access failure
- Firewall missing TCP 6443
- TLS inspection issues

### 22.6 No Hub Backup

A hub without backup is a major operational risk.

### 22.7 Treating Hub-Spoke as Only a Tool Installation

Installing ACM is easy. Designing operating model, RBAC, policy strategy, GitOps flow, and DR process is the real enterprise architecture work.

## 24. Troubleshooting Hub-Spoke Issues

### 24.1 Managed Cluster Not Available

Commands:

```bash
oc get managedclusters
oc describe managedcluster <cluster-name>
oc get managedclusteraddon -n <cluster-name>
oc get events -n <cluster-name> --sort-by=.lastTimestamp
```

On spoke:

```bash
oc get pods -n open-cluster-management-agent
oc get pods -n open-cluster-management-agent-addon
oc logs -n open-cluster-management-agent deploy/klusterlet-registration-agent
oc logs -n open-cluster-management-agent deploy/klusterlet-work-agent
```

Check:

- Spoke can reach hub API.
- Klusterlet pods are running.
- Certificates are valid.
- Time sync is correct.
- Proxy is configured.
- DNS resolves hub API.
- ManagedCluster was accepted.

### 24.2 Cluster Import Fails

Common causes:

- Wrong kubeconfig context
- Hub API not reachable from spoke
- TLS/CA issue
- Proxy issue
- Pull secret issue
- Image registry blocked
- Klusterlet pod cannot start
- Existing stale import resources
- Cluster name conflict

Useful tests from spoke:

```bash
curl -k https://api.hub.example.com:6443/version
oc image info <required-image>
nslookup api.hub.example.com
date
chronyc tracking
```

### 24.3 Policies Not Applying

Commands:

```bash
oc get policy -A
oc describe policy <policy-name> -n <namespace>
oc get placement -A
oc get placementdecision -A
oc get policyplacementbinding -A
```

Check:

- Policy namespace is correct.
- Placement selects clusters.
- PlacementDecision exists.
- PolicyPlacementBinding exists.
- ManagedClusterSetBinding exists.
- User has RBAC to cluster set.
- Policy is not disabled.
- Remediation action is correct.

### 24.4 PlacementDecision Missing

Check:

```bash
oc get placement -A
oc describe placement <placement-name> -n <namespace>
oc get managedclusters --show-labels
oc get managedclustersets
oc get managedclustersetbinding -A
```

Common causes:

- No cluster matches labels.
- ManagedClusterSetBinding missing.
- Cluster not in expected ManagedClusterSet.
- Cluster is unavailable.
- Taints/tolerations mismatch.
- Namespace does not have permission to use cluster set.

### 24.5 Add-On Degraded

Commands:

```bash
oc get managedclusteraddon -A
oc describe managedclusteraddon <addon-name> -n <cluster-name>
oc get pods -n open-cluster-management-agent-addon
```

Check:

- Add-on agent pods running on spoke
- Required permissions
- Network connectivity
- Image pull errors
- Version compatibility
- Proxy and CA

### 24.6 Observability Not Showing Metrics

Check:

```bash
oc get pods -n open-cluster-management-observability
oc get multiclusterobservability -A
oc get managedclusteraddon observability-controller -A
oc describe managedclusteraddon observability-controller -n <cluster-name>
```

Common causes:

- Object storage misconfiguration
- PVC/storage issue
- Observability add-on degraded
- Metrics blocked by network/proxy
- Certificate trust issue
- Too much cardinality
- Retention/storage full

### 24.7 GitOps Sync Fails

Check:

```bash
oc get applications -n openshift-gitops
oc describe application <app> -n openshift-gitops
oc logs -n openshift-gitops deploy/openshift-gitops-application-controller
```

Common causes:

- Git credentials expired
- Repository unreachable
- TLS/CA issue
- RBAC missing on target cluster
- Namespace missing
- Resource conflict
- Admission policy rejects manifest
- CRD not installed before CR

### 24.8 Search Not Returning Data

Check:

```bash
oc get pods -n open-cluster-management
oc get managedclusteraddon search-collector -A
```

Common causes:

- Search collector add-on degraded
- Hub search components unhealthy
- RBAC filtering results
- Cluster unavailable
- Indexed data stale

## 26. Interview and Real-World Scenario Questions

### Q1. What is hub-spoke architecture in OpenShift?

It is a multicluster design where a central hub cluster manages multiple spoke clusters. The hub provides cluster lifecycle, governance, observability, search, policy, and GitOps orchestration. Spoke clusters run workloads and local OpenShift control planes.

### Q2. What is the role of klusterlet?

Klusterlet is the managed cluster agent. It connects the spoke cluster to the hub, handles registration, receives work, applies it locally, and reports status back to the hub.

### Q3. Does the hub directly run workloads on spokes?

No. The hub creates desired-state resources and work objects. The spoke-side agent pulls and applies the work locally.

### Q4. What happens if the hub goes down?

Existing workloads on spoke clusters continue running. However, central visibility, new policy delivery, new application rollout, and lifecycle operations are interrupted until hub service is restored.

### Q5. Why use ManagedClusterSets?

ManagedClusterSets group clusters for RBAC and placement. They allow teams to manage only the clusters they own and allow policies/apps to target logical groups of clusters.

### Q6. How do you target only production clusters?

Use labels and Placement resources.

Example:

```yaml
matchLabels:
  environment: prod
```

### Q7. Why is policy inform mode important?

Inform mode detects non-compliance without changing the cluster. It is safer for initial rollout and production validation.

### Q8. How do you avoid hub becoming a single point of failure?

Use a highly available OpenShift hub, backup and restore, tested DR, GitOps source of truth, possible standby/multiple hubs, and avoid running heavy workloads on the hub.

### Q9. What is the difference between cluster lifecycle and application lifecycle?

Cluster lifecycle manages clusters themselves: create, import, upgrade, hibernate, detach, destroy. Application lifecycle manages applications and Kubernetes resources deployed across clusters.

### Q10. What are common hub-spoke troubleshooting areas?

- Cluster import
- Klusterlet registration
- Network/proxy/CA
- Add-on health
- Policy placement
- GitOps sync
- Observability storage
- RBAC and cluster set permissions

### 27.2 Key Troubleshooting Logic

If policy is not applied:

```text
Policy -> PlacementBinding -> Placement -> PlacementDecision -> ManagedCluster -> Klusterlet -> Applied resource
```

If any link is broken, policy/application delivery fails.

### 27.3 Key Design Logic

Always ask:

- Who owns the hub?
- Who owns each spoke?
- How are clusters grouped?
- How are clusters labeled?
- How are policies promoted?
- What is inform vs enforce?
- How is GitOps structured?
- What happens if hub is down?
- How is hub backed up?
- How are credentials rotated?
- How is compliance reported?

### 27.4 Practical Senior Admin Advice

A 10-year experienced engineer should not only say:

```text
Install ACM and import clusters.
```

A senior answer should include:

```text
Design cluster sets, labels, RBAC, governance, GitOps promotion, observability, backup, DR, upgrade rings, network flow, proxy trust, and operational runbooks.
```

## Closing Note

Hub-spoke architecture is the foundation of enterprise-scale OpenShift fleet management. For a junior administrator, it may look like a simple central console managing many clusters. For an advanced administrator, it is a complete operating model involving fleet inventory, cluster lifecycle, governance, GitOps, security, observability, networking, backup, DR, and organizational responsibility.

A strong OpenShift enterprise architecture does not treat clusters as isolated systems. It treats them as a governed fleet.
