# Production Namespace Design in Enterprise Architecture for Advanced OpenShift Administration

**Audience:** Senior Linux/OpenShift/Kubernetes administrators, platform engineers, SREs, and enterprise architects with production responsibility.  
**Focus:** Designing production namespaces/projects in Red Hat OpenShift Container Platform for security, isolation, scalability, operations, compliance, and GitOps-driven administration.  
**Context:** Advanced OpenShift Administration / enterprise architecture level.

---

## 1. Executive Summary

In OpenShift, a production namespace is not just a place where pods run. It is an enterprise control boundary. It defines who can deploy, what can run, how much resource can be consumed, which traffic is allowed, which storage can be used, how observability is applied, how audit ownership is proven, and how incident response is performed.

In Kubernetes terminology the object is a **Namespace**. In OpenShift, users normally interact with a **Project**, which is an OpenShift abstraction around a namespace with additional project request and access management behavior.

A weak production namespace design creates long-term operational pain:

- Developers get too much access.
- Production workloads share namespaces with test workloads.
- Network traffic is open by default.
- Quotas are missing, causing noisy-neighbor incidents.
- Privileged service accounts are reused.
- Secrets and image pull credentials become uncontrolled.
- Monitoring, backup, and cost ownership are inconsistent.
- GitOps cannot safely separate platform-owned resources from application-owned resources.

A strong production namespace design treats every namespace as a **standardized production landing zone**.

The design should provide:

- Clear ownership.
- Predictable naming.
- Least-privilege RBAC.
- Default-deny network posture.
- ResourceQuota and LimitRange enforcement.
- SCC and Pod Security alignment.
- Dedicated service accounts.
- GitOps lifecycle management.
- Backup and disaster-recovery tagging.
- Observability and audit readiness.
- Separation of application, platform, operator, and CI/CD concerns.

## 2. OpenShift Project vs Kubernetes Namespace

### 2.1 Namespace

A Kubernetes namespace provides a logical scope for namespaced resources such as Pods, Services, Deployments, ConfigMaps, Secrets, RoleBindings, ResourceQuotas, LimitRanges, NetworkPolicies, and PVCs.

Namespaces do **not** automatically provide full security isolation. They are a logical boundary that must be strengthened with RBAC, NetworkPolicy, admission controls, SCCs, quotas, node placement controls, and operational governance.

### 2.2 OpenShift Project

OpenShift exposes namespaces to users as **Projects**. A project typically contains:

- A Kubernetes namespace.
- OpenShift project metadata.
- Access control bindings.
- Optional project request template defaults.
- User-facing project lifecycle behavior.

In enterprise design discussions, the terms namespace and project are often used together:

- **Namespace**: Kubernetes API object and technical boundary.
- **Project**: OpenShift user-facing unit of work and governance boundary.

For production architecture, design the namespace/project as a controlled tenant boundary.

## 3. Why Production Namespace Design Matters

A production namespace design must solve multiple enterprise problems at the same time.

### 3.1 Security Boundary

A namespace should define a clear security boundary for:

- RBAC scope.
- Service account permissions.
- Secrets access.
- Network reachability.
- Pod admission rules.
- SCC access.
- Image pull credentials.
- Deployment authority.

Without these controls, namespace separation becomes cosmetic.

### 3.2 Operational Boundary

A namespace should allow operations teams to answer quickly:

- Who owns this workload?
- What is the support group?
- What is the business criticality?
- Which alerts belong to this application?
- Which backup policy applies?
- Which Git repository is the source of truth?
- Which deployment pipeline last changed it?
- Which cost center pays for it?

### 3.3 Reliability Boundary

Production namespaces should protect the platform and other applications from resource abuse:

- CPU overconsumption.
- Memory pressure.
- Too many pods.
- Too many services.
- PVC sprawl.
- Secret/configmap explosion.
- Uncontrolled logs and metrics.

### 3.4 Compliance Boundary

For regulated workloads, the namespace should carry metadata and controls for:

- Data classification.
- PCI/PII/PHI tagging.
- Audit scope.
- Retention class.
- Backup class.
- Disaster recovery tier.
- Change-management workflow.
- Security exception tracking.

## 4. Core Design Principles

### 4.1 Never Run Business Workloads in Default/System Namespaces

Do not run application workloads in namespaces such as:

- `default`
- `kube-system`
- `kube-public`
- `openshift`
- `openshift-*`
- `openshift-infra`
- `openshift-node`

These namespaces are reserved for cluster and platform components. Some system namespaces are highly privileged and may bypass normal admission behavior. Production applications must run in dedicated application namespaces.

### 4.2 One Namespace Should Have One Clear Purpose

A namespace should not mix unrelated workloads. Avoid namespaces such as:

```text
production
apps
shared
team1
misc
backend
```

These names do not clearly describe ownership, application, environment, or operational responsibility.

Better examples:

```text
prod-payments-api
prod-payments-db
prod-customer-portal
prod-inventory-api
prod-observability-addons
```

### 4.3 Separate Production from Non-Production

Production and non-production workloads should not share the same namespace.

Bad:

```text
payments
  - payments-api-dev
  - payments-api-test
  - payments-api-prod
```

Better:

```text
dev-payments-api
test-payments-api
stage-payments-api
prod-payments-api
```

Production namespaces should have stricter:

- RBAC.
- Network policies.
- Quotas.
- Change controls.
- Backup policy.
- Image policy.
- Deployment approval process.
- Observability thresholds.

### 4.4 Use Namespace-as-a-Service

Do not allow production namespaces to be created manually without standards.

A production namespace should be provisioned from a controlled template or GitOps workflow that automatically applies:

- Namespace object.
- Labels and annotations.
- ResourceQuota.
- LimitRange.
- NetworkPolicy baseline.
- RoleBindings.
- Service accounts.
- Image pull policy references.
- Observability objects.
- Backup labels.
- Optional node selectors.
- Optional operator subscriptions.

### 4.5 Platform-Owned vs Application-Owned Resources

A production namespace contains two classes of resources.

**Platform-owned baseline resources:**

- Namespace labels and annotations.
- ResourceQuota.
- LimitRange.
- Default NetworkPolicies.
- RBAC RoleBindings.
- Service account baseline.
- SCC bindings.
- Backup labels.
- Security labels.
- Monitoring baseline.

**Application-owned resources:**

- Deployments.
- Services.
- Routes.
- ConfigMaps.
- Application Secrets.
- HPAs.
- PDBs.
- ServiceMonitors.
- PrometheusRules.
- Application-specific NetworkPolicies.

Use GitOps repository structure and RBAC to prevent application teams from accidentally modifying platform-owned guardrails.

## 5. Namespace Design Models

There is no single model for every enterprise. Choose based on security, ownership, deployment lifecycle, and operational complexity.

---

### 5.1 Model A: One Namespace per Application per Environment

Example:

```text
dev-payments
test-payments
stage-payments
prod-payments
```

**Best for:**

- Small to medium applications.
- One application team.
- Shared release lifecycle.
- Moderate security separation.

**Advantages:**

- Simple ownership.
- Easy quota management.
- Easy cost tracking.
- Simple GitOps mapping.
- Fewer namespaces.

**Disadvantages:**

- Frontend, backend, workers, and DB clients share the same namespace.
- Network isolation inside the namespace requires pod-level NetworkPolicy.
- A team admin may control all components in the namespace.

**Use when:**

- Components are tightly coupled.
- Same team manages all services.
- Same deployment window applies.
- Data sensitivity is uniform.

---

### 5.2 Model B: One Namespace per Application Component per Environment

Example:

```text
prod-payments-web
prod-payments-api
prod-payments-worker
prod-payments-db-client
```

**Best for:**

- Sensitive applications.
- Strong network segmentation.
- Separate operational teams.
- Different scaling and quota profiles.
- Different release cadences.

**Advantages:**

- Stronger blast-radius control.
- Easier NetworkPolicy design between tiers.
- Separate quotas for web/API/worker.
- Easier RBAC separation.
- Better fit for high-security environments.

**Disadvantages:**

- More namespaces.
- More RoleBindings, quotas, policies, and GitOps objects.
- More complex troubleshooting.
- More operational overhead.

**Use when:**

- API, worker, and database-access components have different risk levels.
- Security requires explicit tier isolation.
- Teams are split by component.
- Compliance demands separation.

---

### 5.3 Model C: One Namespace per Team per Environment

Example:

```text
prod-team-payments
prod-team-orders
prod-team-claims
```

**Best for:**

- Platform teams offering broad developer self-service.
- Teams with many small services.
- Internal development platforms.

**Advantages:**

- Reduced namespace count.
- Easy team ownership.
- Simple developer onboarding.

**Disadvantages:**

- Weak application-level isolation.
- More difficult cost attribution per app.
- Team admin may affect many apps.
- Larger blast radius.

**Use carefully in production.** This model is acceptable only when combined with strong labeling, ResourceQuota, NetworkPolicy, and workload ownership controls.

---

### 5.4 Model D: Dedicated Namespace per Tenant

Example:

```text
prod-tenant-bank-a
prod-tenant-bank-b
prod-tenant-bank-c
```

**Best for:**

- SaaS platforms.
- Multi-tenant enterprise platforms.
- Customer-specific isolation.

**Advantages:**

- Clear tenant boundary.
- Easier tenant-level backup/restore.
- Easier tenant-level reporting.
- Better contract and compliance mapping.

**Disadvantages:**

- High namespace count.
- Requires automation.
- Requires strong quota and monitoring model.

**Use when:**

- Tenants require isolation.
- Regulatory or contractual separation exists.
- Per-tenant lifecycle is important.

---

### 5.5 Recommended Enterprise Default

For most enterprises, start with:

```text
<environment>-<business-domain>-<application>
```

Example:

```text
prod-payments-card-api
prod-payments-upi-api
prod-retail-order-api
prod-hr-payroll
```

For highly sensitive systems, split by tier:

```text
prod-payments-card-web
prod-payments-card-api
prod-payments-card-worker
```

## 6. Naming Convention

A namespace name should communicate environment, business ownership, workload identity, and sometimes component.

### 6.1 Recommended Format

```text
<env>-<business-unit>-<app>[-<component>]
```

Examples:

```text
prod-payments-upi-api
prod-payments-card-worker
prod-retail-order-web
stage-hr-payroll-api
dev-infra-catalog-api
```

### 6.2 Naming Rules

Use:

- Lowercase letters.
- Hyphens.
- Short but meaningful names.
- Stable application identifiers.
- Environment prefix.

Avoid:

- Uppercase names.
- Personal names.
- Temporary names.
- Generic names such as `prod-app`, `backend`, `test1`.
- Names that expose confidential business data.

### 6.3 Environment Codes

Recommended:

```text
dev
sit
uat
stage
perf
dr
prod
```

Be consistent. Do not mix `prd`, `production`, and `prod` across teams.

### 7.3 Why This Matters

These labels and annotations can drive:

- Cost reports.
- Alert routing.
- Compliance scans.
- Security exception workflows.
- Incident ownership.

## 8. RBAC Design for Production Namespaces

RBAC is one of the most important parts of production namespace design.

### 8.1 RBAC Goals

Production RBAC should ensure:

- Developers can view and troubleshoot without uncontrolled production changes.
- CI/CD or GitOps service accounts perform deployments.
- Break-glass access is separate and audited.
- No human user regularly uses cluster-admin for application support.
- Service accounts have only the permissions they need.
- Secrets access is tightly controlled.

### 8.2 Recommended Human Access Model

Use identity-provider groups, not individual user bindings.

Example groups:

```text
ocp-prod-payments-card-api-admins
ocp-prod-payments-card-api-deployers
ocp-prod-payments-card-api-viewers
ocp-prod-payments-card-api-breakglass
```

Recommended bindings:

| Group | Role | Purpose |
|---|---|---|
| `*-viewers` | `view` | Read-only troubleshooting |
| `*-deployers` | Custom deploy role or `edit` with restrictions | Deployment automation or release engineers |
| `*-admins` | Namespace admin, limited membership | Production app owners or platform delegates |
| `*-breakglass` | Temporary elevated role | Emergency access only |

### 8.3 Avoid These RBAC Mistakes

Avoid:

```bash
oc adm policy add-cluster-role-to-user cluster-admin developer1
oc adm policy add-role-to-group admin system:authenticated -n prod-payments
oc adm policy add-role-to-user edit bob -n prod-payments
```

Problems:

- Cluster-admin bypasses namespace boundaries.
- `system:authenticated` grants access to all authenticated users.
- Individual user bindings are hard to audit and offboard.
- Long-lived admin access violates least privilege.

### 8.4 Recommended RoleBinding Example

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: rb-viewers
  namespace: prod-payments-card-api
subjects:
- kind: Group
  apiGroup: rbac.authorization.k8s.io
  name: ocp-prod-payments-card-api-viewers
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: view
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: rb-admins
  namespace: prod-payments-card-api
subjects:
- kind: Group
  apiGroup: rbac.authorization.k8s.io
  name: ocp-prod-payments-card-api-admins
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: admin
```

### 8.5 Production Deployment Access

Prefer GitOps or CI/CD service accounts for deployment instead of human users.

Example:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: deployer-sa
  namespace: prod-payments-card-api
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: rb-deployer-sa-edit
  namespace: prod-payments-card-api
subjects:
- kind: ServiceAccount
  name: deployer-sa
  namespace: prod-payments-card-api
roleRef:
  kind: ClusterRole
  apiGroup: rbac.authorization.k8s.io
  name: edit
```

For stricter environments, create a custom Role instead of using `edit`.

### 8.6 Custom Deploy Role Example

This role permits deployment-related changes without broad access to every namespaced object.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-deployer
  namespace: prod-payments-card-api
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["services", "configmaps"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: ["route.openshift.io"]
  resources: ["routes"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: ["autoscaling"]
  resources: ["horizontalpodautoscalers"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
```

Avoid granting production deployers permission to modify:

- RoleBindings.
- ResourceQuotas.
- LimitRanges.
- NetworkPolicy baselines.
- SCC bindings.
- Namespace labels.
- Backup policies.

## 9. Production Service Account Design

Never use the default service account for production application workloads unless there is a specific reason.

### 9.1 Recommended Pattern

Create one service account per workload identity:

```text
sa-payments-api
sa-payments-worker
sa-payments-migration
sa-payments-readonly-job
```

### 9.2 Why Dedicated Service Accounts Matter

Dedicated service accounts allow:

- Workload-specific RBAC.
- Workload-specific SCC binding.
- Clear audit trails.
- Safer secret attachment.
- Better image pull secret control.
- Separate token rotation and incident response.

### 9.3 Example

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: sa-payments-api
  namespace: prod-payments-card-api
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: prod-payments-card-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      serviceAccountName: sa-payments-api
      containers:
      - name: api
        image: registry.example.com/payments/api:1.2.3
        ports:
        - containerPort: 8443
```

### 9.4 Token Security

Production service account token practices:

- Avoid mounting tokens when not needed.
- Use `automountServiceAccountToken: false` where possible.
- Use short-lived bound tokens for external integrations.
- Avoid using service account tokens outside the cluster.
- Rotate credentials after incidents.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: static-web
spec:
  template:
    spec:
      automountServiceAccountToken: false
```

## 10. SCC and Pod Security Design

OpenShift uses **Security Context Constraints** to control what pods are allowed to do. Pod Security Admission also applies Kubernetes Pod Security Standards behavior.

### 10.1 Production Baseline

Production workloads should run under the most restrictive practical security posture:

- Non-root containers.
- No privileged containers.
- No hostNetwork unless explicitly approved.
- No hostPID or hostIPC.
- No hostPath unless explicitly approved.
- Drop Linux capabilities by default.
- Avoid privilege escalation.
- Read-only root filesystem where possible.
- Explicit seccomp profile where supported.
- Dedicated service account.

### 10.2 Avoid Modifying Default SCCs

Do not edit default SCCs. If a workload truly requires special privileges, create a custom SCC or use a controlled binding to an existing SCC only for the required service account.

Bad:

```bash
oc edit scc restricted-v2
```

Better:

```bash
oc adm policy add-scc-to-user anyuid -z sa-legacy-app -n prod-legacy-app
```

Even better:

- Fix the container image to run as a random non-root UID.
- Use `restricted-v2` compatible images.
- Avoid `anyuid` unless required.
- Document any SCC exception.

### 10.3 SCC Exception Register

Every production namespace should maintain an exception register for privileged requirements.

| Workload | Service Account | SCC | Reason | Risk | Expiry | Owner |
|---|---|---|---|---|---|---|
| legacy-api | sa-legacy-api | anyuid | Vendor image requires UID 0 | Medium | 2026-12-31 | app-owner |

### 10.4 Namespace Run-Level Warning

Never set the following label on application namespaces:

```yaml
openshift.io/run-level: "0"
```

This label is reserved for internal OpenShift components and can cause normal SCC admission to be skipped.

## 11. Pod Security Admission Labels

Pod Security Admission can use namespace labels such as:

```yaml
pod-security.kubernetes.io/enforce: restricted
pod-security.kubernetes.io/audit: restricted
pod-security.kubernetes.io/warn: restricted
```

However, in OpenShift, pod security labels can be synchronized based on SCC permissions in the namespace. For production, define a platform policy for how PSA labels are managed and avoid random manual changes.

### 11.1 Recommended Approach

For standard production namespaces:

- Keep workloads compatible with restricted security.
- Do not grant broad SCC permissions to all service accounts.
- Document exceptions.
- Avoid manually fighting the label synchronization controller unless you understand the impact.

## 12. ResourceQuota Design

ResourceQuota protects the cluster from namespace-level overconsumption.

### 12.1 What Quota Should Control

Production quotas should normally control:

- CPU requests.
- CPU limits.
- Memory requests.
- Memory limits.
- Ephemeral storage.
- PVC count.
- Storage requests.
- Pod count.
- Service count.
- Secret count.
- ConfigMap count.
- Route count.
- LoadBalancer service count, if allowed.
- Object count for high-risk resources.

### 12.2 Example Production ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-prod-standard
  namespace: prod-payments-card-api
spec:
  hard:
    requests.cpu: "8"
    limits.cpu: "16"
    requests.memory: 16Gi
    limits.memory: 32Gi
    requests.ephemeral-storage: 20Gi
    limits.ephemeral-storage: 40Gi
    pods: "40"
    services: "20"
    services.loadbalancers: "0"
    services.nodeports: "0"
    secrets: "50"
    configmaps: "50"
    persistentvolumeclaims: "10"
    requests.storage: 500Gi
    count/deployments.apps: "20"
    count/statefulsets.apps: "5"
    count/jobs.batch: "20"
    count/cronjobs.batch: "10"
```

### 12.3 Quota Sizing Method

For each production namespace:

1. Calculate steady-state workload requirement.
2. Add replica overhead for rolling updates.
3. Add autoscaling headroom.
4. Add operational job headroom.
5. Add incident/debug headroom.
6. Add storage growth forecast.
7. Apply quota slightly above expected peak, not unlimited.

Example:

```text
API deployment:
  replicas: 6
  CPU request: 500m each
  Memory request: 1Gi each

Steady CPU request = 6 * 500m = 3 CPU
Rolling update surge = +2 pods = +1 CPU
HPA max = 12 pods = 6 CPU
Operational jobs = 1 CPU
Recommended requests.cpu quota = 8 CPU
```

### 12.4 Quota Classes

Create standard quota classes instead of custom one-off quotas for every team.

| Class | CPU Request | Memory Request | Pods | Storage | Use Case |
|---|---:|---:|---:|---:|---|
| `prod-small` | 4 | 8Gi | 20 | 100Gi | Small APIs |
| `prod-medium` | 8 | 16Gi | 40 | 500Gi | Standard services |
| `prod-large` | 16 | 64Gi | 80 | 1Ti | Critical platforms |
| `prod-xl` | Custom | Custom | Custom | Custom | Architecture approval required |

### 12.5 ClusterResourceQuota

Use ClusterResourceQuota when quota must apply across multiple namespaces selected by labels.

Example use case:

- All production namespaces for `payments` must not exceed 100 CPUs and 500Gi memory requests.

```yaml
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata:
  name: crq-payments-prod
spec:
  selector:
    labels:
      matchLabels:
        platform.company.com/business-unit: payments
        platform.company.com/environment: prod
  quota:
    hard:
      requests.cpu: "100"
      requests.memory: 500Gi
      limits.cpu: "200"
      limits.memory: 1Ti
      requests.storage: 10Ti
```

### 12.6 Requests vs Limits

Production design guidance:

- Every container should have CPU and memory requests.
- Every container should have memory limits.
- CPU limits should be used carefully because they can cause throttling.
- Critical latency-sensitive workloads may use CPU requests without strict CPU limits, depending on enterprise policy.
- Memory limits are important to prevent node memory pressure.
- Quota should force teams to declare requests.

### 12.7 Object Count Quotas

Object count quotas protect the API server and etcd from uncontrolled object growth.

Recommended object counts:

```yaml
secrets: "50"
configmaps: "50"
pods: "40"
services: "20"
persistentvolumeclaims: "10"
count/jobs.batch: "20"
count/cronjobs.batch: "10"
```

Without object quotas, a broken job controller, failed pipeline, or runaway automation can create operational pressure.

## 13. LimitRange Design

LimitRange sets default and minimum/maximum resource values for pods and containers in a namespace.

### 13.1 Why LimitRange Is Required

Without LimitRange:

- Developers may forget requests and limits.
- Pods may run BestEffort.
- Scheduling becomes unpredictable.
- HPA may not work correctly for CPU utilization.
- Quotas based on requests may block pods with missing requests.

### 13.2 Example Production LimitRange

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-prod-standard
  namespace: prod-payments-card-api
spec:
  limits:
  - type: Container
    min:
      cpu: 50m
      memory: 64Mi
    max:
      cpu: "2"
      memory: 4Gi
    defaultRequest:
      cpu: 250m
      memory: 512Mi
    default:
      cpu: "1"
      memory: 1Gi
  - type: Pod
    max:
      cpu: "4"
      memory: 8Gi
  - type: PersistentVolumeClaim
    min:
      storage: 1Gi
    max:
      storage: 200Gi
```

### 13.3 LimitRange Design Guidance

Set defaults that are safe, not oversized.

Bad default:

```text
CPU default request: 2 cores
Memory default request: 4Gi
```

This wastes capacity when developers forget to set values.

Better default:

```text
CPU default request: 100m-250m
Memory default request: 256Mi-512Mi
```

For production, require teams to explicitly size containers before go-live.

## 14. NetworkPolicy Design

By default, pods in a project can generally communicate freely. NetworkPolicy changes this posture by explicitly allowing required ingress and egress traffic.

Production namespaces should start from **default deny** and then allow only required flows.

### 14.1 NetworkPolicy Goals

Network policy should answer:

- Which namespaces can talk to this namespace?
- Which pods can talk to this pod?
- Which ports are allowed?
- Is egress to the internet allowed?
- Is egress to databases restricted?
- Are monitoring and ingress router paths allowed?
- Are DNS and API access accounted for?

### 14.2 Baseline Default Deny

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: prod-payments-card-api
spec:
  podSelector: {}
  policyTypes:
  - Ingress
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: prod-payments-card-api
spec:
  podSelector: {}
  policyTypes:
  - Egress
```

This blocks traffic unless another NetworkPolicy explicitly allows it.

### 14.3 Allow Same-Namespace Traffic

Use only if your application components inside the namespace need to talk to each other.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: prod-payments-card-api
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector: {}
  egress:
  - to:
    - podSelector: {}
```

For stricter tier isolation, do not allow all same-namespace traffic. Use app-specific labels.

### 14.4 Allow Frontend to API

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-api
  namespace: prod-payments-card-api
spec:
  podSelector:
    matchLabels:
      app: payments-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          platform.company.com/environment: prod
          platform.company.com/application: payments-web
      podSelector:
        matchLabels:
          app: payments-web
    ports:
    - protocol: TCP
      port: 8443
```

### 14.5 Allow API to Database Namespace

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-egress-to-db
  namespace: prod-payments-card-api
spec:
  podSelector:
    matchLabels:
      app: payments-api
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          platform.company.com/environment: prod
          platform.company.com/application: payments-db
      podSelector:
        matchLabels:
          app: payments-db
    ports:
    - protocol: TCP
      port: 5432
```

### 14.6 Allow Ingress Router Traffic

Routes are served by OpenShift ingress router pods, normally in an OpenShift ingress namespace. The exact labels can vary by platform configuration, so verify labels in your cluster before using this example.

```bash
oc get ns openshift-ingress --show-labels
oc get pods -n openshift-ingress --show-labels
```

Example policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-router-to-api
  namespace: prod-payments-card-api
spec:
  podSelector:
    matchLabels:
      app: payments-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-ingress
    ports:
    - protocol: TCP
      port: 8443
```

### 14.7 Allow DNS Egress

If you deny egress, workloads usually need DNS access. Verify DNS namespace, labels, and ports in your cluster.

Example pattern:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-dns
  namespace: prod-payments-card-api
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

In some OpenShift/OVN configurations, DNS pod ports and service translation behavior can require adjustment. Always test with a temporary debug pod before enforcing egress-deny in production.

### 14.8 AdminNetworkPolicy and BaselineAdminNetworkPolicy

Cluster administrators can use AdminNetworkPolicy and BaselineAdminNetworkPolicy for cluster-scoped network governance. These are powerful controls and should be designed carefully.

Use cases:

- Deny traffic between production and non-production namespaces.
- Deny access from application namespaces to platform namespaces.
- Allow DNS as a baseline.
- Enforce egress boundaries for user namespaces.

Critical warning:

- Do not accidentally select system namespaces.
- Do not use overly broad empty selectors against infrastructure namespaces.
- Test on non-production clusters first.
- Keep emergency rollback procedures ready.

### 14.9 NetworkPolicy Documentation Standard

Every production namespace should maintain a traffic matrix.

| Source Namespace | Source App | Destination Namespace | Destination App | Port | Protocol | Reason |
|---|---|---|---|---:|---|---|
| prod-payments-web | payments-web | prod-payments-card-api | payments-api | 8443 | TCP | Web to API |
| prod-payments-card-api | payments-api | prod-payments-db | postgres | 5432 | TCP | API DB access |
| openshift-ingress | router | prod-payments-card-api | payments-api | 8443 | TCP | Route ingress |
| prod-payments-card-api | all pods | openshift-dns | dns | 53 | TCP/UDP | DNS lookup |

Do not approve production go-live without a traffic matrix.

## 15. Ingress, Routes, and TLS Namespace Design

Production namespace design should define how external access is exposed.

### 15.1 Route Ownership

Application teams may own application Routes, but platform teams should define:

- Allowed hostnames.
- TLS policy.
- Certificate issuer.
- Wildcard route policy.
- Edge vs re-encrypt vs passthrough usage.
- HSTS requirements.
- External DNS automation.

### 15.2 Route Naming Pattern

```text
<app>-<component>-route
```

Example:

```text
payments-api-route
payments-web-route
```

### 15.3 TLS Guidance

For production:

- Use HTTPS only.
- Prefer re-encrypt when backend service also uses TLS.
- Avoid insecure edge termination for sensitive internal APIs.
- Use supported certificate automation where available.
- Track certificate ownership and renewal.

Example Route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments-api
  namespace: prod-payments-card-api
spec:
  host: payments-api.apps.example.com
  to:
    kind: Service
    name: payments-api
  port:
    targetPort: https
  tls:
    termination: reencrypt
    insecureEdgeTerminationPolicy: Redirect
```

## 16. Storage and PVC Governance

Production namespaces often fail operationally because storage is not governed.

### 16.1 Storage Design Questions

For every namespace, answer:

- Which StorageClass is allowed?
- Are snapshots supported?
- Are backups application-consistent or crash-consistent?
- What is the maximum PVC size?
- Are RWX volumes allowed?
- Is encryption required?
- What is the retention policy?
- Can developers create PVCs directly?
- Is storage replicated across zones?
- What is the DR restoration process?

### 16.2 PVC Quota

Example:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-storage
  namespace: prod-payments-card-api
spec:
  hard:
    persistentvolumeclaims: "10"
    requests.storage: 500Gi
    gold.storageclass.storage.k8s.io/requests.storage: 500Gi
```

### 16.3 LimitRange for PVC Size

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-pvc-size
  namespace: prod-payments-card-api
spec:
  limits:
  - type: PersistentVolumeClaim
    min:
      storage: 1Gi
    max:
      storage: 200Gi
```

### 16.4 Backup Labels

Add labels that backup tools can select.

```yaml
metadata:
  labels:
    backup.company.com/enabled: "true"
    backup.company.com/policy: gold-daily
    backup.company.com/retention: 35d
```

### 16.5 Stateful Workload Guidance

For stateful workloads:

- Prefer Operators for databases where supported.
- Validate CSI snapshot support.
- Test restore regularly.
- Define RPO/RTO at namespace onboarding time.
- Avoid putting multiple unrelated stateful systems in one namespace.
- Use PDBs carefully with StatefulSets.
- Understand zone failure behavior.

## 18. Reliability and Scheduling Design

A production namespace should include reliability controls for application workloads.

### 18.1 PodDisruptionBudget

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payments-api-pdb
  namespace: prod-payments-card-api
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payments-api
```

### 18.2 Topology Spread Constraints

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 6
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: payments-api
```

### 18.3 HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payments-api-hpa
  namespace: prod-payments-card-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payments-api
  minReplicas: 3
  maxReplicas: 12
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

### 18.4 Namespace Node Placement

For workloads requiring specific node pools, apply node selectors at workload or namespace level. Namespace-level selectors must be used carefully because they affect all pods in the namespace.

Example annotation pattern:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: "node-role.kubernetes.io/app-prod="
```

Use this only after validating the node labels and capacity model.

### 18.5 Taints and Tolerations

For dedicated production nodes:

- Taint nodes to repel non-production workloads.
- Add tolerations only to approved production workloads.
- Do not give broad tolerations to all namespaces.

## 19. Image and Registry Governance

Production namespaces should not pull arbitrary images from the internet.

### 19.1 Image Policy

Define:

- Approved registries.
- Image signing policy.
- Vulnerability scanning gate.
- Tag immutability policy.
- Digest pinning policy.
- Base image standard.
- Emergency image exception process.

### 19.2 Image Pull Secrets

Avoid sharing one global image pull secret with all namespaces unless required by enterprise design.

Preferred approach:

- Namespace-specific pull secret.
- Limited registry scope.
- Rotated credentials.
- Managed through GitOps/secrets management.

### 19.3 Tag Strategy

Avoid deploying mutable tags in production:

Bad:

```text
registry.example.com/payments/api:latest
```

Better:

```text
registry.example.com/payments/api:1.2.3
registry.example.com/payments/api@sha256:<digest>
```

## 20. Secrets and Configuration Design

### 20.1 Secret Ownership

Classify secrets by ownership:

| Secret Type | Owner | Example |
|---|---|---|
| Platform secret | Platform team | Pull secret, CA bundle |
| Application secret | App team | DB password, API key |
| Operator secret | Operator team | Operand credentials |
| External integration secret | Security/IAM team | Cloud credentials |

### 20.2 Secret Rules

Production secrets should:

- Never be stored in plaintext Git.
- Be rotated regularly.
- Be scoped to one namespace unless explicitly approved.
- Be readable only by required service accounts.
- Be excluded from normal developer view where possible.
- Have an owner and expiry.

### 20.3 ConfigMap Rules

ConfigMaps are not secrets. Do not place passwords, tokens, or certificates with private keys in ConfigMaps.

## 21. Operator and Operand Namespace Design

Operators require careful namespace planning.

### 21.1 Operator Namespace Patterns

Common models:

1. Operator installed in a dedicated operator namespace.
2. Operator watches one namespace.
3. Operator watches selected namespaces.
4. Operator watches all namespaces.

### 21.2 Production Rule

Do not install random Operators directly in application production namespaces without platform review.

Review:

- Does the Operator create cluster-scoped resources?
- Which namespaces does it watch?
- What permissions does it require?
- Does it create privileged pods?
- Does it modify network/security settings?
- Does it manage backups or CRDs?
- What is its upgrade policy?

```yaml
  - prod-payments-card-api
```

## 23. Project Request Template

OpenShift allows cluster administrators to customize the default project template used when users request new projects.

### 23.1 What to Include in a Project Template

A project template can include:

- Namespace/project metadata.
- RoleBindings.
- ResourceQuota.
- LimitRange.
- Default NetworkPolicy.
- Service accounts.

For production, many enterprises prefer GitOps-based namespace creation instead of open self-provisioning. However, project templates are still useful for standardizing lower environments or controlled self-service.

### 23.2 Example Project Template Skeleton

```yaml
apiVersion: template.openshift.io/v1
kind: Template
metadata:
  name: project-request
  namespace: openshift-config
parameters:
- name: PROJECT_NAME
- name: PROJECT_ADMIN_USER
objects:
- apiVersion: project.openshift.io/v1
  kind: Project
  metadata:
    name: ${PROJECT_NAME}
    labels:
      platform.company.com/managed-by: template
- apiVersion: v1
  kind: ResourceQuota
  metadata:
    name: rq-default
    namespace: ${PROJECT_NAME}
  spec:
    hard:
      requests.cpu: "2"
      requests.memory: 4Gi
      pods: "10"
- apiVersion: v1
  kind: LimitRange
  metadata:
    name: lr-default
    namespace: ${PROJECT_NAME}
  spec:
    limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 256Mi
      default:
        cpu: 500m
        memory: 512Mi
```

### 23.3 Production Recommendation

For production namespaces:

- Disable unrestricted self-provisioning.
- Require namespace request through ITSM or developer portal.
- Generate namespace from approved template.
- Commit generated manifests to Git.
- Apply through GitOps.
- Keep platform guardrails immutable to app teams.

## 27. Troubleshooting Production Namespace Issues

### 27.1 Namespace Overview

```bash
oc get ns prod-payments-card-api --show-labels
oc describe ns prod-payments-card-api
oc get all -n prod-payments-card-api
```

### 27.2 RBAC Troubleshooting

```bash
oc auth can-i create deployments -n prod-payments-card-api --as user@example.com
oc auth can-i get secrets -n prod-payments-card-api --as user@example.com
oc get rolebinding -n prod-payments-card-api
oc describe rolebinding rb-admins -n prod-payments-card-api
```

For service accounts:

```bash
oc auth can-i get pods \
  --as system:serviceaccount:prod-payments-card-api:sa-payments-api \
  -n prod-payments-card-api
```

### 27.3 Quota Troubleshooting

```bash
oc get quota -n prod-payments-card-api
oc describe quota rq-prod-standard -n prod-payments-card-api
oc get resourcequota rq-prod-standard -n prod-payments-card-api -o yaml
```

Common error:

```text
exceeded quota: rq-prod-standard, requested: requests.cpu=500m, used: requests.cpu=8, limited: requests.cpu=8
```

Fix approach:

1. Check actual usage.
2. Check pending pods.
3. Right-size requests.
4. Remove unused resources.
5. Increase quota only through approval.

### 27.4 LimitRange Troubleshooting

```bash
oc get limitrange -n prod-payments-card-api
oc describe limitrange lr-prod-standard -n prod-payments-card-api
```

Common error:

```text
minimum cpu usage per Container is 50m, but request is 10m
```

Fix:

- Adjust pod request.
- Adjust LimitRange only if platform standard is wrong.

### 27.5 NetworkPolicy Troubleshooting

```bash
oc get networkpolicy -n prod-payments-card-api
```

### 27.6 SCC Troubleshooting

```bash
oc get pod <pod> -n prod-payments-card-api -o yaml | grep -i scc
oc describe pod <pod> -n prod-payments-card-api
oc adm policy who-can use scc restricted-v2
oc adm policy who-can use scc anyuid
```

Common error:

```text
unable to validate against any security context constraint
```

Fix approach:

1. Check service account.
2. Check pod securityContext.
3. Check image UID requirement.
4. Prefer fixing image to run non-root.
5. If exception is required, bind SCC only to the specific service account.

### 27.7 PVC Troubleshooting

```bash
oc get pvc -n prod-payments-card-api
oc describe pvc <pvc> -n prod-payments-card-api
oc get storageclass
oc describe storageclass <sc>
```

Common causes:

- Storage quota exceeded.
- LimitRange PVC max exceeded.
- StorageClass not available.
- WaitForFirstConsumer behavior waiting for pod scheduling.
- Zone/affinity conflict.
- CSI driver issue.

## 28. Common Anti-Patterns

### 28.1 One Giant Production Namespace

```text
prod
```

Problems:

- No clear ownership.
- Weak isolation.
- Hard to troubleshoot.
- RBAC too broad.
- NetworkPolicy complex.
- Quota meaningless.

### 28.2 No Default Deny

Allowing all pod-to-pod traffic creates lateral movement risk. Production namespaces should default-deny and explicitly allow required flows.

### 28.3 Developers as Namespace Admins Forever

Long-lived admin access in production causes:

- Uncontrolled changes.
- Unreviewed secrets access.
- Accidental guardrail modification.
- Audit findings.

Use GitOps and temporary break-glass instead.

### 28.4 Default Service Account Everywhere

Using the default service account hides workload identity and increases blast radius.

### 28.5 Unlimited Quota

No quota means one namespace can affect the whole cluster.

### 28.6 Random SCC Exceptions

Binding `anyuid` or `privileged` to broad groups or default service accounts is dangerous.

### 28.7 Mutable Image Tags in Production

Using `latest` makes deployments non-repeatable and incident rollback difficult.

## 30. Interview-Level Explanation

A strong production namespace design in OpenShift means treating the namespace as an enterprise landing zone, not just a Kubernetes folder. I design production namespaces around ownership, isolation, quota, network security, RBAC, SCC alignment, observability, backup, and GitOps lifecycle.

For a normal production application, I prefer one namespace per application per environment, such as `prod-payments-card-api`. For highly sensitive systems, I split by tier, such as web, API, worker, and database-access namespaces. I apply mandatory labels for environment, business unit, app, owner, compliance, support tier, cost center, and DR tier.

From a security perspective, I avoid default and system namespaces, use group-based RBAC, avoid permanent human admin access, deploy through GitOps service accounts, and bind SCC exceptions only to specific service accounts. I keep workloads compatible with restricted security wherever possible.

From a resource perspective, I apply ResourceQuota and LimitRange to control CPU, memory, storage, pod count, service count, secrets, configmaps, PVCs, and object counts. I size quota based on steady state, rolling update surge, HPA max, jobs, and incident headroom.

From a network perspective, I apply default-deny policies and then explicitly allow traffic from ingress routers, DNS, required application namespaces, and database services. I maintain a traffic matrix for every production namespace.

Finally, I manage namespace baselines through GitOps so RBAC, quotas, NetworkPolicies, service accounts, monitoring, and backup labels are version-controlled and auditable. This gives the enterprise a repeatable, secure, and supportable namespace model.

## 32. Final Recommended Standard

For enterprise OpenShift production namespace design, implement this default standard:

```text
Namespace model: one namespace per application per environment
High-security model: one namespace per application component per environment
Naming: <env>-<business-unit>-<app>[-component]
RBAC: group-based, least privilege, no permanent individual admin
Deployment: GitOps or controlled CI/CD service account
Security: restricted SCC/PSA compatible by default
Network: default-deny plus explicit allow policies
Quota: mandatory ResourceQuota and LimitRange
Storage: PVC quota, backup labels, snapshot validation
Observability: metrics, logs, alerts, runbooks
Backup: RPO/RTO labels and restore test
Governance: namespace created from template or GitOps factory
Review: periodic audit for drift, access, quota, SCC, and network exceptions
```

This design gives the enterprise a repeatable production namespace pattern that supports security, operations, cost management, compliance, and reliable OpenShift administration.
