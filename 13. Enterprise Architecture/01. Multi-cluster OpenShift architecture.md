# Multi-cluster OpenShift Architecture

**Area:** Enterprise Architecture  
**Level:** Advanced OpenShift Administration  
**Audience:** Senior OpenShift / Kubernetes Administrators, Platform Engineers, SREs, Cloud Architects  
**Experience target:** 10+ years Linux, DevOps, infrastructure, networking, and production operations  
**Last reviewed:** 2026-07-03  

---

## 1. Executive summary

A **multi-cluster OpenShift architecture** is an enterprise platform design where multiple OpenShift clusters are operated as one governed fleet instead of as independent isolated platforms. The goal is not simply to install many clusters. The goal is to provide a reliable, secure, repeatable, and auditable container platform across datacenters, cloud regions, business units, application environments, and edge locations.

In a mature enterprise, multi-cluster OpenShift solves problems that a single cluster cannot solve well:

- Regional high availability
- Disaster recovery
- Environment separation
- Regulatory isolation
- Business-unit tenancy
- Workload blast-radius reduction
- Upgrade safety
- Edge deployment
- Hybrid cloud placement
- Standardized security governance
- Centralized observability
- Centralized policy enforcement
- Declarative application and platform configuration

A single OpenShift cluster can be highly available inside one failure domain, but it cannot remove all enterprise risk. A cluster-wide failure, bad upgrade, bad operator, storage outage, datacenter outage, identity-provider failure, or accidental platform-level misconfiguration can still impact all workloads in that cluster. Multi-cluster architecture reduces that risk by spreading workloads and management responsibilities across multiple clusters while retaining centralized control.

The senior administrator's job is to design the fleet so that every cluster has a clear purpose, every control plane has an ownership model, every workload has a placement strategy, and every operational action can be repeated safely.

## 2. Key terms

| Term | Meaning |
|---|---|
| OpenShift cluster | A Kubernetes-based OpenShift Container Platform installation with its own API, control plane, worker nodes, network, storage integration, and cluster operators. |
| Fleet | A group of OpenShift or Kubernetes clusters managed under one operating model. |
| Hub cluster | A central management cluster used by Red Hat Advanced Cluster Management for Kubernetes, GitOps, policy, search, observability, and cluster lifecycle operations. |
| Managed cluster | A cluster imported into or provisioned by a hub so that lifecycle, policy, placement, observability, and application operations can be managed centrally. |
| Workload cluster | A cluster where application workloads run. It might also be a managed cluster. |
| Management cluster | A cluster that runs management services. In hosted control plane designs, the management cluster hosts the control planes for hosted clusters. |
| Hosted cluster | A cluster whose control plane runs as pods on a management cluster while its worker nodes are separate from the control plane. |
| ClusterSet | A logical grouping of managed clusters, often used for access control, placement, and organizational boundaries. |
| Placement | A policy or rule that selects clusters based on labels, claims, environment, region, compliance state, or capacity. |
| GitOps | Declarative management where desired state is stored in Git and synchronized to one or more clusters. |
| Push model | A central Argo CD or GitOps controller applies manifests directly to remote clusters. |
| Pull model | Each target cluster reconciles its own desired state locally, usually receiving application definitions or instructions from the hub. |
| Submariner | A multi-cluster networking solution used with RHACM for cross-cluster network connectivity and service discovery. |
| VolSync | A persistent volume replication mechanism used for business continuity and disaster-recovery scenarios. |

## 3. Why enterprises use multiple OpenShift clusters

### 3.1 Availability and failure-domain isolation

OpenShift control planes are highly available when installed with three or more control-plane nodes. That protects against node-level failure. It does not automatically protect against:

- A full datacenter outage
- Cloud region failure
- Storage backend outage
- Bad cluster-wide configuration
- Failed cluster upgrade
- Control-plane certificate issue
- Accidental deletion of critical cluster resources
- Broken network plugin configuration
- Broken authentication provider

Multiple clusters let you separate failure domains. For example:

- `prod-in1` in Mumbai
- `prod-in2` in Hyderabad
- `prod-dr1` in Bengaluru
- `nonprod-in1` in Delhi NCR
- `edge-store-001` at a remote site

If one cluster fails, business services can fail over, shift traffic, or continue in another region.

### 3.2 Blast-radius reduction

In single-cluster designs, all workloads share the same API server, cluster operators, cluster network, ingress tier, DNS integration, and storage integration. Even with namespaces and RBAC, platform-level failures are shared.

Multi-cluster design lets you reduce blast radius by separating:

- Production and non-production
- Regulated and non-regulated workloads
- Internet-facing and internal-only workloads
- Stateful and stateless platforms
- Business-critical and experimental applications
- Edge and central datacenter workloads
- Different lifecycle speeds

A 10-year experienced administrator should always ask: **What is the maximum business impact if this cluster is lost or misconfigured?**

### 3.3 Upgrade safety

OpenShift upgrades are cluster-scoped. A bad upgrade decision affects that full cluster. Multi-cluster architecture allows upgrade waves:

1. Lab cluster
2. Dev cluster
3. Test cluster
4. Pre-production cluster
5. Lower criticality production cluster
6. Critical production cluster
7. DR cluster after validation

This is safer than upgrading every workload environment at the same time.

### 3.4 Regulatory and compliance segmentation

Some workloads must be isolated due to data classification, geography, customer agreements, audit requirements, or internal security policy. A separate cluster can provide stronger isolation than namespace-level controls.

Examples:

- PCI workload cluster
- Government workload cluster
- Banking data cluster
- Internal developer sandbox cluster
- Public-facing DMZ application cluster
- AI/ML GPU cluster with separate data controls

### 3.5 Hybrid cloud and edge placement

Multi-cluster OpenShift supports workloads across:

- On-premises bare metal
- VMware vSphere
- OpenStack
- AWS
- Azure
- Google Cloud
- Red Hat OpenShift Service on AWS
- Azure Red Hat OpenShift
- Edge single-node OpenShift
- Compact three-node clusters
- Hosted control planes

The enterprise architecture decision is not only technical. It is also based on latency, data gravity, cost, availability, compliance, and supportability.

## 4. Enterprise reference architecture

### 4.1 High-level hub-and-spoke design

```text
                         +----------------------------------+
                         | Enterprise Identity / SSO        |
                         | LDAP / OIDC / SAML / MFA         |
                         +----------------+-----------------+
                                          |
                                          v
+--------------------------------------------------------------------------------+
|                         Management / Hub Cluster                               |
|                                                                                |
|  RHACM / MCE   GitOps / Argo CD   Governance   Search   Observability          |
|  Cluster API   Policies          Placement    Audit    Backup controller       |
+---------+----------------+----------------+----------------+------------------+
          |                |                |                |
          |                |                |                |
          v                v                v                v
+----------------+ +----------------+ +----------------+ +----------------+
| prod-in1       | | prod-in2       | | nonprod-in1    | | edge fleet     |
| OCP cluster    | | OCP cluster    | | OCP cluster    | | SNO/compact    |
| Apps + Storage | | Apps + Storage | | Apps + Storage | | local workloads|
+----------------+ +----------------+ +----------------+ +----------------+
          |                |
          |                |
          +-------+--------+
                  |
                  v
        +--------------------------+
        | Global DNS / GSLB / WAF  |
        | Traffic steering         |
        +--------------------------+
```

The hub cluster is not usually where major business applications should run. It should be treated as a management plane. If application workloads consume hub resources or destabilize the hub, the entire fleet management function becomes fragile.

### 4.2 Typical cluster roles

| Cluster type | Purpose | Runs business workloads? | Key components |
|---|---|---:|---|
| Hub cluster | Central fleet management | Usually no | RHACM, MCE, GitOps, policy, search, observability, backup tools |
| Production cluster | Critical workloads | Yes | Ingress, storage, monitoring, app operators, service mesh if required |
| Non-production cluster | Dev/test workloads | Yes | Lower SLA, shared developer services |
| DR cluster | Recovery target | Sometimes active-passive or active-active | Replicated app config, replicated data, standby routes/DNS |
| Edge cluster | Local low-latency workloads | Yes | SNO/compact cluster, local storage, constrained observability |
| Hosted control plane management cluster | Runs hosted control planes | Usually limited | HyperShift / hosted control plane components |
| Compliance cluster | Regulated workloads | Yes | Hardened policies, strict network/storage/audit controls |

## 5. Core architecture principles

### 5.1 Separate management plane from workload plane

The management plane should remain stable even if application clusters are under stress.

Good practice:

- Dedicated hub cluster
- Dedicated infra nodes for management components
- Resource quotas and requests for hub services
- Separate backup and restore plan for hub resources
- Restricted admin access
- Minimal application workloads on hub

Bad practice:

- Running critical customer workloads on the RHACM hub
- Using the hub as a generic shared cluster
- Allowing development teams to deploy arbitrary workloads on the hub
- No backup for hub policies and placement resources
- No documented hub recovery process

### 5.2 Use labels as architecture metadata

Labels are not decoration. In multi-cluster architecture, labels drive placement, policy, observability grouping, upgrade waves, and access boundaries.

Example cluster labels:

```yaml
metadata:
  labels:
    environment: prod
    region: in-north
    datacenter: delhi-dc1
    platform: baremetal
    compliance: pci
    owner: payments
    tier: critical
    upgrade-wave: wave-3
    network-zone: internal
    storage-profile: odf-replicated
```

A strong cluster-labeling model allows platform automation to decide where applications and policies should apply.

### 5.3 Standardize, but do not over-centralize

The fleet should be consistent where consistency matters:

- Identity provider configuration
- Certificate trust
- Ingress naming standards
- Logging and metrics standards
- StorageClass naming
- NetworkPolicy baseline
- SCC / Pod Security rules
- Image registry trust
- Backup policy
- Upgrade policy
- Audit logging

But not every cluster must be identical. Edge clusters, GPU clusters, PCI clusters, and general-purpose application clusters have different requirements. The architecture should use standards plus overlays.

Example Git repository layout:

```text
platform-config/
  base/
    oauth/
    certs/
    logging/
    monitoring/
    network-policy/
    security-policies/
  overlays/
    prod/
    nonprod/
    pci/
    edge/
    disconnected/
    gpu/
```

### 5.4 Prefer declarative operations

Manual cluster-by-cluster work does not scale. Use GitOps and policy automation for:

- Namespace creation
- RBAC
- NetworkPolicy
- Operator installation
- OAuth configuration
- Trusted CA bundles
- ImageContentSourcePolicy / ImageDigestMirrorSet
- MachineConfig
- StorageClass defaults
- LimitRange and ResourceQuota
- Backup configuration
- Compliance Operator configuration

The rule is simple: **If you need to repeat it on more than one cluster, put it in Git or policy.**

## 6. Red Hat Advanced Cluster Management architecture

### 6.1 RHACM role in the enterprise

Red Hat Advanced Cluster Management for Kubernetes provides a central control point for cluster lifecycle, application management, governance, observability, search, and integrations across a fleet. It commonly uses a hub-and-spoke model.

Major capabilities:

- Create clusters
- Import existing clusters
- Organize clusters into sets
- Apply governance policies
- Use placement to target clusters
- View cross-cluster resources
- Integrate with GitOps
- Observe cluster health and utilization
- Manage business continuity workflows
- Support multi-cluster networking integrations

### 6.2 Hub cluster

The hub cluster runs management services and stores the desired management state for the fleet.

Important hub responsibilities:

- Cluster lifecycle control
- Managed cluster registration
- Klusterlet add-on management
- Policy distribution
- Placement decision evaluation
- Search index
- Observability aggregation
- GitOps integration
- Business continuity management

Operational expectations:

- Treat hub as Tier-0 infrastructure.
- Back up hub configuration and RHACM resources.
- Restrict cluster-admin access.
- Monitor hub CPU, memory, etcd, API latency, and storage.
- Keep hub OpenShift version within supported compatibility boundaries.
- Do not allow random application workloads.

### 6.3 Managed cluster

A managed cluster is a cluster known to the hub. It runs agents/add-ons that communicate with the hub. Depending on network and registration model, communication may be initiated from the managed cluster to the hub, which is useful in restricted environments.

Managed cluster responsibilities:

- Run application workloads
- Run local OpenShift operators
- Enforce locally applied policy
- Report status and compliance
- Send metrics or summaries
- Reconcile local GitOps state if using pull-style architecture

### 6.4 Cluster lifecycle

Cluster lifecycle includes:

1. Provisioning
2. Importing
3. Labeling
4. Grouping into ClusterSets
5. Applying baseline policies
6. Configuring observability
7. Configuring GitOps placement
8. Upgrading
9. Rotating credentials and certificates
10. Decommissioning

Typical lifecycle flow:

```text
Request -> Approval -> Provision -> Import -> Label -> Baseline -> Validate -> Handover -> Operate -> Upgrade -> Retire
```

### 6.5 ClusterSet design

A ClusterSet is a logical collection of clusters. Use ClusterSets to represent strong management boundaries.

Example ClusterSets:

- `prod-critical`
- `prod-standard`
- `nonprod`
- `edge-retail`
- `pci-regulated`
- `shared-services`
- `gpu-ai`

Example YAML:

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta2
kind: ManagedClusterSet
metadata:
  name: prod-critical
```

Bind users or groups to specific ClusterSets rather than giving broad fleet access.

## 7. Multi-cluster application placement

### 7.1 Placement decision model

In enterprise architecture, application placement is not random. It is based on attributes such as:

- Environment
- Region
- Cluster health
- Capacity
- Compliance status
- Latency
- Data residency
- Business owner
- Network zone
- Storage capability
- GPU availability
- Upgrade wave

Example placement intent:

> Deploy payment APIs only to production clusters in India that are PCI-compliant, have ODF replicated storage, and are in upgrade wave 3 or later.

Example conceptual placement:

```yaml
apiVersion: cluster.open-cluster-management.io/v1beta1
kind: Placement
metadata:
  name: payments-prod-placement
  namespace: payments-gitops
spec:
  predicates:
  - requiredClusterSelector:
      labelSelector:
        matchExpressions:
        - key: environment
          operator: In
          values:
          - prod
        - key: compliance
          operator: In
          values:
          - pci
        - key: storage-profile
          operator: In
          values:
          - odf-replicated
```

### 7.2 Application topology patterns

| Pattern | Description | Use case | Risk |
|---|---|---|---|
| Single cluster | App runs in one cluster | Simple apps, noncritical workloads | Cluster outage affects app |
| Active-passive | Primary cluster serves traffic; secondary waits | Stateful apps, simpler DR | Failover time and data lag |
| Active-active regional | App runs in two or more production clusters | Critical stateless or replicated apps | Data consistency and routing complexity |
| Follow-the-sun | Workloads shift by time zone or demand | Global business apps | Requires mature automation |
| Edge-local | Workloads run near users/devices | Retail, telecom, manufacturing | Operational complexity at scale |
| Compliance-isolated | App runs only in approved clusters | PCI, government, banking | Capacity fragmentation |

### 7.3 Multi-cluster route and traffic design

OpenShift Routes are cluster-local. In multi-cluster enterprise architecture, you need a traffic layer above the clusters.

Options:

- Global DNS load balancing
- Cloud global load balancer
- External hardware load balancer
- Anycast or regional load balancing
- Service mesh federation where required
- API gateway in front of cluster ingress
- WAF and DDoS protection before public ingress

Typical active-active traffic path:

```text
User -> Global DNS/GSLB -> Regional LB/WAF -> OpenShift Ingress -> Service -> Pod
```

Traffic decisions should account for:

- Health checks
- Route readiness
- Cluster API health
- Application readiness
- Latency
- Regional failover
- TLS certificate ownership
- DNS TTL
- Session affinity
- Data consistency

Do not rely only on pod readiness when doing regional failover. A pod can be ready while database replication is broken.

## 8. GitOps architecture for multi-cluster OpenShift

### 8.1 Why GitOps is critical

With many clusters, manual configuration causes drift. GitOps provides:

- Version-controlled desired state
- Pull request approval
- Rollback history
- Audit trail
- Repeatable deployments
- Standardized cluster baselines
- Safer promotion between environments

GitOps should manage both:

1. **Platform configuration**
2. **Application configuration**

Keep them separated by repository, ownership, and RBAC.

### 8.2 Recommended repository structure

```text
gitops-root/
  clusters/
    prod-in1/
    prod-in2/
    nonprod-in1/
    edge-store-001/
  cluster-groups/
    base/
    prod/
    nonprod/
    edge/
    pci/
  applications/
    payments-api/
      base/
      overlays/
        dev/
        test/
        prod/
  policies/
    security-baseline/
    compliance-pci/
    network-baseline/
  operators/
    logging/
    openshift-gitops/
    compliance-operator/
    odf/
```

### 8.3 Push GitOps model

In a push model, the central Argo CD instance on the hub applies resources directly to managed clusters.

Advantages:

- Easier initial setup
- Centralized control
- Central Argo CD UI
- Good for small to medium fleets

Disadvantages:

- Hub needs credentials to target clusters
- Remote cluster API endpoints must be reachable
- Central controller can become CPU/memory bottleneck
- Hub outage can block synchronization
- Large fleets may create scaling pressure

Use push model for:

- Small fleets
- Connected datacenter environments
- Strong central operations model
- Early-stage GitOps adoption

### 8.4 Pull GitOps model

In a pull model, application definitions or instructions are propagated from the hub, but each managed cluster performs local reconciliation.

Advantages:

- Better scaling for larger fleets
- Local reconciliation continues even if hub is temporarily unavailable
- Useful for restricted network environments
- Reduces hub-side controller pressure
- Avoids direct hub-to-cluster apply path for every resource

Disadvantages:

- Requires GitOps components on each target cluster
- More moving parts
- Status is not always real-time
- Git repository access must be available from each cluster

Use pull model for:

- Edge clusters
- Large fleets
- Firewalled clusters
- High-scale application distribution
- Clusters with local autonomy requirements

### 8.5 Argo CD Agent pattern

The Argo CD Agent pattern uses a hub-and-spoke model with local Argo CD instances on workload clusters and a central control-plane view. It improves pull-style multi-cluster management and reduces some security and scale issues of traditional central push designs.

Use this pattern when:

- The hub should not store credentials for every workload cluster
- Workload clusters should reconcile locally
- Network paths from hub to workload clusters are restricted
- You need centralized visibility across multiple Argo CD instances
- You are operating at larger fleet scale

Be careful because advanced agent-based designs require stronger Argo CD knowledge, operational maturity, and observability.

## 9. Platform configuration with policy

### 9.1 Governance as code

Governance policies define what must exist or must not exist across clusters.

Common policy categories:

- Required operators
- Prohibited configurations
- Required NetworkPolicy baseline
- Required OAuth configuration
- Required audit logging
- Required image registry configuration
- Required certificate trust bundles
- Required namespace labels
- Required ResourceQuota and LimitRange
- Required Compliance Operator scans
- Required SCC restrictions
- Required machine configuration

### 9.2 Inform vs enforce

Policies should not always enforce immediately.

Use **inform** mode when:

- Introducing a new policy
- Auditing current state
- Measuring drift
- Testing impact
- Preparing production rollout

Use **enforce** mode when:

- The policy is proven safe
- The required state is mandatory
- Exceptions are documented
- Rollback is tested
- Application teams are informed

Example strategy:

```text
Week 1: inform only
Week 2: inform + report non-compliance
Week 3: enforce on nonprod
Week 4: enforce on lower prod
Week 5: enforce on all prod
```

### 9.3 Baseline policy examples

A senior platform team usually creates baseline policies for:

- Disable self-provisioning if required
- Enforce namespace ownership labels
- Ensure default deny NetworkPolicy for selected namespaces
- Install Compliance Operator
- Install File Integrity Operator where required
- Ensure trusted CA bundle ConfigMap
- Ensure image registry mirror configuration
- Ensure cluster monitoring is healthy
- Ensure OAuth identity provider is configured
- Ensure kubeadmin user is removed after enterprise identity is ready
- Ensure audit log forwarding

### 9.4 Example governance policy concept

```yaml
apiVersion: policy.open-cluster-management.io/v1
kind: Policy
metadata:
  name: policy-namespace-required-labels
  namespace: platform-governance
spec:
  remediationAction: inform
  disabled: false
  policy-templates:
  - objectDefinition:
      apiVersion: policy.open-cluster-management.io/v1
      kind: ConfigurationPolicy
      metadata:
        name: namespace-owner-label-required
      spec:
        remediationAction: inform
        severity: medium
        object-templates:
        - complianceType: musthave
          objectDefinition:
            apiVersion: v1
            kind: Namespace
            metadata:
              name: sample-namespace
              labels:
                owner: platform-team
```

This is a simplified example. In real production, you would avoid hard-coding a single namespace unless that is the intended target. Policy generators and templating are usually used for more scalable policy design.

## 10. Multi-cluster networking

### 10.1 Network layers

Multi-cluster networking has several layers:

| Layer | Scope | Example |
|---|---|---|
| Node network | Physical/virtual network for nodes | VLAN, bond, MTU, routing |
| Cluster network | Pod network inside one cluster | OVN-Kubernetes |
| Service network | Kubernetes Service IPs | ClusterIP, NodePort, LoadBalancer |
| Ingress network | North-south application access | OpenShift Router, IngressController |
| API network | Access to Kubernetes/OpenShift APIs | api.cluster.example.com:6443 |
| East-west network | Cluster-to-cluster application traffic | Submariner, service mesh, external routing |
| Management network | Hub to managed cluster communication | RHACM agents, proxy, firewall rules |

### 10.2 CIDR planning

CIDR planning is one of the most important architecture decisions. Avoid overlapping:

- Pod CIDRs
- Service CIDRs
- Node CIDRs
- Machine networks
- Datacenter networks
- VPN networks
- Cloud VPC/VNet ranges

Overlapping CIDRs can break:

- Submariner
- VPN routing
- Service discovery
- DR failover
- NetworkPolicy assumptions
- Load balancer health checks
- Storage replication traffic

Maintain a central IPAM document or system.

Example:

| Cluster | Pod CIDR | Service CIDR | Node network |
|---|---|---|---|
| prod-in1 | 10.128.0.0/14 | 172.30.0.0/16 | 10.10.0.0/22 |
| prod-in2 | 10.132.0.0/14 | 172.31.0.0/16 | 10.20.0.0/22 |
| nonprod-in1 | 10.136.0.0/14 | 172.32.0.0/16 | 10.30.0.0/22 |

### 10.3 Submariner use case

Submariner is used to connect services and pods across clusters. It can support cross-cluster connectivity and service discovery scenarios.

Use it when:

- Applications need private east-west connectivity across clusters
- Service discovery across clusters is required
- You want cluster-to-cluster communication without exposing everything through public ingress
- DR or active-active workloads need inter-cluster traffic

Be careful with:

- CIDR overlap
- MTU
- Firewall rules
- NAT traversal
- Gateway node placement
- Throughput requirements
- Encryption overhead
- Troubleshooting complexity

### 10.4 Ingress and DNS design

Each cluster normally has its own ingress domain:

```text
apps.prod-in1.example.com
apps.prod-in2.example.com
apps.nonprod-in1.example.com
```

Application-facing global domains sit above that:

```text
api.payments.example.com
portal.example.com
orders.example.com
```

Do not couple global application DNS too tightly to cluster-local route names. Use an enterprise DNS/GSLB layer.

### 10.5 Network security

Baseline controls:

- Default deny NetworkPolicy in sensitive namespaces
- Explicit ingress rules for application dependencies
- Explicit egress rules for regulated workloads
- Separate ingress controllers for public and private traffic
- WAF for internet-facing apps
- Egress firewall or egress gateway where needed
- No direct pod network routing from user networks
- API server restricted to admin networks or VPN
- Separate management network where possible

## 11. Identity, access, and security architecture

### 11.1 Central identity

Use enterprise identity providers:

- LDAP
- Active Directory
- OIDC
- SAML through an identity broker
- MFA through enterprise SSO

Avoid local-only users except for emergency break-glass access.

Important decisions:

- Same identity provider for all clusters or per-zone identity?
- How is group sync handled?
- How are admin groups mapped?
- How is break-glass access audited?
- How is kubeadmin removed or disabled after setup?
- How are certificates and CA bundles distributed?

### 11.2 RBAC model

Common role layers:

| Role | Scope | Example |
|---|---|---|
| Fleet admin | All clusters | Platform SRE team |
| Cluster admin | One cluster or ClusterSet | Regional operations team |
| Namespace admin | One or more projects | App team lead |
| Developer edit | Application namespace | Developer team |
| Read-only auditor | Fleet or selected clusters | Security/audit team |
| GitOps controller | Specific managed resources | Argo CD service account |

Do not give cluster-admin to application teams unless there is a strong reason and formal approval.

### 11.3 Secrets strategy

Secrets must not be copied manually across clusters.

Recommended options:

- External Secrets Operator
- Vault integration
- Cloud secret manager integration
- Sealed Secrets where appropriate
- SOPS with GitOps where approved
- Short-lived credentials
- Namespace-scoped secret ownership
- Separate secrets per environment

Never reuse production database passwords in non-production clusters.

### 11.4 Certificate and trust architecture

Multi-cluster OpenShift needs consistent trust for:

- API certificates
- Ingress certificates
- Internal service certificates
- Registry certificates
- Proxy certificates
- LDAP certificates
- OIDC certificates
- Git server certificates
- Mirror registry certificates

Recommended approach:

- Use enterprise CA hierarchy.
- Keep per-cluster certificate inventory.
- Automate certificate distribution where possible.
- Monitor expiry centrally.
- Test rotation in non-production.
- Avoid wildcard certificate sprawl without ownership.

### 11.5 Image security

Enterprise baseline:

- Use approved registries only.
- Mirror required release and operator images for disconnected or controlled environments.
- Enforce image signature or digest policy where required.
- Scan images in CI.
- Block privileged or root workloads unless approved.
- Use SCC and Pod Security Admission controls.
- Use NetworkPolicy for image pull and runtime boundaries.

## 12. Storage and data architecture

### 12.1 Storage is cluster-local unless designed otherwise

Most Kubernetes persistent volumes are bound to one cluster and one storage backend. Multi-cluster does not automatically mean multi-cluster storage.

You must decide:

- Is data active-active or active-passive?
- Is the app stateless or stateful?
- What is the RPO?
- What is the RTO?
- Is storage replicated synchronously or asynchronously?
- Are snapshots application-consistent?
- Is failback required?
- Is the target cluster using the same StorageClass behavior?

### 12.2 StorageClass standardization

Define enterprise storage profiles instead of random StorageClass names.

Example naming:

```text
ocs-storagecluster-ceph-rbd           # block RWO
ocs-storagecluster-cephfs             # shared RWX
thin-csi                              # vSphere thin RWO
fast-nvme-rwo                         # high performance local-backed
backup-snapshot-capable-rwo           # snapshot-ready class
```

Document for each StorageClass:

- Access modes
- Reclaim policy
- Volume binding mode
- Snapshot support
- Expansion support
- Encryption
- Replication
- Performance tier
- Backup support

### 12.3 Volume snapshots

Snapshots are useful but not equal to full disaster recovery.

Check:

- CSI snapshot support
- VolumeSnapshotClass
- Application quiescing requirements
- Database consistency
- Cross-cluster portability
- Snapshot retention
- Restore testing

### 12.4 VolSync and DR

VolSync can replicate persistent volume data across clusters or within a cluster. It is useful for persistent volume replication workflows, especially active-passive recovery scenarios.

Design considerations:

- Replication schedule
- Bandwidth
- Initial sync time
- Incremental sync behavior
- Encryption
- Secret management
- Restore workflow
- Application cutover procedure
- DNS switch procedure
- Data integrity verification

### 12.5 OADP and application backup

OpenShift API for Data Protection, based on Velero, is used for backup and restore of Kubernetes resources and persistent data where supported.

Use OADP for:

- Namespace backup
- Application resource backup
- PV backup/snapshot integration
- Migration-style restore
- DR restore testing

Do not assume OADP automatically handles every application consistency requirement. Databases may need pre/post hooks or native database backup.

## 13. Observability architecture

### 13.1 Observability layers

| Layer | Tooling | Purpose |
|---|---|---|
| Cluster monitoring | OpenShift monitoring stack | Cluster operators, nodes, control plane, platform alerts |
| User workload monitoring | Prometheus/Thanos depending on config | Application metrics |
| Multi-cluster observability | RHACM observability | Fleet health and utilization |
| Logging | Loki/Elasticsearch/third-party SIEM | Logs and audit trails |
| Tracing | Tempo/Jaeger/third-party | Distributed traces |
| Alerting | Alertmanager/SIEM/PagerDuty/etc. | Incident response |

### 13.2 What to monitor across clusters

Fleet-level monitoring:

- Cluster availability
- API server latency
- etcd health
- Node readiness
- ClusterOperator status
- MachineConfigPool status
- Ingress availability
- Route health
- Storage backend health
- PVC pending alerts
- Certificate expiry
- OAuth and identity errors
- GitOps sync status
- Policy compliance status
- Upgrade status
- Backup success/failure
- Capacity trend

### 13.3 Alert routing

Do not send every cluster alert to the same person.

Recommended routing dimensions:

- Cluster environment
- Business service
- Severity
- Team ownership
- Region
- Compliance domain
- Time of day

Example:

```text
Critical prod cluster alert -> Platform SRE on-call
Payment app alert -> Payment SRE team
Compliance policy violation -> Security operations
Nonprod warning -> Ticket only
Edge cluster offline -> Regional support team
```

### 13.4 Logging and audit

Audit logs should be handled differently from application logs.

Important audit events:

- ClusterRoleBinding changes
- OAuth changes
- SCC changes
- Secret access patterns
- Namespace deletion
- NetworkPolicy changes
- Image policy changes
- Node changes
- MachineConfig changes
- Operator subscription changes
- Route and ingress changes

Send audit logs to protected storage or SIEM. Restrict who can modify log forwarding.

## 14. Hosted control planes architecture

### 14.1 Concept

Hosted control planes separate the control plane from worker nodes. The control plane of a hosted cluster runs as pods on a management cluster. Worker nodes belong to the hosted cluster and run customer workloads.

Conceptual view:

```text
+----------------------------------------------------+
| Management Cluster                                 |
|                                                    |
|  Hosted control plane namespace: cluster-a         |
|    kube-apiserver pods                             |
|    etcd pods                                       |
|    controller-manager pods                         |
|    openshift-apiserver pods                        |
|                                                    |
|  Hosted control plane namespace: cluster-b         |
|    control plane components                        |
+-------------------------+--------------------------+
                          |
                          v
              +------------------------+
              | Hosted cluster workers |
              | App pods run here      |
              +------------------------+
```

### 14.2 Why use hosted control planes

Use cases:

- Faster cluster provisioning
- Better control-plane density
- Edge or large fleet management
- Separation of control plane and workers
- Centralized management of many control planes
- Reduced overhead compared to full standalone control planes per cluster

### 14.3 Design considerations

- The management cluster becomes highly critical.
- Use infrastructure nodes for hosted control plane components where appropriate.
- Plan resource requests and limits carefully.
- Protect hosted control plane namespaces.
- Isolate hosted control plane traffic with NetworkPolicy.
- Plan etcd backup and restore.
- Monitor API latency per hosted cluster.
- Validate version compatibility.
- Avoid using the management cluster for unrelated workloads.

## 15. Disaster recovery architecture

### 15.1 RPO and RTO

Before designing DR, define:

| Term | Meaning | Example |
|---|---|---|
| RPO | Maximum acceptable data loss | 15 minutes |
| RTO | Maximum acceptable recovery time | 1 hour |

Architecture changes depending on RPO/RTO.

| RPO/RTO target | Architecture pattern |
|---|---|
| Hours/days | Backup and restore |
| Minutes/hours | Async replication + warm standby |
| Seconds/minutes | Active-active or near-sync replication |
| Near zero | Complex active-active data platform, usually expensive |

### 15.2 DR layers

DR must cover:

- Cluster infrastructure
- etcd and control plane
- Application manifests
- Persistent volumes
- External databases
- DNS and traffic routing
- Secrets
- Certificates
- Image registries
- CI/CD and Git repositories
- Identity provider access
- Observability and logs

### 15.3 Active-passive DR flow

```text
Normal:
Users -> Cluster A active
Data replicated -> Cluster B standby
GitOps keeps manifests ready on Cluster B

Failure:
Detect failure -> Freeze writes if possible -> Promote data on Cluster B -> Enable routes -> Shift DNS/GSLB -> Validate app -> Notify users

Failback:
Repair Cluster A -> Reverse replicate -> Test -> Shift traffic back if required
```

### 15.4 Backup testing

A backup that is never restored is not a backup. Schedule restore tests.

Test cases:

- Restore one namespace
- Restore one application with PVC
- Restore from snapshot
- Restore to a different cluster
- Restore after deleting a route
- Restore after deleting a secret
- Restore after storage outage simulation
- Restore hub policy configuration

## 16. Upgrade strategy for multiple clusters

### 16.1 Upgrade waves

Use cluster labels to define upgrade waves.

```text
wave-0: lab
wave-1: dev
wave-2: test
wave-3: preprod
wave-4: low-criticality prod
wave-5: critical prod
wave-6: DR clusters
```

Do not upgrade all production clusters simultaneously.

### 16.2 Pre-upgrade checks

Before upgrade:

```bash
oc get clusterversion
oc get clusteroperators
oc get mcp
oc get nodes
oc adm top nodes
oc get co | grep -v 'True.*False.*False'
oc get pdb -A
oc get csv -A
oc get pods -A | egrep -v 'Running|Completed'
oc adm must-gather
```

Check:

- ClusterOperators available
- No degraded MachineConfigPool
- Enough node capacity
- Storage healthy
- No critical PDB deadlock
- Operators compatible
- Deprecated APIs removed
- Backup completed
- Monitoring and alerting working
- Application owners informed

After upgrade:

```bash

oc get nodes
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp | tail -50
```

Also validate:

- Critical routes

## 17. Capacity and scale planning

### 17.1 Per-cluster capacity

Track:

- CPU requested vs allocatable
- Memory requested vs allocatable
- Actual CPU usage
- Actual memory usage
- Pod count per node
- PVC capacity
- IOPS and throughput
- Ingress throughput
- API server request rate
- etcd database size
- Image registry usage
- Node pressure events

### 17.2 Fleet capacity

Fleet-level questions:

- Which clusters are near capacity?
- Which regions have no failover capacity?
- Which clusters are overcommitted?
- Which clusters are underutilized?
- Which clusters have too many critical apps?
- Can Cluster B absorb Cluster A during failover?
- Is DR capacity reserved or shared?

### 17.3 Hub scale

Hub cluster scale depends on:

- Number of managed clusters
- Number of policies
- Number of applications
- Number of placements
- Frequency of reconciliation
- Observability metrics volume
- Search index volume
- GitOps model
- Status reporting interval

For large fleets, reduce central pressure by:

- Using pull GitOps
- Grouping policies carefully
- Avoiding excessive policy templates
- Tuning observability metrics collection
- Using separate hubs per region or business domain
- Considering global hub patterns for many hub clusters

## 18. Edge architecture

### 18.1 Edge cluster types

| Type | Description | Use case |
|---|---|---|
| Single-node OpenShift | One node acts as control plane and worker | Remote site, telecom, retail |
| Compact cluster | Three nodes with combined control-plane/worker role | Small site with better HA |
| Standard edge cluster | Separate control plane and workers | Larger site |
| Hosted control plane edge | Control plane hosted centrally, workers at edge | Large edge fleet |

### 18.2 Edge constraints

- Limited bandwidth
- Intermittent connectivity
- Smaller hardware
- Local storage constraints
- Fewer local administrators
- Delayed patch windows
- Physical access risk
- Disconnected installation requirements
- Need for local autonomy

### 18.3 Edge recommendations

- Use GitOps pull model.
- Keep workloads small and predictable.
- Mirror images locally where needed.
- Pre-stage updates.
- Minimize dependencies on central services.
- Use local alert buffering.
- Automate certificate rotation.
- Use strong labels for site metadata.
- Treat edge failures as normal, not exceptional.

## 21. Common multi-cluster failure scenarios

### 21.1 Cluster is imported but unavailable in hub

Possible causes:

- Klusterlet agents not running
- Managed cluster cannot reach hub
- Certificate trust issue
- Proxy misconfiguration
- Expired credentials
- Namespace deletion issue
- Hub API route unreachable

Checks:

```bash
oc get managedcluster <cluster-name> -o yaml
oc get pods -n open-cluster-management-agent
oc get pods -n open-cluster-management-agent-addon
oc logs -n open-cluster-management-agent deploy/klusterlet-agent
```

### 21.2 Policy is not applying

Possible causes:

- Placement does not select cluster
- Cluster labels incorrect
- PlacementBinding missing
- Policy disabled
- Remediation set to inform
- Template error
- Missing permissions

Checks:

```bash
oc get policy -A
oc get placement -A
oc get placementdecision -A
oc get placementbinding -A
oc describe policy <policy-name> -n <namespace>
```

### 21.3 ApplicationSet does not deploy to all clusters

Possible causes:

- Placement selector mismatch
- Cluster secret missing
- GitOpsCluster resource missing
- Argo CD lacks permissions
- Destination namespace missing
- Pull model annotations missing
- Managed cluster cannot reach Git

Checks:

```bash
oc get applicationset -n openshift-gitops
oc describe applicationset <name> -n openshift-gitops
oc get application -A
oc get placementdecision -A
oc get secret -n openshift-gitops | grep cluster
```

### 21.4 Cross-cluster traffic fails

Possible causes:

- CIDR overlap
- Firewall blocked
- Gateway node unavailable
- MTU issue
- Service not exported
- DNS discovery issue
- NetworkPolicy denies traffic

Checks:

```bash
oc get pods -A | grep submariner
oc get networkpolicy -A
oc get svc -A
oc get endpoints -A
```

### 21.5 DR restore works but app fails

Possible causes:

- Secret not restored
- Route hostname conflict
- PVC restored but database inconsistent
- StorageClass mismatch
- External dependency not reachable
- Image pull secret missing
- ConfigMap points to old cluster endpoint
- DNS still points to failed cluster

Checks:

```bash
oc get pods -n <app-ns>
oc describe pod <pod> -n <app-ns>
oc get pvc -n <app-ns>
oc get events -n <app-ns> --sort-by=.lastTimestamp
oc get route -n <app-ns>
oc logs deploy/<app> -n <app-ns>
```

## 24. Senior administrator best practices

1. Do not design clusters only by environment. Design by failure domain, compliance, ownership, and lifecycle.
2. Keep the hub clean. It is a management plane, not a playground.
3. Label every cluster properly. Automation depends on labels.
4. Use GitOps for repeatable state.
5. Use policy for guardrails, not as a replacement for architecture.
6. Prefer pull models for large, edge, or restricted-network fleets.
7. Test DR with real restores, not PowerPoint diagrams.
8. Never ignore CIDR planning.
9. Document every StorageClass and its DR capability.
10. Use upgrade waves.
11. Keep secrets out of Git unless encrypted and approved.
12. Avoid cluster-admin sprawl.
13. Monitor certificate expiry centrally.
14. Validate backup and restore before production onboarding.
15. Separate public and private ingress.
16. Use standard namespace onboarding templates.
17. Track capacity at both cluster and fleet level.
18. Use canary clusters before fleet-wide policy changes.
19. Keep a break-glass process and test it.
20. Make every architecture decision auditable.

## 25. Interview-level explanation

If asked to explain multi-cluster OpenShift architecture in an interview:

> Multi-cluster OpenShift architecture means operating several OpenShift clusters as a governed enterprise fleet. I normally separate the management plane from workload clusters by using a dedicated hub cluster with Red Hat Advanced Cluster Management, multicluster engine, GitOps, governance policies, search, and observability. Workload clusters are grouped by environment, region, compliance, business owner, and failure domain. Applications are placed using labels and placement policies, and configuration is delivered declaratively through GitOps. For small fleets a push GitOps model is simpler, but for large or edge fleets I prefer pull-based reconciliation because each cluster reconciles locally and the hub has less direct dependency on every cluster API. Networking is planned carefully to avoid CIDR overlap, with global DNS or GSLB for north-south traffic and Submariner or service mesh only where east-west cluster connectivity is required. Storage and DR are designed separately because PVCs are normally cluster-local; for stateful apps I define RPO/RTO, snapshot, backup, replication, and failover procedures. The architecture also includes centralized identity, RBAC, policy compliance, observability, upgrade waves, backup testing, and strict control of the hub cluster. The main objective is to reduce blast radius while keeping operations standardized and auditable.

## 28. Final architecture mindset

A multi-cluster OpenShift platform is not successful because it has many clusters. It is successful when the organization can answer these questions clearly:

- Where should this workload run?
- Who can administer this cluster?
- How is the cluster configured?
- How is drift detected?
- How is policy enforced?
- How is traffic routed?
- How is data protected?
- How is failover performed?
- How are upgrades rolled out?
- How is compliance proven?
- How quickly can we rebuild or replace a cluster?

For a senior OpenShift administrator, the target is **fleet reliability with controlled autonomy**: central standards, local resilience, audited changes, repeatable recovery, and minimized blast radius.
