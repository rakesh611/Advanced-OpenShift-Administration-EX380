## 1. What Monitoring Architecture Means in OpenShift

In enterprise architecture, **monitoring architecture** is the complete design of how metrics, alerts, dashboards, health signals, and operational telemetry are collected, stored, queried, routed, secured, and retained across the OpenShift platform.

For a senior OpenShift administrator, monitoring architecture is not only about checking CPU and memory. It answers questions such as:

- Is the OpenShift control plane healthy?
- Is etcd stable?
- Are API servers responding within acceptable latency?
- Are nodes under memory, CPU, disk, PID, or network pressure?
- Are workloads consuming abnormal resources?
- Are applications exposing metrics correctly?
- Are platform alerts routed to the correct operations team?
- Are application alerts separated from platform alerts?
- Can developers view only their own project metrics?
- Is Prometheus storage sized correctly?
- Can the monitoring stack survive node loss?
- Can metrics be forwarded to a central enterprise observability platform?
- Are unsupported changes avoided so upgrades do not break monitoring?

In OpenShift, monitoring architecture is built around a Red Hat-managed Prometheus ecosystem. The platform installs a preconfigured and self-updating monitoring stack for core OpenShift components. User workload monitoring can be enabled separately so application teams can monitor their own services and pods.

---

## 2. Enterprise View of OpenShift Monitoring

At enterprise level, monitoring should be designed as a **platform service**, not as an afterthought.

A good monitoring architecture provides:

| Area | Enterprise Requirement |
|---|---|
| Platform health | Monitor API, etcd, scheduler, controller manager, kubelets, routers, image registry, Operators, nodes |
| Application health | Allow app teams to expose `/metrics` and create alerts safely |
| Availability | Monitoring stack should tolerate pod or node failure |
| Storage | Metrics data should survive pod restarts and be retained for required duration |
| Alerting | Alerts should be routed to correct teams with severity and ownership labels |
| Multi-tenancy | Developers should access only allowed namespace/project metrics |
| Security | Internal TLS, RBAC, OAuth, secrets, and external alert receiver credentials must be protected |
| Scalability | Avoid high-cardinality metrics and uncontrolled scraping |
| Compliance | Retain critical metrics and alert history according to policy |
| Operations | Provide runbooks, dashboards, SLOs, and escalation paths |

A senior admin must understand the difference between:

- **Monitoring stack health** — Is Prometheus/Alertmanager/Thanos healthy?
- **Cluster health** — Is OpenShift itself healthy?
- **Workload health** — Are applications healthy?
- **Business health** — Are services meeting SLA/SLO expectations?

## 3. Default OpenShift Monitoring Stack

OpenShift installs the default monitoring stack in the `openshift-monitoring` namespace during cluster installation.

This stack monitors core platform components such as:

- Kubernetes API server
- OpenShift API server
- etcd
- kubelets
- scheduler
- controller manager
- CoreDNS
- ingress/router HAProxy
- image registry
- Operator Lifecycle Manager
- cluster Operators
- nodes
- internal monitoring components

### Default Architecture Diagram

```text
                        +---------------------------------------+
                        |        OpenShift Web Console          |
                        |        Observe / Dashboards / Alerts  |
                        +-------------------+-------------------+
                                            |
                                            v
+----------------------+      +-----------------------------+
| Cluster Version      |----->| Cluster Monitoring Operator |
| Operator (CVO)       |      | openshift-monitoring        |
+----------------------+      +-------------+---------------+
                                            |
               +----------------------------+----------------------------+
               |                             |                            |
               v                             v                            v
+-----------------------------+   +-----------------------+   +----------------------+
| Prometheus Operator         |   | Prometheus k8s        |   | Alertmanager main    |
| Manages Prometheus/AM       |   | Platform metrics DB   |   | Alert routing        |
+--------------+--------------+   +-----------+-----------+   +----------+-----------+
               |                              |                          |
               |                              v                          v
               |                  +-----------------------+   +----------------------+
               |                  | Thanos Querier        |   | External Receivers   |
               |                  | Query aggregation     |   | Email / Pager / ITSM |
               |                  +-----------+-----------+   +----------------------+
               |                              |
               v                              v
+-----------------------------+   +-----------------------+
| Platform metric exporters   |   | Console/API queries   |
| node-exporter, KSM, OSM     |   | PromQL / dashboards   |
+-----------------------------+   +-----------------------+
```

### Important Principle

Do **not** manually modify monitoring stack resources in `openshift-monitoring`. The Cluster Monitoring Operator continuously reconciles these resources. Unsupported manual changes can be overwritten and are not supported.

## 4. Core Platform Monitoring vs User Workload Monitoring

OpenShift separates monitoring into two major domains.

### 4.1 Core Platform Monitoring

Core platform monitoring is installed by default.

Namespace:

```text
openshift-monitoring
```

Purpose:

- Monitor OpenShift platform components.
- Provide default alerts and dashboards.
- Support cluster health and upgrade safety.
- Send selected telemetry to Red Hat through Telemeter, depending on cluster configuration.

Managed by:

```text
Cluster Monitoring Operator
Prometheus Operator
Cluster Version Operator
```

Used by:

- Cluster administrators
- Platform SRE team
- Infrastructure team
- Red Hat support workflows

### 4.2 User Workload Monitoring

User workload monitoring is optional and is enabled by the cluster administrator.

Namespace:

```text
openshift-user-workload-monitoring
```

Purpose:

- Monitor application services and pods in user-defined projects.
- Allow developers to create `ServiceMonitor`, `PodMonitor`, and `PrometheusRule` objects.
- Separate application metrics from core platform ownership.
- Provide multi-tenant access to project-level metrics.

Managed by:

```text
Prometheus Operator in openshift-user-workload-monitoring
Cluster Monitoring Operator
```

Used by:

- Developers
- Application owners
- DevOps teams
- SRE teams

### 4.3 Comparison Table

| Feature | Core Platform Monitoring | User Workload Monitoring |
|---|---|---|
| Namespace | `openshift-monitoring` | `openshift-user-workload-monitoring` |
| Enabled by default | Yes | No, admin enables it |
| Main purpose | OpenShift/Kubernetes health | Application/project metrics |
| Prometheus | `prometheus-k8s` | `prometheus-user-workload` |
| Rule evaluation | Platform Prometheus | Thanos Ruler for user workloads |
| Alertmanager | Main Alertmanager | Optional dedicated user workload Alertmanager |
| Users | Cluster admins | Developers and project users |
| Customization | CMO supported config only | UWM supported config only |
| CR objects | Platform managed | `ServiceMonitor`, `PodMonitor`, `PrometheusRule` in user namespaces |

## 5. Monitoring Data Flow Architecture

Monitoring data moves through the architecture in stages.

```text
Application / Platform Component
        |
        | exposes /metrics endpoint
        v
Service / Pod Endpoint
        |
        | discovered by ServiceMonitor or PodMonitor
        v
Prometheus Operator
        |
        | generates scrape configuration
        v
Prometheus
        |
        | scrape + store + evaluate rules
        v
+-------------------+--------------------+
|                                        |
v                                        v
Alertmanager                         Thanos Querier
Alert routing                        Query aggregation
|                                        |
v                                        v
Email / Pager / ITSM / Webhook       Console / PromQL / Dashboards
```

For user workload monitoring, the flow is slightly different:

```text
User Project Service/Pod
        |
        v
ServiceMonitor / PodMonitor
        |
        v
Prometheus Operator in openshift-user-workload-monitoring
        |
        v
Prometheus User Workload
        |
        +--> Metrics storage
        |
        +--> Thanos Ruler evaluates user rules
                 |
                 v
              Alertmanager
```

## 6. Key Components and Responsibilities

### 6.1 Cluster Version Operator (CVO)

The CVO manages the lifecycle of cluster Operators installed by OpenShift. It ensures the Cluster Monitoring Operator is installed and updated as part of the OpenShift release lifecycle.

Senior admin view:

- Monitoring upgrades are tied to OpenShift lifecycle.
- Do not treat core monitoring components like manually installed Helm charts.
- During upgrades, check monitoring Operator status carefully.

Useful command:

```bash
oc get clusteroperators monitoring
oc describe clusteroperator monitoring
```

---

### 6.2 Cluster Monitoring Operator (CMO)

The CMO is the central controller for the OpenShift monitoring stack.

It manages:

- Platform Prometheus
- Platform Alertmanager
- Thanos Querier
- Telemeter Client
- Metrics targets
- Monitoring plugin
- User workload monitoring enablement
- Supported monitoring configuration

Senior admin view:

- The CMO is the source of truth.
- Use `cluster-monitoring-config` for platform monitoring configuration.
- Use `user-workload-monitoring-config` for user workload monitoring configuration.
- Do not edit generated StatefulSets, Deployments, Secrets, or Services directly unless Red Hat documentation explicitly allows it.

Useful command:

```bash
oc -n openshift-monitoring get pods
oc -n openshift-monitoring get configmap cluster-monitoring-config -o yaml
oc logs -n openshift-monitoring deploy/cluster-monitoring-operator
```

---

### 6.3 Prometheus Operator

Prometheus Operator manages Prometheus-related custom resources.

In `openshift-monitoring`, it manages platform Prometheus and Alertmanager.

In `openshift-user-workload-monitoring`, it manages user workload Prometheus and Thanos Ruler.

It watches objects such as:

- `ServiceMonitor`
- `PodMonitor`
- `PrometheusRule`
- `AlertmanagerConfig` where supported/enabled

Senior admin view:

- If a target is missing, check label selectors first.
- If a `ServiceMonitor` is ignored, check Prometheus Operator logs.
- Avoid putting user-defined monitoring objects in `openshift-*` or `kube-*` namespaces.

---

### 6.4 Prometheus

Prometheus is the time-series database and rule evaluation engine.

It performs:

- Pull-based scraping
- Time-series storage
- PromQL queries
- Alert rule evaluation
- Recording rule evaluation
- Remote write forwarding where configured

Enterprise concerns:

- Storage usage
- Retention period
- Cardinality
- Scrape interval
- Query performance
- Rule complexity
- Target availability
- Remote write reliability

Useful PromQL examples:

```promql
up

sum by (namespace) (container_memory_working_set_bytes)

sum(rate(container_cpu_usage_seconds_total[5m])) by (namespace)

histogram_quantile(0.95, sum(rate(apiserver_request_duration_seconds_bucket[5m])) by (le, verb))
```

---

### 6.5 Alertmanager

Alertmanager receives alerts and handles:

- Deduplication
- Grouping
- Routing
- Silencing
- Inhibition
- Notification delivery

Common receivers:

- Email
- Slack/Microsoft Teams webhook
- PagerDuty/Opsgenie
- ServiceNow/Jira/ITSM webhook
- Custom webhook

Senior admin view:

- Alerting without ownership labels creates noise.
- Always include labels like `severity`, `team`, `service`, `environment`, and `runbook_url`.
- Platform alerts and application alerts should have different ownership and routing paths.

---

### 6.6 Thanos Querier

Thanos Querier provides a single query interface that can aggregate and optionally deduplicate metrics from platform and user workload Prometheus sources.

Senior admin view:

- Console dashboards generally query through the OpenShift monitoring query path.
- HA Prometheus replicas scrape the same targets independently; query-layer deduplication matters.
- Thanos Querier is not the same as long-term Thanos object storage unless you design external long-term storage separately.

---

### 6.7 Thanos Ruler

For user workload monitoring, Thanos Ruler evaluates rules for user-defined projects.

It handles:

- User-defined alerting rules
- User-defined recording rules

Senior admin view:

- User workload Prometheus stores metrics.
- Thanos Ruler evaluates user workload rules.
- Persistent storage is important for Thanos Ruler in HA production designs.

---

### 6.8 Metrics Server

Metrics Server collects resource metrics and exposes the `metrics.k8s.io` API.

Used by:

- `oc adm top`
- `kubectl top`
- HPA resource metrics
- Other resource-metric consumers

Senior admin view:

- Metrics Server is for recent resource metrics, not long-term monitoring.
- Do not confuse Metrics Server with Prometheus.
- HPA CPU/memory metrics are usually served from `metrics.k8s.io`, not directly from Prometheus.

Commands:

```bash
oc adm top nodes
oc adm top pods -A
oc get --raw /apis/metrics.k8s.io/v1beta1/nodes | jq
```

---

### 6.9 kube-state-metrics

`kube-state-metrics` converts Kubernetes object state into metrics.

Examples:

- Deployment replicas
- Pod phases
- PVC status
- Node conditions
- CronJob status
- DaemonSet status

Useful PromQL examples:

```promql
kube_pod_status_phase
kube_deployment_status_replicas_available
kube_persistentvolumeclaim_status_phase
kube_node_status_condition
```

Senior admin view:

- kube-state-metrics tells you desired/current Kubernetes object state.
- It does not tell you container CPU/memory usage.

---

### 6.10 openshift-state-metrics

`openshift-state-metrics` expands Kubernetes state metrics with OpenShift-specific resources.

Examples:

- BuildConfig
- DeploymentConfig
- ImageStream
- Route
- OpenShift-specific resource state

Senior admin view:

- Useful for OpenShift-native workloads and legacy DeploymentConfig-based environments.

---

### 6.11 node-exporter

`node-exporter` runs on every node and exports Linux host metrics.

Examples:

- CPU
- Memory
- Disk
- Filesystem
- Network
- Load average
- Time sync indicators
- Kernel-level counters

Useful PromQL examples:

```promql
node_memory_MemAvailable_bytes
node_filesystem_avail_bytes
rate(node_network_receive_bytes_total[5m])
rate(node_cpu_seconds_total{mode!="idle"}[5m])
```

Senior admin view:

- Node exporter is essential for infra-level troubleshooting.
- Node pressure, disk saturation, inode exhaustion, and NIC errors often appear here before application symptoms are obvious.

---

### 6.12 Telemeter Client

Telemeter Client sends a subset of platform Prometheus metrics to Red Hat for remote health monitoring, depending on cluster configuration and connectivity.

Senior admin view:

- Useful for Red Hat support and Insights-related workflows.
- Must be considered in disconnected/restricted-network environments.
- Does not replace your internal monitoring or alerting.

---

### 6.13 Monitoring Plugin

The monitoring plugin provides monitoring pages in the OpenShift web console, especially under **Observe**.

It supports:

- Dashboards
- Metrics queries
- Alerts
- Targets
- Project-level views

Senior admin view:

- Developers often consume monitoring through the console, not direct Prometheus UI.
- RBAC controls what users can see.

## 8. High Availability Design

In multi-node clusters, key OpenShift monitoring components run in HA mode with two replicas distributed across nodes.

HA components include:

- Prometheus
- Alertmanager
- Thanos Ruler
- Thanos Querier
- Metrics Server
- Monitoring plugin

### 8.1 Prometheus HA Behavior

OpenShift Prometheus HA does not work like a traditional active/passive database.

Important points:

- Both Prometheus replicas scrape the same targets.
- Both store their own local time-series data.
- Replicas do not continuously synchronize their local TSDB data with each other.
- Data can differ between replicas during network or pod disruption.
- Query-layer deduplication is used to present a cleaner view.

### 8.2 Alertmanager HA Behavior

Alertmanager replicas synchronize notification and silence state.

Important points:

- Alertmanager tries to avoid duplicate notifications.
- If replicas cannot communicate, duplicate alerts can happen.
- Persistent storage helps avoid losing silences and alert state after pod recreation.

### 8.3 Production HA Requirements

For a production multi-node cluster:

- Configure persistent storage for Prometheus.
- Configure persistent storage for Alertmanager.
- Configure persistent storage for Thanos Ruler.
- Place monitoring pods across different nodes.
- Use infra nodes or dedicated monitoring nodes in larger clusters.
- Use node selectors and tolerations through supported ConfigMaps.
- Monitor monitoring stack itself.

### 8.4 Anti-Affinity and Placement

OpenShift handles much of the default placement, but enterprise designs often add:

- Infra node labels
- Taints for infra workloads
- Tolerations in monitoring configuration
- Dedicated storage class for monitoring
- Performance-oriented disks

Example node labeling:

```bash
oc label node worker-1 node-role.kubernetes.io/infra=
oc label node worker-2 node-role.kubernetes.io/infra=
oc label node worker-3 node-role.kubernetes.io/infra=
```

Example taint:

```bash
oc adm taint nodes worker-1 node-role.kubernetes.io/infra=:NoSchedule
```

Then configure monitoring components with `nodeSelector` and `tolerations` through CMO-supported configuration.

## 9. Storage and Retention Architecture

### 9.1 Why Persistent Storage Matters

Prometheus and Alertmanager are stateful.

Without persistent storage:

- Metrics are lost when Prometheus pods are recreated.
- Alertmanager silences can be lost.
- Duplicate notifications can occur after restarts.
- Troubleshooting historical incidents becomes difficult.

For enterprise clusters, persistent storage is strongly recommended.

### 9.2 Storage Design Considerations

| Design Area | Recommendation |
|---|---|
| Volume mode | Use filesystem volumes, not raw block |
| Filesystem | Use POSIX-compliant storage |
| Performance | Prefer low-latency storage for Prometheus TSDB |
| Access mode | Usually RWO per Prometheus replica |
| Retention | Match troubleshooting/compliance needs |
| Capacity | Size for scrape volume, cardinality, retention, and growth |
| Backup | Do not rely only on local Prometheus retention for compliance |

### 9.3 Retention Time vs Retention Size

Prometheus retention can be controlled by:

- Time: `24h`, `7d`, `15d`, `30d`
- Size: `10GB`, `100GB`, `500GB`

Good enterprise practice:

```text
Retention policy = min(time-based limit, size-based limit)
```

Example:

```yaml
prometheus:
  retention: 15d
  retentionSize: 100GB
```

This means Prometheus keeps up to 15 days of data, but can delete earlier if the size limit is reached.

### 9.4 Storage Sizing Factors

Prometheus storage depends on:

- Number of targets
- Number of metrics per target
- Scrape interval
- Label cardinality
- Recording rules
- Retention duration
- Replica count
- Churn rate of pods/containers

High churn creates more series because Kubernetes labels include dynamic identifiers.

### 9.5 Cardinality Risk

Bad metric labels:

```text
user_id
customer_id
session_id
request_id
transaction_id
pod_uid
random_uuid
```

These create unbounded time series.

Better labels:

```text
method
status_code
route
service
namespace
environment
team
```

Senior rule:

> Never allow application teams to publish high-cardinality metrics without review.

## 10. Alerting Architecture

### 10.1 Alert Lifecycle

```text
Metric condition becomes true
        |
        v
Prometheus / Thanos Ruler evaluates alert rule
        |
        v
Alert enters pending state
        |
        v
Condition remains true for `for:` duration
        |
        v
Alert becomes firing
        |
        v
Alertmanager receives alert
        |
        v
Grouping / inhibition / silence / routing
        |
        v
Receiver notification
```

### 10.2 Alert Rule Design

A good alert should be:

- Actionable
- Owned by a team
- Severity labeled
- Linked to a runbook
- Not based on short transient spikes
- Useful at 3 AM

Example labels:

```yaml
labels:
  severity: warning
  team: payments
  service: checkout
  environment: prod
```

Example annotations:

```yaml
annotations:
  summary: "Checkout API error rate is high"
  description: "5xx rate is above 5% for 10 minutes."
  runbook_url: "https://runbooks.example.com/checkout-high-5xx"
```

### 10.3 Severity Model

| Severity | Meaning | Example |
|---|---|---|
| `critical` | Immediate customer/platform impact | API server down, etcd quorum risk, app unavailable |
| `warning` | Degraded but not fully down | High latency, disk nearing full |
| `info` | Awareness only | Certificate expiring in 30 days |

### 10.4 Platform vs Application Alert Routing

Enterprise pattern:

```text
Platform alerts  ---> Platform SRE / OpenShift Admin team
App alerts       ---> Application team
Database alerts  ---> DBA / Database platform team
Security alerts  ---> Security operations team
Storage alerts   ---> Storage team
Network alerts   ---> Network operations team
```

### 10.5 Alert Noise Reduction

Use:

- `for:` duration
- Grouping
- Inhibition
- Severity levels
- Maintenance silences
- Ownership labels
- Runbooks
- SLO-based alerting

Avoid:

- Alerting on every pod restart
- Alerting on CPU spikes without duration
- Alerting without owner
- Critical severity for non-critical symptoms

Useful areas:

- Observe → Dashboards

In OpenShift, administrators often query metrics through:

- Web console Observe page

- Prometheus APIs
- CLI with route/API token

### 11.3 Dashboard Design Principles

A dashboard should answer an operational question.

Examples:

| Dashboard | Should Answer |
|---|---|

## 12. Metrics Discovery: ServiceMonitor, PodMonitor, PrometheusRule

### 12.1 ServiceMonitor

A `ServiceMonitor` tells Prometheus how to scrape metrics from a Kubernetes Service.

Use it when:

- Your application exposes metrics through a Service.
- You want stable service-based discovery.
- Multiple pods are behind one service selector.

Flow:

```text
Deployment -> Pods -> Service -> ServiceMonitor -> Prometheus scrape config
```

### 12.2 PodMonitor

A `PodMonitor` tells Prometheus how to scrape pods directly.

Use it when:

- Metrics are exposed by pods but not through a service.
- You need pod-level discovery.
- You understand pod churn impact.

Flow:

```text
Deployment -> Pods -> PodMonitor -> Prometheus scrape config
```

### 12.3 PrometheusRule

A `PrometheusRule` defines alerting and recording rules.

Use it for:

- Application alerts
- SLO rules
- Precomputed recording rules
- Reducing expensive query cost

### 12.4 Discovery Requirements

Most missing target issues come from:

- Wrong namespace
- Wrong labels
- Wrong service selector
- Wrong port name
- Metrics endpoint not listening
- TLS mismatch
- Authentication issue
- ServiceMonitor selector mismatch
- User workload monitoring not enabled

Senior troubleshooting rule:

> If target is missing, check selectors. If target is down, check endpoint reachability.

## 13. RBAC and Multi-Tenant Monitoring

OpenShift monitoring must respect project boundaries.

### 13.1 Admin View

Cluster admins can view platform-wide metrics and alerts.

Typical users:

```text
cluster-admin
platform-sre
openshift-admin
```

### 13.2 Developer View

Developers should view only their project metrics.

Typical permissions:

```bash
oc adm policy add-role-to-user view alice -n myapp
```

For editing monitoring objects, grant carefully:

```bash
oc adm policy add-role-to-user edit alice -n myapp
```

In production, prefer custom roles for:

- Creating `ServiceMonitor`
- Creating `PodMonitor`
- Creating `PrometheusRule`
- Viewing metrics

### 13.3 Multi-Tenant Guardrails

Use governance for:

- Which namespaces can create monitoring CRs
- Alert label requirements
- Allowed scrape intervals
- Cardinality limits
- Runbook requirements
- Ownership metadata
- Receiver routing standards

## 14. Security Architecture

### 14.1 Internal TLS

OpenShift monitoring uses TLS for internal component communication. The CMO manages internal certificate lifecycle and rotates certificates automatically.

Operational impact:

- During certificate rotation, monitoring pods can restart.
- Temporary mount or restart events can appear.
- This is expected if pods recover automatically.

Check events:

```bash
oc get events -n openshift-monitoring --sort-by=.lastTimestamp
```

### 14.2 Authentication and Authorization

Access to monitoring UIs and APIs is protected by OpenShift authentication and RBAC.

Do not expose Prometheus or Alertmanager unauthenticated.

### 14.3 Secrets

Alert receivers often require secrets:

- Webhook token
- Basic auth password
- OAuth client secret
- TLS client cert
- PagerDuty integration key
- ServiceNow token

Store these as Kubernetes Secrets in the correct namespace.

Do not hardcode secrets in Git.

### 14.4 Unsupported Security Mistakes

Avoid:

- Editing monitoring deployments directly
- Adding custom Prometheus in platform namespaces
- Exposing Prometheus publicly without auth
- Scraping sensitive endpoints without review
- Putting tokens in annotations
- Using insecure HTTP for remote write

### 14.5 NetworkPolicy Considerations

If your cluster enforces default-deny NetworkPolicy, ensure metrics scraping paths are allowed.

Application namespace may need ingress from monitoring namespace pods to metrics port.

Conceptual example:

```text
openshift-user-workload-monitoring/prometheus-user-workload
        ---> app-namespace/service:metrics-port
```

NetworkPolicy must allow this traffic where default-deny is active.

## 15. Network and Access Architecture

### 15.1 Pull-Based Scraping

Prometheus is pull-based:

```text
Prometheus ---> Target /metrics endpoint
```

This means:

- Targets do not push metrics by default.
- Prometheus must reach the target endpoint.
- DNS, service selectors, ports, TLS, and NetworkPolicy must be correct.

### 15.2 Target Endpoint Design

Good endpoint pattern:

```text
http://service.namespace.svc:8080/metrics
```

Recommended:

- Use named service ports.
- Use stable service selectors.
- Keep `/metrics` lightweight.
- Avoid requiring user-level auth for internal metrics unless configured properly.

### 15.3 External Access

For direct API/UI access:

- Use OpenShift-authenticated routes.
- Use bearer tokens.
- Keep RBAC minimal.
- Avoid exposing internal services unnecessarily.

Useful route check:

```bash
oc get route -n openshift-monitoring
```

## 16. Performance and Scalability Architecture

### 16.1 What Usually Breaks Monitoring at Scale

Common scale problems:

- Too many scrape targets
- Too many labels
- High-cardinality metrics
- Very short scrape intervals
- Expensive PromQL queries
- Too many recording rules
- Under-sized Prometheus PVC
- Slow storage backend
- No retention size limit
- Excessive pod churn
- Bad application metrics design

### 16.2 Scrape Interval Strategy

Typical guidelines:

| Workload | Suggested Scrape Interval |
|---|---|
| Critical platform metrics | OpenShift default |
| Normal app metrics | 30s to 60s |
| Heavy exporters | 60s to 120s |
| Batch metrics | 2m to 5m |

Do not set every application to 5s scrape interval unless there is a strong SRE reason.

### 16.3 Recording Rules

Use recording rules for expensive repeated queries.

Bad dashboard query repeated everywhere:

```promql
sum(rate(http_requests_total{status=~"5.."}[5m])) by (namespace, service)
/
sum(rate(http_requests_total[5m])) by (namespace, service)
```

Better:

```yaml
record: service:http_error_rate_5m
expr: |
  sum(rate(http_requests_total{status=~"5.."}[5m])) by (namespace, service)
  /
  sum(rate(http_requests_total[5m])) by (namespace, service)
```

### 16.4 Resource Requests and Limits

Monitoring components need predictable resources.

Enterprise practice:

- Monitor Prometheus memory usage.
- Monitor TSDB head series count.
- Monitor query latency.
- Monitor WAL replay time after restart.
- Increase resources through supported ConfigMaps only.

### 16.5 Placement on Infra Nodes

For large clusters, place monitoring components on infra nodes to isolate them from application workloads.

Benefits:

- Stable monitoring performance
- Reduced noisy-neighbor risk
- Easier capacity planning
- Cleaner chargeback/showback

## 17. Remote Write and Long-Term Metrics Architecture

### 17.1 Why Remote Write Is Used

Local Prometheus is not always enough for enterprise observability.

Use remote write when you need:

- Long-term metrics retention
- Multi-cluster central visibility
- Global dashboards
- Cross-region reporting
- Compliance retention
- Central SRE analytics
- Integration with enterprise observability platforms

Common remote systems:

- Thanos Receive
- Cortex
- Mimir
- VictoriaMetrics
- Managed Prometheus-compatible platforms

### 17.2 Remote Write Flow

```text
OpenShift Prometheus
        |
        | remote_write HTTPS + auth
        v
Central metrics receiver
        |
        v
Long-term storage / dashboards / global alerting
```

### 17.3 Security Requirements

Remote write should use:

- HTTPS
- Authentication
- Secret-managed credentials
- TLS validation
- Network allowlisting
- Clear ownership of receiver endpoint

### 17.4 External Labels

Always attach external labels for multi-cluster metrics.

Example labels:

```yaml
externalLabels:
  cluster: prod-ocp-delhi-01
  region: in-north
  environment: prod
```

Be careful with reserved labels. Avoid labels that conflict with platform expectations.

## 18. Enterprise Reference Architecture Patterns

### 18.1 Small Production Cluster

Use when:

- One cluster
- Limited workloads
- Small team

Pattern:

```text
Default core monitoring
+ User workload monitoring enabled
+ Persistent storage
+ Email/webhook alerting
+ 7-15 days retention
```

Design points:

- Keep simple.
- Use OpenShift console dashboards.
- Avoid custom Prometheus.
- Use alert ownership labels.

---

### 18.2 Large Enterprise Cluster

Use when:

- Hundreds/thousands of pods
- Multiple app teams
- Strict separation of duties

Pattern:

```text
Core monitoring on infra nodes
+ User workload monitoring on infra nodes
+ Dedicated storage class
+ Dedicated Alertmanager routing
+ Remote write to central platform
+ Namespace-level monitoring governance
```

Design points:

- Strong RBAC.
- Quotas and limits for teams.
- Metrics review process.
- Retention size and time configured.
- Runbooks mandatory for critical alerts.

---

### 18.3 Multi-Cluster Enterprise Monitoring

Use when:

- Multiple OpenShift clusters
- Hub-spoke operations
- Regional clusters
- DR clusters

Pattern:

```text
Cluster A Prometheus ---> Remote write ---> Central metrics platform
Cluster B Prometheus ---> Remote write ---> Central metrics platform
Cluster C Prometheus ---> Remote write ---> Central metrics platform

Central dashboards use labels:
cluster, region, environment, business_unit
```

Design points:

- Standardize labels.
- Standardize alert severities.
- Separate local alerting from global reporting.
- Keep local cluster alerting available even if central platform is down.

---

### 18.4 Disconnected / Restricted Network Cluster

Use when:

- No direct internet access
- Private registry
- Government/defense/regulated environments

Pattern:

```text
Local OpenShift monitoring
+ Local alert receivers
+ No dependency on internet receivers
+ Optional internal remote write endpoint
+ Offline runbooks
```

Design points:

- Validate Telemeter/remote health expectations.
- Use internal SMTP/webhook/ITSM endpoints.
- Ensure image mirroring for required components.
- Keep support bundles and must-gather process ready.

## 21. Troubleshooting Playbooks

### 21.1 Monitoring ClusterOperator Degraded

Symptoms:

```bash
oc get co monitoring
```

Shows:

```text
Degraded=True
Available=False
```


Common causes:

- Invalid `cluster-monitoring-config` YAML

- Image pull failure
- Node scheduling issue

- Resource pressure

3. Check affected pod events.

## 22. Common Enterprise Mistakes

### Mistake 1: Installing a Separate Custom Prometheus for Everything

Why it is bad:

- Duplicates platform functionality
- Increases resource usage
- Creates support complexity
- Can conflict with OpenShift monitoring design

Better:

- Use built-in platform monitoring.
- Enable user workload monitoring.
- Use remote write for centralization.

---

### Mistake 2: Editing Generated Monitoring Deployments

Why it is bad:

- CMO overwrites changes.
- Unsupported by Red Hat.
- Breaks upgrades.

Better:

- Configure through supported ConfigMaps.

---

### Mistake 3: No Persistent Storage

Why it is bad:

- Metrics lost on pod restart.
- Silences lost.
- Duplicate notifications possible.
- Incident investigation becomes difficult.

Better:

- Configure PVCs for Prometheus, Alertmanager, and Thanos Ruler.

---

### Mistake 4: High Cardinality Metrics

Why it is bad:

- Prometheus memory grows rapidly.
- Disk fills quickly.
- Queries become slow.
- Monitoring becomes unstable.

Better:

- Review application metric labels.
- Ban unbounded IDs as labels.
- Use logs/traces for request-level detail, not metrics labels.

---

### Mistake 5: Alerts Without Runbooks

Why it is bad:

- On-call engineer does not know what to do.
- Alert becomes noise.
- MTTR increases.

Better:

- Every critical alert should have `runbook_url`.

---

### Mistake 6: No Team Ownership Labels

Why it is bad:

- Alerts go to wrong teams.
- Platform team becomes dumping ground.

Better:

```yaml
labels:
  team: payments
  service: checkout
  environment: prod
```

---

### Mistake 7: Treating Metrics Server as Prometheus

Why it is bad:

- Metrics Server is not long-term monitoring.
- It serves resource metrics API for recent usage.

Better:

- Use Metrics Server for `top` and HPA resource metrics.
- Use Prometheus/Thanos for observability queries and alerts.

## 23. DO380 / Senior Admin Interview Points

### 23.1 Explain Monitoring Architecture

Strong answer:

> OpenShift monitoring is a CMO-managed Prometheus ecosystem. Core platform monitoring runs in `openshift-monitoring` and monitors platform components by default. User workload monitoring is optional and runs in `openshift-user-workload-monitoring`. The stack includes Prometheus, Prometheus Operator, Alertmanager, Thanos Querier, Thanos Ruler, Metrics Server, node-exporter, kube-state-metrics, openshift-state-metrics, Telemeter, and console monitoring plugin. Supported customization is done through `cluster-monitoring-config` and `user-workload-monitoring-config`, not by editing generated resources.

### 23.2 How Do You Enable User Workload Monitoring?

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
```

Then verify:

```bash
oc get pods -n openshift-user-workload-monitoring
```

### 23.3 How Do Applications Expose Metrics?

Steps:

1. Application exposes `/metrics`.
2. Service exposes named metrics port.
3. Developer creates `ServiceMonitor` or `PodMonitor`.
4. Prometheus Operator generates scrape config.
5. Prometheus scrapes target.
6. Metrics appear in Observe page.

### 23.4 Why Is Persistent Storage Important?

Because Prometheus, Alertmanager, and Thanos Ruler are stateful. Without persistent storage, metrics data, silences, and alerting state can be lost during pod recreation.

### 23.5 What Causes Prometheus High Disk Usage?

- High-cardinality labels
- Too many targets
- Short scrape intervals
- Long retention
- Pod churn
- Large histograms
- Uncontrolled app metrics

### 23.6 How Do You Troubleshoot Missing Metrics?

Check:

```bash
oc get servicemonitor -A
oc get podmonitor -A
oc get endpoints -n <namespace>
oc logs -n openshift-user-workload-monitoring deploy/prometheus-operator
```

Then confirm:

- UWM enabled
- Selector labels match
- Service port name matches
- Endpoint is reachable
- Target appears in Observe → Targets

### 23.7 What Is Thanos Querier Used For?

Thanos Querier provides a multi-tenant query interface that aggregates and can deduplicate metrics from core platform and user workload monitoring sources.

### 23.8 What Is Thanos Ruler Used For?

Thanos Ruler evaluates alerting and recording rules for user-defined projects in the user workload monitoring stack.

## Final Senior Admin Summary

Monitoring architecture in OpenShift is a CMO-managed, Prometheus-based observability platform built into the cluster. The default stack monitors core OpenShift components in `openshift-monitoring`, while optional user workload monitoring adds application-level monitoring in `openshift-user-workload-monitoring`.

A 10-year experienced OpenShift administrator should design monitoring around reliability, supportability, HA, storage, alert ownership, RBAC, security, cardinality control, and long-term metrics strategy. The most important production rule is simple:

> Use OpenShift-supported monitoring configuration paths. Do not manually modify generated monitoring stack resources.
