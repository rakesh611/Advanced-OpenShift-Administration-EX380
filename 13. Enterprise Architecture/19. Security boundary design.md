# Security Boundary Design in Enterprise Architecture for Advanced OpenShift Administration

**Audience:** Senior Linux / DevOps / OpenShift administrators with ~10 years of infrastructure experience  
**Context:** Enterprise Architecture, OpenShift Container Platform 4.x, production multi-tenant platforms  
**Goal:** Design security boundaries that reduce blast radius, support compliance, and still allow application teams to deliver quickly.

---

## 1. What “Security Boundary Design” Means in OpenShift

In traditional infrastructure, a security boundary was often a firewall zone, VLAN, VM, subnet, or Active Directory group. In OpenShift, the boundary is not one control. It is a layered design made from identity, namespace, RBAC, admission control, SCC/Pod Security Admission, network policy, node isolation, storage policy, image policy, secret handling, auditing, and operational governance.

A strong OpenShift security boundary answers these questions:

- Who can access the cluster API?
- Who can create, modify, delete, or view resources?
- Which workloads can run privileged?
- Which workloads can talk to which workloads?
- Which workloads can reach external networks?
- Which namespaces belong to which tenant, environment, or trust zone?
- Which nodes can run sensitive or privileged workloads?
- Which images are allowed to run?
- Which secrets and persistent data can be accessed?
- How is activity audited and investigated?
- How is boundary drift detected and corrected?

Security boundary design is therefore a **defense-in-depth architecture**. You should never depend on only one control such as namespace separation or RBAC. A namespace helps organize and scope resources, but it is not a complete hard isolation boundary by itself.

## 2. Senior Architect View: Boundary vs Isolation vs Governance

| Concept | Meaning | OpenShift Examples |
|---|---|---|
| Boundary | A logical or technical line that controls access and blast radius | Project, cluster, node pool, network zone, registry, storage backend |
| Isolation | Enforcement that prevents one workload/user from affecting another | SCC, SELinux, NetworkPolicy, RBAC, taints, separate clusters |
| Governance | Rules and process to keep boundaries consistent over time | GitOps, policy-as-code, audits, naming standards, change control |

A common mistake is to treat a namespace as the whole security design. In enterprise OpenShift, a namespace is only the **starting unit**. A real boundary usually combines:

```text
Identity boundary
+ Namespace/project boundary
+ RBAC boundary
+ Runtime boundary
+ Network boundary
+ Data boundary
+ Node boundary
+ Supply-chain boundary
+ Audit/governance boundary
```

## 3. Boundary Design Principles

### 3.1 Least privilege by default

No user, service account, namespace, or application should receive more permissions than required. Avoid giving `cluster-admin`, `admin`, `edit`, `anyuid`, or `privileged` permissions casually.

Good design:

```text
Developer group -> edit only in assigned dev namespaces
Application admin -> admin only in assigned app namespaces
Platform admin -> cluster-admin, limited to platform team
CI/CD service account -> deploy only to target namespaces
Monitoring service account -> read-only metrics and logs where required
```

Bad design:

```text
All developers -> cluster-admin
All project admins -> can bind SCCs
Default service account -> anyuid
All namespaces -> open ingress and egress
```

### 3.2 Deny-by-default where possible

OpenShift and Kubernetes often start with permissive network behavior unless policies are applied. Enterprise design should move toward:

- Default deny ingress between application namespaces.
- Default deny unnecessary egress.
- Explicit allow rules for DNS, ingress controller, monitoring, CI/CD, and required app-to-app flows.
- Explicit SCC grants only to named service accounts.
- Explicit storage access through PVCs and StorageClasses.

### 3.3 Separate by risk, not only by team

Do not design namespaces only around organizational structure. Design them around trust level and blast radius.

Example:

```text
finance-dev
finance-test
finance-stage
finance-prod
finance-prod-pci
finance-shared-tools
```

Even if the same team owns the application, production, PCI, and shared tooling should not share the same boundary.

### 3.4 Prefer platform guardrails over manual review

Manual security review is useful, but it does not scale. Use OpenShift-native controls and GitOps:

- Default project templates
- ResourceQuota and LimitRange
- RBAC role binding templates
- NetworkPolicy baselines
- SCC admission controls
- Operator installation governance
- Image registry and signature policy
- Compliance Operator / policy-as-code
- Argo CD / OpenShift GitOps

### 3.5 Separate platform administration from tenant administration

A tenant admin should manage applications in their namespace. A platform admin manages cluster-level controls. Never allow tenant admins to change cluster-wide policies unless explicitly required.

## 4. OpenShift Security Boundary Control Map

| Boundary Layer | Control | Purpose |
|---|---|---|
| Cluster boundary | Separate clusters, ACM, hub-spoke, cloud account/subscription/project | Hardest operational boundary |
| API boundary | OAuth, LDAP/OIDC, RBAC, kubeconfig control, MFA via IdP | Controls API access |
| Namespace boundary | Project design, labels, annotations, quotas, LimitRange | Tenant and environment separation |
| Runtime boundary | SCC, Pod Security Admission, SELinux, seccomp, capabilities | Controls how pods run |
| Network boundary | NetworkPolicy, AdminNetworkPolicy, BaselineAdminNetworkPolicy, EgressFirewall, EgressIP, firewall | Controls traffic flows |
| Node boundary | MachineConfigPool, taints, tolerations, node labels, infra/workload nodes | Controls workload placement |
| Data boundary | Secrets, etcd encryption, PVCs, StorageClasses, backup encryption | Protects configuration and persistent data |
| Ingress boundary | Routes, IngressController, TLS profiles, WAF/load balancer | Controls external entry |
| Supply-chain boundary | Trusted registries, image mirrors, image signatures, CI/CD policy | Controls what code runs |
| Operator boundary | OLM, OperatorGroup, install namespace, RBAC review | Controls privileged automation |
| Audit boundary | Audit profiles, logging, SIEM forwarding, alerts | Detects and proves boundary behavior |
| Governance boundary | GitOps, policy-as-code, change control, ownership labels | Prevents drift |

## 5. Cluster-Level Boundary Design

### 5.1 When one cluster is acceptable

A shared cluster is acceptable when tenants have similar risk levels and the enterprise accepts soft multi-tenancy controls.

Use one cluster for:

- Multiple internal application teams in the same business unit.
- Dev/test workloads with moderate risk.
- Non-regulated production workloads with strong namespace, RBAC, and network policy.
- Platform services that are centrally managed.

Minimum required controls:

- Tenant-specific namespaces.
- Group-based RBAC.
- Default NetworkPolicy or AdminNetworkPolicy baseline.
- SCC restrictions.
- Quota and LimitRange.
- Image registry restrictions.
- Logging and audit forwarding.
- GitOps-managed namespace baseline.

### 5.2 When separate clusters are required

Use separate clusters when you need a hard isolation boundary.

Separate clusters are recommended for:

- PCI / regulated workloads.
- Classified or sensitive government workloads.
- Internet-facing workloads with high attack exposure.
- Different legal entities or customers.
- Different operational ownership models.
- Workloads requiring privileged host access.
- Experimental workloads that may destabilize nodes.
- Production vs non-production when compliance requires separation.

Strong enterprise pattern:

```text
Hub cluster: ACM, governance, policy, observability integration
Spoke cluster 1: Non-prod shared
Spoke cluster 2: Standard production
Spoke cluster 3: Regulated production
Spoke cluster 4: Platform tooling / CI/CD
```

### 5.3 Hard vs soft multi-tenancy

| Model | Boundary Strength | Use Case |
|---|---:|---|
| Namespace-only | Weak | Small dev clusters only |
| Namespace + RBAC + NetworkPolicy + SCC | Medium | Shared enterprise app platform |
| Dedicated node pools per tenant | Stronger | Sensitive workloads in shared cluster |
| Dedicated cluster per tenant/zone | Strongest | Regulated, high-risk, external customer workloads |

## 6. Namespace / Project Boundary Design

OpenShift projects are Kubernetes namespaces with OpenShift-specific project features. They are the most common unit of tenant isolation, but they must be reinforced with other controls.

### 6.1 Namespace naming standard

A useful enterprise naming convention:

```text
<business-unit>-<application>-<environment>
<tenant>-<platform-service>-<environment>
<zone>-<application>-<environment>
```

Examples:

```text
fin-payments-dev
fin-payments-test
fin-payments-prod
hr-portal-prod
platform-monitoring-prod
security-tools-prod
```

Avoid ambiguous names:

```text
prod
app1
team-a
namespace1
```

### 6.2 Namespace label standard

Labels are important because NetworkPolicy, AdminNetworkPolicy, cost reporting, GitOps, quotas, and governance can use them.

Example namespace labels:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: fin-payments-prod
  labels:
    tenant: finance
    app: payments
    env: prod
    data-classification: confidential
    zone: internal
    owner: finance-platform
    network-boundary: restricted
    compliance: pci
```

Recommended labels:

| Label | Example | Purpose |
|---|---|---|
| `tenant` | `finance` | Tenant grouping |
| `app` | `payments` | Application identity |
| `env` | `dev`, `test`, `prod` | Environment separation |
| `zone` | `internal`, `dmz`, `restricted` | Network/security zone |
| `data-classification` | `public`, `internal`, `confidential`, `restricted` | Data protection |
| `owner` | `team-name` | Accountability |
| `compliance` | `pci`, `sox`, `none` | Compliance targeting |
| `gitops-managed` | `true` | Drift management |

### 6.3 Namespace lifecycle governance

Every namespace should have a lifecycle:

1. Request
2. Approval
3. Creation from template
4. RBAC binding
5. Quota and limit assignment
6. Network baseline assignment
7. Monitoring/log forwarding inclusion
8. Periodic review
9. Decommission

Do not allow uncontrolled self-provisioning in production clusters unless there is a strong admission/governance layer.

Useful commands:

```bash
# Check who can create projects
oc adm policy who-can create projectrequests

# Remove self-provisioner from authenticated users if required
oc adm policy remove-cluster-role-from-group self-provisioner system:authenticated:oauth

# Reconcile default self-provisioner if needed
oc adm policy reconcile-cluster-role-bindings self-provisioners
```

## 7. RBAC Boundary Design

RBAC is the primary API authorization boundary. It controls what users, groups, and service accounts can do.

### 7.1 Enterprise RBAC model

Use groups from LDAP/OIDC/IdP and bind groups to roles. Avoid binding permissions directly to individual users except for break-glass access.

Example group model:

```text
ocp-platform-admins
ocp-security-admins
ocp-network-admins
ocp-storage-admins
finance-payments-admins
finance-payments-developers
finance-payments-readonly
finance-payments-cicd
```

### 7.2 Role selection

| Role | Scope | Use |
|---|---|---|
| `cluster-admin` | Cluster-wide | Very limited platform admin access |
| `admin` | Namespace-local | Manage most resources in a project, including role bindings in that project |
| `edit` | Namespace-local | Modify application resources, usually cannot modify roles/bindings |
| `view` | Namespace-local | Read-only access |
| Custom Role | Namespace or cluster | Least-privilege role for specific operations |

### 7.3 Recommended RBAC design

```bash
# Platform team
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins

# Application namespace admin
oc adm policy add-role-to-group admin finance-payments-admins -n fin-payments-prod

# Developers can edit app resources in dev/test, not prod
oc adm policy add-role-to-group edit finance-payments-developers -n fin-payments-dev
oc adm policy add-role-to-group edit finance-payments-developers -n fin-payments-test
oc adm policy add-role-to-group view finance-payments-developers -n fin-payments-prod

# Read-only auditors
oc adm policy add-role-to-group view finance-payments-readonly -n fin-payments-prod
```

### 7.4 Use custom roles for CI/CD

CI/CD rarely needs broad `edit`. Create a custom role when possible.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployer-limited
  namespace: fin-payments-prod
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "patch", "update"]
- apiGroups: [""]
  resources: ["services", "configmaps"]
  verbs: ["get", "list", "watch", "create", "patch", "update"]
- apiGroups: ["route.openshift.io"]
  resources: ["routes"]
  verbs: ["get", "list", "watch"]
```

Bind it to a service account:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cicd-deployer-limited
  namespace: fin-payments-prod
subjects:
- kind: ServiceAccount
  name: cicd-deployer
  namespace: fin-payments-prod
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: deployer-limited
```

### 7.5 RBAC validation commands

```bash
# Can current user perform an action?
oc auth can-i create pods -n fin-payments-prod
oc auth can-i update deployments.apps -n fin-payments-prod

# Can another user perform an action?
oc auth can-i create routes.route.openshift.io \
  --as=user1@example.com \
  -n fin-payments-prod

# Can service account perform an action?
oc auth can-i patch deployments.apps \
  --as=system:serviceaccount:fin-payments-prod:cicd-deployer \
  -n fin-payments-prod

# Who can perform risky actions?
oc adm policy who-can create pods/exec -n fin-payments-prod
oc adm policy who-can use scc/privileged
oc adm policy who-can use scc/anyuid
oc adm policy who-can create rolebindings -n fin-payments-prod
```

### 7.6 RBAC anti-patterns

Avoid:

- Giving `cluster-admin` to application teams.
- Binding `system:authenticated` to powerful roles.
- Giving CI/CD service accounts cluster-wide permissions.
- Allowing project admins to bind privileged SCCs.
- Using personal user kubeconfigs in automation.
- Keeping stale users/groups after team changes.

## 8. Service Account Boundary Design

Service accounts are workload identities. Every pod runs as a service account. The service account determines API permissions and SCC eligibility.

### 8.1 Good service account design

Use one service account per workload trust level.

```text
default                    -> no special permissions
payments-api-sa            -> app runtime identity
payments-worker-sa         -> background worker identity
payments-cicd-sa           -> deployment automation identity
payments-job-sa            -> batch job identity
payments-anyuid-sa         -> only if legacy image requires fixed UID
```

Create service accounts explicitly:

```bash
oc create sa payments-api-sa -n fin-payments-prod
oc create sa payments-worker-sa -n fin-payments-prod
oc create sa payments-cicd-sa -n fin-payments-prod
```

Patch deployment to use service account:

```bash
oc set serviceaccount deployment/payments-api payments-api-sa -n fin-payments-prod
```

### 8.2 Avoid using the default service account for everything

The `default` service account should remain low privilege. If a workload needs special access, create a named service account and bind only the required permissions.

### 8.3 Service account token design

Modern OpenShift versions use bound service account token behavior instead of automatically creating long-lived token secrets in the older style. Design automation around short-lived tokens where possible.

Useful command:

```bash
oc create token payments-cicd-sa -n fin-payments-prod --duration=1h
```

For external automation, prefer:

- OIDC/workload identity integration where available.
- Short-lived tokens.
- Dedicated service accounts per pipeline.
- Rotation and revocation process.
- No personal kubeconfig in CI/CD.

## 9. Runtime Security Boundary: SCC, Pod Security Admission, SELinux, Seccomp

Runtime boundary controls what a container can do on the node.

### 9.1 Security Context Constraints

Security Context Constraints (SCCs) are OpenShift-specific admission controls. They control pod permissions such as UID strategy, privileged mode, host namespaces, capabilities, SELinux context, volumes, and privilege escalation.

Important design rule:

```text
Do not modify default SCCs.
Create custom SCCs only when absolutely required and reviewed.
Grant SCCs only to specific service accounts, not broad user groups.
```

### 9.2 Common SCCs and design use

| SCC | Risk | Typical Use |
|---|---:|---|
| `restricted-v3` / `restricted-v2` | Low | Default secure workloads |
| `nonroot-v2` | Low/Medium | Images that can run non-root but need non-random UID behavior |
| `anyuid` | Medium/High | Legacy images requiring fixed UID or root user inside container |
| `hostnetwork-v2` | High | Network agents requiring host networking |
| `privileged` | Very High | Node agents, storage/network/security operators only |

### 9.3 SCC grant pattern

Do not grant `anyuid` to all users in a namespace. Grant it to a named service account.

```bash
oc create sa legacy-app-sa -n fin-legacy-prod
oc adm policy add-scc-to-user anyuid \
  -z legacy-app-sa \
  -n fin-legacy-prod
oc set serviceaccount deployment/legacy-app legacy-app-sa -n fin-legacy-prod
```

Validate:

```bash
oc adm policy who-can use scc/anyuid
oc get pod <pod-name> -n fin-legacy-prod -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

### 9.4 Pod Security Admission

Pod Security Admission applies Kubernetes pod security standards at namespace level using profiles such as `privileged`, `baseline`, and `restricted`, and modes such as `enforce`, `warn`, and `audit`.

Recommended enterprise posture:

```bash
# Warn and audit restricted violations first
oc label namespace fin-payments-prod \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted \
  --overwrite

# Enforce restricted only after compatibility testing
oc label namespace fin-payments-prod \
  pod-security.kubernetes.io/enforce=restricted \
  --overwrite
```

Do not run tenant workloads in system namespaces such as `default`, `kube-system`, `openshift`, or `openshift-*` platform namespaces.

### 9.5 Container securityContext baseline

Recommended workload baseline:

```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop:
    - ALL
  seccompProfile:
    type: RuntimeDefault
```

Pod-level example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: secure-api
  namespace: fin-payments-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: secure-api
  template:
    metadata:
      labels:
        app: secure-api
    spec:
      serviceAccountName: payments-api-sa
      securityContext:
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: api
        image: registry.example.com/finance/secure-api@sha256:<digest>
        ports:
        - containerPort: 8080
        securityContext:
          runAsNonRoot: true
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities:
            drop:
            - ALL
        volumeMounts:
        - name: tmp
          mountPath: /tmp
      volumes:
      - name: tmp
        emptyDir: {}
```

### 9.6 Runtime anti-patterns

Avoid:

```yaml
securityContext:
  privileged: true
  runAsUser: 0
  allowPrivilegeEscalation: true
```

Avoid unless strongly justified:

```yaml
hostNetwork: true
hostPID: true
hostIPC: true
```

These settings weaken the pod-to-node boundary and can bypass normal network controls.

## 10. Network Boundary Design

Network isolation is one of the most important enterprise security boundaries.

### 10.1 Understand default traffic behavior

Without NetworkPolicy, pods might be reachable from other pods and network endpoints depending on cluster network configuration. Therefore production namespaces should not depend on “no one knows the service name” as a boundary.

### 10.2 NetworkPolicy design model

NetworkPolicy is namespace-scoped. It applies to selected pods in the namespace. It does not create traffic; it only allows or denies based on policy selection.

Recommended pattern:

1. Apply default deny ingress.
2. Apply default deny egress if the app can tolerate it.
3. Allow DNS egress.
4. Allow ingress from OpenShift router / ingress controller if needed.
5. Allow only specific app-to-app traffic.
6. Allow monitoring from monitoring namespace.
7. Allow egress to approved external CIDRs/FQDN mechanisms.

### 10.3 Default deny ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: fin-payments-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

### 10.4 Default deny egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: fin-payments-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress
```

### 10.5 Allow DNS egress

Most applications need DNS. In OpenShift, DNS usually runs in `openshift-dns`.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: fin-payments-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

### 10.6 Allow ingress from router to frontend pods

Label your ingress/router namespace based on your cluster. Verify labels first:

```bash
oc get ns openshift-ingress --show-labels
```

Example policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-router-to-web
  namespace: fin-payments-prod
spec:
  podSelector:
    matchLabels:
      app: payments-web
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-ingress
    ports:
    - protocol: TCP
      port: 8080
```

### 10.7 Allow web to API

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-api
  namespace: fin-payments-prod
spec:
  podSelector:
    matchLabels:
      app: payments-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: payments-web
    ports:
    - protocol: TCP
      port: 8080
```

### 10.8 Allow API to database only

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
  namespace: fin-payments-prod
spec:
  podSelector:
    matchLabels:
      app: payments-db
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: payments-api
    ports:
    - protocol: TCP
      port: 5432
```

### 10.9 Cross-namespace allow with namespace labels

Example: allow `checker` namespace pods to access MySQL in `database` namespace.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: mysql-db-conn
  namespace: database
spec:
  podSelector:
    matchLabels:
      deployment: web-mysq
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          team: devsecops
    ports:
    - protocol: TCP
      port: 3306
```

Important: the policy must be created in the namespace containing the target pods.

### 10.10 AdminNetworkPolicy and BaselineAdminNetworkPolicy

For enterprise multi-tenancy, namespace-scoped NetworkPolicy might not be enough because tenant administrators can control policies inside their namespace. OpenShift with OVN-Kubernetes supports cluster-scoped administrative network policies that tenant NetworkPolicies cannot override.

Use AdminNetworkPolicy for:

- Cluster-wide tenant isolation.
- Mandatory deny rules.
- Mandatory monitoring/security allow rules.
- North-south egress restrictions.
- Preventing tenant owners from weakening platform controls.

Example skeleton:

```yaml
apiVersion: policy.networking.k8s.io/v1alpha1
kind: AdminNetworkPolicy
metadata:
  name: tenant-isolation-finance
spec:
  priority: 30
  subject:
    namespaces:
      matchLabels:
        tenant: finance
  ingress:
  - name: deny-non-finance-ingress
    action: Deny
    from:
    - namespaces:
        notSameLabels:
        - tenant
  egress:
  - name: pass-egress-to-namespace-policy
    action: Pass
    to:
    - namespaces: {}
```

Check your OpenShift version and exact API support before using ANP/BANP in production. Treat ANP as a platform-level control owned by cluster/network administrators.

### 10.11 Egress boundary

Egress is often forgotten. It matters because a compromised pod can exfiltrate data externally.

Egress design options:

- NetworkPolicy egress rules.
- EgressFirewall for namespace-level egress control on OVN-Kubernetes.
- EgressIP for stable outbound source IP.
- External firewall allowlisting.
- Proxy-based egress with authentication and logging.
- Service mesh egress gateway for advanced L7 control.

Example egress allow to an internal API CIDR:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-to-internal-api
  namespace: fin-payments-prod
spec:
  podSelector:
    matchLabels:
      app: payments-api
  policyTypes:
  - Egress
  egress:
  - to:
    - ipBlock:
        cidr: 10.40.20.0/24
    ports:
    - protocol: TCP
      port: 443
```

### 10.12 Network boundary validation

Use test pods with appropriate tools:

```bash
oc run net-test --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod, install tools only in test/lab if allowed
curl -vk https://service.namespace.svc:8443
```

Useful OpenShift checks:

```bash
oc get networkpolicy -n fin-payments-prod
oc describe networkpolicy allow-api-to-db -n fin-payments-prod
oc get pods -n fin-payments-prod --show-labels
oc get ns --show-labels
oc get svc,endpoints -n fin-payments-prod
```

### 10.13 Network anti-patterns

Avoid:

- No default deny in production.
- All namespaces allowed to communicate.
- Database pods reachable from all namespaces.
- Egress open to `0.0.0.0/0` without logging or proxy.
- Policies relying on labels that are not controlled.
- HostNetwork pods used for normal applications.
- NetworkPolicy created in the wrong namespace.
- Mismatched `podSelector` labels.

## 11. Node Boundary Design

Node isolation controls where workloads run. It is important when workloads have different risk levels, performance profiles, or hardware access.

### 11.1 Node pool types

Common enterprise node pools:

```text
master/control-plane nodes  -> OpenShift control plane only
infra nodes                 -> routers, registry, monitoring, logging, platform infra
worker-general              -> normal application workloads
worker-prod                 -> production applications
worker-regulated            -> PCI/SOX/confidential workloads
worker-privileged           -> workloads requiring host access
worker-gpu                  -> GPU workloads
worker-edge                 -> edge workloads
```

### 11.2 Taints and tolerations

Use taints to repel workloads unless they explicitly tolerate the node pool.

Example:

```bash
oc adm taint nodes worker-regulated-1 dedicated=regulated:NoSchedule
```

Deployment toleration:

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: regulated
        effect: NoSchedule
```

### 11.3 Node selector

```yaml
spec:
  template:
    spec:
      nodeSelector:
        node-role.kubernetes.io/regulated: ""
```

### 11.4 Design rule

For high-risk workloads:

```text
Namespace isolation + RBAC + NetworkPolicy + SCC is good.
Dedicated nodes improve blast-radius control.
Separate cluster is strongest.
```

Use dedicated nodes for:

- Privileged DaemonSets.
- PCI/regulated workloads.
- GPU workloads with special drivers.
- Noisy performance-sensitive workloads.
- Workloads requiring special kernel, hugepages, SR-IOV, or real-time tuning.

## 12. Data Boundary Design

Data boundary includes secrets, ConfigMaps, persistent volumes, backups, snapshots, and etcd.

### 12.1 ConfigMap vs Secret

| Object | Use | Security Note |
|---|---|---|
| ConfigMap | Non-sensitive configuration | Not for passwords or tokens |
| Secret | Passwords, tokens, keys, certificates | Base64 is not encryption; protect RBAC and etcd |

### 12.2 Secret design

Good practices:

- Store secrets in the same namespace as consuming workloads unless central secret management is used.
- Restrict who can `get`, `list`, or `watch` secrets.
- Avoid mounting secrets into unnecessary pods.
- Avoid exposing secrets as environment variables when file mount is safer.
- Use external secret managers for enterprise-grade rotation.
- Enable etcd encryption.
- Include secret rotation in operational runbooks.

Check who can read secrets:

```bash
oc adm policy who-can get secrets -n fin-payments-prod
oc adm policy who-can list secrets -n fin-payments-prod
```

### 12.3 Etcd encryption

Etcd stores cluster state. Enabling etcd encryption protects sensitive resources if an etcd backup or disk is exposed. Remember that etcd encryption protects values, not object names, namespaces, or resource types.

Enable:

```bash
oc patch apiserver cluster \
  --type=merge \
  -p '{"spec":{"encryption":{"type":"aescbc"}}}'
```

Check status:

```bash
oc get apiserver cluster -o jsonpath='{.spec.encryption.type}{"\n"}'
oc get openshiftapiserver cluster -o yaml | grep -i encryption -A5
oc get kubeapiserver cluster -o yaml | grep -i encryption -A5
```

Backup warning:

```text
If etcd encryption is enabled, protect the static_kuberesources archive separately.
It contains encryption keys required for restore.
```

### 12.4 StorageClass boundary

Do not give all teams the same storage backend if data classification differs.

Example storage classes:

```text
gold-encrypted-rwo
silver-standard-rwo
bronze-dev-rwo
regulated-encrypted-rwx
backup-retained-rwo
```

Design controls:

- Use encrypted backend volumes.
- Separate storage classes by data classification.
- Limit who can create PVCs in production namespaces.
- Use quotas for storage requests.
- Use snapshot policy by environment.
- Avoid RWX for sensitive workloads unless required.
- Validate reclaim policy: `Delete` vs `Retain`.

### 12.5 PersistentVolume reclaim policy

| Reclaim Policy | Behavior | Security Impact |
|---|---|---|
| `Delete` | Deletes backend volume when PVC is removed | Useful for ephemeral/dev data |
| `Retain` | Keeps backend volume after PVC deletion | Safer for critical data, requires manual cleanup |

For production databases, use careful backup and restore design. Do not rely only on PVC snapshots unless application consistency is handled.

## 13. Ingress, Route, and TLS Boundary Design

Ingress boundary controls external access to applications.

### 13.1 Route exposure model

In OpenShift, Routes expose services through the ingress controller/router.

Route TLS types:

| Type | TLS termination | Use Case |
|---|---|---|
| Edge | Router terminates TLS, backend HTTP | Simple web apps |
| Re-encrypt | Router terminates and re-encrypts to backend | Stronger internal security |
| Passthrough | App terminates TLS | App requires end-to-end TLS control |

### 13.2 Secure route example

```bash
oc create route edge payments-web \
  --service=payments-web \
  --hostname=payments.apps.example.com \
  -n fin-payments-prod
```

Force insecure traffic policy:

```bash
oc patch route payments-web -n fin-payments-prod \
  --type=merge \
  -p '{"spec":{"tls":{"insecureEdgeTerminationPolicy":"Redirect"}}}'
```

### 13.3 Ingress boundary controls

Use:

- Dedicated ingress controllers for different zones.
- Separate router shards by namespace labels.
- TLS security profiles.
- External WAF/load balancer for internet-facing apps.
- Route admission policy and hostname ownership.
- NetworkPolicy allowing ingress only from router namespace.

Example zone model:

```text
public ingress controller     -> internet-facing apps
internal ingress controller   -> internal apps only
restricted ingress controller -> regulated apps
```

### 13.4 Certificate boundary

Plan certificates for:

- API server.
- Ingress wildcard.
- Custom application routes.
- Internal service certificates.
- LDAP/OIDC trust.
- Registry trust.
- External proxy trust.

Certificate design rules:

- Use enterprise CA where required.
- Avoid wildcard certificates for unrelated trust zones.
- Track expiry with monitoring.
- Automate renewal where possible.
- Keep private keys out of Git.
- Use sealed/encrypted secret management if GitOps stores TLS secret manifests.

## 14. Image and Supply Chain Boundary Design

The image boundary controls what software is allowed to run.

### 14.1 Trusted registry strategy

Enterprise production clusters should not pull arbitrary public images directly.

Recommended:

```text
Developers build images -> CI scans/signs images -> approved registry -> OpenShift pulls by digest
```

Preferred image reference:

```yaml
image: registry.example.com/finance/payments-api@sha256:<digest>
```

Avoid in production:

```yaml
image: nginx:latest
image: docker.io/random/image:latest
```

### 14.2 Image mirror design

For disconnected or controlled environments, use mirror registries and modern OpenShift mirror resources:

- `ImageDigestMirrorSet` for digest-based mirroring.
- `ImageTagMirrorSet` for tag-based mirroring when required.
- Avoid new use of deprecated `ImageContentSourcePolicy` where newer resources are supported.

### 14.3 Image signature and policy

For higher assurance, use image signature verification. This can involve sigstore/cosign, cluster image policy, namespace image policy, and CI/CD signing pipelines depending on platform version and support status.

Design approach:

1. Build image from approved base image.
2. Scan image for vulnerabilities.
3. Sign image after passing checks.
4. Promote image to production registry.
5. Deploy by digest.
6. Enforce admission/pull policy.
7. Audit runtime image drift.

### 14.4 Supply-chain anti-patterns

Avoid:

- Pulling public images directly in production.
- Using mutable tags like `latest`.
- Allowing any namespace to create ImageStreams from untrusted registries.
- Storing registry credentials broadly.
- Running build pods with unnecessary privileged SCC.
- Sharing one pull secret across all teams.

## 15. Operator Boundary Design

Operators often have broad privileges. A poorly governed Operator can become a cluster-wide risk.

### 15.1 Operator installation models

| Model | Boundary | Risk |
|---|---|---:|
| All namespaces | Cluster-wide | High |
| Selected namespaces | Limited tenant scope | Medium |
| Single namespace | Narrowest | Lower |

### 15.2 Operator governance checklist

Before installing an Operator:

- What ClusterRoles does it request?
- Does it need cluster-wide watch permissions?
- Does it create CRDs?
- Does it run privileged pods?
- Does it require hostNetwork, hostPath, or privileged SCC?
- Which namespace owns the Operator?
- Which teams can create CRs consumed by that Operator?
- Can a tenant use a CR to indirectly create privileged workloads?
- Is the Operator certified/supported?
- How is it upgraded and rolled back?

Useful commands:

```bash
oc get csv -A
oc describe csv <csv-name> -n <operator-namespace>
oc get clusterrole,clusterrolebinding | grep -i <operator-name>
oc get scc
oc adm policy who-can use scc/privileged
```

### 15.3 Operator boundary anti-pattern

Bad pattern:

```text
Install every Operator in openshift-operators with AllNamespaces mode.
Allow every project admin to create CRs for that Operator.
Do not review generated RBAC or SCC usage.
```

Better pattern:

```text
Install high-risk Operators in dedicated namespaces.
Limit OperatorGroup scope.
Restrict who can create custom resources.
Review RBAC and SCC before production use.
Manage Operator subscriptions through GitOps.
```

## 16. Quota and Resource Boundary

Resource boundaries are security boundaries too. Without resource quotas, one tenant can create noisy-neighbor incidents or denial of service.

### 16.1 ResourceQuota example

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: finance-prod-quota
  namespace: fin-payments-prod
spec:
  hard:
    pods: "50"
    requests.cpu: "20"
    requests.memory: 80Gi
    limits.cpu: "40"
    limits.memory: 160Gi
    requests.storage: 1Ti
    persistentvolumeclaims: "20"
    services: "20"
    secrets: "100"
    configmaps: "100"
```

### 16.2 LimitRange example

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-container-limits
  namespace: fin-payments-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 256Mi
    default:
      cpu: 500m
      memory: 512Mi
    min:
      cpu: 10m
      memory: 64Mi
    max:
      cpu: "2"
      memory: 4Gi
```

### 16.3 Boundary impact

Quota protects:

- API server from object sprawl.
- Nodes from overcommit abuse.
- Storage from uncontrolled PVC growth.
- Platform services from tenant mistakes.
- Other tenants from noisy workloads.

## 17. Audit, Logging, and Detection Boundary

A boundary that cannot be audited is weak. You need to detect violations and prove compliance.

### 17.1 Audit log focus areas

Monitor:

- `cluster-admin` role binding changes.
- SCC grants.
- Secret reads in production namespaces.
- Creation of privileged pods.
- Changes to NetworkPolicy/AdminNetworkPolicy.
- Namespace label changes.
- Route and Ingress changes.
- Image pull secret changes.
- Operator installation and Subscription changes.
- API access by service accounts outside normal patterns.

### 17.2 Audit profile design

OpenShift provides predefined audit profiles. More detailed profiles can log request bodies but increase overhead and may capture sensitive data. Choose based on compliance and investigation needs.

Recommended enterprise approach:

```text
Default audit profile for standard clusters.
Higher-detail profile only for regulated clusters or temporary investigation.
Forward audit logs to SIEM.
Protect audit logs from tenant modification.
Define retention by compliance requirement.
```

### 17.3 Useful audit/log commands

```bash
# View API server audit logs from nodes
oc adm node-logs --role=master --path=kube-apiserver/
oc adm node-logs --role=master --path=openshift-apiserver/

# Gather audit logs
oc adm must-gather -- /usr/bin/gather_audit_logs

# Check cluster logging resources
oc get clusterlogforwarder -A
oc get clusterlogging -A
```

### 17.4 Security alerts to implement

Alert on:

- Any new binding to `cluster-admin`.
- Any SCC grant to `privileged`, `anyuid`, `hostnetwork`.
- Any pod using privileged security context.
- Any namespace without default deny policy.
- Any production route without TLS.
- Any image from untrusted registry.
- Any production deployment using `:latest` tag.
- Any service account token secret older than allowed period.
- Any user-created workload in system namespace.

### Step 1: Create namespace with labels


```bash
oc label namespace fin-payments-prod \
```

```bash
oc create sa payments-api-sa -n fin-payments-prod

oc create sa payments-cicd-sa -n fin-payments-prod
```

### Step 4: Bind RBAC

```bash
oc adm policy add-role-to-group admin finance-payments-admins -n fin-payments-prod

oc adm policy add-role-to-group view finance-payments-readonly -n fin-payments-prod
```

### Step 5: Apply quota and limits

```bash
oc apply -f quota.yaml
oc apply -f limitrange.yaml
```

### Step 6: Apply network baseline

```bash
oc apply -f default-deny-ingress.yaml
```

## 21. Troubleshooting Security Boundary Issues

### 21.1 Pod rejected by SCC

Symptoms:

```text
Error creating: pods is forbidden: unable to validate against any security context constraint
```

Check:

```bash
oc describe pod <pod> -n <ns>
oc get sa -n <ns>
oc adm policy who-can use scc/anyuid
oc adm policy who-can use scc/privileged
oc get pod <pod> -n <ns> -o yaml | grep -i securityContext -A20
```

Fix approach:

1. First fix the image to run non-root.
2. Add proper `securityContext`.
3. Use named service account.
4. Grant less risky SCC if required.
5. Use `anyuid` only as exception.
6. Use `privileged` only for platform-level components.

### 21.2 NetworkPolicy not working

Common causes:

- Policy created in wrong namespace.
- `podSelector` labels do not match target pods.
- `namespaceSelector` labels do not exist.
- Service selector does not match pod labels.
- Testing from a pod with hostNetwork.
- Forgetting DNS egress.
- Testing route traffic while only allowing pod-to-pod traffic.

Commands:

```bash
oc get pod -n <ns> --show-labels
oc get ns --show-labels
oc get svc,endpoints -n <ns>
oc describe networkpolicy <policy> -n <ns>
oc get networkpolicy -A
```

### 21.3 RBAC permission denied

Symptoms:

```text
Error from server (Forbidden): users "x" cannot create resource "deployments"
```

Check:

```bash
oc auth can-i create deployments.apps -n <ns>
oc auth can-i create deployments.apps --as=<user> -n <ns>
oc get rolebinding -n <ns>
oc describe rolebinding <binding> -n <ns>
oc get clusterrolebinding | grep <user-or-group>
```

### 21.4 Route exposed but app unreachable

Check:

```bash
oc get route -n <ns>
oc describe route <route> -n <ns>
oc get svc,endpoints -n <ns>
oc get pod -n <ns> --show-labels
oc logs deploy/<deployment> -n <ns>
```

Boundary-related causes:

- NetworkPolicy blocks router namespace.
- Service has no endpoints.
- TLS mode mismatch.
- Application listens on different port.
- Route hostname/DNS incorrect.

### 21.5 Secret access concern

Check:

```bash
oc adm policy who-can get secrets -n <ns>
oc adm policy who-can list secrets -n <ns>
oc get rolebinding -n <ns>
oc get clusterrolebinding | grep -i secret
```

Reduce access:

- Replace broad `edit` with custom roles.
- Remove unnecessary service account permissions.
- Use external secret operator / vault integration.
- Enable etcd encryption.

## 24. Common Interview / Design Discussion Points

### Q1. Is a namespace a security boundary?

A namespace is a logical boundary and an RBAC scope, but not a complete hard security boundary. It must be combined with NetworkPolicy, SCC/Pod Security Admission, quotas, service account isolation, and governance. For strong isolation, use dedicated nodes or separate clusters.

### Q2. How do you isolate two tenants in the same cluster?

Use separate namespaces, group-based RBAC, default deny NetworkPolicy, AdminNetworkPolicy for non-overridable platform controls, quotas, LimitRanges, restricted SCCs, service account isolation, trusted registry policy, and audit monitoring. For sensitive tenants, add dedicated node pools or separate clusters.

### Q3. Why is `anyuid` risky?

`anyuid` allows containers to run with arbitrary UIDs, including root if requested by the image or pod. It weakens OpenShift's default random UID model. Use it only for legacy workloads that cannot run with random non-root UID, and grant it only to a specific service account.

### Q4. Why should default SCCs not be modified?

Default SCCs are managed by the platform and may be reset or recreated during upgrades. Modifying them can break platform behavior or disappear during upgrade. Create custom SCCs only when necessary and manage them carefully.

### Q5. What is the difference between NetworkPolicy and AdminNetworkPolicy?

NetworkPolicy is namespace-scoped and usually controlled by namespace owners. AdminNetworkPolicy is cluster-scoped and designed for administrators to enforce controls that tenant NetworkPolicies cannot override. Use AdminNetworkPolicy for mandatory platform-level network boundaries.

### Q6. How do you prevent data exfiltration from pods?

Use egress default deny, allow only required destinations, route traffic through proxy/egress gateways, use EgressFirewall/EgressIP where appropriate, monitor DNS and outbound traffic, restrict secrets access, and use runtime restrictions to reduce compromise impact.

### Q7. How do you design production and non-production boundaries?

Best design is separate clusters for production and non-production. If sharing a cluster, separate namespaces, node pools, quotas, RBAC, network policies, and image promotion paths. Production should have stricter RBAC, no developer edit access unless approved, stronger audit, and trusted images only.

## 26. Real-World Design Anti-Patterns

### Anti-pattern 1: “One big production namespace”

Problem:

```text
All production apps run in namespace prod.
```

Impact:

- RBAC cannot separate apps well.
- NetworkPolicy becomes messy.
- Secret exposure risk increases.
- Quota cannot isolate teams.
- Troubleshooting blast radius is large.

Better:

```text
<tenant>-<app>-prod per application or bounded application group
```

### Anti-pattern 2: “Developers are project admins in prod”

Impact:

- Developers may change role bindings.
- They may weaken network policies.
- They may expose routes.
- They may create risky workloads.

Better:

```text
Developers: view in prod
CI/CD: controlled deployment role
App owners: limited admin through approval
Platform: cluster controls
```

### Anti-pattern 3: “Anyuid for namespace default service account”

Bad:

```bash
oc adm policy add-scc-to-user anyuid -z default -n app-prod
```

Better:

```bash
oc create sa legacy-sa -n app-prod
oc adm policy add-scc-to-user anyuid -z legacy-sa -n app-prod
oc set serviceaccount deployment/legacy legacy-sa -n app-prod
```

### Anti-pattern 4: “NetworkPolicy after incident only”

Network boundaries must be part of namespace onboarding. Retrofitting after many applications are deployed is harder and riskier.

### Anti-pattern 5: “Everything installed in openshift-operators”

Some Operators need cluster-wide scope, but many do not. Review OperatorGroup and CSV permissions before installing.

## 28. Final Architecture Recommendation

For enterprise OpenShift security boundary design, use this target model:

```text
1. Separate clusters for materially different risk zones.
2. Separate namespaces for every tenant/app/environment.
3. Group-based RBAC through enterprise IdP.
4. Named service accounts for workloads and automation.
5. Restricted SCC by default; special SCCs only by exception.
6. Default deny NetworkPolicy in production namespaces.
7. AdminNetworkPolicy for mandatory cluster-wide network controls.
8. Dedicated node pools for regulated, privileged, GPU, and infra workloads.
9. Etcd encryption and strict secret RBAC.
10. Trusted registry, image scanning, digest deploys, and signing where supported.
11. Audit logs forwarded to SIEM with alerts for risky changes.
12. All namespace baselines managed through GitOps.
```

A mature OpenShift platform does not depend on one security control. It layers many controls so that if one boundary fails, the next boundary limits the damage.
