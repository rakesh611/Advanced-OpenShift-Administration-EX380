# Cluster Backup Strategy in Enterprise Architecture

**Topic:** Cluster backup strategy  
**Track:** Advanced OpenShift Administration / Enterprise Architecture  
**Audience:** Senior Linux, Kubernetes, OpenShift, Platform, SRE, and DevOps engineers  
**Experience level:** 10+ years  
**Last updated:** 2026-07-03

---

## 1. Executive Summary

A strong OpenShift cluster backup strategy is not only an `etcd snapshot` script. In enterprise architecture, backup is a **business continuity capability** that protects the platform control plane, application definitions, persistent data, identity configuration, certificates, GitOps source of truth, registry images, operator state, and recovery procedures.

In OpenShift, the most important principle is:

> **Do not treat the OpenShift cluster as one single backup object. Split the backup design by recovery domain.**

A production-grade strategy normally has these layers:

| Layer | What it protects | Recommended method | Recovery use case |
|---|---|---|---|
| Platform source of truth | Install config, manifests, MachineConfigs, policies, Argo CD apps, Helm values, Kustomize overlays | Git / GitOps / IaC | Rebuild cluster or re-apply configuration |
| Control plane state | Kubernetes/OpenShift API objects stored in etcd | OpenShift etcd backup | Quorum loss, critical cluster state corruption |
| Application metadata | Namespaces, Deployments, Routes, Services, ConfigMaps, Secrets, RBAC, custom resources | OADP / Velero | Application restore, migration, namespace-level recovery |
| Persistent data | PV/PVC data, databases, file stores, VM disks | CSI snapshots, OADP file-system backup, storage-native backup, database-native backup | Stateful workload recovery |
| Images | Internal registry images, application images, disconnected release payloads | OADP internal image backup, registry replication, mirror registry | App redeployment after registry loss |
| Hub/fleet metadata | RHACM managed clusters, policies, applications | ACM backup and restore operator + OADP | Hub cluster disaster recovery |
| Observability/audit evidence | Metrics, logs, audit logs, must-gather, incident evidence | External logging/metrics platforms, object archive | RCA, compliance, forensic recovery |
| Recovery automation | Runbooks, scripts, credentials, DNS procedures, load balancer steps | Git, vault, password manager, offline docs | Faster RTO during crisis |

A senior OpenShift administrator must understand the difference between **availability**, **backup**, **restore**, and **disaster recovery**:

- **Availability** keeps the service running during component failure.
- **Backup** captures a recoverable copy of state.
- **Restore** brings data or configuration back from backup.
- **Disaster recovery** restores business service after a major failure, usually across clusters or sites.

## 2. Why Cluster Backup Strategy Matters in Enterprise Architecture

In a small lab, you might only run:

```bash
/usr/local/bin/cluster-backup.sh /home/core/assets/backup
```

In an enterprise, that is not enough. You must answer architecture-level questions:

- What is the business RPO and RTO?
- What must be recovered first: platform, application, database, identity, or external connectivity?
- Can the cluster be rebuilt from Git?
- Are backups stored outside the failed cluster?
- Are backups encrypted?
- Who can restore?
- Has the restore been tested?
- Does the backup cover PV data or only Kubernetes objects?
- Are Operator-managed resources safe to restore directly?
- What happens if the internal image registry is lost?
- What happens if the RHACM hub cluster is lost?
- What happens if certificates, OAuth, LDAP/OIDC trust, or ingress certificates are corrupted?
- What happens during ransomware or insider deletion?

Enterprise-grade backup is designed around **failure scenarios**, not around tools.

## 3. Recovery Objectives: RPO, RTO, MTD, and Recovery Tiering

### 3.1 RPO - Recovery Point Objective

**RPO** defines how much data loss the business can tolerate.

Examples:

| Workload type | Example RPO | Reason |
|---|---:|---|
| Stateless web frontend | 24 hours or Git-only | Can be redeployed from Git/image registry |
| Internal admin tool | 4-12 hours | Low transaction volume |
| Business API | 1 hour | Config and recent app state matter |
| Database-backed application | 5-15 minutes | Transaction loss is expensive |
| Banking/payment workload | Near-zero | Requires synchronous/near-sync replication |
| RHACM hub policies | 1-4 hours | Managed clusters keep running, but governance/update control is affected |

### 3.2 RTO - Recovery Time Objective

**RTO** defines how quickly service must be restored.

Examples:

| Recovery scenario | Example RTO | Strategy |
|---|---:|---|
| Deleted Deployment | 5-15 minutes | GitOps sync or `oc apply` |
| Deleted namespace | 30-60 minutes | OADP restore + GitOps reconciliation |
| PV corruption | 30 minutes to several hours | Storage snapshot or app-native restore |
| Control plane quorum loss | Several hours | etcd restore runbook |
| Full cluster loss | 4-24 hours | Rebuild cluster + GitOps + OADP/app restore |
| Region loss | Minutes to hours | Multi-cluster DR, DNS failover, storage replication |

### 3.3 MTD - Maximum Tolerable Downtime

**MTD** is the maximum downtime before business damage becomes unacceptable. RTO must be lower than MTD.

Example:

```text
MTD = 8 hours
Target RTO = 4 hours
Target RPO = 1 hour
Backup frequency = hourly for app data, daily for etcd, before/after upgrades
Restore drill frequency = quarterly
```

## 4. OpenShift Backup Domains

OpenShift has multiple backup domains. Each domain needs a different recovery approach.

### 4.1 Control Plane Domain

The control plane includes:

- API server
- Controller manager
- Scheduler
- etcd
- OpenShift Operators
- OAuth
- ClusterVersion and ClusterOperators
- Static pod resources
- Certificate material used by control plane components

The key backup artifact is the **etcd snapshot plus static pod resources**.

This is used for severe cluster-state failures, such as:

- Loss of etcd quorum
- Accidental deletion of critical cluster objects
- Severe control plane state corruption

It should **not** be your normal method for restoring one namespace or one application.

### 4.2 Application Definition Domain

This includes:

- Namespaces/projects
- Deployments, StatefulSets, DaemonSets
- Services, Routes, Ingress objects
- ConfigMaps and Secrets
- RBAC RoleBindings
- ServiceAccounts
- NetworkPolicies
- ResourceQuotas and LimitRanges
- Operator custom resources
- Helm releases
- Argo CD Application resources

Best protection methods:

- GitOps as primary source of truth
- OADP/Velero for namespace and resource backup
- Exported manifests for emergency reference

### 4.3 Persistent Data Domain

This includes:

- PersistentVolumes
- PersistentVolumeClaims
- Database storage
- File storage
- Object data
- VM disks if OpenShift Virtualization is used

Protection methods:

- CSI VolumeSnapshots
- OADP snapshots
- OADP file-system backup using Restic/Kopia, depending on OADP version/configuration
- Storage-native snapshots and replication
- Database-native dumps, PITR, WAL/binlog archiving
- Application-consistent backup hooks

### 4.4 Identity and Trust Domain

This includes:

- OAuth configuration
- HTPasswd, LDAP, OIDC, GitHub, GitLab identity provider config
- LDAP/OIDC CA trust bundles
- API certificates
- Ingress certificates
- Custom route certificates
- Pull secrets
- ServiceAccount token behavior
- Kubeconfig/admin credentials
- External IdP dependency documentation

Protection methods:

- GitOps for declarative OAuth and certificate trust configuration
- External secret manager or sealed/encrypted secrets
- OADP backup for secrets where allowed
- Vault/password-manager escrow for break-glass credentials
- Offline copy of recovery kubeconfig and install metadata

### 4.5 Image and Registry Domain

This includes:

- Internal image registry content
- Build output images
- ImageStreams
- Release payload mirror for disconnected clusters
- Operator catalog mirror
- Helm chart repository mirror

Protection methods:

- Registry replication
- Quay/Harbor/Artifactory backup
- OpenShift internal image backup through OADP where supported
- `oc-mirror` for disconnected release/operator content
- External CI image promotion policy

### 4.6 Hub / Multi-Cluster Domain

In RHACM-based architecture, the hub cluster stores fleet-level state:

- ManagedCluster objects
- Placement resources
- Policies
- Governance configuration
- ApplicationSets/Argo CD integration
- Cluster lifecycle metadata

Managed clusters may continue to run if the hub fails, but governance, upgrades, policy-based alerting, and fleet management are impacted. RHACM provides a cluster backup and restore operator that depends on OADP/Velero to back up and restore hub cluster resources.

## 5. Reference Enterprise Backup Architecture

### 5.1 Logical Architecture

```text
                         +-----------------------------+
                         | Enterprise Git / IaC Repos  |
                         | - install-config            |
                         | - MachineConfig             |
                         | - Argo CD Apps              |
                         | - Policies                  |
                         +--------------+--------------+
                                        |
                                        v
+------------------+        +--------------------------+        +----------------------+
| Admin / CI/CD    | -----> | OpenShift Cluster        | -----> | External Observability|
| pipelines        |        |                          |        | logs / metrics / SIEM |
+------------------+        |  Control Plane / etcd    |        +----------------------+
                            |  Apps / Operators        |
                            |  PVs / Registry          |
                            +------------+-------------+
                                         |
                                         v
                            +--------------------------+
                            | Backup Control Plane     |
                            | - etcd backup job/script |
                            | - OADP / Velero          |
                            | - Storage snapshots      |
                            +------------+-------------+
                                         |
          +------------------------------+------------------------------+
          |                              |                              |
          v                              v                              v
+------------------+          +------------------+           +------------------+
| Object Storage   |          | Storage Snapshot |           | Offsite Archive  |
| S3 / ODF MCG     |          | CSI / array      |           | immutable copy   |
+------------------+          +------------------+           +------------------+
```

### 5.2 Architecture Rule

A cluster backup strategy should follow the **3-2-1-1-0** principle:

| Principle | Meaning in OpenShift |
|---|---|
| 3 copies | Running data + local backup + remote/offsite backup |
| 2 media/types | Object storage plus storage snapshots or external archive |
| 1 offsite | Backup stored outside the production cluster and failure domain |
| 1 immutable/offline | Object lock, WORM, air-gapped, or restricted archive |
| 0 restore errors | Regular validation and restore drills |

## 6. etcd Backup Strategy

### 6.1 What etcd Contains

`etcd` is the key-value store that persists OpenShift/Kubernetes resource object state.

It contains cluster state such as:

- Namespaces
- API objects
- Secrets
- ConfigMaps
- RBAC
- Routes and Services
- Custom resources
- Operator-managed state
- Cluster configuration resources

It does **not** contain the actual bytes inside persistent volumes. For example, a MySQL PVC data directory is not inside etcd; only the Kubernetes metadata about the PVC/PV is inside etcd.

### 6.2 What an etcd Backup Is For

Use an etcd backup for:

- etcd quorum loss
- severe cluster state corruption
- critical platform object deletion where normal API-based recovery is not possible
- disaster recovery of the control plane state

Do not use etcd restore for:

- Normal application rollback
- One Deployment restore
- One ConfigMap restore
- One PVC restore
- Routine namespace migration
- Restoring data from a database

For those cases, use GitOps, OADP, storage snapshot, or application-native restore.

### 6.3 Important etcd Rules

Critical production rules:

1. Take backup regularly.
2. Store backup outside the OpenShift cluster.
3. Do not run backup from every control-plane node.
4. Run backup from **one** control-plane node only.
5. Take backup before cluster upgrades.
6. The backup used for restore must match the same OpenShift z-stream version.
7. Do not take an etcd backup before the first certificate rotation completes after installation.
8. Schedule backup during non-peak hours because the snapshot has high I/O cost.
9. Protect the static pod resources archive carefully, especially when etcd encryption is enabled.

### 6.4 Manual etcd Backup Runbook

Get control-plane nodes:

```bash
oc get nodes -l node-role.kubernetes.io/master=
oc get nodes -l node-role.kubernetes.io/control-plane=
```

Start a root debug session on one control-plane node:

```bash
oc debug --as-root node/<control-plane-node-name>
```

Inside the debug shell:

```bash
chroot /host
mkdir -p /home/core/assets/backup
/usr/local/bin/cluster-backup.sh /home/core/assets/backup
```

Expected artifacts:

```text
snapshot_<timestamp>.db
static_kuberesources_<timestamp>.tar.gz
```

Copy backup to a safe location:

```bash
scp core@<control-plane-node>:/home/core/assets/backup/* ./backup-$(date +%F)/
```

Or from inside the node, push to external object storage using your enterprise-approved method.

### 6.5 Verify etcd Backup Artifacts

Minimum checks:

```bash
ls -lh /home/core/assets/backup
sha256sum /home/core/assets/backup/* > /home/core/assets/backup/SHA256SUMS
```

Check that both files exist:

```bash
ls -1 /home/core/assets/backup | grep snapshot_
ls -1 /home/core/assets/backup | grep static_kuberesources_
```

Do not mark a backup as valid only because the command exited successfully. Enterprise backup validation should include:

- File presence
- Size sanity check
- Checksum generation
- Copy success to external location
- Encryption status
- Restore drill result
- Backup age alerting

### 6.6 etcd Backup Frequency

Recommended enterprise baseline:

| Cluster type | etcd backup frequency |
|---|---|
| Lab/dev | Daily or before risky changes |
| Non-prod shared platform | Daily + before upgrades |
| Production | Daily + before upgrades + before high-risk changes |
| Highly regulated production | Daily or more frequent, plus immutable offsite copy |
| After fresh install | After first certificate rotation period, then baseline backup |

Important: Increasing etcd backup frequency does not replace application-data backup. If a database changes every minute, daily etcd backup will not protect database contents.

### 6.7 etcd Restore Decision Logic

Use this decision tree:

```text
Can the Kubernetes API server return data?
        |
        +-- Yes --> etcd exists. Avoid etcd restore.
        |          Use GitOps, OADP, oc apply, or application restore.
        |
        +-- No --> Is etcd quorum lost or cluster state severely broken?
                   |
                   +-- Yes --> Consider etcd restore as last resort.
                   |
                   +-- No  --> Troubleshoot API/control plane first.
```

If a majority of control-plane/etcd members still exist and quorum is available, prefer replacing the unhealthy member instead of restoring the whole cluster state.

### 6.8 Why etcd Restore Is Dangerous

etcd restore takes the cluster state back to an older point in time. This can create conflict between:

- API state in etcd
- Actual files on control-plane disks
- Running pods on nodes
- PVs and storage backend state
- Operators reconciling newer real-world state against older API state

Potential effects:

- Operator churn
- Stuck control-plane Operators
- PV tracking mismatch
- Deleted workloads reappearing or current workloads disappearing
- Machine reimaging or unexpected machine reconciliation
- Certificate bundle rollback
- Inconsistent application state

Therefore, etcd restore is a **last-resort platform recovery operation**, not a normal rollback tool.

## 7. OADP / Velero Application Backup Strategy

### 7.1 What OADP Protects

OpenShift API for Data Protection, based on Velero, is used for application backup and restore. It can protect:

- Kubernetes resources
- Namespace-scoped application resources
- Internal images
- Persistent volumes through snapshots or file-system backup
- Restore operations through Restore custom resources
- Scheduled backup operations
- Backup/restore hooks

### 7.2 OADP Architecture

```text
+-----------------------------+
| DataProtectionApplication   |
| - backup location           |
| - snapshot location         |
| - Velero configuration      |
| - plugins                   |
+---------------+-------------+
                |
                v
+-----------------------------+
| Velero controller           |
| Backup / Restore / Schedule |
+---------------+-------------+
                |
     +----------+----------+
     |                     |
     v                     v
+------------+       +----------------+
| Object     |       | CSI / Storage  |
| storage    |       | snapshots      |
+------------+       +----------------+
```

### 7.3 OADP Requirements

Typical requirements:

- `cluster-admin` access
- OADP Operator installed
- `DataProtectionApplication` ready
- Object storage for backup metadata and resource archives
- Snapshot-capable storage or file-system backup for PV data
- Correct cloud/S3 credentials
- Network access from cluster to object storage
- Restore-tested namespace/application plan

### 7.4 Backup CR Example

Backup a namespace named `payments-prod`:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-prod-backup-20260703
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payments-prod
  storageLocation: default
  ttl: 720h0m0s
```

Apply:

```bash
oc apply -f backup-payments-prod.yaml
oc get backups.velero.io -n openshift-adp
oc describe backup payments-prod-backup-20260703 -n openshift-adp
```

### 7.5 Restore CR Example

Restore from a backup:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: payments-prod-restore-20260703
  namespace: openshift-adp
spec:
  backupName: payments-prod-backup-20260703
  includedNamespaces:
    - payments-prod
  restorePVs: true
```

Apply:

```bash
oc apply -f restore-payments-prod.yaml
oc get restores.velero.io -n openshift-adp
oc describe restore payments-prod-restore-20260703 -n openshift-adp
```

### 7.6 Schedule CR Example

Daily scheduled backup:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: payments-prod-daily
  namespace: openshift-adp
spec:
  schedule: "0 2 * * *"
  template:
    includedNamespaces:
      - payments-prod
    storageLocation: default
    ttl: 168h0m0s
```

Apply:

```bash
oc apply -f schedule-payments-prod-daily.yaml
oc get schedules.velero.io -n openshift-adp
```

### 7.7 Backup by Labels

A good enterprise pattern is to label critical namespaces and use labels for backup selection.

Example namespace labels:

```bash
oc label namespace payments-prod backup-tier=gold app-owner=payments --overwrite
oc label namespace hr-prod backup-tier=silver app-owner=hr --overwrite
```

Gold backup schedule:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: gold-namespaces-hourly
  namespace: openshift-adp
spec:
  schedule: "0 * * * *"
  template:
    labelSelector:
      matchLabels:
        backup-tier: gold
    storageLocation: default
    ttl: 168h0m0s
```

### 7.8 What to Exclude

Do not blindly back up and restore everything.

Common exclusions:

- Events
- Pods recreated by controllers
- Nodes
- Machine objects, unless intentionally planned
- Some Operator installation resources
- Temporary resources
- Backup/Restore CRs themselves
- Resources recreated by owner resources
- Cluster-scoped resources that belong to another cluster identity

Example:

```yaml
spec:
  excludedResources:
    - events
    - events.events.k8s.io
    - pods
    - replicasets.apps
    - backups.velero.io
    - restores.velero.io
```

Important: Exclusion policy must be tested per application and per Operator. Operator-managed workloads require special care because some custom resources are declarative source-of-truth while other generated objects should not be restored directly.

## 8. Stateful Application Backup Strategy

### 8.1 Why Stateful Apps Need Special Handling

Kubernetes resource backup is not enough for stateful apps. For example:

```text
Deployment + Service + Route + Secret = app definition
PVC data = actual business data
Database transaction logs = consistency and point-in-time recovery
```

If you restore only the YAML objects, the application might start with an empty or inconsistent volume.

### 8.2 Crash-Consistent vs Application-Consistent Backup

| Backup type | Meaning | Risk |
|---|---|---|
| Crash-consistent | Snapshot taken while app is running | Similar to sudden power loss; database may need recovery |
| Application-consistent | App is quiesced/flushed before snapshot | Safer for databases and critical file systems |
| Transaction-consistent | Database backup captures a valid transaction boundary | Best for databases |
| Point-in-time recovery | Restore to a specific time using logs | Best for high-value systems |

### 8.3 Application-Consistent Patterns

For databases:

- Use database-native backup first.
- Use storage snapshots as secondary fast restore.
- Use OADP hooks to quiesce or flush data where supported.
- Use WAL/binlog/archive logs for point-in-time recovery.
- Validate restore into a test namespace.

Examples:

| Database | Preferred backup pattern |
|---|---|
| PostgreSQL | `pg_dump`, base backup, WAL archive, operator-native backup |
| MySQL/MariaDB | `mysqldump`, Percona XtraBackup, binlog archive |
| MongoDB | `mongodump`, Ops Manager/Cloud Manager, volume snapshot with fsync lock where appropriate |
| Elasticsearch/OpenSearch | Repository snapshot API |
| Redis | RDB/AOF backup plus storage snapshot |

### 8.4 Backup Hooks Example Concept

Backup hooks can run commands before or after backup.

Conceptual example:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: mysql-backup-with-hook
  namespace: openshift-adp
spec:
  includedNamespaces:
    - mysql-prod
  hooks:
    resources:
      - name: mysql-flush
        includedNamespaces:
          - mysql-prod
        labelSelector:
          matchLabels:
            app: mysql
        pre:
          - exec:
              container: mysql
              command:
                - /bin/sh
                - -c
                - "mysqladmin flush-tables --user=root --password=$MYSQL_ROOT_PASSWORD"
              onError: Fail
              timeout: 30s
```

This is only an example. In production, use an application-supported backup method and test consistency.

## 9. GitOps-Driven Backup and Recovery

A mature OpenShift architecture treats Git as the first recovery mechanism for configuration.

### 9.1 What Should Be in Git

Store declarative configuration such as:

- Namespace definitions
- RBAC
- Quotas and LimitRanges
- NetworkPolicies
- SCC bindings where acceptable
- Operator subscriptions
- Operator custom resources
- IngressController configuration
- OAuth configuration references
- MachineConfigs
- NTP/Chrony configuration
- Proxy, image registry, image content source policy / IDMS/ITMS
- Argo CD Applications/ApplicationSets
- Helm values
- Kustomize overlays
- PolicyGenerator resources for ACM governance

### 9.2 What Should Not Be Plaintext in Git

Do not store raw sensitive data in plaintext:

- Passwords
- Private keys
- Pull secrets
- Database credentials
- OAuth client secrets
- TLS private keys
- LDAP bind passwords

Use one of:

- External Secrets Operator
- Vault
- Sealed Secrets
- SOPS with KMS/HSM
- Cloud secret manager
- GitOps secret plugin with strong access controls

### 9.3 GitOps Recovery Flow

```text
1. Rebuild or repair cluster
2. Install base operators
3. Restore secret management integration
4. Install Argo CD / OpenShift GitOps
5. Sync platform configuration
6. Sync application definitions
7. Restore PV/application data from OADP/storage/app backup
8. Validate routes, DNS, certificates, and application health
```

### 9.4 Golden Rule

If a resource is important and declarative, it should be recoverable from Git.

If a resource contains changing runtime state, it needs backup.

If a resource contains business transactions, it needs application-aware backup.

## 10. Multi-Cluster and RHACM Backup Strategy

### 10.1 Why Hub Backup Matters

In a multi-cluster architecture, Red Hat Advanced Cluster Management often manages:

- Cluster lifecycle
- Policies
- Governance
- Application placement
- Fleet observability
- Upgrade orchestration

If the hub cluster fails, managed clusters can keep running, but centralized operations are degraded.

### 10.2 RHACM Hub Backup Architecture

```text
+-------------------+         +-------------------+
| Active ACM Hub    | ----->  | Backup Storage    |
| cluster-backup    |         | OADP / Velero     |
+---------+---------+         +---------+---------+
          |                             |
          | disaster                    | restore
          v                             v
+-------------------+         +-------------------+
| Managed clusters  |         | Passive/New Hub   |
| continue running  | <-----  | restored metadata |
+-------------------+         +-------------------+
```

### 10.3 ACM Backup Scope

ACM backup and restore focuses on hub resources such as:

- Managed clusters
- Applications
- Policies
- Selected custom resources
- Hub configuration needed for fleet management

It does not replace application data backup inside each managed cluster.

### 10.4 Active/Passive Hub Pattern

Enterprise pattern:

1. Active hub manages clusters.
2. Backup schedule continuously stores hub resources to object storage.
3. Passive/new hub is prepared with same operator stack and namespaces.
4. During disaster, restore hub resources to passive/new hub.
5. Reconnect/import managed clusters where required.
6. Validate policies, placements, and applications.

## 11. Storage and ODF Disaster Recovery Strategy

### 11.1 Storage DR Options

| Option | Suitable for | Notes |
|---|---|---|
| Local CSI snapshot | Fast rollback in same cluster/site | Not enough for site failure |
| OADP + object store | Namespace/application recovery | Must include PV strategy |
| Storage array replication | Enterprise storage platforms | Needs OpenShift integration testing |
| ODF Metro-DR | Low-latency two-site DR | Uses RHACM/ODF/Ceph components |
| ODF Regional-DR | Regional failover | Depends on supported platform and design |
| Database replication | Critical databases | Often best RPO/RTO for transactional systems |

### 11.2 Metro-DR vs Regional-DR

| Pattern | Design idea | Use case |
|---|---|---|
| Metro-DR | Two OpenShift clusters across nearby sites with replicated storage and RHACM/ODF orchestration | Low RTO/RPO across metro distance |
| Regional-DR | Two clusters across farther sites/regions with asynchronous replication | Region-level disaster recovery |

### 11.3 Backup vs Replication

Replication is not backup.

If an admin deletes data and deletion is replicated, the remote side also loses the data. For ransomware or logical corruption, you still need immutable backup or point-in-time restore.

## 12. Security Architecture for Backups

### 12.1 Backup Data Classification

Backups may contain:

- Secrets
- Tokens
- TLS private keys
- OAuth credentials
- LDAP bind passwords
- Database credentials
- Business data
- Internal image content
- Cluster topology
- Namespace names and object names

Treat backup storage as highly sensitive.

### 12.2 Security Controls

| Control | Recommendation |
|---|---|
| Encryption in transit | TLS for S3/object storage and storage API |
| Encryption at rest | Object storage encryption/KMS, storage encryption |
| Key management | KMS/HSM, strict rotation, limited key access |
| RBAC | Only platform backup operators and break-glass admins can restore |
| Immutable backups | Object lock/WORM/versioning where supported |
| Offsite copy | Store outside production cluster and primary failure domain |
| Network policy | Restrict backup controller egress to backup endpoints |
| Audit logging | Log backup and restore operations |
| Secret separation | Store static kube resources archive separately when required |
| Restore approval | Production restore should require change/incident approval |

### 12.3 etcd Encryption Consideration

When etcd encryption is enabled, static Kubernetes resources generated by the backup contain material required for restore. The static resource archive should be protected separately from the snapshot when policy requires stronger separation.

Also remember: etcd encryption encrypts values, not all metadata. Resource type names, namespaces, and object names can still reveal sensitive information.

## 13. Backup Scheduling and Retention Design

### 13.1 Example Enterprise Schedule

| Backup type | Frequency | Retention | Storage target |
|---|---:|---:|---|
| etcd backup | Daily + before upgrades | 7-30 days | External secure object/archive |
| Gold app OADP backup | Hourly or every 4 hours | 7-30 days | Object storage + PV snapshot |
| Silver app OADP backup | Daily | 14-30 days | Object storage |
| Bronze app backup | Weekly or Git-only | 30 days | Git/OADP as needed |
| Database-native backup | App-specific, often 5-60 minutes | 7-90 days | DB backup repository |
| Registry backup | Daily or replication-based | 30+ days | Registry backend backup |
| ACM hub backup | Hourly/daily depending fleet criticality | 7-30 days | Object storage |
| Must-gather archive | Before/after major incidents/upgrades | Per policy | Support archive/SIEM/object storage |

### 13.2 Backup Windows

Schedule backup windows based on:

- Application transaction patterns
- etcd I/O impact
- Storage snapshot load
- Object storage bandwidth
- Database maintenance window
- Batch jobs
- RPO requirements

Avoid scheduling all cluster backups at exactly the same time.

### 13.3 Retention Considerations

Long retention is not always better. Consider:

- Compliance requirement
- Storage cost
- Data privacy requirements
- Secret rotation impact
- Right-to-delete requirements
- Backup encryption key lifetime
- Restore compatibility across OpenShift versions

## 14. Validation and Restore Testing

### 14.1 Backup Without Restore Test Is Not a Backup

A backup is only useful if it can be restored.

Validation levels:

| Level | Test |
|---|---|
| Level 1 | Backup object exists and status is completed |
| Level 2 | Backup artifact copied to remote storage with checksum |
| Level 3 | Namespace restored into test namespace |
| Level 4 | Application passes functional health checks after restore |
| Level 5 | Full cluster rebuild + app restore drill |
| Level 6 | Site failover/failback exercise |

### 14.2 Restore Drill Checklist

For each critical application:

```text
[ ] Identify RPO/RTO
[ ] Confirm backup schedule
[ ] Confirm backup includes resources and PV data
[ ] Restore to isolated namespace
[ ] Patch routes/hostnames to avoid production collision
[ ] Validate pods, services, routes, PVCs
[ ] Run application smoke tests
[ ] Validate database consistency
[ ] Validate logs and metrics
[ ] Document restore time
[ ] Record gaps and remediation actions
```

### 14.3 etcd Restore Drill

Do not casually perform etcd restore on production.

Recommended approach:

- Practice in a non-production cluster.
- Use same OpenShift version behavior as production.
- Keep SSH access to all control-plane nodes before starting.
- Confirm backup includes snapshot and static pod resources.
- Confirm recovery host selection.
- Document expected API outage.
- Validate ClusterOperators after restore.

## 17. Common Mistakes

### Mistake 1: Thinking etcd Backup Protects PV Data

Wrong assumption:

```text
I have etcd backup, so my database data is safe.
```

Correct understanding:

```text
etcd contains PVC/PV metadata, not the database files inside the volume.
```

### Mistake 2: Storing Backup Inside the Same Cluster

If backup is stored only in a PVC inside the same cluster, cluster loss can destroy the backup.

Correct pattern:

```text
Cluster -> object storage outside cluster -> immutable/offsite copy
```

### Mistake 3: No Restore Drill

A green backup status does not guarantee business recovery. Restore drills must validate application functionality.

### Mistake 4: Restoring Operators Blindly

Operator-managed resources can be complex. Some resources are source-of-truth CRs; others are generated. Restoring generated resources can cause conflicts.

### Mistake 5: Same Credentials for Backup and Production Admins

If a compromised admin can delete production and backups, backup is not ransomware-resistant.

### Mistake 6: No Version Awareness

OpenShift etcd restore requires version compatibility. Backups should be taken before upgrades and tracked with cluster version metadata.

### Mistake 7: No DNS / Load Balancer Recovery Plan

Application backup is useless if external users cannot reach the restored app.

## 18. Interview / Real-World Explanation

### Question: What is your OpenShift cluster backup strategy?

Strong answer:

```text
I separate OpenShift backup into control-plane, application, persistent data, image registry, GitOps, and multi-cluster management domains.

For control-plane recovery, I take regular etcd backups from one control-plane node only and store the snapshot and static Kubernetes resources outside the cluster, especially before upgrades. I treat etcd restore as a last resort because it rolls the cluster state back in time and can create inconsistencies with running workloads and PVs.

For applications, I use GitOps as the primary source of truth for manifests and OADP/Velero for namespace-level backup and restore. For PVs, I use CSI snapshots or file-system backup depending on storage support. For databases, I prefer database-native backups and WAL/binlog-based PITR because PV snapshots alone may be only crash-consistent.

For enterprise DR, I define RPO/RTO per workload tier, store backups in secure off-cluster object storage, enable immutability where possible, monitor backup age and failure status, and run restore drills. In multi-cluster environments, I also back up RHACM hub resources and use GitOps/policies to rebuild fleet state.
```

### Question: When would you use etcd restore?

Answer:

```text
Only for severe platform recovery such as etcd quorum loss or critical cluster-state corruption where normal API-based recovery is not possible. If the API server is available and I can retrieve resources, I avoid etcd restore and use GitOps, OADP, or application-level recovery instead.
```

### Question: Does OADP replace database backup?

Answer:

```text
No. OADP can protect Kubernetes resources and PVs using snapshots or file-system backup, but transactional databases often require database-native backup for consistency and point-in-time recovery. For critical databases, I combine OADP metadata backup with database-native backups and storage snapshots.
```

## 20. Enterprise Backup Policy Template

Use this as a starting policy.

```yaml
backupPolicy:
  platform:
    etcd:
      frequency: daily
      additionalTriggers:
        - before-upgrade
        - before-control-plane-change
        - before-certificate-rotation-change
      storage:
        primary: secure-object-storage
        secondary: immutable-offsite-archive
      retention: 30d
      restoreTest: quarterly-nonprod
  applications:
    tiers:
      gold:
        rpo: 1h
        rto: 2h
        oadpSchedule: hourly
        pvProtection: csi-snapshot-or-db-native
        restoreTest: monthly
      silver:
        rpo: 24h
        rto: 8h
        oadpSchedule: daily
        pvProtection: snapshot-or-fs-backup
        restoreTest: quarterly
      bronze:
        rpo: git
        rto: best-effort
        oadpSchedule: weekly
        pvProtection: optional
        restoreTest: semiannual
  security:
    encryptionAtRest: true
    encryptionInTransit: true
    immutableBackup: true
    restoreApprovalRequired: true
    backupAdminGroup: platform-backup-admins
  validation:
    backupStatusMonitoring: true
    rpoBreachAlerting: true
    restoreDrillEvidenceRequired: true
```
