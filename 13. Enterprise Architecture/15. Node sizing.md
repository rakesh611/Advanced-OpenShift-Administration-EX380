## 1. What Node Sizing Means in Enterprise Architecture

**Node sizing** is the process of deciding how much CPU, memory, disk, network bandwidth, and I/O capacity each OpenShift node should have, and how many nodes of each role are required to run the platform and application workloads reliably.

In a basic lab, node sizing usually means:

```text
How many vCPU and how much RAM should I give to a worker node?
```

In enterprise architecture, node sizing means much more:

```text
Can the cluster continue operating during node failure, zone failure, upgrade, workload burst, logging spike, route traffic surge, storage rebuild, and future growth without violating SLOs?
```

A senior OpenShift administrator must size nodes for:

- Control plane stability
- etcd latency and disk I/O
- Worker workload capacity
- Pod density
- CPU overcommitment
- Memory headroom
- System-reserved and kube-reserved resources
- Infra components such as Ingress, Registry, Monitoring, Logging, GitOps, ACM, and Service Mesh
- Storage workloads such as ODF / Ceph
- Upgrade disruption
- Node drain and eviction capacity
- High availability across zones or racks
- Future growth
- Cost control

Good node sizing is not just about making pods run. It is about keeping the cluster predictable under pressure.

---

## 2. Why Node Sizing Is an Architecture Decision, Not Only a Hardware Decision

In OpenShift, a node is not just a server. It is a scheduling unit, failure domain, security boundary, networking participant, storage consumer, and upgrade target.

Wrong node sizing causes many enterprise problems:

| Problem | Typical Root Cause |
|---|---|
| Pods stuck in `Pending` | Insufficient allocatable CPU/memory, taints, affinity, PVC zone mismatch |
| Node `NotReady` | System daemons starved, disk pressure, memory pressure, network instability |
| API slow during deployment waves | Control plane undersized or high object churn |
| etcd alerts | Control plane disk latency or excessive object count |
| Router latency | Infra nodes too small or too few router replicas |
| Prometheus OOMKilled | Monitoring stack memory underestimated |
| Upgrade stuck | Not enough spare capacity for drain and rescheduling |
| Storage degraded | ODF nodes undersized or failure domains not balanced |
| High cloud bill | Oversized nodes without workload utilization governance |

A 10-year experienced admin does not ask only, “How many cores are needed?” The better question is:

```text
What failure, upgrade, scaling, and workload assumptions must this node pool survive?
```

## 3. OpenShift Node Roles and Their Sizing Impact

OpenShift nodes generally fall into these categories.

### 3.1 Control Plane Nodes

Control plane nodes run critical cluster components such as:

- Kubernetes API server
- OpenShift API server
- etcd
- Scheduler
- Controller managers
- Cluster Version Operator
- Authentication/OAuth components
- Machine Config Operator components
- Other platform operators

Control plane nodes are usually **three nodes** in production HA clusters. Their sizing depends on:

- Number of worker nodes
- Number of namespaces/projects
- Number of pods
- Number of services/routes/secrets/config maps
- Number of CRDs and installed Operators
- API request rate
- Object churn rate
- etcd database size and latency
- Upgrade and failover behavior

### 3.2 Worker Nodes

Worker nodes run application workloads. They are sized based on:

- Application pod CPU requests
- Application pod memory requests
- Pod density
- Workload burst behavior
- DaemonSet overhead
- Service mesh sidecars
- Logging agents
- Security agents
- Storage CSI plugins
- Node-exporter and monitoring overhead
- Node drain capacity

### 3.3 Infrastructure Nodes

Infrastructure nodes run OpenShift platform services that should be isolated from application workloads, commonly:

- Ingress routers
- Internal image registry
- Monitoring stack
- Logging stack
- GitOps / Argo CD
- ACM / MCE hub components
- Service Mesh control plane
- Quay, if deployed internally

Infra node sizing is often underestimated because these components look small in a new cluster but grow with routes, metrics, logs, namespaces, pods, and retention.

### 3.4 Storage Nodes

Storage nodes run storage systems such as OpenShift Data Foundation / Ceph. They require sizing for:

- CPU
- Memory
- NVMe/SSD/HDD devices
- Disk count
- Disk latency
- Network throughput
- Failure domains
- Rebuild operations
- Recovery load

Storage nodes should not be treated like normal stateless worker nodes.

### 3.5 Special-Purpose Nodes

Enterprise clusters often have dedicated node pools for:

- GPU workloads
- Low-latency workloads
- Telco / real-time workloads
- Build workloads
- CI/CD runners
- Database workloads
- Edge workloads
- Windows containers
- OpenShift Virtualization

Each special-purpose pool should have its own labels, taints, MachineConfigPool, and capacity model.

## 4. Baseline Minimum Requirements

Red Hat documents minimum installation requirements, but enterprise sizing should not stop at the minimum.

Typical minimum OpenShift 4.21 installation requirements include:

| Machine | OS | vCPU | RAM | Storage | IOPS |
|---|---:|---:|---:|---:|---:|
| Bootstrap | RHCOS | 4 | 16 GB | 100 GB | 300 |
| Control plane | RHCOS | 4 | 16 GB | 100 GB | 300 |
| Compute | RHCOS | 2 | 8 GB | 100 GB | 300 |

These are **minimums to run the cluster**, not recommended enterprise production sizing.

For production, consider them as the floor, not the design target.

A practical enterprise starting point is often closer to:

| Node Type | Small Prod | Medium Prod | Large Prod |
|---|---:|---:|---:|
| Control plane | 8 vCPU / 32 GB | 16 vCPU / 64 GB | 16-24 vCPU / 128 GB |
| Worker | 8 vCPU / 32 GB | 16 vCPU / 64 GB | 32 vCPU / 128 GB |
| Infra | 8 vCPU / 32-48 GB | 16 vCPU / 64-128 GB | 32 vCPU / 128-192 GB |
| ODF storage | 16 vCPU / 64 GB | 16-24 vCPU / 64-128 GB | Based on ODF sizing tool |

These are not universal rules. They are starting profiles that must be validated with workload requests, cluster density, monitoring retention, storage design, and platform version.

## 5. The Core Sizing Model

A mature OpenShift sizing approach uses four layers.

### 5.1 Layer 1: Platform Minimum Capacity

This includes resources consumed by OpenShift itself:

- Kubelet
- CRI-O
- Node OS
- SDN/OVN-Kubernetes components
- DNS
- CSI plugins
- Monitoring agents
- Logging agents
- Security agents
- Machine Config Daemon
- Cluster operators

This is why node **capacity** is not equal to node **allocatable**.

```text
Node Capacity
- System Reserved
- Kube Reserved
- Eviction Thresholds
= Node Allocatable
```

The scheduler uses `node.Status.Allocatable`, not raw capacity.

### 5.2 Layer 2: Workload Requested Capacity

For schedulable workloads:

```text
Total workload CPU request = sum(all pod CPU requests)
Total workload memory request = sum(all pod memory requests)
```

The scheduler places pods based primarily on requests, not limits.

### 5.3 Layer 3: Operational Headroom

Enterprise clusters need headroom for:

- Node failure
- Zone failure
- Rolling updates
- Application rollout surge
- CronJob bursts
- HPA scale-out
- Build workloads
- Temporary troubleshooting pods
- Security scanning
- Log spikes
- Monitoring spikes

A common target is:

```text
Normal steady-state utilization: 50-65%
Warning zone: 65-75%
Risk zone: 75-85%
Emergency zone: >85%
```

For control plane nodes, Red Hat specifically recommends keeping CPU and memory usage at **no more than 60%** of available capacity in large/dense clusters to absorb failover and upgrade spikes.

### 5.4 Layer 4: Growth Buffer

You should size for the next 12-18 months, not just day one.

Growth inputs:

- Number of application teams
- Number of namespaces
- Number of pods per application
- Expected HPA growth
- CI/CD frequency
- Number of routes
- Number of secrets/config maps
- Logging retention
- Monitoring retention
- Future Operators
- Multi-cluster expansion

## 6. Control Plane Node Sizing

Control plane sizing is the most critical part of cluster architecture.

### 6.1 What Control Plane Nodes Actually Handle

Control plane nodes manage cluster state and decisions:

- API authentication and authorization
- Object validation and admission
- etcd persistence
- Scheduling decisions
- Controller reconciliation
- Operator reconciliation
- Cluster version upgrades
- Node lifecycle
- Machine API lifecycle
- Network operator state
- Storage operator state

In enterprise clusters, the control plane becomes stressed not only by pod count but also by **object count and churn**.

High churn examples:

- CI/CD pipelines creating many short-lived pods
- CronJobs running frequently
- HPA scaling frequently
- Operators constantly reconciling
- Logging/monitoring objects growing
- GitOps repeatedly applying resources
- Large number of namespaces
- Large number of secrets/config maps
- Many CRDs

### 6.2 Why etcd Matters

etcd stores the cluster state. It is latency sensitive and disk-I/O sensitive.

Control plane node sizing must include:

- Fast persistent disk
- Low latency
- Stable IOPS
- No noisy-neighbor storage
- Reliable network among control plane nodes
- Sufficient CPU for API and etcd processing
- Sufficient memory for API caches and operators

On cloud platforms, avoid burst-only disk behavior for etcd. Use predictable IOPS. In Red Hat scale testing on AWS, control plane/etcd used gp3 disks with baseline performance because etcd is latency sensitive.

### 6.3 Control Plane Sizing Guideline

Red Hat control-plane sizing guidance depends on compute node count and cluster-density testing. A simplified view from OpenShift 4.21 guidance is:

| Compute Nodes | Cluster Density / Namespaces | Control Plane CPU | Control Plane Memory |
|---:|---:|---:|---:|
| 24 | 500 | 4 cores | 16 GB |
| 120 | 1000 | 8 cores | 32 GB |
| 252 | 4000 | 16 cores, or 24 with OVN-Kubernetes | 64 GB, or 128 GB with OVN-Kubernetes |
| 501 | 4000 | 16 cores | 96 GB |

This table must be interpreted carefully:

- It is based on specific test methodology.
- Object counts matter.
- Namespace count matters.
- Operators matter.
- OVN-Kubernetes can change control plane sizing needs.
- Rapid object creation uses more control-plane resources than stable running workloads.

### 6.4 OLM and Namespace Count

Operator Lifecycle Manager runs on control plane nodes. Its memory footprint increases with namespace count and number of user-installed Operators.

Approximate OLM memory behavior from Red Hat cluster maximum testing:

| Namespaces | OLM Idle Memory | OLM Memory with 5 User Operators |
|---:|---:|---:|
| 500 | 0.823 GB | 1.7 GB |
| 1000 | 1.2 GB | 2.5 GB |
| 2000 | 2.0 GB | 4.4 GB |
| 4000 | 3.8 GB | 7.6 GB |
| 8000 | 6.9 GB | 14.8 GB |
| 10000 | 9.9 GB | 21.6 GB |

Architecture lesson:

```text
Large number of namespaces + many Operators = control plane memory pressure.
```

### 6.5 Control Plane Utilization Target

For production:

```text
Control plane steady-state CPU <= 60%
Control plane steady-state memory <= 60%
```

Reason: during failure or upgrade, one control plane node may be unavailable and the remaining nodes must absorb load.

### 6.6 Control Plane Anti-Patterns

Avoid:

- Running user workloads on control plane nodes in production
- Using slow disks for etcd
- Sharing etcd disk with noisy workloads
- Undersizing for namespace count
- Ignoring API request rate
- Ignoring Operator count
- Installing many Operators globally without governance
- Allowing uncontrolled CI/CD churn
- Treating 4 vCPU / 16 GB as a production standard

### 6.7 Control Plane Sizing Checklist

Before sizing, collect:

```text
Expected worker node count
Expected namespace count
Expected pod count
Expected routes/services/secrets/configmaps
Expected CRD count
Expected installed Operators
Expected API request rate
Expected rollout frequency
Expected CI/CD job rate
Expected upgrade window
Expected availability target
Platform: bare metal / vSphere / AWS / Azure / GCP / OpenStack
Network plugin: OVN-Kubernetes
Storage backend for etcd
```

## 7. Worker Node Sizing

Worker sizing is workload sizing plus platform overhead plus failure headroom.

### 7.1 Worker Node Sizing Inputs

For each workload type:

- Pod replica count
- CPU request
- CPU limit
- Memory request
- Memory limit
- Ephemeral storage request/limit
- PVC requirements
- Network throughput
- Sidecars
- Init containers
- Startup spikes
- JVM heap behavior
- HPA max replicas
- PDB requirements
- Anti-affinity requirements

### 7.2 Worker Allocatable Calculation

Example:

```text
Node capacity: 16 vCPU, 64 GiB RAM
System reserved: 1 vCPU, 4 GiB RAM
Eviction reserve: 1 GiB RAM
DaemonSet overhead: 1 vCPU, 3 GiB RAM
Operational headroom: 25%
```

Effective schedulable target:

```text
CPU allocatable target = (16 - 1 - 1) * 0.75 = 10.5 vCPU
Memory allocatable target = (64 - 4 - 1 - 3) * 0.75 = 42 GiB
```

The node may show more allocatable than this, but enterprise design should not plan to consume everything.

### 7.3 Worker Node Profile Examples

| Profile | Example Size | Best For | Risk |
|---|---:|---|---|
| Small | 4-8 vCPU / 16-32 GB | Dev/test, small apps | More nodes, more overhead |
| Medium | 16 vCPU / 64 GB | General enterprise apps | Balanced choice |
| Large | 32 vCPU / 128 GB | Dense workloads, fewer nodes | Bigger failure blast radius |
| Memory optimized | 16-32 vCPU / 128-256 GB | JVM, analytics, cache | Cost and NUMA concerns |
| CPU optimized | 32-64 vCPU / 64-128 GB | Compute services, build farms | Memory may become limiter |
| Storage optimized | 16-32 vCPU / 64-128 GB + NVMe | ODF, logs, databases | Needs storage-specific tuning |

### 7.4 Worker Sizing Best Practice

For general enterprise application nodes:

```text
Prefer medium-size nodes first.
Use separate node pools for special workloads.
Avoid mixing very different workload profiles on one pool.
```

Good default starting pool:

```text
16 vCPU / 64 GB RAM / 120-250 GB root disk
```

For memory-heavy Java workloads:

```text
16 vCPU / 128 GB RAM
```

For build-heavy workloads:

```text
32 vCPU / 64-128 GB RAM / larger ephemeral storage
```

For database/stateful workloads:

```text
Dedicated pool, storage-aware scheduling, strong CPU/memory reservations, low overcommitment
```

## 8. Infrastructure Node Sizing

Infra nodes are commonly used for:

- Ingress routers
- Registry
- Monitoring
- Logging
- GitOps
- ACM/MCE
- Service Mesh control plane

### 8.1 Why Infra Nodes Need Dedicated Capacity

If infra components run on the same workers as user applications, application spikes can impact platform services.

Examples:

- Application logs spike → logging collector and Loki/Elastic pressure
- Many routes → router memory/CPU pressure
- Many pods → Prometheus time-series growth
- Many namespaces → increased monitoring cardinality
- Registry usage → disk and network pressure

### 8.2 Red Hat Infra Node Sizing Guidance

OpenShift 4.21 infrastructure node sizing guidance is based on cluster-density testing where Monitoring and default Ingress were moved to infra nodes.

Simplified guidance:

| Worker Nodes | Cluster Density / Namespaces | Infra Node CPU | Infra Node Memory |
|---:|---:|---:|---:|
| 27 | 500 | 4 cores | 24 GB |
| 120 | 1000 | 8 cores | 48 GB |
| 252 | 4000 | 16 cores | 128 GB |
| 501 | 4000 | 32 cores | 128 GB |

Red Hat generally recommends **three infrastructure nodes per cluster**.

### 8.3 Practical Infra Node Starting Point

For enterprise production:

```text
Minimum practical infra pool: 3 nodes
Small: 8 vCPU / 32-48 GB
Medium: 16 vCPU / 64-128 GB
Large: 32 vCPU / 128-192 GB
```

### 8.4 Components That Influence Infra Sizing

| Component | Sizing Driver |
|---|---|
| Ingress router | Routes, TLS, request rate, connection count, payload size |
| Monitoring | Nodes, pods, metrics cardinality, scrape interval, retention |
| Registry | Image size, pull frequency, build frequency, storage backend |
| Logging | Log rate, retention, parsing, indexing, number of tenants |
| GitOps | App count, sync frequency, repo size, cluster count |
| ACM/MCE | Managed cluster count, policies, observability, search |
| Service Mesh | Mesh size, sidecar count, telemetry volume |

### 8.5 Infra Node Taints and Placement

Typical pattern:

```bash
oc label node <node> node-role.kubernetes.io/infra=
oc adm taint nodes <node> node-role.kubernetes.io/infra=:NoSchedule
```

Then configure platform components to tolerate infra taints and select infra nodes.

## 9. Storage Node Sizing

Storage nodes require separate thinking because they are both compute and storage infrastructure.

### 9.1 ODF / Ceph Resource Requirements

Red Hat OpenShift Data Foundation services have explicit aggregate resource requirements. For ODF 4.21, internal mode base services require approximately:

```text
30 logical CPU
72 GiB memory
3 storage devices
```

Additional device sets require more resources.

A three-node ODF design often starts from:

```text
Per storage node: about 10 CPU and 24 GiB memory for ODF services only
```

But this excludes:

- OpenShift system overhead
- Other workloads
- Monitoring/logging overhead
- Failure headroom
- Recovery/rebalance operations

A safer enterprise storage-node profile is commonly:

```text
16 vCPU / 64 GB RAM minimum per ODF node
NVMe/SSD preferred for performance-sensitive workloads
Separate OS disk and storage disks
At least 3 failure domains
```

### 9.2 Storage Node Design Rules

Use storage-specific node pools when possible:

```text
node-role.kubernetes.io/infra-storage
cluster.ocs.openshift.io/openshift-storage=
```

Key rules:

- Use at least three storage nodes for HA.
- Spread storage nodes across zones/racks.
- Keep disk types consistent within device sets.
- Do not mix slow and fast disks in the same performance tier.
- Avoid high CPU overcommitment.
- Plan for rebuild traffic.
- Plan network throughput for replication.
- Keep capacity below alert thresholds.

### 9.3 Storage Failure Headroom

When one storage node fails, remaining nodes must:

- Continue serving I/O
- Rebalance/recover data
- Handle application traffic
- Maintain quorum

Therefore storage nodes must not run at high steady-state utilization.

Practical target:

```text
Storage node steady CPU: < 60-65%
Storage node memory: < 70%
Storage capacity: act before 75%, urgent before 85%
```

## 10. Pod Density and `maxPods`

Pod density means how many pods are placed on each node.

### 10.1 Default `maxPods`

In OpenShift 4.21, the documented default maximum number of pods per node is **250**. The actual number of pods that fit depends on CPU, memory, storage, application behavior, networking, and platform overhead.

Formula:

```text
required pods per cluster / pods per node = total nodes needed
```

Example:

```text
2200 required pods / 110 pods per node = 20 worker nodes
```

### 10.2 Do Not Size by Pod Count Alone

This is wrong:

```text
250 pods per node means I can run 250 production pods on every worker.
```

Better:

```text
Pod count is one limit. CPU, memory, ephemeral storage, network, process count, and API churn are usually reached earlier.
```

### 10.3 High Pod Density Risks

High pod density increases:

- Kubelet load
- CRI-O load
- Node network rules
- DNS traffic
- Log volume
- Metrics cardinality
- API updates
- Eviction complexity
- Drain time
- Failure blast radius

### 10.4 When to Change `maxPods`

Change `maxPods` only when:

- You understand pod resource profiles
- Nodes have enough CPU and memory
- Network CIDR/hostPrefix supports the target density
- API server and kubelet QPS are considered
- Logging/monitoring overhead is tested
- Drain time is acceptable

Example KubeletConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: set-worker-maxpods
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: worker-maxpods
  kubeletConfig:
    maxPods: 500
    kubeAPIQPS: 100
    kubeAPIBurst: 200
```

Label the MachineConfigPool:

```bash
oc label machineconfigpool worker custom-kubelet=worker-maxpods
oc create -f set-worker-maxpods.yaml
```

Important: KubeletConfig changes trigger Machine Config Operator rollout and node reboots.

## 11. CPU Sizing

### 11.1 CPU Requests vs Limits

CPU request is used for scheduling. CPU limit controls maximum CPU usage.

Example:

```yaml
resources:
  requests:
    cpu: 500m
  limits:
    cpu: "1"
```

Meaning:

- Scheduler reserves 0.5 CPU.
- Container can burst up to 1 CPU.
- If CPU is saturated, throttling can occur.

### 11.2 CPU Overcommitment

CPU can usually be overcommitted because workloads may not use their full CPU simultaneously.

Common enterprise CPU overcommit ranges:

| Workload Type | CPU Overcommit Guidance |
|---|---:|
| Stateless web apps | 1.5x - 3x possible |
| APIs/microservices | 1.5x - 2x common |
| JVM apps | 1.2x - 1.8x cautious |
| Databases | Avoid or minimal |
| Build workloads | Low to moderate |
| Real-time/telco | Avoid |
| Storage nodes | Avoid aggressive overcommit |

### 11.3 CPU Sizing Formula

```text
Required worker CPU = sum(pod CPU requests) + DaemonSet CPU + system reserve + headroom
```

With overcommit:

```text
Physical CPU required = Required requested CPU / CPU overcommit ratio
```

Example:

```text
Total pod CPU requests: 320 cores
DaemonSet/system overhead: 40 cores
Headroom: 25%
Total logical requirement: (320 + 40) / 0.75 = 480 cores
CPU overcommit ratio: 1.5
Physical allocatable CPU target: 480 / 1.5 = 320 cores
```

### 11.4 CPU Anti-Patterns

Avoid:

- No CPU requests
- Very high CPU limits with tiny requests
- Running all workloads as BestEffort
- Treating CPU limit as capacity plan
- Oversubscribing build nodes heavily
- Ignoring throttling metrics
- Ignoring sidecars

Useful Prometheus queries:

```promql
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m]))
```

```promql
sum by (namespace, pod) (rate(container_cpu_cfs_throttled_seconds_total{container!="",pod!=""}[5m]))
```

## 12. Memory Sizing

Memory is less forgiving than CPU. CPU throttling slows applications. Memory exhaustion kills pods or destabilizes nodes.

### 12.1 Memory Request vs Limit

Memory request is scheduling reservation. Memory limit is hard maximum. If a container exceeds its memory limit, it can be OOMKilled.

### 12.2 Memory Overcommitment

Memory overcommitment must be conservative.

| Workload Type | Memory Overcommit Guidance |
|---|---:|
| Stateless lightweight apps | Moderate |
| JVM apps | Low |
| Databases | Avoid |
| Caches | Avoid |
| Storage nodes | Avoid |
| Real-time workloads | Avoid |
| Build workloads | Depends on build type |

### 12.3 JVM Considerations

Java workloads need special care:

- JVM heap is not total process memory.
- Native memory, metaspace, thread stacks, direct buffers, and sidecars also consume memory.
- If limit equals heap size, OOM risk is high.

Example:

```text
Pod memory limit: 2 GiB
Recommended JVM max heap: ~1.2-1.5 GiB
Remaining: native memory + metaspace + thread stack + sidecar + safety buffer
```

### 12.4 Memory Sizing Formula

```text
Required memory = sum(pod memory requests) + DaemonSet memory + system reserve + eviction buffer + headroom
```

Example:

```text
Application requests: 1,800 GiB
DaemonSets/platform: 120 GiB
System reserve/eviction: 160 GiB
Headroom: 25%
Required total = (1800 + 120 + 160) / 0.75 = 2773 GiB
```

If workers are 64 GiB each and practical target per worker is 42 GiB:

```text
2773 / 42 = 67 worker nodes
```

## 13. Ephemeral Storage and Root Disk Sizing

Ephemeral storage includes:

- Container writable layers
- Logs
- EmptyDir volumes
- Pulled images
- Build temporary data
- Node-level runtime data

### 13.1 Why Root Disk Fills

Common causes:

- Large container logs
- Too many image pulls
- Build workloads
- Image pruning disabled/misconfigured
- Applications writing to container filesystem
- EmptyDir without limits
- Debug pods copying large files
- CrashLoopBackOff generating logs rapidly

### 13.2 Root Disk Starting Points

| Node Type | Root Disk Starting Point |
|---|---:|
| Control plane | 120-220 GB fast disk |
| General worker | 120-250 GB |
| Build worker | 250-500 GB |
| Infra node | 120-250 GB, more if registry/logging local components exist |
| Storage node | Separate OS disk + dedicated storage devices |

### 13.3 Configure Container Log Size

Example KubeletConfig:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-log-size
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: worker-log-size
  kubeletConfig:
    containerLogMaxSize: 50Mi
    containerLogMaxFiles: 5
```

### 13.4 Set Ephemeral Storage Requests and Limits

```yaml
resources:
  requests:
    ephemeral-storage: 1Gi
  limits:
    ephemeral-storage: 5Gi
```

## 14. Network Sizing

Network capacity affects:

- Pod-to-pod traffic
- Ingress traffic
- East-west microservice traffic
- Storage replication
- Image pulls
- Logging traffic
- Monitoring scrape traffic
- API traffic
- Node heartbeats

### 14.1 Network Sizing Inputs

Collect:

```text
Ingress requests per second
Average payload size
Peak payload size
East-west traffic volume
Image pull frequency
Log volume per second
Storage replication traffic
Backup traffic
Zone/rack topology
MTU requirement
Firewall/load balancer throughput
```

### 14.2 Storage Network

For ODF/Ceph, network matters heavily.

Production guidance:

- Prefer 10/25/40/100 GbE depending on workload.
- Avoid sharing saturated application network with storage replication.
- Ensure low latency between failure domains.
- Consider jumbo frames only if end-to-end supported.
- Monitor retransmits and packet drops.

### 14.3 Ingress Network

Router sizing depends on:

- Route count
- TLS termination mode
- Connection count
- Request rate
- Response size
- WebSocket usage
- mTLS or re-encryption

Use multiple router replicas and spread them across infra nodes.

## 15. Sizing for Availability and Failure Scenarios

Enterprise sizing must answer:

```text
What happens when one node fails?
What happens when one zone fails?
What happens during upgrade drain?
What happens during storage rebuild?
```

### 15.1 N+1 Sizing

For a worker pool:

```text
Required capacity must fit after losing one node.
```

If you have 5 workers and each is 60% utilized, losing one worker pushes average utilization to:

```text
(5 * 60%) / 4 = 75%
```

If each is 80% utilized:

```text
(5 * 80%) / 4 = 100%
```

That means no room for rescheduling, rollout, or spikes.

### 15.2 Zone-Aware Sizing

For three zones, plan so workload can survive one-zone loss if required.

If a workload needs 300 pods and must survive one zone failure:

```text
Each remaining two zones must handle all required pods.
Design capacity per zone = total required capacity / 2
```

### 15.3 PodDisruptionBudget Impact

PDBs protect availability, but they can slow drains.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp
```

If replicas are too low or anti-affinity is too strict, node drain can hang.

Sizing must include drain feasibility.

## 16. Sizing for Upgrades and Maintenance

OpenShift upgrades involve:

- Control plane updates
- Operator updates
- Machine Config Pool updates
- Node drains
- Node reboots
- Workload rescheduling

### 16.1 Upgrade Headroom

During worker update:

```text
One or more nodes may be unavailable.
Remaining nodes must absorb evicted pods.
```

For production, keep enough headroom for:

- One worker node unavailable per pool
- One infra node unavailable
- Control plane spike during upgrade
- Application rollout surge

### 16.2 MachineConfigPool Strategy

Separate pools reduce blast radius:

```text
worker-general
worker-build
worker-db
worker-gpu
infra
storage
```

This helps you roll out node-level changes safely.

### 16.3 Check MCP Status

```bash
oc get mcp
oc describe mcp worker
oc get nodes
```

## 17. Small Nodes vs Large Nodes

### 17.1 Small Nodes

Advantages:

- Smaller failure blast radius
- Easier bin-packing for small pods
- More granular scaling
- Faster replacement

Disadvantages:

- More kubelet/node overhead
- More OS overhead
- More objects for control plane
- More nodes to patch
- More DaemonSet overhead

### 17.2 Large Nodes

Advantages:

- Better for large pods
- Less node count overhead
- Fewer machines to manage
- Better for memory-heavy workloads

Disadvantages:

- Bigger failure blast radius
- More pods evicted during drain
- Longer drain times
- More risk if node has hardware issue
- More NUMA considerations

### 17.3 Practical Recommendation

For general-purpose enterprise OpenShift:

```text
Start with medium nodes.
Use dedicated pools for special workloads.
Scale horizontally when workload is broad.
Scale vertically when workload pods are large.
```

## 18. Cloud, VMware, and Bare-Metal Considerations

### 18.1 Cloud

Cloud sizing must include:

- Instance family
- vCPU/memory ratio
- Disk type and IOPS
- Network bandwidth limit
- Availability zones
- API quotas
- Autoscaling limits
- Load balancer limits
- Storage attachment limits

Avoid choosing instance types only by CPU/RAM. Check network and EBS/disk bandwidth.

### 18.2 VMware vSphere

vSphere sizing must include:

- CPU overcommit ratio at hypervisor layer
- Memory reservation policy
- Datastore latency
- vSAN/VMFS performance
- DRS behavior
- Anti-affinity rules for control plane nodes
- VM hardware version
- Network port group design
- Storage policy

Do not heavily overcommit control plane VMs. etcd is sensitive to latency.

### 18.3 Bare Metal

Bare metal sizing must include:

- CPU sockets and NUMA layout
- RAM channels
- Disk controller
- NVMe/SATA/SAS type
- RAID/HBA mode
- NIC bonding
- Firmware consistency
- Out-of-band management
- Rack/failure-domain layout

Bare metal gives predictable performance but requires stronger upfront planning.

## 19. Sizing Formulas

### 19.1 Pods Per Cluster

```text
required pods per cluster / pods per node = total nodes needed
```

### 19.2 Expected Pods Per Node

```text
required pods per cluster / total nodes = expected pods per node
```

### 19.3 CPU Capacity

```text
required CPU = (sum pod CPU requests + daemonset CPU + system CPU) / target utilization
```

### 19.4 Memory Capacity

```text
required memory = (sum pod memory requests + daemonset memory + system memory + eviction buffer) / target utilization
```

### 19.5 Node Count by CPU

```text
nodes by CPU = required CPU / usable CPU per node
```

### 19.6 Node Count by Memory

```text
nodes by memory = required memory / usable memory per node
```

### 19.7 Final Node Count

```text
final nodes = max(nodes by CPU, nodes by memory, nodes by pod density, nodes by failure-domain requirement)
```

### 19.8 N+1 Capacity

```text
required per-node utilization after one node loss = total used capacity / (node count - 1)
```

Keep this below your operational target.

## 20. Enterprise Sizing Examples

### 20.1 Example 1: Medium Enterprise Application Cluster

Assumptions:

```text
Applications: 80
Namespaces: 120
Average replicas per app: 3
Total app pods: 240
Sidecars/agents: 20% overhead
Total expected pods: 300
Average CPU request: 500m
Average memory request: 1 GiB
Target utilization: 65%
Worker profile: 16 vCPU / 64 GiB
Usable target per worker: 10 vCPU / 40 GiB
```

CPU:

```text
300 pods * 0.5 CPU = 150 CPU
150 / 10 usable CPU per node = 15 workers
```

Memory:

```text
300 pods * 1 GiB = 300 GiB
300 / 40 GiB usable memory per node = 8 workers
```

Pod density:

```text
300 pods / 60 pods per node target = 5 workers
```

Final:

```text
15 workers minimum by CPU
Add N+1 and growth: 18-20 workers
```

Suggested architecture:

```text
3 control plane nodes: 16 vCPU / 64 GB
3 infra nodes: 16 vCPU / 64 GB
18-20 worker nodes: 16 vCPU / 64 GB
Optional 3 storage nodes if ODF internal mode is used
```

### 20.2 Example 2: Memory-Heavy Java Platform

Assumptions:

```text
200 Java pods
Each pod request: 1 CPU / 4 GiB RAM
Worker profile: 16 vCPU / 128 GiB
Usable target per worker: 10 CPU / 85 GiB
```

CPU:

```text
200 CPU / 10 = 20 workers
```

Memory:

```text
800 GiB / 85 = 10 workers
```

Final:

```text
20 workers by CPU
Add failure and growth: 24 workers
```

But if Java CPU usage is low and requests are overestimated, tune requests using real metrics before buying hardware.

### 20.3 Example 3: CI/CD Build Node Pool

Build workloads need:

- Higher CPU
- Larger ephemeral storage
- Higher image pull bandwidth
- Cache strategy
- Lower pod density

Suggested pool:

```text
worker-build: 32 vCPU / 128 GB / 500 GB root disk
Taint: workload=build:NoSchedule
```

Use tolerations for build pods.

### 20.4 Example 4: ODF Internal Storage Pool

Suggested starting architecture:

```text
3 storage nodes
Each: 16 vCPU / 64 GB RAM
Separate OS disk
3+ storage devices total, spread across failure domains
10/25 GbE network preferred depending on workload
```

For high-performance workloads:

```text
Use NVMe/SSD
Increase CPU/memory
Validate with ODF sizing tool
Keep storage traffic predictable
```

## 22. Common Sizing Mistakes

### Mistake 1: Using Minimum Requirements as Production Sizing

Minimum requirements are for installation viability, not enterprise workload operation.

### Mistake 2: Ignoring Node Allocatable

Scheduler uses allocatable, not raw capacity.

### Mistake 3: No Resource Requests

Pods without requests make capacity planning unreliable.

### Mistake 4: Oversized Limits and Tiny Requests

This causes noisy-neighbor behavior and unexpected throttling/OOM.

### Mistake 5: No Infra Nodes

Running routers, monitoring, registry, and apps together can cause platform instability under load.

### Mistake 6: Undersizing Control Plane Disk

etcd latency can damage cluster responsiveness.

### Mistake 7: Ignoring Upgrade Capacity

Clusters that run at 85-90% utilization may fail to drain nodes during upgrades.

### Mistake 8: Mixing All Workloads in One Pool

Databases, builds, JVM apps, routers, and storage workloads have different needs.

### Mistake 9: Ignoring Object Count

Control plane load depends on namespaces, services, routes, secrets, config maps, CRDs, and API churn, not only pods.

### Mistake 10: Ignoring Storage Recovery

Storage nodes need spare CPU, memory, disk, and network for recovery events.

## 24. Interview-Level Explanation

If asked in an interview, answer like this:

> Node sizing in OpenShift is not only deciding CPU and RAM per node. I size the cluster by separating control plane, worker, infra, and storage responsibilities. For the control plane, I look at worker count, namespace count, API churn, object count, OLM/Operator footprint, and etcd disk latency. For workers, I calculate total workload requests, DaemonSet overhead, system-reserved resources, pod density, and failure headroom. For infra nodes, I size routers, registry, monitoring, logging, GitOps, and ACM separately because these platform services grow with routes, pods, metrics, and logs. For storage nodes such as ODF, I treat them as a special pool with dedicated CPU, memory, disks, and network throughput. I always plan for node failure, zone failure, upgrade drain, and 12-18 months of growth. I validate sizing using `oc adm top`, node allocatable, Prometheus metrics, API request rate, etcd health, and pod scheduling behavior. A good sizing design keeps control plane usage below safe thresholds, avoids overcommitting memory-sensitive workloads, and uses dedicated node pools for different workload patterns.

## Final Senior Admin Notes

Node sizing should always be treated as a living architecture decision. The first sizing baseline is only the starting point. Real sizing maturity comes from measuring production behavior, tuning requests and limits, separating workload classes, validating failure scenarios, and continuously comparing actual growth against the original assumptions.

A well-sized OpenShift cluster should satisfy these conditions:

```text
The control plane remains stable during failure and upgrade.
Worker nodes have enough allocatable capacity for workload growth.
Infra components are isolated from noisy application workloads.
Storage nodes have enough CPU, memory, disk, and network for recovery.
Pod density does not overload kubelet, network, logging, or monitoring.
The cluster can drain and upgrade without emergency scaling.
Capacity trends are reviewed before users feel performance impact.
```

That is the difference between lab-level sizing and enterprise architecture-level node sizing.
