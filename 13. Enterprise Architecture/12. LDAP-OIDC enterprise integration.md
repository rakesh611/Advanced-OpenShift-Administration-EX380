## 1. Why LDAP/OIDC Integration Matters in Enterprise Architecture

In a lab cluster, you can log in with `kubeadmin` or a local `htpasswd` identity provider. In an enterprise cluster, that is not enough.

A production OpenShift platform must integrate with the company identity system so that users, administrators, auditors, automation teams, and security teams can follow the same enterprise access lifecycle used across the organization.

Enterprise identity integration solves these problems:

- **Centralized login:** Users authenticate with corporate identity, not local cluster passwords.
- **Joiner-mover-leaver control:** When a user joins, changes department, or leaves, access is managed centrally.
- **MFA and conditional access:** OIDC/SAML-based enterprise identity platforms can enforce MFA, device posture, location policy, risk-based access, and session controls.
- **Audit alignment:** Security teams can map OpenShift access to corporate users and groups.
- **RBAC governance:** OpenShift permissions can be assigned to groups instead of individual users.
- **Multi-cluster consistency:** The same enterprise groups can be reused across dev, test, staging, DR, and production clusters.
- **Compliance:** Enterprise access policies can meet audit requirements such as least privilege, traceability, separation of duties, and timely revocation.

For a senior OpenShift administrator, LDAP/OIDC integration is not just a login configuration. It is part of the **enterprise control plane**.

## 2. Authentication vs Authorization in OpenShift

Before designing LDAP/OIDC integration, clearly separate authentication and authorization.

### Authentication

Authentication answers:

> Who are you?

Examples:

- User logs in with LDAP username and password.
- User logs in through OIDC SSO with Microsoft Entra ID, Keycloak, Okta, Ping Identity, GitLab, Google, or Red Hat SSO.
- User gets an OAuth access token from OpenShift.
- OpenShift validates an external OIDC token directly.

OpenShift authentication creates or validates a user identity.

### Authorization

Authorization answers:

> What are you allowed to do?

Examples:

- Can the user create projects?
- Can the user edit deployments in namespace `payments-prod`?
- Can the user view cluster nodes?
- Can the user bind SCCs?
- Can the user manage operators?
- Can the user create NetworkPolicy objects?

Authorization in OpenShift is mainly handled through Kubernetes/OpenShift RBAC:

- `Role`
- `ClusterRole`
- `RoleBinding`
- `ClusterRoleBinding`

### Enterprise architecture rule

Do not confuse login success with access design.

A user can authenticate successfully but still have no useful permission. That is expected and healthy. Authentication only proves identity. RBAC grants capability.

Recommended enterprise flow:

```text
Corporate Identity Source
        |
        |  Authentication
        v
OpenShift User / Identity
        |
        |  Group membership
        v
OpenShift Groups
        |
        |  RoleBinding / ClusterRoleBinding
        v
Actual permissions
```

## 3. OpenShift Identity Architecture Components

### 3.1 Built-in OpenShift OAuth server

OpenShift includes a built-in OAuth server. In the traditional OpenShift authentication model, users authenticate through this OAuth server, and administrators configure identity providers in the cluster-wide `OAuth` custom resource.

Important object:

```bash
oc get oauth cluster -o yaml
```

Example API object:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: enterprise-oidc
    mappingMethod: claim
    type: OpenID
    openID:
      # provider configuration
```

### 3.2 Authentication Operator

The Authentication Operator manages cluster authentication resources. If identity provider configuration is invalid, the authentication cluster operator can become degraded.

Check it with:

```bash
oc get co authentication
oc describe co authentication
```

Also check related operators:

```bash
oc get co oauth-apiserver kube-apiserver console authentication
```

### 3.3 OAuth pods

For the built-in OAuth model, OpenShift runs OAuth components in the `openshift-authentication` namespace.

Useful commands:

```bash
oc get pods -n openshift-authentication
oc get deploy -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift
```

### 3.4 Users

An OpenShift `User` object represents a user known to the cluster.

```bash
oc get users
oc describe user <username>
```

A user might be automatically created on first successful login, depending on the configured `mappingMethod`.

### 3.5 Identities

An `Identity` object represents the identity returned by an identity provider.

```bash
oc get identities
oc describe identity <provider-name>:<provider-user-id>
```

Example identity names:

```text
ldapidp:uid=jdoe,ou=users,dc=example,dc=com
enterprise-oidc:00u123abc456
keycloak-prod:8f12d5c8-9a11-43c4-a1ad-7a1e11a55520
```

### 3.6 UserIdentityMapping

`UserIdentityMapping` links an OpenShift user to an external identity.

```bash
oc get useridentitymapping
oc create useridentitymapping <identity-provider>:<provider-user-id> <openshift-username>
```

This becomes important when using `mappingMethod: lookup`, during migrations, or when merging identities from multiple identity providers.

### 3.7 Groups

OpenShift groups are used heavily in enterprise RBAC.

```bash
oc get groups
oc describe group <group-name>
```

Groups can be:

- Created manually.
- Synced from LDAP.
- Derived from external OIDC claims in some authentication models.
- Managed declaratively by GitOps.

### 3.8 RoleBindings and ClusterRoleBindings

A group has no power until it is bound to a role.

Namespace-level example:

```bash
oc adm policy add-role-to-group edit ocp-dev-payments -n payments-dev
```

Cluster-level example:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
```

## 4. Enterprise Integration Patterns

OpenShift commonly supports three enterprise identity patterns.

### Pattern 1: LDAP/Active Directory through built-in OpenShift OAuth

```text
User / oc / Browser
        |
        v
OpenShift OAuth Server
        |
        | LDAP search + simple bind
        v
LDAP / Active Directory
        |
        v
OpenShift User + Identity
        |
        v
OpenShift RBAC
```

Use this pattern when:

- The enterprise identity source is LDAP or Active Directory.
- OIDC is not available.
- You need simple username/password validation against LDAP.
- MFA and modern conditional access are not mandatory or are handled elsewhere.

Limitations:

- LDAP integration itself is not a modern SSO flow.
- MFA is not natively part of simple LDAP bind.
- Group membership is usually handled separately with LDAP group sync.
- LDAP bind exposes the cluster login flow directly to directory availability and latency.

### Pattern 2: OIDC through built-in OpenShift OAuth

```text
User Browser
    |
    v
OpenShift OAuth Server
    |
    | Authorization Code Flow
    v
OIDC Provider
(Keycloak / Entra ID / Okta / Ping / GitLab / Google / Red Hat SSO)
    |
    v
OpenShift OAuth token
    |
    v
OpenShift API / Console
```

Use this pattern when:

- Enterprise SSO is already based on OIDC.
- You need MFA, SSO, central session policy, and modern access controls.
- You want OpenShift to continue issuing its own OAuth tokens.
- You want to keep the traditional OpenShift OAuth server behavior.

### Pattern 3: Direct external OIDC authentication

```text
User / CLI / Console
        |
        v
External OIDC Provider issues token directly
        |
        v
OpenShift API validates external OIDC token
        |
        v
RBAC based on mapped user/group claims
```

Use this pattern when:

- You want the enterprise OIDC provider to issue the tokens used directly by OpenShift.
- You want consistent token issuer and claim mapping across many clusters.
- You are ready for the operational tradeoffs of bypassing the built-in OAuth server.
- You have mature identity provider operations and rollback planning.

## 5. LDAP Enterprise Integration Deep Dive

### 5.1 What LDAP integration means in OpenShift

LDAP integration allows OpenShift to validate usernames and passwords against an LDAPv3 server using simple bind authentication.

In practical enterprise environments, LDAP usually means one of these:

- Microsoft Active Directory LDAP endpoint.
- Red Hat Directory Server.
- OpenLDAP.
- 389 Directory Server.
- Enterprise identity directory exposed through LDAP.

### 5.2 LDAP login flow

When a user runs:

```bash
oc login -u jdoe
```

or logs in through the OpenShift console, the flow is:

```text
1. User provides username and password.
2. OpenShift OAuth server builds an LDAP search filter.
3. OAuth server searches the LDAP directory.
4. If exactly one LDAP entry matches, OpenShift attempts simple bind using that user's DN and supplied password.
5. If bind succeeds, OpenShift builds an identity from configured LDAP attributes.
6. OpenShift maps that identity to an OpenShift user based on mappingMethod.
7. User receives an OpenShift OAuth token.
8. RBAC decides what the user can do.
```

Important production point:

> LDAP authentication must return exactly one matching LDAP entry. Zero matches fail. Multiple matches fail. This is why your LDAP search base, search attribute, and filter must be carefully designed.

### 5.3 LDAP URL structure

OpenShift uses an RFC 2255 LDAP URL format:

```text
ldap://host:port/basedn?attribute?scope?filter
```

Examples:

```text
ldaps://ldap.example.com:636/ou=users,dc=example,dc=com?sAMAccountName?sub?(objectClass=user)
ldaps://ldap.example.com:636/ou=people,dc=example,dc=com?uid?sub?(enabled=true)
ldaps://ad.example.com:636/dc=example,dc=com?userPrincipalName?sub?(objectClass=person)
```

Components:

| Component | Meaning |
|---|---|
| `ldap` / `ldaps` | Protocol. Use `ldaps` for TLS on 636. |
| `host:port` | LDAP server or load-balanced LDAP VIP. |
| `basedn` | Root DN where OpenShift starts searching. |
| `attribute` | Attribute matched against the supplied username. |
| `scope` | Usually `sub`; searches the base DN subtree. |
| `filter` | LDAP filter to limit eligible accounts. |

If the user enters `jdoe`, and the LDAP URL is:

```text
ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid?sub?(enabled=true)
```

OpenShift effectively builds a search filter like:

```text
(&(enabled=true)(uid=jdoe))
```

### 5.4 Attribute design

A senior admin must design attributes carefully.

Common LDAP attributes:

| Use | LDAP / AD attribute examples | Recommendation |
|---|---|---|
| Identity ID | `dn`, `entryUUID`, `objectGUID`, `uid` | Use a stable unique attribute. |
| Preferred username | `uid`, `sAMAccountName`, `userPrincipalName`, `mail` | Use value users recognize. |
| Email | `mail`, `userPrincipalName` | Prefer `mail`. |
| Display name | `cn`, `displayName` | Prefer human-readable display name. |
| Search username | `uid`, `sAMAccountName`, `userPrincipalName` | Must be unique under search base. |

#### Strong identity choice

For `attributes.id`, choose an attribute that does not change easily.

Good options:

- `dn` in simple environments.
- `entryUUID` in LDAP directories that support it.
- `objectGUID` in Active Directory, but be aware that binary attributes can be hard to inspect and migrate.
- A stable immutable employee identifier, if available.

Risky options:

- `mail` if email addresses change after marriage, department move, or domain migration.
- `cn` if display names are not unique.
- `sAMAccountName` if usernames can be reused after employee exit.

### 5.5 LDAP TLS design

Production LDAP integration should use encrypted transport.

Preferred:

```text
ldaps://ldap.example.com:636/...
```

or LDAP upgraded to TLS when supported.

Avoid:

```yaml
insecure: true
```

Recommended production posture:

```yaml
insecure: false
ca:
  name: ldap-ca
```

The CA bundle must be stored in a ConfigMap in the `openshift-config` namespace with key `ca.crt`.

Example:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=/path/to/enterprise-ldap-ca.pem \
  -n openshift-config
```

### 5.6 LDAP bind account

Many enterprise directories do not allow anonymous search. In that case, OpenShift needs a bind DN and bind password for the search phase.

Example service account:

```text
CN=svc-openshift-ldap,OU=Service Accounts,DC=example,DC=com
```

Rules for this account:

- Read-only only.
- No interactive login.
- Password managed by vault or secret rotation process.
- Allowed to search only required OUs if possible.
- Monitored by security team.
- Password rotation tested before production change.

Create bind password secret:

```bash
oc create secret generic ldap-bind-secret \
  --from-literal=bindPassword='<bind-password>' \
  -n openshift-config
```

The key name must be `bindPassword`.

### 5.7 Sample LDAP identity provider CR

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: enterprise-ldap
    mappingMethod: claim
    type: LDAP
    ldap:
      url: "ldaps://ldap.example.com:636/ou=users,dc=example,dc=com?sAMAccountName?sub?(objectClass=user)"
      bindDN: "CN=svc-openshift-ldap,OU=Service Accounts,DC=example,DC=com"
      bindPassword:
        name: ldap-bind-secret
      ca:
        name: ldap-ca
      insecure: false
      attributes:
        id:
        - dn
        preferredUsername:
        - sAMAccountName
        name:
        - displayName
        - cn
        email:
        - mail
```

Apply:

```bash
oc apply -f oauth-ldap.yaml
```

Validate:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc login -u jdoe
oc whoami
oc get users
oc get identities | grep enterprise-ldap
```

### 5.8 Active Directory example

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: ad-corp
    mappingMethod: claim
    type: LDAP
    ldap:
      url: "ldaps://ad01.corp.example.com:636/dc=corp,dc=example,dc=com?sAMAccountName?sub?(&(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))"
      bindDN: "CN=svc-openshift-ldap,OU=Service Accounts,DC=corp,DC=example,DC=com"
      bindPassword:
        name: ad-bind-secret
      ca:
        name: ad-ca
      insecure: false
      attributes:
        id:
        - dn
        preferredUsername:
        - sAMAccountName
        name:
        - displayName
        email:
        - mail
```

Notes:

- The filter excludes disabled AD accounts using the `userAccountControl` bitwise match.
- Use a load-balanced AD LDAP endpoint where possible.
- Validate LDAP latency from master/control-plane nodes.
- Confirm DNS resolution and CA trust from the cluster.

### 5.9 LDAP mapping methods

OpenShift supports common identity provider `mappingMethod` values.

#### `claim`

Default behavior.

```yaml
mappingMethod: claim
```

Behavior:

- OpenShift provisions a user using the preferred username from the identity provider.
- Login fails if that username is already mapped to a different identity.

Use when:

- You have one identity provider.
- Usernames are unique and stable.
- You are not trying to merge users from multiple identity providers.

#### `lookup`

```yaml
mappingMethod: lookup
```

Behavior:

- OpenShift does not automatically create users or identity mappings.
- Admins must pre-create the user, identity, and mapping.

Use when:

- You want to whitelist specific LDAP users.
- You want strong control over who can log in.
- You are migrating identities carefully.

Example:

```bash
oc create user jdoe
oc create identity enterprise-ldap:uid=jdoe,ou=users,dc=example,dc=com
oc create useridentitymapping enterprise-ldap:uid=jdoe,ou=users,dc=example,dc=com jdoe
```

#### `add`

```yaml
mappingMethod: add
```

Behavior:

- If a user already exists with the preferred username, OpenShift maps the new identity to the existing user.

Use when:

- You are adding a new identity provider that represents the same users.
- You are migrating from `htpasswd` to LDAP or LDAP to OIDC.
- You want to avoid duplicate OpenShift users.

Be careful:

- Wrong use can map unintended identities to existing users.
- Test in non-production before using in production.

## 6. LDAP Group Synchronization Architecture

### 6.1 Why LDAP group sync is separate

LDAP login validates the user. It does not automatically mean all LDAP groups become OpenShift groups.

In most LDAP/AD designs, group synchronization is configured separately using:

```bash
oc adm groups sync
```

This command reads LDAP group/user membership and creates or updates OpenShift `Group` objects.

### 6.2 Group sync flow

```text
LDAP / Active Directory
        |
        | oc adm groups sync
        v
OpenShift Group objects
        |
        | RoleBinding / ClusterRoleBinding
        v
Actual access in namespaces or cluster
```

### 6.3 Supported LDAP group schemas

OpenShift LDAP group sync commonly supports these schema patterns:

1. **RFC 2307**
   - Group entries contain member identifiers.
   - Common in Unix/Linux LDAP environments.

2. **Active Directory**
   - User entries contain `memberOf` attributes.
   - Common in Microsoft AD.

3. **Augmented Active Directory**
   - Uses both group and user queries.
   - Helpful when you need more control over group names and user mapping.

### 6.4 Active Directory group sync example

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ad01.corp.example.com:636
bindDN: "CN=svc-openshift-ldap,OU=Service Accounts,DC=corp,DC=example,DC=com"
bindPassword:
  file: /etc/secrets/bindPassword
ca: /etc/config/ca.crt
insecure: false
activeDirectory:
  usersQuery:
    baseDN: "OU=Users,DC=corp,DC=example,DC=com"
    scope: sub
    derefAliases: never
    filter: "(objectClass=user)"
    pageSize: 0
  userNameAttributes:
  - sAMAccountName
  groupMembershipAttributes:
  - memberOf
```

Dry run:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml
```

Apply changes:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

Synchronize selected groups only:

```bash
cat > whitelist.txt <<'EOF_WHITELIST'
CN=ocp-platform-admins,OU=Groups,DC=corp,DC=example,DC=com
CN=ocp-payments-dev,OU=Groups,DC=corp,DC=example,DC=com
CN=ocp-payments-prod-view,OU=Groups,DC=corp,DC=example,DC=com
EOF_WHITELIST

oc adm groups sync \
  --whitelist=whitelist.txt \
  --sync-config=ldap-sync.yaml \
  --confirm
```

Prune stale groups:

```bash
oc adm prune groups --sync-config=ldap-sync.yaml --confirm
```

### 6.5 Automated LDAP group sync

In production, run LDAP group sync as a controlled CronJob or scheduled automation.

Example strategy:

| Environment | Frequency | Notes |
|---|---:|---|
| Dev | Every 1 hour | Access changes are frequent. |
| Test/UAT | Every 2-4 hours | Balanced sync. |
| Production | Every 15-60 minutes depending on policy | Security may require faster revocation. |
| Restricted clusters | Manual approval + sync | Used for high-security environments. |

Operational model:

```text
1. LDAP group membership changes in AD.
2. Scheduled sync updates OpenShift Group objects.
3. RBAC bindings already reference those group names.
4. Access is granted or removed automatically after sync.
```

### 6.6 Group naming standards

Do not sync every enterprise group. Sync only groups relevant to OpenShift.

Recommended naming convention:

```text
ocp-<scope>-<role>
ocp-<cluster>-<namespace>-<role>
ocp-<business-unit>-<application>-<env>-<role>
```

Examples:

```text
ocp-platform-admins
ocp-cluster-readonly
ocp-payments-dev-edit
ocp-payments-prod-view
ocp-security-auditors
ocp-network-admins
ocp-operators-admins
```

Bad examples:

```text
Domain Users
IT Team
Developers
All Employees
Cloud Users
```

Why bad?

- Too broad.
- Hard to audit.
- Not environment-specific.
- Not aligned to least privilege.
- Risk of accidental cluster-wide access.

## 7. OIDC Enterprise Integration Deep Dive

### 7.1 What OIDC is

OpenID Connect is an identity layer built on OAuth 2.0. It allows a client, such as OpenShift, to verify the identity of a user based on authentication performed by an external authorization server.

In enterprise terms:

```text
OIDC = modern SSO identity protocol
OAuth 2.0 = authorization framework
ID Token = identity proof about the user
Access Token = token used to access a resource
Claims = user attributes inside token/UserInfo response
```

Common OIDC providers:

- Keycloak
- Red Hat Single Sign-On
- Microsoft Entra ID
- Okta
- Ping Identity
- Google
- GitLab
- Active Directory Federation Services

### 7.2 OIDC with built-in OpenShift OAuth

Traditional OIDC integration uses this flow:

```text
1. User opens OpenShift console.
2. OpenShift redirects user to OIDC provider.
3. OIDC provider authenticates user.
4. OIDC provider returns authorization code to OpenShift.
5. OpenShift exchanges code for ID token/access token.
6. OpenShift reads claims from ID token and optional UserInfo endpoint.
7. OpenShift maps external identity to OpenShift user.
8. OpenShift issues its own OAuth token.
9. User accesses OpenShift API/console.
```

Architecture diagram:

```text
+-------------+        +------------------------+        +-------------------+
| User Browser| -----> | OpenShift OAuth Server | -----> | Enterprise OIDC   |
| or oc CLI   | <----- |                        | <----- | Provider          |
+-------------+        +------------------------+        +-------------------+
                              |
                              v
                        OpenShift User
                              |
                              v
                           RBAC
```

### 7.3 OIDC discovery

OpenShift expects the OIDC provider to support OIDC Discovery.

Discovery endpoint pattern:

```text
https://idp.example.com/realms/openshift/.well-known/openid-configuration
```

OpenShift uses discovery to learn:

- Authorization endpoint.
- Token endpoint.
- JWKS URI.
- Supported scopes.
- Issuer metadata.

### 7.4 OIDC claims

Important claims:

| Claim | Meaning | Use in OpenShift |
|---|---|---|
| `sub` | Stable subject identifier | Best identity claim. |
| `preferred_username` | User-friendly login name | Good preferred username. |
| `email` | User email | Useful for email and sometimes username. |
| `name` | Display name | Good display name. |
| `groups` | Group membership | Useful in direct OIDC or external group mapping designs. |
| `aud` | Audience/client ID | Must match expected client. |
| `iss` | Token issuer | Must match configured issuer. |

Enterprise recommendation:

- Use `sub` as the identity claim.
- Use `preferred_username` or `email` as preferred username.
- Do not use mutable display fields as identity.
- Ensure claims are stable across environments.

### 7.5 OIDC client registration

In the identity provider, create an OIDC client/application for OpenShift.

Typical values:

```text
Client ID: openshift-prod
Client type: confidential
Flow: Authorization Code Flow
Redirect URI: https://oauth-openshift.apps.<cluster-domain>/oauth2callback/<provider-name>
Scopes: openid email profile groups
```

Example redirect URI:

```text
https://oauth-openshift.apps.ocp4.example.com/oauth2callback/enterprise-oidc
```

The `<provider-name>` part must match:

```yaml
identityProviders:
- name: enterprise-oidc
```

### 7.6 OIDC client secret

Create the OIDC client secret in `openshift-config`:

```bash
oc create secret generic oidc-client-secret \
  --from-literal=clientSecret='<client-secret>' \
  -n openshift-config
```

The key name must be:

```text
clientSecret
```

### 7.7 OIDC CA bundle

If the OIDC provider uses an internal enterprise CA, provide CA trust:

```bash
oc create configmap oidc-ca \
  --from-file=ca.crt=/path/to/enterprise-oidc-ca.pem \
  -n openshift-config
```

### 7.8 Standard OIDC identity provider CR

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: enterprise-oidc
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift-prod
      clientSecret:
        name: oidc-client-secret
      issuer: https://sso.example.com/realms/openshift
      ca:
        name: oidc-ca
      claims:
        id:
        - sub
        preferredUsername:
        - preferred_username
        - email
        name:
        - name
        email:
        - email
      extraScopes:
      - email
      - profile
```

Apply:

```bash
oc apply -f oauth-oidc.yaml
```

Validate:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift
```

Login validation:

```bash
oc login --token=<token>
oc whoami
oc get users
oc get identities | grep enterprise-oidc
```

### 7.9 OIDC and CLI login

For OIDC with the built-in OpenShift OAuth server, users generally authenticate through a browser and copy a token for CLI access.

Console path:

```text
Help -> Command Line Tools -> Copy Login Command
```

CLI pattern:

```bash
oc login --token=<token> --server=https://api.<cluster-domain>:6443
```

Important point:

> Do not assume `oc login -u username -p password` works with OIDC. Many OIDC providers do not support password grant flows, and modern enterprise SSO commonly disables direct password grants.

### 7.10 Provider-specific notes

#### Keycloak / Red Hat SSO

Good for:

- Internal enterprise SSO.
- User federation from LDAP/AD.
- Fine control over claims and mappers.
- Lab and enterprise training environments.

Design tips:

- Configure a dedicated realm or client for OpenShift.
- Map LDAP groups to OIDC groups if group claims are required.
- Keep `sub` stable.
- Avoid changing realm issuer URL after production go-live.

#### Microsoft Entra ID

Good for:

- Azure-centric enterprises.
- Conditional access.
- MFA.
- Device and location policies.

Design tips:

- Verify issuer format carefully.
- Validate group claim behavior.
- Large group memberships can cause token overage scenarios.
- Plan group mapping carefully if you need group-based RBAC.

#### Okta / Ping Identity

Good for:

- Enterprise SSO with strong policy controls.
- Complex multi-application identity governance.

Design tips:

- Use dedicated app integration for each cluster or cluster group.
- Keep client secrets rotated.
- Confirm redirect URI exactly.
- Confirm required scopes and claim mappings.

#### AD FS

Good for:

- Traditional Microsoft identity environments.

Design tips:

- Avoid unsupported custom claim expectations.
- Test thoroughly before production.
- Prefer modern Entra ID or Keycloak where possible for new platforms.

## 8. Direct External OIDC Authentication

### 8.1 What direct OIDC authentication changes

Direct external OIDC authentication is a newer architecture where OpenShift uses an external OIDC provider directly for tokens instead of relying on the built-in OpenShift OAuth server to issue OpenShift tokens.

Traditional model:

```text
External IdP -> OpenShift OAuth Server -> OpenShift OAuth token -> API
```

Direct OIDC model:

```text
External OIDC Provider -> Token -> OpenShift API validates token directly
```

### 8.2 Why enterprises consider direct OIDC

Direct OIDC can be attractive when:

- The enterprise wants one central token issuer.
- Multiple clusters should validate the same identity provider tokens.
- Identity teams want to manage sessions, lifetimes, MFA, and claims centrally.
- Platform teams want consistency across on-prem, cloud, and hybrid clusters.
- OpenShift authentication should align closely with Kubernetes OIDC-style authentication.

### 8.3 Tradeoffs

Direct OIDC is powerful but has serious operational implications.

Important tradeoffs:

- The built-in OAuth server is bypassed/replaced.
- Only one direct OIDC provider may be configured.
- Existing OAuth-related resources and user/group APIs may not behave the same way.
- Rollback planning is mandatory.
- Long-lived emergency cluster-admin access is mandatory before switching.
- Existing automation that depends on OpenShift OAuth tokens may need redesign.

### 8.4 Example direct OIDC authentication CR

The exact fields should be validated against your OpenShift version, but the architecture looks like this:

```yaml
apiVersion: config.openshift.io/v1
kind: Authentication
metadata:
  name: cluster
spec:
  type: OIDC
  oidcProviders:
  - name: enterprise-direct-oidc
    issuer:
      issuerURL: https://sso.example.com/realms/openshift
      audiences:
      - openshift-cli
      - openshift-console
      certificateAuthority:
        name: oidc-ca
    claimMappings:
      username:
        claim: preferred_username
        prefixPolicy: Prefix
        prefix:
          prefixString: "oidc:"
      groups:
        claim: groups
        prefix: "oidc:"
      uid:
        claim: sub
    oidcClients:
    - clientID: openshift-cli
      clientSecret:
        name: openshift-cli-secret
      componentName: cli
    - clientID: openshift-console
      clientSecret:
        name: openshift-console-secret
      componentName: console
```

### 8.5 Direct OIDC design checklist

Before enabling direct OIDC:

- Export current OAuth config.
- Export users, groups, identities, OAuth clients, and related RBAC.
- Prepare a certificate-based admin kubeconfig.
- Verify OIDC issuer URL.
- Verify JWKS and CA trust.
- Confirm required audiences.
- Confirm username claim.
- Confirm group claim.
- Confirm token lifetime and refresh behavior.
- Test CLI login.
- Test console login.
- Test admin RBAC.
- Test namespace RBAC.
- Test emergency rollback.

Backup commands:

```bash
mkdir -p auth-backup
oc get oauth cluster -o yaml > auth-backup/oauth-cluster.yaml
oc get authentication.config.openshift.io cluster -o yaml > auth-backup/authentication-cluster.yaml
oc get users -o yaml > auth-backup/users.yaml
oc get groups -o yaml > auth-backup/groups.yaml
oc get identities -o yaml > auth-backup/identities.yaml
oc get useridentitymappings -o yaml > auth-backup/useridentitymappings.yaml
oc get clusterrolebindings -o yaml > auth-backup/clusterrolebindings.yaml
oc get rolebindings -A -o yaml > auth-backup/rolebindings-all-ns.yaml
```

## 9. LDAP vs OIDC vs Direct OIDC Decision Matrix

| Requirement | LDAP via OpenShift OAuth | OIDC via OpenShift OAuth | Direct external OIDC |
|---|---|---|---|
| Basic AD username/password login | Good | Depends on upstream IdP | Not primary use case |
| Modern SSO | Weak | Strong | Strong |
| MFA / conditional access | Weak unless external controls exist | Strong | Strong |
| Uses built-in OpenShift OAuth server | Yes | Yes | No / replaced |
| Operational simplicity | Medium | Medium | Advanced |
| Group sync | Usually LDAP sync job | Claims or external process depending design | Claim mapping from token |
| Multiple IdPs | Possible | Possible | Limited to one direct provider |
| Good for legacy enterprise AD | Good | Good if AD is federated to OIDC | Good if IdP supports required claims |
| Good for multi-cluster SSO | Moderate | Strong | Strongest if standardized |
| Risk of lockout during change | Medium | Medium | High without planning |
| Recommended for new enterprises | Only when OIDC unavailable | Yes | Yes for mature teams |

Senior recommendation:

```text
If the enterprise has a modern IdP, prefer OIDC.
If the enterprise has only AD/LDAP, LDAP works but design group sync and TLS carefully.
If the enterprise operates many clusters and wants centralized token governance, evaluate direct OIDC after proper testing.
```

## 10. Enterprise RBAC Design

### 10.1 RBAC should bind groups, not users

Bad:

```bash
oc adm policy add-cluster-role-to-user cluster-admin jdoe
```

Better:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
```

Why?

- Easier offboarding.
- Easier audit.
- Better separation of duties.
- Works across many clusters.
- No need to change OpenShift RBAC for every user change.

### 10.2 Recommended enterprise groups

| Group | Purpose | Binding |
|---|---|---|
| `ocp-platform-admins` | Full cluster administration | `cluster-admin` |
| `ocp-cluster-readonly` | Cluster-wide read-only access | `cluster-reader` or custom read-only role |
| `ocp-security-auditors` | Audit and compliance review | Custom read-only + audit permissions |
| `ocp-network-admins` | NetworkPolicy, ingress, egress controls | Custom cluster/namespace roles |
| `ocp-operators-admins` | Operator lifecycle management | Custom role or admin in operator namespaces |
| `ocp-<app>-dev-edit` | Developer edit access to dev namespace | `edit` in namespace |
| `ocp-<app>-prod-view` | Production read-only access | `view` in namespace |
| `ocp-<app>-prod-admin` | Production support admin | Custom role, avoid broad cluster-admin |

### 10.3 Example namespace RBAC

```bash
oc new-project payments-dev
oc new-project payments-prod

oc adm policy add-role-to-group edit ocp-payments-dev-edit -n payments-dev
oc adm policy add-role-to-group view ocp-payments-prod-view -n payments-prod
oc adm policy add-role-to-group admin ocp-payments-prod-admin -n payments-prod
```

### 10.4 Example cluster-level RBAC

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
oc adm policy add-cluster-role-to-group cluster-reader ocp-cluster-readonly
```

### 10.5 Test RBAC

Use impersonation:

```bash
oc auth can-i create pods -n payments-dev --as=jdoe
oc auth can-i delete projects --as=jdoe
oc auth can-i get nodes --as=jdoe
oc auth can-i '*' '*' --as=jdoe
```

Use group impersonation:

```bash
oc auth can-i create deployments -n payments-dev --as=someuser --as-group=ocp-payments-dev-edit
```

## 11. Security Hardening

### 11.1 Remove `kubeadmin` only after enterprise admin access works

After configuring a real identity provider and assigning cluster-admin to an enterprise admin group, remove `kubeadmin`:

```bash
oc delete secret kubeadmin -n kube-system
```

Do not remove it before another cluster-admin path is verified.

Validation first:

```bash
oc login --token=<enterprise-admin-token>
oc whoami
oc auth can-i '*' '*'
oc get nodes
oc get co
```

### 11.2 Use break-glass access

Production clusters need emergency access that does not depend on the enterprise IdP being online.

Options:

- Certificate-based admin kubeconfig from installation.
- Long-lived service account token kubeconfig where policy allows.
- Securely stored emergency admin credentials.

Rules:

- Store in enterprise vault.
- Require approval workflow.
- Monitor access.
- Rotate regularly.
- Test during DR exercises.

### 11.3 Protect secrets

Identity integration secrets include:

- LDAP bind password.
- OIDC client secret.
- CA bundles.
- OAuth backup exports.

Best practices:

- Store source-of-truth secrets in vault.
- Use GitOps with sealed secrets or external secrets, not plaintext.
- Rotate secrets regularly.
- Audit who can read secrets in `openshift-config`.
- Never paste secrets in ticket comments, chat, screenshots, or public repos.

### 11.4 Use TLS everywhere

For LDAP:

```yaml
insecure: false
url: "ldaps://ldap.example.com:636/..."
```

For OIDC:

```yaml
issuer: https://sso.example.com/realms/openshift
ca:
  name: oidc-ca
```

Avoid HTTP issuer URLs and insecure LDAP.

### 11.5 Least privilege

Avoid giving broad cluster-admin to general IT groups.

Bad:

```text
Domain Admins -> cluster-admin
All Developers -> edit on all namespaces
```

Good:

```text
ocp-platform-admins -> cluster-admin
ocp-security-auditors -> read-only audit role
ocp-payments-dev-edit -> edit only in payments-dev
ocp-payments-prod-view -> view only in payments-prod
```

### 11.6 Session and token governance

Review:

```bash
oc get oauthaccesstokens
oc get oauthauthorizetokens
```

Operational considerations:

- Token lifetime.
- IdP session lifetime.
- Logout behavior.
- Revocation behavior.
- Browser session cache.
- CLI token management.
- Handling compromised accounts.

### 11.7 Audit logging

For security investigations, correlate:

- OpenShift audit logs.
- IdP login logs.
- LDAP bind logs.
- Group sync job logs.
- RBAC change history.
- GitOps commit history.
- Vault secret access logs.

Example audit questions:

```text
Who granted cluster-admin?
When did user jdoe first log in?
Which groups was jdoe in at the time?
Was the access from LDAP sync or OIDC claim?
Did the user use console or CLI?
Which namespace actions were performed?
```

## 12. Multi-Cluster and Hybrid Enterprise Design

### 12.1 Standardize identity provider names

Use the same identity provider name across clusters where possible.

Example:

```yaml
name: enterprise-oidc
```

Avoid:

```yaml
name: oidc1
name: test-login
name: myidp
```

Why?

- Easier troubleshooting.
- Consistent identity names.
- Easier GitOps templates.
- Easier audit reporting.

### 12.2 Standardize group names

Use global enterprise group names that map clearly to environment and role.

Example:

```text
ocp-prod-platform-admins
ocp-nonprod-platform-admins
ocp-payments-prod-view
ocp-payments-prod-admin
ocp-payments-dev-edit
```

### 12.3 Use GitOps for identity configuration

Recommended GitOps repositories:

```text
platform-config/
  clusters/
    prod-ocp01/
      oauth.yaml
      rbac.yaml
      ldap-group-sync.yaml
    nonprod-ocp01/
      oauth.yaml
      rbac.yaml
  base/
    rbac/
    oauth/
    group-sync/
```

Do not store raw secrets in Git.

Use:

- External Secrets Operator.
- Sealed Secrets.
- Vault integration.
- SOPS where approved.

### 12.4 Hub-spoke architecture

In an Advanced Cluster Management or GitOps-driven architecture:

```text
Enterprise IdP
      |
      +--> Hub cluster
      |       |
      |       +--> GitOps/ACM policy pushes auth/RBAC config
      |
      +--> Spoke cluster 1
      +--> Spoke cluster 2
      +--> Spoke cluster 3
```

Use policies to enforce:

- OAuth/OIDC configuration.
- Required RBAC groups.
- No local insecure IdPs in production.
- `kubeadmin` removed after bootstrap.
- Break-glass access present.
- Audit logging enabled.

### 12.5 DR architecture

Identity is a DR dependency.

Questions to answer:

- Can users log in if primary IdP is unavailable?
- Is the OIDC issuer reachable from DR cluster?
- Is LDAP reachable from DR site?
- Are CA bundles replicated?
- Are client secrets available in DR vault?
- Does DNS fail over correctly?
- Are group sync jobs running in DR?
- Is break-glass access tested?

## 14. Troubleshooting Guide

### 14.1 Authentication operator degraded

Commands:

```bash
oc get co authentication
oc describe co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift
```

Common causes:

- Invalid OAuth CR syntax.
- Secret missing or wrong key name.
- ConfigMap missing `ca.crt` key.
- Invalid issuer URL.
- LDAP URL syntax error.
- LDAP CA trust failure.
- OIDC discovery endpoint unreachable.
- OIDC client secret wrong.

### 14.2 LDAP login fails

Symptoms:

```text
Login failed
Invalid credentials
OAuth server logs show LDAP search or bind errors
```

Checks:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift | grep -i ldap
oc get secret ldap-bind-secret -n openshift-config -o yaml
oc get configmap ldap-ca -n openshift-config -o yaml
oc get oauth cluster -o yaml
```

Root causes and fixes:

| Symptom | Likely cause | Fix |
|---|---|---|
| Zero LDAP entries found | Wrong base DN, attribute, or filter | Test with `ldapsearch`; correct URL. |
| Multiple LDAP entries found | Non-unique search attribute | Use unique attribute or narrower base DN. |
| Bind failed | Wrong password or disabled user | Validate user credentials. |
| Search bind failed | Wrong bindDN/bindPassword | Fix service account secret. |
| TLS error | Missing CA or wrong cert chain | Update CA ConfigMap. |
| Timeout | Firewall/DNS/routing issue | Validate from cluster network. |

### 14.3 OIDC login fails

Common symptoms:

```text
invalid_client
invalid_redirect_uri
issuer mismatch
audience mismatch
claim not found
x509 certificate signed by unknown authority
```

Troubleshooting commands:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift | grep -i oidc
oc get oauth cluster -o yaml
oc get secret oidc-client-secret -n openshift-config -o yaml
oc get configmap oidc-ca -n openshift-config -o yaml
curl -vk https://sso.example.com/realms/openshift/.well-known/openid-configuration
```

Root causes and fixes:

| Error | Likely cause | Fix |
|---|---|---|
| `invalid_client` | Wrong client ID or secret | Recreate secret and confirm IdP app. |
| `invalid_redirect_uri` | Redirect URI mismatch | Match exact OpenShift callback URL. |
| Issuer mismatch | Configured issuer differs from token `iss` | Use exact issuer from discovery document. |
| Audience mismatch | Token `aud` does not include client ID | Fix client/audience settings. |
| Claim missing | IdP does not send configured claim | Add claim mapper or change claims list. |
| x509 error | Missing enterprise CA | Add CA ConfigMap. |
| CLI password login fails | OIDC provider does not support ROPC | Use browser token flow. |

### 14.4 User created but no access

This is not an authentication issue. It is RBAC.

Check:

```bash
oc whoami
oc get users
oc get groups
oc describe group <group>
oc auth can-i get pods -n <namespace>
oc auth can-i get pods -n <namespace> --as=<username>
```

Fix:

```bash
oc adm policy add-role-to-group view <group> -n <namespace>
oc adm policy add-role-to-group edit <group> -n <namespace>
oc adm policy add-cluster-role-to-group cluster-reader <group>
```

### 14.5 LDAP group sync does not update groups

Check dry run first:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml
```

Apply only after review:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

Common causes:

- Forgot `--confirm`.
- Wrong group DN in whitelist.
- Wrong schema type.
- Wrong `userNameAttributes`.
- Bind account cannot read group membership.
- Nested groups not handled as expected.
- AD `memberOf` values not returned due permissions or query design.

### 14.6 Duplicate users after migration

Symptoms:

```text
jdoe
jdoe2
jdoe@example.com
```

Cause:

- New identity provider returns a different preferred username.
- `mappingMethod: claim` created a new user instead of mapping to existing user.

Fix strategy:

- Test with `mappingMethod: add` during migration if identities should merge.
- Or manually create user identity mappings.
- Clean up duplicate users only after validating ownership and audit requirements.

### 14.7 Locked out after auth change

Use break-glass kubeconfig.

Check and restore:

```bash
oc get authentication.config.openshift.io cluster -o yaml
oc get oauth cluster -o yaml
oc apply -f auth-backup/oauth-cluster.yaml
```

If using direct OIDC, use the backup plan created before switching.

## 15. Migration Strategy

### 15.1 HTPasswd to LDAP

Recommended approach:

```text
1. Export current users, identities, and RBAC.
2. Configure LDAP as additional identity provider.
3. Test with limited pilot users.
4. Use mappingMethod carefully.
5. Bind LDAP-synced groups to roles.
6. Validate access.
7. Communicate new login process.
8. Remove htpasswd after cutover.
9. Remove kubeadmin only after enterprise admin validation.
```

### 15.2 LDAP to OIDC

Recommended approach:

```text
1. Keep LDAP as source behind IdP if possible.
2. Configure Keycloak/Entra/Okta to federate LDAP users.
3. Expose stable OIDC claims.
4. Add OIDC provider to OpenShift.
5. Use mappingMethod add or planned manual mapping if same users must retain identity.
6. Pilot with non-production namespace RBAC.
7. Migrate admin groups.
8. Disable LDAP provider only after full validation.
```

### 15.3 Built-in OAuth OIDC to direct OIDC

Recommended approach:

```text
1. Treat as major architecture change.
2. Back up all auth-related objects.
3. Confirm long-lived emergency admin access.
4. Test in lower environment.
5. Validate CLI and console flows.
6. Validate group claim mapping.
7. Validate RBAC behavior.
8. Test rollback.
9. Schedule production change window.
10. Monitor authentication, API server, and user access after change.
```

## 17. Interview and Real-World Scenario Notes

### Scenario 1: User can log in but cannot create pods

Answer:

Authentication is working. Authorization is missing. Check user groups and RBAC bindings.

Commands:

```bash
oc whoami
oc get groups
oc auth can-i create pods -n <namespace>
oc adm policy add-role-to-group edit <group> -n <namespace>
```

### Scenario 2: LDAP login fails for one user but works for others

Possible causes:

- User disabled in AD.
- User outside configured base DN.
- User missing search attribute.
- Duplicate LDAP entries.
- Password expired.
- Filter excludes user.

### Scenario 3: All LDAP users fail suddenly

Possible causes:

- LDAP server down.
- Firewall change.
- DNS issue.
- Expired LDAP server certificate.
- Expired bind account password.
- CA bundle changed.
- Authentication operator degraded.

### Scenario 4: OIDC console login works but CLI login with password fails

Expected in many enterprise OIDC designs. Use browser token flow:

```bash
oc login --token=<token>
```

### Scenario 5: After migration, users lost access

Likely group or username mapping changed.

Check:

```bash
oc get users
oc get identities
oc get groups
oc describe clusterrolebinding <binding>
oc auth can-i get pods -n <namespace> --as=<user>
```

### Scenario 6: You need to integrate 20 OpenShift clusters with enterprise identity

Recommended design:

- Use OIDC SSO if available.
- Use consistent provider name.
- Use consistent group naming.
- Manage config with GitOps/ACM.
- Use RBAC manifests per environment.
- Monitor auth health centrally.
- Keep break-glass access per cluster.

### Scenario 7: Security asks why not give AD Domain Admins cluster-admin

Answer:

Domain Admin is an infrastructure directory role, not an OpenShift platform role. Cluster-admin gives full Kubernetes/OpenShift control, including workloads, secrets, operators, SCCs, and potentially business application data. Use a dedicated, approved OpenShift platform admin group with audit and separation of duties.

## Final Senior Admin Summary

For enterprise OpenShift architecture, LDAP/OIDC integration should be designed as an identity control plane, not a simple login feature.

Use LDAP when the organization only exposes directory authentication. Use OIDC when the organization supports modern SSO, MFA, and centralized access policy. Consider direct external OIDC only when the platform team has strong operational maturity, rollback planning, and centralized token governance requirements.

The best production design is usually:

```text
Enterprise directory -> Enterprise IdP/OIDC -> OpenShift authentication -> Group-based RBAC -> Audited access
```

Never stop at “user can log in.” The real enterprise architecture goal is:

```text
Right identity + right group + right RBAC + right audit + right revocation path
```
