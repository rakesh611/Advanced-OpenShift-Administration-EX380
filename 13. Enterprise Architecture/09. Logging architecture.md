## 1. Executive Summary

In an enterprise OpenShift environment, **logging architecture** is the design of how logs are generated, collected, enriched, filtered, routed, stored, queried, secured, retained, and integrated with enterprise observability or SIEM platforms.

A mature OpenShift logging architecture is not only about installing an Operator. It answers questions such as:

- Which logs are collected: application, infrastructure, audit, node, network, security, operator, and platform logs?
- Where are logs stored: in-cluster LokiStack, external Loki, Splunk, Kafka, Elasticsearch, cloud logging, or SIEM?
- How long are logs retained locally and externally?
- Who can query which logs?
- How do you prevent noisy workloads from breaking the logging pipeline?
- How do you protect sensitive data inside logs?
- How do you operate logging across dev, test, production, DR, and multi-cluster environments?
- How do you keep logging available during node failure, object storage failure, cluster upgrade, or network partition?

For modern Red Hat OpenShift Logging 6.x, the architecture is separated into three major responsibilities:

| Layer | Main component | Responsibility |
|---|---|---|
| Collection and forwarding | Red Hat OpenShift Logging Operator + Vector collector | Collect logs from nodes and pods, enrich them, apply filters, and forward them |
| Storage | Loki Operator + LokiStack | Store and index logs using object storage and Loki components |
| Visualization | Cluster Observability Operator | Adds log visualization in the OpenShift web console through a UIPlugin |

This separation is important for enterprise architecture because it allows different teams to own different parts of the platform:

- Platform team owns log collection policy.
- Storage/platform team owns Loki object storage and capacity.
- Security/SOC team owns audit forwarding and SIEM integration.
- Application teams own log quality and log volume discipline.
- Compliance team defines retention and access rules.

## 2. What “Logging Architecture” Means in Enterprise Architecture

In enterprise architecture, logging is not a standalone tool. It is part of the **observability, security, compliance, and operations architecture**.

### 2.1 Logging vs Monitoring vs Tracing

| Area | Main question answered | Examples |
|---|---|---|
| Metrics | What is happening numerically? | CPU, memory, request count, error rate, latency percentile |
| Logs | What happened in detail? | Error messages, stack traces, audit events, API calls |
| Traces | Where did a request travel? | Service A → Service B → Database latency |
| Events | What changed in the cluster? | Pod scheduled, image pull failed, node not ready |

OpenShift already includes a strong metrics stack for cluster monitoring. Logging complements that by providing detailed records for troubleshooting, audit, and investigation.

### 2.2 Enterprise Logging Goals

A production logging design should support these goals:

1. **Troubleshooting**
   - Developers and SREs should quickly find application errors.
   - Platform admins should find node, operator, API, and infrastructure issues.

2. **Security investigation**
   - Security teams should investigate suspicious API access, privilege escalation, failed authentication, and unusual network behavior.

3. **Compliance and audit**
   - Audit logs must be retained according to policy.
   - Some environments require tamper-resistant external forwarding.

4. **Operational continuity**
   - Logging should continue during node churn, application scale-out, upgrades, and partial failures.

5. **Cost control**
   - Logs can grow faster than metrics.
   - Architecture must control volume, cardinality, retention, and noisy workloads.

6. **Tenant isolation**
   - Application teams should not see other teams’ logs unless explicitly permitted.
   - Audit logs should be restricted to platform/security administrators.

### 2.3 Logging Architecture Design Domains

A senior OpenShift administrator should think about logging in these domains:

| Domain | Design decision |
|---|---|
| Source | What log sources are collected? |
| Collection | Which collector runs on nodes? |
| Enrichment | What Kubernetes metadata is added? |
| Filtering | What logs are dropped, pruned, parsed, or routed? |
| Transport | How are logs sent: Loki, Kafka, HTTP, Splunk, syslog, cloud provider? |
| Storage | In-cluster or external? Short-term or long-term? |
| Query | Console, Loki API, LogQL, SIEM, external dashboard? |
| Security | RBAC, TLS, service account, secrets, tenant boundary? |
| Retention | 7 days, 14 days, 30 days, external archive? |
| Resilience | What happens if object storage or external SIEM is down? |
| Governance | Who owns log schema, retention, and PII masking? |
| Cost | How do you manage log ingestion rate and object storage growth? |

## 3. Modern OpenShift Logging Stack Overview

### 3.1 Current Red Hat OpenShift Logging 6.x Direction

Modern Red Hat OpenShift Logging uses the following model:

```text
Applications / Platform / Audit Sources
            |
            v
Vector Collector DaemonSet
            |
            v
ClusterLogForwarder Pipelines
            |
            +------------------> LokiStack, managed by Loki Operator
            |
            +------------------> External systems: Splunk, Kafka, HTTP, Elasticsearch, CloudWatch, Azure Monitor, etc.
            |
            v
OpenShift Console Logs UI, managed by Cluster Observability Operator
```

Key architectural points:

- The **Red Hat OpenShift Logging Operator** manages log collection and forwarding.
- The **Loki Operator** manages LokiStack log storage.
- The **Cluster Observability Operator** provides console log visualization.
- The **ClusterLogForwarder** custom resource defines inputs, filters, outputs, and pipelines.
- The **LokiStack** custom resource defines log storage, size, tenancy, storage backend, schema, retention, and related Loki behavior.

### 3.2 Important Change from Older Logging Architectures

Older OpenShift logging designs commonly used:

```text
Fluentd collector -> Elasticsearch -> Kibana
```

In newer OpenShift Logging 6.x architecture:

```text
Vector collector -> LokiStack -> OpenShift Console Logs UI
```

The old Elasticsearch/Kibana-based managed stack is no longer the strategic direction for current OpenShift Logging 6.x. For new enterprise designs, prefer **Vector + LokiStack + ClusterLogForwarder + Cluster Observability Operator**.

### 3.3 Why This Matters for a Senior Admin

A 10-year experienced admin should not treat logging as “install Operator and done.” The real architecture decisions are:

- Should this cluster store logs locally or only forward externally?
- Should audit logs go to the same destination as application logs?
- Do we need a central logging cluster for multiple OpenShift clusters?
- Should dev/test logs have shorter retention than production logs?
- Are we using infra nodes for Loki components?
- Is object storage production-grade and replicated?
- Are application teams generating uncontrolled log volume?
- Are logs leaking credentials or PII?
- Is the cluster logging stack itself monitored?

## 4. End-to-End Logging Data Flow

### 4.1 High-Level Flow

```text
+-----------------------------+
| Application containers      |
| stdout / stderr             |
+-------------+---------------+
              |
              v
+-----------------------------+
| Node filesystem             |
| /var/log/pods               |
| /var/log/containers         |
| systemd journal             |
| audit log files             |
+-------------+---------------+
              |
              v
+-----------------------------+
| Vector collector pod        |
| Runs as DaemonSet           |
| One collector per node      |
+-------------+---------------+
              |
              v
+-----------------------------+
| Enrichment                  |
| Kubernetes metadata         |
| log_type                    |
| namespace / pod / container |
+-------------+---------------+
              |
              v
+-----------------------------+
| ClusterLogForwarder         |
| inputs -> filters -> outputs|
+-------------+---------------+
              |
              +----------------------------+
              |                            |
              v                            v
+-----------------------------+  +-----------------------------+
| LokiStack                   |  | External destinations       |
| Short-term troubleshooting  |  | SIEM / Kafka / Splunk etc.  |
+-------------+---------------+  +-----------------------------+
              |
              v
+-----------------------------+
| Query / visualization       |
| Observe -> Logs             |
| Loki API / LogQL            |
+-----------------------------+
```

### 4.2 Detailed Flow Explanation

#### Step 1: Application writes logs

In Kubernetes and OpenShift, the best practice is for containers to write logs to **stdout** and **stderr**. The container runtime writes these streams to node log files. If an application writes only to an internal file inside the container filesystem, the default collector might not collect it unless a sidecar or application change is introduced.

#### Step 2: Node stores container log files

Each node has container log files. These are the raw data source for the collector. Node-level infrastructure and audit logs may also come from system logs, journal logs, or specific audit log file paths depending on source type.

#### Step 3: Vector collector runs on each node

The collector runs as a **DaemonSet** so that every node that runs workloads has a local log collector. This architecture avoids sending logs over the network from application pods to a central collector first. Instead, collection happens close to the source.

#### Step 4: Collector enriches logs

The collector adds metadata such as:

- Kubernetes namespace
- Pod name
- Container name
- Labels
- Node name
- Log type
- Timestamp
- Source

This enrichment is critical because enterprise queries usually depend on namespace, application, team, environment, and platform ownership.

#### Step 5: ClusterLogForwarder applies pipeline logic

The ClusterLogForwarder determines:

- Which logs are selected
- Which filters are applied
- Which destinations receive which logs
- Whether logs are sent to LokiStack, external systems, or both

#### Step 6: Logs are stored or forwarded

Logs may be:

- Stored in LokiStack for short-term troubleshooting.
- Forwarded to Splunk or SIEM for compliance/security.
- Sent to Kafka as an enterprise log bus.
- Sent to cloud-native logging services.
- Sent to external Loki or Elasticsearch.

#### Step 7: Users query logs

Users can query logs from:

- OpenShift web console under **Observe → Logs** when the UI plugin is enabled.
- Loki API or LogQL.
- External systems such as Splunk, Elastic, Kafka consumers, SIEM tools, or cloud logging.

## 5. Major Components

### 5.1 Red Hat OpenShift Logging Operator

The Red Hat OpenShift Logging Operator is responsible for collection and forwarding. It watches ClusterLogForwarder resources and deploys/configures the collector.

Responsibilities:

- Deploy Vector collector.
- Configure log inputs.
- Configure forwarding outputs.
- Apply filters.
- Manage pipelines.
- Manage collector configuration rollout.
- Support forwarding to multiple output types.

It is usually installed in the `openshift-logging` namespace.

Important resources:

```bash
oc get pods -n openshift-logging
oc get clusterlogforwarder -A
oc get ds -n openshift-logging
oc get sa -n openshift-logging
```

### 5.2 Vector Collector

Vector is the collector/forwarder used in the modern logging stack. It runs on nodes and performs:

- Tailing of container logs.
- Collection of infrastructure logs.
- Collection of audit logs if RBAC allows it.
- Metadata enrichment.
- Transformation and filtering.
- Delivery to configured outputs.

Typical collector deployment model:

```text
Node 1 -> Vector collector pod
Node 2 -> Vector collector pod
Node 3 -> Vector collector pod
...
```

Important operational point:

- The collector should run on **every node that produces logs**.
- Do not schedule the collector only on infra nodes if you expect to collect application logs from worker nodes.
- Loki storage components can be isolated to infra nodes, but the collector must follow log-producing nodes.

### 5.3 ClusterLogForwarder

The ClusterLogForwarder is the routing brain of the logging architecture.

It defines:

| Section | Meaning |
|---|---|
| `serviceAccount` | Service account used by the collector |
| `inputs` | Log sources such as application, infrastructure, audit, or selected namespaces |
| `filters` | Drop, prune, detect multiline exceptions, audit filters, etc. |
| `outputs` | Destinations such as LokiStack, Splunk, Kafka, HTTP, CloudWatch |
| `pipelines` | Connect inputs + filters + outputs |

Conceptually:

```text
Input: application logs from namespaces app-prod and app-dev
Filter: drop health check logs
Output: LokiStack + Splunk
Pipeline: app-prod-pipeline
```

### 5.4 Loki Operator

The Loki Operator manages LokiStack. It is responsible for the log storage layer.

Responsibilities:

- Deploy Loki components.
- Manage LokiStack custom resource.
- Connect Loki to object storage.
- Configure tenancy.
- Configure retention.
- Configure size and replication behavior.
- Manage Loki upgrades and schema changes.

Typical namespace for the Operator is `openshift-operators-redhat`, while the `LokiStack` instance normally lives in `openshift-logging`.

### 5.5 LokiStack

LokiStack is the OpenShift-supported Loki deployment pattern. It combines Loki with OpenShift authentication and multi-tenancy integration.

Main responsibilities:

- Receive logs from collectors.
- Store log chunks and indexes in object storage.
- Support querying through Loki API and console UI.
- Enforce tenancy modes.
- Apply retention rules.

Common LokiStack components include, depending on size and enabled features:

- Gateway/proxy
- Distributor
- Ingester
- Querier
- Query frontend
- Index gateway
- Compactor
- Ruler

### 5.6 Cluster Observability Operator

The Cluster Observability Operator enables console log visualization through a `UIPlugin`.

It allows users to access logs from:

```text
OpenShift Console -> Observe -> Logs
```

Important point:

- The Cluster Observability Operator is optional for collection/storage/forwarding.
- It is required if you want the integrated web console log view.

## 6. Log Types in OpenShift

OpenShift logging commonly separates logs into three high-level categories.

### 6.1 Application Logs

Application logs are generated by user workloads.

Examples:

- Java application stack traces
- Nginx access logs
- Python application errors
- Node.js service logs
- Database client errors from application pods
- Microservice transaction logs

Typical source:

```text
container stdout/stderr
```

Typical users:

- Developers
- Application support teams
- SRE teams
- Platform teams during incident investigation

Architecture guidance:

- Keep application logs structured where possible, preferably JSON.
- Avoid secrets, passwords, tokens, and personal information in logs.
- Use log levels correctly: DEBUG should not run permanently in production unless justified.
- Separate production and non-production retention.
- Use namespace, labels, and application ownership metadata to route logs.

### 6.2 Infrastructure Logs

Infrastructure logs come from OpenShift and node-level components.

Examples:

- kubelet logs
- CRI-O logs
- node system logs
- OpenShift operator logs
- router/ingress logs
- registry logs
- monitoring component logs
- network component logs

Typical users:

- OpenShift administrators
- Platform engineering team
- Infrastructure team
- Red Hat support during cases

Architecture guidance:

- Infrastructure logs are essential for platform troubleshooting.
- They should have stricter access than normal application logs.
- They should be forwarded externally if required for compliance or long-term incident review.

### 6.3 Audit Logs

Audit logs record security-relevant actions.

Examples:

- Kubernetes API requests
- OpenShift API requests
- Authentication and authorization-related activity
- Changes to RBAC
- Secret access attempts
- Privileged workload creation
- Network/audit sources depending on configuration

Typical users:

- Security team
- Compliance team
- Platform administrators
- Incident response team

Architecture guidance:

- Audit logs should usually be forwarded to an external SIEM or immutable log platform.
- Audit log retention is often longer than application log retention.
- Access to audit logs should be restricted.
- Audit filtering can reduce volume, but do not filter so aggressively that investigations become impossible.

### 6.4 Recommended Enterprise Classification

| Log category | Primary purpose | Retention suggestion | Destination |
|---|---|---|---|
| Application dev/test | Developer troubleshooting | 3-7 days | In-cluster Loki |
| Application prod | Troubleshooting and RCA | 7-30 days local, longer external | Loki + external |
| Infrastructure | Platform troubleshooting | 14-30 days local | Loki + external |
| Audit | Security and compliance | Per compliance policy | External SIEM + secure archive |
| Security events | Incident response | Long-term | SIEM/SOAR |
| High-volume debug | Temporary troubleshooting | Hours to 1 day | Temporary only |

## 7. ClusterLogForwarder Architecture

### 7.1 Why ClusterLogForwarder Is Central

The ClusterLogForwarder is where architecture becomes policy.

Without a good forwarding design, all logs may be treated the same. That is usually wrong for enterprise environments.

Example enterprise requirements:

- App logs from `prod-*` namespaces go to Loki and Splunk.
- App logs from `dev-*` namespaces go only to Loki with short retention.
- Audit logs go to Splunk/SIEM and are not visible to developers.
- Noisy health-check logs are dropped.
- Sensitive Kubernetes annotations are pruned before forwarding externally.
- Kafka is used as a central log bus for multiple downstream consumers.

### 7.2 ClusterLogForwarder Building Blocks

#### Inputs

Inputs select log sources.

Common input types:

- `application`
- `infrastructure`
- `audit`

Examples:

```yaml
inputs:
  - name: prod-app-logs
    type: application
    application:
      includes:
        - namespace: prod-payments
        - namespace: prod-orders
```

#### Filters

Filters modify, drop, prune, or process logs.

Common uses:

- Drop noise.
- Remove large metadata fields.
- Remove sensitive fields.
- Detect multiline exceptions.
- Apply audit filtering.

Example concept:

```yaml
filters:
  - name: drop-health-checks
    type: drop
    drop:
      - test:
          - field: .message
            matches: "GET /healthz"
```

#### Outputs

Outputs define destinations.

Examples:

- `lokiStack`
- `loki`
- `kafka`
- `splunk`
- `http`
- `syslog`
- `elasticsearch`
- `cloudwatch`
- `azureMonitor`
- `googleCloudLogging`

#### Pipelines

Pipelines connect inputs, filters, and outputs.

```yaml
pipelines:
  - name: prod-app-pipeline
    inputRefs:
      - prod-app-logs
    filterRefs:
      - drop-health-checks
    outputRefs:
      - default-lokistack
      - splunk-siem
```

### 7.3 Pipeline Design Strategy

A mature enterprise design normally uses different pipelines for different purposes:

| Pipeline | Inputs | Filters | Outputs |
|---|---|---|---|
| `prod-apps` | Production application namespaces | Drop health checks, prune annotations | Loki + Splunk |
| `dev-apps` | Development namespaces | Drop debug noise | Loki only |
| `platform` | Infrastructure logs | Minimal pruning | Loki + Kafka |
| `audit-security` | Audit logs | Audit filter policy | SIEM |
| `critical-ns` | Business-critical namespaces | No aggressive filtering | Loki + SIEM |

### 7.4 Delivery Semantics

When forwarding logs, understand delivery guarantees.

Common concepts:

| Mode | Meaning | Tradeoff |
|---|---|---|
| AtLeastOnce | Collector retries and may resend logs after failure | Better durability, possible duplicates |
| AtMostOnce | Collector does not try hard to recover after crash | Better throughput, possible log loss |

For audit and compliance pipelines, prefer durability over perfect deduplication. For noisy application debug logs, throughput may matter more.

### 7.5 Multi-Destination Forwarding

A single input can be forwarded to multiple outputs.

Example:

```text
Production app logs -> LokiStack for 14 days
Production app logs -> Splunk for 90 days
Production app logs -> Kafka for analytics pipeline
```

Benefits:

- Developers get fast local troubleshooting.
- Security gets central visibility.
- Data platform can consume logs asynchronously.

Risks:

- Duplicate cost.
- Higher network usage.
- More failure modes.
- More secrets and certificates to manage.

### 7.6 Namespace-Based Routing

Namespace routing is one of the most useful patterns.

Example:

```text
prod-* namespaces -> production SIEM index
dev-* namespaces  -> short-retention Loki only
pci-* namespaces  -> restricted compliance destination
```

Design recommendation:

Use namespace labels such as:

```yaml
metadata:
  labels:
    environment: prod
    business-unit: finance
    compliance: pci
    owner: payments-team
```

Then design pipelines around labels or namespace selection.

### 7.7 Application Label-Based Routing

For multi-tenant clusters, label consistency is important.

Recommended labels:

```yaml
app.kubernetes.io/name: payments-api
app.kubernetes.io/part-of: payments-platform
app.kubernetes.io/component: backend
app.kubernetes.io/managed-by: helm
environment: prod
team: payments
```

Why it matters:

- Log routing can depend on labels.
- Querying becomes easier.
- Ownership becomes visible.
- Noisy teams can be identified.

## 8. LokiStack Storage Architecture

### 8.1 LokiStack Role in OpenShift

LokiStack provides a short-term log store for troubleshooting and querying. In enterprise design, it is usually the “hot” log store.

```text
Hot logs      -> LokiStack, fast troubleshooting, short retention
Warm logs     -> External SIEM/log platform
Cold archive  -> Object lock/archive/compliance storage
```

### 8.2 Loki Is Not Elasticsearch

Loki and Elasticsearch have different indexing models.

| Area | Loki | Elasticsearch |
|---|---|---|
| Indexing | Indexes labels, not full text by default | Full-text indexing |
| Storage | Object storage optimized | Disk/index-heavy architecture |
| Query language | LogQL | Elasticsearch DSL / KQL |
| Best use | Recent troubleshooting, label-based search | Full-text search, analytics |
| Cost profile | Often lower for high-volume logs | Can be higher due to indexing |

This means Loki design depends heavily on **label discipline**.

### 8.3 LokiStack Storage Requirements

LokiStack has two storage concerns:

1. **Block storage / StorageClass**
   - Used by internal Loki components.
   - Supports write-ahead logs, caches, and compactor working data.

2. **Object storage**
   - Used for actual log chunks and indexes.
   - S3-compatible storage is commonly used.
   - Examples include AWS S3, GCS, Azure Blob, Ceph RGW, OpenShift Data Foundation object storage, Swift, or other S3-compatible platforms.

This distinction is very important. Many admins confuse `storageClassName` with object storage. `storageClassName` is not the bucket. The object storage connection is configured through a secret referenced by the LokiStack CR.

### 8.4 Object Storage Architecture

Object storage is the backbone of LokiStack durability.

Typical production architecture:

```text
Loki ingesters / compactors / query components
              |
              v
S3-compatible object storage bucket
              |
              +--> lifecycle policy
              +--> replication policy
              +--> encryption policy
              +--> access policy
```

Production requirements:

- High availability.
- Sufficient throughput.
- TLS trust configured.
- Bucket lifecycle aligned with retention.
- Bucket permissions restricted.
- Encryption at rest.
- Backup/replication according to policy.

### 8.5 LokiStack Tenancy

OpenShift-oriented LokiStack tenancy helps separate log access between tenants such as:

- application
- infrastructure
- audit

Enterprise use:

- Developers can query their application logs.
- Platform admins can query infrastructure logs.
- Security admins can query audit logs.

Tenancy must be combined with OpenShift RBAC. Tenancy is not a replacement for RBAC; it works with it.

### 8.6 LokiStack Sizing

LokiStack supports named deployment sizes such as:

- `1x.demo`
- `1x.pico`
- `1x.extra-small`
- `1x.small`
- `1x.medium`

For production, do not blindly choose a size. Start with expected log ingestion and query load, then monitor.

Sizing inputs:

| Input | Question |
|---|---|
| Daily log volume | GB/day or TB/day? |
| Peak burst | What happens during incidents? |
| Query load | How many users query logs? |
| Retention | How many days local? |
| Tenant count | How many teams/namespaces? |
| Audit volume | Are audit logs verbose? |
| Object storage | Can bucket sustain write/read throughput? |
| Node capacity | Are infra nodes sized for Loki components? |

### 8.7 Retention Design

LokiStack retention should be explicit.

Without retention, object storage can grow continuously. In enterprise architecture, define retention intentionally:

| Log type | Example Loki retention |
|---|---|
| dev application | 3 days |
| test application | 7 days |
| prod application | 14-30 days |
| infrastructure | 14-30 days |
| audit | Short local retention, long external retention |

For compliance, use an external system with retention and immutability controls if required.

### 8.8 Label Cardinality

Loki performance depends on labels. High-cardinality labels are dangerous.

Good labels:

- namespace
- app
- container
- log_type
- environment
- team

Risky labels:

- request ID
- transaction ID
- user ID
- pod UID
- container ID
- session ID
- IP address when extremely variable
- timestamp-derived values

Rule:

> Use labels for dimensions you commonly filter on and that have controlled cardinality. Keep highly unique values inside the log message, not as labels.

## 9. Visualization Architecture

### 9.1 OpenShift Console Logs UI

With the Cluster Observability Operator and `UIPlugin`, logs can appear in:

```text
OpenShift Console -> Observe -> Logs
```

This provides a native OpenShift user experience.

Benefits:

- Developers do not need separate tooling for basic troubleshooting.
- RBAC-integrated access.
- Namespace context is natural.
- Useful during application incident response.

### 9.2 External Visualization

Many enterprises still use external tools:

- Splunk
- Elastic
- Grafana
- CloudWatch
- Azure Monitor
- Google Cloud Logging
- Datadog
- SIEM/SOAR tools

Architecture recommendation:

Use OpenShift console for immediate cluster-local troubleshooting, and forward important logs to enterprise systems for long-term retention, correlation, analytics, and compliance.

### 9.3 Query Path

Typical local query path:

```text
User -> OpenShift Console -> Logging UIPlugin -> Loki gateway/proxy -> Loki query components -> Object storage
```

Potential bottlenecks:

- Query frontend CPU/memory.
- Object storage read latency.
- High-cardinality labels.
- Very broad time-range queries.
- Too many concurrent users.
- Large JSON logs with huge message fields.

## 10. Enterprise Deployment Models

### 10.1 Single-Cluster Local Logging

```text
Cluster A
  Vector -> LokiStack -> Console
```

Best for:

- Small environments.
- Dev/test clusters.
- Labs.
- Short-term troubleshooting.

Pros:

- Simple.
- Fast to deploy.
- Local visibility.

Cons:

- Logs may be lost if cluster/object storage has issues.
- Not enough for enterprise compliance.
- Hard to correlate across clusters.

### 10.2 Local + External SIEM

```text
Cluster A
  Vector -> LokiStack      -> local troubleshooting
         -> Splunk/SIEM    -> compliance/security
```

Best for:

- Production clusters.
- Regulated environments.
- Security monitoring.

Pros:

- Developers get fast local logs.
- Security gets central immutable trail.
- Retention can differ by destination.

Cons:

- More cost.
- More network and TLS complexity.
- More operational dependencies.

### 10.3 Multi-Cluster Central Logging

```text
Cluster A -> Forward logs -> Central logging platform
Cluster B -> Forward logs -> Central logging platform
Cluster C -> Forward logs -> Central logging platform
```

Best for:

- Large enterprises.
- Hub-spoke OpenShift architecture.
- ACM-managed fleets.
- DR and compliance.

Design options:

1. Each cluster has local short-term LokiStack and forwards to central SIEM.
2. Edge clusters only forward to central logging, no local LokiStack.
3. Production clusters use dedicated logging buckets and dedicated external indexes.
4. Dev/test clusters use shorter local-only retention.

### 10.4 Edge and Remote Site Logging

Edge sites often have limited CPU, memory, disk, and network.

Recommended approach:

- Keep minimal local retention.
- Forward important logs to central systems.
- Avoid storing all logs locally.
- Use filters to reduce noise.
- Prioritize audit and platform health logs.

### 10.5 Disconnected / Air-Gapped Logging

For disconnected OpenShift:

- Mirror Operator catalogs.
- Mirror logging images.
- Use internal object storage.
- Use internal CA trust bundles.
- Use internal SIEM/syslog/Splunk/Kafka endpoints.
- Verify network routes and DNS.
- Document certificate rotation process.

Common disconnected issue:

```text
LokiStack Ready = True, but logs are not stored
```

Frequent cause:

- Object storage endpoint uses internal CA and LokiStack does not trust the CA bundle.

## 11. Sizing and Capacity Planning

### 11.1 Start with Log Volume

The first sizing question is:

```text
How many GB or TB of logs per day will this cluster generate?
```

Estimate per source:

| Source | Estimate method |
|---|---|
| Application logs | Average log line size × lines/sec × replicas |
| Infrastructure logs | Baseline from similar cluster |
| Audit logs | API request volume × audit policy verbosity |
| Ingress/router logs | Requests/sec × access log size |
| Debug logs | Treat as temporary burst |

### 11.2 Capacity Formula

Basic estimate:

```text
Daily log volume = average bytes per log event × events per second × 86400
Retention storage = daily log volume × retention days × compression factor overhead
```

Example:

```text
Average event size: 700 bytes
Events/sec: 10,000
Daily raw = 700 × 10,000 × 86400 = 604,800,000,000 bytes ≈ 604 GB/day
Retention 14 days = 8.4 TB raw before compression/overhead
```

This is why uncontrolled application logs can become expensive quickly.

### 11.3 Measure, Do Not Guess Forever

Before production rollout:

1. Deploy with conservative sizing.
2. Measure ingestion rate.
3. Measure object storage growth.
4. Measure query latency.
5. Measure collector CPU/memory.
6. Adjust retention and filters.
7. Right-size LokiStack.

### 11.4 Collector Sizing

Collector resource pressure increases with:

- More logs per second.
- Larger log lines.
- Multiline exception detection.
- Complex filters.
- Many outputs.
- Slow external destinations.
- TLS encryption overhead.
- Network instability.

Monitor:

```bash
oc adm top pods -n openshift-logging
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

### 11.5 Loki Query Sizing

Query pressure increases with:

- Broad time ranges.
- Regex-heavy queries.
- High-cardinality labels.
- Many users querying during incidents.
- Dashboards refreshing frequently.
- Object storage latency.

Best practices:

- Query narrow time windows first.
- Use labels before text filters.
- Avoid unbounded regex queries.
- Use environment/team labels carefully.
- Educate users on LogQL query discipline.

### 11.6 Infra Node Placement

For enterprise clusters, consider running logging storage components on infra nodes.

Example intent:

```text
Worker nodes     -> run application workloads and collector pods
Infra nodes      -> run router, registry, monitoring, logging storage/query components
Master nodes     -> control plane only
```

Important distinction:

- Vector collector must run on log-producing nodes.
- Loki components can be placed on infra nodes using node selectors/tolerations where supported.

### 11.7 Object Storage Sizing

Object storage must be designed for:

- Write throughput.
- Read throughput during queries.
- Retention growth.
- Lifecycle deletion.
- Replication.
- TLS and network latency.
- Bucket policy.

Do not size object storage only by raw capacity. Query performance depends on object storage behavior.

## 12. Retention, Compliance, and Data Governance

### 12.1 Retention Tiers

A good enterprise pattern is tiered retention:

```text
Tier 1: Hot logs in LokiStack
  - 7 to 30 days
  - Fast troubleshooting
  - OpenShift Console access

Tier 2: Warm logs in SIEM/log analytics
  - 30 to 180 days
  - Security and operations analytics

Tier 3: Cold archive
  - 1 year to 7 years depending on regulation
  - Immutable/object-lock/archive storage
```

### 12.2 Compliance Requirements

Possible requirements:

- Audit logs retained for a fixed period.
- Logs must be tamper-evident or immutable.
- Access to logs must be audited.
- Logs must not contain secrets or personal data unless governed.
- Certain logs must be stored in a specific region.
- Logs must be encrypted in transit and at rest.

### 12.3 Data Sensitivity

Application logs often accidentally contain sensitive data.

Examples:

- Passwords
- JWT tokens
- OAuth access tokens
- API keys
- Session cookies
- Aadhaar/PAN or other identity data
- Customer email/phone
- Payment data
- Internal URLs and hostnames

Architecture controls:

- Developer logging standards.
- Application-side redaction.
- Admission controls or code review gates.
- Collector prune/drop filters where feasible.
- SIEM masking rules.
- Restricted RBAC.

### 12.4 Audit Log Handling

Audit logs are high value and sensitive.

Recommended design:

```text
Audit logs -> External SIEM / secure log archive
Audit logs -> Optional short-term Loki for platform admins only
```

Avoid:

- Giving developers audit log access by default.
- Dropping important audit events to reduce cost without security approval.
- Storing audit logs only inside the same cluster that may be compromised.

## 13. Security Architecture

### 13.1 RBAC for Collection

Modern logging requires explicit RBAC for the collector service account.

Common cluster roles:

- `collect-application-logs`
- `collect-infrastructure-logs`
- `collect-audit-logs`

Example:

```bash
oc create sa logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:logging-collector

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:logging-collector

oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:logging-collector
```

Security principle:

> Grant only the log collection permissions required by the pipeline.

If you do not collect audit logs, do not bind `collect-audit-logs`.

### 13.2 RBAC for Querying

Query access should follow least privilege.

Recommended model:

| User group | Access |
|---|---|
| Developers | Own namespace application logs |
| App support | Application logs for supported namespaces |
| Platform admins | Infrastructure and app logs |
| Security team | Audit and security logs |
| Compliance auditors | Read-only audit/compliance views |

### 13.3 TLS and Certificates

TLS matters in three places:

1. Collector to LokiStack.
2. Collector to external destinations.
3. LokiStack to object storage.

Common certificate problems:

- Internal CA not trusted.
- Expired external endpoint certificate.
- Wrong SAN in certificate.
- Secret has wrong key names.
- CA bundle missing.
- mTLS certificate/key mismatch.

### 13.4 Secrets Management

Logging often needs secrets for:

- S3 object storage credentials.
- Splunk HEC token.
- Kafka SASL username/password.
- Elasticsearch credentials.
- Cloud provider credentials.
- TLS private keys.

Best practices:

- Store secrets in `openshift-logging` only when needed there.
- Use external secret operators if enterprise standard requires it.
- Rotate credentials regularly.
- Avoid embedding secrets in Git.
- Use Sealed Secrets, External Secrets Operator, Vault, or GitOps-safe secret flow.
- Keep audit trail of secret updates.

### 13.5 NetworkPolicy

If your cluster enforces NetworkPolicy, allow required traffic:

- Collector pods to Loki gateway/service.
- Collector pods to external log destinations.
- Loki components to object storage endpoint.
- Console/observability plugin to Loki query endpoint.
- DNS access from logging namespace.

Example egress destinations:

```text
openshift-logging -> S3 endpoint
openshift-logging -> Splunk HEC
openshift-logging -> Kafka brokers
openshift-logging -> internal CA/OCSP if required
```

### 13.6 Security Risks in Logging

| Risk | Impact | Control |
|---|---|---|
| Logs contain secrets | Credential compromise | App redaction, filters, scanning |
| Developers see other teams’ logs | Data leakage | RBAC and tenancy |
| Audit logs stored only locally | Attacker can delete trail | External forwarding |
| No TLS to external destination | Data interception | TLS/mTLS |
| Over-permissive service account | Privilege exposure | Least privilege RBAC |
| GitOps stores raw secret | Secret leak | Sealed/external secrets |

## 14. High Availability and Failure Domains

### 14.1 Collector HA

Collectors run as a DaemonSet. If one node fails, its collector fails with it. Other nodes continue collecting logs.

Failure considerations:

| Failure | Result |
|---|---|
| One collector pod crashes | Logs on that node may be delayed or lost depending on buffering/delivery |
| One worker node fails | Logs on failed node may be unavailable after local files disappear |
| External destination down | Collector retries or drops depending on tuning and buffer behavior |
| Cluster API unavailable | Metadata enrichment may be affected |

### 14.2 LokiStack HA

LokiStack HA depends on:

- Deployment size.
- Replication settings.
- Pod topology spread.
- Object storage durability.
- Persistent volume availability.
- Network availability.

For production:

- Use production-supported size.
- Avoid demo sizing.
- Use replicated object storage.
- Spread components across zones where possible.
- Monitor compactor and ingester health.

### 14.3 Object Storage as Critical Dependency

If object storage is unavailable:

- Loki ingestion may fail or degrade.
- Queries may fail.
- Logs may be delayed or dropped depending on buffering and failure duration.

Design controls:

- Use highly available object storage.
- Monitor bucket availability.
- Monitor latency and error rates.
- Use lifecycle policies carefully.
- Test credential rotation.
- Test CA rotation.

### 14.4 External Destination Failure

If Splunk/Kafka/SIEM is down:

Possible outcomes:

- Collector retries.
- Buffer grows.
- Collector resource usage increases.
- Logs may be dropped after retry/buffer limits.
- Pipelines to other outputs may still work, depending on configuration and failure mode.

Design recommendation:

- Use separate pipelines for critical destinations.
- Use Kafka as buffer when enterprise systems are unstable.
- Alert on delivery errors.
- Define log-loss acceptance by pipeline.

## 18. Troubleshooting Playbook

### 18.1 Problem: No Logs in Console

Checklist:

```bash
oc get pods -n openshift-logging
oc get lokistack -n openshift-logging
oc get clusterlogforwarder -A
oc get uiplugin -A
oc get csv -A | egrep 'loki|logging|observability'
```

Possible causes:

| Cause | Check | Fix |
|---|---|---|
| Cluster Observability Operator missing | `oc get csv -n openshift-operators` | Install COO |
| UIPlugin missing | `oc get uiplugin` | Create `UIPlugin` CR |
| LokiStack not ready | `oc get lokistack` | Check Loki pods/events |
| Collector not running | `oc get pods -l app.kubernetes.io/component=collector` | Fix collector rollout |
| RBAC missing | Check ClusterRoleBindings | Bind collect roles |
| Object storage issue | Loki logs/events | Fix secret/CA/network |

### 18.2 Problem: Collector Pods Not Running on All Nodes

Check:

```bash
oc get nodes
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc describe pod -n openshift-logging <collector-pod>
oc get ds -n openshift-logging
```

Possible causes:

- Node taints not tolerated.
- Resource pressure.
- Image pull issue.
- SCC/security issue.
- Operator configuration issue.

### 18.3 Problem: ClusterLogForwarder Ready but No Logs Stored

Common causes:

- Collector cannot reach LokiStack.
- LokiStack cannot reach object storage.
- Object storage CA bundle missing.
- Wrong object storage secret.
- NetworkPolicy blocks traffic.
- Pipeline output reference wrong.
- Service account lacks collection roles.

Commands:

```bash
oc describe clusterlogforwarder -n openshift-logging <name>
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
oc get events -n openshift-logging --sort-by=.lastTimestamp
oc logs -n openshift-logging -l app.kubernetes.io/name=loki --tail=200
```

### 18.4 Problem: Audit Logs Missing

Check RBAC:

```bash
oc get clusterrole collect-audit-logs
oc get clusterrolebinding | grep collect-audit
oc get clusterlogforwarder -A -o yaml | grep -A5 audit
```

Possible causes:

- `collect-audit-logs` not bound to collector service account.
- Audit input missing from pipeline.
- Audit filter too aggressive.
- Output destination failing.

### 18.5 Problem: External Splunk/Kafka/SIEM Not Receiving Logs

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=300
oc get secret -n openshift-logging
oc describe clusterlogforwarder -n openshift-logging <name>
```

Validate from debug pod:

```bash
oc -n openshift-logging run net-test --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk https://splunk.example.com:8088
```

Possible causes:

- Wrong token/secret.
- TLS CA issue.
- Firewall blocked.
- Proxy not configured.
- Kafka SASL mechanism mismatch.
- Wrong topic or endpoint URL.

### 18.6 Problem: Loki Queries Are Slow

Possible causes:

- Query time range too broad.
- Poor label usage.
- High-cardinality labels.
- Object storage latency.
- Undersized LokiStack.
- Too many concurrent queries.
- Regex-heavy LogQL.

Actions:

- Query narrower time windows.
- Use labels first, then text filter.
- Review label cardinality.
- Increase LokiStack size if justified.
- Check object storage performance.
- Educate users on query patterns.

### 18.7 Problem: Object Storage Growing Too Fast

Possible causes:

- Retention not configured.
- Bucket lifecycle not configured.
- Debug logs enabled.
- Noisy namespace.
- Audit verbosity high.
- Duplicate forwarding/storage.

Actions:

```bash
oc get lokistack -n openshift-logging -o yaml
```

Review:

- `spec.limits.global.retention`
- tenant-specific retention
- bucket lifecycle policy
- noisy application teams
- log level standards

### 18.8 Problem: Multiline Java Exceptions Look Broken

Cause:

- Stack trace split into many separate log entries.

Possible fix:

- Use multiline exception detection filter.
- Prefer structured JSON logs with stack trace field.
- Understand performance impact before enabling broadly.

### 18.9 Problem: Application Logs Missing for One Namespace

Check:

```bash
oc get pods -n <namespace>
oc logs -n <namespace> <pod>
oc get clusterlogforwarder -A -o yaml
oc get ns <namespace> --show-labels
```

Possible causes:

- Application writes logs to file, not stdout/stderr.
- Namespace not included in input.
- Namespace excluded by filter.
- Pod labels do not match selector.
- Collector not running on node where pod is scheduled.

## 19. Production Design Patterns

### 19.1 Pattern: Local Hot Store + External Compliance Store

```text
Application/infrastructure logs -> LokiStack, 14 days
Audit/security logs             -> SIEM, 1 year+
Critical application logs        -> LokiStack + SIEM
```

Use when:

- Production workloads need fast troubleshooting.
- Security needs long-term audit.
- Cost must be controlled.

### 19.2 Pattern: Kafka as Enterprise Log Bus

```text
OpenShift clusters -> Kafka -> Splunk / data lake / fraud analytics / SIEM
```

Benefits:

- Decouples cluster from downstream systems.
- Handles multiple consumers.
- Useful for high-volume enterprise logging.

Risks:

- Kafka itself becomes critical infrastructure.
- Need topic design and retention.
- Need TLS/SASL management.

### 19.3 Pattern: Namespace-Based Retention

```text
prod-* -> 30 days local
stage-* -> 14 days local
dev-* -> 3 days local
```

Benefits:

- Controls cost.
- Matches business importance.
- Easy to explain to teams.

### 19.4 Pattern: Compliance Namespace Isolation

```text
pci-* namespaces -> dedicated SIEM index
hipaa-* namespaces -> restricted log destination
normal namespaces -> standard Loki
```

Benefits:

- Stronger governance.
- Easier audit evidence.
- Clear access boundaries.

### 19.5 Pattern: Edge Cluster Forward-Only

```text
Edge cluster collector -> central logging
Minimal or no local LokiStack
```

Benefits:

- Low resource usage on edge.
- Central audit visibility.

Risks:

- Local troubleshooting harder during WAN failure.
- Need buffering/failure policy.

---

## 20. Anti-Patterns

### 20.1 Storing Everything Forever in LokiStack

Bad because:

- Object storage grows forever.
- Query performance degrades.
- Cost becomes uncontrolled.
- LokiStack is intended for short-term troubleshooting, not unlimited archival.

Better:

- Use LokiStack for hot logs.
- Use external archival for long-term retention.

### 20.2 Sending All Logs to Security SIEM Without Filtering Strategy

Bad because:

- SIEM cost explodes.
- Security analysts drown in noise.
- Important events become harder to find.

Better:

- Route audit/security-critical logs to SIEM.
- Summarize or filter noisy logs.
- Keep raw app debug logs local and short-term.

### 20.3 Allowing DEBUG Logs Permanently in Production

Bad because:

- High cost.
- Sensitive data risk.
- Noise hides real issues.

Better:

- Use INFO/WARN/ERROR by default.
- Enable DEBUG temporarily with change approval.
- Automatically revert debug log levels.

### 20.4 High-Cardinality Loki Labels

Bad labels:

```text
request_id
session_id
user_id
trace_id
pod_uid
container_id
```

Better:

- Keep unique values in message fields.
- Use controlled labels such as namespace, app, team, environment.

### 20.5 No External Audit Forwarding

Bad because:

- If the cluster is compromised, local logs may be tampered with or deleted.
- Compliance evidence may be insufficient.

Better:

- Forward audit logs to external SIEM/archive.

### 20.6 Manual Console-Only Logging Configuration

Bad because:

- No version control.
- No approval trail.
- Hard to restore.
- Easy to drift.

Better:

- Use GitOps.

```yaml
    - name: default-lokistack
      type: lokiStack
      lokiStack:
        target:
          name: logging-loki
          namespace: openshift-logging
        authentication:
          token:
            from: serviceAccount
      tls:
        ca:
          key: service-ca.crt
          configMapName: logging-loki-gateway-ca-bundle
    - name: splunk-siem
      type: splunk
      splunk:
        url: https://splunk-hec.example.com:8088
        authentication:
          token:
            secretName: splunk-hec-secret
            key: hecToken
        index: '{.log_type||"undefined"}'
        source: '{.log_source||"undefined"}'
        tuning:
          compression: gzip
  pipelines:
    - name: prod-apps-to-loki-and-splunk
      inputRefs:
        - prod-apps
      filterRefs:
        - drop-health-checks
      outputRefs:
        - default-lokistack
        - splunk-siem
```

## 22. Interview and Real-World Scenario Notes

### 22.1 How to Explain Logging Architecture in an Interview

A strong answer:

> In OpenShift, I design logging as a pipeline. Logs are produced by application containers, platform components, and audit sources. A node-level Vector collector, managed by the Red Hat OpenShift Logging Operator, collects and enriches logs. ClusterLogForwarder defines which logs are selected, filtered, and routed. For local short-term troubleshooting, logs are stored in LokiStack, managed by the Loki Operator with S3-compatible object storage. For enterprise retention and security, important logs, especially audit logs, are forwarded to external SIEM or log analytics systems. The Cluster Observability Operator enables console-based log visualization. I design retention, RBAC, TLS, object storage, noisy log control, and multi-cluster forwarding as part of the architecture.

### 22.2 Scenario: Production App Team Says Logs Are Missing

Approach:

1. Confirm app writes to stdout/stderr.
2. Check `oc logs` for pod.
3. Check namespace is included in ClusterLogForwarder input.
4. Check filters are not dropping logs.
5. Check collector pod on the node.
6. Check collector logs.
7. Check Loki/external destination health.
8. Check RBAC and service account.

Commands:

```bash
oc logs -n <ns> <pod>
oc get pod -n <ns> <pod> -o wide
oc get pods -n openshift-logging -o wide | grep <node>
oc logs -n openshift-logging <collector-pod> --tail=200
oc get clusterlogforwarder -A -o yaml
```

### 22.3 Scenario: Security Wants 1-Year Audit Retention

Recommended answer:

- Do not keep 1 year only in in-cluster LokiStack.
- Forward audit logs to external SIEM/archive.
- Keep short local retention for operational troubleshooting.
- Ensure TLS/mTLS and RBAC.
- Validate ingestion with test events.
- Document retention and access controls.

### 22.4 Scenario: Logging Cost Is Too High

Actions:

1. Identify top log-producing namespaces.
2. Disable unnecessary DEBUG logs.
3. Drop health check and metrics scrape noise.
4. Reduce dev/test retention.
5. Avoid duplicating logs to multiple paid systems.
6. Review audit policy/filtering with security.
7. Review label cardinality and query patterns.
8. Educate app teams on structured logging.

### 22.5 Scenario: LokiStack Ready but Logs Not Appearing

Likely causes:

- Collector cannot connect to Loki.
- Missing object storage CA bundle.
- Object storage credentials wrong.
- NetworkPolicy blocks egress.
- ClusterLogForwarder output or pipeline misconfigured.
- UIPlugin missing if only console view is broken.

### 22.6 Scenario: Designing Logging for 20 OpenShift Clusters

Recommended design:

```text
Each cluster:
  - Local LokiStack for short troubleshooting retention
  - ClusterLogForwarder for routing
  - Audit logs to central SIEM
  - Critical app logs to central Kafka/Splunk
  - GitOps-managed configuration

Central:
  - SIEM/log analytics
  - Long-term archive
  - Dashboards and correlation
  - Compliance reporting
```

Key architecture decisions:

- Standard namespace labels.
- Standard retention tiers.
- Standard service account/RBAC.
- Per-environment destinations.
- Central certificate and secret rotation process.
- Common alerting for pipeline health.

## Practical Memory Points for Advanced OpenShift Administration

Remember these points for real production work and interviews:

1. **Logging is a pipeline, not a product.**
2. **Vector collects; ClusterLogForwarder routes; LokiStack stores; COO visualizes.**
3. **LokiStack is best treated as hot, short-term troubleshooting storage.**
4. **Audit logs should usually be forwarded externally.**
5. **Object storage and StorageClass are different LokiStack requirements.**
6. **RBAC is required for collection: application, infrastructure, and audit roles.**
7. **Collector runs on every log-producing node.**
8. **High-cardinality labels are one of the fastest ways to hurt Loki performance.**
9. **Retention must be explicit, or storage can grow unexpectedly.**
10. **GitOps should manage logging configuration in serious enterprise clusters.**
