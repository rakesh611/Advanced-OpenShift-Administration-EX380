## 1. Executive Summary

**SIEM integration** in OpenShift means collecting security-relevant telemetry from the OpenShift platform, Kubernetes control plane, node layer, application workloads, identity providers, network layer, image pipeline, and supporting operators, then forwarding that telemetry to a centralized **Security Information and Event Management** platform for correlation, alerting, investigation, compliance, and long-term retention.

In enterprise architecture, SIEM integration is not only a logging task. It is a **security control plane integration**. It connects OpenShift operations with the organization’s SOC, audit, compliance, incident response, and risk management functions.

A mature OpenShift SIEM architecture answers these questions:

- Who accessed the cluster?
- What API actions were performed?
- Which user created, deleted, patched, or escalated resources?
- Which service account was used?
- Which namespaces generated suspicious activity?
- Were privileged workloads created?
- Were secrets accessed or modified?
- Were RBAC bindings changed?
- Were network policies changed or bypassed?
- Did any operator, route, registry, ingress, node, or kubelet component show suspicious behavior?
- Can security teams correlate OpenShift activity with firewall, IAM, VPN, endpoint, cloud, and vulnerability data?

A 10-year experienced OpenShift administrator should design SIEM integration with the same seriousness as authentication, RBAC, networking, storage, and disaster recovery. Poor SIEM integration creates blind spots. Over-forwarding creates cost explosions. Incorrect filtering can remove evidence. Weak transport security can leak sensitive audit trails. Bad RBAC can stop the collector or overexpose logs.

## 2. What SIEM Integration Means in OpenShift Enterprise Architecture

At a simple level, SIEM integration means:

```text
OpenShift logs/events/audit records ---> Collector ---> Forwarder ---> SIEM
```

At enterprise scale, it becomes:

```text
+-------------------------+
| OpenShift Cluster       |
|                         |
|  Application Logs       |
|  Infrastructure Logs    |
|  Audit Logs             |
|  Security Events        |
|  Network Events         |
|  Operator Events        |
+-----------+-------------+
            |
            v
+-------------------------+
| OpenShift Logging       |
| Collector DaemonSet     |
| ClusterLogForwarder     |
| Filters / Pipelines     |
+-----------+-------------+
            |
            +--------------------+--------------------+-------------------+
            |                    |                    |                   |
            v                    v                    v                   v
      +-----------+        +-----------+        +-------------+     +--------------+
      | SIEM      |        | Loki      |        | Object      |     | Kafka / OTel |
      | Splunk    |        | Short-term|        | Archive     |     | Buffer       |
      | QRadar    |        | Ops Logs  |        | Compliance  |     | Gateway      |
      | Sentinel  |        +-----------+        +-------------+     +--------------+
      +-----------+
```

The important point is that **not every log should go to the same destination**. Enterprise architecture separates log consumers:

| Consumer | Needs | Typical Destination |
|---|---|---|
| Developers | Application debugging | Loki, Splunk app index, namespace-specific tools |
| SRE / Platform Team | Cluster troubleshooting | LokiStack, Elasticsearch, Splunk infra index |
| SOC / Security Team | Detection, investigation, correlation | SIEM |
| Compliance / Audit Team | Immutable retention | S3/object storage, WORM storage, archive SIEM index |
| Management / Risk Team | Dashboards and evidence | SIEM reports, GRC tooling |

A good design provides each team the right signal without exposing unnecessary sensitive data or wasting ingestion cost.

## 3. Why SIEM Integration Is Critical in Enterprise OpenShift

OpenShift is not just a container runtime. It is a full platform containing:

- Kubernetes API server
- OpenShift API server
- OAuth server
- Ingress/router layer
- Container runtime and node OS
- Machine configuration
- Operators
- Routes and services
- Service accounts and tokens
- Secrets and ConfigMaps
- RBAC
- SCC / Pod Security admission behavior
- Image registry and pull secrets
- CI/CD pipelines
- Storage integrations
- Network policies and SDN/OVN components

Because OpenShift centralizes workload deployment, identity, authorization, and infrastructure automation, it becomes a high-value security target.

### Key Threats SIEM Helps Detect

| Threat | Example Signal |
|---|---|
| Privilege escalation | New `cluster-admin` binding, use of privileged SCC |
| Unauthorized access | Failed OAuth login, unusual kubeconfig use |
| Secret theft | API access to Secret resources, unusual namespace access |
| Container breakout attempt | Privileged pod, hostPath mount, hostNetwork usage |
| Lateral movement | Service account token used across namespaces |
| Misconfiguration | NetworkPolicy deleted, route exposed externally |
| Malicious deployment | Suspicious image, unknown registry, crypto-mining process logs |
| Insider risk | Admin deletes audit-related resources or disables logging |
| Compliance violation | Missing audit retention, unencrypted forwarding, log gaps |
| Supply-chain issue | Pipeline deploys unapproved image or tag |

### SIEM as Part of Enterprise Defense-in-Depth

SIEM integration supports:

- **Detective controls:** Detect suspicious activity.
- **Forensic controls:** Preserve evidence for investigation.
- **Compliance controls:** Prove who did what and when.
- **Operational controls:** Alert on platform failures affecting security visibility.
- **Governance controls:** Map OpenShift activity to enterprise risk policies.

## 4. Core Architecture Components

A production SIEM integration usually has these layers:

```text
[Log Sources]
     |
     v
[Collection Layer]
     |
     v
[Filtering / Normalization Layer]
     |
     v
[Transport Layer]
     |
     v
[Buffer / Broker Layer - Optional]
     |
     v
[SIEM Ingestion Layer]
     |
     v
[Correlation / Detection / Retention]
```

### 4.1 Log Sources

OpenShift log sources include:

- Container stdout/stderr logs
- Node journal logs
- Kubernetes API audit logs
- OpenShift API audit logs
- OAuth audit logs
- `auditd` node logs
- OVN network audit logs
- Router/ingress logs
- Operator logs
- Events from namespaces
- Security tool events such as Compliance Operator, RHACS, Falco, image scanner, admission controllers

### 4.2 Collection Layer

In Red Hat OpenShift Logging, collection is performed by collector pods, usually deployed as a **DaemonSet**, so one collector pod runs on each node. This gives access to local node log files, container logs, and selected platform logs.

### 4.3 Filtering / Normalization Layer

This layer decides:

- Which logs are collected
- Which logs are dropped
- Which fields are removed
- Which metadata is added
- Which records are parsed as JSON
- Which streams are rate-limited
- Which logs go to which destination

### 4.4 Transport Layer

Common transport methods:

- HTTPS to Splunk HEC
- Syslog over TLS
- Kafka with SASL/TLS
- Generic HTTPS endpoint
- OTLP/HTTP to OpenTelemetry Collector
- Cloud-native APIs such as CloudWatch or Azure Monitor
- S3-compatible object storage for archive

### 4.5 SIEM Layer

Examples:

- Splunk Enterprise / Splunk Cloud
- IBM QRadar
- Microsoft Sentinel
- Elastic Security
- Google Security Operations
- ArcSight
- LogRhythm
- Securonix
- Chronicle-style security data lake

## 5. OpenShift Log and Security Event Sources

A senior administrator should understand exactly what OpenShift emits and why it matters.

### 5.1 Application Logs

Application logs are generated by user workloads in application namespaces.

Examples:

```text
Namespace: payments-prod
Pod: payment-api-7f98d8c77b-k2j9p
Container: payment-api
Log: failed login for user account_id=12345 from ip=10.20.30.40
```

Security value:

- App login failures
- Business fraud signals
- Application errors caused by attack attempts
- SQL injection traces
- Authentication bypass attempts
- API abuse
- Rate-limit violations

Design concern:

Application logs can contain PII, secrets, tokens, request bodies, customer data, or payment details. Do not blindly forward all application logs to a third-party SIEM without classification and masking/pruning controls.

### 5.2 Infrastructure Logs

Infrastructure logs come from OpenShift and Kubernetes components, node services, and system namespaces such as `openshift-*`, `kube-*`, and `default`.

Examples:

- kubelet logs
- CRI-O logs
- node journal logs
- router logs
- registry logs
- operator logs
- DNS logs
- Machine Config Operator logs
- Cluster Version Operator logs
- monitoring stack logs

Security value:

- Node pressure and abnormal restarts
- Unauthorized node-level changes
- Router exposure changes
- Operator failure or tampering
- Image pull issues
- Certificate trust failures
- API connectivity anomalies

### 5.3 Audit Logs

Audit logs are the most important security source for OpenShift SIEM integration.

Audit logs answer:

- Who called the API?
- What resource was requested?
- Which verb was used?
- Was the action allowed or denied?
- Which namespace and object were involved?
- Which user-agent was used?
- Which source IP made the request?
- Which service account was used?

Important audit sources:

- Kubernetes API server audit logs
- OpenShift API server audit logs
- OAuth server audit logs
- Node `auditd` logs
- OVN audit logs

High-value audit events:

| Event | Why it matters |
|---|---|
| `create clusterrolebinding` | Possible privilege escalation |
| `patch rolebinding` | Namespace-level privilege change |
| `get secret` | Possible secret access |
| `create pod` with privileged settings | Possible container escape attempt |
| `delete networkpolicy` | Possible lateral movement path |
| `create route` | External exposure |
| `delete clusterlogforwarder` | Logging tampering |
| `patch oauth` | Authentication tampering |
| `create serviceaccount token` | Credential creation |

### 5.4 Kubernetes Events

Kubernetes events are not the same as logs. They describe state transitions and warnings.

Examples:

```bash
oc get events -A --sort-by=.lastTimestamp
```

Security value:

- Failed scheduling due to policy
- Image pull failures from unknown registry
- BackOff events
- Admission denials
- Failed mounts
- Node readiness changes

Design note:

Events are useful but short-lived. If the enterprise requires long-term investigation, event forwarding must be explicitly designed through tooling because Kubernetes events are not durable by default.

### 5.5 OAuth and Identity Logs

OpenShift OAuth logs show authentication behavior.

Security value:

- Login failures
- Unexpected identity provider usage
- OAuth token issues
- kubeadmin usage
- Suspicious source IPs
- Brute force attempts

### 5.6 RBAC and Authorization Logs

RBAC-related audit records are among the highest-priority SIEM signals.

Watch these resources:

- `clusterroles`
- `clusterrolebindings`
- `roles`
- `rolebindings`
- `serviceaccounts`
- `secrets`
- `oauths`
- `groups`
- `users`

### 5.7 SCC and Pod Security Signals

OpenShift Security Context Constraints control what pods can do at runtime.

High-risk workload signals:

- `privileged: true`
- `hostNetwork: true`
- `hostPID: true`
- `hostIPC: true`
- `hostPath` volumes
- `runAsUser: 0`
- added Linux capabilities
- disabled SELinux confinement
- mounted service account token unexpectedly

### 5.8 Network and OVN Logs

Network security signals include:

- NetworkPolicy changes
- Egress firewall changes
- Route creation or deletion
- Ingress controller changes
- OVN ACL or policy-related logs
- DNS anomalies
- Service exposure changes

## 6. SIEM Integration Reference Architecture

### 6.1 Direct Forwarding Pattern

```text
OpenShift Collector ---> SIEM Endpoint
```

Use this when:

- One or two clusters
- SIEM endpoint is highly available
- Network path is reliable
- Ingestion rate is predictable
- Direct TLS connectivity is approved

Pros:

- Simple
- Lower latency
- Fewer components
- Easier to troubleshoot

Cons:

- SIEM outage may cause drops or backpressure depending on delivery mode
- Limited buffering
- Harder to fan out to many consumers
- Cluster-to-SIEM firewall rules needed from every node

### 6.2 Brokered Kafka Pattern

```text
OpenShift Collector ---> Kafka ---> SIEM Consumers
```

Use this when:

- Many clusters forward logs
- SIEM ingestion has variable availability
- SOC wants replay capability
- Logs must be enriched by intermediate processors
- Multiple downstream systems consume the same data

Pros:

- Decouples OpenShift from SIEM availability
- Supports replay
- Supports fan-out
- Better for high-volume environments

Cons:

- More operational complexity
- Kafka must be secured and monitored
- Additional cost
- More latency

### 6.3 Local Operations + Security Split Pattern

```text
Application + Infrastructure Logs ---> LokiStack / Ops Search
Audit + Security Logs -------------> SIEM
Audit Archive ---------------------> Object Storage
```

This is often the best enterprise pattern.

Benefits:

- Developers and SREs get fast operational troubleshooting.
- SOC receives high-value security events.
- Audit/compliance retains immutable records.
- SIEM ingestion cost is controlled.

### 6.4 Multi-Cluster Hub-Spoke Pattern

```text
Cluster A Collector ---+
Cluster B Collector ---+---> Regional Gateway/Kafka/OTel Collector ---> Enterprise SIEM
Cluster C Collector ---+
```

Use this when:

- Many OpenShift clusters exist across data centers or cloud regions
- Central SOC monitors all clusters
- Network segmentation requires regional aggregation
- Data sovereignty rules apply

## 7. OpenShift Logging and ClusterLogForwarder Architecture

Modern Red Hat OpenShift Logging uses the **ClusterLogForwarder** custom resource to define log forwarding behavior.

Conceptually:

```text
Input ---> Filter ---> Output
   \         |          /
    \        |         /
     +---- Pipeline ---+
```

### 7.1 Key ClusterLogForwarder Concepts

| Component | Purpose |
|---|---|
| `inputs` | Select log sources such as application, infrastructure, audit, or custom selectors |
| `filters` | Drop, prune, parse, enrich, or transform log records |
| `outputs` | Define destinations such as Splunk, syslog, Kafka, HTTP, Loki, S3 |
| `pipelines` | Connect inputs, filters, and outputs |
| `serviceAccount` | Identity used by collector to access logs |

### 7.2 Important API Version Note

Older OpenShift Logging examples often used:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
```

Newer Red Hat OpenShift Logging 6.x examples use:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
```

For production, always check the installed CRD version:

```bash
oc api-resources | grep -i clusterlogforwarder
oc explain clusterlogforwarder --api-version=observability.openshift.io/v1
oc get crd | grep -i clusterlogforwarder
```

### 7.3 Collector as DaemonSet

The collector usually runs as a DaemonSet so it can collect node-local logs from every node.

Check collector pods:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
```

Check DaemonSet:

```bash
oc get ds -n openshift-logging
```

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

## 8. Log Categories: Application, Infrastructure, and Audit

### 8.1 Application Input

Application logs come from user application containers.

Example input selecting production namespaces:

```yaml
inputs:
- name: prod-app-logs
  type: application
  application:
    includes:
    - namespace: payments-prod
    - namespace: orders-prod
    excludes:
    - namespace: dev-noisy
```

### 8.2 Infrastructure Input

Infrastructure logs include logs from system namespaces and node journals.

Example:

```yaml
pipelines:
- name: infra-to-siem
  inputRefs:
  - infrastructure
  outputRefs:
  - enterprise-siem
```

### 8.3 Audit Input

Audit logs are high-sensitivity and high-value.

Example:

```yaml
pipelines:
- name: audit-to-siem
  inputRefs:
  - audit
  outputRefs:
  - enterprise-siem
```

Before using `audit` in `inputRefs`, the collector service account must have permission to collect audit logs.

## 9. Audit Log Architecture and API Server Audit Policy

OpenShift supports configurable API server audit profiles.

Typical profiles:

| Profile | Description | Enterprise Use |
|---|---|---|
| `Default` | Metadata for read/write requests, limited request body logging | Recommended baseline |
| `WriteRequestBodies` | Adds request bodies for write operations | Useful for investigations but higher overhead |
| `AllRequestBodies` | Adds request bodies for read and write operations | Very high overhead, use carefully |
| `None` | Disables audit logging | Avoid in production |

### 9.1 Check Current Audit Profile

```bash
oc get apiserver cluster -o yaml | grep -A5 audit
```

Or:

```bash
oc get apiserver cluster -o jsonpath='{.spec.audit.profile}{"\n"}'
```

### 9.2 Configure Audit Profile

```bash
oc edit apiserver cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  audit:
    profile: Default
```

For a higher-detail investigation window:

```yaml
spec:
  audit:
    profile: WriteRequestBodies
```

### 9.3 Senior-Level Design Advice

Do not set `AllRequestBodies` across production for long periods unless there is a clear requirement and capacity approval. It can increase CPU, memory, disk I/O, storage, and SIEM ingestion cost.

A better model:

1. Use `Default` globally.
2. Use custom audit rules for specific groups if required.
3. Route audit logs separately from application logs.
4. Apply retention and immutability controls.
5. Monitor for audit pipeline failure.

### 9.4 Audit Events to Prioritize in SIEM

| Resource | Verb | Severity |
|---|---|---|
| `clusterrolebindings` | create/update/patch/delete | Critical |
| `clusterroles` | create/update/patch/delete | Critical |
| `rolebindings` | create/update/patch/delete | High |
| `secrets` | get/list/watch/create/update/delete | High/Critical |
| `serviceaccounts/token` | create | High |
| `pods` | create with risky security context | High |
| `routes` | create/update | Medium/High |
| `networkpolicies` | delete/patch | High |
| `oauths` | update/patch | Critical |
| `clusterlogforwarders` | update/delete | Critical |
| `apiservers` | update/patch | Critical |
| `machinesets` | update/delete | High |
| `nodes` | update/delete | High |

## 10. SIEM Destination Patterns

### 10.1 Splunk HEC

Best when:

- Enterprise uses Splunk
- HTTP Event Collector is approved
- Index routing is required
- Token-based ingestion is available

Design points:

- Use HTTPS.
- Store HEC token in Kubernetes Secret.
- Use separate tokens/indexes for app, infra, and audit.
- Use index naming standards.
- Add cluster labels.
- Rate-limit noisy streams.

### 10.2 Syslog over TLS

Best when:

- Existing SIEM expects syslog
- Security gateways or collectors already exist
- Network devices and Linux systems use common syslog flows

Design points:

- Prefer TLS over TCP/UDP.
- Use RFC5424 where possible.
- Avoid UDP for critical audit logs.
- Validate CA trust.
- Ensure firewall permits egress from all collector pods/nodes.

### 10.3 Kafka

Best when:

- Multi-cluster scale
- Replay required
- Multiple downstream consumers
- SIEM is not always available
- SOC data lake pattern exists

Design points:

- Use SASL/TLS.
- Partition by cluster/log type/namespace.
- Define retention by topic.
- Monitor consumer lag.
- Protect audit topics with strict ACLs.

### 10.4 Generic HTTP

Best when:

- Custom SIEM gateway
- Webhook collector
- OpenTelemetry Collector HTTP receiver
- Vendor-neutral ingestion gateway

Design points:

- Use mutual TLS if possible.
- Define schema contracts.
- Include tenant/cluster metadata.
- Handle retries and non-2xx responses.

### 10.5 OTLP / OpenTelemetry Gateway

Best when:

- Organization standardizes on OpenTelemetry
- Logs, metrics, and traces are centralized through OTel collectors
- Multiple vendor backends are used

Design points:

- Use regional OTel collectors.
- Enforce TLS.
- Normalize attributes.
- Route to SIEM, data lake, and observability platforms.

### 10.6 Object Storage Archive

Best when:

- Compliance requires long-term retention
- SIEM is too expensive for raw long-term logs
- Immutable/WORM retention is required

Design points:

- Use bucket versioning and object lock where available.
- Encrypt with enterprise KMS.
- Separate audit archive from app logs.
- Define lifecycle tiers.
- Maintain search strategy for investigations.

## 11. Enterprise Routing Strategy

A practical enterprise routing model:

```text
Application logs:
  - Prod critical apps ---> SIEM + Loki/Splunk app index
  - Non-prod apps -------> Loki only or low-cost storage
  - Noisy debug logs ----> drop/rate-limit

Infrastructure logs:
  - Core platform -------> SIEM + operations log store
  - Operator logs -------> operations log store, selected SIEM rules

Audit logs:
  - API audit -----------> SIEM + immutable archive
  - OAuth audit ---------> SIEM
  - auditd/OVN ----------> SIEM or security archive
```

### Recommended Index/Topic Strategy

| Log Type | SIEM Index / Kafka Topic Example |
|---|---|
| Audit | `ocp_audit_prod` |
| Infrastructure | `ocp_infra_prod` |
| Application critical | `ocp_app_critical_prod` |
| Non-prod app | `ocp_app_nonprod` |
| Security tools | `ocp_security_tools` |
| Platform admin actions | `ocp_admin_activity` |

### Required Metadata Fields

Every forwarded record should include or allow derivation of:

- cluster name
- cluster ID
- environment: prod/non-prod/dev
- region/data center
- namespace
- pod name
- container name
- node name
- log type
- source component
- user/service account where applicable
- audit verb/resource/namespace
- severity
- tenant/business unit

## 12. Security Boundary Design for SIEM Integration

SIEM integration crosses trust boundaries:

```text
OpenShift workload boundary
      |
OpenShift platform boundary
      |
Network/security zone boundary
      |
SOC/SIEM boundary
      |
Compliance/archive boundary
```

### 12.1 Trust Boundary Rules

1. Audit logs are security-sensitive data.
2. SIEM tokens are secrets and must not be visible to developers.
3. Collector service accounts must follow least privilege.
4. SIEM egress must be explicitly allowed.
5. Logs leaving the cluster must be encrypted.
6. Sensitive application fields must be pruned or masked where required.
7. Non-prod clusters should not share the same SIEM token/index as prod.
8. Security teams should be able to detect logging pipeline tampering.

### 12.2 Namespace Boundary

Keep logging resources in a controlled namespace:

```bash
oc get ns openshift-logging
```

Access to this namespace should be limited to platform administrators and authorized security administrators.

### 12.3 Administrative Boundary

Separate duties:

| Role | Permission |
|---|---|
| Platform Admin | Install logging operator, manage collectors |
| Security Admin | Define audit forwarding, SIEM routing requirements |
| SOC Analyst | Search SIEM, investigate alerts |
| Developer | View own application logs only |
| Compliance Officer | Access audit reports/archive |

## 13. RBAC and Service Account Design

The collector needs a service account. That service account must be granted explicit permissions for the log types it collects.

### 13.1 Create Collector Service Account

```bash
oc create sa collector -n openshift-logging
```

### 13.2 Grant Log Collection Roles

Application logs:

```bash
oc adm policy add-cluster-role-to-user collect-application-logs \
  system:serviceaccount:openshift-logging:collector
```

Infrastructure logs:

```bash
oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  system:serviceaccount:openshift-logging:collector
```

Audit logs:

```bash
oc adm policy add-cluster-role-to-user collect-audit-logs \
  system:serviceaccount:openshift-logging:collector
```

### 13.3 Verify RBAC Bindings

```bash
oc get clusterrolebinding -o wide | grep collect
```

### 13.4 Senior-Level Warning

If `ClusterLogForwarder` references a log type that the collector service account is not authorized to collect, the logging operator can remove or stop the collector DaemonSet as a protective behavior. In production, always create RBAC first, then apply the forwarding pipeline.

Correct sequence:

```text
1. Create service account
2. Create SIEM secret / CA secret
3. Grant collector ClusterRoleBindings
4. Apply ClusterLogForwarder
5. Verify collector pods
6. Verify SIEM receives logs
7. Enable alerts for pipeline health
```

## 14. TLS, Certificates, Secrets, and Trust Design

### 14.1 Secrets

SIEM credentials must be stored in Kubernetes Secrets.

Examples:

- Splunk HEC token
- HTTP bearer token
- Kafka SASL username/password
- Syslog client certificate
- CA bundle
- Cloud provider credentials

Create secret example:

```bash
oc create secret generic splunk-hec-secret \
  -n openshift-logging \
  --from-literal=hecToken='<SPLUNK_HEC_TOKEN>'
```

Never store SIEM tokens in:

- Git plaintext
- ConfigMaps
- YAML files committed to repositories
- Shell history
- Shared tickets
- Application namespaces

### 14.2 CA Trust

For HTTPS/TLS SIEM endpoints, the collector must trust the SIEM endpoint certificate.

Create CA secret example:

```bash
oc create secret generic siem-ca \
  -n openshift-logging \
  --from-file=ca-bundle.crt=./siem-ca.crt
```

### 14.3 mTLS Design

For high-security environments, use mutual TLS:

- SIEM validates collector client certificate.
- Collector validates SIEM server certificate.
- Certificates rotate through approved PKI process.
- Private keys are stored as secrets and access is restricted.

### 14.4 Certificate Rotation

Operational requirements:

- Track certificate expiry.
- Alert before expiry.
- Test rotation in non-prod.
- Validate collector reload behavior.
- Avoid expired SIEM CA bundles.

Commands:

```bash
oc get secret -n openshift-logging
oc describe secret siem-ca -n openshift-logging
oc get clusterlogforwarder instance -n openshift-logging -o yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector | grep -i cert
```

## 15. Network Design for SIEM Forwarding

### 15.1 Egress Path

Collectors usually run on every node. Therefore, network design must allow collector pods to reach SIEM endpoints.

Questions:

- Does every worker node need egress to SIEM?
- Is egress routed through a proxy?
- Is SIEM internal, DMZ, or SaaS?
- Which ports are required?
- Is DNS resolution available from collector pods?
- Is TLS inspection present?
- Are firewalls stateful?
- Is source NAT used?

### 15.2 Common Ports

| Destination | Port |
|---|---|
| Splunk HEC | 8088/TCP, often HTTPS |
| Syslog TLS | 6514/TCP |
| Syslog TCP | 514/TCP |
| Syslog UDP | 514/UDP |
| Kafka TLS | 9093/TCP |
| Kafka plaintext | 9092/TCP |
| HTTPS gateway | 443/TCP |
| OpenTelemetry HTTP | 4318/TCP |
| OpenTelemetry gRPC | 4317/TCP |

### 15.3 NetworkPolicy / Egress Control

For regulated environments, explicitly allow only required egress from `openshift-logging`.

Example conceptual policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-collector-to-siem
  namespace: openshift-logging
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/component: collector
  policyTypes:
  - Egress
  egress:
  - to:
    - ipBlock:
        cidr: 10.50.20.30/32
    ports:
    - protocol: TCP
      port: 8088
```

Note: In OpenShift using OVN-Kubernetes and enterprise network controls, you might also use egress firewall, admin network policy, firewall rules, proxy settings, or cluster-wide egress architecture depending on the platform standard.

### 15.4 DNS and Proxy

## 16. Data Classification and Sensitive Data Handling

Logs may contain sensitive data.

### 16.1 Sensitive Fields

Examples:

- Authorization headers
- Bearer tokens
- OAuth tokens
- Session IDs
- Customer data
- Email addresses
- PAN/payment data
- Aadhaar/PAN-like identity numbers
- Passwords accidentally logged by applications
- Secret names and secret values
- Internal hostnames
- IP addresses
- Request/response bodies

### 16.2 Data Classification Model

| Classification | Example | Forwarding Rule |
|---|---|---|
| Public | Generic app status | Can forward broadly |
| Internal | Namespace, pod, route names | Forward to internal tools |
| Confidential | User IDs, internal IPs | SIEM with access control |
| Restricted | Secrets, tokens, payment data | Mask/prune; avoid forwarding raw |
| Regulated | Audit logs, compliance records | SIEM + immutable archive |

### 16.3 Pruning Strategy

Use filters to remove high-risk fields before forwarding to SaaS or shared SIEM indexes.

Conceptual example:

```yaml
filters:
- name: prune-sensitive-fields
  type: prune
  prune:
    notIn:
    - .message
    - .kubernetes.namespace_name
    - .kubernetes.pod_name
    - .kubernetes.container_name
    - .level
```

Actual field names depend on your collector format and destination schema. Always validate with sample events.

### 16.4 Application Logging Policy

Application teams should follow rules:

- Never log passwords.
- Never log tokens.
- Never log full request bodies containing PII.
- Use structured JSON logs.
- Include correlation IDs.
- Include severity levels.
- Avoid debug logs in production.
- Mask sensitive values before writing to stdout.

## 17. Filtering, Pruning, Parsing, Enrichment, and Rate Limiting

### 17.1 Filtering

Filtering reduces noise and cost.

Examples to drop:

- debug logs
- health check logs
- known noisy namespaces
- temporary test workloads
- repeated benign warnings

But never drop without approval:

- audit records
- RBAC changes
- secret access
- route exposure
- security context changes
- authentication failures

### 17.2 Pruning

Pruning removes fields while keeping the event.

Use cases:

- Remove annotations that contain sensitive metadata.
- Remove labels that expose internal business info.
- Remove large Kubernetes metadata fields to reduce size.
- Remove request bodies before SaaS forwarding.

### 17.3 Parsing

Structured JSON logs are easier for SIEM correlation.

Good application log:

```json
{
  "timestamp": "2026-07-03T10:00:00Z",
  "level": "WARN",
  "service": "payment-api",
  "event": "login_failed",
  "user_id": "u-1234",
  "source_ip": "10.10.20.30",
  "correlation_id": "abc-xyz"
}
```

Poor application log:

```text
something failed for user maybe check later
```

### 17.4 Enrichment

Add metadata:

- cluster name
- environment
- data center
- business unit
- application owner
- compliance tier

Example pipeline label strategy:

```yaml
pipelines:
- name: audit-to-siem
  inputRefs:
  - audit
  outputRefs:
  - splunk-audit
  labels:
    cluster: ocp-prod-delhi-01
    environment: prod
    platform: openshift
```

Check your installed CRD with `oc explain` because exact field support may vary by version.

### 17.5 Rate Limiting

Rate limiting protects SIEM ingestion and cluster resources.

Example concept:

```yaml
inputs:
- name: limited-app-logs
  type: application
  application:
    tuning:
      rateLimitPerContainer:
        maxRecordsPerSecond: 100
```

Output rate limit concept:

```yaml
outputs:
- name: limited-splunk
  type: splunk
  splunk:
    url: https://splunk.example.com:8088
    authentication:
      token:
        secretName: splunk-hec-secret
        key: hecToken
  rateLimit:
    maxRecordsPerSecond: 1000
```

Senior-level warning: when rate limits are exceeded, excess records can be dropped. Monitor rate-limit metrics and tune carefully.

## 24. Capacity Planning for SIEM Log Forwarding

### 24.1 Sizing Dimensions

Estimate:

- number of nodes
- number of pods
- log lines per second per pod
- average log event size
- audit event rate
- peak deployment windows
- incident surge volume
- retention period
- SIEM ingest license cost
- network bandwidth
- collector CPU/memory

### 24.2 Formula

```text
Daily Volume GB = Events per second × Average event size bytes × 86400 / 1024^3
```

Example:

```text
5,000 events/sec × 800 bytes × 86400 / 1024^3
≈ 321 GB/day
```

If SIEM cost is based on GB/day, this is a major architecture concern.

### 24.3 Volume Control

Reduce unnecessary ingestion by:

- filtering debug logs
- pruning large metadata
- using namespace-specific routing
- keeping non-prod out of expensive SIEM indexes
- sending raw archive to object storage
- summarizing low-value logs
- using rate limits carefully

### 24.4 Audit Log Cost

Audit logs can be very high volume, especially with:

- many controllers
- GitOps tools
- monitoring tools
- CI/CD pipelines
- autoscalers
- service mesh
- frequent watches/lists

Do not enable extremely verbose audit profiles without capacity review.

## 25. High Availability and Failure Handling

### 25.1 Failure Types

| Failure | Example | Impact |
|---|---|---|
| Collector failure | DaemonSet pod crash | Node logs missing |
| SIEM endpoint down | HEC unavailable | Delivery failures/drops |
| Network outage | Firewall/DNS issue | No forwarding |
| Token expired | HEC token invalid | Authentication failure |
| CA expired | TLS validation failure | Delivery failure |
| Rate limit exceeded | Too much log volume | Records dropped |
| Bad CLF config | invalid CR | Collector not configured |
| Missing RBAC | unauthorized input | Collector stopped/removed |

### 25.2 Delivery Mode

Some outputs support delivery tuning such as `AtLeastOnce` and `AtMostOnce`.

| Mode | Meaning | Risk |
|---|---|---|
| `AtLeastOnce` | Retries can resend records | Possible duplicates |
| `AtMostOnce` | Prioritizes throughput | Possible loss |

For audit logs, prefer stronger delivery semantics where supported, but understand that exact semantics depend on destination/output type and collector behavior.

### 25.3 Health Monitoring

Monitor:

- collector pod readiness
- collector restarts
- ClusterLogForwarder status conditions
- output error counters
- rate-limited/dropped records
- SIEM ingestion rate
- Kafka lag if used
- archive write failures
- certificate expiration

## 27. Detection Engineering for OpenShift SIEM

### 27.1 Critical Detection Rules

#### Rule 1: Cluster Admin Binding Created

Logic:

```text
objectRef.resource=clusterrolebindings
verb=create
requestObject.roleRef.name=cluster-admin
```

Severity: Critical

Response:

1. Identify user.
2. Confirm change ticket.
3. Review source IP and user agent.
4. Check whether new subject is user/group/serviceaccount.
5. Revoke if unauthorized.
6. Investigate subsequent activity.

#### Rule 2: Secret Access by Human User

Logic:

```text
objectRef.resource=secrets
verb IN (get,list,watch)
user.username NOT LIKE system:serviceaccount:*
```

Severity: High/Critical

#### Rule 3: Privileged Pod Created

Logic:

```text
objectRef.resource=pods
verb=create
requestObject.spec.containers.securityContext.privileged=true
```

Severity: High

#### Rule 4: NetworkPolicy Deleted in Production

Logic:

```text
objectRef.resource=networkpolicies
verb=delete
objectRef.namespace MATCHES *-prod
```

Severity: High

#### Rule 5: Logging Pipeline Tampering

Logic:

```text
objectRef.resource IN (clusterlogforwarders, clusterloggings, subscriptions, secrets)
objectRef.namespace=openshift-logging
verb IN (update,patch,delete)
```

Severity: Critical

#### Rule 6: Audit Profile Disabled

Logic:

```text
objectRef.resource=apiservers
verb IN (update,patch)
requestObject.spec.audit.profile=None
```

Severity: Critical

#### Rule 7: Suspicious Service Account Token Creation

Logic:

```text
objectRef.resource=serviceaccounts
subresource=token
verb=create
namespace=prod
```

Severity: High

#### Rule 8: Route Created for Sensitive Namespace

Logic:

```text
objectRef.resource=routes
verb=create
objectRef.namespace IN (payments-prod, identity-prod, admin-prod)
```

Severity: Medium/High

#### Rule 9: Pod with hostPath Mount

Logic:

```text
objectRef.resource=pods
verb=create
requestObject.spec.volumes.hostPath exists
```

Severity: High

#### Rule 10: Kubeadmin Usage

Logic:

```text
user.username=kubeadmin
```

Severity: High/Critical in mature enterprise

## 30. Troubleshooting Guide

### 30.1 ClusterLogForwarder Not Ready

Check:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml
```

Look at:

- `status.conditions`
- validation errors
- unauthorized inputs
- missing secrets
- incorrect output fields
- invalid URL
- unsupported output type

### 30.2 Collector Pods Missing

Possible causes:

- Missing RBAC for requested input
- Invalid ClusterLogForwarder config
- Logging operator issue
- Namespace/CRD mismatch

Commands:

```bash
oc get pods -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp
oc get clusterrolebinding -o wide | grep collect
```

### 30.3 No Logs in SIEM

Check:

1. Collector running?
2. CLF Ready=True?
3. SIEM secret correct?
4. CA trust correct?
5. Firewall open?
6. DNS resolves?
7. SIEM HEC/syslog listener healthy?
8. Index/topic exists?
9. Time range correct in SIEM search?
10. Are filters dropping logs?

### 30.4 TLS Certificate Errors

Collector log symptoms:

```text
certificate verify failed
unknown authority
self-signed certificate in certificate chain
x509: certificate has expired
```

Fix:

- Confirm correct CA secret.
- Confirm key name matches config.
- Confirm SIEM certificate chain.
- Confirm endpoint hostname matches certificate SAN.
- Rotate expired certificates.

Commands:

```bash
oc get secret splunk-ca -n openshift-logging -o yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector | grep -i x509
```

### 30.5 Authentication Failure

Symptoms:

```text
401 Unauthorized
403 Forbidden
invalid token
authentication failed
```

Fix:

- Validate HEC token.
- Validate Kafka SASL credentials.
- Validate HTTP bearer token.
- Confirm secret key name.
- Confirm token is allowed for target index.
- Rotate token if compromised.

### 30.6 Rate-Limited or Dropped Logs

Symptoms:

- SIEM volume lower than expected
- collector logs mention dropped records
- metrics show rate limited events

Fix:

- Increase limit if approved.
- Filter noisy logs earlier.
- Separate high-volume apps.
- Use Kafka buffer.
- Increase SIEM license/capacity.

### 30.7 Duplicate Logs

Possible causes:

- Multiple pipelines sending same input to same output
- AtLeastOnce retry after crash
- SIEM relay duplication
- Kafka consumer replay

Fix:

- Review pipeline design.
- Use event IDs or hashes for deduplication.
- Separate outputs clearly.
- Check broker replay behavior.

### 30.8 Missing Audit Logs Only

Possible causes:

- `collect-audit-logs` role missing
- `audit` not in `inputRefs`
- audit profile changed
- filter accidentally drops audit logs
- SIEM index routing issue

Commands:

```bash
oc get clusterrolebinding -o wide | grep collect-audit
oc get clusterlogforwarder instance -n openshift-logging -o yaml | grep -A5 audit
oc get apiserver cluster -o yaml | grep -A10 audit
```

## 32. Common Enterprise Mistakes

### Mistake 1: Forwarding Everything to SIEM

This causes cost explosion and alert fatigue.

Better:

- Send high-value security logs to SIEM.
- Send operational logs to Loki or cheaper storage.
- Archive raw audit logs separately.

### Mistake 2: Ignoring Audit Logs

Application logs alone are not enough. API audit logs are mandatory for security investigation.

### Mistake 3: Using UDP Syslog for Critical Audit Logs

UDP can lose logs silently. Use TLS/TCP or a broker.

### Mistake 4: Not Adding Cluster Metadata

Without cluster labels, SOC cannot distinguish prod from non-prod or identify source environment.

### Mistake 5: Giving Developers Access to Raw Audit Logs

Audit logs can expose sensitive user, namespace, and access details. Access must be restricted.

### Mistake 6: Applying ClusterLogForwarder Before RBAC

This can break collection if the service account lacks required permissions.

### Mistake 7: No Alert for Logging Pipeline Failure

A SIEM integration that silently fails is a security blind spot.

### Mistake 8: No Certificate Rotation Process

Expired CA or endpoint certificates are a common cause of sudden SIEM outage.

### Mistake 9: No Data Masking Policy

Application logs can leak sensitive data. SIEM is not a dumping ground for raw application output.

### Mistake 10: No Detection Engineering

Forwarding logs without rules, dashboards, and response procedures gives limited security value.

## 33. Interview and Real-World Scenario Questions

### Q1. What is SIEM integration in OpenShift?

It is the architecture and configuration used to collect application, infrastructure, audit, and security-related logs from OpenShift and forward them to a centralized SIEM for detection, investigation, compliance, and retention.

### Q2. Which OpenShift logs are most important for security?

Audit logs are most important because they show API activity: who performed what action, on which resource, from where, and whether it succeeded. Infrastructure logs, OAuth logs, RBAC changes, route changes, pod security context changes, and application security logs are also important.

### Q3. What is ClusterLogForwarder?

ClusterLogForwarder is the OpenShift Logging custom resource that defines log inputs, filters, outputs, and pipelines. It controls how collected logs are routed to destinations such as Splunk, syslog, Kafka, Loki, HTTP endpoints, cloud logging services, or object storage.

### Q4. Why should audit logs be routed separately?

Audit logs are sensitive, high-value, often high-volume, and compliance-relevant. They require stronger access control, longer retention, tamper detection, and sometimes immutable archival. They should not be mixed casually with developer application logs.

### Q5. What happens if the collector service account does not have permission for a requested log type?

In newer OpenShift Logging behavior, the operator can place the collector in a protective failure state or remove/stop the collector DaemonSet, which stops log collection. Therefore, RBAC must be created before referencing a log type in ClusterLogForwarder.

### Q6. How would you integrate OpenShift with Splunk?

Use OpenShift Logging Operator, create a collector service account, bind required collect roles, create a Kubernetes Secret containing the Splunk HEC token, configure TLS CA trust, create a ClusterLogForwarder with Splunk output, define pipelines for audit/infrastructure/application logs, apply it, then verify collector status and Splunk ingestion.

### Q7. Why use Kafka between OpenShift and SIEM?

Kafka decouples OpenShift from SIEM availability, supports buffering, replay, multiple consumers, and high-volume multi-cluster ingestion. It is useful for large enterprise environments.

### Q8. How do you prevent SIEM cost explosion?

Use routing, filtering, pruning, rate limiting, namespace selection, log classification, short-term operational storage, and long-term low-cost archive. Do not send all debug and non-prod logs to expensive SIEM indexes.

### Q9. What alerts should SOC create for OpenShift?

Critical alerts include cluster-admin binding creation, secret access by human users, privileged pod creation, network policy deletion, audit profile disabled, logging pipeline modification, suspicious service account token creation, and kubeadmin usage.

### Q10. How do you troubleshoot missing logs in SIEM?

Check ClusterLogForwarder status, collector pods, collector logs, RBAC, secrets, TLS CA, network connectivity, SIEM endpoint health, indexes/topics, filters, and rate limits. Generate a test event and trace it end-to-end.

## Final Senior Architect Summary

For enterprise OpenShift, SIEM integration is not just “send logs to Splunk.” It is a production-grade security observability architecture.

A strong design has:

- clearly separated application, infrastructure, and audit pipelines;
- least-privilege collector service account permissions;
- TLS-protected forwarding;
- SIEM token and CA secret management;
- network egress control;
- filtering and pruning for cost and privacy;
- immutable audit archive where required;
- multi-cluster metadata enrichment;
- monitoring of collector health and SIEM ingestion;
- detection rules for RBAC, secrets, privileged pods, routes, network policy, and logging tampering;
- documented operational and incident response runbooks.

A 10-year experienced OpenShift administrator should always design SIEM integration with security, compliance, availability, scalability, and cost in mind.
