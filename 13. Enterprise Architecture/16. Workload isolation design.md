# Workload Isolation Design in Enterprise Architecture for Advanced OpenShift Administration

**Audience:** Senior Linux / Kubernetes / OpenShift administrators, platform engineers, SREs, and enterprise architects with around 10 years of infrastructure experience.  
**Scope:** Red Hat OpenShift Container Platform 4.x, especially enterprise/self-managed clusters.  
**Goal:** Design workload isolation so that applications, teams, environments, security zones, and platform components can safely share OpenShift without causing security exposure, noisy-neighbor impact, unstable upgrades, or operational confusion.

---

## 1. What Workload Isolation Means

Workload isolation is the design practice of separating workloads so that one workload, team, tenant, environment, or failure domain cannot negatively impact another beyond an accepted level.

In OpenShift, isolation is not a single feature. It is a layered design using:

- **Projects / namespaces** for administrative and logical separation.
- **RBAC** for user and service account permission boundaries.
- **Security Context Constraints (SCCs)** and Pod Security Admission behavior for runtime privilege control.
- **NetworkPolicy, EgressFirewall, egress IPs, and ingress sharding** for traffic isolation.
- **Node labels, taints, tolerations, node selectors, affinity, anti-affinity, and topology spread constraints** for compute placement.
- **ResourceQuota, LimitRange, requests, limits, PriorityClass, and autoscaling** for resource fairness.
- **StorageClass, PVC quotas, storage topology, encryption, and backup boundaries** for storage isolation.
- **Monitoring, logging, audit, chargeback, and policy management** for operational isolation.
- **Separate clusters** where namespace/node-level isolation is not enough.

A strong enterprise design assumes that isolation must protect against three kinds of risk:

1. **Security risk:** unauthorized access, privilege escalation, lateral movement, secret leakage, image compromise, or unexpected traffic paths.
2. **Reliability risk:** noisy-neighbor CPU/memory/storage/network consumption, scheduling starvation, failing nodes, broken operators, or unsafe pod disruption.
3. **Governance risk:** unclear ownership, uncontrolled self-service, noncompliant configuration, lack of audit evidence, and uncontrolled cost growth.

## 2. Enterprise Architecture View

### 2.1 Workload isolation is a business design, not only a Kubernetes design

Before choosing OpenShift objects, first classify workloads from a business and risk point of view.

Typical classification dimensions:

| Dimension | Questions to ask | Isolation impact |
|---|---|---|
| Business criticality | Is this revenue, citizen service, defence, banking, internal IT, test, or sandbox? | Critical workloads may need dedicated node pools, stricter PDBs, reserved capacity, and controlled release windows. |
| Environment | Is this dev, QA, UAT, pre-prod, prod, DR, or lab? | Production normally requires separate projects and often separate clusters from non-prod. |
| Tenant/team | Which application team owns it? | Determines project naming, RBAC, quota, monitoring, and chargeback boundaries. |
| Security zone | Internet-facing, internal, regulated, PCI, restricted, classified, management, build, or shared services? | Determines network policy, ingress/egress controls, route sharding, SCC rules, and node placement. |
| Runtime privilege | Does it need root, host network, hostPath, privileged mode, custom capabilities, device access, GPU, SR-IOV, or local storage? | May need dedicated service accounts, custom SCC, node pools, and strict approval. |
| Resource profile | CPU-heavy, memory-heavy, latency-sensitive, storage-heavy, batch, CI/CD, AI/GPU, database, or stateless web? | Determines node sizing, topology, quotas, limits, and autoscaling design. |
| Availability requirement | RTO/RPO, SLA, maintenance tolerance, zone redundancy, disaster recovery? | Determines topology spread, anti-affinity, PDB, replica count, backup and multi-cluster design. |
| Compliance | Audit, encryption, retention, external firewall allowlisting, data sovereignty? | Determines logging/audit retention, egress IP, encryption, backup, namespace policy, and cluster separation. |

A senior OpenShift administrator should never start with only `oc label node`. First define the isolation objective, then map it to platform controls.

## 3. Isolation Levels

OpenShift supports several practical isolation levels. The right level depends on trust, risk, performance, and cost.

### 3.1 Level 1: Logical isolation by project

Use when teams are trusted within the same organization and workloads do not need hard compute separation.

Controls:

- Separate projects / namespaces.
- RBAC per team.
- ResourceQuota and LimitRange.
- Default-deny NetworkPolicy.
- Dedicated service accounts.
- Image pull secrets scoped to the project.
- Project-level monitoring and alert ownership.

Suitable for:

- Dev and QA teams.
- Internal business applications.
- Shared non-regulated workloads.
- Training and lab environments.

Not enough for:

- Strongly regulated workloads.
- Untrusted tenants.
- Workloads requiring privileged access.
- Strict latency or noisy-neighbor protection.

### 3.2 Level 2: Logical + network + resource isolation

Use when teams share compute nodes but must have strong traffic and resource boundaries.

Additional controls:

- Default-deny ingress and egress NetworkPolicy.
- EgressFirewall for external destination control.
- Egress IP for fixed source IP requirements.
- Strict quota and object count limits.
- LimitRange enforcing default requests and limits.
- Admission policy to require labels, resource requests, probes, and non-root runtime.

Suitable for:

- Multiple internal production applications.
- Shared enterprise platform with strong governance.
- Workloads that can share worker nodes safely.

### 3.3 Level 3: Dedicated node pool isolation

Use when workloads need stronger compute separation.

Additional controls:

- Dedicated MachineSets / MachinePools.
- Node labels representing workload class, tenant, compliance zone, or hardware type.
- Taints on dedicated nodes.
- Tolerations only on approved workloads.
- Project node selector to force namespace workloads onto approved nodes.
- Quota and PriorityClass to avoid starvation.
- Dedicated ingress router shard if traffic isolation is needed.

Suitable for:

- Production vs non-production separation.
- PCI or regulated apps.
- Database workloads.
- CI/CD build farms.
- GPU or special hardware workloads.
- Latency-sensitive services.

### 3.4 Level 4: Dedicated cluster isolation

Use when namespace/node isolation is insufficient.

Typical reasons:

- Different security trust domains.
- Regulatory requirement for hard separation.
- Different upgrade cadence.
- Different identity provider or audit boundary.
- High blast-radius concern.
- Very large workload requiring independent scaling.
- Separate business unit or customer tenancy.

Examples:

- One cluster for prod, one for non-prod.
- Separate cluster for internet-facing DMZ workloads.
- Separate cluster for PCI/cardholder workloads.
- Separate cluster for management tooling such as ACM, GitOps, ACS, and shared observability.

### 3.5 Level 5: Multi-cluster / hub-spoke isolation

Use when the enterprise operates many clusters across regions, data centers, business units, or cloud providers.

Controls:

- Red Hat Advanced Cluster Management or equivalent governance.
- GitOps-based cluster policy.
- Central identity and RBAC mapping.
- Central observability with per-cluster isolation.
- Cluster sets for environment, region, or business unit.
- Standard namespace, network, quota, SCC, and compliance policy templates.

## 4. Key Design Principle: Isolation Must Be Layered

A common beginner mistake is to think:

> “I created a namespace, so the workload is isolated.”

A namespace alone is not enough. By default, workloads might still communicate, compete for resources, and use service accounts with too much permission.

A mature OpenShift design layers isolation like this:

```text
Enterprise policy
   ↓
Cluster boundary
   ↓
Project / namespace boundary
   ↓
RBAC and service account boundary
   ↓
Pod security / SCC boundary
   ↓
Network ingress/egress boundary
   ↓
Node placement / taint boundary
   ↓
Quota / limit / autoscaling boundary
   ↓
Storage / backup / data boundary
   ↓
Monitoring / audit / governance boundary
```

Every important workload should have an isolation profile. Example:

```yaml
workloadIsolationProfile:
  application: payment-api
  environment: prod
  tenant: finance
  securityZone: restricted-internal
  computeIsolation: dedicated-node-pool
  networkIsolation: default-deny-plus-approved-ingress-egress
  runtimeSecurity: restricted-v2-or-custom-nonroot-scc
  storageIsolation: encrypted-rwo-gold-storageclass
  ingressIsolation: finance-private-router-shard
  egressControl: egress-ip-and-egress-firewall
  quotaModel: gold-prod-quota
  observability: finance-prod-dashboard-and-alerts
  backup: app-aware-backup-with-rpo-15m
```

## 5. Namespace / Project Isolation

### 5.1 Purpose

Projects are the first logical boundary in OpenShift. A project is an OpenShift-managed namespace with additional metadata and user-facing behavior.

Use projects to separate:

- Applications.
- Environments.
- Teams.
- Tenants.
- Security zones.
- Build pipelines.
- Platform components.

### 5.2 Recommended naming standard

A clear naming standard reduces mistakes during incident response and automation.

Recommended format:

```text
<business-unit>-<app>-<environment>
```

Examples:

```text
fin-payment-prod
fin-payment-uat
hr-portal-dev
platform-monitoring-prod
sec-tools-prod
build-jenkins-prod
```

For large enterprises:

```text
<region>-<business-unit>-<app>-<environment>
```

Example:

```text
in-delhi-fin-payment-prod
```

### 5.3 Namespace labels

Labels are important because NetworkPolicy, IngressController sharding, GitOps, policy engines, and observability tools can select namespaces by labels.

Example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: fin-payment-prod
  labels:
    environment: prod
    business-unit: finance
    app.kubernetes.io/part-of: payment
    isolation.openshift.io/tier: gold
    security-zone: restricted-internal
    network-policy: default-deny
    owner: platform-team
  annotations:
    openshift.io/display-name: Finance Payment Production
    openshift.io/description: Production namespace for Finance Payment API
```

### 5.4 Project node selector

A project node selector constrains pods created in that project to nodes with matching labels. This is useful when an entire namespace must run only on approved nodes.

Example:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: fin-payment-prod
  annotations:
    openshift.io/node-selector: workload-tier=gold,security-zone=restricted
```

Node labels:

```bash
oc label node worker-gold-1 workload-tier=gold security-zone=restricted
oc label node worker-gold-2 workload-tier=gold security-zone=restricted
oc label node worker-gold-3 workload-tier=gold security-zone=restricted
```

Important design note:

- Project node selector is good for namespace-wide placement.
- It is not enough for hard isolation if the target nodes are not tainted.
- Without taints, other workloads can still land on those nodes if they use matching selectors or if selectors are too broad.

Recommended enterprise pattern:

```text
Project node selector + node taint + workload toleration + RBAC/admission control
```

## 6. RBAC Isolation

### 6.1 Purpose

RBAC controls who can do what in the cluster or project.

Typical enterprise roles:

| Role | Scope | Typical permission |
|---|---|---|
| Platform admin | Cluster | Full cluster administration. |
| Security admin | Cluster or selected namespaces | Security policy, audit, SCC review, network policy review. |
| App admin | Project | Manage deployments, services, routes, config, secrets inside app project. |
| Developer | Project | Deploy and troubleshoot app resources, but not modify security boundaries. |
| Viewer | Project | Read-only access for support, audit, or business teams. |
| CI/CD service account | Project or selected namespaces | Deploy only required resources. |

### 6.2 Design rules

1. Avoid giving `cluster-admin` to application teams.
2. Prefer project-scoped roles over cluster-scoped roles.
3. Use groups from LDAP/OIDC/IdP instead of individual users.
4. Use separate service accounts for runtime, deployment pipeline, backup, monitoring, and jobs.
5. Avoid using the `default` service account for production workloads.
6. Review RBAC regularly with audit evidence.

### 6.3 Example RBAC model

```bash
# Finance developers can edit only the UAT project
oc adm policy add-role-to-group edit finance-devs -n fin-payment-uat

# Finance production operators can view production
oc adm policy add-role-to-group view finance-ops -n fin-payment-prod

# A controlled deployment service account can deploy to prod
oc create sa deployer -n fin-payment-prod
oc adm policy add-role-to-user edit system:serviceaccount:fin-payment-prod:deployer -n fin-payment-prod
```

### 6.4 Anti-pattern

Do not give a CI/CD tool broad cluster access just because deployment is failing. Fix the exact missing permission.

Bad:

```bash
oc adm policy add-cluster-role-to-user cluster-admin system:serviceaccount:ci:jenkins
```

Better:

```bash
oc adm policy add-role-to-user edit system:serviceaccount:ci:jenkins -n fin-payment-uat
oc adm policy add-role-to-user edit system:serviceaccount:ci:jenkins -n fin-payment-prod
```

Even better in regulated environments:

- CI can deploy to dev and UAT.
- Production deployment is performed by GitOps controller with controlled approval.
- Human developers have view-only access to production.

## 7. Compute Isolation

Compute isolation controls where pods run and how much CPU, memory, and node capacity they can consume.

### 7.1 Node label strategy

Design node labels carefully. Labels become part of your architecture API.

Recommended categories:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
workload-tier=gold|silver|bronze
security-zone=restricted|internal|dmz|shared
hardware-profile=standard|memory-optimized|cpu-optimized|gpu|storage
business-unit=finance|hr|platform|security
failure-domain=zone-a|zone-b|zone-c
lifecycle=prod|nonprod|sandbox
```

Example:

```bash
oc label node worker01 workload-tier=gold security-zone=restricted hardware-profile=standard lifecycle=prod
oc label node worker02 workload-tier=gold security-zone=restricted hardware-profile=standard lifecycle=prod
oc label node worker03 workload-tier=gold security-zone=restricted hardware-profile=standard lifecycle=prod
```

### 7.2 Taints and tolerations

A taint tells the scheduler: “Do not schedule normal pods here unless they explicitly tolerate this taint.”

Example dedicated finance node pool:

```bash
oc adm taint nodes -l business-unit=finance dedicated=finance:NoSchedule
```

Application toleration:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: fin-payment-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      serviceAccountName: payment-api-sa
      tolerations:
      - key: dedicated
        operator: Equal
        value: finance
        effect: NoSchedule
      nodeSelector:
        business-unit: finance
        lifecycle: prod
      containers:
      - name: payment-api
        image: registry.example.com/finance/payment-api:1.0.0
        resources:
          requests:
            cpu: "500m"
            memory: "512Mi"
          limits:
            cpu: "1"
            memory: "1Gi"
```

### 7.3 Taint effects

| Effect | Meaning | Enterprise use |
|---|---|---|
| `NoSchedule` | New pods that do not tolerate the taint will not be scheduled on the node. | Most common for dedicated node pools. |
| `PreferNoSchedule` | Scheduler tries to avoid the node but may still place pods there. | Soft isolation; not suitable for strict tenancy. |
| `NoExecute` | Existing pods without toleration are evicted. | Strong isolation and node evacuation scenarios; use carefully. |

For production isolation, prefer `NoSchedule` unless you intentionally want eviction behavior.

### 7.4 Node selector vs node affinity

#### Node selector

Simple and strict:

```yaml
nodeSelector:
  workload-tier: gold
  lifecycle: prod
```

Good for simple placement.

#### Node affinity

More expressive:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: analytics-worker
spec:
  replicas: 3
  selector:
    matchLabels:
      app: analytics-worker
  template:
    metadata:
      labels:
        app: analytics-worker
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: hardware-profile
                operator: In
                values:
                - memory-optimized
                - cpu-optimized
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: workload-tier
                operator: In
                values:
                - gold
      containers:
      - name: worker
        image: registry.example.com/analytics/worker:1.0
```

Use node affinity when:

- Multiple acceptable node classes exist.
- You want mandatory and preferred placement rules.
- You need more expressive matching.

### 7.5 Pod anti-affinity

Pod anti-affinity prevents replicas from landing together, reducing single-node failure impact.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - payment-api
            topologyKey: kubernetes.io/hostname
      containers:
      - name: payment-api
        image: registry.example.com/finance/payment-api:1.0.0
```

This keeps replicas on different nodes.

### 7.6 Topology spread constraints

Topology spread constraints distribute pods across zones, racks, nodes, or other topology labels.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 6
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment-api
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: payment-api
      containers:
      - name: payment-api
        image: registry.example.com/finance/payment-api:1.0.0
```

Design note:

- Use `DoNotSchedule` only when capacity is guaranteed.
- Use `ScheduleAnyway` when availability preference should not block deployments.

### 7.7 Dedicated MachineSets / MachinePools

For real enterprise compute isolation, create dedicated compute pools instead of manually labeling random nodes.

Example node pool categories:

| Pool | Purpose | Labels | Taints |
|---|---|---|---|
| worker-general | Shared apps | `workload-tier=silver` | none or soft taint |
| worker-prod-gold | Critical production apps | `workload-tier=gold,lifecycle=prod` | `dedicated=prod-gold:NoSchedule` |
| worker-finance | Finance regulated workloads | `business-unit=finance,security-zone=restricted` | `dedicated=finance:NoSchedule` |
| worker-build | CI/CD builds | `workload-type=build` | `dedicated=build:NoSchedule` |
| worker-gpu | AI/GPU workloads | `hardware-profile=gpu` | `nvidia.com/gpu=true:NoSchedule` or dedicated taint |
| infra | Router, registry, monitoring, platform infra | `node-role.kubernetes.io/infra=` | `node-role.kubernetes.io/infra=:NoSchedule` |
| storage | ODF/local storage | `cluster.ocs.openshift.io/openshift-storage=` or storage-specific labels | storage-specific taints |

## 8. Infrastructure Node Isolation

### 8.1 Purpose

Infrastructure nodes separate platform infrastructure components from user workloads.

Common components placed on infra nodes:

- Ingress routers.
- Internal image registry.
- Monitoring stack.
- Logging stack.
- Some platform operators.
- GitOps/ACM/ACS components, depending on architecture and support rules.

### 8.2 Why infra isolation matters

Without infra nodes:

- User workloads can compete with routers and monitoring.
- Heavy apps can impact ingress latency.
- Monitoring can become unstable during app resource spikes.
- Platform components may be harder to size and troubleshoot.
- Subscription/capacity accounting may be affected depending on Red Hat rules and component eligibility.

### 8.3 Infra node label and taint pattern

Example:

```bash
oc label node infra01 node-role.kubernetes.io/infra=
oc label node infra02 node-role.kubernetes.io/infra=
oc label node infra03 node-role.kubernetes.io/infra=

oc adm taint nodes -l node-role.kubernetes.io/infra node-role.kubernetes.io/infra=:NoSchedule
```

Router placement example:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  replicas: 3
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
```

### 8.4 Design caution

Do not taint infra nodes and assume all platform components will automatically tolerate the taint. Confirm every operator-managed component has proper node placement and tolerations before applying strict taints.

Recommended process:

1. Create infra nodes.
2. Label infra nodes.
3. Configure router, registry, monitoring, logging, and selected operators to target infra nodes.
4. Verify pods move successfully.
5. Apply taint.
6. Re-verify no critical DaemonSet or operator pod is pending.
7. Add alerting for infra node saturation.

## 9. Resource Isolation

### 9.1 Why resource isolation matters

In a shared cluster, one team can accidentally consume all CPU, memory, pods, PVCs, secrets, services, or routes. Resource isolation prevents noisy-neighbor problems.

Resource isolation uses:

- Requests and limits.
- ResourceQuota.
- LimitRange.
- Object count quotas.
- PriorityClass.
- HPA/VPA/KEDA where appropriate.
- Cluster Autoscaler and MachineAutoscaler where supported.

### 9.2 Requests and limits

Requests are used by the scheduler to reserve resources. Limits cap runtime resource usage.

Example:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

Design guidance:

- Always require requests for production workloads.
- Avoid setting CPU limits blindly for latency-sensitive services because CPU throttling can hurt performance.
- Always set memory limits carefully because exceeding memory limit can kill the container.
- Use realistic requests based on metrics, not guesses.
- For Java workloads, align JVM heap with container memory limit.

### 9.3 ResourceQuota example

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-fin-payment-prod
  namespace: fin-payment-prod
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
    services: "20"
    secrets: "50"
    configmaps: "50"
    persistentvolumeclaims: "20"
    requests.storage: 2Ti
```

### 9.4 LimitRange example

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-default-container
  namespace: fin-payment-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: "100m"
      memory: "256Mi"
    default:
      cpu: "500m"
      memory: "512Mi"
    min:
      cpu: "50m"
      memory: "64Mi"
    max:
      cpu: "2"
      memory: "4Gi"
  - type: Pod
    max:
      cpu: "4"
      memory: "8Gi"
```

### 9.5 Quota design by tier

| Tier | Use case | Quota model |
|---|---|---|
| Bronze | Dev/sandbox | Small quota, strict object count, lower storage, no dedicated nodes. |
| Silver | Shared non-prod / normal apps | Moderate quota, default-deny network, shared workers. |
| Gold | Production critical | Larger quota, dedicated nodes or reserved capacity, strict policies. |
| Platinum | Regulated / mission critical | Dedicated node pool or cluster, approved SCC, strict egress, app-aware backup. |

### 9.6 Object count quotas

Do not only quota CPU and memory. Also limit object sprawl.

Useful object quotas:

```yaml
hard:
  pods: "100"
  services: "20"
  secrets: "50"
  configmaps: "50"
  persistentvolumeclaims: "20"
  count/routes.route.openshift.io: "20"
  count/jobs.batch: "50"
  count/cronjobs.batch: "20"
```

### 9.7 PriorityClass

Use PriorityClass carefully. It can protect platform-critical workloads, but wrong use can evict lower-priority business workloads.

Recommended:

- Platform components: highest priority, usually managed by OpenShift.
- Critical business apps: controlled high priority.
- Normal apps: default priority.
- Batch/dev/sandbox: lower priority.

Avoid giving every team high priority. If everything is high priority, priority has no value.

## 10. Network Isolation

### 10.1 Default network risk

In many Kubernetes/OpenShift designs, pods can communicate freely unless a network policy isolates them. For enterprise architecture, assume every production namespace needs explicit network policy.

Network isolation answers:

- Which pods can talk to this pod?
- Which namespaces can talk to this namespace?
- Which external services can this workload access?
- Which ingress routers can reach this app?
- Does this workload need fixed egress source IP?
- Is traffic internet-facing, internal, or restricted?

### 10.2 Default deny NetworkPolicy

Start with deny-by-default, then allow only required paths.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: fin-payment-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

This isolates all pods in the namespace for ingress and egress until allow rules are added.

### 10.3 Allow same namespace traffic

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: fin-payment-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector: {}
  egress:
  - to:
    - podSelector: {}
```

### 10.4 Allow ingress router to reach app pods

Example using namespace name label. Confirm namespace labels in your cluster before using in production.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
  namespace: fin-payment-prod
spec:
  podSelector:
    matchLabels:
      app: payment-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-ingress
```

### 10.5 Allow app to database in another namespace

Database namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-payment-api-to-mysql
  namespace: fin-database-prod
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          app.kubernetes.io/part-of: payment
          environment: prod
      podSelector:
        matchLabels:
          app: payment-api
    ports:
    - protocol: TCP
      port: 3306
```

### 10.6 Allow DNS egress

If you deny all egress, pods may fail DNS resolution unless DNS is allowed.

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: fin-payment-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

### 10.7 EgressFirewall

Use EgressFirewall to restrict external destinations from a namespace.

Example:

```yaml

  name: default
  namespace: fin-payment-prod

  egress:
  - type: Allow
    to:
      cidrSelector: 10.50.10.0/24
  - type: Allow
    to:
      dnsName: api.partner.example.com
  - type: Deny
    to:
      cidrSelector: 0.0.0.0/0
```

Design notes:

- Keep rules simple and documented.
- Avoid allowing broad internet access from production namespaces.
- Coordinate with enterprise firewall teams.
- Test return traffic behavior, especially with OVN-Kubernetes and shared gateway mode.

### 10.8 Egress IP

Use egress IP when an external system needs to allowlist traffic from a stable source IP.

Example namespace label:

```bash
oc label namespace fin-payment-prod egress=payment-prod
```

```yaml
  name: payment-prod-egress
```

- Reserve egress IPs in network/IPAM documentation.

### 10.9 Ingress isolation and router sharding

Router sharding isolates inbound traffic by running separate IngressController instances for selected namespaces or routes.

Use cases:

- Separate DMZ and internal routes.
- Separate regulated application traffic.
- Separate high-volume tenant traffic.
- Dedicated router certificates and load balancers.
- Different endpoint publishing strategies.

```yaml

  name: finance-private
  namespace: openshift-ingress-operator

    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""

      operator: Exists
      effect: NoSchedule
```

## 11. Runtime Security Isolation: SCC and Pod Security

### 11.1 Purpose

Security Context Constraints control what pods are allowed to do at runtime. They govern things such as:

- Running as privileged.
- Running as root or specific UID ranges.
- Host network access.
- Host PID/IPC access.
- HostPath volume usage.
- Linux capabilities.
- SELinux context behavior.
- Allowed volume types.
- Seccomp profiles.

### 11.2 Enterprise SCC design rules

1. Use the most restrictive SCC that works.
2. Bind SCCs to service accounts, not broad users or groups.
3. Do not modify default SCCs; create custom SCCs when required.
4. Avoid `privileged` SCC except for trusted platform components.
5. Avoid `anyuid` unless the application truly requires it.
6. Make image teams fix containers to run non-root wherever possible.
7. Treat hostPath, hostNetwork, and privileged containers as exceptions requiring approval.
8. Audit SCC usage regularly.

### 11.3 Service account based SCC assignment

Create a dedicated service account:

```bash
oc create sa payment-api-sa -n fin-payment-prod
```

Bind a specific SCC when required:

```bash
oc adm policy add-scc-to-user nonroot-v2 -z payment-api-sa -n fin-payment-prod
```

For legacy image requiring arbitrary/root UID:

```bash
oc adm policy add-scc-to-user anyuid -z legacy-app-sa -n legacy-prod
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: fin-payment-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      serviceAccountName: payment-api-sa
      containers:
      - name: payment-api
        image: registry.example.com/finance/payment-api:1.0.0
        securityContext:
          allowPrivilegeEscalation: false
          runAsNonRoot: true
          capabilities:
            drop:
            - ALL
```

### 11.4 SCC troubleshooting commands

```bash
# Check which SCC admitted a running pod
oc get pod <pod> -n <namespace> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'

# Check service account bindings
oc describe sa <serviceaccount> -n <namespace>

# Check pod events
oc describe pod <pod> -n <namespace>

# List SCCs
oc get scc

# Review SCC definition
oc describe scc restricted-v2
```

### 11.5 Common SCC errors

| Error | Likely cause | Fix |
|---|---|---|
| `unable to validate against any security context constraint` | Pod asks for permissions not allowed by assigned SCC. | Use less privileged pod settings or bind appropriate SCC to service account. |
| `runAsUser invalid` | UID not allowed by namespace range or SCC. | Use arbitrary UID-compatible image or appropriate SCC. |
| `hostPath volumes are not allowed` | Pod uses hostPath but SCC disallows it. | Remove hostPath or use approved custom SCC only for trusted workloads. |
| `privileged containers are not allowed` | Pod requests privileged mode. | Avoid privileged; if unavoidable, isolate on dedicated nodes and use approved SCC. |
| `hostNetwork is not allowed` | Pod requests host network. | Avoid hostNetwork; if required, use strict SCC and dedicated nodes. |

## 12. Storage Isolation

### 12.1 Storage isolation goals

Storage isolation protects data confidentiality, availability, performance, backup scope, and cost.

Design dimensions:

- StorageClass per performance and protection tier.
- PVC quota per namespace.
- Access mode selection: RWO, RWX, ROX.
- Storage topology and zone awareness.
- Encryption at rest.
- Backup and restore boundaries.
- Snapshot policy.
- Retention policy.
- Storage performance isolation.

### 12.2 StorageClass tiering

| Tier | Use case | Example backend |
|---|---|---|
| bronze | Dev/test, low cost | standard block/file storage |
| silver | Normal production | replicated block storage |
| gold | Critical production | high-performance replicated storage |
| archive | Long retention, backup-like storage | object/archive storage |
| local-fast | Databases, low latency | local volumes, NVMe, carefully designed |

### 12.3 PVC quota example

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-storage
  namespace: fin-payment-prod
spec:
  hard:
    persistentvolumeclaims: "20"
    requests.storage: 2Ti
    gold.storageclass.storage.k8s.io/requests.storage: 1Ti
    silver.storageclass.storage.k8s.io/requests.storage: 1Ti
```

### 12.4 Storage isolation rules

1. Do not allow every namespace to consume unlimited PVCs.
2. Use dedicated StorageClasses for regulated or performance-sensitive workloads.
3. Avoid sharing RWX volumes across unrelated applications.
4. Do not use hostPath for application data except controlled platform/internal scenarios.
5. Align backup policy with namespace/app ownership.
6. Test restore, not only backup creation.
7. Document which workloads require crash-consistent vs application-consistent backup.

## 13. Build and CI/CD Workload Isolation

Build workloads can be noisy and risky. They pull source code, run scripts, consume CPU/memory, access registries, and sometimes need privileged builders.

### 13.1 Why isolate builds

Builds can:

- Consume high CPU and memory.
- Pull untrusted dependencies.
- Generate many temporary objects.
- Require registry credentials.
- Use privileged or root-like behavior depending on build strategy.
- Impact application runtime workloads if scheduled on the same nodes.

### 13.2 Recommended build isolation pattern

- Dedicated `build-*` namespaces.
- Dedicated build service accounts.
- Dedicated build node pool.
- Taint build nodes.
- Quota build namespaces.
- Strict network egress to artifact repositories only.
- Separate registry credentials by environment.
- Separate production deployment identity from build identity.

Example node taint:

```bash
oc label node build01 workload-type=build
oc label node build02 workload-type=build
oc adm taint nodes -l workload-type=build dedicated=build:NoSchedule
```

Example build pod toleration:

```yaml
spec:
  tolerations:
  - key: dedicated
    operator: Equal
    value: build
    effect: NoSchedule
  nodeSelector:
    workload-type: build
```

### 13.3 GitOps production isolation

For production, prefer GitOps with controlled pull-based reconciliation.

Pattern:

```text
Developer → Git merge request → approval → GitOps repo → Argo CD/OpenShift GitOps → production namespace
```

Benefits:

- Production changes are auditable.
- Human users do not need broad production edit access.
- Rollback is controlled through Git.
- Drift can be detected.

## 14. Workload Isolation Design Patterns

### Pattern A: Shared cluster, namespace isolation

Use for standard internal applications.

Architecture:

```text
Cluster
 ├── app1-dev namespace
 ├── app1-uat namespace
 ├── app1-prod namespace
 ├── app2-dev namespace
 └── app2-prod namespace

Shared worker nodes
Default-deny NetworkPolicy
Quota per namespace
RBAC per group
Restricted SCC
```

Pros:

- Cost efficient.
- Easy to operate.
- Good for trusted teams.

Cons:

- Compute is still shared.
- Strong compliance isolation may not be enough.
- Noisy-neighbor risk remains if quotas are weak.

### Pattern B: Production dedicated node pool

Use when production must not share nodes with dev/test.

```text
Cluster
 ├── shared non-prod workers
 └── prod-gold workers with taint dedicated=prod-gold:NoSchedule

Production namespaces:
 - project node selector workload-tier=gold,lifecycle=prod
 - toleration dedicated=prod-gold
 - strict quota
 - strict NetworkPolicy
```

Pros:

- Stronger reliability isolation.
- Better capacity planning.
- Easier incident scoping.

Cons:

- Higher cost.
- Requires placement governance.

### Pattern C: Regulated finance workload

Use for payment, banking, defence, or confidential workloads.

Controls:

- Separate namespace or cluster.
- Dedicated node pool.
- Taints and tolerations.
- Default-deny ingress and egress.
- Egress IP allowlisted at external firewall.
- EgressFirewall limiting external destinations.
- Private router shard.
- Strict SCC, non-root, no hostPath, no privileged.
- Encrypted storage.
- App-aware backup.
- Central audit and longer log retention.
- GitOps-only production deployment.

### Pattern D: DMZ / internet-facing workload

Controls:

- Separate DMZ cluster or DMZ node pool.
- Dedicated ingress controller with external load balancer.
- Strict namespace selector for router shard.
- Default-deny east-west traffic.
- Egress restricted to required backend services.
- WAF/API gateway integration if required.
- No direct access to internal databases unless approved.

### Pattern E: GPU / AI workload isolation

Controls:

- Dedicated GPU nodes.
- GPU operator/device plugin.
- Node labels for GPU type.
- GPU taints.
- Namespace quota for GPU resources.
- Scheduling constraints.
- Storage bandwidth planning.
- Separate monitoring for GPU utilization.

Example quota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-gpu
  namespace: ai-model-prod
spec:
  hard:
    requests.cpu: "40"
    requests.memory: 160Gi
    limits.nvidia.com/gpu: "4"
    requests.nvidia.com/gpu: "4"
```

### Pattern F: Database workload isolation

Controls:

- Dedicated nodes or storage-optimized nodes.
- Anti-affinity and topology spread.
- StorageClass with required IOPS and replication.
- Strict backup and restore testing.
- NetworkPolicy allowing only app namespace traffic.
- PDB for controlled disruption.
- Avoid aggressive CPU limits without testing.

### Pattern G: Platform management workload isolation

Use a management cluster or infra node pool for:

- Advanced Cluster Management.
- OpenShift GitOps.
- Advanced Cluster Security.
- Central observability/logging.
- Automation controllers.

Controls:

- Dedicated management namespaces.
- Restricted admin access.
- Infra/management node placement.
- Backup for management control plane data.
- Separate upgrade testing.

Isolation is not only security. It also protects availability during node drains, upgrades, and failures.

- Test node drain behavior before production upgrade windows.

### 16.1 HPA isolation

HPA helps workload responsiveness but can also consume quota quickly.

Example:

### 16.2 Cluster Autoscaler / MachineAutoscaler

For cloud or supported infrastructure, node pool autoscaling can increase capacity. But autoscaling should respect isolation.

Guidelines:

- Separate autoscaling groups by workload tier.
- Do not let low-priority workloads scale expensive dedicated pools.
- Define max node limits per pool.
- Monitor pending pods by namespace and reason.

## 20. Troubleshooting Workload Isolation Issues

### 20.1 Pod stuck Pending

Common causes:

- Node selector does not match any node.
- Taint exists but pod has no toleration.
- Quota exceeded.
- PVC cannot bind.
- Topology spread constraint cannot be satisfied.
- Node affinity is too strict.
- Insufficient CPU/memory.

Commands:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
oc get nodes --show-labels
oc describe node <node>
oc describe quota -n <namespace>
oc get pvc -n <namespace>
```

### 20.2 Pod scheduled on wrong node

Check:

```bash
oc get pod <pod> -n <namespace> -o yaml | egrep -A5 "nodeSelector|affinity|tolerations"
oc get ns <namespace> -o yaml | grep openshift.io/node-selector -A2
oc get node <node> --show-labels
```

Possible reasons:

- Namespace annotation missing.
- Deployment does not include nodeSelector.
- Taint missing from dedicated node pool.
- Toleration too broad, for example `operator: Exists` on a generic key.
- Node labels inconsistent.

### 20.3 NetworkPolicy not working

Check:

```bash
oc get networkpolicy -n <namespace>
oc describe networkpolicy <policy> -n <namespace>
oc get pod -n <namespace> --show-labels
oc get ns --show-labels
oc rsh <pod> curl -v http://<service>.<namespace>.svc.cluster.local:<port>
```

Common reasons:

- Pod labels do not match policy selector.
- Namespace labels do not match namespaceSelector.
- Egress deny blocks DNS.
- Traffic uses hostNetwork pods; host network behavior can differ.
- Policy is created in wrong namespace.
- Service port and target port confusion.

### 20.4 SCC admission failure

Check:

```bash
oc describe pod <pod> -n <namespace>
oc get sa <sa> -n <namespace> -o yaml
oc get scc
oc adm policy who-can use scc/<scc-name>
```

Common fixes:

- Remove unnecessary privileged fields from pod spec.
- Use non-root image.
- Bind approved SCC to service account.
- Avoid binding SCC to broad users/groups.

### 20.5 Quota exceeded

Check:

```bash
oc describe quota -n <namespace>
oc get resourcequota -n <namespace> -o yaml
oc get pods -n <namespace>
oc get pvc -n <namespace>
```

Fix:

- Delete unused objects.
- Tune requests and limits.
- Increase quota after capacity approval.
- Move workload to correct tier/pool.

- [ ] Monitoring and alert owner is defined.

### 21.2 Node pool checklist

- [ ] Node pool purpose is documented.
- [ ] MachineSet/MachinePool exists for desired capacity.
- [ ] Labels are standardized.
- [ ] Taints are applied for dedicated pools.
- [ ] Approved workloads have tolerations.
- [ ] Infra/platform pods are validated after tainting.
- [ ] Capacity headroom is monitored.
- [ ] Upgrade/drain behavior is tested.

### 21.3 Network checklist

- [ ] Default-deny ingress and egress policy exists for production namespaces.
- [ ] DNS egress is allowed where needed.
- [ ] Ingress router access is explicitly allowed.
- [ ] Cross-namespace traffic is explicitly allowed.
- [ ] External egress is restricted.
- [ ] Egress IP is used where external allowlisting is required.
- [ ] Route sharding is used for DMZ/private/regulated ingress where needed.
- [ ] NetworkPolicy labels are governed by GitOps/policy.

### 21.4 Security checklist

- [ ] Workload uses non-root image if possible.
- [ ] SCC is least privilege.
- [ ] SCC is bound to service account, not broad group.
- [ ] Privileged/hostNetwork/hostPath usage has exception approval.
- [ ] Image source is approved.
- [ ] Secrets are project-scoped and rotated.
- [ ] Audit alerts exist for RBAC/SCC/network changes.

## 22. Common Anti-Patterns

### Anti-pattern 1: Namespace-only isolation

Problem:

```text
Team A and Team B have separate namespaces, but no quota and no NetworkPolicy.
```

Impact:

- Teams can consume shared capacity.
- Pods may communicate unexpectedly.
- Security boundary is weak.

Better:

```text
Namespace + RBAC + quota + LimitRange + default-deny NetworkPolicy + service account isolation.
```

### Anti-pattern 2: Dedicated nodes without taints

Problem:

```text
Nodes are labeled finance=true, but not tainted.
```

Impact:

- Other pods may still land there.
- Dedicated capacity is not guaranteed.

Better:

```text
Label + taint + namespace node selector + workload toleration.
```

### Anti-pattern 3: Broad tolerations

Problem:

```yaml
tolerations:
- operator: Exists
```

Impact:

- Pod can tolerate many taints and land on nodes it should not use.

Better:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: finance-prod
  effect: NoSchedule
```

### Anti-pattern 4: Giving anyuid to the whole namespace

Problem:

```bash
oc adm policy add-scc-to-group anyuid system:serviceaccounts:legacy-prod
```

Impact:

- Every service account in the namespace can run with anyuid.

Better:

```bash
oc create sa legacy-app-sa -n legacy-prod
oc adm policy add-scc-to-user anyuid -z legacy-app-sa -n legacy-prod
```

### Anti-pattern 5: Default-deny egress without DNS allow

Problem:

```text
All egress blocked; application cannot resolve service names.
```

Better:

```text
Allow DNS egress to openshift-dns namespace, then allow required app destinations.
```

### Anti-pattern 6: No PDB for production apps

Problem:

```text
Node drain during upgrade evicts all replicas at once or causes downtime.
```

Better:

```text
Replica count + anti-affinity/topology spread + PDB + readiness probes.
```

### Anti-pattern 7: Mixing prod and dev on same node pool without quota

Problem:

```text
Dev load test consumes cluster capacity and impacts production.
```

Better:

```text
Separate quotas, PriorityClass, and ideally separate node pools for production.
```

## 23. Senior-Level Design Recommendations

1. **Do not overuse dedicated clusters.** They improve isolation but increase operational cost. Use them when risk justifies it.
2. **Do not underuse dedicated node pools.** For critical production, dedicated pools are often the right balance between cost and isolation.
3. **Make namespace labels part of governance.** Many controls depend on labels.
4. **Use taints for hard compute isolation.** Labels alone are placement hints/requirements, not a protection mechanism against other workloads.
5. **Use default-deny network policy for production.** Add explicit allow policies.
6. **Control egress.** Many breaches and data leaks happen through outbound paths.
7. **Bind SCCs narrowly.** Service-account-specific SCC binding is much safer than namespace-wide broad binding.
8. **Quota everything.** CPU/memory alone is not enough; include objects, storage, routes, PVCs, jobs, and secrets.
9. **Separate build from runtime.** Build workloads are noisy and may be less trusted.
10. **Treat infra components as production-critical.** Routers, monitoring, registry, logging, and operators deserve protected capacity.
11. **Automate isolation.** Use GitOps and policy-as-code so isolation is repeatable and auditable.
12. **Test isolation.** Validate with actual pod placement, network connectivity, SCC annotation, quota usage, and node drain tests.

## 24. Interview / Real-World Questions

### Q1. Is namespace isolation enough for production?

No. Namespace isolation is only the logical starting point. Production isolation should also include RBAC, quota, LimitRange, NetworkPolicy, SCC/service account design, storage quota, observability, and sometimes dedicated node pools.

### Q2. What is the difference between nodeSelector and taint/toleration?

`nodeSelector` attracts or restricts a pod to nodes with matching labels. A taint repels pods from a node unless the pod has a matching toleration. For dedicated nodes, use both: selector to place approved pods there, taint to keep unapproved pods out.

### Q3. Why use project node selectors?

They enforce namespace-wide placement. This prevents application teams from accidentally deploying workloads to the wrong node class. However, they should be combined with node taints for stronger isolation.

### Q4. How do you isolate two applications at network level?

Create default-deny NetworkPolicy in each namespace, then add allow policies based on exact namespace labels, pod labels, and ports. Also control egress if external access must be restricted.

### Q5. How do you isolate infra components?

Create infra MachineSets/MachinePools, label nodes with `node-role.kubernetes.io/infra`, configure operators such as ingress, registry, monitoring, and logging to use node placement/tolerations, then taint infra nodes to prevent user workloads.

### Q6. How do you troubleshoot a pod pending because of isolation rules?

Use `oc describe pod`, check events, node selectors, namespace annotations, taints/tolerations, node labels, quota, PVC status, and topology constraints.

### Q7. When should you use separate clusters instead of node pools?

Use separate clusters for different trust domains, strict regulatory separation, different upgrade cadence, large blast-radius concerns, different identity/audit boundaries, or when a business/customer requires hard separation.

## 27. Final Architecture Summary

A strong OpenShift workload isolation design should answer these questions clearly:

1. **Who owns the workload?** Project labels, RBAC groups, service accounts, audit ownership.
2. **Where can it run?** Node labels, selectors, affinity, taints, tolerations, dedicated pools.
3. **What can it access?** NetworkPolicy, EgressFirewall, egress IP, route sharding, storage boundaries.
4. **What privileges can it use?** SCC, service account, securityContext, non-root images, capability drops.
5. **How much can it consume?** Requests, limits, quotas, object count quotas, storage quotas, autoscaling limits.
6. **How is it protected during failure and maintenance?** Replicas, PDB, anti-affinity, topology spread, backup, DR.
7. **How is it governed?** GitOps, policy-as-code, audit, monitoring, chargeback, review process.

The best enterprise design is not the strictest design everywhere. It is the design that applies the right level of isolation based on business risk, security requirements, workload behavior, and operational cost.

For a 10-year experienced OpenShift administrator, the expectation is to design the full isolation model, automate it, validate it, monitor it, and explain the trade-offs clearly to application, security, network, and management teams.
