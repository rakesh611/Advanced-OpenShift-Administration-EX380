## 1. What Cluster Upgrade Planning Means in Enterprise Architecture

Cluster upgrade planning is the structured process of moving an OpenShift cluster from one supported release to another while preserving platform availability, application continuity, security posture, compliance evidence, and operational control.

In a small lab, an upgrade may look like this:

```bash
oc adm upgrade
oc adm upgrade --to=<version>
```

In an enterprise, that is only the execution command. The real work is architecture-level planning:

- Which clusters are upgraded first?
- Which business services depend on each cluster?
- Which APIs, Operators, admission policies, storage plugins, network plugins, and security controls are impacted?
- Which applications can tolerate node drains?
- Which workloads are protected by PodDisruptionBudgets?
- Which clusters are internet-connected and which are disconnected?
- Which upgrade path is allowed by the OpenShift update graph?
- Which teams must approve the change?
- What is the recovery plan if the upgrade fails midway?
- What evidence is required for audit, compliance, and post-change review?

For a senior OpenShift administrator, upgrade planning is not just a maintenance activity. It is a platform lifecycle architecture function.

## 2. Why Cluster Upgrades Are Architectural Events, Not Only Operations Tasks

OpenShift upgrades affect multiple layers at once:

```text
Business Service Layer
  Applications, APIs, transactions, customer-facing services

Platform Service Layer
  Routes, ingress, service mesh, image registry, monitoring, logging, OLM Operators

Kubernetes Control Plane Layer
  kube-apiserver, controller manager, scheduler, admission, CRDs, API versions

OpenShift Control Plane Layer
  Cluster Version Operator, Cluster Operators, OAuth, console, image registry, marketplace

Node Operating System Layer
  RHCOS, kubelet, CRI-O, kernel, NetworkManager, systemd, machine config

Infrastructure Layer
  vSphere, bare metal, cloud IaaS, load balancers, DNS, storage arrays, firewall, proxy

Governance Layer
  CAB, risk approval, security approval, compliance, audit, SLA, rollback decision
```

Because OpenShift 4.x integrates the cluster lifecycle with RHCOS and cluster operators, an upgrade can include changes to Kubernetes, OpenShift operators, the container runtime, node OS packages, kubelet, CRI-O, kernel modules, and platform APIs.

This is why upgrade planning must be part of Enterprise Architecture:

- It controls lifecycle risk.
- It protects business continuity.
- It validates platform compatibility.
- It aligns with security patching and vulnerability management.
- It manages multi-cluster consistency.
- It provides evidence for governance and audit.

## 3. OpenShift Upgrade Architecture Overview

OpenShift 4.x uses an operator-driven update model. The upgrade is not a simple package update on each node. It is an orchestrated reconciliation process.

High-level architecture:

```text
Red Hat Update Service / OpenShift Update Service
        |
        | update graph, channel, target release
        v
Cluster Version Operator
        |
        | applies release payload manifests
        v
Cluster Operators
        |
        | reconcile target component versions
        v
Machine Config Operator
        |
        | updates RHCOS, kubelet, CRI-O, kernel, systemd, node config
        v
MachineConfigPools
        |
        | drains, updates, reboots nodes pool by pool
        v
Applications
        |
        | rescheduled based on availability, replicas, PDB, topology spread, capacity
```

The Cluster Version Operator, or CVO, is the main orchestrator. It communicates through the `ClusterVersion` resource, retrieves available update paths, applies release payload manifests, and tracks cluster upgrade status.

Check the cluster version object:

```bash
oc get clusterversion
oc get clusterversion version -o yaml
```

Common output:

```text
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE   STATUS
version   4.19.12   True        False         10d     Cluster version is 4.19.12
```

During upgrade:

```text
AVAILABLE   PROGRESSING   STATUS
True        True          Working towards 4.20.x
```

The CVO watches Cluster Operators:

```bash
oc get co
```

Example:

```text
NAME                          VERSION   AVAILABLE   PROGRESSING   DEGRADED
authentication                4.19.12   True        False         False
console                       4.19.12   True        False         False
dns                           4.19.12   True        False         False
ingress                       4.19.12   True        False         False
machine-config                4.19.12   True        False         False
monitoring                    4.19.12   True        False         False
network                       4.19.12   True        False         False
```

A clean upgrade requires all critical Cluster Operators to be `Available=True`, `Progressing=False`, and `Degraded=False` before the change window begins.

## 4. Main Upgrade Components

### 4.1 Cluster Version Operator

The CVO is responsible for driving OpenShift updates. It tracks desired and current cluster state through the `ClusterVersion` object.

Important fields:

```bash
oc get clusterversion version -o jsonpath='{.status.desired.version}{"\n"}'
oc get clusterversion version -o jsonpath='{.status.availableUpdates}{"\n"}'
oc get clusterversion version -o jsonpath='{.status.conditions}{"\n"}'
```

Important CVO conditions:

| Condition | Meaning |
|---|---|
| `Available` | Cluster version is available |
| `Progressing` | Upgrade or reconciliation is in progress |
| `Failing` | CVO cannot complete target state |
| `RetrievedUpdates` | Update recommendations were retrieved |
| `ReleaseAccepted` | Requested release payload passed verification and precondition checks |

### 4.2 Cluster Operators

Cluster Operators manage platform components. During upgrade, each operator reconciles its operands to the target release.

Examples:

- `kube-apiserver`
- `kube-controller-manager`
- `kube-scheduler`
- `openshift-apiserver`
- `authentication`
- `ingress`
- `network`
- `dns`
- `machine-config`
- `monitoring`
- `image-registry`
- `operator-lifecycle-manager`

A degraded Cluster Operator can block or delay upgrade.

### 4.3 Machine Config Operator

The Machine Config Operator, or MCO, manages RHCOS and node-level configuration. It can update:

- kubelet
- CRI-O
- kernel
- systemd units
- NetworkManager configuration
- OS-level files
- container runtime configuration
- node boot image related components depending on platform and version

The MCO applies changes through MachineConfigPools.

```bash
oc get mcp
```

Example:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED
master    rendered-master-xxxx                               True      False      False
worker    rendered-worker-yyyy                               True      False      False
```

During upgrade, MCPs move to `UPDATING=True` as nodes drain, update, and reboot.

### 4.4 MachineConfigPools

A MachineConfigPool groups nodes that receive the same rendered machine configuration.

Common pools:

- `master`
- `worker`
- `infra`
- custom workload pools

Enterprise clusters often use custom MCPs for:

- infra nodes
- logging nodes
- storage nodes
- GPU nodes
- edge nodes
- DMZ nodes
- special compliance zones

Custom MCPs are important for canary upgrade strategies.

### 4.5 OpenShift Update Service

Connected clusters retrieve update recommendations from Red Hat-hosted services. Disconnected clusters can use a local OpenShift Update Service to provide graph data inside the restricted network.

### 4.6 Release Payload

An OpenShift release payload contains the manifests and images required to move the cluster to the target version.

Check release image:

```bash
oc adm release info <release-image>
```

Example:

```bash
oc adm release info quay.io/openshift-release-dev/ocp-release:<version>-x86_64
```

## 5. Upgrade Types

### 5.1 Patch / Z-Stream Update

Example:

```text
4.19.10 -> 4.19.12
```

Characteristics:

- Usually lower risk than minor upgrades.
- Mostly bug fixes, CVEs, stability improvements.
- Still can include node reboots if RHCOS or machine config changes are included.
- Should still go through pre-checks and post-validation.

### 5.2 Minor / Y-Stream Update

Example:

```text
4.19.x -> 4.20.x
```

Characteristics:

- Higher risk than z-stream.
- Includes Kubernetes version change.
- Can include removed APIs.
- Can require administrator acknowledgment.
- Can affect OLM Operators and CRDs.
- Must be planned with workload compatibility.

### 5.3 EUS-to-EUS Update

Example:

```text
4.18 EUS -> 4.20 EUS
```

Characteristics:

- Used by enterprises that want longer support windows.
- Requires careful sequencing.
- May use control-plane-only intermediate updates depending on supported path.
- Operators and worker nodes require special attention.

### 5.4 Control Plane Only Update

Control plane only updates are used in certain EUS strategies where worker nodes are paused while the control plane is moved through an intermediate release.

This is not a casual optimization. It must be planned carefully because worker MCPs are paused and will not receive machine config updates until resumed.

### 5.5 Canary Worker Update

A canary strategy upgrades a small subset of worker nodes first before the full fleet.

Typical use cases:

- Large clusters
- Business-critical workloads
- Custom machine configs
- Hardware-specific nodes
- Bare-metal clusters
- GPU or storage nodes
- Risk-controlled upgrade rollout

### 5.6 Disconnected Upgrade

A disconnected upgrade is used when clusters cannot access the internet or when enterprises require local approval of images and update recommendations.

Requirements:

- Mirror registry
- Mirrored release images
- Mirrored operator catalogs
- ImageDigestMirrorSet or related mirror configuration
- Optional local OpenShift Update Service
- Pull secret and trust configuration
- Local DNS, CA, and registry availability

### 5.7 Hosted Control Plane / Hypershift Upgrade

Hosted control planes require different upgrade planning because the control plane and worker nodes may be managed separately. This guide focuses mainly on standalone OpenShift clusters, but the same enterprise planning principles apply.

## 6. Enterprise Upgrade Strategy

A mature enterprise upgrade strategy answers the following:

```text
What do we upgrade?
When do we upgrade?
Who approves it?
How do we test it?
How do we observe it?
How do we recover?
How do we prove success?
```

### 6.1 Strategic Objectives

Cluster upgrade planning should satisfy these objectives:

1. Keep clusters within supported lifecycle.
2. Apply security fixes in an acceptable SLA.
3. Reduce upgrade blast radius.
4. Validate application compatibility before production.
5. Avoid unsupported version jumps.
6. Keep cluster operators healthy.
7. Maintain application SLAs.
8. Preserve audit and compliance evidence.
9. Standardize upgrade execution across clusters.
10. Build repeatable operational runbooks.

### 6.2 Enterprise Upgrade Policy Example

```yaml
upgradePolicy:
  patchUpdates:
    frequency: monthly
    emergencySecurityPatchSLA: 7 days
    requiredApprovals:
      - platform-owner
      - application-owner-for-critical-namespaces
  minorUpdates:
    frequency: quarterly-or-EUS-based
    requiredApprovals:
      - enterprise-architecture
      - platform-operations
      - security
      - application-service-owner
      - change-advisory-board
  rings:
    - lab
    - dev
    - nonprod
    - preprod
    - prod-canary
    - prod-main
  prechecksRequired: true
  etcdBackupRequired: true
  postValidationRequired: true
  rollbackPlanRequired: true
```

## 7. Version, Channel, and Lifecycle Planning

OpenShift updates are controlled by channels and the update graph.

Common channel types:

| Channel | Usage |
|---|---|
| `candidate-*` | Early access and validation, not normally for production |
| `fast-*` | Supported updates available earlier |
| `stable-*` | Updates promoted after additional time in fast channel |
| `eus-*` | Extended Update Support path for supported even-numbered releases |

Example:

```bash
oc adm upgrade
oc adm upgrade channel
oc adm upgrade channel stable-4.20
```

Planning considerations:

- Do not randomly jump versions.
- Follow the recommended update graph.
- Use release notes and known issues before selecting a target version.
- Avoid first-day adoption of new minor versions for critical production unless required for security or support.
- Prefer tested z-stream versions with known stability.
- Consider EUS for large enterprises with strict validation cycles.

### 7.1 How to Select Target Version

A senior admin should not simply choose the latest available version. Use this decision model:

```text
Is the current version approaching end of support?
  yes -> prioritize lifecycle update

Is there a critical CVE fixed in a target z-stream?
  yes -> prioritize security patch

Is the target minor version new?
  yes -> review known issues and wait for mature z-stream if possible

Are required Operators compatible?
  no -> stop and resolve

Are removed APIs still used?
  yes -> stop and migrate

Is staging validation successful?
  no -> stop production rollout
```

### 7.2 Version Selection Checklist

```bash
oc version
oc adm upgrade
oc get clusterversion version -o yaml
oc get co
oc get mcp
```

Review:

- Current version
- Desired version
- Available updates
- Conditional updates
- Channel
- Release notes
- Known issues
- Operator compatibility
- API removals
- Infrastructure provider limitations
- Support lifecycle

## 8. EUS-to-EUS Upgrade Planning

EUS releases are important in enterprise architecture because they provide a longer validation and support window.

Typical model:

```text
4.14 EUS -> 4.16 EUS -> 4.18 EUS -> 4.20 EUS
```

Do not treat EUS-to-EUS as a direct version skip. Kubernetes and OpenShift minor version changes must be serialized through supported paths.

### 8.1 Why Enterprises Use EUS

- Lower frequency of major upgrade projects.
- Longer support window.
- Better alignment with annual compliance cycles.
- More time for application testing.
- Easier standardization across many clusters.

### 8.2 EUS Risk Areas

- Large change delta between business validation cycles.
- More APIs may be deprecated or removed across the jump.
- Operators may need sequential upgrades.
- Worker nodes may be paused for control-plane-only workflows.
- Application teams may underestimate compatibility testing.

### 8.3 EUS Planning Pattern

```text
1. Confirm current EUS release and target EUS release.
2. Confirm supported update graph.
3. Upgrade to latest z-stream of current EUS if required.
4. Perform control plane update to intermediate release if applicable.
5. Upgrade OLM Operators where required.
6. Continue control plane update to target EUS.
7. Resume worker MCPs.
8. Validate worker reboots and workload health.
9. Complete post-upgrade testing.
```

### 8.4 EUS Go / No-Go Criteria

Go only if:

- `oc get co` is healthy.
- `oc get mcp` is healthy.
- etcd backup completed.
- Required admin acknowledgments completed.
- Removed APIs are migrated.
- Operators are compatible.
- Application owners signed off.
- Monitoring and logging are healthy.
- Change window and recovery bridge are active.

## 9. Multi-Cluster Upgrade Architecture

Enterprises rarely operate one cluster. They operate a fleet:

```text
Hub Cluster
  ACM / multicluster engine / GitOps / policy / observability

Managed Clusters
  dev
  test
  qa
  preprod
  prod-region-1
  prod-region-2
  dr-site
  edge-site-1
  edge-site-2
```

### 9.1 Multi-Cluster Upgrade Principles

- Never upgrade all production clusters simultaneously.
- Use ring-based rollout.
- Keep at least one rollback-safe production region on the previous version during initial validation where business architecture allows.
- Do not upgrade DR blindly without understanding replication compatibility.
- Validate platform add-ons per cluster type.
- Ensure fleet policies do not fight upgrade changes.
- Use GitOps to standardize configuration drift remediation.

### 9.2 Hub-Spoke Upgrade Planning

In ACM-style architecture:

```text
Hub first or managed first?
```

The answer depends on compatibility.

Common pattern:

1. Validate ACM/hub compatibility with current and target managed cluster versions.
2. Upgrade non-production managed clusters.
3. Upgrade hub if required by support matrix.
4. Upgrade production managed clusters ring by ring.
5. Validate policies, placements, observability, and application sets.

### 9.3 Fleet Upgrade Matrix

| Cluster | Business Criticality | Current Version | Target Version | Ring | Window | Owner | Status |
|---|---:|---|---|---|---|---|---|
| lab-01 | Low | 4.19.x | 4.20.x | 0 | weekday | platform | ready |
| dev-01 | Low | 4.19.x | 4.20.x | 1 | weekday | platform | ready |
| preprod-01 | Medium | 4.19.x | 4.20.x | 2 | weekend | app+platform | pending |
| prod-canary-01 | High | 4.19.x | 4.20.x | 3 | approved | CAB | pending |
| prod-main-01 | Critical | 4.19.x | 4.20.x | 4 | approved | CAB | blocked |

## 10. Upgrade Ring Model

A ring model reduces risk by gradually expanding upgrade exposure.

```text
Ring 0: Lab / Sandbox
Ring 1: Internal Dev
Ring 2: QA / Test
Ring 3: Pre-Production
Ring 4: Production Canary
Ring 5: Production Main
Ring 6: DR / Edge / Special Clusters
```

### 10.1 Ring 0 - Lab

Purpose:

- Validate command syntax.
- Validate mirrored content.
- Validate admin acknowledgments.
- Validate release image availability.
- Test runbook.

### 10.2 Ring 1 - Dev

Purpose:

- Validate CI/CD workloads.
- Validate basic application deployments.
- Detect common API breakage.

### 10.3 Ring 2 - QA

Purpose:

- Validate application regression tests.
- Validate operator compatibility.
- Validate ingress, storage, service mesh, and monitoring.

### 10.4 Ring 3 - Pre-Production

Purpose:

- Production-like traffic and topology.
- Performance testing.
- Failover test.
- Backup and restore test.

### 10.5 Ring 4 - Production Canary

Purpose:

- Low percentage of production workloads.
- Real user traffic.
- Observe for hidden issues.

### 10.6 Ring 5 - Production Main

Purpose:

- Full rollout after evidence from previous rings.

### 10.7 Ring 6 - DR, Edge, and Special Clusters

Special clusters require separate planning:

- DR clusters must remain compatible with replication tools.
- Edge clusters may have bandwidth and maintenance constraints.
- Disconnected clusters require local mirror readiness.
- Storage-heavy clusters require CSI and ODF checks.

## 11. Upgrade Governance Model

### 11.1 Roles and Responsibilities

| Role | Responsibility |
|---|---|
| Enterprise Architect | Ensures lifecycle alignment, risk model, and target architecture |
| Platform Architect | Defines technical upgrade strategy |
| OpenShift Administrator | Performs pre-checks, execution, monitoring, troubleshooting |
| SRE | Defines SLO, error budget, observability, rollback triggers |
| Security Team | Reviews CVEs, compliance, SCC/PSA, certificates, audit |
| Network Team | Confirms firewall, DNS, load balancer, proxy, VIPs |
| Storage Team | Confirms CSI, backend health, snapshots, replication |
| Application Owner | Validates workload behavior and signs off |
| CAB | Approves change and maintenance window |
| Vendor Support | Available for high-risk upgrades if required |

### 11.2 Governance Artifacts

Each enterprise upgrade should produce:

- Upgrade design document
- Impact assessment
- Application compatibility matrix
- Risk register
- Backout and recovery plan
- Communication plan
- Pre-check evidence
- Execution log
- Post-check evidence
- Problem record if issues occurred
- Lessons learned

### 11.3 Change Ticket Template

```yaml
changeRequest:
  title: Upgrade OpenShift cluster <cluster-name> from <current> to <target>

    - ingress
    - platform-api
    - applications-on-worker-reboot

    - CAB
```

## 12. Upgrade Readiness Assessment

Upgrade readiness means the cluster, workloads, infrastructure, and teams are ready.

### 12.1 Technical Readiness

```bash
oc get clusterversion
oc get co
oc get mcp
oc get nodes
oc get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Check:

- No degraded Cluster Operators.
- No updating/degraded MCPs.
- No NotReady nodes.
- No certificate expiry risk.
- No image registry errors.
- No monitoring stack failure.
- No etcd quorum issues.
- No storage backend issue.
- No DNS/ingress degradation.
- No broken OAuth provider.

### 12.2 Application Readiness

Check:

- Deployments have more than one replica where required.
- Stateful apps have backup and recovery plan.
- PDBs do not block drains.
- Readiness probes are correct.
- Liveness probes are not too aggressive.
- Routes and services are monitored.
- Application teams approve.

### 12.3 Infrastructure Readiness

Check:

- Load balancers healthy.
- DNS records stable.
- Proxy reachable.
- Firewall rules allow required registries.
- Storage backend healthy.
- vSphere or cloud quotas available.
- Node replacement automation healthy.
- NTP/chrony synchronized.
- Mirror registry available for disconnected clusters.

### 12.4 Operational Readiness

Check:

- Change approved.
- Support bridge open.
- Admins have `cluster-admin` access.
- Break-glass credentials tested.
- Vendor support case opened if needed.
- Runbook reviewed.
- Monitoring dashboard ready.
- Communication message prepared.

## 16. MachineConfigPool and Node Readiness

MCP readiness is critical because OpenShift upgrades usually require node-level updates.

### 16.1 Check MCPs

```bash
oc get mcp
```

Expected:

```text
master   UPDATED=True   UPDATING=False   DEGRADED=False
worker   UPDATED=True   UPDATING=False   DEGRADED=False
```

### 16.2 MCP Paused State

```bash
oc get mcp -o jsonpath='{range .items[*]}{.metadata.name}{" paused="}{.spec.paused}{"\n"}{end}'
```

A paused MCP is skipped during node updates. This is useful for canary/control-plane-only strategies, but dangerous if forgotten.

Unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Pause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
```

### 16.3 Node Drain Risk

During MCP update, nodes are drained and rebooted if required. Risk comes from:

- Single-replica pods
- Strict PDBs
- Stateful workloads
- Local storage
- DaemonSets with issues
- Insufficient capacity on remaining nodes
- Pods without readiness probes
- Long terminationGracePeriodSeconds

### 16.4 Machine Config Drift

If an admin manually changes files on RHCOS nodes outside MachineConfig, MCO can detect drift and mark nodes degraded.

Avoid manual host changes unless they are part of an approved break-glass process and reconciled back into MachineConfig.

## 17. etcd Backup and Control Plane Recovery Planning

Before a cluster upgrade, take an etcd backup from a single control plane node and store it securely outside the cluster.

### 17.1 Why etcd Backup Matters

etcd contains cluster state:

- Kubernetes API objects
- OpenShift resources
- Secrets
- ConfigMaps
- CRDs
- Cluster configuration
- RBAC
- Operator state

If you lose etcd quorum or corrupt cluster state, etcd restore may be required.

### 17.2 Backup Command

From a control plane node:

```bash
oc debug node/<master-node>
chroot /host
/usr/local/bin/cluster-backup.sh /home/core/assets/backup
```

Copy backup files to secure storage:

```bash
scp core@<master-node>:/home/core/assets/backup/* ./etcd-backup-<cluster>-<date>/
```

### 17.3 Backup Rules

- Take backup during low activity period.
- Take backup from one master only, not all masters.
- Store backup outside the cluster.
- Encrypt backup storage.
- Record cluster version and timestamp.
- Test restore process in non-production.
- Do not treat etcd backup as application data backup.

### 17.4 Backup Evidence

Capture:

```text
backup path
backup timestamp
source master node
cluster version
backup file checksums
backup operator/admin name
storage location
restore test status
```

Example checksum:

```bash
sha256sum snapshot_*.db static_kuberesources_*.tar.gz > SHA256SUMS
```

## 28. Disconnected and Air-Gapped Upgrade Planning

Disconnected environments require extra planning because the cluster cannot pull release images or update graph data from the internet.

### 28.1 Required Components

```text

        v
Mirror registry
        |
        | IDMS / ITMS / CatalogSource / UpdateService
        v
Disconnected OpenShift cluster
```

### 28.2 Disconnected Upgrade Requirements

- Mirror registry is available and trusted.
- Release images for target version are mirrored.
- Operator catalogs are mirrored.
- Additional workload images are mirrored.
- Pull secret includes mirror credentials.
- Cluster trusts mirror registry CA.
- ImageDigestMirrorSet / ImageTagMirrorSet resources are applied.
- Local OpenShift Update Service is configured if update recommendations are required.

| Failure | Cause |
|---|---|
| Release image pull fails | Missing mirrored image or bad pull secret |
| CatalogSource unhealthy | Catalog image not mirrored or registry CA issue |
| CVO cannot retrieve updates | OSUS not configured or graph data missing |
| Nodes cannot pull RHCOS payload | Mirror registry unreachable from node network |


### 32.3 Common PDB Problems

| Situation | Result |
|---|---|
| Single replica app with `minAvailable: 1` | Drain blocked |
| App unhealthy before drain | Allowed disruptions becomes 0 |

- Fix unhealthy pods.
- Adjust PDB during approved window.
- Move workload to non-upgrading pool.
- Use canary worker strategy.

## 33. Maintenance Window Planning

### 33.1 Window Design

A good window includes:

```text
T-60 min: final prechecks
T-30 min: stakeholder notification
T-15 min: freeze deployments
T-00 min: start upgrade
T+X min: monitor control plane
T+Y min: monitor worker MCPs
T+Z min: post-validation
T+Z+30 min: business validation
T+Z+60 min: close or extend change
```

### 33.2 Window Sizing Factors

- Number of nodes
- Number of MCPs
- Node reboot duration
- Cloud or bare-metal boot speed
- Workload drain behavior
- PDB constraints
- Operator upgrade duration
- ODF or storage operations
- Network speed for image pulls
- Disconnected registry performance

### 33.3 Freeze Policy

During upgrade window:

- Freeze non-emergency application deployments.
- Freeze cluster configuration changes.
- Avoid operator subscription changes unless planned.
- Avoid machine scaling unless part of plan.
- Avoid certificate rotation changes unless necessary.

## 39. Canary Worker Upgrade Strategy

Canary upgrades reduce risk by testing a small worker subset first.

### 39.1 When to Use Canary

Use canary if:

- Cluster is large.
- Workloads are critical.
- Nodes have custom MachineConfigs.
- Hardware is heterogeneous.
- Bare metal drivers are involved.
- GPU, DPDK, SR-IOV, or storage nodes exist.
- Past upgrades had node-level issues.

### 39.2 Canary MCP Concept

Create a custom MCP for a small set of nodes:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-canary
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - worker-canary
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-canary: ""
```

Label one or two worker nodes:

```bash
oc label node <node> node-role.kubernetes.io/worker-canary=
```

### 39.3 Canary Flow

```text
1. Pause main worker MCP.
2. Keep canary MCP unpaused.
3. Start upgrade.
4. Allow canary nodes to update.
5. Validate applications on canary nodes.
6. Unpause main worker MCP.
7. Continue full worker rollout.
```

### 39.4 Risks

- Incorrect MCP selector can affect more nodes than intended.
- Paused MCP can be forgotten.
- Workloads may not naturally schedule to canary nodes.
- Canary may not represent production hardware.

## 40. Control Plane Only Upgrade Strategy

Control plane only updates are typically associated with EUS-to-EUS workflows.

### 40.1 Purpose

The goal is to update control plane components while delaying worker node updates.

### 40.2 High-Level Flow

```text
1. Confirm all MCPs are healthy.
2. Pause worker MCPs.
3. Upgrade control plane to intermediate target.
4. Validate control plane and Cluster Operators.
5. Upgrade to final target.
6. Update OLM Operators if required.
7. Unpause worker MCPs.
8. Allow worker nodes to update.
9. Validate applications.
```

### 40.3 Important Warning

Do not pause worker pools without a formal tracker. Paused pools can leave nodes on old machine config and create long-term drift.

Check paused pools:

```bash
oc get mcp -o jsonpath='{range .items[*]}{.metadata.name}{" paused="}{.spec.paused}{"\n"}{end}'
```

## 42. Compact Three-Node Cluster Upgrade Planning

A compact cluster usually has three nodes acting as both master and worker.

### 42.1 Risks

- Control plane and workloads share capacity.
- Node drain affects etcd quorum planning.
- Workload capacity is limited during node reboot.
- PDBs can block drains.

### 42.2 Planning

- Ensure all three nodes are healthy before upgrade.
- Avoid upgrades if one node is degraded.
- Reduce non-critical workload load before upgrade.
- Validate etcd health.
- Ensure PDBs permit disruption.
- Consider temporary capacity where possible.

## 47. Rollback, Restore, and Recovery Thinking

### 47.1 Important Concept

OpenShift upgrades are not usually rolled back like application deployments. Once control plane and etcd state advance, rollback is a recovery operation, not a simple downgrade button.

### 47.2 Recovery Options

| Situation | Possible Action |
|---|---|
| Upgrade precondition fails before changes | Fix issue and retry |
| Worker MCP paused intentionally | Resume when ready |
| Worker node update fails | Fix node, replace node, or remediate MCP |
| Operator degraded | Troubleshoot operator and operands |
| Application broken | Roll back app version or restore app data |
| Cluster unusable | etcd restore / disaster recovery process |
| Disconnected image missing | Mirror missing content and retry |

### 47.3 When to Stop

Stop and escalate if:

- API is unstable.
- etcd is degraded.
- Multiple Cluster Operators are degraded.
- More than planned nodes are NotReady.
- Ingress outage affects critical apps.
- Storage backend is degraded.
- Upgrade exceeds change window and business risk is rising.

### 47.4 Red Hat Support

For high-risk production upgrades, open a proactive support case with:

- Current version
- Target version
- Cluster ID
- Upgrade plan
- Precheck evidence
- Must-gather if requested

Collect must-gather:

```bash
oc adm must-gather
```

### 49.1 Pattern: Standard Production Upgrade

```text

```

Use for normal z-stream updates and smaller clusters.

### 49.2 Pattern: Ring-Based Fleet Upgrade

```text

```

Use for multi-cluster enterprises.

### 49.3 Pattern: Canary Worker Pool

```text
Pause main worker -> update canary -> validate -> unpause main worker
```

Use for large or high-risk clusters.

### 49.4 Pattern: Disconnected Mirrored Upgrade

```text
Mirror release -> mirror catalogs -> apply mirror config -> validate pulls -> upgrade
```

Use for air-gapped or controlled-content environments.

### 49.5 Pattern: EUS Lifecycle Upgrade

```text
Current EUS latest z-stream -> intermediate control plane -> target EUS -> worker update
```

Use for large enterprises that prefer longer support windows.

## 50. Common Mistakes by Administrators

### Mistake 1: Starting Upgrade with Degraded Operators

Never ignore degraded Cluster Operators unless fully understood and approved.

### Mistake 2: Not Taking etcd Backup

etcd backup is mandatory for serious production planning.

### Mistake 3: Ignoring PDBs

Strict PDBs can block node drains and extend upgrade time.

### Mistake 4: Forgetting Paused MCPs

Paused MCPs can leave nodes unpatched.

### Mistake 5: Automatic Operator Surprises

OLM Operators can upgrade during or around platform upgrades if subscriptions are automatic.

### Mistake 6: No API Deprecation Scan

Removed API usage can break workloads or block minor upgrades.

### Mistake 7: No Application Owner Sign-Off

Platform health does not mean business application health.

### Mistake 8: Treating Disconnected Like Connected

Disconnected clusters require mirror, catalog, trust, and update graph planning.

### Mistake 9: No Capacity Headroom

Node drains fail or cause application disruption when cluster is already overloaded.

### Mistake 10: No Post-Upgrade Evidence

Without evidence, audit and RCA become difficult.

## 51. Interview and Real-World Scenario Questions

### Q1. Why does OpenShift use CVO during upgrades?

Because OpenShift upgrades are declarative and operator-driven. The CVO applies release payload manifests, tracks cluster version state, coordinates Cluster Operators, and reports upgrade progress through the `ClusterVersion` resource.

### Q2. Why can an MCP block upgrade completion?

Because node-level updates are applied through MachineConfigPools. If a node cannot drain, reboot, apply config, or return Ready, the MCP may remain updating or degraded, preventing the cluster from reaching fully updated state.

### Q3. Why is etcd backup required before upgrade?

Because etcd stores cluster state. If control plane state is corrupted or quorum is lost, an etcd backup may be required for disaster recovery.

### Q4. Why are removed APIs important?

Workloads, webhooks, operators, or external clients using removed APIs may fail after the target Kubernetes/OpenShift version no longer serves those APIs.

### Q5. Why is a canary MCP useful?

It limits node-level upgrade exposure to a small subset of worker nodes first, allowing administrators to detect RHCOS, kubelet, CRI-O, driver, or workload scheduling problems before upgrading the whole worker fleet.

### Q6. How do you plan upgrades for 20 clusters?

Use a ring model, lifecycle matrix, standardized prechecks, GitOps policy validation, change windows by business criticality, and post-upgrade evidence. Do not upgrade all production clusters simultaneously.

### Q7. What is special about disconnected upgrades?

The cluster needs local access to mirrored release images, operator catalogs, trust configuration, pull secrets, and optionally local OpenShift Update Service graph data.

### Q8. Why can PDBs block upgrades?

OpenShift drains nodes during machine config updates. PDBs can prevent pod eviction when allowed disruptions are zero.

### Q9. How do you know upgrade completed successfully?

Check `clusterversion`, Cluster Operators, MCPs, nodes, pods, routes, PVCs, monitoring alerts, and application smoke tests. Success is both platform-level and business-service-level.

### Q10. What is the difference between rollback and recovery?

Rollback implies returning to previous version easily. OpenShift cluster downgrade is not normally a simple supported operation. Recovery means fixing the failed component, resuming upgrade, replacing nodes, restoring applications, or using etcd disaster recovery if necessary.

## 52. Final Senior Administrator View

Cluster upgrade planning is one of the most important Enterprise Architecture responsibilities in OpenShift administration.

A junior administrator asks:

```text
Which command starts the upgrade?
```

A senior administrator asks:

```text
Is the cluster ready?
Are applications ready?
Is storage healthy?
Are APIs compatible?
Are operators compatible?
Is the business ready?
Is recovery tested?
Can we prove success?
```

In production OpenShift, the upgrade command is the smallest part of the job. The real skill is designing a controlled, observable, recoverable, and repeatable upgrade process across the enterprise cluster fleet.

The best upgrade is not the fastest upgrade. The best upgrade is the one that:

- follows a supported path,
- protects business services,
- keeps the platform secure,
- minimizes blast radius,
- provides clear evidence,
- and leaves the cluster healthier than before.
