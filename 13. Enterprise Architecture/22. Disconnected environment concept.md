## 1. Executive Summary

A **disconnected environment** in OpenShift means the cluster runs without direct access to public internet registries, public update services, public package repositories, public source-code services, or public security feeds. In enterprise architecture, this is not only an installation style. It is a complete operating model for controlling the movement of software, patches, container images, Operators, Helm charts, signatures, certificates, and support data between an external connected zone and an internal restricted zone.

For a senior OpenShift administrator, the key point is this:

> A disconnected OpenShift cluster is only as reliable as the internal services that replace the internet.

In a connected cluster, nodes can pull images from Red Hat registries, Operator catalogs, Quay, GitHub, external Helm repositories, and update services. In a disconnected cluster, those dependencies must be recreated internally:

- OpenShift release payload images must exist in a private mirror registry.
- Red Hat Operator catalogs must be mirrored internally.
- Required application base images must be mirrored internally.
- Update graph information must be made available locally if using OpenShift Update Service.
- Internal CA certificates must be trusted by the cluster.
- Pull secrets must include mirror registry credentials.
- DNS, NTP, load balancers, identity providers, logging, monitoring, storage, backup, and GitOps tools must work without relying on the public internet.

A disconnected environment is common in defense, telecom, government, banking, manufacturing, OT/edge, regulated cloud, and critical infrastructure. The design must treat the mirror registry, signing policy, update process, and content promotion process as first-class enterprise architecture components.

## 2. What Is a Disconnected Environment?

A **disconnected environment** is an environment where OpenShift cluster nodes cannot directly reach public internet endpoints such as:

- `quay.io`
- `registry.redhat.io`
- `registry.access.redhat.com`
- Public Operator catalog sources
- Public Helm repositories
- Public Git repositories
- Public update graph services
- Public package repositories
- Public vulnerability databases
- External telemetry or cloud APIs

In OpenShift, this is also called a **restricted network** or **air-gapped** deployment, depending on the level of separation.

A disconnected environment does not mean the platform is incomplete. It means the platform must consume approved internal copies of required content.

### 2.1 Simple Definition

A disconnected OpenShift environment is an OpenShift deployment where cluster nodes use internal enterprise services instead of external internet services for installation, image pulls, Operators, updates, builds, monitoring, support, and compliance.

### 2.2 Senior-Level Definition

From an enterprise architecture point of view, a disconnected OpenShift environment is a controlled software supply chain architecture where external dependencies are acquired, scanned, approved, signed or verified, mirrored, promoted, and consumed through internal registries and repositories under enterprise governance.

The disconnected model is not only about blocking internet access. It is about controlling:

- **What software enters the environment**
- **Who approves it**
- **Where it is stored**
- **How it is verified**
- **How it is promoted**
- **Which clusters can consume it**
- **How updates are tested and rolled out**
- **How evidence is produced for audits**

## 3. Why Enterprises Use Disconnected OpenShift

Enterprises choose disconnected OpenShift for several reasons.

### 3.1 Security Isolation

Highly sensitive environments do not allow production infrastructure to communicate with the public internet. This reduces exposure to:

- External registry compromise
- Supply chain attacks
- Unauthorized image downloads
- Data exfiltration
- Command-and-control callbacks
- Accidental dependency drift

### 3.2 Regulatory and Compliance Requirements

Disconnected environments are common where governance requires strict control over external content. Examples include:

- Defense networks
- Government classified networks
- Banking and financial services
- Critical infrastructure
- Telecom core networks
- Healthcare environments
- Industrial control systems
- Sovereign cloud deployments

### 3.3 Supply Chain Control

In a connected environment, developers might reference public images directly. In a mature enterprise, this is risky. Disconnected design forces image consumption through approved mirrors.

This supports:

- Image scanning
- SBOM validation
- Signature verification
- Vulnerability acceptance workflow
- Approved base image strategy
- Content retention policy
- Traceability

### 3.4 Predictable Operations

When all content is internal, production behavior becomes more predictable. OpenShift upgrades, Operator installations, application deployments, and builds do not depend on internet availability or external registry rate limits.

### 3.5 Edge and Remote Site Requirements

Many edge locations have unreliable or unavailable internet connectivity. A disconnected pattern allows remote sites to run local OpenShift clusters using locally synchronized content.

## 4. Connectivity Models

Disconnected architecture is not a single pattern. Enterprises usually fall into one of these models.

### 4.1 Fully Connected

Cluster nodes can directly reach public Red Hat registries, update services, Operator catalogs, and external repositories.

**Used for:** Labs, development, non-sensitive environments.

**Risk:** Least control over external dependencies unless additional governance is applied.

### 4.2 Restricted Network with Proxy

Cluster nodes do not have open internet access but can reach approved endpoints through a controlled proxy.

**Used for:** Enterprises that allow tightly controlled outbound access.

**Key design point:** Proxy allowlists must include required OpenShift endpoints, registries, telemetry, and package sources. This is not truly air-gapped.

### 4.3 Partially Disconnected

A mirror host has access to both the internet and the internal mirror registry, but cluster nodes cannot access the internet.

**Typical pattern:**

```text
Internet -> Mirror Host -> Internal Mirror Registry -> OpenShift Cluster
```

This is easier to operate because mirroring can happen directly from external registries to the internal registry.

### 4.4 Fully Disconnected / Air-Gapped

No system has simultaneous access to the internet and the internal restricted network. Content is first downloaded to disk or removable media in a connected zone, physically or logically transferred, and then uploaded to the internal mirror registry.

**Typical pattern:**

```text
Connected Zone
  -> Download images to archive
  -> Scan and approve
  -> Transfer media
  -> Import into Restricted Zone mirror registry
  -> Cluster consumes internal content
```

### 4.5 Dark Site

A dark site is a highly restricted environment with no external connectivity, often including strict physical access control and removable media governance.

**Design impact:**

- Updates are slower.
- Content approval is formal.
- Troubleshooting data export is controlled.
- Support cases require sanitized must-gather bundles.
- Internal observability and documentation become very important.

## 5. Core Architecture Principles

### 5.1 Treat the Mirror Registry as Critical Infrastructure

In disconnected OpenShift, the mirror registry is not optional. It must be available for:

- Installation
- Cluster upgrades
- MachineConfig changes that cause node reboots
- Pod rescheduling
- Operator installation and upgrade
- Application deployment
- Build pipelines
- Disaster recovery

If the mirror registry is down, new pods might fail with `ImagePullBackOff`, upgrades might fail, Operators might not install, and node replacement might break.

**Production rule:** The mirror registry availability target should be at least equal to the OpenShift platform availability target.

### 5.2 Use Digest-Based References for Platform Content

OpenShift release payloads and many mirrored platform images should be consumed by digest rather than mutable tags.

Example:

```text
registry.example.com/ocp4/openshift4@sha256:<digest>
```

Digest-based pulls provide immutability and reduce risk from tag drift.

### 5.3 Separate Content Zones

A mature enterprise separates content into zones:

```text
External Source
  -> Acquisition Zone
  -> Scanning Zone
  -> Approval Zone
  -> Internal Mirror Registry
  -> Non-prod Clusters
  -> Production Clusters
```

Do not mirror directly into production without validation.

### 5.4 Keep Installation Content and Application Content Separate

OpenShift platform images, Operator images, application images, and developer build images should have separate repository structures and access controls.

Example:

```text
registry.internal.example.com/ocp4/release
registry.internal.example.com/ocp4/operators
registry.internal.example.com/redhat/base-images
registry.internal.example.com/apps/dev
registry.internal.example.com/apps/test
registry.internal.example.com/apps/prod
registry.internal.example.com/tools/helm
```

### 5.5 Design for Repeatability

Disconnected environments fail when the mirroring process is manual and undocumented. Every mirror operation should be declarative and repeatable.

Use:

- `ImageSetConfiguration`
- Git-managed mirror configs
- Change tickets
- Content manifests
- Checksums
- Automation scripts
- Promotion pipelines

### 5.6 Do Not Assume Internet-Like Behavior

In connected OpenShift, some behavior silently depends on external access. In disconnected environments, you must explicitly design for:

- Samples
- Builder images
- Operator catalogs
- Source-to-image builds
- Git repositories
- Maven/npm/PyPI dependencies
- Container vulnerability feeds
- Must-gather uploads
- Telemetry restrictions

## 6. Reference Architecture

### 6.1 High-Level Architecture

```text
+-------------------------------------------------------------+
|                    Connected / External Zone                |
|                                                             |
|  Red Hat Registries   Operator Catalogs   Helm Repos         |
|  Git Repos            Vendor Images       Security Feeds     |
|        |                                                    |
|        v                                                    |
|  +----------------+                                        |
|  | Mirror Host    | oc-mirror / skopeo / helm / scanners    |
|  +----------------+                                        |
+-------------------------|-----------------------------------+
                          |
                          | controlled transfer / direct sync
                          v
+-------------------------------------------------------------+
|                 Restricted / Disconnected Zone              |
|                                                             |
|  +-----------------------+     +--------------------------+  |
|  | Internal Mirror       |     | Internal Git / Artifact   |  |
|  | Registry / Quay       |     | Repositories             |  |
|  +-----------------------+     +--------------------------+  |
|        |                            |                       |
|        v                            v                       |
|  +-------------------------------------------------------+  |
|  |               OpenShift Cluster(s)                    |  |
|  |                                                       |  |
|  | Masters / Workers / Infra Nodes / Storage / Operators |  |
|  +-------------------------------------------------------+  |
|                                                             |
|  Internal DNS | NTP | CA | LDAP/OIDC | Monitoring | Backup   |
+-------------------------------------------------------------+
```

### 6.2 Enterprise Multi-Cluster Pattern

For multiple OpenShift clusters, use a shared enterprise mirror registry and cluster-specific policy.

```text
                           +-------------------+
                           | Enterprise Mirror |
                           | Registry / Quay   |
                           +---------+---------+
                                     |
        +----------------------------+----------------------------+
        |                            |                            |
+-------v--------+          +--------v-------+           +--------v-------+
| Dev Cluster    |          | Test Cluster   |           | Prod Cluster   |
| OCP 4.x        |          | OCP 4.x        |           | OCP 4.x        |
+----------------+          +----------------+           +----------------+
```

Design recommendation:

- Mirror content centrally.
- Promote content gradually.
- Use separate namespaces or repositories for dev, test, and prod content.
- Do not let production clusters consume unvalidated images.

## 7. Critical Components

A disconnected OpenShift architecture needs the following components.

### 7.1 Mirror Registry

Stores mirrored OpenShift release images, Operator catalogs, application images, tools, and sometimes Helm chart-related images.

Common choices:

- Red Hat Quay
- Mirror registry for Red Hat OpenShift
- JFrog Artifactory
- Sonatype Nexus Repository
- Harbor
- Other Docker v2 compatible registries

For production, Red Hat Quay is commonly preferred because it supports enterprise registry features such as high availability, repository mirroring, access control, garbage collection, and integration with security workflows.

### 7.2 Mirror Host

The mirror host runs mirroring tools and acts as the controlled bridge for content acquisition.

Required tools commonly include:

```bash
oc
oc-mirror
podman
skopeo
jq
tar
gzip
openssl
helm
```

In fully disconnected sites, there may be two mirror hosts:

- Connected mirror host in the external zone
- Disconnected import host in the restricted zone

### 7.3 Internal DNS

OpenShift requires reliable DNS. In disconnected environments, DNS must resolve:

```text
api.<cluster>.<baseDomain>
api-int.<cluster>.<baseDomain>
*.apps.<cluster>.<baseDomain>
registry.internal.example.com
ldap.internal.example.com
git.internal.example.com
ntp.internal.example.com
```

### 7.4 Internal NTP

Time synchronization is critical for:

- TLS certificates
- OAuth authentication
- etcd consistency
- audit logs
- log correlation
- certificate rotation
- image signature verification

Disconnected environments must have internal NTP servers.

### 7.5 Internal PKI / CA

The cluster must trust the internal mirror registry certificate. During installation, this is commonly handled with `additionalTrustBundle` in `install-config.yaml`. After installation, additional registry trust is commonly handled through the cluster image configuration and ConfigMaps in `openshift-config`.

### 7.6 Pull Secret Management

Pull secrets must include credentials for internal registries. The global pull secret is especially important for platform components and mirrored registries.

### 7.7 Internal Git and Artifact Repositories

Developers and GitOps tools need internal repositories:

- GitLab / Gitea / Bitbucket / Azure DevOps Server
- Nexus / Artifactory for Maven, npm, PyPI, RPMs
- Internal Helm chart repositories
- Internal container registries

### 7.8 OpenShift Update Service

In a connected cluster, update recommendations come from Red Hat update graph services. In disconnected environments, enterprises can deploy OpenShift Update Service internally so clusters can receive local update graph data and recommended update paths.

### 7.9 Security and Scanning Tools

Disconnected does not remove the need for scanning. It increases the importance of internal scanning.

Common controls:

- Vulnerability scanner
- Malware scanner
- SBOM repository
- Image signature verification
- Admission policy
- Approved base image catalog
- Audit logging
- Registry access logs

## 8. Image Supply Chain Design

The most important disconnected environment concept is the **image supply chain**.

### 8.1 What Must Be Mirrored?

At minimum:

1. OpenShift release payload
2. OpenShift installer and CLI tools, as required for installation workflow
3. Red Hat Operator catalogs
4. Required Operator bundle images
5. Required application runtime images
6. Base images for builds
7. Helm chart referenced images
8. Must-gather images
9. Cluster Samples Operator images, if samples are used
10. OpenShift Update Service graph data image, if OSUS is used

### 8.2 Release Payload Images

The OpenShift release payload contains the cluster version components. Without the mirrored release payload, disconnected installation and upgrades cannot proceed.

Example high-level release flow:

```text
quay.io/openshift-release-dev/ocp-release
quay.io/openshift-release-dev/ocp-v4.0-art-dev
        |
        v
registry.internal.example.com/ocp4/openshift4
```

### 8.3 Operator Images

Operators are delivered through catalogs. In disconnected environments, you mirror only the Operators, channels, versions, and architectures you need.

Bad practice:

```text
Mirror every Operator from every catalog without lifecycle control.
```

Better practice:

```text
Mirror only approved Operators:
- local-storage-operator
- openshift-gitops-operator
- advanced-cluster-management
- odf-operator
- compliance-operator
- file-integrity-operator
- openshift-pipelines-operator
```

### 8.4 Application Images

Application teams must not reference public images directly.

Bad practice:

```yaml
image: docker.io/library/nginx:latest
```

Better practice:

```yaml
image: registry.internal.example.com/approved/nginx@sha256:<digest>
```

### 8.5 Build Dependencies

Disconnected OpenShift builds often fail because application source builds still try to access the internet.

Examples:

- Maven downloads from Maven Central
- Node.js downloads from npmjs.org
- Python downloads from PyPI
- Ruby downloads from RubyGems
- Go modules download from public module proxies
- Containerfiles use `FROM docker.io/...`

Enterprise solution:

- Internal Maven repository
- Internal npm registry proxy
- Internal PyPI mirror
- Internal RPM repository
- Approved base images
- Internal Git
- Build pipeline validation

## 9. Mirror Registry Architecture

### 9.1 Small Lab Registry vs Enterprise Registry

For labs or small disconnected environments, the mirror registry for Red Hat OpenShift can be used as a simple target for required OpenShift content. For enterprise production, use a highly available registry platform such as Red Hat Quay or another supported Docker v2 registry.

### 9.2 Registry Availability

A production mirror registry must be designed for:

- High availability
- Backup and restore
- Storage redundancy
- TLS certificate lifecycle
- Authentication integration
- Role-based access control
- Garbage collection
- Audit logs
- Performance monitoring
- Capacity forecasting

### 9.3 Registry Storage

Storage must handle:

- Initial OpenShift payload mirror
- Multiple OpenShift versions
- Multiple architectures
- Operator catalogs
- Application images
- Helm chart images
- Retention of previous releases for rollback/recovery
- Future growth

### 9.4 Repository Layout Example

```text
registry.internal.example.com/
  ocp4/
    release/
    operators/
    graph-data/
  redhat/
    ubi8/
    ubi9/
    rhel9/
  platform-tools/
    must-gather/
    cli/
  apps/
    dev/
    test/
    prod/
  third-party/
    approved/
```

### 9.5 Access Control Model

A good registry RBAC model separates duties:

| Role | Responsibility |
|---|---|
| Registry Admin | Registry platform, storage, TLS, replication |
| Mirror Admin | Mirrors Red Hat and approved third-party content |
| Security Reviewer | Scans and approves images |
| App Team | Pushes app images into dev/test repos |
| Release Manager | Promotes approved images to prod repos |
| OpenShift Cluster | Pulls approved content only |

### 9.6 Registry Certificate Strategy

Use enterprise CA-signed certificates where possible. Avoid insecure registries in production.

Required considerations:

- Registry certificate SAN must match the FQDN used by cluster nodes.
- Certificate chain must be included in trust bundles.
- Expiry must be monitored.
- Rotation must be tested.
- All nodes must trust the registry CA.

## 10. oc-mirror Concept and Workflow

`oc-mirror` is the primary OpenShift tool used to mirror release payloads, Operator catalogs, Helm charts, and additional images to a disconnected registry.

### 10.1 Why oc-mirror Matters

`oc-mirror` provides a declarative image-set approach. Instead of manually copying images one by one, you define the desired content in an `ImageSetConfiguration` file.

It helps with:

- Release image mirroring
- Operator catalog mirroring
- Additional image mirroring
- Helm chart image handling
- Incremental mirroring
- Generated cluster resources
- Update graph support
- Repeatable disconnected workflows

### 10.2 oc-mirror v2 Concept

Recent OpenShift documentation emphasizes `oc-mirror` plugin v2. It supports centralized mirroring of OpenShift releases, Operators, Helm charts, and other images, and can generate `ImageDigestMirrorSet` and `ImageTagMirrorSet` resources for cluster configuration.

### 10.3 High-Level oc-mirror Workflow

```text
1. Create ImageSetConfiguration YAML
2. Run oc mirror from connected mirror host
3. Push directly to internal registry OR create archive on disk
4. Transfer archive to disconnected zone if needed
5. Import archive into internal mirror registry
6. Apply generated cluster resources
7. Configure OperatorHub/CatalogSources
8. Repeat periodically for updates
```

### 10.4 Connected Mirroring

Used when the mirror host can reach both internet and internal mirror registry.

```bash
oc mirror --config=imageset-config.yaml docker://registry.internal.example.com
```

### 10.5 Fully Disconnected Mirroring

Used when no host can access both internet and internal mirror registry.

Mirror to disk in connected zone:

```bash
oc mirror --config=imageset-config.yaml file:///mnt/mirror-archive
```

Transfer the archive into disconnected zone, then import:

```bash
oc mirror --from file:///mnt/mirror-archive docker://registry.internal.example.com
```

### 10.6 Example ImageSetConfiguration

> Adjust versions, channels, catalog names, architectures, and Operators according to your enterprise standard.

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration
mirror:
  platform:
    channels:
      - name: stable-4.20
        minVersion: 4.20.0
        maxVersion: 4.20.5
    graph: true
  operators:
    - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.20
      packages:
        - name: local-storage-operator
        - name: openshift-gitops-operator
        - name: odf-operator
        - name: compliance-operator
        - name: file-integrity-operator
  additionalImages:
    - name: registry.redhat.io/ubi9/ubi:latest
    - name: registry.redhat.io/ubi9/ubi-minimal:latest
    - name: registry.redhat.io/rhel9/support-tools:latest
```

### 10.7 Important Operational Rule

Once a mirror registry is populated by `oc-mirror`, future updates to that mirror should continue using `oc-mirror` with the same storage backend and controlled configuration. Do not mix uncontrolled manual pushes with managed mirror operations unless you have a clear repository separation.

## 11. Installation Design in a Disconnected Environment

### 11.1 Pre-Installation Questions

Before installation, answer these design questions:

1. Which OpenShift version and architecture are approved?
2. Which installation method will be used?
   - Agent-based Installer
   - Bare-metal IPI
   - Bare-metal UPI
   - vSphere IPI/UPI
   - Cloud restricted network installation
3. Where is the mirror registry hosted?
4. Is the registry highly available?
5. Which CA signs the registry certificate?
6. Is DNS ready?
7. Is NTP ready?
8. Are load balancers ready?
9. Are firewall rules documented?
10. Is the pull secret updated with mirror registry credentials?
11. Which Operators are required at Day 1?
12. Which Operators can wait until Day 2?
13. How will upgrades be performed?
14. How will must-gather data be exported for support?

### 11.2 Installation Content Flow

```text
Red Hat release image
       |
       v
Mirror host downloads/mirrors image
       |
       v
Internal mirror registry
       |
       v
install-config.yaml contains mirror information and trust bundle
       |
       v
Installer creates cluster using internal image sources
       |
       v
Cluster nodes pull platform images from internal mirror
```

### 11.3 install-config.yaml Key Fields

Disconnected installation usually requires:

- `pullSecret` containing internal mirror registry credentials
- `additionalTrustBundle` containing mirror registry CA certificate
- `imageContentSources` or generated mirror source data, depending on installer workflow and OpenShift version/tooling output

Example concept:

```yaml
apiVersion: v1
baseDomain: example.com
metadata:
  name: ocp-prod
pullSecret: '{"auths":{"registry.internal.example.com":{"auth":"..."}}}'
additionalTrustBundle: |
  -----BEGIN CERTIFICATE-----
  <internal-registry-ca>
  -----END CERTIFICATE-----
imageContentSources:
- mirrors:
  - registry.internal.example.com/ocp4/openshift4
  source: quay.io/openshift-release-dev/ocp-release
- mirrors:
  - registry.internal.example.com/ocp4/openshift4
  source: quay.io/openshift-release-dev/ocp-v4.0-art-dev
```

### 11.4 Agent-Based Installer Design

The Agent-based Installer is very useful for disconnected bare-metal and edge environments because it can generate bootable ISO assets from `install-config.yaml` and `agent-config.yaml`.

Key points:

- The ISO must include enough configuration for hosts to discover and join the installation.
- The registry certificate must be trusted.
- The mirror source configuration must be valid.
- The rendezvous node must be reachable by other nodes.
- DNS and NTP must be working.
- Hostnames and network interfaces must match the plan.

### 11.5 Installation Validation Commands

Before installation, validate mirror registry access from a host in the disconnected network:

```bash
podman login registry.internal.example.com
podman pull registry.internal.example.com/ocp4/openshift4@sha256:<digest>
curl -vk https://registry.internal.example.com/v2/
```

Validate DNS:

```bash
dig api.ocp-prod.example.com
dig api-int.ocp-prod.example.com
dig test.apps.ocp-prod.example.com
dig registry.internal.example.com
```

Validate NTP:

```bash
chronyc sources -v
chronyc tracking
```

Validate certificate chain:

```bash
openssl s_client -connect registry.internal.example.com:443 -showcerts
```

## 12. Day-2 Operations

Disconnected architecture must support the full cluster lifecycle, not only installation.

### 12.1 Day-2 Areas

After installation, plan for:

- Operator installation and upgrades
- Cluster updates
- Image registry trust changes
- Global pull secret rotation
- Node replacement
- Application deployments
- GitOps synchronization
- Vulnerability remediation
- Certificate rotation
- Backup and restore
- Support bundle generation
- Audit evidence collection

### 12.2 Day-2 Mirror Updates

A disconnected cluster does not automatically receive new release images or Operator updates. You must mirror new content intentionally.

Recommended process:

```text
1. Security/release team approves new OpenShift version
2. Mirror team updates ImageSetConfiguration
3. Content is mirrored into staging registry
4. Security scans content
5. Non-prod cluster validates update
6. CAB/change approval
7. Content promoted to production registry namespace
8. Production cluster updated
9. Post-check and audit evidence stored
```

### 12.3 Node Replacement Risk

A common failure in disconnected environments appears during node replacement. The new node needs to pull Machine Config Daemon, kubelet-related images, CNI images, and other platform components. If the mirror registry is unreachable or incomplete, the node cannot become healthy.

Always test:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
# Replace/rebuild node according to platform
oc get nodes
oc get co
```

### 12.4 Global Pull Secret Updates

When registry credentials rotate, update the global pull secret carefully.

Typical check:

```bash
oc get secret/pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Update flow:

```bash
oc set data secret/pull-secret -n openshift-config --from-file=.dockerconfigjson=pull-secret.json
```

Then monitor cluster operators:

```bash
oc get co
oc get mcp
```

## 13. Operator Lifecycle Management in Disconnected Environments

### 13.1 Connected vs Disconnected OperatorHub

In connected OpenShift, OperatorHub can use default catalog sources that reference external registries. In disconnected OpenShift, you must mirror Operator catalogs and create internal `CatalogSource` objects.

### 13.2 Disable Default Sources When Needed

In a fully disconnected environment, default OperatorHub sources that point externally are not useful and can create noise. A common pattern is to disable default sources and provide internal catalog sources.

Example:

```bash
oc patch OperatorHub cluster --type json \
  -p '[{"op": "add", "path": "/spec/disableAllDefaultSources", "value": true}]'
```

### 13.3 Internal CatalogSource Example

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators-disconnected
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: registry.internal.example.com/ocp4/operators/redhat-operator-index:v4.20
  displayName: Red Hat Operators - Disconnected
  publisher: Internal Platform Team
```

Apply and verify:

```bash
oc apply -f catalogsource.yaml
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
oc get packagemanifest -n openshift-marketplace | head
```

### 13.4 Operator Version Control

In connected clusters, administrators often accept automatic Operator upgrades. In disconnected clusters, automatic upgrades can fail if the required new images are not mirrored.

Recommended production pattern:

- Use manual approval for critical Operators.
- Mirror exact Operator versions/channels.
- Test in non-prod first.
- Promote catalog changes to prod only after validation.
- Keep Operator subscription strategy aligned with mirror cadence.

Example Subscription:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-gitops-operator
  namespace: openshift-operators
spec:
  channel: latest
  installPlanApproval: Manual
  name: openshift-gitops-operator
  source: redhat-operators-disconnected
  sourceNamespace: openshift-marketplace
```

## 14. Cluster Update Strategy

### 14.1 Why Updates Are Different

In a connected OpenShift environment, the Cluster Version Operator can use update graph information and pull release images externally. In a disconnected environment, you must ensure:

- Target release image is mirrored.
- Update graph is available internally, if using OSUS.
- Signature validation works.
- Mirror configuration redirects pulls correctly.
- All cluster nodes can access the mirror registry.

### 14.2 Two Update Models

#### Model A: With OpenShift Update Service

This gives a connected-like experience using internal update graph data.

High-level flow:

```text
Mirror release images + graph data
Deploy OSUS internally
Configure CVO to use internal OSUS
Update through web console or oc
```

#### Model B: Without OpenShift Update Service

You manually specify the target release image digest.

Example concept:

```bash
oc adm upgrade --to-image registry.internal.example.com/ocp4/openshift4@sha256:<target-release-digest>
```

### 14.3 Recommended Enterprise Upgrade Flow

```text
1. Review Red Hat release notes and errata
2. Mirror target release into staging mirror
3. Update non-prod cluster
4. Validate cluster operators, workloads, storage, routes, ingress, monitoring
5. Validate rollback/contingency plan
6. Approve change
7. Promote mirrored target release to prod namespace
8. Update production cluster during maintenance window
9. Monitor CVO, MCP, CO, nodes, alerts, workloads
10. Store evidence and update platform baseline
```

### 14.4 Upgrade Validation Commands

Before update:

```bash
oc get clusterversion
oc adm upgrade
oc get co
oc get mcp
oc get nodes
oc get pods -A | egrep -v 'Running|Completed'
```

During update:

```bash
watch 'oc get clusterversion; oc get co; oc get mcp; oc get nodes'
```

After update:

```bash
oc get clusterversion
oc get co
oc get mcp
oc adm top nodes
oc adm top pods -A
```

### 14.5 Upgrade Risk Areas

- Mirror registry outage
- Incomplete mirrored release
- Missing Operator images
- Expired registry certificate
- Pull secret mismatch
- IDMS/ITMS misconfiguration
- MachineConfigPool degraded
- NetworkPolicy blocking registry access
- Firewall blocking registry port
- Storage issue during registry pull
- Insufficient node capacity during rolling update

## 15. Image Registry Trust, IDMS, ITMS, and ICSP

OpenShift uses mirror configuration resources to redirect image pulls from source registries to internal mirrored registries.

### 15.1 ImageDigestMirrorSet

`ImageDigestMirrorSet` is used for digest-based image pulls.

Use it for:

- Release payloads
- Immutable platform images
- Production-grade image pinning

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: release-mirror
spec:
  imageDigestMirrors:
  - source: quay.io/openshift-release-dev/ocp-release
    mirrors:
    - registry.internal.example.com/ocp4/openshift4
```

### 15.2 ImageTagMirrorSet

`ImageTagMirrorSet` is used for tag-based image pulls.

Use it carefully because tags are mutable.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: ImageTagMirrorSet
metadata:
  name: approved-base-images
spec:
  imageTagMirrors:
  - source: registry.redhat.io/ubi9
    mirrors:
    - registry.internal.example.com/redhat/ubi9
```

### 15.3 ImageContentSourcePolicy

`ImageContentSourcePolicy` was historically used for digest-based mirroring, but newer OpenShift architecture favors `ImageDigestMirrorSet` and `ImageTagMirrorSet`. Existing ICSP objects can still exist in upgraded environments, but new deployments should prefer the newer resources.

### 15.4 Trust Bundle for Registry CA

If your internal registry uses an enterprise or private CA, configure OpenShift to trust it.

Create ConfigMap:

```bash
oc create configmap registry-ca \
  -n openshift-config \
  --from-file=registry.internal.example.com..443=registry-ca.crt
```

Patch image config:

```bash
oc patch image.config.openshift.io/cluster --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-ca"}}}'
```

Monitor:

```bash
oc get mcp
oc get co
```

### 15.5 Registry Source Policy

You can restrict registries cluster-wide.

Example allowlist concept:

```yaml
apiVersion: config.openshift.io/v1
kind: Image
metadata:
  name: cluster
spec:
  registrySources:
    allowedRegistries:
    - registry.internal.example.com
    - image-registry.openshift-image-registry.svc:5000
```

Be careful. If you block required registries before mirror policy is correct, pods can fail.

## 16. Developer Platform Design

A disconnected platform must still support developer productivity.

### 16.1 Developer Requirements

Developers need:

- Approved base images
- Internal Git repositories
- Internal CI/CD runners
- Internal artifact repositories
- Internal Helm charts
- Templates and samples
- Documentation
- Self-service namespaces
- Build pipelines
- Internal image promotion

### 16.2 Source-to-Image Challenges

S2I builds commonly reference builder images and external package repositories. In disconnected environments:

- Builder images must be mirrored.
- Source code must be internal.
- Dependencies must come from internal artifact repositories.
- BuildConfig secrets must trust internal Git certificates.

Example Maven settings for internal repository:

```xml
<settings>
  <mirrors>
    <mirror>

  </mirrors>

```

### 16.3 Application Image Promotion

Recommended flow:

```text
Developer build -> dev image repo -> scan -> test -> approve -> prod image repo
```

Never let production pull directly from dev repositories.

### 16.4 GitOps in Disconnected Environments

GitOps works very well in disconnected environments if all dependencies are internal.

Required design:

- Internal Git server
- Internal GitOps Operator catalog
- Internal Argo CD images
- Internal Helm/Kustomize dependencies
- Internal cluster API endpoints
- Controlled credentials
- Repo signing or branch protection

## 17. Security Architecture

### 17.1 Security Goal

The goal is not just no internet access. The goal is controlled, auditable, verified software flow.

### 17.2 Supply Chain Controls

Implement:

- Approved image sources
- Image scanning
- Signature verification
- SBOM collection
- Vulnerability exception process
- Admission control
- Namespace isolation
- Least privilege RBAC
- Audit logging
- Change approvals

### 17.3 Image Signing and Verification

Use signature verification where practical. For platform release images, the Cluster Version Operator validates release image authenticity during updates. For enterprise application images, define your own signing model using tools such as cosign and policy enforcement.

### 17.4 Registry Hardening

Mirror registry hardening checklist:

- TLS only
- Enterprise CA certificate
- Strong authentication
- Least privilege repository access
- No anonymous push
- Audit logs enabled
- Regular backup
- Vulnerability scanning
- Storage encryption
- Retention policy
- Garbage collection schedule
- Monitoring and alerting

### 17.5 Removable Media Governance

In fully air-gapped environments, removable media is a security boundary.

Controls:

- Media registration
- Malware scan before import
- Hash validation
- Chain-of-custody log
- Two-person approval
- Read-only transfer where possible
- Post-transfer verification
- Secure destruction or reclassification

### 17.6 Secrets Management

Disconnected does not eliminate secret risk. Use:

- OpenShift Secrets for basic needs
- External Secrets Operator with internal vault, if available
- HashiCorp Vault or CyberArk deployed internally
- Sealed Secrets only if key management is mature
- Rotation procedures
- Audit trail

## 18. Network and DNS Design

### 18.1 Required Internal Connectivity

Cluster nodes must reach:

- API load balancer
- Ingress load balancer
- Internal mirror registry
- Internal DNS
- Internal NTP
- Internal identity provider
- Internal Git/artifact repos
- Internal monitoring/logging endpoints
- Internal storage endpoints
- Internal backup target

### 18.2 Registry Firewall Rules

Every node that can run workloads must reach the mirror registry.

Example:

```text
Source: OpenShift nodes
Destination: registry.internal.example.com
Port: 443/TCP
Action: Allow
```

Do not allow only masters. Workers and infra nodes also pull images.

### 18.3 DNS Records

Example cluster DNS:

```text
api.ocp-prod.example.com        -> API load balancer
api-int.ocp-prod.example.com    -> Internal API load balancer
*.apps.ocp-prod.example.com     -> Ingress load balancer
registry.internal.example.com   -> Mirror registry VIP
```

### 18.4 Proxy Considerations

If using proxy in restricted mode, define:

- `HTTP_PROXY`
- `HTTPS_PROXY`
- `NO_PROXY`

`NO_PROXY` must include cluster internal domains, service networks, pod networks, registry endpoints if internal, API VIPs, and metadata endpoints where applicable.

Bad `NO_PROXY` design can cause internal cluster traffic to route incorrectly through the proxy.

## 23. Common Failure Scenarios and Troubleshooting

### 23.1 ImagePullBackOff

Symptoms:

```bash
oc get pods -A | grep ImagePullBackOff
oc describe pod <pod> -n <namespace>
```

Common causes:

- Image not mirrored
- Wrong mirror path
- Missing pull secret
- Registry certificate not trusted
- Registry unreachable
- IDMS/ITMS incorrect
- Firewall blocked
- DNS resolution failure

Checks:

```bash
oc describe pod <pod> -n <namespace>
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get image.config.openshift.io/cluster -o yaml
oc get secret/pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Node-level debug:

```bash
oc debug node/<node>
chroot /host
cat /etc/containers/registries.conf
curl -vk https://registry.internal.example.com/v2/
crictl pull registry.internal.example.com/path/image@sha256:<digest>
```

### 23.2 Registry Certificate Error

Symptoms:

```text
x509: certificate signed by unknown authority
```

Fix areas:

- Validate certificate chain.
- Add CA to `additionalTrustBundle` during install.
- Add CA through `image.config.openshift.io/cluster` after install.
- Confirm ConfigMap key format for registry host and port.

### 23.3 Operator Not Visible in OperatorHub

Common causes:

- CatalogSource not created
- Catalog pod failing
- Operator not included in mirror config
- Wrong catalog version
- Default sources disabled without replacement
- Marketplace namespace issue

Commands:

```bash
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
oc logs <catalog-pod> -n openshift-marketplace
oc get packagemanifest -n openshift-marketplace | grep <operator>
```

### 23.4 Cluster Upgrade Fails

Common causes:

- Target release not mirrored
- CVO cannot pull release image
- Signature validation issue
- OSUS graph missing target edge
- Registry unreachable from one or more nodes
- MachineConfigPool degraded

Commands:

```bash
oc get clusterversion -o yaml
oc adm upgrade
oc get co
oc get mcp
oc logs -n openshift-cluster-version deploy/cluster-version-operator
```

### 23.5 oc-mirror Fails

Common causes:

- Invalid credentials
- Expired pull secret
- Missing registry trust
- Insufficient disk
- Interrupted transfer
- Changed/deleted mirror metadata
- Unsupported catalog/package/version
- Registry repository permission problem

Checks:

```bash
oc mirror --config=imageset-config.yaml docker://registry.internal.example.com --dry-run
podman login registry.redhat.io
podman login registry.internal.example.com
df -h
```

### 23.6 Samples Not Working

Symptoms:

- ImageStreams fail to import
- Templates reference external images
- Builder images unavailable

Fix:

- Mirror required sample images.
- Set `samplesRegistry` to internal registry.
- Skip unused image streams.
- Use `Removed` or `Unmanaged` state until mirror is ready.

## 25. Interview and Real-World Explanation

### 25.1 Short Interview Answer

A disconnected OpenShift environment is a restricted-network deployment where cluster nodes cannot directly access the internet. Instead of pulling OpenShift release images, Operator catalogs, and application images from public registries, we mirror all required content into an internal registry such as Quay. The cluster is configured with mirror policies, pull secrets, and trusted CA bundles so all image pulls resolve internally. For Day-2 operations, we mirror new OpenShift releases, Operator updates, graph data for OSUS if needed, and approved application images through a controlled change process.

### 25.2 Senior-Level Interview Answer

In enterprise architecture, disconnected OpenShift is a complete supply-chain and lifecycle management model. The key design point is that the internet is replaced by trusted internal services: a highly available mirror registry, internal Operator catalogs, internal Git and artifact repositories, internal CA, internal DNS/NTP, and local update services. We use `oc-mirror` and declarative image-set configuration to mirror only approved OpenShift releases, Operators, Helm charts, and additional images. Then we configure the cluster using pull secrets, trust bundles, IDMS/ITMS resources, and internal CatalogSources. For production, I treat the mirror registry as critical infrastructure, design it with HA and backups, and control content promotion through dev, test, and prod stages with scanning, approval, and audit evidence.

### 25.3 What a 10-Year Engineer Should Emphasize

A junior engineer may say, “Disconnected means no internet.”

A senior engineer should say:

> Disconnected OpenShift means the external software supply chain is replaced by an internal controlled supply chain. The mirror registry, update process, catalog management, image trust, dependency repositories, and governance process become part of the platform architecture. The risk is not only installation failure; the bigger risk is Day-2 failure during upgrades, Operator updates, node replacement, certificate rotation, and application builds.

### 25.4 Real Production Scenario

Suppose a bank runs OpenShift in a restricted data center. Production nodes cannot reach public registries. The platform team mirrors OpenShift 4.20 release payloads, Red Hat Operator catalogs, UBI images, GitOps Operator, Compliance Operator, ODF Operator, and application base images into internal Quay. Security scans the content and approves it. The non-prod cluster updates first. After validation, the same image set is promoted to production. The production cluster updates using internal release images and internal update graph data. Developers build applications using internal Git and Nexus. Admission policies block images from unapproved registries. Audit teams can trace every image digest from source to production.

That is a mature disconnected architecture.

## Final Practical Summary

A disconnected OpenShift environment is not simply an offline cluster. It is an enterprise-controlled platform ecosystem. To run it successfully, you must design the mirror registry, image mirroring process, trust model, Operator catalog strategy, update workflow, developer dependency model, and governance process before installation.

The most important production lessons are:

1. Mirror registry availability is platform availability.
2. Day-2 operations are harder than installation.
3. Operator updates must match mirrored catalogs.
4. Application builds need internal dependency repositories.
5. Registry certificates and pull secrets must be managed like critical platform assets.
6. IDMS/ITMS and CatalogSources are central to disconnected operations.
7. Every mirrored image must be traceable, approved, and reproducible.
8. Test upgrades in non-prod using the same mirror process before production.
9. Document every content movement for audit and troubleshooting.
10. Treat disconnected OpenShift as a software supply chain architecture, not only a network restriction.
