## 1. Executive Summary

Authentication architecture in OpenShift defines **how users, administrators, automation tools, applications, and platform components prove their identity before accessing the cluster API**.

In enterprise architecture, OpenShift authentication is not just an `oc login` topic. It is a control-plane security design that touches:

- API server access
- Web console access
- OAuth flows
- Identity providers
- LDAP/OIDC/SSO integration
- Service accounts
- CI/CD automation
- Token lifetime
- Group synchronization
- RBAC mapping
- Audit logs
- Break-glass access
- Disaster recovery
- Multi-cluster governance
- Compliance reporting

A mature OpenShift authentication architecture should answer these questions:

| Question | Enterprise Expectation |
|---|---|
| Who can log in? | Only users from approved identity providers |
| How are users authenticated? | Corporate SSO, LDAP, OIDC, or controlled local IDP |
| How are admins separated from developers? | Group-driven RBAC and least privilege |
| How do workloads authenticate? | Service accounts with scoped tokens |
| How do CI/CD systems authenticate? | Dedicated service accounts or OAuth clients, not personal tokens |
| What happens if SSO fails? | Tested break-glass access path |
| Are tokens long-lived? | Controlled lifetime, inactivity timeout, rotation policy |
| Can access be audited? | API, OAuth, RBAC, and user activity logs retained centrally |
| Can access be reproduced after DR? | Identity, RBAC, OAuth, and secret configuration backed up |

In production, authentication should be designed as a **platform service**, not as a one-time cluster post-install step.

## 2. Authentication vs Authorization

Before designing architecture, separate two concepts clearly.

### 2.1 Authentication

Authentication answers:

> Who are you?

Examples:

- `rakesh` logs in using LDAP.
- `platform-admin@example.com` logs in using OIDC/SSO.
- A pod accesses the Kubernetes API using a service account token.
- A user authenticates with an OAuth access token.
- A break-glass admin uses a client certificate.

OpenShift authentication identifies the requestor.

### 2.2 Authorization

Authorization answers:

> What are you allowed to do?

Examples:

- Can the user create projects?
- Can the user delete pods in production?
- Can the service account use `anyuid` SCC?
- Can the CI/CD pipeline update a deployment?
- Can a developer view secrets?

OpenShift authorization is mainly implemented through Kubernetes/OpenShift RBAC, SCCs, admission controls, and cluster policies.

### 2.3 Relationship

Authentication happens first. Authorization happens after authentication.

```text
User / Client
     |
     | 1. Proves identity
     v
Authentication Layer
     |
     | 2. Produces user, group, service account identity
     v
Authorization Layer
     |
     | 3. Checks RBAC / SCC / admission / policy
     v
API Server Allows or Denies Request
```

A user can authenticate successfully and still receive:

```text
Error from server (Forbidden): ... cannot create resource ...
```

That means authentication worked, but authorization failed.

## 3. Why Authentication Architecture Matters in Enterprise OpenShift

Authentication architecture is critical because OpenShift is an API-driven platform. Almost every action flows through the API server:

- Web console actions
- `oc` CLI operations
- CI/CD deployments
- GitOps reconciliations
- Operator activity
- Monitoring access
- Admission control
- Service account calls
- Project creation
- Secrets access
- Image registry access

If authentication is weak, the entire platform risk increases.

### 3.1 Enterprise Risk Areas

| Risk Area | Example Problem | Impact |
|---|---|---|
| Weak identity source | Local users manually created without lifecycle control | Orphaned access after employee leaves |
| Shared admin account | Multiple engineers use same credentials | No accountability |
| Long-lived tokens | Personal token used in Jenkins | Credential leakage risk |
| No group mapping | Direct RBAC to individual users | Hard to audit and maintain |
| No break-glass design | SSO outage blocks cluster access | Production incident escalation failure |
| No token policy | Sessions never expire effectively | Persistent attack window |
| No audit retention | Cannot prove who changed what | Compliance failure |
| Poor service account design | Default service account has broad access | Lateral movement risk |

### 3.2 Enterprise Architecture Goal

The goal is to create a design where:

- Human users authenticate through enterprise identity systems.
- Admin access is group-based and traceable.
- Automation uses non-human identities.
- Service accounts are scoped per namespace and purpose.
- Tokens are time-bound where possible.
- Kubeadmin is removed after proper admin identity is created.
- Break-glass access exists but is protected and audited.
- Identity configuration is backed up and version-controlled where appropriate.
- Multi-cluster access is consistent and centrally governed.

```text
|                               +---------------+---------------+  |
|                                               |                  |
|                                               | Validates user   |
|                                               v                  |
|                               +-------------------------------+  |
|                               | Identity Provider              |  |

|                               +---------------+---------------+  |
|                                               |                  |
|                                               | Issues OAuth     |

|                                               v                  |
|  +-------------------+        +-------------------------------+  |

|                               +-------------------------------+  |
|                                                                  |
|  +-------------------+                                           |
```

### 4.2 Main Authentication Paths

| Path | Used By | Credential Type | Typical Use |
|---|---|---|---|
| OAuth login | Human users | OAuth token | CLI and console login |

| HTPasswd login | Local users | htpasswd file | Lab, bootstrap, emergency, small clusters |
| X.509 client certificate | Admin/system identities | Client certificate/key | Bootstrap, system admin, kubeconfig |
| Service account token | Pods/operators/automation | Bearer token | Workload access to API |
| OAuth client | External apps | Client ID/secret or redirect flow | Custom portals, integrations |

## 5. Core Components

### 5.1 API Server

The API server is the main enforcement point for authenticated requests.

A request normally includes one of the following:

- OAuth bearer token
- Service account bearer token
- X.509 client certificate
- Impersonation headers, when allowed

The API server authenticates the request, extracts identity details, then runs authorization.

Important identity attributes include:

- Username
- UID
- Groups
- Extra attributes
- Service account namespace/name

### 5.2 Internal OAuth Server

OpenShift includes an internal OAuth server. It handles user login, communicates with configured identity providers, and creates access tokens for users.

Key functions:

- Presents login flow for web console and CLI.
- Redirects users to external IdP when needed.
- Validates username/password or external identity assertion.
- Creates OpenShift user/identity linkage.
- Issues OAuth access tokens.
- Supports token duration and inactivity controls.
- Supports OAuth clients and redirect flows.

Common OAuth server resources:

```bash
oc get authentication cluster -o yaml
oc get oauth cluster -o yaml
oc get pods -n openshift-authentication
oc get route -n openshift-authentication
```

### 5.3 Authentication Operator

The Authentication Operator manages authentication-related cluster components. It reconciles the desired state from cluster configuration.

Useful checks:

```bash
oc get clusteroperator authentication
oc describe clusteroperator authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deployment/oauth-openshift
```

If authentication configuration is invalid, the operator can become degraded.

### 5.4 Identity Providers

Identity providers validate human users. Common providers include:

- `HTPasswd`
- `LDAP`
- `OpenID Connect`
- `GitHub`
- `GitLab`
- `Google`
- `Keystone`
- `RequestHeader`
- `BasicAuth`

In enterprise environments, the most common patterns are:

- OIDC with corporate SSO
- LDAP/Active Directory
- Multiple IDPs for admin/developer separation
- HTPasswd only for emergency or non-production use

### 5.5 Users and Identities

OpenShift separates **User** and **Identity** objects.

| Object | Meaning |
|---|---|
| `User` | OpenShift user representation |
| `Identity` | External identity source mapping |
| `Group` | Collection of users for RBAC assignment |

Useful commands:

```bash
oc get users
oc get identities
oc get groups
oc describe user <username>
oc describe identity <idp-name>:<idp-user>
```

Example identity name:

```text
ldap-provider:rakesh
```

This means the user `rakesh` came from the identity provider named `ldap-provider`.

### 5.6 OAuth Tokens

Human users receive OAuth access tokens after successful login.

Useful commands:

```bash
oc whoami
oc whoami -t
oc get oauthaccesstokens
oc get useroauthaccesstokens
```

Tokens are sensitive credentials. Never store personal tokens in Git, Jenkins variables, plaintext scripts, or shared jump servers.

### 5.7 Service Accounts

Service accounts are identities for workloads, controllers, operators, and automation.

Format:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

Example:

```text
system:serviceaccount:prod-cicd:deploy-bot
```

Service accounts should be scoped by namespace and purpose.

### 5.8 RBAC

RBAC is not authentication, but it depends on authentication output.

After authentication, RBAC decides whether the request is allowed.

Useful commands:

```bash
oc auth can-i create pods -n myproject
oc auth can-i create routes -n myproject --as rakesh
oc auth can-i '*' '*' --as system:serviceaccount:prod:deploy-bot -n prod
```

## 6. Identity Lifecycle in OpenShift

### 6.1 User Login Lifecycle

```text
1. User accesses console or runs oc login.
2. OpenShift OAuth server starts authentication flow.
3. OAuth server sends credentials or redirect to identity provider.
4. Identity provider validates user.
5. OAuth server maps external identity to OpenShift identity.
6. OpenShift creates or updates Identity/User objects.
7. OAuth server issues access token.
8. User sends token to API server.
9. API server authenticates token.
10. RBAC checks permissions.
11. Request is allowed or denied.
```

### 6.2 Identity Mapping

OpenShift maps external identity to internal user.

Example:

```text
External LDAP username: rjha
IDP name: corporate-ldap
OpenShift identity: corporate-ldap:rjha
OpenShift user: rjha
Groups: ocp-prod-admins, ocp-viewers
```

### 6.3 User Deprovisioning

Removing a user from LDAP/SSO stops future login, but existing tokens and existing OpenShift `User` objects may still need operational cleanup depending on policy.

Recommended process:

```bash
# Review user and tokens
oc get user <username>
oc get useroauthaccesstokens | grep <username>

# Remove direct RBAC bindings if any exist
oc get rolebinding,clusterrolebinding -A -o wide | grep <username>

# Prefer group-based RBAC so removing user from corporate group is enough
```

For high-security environments, revoke tokens and clean direct bindings when offboarding privileged users.

## 7. Authentication Request Flow

### 7.1 CLI Login Flow

Command:

```bash
oc login https://api.ocp.example.com:6443
```

Flow:

```text
oc CLI
  |
  | Requests login
  v
OAuth Server
  |
  | Validates user through configured IDP
  v
Identity Provider
  |
  | Success
  v
OAuth Server issues token
  |
  v
oc CLI stores token in kubeconfig
  |
  v
Future oc commands use bearer token
  |
  v
API Server authenticates token and checks RBAC
```

The token is stored in kubeconfig, normally under:

```bash
~/.kube/config
```

Security implication:

- Protect kubeconfig like a password.
- Do not copy admin kubeconfig to shared systems.
- Do not commit kubeconfig to Git.

### 7.2 Console Login Flow

```text
Browser
  |
  v
OpenShift Web Console
  |
  v
OAuth Login Route
  |
  v
Identity Provider Login
  |
  v
OAuth Callback
  |
  v
Console Session Established
  |
  v
API calls made using user token
```

### 7.3 API Token Flow

After login, an API request looks like:

```bash
curl -k \
  -H "Authorization: Bearer $(oc whoami -t)" \
  https://api.ocp.example.com:6443/apis/project.openshift.io/v1/projects
```

The API server validates the bearer token and authorizes the request.

### 7.4 Service Account Token Flow

Inside a pod:

```text
Pod
  |
  | Mounted service account token
  v
Kubernetes API Server
  |
  | Authenticates as system:serviceaccount:namespace:name
  v
RBAC Check
  |
  v
Allowed / Forbidden
```

Default token path in many pod patterns:

```text
/var/run/secrets/kubernetes.io/serviceaccount/token
```

Modern designs should prefer projected, audience-bound, time-bound service account tokens where possible.

## 8. Human User Authentication Patterns

### 8.1 Pattern 1: Corporate OIDC/SSO

Best for large enterprises.

```text
OpenShift OAuth Server <----OIDC----> Corporate Identity Provider
                                         Azure AD / Keycloak / Okta / Ping / RH-SSO
```

Benefits:

- Centralized MFA
- Centralized password policy
- Joiner/mover/leaver lifecycle
- Conditional access
- Enterprise audit integration
- Federation across multiple clusters

Considerations:

- OIDC claim mapping must be carefully designed.
- Group claim size can become large.
- Break-glass access is required if SSO is down.
- TLS trust for IdP endpoints must be correct.

Recommended use:

- Production clusters
- Multi-cluster environments
- Regulated workloads
- Shared enterprise platforms

### 8.2 Pattern 2: LDAP / Active Directory

Common in on-prem enterprise environments.

```text
OpenShift OAuth Server <----LDAP bind----> Active Directory / LDAP
```

Benefits:

- Integrates with existing corporate directory.
- Simple username/password model.
- Works well in disconnected or restricted environments.
- Supports LDAP group sync with OpenShift groups.

Considerations:

- Use LDAPS or StartTLS.
- Do not use insecure LDAP bind over plaintext networks.
- Bind account must be protected.
- Group sync requires scheduled operation and monitoring.
- LDAP outage can block new logins.

### 8.3 Pattern 3: HTPasswd

HTPasswd is useful for:

- Lab clusters
- Training environments
- Initial bootstrap
- Emergency access
- Small non-production clusters

It is generally not ideal as the primary enterprise identity provider because it lacks centralized lifecycle management.

### 8.4 Pattern 4: Multiple Identity Providers

Example:

```yaml
identityProviders:
- name: corporate-oidc
  type: OpenID
- name: emergency-admins
  type: HTPasswd
```

Use cases:

- Corporate SSO for normal users
- HTPasswd for emergency break-glass users
- Separate external partner identity source
- Migration from LDAP to OIDC

Design warning:

- Usernames from multiple IDPs can collide.
- Identity provider names must be meaningful and stable.
- RBAC should use groups, not direct users, wherever possible.

## 9. Machine and Workload Authentication Patterns

### 9.1 Workload-to-API Access

Pods use service accounts.

Example:

```bash
oc create sa app-reader -n app-prod
oc adm policy add-role-to-user view \
  system:serviceaccount:app-prod:app-reader \
  -n app-prod
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
  namespace: app-prod
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app
  template:
    metadata:
      labels:
        app: app
    spec:
      serviceAccountName: app-reader
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi
        command: ["sleep", "infinity"]
```

### 9.2 CI/CD Authentication

Avoid this pattern:

```text
Jenkins uses a human admin user's personal token
```

Use this pattern:

```text
Jenkins/GitLab/ArgoCD uses dedicated service account or OAuth client
```

Example:

```bash
oc create sa deploy-bot -n prod-cicd
oc adm policy add-role-to-user edit \
  system:serviceaccount:prod-cicd:deploy-bot \
  -n app-prod
```

Better design:

- Separate service account per environment.
- Separate service account per application team.
- Minimal RBAC role required for deployment.
- Rotate credentials periodically.
- Store tokens only in secure secret managers.
- Prefer GitOps controller identity for continuous reconciliation.

### 9.3 Operator Authentication

Operators usually run with service accounts and ClusterRoles.

Architecture considerations:

- Review operator ClusterRole permissions before production install.
- Avoid installing unnecessary operators with broad cluster permissions.
- Keep operators in dedicated namespaces.
- Monitor operator service account token usage.
- Ensure OLM-managed RBAC is understood by the platform team.

## 10. Identity Provider Architecture

### 10.1 Identity Provider Selection Matrix

| Provider | Enterprise Use | Strength | Weakness |
|---|---|---|---|
| OIDC | Strongly recommended | SSO, MFA, federation | Requires IdP and claim design |
| LDAP/AD | Common on-prem | Existing directory integration | Bind/TLS/group sync complexity |
| HTPasswd | Lab/break-glass | Simple, local | Poor lifecycle management |
| GitHub/GitLab | Dev-oriented | Easy developer login | Enterprise compliance depends on org setup |
| Keystone | OpenStack environments | Shared auth with OpenStack | Niche use case |
| RequestHeader | Advanced proxy auth | Integrates with front proxy | Requires strict header trust design |
| BasicAuth | Legacy/generic | Simple backend integration | Less preferred for modern SSO |

### 10.2 IDP Naming Strategy

Good names:

```text
corp-oidc
corp-ldap
breakglass-htpasswd
partner-github
```

Bad names:

```text
idp1
ldap
test
openshift
```

Why names matter:

- Identity objects include the IDP name.
- Migration becomes difficult if names are unclear.
- Audit logs are easier to interpret with meaningful names.
- Multiple IDPs require collision-safe naming.

### 10.3 Mapping Method Strategy

Identity mapping controls how identities map to users.

Common strategies include:

- `claim`
- `lookup`
- `add`
- `generate`

Enterprise guidance:

| Mapping Method | Typical Use |
|---|---|
| `claim` | One external identity claims a username; avoid conflicting identities |
| `lookup` | Strict pre-created users only; useful for controlled environments |
| `add` | Add identity to existing user when possible |
| `generate` | Generate unique usernames to avoid collision |

For production, avoid accidental user collisions when multiple IDPs exist.

### 10.4 Certificate Trust for IDPs

For LDAP over TLS, OIDC using private CA, GitHub Enterprise, or custom SSO endpoints, OpenShift must trust the provider CA.

Common pattern:

```bash
oc create configmap idp-ca \
  --from-file=ca.crt=/path/to/ca.crt \
  -n openshift-config
```

Then reference the CA config map in the OAuth configuration.

Architecture rule:

> Never disable TLS verification to make authentication work. Fix CA trust properly.

## 11. OAuth Server Architecture

### 11.1 Role of the Internal OAuth Server

The OpenShift OAuth server is the broker between users and the OpenShift API.

It performs these functions:

- Accepts login requests from console and CLI.
- Talks to configured identity providers.
- Handles OAuth grant flows.
- Issues access tokens.
- Manages user-owned OAuth tokens.
- Supports OAuth client integrations.
- Supports token lifetime and inactivity timeout.

### 11.2 Important Namespaces

| Namespace | Purpose |
|---|---|
| `openshift-authentication` | OAuth server pods and authentication components |
| `openshift-authentication-operator` | Authentication operator |
| `openshift-config` | Cluster authentication configuration secrets/configmaps |
| `openshift-config-managed` | Managed rendered configuration |

Useful commands:

```bash
oc get pods -n openshift-authentication
oc get deployment -n openshift-authentication
oc get clusteroperator authentication
oc get secret -n openshift-config
oc get configmap -n openshift-config
```

### 11.3 OAuth Configuration Object

The cluster OAuth configuration is named `cluster`.

```bash
oc get oauth cluster -o yaml
```

Example skeleton:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corp-oidc
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift
      clientSecret:
        name: oidc-client-secret
      issuer: https://sso.example.com/auth/realms/platform
      claims:
        preferredUsername:
        - preferred_username
        name:
        - name
        email:
        - email
```

### 11.4 OAuth Server Token Duration

Default user OAuth tokens are commonly configured with a maximum age. Production platforms should review:

- Access token lifetime
- Inactivity timeout
- OAuth client-specific timeout
- Session expectations for console users
- Automation impact

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  tokenConfig:
    accessTokenMaxAgeSeconds: 86400
```

### 11.5 OAuth Inactivity Timeout

Inactivity timeout helps reduce risk from forgotten sessions.

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  tokenConfig:
    accessTokenInactivityTimeout: 30m
```

Design advice:

| Environment | Suggested Policy |
|---|---|
| Lab | Longer sessions acceptable |
| Dev | Moderate timeout |
| Production | Shorter inactivity timeout for privileged users |
| Regulated | Align with security policy and audit requirements |

## 12. Token Architecture

### 12.1 Token Types

| Token Type | Used By | Scope |
|---|---|---|
| OAuth access token | Human users | User access to API |
| UserOAuthAccessToken | User-owned OAuth token view | User-scoped token visibility |
| Service account token | Pods/controllers | Service account API access |
| Bound service account token | Modern workload auth | Audience/time-bound access |
| OAuth authorize token | OAuth flow | Temporary authorization flow |

### 12.2 Personal Token Risk

Personal tokens are dangerous when used for automation.

Bad example:

```bash
export TOKEN=sha256~personal-user-token
oc login --token=$TOKEN --server=https://api.ocp.example.com:6443
```

Problems:

- Token belongs to a human.
- Hard to rotate safely.
- Access changes with user role.
- Audit shows human identity, not automation identity.
- User departure can break pipeline.

### 12.3 Service Account Token Best Practice

Good pattern:

```text
Each automation system gets a named service account.
Each service account gets minimum required RBAC.
Each service account is tied to a namespace and purpose.
Tokens are stored in a secret manager.
```

### 12.4 Bound Service Account Tokens

Bound service account tokens improve security because they can be:

- Time-bound
- Audience-bound
- Mounted through projected volumes
- Requested using the TokenRequest API

Example projected token:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: token-demo
  namespace: app-prod
spec:
  serviceAccountName: app-reader
  containers:
  - name: app
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "infinity"]
    volumeMounts:
    - name: api-token
      mountPath: /var/run/secrets/tokens
  volumes:
  - name: api-token
    projected:
      sources:
      - serviceAccountToken:
          path: token
          expirationSeconds: 3600
          audience: https://kubernetes.default.svc
```

## 13. Certificate-Based Authentication

### 13.1 X.509 Client Certificates

OpenShift and Kubernetes can authenticate clients using X.509 certificates.

Typical examples:

- Bootstrap kubeconfig
- `kubeadmin`/installation access path
- `system:admin` kubeconfig
- Control plane component credentials
- Some advanced automation integrations

### 13.2 Certificate Identity

The username usually comes from the certificate subject CN, and groups can come from O fields depending on Kubernetes client certificate authentication behavior.

Example conceptual certificate subject:

```text
CN=system:admin,O=system:masters
```

This represents a highly privileged identity.

### 13.3 Enterprise Guidance

- Do not distribute `system:admin` kubeconfig broadly.
- Store break-glass kubeconfig in a secure vault.
- Require approval to retrieve break-glass credentials.
- Rotate certificates according to security policy.
- Audit every use of certificate-based admin access.
- Prefer named human identities through SSO for normal administration.

### 13.4 Difference Between kubeadmin and system:admin

| Identity | Usage | Risk |
|---|---|---|
| `kubeadmin` | Initial cluster admin login after install | Should be removed after real admin exists |
| `system:admin` | Certificate-based privileged identity | Break-glass/system-level use only |

Production rule:

> Create a real cluster-admin user or group through enterprise IDP first. Then remove kubeadmin.

## 14. Service Account Authentication

### 14.1 What is a Service Account?

A service account is a namespaced identity used by pods and automation to access the API.

Default service accounts per namespace usually include:

```text
default
builder
deployer
```

Additional service accounts should be created for specific use cases.

### 14.2 Service Account Naming

Good names:

```text
deploy-bot
backup-reader
metrics-scraper
argocd-application-controller
image-pruner
```

Bad names:

```text
admin
sa1
test
root
```

### 14.3 Service Account RBAC Example

```bash
oc create sa deploy-bot -n app-prod

oc adm policy add-role-to-user edit \
  system:serviceaccount:app-prod:deploy-bot \
  -n app-prod
```

Test:

```bash
oc auth can-i update deployment \
  --as system:serviceaccount:app-prod:deploy-bot \
  -n app-prod
```

### 14.4 Service Account and SCC

Authentication identifies the service account. Authorization and SCC admission decide whether the pod can run with requested security settings.

Example:

```bash
oc adm policy add-scc-to-user anyuid \
  -z app-sa \
  -n app-prod
```

The identity becomes:

```text
system:serviceaccount:app-prod:app-sa
```

Use SCC assignment carefully. Avoid broad SCC privileges for default service accounts.

## 15. OAuth Clients and External Integrations

### 15.1 What is an OAuth Client?

An OAuth client is an application that requests user authentication through the OpenShift OAuth server.

Examples:

- OpenShift web console
- CLI login flow
- Custom developer portal
- Dashboard integration
- Service account as OAuth client

### 15.2 Default OAuth Clients

OpenShift includes default OAuth clients for platform functions such as console and CLI flows.

Useful commands:

```bash
oc get oauthclients
oc describe oauthclient <client-name>
```

### 15.3 Registering a Custom OAuth Client

Example:

```yaml
apiVersion: oauth.openshift.io/v1
kind: OAuthClient
metadata:
  name: custom-portal
secret: redhat123
redirectURIs:
- https://portal.example.com/oauth/callback
grantMethod: prompt
```

Apply:

```bash
oc apply -f oauthclient.yaml
```

Design guidance:

- Use secure redirect URIs.
- Avoid wildcard or broad redirects.
- Store client secrets securely.
- Use prompt grants unless auto-approval is explicitly justified.
- Review client access periodically.

### 15.4 Service Account as OAuth Client

Service accounts can be used as OAuth clients for certain integration patterns.

Use cases:

- Application wants OpenShift OAuth login.
- Namespace-scoped app integrates with OAuth.
- Internal tools need user login delegated to OpenShift.

Architecture caution:

- Do not confuse service account OAuth client identity with service account API token identity.
- Document which integration uses which authentication flow.

## 17. Enterprise Group and Role Design

### 17.1 Group-First Design

Avoid direct RBAC to individual users.

Bad:

```bash
oc adm policy add-cluster-role-to-user cluster-admin rakesh
```

Good:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
```

Then manage group membership in LDAP/SSO.

### 17.2 Recommended Enterprise Groups

| Group | Purpose | Scope |
|---|---|---|
| `ocp-platform-admins` | Full cluster administration | Cluster-wide |
| `ocp-security-admins` | Security configuration, SCC, policies | Cluster-wide limited |
| `ocp-operators-admins` | Operator lifecycle management | Cluster-wide or selected namespaces |
| `ocp-project-creators` | Create projects | Cluster-wide limited |
| `app-dev-<team>` | Developer edit access | Namespace |
| `app-view-<team>` | Read-only access | Namespace |
| `app-prod-release-managers` | Production deployment access | Production namespaces |
| `ocp-auditors` | Read-only audit/compliance | Cluster-wide view |
| `ocp-breakglass-admins` | Emergency admin access | Cluster-wide, tightly controlled |

### 17.3 Role Separation

| Role | Should Have | Should Not Have |
|---|---|---|
| Platform Admin | Cluster lifecycle, nodes, operators, auth config | App secret ownership unless required |
| Security Admin | SCC, security policies, compliance | Daily app deployments |
| Developer | App resources in dev/test | ClusterRole modification |
| Release Manager | Controlled prod rollout | Cluster-admin |
| Auditor | Read access to state/logs | Write access |
| CI/CD Bot | Deploy permissions | Human login capability |

### 17.4 Naming Convention

Recommended format:

```text
ocp-<env>-<team>-<role>
```

Examples:

```text
ocp-prod-platform-admins
ocp-prod-payments-edit
ocp-prod-payments-view
ocp-dev-project-creators
ocp-dr-breakglass-admins
```

## 18. Multi-Cluster Authentication Architecture

### 18.1 Problem Statement

Enterprises rarely run only one OpenShift cluster. They often run:

- Dev cluster
- Test cluster
- Staging cluster
- Production cluster
- DR cluster
- Edge clusters
- Management/hub cluster
- Dedicated business-unit clusters

Authentication architecture must be consistent across all clusters.

### 18.2 Recommended Multi-Cluster Pattern

```text
                         +----------------------+
                         | Enterprise IdP / SSO |
                         | OIDC / LDAP / MFA    |
                         +----------+-----------+
                                    |
          +-------------------------+-------------------------+
          |                         |                         |
          v                         v                         v
+-------------------+     +-------------------+     +-------------------+
| OCP Dev Cluster   |     | OCP Test Cluster  |     | OCP Prod Cluster  |
| OAuth -> SSO      |     | OAuth -> SSO      |     | OAuth -> SSO      |
+-------------------+     +-------------------+     +-------------------+
          |                         |                         |
          v                         v                         v
   Group-based RBAC          Group-based RBAC          Group-based RBAC
```

### 18.3 Design Rules

- Use the same IDP type across clusters where possible.
- Use consistent IDP names.
- Use consistent group naming.
- Use different RBAC bindings per environment.
- Use stricter token and admin policies in production.
- Ensure DR cluster can authenticate if primary IdP dependency is unavailable.
- Store OAuth configuration as GitOps-managed YAML where appropriate.

### 18.4 Environment-Specific RBAC

Same user, different access by cluster:

| User Group | Dev | Test | Prod |
|---|---|---|---|
| `payments-devs` | edit | edit | view |
| `payments-release` | view | edit | edit/controlled |
| `platform-admins` | admin | admin | admin |
| `auditors` | view | view | view |

## 19. Hub-Spoke and ACM-Oriented Design

### 19.1 Hub-Spoke Concept

In Advanced Cluster Management style architecture:

```text
                 +----------------------+
                 | ACM Hub Cluster      |
                 | Governance / Policy  |
                 +----------+-----------+
                            |
       +--------------------+--------------------+
       |                    |                    |
       v                    v                    v
+--------------+     +--------------+     +--------------+
| Spoke Dev    |     | Spoke Prod   |     | Spoke DR     |
+--------------+     +--------------+     +--------------+
```

Authentication design must define:

- Who can access the hub?
- Who can manage managed clusters?
- Who can push policies?
- Who can view compliance?
- Who can access spoke clusters directly?

### 19.2 Hub Cluster Authentication

The hub is highly sensitive because it can govern multiple clusters.

Recommended controls:

- OIDC/SSO with MFA.
- Separate hub admin group.
- No broad developer access to hub.
- Audit logging enabled and forwarded.
- Break-glass path secured.
- GitOps-controlled RBAC and policies.

### 19.3 Spoke Cluster Authentication

Spokes should still have their own authentication configuration.

Do not rely only on hub access. During hub outage or network partition, platform admins may need direct spoke access.

### 19.4 Governance Policies

Use policies to enforce:

- OAuth configuration standard.
- Kubeadmin removal.
- Required IDP presence.
- Required admin groups.
- Disallowed direct cluster-admin users.
- Service account token best practices.
- Audit log profile.

## 20. DR and Break-Glass Authentication Design

### 20.1 Why Break-Glass Matters

Authentication dependencies can fail:

- Corporate SSO outage
- LDAP outage
- DNS outage
- CA trust issue
- Expired IdP certificate
- Misconfigured OAuth object
- Network issue between cluster and IdP
- Accidental removal of admin RBAC

A production cluster must have an emergency access model.

### 20.2 Break-Glass Requirements

A good break-glass design includes:

- Separate emergency identity provider or certificate path.
- Credentials stored in a secure vault.
- Dual approval process.
- Rotation after use.
- Monitoring and alerting on use.
- Explicit documentation.
- Regular testing.

### 20.3 Break-Glass Options

| Option | Use Case | Risk |
|---|---|---|
| HTPasswd emergency admin | SSO/LDAP outage | Local password management |
| Certificate kubeconfig | Deep control-plane recovery | Very high privilege |
| Secondary OIDC/LDAP | Identity provider redundancy | More complexity |
| Bastion vault retrieval | Controlled emergency process | Operational dependency |

### 20.4 DR Cluster Design

DR cluster authentication must be tested independently.

Check:

- Can admins log in to DR if primary region is down?
- Is the IdP reachable from DR?
- Are CA bundles restored?
- Are OAuth secrets restored?
- Are RBAC bindings restored?
- Are break-glass users available?
- Are DNS names updated?
- Does the console route work?

### 20.5 Backup Scope

Back up at least:

```text
OAuth configuration
IDP secrets
CA config maps
RBAC objects
Groups
OAuthClient objects
ServiceAccounts
ClusterRoleBindings
RoleBindings
Project templates
Audit policy configuration
```

Be careful with secrets. Backups must be encrypted and access-controlled.

## 21. Security Hardening

### 21.1 Remove kubeadmin After Real Admin Exists

Production flow:

```bash
# 1. Configure enterprise IDP
oc apply -f oauth-idp.yaml

# 2. Login as real admin user
oc login -u platform-admin

# 3. Grant cluster-admin to admin group
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins

# 4. Verify access
oc auth can-i '*' '*' --all-namespaces

# 5. Remove kubeadmin only after verification
oc delete secret kubeadmin -n kube-system
```

Warning:

> Do not remove kubeadmin until another working cluster-admin identity is confirmed.

### 21.2 Enforce Group-Based Admin

Avoid permanent direct cluster-admin to users.

Check direct users:

```bash
oc get clusterrolebinding -o custom-columns=NAME:.metadata.name,SUBJECTS:.subjects
```

Look for subjects of kind `User` with powerful roles.

### 21.3 Protect OAuth Secrets

OAuth secrets in `openshift-config` can contain:

- OIDC client secrets
- LDAP bind credentials
- Client certificates
- Private keys

Controls:

- Restrict access to `openshift-config` namespace.
- Enable etcd encryption where required.
- Avoid dumping secrets in support logs.
- Rotate after suspected exposure.
- Store source-of-truth secrets in a vault.

### 21.4 Token Lifetime Policy

Recommended:

- Use default or shorter lifetimes for privileged users.
- Configure inactivity timeout in production.
- Avoid never-expiring personal tokens.
- Use service accounts for automation.
- Rotate service account credentials.
- Revoke tokens after user offboarding.

### 21.5 TLS Hardening

Authentication depends heavily on TLS.

Check:

- API server certificate validity.
- Console route certificate validity.
- OAuth route certificate validity.
- IdP certificate validity.
- LDAP CA trust.
- OIDC issuer certificate chain.
- Corporate proxy certificates if used.

### 21.6 Avoid Insecure LDAP

Do not use simple bind over plaintext networks.

Prefer:

```text
LDAPS on 636
StartTLS on 389
Private network + TLS
Dedicated low-privilege bind account
```

### 21.7 Service Account Hardening

- Do not use default service account for privileged apps.
- Disable unnecessary automounting where possible.
- Use projected tokens.
- Bind only required roles.
- Review ClusterRoles granted to service accounts.
- Avoid adding broad SCCs to all service accounts.

Example:

```yaml
automountServiceAccountToken: false
```

Use this for pods that do not need API access.

## 24. Operational Runbooks

### 24.1 Runbook: Add LDAP IDP

High-level steps:

```text
1. Collect LDAP URL, bind DN, bind password, CA certificate.
2. Create bind password secret in openshift-config.
3. Create LDAP CA config map if using private CA.
4. Patch OAuth cluster configuration.
5. Monitor authentication operator.
6. Test login with normal user.
7. Verify user and identity objects.
8. Bind LDAP-synced groups to RBAC.
9. Document rollback procedure.
```

Commands:

```bash
oc create secret generic ldap-bind-password \
  --from-literal=bindPassword='REDACTED' \
  -n openshift-config

oc create configmap ldap-ca \
  --from-file=ca.crt=ldap-ca.crt \
  -n openshift-config

oc apply -f oauth-ldap.yaml

oc get co authentication
oc logs -n openshift-authentication deployment/oauth-openshift
```

### 24.2 Runbook: Add OIDC IDP

```text
1. Confirm OIDC issuer URL.
2. Confirm client ID and secret.
3. Confirm redirect URI expected by IdP.
4. Confirm claims: preferred_username, name, email, groups if used.
5. Create client secret in openshift-config.
6. Create CA config map if private CA.
7. Apply OAuth config.
8. Test login.
9. Verify username mapping.
10. Verify group/RBAC mapping.
```

Commands:

```bash
oc create secret generic oidc-client-secret \
  --from-literal=clientSecret='REDACTED' \
  -n openshift-config

oc apply -f oauth-oidc.yaml
oc get co authentication
```

### 24.3 Runbook: Remove kubeadmin

```text
1. Configure real IDP.
2. Create admin group.
3. Bind cluster-admin to admin group.
4. Login as admin user from IDP.
5. Confirm cluster-admin rights.
6. Store break-glass process.
7. Delete kubeadmin secret.
8. Confirm kubeadmin login no longer works.
```

Commands:

```bash
oc adm policy add-cluster-role-to-group cluster-admin ocp-platform-admins
oc auth can-i '*' '*' --all-namespaces
oc delete secret kubeadmin -n kube-system
```

### 24.4 Runbook: Rotate OIDC Client Secret

```text
1. Create new client secret in external IdP.
2. Update OpenShift secret in openshift-config.
3. Wait for authentication operator reconciliation.
4. Test login.
5. Remove old secret from IdP.
6. Record change in change management.
```

Command:

```bash
oc create secret generic oidc-client-secret \
  --from-literal=clientSecret='NEW_SECRET' \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

### 24.5 Runbook: Emergency IDP Failure

```text
1. Confirm API server health.
2. Confirm OAuth pod health.
3. Check IDP reachability from cluster/network.
4. Check DNS resolution.
5. Check IdP certificate expiry.
6. Check OAuth logs.
7. Use break-glass access only if required.
8. Restore IDP or rollback OAuth change.
9. Rotate break-glass credentials if used.
10. Perform incident review.
```


## 25. Troubleshooting Guide

### 25.1 User Cannot Login

Symptoms:

```text
Login failed
401 Unauthorized
Invalid credentials
OAuth error
```

Check:

```bash
oc get co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deployment/oauth-openshift
oc get oauth cluster -o yaml
```

Common causes:

| Cause | Fix |
|---|---|
| Wrong password | Verify at IdP |
| User not in allowed group | Update IdP/group policy |
| LDAP bind failure | Check bind DN/password |
| TLS trust issue | Fix CA config map |
| OIDC issuer mismatch | Correct issuer URL |
| Wrong claim mapping | Fix preferredUsername/name/email claims |
| OAuth config invalid | Check operator status and events |

### 25.2 Authentication Operator Degraded

Check:

```bash
oc describe co authentication
oc get events -A | grep -i authentication
oc logs -n openshift-authentication-operator deployment/authentication-operator
```

Common causes:

- Invalid OAuth YAML
- Missing secret referenced by IDP
- Missing CA config map
- Invalid certificate
- Route/certificate problem
- OAuth pod crashloop

### 25.3 LDAP Login Fails

Check:

```bash
ldapsearch -H ldaps://ldap.example.com:636 \
  -D "cn=bind,dc=example,dc=com" \
  -W \
  -b "ou=users,dc=example,dc=com" \
  "(uid=rakesh)"
```

Inside cluster or bastion:

```bash
openssl s_client -connect ldap.example.com:636 -showcerts
```

Common issues:

- Wrong bind DN
- Wrong base DN
- Wrong user filter
- Expired LDAP certificate
- Missing LDAP CA
- Firewall blocking 636
- LDAP account locked

### 25.4 OIDC Login Fails

Check OIDC discovery:

```bash
curl -vk https://sso.example.com/.well-known/openid-configuration
```

Check:

- Issuer URL exactly matches token issuer.
- Client secret is correct.
- Redirect URI is registered in IdP.
- Required claims exist.
- CA trust is correct.
- Group claim is not too large.

### 25.5 User Logs In But Has No Access

This is usually authorization, not authentication.

Check:

```bash
oc whoami
oc get user $(oc whoami) -o yaml
oc get groups | grep <username>
oc auth can-i get pods -n <namespace>
oc get rolebinding,clusterrolebinding -A -o wide | grep <username>
```

Fix:

- Add user to correct group in IdP.
- Sync LDAP groups if needed.
- Create RoleBinding/ClusterRoleBinding to group.
- Avoid direct user binding unless temporary.

### 25.6 Service Account Forbidden

Symptoms:

```text
User "system:serviceaccount:app:deploy-bot" cannot update resource "deployments"
```

Check:

```bash
oc auth can-i update deployments \
  --as system:serviceaccount:app:deploy-bot \
  -n app

oc get rolebinding -n app -o wide
oc get clusterrolebinding -o wide | grep deploy-bot
```

Fix:

```bash
oc adm policy add-role-to-user edit \
  system:serviceaccount:app:deploy-bot \
  -n app
```

### 25.7 Token Expired

Symptoms:

```text
You must be logged in to the server
Unauthorized
```

Fix:

```bash
oc login https://api.ocp.example.com:6443
```

Check token duration and inactivity policy.

### 25.8 Changed OAuth Config but Login Still Fails

Check reconciliation:

```bash
oc get co authentication
oc rollout status deployment/oauth-openshift -n openshift-authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deployment/oauth-openshift
```

Potential fixes:

- Ensure referenced secret exists in `openshift-config`.
- Ensure referenced config map exists in `openshift-config`.
- Check YAML indentation and field names.
- Check operator events.
- Roll back to previous OAuth config if needed.

## 26. Reference Configuration Examples

### 26.1 HTPasswd IDP

Create htpasswd file:

```bash
htpasswd -c -B -b users.htpasswd admin StrongPassword123
htpasswd -B -b users.htpasswd rakesh StrongPassword123
```

Create secret:

```bash
oc create secret generic htpass-secret \
  --from-file=htpasswd=users.htpasswd \
  -n openshift-config
```

OAuth config:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: emergency-htpasswd
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpass-secret
```

Apply:

```bash
oc apply -f oauth-htpasswd.yaml
```

### 26.2 LDAP IDP

Create bind secret:

```bash
oc create secret generic ldap-bind-password \
  --from-literal=bindPassword='REDACTED' \
  -n openshift-config
```

Create CA config map:

```bash
oc create configmap ldap-ca \
  --from-file=ca.crt=ldap-ca.crt \
  -n openshift-config
```

OAuth config:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corp-ldap
    mappingMethod: claim
    type: LDAP
    ldap:
      url: "ldaps://ldap.example.com/ou=users,dc=example,dc=com?uid"
      bindDN: "cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com"
      bindPassword:
        name: ldap-bind-password
      ca:
        name: ldap-ca
      attributes:
        id:
        - dn
        preferredUsername:
        - uid
        name:
        - cn
        email:
        - mail
```

### 26.3 OIDC IDP

Create client secret:

```bash
oc create secret generic oidc-client-secret \
  --from-literal=clientSecret='REDACTED' \
  -n openshift-config
```

OAuth config:

```yaml
apiVersion: config.openshift.io/v1
kind: OAuth
metadata:
  name: cluster
spec:
  identityProviders:
  - name: corp-oidc
    mappingMethod: claim
    type: OpenID
    openID:
      clientID: openshift-console
      clientSecret:
        name: oidc-client-secret
      issuer: https://sso.example.com/realms/platform
      claims:
        preferredUsername:
        - preferred_username
        name:
        - name
        email:
        - email
```

### 26.9 LDAP Group Sync Concept

Example sync configuration skeleton:

```yaml
kind: LDAPSyncConfig
apiVersion: v1
url: ldaps://ldap.example.com:636
bindDN: cn=openshift-bind,ou=serviceaccounts,dc=example,dc=com
bindPassword: REDACTED
ca: ldap-ca.crt
rfc2307:
  groupsQuery:
    baseDN: ou=groups,dc=example,dc=com
    scope: sub
    filter: "(objectClass=groupOfNames)"
  groupUIDAttribute: dn
  groupNameAttributes: [ cn ]
  groupMembershipAttributes: [ member ]
  usersQuery:
    baseDN: ou=users,dc=example,dc=com
    scope: sub
  userUIDAttribute: dn
  userNameAttributes: [ uid ]
```

Run sync:

```bash
oc adm groups sync --sync-config=ldap-sync.yaml --confirm
```

## 27. Production Design Checklist

### 27.1 Identity Provider

- [ ] Primary enterprise IDP configured.
- [ ] IDP name is meaningful and stable.
- [ ] TLS CA trust is configured.
- [ ] Bind secrets/client secrets stored securely.
- [ ] MFA enforced at external IdP where required.
- [ ] Claims and username mapping tested.
- [ ] Group mapping/sync tested.
- [ ] IDP outage behavior documented.

### 27.2 Admin Access

- [ ] Cluster-admin assigned to group, not individual user.
- [ ] Minimum number of cluster-admin users.
- [ ] Break-glass access documented.
- [ ] Break-glass credentials stored in vault.
- [ ] kubeadmin removed after real admin exists.
- [ ] system:admin kubeconfig protected.

### 27.3 RBAC

- [ ] Group-first RBAC model.
- [ ] No unnecessary direct user bindings.
- [ ] No broad `system:authenticated` grants.
- [ ] Project creation controlled.
- [ ] Production access separated from dev/test.
- [ ] Auditors have read-only access.

### 27.4 Tokens

- [ ] OAuth token max age reviewed.
- [ ] Inactivity timeout configured if required.
- [ ] Personal tokens not used in automation.
- [ ] Service account tokens scoped.
- [ ] Bound tokens used where possible.
- [ ] Token rotation process exists.

### 27.5 Service Accounts

- [ ] Dedicated service accounts per workload/automation.
- [ ] Default service account not privileged.
- [ ] `automountServiceAccountToken: false` used where possible.
- [ ] SCC assignments reviewed.
- [ ] ClusterRoleBindings to service accounts reviewed.

### 27.6 Observability and Audit

- [ ] Authentication operator monitored.
- [ ] OAuth pod logs collected.
- [ ] OAuth route monitored.
- [ ] IDP endpoint monitored.
- [ ] Audit logs centralized.
- [ ] Alerts for RBAC and OAuth changes.
- [ ] Break-glass usage alert configured.

### 27.7 Backup and DR

- [ ] OAuth config backed up.
- [ ] IDP secrets backed up securely.
- [ ] CA config maps backed up.
- [ ] RBAC backed up.
- [ ] Groups backed up or recoverable from IdP.
- [ ] OAuthClients backed up.
- [ ] DR login tested.
- [ ] Break-glass tested in DR.

## 28. Interview and Real-World Scenario Questions

### Question 1: A user can log in but cannot create pods. Where is the issue?

Authentication succeeded. The issue is authorization. Check RBAC:

```bash
oc auth can-i create pods --as <user> -n <namespace>
oc get rolebinding -n <namespace>
oc get clusterrolebinding
```

### Question 2: Why should kubeadmin be removed?

`kubeadmin` is an initial bootstrap admin account. In enterprise production, admin access should be through named users and enterprise identity providers. Keeping kubeadmin increases risk and weakens accountability.

### Question 3: Why is group-based RBAC better than user-based RBAC?

Group-based RBAC supports enterprise lifecycle management. When a user joins, moves, or leaves, access can be managed from LDAP/SSO groups instead of editing cluster bindings for each user.

### Question 4: Jenkins needs deployment access. Should you use your personal token?

No. Create a dedicated service account with minimum required access and store its token securely.

### Question 5: SSO is down and production is impacted. What should happen?

Use the documented break-glass process. Access should be controlled, audited, and rotated after use. The incident should also validate why SSO outage affected cluster access and whether redundancy is required.

### Question 6: OAuth Operator is degraded after applying IDP config. What do you check?

```bash
oc describe co authentication
oc logs -n openshift-authentication deployment/oauth-openshift
oc get events -n openshift-authentication
oc get oauth cluster -o yaml
oc get secret,cm -n openshift-config
```

Look for missing referenced secrets, bad CA config map, invalid fields, or unreachable IDP.

### Question 7: What is the difference between OAuth token and service account token?

OAuth tokens normally represent human users authenticated through the OAuth server. Service account tokens represent namespaced workload identities such as pods, operators, and automation.

### Question 8: Why is OIDC preferred in many enterprises?

OIDC integrates with modern SSO, MFA, conditional access, centralized identity lifecycle, and federation across platforms. It is usually better aligned with enterprise IAM than local cluster-managed users.

## 29. Best Practices Summary

1. Use enterprise OIDC/SSO or LDAP for production authentication.
2. Use HTPasswd only for labs, bootstrap, or tightly controlled emergency access.
3. Remove kubeadmin after a real cluster-admin group is working.
4. Bind RBAC to groups, not individual users.
5. Separate admin, developer, release, auditor, and automation access.
6. Use service accounts for automation, not personal tokens.
7. Use least privilege for service accounts.
8. Configure token lifetime and inactivity timeout according to risk.
9. Protect OAuth secrets, LDAP bind passwords, and OIDC client secrets.
10. Fix TLS trust properly; do not bypass certificate validation.
11. Monitor Authentication Operator and OAuth pods.
12. Centralize audit logs and alert on privileged authentication/RBAC changes.
13. Maintain a tested break-glass process.
14. Back up OAuth, RBAC, group, CA, secret, and OAuthClient configuration.
15. Standardize authentication architecture across clusters.
16. Use GitOps for authentication/RBAC configuration where appropriate, but protect secrets carefully.
17. Review ClusterRoleBindings regularly.
18. Avoid broad grants to `system:authenticated`.
19. Disable self-provisioning if project creation must be controlled.
20. Test authentication in DR, not only in primary production.

## Final Notes for Advanced Administrators

For a 10+ year OpenShift administrator, authentication architecture should be treated as a production platform capability. It is not enough to know how to run `oc login` or configure one LDAP provider.

You should be able to:

- Design authentication for multi-cluster environments.
- Defend OIDC vs LDAP choices.
- Explain OAuth token flow clearly.
- Separate human and machine identities.
- Integrate groups with RBAC.
- Troubleshoot login failures quickly.
- Secure service accounts and automation identities.
- Build break-glass access without weakening normal security.
- Prove authentication events through logs and audit trails.
- Recover authentication after disaster or misconfiguration.

A mature platform team owns authentication as a lifecycle: design, configure, test, monitor, audit, rotate, and recover.
