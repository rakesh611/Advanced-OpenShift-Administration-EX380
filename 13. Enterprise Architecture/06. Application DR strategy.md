# Application DR Strategy in Enterprise Architecture for Advanced OpenShift Administration

**Topic:** Application Disaster Recovery (DR) Strategy  
**Track:** Advanced OpenShift Administration / DO380-style Enterprise Architecture  
**Target experience level:** 10+ years Linux, Kubernetes, OpenShift, DevOps, SRE, Platform Engineering  
**Focus:** Designing, operating, testing, and troubleshooting application-level DR on Red Hat OpenShift

---

## 1. Executive Summary

Application Disaster Recovery (Application DR) is the strategy, architecture, automation, and operational process used to recover business applications after a major failure. In OpenShift, Application DR is not only about taking a backup. It includes application manifests, persistent data, secrets, certificates, routes, DNS, container images, operators, external dependencies, identity integration, CI/CD, GitOps, monitoring, and a tested failover/failback runbook.

A mature OpenShift administrator must separate **cluster recovery** from **application recovery**:

- **Cluster DR** focuses on restoring OpenShift control-plane state, etcd, cluster operators, nodes, certificates, and infrastructure.
- **Application DR** focuses on restoring or moving business workloads, namespaces, deployments, services, routes, PVC data, application configuration, secrets, and dependencies.

In enterprise OpenShift, the strongest Application DR design usually combines:

1. **GitOps** for declarative application and platform configuration.
2. **OADP / Velero** for Kubernetes resource, namespace, image, and persistent-volume backup/restore.
3. **CSI snapshots or file-system backup** for PVC data protection.
4. **Database-native replication or backup** for high-value databases.
5. **ODF Metro-DR / Regional-DR** where OpenShift Data Foundation is the storage platform and workload mobility is required.
6. **ACM / RHACM** for multi-cluster governance, placement, policy, and hub-spoke operations.
7. **DNS, ingress, certificates, and traffic management** for controlled failover.
8. **Regular DR drills** with measurable RTO/RPO evidence.

A senior administrator does not ask only, “Do we have backup?” A senior administrator asks:

- What is the business RTO and RPO?
- Which applications are tier-0, tier-1, tier-2, or tier-3?
- Is the application stateless or stateful?
- Is the data crash-consistent or application-consistent?
- Are secrets, certificates, image pull secrets, routes, and external integrations recoverable?
- Can the application be rebuilt from Git and restored from backup in another cluster?
- Is the restore tested, documented, automated, and auditable?

## 2. What Application DR Means in OpenShift

Application DR means restoring a complete usable application service, not merely recreating pods.

A complete OpenShift application normally includes:

- Namespace / project
- Deployments, StatefulSets, DaemonSets, Jobs, CronJobs
- Services
- Routes or Ingress objects
- ConfigMaps
- Secrets
- ServiceAccounts
- RBAC: Roles, RoleBindings, sometimes ClusterRoles and ClusterRoleBindings
- SecurityContextConstraints permissions or Pod Security Admission labels
- NetworkPolicies
- ResourceQuotas and LimitRanges
- HorizontalPodAutoscalers
- PodDisruptionBudgets
- ImageStreams, BuildConfigs, Pipelines, Tekton resources, Helm releases, Argo CD Applications
- Operator custom resources, for example Kafka, AMQ, PostgreSQL, GitLab Runner, Elastic, Service Mesh, Serverless
- PersistentVolumeClaims and their backend data
- TLS certificates and CA bundles
- External DNS records
- External database, queue, object storage, LDAP, IdP, API gateway, payment gateway, monitoring, logging, and secrets-management integrations

A restore is successful only when the application is reachable, authenticated, authorized, connected to dependencies, serving correct data, and meeting the agreed recovery objective.

## 3. DR, HA, Backup, Restore, Failover, and Failback

These terms are often mixed, but in enterprise architecture they mean different things.

### 3.1 High Availability

High Availability keeps the application available during smaller failures such as pod crash, node failure, or zone-level disruption.

Examples:

- Multiple pod replicas
- Health checks and self-healing
- Multiple worker nodes
- Pod anti-affinity
- Topology spread constraints
- Load-balanced routes
- Highly available database cluster
- Storage replication within the same failure domain

HA reduces downtime for expected failures, but HA alone is not DR.

### 3.2 Backup

Backup is a point-in-time copy of resources or data.

Examples:

- OADP Backup CR
- Velero backup
- CSI VolumeSnapshot
- Restic/Kopia file-system backup
- Database dump
- Object-storage copy
- Image registry mirror
- etcd snapshot

Backup is only useful when restore is tested.

### 3.3 Restore

Restore is the process of recreating application resources and data from backup.

Examples:

- Restore namespace from OADP backup
- Restore PVC from CSI snapshot
- Restore PostgreSQL dump
- Rehydrate app manifests using GitOps

### 3.4 Disaster Recovery

DR is the complete business process that brings service back after a major failure.

Examples:

- Primary cluster unavailable
- Region unavailable
- Storage system corrupted
- Accidental namespace deletion
- Ransomware or destructive change
- Failed upgrade causing application outage

### 3.5 Failover

Failover moves service from primary to secondary location.

Examples:

- Change DNS to secondary cluster route
- Promote replicated database in DR site
- Restore application into standby cluster
- Trigger ODF Regional-DR failover

### 3.6 Failback / Relocation

Failback moves service back to original primary after repair.

Examples:

- Re-sync data from DR to primary
- Restore application to original cluster
- Move DNS back
- Trigger ODF relocation

## 4. RTO and RPO

### 4.1 Recovery Time Objective

**RTO** means how long the business can tolerate the application being unavailable.

Example:

- Payment gateway RTO: 15 minutes
- Internal reporting RTO: 8 hours
- Development namespace RTO: 48 hours

RTO drives architecture. A 15-minute RTO usually requires pre-provisioned DR capacity, automated DNS failover, replicated storage/database, tested runbooks, and monitoring integration. An 8-hour RTO might be satisfied by backup restore.

### 4.2 Recovery Point Objective

**RPO** means maximum acceptable data loss.

Example:

- Banking transaction app RPO: near zero
- Customer portal RPO: 5 minutes
- Internal wiki RPO: 24 hours

RPO drives backup frequency and replication design.

### 4.3 Mapping RTO/RPO to OpenShift DR Patterns

| Application Type | Example | Suggested Pattern | Typical RTO | Typical RPO |
|---|---|---|---:|---:|
| Stateless web app | Frontend, API gateway | GitOps redeploy + image registry mirror | Minutes | Near zero if no data |
| Simple stateful app | Small internal DB | OADP scheduled backup + PVC snapshot | 1-4 hours | Backup interval |
| Business-critical DB | PostgreSQL, MySQL, MongoDB | DB-native replication + OADP for app objects | Minutes to 1 hour | Seconds to minutes |
| Enterprise stateful platform | Kafka, AMQ, Elasticsearch | Operator-supported DR + storage replication + GitOps | Depends on product | Depends on replication |
| ODF-backed app requiring site DR | Stateful app on ODF | ODF Metro-DR / Regional-DR with ACM | Minutes to hours | Metro near-zero, Regional async |
| Low-priority dev/test | Test app | Recreate from Git, no data restore | Hours to days | Not guaranteed |

## 5. Failure Scenarios for Application DR

A strong strategy starts with failure scenarios.

### 5.1 Namespace Accidentally Deleted

Symptoms:

- Project is gone
- All namespaced objects deleted
- PVCs may be deleted depending on reclaim policy and storage behavior

Recovery:

- Restore namespace from OADP backup
- Restore PVCs from snapshot or file-system backup
- Reapply GitOps manifests
- Recreate external DNS if required
- Validate application health

### 5.2 Bad Deployment or Configuration Change

Symptoms:

- New release fails
- ConfigMap/Secret wrong
- Route changed incorrectly
- NetworkPolicy blocks traffic

Recovery:

- Roll back Deployment/DeploymentConfig
- Revert Git commit
- Restore specific ConfigMap/Secret from backup
- Reapply known-good NetworkPolicy
- Validate application endpoints

### 5.3 PVC Data Corruption

Symptoms:

- Application starts but data is wrong
- Database complains about corrupted files
- Files missing or modified

Recovery:

- Stop writers
- Restore PVC from last known-good snapshot/backup
- Run application-specific consistency checks
- Bring application back online

### 5.4 Primary Cluster Lost

Symptoms:

- API unreachable
- Ingress unavailable
- Workers/control plane unreachable
- Storage inaccessible

Recovery options:

- Activate standby cluster
- Restore application into DR cluster using OADP
- Use GitOps to recreate resources
- Restore or promote data
- Change DNS/GSLB traffic to DR cluster

### 5.5 Region or Data-Center Failure

Symptoms:

- Entire site unavailable
- Storage and network unavailable
- External dependencies may also fail

Recovery:

- Use multi-cluster DR design
- Promote secondary data copy
- Fail over DNS
- Validate dependencies from DR region
- Execute communication plan

### 5.6 Security Incident / Ransomware / Destructive Admin Action

Symptoms:

- Secrets modified
- Images replaced
- Resources deleted
- Data encrypted or corrupted

Recovery:

- Stop access paths
- Preserve audit logs
- Identify blast radius
- Restore from immutable backups
- Rotate credentials and certificates
- Redeploy from trusted Git and signed image sources

## 6. Application Classification Model

Not every application needs the same DR level. A senior platform team classifies applications by business criticality.

### 6.1 Tier 0: Mission-Critical

Examples:

- Banking transaction system
- Payment platform
- National identity service
- Healthcare emergency system

Requirements:

- Very low RTO/RPO
- Multi-site design
- Data replication
- Automated failover or semi-automated controlled failover
- Continuous monitoring
- DR drill at least quarterly
- Security, audit, and compliance evidence

### 6.2 Tier 1: Business-Critical

Examples:

- Customer portal
- ERP integration
- Order management
- Core API platform

Requirements:

- RTO normally less than 1-4 hours
- Frequent backup or replication
- Documented and tested restore
- DNS failover
- Standby cluster capacity

### 6.3 Tier 2: Important but Not Immediate

Examples:

- Internal reporting
- Batch processing
- Back-office apps

Requirements:

- RTO normally 8-24 hours
- Daily or frequent scheduled backups
- Restore runbook

### 6.4 Tier 3: Non-Critical

Examples:

- Dev/test workloads
- Sandbox environments
- Temporary demos

Requirements:

- Rebuild from Git
- Optional backup
- No expensive replication unless justified

## 7. Reference Architecture Patterns

## 7.1 Pattern A: Stateless Application DR Using GitOps

### Use Case

Best for frontend, API, and stateless workloads where data is outside the cluster or disposable.

### Architecture

```text
Git Repository
   |
   | Argo CD / OpenShift GitOps
   v
Primary OpenShift Cluster        Secondary OpenShift Cluster
app namespace                     app namespace
Deployment                        Deployment
Service                           Service
Route                             Route
ConfigMap                         ConfigMap
Secret via External Secrets       Secret via External Secrets
```

### Strategy

- Store all Kubernetes manifests in Git.
- Use Kustomize, Helm, or raw YAML.
- Use OpenShift GitOps / Argo CD to sync to both clusters.
- Use cluster-specific overlays for route hostnames, storage classes, ingress domains, and secret references.
- Use external database or replicated database.
- Use DNS/GSLB to switch traffic.

### Advantages

- Fast recovery.
- Minimal backup dependency.
- Good audit trail.
- Easy promotion across clusters.

### Limitations

- Does not protect in-cluster persistent data.
- Requires Git discipline.
- Secrets must be handled securely.

---

## 7.2 Pattern B: Backup/Restore DR with OADP

### Use Case

Best for applications that need namespace-level backup and restore, including Kubernetes resources and PVCs.

### Architecture

```text
Primary OpenShift Cluster
  | OADP / Velero Backup
  | Kubernetes resources + PV snapshots/file backup
  v
Object Storage / Backup Target
  ^
  | OADP / Velero Restore
Secondary OpenShift Cluster
```

### Strategy

- Install OADP Operator.
- Configure DataProtectionApplication.
- Use object storage for backup metadata.
- Use CSI snapshots where supported.
- Use Restic/Kopia file-system backup when snapshots are unavailable or unsuitable.
- Schedule namespace-level backups.
- Test restores into isolated namespace or DR cluster.

### Advantages

- Works well for many namespace-scoped workloads.
- Protects Kubernetes objects and PVC data.
- Backup can be filtered by namespace, resource type, and labels.
- Supports hooks for backup/restore operations.

### Limitations

- Restore time depends on data size and object storage speed.
- Cross-cluster restore needs compatible storage classes, operators, CRDs, routes, and cluster-scoped dependencies.
- Application-consistency often requires app-specific hooks or database-native backup.

---

## 7.3 Pattern C: Database-Native DR Plus OpenShift Object Restore

### Use Case

Best for high-value stateful applications where database correctness is more important than generic volume backup.

### Architecture

```text
Primary OpenShift Cluster                  Secondary OpenShift Cluster
App pods                                   App pods standby
DB primary  ---- native replication ---->  DB replica / standby
OADP backs up app objects                  OADP restores app objects
GitOps controls manifests                  GitOps controls manifests
```

### Strategy

- Use PostgreSQL streaming replication, MySQL replication, MongoDB replica sets, Kafka MirrorMaker, or vendor-supported replication.
- Use OADP to protect Kubernetes application objects.
- Use GitOps to rebuild stateless components.
- Promote database replica during failover.
- Update application connection strings, service aliases, or DNS.

### Advantages

- Better RPO than scheduled backups.
- Database recovery is controlled by database technology.
- Better consistency for transactional workloads.

### Limitations

- More operational complexity.
- Requires database expertise.
- Failback must be carefully planned to avoid split-brain.

---

## 7.4 Pattern D: ODF Metro-DR / Regional-DR with RHACM

### Use Case

Best for stateful applications running on OpenShift Data Foundation where multi-cluster application and data mobility is required.

### Architecture

```text
                         RHACM Hub Cluster
                              |
                  DRPolicy / DRPlacementControl
                              |
        ------------------------------------------------
        |                                              |
Managed Cluster A                              Managed Cluster B
ODF storage                                    ODF storage
Application primary                            Application failover target
PVC replication                                PVC replication
```

### Strategy

- Deploy RHACM hub cluster.
- Import or create managed OpenShift clusters.
- Deploy ODF on managed clusters.
- Configure DRPolicy.
- Protect applications using DRPlacementControl.
- Execute failover or relocation using OpenShift DR workflows.

### Metro-DR

Metro-DR is intended for metropolitan distance / low-latency designs. It targets business continuity during a data-center or availability-zone style failure and is usually designed for no data loss where synchronous replication is applicable.

### Regional-DR

Regional-DR targets region-level failures across distance. It uses asynchronous replication and can therefore have some data loss within the defined RPO.

### Advantages

- Enterprise-grade storage-integrated DR.
- Application mobility controlled through RHACM and ODF DR resources.
- Useful for stateful workloads requiring coordinated failover/relocation.

### Limitations

- Requires supported ODF/RHACM versions and topology.
- Requires careful storage, network, and entitlement planning.
- Operationally more complex than simple backup/restore.

---

## 7.5 Pattern E: Active-Active Application DR

### Use Case

Best for globally distributed stateless services or applications explicitly designed for multi-writer/multi-region operation.

### Architecture

```text
Global DNS / GSLB / Load Balancer
        |                         |
Cluster A                      Cluster B
App replicas                   App replicas
Local cache                    Local cache
Global DB / replicated DB      Global DB / replicated DB
```

### Strategy

- Deploy application to multiple clusters simultaneously.
- Use global load balancing.
- Use active-active compatible database or external service.
- Ensure idempotent APIs and conflict handling.
- Keep configuration consistent through GitOps.

### Advantages

- Very low RTO.
- Better user proximity.
- Can survive one site outage.

### Limitations

- Hardest architecture to operate.
- Application must be designed for active-active.
- Split-brain, data conflicts, and global transaction consistency are major risks.

## 8. Cluster DR vs Application DR

### 8.1 Cluster DR

Cluster DR protects the OpenShift platform itself.

Important areas:

- etcd backup
- Control-plane recovery
- Cluster certificates
- Cluster operators
- Machine API / infrastructure
- Ingress, DNS, registry, monitoring, logging
- Identity providers
- Cluster-wide resources

Cluster DR is required when the cluster itself is damaged.

### 8.2 Application DR

Application DR protects business services running on top of OpenShift.

Important areas:

- Namespaces
- Application manifests
- PVC data
- Secrets
- ConfigMaps
- Routes
- RBAC
- NetworkPolicy
- Operator CRs
- External integrations

Application DR may restore to the same cluster, a replacement cluster, or a secondary cluster.

### 8.3 Why etcd Backup Alone Is Not Enough

An etcd backup restores cluster object state for a cluster recovery scenario. It does not automatically solve application-level DR across different clusters, different infrastructure, different storage backends, or different regions.

For application DR, you need a combination of:

- Application manifests
- Application data backup/replication
- External dependencies
- Cluster-scoped prerequisite resources
- Restore automation
- DNS/traffic failover
- Validation

## 9. Enterprise Application DR Design Principles

## 9.1 Design for Recovery, Not Only Deployment

Many teams automate deployment but ignore recovery. A DR-ready application must be deployable and recoverable.

Checklist:

- Can the app be deployed from Git to a clean cluster?
- Can secrets be restored or regenerated?
- Can PVC data be restored?
- Are CRDs and operators available before custom resources restore?
- Are images available if the original registry is down?
- Can DNS be switched to another cluster?
- Are runbooks tested by someone other than the author?

## 9.2 Use Declarative Configuration

Prefer Git-managed configuration:

- Namespace definitions
- RBAC
- Quotas and limits
- NetworkPolicies
- Deployments and StatefulSets
- Services and Routes
- Argo CD Applications
- Helm values
- Operator subscriptions
- ExternalSecret definitions

Avoid manual-only configuration. Manual changes disappear during DR or create drift.

## 9.3 Protect Data According to Application Semantics

Not all storage backups are equal.

- A crash-consistent volume snapshot may be acceptable for static files.
- A relational database may require transaction-log backup or application hooks.
- A distributed database may require native backup tooling.
- A message broker may require cluster-aware replication.
- Object storage may require bucket replication and versioning.

## 9.4 Avoid Single Points of Failure

Common hidden SPOFs:

- One image registry
- One Git server
- One DNS provider
- One external database
- One IdP
- One object-storage bucket
- One ACM hub without backup
- One certificate authority path
- One storage backend

## 9.5 Make DR Observable

You must monitor backup and replication health.

Examples:

- Last successful OADP backup time
- Backup failure alerts
- VolumeSnapshot status
- Object-storage availability
- Database replication lag
- DR cluster capacity
- Argo CD sync health
- DNS health
- Application synthetic checks

## 9.6 Test Restore Regularly

Untested backup is a false sense of safety.

A mature team performs:

- Namespace restore test
- PVC restore test
- Full app restore test
- Cross-cluster restore test
- DNS failover test
- Security credential restore test
- Failback test
- Post-restore data validation

## 10. OpenShift Components to Include in Application DR

## 10.1 Namespace / Project

Back up or declare:

```yaml
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: payments-prod
  labels:
    app-tier: tier-0
    dr-policy: regional
```

Also include namespace labels required by:

- Pod Security Admission
- NetworkPolicy selectors
- ACM placement
- Service Mesh injection
- Monitoring scraping
- Cost allocation

## 10.2 Workload Controllers

Include:

- Deployment
- StatefulSet
- DaemonSet
- Job
- CronJob
- DeploymentConfig if still used

Validate:

- Image references
- Resource requests/limits
- Probes
- Affinity/anti-affinity
- Topology spread constraints
- Security context
- ServiceAccount
- Volume mounts

## 10.3 Services and Routes

Include:

- Service
- Route
- Ingress
- TLS certs
- Destination CA certs
- Re-encrypt/edge/passthrough route configuration

Example route:

```yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payments
  namespace: payments-prod
spec:
  host: payments.example.com
  to:
    kind: Service
    name: payments-api
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
```

DR consideration:

- The same hostname cannot safely point to both clusters unless active-active is intended.
- DNS TTL must match RTO requirement.
- Certificates must be available in the DR cluster.

## 10.4 ConfigMaps and Secrets

ConfigMaps are usually safe in Git if they do not contain secrets.

Secrets require careful handling:

- OADP can back up Kubernetes Secret objects, but this may not be enough for compliance.
- Prefer External Secrets, Vault, CyberArk, AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault style integration.
- For GitOps, use Sealed Secrets, SOPS, or external secret references, not plaintext secrets.
- Rotate secrets after security incident restore.

## 10.5 RBAC

Include:

- Role
- RoleBinding
- ServiceAccount
- SCC grants if needed
- ClusterRole/ClusterRoleBinding if app requires cluster-wide access

Example SCC grant command:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n payments-prod
```

DR risk:

- Restored pods may fail with `Error creating: pods ... is forbidden` if ServiceAccount or SCC permission is missing.

## 10.6 NetworkPolicies

Include all NetworkPolicies.

DR risk:

- Application restores successfully but cannot talk to database because labels differ in DR namespace.
- DNS, monitoring, ingress, or service mesh traffic gets blocked.

Validate:

```bash
oc get networkpolicy -n payments-prod
oc get pods -n payments-prod --show-labels
oc get svc -n payments-prod
```

## 10.7 PersistentVolumeClaims

PVC strategy depends on storage backend.

Include:

- PVC manifest
- StorageClass mapping
- Access mode
- Capacity
- VolumeMode
- Snapshot class
- Backup annotation if using file-system backup

Example PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data
  namespace: payments-prod
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: ocs-storagecluster-ceph-rbd
  resources:
    requests:
      storage: 100Gi
```

DR risk:

- Source cluster uses `ocs-storagecluster-ceph-rbd` but DR cluster uses `managed-csi` or another class.
- Restore may create PVC that remains Pending.
- PV restore may fail if snapshot backend is unavailable.

## 10.8 Operators and CRDs

Many enterprise apps are operator-managed.

Examples:

- PostgreSQL operator
- AMQ Streams / Kafka
- OpenShift Service Mesh
- OpenShift Serverless
- OpenShift Pipelines
- OpenShift GitOps
- Elastic / logging
- External Secrets Operator

DR rule:

**Install operator and CRDs before restoring custom resources.**

If a custom resource is restored before its CRD exists, restore can fail or skip resources.

## 10.9 Internal Image Registry and Images

Application DR must ensure images are available.

Options:

- Mirror application images to DR registry.
- Use immutable image digests.
- Use imageContentSourcePolicy or ImageDigestMirrorSet where appropriate.
- Backup internal images if using OADP support for images.
- Avoid relying only on one CI/CD registry.

Example image reference:

```yaml
image: registry.example.com/payments/api@sha256:abc123...
```

## 10.10 Build and Pipeline Resources

If the application must be rebuilt during DR, include:

- BuildConfig
- ImageStream
- Tekton Pipeline
- PipelineRun templates
- Git credentials
- Maven/npm/PyPI mirrors
- Binary artifact repository

But for strict DR, prefer restoring/running known-good images rather than rebuilding during outage.

## 11. OADP-Based Application Backup and Restore

OpenShift API for Data Protection (OADP) uses Velero-based workflows to back up and restore application resources and persistent data. In modern OpenShift versions, OADP is the standard Red Hat-supported approach for application backup/restore use cases.

## 11.1 What OADP Can Protect

OADP can protect:

- Kubernetes resources
- OpenShift resources
- Namespaces
- Internal images
- Persistent volumes using snapshots or file-system backup
- Application backups by namespace, labels, or resource filters

## 11.2 OADP Requirements

Typical requirements:

- `cluster-admin` access
- OADP Operator installed
- Object storage for backup metadata and data
- Snapshot-capable storage if using CSI snapshots
- Restic/Kopia file-system backup if not using snapshots
- Network connectivity from cluster to backup storage
- Correct credentials and CA trust

## 11.3 Install OADP Operator

Example using OperatorHub / OLM:

```bash
oc new-project openshift-adp

cat <<'EOF_SUB' | oc apply -f -
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-adp
  namespace: openshift-adp
spec:
  targetNamespaces:
  - openshift-adp
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: redhat-oadp-operator
  namespace: openshift-adp
spec:
  channel: stable-1.4
  installPlanApproval: Automatic
  name: redhat-oadp-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF_SUB
```

Check status:

```bash
oc get csv -n openshift-adp
oc get pods -n openshift-adp
```

> Adjust the OADP channel according to your supported OpenShift and OADP compatibility matrix.

## 11.4 Create Cloud/Object Storage Secret

Example for S3-compatible storage:

```bash
cat > credentials-velero <<'EOF_SECRET'
[default]
aws_access_key_id = CHANGE_ME_ACCESS_KEY
aws_secret_access_key = CHANGE_ME_SECRET_KEY
EOF_SECRET

oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

## 11.5 Create DataProtectionApplication

Example for S3-compatible object storage and CSI snapshots:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-s3
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
      resourceTimeout: 10m
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
    - velero:
        provider: aws
        default: true
        objectStorage:
          bucket: ocp-app-backups
          prefix: prod-cluster-a
        config:
          region: us-east-1
          s3ForcePathStyle: "true"
          s3Url: https://s3.example.com
        credential:
          name: cloud-credentials
          key: cloud
  snapshotLocations:
    - velero:
        provider: aws
        config:
          region: us-east-1
```

Apply:

```bash
oc apply -f dpa-s3.yaml
oc get dpa -n openshift-adp
oc get backupstoragelocation -n openshift-adp
oc get volumesnapshotlocation -n openshift-adp
```

## 11.6 Create Namespace Backup

Example Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-prod-manual-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payments-prod
  storageLocation: dpa-s3-1
  ttl: 720h0m0s
  snapshotMoveData: true
```

Apply and monitor:

```bash
oc apply -f backup-payments.yaml
oc get backup -n openshift-adp
oc describe backup payments-prod-manual-001 -n openshift-adp
velero backup describe payments-prod-manual-001 --details
velero backup logs payments-prod-manual-001
```

## 11.7 Schedule Application Backup

Example daily backup:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: payments-prod-daily
  namespace: openshift-adp
spec:
  schedule: "0 2 * * *"
  template:
    includedNamespaces:
      - payments-prod
    storageLocation: dpa-s3-1
    ttl: 168h0m0s
    snapshotMoveData: true
```

Check:

```bash
oc get schedule -n openshift-adp
oc get backup -n openshift-adp
```

## 11.8 Backup Using Label Selector

Useful when a namespace has multiple applications.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-api-label-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payments-prod
  labelSelector:
    matchLabels:
      app.kubernetes.io/name: payments-api
  storageLocation: dpa-s3-1
```

## 11.9 Excluding Resources from Backup

Some resources should not be restored blindly.

Examples:

- Events
- Pods created by controllers
- Temporary Jobs
- Operator-generated status objects
- Certain cluster-scoped resources

Example:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-prod-filtered
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payments-prod
  excludedResources:
    - events
    - pods
```

## 11.10 Restore Application

Example Restore CR:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-payments-prod-001
  namespace: openshift-adp
spec:
  backupName: payments-prod-manual-001
  includedNamespaces:
    - payments-prod
```

Apply and monitor:

```bash
oc apply -f restore-payments.yaml
oc get restore -n openshift-adp
oc describe restore restore-payments-prod-001 -n openshift-adp
velero restore describe restore-payments-prod-001 --details
velero restore logs restore-payments-prod-001
```

## 11.11 Restore Into Different Namespace

Useful for testing or parallel recovery:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-payments-to-test
  namespace: openshift-adp
spec:
  backupName: payments-prod-manual-001
  namespaceMapping:
    payments-prod: payments-restore-test
```

Post-restore checks:

```bash
oc get all -n payments-restore-test
oc get pvc -n payments-restore-test
oc get route -n payments-restore-test
oc get events -n payments-restore-test --sort-by=.lastTimestamp
```

## 11.12 Application-Consistent Backup Hooks

A generic PVC snapshot may be crash-consistent. For application consistency, use hooks.

Example pre/post hook idea for a database-like workload:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: db-backup-with-hooks
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payments-prod
  hooks:
    resources:
      - name: quiesce-db
        includedNamespaces:
          - payments-prod
        labelSelector:
          matchLabels:
            app: postgres
        pre:
          - exec:
              container: postgres
              command:
                - /bin/bash
                - -c
                - "psql -U postgres -c 'CHECKPOINT;'"
              onError: Fail
              timeout: 60s
        post:
          - exec:
              container: postgres
              command:
                - /bin/bash
                - -c
                - "echo backup-completed"
              onError: Continue
              timeout: 60s
```

For real production databases, prefer vendor-recommended backup and replication procedures over generic filesystem snapshots.

## 12. PVC Backup Strategy

## 12.1 Snapshot-Based Backup

Snapshot backup uses storage backend snapshot APIs, usually through CSI.

Good for:

- Faster backup of block volumes
- Large PVCs
- Storage systems with snapshot support

Requirements:

- CSI driver supports snapshots
- VolumeSnapshotClass exists
- Snapshot location is configured
- Storage backend supports restore from snapshot

Check snapshot classes:

```bash
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

## 12.2 File-System Backup

File-system backup uses agents such as Restic/Kopia to copy files from mounted volumes.

Good for:

- Storage without snapshots
- File-level backup
- Some cross-storage restore cases

Limitations:

- Can be slower for large volumes
- Consistency depends on application behavior
- Requires node agent

## 12.3 Database-Native Backup

Examples:

- `pg_dump`, `pg_basebackup`, WAL archiving
- MySQL dump, physical backup, binlog replication
- MongoDB Ops Manager / mongodump / replica sets
- Kafka MirrorMaker / cluster linking / operator-supported backup

Good for:

- Transactional consistency
- Point-in-time recovery
- Low RPO

## 12.4 Storage Replication

Examples:

- ODF mirroring
- Ceph RBD mirroring
- SAN replication
- Cloud disk replication

Good for:

- Larger stateful workloads
- Site-level DR
- Faster failover than full restore

Risk:

- Replication can also replicate corruption if not combined with immutable backups and point-in-time recovery.

## 13. ODF Metro-DR and Regional-DR Strategy

OpenShift Data Foundation DR integrates storage replication and multi-cluster placement workflows. It is especially relevant when applications use ODF-backed PVCs.

## 13.1 Core Components

- RHACM hub cluster
- Two managed OpenShift clusters
- ODF on managed clusters
- OpenShift DR components
- DRPolicy
- DRPlacementControl
- PlacementRule / Placement
- ManagedCluster resources
- Application resources

## 13.2 Metro-DR

Metro-DR protects workloads between nearby data centers or availability zones where latency is low enough for synchronous-style protection.

Design intent:

- Data-center failure protection
- Minimal or no data loss
- Stronger consistency
- Requires strict network/storage design

## 13.3 Regional-DR

Regional-DR protects workloads across distance and usually uses asynchronous replication.

Design intent:

- Region failure protection
- Predictable RPO but possible data loss
- Broader failure protection than Metro-DR

## 13.4 RHACM Hub Consideration

The RHACM hub is the multi-cluster control plane for many DR workflows. The hub itself must also be protected.

Hub DR options:

- Backup RHACM hub resources
- Active/passive hub design
- Recreate hub and restore ACM resources
- Ensure same operator versions and namespaces during restore

## 13.5 DRPolicy Concept

A DRPolicy defines which clusters participate in the DR relationship and the scheduling/replication policy.

Conceptual example:

```yaml
apiVersion: ramendr.openshift.io/v1alpha1
kind: DRPolicy
metadata:
  name: regional-dr-policy
spec:
  drClusters:
    - ocp-east
    - ocp-west
  schedulingInterval: 5m
```

> The exact API version and fields can vary by ODF/OpenShift DR release. Always check the installed CRD and supported documentation for your environment.

Check installed CRDs:

```bash
oc get crd | grep -i ramen
oc explain drpolicy
oc explain drplacementcontrol
```

## 13.6 Failover and Relocation Concepts

### Failover

Failover is used when the primary cluster or site is unavailable or must be abandoned.

High-level steps:

1. Confirm disaster condition.
2. Freeze change activity.
3. Confirm last replication status.
4. Trigger failover to secondary cluster.
5. Validate PVC attachment and application pods.
6. Switch DNS/traffic.
7. Run application validation.
8. Communicate service restoration.

### Relocation

Relocation is a planned movement back to original primary or another cluster.

High-level steps:

1. Confirm primary site is healthy.
2. Confirm replication from active site to target site.
3. Schedule maintenance window if required.
4. Stop writes or use controlled relocation workflow.
5. Relocate workload.
6. Validate data and app health.
7. Switch traffic back.

## 14. GitOps-Driven DR

GitOps is one of the most important parts of modern Application DR.

## 14.1 Why GitOps Matters for DR

Without GitOps, a restored cluster may not match production.

GitOps gives:

- Version-controlled desired state
- Pull-based reconciliation
- Audit history
- Repeatable cluster bootstrap
- Multi-cluster consistency
- Easy rollback

## 14.2 Git Repository Structure

Example:

```text
platform-gitops/
  clusters/
    prod-east/
      operators/
      namespaces/
      apps/
    prod-west/
      operators/
      namespaces/
      apps/
  apps/
    payments/
      base/
        deployment.yaml
        service.yaml
        route.yaml
        networkpolicy.yaml
      overlays/
        prod-east/
          kustomization.yaml
          route-patch.yaml
          storage-patch.yaml
        prod-west/
          kustomization.yaml
          route-patch.yaml
          storage-patch.yaml
```

## 14.3 Cluster Bootstrap Order

Recommended order:

1. Install base OpenShift cluster.
2. Configure identity providers and certificates.
3. Configure image registry and pull secrets.
4. Install required operators.
5. Configure storage classes and snapshot classes.
6. Install OADP / backup agents.
7. Configure GitOps operator.
8. Sync platform namespaces, RBAC, policies.
9. Sync application prerequisites.
10. Restore data.
11. Sync application workloads.
12. Validate service and switch traffic.

## 14.4 Argo CD Application Example

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-prod
  namespace: openshift-gitops
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/apps.git
    targetRevision: main
    path: apps/payments/overlays/prod-east
  destination:
    server: https://kubernetes.default.svc
    namespace: payments-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

## 14.5 GitOps and OADP Together

A practical pattern:

- GitOps owns desired configuration.
- OADP owns backup/restore of runtime resources and PVC data.
- Database-native tools own transactional data backup.
- GitOps resyncs any missing or drifted configuration after restore.

Avoid conflict:

- Do not let GitOps prune restored resources unintentionally.
- Pause auto-sync during restore if required.
- Use app-of-apps carefully.
- Validate namespace mapping.

## 15. DNS, Ingress, and Traffic Failover

Application DR fails if users cannot reach the restored service.

## 15.1 DNS TTL

For critical apps, set DNS TTL low enough before an incident.

Example:

- Tier-0: 30-60 seconds
- Tier-1: 1-5 minutes
- Tier-2: 15-60 minutes

Low TTL increases DNS traffic but improves failover time.

## 15.2 Route Hostname Strategy

Options:

### Same Hostname, Active-Passive

```text
payments.example.com -> primary router VIP
```

During failover:

```text
payments.example.com -> secondary router VIP
```

### Different Hostnames with GSLB

```text
payments.example.com -> GSLB
payments-east.apps.example.com -> cluster A
payments-west.apps.example.com -> cluster B
```

### Active-Active

```text
payments.example.com -> both clusters with health checks
```

Only use active-active if the application and data layer support it.

## 15.3 TLS Certificate Strategy

Certificates must be available in DR cluster.

Options:

- Wildcard certificate for route domain
- Application-specific cert stored in external secret manager
- cert-manager with DNS-01 challenge
- Enterprise PKI with automated issuance
- OADP backup of route TLS secrets where permitted

Validate:

```bash
oc get route payments -n payments-prod -o yaml
curl -vk https://payments.example.com/health
openssl s_client -connect payments.example.com:443 -servername payments.example.com
```

## 16. Security and Compliance in Application DR

## 16.1 Secrets

Do not treat secrets as an afterthought.

Recommended:

- Store secrets in external secret manager.
- Use short-lived credentials where possible.
- Rotate secrets after restore into DR.
- Separate backup encryption keys from cluster admin access.
- Encrypt backups at rest.
- Restrict backup object-storage bucket access.

## 16.2 RBAC

DR operators need elevated permissions. Control them tightly.

Recommended:

- Dedicated DR admin group
- Break-glass access process
- Audit logging enabled
- Least privilege for application teams
- Separate backup/restore roles where possible

## 16.3 Backup Immutability

For ransomware resilience:

- Use object-lock or immutable bucket policies where supported.
- Keep offline or cross-account backup copies.
- Enable object versioning.
- Limit delete permissions.
- Monitor unusual backup deletion activity.

## 16.4 Compliance Evidence

Maintain evidence:

- Backup schedule
- Successful backup logs
- Restore test results
- DR drill report
- RTO/RPO measurement
- Approval records
- Security sign-off
- Post-incident review

## 17. Application-Consistent Backup Design

## 17.1 Crash-Consistent Backup

Crash-consistent backup captures data as if the system suddenly lost power.

Good for:

- Static content
- Some file stores
- Apps that can recover from journaling

Risk:

- Database may require recovery.
- In-flight transactions may be lost.

## 17.2 Application-Consistent Backup

Application-consistent backup coordinates with the application.

Methods:

- Database checkpoint
- Freeze file system
- Stop writes temporarily
- Pre-backup hook
- Post-backup hook
- Native backup API
- Transaction log archive

## 17.3 Example PostgreSQL Strategy

Better than raw PVC snapshot:

- Continuous WAL archiving
- Daily base backup
- OADP backup of Kubernetes objects
- Test point-in-time recovery
- Keep secrets and certificates restorable

## 17.4 Example MySQL Strategy

- Replication to DR cluster
- Binary logs retained
- Scheduled logical or physical backup
- OADP backs up app resources
- Failover process promotes replica

## 17.5 Example Kafka Strategy

- MirrorMaker or vendor-supported replication
- Topic config backup
- ACL backup
- Schema registry backup
- Operator CR backup
- Do not rely only on PVC snapshots for distributed log recovery unless vendor supports that approach

## 18. Image Registry DR

## 18.1 Image Risks

- Primary registry down
- Image tag overwritten
- Build artifact lost
- Pull secret missing
- Disconnected cluster cannot reach external registry

## 18.2 Recommended Practices

- Use immutable digests.
- Mirror images to DR registry.
- Use signed images where possible.
- Back up internal registry if used for production images.
- Keep pull secrets available in DR.
- Maintain oc-mirror process for disconnected environments.

## 20. Application DR Runbook: Planned Failover

Use planned failover when the primary site is still available but must be evacuated.

## 20.1 Preconditions

- DR cluster healthy
- Latest backup successful
- Replication healthy
- DNS access available
- Required operators installed in DR
- Secrets available
- Application owners available
- Change window approved

## 20.2 Steps

### Step 1: Announce Change Freeze

Stop deployments and configuration changes.

```bash
oc annotate namespace payments-prod dr/change-freeze="true" --overwrite
```

### Step 2: Confirm Application Health on Primary

```bash
oc get pods -n payments-prod
oc get pvc -n payments-prod
oc get route -n payments-prod
curl -k https://payments.example.com/health
```

### Step 3: Take Final Backup or Confirm Replication

```bash
oc create -f backup-payments-final.yaml
oc get backup -n openshift-adp
velero backup describe payments-prod-final --details
```

For database-native replication:

```bash
# Example only; actual commands depend on DB
psql -c "select pg_is_in_recovery();"
psql -c "select now() - pg_last_xact_replay_timestamp() as replica_lag;"
```

### Step 4: Scale Down Writers on Primary

```bash
oc scale deploy/payments-api --replicas=0 -n payments-prod
oc scale deploy/payments-worker --replicas=0 -n payments-prod
```

For StatefulSet:

```bash
oc scale sts/payments-db --replicas=0 -n payments-prod
```

### Step 5: Restore or Activate in DR Cluster

Login to DR cluster:

```bash
oc login https://api.dr.example.com:6443
```

Restore:

```bash
oc apply -f restore-payments-final.yaml
oc get restore -n openshift-adp
```

Or sync GitOps:

```bash
argocd app sync payments-prod
argocd app wait payments-prod --health
```

### Step 6: Validate DR Application

```bash
oc get pods -n payments-prod
oc get pvc -n payments-prod
oc get svc -n payments-prod
oc get route -n payments-prod
curl -k https://payments-dr.apps.dr.example.com/health
```

### Step 7: Switch DNS / GSLB

Change:

```text
payments.example.com -> DR cluster router/load balancer
```

Verify:

```bash
dig payments.example.com
curl -vk https://payments.example.com/health
```

### Step 8: Business Validation

Application team validates:

- Login
- Transaction flow
- Data correctness
- API response
- Background jobs
- Monitoring
- Logs

### Step 9: Close Change

Record:

- Actual RTO
- Actual RPO
- Issues found
- Commands executed
- Evidence screenshots/logs

## 21. Application DR Runbook: Unplanned Failover

Use unplanned failover when primary cluster or site is unavailable.

## 21.1 Preconditions

- Disaster declared by incident commander
- Primary cluster unreachable or unsafe
- DR cluster reachable
- Backup/replica available
- DNS/GSLB control available

## 21.2 Steps

### Step 1: Confirm Primary Failure

From admin workstation:

```bash
oc login https://api.primary.example.com:6443
curl -k https://api.primary.example.com:6443/readyz
curl -k https://payments.example.com/health
```

If primary is unreachable, do not attempt risky partial writes.

### Step 2: Prevent Split-Brain

If any part of primary is still running, isolate it before promoting DR.

Actions may include:

- Disable load balancer target
- Remove route from DNS/GSLB
- Block application ingress
- Stop database primary if reachable
- Confirm only one write location exists

### Step 3: Determine Recovery Point

Check latest backup:

```bash
oc get backup -n openshift-adp --sort-by=.metadata.creationTimestamp
velero backup describe payments-prod-daily-20260703020000 --details
```

Check database replica lag or last WAL/binlog position if available.

### Step 4: Restore or Promote Data

OADP restore:

```bash
oc apply -f restore-payments-latest.yaml
```

Database promote example concept:

```bash
# Example only
patronictl failover
# or promote replica using vendor-supported process
```

### Step 5: Start Application in DR

```bash
oc scale deploy/payments-api --replicas=3 -n payments-prod
oc scale deploy/payments-worker --replicas=2 -n payments-prod
```

### Step 6: Validate Internally

```bash
oc get pods -n payments-prod -o wide
oc get events -n payments-prod --sort-by=.lastTimestamp
oc logs deploy/payments-api -n payments-prod --tail=100
curl -k https://payments-dr.apps.dr.example.com/health
```

### Step 7: Switch Public Traffic

```bash
dig payments.example.com
curl -vk https://payments.example.com/health
```

### Step 8: Monitor Closely

Monitor:

- Error rate
- Latency
- Database health
- Queue depth
- Pod restarts
- PVC attach/mount events
- Route availability
- Certificate validity

### Step 9: Communicate Status

Report:

- Service restored time
- Data loss estimate
- Known degraded functions
- Next update time
- Failback plan status

## 22. Application DR Runbook: Failback

Failback is riskier than failover because data has changed in DR site.

## 22.1 Preconditions

- Original primary cluster rebuilt and validated
- Required operators installed
- Storage healthy
- Networking healthy
- DNS controlled
- Data synchronization path confirmed
- Business approval obtained

## 22.2 Steps

### Step 1: Confirm DR Is Current Source of Truth

```bash
curl -k https://payments.example.com/health
oc get pods -n payments-prod
```

### Step 2: Prepare Primary as Target

- Install same operators
- Configure storage
- Configure OADP
- Configure GitOps
- Configure secrets
- Validate routes but do not switch traffic yet

### Step 3: Sync Data Back

Options:

- Database-native replication from DR to primary
- ODF relocation workflow
- OADP backup from DR and restore to primary
- Storage replication reverse direction

### Step 4: Freeze Writes

```bash
oc scale deploy/payments-api --replicas=0 -n payments-prod
oc scale deploy/payments-worker --replicas=0 -n payments-prod
```

### Step 5: Final Sync

Run final data sync or backup.

### Step 6: Start App on Primary

```bash
oc login https://api.primary.example.com:6443
argocd app sync payments-prod
oc get pods -n payments-prod
curl -k https://payments-primary.apps.primary.example.com/health
```

### Step 7: Switch DNS Back

```text
payments.example.com -> primary cluster router/load balancer
```

### Step 8: Validate and Monitor

Run business validation and monitor for several hours.

## 24. Troubleshooting Application DR

## 24.1 BackupStorageLocation Not Available

Check:

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation <name> -n openshift-adp
oc logs deploy/velero -n openshift-adp
```

Common causes:

- Wrong object-storage credentials
- Wrong bucket name
- Wrong endpoint URL
- Missing CA trust
- Network/firewall issue
- DNS issue

## 24.2 Backup Fails

Check:

```bash
oc describe backup <backup-name> -n openshift-adp
velero backup logs <backup-name>
oc get events -n openshift-adp --sort-by=.lastTimestamp
```

Common causes:

- API resource unavailable
- CRD deleted or broken
- Volume snapshot failure
- Insufficient permissions
- Object storage not reachable
- Hook timeout

## 24.3 Restore Fails

Check:

```bash
oc describe restore <restore-name> -n openshift-adp
velero restore logs <restore-name>
oc get events -A --sort-by=.lastTimestamp | tail -50
```

Common causes:

- Namespace already exists with conflicting resources
- CRDs missing
- Operators missing
- StorageClass missing
- PVC capacity mismatch
- SCC/RBAC missing
- NetworkPolicy restored before dependencies are ready

## 24.4 PVC Pending After Restore

Check:

```bash
oc get pvc -n payments-prod
oc describe pvc <pvc-name> -n payments-prod
oc get sc
oc get events -n payments-prod --sort-by=.lastTimestamp
```

Common causes:

- StorageClass name does not exist in DR cluster
- CSI driver not installed
- VolumeSnapshotContent not available
- Access mode unsupported
- Insufficient storage capacity
- Topology constraints

Fix options:

- Map storage class during restore if supported.
- Pre-create compatible StorageClass.
- Restore into a cluster with same CSI driver.
- Use file-system backup restore instead of snapshot restore.

## 24.5 Pods CrashLoop After Restore

Check:

```bash
oc get pods -n payments-prod
oc describe pod <pod> -n payments-prod
oc logs <pod> -n payments-prod --previous
```

Common causes:

- Secret missing or stale
- ConfigMap wrong
- Database endpoint changed
- PVC mounted but data inconsistent
- Image pull secret missing
- SCC issue
- Route/certificate dependency missing

## 24.6 Route Restored but App Not Reachable

Check:

```bash
oc get route -n payments-prod
oc describe route payments -n payments-prod
oc get endpoints -n payments-prod
oc get svc -n payments-prod
curl -vk https://payments.example.com/health
```

Common causes:

- DNS still points to old cluster
- TLS certificate missing/wrong
- Service selector mismatch
- No ready endpoints
- NetworkPolicy blocks ingress
- Router shard mismatch

## 24.7 GitOps Prunes Restored Objects

Symptoms:

- Restore succeeds but Argo CD deletes resources
- Application disappears after sync

Fix:

- Pause auto-sync before restore.
- Update Git desired state first.
- Use proper namespace mapping.
- Add restored resources to Git or exclude them intentionally.

## 25. Practical Example: 3-Tier Application DR Design

## 25.1 Application

Application: `payments-prod`

Components:

- Frontend Deployment
- API Deployment
- Worker Deployment
- PostgreSQL StatefulSet
- Redis cache
- Route: `payments.example.com`
- PVC: `pgdata`
- Secret: DB credentials
- ConfigMap: app settings
- NetworkPolicy: frontend -> api -> db

## 25.2 DR Requirement

- RTO: 1 hour
- RPO: 15 minutes
- DR site: secondary OpenShift cluster
- Data: PostgreSQL must have point-in-time recovery

## 25.3 Recommended Design

- GitOps deploys frontend, API, worker, Service, Route, ConfigMap, NetworkPolicy.
- Secrets come from external secret manager.
- PostgreSQL uses WAL archiving every few minutes to object storage.
- OADP backs up namespace every 4 hours.
- OADP backs up PVC snapshot daily for additional protection.
- Images are mirrored to DR registry.
- DNS TTL is 60 seconds.
- DR cluster has warm standby capacity.
- Monthly restore test.

## 25.4 Recovery Flow

1. Declare incident.
2. Restore namespace resources using GitOps/OADP.
3. Restore PostgreSQL to latest consistent point using WAL.
4. Start API/worker/frontend.
5. Validate internal route.
6. Switch DNS.
7. Measure RTO/RPO.

## 26. Best Practices for Senior OpenShift Administrators

## 26.1 Do Not Back Up Everything Blindly

Blind full-cluster application restore can create conflicts.

Better:

- Know application ownership.
- Separate cluster-scoped and namespace-scoped resources.
- Use labels.
- Use GitOps for desired state.
- Use OADP for runtime and data backup.

## 26.2 Keep Restore Cluster Compatible

Compatibility checklist:

- Same or compatible OpenShift version
- Required CRDs installed
- Required operators installed
- Same namespace names if required
- Compatible StorageClass
- Compatible ingress domain strategy
- Compatible SCC/PSA policies
- Compatible image registry access

## 26.3 Use Labels for DR Operations

Example:

```yaml
metadata:
  labels:
    app.kubernetes.io/name: payments
    app.kubernetes.io/part-of: payments-platform
    dr.openshift.io/tier: tier-1
    backup.openshift.io/enabled: "true"
```

Labels help:

- Backup selection
- Policy targeting
- Monitoring
- Ownership
- Cost allocation

## 26.4 Separate Runtime State from Desired State

Desired state:

- Git repo
- Helm charts
- Kustomize overlays
- Operator subscriptions

Runtime state:

- PVC data
- Generated tokens
- Job history
- Application runtime metadata

Use the correct protection mechanism for each.

## 26.5 Design for Restore Order

Restore order matters:

1. Cluster prerequisites
2. Operators and CRDs
3. Namespaces
4. RBAC and SCC
5. Storage classes and snapshot classes
6. Secrets and ConfigMaps
7. PVCs/data
8. Services
9. Workload controllers
10. Routes/Ingress
11. DNS switch
12. Business validation

## 26.6 Keep DR Runbooks Simple

During a disaster, complex procedures fail.

Runbooks should have:

- Clear owner
- Preconditions
- Exact commands
- Validation commands
- Rollback decision
- Escalation contacts
- Expected outputs
- Known issues

## 27. Interview-Level Explanation

If asked in an advanced OpenShift interview: “How do you design Application DR strategy?”

A strong answer:

> I start with business RTO/RPO and classify applications by criticality. Then I separate stateless configuration from stateful data. For OpenShift objects, I prefer GitOps as the source of truth and OADP/Velero for namespace-level backup and restore. For PVCs, I use CSI snapshots where supported or file-system backup with Kopia/Restic. For databases, I do not rely only on volume snapshots; I use database-native replication or point-in-time recovery. For multi-cluster enterprise DR, I use RHACM for governance and placement, and if the platform uses OpenShift Data Foundation, I evaluate Metro-DR or Regional-DR depending on latency, distance, and data-loss tolerance. I also include image registry mirroring, secrets management, DNS failover, certificate availability, monitoring, and regular DR drills. A DR strategy is only valid when restore is tested and actual RTO/RPO are measured.

## 30. Common Mistakes

1. Taking backups but never testing restore.
2. Restoring app resources without required operators/CRDs.
3. Assuming etcd backup equals application DR.
4. Forgetting image registry availability.
5. Forgetting secrets, pull secrets, certificates, and CA bundles.
6. Restoring PVCs into a cluster without compatible StorageClass.
7. Using crash-consistent snapshots for databases without validation.
8. DNS TTL too high for required RTO.
9. GitOps auto-prune deletes restored objects.
10. No documented failback process.
11. No monitoring for failed backup schedules.
12. No immutable backup copy.
13. No separation between cluster admin DR and application team DR.
14. Restoring production into test without changing routes or external integrations.
15. Creating active-active traffic for an application that supports only single-writer data.

## 31. Recommended Enterprise Application DR Blueprint

For a production OpenShift environment with multiple applications:

### Platform Layer

- Multi-zone OpenShift cluster where possible
- Dedicated infra nodes for routers/registry/monitoring if required
- ODF or enterprise CSI storage
- VolumeSnapshotClass configured
- OADP installed and monitored
- OpenShift GitOps installed
- RHACM for multi-cluster governance
- Central logging and monitoring
- Trusted certificate and identity integration

### Application Layer

- App manifests in Git
- Namespace per application/environment
- Labels for backup and ownership
- Secrets from external secret manager
- PVC strategy per application
- Database-native replication/backup for critical DBs
- NetworkPolicy included in Git
- Health endpoints exposed
- Resource requests/limits and probes configured

### DR Layer

- Object storage for backups with versioning/immutability
- Backup schedules per tier
- DR cluster with required operators
- Image registry mirror
- DNS/GSLB failover
- Runbooks in Git
- Quarterly restore/failover tests for critical apps
- Evidence stored for audit

## 32. Final Senior-Level Summary

Application DR in OpenShift is a complete enterprise architecture discipline. It is not a single command, a single backup tool, or only an etcd snapshot. A reliable strategy combines declarative configuration, storage-aware backup, application-aware data protection, multi-cluster design, secure secrets handling, image availability, DNS failover, observability, and tested runbooks.

For 10+ years experience level, the expected mindset is:

- Start from business impact, not technology.
- Convert RTO/RPO into architecture.
- Use GitOps for rebuildability.
- Use OADP for application backup/restore.
- Use CSI snapshots or file-system backup based on storage support.
- Use database-native DR for transactional systems.
- Use ODF Metro/Regional DR where storage-integrated multi-cluster failover is required.
- Protect the ACM hub if it is part of your DR control plane.
- Never trust backup until restore is tested.
- Document exact commands and validation steps.
- Measure actual RTO/RPO during drills.

A mature OpenShift Application DR strategy answers one practical question:

> “If the primary application platform is gone right now, can we restore service on another platform, with known data loss, within agreed business time, using a tested and repeatable process?”

If the answer is yes, the DR strategy is real. If the answer is “we have backups somewhere,” the DR strategy is incomplete.
