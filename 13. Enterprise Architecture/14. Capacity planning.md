## 1. What Capacity Planning Means in Enterprise Architecture

Capacity planning is the discipline of predicting, allocating, validating, monitoring, and governing infrastructure resources so that business services run reliably at agreed performance, availability, compliance, and cost levels.

In traditional infrastructure, capacity planning usually meant estimating CPU, RAM, disk, network, and backup requirements for servers. In OpenShift, capacity planning is broader because the platform itself is a multi-tenant distributed system. You are not only sizing virtual machines or bare-metal nodes; you are sizing an entire platform with schedulers, Operators, container runtimes, overlay networking, ingress routers, storage classes, monitoring, logging, registry, CI/CD workloads, tenants, and future scaling behavior.

A senior OpenShift administrator should think of capacity planning as an enterprise architecture function, not only an operations task.

Enterprise capacity planning answers questions like:

- How many clusters are required for production, non-production, DR, edge, or regulated workloads?
- How large should each cluster be?
- How many control plane, infrastructure, and worker nodes are required?
- Which workloads can be co-located, and which must be isolated?
- What is the safe pod density per node?
- How much CPU and memory can tenants request without overloading the cluster?
- How much unused buffer is required for failures, upgrades, patching, and burst traffic?
- How much storage capacity, IOPS, throughput, and backup capacity are required?
- What is the growth model for the next 3, 6, 12, and 24 months?
- Where should autoscaling be used, and where should static capacity be reserved?
- How do quotas, limits, and chargeback/showback prevent noisy-neighbor problems?

In short:

> Capacity planning is the bridge between business demand and platform reliability.

## 2. Why Capacity Planning Is Critical in OpenShift

OpenShift capacity failures usually do not start as a complete outage. They start as slow scheduling, unstable pods, failed builds, OOMKilled workloads, PVC provisioning delays, router saturation, API latency, high etcd disk latency, or monitoring storage exhaustion.

Typical capacity-related incidents include:

- Pods remain in `Pending` because CPU, memory, PVC, node selector, taint, or topology constraints cannot be satisfied.
- Nodes show `MemoryPressure`, `DiskPressure`, or `PIDPressure`.
- Applications restart because memory limits are too low.
- CPU-intensive workloads are throttled because limits are too aggressive.
- One project consumes too many pods, routes, services, secrets, or PVCs.
- Operators create many custom resources and increase API/etcd load.
- Monitoring or logging runs out of persistent storage.
- CI/CD builds spike CPU and image pull activity during business hours.
- Ingress routers become bottlenecks during peak traffic.
- Autoscaling adds replicas, but no node capacity exists to schedule them.
- Cluster upgrades fail or take too long because there is no spare node capacity.
- Zone failure cannot be tolerated because remaining zones do not have enough capacity.

For enterprise OpenShift, capacity planning protects four things:

1. **Availability**: enough spare resources to survive failures and upgrades.
2. **Performance**: enough CPU, memory, I/O, and network capacity to meet SLOs.
3. **Governance**: tenants cannot consume unlimited shared resources.
4. **Cost control**: resources are right-sized instead of massively over-provisioned.

## 3. Capacity Planning vs Sizing vs Performance Tuning vs Autoscaling

These terms are related but not the same.

| Term | Meaning | Example |
|---|---|---|
| Capacity planning | Long-term resource strategy based on business demand, growth, failure scenarios, and governance | Planning 12-month cluster growth for 200 applications |
| Initial sizing | First-pass resource estimate before deployment | Choosing 3 control plane nodes, 3 infra nodes, and 12 workers |
| Performance tuning | Optimizing behavior after measuring workload performance | Tuning JVM heap, CPU manager, huge pages, router threads, storage class |
| Autoscaling | Dynamic scaling based on demand or scheduling pressure | HPA scales app pods; Cluster Autoscaler adds worker nodes |
| Right-sizing | Adjusting requests, limits, replicas, and node types based on real usage | Reducing memory request from 2Gi to 768Mi after 30-day observation |

A common junior mistake is saying, “We have autoscaling, so we do not need capacity planning.” Autoscaling does not remove the need for planning. It only automates part of the response after demand appears. You still must define maximum nodes, cloud quota, IP ranges, storage capacity, route capacity, PDB behavior, cost guardrails, and failure buffers.

## 4. Enterprise Capacity Planning Principles

### 4.1 Plan from business demand, not only infrastructure supply

Start with business/application inputs:

- Number of applications
- Criticality tier
- Number of users
- Request rate
- Batch schedules
- Peak windows
- Release frequency
- DR requirements
- Data retention
- Compliance isolation
- Growth forecast

Then translate those into OpenShift resources:

- CPU requests and limits
- Memory requests and limits
- Replica count
- Pod count
- PVC count and size
- Storage IOPS and throughput
- Route count
- Service count
- NetworkPolicy count
- Log volume
- Metrics cardinality
- Backup size
- Image registry growth

### 4.2 Use requests for scheduling, limits for protection

The Kubernetes scheduler places pods based primarily on resource requests. If teams do not set realistic requests, the scheduler cannot make good decisions. If limits are too low, applications can throttle or restart. If limits are missing in a multi-tenant cluster, one workload can consume shared node resources.

A practical enterprise pattern:

- CPU request: based on normal steady-state usage plus safe buffer.
- CPU limit: optional for latency-sensitive workloads; useful for noisy-neighbor control.
- Memory request: close to real working set.
- Memory limit: always carefully tested because exceeding memory limit causes OOM kill.
- Ephemeral storage request/limit: required for workloads generating temp files, logs, cache, or build artifacts.

### 4.3 Separate critical capacity from best-effort capacity

Not all workloads deserve the same resource guarantee.

| Workload type | Planning approach |
|---|---|
| Critical production | Reserved capacity, strong requests, PDB, anti-affinity, monitoring, DR |
| Business production | Requests/limits, HPA, quotas, zone distribution |
| Non-production | Higher overcommit, scheduled shutdown, lower quotas |
| CI/CD builds | Isolated build nodes or quota-controlled burst pools |
| Batch jobs | Time-windowed capacity and queueing |
| Observability | Dedicated infra capacity and storage |

### 4.4 Plan for failure, upgrade, and maintenance

A cluster sized only for normal running state is under-sized.

You must reserve capacity for:

- One worker node failure
- One availability zone failure, if multi-zone
- Rolling OpenShift upgrades
- Application rolling deployments
- Drain/cordon maintenance
- Infra node replacement
- Storage node replacement
- Monitoring/logging spikes
- Incident debugging pods

A production cluster should normally have enough headroom that critical workloads remain schedulable after losing at least one worker node or one zone, depending on architecture.

### 4.5 Measure before, during, and after

Capacity planning is iterative:

1. Estimate from workload requirements.
2. Deploy with governance.
3. Measure real usage.
4. Right-size requests and limits.
5. Forecast growth.
6. Expand before saturation.
7. Repeat monthly or quarterly.

## 7. Compute Capacity Planning

CPU planning in OpenShift is based on requests, limits, actual usage, throttling, and node allocatable CPU.

### 7.1 CPU units

In Kubernetes/OpenShift:

- `1` CPU means one vCPU/core depending on environment.
- `500m` means half a CPU.
- `100m` means 0.1 CPU.

Example:

```yaml
resources:
  requests:
    cpu: 500m
  limits:
    cpu: "2"
```

This pod asks scheduler to reserve 0.5 CPU but can use up to 2 CPU if available and if CPU limit is enforced.

### 7.2 CPU request calculation

A practical request model:

```text
CPU request per pod = P95 steady CPU usage + safety margin
```

Example:

```text
Observed P95 CPU usage = 350m
Safety margin = 30%
CPU request = 350m × 1.3 = 455m
Round to 500m
```

For production workloads, avoid sizing requests only from average usage. Averages hide peaks.

### 7.3 CPU limit planning

CPU limits are useful for preventing noisy-neighbor behavior, but they can also cause CPU throttling. For latency-sensitive applications, overly tight CPU limits can increase response time.

Practical guidance:

| Workload | CPU request | CPU limit |
|---|---|---|
| Latency-sensitive API | P95 + buffer | 2x-4x request or no limit after risk review |
| Batch job | Expected usage | Hard limit to protect node |
| Dev/test workload | Conservative | Limit required |
| Shared tenant workload | Required | Required by governance |
| Guaranteed workload | Request = limit | For dedicated predictable performance |

### 7.4 CPU overcommit

CPU is compressible. Multiple pods can request less CPU than they might burst to. CPU overcommit can be acceptable when workloads are not all peaking simultaneously.

Example:

```text
Node allocatable CPU = 32 cores
Total CPU requests scheduled = 28 cores
Total CPU limits scheduled = 80 cores
```

This means the node is safe from a scheduling perspective but can become throttled if too many pods try to use their full limits simultaneously.

Enterprise overcommit guidance:

| Environment | CPU request overcommit approach |
|---|---|
| Production Tier 1 | Low overcommit; strong monitoring |
| Production general | Moderate overcommit if usage patterns differ |
| Non-production | Higher overcommit acceptable |
| CI/build | Isolate or limit to avoid platform impact |
| Telco/low-latency | Avoid overcommit; consider CPU pinning and performance profiles |

### 7.5 CPU capacity formula

```text
Required worker CPU = Sum(application CPU requests) + platform overhead + failure buffer + growth buffer
```

Example:

```text
Application CPU requests = 320 cores
Platform overhead = 10% = 32 cores
Failure buffer = 20% = 64 cores
Growth buffer = 25% = 80 cores
Required CPU = 320 + 32 + 64 + 80 = 496 cores
```

If each worker node has 32 allocatable cores:

```text
Required workers = 496 / 32 = 15.5 → 16 workers
```

Add zone balance and node failure rules before finalizing.

### 7.6 CPU saturation symptoms

Look for:

- High CPU usage relative to requests
- CPU throttling
- Increased application latency
- HPA scaling frequently
- Pods stuck Pending due to insufficient CPU
- Node load average consistently high
- API server or router CPU saturation

## 8. Memory Capacity Planning

Memory planning is stricter than CPU planning because memory is not compressible in the same way. If a container exceeds its memory limit, it can be killed.

### 8.1 Memory request and limit behavior

Example:

```yaml
resources:
  requests:
    memory: 1Gi
  limits:
    memory: 2Gi
```

The scheduler reserves 1Gi for placement. The container can use up to 2Gi. If it exceeds 2Gi, it is at risk of OOM kill.

### 8.2 Memory request calculation

A practical formula:

```text
Memory request = P95 working set + application runtime buffer
```

For Java:

```text
Memory request = JVM heap + metaspace + thread stacks + direct memory + native overhead + sidecar overhead + buffer
```

For Go/Node.js/Python:

```text
Memory request = observed working set + GC/runtime overhead + traffic burst buffer
```

### 8.3 Memory limit calculation

```text
Memory limit = expected maximum working set + failure margin
```

Do not set memory limits blindly. A limit that is too low causes restarts; a limit that is too high weakens tenant isolation.

### 8.4 Memory overcommit

Memory overcommit is riskier than CPU overcommit. The scheduler uses requests, not actual future usage. If many pods use memory above request at the same time, the node can experience memory pressure and evictions.

Enterprise guidance:

| Environment | Memory overcommit |
|---|---|
| Tier 1 production | Avoid or keep very low |
| General production | Limited and monitored |
| Non-production | Moderate overcommit acceptable |
| Batch | Depends on job failure tolerance |
| JVM-heavy workloads | Be conservative |

### 8.5 Memory capacity formula

```text
Required worker memory = Sum(memory requests) + platform overhead + failure buffer + growth buffer
```

Example:

```text
Application memory requests = 1,200 Gi
Platform overhead = 10% = 120 Gi
Failure buffer = 20% = 240 Gi
Growth buffer = 25% = 300 Gi
Required memory = 1,860 Gi
```

If each worker has 120Gi allocatable memory:

```text
Required workers = 1,860 / 120 = 15.5 → 16 workers
```

Compare CPU-based worker count and memory-based worker count. The larger number wins.

### 8.6 Memory pressure symptoms

- Pod `OOMKilled`
- Node `MemoryPressure`
- Evicted pods
- High container memory working set
- Kernel OOM events
- JVM full GC or heap pressure
- Prometheus/Elasticsearch/Loki memory pressure

## 9. Pod Density and Node Count Planning

Pod density means how many pods you run per node. It is affected by CPU, memory, storage, network, IP allocation, kubelet settings, CNI behavior, and control-plane/API scalability.

### 9.1 Why pod density matters

High pod density reduces infrastructure cost but increases blast radius and control-plane load.

Low pod density improves isolation and fault tolerance but increases node count, cost, and operational overhead.

### 9.2 Pod density formula

```text
Required nodes by pod count = Required pods per cluster / Target pods per node
```

Example:

```text
Required pods = 2,200
Target pods per node = 110
Required nodes = 2,200 / 110 = 20 nodes
```

### 9.3 Compare all node-count drivers

Final worker count should be the maximum of multiple calculations:

```text
Workers required = max(
  CPU-based workers,
  Memory-based workers,
  Pod-density-based workers,
  Storage-attachment-based workers,
  Network/IP-based workers,
  Zone/failure-based workers
)
```

Example:

| Driver | Required workers |
|---|---:|
| CPU | 14 |
| Memory | 16 |
| Pod density | 20 |
| Storage volume attachment | 12 |
| Zone failure buffer | 18 |
| Final | 20 |

### 9.4 Do not chase maximum pod density blindly

OpenShift documents tested scale maximums, but those are not a recommendation to run every production cluster at the upper boundary. Real workload behavior matters.

Factors that reduce practical pod density:

- Heavy CPU usage
- High memory usage
- Many services/endpoints
- Many NetworkPolicies
- Many secrets/config maps
- Large sidecars
- Service mesh injection
- High log volume
- High metrics cardinality
- PVC attachment limits
- Image pull frequency
- Application startup spikes

### 9.5 Node size trade-off

| Node type | Advantages | Disadvantages |
|---|---|---|
| Few large nodes | Better packing, fewer nodes to manage | Larger failure blast radius, slower drain, bigger impact during node loss |
| Many small nodes | Smaller blast radius, easier drain | More kubelet/node overhead, more node objects, possibly higher cost |
| Mixed pools | Fit workload profiles better | More scheduling/governance complexity |

A senior design normally uses multiple node pools instead of one generic pool for everything.

## 10. Control Plane and etcd Capacity

The OpenShift control plane is responsible for API, scheduling, controllers, authentication, and state storage through etcd. Control plane capacity is not measured only by number of worker nodes; it is driven by object count and rate of change.

### 10.1 Control plane load drivers

- Number of nodes
- Number of pods
- Number of namespaces/projects
- Number of services/endpoints
- Number of routes
- Number of secrets/config maps
- Number of custom resources
- Number of Operators
- Frequency of deployments
- Frequency of builds/jobs
- Watch activity from controllers and tools
- CI/CD automation polling API
- Monitoring scraping API metrics

### 10.2 etcd considerations

etcd is latency-sensitive and I/O-sensitive. Poor etcd disk latency can affect API responsiveness and cluster stability.

Plan for:

- Fast, reliable disks for control plane nodes
- Low-latency network between control plane nodes
- Stable time synchronization
- Object-count governance
- Regular backup strategy
- Monitoring of DB size, fsync latency, leader changes, and API latency

### 10.3 Object count matters

A cluster with fewer pods but many rapidly changing objects can create more control-plane pressure than a cluster with more stable pods.

Examples of object-heavy patterns:

- CI systems creating thousands of short-lived Jobs/Pods
- Operators creating many custom resources
- Projects with thousands of Secrets or ConfigMaps
- Service mesh with high sidecar and config object count
- Frequent GitOps sync of many small resources

### 10.4 Control plane anti-patterns

Avoid:

- Running application workloads on control plane nodes in production.
- Excessively large single namespaces.
- Unbounded CRD installation by tenants.
- CI/CD tools polling APIs too frequently.
- Keeping thousands of completed Jobs forever.
- Creating one ConfigMap/Secret per tiny setting at massive scale.

### 10.5 Control plane capacity controls

Use:

- Namespace design standards
- ResourceQuota object counts
- LimitRange defaults
- TTL for completed Jobs where appropriate
- GitOps sync tuning
- Operator approval governance
- CI/CD API rate discipline
- Separate clusters for high-churn workloads if needed

## 11. Infrastructure Node Capacity

Infrastructure nodes usually host OpenShift platform services that should be isolated from application workloads.

Common infra workloads:

- Ingress router
- Image registry
- Monitoring stack
- Logging collectors/aggregators/log store components
- GitOps controllers
- Pipelines controllers
- Service mesh control plane
- Cluster observability components
- Security/scan operators

### 11.1 Why infra nodes matter

If routers, monitoring, registry, and logging share general worker nodes with unpredictable application workloads, platform services can degrade during application peaks.

Infra node isolation improves:

- Platform stability
- Upgrade predictability
- Cost/showback separation
- Troubleshooting clarity
- Compliance boundaries

### 11.2 Infra node sizing approach

Estimate infra separately:

```text
Infra CPU = router CPU + registry CPU + monitoring CPU + logging CPU + operators + buffer
Infra memory = router memory + registry memory + monitoring memory + logging memory + operators + buffer
Infra storage = registry + monitoring + logging + alerting + local overhead
```

### 11.3 Minimum infra pattern

For production:

- At least 3 infra nodes across zones where possible.
- Taints and tolerations to keep app workloads off infra nodes.
- Dedicated MachineSet/MachineConfigPool if using Machine API.
- Router replicas spread across zones.
- Monitoring storage with redundancy and enough retention.

Example taint:

```bash
oc adm taint nodes <infra-node> node-role.kubernetes.io/infra=:NoSchedule
```

Example label:

```bash
oc label node <infra-node> node-role.kubernetes.io/infra=
```

## 12. Storage Capacity Planning

Storage planning includes capacity, performance, access mode, failure domain, backup, snapshot, retention, and restore speed.

### 12.1 Storage dimensions

| Dimension | Questions |
|---|---|
| Capacity | How many GiB/TiB are required now and in 12 months? |
| IOPS | How many read/write operations per second? |
| Throughput | How many MB/s or GB/s? |
| Latency | What is acceptable read/write latency? |
| Access mode | RWO, RWX, ROX? |
| Expansion | Can PVCs be expanded online? |
| Snapshot | Does CSI support VolumeSnapshot? |
| Backup | Crash-consistent or application-consistent? |
| DR | Can data be replicated to another site/cluster? |
| Security | Encryption at rest/in transit? |

### 12.2 Capacity formula

```text
Required storage = application data + database data + logs + backups + snapshots + registry + monitoring + growth + free-space buffer
```

Example:

```text
Application PVCs = 20 TiB
Database PVCs = 15 TiB
Registry = 3 TiB
Monitoring = 2 TiB
Logging = 10 TiB
Snapshots = 15 TiB
Growth buffer 12 months = 30%
Free-space buffer = 20%
Base = 65 TiB
After growth = 84.5 TiB
After free-space buffer = 101.4 TiB
Plan ≈ 105 TiB usable
```

### 12.3 Storage class strategy

Use multiple StorageClasses based on workload needs:

| StorageClass type | Use case |
|---|---|
| fast-block | Databases, monitoring, low-latency apps |
| standard-block | General RWO workloads |
| shared-file | RWX workloads, shared content |
| object-backed | Registry, backups, logs, artifacts |
| encrypted | Compliance workloads |
| replicated | HA stateful workloads |

### 12.4 Access mode planning

| Access mode | Meaning | Common use |
|---|---|---|
| RWO | ReadWriteOnce | Most databases and app data volumes |
| RWX | ReadWriteMany | Shared content, multi-pod file access |
| ROX | ReadOnlyMany | Shared read-only content |

Do not choose RWX only because it feels convenient. RWX file storage can introduce latency and consistency issues for workloads that need block-like behavior.

### 12.5 Storage performance planning

For each stateful workload, collect:

- Read IOPS
- Write IOPS
- Read latency P95/P99
- Write latency P95/P99
- Throughput
- Working set size
- Backup window
- Restore time requirement

Example database planning:

```text
PostgreSQL workload:
- Data size: 2 TiB
- Growth: 100 Gi/month
- Required write latency: < 5ms P95
- Required IOPS: 8,000 write / 12,000 read
- Backup: daily full + WAL/archive
- RPO: 5 minutes
- RTO: 30 minutes
```

This is not just a PVC size question. It is a storage performance architecture question.

### 12.6 Snapshot and backup capacity

Snapshots are not free. They consume backend capacity as changed blocks accumulate.

Plan:

```text
Snapshot capacity = source volume size × change rate × retention period
```

Example:

```text
Source PVC = 1 TiB
Daily change rate = 10%
Retention = 7 days
Snapshot capacity ≈ 1 TiB × 10% × 7 = 700 GiB
```

For application-consistent backups, also plan pre/post hooks, quiescing, database dumps, WAL archiving, and restore validation.

### 12.7 Storage anti-patterns

Avoid:

- One default StorageClass for every workload.
- Ignoring IOPS and latency.
- Using low-performance storage for etcd, Prometheus, databases, or logging.
- No PVC quota by project.
- No expansion policy.
- No snapshot retention policy.
- No restore testing.
- Assuming storage capacity equals usable protected capacity.

## 13. Network Capacity Planning

OpenShift networking capacity includes pod network, service network, ingress/egress, DNS, firewall, load balancer, NetworkPolicy, and external dependencies.

### 13.1 Network capacity domains

| Domain | Planning item |
|---|---|
| Pod network | Pod CIDR size, pod density, IP exhaustion |
| Service network | Service CIDR size, service count |
| Ingress | Router throughput, TLS, route count, LB capacity |
| Egress | NAT capacity, firewall sessions, proxy throughput |
| DNS | Query volume, CoreDNS/DNS operator capacity |
| NetworkPolicy | Policy complexity and enforcement overhead |
| External | DB, LDAP, registry, object storage, APIs |

### 13.2 CIDR planning

Plan pod and service CIDRs before installation. Changing cluster network CIDRs later is not trivial and may require cluster redeployment depending on design.

Consider:

- Maximum nodes
- Maximum pods per node
- Future expansion
- Cluster-to-cluster routing
- Overlap with corporate networks
- VPN/MPLS/SD-WAN address ranges
- DR site routing

Example:

```text
Expected max nodes = 300
Target max pods per node = 250
Required pod IPs = 300 × 250 = 75,000
Add growth/failure buffer = 30%
Required pod IPs ≈ 97,500
```

### 13.3 Network throughput planning

For each application:

```text
Ingress bandwidth = request rate × average request/response size
Egress bandwidth = downstream call rate × payload size
East-west bandwidth = service-to-service call volume
```

Example:

```text
API peak = 5,000 RPS
Average response = 100KB
Ingress response bandwidth = 5,000 × 100KB = 500,000KB/s ≈ 488MB/s ≈ 3.9Gbps
```

Add TLS overhead, retries, logging/metrics, and burst factor.

### 13.4 Egress planning

Egress is often forgotten.

Plan for:

- External database connections
- Package/image downloads
- API integrations
- SaaS endpoints
- Object storage backups
- Log forwarding
- Proxy/firewall throughput
- NAT gateway limits
- Connection tracking limits

### 13.5 DNS capacity

DNS problems look like application problems. High pod churn and service discovery activity can increase DNS load.

Watch for:

- High DNS query latency
- DNS pod CPU usage
- Applications doing excessive DNS lookups
- Missing DNS caching in application runtimes
- Large numbers of services

### 13.6 NetworkPolicy scale

NetworkPolicy is essential for security, but excessive or poorly designed policies can increase operational complexity.

Plan policy architecture:

- Default deny per namespace
- Allow required ingress explicitly
- Use labels consistently
- Avoid one-off labels per pod unless necessary
- Standardize namespace labels such as `team`, `env`, `zone`, `data-classification`

## 14. Ingress and Route Capacity

OpenShift routes are served by ingress controllers/router pods. Ingress capacity depends on number of routes, TLS termination, request rate, connection count, payload size, and router replicas.

### 14.1 Ingress capacity inputs

For each exposed application:

- Number of routes
- TLS termination type: edge, passthrough, re-encrypt
- Peak RPS
- Concurrent connections
- WebSocket/long-lived connections
- Average payload size
- Upload/download traffic
- Timeout requirements
- WAF/proxy integration

### 14.2 Router scaling

Router capacity can be scaled by:

- Increasing ingress controller replicas
- Using dedicated infra nodes
- Creating sharded ingress controllers
- Separating internal and external routes
- Using different ingress controllers for different teams/environments
- Ensuring load balancer capacity is sufficient

### 14.3 Route sharding pattern

Example enterprise model:

| Ingress controller | Purpose |
|---|---|
| default-external | Public applications |
| internal | Internal corporate applications |
| pci | PCI-regulated workloads |
| dev | Non-production routes |
| high-throughput | Heavy traffic APIs |

### 14.4 Ingress anti-patterns

Avoid:

- One default ingress controller for all traffic in a large enterprise.
- Running routers on overloaded worker nodes.
- Ignoring TLS CPU cost.
- No route ownership policy.
- No limit on routes per namespace.
- No separation between internal and external exposure.

## 15. Registry and Image Capacity

The internal OpenShift image registry stores image layers and metadata. Even if many enterprises use external registries like Quay, Harbor, Nexus, or Artifactory, OpenShift image capacity still matters for builds and image streams.

### 15.1 Registry capacity drivers

- Number of applications
- Build frequency
- Image size
- Number of tags retained
- Number of environments
- CI/CD pipeline behavior
- Image pruning policy
- Multi-architecture images
- Vulnerability scanning retention

### 15.2 Registry storage formula

```text
Registry storage = average image size × builds per day × retention days × environments × deduplication factor
```

Example:

```text
Average image = 800Mi
Builds/day = 100
Retention = 14 days
Environments = 3
Raw = 800Mi × 100 × 14 × 3 = 3,360,000Mi ≈ 3.2TiB
After layer reuse/deduplication, actual may be lower, but plan conservative capacity.
```

### 15.3 Image pull capacity

Image pulls consume:

- Registry bandwidth
- Node disk space
- CRI-O storage
- Network bandwidth
- Startup time

High image pull activity during deployments can create performance issues.

Mitigations:

- Use image pruning.
- Keep image sizes small.
- Use local registry mirrors in disconnected sites.
- Stagger deployments.
- Use pre-pull DaemonSets only when justified.
- Avoid unnecessary rebuilds.

## 16. Monitoring, Logging, and Observability Capacity

Observability systems are themselves workloads that need capacity. Monitoring and logging often become some of the largest storage consumers in an OpenShift platform.

### 16.1 Monitoring capacity drivers

- Number of nodes
- Number of pods
- Number of services
- Number of ServiceMonitors/PodMonitors
- Scrape interval
- Metrics cardinality
- Retention period
- Alerting rules
- Recording rules
- User workload monitoring enablement

### 16.2 Prometheus storage rough model

Prometheus storage depends heavily on sample count and retention.

```text
Samples per second = active time series / scrape interval
Daily samples = samples per second × 86,400
Storage = daily samples × bytes per sample × retention days
```

Example:

```text
Active series = 1,000,000
Scrape interval = 30s
Samples/sec = 33,333
Daily samples ≈ 2.88 billion
If compressed cost ≈ 1.5 bytes/sample:
Daily storage ≈ 4.3GB plus index/WAL overhead
Retention 15 days ≈ 64.5GB plus overhead
```

In real environments, always validate with actual Prometheus TSDB metrics because label cardinality can radically change storage needs.

### 16.3 Metrics cardinality control

Bad metric labels can explode cardinality.

Avoid labels like:

- user ID
- request ID
- session ID
- timestamp
- full URL with IDs
- pod UID when unnecessary
- transaction ID

Good labels:

- service
- namespace
- route
- method
- status code class
- environment
- region/zone

### 16.4 Logging capacity drivers

- Application log volume per pod
- Number of pods
- Log level
- Retention days
- Indexing strategy
- Compression ratio
- Audit log requirements
- Security log forwarding
- Multi-cluster aggregation

Logging formula:

```text
Daily log volume = pods × average logs per pod per day
Storage = daily volume × retention days × replication factor × index overhead
```

Example:

```text
500 pods × 2GB/day = 1TB/day
Retention = 14 days
Replication factor = 2
Index overhead = 30%
Required = 1TB × 14 × 2 × 1.3 = 36.4TB
```

### 16.5 Observability anti-patterns

Avoid:

- Debug log level permanently enabled.
- No retention policy.
- No metric cardinality review.
- Scraping every endpoint too frequently.
- Monitoring PVCs without alerting on free space.
- Storing all logs in-cluster without capacity forecast.
- No separation between platform monitoring and application observability.

## 17. Quota, LimitRange, and Multi-Tenant Governance

Capacity planning without quota is only a spreadsheet. Quota turns architecture into enforceable policy.

### 17.1 ResourceQuota

`ResourceQuota` limits aggregate resource consumption inside a namespace/project.

It can limit:

- CPU requests
- CPU limits
- Memory requests
- Memory limits
- Storage requests
- PVC count
- Pod count
- Service count
- Secret count
- ConfigMap count
- Route count using object count syntax where supported
- Extended resources such as GPU

Example:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-prod-quota
  namespace: team-a-prod
spec:
  hard:
    requests.cpu: "40"
    limits.cpu: "80"
    requests.memory: 160Gi
    limits.memory: 240Gi
    requests.storage: 2Ti
    pods: "200"
    services: "50"
    secrets: "100"
    configmaps: "100"
    persistentvolumeclaims: "40"
```

### 17.2 LimitRange

`LimitRange` sets default, minimum, and maximum resource values in a namespace.

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-container-limits
  namespace: team-a-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 256Mi
    default:
      cpu: 500m
      memory: 512Mi
    min:
      cpu: 50m
      memory: 128Mi
    max:
      cpu: "2"
      memory: 4Gi
```

### 17.3 Quota design by environment

| Environment | Quota style |
|---|---|
| Production | Strict CPU/memory/storage/object quotas |
| Staging | Similar to prod but smaller |
| Development | Lower quota, higher overcommit |
| Sandbox | Very small quota and TTL cleanup |
| CI/CD | Separate build quota and concurrency controls |

### 17.4 Quota governance model

A mature governance process includes:

1. Default quota template per environment.
2. Exception process for larger quota.
3. Monthly usage review.
4. Showback/chargeback by project/team.
5. Alerting when namespace usage exceeds threshold.
6. Automated cleanup for abandoned namespaces.
7. GitOps-managed quotas.

### 17.5 Requests and limits enforcement

If quotas include `requests.cpu`, `requests.memory`, `limits.cpu`, or `limits.memory`, then workloads must specify those values or receive defaults through LimitRange. This is useful because it prevents teams from deploying pods without resource governance.

## 18. Autoscaling Strategy

Autoscaling is a capacity execution mechanism. It should be designed with guardrails.

### 18.1 Types of autoscaling

| Autoscaling type | Object/operator | What it scales |
|---|---|---|
| Horizontal Pod Autoscaler | HPA | Pod replicas |
| Vertical Pod Autoscaler | VPA | Pod requests/recommendations |
| Cluster Autoscaler | ClusterAutoscaler | Cluster worker capacity |
| Machine Autoscaler | MachineAutoscaler | MachineSet replicas |
| Custom Metrics Autoscaler | KEDA-based operator | Pods/jobs based on custom/external metrics |

### 18.2 HPA capacity impact

HPA increases pod replicas. It does not guarantee node capacity exists.

Example:

```text
API deployment current replicas = 5
HPA max replicas = 30
CPU request per pod = 500m
Additional CPU request possible = (30 - 5) × 500m = 12.5 cores
```

The cluster must have spare capacity or cluster autoscaler capacity to schedule those additional pods.

### 18.3 Cluster autoscaler planning

When using Cluster Autoscaler:

- Define `maxNodesTotal` carefully.
- Align max nodes with cloud quota.
- Ensure MachineAutoscaler min/max per MachineSet.
- Keep enough IP address capacity.
- Keep enough storage attachment and load balancer capacity.
- Understand scale-up time.
- Plan cost maximums.
- Ensure PDBs do not block scale-down.

### 18.4 Autoscaling anti-patterns

Avoid:

- HPA max replicas higher than cluster can ever support.
- Cluster Autoscaler max nodes not aligned with subnet/IP capacity.
- Using CPU HPA for workloads bottlenecked on memory, I/O, locks, or external APIs.
- Aggressive scale-down causing repeated cold starts.
- No PDB review.
- No cost guardrails.
- No alert when autoscaler reaches max.

### 18.5 Autoscaling design example

```text
Application: payment-api
Normal replicas: 6
HPA min: 6
HPA max: 30
CPU request: 500m
Memory request: 1Gi
Peak additional capacity: 24 pods = 12 CPU + 24Gi memory
Cluster autoscaler max additional workers: 6 nodes
Each worker allocatable: 8 CPU + 32Gi memory
Max added capacity: 48 CPU + 192Gi memory
Result: HPA burst fits within cluster autoscaler envelope.
```

## 19. Capacity Forecasting and Growth Models

Capacity planning should be time-based.

### 19.1 Forecast periods

| Period | Purpose |
|---|---|
| Daily | Incident prevention, immediate saturation |
| Weekly | Short-term trend and cleanup |
| Monthly | Quota review and right-sizing |
| Quarterly | Procurement/cloud commitment planning |
| Yearly | Enterprise architecture and budget planning |

### 19.2 Linear growth model

```text
Future capacity = current usage + (monthly growth × months)
```

Example:

```text
Current memory requests = 1,000Gi
Growth = 80Gi/month
Forecast 6 months = 1,000 + (80 × 6) = 1,480Gi
Add 25% buffer = 1,850Gi
```

### 19.3 Peak-based model

Use for seasonal workloads.

```text
Capacity = annual peak × safety factor
```

Example:

```text
Normal pods = 800
Festival peak = 2,000
Safety factor = 1.25
Planned pod capacity = 2,500
```

### 19.4 Percentile-based model

Use Prometheus data:

- CPU request planning: P95/P99 actual usage plus buffer
- Memory request planning: P95 working set plus buffer
- Storage planning: current used + growth rate + retention
- Network planning: P95/P99 bandwidth and connection count

### 19.5 Burn-rate model

For storage:

```text
Days until full = available capacity / daily growth rate
```

Example:

```text
Available = 20TiB
Daily growth = 500GiB/day
Days until full = 20,480GiB / 500GiB = 40.9 days
```

Set alerts well before the burn-down reaches procurement or provisioning lead time.

## 20. Capacity Planning for High Availability and Disaster Recovery

HA/DR capacity is where many designs fail. Running normally is easy. Surviving failure is the real test.

### 20.1 N+1 node failure capacity

If one worker fails, remaining workers must run critical pods.

```text
Required capacity after one-node failure = current scheduled requests must fit on remaining nodes
```

Example:

```text
Workers = 10
Each allocatable = 32 CPU, 128Gi
Total = 320 CPU, 1280Gi
One node failure total = 288 CPU, 1152Gi
Critical scheduled requests must be below this after buffer.
```

### 20.2 Zone failure capacity

For multi-zone clusters, decide whether the platform must survive a full zone failure.

Example three-zone model:

```text
Total workers = 18
Workers per zone = 6
If one zone fails, remaining workers = 12
Production critical workload must fit into 12 workers.
```

This often means running at lower normal utilization, such as 50-60%, to tolerate a zone loss.

### 20.3 Upgrade capacity

During upgrade, nodes are drained and rebooted/replaced. If no spare capacity exists, pods cannot move safely.

Plan:

- PDBs allow at least one replica disruption where appropriate.
- Enough spare CPU/memory exists for drained node workloads.
- Stateful workloads have safe disruption policy.
- Infra nodes have enough router/monitoring redundancy.

### 20.4 DR cluster capacity

DR design options:

| DR model | Capacity approach |
|---|---|
| Active-active | Both sites sized for normal load plus failover share |
| Active-passive warm | DR site has enough base capacity, scales during failover |
| Active-passive cold | Lower cost, longer RTO, capacity provisioned during disaster |
| Backup/restore | Capacity required for restore target and data rehydration |

### 20.5 DR capacity formula

```text
DR required capacity = critical workload capacity + platform services + restore overhead + failover buffer
```

Do not forget:

- Image registry availability
- DNS failover
- External database capacity
- Storage replication
- Backup restore bandwidth
- Secrets/certificates
- Ingress/load balancer capacity
- Monitoring/logging after failover

## 21. Capacity Planning for Different Workload Types

### 21.1 Stateless microservices

Plan for:

- Replica count
- HPA behavior
- CPU and memory requests
- Startup spikes
- Readiness/liveness probes
- Route/service count
- NetworkPolicy count
- Log volume

Best practices:

- Use HPA for variable traffic.
- Keep images small.
- Set realistic readiness probes.
- Use PDB for critical services.
- Distribute replicas across zones/nodes.

### 21.2 Stateful applications

Plan for:

- PVC size and growth
- IOPS/latency
- Backup and restore time
- Pod disruption behavior
- Storage topology
- StatefulSet rolling update behavior
- Anti-affinity
- Data replication

Best practices:

- Prefer managed external databases for enterprise critical data when possible.
- Use CSI snapshots only after validating consistency needs.
- Test restore, not only backup.
- Monitor PVC usage and storage latency.

### 21.3 CI/CD workloads

CI/CD can be high churn and high burst.

Plan for:

- Build concurrency
- Build pod CPU/memory
- Image pull/push bandwidth
- Registry storage
- Temporary storage
- Cache strategy
- Pipeline retention

Best practices:

- Isolate build workloads.
- Apply quotas.
- Use separate node pool for builds.
- Limit parallelism.
- Prune old build artifacts/images.

### 21.4 Batch jobs and CronJobs

Plan for:

- Job schedule overlap
- Peak concurrent jobs
- Retry behavior
- Backoff limits
- Temporary storage
- External dependency load

Best practices:

- Avoid all CronJobs starting exactly at midnight.
- Stagger schedules.
- Set resource requests/limits.
- Set history limits.
- Clean up completed jobs.

### 21.5 JVM workloads

Plan for:

- Heap size
- Non-heap memory
- Thread count
- Direct memory
- Container awareness
- GC behavior
- Startup CPU

Best practices:

- Do not set memory limit equal only to heap size.
- Leave room for metaspace, native memory, thread stacks, and sidecars.
- Use JVM container flags appropriate to runtime version.

### 21.6 Service mesh workloads

Service mesh adds sidecars and control-plane overhead.

Plan for:

- Extra CPU/memory per pod
- More metrics
- More logs
- More certificates/secrets
- More config objects
- Increased network latency

Best practices:

- Use mesh only where needed.
- Size sidecar requests explicitly.
- Watch metrics cardinality.
- Avoid injecting every namespace by default in large clusters.

### 21.7 GPU and specialized hardware

Plan for:

- Extended resource quotas
- Node labels/taints
- Driver/operator capacity
- GPU memory
- Workload scheduling constraints
- Utilization monitoring

Best practices:

- Isolate GPU nodes.
- Use quotas for `requests.nvidia.com/gpu` or other extended resources.
- Avoid CPU/memory starvation around GPU workloads.

## 26. Common Mistakes and Senior-Level Recommendations

### Mistake 1: Planning from node capacity instead of workload demand

Wrong:

```text
We have 10 nodes, each 32 CPU, so we are fine.
```

Right:

```text
We need 240 requested CPU, 900Gi requested memory, 1,800 pods peak, N+1 failure buffer, 25% growth, and enough infra capacity.
```

### Mistake 2: Ignoring requests and limits

Without requests, the scheduler cannot place workloads intelligently. Without limits or governance, tenants can consume too much shared resource.

### Mistake 3: Sizing only for normal load

Plan for peak, failover, upgrade, and growth.

### Mistake 4: Ignoring storage performance

PVC size alone does not define storage capacity. IOPS, latency, throughput, access mode, snapshot behavior, and backup/restore time matter.

### Mistake 5: No quota per namespace

A shared platform without quotas becomes first-come-first-served infrastructure.

### Mistake 6: Overusing one giant cluster

Large clusters are powerful, but blast radius, tenant isolation, upgrade windows, and control-plane object count matter. Sometimes multiple smaller clusters are better.

### Mistake 7: Autoscaling without limits

Autoscaling must have guardrails. HPA, MachineAutoscaler, cloud quota, IP ranges, and budget must align.

### Mistake 8: No capacity for observability

Monitoring and logging must be sized like production workloads.

### Mistake 9: Forgetting node drain capacity

If a node cannot be drained without pending pods, the cluster is under-sized for maintenance.

### Mistake 10: No restore testing

Backup capacity planning is incomplete until restore time and restore capacity are validated.

## 27. Interview and Real-Project Talking Points

Use these points when discussing OpenShift capacity planning as a senior administrator.

### 27.1 Short explanation

Capacity planning in OpenShift is the process of translating business and application demand into cluster resources such as worker nodes, CPU, memory, pod density, storage, network, ingress, monitoring, logging, quota, and autoscaling limits. It must include normal load, peak load, failure scenarios, upgrades, DR, and future growth.

### 27.2 Senior-level explanation

In enterprise OpenShift, I do not size only by CPU and memory. I build a demand model per application and namespace, calculate requested CPU/memory, pod density, PVC growth, storage performance, route/service/object count, log volume, monitoring cardinality, and network throughput. Then I compare those requirements against node allocatable capacity, tested scale boundaries, control-plane behavior, infra services, and failure-domain requirements. I enforce the model with ResourceQuota, LimitRange, node pools, taints/tolerations, HPA/VPA, Cluster Autoscaler, PDBs, and continuous Prometheus-based forecasting.

### 27.3 Real-project answer

For production, I usually separate worker pools by workload class: general, infra, build, storage-heavy, GPU, or memory-optimized. I reserve capacity for OpenShift system pods and DaemonSets, then add N+1 or zone-failure buffer depending on SLA. I use quotas to control tenant consumption and review actual usage monthly to right-size requests. For storage, I plan not only PVC size but also IOPS, latency, snapshots, backup retention, and restore time. For ingress, I plan route count, TLS, RPS, and router replicas. For observability, I plan Prometheus retention, log ingestion, and metrics cardinality because monitoring can become a major capacity consumer.

### 27.4 Red flags to mention

- Pods without requests/limits
- High memory overcommit in production
- No namespace quota
- No spare capacity for node drain
- Infra services mixed with noisy workloads
- Monitoring PVC nearly full
- Too many high-cardinality metrics
- HPA max replicas not aligned with node capacity
- Large object count in a single namespace
- No storage performance validation

## Closing Note

For a 10-year-experience OpenShift administrator, capacity planning is not only about adding more worker nodes. It is about designing a predictable, governed, observable, scalable, and cost-aware platform. The best capacity plans combine architecture standards, workload measurements, quotas, autoscaling, storage and network engineering, DR assumptions, and continuous review.

A strong OpenShift capacity planning statement is:

> “I size OpenShift from workload demand and failure requirements, validate it against tested platform limits, enforce it through quotas and node pool design, and continuously improve it with Prometheus-based measurement and forecasting.”
