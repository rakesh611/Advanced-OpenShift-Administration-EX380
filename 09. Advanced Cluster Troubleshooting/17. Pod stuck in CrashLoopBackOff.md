## 1. Executive Summary

A pod shown as `CrashLoopBackOff` means at least one container in the pod is repeatedly starting, exiting or being killed, and then being restarted by kubelet according to the pod restart policy. Kubernetes/OpenShift applies a back-off delay between restarts to avoid continuously hammering the node and control plane with rapid restart attempts.

In OpenShift, `CrashLoopBackOff` is usually not the root cause. It is the symptom. The actual root cause is normally visible in one or more of the following places:

- `oc describe pod <pod>`
- `oc logs <pod> -c <container>`
- `oc logs <pod> -c <container> --previous`
- `.status.containerStatuses[*].lastState.terminated`
- pod events
- application startup logs
- liveness/startup probe failure events
- node kubelet and CRI-O logs
- memory and CPU metrics
- OpenShift Security Context Constraint admission/runtime behavior
- dependency checks such as database, DNS, route, service, certificate, or external API connectivity

For a senior administrator, the objective is not just to restart the pod. The objective is to answer:

1. **Which container is crashing?**
2. **What killed it or why did it exit?**
3. **Was the exit application-driven, kubelet-driven, kernel-driven, security-driven, or dependency-driven?**
4. **Was this introduced by a recent deployment, config change, node issue, operator upgrade, image change, or traffic increase?**
5. **What is the safest fix with minimum blast radius?**

## 2. What `CrashLoopBackOff` Really Means

A pod can contain one or more containers. `CrashLoopBackOff` is usually displayed when a container inside the pod repeatedly terminates and kubelet backs off before restarting it.

Typical sequence:

```text
1. Pod is scheduled to a node.
2. Image is pulled or already available.
3. Container is created.
4. Container starts.
5. Container exits, crashes, is killed, or fails a liveness/startup probe.
6. kubelet restarts it because restartPolicy allows restart.
7. It fails again.
8. kubelet increases the delay between restarts.
9. oc get pods shows CrashLoopBackOff.
```

Important points:

- `CrashLoopBackOff` is not normally a scheduler issue.
- It is not normally an image pull issue.
- It means the container reached the start/run phase but did not remain healthy.
- The current log may be empty because the container exits quickly.
- The previous container log is often the most important evidence.

Use:

```bash
oc logs <pod> -n <namespace> -c <container> --previous
```

That command often shows the real failure.

## 3. `CrashLoopBackOff` vs Other Pod States

| Pod state | Meaning | First place to check |
|---|---|---|
| `Pending` | Pod not scheduled or waiting for resources/PVC | `oc describe pod`, scheduler events, PVC, node capacity |
| `ContainerCreating` | Runtime is creating container, mounting volumes, attaching network | events, kubelet, CRI-O, CNI, storage |
| `ImagePullBackOff` | Image pull failed and is backed off | image name, registry, pull secret, CA, network |
| `ErrImagePull` | Generic image retrieval error | image reference, registry auth, tag |
| `CreateContainerConfigError` | Invalid config before container start | ConfigMap, Secret, env, volume reference |
| `RunContainerError` | Runtime failed to start container | command, permission, runtime, mount, SELinux |
| `CrashLoopBackOff` | Container starts but repeatedly exits or is killed | previous logs, lastState, exit code, probes, OOM |
| `OOMKilled` | Container exceeded memory limit or was killed due to memory pressure | resource limits, memory metrics, node pressure |
| `Completed` | Container finished successfully | expected for Jobs, bad for long-running Deployments |
| `Error` | Container exited with non-zero code | logs and exit code |

A common mistake is treating all pod failures the same. `CrashLoopBackOff` requires container-level runtime and application investigation, not scheduler investigation first.

## 4. Senior Troubleshooting Mindset

A 10-year experienced OpenShift administrator follows evidence, not guesses.

### Golden rules

1. **Do not delete the pod immediately.**  
   Deleting can remove useful evidence like previous logs and events.

2. **Identify the exact crashing container.**  
   Multi-container pods are common with service meshes, sidecars, init containers, log collectors, and operators.

3. **Collect evidence before changing anything.**  
   Save pod YAML, describe output, logs, events, deployment YAML, and metrics.

4. **Check recent changes.**  
   Crash loops often follow an image rollout, ConfigMap change, Secret rotation, probe change, SCC change, certificate expiry, or dependency outage.

5. **Differentiate symptom from root cause.**  
   A liveness probe failure may be the immediate kill reason, but the deeper cause may be slow database initialization.

6. **Fix the controller, not only the pod.**  
   If the pod is owned by a Deployment, DeploymentConfig, StatefulSet, DaemonSet, Job, CronJob, or Operator, patch the owner resource.

7. **Respect OpenShift security model.**  
   Avoid blindly granting `anyuid`, `privileged`, or `hostmount-anyuid`. Use least privilege.

8. **Use rollout strategy.**  
   Roll back, pause, patch, canary, or scale carefully depending on production impact.

## 5. Fast Triage Workflow

Replace variables:

```bash
NS=<namespace>
POD=<pod-name>
```

### Step 1: Confirm status

```bash
oc get pod -n $NS $POD -o wide
oc get pod -n $NS $POD -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.state}{"\t"}{.lastState}{"\t"}{.restartCount}{"\n"}{end}'
```

### Step 2: Describe pod

```bash
oc describe pod -n $NS $POD
```

Look for:

```text
State:          Waiting
Reason:         CrashLoopBackOff
Last State:     Terminated
Reason:         Error / OOMKilled / Completed
Exit Code:      1 / 2 / 126 / 127 / 137 / 139 / 143
Started:
Finished:
Restart Count:
Events:
```

### Step 3: List containers

```bash
oc get pod -n $NS $POD -o jsonpath='{.spec.containers[*].name}{"\n"}'
oc get pod -n $NS $POD -o jsonpath='{.spec.initContainers[*].name}{"\n"}'
```

### Step 4: Current and previous logs

```bash
# Current container attempt
oc logs -n $NS $POD -c <container>

# Previous crashed attempt - often most useful
oc logs -n $NS $POD -c <container> --previous

# Tail and timestamps
oc logs -n $NS $POD -c <container> --previous --timestamps --tail=200
```

### Step 5: Events sorted by time

```bash
oc get events -n $NS --sort-by='.lastTimestamp' | tail -50
oc get events -n $NS --field-selector involvedObject.name=$POD --sort-by='.lastTimestamp'
```

### Step 6: Identify owner

```bash
oc get pod -n $NS $POD -o jsonpath='{.metadata.ownerReferences[*].kind}{"/"}{.metadata.ownerReferences[*].name}{"\n"}'
```

Then inspect the owner:

```bash
oc get deploy,dc,sts,ds,job -n $NS
oc describe deploy -n $NS <deployment>
oc rollout history deploy -n $NS <deployment>
```

### Step 7: Check resource usage

```bash
oc adm top pod -n $NS $POD --containers
oc adm top pods -n $NS
oc adm top nodes
```

### Step 8: Quick classification

| Evidence | Likely cause |
|---|---|
| `Reason: OOMKilled`, exit `137` | Memory limit exceeded or node memory pressure |
| exit `127` | Command/binary not found |
| exit `126` | Command found but not executable / permission issue |
| exit `1` or `2` | Application/config error |
| exit `139` | Segmentation fault/native crash |
| `Liveness probe failed` | Probe too aggressive or app unhealthy |
| `Startup probe failed` | App did not initialize in time |
| `permission denied`, `EACCES` | UID/SCC/volume permission/SELinux issue |
| `connection refused`, `timeout`, `no such host` | Dependency, service, DNS, network policy, route, cert issue |
| `Back-off restarting failed container` | Symptom, not root cause |

## 6. Deep Diagnostic Workflow

### 6.1 Capture baseline evidence

Create a local evidence directory:

```bash
NS=<namespace>
POD=<pod-name>
mkdir -p crashloop-$NS-$POD

oc get pod -n $NS $POD -o yaml > crashloop-$NS-$POD/pod.yaml
oc describe pod -n $NS $POD > crashloop-$NS-$POD/pod.describe.txt
oc get events -n $NS --sort-by='.lastTimestamp' > crashloop-$NS-$POD/events.txt
oc get deploy,dc,sts,ds,rs,job,cronjob -n $NS -o wide > crashloop-$NS-$POD/workloads.txt
```

Save logs for each container:

```bash
for c in $(oc get pod -n $NS $POD -o jsonpath='{.spec.containers[*].name}'); do
  oc logs -n $NS $POD -c $c --timestamps > crashloop-$NS-$POD/$c.current.log 2>&1 || true
  oc logs -n $NS $POD -c $c --previous --timestamps > crashloop-$NS-$POD/$c.previous.log 2>&1 || true
done
```

Save init container logs:

```bash
for c in $(oc get pod -n $NS $POD -o jsonpath='{.spec.initContainers[*].name}'); do
  oc logs -n $NS $POD -c $c --timestamps > crashloop-$NS-$POD/init-$c.current.log 2>&1 || true
  oc logs -n $NS $POD -c $c --previous --timestamps > crashloop-$NS-$POD/init-$c.previous.log 2>&1 || true
done
```

### 6.2 Check status fields directly

```bash
oc get pod -n $NS $POD -o json | jq '.status.containerStatuses[] | {
  name,
  ready,
  restartCount,
  state,
  lastState,
  started
}'
```

Without `jq`:

```bash
oc get pod -n $NS $POD -o jsonpath='{range .status.containerStatuses[*]}Container={.name}{"\n"}Ready={.ready}{"\n"}RestartCount={.restartCount}{"\n"}State={.state}{"\n"}LastState={.lastState}{"\n\n"}{end}'
```

### 6.3 Confirm pod owner and rollout revision

```bash
OWNER_KIND=$(oc get pod -n $NS $POD -o jsonpath='{.metadata.ownerReferences[0].kind}')
OWNER_NAME=$(oc get pod -n $NS $POD -o jsonpath='{.metadata.ownerReferences[0].name}')
echo "$OWNER_KIND/$OWNER_NAME"
```

If owner is ReplicaSet, find Deployment:

```bash
RS=$OWNER_NAME
oc get rs -n $NS $RS -o jsonpath='{.metadata.ownerReferences[0].kind}{"/"}{.metadata.ownerReferences[0].name}{"\n"}'
```

Rollout history:

```bash
oc rollout history deploy -n $NS <deployment-name>
oc rollout status deploy -n $NS <deployment-name>
```

### 6.4 Compare running vs desired configuration

```bash
oc get deploy -n $NS <deployment-name> -o yaml > deployment.yaml
oc get rs -n $NS -l app=<label> -o wide
```

Check whether the crash started after:

- image tag change
- ConfigMap or Secret update
- resource limit change
- probe change
- service account change
- SCC binding change
- route/TLS change
- node replacement
- operator upgrade
- application dependency upgrade

### 6.5 Inspect exact container command

```bash
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*]}{.name}{"\ncommand: "}{.command}{"\nargs: "}{.args}{"\n\n"}{end}'
```

### 6.6 Inspect mounted config and secrets references

```bash
oc get pod -n $NS $POD -o jsonpath='{range .spec.volumes[*]}{.name}{"\t"}{.configMap.name}{"\t"}{.secret.secretName}{"\n"}{end}'
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*].env[*]}{.name}{"\t"}{.valueFrom.configMapKeyRef.name}{"\t"}{.valueFrom.secretKeyRef.name}{"\n"}{end}'
```

### 6.7 Check runtime node

```bash
NODE=$(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
echo $NODE
oc describe node $NODE
oc adm top node $NODE
```

## 7. Reading Pod Status Like an Expert

Example status:

```yaml
containerStatuses:
- name: app
  ready: false
  restartCount: 12
  state:
    waiting:
      reason: CrashLoopBackOff
      message: back-off 5m0s restarting failed container=app pod=myapp-...
  lastState:
    terminated:
      reason: Error
      exitCode: 1
      startedAt: "2026-07-03T10:01:00Z"
      finishedAt: "2026-07-03T10:01:03Z"
```

How to interpret:

- `state.waiting.reason=CrashLoopBackOff`: current displayed state.
- `lastState.terminated.reason=Error`: last attempt ended in error.
- `exitCode=1`: application or script exited with generic failure.
- `startedAt` and `finishedAt` difference is 3 seconds: application fails almost immediately.
- `restartCount=12`: loop has repeated; check previous logs quickly before evidence rotates.

Another example:

```yaml
lastState:
  terminated:
    reason: OOMKilled
    exitCode: 137
```

This means the container was killed due to memory exhaustion or cgroup memory limit breach. Fixing application configuration alone may not be enough; you need memory analysis.

## 8. Most Common Root Causes

### 8.1 Application-level causes

- application exits because required config is missing
- application cannot connect to DB/cache/message broker
- wrong command, args, or startup script
- migration failure
- invalid license file
- expired certificate
- application panic/exception
- missing writable directory
- JVM/native memory crash
- service port already in use inside container
- wrong working directory

### 8.2 OpenShift/Kubernetes causes

- liveness probe too aggressive
- startup probe missing for slow application
- memory limit too low
- CPU request too low causing slow startup
- Secret/ConfigMap key missing
- SCC denies expected UID or filesystem access
- pod running as random UID and image expects root or fixed UID
- read-only root filesystem but app writes under `/tmp`, `/var`, `/run`, `/opt`, or home directory
- volume permission mismatch
- projected token/config volume issue
- node pressure
- CRI-O/runtime issue

### 8.3 External causes

- database unavailable
- DNS issue
- NetworkPolicy blocking egress or ingress
- service endpoint missing
- certificate trust issue
- expired TLS certificate
- route/load balancer change
- external API throttling
- firewall/proxy outage

## 9. Application Crash Issues

### Symptoms

```text
Exception in thread "main"
panic: runtime error
FATAL: database is required
Config file not found
Unable to start embedded server
Migration failed
Application failed to start
```

### Commands

```bash
oc logs -n $NS $POD -c <container> --previous --timestamps
oc logs -n $NS deploy/<deployment-name> --all-containers --since=30m
oc describe pod -n $NS $POD
```

### How to prove it

Check `lastState`:

```bash
oc get pod -n $NS $POD -o json | jq '.status.containerStatuses[] | select(.name=="app") | .lastState'
```

Check exit code:

```bash
oc get pod -n $NS $POD -o jsonpath='{.status.containerStatuses[?(@.name=="app")].lastState.terminated.exitCode}{"\n"}'
```

### Typical fixes

- correct env variables
- correct mounted configuration
- correct Secret key name
- rollback bad release
- fix application startup dependency
- increase startup timeout
- run DB migration manually or as a controlled Job
- ensure image contains expected binary/config

### Production-safe approach

```bash
# Pause rollout before repeated changes
oc rollout pause deploy/<deployment> -n $NS

# Patch safely or apply corrected manifest
oc set env deploy/<deployment> -n $NS KEY=value

# Resume rollout
oc rollout resume deploy/<deployment> -n $NS
oc rollout status deploy/<deployment> -n $NS
```

Rollback if needed:

```bash
oc rollout history deploy/<deployment> -n $NS
oc rollout undo deploy/<deployment> -n $NS
```

## 10. Bad Command, Args, or Entrypoint

### Symptoms

```text
/bin/sh: myapp: command not found
exec: "start.sh": executable file not found in $PATH
permission denied
no such file or directory
standard_init_linux.go: exec user process caused
```

### Exit codes

| Exit code | Meaning |
|---|---|
| `126` | Command found but not executable / permission denied |
| `127` | Command not found |
| `1` | Generic failure |
| `2` | Shell misuse or app-specific error |

### Commands

```bash
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*]}{.name}{"\ncommand: "}{.command}{"\nargs: "}{.args}{"\nimage: "}{.image}{"\n\n"}{end}'
oc logs -n $NS $POD -c <container> --previous
```

### Debug image entrypoint

Create a temporary debug pod using the same image but override command:

```bash
oc run debug-image -n $NS --image=<image> --restart=Never --command -- sleep 3600
oc rsh -n $NS debug-image
```

Inside:

```bash
id
pwd
ls -l /
ls -l /app
which myapp || true
ls -l /app/start.sh
```

### Fix examples

Wrong:

```yaml
command: ["start.sh"]
```

Better:

```yaml
command: ["/bin/sh", "-c"]
args:
  - exec /app/start.sh
```

Ensure executable bit in image build:

```Dockerfile
COPY start.sh /app/start.sh
RUN chmod 0755 /app/start.sh
```

But avoid solving OpenShift permission issues by blindly running as root.

## 11. Configuration, Secret, and Environment Variable Issues

### Symptoms

```text
Missing required environment variable DB_PASSWORD
ConfigMap key not found
Secret key does not exist
open /etc/app/config.yaml: no such file or directory
invalid YAML
invalid JSON
failed to parse duration
```

### Important distinction

- If a referenced ConfigMap/Secret object is missing, pod may show `CreateContainerConfigError` before container starts.
- If object exists but application does not like the value, pod may start and then crash into `CrashLoopBackOff`.

### Commands

```bash
oc describe pod -n $NS $POD
oc set env deploy/<deployment> -n $NS --list
oc get configmap -n $NS
oc get secret -n $NS
oc get configmap -n $NS <name> -o yaml
oc get secret -n $NS <name> -o yaml
```

Decode a Secret value:

```bash
oc get secret -n $NS <secret> -o jsonpath='{.data.<key>}' | base64 -d; echo
```

Check mounted files:

```bash
oc rsh -n $NS $POD -c <container>
ls -la /etc/app
cat /etc/app/config.yaml
```

If container exits too quickly, use a debug pod with same mounts or temporarily override command in a non-production copy.

### Fix examples

Patch env var:

```bash
oc set env deploy/<deployment> -n $NS DB_HOST=mysql DB_PORT=3306
```

Create/update ConfigMap:

```bash
oc create configmap app-config -n $NS --from-file=config.yaml=./config.yaml --dry-run=client -o yaml | oc apply -f -
oc rollout restart deploy/<deployment> -n $NS
```

Create/update Secret:

```bash
oc create secret generic app-secret -n $NS \
  --from-literal=DB_PASSWORD='redhat' \
  --dry-run=client -o yaml | oc apply -f -
oc rollout restart deploy/<deployment> -n $NS
```

### Senior note

ConfigMap and Secret changes do not always restart pods automatically. If the value is consumed as environment variables, the pod must be recreated. If the value is mounted as a volume, kubelet updates it eventually, but applications may not reload it automatically.

## 12. OpenShift SCC, UID, SELinux, and Permission Issues

OpenShift runs containers with stronger security defaults than vanilla Kubernetes. A container image that works locally with Docker as root may crash in OpenShift because OpenShift assigns a random high UID and constrains filesystem access.

### Symptoms

```text
permission denied
EACCES
mkdir: cannot create directory '/var/cache/nginx': Permission denied
nginx: [emerg] mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)
listen tcp :80: bind: permission denied
chown: changing ownership: Operation not permitted
unable to write PID file
open /run/app/app.pid: permission denied
```

### Key concepts

OpenShift Security Context Constraints control what a pod can do. SCCs can control privileged mode, allowed capabilities, host access, SELinux context, container user ID, FSGroup, supplemental groups, seccomp profiles, and volume types.

Default OpenShift behavior commonly expects images to run as non-root and support arbitrary UIDs.

### Commands

Check service account:

```bash
oc get pod -n $NS $POD -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

Check SCC annotation on admitted pod:

```bash
oc get pod -n $NS $POD -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

Check UID actually running:

```bash
oc rsh -n $NS $POD -c <container> id
```

Check namespace UID range:

```bash
oc get ns $NS -o yaml | grep -E 'uid-range|supplemental-groups|mcs'
```

Check pod security context:

```bash
oc get pod -n $NS $POD -o yaml | grep -A30 -B5 securityContext
```

Check SCC access:

```bash
oc adm policy who-can use scc anyuid
oc adm policy who-can use scc privileged
```

### Correct image design for OpenShift

A good OpenShift-compatible image:

- does not require root
- does not require fixed UID
- writes only to writable paths
- gives group `0` write access to required directories
- avoids privileged ports under `1024`
- uses `/tmp`, `/var/tmp`, or configured writable directories
- avoids runtime `chown` as root

Example Dockerfile pattern:

```Dockerfile
RUN mkdir -p /app /app/data /tmp/app \
    && chgrp -R 0 /app /tmp/app \
    && chmod -R g=u /app /tmp/app

USER 1001
WORKDIR /app
```

### Safer fixes

Prefer fixing image permissions:

```Dockerfile
RUN chgrp -R 0 /var/cache/nginx /var/run /var/log/nginx \
    && chmod -R g=u /var/cache/nginx /var/run /var/log/nginx
```

Use non-privileged port:

```yaml
ports:
- containerPort: 8080
```

Configure application to write to `/tmp` or mounted writable volume.

### When `anyuid` is used

For legacy images that require a fixed UID/root, bind the minimum required SCC to the service account, not to all users.

```bash
oc create sa legacy-app-sa -n $NS
oc adm policy add-scc-to-user anyuid -z legacy-app-sa -n $NS
oc set serviceaccount deploy/<deployment> legacy-app-sa -n $NS
oc rollout restart deploy/<deployment> -n $NS
```

Remove when no longer needed:

```bash
oc adm policy remove-scc-from-user anyuid -z legacy-app-sa -n $NS
```

### Senior warning

Do not modify default SCCs. Create custom SCCs only when necessary and document why. Granting `privileged` or `hostmount-anyuid` can create serious security exposure and should require change approval.

## 13. Liveness Probe Causing Crash Loops

A liveness probe failure kills the container. If the application is healthy but slow, overloaded, or the probe is wrong, kubelet can create a crash loop.

### Symptoms in events

```text
Warning  Unhealthy  kubelet  Liveness probe failed: HTTP probe failed with statuscode: 500
Warning  Unhealthy  kubelet  Liveness probe failed: Get "http://10.x.x.x:8080/health": context deadline exceeded
Normal   Killing    kubelet  Container app failed liveness probe, will be restarted
Warning  BackOff    kubelet  Back-off restarting failed container app
```

### Commands

```bash
oc describe pod -n $NS $POD | sed -n '/Events:/,$p'
oc get pod -n $NS $POD -o yaml | grep -A40 -B5 livenessProbe
oc logs -n $NS $POD -c <container> --previous --timestamps
```

### Common probe mistakes

| Mistake | Result |
|---|---|
| Liveness points to readiness endpoint | Container restarted during dependency outage |
| Initial delay too short | App killed before boot completes |
| Timeout too low | App killed during CPU/network spikes |
| Wrong port | Constant liveness failure |
| Wrong path | HTTP 404/500 triggers restart |
| Probe requires DB | DB outage restarts all app pods |
| HTTPS probe against HTTP port | TLS/connection failure |
| Missing startup probe | Slow first boot becomes crash loop |

### Good probe design

- Liveness should answer: “Is this process irrecoverably broken?”
- Readiness should answer: “Can this pod receive traffic now?”
- Startup should answer: “Has initial boot completed?”

Do not use liveness to check every dependency. If DB is down, the pod should usually become NotReady, not restart forever.

### Fix example

Bad:

```yaml
livenessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 1
  failureThreshold: 3
```

Better:

```yaml
startupProbe:
  httpGet:
    path: /startup
    port: 8080
  periodSeconds: 10
  failureThreshold: 30

readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

livenessProbe:
  httpGet:
    path: /live
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 20
  timeoutSeconds: 3
  failureThreshold: 3
```

Patch deployment:

```bash
oc edit deploy/<deployment> -n $NS
oc rollout status deploy/<deployment> -n $NS
```

## 14. Startup Probe and Slow Application Boot

Many enterprise applications need time for:

- JVM warmup
- database migration
- cache initialization
- certificate loading
- dependency discovery
- service mesh sidecar readiness
- large configuration parsing
- first-time schema initialization

Without a startup probe, liveness may start killing the app too early.

### Symptoms

```text
Application started after 90 seconds locally, but pod restarts every 30 seconds.
Liveness probe failed before server is ready.
```

### Diagnose

```bash
oc describe pod -n $NS $POD | grep -i -A5 -B5 probe
oc logs -n $NS $POD -c <container> --previous --timestamps
```

Compare timestamps:

```text
10:00:00 App starting
10:00:20 Loading configuration
10:00:30 Killed by liveness probe
```

### Fix

Add startup probe with enough budget:

```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 10
  failureThreshold: 60
  timeoutSeconds: 2
```

This gives up to 10 * 60 = 600 seconds before kubelet kills the container for startup failure.

## 15. OOMKilled and Memory Pressure

`OOMKilled` is one of the most important `CrashLoopBackOff` causes.

### Symptoms

```yaml
lastState:
  terminated:
    reason: OOMKilled
    exitCode: 137
```

Logs may stop suddenly without a stack trace.

Events may show:

```text
Container app was OOMKilled
```

### Commands

```bash
oc describe pod -n $NS $POD
oc get pod -n $NS $POD -o json | jq '.status.containerStatuses[] | {name, restartCount, lastState}'
oc adm top pod -n $NS $POD --containers
oc adm top pods -n $NS
oc adm top node $(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
```

Check resource limits:

```bash
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*]}{.name}{"\nrequests: "}{.resources.requests}{"\nlimits: "}{.resources.limits}{"\n\n"}{end}'
```

### Understand exit code 137

Exit code `137` usually means the process received SIGKILL. In containers, the most common reason is memory limit enforcement by cgroups or the node/kernel under pressure.

### Common OOM causes

- memory limit too low
- Java heap not container-aware or too large
- native memory usage ignored
- cache size unbounded
- memory leak
- high request concurrency
- large file processing
- sidecar memory overhead not considered
- node memory pressure
- app has no memory limit and gets killed during node pressure

### Java-specific checks

For Java workloads, do not set heap equal to container memory limit. Leave room for:

- metaspace
- thread stacks
- direct buffers
- JIT/code cache
- native libraries
- TLS buffers
- monitoring agent
- service mesh sidecar overhead

Example:

```yaml
env:
- name: JAVA_TOOL_OPTIONS
  value: >-
    -XX:MaxRAMPercentage=70
    -XX:+ExitOnOutOfMemoryError
resources:
  requests:
    memory: 512Mi
    cpu: 250m
  limits:
    memory: 1Gi
    cpu: "1"
```

### Fix options

Increase memory limit if justified:

```bash
oc set resources deploy/<deployment> -n $NS \
  --requests=cpu=250m,memory=512Mi \
  --limits=cpu=1,memory=1Gi
```

Rollout:

```bash
oc rollout status deploy/<deployment> -n $NS
```

But do not only increase memory blindly. Confirm if the app is leaking memory.

### Advanced OOM analysis

Use Prometheus/metrics if available:

- container memory working set
- container memory RSS
- restart count increase
- node memory pressure
- pod memory limit utilization
- JVM heap metrics
- garbage collection frequency

Useful PromQL examples:

```promql
rate(kube_pod_container_status_restarts_total{namespace="$NS", pod=~"$POD"}[5m])
```

```promql
container_memory_working_set_bytes{namespace="$NS", pod="$POD", container="app"}
```

```promql
kube_pod_container_resource_limits{namespace="$NS", pod="$POD", resource="memory"}
```

## 16. CPU Starvation, Timeout, and Thread Exhaustion

CPU starvation does not usually kill a container directly, but it can cause:

- slow startup
- liveness timeout
- readiness failure
- request timeout
- application watchdog exit
- thread starvation
- JVM GC delays

### Symptoms

```text
Liveness probe failed: context deadline exceeded
Read timeout
Application startup timed out
GC overhead limit exceeded
```

### Commands

```bash
oc adm top pod -n $NS $POD --containers
oc adm top pods -n $NS
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{.resources}{"\n\n"}{end}'
```

### Fixes

- increase CPU request for guaranteed scheduling share
- increase timeoutSeconds on probes
- use startupProbe
- reduce startup workload
- move heavy migration to Job
- tune thread pools
- avoid tiny CPU requests for JVM apps

Example:

```bash
oc set resources deploy/<deployment> -n $NS \
  --requests=cpu=500m,memory=1Gi \
  --limits=cpu=2,memory=2Gi
```

## 17. Storage and Volume Mount Problems

Some volume problems stop the container before start, but others allow the container to start and then crash because files are missing, read-only, incorrectly owned, or not writable.

### Symptoms

```text
permission denied
read-only file system
no such file or directory
failed to open database file
cannot write pid file
mkdir /data: permission denied
```

### Commands

```bash
oc describe pod -n $NS $POD
oc get pvc -n $NS
oc describe pvc -n $NS <pvc>
oc get pv
oc get pod -n $NS $POD -o yaml | grep -A40 volumes:
oc get pod -n $NS $POD -o yaml | grep -A40 volumeMounts:
```

If pod can stay alive briefly or with debug command:

```bash
oc rsh -n $NS $POD -c <container>
mount | grep -E '/data|/app|/var'
ls -lZ /data
id
```

### Common OpenShift storage causes

- PVC mounted read-only while app expects write
- app writes to image path instead of mounted volume
- fixed UID cannot write to PVC
- FSGroup not applied as expected
- SELinux label mismatch on hostPath/local path
- ConfigMap mounted over a directory hiding application files
- Secret/config volume has default `0444` permissions
- app tries to modify ConfigMap/Secret volume, which is read-only

### Fix examples

Mount writable PVC to correct path:

```yaml
volumeMounts:
- name: app-data
  mountPath: /var/lib/app
volumes:
- name: app-data
  persistentVolumeClaim:
    claimName: app-data-pvc
```

For images expecting arbitrary UID, group permissions should allow writes:

```Dockerfile
RUN chgrp -R 0 /var/lib/app && chmod -R g=u /var/lib/app
```

Avoid mounting ConfigMap over an application directory that contains required files:

Bad:

```yaml
mountPath: /app
```

Better:

```yaml
mountPath: /app/config/config.yaml
subPath: config.yaml
```

## 18. Network and Dependency Failures

Applications often exit when dependencies are unavailable. This creates a crash loop even though the container image is fine.

### Symptoms

```text
dial tcp: lookup mysql: no such host
connection refused
connection timed out
SSLHandshakeException
certificate signed by unknown authority
FATAL: password authentication failed
Redis connection refused
Kafka bootstrap servers unavailable
```

### Commands

Check services/endpoints:

```bash
oc get svc,endpoints,endpointslice -n $NS
oc describe svc -n $NS <service>
oc get pods -n $NS -l <selector>
```

DNS test from a debug pod:

```bash
oc run net-debug -n $NS --image=registry.access.redhat.com/ubi9/ubi --restart=Never --command -- sleep 3600
oc rsh -n $NS net-debug
```

Inside debug pod:

```bash
getent hosts mysql
curl -vk http://service:8080/health
curl -vk https://service:8443/health
```

If `nc` is installed:

```bash
nc -zv mysql 3306
```

If not installed, use bash TCP check:

```bash

```

Check NetworkPolicy:

```bash

oc describe networkpolicy -n $NS <policy>
```

Check cross-namespace labels:

```bash
oc get ns --show-labels
oc get pods -n <target-ns> --show-labels
```

### Fixes

- correct service name or namespace FQDN
- fix Service selector labels
- fix target port
- create correct NetworkPolicy allow rules
- mount trusted CA bundle
- correct DB credentials
- increase retry/backoff in application instead of exiting immediately
- move dependency checks from liveness to readiness

### Senior note

A production-grade app should usually not exit immediately if DB is temporarily unavailable. It should retry with backoff and fail readiness until dependencies recover. Crashing every few seconds worsens outages.

## 19. Image, Runtime, and Architecture Issues

Some image problems appear after start rather than during pull.

### Symptoms

```text
exec format error
no such file or directory
GLIBC_2.xx not found
libssl.so not found
permission denied
standard_init_linux.go
```

### Causes

- wrong CPU architecture image, for example ARM image on x86_64 node
- missing shared library
- script has Windows CRLF line endings
- shebang points to missing interpreter
- binary not executable
- distroless/minimal image missing shell or tool expected by startup script


Fix CRLF:

```bash
sed -i 's/\r$//' start.sh
```

## 20. Operator Managed Pods

If the crashing pod belongs to an Operator-managed operand, do not manually edit the pod or deployment unless you understand reconciliation behavior.

### Symptoms

- manual patch is reverted
- pod recreated with same bad config
- ClusterOperator degraded
- CSV failed or degraded
- Operand CR has invalid spec

### Commands

```bash
oc get pod -n <operator-namespace> <pod> -o jsonpath='{.metadata.ownerReferences[*].kind}{"/"}{.metadata.ownerReferences[*].name}{"\n"}'
oc get csv -A
oc get subscription -A
oc get installplan -A
oc get co
oc describe co <operator>
```

Check custom resources:

```bash
oc api-resources | grep -i <operator>
oc get <custom-resource> -A
oc describe <custom-resource> -n <ns> <name>
```

### Fix strategy

1. Identify whether crash is operator pod or operand pod.
2. Check CSV/Subscription/InstallPlan.
3. Check operator logs.
4. Check operand custom resource status.
5. Fix the custom resource or subscription source, not only the generated deployment.
6. Use operator documentation for supported changes.

### Example

If an Elasticsearch, GitLab, Quay, or database operand pod is crash-looping due to invalid CR configuration, manual deployment patches may be overwritten. Patch the CR that the operator watches.

## 22. Node-Level and CRI-O Investigation

Most `CrashLoopBackOff` issues are application-level, but node-level investigation is required when:

- multiple unrelated pods crash on same node
- CRI-O errors appear
- node is `NotReady`
- node has `MemoryPressure`, `DiskPressure`, or `PIDPressure`
- container logs are missing
- pod sandbox/container creation errors occur
- kernel OOM messages exist

### Identify node

```bash
NODE=$(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
echo $NODE
oc describe node $NODE
oc adm top node $NODE
```

### Debug node

```bash
oc debug node/$NODE
chroot /host
```

Inside node debug shell:

```bash
systemctl status kubelet
systemctl status crio
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
dmesg -T | egrep -i 'oom|killed process|memory|segfault' | tail -100
crictl ps -a | head
crictl pods | head
```

Find container:

```bash
crictl ps -a | grep <pod-name>
crictl inspect <container-id>
crictl logs <container-id>
```

Check node pressure:

```bash
oc describe node $NODE | egrep -A5 'Conditions|Pressure|Allocated resources'
df -h
free -m
pidstat 1 5 || true
```

### Node remediation

If node has systemic issues:

```bash
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data
```

Then repair/reboot/reprovision depending on root cause:

```bash
systemctl restart crio kubelet
# or controlled reboot through approved change process
```

After recovery:

```bash
oc adm uncordon $NODE
```

### Senior warning

Restarting CRI-O/kubelet can disrupt workloads on that node. Drain first where possible and follow production change controls.

## 25. Production-Safe Remediation Strategy

### 25.1 Avoid panic actions

Do not immediately run:

```bash
oc delete pod <pod>
```

unless:

- evidence is already collected
- pod is stateless and controller will recreate it
- deletion is part of a known safe recovery step

### 25.2 Fix controller source

| Pod owner | Fix resource |
|---|---|
| Deployment | Deployment spec |
| DeploymentConfig | DeploymentConfig spec |
| StatefulSet | StatefulSet spec, PVC, ordered rollout |
| DaemonSet | DaemonSet spec, node compatibility |
| Job | Job template or create new Job |
| CronJob | CronJob template |
| Operator | Custom Resource / Subscription / CSV |
| Static pod | MachineConfig/static pod source/operator-managed config |

### 25.3 Use rollout controls

```bash
oc rollout pause deploy/<deployment> -n $NS
oc rollout history deploy/<deployment> -n $NS
oc rollout undo deploy/<deployment> -n $NS
oc rollout resume deploy/<deployment> -n $NS
oc rollout status deploy/<deployment> -n $NS
```

### 25.4 Reduce blast radius

- scale only affected deployment
- patch only affected namespace
- use canary deployment for risky changes
- avoid cluster-wide SCC or namespace security changes
- do not modify default SCCs
- coordinate with app owners before changing resource limits

### 25.5 Document final RCA

Minimum RCA fields:

```text
Incident ID:
Namespace:
Application:
Pod:
Container:
Start time:
Detected by:
Impact:
Immediate symptom:
Root cause:
Evidence:
Fix applied:
Validation:
Preventive action:
Owner:
```

## 26. Case Studies

### Case Study 1: Missing Secret key

#### Symptom

```text
CrashLoopBackOff
Application log: Missing required environment variable MYSQL_ROOT_PASSWORD
```

#### Investigation

```bash
oc logs -n app mysql-xxx -c mysql --previous
oc set env deploy/mysql -n app --list
oc get secret -n app
oc get secret db-secret -n app -o yaml
```

#### Root cause

Secret existed but key was named `MYSQL_PASSWORD`; application expected `MYSQL_ROOT_PASSWORD`.

#### Fix

```bash
oc create secret generic db-secret -n app \
  --from-literal=MYSQL_ROOT_PASSWORD=redhat \
  --dry-run=client -o yaml | oc apply -f -

oc rollout restart deploy/mysql -n app
```

#### Validation

```bash
oc rollout status deploy/mysql -n app
oc logs -n app deploy/mysql
```

---

### Case Study 2: Liveness probe too aggressive

#### Symptom

```text
Normal Killing: Container app failed liveness probe, will be restarted
```

#### Evidence

App takes 90 seconds to start, but liveness starts at 15 seconds.

#### Fix

Add startup probe:

```yaml
startupProbe:
  httpGet:
    path: /startup
    port: 8080
  periodSeconds: 10
  failureThreshold: 15
```

Increase liveness initial delay or allow startup probe to gate liveness.

#### Validation

```bash
oc describe pod -n app <new-pod> | grep -i probe
oc rollout status deploy/app -n app
```

---

### Case Study 3: OpenShift random UID permission issue

#### Symptom

```text
nginx: [emerg] mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)
```

#### Root cause

Image expected root user and writable `/var/cache/nginx`, but OpenShift ran the container with a random non-root UID.

#### Better fix

Rebuild image with group-writable directories and run on non-root port:

```Dockerfile
RUN chgrp -R 0 /var/cache/nginx /var/run /var/log/nginx \
    && chmod -R g=u /var/cache/nginx /var/run /var/log/nginx
USER 1001
```

Use port `8080` instead of `80`.

#### Temporary workaround if approved

```bash
oc create sa nginx-legacy -n web
oc adm policy add-scc-to-user anyuid -z nginx-legacy -n web
oc set serviceaccount deploy/nginx nginx-legacy -n web
oc rollout restart deploy/nginx -n web
```

---

### Case Study 4: OOMKilled Java pod

#### Symptom

```yaml
lastState:
  terminated:
    reason: OOMKilled
    exitCode: 137
```

#### Investigation

```bash
oc adm top pod -n payments payments-api-xxx --containers
oc get deploy payments-api -n payments -o yaml | grep -A10 resources
```

#### Root cause

Container memory limit was `512Mi`, JVM heap tried to use most of the limit, and native memory caused cgroup OOM.

#### Fix

```yaml
env:
- name: JAVA_TOOL_OPTIONS
  value: "-XX:MaxRAMPercentage=65 -XX:+ExitOnOutOfMemoryError"
resources:
  requests:
    memory: 1Gi
    cpu: 500m
  limits:
    memory: 2Gi
    cpu: "2"
```

#### Validation

Monitor restarts and memory trend for at least one traffic cycle.

---

### Case Study 5: Service selector mismatch

#### Symptom

```text
App exits: cannot connect to http://backend:8080
```

#### Investigation

```bash
oc get svc backend -n app -o yaml
oc get endpoints backend -n app
oc get pods -n app --show-labels
```

#### Finding

Service selector:

```yaml
selector:
  app: backend
```

Pods label:

```yaml
labels:
  app.kubernetes.io/name: backend
```

No endpoints existed.

#### Fix

Patch service selector or deployment labels consistently:

```bash
oc patch svc backend -n app -p '{"spec":{"selector":{"app.kubernetes.io/name":"backend"}}}'
```

### Case Study 6: ConfigMap mounted over application directory

#### Symptom

```text
/app/start.sh: no such file or directory
```

#### Root cause

ConfigMap was mounted at `/app`, hiding files baked into the image.

#### Bad YAML

```yaml
volumeMounts:
- name: config
  mountPath: /app
```

#### Fix

```yaml
volumeMounts:
- name: config
  mountPath: /app/config.yaml
  subPath: config.yaml
```

## 29. Prevention and Operational Best Practices

### 29.1 Build images for OpenShift

- support arbitrary UID
- avoid root-only paths
- avoid privileged ports
- make writable paths group-writable by group `0`
- use non-root user
- include minimal diagnostics only where appropriate
- use immutable image tags or digests in production

### 29.2 Design proper probes

- use startup probe for slow initialization
- keep liveness independent from external dependencies where possible
- use readiness for dependency availability
- set realistic timeouts
- monitor probe failure rate

### 29.3 Resource management

- set requests and limits based on measurement
- monitor memory trends
- leave memory headroom for JVM/native processes
- avoid tiny CPU requests for heavy startup apps
- use HPA carefully with resource requests

### 29.4 Configuration management

- validate ConfigMaps and Secrets in CI/CD
- avoid manual production edits without GitOps tracking
- use rollout restarts after env-based config changes
- version critical config
- use canary rollout for risky changes

### 29.5 Dependency resilience

- apps should retry dependencies with exponential backoff
- dependency outage should normally fail readiness, not cause crash
- do not put dependency checks in liveness unless process is unrecoverable
- make TLS trust explicit

### 29.6 Observability

Alert on:

- restart rate
- `CrashLoopBackOff` pods
- OOMKilled events
- liveness probe failures
- high memory limit utilization
- node pressure
- deployment rollout failures

Example PromQL:

```promql
increase(kube_pod_container_status_restarts_total[10m]) > 3
```

```promql
kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"} == 1
```

```promql
increase(kube_pod_container_status_restarts_total[5m]) > 0
and
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

### 29.7 Change management

Before deploying:

- confirm image runs as non-root
- validate probes
- validate ConfigMap/Secret references
- confirm service endpoints
- confirm resource limits
- run smoke tests in staging
- verify rollback path

## 30. Interview and Real-World Talking Points

If asked in an interview, answer like this:

> `CrashLoopBackOff` means the container starts but repeatedly exits or is killed, and kubelet is backing off before restart. I first identify the crashing container using `oc describe pod` and `containerStatuses`, then check `oc logs --previous` because the current container may already have restarted. I inspect `lastState.terminated.reason`, exit code, events, probes, resource limits, SCC annotation, service account, mounted ConfigMaps/Secrets, and dependency connectivity. If it is `OOMKilled`, I validate memory limits and usage. If events show liveness failure, I verify probe path, port, timeout, and startup timing. In OpenShift, I also check random UID/SCC-related permission problems. Finally, I fix the owning controller or operator-managed CR, not only the pod, and validate using rollout status, logs, events, metrics, and restart count.

Advanced points to mention:

- `--previous` logs are critical.
- Exit codes help classify root cause.
- Liveness should not be used as dependency readiness.
- OpenShift arbitrary UID commonly breaks root-designed images.
- `anyuid` is a workaround, not the preferred fix.
- OOMKilled requires memory and application analysis, not only pod deletion.
- Operator-managed resources should be fixed through the CR/operator path.
- Node-level analysis is needed when unrelated pods fail on the same node.
