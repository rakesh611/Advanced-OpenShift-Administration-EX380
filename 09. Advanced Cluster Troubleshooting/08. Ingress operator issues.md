# Ingress Operator Issues — Advanced Cluster Troubleshooting for OpenShift Administration

**Audience:** Advanced OpenShift administrators, L3 support engineers, SREs, platform engineers  
**Experience level:** Written for an administrator with ~10 years of Linux, networking, Kubernetes, and OpenShift operations experience  
**Focus:** Troubleshooting `ingress` ClusterOperator, IngressController, router pods, HAProxy routing, wildcard DNS, load balancer, routes, TLS, canary checks, and production incidents  
**Applies to:** OpenShift Container Platform 4.x

---

## 1. What the Ingress Operator does

In OpenShift, the **Ingress Operator** is responsible for enabling external access to services running inside the cluster.

The Ingress Operator manages one or more **IngressController** resources. Each IngressController normally creates and manages HAProxy-based router components that expose OpenShift `Route` and Kubernetes `Ingress` resources.

In simple words:

```text
External Client
   |
   | DNS: app.apps.cluster.example.com
   v
Load Balancer / VIP / NodePort / HostNetwork
   |
   v
OpenShift Router Pod: HAProxy
   |
   v
OpenShift Service
   |
   v
Application Pod Endpoint
```

The Ingress Operator is not only about application routes. Several core OpenShift components also depend on route availability, for example:

- OAuth route
- Console route
- Downloads route
- Monitoring routes
- Canary route used by the Ingress Operator for health verification

If the Ingress stack is unhealthy, users may report:

- Application URLs are down
- Console URL is unavailable
- OAuth login fails
- Routes return `503`
- Routes return wrong certificate
- `oc get co ingress` shows `Degraded=True`
- Cluster upgrade is blocked or risky
- IngressController status shows canary failures
- Router pods are pending, crash looping, or not ready

## 4. Troubleshooting mindset

Ingress issues are usually not one-layer problems. Always isolate the failure layer.

Use this flow:

```text
1. ClusterOperator status
2. IngressController status
3. Operator pod logs
4. Router deployment/pods
5. Router service / endpoint publishing
6. DNS wildcard record
7. Load balancer / VIP / firewall
8. Canary route
9. Route admission
10. Service selector and endpoints
11. Backend pod readiness
12. TLS termination and certificates
```

Do not start by editing random router deployments. In OpenShift 4, router deployments are operator-managed. Permanent changes must usually be made through:

```bash
oc edit ingresscontroller/default -n openshift-ingress-operator
```

or:

```bash
oc patch ingresscontroller/default -n openshift-ingress-operator ...
```

## 5. First 5-minute incident checklist

Run these commands first in any Ingress incident:

```bash
oc get co ingress
oc describe co ingress
oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller/default -n openshift-ingress-operator
oc get pods -n openshift-ingress-operator -o wide
oc logs -n openshift-ingress-operator deploy/ingress-operator
oc get pods -n openshift-ingress -o wide
oc get svc -n openshift-ingress
oc get route -n openshift-ingress-canary
oc describe route canary -n openshift-ingress-canary
```

Then test from outside:

```bash
dig +short '*.apps.<cluster-domain>'
dig +short canary-openshift-ingress-canary.apps.<cluster-domain>
curl -vk https://console-openshift-console.apps.<cluster-domain>
curl -v  http://canary-openshift-ingress-canary.apps.<cluster-domain>
```

Test from inside the cluster:

```bash
oc run netshoot -n default --rm -it --restart=Never \
  --image=registry.redhat.io/ubi9/ubi -- /bin/bash
```

Inside the pod:

```bash
curl -v http://canary-openshift-ingress-canary.apps.<cluster-domain>
curl -vk https://console-openshift-console.apps.<cluster-domain>
getent hosts canary-openshift-ingress-canary.apps.<cluster-domain>
```

If `curl` works inside the cluster but fails outside, suspect:

- External DNS
- Load balancer
- Firewall
- VIP ownership
- NodePort or HostNetwork exposure
- Cloud load balancer health check
- External network path

If it fails both inside and outside, suspect:

- Router pods
- Router service
- IngressController
- Route admission
- Cluster DNS
- Network plugin
- Backend service/pod readiness

## 6. Understanding `oc get co ingress`

`oc get co ingress` gives the high-level condition of the Ingress stack.

Example:

```bash
oc get co ingress
```

```text
NAME      VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE
ingress   4.14.0    True        False         True       30m
```

This means the operator might still have an available router, but something is wrong and requires investigation.

Always inspect the message:

```bash
oc describe co ingress
```

or:

```bash
oc get co ingress -o yaml
```

Important condition fields:

```yaml
status:
  conditions:
  - type: Available
    status: "True"
  - type: Progressing
    status: "False"
  - type: Degraded
    status: "True"
    reason: CanaryChecksRepetitiveFailures
    message: Canary route checks for the default ingress controller are failing
```

Interpretation:

| Condition | Meaning |
|---|---|
| `Available=True` | At least the required ingress function is available |
| `Progressing=True` | Operator is applying or reconciling changes |
| `Degraded=True` | One or more required checks or managed resources are failing |

`Degraded=True` does not always mean every route is down. It means the operator has detected a fault. In production, treat it seriously because it may affect upgrades, console, OAuth, route admission, or future reconciliation.

## 7. IngressController deep inspection

The IngressController CR is the main object for router configuration.

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml
```

Important fields:

```yaml
spec:
  domain: apps.ocp4.example.com
  replicas: 2
  endpointPublishingStrategy:
    type: LoadBalancerService
  defaultCertificate:
    name: custom-certs-default
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/worker: ""
  routeSelector: {}
  namespaceSelector: {}
status:
  availableReplicas: 2
  conditions:
  - type: Available
  - type: Progressing
  - type: Degraded
  endpointPublishingStrategy:
    type: LoadBalancerService
  domain: apps.ocp4.example.com
```

Useful commands:

```bash
oc describe ingresscontroller/default -n openshift-ingress-operator
oc get ingresscontroller/default -n openshift-ingress-operator \
  -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" msg="}{.message}{"\n"}{end}'
```

Check domain:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o jsonpath='{.status.domain}{"\n"}'
oc get ingresses.config/cluster -o yaml
```

Remember:

- `ingresses.config/cluster.spec.domain` defines the cluster ingress domain.
- The default IngressController uses that domain unless its own domain is configured.
- Route hosts are normally generated from the IngressController domain.

## 8. Issue: `CanaryChecksRepetitiveFailures`

### 8.1 What it means

The Ingress Operator creates and checks a canary route:

```text
canary-openshift-ingress-canary.apps.<cluster-domain>
```

The operator periodically sends HTTP requests to this route. If the canary route cannot be reached repeatedly, the Ingress Operator marks the IngressController or ClusterOperator as degraded.

Typical message:

```text
CanaryChecksSucceeding=False
CanaryChecksRepetitiveFailures:
Canary route checks for the default ingress controller are failing
```

Operator logs may show:

```text
error performing canary route check
error sending canary HTTP Request
Client.Timeout exceeded while awaiting headers
```

---

### 8.2 Common root causes

| Cause | Explanation |
|---|---|
| Wildcard DNS broken | `*.apps.<cluster-domain>` does not resolve to router LB/VIP |
| Canary host DNS broken | Canary route host does not resolve |
| LB not forwarding | LB receives traffic but does not send it to router nodes |
| Firewall blocked | Port 80/443 blocked from operator path |
| Router pods not ready | HAProxy is unavailable or not accepting traffic |
| Router service wrong | Service has no endpoints or wrong type |
| NetworkPolicy / firewall | Traffic from operator to route blocked |
| Node route issue | Router pod node cannot receive traffic |
| Incorrect endpointPublishingStrategy | Router published differently than DNS/LB expects |
| Proxy environment issue | Operator tries to reach route through wrong proxy |
| Custom domain misconfigured | Ingress domain changed but DNS/certs not aligned |

---

### 8.3 Diagnostic commands

Check ClusterOperator:

```bash
oc get co ingress -o yaml
oc describe co ingress
```

Check IngressController:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml
oc describe ingresscontroller/default -n openshift-ingress-operator
```

Check operator logs:

```bash
oc logs -n openshift-ingress-operator deploy/ingress-operator
```

Search for canary:

```bash
oc logs -n openshift-ingress-operator deploy/ingress-operator | grep -i canary
```

Check canary resources:

```bash
oc get all -n openshift-ingress-canary
oc get route canary -n openshift-ingress-canary -o yaml
oc describe route canary -n openshift-ingress-canary
```

Check canary pod and service:

```bash
oc get pods -n openshift-ingress-canary -o wide
oc get svc -n openshift-ingress-canary
oc get endpoints -n openshift-ingress-canary
```

Test canary route:

```bash
CANARY_HOST=$(oc get route canary -n openshift-ingress-canary -o jsonpath='{.spec.host}')
echo $CANARY_HOST

curl -v http://$CANARY_HOST
curl -vk https://$CANARY_HOST
dig +short $CANARY_HOST
```

Test with Host header directly against router service or LB IP:

```bash
curl -v -H "Host: $CANARY_HOST" http://<router-lb-ip>
curl -vk -H "Host: $CANARY_HOST" https://<router-lb-ip>
```

Test from inside the cluster:

```bash
oc run curl-test -n default --rm -it --restart=Never \
  --image=registry.redhat.io/ubi9/ubi -- /bin/bash
```

Inside:

```bash
curl -v http://$CANARY_HOST
getent hosts $CANARY_HOST
```

### 8.4 How to isolate the canary failure

#### Case A: DNS does not resolve

```bash
dig +short canary-openshift-ingress-canary.apps.<cluster-domain>
```

No output means DNS is broken.

Fix:

- Create or correct wildcard DNS:

```text
*.apps.<cluster-domain>  A/CNAME  <router-lb-or-vip>
```

For bare metal:

```text
*.apps.ocp4.example.com  A  <ingress-vip>
```

For cloud:

```text
*.apps.ocp4.example.com  CNAME  <cloud-lb-dns-name>
```

---

#### Case B: DNS resolves, but curl times out

```bash
curl -v http://canary-openshift-ingress-canary.apps.<cluster-domain>
```

Timeout means network path problem.

Check:

```bash
oc get svc router-default -n openshift-ingress
oc get endpoints router-default -n openshift-ingress
oc get pods -n openshift-ingress -o wide
```

Also check:

- Load balancer backend pool
- Firewall rules
- Security groups
- Node health checks
- VIP ownership
- Keepalived status on bare metal
- NodePort listening on workers
- HostNetwork ports 80/443 listening on router nodes

---

#### Case C: Curl reaches router but returns `503`

This means router got the request but backend service has no usable endpoint.

Check canary service endpoints:

```bash
oc get svc,endpoints,pods -n openshift-ingress-canary
oc describe svc canary -n openshift-ingress-canary
```

If endpoints are empty, check pod labels and readiness.

---

#### Case D: Curl reaches router but returns wrong cert or TLS failure

Check default certificate and route TLS behavior:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml
oc get secrets -n openshift-ingress
oc get route canary -n openshift-ingress-canary -o yaml
openssl s_client -connect <host>:443 -servername <host> -showcerts
```

---

### 8.5 Safe remediation

If canary route object is corrupt or stale, recreate it:

```bash
oc delete route canary -n openshift-ingress-canary
```

The operator should recreate it.

Then monitor:

```bash
watch 'oc get co ingress; oc get ingresscontroller/default -n openshift-ingress-operator'
```

Do not delete random objects repeatedly. If the canary keeps failing, fix the underlying DNS/LB/router/backend issue.

## 9. Issue: Router pods are Pending

### 9.1 Symptoms

```bash
oc get pods -n openshift-ingress
```

```text
router-default-xxxxx   0/1   Pending
```

Describe pod:

```bash
oc describe pod <router-pod> -n openshift-ingress
```

Common events:

```text
0/6 nodes are available: node(s) didn't match node selector
0/6 nodes are available: insufficient memory
0/6 nodes are available: node(s) had taint that the pod didn't tolerate
pod has unbound immediate PersistentVolumeClaims
```

Router pods normally should not need PVCs. If you see PVC-related events, inspect custom changes or unsupported modifications.

---

### 9.2 Root causes

| Root cause | Investigation |
|---|---|
| Bad `nodePlacement` | IngressController has node selector matching no nodes |
| Taints | Router pods do not tolerate target node taints |
| Insufficient CPU/memory | Worker nodes are resource constrained |
| MachineConfig/MCP issue | Worker nodes unavailable or degraded |
| Node NotReady | Router pod cannot be scheduled |
| Topology constraints | Replicas cannot spread as required |
| Custom tolerations wrong | Router pods blocked from expected nodes |

---

### 9.3 Diagnostics

Check IngressController placement:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml | yq '.spec.nodePlacement'
```

Without `yq`:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o jsonpath='{.spec.nodePlacement}{"\n"}'
```

Check nodes and labels:

```bash
oc get nodes --show-labels
oc get nodes -l node-role.kubernetes.io/worker=
```

Check taints:

```bash
oc describe node <node-name> | grep -i taint -A2
```

Check pod events:

```bash
oc describe pod <router-pod> -n openshift-ingress
```

Check router deployment generated by operator:

```bash
oc get deploy router-default -n openshift-ingress -o yaml
```

---

### 9.4 Fix examples

#### Fix wrong node selector

If IngressController has an overly strict selector:

```yaml
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
```

but no infra nodes exist:

```bash
oc get nodes -l node-role.kubernetes.io/infra=
```

Add label to intended nodes:

```bash
oc label node <node-name> node-role.kubernetes.io/infra=
```

or remove/update nodePlacement:

```bash
oc edit ingresscontroller/default -n openshift-ingress-operator
```

#### Add toleration if routers must run on tainted infra nodes

Example:

```yaml
spec:
  nodePlacement:
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
```

Patch carefully:

```bash
oc edit ingresscontroller/default -n openshift-ingress-operator
```

## 10. Issue: Router pods are CrashLoopBackOff

### 10.1 Symptoms

```bash
oc get pods -n openshift-ingress
```

```text
router-default-xxxxx   0/1   CrashLoopBackOff
```

Check logs:

```bash
oc logs <router-pod> -n openshift-ingress
oc logs <router-pod> -n openshift-ingress --previous
```

Check events:

```bash
oc describe pod <router-pod> -n openshift-ingress
```

---

### 10.2 Common root causes

| Root cause | Explanation |
|---|---|
| Invalid default certificate | Router cannot load malformed certificate/key |
| Secret missing | IngressController references missing cert secret |
| TLS key mismatch | `tls.crt` and `tls.key` do not match |
| Invalid custom error page ConfigMap | Router outage can occur if custom error page format is invalid |
| Invalid unsupported router customization | Manual changes to generated deployment |
| Broken image pull | Router image cannot be pulled |
| SCC/security context issue | Rare unless resources modified |
| Port conflict in hostNetwork mode | Another process uses 80/443 on target node |

---

### 10.3 Diagnose certificate-related crash

Check default certificate reference:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml | grep -A5 defaultCertificate
```

Example:

```yaml
spec:
  defaultCertificate:
    name: custom-certs-default
```

The secret must exist in `openshift-ingress`:

```bash
oc get secret custom-certs-default -n openshift-ingress
oc describe secret custom-certs-default -n openshift-ingress
```

Secret should normally be type `kubernetes.io/tls`:

```bash
oc get secret custom-certs-default -n openshift-ingress -o jsonpath='{.type}{"\n"}'
```

Validate cert and key:

```bash
oc extract secret/custom-certs-default -n openshift-ingress --to=/tmp/router-cert --confirm

openssl x509 -in /tmp/router-cert/tls.crt -noout -text
openssl rsa  -in /tmp/router-cert/tls.key -check -noout
```

Check cert/key match:

```bash
openssl x509 -noout -modulus -in /tmp/router-cert/tls.crt | openssl md5
openssl rsa  -noout -modulus -in /tmp/router-cert/tls.key | openssl md5
```

The hashes must match.

---

### 10.4 Fix bad default certificate

Create correct TLS secret:

```bash
oc create secret tls custom-certs-default \
  --cert=tls.crt \
  --key=tls.key \
  -n openshift-ingress
```

Patch IngressController:

```bash
oc patch ingresscontroller/default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"custom-certs-default"}}}'
```

To remove custom certificate and return to generated certificate:

```bash
oc patch ingresscontroller/default \
  -n openshift-ingress-operator \
  --type=json \
  -p='[{"op":"remove","path":"/spec/defaultCertificate"}]'
```

Monitor rollout:

```bash
oc rollout status deploy/router-default -n openshift-ingress
oc get co ingress
```

## 11. Issue: Route returns `503 Service Unavailable`

### 11.1 Meaning

A `503` from OpenShift router usually means:

```text
Router admitted the route, but there is no healthy backend endpoint.
```

Common reasons:

- Service selector does not match pod labels
- Pod is not Ready
- Wrong service port or targetPort
- Route points to wrong service
- Backend pod failing readiness probe
- NetworkPolicy blocks router-to-pod traffic
- EndpointSlice empty
- Re-encrypt TLS backend certificate mismatch
- Application listens on different port

---

### 11.2 Diagnostic flow

Assume route:

```bash
oc get route myapp -n myproj
```

Get route host:

```bash
HOST=$(oc get route myapp -n myproj -o jsonpath='{.spec.host}')
echo $HOST
curl -vk https://$HOST
```

Check route admission:

```bash
oc describe route myapp -n myproj
oc get route myapp -n myproj -o yaml
```

Check service:

```bash
oc get svc -n myproj
oc describe svc <service-name> -n myproj
```

Check endpoints:

```bash
oc get endpoints <service-name> -n myproj
oc get endpointslice -n myproj -l kubernetes.io/service-name=<service-name>
```

Check pods and labels:

```bash
oc get pods -n myproj --show-labels
oc get svc <service-name> -n myproj -o yaml
```

Compare:

```yaml
service.spec.selector
```

with:

```yaml
pod.metadata.labels
```

Check readiness:

```bash
oc get pods -n myproj
oc describe pod <pod-name> -n myproj
oc logs <pod-name> -n myproj
```

Check route target:

```bash
oc get route myapp -n myproj -o yaml
```

Important:

```yaml
spec:
  to:
    kind: Service
    name: myapp
  port:
    targetPort: 8080
```

Check service ports:

```bash
oc get svc myapp -n myproj -o yaml
```

---

### 11.3 Fix service selector mismatch

Example problem:

```yaml
Service selector:
  app: frontend
Pod labels:
  app: web
```

Fix service selector:

```bash
oc patch svc myapp -n myproj \
  --type=merge \
  -p '{"spec":{"selector":{"app":"web"}}}'
```

Verify endpoints:

```bash
oc get endpoints myapp -n myproj
curl -vk https://$HOST
```

---

### 11.4 Fix wrong targetPort

Example service:

```yaml
ports:
- port: 80
  targetPort: 8080
```

But app listens on `8081`.

Check inside pod:

```bash
oc rsh <pod-name> -n myproj
ss -lntp
```

Patch service:

```bash
oc patch svc myapp -n myproj \
  --type=merge \
  -p '{"spec":{"ports":[{"name":"http","port":80,"targetPort":8081}]}}'
```

## 12. Issue: Route returns `404 Not Found`

### 12.1 Meaning

A router `404` often means:

```text
The request reached an OpenShift router, but no admitted route matched the Host header.
```

Common reasons:

- DNS points to wrong cluster/router
- Host header does not match route host
- Route not admitted
- Route belongs to a different IngressController shard
- Wildcard route conflict
- Wrong route hostname
- Using `curl https://ip` without Host header
- Route deleted/recreated with different host
- Multiple clusters share DNS accidentally

---

### 12.2 Diagnostics

Check host:

```bash
oc get route -A | grep <hostname>
```

Check exact route:

```bash
oc get route <route-name> -n <namespace> -o yaml
```

Inspect status:

```yaml
status:
  ingress:
  - host: app.apps.ocp4.example.com
    routerName: default
    conditions:
    - type: Admitted
      status: "True"
```

If `status.ingress` is empty or `Admitted=False`, router did not admit the route.

Test with Host header:

```bash
curl -vk -H "Host: app.apps.ocp4.example.com" https://<router-lb-ip>
curl -v  -H "Host: app.apps.ocp4.example.com" http://<router-lb-ip>
```

If Host-header test works but normal URL fails, DNS is wrong.

---

### 12.3 Fix

- Correct DNS to point to correct router LB/VIP.
- Ensure route host is correct.
- Ensure route is admitted.
- Check routeSelector/namespaceSelector if using sharded ingress.
- Avoid duplicate hostnames unless route admission policy allows it and trust model is understood.

## 13. Issue: Route is not admitted

### 13.1 Symptoms

```bash
oc describe route myapp -n myproj
```

You may see:

```text
Requested Host: myapp.apps.ocp4.example.com
... no ingress status ...
```

or:

```yaml
status:
  ingress:
  - conditions:
    - type: Admitted
      status: "False"
      reason: HostAlreadyClaimed
```

---

### 13.2 Common root causes

| Cause | Explanation |
|---|---|
| Host already claimed | Another route already owns the same hostname |
| IngressController selector mismatch | Route labels or namespace labels do not match shard |
| Invalid wildcard policy | Wildcard routes are not allowed |
| Namespace ownership policy | Host claims across namespaces are disallowed by default |
| Wrong route host domain | Host does not belong to the intended ingress domain |
| Router not running | No router is available to admit routes |
| Route syntax issue | Invalid TLS or service reference |

---

### 13.3 Diagnostic commands

Find duplicate host:

```bash
oc get route -A --no-headers | awk '{print $1, $2, $3}' | grep <hostname>
```

Better:

```bash
oc get route -A -o custom-columns=NAMESPACE:.metadata.namespace,NAME:.metadata.name,HOST:.spec.host
```

Check route status:

```bash
oc get route myapp -n myproj -o yaml
```

Check IngressController selectors:

```bash
oc get ingresscontroller -n openshift-ingress-operator -o yaml
```

Look for:

```yaml
spec:
  routeSelector:
  namespaceSelector:
```

Check namespace labels:

```bash
oc get ns myproj --show-labels
```

Check route labels:

```bash
oc get route myapp -n myproj --show-labels
```

---

### 13.4 Fix duplicate host

Option 1: Use unique hostname:

```bash
oc patch route myapp -n myproj \
  --type=merge \
  -p '{"spec":{"host":"myapp-new.apps.ocp4.example.com"}}'
```

Option 2: Delete the stale route claiming the host:

```bash
oc delete route <old-route> -n <old-namespace>
```

Option 3: Allow inter-namespace host claims only if this is intentional and trusted:

```bash
oc patch ingresscontroller/default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"routeAdmission":{"namespaceOwnership":"InterNamespaceAllowed"}}}'
```

Use this carefully. Allowing host claims across namespaces can allow one namespace to take over a hostname used by another namespace.

## 16. Issue: Custom default certificate problem

### 16.1 Symptoms

- Browser says certificate invalid
- OAuth or console shows TLS warning
- Router pods redeploy after cert change
- Router pods crash after cert change
- Apps show old certificate
- Some routes show correct cert, others do not

---

### 16.2 Important rule

For IngressController default certificate:

- Secret must be in `openshift-ingress`
- Secret should be type `kubernetes.io/tls`
- Secret must contain `tls.crt` and `tls.key`
- Certificate should include SAN for wildcard ingress domain, for example:

```text
*.apps.ocp4.example.com
```

Modern clients validate SAN, not only Common Name.

---

### 16.3 Check active certificate

```bash
HOST=console-openshift-console.apps.<cluster-domain>
openssl s_client -connect ${HOST}:443 -servername ${HOST} -showcerts </dev/null
```

Inspect:

```bash
echo | openssl s_client -connect ${HOST}:443 -servername ${HOST} 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

---

### 16.4 Create custom default certificate

```bash
oc create secret tls custom-certs-default \
  --cert=wildcard.apps.crt \
  --key=wildcard.apps.key \
  -n openshift-ingress
```

Patch:

```bash
oc patch ingresscontroller/default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"defaultCertificate":{"name":"custom-certs-default"}}}'
```

Watch rollout:

```bash
oc rollout status deployment/router-default -n openshift-ingress
oc get pods -n openshift-ingress
```

---

### 16.5 Common certificate mistakes

| Mistake | Result |
|---|---|
| Secret created in wrong namespace | IngressController degraded or cert not applied |
| Secret key names wrong | Router cannot load cert |
| Certificate lacks wildcard SAN | Browser TLS validation fails |
| Key and cert mismatch | Router may fail to start |
| Intermediate CA missing | Browser/client trust failure |
| Expired certificate | TLS errors |
| Cert covers `*.example.com` but route is `*.apps.example.com` | TLS mismatch |
| Using route cert when default cert expected | Only that route works, others still use default |

## 17. Issue: Edge, re-encrypt, and passthrough route TLS problems

### 17.1 TLS termination types

| Type | TLS terminates at | Backend traffic |
|---|---|---|
| Edge | Router | HTTP to pod/service |
| Re-encrypt | Router and backend | HTTPS from router to pod/service |
| Passthrough | Application pod | Router passes TLS without termination |

---

### 17.2 Edge route troubleshooting

Create example:

```bash
oc create route edge myapp \
  --service=myapp \
  --hostname=myapp.apps.ocp4.example.com \
  --cert=tls.crt \
  --key=tls.key \
  -n myproj
```

Common problems:

- Cert does not match hostname
- Key mismatch
- Route points to wrong service
- Backend service expects HTTPS but edge sends HTTP
- App redirects incorrectly

Check:

```bash
oc get route myapp -n myproj -o yaml
curl -vk https://myapp.apps.ocp4.example.com
```

---

### 17.3 Re-encrypt route troubleshooting

Re-encrypt means:

```text
Client --HTTPS--> Router --HTTPS--> Backend Pod
```

Common problems:

- Missing `destinationCACertificate`
- Backend cert CN/SAN does not match service name expected by router
- Backend pod is not listening on HTTPS
- Service targetPort wrong
- App presents self-signed cert not trusted by route destination CA

Check route:

```bash
oc get route myapp -n myproj -o yaml
```

Look for:

```yaml
spec:
  tls:
    termination: reencrypt
    destinationCACertificate: |
      -----BEGIN CERTIFICATE-----
```

Test backend directly from cluster:

```bash
oc run tls-test -n myproj --rm -it --restart=Never \
  --image=registry.redhat.io/ubi9/ubi -- /bin/bash
```

Inside:

```bash
curl -vk https://myapp.<myproj>.svc.cluster.local:<port>
openssl s_client -connect myapp.<myproj>.svc.cluster.local:<port> -showcerts
```

---

### 17.4 Passthrough route troubleshooting

Passthrough means:

```text
Client --HTTPS--> Router --TCP/SNI pass-through--> Pod
```

Router does not terminate TLS.

Common problems:

- Client uses IP instead of hostname, so SNI is missing
- Backend does not serve TLS
- Backend cert mismatch
- Route target service port wrong
- App requires HTTP but route is passthrough
- Multiple apps depend on same SNI host incorrectly

Test with SNI:

```bash
openssl s_client -connect myapp.apps.ocp4.example.com:443 \
  -servername myapp.apps.ocp4.example.com
```

Curl:

```bash
curl -vk https://myapp.apps.ocp4.example.com
```

Do not test passthrough only by IP unless you also provide SNI through a suitable tool.

## 18. Issue: Sharded IngressController problems

### 18.1 What is sharding?

Ingress sharding means using multiple IngressControllers for different traffic groups.

Example:

- `default` router handles general apps
- `internal` router handles internal apps
- `partner` router handles partner apps
- `pci` router handles regulated apps

Selectors decide which routes each router admits:

```yaml
spec:
  namespaceSelector:
    matchLabels:
      router: internal
  routeSelector:
    matchLabels:
      type: internal
```

---

### 18.2 Symptoms

- Route is created but not reachable
- Route has no `status.ingress`
- Route admitted by unexpected router
- DNS points to default router but route belongs to custom router
- App works only when using another domain
- `404` because request reaches wrong shard

---

### 18.3 Diagnostics

List IngressControllers:

```bash
oc get ingresscontroller -n openshift-ingress-operator
```

Show selectors:

```bash
oc get ingresscontroller -n openshift-ingress-operator -o yaml
```

Check route status:

```bash
oc get route myapp -n myproj -o yaml
```

Look for:

```yaml
status:
  ingress:
  - routerName: internal
    host: myapp.apps-internal.ocp4.example.com
```

Check namespace labels:

```bash
oc get ns myproj --show-labels
```

Check route labels:

```bash
oc get route myapp -n myproj --show-labels
```

---

### 18.4 Fix

If route should be admitted by custom router, label namespace or route correctly:

```bash
oc label namespace myproj router=internal
oc label route myapp -n myproj type=internal
```

If DNS is wrong, point route domain to correct router LB/VIP:

```text
*.apps-internal.ocp4.example.com -> internal router LB/VIP
```

If route should be on default router, remove labels or adjust selectors.

## 19. Issue: `endpointPublishingStrategy` mismatch

### 19.1 What it controls

`endpointPublishingStrategy` defines how router endpoints are exposed outside the cluster.

Common types:

| Type | Typical usage |
|---|---|
| `LoadBalancerService` | Cloud platforms or environments with service load balancer |
| `HostNetwork` | Router binds directly to node network ports |
| `NodePortService` | External LB forwards to node ports |
| `Private` | Internal-only exposure |

Check:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator \
  -o jsonpath='{.status.endpointPublishingStrategy}{"\n"}'
```

---

### 19.2 Symptoms of mismatch

- DNS points to a VIP but router is exposed as LoadBalancer
- LB forwards to node ports but router uses HostNetwork
- Cloud LB is internal but external DNS points to it
- External clients cannot reach internal-only router
- Canary route fails because operator cannot reach published endpoint
- Health checks fail after strategy changes

---

### 19.3 Diagnostics

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml
oc get svc router-default -n openshift-ingress -o yaml
oc get pods -n openshift-ingress -o wide
oc get infrastructure cluster -o yaml
```

Check whether router service type matches your design:

```bash
oc get svc router-default -n openshift-ingress
```

Examples:

```text
LoadBalancerService -> Service type LoadBalancer
NodePortService     -> Service type NodePort
HostNetwork         -> Router pods bind host ports 80/443
Private             -> Internal access only
```

---

### 19.4 Fix

Do not change endpoint publishing strategy casually on production clusters. It can affect all application ingress.

If a change is required, plan:

1. Current route DNS and LB design
2. Target route DNS and LB design
3. External firewall/security group changes
4. Router rollout impact
5. Canary route validation
6. Console/OAuth route validation
7. Rollback plan

Edit:

```bash
oc edit ingresscontroller/default -n openshift-ingress-operator
```

## 20. Issue: PROXY protocol mismatch

### 20.1 Symptoms

- Routes fail immediately after enabling PROXY protocol
- Router logs show malformed request
- Client sees connection reset
- Source IP preservation not working
- LB health checks fail

---

### 20.2 Rule

OpenShift router and external load balancer must agree:

```text
Both sides TCP only
or
Both sides PROXY protocol
```

If LB sends PROXY headers but router expects plain TCP, traffic breaks.

If router expects PROXY headers but LB sends plain TCP, traffic breaks.

---

### 20.3 Diagnostics

Check IngressController:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml
```

Look under:

```yaml
spec:
  endpointPublishingStrategy:
    hostNetwork:
      protocol: PROXY
```

or:

```yaml
nodePort:
  protocol: PROXY
```

Check LB configuration:

- Listener protocol
- Backend protocol
- Proxy protocol v1/v2 setting
- Health check protocol

Check router logs:

```bash
oc logs -n openshift-ingress deploy/router-default
```

---

### 20.4 Fix

Align both sides.

If using plain TCP:

```yaml
protocol: TCP
```

If using PROXY:

```yaml
protocol: PROXY
```

Then ensure external LB is configured accordingly.

## 26. NetworkPolicy and router traffic

### 26.1 Problem

In some restricted namespaces, NetworkPolicy can block traffic from router pods to application pods.

Symptoms:

- Route admitted
- Service endpoints exist
- Pod is ready
- Direct service access from same namespace works
- Route returns `503` or times out
- Router cannot connect to backend

### 26.2 Check NetworkPolicy

```bash

oc describe networkpolicy -n myproj
```

Check router pod namespace and labels:

```bash

oc get pods -n openshift-ingress --show-labels
```

---

### 26.3 Allow ingress from router namespace

Example policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
  namespace: myproj
spec:
  podSelector:
    matchLabels:
      app: myapp
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-ingress
    ports:
    - protocol: TCP
      port: 8080
```

Apply:

```bash
oc apply -f allow-from-openshift-ingress.yaml
```

Note: Check actual namespace labels in your cluster before relying on this exact selector.

## 30. Production incident decision tree

### 30.1 All routes down

```text
All routes down?
  |
  +-- Are router pods running?
  |      |
  |      +-- No -> troubleshoot scheduler, image pull, cert, crashloop
  |      +-- Yes
  |
  +-- Does wildcard DNS resolve?
  |      |
  |      +-- No -> fix DNS
  |      +-- Yes
  |
  +-- Does LB/VIP forward to router?
  |      |
  |      +-- No -> fix LB/firewall/VIP/security group
  |      +-- Yes
  |
  +-- Does canary route work?
         |
         +-- No -> inspect canary svc/pod/route/operator logs
         +-- Yes -> check app route admission/backend
```

---

### 30.2 One app route down

```text
Single app route down?
  |
  +-- Route admitted?
  |      |
  |      +-- No -> host conflict/shard/selector/route policy
  |      +-- Yes
  |
  +-- Status 404?
  |      |
  |      +-- Yes -> wrong host/DNS/wrong router shard
  |
  +-- Status 503?
  |      |
  |      +-- Yes -> service endpoints/readiness/targetPort/backend TLS
  |
  +-- TLS error?
         |
         +-- Yes -> route cert/default cert/SNI/reencrypt/destination CA
```

## 33. Preventive best practices

### 33.1 DNS

- Always maintain wildcard DNS for `*.apps.<cluster-domain>`.
- Keep TTL reasonable.
- Avoid pointing wildcard apps DNS to old clusters.
- Validate DNS after disaster recovery or LB replacement.
- Monitor DNS resolution from internal and external networks.

### 33.2 Load balancer

- Use health checks compatible with router exposure mode.
- Monitor backend node health.
- Keep security groups/firewalls aligned with 80/443.
- Document whether router uses `LoadBalancerService`, `NodePortService`, `HostNetwork`, or `Private`.
- Do not mix PROXY protocol and plain TCP accidentally.

### 33.3 Router replicas

- Use at least 2 replicas for production.
- Use proper node placement for infra nodes.
- Avoid scheduling all router pods on the same failure domain.
- Monitor available replicas.

Scale example:

```bash
oc patch ingresscontroller/default \
  -n openshift-ingress-operator \
  --type=merge \
  -p '{"spec":{"replicas":3}}'
```

### 33.4 Certificates

- Track expiry of wildcard ingress certs.
- Use SAN-based wildcard certificates.
- Store cert/key securely.
- Validate key/cert pair before applying.
- Apply during a maintenance window if router rollout impact matters.
- Test console, OAuth, canary, and sample app after change.

### 33.5 Sharding

- Use clear route and namespace labels.
- Document domain-to-router mapping.
- Keep DNS records aligned with each shard.
- Avoid overlapping domains unless intentional.
- Test route admission after selector changes.

### 33.6 Change management

Before changing IngressController:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml > before-ingresscontroller.yaml
oc get co ingress
oc get pods -n openshift-ingress
```

After change:

```bash
oc rollout status deploy/router-default -n openshift-ingress
oc get co ingress
curl -vk https://console-openshift-console.apps.<cluster-domain>
curl -v  http://canary-openshift-ingress-canary.apps.<cluster-domain>
```

## 34. Interview and real-world explanation

If asked in an interview:

> How do you troubleshoot Ingress Operator degraded in OpenShift?

Answer like this:

```text
I start with oc get co ingress and oc describe co ingress to identify whether the issue is with availability, progression, degradation, or canary checks. Then I inspect the IngressController CR in openshift-ingress-operator, because router configuration is operator-managed. I check the ingress-operator logs, router pods in openshift-ingress, router service type and endpoints, and the canary route in openshift-ingress-canary.

If the error is CanaryChecksRepetitiveFailures, I verify wildcard DNS, canary route DNS resolution, load balancer forwarding, firewall rules, router pod readiness, and canary service endpoints. I use curl with the Host header directly against the router LB or node to separate DNS/LB issues from router/route/backend issues.

For an application route, I check whether the route is admitted. If it returns 404, I suspect wrong Host header, wrong router shard, or DNS pointing to the wrong router. If it returns 503, I check service selectors, endpoints, pod readiness, targetPort, NetworkPolicy, and TLS termination. I avoid editing router deployments directly and make persistent changes through the IngressController CR.
```

## 36. Common mistakes by administrators

| Mistake | Why it is dangerous |
|---|---|
| Editing `router-default` deployment manually | Operator may revert changes |
| Ignoring `CanaryChecksRepetitiveFailures` because apps still work | Health checks and upgrades can be impacted |
| Creating default cert secret in wrong namespace | IngressController cannot use it |
| Changing apps domain without DNS planning | All new route hostnames can break |
| Assuming `503` means router is down | Usually backend service/endpoints problem |
| Assuming `404` means app is down | Usually host/route admission/router shard problem |
| Using IP-based curl for passthrough route | SNI is missing |
| Enabling PROXY protocol only on one side | Breaks traffic |
| Allowing inter-namespace host claims casually | Can create hostname takeover risk |
| Forgetting NetworkPolicy impact | Router-to-pod traffic may be blocked |

## 37. Fast root-cause map

| Symptom | Most likely root cause |
|---|---|
| `co ingress Degraded=True`, canary failure | DNS/LB/router/canary path |
| All routes timeout | LB/firewall/VIP/DNS |
| All routes 503 | Router can reach no backends or widespread service issue |
| One route 503 | Service selector/endpoints/readiness/targetPort |
| One route 404 | Host mismatch, route not admitted, wrong router |
| Browser cert warning on all apps | Default wildcard cert issue |
| Browser cert warning on one app | Route-specific cert issue |
| Router pod Pending | nodePlacement, taints, resources, nodes |
| Router pod CrashLoop | certificate, config, image, custom error pages |
| Route not admitted | duplicate host, shard selector, namespace ownership |
| Works with Host header to LB IP, fails by name | DNS problem |
| Works inside cluster, fails outside | External DNS/LB/firewall |
| Fails inside and outside | Router/route/service/backend |

## 39. Final senior-admin summary

Ingress Operator troubleshooting is about isolating the traffic path.

For a 10-year experienced admin, the most important skill is not memorizing commands. It is knowing exactly where the failure sits:

```text
Client -> DNS -> LB/VIP -> Router Service -> Router Pod -> Route Admission -> Service -> Endpoint -> Pod -> App
```

Use this rule:

```text
404 = router reached, no matching admitted route
503 = route matched, backend unavailable
Timeout = DNS/LB/firewall/network path
TLS error = cert/SNI/termination/destination CA
Canary failure = operator cannot validate route path
```

Always troubleshoot from both directions:

```text
Outside client -> route
Inside pod -> route
Inside pod -> service
Router/LB IP + Host header -> route
```

And always remember:

```text
OpenShift 4 router configuration is operator-managed.
Permanent fixes belong in the IngressController CR, not manual router deployment edits.
```
