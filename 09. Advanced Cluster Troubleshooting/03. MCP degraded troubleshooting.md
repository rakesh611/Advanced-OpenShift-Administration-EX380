## 1. What MCP degraded means

In OpenShift, **MCP degraded** means that the **Machine Config Operator (MCO)** cannot successfully apply, verify, or reconcile the expected node-level configuration for one or more nodes in a **MachineConfigPool**.

A MachineConfigPool normally represents a group of nodes such as:

- `master`
- `worker`
- `infra`
- `storage`
- custom pools such as `gpu`, `router`, `logging`, or `db-worker`

When the MCP shows `DEGRADED=True`, at least one node in that pool is failing machine configuration reconciliation.

Typical command:

```bash
oc get mcp
```

Example:

```text
NAME      CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT   AGE
master    rendered-master-6f5c9b4a8c...                     True      False      False      3              3                   3                     0                      60d
worker    rendered-worker-9d7e2c1b6a...                     False     True       True       6              5                   5                     1                      60d
```

Interpretation:

- The `worker` pool is degraded.
- One worker node is reporting degraded status.
- The pool is also updating, meaning a desired config rollout is incomplete.
- Cluster upgrades can be blocked until this is resolved.

## 2. Mental model: MCO, MCP, MC, rendered MC, and MCD

Before troubleshooting, understand the moving parts.

### 2.1 Machine Config Operator components

The MCO manages operating system and node-level configuration. It handles things between the Linux kernel and kubelet, including:

- RHCOS updates
- `rpm-ostree` pivots
- kubelet configuration
- CRI-O configuration
- systemd units
- files under `/etc` and `/var`
- kernel arguments
- registry configuration
- SSH keys
- node reboot orchestration

Core components:

| Component | Namespace | Purpose |
|---|---|---|
| `machine-config-operator` | `openshift-machine-config-operator` | Top-level operator process |
| `machine-config-controller` | `openshift-machine-config-operator` | Renders configs and controls pool rollout |
| `machine-config-daemon` | `openshift-machine-config-operator` | DaemonSet pod on each node that applies and validates config |
| `machine-config-server` | `openshift-machine-config-operator` | Serves Ignition configs to nodes, especially during bootstrap/join |

Check them:

```bash
oc get pods -n openshift-machine-config-operator -o wide
oc get ds -n openshift-machine-config-operator
oc get deploy -n openshift-machine-config-operator
```

### 2.2 MachineConfig

A `MachineConfig` is declarative node OS configuration.

Example types of changes:

- Add `/etc/chrony.conf`
- Add `/etc/containers/registries.conf`
- Add a systemd drop-in
- Add kernel arguments
- Configure kubelet or CRI-O indirectly through generated MachineConfigs

List MachineConfigs:

```bash
oc get mc
```

### 2.3 Rendered MachineConfig

The MCO combines all MachineConfigs selected by a pool and creates a final generated config called a **rendered MachineConfig**.

Example:

```text
rendered-worker-9d7e2c1b6a1d8b2c...
rendered-master-6f5c9b4a8c9f2e1d...
```

The MCP points to the rendered config:

```bash
oc get mcp worker -o jsonpath='{.status.configuration.name}{"\n"}'
```

Each node also has annotations showing current and desired rendered config:

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 2.4 Machine Config Daemon

`machine-config-daemon` runs on each node. It is the component that actually:

1. Detects desired config change.
2. Validates current on-disk state.
3. Cordons and drains the node when needed.
4. Applies the new config.
5. Reboots the node when needed.
6. Uncordons the node.
7. Marks the node as `Done`, `Working`, or `Degraded`.

The MCP becomes degraded when one or more nodes report degraded status or cannot reconcile to desired state.

## 3. Why MCP degradation is serious

MCP degradation is not a small cosmetic issue. In production it can cause:

- Cluster upgrade blocked or stuck.
- Node OS update blocked.
- Kubelet / CRI-O configuration rollout blocked.
- Registry, proxy, certificate, chrony, SSH, or kernel config rollout blocked.
- Control plane updates stuck when `master` MCP is degraded.
- Application disruption if nodes are cordoned, draining, or rebooting repeatedly.
- Inconsistent node behavior across the same pool.

For example, during an upgrade, Cluster Version Operator might show:

```bash
oc get clusterversion
oc describe clusterversion version
```

Possible symptom:

```text
Unable to apply 4.x.y: the cluster operator machine-config is degraded
```

Always fix MCP degradation before continuing upgrade or major platform changes.

## 4. MCP status fields explained

Command:

```bash
oc get mcp
```

Important columns:

| Column | Meaning | Senior admin interpretation |
|---|---|---|
| `CONFIG` | Current rendered config for the pool | Desired end-state rendered MC |
| `UPDATED` | All nodes in pool are on current rendered config | `True` means rollout complete |
| `UPDATING` | At least one node is moving to desired config | Normal during rollout, bad if stuck too long |
| `DEGRADED` | One or more nodes failed reconciliation | Needs investigation |
| `MACHINECOUNT` | Total nodes selected by this MCP | Verify custom selector correctness |
| `READYMACHINECOUNT` | Ready nodes in the pool | Low value means node readiness problem |
| `UPDATEDMACHINECOUNT` | Nodes already on desired config | Compare with total count |
| `DEGRADEDMACHINECOUNT` | Nodes reporting degraded/unreconcilable | Start here |

Detailed conditions:

```bash
oc get mcp worker -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

Describe gives the human-readable reason:

```bash
oc describe mcp worker
```

Look for:

```text
Type:     NodeDegraded
Status:   True
Reason:   1 nodes are reporting degraded status on sync
Message:  Node worker-1 is reporting: "content mismatch for file /etc/..."
```

## 5. First 10-minute triage

When you are called for MCP degraded issue, do not immediately reboot nodes. First collect facts.

### Step 1: Check cluster operators

```bash
oc get co
oc describe co machine-config
```

Focus on:

- `Available`
- `Progressing`
- `Degraded`
- `Upgradeable`
- `Message`
- `Reason`

### Step 2: Check MCP summary

```bash
oc get mcp
```

### Step 3: Check nodes

```bash
oc get nodes
```

Look for:

- `NotReady`
- `SchedulingDisabled`
- unexpected role labels
- recently rebooted nodes
- nodes missing from MCP count

### Step 4: Check MCO pods

```bash
oc get pods -n openshift-machine-config-operator -o wide
```

Important symptoms:

- `machine-config-daemon` pod missing on the degraded node
- daemon pod in `CrashLoopBackOff`
- daemon pod running but logs show validation failure
- controller pod errors
- machine-config-server errors during node join/bootstrap scenarios

### Step 5: Find degraded node and reason

```bash
oc describe mcp <pool-name>
```

Then:

```bash
oc describe node <node-name>
```

### Step 6: Read MCD logs for the affected node

```bash
NODE=<node-name>
MCD_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide --no-headers | awk -v n="$NODE" '$7==n {print $1}')
echo "$MCD_POD"
oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon --since=4h
```

Filter useful lines:

```bash
oc logs -n openshift-machine-config-operator "$MCD_POD" -c machine-config-daemon --since=4h \
  | egrep -i 'degraded|error|fail|drift|mismatch|unexpected|drain|pivot|rpm|ostree|reboot|desired|current|validation'
```

## 6. Find the exact degraded node

### 6.1 From MCP describe

```bash
oc describe mcp worker
```

Common output:

```text
Message: Node worker-2.example.com is reporting: "unexpected on-disk state validating against rendered-worker-xxxxx: content mismatch for file /etc/chrony.conf"
Reason:  1 nodes are reporting degraded status on sync
Type:    NodeDegraded
```

### 6.2 From node annotations

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason
```

Example:

```text
NAME                 STATE      CURRENT                    DESIRED                    REASON
worker-1.example.com Done       rendered-worker-a1         rendered-worker-a1         <none>
worker-2.example.com Degraded   rendered-worker-a1         rendered-worker-b2         content mismatch for file /etc/chrony.conf
worker-3.example.com Done       rendered-worker-b2         rendered-worker-b2         <none>
```

### 6.3 From events

```bash
oc get events -A --sort-by=.lastTimestamp | egrep -i 'machine|config|degraded|drain|reboot|failed|mcd|mco'
```

For a specific node:

```bash
oc get events -A --field-selector involvedObject.name=<node-name> --sort-by=.lastTimestamp
```

### 6.4 From MCD pod placement

```bash
oc get pods -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide
```

Find the pod running on the affected node, then check logs.

## 7. Read the real error from MCP, node annotations, events, and MCD logs

Do not troubleshoot MCP degraded only from `oc get mcp`. That output tells you **what** is degraded, not **why**.

Use this order:

```bash
POOL=worker
oc describe mcp $POOL
```

```bash
NODE=<degraded-node>
oc describe node $NODE
```

```bash
oc get node $NODE -o yaml | sed -n '/machineconfiguration.openshift.io/p'
```

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide --no-headers | awk -v n="$NODE" '$7==n {print $1}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --since=6h
```

Also check controller logs if the issue is rollout/drain/rendering related:

```bash
MCC_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-controller -o jsonpath='{.items[0].metadata.name}')
oc logs -n openshift-machine-config-operator $MCC_POD -c machine-config-controller --since=6h
```

Common error fragments and meaning:

| Error fragment | Likely cause |
|---|---|
| `content mismatch for file` | Configuration drift or manual file edit |
| `mode mismatch for file` | File permission drift |
| `missing file` | Managed file deleted manually |
| `unexpected on-disk state` | Node does not match current rendered MC |
| `failed to drain node` | PDB, stuck pod, API issue, node pressure, finalizer |
| `failed to reboot` | OS/systemd/reboot issue, MCD cannot complete reboot |
| `error running rpm-ostree` | OS pivot/update failure |
| `failed to pull` | Registry, mirror, proxy, pull-secret, disconnected config issue |
| `kubelet health failure` | Bad kubelet config or kubelet service problem |
| `rendered-... not found` | Rendered MC deleted or inconsistent references |
| `ImageBuildDegraded` | On-cluster layered image build failure |
| `PinnedImageSet` / `preload` failure | Image pinning/prefetch/storage/auth problem |

## 8. Troubleshooting decision tree

Use this decision tree in production.

```text
MCP DEGRADED
│
├── Is ClusterOperator machine-config degraded?
│   ├── yes: read oc describe co machine-config
│   └── no: MCP may be temporarily rolling or custom pool issue
│
├── Which MCP is degraded?
│   ├── master: higher risk; protect etcd quorum
│   ├── worker: workload disruption risk
│   └── custom: check node labels and selector
│
├── Which node is degraded?
│   ├── node Ready? yes
│   │   ├── MCD logs show content/mode mismatch → config drift
│   │   ├── MCD logs show drain failure → app/PDB/stuck pod
│   │   ├── MCD logs show rpm-ostree/pivot → OS image/update issue
│   │   └── MCD logs show kubelet/crio → generated config issue
│   │
│   └── node Ready? no
│       ├── check kubelet/crio/journal
│       ├── check disk/network/certs/time
│       └── restore node first, then MCP will reconcile
│
├── Is currentConfig == desiredConfig?
│   ├── yes + degraded: usually drift or post-apply validation
│   └── no + degraded: rollout failed while moving to desired config
│
├── Was a recent MC/KubeletConfig/ContainerRuntimeConfig applied?
│   ├── yes: inspect or rollback/fix that object
│   └── no: check manual node changes, OS image, disk, MCO health
│
└── After fix:
    ├── wait for MCP updated
    ├── verify node annotations
    ├── verify CO machine-config
    └── verify clusterversion/upgrade state
```

## 9. Case 1: Configuration drift / on-disk validation failure

### 9.1 What it means

Configuration drift means the node's real on-disk file, unit, permission, ownership, or OS image does not match the currently applied rendered MachineConfig.

Example causes:

- Someone manually edited `/etc/chrony.conf` on a node.
- Someone changed file mode from `0644` to `0600`.
- A script modified a file managed by MCO.
- A security tool changed permissions.
- A file managed by MachineConfig was deleted.
- An out-of-band SSH change was made directly on RHCOS.

Example MCP message:

```text
Node worker-2 is reporting: "content mismatch for file /etc/chrony.conf"
```

### 9.2 Confirm drift

```bash
oc describe mcp worker
```

```bash
NODE=<node-name>
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

MCD logs:

```bash
MCD_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide --no-headers | awk -v n="$NODE" '$7==n {print $1}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --since=4h | egrep -i 'mismatch|drift|unexpected|validation|degraded'
```

### 9.3 Get the current rendered config for the node

```bash
CURRENT=$(oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}')
DESIRED=$(oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}')
echo "CURRENT=$CURRENT"
echo "DESIRED=$DESIRED"
```

If drift is against current config, inspect the current rendered MC:

```bash
oc get mc $CURRENT -o yaml > /tmp/${CURRENT}.yaml
```

### 9.4 Find the expected file definition

Example for `/etc/chrony.conf`:

```bash
MC=$CURRENT
FILE=/etc/chrony.conf
oc get mc $MC -o json | jq -r --arg f "$FILE" '.spec.config.storage.files[]? | select(.path==$f)'
```

Get file metadata:

```bash
oc get mc $MC -o json | jq -r --arg f "$FILE" '
  .spec.config.storage.files[]? | select(.path==$f) |
  {path, mode, user: .user.name, group: .group.name, source: .contents.source}'
```

### 9.5 Check actual file on node

```bash
oc debug node/$NODE
chroot /host
ls -l /etc/chrony.conf
stat /etc/chrony.conf
sha256sum /etc/chrony.conf
exit
exit
```

Or one-shot:

```bash
oc debug node/$NODE -- chroot /host stat /etc/chrony.conf
oc debug node/$NODE -- chroot /host sha256sum /etc/chrony.conf
```

### 9.6 Fix strategy

Preferred order:

1. **Undo the manual change** so the file matches MachineConfig.
2. **Fix the MachineConfig source** if the desired state is wrong.
3. **Avoid repeated manual node edits**; manage the file through MachineConfig.
4. Use the MCD force file only when you understand the impact.

### 9.7 Restore file manually from desired source

If the MachineConfig contains a `data:` URL, decode it carefully.

Example helper:

```bash
MC=$CURRENT
FILE=/etc/chrony.conf
oc get mc $MC -o json | jq -r --arg f "$FILE" '.spec.config.storage.files[]? | select(.path==$f) | .contents.source'
```

If the output is base64 data, decode it on your workstation, compare, then apply on the node.

On node:

```bash
oc debug node/$NODE
chroot /host
cp -a /etc/chrony.conf /etc/chrony.conf.backup.$(date +%F-%H%M%S)
vi /etc/chrony.conf
chmod 0644 /etc/chrony.conf
chown root:root /etc/chrony.conf
exit
exit
```

Then check MCD logs and MCP:

```bash
oc get mcp worker -w
```

### 9.8 When to use force file

If drift is understood and you need MCD to reapply the current MachineConfig:

```bash
oc debug node/$NODE
chroot /host
touch /run/machine-config-daemon-force
exit
exit
```

Important:

- This bypasses normal preflight drift check.
- This causes the node to reboot.
- Use it only after you identify the drift and accept the reboot.
- On control plane nodes, do one node at a time and maintain etcd quorum.

## 10. Case 2: Drain failure

### 10.1 What it means

MCO normally applies disruptive config changes through this flow:

```text
cordon → drain → apply config → reboot → uncordon
```

If drain fails, the node cannot be rebooted safely by MCO, so the MCP may become stuck updating/degraded.

Common causes:

- PodDisruptionBudget blocks eviction.
- Single replica application has strict PDB.
- Pod stuck terminating.
- Pod has finalizer issue.
- Node has workload that cannot be evicted.
- API server or kubelet issue during eviction.
- Local storage / emptyDir workload risk.
- Static pods on control plane are not drained like normal pods.

### 10.2 Confirm drain failure

Controller logs:

```bash
MCC_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-controller -o jsonpath='{.items[0].metadata.name}')
oc logs -n openshift-machine-config-operator $MCC_POD -c machine-config-controller --since=6h | egrep -i 'drain|evict|pdb|failed|error|cannot'
```

MCD logs:

```bash
NODE=<node-name>
MCD_POD=$(oc get pod -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -o wide --no-headers | awk -v n="$NODE" '$7==n {print $1}')
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --since=6h | egrep -i 'drain|evict|pdb|failed|error|cannot'
```

Check pods on node:

```bash
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
```

Check PDBs:

```bash
oc get pdb -A
oc get pdb -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,MIN:.spec.minAvailable,MAX:.spec.maxUnavailable,ALLOWED:.status.disruptionsAllowed,CURRENT:.status.currentHealthy,DESIRED:.status.desiredHealthy
```

### 10.3 Run drain dry-run carefully

Do not fight MCO with a real manual drain unless you know why.

Use dry-run first:

```bash
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

This can reveal eviction blockers.

### 10.4 Fix drain blockers

Common fixes:

#### Fix PDB issue

If `disruptionsAllowed=0`, do not blindly delete the PDB. Safer options:

- Scale application replicas up.
- Fix unhealthy pods so PDB allows disruption.
- Temporarily relax PDB with app owner approval.
- Move workload manually if safe.

Commands:

```bash
oc -n <ns> get deploy,statefulset,pods,pdb
oc -n <ns> scale deploy/<app> --replicas=<higher-number>
oc -n <ns> describe pdb <pdb-name>
```

#### Fix stuck terminating pod

```bash
oc -n <ns> describe pod <pod>
oc -n <ns> get pod <pod> -o yaml | less
```

Look for:

- finalizers
- volume detach issues
- CSI problems
- kubelet communication issues

Use force delete only after confirming workload impact:

```bash
oc -n <ns> delete pod <pod> --grace-period=0 --force
```

#### Fix local storage workload

For workloads with local data:

- Confirm data persistence strategy.
- Confirm if pod can be evicted.
- Use app-specific failover procedure.

### 10.5 Verify drain recovery

After fixing blocker, the MCO should retry.

```bash
oc get mcp worker -w
oc get nodes
oc logs -n openshift-machine-config-operator $MCC_POD -c machine-config-controller --since=30m | egrep -i 'drain|evict|reboot|uncordon|complete'
```

## 11. Case 3: Node NotReady or unreachable during MCP rollout

### 11.1 What it means

If a node is `NotReady`, MCO/MCD cannot reliably complete reconciliation. The MCP might show:

- `UPDATING=True`
- `DEGRADED=True`
- `READYMACHINECOUNT` lower than `MACHINECOUNT`
- `UNAVAILABLEMACHINECOUNT` non-zero in detailed status

Check:

```bash
oc get nodes
oc describe node $NODE
```

### 11.2 Troubleshoot node health first

Use debug if API still reaches node enough to create debug pod:

```bash
oc debug node/$NODE
chroot /host
systemctl status kubelet --no-pager
systemctl status crio --no-pager
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
journalctl -u machine-config-daemon-firstboot -b --no-pager | tail -200
journalctl -u rpm-ostreed -b --no-pager | tail -200
df -h
free -m
exit
exit
```

If `oc debug` cannot run, use SSH or console access:

```bash
ssh core@$NODE
sudo -i
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
systemctl status kubelet crio --no-pager
```

### 11.3 Common Node NotReady causes during MCP update

| Symptom | Possible cause |
|---|---|
| kubelet fails after new config | Bad `KubeletConfig` |
| CRI-O fails | Bad `ContainerRuntimeConfig`, registry config, storage issue |
| node reboot loop | kernel args, OS pivot, systemd unit issue |
| node cannot pull MCD image | registry/mirror/proxy/pull-secret issue |
| node time wrong | cert validation / TLS issue |
| disk full | kubelet/CRI-O/rpm-ostree failure |
| network broken | bad NetworkManager MachineConfig |

### 11.4 Recovery approach

1. Restore kubelet/CRI-O enough for the node to become `Ready`.
2. Fix or remove the bad config object.
3. Let MCO render a new config.
4. If needed, use force file after the node is healthy enough.
5. Avoid rebooting all affected nodes at once.

## 12. Case 4: Bad MachineConfig content

### 12.1 What it means

A custom MachineConfig can make nodes degraded if it writes invalid or dangerous node configuration.

Examples:

- Invalid systemd unit.
- Bad kubelet drop-in.
- Wrong file path.
- Wrong file mode.
- Invalid NetworkManager keyfile.
- Bad registries.conf.
- Bad chrony config.
- Kernel argument that prevents boot.
- Broken proxy or CA trust configuration.

### 12.2 Identify recent MachineConfigs

```bash
oc get mc --sort-by=.metadata.creationTimestamp
```

Look at custom configs near the time degradation began:

```bash
oc get mc
oc describe mc <mc-name>
oc get mc <mc-name> -o yaml
```

### 12.3 See which MachineConfigs feed a rendered config

```bash
POOL=worker
RENDERED=$(oc get mcp $POOL -o jsonpath='{.status.configuration.name}')
oc get mc $RENDERED -o json | jq -r '.spec.config.storage.files[]?.path'
oc get mc $RENDERED -o json | jq -r '.metadata.name'
oc get mcp $POOL -o json | jq '.status.configuration.source[]?.name'
```

### 12.4 Roll back or fix bad MachineConfig

Best practice: fix the source MachineConfig rather than manually editing the rendered MachineConfig.

If a custom MC is wrong:

```bash
oc get mc <bad-mc> -o yaml > bad-mc-backup.yaml
oc edit mc <bad-mc>
```

Or remove it if it is not needed:

```bash
oc delete mc <bad-mc>
```

Then watch new render and rollout:

```bash
oc get mcp worker -w
```

### 12.5 Important warning

Do **not** delete a rendered MachineConfig that is currently used by a pool or node.

Check first:

```bash
oc get mcp -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.configuration.name}{"\n"}{end}'
oc get nodes -o custom-columns=NAME:.metadata.name,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig
```

If a rendered MC appears in `currentConfig`, `desiredConfig`, or MCP status, do not delete it.

## 15. Case 7: OS pivot / rpm-ostree / image pull failure

### 15.1 What it means

During OpenShift upgrade, MCO updates the underlying RHCOS image using `rpm-ostree`. If the node cannot pull or deploy the target OS image, the MCP can become degraded.

Common causes:

- Disconnected mirror not configured correctly.
- Pull secret missing credentials.
- Proxy blocks registry.
- Custom CA missing.
- Registry unavailable.
- Disk full under `/var` or `/sysroot`.
- `rpm-ostreed` service failure.
- Corrupt ostree state.

### 15.2 Check MCD logs

```bash
oc logs -n openshift-machine-config-operator $MCD_POD -c machine-config-daemon --since=6h \
  | egrep -i 'pivot|rpm-ostree|ostree|image|pull|digest|signature|registry|unauthorized|x509|proxy|no space'
```

### 15.3 Check node services

```bash
oc debug node/$NODE
chroot /host
systemctl status rpm-ostreed --no-pager
journalctl -u rpm-ostreed -b --no-pager | tail -300
journalctl -u crio -b --no-pager | tail -200
df -h / /var /sysroot /boot
exit
exit
```

### 15.4 Check image pull from node

From debug shell:

```bash
oc debug node/$NODE
chroot /host
cat /etc/containers/registries.conf
ls -l /var/lib/kubelet/config.json
podman pull --authfile /var/lib/kubelet/config.json <target-os-image-or-release-image>
exit
exit
```

For disconnected clusters, verify:

```bash
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get proxy/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
```

### 15.5 Recovery ideas

- Fix mirror configuration.
- Fix pull secret.
- Fix proxy or trusted CA.
- Restore registry availability.
- Free disk space safely.
- Retry MCO rollout after node pull works.
- Avoid manual `rpm-ostree` changes unless directed by support or you fully understand the boot deployment state.

## 16. Case 8: Rendered MachineConfig missing or accidentally deleted

### 16.1 Symptom

MCD or MCP logs may show:

```text
machineconfig.machineconfiguration.openshift.io "rendered-worker-xxxxx" not found
```

This often happens when someone deleted an in-use rendered MachineConfig.

### 16.2 Confirm

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig
oc get mcp -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.configuration.name}{"\n"}{end}'
oc get mc | grep rendered
```

If a node references a rendered config that does not exist, that is the issue.

### 16.3 Recovery approach

Preferred recovery depends on context and OpenShift version. General strategy:

1. Do not delete more rendered configs.
2. Check whether the rendered config can be regenerated by the controller.
3. Inspect source MachineConfigs selected by the pool.
4. If the MCP can render a new desired config, let the node move to it.
5. If the node is stuck referencing missing current config, collect evidence and consider Red Hat support.

Useful commands:

```bash
oc describe co machine-config
oc describe mcp <pool>
oc get mc -l machineconfiguration.openshift.io/role=<role>
oc get mcp <pool> -o yaml
```

If you changed or recreated a source MC, monitor:

```bash
oc get mc --sort-by=.metadata.creationTimestamp | tail
oc get mcp <pool> -w
```

### 16.4 Prevention

Use prune commands cautiously and never delete configs in use:

```bash
oc adm prune renderedmachineconfigs --pool-name=worker
```

Dry-run review first. Do not manually delete `rendered-*` objects without checking node annotations and MCP status.

## 17. Case 9: Custom MCP selector or node label mistake

### 17.1 What it means

Custom MCPs rely on labels and selectors. A mistake can make nodes fall into the wrong pool or make a pool select unexpected MachineConfigs.

Example custom infra pool:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Nodes usually keep the `worker` role and add a custom role such as `infra`.

### 17.2 Check pool selectors

```bash
oc get mcp <pool> -o yaml
```

Check selected nodes:

```bash
oc get nodes --show-labels | grep <role>
```

Check MachineConfigs selected by role:

```bash
oc get mc -l machineconfiguration.openshift.io/role=worker
oc get mc -l machineconfiguration.openshift.io/role=infra
```

### 17.3 Common mistakes

| Mistake | Impact |
|---|---|
| Node label missing | Node not selected by expected custom pool |
| Node selected by wrong pool | Wrong rendered config applied |
| MachineConfig role label wrong | Config never included in desired render |
| Custom MCP selector excludes `worker` configs | Base worker config missing |
| Multiple custom pools select same node | Confusing and risky rollout behavior |

### 17.4 Recovery

Fix labels or MCP selectors carefully:

```bash
oc label node <node> node-role.kubernetes.io/infra=""
oc label node <node> node-role.kubernetes.io/infra-
```

Fix MachineConfig labels:

```bash
oc label mc <mc-name> machineconfiguration.openshift.io/role=infra --overwrite
```

Watch:

```bash
oc get mcp -w
```

## 18. Case 10: Disk, filesystem, SELinux, or permission issue

### 18.1 Disk full

MCD, CRI-O, kubelet, and rpm-ostree need disk space.

Check:

```bash
oc debug node/$NODE
chroot /host
df -h
findmnt
journalctl -u kubelet -b --no-pager | egrep -i 'no space|disk|eviction|imagefs|nodefs' | tail -50
journalctl -u crio -b --no-pager | egrep -i 'no space|disk|overlay|storage' | tail -50
journalctl -u rpm-ostreed -b --no-pager | egrep -i 'no space|error|failed' | tail -50
exit
exit
```

Fix carefully. Do not randomly delete files under `/usr`, `/ostree`, `/etc`, or `/var/lib/kubelet`.

Safer checks:

```bash
oc adm top nodes
oc adm top pods -A
```

Use application cleanup, image pruning policy, log rotation, or platform-supported cleanup methods.

### 18.2 File permission or ownership mismatch

Example MCP error:

```text
mode mismatch for file /etc/example.conf
```

Check expected mode:

```bash
MC=<rendered-mc>
FILE=/etc/example.conf
oc get mc $MC -o json | jq -r --arg f "$FILE" '.spec.config.storage.files[]? | select(.path==$f) | {path,mode,user:.user.name,group:.group.name}'
```

Check actual:

```bash
oc debug node/$NODE -- chroot /host stat /etc/example.conf
```

Fix:

```bash
oc debug node/$NODE
chroot /host
chmod <mode> /etc/example.conf
chown <user>:<group> /etc/example.conf
exit
exit
```

### 18.3 SELinux context

If a file or service fails due to SELinux context, check:

```bash
oc debug node/$NODE
chroot /host
ls -Z /path/to/file
ausearch -m AVC -ts recent 2>/dev/null | tail -50
journalctl -b --no-pager | grep -i denied | tail -50
exit
exit
```

Be careful with manual SELinux changes. Prefer correct MachineConfig-managed file location, mode, and service design.

## 19. Case 11: Paused MCP confusion

### 19.1 What paused means

A paused MCP does not roll out newly rendered configs to nodes until unpaused.

Check:

```bash
oc get mcp <pool> -o jsonpath='{.spec.paused}{"\n"}'
```

If `true`, the pool is paused.

### 19.2 Symptoms

- `UPDATED=False`
- `UPDATING=False`
- `DEGRADED=False`
- nodes not moving to desired config
- admin thinks rollout is stuck, but pool is intentionally paused

### 19.3 Unpause

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":false}}'
```

Pause:

```bash
oc patch mcp <pool> --type=merge -p '{"spec":{"paused":true}}'
```

### 19.4 Senior rule

Do not leave MCP paused after maintenance. A paused MCP can hide pending config changes and later create surprise reboots when unpaused.

## 21. How to safely use the MCD force file

### 21.1 What the force file does

The force file is:

```text
/run/machine-config-daemon-force
```

Creating this file causes MCD to bypass usual preflight configuration drift validation and reapply the current MachineConfig. It also causes a node reboot.

### 21.2 When it is useful

Use it when:

- You understand the drift.
- You want MCD to reapply the current rendered config.
- The node is otherwise healthy enough to reboot.
- You have maintenance approval for workload disruption.

### 21.3 When not to use it

Do not use it blindly when:

- You do not know why the node is degraded.
- The node has unresolved disk or boot issue.
- The bad desired config will break the node again.
- Multiple control plane nodes are degraded and quorum is at risk.
- The MCD pod is not running and cannot observe the force file.

### 21.4 Command

```bash
NODE=<node-name>
oc debug node/$NODE
chroot /host
touch /run/machine-config-daemon-force
exit
exit
```

Watch:

```bash
oc get node $NODE -w
oc get mcp -w
```

### 21.5 Production method

For master/control plane pool:

1. Check etcd health first.
2. Work on one master at a time.
3. Wait for node to become `Ready`.
4. Wait for MCP to update or move to next node.
5. Continue only after cluster is stable.

Check etcd/operator health:

```bash
oc get co etcd kube-apiserver kube-controller-manager kube-scheduler machine-config
oc get pods -n openshift-etcd -o wide
```

## 22. How to compare current, desired, and rendered configs

### 22.1 Get node current and desired config

```bash
NODE=<node-name>
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 22.2 Export rendered configs

```bash
CURRENT=$(oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}')
DESIRED=$(oc get node $NODE -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}')

oc get mc $CURRENT -o yaml > /tmp/${CURRENT}.yaml
oc get mc $DESIRED -o yaml > /tmp/${DESIRED}.yaml
```

### 22.3 Compare files in rendered configs

```bash
oc get mc $CURRENT -o json | jq -r '.spec.config.storage.files[]?.path' | sort > /tmp/current-files.txt
oc get mc $DESIRED -o json | jq -r '.spec.config.storage.files[]?.path' | sort > /tmp/desired-files.txt
diff -u /tmp/current-files.txt /tmp/desired-files.txt
```

### 22.4 Compare systemd units

```bash
oc get mc $CURRENT -o json | jq -r '.spec.config.systemd.units[]?.name' | sort > /tmp/current-units.txt
oc get mc $DESIRED -o json | jq -r '.spec.config.systemd.units[]?.name' | sort > /tmp/desired-units.txt
diff -u /tmp/current-units.txt /tmp/desired-units.txt
```

### 22.5 See source MachineConfigs for rendered config

```bash
oc get mcp worker -o json | jq -r '.status.configuration.source[]?.name'
```

Or directly from rendered MC if source info exists:

```bash
oc get mc $DESIRED -o json | jq '.metadata.annotations, .spec.config'
```

### 22.6 Determine if node is stuck before or after applying desired config

| Current vs Desired | State | Meaning |
|---|---|---|
| current = desired | Degraded | Usually validation/drift after applying current config |
| current != desired | Working | Normal rollout in progress |
| current != desired | Degraded | Failed while moving from current to desired |
| current = desired | Done | Healthy |

## 26. Production safety rules

### 26.1 Do not reboot everything

Never reboot all masters or all workers at once to “fix” MCP degraded.

For masters:

- Maintain etcd quorum.
- Work one node at a time.
- Confirm control plane operators healthy before the next node.

### 26.2 Do not delete rendered MachineConfigs blindly

Rendered MCs may be referenced by nodes. Deleting them can make recovery harder.

Check:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig
oc get mcp -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.configuration.name}{"\n"}{end}'
```

### 26.3 Do not manually edit managed files as a permanent fix

If MCO manages the file, the permanent fix must be in MachineConfig, KubeletConfig, ContainerRuntimeConfig, Image config, Proxy config, or another declarative object.

Manual edits are acceptable only as emergency recovery or to restore drift.

### 26.4 Do not ignore paused pools

Paused MCPs can accumulate pending changes. Unpausing later may trigger unexpected reboots.

### 26.5 Do not set `maxUnavailable` too high casually

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.maxUnavailable}{"\n"}'
```

Patch carefully:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

High `maxUnavailable` can increase disruption during node updates.

### 26.6 Do not fight MCO with manual drain/uncordon loops

If MCO is controlling rollout, understand why it cordoned/drained the node. Manual uncordon might only hide the symptom and MCO can cordon again.

## 27. Senior admin troubleshooting examples

### Example 1: Worker MCP degraded due to content mismatch

Symptom:

```bash
oc get mcp
```

```text
worker   rendered-worker-b2   False   True   True   5   4   4   1
```

Find reason:

```bash
oc describe mcp worker
```

```text
Node worker-3 is reporting: "content mismatch for file /etc/chrony.conf"
```

Check node annotation:

```bash
oc get node worker-3 -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

Check actual file:

```bash
oc debug node/worker-3 -- chroot /host sha256sum /etc/chrony.conf
oc debug node/worker-3 -- chroot /host stat /etc/chrony.conf
```

Fix:

- Restore expected content and mode from rendered MachineConfig.
- Or correct the source MachineConfig if desired config is wrong.

Then:

```bash
oc get mcp worker -w
```

Expected:

```text
worker   ...   True   False   False   ...   0
```

### Example 2: MCP degraded during upgrade because drain blocked by PDB

Symptom:

```bash
oc describe co machine-config
```

```text
Failed to resync because pool worker is not ready; node drain failed
```

Check controller logs:

```bash
oc logs -n openshift-machine-config-operator $MCC_POD -c machine-config-controller --since=6h | grep -i drain
```

Check pods on node:

```bash
oc get pods -A --field-selector spec.nodeName=worker-2 -o wide
```

Check PDB:

```bash
oc get pdb -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,ALLOWED:.status.disruptionsAllowed,CURRENT:.status.currentHealthy,DESIRED:.status.desiredHealthy
```

Fix:

- Scale deployment from 1 to 2 or 3 replicas.
- Ensure the second pod becomes healthy.
- Confirm `disruptionsAllowed > 0`.
- Let MCO retry drain.

### Example 3: Bad KubeletConfig makes node NotReady

Symptom:

```bash
oc get nodes
```

```text
worker-4   NotReady,SchedulingDisabled
```

MCP:

```text
worker degraded; node worker-4 unavailable
```

Check kubelet:

```bash
oc debug node/worker-4 -- chroot /host journalctl -u kubelet -b --no-pager | tail -200
```

If logs show invalid kubelet config, inspect recent KubeletConfig:

```bash
oc get kubeletconfig
oc get mc | grep kubelet
```

Recovery:

```bash
oc get kubeletconfig bad-config -o yaml > bad-config-backup.yaml
oc delete kubeletconfig bad-config
```

If kubelet needs temporary manual correction to start, repair on the node, start kubelet, then allow MCO to reconcile.

### Example 4: Disconnected registry misconfiguration blocks OS image pull

Symptom:

```text
failed to pull osImageURL ... x509 certificate signed by unknown authority
```

Check:

```bash
oc get proxy/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
```

On node:

```bash
oc debug node/$NODE
chroot /host
cat /etc/containers/registries.conf
podman pull --authfile /var/lib/kubelet/config.json <image>
exit
exit
```

Fix:

- Add correct CA to image config or proxy trust bundle.
- Fix mirror config.
- Fix pull secret.
- Confirm `podman pull` works on the node.
- Let MCO retry.

### Example 5: Pool appears stuck but is paused

Check:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

If true:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Watch:

```bash
oc get mcp worker -w
```

## 28. Interview / real-world explanation

A strong senior-level explanation:

> MCP degraded means the Machine Config Operator cannot reconcile the desired node configuration for at least one node in a MachineConfigPool. I first check `oc describe co machine-config` and `oc get mcp` to identify the affected pool. Then I find the degraded node from `oc describe mcp`, node annotations such as `machineconfiguration.openshift.io/state`, `currentConfig`, `desiredConfig`, and the MCD logs on that node. I classify the failure as configuration drift, drain failure, node NotReady, bad MachineConfig/KubeletConfig/ContainerRuntimeConfig, OS pivot/image pull failure, selector issue, or disk/runtime issue. I avoid blind reboots and do not delete rendered MachineConfigs in use. For drift, I compare the node’s on-disk state against the rendered MachineConfig and restore the expected content or fix the source MachineConfig. For drain issues, I check PDBs and pods on the node. After remediation, I verify `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`, node `currentConfig=desiredConfig`, and `machine-config` ClusterOperator is healthy.
