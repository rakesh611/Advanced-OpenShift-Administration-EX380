# Node Certificate Approval in OpenShift — Advanced Cluster Troubleshooting

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and L3 support engineers  
**Level:** 10+ years Linux/Kubernetes/OpenShift operations experience  
**Focus area:** Advanced Cluster Troubleshooting  
**Primary tool:** `oc` CLI  
**Applies to:** OpenShift Container Platform 4.x, especially installer-provisioned infrastructure (IPI), user-provisioned infrastructure (UPI), bare metal, vSphere, cloud, and disconnected environments

---

## 1. Executive Summary

Node certificate approval is the process by which OpenShift validates and signs certificate signing requests (CSRs) created by kubelets when nodes join or rejoin the cluster. Without the correct certificates, a node cannot fully authenticate to the Kubernetes API server, and the API server cannot safely connect back to the kubelet for operations such as logs, exec, rsh, metrics, and pod status interactions.

In OpenShift, node certificate troubleshooting is especially important in these situations:

- New worker node added but not appearing in `oc get nodes`
- Node appears but remains `NotReady`
- `oc logs`, `oc exec`, or `oc rsh` fails even though pods are running
- Bare-metal or UPI cluster has pending CSRs after installation or scaling
- Machine API is unavailable or unsupported
- Cluster has resumed from hibernation
- Node certificates rotated while the cluster was offline
- Kubelet is repeatedly generating CSRs
- Multiple CSRs exist for the same node
- Cluster Machine Approver is not approving expected CSRs
- Control plane bootstrap or worker bootstrap is stuck

A senior administrator must understand not only **how to approve CSRs**, but also **which CSRs are safe to approve**, **why they are pending**, **what component should normally approve them**, and **what security risk is introduced by blind approval**.

The most dangerous command in this topic is not complex:

```bash
oc get csr -o name | xargs oc adm certificate approve
```

It is dangerous because it approves every pending CSR without validating the requester, signer, node identity, hostname, IP address, or whether the request belongs to a real node. In production, especially in UPI or bare-metal environments, you should inspect CSRs before approval.

## 2. Why Node Certificates Matter

OpenShift uses TLS certificates heavily. For nodes, certificates are used in two main directions:

1. **Kubelet to API server**  
   The kubelet authenticates to the API server as a node identity such as:

   ```text
   system:node:<node-name>
   ```

2. **API server to kubelet**  
   The API server connects to the kubelet HTTPS endpoint, normally port `10250`, for operations such as:

   - `oc logs`
   - `oc exec`
   - `oc rsh`
   - retrieving pod/container status details
   - kubelet API interactions
   - some metrics and diagnostic paths

If the kubelet client certificate is missing or invalid, the node cannot authenticate properly to the API server. If the kubelet serving certificate is missing or not approved, the node can sometimes appear joined, but API-server-to-kubelet operations fail.

This creates a common troubleshooting trap:

```text
Node Ready: yes
Pod Running: yes
oc logs: fails
oc exec: fails
```

That pattern often points to a kubelet serving certificate problem, network path problem to port `10250`, or kubelet authentication/authorization problem.

## 3. OpenShift Node Certificate Flow

When a new OpenShift node boots, the high-level flow is:

```text
Node boots with ignition
        |
        v
Machine Config Server provides configuration
        |
        v
Kubelet starts using bootstrap credentials
        |
        v
Kubelet creates CSR for client certificate
        |
        v
CSR is approved and signed
        |
        v
Kubelet authenticates as system:node:<node-name>
        |
        v
Node object appears or becomes usable
        |
        v
Kubelet creates CSR for serving certificate
        |
        v
Serving CSR is approved and signed
        |
        v
API server can securely connect to kubelet
```

In OpenShift 4.x, the exact automation differs by platform and installation type.

### 3.1 Client CSR

The client CSR is used by the kubelet to authenticate to the API server.

Typical signer:

```text
kubernetes.io/kube-apiserver-client-kubelet
```

Typical subject:

```text
CN = system:node:<node-name>
O  = system:nodes
```

Typical requester for a new bootstrapping node in OpenShift:

```text
system:serviceaccount:openshift-machine-config-operator:node-bootstrapper
```

After the client certificate is approved and issued, the kubelet can authenticate as a real node.

### 3.2 Serving CSR

The serving CSR is used by the kubelet HTTPS server. This certificate allows the API server to connect to the kubelet securely.

Typical signer:

```text
kubernetes.io/kubelet-serving
```

Typical subject:

```text
CN = system:node:<node-name>
O  = system:nodes
```

Typical SANs:

```text
DNS:<node-name>
DNS:<node-name>.<cluster-domain-or-internal-domain>
IP Address:<node-ip>
```

The serving CSR is commonly the CSR that remains pending in manual environments. If it is not approved, the node might join, but commands that require API-server-to-kubelet communication can fail.

## 4. Important OpenShift Behavior

### 4.1 Two CSRs per node is normal

When adding a node, you commonly see two CSR phases:

1. Client CSR
2. Serving CSR

The client CSR must be approved first. After that, the kubelet generates the serving CSR.

Example:

```bash
oc get csr
```

Example output:

```text
NAME        AGE   SIGNERNAME                                    REQUESTOR                                                                   CONDITION
csr-abc12   5m    kubernetes.io/kube-apiserver-client-kubelet   system:serviceaccount:openshift-machine-config-operator:node-bootstrapper   Pending
```

After approval:

```text
NAME        AGE   SIGNERNAME                         REQUESTOR                 CONDITION
csr-def34   1m    kubernetes.io/kubelet-serving      system:node:worker-4      Pending
```

### 4.2 More than two CSRs per node can be normal after delay

CSRs rotate. If you add machines and do not approve the CSRs quickly, the kubelet can generate new CSRs. You might see more than two CSRs for the same node.

This does not automatically mean an attack or corruption. It often means the node waited too long for approval. However, you must inspect them carefully because multiple CSRs also make blind approval riskier.

### 4.3 Serving CSRs are not automatically approved by upstream kube-controller-manager

In Kubernetes, the kubelet client signer can be auto-approved by the certificate approval controller, but kubelet serving CSRs are intentionally not automatically approved by the upstream kube-controller-manager. This is because validating a serving certificate is more sensitive: the requested DNS names and IP addresses must really belong to the node.

In OpenShift, the Cluster Machine Approver and platform-specific automation can approve some CSRs when enough machine identity information exists. On UPI, bare metal, and other environments without full automatic machine management, administrators often need a safe manual or custom automated approval process.

### 4.4 Machine API changes the approval experience

In IPI or Machine API-managed clusters, OpenShift has more metadata to validate a joining machine. The Cluster Machine Approver can approve expected worker-node CSRs after installation.

In UPI or infrastructure with limited automatic machine management, OpenShift cannot always prove that a kubelet serving certificate belongs to a real, expected node. That is why manual approval or a custom approval controller/process might be required.

### 4.5 Bootstrap is different from day-2 operations

During cluster bootstrap, control plane CSR approval is handled differently. Bootstrap components can approve initial control-plane CSRs. After installation, worker nodes and replacement nodes follow the normal CSR flow.

Do not confuse:

```text
bootstrap installation CSR behavior
```

with:

```text
day-2 node replacement or scale-out CSR behavior
```

They are not operationally identical.

## 5. Key Objects and Components

## 5.1 CertificateSigningRequest object

CSRs are cluster-scoped resources:

```bash
oc get csr
```

They are not namespaced.

Useful fields:

```bash
oc get csr <csr-name> -o yaml
```

Important fields:

```yaml
spec:
  signerName: kubernetes.io/kube-apiserver-client-kubelet
  request: <base64-encoded-csr>
  usages:
  - digital signature
  - key encipherment
  - client auth
  username: system:serviceaccount:openshift-machine-config-operator:node-bootstrapper
status:
  conditions:
  - type: Approved
```

Or for serving:

```yaml
spec:
  signerName: kubernetes.io/kubelet-serving
  usages:
  - digital signature
  - key encipherment
  - server auth
  username: system:node:worker-4
```

### 5.2 Kubelet

The kubelet runs on every node. It is responsible for:

- registering the node
- running pods through CRI-O
- reporting node and pod status
- requesting certificates
- rotating certificates
- exposing kubelet HTTPS endpoint on port `10250`

Important node-side paths:

```text
/var/lib/kubelet/
/var/lib/kubelet/pki/
/etc/kubernetes/kubeconfig
/etc/kubernetes/kubelet.conf
/etc/kubernetes/manifests/
/etc/machine-config-daemon/
```

Useful node-side commands:

```bash
systemctl status kubelet
journalctl -u kubelet -b --no-pager
journalctl -u kubelet -b --no-pager | grep -i csr
journalctl -u kubelet -b --no-pager | grep -i certificate
```

### 5.3 Cluster Machine Approver

The Cluster Machine Approver is an OpenShift cluster component that helps approve CSRs for new worker nodes after installation when the platform has enough machine information.

Check it:

```bash
oc get pods -n openshift-cluster-machine-approver
oc logs -n openshift-cluster-machine-approver deploy/machine-approver
```

Also check the ClusterOperator:

```bash
oc get co cluster-machine-approver
oc describe co cluster-machine-approver
```

### 5.4 Machine API

Machine API resources help OpenShift understand expected machines.

Check machines:

```bash
oc get machines -n openshift-machine-api
oc get machinesets -n openshift-machine-api
oc describe machine <machine-name> -n openshift-machine-api
```

If the node exists but the Machine object is missing, stale, or broken, automatic approval might not behave as expected.

### 5.5 Machine Config Server

New RHCOS nodes retrieve configuration from the Machine Config Server during bootstrap. The Machine Config Server must be reachable by new nodes.

Common ports:

```text
22623/tcp
22624/tcp
```

If the node cannot get ignition or machine config, it may never reach the point of creating CSRs.

## 6. CSR Signer Types You Must Know

## 6.1 `kubernetes.io/kube-apiserver-client-kubelet`

Purpose:

```text
Kubelet authenticates to the Kubernetes API server.
```

Expected identity:

```text
CN=system:node:<node-name>
O=system:nodes
```

Expected usage:

```text
client auth
```

Typical new-node requester:

```text
system:serviceaccount:openshift-machine-config-operator:node-bootstrapper
```

Operational impact if missing:

- Node might not register
- Node can remain absent from `oc get nodes`
- Kubelet logs show authentication/certificate/bootstrap errors
- Machine might stay Provisioned/Running but no Node object appears

### 6.2 `kubernetes.io/kubelet-serving`

Purpose:

```text
API server connects securely to kubelet HTTPS endpoint.
```

Expected identity:

```text
CN=system:node:<node-name>
O=system:nodes
```

Expected usage:

```text
server auth
```

Expected SANs:

```text
DNS names and IP addresses that really belong to the node
```

Operational impact if missing:

- `oc logs` can fail
- `oc exec` can fail
- `oc rsh` can fail
- API server cannot verify kubelet serving certificate
- Node may still show `Ready`

### 6.3 Other CSRs

Not every CSR is a node CSR. You might see CSRs from other components or custom workloads.

Never approve a CSR only because it is pending.

Always check:

```bash
oc get csr <csr-name> -o jsonpath='{.spec.signerName}{"\n"}{.spec.username}{"\n"}{.spec.usages}{"\n"}'
```

## 8. Safe Manual CSR Approval Workflow

This is the production-safe workflow.

## 8.1 List pending CSRs with useful fields

```bash
oc get csr -o custom-columns=NAME:.metadata.name,AGE:.metadata.creationTimestamp,SIGNER:.spec.signerName,REQUESTOR:.spec.username,CONDITION:.status.conditions[*].type
```

Example:

```text
NAME        AGE                   SIGNER                                      REQUESTOR                                                                   CONDITION
csr-x9k2v   2026-07-03T10:10:00Z  kubernetes.io/kube-apiserver-client-kubelet system:serviceaccount:openshift-machine-config-operator:node-bootstrapper        <none>
csr-b2p8m   2026-07-03T10:12:00Z  kubernetes.io/kubelet-serving               system:node:worker-4                                                       <none>
```

## 8.2 Decode the CSR

```bash
CSR=csr-x9k2v
oc get csr $CSR -o jsonpath='{.spec.request}' | base64 -d > /tmp/$CSR.csr
openssl req -in /tmp/$CSR.csr -noout -text
```

Check:

- Subject CN
- Organization
- DNS SANs
- IP SANs
- Key usages
- Extended key usages

## 8.3 Validate client CSR

For client CSR:

```text
Signer: kubernetes.io/kube-apiserver-client-kubelet
CN:     system:node:<expected-node-name>
O:      system:nodes
Usage:  client auth
```

Validate the requestor:

```bash
oc get csr $CSR -o jsonpath='{.spec.username}{"\n"}'
```

Expected during bootstrap:

```text
system:serviceaccount:openshift-machine-config-operator:node-bootstrapper
```

Approve only after confirming it belongs to a legitimate new node:

```bash
oc adm certificate approve $CSR
```

## 8.4 Wait for serving CSR

After client CSR approval:

```bash
watch -n 5 'oc get csr'
```

Or:

```bash
oc get csr --watch
```

You should see a serving CSR:

```text
kubernetes.io/kubelet-serving
```

## 8.5 Validate serving CSR

Decode it:

```bash
CSR=csr-b2p8m
oc get csr $CSR -o jsonpath='{.spec.request}' | base64 -d > /tmp/$CSR.csr
openssl req -in /tmp/$CSR.csr -noout -text
```

Validate:

```text
Signer: kubernetes.io/kubelet-serving
CN:     system:node:<expected-node-name>
O:      system:nodes
Usage:  server auth
SANs:   node DNS/IP values only
```

Confirm the IP belongs to the node:

```bash
oc get node <node-name> -o wide
```

Or compare with infrastructure inventory, DHCP, DNS, BMC/IPMI, cloud instance, vSphere VM, or bare-metal host records.

Approve:

```bash
oc adm certificate approve $CSR
```

## 8.6 Verify node and kubelet operations

```bash
oc get nodes -o wide
oc describe node <node-name>
oc adm node-logs <node-name> -u kubelet --tail=50
```

Test pod log path:

```bash
oc get pods -A -o wide | grep <node-name>
oc logs -n <namespace> <pod-name>
```

Test exec path:

```bash
oc exec -n <namespace> <pod-name> -- whoami
```

## 9. One-liners for Controlled Approval

## 9.1 Approve only pending client kubelet CSRs

Use with care. Review output before piping to approval.

Preview:

```bash
oc get csr -o jsonpath='{range .items[?(@.spec.signerName=="kubernetes.io/kube-apiserver-client-kubelet")]}{.metadata.name}{"\t"}{.spec.username}{"\t"}{.status.conditions[*].type}{"\n"}{end}'
```

Approve pending only:

```bash
oc get csr -o json | jq -r '
  .items[]
  | select(.spec.signerName == "kubernetes.io/kube-apiserver-client-kubelet")
  | select((.status.conditions // []) | length == 0)
  | .metadata.name
' | xargs -r oc adm certificate approve
```

## 9.2 Approve only pending kubelet serving CSRs after inspection

Preview:

```bash
oc get csr -o json | jq -r '
  .items[]
  | select(.spec.signerName == "kubernetes.io/kubelet-serving")
  | select((.status.conditions // []) | length == 0)
  | [.metadata.name, .spec.username] | @tsv
'
```

Approve:

```bash
oc get csr -o json | jq -r '
  .items[]
  | select(.spec.signerName == "kubernetes.io/kubelet-serving")
  | select((.status.conditions // []) | length == 0)
  | .metadata.name
' | xargs -r oc adm certificate approve
```

Do not run this blindly in production. Use it only when you have already validated the nodes.

## 9.3 Approve all pending CSRs

This is common in labs but risky in production:

```bash
oc get csr -o go-template='{{range .items}}{{if not .status}}{{.metadata.name}}{{"\n"}}{{end}}{{end}}' | xargs oc adm certificate approve
```

Use this only in controlled lab/exam environments or when you have already confirmed that every pending CSR is legitimate.

## 10. Deep Inspection Commands

## 10.1 Show signer, requestor, condition

```bash
oc get csr -o custom-columns=NAME:.metadata.name,SIGNER:.spec.signerName,REQUESTOR:.spec.username,USAGES:.spec.usages,CONDITION:.status.conditions[*].type
```

## 10.2 Show all pending CSR names

```bash
oc get csr -o jsonpath='{range .items[?(@.status.conditions==null)]}{.metadata.name}{"\n"}{end}'
```

## 10.3 Decode every pending CSR

```bash
for csr in $(oc get csr -o jsonpath='{range .items[?(@.status.conditions==null)]}{.metadata.name}{"\n"}{end}'); do
  echo "===== $csr ====="
  oc get csr "$csr" -o jsonpath='{.spec.signerName}{"\n"}{.spec.username}{"\n"}'
  oc get csr "$csr" -o jsonpath='{.spec.request}' | base64 -d | openssl req -noout -subject -text | egrep 'Subject:|DNS:|IP Address:|TLS Web Client|TLS Web Server|X509v3 Key Usage|X509v3 Extended Key Usage'
done
```

## 10.4 Find CSRs for a node

```bash
NODE=worker-4
oc get csr -o json | jq -r --arg NODE "$NODE" '
  .items[]
  | select(.spec.username | contains($NODE))
  | [.metadata.name, .spec.signerName, .spec.username, (.status.conditions[0].type // "Pending")] | @tsv
'
```

This catches serving CSRs requested by `system:node:<node-name>`. For bootstrap client CSRs, decode the CSR subject because the requestor might be `node-bootstrapper` instead of `system:node:<node-name>`.

## 10.5 Show CSR age in a readable table

```bash
oc get csr --sort-by=.metadata.creationTimestamp
```

## 10.6 Inspect an approved certificate

```bash
CSR=csr-b2p8m
oc get csr $CSR -o jsonpath='{.status.certificate}' | base64 -d | openssl x509 -noout -text
```

## 11. Common Failure Scenarios and Fixes

## 11.1 New node not visible in `oc get nodes`

### Symptoms

```bash
oc get nodes
```

New node is absent.

CSRs show pending client requests:

```bash
oc get csr
```

Example:

```text
csr-abc12   kubernetes.io/kube-apiserver-client-kubelet   node-bootstrapper   Pending
```

### Likely causes

- Client CSR not approved
- Node cannot reach API server
- Node cannot reach Machine Config Server
- Bootstrap ignition is wrong or stale
- Node hostname mismatch
- DNS issue
- NTP/time skew
- Bootstrap kubeconfig issue
- Machine Config Daemon/bootstrap failure
- Firewall blocking required ports

### Fix

1. Verify node is expected.
2. Decode CSR and confirm CN.
3. Approve the client CSR.
4. Watch node registration.

```bash
oc adm certificate approve <client-csr>
watch -n 5 'oc get nodes -o wide; echo; oc get csr'
```

If no CSR exists, troubleshoot node bootstrapping:

```bash
# From node console/SSH
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -100
curl -k https://api.<cluster-domain>:6443/readyz
curl -k https://api-int.<cluster-domain>:22623/config/worker
```

## 11.2 Node appears but `oc logs` fails

### Symptoms

```bash
oc get nodes
```

Node is Ready.

But:

```bash
oc logs -n <namespace> <pod>
```

fails with errors such as:

```text
Error from server: Get "https://<node>:10250/containerLogs/...": x509: certificate signed by unknown authority
```

or:

```text
remote error: tls: internal error
```

or:

```text
error dialing backend: remote error: tls: bad certificate
```

### Likely causes

- Kubelet serving CSR not approved
- Serving certificate SAN does not match node address used by API server
- API server cannot reach kubelet on `10250`
- Node firewall/security group blocks `10250`
- Kubelet down or unhealthy
- Hostname or DNS mismatch

### Fix

Check serving CSR:

```bash
oc get csr | grep kubelet-serving
```

Decode and approve if valid:

```bash
CSR=<serving-csr>
oc get csr $CSR -o jsonpath='{.spec.request}' | base64 -d | openssl req -noout -text
oc adm certificate approve $CSR
```

Then test:

```bash
oc logs -n <namespace> <pod>
oc exec -n <namespace> <pod> -- date
```

If still failing, test network path to kubelet:

```bash
oc debug node/<node-name>
chroot /host
ss -lntp | grep 10250
systemctl status kubelet
```

## 11.3 Node remains `NotReady` after CSR approval

### Symptoms

```text
NAME       STATUS     ROLES    AGE   VERSION
worker-4   NotReady   worker   20m   v1.x
```

CSRs are approved.

### Likely causes

- CNI/OVN not ready
- kubelet cannot contact CRI-O
- MachineConfigPool update in progress or degraded
- Node time skew
- Disk pressure, memory pressure, PID pressure
- Invalid kubelet config
- Wrong node IP selected
- Firewall issue

### Fix

Describe node:

```bash
oc describe node worker-4
```

Check key conditions:

```text
Ready
MemoryPressure
DiskPressure
PIDPressure
NetworkUnavailable
```

Check MCP:

```bash
oc get mcp
oc describe mcp worker
```

Debug node:

```bash
oc debug node/worker-4
chroot /host
systemctl status kubelet
systemctl status crio
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
```

Check OVN/SDN:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide | grep worker-4
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --tail=100
```

CSR approval only solves certificate trust. It does not fix CNI, CRI-O, disk, DNS, routing, or MachineConfigPool problems.

## 11.4 CSRs keep reappearing

### Symptoms

```bash
watch oc get csr
```

New pending CSRs keep appearing for the same node.

### Likely causes

- CSR not approved within rotation interval
- Kubelet cannot retrieve or persist signed certificate
- Disk read-only or full
- `/var/lib/kubelet/pki` permissions problem
- Kubelet restarted repeatedly
- Node identity/hostname changes between boots
- Time skew causing certificate validity problems
- Cluster CA or signer/controller issue

### Fix

Check kubelet logs:

```bash
journalctl -u kubelet -b --no-pager | egrep -i 'certificate|csr|rotate|x509|failed|error'
```

Check disk:

```bash
df -h
mount | grep ' / '
```

Check time:

```bash
timedatectl
chronyc tracking
```

Check certificate files:

```bash
ls -l /var/lib/kubelet/pki/
openssl x509 -in /var/lib/kubelet/pki/kubelet-client-current.pem -noout -dates -subject 2>/dev/null || true
```

Approve all valid CSRs for the node if multiple legitimate rotations exist:

```bash
oc get csr --sort-by=.metadata.creationTimestamp
```

Decode before approving.

## 11.5 Cluster Machine Approver not approving CSRs

### Symptoms

Pending CSRs remain in a Machine API-managed cluster.

### Checks

```bash
oc get co cluster-machine-approver
oc describe co cluster-machine-approver
oc get pods -n openshift-cluster-machine-approver
oc logs -n openshift-cluster-machine-approver deploy/machine-approver --tail=200
```

Check Machine objects:

```bash
oc get machines -n openshift-machine-api -o wide
oc describe machine <machine-name> -n openshift-machine-api
```

Check whether a Machine object maps to the Node:

```bash
oc get machine -n openshift-machine-api -o json | jq -r '.items[] | [.metadata.name, .status.nodeRef.name, .status.phase] | @tsv'
```

### Likely causes

- Machine object missing
- Machine stuck in Provisioning/Provisioned/Failed
- Provider ID mismatch
- Node name does not match expected machine metadata
- Machine API Operator degraded
- Cluster Machine Approver degraded
- Cloud provider API problem
- UPI/bare-metal environment lacks machine metadata

### Fix

Fix the Machine API issue first if automation is expected. If this is UPI/bare metal and manual approval is expected, use the safe manual workflow.

## 11.6 Control plane replacement stuck

### Symptoms

- Replacing master/control-plane node
- New control-plane host boots
- CSRs pending
- etcd membership or static pod rollout blocked

### Important note

Control plane node replacement is more sensitive than worker node replacement. Do not blindly approve CSRs if the node identity, hostname, IP, or etcd membership is uncertain.

### Checks

```bash
oc get nodes -l node-role.kubernetes.io/master
oc get csr
```

## 12. Security Model and Approval Risk

Approving a node CSR means you are allowing an identity into the cluster trust model.

For client CSRs, approval can allow a kubelet to authenticate as:

```text
system:node:<node-name>
```

For serving CSRs, approval can allow the API server to trust a kubelet endpoint for a specific node name/IP/DNS set.

### 12.1 Why blind approval is risky

A malicious or misconfigured system might attempt to request a certificate using a node-like identity. If you approve it blindly, you might grant trust to an unintended machine.

Risks include:

- rogue node joining the cluster
- node impersonation
- incorrect node IP/DNS in serving certificate
- API server trusting a wrong kubelet endpoint
- later troubleshooting confusion due to duplicate node names
- audit/security compliance failure

### 12.2 Minimum validation before approval

Before approving a CSR in production, validate:

1. The node is expected.
2. The node hostname is correct.
3. The node IP belongs to the expected machine.
4. The CSR signer is expected.
5. The subject is expected.
6. The organization is `system:nodes` for kubelet CSRs.
7. The usage is appropriate.
8. The requester is expected.
9. The Machine object or infrastructure inventory matches.
10. There are no duplicate node names or stale machines.

### 12.3 Client CSR validation matrix

| Field | Expected value |
|---|---|
| `spec.signerName` | `kubernetes.io/kube-apiserver-client-kubelet` |
| Subject CN | `system:node:<node-name>` |
| Subject O | `system:nodes` |
| Usage | client auth |
| Requester during bootstrap | `system:serviceaccount:openshift-machine-config-operator:node-bootstrapper` |
| Approval risk | Grants node client identity |

### 12.4 Serving CSR validation matrix

| Field | Expected value |
|---|---|
| `spec.signerName` | `kubernetes.io/kubelet-serving` |
| Subject CN | `system:node:<node-name>` |
| Subject O | `system:nodes` |
| Usage | server auth |
| SAN DNS | expected node DNS names |
| SAN IP | expected node IP addresses |
| Requester | usually `system:node:<node-name>` |
| Approval risk | API server trusts kubelet endpoint |

## 13. Troubleshooting by Symptom

## 13.1 `oc get csr` shows many Pending entries

Run:

```bash
oc get csr --sort-by=.metadata.creationTimestamp
```

Group by signer:

```bash
oc get csr -o json | jq -r '.items[] | [.spec.signerName, (.status.conditions[0].type // "Pending")] | @tsv' | sort | uniq -c
```

Look for old CSRs:

```bash
oc get csr --sort-by=.metadata.creationTimestamp | head
```

Action:

- Do not approve all immediately.
- Identify which nodes are joining or rotating.
- Delete stale denied/failed CSRs only after confirming they are obsolete.
- Approve valid pending CSRs in correct order.

## 13.2 `oc get nodes` does not show new worker

Likely client CSR pending or node cannot reach API/MCS.

Run:

```bash
oc get csr
oc get machines -n openshift-machine-api -o wide
```

If no CSR:

- Check ignition
- Check MCS reachability
- Check DNS
- Check API reachability
- Check node boot logs

If CSR exists:

- Decode client CSR
- Approve if valid

## 13.3 `oc logs` fails on only one node

Likely node-specific serving cert or network issue.

Find pod node:

```bash
oc get pod -n <namespace> <pod> -o wide
```

Check serving CSR for that node:

```bash
oc get csr | grep <node-name>
```

Check kubelet port:

```bash
oc debug node/<node-name>
chroot /host
ss -lntp | grep 10250
systemctl status kubelet
```

## 13.4 `oc logs` fails on all nodes

This is less likely to be a single node CSR issue. Check:

```bash
oc get co kube-apiserver authentication network
oc get pods -n openshift-kube-apiserver
oc get csr
```

Possible causes:

- API server issue
- network/firewall issue from control plane to workers
- global serving CSR approval backlog
- kubelet serving cert rotation issue on many nodes
- cluster CA/trust bundle issue

## 13.5 Node certificate expired

Check node certificate dates:

```bash

openssl x509 -in /var/lib/kubelet/pki/kubelet-client-current.pem -noout -dates -subject
```

If rotation CSRs exist, validate and approve as required.

## 13.6 Node hostname changed

Symptoms:

- New CSR subject references unexpected node name
- Old node object remains
- New node object appears separately
- Machine object maps incorrectly

Check:

```bash

oc get nodes
oc get csr
```

## 16. UPI and Bare Metal Special Considerations

UPI and bare-metal clusters need extra care because the cluster may not have enough authoritative machine metadata to verify every new node automatically.

### 16.1 Common UPI pain points

- Static DHCP entries missing
- Reverse DNS mismatch
- Node hostname mismatch
- Reused VM/template with stale identity
- Wrong ignition file
- API-int load balancer missing port `22623`
- API load balancer missing port `6443`
- Firewall blocks `10250`
- Manual CSR approval forgotten
- Serving CSRs pending after node replacement
- Duplicate node names after reinstall

### 16.2 Recommended UPI approval process

Maintain an inventory file:

```text
node-name, role, mac-address, ip-address, bmc-address, serial, rack, expected-dns
worker-4, worker, 52:54:00:aa:bb:cc, 10.10.10.44, 10.10.20.44, ABC123, rack7, worker-4.ocp.example.com
```

Before approval, compare CSR SANs with inventory.

For serving CSR:

```bash
oc get csr <csr> -o jsonpath='{.spec.request}' | base64 -d | openssl req -noout -text | egrep 'Subject:|DNS:|IP Address:'
```

Only approve when values match.

### 16.3 Do not approve stale node identity

If a machine was reinstalled but kept the same hostname, confirm old node object and machine references are cleaned up as appropriate.

```bash
oc get node <node-name>
oc describe node <node-name>
oc get machine -n openshift-machine-api -o wide | grep <node-name>
```

If decommissioning old node:

```bash
oc adm cordon <node-name>
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
oc delete node <node-name>
```

Be careful with control-plane nodes; follow official replacement procedures.

## 18. Certificate Rotation

Kubelet certificates rotate automatically. Rotation can generate new CSRs.

A healthy cluster should handle routine rotation automatically where supported. Problems occur when:

- approval automation is unavailable
- cluster was powered off or hibernated
- certificates expired while cluster was down
- signer/controller-manager issue exists
- node cannot persist new certificates
- clock skew causes validity errors

Check rotation logs:

Check pending CSRs:


## 22. Advanced: Build a CSR Review Script

This script prints signer, username, subject, and SANs for pending CSRs.

```bash
#!/usr/bin/env bash
set -euo pipefail

for csr in $(oc get csr -o jsonpath='{range .items[?(@.status.conditions==null)]}{.metadata.name}{"\n"}{end}'); do
  echo
  echo "================================================================================"
  echo "CSR: $csr"
  echo "================================================================================"
  echo "Signer:   $(oc get csr "$csr" -o jsonpath='{.spec.signerName}')"
  echo "User:     $(oc get csr "$csr" -o jsonpath='{.spec.username}')"
  echo "Usages:   $(oc get csr "$csr" -o jsonpath='{.spec.usages}')"
  echo
  oc get csr "$csr" -o jsonpath='{.spec.request}' \
    | base64 -d \
    | openssl req -noout -text \
    | egrep 'Subject:|DNS:|IP Address:|X509v3 Key Usage|X509v3 Extended Key Usage|TLS Web Client|TLS Web Server' || true
  echo
  echo "Approve manually with: oc adm certificate approve $csr"
done
```

Save:

```bash
vi review-pending-csrs.sh
chmod +x review-pending-csrs.sh
./review-pending-csrs.sh
```

## 23. Advanced: Safer Semi-Automatic Approval Concept

In mature environments, avoid human blind approval by using an inventory-based process.

Example logic:

```text
For every pending kubelet-serving CSR:
  Decode CSR
  Extract node name from CN
  Extract DNS/IP SANs
  Check node name in approved inventory
  Check IP SAN matches inventory
  Check requester is system:node:<node-name>
  Check signer is kubernetes.io/kubelet-serving
  Check usage is server auth
  If all pass, approve
  Else, alert platform team
```

Pseudo-command approach:

```bash
# Do not copy as production automation without testing.
# This is a design pattern, not a complete security product.
```

Production requirements:

- inventory source of truth
- audit logs
- deny-by-default behavior
- alerting for mismatches
- dry-run mode
- change-management approval
- separate policy for control-plane nodes
- integration with CMDB/cloud/vSphere/bare-metal inventory

## 27. Interview / Real-World Explanation

If asked in an interview:

> What is node certificate approval in OpenShift?

Answer:

```text
When an OpenShift node joins the cluster, the kubelet uses bootstrap credentials to request certificates from the Kubernetes certificates API. The first important CSR is the kubelet client certificate, which lets the kubelet authenticate to the API server as system:node:<node-name>. After that is approved, the kubelet requests a serving certificate so the API server can securely connect back to the kubelet on port 10250. In OpenShift, the Cluster Machine Approver can approve expected CSRs in Machine API-managed environments, but UPI and bare-metal clusters often require manual or custom approval, especially for kubelet-serving CSRs. If the client CSR is pending, the node may not join. If the serving CSR is pending, the node may be Ready but oc logs, oc exec, or oc rsh can fail. In production, I never approve CSRs blindly; I decode the CSR and validate signerName, requestor, CN, organization, SAN DNS/IP, node inventory, and Machine object before approval.
```

## 29. What Not To Do

Do not approve all CSRs blindly in production.

Do not approve a serving CSR with unknown IP SANs.

Do not approve a CSR for a hostname that does not match inventory.

Do not assume `Node Ready` means serving certificates are correct.

Do not delete CSRs randomly while the node is still bootstrapping.

Do not troubleshoot only from the cluster side if no CSR appears; check the node console/kubelet logs.

Do not confuse API certificate, ingress certificate, service serving certificate, and kubelet node certificates. They solve different problems.

Do not ignore time synchronization. Time skew breaks certificates.

Do not treat UPI/bare metal the same as IPI cloud clusters.

## 30. Quick Difference: Client CSR vs Serving CSR

| Topic | Client CSR | Serving CSR |
|---|---|---|
| Direction | kubelet to API server | API server to kubelet |
| Signer | `kubernetes.io/kube-apiserver-client-kubelet` | `kubernetes.io/kubelet-serving` |
| Main usage | client auth | server auth |
| Subject | `system:node:<node>` | `system:node:<node>` |
| Common requestor | `node-bootstrapper` during first join | `system:node:<node>` |
| If pending | node may not join | logs/exec/rsh may fail |
| Approval sensitivity | grants node identity | validates kubelet endpoint DNS/IP |
| Production validation | CN/O/requestor/inventory | CN/O/SAN IP/DNS/inventory |

```text
Unauthorized
```

Possible meaning:

- kubelet client certificate invalid
- bootstrap auth problem
- RBAC/bootstrap issue

### Error: certificate has expired or is not yet valid

```text
x509: certificate has expired or is not yet valid
```

Possible meaning:

- certificate rotation problem
- node clock skew
- cluster was offline too long

## 32. Exam/Lab Notes

In training or exam labs, you may be expected to approve CSRs quickly.

Useful lab command:

```bash
oc get csr
oc adm certificate approve <csr-name>
```

For multiple pending CSRs in a controlled lab:

```bash
oc get csr -o go-template='{{range .items}}{{if not .status}}{{.metadata.name}}{{"\n"}}{{end}}{{end}}' | xargs oc adm certificate approve
```

Then verify:

```bash
oc get nodes
oc get csr
```

For real production, inspect before approval.

## 33. Senior Admin Mental Model

Think of node certificate approval as a gate in the cluster trust chain.

```text
Ignition gives the node enough configuration to ask for trust.
CSR approval grants trust.
Client cert lets node speak as a node.
Serving cert lets API server trust the node endpoint.
Machine API and Cluster Machine Approver automate trust only when identity can be verified.
UPI/bare metal requires stronger operational discipline because the cluster has less external machine identity.
```

When troubleshooting, always separate three questions:

1. Did the node request trust?
2. Did the cluster approve and issue trust?
3. Can both sides communicate using that trust?

Those map to:

```text
CSR exists?
CSR approved and certificate issued?
API/kubelet network and TLS path works?
```

## 35. Final Takeaway

For advanced OpenShift troubleshooting, node certificate approval is not just a command. It is a trust validation process.

A junior admin asks:

```text
Which CSR should I approve?
```

A senior admin asks:

```text
Who requested this certificate?
What identity does it claim?
Which signer will sign it?
Which DNS/IP names are inside it?
Does that match real infrastructure?
What will break if I do not approve it?
What security risk exists if I approve it?
```

That mindset is what separates safe production troubleshooting from risky cluster operations.
