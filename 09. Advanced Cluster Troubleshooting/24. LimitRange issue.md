# LimitRange Issue - Advanced Cluster Troubleshooting for OpenShift Administration

> Target audience: Advanced OpenShift administrators, SREs, platform engineers, L3 support engineers, and Red Hat exam/lab candidates.  
> Skill level: Senior / 10+ years practical administration style.  
> Scope: OpenShift 4.x / Kubernetes namespaces, projects, LimitRange, ResourceQuota, pod admission, scheduling, resource defaults, HPA behavior, PVC limits, troubleshooting, and remediation.

---

## 1. What is a LimitRange?

A `LimitRange` is a namespace-scoped policy object used to control resource boundaries for objects created inside a project/namespace.

In OpenShift, a project is a Kubernetes namespace with extra OpenShift metadata and access-control behavior. A `LimitRange` is normally created by a cluster administrator or automation such as a project template. It is used to define allowed minimums, maximums, defaults, and request-to-limit ratios for resources such as CPU, memory, storage, and in OpenShift-specific cases image/image stream constraints.

A `LimitRange` can control resources at these levels:

- `Container`
- `Pod`
- `PersistentVolumeClaim`
- OpenShift image-related resources in supported OpenShift contexts

Common uses:

- Force every container to have CPU and memory requests.
- Force every container to have CPU and memory limits.
- Prevent users from creating extremely large pods.
- Prevent tiny requests that cause unrealistic scheduling and noisy-neighbor problems.
- Set default requests and limits when application teams forget them.
- Prevent PVCs from requesting less than or more than allowed storage.
- Support ResourceQuota enforcement by injecting defaults.

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: project-resource-limits
  namespace: demo
spec:
  limits:
  - type: Container
    min:
      cpu: 50m
      memory: 64Mi
    max:
      cpu: "2"
      memory: 2Gi
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
    maxLimitRequestRatio:
      cpu: "10"
      memory: "4"
```

In this example:

- A container request below `50m` CPU or `64Mi` memory is rejected.
- A container limit above `2` CPU or `2Gi` memory is rejected.
- If the workload does not specify a request, OpenShift/Kubernetes injects `100m` CPU and `128Mi` memory.
- If the workload does not specify a limit, OpenShift/Kubernetes injects `500m` CPU and `512Mi` memory.
- If limit/request ratio is too high, the pod is rejected.

## 2. Why LimitRange issues are common in advanced OpenShift troubleshooting

LimitRange issues are common because they happen very early in the workload lifecycle. Many administrators initially look at pod logs, node health, image pulls, or scheduler events, but the pod might never be admitted by the API server.

A LimitRange problem can look like:

- Deployment creates no pods.
- ReplicaSet shows `FailedCreate` events.
- Job or CronJob does not create pods.
- Helm chart installation fails.
- Operator operand creation fails.
- Application works in one namespace but fails in another.
- Pod is rejected with `403 Forbidden`.
- Pod is created but has unexpected CPU/memory values.
- HPA behaves strangely because requests were defaulted unexpectedly.
- Pods start getting `OOMKilled` after a project template change.
- Pods remain `Pending` because default requests are too high for available nodes.
- PVC creation fails because requested storage violates min/max rules.

A senior OpenShift administrator must immediately decide whether the issue is:

1. **Admission-time rejection** - API server rejects the object.
2. **Defaulting surprise** - object is admitted, but mutated with default values.
3. **Scheduling failure** - pod exists but cannot fit on nodes due to requests.
4. **Runtime failure** - pod runs but is killed/throttled due to limits.
5. **Quota conflict** - LimitRange and ResourceQuota combine to block the workload.
6. **Policy propagation problem** - project template or GitOps applied a bad LimitRange across projects.

## 3. LimitRange versus ResourceQuota

Many production incidents happen because engineers confuse `LimitRange` and `ResourceQuota`.

| Feature | LimitRange | ResourceQuota |
|---|---|---|
| Scope | Namespace/project | Namespace/project |
| Controls | Per object / per pod / per container / per PVC | Total namespace consumption |
| Example | One container cannot exceed 2 CPU | All pods in namespace cannot exceed 20 CPU requests |
| Can inject defaults? | Yes | No |
| Can reject individual oversized pod? | Yes | Indirectly |
| Can restrict object count? | No | Yes |
| Typical error | `minimum cpu usage per Container is...` | `exceeded quota: compute-resources` |
| Main function | Guardrail per workload | Budget for whole project |

Simple analogy:

- `LimitRange` says: “One container cannot be too small or too large.”
- `ResourceQuota` says: “The entire project cannot consume more than this total amount.”

Both are often used together:

```text
LimitRange  -> sets per-container defaults and boundaries
ResourceQuota -> controls total project resource budget
```

Example combined behavior:

```yaml
# LimitRange injects defaults
request: 100m CPU, 128Mi memory
limit: 500m CPU, 512Mi memory

# ResourceQuota caps namespace total
requests.cpu: 4
requests.memory: 8Gi
limits.cpu: 8
limits.memory: 16Gi
```

If a deployment scales to many replicas, each defaulted pod consumes quota. The application team might say, “We did not set any requests,” but the LimitRange did it for them.

## 4. Where LimitRange fits in the request flow

When a user creates a pod, deployment, job, or PVC, the object goes through the API server admission chain.

For a Deployment:

```text
User / CI / Helm / Operator
        |
        v
OpenShift API server
        |
        v
Authentication and authorization
        |
        v
Admission chain
        |
        +--> Security admission / SCC / Pod Security Admission
        +--> LimitRanger admission
        +--> ResourceQuota admission
        +--> Other admission plugins/webhooks
        |
        v
Object stored in etcd
        |
        v
Controller creates ReplicaSet/Pod
        |
        v
Scheduler places pod on node
        |
        v
Kubelet + CRI-O starts container
```

Important point:

If the workload violates LimitRange, the object may be rejected before the pod ever reaches the scheduler or kubelet.

For a Deployment, the Deployment object itself may be created successfully, but the ReplicaSet fails to create pods. That is why the administrator must check ReplicaSet events, not only Deployment status.

## 5. Important LimitRange fields

### 5.1 `type`

Defines which object kind the rule applies to.

Common values:

```yaml
type: Container
type: Pod
type: PersistentVolumeClaim
```

### 5.2 `min`

Minimum allowed request or limit for the selected type.

Example:

```yaml
min:
  cpu: 100m
  memory: 64Mi
```

A container requesting `50m` CPU violates this rule.

### 5.3 `max`

Maximum allowed request or limit.

Example:

```yaml
max:
  cpu: "2"
  memory: 2Gi
```

A container with memory limit `4Gi` violates this rule.

### 5.4 `defaultRequest`

Default request injected when a container does not define a request.

Example:

```yaml
defaultRequest:
  cpu: 100m
  memory: 128Mi
```

This affects scheduling and quota accounting.

### 5.5 `default`

Default limit injected when a container does not define a limit.

Example:

```yaml
default:
  cpu: 500m
  memory: 512Mi
```

This affects runtime behavior. Memory limit can cause `OOMKilled`; CPU limit can cause throttling.

### 5.6 `maxLimitRequestRatio`

Controls the maximum allowed ratio between limit and request.

Example:

```yaml
maxLimitRequestRatio:
  cpu: "10"
```

If request is `100m`, CPU limit cannot exceed `1` CPU when ratio is `10`.

Calculation:

```text
limit / request <= maxLimitRequestRatio
```

So:

```text
1000m / 100m = 10 -> allowed
2000m / 100m = 20 -> rejected
```

## 6. Common symptoms and what they really mean

### 6.1 Pod creation fails with `Forbidden`

Typical event:

```text
Error creating: pods "web-xxxx" is forbidden:
minimum cpu usage per Container is 100m, but request is 50m
```

Meaning:

- API admission rejected the pod.
- The pod might not exist.
- Check ReplicaSet or Job events.

Commands:

```bash
oc get deploy -n demo
oc get rs -n demo
oc describe rs <replicaset-name> -n demo
oc get events -n demo --sort-by=.lastTimestamp
oc get limitrange -n demo
oc describe limitrange -n demo
```

### 6.2 Deployment exists but no pods are created

Deployment may show:

```text
0 available / 0 ready
```

ReplicaSet events may show:

```text
Warning  FailedCreate  replicaset-controller  Error creating: pods "app-xxx" is forbidden: ...
```

This is a classic sign that the Deployment object was accepted, but pod template admission failed.

Troubleshoot like this:

```bash
NS=demo
APP=myapp

oc get deploy $APP -n $NS -o wide
oc describe deploy $APP -n $NS
oc get rs -n $NS -l app=$APP
oc describe rs -n $NS
oc get events -n $NS --sort-by=.lastTimestamp | tail -30
```

### 6.3 Helm install fails

Typical Helm output:

```text
Error: INSTALLATION FAILED: pods "app-test" is forbidden:
maximum memory usage per Container is 1Gi, but limit is 2Gi
```

Meaning:

- Chart values define resources outside namespace policy.
- Helm itself is not the root cause.
- Fix `values.yaml` or namespace LimitRange.

### 6.4 Operator install succeeds but operand fails

The Operator pod may be running, but the application managed by the Operator fails to create.

Look at:

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc logs deploy/<operator-controller> -n <operator-namespace>
oc get events -n <operand-namespace> --sort-by=.lastTimestamp
oc describe limitrange -n <operand-namespace>
```

Operators often create StatefulSets, Deployments, Jobs, or PVCs. If the operand namespace has strict LimitRange rules, the Operator-created resources can be rejected.

### 6.5 Pod exists but resources are different from YAML

Example submitted pod:

```yaml
resources: {}
```

Actual admitted pod:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

This means LimitRange defaulting mutated the pod at admission time.

Check:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.containers[].resources'
oc describe limitrange -n <ns>
```

### 6.6 Pod is `Pending` after LimitRange was added

The pod was admitted, but default requests might be too high for available nodes.

Check:

```bash
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc adm top nodes
oc get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
```

Typical scheduler event:

```text
0/6 nodes are available: 6 Insufficient cpu
```

Meaning:

- LimitRange default request increased pod scheduling footprint.
- Scheduler uses requests, not actual usage, for placement.

### 6.7 Pod starts but gets `OOMKilled`

LimitRange may have injected a memory limit that is too low.

Check:

```bash
oc describe pod <pod> -n <ns>
oc logs <pod> -n <ns> --previous
oc adm top pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}{"\n"}'
oc get pod <pod> -n <ns> -o jsonpath='{.spec.containers[*].resources}{"\n"}'
```

Typical status:

```text
Last State: Terminated
Reason: OOMKilled
Exit Code: 137
```

Meaning:

- The process exceeded the memory cgroup limit.
- The limit may be explicitly set by the app manifest or injected by LimitRange.

### 6.8 CPU throttling after default limit injection

CPU limits are enforced by Linux cgroups. A low CPU limit can throttle an application even if nodes have free CPU.

Check application symptoms:

- High latency
- Slow startup
- Readiness probe failures
- Timeouts under load

Useful commands:

```bash
oc adm top pod -n <ns>
oc get pod <pod> -n <ns> -o yaml | yq '.spec.containers[].resources'
```

If cluster monitoring is available, query CPU throttling metrics in Prometheus:

```promql
rate(container_cpu_cfs_throttled_seconds_total{namespace="demo", pod=~"myapp-.*"}[5m])
```

### 6.9 PVC creation fails

Typical error:

```text
persistentvolumeclaims "data" is forbidden:
minimum storage usage per PersistentVolumeClaim is 2Gi, but request is 1Gi
```

Check:

```bash
oc get limitrange -n <ns>
oc describe limitrange -n <ns>
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
```

## 7. Fast triage checklist

Use this when you are on an incident bridge and need quick direction.

```bash
# 1. Select namespace
NS=<namespace>

# 2. Check LimitRange and ResourceQuota
oc get limitrange -n $NS
oc describe limitrange -n $NS
oc get resourcequota -n $NS
oc describe resourcequota -n $NS

# 3. Check workload status
oc get deploy,sts,ds,job,cronjob,pod,pvc -n $NS

# 4. Check events
oc get events -n $NS --sort-by=.lastTimestamp | tail -50

# 5. For Deployment/StatefulSet, check lower-level controller
oc get rs -n $NS
oc describe rs <rs-name> -n $NS

# 6. Inspect admitted resources on existing pod
oc get pod <pod> -n $NS -o yaml | yq '.spec.containers[].resources'

# 7. Test with server-side dry run
oc apply -f workload.yaml -n $NS --dry-run=server
```

Key decision:

```text
Forbidden at create/update time -> LimitRange/Quota/admission issue
Pending after creation          -> Scheduler/resource capacity issue
Running then OOMKilled          -> Runtime memory limit issue
Running but slow/throttled      -> CPU limit/throttling issue
```

## 8. Deep diagnostic workflow

### Step 1: Confirm the namespace policy

```bash
NS=demo

oc get limitrange -n $NS -o wide
oc describe limitrange -n $NS
oc get limitrange -n $NS -o yaml
```

Look for:

- `type: Container`
- `type: Pod`
- `type: PersistentVolumeClaim`
- `min`
- `max`
- `default`
- `defaultRequest`
- `maxLimitRequestRatio`

Also check quota:

```bash
oc get quota -n $NS
oc describe quota -n $NS
```

Why both? Because a pod may pass LimitRange but fail ResourceQuota, or LimitRange defaults may cause ResourceQuota exhaustion.

---

### Step 2: Find the exact rejection message

Events are your best friend.

```bash
oc get events -n $NS --sort-by=.lastTimestamp
```

For Deployments:

```bash
oc get deploy -n $NS
oc get rs -n $NS
oc describe rs <replicaset> -n $NS
```

For StatefulSets:

```bash
oc describe sts <statefulset> -n $NS
oc get events -n $NS --sort-by=.lastTimestamp
```

For Jobs:

```bash
oc describe job <job> -n $NS
oc get events -n $NS --sort-by=.lastTimestamp
```

For CronJobs:

```bash
oc describe cronjob <cronjob> -n $NS
oc get jobs -n $NS
oc describe job <job-created-by-cronjob> -n $NS
```

---

### Step 3: Use server-side dry-run before applying changes

This is very useful in production because it tests API admission without creating the object.

```bash
oc apply -f deployment.yaml -n $NS --dry-run=server
```

If it fails, you get the admission error immediately.

Example:

```text
Error from server (Forbidden): error when creating "deployment.yaml":
pods "web" is forbidden: minimum memory usage per Container is 128Mi, but request is 64Mi
```

---

### Step 4: Compare submitted manifest with admitted pod

The original Deployment might not show defaulted values in the pod template exactly as expected. Always inspect the actual pod:

```bash
oc get pod <pod> -n $NS -o yaml | yq '.spec.containers[] | {name: .name, resources: .resources}'
```

Without `yq`:

```bash
oc get pod <pod> -n $NS -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{.resources}{"\n---\n"}{end}'
```

---

### Step 5: Check whether the issue is caused by a project template

In many OpenShift environments, default `LimitRange` objects are inserted into every new project through the project request template.

Check cluster project template configuration:

```bash
oc get project.config.openshift.io/cluster -o yaml
```

Look for:

```yaml
spec:
  projectRequestTemplate:
    name: project-request
```

Find the template:

```bash
oc get template -A | grep project-request
oc get template project-request -n openshift-config -o yaml
```

Search for `LimitRange` inside it:

```bash
oc get template project-request -n openshift-config -o yaml | grep -n "LimitRange" -A80
```

If the bad LimitRange comes from the project template, fixing only one namespace might not be enough. You must correct the template and then decide whether to patch existing projects.

## 9. Common LimitRange failure scenarios with fixes

### Scenario 1: Missing requests or limits

#### Symptom

```text
pods "app" is forbidden: failed quota: compute-resources:
must specify requests.cpu, requests.memory, limits.cpu, limits.memory
```

This message often comes from ResourceQuota, but the solution might involve LimitRange defaults.

#### Root cause

The namespace has quota requiring CPU/memory requests and limits. The application manifest does not define them. If no LimitRange injects defaults, admission fails.

#### Fix option A: Add resources to workload

```bash
oc set resources deployment/app -n demo \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi
```

#### Fix option B: Add a LimitRange default

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-compute
  namespace: demo
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
```

Apply:

```bash
oc apply -f default-compute.yaml
```

#### Senior note

Do not blindly add defaults without capacity planning. Default requests affect scheduler placement and quota consumption.

---

### Scenario 2: Container request is below minimum

#### Symptom

```text
minimum cpu usage per Container is 100m, but request is 50m
```

#### Root cause

LimitRange has:

```yaml
min:
  cpu: 100m
```

But the workload has:

```yaml
requests:
  cpu: 50m
```

#### Fix

Patch workload:

```bash
oc set resources deployment/web -n demo --requests=cpu=100m,memory=128Mi
```

Or edit YAML:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
```

#### When to change LimitRange instead

Change the LimitRange only if the minimum is unrealistic for the platform. For example, requiring `500m` CPU minimum for every sidecar-heavy microservice namespace might waste capacity.

---

### Scenario 3: Container limit is above maximum

#### Symptom

```text
maximum memory usage per Container is 1Gi, but limit is 2Gi
```

#### Root cause

Workload requests a limit higher than namespace policy.

#### Fix option A: Reduce workload limit

```bash
oc set resources deployment/api -n demo --limits=memory=1Gi
```

#### Fix option B: Increase LimitRange maximum

```bash
oc edit limitrange project-resource-limits -n demo
```

Change:

```yaml
max:
  memory: 2Gi
```

#### Senior note

Increasing max memory can cause node pressure if many workloads use the new upper bound. Check cluster allocatable memory and quota before changing.

---

### Scenario 4: Limit/request ratio violation

#### Symptom

```text
cpu max limit to request ratio per Container is 10, but provided ratio is 20
```

#### Root cause

Example:

```yaml
requests:
  cpu: 100m
limits:
  cpu: "2"
```

Calculation:

```text
2 CPU / 100m = 2000m / 100m = 20
```

If `maxLimitRequestRatio.cpu` is `10`, this fails.

#### Fix option A: Increase request

```yaml
resources:
  requests:
    cpu: 200m
  limits:
    cpu: "2"
```

Now:

```text
2000m / 200m = 10
```

#### Fix option B: Lower limit

```yaml
resources:
  requests:
    cpu: 100m
  limits:
    cpu: "1"
```

Now:

```text
1000m / 100m = 10
```

#### Senior note

High CPU limit with tiny CPU request can create noisy-neighbor behavior. Ratio rules are useful in shared clusters.

---

### Scenario 5: Pod-level maximum violation

#### Symptom

```text
maximum cpu usage per Pod is 2, but total limit is 3
```

#### Root cause

LimitRange includes a `Pod` type maximum:

```yaml
- type: Pod
  max:
    cpu: "2"
    memory: 2Gi
```

The pod has multiple containers:

```text
app container limit: 1500m
sidecar limit: 1000m
agent limit: 500m
Total: 3000m = 3 CPU
```

#### Fix

Reduce total pod limits or increase pod-level max.

Check all containers:

```bash
oc get pod <pod> -n demo -o jsonpath='{range .spec.containers[*]}{.name}{" requests="}{.resources.requests}{" limits="}{.resources.limits}{"\n"}{end}'
```

#### Senior note

Service mesh sidecars, logging agents, and security sidecars can push a pod over pod-level limits even when the main app container looks correct.

---

### Scenario 6: Defaults cause ResourceQuota exhaustion

#### Symptom

```text
exceeded quota: compute-resources, requested: requests.cpu=500m, used: requests.cpu=3900m, limited: requests.cpu=4
```

#### Root cause

LimitRange defaulted every new pod to `500m` CPU request. Namespace quota allows only `4` CPU. Scaling beyond 8 replicas fails.

#### Check

```bash
oc describe quota -n demo
oc describe limitrange -n demo
oc get deploy app -n demo -o yaml | yq '.spec.replicas, .spec.template.spec.containers[].resources'
```

#### Fix options

1. Lower default request in LimitRange.
2. Set realistic explicit requests on workload.
3. Increase ResourceQuota if the namespace genuinely needs more.
4. Reduce replicas.
5. Split workloads across namespaces with separate quotas.

Example patch workload:

```bash
oc set resources deployment/app -n demo \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi
```

---

### Scenario 7: Defaults make pods unschedulable

#### Symptom

```text
0/5 nodes are available: 5 Insufficient memory
```

#### Root cause

LimitRange default memory request is too high. Scheduler only considers requests, not actual usage.

Example:

```yaml
defaultRequest:
  memory: 2Gi
```

A 10-replica deployment now requests 20Gi memory even if actual usage is 200Mi per pod.

#### Check

```bash
oc describe pod <pod> -n demo
oc get pod <pod> -n demo -o yaml | yq '.spec.containers[].resources.requests'
oc get nodes -o custom-columns=NAME:.metadata.name,ALLOCATABLE_MEMORY:.status.allocatable.memory
```

#### Fix

Set workload-specific realistic requests:

```bash
oc set resources deployment/app -n demo --requests=cpu=100m,memory=256Mi
```

Or adjust namespace default after impact analysis.

---

### Scenario 8: Default memory limit causes OOMKilled

#### Symptom

```text
Reason: OOMKilled
Exit Code: 137
```

#### Root cause

LimitRange injected a memory limit too low for the app.

Example:

```yaml
default:
  memory: 256Mi
```

Java, Node.js, databases, build pods, and data-processing jobs commonly hit this.

#### Fix

Set explicit app memory limit:

```bash
oc set resources deployment/api -n demo --limits=memory=1Gi --requests=memory=512Mi
```

Then restart rollout:

```bash
oc rollout restart deployment/api -n demo
oc rollout status deployment/api -n demo
```

#### Senior note

Do not fix OOMKilled only by increasing limits. Check memory leak, heap sizing, JVM flags, application profile, and node memory pressure.

For Java:

```bash
JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
```

---

### Scenario 9: CPU limit causes throttling and readiness failures

#### Symptom

- App starts slowly.
- Readiness probe fails.
- Latency increases under load.
- CPU usage appears below node capacity.

#### Root cause

LimitRange injected a low CPU limit:

```yaml
default:
  cpu: 200m
```

The app needs CPU bursts but is throttled at 200m.

#### Fix

Set higher limit or remove CPU limit strategy based on platform policy.

```bash
oc set resources deployment/api -n demo --requests=cpu=200m --limits=cpu=1
```

#### Senior note

Many SRE teams prefer CPU requests without CPU limits for latency-sensitive services, while still enforcing memory limits. Whether this is allowed depends on your platform governance.

---

### Scenario 10: HPA cannot calculate CPU utilization

#### Symptom

```text
failed to get cpu utilization: missing request for cpu
```

#### Root cause

HPA CPU percentage requires CPU requests. If no CPU request exists and no LimitRange defaultRequest injects it, HPA cannot calculate utilization percentage.

#### Fix

Set CPU request:

```bash
oc set resources deployment/web -n demo --requests=cpu=100m,memory=128Mi --limits=cpu=500m,memory=512Mi
```

Or define LimitRange defaultRequest.

#### Senior note

If LimitRange defaultRequest is too low, HPA may scale too aggressively. If too high, HPA may scale too slowly.

Example:

```text
Actual CPU usage: 100m
Request: 100m
HPA utilization: 100%

Actual CPU usage: 100m
Request: 500m
HPA utilization: 20%
```

---

### Scenario 11: Multiple LimitRanges exist in the same namespace

#### Symptom

- Defaults look inconsistent.
- One application receives unexpected values.
- Troubleshooting is confusing because more than one LimitRange matches.

#### Root cause

Namespace has multiple `LimitRange` objects.

Check:

```bash
oc get limitrange -n demo
oc get limitrange -n demo -o yaml
```

#### Fix

Use a single well-defined LimitRange per namespace unless there is a strong reason for multiple objects.

```bash
oc delete limitrange old-defaults -n demo
```

#### Senior note

Multiple LimitRanges can make defaulting behavior hard to reason about. Standardize with GitOps and policy review.

---

### Scenario 12: Existing pods are not changed after LimitRange update

#### Symptom

You update the LimitRange, but existing pods still show old resource values.

#### Root cause

LimitRange validation/defaulting happens at admission time. Existing pods are not automatically mutated.

#### Fix

Restart or recreate pods through their controller:

```bash
oc rollout restart deployment/app -n demo
oc rollout status deployment/app -n demo
```

For StatefulSet:

```bash
oc rollout restart statefulset/db -n demo
```

For standalone pod:

```bash
oc delete pod <pod> -n demo
```

---

### Scenario 13: PVC request violates LimitRange

#### Symptom

```text
minimum storage usage per PersistentVolumeClaim is 2Gi, but request is 1Gi
```

or:

```text
maximum storage usage per PersistentVolumeClaim is 50Gi, but request is 100Gi
```

#### Root cause

Namespace LimitRange includes:

```yaml
- type: PersistentVolumeClaim
  min:
    storage: 2Gi
  max:
    storage: 50Gi
```

#### Fix

Change PVC request:

```yaml
resources:
  requests:
    storage: 2Gi
```

Or change LimitRange if policy is wrong:

```bash
oc edit limitrange pvc-limits -n demo
```

#### Senior note

Do not confuse PVC LimitRange failure with storage class binding failure. LimitRange failure is admission-time. Storage binding failure usually appears as PVC `Pending` after creation.

---

### Scenario 14: Build pods fail because default limit is too low

#### Symptom

OpenShift BuildConfig or pipeline build fails, often with OOMKilled or pod creation failure.

Check:

```bash
oc get builds -n demo
oc describe build <build-name> -n demo
oc get pods -n demo | grep build
oc describe pod <build-pod> -n demo
oc describe limitrange -n demo
```

#### Root cause

Build pods inherit namespace LimitRange defaults. Image builds often need more memory/CPU than normal app pods.

#### Fix options

- Set explicit build resource requests/limits where supported.
- Use a separate build namespace with appropriate LimitRange.
- Adjust default memory limit if it is too low for common builds.

### Scenario 15: CronJob fails silently at schedule time

#### Symptom

CronJob exists, but Jobs fail or no pods are created.

Check:

```bash
oc get cronjob -n demo
oc get job -n demo
oc describe job <job> -n demo
oc get events -n demo --sort-by=.lastTimestamp
```

#### Root cause

The pod template inside the CronJob violates LimitRange.

#### Fix

Patch the CronJob container resources:

```bash
oc patch cronjob backup -n demo --type='json' -p='[
  {"op":"add","path":"/spec/jobTemplate/spec/template/spec/containers/0/resources","value":{
    "requests":{"cpu":"100m","memory":"128Mi"},
    "limits":{"cpu":"500m","memory":"512Mi"}
  }}
]'
```

## 10. Error message decoding table

| Error / Symptom | Likely Root Cause | Check | Fix |
|---|---|---|---|
| `minimum cpu usage per Container is...` | Request below `min.cpu` | `oc describe limits` | Increase request or lower min |
| `maximum memory usage per Container is...` | Limit above `max.memory` | Workload resources | Lower limit or raise max |
| `max limit to request ratio...` | Limit/request ratio too high | `maxLimitRequestRatio` | Raise request or lower limit |
| `must specify requests.cpu` | ResourceQuota requires request, no default | Quota + LimitRange | Add requests or LimitRange defaultRequest |
| `exceeded quota` after adding LimitRange | Defaults consume quota | Quota used/hard | Tune defaults, quota, or replicas |
| Pods `Pending` with insufficient CPU | Default request too high | Pod requests + node allocatable | Reduce request or add capacity |
| `OOMKilled` | Memory limit too low | Pod limit + previous logs | Increase limit or fix app memory |
| Readiness probe fails under load | CPU throttling | CPU limit + app latency | Raise/remove CPU limit |
| PVC creation forbidden | PVC storage min/max violation | PVC LimitRange | Change requested storage |
| Works in namespace A, fails in B | Different LimitRange/quota | Compare namespace policies | Align policies |

## 12. How LimitRange affects QoS classes

Kubernetes pod Quality of Service class depends on requests and limits.

| QoS Class | Condition |
|---|---|
| `Guaranteed` | Every container has CPU and memory request equal to limit |
| `Burstable` | At least one request/limit exists, but not all are equal |
| `BestEffort` | No requests or limits at all |

LimitRange defaults can change QoS.

Example without LimitRange:

```yaml
resources: {}
```

QoS:

```text
BestEffort
```

After LimitRange default injection:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

QoS:

```text
Burstable
```

If defaults make request equal to limit:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

QoS:

```text
Guaranteed
```

Troubleshooting command:

```bash
oc get pod <pod> -n demo -o jsonpath='{.status.qosClass}{"\n"}'
```

Senior note:

QoS class affects eviction priority during node pressure. A poorly planned LimitRange can unexpectedly change eviction behavior across a namespace.

## 13. LimitRange and scheduler behavior

The scheduler uses resource **requests**, not limits, when deciding whether a pod can fit on a node.

Example:

```yaml
requests:
  cpu: 500m
  memory: 1Gi
limits:
  cpu: 2
  memory: 2Gi
```

Scheduling footprint:

```text
CPU: 500m
Memory: 1Gi
```

Runtime ceiling:

```text
CPU limit: 2 CPU
Memory limit: 2Gi
```

If LimitRange injects high default requests, cluster bin-packing becomes inefficient.

Check node allocatable:

```bash
oc get nodes -o custom-columns=NODE:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
```

Check pod requests:

```bash
oc describe node <node-name>
```

Look at allocated resources section:

```text
Allocated resources:
  Resource           Requests      Limits
  cpu                3500m (87%)   9000m (225%)
  memory             12Gi (75%)    30Gi (187%)
```

Senior note:

Limits can exceed node capacity because CPU/memory limits are not used the same way as requests for scheduling. Requests must fit. Limits can be overcommitted, except for non-overcommittable resources such as hugepages and some extended resources.

## 14. LimitRange and HPA behavior

Horizontal Pod Autoscaler uses metrics such as CPU utilization. For CPU percentage-based HPA, utilization is calculated against CPU request.

Formula:

```text
CPU utilization percentage = current CPU usage / CPU request * 100
```

Example:

```text
Current CPU usage: 200m
CPU request: 100m
Utilization: 200%
```

Another example:

```text
Current CPU usage: 200m
CPU request: 500m
Utilization: 40%
```

Therefore, LimitRange `defaultRequest.cpu` directly impacts HPA behavior if workloads do not specify explicit requests.

Troubleshoot:

```bash
oc get hpa -n demo
oc describe hpa <hpa-name> -n demo
oc get pod -n demo -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.containers[*].resources.requests.cpu}{"\n"}{end}'
```

Fix:

```bash
oc set resources deployment/web -n demo --requests=cpu=200m,memory=256Mi --limits=cpu=1,memory=512Mi
```

Senior note:

For HPA-enabled workloads, do not rely blindly on namespace defaults. Set explicit requests based on real metrics.

## 15. LimitRange and memory troubleshooting

Memory requests and limits behave differently.

### Memory request

- Used by scheduler.
- Used for placement decisions.
- Does not stop the process from using more memory.

### Memory limit

- Enforced by cgroups.
- Container can be killed if it exceeds limit.
- Usually appears as `OOMKilled` with exit code `137`.

Troubleshoot memory:

```bash
oc adm top pod -n demo
oc describe pod <pod> -n demo
oc logs <pod> -n demo --previous
oc get pod <pod> -n demo -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}{"\n"}'
```

Check actual limits:

```bash
oc get pod <pod> -n demo -o yaml | yq '.spec.containers[].resources.limits.memory'
```

Inside container, if allowed:

```bash
cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes
```

Senior note:

If the app uses memory-backed `emptyDir`, that memory can count against the pod/container memory limit. This can cause confusing OOMKilled events even when application heap appears normal.

## 16. LimitRange and CPU troubleshooting

CPU request:

- Used by scheduler.
- Influences CPU shares.
- Important for HPA calculations.

CPU limit:

- Enforced through CFS quota.
- Can throttle application.
- Throttling can cause latency and probe failures.

Check resources:

```bash
oc get pod <pod> -n demo -o yaml | yq '.spec.containers[].resources'
```

Check live CPU:

```bash
oc adm top pod <pod> -n demo
```

Prometheus query for throttling:

```promql
rate(container_cpu_cfs_throttled_seconds_total{namespace="demo", pod=~"web-.*"}[5m])
```

Senior note:

Low CPU limits can hurt more than low CPU requests. Requests influence scheduling; limits enforce hard throttling.

## 19. Remediation strategy in production

### 19.1 Do not immediately delete the LimitRange

Deleting a LimitRange may allow uncontrolled workloads, quota bypass problems, or poor scheduling behavior.

Instead:

1. Identify the exact workload violation.
2. Confirm whether the policy or workload is wrong.
3. Patch the workload if only one app is wrong.
4. Patch the LimitRange if the policy is globally wrong.
5. Update GitOps/project template source of truth.
6. Restart workloads only when necessary.
7. Monitor quota, scheduling, OOMKilled, and throttling after change.

### 19.2 Decide workload fix versus platform policy fix

| Situation | Better Fix |
|---|---|
| One app has unrealistic limit | Fix app manifest |
| All apps fail due to too-high minimum | Fix LimitRange |
| HPA workloads scaling badly | Set explicit requests per app |
| Build pods OOMKilled | Separate build policy or adjust build resources |
| Quota exhausted due to default requests | Tune defaults or quota |
| New projects inherit bad policy | Fix project template / GitOps source |

### 19.3 Patch example: update LimitRange default memory

```bash
oc patch limitrange default-app-limits -n demo --type='json' -p='[
  {"op":"replace","path":"/spec/limits/0/default/memory","value":"1Gi"},
  {"op":"replace","path":"/spec/limits/0/defaultRequest/memory","value":"256Mi"}
]'
```

### 19.4 Patch example: update deployment resources

```bash
oc set resources deployment/api -n demo \
  --requests=cpu=250m,memory=256Mi \
  --limits=cpu=1,memory=1Gi
```

### 19.5 Rollout safely

```bash
oc rollout status deployment/api -n demo
oc get pods -n demo -w
```

If bad rollout:

```bash
oc rollout undo deployment/api -n demo
```

## 20. Senior troubleshooting examples

### Example A: Application fails only in production

#### Problem

Developer says:

```text
Same YAML works in dev but fails in prod.
```

#### Investigation

```bash
oc describe limitrange -n dev
oc describe limitrange -n prod
oc describe quota -n dev
oc describe quota -n prod
oc get events -n prod --sort-by=.lastTimestamp | tail -30
```

#### Finding

Dev has no LimitRange. Prod has:

```yaml
max:
  memory: 1Gi
```

Application YAML has:

```yaml
limits:
  memory: 2Gi
```

#### Resolution

Either lower application memory limit to 1Gi or approve a prod policy exception by increasing LimitRange max.

#### Senior conclusion

Not a node issue, not image issue, not OpenShift bug. This is namespace admission policy difference.

---

### Example B: Pods pending after namespace policy rollout

#### Problem

After applying a default LimitRange to all projects, many new pods are stuck `Pending`.

#### Investigation

```bash
oc get pods -A --field-selector=status.phase=Pending
oc describe pod <pending-pod> -n <ns>
oc get pod <pending-pod> -n <ns> -o yaml | yq '.spec.containers[].resources.requests'
oc describe nodes | grep -A5 "Allocated resources"
```

#### Finding

Default request is:

```yaml
defaultRequest:
  memory: 1Gi
```

Small workloads that previously had no requests now each request 1Gi. Nodes do not have enough allocatable memory.

#### Resolution

Reduce default memory request to `128Mi` or `256Mi`, then recreate affected pods.

```bash
oc patch limitrange default-app-limits -n demo --type='json' -p='[
  {"op":"replace","path":"/spec/limits/0/defaultRequest/memory","value":"256Mi"}
]'

oc rollout restart deployment/app -n demo
```

#### Senior conclusion

LimitRange did not directly make pods fail. It changed scheduler input by injecting requests.

---

### Example C: HPA scales unexpectedly

#### Problem

App scales from 2 to 20 replicas under moderate traffic.

#### Investigation

```bash
oc describe hpa web -n demo
oc get pod -n demo -l app=web -o jsonpath='{range .items[*]}{.metadata.name}{" cpu_request="}{.spec.containers[0].resources.requests.cpu}{"\n"}{end}'
oc describe limitrange -n demo
```

#### Finding

LimitRange default request is `50m`. Actual usage is around `100m` per pod.

HPA sees:

```text
100m / 50m = 200% utilization
```

#### Resolution

Set explicit CPU request based on real baseline:

```bash
oc set resources deployment/web -n demo --requests=cpu=200m,memory=256Mi --limits=cpu=1,memory=512Mi
```

#### Senior conclusion

HPA issue was caused by unrealistic default request, not traffic alone.

### Example D: Operator operand fails

#### Problem

An Operator installs successfully, but custom resource remains degraded.

#### Investigation

```bash
oc get csv -n openshift-operators
oc logs deploy/<operator-deployment> -n openshift-operators
oc get events -n app-namespace --sort-by=.lastTimestamp
oc describe limitrange -n app-namespace
```

#### Finding

Operator tries to create StatefulSet with PVC request `1Gi`, but namespace LimitRange requires minimum PVC storage `5Gi`.

#### Resolution

Patch custom resource storage size to `5Gi` or adjust namespace PVC LimitRange.

Operator is not broken. Its generated operand violates namespace policy.

## 21. LimitRange issue during OpenShift exams/labs

In lab or exam environments, LimitRange tasks usually test whether you can:

1. Create the correct namespace/project.
2. Create a valid `LimitRange` YAML.
3. Use correct `type` values: `Pod`, `Container`, `PersistentVolumeClaim`.
4. Use correct units: `m`, `Mi`, `Gi`.
5. Put the object in the correct namespace.
6. Verify using `oc describe limits`.
7. Avoid extra objects that violate the task requirement.

### Common exam mistakes

#### Mistake 1: Wrong namespace

```yaml
metadata:
  namespace: default
```

But task asks namespace `darpa`.

Fix:

```bash
oc apply -f limitrange.yaml -n darpa
```

or ensure YAML has:

```yaml
metadata:
  namespace: darpa
```

#### Mistake 2: Wrong resource type

Wrong:

```yaml
type: Containers
```

Correct:

```yaml
type: Container
```

#### Mistake 3: CPU and memory units mixed

Correct CPU examples:

```yaml
cpu: 100m
cpu: "1"
```

Correct memory examples:

```yaml
memory: 128Mi
memory: 1Gi
```

Avoid mistakes like:

```yaml
memory: 100m   # wrong intent; m is milli, not Mi memory
cpu: 100Mi     # invalid/wrong intent for CPU
```

#### Mistake 4: Default versus defaultRequest confusion

```yaml
defaultRequest:
  cpu: 100m
```

means request.

```yaml
default:
  cpu: 500m
```

means limit.

#### Mistake 5: Forgetting to verify

Always verify:

```bash
oc get limits -n <namespace>
oc describe limits -n <namespace>
```

## 23. Best practices for production LimitRange design

### 23.1 Use different policies for different namespace types

Do not use the same LimitRange for every namespace.

Suggested classes:

| Namespace Type | Example Policy |
|---|---|
| Small app/dev | Low defaults, moderate max |
| Production app | Realistic defaults, stricter ratio |
| Build/CI | Higher memory/CPU max |
| Data workloads | Higher memory and PVC max |
| Monitoring/logging | Explicit resources, avoid generic defaults |
| Operators | Validate vendor recommendations |

### 23.2 Avoid unrealistic default requests

Bad default:

```yaml
defaultRequest:
  cpu: "1"
  memory: 1Gi
```

This can waste cluster capacity for small workloads.

Better default for general microservices:

```yaml
defaultRequest:
  cpu: 100m
  memory: 128Mi
```

But always adjust based on real usage.

### 23.3 Do not set very low memory defaults

Bad:

```yaml
default:
  memory: 64Mi
```

This can break Java, Node.js, Python, build pods, and operators.

### 23.4 Be careful with CPU limits

CPU limits can introduce throttling. For latency-sensitive apps, consider a policy that requires CPU requests but does not force tiny CPU limits, depending on your organization’s governance model.

### 23.5 Use GitOps for policy consistency

Store LimitRange definitions in Git:

```text
cluster-config/
  namespaces/
    dev/
      limitrange.yaml
      resourcequota.yaml
    prod/
      limitrange.yaml
      resourcequota.yaml
```

Use Argo CD, OpenShift GitOps, or another controlled mechanism to apply changes.

### 23.6 Document exception process

Some workloads need exceptions:

- Databases
- JVM services
- Build pods
- ML workloads
- Logging/monitoring stack
- Operators

Have a clear process:

1. Team submits requested resources.
2. Platform team checks actual usage.
3. Quota and LimitRange are adjusted if justified.
4. Change is tracked in Git.

## 26. Senior admin notes and gotchas

1. **LimitRange is namespace-scoped.** If an app works in one project and fails in another, compare namespace policies first.
2. **A Deployment can exist even when pods cannot be created.** Always inspect ReplicaSet events.
3. **Default values are injected only during admission.** Existing pods do not automatically change after LimitRange update.
4. **Requests affect scheduling.** Limits affect runtime enforcement.
5. **Memory limits can kill containers.** CPU limits throttle containers.
6. **ResourceQuota and LimitRange interact heavily.** Defaults can help satisfy quota requirements but also consume quota.
7. **HPA depends on requests.** Bad default CPU requests can cause bad autoscaling decisions.
8. **Multiple LimitRanges are confusing.** Prefer one clear policy per namespace.
9. **Project templates can spread bad policy.** Check `project.config.openshift.io/cluster` and templates.
10. **Operators are not immune.** Operator-generated pods/PVCs must satisfy namespace LimitRange.
11. **PVC LimitRange is admission-time.** StorageClass binding issues happen after PVC exists.
12. **Do not delete policies under pressure.** Patch safely and preserve governance.

## 27. Practical incident response runbook

Use this as a production-ready runbook.

### Input

```bash
NS=<namespace>
WORKLOAD=<deployment-or-statefulset-or-job>
```

### Runbook

```bash
# 1. Capture namespace policy
oc get limitrange,quota -n $NS
oc describe limitrange -n $NS
oc describe quota -n $NS

# 2. Capture workload status
oc get deploy,sts,ds,job,cronjob,pod,pvc -n $NS

# 3. Capture recent events
oc get events -n $NS --sort-by=.lastTimestamp | tail -80

# 4. If Deployment, inspect ReplicaSets
oc get rs -n $NS
oc describe rs -n $NS

# 5. If pod exists, inspect resources and state
POD=$(oc get pod -n $NS --no-headers | awk 'NR==1{print $1}')
oc describe pod $POD -n $NS
oc get pod $POD -n $NS -o yaml | yq '.spec.containers[].resources'
oc get pod $POD -n $NS -o jsonpath='{.status.qosClass}{"\n"}'

# 6. Check usage if metrics are available
oc adm top pod -n $NS || true
oc adm top node || true
```

### Interpret

```text
Event says Forbidden + minimum/maximum/ratio -> LimitRange violation
Event says exceeded quota                  -> ResourceQuota issue, maybe caused by defaults
Pod Pending + Insufficient CPU/memory      -> requests/capacity/scheduling issue
Pod OOMKilled                              -> memory limit/runtime issue
High latency + low CPU limit               -> CPU throttling suspicion
```

### Fix examples

```bash
# Fix workload resources
oc set resources deployment/$WORKLOAD -n $NS \
  --requests=cpu=200m,memory=256Mi \
  --limits=cpu=1,memory=1Gi

# Restart workload
oc rollout restart deployment/$WORKLOAD -n $NS
oc rollout status deployment/$WORKLOAD -n $NS
```

## 28. Interview-level explanation

A LimitRange issue in OpenShift is usually an admission-control or resource-governance problem where a namespace policy rejects or mutates workload resource definitions. The administrator must check namespace `LimitRange`, `ResourceQuota`, workload events, and admitted pod resources. LimitRange can set minimum and maximum CPU/memory, default requests and limits, request-to-limit ratios, and PVC storage bounds. Failures often appear as `Forbidden` events on ReplicaSets, Jobs, or PVCs. Even when workloads are admitted, default requests can cause scheduling failures or quota exhaustion, while default limits can cause OOMKilled or CPU throttling at runtime. A senior admin troubleshoots by identifying whether the problem is admission-time, scheduling-time, or runtime, then decides whether to patch the workload, namespace policy, quota, project template, or cluster capacity.

## 30. Final summary

LimitRange is not just a small YAML object. In production OpenShift, it is a major resource governance control point. It can reject pods before creation, inject defaults that alter scheduling and quota behavior, cause OOMKilled or CPU throttling indirectly, and break Helm charts, Operators, Jobs, CronJobs, PVCs, and project templates when misconfigured.

For advanced troubleshooting, always remember:

```text
LimitRange controls individual object boundaries.
ResourceQuota controls total namespace budget.
Requests drive scheduling and HPA math.
Limits drive runtime enforcement.
Events reveal admission failures.
ReplicaSet/Job events reveal pod creation failures.
Existing pods do not change until recreated.
```

A 10-year experienced OpenShift administrator does not troubleshoot LimitRange issues by guessing. They follow the object lifecycle: admission, defaulting, quota accounting, scheduling, kubelet enforcement, and application behavior.
