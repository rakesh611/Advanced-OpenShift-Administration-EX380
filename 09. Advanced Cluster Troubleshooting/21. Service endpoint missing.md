# Service Endpoint Missing — Advanced OpenShift Cluster Troubleshooting

**Area:** Advanced Cluster Troubleshooting  
**Audience:** Advanced OpenShift Administration / L3 Support / SRE  
**Experience level:** 10+ years Linux, Kubernetes, OpenShift operations  
**Platform focus:** OpenShift Container Platform 4.x  
**Last updated:** 2026-07-03

---

## 1. What “Service endpoint missing” means

In OpenShift, a **Service** gives a stable virtual IP/DNS name in front of changing Pods. The Service itself does not run your application. It only forwards traffic to backend endpoints. Those endpoints are normally Pod IPs and ports selected by the Service selector.

When you see **Service endpoint missing**, it usually means one of these:

```text
Route / client / another Pod
        |
        v
Service exists
        |
        v
No ready backend endpoint found
        |
        v
Traffic cannot reach any application Pod
```

Typical symptoms:

```bash
oc describe svc <service> -n <namespace>
# Endpoints: <none>

oc get endpoints <service> -n <namespace>
# NAME      ENDPOINTS   AGE
# my-svc    <none>      10m

oc get endpointslice -n <namespace> -l kubernetes.io/service-name=<service>
# No resources found
# or slices exist but endpoint condition ready=false
```

For an OpenShift Route, the user-facing symptom is often:

```text
Application is not available
```

or HTTP 503 from the router because the Route points to a Service, but the Service has no usable backend endpoints.

In admission webhook cases, the symptom may look like:

```text
Internal error occurred: failed calling webhook ... no endpoints available for service "<webhook-service>"
```

That means the API server is trying to call a webhook Service, but the Service has no ready backend Pod.

## 2. Mental model: Route → Service → EndpointSlice → Pod → Container port

A senior administrator should always troubleshoot this layer by layer.

```text
External client
   |
   | DNS + router canonical hostname
   v
OpenShift Route
   |
   | route.spec.to.name + route.spec.port.targetPort
   v
Kubernetes Service
   |
   | service.spec.selector + service.spec.ports[].targetPort
   v
EndpointSlice / Endpoints
   |
   | ready backend IP:port list
   v
Pod IP
   |
   | container actually listening on target port
   v
Application process
```

Important rules:

1. A Service selector matches **Pod labels**, not Deployment labels, not ReplicaSet labels, and not Route labels.
2. Endpoints are namespace-scoped. A Service can automatically select Pods only inside the **same namespace**.
3. A Service with a selector is normally managed automatically by Kubernetes/OpenShift control plane controllers.
4. Modern clusters use **EndpointSlice** as the scalable backend object. The older `Endpoints` object may still be visible and useful for quick checks, but EndpointSlice gives better detail.
5. Pods that are not Ready are normally not used for Service traffic unless `publishNotReadyAddresses: true` is configured.
6. NetworkPolicy, DNS, OVN-Kubernetes, kube-proxy, or router issues can break traffic even when endpoints exist. But if endpoints are missing, fix endpoint generation first.

## 3. Quick triage command set

Set variables first:

```bash
NS=<namespace>
SVC=<service-name>
```

Run these commands in order:

```bash
oc get svc "$SVC" -n "$NS" -o wide
oc describe svc "$SVC" -n "$NS"

oc get endpoints "$SVC" -n "$NS" -o wide
oc get endpointslice -n "$NS" -l kubernetes.io/service-name="$SVC" -o wide

oc get pods -n "$NS" --show-labels
oc get pods -n "$NS" -o wide

oc get route -n "$NS"
oc describe route -n "$NS"

oc get events -n "$NS" --sort-by=.lastTimestamp | tail -50
```

Extract the Service selector:

```bash
oc get svc "$SVC" -n "$NS" -o jsonpath='{.spec.selector}{"\n"}'
```

Build a label selector string from the Service selector:

```bash
SELECTOR=$(oc get svc "$SVC" -n "$NS" \
  -o go-template='{{range $k,$v := .spec.selector}}{{printf "%s=%s," $k $v}}{{end}}' | sed 's/,$//')

echo "$SELECTOR"
oc get pods -n "$NS" -l "$SELECTOR" -o wide --show-labels
```

If this returns no Pods, you likely have a selector/label/namespace issue.

## 4. First classification: missing, unready, or unreachable?

Do not mix these three cases. They require different fixes.

| Case | What you see | Meaning | First area to inspect |
|---|---|---|---|
| Missing endpoints | `Endpoints: <none>` and no EndpointSlices or empty slices | Service found no matching ready backend | Selector, namespace, Pod labels, Pod status |
| Unready endpoints | EndpointSlice exists but `ready=false` / Pods show `0/1 Ready` | Pods match selector but are not ready for traffic | Readiness probe, app health, startup, config |
| Endpoints exist but traffic fails | EndpointSlice shows ready IP:port | Backend exists but path is broken | targetPort, app listening port, NetworkPolicy, OVN, router, TLS |

A common mistake is to jump to NetworkPolicy or OVN too early. If the Service has no endpoints, the problem is usually above the network dataplane: labels, selectors, Pods, readiness, or rollout.

## 5. Core objects involved

### 5.1 Service

A Service defines:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: 8080
```

Meaning:

```text
Clients connect to service/web on port 80.
The Service forwards to Pods in the same namespace with label app=web.
Traffic is sent to target port 8080 on those Pods.
```

Check it:

```bash
oc get svc web -n app -o yaml
oc describe svc web -n app
```

### 5.2 EndpointSlice

EndpointSlice is the modern object that stores backend endpoints for a Service.

Check EndpointSlices:

```bash
oc get endpointslice -n "$NS" -l kubernetes.io/service-name="$SVC"

oc get endpointslice -n "$NS" \
  -l kubernetes.io/service-name="$SVC" \
  -o yaml
```

Useful fields:

```yaml
endpoints:
- addresses:
  - 10.128.2.45
  conditions:
    ready: true
    serving: true
    terminating: false
  targetRef:
    kind: Pod
    name: web-7b6c8d9b9f-mx2pq
ports:
- name: http
  port: 8080
  protocol: TCP
```

If there are no EndpointSlices, the Service likely has no selector match, no Pods, or the selectorless Service is not manually configured.

If EndpointSlices exist but `ready: false`, then Pods are selected but not considered ready.

### 5.3 Endpoints

The legacy object is still useful for quick checks:

```bash
oc get endpoints "$SVC" -n "$NS" -o yaml
oc describe endpoints "$SVC" -n "$NS"
```

You may see:

```yaml
subsets:
- addresses:
  - ip: 10.128.2.45
    targetRef:
      kind: Pod
      name: web-xxx
  ports:
  - port: 8080
```

or:

```yaml
subsets: []
```

or no subsets at all.

For advanced troubleshooting, prefer EndpointSlice when you need readiness, terminating, and serving condition details.

## 6. Most common root causes

## 6.1 Service selector does not match Pod labels

This is the number one cause.

Example broken Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend
spec:
  selector:
    app: frontend
  ports:
  - port: 80
    targetPort: 8080
```

Actual Pods:

```bash
oc get pods -n app --show-labels
# NAME                        READY   STATUS    LABELS
# frontend-7b8d8f5c7d-abcde   1/1     Running   app=web,pod-template-hash=7b8d8f5c7d
```

Service wants:

```text
app=frontend
```

Pod has:

```text
app=web
```

Result:

```text
No matching Pods → no endpoints
```

### Diagnose

```bash
oc describe svc frontend -n app
oc get pods -n app --show-labels

SELECTOR=$(oc get svc frontend -n app \
  -o go-template='{{range $k,$v := .spec.selector}}{{printf "%s=%s," $k $v}}{{end}}' | sed 's/,$//')

oc get pods -n app -l "$SELECTOR" --show-labels
```

### Fix option A: fix Service selector

Use this when the existing Pod labels are correct and the Service is wrong.

```bash
oc patch svc frontend -n app --type merge \
  -p '{"spec":{"selector":{"app":"web"}}}'
```

### Fix option B: fix workload Pod template labels

Use this when the Service selector is the intended contract and the Deployment template is wrong.

```bash
oc patch deployment frontend -n app --type merge \
  -p '{"spec":{"template":{"metadata":{"labels":{"app":"frontend"}}}}}'
```

Then verify rollout:

```bash
oc rollout status deployment/frontend -n app
oc get pods -n app --show-labels
oc get endpoints frontend -n app
```

### Senior-level warning

Do not only label the current running Pod unless this is an emergency test:

```bash
oc label pod frontend-xxx app=frontend -n app --overwrite
```

That label disappears when the Pod is replaced. Fix the Deployment, DeploymentConfig, StatefulSet, DaemonSet, Job, or Operator-managed custom resource that creates the Pod.

## 6.2 Service created in the wrong namespace

A Service selector does not automatically select Pods from another namespace.

Example:

```text
Service: namespace app-prod
Pods:    namespace app-dev
```

The selector may look correct, but no endpoints appear because the Pods are not in the same namespace.

### Diagnose

```bash
oc get svc -A | grep frontend
oc get pods -A --show-labels | grep frontend

oc get svc frontend -n app-prod -o yaml
oc get pods -n app-prod --show-labels
oc get pods -n app-dev --show-labels
```

### Fix

Create the Service in the same namespace as the Pods:

```bash
oc get svc frontend -n app-prod -o yaml > frontend-svc.yaml
# edit metadata.namespace to app-dev, remove clusterIP/resourceVersion/uid/managedFields
oc apply -f frontend-svc.yaml
```

Or expose the correct workload from the correct namespace:

```bash
oc project app-dev
oc expose deployment/frontend --name=frontend --port=80 --target-port=8080
```

## 6.3 Pods are not Running

If Pods are Pending, CrashLoopBackOff, ImagePullBackOff, Error, Completed, or Evicted, endpoints may be absent.

### Diagnose

```bash
oc get pods -n "$NS" -o wide
oc describe pod <pod-name> -n "$NS"
oc logs <pod-name> -n "$NS" --all-containers
oc logs <pod-name> -n "$NS" --previous --all-containers
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -80
```

### Common Pod-level causes

| Pod state | Endpoint effect | Likely cause |
|---|---|---|
| Pending | No Pod IP yet, no endpoint | scheduling, quota, PVC, node selector, taints |
| ImagePullBackOff | Container not running, no ready endpoint | registry, pull secret, image name/tag |
| CrashLoopBackOff | Pod may exist but not ready | app crash, config, secret, DB dependency |
| Running but `0/1 Ready` | Endpoint may be unready | readiness probe failure |
| Completed | Usually no service endpoint | Job/CronJob not a long-running backend |
| Terminating | Endpoint may be removed or marked terminating | rollout/deletion/drain |

### Fix

Fix the Pod root cause first. Service endpoints are a consequence of healthy selected Pods; they are not usually repaired directly.

## 6.4 Readiness probe failing

A Pod can be Running but not Ready. In that case, the Service may not route traffic to it.

### Diagnose

```bash
oc get pods -n "$NS"
oc describe pod <pod-name> -n "$NS" | sed -n '/Conditions:/,/Volumes:/p'
oc describe pod <pod-name> -n "$NS" | sed -n '/Events:/,$p'

oc get endpointslice -n "$NS" \
  -l kubernetes.io/service-name="$SVC" \
  -o yaml
```

Look for:

```text
Readiness probe failed
HTTP probe failed with statuscode: 500
connection refused
context deadline exceeded
```

### Example broken readiness probe

```yaml
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
```

Application actually exposes:

```text
/ready on port 8443
```

Result:

```text
Pod Running but not Ready → endpoint not used
```

### Fix

Patch the workload, not the Pod:

```bash
oc edit deployment <deployment> -n "$NS"
```

Correct example:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8443
    scheme: HTTPS
  initialDelaySeconds: 20
  timeoutSeconds: 5
  periodSeconds: 10
  failureThreshold: 6
```

Then verify:

```bash
oc rollout status deployment/<deployment> -n "$NS"
oc get pods -n "$NS"
oc get endpoints "$SVC" -n "$NS"
oc get endpointslice -n "$NS" -l kubernetes.io/service-name="$SVC" -o wide
```

### Senior-level warning

Do not delete readiness probes just to make the endpoint appear. A readiness probe protects users from being sent to an application instance that cannot serve traffic. Tune it correctly.

## 6.5 Service `targetPort` does not match the container port

This case can be confusing because endpoints may exist, but traffic still fails.

Example:

```yaml
kind: Service
spec:
  ports:
  - name: http
    port: 80
    targetPort: 8080
```

But application listens on 8081:

```bash
oc rsh <pod>
ss -lntp
# LISTEN 0 4096 0.0.0.0:8081
```

Service has endpoints, but the endpoint port is wrong.

### Diagnose

```bash
oc get svc "$SVC" -n "$NS" -o yaml
oc get pod <pod> -n "$NS" -o yaml | grep -A5 -B2 containerPort
oc rsh <pod> ss -lntp
```

If the image is minimal and lacks `ss`:

```bash
oc debug pod/<pod> -n "$NS" --image=registry.access.redhat.com/ubi9/ubi --target=<container-name>
```

or test from another debug Pod:

```bash
oc run net-debug -n "$NS" --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash

curl -v http://$SVC.$NS.svc.cluster.local:80/
```

### Fix

Patch the Service:

```bash
oc patch svc "$SVC" -n "$NS" --type merge \
  -p '{"spec":{"ports":[{"name":"http","port":80,"targetPort":8081,"protocol":"TCP"}]}}'
```

Be careful when a Service has multiple ports. In that case, edit the YAML carefully:

```bash
oc edit svc "$SVC" -n "$NS"
```

## 6.6 Named `targetPort` does not exist in the Pod

This is a high-value troubleshooting point.

Service:

```yaml
ports:
- name: http
  port: 80
  targetPort: web
```

Pod container ports:

```yaml
ports:
- name: http
  containerPort: 8080
```

The Service targetPort is `web`, but the Pod exposes named port `http`.

### Diagnose

```bash
oc get svc "$SVC" -n "$NS" -o jsonpath='{.spec.ports}{"\n"}'
oc get pods -n "$NS" -l "$SELECTOR" -o yaml | grep -A6 -B2 'containerPort\|name:'
```

### Fix option A: change Service targetPort

```yaml
ports:
- name: http
  port: 80
  targetPort: http
```

### Fix option B: change container port name

```yaml
ports:
- name: web
  containerPort: 8080
```

For production, prefer stable, meaningful port names such as `http`, `https`, `metrics`, `grpc`, or `tcp-db`.

## 6.7 Deployment selector and Pod template labels drifted

Sometimes the Deployment exists but creates Pods with labels that do not match the Service.

Check:

```bash
oc get deploy <deployment> -n "$NS" -o yaml | sed -n '/selector:/,/template:/p'
oc get deploy <deployment> -n "$NS" -o yaml | sed -n '/template:/,/spec:/p'
```

Important:

```yaml
spec:
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: frontend
```

This kind of drift usually causes rollout issues or no Pods under the expected selector.

### Fix

Deployment `.spec.selector` is immutable in Kubernetes. Usually you fix the Pod template labels or recreate the Deployment correctly.

Safer process:

```bash
oc get deploy <deployment> -n "$NS" -o yaml > deploy-backup.yaml
oc rollout history deployment/<deployment> -n "$NS"
oc edit deployment <deployment> -n "$NS"
```

If immutable selector is wrong, create a corrected Deployment and migrate traffic carefully.

## 6.8 Route points to the wrong Service or wrong Service port

In OpenShift, Route does not select Pods directly. It points to a Service.

### Diagnose

```bash
oc get route -n "$NS"
oc describe route <route-name> -n "$NS"
oc get route <route-name> -n "$NS" -o yaml
oc get svc -n "$NS"
oc describe svc <service-name> -n "$NS"
```

Route example:

```yaml
spec:
  to:
    kind: Service
    name: web
  port:
    targetPort: http
```

Service must have a port with that name:

```yaml
spec:
  ports:
  - name: http
    port: 8080
    targetPort: 8080
```

If Route uses `targetPort: http`, but the Service port is named `web`, the Route may not target the expected backend.

### Fix

Patch Route target Service:

```bash
oc patch route <route-name> -n "$NS" --type merge \
  -p '{"spec":{"to":{"kind":"Service","name":"web"}}}'
```

Patch Route target port:

```bash
oc patch route <route-name> -n "$NS" --type merge \
  -p '{"spec":{"port":{"targetPort":"http"}}}'
```

Or recreate cleanly:

```bash
oc delete route <route-name> -n "$NS"
oc expose svc web -n "$NS" --name=<route-name>
```

For TLS routes, preserve TLS settings before deleting.

## 6.9 Service selector is empty or selectorless by design

A Service without a selector does **not** automatically discover Pods.

Selectorless Service example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  ports:
  - name: mysql
    port: 3306
    targetPort: 3306
```

This is valid for external backends, but you must manually provide EndpointSlices or use another Service type such as ExternalName.

### Diagnose

```bash
oc get svc external-db -n "$NS" -o yaml
```

If this returns no `.spec.selector`, missing endpoints may be expected.

### Fix with EndpointSlice

Example manual EndpointSlice:

```yaml
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: external-db-1
  namespace: app
  labels:
    kubernetes.io/service-name: external-db
    endpointslice.kubernetes.io/managed-by: manual-admin
addressType: IPv4
ports:
- name: mysql
  protocol: TCP
  port: 3306
endpoints:
- addresses:
  - "192.168.10.50"
```

Apply:

```bash
oc apply -f external-db-endpointslice.yaml
oc get endpointslice -n app -l kubernetes.io/service-name=external-db -o yaml
```

### Fix with ExternalName

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: db.example.com
```

Use ExternalName when DNS indirection is acceptable and no ClusterIP load balancing is required.

## 6.10 Headless Service confusion

A headless Service has:

```yaml
spec:
  clusterIP: None
```

This is common for StatefulSets.

Headless Services still use selectors and EndpointSlices when they select Pods. However, DNS behavior differs because clients can receive individual Pod records rather than a virtual ClusterIP.

### Diagnose

```bash
oc get svc "$SVC" -n "$NS" -o yaml | grep -A5 -B2 clusterIP
oc get endpointslice -n "$NS" -l kubernetes.io/service-name="$SVC" -o wide
oc get statefulset -n "$NS"
oc get pods -n "$NS" -o wide --show-labels
```

If the StatefulSet Pods are not Ready, endpoint publication depends on readiness and `publishNotReadyAddresses` behavior.

## 6.11 Operator-managed app changed labels during upgrade

Operators often manage Services and Pods through custom resources. If you patch the Service manually, the Operator may revert your change.

### Diagnose

```bash
oc get svc "$SVC" -n "$NS" -o yaml | grep -A10 ownerReferences
oc get pod -n "$NS" --show-labels
oc get csv -A | grep -i <operator>
oc get subscription -A | grep -i <operator>
oc get installplan -A | grep -i <operator>
```

Check owner references:

```yaml
ownerReferences:
- apiVersion: apps.example.com/v1
  kind: MyApp
  name: production
```

### Fix

Fix the Operator custom resource, not only the generated Service:

```bash
oc get <custom-resource-kind> -n "$NS"
oc edit <custom-resource-kind> <name> -n "$NS"
```

If production is down, you can apply a temporary emergency patch, but document that it may be reconciled back by the Operator.

## 6.12 Admission webhook Service has no endpoints

This is a severe cluster issue because it can block object creation, update, or deletion.

Typical error:

```text
failed calling webhook "validate.example.com": failed to call webhook:
Post "https://webhook-service.webhook-ns.svc:443/...":
no endpoints available for service "webhook-service"
```

### Diagnose

Find webhook configurations:

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
```

Find the service reference:

```bash
oc get validatingwebhookconfiguration <name> -o yaml | grep -A10 'service:'
oc get mutatingwebhookconfiguration <name> -o yaml | grep -A10 'service:'
```

Check the webhook Service and Pods:

```bash
WEBHOOK_NS=<namespace>
WEBHOOK_SVC=<service>

oc get svc "$WEBHOOK_SVC" -n "$WEBHOOK_NS" -o yaml
oc describe svc "$WEBHOOK_SVC" -n "$WEBHOOK_NS"
oc get endpoints "$WEBHOOK_SVC" -n "$WEBHOOK_NS" -o wide
oc get endpointslice -n "$WEBHOOK_NS" -l kubernetes.io/service-name="$WEBHOOK_SVC" -o yaml
oc get pods -n "$WEBHOOK_NS" -o wide --show-labels
oc get events -n "$WEBHOOK_NS" --sort-by=.lastTimestamp | tail -80
```

### Common causes

| Cause | Effect |
|---|---|
| Webhook Pod CrashLoopBackOff | No ready endpoint |
| Webhook Deployment scaled to 0 | No backend Pods |
| Service selector wrong after upgrade | No matching Pods |
| Certificate volume/secret missing | Pod fails startup/readiness |
| Readiness probe wrong | Pod Running but unready |
| Operator failed upgrade | Generated resources inconsistent |

### Emergency mitigation

If the webhook blocks cluster recovery, evaluate `failurePolicy`.

```bash
oc get validatingwebhookconfiguration <name> -o yaml | grep -A3 failurePolicy
```

For non-critical webhooks, a temporary patch from `Fail` to `Ignore` may restore cluster operations:

```bash
oc patch validatingwebhookconfiguration <name> --type='json' \
  -p='[{"op":"replace","path":"/webhooks/0/failurePolicy","value":"Ignore"}]'
```

Use this only with change approval. Restore the original value after fixing the webhook backend.

## 6.13 Pod labels changed by CI/CD or Helm values

Helm charts commonly template labels. A minor values change can break Service selectors.

### Diagnose

```bash
helm list -n "$NS"
helm get values <release> -n "$NS"
helm get manifest <release> -n "$NS" | less

oc get svc "$SVC" -n "$NS" -o yaml
oc get deploy -n "$NS" -o yaml | grep -A20 -B5 labels:
```

Look for mismatch between:

```yaml
service.spec.selector
```

and:

```yaml
deployment.spec.template.metadata.labels
```

### Fix

Fix the Helm values and upgrade the release:

```bash
helm upgrade <release> <chart> -n "$NS" -f values.yaml
```

Avoid manual `oc patch` on Helm-managed resources unless it is an emergency.

## 6.14 Service selects the wrong Pods

Sometimes endpoints are not missing, but the Service points to the wrong backend.

Example:

```yaml
selector:
  app: api
```

But both old and new Pods have `app=api`:

```text
api-v1 pods: app=api,version=v1
api-v2 pods: app=api,version=v2
```

The Service sends traffic to both versions unexpectedly.

### Diagnose

```bash
oc get pods -n "$NS" -l app=api --show-labels -o wide
oc get endpointslice -n "$NS" -l kubernetes.io/service-name="$SVC" -o yaml | grep -A10 targetRef
```

### Fix

Make the Service selector more specific:

```bash
oc patch svc api -n "$NS" --type merge \
  -p '{"spec":{"selector":{"app":"api","version":"v2"}}}'
```

For blue/green deployments, make labels intentional:

```yaml
app: api
track: blue
```

or:

```yaml
app.kubernetes.io/name: api
app.kubernetes.io/instance: production
app.kubernetes.io/version: v2
```

## 7. Deep-dive diagnostic workflow

## Step 1: Confirm the user-facing symptom

For Route:

```bash
ROUTE=<route-name>
NS=<namespace>

oc get route "$ROUTE" -n "$NS"
oc describe route "$ROUTE" -n "$NS"
HOST=$(oc get route "$ROUTE" -n "$NS" -o jsonpath='{.spec.host}')
echo "$HOST"
curl -vk "https://$HOST/"
curl -v "http://$HOST/"
```

For internal Service:

```bash
oc run net-debug -n "$NS" --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash

curl -v http://$SVC.$NS.svc.cluster.local:<port>/
```

For TCP service:

```bash
oc run net-debug -n "$NS" --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash

# install tools if repos are available, or use bash TCP check
timeout 5 bash -c '</dev/tcp/'"$SVC.$NS.svc.cluster.local"'/3306' && echo OK || echo FAIL
```

## Step 2: Inspect the Service

```bash
oc get svc "$SVC" -n "$NS" -o wide
oc describe svc "$SVC" -n "$NS"
oc get svc "$SVC" -n "$NS" -o yaml
```

Important fields:

```yaml
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
  - name: http
    port: 80
    protocol: TCP
    targetPort: 8080
```

Questions:

1. Does the Service have a selector?
2. Is the Service in the same namespace as the Pods?
3. Does the Service port match the Route target port?
4. Does targetPort match the container listener?
5. Is it a normal ClusterIP, headless Service, ExternalName, or selectorless Service?

## Step 3: Inspect selected Pods

```bash
SELECTOR=$(oc get svc "$SVC" -n "$NS" \
  -o go-template='{{range $k,$v := .spec.selector}}{{printf "%s=%s," $k $v}}{{end}}' | sed 's/,$//')

echo "Service selector: $SELECTOR"
oc get pods -n "$NS" -l "$SELECTOR" -o wide --show-labels
```

If output is empty:

```text
Service selector mismatch or wrong namespace.
```

If Pods exist:

```bash
oc describe pod -n "$NS" -l "$SELECTOR"
oc get pods -n "$NS" -l "$SELECTOR" -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\t"}{range .status.conditions[*]}{.type}{"="}{.status}{" "}{end}{"\n"}{end}'
```

## Step 4: Inspect EndpointSlice

```bash
oc get endpointslice -n "$NS" -l kubernetes.io/service-name="$SVC" -o wide
oc get endpointslice -n "$NS" -l kubernetes.io/service-name="$SVC" -o yaml
```

Look for:

```yaml
conditions:
  ready: false
  serving: false
  terminating: false
```

or:

```yaml
endpoints: []
```

or no EndpointSlice object.

## Step 5: Inspect the workload owner

Find owners:

```bash
oc get pods -n "$NS" -l "$SELECTOR" -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .metadata.ownerReferences[*]}{.kind}{"/"}{.name}{" "}{end}{"\n"}{end}'
```

Then inspect owner:

```bash
oc get deploy,dc,sts,ds,rs -n "$NS"
oc describe deployment <name> -n "$NS"
oc rollout status deployment/<name> -n "$NS"
oc rollout history deployment/<name> -n "$NS"
```

## Step 6: Test Pod IP directly

If endpoints exist but Service fails, test Pod IP and port:

```bash
POD=<pod-name>
POD_IP=$(oc get pod "$POD" -n "$NS" -o jsonpath='{.status.podIP}')
echo "$POD_IP"

oc run net-debug -n "$NS" --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash

curl -v http://$POD_IP:<target-port>/
curl -v http://$SVC.$NS.svc.cluster.local:<service-port>/
```

Interpretation:

| Pod IP test | Service DNS test | Meaning |
|---|---|---|
| Fails | Fails | App not listening, Pod issue, NetworkPolicy to Pod |
| Works | Fails | Service/targetPort/kube-proxy/OVN/service path issue |
| Works | Works | Route/router/TLS/client path issue |

## Step 7: Check NetworkPolicy only after endpoints are present

```bash
oc get networkpolicy -n "$NS"
oc describe networkpolicy -n "$NS"
```

NetworkPolicy does not normally prevent EndpointSlice creation. It can block traffic to endpoints after they exist.

## Step 8: Check cluster-level network diagnostics

OpenShift includes network diagnostics objects:

```bash
oc get podnetworkconnectivitychecks -n openshift-network-diagnostics
oc get pods -n openshift-network-diagnostics -o wide
oc logs -n openshift-network-diagnostics -l app=network-check-source --tail=100
```

Use this to determine if a broader cluster network issue exists. But again, missing endpoints are usually an object-selection/readiness problem, not an OVN dataplane problem.

## 9. Production decision tree

```text
Start: Service endpoint missing
 |
 |-- Does Service exist in correct namespace?
 |      |-- No  -> create/fix Service in correct namespace
 |      '-- Yes
 |
 |-- Does Service have selector?
 |      |-- No  -> selectorless service; create EndpointSlice manually or use ExternalName
 |      '-- Yes
 |
 |-- Do Pods match Service selector in same namespace?
 |      |-- No  -> fix Service selector or workload Pod template labels
 |      '-- Yes
 |
 |-- Are matching Pods Running?
 |      |-- No  -> fix scheduling/image/crash/PVC/quota/SCC issues
 |      '-- Yes
 |
 |-- Are matching Pods Ready?
 |      |-- No  -> fix readiness probe/app dependency/startup/config
 |      '-- Yes
 |
 |-- Do EndpointSlices show ready endpoints?
 |      |-- No  -> inspect endpoint controller symptoms, Pod readiness gates, terminating Pods
 |      '-- Yes
 |
 |-- Does Service targetPort match app listener?
 |      |-- No  -> fix Service targetPort or container port name
 |      '-- Yes
 |
 |-- Does Route target correct Service and Service port?
 |      |-- No  -> fix Route target/port
 |      '-- Yes
 |
 '-- Endpoints exist. Move to traffic-path troubleshooting:
        NetworkPolicy, OVN-Kubernetes, DNS, router, TLS, app response.
```

## 10. Real-world troubleshooting scenarios

## Scenario 1: Route returns 503 and Service has `<none>` endpoints

### Symptom

```bash
curl -I http://frontend.apps.example.com
# HTTP/1.1 503 Service Unavailable

oc describe svc frontend -n app
# Endpoints: <none>
```

### Investigation

```bash
oc get svc frontend -n app -o jsonpath='{.spec.selector}{"\n"}'
# {"app":"frontend"}

oc get pods -n app --show-labels
# frontend-6d8849d96f-k5q7r app=web
```

### Root cause

Service selector expects `app=frontend`, but Pod label is `app=web`.

### Fix

```bash
oc patch deployment frontend -n app --type merge \
  -p '{"spec":{"template":{"metadata":{"labels":{"app":"frontend"}}}}}'

oc rollout status deployment/frontend -n app
oc get endpoints frontend -n app
```

---

## Scenario 2: Pods Running but endpoints still missing

### Symptom

```bash
oc get pods -n app
# NAME                     READY   STATUS    RESTARTS   AGE
# api-7db8b48f56-7kslm     0/1     Running   0          4m

oc get endpoints api -n app
# ENDPOINTS: <none>
```

### Investigation

```bash
oc describe pod api-7db8b48f56-7kslm -n app
# Readiness probe failed: HTTP probe failed with statuscode: 503
```

### Root cause

Application is Running, but not Ready. Service has no ready backend.

### Fix

Fix the app dependency or readiness probe:

```bash
oc logs deploy/api -n app
oc set env deployment/api DB_HOST=db.app.svc.cluster.local -n app
oc rollout status deployment/api -n app
oc get endpoints api -n app
```

## Scenario 3: Endpoint exists but route still fails

### Symptom

```bash
oc get endpoints web -n app
# web   10.128.2.20:8081

curl http://web.app.svc.cluster.local:80
# connection refused
```

### Investigation

```bash
oc get svc web -n app -o yaml
# targetPort: 8081

oc rsh web-xxx ss -lntp
# app listens on 8080
```

### Root cause

Service targetPort is wrong.

### Fix

```bash
oc patch svc web -n app --type merge \
  -p '{"spec":{"ports":[{"name":"http","port":80,"targetPort":8080,"protocol":"TCP"}]}}'
```

## Scenario 4: Webhook blocks deployments with no endpoints

### Symptom

```text
Error from server (InternalError): error when creating "app.yaml":
failed calling webhook "validate.policy.example.com":
no endpoints available for service "policy-webhook"
```

### Investigation

```bash
oc get validatingwebhookconfiguration | grep policy
oc get svc policy-webhook -n policy-system -o yaml
oc get endpoints policy-webhook -n policy-system
oc get pods -n policy-system --show-labels
```

### Root cause

Webhook Deployment is CrashLoopBackOff because its TLS secret is missing.

### Fix

```bash
oc get secret -n policy-system
oc describe pod -n policy-system -l app=policy-webhook
oc logs -n policy-system deploy/policy-webhook
```

Recreate/fix the TLS secret or operator custom resource. If the webhook blocks urgent recovery and is non-critical, temporarily set `failurePolicy: Ignore` with approval.

## Scenario 5: Helm upgrade changed labels

### Symptom

```bash
oc get endpoints backend -n app
# <none>
```

Before Helm upgrade:

```yaml
app: backend
```

After Helm upgrade:

```yaml

```

Service still selects:

```yaml

  app: backend
```

### Fix

Update Helm values/templates so the Service selector and Pod template labels match.

```bash

```

## 11. What not to do in production

Avoid these mistakes:

### 11.1 Do not manually create Endpoints for a normal selector-based Service

For normal Services, the control plane manages EndpointSlices and Endpoints. Manual endpoint objects can create confusion and may be overwritten or ignored.

Use manual EndpointSlices only for selectorless Services or special integrations.

### 11.2 Do not label only a live Pod as a permanent fix

This works temporarily:

```bash
oc label pod api-xxx app=api -n app --overwrite
```

But new Pods from the Deployment will not inherit that label unless you patch the Pod template.

Correct:

```bash
oc patch deployment api -n app --type merge \
  -p '{"spec":{"template":{"metadata":{"labels":{"app":"api"}}}}}'
```

### 11.3 Do not remove readiness probes blindly

A readiness probe failure is often telling the truth: the app is not ready. Fix application health, dependencies, startup timing, or probe configuration.

### 11.4 Do not blame OVN before checking selectors

Network plugins do not decide which Pods a Service selects. Service selectors and readiness determine endpoint population.

### 11.5 Do not patch Operator-managed Services without checking ownerReferences

Operators may revert manual patches. Fix the custom resource or Helm values that own the Service.

## 13. OpenShift-specific areas to verify

## 13.1 Route admission and router behavior

```bash
oc get route -n "$NS" -o wide
oc describe route <route> -n "$NS"
oc get pods -n openshift-ingress -o wide
oc logs -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=default --tail=100
```

If the Service has no endpoints, router usually returns 503. If endpoints exist but only external route fails, investigate router, route TLS, DNS, and ingress controller sharding.

## 13.2 NetworkPolicy

```bash
oc get networkpolicy -n "$NS"
oc describe networkpolicy -n "$NS"
```

NetworkPolicy can block traffic from the router namespace or client Pods to backend Pods. It does not usually remove endpoints.

For routes, remember router Pods run in `openshift-ingress`. If backend namespace has restrictive ingress NetworkPolicies, allow ingress from router Pods or namespaces as required by your security model.

## 13.3 SecurityContextConstraints and Pod startup

SCC problems can prevent Pods from starting, indirectly causing no endpoints.

```bash
oc describe pod <pod> -n "$NS"
# look for: unable to validate against any security context constraint
```

Fix by using the correct ServiceAccount/SCC policy. Do not grant `anyuid` broadly without approval.

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n "$NS"
```

## 13.4 Quota and LimitRange

Quota can prevent ReplicaSets from creating Pods. No Pods means no endpoints.

```bash
oc describe quota -n "$NS"
oc describe limitrange -n "$NS"
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -80
```

## 13.5 PVC and storage

If Pods are Pending due to PVC binding or mount errors, endpoints will be missing.

```bash
oc get pvc -n "$NS"
oc describe pvc <pvc> -n "$NS"
oc describe pod <pod> -n "$NS"
oc get sc
```

## 16. Troubleshooting matrix

| Symptom | Likely cause | Verify | Fix |
|---|---|---|---|
| `Endpoints: <none>` | Selector mismatch | `oc get svc -o yaml`, `oc get pods --show-labels` | Patch Service selector or workload labels |
| No Pods from Service selector | Wrong namespace or labels | `oc get pods -l "$SELECTOR"` | Create Service in correct namespace or fix labels |
| Pods `0/1 Ready` | Readiness probe failing | `oc describe pod`, EndpointSlice conditions | Fix probe/app dependency |
| Pods Pending | Scheduling/PVC/quota | `oc describe pod`, events | Fix scheduler/storage/quota issue |
| Pods CrashLoopBackOff | App crash/config | `oc logs --previous` | Fix app config/secret/env |
| Endpoint exists, service fails | Wrong targetPort | `oc get svc -o yaml`, test Pod IP | Patch targetPort |
| Route 503 | Service has no endpoint or route wrong service/port | `oc describe route`, `oc describe svc` | Fix backend Service/endpoint or Route target |
| Webhook no endpoints | Webhook backend down | webhook config + service + pods | Fix webhook deployment/operator/certs |
| Operator app reverts fix | Operator reconciliation | `ownerReferences`, CR, CSV | Fix custom resource/values |
| Only external access fails | Router/DNS/TLS/NetworkPolicy | internal curl works, route fails | Fix route/router/DNS/TLS/policy |

## 17. Senior troubleshooting checklist

Use this before declaring the issue resolved:

```text
[ ] Service exists in expected namespace.
[ ] Service selector is intentional and documented.
[ ] Matching Pods exist in the same namespace.
[ ] Matching Pods are Running.
[ ] Matching Pods are Ready.
[ ] EndpointSlices show ready endpoints.
[ ] Legacy Endpoints output is consistent with EndpointSlice output.
[ ] Service targetPort matches container listener.
[ ] Named targetPort exists as a named containerPort if name-based.
[ ] Route points to correct Service.
[ ] Route targetPort matches a Service port name/number.
[ ] App is reachable by Pod IP from debug Pod.
[ ] App is reachable by Service DNS from debug Pod.
[ ] Route is reachable externally if this is an ingress issue.

[ ] Helm/Operator/GitOps source of truth is updated.
[ ] Events and rollout status are clean.
```

## 19. Interview-ready explanation

A strong answer:

> A Service endpoint is missing when the Service has no ready backend Pod IP and port to send traffic to. I first check the Service selector and compare it with Pod template labels in the same namespace. Then I check whether the matching Pods are Running and Ready, because readiness failures remove Pods from Service traffic. In OpenShift 4, I inspect both Endpoints and EndpointSlices, because EndpointSlice is the modern source for scalable Service backends. If endpoints exist but traffic still fails, I move down to targetPort, app listener, Route target port, NetworkPolicy, OVN, router, and DNS. I avoid manually editing endpoints for selector-based Services and fix the source of truth: Deployment, Helm chart, Operator custom resource, or GitOps manifest.

## 21. Final production principle

Do not troubleshoot a missing Service endpoint as a single command problem. Treat it as a chain:

```text
Service selector contract
    → Pod labels
    → Pod lifecycle
    → readiness
    → EndpointSlice generation
    → Service targetPort
    → Route/router
    → NetworkPolicy/OVN/DNS/TLS
```

In most real incidents, the fastest fix comes from comparing these two objects:

```bash
oc get svc <svc> -n <ns> -o yaml
oc get pods -n <ns> --show-labels
```

If the selector and labels are wrong, no amount of router, DNS, or OVN troubleshooting will create a backend endpoint.
