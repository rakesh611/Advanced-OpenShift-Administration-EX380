# Pod Stuck in `ImagePullBackOff` — Advanced OpenShift Administration Troubleshooting Guide

**Audience:** Advanced OpenShift / Kubernetes administrators with ~10 years of Linux, DevOps, and platform operations experience  
**Scope:** OpenShift Container Platform 4.x, CRI-O, Kubernetes pods, Operators, disconnected clusters, private registries, global pull secrets, service account pull secrets, image mirrors, registry trust, and production incident handling  
**Goal:** Diagnose and fix pods stuck in `ImagePullBackOff` or `ErrImagePull` quickly, safely, and permanently.

---

## 1. Executive Summary

`ImagePullBackOff` means the pod is scheduled to a node, but the kubelet on that node cannot pull one or more container images required by the pod. The container never reaches application startup, so application logs often do not exist yet. The real evidence is usually in:

- `oc describe pod <pod> -n <namespace>` events
- kubelet logs on the node
- CRI-O logs on the node
- registry authentication and authorization
- image name, tag, digest, architecture, and manifest availability
- cluster pull-secret and namespace/service-account pull secrets
- registry mirror, proxy, DNS, firewall, and CA trust configuration

`ImagePullBackOff` is not the first failure. The first failure is usually `ErrImagePull`; after repeated failures, Kubernetes backs off retry attempts and shows `ImagePullBackOff`.

In production, do not blindly delete pods first. First capture the events, image reference, service account, node, registry, error message, and recent workload changes. Then apply the smallest safe fix.

---

## 2. What Happens Internally When OpenShift Starts a Pod

When a pod is created from a `Deployment`, `DeploymentConfig`, `StatefulSet`, `DaemonSet`, `Job`, `CronJob`, Operator operand, or static manifest, the normal flow is:

1. API server accepts the workload object.
2. Controller creates a ReplicaSet / replication controller / pod.
3. Scheduler assigns the pod to a node.
4. Kubelet on that node sees the pod assignment.
5. Kubelet asks CRI-O to ensure the image exists locally.
6. CRI-O resolves the image reference through `/etc/containers/registries.conf`, pull secrets, mirror rules, short-name policy, proxy, and trust configuration.
7. CRI-O contacts the registry.
8. Registry returns the manifest and image layers.
9. CRI-O stores the layers locally.
10. Kubelet starts the container.

`ImagePullBackOff` happens between steps 5 and 8. The pod is usually already scheduled, so the root cause is normally not CPU, memory, taints, tolerations, node selectors, or PVC binding. Those cause `Pending`, not `ImagePullBackOff`.

## 3. Difference Between `ErrImagePull` and `ImagePullBackOff`

| Status | Meaning | Typical Timing | What to Do |
|---|---|---:|---|
| `ErrImagePull` | The first image pull attempt failed. | Early failure after scheduling. | Read pod events immediately. |
| `ImagePullBackOff` | Kubelet is retrying image pulls with increasing delay. | After repeated pull failures. | Fix the root cause; retry happens automatically. |
| `InvalidImageName` | Image reference format is invalid. | Immediate. | Correct image name syntax. |
| `CreateContainerConfigError` | Kubelet cannot construct container config, often secret/config issue. | Before container start. | Check referenced secret/configmap/env/volume. |
| `CrashLoopBackOff` | Image pulled and container started, but process exits repeatedly. | After container start. | Check container logs and app startup. |

Important operational point: `ImagePullBackOff` means the application process has not started, so `oc logs <pod>` usually returns nothing useful unless another container in the pod already started.

## 4. Fast Triage Commands

Set variables first:

```bash
NS=<namespace>
POD=<pod-name>
```

Check current status:

```bash
oc get pod -n $NS $POD -o wide
oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}{"\n"}'
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*]}{.name}{" => "}{.image}{"\n"}{end}'
oc get pod -n $NS $POD -o jsonpath='{range .spec.initContainers[*]}INIT:{.name}{" => "}{.image}{"\n"}{end}'
```

Read events:

```bash
oc describe pod -n $NS $POD
```

Get only event messages:

```bash
oc get events -n $NS \
  --field-selector involvedObject.name=$POD \
  --sort-by='.lastTimestamp'
```

Find all pods with image pull failures:

```bash
oc get pods -A | egrep 'ImagePullBackOff|ErrImagePull|InvalidImageName'
```

Find image pull failures by events across all namespaces:

```bash
oc get events -A --sort-by='.lastTimestamp' | egrep -i 'pull|image|BackOff|ErrImagePull|ImagePullBackOff|unauthorized|denied|manifest|x509|timeout'
```

Check the owning workload:

```bash
oc get pod -n $NS $POD -o jsonpath='{.metadata.ownerReferences[*].kind}{" "}{.metadata.ownerReferences[*].name}{"\n"}'
```

Check service account used by the pod:

```bash
oc get pod -n $NS $POD -o jsonpath='{.spec.serviceAccountName}{"\n"}'
SA=$(oc get pod -n $NS $POD -o jsonpath='{.spec.serviceAccountName}')
oc get sa -n $NS $SA -o yaml
```

## 5. Senior Troubleshooting Mindset

Do not start by changing random secrets. Start by classifying the error message.

### First question: what exact image cannot be pulled?

A pod can have:

- init containers
- app containers
- sidecars
- operator-injected containers
- service mesh proxies
- logging/monitoring agents

Always identify the exact failing image:

```bash
oc describe pod -n $NS $POD | sed -n '/Containers:/,/Conditions:/p'
oc describe pod -n $NS $POD | sed -n '/Events:/,$p'
```

### Second question: is this a single pod, namespace-wide, node-wide, or cluster-wide issue?

```bash
# Single namespace
oc get pods -n $NS -o wide | egrep 'ImagePull|ErrImagePull|InvalidImageName'

# All namespaces
oc get pods -A -o wide | egrep 'ImagePull|ErrImagePull|InvalidImageName'

# Are failures concentrated on one node?
oc get pods -A -o wide | egrep 'ImagePull|ErrImagePull|InvalidImageName' | awk '{print $1,$2,$4,$8}' | column -t
```

Interpretation:

| Blast Radius | Likely Cause |
|---|---|
| One pod | Wrong image name/tag/digest, wrong workload YAML, missing imagePullSecret. |
| One namespace | Service account pull secret issue, namespace secret deleted, RBAC/image pull permission, GitOps applied wrong secret. |
| One node | Node DNS, proxy, CRI-O, CA trust, disk pressure, corrupted local image storage, node firewall. |
| Many namespaces / many nodes | Global pull secret, registry outage, enterprise proxy, cluster-wide mirror/CA/registry config, disconnected mirror sync issue. |
| Only Operator catalog pods | CatalogSource index image pull secret, marketplace namespace, disconnected catalog mirror, index image unavailable. |
| Only internal registry images | OpenShift image registry route/service/storage, image stream import, registry auth, internal registry operator issue. |

## 6. Common Event Messages and Root Causes

### 6.1 `pull access denied`, `repository does not exist`, or `may require authorization`

Example:

```text
Failed to pull image "quay.io/acme/app:v1": rpc error: code = Unknown desc = reading manifest v1 in quay.io/acme/app: unauthorized: access to the requested resource is not authorized
```

Likely causes:

- private registry credentials missing
- secret exists but not linked to service account
- secret exists in wrong namespace
- wrong registry server key inside `.dockerconfigjson`
- wrong username/token/password
- token expired or rotated
- robot account lacks repository access
- repository path typo
- GitOps overwrote `imagePullSecrets`

Fix pattern:

```bash
oc create secret docker-registry regcred \
  --docker-server=quay.io \
  --docker-username='<user-or-robot>' \
  --docker-password='<token-or-password>' \
  --docker-email='unused@example.com' \
  -n $NS

oc secrets link $SA regcred --for=pull -n $NS

oc get sa -n $NS $SA -o yaml
oc delete pod -n $NS $POD
```

If the workload explicitly defines `imagePullSecrets`, patch the workload instead of relying only on the service account:

```bash
oc patch deployment/<deployment-name> -n $NS --type='merge' \
  -p '{"spec":{"template":{"spec":{"imagePullSecrets":[{"name":"regcred"}]}}}}'
```

For `DeploymentConfig`:

```bash
oc patch dc/<dc-name> -n $NS --type='merge' \
  -p '{"spec":{"template":{"spec":{"imagePullSecrets":[{"name":"regcred"}]}}}}'
```

### 6.2 `manifest unknown` or `manifest not found`

Example:

```text
manifest unknown: manifest unknown
```

Likely causes:

- tag does not exist
- digest does not exist
- image was deleted or garbage-collected from registry
- CI pipeline pushed to a different repository
- promotion pipeline did not promote image to production registry
- wrong architecture manifest
- mirrored registry missing that tag/digest

Verify with tools:

```bash
IMG=<image-reference>
podman manifest inspect $IMG
skopeo inspect docker://$IMG
```

On OpenShift, for internal images:

```bash
oc get is -n $NS
oc describe is/<imagestream> -n $NS
oc get istag -n $NS
```

Fix:

- correct the image tag or digest
- push the missing image
- re-run image promotion/mirroring
- use immutable digest references for production
- verify multi-architecture manifest if running mixed architecture nodes

Patch examples:

```bash
oc set image deployment/<deployment-name> <container-name>=quay.io/acme/app:v1.2.3 -n $NS
oc rollout status deployment/<deployment-name> -n $NS
```

### 6.3 `x509: certificate signed by unknown authority`

Example:

```text
x509: certificate signed by unknown authority
```

Likely causes:

- registry uses private CA
- registry certificate chain incomplete
- intermediate CA missing
- certificate CN/SAN does not match registry hostname
- node does not trust registry CA
- cluster image config CA not applied
- registry certificate rotated without updating cluster trust

First verify from a debug pod or node:

```bash
REGISTRY=<registry.example.com:5000>
openssl s_client -connect $REGISTRY -servername ${REGISTRY%%:*} -showcerts </dev/null
```

OpenShift cluster-wide registry CA configuration normally uses a ConfigMap in `openshift-config` and updates the cluster image configuration:

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=<registry-hostname>..<registry-port>=ca.crt

oc patch image.config.openshift.io/cluster --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Example for `registry.example.com:5000`:

```bash
oc create configmap registry-cas -n openshift-config \
  --from-file=registry.example.com..5000=ca.crt

oc patch image.config.openshift.io/cluster --type=merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Then check Machine Config Operator rollout:

```bash
oc get co machine-config
oc get mcp
oc describe mcp worker
```

If this is urgent and only one workload is affected, confirm the certificate is correct before changing cluster-wide trust.

### 6.4 `dial tcp: lookup <registry>: no such host`

Likely causes:

- DNS issue on node
- wrong registry hostname
- cluster DNS issue
- corporate DNS outage
- node `/etc/resolv.conf` issue
- proxy intercepting DNS
- disconnected cluster not resolving external registry by design

Check from a pod:

```bash
oc run dns-test -n $NS --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
getent hosts quay.io
curl -vk https://quay.io/v2/
```

Check from the failing node:

```bash
NODE=$(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
oc debug node/$NODE
chroot /host
getent hosts <registry-hostname>
curl -vk https://<registry-hostname>/v2/
```

Fix depends on cause:

- correct typo in image registry hostname
- fix DNS server / forwarding
- fix node network
- configure disconnected mirror
- configure proxy/noProxy correctly

### 6.5 `i/o timeout`, `context deadline exceeded`, or `connection refused`

Likely causes:

- firewall blocks registry port
- proxy missing or wrong
- registry outage
- MTU/network path issue
- overloaded registry
- egress NetworkPolicy is not usually the cause, because image pulling is done by the node/CRI-O, not by the pod network
- disconnected cluster trying to reach public internet

Check from failing node:

```bash
NODE=$(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
oc debug node/$NODE
chroot /host
curl -vk https://<registry>/v2/
podman pull <image>
crictl pull <image>
```

Check proxy cluster config:

```bash
oc get proxy/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
```

Fix:

- allow egress from nodes to registry
- configure cluster proxy and `noProxy`
- configure mirror registry for disconnected environment
- fix registry service availability
- fix firewall/route/MTU

### 6.6 `toomanyrequests` or rate limit errors

Likely causes:

- anonymous Docker Hub pulls
- many nodes pulling at once during rollout
- CI/CD deployments repeatedly pulling same public image
- no registry cache/mirror

Fix:

- authenticate with registry
- mirror public images to internal registry
- use Red Hat or enterprise registry
- pin production images to internal registry
- avoid `imagePullPolicy: Always` with public unauthenticated images unless required
- throttle rollouts during incident

### 6.7 `no matching manifest for linux/amd64`, `linux/arm64`, or architecture mismatch

Likely causes:

- image only built for one CPU architecture
- mixed architecture cluster
- node architecture does not match image manifest
- mirror lost multi-architecture manifest list

Check node architecture:

```bash
oc get node $NODE -o jsonpath='{.status.nodeInfo.architecture}{"\n"}'
oc get node $NODE -o jsonpath='{.status.nodeInfo.operatingSystem}{"\n"}'
```

Inspect image manifest:

```bash
skopeo inspect --raw docker://<image> | jq .
podman manifest inspect <image>
```

Fix:

- build multi-architecture image
- schedule workload only to compatible nodes
- fix mirror process to include all manifests
- use architecture-specific image only when intentional

### 6.8 `invalid reference format`

Likely causes:

- uppercase registry/repository path where not allowed
- empty image variable from Helm/Kustomize/template
- image string contains spaces/newlines
- malformed digest
- missing registry path
- bad tag interpolation

Check actual rendered image:

```bash
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*]}{.name}{" => ["}{.image}{"]\n"}{end}'
oc get deployment -n $NS <deployment-name> -o yaml | grep -n "image:"
```

Fix source manifest, Helm values, Kustomize patch, ArgoCD Application, or Operator custom resource.

## 7. OpenShift-Specific Areas to Check

## 7.1 Service Account Pull Secrets

In OpenShift, pods run under a service account. Most application pods use `default` unless specified. Pull secrets can be linked to that service account.

Check service account:

```bash
SA=$(oc get pod -n $NS $POD -o jsonpath='{.spec.serviceAccountName}')
oc get sa -n $NS $SA -o yaml
```

Look for:

```yaml
imagePullSecrets:
- name: default-dockercfg-xxxxx
- name: regcred
```

Check secret exists:

```bash
oc get secret -n $NS
oc get secret -n $NS regcred -o yaml
```

Decode Docker config safely:

```bash
oc get secret regcred -n $NS -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Common mistakes:

- secret created in `default` namespace but workload runs in `app-prod`
- service account is `builder` or custom SA, not `default`
- secret linked for mount instead of pull
- secret type is wrong
- registry server key does not exactly match image registry hostname and port

Correct link:

```bash
oc secrets link <service-account> <secret-name> --for=pull -n <namespace>
```

Incorrect for image pull only:

```bash
oc secrets link <service-account> <secret-name> -n <namespace>
```

The above links as a mount secret, not necessarily as an image pull secret.

## 7.2 Global Cluster Pull Secret

The global pull secret lives in:

```bash
openshift-config/pull-secret
```

Check:

```bash
oc get secret pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Use cases:

- OpenShift release payload images
- Red Hat registry images
- cluster-wide registry credentials
- Operators and operands depending on global credentials

When to update global pull secret:

- cluster-wide registry credential change
- adding credentials used by many namespaces
- Red Hat pull secret rotated
- disconnected registry credentials changed

Safer workflow:

```bash
oc get secret/pull-secret -n openshift-config \
  --template='{{index .data ".dockerconfigjson" | base64decode}}' > pull-secret.json

# Merge new auth into pull-secret.json using jq or an editor.
# Validate JSON before applying.
jq . pull-secret.json >/dev/null

oc set data secret/pull-secret -n openshift-config \
  --from-file=.dockerconfigjson=pull-secret.json

oc get co machine-config
oc get mcp
```

Notes:

- Global pull secret changes are sensitive; always back up the existing secret.
- Do not overwrite existing auths accidentally.
- Validate JSON before applying.
- Watch MCO/MCP status after changes.

## 7.3 Internal OpenShift Registry Images

Image reference examples:

```text
image-registry.openshift-image-registry.svc:5000/project/app:tag
image-registry.openshift-image-registry.svc:5000/project/app@sha256:<digest>
```

Check registry operator:

```bash
oc get co image-registry
oc get pods -n openshift-image-registry
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Check service and endpoints:

```bash
oc get svc -n openshift-image-registry
oc get endpoints -n openshift-image-registry
```

Check image stream:

```bash
oc get is -n $NS
oc describe is/<image-stream> -n $NS
oc get istag -n $NS
```

Common causes:

- internal registry removed or unmanaged
- registry pod down
- registry storage issue
- image stream tag points to missing digest
- namespace pull permission issue
- service account lacks permission to pull image from another namespace

Allow a service account in one namespace to pull from another namespace:

```bash
# Allow service accounts in target namespace to pull images from source namespace
oc policy add-role-to-group system:image-puller \
  system:serviceaccounts:<target-namespace> \
  -n <source-namespace>
```

Example:

```bash
oc policy add-role-to-group system:image-puller \
  system:serviceaccounts:prod \
  -n build
```

This allows pods in `prod` to pull images from image streams in `build`.

## 7.4 Operator CatalogSource `ImagePullBackOff`

For OperatorHub or custom catalogs, an index image is used by a `CatalogSource`. If the catalog pod fails with `ImagePullBackOff`, the problem is usually the index image, not the application operand.

Check:

```bash
oc get catalogsource -A
oc get pods -n openshift-marketplace
oc describe pod -n openshift-marketplace <catalog-pod>
oc get catalogsource -n openshift-marketplace <catalogsource-name> -o yaml
```

Common causes:

- index image in private registry without pull secret
- disconnected catalog mirror incomplete
- wrong index image tag
- registry CA not trusted
- marketplace namespace missing secret
- global pull secret missing registry credentials

For private index images, configure the secret where the `CatalogSource` pod runs. In many clusters this is `openshift-marketplace`.

## 7.5 Disconnected / Restricted Network Clusters

In disconnected clusters, external image pulls should not happen at runtime. A pod trying to pull from `quay.io`, `registry.redhat.io`, `docker.io`, or `gcr.io` may fail because the nodes cannot reach the internet. The correct pattern is to mirror images to the local registry and configure mirror rules.

Check image configuration:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get imagecontentsourcepolicy
```

Modern OpenShift uses:

- `ImageDigestMirrorSet` for digest-based mirrors
- `ImageTagMirrorSet` for tag-based mirrors

Older clusters may still have `ImageContentSourcePolicy`.

Check node registry configuration:

```bash
NODE=$(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
oc debug node/$NODE
chroot /host
cat /etc/containers/registries.conf
ls -l /etc/containers/registries.conf.d/
```

Common disconnected causes:

- image never mirrored
- wrong mirror namespace/path
- digest mirror configured but workload uses tag and no tag mirror exists
- tag mirror configured but workload uses digest and no digest mirror exists
- ICSP/IDMS/ITMS changed but MCP not rolled out
- mirror registry certificate not trusted
- mirror registry credentials missing
- mirror registry garbage-collected content

Fix workflow:

1. Confirm image reference required by workload.
2. Confirm image exists in mirror registry.
3. Confirm cluster mirror resources route source to mirror.
4. Confirm node has updated `registries.conf`.
5. Confirm node trusts mirror registry CA.
6. Confirm pull credentials exist.
7. Restart/recreate failed pod.

## 7.6 CRI-O and Node-Level Troubleshooting

When pod events are not enough, go to the node.

Identify node:

```bash
NODE=$(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
echo $NODE
```

Open node debug shell:

```bash
oc debug node/$NODE
chroot /host
```

Check CRI-O:

```bash
systemctl status crio --no-pager
journalctl -u crio --since "1 hour ago" --no-pager | egrep -i 'pull|image|error|x509|unauthorized|manifest|timeout|denied'
journalctl -u kubelet --since "1 hour ago" --no-pager | egrep -i 'pull|image|BackOff|ErrImagePull|x509|unauthorized|manifest|timeout|denied'
```

Try direct pull from node:

```bash
crictl pull <image>
podman pull <image>
```

Check local image store:

```bash
crictl images | grep -i '<app-or-registry>'
podman images | grep -i '<app-or-registry>'
```

Check disk pressure:

```bash
df -h
podman system df
crictl images
journalctl -u kubelet --since "1 hour ago" --no-pager | grep -i 'disk\|evict\|imagefs'
```

If image storage is full:

```bash
crictl rmi --prune
```

Use caution. Do not remove images blindly on production nodes during active incidents unless you understand the impact.

## 7.7 Proxy Configuration

In enterprise environments, registry access may require an HTTP/HTTPS proxy.

Check cluster proxy:

```bash
oc get proxy/cluster -o yaml
```

Key fields:

```yaml
spec:
  httpProxy: http://proxy.example.com:8080
  httpsProxy: http://proxy.example.com:8080
  noProxy: .cluster.local,.svc,10.0.0.0/8,registry.internal.example.com
```

Common proxy mistakes:

- internal registry not in `noProxy`
- mirror registry accidentally sent through external proxy
- external registry not reachable because proxy missing
- proxy uses TLS interception but CA is not trusted
- proxy requires authentication not configured

After proxy changes, watch operators and MCP:

```bash
oc get co
oc get mcp
```

## 8. Step-by-Step Production Runbook

## Step 1 — Capture Current Evidence

```bash
mkdir -p /tmp/imagepull-$NS-$POD
oc get pod -n $NS $POD -o yaml > /tmp/imagepull-$NS-$POD/pod.yaml
oc describe pod -n $NS $POD > /tmp/imagepull-$NS-$POD/pod.describe.txt
oc get events -n $NS --sort-by='.lastTimestamp' > /tmp/imagepull-$NS-$POD/events.txt
```

Capture workload:

```bash
OWNER_KIND=$(oc get pod -n $NS $POD -o jsonpath='{.metadata.ownerReferences[0].kind}')
OWNER_NAME=$(oc get pod -n $NS $POD -o jsonpath='{.metadata.ownerReferences[0].name}')
echo "$OWNER_KIND $OWNER_NAME"
```

If owner is ReplicaSet, find Deployment:

```bash
RS=$OWNER_NAME
oc get rs -n $NS $RS -o jsonpath='{.metadata.ownerReferences[0].kind}{" "}{.metadata.ownerReferences[0].name}{"\n"}'
```

## Step 2 — Identify the Failing Image

```bash
oc get pod -n $NS $POD -o jsonpath='{range .spec.initContainers[*]}INIT {.name}{" => "}{.image}{"\n"}{end}{range .spec.containers[*]}APP {.name}{" => "}{.image}{"\n"}{end}'
```

## Step 3 — Read the Event Message Carefully

```bash
oc describe pod -n $NS $POD | sed -n '/Events:/,$p'
```

Classify into one of these buckets:

1. image reference error
2. tag/digest missing
3. authentication/authorization
4. TLS/CA trust
5. DNS/connectivity/proxy
6. mirror/disconnected
7. architecture mismatch
8. node/CRI-O/storage
9. Operator catalog/index image

## Step 4 — Check Service Account and Pull Secret

```bash
SA=$(oc get pod -n $NS $POD -o jsonpath='{.spec.serviceAccountName}')
oc get sa -n $NS $SA -o yaml
oc get secret -n $NS
```

Validate secret:

```bash
SECRET=<secret-name>
oc get secret -n $NS $SECRET -o jsonpath='{.type}{"\n"}'
oc get secret -n $NS $SECRET -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

Expected type:

```text
kubernetes.io/dockerconfigjson
```

or older:

```text
kubernetes.io/dockercfg
```

## Step 5 — Verify Registry from Node

```bash
NODE=$(oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}')
oc debug node/$NODE
chroot /host
curl -vk https://<registry>/v2/
crictl pull <image>
```

Interpretation:

| Node Pull Result | Meaning |
|---|---|
| Works from node but pod fails | service account or namespace-level pull secret problem. |
| Fails from node with x509 | CA trust problem. |
| Fails from node with DNS | node DNS or registry hostname problem. |
| Fails from node with unauthorized | credentials problem. |
| Fails from node with manifest unknown | image/tag/digest missing. |
| Fails only on one node | node-specific network/CRI-O/storage problem. |

## Step 6 — Apply Minimal Fix

Use exact fix based on cause:

- typo: patch image reference
- missing tag: push/promote image or correct tag
- auth: create/update pull secret and link to correct service account
- global auth: update `openshift-config/pull-secret`
- CA: update `image.config.openshift.io/cluster` additionalTrustedCA
- disconnected: fix IDMS/ITMS/mirror content
- proxy: fix `proxy/cluster` and `noProxy`
- node issue: remediate node, CRI-O, DNS, disk, or registry trust

## Step 7 — Recreate Pod or Trigger Rollout

After fixing credentials or image reference, Kubernetes will retry automatically. To speed up:

```bash
oc delete pod -n $NS $POD
```

For deployments:

```bash
oc rollout restart deployment/<deployment-name> -n $NS
oc rollout status deployment/<deployment-name> -n $NS
```

For deployment configs:

```bash
oc rollout latest dc/<dc-name> -n $NS
oc rollout status dc/<dc-name> -n $NS
```

For jobs:

```bash
oc delete job/<job-name> -n $NS
# recreate from manifest or rerun CronJob manually if needed
```

For CronJob manual test:

```bash
oc create job manual-test-$(date +%s) --from=cronjob/<cronjob-name> -n $NS
```

## Step 8 — Confirm Recovery

```bash
oc get pods -n $NS -o wide
oc describe pod -n $NS <new-pod> | sed -n '/Events:/,$p'
oc logs -n $NS <new-pod> --all-containers=true --tail=50
```

Confirm no broader failures:

```bash
oc get pods -A | egrep 'ImagePullBackOff|ErrImagePull|InvalidImageName' || echo "No image pull failures found"
oc get co
```

## 9. Advanced Diagnostics by Scenario

## 9.1 Image Pull Secret Exists but Still Unauthorized

Checklist:

```bash
oc get secret regcred -n $NS -o jsonpath='{.type}{"\n"}'
oc get secret regcred -n $NS -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
oc get sa $SA -n $NS -o yaml
oc get pod $POD -n $NS -o yaml | yq '.spec.imagePullSecrets'
```

Common subtle issues:

- Secret has auth for `https://quay.io` but image uses `quay.io`.
- Secret has auth for `registry.example.com` but image uses `registry.example.com:5000`.
- Secret has auth for a parent path but registry requires repository-specific permission.
- Secret was recreated but pod is still using old admission-time references.
- Workload uses custom SA, but secret linked to `default`.
- Pull secret JSON is valid but token lacks repo access.
- External Secrets Operator rotated secret with wrong data key.

Recreate cleanly:

```bash
oc delete secret regcred -n $NS
oc create secret docker-registry regcred \
  --docker-server=<exact-registry-host[:port]> \
  --docker-username='<username>' \
  --docker-password='<password-or-token>' \
  --docker-email='unused@example.com' \
  -n $NS
oc secrets link $SA regcred --for=pull -n $NS
oc delete pod -n $NS $POD
```

## 9.2 Image Pull Fails Only on New Nodes

Likely causes:

- image cached on old nodes, missing from new nodes
- new nodes lack CA trust
- new nodes lack proxy/noProxy config
- MCP not fully updated
- registry credentials changed but old nodes still have cached image
- MachineConfigPool degraded

Check:

```bash
oc get mcp
oc get nodes
oc get pods -A -o wide | egrep 'ImagePull|ErrImagePull'
```

From new node:

```bash
oc debug node/<new-node>
chroot /host
cat /etc/containers/registries.conf
ls -l /etc/pki/ca-trust/source/anchors/
crictl pull <image>
```

Fix cluster-level config and wait for MCP convergence.

## 9.3 Works with `podman pull` on Admin Laptop but Fails in Cluster

Your laptop is not the node. Differences include:

- laptop has different DNS
- laptop has registry login
- laptop has CA trust
- laptop bypasses corporate proxy
- laptop architecture differs
- laptop can reach internet, cluster nodes cannot

Always test from the failing OpenShift node.

## 9.4 Image Pull Fails for Init Container Only

Check init containers separately:

```bash
oc get pod -n $NS $POD -o jsonpath='{range .spec.initContainers[*]}{.name}{" => "}{.image}{"\n"}{end}'
oc describe pod -n $NS $POD | sed -n '/Init Containers:/,/Containers:/p'
```

If an init container image fails, the main app containers never start. Fix the init image exactly like any other image.

## 9.5 Image Pull Fails for Service Mesh Sidecar

If using OpenShift Service Mesh / Istio, the failing image may be an injected sidecar. Check:

```bash
oc get pod -n $NS $POD -o yaml | grep -n "image:"
oc get smcp -A
oc get pods -n istio-system
```

Common causes:

- sidecar image from disconnected mirror missing
- service mesh control plane upgraded but mirror incomplete
- proxy image registry not trusted

## 9.6 Image Pull Fails for Build Output Image

In OpenShift build workflows:

```bash
oc get builds -n $NS
oc logs build/<build-name> -n $NS
oc get is -n $NS
oc describe is/<image-stream> -n $NS
```

Common causes:

- build failed, so image tag was never created
- image stream points to older/missing digest
- build pushed to wrong namespace
- deploy triggers fired before image was available
- internal registry storage problem

## 9.7 Image Pull Failure After ImageStream Import

Check import status:

```bash
oc import-image <is-name>:<tag> --from=<external-image> --confirm -n $NS
oc describe is/<is-name> -n $NS
```

If import fails due to TLS, auth, DNS, or manifest issues, deployment may also fail.

## 9.8 Image Pull Fails for `registry.redhat.io`

Likely causes:

- Red Hat pull secret missing or expired
- global pull secret overwritten incorrectly
- disconnected cluster not mirrored
- proxy/firewall blocks `registry.redhat.io`
- cluster transferred owners without proper pull secret update

Check:

```bash
oc get secret pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq '.auths | keys'
oc get co
oc get pods -A | egrep 'ImagePull|ErrImagePull'
```

Fix by updating global pull secret safely or mirroring images if disconnected.

## 10. Image Pull Policy Deep Dive

`imagePullPolicy` controls when kubelet asks the runtime to pull an image.

| Policy | Behavior | Production Use |
|---|---|---|
| `IfNotPresent` | Pull only if image not present locally. | Good for stable tagged or digest-pinned images. |
| `Always` | Always resolve/pull before start. Runtime may reuse cached layers. | Good when tags are mutable, but can expose registry outages. |
| `Never` | Never pull. Use only local image. | Rare in OpenShift, mostly special node-preload cases. |

Default behavior:

- image tag omitted -> usually treated like `latest`, policy `Always`
- tag `latest` -> policy `Always`
- non-`latest` tag -> policy `IfNotPresent`
- digest -> usually `IfNotPresent`

Production recommendation:

- avoid `:latest`
- use meaningful immutable tags, for example `v1.4.2`
- for highest reproducibility, pin by digest
- in regulated environments, deploy only signed/scanned images from approved registries
- mirror external images to internal registry

Example digest-pinned image:

```yaml
containers:
- name: app
  image: quay.io/acme/app@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  imagePullPolicy: IfNotPresent
```

## 11. Security and Governance Considerations

Image pull failures are often a symptom of weak image governance.

Recommended controls:

1. Only approved registries allowed.
2. External images mirrored internally.
3. Production deployments use immutable tags or digests.
4. Pull secrets managed by platform team or external secret management.
5. Robot accounts used instead of personal user credentials.
6. Tokens rotated with change windows and validation.
7. Registry CA lifecycle tracked like any other certificate.
8. Workloads use dedicated service accounts.
9. Build namespace and runtime namespace permissions are explicit.
10. Operator catalogs mirrored and validated before upgrades.

OpenShift features to consider:

```bash
oc get image.config.openshift.io/cluster -o yaml
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

Depending on your OpenShift version and policy tooling, also evaluate:

- admission policies
- image signature verification
- Quay robot accounts
- Red Hat Advanced Cluster Security policies
- GitOps guardrails
- namespace templates with default pull secrets

## 18. Interview / Senior Admin Explanation

A strong senior-level explanation:

> `ImagePullBackOff` means the scheduler already placed the pod, but kubelet on the assigned node cannot pull one or more container images through CRI-O. I first inspect `oc describe pod` events to identify the exact failing image and error class: wrong tag, unauthorized, x509, DNS, timeout, mirror, or architecture. Then I check the service account, namespace pull secrets, global pull secret, registry CA, proxy, mirror configuration, and direct pull from the failing node using `oc debug node` and `crictl pull`. In OpenShift I also check image streams, internal registry health, `system:image-puller` permissions, CatalogSource pods for Operators, and MCO/MCP rollout for registry CA or mirror changes. I avoid deleting evidence first, apply the smallest safe fix, recreate the pod or restart rollout, and then add preventive controls such as digest pinning, internal mirroring, robot-account secrets, and CA lifecycle management.

## 19. Quick Root Cause Mapping

| Error Text | Primary Fix |
|---|---|
| `unauthorized: authentication required` | Create/update pull secret; link to correct SA; fix registry permissions. |
| `pull access denied` | Check repo path, credentials, repository access. |
| `manifest unknown` | Correct tag/digest; push or mirror missing image. |
| `x509: certificate signed by unknown authority` | Add registry CA to OpenShift image config; fix cert chain. |
| `lookup registry... no such host` | Fix DNS, hostname, disconnected mirror config. |
| `i/o timeout` | Fix firewall, proxy, routing, registry availability. |
| `connection refused` | Registry service/port unavailable or blocked. |
| `toomanyrequests` | Authenticate, mirror, cache, reduce pull pressure. |
| `no matching manifest for linux/...` | Build/mirror correct architecture image. |
| `invalid reference format` | Fix malformed image string/template variable. |
| Fails only on one node | Debug node CRI-O, DNS, CA, proxy, disk, network. |
| Fails only for Operator catalog | Fix CatalogSource index image and marketplace pull credentials/mirror. |

## 21. Final Best Practices

For experienced OpenShift administrators, the most important habit is classification. Do not treat all `ImagePullBackOff` cases as secret problems. The event message usually tells you the category. Once you classify it, the fix is normally straightforward.

A mature OpenShift platform should make image pulls boring:

- standard internal registries
- tested pull secrets
- trusted CAs
- working proxy/noProxy
- image mirrors for disconnected environments
- digest-pinned production images
- validated Operator catalogs
- documented token rotation
- monitoring on image pull failures
- clear ownership between application, platform, network, and registry teams

When these controls are in place, `ImagePullBackOff` becomes a quick operational fix rather than a long production outage.
