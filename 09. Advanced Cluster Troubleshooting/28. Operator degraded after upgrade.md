## 1. Executive Summary

An Operator becomes **degraded after upgrade** when it cannot reconcile the new desired state introduced by a cluster upgrade, Operator upgrade, catalog update, CRD change, operand image change, API change, or configuration change.

In OpenShift 4.x, this is a serious troubleshooting topic because Operators are not just add-ons. Many core platform components are Operators:

- `authentication`
- `console`
- `dns`
- `etcd`
- `image-registry`
- `ingress`
- `kube-apiserver`
- `kube-controller-manager`
- `kube-scheduler`
- `machine-config`
- `monitoring`
- `network`
- `openshift-apiserver`
- `operator-lifecycle-manager`
- `storage`

During a cluster upgrade, the **Cluster Version Operator (CVO)** updates the release payload and waits for ClusterOperators to become healthy. If a ClusterOperator remains `Degraded=True`, the upgrade can appear stuck, partially completed, or risky to continue.

A senior administrator should not troubleshoot this as only a pod restart problem. You must identify:

1. Is the degraded Operator a **CVO-managed ClusterOperator** or an **OLM-managed add-on Operator**?
2. Did the upgrade fail during platform manifest reconciliation, node rollout, Operator reconciliation, operand rollout, image pull, webhook/API registration, or external dependency validation?
3. Is user workload impacted, or is only the Operator reporting degraded while operands remain available?
4. Is the remediation safe, supported, and reversible?

## 2. What Does "Operator Degraded After Upgrade" Mean?

In OpenShift, an Operator continuously reconciles desired state to actual state. After an upgrade, the desired state changes. The Operator may need to:

- Deploy a new Operator pod image.
- Deploy new operand images.
- Apply new CRDs.
- Migrate custom resources.
- Reconcile new default configuration.
- Validate new required fields.
- Update RBAC permissions.
- Update webhooks or APIService objects.
- Restart static pods.
- Drain and reboot nodes through MachineConfigPool changes.
- Recreate router, registry, monitoring, DNS, or authentication components.

An Operator reports degraded when it detects a persistent failure that requires investigation or intervention. A degraded status does not always mean the service is fully down, but it means the Operator cannot fully reconcile or verify healthy state.

Example:

```bash
$ oc get co
NAME              VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
ingress           4.14.18   True        False         True       35m     The default ingress controller reports degraded: route health check failed
monitoring        4.14.18   False       True          True       20m     reconciling Alertmanager failed
machine-config    4.14.18   True        True          True       1h      pool worker has degraded machine
```

The correct question is not only: **"Which pod is failing?"**  
The correct question is: **"Which desired state cannot be reconciled, and which dependency is blocking it?"**

## 3. Cluster Operators vs OLM Operators

This distinction is critical.

### 3.1 CVO-Managed Cluster Operators

These are built into OpenShift and visible with:

```bash
oc get clusteroperators
oc get co
```

Examples:

```bash
oc get co authentication
oc get co ingress
oc get co monitoring
oc get co machine-config
oc get co network
```

They are managed by the **Cluster Version Operator**. You do not normally upgrade these individually. They are upgraded as part of the OpenShift release payload.

Common resources:

```bash
oc get clusterversion
oc describe clusterversion version
oc get co
oc describe co <operator-name>
oc get pods -n openshift-<operator-namespace>
```

Do **not** delete ClusterOperator objects to fix them. A ClusterOperator object is a status/control interface for the cluster component, not a normal application resource you should recreate casually.

### 3.2 OLM-Managed Operators

These are installed from OperatorHub or custom catalogs and managed by **Operator Lifecycle Manager (OLM)**.

Examples:

- OpenShift GitOps Operator
- OpenShift Pipelines Operator
- OpenShift Logging Operator
- OpenShift Data Foundation Operator
- Service Mesh Operator
- Compliance Operator
- File Integrity Operator
- Custom third-party Operators

Important OLM resources:

```bash
oc get subscriptions -A
oc get csv -A
oc get installplans -A
oc get catalogsources -A
oc get operatorgroups -A
oc get packagemanifests
```

For OLM Operators, degradation after upgrade often comes from:

- Catalog source unavailable.
- Subscription cannot resolve update path.
- InstallPlan pending manual approval.
- CSV failed requirements.
- CRD/API version incompatibility.
- OperatorGroup mismatch.
- Unsupported target OpenShift version.
- Disconnected mirror missing bundle or operand image.

## 4. Upgrade Architecture: How CVO Controls Cluster Upgrade

OpenShift cluster upgrade is controlled by the **Cluster Version Operator (CVO)**.

The CVO takes the target release payload and applies manifests in a dependency-aware order. Some resources must exist before others. For example, a CRD must exist before custom resources that use that CRD.

OpenShift release manifests include encoded ordering, often discussed as **runlevels**. The CVO applies manifests following the generated dependency graph.

A very important upgrade behavior:

- The CVO applies manifests for a runlevel.
- For resources it monitors, it waits until they become stable.
- For ClusterOperators, the CVO waits for healthy status before proceeding to later stages.

For each runlevel, ClusterOperators must normally satisfy:

```text
Available=True
Degraded=False
Version matches target release
```

If one Operator remains degraded, the upgrade might show something like:

```bash
$ oc get clusterversion
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE   STATUS
version   4.14.18   True        True          72m     Working towards 4.14.18: 711 of 850 done, waiting on ingress
```

Or:

```bash
$ oc adm upgrade
Cluster version is 4.14.17
Upgradeable=True
Progressing=True: Working towards 4.14.18: 711 of 850 done, waiting on machine-config
```

This means the cluster is not necessarily completely broken. It means CVO cannot declare the upgrade completed because one or more required components have not converged.

## 5. Important Conditions: Available, Progressing, Degraded, Upgradeable

### 5.1 Available

`Available=True` means the Operator believes its managed component is available enough to serve.

Example:

```bash
oc get co ingress
```

Output:

```text
NAME      VERSION   AVAILABLE   PROGRESSING   DEGRADED
ingress   4.14.18   True        False         False
```

### 5.2 Progressing

`Progressing=True` means the Operator is actively rolling out, reconciling, upgrading, or waiting for new state.

This can be normal during an upgrade.

Concern starts when:

- It stays progressing for a long time.
- The message repeats the same failure.
- It is combined with `Degraded=True`.
- Upgrade status does not move for a long period.

### 5.3 Degraded

`Degraded=True` means the Operator found a persistent problem.

Examples:

```text
Degraded=True: failed to apply manifests
Degraded=True: deployment has unavailable replicas
Degraded=True: webhook service has no endpoints
Degraded=True: route health checks failed
Degraded=True: machine config pool worker degraded
```

Degraded does not always equal outage. For example:

```text
Available=True, Degraded=True
```

This can mean the component is serving traffic but has a configuration or reconciliation issue.

More serious:

```text
Available=False, Degraded=True
```

This usually means platform functionality is impacted.

### 5.4 Upgradeable

`Upgradeable=False` means an Operator is telling CVO that the current cluster state is not safe for a certain upgrade, commonly minor upgrades.

Example:

```bash
oc get co cloud-credential -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{"  "}{.message}{"\n"}{end}'
```

Example issue:

```text
Upgradeable=False  Credentials must be updated before upgrading to 4.x.y
```

A senior admin should treat `Upgradeable=False` as a pre-upgrade blocker, not something to bypass casually.

## 6. Common Symptoms

### 6.1 Cluster upgrade stuck waiting on one Operator

```bash
oc get clusterversion
```

```text
STATUS
Working towards 4.14.18: 735 of 850 done, waiting on monitoring
```

### 6.2 `oc get co` shows one or more degraded Operators

```bash
oc get co | egrep 'False|True.*True|Degraded'
```

Example:

```text
monitoring        4.14.18   False   True   True   43m
```

### 6.3 Operator pod CrashLoopBackOff

```bash
oc get pods -n openshift-monitoring
```

```text
cluster-monitoring-operator-xxxx   0/1   CrashLoopBackOff
```

### 6.4 Operand pod unavailable

The Operator pod is running, but the component it manages is broken.

Example:

```bash
oc get pods -n openshift-ingress
```

```text
router-default-xxxxx   0/1   CrashLoopBackOff
```

### 6.5 OLM Operator CSV failed

```bash
oc get csv -A | grep -i failed
```

Example:

```text
openshift-logging   cluster-logging.v5.8.0   ClusterServiceVersion   Failed
```

### 6.6 Subscription or InstallPlan stuck

```bash
oc get sub,installplan -A
```

```text
InstallPlanPending
InstallPlanFailed
CatalogSourcesUnhealthy
```

### 6.7 Webhook or APIService unavailable

```bash
oc get apiservice | grep False
oc get validatingwebhookconfigurations
oc get mutatingwebhookconfigurations
```

Symptoms:

```text
failed calling webhook
no endpoints available for service
x509: certificate signed by unknown authority
service unavailable
```

## 7. High-Level Troubleshooting Strategy

Use a layered approach.

```text
Layer 1: Cluster upgrade status
Layer 2: Degraded ClusterOperator status and condition messages
Layer 3: Operator namespace pods and logs
Layer 4: Operand resources managed by the Operator
Layer 5: Dependencies: nodes, MCP, image pull, DNS, ingress, API, etcd, storage
Layer 6: OLM resources if the Operator is OLM-managed
Layer 7: External dependencies: cloud API, registry mirror, proxy, certificates, identity provider
```

Do not start by deleting pods blindly. Pod deletion can be useful only after you understand what is blocking reconciliation.

## 8. First 10 Minutes: Stabilization Checklist

### 8.1 Confirm API access

```bash
oc whoami
oc get clusterversion
oc get co
oc get nodes
```

If API is unstable, prioritize control plane health:

```bash
oc get pods -n openshift-kube-apiserver
oc get pods -n openshift-etcd
oc get pods -n openshift-authentication
```

### 8.2 Check upgrade status

```bash
oc adm upgrade
oc adm upgrade status
oc get clusterversion version -o yaml
```

Use:

```bash
watch -n 10 'oc adm upgrade status'
```

### 8.3 Identify degraded Operators

```bash
oc get co
oc get co | awk 'NR==1 || $4=="True" || $5=="True" || $3=="False"'
```

Columns usually represent:

```text
NAME VERSION AVAILABLE PROGRESSING DEGRADED SINCE MESSAGE
```

### 8.4 Capture current state before fixing

```bash
mkdir -p ~/upgrade-triage-$(date +%F-%H%M)
cd ~/upgrade-triage-$(date +%F-%H%M)

oc get clusterversion version -o yaml > clusterversion.yaml
oc get co -o wide > clusteroperators.txt
oc get co -o yaml > clusteroperators.yaml
oc get nodes -o wide > nodes.txt
oc get mcp -o wide > mcp.txt
oc get events -A --sort-by=.lastTimestamp > events.txt
```

### 8.5 Decide severity

| State | Meaning | Severity |
|---|---|---|
| `Available=True`, `Degraded=True` | Component mostly serving, but reconciliation failed | Medium to High |
| `Available=False`, `Degraded=True` | Component unavailable | High |
| Multiple core Operators degraded | Possible infrastructure or dependency failure | Critical |
| `kube-apiserver`, `etcd`, `authentication` degraded | Control plane or login impact | Critical |
| `machine-config` degraded after upgrade | Node rollout blocked | High |
| OLM add-on Operator CSV failed | Add-on or workload domain impacted | Medium to High |

```text

|
|-- Is it visible in `oc get co`?
|     |
|     |-- Yes: CVO-managed ClusterOperator
|     |     |
|     |     |-- Check `oc describe co <name>`

|     |
|     |-- No: likely OLM-managed Operator
|           |
|           |-- Check Subscription
|           |-- Check InstallPlan

|           |-- Check CatalogSource health
|           |-- Check OperatorGroup
```

## 11. Deep-Dive Root Cause Matrix

| Root Cause | Typical Evidence | Commands | Remediation Direction |
|---|---|---|---|
| Operator pod CrashLoopBackOff | Operator pod restarts, panic, config error | `oc logs --previous`, `oc describe pod` | Fix config, check release bug, rollback custom config if supported |
| Operand unavailable | Operator pod running but managed pods down | `oc get pods`, `oc describe deploy/ds/sts` | Fix operand dependency: image, cert, SCC, storage, node |
| Image pull failure | `ImagePullBackOff`, `ErrImagePull` | `oc describe pod`, mirror config | Fix pull secret, mirror, ICSP/IDMS/ITMS, catalog image |
| Catalog unavailable | `CatalogSourcesUnhealthy` | `oc get catalogsource -A`, catalog pod logs | Fix catalog pod, registry, disconnected mirror |
| InstallPlan pending | Manual approval not approved | `oc get installplan -A` | Approve after validation |
| InstallPlan failed | Bundle unpack or resource apply failed | `oc describe installplan` | Fix missing APIs, catalog, CRD conflict, RBAC |
| CSV failed | `Failed`, `RequirementsNotMet` | `oc describe csv` | Fix required CRDs/APIs/RBAC/operatorgroup |
| Webhook unavailable | `failed calling webhook`, `no endpoints` | `oc get validatingwebhookconfiguration`, endpoints | Restore webhook service/pods or remove stale webhook only after validation |
| APIService unavailable | Aggregated API down | `oc get apiservice | grep False` | Fix service/endpoints/certs for APIService backend |
| Bad custom config | Operator message mentions invalid config | `oc get <config> -o yaml` | Revert or correct unsupported/invalid config |
| MCP degraded | Node config failed, drain blocked | `oc get mcp`, `oc describe mcp` | Fix bad MachineConfig, node issue, disk, kubelet, drain blockers |
| Node NotReady | Operators cannot schedule operands | `oc get nodes`, `oc describe node` | Fix kubelet, CRI-O, networking, disk pressure |
| Storage unavailable | PVC pending, CSI degraded | `oc get pvc`, `oc get sc`, CSI logs | Fix storage backend, CSI driver, credentials |
| DNS broken | Route checks, service discovery failing | `oc get pods -n openshift-dns`, `dig/nslookup` | Fix DNS operator/CoreDNS/network |
| Ingress broken | Routes unavailable, canary route failed | `oc get ingresscontroller`, router logs | Fix router pods, LB, DNS, certificates, network |
| Proxy/trust issue | x509, connection refused, TLS errors | `oc get proxy/cluster`, CA bundle | Fix trusted CA/proxy/noProxy |
| Cloud credential issue | `Upgradeable=False`, cloud API failures | `oc describe co cloud-credential` | Update credentials/permissions/annotations |
| Release bug | Known issue in release notes | Check Red Hat errata/release notes | Workaround or update to fixed z-stream |

## 12. Troubleshooting CVO-Managed Cluster Operators

### 12.1 Start with CVO view

```bash
oc adm upgrade
oc adm upgrade status
oc get clusterversion version -o yaml
```

Look for:

```text
Progressing=True
Failing=True
RetrievedUpdates=False
Available=False
```

Extract condition messages:

```bash
oc get clusterversion version -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{"\n"}{.message}{"\n\n"}{end}'
```

### 12.2 Identify what CVO is waiting on

```bash
oc get clusterversion
```

Example:

```text
Working towards 4.14.18: 785 of 850 done, waiting on machine-config
```

Then:

```bash
oc describe co machine-config
```

### 12.3 Read the ClusterOperator message carefully

This message often tells the real problem.

```bash
oc get co ingress -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{"\nReason: "}{.reason}{"\nMessage: "}{.message}{"\n\n"}{end}'
```

Example:

```text
Degraded=True
Reason: IngressControllersDegraded
Message: The default ingress controller reports Degraded=True: CanaryChecksRepetitiveFailures
```

From this you know the problem is likely route health, router pod, DNS, load balancer, or ingress canary, not simply the ingress-operator pod.

### 12.4 Check Operator deployment and logs

Example for ingress:

```bash
oc get pods -n openshift-ingress-operator
oc logs -n openshift-ingress-operator deploy/ingress-operator --tail=200
```

Example for monitoring:

```bash
oc get pods -n openshift-monitoring
oc logs -n openshift-monitoring deploy/cluster-monitoring-operator --tail=200
```

Example for network:

```bash
oc get pods -n openshift-network-operator
oc logs -n openshift-network-operator deploy/network-operator --tail=200
```

### 12.5 Check operand resources

For ingress:

```bash
oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller/default -n openshift-ingress-operator
oc get pods -n openshift-ingress -o wide
oc logs -n openshift-ingress deploy/router-default --tail=100
```

For monitoring:

```bash
oc get pods -n openshift-monitoring
oc get prometheus,alertmanager,thanosruler -n openshift-monitoring
oc describe prometheus k8s -n openshift-monitoring
```

For image registry:

```bash
oc get configs.imageregistry.operator.openshift.io cluster -o yaml
oc get pods -n openshift-image-registry
oc logs -n openshift-image-registry deploy/image-registry --tail=100
```

For network:

```bash
oc get network.operator cluster -o yaml
oc get pods -n openshift-ovn-kubernetes -o wide
oc get pods -n openshift-network-operator
```

### 12.6 Check CVO logs

```bash
oc get pods -n openshift-cluster-version
oc logs -n openshift-cluster-version deploy/cluster-version-operator --tail=300
```

Search for the degraded Operator name:

```bash
oc logs -n openshift-cluster-version deploy/cluster-version-operator --tail=1000 | grep -i 'ingress\|monitoring\|machine-config\|error\|degraded'
```

### 12.7 Never force blindly

Avoid:

```bash
oc adm upgrade --force
```

Force bypasses safety checks and can leave the cluster in a worse state. Use only with a clear support-backed reason, known bug, and rollback/backup plan.

## 13. Troubleshooting OLM-Managed Operators

OLM-managed Operators are upgraded through `Subscription`, `InstallPlan`, `ClusterServiceVersion`, and catalog sources.

### 13.1 List all unhealthy OLM resources

```bash
oc get sub -A
oc get installplan -A
oc get csv -A
oc get catalogsource -A
```

Useful filters:

```bash
oc get csv -A | egrep -i 'failed|pending|replacing'
oc get installplan -A | egrep -i 'false|pending|failed'
```

### 13.2 Subscription diagnosis

```bash
oc describe sub <subscription-name> -n <namespace>
```

Look for conditions:

```text
CatalogSourcesUnhealthy
InstallPlanMissing
InstallPlanPending
InstallPlanFailed
ResolutionFailed
```

Common issue:

```text
constraints not satisfiable
no operators found in package
bundle does not support OpenShift version
```

### 13.3 InstallPlan diagnosis

```bash
oc get installplan -n <namespace>
oc describe installplan <installplan-name> -n <namespace>
```

If approval is manual:

```bash
oc patch installplan <installplan-name> -n <namespace> --type merge -p '{"spec":{"approved":true}}'
```

Only approve after checking what the InstallPlan will install:

```bash
oc get installplan <installplan-name> -n <namespace> -o yaml
```

### 13.4 CSV diagnosis

```bash
oc describe csv <csv-name> -n <namespace>
```

Important fields:

```text
Phase
Reason
Message
RequirementStatus
```

Common CSV reasons:

| Reason | Meaning |
|---|---|
| `RequirementsNotMet` | Required CRD/API/RBAC missing |
| `InstallCheckFailed` | Operator install validation failed |
| `ComponentUnhealthy` | Operator deployment not healthy |
| `OwnerConflict` | Another CSV owns the same API |
| `NoOperatorGroup` | Namespace has no OperatorGroup |
| `TooManyOperatorGroups` | Namespace has multiple OperatorGroups |
| `UnsupportedOperatorGroup` | Operator cannot run with selected scope |

### 13.5 CatalogSource diagnosis

## 15. Disconnected / Restricted Network Upgrade Issues

Disconnected upgrades frequently cause Operator degraded states because all release payload images, Operator bundle images, catalog images, and operand images must be mirrored correctly.

### Symptoms

```text
ImagePullBackOff
manifest unknown
no such image
x509 certificate signed by unknown authority
CatalogSourcesUnhealthy
bundle unpacking failed
```

### Check mirror configuration

Depending on OpenShift version and configuration:

```bash

```

### Check catalog pods

```bash

```

### Common causes

- Release payload mirrored but Operator catalog not mirrored.
- Operator bundle mirrored but operand images missing.

## 19. Safe Remediation Principles

### 19.1 Do not treat all degraded Operators the same

`Available=True, Degraded=True` is different from `Available=False, Degraded=True`.

### 19.2 Do not delete important cluster resources blindly

Avoid blindly deleting:

```text
ClusterOperator
ClusterVersion
MachineConfig
MachineConfigPool
CRDs
APIService
ValidatingWebhookConfiguration
MutatingWebhookConfiguration
CSV
InstallPlan
```

### 19.3 Prefer fixing the dependency over restarting the symptom

If a pod is failing due to image pull, deleting the pod will not help. Fix the registry/pull secret/mirror.

If a route canary fails due to DNS, restarting the ingress operator will not fix DNS.

If monitoring is degraded due to invalid config YAML, restarting monitoring pods will not fix the YAML.

### 19.4 Take evidence before remediation

```bash
oc get co -o yaml > co-before.yaml
oc get clusterversion version -o yaml > cv-before.yaml
oc get events -A --sort-by=.lastTimestamp > events-before.txt
```

### 19.5 Change one thing at a time

After each change:

```bash
watch -n 10 'oc get co'
watch -n 10 'oc adm upgrade status'
```

### 19.6 Know when to engage Red Hat Support

Engage support immediately when:

- `etcd`, `kube-apiserver`, or `authentication` is unavailable.
- Multiple control plane Operators are degraded.
- Upgrade is stuck for hours with no progress in production.
- Static pod revisions are broken.
- Etcd quorum is at risk.
- You are considering force upgrade or manual etcd/static pod changes.

## 21. Example End-to-End RCA Scenario

### Problem

After upgrading OpenShift from `4.13.z` to `4.14.z`, the cluster upgrade does not complete. `oc get clusterversion` says it is waiting on `ingress`.

### Step 1: Check upgrade

```bash
oc get clusterversion
```

Output:

```text
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE   STATUS
version   4.13.31   True        True          2h      Working towards 4.14.18: 789 of 850 done, waiting on ingress
```

### Step 2: Check ClusterOperators

```bash
oc get co ingress
```

Output:

```text
NAME      VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
ingress   4.14.18   True        False         True       1h      CanaryChecksRepetitiveFailures
```

### Step 3: Describe ingress

```bash
oc describe co ingress
```

Message:

```text
Canary route checks are failing. The default ingress controller is degraded.
```

### Step 4: Check router and canary

```bash
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-ingress-canary
oc get route -n openshift-ingress-canary
```

Router pods are running.

### Step 5: Check DNS

```bash
oc get dns cluster -o yaml
nslookup canary-openshift-ingress-canary.apps.example.com
curl -kI https://canary-openshift-ingress-canary.apps.example.com
```

DNS does not resolve wildcard route.

### Step 6: Root cause

External wildcard DNS entry for `*.apps.example.com` was changed during maintenance and no longer points to the load balancer.

### Step 7: Remediation

Restore wildcard DNS to the router/load balancer address.

### Step 8: Verify

```bash
watch -n 10 'oc get co ingress; oc get clusterversion'
```

Expected:

```text
ingress   4.14.18   True   False   False
version   4.14.18   True   False   False   Cluster version is 4.14.18
```

### RCA Statement

```text
During OpenShift upgrade, the Ingress Operator reported degraded because ingress canary route checks failed. Router pods were healthy, but wildcard DNS for the apps domain was misconfigured and did not resolve to the load balancer. CVO waited on the ingress ClusterOperator because it had not reached Degraded=False. Restoring wildcard DNS allowed the ingress canary check to pass and the upgrade completed.
```

## 23. Interview / Real-World Questions

### Q1. Why can one degraded Operator block an OpenShift upgrade?

Because CVO waits for ClusterOperators in the current runlevel to report `Available=True`, `Degraded=False`, and the desired target version before proceeding. If one Operator cannot reconcile, CVO cannot safely declare the upgrade complete.

### Q2. Is `Degraded=True` always an outage?

No. An Operator can be `Available=True` and `Degraded=True`. That means the component may still be serving, but reconciliation or validation has failed. However, it still requires investigation.

### Q3. What is the first command you run?

```bash
oc get clusterversion
oc get co
oc adm upgrade status
```

These establish upgrade state and affected Operators.

### Q4. What is the difference between ClusterOperator and CSV?

A `ClusterOperator` reports health for a CVO-managed OpenShift platform component. A `ClusterServiceVersion` reports lifecycle/install status for an OLM-managed Operator.

### Q5. Why should you not delete a ClusterOperator object?

It is a platform status/control resource managed by OpenShift. Deleting it does not fix the underlying Operator dependency and may remove useful status or cause unsafe behavior.

### Q6. What if an OLM Operator is stuck after upgrade?

Check:

```bash
oc describe sub
oc describe installplan
oc describe csv
oc describe catalogsource
oc describe operatorgroup
```

The issue is often catalog resolution, manual approval, unsupported API, failed requirements, or catalog image pull.

### Q7. How do you handle disconnected upgrade Operator failures?

Verify all required images exist in the mirror registry: release payload, catalog image, bundle images, and operand images. Then verify pull secret, mirror policy, trusted CA, and catalog pod health.

### Q8. When do you call Red Hat Support?

When control plane Operators are degraded, etcd quorum is at risk, upgrade is stuck in production, force upgrade is being considered, static pod revision rollout is broken, or the error appears to match a product bug.

## Final Senior Admin Notes

When an Operator is degraded after upgrade, do not troubleshoot only at the pod level. Think like a platform engineer:

```text
Upgrade desired state changed.
Operator reconciliation failed.
The failure message points to a dependency.
Fix the dependency, not only the symptom.
Verify CVO, ClusterOperator, pods, operands, nodes, and external systems.
Document RCA and preventive controls.
```

The best OpenShift administrators are careful during upgrades because the cluster is in a transitional state. A quick restart may hide the symptom temporarily, but understanding CVO, Operator conditions, OLM, MCP, webhooks, image mirrors, certificates, and dependency chains is what solves the issue permanently.
