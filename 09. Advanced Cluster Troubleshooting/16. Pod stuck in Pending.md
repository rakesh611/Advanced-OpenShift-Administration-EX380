# Pod Stuck in Pending - Advanced Cluster Troubleshooting for OpenShift Administration

**Audience:** Advanced OpenShift administrators, L2/L3 support engineers, SREs, platform engineers  
**Experience level:** 10+ years Linux/DevOps/OpenShift operations  
**Scope:** OpenShift Container Platform 4.x, Kubernetes scheduling, node health, quotas, storage, taints/tolerations, affinity, operators, autoscaling, and production troubleshooting  
**Main command style:** `oc` CLI

---

## 1. What does `Pending` really mean?

A pod in `Pending` means the Kubernetes API has accepted the pod object, but one or more containers have not been created yet. This includes two very different situations:

1. **The pod is not scheduled yet**
   - `NODE` column is empty.
   - Scheduler has not bound the pod to any node.
   - Most common reasons: insufficient CPU/memory, taints, node selector mismatch, affinity/anti-affinity, PVC binding issue, quota, unavailable nodes, max pod density, GPU/device shortage.

2. **The pod is already scheduled but still not creating containers**
   - `NODE` column has a node name.
   - Scheduler already selected a node.
   - Kubelet/CRI-O/CNI/storage is stuck before the container becomes `Running`.
   - Most common reasons: image pull, CNI issue, volume attach/mount issue, CSI driver issue, secret/config issue, node pressure, CRI-O/kubelet issue, admission failure on node.

That distinction is the first rule in advanced troubleshooting.

```bash
oc get pod <pod_name> -n <namespace> -o wide
```

Example:

```bash
NAME        READY   STATUS    RESTARTS   AGE   IP       NODE
web-7c9...  0/1     Pending   0          5m    <none>   <none>
```

This means **unscheduled Pending**.

```bash
NAME        READY   STATUS              RESTARTS   AGE   IP       NODE
web-7c9...  0/1     ContainerCreating   0          5m    <none>   worker-1
```

This means **scheduled but not started**.

## 2. OpenShift scheduling flow

When you create a Deployment, StatefulSet, Job, CronJob, Operator operand, or raw Pod, OpenShift follows a layered flow:

```text
User / Controller creates Pod
        |
        v
API server admission
        |
        |-- validates object
        |-- applies defaults
        |-- checks ResourceQuota / LimitRange
        |-- applies OpenShift security admission / SCC-related rules
        v
Pod stored in etcd
        |
        v
Scheduler watches unscheduled Pods
        |
        |-- filters nodes
        |   |-- Ready?
        |   |-- schedulable?
        |   |-- enough allocatable CPU/memory/ephemeral storage/pods?
        |   |-- nodeSelector / nodeAffinity match?
        |   |-- taints tolerated?
        |   |-- pod affinity/anti-affinity satisfied?
        |   |-- PVC topology compatible?
        |   |-- GPU / device / hugepage / NUMA constraints satisfied?
        |
        |-- scores feasible nodes
        |-- binds Pod to selected node
        v
Kubelet on node admits Pod
        |
        |-- pulls image through CRI-O
        |-- mounts volumes
        |-- creates sandbox
        |-- attaches pod network through CNI/OVN-Kubernetes
        |-- starts containers
        v
Pod Running
```

A pod can remain `Pending` at any layer before containers start.

## 4. Read `oc describe pod` like an expert

The **Events** section usually tells the truth.

```bash
oc describe pod <pod_name> -n <namespace>
```

Common event messages:

| Event message | Meaning | Main area |
|---|---|---|
| `0/6 nodes are available: 6 Insufficient cpu` | Requests cannot fit on any node | Capacity/resources |
| `0/6 nodes are available: 6 Insufficient memory` | Memory requests cannot fit | Capacity/resources |
| `node(s) had untolerated taint` | Pod lacks required toleration | Taints/tolerations |
| `node(s) didn't match Pod's node affinity/selector` | Labels and selectors do not match | Placement rules |
| `pod has unbound immediate PersistentVolumeClaims` | PVC cannot bind before scheduling | Storage/PVC |
| `preemption: no victims found` | Evicting lower priority pods cannot help | Priority/preemption |
| `Too many pods` | Node pod density exhausted | Kubelet maxPods / node capacity |
| `Insufficient nvidia.com/gpu` | GPU/device plugin resource shortage | Extended resources |
| `didn't match pod anti-affinity rules` | Required anti-affinity blocks scheduling | Affinity |
| `MatchNodeSelector` | Namespace/project node selector blocks pod | OpenShift project placement |
| `FailedMount` | Scheduled but volume mount failed | Storage/kubelet |
| `FailedCreatePodSandBox` | CNI/runtime issue after scheduling | OVN-Kubernetes/CRI-O |
| `ErrImagePull` or `ImagePullBackOff` | Image pull issue, often shown while phase remains Pending | Registry/image pull |

Important: Events rotate. If the issue is intermittent or old, gather data early.

```bash
oc get events -A --sort-by=.lastTimestamp > /tmp/cluster-events.txt
oc adm must-gather
```

## 6. Case 1: Insufficient CPU

### Symptom

```text
Warning  FailedScheduling  default-scheduler  0/5 nodes are available: 5 Insufficient cpu.
```

### Why it happens

The scheduler uses **requested CPU**, not current CPU usage, to decide whether a pod fits. A node may show low real-time CPU usage, but if existing pods already reserve the allocatable CPU through requests, a new pod cannot be scheduled.

Check pod requests:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.containers[*]}{.name}{" requests="}{.resources.requests}{" limits="}{.resources.limits}{"\n"}{end}'
```

Check node allocatable and allocated resources:

```bash
oc describe node <node_name> | egrep -A20 'Allocatable|Allocated resources'
```

Check all large CPU request consumers:

```bash
oc get pods -A -o custom-columns='NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName,CPU_REQ:.spec.containers[*].resources.requests.cpu,MEM_REQ:.spec.containers[*].resources.requests.memory' | column -t
```

### Production-grade fixes

#### Option A: Correct unrealistic requests

```bash
oc set resources deployment/<deploy> -n <ns> \
  --requests=cpu=200m,memory=256Mi \
  --limits=cpu=1,memory=512Mi
```

Use this only after confirming the workload can run with those requests. Do not blindly reduce requests for critical workloads.

#### Option B: Scale down non-critical workloads

```bash
oc scale deployment/<non_critical_deploy> -n <ns> --replicas=0
```

#### Option C: Add worker capacity

For cloud or Machine API based clusters, add/scale worker machines or configure machine autoscaling.

```bash
oc get machinesets -n openshift-machine-api
oc scale machineset <machineset_name> -n openshift-machine-api --replicas=<count>
```

#### Option D: Use priority and preemption carefully

High-priority pods can preempt lower-priority pods only if preemption can make the pending pod schedulable. Preemption does not solve taints, hard affinity, missing PVC, missing devices, or topology incompatibility.

Check priority:

```bash
oc get priorityclass
oc get pod <pod> -n <ns> -o jsonpath='{.spec.priorityClassName}{" priority="}{.spec.priority}{"\n"}'
```

## 7. Case 2: Insufficient memory

### Symptom

```text
0/4 nodes are available: 4 Insufficient memory.
```

### Root cause

The scheduler uses memory **requests** against node **allocatable** memory. It does not schedule based on current free memory from `free -m`. A node can have free memory but no remaining schedulable allocatable memory because requests are already reserved.

### Commands

```bash
oc describe node <node> | egrep -A20 'Allocatable|Allocated resources'
oc adm top nodes
oc adm top pods -A --sort-by=memory
```

Find workloads with large memory requests:

```bash
oc get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.spec.nodeName}{"\t"}{range .spec.containers[*]}{.resources.requests.memory}{","}{end}{"\n"}{end}' | column -t
```

### Fix options

1. Adjust workload requests/limits after performance validation.
2. Add more worker capacity.
3. Move large workloads to dedicated nodes.
4. Use VPA recommendations if available in your platform process.
5. Avoid setting memory requests equal to huge limits unless needed.

Example:

```bash
oc set resources deployment/api -n app-prod \
  --requests=memory=512Mi,cpu=250m \
  --limits=memory=1Gi,cpu=1
```

## 8. Case 3: Node is `SchedulingDisabled` / cordoned

### Symptom

```bash
oc get nodes
```

```text
NAME       STATUS                     ROLES    AGE
worker-1   Ready,SchedulingDisabled   worker   40d
worker-2   Ready                      worker   40d
```

If most or all suitable nodes are cordoned, pods remain Pending.

### Check

```bash
oc describe node worker-1 | grep -i unschedulable
oc get node worker-1 -o jsonpath='{.spec.unschedulable}{"\n"}'
```

### Fix

Only uncordon after confirming maintenance is complete.

```bash
oc adm uncordon worker-1
```

### Real-world caution

Never uncordon a node blindly during an active MachineConfigPool update, hardware maintenance, disk issue, or incident. Check:

```bash
oc get mcp
oc describe mcp worker
oc get machineconfigpool worker -o yaml
oc get co machine-config
```

### Symptom

```text
0/3 nodes are available: 3 node(s) were not ready.
```

or:

```bash
oc get nodes
```

```text
worker-2   NotReady   worker   15d
```

### Check node conditions

```bash
oc describe node worker-2
```

Look for:

- `Ready=False`
- `MemoryPressure=True`
- `DiskPressure=True`
- `PIDPressure=True`
- `NetworkUnavailable=True`
- `KubeletNotReady`
- `container runtime is down`
- `node.kubernetes.io/unreachable`

### Check Machine API and MachineConfigPool

```bash

oc get machinesets -A

oc get co
```

### Debug node

```bash
oc debug node/worker-2
chroot /host
systemctl status kubelet
systemctl status crio
journalctl -u kubelet -b --no-pager | tail -200
```

```bash
crictl ps -a
```

## 10. Case 5: Untolerated taints

### Symptom

```text
0/5 nodes are available: 2 node(s) had untolerated taint {node-role.kubernetes.io/infra: }, 3 node(s) had untolerated taint {dedicated: database}.
```

### Meaning

A taint repels pods from a node unless the pod has a matching toleration.

Common OpenShift taints:

```text
node-role.kubernetes.io/master:NoSchedule
node-role.kubernetes.io/control-plane:NoSchedule
node-role.kubernetes.io/infra:NoSchedule
dedicated=<team>:NoSchedule
node.kubernetes.io/memory-pressure:NoSchedule
node.kubernetes.io/disk-pressure:NoSchedule
node.kubernetes.io/unreachable:NoSchedule
```

### Check taints

```bash
oc describe node <node> | grep -A5 Taints
oc get nodes -o custom-columns='NODE:.metadata.name,TAINTS:.spec.taints'
```

### Check pod tolerations

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.tolerations'
```

Without `yq`:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.tolerations}{"\n"}'
```

### Fix option A: Add toleration to workload

Example Deployment patch:

```bash
oc patch deployment <deploy> -n <ns> --type='json' -p='[
  {
    "op": "add",
    "path": "/spec/template/spec/tolerations",
    "value": [
      {
        "key": "dedicated",
        "operator": "Equal",
        "value": "database",
        "effect": "NoSchedule"
      }
    ]
  }
]'
```

If tolerations already exist, use a strategic merge patch:

```bash
oc patch deployment <deploy> -n <ns> --type='merge' -p='{
  "spec": {
    "template": {
      "spec": {
        "tolerations": [
          {
            "key": "dedicated",
            "operator": "Equal",
            "value": "database",
            "effect": "NoSchedule"
          }
        ]
      }
    }
  }
}'
```

### Fix option B: Remove incorrect taint

Only remove a taint if it was accidentally applied.

```bash
oc adm taint nodes <node> dedicated=database:NoSchedule-
```

### Expert caution

Do not add tolerations just to make pods run anywhere. Taints are often used to protect:

- control plane nodes
- infra/router/registry nodes
- GPU nodes
- storage nodes
- compliance-isolated nodes
- workload-specific nodes

The correct fix is usually **matching both toleration and node affinity/selector**, not toleration alone.

## 11. Case 6: Node selector mismatch

### Symptom

```text
0/6 nodes are available: 6 node(s) didn't match Pod's node affinity/selector.
```

### Check pod selectors

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeSelector}{"\n"}'
oc get pod <pod> -n <ns> -o yaml | grep -A20 nodeSelector
```

### Check node labels

```bash
oc get nodes --show-labels
oc get nodes -l disktype=ssd
```

### Fix option A: Label appropriate nodes

```bash
oc label node worker-1 disktype=ssd
```

### Fix option B: Correct workload selector

```bash
oc patch deployment <deploy> -n <ns> --type='merge' -p='{
  "spec": {
    "template": {
      "spec": {
        "nodeSelector": {
          "node-role.kubernetes.io/worker": ""
        }
      }
    }
  }
}'
```

### OpenShift project-level node selector

OpenShift can apply a node selector at namespace/project level. This is easy to miss.

Check namespace annotations:

```bash
oc get namespace <ns> -o yaml | grep -i selector -A5
```

Common annotation:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: env=prod
```

If the project selector is wrong, pods in that namespace may never schedule even if the pod spec looks correct.

Patch carefully:

```bash
oc annotate namespace <ns> openshift.io/node-selector- --overwrite
```

or set a correct selector:

```bash
oc annotate namespace <ns> openshift.io/node-selector='env=prod' --overwrite
```

## 12. Case 7: Node affinity / anti-affinity blocks scheduling

### Symptom

```text
0/4 nodes are available: 4 node(s) didn't match Pod's node affinity/selector.
```

or:

```text
0/4 nodes are available: 4 node(s) didn't match pod anti-affinity rules.
```

### Check affinity

```bash
oc get pod <pod> -n <ns> -o yaml | sed -n '/affinity:/,/containers:/p'
```

Important distinction:

- `requiredDuringSchedulingIgnoredDuringExecution` = hard requirement.
- `preferredDuringSchedulingIgnoredDuringExecution` = soft preference.

Hard requirements commonly cause Pending.

### Example problem

```yaml
nodeAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    nodeSelectorTerms:
    - matchExpressions:
      - key: topology.kubernetes.io/zone
        operator: In
        values:
        - zone-a
```

If no node has `topology.kubernetes.io/zone=zone-a`, the pod will not schedule.

### Fix

Check labels:

```bash
oc get nodes -L topology.kubernetes.io/zone
```

Correct the values:

```bash
oc patch deployment <deploy> -n <ns> --type='merge' -p='{
  "spec": {
    "template": {
      "spec": {
        "affinity": null
      }
    }
  }
}'
```

Use this null patch only for testing or after confirming affinity is wrong. In production, preserve the required placement policy and correct labels or node groups.

### Anti-affinity trap

A common mistake is requiring every replica to land on a different hostname with too few nodes.

Example:

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: web
    topologyKey: kubernetes.io/hostname
```

If replicas exceed eligible nodes, extra replicas stay Pending.

Fix options:

1. Add more eligible nodes.
2. Change required anti-affinity to preferred.
3. Reduce replicas.
4. Use topology spread constraints with realistic `maxSkew`.

## 13. Case 8: Topology spread constraints too strict

### Symptom

```text
0/6 nodes are available: 6 node(s) didn't satisfy existing pods anti-affinity rules or topology spread constraints.
```

### Check

```bash
oc get pod <pod> -n <ns> -o yaml | sed -n '/topologySpreadConstraints:/,/containers:/p'
```

Example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: api
```

If the cluster has missing zone labels, uneven zones, or not enough nodes in one zone, pods can remain Pending.

### Fix options

- Ensure all eligible nodes have the topology label.
- Add capacity in the missing zone.
- Change `whenUnsatisfiable` from `DoNotSchedule` to `ScheduleAnyway` if soft spread is acceptable.
- Reduce replica count until capacity is available.

## 14. Case 9: Pod has unbound immediate PVC

### Symptom

```text
0/3 nodes are available: pod has unbound immediate PersistentVolumeClaims.
```

### Meaning

The pod references a PVC that is not `Bound`. The scheduler cannot continue because storage is unresolved.

### Check PVC

```bash
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get pv
oc get sc
```

Check the pod volume reference:

```bash
oc get pod <pod> -n <ns> -o yaml | sed -n '/volumes:/,/containers:/p'
```

### Common PVC causes

| Cause | How to detect | Fix |
|---|---|---|
| No default StorageClass | `oc get sc` has no `(default)` | Specify `storageClassName` or set default SC |
| Wrong StorageClass name | PVC event says class not found | Correct PVC/workload template |
| Dynamic provisioner broken | PVC event mentions provisioner errors | Fix CSI/operator/storage backend |
| No matching static PV | PVC stays Pending; no PV matches size/accessMode/class | Create matching PV or adjust PVC |
| Access mode mismatch | PVC asks RWX but only RWO available | Use compatible storage backend |
| Topology/zone mismatch | PV node affinity conflicts with pod constraints | Align zone, node labels, StorageClass, pod affinity |
| Local PV unavailable | Local disk PV tied to unavailable node | Recover node or create local PV on eligible node |

### Fix example: no default StorageClass

```bash
oc get sc
oc patch storageclass <sc_name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
```

### Fix example: wrong StorageClass in StatefulSet

For StatefulSets, `volumeClaimTemplates` are immutable in many practical workflows. Usually you create a new StatefulSet or migrate data carefully.

```bash
oc get statefulset <sts> -n <ns> -o yaml > /tmp/sts-backup.yaml
```

Plan data migration before deleting PVCs. Deleting a PVC can delete application data depending on PV reclaim policy and storage backend.

## 15. Case 10: `WaitForFirstConsumer` confusion

### Symptom

PVC status:

```text
waiting for first consumer to be created before binding
```

Pod status may be Pending.

### Meaning

With `volumeBindingMode: WaitForFirstConsumer`, PV binding/provisioning is intentionally delayed until a pod exists, so the scheduler can select storage compatible with the selected node or zone.

This is normal for topology-aware storage such as local storage or zonal cloud volumes.

### Check StorageClass

```bash
oc get sc <sc> -o yaml | grep volumeBindingMode -A2
```

### When it is healthy

PVC:

```text
Pending: waiting for first consumer
```

Pod created using the PVC.

Then scheduler and provisioner coordinate placement and provisioning.

### When it becomes a problem

- Pod also has impossible node selector.
- Pod has untolerated taint issue.
- Node affinity conflicts with storage topology.
- CSI provisioner is unhealthy.
- Local PV exists only on nodes that the pod cannot use.

### Troubleshooting

```bash
oc describe pod <pod> -n <ns>
oc describe pvc <pvc> -n <ns>
oc get sc <sc> -o yaml
oc get pv -o wide
oc get csinode
oc get pods -n openshift-cluster-csi-drivers
oc get co storage
```

For ODF:

```bash
oc get pods -n openshift-storage
oc get cephcluster -n openshift-storage
oc get storagecluster -n openshift-storage
```

## 16. Case 11: ResourceQuota blocks pod creation or scheduling

### Symptom examples

Sometimes the pod never appears because admission rejects it:

```text
Error from server (Forbidden): exceeded quota
```

Sometimes controllers show errors while pods remain missing or Pending-like from application perspective.

### Check quota

```bash
oc get resourcequota -n <ns>
oc describe resourcequota -n <ns>
```

Look for:

```text
pods: used 10, hard 10
requests.cpu: used 8, hard 8
requests.memory: used 16Gi, hard 16Gi
limits.cpu: used 20, hard 20
persistentvolumeclaims: used 5, hard 5
requests.storage: used 500Gi, hard 500Gi
```

### Check controller events

```bash
oc describe deployment <deploy> -n <ns>
oc describe replicaset <rs> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp | grep -i quota
```

### Fix options

1. Increase quota after approval.
2. Reduce replicas.
3. Reduce requests if oversized.
4. Delete unused pods/PVCs/secrets/configmaps if object count quota is exhausted.
5. Move workload to a namespace with appropriate quota.

Example quota update:

```bash
oc patch resourcequota app-quota -n <ns> --type='merge' -p='{
  "spec": {
    "hard": {
      "requests.cpu": "10",
      "requests.memory": "20Gi",
      "pods": "50"
    }
  }
}'
```

## 17. Case 12: LimitRange defaulting creates oversized requests

### Symptom

Pod manifest has no requests, but after admission the pod has default requests that make it unschedulable.

### Check LimitRange

```bash
oc get limitrange -n <ns>
oc describe limitrange -n <ns>
```

Check the admitted pod spec:

```bash
oc get pod <pod> -n <ns> -o yaml | grep -A10 resources:
```

Example LimitRange:

```yaml
limits:
- type: Container
  defaultRequest:
    cpu: "2"
    memory: 4Gi
```

A small container with no explicit request now reserves 2 CPU and 4Gi memory.

### Fix

Set realistic requests in workload:

```bash
oc set resources deployment/<deploy> -n <ns> \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi
```

Or correct LimitRange defaults:

```bash
oc edit limitrange <limitrange> -n <ns>
```

## 18. Case 13: Too many pods on node / max pod density

### Symptom

```text
0/3 nodes are available: 3 Too many pods.
```

### Root cause

Each node has a maximum pod capacity. Even if CPU/memory are available, the scheduler will not exceed the pod count capacity.

Check node pod capacity:

```bash
oc get node <node> -o jsonpath='{.status.capacity.pods}{" capacity\n"}{.status.allocatable.pods}{" allocatable\n"}'
```

Check pods per node:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node> | wc -l
```

Better:

```bash
for n in $(oc get nodes -o name | cut -d/ -f2); do
  count=$(oc get pods -A --field-selector spec.nodeName=$n --no-headers 2>/dev/null | wc -l)
  cap=$(oc get node $n -o jsonpath='{.status.allocatable.pods}')
  echo "$n pods=$count allocatable=$cap"
done
```

### Fix options

- Add nodes.
- Reduce daemonset footprint.
- Consolidate tiny workloads.
- Tune max pods only through supported OpenShift mechanisms and after capacity planning.

Do not change kubelet configuration directly on the node. In OpenShift, node configuration is managed through the Machine Config Operator and supported custom resources.

## 19. Case 14: GPU, SR-IOV, hugepages, and extended resources

### Symptom

```text
0/5 nodes are available: 5 Insufficient nvidia.com/gpu.
0/5 nodes are available: 5 Insufficient openshift.io/sriov_netdevice.
```

## 20. Case 15: Control plane / infra node scheduling mistake

### Symptom

Workload is intended to run on master/control-plane or infra nodes but remains Pending due to taints.

### Check roles and taints

```bash
oc get nodes
oc describe node <control_plane_node> | grep -A5 Taints
oc get nodes -l node-role.kubernetes.io/infra=
oc get nodes -l node-role.kubernetes.io/control-plane=
```

### Fix pattern

For infra workloads, use both:

1. `nodeSelector` or affinity for infra node label
2. matching toleration for infra taint

Example:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
```

Do not run arbitrary user workloads on control plane nodes unless your cluster design explicitly supports it.

## 21. Case 16: Namespace/project default node selector

### Why this is OpenShift-specific and important

In OpenShift, projects can have default node selectors. A user may create a pod without any `nodeSelector`, but the effective scheduling can still be constrained by the namespace annotation.

### Symptom

Pod events mention node selector mismatch, but pod YAML does not clearly show a selector.

### Check

```bash
oc get ns <ns> -o yaml | grep -i 'openshift.io/node-selector' -A2
```

### Example

```yaml
metadata:
  annotations:
    openshift.io/node-selector: type=app
```

If no node has `type=app`, all normal pods in that namespace stay Pending.

### Fix

```bash
oc label node worker-1 type=app
```

or remove/update the annotation:

```bash
oc annotate ns <ns> openshift.io/node-selector- --overwrite
```

## 36. Advanced: Understanding scheduler filter failures

When `oc describe pod` says:

```text
0/10 nodes are available: 
2 Insufficient memory,
3 node(s) didn't match Pod's node affinity/selector,
5 node(s) had untolerated taint.
```

Read this as:

- The scheduler evaluated 10 nodes.
- No node passed all filters.
- Different nodes failed for different reasons.
- You need at least one node that satisfies **all** constraints at the same time.

A common mistake is fixing only one filter. Example:

- You add toleration for infra taint.
- But infra nodes still do not have enough memory.
- Pod remains Pending.

Always build a feasible-node matrix.

### Feasible node matrix example

| Node | Ready | Schedulable | Taint tolerated | Label match | CPU fit | Memory fit | PVC topology | Result |
|---|---|---|---|---|---|---|---|---|
| worker-1 | Yes | Yes | Yes | No | Yes | Yes | Yes | Fail label |
| worker-2 | Yes | Yes | No | Yes | Yes | Yes | Yes | Fail taint |
| worker-3 | Yes | Yes | Yes | Yes | No | Yes | Yes | Fail CPU |
| worker-4 | Yes | Yes | Yes | Yes | Yes | Yes | No | Fail storage |

You need one row with all `Yes`.

## 40. Production incident workflow

### Step 1: Identify blast radius

```bash
oc get pods -A | egrep 'Pending|ContainerCreating|ImagePullBackOff|ErrImagePull'
oc get pods -A -o wide | grep Pending
```

Ask:

- One namespace or many?
- One node or many?
- One workload type or all workloads?
- Only storage workloads?
- Only GPU/SR-IOV workloads?
- Only after recent deployment or cluster upgrade?

### Step 2: Classify Pending type

```bash
oc get pod <pod> -n <ns> -o wide
```

- `NODE=<none>` = scheduler problem.
- `NODE=<node>` = kubelet/runtime/storage/network/image problem.

### Step 3: Capture evidence

```bash
mkdir -p pending-debug
oc get pod <pod> -n <ns> -o yaml > pending-debug/pod.yaml
oc describe pod <pod> -n <ns> > pending-debug/pod-describe.txt
oc get events -n <ns> --sort-by=.lastTimestamp > pending-debug/events.txt
oc get nodes -o wide > pending-debug/nodes.txt
oc describe nodes > pending-debug/nodes-describe.txt
oc get pvc,pv,sc -A > pending-debug/storage.txt
oc get quota,limitrange -n <ns> -o yaml > pending-debug/quota-limits.yaml
oc get co > pending-debug/clusteroperators.txt
oc get mcp > pending-debug/mcp.txt
```

### Step 4: Apply least-risk fix

Preferred production fix order:

1. Correct obvious bad workload spec.
2. Scale non-critical workloads down if capacity incident.
3. Add capacity.
4. Correct labels/taints only if change is intended.
5. Fix storage/CNI/runtime operator.
6. Restart node services only after evidence capture and impact review.
7. Reboot/drain node if node-specific and service restart is insufficient.

### Step 5: Verify

```bash
oc get pod <pod> -n <ns> -w
oc describe pod <pod> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp | tail -30
```

### Step 6: Prevent recurrence

- Right-size requests and limits.
- Maintain namespace quota dashboards.
- Monitor Pending pods cluster-wide.
- Alert on `FailedScheduling` events.
- Ensure MachineAutoscaler covers all workload pools.
- Keep node labels/taints documented.
- Test storage classes and topology during platform changes.
- Review anti-affinity and topology spread before scaling replicas.

## 41. Monitoring and alerting ideas

### Prometheus queries

Pods in Pending:

```promql
sum by (namespace, pod) (kube_pod_status_phase{phase="Pending"} == 1)
```

Pending pods by namespace:

```promql
sum by (namespace) (kube_pod_status_phase{phase="Pending"} == 1)
```

Unschedulable pods:

```promql
sum by (namespace, pod) (kube_pod_status_unschedulable == 1)
```

Node not ready:

```promql
kube_node_status_condition{condition="Ready",status="true"} == 0
```

Node pressure:

```promql
kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"} == 1
```

CPU request saturation:

```promql
sum(kube_pod_container_resource_requests{resource="cpu"}) by (node)
/
sum(kube_node_status_allocatable{resource="cpu"}) by (node)
```

Memory request saturation:

```promql
sum(kube_pod_container_resource_requests{resource="memory"}) by (node)
/
sum(kube_node_status_allocatable{resource="memory"}) by (node)
```

### Alerting recommendations

Alert when:

- Pod Pending > 10 minutes for production namespace.
- Unschedulable pods > 0 for critical apps.
- Node allocatable CPU request saturation > 90%.
- Node allocatable memory request saturation > 90%.
- PVC Pending > 10 minutes.
- Scheduler operator degraded.
- Storage/network cluster operator degraded.
- MachineAutoscaler at max while unschedulable pods exist.

## 42. Common mistakes by junior admins

1. Looking only at `oc get pods` and not `oc describe pod`.
2. Confusing actual CPU usage with requested CPU reservation.
3. Removing taints from infra/control-plane nodes without understanding design.
4. Deleting PVCs to fix Pending StatefulSet pods.
5. Patching Operator-managed Deployments directly.
6. Ignoring namespace-level node selector.

## 43. Interview / real-time troubleshooting explanation

When asked, “A pod is stuck in Pending, what will you check?” answer like this:

> First I check whether the pod is unscheduled or already assigned to a node using `oc get pod -o wide`. If `NODE` is empty, I focus on scheduler events from `oc describe pod`, especially insufficient resources, taints, node selectors, affinity, PVC binding, quota, extended resources, and node readiness. If `NODE` is assigned but the pod is still Pending or ContainerCreating, I move to kubelet-side causes such as image pull, volume mount, CNI sandbox creation, CRI-O, or node pressure. I also check namespace quota and LimitRange, project node selector, node labels/taints, PVC/PV/StorageClass, cluster operators, MCP status, and scheduler logs if the issue is cluster-wide. I avoid risky fixes like deleting PVCs or removing taints until I know the exact scheduling filter failure.

## 44. Quick runbook

```bash
# 1. Set variables
NS=<namespace>
POD=<pod>

# 2. Is it scheduled?
oc get pod $POD -n $NS -o wide
oc get pod $POD -n $NS -o jsonpath='{.spec.nodeName}{"\n"}'

# 3. Read events
oc describe pod $POD -n $NS
oc get events -n $NS --sort-by=.lastTimestamp | tail -50

# 4. Check namespace controls
oc describe quota -n $NS
oc describe limitrange -n $NS
oc get ns $NS -o yaml | grep -i node-selector -A3

# 5. Check nodes
oc get nodes
oc get nodes --show-labels
oc describe node <node>
oc adm top nodes

# 6. Check taints/tolerations
oc get nodes -o custom-columns='NODE:.metadata.name,TAINTS:.spec.taints'
oc get pod $POD -n $NS -o jsonpath='{.spec.tolerations}{"\n"}'

# 7. Check affinity/selectors
oc get pod $POD -n $NS -o jsonpath='{.spec.nodeSelector}{"\n"}'
oc get pod $POD -n $NS -o yaml | grep -A40 affinity:

# 8. Check storage
oc get pvc -n $NS
oc describe pvc <pvc> -n $NS
oc get pv
oc get sc
oc get volumeattachment

# 9. If scheduled to node, debug node-side
NODE=$(oc get pod $POD -n $NS -o jsonpath='{.spec.nodeName}')
oc debug node/$NODE
chroot /host
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200

# 10. Cluster health
oc get co
oc get mcp
oc get pods -n openshift-kube-scheduler
oc get pods -n openshift-ovn-kubernetes
oc get pods -n openshift-cluster-csi-drivers
```

## 45. Root cause mapping table

| Symptom | Check first | Likely fix |
|---|---|---|
| `Insufficient cpu` | Pod requests, node allocatable | Right-size requests, add nodes, scale down workloads |
| `Insufficient memory` | Requests vs allocatable | Right-size memory, add nodes |
| `Too many pods` | Node pod capacity | Add nodes, reduce pod density |
| `Untolerated taint` | Node taints, pod tolerations | Add correct toleration or use correct node pool |
| `Node affinity/selector mismatch` | Pod selector, namespace selector, node labels | Correct labels/selectors |
| `Pod anti-affinity` | Required anti-affinity, replica count | Add nodes or soften anti-affinity |
| `Topology spread` | Zone labels, maxSkew, DoNotSchedule | Add zone capacity or change policy |
| `Unbound immediate PVC` | PVC/PV/SC events | Fix StorageClass/provisioner/PV/access mode |
| `WaitForFirstConsumer` stuck | Pod + PVC + topology | Fix pod constraints or CSI/storage topology |
| `Insufficient GPU` | Extended resources | Add GPU nodes, fix device plugin |
| `SchedulerName custom` | `.spec.schedulerName` | Restore scheduler or correct schedulerName |
| `NODE assigned + FailedMount` | Kubelet/PVC/VolumeAttachment | Fix CSI/backend/mount issue |
| `NODE assigned + FailedCreatePodSandBox` | OVN/CRI-O/kubelet | Fix CNI/runtime/node |
| `ErrImagePull` | Image, pull secret, registry | Fix image/pull secret/proxy/CA |
| Many namespaces affected | `oc get co`, scheduler/network/storage | Platform-level incident |
| One node affected | `oc describe node`, node logs | Cordon/drain/reboot or fix node |

## 46. Senior admin checklist before closing incident

- [ ] Confirmed whether Pending was scheduler-side or node-side.
- [ ] Captured pod YAML, describe output, and events.
- [ ] Identified exact scheduler filter or kubelet failure.
- [ ] Checked quota, LimitRange, namespace node selector.
- [ ] Checked node labels, taints, readiness, pressure, allocatable resources.
- [ ] Checked PVC/PV/StorageClass if volumes are used.
- [ ] Checked owning controller/operator.
- [ ] Applied least-risk fix.
- [ ] Verified new pod reached Running and Ready.
- [ ] Verified application health, not only pod phase.
- [ ] Added monitoring/prevention action.
- [ ] Documented root cause and corrective action.

## 47. Final summary

A pod stuck in `Pending` is not one issue. It is a symptom that the pod has not completed the path from API admission to scheduler binding to kubelet container creation.

The fastest expert method is:

1. Check `NODE` in `oc get pod -o wide`.
2. If `NODE` is empty, troubleshoot scheduler constraints.
3. If `NODE` exists, troubleshoot kubelet, CRI-O, CNI, image pull, or storage.
4. Use `oc describe pod` events as the primary source of truth.
5. Always check OpenShift-specific controls: project node selector, SCC/admission behavior, ClusterOperators, MachineConfigPool, Operators, and storage/network operators.
6. Fix the exact failed filter, not the symptom.
