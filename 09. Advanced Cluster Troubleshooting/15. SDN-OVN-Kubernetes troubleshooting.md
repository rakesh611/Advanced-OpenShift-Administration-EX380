# SDN/OVN-Kubernetes Troubleshooting for Advanced OpenShift Administration

**Audience:** Senior Linux/OpenShift/Kubernetes administrators with production operations experience  
**Skill level:** Advanced / L3 / platform engineering  
**Focus:** OpenShift cluster networking, legacy OpenShift SDN context, OVN-Kubernetes troubleshooting, packet path analysis, failure isolation, and recovery runbooks  
**Format:** Single Markdown runbook

---

## 1. Executive Summary

In OpenShift, most “network issues” are not purely network issues. They are usually a combination of one or more of the following:

- Pod scheduling or CNI attachment failure
- Node-level network configuration drift
- MTU mismatch
- DNS resolution failure
- NetworkPolicy or EgressFirewall blocking traffic
- Service selector or endpoint mismatch
- Route/Ingress misconfiguration
- OVN logical database, OVS, or flow programming problem
- Firewall/security-group/ACL issue outside the cluster
- Certificate or API reachability issue that looks like networking
- Node resource pressure causing networking DaemonSet instability

For a senior OpenShift administrator, the key is not to randomly restart pods. The key is to identify the failing traffic path, isolate the layer, compare desired state with actual state, and collect enough evidence before making changes.

This guide explains how to troubleshoot both **legacy OpenShift SDN** and modern **OVN-Kubernetes**, with the primary focus on OVN-Kubernetes because it is the default and current OpenShift networking provider in modern OpenShift 4.x releases.

> Important version note: OpenShift SDN is legacy. It was deprecated in earlier OpenShift 4 releases, unavailable for new installations from OpenShift 4.15, and removed/not supported from OpenShift 4.17 onward. For current clusters, expect OVN-Kubernetes unless you are maintaining an older cluster.

## 2. Quick Mental Model

### 2.1 What OpenShift networking must provide

OpenShift networking must allow:

1. Pod-to-pod communication inside the same namespace.
2. Pod-to-pod communication across namespaces, unless restricted by policy.
3. Pod-to-service communication through ClusterIP services.
4. Pod-to-external communication through node gateway/egress path.
5. External-to-application communication through Routes, Ingress, LoadBalancer, or NodePort.
6. DNS resolution through CoreDNS/DNS Operator.
7. Network security enforcement using NetworkPolicy, EgressFirewall, EgressIP, and related OVN constructs.
8. Stable cluster control-plane communication between nodes, API, operators, and kubelet.

When any of these break, always ask:

- Which direction is broken?
- Which protocol and port?
- Is it same-node or cross-node?
- Is DNS failing or is raw IP failing?
- Is only one namespace affected or the whole cluster?
- Is only one node affected or all nodes?
- Is the application listening on the expected port?
- Is the OpenShift Service selecting the correct pods?
- Are endpoints present?
- Is traffic blocked by Kubernetes NetworkPolicy, EgressFirewall, cloud firewall, local firewall, or corporate firewall?

## 3. OpenShift SDN vs OVN-Kubernetes

### 3.1 Legacy OpenShift SDN

OpenShift SDN was the older CNI plugin used by OpenShift. It used an overlay network and implemented isolation depending on the configured mode, such as network policy mode.

Common OpenShift SDN troubleshooting areas:

- `openshift-sdn` namespace
- `sdn` DaemonSet pods
- VXLAN overlay
- Node subnet assignment
- NetNamespace objects in older OpenShift versions
- iptables rules
- NetworkPolicy mode behavior
- EgressIP behavior

In older clusters, you might see components such as:

```bash
oc get pods -n openshift-sdn
oc get ds -n openshift-sdn
oc logs -n openshift-sdn ds/sdn
```

However, for current OpenShift versions, you should treat OpenShift SDN as legacy. Do not design new troubleshooting procedures around SDN unless your cluster still runs an older supported version.

### 3.2 OVN-Kubernetes

OVN-Kubernetes is the current primary OpenShift networking provider. It is based on **OVN** and **Open vSwitch (OVS)**. It programs logical networking in OVN databases and translates that into OVS/OpenFlow rules on each node.

Key characteristics:

- Uses OVN logical switches, logical routers, ACLs, logical ports, and load balancers.
- Uses OVS on each node.
- Uses Geneve overlay encapsulation for cross-node pod traffic.
- Implements Kubernetes Service handling using OVN load-balancer constructs.
- Implements NetworkPolicy as OVN ACLs.
- Supports egress features such as EgressIP, EgressFirewall, and EgressService depending on OpenShift version and configuration.
- Runs its main components in `openshift-ovn-kubernetes`.

## 4. OVN-Kubernetes Architecture for Troubleshooting

### 4.1 Important namespaces

```bash
oc get ns | egrep 'openshift-ovn-kubernetes|openshift-network|openshift-dns|openshift-ingress|openshift-ingress-operator'
```

Important namespaces:

| Namespace | Purpose |
|---|---|
| `openshift-ovn-kubernetes` | OVN-Kubernetes control plane and node networking pods |
| `openshift-network-operator` | Cluster Network Operator |
| `openshift-dns` | CoreDNS pods and DNS services |
| `openshift-ingress` | Router pods for Routes |
| `openshift-ingress-operator` | Ingress Operator |
| `openshift-machine-config-operator` | Node OS and network config rollout impact |

### 4.2 Important operators

```bash
oc get co network dns ingress kube-apiserver authentication machine-config
```

Pay attention to:

- `network`
- `dns`
- `ingress`
- `machine-config`
- `kube-apiserver`

Network symptoms are often caused by another degraded operator. For example:

- DNS degraded can look like service failure.
- Ingress degraded can look like application network failure.
- MachineConfigPool degraded can leave node network configuration inconsistent.
- API degradation can prevent CNI reconciliation.

### 4.3 Main OVN-Kubernetes resources

```bash
oc get all -n openshift-ovn-kubernetes
oc get cm -n openshift-ovn-kubernetes
oc get ds -n openshift-ovn-kubernetes
oc get deploy -n openshift-ovn-kubernetes
oc get pods -n openshift-ovn-kubernetes -o wide
```

Common components include:

| Component | Type | Purpose |
|---|---|---|
| `ovnkube-node` | DaemonSet | Runs OVN/OVS node-side components on every node |
| `ovnkube-control-plane` | Deployment | Cluster-level OVN-Kubernetes control-plane functions |
| `ovnkube-controller` | Container | Handles Kubernetes object reconciliation into OVN state |
| `ovn-controller` | Container | Programs OVS flows from OVN Southbound state |
| `northd` | Container | Translates OVN Northbound logical config into Southbound logical flows |
| `nbdb` | Container | OVN Northbound database |
| `sbdb` | Container | OVN Southbound database |
| `ovn-acl-logging` | Container | ACL logging support |

Container names can vary slightly by OpenShift release, so always confirm with:

```bash
POD=$(oc get pod -n openshift-ovn-kubernetes -l app=ovnkube-node -o jsonpath='{.items[0].metadata.name}')
oc get pod -n openshift-ovn-kubernetes "$POD" -o jsonpath='{.spec.containers[*].name}' ; echo
```

### 4.4 Logical architecture

A simplified data flow is:

```text
Kubernetes API objects
        |
        v
OVN-Kubernetes controller
        |
        v
OVN Northbound DB
        |
        v
ovn-northd
        |
        v
OVN Southbound DB
        |
        v
ovn-controller on each node
        |
        v
Open vSwitch / OpenFlow rules
        |
        v
Pod traffic forwarding
```

When troubleshooting, this means you must compare:

1. Kubernetes desired state: Pods, Services, Endpoints, NetworkPolicies.
2. OVN logical state: logical switches, logical ports, routers, ACLs, load balancers.
3. OVS datapath state: bridges, ports, flows, interfaces.
4. Actual packet behavior: curl, nc, tcpdump, ovnkube-trace.

## 5. First 15-Minute Triage

### 5.1 Confirm cluster health

```bash
oc whoami
oc get clusterversion
oc get co
oc get nodes
oc get mcp
oc get pods -A | egrep -v 'Running|Completed'
```

Look for:

- `network` ClusterOperator degraded/progressing
- Nodes `NotReady`
- `ovnkube-node` pods not running on one or more nodes
- DNS pods crashlooping
- Ingress routers not ready
- MachineConfigPools stuck updating

### 5.2 Identify the failing traffic path

Use this decision table before deep debugging.

| Failing path | First checks |
|---|---|
| Pod cannot start, CNI error | Pod events, `ovnkube-node` on that node, kubelet logs, CRI-O logs |
| Pod-to-pod same namespace fails | Pod IPs, app listener, NetworkPolicy, same-node vs cross-node |
| Pod-to-pod cross namespace fails | NetworkPolicy, namespace labels, pod labels, service selectors |
| Pod-to-service fails | Service selector, endpoints/endpointslices, targetPort, kube service translation |
| Pod-to-external fails | DNS, node egress, EgressFirewall, EgressIP, external firewall, proxy |
| External-to-route fails | Route, router pod, service endpoints, TLS, wildcard DNS, ingress operator |
| Only one node affected | `ovnkube-node`, OVS, MTU, node firewall, cloud SG, NIC, routing |
| Only DNS names fail | DNS Operator/CoreDNS, `/etc/resolv.conf`, NetworkPolicy to DNS |
| Only large packets fail | MTU/Geneve overlay/path MTU issue |

### 5.3 Check OVN pods quickly

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc get ds -n openshift-ovn-kubernetes
oc get deploy -n openshift-ovn-kubernetes
```

Check logs:

```bash
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --all-containers --tail=50
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-control-plane --all-containers --tail=50
```

For one node:

```bash
NODE=<node-name>
POD=$(oc get pod -n openshift-ovn-kubernetes -l app=ovnkube-node -o wide | awk -v n="$NODE" '$0 ~ n {print $1; exit}')
echo "$POD"
oc logs -n openshift-ovn-kubernetes "$POD" -c ovnkube-controller --tail=100
oc logs -n openshift-ovn-kubernetes "$POD" -c ovn-controller --tail=100
oc logs -n openshift-ovn-kubernetes "$POD" -c northd --tail=100
```

If container names differ:

```bash
oc get pod -n openshift-ovn-kubernetes "$POD" -o jsonpath='{.spec.containers[*].name}' ; echo
```

### 5.4 Describe the Network ClusterOperator

```bash
oc describe co network
oc get co network -o yaml
```

Look for:

- `Available=False`
- `Degraded=True`
- `Progressing=True` for too long
- CNO messages about rendering, daemonset rollout, invalid config, MTU, IPsec, migration, or unsupported changes

### 5.5 Check configured network type

```bash
oc get network.operator.openshift.io cluster -o yaml
oc get network.config.openshift.io cluster -o yaml
```

Expected modern output normally shows:

```yaml
spec:
  defaultNetwork:
    type: OVNKubernetes
```

Remember: the default network plugin type cannot be casually changed after installation. Treat network type migration as a major maintenance activity, not a troubleshooting shortcut.

## 6. Golden Rule: Define the Failure Precisely

Before you troubleshoot OVN internals, reproduce the problem with controlled test pods.

### 6.1 Create test namespaces

```bash
oc new-project net-a
oc new-project net-b
```

### 6.2 Create test pods

```bash
oc run web-a -n net-a --image=registry.access.redhat.com/ubi9/httpd-24 --restart=Never
oc run client-b -n net-b --image=registry.access.redhat.com/ubi9/ubi --restart=Never -- sleep 36000
```

If external registry access is blocked, use your internal registry image.

### 6.3 Check pod IP and placement

```bash
oc get pod -n net-a -o wide
oc get pod -n net-b -o wide
```

### 6.4 Test raw IP before DNS/service

```bash
WEBIP=$(oc get pod web-a -n net-a -o jsonpath='{.status.podIP}')
oc exec -n net-b client-b -- curl -sv --connect-timeout 3 http://$WEBIP:8080/ || true
```

### 6.5 Test service next

```bash
oc expose pod web-a -n net-a --port=8080 --target-port=8080 --name=web-a
oc get svc,endpoints,endpointslice -n net-a
oc exec -n net-b client-b -- curl -sv --connect-timeout 3 http://web-a.net-a.svc.cluster.local:8080/ || true
```

### 6.6 Test route last

```bash
oc expose svc web-a -n net-a
oc get route -n net-a
```

This order is important:

1. Pod IP works but Service fails → Service/endpoints/OVN LB issue.
2. Service works but DNS name fails → DNS issue.
3. ClusterIP works but Route fails → Ingress/router/route issue.
4. Same-node works but cross-node fails → overlay/Geneve/MTU/node firewall issue.
5. Small packets work but large packets fail → MTU/path MTU issue.

## 7. CNI Attachment and Pod Sandbox Failures

### 7.1 Symptoms

Typical symptoms:

```text
FailedCreatePodSandBox
failed to setup network for sandbox
CNI plugin error
failed to configure pod interface
error adding container to network
Multus: error invoking delegate
context deadline exceeded
```

### 7.2 First checks

```bash
NS=<namespace>
POD=<pod>
oc describe pod -n "$NS" "$POD"
oc get pod -n "$NS" "$POD" -o yaml
```

Check the node:

```bash
NODE=$(oc get pod -n "$NS" "$POD" -o jsonpath='{.spec.nodeName}')
echo "$NODE"
oc get node "$NODE" -o wide
oc describe node "$NODE"
```

Check OVN on that node:

```bash
OVNPOD=$(oc get pod -n openshift-ovn-kubernetes -l app=ovnkube-node -o wide | awk -v n="$NODE" '$0 ~ n {print $1; exit}')
echo "$OVNPOD"
oc get pod -n openshift-ovn-kubernetes "$OVNPOD" -o wide
oc logs -n openshift-ovn-kubernetes "$OVNPOD" --all-containers --tail=200
```

Check kubelet and CRI-O from node debug:

```bash
oc debug node/$NODE
chroot /host
journalctl -u kubelet --since "30 min ago" --no-pager
journalctl -u crio --since "30 min ago" --no-pager
exit
exit
```

### 7.3 Common root causes

| Root cause | Evidence | Action |
|---|---|---|
| `ovnkube-node` not running | DaemonSet pod missing/crashloop | Fix node pressure, image pull, SCC, config, or CNO issue |
| Node NotReady | `oc get nodes` | Troubleshoot kubelet, CRI-O, network reachability to API |
| Stale CNI state | Repeated sandbox creation errors on one node | Drain node, restart kubelet/CRI-O only with change control |
| Disk pressure | Node conditions, image GC failures | Free disk, fix logs/images, check `/var/lib/containers` |
| Invalid NetworkAttachmentDefinition | Multus errors | Fix NAD config, namespace, plugin config |
| MTU mismatch | CNI completes but traffic breaks | Fix MTU consistently through CNO/MachineConfig/cloud network |
| OVS bridge issue | Missing `br-int` or ports | Check OVS state; involve support if DB/OVS corrupted |

### 7.4 Do not immediately delete OVN pods

Deleting `ovnkube-node` pods may hide evidence and cause disruption. First collect:

```bash
oc adm must-gather
oc get co network -o yaml > network-co.yaml
oc get pods -n openshift-ovn-kubernetes -o wide > ovn-pods.txt
oc logs -n openshift-ovn-kubernetes "$OVNPOD" --all-containers --previous --tail=500 > ovn-prev.log || true
oc logs -n openshift-ovn-kubernetes "$OVNPOD" --all-containers --tail=500 > ovn-current.log || true
```

Then take controlled action.

```bash
POD=<ovnkube-node-pod>

```

### 8.2 View all recent logs

```bash
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --all-containers --tail=100
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-control-plane --all-containers --tail=100
```

### 8.3 View a specific container

```bash
oc logs -n openshift-ovn-kubernetes "$POD" -c ovn-controller --tail=200
oc logs -n openshift-ovn-kubernetes "$POD" -c ovnkube-controller --tail=200
oc logs -n openshift-ovn-kubernetes "$POD" -c northd --tail=200
oc logs -n openshift-ovn-kubernetes "$POD" -c nbdb --tail=200
oc logs -n openshift-ovn-kubernetes "$POD" -c sbdb --tail=200
```

### 8.4 Follow logs during reproduction

```bash
oc logs -n openshift-ovn-kubernetes "$POD" -c ovn-controller -f
```

In another terminal, reproduce:

```bash
oc exec -n <client-ns> <client-pod> -- curl -sv --connect-timeout 3 <target>
```

### 8.5 What to search in logs

```bash
oc logs -n openshift-ovn-kubernetes "$POD" --all-containers --tail=1000 | egrep -i \
'error|failed|timeout|denied|refused|no route|mtu|geneve|ovs|ovn|acl|egress|ipam|panic|leader|db|raft'
```

Important patterns:

| Log pattern | Possible meaning |
|---|---|
| `failed to transact` | OVN DB transaction problem |
| `connection refused` to NB/SB DB | OVN database connectivity issue |
| `failed to add logical port` | Pod logical port reconciliation problem |
| `no pod annotation` | CNI or controller annotation race/problem |
| `failed to configure management port` | Node management port issue |
| `timeout` | API, DB, or node overload |
| `failed to assign egress IP` | EgressIP node label/IP conflict/routing issue |
| `ACL` messages | NetworkPolicy/EgressFirewall behavior |

## 9. Node-Level OVN and OVS Inspection

Many serious OVN issues require node-level inspection.

### 9.1 Enter node debug shell

```bash
NODE=<node-name>
oc debug node/$NODE
chroot /host
```

### 9.2 Check node network basics

```bash
ip addr
ip route
ip rule
nmcli con show
nmcli dev status
hostname -f
systemctl status ovs-vswitchd --no-pager
systemctl status ovsdb-server --no-pager
journalctl -u ovs-vswitchd --since "30 min ago" --no-pager
journalctl -u ovsdb-server --since "30 min ago" --no-pager
```

### 9.3 Check OVS bridges

```bash
ovs-vsctl show
ovs-vsctl list-br
ovs-vsctl list-ports br-int
ovs-ofctl show br-int
ovs-ofctl dump-flows br-int | head -50
```

Common bridges/interfaces:

| Object | Meaning |
|---|---|
| `br-int` | Integration bridge used by OVN/OVS |
| `ovn-k8s-mp0` | OVN-Kubernetes management port on node |
| pod veth/interface | Pod connection into OVS |
| Geneve tunnel interfaces | Cross-node overlay tunnels |

### 9.4 Check OVN controller status

Depending on host tools and release, these may be available:

```bash
ovn-appctl -t ovn-controller status || true
ovs-appctl -t ovs-vswitchd vlog/list || true
ovs-vsctl get Open_vSwitch . external_ids || true
```

Useful fields in `external_ids` might include chassis and OVN remote details.

### 9.5 Check packet counters

```bash
ip -s link
ovs-ofctl dump-ports br-int
ovs-ofctl dump-flows br-int | egrep -i 'drop|controller|ct|actions' | head -100
```

Counters help you answer:

- Is traffic reaching the node?
- Is traffic entering OVS?
- Is traffic being dropped?
- Are flows installed?
- Is the correct tunnel being used?

## 10. Pod-to-Pod Troubleshooting

### 10.1 Same-node vs cross-node test

```bash
oc get pod -A -o wide | egrep '<pod-a>|<pod-b>'
```

If both pods are on the same node and communication works, but cross-node fails, focus on:

- Geneve overlay
- MTU
- node-to-node firewall
- cloud security groups
- physical network ACLs
- OVS tunnel state

If same-node also fails, focus on:

- application listener
- pod IP/interface
- NetworkPolicy
- OVN ACLs
- CNI attachment

### 10.2 Test from debug pod

```bash
oc run netshoot -n <ns> --image=nicolaka/netshoot --restart=Never -- sleep 36000
```

If external image is unavailable, use UBI and install/debug with available tools, or use an internally mirrored troubleshooting image.

```bash
oc exec -it -n <ns> netshoot -- bash
ip addr
ip route
curl -sv <target-ip>:<port>
nc -vz <target-ip> <port>
```

In exam/lab environments, minimal images often do not include `nc`, `telnet`, `dig`, or `tcpdump`. Use an image that has troubleshooting tools or test with `curl` and shell redirection:

```bash
timeout 3 bash -c '</dev/tcp/<ip>/<port>' && echo open || echo closed
```

### 10.3 Verify target pod is listening

```bash
oc exec -n <target-ns> <target-pod> -- ss -lntup || true
oc exec -n <target-ns> <target-pod> -- curl -sv localhost:<port> || true
```

If the application is not listening, OVN is not the root cause.

### 10.4 Verify labels and namespaces

```bash
oc get pod -n <target-ns> --show-labels
oc get ns --show-labels
```

NetworkPolicy selectors depend on labels. One wrong label can cause complete denial.

## 11. Service and Endpoint Troubleshooting

A large percentage of “network” incidents are Service selector or targetPort mistakes.

### 11.1 Check Service

```bash
oc get svc -n <ns> <svc> -o yaml
oc describe svc -n <ns> <svc>
```

Verify:

- `spec.selector`
- `spec.ports[].port`
- `spec.ports[].targetPort`
- `spec.type`
- `clusterIP`

### 11.2 Check endpoints

```bash
oc get endpoints -n <ns> <svc> -o wide
oc get endpointslice -n <ns> -l kubernetes.io/service-name=<svc> -o yaml
```

If endpoints are empty:

```bash
oc get pod -n <ns> --show-labels
oc get pod -n <ns> -l <selector-from-service> -o wide
```

No endpoints means traffic has nowhere to go. Fix labels, readiness probes, or selectors before touching OVN.

### 11.3 Check readiness impact

A pod can be running but not an endpoint if readiness fails.

```bash
oc describe pod -n <ns> <pod>
oc get pod -n <ns> <pod> -o jsonpath='{.status.conditions}' | jq .
```

Common issue:

```yaml
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
```

But application listens on 8443 or path is wrong. Service endpoints stay empty.

### 11.4 OVN Service load balancer issue suspicion

Only suspect OVN service translation if:

- Service has correct endpoints.
- Pod IP direct connection works.
- ClusterIP connection fails.
- NetworkPolicy is not blocking.
- DNS resolves correctly.

Then collect:

```bash
oc get svc,endpoints,endpointslice -n <ns> <svc> -o yaml
oc get pods -n openshift-ovn-kubernetes -o wide
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node --all-containers --tail=500
```

Use `ovnkube-trace` if available.

## 12. DNS Troubleshooting

DNS failures often look like network failures.

### 12.1 Quick DNS checks

```bash
oc get co dns
oc get pods -n openshift-dns -o wide
oc get svc -n openshift-dns
oc logs -n openshift-dns -l dns.operator.openshift.io/daemonset-dns=default --tail=100
```

From a pod:

```bash
oc exec -n <ns> <pod> -- cat /etc/resolv.conf
oc exec -n <ns> <pod> -- getent hosts kubernetes.default.svc.cluster.local
oc exec -n <ns> <pod> -- getent hosts <svc>.<ns>.svc.cluster.local
```

If `dig` exists:

```bash
oc exec -n <ns> <pod> -- dig kubernetes.default.svc.cluster.local
```

### 12.2 DNS service path

```bash
oc get svc -n openshift-dns dns-default -o wide
oc get endpoints -n openshift-dns dns-default -o wide
```

Test DNS service IP:

```bash
DNSIP=$(oc get svc -n openshift-dns dns-default -o jsonpath='{.spec.clusterIP}')
oc exec -n <ns> <pod> -- nslookup kubernetes.default.svc.cluster.local $DNSIP || true
```

### 12.3 NetworkPolicy blocking DNS

If a namespace has default-deny egress, DNS may be blocked. Allow DNS to `openshift-dns`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: app-ns
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 5353
    - protocol: TCP
      port: 5353
```

Check actual DNS port in your cluster before applying. OpenShift DNS commonly exposes DNS on port 5353 behind the service.

## 13. NetworkPolicy Troubleshooting

### 13.1 Core rule

In Kubernetes, once a pod is selected by an ingress NetworkPolicy, only allowed ingress traffic is permitted. Once selected by an egress NetworkPolicy, only allowed egress traffic is permitted.

OVN-Kubernetes implements NetworkPolicy using OVN ACLs.

### 13.2 List policies

```bash
oc get netpol -A
oc describe netpol -n <ns>
oc get netpol -n <ns> -o yaml
```

### 13.3 Common mistakes

| Mistake | Symptom |
|---|---|
| Policy created in wrong namespace | No effect or wrong pods blocked |
| `podSelector` selects wrong pods | Traffic unexpectedly allowed/denied |
| Missing namespace label | Cross-namespace allow rule does not match |
| Wrong port number | TCP connect timeout/refused |
| Wrong protocol | UDP/TCP mismatch |
| Forgot DNS egress | Apps cannot resolve names |
| Default deny applied too broadly | Namespace outage |
| Confusing service labels with pod labels | Rule does not match traffic source/destination |

### 13.4 Debug policy matching

Check namespace labels:

```bash
oc get ns --show-labels
oc get ns <ns> -o yaml
```

Check pod labels:

```bash
oc get pod -n <ns> --show-labels
```

Check policy YAML:

```bash
oc get netpol -n <ns> <policy> -o yaml
```

### 13.5 Controlled test

Create a temporary allow-all policy to prove policy is the blocker:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: temp-allow-all
  namespace: target-ns
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - {}
  egress:
  - {}
```

Apply only in a controlled maintenance/test window:

```bash
oc apply -f temp-allow-all.yaml
```

If traffic starts working, the root cause is policy. Remove temporary policy:

```bash
oc delete netpol temp-allow-all -n target-ns
```

### 13.6 Example: allow MySQL from checker namespace

Scenario:

- DB namespace: `database`
- Source namespace: `checker`
- Source pod label: `deployment=web-mysq`
- Destination pod label: `app=mysql`
- Port: TCP 3306

Label source namespace:

```bash
oc label ns checker team=devsecops --overwrite
```

Policy in destination namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: mysql-db-conn
  namespace: database
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          team: devsecops
      podSelector:
        matchLabels:
          deployment: web-mysq
    ports:
    - protocol: TCP
      port: 3306
```

Verify:

```bash
oc get netpol -n database mysql-db-conn -o yaml
oc get ns checker --show-labels
oc get pod -n checker --show-labels
oc get pod -n database --show-labels
```

Test:

```bash
DBIP=$(oc get pod -n database -l app=mysql -o jsonpath='{.items[0].status.podIP}')
oc exec -n checker <checker-pod> -- bash -c "timeout 3 bash -c '</dev/tcp/$DBIP/3306' && echo open || echo blocked"
```

## 14. EgressFirewall Troubleshooting

### 14.1 What EgressFirewall does

`EgressFirewall` controls outbound traffic from pods in a namespace to external destinations. It is namespace-scoped and uses ordered allow/deny rules.

### 14.2 List EgressFirewall objects

```bash
oc get egressfirewall -A
oc get egressfirewall -n <ns> -o yaml
```

### 14.3 Critical limitations and gotchas

Important behavior to remember:

- A project can have only one `EgressFirewall` object.
- Egress firewall does not apply to host-networked pods.
- A deny rule such as `0.0.0.0/0` can block access to the OpenShift API unless explicit allow rules are placed before it.
- If rules use external DNS names and the pod uses an external DNS server, allow DNS traffic to that DNS server.
- Rule order matters.

### 14.4 Troubleshooting flow

From affected pod:

```bash
oc exec -n <ns> <pod> -- curl -sv --connect-timeout 3 https://<external-host> || true
oc exec -n <ns> <pod> -- getent hosts <external-host> || true
```

Check policy:

```bash
oc get egressfirewall -n <ns> -o yaml
```

Check API endpoint if global deny exists:

```bash
oc get ep kubernetes -n default -o wide
```

If egress deny-all is required, allow API/DNS/proxy destinations first.

Example structure:

```yaml
apiVersion: k8s.ovn.org/v1
kind: EgressFirewall
metadata:
  name: default
  namespace: app-ns
spec:
  egress:
  - type: Allow
    to:
      cidrSelector: <api-server-cidr-or-ip>
  - type: Allow
    to:
      cidrSelector: <dns-server-cidr-or-ip>
  - type: Allow
    to:
      dnsName: allowed.example.com
  - type: Deny
    to:
      cidrSelector: 0.0.0.0/0
```

## 15. EgressIP Troubleshooting

### 15.1 What EgressIP does

EgressIP gives selected pods or namespaces a consistent source IP when communicating outside the cluster.

Useful when:

- External firewalls allow only specific source IPs.
- Database or third-party service allowlists cluster traffic.
- Audit teams require stable egress identity.

### 15.2 Required elements

At minimum:

1. One or more nodes labeled as egress-assignable.
2. An `EgressIP` object.
3. Namespace labels and/or pod labels matching the EgressIP selectors.
4. Egress IP address reachable/routable on the node network.
5. No conflict with existing IP addresses.

### 15.3 Commands

```bash
oc get egressip
oc get egressip -o yaml
oc get nodes -l k8s.ovn.org/egress-assignable=
oc get ns --show-labels
oc get pod -n <ns> --show-labels
```

Label a node:

```bash
oc label node <node-name> k8s.ovn.org/egress-assignable=""
```

### 15.4 Common failure causes

| Cause | Evidence | Fix |
|---|---|---|
| No egress-assignable node | EgressIP not assigned | Label suitable node |
| IP not in reachable subnet | External traffic fails | Use routable IP on node network |
| IP conflict | ARP/routing instability | Choose unused IP |
| Namespace selector mismatch | Pod uses normal node IP | Fix namespace labels |
| Pod selector mismatch | Only some pods affected | Fix pod labels |
| External firewall wrong | Packet leaves with correct IP but denied | Update firewall allowlist |
| Node hosting EgressIP down | Failover or outage depending config | Check node health and reassignment |

### 15.5 Verify source IP

From selected pod:

```bash
oc exec -n <ns> <pod> -- curl -s https://ifconfig.me || true
```

In restricted environments, test against an internal echo server or firewall logs.

From node debug:

```bash
ip addr | grep <egress-ip> || true
ip route get <external-ip>
```

## 18. MTU and Geneve Overlay Troubleshooting

### 18.1 Why MTU matters

OVN-Kubernetes uses an overlay network. Overlay encapsulation adds overhead. If the physical network MTU and OVN overlay MTU are inconsistent, symptoms can be confusing:

- Small pings work, large requests fail.
- TLS handshakes hang.
- Image pulls fail intermittently.
- `curl` connects but stalls.
- Database connections fail under load.
- Cross-node traffic fails but same-node works.

### 18.2 Check cluster MTU config

```bash
oc get network.operator.openshift.io cluster -o yaml | egrep -i 'mtu|geneve|defaultNetwork|clusterNetwork' -A5 -B5
oc get network.config.openshift.io cluster -o yaml | egrep -i 'mtu|network|serviceNetwork|clusterNetwork' -A5 -B5
```

### 18.3 Check node MTU

```bash
oc debug node/<node>
chroot /host
ip link show
nmcli dev show | egrep 'GENERAL.DEVICE|MTU'
exit
exit
```

### 18.4 Test packet size

From a pod:

```bash
ping -M do -s 1400 <target-pod-ip>
ping -M do -s 1300 <target-pod-ip>
```

For IPv4, packet size plus headers matters. Test gradually.

### 18.5 Common MTU root causes

| Environment | Risk |
|---|---|
| VMware | vSwitch or port group MTU mismatch |
| Bare metal | Switch trunk MTU mismatch |
| Cloud | VPC/VNet MTU constraints |
| IPsec | Additional overhead |
| Nested virtualization | Outer network MTU smaller than expected |
| Mixed NIC configs | One node differs from others |

### 18.6 Fix approach

Do not manually edit random node interfaces unless you know the cluster network design. Prefer supported OpenShift configuration paths through the Network Operator, MachineConfig, NMState, or platform-specific network configuration.

Collect before changing:

```bash
oc get network.operator.openshift.io cluster -o yaml
oc get network.config.openshift.io cluster -o yaml
oc get nodes -o wide
for n in $(oc get nodes -o name); do echo ===$n===; oc debug $n -- chroot /host ip link show 2>/dev/null | egrep '^[0-9]+:|mtu' ; done
```

## 20. OVN Logical State Inspection

In many cases, Kubernetes objects look correct, but OVN logical state is stale or incorrect. Use OVN tools carefully.

### 20.1 Access OVN containers

```bash
POD=$(oc get pod -n openshift-ovn-kubernetes -l app=ovnkube-node -o jsonpath='{.items[0].metadata.name}')
oc rsh -n openshift-ovn-kubernetes -c nbdb "$POD"
```

Depending on release and permissions, commands may need to run inside specific containers.

### 20.2 Useful OVN commands

Inside an OVN container:

```bash
ovn-nbctl show
ovn-sbctl show
ovn-nbctl list logical_switch | head
ovn-nbctl list logical_router | head
ovn-nbctl list acl | head
ovn-nbctl list load_balancer | head
```

### 20.3 Map pod to logical port

Get pod annotations:

```bash
oc get pod -n <ns> <pod> -o jsonpath='{.metadata.annotations}' | jq .
```

Look for OVN-related annotations such as pod IP, MAC, gateway, routes, and logical port information.

Search logical switch ports:

```bash
ovn-nbctl --columns=name,addresses list logical_switch_port | grep <pod-name> -A3 -B3
```

### 20.4 NetworkPolicy as ACLs

OVN represents network policies as ACLs. When a policy is suspected:

```bash
ovn-nbctl list acl | egrep -i '<namespace>|<pod>|<ip>|drop|allow' -A5 -B5
```

Do not manually delete OVN ACLs to fix a Kubernetes policy problem. Fix the Kubernetes `NetworkPolicy` object and let the controller reconcile.

## 21. `ovnkube-trace` for Deep Packet Path Debugging

### 21.1 What it does

`ovnkube-trace` simulates and correlates OVN and OVS traffic flow. It can help answer:

- Would OVN allow this packet?
- Which ACL matched?
- Which logical router/switch path is used?
- Where is the packet dropped?
- Does the Service translation path look correct?

### 21.2 Copy tool locally

Example:

```bash
POD=$(oc get pod -n openshift-ovn-kubernetes -l app=ovnkube-control-plane -o jsonpath='{.items[0].metadata.name}')
oc cp -n openshift-ovn-kubernetes "$POD":/usr/bin/ovnkube-trace -c ovnkube-cluster-manager ./ovnkube-trace
chmod +x ./ovnkube-trace
./ovnkube-trace --help
```

Container names can vary by release. Confirm with:

```bash
oc get pod -n openshift-ovn-kubernetes "$POD" -o jsonpath='{.spec.containers[*].name}' ; echo
```

### 21.3 Example traces

Pod to pod:

```bash
./ovnkube-trace \
  --src-namespace net-a \
  --src pod/client \
  --dst-namespace net-b \
  --dst pod/server \
  --tcp \
  --dst-port 8080
```

Pod to service:

```bash
./ovnkube-trace \
  --src-namespace net-a \
  --src pod/client \
  --dst-namespace net-b \
  --dst service/web \
  --tcp \
  --dst-port 8080
```

Default-deny policy validation:

```bash
./ovnkube-trace \
  --src-namespace blocked-ns \
  --src pod/client \
  --dst-namespace app-ns \
  --dst pod/server \
  --tcp \
  --dst-port 8443
```

### 21.4 How to read output

Focus on:

- Source logical port
- Destination logical port or load balancer
- Matched ACL
- Drop/allow action
- NAT action
- Logical router hop
- OVS flow translation

If `ovnkube-trace` shows drop due to ACL, fix policy. If trace shows allowed but real traffic fails, suspect node datapath, OVS, MTU, physical network, or application layer.

## 22. Packet Capture

### 22.1 Capture from pod

If the image has `tcpdump`:

```bash
oc exec -n <ns> <pod> -- tcpdump -nn -i any host <target-ip>
```

If not, use an ephemeral debug container if your cluster allows it, or capture on the node.

### 22.2 Capture on node

```bash
oc debug node/<node>
chroot /host
ip addr
 tcpdump -nn -i any host <pod-ip> or host <target-ip>
```

For overlay traffic between nodes:

```bash
tcpdump -nn -i any udp port 6081
```

Geneve commonly uses UDP 6081. Validate your cluster configuration before assuming.

### 22.3 Capture strategy

For pod-to-pod cross-node failure, capture at:

1. Source pod interface or source node.
2. Source node physical NIC.
3. Destination node physical NIC.
4. Destination pod interface or destination node.

Interpretation:

| Observation | Meaning |
|---|---|
| Packet leaves source pod but not source node | OVS/OVN local drop |
| Packet leaves source node but not reaches destination node | Underlay firewall/routing issue |
| Packet reaches destination node but not pod | OVS/OVN destination node issue |
| Packet reaches pod but no reply | Application/policy/return path issue |

## 24. Troubleshooting `ovnkube-node` CrashLoopBackOff

### 24.1 Check pod status

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc describe pod -n openshift-ovn-kubernetes <ovnkube-node-pod>
oc logs -n openshift-ovn-kubernetes <ovnkube-node-pod> --all-containers --previous --tail=500
```

### 24.2 Common causes

| Cause | Evidence | Action |
|---|---|---|
| Node disk pressure | Evictions, write errors | Free disk, check CRI-O storage |
| OVS service unhealthy | Node journal, OVS status | Investigate OVS service and node state |
| Bad config rollout | Recent network/MCO changes | Review CNO/MCO changes |
| Image pull issue | ImagePullBackOff | Check registry, pull secret, mirror config |
| API connectivity issue | Logs show API timeout | Check node-to-API routing/firewall/DNS |

### 24.3 Recovery sequence

1. Collect logs and must-gather.
2. Confirm node health.
3. Confirm OVS services.
4. Confirm API access from node.
5. Confirm CNO not degraded due to invalid config.
6. Drain affected node if workload impact exists.
7. Restart affected services only if the cause is understood.
8. If OVS/OVN database corruption is suspected, involve Red Hat Support before destructive cleanup.

OVN-Kubernetes usually handles the default pod network. Multus can attach secondary networks using NetworkAttachmentDefinitions.

### 26.1 Symptoms

```text

failed to find plugin
failed to load netconf
IPAM allocation failed
whereabouts allocation error
```

## 30. Advanced Case Studies

### Case 1: Pod-to-service fails, pod-to-pod IP works

Symptoms:

```text
curl podIP:8080 works
curl serviceName:8080 fails
DNS resolves service name
```

Likely causes:

- Service targetPort wrong.
- EndpointSlice stale/missing.
- Service selector wrong.
- OVN load balancer state issue.

Flow:

```bash
oc get svc -n app web -o yaml
oc get endpoints -n app web -o wide
oc get endpointslice -n app -l kubernetes.io/service-name=web -o yaml
oc get pod -n app --show-labels
```

Fix selector/targetPort first. Only inspect OVN LB after Kubernetes objects are correct.

---

### Case 2: Cross-node traffic fails, same-node works

Likely causes:

- Geneve UDP blocked.
- MTU mismatch.
- Node routing issue.
- OVS tunnel issue.
- Cloud security group blocks node-to-node overlay.

Flow:

```bash
oc get pod -A -o wide | egrep '<client>|<server>'
oc debug node/<source-node>
chroot /host
ping <destination-node-ip>
tcpdump -nn -i any udp port 6081
```

Run traffic while capturing. If packets leave source but never arrive, check physical/cloud network.

---

### Case 3: Namespace outage after applying NetworkPolicy

Symptoms:

- App cannot call DB.
- App cannot resolve DNS.
- App cannot call API.
- Only one namespace affected.

Flow:

```bash
oc get netpol -n app
oc get egressfirewall -n app
oc get pod -n app --show-labels
oc get ns --show-labels
```

Temporary proof:

```bash
oc apply -f temp-allow-all.yaml
```

If traffic works, rewrite policy correctly and remove temporary allow.

---

### Case 4: External vendor says traffic source IP is wrong

Likely causes:

- EgressIP not assigned.
- Namespace selector mismatch.
- Egress pod scheduled on unexpected node.
- External firewall sees node IP instead of EgressIP.
- NAT/proxy changes source after cluster.

Flow:

```bash
oc get egressip -o yaml
oc get nodes -l k8s.ovn.org/egress-assignable=
oc get ns <ns> --show-labels
oc get pod -n <ns> --show-labels -o wide
```

Test source IP using controlled endpoint or firewall logs.

---

### Case 5: Route returns 503

Likely causes:

- Service has no endpoints.
- Readiness probe failing.
- Route targetPort mismatch.
- Router cannot reach backend.

Flow:

```bash
oc describe route -n app web
oc get svc -n app web -o yaml
oc get endpoints -n app web -o wide
oc describe pod -n app <pod>
oc logs -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=default --tail=100
```

Fix endpoints/readiness before touching router or OVN.

---

### Case 6: CNI fails only on one node

Likely causes:

- `ovnkube-node` broken on that node.
- OVS service issue.
- Node disk/resource pressure.
- Node network config drift.
- Kubelet/CRI-O problem.

Flow:

```bash
oc get node <node>
oc describe node <node>
oc get pod -n openshift-ovn-kubernetes -o wide | grep <node>
oc logs -n openshift-ovn-kubernetes <ovnkube-node-pod> --all-containers --tail=300
oc debug node/<node>
chroot /host
systemctl status kubelet crio ovs-vswitchd ovsdb-server --no-pager
journalctl -u kubelet --since "1 hour ago" --no-pager
```

Drain node if production workload is impacted:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

Use with caution and only when disruption is acceptable.

```text
 |-- Is cluster API reachable?
 |      |-- No  -> troubleshoot API/LB/DNS/node connectivity first
 |      |-- Yes
 |
 |-- Are ClusterOperators healthy?
 |      |-- network degraded -> inspect CNO + OVN pods
 |      |-- dns degraded     -> fix DNS before app network
 |      |-- ingress degraded -> fix ingress before routes
 |
 |-- Is issue cluster-wide?
 |      |-- Yes -> CNO/OVN/DNS/MTU/underlay/firewall
 |      |-- No
 |
 |-- Is issue node-specific?
 |      |-- Yes -> ovnkube-node, OVS, kubelet, CRI-O, node network
 |      |-- No
 |
 |-- Is issue namespace-specific?
 |      |-- Yes -> NetworkPolicy, EgressFirewall, quota, service selectors
 |      |-- No
 |
 |-- Does raw pod IP work?
 |      |-- No -> app listener, pod network, policy, node path
 |      |-- Yes
 |
 |-- Does Service ClusterIP work?
 |      |-- No -> service selector, endpoints, OVN LB
 |      |-- Yes
 |
 |-- Does DNS name work?
 |      |-- No -> DNS/CoreDNS/policy to DNS
 |      |-- Yes
 |
 |-- Does Route/External access work?
        |-- No -> ingress/router/route/TLS/external LB
        |-- Yes -> issue resolved or intermittent; collect traces
```

## 33. Production Safety Guidelines

### 33.1 Avoid these during live incidents

Do not casually run:

```bash
oc delete pod -n openshift-ovn-kubernetes --all
systemctl restart NetworkManager
systemctl restart ovs-vswitchd
rm -rf /var/lib/openvswitch/*
rm -rf /var/lib/ovn/*
oc patch network.operator.openshift.io cluster ...
```

These can cause wider outage.

### 33.2 Safer approach

1. Reproduce with a controlled test pod.
2. Identify exact failing path.
3. Confirm Kubernetes objects first.
4. Check operators and OVN pods.
5. Collect logs and must-gather.
6. Drain/cordon a single affected node if needed.
7. Make one change at a time.
8. Validate and document.

### 33.3 Evidence to collect before escalation

```bash
oc get co -o wide
oc describe co network
oc get network.operator.openshift.io cluster -o yaml
oc get network.config.openshift.io cluster -o yaml
oc get pods -n openshift-ovn-kubernetes -o wide

oc logs -n openshift-ovn-kubernetes -l app=ovnkube-control-plane --all-containers --tail=500
oc get netpol -A -o yaml
oc get egressfirewall -A -o yaml
oc get egressip -A -o yaml
oc adm must-gather
```

## 34. Interview / Real-Time Explanation

If asked in an interview, explain like this:

> In OpenShift 4, I first identify whether the failure is pod-to-pod, pod-to-service, pod-to-external, or external-to-route. I check ClusterOperators, especially network, DNS, and ingress. For OVN-Kubernetes, I inspect `openshift-ovn-kubernetes`, especially `ovnkube-node` and `ovnkube-control-plane` pods. I validate Kubernetes objects first: Services, Endpoints, EndpointSlices, NetworkPolicies, EgressFirewall, and EgressIP. If the issue is node-specific, I debug the node, check kubelet, CRI-O, OVS, `br-int`, routes, MTU, and Geneve connectivity. If policy is suspected, I verify namespace and pod selectors and use controlled test pods. For deeper flow analysis, I use `ovnkube-trace`, OVN DB inspection, OVS flow checks, and tcpdump. I avoid restarting OVN components blindly and collect must-gather before disruptive recovery.

## 36. Common Mistakes by Administrators

| Mistake | Better approach |
|---|---|
| Restarting OVN pods first | Reproduce, isolate, collect logs first |
| Debugging Route before checking endpoints | Always check Service and endpoints first |
| Assuming DNS issue is OVN issue | Test raw IP before DNS name |
| Ignoring same-node vs cross-node | This distinction identifies overlay/underlay issues |
| Forgetting NetworkPolicy selectors use labels | Verify pod and namespace labels |
| Applying default deny without DNS/API allow | Add required infrastructure egress allows |
| Manually editing CNO-managed resources | Change supported CRs only |
| Not collecting previous logs | Use `--previous` for crashloops |
| Treating EgressIP as magic NAT | Verify node label, assignment, route, and external firewall |
| Not checking MTU | MTU causes intermittent and confusing symptoms |

## 37. Troubleshooting Checklist

Use this checklist in real incidents.

```text
[ ] Confirm exact failing path: pod IP, service, DNS, route, external.
[ ] Confirm whether issue is cluster-wide, node-specific, namespace-specific, or app-specific.
[ ] Check ClusterOperators: network, dns, ingress, machine-config.
[ ] Check nodes and MCP state.
[ ] Check OVN pods in openshift-ovn-kubernetes.
[ ] Check CNO logs.
[ ] Check Service selectors and endpoints.
[ ] Check pod readiness.
[ ] Check DNS resolution separately.
[ ] Check NetworkPolicy and EgressFirewall.
[ ] Check EgressIP/EgressService if external source IP is relevant.
[ ] Check same-node vs cross-node behavior.
[ ] Check MTU and Geneve/underlay reachability.
[ ] Use node debug for OVS, routes, kubelet, CRI-O logs.
[ ] Use tcpdump or ovnkube-trace for deep packet analysis.
[ ] Collect must-gather before disruptive remediation.
[ ] Make one change at a time and validate.
```

## 39. Final Notes for Advanced Administrators

For real production troubleshooting, remember this principle:

> Do not troubleshoot OVN internals until Kubernetes objects are proven correct.

The majority of incidents are caused by incorrect selectors, missing endpoints, readiness failures, DNS restrictions, NetworkPolicy mistakes, or external firewall rules. OVN/OVS deep debugging becomes necessary only after those are ruled out.

A strong L3 OpenShift administrator should be able to explain and prove:

- Where traffic starts.
- Where traffic should go.
- Which object controls that path.
- Which policy allows or denies it.
- Which node owns the datapath.
- Whether the packet enters and exits the node.
- Whether OVN desired state matches OVS actual state.

That is the difference between basic command execution and senior-level OpenShift network troubleshooting.
