## 1. Executive Summary

When traffic is blocked by `NetworkPolicy`, the cluster is usually healthy. The CNI is doing exactly what it was instructed to do. The problem is commonly one of these:

- A `default-deny` policy was added but required allow rules were not added.
- The policy was created in the wrong namespace.
- The policy selects the wrong destination pods.
- The source pod label or namespace label does not match the policy.
- The YAML uses `namespaceSelector` and `podSelector` incorrectly.
- Egress isolation blocks DNS, API, database, registry, or external traffic.
- OpenShift route traffic is blocked because ingress controller traffic is not explicitly allowed.
- An `AdminNetworkPolicy` or `BaselineAdminNetworkPolicy` is overriding or changing the expected namespace-level behavior.
- The issue is actually service selector, endpoint, port, DNS, application bind, TLS, or readiness — not NetworkPolicy.

A senior OpenShift administrator should not start by deleting policies. First prove the failing tuple:

```text
source namespace + source pod + destination namespace + destination pod/service/IP + port + protocol + direction
```

Then check whether both sides allow it:

```text
source egress must allow the connection
AND
destination ingress must allow the connection
```

If either side blocks it, traffic fails.

## 2. Mental Model: What NetworkPolicy Actually Does

A Kubernetes `NetworkPolicy` is a namespace-scoped allow-list object.

It does **not** behave like a traditional firewall where rules are processed top-to-bottom with explicit deny and allow ordering. Standard Kubernetes `NetworkPolicy` has these important properties:

1. Policies are **additive**.
2. There is no ordering between namespace-scoped `NetworkPolicy` objects.
3. Standard `NetworkPolicy` does not have an explicit `deny` action.
4. A pod becomes isolated only when at least one policy selects it for a direction.
5. If a pod is isolated for ingress, only allowed ingress connections work.
6. If a pod is isolated for egress, only allowed egress connections work.
7. For pod-to-pod traffic to work, source egress and destination ingress must both allow the connection.
8. Reply traffic for an allowed connection is implicitly allowed.

### Basic object shape

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-client-to-api
  namespace: app-prod
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: client
    ports:
    - protocol: TCP
      port: 8080
```

Important meaning:

```text
This policy lives in namespace app-prod.
It applies to destination pods in app-prod with label app=api.
It allows ingress from source pods in the same namespace with label app=client.
It allows only TCP destination port 8080.
It does not allow traffic from every namespace.
It does not allow every port.
It does not control egress unless Egress is included in policyTypes.
```

## 3. OpenShift-Specific Policy Evaluation

Modern OpenShift with OVN-Kubernetes can evaluate more than standard namespace `NetworkPolicy`.

The practical evaluation order is:

```text
1. AdminNetworkPolicy, cluster-scoped
2. NetworkPolicy, namespace-scoped
3. BaselineAdminNetworkPolicy, cluster-scoped baseline
```

### What this means operationally

If a tenant says, “My NetworkPolicy allows it, but traffic still fails,” do not only inspect `NetworkPolicy` in the namespace. Also check cluster-scoped policy resources:

```bash
oc get adminnetworkpolicy
oc get baselineadminnetworkpolicy
oc describe adminnetworkpolicy
oc describe baselineadminnetworkpolicy
```

Depending on OpenShift version and enabled APIs, resource names might require fully qualified names:

```bash
oc api-resources | grep -i networkpolicy
oc get adminnetworkpolicies.policy.networking.k8s.io
oc get baselineadminnetworkpolicies.policy.networking.k8s.io
```

### Difference between the policy types

| Policy type | Scope | Typical owner | Can explicitly deny? | Notes |
|---|---:|---|---:|---|
| `NetworkPolicy` | Namespace | App / project admin | No, implicit deny only after isolation | Additive allow-list |
| `AdminNetworkPolicy` | Cluster | Cluster admin | Yes | Higher priority than namespace policy |
| `BaselineAdminNetworkPolicy` | Cluster | Cluster admin | Yes | Baseline, lower priority than namespace policy |

For L3 troubleshooting, always check all three layers before declaring the namespace policy correct.

## 4. Common Symptoms

NetworkPolicy blocking usually appears as one of these symptoms:

```text
curl: Connection timed out
curl: Failed to connect
nc: timed out
psql: connection timeout
mysql: Can't connect to MySQL server
MongoDB server selection timeout
HTTP 504 from route
HTTP route works from one namespace but not another
Pod can resolve DNS but cannot connect
Pod cannot resolve DNS after default-deny egress
Pod IP works but service DNS name does not
Service has endpoints but traffic still fails
Application logs show connection refused or timeout to database
Readiness probe fails after network hardening
Route returns 503/504 after applying default-deny
```

### Timeout vs refused

A useful senior-admin distinction:

| Symptom | Usually means |
|---|---|
| `Connection timed out` | NetworkPolicy, firewall, routing, security group, dropped packet |
| `Connection refused` | Destination reached, but no process is listening, wrong port, app bind issue |
| `No route to host` | Routing/CNI/node issue or blocked host route |
| `Could not resolve host` | DNS blocked or DNS service unavailable |
| HTTP 503 from route | Route/service/endpoints/readiness problem, not always NetworkPolicy |
| HTTP 504 from route | Ingress/router reached but backend connection timed out; NetworkPolicy is possible |

NetworkPolicy usually drops traffic. It often causes timeout, not refused.

## 5. Fast Triage Checklist

Use this checklist before making changes.

```bash
# 1. Confirm cluster network type
oc get network.config/cluster -o jsonpath='{.status.networkType}{"\n"}'
oc get co network

# 2. Identify source and destination pods
oc get pod -A -o wide --show-labels | grep -E 'source|client|checker|frontend|api|db|mysql'

# 3. Check service and endpoints
oc get svc,endpoints,endpointslice -n <dest-namespace> -o wide
oc describe svc <service> -n <dest-namespace>

# 4. List network policies
oc get networkpolicy -A
oc describe networkpolicy -n <dest-namespace>
oc describe networkpolicy -n <source-namespace>

# 5. Check cluster-scoped policy APIs
oc get adminnetworkpolicy 2>/dev/null || true
oc get baselineadminnetworkpolicy 2>/dev/null || true

# 6. Check labels used by selectors
oc get ns --show-labels
oc get pod -n <source-namespace> --show-labels
oc get pod -n <dest-namespace> --show-labels

# 7. Test connectivity from the real source pod
oc exec -n <source-namespace> <source-pod> -- curl -svm 5 http://<service>.<dest-namespace>.svc:<port>/
oc exec -n <source-namespace> <source-pod> -- nc -vz -w 3 <service>.<dest-namespace>.svc <port>

# 8. Test DNS separately
oc exec -n <source-namespace> <source-pod> -- getent hosts <service>.<dest-namespace>.svc
oc exec -n <source-namespace> <source-pod> -- nslookup <service>.<dest-namespace>.svc
```

If the image does not contain `curl`, `nc`, or `nslookup`, run a temporary debug pod.

```bash
oc run net-debug -n <source-namespace> \
  --image=registry.access.redhat.com/ubi9/ubi \
  --restart=Never --command -- sleep 3600

oc exec -n <source-namespace> net-debug -- bash -lc 'microdnf -y install nmap-ncat bind-utils curl iproute && nc -vz -w 3 <service>.<dest-namespace>.svc <port>'
```

In disconnected labs, replace the image with your local registry image, for example:

```bash
registry.ocp4.example.com:8443/ubi9/ubi
```

## 6. Golden Rule: Test Source, Destination, Port, Protocol, and Direction

Do not say “network is blocked” until you know the exact tuple.

Fill this table during troubleshooting:

| Field | Example |
|---|---|
| Source namespace | `checker` |
| Source pod | `checker-7c88d4f9c9-kp2wq` |
| Source labels | `app=checker`, `role=client` |
| Destination namespace | `database` |
| Destination pod | `mysql-6f7797dbd7-b9nqv` |
| Destination labels | `app=mysql`, `deployment=web-mysq` |
| Destination service | `mysql.database.svc` |
| Destination port | `3306/TCP` |
| Direction | source egress + destination ingress |
| Expected policy | allow checker → mysql on TCP/3306 |
| Actual result | timeout |

Then verify each layer.

```bash
SRC_NS=checker
DST_NS=database
SRC_POD=$(oc get pod -n $SRC_NS -l app=checker -o jsonpath='{.items[0].metadata.name}')
DST_SVC=mysql
PORT=3306

oc exec -n $SRC_NS $SRC_POD -- nc -vz -w 3 ${DST_SVC}.${DST_NS}.svc $PORT
```

## 8. How NetworkPolicy Blocks Traffic

### Case 1: No policies exist

```text
No NetworkPolicy selects the pod.
Ingress allowed.
Egress allowed.
Traffic should not be blocked by NetworkPolicy.
```

### Case 2: Policy selects destination pod for ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-only-api
  namespace: database
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: api
    ports:
    - protocol: TCP
      port: 3306
```

Now pods with `app=mysql` are ingress-isolated. They accept only traffic matching the rule.

If the source namespace does not have `name=api`, traffic is blocked.

### Case 3: Policy selects source pod for egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-egress-only-api
  namespace: frontend
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          purpose: api
    ports:
    - protocol: TCP
      port: 8080
```

Now pods with `app=frontend` are egress-isolated. They can only connect to the allowed destinations.

If they need DNS, database, API server, registry, metrics, or another service, it must be explicitly allowed.

## 9. Ingress vs Egress Blocking

For a connection from pod A to pod B:

```text
A egress policy must allow A -> B
B ingress policy must allow A -> B
```

### Troubleshooting order

1. Check destination namespace ingress policy.
2. Check source namespace egress policy.
3. Check cluster-scoped AdminNetworkPolicy.
4. Check BaselineAdminNetworkPolicy.
5. Check service/endpoints/app if policy allows traffic.

### Example

```text
frontend/client -> database/mysql:3306
```

Required:

```text
source namespace frontend:
  if frontend pod is egress-isolated, allow egress to database/mysql:3306

destination namespace database:
  if mysql pod is ingress-isolated, allow ingress from frontend/client:3306
```

A common mistake is to create only the ingress allow in `database`, while an egress default-deny in `frontend` still blocks the connection.

## 10. Default Deny Policies

Default deny is useful but dangerous when applied without allow rules.

### Default deny ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

Equivalent common form:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-by-default
  namespace: app-prod
spec:
  podSelector: {}
  ingress: []
```

Meaning:

```text
All pods in app-prod are ingress-isolated.
No ingress traffic is allowed unless another policy allows it.
```

### Default deny egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress
```

Meaning:

```text
All pods in app-prod are egress-isolated.
No outbound traffic is allowed unless another policy allows it.
DNS will also be blocked unless allowed.
```

### Default deny both directions

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

This is a hard isolation baseline. Use it only with a complete set of allow rules.

### Production warning

Never apply default-deny across a production namespace without first identifying:

- ingress controller requirements
- service-to-service dependencies
- DNS dependencies
- API server access requirements
- database access
- monitoring scrape access
- logging/metrics agents
- external payment/SaaS/proxy dependencies
- image registry, if build pods run in the namespace
- readiness/liveness probe traffic path

## 11. Selector Problems

Most NetworkPolicy incidents are selector incidents.

### `spec.podSelector` selects destination pods for ingress

This is the most common misunderstanding.

```yaml
spec:
  podSelector:
    matchLabels:
      app: mysql
```

In an ingress policy, this does **not** mean “allow from mysql.” It means:

```text
Apply this policy to destination pods labeled app=mysql.
```

The source is selected under:

```yaml
spec:
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: client
```

### Validate selected destination pods

```bash
oc get netpol allow-mysql -n database -o yaml
oc get pod -n database -l app=mysql --show-labels -o wide
```

If no pod is returned, the policy is not selecting the intended destination pods.

### Validate source pods

```bash
oc get pod -n checker -l app=checker --show-labels -o wide
```

If no pod is returned, the allow rule does not match the source.

### Common selector mistakes

| Mistake | Example | Result |
|---|---|---|
| Wrong label key | `app=mysql` but pod has `deployment=mysql` | No match |
| Wrong label value | `role=db` but pod has `role=database` | No match |
| Label on Deployment only | Policy needs pod labels | No match if pod template lacks label |
| Typo | `web-mysq` vs `web-mysql` | No match |
| Wrong namespace | Policy created in `checker`, but should be in `database` | Destination not protected/allowed as expected |
| Using service labels | Service selector differs from pod labels | Policy selects pods, not services |

### Check Deployment pod-template labels

```bash
oc get deploy <deploy> -n <namespace> -o jsonpath='{.spec.template.metadata.labels}{"\n"}'
oc get pod -n <namespace> --show-labels
```

NetworkPolicy matches pod labels, not Deployment labels alone.

## 12. Namespace Selector Problems

A `namespaceSelector` matches namespace labels, not namespace names, unless the namespace has a label representing its name.

Modern Kubernetes automatically adds:

```text
kubernetes.io/metadata.name=<namespace-name>
```

But do not assume. Verify:

```bash
oc get ns checker --show-labels
oc get ns database --show-labels
```

### Example using namespace name label

```yaml
namespaceSelector:
  matchLabels:
    kubernetes.io/metadata.name: checker
```

### Example using custom tenant label

```bash
oc label ns checker team=devsecops --overwrite
```

```yaml
namespaceSelector:
  matchLabels:
    team: devsecops
```

### Common namespaceSelector mistake

Wrong:

```yaml
namespaceSelector:
  matchLabels:
    name: checker
```

Unless you actually labeled the namespace with `name=checker`, this matches nothing.

Correct after verification:

```yaml
namespaceSelector:
  matchLabels:
    kubernetes.io/metadata.name: checker
```

or:

```bash
oc label ns checker name=checker --overwrite
```

## 13. YAML AND/OR Mistakes

This is a high-value exam and production troubleshooting topic.

### Same list item means AND

```yaml
from:
- namespaceSelector:
    matchLabels:
      team: devsecops
  podSelector:
    matchLabels:
      app: checker
```

Meaning:

```text
Allow pods with app=checker
AND
only if they are in namespaces labeled team=devsecops.
```

### Separate list items mean OR

```yaml
from:
- namespaceSelector:
    matchLabels:
      team: devsecops
- podSelector:
    matchLabels:
      app: checker
```

Meaning:

```text
Allow all pods in namespaces labeled team=devsecops
OR
allow pods with app=checker in the same namespace as the policy.
```

This difference causes many real incidents.

### Wrong cross-namespace policy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-checker-to-mysql
  namespace: database
spec:
  podSelector:
    matchLabels:
      app: mysql
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: checker
    ports:
    - protocol: TCP
      port: 3306
```

Problem:

```text
from.podSelector without namespaceSelector only selects source pods in the same namespace as the policy.
Because this policy is in database namespace, it looks for app=checker pods inside database namespace.
It does not allow checker namespace pods.
```

Correct:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-checker-to-mysql
  namespace: database
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: checker
      podSelector:
        matchLabels:
          app: checker
    ports:
    - protocol: TCP
      port: 3306
```

## 14. Route and Ingress Controller Traffic Blocked

A classic OpenShift outage:

```text
Application works from inside namespace.
Route returns 503/504 or times out.
A default-deny ingress NetworkPolicy was added.
Ingress controller traffic is not allowed.
```

OpenShift routes are served by ingress/router pods, commonly in `openshift-ingress`. If destination application pods are ingress-isolated, router traffic must be allowed.

### Allow from OpenShift ingress controller

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/ingress: ""
```

This allows ingress controller namespace traffic to app pods.

### More restrictive version

If only pods labeled `app=web` should receive route traffic:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-route-to-web
  namespace: app-prod
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/ingress: ""
    ports:
    - protocol: TCP
      port: 8080
```

Use the container listening port, not necessarily the route external port.

### Validate route path

```bash
oc get route -n app-prod
oc describe route <route> -n app-prod
oc get svc,endpoints -n app-prod
oc get pod -n app-prod -l app=web -o wide --show-labels
curl -vk --connect-timeout 5 https://<route-host>
```

If route fails after default-deny but service works from inside the namespace, suspect missing ingress-controller allow.

## 15. DNS Blocked by Egress Policy

Default-deny egress often breaks DNS.

Symptoms:

```text
curl: Could not resolve host
nslookup times out
application cannot resolve database/service/external hostname
Java UnknownHostException
```

### Confirm DNS failure

```bash
oc exec -n app-prod <pod> -- getent hosts kubernetes.default.svc
oc exec -n app-prod <pod> -- nslookup mysql.database.svc
```

### Allow egress to OpenShift DNS

First inspect DNS namespace and pods:

```bash
oc get ns openshift-dns --show-labels
oc get pods -n openshift-dns --show-labels -o wide
oc get svc -n openshift-dns
```

Then create a policy similar to this:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

If your cluster labels differ, adjust the selector after checking labels.

### Important

Allowing DNS only resolves names. It does not allow traffic to the resolved destination. You still need allow rules for the application port.

## 16. Service Works by Pod IP but Not by Service Name

This is usually not NetworkPolicy alone. Separate the failure:

| Test | Meaning |
|---|---|
| Pod IP works, service DNS fails to resolve | DNS problem |
| Pod IP works, service ClusterIP fails | Service selector, kube-proxy/OVN service load balancer, endpoint issue |
| Service works, route fails | Ingress/router/route/backend policy issue |
| Pod IP fails and service fails | NetworkPolicy, app port, node/CNI issue |

### Commands

```bash
# Destination pod IP
oc get pod -n database -l app=mysql -o wide

# Destination service and endpoints
oc get svc mysql -n database -o wide
oc get endpoints mysql -n database -o wide
oc get endpointslice -n database -l kubernetes.io/service-name=mysql -o wide

# Test DNS
oc exec -n checker $SRC_POD -- getent hosts mysql.database.svc

# Test ClusterIP
SVC_IP=$(oc get svc mysql -n database -o jsonpath='{.spec.clusterIP}')
oc exec -n checker $SRC_POD -- nc -vz -w 3 $SVC_IP 3306

# Test PodIP
POD_IP=$(oc get pod -n database -l app=mysql -o jsonpath='{.items[0].status.podIP}')
oc exec -n checker $SRC_POD -- nc -vz -w 3 $POD_IP 3306
```

### Check service selector mismatch

```bash
oc get svc mysql -n database -o jsonpath='{.spec.selector}{"\n"}'
oc get pod -n database --show-labels
```

If the service has no endpoints, NetworkPolicy is not the first suspect.

## 17. Service Name Works but External Route Fails

If internal service access works but external route fails:

Check:

```bash
oc get route -n <namespace>
oc describe route <route> -n <namespace>
oc get svc,endpoints -n <namespace>
oc logs -n openshift-ingress deploy/router-default --tail=100 2>/dev/null || true
```

Potential causes:

- Missing allow from `openshift-ingress` namespace.
- Service targetPort mismatch.
- Pod readiness failing; router has no usable endpoint.
- TLS termination/misconfigured certificate.
- Route points to wrong service or wrong service port.
- Application listens only on localhost inside container.
- Backend requires HTTPS but route sends HTTP, or vice versa.

NetworkPolicy suspicion increases when the route worked before a default-deny policy was applied.

## 18. Cross-Namespace Traffic Blocked

Scenario:

```text
namespace checker: source pod app=checker
namespace database: destination pod app=mysql
target port: 3306/TCP
```

### Label source namespace

```bash
oc label ns checker team=devsecops --overwrite
```

### Ensure source pod has expected label

```bash
oc label pod -n checker <checker-pod> app=checker --overwrite
```

For Deployment-managed pods, label the Deployment template instead:

```bash
oc patch deploy checker -n checker --type merge -p \
  '{"spec":{"template":{"metadata":{"labels":{"app":"checker"}}}}}'
```

### Correct destination ingress policy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-checker-to-mysql
  namespace: database
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          team: devsecops
      podSelector:
        matchLabels:
          app: checker
    ports:
    - protocol: TCP
      port: 3306
```

### If source namespace has egress default-deny

Add source egress allow:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-to-mysql
  namespace: checker
spec:
  podSelector:
    matchLabels:
      app: checker
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: database
      podSelector:
        matchLabels:
          app: mysql
    ports:
    - protocol: TCP
      port: 3306
```

Now both directions are covered.

## 20. AdminNetworkPolicy and BaselineAdminNetworkPolicy

In newer OpenShift releases, cluster administrators might use `AdminNetworkPolicy` and `BaselineAdminNetworkPolicy` for cluster-wide controls.

### Why this matters

A namespace `NetworkPolicy` can look correct, but traffic can still fail because:

- An `AdminNetworkPolicy` has an explicit deny rule.
- An `AdminNetworkPolicy` does not pass traffic down to namespace policies.
- A `BaselineAdminNetworkPolicy` denies traffic when no namespace policy overrides it.
- Cluster policy is selecting broader namespaces than intended.

### Inspect resources

```bash
oc api-resources | grep -i networkpolicy
oc get adminnetworkpolicy -o yaml 2>/dev/null || true
oc get baselineadminnetworkpolicy -o yaml 2>/dev/null || true
```

### Troubleshooting questions

Ask:

```text
Does an ANP subject select my source or destination namespace?
Does the rule action Deny this traffic?
Does the rule action Pass this traffic to namespace NetworkPolicy?
Does a lower number priority ANP override a later rule?
Does BANP deny this traffic as baseline?
```

### Production warning

Be very careful with broad selectors in cluster-scoped policies. A bad cluster-scoped deny can impact platform namespaces and make the cluster difficult to operate.

## 21. HostNetwork and OpenShift System Components

Host-networked pods and OpenShift system traffic require special care.

Examples of traffic that might be affected after applying restrictive policies:

- OpenShift ingress/router traffic
- OpenShift API server callbacks
- monitoring scrapes
- DNS traffic
- node-local components
- operators using host networking
- webhooks or admission controllers

### Allow from host-network namespaces

OpenShift documents a useful pattern using the namespace label for host-network traffic:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-hostnetwork
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/host-network: ""
```

### Validate namespace labels

```bash
oc get ns --show-labels | grep -E 'host-network|ingress|openshift-ingress|openshift-kube-apiserver'
```

### Important

Do not manually apply reserved OpenShift policy-group labels to your own custom namespaces. Use custom labels for custom grouping.

## 22. External IP, LoadBalancer, Node, and ipBlock Behavior

`ipBlock` is for CIDR-based sources or destinations. It is best used for cluster-external IP ranges, not pod IPs.

### Example: allow egress to an external API

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-external-api
  namespace: app-prod
spec:
  podSelector:
    matchLabels:
      app: worker
  policyTypes:
  - Egress
  egress:
  - to:
    - ipBlock:
        cidr: 203.0.113.10/32
    ports:
    - protocol: TCP
      port: 443
```

### Avoid using pod CIDRs in ipBlock

Pod IPs are ephemeral. A restarted pod can get a new IP, and IP-based rules become fragile.

Prefer:

```yaml
namespaceSelector + podSelector
```

for in-cluster pod traffic.

### External IP and service behavior

When services expose external IPs or traffic goes through load balancers, the source IP seen by NetworkPolicy can vary depending on implementation and traffic path.

For OpenShift OVN-Kubernetes, explicitly allow required namespaces and service ports when external IP service access crosses namespace boundaries.

## 26. Performance and Scale Considerations

NetworkPolicy can affect OVN/OVS flow scale.

Bad design:

```text
Hundreds of tiny policies selecting individual pods.
Many rules with highly specific podSelector/namespaceSelector combinations.
Policy churn from automation repeatedly creating/deleting policies.
```

Better design:

```text
Use stable labels.
Group workloads by namespace where possible.
Use one policy with multiple rules if the same podSelector is repeated.
Use matchExpressions to consolidate similar selectors.
Avoid per-pod unique labels for policy selection.
Prefer namespace-level grouping for tenant boundaries.
```

### Example optimization

Less efficient:

```yaml
ingress:
- from:
  - podSelector:
      matchLabels:
        role: frontend
- from:
  - podSelector:
      matchLabels:
        role: backend
```

More efficient:

```yaml
ingress:
- from:
  - podSelector:
      matchExpressions:
      - key: role
        operator: In
        values:
        - frontend
        - backend
```

### Operational warning

A NetworkPolicy may be logically correct but operationally expensive at scale. In very large namespaces, policy design can contribute to slow convergence or high flow counts.

## 27. Safe Remediation Playbooks

### Playbook A: Route broken after default-deny ingress

1. Confirm route/service/endpoints.
2. Confirm default-deny ingress policy exists.
3. Add allow from OpenShift ingress.
4. Test route.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/ingress: ""
```

### Playbook B: DNS broken after default-deny egress

1. Confirm `nslookup` timeout.
2. Add DNS egress allow.
3. Retest DNS.
4. Add app destination allow rules.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress

  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

### Playbook C: Database traffic blocked cross namespace

1. Check source namespace label.
2. Check source pod label.
3. Check destination pod label.
4. Add destination ingress allow.
5. If source has egress default-deny, add source egress allow.
6. Test with `nc`.

### Playbook D: Temporarily prove NetworkPolicy is the cause

Do not delete production policy blindly. Instead create a narrow temporary allow rule.

```yaml
        matchLabels:
```

Remove after permanent remediation:


## 28. Break-Glass Recovery

Use only during an active outage and with approval.

### Option 1: Delete the newest suspicious policy

```bash
oc get netpol -n <namespace> --sort-by=.metadata.creationTimestamp
oc delete netpol <policy> -n <namespace>
```

### Option 2: Add temporary allow-all ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: breakglass-allow-all-ingress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - {}
```

### Option 3: Add temporary allow-all egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: breakglass-allow-all-egress
  namespace: app-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - {}
```

### Warning

Because NetworkPolicies are additive, an allow-all policy can override the restrictive effect of other namespace policies for selected pods. Use this as a temporary restore-service measure only.

Track it:

```bash
oc annotate netpol breakglass-allow-all-ingress -n app-prod \
  incident="INC12345" owner="platform" expires="2026-07-04T00:00:00+05:30" --overwrite
```

## 29. Real-World Root Cause Matrix

| Symptom | Fast check | Likely root cause | Fix |
|---|---|---|---|
| Route times out after hardening | `oc get netpol -n app` | Missing allow from ingress controller | Add `allow-from-openshift-ingress` |
| App cannot resolve service DNS | `nslookup svc.ns.svc` | Egress default-deny blocks DNS | Allow UDP/TCP 53 to DNS |
| DB connection timeout | `nc -vz db 3306` | Destination ingress or source egress block | Allow both sides if isolated |
| Policy exists but no effect | `oc get pod -l ...` | `spec.podSelector` matches no pods | Fix labels/selectors |
| Cross-namespace allow fails | `oc get ns --show-labels` | Missing namespace label | Add correct namespace label or use existing one |
| Same namespace allow works, cross namespace fails | Inspect YAML `from` | Missing `namespaceSelector` | Add namespace selector |
| Too much traffic allowed | YAML has separate selector list items | OR used instead of AND | Put namespaceSelector and podSelector in same item |
| Too little traffic allowed | YAML has same item selectors | AND used instead of OR | Split into separate list entries |
| Service has no endpoints | `oc get endpoints` | Service selector/readiness issue | Fix service selector/readiness |
| `Connection refused` | `nc` returns refused | App not listening/wrong port | Fix container port/app bind |
| Namespace policy allows but blocked | `oc get anp,banp` | Cluster-scoped policy deny | Fix ANP/BANP |
| External API blocked | `curl external` | Egress default-deny | Add egress to IP/CIDR/port/proxy |
| Monitoring scrape fails | Check monitoring policies | Scraper namespace not allowed | Allow monitoring namespace/pods |

## 31. Interview / Exam Notes

### Key statements to remember

```text
NetworkPolicy is namespace-scoped.
NetworkPolicy selects pods, not services.
In ingress policy, spec.podSelector selects destination pods.
In egress policy, spec.podSelector selects source pods.
podSelector without namespaceSelector selects pods in the same namespace as the policy.
namespaceSelector matches namespace labels, not namespace names unless such a label exists.
Policies are additive; there is no rule ordering between standard NetworkPolicies.
NetworkPolicy has implicit deny only after a pod is isolated.
Both source egress and destination ingress must allow pod-to-pod communication.
Default-deny egress also blocks DNS.
OpenShift routes need ingress-controller traffic allowed when destination pods are ingress-isolated.
AdminNetworkPolicy can override namespace-level assumptions.
```

### Common exam-style task

```text
Allow pod checker in namespace checker to access MySQL pod in namespace database on TCP/3306.
```

Correct thinking:

```text
Create policy in destination namespace database.
Select destination MySQL pods.
Allow source namespace checker using namespaceSelector.
Allow source checker pods using podSelector.
Allow TCP/3306.
Verify using nc/curl from checker pod.
```

## 33. Final Troubleshooting Runbook

Use this end-to-end sequence during an incident.

### Step 1: Define the failed tuple

```bash
SRC_NS=<source-namespace>
SRC_POD=<source-pod>
DST_NS=<destination-namespace>
DST_SVC=<destination-service>
DST_PORT=<destination-port>
PROTO=TCP
```

### Step 2: Confirm destination is healthy

```bash
oc get pod -n $DST_NS -o wide --show-labels
oc get svc,endpoints,endpointslice -n $DST_NS -o wide
oc describe svc $DST_SVC -n $DST_NS
```

### Step 3: Confirm source can run test

```bash
oc get pod -n $SRC_NS $SRC_POD -o wide --show-labels
oc exec -n $SRC_NS $SRC_POD -- sh -c 'hostname; ip addr | head; cat /etc/resolv.conf'
```

### Step 4: Test DNS

```bash
oc exec -n $SRC_NS $SRC_POD -- getent hosts ${DST_SVC}.${DST_NS}.svc
```

### Step 5: Test TCP/UDP

```bash
oc exec -n $SRC_NS $SRC_POD -- nc -vz -w 3 ${DST_SVC}.${DST_NS}.svc $DST_PORT
```

For HTTP:

```bash
oc exec -n $SRC_NS $SRC_POD -- curl -svm 5 http://${DST_SVC}.${DST_NS}.svc:${DST_PORT}/
```

### Step 6: List policies in both namespaces

```bash
oc get netpol -n $SRC_NS -o wide
oc get netpol -n $DST_NS -o wide
oc describe netpol -n $SRC_NS
oc describe netpol -n $DST_NS
```

### Step 7: Check cluster policies

```bash
oc get adminnetworkpolicy -o yaml 2>/dev/null || true
oc get baselineadminnetworkpolicy -o yaml 2>/dev/null || true
```

### Step 8: Verify labels

```bash
oc get ns $SRC_NS $DST_NS --show-labels
oc get pod -n $SRC_NS $SRC_POD --show-labels
oc get pod -n $DST_NS --show-labels
```

### Step 9: Fix with narrow allow

Apply the smallest policy that allows the exact tuple.

### Step 10: Retest

```bash
oc exec -n $SRC_NS $SRC_POD -- nc -vz -w 3 ${DST_SVC}.${DST_NS}.svc $DST_PORT
```

### Step 11: Validate no over-permission

```bash
oc describe netpol -n $DST_NS
oc get netpol -n $DST_NS -o yaml
```

## Closing Note

NetworkPolicy troubleshooting is not about guessing. It is about proving selectors and direction.

A strong OpenShift administrator always asks:

```text
Which pod is selected?
Which namespace is selected?
Which direction is isolated?
Which port is allowed?
Which cluster-scoped policy applies?
Did I test from the real source pod?
```

If you answer those questions with evidence, NetworkPolicy incidents become predictable and fast to resolve.
