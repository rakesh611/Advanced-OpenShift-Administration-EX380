## 1. What “Image Registry Issues” Means in OpenShift

In OpenShift, “image registry issue” can mean many different failures. A junior admin often thinks only about one command:

```bash
oc get pods
```

A senior admin separates the problem into layers:

| Layer | Example Problem |
|---|---|
| Cluster image registry | Internal OpenShift registry unavailable, degraded, removed, no storage |
| Registry Operator | `image-registry` ClusterOperator degraded or progressing |
| Storage | PVC pending, bucket inaccessible, no space, permission denied, object storage issue |
| Network | Worker cannot reach internal/external registry, DNS failure, proxy failure |
| TLS trust | `x509: certificate signed by unknown authority` |
| Authentication | `unauthorized: authentication required`, expired token, missing pull secret |
| Authorization | User/service account cannot push or pull from namespace registry path |
| Runtime | CRI-O cannot pull image; kubelet reports image pull failures |
| Image policy | Registry blocked, allowlist missing, insecure registry not configured |
| ImageStream | Import fails, tag not resolved, image trigger not firing |
| Build | Build pod cannot pull builder image or push output image |
| Disconnected setup | Mirror registry incomplete, ImageContentSourcePolicy/ImageDigestMirrorSet wrong |
| External registry | Quay/registry.redhat.io/docker.io rate limit, outage, credential issue |

OpenShift image troubleshooting is not one command. It is a chain:

```text
Pod spec / BuildConfig / ImageStream
        ↓
ServiceAccount pull secret / global pull secret
        ↓
Image policy: allowed / blocked / mirror / insecure / CA
        ↓
Node CRI-O + kubelet
        ↓
DNS / proxy / firewall / route
        ↓
Registry authentication / authorization
        ↓
Registry storage
        ↓
Image Registry Operator health
```

## 2. OpenShift Image Registry Architecture

OpenShift provides an integrated container image registry. It is normally managed by the **Image Registry Operator**.

### 2.1 Main Architecture

```text
Developer / Build pod / Workload pod
          |
          | pull / push image
          v
image-registry service
openshift-image-registry.svc:5000
          |
          v
image-registry deployment / pods
          |
          v
Backend storage
S3 / Azure Blob / GCS / Swift / PVC / object storage / configured storage
```

### 2.2 Important Namespaces

| Namespace | Purpose |
|---|---|
| `openshift-image-registry` | Internal registry operator-managed components |
| `openshift-config` | Global pull secret, additional trusted CAs |
| `openshift` | Default image streams and samples |
| `openshift-marketplace` | Operator catalogs, catalog images |
| Application namespace | Service accounts, image pull secrets, image streams, build configs |

### 2.3 Registry Access Modes

| Access Mode | Hostname / Endpoint | Used By |
|---|---|---|
| Internal service | `image-registry.openshift-image-registry.svc:5000` | Pods/builds inside cluster |
| Internal default service with project path | `image-registry.openshift-image-registry.svc:5000/<namespace>/<image>:<tag>` | Workloads/builds |
| External route | `default-route-openshift-image-registry.apps.<cluster-domain>` | Admins pushing from outside |
| External custom route | Admin-defined route host | External CI/CD or admin push/pull |

### 2.4 Why Registry Storage Matters

The registry needs storage for image blobs and manifests. If storage is not configured, the registry cannot reliably run. On some platforms, registry storage is automatically configured. On others, especially many bare metal, vSphere, and user-provisioned environments, you must configure it.

Common storage backends:

| Backend | Typical Environment |
|---|---|
| S3 | AWS |
| Azure Blob | Azure |
| GCS | Google Cloud |
| Swift | OpenStack |
| PVC | Bare metal, vSphere, lab, small environments |
| External object storage | Production on-prem or disconnected setups |

## 5. Fast Triage Workflow

This is the first workflow I use in real production.

### Step 1: Identify the Exact Failure Class

```bash
oc get pods -A | egrep 'ImagePullBackOff|ErrImagePull|InvalidImageName|CrashLoopBackOff'
```

Then inspect one failed pod:

```bash
oc describe pod <pod-name> -n <namespace>
```

Look at the **Events** section first.

### Step 2: Check Cluster Registry Operator

```bash
oc get co image-registry
oc describe co image-registry
```

### Step 3: Check Registry Namespace

```bash
oc get all -n openshift-image-registry
oc get pvc -n openshift-image-registry
oc get events -n openshift-image-registry --sort-by=.lastTimestamp
```

### Step 4: Check Registry Config

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Focus on:

```yaml
spec.managementState
spec.storage
spec.defaultRoute
spec.replicas
status.conditions
```

### Step 5: Check Image Policy

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Focus on:

```yaml
spec.registrySources
spec.additionalTrustedCA
status.internalRegistryHostname
```

### Step 6: Check Pull Secret

For global pull secret:

```bash
oc extract secret/pull-secret -n openshift-config --to=/tmp/pullsecret --confirm
cat /tmp/pullsecret/.dockerconfigjson | jq
```

For namespace/service account:

```bash
oc describe sa default -n <namespace>
oc describe sa builder -n <namespace>
```

### Step 7: Test From a Node

```bash
oc debug node/<node-name>
chroot /host
crictl pull <image>
```

Or test DNS/connectivity:

```bash
getent hosts registry.redhat.io
curl -vk https://registry.redhat.io/v2/
curl -vk https://image-registry.openshift-image-registry.svc:5000/v2/
```

### Step 8: Decide the Layer

Use this table:

| Event Message | Most Likely Layer |
|---|---|
| `x509: certificate signed by unknown authority` | CA trust |
| `unauthorized: authentication required` | Pull secret/auth |
| `manifest unknown` | Wrong image/tag |
| `no such host` | DNS |
| `i/o timeout` | Network/proxy/firewall |
| `server gave HTTP response to HTTPS client` | Insecure registry config |
| `denied by policy` | Allowed/blocked registry policy |
| `registry is removed` | Image Registry Operator config/storage |
| PVC pending | Storage class/PV issue |
| Build push denied | RBAC/image push permission/internal registry auth |

## 6. Image Registry Operator Troubleshooting

The Image Registry Operator manages the internal OpenShift registry.

### 6.1 Check ClusterOperator

```bash
oc get co image-registry
oc describe co image-registry
```

Look for:

```text
Available=False
Progressing=True
Degraded=True
Upgradeable=False
```

### 6.2 Check Operator Pod

```bash
oc get pods -n openshift-image-registry
oc logs deploy/cluster-image-registry-operator -n openshift-image-registry
```

If the operator itself is failing:

```bash
oc describe pod -l name=cluster-image-registry-operator -n openshift-image-registry
```

Check events:

```bash
oc get events -n openshift-image-registry --sort-by=.lastTimestamp
```

### 6.3 Management State Problems

Check:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o jsonpath='{.spec.managementState}{"\n"}'
```

Possible values:

| State | Meaning |
|---|---|
| `Managed` | Operator actively manages registry |
| `Unmanaged` | Operator does not reconcile changes |
| `Removed` | Registry is intentionally removed |

If registry is removed:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"managementState":"Managed"}}'
```

But **do not just set Managed blindly**. Confirm storage is configured, otherwise the operator can remain degraded.

### 6.4 Registry Removed After Installation

On platforms without default shareable object storage, the image registry may be installed as `Removed`.

Symptoms:

```bash
oc get co image-registry
```

```text
Available=False
Degraded=True
Message: The registry is removed
```

Check config:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Typical fix with PVC storage:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"managementState":"Managed","storage":{"pvc":{"claim":""}}}}'
```

The empty claim lets the operator create a PVC in many supported configurations. In stricter production environments, you should define storage explicitly according to your platform/storage design.

Check:

```bash
oc get pvc -n openshift-image-registry
oc get deploy -n openshift-image-registry
oc get pods -n openshift-image-registry
oc get co image-registry
```

### 6.5 Operator Cannot Apply Resources

Symptoms:

```text
Failed to create deployment
Failed to update service
Failed to apply route
```

Check operator logs:

```bash
oc logs deploy/cluster-image-registry-operator -n openshift-image-registry
```

Check API/RBAC/admission errors:

```bash
oc get events -n openshift-image-registry --sort-by=.lastTimestamp
oc auth can-i '*' '*' --as=system:serviceaccount:openshift-image-registry:cluster-image-registry-operator
```

Normally, Red Hat-managed cluster operators should already have the correct permissions. If permissions are missing, suspect:

- accidental deletion of cluster roles/bindings
- broken operator install payload
- unsupported manual modification
- admission webhook blocking operator resources
- API server/RBAC problem beyond the registry itself

### 6.6 Registry Deployment Minimum Availability Failure

Symptoms:

```text
Deployment does not have minimum availability
```

Check:

```bash
oc get deploy image-registry -n openshift-image-registry
oc describe deploy image-registry -n openshift-image-registry
oc get rs -n openshift-image-registry
oc get pods -l docker-registry=default -n openshift-image-registry
```

Then inspect pods:

```bash
oc describe pod <registry-pod> -n openshift-image-registry
oc logs <registry-pod> -n openshift-image-registry
```

Common causes:

| Cause | Evidence |
|---|---|
| Storage mount failure | Pod stuck `ContainerCreating`; PVC events |
| Bad storage credentials | Registry logs show S3/Azure/GCS auth errors |
| Node scheduling issue | Pod pending, taints, insufficient CPU/memory |
| Probe failure | Readiness/liveness probe errors |
| Bad route/cert config | TLS-related logs |
| Network issue to object storage | timeout in registry logs |

## 7. Registry Storage Issues

Registry storage issues are among the most common internal registry failures.

### 7.1 Check Storage Configuration

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Examples:

#### PVC

```yaml
spec:
  storage:
    pvc:
      claim: image-registry-storage
```

#### Empty PVC Claim

```yaml
spec:
  storage:
    pvc:
      claim: ""
```

#### S3

```yaml
spec:
  storage:
    s3:
      bucket: my-registry-bucket
      region: us-east-1
```

### 7.2 Check PVC

```bash
oc get pvc -n openshift-image-registry
oc describe pvc -n openshift-image-registry
oc get pv
oc get sc
```

Common PVC states:

| PVC State | Meaning |
|---|---|
| `Pending` | No matching PV or dynamic provisioning failed |
| `Bound` | PVC has storage |
| `Lost` | Bound PV no longer available |
| `Terminating` | Finalizer/protection or pod still using it |

### 7.3 PVC Pending

Example:

```text
persistentvolumeclaim/image-registry-storage Pending
```

Check:

```bash
oc describe pvc image-registry-storage -n openshift-image-registry
```

Common reasons:

```text
no persistent volumes available for this claim
storageclass.storage.k8s.io "xyz" not found
waiting for first consumer
failed to provision volume
```

Fix based on cause:

#### No default StorageClass

```bash
oc get sc
```

If no default class, either set one:

```bash
oc annotate sc <storageclass-name> storageclass.kubernetes.io/is-default-class=true
```

Or patch registry to use a known PVC/storage option.

#### Static PV Example

For a lab NFS-backed registry PVC:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: registry-pv
spec:
  capacity:
    storage: 100Gi
  accessModes:
  - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: nfs.example.com
    path: /exports/registry
```

Apply:

```bash
oc apply -f registry-pv.yaml
```

Then create PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: image-registry-storage
  namespace: openshift-image-registry
spec:
  accessModes:
  - ReadWriteMany
  resources:
    requests:
      storage: 100Gi
```

Apply:

```bash
oc apply -f registry-pvc.yaml
```

Patch registry:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"managementState":"Managed","storage":{"pvc":{"claim":"image-registry-storage"}}}}'
```

### 7.4 Storage Permission Denied

Registry pod logs may show:

```text
permission denied
filesystem: mkdir /registry/docker: permission denied
```

Check volume permissions. For NFS:

- export path exists
- correct ownership/permissions
- SELinux context if applicable
- no root squash issue affecting write operations
- RW access from worker nodes

Debug:

```bash
oc rsh -n openshift-image-registry <registry-pod>
id
mount | grep registry
touch /registry/test
```

If `oc rsh` is unavailable due to readiness issues, use a debug/helper pod with the same PVC only in a controlled maintenance window.

### 7.5 No Space Left on Device

Symptoms:

```text
no space left on device
blob upload invalid
filesystem: write: no space left on device
```

Check PVC capacity:

```bash
oc get pvc -n openshift-image-registry
oc describe pvc <pvc-name> -n openshift-image-registry
```

Check actual usage:

```bash
oc exec -n openshift-image-registry deploy/image-registry -- df -h
```

For object storage, check bucket quota/usage from cloud or storage console.

Options:

1. Expand PVC if supported:
   ```bash
   oc patch pvc image-registry-storage -n openshift-image-registry \
     -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'
   ```

2. Prune unused images:
   ```bash
   oc adm prune images --confirm
   ```

3. Fix build/deployment retention policies.

4. Move to object storage for production scale.

### 7.6 Object Storage Credential or Network Failure

Registry logs may show:

```text
AccessDenied
SignatureDoesNotMatch
NoSuchBucket
RequestTimeout
connection reset by peer
```

Check:

```bash
oc logs deploy/image-registry -n openshift-image-registry
oc get secret -n openshift-image-registry
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Common issues:

| Issue | Fix |
|---|---|
| Bucket deleted | Recreate bucket or restore config |
| Wrong region | Correct region in registry config |
| Expired cloud credential | Rotate secret |
| Network blocked to object endpoint | Check firewall/proxy/routing |
| IAM missing permissions | Grant read/write/list/delete as required |
| Proxy missing | Configure cluster-wide proxy/noProxy correctly |

## 8. Registry Pod, Deployment, Service, and Route Issues

### 8.1 Check Registry Pods

```bash
oc get pods -n openshift-image-registry -o wide
```

Common problems:

| Pod State | Cause |
|---|---|
| `Pending` | Scheduling, resources, PVC, node selector, taints |
| `ContainerCreating` | Volume mount, CNI, image pull |
| `CrashLoopBackOff` | Registry config/storage/backend error |
| `Running 0/1` | Readiness probe failing |
| `Running 1/1` | Pod healthy, issue may be route/auth/client |

### 8.2 Check Deployment

```bash
oc describe deploy image-registry -n openshift-image-registry
```

Check:

```text
Replicas
AvailableReplicas
Conditions
Strategy
Node selector
Tolerations
Volumes
Environment variables
```

### 8.3 Registry Readiness Probe Failure

Example:

```text
Readiness probe failed: HTTP probe failed with statuscode: 503
```

Check logs:

```bash
oc logs deploy/image-registry -n openshift-image-registry
```

Likely causes:

- backend storage not ready
- registry cannot write to storage
- registry cannot initialize
- network to object storage failing
- bad config secret

### 8.4 Service Missing or Wrong

Check:

```bash
oc get svc -n openshift-image-registry
oc describe svc image-registry -n openshift-image-registry
oc get endpoints image-registry -n openshift-image-registry
```

Expected service:

```text
image-registry   ClusterIP   <ip>   5000/TCP
```

If endpoints are empty:

```bash
oc get pods -n openshift-image-registry --show-labels
oc get endpoints image-registry -n openshift-image-registry -o yaml
```

Empty endpoints usually means:

- registry pod not ready
- labels do not match service selector
- operator reconciliation broken
- manual unsupported modification changed labels/selectors

Do not manually edit operator-managed service selectors unless Red Hat support or official procedure requires it. Fix the underlying pod/operator issue.

### 8.5 Exposing the Registry Externally

Check route:

```bash
oc get route -n openshift-image-registry
```

Enable default route:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"defaultRoute":true}}'
```

Get route:

```bash
oc get route default-route -n openshift-image-registry
```

Login from outside:

```bash
HOST=$(oc get route default-route -n openshift-image-registry -o jsonpath='{.spec.host}')
podman login -u $(oc whoami) -p $(oc whoami -t) $HOST
```

Tag and push:

```bash
podman tag localhost/myapp:latest $HOST/myproject/myapp:latest
podman push $HOST/myproject/myapp:latest
```

### 8.6 Route Returns 503

Check route backend:

```bash
oc describe route default-route -n openshift-image-registry
oc get endpoints image-registry -n openshift-image-registry
```

If endpoints are empty, the route is not the problem. Fix registry pods/readiness first.

Check ingress/router:

```bash
oc get co ingress
oc get pods -n openshift-ingress
oc logs -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=default
```

### 8.7 Route TLS Problem

Symptoms:

```text
x509: certificate signed by unknown authority
certificate is valid for ..., not ...
```

Check:

```bash
oc get route default-route -n openshift-image-registry -o yaml
```

If using custom certs, validate:

```bash
openssl s_client -connect <route-host>:443 -servername <route-host> </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
```

Make sure the certificate CN/SAN matches the route hostname.

## 9. Image Pull Failures: `ImagePullBackOff` and `ErrImagePull`

Image pull failures can come from many layers.

### 9.1 Start With Pod Events

```bash
oc describe pod <pod> -n <namespace>
```

Look at:

```text
Events:
  Warning  Failed  kubelet  Failed to pull image ...
```

### 9.2 Typical Error Mapping

| Error | Meaning | First Fix Area |
|---|---|---|
| `unauthorized: authentication required` | Missing/wrong credentials | Pull secret |
| `denied: requested access` | Authenticated but not authorized | Registry permissions/repository |
| `manifest unknown` | Tag/digest does not exist | Image reference/tag |
| `not found` | Repository/tag missing | Image reference |
| `x509` | CA not trusted | additionalTrustedCA |
| `no such host` | DNS failure | DNS/network |
| `i/o timeout` | Network/firewall/proxy | Egress/network |
| `connection refused` | Registry service not listening | Registry endpoint |
| `HTTP response to HTTPS client` | Registry is insecure/HTTP | insecureRegistries |
| `too many requests` | Rate limit | Mirror/authenticate/use pull secret |
| `invalid reference format` | Bad image name | YAML/spec typo |

### 9.3 Validate Image Name

Common mistakes:

```yaml
image: nginx
image: nginx:latest
image: registry.example.com/project/app:v1
image: image-registry.openshift-image-registry.svc:5000/myproject/myapp:latest
```

Bad examples:

```yaml
image: https://registry.example.com/app:v1
image: registry.example.com:5000/app:v1/
image: registry.example.com/app v1
image: registry.example.com/app:
```

Check deployment:

```bash
oc get deploy <deploy> -n <namespace> -o jsonpath='{.spec.template.spec.containers[*].image}{"\n"}'
```

Patch image:

```bash
oc set image deploy/<deploy> <container>=<correct-image> -n <namespace>
```

### 9.4 Pull From Internal Registry

Internal registry reference pattern:

```text
image-registry.openshift-image-registry.svc:5000/<namespace>/<imagestream-or-image>:<tag>
```

Example:

```bash
oc set image deploy/myapp \
  myapp=image-registry.openshift-image-registry.svc:5000/dev/myapp:latest \
  -n prod
```

### 9.5 Pull From External Registry

Test manually from a node:

```bash
oc debug node/<node>
chroot /host
crictl pull registry.example.com/team/app:v1
```

If `crictl pull` fails on the node, the problem is not Kubernetes YAML only. It is node runtime, DNS, CA, auth, policy, mirror, or network.

Check:

```bash
oc get pods -o wide -n <namespace>
```

## 10. Authentication and Pull Secret Problems

### 10.1 Types of Pull Secrets

| Pull Secret Type | Location | Scope |
|---|---|---|
| Global pull secret | `openshift-config/pull-secret` | Cluster-level |
| Namespace secret | App namespace | Project-specific |
| ServiceAccount imagePullSecret | Attached to SA | Pod-specific |
| Build source/pull secret | BuildConfig | Build-specific |
| CatalogSource secret | Catalog namespace | Operator catalog image pull |

### 10.2 Global Pull Secret

View:

```bash
oc extract secret/pull-secret -n openshift-config --to=/tmp/pullsecret --confirm
cat /tmp/pullsecret/.dockerconfigjson | jq
```

Update carefully:

```bash
oc set data secret/pull-secret -n openshift-config \
  --from-file=.dockerconfigjson=/path/to/merged-pull-secret.json
```

Important production note:

- Always merge credentials; do not accidentally overwrite Red Hat registry credentials.
- Keep a backup before modification.
- A pull secret update may roll out to nodes through cluster components. Watch MCP and node status.

Backup:

```bash
oc get secret pull-secret -n openshift-config -o yaml > pull-secret-backup.yaml
```

### 10.3 Create Namespace Pull Secret

```bash
oc create secret docker-registry myregistry-pull \
  --docker-server=registry.example.com \
  --docker-username=myuser \
  --docker-password='mypassword' \
  --docker-email=unused@example.com \
  -n myproject
```

Attach to default service account:

```bash
oc secrets link default myregistry-pull --for=pull -n myproject
```

Verify:

```bash
oc describe sa default -n myproject
```

Expected:

```text
Image pull secrets: myregistry-pull
```

### 10.4 Attach Pull Secret to a Specific ServiceAccount

```bash
oc create sa app-sa -n myproject

oc secrets link app-sa myregistry-pull --for=pull -n myproject
```

Deployment:

```yaml
spec:
  template:
    spec:
      serviceAccountName: app-sa
```

### 10.5 Build Pull Secret

BuildConfig example:

```yaml
apiVersion: build.openshift.io/v1

  name: myapp

      uri: https://git.example.com/team/myapp.git

      kind: ImageStreamTag
```

### 10.6 Unauthorized Pull From Internal Registry

Symptoms:

```text
unauthorized: authentication required
```

If pulling from internal registry across namespaces, verify permission.

For pod in namespace `prod` pulling image from namespace `dev`:

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:prod:default \
  -n dev
```

Explanation:

- The permission is granted **in the source image namespace**.
- The subject is the service account from the consuming namespace.

Verify:

```bash
oc auth can-i get imagestreams/layers \
  --as=system:serviceaccount:prod:default \
  -n dev
```

### 10.7 Unauthorized Push to Internal Registry

To push to project `dev`, user or service account needs image push permission in that namespace.

For a user:

```bash
oc policy add-role-to-user system:image-builder <username> -n dev
```

For a service account:

```bash
oc policy add-role-to-user system:image-builder \
  system:serviceaccount:ci:builder \
  -n dev
```

Test login:

```bash
HOST=$(oc get route default-route -n openshift-image-registry -o jsonpath='{.spec.host}')
podman login -u <username> -p $(oc whoami -t) $HOST
```

Push:

```bash
podman push $HOST/dev/myapp:latest
```

### 10.8 Secret Exists but Pull Still Fails

Check these mistakes:

| Mistake | Check |
|---|---|
| Secret created in wrong namespace | `oc get secret -n <namespace>` |
| Secret not linked to SA | `oc describe sa <sa> -n <namespace>` |
| Deployment uses different SA | `oc get deploy -o yaml` |
| Registry server key mismatch | Check `.dockerconfigjson` auth key |
| Password/token expired | Re-login and recreate secret |
| Secret type wrong | `kubernetes.io/dockerconfigjson` expected |
| Node not updated with global pull secret | Check MCP/node rollout |
| External registry requires repository-specific permission | Test with same credentials using podman |

Inspect secret:

```bash
oc get secret myregistry-pull -n myproject \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq
```

The registry key must match the image reference host.

Example:

Image:

```text
registry.example.com:8443/team/app:v1
```

Secret must contain auth for:

```text
registry.example.com:8443
```

Not only:

```text
registry.example.com
```

## 11. TLS, CA, and x509 Registry Issues

### 11.1 Common x509 Errors

```text
x509: certificate signed by unknown authority
x509: certificate has expired or is not yet valid
x509: certificate is valid for registry1.example.com, not registry2.example.com
certificate signed by unknown authority
```

### 11.2 Determine Which Client Fails

| Client | Where CA Must Be Trusted |
|---|---|
| Pod pull by kubelet/CRI-O | Node trust via image config/MCO |
| ImageStream import | Cluster image import controller trust |
| Build pod pulling base image | Node/runtime and build strategy secret |
| External podman push | Admin workstation trust |
| Operator catalog pull | Node/runtime and catalog namespace secret |

### 11.3 Add Additional Trusted CA for Registries

Create a ConfigMap in `openshift-config`.

The key name must match the registry hostname, including port if used.

Example for `registry.lab.example.com:5000`:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.lab.example.com..5000=/path/to/ca.crt
```

Many OpenShift examples use `..` to represent `:` in the ConfigMap key name.

Patch image config:

```bash
oc patch image.config.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Watch rollout:

```bash
oc get mcp
oc describe mcp worker
```

Test after rollout:

```bash
oc debug node/<node>
chroot /host
crictl pull registry.lab.example.com:5000/team/app:v1
```

### 11.4 Validate Certificate From Node

```bash
oc debug node/<node>
chroot /host
openssl s_client -connect registry.lab.example.com:5000 -servername registry.lab.example.com </dev/null
```

Check:

```text
Verify return code: 0 (ok)
```

If not OK, inspect issuer/SAN:

```bash
openssl s_client -connect registry.lab.example.com:5000 -servername registry.lab.example.com </dev/null 2>/dev/null \
 | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### 11.5 `server gave HTTP response to HTTPS client`

This means the client tried HTTPS but the registry is plain HTTP.

Options:

1. Fix registry to use proper TLS.
2. In lab/non-production, configure insecure registry.

Patch:

```bash
oc patch image.config.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"registrySources":{"insecureRegistries":["registry.lab.example.com:5000"]}}}'
```

Watch MCP:

```bash
oc get mcp
```

Test:

```bash
oc debug node/<node>
chroot /host
crictl pull registry.lab.example.com:5000/team/app:v1
```

Production recommendation: use trusted TLS, not insecure registries.

### 11.6 Certificate Expired

Symptoms:

```text
certificate has expired or is not yet valid
```

Check certificate dates:

```bash
openssl s_client -connect registry.example.com:443 -servername registry.example.com </dev/null 2>/dev/null \
 | openssl x509 -noout -dates
```

Fix:

- Renew registry certificate.
- Update OpenShift trusted CA if CA chain changed.
- Restart/reload external registry if needed.
- Wait for MCO rollout if OpenShift CA ConfigMap changed.

## 12. Allowed, Blocked, Insecure, and Mirrored Registry Policy Issues

OpenShift can enforce image registry sources using the cluster image configuration resource.

### 12.1 Check Current Image Policy

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Look for:

```yaml
spec:
  registrySources:
    allowedRegistries:
    - registry.redhat.io
    - quay.io
    blockedRegistries:
    - docker.io
    insecureRegistries:
    - registry.lab.example.com:5000
```

### 12.2 Allowed vs Blocked Registries

Important concept:

- `allowedRegistries`: only listed registries are allowed; all others are blocked.
- `blockedRegistries`: listed registries are blocked; all others are allowed.
- You should not configure both as active policy for the same intent.

If workloads fail after a registry policy change, check if the image registry is missing from allowlist.

Example internal registry must be allowed if allowlist is used:

```yaml
allowedRegistries:
- registry.redhat.io
- quay.io
- image-registry.openshift-image-registry.svc:5000
- default-route-openshift-image-registry.apps.example.com
```

Patch example:

```bash
oc patch image.config.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"registrySources":{"allowedRegistries":["registry.redhat.io","quay.io","image-registry.openshift-image-registry.svc:5000"]}}}'
```

### 12.3 Policy Change Not Applied on Nodes

Check MCP:

```bash
oc get mcp
oc describe mcp worker
```

Check node files:

```bash
oc debug node/<node>
chroot /host
cat /etc/containers/registries.conf
cat /etc/containers/policy.json
```

If MCP degraded:

```bash
oc describe mcp worker
oc get mc
oc get nodes
```

A registry policy problem can look like an image pull issue, but the real problem is Machine Config rollout.

### 12.4 Insecure Registry Misconfiguration

Check:

```bash
oc get image.config.openshift.io/cluster -o jsonpath='{.spec.registrySources.insecureRegistries}{"\n"}'
```

Registry host must match exact image host and port.

Image:

```text
registry.lab.example.com:5000/team/app:v1
```

Config:

```yaml
insecureRegistries:
- registry.lab.example.com:5000
```

Not:

```yaml
insecureRegistries:
- registry.lab.example.com
```

### 12.5 Mirror Registry Config

Modern OpenShift versions can use resources such as:

- `ImageContentSourcePolicy` in older 4.x flows
- `ImageDigestMirrorSet`
- `ImageTagMirrorSet`

Check:

```bash
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

Inspect:

```bash
oc get imagedigestmirrorset -o yaml
oc get imagetagmirrorset -o yaml
```

If mirror config is changed, check MCP rollout:

```bash
oc get mcp
```

Common issues:

| Issue | Symptom |
|---|---|
| Mirror missing image digest | Pull falls back or fails |
| Digest-only mirror used for tag pull | Tag pull not mirrored as expected |
| Wrong source registry | Mirror never used |
| Mirror requires auth but pull secret missing | Unauthorized |
| Mirror CA missing | x509 |
| Policy deployed but MCP not updated | Some nodes fail, some work |

Symptoms:

```text

```

- use digest
- push missing image
- verify repository path

```bash
oc describe is <imagestream> -n <namespace>
```

|---|---|
| `ImageStreamTag` | ImageStream import/tag/state |

In disconnected environments, sample image streams may still point to external registries that are unreachable.



### 16.7 CatalogSource ImagePullBackOff

Check catalog pods:

```bash
oc get pods -n openshift-marketplace
oc describe pod <catalog-pod> -n openshift-marketplace
```

Check CatalogSource:

```bash
oc get catalogsource -n openshift-marketplace
oc describe catalogsource <name> -n openshift-marketplace
```

If index image is private, create secret in `openshift-marketplace` and reference it in CatalogSource if required.

Example:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: custom-catalog
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: mirror.registry.example.com:8443/olm/custom-index:v1

  - mirror-pull-secret
```

### 16.8 Mirror Contains Tag but Pull Uses Digest

OpenShift release and many operator flows use digests, not only tags.

Wrong mirror:

```text
mirror has: app:v1
cluster pulls: app@sha256:abc...
```

Fix:

- mirror digest content, not only tags
- verify with `skopeo inspect`
- use the correct mirror mapping generated by `oc mirror` or supported mirroring workflow

### 16.9 Proxy and noProxy

Disconnected does not always mean no proxy. Check:

```bash
oc get proxy/cluster -o yaml
```

Important fields:

```yaml
spec:
  httpProxy:
  httpsProxy:
  noProxy:
```

The mirror registry should usually be in `noProxy` if it is internal.

Add if needed:

```bash
oc patch proxy/cluster --type merge \
  -p '{"spec":{"noProxy":"mirror.registry.example.com,.example.com,10.0.0.0/8"}}'
```

Be careful: patching proxy can affect many cluster components.

## 18. Registry Performance and Capacity Issues

### 18.1 Symptoms

```text
Slow image pulls
Build push timeout
Registry pod high CPU/memory
Blob upload timeout
Context deadline exceeded
503 from registry route
Node image pulls timing out during rollout
```

### 18.2 Check Registry Pod Resources

```bash
oc adm top pods -n openshift-image-registry
oc describe deploy image-registry -n openshift-image-registry
```

### 18.3 Scale Registry Replicas

Check current:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o jsonpath='{.spec.replicas}{"\n"}'
```

Patch:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"replicas":2}}'
```

Storage must support multi-replica access. Object storage is usually better for scalable registry deployments. PVC-based storage may have access mode limitations.

### 18.4 Check Storage Latency

Registry performance is heavily dependent on backend storage.

For object storage:

- bucket latency
- region distance
- network path
- proxy
- rate limits
- cloud throttling

For PVC/NFS:

- NFS server performance
- network bandwidth
- export options
- inode usage
- storage backend latency

### 18.5 Image Pruning

Manual prune dry-run:

```bash
oc adm prune images
```

Confirm:

```bash
oc adm prune images --confirm
```

Be careful in production:

- Understand retention.
- Avoid deleting images needed for rollback.
- Coordinate with app teams.
- Check registry storage backup/retention policy.

### 18.6 Avoid Excessive `latest`

Mutable tags cause confusion and re-pull problems. Prefer immutable image digests in production GitOps flows:

```yaml
image: registry.example.com/team/app@sha256:<digest>
```

Use tags for promotion workflows only when controlled.

## 19. Security, RBAC, SCC, and Admission-Related Image Issues

### 19.1 Image Pull vs Pod Security

An image pull issue occurs before container runtime starts the container. SCC/Pod Security issues usually show different errors:

```text
violates PodSecurity
unable to validate against any security context constraint
container has runAsNonRoot and image will run as root
```

Do not confuse these with image pull failures.

### 19.2 Image Requires Root but OpenShift Runs Random UID

Symptoms after image pull succeeds:

```text
permission denied
cannot write to /app
container exits
CrashLoopBackOff
```

This is not registry failure. It is image compatibility/security context issue.

Check logs:

```bash
oc logs <pod> -n <namespace>
```

Fix image to support arbitrary UID, or use appropriate SCC only when justified.

### 19.3 Internal Registry Cross-Namespace Pull

Again, for namespace `prod` pulling from `dev`:

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:prod:default \
  -n dev
```

### 19.4 Admission Webhooks Blocking Images

Some clusters use policy engines:

- Gatekeeper/OPA
- Kyverno
- Red Hat Advanced Cluster Security
- custom admission webhooks
- image signature enforcement

Symptoms:

```text
admission webhook denied the request
image registry not allowed
unsigned image denied
image violates policy
```

Check:

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc get events -n <namespace>
oc describe pod <pod> -n <namespace>
```

This is not a registry availability issue, but it blocks image usage.

### 19.5 Image Signature Policy

If image signature policy is enforced, check:

```bash
oc get image.config.openshift.io/cluster -o yaml
```

Node-level:

```bash
oc debug node/<node>
chroot /host
cat /etc/containers/policy.json
```

## 21. Production Recovery Runbooks

### Runbook 1: Internal Registry Removed / Not Available

**Symptoms**

```bash
oc get co image-registry
```

```text
Available=False Degraded=True Message: The registry is removed
```

**Steps**

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
oc get sc
oc get pvc -n openshift-image-registry
```

If using PVC for lab/small environment:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"managementState":"Managed","storage":{"pvc":{"claim":""}}}}'
```

Watch:

```bash
watch oc get co image-registry
oc get pods -n openshift-image-registry
oc get pvc -n openshift-image-registry
```

Validate:

```bash
oc get svc -n openshift-image-registry
oc run test --image=image-registry.openshift-image-registry.svc:5000/openshift/cli:latest --restart=Never
```

Use an image that actually exists in your cluster.

---

### Runbook 2: Workload Cannot Pull Private External Image

**Symptoms**

```text
ImagePullBackOff
unauthorized: authentication required
```

**Steps**

```bash
oc describe pod <pod> -n <ns>
oc get deploy <deploy> -n <ns> -o yaml | grep serviceAccountName
oc describe sa <sa> -n <ns>
```

Create secret:

```bash
oc create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=user \
  --docker-password='password' \
  --docker-email=unused@example.com \
  -n <ns>
```

Link:

```bash
oc secrets link <sa> regcred --for=pull -n <ns>
```

Restart rollout:

```bash
oc rollout restart deploy/<deploy> -n <ns>
```

Validate:

```bash
oc get pods -n <ns>
oc describe pod <new-pod> -n <ns>
```

---

### Runbook 3: x509 Pull Failure From Private Registry

**Symptoms**

```text
x509: certificate signed by unknown authority
```

**Steps**

Validate from node:

```bash
oc debug node/<node>
chroot /host
openssl s_client -connect registry.example.com:5000 -servername registry.example.com </dev/null
```

Create CA ConfigMap:

```bash
oc create configmap registry-cas \
  -n openshift-config \
  --from-file=registry.example.com..5000=/path/to/ca.crt
```

Patch:

```bash
oc patch image.config.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"additionalTrustedCA":{"name":"registry-cas"}}}'
```

Watch:

```bash
oc get mcp
```

Test:

```bash
oc debug node/<node>
chroot /host
crictl pull registry.example.com:5000/team/app:v1
```

---

### Runbook 4: Registry Route Push Fails

**Symptoms**

```text
podman push default-route-openshift-image-registry... denied
```

**Steps**

Enable route:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"defaultRoute":true}}'
```

Get host:

```bash
HOST=$(oc get route default-route -n openshift-image-registry -o jsonpath='{.spec.host}')
echo $HOST
```

Login:

```bash
podman login -u $(oc whoami) -p $(oc whoami -t) $HOST
```

Grant push permission:

```bash
oc policy add-role-to-user system:image-builder $(oc whoami) -n <target-project>
```

Push:

```bash
podman tag localhost/app:latest $HOST/<target-project>/app:latest
podman push $HOST/<target-project>/app:latest
```

Verify:

```bash
oc get is -n <target-project>
oc describe is app -n <target-project>
```

---

### Runbook 5: Registry PVC Full

**Symptoms**

```text
no space left on device
blob upload invalid
push timeout
```

**Steps**

```bash
oc get pvc -n openshift-image-registry
oc exec -n openshift-image-registry deploy/image-registry -- df -h
```

Dry-run prune:

```bash
oc adm prune images
```

Confirm after approval:

```bash
oc adm prune images --confirm
```

Expand PVC if supported:

```bash
oc patch pvc <pvc-name> -n openshift-image-registry \
  -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'
```

Watch:

```bash
oc get pvc -n openshift-image-registry
oc get pods -n openshift-image-registry
```

### Runbook 6: Disconnected CatalogSource ImagePullBackOff

**Symptoms**

```bash
oc get pods -n openshift-marketplace
```

```text
redhat-operators-xxxxx ImagePullBackOff
```

**Steps**

```bash
oc describe pod <catalog-pod> -n openshift-marketplace
oc get catalogsource -n openshift-marketplace -o yaml
oc get imagedigestmirrorset,imagetagmirrorset,imagecontentsourcepolicy
```

Check mirror pull from node:

```bash
oc debug node/<node>
chroot /host
crictl pull mirror.registry.example.com:8443/olm/index@sha256:<digest>
```

If unauthorized:

```bash
oc extract secret/pull-secret -n openshift-config --to=/tmp/pullsecret --confirm
cat /tmp/pullsecret/.dockerconfigjson | jq '.auths | keys'
```

If x509, configure CA. If manifest unknown, mirror content is incomplete.

## 23. Interview / Real-World Scenario Questions

### Q1. `image-registry` ClusterOperator is degraded. What do you check first?

Answer:

1. `oc describe co image-registry`
2. `oc get configs.imageregistry.operator.openshift.io/cluster -o yaml`
3. `oc get pods,pvc,events -n openshift-image-registry`
4. operator logs
5. registry pod logs
6. storage backend/PVC/bucket

The most common causes are `managementState: Removed`, missing storage, PVC pending, registry pod not ready, or backend storage errors.

---

### Q2. Why is the internal registry removed after installation?

On some platforms, especially where default shareable object storage is not automatically configured, OpenShift can complete installation with the registry in `Removed` state. You must configure registry storage and set `managementState: Managed`.

---

### Q3. A pod fails with `x509: certificate signed by unknown authority`. What is the fix?

Add the registry CA to a ConfigMap in `openshift-config`, then reference it from `image.config.openshift.io/cluster` using `spec.additionalTrustedCA`. Watch MCP rollout and test from a node with `crictl pull`.

---

### Q4. A pod in `prod` pulls an internal image from namespace `dev` and gets unauthorized. What is the fix?

Grant the `prod` service account permission to pull images from `dev`:

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:prod:default \
  -n dev
```

The role is added in the image source namespace.

---

### Q5. Build fails while pushing output to internal registry. What do you check?

1. Registry operator health.
2. Registry pod and storage.
3. Build logs.
4. `builder` service account permissions.
5. Output ImageStream exists.
6. Internal registry service DNS/connectivity.

---

### Q6. How do you expose the internal registry externally?

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster \
  --type merge \
  -p '{"spec":{"defaultRoute":true}}'
```

Then get the route and login:

```bash
HOST=$(oc get route default-route -n openshift-image-registry -o jsonpath='{.spec.host}')
podman login -u $(oc whoami) -p $(oc whoami -t) $HOST
```

---

### Q7. Why does image pull work on one worker but fail on another?

Possible causes:

- MCP rollout incomplete
- node-specific DNS/network issue
- stale CA trust
- node disk pressure
- CRI-O problem
- proxy/noProxy issue
- different firewall path

Debug with:

```bash
oc debug node/<node>
chroot /host
crictl pull <image>
journalctl -u crio -n 200
```

---

### Q8. What is the difference between global pull secret and namespace pull secret?

Global pull secret applies cluster-wide and is stored in `openshift-config/pull-secret`. Namespace pull secrets are created in a project and attached to a service account. For application-specific private registries, namespace/service-account pull secrets are usually safer than modifying the global secret.

---

### Q9. Why can an ImageStream import fail even when a pod can pull the image?

Because ImageStream import uses OpenShift image import mechanisms and may require:

- correct pull secret linkage
- trusted CA
- correct registry policy
- accessible external registry metadata
- valid tag/digest

Pod pull and image import are related but not always identical paths.

---

### Q10. In disconnected OpenShift, operator catalog pod is `ImagePullBackOff`. What do you check?

1. CatalogSource image reference.
2. Mirror registry contains index image.
3. Mirror registry credentials in global pull secret or CatalogSource secret.
4. Mirror registry CA trust.
5. ImageDigestMirrorSet/ImageTagMirrorSet/ImageContentSourcePolicy.
6. Node `crictl pull` from mirror.

## 24. Best Practices

### 24.1 Production Registry Design

- Prefer object storage for scalable production registries.
- Avoid single fragile NFS storage for large production clusters unless intentionally designed.
- Monitor registry storage capacity and latency.
- Keep registry replicas aligned with storage backend capabilities.
- Test push/pull during change windows.

### 24.2 Pull Secret Hygiene

- Do not overwrite global pull secret blindly.
- Always merge JSON credentials.
- Keep backup before update.
- Prefer namespace pull secrets for app-specific private registries.
- Rotate credentials and document ownership.

### 24.3 TLS and CA Management

- Use valid TLS certificates for registries.
- Avoid insecure registries in production.
- Use `additionalTrustedCA` for internal/private CA.
- Validate SAN, expiry, and chain.
- Monitor certificate expiry.

### 24.4 Registry Policy

- Use `allowedRegistries` carefully.
- Always include required Red Hat, mirror, internal, and app registries.
- Understand that registry policy changes can trigger node/MCP updates.
- Test on non-production before enforcing allowlists.

### 24.5 Disconnected Environments

- Mirror by digest where required.
- Validate mirror completeness.
- Include release images, operator catalogs, operand images, and app images.
- Keep mirror registry HA and backed up.
- Add mirror registry to pull secret and trusted CA.
- Keep proxy/noProxy correct.

### 24.6 Troubleshooting Discipline

Always capture:

```bash
oc get co
oc describe co image-registry
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
oc get all,pvc,events -n openshift-image-registry
oc describe pod <failing-pod> -n <namespace>
oc logs deploy/image-registry -n openshift-image-registry
oc logs deploy/cluster-image-registry-operator -n openshift-image-registry
oc get mcp
```

For support:

```bash
oc adm must-gather
```

## Final Senior Admin Summary

When troubleshooting OpenShift image registry issues, do not start by guessing. Classify the issue:

```text
Is the internal registry unhealthy?
Is the pod unable to pull?
Is the build unable to push?
Is the image stream unable to import?
Is the node unable to reach/trust/authenticate to a registry?
Is disconnected mirroring incomplete?
```

Then follow the layers:

```text
ClusterOperator → Registry config → Registry pod → Storage → Service/Route
→ Image policy → Pull secret → CA trust → Node runtime → Network → Registry backend
```

The best OpenShift administrators are not the ones who remember the most commands. They are the ones who can read the event message, map it to the correct layer, and prove the failure with the smallest accurate test.
