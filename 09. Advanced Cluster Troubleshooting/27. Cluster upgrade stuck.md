## 1. What “Cluster upgrade stuck” means

In OpenShift 4, a cluster upgrade is not a simple package update. It is an orchestrated platform lifecycle operation. The **Cluster Version Operator (CVO)** applies a release payload, updates cluster operators, and waits until all required operators report healthy state.

A cluster upgrade is considered **stuck** when one or more of the following conditions remain unchanged for a long time:

```bash
oc get clusterversion
```

Example:

```text
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE   STATUS
version   4.14.34   True        True          3h20m   Working towards 4.15.20: 731 of 850 done
```

Or:

```text
version   4.14.34   True        True          6h10m   Unable to apply 4.15.20: the cluster operator machine-config is degraded
```

Common symptoms:

- `ClusterVersion` shows `Progressing=True` for hours.
- `oc adm upgrade status` shows one operator or node stuck.
- One or more `ClusterOperator` resources show `Available=False`, `Degraded=True`, or `Progressing=True` for too long.
- `machine-config` operator is degraded.
- One or more `MachineConfigPool` resources show `UPDATED=False`, `UPDATING=True`, or `DEGRADED=True`.
- Worker or master nodes are stuck in `SchedulingDisabled`, `NotReady`, or old version.
- CVO says it cannot retrieve update graph, release image, or update payload.
- Upgrade is blocked before starting because cluster is not upgradeable.

A stuck upgrade does **not always mean the cluster is down**. In many cases, the cluster continues serving applications, but the platform is in a partially-upgraded state. That partial state must be treated seriously because operators, operands, node OS, kubelet, CRI-O, and API components might be on different versions.

## 2. OpenShift upgrade architecture

### 2.1 Main components involved

| Component | Role during upgrade |
|---|---|
| `ClusterVersion` | Stores desired version, current history, available updates, and upgrade conditions. |
| Cluster Version Operator `CVO` | Drives the cluster update by reconciling manifests from the release payload. |
| OpenShift Update Service `OSUS` | Provides update graph and recommended update paths. |
| Cluster Operators `CO` | Own platform components such as API server, ingress, DNS, monitoring, authentication, network, machine-config, image-registry, etc. |
| Machine Config Operator `MCO` | Updates RHCOS, kubelet, CRI-O, kernel arguments, systemd units, and node-level config. |
| Machine Config Pool `MCP` | Groups nodes and controls node rollout for master, worker, infra, or custom pools. |
| Operator Lifecycle Manager `OLM` | Manages optional installed operators from OperatorHub. Some operator compatibility issues can block upgrades. |
| Nodes | Must drain, apply config, reboot, and return Ready for node-level upgrade completion. |

### 2.2 High-level upgrade flow

The experienced admin mental model:

```text
Admin requests update
        |
        v
CVO sets desiredUpdate
        |
        v
CVO pulls and validates release payload image
        |
        v
CVO applies manifests from payload
        |
        v
Cluster Operators update themselves
        |
        v
Operators update operands
        |
        v
MCO rolls out node OS/config changes
        |
        v
Nodes drain -> apply -> reboot -> return Ready
        |
        v
All ClusterOperators report healthy
        |
        v
ClusterVersion reports target version complete
```

### 2.3 Why upgrades get stuck

Most stuck upgrades are not CVO bugs. CVO is usually the messenger. It waits because one lower-level component cannot satisfy the desired state.

Typical root causes:

- Bad cluster health before upgrade.
- Degraded ClusterOperator before or during upgrade.
- MCP paused.
- MachineConfig drift.
- Node cannot drain due to PDB, local storage, finalizer, or unhealthy workload.
- Node cannot reboot or return Ready.
- Release image pull failure.
- Disconnected mirror registry missing content.
- Incompatible OLM operator.
- API deprecation/admin acknowledgment missing.
- etcd or API server instability.
- Certificate, DNS, ingress, image registry, or network operator issue.

## 3. How to read upgrade status like an experienced admin

### 3.1 Start with ClusterVersion

```bash
oc get clusterversion version
oc describe clusterversion version
oc get clusterversion version -o yaml
```

Important fields:

```yaml
spec:
  desiredUpdate:
    version: 4.x.y
status:
  desired:
    version: 4.x.y
  history:
  - version: 4.x.y
    state: Partial|Completed
  conditions:
  - type: Available
  - type: Progressing
  - type: Failing
  - type: Upgradeable
```

Interpretation:

| Condition | Meaning |
|---|---|
| `Available=True` | Cluster version operator sees the cluster as available. |
| `Progressing=True` | Upgrade or reconciliation is still in progress. |
| `Failing=True` | CVO encountered a failure applying or verifying the payload. |
| `Upgradeable=False` | Cluster is not safe for minor upgrade unless forced. Usually fix the reason, do not force. |

### 3.2 Check all ClusterOperators

```bash
oc get co
```

Good state:

```text
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED
kube-apiserver   4.15.20   True        False         False
machine-config   4.15.20   True        False         False
network          4.15.20   True        False         False
```

Bad state:

```text
machine-config   4.15.20   False       True          True
monitoring       4.14.34   False       True          True
```

The stuck operator is usually the first serious clue.

### 3.3 Use `oc adm upgrade status`

For supported OpenShift versions where available, use:

```bash
export OC_ENABLE_CMD_UPGRADE_STATUS=true
oc adm upgrade status
```

This gives a better breakdown of:

- Control plane status
- Worker node status
- Operator progress
- Which node/operator is blocking

Treat it as read-only diagnostic output.

### 3.4 Read status messages, not only booleans

Do not stop at:

```bash
oc get co
```

Always run:

```bash
oc describe co <operator-name>
```

Example:

```bash
oc describe co machine-config
```

Look for:

- `Message`
- `Reason`
- `LastTransitionTime`
- `RelatedObjects`

Very often the answer is directly inside the condition message.

## 4. First 15-minute triage checklist

During a production upgrade incident, do not randomly patch resources. First build the evidence.

### 4.1 Save current state

```bash
mkdir -p ~/upgrade-triage-$(date +%F-%H%M)
cd ~/upgrade-triage-$(date +%F-%H%M)

oc get clusterversion version -o yaml > clusterversion.yaml
oc get co -o wide > clusteroperators.txt
oc get co -o yaml > clusteroperators.yaml
oc get mcp -o wide > mcp.txt
oc get nodes -o wide > nodes.txt
oc get pods -A -o wide > pods-all.txt
oc get events -A --sort-by=.lastTimestamp > events-all.txt
```

### 4.2 Identify the blocking layer

Run:

```bash
oc get clusterversion version
oc get co
oc get mcp
oc get nodes
```

Ask:

1. Is CVO failing to fetch or apply payload?
2. Is a ClusterOperator degraded?
3. Is MCO/MCP degraded?
4. Is one node stuck draining, rebooting, or NotReady?
5. Is an OLM operator incompatible or pending?
6. Is this a disconnected registry/mirror issue?
7. Is this an admin acknowledgment / removed API block?

### 4.3 Gather logs early

```bash
oc logs -n openshift-cluster-version deploy/cluster-version-operator --since=2h > cvo.log
```

For a problematic operator:

```bash
oc get pods -n <operator-namespace> -o wide
oc logs -n <operator-namespace> <operator-pod> --since=2h
```

For MCO:

```bash
oc get pods -n openshift-machine-config-operator -o wide
oc logs -n openshift-machine-config-operator deploy/machine-config-operator --since=2h
oc logs -n openshift-machine-config-operator deploy/machine-config-controller --since=2h
```

## 5. Golden troubleshooting command set

### 5.1 Upgrade status

```bash
oc get clusterversion version
oc describe clusterversion version
oc get clusterversion version -o jsonpath='{.status.conditions}' | jq
oc get clusterversion version -o jsonpath='{.status.history}' | jq
```

### 5.2 Available updates and channel

```bash
oc adm upgrade
oc get clusterversion version -o jsonpath='{.spec.channel}{"\n"}'
oc get clusterversion version -o jsonpath='{.status.availableUpdates}' | jq
```

### 5.3 Include not-recommended updates

```bash
oc adm upgrade --include-not-recommended
```

Use this only to understand risks. Do not choose a not-recommended path without risk review and change approval.

### 5.4 ClusterOperator health

```bash
oc get co
oc get co -o custom-columns='NAME:.metadata.name,VERSION:.status.versions[?(@.name=="operator")].version,AVAILABLE:.status.conditions[?(@.type=="Available")].status,PROGRESSING:.status.conditions[?(@.type=="Progressing")].status,DEGRADED:.status.conditions[?(@.type=="Degraded")].status,MESSAGE:.status.conditions[?(@.type=="Degraded")].message'
```

### 5.5 Machine config

```bash
oc get mcp
oc describe mcp master
oc describe mcp worker
oc get mc
oc get nodes -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status,VERSION:.status.nodeInfo.kubeletVersion,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason'
```

### 5.6 Node drain investigation

```bash
NODE=<node-name>
oc get pods -A -o wide --field-selector spec.nodeName=${NODE}
oc get pdb -A
oc describe node ${NODE}
oc adm drain ${NODE} --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

### 5.7 Operator pods and logs

```bash
oc get pods -n openshift-cluster-version -o wide
oc logs -n openshift-cluster-version deploy/cluster-version-operator --since=2h

oc get pods -n openshift-machine-config-operator -o wide
oc logs -n openshift-machine-config-operator deploy/machine-config-operator --since=2h
oc logs -n openshift-machine-config-operator deploy/machine-config-controller --since=2h
```

### 5.8 Events

```bash
oc get events -A --sort-by=.lastTimestamp | tail -200
```

### 5.9 Must-gather

```bash
oc adm must-gather
```

Optional targeted gather examples:

```bash
oc adm must-gather -- /usr/bin/gather_audit_logs
oc adm must-gather -- /usr/bin/gather_network_logs
```

Availability of targeted gather scripts depends on OpenShift version and image content.

## 6. Decision tree: where is the upgrade stuck?

```text
START
 |
 |-- oc get clusterversion shows Failing=True?
 |       |
 |       |-- Yes -> Check CVO logs and describe clusterversion
 |       |-- No  -> Continue
 |
 |-- oc get co shows Degraded=True or Available=False?
 |       |
 |       |-- Yes -> Troubleshoot that specific ClusterOperator
 |       |-- No  -> Continue
 |
 |-- oc get mcp shows DEGRADED=True or UPDATING=True for long time?
 |       |
 |       |-- Yes -> Troubleshoot MCO/MCP/node drain/config drift
 |       |-- No  -> Continue
 |
 |-- nodes show NotReady/SchedulingDisabled/old kubelet version?
 |       |
 |       |-- Yes -> Troubleshoot node, MCD, drain, reboot, kubelet, CRI-O
 |       |-- No  -> Continue
 |
 |-- OLM operators pending/incompatible?
 |       |
 |       |-- Yes -> Fix subscriptions/installplans/CSV/operator compatibility
 |       |-- No  -> Continue
 |
 |-- disconnected cluster or mirror registry?
 |       |
 |       |-- Yes -> Validate release image mirror, ICSP/IDMS/ITMS, pull secret, registry CA
 |       |-- No  -> Continue
 |
 |-- admin ack / Upgradeable=False?
 |       |
 |       |-- Yes -> Resolve API removals and acknowledge only after validation
 |       |-- No  -> Collect must-gather and escalate with evidence
```

## 7. Scenario 1: ClusterVersion stuck or CVO failing

### 7.1 Symptoms

```bash
oc get clusterversion version
```

Examples:

```text
Unable to apply 4.15.20: an unknown error has occurred
```

```text
The update cannot be verified: unable to retrieve release image
```

```text
Cluster operator <name> has not yet successfully rolled out
```

```text
Cluster version is 4.14.34, but desired version is 4.15.20
```

### 7.2 Diagnostic commands

```bash
oc describe clusterversion version
oc get clusterversion version -o yaml
oc logs -n openshift-cluster-version deploy/cluster-version-operator --since=4h
oc get pods -n openshift-cluster-version -o wide
```

Check update history:

```bash
oc get clusterversion version -o jsonpath='{range .status.history[*]}{.version}{"\t"}{.state}{"\t"}{.startedTime}{"\t"}{.completionTime}{"\n"}{end}'
```

Check desired update:

```bash
oc get clusterversion version -o jsonpath='{.spec.desiredUpdate}{"\n"}'
```

### 7.3 Common CVO messages and interpretation

| Message pattern | Likely meaning |
|---|---|
| `cluster operator X has not yet successfully rolled out` | CVO is waiting for that ClusterOperator. Troubleshoot operator X. |
| `Unable to retrieve available updates` | OSUS/upstream/network/proxy/certificate issue. |
| `Release image ... could not be pulled` | Pull secret, registry, mirror, proxy, or CA trust issue. |
| `Upgradeable=False` | Minor upgrade blocked by a component or admin acknowledgment requirement. |
| `Working towards ... N of M done` | CVO is applying payload manifests; check if number is changing. |
| `Precondition ... failed` | Cluster state violates upgrade precondition. |

### 7.4 Corrective actions

Do not try to “fix CVO” first unless CVO itself is unhealthy. Usually:

1. Read `oc describe clusterversion version`.
2. Identify the specific blocking operator.
3. Troubleshoot that operator.
4. Re-check CVO after operator recovers.

If CVO pod itself is not running:

```bash
oc get pods -n openshift-cluster-version -o wide
oc describe pod -n openshift-cluster-version <cvo-pod>
oc logs -n openshift-cluster-version <cvo-pod> --previous
```

Check image pull, scheduling, node, SCC, and API availability issues.

## 8. Scenario 2: ClusterOperator not Available / Degraded / Progressing

### 8.1 Symptoms

```bash
oc get co
```

Example:

```text
NAME              VERSION   AVAILABLE   PROGRESSING   DEGRADED
machine-config    4.15.20   False       True          True
monitoring        4.15.20   False       True          True
network           4.15.20   True        True          False
```

### 8.2 Experienced interpretation

Do not assume every `Progressing=True` is bad. During upgrade, `Progressing=True` is expected. It becomes a problem when:

- It remains unchanged for a long time.
- It is combined with `Available=False`.
- It is combined with `Degraded=True`.
- It blocks CVO completion.
- The message points to failing operands or rollout failures.

### 8.3 Diagnostic commands

```bash
CO=<clusteroperator-name>
oc describe co ${CO}
oc get co ${CO} -o yaml
```

Find related objects:

```bash
oc get co ${CO} -o jsonpath='{.status.relatedObjects}' | jq
```

Then inspect related namespace/pods.

Examples:

```bash
oc get pods -n openshift-monitoring -o wide
oc get pods -n openshift-ingress-operator -o wide
oc get pods -n openshift-network-operator -o wide
oc get pods -n openshift-authentication -o wide
oc get pods -n openshift-dns -o wide
```

### 8.4 General operator troubleshooting pattern

For any degraded operator:

```bash
NS=<operator-namespace>
oc get deploy,ds,sts,pods -n ${NS} -o wide
oc get events -n ${NS} --sort-by=.lastTimestamp
oc describe pod -n ${NS} <pod>
oc logs -n ${NS} <pod> --since=2h
oc logs -n ${NS} <pod> --previous
```

Check operands too. For example, if `ingress` is degraded, do not only check `openshift-ingress-operator`; also check router pods in `openshift-ingress`.

### 8.5 Common operator-specific blockers

| Operator | Common upgrade blockers |
|---|---|
| `machine-config` | MCP degraded, paused MCP, node drain failure, config drift, node reboot failure. |
| `network` | OVN-Kubernetes rollout failure, CNI daemonset unavailable, node network issue, MTU mismatch. |
| `dns` | DNS daemonset unavailable, CoreDNS pods failing, node scheduling issue. |
| `ingress` | Router deployment unavailable, certificate issue, LB issue, canary route failing. |
| `authentication` | OAuth server unavailable, route/cert/secret issue, API server dependency. |
| `monitoring` | Prometheus/Thanos/Alertmanager pods pending, PVC issue, resource pressure, PDB. |
| `image-registry` | Storage/PVC/S3 issue, registry route/cert issue, pod not ready. |
| `kube-apiserver` | Static pod rollout issue, revision stuck, etcd/API instability. |
| `etcd` | Member unhealthy, disk latency, quorum risk, cert issue. |
| `operator-lifecycle-manager` | package server/APIService/CSV/InstallPlan issue. |

## 9. Scenario 3: Machine Config Operator / MCP stuck

MCO/MCP issues are among the most common reasons for stuck OpenShift upgrades.

### 9.1 Why MCO matters

MCO owns node-level changes. During cluster upgrades it may update:

- RHCOS content
- kubelet
- CRI-O
- systemd units
- kernel arguments
- SSH keys
- node-level files from MachineConfig
- container runtime configuration

Typical MCO sequence per node:

```text
cordon -> drain -> apply config -> reboot -> uncordon
```

If any step fails, upgrade can stop.

### 9.2 Symptoms

```bash
oc get co machine-config
oc get mcp
```

Example:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT   UPDATEDMACHINECOUNT   DEGRADEDMACHINECOUNT
master   rendered-master-xxxx                              True      False      False      3              3                   3                     0
worker   rendered-worker-yyyy                              False     True       True       5              4                   3                     1
```

### 9.3 Diagnostic commands

```bash
oc describe co machine-config
oc get mcp -o wide
oc describe mcp worker
oc describe mcp master
```

Node annotations:

```bash
oc get nodes -o custom-columns='NAME:.metadata.name,ROLE:.metadata.labels.node-role\.kubernetes\.io/worker,VERSION:.status.nodeInfo.kubeletVersion,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason'
```

MCO pods:

```bash
oc get pods -n openshift-machine-config-operator -o wide
```

MCO logs:

```bash
oc logs -n openshift-machine-config-operator deploy/machine-config-operator --since=4h
oc logs -n openshift-machine-config-operator deploy/machine-config-controller --since=4h
oc logs -n openshift-machine-config-operator deploy/machine-config-server --since=4h
```

Machine Config Daemon logs for the affected node:

```bash
NODE=<node-name>
MCD_POD=$(oc get pod -n openshift-machine-config-operator -o wide | awk -v node="$NODE" '$0 ~ node && $1 ~ /machine-config-daemon/ {print $1; exit}')
echo ${MCD_POD}
oc logs -n openshift-machine-config-operator ${MCD_POD} -c machine-config-daemon --since=4h
```

### 9.4 Common MCP stuck causes

| Cause | Evidence | Fix direction |
|---|---|---|
| Node drain blocked | MCD logs show drain timeout / cannot evict pod | Fix PDB/workload or manually resolve blocking pod. |
| MCP paused | `spec.paused: true` | Unpause after confirming safe. |
| Config drift | MCP message shows content mismatch/file permission mismatch | Restore file or use force file cautiously. |
| Node NotReady | `oc get nodes` shows NotReady | Fix kubelet/CRI-O/network/disk/cert issue. |
| Node cannot reboot | Node remains old config/version | Check console/iLO/cloud, kubelet, MCD logs. |
| Bad custom MachineConfig | New rendered config causes failures | Fix or remove bad MachineConfig, let MCO render again. |
| Disk pressure | Node condition DiskPressure | Free disk, fix image garbage collection, node filesystem. |
| Invalid kernel args | Node fails boot or kubelet starts incorrectly | Console access may be required. |

## 10. Scenario 4: Node drain blocked by PDB or unhealthy workload

### 10.1 Symptoms

`machine-config` degraded message may include:

```text
failed to drain node: <node> after 1 hour
cannot evict pod as it would violate the pod's disruption budget
```

MCD logs may show:

```text
error when evicting pods ... Cannot evict pod as it would violate the pod's disruption budget
```

### 10.2 Find pods on affected node

```bash
NODE=<node-name>
oc get pods -A -o wide --field-selector spec.nodeName=${NODE}
```

### 10.3 Check PDBs

```bash
oc get pdb -A
oc describe pdb -n <namespace> <pdb-name>
```

Look at:

- `Allowed disruptions`
- `Current healthy`
- `Desired healthy`
- `Disruptions allowed`

If `ALLOWED DISRUPTIONS` is `0`, voluntary eviction can be blocked.

### 10.4 Dry-run drain

```bash
oc adm drain ${NODE} --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

If it reports PDB violation, identify the workload.

### 10.5 Fix options

#### Option A: Make workload healthy

If the workload has multiple replicas but only one is healthy, fix the unhealthy replica first.

```bash
oc get deploy,sts,pods -n <namespace> -o wide
oc describe pod -n <namespace> <pod>
oc logs -n <namespace> <pod> --previous
```

#### Option B: Temporarily scale up replicas

```bash
oc scale deploy/<deployment> -n <namespace> --replicas=<higher-number>
```

Wait until additional pods are Ready:

```bash
oc get pods -n <namespace> -w
```

#### Option C: Temporarily adjust PDB

Only with change approval:

```bash
oc patch pdb <pdb-name> -n <namespace> --type=merge -p '{"spec":{"minAvailable":0}}'
```

Or adjust `maxUnavailable` if that is how the PDB is defined.

After upgrade progresses, restore original PDB.

#### Option D: Delete a stuck pod manually

Only when you understand impact:

```bash
oc delete pod -n <namespace> <pod-name>
```

Avoid `--force --grace-period=0` unless the pod is truly orphaned or node is dead, because force deletion can cause split-brain risk for stateful workloads.

### 10.6 Important note for stateful workloads

For StatefulSets, storage-backed databases, brokers, quorum systems, and single-replica components, never “just delete pods” to unblock a drain. First check:

- Application quorum
- PVC attach/detach status
- Data replication state
- PDB intention
- Anti-affinity / topology constraints
- Availability SLA

## 11. Scenario 5: MCP paused

### 11.1 Symptoms

```bash
oc get mcp -o yaml | grep -A5 paused
```

Or:

```bash
oc get mcp worker -o jsonpath='{.spec.paused}{"\n"}'
```

If `true`, MCO will not continue applying new config to that pool.

### 11.2 Why admins pause MCP

Common valid reasons:

- Canary upgrade strategy.
- Controlled reboot windows.
- Troubleshooting node config.
- Avoid worker disruption during business hours.

Common problem:

- Admin forgot to unpause after maintenance.

### 11.3 Fix

First verify why it was paused:

```bash
oc get mcp worker -o yaml
oc get mc --sort-by=.metadata.creationTimestamp
```

Then unpause:

```bash
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'
```

Watch:

```bash
watch -n 10 'oc get mcp; echo; oc get nodes'
```

### 11.4 Do not unpause blindly

If a bad MachineConfig is waiting, unpausing can reboot or break many nodes. Review recent custom MachineConfigs first:

```bash
oc get mc --sort-by=.metadata.creationTimestamp
oc describe mc <machineconfig-name>
```

## 12. Scenario 6: MachineConfig drift or rendered config mismatch

### 12.1 What config drift means

Configuration drift means node disk state does not match the MachineConfig that OpenShift believes is applied. Example causes:

- Someone manually edited a file managed by MachineConfig.
- File permission changed.
- Systemd unit changed outside MCO.
- Kernel arguments or CRI-O config changed manually.
- Node was repaired manually but annotations still show old state.

### 12.2 Symptoms

```bash
oc describe mcp worker
```

Example message:

```text
Node <node> is reporting: "content mismatch for file /etc/..."
```

Node annotation:

```bash
oc describe node <node> | grep -i machineconfiguration -A10
```

### 12.3 Diagnose current and desired config

```bash
NODE=<node-name>
oc get node ${NODE} -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}'
oc get node ${NODE} -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}'
oc get node ${NODE} -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
oc get node ${NODE} -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/reason}{"\n"}'
```

### 12.4 Inspect rendered MachineConfig

```bash
MC=<rendered-machineconfig-name>
oc get mc ${MC} -o yaml
```

Look for files:

```bash
oc get mc ${MC} -o json | jq '.spec.config.storage.files[]? | {path, mode, contents}'
```

### 12.5 Fix direction 1: restore file content/permissions

Debug node:

```bash
oc debug node/${NODE}
chroot /host
```

Check file:

```bash
ls -l /path/from/error
stat /path/from/error
cat /path/from/error
```

Restore expected content/permissions according to MachineConfig.

Exit debug shell and wait for MCD to retry.

### 12.6 Fix direction 2: force MCD to re-apply current MachineConfig

Use cautiously. This can reboot the node.

```bash
oc debug node/${NODE} -- chroot /host touch /run/machine-config-daemon-force
```

Then watch:

```bash
watch -n 10 "oc get node ${NODE}; oc get mcp"
```

### 12.7 Fix direction 3: remove or correct bad custom MachineConfig

If a recently-created custom MachineConfig is wrong:

```bash
oc get mc --sort-by=.metadata.creationTimestamp
oc describe mc <bad-mc>
```

Backup first:

```bash
oc get mc <bad-mc> -o yaml > bad-mc-backup.yaml
```

Then correct or delete:

```bash
oc delete mc <bad-mc>
```

Wait for new rendered config:

```bash
watch -n 10 'oc get mcp; oc get mc --sort-by=.metadata.creationTimestamp | tail'
```

### 12.8 Senior admin warning

Do not randomly patch node annotations such as `currentConfig` and `desiredConfig` unless you have Red Hat support guidance or very strong recovery knowledge. Incorrect annotation manipulation can make the node state worse.

## 13. Scenario 7: Node NotReady during upgrade

### 13.1 Symptoms

```bash
oc get nodes
```

Example:

```text
worker-2   NotReady,SchedulingDisabled   worker   211d   v1.28.x
```

MCP may show:

```text
READYMACHINECOUNT lower than MACHINECOUNT
```

### 13.2 Diagnostic commands

```bash
NODE=<node-name>
oc describe node ${NODE}
oc get pods -A -o wide --field-selector spec.nodeName=${NODE}
```

Check node conditions:

```bash
oc get node ${NODE} -o json | jq '.status.conditions[] | {type,status,reason,message,lastTransitionTime}'
```

Debug node if accessible:

```bash
oc debug node/${NODE}
chroot /host
systemctl status kubelet
systemctl status crio
journalctl -u kubelet -b --no-pager | tail -200
journalctl -u crio -b --no-pager | tail -200
journalctl -u machine-config-daemon -b --no-pager | tail -200
```

### 13.3 Common causes

| Symptom | Likely cause |
|---|---|
| `KubeletNotReady` | kubelet cannot start, CNI not ready, cert issue, CRI-O issue. |
| `NetworkPluginNotReady` | OVN/CNI problem. |
| `DiskPressure=True` | Disk full, image filesystem full, logs too large. |
| Node unreachable | Network, host down, reboot stuck, cloud/bare-metal issue. |
| CRI-O failing | Runtime config issue, storage issue, invalid MachineConfig. |
| Node old version | MCD not applying config, reboot failure, drain failure. |

### 13.4 Fix examples

Disk pressure:

```bash
oc debug node/${NODE}
chroot /host
df -h
journalctl --disk-usage
crictl images
crictl ps -a
```

Be careful deleting images/containers manually. Prefer normal kubelet garbage collection where possible.

Kubelet failure:

```bash
journalctl -u kubelet -b --no-pager | tail -200
systemctl restart kubelet
```

CRI-O failure:

```bash
journalctl -u crio -b --no-pager | tail -200
systemctl restart crio
systemctl restart kubelet
```

If node is physically or cloud unreachable, use console/cloud provider/iLO/iDRAC access.

## 14. Scenario 8: Incompatible or pending OLM Operators

OpenShift cluster upgrades can be blocked or made risky by installed OLM-managed operators, especially when:

- Subscription uses manual approval and InstallPlan is pending.
- Operator channel is old.
- Operator does not support target OpenShift version.
- CSV is stuck in `Pending`, `Failed`, or `Replacing`.
- Catalog source is unavailable.
- Bundle image cannot be pulled.

### 14.1 Check OLM state

```bash
oc get subscriptions -A
oc get installplans -A
oc get csv -A
oc get catalogsources -n openshift-marketplace
oc get pods -n openshift-marketplace
oc get pods -n openshift-operator-lifecycle-manager
```

### 14.2 Find pending manual approvals

```bash
oc get installplans -A -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,APPROVED:.spec.approved,PHASE:.status.phase'
```

Approve if validated:

```bash
oc patch installplan <installplan-name> -n <namespace> --type=merge -p '{"spec":{"approved":true}}'
```

### 14.3 Check failed CSVs

```bash
oc get csv -A | egrep -v 'Succeeded|PHASE'
oc describe csv -n <namespace> <csv-name>
```

### 14.4 Check subscription channel

```bash
oc get sub -n <namespace> <subscription-name> -o yaml
```

Look at:

```yaml
spec:
  channel:
  installPlanApproval:
  source:
  sourceNamespace:
status:
  conditions:
  currentCSV:
  installedCSV:
```

### 14.5 Corrective actions

- Move subscription to a supported newer channel.
- Approve pending InstallPlan after reviewing resources.
- Fix catalog source image pull issue.
- Mirror operator catalog content for disconnected clusters.
- Refresh a failing subscription only after backing up objects.
- Confirm operator vendor support for target OpenShift version.

Example backup:

```bash
oc get sub,csv,installplan -n <namespace> -o yaml > olm-backup-<namespace>.yaml
```

### 14.6 Important warning

Do not delete CSVs or subscriptions blindly. Some operators own CRDs and operands that run production services. Improper deletion can orphan operands or remove controllers needed for storage, logging, service mesh, virtualization, or security tools.

## 15. Scenario 9: Disconnected / restricted network upgrade stuck

Disconnected upgrades fail differently from connected upgrades. The cluster cannot pull from Red Hat registries or public update services directly, so mirror configuration must be perfect.

### 15.1 Symptoms

- CVO cannot retrieve available updates.
- CVO cannot pull release image.
- Nodes cannot pull MCO/RHCOS update payload.
- Catalog sources fail image pulls.
- `ImagePullBackOff` in platform namespaces.
- Upgrade target not visible.
- `x509: certificate signed by unknown authority` for mirror registry.
- `manifest unknown` or `blob unknown` from mirror registry.

### 15.2 Check cluster version upstream/channel

```bash
oc get clusterversion version -o yaml | egrep -i 'channel|upstream|desiredUpdate|availableUpdates' -A5
oc adm upgrade
```

### 15.3 Check image mirror config

Depending on OpenShift version and configuration, check:

```bash
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get image.config.openshift.io/cluster -o yaml
```

### 15.4 Check pull secret

```bash
oc get secret pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq
```

Do not print this in shared channels because it contains credentials.

### 15.5 Check registry CA trust

```bash
oc get cm -n openshift-config
oc get image.config.openshift.io/cluster -o yaml
```

Look for:

```yaml
spec:
  additionalTrustedCA:
    name: <configmap-name>
```

### 15.6 Test release image from a trusted host

```bash
oc adm release info <mirror-registry>/<repo>@sha256:<digest>
```

Or:

```bash
oc image info <mirror-registry>/<repo>@sha256:<digest>
```

### 15.7 Check if payload images exist in mirror

Common problem: admin mirrored release image but not all required images, or mirror was garbage-collected.

Validate mirror process output and confirm digest exists.

### 15.8 Corrective actions

- Re-mirror the exact target release payload.
- Fix `ImageDigestMirrorSet` / `ImageContentSourcePolicy` mappings.
- Fix mirror registry certificate and add trusted CA.
- Fix pull secret for mirror registry.
- Keep mirror registry available throughout the upgrade.
- In disconnected clusters, ensure operator catalogs are mirrored separately if OLM-managed operators also need upgrades.

## 16. Scenario 10: Upgrade blocked by admin acknowledgment / removed APIs

OpenShift minor upgrades can require administrator acknowledgment when Kubernetes APIs are removed in the target version. This protects the cluster from upgrading while workloads or clients still use removed API versions.

### 16.1 Symptoms

```bash
oc adm upgrade
```

May show no minor update or message about admin acknowledgment.

`ClusterVersion` may show:

```text
Upgradeable=False
```

### 16.2 Check Upgradeable condition

```bash
oc get clusterversion version -o json | jq '.status.conditions[] | select(.type=="Upgradeable")'
```

Or:

```bash
oc describe clusterversion version
```

### 16.3 Check admin acks ConfigMap

```bash
oc get cm admin-acks -n openshift-config -o yaml
```

A key can look like:

```yaml
data:
  ack-<version-specific-api-removal-key>: "true"
```

The exact key depends on the source and target OpenShift version. Always check the official documentation for that version.

### 16.4 Correct process

1. Identify APIs removed in target version.
2. Find workloads/manifests/clients using removed APIs.
3. Migrate to supported API versions.
4. Validate applications.
5. Set admin acknowledgment.
6. Start upgrade.

### 16.5 Useful API discovery commands

```bash
oc get apirequestcounts
oc get apirequestcounts -o wide
oc describe apirequestcount <resource>.<group>
```

Search manifests in GitOps repositories too. OpenShift cannot find every external client or idle workload.

### 16.6 Warning

Do not set admin acknowledgment just to “unblock upgrade” without API validation. The cluster may upgrade successfully but applications or automation using removed APIs can break after upgrade.

## 18. Scenario 12: etcd or control plane instability

If etcd or API server is unstable, stop treating this as a normal stuck upgrade. This is a control plane incident.

### 18.1 Symptoms

```bash
oc get co etcd kube-apiserver openshift-apiserver
```

Possible signs:

- `etcd Degraded=True`
- API requests timeout.
- Static pods stuck in old revisions.
- Control plane nodes NotReady.
- ClusterVersion cannot apply manifests due to API errors.

### 18.2 Diagnostics

```bash
oc describe co etcd
oc describe co kube-apiserver
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-kube-controller-manager -o wide
oc get pods -n openshift-kube-scheduler -o wide
```

Check etcd operator logs:

```bash
oc logs -n openshift-etcd-operator deploy/etcd-operator --since=2h
```

Check etcd pods:

```bash
oc logs -n openshift-etcd <etcd-pod> -c etcd --since=2h
```

### 18.3 etcd health check

Use supported methods and be careful with etcd credentials.

```bash
oc rsh -n openshift-etcd <etcd-pod>
```

Then use `etcdctl` only if you know the cert paths and support policy for your version.

### 18.4 Fix direction

- Do not reboot multiple masters together.
- Maintain etcd quorum.
- Fix disk latency / disk full issues.
- Fix unhealthy master node first.
- Collect must-gather quickly.
- Escalate to Red Hat support if etcd quorum or static pod revision is involved.

## 20. Scenario 14: Upgrade looks stuck but is actually slow

Not every long upgrade is broken. Some clusters take longer due to:

- Large number of nodes.
- Large number of routes/endpoints.
- Heavy monitoring data / PVC attach-detach.
- Slow node reboot.
- Slow cloud provider API.
- Low `maxUnavailable` in MCP.
- Large custom pools.
- Many Operators and operands.
- Bare-metal firmware/BIOS boot delays.

### 20.1 How to confirm progress

Run the same commands every 10-15 minutes and compare:

```bash
oc get clusterversion version
oc get co
oc get mcp
oc get nodes
```

Check whether:

- `UPDATEDMACHINECOUNT` is increasing.
- Nodes are moving from old to new config.
- ClusterOperator versions are changing.
- CVO “N of M done” count is increasing.
- New node reboots are occurring one by one.

### 20.2 Watch MCP

```bash
watch -n 15 'oc get mcp; echo; oc get nodes -o wide'
```

### 20.3 Check maxUnavailable

```bash
oc get mcp worker -o yaml | grep -A5 maxUnavailable
```

Default behavior is conservative. Increasing `maxUnavailable` can speed rollout but increases disruption risk. Do not change it during an incident unless you understand workload capacity and availability impact.

## 21. Safe recovery principles

### 21.1 Fix the blocker, not the symptom

If CVO says:

```text
machine-config has not yet successfully rolled out
```

Do not patch CVO. Troubleshoot MCO/MCP.

If MCP says:

```text
failed to drain node
```

Do not delete MCP. Fix drain blocker.

If ingress says:

```text
canary route failed
```

Do not mark operator healthy manually. Fix route/router/DNS/LB.

### 21.2 One change at a time

During stuck upgrades, make one corrective action and observe. Multiple simultaneous changes destroy evidence and make rollback reasoning difficult.

### 21.3 Preserve evidence

Before deletion/patch:

```bash
oc get <resource> <name> -n <namespace> -o yaml > backup.yaml
```

### 21.4 Prefer supported reconciliation

OpenShift is operator-driven. Most fixes should allow the relevant operator to reconcile naturally.

### 21.5 Escalate early for control plane issues

If `etcd`, `kube-apiserver`, or multiple masters are unhealthy, collect data and escalate. Avoid improvising on control plane static pod resources.

## 22. What not to do during a stuck upgrade

Avoid these unless directed by Red Hat support or you fully understand consequences:

- Do not edit `ClusterVersion.status`.
- Do not delete ClusterOperators.
- Do not delete CVO deployment casually.
- Do not force reboot all masters.
- Do not reboot multiple etcd members together.
- Do not delete random MachineConfigs.
- Do not patch node `currentConfig` / `desiredConfig` randomly.
- Do not force delete stateful pods without understanding quorum/data impact.
- Do not set admin acknowledgment without removed API validation.
- Do not approve unknown InstallPlans blindly.
- Do not disable PDBs permanently to make upgrade pass.
- Do not increase MCP `maxUnavailable` during business hours without risk review.
- Do not run unsupported etcd recovery commands from old blog posts.

## 24. Production prevention checklist

### 24.1 Pre-upgrade health check

Run before upgrade:

```bash
oc get clusterversion version
oc get co
oc get mcp
oc get nodes
oc get pods -A | egrep -v 'Running|Completed'
oc get pdb -A
oc get csv -A | egrep -v 'Succeeded|PHASE'
oc get installplans -A
```

Do not start upgrade if:

- Any ClusterOperator is degraded.
- Any MCP is degraded or paused unexpectedly.
- Any node is NotReady.
- Critical namespaces have crashlooping platform pods.
- OLM has failed/pending operators.
- etcd shows degraded.
- Registry/mirror/pull secret is not validated.
- Admin acknowledgment requirement is unresolved.

### 24.2 Verify upgrade path

```bash
oc adm upgrade
oc adm upgrade --include-not-recommended
```

Use recommended update paths for production unless there is a documented exception.

### 24.3 Backup important resources

At minimum:

```bash
oc get clusterversion version -o yaml > pre-cv.yaml
oc get co -o yaml > pre-co.yaml
oc get mcp -o yaml > pre-mcp.yaml
oc get mc -o yaml > pre-mc.yaml
oc get nodes -o yaml > pre-nodes.yaml
oc get sub,installplan,csv -A -o yaml > pre-olm.yaml
```

Also ensure etcd backup/snapshot procedures follow your platform support policy.

### 24.4 Validate workloads and PDBs

```bash
oc get pdb -A
oc get deploy,sts -A
```

Look for risky patterns:

- Single replica with strict PDB.
- StatefulSet with `minAvailable: 100%`.
- Pods with local storage and no redundancy.
- Anti-affinity causing replacement pods to stay Pending.
- ResourceQuota blocking replacement pods.
- Namespace LimitRange causing new pods to fail.

### 24.5 Check cluster capacity

During upgrade, nodes drain one by one. Remaining nodes must have capacity.

```bash
oc adm top nodes
oc adm top pods -A --sort-by=cpu
oc adm top pods -A --sort-by=memory
```

Also check quota:

```bash
oc get quota -A
```

### 24.6 Disconnected pre-check

For disconnected clusters:

- Mirror release payload.
- Mirror operator catalogs.
- Validate pull secret.
- Validate mirror registry CA.
- Validate `ImageDigestMirrorSet` / `ImageContentSourcePolicy`.
- Run `oc adm release info` against mirrored payload.
- Keep mirror registry available for entire upgrade.

### 24.7 Change window planning

Prepare:

- Rollback/abort decision criteria.
- Red Hat support case procedure.
- Node console/cloud access.
- Application owners for PDB changes.
- Storage/network team contacts.
- Monitoring dashboard.
- Communication plan.

## 25. Real-world L3 troubleshooting workflow

This is the workflow I would follow as an L3 OpenShift admin during a live stuck upgrade.

### Step 1: Confirm stuck state

```bash
oc get clusterversion version
export OC_ENABLE_CMD_UPGRADE_STATUS=true
oc adm upgrade status
```

If status changes every few minutes, observe. If unchanged for a long time, continue.

### Step 2: Find blocking operator

```bash
oc get co
```

Pick the operator with bad condition:

```bash
oc describe co <operator>
```

### Step 3: If machine-config is involved

```bash
oc get mcp
oc describe mcp worker
oc describe mcp master
oc get nodes -o wide
```

Identify affected node:

```bash
oc get nodes -o custom-columns='NAME:.metadata.name,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state,REASON:.metadata.annotations.machineconfiguration\.openshift\.io/reason,CURRENT:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig'
```

### Step 4: Check MCD logs

```bash
NODE=<node>
MCD_POD=$(oc get pods -n openshift-machine-config-operator -o wide | awk -v node="$NODE" '$0 ~ node && $1 ~ /machine-config-daemon/ {print $1; exit}')
oc logs -n openshift-machine-config-operator ${MCD_POD} -c machine-config-daemon --since=4h
```

### Step 5: Classify issue

| Evidence | Classification |
|---|---|
| `cannot evict pod` | Drain/PDB issue |
| `content mismatch` | Config drift |
| `node not ready` | Node health issue |
| `paused: true` | MCP paused |
| `failed to pull` | Registry/image issue |
| `x509` | CA trust issue |
| `unauthorized` | Pull secret issue |
| `CSV failed` | OLM issue |
| `Upgradeable=False` | Precondition/admin ack/operator block |

### Step 6: Apply least risky fix

Examples:

- Scale workload up to satisfy PDB.
- Restore file permission drift.
- Unpause MCP after validating configs.
- Fix registry CA or pull secret.
- Approve validated InstallPlan.
- Fix degraded operator operand.

### Step 7: Watch recovery

```bash
watch -n 15 'oc get clusterversion version; echo; oc get co; echo; oc get mcp; echo; oc get nodes'
```

### Step 8: Post-fix validation

```bash
oc get clusterversion version
oc get co
oc get mcp
oc get nodes
oc adm upgrade
```

### Step 9: Document root cause

Record:

- Upgrade from/to version.
- Exact stuck time.
- Blocking operator.
- Condition message.
- Root cause.
- Fix applied.
- Time to recovery.
- Prevention action.

## 26. Interview / exam notes

### 26.1 One-line answer

A stuck OpenShift upgrade means the CVO is unable to complete reconciliation of the target release because one or more cluster operators, node pools, nodes, payload images, OLM operators, or upgrade preconditions are not healthy.

### 26.2 Best first commands

```bash
oc get clusterversion version
oc describe clusterversion version
oc get co
oc get mcp
oc get nodes
```

### 26.3 Most common real answer

In production, the most common blocker is often:

```text
machine-config operator degraded because a node cannot drain, reboot, or apply rendered config.
```

### 26.4 What to say about rollback

OpenShift upgrades are not normally handled by simple rollback. You should fix the failing component and allow operators to reconcile. For failed or risky control-plane upgrade states, collect must-gather and engage Red Hat support.

### 26.5 What to say about CVO

CVO does not directly upgrade every component by hand. It applies the release payload and waits for cluster operators to roll out their own components and report healthy status.

### 26.6 What to say about MCO

MCO updates node-level configuration and OS content. It cordons, drains, applies config, reboots, and uncordons nodes while respecting the MachineConfigPool rollout policy.

### 26.7 What to say about PDB

A PDB can block node drain during MCO rollout. Fix application availability, scale replicas, or temporarily adjust PDB with approval, then allow MCO to continue.

## Final practical summary

When an OpenShift cluster upgrade is stuck, do not start by restarting random pods. Start with the platform control plane view:

```bash
oc get clusterversion version
oc describe clusterversion version
oc get co
oc get mcp
oc get nodes
```

Then follow the blocking chain:

```text
ClusterVersion -> ClusterOperator -> Operator pods/operands -> MCP -> Node -> Pod/PDB/Runtime/Registry
```

Most stuck upgrade incidents are solved by fixing the first degraded component in that chain and allowing OpenShift operators to reconcile naturally.
