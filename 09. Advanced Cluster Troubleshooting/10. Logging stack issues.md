## 1. What “Logging stack issues” means

In OpenShift, **logging stack issues** mean any failure that prevents logs from being collected, processed, forwarded, stored, queried, or visualized.

A logging problem is not always a “logging Operator problem”. In production, the root cause can live in any of these layers:

```text
Application / Node / Audit source
        ↓
Container runtime log file / journald / audit file
        ↓
Collector pod on node, usually Vector in modern OpenShift Logging
        ↓
ClusterLogForwarder configuration
        ↓
Output destination: LokiStack, Kafka, Splunk, syslog, HTTP, cloud log service, etc.
        ↓
Storage backend: object storage, PVC, WAL, index gateway, ingester, querier
        ↓
Visualization: Observe → Logs, Cluster Observability Operator, UIPlugin
        ↓
RBAC / tenancy / user permissions
```

A senior admin does not start by restarting pods randomly. A senior admin first identifies **which stage of the pipeline is broken**.

### Typical user complaints

Users usually report logging issues like this:

- “No logs are visible in Observe → Logs.”
- “Application logs are missing but infrastructure logs are visible.”
- “Only old logs are visible.”
- “Collector pods are CrashLoopBackOff.”
- “LokiStack is degraded.”
- “Logs are delayed by 30 minutes.”
- “Splunk/Kafka/Syslog is not receiving logs.”
- “Audit logs are missing.”
- “Some namespaces have logs, some do not.”
- “Non-admin users cannot query logs.”
- “Collector logs show `429 Too Many Requests`.”
- “Collector logs show `certificate verify failed`.”
- “Loki ingester is Pending because PVC is Pending.”
- “Logging worked before upgrade, now nothing appears.”

The important rule is:

> **Do not treat logging as one component. Treat it as an end-to-end pipeline.**

## 2. Modern OpenShift Logging architecture

Modern OpenShift Logging uses multiple Operators and components.

### Main components

| Component | Purpose | Namespace commonly used |
|---|---|---|
| Red Hat OpenShift Logging Operator | Manages log collection and forwarding | `openshift-logging` |
| Loki Operator | Manages `LokiStack` storage | `openshift-operators-redhat` or `openshift-operators`, depending on install method |
| Cluster Observability Operator | Provides log visualization in console | `openshift-operators` |
| `ClusterLogForwarder` | Main CR for selecting, filtering, and forwarding logs | `openshift-logging` |
| Vector collector | Node-level collector that tails logs and forwards them | `openshift-logging` |
| LokiStack | Log storage/query stack | `openshift-logging` |
| UIPlugin | Enables Observe → Logs in web console | Usually managed by Cluster Observability Operator |
| Object storage | Backend for Loki chunks/index data | S3, Azure, GCS, ODF RGW, MinIO-like supported backend, etc. |

### Modern high-level data path

```text
/var/log/containers/*.log
/var/log/pods/*
journald
/var/log/audit/audit.log
        ↓
Vector collector DaemonSet
        ↓
ClusterLogForwarder pipelines
        ↓
Outputs:
  - LokiStack
  - Kafka
  - Splunk
  - Syslog
  - HTTP
  - Cloud provider logs
        ↓
Observe → Logs / Loki queries / external SIEM
```

### Key modern objects

```bash
oc get ns openshift-logging
oc get csv -n openshift-logging
oc get subscription -n openshift-logging
oc get clusterlogforwarder -n openshift-logging
oc get lokistack -n openshift-logging
oc get pods -n openshift-logging
oc get svc -n openshift-logging
oc get cm,secret -n openshift-logging
```

### What a healthy stack usually looks like

```bash
oc get pods -n openshift-logging
```

Expected categories:

```text
collector pods               Running, normally one per schedulable node
loki gateway                  Running
loki distributor              Running
loki ingester                 Running
loki querier                  Running
loki query-frontend           Running
loki compactor                Running, depending on size/config
loki index-gateway            Running, depending on size/config
logging operator pod          Running
```

Not every environment has the exact same pod names. Always inspect labels and owner references.

```bash
oc get pod -n openshift-logging --show-labels
oc describe pod <pod> -n openshift-logging
oc get deploy,ds,sts -n openshift-logging
```

## 3. Legacy vs modern logging stack

OpenShift environments may have different logging generations. This matters a lot during troubleshooting.

### Modern Logging 6 style

Modern Logging 6 introduced a cleaner separation:

- Red Hat OpenShift Logging Operator manages collection and forwarding.
- Loki Operator manages storage.
- Cluster Observability Operator manages visualization.
- Vector is the supported collector.
- `ClusterLogForwarder` uses the `observability.openshift.io` API group.
- Legacy `ClusterLogging` is no longer the main management object in the same way.

Modern CR example:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: default-logstore
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

### Legacy Logging 5 style

Older deployments may use:

- `ClusterLogging` CR
- `ClusterLogForwarder` under `logging.openshift.io`
- Fluentd collector
- Elasticsearch log store
- Kibana visualization

Legacy objects:

```bash
oc get clusterlogging -n openshift-logging
oc get clusterlogforwarder -n openshift-logging -o yaml
oc get elasticsearch -n openshift-logging
oc get kibana -n openshift-logging
oc get pods -n openshift-logging | egrep 'fluentd|elasticsearch|kibana'
```

### Senior-admin warning

When you troubleshoot, first identify stack generation:

```bash
oc api-resources | grep -i logforwarder
oc api-resources | grep -i clusterlogging
oc get clusterlogforwarder -A -o wide
oc get clusterlogging -A
oc get csv -A | egrep -i 'logging|loki|observability|elasticsearch'
```

Do not apply Logging 6 YAML blindly to a Logging 5 environment, and do not troubleshoot Vector if the environment still uses Fluentd.

## 4. Fast senior-admin triage flow

Use this flow when production logging is broken and people are waiting.

### Step 1: Confirm user impact

Ask or determine:

```text
Which logs are missing?
- application
- infrastructure
- audit
- all logs

Where are they missing?
- OpenShift web console Observe → Logs
- Loki query
- external SIEM
- Splunk
- Kafka
- syslog

When did it start?
- after upgrade
- after certificate rotation
- after network policy change
- after storage change
- after namespace/project changes
- after adding filters/rate limits
```

### Step 2: Check global health

```bash
oc get co
oc get clusterversion
oc get nodes
oc get mcp
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Logging can break because the cluster is unhealthy. If nodes are NotReady, CNI is broken, DNS is broken, or storage is degraded, logging will also fail.

### Step 3: Check Operator and CR status

```bash
oc get csv -n openshift-logging
oc get subscription -n openshift-logging
oc get installplan -n openshift-logging
oc get clusterlogforwarder -n openshift-logging
oc get lokistack -n openshift-logging
```

For modern `ClusterLogForwarder`:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Healthy conditions should normally include:

```text
observability.openshift.io/Authorized=True
observability.openshift.io/Valid=True
Ready=True
```

### Step 4: Check collectors

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
oc describe pod -n openshift-logging -l app.kubernetes.io/component=collector
```

If no collector pod exists, check RBAC and `ClusterLogForwarder` conditions.

### Step 5: Check LokiStack storage path

```bash
oc get pods -n openshift-logging | egrep -i 'loki|gateway|ingester|querier|distributor|compactor|index'
oc get pvc -n openshift-logging
oc get lokistack -n openshift-logging -o yaml
oc describe lokistack <name> -n openshift-logging
```

### Step 6: Check UI and user permissions

```bash
oc get csv -A | grep -i observability
oc get uiplugin -A
oc auth can-i get pods/log -n <app-namespace> --as=<user>
oc auth can-i get applicationlogs.observability.openshift.io --as=<user>
```

### Step 7: Check exact error messages

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m | \
  egrep -i 'error|warn|denied|forbidden|certificate|tls|timeout|429|503|connection|loki|kafka|splunk|syslog'
```

## 6. Failure domain map

A good OpenShift admin classifies logging issues by failure domain.

| Failure domain | Symptoms | First object to check |
|---|---|---|
| OLM / Operator | CSV Pending/Failed, no CRDs, Operator pod crash | `Subscription`, `CSV`, `InstallPlan` |
| CR validation | `ClusterLogForwarder Ready=False`, no collector DaemonSet | `ClusterLogForwarder.status.conditions` |
| RBAC | `Authorized=False`, collector not created, missing audit/app logs | service account + clusterrolebindings |
| Collector scheduling | Collector not on all nodes, Pending pods | DaemonSet, taints, tolerations, node selectors |
| Collector runtime | CrashLoop, OOMKilled, parse errors | collector pod logs, resources |
| Node log source | Specific node logs missing | `/var/log/containers`, journald, kubelet, CRI-O |
| Loki gateway | 401/403/503, query failures | gateway pod logs/service/endpoints |
| Loki ingestion | 429, ingestion delay, missing recent logs | distributor/ingester logs, limits |
| Loki query | UI timeout, partial logs | querier/query-frontend logs |
| Object storage | Loki pods crash, upload failures, 5xx, access denied | object storage secret + connectivity |
| PVC/storage | Loki pod Pending, WAL PVC stuck | PVC/PV/storageclass/events |
| TLS/CA | `certificate verify failed`, Ready=True but no logs | CLF output `tls.ca` |
| Network | timeout, connection refused | service, endpoints, NetworkPolicy, DNS |
| UI | No Observe → Logs tab | COO + UIPlugin |
| User access | Admin sees logs, user cannot | cluster roles/rolebindings/tenancy |
| External destination | OpenShift has logs, SIEM does not | output config + secret + destination logs |

## 7. Operator installation and OLM issues

Logging is Operator-managed. If Operators are unhealthy, the stack will not reconcile correctly.

### 7.1 Check installed Operators

```bash
oc get csv -A | egrep -i 'logging|loki|observability|elasticsearch'
oc get sub -A | egrep -i 'logging|loki|observability|elasticsearch'
oc get installplan -A | egrep -i 'logging|loki|observability|elasticsearch'
```

Expected modern components:

```text
Red Hat OpenShift Logging Operator
Loki Operator
Cluster Observability Operator, if UI logging is needed
```

### 7.2 CSV stuck in Pending

Check:

```bash
oc describe csv <csv-name> -n <namespace>
oc describe sub <subscription-name> -n <namespace>
oc get installplan -n <namespace>
oc describe installplan <installplan-name> -n <namespace>
oc get catalogsource -n openshift-marketplace
oc get pods -n openshift-marketplace
```

Common causes:

- Wrong channel.
- Wrong source, for example community catalog instead of `redhat-operators`.
- Disconnected cluster missing mirrored catalog content.
- Manual InstallPlan not approved.
- Operator dependency resolution failed.
- Namespace has wrong `OperatorGroup`.
- CatalogSource pod is CrashLoopBackOff.
- Marketplace disabled or restricted network misconfigured.

Fix examples:

```bash
# Approve a manual install plan
oc patch installplan <installplan> -n <ns> --type merge -p '{"spec":{"approved":true}}'

# Check package manifest channels
oc get packagemanifest cluster-logging -n openshift-marketplace -o yaml | grep -A5 channels
oc get packagemanifest loki-operator -n openshift-marketplace -o yaml | grep -A5 channels
```

### 7.3 Operator pod CrashLoopBackOff

```bash
oc get pods -n openshift-logging
oc logs <operator-pod> -n openshift-logging --previous
oc describe pod <operator-pod> -n openshift-logging
```

Common causes:

- Image pull failure.
- Missing pull secret in disconnected registry.
- SCC/permission issue.
- Bad Operator version/channel combination.
- API server connectivity issue.
- CRD conversion or webhook issue.

### 7.4 Senior admin decision

If OLM is broken, do not troubleshoot collector or Loki first. Fix OLM first because the desired state controller is not reliable.

## 8. `ClusterLogForwarder` issues

`ClusterLogForwarder` is the central object for log collection and forwarding.

### 8.1 Check existence and API group

```bash
oc get clusterlogforwarder -A
oc get clusterlogforwarder instance -n openshift-logging -o yaml
oc api-resources | grep -i clusterlogforwarder
```

Modern API:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
```

Legacy API:

```yaml
apiVersion: logging.openshift.io/v1
kind: ClusterLogForwarder
```

### 8.2 Check status conditions

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Important conditions:

| Condition | Meaning | Troubleshooting direction |
|---|---|---|
| `observability.openshift.io/Authorized` | Collector service account has required log collection permissions | Fix service account ClusterRoleBindings |
| `observability.openshift.io/Valid` | CR is structurally and semantically valid | Fix YAML fields, output references, secret references |
| `Ready` | Operator reconciled resources successfully | If `False`, read message carefully |

### 8.3 `Authorized=False`

Symptom:

```text
collector service account is not authorized to collect log type: application/infrastructure/audit
```

Check service account:

```bash
oc get sa -n openshift-logging
oc get clusterrole | grep -i log
oc get clusterrolebinding | grep -i collector
```

Typical fix for modern logging collector:

```bash
oc create sa logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user logging-collector-logs-writer \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-application-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  -z logging-collector -n openshift-logging

# Add only if audit collection is configured and allowed in your environment.
oc adm policy add-cluster-role-to-user collect-audit-logs \
  -z logging-collector -n openshift-logging
```

Then re-check:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

### 8.4 `Valid=False`

Common mistakes:

- `outputRefs` points to a non-existing output.
- `filterRefs` points to a non-existing filter.
- Secret name is wrong.
- TLS config references a missing ConfigMap/key.
- Output type is wrong.
- LokiStack target name/namespace is wrong.
- Pipeline references unauthorized input type.
- YAML uses old API fields with new API group.
- Wrong namespace or wrong resource name expected by the Operator.

Check:

```bash
oc describe clusterlogforwarder instance -n openshift-logging
oc get cm,secret -n openshift-logging
oc get lokistack -n openshift-logging
```

### 8.5 `Ready=True` but no logs

This is a common production trap.

`Ready=True` means the Operator reconciled the CR. It does **not always prove** that logs are successfully reaching the destination.

Check collector logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200 | \
  egrep -i 'error|warn|certificate|tls|connection|timeout|denied|forbidden|loki|429|503'
```

Common causes:

- Missing TLS CA bundle for LokiStack gateway.
- Destination reachable only through proxy but proxy config wrong.
- External destination certificate untrusted.
- NetworkPolicy blocks collector egress.
- Loki gateway/service endpoint unavailable.
- Wrong tenant/auth token.
- Output is rate limited.

### 8.6 Minimal working CLF for LokiStack

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
  - name: default-lokistack
    type: lokiStack
    lokiStack:
      target:
        name: logging-loki
        namespace: openshift-logging
      authentication:
        token:
          from: serviceAccount
    tls:
      ca:
        configMapName: logging-loki-gateway-ca-bundle
        key: service-ca.crt
  pipelines:
  - name: default-logstore
    inputRefs:
    - application
    - infrastructure
    outputRefs:
    - default-lokistack
```

Apply and verify:

```bash
oc apply -f clf.yaml
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
```

## 9. Collector / Vector issues

The collector is the part that actually reads logs from nodes and sends them to outputs.

### 9.1 Check collector DaemonSet

```bash
oc get ds -n openshift-logging
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector -o wide
oc describe ds -n openshift-logging
```

Expected:

- One collector pod per applicable node.
- Pods Running and Ready.
- Pods scheduled on worker and/or control-plane nodes depending on configuration.

### 9.2 Collector pod Pending

Check:

```bash
oc describe pod <collector-pod> -n openshift-logging
oc get nodes --show-labels
oc describe node <node>
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -50
```

Common causes:

- Node taints not tolerated.
- Node selector excludes nodes.
- Insufficient CPU/memory.
- Namespace quota blocks pod creation.
- SCC/admission issue.
- ImagePullBackOff in disconnected environment.

Fix direction:

- Correct collector scheduling config.
- Increase node capacity.
- Fix image mirror/pull secret.
- Add required tolerations only if supported by Operator configuration.
- Avoid manually editing Operator-owned DaemonSet; fix the owning CR.

### 9.3 Collector CrashLoopBackOff

```bash
oc logs <collector-pod> -n openshift-logging --previous
oc logs <collector-pod> -n openshift-logging
oc describe pod <collector-pod> -n openshift-logging
```

Common causes:

- Invalid generated Vector configuration.
- Missing secret/configmap.
- TLS/key file missing.
- Destination config error.
- OOMKilled due to high log volume.
- File permission issue reading host paths.
- Bug or unsupported output setting.

Look for:

```text
configuration error
failed to build sink
failed to open file
permission denied
No such file or directory
certificate verify failed
connection refused
timed out
429 Too Many Requests
```

### 9.4 Collector OOMKilled

Check:

```bash
oc describe pod <collector-pod> -n openshift-logging | egrep -i 'oom|killed|memory|limit|request'
oc adm top pod -n openshift-logging
oc adm top node
```

Common causes:

- Noisy application producing huge log volume.
- Large multiline logs.
- Backpressure from slow destination.
- Too many outputs/pipelines.
- Destination unreachable causing buffer growth.
- CPU throttling.

Fix direction:

- Identify noisy namespace/pod.
- Add input filters.
- Add rate limits carefully.
- Scale destination capacity.
- Increase collector resource requests/limits through supported configuration.
- Fix destination latency.

### 9.5 Collector not deployed after CLF creation

If `ClusterLogForwarder` exists but collector DaemonSet is absent:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
```

Common cause:

```text
Authorized=False
```

Fix RBAC for the collector service account.

### 9.6 Collector logs show `certificate verify failed`

Symptom:

```text
certificate verify failed: self-signed certificate in certificate chain
```

Cause:

- Missing or incorrect CA configuration for output.
- LokiStack gateway uses service CA but CLF does not trust it.
- External destination uses corporate CA not mounted into collector.

Fix example for LokiStack:

```yaml
outputs:
- name: default-lokistack
  type: lokiStack
  lokiStack:
    target:
      name: logging-loki
      namespace: openshift-logging
    authentication:
      token:
        from: serviceAccount
  tls:
    ca:
      configMapName: logging-loki-gateway-ca-bundle
      key: service-ca.crt
```

Then:

```bash
oc apply -f clf.yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

### 9.7 Collector logs show 429

Symptom:

```text
429 Too Many Requests
Ingestion rate limit exceeded
```

Meaning:

- Loki or external destination is throttling ingestion.
- During initial onboarding, collectors may flush backlog and 429 can be temporary.
- If persistent, tune ingestion limits, reduce noise, or scale destination.

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m | grep -i '429'
oc logs -n openshift-logging -l app.kubernetes.io/component=ingester --since=30m | grep -i 'rate'
```

Fix direction:

- For LokiStack, adjust `spec.limits.global.ingestion` carefully.
- Add input rate limits for noisy namespaces.
- Drop unnecessary debug logs.
- Reduce high-cardinality labels.
- Scale Loki components if the deployment size supports it.

## 10. Node log source issues

Sometimes the logging stack is healthy, but one node or one log type is missing.

### 10.1 Container log files

OpenShift/Kubernetes container logs are normally under:

```text
/var/log/containers/*.log
/var/log/pods/*
```

Use debug node:

```bash
oc debug node/<node-name>
chroot /host
ls -lh /var/log/containers | head
ls -lh /var/log/pods | head
```

Check a specific pod:

```bash
ls -l /var/log/containers | grep <pod-name>
```

### 10.2 Journald logs

Infrastructure logs may come from journald.

## 11. LokiStack issues

LokiStack is the log storage/query system used by modern OpenShift Logging.

### 11.1 Check LokiStack CR

```bash
oc get lokistack -n openshift-logging
oc describe lokistack <name> -n openshift-logging
oc get lokistack <name> -n openshift-logging -o yaml
```

Important fields:

```yaml
spec:
  size: 1x.extra-small | 1x.small | 1x.medium | ...
  storage:
    schemas:
    - version: v13
      effectiveDate: "YYYY-MM-DD"
    secret:
      name: <object-storage-secret>
      type: s3 | azure | gcs | swift
  limits:
    global:
      ingestion:
        ingestionRate: <MB/s>
        ingestionBurstSize: <MB>
  tenants:
    mode: openshift-logging
```

Field names can vary by version. Always verify with:

```bash
oc explain lokistack.spec
oc explain lokistack.spec.storage
oc explain lokistack.spec.limits
```

### 11.2 Loki pods

```bash
oc get pods -n openshift-logging | egrep -i 'loki|gateway|ingester|distributor|querier|frontend|compactor|index'
```

Typical component roles:

| Component | Role | Common failure symptom |
|---|---|---|
| gateway | Auth, tenancy, query/ingest entry point | 401/403/503, TLS errors |
| distributor | Receives writes, validates, forwards to ingesters | 429, push errors |
| ingester | Stores recent logs, writes chunks | OOM, PVC/WAL issues, rate limit |
| querier | Reads logs from ingesters/object store | query timeout |
| query-frontend | Query scheduling/caching | UI slow/timeout |
| compactor | Compacts index/chunks | object store errors |
| index-gateway | Index access | Pending PVC, query errors |
| ruler | Alert/rule evaluation, if enabled | rule failures |

### 11.3 LokiStack Degraded

Check:

```bash
oc describe lokistack <name> -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -80
oc get pods -n openshift-logging | grep -i loki
```

Common causes:

- Object storage secret incorrect.
- Object bucket unreachable.
- Storage schema issue.
- Ingester or index-gateway PVC Pending.
- Pod anti-affinity not satisfiable.
- Insufficient CPU/memory.
- NetworkPolicy blocks internal components.
- Service CA or gateway certificate issue.

### 11.4 Loki gateway errors

Check gateway logs:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=gateway --tail=100
```

Common errors:

```text
401 Unauthorized
403 Forbidden
x509: certificate signed by unknown authority
upstream connect error
no healthy upstream
context deadline exceeded
```

Troubleshooting:

```bash
oc get svc,endpoints -n openshift-logging | grep -i loki
oc get route -n openshift-logging | grep -i loki
oc get cm -n openshift-logging | grep -i ca
oc get secret -n openshift-logging | grep -i loki
```

### 11.5 Loki ingestion delay

Symptoms:

- Logs appear after 10–30 minutes.
- Collector has retries.
- Ingester CPU/memory high.
- 429 rate limit.
- Object store latency high.

Check:

```bash
oc adm top pod -n openshift-logging
oc logs -n openshift-logging -l app.kubernetes.io/component=ingester --since=30m | egrep -i 'error|warn|rate|flush|chunk|timeout'
oc logs -n openshift-logging -l app.kubernetes.io/component=distributor --since=30m | egrep -i 'error|warn|429|rate|push'
```

Fix direction:

- Reduce log volume.
- Add filters/rate limits.
- Increase LokiStack size if supported.
- Improve object storage performance.
- Adjust ingestion limits after capacity review.

### 11.6 Query timeout

Symptoms:

- Observe → Logs opens but queries fail.
- Specific namespace queries time out.
- Large time-range queries fail.

Check:

```bash
oc logs -n openshift-logging -l app.kubernetes.io/component=querier --since=30m | egrep -i 'timeout|error|slow|deadline'
oc logs -n openshift-logging -l app.kubernetes.io/component=query-frontend --since=30m | egrep -i 'timeout|error|queue|deadline'
```

Fix direction:

- Query smaller time ranges.
- Avoid broad `{}` style queries.
- Reduce high-cardinality labels.
- Tune LokiStack size.
- Confirm object storage latency.

## 12. Object storage issues

Loki depends heavily on object storage. If object storage is broken, Loki becomes unreliable.

### 12.1 Object storage secret

Check secret:

```bash
oc get secret -n openshift-logging
oc get lokistack <name> -n openshift-logging -o yaml | grep -A20 storage
```

Decode carefully:

```bash
oc get secret <secret-name> -n openshift-logging -o jsonpath='{.data}' | jq
```

Do not paste secrets into tickets or chats.

### 12.2 Common object storage failures

| Error | Meaning | Fix direction |
|---|---|---|
| `AccessDenied` | Wrong access key, bucket policy, IAM role | Fix credentials/policy |
| `NoSuchBucket` | Bucket missing/wrong name | Create bucket or fix config |
| `SignatureDoesNotMatch` | Wrong secret key/region/endpoint | Fix S3 fields |
| `x509 unknown authority` | Object endpoint cert not trusted | Add correct CA |
| `connection refused` | Endpoint down/wrong port | Fix service/route/firewall |
| `timeout` | Network or object storage latency | Network/storage performance RCA |
| `SlowDown` | Provider throttling | Reduce load or increase backend capacity |

### 12.3 Test from inside cluster

Create a temporary debug pod with network tools if allowed:

```bash
oc run netdebug -n openshift-logging --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc rsh -n openshift-logging netdebug
```

Inside pod:

```bash
curl -vk https://<object-storage-endpoint>

```

If minimal image lacks tools, use an approved internal troubleshooting image.

### 12.4 ODF / RGW backend

For OpenShift Data Foundation-backed object storage:

## 13. PVC, WAL, and storage scheduling issues

Some Loki components use PVCs, including WAL and index-related storage depending on deployment size and version.

### 13.1 Check PVCs

```bash
oc get pvc -n openshift-logging
oc describe pvc <pvc-name> -n openshift-logging
oc get storageclass
oc get pv | grep openshift-logging
```

### 13.2 Loki pod Pending because PVC Pending

Symptoms:

```text
logging-loki-ingester-0    0/1 Pending
storage-logging-loki...    Pending
```

Check:

```bash
oc describe pod <pod> -n openshift-logging
oc describe pvc <pvc> -n openshift-logging
oc get events -n openshift-logging --sort-by=.lastTimestamp | tail -80
```

Common causes:

- StorageClass missing.
- Storage provisioner unavailable.
- Zone mismatch.
- VolumeBindingMode `WaitForFirstConsumer` and scheduling conflict.
- No PV capacity.
- PVC stuck because failed node/zone.
- Quota blocks PVC.

### 13.3 PVC stuck Terminating

Check finalizers:

```bash
oc get pvc <pvc-name> -n openshift-logging -o yaml | grep -A5 finalizers
```

Emergency fix only after verifying data impact:

```bash
oc patch pvc <pvc-name> -n openshift-logging \
  -p '{"metadata":{"finalizers":null}}' --type=merge
```

Senior-admin warning:

> Removing PVC finalizers is a break-glass action. It can cause data loss or orphaned volumes. Use only when you understand whether the data is disposable or recoverable.

### 13.4 Multi-zone failure

If a zone is unavailable, Loki pods with PVCs in that zone might not reschedule elsewhere until PVCs are handled.

Check pod zone:

```bash
oc get pod <pod> -n openshift-logging -o wide
oc get pv <pv-name> -o yaml | egrep -i 'zone|topology|nodeAffinity' -A5
```

Fix direction:

- Restore failed zone.
- Delete affected pod/PVC only if data loss is acceptable or replicated elsewhere.
- Ensure storage topology and Loki replication are designed for zone failures.

## 14. TLS, CA bundle, proxy, and certificate issues

TLS problems are one of the most common causes of “Ready but no logs”.

### 14.1 Symptoms

Collector logs:

```text
certificate verify failed
x509: certificate signed by unknown authority
self-signed certificate in certificate chain
TLS handshake failed
```

External outputs:

```text
HTTP 400/401/403
connection reset by peer
remote error: tls: bad certificate
```

### 14.2 LokiStack gateway CA

Check CA ConfigMap:

```bash
oc get cm -n openshift-logging | grep -i ca
oc get cm logging-loki-gateway-ca-bundle -n openshift-logging -o yaml
```

Check CLF output:

```bash
oc get clusterlogforwarder instance -n openshift-logging -o yaml | grep -A20 tls
```

Correct pattern:

```yaml
tls:
  ca:
    configMapName: logging-loki-gateway-ca-bundle
    key: service-ca.crt
```

### 14.3 External destination CA

For Splunk, Kafka, HTTP, syslog TLS, or cloud endpoints:

- Confirm server certificate chain.
- Confirm hostname matches certificate SAN.
- Confirm CA is mounted through ConfigMap/Secret as required by output type.
- Confirm proxy does not intercept TLS without trusted CA.

Test:

```bash
openssl s_client -connect <host>:<port> -servername <host> -showcerts </dev/null
```

From inside cluster:

```bash
oc run tlsdebug -n openshift-logging --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc rsh -n openshift-logging tlsdebug
curl -vk https://<destination>
```

### 14.4 Cluster-wide proxy issues

Check:

```bash
oc get proxy/cluster -o yaml
oc get cm trusted-ca-bundle -n openshift-config -o yaml
oc get pods -n openshift-logging -o yaml | grep -i proxy -A5
```

Common issues:

- Destination must use FQDN, not IP, when proxy rules require hostname.
- `NO_PROXY` missing internal service domains.
- Proxy certificate not trusted.
- Proxy blocks large requests.
- External destination bypasses proxy unexpectedly.

## 19. Rate limit, noisy logs, cardinality, and performance issues

Logging problems are often capacity problems.

### 19.1 Signs of log volume pressure

- Collector CPU high.
- Collector memory high.
- Collector OOMKilled.
- Loki distributor/ingester CPU high.
- Loki returns 429.
- Queries slow or timeout.
- Object storage requests increase.
- Logs delayed.
- External destination throttles.

Check:

```bash
oc adm top pod -n openshift-logging
oc adm top node
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --since=30m | grep -i rate
```

### 19.2 Identify noisy workloads

OpenShift does not always give direct “top log producer” out of the box, but you can inspect:

```bash
# On node debug session
oc debug node/<node>
chroot /host
find /var/log/containers -type f -printf '%s %p\n' | sort -nr | head -20
```

Look for:

- Repeating stack traces.
- Debug logs enabled in production.
- Health check logs every second.
- Sidecar logs too verbose.
- JSON logs with huge payloads.
- Infinite retry loops.

### 19.3 Rate limiting

Rate limits protect the platform but can drop logs.

Example input rate limit:

```yaml
spec:
  inputs:
  - name: limited-app-logs
    type: application
    application:
      tuning:
        rateLimitPerContainer:
          maxRecordsPerSecond: 100
```

Example output rate limit:

```yaml
spec:
  outputs:
  - name: limited-kafka
    type: kafka
    kafka:
      brokers:
      - kafka.example.com:9092
      topic: logs
    rateLimit:
      maxRecordsPerSecond: 5000
```

Warning:

> Rate limiting can drop records. Use it as a protection mechanism, not as a substitute for fixing noisy applications.

### 19.4 High-cardinality labels

High cardinality means too many unique label combinations. It hurts Loki query and ingestion performance.

Bad label examples:

```text
request_id
trace_id
session_id
user_id
pod_uid
container_id
full URL path with IDs
```

Good label examples:

```text
namespace
pod
container
app
log_type
environment
team
```

Fix direction:

- Avoid promoting dynamic fields to labels.
- Keep high-cardinality data inside log body, not labels.
- Use filters/pruning to remove unnecessary metadata.

### 19.5 Large multiline logs

Problems:

- Big Java stack traces.
- Huge JSON blobs.
- Logs larger than receiver request limit.
- Increased memory use in collector.

Fix direction:

- Reduce application verbosity.
- Configure sane multiline behavior if supported.
- Avoid logging full payloads/secrets.
- Add output size/rate controls.

## 21. Upgrade and migration issues

Logging upgrades are common breaking points.

### 21.1 Key upgrade risks

- Logging Operator and Loki Operator version mismatch.
- Unsupported channel jump.
- Legacy `ClusterLogging` still present.
- Fluentd configuration not migrated to Vector.
- Elasticsearch/Kibana still expected after migration.
- API group changed from `logging.openshift.io` to `observability.openshift.io`.
- Old CLF syntax used with new Operator.
- UI plugin not installed after migration.
- LokiStack storage schema not upgraded properly.

### 21.2 Pre-upgrade checks

```bash
oc get csv -A | egrep -i 'logging|loki|observability|elasticsearch'
oc get sub -A | egrep -i 'logging|loki|observability|elasticsearch'
oc get clusterlogging -A
oc get clusterlogforwarder -A -o yaml > clf-backup.yaml
oc get lokistack -A -o yaml > lokistack-backup.yaml
oc get secret,cm -n openshift-logging -o yaml > logging-secret-cm-backup.yaml
oc get pods -n openshift-logging -o wide
oc get pvc -n openshift-logging
```

### 21.3 After upgrade, no logs

Check order:

```bash
oc get csv -A | egrep -i 'logging|loki|observability'
oc get clusterlogforwarder -n openshift-logging -o yaml
oc get lokistack -n openshift-logging -o yaml
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=200
```

Common fixes:

- Update CLF API/schema.
- Add missing service account RBAC.
- Fix TLS CA bundle.
- Update LokiStack storage schema.
- Install COO/UIPlugin for console visualization.
- Remove old Elasticsearch/Kibana expectations.

### 21.4 Do not mix old and new assumptions

Example mistakes:

```bash
# Wrong in modern Vector/Loki-only environment:
oc delete pod -l component=fluentd -n openshift-logging
oc get elasticsearch -n openshift-logging
```

Instead:

```bash
oc get pods -n openshift-logging -l app.kubernetes.io/component=collector
oc get lokistack -n openshift-logging
```

### 23.2 RCA example: Missing TLS CA

```markdown
## Root cause
The ClusterLogForwarder was valid and Ready, but the collector could not establish a trusted TLS connection to the LokiStack gateway. The output configuration missed the Loki gateway service CA bundle.

## Evidence
Collector logs showed:
certificate verify failed: self-signed certificate in certificate chain

ClusterLogForwarder showed Ready=True, which only confirmed successful reconciliation, not successful delivery.

## Fix
Added tls.ca configuration referencing logging-loki-gateway-ca-bundle/service-ca.crt.

## Prevention
Add post-change validation that checks collector logs and performs a query from Observe → Logs after every CLF change.
```

### 23.3 RCA example: Noisy app caused 429

```markdown
## Root cause
A production application entered a retry loop and generated a high log volume. Loki ingestion limits were exceeded, causing collectors to receive repeated 429 responses.

## Evidence
Collector logs showed 429 Too Many Requests.
Node log file inspection showed one pod producing the largest files under /var/log/containers.
Loki distributor and ingester logs showed rate-limit messages.

## Fix
Application logging level was reduced. Temporary input rate limit was configured for the affected namespace. Loki ingestion capacity was reviewed.

## Prevention
Create alert for collector output rate-limited records and define namespace log volume SLOs.
```

## 25. Best practices for stable logging

### 25.1 Design practices

- Treat logging as a production platform service.
- Define retention expectations clearly.
- Do not use LokiStack as long-term compliance archive unless designed and supported for that requirement.
- Keep audit logs separate and access-controlled.
- Use external SIEM for long-term security retention if required.
- Size object storage for sustained ingestion and query load.
- Use multiple failure domains where supported.

### 25.2 Operational practices

- Validate `ClusterLogForwarder` after every change.
- Always check collector logs, not only CR status.
- Monitor dropped/rate-limited logs.
- Alert on collector restarts and Loki component failures.
- Keep a known-good CLF YAML backup.
- Track log volume by namespace/team.
- Review noisy applications regularly.

### 25.3 Change management

Before changing logging:

```bash
oc get clusterlogforwarder -n openshift-logging -o yaml > backup-clf-$(date +%F).yaml
oc get lokistack -n openshift-logging -o yaml > backup-lokistack-$(date +%F).yaml
oc get secret,cm -n openshift-logging -o yaml > backup-logging-cm-secret-$(date +%F).yaml
```

After changing logging:

```bash
oc get clusterlogforwarder instance -n openshift-logging \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool
oc get pods -n openshift-logging
oc logs -n openshift-logging -l app.kubernetes.io/component=collector --tail=100
```

Then verify from UI or query endpoint.

### 25.4 Security practices

- Do not give audit log access to normal users.
- Do not log secrets, tokens, passwords, private keys, or full request payloads.
- Use TLS for external forwarding.
- Use least-privilege tokens for external systems.
- Rotate forwarding credentials.
- Protect object storage credentials.
- Keep logging namespace access restricted.

### 25.5 Capacity practices

- Plan for peak log volume, not average.
- Avoid debug logs in production.
- Define namespace/team log budgets.
- Watch collector CPU/memory.
- Watch Loki ingestion and query latency.
- Scale LokiStack according to observed load and supported profiles.
- Validate object storage throughput.

## 26. Interview and exam-style points

### Question: What do you check first when no logs are visible?

Strong answer:

```text
I first identify whether the problem is collection, forwarding, storage, visualization, or RBAC. I check ClusterLogForwarder status conditions, collector pod health/logs, LokiStack pods/PVCs, and then UI/RBAC. I do not assume Ready=True means delivery is working; I verify collector logs and actual log queries.
```

### Question: What does `ClusterLogForwarder Ready=True` mean?

Strong answer:

```text
It means the Operator could reconcile the CR and create supporting resources. It does not guarantee the collector can connect to the destination. For example, a missing TLS CA can still make collectors fail while CLF is Ready.
```

### Question: Why can admin see logs but developer cannot?

Strong answer:

```text
OpenShift logging is multi-tenant. Developers need namespace/application log permissions. Infrastructure and audit logs usually require stronger cluster-level roles. I verify with `oc auth can-i` and check logging-specific roles/rolebindings.
```

### Question: How do you handle `429 Too Many Requests` from Loki?

Strong answer:

```text
I determine if it is temporary backlog ingestion or persistent overload. I check collector, distributor, and ingester logs, identify noisy workloads, review rate limit/drop metrics, reduce log volume or add filters, and only then tune LokiStack ingestion limits or scale capacity.
```

### Question: What are common causes of collector CrashLoopBackOff?

Strong answer:

```text
Invalid generated configuration, missing secret or ConfigMap, TLS/auth error, unsupported output setting, OOMKilled due to log volume/backpressure, or image pull issues in disconnected clusters.
```

### Question: What changed in modern Logging 6?

Strong answer:

```text
Logging 6 separates responsibilities: OpenShift Logging Operator handles collection/forwarding, Loki Operator handles storage, and Cluster Observability Operator handles visualization. Vector is the supported collector, Loki replaces Elasticsearch for managed log storage, and ClusterLogForwarder uses the observability API.
```
