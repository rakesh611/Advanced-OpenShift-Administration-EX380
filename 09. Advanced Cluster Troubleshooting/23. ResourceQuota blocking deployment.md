# ResourceQuota Blocking Deployment — Advanced OpenShift Troubleshooting Guide

**Audience:** Advanced OpenShift administrators, SREs, platform engineers, and EX280/DO380/advanced cluster troubleshooting learners  
**Level:** 10+ years production operations mindset  
**Scope:** OpenShift Container Platform 4.x / Kubernetes namespaces / OpenShift projects  
**Main symptom:** A Deployment, DeploymentConfig, Job, Build, Pod, or Helm release fails to create or scale workloads because the project quota is exhausted or because required requests/limits are missing.

---

## 1. Executive Summary

`ResourceQuota blocking deployment` means OpenShift is refusing to admit one or more resources because the project has a `ResourceQuota` or `ClusterResourceQuota` policy and the requested change would violate it.

In many real incidents, the Deployment object itself is created successfully, but the ReplicaSet cannot create Pods. The user says, “Deployment is created but no pod is running.” The real failure is usually visible in ReplicaSet events:

```text
Error creating: pods "web-xxxx" is forbidden: exceeded quota: compute-resources,
requested: requests.cpu=500m,requests.memory=512Mi,
used: requests.cpu=1900m,requests.memory=3584Mi,
limited: requests.cpu=2,requests.memory=4Gi
```

Or:

```text
Error creating: pods "web-xxxx" is forbidden: failed quota: compute-resources:
must specify requests.cpu for: app; requests.memory for: app
```

Senior admin mindset:

- Do not troubleshoot this as a scheduler issue first.
- Do not immediately add worker nodes.
- Do not restart kubelet, CRI-O, or the Deployment.
- First read the admission error from events, then compare quota `Used` vs `Hard`.
- Remember that a Deployment can be valid while the ReplicaSet is forbidden from creating Pods.

## 2. What ResourceQuota Actually Does

A `ResourceQuota` is a namespace/project-level budget. In OpenShift, a project is a Kubernetes namespace with extra OpenShift management features.

A quota can limit:

- Number of Pods
- Number of Services
- Number of Secrets
- Number of ConfigMaps
- Number of PVCs
- Total requested CPU
- Total requested memory
- Total CPU limits
- Total memory limits
- Total storage requested by PVCs
- Storage requested by a specific StorageClass
- Object count of namespaced resources
- Quota by scope such as `BestEffort`, `NotBestEffort`, `Terminating`, `NotTerminating`, or priority classes

Important operational point:

A quota does not measure actual CPU or memory usage. It measures the resource values declared in object specs, especially `requests` and `limits`.

Example:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: 1
    memory: 1Gi
```

If this Pod is created, quota usage increases by:

```text
requests.cpu    +500m
requests.memory +512Mi
limits.cpu      +1
limits.memory   +1Gi
pods            +1
```

Even if the application is idle and using only 10 MiB memory, quota accounting is based on the declared values, not live usage.

## 3. How the Failure Happens Internally

### 3.1 API admission flow

When a user runs:

```bash
oc apply -f deployment.yaml
```

OpenShift API admission evaluates the request. Depending on what is being created, this can happen at several layers:

1. The Deployment object is submitted.
2. The Deployment controller creates a ReplicaSet.
3. The ReplicaSet controller creates Pods.
4. The ResourceQuota admission plugin checks whether the new object would exceed the quota.
5. If quota would be exceeded, the API server rejects the create/update request with `Forbidden`.
6. The rejection is recorded as an event on the ReplicaSet, DeploymentConfig, Job, Build, or Pod creator.

This is why a Deployment can show `0/3` replicas without obvious Pod logs. The Pod was never admitted, so there is no container to log into.

### 3.2 Admission failure vs scheduling failure

These two problems look similar to junior admins but are very different.

| Problem | Where it fails | Typical message | Pod exists? | Fix direction |
|---|---|---|---|---|
| ResourceQuota exceeded | API admission | `forbidden: exceeded quota` | Often no | Reduce request, free quota, increase quota |
| Missing requests/limits under quota | API admission | `must specify requests.cpu` | No | Add requests/limits or LimitRange defaults |
| Node capacity insufficient | Scheduler | `0/5 nodes are available: Insufficient cpu` | Yes, Pending | Add capacity, reduce requests, scheduling changes |
| LimitRange violation | API admission | `maximum cpu usage per Container is...` | No | Adjust app resources or LimitRange |
| SCC violation | API admission | `would violate PodSecurity` / SCC errors | No | Fix securityContext or SCC binding |

ResourceQuota failures are not fixed by cordon/uncordon, draining nodes, restarting scheduler, or deleting random Pods unless the quota usage is actually freed.

## 4. Common Error Patterns

### 4.1 Quota exceeded for Pods

```text
pods "frontend-xxxx" is forbidden: exceeded quota: object-counts,
requested: pods=1, used: pods=10, limited: pods=10
```

Meaning:

The project already has 10 non-terminal Pods and quota allows only 10. A new Pod cannot be admitted.

Common causes:

- Old Pods not cleaned up
- Jobs/CronJobs keeping completed Pods
- Rollout `maxSurge` temporarily needs extra Pods
- HPA scaled up to quota limit
- Debug Pods left in namespace
- Build/deployer Pods consuming quota

### 4.2 Quota exceeded for CPU request

```text
pods "api-xxxx" is forbidden: exceeded quota: compute-resources,
requested: requests.cpu=500m, used: requests.cpu=1800m, limited: requests.cpu=2
```

Meaning:

The new Pod asks for 500 millicores. Current quota usage is 1800 millicores. Hard quota is 2000 millicores. Only 200 millicores are available.

Available CPU request quota:

```text
2 cores - 1800m = 200m available
```

The new Pod needs 500m, so admission is denied.

### 4.3 Quota exceeded for memory request

```text
pods "worker-xxxx" is forbidden: exceeded quota: compute-resources,
requested: requests.memory=1Gi, used: requests.memory=7Gi, limited: requests.memory=8Gi
```

Meaning:

Only 1Gi remains. If the rollout needs more than one new Pod, the first Pod might pass and later Pods might fail.

### 4.4 Missing requests/limits

```text
pods "nginx-xxxx" is forbidden: failed quota: compute-resources:
must specify requests.cpu for: nginx; requests.memory for: nginx
```

Meaning:

The namespace has a quota for `requests.cpu` and/or `requests.memory`. Every incoming container must explicitly set those requests unless a `LimitRange` injects defaults.

### 4.5 LimitRange default unexpectedly consumes quota

A Deployment has no resources in YAML:

```yaml
containers:
- name: app
  image: nginx
```

But a namespace `LimitRange` injects default values:

```yaml
defaultRequest:
  cpu: 500m
  memory: 512Mi
default:
  cpu: 1
  memory: 1Gi
```

A 5-replica Deployment silently consumes:

```text
requests.cpu    5 × 500m = 2500m
requests.memory 5 × 512Mi = 2560Mi
limits.cpu      5 × 1 = 5 cores
limits.memory   5 × 1Gi = 5Gi
```

This surprises teams that expect “small nginx Pod” behavior.

### 4.6 Object count quota blocks non-Pod resources

```text
secrets "app-token" is forbidden: exceeded quota: object-counts,
requested: secrets=1, used: secrets=20, limited: secrets=20
```

The application may fail before Pod creation if Helm or an Operator tries to create extra Secrets, ConfigMaps, Services, Routes, PVCs, or ServiceAccounts.

### 4.7 PVC or storage quota blocks deployment

```text
persistentvolumeclaims "mysql-data" is forbidden: exceeded quota: storage-consumption,
requested: requests.storage=20Gi, used: requests.storage=90Gi, limited: requests.storage=100Gi
```

If the workload depends on a PVC, the Deployment may be created but Pods fail or remain blocked because the claim cannot be created.

## 5. First 5-Minute Triage Runbook

Set variables:

```bash
NS=<project-name>
APP=<deployment-name>
```

### Step 1: Check Deployment state

```bash
oc get deploy -n $NS
oc describe deploy $APP -n $NS
```

Look for:

```text
Available      False
Progressing    True/False
ReplicaFailure True
```

`ReplicaFailure=True` often points to quota, SCC, image pull, or admission errors.

### Step 2: Check ReplicaSet events

```bash
oc get rs -n $NS
oc describe rs -n $NS -l app=$APP
```

If labels are unknown:

```bash
oc get rs -n $NS --sort-by=.metadata.creationTimestamp
oc describe rs <replicaset-name> -n $NS
```

Find event messages like:

```text
FailedCreate
Error creating: pods "..." is forbidden: exceeded quota
```

This is usually the smoking gun.

### Step 3: Check namespace events sorted by time

```bash
oc get events -n $NS --sort-by=.lastTimestamp
```

For newer clusters, also try:

```bash
oc get events -n $NS --sort-by=.metadata.creationTimestamp
```

Filter quota messages:

```bash
oc get events -n $NS --sort-by=.lastTimestamp | grep -iE 'quota|exceeded|forbidden|failedcreate|must specify'
```

### Step 4: List quotas

```bash
oc get resourcequota -n $NS
oc describe resourcequota -n $NS
```

Short form:

```bash
oc get quota -n $NS
oc describe quota -n $NS
```

Focus on columns:

```text
Resource            Used    Hard
requests.cpu        1900m   2
requests.memory     3584Mi  4Gi
limits.cpu          4       4
limits.memory       8Gi     8Gi
pods                10      10
persistentvolumeclaims 4    4
```

### Step 5: Check cluster-wide quota applied to the project

OpenShift can apply quotas across multiple projects with `ClusterResourceQuota`.

As a project admin:

```bash
oc describe appliedclusterresourcequota -n $NS
```

As cluster-admin:

```bash
oc get clusterresourcequota
oc describe clusterresourcequota <name>
```

Do not stop at namespace `ResourceQuota`. The project may be limited by both project quota and cluster resource quota.

### Step 6: Check LimitRange

```bash
oc get limitrange -n $NS
oc describe limitrange -n $NS
```

Look for:

```text
Default Request
Default Limit
Min
Max
Max Limit/Request Ratio
```

A LimitRange can inject defaults or reject Pods that exceed min/max rules.

### Step 7: Check actual Pods and consumers

```bash
oc get pods -n $NS
oc get pods -n $NS --field-selector=status.phase!=Succeeded,status.phase!=Failed
```

Count non-terminal Pods:

```bash
oc get pods -n $NS --field-selector=status.phase!=Succeeded,status.phase!=Failed --no-headers | wc -l
```

Find old or unnecessary Pods:

```bash
oc get pods -n $NS --sort-by=.metadata.creationTimestamp
```

### Step 8: Compare requested new Pod resources

```bash
oc get deploy $APP -n $NS -o yaml | sed -n '/resources:/,/imagePullPolicy/p'
```

Better with `yq` if available:

```bash
oc get deploy $APP -n $NS -o yaml | yq '.spec.template.spec.containers[].resources'
```

Without `yq`, use JSONPath:

```bash
oc get deploy $APP -n $NS -o jsonpath='{range .spec.template.spec.containers[*]}{.name}{"\n"}{.resources}{"\n\n"}{end}'
```

```text
Deployment not creating Pods
        |
        v

        |
        +--> No quota message?
        |       Check SCC, image pull, scheduler, node, network, webhook, operator
        |

                |

```

## 7. Deep Dive: Requests, Limits, Quota, and Scheduling

### 7.1 Requests

Requests are used by the scheduler and quota accounting.

Example:

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
```

If replicas are 4:

```text
Total CPU request    = 4 × 250m = 1000m = 1 core
Total memory request = 4 × 256Mi = 1024Mi = 1Gi
```

If quota hard limit is:

```text
requests.cpu: 1
requests.memory: 1Gi
```

Then the workload uses the entire quota. Scaling to 5 replicas fails.

### 7.2 Limits

Limits are maximum allowed runtime consumption and are also quota-accounted if quota tracks `limits.cpu` or `limits.memory`.

Example:

```yaml
resources:
  limits:
    cpu: 1
    memory: 1Gi
```

A 4-replica app consumes:

```text
limits.cpu: 4
limits.memory: 4Gi
```

Even if requests are low, limits can block admission.

### 7.3 CPU units

```text
1000m = 1 CPU core
500m  = 0.5 CPU core
250m  = 0.25 CPU core
```

### 7.4 Memory units

Prefer binary units:

```text
Mi = mebibytes
Gi = gibibytes
```

Common mistakes:

```yaml
memory: 512m   # wrong intention: this is milli-bytes style and not 512Mi
memory: 512Mi  # correct for 512 mebibytes
```

### 7.5 Why quota says `memory` and `requests.memory` are similar

In Kubernetes/OpenShift quota accounting, `memory` and `requests.memory` are commonly treated as equivalent quota resource names for memory requests. Same for `cpu` and `requests.cpu`.

## 8. Rollout Strategy Can Trigger Quota Failures

A very common production case:

```yaml
replicas: 10
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 25%
```

During rollout, the Deployment may create extra Pods above steady-state replica count.

If replicas are 10 and `maxSurge` is 25%, OpenShift/Kubernetes may temporarily create up to 13 Pods.

If quota allows exactly 10 Pods, rollout can fail even though the steady-state app uses only 10 Pods.

### Fix option 1: Temporarily increase quota

```bash
oc patch quota compute-resources -n $NS --type=merge \
  -p '{"spec":{"hard":{"pods":"13"}}}'
```

### Fix option 2: Reduce maxSurge

```bash
oc patch deploy $APP -n $NS --type=merge -p \
'{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'
```

This allows rolling replacement without exceeding Pod count quota, but rollout may be slower and less available.

### Fix option 3: Scale down temporarily

```bash
oc scale deploy $APP -n $NS --replicas=8
oc rollout restart deploy/$APP -n $NS
```

Use this carefully in production because it reduces capacity.

## 9. HPA Can Hit Quota During Scale-Up

Horizontal Pod Autoscaler may try to scale from 3 to 8 replicas, but quota may allow only 5 Pods or may not have enough CPU/memory request quota.

Check HPA:

```bash
oc get hpa -n $NS
oc describe hpa <hpa-name> -n $NS
```

Check target Deployment:

```bash
oc get deploy $APP -n $NS -o jsonpath='{.spec.replicas}{"\n"}'
oc get deploy $APP -n $NS -o yaml | grep -A20 resources:
```

Common HPA + quota failure pattern:

```text
HPA desired replicas: 8
Current replicas: 5
Quota pods hard: 5
Result: scale-up blocked by quota
```

Recommended production fix:

- Align `ResourceQuota` with HPA `maxReplicas`.
- Include rollout surge headroom.
- Ensure every container has CPU/memory requests, because HPA CPU utilization uses requests.

Formula:

```text
Required pod quota = HPA maxReplicas + rollout surge headroom + operational debug headroom
```

Example:

```text
HPA maxReplicas = 8
maxSurge = 2
debug/batch headroom = 1
minimum pods quota = 11
```

## 10. LimitRange Interaction

`LimitRange` and `ResourceQuota` often work together.

### 10.1 ResourceQuota requires requests/limits

If quota tracks `requests.cpu`, `requests.memory`, `limits.cpu`, or `limits.memory`, incoming containers must specify the corresponding values unless defaults are injected.

### 10.2 LimitRange can provide defaults

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-compute
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
```

This prevents missing request/limit admission failures.

### 10.3 LimitRange can also cause quota exhaustion

If defaults are too high, every container consumes quota even if the app does not need that much.

Example:

```text
Default request = 500m CPU / 512Mi memory
10 Pods = 5 CPU / 5Gi request quota
```

For a small web app, this may be wasteful.

### 10.4 Check generated Pod spec after admission

If a Pod was admitted, inspect actual resources:

```bash
oc get pod <pod> -n $NS -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{.resources}{"\n\n"}{end}'
```

If Pod was rejected and never created, inspect Deployment spec and LimitRange.

## 11. ClusterResourceQuota: The Hidden Quota

OpenShift supports `ClusterResourceQuota`, which applies quota across multiple projects selected by labels or annotations.

This can confuse teams because:

```bash
oc describe quota -n app1
```

may look fine, but:

```bash
oc describe appliedclusterresourcequota -n app1
```

shows exhausted quota across several projects.

Example scenario:

```text
Team A has projects:
- app-dev
- app-test
- app-prod

ClusterResourceQuota for Team A:
pods: 30
requests.cpu: 20
requests.memory: 80Gi

app-dev uses 20 Pods
app-test uses 8 Pods
app-prod tries to deploy 5 Pods
Total would be 33 Pods, so app-prod fails.
```

Troubleshooting commands:

```bash
oc describe appliedclusterresourcequota -n $NS
oc get clusterresourcequota
oc describe clusterresourcequota <name>
```

Find selected projects:

```bash
oc get ns --show-labels
oc get ns -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.labels}{"\t"}{.metadata.annotations.openshift\.io/requester}{"\n"}{end}'
```

## 13. Practical Lab: Reproduce ResourceQuota Blocking Deployment

### 13.1 Create project

```bash
oc new-project quota-demo
```

### 13.2 Create quota

```bash
cat <<'EOFQ' | oc apply -f -
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: quota-demo
spec:
  hard:
    pods: "2"
    requests.cpu: "500m"
    requests.memory: "512Mi"
    limits.cpu: "1"
    limits.memory: "1Gi"
EOFQ
```

### 13.3 Create LimitRange defaults

```bash
cat <<'EOFL' | oc apply -f -
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: quota-demo
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 250m
      memory: 256Mi
    default:
      cpu: 500m
      memory: 512Mi
EOFL
```

### 13.4 Create Deployment with 3 replicas

```bash
cat <<'EOFD' | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: quota-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/nginx-120
        ports:
        - containerPort: 8080
EOFD
```

Expected result:

- Deployment object is created.
- Only 2 Pods can be created because quota allows 2 Pods and 500m CPU request total.
- Third Pod fails admission.

### 13.5 Confirm failure

```bash
oc get deploy,pods -n quota-demo
oc describe rs -n quota-demo
oc describe quota compute-quota -n quota-demo
oc get events -n quota-demo --sort-by=.lastTimestamp
```

### 13.6 Fix by reducing replicas

```bash
oc scale deploy web -n quota-demo --replicas=2
```

### 13.7 Fix by increasing quota

```bash
oc patch quota compute-quota -n quota-demo --type=merge -p \
'{"spec":{"hard":{"pods":"3","requests.cpu":"750m","requests.memory":"768Mi","limits.cpu":"1500m","limits.memory":"1536Mi"}}}'
```

### 13.8 Verify

```bash
oc rollout status deploy/web -n quota-demo
oc get pods -n quota-demo
oc describe quota compute-quota -n quota-demo
```

## 14. Fix Strategies by Scenario

### Scenario A: Pod count quota exhausted

Diagnosis:

```bash
oc describe quota -n $NS | grep -E '^ *pods|Resource|Used|Hard'
oc get pods -n $NS --field-selector=status.phase!=Succeeded,status.phase!=Failed
```

Fix options:

```bash
# Reduce replicas
oc scale deploy $APP -n $NS --replicas=<lower-number>

# Cleanup old completed pods if they are standalone and safe
oc delete pod -n $NS --field-selector=status.phase=Succeeded

# Increase pod quota
oc patch quota <quota-name> -n $NS --type=merge -p '{"spec":{"hard":{"pods":"<new-limit>"}}}'
```

Production recommendation:

Do not set Pod quota equal to normal replica count. Add headroom for rollouts, HPA, jobs, debug Pods, and operator/helper Pods.

---

### Scenario B: CPU request quota exhausted

Diagnosis:

```bash
oc describe quota -n $NS | grep -E 'requests.cpu|cpu|Resource|Used|Hard'
oc get deploy $APP -n $NS -o yaml | grep -A10 requests:
```

Fix options:

```bash
# Lower app CPU request after performance validation
oc set resources deploy/$APP -n $NS --requests=cpu=200m,memory=256Mi

# Scale down
oc scale deploy/$APP -n $NS --replicas=<lower-number>

# Increase quota
oc patch quota <quota-name> -n $NS --type=merge -p '{"spec":{"hard":{"requests.cpu":"4"}}}'
```

Senior note:

Lowering requests can allow admission but may cause scheduling density issues or runtime contention. Validate against metrics and SLOs.

---

### Scenario C: Memory request quota exhausted

Diagnosis:

```bash
oc describe quota -n $NS | grep -E 'requests.memory|memory|Resource|Used|Hard'
oc adm top pods -n $NS 2>/dev/null || true
```

Fix options:

```bash
oc set resources deploy/$APP -n $NS --requests=memory=256Mi
oc patch quota <quota-name> -n $NS --type=merge -p '{"spec":{"hard":{"requests.memory":"8Gi"}}}'
```

Senior note:

Do not blindly reduce memory request below steady-state working set. If memory limit is too low, the app may later enter `OOMKilled` / `CrashLoopBackOff`.

---

### Scenario D: Missing requests/limits

Diagnosis:

```bash
oc get events -n $NS --sort-by=.lastTimestamp | grep -i 'must specify'
oc describe quota -n $NS
oc describe limitrange -n $NS
```

Fix option 1: Add resources to Deployment

```bash
oc set resources deploy/$APP -n $NS \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi
```

Fix option 2: Create a LimitRange default

```bash
cat <<EOF | oc apply -f -
apiVersion: v1
kind: LimitRange
metadata:
  name: default-compute
  namespace: $NS
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
EOF
```

Senior recommendation:

For platform consistency, use both:

- `ResourceQuota` for project/team budget
- `LimitRange` for default/min/max per container
- Application-specific resources for production workloads

---

### Scenario E: Rollout blocked by maxSurge

Diagnosis:

```bash
oc get deploy $APP -n $NS -o jsonpath='{.spec.replicas}{"\n"}{.spec.strategy}{"\n"}'
oc describe quota -n $NS | grep pods
oc describe rs -n $NS | grep -i quota -A3 -B3
```

Fix options:

```bash
# Avoid extra surge pods
oc patch deploy $APP -n $NS --type=merge -p \
'{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'

# Or increase pod quota with rollout headroom
oc patch quota <quota-name> -n $NS --type=merge -p '{"spec":{"hard":{"pods":"<replicas-plus-surge>"}}}'
```

---

### Scenario F: ClusterResourceQuota exhausted

Diagnosis:

```bash
oc describe appliedclusterresourcequota -n $NS
oc get clusterresourcequota
oc describe clusterresourcequota <name>
```

Fix options:

- Free quota in another selected project.
- Move project labels/annotations only if policy allows.
- Increase `ClusterResourceQuota` after capacity review.
- Split team quota into environment-specific quotas if one environment starves another.

Example patch:

```bash
oc patch clusterresourcequota <name> --type=merge -p \
'{"spec":{"quota":{"hard":{"pods":"50","requests.cpu":"20","requests.memory":"80Gi"}}}}'
```

---

### Scenario G: Storage quota exhausted

Diagnosis:

```bash
oc describe quota -n $NS | grep -E 'persistentvolumeclaims|requests.storage|storageclass'
oc get pvc -n $NS
```

Fix options:

```bash
# Delete unused PVC only after data owner approval
oc delete pvc <unused-pvc> -n $NS

# Reduce requested PVC size in Helm values or manifest before creation

# Increase storage quota
oc patch quota <quota-name> -n $NS --type=merge -p \
'{"spec":{"hard":{"persistentvolumeclaims":"10","requests.storage":"200Gi"}}}'
```

Senior warning:

Deleting PVCs can delete application data depending on StorageClass reclaim policy and PV lifecycle. Always confirm before deleting.

## 15. Production Checklist Before Increasing Quota

Before raising quota, answer these questions:

1. Is the application right-sized?
2. Are requests based on actual metrics or copy-paste defaults?
3. Is HPA `maxReplicas` aligned with quota?
4. Does rolling update need surge headroom?
5. Are completed Jobs, old Pods, old Secrets, and unused PVCs cleaned up?
6. Is quota exhausted by another project through `ClusterResourceQuota`?
7. Does the namespace have a high default `LimitRange`?
8. Does increasing namespace quota exceed actual cluster capacity?
9. Will this affect other tenants?
10. Should the fix be temporary or permanent?

## 16. Right-Sizing Formulae

### 16.1 Required CPU request quota

```text
Required requests.cpu = replicas × per_pod_cpu_request
```

With HPA:

```text
Required requests.cpu = hpa_max_replicas × per_pod_cpu_request
```

With rollout surge:

```text
Required requests.cpu = (hpa_max_replicas + surge_pods) × per_pod_cpu_request
```

### 16.2 Required memory request quota

```text
Required requests.memory = replicas × per_pod_memory_request
```

With HPA and rollout:

```text
Required requests.memory = (hpa_max_replicas + surge_pods) × per_pod_memory_request
```

### 16.3 Required pod quota

```text
Required pods = app_replicas + rollout_surge + jobs + debug_headroom + operator_helper_pods
```

### 16.4 Required object count quota for Helm apps

Helm charts often create:

```text
1 Deployment
1 Service
1 Route/Ingress
1 ServiceAccount
1 ConfigMap
1 Secret
1 PVC
1 or more Pods
1 or more ReplicaSets
Hooks as Jobs/Pods
```

For Helm-heavy namespaces, object count quotas must include release metadata Secrets/ConfigMaps and hook Jobs.

## 18. Common False Leads

### False lead 1: “Pods are Pending, so it must be node capacity”

If Pods are not created at all, it is not scheduler capacity. Check ReplicaSet events.

### False lead 2: “Deployment exists, so quota is not the issue”

Deployment object creation may succeed. Pod creation can still fail.

### False lead 3: “CPU usage is low, so quota should not block”

Quota uses declared requests/limits, not live CPU usage.

### False lead 4: “Deleting a Pod should instantly free quota”

Quota usage is decremented after deletion and quota recalculation. There can be a delay.

### False lead 5: “No namespace quota means no quota problem”

OpenShift `ClusterResourceQuota` may still apply through `AppliedClusterResourceQuota`.

### False lead 6: “Only Pods matter”

Object count quotas for Secrets, ConfigMaps, Services, PVCs, and ReplicaSets can block applications before Pods appear.

## 19. Example Incident Walkthrough

### Situation

A developer reports:

```text
I deployed payment-api but no new pods are coming up.
```

### Check Deployment

```bash
NS=payments
APP=payment-api
oc get deploy $APP -n $NS
```

Output:

```text
NAME          READY   UP-TO-DATE   AVAILABLE   AGE
payment-api   3/5     3            3           12m
```

### Check ReplicaSet

```bash
oc describe rs -n $NS -l app=payment-api
```

Event:

```text
Warning FailedCreate  replicaset-controller  Error creating: pods "payment-api-abc" is forbidden: exceeded quota: compute-resources, requested: requests.cpu=500m, used: requests.cpu=3500m, limited: requests.cpu=4
```

### Interpret

Available CPU request quota:

```text
4 cores - 3500m = 500m
```

Only one more Pod can be admitted. Deployment wants two more Pods. Also rollout surge might need additional temporary Pods.

### Check quota

```bash
oc describe quota compute-resources -n payments
```

Output:

```text
Resource          Used    Hard
requests.cpu      3500m   4
requests.memory   7Gi     8Gi
pods              9       10
```

### Check Deployment resources

```bash
oc get deploy payment-api -n payments -o jsonpath='{range .spec.template.spec.containers[*]}{.name}{" "}{.resources.requests}{"\n"}{end}'
```

Output:

```text
payment-api {"cpu":"500m","memory":"1Gi"}
```

### Fix decision

Options:

1. Increase CPU request quota to at least 5 cores.
2. Reduce replicas.
3. Reduce CPU request after validating metrics.
4. Change rollout strategy to avoid surge.
5. Cleanup old workloads.

Production-safe fix after approval:

```bash
oc patch quota compute-resources -n payments --type=merge -p \
'{"spec":{"hard":{"requests.cpu":"5","requests.memory":"10Gi","pods":"12"}}}'
```

Verify:

```bash
oc rollout status deploy/payment-api -n payments
oc get pods -n payments -l app=payment-api
oc describe quota compute-resources -n payments
```

Post-incident action:

- Add quota alert at 80%.
- Review HPA max replicas.
- Add rollout surge headroom to quota policy.
- Document per-environment quota sizing.

```yaml
apiVersion: v1
```

```yaml
  name: default-container-resources
spec:

      memory: 128Mi
    default:

      memory: 32Mi
```

## 21. Safe Remediation Patterns

### 21.1 Temporary emergency quota increase

Use when production deployment is blocked and capacity exists.

```bash
oc patch quota compute-resources -n $NS --type=merge -p \
'{"spec":{"hard":{"pods":"30","requests.cpu":"12","requests.memory":"48Gi"}}}'
```

Record:

```text
Who approved?
Why needed?
Old quota?
New quota?
Rollback date?
Capacity impact?
```

### 21.2 Reduce rollout surge

Use when quota equals steady-state replica count.

```bash
oc patch deploy $APP -n $NS --type=merge -p \
'{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'
```

### 21.3 Reduce over-sized requests

Use only after checking real usage.

```bash
oc adm top pods -n $NS
oc set resources deploy/$APP -n $NS --requests=cpu=200m,memory=256Mi --limits=cpu=1,memory=1Gi
```

### 21.4 Cleanup old workload objects

```bash
oc get jobs,cronjobs,pods,pvc,secrets,configmaps -n $NS
```

Delete only confirmed-unused resources.

### 21.5 Add LimitRange defaults

Use when many apps are blocked by missing requests/limits.

```bash
oc apply -f limitrange-defaults.yaml -n $NS
```

## 22. What Not To Do

Do not:

```bash
systemctl restart kubelet
systemctl restart crio
oc delete pod --all -n production
oc adm drain <node>
oc delete quota <quota-name> -n production
oc patch finalizers blindly
```

Unless you have a separate confirmed reason.

Why:

- ResourceQuota is API admission, not node runtime.
- Restarting nodes does not change namespace quota.
- Deleting quota removes tenant guardrails.
- Force-deleting resources can cause data loss or controller inconsistency.

## 24. Interview-Level Explanation

A strong answer:

> ResourceQuota is enforced at API admission level. In OpenShift, a Deployment may be accepted, but the ReplicaSet may fail to create Pods if creating those Pods would exceed project or cluster resource quota. I troubleshoot it by reading Deployment and ReplicaSet events, then comparing `oc describe quota` Used versus Hard. I also check `AppliedClusterResourceQuota` because OpenShift can enforce quota across multiple projects. If the quota tracks CPU or memory requests/limits, every container must define those resources or get defaults from LimitRange. Fix depends on the exhausted resource: reduce replicas or resource requests, clean up unused objects, adjust rollout surge or HPA max replicas, add LimitRange defaults, or increase quota after validating cluster capacity.

## 26. Preventive Design Standards

For each production namespace/project:

1. Define a ResourceQuota.
2. Define a LimitRange.
3. Set CPU and memory requests for every container.
4. Align quota with HPA max replicas.
5. Add rollout surge headroom.
6. Add debug/maintenance headroom.
7. Monitor quota usage at 70%, 80%, and 90%.
8. Use separate quotas for dev, test, and prod.
9. Avoid one huge ClusterResourceQuota selecting too many active projects.
10. Review quota monthly against real utilization.

Recommended structure:

```text
Project quota = steady-state workload + HPA headroom + rollout headroom + operational headroom
```

Example:

```text
App steady state: 6 Pods × 500m CPU × 512Mi memory
HPA max: 10 Pods
Rollout surge: 2 Pods
Debug headroom: 1 Pod

Quota minimum:
pods: 13
requests.cpu: 13 × 500m = 6500m
requests.memory: 13 × 512Mi = 6656Mi
```

## 28. Final Senior Admin Summary

When ResourceQuota blocks deployment, think admission control, not node failure.

The best troubleshooting order is:

```text
Deployment status -> ReplicaSet events -> namespace events -> ResourceQuota -> AppliedClusterResourceQuota -> LimitRange -> workload requests/limits -> rollout/HPA behavior -> cleanup or quota change
```

The best fix is not always “increase quota.” Sometimes the correct fix is:

- add missing requests/limits,
- reduce inflated LimitRange defaults,
- reduce rollout surge,
- align HPA with quota,
- delete unused objects,
- clean completed jobs,
- resize application requests,
- or split a bad ClusterResourceQuota design.

A 10-year OpenShift admin treats quota as a capacity contract between platform and application teams. If that contract is too tight, deployments fail. If it is too loose, tenants can exhaust the cluster. The skill is to size it with enough production headroom while keeping the cluster protected.
