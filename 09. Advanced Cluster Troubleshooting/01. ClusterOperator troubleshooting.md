## 1. Purpose of ClusterOperator Troubleshooting

ClusterOperator troubleshooting is the process of diagnosing why one or more core OpenShift platform components are not healthy. In OpenShift 4, most platform components are managed by operators. These include authentication, ingress, DNS, networking, monitoring, image registry, API servers, machine configuration, storage, and other control-plane or infrastructure functions.

When a cluster has problems, a senior OpenShift administrator normally starts with:

```bash
oc get co
oc get clusterversion
oc get nodes
oc get mcp
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp
```

`oc get co` is one of the fastest ways to understand whether the platform itself is healthy.

ClusterOperator troubleshooting helps answer questions like:

- Is the control plane healthy?
- Is the cluster still upgrading?
- Which operator is degraded?
- Is the issue in the operator pod or the operand it manages?
- Is the problem caused by nodes, certificates, image pulls, proxy, DNS, cloud credentials, storage, or networking?
- Is the cluster safe to upgrade?
- Which logs and resources are needed before opening a Red Hat support case?

A ClusterOperator problem is often not the root cause by itself. It is usually a symptom reported by a controller that cannot reconcile the expected platform state.

## 2. What Is a ClusterOperator?

A `ClusterOperator` is a cluster-scoped OpenShift API object that reports the health and version of a core or optional OpenShift component managed by the Cluster Version Operator.

Short name:

```bash
co
```

Full resource:

```bash
clusteroperators.config.openshift.io
```

Examples:

```bash
oc get clusteroperators
oc get co
oc get co authentication
oc describe co ingress
oc get co network -o yaml
```

A ClusterOperator object is primarily a **status reporting object**. It tells you the state of the operator and the components it manages.

Typical ClusterOperators include:

```text
authentication
baremetal
cloud-controller-manager
cloud-credential
cluster-autoscaler
config-operator
console
control-plane-machine-set
dns
etcd
image-registry
ingress
insights
kube-apiserver
kube-controller-manager
kube-scheduler
kube-storage-version-migrator
machine-api
machine-approver
machine-config
marketplace
monitoring
network
node-tuning
openshift-apiserver
openshift-controller-manager
operator-lifecycle-manager
service-ca
storage
```

The exact list depends on OpenShift version, platform type, installation method, enabled capabilities, and optional components.

Important point:

> `ClusterOperator` is not the same thing as a user-installed Operator from OperatorHub.

ClusterOperators are platform components. They are part of the OpenShift release payload and are normally managed by the Cluster Version Operator, not by an OLM `Subscription`.

## 3. ClusterOperator vs OLM Operator

This distinction is very important in production and in exams.

| Item | ClusterOperator | OLM/Application Operator |
|---|---|---|
| Managed by | Cluster Version Operator | Operator Lifecycle Manager |
| Resource health object | `ClusterOperator` | `CSV`, `Subscription`, `InstallPlan`, `OperatorCondition` |
| Scope | Core OpenShift platform | Application/platform add-on workloads |
| Upgrade source | OpenShift release payload | CatalogSource / OperatorHub index |
| Example | `authentication`, `ingress`, `network` | `file-integrity-operator`, `odf-operator`, `cert-manager` |
| Troubleshoot with | `oc get co`, operator namespace, CVO logs | `oc get csv`, `oc get sub`, `oc get installplan` |
| Has OLM Subscription? | Normally no | Yes |

Do not troubleshoot a degraded ClusterOperator by looking for a `Subscription` unless it is specifically the OLM stack itself, such as `operator-lifecycle-manager` or marketplace-related components.

Wrong approach:

```bash
oc get subscription -A | grep authentication
```

Better approach:

```bash
oc get co authentication -o yaml
oc get pods -n openshift-authentication
oc get pods -n openshift-authentication-operator
```

## 4. Cluster Version Operator Relationship

The Cluster Version Operator, or CVO, manages the OpenShift release payload. The release payload contains manifests and images for platform operators and operands. The CVO applies those manifests and tracks whether each ClusterOperator reaches the desired version and health.

Check CVO state:

```bash
oc get clusterversion
oc get clusterversion version -o yaml
oc describe clusterversion version
```

Check CVO pod:

```bash
oc get pods -n openshift-cluster-version
oc logs -n openshift-cluster-version deploy/cluster-version-operator
```

During upgrades, the CVO waits for operators to become healthy before continuing to later stages. A blocked ClusterOperator can block an upgrade.

A healthy upgrade usually requires:

- ClusterOperators `Available=True`
- ClusterOperators `Degraded=False`
- ClusterOperators reporting the desired version in their `ClusterOperator` status

A senior administrator uses `ClusterOperator` status and `ClusterVersion` status together. `oc get co` tells you which component is unhealthy. `oc get clusterversion` tells you whether the entire cluster update flow is blocked, failing, progressing, or completed.

## 5. ClusterOperator Status Anatomy

View full status:

```bash
oc get co <name> -o yaml
```

Important fields:

```yaml
status:
  conditions:
  - type: Available
    status: "True"
    reason: AsExpected
    message: ...
    lastTransitionTime: ...
  - type: Progressing
    status: "False"
    reason: AsExpected
    message: ...
    lastTransitionTime: ...
  - type: Degraded
    status: "False"
    reason: AsExpected
    message: ...
    lastTransitionTime: ...
  - type: Upgradeable
    status: "True"
    reason: AsExpected
    message: ...
    lastTransitionTime: ...
  relatedObjects:
  - group: operator.openshift.io
    resource: ingresscontrollers
    namespace: openshift-ingress-operator
    name: default
  versions:
  - name: operator
    version: 4.x.y
```

### 5.1 `status.conditions`

This is the most important field for health investigation.

Every condition has:

| Field | Meaning |
|---|---|
| `type` | Health aspect, such as `Available`, `Progressing`, `Degraded`, `Upgradeable` |
| `status` | `True`, `False`, or `Unknown` |
| `reason` | Short machine-readable reason, usually CamelCase |
| `message` | Human-readable explanation; often the best first clue |
| `lastTransitionTime` | Time when that condition last changed status |

Always read the `message`. Many administrators only look at the table output and miss the actual error message.

### 5.2 `status.relatedObjects`

This tells you which objects are connected to the operator. It often points to:

- Operator namespace
- Operand namespace
- Config CR
- Deployment
- DaemonSet
- API resource owned by the operator

Example use:

```bash
oc get co ingress -o jsonpath='{range .status.relatedObjects[*]}{.group}{"\t"}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

### 5.3 `status.versions`

This tells you which operator and operand versions are reported as available.

Example:

```bash
oc get co kube-apiserver -o jsonpath='{.status.versions}' | jq
```

During upgrades, version mismatch can indicate that an operator has not completed rollout.

### 5.4 `status.extension`

Some operators expose extra status under `status.extension`. This is operator-specific and can contain useful internal status.

Inspect it:

```bash
oc get co <operator> -o jsonpath='{.status.extension}' | jq
```

## 6. Understanding `oc get co`

Basic command:

```bash
oc get co
```

Example output:

```text
NAME                    VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
authentication          4.16.12   True        False         False      10d
console                 4.16.12   False       True          True       8m      DeploymentAvailable: 0 replicas available...
ingress                 4.16.12   True        False         True       2h      The "default" ingress controller reports Degraded=True...
machine-config          4.16.12   True        True          False      1h      Working towards 4.16.12: 2 nodes are updating
network                 4.16.12   True        False         False      10d
```

Interpretation:

| Pattern | Meaning | Severity |
|---|---|---|
| `Available=True`, `Progressing=False`, `Degraded=False` | Healthy | Normal |
| `Available=True`, `Progressing=True`, `Degraded=False` | Updating or reconciling | Watch |
| `Available=True`, `Progressing=False`, `Degraded=True` | Functioning but has detected issue | Investigate |
| `Available=False`, `Degraded=True` | Component unavailable and unhealthy | Critical |
| `Available=Unknown` | Operator cannot determine status | Critical/Investigate |
| `Upgradeable=False` | Cluster might be blocked from minor update | Maintenance concern |

The `SINCE` column matters. A condition that has been degraded for 30 seconds during a rollout is different from one degraded for 3 days.

Useful watch command:

```bash
watch -n 5 'oc get co'
```

Better watch during upgrade:

```bash
watch -n 10 'oc get clusterversion; echo; oc get co'
```

## 7. Important Conditions: Available, Progressing, Degraded, Upgradeable

### 7.1 `Available`

`Available=True` means the operator reports that the component it manages is available enough to serve its expected function.

Examples:

- `ingress` available means router/ingress components are available enough to serve routes.
- `dns` available means DNS components are available enough to answer cluster DNS.
- `authentication` available means OAuth/authentication stack is available.

`Available=False` is usually high priority because it can indicate user-visible or control-plane impact.

Check:

```bash
oc get co <name> -o jsonpath='{range .status.conditions[?(@.type=="Available")]}{.status}{"\n"}{.reason}{"\n"}{.message}{"\n"}{.lastTransitionTime}{"\n"}{end}'
```

### 7.2 `Progressing`

`Progressing=True` means the operator is actively working toward a desired state. This can be normal during:

- Cluster installation
- Cluster upgrade
- Configuration change
- Operand rollout
- Node update
- Certificate rotation
- Deployment rollout

It becomes suspicious when it remains true for too long without progress.

Check progress details:

```bash
oc get co <name> -o yaml | yq '.status.conditions[] | select(.type=="Progressing")'
```

Without `yq`:

```bash
oc get co <name> -o jsonpath='{range .status.conditions[?(@.type=="Progressing")]}{.status}{"\n"}{.reason}{"\n"}{.message}{"\n"}{end}'
```

### 7.3 `Degraded`

`Degraded=True` means the operator detected a problem in itself or in one of its managed components.

Important nuance:

`Degraded=True` does not always mean outage. If `Available=True`, the component might still be serving traffic, but the operator has detected a condition that needs attention.

Examples:

- A router deployment has enough replicas, but one replica is failing.
- An operator cannot update a secondary resource.
- A certificate is nearing expiration.
- A node cannot apply a MachineConfig.
- A storage driver operand is unhealthy.

Check:

```bash
oc get co <name> -o jsonpath='{range .status.conditions[?(@.type=="Degraded")]}{.status}{"\n"}{.reason}{"\n"}{.message}{"\n"}{end}'
```

### 7.4 `Upgradeable`

`Upgradeable=False` means the operator is reporting that the cluster should not perform certain updates, usually minor version updates, until an administrator resolves a condition.

Examples:

- Deprecated API usage must be removed.
- Manual acknowledgment is required before upgrading to a new minor version.
- Storage or platform prerequisites are not met.
- An operator-specific compatibility check failed.

Check all Upgradeable messages:

```bash
oc get co -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.conditions[?(@.type=="Upgradeable")]}{.status}{"\t"}{.reason}{"\t"}{.message}{end}{"\n"}{end}'
```

## 8. Senior Troubleshooting Mindset

A junior admin asks: “Which operator is red?”

A senior admin asks:

1. What changed recently?
2. Is the issue in the operator or the operand?
3. Is the problem cluster-wide or isolated to one node/namespace/component?
4. Is the component unavailable, degraded but available, or just progressing?
5. Is the issue blocking an upgrade?
6. Is there an external dependency: DNS, proxy, pull secret, registry, cloud API, load balancer, storage, or identity provider?
7. Is there a known safe remediation, or should evidence be collected before touching anything?

ClusterOperators are reconciliation controllers. Most failures happen because the desired state cannot be achieved.

Typical desired state blockers:

- Pods cannot schedule.
- Images cannot pull.
- Certificates or secrets are invalid.
- Admission rejects pods due to SCC/security settings.
- Node is NotReady.
- MachineConfigPool is updating/degraded.
- Network plugin or DNS is broken.
- Cloud provider API is unreachable.
- Proxy or trust bundle is misconfigured.
- API server is overloaded or etcd is unhealthy.
- Manual changes drifted from CVO-managed manifests.

## 9. Golden Troubleshooting Workflow

Use this workflow in almost every ClusterOperator issue.

### Step 1: Capture cluster-level state

```bash
oc get clusterversion
oc get co
oc get nodes
oc get mcp
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp | tail -100
```

### Step 2: Identify the primary failing operator

Do not chase every degraded operator blindly. Some operators degrade because another foundational operator is broken.

Foundation order to check:

1. `etcd`
2. `kube-apiserver`
3. `kube-controller-manager`
4. `kube-scheduler`
5. `network`
6. `dns`
7. `machine-config`
8. `authentication`
9. `ingress`
10. Higher-level components such as `console`, `monitoring`, `image-registry`

Example:

If `network` and `dns` are degraded, and `console` is also degraded, fix `network`/`dns` first. Console might only be a victim.

### Step 3: Read the failing condition message

```bash
oc describe co <name>
oc get co <name> -o yaml
```

Focus on:

```yaml
status.conditions[*].reason
status.conditions[*].message
status.conditions[*].lastTransitionTime
status.relatedObjects
status.versions
```

### Step 4: Locate operator and operand namespaces

Common pattern:

```bash
oc get co <name> -o jsonpath='{range .status.relatedObjects[*]}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

Then inspect namespaces:

```bash
oc get pods -n <operator-namespace>
oc get pods -n <operand-namespace>
oc get deploy,ds,sts -n <namespace>
```

### Step 5: Inspect unhealthy pods

```bash
oc get pods -n <ns>
oc describe pod <pod> -n <ns>
oc logs <pod> -n <ns> --all-containers --previous
oc logs <pod> -n <ns> --all-containers
```

For deployment-based operators:

```bash
oc logs -n <ns> deploy/<operator-deployment> --all-containers
```

For daemonsets:

```bash
oc logs -n <ns> ds/<daemonset> --all-containers
```

### Step 6: Check events and rollout status

```bash
oc get events -n <ns> --sort-by=.lastTimestamp
oc rollout status deploy/<name> -n <ns>
oc rollout status ds/<name> -n <ns>
oc describe deploy/<name> -n <ns>
oc describe ds/<name> -n <ns>
```

### Step 7: Check dependent cluster resources

Depending on the operator:

```bash
oc get nodes
oc get csr
oc get mcp
oc get machines -A
oc get machinesets -A
oc get ingresscontroller -A
oc get dns.operator/default -o yaml
oc get network.operator/cluster -o yaml
oc get authentication.operator/cluster -o yaml
oc get image.config.openshift.io/cluster -o yaml
oc get proxy.config.openshift.io/cluster -o yaml
```

### Step 8: Confirm whether this is an upgrade problem

```bash
oc get clusterversion version -o yaml
oc adm upgrade
oc logs -n openshift-cluster-version deploy/cluster-version-operator
```

### Step 9: Collect evidence before risky remediation

```bash
oc adm must-gather
oc adm inspect clusteroperator/<name>
oc adm inspect ns/<namespace>
```

### Step 10: Remediate safely

Prefer fixing the underlying dependency, not forcing status.

Examples:

- Approve pending CSRs if appropriate.
- Fix node readiness.
- Fix pull secret/registry trust.
- Restore deleted config object.
- Fix proxy CA/trust bundle.
- Restore ingress certificates/secrets.
- Correct unsupported manual changes.
- Let MachineConfigPool finish.

Avoid:

- Editing `ClusterOperator.status`
- Deleting ClusterOperator resources
- Deleting CVO-managed resources without knowing consequences
- Force-upgrading without support guidance
- Patching core deployments permanently outside supported config APIs

## 10. Command Toolkit

### 10.1 List unhealthy ClusterOperators

```bash
oc get co | awk 'NR==1 || $3!="True" || $4!="False" || $5!="False"'
```

### 10.2 Show only degraded operators

```bash
oc get co -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.conditions[?(@.type=="Degraded")]}{.status}{"\t"}{.reason}{"\t"}{.message}{end}{"\n"}{end}' | grep -P '\tTrue\t'
```

### 10.3 Show all condition messages compactly

```bash
for co in $(oc get co -o name); do
  echo "===== $co ====="
  oc get $co -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{"\n"}{.message}{"\n\n"}{end}'
done
```

### 10.4 Show condition transition times

```bash
oc get co -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .status.conditions[*]}{"  "}{.type}{"="}{.status}{" since "}{.lastTransitionTime}{" reason="}{.reason}{"\n"}{end}{"\n"}{end}'
```

### 10.5 Check version mismatches

```bash
oc get co -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.versions[*]}{.name}{"="}{.version}{" "}{end}{"\n"}{end}'
```

### 10.6 Check related objects

```bash
oc get co <name> -o jsonpath='{range .status.relatedObjects[*]}{.group}{"\t"}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

### 10.7 Inspect all resources in operator namespace

```bash
NS=<namespace>
oc get all -n $NS
oc get events -n $NS --sort-by=.lastTimestamp
```

### 10.8 Logs for an operator deployment

```bash
oc logs -n <ns> deploy/<deployment-name> --all-containers --since=1h
```

### 10.9 Previous crashed container logs

```bash
oc logs -n <ns> <pod-name> --all-containers --previous
```

### 10.10 Check API server pressure

```bash
oc get --raw='/readyz?verbose'
oc get --raw='/livez?verbose'
oc get --raw='/healthz?verbose'
```

### 10.11 Check cluster alerts

```bash
oc -n openshift-monitoring exec -c prometheus prometheus-k8s-0 -- promtool query instant http://localhost:9090 'ALERTS{alertstate="firing"}'
```

If direct Prometheus access is not practical, use the web console: **Observe → Alerting**.

## 11. Reading ClusterOperator YAML Properly

Example:

```bash
oc get co ingress -o yaml
```

Do not just look at `Available`, `Progressing`, and `Degraded`. Read the complete `conditions` list.

Example failure:

```yaml
conditions:
- type: Available
  status: "True"
  reason: IngressAvailable
  message: The ingress controller is available.
- type: Progressing
  status: "False"
  reason: AsExpected
- type: Degraded
  status: "True"
  reason: IngressControllerDegraded
  message: 'The "default" ingress controller reports Degraded=True: One or more other status conditions indicate a degraded state: CanaryChecksSucceeding=False'
```

Interpretation:

- Router is available.
- Operator is not rolling out.
- Canary checks are failing.
- Root cause might be route reachability, DNS, router pods, load balancer, network policy, or ingress canary service.

Next commands:

```bash
oc get pods -n openshift-ingress
oc get pods -n openshift-ingress-operator
oc logs -n openshift-ingress-operator deploy/ingress-operator --since=1h
oc get ingresscontroller -n openshift-ingress-operator default -o yaml
oc get route -n openshift-ingress-canary
oc get svc,endpoints -n openshift-ingress-canary
```

## 12. Using `relatedObjects` for Root Cause Analysis

`relatedObjects` is one of the most underused troubleshooting fields.

Example:

```bash
oc get co authentication -o jsonpath='{range .status.relatedObjects[*]}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

Possible output:

```text
namespaces      openshift-authentication
namespaces      openshift-authentication-operator
authentications.operator.openshift.io        cluster
```

This tells you where to look:

```bash
oc get pods -n openshift-authentication
oc get pods -n openshift-authentication-operator
oc get authentication.operator.openshift.io cluster -o yaml
```

Generic helper script:

```bash
CO=<operator-name>
oc get co $CO -o jsonpath='{range .status.relatedObjects[*]}{.group}{"/"}{.resource}{"\t"}{.namespace}{"\t"}{.name}{"\n"}{end}'
```

If `relatedObjects` includes a namespace, always inspect pods and events in that namespace.

```bash
for ns in $(oc get co $CO -o jsonpath='{range .status.relatedObjects[*]}{.namespace}{"\n"}{end}' | sort -u | grep -v '^$'); do
  echo "===== namespace: $ns ====="
  oc get pods -n $ns
  oc get events -n $ns --sort-by=.lastTimestamp | tail -20
done
```

## 13. Finding the Operator Namespace, Pods, and Operands

Most ClusterOperators have two layers:

1. **Operator**: Controller that reconciles desired state.
2. **Operand**: Actual component being managed.

Example with ingress:

| Layer | Namespace | Resource |
|---|---|---|
| Operator | `openshift-ingress-operator` | `deployment/ingress-operator` |
| Operand | `openshift-ingress` | `deployment/router-default` |

Example with authentication:

| Layer | Namespace | Resource |
|---|---|---|
| Operator | `openshift-authentication-operator` | `deployment/authentication-operator` |
| Operand | `openshift-authentication` | `deployment/oauth-openshift` |

Example with DNS:

| Layer | Namespace | Resource |
|---|---|---|
| Operator | `openshift-dns-operator` | `deployment/dns-operator` |
| Operand | `openshift-dns` | `daemonset/dns-default`, `daemonset/node-resolver` |

Example with Machine Config:

| Layer | Namespace | Resource |
|---|---|---|
| Operator | `openshift-machine-config-operator` | MCO deployments |
| Operand | Nodes | MachineConfigDaemon on each node, MachineConfigPools |

Commands:

```bash
oc get pods -n <operator-namespace>
oc get pods -n <operand-namespace>
oc get deploy,ds,sts -n <operator-namespace>
oc get deploy,ds,sts -n <operand-namespace>
```

Always determine whether the operator is unhealthy or whether the operand is unhealthy.

### Operator pod problem example

```text
authentication-operator-xxxx   0/1   CrashLoopBackOff
```

Likely issue:

- Operator container crash
- Bad image pull
- Missing secret/configmap
- Bad RBAC
- Node scheduling problem

### Operand problem example

```text
oauth-openshift-xxxx   0/1   CrashLoopBackOff
```

Likely issue:

- Invalid OAuth config
- Bad identity provider secret
- Bad certificate
- Route/ingress issue
- API dependency issue

## 14. Troubleshooting by Condition Type

### 14.1 `Available=False`

This is often critical.

Workflow:

```bash
CO=<name>
oc describe co $CO
oc get co $CO -o yaml
oc get co $CO -o jsonpath='{range .status.conditions[?(@.type=="Available")]}{.reason}{"\n"}{.message}{"\n"}{end}'
```

Then inspect related namespaces:

```bash
oc get co $CO -o jsonpath='{range .status.relatedObjects[*]}{.namespace}{"\n"}{end}' | sort -u
```

Common root causes:

- Operand deployment has zero available replicas.
- DaemonSet pods are not ready on required nodes.
- Operator cannot reach API dependency.
- Node is NotReady.
- Required certificate/secret missing.
- Image pull failure.
- PVC/storage problem.
- Admission/SCC rejection.
- DNS or network failure.

Commands:

```bash
oc get pods -n <ns>
oc describe pod <bad-pod> -n <ns>
oc logs <bad-pod> -n <ns> --all-containers --previous
oc get events -n <ns> --sort-by=.lastTimestamp
oc get deploy,ds,sts -n <ns>
oc describe deploy/<name> -n <ns>
```

### 14.2 `Progressing=True`

`Progressing=True` can be normal.

Ask:

- Is the cluster installing?
- Is the cluster upgrading?
- Did someone change config recently?
- Are pods rolling out?
- Are MachineConfigPools updating?
- Is it stuck at the same message for a long time?

Commands:

```bash
oc get clusterversion
oc get co <name> -o yaml
oc rollout status deploy/<name> -n <ns>
oc rollout status ds/<name> -n <ns>
oc get mcp
oc describe mcp <pool>
```

Common stuck-progressing root causes:

- Deployment rollout blocked by unavailable pods.
- DaemonSet cannot schedule on some nodes.
- Node drain blocked by PodDisruptionBudget.
- MachineConfigPool stuck updating.
- Image pull blocked.
- New config invalid.
- CVO cannot apply a payload manifest.

### 14.3 `Degraded=True`

Workflow:

```bash
oc get co <name> -o jsonpath='{range .status.conditions[?(@.type=="Degraded")]}{.reason}{"\n"}{.message}{"\n"}{end}'
```

Classify:

| Case | Meaning |
|---|---|
| `Available=True`, `Degraded=True` | Component running but unhealthy condition exists |
| `Available=False`, `Degraded=True` | Component likely down or severely impacted |
| `Progressing=True`, `Degraded=True` | Rollout/update is failing or partially failing |

Common degraded messages point directly to subconditions such as:

- `DeploymentAvailable=False`
- `NodeInstallerDegraded=True`
- `InstallerPodPending`
- `CanaryChecksSucceeding=False`
- `MachineConfigPoolDegraded=True`
- `RouteHealthAvailable=False`
- `StaticPodsDegraded=True`

### 14.4 `Upgradeable=False`

Workflow:

```bash
oc get co -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.conditions[?(@.type=="Upgradeable")]}{.status}{"\t"}{.reason}{"\t"}{.message}{end}{"\n"}{end}' | grep False
```

Read carefully. Do not override blindly.

Common examples:

- Admin acknowledgment needed for minor upgrade.
- Deprecated API usage detected.
- Cluster config incompatible with target release.
- Operator-specific prerequisites missing.

The right fix is usually written in the message.

### 14.5 `Unknown`

`Unknown` means the operator cannot confidently report health.

Common causes:

- Operator pod cannot contact API server.
- Informer/cache sync failure.
- APIService unavailable.
- RBAC or admission problem.
- Severe API latency.
- Network partition.

Commands:

```bash
oc get apiservices | grep -v True
oc get --raw='/readyz?verbose'
oc get endpoints kubernetes -n default
oc logs -n <operator-ns> deploy/<operator> --since=1h
```

## 16. Common Root Causes

### 16.1 Node NotReady

Symptoms:

- Multiple ClusterOperators degraded.
- DaemonSet operands unavailable.
- MachineConfigPool degraded.
- Network/DNS degraded.

Commands:

```bash
oc get nodes
oc describe node <node>
oc adm node-logs <node> -u kubelet
oc adm node-logs <node> -u crio
oc debug node/<node>
```

Inside debug:

```bash
chroot /host
systemctl status kubelet
systemctl status crio
journalctl -b -u kubelet
journalctl -b -u crio
crictl ps -a
```

### 16.2 Pending CSRs

Symptoms:

- New nodes do not become Ready.
- Machine approver degraded.
- Operators depending on nodes fail.

Commands:

```bash
oc get csr
oc get csr -o wide
oc describe csr <csr-name>
```

Approve only if the CSR is expected and valid:

```bash
oc adm certificate approve <csr-name>
```

Do not blindly approve CSRs in production.

### 16.3 Image Pull Failure

Symptoms:

```text
ImagePullBackOff
ErrImagePull
```

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get secret/pull-secret -n openshift-config -o yaml
oc get image.config.openshift.io/cluster -o yaml
oc get proxy.config.openshift.io/cluster -o yaml
```

Check:

- Pull secret validity
- Registry reachability
- Proxy settings
- Trusted CA bundle
- Disconnected mirror config
- ImageContentSourcePolicy / ImageDigestMirrorSet / ImageTagMirrorSet

### 16.4 Proxy or Trust Bundle Misconfiguration

Symptoms:

- Operators cannot reach external services.
- Image pulls fail.
- Cloud provider calls fail.
- Console/monitoring/insights issues.

Commands:

```bash
oc get proxy cluster -o yaml
oc get configmap -n openshift-config
oc get image.config.openshift.io/cluster -o yaml
```

Check:

- `httpProxy`
- `httpsProxy`
- `noProxy`
- trusted CA ConfigMap
- internal cluster domains in noProxy
- service/network CIDRs in noProxy

Common mistake:

Missing `.cluster.local`, service CIDR, machine CIDR, or internal registry in `noProxy`.

### 16.5 DNS Failure

Symptoms:

- Pods cannot resolve services.
- Console, authentication, ingress, monitoring degrade.
- Operators fail with lookup errors.

Commands:

```bash
oc get co dns
oc get pods -n openshift-dns
oc get ds -n openshift-dns
oc logs -n openshift-dns ds/dns-default --all-containers --since=1h
oc get dns.operator/default -o yaml
```

Debug from a pod:

```bash
oc run dns-test --image=registry.access.redhat.com/ubi9/ubi --restart=Never -it --rm -- /bin/bash
getent hosts kubernetes.default.svc
getent hosts oauth-openshift.openshift-authentication.svc
```

### 16.6 Network Plugin Failure

Symptoms:

- `network` degraded.
- Pods cannot communicate.
- Node networking broken.
- DNS and ingress also degraded.

Commands:

```bash
oc get co network
oc get pods -n openshift-ovn-kubernetes
oc get pods -n openshift-network-operator
oc logs -n openshift-network-operator deploy/network-operator --since=1h
oc get network.operator cluster -o yaml
oc get network.config cluster -o yaml
```

For OVN-Kubernetes:

```bash
oc get pods -n openshift-ovn-kubernetes -o wide
oc logs -n openshift-ovn-kubernetes ds/ovnkube-node -c ovn-controller --since=1h
oc logs -n openshift-ovn-kubernetes ds/ovnkube-node -c ovnkube-node --since=1h
```

Node-level checks:

```bash
oc debug node/<node>
chroot /host
ip addr
ip route
ovs-vsctl show
systemctl status ovs-vswitchd
journalctl -b -u ovs-vswitchd
```

### 16.7 Certificate Problems

Symptoms:

- Authentication fails.
- API server degraded.
- Ingress degraded.
- Webhook TLS errors.
- x509 unknown authority errors.

Commands:

```bash
oc get co authentication kube-apiserver openshift-apiserver ingress
oc get secrets -A | grep -i cert
oc get apiservices | grep -v True
oc get csr
```

Check route certificate:

```bash
oc get ingresscontroller -n openshift-ingress-operator default -o yaml
oc get secret -n openshift-ingress <secret-name> -o yaml
```

Check OAuth route:

```bash
oc get route -n openshift-authentication
```

### 16.8 Storage/PVC Problems

Symptoms:

- Monitoring degraded due to Prometheus PVC.
- Image registry unavailable due to storage.
- CSI/storage operator degraded.

Commands:

```bash
oc get co storage image-registry monitoring
oc get sc
oc get pvc -A
oc get pv
oc get pods -A | grep -E 'Pending|ContainerCreating'
oc describe pvc <pvc> -n <ns>
oc describe pod <pod> -n <ns>
```

### 16.9 Admission/Webhook Problems

Symptoms:

- CVO cannot apply manifests.
- Pods cannot create.
- Operators log webhook timeout or denied request.

Commands:

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc get apiservices | grep -v True
oc get events -A --sort-by=.lastTimestamp | grep -i webhook
```

Webhook problems can break many unrelated operators.

### 16.10 Manual Drift from Supported State

Symptoms:

- CVO repeatedly reverts changes.
- Operator keeps reconciling the same object.
- Rollout behaves unexpectedly.

Examples of unsafe manual changes:

- Editing CVO-managed deployments directly.
- Changing labels/selectors on platform services.
- Deleting operator-managed secrets/configmaps.
- Manually scaling platform deployments.
- Changing node files outside MachineConfig.

Fix by restoring supported configuration through the correct OpenShift API, not by fighting the operator.

## 18. Advanced Investigation Patterns

### 18.1 Identify cascading failures

Example:

```text
network      Degraded=True
 DNS         Degraded=True
ingress      Degraded=True
console      Degraded=True
authentication Degraded=True
```

Do not start with console. Start with network.

Reason:

- DNS depends on network.
- Ingress depends on network and DNS.
- Authentication route depends on ingress.
- Console depends on authentication and ingress.

### 18.2 Compare before and after upgrade

```bash
oc get clusterversion version -o jsonpath='{.status.history}' | jq
oc get co -o wide
oc get co <name> -o yaml
```

Check if the operator reported the desired version.

### 18.3 Find all non-running platform pods

```bash
oc get pods -A | egrep '^openshift-|^kube-' | egrep -v 'Running|Completed'
```

### 18.4 Find recent warnings across cluster

```bash
oc get events -A --field-selector type=Warning --sort-by=.lastTimestamp | tail -100
```

### 18.5 Find pods with restart spikes

```bash
oc get pods -A --sort-by='.status.containerStatuses[0].restartCount'
```

Alternative:

```bash
oc get pods -A -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,STATUS:.status.phase,RESTARTS:.status.containerStatuses[*].restartCount' | sort -k4 -n
```

### 18.6 Check APIService health

```bash
oc get apiservices | awk 'NR==1 || $2!="True"'
```

Bad APIService availability can cause discovery issues and operator errors.

### 18.7 Check webhook blast radius

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc get events -A --sort-by=.lastTimestamp | grep -i webhook
```

If many operators suddenly fail to create/update resources, suspect admission webhooks.

### 18.8 Check resource pressure

```bash
oc adm top nodes
oc adm top pods -A
oc describe node <node> | egrep -i 'Pressure|Allocated|Events' -A20
```

Resource pressure can cause platform pod eviction, scheduling failure, or slow reconciliation.

### 18.9 Check control-plane static pod revisions

```bash
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-controller-manager -o wide
oc get pods -n openshift-kube-scheduler -o wide
```

Look for old revisions not terminating, installer pods failing, or one master stuck.

### 18.10 Check managedFields and ownership

Sometimes a manually changed object conflicts with operator reconciliation.

```bash
oc get <resource> <name> -n <ns> -o yaml --show-managed-fields
```

This is advanced and noisy but useful for identifying who last changed an object.

### 19.1 Events

Events are best for Kubernetes scheduling, image pull, volume mount, and admission issues.

```bash
oc get events -n <ns> --sort-by=.lastTimestamp
oc describe pod <pod> -n <ns>
```

Typical useful event reasons:

```text
FailedScheduling
FailedMount
FailedAttachVolume
BackOff
Failed
Unhealthy
FailedCreate
FailedCreatePodSandBox
FailedPull
ErrImagePull
ImagePullBackOff
Killing
Preempting
```

### 19.2 Logs

Operator logs explain reconciliation failures.

```bash
oc logs -n <operator-ns> deploy/<operator-deployment> --since=1h
```

Operand logs explain runtime failures.

```bash
oc logs -n <operand-ns> <pod> --all-containers --since=1h
```

```bash
oc logs -n <ns> <pod> --all-containers --previous
```

## 21. Safe Remediation Rules

### 21.1 Do not edit ClusterOperator status

Never fix an operator by patching `status.conditions`.

Wrong:

```bash
oc patch co ingress --type=merge -p '{"status":{"conditions":...}}'
```

Why wrong:

- Status is owned by the operator.
- It will be overwritten.
- It hides the symptom, not the cause.
- It can mislead CVO and administrators.

### 21.2 Do not delete ClusterOperator objects casually

Deleting a ClusterOperator object is not normal remediation. It can hide status and create more confusion.

### 21.3 Use supported config APIs

Examples:

| Component | Supported config API |
|---|---|
| OAuth/authentication | `oauth.config.openshift.io/cluster`, `authentication.operator.openshift.io/cluster` |
| Ingress | `ingresscontrollers.operator.openshift.io` |
| DNS | `dns.operator.openshift.io/default` |
| Network | `network.operator.openshift.io/cluster` |
| Image registry | `configs.imageregistry.operator.openshift.io/cluster` |
| Proxy | `proxy.config.openshift.io/cluster` |
| Machine config | `MachineConfig`, `KubeletConfig`, `ContainerRuntimeConfig` |
| Monitoring | `cluster-monitoring-config` ConfigMap, supported monitoring APIs |

### 21.4 Avoid permanent manual changes to CVO-managed resources

Examples of risky direct edits:

```bash
oc edit deploy/router-default -n openshift-ingress
oc scale deploy/oauth-openshift -n openshift-authentication --replicas=0
oc delete secret <platform-secret> -n openshift-*
oc edit ds/dns-default -n openshift-dns
```

Some temporary actions are acceptable during an incident, but document them and understand reconciliation.

### 21.5 Fix the dependency, not the symptom

Examples:

| Symptom | Real fix |
|---|---|
| Console degraded because route unavailable | Fix ingress/router/authentication |
| Monitoring degraded because PVC pending | Fix storage class/provisioner |
| Network degraded because node NotReady | Fix node/kubelet/CRI-O/network host issue |
| Authentication degraded after HTPasswd change | Fix secret and OAuth config |
| Image registry unavailable due to storage | Configure registry storage |
| Upgrade blocked by `Upgradeable=False` | Follow operator message and complete prerequisite |

## 22. Production Incident Runbook

Use this during a real incident.

### 22.1 First 5 minutes

```bash
oc whoami
oc get clusterversion
oc get co
oc get nodes
oc get mcp
oc get pods -A | egrep -v 'Running|Completed'
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Classify severity:

| Severity | Example |
|---|---|
| SEV1 | API unavailable, etcd degraded, many operators unavailable |
| SEV2 | Ingress/authentication unavailable, user access impacted |
| SEV3 | One operator degraded but available |
| SEV4 | Upgradeable false, no immediate outage |

### 22.2 Identify primary failing component

Prioritize:

```text
etcd → kube-apiserver → network → dns → machine-config → ingress/authentication → higher-level operators
```

### 22.3 Collect messages

```bash
for co in $(oc get co -o name); do
  echo "===== $co ====="
  oc get $co -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{"\n"}{.message}{"\n"}{end}'
  echo
 done
```

### 22.4 Inspect relevant namespaces

```bash
CO=<name>
for ns in $(oc get co $CO -o jsonpath='{range .status.relatedObjects[*]}{.namespace}{"\n"}{end}' | sort -u | grep -v '^$'); do
  echo "===== $ns ====="
  oc get pods -n $ns -o wide
  oc get events -n $ns --sort-by=.lastTimestamp | tail -30
 done
```

### 22.5 Check recent changes

Ask or check:

- Was the cluster upgraded?
- Was OAuth changed?
- Was proxy changed?
- Was ingress certificate changed?
- Was pull secret changed?
- Was MachineConfig/KubeletConfig changed?
- Were nodes rebooted?
- Did cloud credentials rotate?
- Did storage/network infrastructure change?
- Did someone apply GitOps changes?

### 22.6 Apply narrow remediation

Examples:

- Restart one crashed operator pod only if safe and after logs are captured.
- Fix invalid config and wait for operator rollout.
- Approve valid CSRs.
- Restore missing secret/configmap from backup or correct source.
- Fix node NotReady.
- Fix storage backend.
- Fix wildcard DNS/load balancer.

### 22.7 Validate recovery

```bash
oc get co
oc get clusterversion
oc get nodes
oc get mcp
oc get pods -A | egrep -v 'Running|Completed'
```

For specific operator:

```bash
oc get co <name>
oc describe co <name>
oc rollout status deploy/<operand> -n <ns>
```

### 22.8 Document incident

Record:

- Start/end time
- Affected ClusterOperators
- Initial condition messages
- Root cause
- Commands used
- Changes made
- Validation proof
- Follow-up actions

## 23. Interview and Exam Notes

### 23.1 Common interview questions

**Q: What is `oc get co` used for?**  
It lists ClusterOperators and their health conditions: version, Available, Progressing, Degraded, age, and message. It is a primary cluster health command in OpenShift.

**Q: Difference between ClusterOperator and OLM Operator?**  
ClusterOperators are core OpenShift platform operators managed by CVO. OLM Operators are application/add-on operators managed by Operator Lifecycle Manager using Subscriptions, InstallPlans, and CSVs.

**Q: What does `Degraded=True` mean?**  
The operator has detected a problem in itself or its managed components. It may or may not mean an outage. Check `Available` to determine service impact.

**Q: Why can an upgrade be stuck even when pods look healthy?**  
A ClusterOperator might not be reporting the desired version, might still be Progressing, or CVO might be blocked applying a payload manifest.

**Q: Where do you check logs for a ClusterOperator?**  
Find related namespaces from `status.relatedObjects`, then inspect operator pods and operand pods. Operator logs explain reconciliation; operand logs explain runtime failures.

**Q: Should you patch ClusterOperator status?**  
No. Status is owned by the operator and should not be manually modified.

### 23.2 Exam-style approach

In an exam or lab:

1. Run `oc get co`.
2. Pick the failing operator.
3. Run `oc describe co <name>`.
4. Read the condition message.
5. Inspect related namespaces.
6. Check pods/events/logs.
7. Fix the actual dependency.
8. Validate with `oc get co`.

Do not over-engineer. Most lab issues are caused by:

- Bad config
- Missing secret
- Bad image
- Pod not ready
- Service selector mismatch
- Route/certificate issue
- Node/pod scheduling issue
- NetworkPolicy blocking traffic
- Storage/PVC issue

## Final Senior Admin Notes

ClusterOperator troubleshooting is not just reading `oc get co`. It is the discipline of moving from platform-level symptoms to controller-level reconciliation failures and then to the real dependency that blocked the desired state.

The best production approach is:

```text
ClusterOperator condition → condition message → relatedObjects → operator namespace → operand namespace → pods/events/logs → dependency → safe remediation → validation
```

Always remember:

- `Available=False` means service availability risk.
- `Progressing=True` means reconciliation or rollout is ongoing.
- `Degraded=True` means the operator detected a problem.
- `Upgradeable=False` means update safety is blocked or restricted.
- `ClusterOperator` is a status object, not the place to force-fix health.
- Fix the dependency that prevents reconciliation.
