# API Server Unavailable - Advanced Cluster Troubleshooting for OpenShift Administration

> **Audience:** Senior Linux/OpenShift/Kubernetes administrators with ~10 years of infrastructure experience  
> **Scope:** OpenShift Container Platform 4.x / Kubernetes control plane troubleshooting  
> **Focus:** Diagnosing and recovering from `API server unavailable`, `connection refused`, `timeout`, `x509`, `EOF`, `503`, `kube-apiserver degraded`, and control-plane access failures.

---

## 1. What “API server unavailable” means

In OpenShift, almost every administrative action goes through the Kubernetes API endpoint:

```bash
https://api.<cluster_name>.<base_domain>:6443
```

When the API server is unavailable, the cluster may still have running workloads, but the control plane cannot reliably accept, validate, persist, or serve API requests. This affects:

- `oc login`
- `oc get nodes`
- Web console login
- Operator reconciliation
- MachineConfig rollouts
- Scheduler/controller updates
- Node status updates
- New pod scheduling
- Certificate signing request approval
- Route/app deployment changes
- GitOps/CI/CD automation

A good administrator does **not** immediately restart random services. First, identify **which layer is broken**:

1. Client-side issue
2. DNS issue
3. Load balancer issue
4. Network/firewall issue
5. API server process issue
6. Kubelet/static pod issue on control-plane nodes
7. etcd/quorum issue
8. Certificate issue
9. Resource pressure issue
10. Operator rollout/configuration issue
11. Platform/provider issue

## 2. Control plane architecture recap

OpenShift has two important API layers:

| Component | Namespace | Purpose |
|---|---|---|
| `kube-apiserver` | `openshift-kube-apiserver` | Kubernetes API: pods, services, deployments, nodes, RBAC, CRDs |
| `openshift-apiserver` | `openshift-apiserver` | OpenShift API resources: projects, routes, templates, builds, image streams |
| OAuth API/server | `openshift-authentication`, `openshift-oauth-apiserver` | Login/token authentication |
| etcd | `openshift-etcd` | Persistent key-value store for cluster state |
| kube-controller-manager | `openshift-kube-controller-manager` | Reconciles Kubernetes state |
| kube-scheduler | `openshift-kube-scheduler` | Schedules pods |

The API server is the **front door** of the cluster. etcd is the **source of truth**. If etcd is unhealthy, slow, or has lost quorum, the API server may start but fail `/readyz` checks or become very slow.

Important control-plane ports:

| Port | Component | Why it matters |
|---:|---|---|
| `6443/TCP` | Kubernetes API server | Main external/internal API endpoint |
| `22623/TCP` | Machine Config Server | Used by nodes during boot/config retrieval, especially `api-int` |
| `2379-2380/TCP` | etcd | etcd client/peer communication |
| `10250/TCP` | kubelet | Used by API server for logs/exec/attach/port-forward |
| `443/TCP` | Routes/console ingress | Console/OAuth flow may depend on it |

## 4. Senior troubleshooting mindset

Do not treat “API unavailable” as one problem. Treat it as a path:

```text
client -> DNS -> LB/VIP -> control-plane node:6443 -> kube-apiserver static pod -> etcd -> authn/authz/admission -> response
```

Break the path into checkpoints:

```text
1. Can my client resolve api.<cluster>.<domain>?
2. Can my client reach TCP/6443?
3. Is the load balancer forwarding to healthy masters?
4. Is at least one kube-apiserver answering /livez?
5. Is at least one kube-apiserver ready on /readyz?
6. Are all control-plane nodes Ready?
7. Are static pods running on each master?
8. Is etcd healthy and has quorum?
9. Are certificates valid?
10. Did a recent update/configuration change break rollout?
```

## 5. Severity classification

| Severity | Condition | Example |
|---|---|---|
| SEV-1 | API completely unreachable from all admin networks | `oc get nodes` times out everywhere |
| SEV-1 | etcd quorum lost | API cannot persist/read cluster state |
| SEV-1 | Multiple control-plane nodes down | 2 of 3 masters unavailable |
| SEV-2 | API intermittent | Requests succeed sometimes, fail sometimes |
| SEV-2 | One kube-apiserver replica degraded | LB may still hide failure |
| SEV-3 | Console unavailable but CLI works | OAuth/console/route problem, not full API failure |
| SEV-3 | Only one admin workstation affected | Local DNS/proxy/kubeconfig problem |

## 6. First 5-minute triage

Run these from your admin workstation:

```bash
export API=api.<cluster_name>.<base_domain>

# DNS
getent hosts $API
nslookup $API
dig +short $API

# TCP reachability
nc -vz $API 6443
curl -vk https://$API:6443/livez
curl -vk https://$API:6443/readyz

# Authenticated API check, if login works
oc whoami
oc get --raw='/livez?verbose'
oc get --raw='/readyz?verbose'
```

If `nc` is unavailable:

```bash
timeout 5 bash -c '</dev/tcp/'$API'/6443' && echo open || echo closed
```

Or:

```bash
curl -vk --connect-timeout 5 https://$API:6443/version
```

Interpretation:

| Result | Meaning |
|---|---|
| DNS fails | Fix DNS/client resolver/forwarder first |
| TCP timeout | Routing/firewall/LB/VIP/backend network issue |
| TCP refused | No listener on target, LB backend down, wrong VIP, haproxy not listening |
| TLS cert error | Certificate/SAN/CA/time issue |
| `/livez` OK but `/readyz` fails | API process alive but not ready, commonly etcd or post-start hook issue |
| `/readyz` OK but `oc login` fails | Authentication/OAuth/RBAC/token issue |
| CLI works but console fails | Console/OAuth/route/ingress issue, not full API outage |

## 7. Health endpoints: `/livez` vs `/readyz`

Use API health endpoints carefully:

```bash
curl -k https://api.<cluster>.<domain>:6443/livez
curl -k https://api.<cluster>.<domain>:6443/readyz
curl -k https://api.<cluster>.<domain>:6443/readyz?verbose
```

Authenticated check:

```bash
oc get --raw='/readyz?verbose'
oc get --raw='/livez?verbose'
```

Typical useful output:

```text
[+]ping ok
[+]log ok
[+]etcd ok
[+]poststarthook/start-kube-apiserver-admission-initializer ok
[+]poststarthook/generic-apiserver-start-informers ok
readyz check passed
```

If you see:

```text
[-]etcd failed
```

then do not waste time on routes or console. Go directly to etcd health, etcd pods, disk latency, quorum, certificates, and control-plane node health.

If `/livez` fails, the API server process itself is unhealthy. If `/livez` passes but `/readyz` fails, the process is alive but not safe to receive traffic.

## 8. Decision tree

```text
START: API server unavailable

A. Is it only one client?
   ├─ Yes -> Check kubeconfig, DNS, proxy, VPN, CA trust, local time
   └─ No  -> Continue

B. Does api.<cluster> resolve?
   ├─ No  -> DNS issue
   └─ Yes -> Continue

C. Is TCP/6443 reachable?
   ├─ Timeout -> Routing/firewall/LB/backend issue
   ├─ Refused -> LB listener/backend/API pod not listening
   └─ Yes     -> Continue

D. Does /livez return OK?
   ├─ No  -> kube-apiserver process/static pod/kubelet/node issue
   └─ Yes -> Continue

E. Does /readyz return OK?
   ├─ No  -> usually etcd, post-start hooks, informer sync, admission, APIService
   └─ Yes -> Continue

F. Does authentication work?
   ├─ No  -> OAuth/authentication/operator/cert/token issue
   └─ Yes -> API is available; issue is higher layer
```

## 9. Layer 1: Client-side checks

Before declaring a cluster outage, verify the client.

### 9.1 Check kubeconfig

```bash
echo $KUBECONFIG
oc config view --minify
oc config current-context
oc whoami --show-server
```

Expected server:

```text
https://api.<cluster_name>.<base_domain>:6443
```

Common mistakes:

- Old kubeconfig after cluster reinstall
- Wrong cluster context
- Expired token
- Corporate proxy intercepting TLS
- VPN not connected
- `/etc/hosts` overriding API record
- Wrong CA bundle
- Local clock drift causing x509 errors

### 9.2 Check local proxy variables

```bash
env | grep -i proxy
```

If proxy is wrongly set:

```bash
unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy
export NO_PROXY=.cluster.local,.svc,api.<cluster>.<domain>,api-int.<cluster>.<domain>
```

### 9.3 Check local time

```bash
date
chronyc tracking || timedatectl
```

If the client clock is wrong, certificates may appear invalid even when the cluster is healthy.

## 10. Layer 2: DNS troubleshooting

### 10.1 Check API record

```bash
dig api.<cluster>.<base_domain>
dig api-int.<cluster>.<base_domain>
dig +short api.<cluster>.<base_domain>
dig +short api-int.<cluster>.<base_domain>
```

Expected:

- `api.<cluster>` resolves to external/public/private API load balancer depending on topology.
- `api-int.<cluster>` resolves to internal API load balancer/VIP.

### 10.2 Compare resolvers

```bash
dig @<dns_server_1> api.<cluster>.<base_domain>
dig @<dns_server_2> api.<cluster>.<base_domain>
```

If DNS differs between client, bastion, and nodes, you can get inconsistent API behavior.

### 10.3 Node-side DNS check

If API still works partially:

```bash
oc debug node/<master-node>
chroot /host
cat /etc/resolv.conf
dig api.<cluster>.<base_domain>
dig api-int.<cluster>.<base_domain>
```

If API does not work, SSH to a control-plane node if allowed:

```bash
ssh core@<master-node>
dig api.<cluster>.<base_domain>
dig api-int.<cluster>.<base_domain>
```

### 10.4 DNS failure patterns

| Symptom | Likely cause |
|---|---|
| `server can't find api... NXDOMAIN` | Missing DNS zone/record |
| Resolves to old IP | Cluster reinstalled but DNS not updated |
| Client resolves public IP, nodes resolve private IP | Split-horizon DNS; verify expected design |
| `api-int` missing | Node boot/MCO/static pod rollout issues possible |
| Reverse lookup missing | Usually not fatal, but important in strict environments |

## 11. Layer 3: Load balancer / VIP troubleshooting

In highly available OpenShift, API traffic normally goes through a load balancer or VIP and then to control-plane nodes.

### 11.1 Check listener

On HAProxy/load balancer host:

```bash
sudo ss -lntp | egrep ':6443|:22623|:443|:80'
sudo systemctl status haproxy
sudo journalctl -u haproxy -b --no-pager | tail -100
```

For HAProxy:

```bash
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
```

### 11.2 Example HAProxy API backend

```haproxy
frontend openshift-api-server
    bind *:6443
    default_backend openshift-api-server

backend openshift-api-server
    balance source
    option tcp-check
    server master-0 master-0.ocp4.example.com:6443 check
    server master-1 master-1.ocp4.example.com:6443 check
    server master-2 master-2.ocp4.example.com:6443 check
```

### 11.3 Check each backend directly

From bastion/LB:

```bash
for m in master-0 master-1 master-2; do
  echo "=== $m ==="
  nc -vz $m 6443
  curl -k --connect-timeout 5 https://$m:6443/livez
  curl -k --connect-timeout 5 https://$m:6443/readyz
 done
```

If one backend fails, remove it from rotation only after confirming it is unhealthy. Do not mask a quorum/control-plane problem by blindly removing backends.

### 11.4 LB failure patterns

| Symptom | Meaning |
|---|---|
| API works directly to one master but not via LB | LB/VIP/listener/routing problem |
| API works via LB sometimes only | One or more bad backends in rotation |
| `/livez` OK on all masters but LB returns timeout | LB health check/firewall/path problem |
| `connection refused` from LB | Listener down, wrong bind, wrong VIP, no process listening |
| Long TLS handshake | LB overload, backend overload, packet loss, MTU, CPU pressure |

## 12. Layer 4: Network and firewall checks

### 12.1 From admin workstation

```bash
traceroute api.<cluster>.<domain>
tracepath api.<cluster>.<domain>
nc -vz api.<cluster>.<domain> 6443
curl -vk --connect-timeout 5 https://api.<cluster>.<domain>:6443/version
```

### 12.2 From load balancer to masters

```bash
for m in master-0 master-1 master-2; do
  nc -vz $m 6443
  nc -vz $m 22623
  nc -vz $m 10250
 done
```

### 12.3 From master to master

```bash
ssh core@master-0
for m in master-0 master-1 master-2; do
  nc -vz $m 2379
  nc -vz $m 2380
  nc -vz $m 6443
 done
```

### 12.4 Firewall/ACL items to verify

- Admin network to API LB: `6443/TCP`
- LB to masters: `6443/TCP`, `22623/TCP`
- Masters to masters: `2379-2380/TCP`, `6443/TCP`, `10250/TCP`
- Nodes to API/internal API
- Security groups / NSGs / firewall zones
- On-prem VLAN ACLs
- Cloud route tables
- MTU mismatch, especially with OVN/SDN overlays

## 14. Layer 6: kube-apiserver pods and static pod revisions

The kube-apiserver is managed by an operator and runs as static pods on control-plane nodes.

### 14.1 List API server pods

```bash
oc get pods -n openshift-kube-apiserver -o wide
```

Example:

```text
kube-apiserver-master-0   5/5 Running
kube-apiserver-master-1   5/5 Running
kube-apiserver-master-2   5/5 Running
```

### 14.2 Check containers

```bash
oc get pod -n openshift-kube-apiserver <pod> -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.ready}{"\t"}{.restartCount}{"\t"}{.state}{"\n"}{end}'
```

Important containers may include:

- `kube-apiserver`
- `kube-apiserver-cert-syncer`
- `kube-apiserver-cert-regeneration-controller`
- `kube-apiserver-insecure-readyz`
- `watch-termination`

### 14.3 Logs

```bash
oc logs -n openshift-kube-apiserver pod/<kube-apiserver-pod> -c kube-apiserver --tail=200
oc logs -n openshift-kube-apiserver pod/<kube-apiserver-pod> -c kube-apiserver --previous --tail=200
```

Search for:

```bash
oc logs -n openshift-kube-apiserver pod/<pod> -c kube-apiserver | egrep -i 'etcd|timeout|certificate|x509|panic|fatal|no space|too many requests|denied|poststarthook|failed'
```

### 14.4 Revision resources

```bash
oc get configmap -n openshift-kube-apiserver | grep revision
oc get secret -n openshift-kube-apiserver | grep revision
oc get pod -n openshift-kube-apiserver | grep installer
```

Check installer pod logs:

```bash
oc logs -n openshift-kube-apiserver pod/installer-<revision>-<node> --all-containers=true
```

If an installer pod failed on one master, the operator may mark the rollout degraded.

## 15. Layer 7: When API is down - use node-level access

If `oc` cannot talk to the API, you must inspect control-plane nodes directly.

> Use SSH only when API-based collection is not possible or insufficient. OpenShift nodes are RHCOS/immutable, and manual node changes should be minimal, documented, and reversible.

### 15.1 SSH to control-plane node

```bash
ssh core@master-0.<cluster>.<domain>
```

### 15.2 Check kubelet

```bash
sudo systemctl status kubelet
sudo journalctl -u kubelet -b --no-pager | tail -200
sudo journalctl -u kubelet -b --no-pager | egrep -i 'static|apiserver|etcd|certificate|x509|failed|error|runtime|crio|manifest'
```

### 15.3 Check CRI-O

```bash
sudo systemctl status crio
sudo journalctl -u crio -b --no-pager | tail -200
sudo crictl ps -a | egrep 'kube-apiserver|etcd|scheduler|controller|oauth|apiserver'
```

### 15.4 Check static pod manifests

```bash
sudo ls -l /etc/kubernetes/manifests/
sudo ls -l /etc/kubernetes/static-pod-resources/
```

Common files:

```text
/etc/kubernetes/manifests/kube-apiserver-pod.yaml
/etc/kubernetes/manifests/etcd-pod.yaml
/etc/kubernetes/manifests/kube-controller-manager-pod.yaml
/etc/kubernetes/manifests/kube-scheduler-pod.yaml
```

### 15.5 Inspect local API server container

```bash
sudo crictl ps -a | grep kube-apiserver
sudo crictl logs <container_id> | tail -200
sudo crictl inspect <container_id> | less
```

### 15.6 Check listener locally

```bash
sudo ss -lntp | grep 6443
curl -k https://localhost:6443/livez
curl -k https://localhost:6443/readyz?verbose
```

Interpretation:

| Node-local check | Meaning |
|---|---|
| `localhost:6443/livez` fails | kube-apiserver not alive on this node |
| `localhost:6443/livez` OK but external fails | LB/firewall/network path issue |
| `localhost:6443/readyz` fails with etcd | API alive but etcd/backend readiness issue |
| No process listening on 6443 | static pod/kubelet/CRI-O/manifest issue |

## 16. Layer 8: etcd troubleshooting

Many API outages are actually etcd outages.

### 16.1 Check etcd ClusterOperator

```bash
oc get co etcd
oc describe co etcd
oc get pods -n openshift-etcd -o wide
oc get events -n openshift-etcd --sort-by=.lastTimestamp | tail -50
```

### 16.2 Check etcd logs

```bash
oc logs -n openshift-etcd pod/<etcd-pod> -c etcd --tail=200
oc logs -n openshift-etcd pod/<etcd-pod> -c etcd --previous --tail=200
```

Search:

```bash
oc logs -n openshift-etcd pod/<etcd-pod> -c etcd | egrep -i 'leader|election|quorum|rafthttp|unhealthy|timeout|no space|database|corrupt|panic|certificate|x509|peer'
```

### 16.3 etcd endpoint health

```bash
oc rsh -n openshift-etcd <etcd-pod>
etcdctl endpoint health -w table
etcdctl endpoint status -w table
etcdctl member list -w table
```

If using `oc rsh` is impossible, SSH to a control-plane node and use `crictl exec` into etcd if available.

### 16.4 etcd failure patterns

| Symptom | Meaning |
|---|---|
| `context deadline exceeded` | etcd slow/unreachable |
| `no leader` | quorum/election/network issue |
| Frequent leader changes | network latency, disk latency, overloaded node |
| `mvcc: database space exceeded` | etcd database quota/storage issue |
| `x509` peer/client errors | etcd certificate/time/trust issue |
| One member unhealthy | Replace/member recovery may be needed |
| Majority members down | Disaster recovery path, not normal operator rollout |

### 16.5 Disk and latency checks

On each master:

```bash
ssh core@master-0
uptime
free -h
df -h
sudo journalctl -u kubelet -b --no-pager | egrep -i 'disk|pressure|eviction'
```

Check etcd backend storage path:

```bash
sudo du -sh /var/lib/etcd 2>/dev/null || true
sudo find /var/lib/etcd -maxdepth 2 -type f -printf '%p %s\n' 2>/dev/null | sort -k2 -nr | head
```

### 16.6 Quorum rule

For a 3-member etcd cluster:

```text
Healthy majority required = 2 members
```

For a 5-member etcd cluster:

```text
Healthy majority required = 3 members
```

If you lose majority, the API server cannot reliably serve state-changing requests and may become unavailable.

### 16.7 Safe etcd guidance

Do **not** remove etcd members casually. Removing a healthy member can cause quorum loss. Before any destructive etcd operation:

```bash
oc adm must-gather
oc adm inspect ns/openshift-etcd co/etcd
```

Take an etcd backup when the procedure requires it:

```bash
ssh core@<master-node>
sudo -E /usr/local/bin/cluster-backup.sh /home/core/assets/backup
```

Then copy backup securely:

```bash
scp -r core@<master-node>:/home/core/assets/backup ./etcd-backup-$(date +%F)
```

## 17. Layer 9: Certificate troubleshooting

Certificate problems often show as:

```text
x509: certificate has expired or is not yet valid
x509: certificate signed by unknown authority
certificate is valid for ..., not api.<cluster>
remote error: tls: bad certificate
```

### 17.1 Check API certificate externally

```bash
openssl s_client -connect api.<cluster>.<domain>:6443 -servername api.<cluster>.<domain> </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

Verify:

- `notBefore`
- `notAfter`
- Subject Alternative Names contain the API hostname
- Issuer is expected
- Client trusts the CA

### 17.2 Check local time on all masters

```bash
for m in master-0 master-1 master-2; do
  echo "=== $m ==="
  ssh core@$m date
  ssh core@$m chronyc tracking
 done
```

Clock skew can make valid certificates appear invalid.

### 17.3 API named certificate renewal

If a custom/named API certificate is configured and expired, renew its backing secret.

Check config:

```bash
oc get apiserver cluster -o yaml
```

Look for:

```yaml
spec:
  servingCerts:
    namedCertificates:
```

After updating the secret, monitor:

```bash
oc get co kube-apiserver
oc get pods -n openshift-kube-apiserver
```

Do not apply multiple API certificate changes during an in-progress rollout.

### 17.4 CSR issues

```bash
oc get csr
oc describe csr <csr-name>
```

Approve only valid CSRs:

```bash
oc adm certificate approve <csr-name>
```

Do not blindly approve CSRs in production unless you have validated the requester and node identity.

## 18. Layer 10: Authentication vs API availability

Sometimes the API is healthy, but login fails.

### 18.1 Test unauthenticated health

```bash
curl -k https://api.<cluster>.<domain>:6443/livez
curl -k https://api.<cluster>.<domain>:6443/readyz
```

### 18.2 Test API version

```bash
curl -k https://api.<cluster>.<domain>:6443/version
```

If this works, the API endpoint is reachable.

### 18.3 Test login path

```bash
oc login https://api.<cluster>.<domain>:6443 -u <user> -p '<password>'
oc whoami
oc get users
```

### 18.4 Check authentication operator

```bash
oc get co authentication
oc describe co authentication
oc get pods -n openshift-authentication
oc logs -n openshift-authentication deploy/oauth-openshift --tail=200
```

### 18.5 OAuth route/ingress dependency

Console login depends on OAuth and routes. CLI token login can fail due to OAuth even when raw API `/readyz` is OK.

Check:

```bash
oc get route -n openshift-authentication
oc get route -n openshift-console
oc get co ingress
oc get pods -n openshift-ingress
```

## 19. Layer 11: APIService and aggregated API failures

Kubernetes aggregated APIs can affect discovery and client behavior.

Check APIService availability:

```bash
oc get apiservice
oc get apiservice | grep False
oc describe apiservice <name>
```

Symptoms:

```text
unable to retrieve the complete list of server APIs
```

Common causes:

- metrics API unavailable
- custom operator APIService backend down
- CA bundle mismatch
- service endpoint missing
- network policy blocking aggregated API backend

Fix depends on the failing APIService. Do not delete core APIService objects unless you fully understand ownership.

## 20. Layer 12: Resource pressure on control-plane nodes

API can become slow/unavailable if masters are overloaded.

### 20.1 Check node status

```bash

oc adm top nodes
oc adm top pods -A --sort-by=cpu
oc adm top pods -A --sort-by=memory
```

### 20.2 Check from node

```bash

uptime
free -h
df -h
sudo crictl stats
sudo journalctl -u kubelet -b --no-pager | egrep -i 'eviction|pressure|memory|disk|pid'
```

### 20.3 Resource pressure patterns

| Condition | API impact |
|---|---|
| Disk full on `/var` | static pods, logs, image pulls, etcd may fail |
| Memory pressure | kube-apiserver/etcd killed or throttled |
| CPU saturation | API latency, timeouts, readiness failures |
| PID pressure | containers/processes cannot start |
| Slow disk | etcd latency, leader elections, API timeout |

## 33. Recovery actions by failure domain

### 33.1 Client-side issue

Fix kubeconfig/context/proxy/time.

```bash
oc config use-context <context>
unset HTTPS_PROXY HTTP_PROXY
export NO_PROXY=.svc,.cluster.local,api.<cluster>,api-int.<cluster>
```

### 33.2 DNS issue

Fix authoritative records. Validate from client, LB, and nodes.

```bash
dig api.<cluster>.<domain>
dig api-int.<cluster>.<domain>
```

### 33.3 LB issue

Fix listener/backend pool/health check. Validate every backend.

```bash
curl -k https://master-0:6443/livez
curl -k https://master-1:6443/livez
curl -k https://master-2:6443/livez
```

### 33.4 One kube-apiserver pod down

Inspect that master only:

```bash
oc describe co kube-apiserver
oc get pods -n openshift-kube-apiserver -o wide
oc logs -n openshift-kube-apiserver pod/<pod> -c kube-apiserver --previous
```

If API unavailable, node SSH:

```bash
sudo systemctl status kubelet crio
sudo crictl ps -a | grep kube-apiserver
sudo crictl logs <container-id>
```

### 33.5 kubelet down on one master

```bash
sudo systemctl status kubelet
sudo journalctl -u kubelet -b --no-pager | tail -200
sudo systemctl restart kubelet
```

Restarting kubelet on one master is generally safer than rebooting all masters, but still confirm etcd quorum and current incident state before acting.

### 33.6 CRI-O down on one master

```bash
sudo systemctl status crio
sudo journalctl -u crio -b --no-pager | tail -200
sudo systemctl restart crio
```

### 33.7 etcd one member down

Follow documented unhealthy member replacement procedure for your OCP version. Validate:

```bash
etcdctl member list -w table
etcdctl endpoint health -w table
```

Take backup where required and do not remove the wrong member.

### 33.8 etcd quorum lost

This is disaster recovery territory. Stop ad-hoc changes, preserve evidence, and use supported restore procedure with existing etcd snapshot.

### 33.9 Certificate expired/custom named cert issue

Renew/update secret and monitor kube-apiserver operator. Validate SAN, issuer, dates, and client CA trust.

### 33.10 Control-plane node NotReady

Investigate node health:

```bash
oc describe node <master>
oc adm node-logs <master> -u kubelet
oc adm node-logs <master> -u crio
```

If API is down:

```bash
ssh core@<master>
sudo journalctl -u kubelet -b --no-pager | tail -200
sudo journalctl -u crio -b --no-pager | tail -200
```

## 34. What not to do during API outage

Avoid these mistakes:

- Do not reboot all control-plane nodes together.
- Do not remove etcd members without confirming the unhealthy member.
- Do not approve all CSRs blindly in a compromised or unknown environment.
- Do not delete kube-apiserver/operator resources randomly.
- Do not edit static pod manifests manually unless following a supported emergency procedure.
- Do not ignore DNS/LB and jump directly to etcd.
- Do not make multiple certificate/config changes while a rollout is progressing.
- Do not clear `/var/lib/etcd` or container storage casually.
- Do not restore an old etcd snapshot unless you understand data loss implications.
- Do not scale operators manually unless directed by a supported procedure.


```bash
jq -r '.user.username + " " + .verb + " " + .objectRef.resource' audit.log | sort | uniq -c | sort -nr | head
```

## 40. Interview/exam-style explanation

If asked, “How do you troubleshoot API server unavailable in OpenShift?” answer like this:

> I troubleshoot it by following the request path. First I confirm whether it is client-specific or cluster-wide. Then I validate DNS for `api` and `api-int`, TCP reachability to `6443`, and load balancer backend health. If the network path is good, I check `/livez` and `/readyz?verbose`. `/livez` tells me whether the API process is alive; `/readyz` tells me whether it is ready to serve traffic, commonly exposing etcd or post-start hook failures. If `oc` works partially, I inspect `co/kube-apiserver`, `co/etcd`, API server pods, operator logs, events, and static pod revisions. If the API is fully down, I SSH to control-plane nodes and inspect kubelet, CRI-O, static pod manifests, `crictl` containers, local `localhost:6443`, and etcd logs. I avoid rebooting all masters or modifying etcd blindly because preserving quorum is critical. I collect must-gather or node-level evidence before recovery actions.

## 41. Production-ready checklist

### Before incident

- Monitor API `/readyz` and `/livez`.
- Monitor etcd health, leader changes, disk fsync latency, DB size.
- Monitor LB backend status.
- Monitor control-plane node CPU, memory, disk, PID pressure.
- Alert on ClusterOperator `Degraded=True`.
- Alert on MachineConfigPool master degraded/updating too long.
- Keep etcd backups scheduled and tested.
- Document LB/DNS/firewall ownership.
- Keep break-glass SSH procedure documented.
- Keep Red Hat support/must-gather process ready.

### During incident

- Freeze non-essential changes.
- Confirm scope.
- Preserve etcd quorum.
- Check DNS/LB before deep cluster debugging.
- Use `/readyz?verbose` to identify backend checks.
- Capture operator status/events/logs if API works.
- Use SSH/crictl only if API does not work.
- Avoid destructive etcd operations without backup/procedure.

### After incident

- Record root cause.
- Record exact timeline.
- Review monitoring gaps.
- Add synthetic API checks.
- Validate etcd backup freshness.
- Review LB health check behavior.
- Review recent change process.
- Add runbook improvements.

## 42. Root cause examples

| Root cause | Why API failed | Fix |
|---|---|---|
| Wrong DNS after LB migration | Clients reached old VIP | Correct DNS and TTL process |
| HAProxy stopped | No listener on 6443 | Restart/fix HAProxy config/systemd |
| One bad master in LB | Intermittent failures | Remove temporarily, fix master, re-add |
| etcd no leader | API not ready | Restore quorum/fix etcd member/network |
| Disk full on master | static pods/etcd failed | Free disk safely, fix log/image growth |
| Expired custom API cert | TLS clients failed | Renew secret/cert, validate CA/SAN |
| Bad MachineConfig | kubelet/CRI-O broken | Roll back/fix MachineConfig, recover node |
| Clock skew | Certs invalid/elections unstable | Fix chrony/NTP |
| Admission webhook down | API writes failed | Fix webhook backend/cert/failurePolicy |
| Upgrade interrupted | Static pod revision mismatch | Inspect operators/revisions, complete recovery |

## 43. Safe escalation criteria

Escalate to Red Hat/platform SRE immediately when:

- etcd quorum is lost.
- More than one control-plane node is down in a 3-master cluster.
- etcd corruption is suspected.
- API cert recovery procedure is unclear.
- Static pod manifests/resources appear damaged.
- Upgrade is stuck with multiple control-plane operators degraded.
- You are considering snapshot restore.
- You cannot collect enough data before recovery.

## 45. Final mental model

Remember this single line:

```text
API unavailable = prove the path: client -> DNS -> LB -> master:6443 -> kube-apiserver -> etcd -> auth/admission -> response
```

For a senior OpenShift administrator, the most important skill is not memorizing one command. It is isolating the failing layer quickly, preserving quorum, avoiding unsafe recovery actions, and collecting useful evidence before the system state changes.
