# Node NotReady Troubleshooting in Advanced OpenShift Administration

**Audience:** Advanced OpenShift administrators, L3 platform engineers, SREs, and candidates preparing for advanced OpenShift administration/troubleshooting roles.

**Experience level:** Written from a 10-year Linux/OpenShift operations mindset.

**Scope:** OpenShift Container Platform 4.x, RHCOS/RHEL CoreOS-style nodes, CRI-O runtime, Machine Config Operator-managed nodes, OVN-Kubernetes networking, and production troubleshooting practices.

---

## 1. What `Node NotReady` Means

In OpenShift, a node is marked `NotReady` when the Kubernetes control plane no longer considers that node healthy enough to receive or reliably run workloads. The `Ready` condition is part of the node status.

Typical output:

```bash
oc get nodes
```

Example:

```text
NAME                         STATUS     ROLES                  AGE   VERSION
master-0.ocp4.example.com    Ready      control-plane,master   30d   v1.xx.x
worker-0.ocp4.example.com    NotReady   worker                 30d   v1.xx.x
worker-1.ocp4.example.com    Ready      worker                 30d   v1.xx.x
```

`NotReady` does **not** always mean the node is powered off. It can mean any of the following:

- The kubelet is down or unhealthy.
- The node cannot reach the API server.
- The API server cannot receive node heartbeats.
- CRI-O is unhealthy, causing kubelet runtime errors.
- The node is under disk, memory, PID, or CPU pressure.
- CNI/OVN networking is broken.
- Node certificates expired or CSRs are pending.
- Machine Config Operator changes are stuck.
- The OS booted but critical systemd services failed.
- A cloud/bare-metal/hypervisor issue caused host instability.

A senior administrator does not troubleshoot `NotReady` as a single error. You troubleshoot it as a **node control-plane communication, kubelet, runtime, OS, networking, resource, certificate, and MCO state problem**.

## 2. Node Health Architecture

### 2.1 Main Components Involved

| Component | Role in Node Readiness | Common Failure Impact |
|---|---|---|
| `kubelet` | Reports node status and manages pods | Node becomes `NotReady` or `Unknown` |
| CRI-O | Container runtime used by kubelet | Pods fail, kubelet reports runtime unavailable |
| API server | Receives node status and leases | Node can appear `Unknown` if heartbeats stop |
| Node lease | Lightweight heartbeat object in `kube-node-lease` namespace | Missing or stale lease indicates heartbeat failure |
| MCO/MCD | Applies OS/kubelet/CRI-O configs and reboots nodes | Node can be updating, degraded, or rebooting |
| NetworkManager | Host networking | API, DNS, gateway, or node interface failures |
| OVN-Kubernetes | Cluster pod/service networking | Node networking or pod connectivity failures |
| CSI node plugins | Storage attach/mount/unmount | Pods stuck; sometimes kubelet blocked or overloaded |
| node-exporter / metrics | Observability | Helps confirm resource pressure |
| Machine API | Cloud/VM lifecycle | Node object and machine object mismatch |
| etcd | Control plane state | Control plane node NotReady can affect quorum |

### 2.2 Kubelet Heartbeat Flow

At a high level:

```text
Node OS boots
  ↓
systemd starts NetworkManager, crio, kubelet
  ↓
kubelet authenticates to API server
  ↓
kubelet updates Node status and Node Lease
  ↓
control plane observes Ready condition
  ↓
scheduler can place pods if node is schedulable and not tainted
```

If this flow breaks, the node can become `NotReady`, `Unknown`, or remain `Ready` but degraded in another way.

## 3. `Ready`, `False`, and `Unknown`

### 3.1 Node Condition Meaning

Check conditions:

```bash
oc describe node <node-name>
```

Important conditions:

| Condition | Meaning |
|---|---|
| `Ready=True` | Node is healthy and accepting pods. |
| `Ready=False` | Kubelet is reporting the node is unhealthy. |
| `Ready=Unknown` | Control plane has stopped receiving heartbeat updates from the node. |
| `DiskPressure=True` | Node filesystem/image/container storage is low. |
| `MemoryPressure=True` | Node memory is low. |
| `PIDPressure=True` | Too many processes/PIDs on the node. |
| `NetworkUnavailable=True` | Node network is not correctly configured. |

### 3.2 `NotReady` vs `Unknown`

| State | Senior-Level Interpretation |
|---|---|
| `Ready=False` | Kubelet is alive enough to report a problem. Look at kubelet, CRI-O, resource pressure, runtime, CNI. |
| `Ready=Unknown` | The API server cannot hear from kubelet. Look at node power, network, API reachability, kubelet crash, cert/auth, severe CPU hang. |
| `Ready,SchedulingDisabled` | Node is healthy but cordoned. This is not the same as `NotReady`. |
| `NotReady,SchedulingDisabled` | Node is unhealthy and also cordoned, often during maintenance or MCO update failure. |

## 4. Immediate Production Triage Mindset

Before touching the node, answer these questions:

1. **How many nodes are affected?**
   - One worker only?
   - All workers?
   - One control plane node?
   - Multiple control plane nodes?
   - Entire cluster?

2. **Is this during an update, reboot, or MCO rollout?**
   - Check MachineConfigPools and ClusterVersion.

3. **Is the API healthy?**
   - If the API is degraded, node symptoms might be secondary.

4. **Are workloads already disrupted?**
   - Check pods on the affected node and application availability.

5. **Is it safe to drain or reboot?**
   - Never blindly reboot a control plane node.
   - Never drain multiple nodes without checking PDBs, quorum, replicas, and capacity.

6. **Can you preserve evidence?**
   - Collect logs before rebooting if possible.

## 6. Troubleshooting Flow

Use this order in real production. It prevents random reboots and reduces MTTR.

```text
1. Confirm scope
2. Check ClusterOperators and MCP state
3. Inspect node conditions, taints, events, and lease
4. Check kubelet logs
5. Check CRI-O/runtime health
6. Check resource pressure: disk, memory, PID, CPU
7. Check network and API reachability
8. Check certificates and CSRs
9. Check MCO/MCD drift or update state
10. Check CNI/OVN and storage plugins
11. Decide: fix service/config/resource, reboot safely, replace node, or escalate
```

---

## 7. Step 1: Confirm the Scope

```bash
oc get nodes -o wide
oc get nodes --show-labels
oc get co
oc get mcp
```

### Interpretation

| Scope | Likely Area |
|---|---|
| Single worker NotReady | Node-local issue: kubelet, CRI-O, disk, OS, network, VM/hardware |
| Multiple workers in same zone/rack | Network, storage, hypervisor, cloud AZ, DHCP/DNS, ToR switch |
| All workers NotReady | API reachability, load balancer, node certs, cluster network, MCO rollout |
| One control plane NotReady | Host/network/kubelet/etcd member issue |
| Multiple control plane NotReady | High severity: etcd quorum/API/control plane instability |
| Node NotReady after update | MCO/MCD, reboot, OS pivot, kernel, CRI-O/kubelet config |
| Newly added node NotReady | CSR, ignition, pull secret, DNS, machine config server, NTP, network |

---

## 8. Step 2: Inspect Node Conditions

```bash
oc describe node <node-name>
```

Focus on:

```text
Conditions:
  Type             Status  Reason                  Message
  Ready            False   KubeletNotReady          container runtime network not ready
  DiskPressure     True    KubeletHasDiskPressure   kubelet has disk pressure
  MemoryPressure   False   KubeletHasSufficientMemory
  PIDPressure      False   KubeletHasSufficientPID
```

### Common `Ready=False` Reasons

| Reason | Meaning | Start Here |
|---|---|---|
| `KubeletNotReady` | Kubelet reports node is unhealthy | kubelet logs |
| `KubeletReady` absent | Kubelet might be down or unable to post | kubelet service/API reachability |
| `ContainerRuntimeNotReady` | CRI-O/runtime problem | crio logs, crictl |
| `NetworkPluginNotReady` | CNI/OVN issue | ovnkube-node, network operator |
| `KubeletHasDiskPressure` | Disk threshold exceeded | df, crictl images, logs |
| `KubeletHasInsufficientMemory` | Memory pressure | workload usage, system reserve |
| `KubeletHasPIDPressure` | PID exhaustion | process/thread leak |

## 9. Step 3: Check Taints

When a node becomes NotReady, Kubernetes/OpenShift can add taints such as:

```text
node.kubernetes.io/not-ready:NoSchedule
node.kubernetes.io/unreachable:NoExecute
node.kubernetes.io/disk-pressure:NoSchedule
node.kubernetes.io/memory-pressure:NoSchedule
node.kubernetes.io/pid-pressure:NoSchedule
```

Check:

```bash
oc describe node <node-name> | sed -n '/Taints:/,/Unschedulable:/p'
oc get node <node-name> -o jsonpath='{.spec.taints}' | jq
```

### Important Production Note

Do not remove NotReady taints manually as a shortcut. Taints are symptoms. If you remove them without fixing the node, you can schedule workloads onto an unhealthy node and make the incident worse.

## 10. Step 4: Check Node Lease

Node lease shows whether kubelet is updating lightweight heartbeat records.

```bash
oc get lease -n kube-node-lease <node-name> -o yaml
```

Look at:

```yaml
spec:
  holderIdentity: worker-0.ocp4.example.com
  renewTime: "2026-07-03T10:20:30Z"
```

### Interpretation

| Lease State | Meaning |
|---|---|
| Renew time is current | Kubelet can talk to API; problem might be runtime/resource condition. |
| Renew time is stale | Kubelet cannot update heartbeat or is down/hung. |
| Lease missing for new node | Node bootstrap/CSR/kubelet registration problem. |

## 11. Step 5: Check Kubelet

Kubelet is the first major suspect in `Node NotReady`.

### 11.1 Logs from API Path

```bash
oc adm node-logs <node-name> -u kubelet --tail=300
```

### 11.2 Logs from Debug Pod

```bash
oc debug node/<node-name>
chroot /host
systemctl status kubelet
journalctl -b -u kubelet --no-pager | tail -200
journalctl -u kubelet --since "2 hours ago" --no-pager
```

### 11.3 Common Kubelet Errors

| Log Pattern | Meaning | Action |
|---|---|---|
| `container runtime is down` | CRI-O unavailable | Check/restart CRI-O only after evidence |
| `network plugin is not ready` | CNI/OVN issue | Check ovnkube-node and CNI files |
| `failed to update node status` | API/network/auth issue | Check API reachability/certs |
| `x509: certificate has expired` | Kubelet cert issue | Check CSRs/certs/time |
| `eviction manager` | Disk/memory/node pressure | Check pressure metrics |
| `PLEG is not healthy` | Runtime overloaded/hung | Check CRI-O, pod count, CPU, disk I/O |
| `failed to run Kubelet` | Bad config or missing files | Check MCO/kubelet config |
| `node not found` | Node object deleted or bootstrap issue | Check node registration/CSR |

### 11.4 Kubelet Service State

```bash
systemctl is-active kubelet
systemctl is-enabled kubelet
systemctl status kubelet --no-pager
```

If kubelet is failed:

```bash
journalctl -xeu kubelet --no-pager
```

Do **not** permanently edit kubelet systemd units manually on RHCOS. OpenShift expects node-level config changes through MCO/KubeletConfig/MachineConfig.

## 12. Step 6: Check CRI-O Runtime

CRI-O is required for kubelet to create and manage containers. If CRI-O is broken, kubelet often reports `ContainerRuntimeNotReady`.

### 12.1 CRI-O Service

```bash
oc adm node-logs <node-name> -u crio --tail=300
```

Or:

```bash
oc debug node/<node-name>
chroot /host
systemctl status crio --no-pager
journalctl -b -u crio --no-pager | tail -200
crictl info
crictl ps -a
crictl images
crictl stats
```

### 12.2 CRI-O Failure Patterns

| Symptom | Possible Cause | Action |
|---|---|---|
| `crio.service failed` | Runtime crash/config issue | Check journal and MCO changes |
| Image pull failures | Registry/DNS/proxy/pull secret | Test DNS/registry route |
| `no space left on device` | Image/container/log filesystem full | Clean safely, fix logs/GC |
| Runtime calls hang | Storage I/O, overlay corruption, huge pod count | Check disk I/O and CRI-O logs |
| Sandbox creation failure | CNI issue | Check CNI/OVN pods/config |
| `permission denied` | SELinux/file permission drift | Check audit logs/MCO drift |

### 12.3 Restarting CRI-O

Restarting CRI-O can disrupt pods. Use only when you understand impact.

```bash
systemctl restart crio
systemctl status crio --no-pager
systemctl restart kubelet
```

Production approach:

```bash
oc adm cordon <node-name>
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data --timeout=10m
# Then perform controlled service restart or reboot
```

If the node is already NotReady, drain might fail or hang because the API cannot reliably evict pods. In that case, assess workload ownership and use `--force` only when required and understood.

## 13. Step 7: DiskPressure Troubleshooting

Disk pressure is one of the most common real-world causes of node instability.

### 13.1 Check from OpenShift

```bash
oc describe node <node-name> | egrep -A5 'DiskPressure|Allocated resources|Events'
oc adm top nodes
```

### 13.2 Check from Host

```bash
oc debug node/<node-name>
chroot /host

df -hT
df -ih
du -xhd1 /var | sort -h
du -xhd1 /var/lib | sort -h
du -xhd1 /var/lib/containers | sort -h
du -xhd1 /var/log | sort -h
journalctl --disk-usage
crictl images
crictl ps -a
```

### 13.3 Common Full Paths

| Path | Why It Fills |
|---|---|
| `/var/lib/containers` | Images, writable layers, stopped containers |
| `/var/log` | Journald, pod logs, audit logs |
| `/var/lib/kubelet` | Pod volumes, emptyDir, plugin data |
| `/var/lib/etcd` | Control plane only; etcd DB/WAL growth |
| `/sysroot` | OS partition, updates, rpm-ostree state |

### 13.4 Safe Cleanup Principles

Good first checks:

```bash
journalctl --vacuum-time=7d
journalctl --vacuum-size=1G
```

For container images, prefer supported kubelet/CRI-O garbage collection behavior. Avoid randomly deleting files under `/var/lib/containers` by hand. Manual deletion can corrupt runtime metadata.

For application logs:

```bash
oc get pods -A -o wide | grep <node-name>
oc logs -n <ns> <pod> --previous
```

Fix the cause:

- Configure application log rotation.
- Reduce noisy logging.
- Add resource limits and ephemeral-storage requests/limits.
- Tune image garbage collection carefully.
- Increase node disk size if needed.
- Fix workloads using large `emptyDir` volumes.

### 13.5 DiskPressure Decision Table

| Finding | Likely Fix |
|---|---|
| `/var/log` full | Vacuum journald, fix log verbosity, configure retention |
| `/var/lib/containers` full | Remove unused images safely, tune GC, increase disk |
| Inodes full but space available | Many tiny files; identify directory with inode growth |
| `/var/lib/kubelet/pods` huge | Pod volume/emptyDir issue; identify pod owner |
| etcd disk pressure | Critical control plane incident; check etcd DB, compaction, defrag, disk I/O |

## 14. Step 8: MemoryPressure, CPU Starvation, and PIDPressure

A node can become NotReady not because kubelet is broken, but because kubelet and CRI-O cannot get enough CPU/memory to operate.

### 14.1 Memory Checks

```bash
oc adm top nodes
oc adm top pods -A --sort-by=memory
```

Inside node:

```bash
free -h
cat /proc/meminfo | egrep 'MemAvailable|MemFree|Swap|Dirty|Writeback'
ps -eo pid,ppid,cmd,%mem,%cpu --sort=-%mem | head -30
crictl stats
```

### 14.2 CPU Checks

```bash
uptime
vmstat 1 10
mpstat -P ALL 1 5
pidstat 1 5
ps -eo pid,ppid,cmd,%cpu,%mem --sort=-%cpu | head -30
```

High load with low CPU usage often means I/O wait. Check:

```bash
iostat -xz 1 5
```

### 14.3 PID Pressure Checks

```bash
ps -eLf | wc -l
cat /proc/sys/kernel/pid_max
systemctl status kubelet crio
```

Find process/thread explosion:

```bash
ps -eLo pid,ppid,nlwp,cmd --sort=-nlwp | head -30
```

### 14.4 Senior-Level Causes

| Cause | Why Node Becomes NotReady |
|---|---|
| Too many pods per node | kubelet/CRI-O overwhelmed |
| No memory limits | Workload consumes system memory |
| CPU-starved system daemons | kubelet misses heartbeats |
| Heavy image pulls | Disk I/O and CPU spike |
| Logging storm | Disk + CPU + inode pressure |
| PID leak | kubelet cannot fork/manage processes |
| Huge number of secrets/configmaps mounted | kubelet sync pressure |

### 14.5 Long-Term Fixes

- Enforce `ResourceQuota` and `LimitRange`.
- Configure workload requests/limits correctly.
- Reduce pod density where needed.
- Reserve resources for system daemons using supported OpenShift mechanisms.
- Separate infra/router/logging/storage workloads onto infra nodes.
- Use cluster autoscaling or add capacity.
- Fix application memory/thread leaks.

## 15. Step 9: Network and API Reachability

A healthy kubelet must reach the API server. Node NotReady often happens because kubelet cannot reach `api` or `api-int`.

### 15.1 Check Node IP and Routes

```bash
oc get node <node-name> -o wide
oc describe node <node-name> | sed -n '/Addresses:/,/Capacity:/p'
```

Inside host:

```bash
ip addr
ip route
nmcli dev status
nmcli con show
```

### 15.2 Check API from Node

```bash
curl -k https://api.<cluster-domain>:6443/readyz
curl -k https://api-int.<cluster-domain>:6443/readyz
```

Also check DNS:

```bash
getent hosts api.<cluster-domain>
getent hosts api-int.<cluster-domain>
cat /etc/resolv.conf
```

### 15.3 Common Network Causes

| Symptom | Likely Cause |
|---|---|
| Node cannot resolve API | DNS failure, wrong resolv.conf, NetworkManager issue |
| Node resolves API but cannot connect 6443 | Firewall, LB, route, VLAN, security group, proxy |
| Only one subnet/rack affected | Physical network/AZ/ToR/router issue |
| API reachable but kubelet auth fails | Cert/CSR/time issue |
| Node IP changed | DHCP/hostname/IP mismatch; node object stale |
| MTU mismatch | Pod network failures, intermittent readiness issues |

### 15.4 Firewall and Port Thinking

For node readiness, check at least:

- TCP 6443 from node to API load balancer/API VIP.
- DNS access to configured resolvers.
- NTP/chrony time sync.
- Registry access if pulls are involved.
- OVN/Geneve/overlay requirements between nodes, depending on topology.

## 16. Step 10: CNI / OVN-Kubernetes Troubleshooting

If kubelet says `NetworkPluginNotReady`, look at CNI and OVN components.

### 16.1 Cluster Network Operators

```bash
oc get co network

oc get pods -n openshift-network-operator -o wide
```

### 16.2 Node-Level OVN Pods

```bash
oc get pods -n openshift-ovn-kubernetes -o wide | grep <node-name>
```

Check logs:

```bash
oc logs -n openshift-ovn-kubernetes <ovnkube-node-pod> -c ovnkube-node --tail=200
oc logs -n openshift-ovn-kubernetes <ovnkube-node-pod> -c ovn-controller --tail=200
```

### 16.3 Host CNI Files

Inside node:

```bash
ls -l /etc/cni/net.d/
ls -l /var/lib/cni/
ls -l /run/ovn-kubernetes/
```

### 16.4 Network Plugin Failure Patterns

| Error | Meaning | Action |
|---|---|---|
| `cni plugin not initialized` | CNI config missing/not ready | Check ovnkube-node and CNI files |
| `failed to create pod sandbox` | Runtime/CNI problem | Check CRI-O + OVN logs |
| `OVN database connection failed` | OVN control plane connectivity | Check ovnkube-master/DB pods |
| `mtu` related errors | MTU mismatch | Validate host NIC, overlay MTU, cloud network |
| Pod IP allocation failure | IPAM/subnet exhaustion or OVN issue | Check network operator and node subnet annotations |

## 17. Step 11: Certificate and CSR Issues

New nodes or rebooted nodes can become NotReady if kubelet certificates are not valid or CSRs are pending.

### 17.1 Check CSRs

```bash
oc get csr
oc get csr -o wide
```

Look for `Pending` CSRs related to the node.

### 17.2 Approve Valid CSRs Carefully

```bash
oc adm certificate approve <csr-name>
```

Do not blindly approve every CSR in production. Validate:

- Node name
- Username, such as `system:node:<node-name>`
- Signer name
- Requested addresses
- Whether the node is expected

### 17.3 Time Sync

Certificate problems can also come from time drift.

Inside node:

```bash
timedatectl
chronyc tracking || true
journalctl -b -u chronyd --no-pager | tail -100
```

### 17.4 Kubelet Cert Log Patterns

| Log Pattern | Meaning |
|---|---|
| `x509: certificate has expired` | Expired kubelet/client/server cert |
| `certificate signed by unknown authority` | CA/trust mismatch |
| `Unauthorized` | Kubelet auth to API failed |
| `cannot create certificate signing request` | API/auth/network problem |

## 18. Step 12: Machine Config Operator and Machine Config Daemon

MCO is central in OpenShift node lifecycle. It manages OS-level configuration, kubelet configuration, CRI-O configuration, kernel arguments, registries, SSH keys, and node reboots.

### 18.1 Check MCP State

```bash
oc get mcp
oc describe mcp worker
oc describe mcp master
```

Important fields:

| Field | Meaning |
|---|---|
| `UPDATED` | Pool has applied current desired config |
| `UPDATING` | MCO is applying a new config |
| `DEGRADED` | MCO cannot apply or reconcile config |
| `MACHINECOUNT` | Total nodes in pool |
| `READYMACHINECOUNT` | Nodes ready and matching required state |
| `DEGRADEDMACHINECOUNT` | Nodes degraded/unreconcilable |

### 18.2 Check Node Annotations

```bash
oc describe node <node-name> | egrep -i 'machineconfiguration|currentConfig|desiredConfig|state|reason|message'
```

Look for:

```text
machineconfiguration.openshift.io/currentConfig
machineconfiguration.openshift.io/desiredConfig
machineconfiguration.openshift.io/state
machineconfiguration.openshift.io/reason
```

### 18.3 MCD Logs

```bash
oc get pods -n openshift-machine-config-operator -o wide
oc logs -n openshift-machine-config-operator <mcd-pod-on-node> -c machine-config-daemon --tail=300
```

### 18.4 MCO/MCD Failure Patterns

| Symptom | Meaning | Action |
|---|---|---|
| MCP `UPDATING=True` long time | Node stuck applying config/rebooting | Check MCD logs and node state |
| MCP `DEGRADED=True` | Config drift or failed apply | Check `oc describe mcp` message |
| Node `currentConfig != desiredConfig` | Node has not completed update | Check reboot, drain, MCD logs |
| `content mismatch for file` | File changed manually outside MCO | Restore file or use force file carefully |
| MCD cannot drain | PDB, stuck pods, API issue | Check drain errors, PDBs |

### 18.5 Configuration Drift

Configuration drift happens when files managed by MCO are changed manually on the node. The MCD detects the mismatch and marks node/MCP degraded.

Production rule:

> Do not manually edit MCO-managed files on RHCOS nodes. Use `MachineConfig`, `KubeletConfig`, or supported Operators.

## 19. Step 13: Control Plane Node NotReady

Control plane node NotReady requires extra caution.

### 19.1 Check Control Plane Health

```bash
oc get nodes -l node-role.kubernetes.io/master
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-apiserver -o wide
oc get co kube-apiserver etcd authentication ingress network
```

### 19.2 Etcd Impact

On a 3-control-plane cluster:

- 1 control plane node down: cluster should usually survive.
- 2 control plane nodes down: etcd quorum likely lost; major incident.
- Do not reboot additional control plane nodes while etcd health is unknown.

### 19.3 Etcd Health

```bash
oc -n openshift-etcd get pods -o wide
oc -n openshift-etcd logs -l app=etcd --tail=100
```

Use supported etcd health procedures for your OpenShift version. Avoid unsupported direct etcd data manipulation.

### 19.4 Static Pods

Control plane components run as static pods managed by kubelet:

- kube-apiserver
- kube-controller-manager
- kube-scheduler
- etcd

If kubelet is down on a control plane node, static pods on that node are also impacted.

## 20. Step 14: Worker Node NotReady

Worker node NotReady usually affects application workloads, routers, monitoring, logging, storage, or infra pods scheduled there.

### 20.1 Find Pods on Affected Node

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node-name>
```

If the field selector does not work in your environment:

```bash
oc get pods -A -o wide | grep <node-name>
```

### 20.2 Check Application Impact

```bash
oc get pods -A | egrep -i 'CrashLoopBackOff|Error|Pending|Terminating|Unknown|ContainerCreating'
oc get route -A
oc get ingresscontroller -n openshift-ingress-operator
oc get pods -n openshift-ingress -o wide
```

### 20.3 Safe Recovery Strategy

| Case | Strategy |
|---|---|
| Node temporarily rebooting | Wait briefly, monitor kubelet/lease/MCP |
| Node isolated but workloads replicated | Cordon/drain or replace node |
| Node has local PV workloads | Do not force delete without storage impact review |
| Node has router pods | Ensure ingress has enough replicas elsewhere |
| Node has logging/storage/monitoring | Check operator-specific health |

## 21. Step 15: Pods Stuck on NotReady Node

Pods on a NotReady node may show:

```text
Unknown
Terminating
NodeLost
ContainerStatusUnknown
```

Check:

```bash
oc get pods -A -o wide | grep <node-name>
oc describe pod -n <namespace> <pod-name>
```

### Important

Do not force delete stateful pods without knowing storage behavior.

For stateless workloads:

```bash
oc delete pod -n <namespace> <pod-name> --grace-period=0 --force
```

Use this carefully. It removes the API object; it does not magically stop a process on a partitioned node. If the node is network-partitioned but still running, duplicate workload risk can exist for some applications.

## 22. Step 16: Storage-Related Node NotReady

Storage problems often look like kubelet/runtime problems.

### 22.1 Symptoms

- Pods stuck in `ContainerCreating`.
- Kubelet logs show mount/unmount timeout.
- CSI node plugin is failing on the node.
- Node drain stuck because volumes cannot detach.
- Node has high I/O wait.
- `/var/lib/kubelet/plugins` or `/var/lib/kubelet/pods` has stale mounts.

### 22.2 Commands

```bash
oc get csidriver
oc get pods -A -o wide | egrep -i 'csi|odf|rook|ceph|storage'
oc get pv,pvc -A
oc describe pod -n <ns> <pod>
```

Inside node:

```bash
mount | grep kubelet
findmnt | grep kubelet
lsblk
journalctl -b -u kubelet --no-pager | egrep -i 'mount|volume|csi|timeout|detach|attach'
```

### 22.3 Senior-Level Warning

Never blindly unmount or delete storage paths from `/var/lib/kubelet` in production. Check CSI driver documentation and application data consistency first.

For newly added compute nodes:

6. Node becomes Ready.

## 25. Step 19: Node NotReady After Upgrade

OpenShift upgrades involve ClusterVersion, ClusterOperators, MCO, node drains, reboots, and new kubelet/CRI-O/RHCOS versions.

### 25.1 Check Upgrade State

```bash
oc get clusterversion
oc describe clusterversion
oc get co
oc get mcp
oc describe mcp worker
oc describe mcp master
```

### 25.2 Common Upgrade Failure Causes

| Symptom | Cause |
|---|---|
| Node reboots and never returns | OS boot/kernel/initramfs/NIC issue |
| MCP stuck updating | MCD failed, drain blocked, config failed |
| Node degraded | Config drift or failed apply |
| CRI-O fails after reboot | Runtime config/storage issue |
| Kubelet fails after reboot | Bad kubelet config, cert, network |
| Multiple nodes updating at once unexpectedly | MCP maxUnavailable/custom pool issue |

### 25.3 Senior-Level Upgrade Rule

If multiple nodes are NotReady during upgrade, stop making changes and stabilize one layer at a time:

1. API and etcd health.
2. MCP state.
3. One affected node logs.
4. Runtime/kubelet.
5. Network and storage.

## 27. Step 21: Cordon, Drain, Reboot, Uncordon

### 27.1 Cordon

```bash
oc adm cordon <node-name>
```

This prevents new pods from being scheduled.

### 27.2 Drain

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data --timeout=10m
```

If unmanaged pods exist:

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data --force --timeout=10m
```

If PDB blocks eviction, do not bypass immediately. First check:

```bash
oc get pdb -A
oc describe pdb -n <ns> <pdb-name>
```

### 27.3 Reboot Safely

```bash
oc debug node/<node-name>
chroot /host
systemctl reboot
```

### 27.4 Uncordon

```bash
oc adm uncordon <node-name>
oc get node <node-name>
```

### 27.5 When Not to Drain/Reboot

Do not drain/reboot immediately when:

- Multiple control plane nodes are unhealthy.
- Etcd quorum is uncertain.
- Node has local PV/stateful data.
- You have not checked PDBs.
- The issue is clearly cluster-wide API/network.
- You have not captured logs and the issue is recurring.

## 28. Root Cause Decision Matrix

| Observation | Likely Root Cause | Next Command |
|---|---|---|
| `Ready=Unknown`, stale lease | Kubelet down, node unreachable, API path broken | `oc adm node-logs NODE -u kubelet`, node console |
| `Ready=False`, `ContainerRuntimeNotReady` | CRI-O issue | `oc adm node-logs NODE -u crio` |
| `Ready=False`, `NetworkPluginNotReady` | CNI/OVN issue | `oc get pods -n openshift-ovn-kubernetes -o wide` |
| `DiskPressure=True` | Disk/inode full | `df -hT`, `df -ih`, `du -xhd1 /var` |
| `MemoryPressure=True` | Memory exhaustion | `oc adm top pods -A --sort-by=memory` |
| `PIDPressure=True` | Process/thread leak | `ps -eLf | wc -l` |
| MCP degraded | MCO config drift/apply failure | `oc describe mcp <pool>` |
| Newly added node stuck | CSR/DNS/API/ignition | `oc get csr`, node network checks |
| Node NotReady after reboot | Boot/kubelet/network/runtime | console + journalctl |
| Node NotReady after upgrade | MCO/MCD/OS pivot | `oc get mcp`, MCD logs |
| API unreachable from node | DNS/LB/firewall/routing | `curl -k https://api...:6443/readyz` |
| Kubelet x509 error | Cert/time/CSR issue | `oc get csr`, `timedatectl` |

## 30. Common Real-World Scenarios

### Scenario 1: Worker Node `NotReady` with `DiskPressure=True`

Symptoms:

```text
Ready=False
DiskPressure=True
Eviction manager messages in kubelet logs
```

Commands:

```bash
oc debug node/worker-0
chroot /host
df -hT
df -ih
du -xhd1 /var | sort -h
du -xhd1 /var/lib/containers | sort -h
journalctl --disk-usage
```

Fix path:

1. Cordon node if unstable.
2. Identify growth path.
3. Vacuum journald if logs are the cause.
4. Fix noisy application or log retention.
5. Let kubelet/CRI-O garbage collection recover if image pressure.
6. Increase disk if pressure is structural.
7. Uncordon after node is Ready and pressure clears.

### Scenario 2: Node `NotReady` After Reboot

Symptoms:

```text
Node rebooted during patching/MCO update
Node does not return Ready
Lease stale
```


- Check VM console or bare-metal console.

| Node State | Fix |
|---|---|
| Not powered on | Start/repair VM/host |
| Booted but no network | Fix VLAN/DHCP/static IP/NM config |
| Network OK but kubelet failed | Check kubelet logs/config/certs |

## 33. What Not To Do

Avoid these mistakes:

1. **Do not reboot first and investigate later** unless there is an immediate business need and the risk is understood.
2. **Do not delete node objects randomly**; deleting a node object does not fix the host.
3. **Do not approve all CSRs blindly**; validate them.
4. **Do not edit kubelet/CRI-O config manually** on RHCOS; use MCO-supported config.
5. **Do not delete `/var/lib/containers` manually** unless following a verified recovery procedure.
6. **Do not force delete stateful pods** without storage/application review.
7. **Do not reboot multiple control plane nodes** without confirming etcd quorum.
8. **Do not bypass PDBs** unless business impact and data risk are understood.
9. **Do not ignore MCO degraded state**; future updates can become blocked.
10. **Do not treat `SchedulingDisabled` as a failure**; it usually means cordoned.

## 34. Senior Troubleshooting Patterns

### Pattern 1: Separate Symptom from Cause

`NotReady` is a symptom. The cause might be:

```text
Network → API unreachable → stale lease → Node Unknown
Disk full → CRI-O unstable → kubelet runtime not ready → Node NotReady
MCO drift → config blocked → kubelet bad config → Node NotReady
Memory pressure → kubelet starved → missed heartbeats → Node Unknown
```

### Pattern 2: Compare Good Node vs Bad Node

Pick a healthy node in the same role/zone:

```bash
GOOD=<ready-node>
BAD=<notready-node>

oc describe node $GOOD > good-node.txt
oc describe node $BAD > bad-node.txt
diff -u good-node.txt bad-node.txt | less
```

Compare:

- Labels
- Taints
- Kubelet version
- Container runtime version
- MachineConfig annotations
- Node IPs
- Allocatable resources
- Events

### Pattern 3: Always Check Recent Change

Ask:

- Did we upgrade OpenShift?
- Did MCO apply a new config?
- Did a network/firewall/DNS change happen?
- Did a certificate rotate?
- Did a node reboot?
- Did storage backend change?
- Did workload density increase?
- Did logging volume spike?

### Pattern 4: Time Correlation

Use timestamps:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -200
journalctl --since "2026-07-03 10:00:00" -u kubelet -u crio --no-pager
```

Correlate:

```text
10:02 MCO starts drain
10:05 node reboots
10:08 kubelet starts
10:09 CRI-O fails
10:10 node NotReady
```

This is how senior engineers identify root cause instead of guessing.

## 35. Production Recovery Strategies

### 35.1 Fix in Place

Use when:

- Cause is simple and node is recoverable.
- Disk/log pressure can be cleaned.
- CRI-O/kubelet can be restarted safely.
- Network misconfiguration is obvious.
- MCO drift can be corrected.

### 35.2 Reboot Node

Use when:

- Kernel/network/runtime is wedged.
- Node completed update but services are stuck.
- Systemd services cannot recover cleanly.
- Business impact is lower than continued outage.

Always cordon/drain when possible.

### 35.3 Replace Node

Use when:

- Cloud/VM/hardware is unhealthy.
- Root disk corruption exists.
- Node repeatedly becomes NotReady.
- MCO state cannot be reconciled safely.
- Bare-metal hardware/NIC/storage is failing.
- Worker node replacement is faster and safer.

For Machine API clusters, replacement usually means deleting/replacing the Machine after validating capacity and workload safety.

### 35.4 Escalate

Escalate when:

- Multiple control plane nodes affected.
- Etcd quorum risk exists.
- MCO degraded across many nodes.
- Node filesystem/runtime corruption suspected.
- Storage backend might have data consistency risk.
- Repeated unexplained NotReady flapping.

## 36. Interview / Exam-Oriented Explanation

### Question: How do you troubleshoot a Node NotReady in OpenShift?

Strong answer:

> I first identify scope using `oc get nodes -o wide`, `oc get co`, and `oc get mcp`. Then I inspect the affected node with `oc describe node` to check Ready condition, taints, pressure conditions, events, and MachineConfig annotations. I check the node lease in `kube-node-lease` to see whether kubelet heartbeats are current. Next I collect kubelet and CRI-O logs with `oc adm node-logs` or `oc debug node/<node>` and `journalctl`. Based on errors, I branch into runtime, disk, memory/PID pressure, network/API reachability, certificate/CSR, CNI/OVN, or MCO troubleshooting. I cordon/drain only when safe, avoid rebooting control plane nodes blindly, collect must-gather/logs for escalation, and decide whether to fix in place, reboot, or replace the node.

### Question: What is the difference between `NotReady` and `SchedulingDisabled`?

Answer:

> `NotReady` means the node health/readiness condition is not healthy. `SchedulingDisabled` means the node is cordoned and the scheduler should not place new pods there. A node can be `Ready,SchedulingDisabled`, which means healthy but intentionally unschedulable.

### Question: What are your first five commands?

```bash
oc get nodes -o wide
oc get co
oc get mcp
oc describe node <node-name>
oc adm node-logs <node-name> -u kubelet --tail=300
```

Then:

```bash
oc adm node-logs <node-name> -u crio --tail=300
oc get lease -n kube-node-lease <node-name> -o yaml
oc get pods -A -o wide | grep <node-name>
```

## 38. Prevention Best Practices

- Monitor `KubeNodeNotReady`, disk pressure, memory pressure, PID pressure, and MCP degraded alerts.
- Keep enough spare worker capacity for drains and failures.
- Use PodDisruptionBudgets carefully; avoid blocking all node maintenance.
- Enforce resource requests/limits and ephemeral-storage limits.
- Keep application logs under control.
- Use infra nodes for routers/monitoring/logging when appropriate.
- Avoid manual host changes outside MCO.
- Test MachineConfig and KubeletConfig changes in non-production first.
- Maintain DNS, NTP, registry, API LB, and firewall reliability.
- Keep documentation for node replacement per platform.
- Review upgrade readiness before applying cluster updates.
