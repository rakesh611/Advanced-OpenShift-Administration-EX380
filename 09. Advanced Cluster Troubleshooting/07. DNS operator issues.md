# DNS Operator Issues - Advanced Cluster Troubleshooting for OpenShift Administration

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and L3 support engineers  
**Experience level:** 10+ years Linux / Kubernetes / OpenShift administration  
**Scope:** OpenShift Container Platform 4.x DNS Operator, CoreDNS, cluster service discovery, upstream DNS forwarding, node-resolver, and DNS-related cluster degradation  
**Last reviewed:** 2026-07-03

---

## 1. Executive Summary

In OpenShift 4.x, DNS is not just a background service. It is a core cluster dependency used by almost every workload and many platform components. If DNS is broken, applications might not reach services, builds can fail, image pulls can fail, operators can become degraded, OAuth/API calls can appear unstable, and troubleshooting can become confusing because many unrelated symptoms are caused by the same name-resolution failure.

The **DNS Operator** manages the cluster DNS stack. It deploys and reconciles **CoreDNS** so that pods can resolve Kubernetes service names such as:

```text
kubernetes.default.svc
my-service.my-project.svc
my-service.my-project.svc.cluster.local
image-registry.openshift-image-registry.svc
```

A senior administrator should troubleshoot DNS issues by separating the problem into four layers:

1. **Operator layer** - Is `clusteroperator/dns` healthy? Is the DNS Operator deployment running?
2. **CoreDNS layer** - Are `dns-default` CoreDNS pods running and ready on expected nodes?
3. **Service discovery layer** - Does the DNS service have ClusterIP and endpoints? Are pods receiving the correct `/etc/resolv.conf`?
4. **Upstream/network layer** - Can CoreDNS reach upstream DNS resolvers for external domains? Are forwarding rules, firewalls, TLS, proxy, MTU, and routing correct?

A common mistake is to immediately blame CoreDNS when a workload cannot resolve a name. In production, DNS symptoms are often caused by bad NetworkPolicy, wrong service names, no service endpoints, blocked UDP/TCP 53, broken upstream resolvers, node placement mistakes, or unsupported manual edits to operator-managed resources.

## 2. DNS Operator Architecture in OpenShift

### 2.1 Key Components

| Component | Namespace | Type | Purpose |
|---|---:|---|---|
| `clusteroperator/dns` | cluster-scoped | ClusterOperator | Reports health of the DNS Operator and managed DNS stack. |
| `dns.operator/default` | cluster-scoped | DNS custom resource | Main desired configuration for cluster DNS. |
| `dns-operator` | `openshift-dns-operator` | Deployment | Reconciles DNS CR, CoreDNS daemonset, service, config map, node-resolver resources. |
| `dns-default` | `openshift-dns` | DaemonSet | Runs CoreDNS pods. Usually one DNS pod per eligible node. |
| `node-resolver` | `openshift-dns` | DaemonSet | Maintains node-level resolver support for internal registry service name resolution. |
| `dns-default` | `openshift-dns` | Service | ClusterIP service that pods use as their nameserver. |
| `dns-default` | `openshift-dns` | ConfigMap | Generated CoreDNS Corefile/configuration. Do not manually edit in normal `Managed` mode. |

### 2.2 Normal DNS Query Path

For a normal pod using `dnsPolicy: ClusterFirst`:

```text
Application container
  -> glibc/musl resolver reads /etc/resolv.conf
  -> queries DNS service ClusterIP, usually x.y.z.10 from service CIDR
  -> kube-proxy/OVN service load balancing sends query to CoreDNS endpoint
  -> CoreDNS answers internal cluster.local/service queries
  -> CoreDNS forwards external queries to upstream resolvers
  -> response returns to pod
```

Example `/etc/resolv.conf` inside a pod:

```text
nameserver 172.30.0.10
search my-project.svc.cluster.local svc.cluster.local cluster.local example.com
options ndots:5
```

Important implications:

- `nameserver` should normally be the OpenShift DNS service ClusterIP.
- Short names are expanded using search domains.
- `ndots:5` can cause multiple search-domain queries before trying the absolute name, which can increase DNS traffic for external names.
- A pod can resolve `my-service` only if it is in the same namespace. Cross-namespace service lookup should use `my-service.other-namespace` or full FQDN.

### 2.3 DNS Operator vs External DNS Operator

Do not confuse these two:

| Operator | Purpose |
|---|---|
| **DNS Operator** | Internal cluster DNS for pods and services. Manages CoreDNS. |
| **External DNS Operator** | Manages DNS records in external DNS providers for routes/services. Optional add-on. |

If a pod cannot resolve `my-service.my-ns.svc.cluster.local`, investigate the DNS Operator/CoreDNS path.

If an external client cannot resolve `app.apps.example.com`, investigate wildcard DNS, Ingress, route, cloud DNS, or External DNS Operator if deployed.

## 3. What Counts as a DNS Operator Issue?

A real DNS Operator issue usually shows one or more of these:

```bash
oc get co dns
oc describe co dns
```

Bad states include:

```text
AVAILABLE=False
DEGRADED=True
PROGRESSING=True for too long
MESSAGE contains DNSNotAvailable, DNSDegraded, sync failure, daemonset unavailable, service missing, etc.
```

However, not every DNS failure means `clusteroperator/dns` is degraded. For example:

- A single application uses the wrong service name.
- A namespace has an egress-deny NetworkPolicy blocking DNS.
- A Service has no endpoints.
- A workload overrides `dnsPolicy` or `dnsConfig` incorrectly.
- Only external DNS fails because upstream corporate DNS is unreachable.
- Only some nodes fail because of node-local network or placement issues.

A senior admin always scopes the blast radius first.

## 4. High-Level Troubleshooting Decision Tree

Use this quick decision tree before changing anything.

```text
1. Is clusteroperator/dns degraded?
   yes -> inspect operator, daemonsets, service, endpoints, logs.
   no  -> continue.

2. Do internal service names resolve from a fresh test pod?
   no  -> check CoreDNS pods, service endpoints, pod resolv.conf, DNS NetworkPolicy.
   yes -> continue.

3. Do external names resolve from a fresh test pod?
   no  -> check upstreamResolvers, node /etc/resolv.conf, firewall, proxy, split DNS.
   yes -> continue.

4. Is the issue limited to one namespace/app?
   yes -> check service name, endpoints, pod DNS policy, egress NetworkPolicy, app resolver behavior.
   no  -> continue.

5. Is the issue limited to pods on specific nodes?
   yes -> check CoreDNS placement, node networking, OVN/kube-proxy, MTU, firewall, node-resolver.
   no  -> inspect cluster-wide DNS load/performance and upstream resolver health.
```

## 5. Golden Commands for DNS Operator Troubleshooting

### 5.1 Operator and ClusterOperator Status

```bash
oc get co dns
oc describe co dns

oc get deployment -n openshift-dns-operator dns-operator
oc get pods -n openshift-dns-operator -o wide
oc describe deployment -n openshift-dns-operator dns-operator
oc logs -n openshift-dns-operator deployment/dns-operator -c dns-operator
```

Expected healthy state:

```text
NAME   VERSION   AVAILABLE   PROGRESSING   DEGRADED
dns    4.x       True        False         False
```

### 5.2 DNS CR and Rendered Configuration

```bash
oc get dns.operator/default -o yaml
oc describe dns.operator/default

oc get configmap -n openshift-dns dns-default -o yaml
```

Important fields:

```yaml
spec:
  managementState: Managed
  logLevel: Normal
  operatorLogLevel: Normal
  cache:
    positiveTTL: ...
    negativeTTL: ...
  servers: []
  upstreamResolvers: {}
  nodePlacement: {}
status:
  clusterDomain: cluster.local
  clusterIP: <dns-service-cluster-ip>
```

### 5.3 CoreDNS and node-resolver DaemonSets

```bash
oc get ds -n openshift-dns
oc get ds -n openshift-dns dns-default node-resolver -o wide
oc describe ds -n openshift-dns dns-default
oc describe ds -n openshift-dns node-resolver

oc get pods -n openshift-dns -o wide
oc get pods -n openshift-dns -l dns.operator.openshift.io/daemonset-dns=default -o wide
oc get pods -n openshift-dns -l dns.operator.openshift.io/daemonset-node-resolver=default -o wide
```

Healthy signs:

- `dns-default` desired/current/ready should match the intended number of eligible nodes.
- `node-resolver` should normally run on every node.
- CoreDNS pods should not be stuck in `CrashLoopBackOff`, `Pending`, `ImagePullBackOff`, or `ContainerCreating`.

### 5.4 DNS Service, Endpoints, and EndpointSlices

```bash
oc get svc -n openshift-dns dns-default -o wide
oc describe svc -n openshift-dns dns-default

oc get endpoints -n openshift-dns dns-default -o yaml
oc get endpointslices -n openshift-dns -l kubernetes.io/service-name=dns-default -o yaml
```

Critical checks:

- Service must have a ClusterIP.
- Endpoints/EndpointSlices must point to ready CoreDNS pods.
- DNS service ports should include UDP/TCP 53.

### 5.5 CoreDNS Logs

```bash
# Specific pod
oc logs -n openshift-dns -c dns <coredns-pod-name>

# Follow multiple CoreDNS pods
oc logs -n openshift-dns -c dns \
  -l dns.operator.openshift.io/daemonset-dns=default \
  -f --max-log-requests=6
```

### 5.6 Events

```bash
oc get events -n openshift-dns --sort-by='.lastTimestamp'
oc get events -n openshift-dns-operator --sort-by='.lastTimestamp'
```

Look for:

```text
FailedScheduling
FailedMount
BackOff
Unhealthy
FailedCreate
FailedUpdate
FailedPull
Readiness probe failed
Liveness probe failed
```

## 6. Creating a Reliable DNS Test Pod

In restricted or disconnected environments, your usual `busybox`, `dnsutils`, or `netshoot` image might not be available. Use whatever image exists in your registry. For OpenShift labs, UBI is often available.

### 6.1 UBI-Based Test Pod

```bash
oc new-project dns-test

oc run dns-test \
  -n dns-test \
  --image=registry.access.redhat.com/ubi9/ubi \
  --restart=Never \
  --command -- sleep 3600

oc wait pod/dns-test -n dns-test --for=condition=Ready --timeout=120s
```

Check resolver config:

```bash
oc exec -n dns-test dns-test -- cat /etc/resolv.conf
```

Test internal service DNS:

```bash
oc exec -n dns-test dns-test -- getent hosts kubernetes.default.svc
oc exec -n dns-test dns-test -- getent hosts kubernetes.default.svc.cluster.local
oc exec -n dns-test dns-test -- getent hosts image-registry.openshift-image-registry.svc
```

Test external DNS:

```bash
oc exec -n dns-test dns-test -- getent hosts redhat.com
```

If tools are available:

```bash
oc exec -n dns-test dns-test -- nslookup kubernetes.default.svc
oc exec -n dns-test dns-test -- dig kubernetes.default.svc.cluster.local
oc exec -n dns-test dns-test -- dig @<dns-service-cluster-ip> kubernetes.default.svc.cluster.local
```

### 6.2 Test from a Specific Node

If only one node is suspected:

```bash
oc run dns-test-worker01 \
  -n dns-test \
  --image=registry.access.redhat.com/ubi9/ubi \
  --restart=Never \
  --overrides='{
    "spec": {
      "nodeSelector": {"kubernetes.io/hostname": "worker01.example.com"},
      "containers": [{"name":"dns-test-worker01","image":"registry.access.redhat.com/ubi9/ubi","command":["sleep","3600"]}]
    }
  }'
```

Then run the same `cat /etc/resolv.conf` and `getent hosts` tests.

## 7. Understanding ClusterOperator DNS Conditions

Check:

```bash
oc describe clusteroperator/dns
```

Common condition meanings:

| Condition | Meaning | Troubleshooting direction |
|---|---|---|
| `Available=True` | At least one CoreDNS pod is available and DNS service has ClusterIP. | Basic DNS stack is up, but localized issues can still exist. |
| `Available=False` | DNS service/CoreDNS availability is broken. | Check daemonset, service, endpoints, operator logs. |
| `Progressing=True` | Desired and current DNS state differ. | Recent config change, rollout, upgrade, or stuck reconciliation. |
| `Degraded=True` | Operator detected a failure reconciling or running DNS. | Read condition message and operator logs first. |
| `Upgradeable=False` | DNS configuration blocks upgrade. | Common when `managementState: Unmanaged`. |

Senior admin approach:

1. Read `Reason` and `Message` exactly.
2. Check `LastTransitionTime` to correlate with recent changes.
3. Compare with cluster events, machine config changes, network changes, and DNS CR modifications.
4. Avoid deleting resources until you understand whether the operator is actively reconciling or blocked.

## Scenario 1: `clusteroperator/dns` is Degraded

### Symptoms

```bash
oc get co dns
```

Example:

```text
NAME   AVAILABLE   PROGRESSING   DEGRADED   MESSAGE
dns    False       True          True       DNS default is not available ...
```

Application symptoms:

- Pods cannot resolve `*.svc` names.
- Build pods fail to reach services.
- Operators show follow-on degradation.
- Internal registry resolution might fail.

### Investigation

```bash
oc describe co dns
oc get pods -n openshift-dns-operator -o wide
oc logs -n openshift-dns-operator deployment/dns-operator -c dns-operator

oc get ds,pods,svc,endpoints -n openshift-dns -o wide
oc describe ds -n openshift-dns dns-default
oc get events -n openshift-dns --sort-by='.lastTimestamp'
```

### Root Causes

Common causes include:

- DNS Operator pod not running.
- CoreDNS daemonset cannot schedule.
- CoreDNS pods crash due to bad generated Corefile or upstream configuration.
- DNS service missing ClusterIP or endpoints.
- Invalid `dns.operator/default` configuration.
- Wrong `nodePlacement` causing no eligible nodes.
- Manual edits to operator-managed resources.
- Image pull failures or cluster release payload issues during upgrade.

### Fix Strategy

1. Restore operator health first.
2. Restore CoreDNS daemonset readiness second.
3. Restore service endpoints third.
4. Test from a fresh pod last.

Commands:

```bash
oc rollout status deployment/dns-operator -n openshift-dns-operator
oc rollout status ds/dns-default -n openshift-dns

oc get dns.operator/default -o yaml
oc get configmap/dns-default -n openshift-dns -o yaml
```

If the issue started after a DNS CR change, review recent spec fields:

```bash
oc get dns.operator/default -o jsonpath='{.spec}' | jq .
```

If `jq` is not available:

```bash
oc get dns.operator/default -o yaml
```

Revert risky fields to default/minimal known-good state where appropriate:

```bash
oc patch dns.operator/default --type=merge -p '{"spec":{"managementState":"Managed","logLevel":"Normal","operatorLogLevel":"Normal","nodePlacement":{}}}'
```

Be careful: do not blindly remove valid forwarding settings in production. Capture the current YAML before patching:

```bash
oc get dns.operator/default -o yaml > dns-default-before-change.yaml
```

## Scenario 2: CoreDNS Pods are Pending

### Symptoms

```bash
oc get pods -n openshift-dns -o wide
```

Example:

```text
dns-default-abcde   0/2   Pending   0   10m
```

### Investigation

```bash
oc describe pod -n openshift-dns <pending-dns-pod>
oc describe ds -n openshift-dns dns-default
oc get nodes --show-labels
oc describe node <node-name>
oc get dns.operator/default -o yaml
```

### Common Causes

- Node selector does not match any node.
- Taints are present but CoreDNS tolerations do not match.
- Node pressure: memory, disk, PID, or ephemeral storage.
- Control plane / infra nodes tainted and worker nodes unavailable.
- `nodePlacement` was customized incorrectly.

### Fix

Check current placement config:

```bash
oc get dns.operator/default -o jsonpath='{.spec.nodePlacement}'
```

Return to default placement if a bad custom placement caused the issue:

```bash
oc patch dns.operator/default --type=merge -p '{"spec":{"nodePlacement":{}}}'
```

If you intentionally restrict placement, ensure matching labels and tolerations exist:

```bash
oc get nodes -L node-role.kubernetes.io/worker,kubernetes.io/os
oc describe node <node> | egrep -i 'Taints|Labels'
```

Example controlled placement:

```yaml
apiVersion: operator.openshift.io/v1
kind: DNS
metadata:
  name: default
spec:
  nodePlacement:
    nodeSelector:
      kubernetes.io/os: linux
    tolerations:
    - key: node-role.kubernetes.io/master
      operator: Exists
      effect: NoSchedule
```

Production note: restricting DNS pods to a small node set can create cross-node DNS dependency and increase outage blast radius. It is usually safer to run CoreDNS broadly unless there is a strong security or architecture reason.

## Scenario 3: CoreDNS Pods are CrashLoopBackOff

### Symptoms

```bash
oc get pods -n openshift-dns
```

Example:

```text
dns-default-x7k9p   1/2   CrashLoopBackOff   12   15m
```

### Investigation

```bash
oc logs -n openshift-dns <coredns-pod> -c dns --previous
oc logs -n openshift-dns <coredns-pod> -c dns
oc describe pod -n openshift-dns <coredns-pod>
oc get cm -n openshift-dns dns-default -o yaml
oc get dns.operator/default -o yaml
oc logs -n openshift-dns-operator deployment/dns-operator -c dns-operator
```

### Common Causes

- Invalid CoreDNS configuration generated from invalid DNS CR fields.
- Bad forwarding configuration.
- TLS forwarding configuration points to wrong CA, wrong server name, or unreachable upstream.
- Resource pressure on node.
- Image/runtime issue.

### Fix

If bad forwarding was recently added, validate:

```yaml
spec:
  servers:
  - name: example-server
    zones:
    - example.com
    forwardPlugin:
      policy: Random
      upstreams:
      - 10.10.10.10
      - 10.10.10.11:53
```

Rules to remember:

- `spec.servers[].zones` is for zones outside the cluster domain.
- Do not set `cluster.local` as a forwarding zone.
- `forwardPlugin.upstreams` has a practical documented limit. Keep it small and intentional.
- If using DNS-over-TLS, verify CA bundle, server name, transport, and port.

After correcting the DNS CR:

```bash
oc rollout status ds/dns-default -n openshift-dns
oc get pods -n openshift-dns -o wide
```

## Scenario 4: DNS Service Has No Endpoints

### Symptoms

Pods have correct nameserver IP but DNS queries time out.

```bash
oc get svc -n openshift-dns dns-default
oc get endpoints -n openshift-dns dns-default
```

Example:

```text
NAME          ENDPOINTS   AGE
dns-default   <none>      100d
```

### Investigation

```bash
oc get pods -n openshift-dns -l dns.operator.openshift.io/daemonset-dns=default -o wide
oc describe svc -n openshift-dns dns-default
oc describe endpoints -n openshift-dns dns-default
oc get endpointslices -n openshift-dns -l kubernetes.io/service-name=dns-default -o yaml
```

### Common Causes

- CoreDNS pods are not Ready.
- Readiness probe failing.
- Service selector does not match pods due to unsupported manual edit.
- DNS Operator not reconciling because `managementState: Unmanaged`.
- CoreDNS pods exist but are only on nodes unreachable from workload nodes.

### Fix

First restore `Managed` state:

```bash
oc get dns.operator/default -o jsonpath='{.spec.managementState}{"\n"}'
oc patch dns.operator/default --type=merge -p '{"spec":{"managementState":"Managed"}}'
```

Then verify operator reconciliation:

```bash
oc logs -n openshift-dns-operator deployment/dns-operator -c dns-operator
oc rollout status ds/dns-default -n openshift-dns
oc get endpoints -n openshift-dns dns-default
```

If service or daemonset was manually modified, let the operator reconcile. In severe cases, after taking backups and only with change approval, deleting operator-managed child resources can force recreation:

```bash
oc get svc,ds,cm -n openshift-dns -o yaml > openshift-dns-backup.yaml
```

Do not delete critical resources during a production incident without understanding impact.

## Scenario 5: Internal Service DNS Fails but DNS Operator is Healthy

### Symptoms

`oc get co dns` is healthy, but application logs show:

```text
no such host
Name or service not known
Temporary failure in name resolution
lookup mysql on 172.30.0.10:53: no such host
```

### Investigation

From a test pod in the same namespace:

```bash
oc exec -n <namespace> <pod> -- cat /etc/resolv.conf
oc exec -n <namespace> <pod> -- getent hosts <service-name>
oc exec -n <namespace> <pod> -- getent hosts <service-name>.<namespace>.svc
oc exec -n <namespace> <pod> -- getent hosts <service-name>.<namespace>.svc.cluster.local
```

Check the service and endpoints:

```bash
oc get svc -n <namespace> <service-name> -o wide
oc get endpoints -n <namespace> <service-name> -o wide
oc get endpointslices -n <namespace> -l kubernetes.io/service-name=<service-name> -o yaml
oc describe svc -n <namespace> <service-name>
```

### Common Causes

- Service name typo.
- Wrong namespace.
- Service exists but has no endpoints.
- Service selector does not match pod labels.
- Headless service behavior misunderstood.
- Application uses short name from a different namespace.
- Pod has `dnsPolicy: Default` or custom `dnsConfig` instead of `ClusterFirst`.
- Namespace egress NetworkPolicy blocks DNS.

### Fix Examples

#### Fix wrong service selector

```bash
oc get pods -n <namespace> --show-labels
oc describe svc -n <namespace> <service-name>
```

Patch service selector:

```bash
oc patch svc <service-name> -n <namespace> -p '{"spec":{"selector":{"app":"myapp"}}}'
```

#### Use cross-namespace FQDN

Instead of:

```text
mysql
```

Use:

```text
mysql.database.svc.cluster.local
```

#### Check pod DNS policy

```bash
oc get pod <pod> -n <namespace> -o yaml | egrep -A5 'dnsPolicy|dnsConfig'
```

Normal application pods should usually use:

```yaml
dnsPolicy: ClusterFirst
```

#### Allow DNS in NetworkPolicy

If the namespace has default-deny egress, allow DNS to OpenShift DNS:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: my-project
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

Note: NetworkPolicy behavior depends on your CNI and policy combination. In OpenShift SDN/OVN-Kubernetes, egress policies can break DNS if DNS egress is not explicitly allowed.

## Scenario 6: External DNS Fails but Internal Service DNS Works

### Symptoms

Inside a pod:

```bash
getent hosts kubernetes.default.svc        # works
getent hosts redhat.com                    # fails
```

### Meaning

CoreDNS is probably serving internal cluster records, but upstream DNS resolution is broken.

### Investigation

```bash
oc get dns.operator/default -o yaml
oc get cm -n openshift-dns dns-default -o yaml
oc logs -n openshift-dns -c dns -l dns.operator.openshift.io/daemonset-dns=default --tail=100
```

Check node resolver configuration from a node:

```bash
oc debug node/<node-name>
chroot /host
cat /etc/resolv.conf
```

Test upstream reachability from a debug pod or node:

```bash
# If tools exist
dig @<upstream-dns-ip> redhat.com
nslookup redhat.com <upstream-dns-ip>

# Basic network tests
nc -vz <upstream-dns-ip> 53
nc -vzu <upstream-dns-ip> 53
```

### Common Causes

- Upstream corporate DNS server down.
- Firewall blocks UDP/TCP 53 from cluster nodes.
- Firewall blocks DNS-over-TLS port 853.
- Incorrect `spec.upstreamResolvers` address/port.
- DNS forwarding zone is wrong.
- Split-horizon DNS points to a resolver not reachable from OpenShift nodes.
- Proxy settings misunderstood: DNS does not use HTTP proxy.
- Upstream resolver rate-limits large clusters.
- `ndots:5` causes high query load for external names.

### Fix: Configure Upstream Resolvers

Example:

```yaml
apiVersion: operator.openshift.io/v1
kind: DNS
metadata:
  name: default
spec:
  upstreamResolvers:
    policy: Sequential
    upstreams:
    - type: Network
      address: 10.10.10.10
      port: 53
    - type: Network
      address: 10.10.10.11
      port: 53
```

Apply carefully:

```bash
oc edit dns.operator/default
```

Verify generated CoreDNS config:

```bash
oc get cm -n openshift-dns dns-default -o yaml
```

Test again:

```bash
oc exec -n dns-test dns-test -- getent hosts redhat.com
```

## Scenario 7: DNS Forwarding Zone Misconfiguration

### Use Case

You want `*.corp.example.com` to resolve through corporate DNS, while normal internet names use default upstreams.

### Correct Pattern

```yaml
apiVersion: operator.openshift.io/v1
kind: DNS
metadata:
  name: default
spec:
  servers:
  - name: corp-dns
    zones:
    - corp.example.com
    forwardPlugin:
      policy: Sequential
      upstreams:
      - 10.20.30.10
      - 10.20.30.11
```

### Common Mistakes

| Mistake | Result |
|---|---|
| Forwarding `cluster.local` | Invalid/unsupported for cluster service discovery zone. |
| Forwarding too broad a zone such as `com` | Unexpected query routing and latency. |
| Using DNS servers unreachable from cluster nodes | Timeouts. |
| Missing TCP 53 | Large responses or TCP fallback fail. |
| Wrong split-DNS resolver | Apps resolve private names to public/wrong IPs. |
| Using one upstream without redundancy | Single point of failure. |

### Validation

```bash
oc get dns.operator/default -o yaml
oc get cm -n openshift-dns dns-default -o yaml
oc logs -n openshift-dns -c dns -l dns.operator.openshift.io/daemonset-dns=default --tail=200

oc exec -n dns-test dns-test -- getent hosts app.corp.example.com
oc exec -n dns-test dns-test -- getent hosts redhat.com
oc exec -n dns-test dns-test -- getent hosts kubernetes.default.svc
```

All three tests should behave as expected.

## Scenario 8: DNS-over-TLS Forwarding Issues

### Symptoms

- Internal service names resolve.
- External or forwarded zones fail.
- CoreDNS logs show TLS handshake or certificate validation errors.
- Queries time out on port 853.

### Investigation

```bash
oc get dns.operator/default -o yaml
oc get cm -n openshift-dns dns-default -o yaml
oc logs -n openshift-dns -c dns -l dns.operator.openshift.io/daemonset-dns=default --tail=200
```

Check network path:

```bash
nc -vz <tls-dns-server-ip> 853
openssl s_client -connect <tls-dns-server-ip>:853 -servername <dns-server-name>
```

### Common Causes

- Upstream does not support DNS-over-TLS.
- Port 853 blocked.
- TLS server name does not match certificate SAN/CN.
- Custom CA bundle missing or wrong.
- CA ConfigMap placed in wrong namespace.
- CA ConfigMap key is wrong.

### Fix Pattern

For TLS forwarding, verify:

- `transport` is TLS where required.
- `serverName` matches certificate.
- CA bundle exists in `openshift-config` if using custom CA.
- ConfigMap contains the expected CA key.
- Firewall permits TCP 853.

Rollback to plain DNS temporarily only if approved by security policy.

## Scenario 9: DNS Works from Some Nodes but Fails from Others

### Symptoms

- Pods on worker01 resolve names.
- Pods on worker02 fail.
- `clusteroperator/dns` might still show healthy if enough DNS pods are available.

### Investigation

Compare test pods pinned to each node:

```bash
oc get pods -A -o wide | grep <node-name>
```

Check CoreDNS placement:

```bash
oc get pods -n openshift-dns -o wide
oc get ds -n openshift-dns dns-default -o wide
oc describe ds -n openshift-dns dns-default
```

Check node network health:

```bash
oc get nodes
oc describe node <bad-node>
oc adm top node <bad-node>
```

Check OVN/network operator symptoms:

```bash
oc get co network
oc describe co network
oc get pods -n openshift-ovn-kubernetes -o wide | grep <bad-node>
```

### Common Causes

- Node has broken CNI/OVN state.
- Node cannot reach DNS service endpoints on other nodes.
- CoreDNS restricted to nodes that are unreachable from some workloads.
- MTU mismatch causing larger DNS responses to fail.
- Host firewall/security group blocks UDP/TCP 53 between nodes.
- Node resource pressure affects DNS or networking.

### Fix Approach

1. Confirm if DNS service ClusterIP is reachable from affected node/pod.
2. Confirm if affected node has local CoreDNS pod.
3. Check OVN/node network pods on the affected node.
4. If node networking is broken, troubleshoot as node/network issue, not DNS Operator only.
5. Consider draining/rebooting a bad worker only after collecting evidence.

Useful commands:

```bash
oc debug node/<bad-node>
chroot /host
crictl ps | grep dns
ip route
ss -lunpt | grep ':53'
```

## Scenario 10: `node-resolver` Issues and Internal Registry Name Resolution

### What node-resolver Does

The `node-resolver` daemonset is managed by the DNS Operator. It helps node-level resolution for the internal image registry service name, especially for container runtime image pulls involving:

```text
image-registry.openshift-image-registry.svc
```

It updates node host resolver/hosts behavior so the node can resolve the internal registry service.

### Symptoms

- Build or deployment image pulls from internal registry fail.
- Pods cannot pull images such as:

```text
image-registry.openshift-image-registry.svc:5000/project/image:tag
```

- Node-level tools cannot resolve internal registry service.
- `node-resolver` pods missing or failing.

### Investigation

```bash
oc get ds -n openshift-dns node-resolver -o wide
oc get pods -n openshift-dns -l dns.operator.openshift.io/daemonset-node-resolver=default -o wide
oc describe ds -n openshift-dns node-resolver
oc logs -n openshift-dns <node-resolver-pod>
```

Debug node:

```bash
oc debug node/<node-name>
chroot /host
getent hosts image-registry.openshift-image-registry.svc
cat /etc/hosts | grep image-registry
```

### Common Causes

- `node-resolver` daemonset not scheduled on all nodes.
- Node taints/labels prevent scheduling.
- DNS Operator not reconciling.
- Internal registry service missing or moved.
- Node filesystem or permissions issue.

### Fix

Restore DNS Operator to `Managed`, fix scheduling, and verify node-resolver rollout:

```bash
oc patch dns.operator/default --type=merge -p '{"spec":{"managementState":"Managed"}}'
oc rollout status ds/node-resolver -n openshift-dns
```

Then test from the node.

## Scenario 11: DNS Query Timeouts Under Load

### Symptoms

Application logs:

```text
lookup service.namespace.svc.cluster.local on 172.30.0.10:53: read udp ... i/o timeout
Temporary failure in name resolution
```

Cluster symptoms:

- DNS works intermittently.
- Only high-traffic apps fail.
- Failures increase during deployments, node restarts, or traffic spikes.
- External DNS failures more frequent than internal DNS failures.

### Investigation

```bash
oc get pods -n openshift-dns -o wide
oc adm top pods -n openshift-dns
oc adm top nodes

oc logs -n openshift-dns -c dns \
  -l dns.operator.openshift.io/daemonset-dns=default \
  --tail=300
```

Check if upstream DNS is slow or rate-limiting:

```bash
oc exec -n dns-test dns-test -- getent hosts redhat.com
oc exec -n dns-test dns-test -- getent hosts a-known-internal-service.default.svc.cluster.local
```

If internal is fast but external times out, upstream is likely involved.

### Root Causes

- Upstream resolver overloaded or rate-limiting.
- Low CoreDNS cache TTL increases query volume.
- Application repeatedly resolves external short names with `ndots:5` overhead.
- Large number of short-lived pods generating DNS bursts.
- NetworkPolicy or firewall intermittently drops UDP.
- TCP fallback blocked.
- MTU/fragmentation issue.
- CoreDNS pods CPU throttled due to node pressure.

### Fix Options

#### Tune DNS Cache Carefully

Example:

```yaml
apiVersion: operator.openshift.io/v1
kind: DNS
metadata:
  name: default
spec:
  cache:
    positiveTTL: 900s
    negativeTTL: 30s
```

Do not set TTLs too low. Low TTL values can increase load on CoreDNS and upstream resolvers.

#### Use FQDNs for External Names in Applications

Use:

```text
api.example.com.
```

instead of:

```text
api.example.com
```

The trailing dot tells resolvers it is absolute and can reduce search-domain expansion behavior in some clients.

#### Allow TCP 53

Many admins allow only UDP 53 and forget TCP 53. DNS may require TCP for large responses, truncation fallback, or some resolver behavior.

NetworkPolicy/firewall should allow both:

```text
UDP/53
TCP/53
```

## Scenario 12: `managementState: Unmanaged` Causes Drift or Upgrade Block

### Meaning

`managementState: Unmanaged` tells the DNS Operator to stop managing DNS resources. This is useful only for temporary support-approved workarounds or tests.

### Symptoms

```bash
oc get dns.operator/default -o jsonpath='{.spec.managementState}{"\n"}'
```

Output:

```text
Unmanaged
```

Possible effects:

- Manual changes stay in place.
- Operator does not repair drift.
- Cluster upgrade can be blocked.
- DNS service/daemonset/configmap may become inconsistent over time.

### Fix

Return to managed mode:

```bash
oc patch dns.operator/default --type=merge -p '{"spec":{"managementState":"Managed"}}'
```

Verify:

```bash
oc get dns.operator/default -o jsonpath='{.spec.managementState}{"\n"}'
oc get co dns
oc rollout status ds/dns-default -n openshift-dns
```

Production rule: never leave the DNS Operator unmanaged after an incident unless Red Hat support or your internal platform architecture explicitly requires it.

## 10. DNS Forwarding Configuration Patterns

### 10.1 Default Upstream Resolvers

If `spec.upstreamResolvers` is not set, CoreDNS typically uses system resolver configuration from the node environment as rendered into CoreDNS behavior.

Check:

```bash
oc get dns.operator/default -o yaml
oc get cm -n openshift-dns dns-default -o yaml
```

### 10.2 Forward Specific Corporate Zone

```yaml
apiVersion: operator.openshift.io/v1
kind: DNS
metadata:
  name: default
spec:
  servers:
  - name: corp-example
    zones:
    - corp.example.com
    forwardPlugin:
      policy: Sequential
      upstreams:
      - 10.10.10.10
      - 10.10.10.11
```

### 10.3 Configure Default Upstream Resolvers

```yaml
apiVersion: operator.openshift.io/v1
kind: DNS
metadata:
  name: default
spec:
  upstreamResolvers:
    policy: Sequential
    upstreams:
    - type: Network
      address: 10.10.10.10
      port: 53
    - type: Network
      address: 10.10.10.11
      port: 53
```

### 10.4 Validate Forwarding

```bash
oc get cm -n openshift-dns dns-default -o yaml
oc logs -n openshift-dns -c dns -l dns.operator.openshift.io/daemonset-dns=default --tail=100

oc exec -n dns-test dns-test -- getent hosts host.corp.example.com
oc exec -n dns-test dns-test -- getent hosts redhat.com
oc exec -n dns-test dns-test -- getent hosts kubernetes.default.svc
```

A correct forwarding change should not break `cluster.local` names.

## 11. DNS and NetworkPolicy

### 11.1 Why NetworkPolicy Breaks DNS

If a namespace has default-deny egress, pods cannot talk to OpenShift DNS unless allowed. This often looks like a DNS Operator outage, but the operator is healthy.

Example default-deny egress:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
spec:
  podSelector: {}
  policyTypes:
  - Egress
```

After this, all egress is blocked unless allowed. DNS is egress traffic.

### 11.2 Allow DNS Egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: app-project
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

### 11.3 Test After Applying

```bash
oc exec -n app-project <pod> -- getent hosts kubernetes.default.svc
oc exec -n app-project <pod> -- getent hosts redhat.com
```

If internal DNS works but external HTTP still fails, allow application egress separately. DNS allow rules only permit name resolution, not application traffic.

## 12. DNS and Routes: Common Misunderstanding

The DNS Operator does **not** automatically make external route hostnames resolvable for clients outside the cluster.

For routes like:

```text
https://myapp.apps.ocp4.example.com
```

You need external DNS records such as:

```text
*.apps.ocp4.example.com -> router/load balancer IP
```

or records managed by cloud DNS / External DNS Operator.

If `curl https://myapp.apps...` fails from your laptop due to name resolution, check external DNS, not CoreDNS.

If a pod inside the cluster cannot resolve an external route hostname, then CoreDNS upstream forwarding may be involved.

## 17. Production-Safe Remediation Principles

### 17.1 Do First

- Read `oc describe co dns` message.
- Capture current DNS CR YAML.
- Check CoreDNS daemonset health.
- Check DNS service endpoints.
- Test from a fresh pod.
- Compare internal vs external DNS.
- Check NetworkPolicy before changing DNS Operator config.

### 17.2 Avoid Unless You Know Why

- Do not edit `openshift-dns/dns-default` ConfigMap directly in `Managed` mode.
- Do not delete daemonsets/services blindly.
- Do not leave `managementState: Unmanaged` after testing.
- Do not enable `Trace` logs for long periods.
- Do not point all DNS to a single upstream resolver.
- Do not block TCP 53.
- Do not restrict DNS pods to too few nodes without architecture approval.

### 17.3 Restore Known-Good Baseline

A minimal conservative baseline:

```yaml
apiVersion: operator.openshift.io/v1
kind: DNS
metadata:
  name: default
spec:
  managementState: Managed
  logLevel: Normal
  operatorLogLevel: Normal
  nodePlacement: {}
```

Do not remove `servers`, `upstreamResolvers`, or `cache` from a real production cluster without confirming they are not required.

## 18. Interview / Exam / L3 Support Style Questions

### Q1. `oc get co dns` shows `Available=True`, but one application cannot resolve `mysql`. What do you check?

Check whether `mysql` service exists in the same namespace, whether service endpoints exist, whether the app is in another namespace and needs `mysql.database.svc.cluster.local`, whether pod `dnsPolicy` is normal, and whether NetworkPolicy blocks DNS egress.

### Q2. Internal service names resolve, but `redhat.com` fails. Is DNS Operator broken?

Not necessarily. CoreDNS internal service discovery works. Check upstream resolvers, DNS forwarding, firewall to UDP/TCP 53 or TCP 853, node `/etc/resolv.conf`, and corporate DNS health.

### Q3. Why should TCP 53 be allowed?

DNS normally uses UDP, but TCP can be required for large responses, truncated UDP responses, zone transfers in other contexts, and some resolver fallback behavior. Blocking TCP 53 causes intermittent or domain-specific failures.

### Q4. Why is `managementState: Unmanaged` dangerous?

The operator stops reconciling resources. Manual drift is not repaired, cluster upgrades can be blocked, and DNS resources can become stale or inconsistent.

### Q5. Why can NetworkPolicy break DNS?

DNS queries from a pod to OpenShift DNS are egress traffic. A default-deny egress policy blocks UDP/TCP 53 unless explicitly allowed.

### Q6. What is the difference between `spec.servers` and `spec.upstreamResolvers`?

`spec.servers` configures forwarding for specific zones. `spec.upstreamResolvers` configures default upstream resolvers for queries that are not handled by cluster DNS or more specific server blocks.

### Q7. What does `node-resolver` help with?

It helps node-level resolution for the internal image registry service name so the container runtime can resolve the registry service during image pulls.

### Q8. Why can DNS fail only on one node?

Node-specific CNI problems, routing, MTU, firewall/security group rules, resource pressure, or placement causing pods to use remote CoreDNS endpoints through a broken path.

## 19. Quick Runbook: 15-Minute DNS Incident Flow

```bash
# 1. Check cluster DNS operator
oc get co dns
oc describe co dns

# 2. Check DNS operator deployment
oc get pods -n openshift-dns-operator -o wide
oc logs -n openshift-dns-operator deployment/dns-operator -c dns-operator --tail=100

# 3. Check CoreDNS and node-resolver
oc get ds,pods,svc,endpoints -n openshift-dns -o wide

# 4. Check DNS CR
oc get dns.operator/default -o yaml

# 5. Check logs
oc logs -n openshift-dns -c dns -l dns.operator.openshift.io/daemonset-dns=default --tail=200

# 6. Create test pod
oc new-project dns-test || true
oc run dns-test -n dns-test --image=registry.access.redhat.com/ubi9/ubi --restart=Never --command -- sleep 3600
oc wait pod/dns-test -n dns-test --for=condition=Ready --timeout=120s

# 7. Test resolver config and internal/external DNS
oc exec -n dns-test dns-test -- cat /etc/resolv.conf
oc exec -n dns-test dns-test -- getent hosts kubernetes.default.svc
oc exec -n dns-test dns-test -- getent hosts image-registry.openshift-image-registry.svc
oc exec -n dns-test dns-test -- getent hosts redhat.com
```

Interpretation:

| Result | Meaning |
|---|---|
| Internal and external fail | CoreDNS service path, endpoints, pod DNS config, or DNS egress blocked. |
| Internal works, external fails | Upstream DNS/forwarding/firewall issue. |
| Only one app fails | App namespace/service/NetworkPolicy/dnsPolicy issue. |
| Only one node fails | Node networking/placement/OVN/firewall issue. |
| `co dns` degraded | Operator/CoreDNS managed stack issue. |

## 23. Final Practical Advice

In real OpenShift operations, DNS incidents are high-pressure because everything looks broken at once. Stay systematic:

1. Start with `oc get co dns` and `oc describe co dns`.
2. Validate CoreDNS pods and service endpoints.
3. Test from a clean pod.
4. Separate internal service DNS from external upstream DNS.
5. Check NetworkPolicy and node-specific symptoms before changing operator config.
6. Do not leave debug settings or unmanaged state behind.

The best OpenShift admins do not just restart CoreDNS. They identify exactly where the DNS query fails and fix that layer.
