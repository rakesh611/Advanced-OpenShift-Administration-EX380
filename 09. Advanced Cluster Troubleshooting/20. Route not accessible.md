# Route Not Accessible - Advanced OpenShift Administration Troubleshooting Guide

**Topic:** Route not accessible  
**Area:** Advanced Cluster Troubleshooting  
**Audience:** Advanced OpenShift Administrator / L3 Support / SRE / Platform Engineer  
**Experience level:** ~10 years Linux, Kubernetes, OpenShift, networking, and production support  
**Applies to:** OpenShift Container Platform 4.x. Commands are written for `oc` CLI and HAProxy-based OpenShift Ingress Controller.

---

## 1. What does "Route not accessible" mean?

In OpenShift, a **Route** exposes an internal Kubernetes `Service` through the OpenShift Ingress Controller, normally the HAProxy router. A route problem means the external request is not successfully reaching the application pod through this path:

```text
Client / Browser / curl
        |
        v
DNS for route host
        |
        v
External Load Balancer / VIP / NodePort / HostNetwork endpoint
        |
        v
OpenShift router pod in openshift-ingress namespace
        |
        v
Route admission and HAProxy frontend/backend configuration
        |
        v
Kubernetes Service
        |
        v
Endpoints / EndpointSlices
        |
        v
Application Pod IP and targetPort
        |
        v
Application process listening inside the container
```

When a route is not accessible, do **not** start by deleting and recreating resources. Troubleshoot layer by layer. In production, many route issues are caused by a simple mismatch between route, service, target port, pod labels, DNS, TLS termination, router shard selection, or NetworkPolicy.

## 2. Common symptoms and what they usually mean

| Symptom | Typical meaning | First area to check |
|---|---|---|
| `Could not resolve host` | DNS does not resolve the route hostname | External DNS / wildcard apps DNS / route host typo |
| `Connection timed out` | Traffic cannot reach router/LB/VIP/node | Firewall, LB health, endpoint publishing strategy, security group, router pods not on expected nodes |
| `Connection refused` | IP reachable but port not listening | LB target wrong, router pods down, HostNetwork/NodePort problem, port 80/443 blocked |
| HTTP `404` from OpenShift router | Router received traffic but no admitted route matched host/path | Route admission, hostname mismatch, path mismatch, wrong shard, duplicate host |
| HTTP `503 Service Unavailable` | Router matched the route but no usable backend endpoint | Service selector, endpoints, pod readiness, targetPort, NetworkPolicy, backend health |
| HTTP `502 Bad Gateway` | Router connected but backend failed/protocol mismatch | TLS re-encrypt CA mismatch, app closed connection, wrong backend protocol |
| HTTP `504 Gateway Timeout` | Router waited too long for backend response | Slow app, route timeout, backend dependency, NetworkPolicy/drop, overloaded pod |
| TLS certificate warning | Cert SAN/CN does not match route host or chain incomplete | Route TLS certificate, default router certificate, CA chain |
| `SSL handshake failure` | TLS termination mode or cert trust mismatch | Edge/reencrypt/passthrough config, backend TLS, destination CA |
| Works with `curl -k` only | Client does not trust certificate chain | CA chain, cert issuer, browser/client trust store |
| Works inside cluster but not outside | App/service okay, ingress edge problem | DNS, firewall, LB, router exposure |
| Works by ClusterIP but not route | Service/backend okay, route/router problem | Route admission, TLS, router logs, NetworkPolicy from router |
| Works by route from some clients only | Client/network/source-specific issue | IP allowlist, firewall, proxy, split DNS, source-based LB/security groups |

## 3. Important OpenShift objects involved

| Object | Namespace | Purpose |
|---|---|---|
| `Route` | Application namespace | Exposes a service by hostname/path |
| `Service` | Application namespace | Stable virtual IP and port for pods |
| `Endpoints` / `EndpointSlice` | Application namespace | Actual backend pod IPs selected by service |
| `Pod` | Application namespace | Runs the application process |
| `Deployment` / `DeploymentConfig` / `StatefulSet` | Application namespace | Owns pod lifecycle |
| `NetworkPolicy` | Application namespace | Can block router-to-pod traffic |
| `IngressController` | `openshift-ingress-operator` | Defines router deployment, domain, replicas, sharding, TLS, endpoint publishing |
| Router pods | `openshift-ingress` | HAProxy router pods serving routes |
| `ClusterOperator/ingress` | Cluster scope | Health of Ingress Operator |
| `ClusterOperator/dns` | Cluster scope | Health of cluster DNS operator |
| External LB / VIP | Infrastructure | Forwards external traffic to router endpoints |
| External DNS | Infrastructure | Resolves `*.apps.<cluster-domain>` to router/LB |

## 4. Five-minute production triage

Set variables first:

```bash
NS=<application_namespace>
ROUTE=<route_name>
SVC=<service_name>
```

### 4.1 Check route, service, endpoints, pods

```bash
oc get route -n $NS
oc get route $ROUTE -n $NS -o wide
oc describe route $ROUTE -n $NS

oc get svc -n $NS
oc describe svc $SVC -n $NS

oc get endpoints $SVC -n $NS -o wide
oc get endpointslice -n $NS -l kubernetes.io/service-name=$SVC -o wide

oc get pods -n $NS -o wide
oc get pods -n $NS --show-labels
```

### 4.2 Extract the route host and test

```bash
HOST=$(oc get route $ROUTE -n $NS -o jsonpath='{.spec.host}')
echo $HOST

curl -v http://$HOST/
curl -vk https://$HOST/
```

For path-based routes:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.spec.path}{"\n"}'
curl -vk https://$HOST/<path>
```

### 4.3 Check cluster Ingress health

```bash
oc get co ingress dns network
oc describe co ingress
oc describe co dns

oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller/default -n openshift-ingress-operator

oc get pods -n openshift-ingress -o wide
oc get svc -n openshift-ingress
oc get deployment -n openshift-ingress
```

### 4.4 Check router logs

```bash
oc logs -n openshift-ingress deployment/router-default --tail=100
```

If access logs are enabled to the sidecar container:

```bash
oc logs -n openshift-ingress deployment/router-default -c logs --tail=100
```

### 4.5 Check from inside the cluster

```bash
oc run curltest -n $NS --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
curl -v http://$SVC:8080/
curl -vk https://$HOST/
```

If the UBI image does not have tools:

```bash
dnf -y install bind-utils iproute iputils curl nc
```

## 5. Understand the route lifecycle

A route must pass through several states before it works:

1. The `Route` object must exist and point to the correct `Service`.
2. The route must be **admitted** by at least one Ingress Controller.
3. The router must generate an HAProxy configuration for the route.
4. DNS must resolve the route host to the correct router/LB address.
5. Client traffic must reach the router on the correct port.
6. The router must match the request host and path.
7. The router must find healthy service endpoints.
8. The application pod must accept the connection and return a valid response.

The most useful command for route admission is:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{range .status.ingress[*]}router={.routerName} host={.host} admitted={range .conditions[*]}{.type}={.status} reason={.reason} message={.message}{end}{"\n"}{end}'
```

A healthy route normally shows something similar to:

```text
router=default host=myapp.apps.example.com admitted=Admitted=True reason=Admitted message=
```

If `Admitted=False`, the router is not serving the route. Common reasons are duplicate hostname, sharding selector mismatch, wildcard policy rejection, HSTS admission policy rejection, or namespace ownership policy conflict.

## 6. Route object troubleshooting

### 6.1 Check basic route fields

```bash
oc get route $ROUTE -n $NS -o yaml
```

Important fields:

```yaml
spec:
  host: app.apps.example.com
  path: /api
  to:
    kind: Service
    name: myservice
    weight: 100
  port:
    targetPort: 8080-tcp
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
```

Verify:

| Field | What to verify |
|---|---|
| `spec.host` | Host matches the URL being requested |
| `spec.path` | Requested URL path matches route path |
| `spec.to.name` | Service exists in same namespace |
| `spec.port.targetPort` | Route points to a service port name or number that exists |
| `spec.tls.termination` | Correct TLS model: edge, reencrypt, or passthrough |
| `status.ingress` | Route is admitted by expected router |

### 6.2 Route points to wrong service

Symptom:

```text
HTTP 503, 404, or response from wrong application
```

Check:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.spec.to.name}{"\n"}'
oc get svc -n $NS
```

Fix:

```bash
oc patch route $ROUTE -n $NS --type=merge -p '{"spec":{"to":{"kind":"Service","name":"correct-service"}}}'
```

Or recreate cleanly:

```bash
oc delete route $ROUTE -n $NS
oc expose svc correct-service -n $NS --name=$ROUTE --hostname=$HOST
```

### 6.3 Route targetPort mismatch

Symptom:

```text
Route exists, service exists, endpoints exist, but router returns 503/502 or traffic goes nowhere.
```

Check route port:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.spec.port.targetPort}{"\n"}'
```

Check service ports:

```bash
oc get svc $SVC -n $NS -o yaml
```

Example service:

```yaml
ports:
- name: http
  port: 8080
  targetPort: 8080
```

Route should use service port name or matching port:

```yaml
spec:
  port:
    targetPort: http
```

Fix:

```bash
oc patch route $ROUTE -n $NS --type=merge -p '{"spec":{"port":{"targetPort":"http"}}}'
```

### 6.4 Path mismatch

Path-based routes are host + path based. Example:

```yaml
spec:
  host: app.apps.example.com
  path: /api
```

This does not necessarily match every request to `/`. Test correct path:

```bash
curl -vk https://app.apps.example.com/api
curl -vk https://app.apps.example.com/api/health
```

Check all routes with same host:

```bash
oc get route -A --field-selector spec.host=$HOST
```

If `--field-selector` is not supported for `spec.host` in your version, use:

```bash
oc get route -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,HOST:.spec.host,PATH:.spec.path,SVC:.spec.to.name,TLS:.spec.tls.termination' | grep "$HOST"
```

### 6.5 Duplicate hostname across namespaces

Symptom:

```text
Route status shows Admitted=False, HostAlreadyClaimed, or route not selected.
```

Find duplicate host:

```bash
oc get route -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,HOST:.spec.host,PATH:.spec.path,ADMITTED:.status.ingress[*].conditions[*].status,REASON:.status.ingress[*].conditions[*].reason' | grep "$HOST"
```

Fix options:

1. Use unique hostname.
2. Delete old/stale route claiming the same host.
3. For controlled multi-namespace path sharing, configure `routeAdmission.namespaceOwnership` carefully at the IngressController level.

Do not change cluster-wide namespace ownership policy casually in production. It affects route admission behavior cluster-wide or per ingress shard.

## 7. Service and endpoint troubleshooting

A route does not send traffic directly to pods. It sends traffic to a Kubernetes `Service`. The service selects pods using labels and creates endpoints.

### 7.1 Service selector mismatch

Symptom:

```text
HTTP 503 from route
oc get endpoints <svc> shows <none>
```

Check service selector:

```bash
oc get svc $SVC -n $NS -o jsonpath='{.spec.selector}{"\n"}'
oc describe svc $SVC -n $NS
```

Check pod labels:

```bash
oc get pods -n $NS --show-labels
```

Example problem:

```yaml
Service selector:
  app: frontend

Pod labels:
  deployment: frontend
```

Fix service selector:

```bash
oc patch svc $SVC -n $NS --type=merge -p '{"spec":{"selector":{"deployment":"frontend"}}}'
```

Or fix pod/deployment labels:

```bash
oc label deployment frontend -n $NS app=frontend --overwrite
```

Then verify:

```bash
oc get endpoints $SVC -n $NS -o wide
oc get endpointslice -n $NS -l kubernetes.io/service-name=$SVC -o wide
```

### 7.2 Pod exists but is not Ready

A service endpoint is generally available only when the selected pod is ready. If readiness probes fail, the route can return 503.

Check:

```bash
oc get pods -n $NS
oc describe pod <pod> -n $NS
oc logs <pod> -n $NS --tail=100
oc get events -n $NS --sort-by=.lastTimestamp
```

Common causes:

- Readiness probe path wrong
- App starts slowly
- Container port wrong
- App binds to `127.0.0.1` only instead of `0.0.0.0`
- Dependency such as DB/cache unavailable
- Secret/config missing
- CrashLoopBackOff
- ImagePullBackOff

Validate the application is listening inside the pod:

```bash
oc rsh -n $NS <pod>
ss -lntp
curl -v http://127.0.0.1:<container_port>/
curl -v http://$(hostname -i):<container_port>/
```

If `127.0.0.1` works but pod IP does not, the app is bound only to loopback. Fix app binding to `0.0.0.0`.

### 7.3 Service port vs targetPort mismatch

Example deployment exposes container port 8080:

```yaml
containers:
- ports:
  - containerPort: 8080
```

Service must target that port:

```yaml
ports:
- name: http
  port: 8080
  targetPort: 8080
```

Check:

```bash
oc get svc $SVC -n $NS -o yaml
oc get pod <pod> -n $NS -o yaml | grep -A5 ports:
```

Fix:

```bash
oc patch svc $SVC -n $NS --type=json -p='[{"op":"replace","path":"/spec/ports/0/targetPort","value":8080}]'
```

### 7.4 Test service directly from a debug pod

```bash
oc run netshoot -n $NS --rm -it --restart=Never --image=nicolaka/netshoot -- bash
```

If external images are not allowed, use UBI:

```bash
oc run curltest -n $NS --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside the debug pod:

```bash
curl -v http://$SVC:<service_port>/
curl -v http://$SVC.$NS.svc.cluster.local:<service_port>/
nc -vz $SVC <service_port>
```

If service works internally but route fails, move to route/router/DNS/TLS/NetworkPolicy checks.

## 8. DNS troubleshooting

DNS is one of the most common causes of route access failure.

### 8.1 Check route host

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.spec.host}{"\n"}'
oc get ingresses.config/cluster -o jsonpath='{.spec.domain}{"\n"}'
```

Typical route host:

```text
myapp-myproject.apps.cluster.example.com
```

Typical wildcard DNS should exist:

```text
*.apps.cluster.example.com  ->  ingress load balancer / VIP
```

### 8.2 Test DNS from client machine

```bash
HOST=$(oc get route $ROUTE -n $NS -o jsonpath='{.spec.host}')
dig +short $HOST
nslookup $HOST
```

If this returns nothing:

- The route hostname is wrong.
- The wildcard apps DNS record is missing.
- Split DNS is misconfigured.
- DNS propagation has not completed.
- Client is using the wrong resolver.

### 8.3 Test DNS from inside the cluster

```bash
oc run dns-test -n $NS --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
dnf -y install bind-utils
nslookup $HOST
dig +short $HOST
```

### 8.4 Bypass DNS with curl --resolve

If you know the router/LB IP, bypass DNS:

```bash
ROUTER_IP=<router_or_load_balancer_ip>
curl -vk --resolve $HOST:443:$ROUTER_IP https://$HOST/
curl -v  --resolve $HOST:80:$ROUTER_IP  http://$HOST/
```

Interpretation:

| Result | Meaning |
|---|---|
| Works with `--resolve`, fails normally | DNS problem |
| Fails with `--resolve` too | Router/LB/route/backend problem |

### 8.5 Check router canonical hostname

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.status.ingress[*].routerCanonicalHostname}{"\n"}'
```

The route may publish a router canonical hostname. External DNS can use CNAME records pointing route hosts to the router canonical hostname.

## 9. External load balancer, VIP, firewall, and endpoint publishing

OpenShift IngressController can be exposed using different endpoint publishing strategies depending on platform:

- `LoadBalancerService`
- `NodePortService`
- `HostNetwork`
- `Private`

Check:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml | yq '.status.endpointPublishingStrategy'
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml | grep -A30 endpointPublishingStrategy
```

If `yq` is not available:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o jsonpath='{.status.endpointPublishingStrategy.type}{"\n"}'
```

### 9.1 Check router service

```bash
oc get svc -n openshift-ingress
oc describe svc router-default -n openshift-ingress
```

For `LoadBalancerService`, check external IP/hostname:

```bash
oc get svc router-default -n openshift-ingress -o wide
oc get svc router-default -n openshift-ingress -o jsonpath='{.status.loadBalancer.ingress}{"\n"}'
```

For `NodePortService`, check node ports:

```bash
oc get svc router-default -n openshift-ingress -o yaml | grep -A20 ports:
```

For `HostNetwork`, router pods bind directly to node ports 80/443 on selected nodes.

### 9.2 Check router pod placement

```bash
oc get pods -n openshift-ingress -o wide
oc describe ingresscontroller/default -n openshift-ingress-operator | egrep -i 'Node Placement|nodeSelector|tolerations|replicas|Available'
```

If the external LB targets worker nodes where no router pod is running, route access can fail or be intermittent.

### 9.3 Firewall checks from external client

```bash
nc -vz $HOST 80
nc -vz $HOST 443
curl -v http://$HOST/
curl -vk https://$HOST/
```

If `nc` is unavailable:

```bash
curl -v telnet://$HOST:443
```

Or with bash:

```bash
timeout 5 bash -c '</dev/tcp/'$HOST'/443' && echo open || echo failed
```

### 9.4 Bare metal checklist

On bare metal or UPI, route issues frequently come from infrastructure:

- `*.apps.<cluster-domain>` does not point to the ingress VIP.
- VIP is not advertised by keepalived/MetalLB/F5/HAProxy.
- External LB targets wrong nodes.
- External LB health check uses wrong port/protocol.
- Firewall blocks 80/443 to worker/router nodes.
- Router pods are scheduled on infra nodes, but LB targets workers only.
- PROXY protocol mismatch between LB and IngressController.

Check LB/VIP path:

```bash
traceroute $HOST
curl -vk --connect-timeout 5 https://$HOST/
```

On nodes:

```bash
oc debug node/<node_name>
chroot /host
ss -lntp | egrep ':80|:443'
iptables-save | grep -E '80|443'
nft list ruleset | grep -E '80|443'
```

Use node debugging carefully in production.

## 10. Router / Ingress Controller troubleshooting

### 10.1 Check Ingress ClusterOperator

```bash
oc get co ingress
oc describe co ingress
```

Look for:

- `Available=False`
- `Progressing=True` for long time
- `Degraded=True`
- Router deployment unavailable
- Canary route failures
- Certificate or DNS related messages

### 10.2 Check IngressController status

```bash
oc get ingresscontroller -n openshift-ingress-operator
oc describe ingresscontroller/default -n openshift-ingress-operator
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml
```

Important fields:

```yaml
spec:
  domain: apps.example.com
  replicas: 2
  endpointPublishingStrategy:
    type: LoadBalancerService
  routeSelector: {}
  namespaceSelector: {}
  routeAdmission:
    namespaceOwnership: Strict
    wildcardPolicy: WildcardsDisallowed
status:
  availableReplicas: 2
  domain: apps.example.com
```

### 10.3 Check router pods

```bash
oc get pods -n openshift-ingress -o wide
oc describe pod -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=default
oc logs -n openshift-ingress deployment/router-default --tail=200
```

Common router pod problems:

- CrashLoopBackOff
- Image pull issue
- Node pressure
- Failing liveness/readiness probe
- Bad custom certificate secret
- Bad route annotation causing config reload issues
- Insufficient replicas
- Misconfigured node placement

### 10.4 Check router HAProxy config for route

```bash
ROUTER_POD=$(oc get pod -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=default -o jsonpath='{.items[0].metadata.name}')
echo $ROUTER_POD

oc rsh -n openshift-ingress $ROUTER_POD grep -n "$HOST" /var/lib/haproxy/conf/haproxy.config
```

If route host is not present in HAProxy config:

- Route was not admitted.
- Wrong IngressController shard selected.
- Router has not reconciled yet.
- Router pod/config reload failed.

### 10.5 Enable Ingress access logs temporarily

For low-traffic or short-term troubleshooting:

```bash
oc patch ingresscontroller default -n openshift-ingress-operator --type=merge \
  -p '{"spec":{"logging":{"access":{"destination":{"type":"Container"}}}}}'
```

Then stream logs:

```bash
oc logs -n openshift-ingress deployment/router-default -c logs -f
```

Disable after troubleshooting:

```bash
oc patch ingresscontroller default -n openshift-ingress-operator --type=json \
  -p='[{"op":"remove","path":"/spec/logging"}]'
```

Do not leave verbose access logging enabled on high-traffic clusters unless it is sized and integrated properly.

## 11. Ingress sharding issues

Ingress sharding is used when multiple IngressControllers serve different sets of routes. A route can be inaccessible if it is not selected by the expected shard.

### 11.1 Check all IngressControllers

```bash
oc get ingresscontroller -n openshift-ingress-operator -o wide
oc get ingresscontroller -n openshift-ingress-operator -o yaml
```

Look for:

```yaml
spec:
  domain: apps-internal.example.com
  namespaceSelector:
    matchLabels:
      router: internal
  routeSelector:
    matchLabels:
      type: internal
```

### 11.2 Check route labels and namespace labels

```bash
oc get route $ROUTE -n $NS --show-labels
oc get ns $NS --show-labels
```

If the IngressController selects routes with `type=internal`, your route needs that label:

```bash
oc label route $ROUTE -n $NS type=internal --overwrite
```

If it selects namespaces with `router=internal`, your namespace needs that label:

```bash
oc label namespace $NS router=internal --overwrite
```

### 11.3 Confirm route is admitted by expected router

```bash
oc get route $ROUTE -n $NS -o yaml | yq '.status.ingress'
```

Without `yq`:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{range .status.ingress[*]}{.routerName}{" "}{.host}{" "}{.conditions[*].type}{"="}{.conditions[*].status}{" "}{.conditions[*].reason}{"\n"}{end}'
```

If route is admitted by an internal router but DNS points to external router, the client will get 404 or timeout.

## 12. TLS termination troubleshooting

OpenShift routes commonly use one of three TLS termination modes.

### 12.1 Edge route

```text
Client --HTTPS--> Router --HTTP--> Pod
```

Router terminates TLS. Backend pod receives HTTP.

Example:

```yaml
spec:
  tls:
    termination: edge
```

Common issues:

- Certificate does not match route host.
- Missing intermediate CA.
- Client does not trust certificate.
- Application expects HTTPS but receives HTTP from router.
- `insecureEdgeTerminationPolicy: Redirect` causes HTTP to HTTPS redirects.

Test:

```bash
curl -vk https://$HOST/
openssl s_client -connect $HOST:443 -servername $HOST -showcerts </dev/null
```

Check cert SAN/CN:

```bash
openssl s_client -connect $HOST:443 -servername $HOST </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### 12.2 Re-encrypt route

```text
Client --HTTPS--> Router --HTTPS--> Pod
```

Router terminates TLS and re-encrypts to backend. The router must trust the backend certificate using `destinationCACertificate`.

Example:

```yaml
spec:
  tls:
    termination: reencrypt
    destinationCACertificate: |-
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----
```

Common issues:

- Backend certificate not trusted by `destinationCACertificate`.
- Backend certificate CN/SAN does not match what router validates.
- Backend app not listening on HTTPS.
- Route/service targetPort points to HTTP port instead of HTTPS port.
- Expired backend certificate.

Check route:

```bash
oc get route $ROUTE -n $NS -o yaml
```

Test backend from inside cluster:

```bash
oc run curltest -n $NS --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
curl -vk https://$SVC:<https_service_port>/
openssl s_client -connect $SVC:<https_service_port> -servername <backend_server_name> -showcerts </dev/null
```

Fix destination CA:

```bash
oc patch route $ROUTE -n $NS --type=merge -p '{"spec":{"tls":{"destinationCACertificate":"'"$(awk 'NF {sub(/\r/, ""); printf "%s\\n",$0;}' dest-ca.crt)"'"}}}'
```

A safer approach is to edit YAML:

```bash
oc edit route $ROUTE -n $NS
```

### 12.3 Passthrough route

```text
Client --HTTPS--> Router --TCP passthrough/SNI--> Pod
```

Router does not decrypt traffic. It uses SNI to route the connection.

Example:

```yaml
spec:
  tls:
    termination: passthrough
```

Important limitations:

- Backend pod must terminate TLS.
- Route path-based routing does not work because router cannot read HTTP path inside encrypted traffic.
- Route cert/key are not configured on the route; cert is served by backend pod.
- Client must send SNI for correct hostname.

Test with SNI:

```bash
openssl s_client -connect $HOST:443 -servername $HOST -showcerts </dev/null
curl -vk https://$HOST/
```

Test without SNI to reproduce some client issues:

```bash
openssl s_client -connect $HOST:443 -showcerts </dev/null
```

If only old clients fail, check SNI support.

### 12.4 Wrong TLS mode symptoms

| Problem | Likely symptom |
|---|---|
| Edge route to backend that only accepts HTTPS | 503/502 or backend protocol errors |
| Re-encrypt route to backend HTTP port | TLS handshake failure / 503 |
| Passthrough route with HTTP backend | TLS handshake failure |
| Path configured on passthrough route | Path matching ineffective |
| Missing destination CA in re-encrypt route | 503 / certificate verify errors |
| Cert SAN does not include route host | Browser warning / hostname mismatch |

## 13. NetworkPolicy and route traffic

NetworkPolicy can block traffic from the router pods to application pods. This is very common after teams implement default-deny policies.

### 13.1 Check policies

```bash
oc get networkpolicy -n $NS
oc describe networkpolicy -n $NS
```

If there is a default-deny ingress policy like this:

```yaml
kind: NetworkPolicy
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress: []
```

Then route traffic can be blocked unless explicitly allowed.

### 13.2 Identify router namespace and labels

Router pods are normally in `openshift-ingress`:

```bash
oc get ns openshift-ingress --show-labels
oc get pods -n openshift-ingress --show-labels
```

The namespace normally has a stable label:

```text
kubernetes.io/metadata.name=openshift-ingress
```

### 13.3 Allow route traffic from openshift-ingress

Example: allow router pods to reach pods with `app=myapp` on TCP 8080.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
  namespace: myproject
spec:
  podSelector:
    matchLabels:
      app: myapp
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-ingress
    ports:
    - protocol: TCP
      port: 8080
```

Apply:

```bash
oc apply -f allow-from-openshift-ingress.yaml
```

If route works after deleting/relaxing NetworkPolicy, the policy was the cause. Do not leave production namespaces wide open; create a precise allow rule.

## 14. HTTP status code based RCA

### 14.1 Router returns 404

A router 404 generally means the request reached a router, but no route matched the request host/path.

Check:

```bash
curl -vk https://$HOST/
oc get route $ROUTE -n $NS -o yaml
oc get route -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,HOST:.spec.host,PATH:.spec.path,TLS:.spec.tls.termination' | grep "$HOST"
```

Common causes:

- DNS points to wrong router shard.
- Route not admitted.
- Hostname typo.
- Request uses wrong host header.
- Path does not match.
- Duplicate host conflict.
- Route is admitted by internal router but client reaches external router.

Test host header explicitly:

```bash
ROUTER_IP=<router_ip>
curl -vk --resolve $HOST:443:$ROUTER_IP https://$HOST/
```

Or:

```bash
curl -vk https://$ROUTER_IP/ -H "Host: $HOST"
```

For HTTPS, prefer `--resolve` because SNI must match the hostname.

### 14.2 Router returns 503

503 means route was matched, but backend is unavailable or unhealthy.

Check endpoints:

```bash
oc get endpoints $SVC -n $NS -o wide
oc get endpointslice -n $NS -l kubernetes.io/service-name=$SVC -o wide
```

Check pods:

```bash
oc get pods -n $NS -o wide
oc describe pod <pod> -n $NS
```

Check service selector:

```bash
oc describe svc $SVC -n $NS
oc get pods -n $NS --show-labels
```

Check NetworkPolicy:

```bash
oc get networkpolicy -n $NS
```

Check router logs:

```bash
oc logs -n openshift-ingress deployment/router-default --tail=200
```

### 14.3 Router returns 502

502 usually indicates backend connection/protocol failure.

Common causes:

- Route uses edge but backend expects HTTPS.
- Route uses re-encrypt but backend certificate is wrong.
- Backend closes connection immediately.
- App crashes during request.
- Wrong service port.
- HTTP/2 or WebSocket behavior mismatch.

Check backend manually:

```bash
oc run curltest -n $NS --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -v http://$SVC:<port>/
curl -vk https://$SVC:<port>/
```

### 14.4 Router returns 504

504 means timeout.

Check route timeout annotation:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.metadata.annotations.haproxy\.router\.openshift\.io/timeout}{"\n"}'
```

Set route timeout if the application legitimately needs more time:

```bash
oc annotate route $ROUTE -n $NS --overwrite haproxy.router.openshift.io/timeout=60s
```

Also check external LB timeout. External LB timeout should be greater than the route timeout to avoid unexpected disconnects.

## 15. Route annotations that can break or affect access

List annotations:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.metadata.annotations}{"\n"}'
```

Important annotations:

| Annotation | Effect |
|---|---|
| `haproxy.router.openshift.io/timeout` | Per-route backend timeout |
| `haproxy.router.openshift.io/ip_allowlist` | Allows only specific source IP/CIDR ranges |
| `haproxy.router.openshift.io/balance` | Load balancing algorithm |
| `haproxy.router.openshift.io/disable_cookies` | Disables cookie-based persistence |
| `router.openshift.io/cookie_name` | Custom route cookie name |
| `haproxy.router.openshift.io/rewrite-target` | Rewrites backend request path |
| `haproxy.router.openshift.io/hsts_header` | HSTS behavior for secure routes |
| `haproxy.router.openshift.io/rate-limit-connections` | Enables connection rate limiting |

### 15.1 IP allowlist issue

Symptom:

- Route works from some IPs but not others.
- Requests from non-allowed IPs are dropped.

Check:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.metadata.annotations.haproxy\.router\.openshift\.io/ip_allowlist}{"\n"}'
```

Remove temporarily for testing:

```bash
oc annotate route $ROUTE -n $NS haproxy.router.openshift.io/ip_allowlist-
```

Add correct allowlist:

```bash
oc annotate route $ROUTE -n $NS --overwrite haproxy.router.openshift.io/ip_allowlist='10.10.10.0/24 192.168.1.10'
```

### 15.2 Rewrite target issue

Symptom:

- Route opens but application returns 404.
- Backend receives unexpected path.

Check:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.spec.path}{"\n"}'
oc get route $ROUTE -n $NS -o jsonpath='{.metadata.annotations.haproxy\.router\.openshift\.io/rewrite-target}{"\n"}'
```

Test:

```bash
curl -vk https://$HOST/original/path
```

Fix or remove:

```bash
oc annotate route $ROUTE -n $NS haproxy.router.openshift.io/rewrite-target-
```

### 15.3 HSTS issue

Symptom:

- Browser forces HTTPS even after route changed.
- Browser fails but `curl http://...` seems okay.

Check HSTS annotation:

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.metadata.annotations.haproxy\.router\.openshift\.io/hsts_header}{"\n"}'
```

Disable per route:

```bash
oc annotate route $ROUTE -n $NS --overwrite "haproxy.router.openshift.io/hsts_header=max-age=0"
```

Remember browser HSTS cache can persist. Test with curl or a clean browser profile.

## 16. Application-level causes that look like route issues

Sometimes the route is healthy, but the application is not serving correctly.

### 16.1 App returns 404

Router 404 and application 404 are different.

Check response headers:

```bash
curl -vk https://$HOST/ -I
```

Router default 404 often has router-specific behavior. Application 404 usually includes app/server headers or application content.

Test service directly:

```bash
oc run curltest -n $NS --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -v http://$SVC:<port>/
```

### 16.2 App requires context path

Example app only responds at `/myapp`:

```bash
curl -vk https://$HOST/myapp
```

Fix route path or app configuration depending on requirement.

### 16.3 App redirects to wrong host or HTTP/HTTPS

Check redirects:

```bash
curl -vkL https://$HOST/
curl -vk https://$HOST/ -I
```

Common causes:

- App does not trust `X-Forwarded-Proto`.
- App base URL configured to internal service DNS.
- App redirects HTTPS to HTTP or wrong domain.
- Edge route sends HTTP to backend, but app thinks original request was HTTP.

For edge/reencrypt routes, validate forwarded headers behavior and app proxy settings.

### 17.1 Check router to backend connectivity from router pod

The Ingress Operator uses canary checks to validate default ingress behavior. If `ClusterOperator/ingress` is degraded due to canary failures, user routes may also be affected.

Check:

```bash

```

Check canary route:

```bash

```

If canary fails:

- DNS might not resolve wildcard apps domain correctly from inside cluster.
- Router pods might be unavailable.
- Network path from canary to router might be broken.
- Router service/LB might be unhealthy.
- IngressController domain/endpoint publishing might be wrong.

## 19. Certificate and default router certificate checks

### 19.1 Check route-specific certificate

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.spec.tls.certificate}{"\n"}' > route.crt
openssl x509 -in route.crt -noout -subject -issuer -dates -ext subjectAltName
```

If no cert is configured on the route, the router default certificate is used for secure routes.

### 19.2 Check IngressController default certificate

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o jsonpath='{.spec.defaultCertificate.name}{"\n"}'
```

If configured:

```bash
CERT_SECRET=$(oc get ingresscontroller/default -n openshift-ingress-operator -o jsonpath='{.spec.defaultCertificate.name}')
oc get secret $CERT_SECRET -n openshift-ingress -o yaml
```

Check cert:

```bash
oc get secret $CERT_SECRET -n openshift-ingress -o jsonpath='{.data.tls\.crt}' | base64 -d > default-router.crt
openssl x509 -in default-router.crt -noout -subject -issuer -dates -ext subjectAltName
```

### 19.3 Verify from client

```bash
openssl s_client -connect $HOST:443 -servername $HOST -showcerts </dev/null
```

Look for:

- `Verify return code: 0 (ok)`
- Correct SAN for `$HOST`
- Complete certificate chain
- Valid dates
- Expected issuer

Routes can split traffic across multiple services.

Check:

Check all services and endpoints:


Temporarily set traffic to known-good backend:


Verify:

```bash
oc describe route $ROUTE -n $NS
```

## 21. WebSocket, gRPC, HTTP/2, and long-running connections

### 21.1 Long-running HTTP requests

If long requests fail:

```bash

```

Also ensure external LB timeout is higher than route timeout.

### 21.2 WebSocket

WebSocket usually works through edge/reencrypt routes, but check:

- Route timeout
- App supports proxy headers
- External LB supports WebSocket upgrade
- No intermediate proxy strips `Upgrade` and `Connection` headers

Test:

```bash
curl -vk \
  -H "Connection: Upgrade" \
  -H "Upgrade: websocket" \
  -H "Host: $HOST" \
```

### 21.3 gRPC / HTTP/2

If gRPC fails:

- Confirm whether IngressController HTTP/2 is enabled.
- Confirm service `appProtocol` if required.
- Confirm route termination mode.
- Prefer re-encrypt or passthrough depending on architecture.

Check ingress annotations/config:

```bash
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml | grep -i http2 -C3
oc get ingresses.config/cluster -o yaml | grep -i http2 -C3
```

## 22. Production-grade RCA workflow

Use this order in real incidents.

### Step 1: Confirm exact failure

```bash
curl -vk https://$HOST/ --connect-timeout 10
curl -v  http://$HOST/ --connect-timeout 10
```

Record:

- Client source IP/network
- Exact URL
- HTTP status code
- TLS error text
- Time of failure
- Whether issue is global or client-specific

### Step 2: Confirm route is admitted

```bash
oc describe route $ROUTE -n $NS
oc get route $ROUTE -n $NS -o yaml
```

If not admitted, fix route admission before checking pods.

### Step 3: Confirm DNS

```bash
dig +short $HOST
curl -vk --resolve $HOST:443:<router_ip> https://$HOST/
```

If `--resolve` works, fix DNS.

### Step 4: Confirm router is healthy

```bash
oc get co ingress
oc get pods -n openshift-ingress -o wide
oc logs -n openshift-ingress deployment/router-default --tail=100
```

### Step 5: Confirm service endpoints

```bash
oc get svc $SVC -n $NS -o yaml
oc get endpoints $SVC -n $NS -o wide
oc get pods -n $NS -o wide --show-labels
```

If endpoints are missing, fix service selector or pod readiness.

### Step 6: Confirm backend app

```bash
oc rsh -n $NS <pod>
ss -lntp
curl -v http://127.0.0.1:<port>/
```

### Step 7: Confirm NetworkPolicy

```bash
oc get networkpolicy -n $NS
oc describe networkpolicy -n $NS
```

Allow `openshift-ingress` namespace if default deny is enabled.

### Step 8: Confirm TLS mode

```bash
oc get route $ROUTE -n $NS -o jsonpath='{.spec.tls.termination}{"\n"}'
openssl s_client -connect $HOST:443 -servername $HOST -showcerts </dev/null
```

### Step 9: Confirm infra path

```bash
oc get svc router-default -n openshift-ingress -o wide
oc get ingresscontroller/default -n openshift-ingress-operator -o yaml | grep -A30 endpointPublishingStrategy
nc -vz $HOST 443
```

### Step 10: Enable access logs if needed

```bash
oc patch ingresscontroller default -n openshift-ingress-operator --type=merge \
  -p '{"spec":{"logging":{"access":{"destination":{"type":"Container"}}}}}'

oc logs -n openshift-ingress deployment/router-default -c logs -f
```

## 23. Real-world scenarios and fixes

### Scenario 1: Route returns 503 because service has no endpoints

Check:

```bash
oc get endpoints mysvc -n myapp
```

Output:

```text
NAME    ENDPOINTS   AGE
mysvc   <none>      10m
```

Root cause:

```text
Service selector does not match pod labels.
```

Fix:

```bash
oc get svc mysvc -n myapp -o jsonpath='{.spec.selector}{"\n"}'
oc get pods -n myapp --show-labels
oc patch svc mysvc -n myapp --type=merge -p '{"spec":{"selector":{"app":"myapp"}}}'
```

Verify:

```bash
oc get endpoints mysvc -n myapp -o wide
curl -vk https://$(oc get route myroute -n myapp -o jsonpath='{.spec.host}')/
```

### Scenario 2: Route returns 404 because DNS points to wrong router shard

Check:

```bash
oc get route myroute -n myapp -o yaml | grep -A20 status:
oc get ingresscontroller -n openshift-ingress-operator
```

Root cause:

```text
Route admitted by internal router, but public DNS points to external router.
```

Fix:

- Update DNS to point to correct router canonical hostname/LB.
- Or label route/namespace so it is admitted by public router.
- Or create route with correct domain for intended IngressController.

### Scenario 3: Re-encrypt route returns 503 after certificate rotation

Check:

```bash
oc get route myroute -n myapp -o yaml | grep -A30 destinationCACertificate
openssl s_client -connect myservice.myapp.svc:8443 -servername backend.internal -showcerts </dev/null
```

Root cause:

```text
Backend certificate changed, but route destinationCACertificate still contains old CA.
```

Fix:

```bash
oc edit route myroute -n myapp
# Update spec.tls.destinationCACertificate
```

Verify:

```bash
curl -vk https://$HOST/
```

### Scenario 4: Route works from office but not from home

Check:

```bash
oc get route myroute -n myapp -o jsonpath='{.metadata.annotations.haproxy\.router\.openshift\.io/ip_allowlist}{"\n"}'
```

Root cause:

```text
Route IP allowlist allows office CIDR only.
```

Fix:

```bash
oc annotate route myroute -n myapp --overwrite haproxy.router.openshift.io/ip_allowlist='office_cidr vpn_cidr'
```

### Scenario 5: Browser fails but curl works

Check:

```bash
curl -vkI https://$HOST/
oc get route $ROUTE -n $NS -o jsonpath='{.metadata.annotations.haproxy\.router\.openshift\.io/hsts_header}{"\n"}'
openssl s_client -connect $HOST:443 -servername $HOST -showcerts </dev/null
```

Possible causes:

- HSTS cached in browser.
- Browser does not trust CA.
- Certificate chain incomplete.
- Mixed content or app redirect issue.

Fix depends on exact browser error. Validate with clean profile and `curl -vk`.

### Scenario 6: Intermittent 503 during deployment rollout

Check:

```bash
oc rollout status deployment/<deploy> -n $NS
oc get endpoints $SVC -n $NS -w
oc describe deployment <deploy> -n $NS
```

Root cause examples:

- Readiness probe too optimistic.
- App accepts traffic before dependency is ready.
- RollingUpdate maxUnavailable too high.
- Service selector matches old and new incompatible pods.

Fix:

- Correct readiness probe.
- Use graceful shutdown and preStop hook.
- Tune rolling update strategy.
- Avoid selecting incompatible versions with same service during migration.

## 25. Prevention and best practices

### 25.1 Naming and ownership

- Use predictable route names and hosts.
- Avoid duplicate hostnames across namespaces unless intentionally configured.
- Track route ownership in GitOps.
- Use labels to indicate shard ownership, for example `router=external` or `router=internal`.

### 25.2 Service and labels

- Keep service selectors stable.
- Do not use overly broad selectors.
- Verify endpoints after every deployment.
- Use readiness probes that reflect real application readiness.

### 25.3 TLS

- Automate certificate renewal.
- Monitor expiry for route certs and backend certs.
- Keep CA chains complete.
- For re-encrypt, update destination CA when backend CA rotates.

### 25.4 DNS and ingress

- Monitor wildcard apps DNS.
- Document router canonical hostnames and LB targets.
- For sharded ingress, document which domains are internal/external.
- Confirm split DNS behavior from internal and external networks.

### 25.5 NetworkPolicy

- When using default-deny, always include allow rules for `openshift-ingress` to app ports.
- Keep policies port-specific.
- Validate policy changes in staging before production.

### 25.6 Observability

- Monitor `ClusterOperator/ingress` and `ClusterOperator/dns`.
- Monitor router pod availability and restarts.
- Enable access logging only where capacity supports it.
- Use synthetic checks for critical routes.

## 27. Interview/L3 explanation

When I troubleshoot an inaccessible OpenShift route, I do not treat it as only an application problem. I follow the ingress chain from outside to inside: DNS, external load balancer or VIP, OpenShift router, route admission, service, endpoints, pod readiness, NetworkPolicy, and application listener. I first identify the exact client error because DNS failure, TCP timeout, router 404, router 503, TLS error, and application 404 all point to different layers.

My first commands are `oc describe route`, `oc get endpoints`, `oc get pods --show-labels`, `oc get co ingress`, and `curl -vk`. If the router returns 404, I check route admission, host/path matching, duplicate hostnames, and ingress sharding. If the router returns 503, I check service selectors, endpoints, pod readiness, target ports, and NetworkPolicy from `openshift-ingress`. For TLS routes, I verify whether the route is edge, re-encrypt, or passthrough and test certificates using `openssl s_client` with SNI.

For production RCA, I also check router pod health in `openshift-ingress`, IngressController status in `openshift-ingress-operator`, external DNS resolution, and the router service or load balancer. I enable Ingress access logs temporarily only when needed, collect `oc adm must-gather` or `oc adm inspect`, and avoid unnecessary deletion or recreation of resources until the failing layer is confirmed.
