# RBAC Permission Issue – Advanced Cluster Troubleshooting for OpenShift Administration

**Topic:** RBAC permission issue  
**Course area:** Advanced Cluster Troubleshooting  
**Target role:** Advanced OpenShift Administrator / OpenShift L2-L3 / Platform Engineer / SRE  
**Experience level:** Written from a 10+ years Linux, Kubernetes, and OpenShift administration perspective  
**Platform focus:** Red Hat OpenShift Container Platform 4.x

---

## 1. What is an RBAC permission issue?

An **RBAC permission issue** happens when a user, group, or service account tries to perform an action in OpenShift, but the OpenShift API server denies the request because the subject does not have the required permission.

Typical error:

```text
Error from server (Forbidden): pods is forbidden: User "john" cannot list resource "pods" in API group "" in the namespace "app1"
```

Another common service account error:

```text
Error from server (Forbidden): configmaps is forbidden: User "system:serviceaccount:demo:app-sa" cannot get resource "configmaps" in API group "" in the namespace "demo"
```

In OpenShift, RBAC answers this question:

> Is this authenticated identity allowed to perform this verb on this resource in this scope?

Example:

```text
Can user john create deployments.apps in project demo?
Can service account backend-sa get secrets in project payment?
Can group dev-team update routes.route.openshift.io in namespace web-prod?
Can user qwerty create projects cluster-wide?
```

If the answer is no, you get a **Forbidden** response.

## 2. RBAC is authorization, not authentication

Many administrators mix authentication and authorization during troubleshooting.

| Area | Question answered | OpenShift objects/components |
|---|---|---|
| Authentication | Who are you? | OAuth, identity providers, kubeconfig, token, user identity |
| Authorization / RBAC | What are you allowed to do? | Role, ClusterRole, RoleBinding, ClusterRoleBinding |
| Admission / SCC | Is the requested pod security context allowed? | SecurityContextConstraints, Pod Security Admission, admission controllers |
| Quota / limits | Is the namespace allowed to consume more resources? | ResourceQuota, LimitRange |
| Network access | Can traffic flow between pods/namespaces? | NetworkPolicy, routes, services, ingress |

A user can authenticate successfully and still fail authorization.

Example:

```bash
oc login -u john
oc get pods -n prod
```

Output:

```text
Error from server (Forbidden): pods is forbidden: User "john" cannot list resource "pods" in API group "" in the namespace "prod"
```

This means:

- Login is working.
- User exists.
- Token is valid.
- RBAC does not allow `list pods` in namespace `prod`.

## 3. OpenShift RBAC mental model

OpenShift RBAC is built from four important concepts:

```text
Subject  +  Role/ClusterRole  +  Binding  +  Scope
```

### 3.1 Subject

A subject is the identity receiving permission.

Subject types:

```text
User
Group
ServiceAccount
```

Examples:

```text
john
natasha
site-users
system:serviceaccount:demo:default
system:serviceaccount:app1:backend-sa
```

Service account identity format:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

Example:

```text
system:serviceaccount:demo:robot
```

### 3.2 Verb

A verb is the action being performed.

Common verbs:

```text
get
list
watch
create
update
patch
delete
deletecollection
use
impersonate
bind
escalate
```

Important difference:

| Verb | Meaning |
|---|---|
| get | Read one object by name |
| list | Read many objects |
| watch | Stream changes |
| create | Create new object |
| update | Replace full object |
| patch | Partially modify object |
| delete | Delete one object |
| use | Use special resource such as SCC |
| bind | Bind a role to another subject |
| escalate | Create/update a role with permissions greater than your own |
| impersonate | Act as another user/group/service account |

### 3.3 Resource

A resource is the API object being accessed.

Examples:

```text
pods
services
secrets
configmaps
deployments
statefulsets
routes
imagestreams
projects
namespaces
securitycontextconstraints
clusterroles
rolebindings
```

### 3.4 API group

Kubernetes and OpenShift resources live in API groups.

Examples:

| Resource | API group |
|---|---|
| pods | core API group, written as `""` in YAML |
| services | core API group, written as `""` |
| deployments | `apps` |
| routes | `route.openshift.io` |
| imagestreams | `image.openshift.io` |
| projects | `project.openshift.io` |
| securitycontextconstraints | `security.openshift.io` |
| clusterroles | `rbac.authorization.k8s.io` |

Find API group quickly:

```bash
oc api-resources | grep -i deployment
oc api-resources | grep -i route
oc api-resources | grep -i securitycontextconstraints
```

Example:

```bash
oc api-resources | grep -i route
```

Output example:

```text
routes    route,rt    route.openshift.io/v1    true    Route
```

This tells you:

```yaml
apiGroups:
- route.openshift.io
resources:
- routes
```

### 3.5 Role

A **Role** is namespaced. It grants permissions only inside one namespace/project.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: configmap-reader
  namespace: demo
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "watch"]
```

### 3.6 ClusterRole

A **ClusterRole** exists at cluster level. It can be used in two ways:

1. Bound cluster-wide using a **ClusterRoleBinding**.
2. Bound inside one namespace using a **RoleBinding**.

Example:

```bash
oc adm policy add-role-to-user view john -n demo
```

This command uses the cluster role `view`, but binds it locally in namespace `demo`.

### 3.7 RoleBinding

A **RoleBinding** grants a Role or ClusterRole to a subject inside one namespace.

Example:

```bash
oc adm policy add-role-to-user edit john -n demo
```

Meaning:

```text
Give user john edit permission only in namespace demo.
```

### 3.8 ClusterRoleBinding

A **ClusterRoleBinding** grants a ClusterRole to a subject cluster-wide.

Example:

```bash
oc adm policy add-cluster-role-to-user cluster-reader john
```

Meaning:

```text
Give user john cluster-reader permission across the cluster.
```

Use this carefully. Cluster-wide access should be limited.

## 4. How OpenShift evaluates RBAC authorization

When a request reaches the OpenShift API server, authorization is evaluated approximately like this:

```text
1. Identify the user and groups from the authenticated token.
2. Identify the requested action:
   - namespace/project
   - API group
   - resource
   - subresource
   - verb
   - resource name, if applicable
3. Find all RoleBindings and ClusterRoleBindings applicable to the subject.
4. Resolve the Roles and ClusterRoles referenced by those bindings.
5. Check whether any policy rule allows the requested action.
6. If no matching allow rule is found, deny by default.
```

Important point:

```text
RBAC is allow-based. There is no normal Kubernetes/OpenShift RBAC deny rule.
```

So when troubleshooting, your job is to find out:

```text
Which required allow rule is missing?
```

## 5. Common symptoms of RBAC permission issues

### 5.1 User cannot view pods

```text
Error from server (Forbidden): pods is forbidden: User "john" cannot list resource "pods" in API group "" in the namespace "demo"
```

Likely missing:

```text
list pods in namespace demo
```

Check:

```bash
oc auth can-i list pods -n demo --as=john
```

Fix example:

```bash
oc adm policy add-role-to-user view john -n demo
```

### 5.2 User cannot create deployments

```text
Error from server (Forbidden): deployments.apps is forbidden: User "john" cannot create resource "deployments" in API group "apps" in the namespace "demo"
```

Check:

```bash
oc auth can-i create deployments.apps -n demo --as=john
```

Fix example:

```bash
oc adm policy add-role-to-user edit john -n demo
```

Or create a custom Role with only deployment permissions.

### 5.3 User cannot create project

```text
Error from server (Forbidden): You may not request a new project via this API.
```

Check:

```bash
oc auth can-i create projectrequests.project.openshift.io --as=john
```

Possible fix:

```bash
oc adm policy add-cluster-role-to-user self-provisioner john
```

Or for a group:

```bash
oc adm policy add-cluster-role-to-group self-provisioner developers
```

### 5.4 Service account cannot read ConfigMap

Application log:

```text
configmaps "app-config" is forbidden: User "system:serviceaccount:demo:backend-sa" cannot get resource "configmaps" in API group "" in the namespace "demo"
```

Check:

```bash
oc auth can-i get configmap/app-config -n demo --as=system:serviceaccount:demo:backend-sa
```

Fix:

```bash
oc create role configmap-reader \
  --verb=get,list,watch \
  --resource=configmaps \
  -n demo

oc adm policy add-role-to-user configmap-reader \
  system:serviceaccount:demo:backend-sa \
  -n demo
```

### 5.5 Helm install fails with Forbidden

Example:

```text
Error: rendered manifests contain a resource that already exists or cannot be created: roles.rbac.authorization.k8s.io is forbidden
```

Check the user running Helm:

```bash
oc whoami
oc auth can-i create roles -n demo
oc auth can-i create rolebindings -n demo
oc auth can-i create deployments.apps -n demo
oc auth can-i create services -n demo
oc auth can-i create routes.route.openshift.io -n demo
```

Fix depends on chart requirements. For many app charts, namespace `admin` or carefully designed custom permissions are required.

### 5.6 Operator installation fails due RBAC

Symptoms:

```text
installplans.operators.coreos.com is forbidden
clusterserviceversions.operators.coreos.com is forbidden
subscriptions.operators.coreos.com is forbidden
```

Check:

```bash
oc auth can-i create subscriptions.operators.coreos.com -n openshift-operators
oc auth can-i create operatorgroups.operators.coreos.com -n openshift-operators
oc auth can-i create installplans.operators.coreos.com -n openshift-operators
```

In production, Operator installation is usually performed by a cluster admin or delegated platform admin because Operators may require cluster-scoped permissions.

### 5.7 Pod fails because of SCC but looks like RBAC

Error:

```text
Error creating: pods "app-xxx" is forbidden: unable to validate against any security context constraint
```

This is not normal Role/RoleBinding permission for pods. This is **SCC admission**. SCC access is still granted using RBAC-style commands, but the problem is pod security admission, not basic namespace access.

Check:

```bash
oc get sa -n demo
oc describe pod <pod-name> -n demo
oc get events -n demo --sort-by=.lastTimestamp
```

Fix example:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n demo
```

For production, do not blindly grant `anyuid` or `privileged`. Understand the container requirement first.

## 6. High-speed troubleshooting workflow

Use this workflow during real outages, exams, and production escalations.

### Step 1: Capture the exact Forbidden message

Do not start by guessing the role. First capture:

```text
user/service account
verb
resource
API group
namespace
subresource
resource name
```

Example error:

```text
Error from server (Forbidden): deployments.apps is forbidden: User "john" cannot patch resource "deployments/scale" in API group "apps" in the namespace "demo"
```

Interpretation:

```text
Subject: john
Verb: patch
Resource: deployments
Subresource: scale
API group: apps
Namespace: demo
```

The missing permission is not simply `patch deployments`; it is often:

```yaml
resources:
- deployments/scale
verbs:
- patch
```

### Step 2: Confirm who is making the request

For CLI user:

```bash
oc whoami
oc whoami --show-groups
oc whoami --show-token
```

For service account used by pod:

```bash
oc get pod <pod-name> -n <namespace> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

Then build the service account identity:

```text
system:serviceaccount:<namespace>:<serviceAccountName>
```

Example:

```text
system:serviceaccount:demo:backend-sa
```

### Step 3: Test permission with `oc auth can-i`

For current user:

```bash
oc auth can-i list pods -n demo
oc auth can-i create deployments.apps -n demo
oc auth can-i patch deployments/scale.apps -n demo
```

For another user:

```bash
oc auth can-i list pods -n demo --as=john
oc auth can-i create deployments.apps -n demo --as=john
```

For a service account:

```bash
oc auth can-i get configmaps -n demo --as=system:serviceaccount:demo:backend-sa
```

For all allowed actions:

```bash
oc auth can-i --list -n demo
oc auth can-i --list -n demo --as=john
oc auth can-i --list -n demo --as=system:serviceaccount:demo:backend-sa
```

For cluster-scoped resource:

```bash
oc auth can-i get nodes --as=john
oc auth can-i create namespaces --as=john
oc auth can-i create projectrequests.project.openshift.io --as=john
```

### Step 4: Identify the resource and API group

Use:

```bash
oc api-resources | grep -i <resource>
```

Examples:

```bash
oc api-resources | grep -i deployment
oc api-resources | grep -i route
oc api-resources | grep -i imagestream
oc api-resources | grep -i project
oc api-resources | grep -i securitycontextconstraints
```

For YAML roles, API group matters.

Wrong:

```yaml
apiGroups: [""]
resources: ["deployments"]
```

Correct:

```yaml
apiGroups: ["apps"]
resources: ["deployments"]
```

Wrong:

```yaml
apiGroups: [""]
resources: ["routes"]
```

Correct:

```yaml
apiGroups: ["route.openshift.io"]
resources: ["routes"]
```

### Step 5: Check local RoleBindings

```bash
oc get rolebinding -n demo
oc describe rolebinding -n demo
oc get rolebinding -n demo -o wide
oc get rolebinding -n demo -o yaml
```

Useful filter:

```bash
oc get rolebinding -n demo -o yaml | grep -A5 -B5 john
oc get rolebinding -n demo -o yaml | grep -A5 -B5 backend-sa
oc get rolebinding -n demo -o yaml | grep -A5 -B5 site-users
```

### Step 6: Check cluster-wide ClusterRoleBindings

```bash
oc get clusterrolebinding
oc describe clusterrolebinding <name>
oc get clusterrolebinding -o yaml | grep -A6 -B6 john
oc get clusterrolebinding -o yaml | grep -A6 -B6 site-users
```

Be careful. A user may have permission through a group, not directly.

### Step 7: Inspect the effective Role or ClusterRole

```bash
oc describe clusterrole view
oc describe clusterrole edit
oc describe clusterrole admin
oc describe clusterrole self-provisioner
oc describe clusterrole cluster-reader
```

For custom role:

```bash
oc describe role <role-name> -n demo
oc get role <role-name> -n demo -o yaml
```

For custom cluster role:

```bash
oc describe clusterrole <clusterrole-name>
oc get clusterrole <clusterrole-name> -o yaml
```

### Step 8: Check whether the issue is namespace-scoped or cluster-scoped

Namespace-scoped resources:

```text
pods
services
configmaps
secrets
deployments
statefulsets
routes
rolebindings
roles
pvc
imagestreams
```

Cluster-scoped resources:

```text
nodes
namespaces
projects
clusterroles
clusterrolebindings
persistentvolumes
storageclasses
securitycontextconstraints
customresourcedefinitions
projectrequests
```

If the resource is cluster-scoped, a local RoleBinding will not be enough.

Example:

```bash
oc adm policy add-role-to-user admin john -n demo
```

This does **not** allow john to get nodes.

Check:

```bash
oc auth can-i get nodes --as=john
```

### Step 9: Confirm group membership

```bash
oc get groups
oc describe group site-users
oc get group site-users -o yaml
```

For current logged-in user:

```bash
oc whoami --show-groups
```

If the permission is granted to a group but the user is not a member, RBAC will fail.

### Step 10: Apply least-privilege fix

Avoid this lazy fix:

```bash
oc adm policy add-cluster-role-to-user cluster-admin john
```

Prefer this style:

```bash
oc adm policy add-role-to-user view john -n demo
```

Or custom Role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployment-restarter
  namespace: demo
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "patch"]
```

Bind it:

```bash
oc adm policy add-role-to-user deployment-restarter john -n demo
```

## 8. Default OpenShift roles you must understand

### 8.1 `view`

Allows read-only access to most resources in a namespace.

Typical use:

```bash
oc adm policy add-role-to-user view natasha -n apollo
```

Good for:

```text
Developers who need to inspect apps but not change them.
Auditors who need namespace visibility.
Support users who need read-only troubleshooting access.
```

Limitations:

```text
Usually does not allow reading secrets.
Does not allow modifying workloads.
Does not allow creating routes/services/deployments.
```

### 8.2 `edit`

Allows modifying most application resources in a namespace.

Typical use:

```bash
oc adm policy add-role-to-user edit harry -n demo
```

Good for:

```text
Application developers managing deployments, services, configmaps, routes.
```

Security consideration:

```text
edit is powerful. It may allow users to manipulate workloads that run under service accounts in the namespace.
```

### 8.3 `admin`

Allows namespace administration, including managing most role bindings in that namespace.

Typical use:

```bash
oc adm policy add-role-to-user admin armstrong -n apollo
```

Good for:

```text
Project owners.
Team leads responsible for namespace-level access.
```

Limitation:

```text
admin in one namespace is not cluster-admin.
```

### 8.4 `cluster-reader`

Read-only access to cluster-level information.

Example:

```bash
oc adm policy add-cluster-role-to-user cluster-reader john
```

Good for:

```text
Operations users who need to inspect cluster status but not change objects.
```

### 8.5 `self-provisioner`

Allows creation of new projects through project requests.

Example:

```bash
oc adm policy add-cluster-role-to-user self-provisioner john
```

Remove from a user:

```bash
oc adm policy remove-cluster-role-from-user self-provisioner john
```

Remove from all authenticated users:

```bash
oc adm policy remove-cluster-role-from-group self-provisioner system:authenticated:oauth
```

### 8.6 `cluster-admin`

Full cluster administrator access.

Example:

```bash
oc adm policy add-cluster-role-to-user cluster-admin bob
```

Use only for trusted platform administrators.

Important distinction:

```bash
oc adm policy add-role-to-user cluster-admin bob -n demo
```

This creates a local RoleBinding to the `cluster-admin` ClusterRole in namespace `demo`. It does not make Bob a true cluster-wide admin.

True cluster-wide admin:

```bash
oc adm policy add-cluster-role-to-user cluster-admin bob
```

## Scenario 1: User cannot see a project

### Symptom

```bash
oc login -u natasha
oc get pods -n apollo
```

Output:

```text
Error from server (Forbidden): pods is forbidden: User "natasha" cannot list resource "pods" in API group "" in the namespace "apollo"
```

### Diagnosis

```bash
oc auth can-i list pods -n apollo --as=natasha
oc get rolebindings -n apollo
oc get rolebindings -n apollo -o yaml | grep -A5 -B5 natasha
```

### Fix

Read-only:

```bash
oc adm policy add-role-to-user view natasha -n apollo
```

Verify:

```bash
oc auth can-i list pods -n apollo --as=natasha
oc auth can-i create pods -n apollo --as=natasha
```

Expected:

```text
yes
no
```

## Scenario 2: User can view resources but cannot modify deployment

### Symptom

```bash
oc set image deployment/web web=registry.example.com/web:v2 -n demo
```

Output:

```text
Error from server (Forbidden): deployments.apps "web" is forbidden: User "john" cannot patch resource "deployments" in API group "apps" in the namespace "demo"
```

### Diagnosis

```bash
oc auth can-i get deployments.apps -n demo --as=john
oc auth can-i patch deployments.apps -n demo --as=john
oc auth can-i update deployments.apps -n demo --as=john
```

If only `get` is allowed, user probably has `view`.

### Fix option 1: Grant edit

```bash
oc adm policy add-role-to-user edit john -n demo
```

### Fix option 2: Grant custom deployment patch role

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployment-patcher
  namespace: demo
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "patch"]
```

Apply and bind:

```bash
oc apply -f deployment-patcher.yaml
oc adm policy add-role-to-user deployment-patcher john -n demo
```

Verify:

```bash
oc auth can-i patch deployments.apps -n demo --as=john
```

## Scenario 3: User cannot scale deployment

### Symptom

```bash
oc scale deployment/web --replicas=5 -n demo
```

Output:

```text
Error from server (Forbidden): deployments.apps "web" is forbidden: User "john" cannot patch resource "deployments/scale" in API group "apps" in the namespace "demo"
```

### Root cause

Scaling often uses the `scale` subresource.

Required resource:

```text
deployments/scale
```

Not only:

```text
deployments
```

### Check

```bash
oc auth can-i patch deployments/scale.apps -n demo --as=john
```

### Fix

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployment-scaler
  namespace: demo
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "deployments/scale"]
  verbs: ["get", "list", "watch", "patch", "update"]
```

Bind:

```bash
oc apply -f deployment-scaler.yaml
oc adm policy add-role-to-user deployment-scaler john -n demo
```

## Scenario 4: Service account cannot access Kubernetes API

### Symptom

Application pod log:

```text
Forbidden: User "system:serviceaccount:demo:backend-sa" cannot list resource "pods" in API group "" in the namespace "demo"
```

### Diagnosis

Find service account:

```bash
oc get pod backend-xxxxx -n demo -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

Test:

```bash
oc auth can-i list pods -n demo --as=system:serviceaccount:demo:backend-sa
```

Check bindings:

```bash
oc get rolebinding -n demo -o yaml | grep -A6 -B6 backend-sa
```

### Fix

```bash
oc create role pod-reader \
  --verb=get,list,watch \
  --resource=pods \
  -n demo

oc adm policy add-role-to-user pod-reader \
  system:serviceaccount:demo:backend-sa \
  -n demo
```

Or:

```bash
oc adm policy add-role-to-user pod-reader -z backend-sa -n demo
```

Verify:

```bash
oc auth can-i list pods -n demo --as=system:serviceaccount:demo:backend-sa
```

## Scenario 5: User cannot read pod logs

### Symptom

```bash
oc logs pod/web-abc -n demo
```

Output:

```text
Error from server (Forbidden): pods "web-abc" is forbidden: User "john" cannot get resource "pods/log" in API group "" in the namespace "demo"
```

### Root cause

Pod logs use the `pods/log` subresource.

### Check

```bash
oc auth can-i get pods/log -n demo --as=john
```

### Fix


## Scenario 9: Image pull from another project fails

### Symptom

Pod in namespace `app` uses an image stream from namespace `tools` and fails with image pull authorization issue.

Example:

```text
Failed to pull image "image-registry.openshift-image-registry.svc:5000/tools/backend:latest": unauthorized
```

### Root cause

The service account running the pod in `app` may not be allowed to pull images from image streams in `tools`.

### Fix

Allow service accounts in namespace `app` to pull images from namespace `tools`:

```bash
oc policy add-role-to-group system:image-puller \
  system:serviceaccounts:app \
  -n tools
```

Meaning:

```text
In namespace tools, grant image puller permission to all service accounts from namespace app.
```

For one service account:

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:app:backend-sa \
  -n tools
```

Verify:

```bash
oc auth can-i get imagestreams/layers.image.openshift.io \
  -n tools \
  --as=system:serviceaccount:app:backend-sa
```

## Scenario 14: Operator operand service account lacks permission

### Symptom

Operator is installed, but the operand pod or controller logs show Forbidden.

Example:

```text
secrets is forbidden: User "system:serviceaccount:my-operator:controller-manager" cannot watch resource "secrets" in API group "" in the namespace "app1"
```

### Diagnosis

```bash
oc logs deploy/<operator-controller> -n my-operator
```

### Fix

```bash
  system:serviceaccount:my-operator:controller-manager \
  -n app1
```

Do not manually over-grant cluster-admin to an operator unless vendor documentation explicitly requires it and risk is accepted.

## 10. RBAC vs SCC troubleshooting

SCC is one of the biggest OpenShift-specific confusion points.

### 10.1 RBAC Forbidden example

```text
User "john" cannot create resource "deployments" in API group "apps" in the namespace "demo"
```

This means John lacks RBAC permission to create deployments.

### 10.2 SCC Forbidden example

```text
pods "mysql-1" is forbidden: unable to validate against any security context constraint: provider restricted-v2: .spec.securityContext.runAsUser: Invalid value: 0: must be in the ranges...
```

This means pod security settings are not accepted by SCC.

### 10.3 SCC check commands

```bash
oc get scc
oc describe scc restricted-v2
oc describe scc anyuid
oc get events -n demo --sort-by=.lastTimestamp
oc describe pod <pod-name> -n demo
```

### 10.4 SCC fix example

```bash
oc create sa mysql-sa -n demo
oc adm policy add-scc-to-user anyuid -z mysql-sa -n demo
oc set serviceaccount deployment/mysql mysql-sa -n demo
```

Verify:

```bash
oc get deploy mysql -n demo -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
oc auth can-i use scc/anyuid --as=system:serviceaccount:demo:mysql-sa
```

This gives John route read access only in namespace `demo`.

## 12. Advanced RBAC details for experienced administrators

## 12.1 Local RoleBinding can reference a ClusterRole

This is normal and commonly used.

Example:

```bash
oc adm policy add-role-to-user view john -n demo
```

This creates a RoleBinding in namespace `demo` referencing ClusterRole `view`.

This does not give John view access to every namespace.

## 12.2 ClusterRoleBinding is cluster-wide

Example:

```bash
oc adm policy add-cluster-role-to-user view john
```

This gives `view` cluster-wide. Use carefully.

In many environments, cluster-wide view may expose metadata across many namespaces.

## 12.3 API group mismatch causes silent RBAC design failure

This Role will not allow deployment access:

```yaml
rules:
- apiGroups: [""]
  resources: ["deployments"]
  verbs: ["get", "list"]
```

Correct:

```yaml
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list"]
```

Always use:

```bash
oc api-resources | grep -i <resource>
```

## 12.4 Subresources require explicit permissions

Common subresources:

```text
pods/log
pods/exec
pods/attach
pods/portforward
deployments/scale
statefulsets/scale
deploymentconfigs/scale
imagestreams/layers
```

Example:

```yaml
resources:
- pods
- pods/log
verbs:
- get
- list
- watch
```

Exec example:

```yaml
resources:
- pods/exec
verbs:
- create
```

Scale example:

```yaml
resources:
- deployments/scale
verbs:
- get
- update
- patch
```

## 12.5 `resourceNames` can restrict access to specific objects

Example: allow reading only one secret.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: one-secret-reader
  namespace: demo
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["db-secret"]
  verbs: ["get"]
```

Important limitation:

```text
resourceNames works with get/update/patch/delete for named objects.
It does not generally work with list/watch the way many people expect.
```

## 12.6 Wildcards are dangerous

Dangerous role:

```yaml
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["*"]
```

This is effectively admin-like. Avoid unless you are building a controlled platform admin role and understand the impact.

## 12.7 Secrets are sensitive even with namespace access

Reading secrets is powerful because secrets may contain:

```text
Database passwords
API tokens
TLS private keys
Registry credentials
Application credentials
```

Do not add secret read access to a generic support role unless required.

## 12.8 `pods/exec` is also sensitive

A user with exec can enter a running container and potentially read mounted secrets or call internal services.

Treat `pods/exec` almost like elevated troubleshooting access.

## 12.9 `bind`, `escalate`, and `impersonate` are high-risk verbs

| Verb | Risk |
|---|---|
| bind | Can grant roles to subjects |
| escalate | Can create/update roles beyond current permission level |
| impersonate | Can act as another user/group/service account |

Check:

```bash
oc auth can-i bind clusterrole/admin --as=john
oc auth can-i escalate clusterroles.rbac.authorization.k8s.io --as=john
oc auth can-i impersonate users --as=john
```

These should be tightly controlled.

## 12.10 Aggregated ClusterRoles

Some ClusterRoles are aggregated from other ClusterRoles using labels and aggregation rules. This is common in Kubernetes/OpenShift default roles.

Check:

```bash
oc get clusterrole admin -o yaml
oc get clusterrole edit -o yaml
oc get clusterrole view -o yaml
```

Look for:

```yaml
aggregationRule:
  clusterRoleSelectors:
```

Be careful when creating ClusterRoles with aggregation labels. You can accidentally add permissions to default roles.

## 13. RBAC troubleshooting matrix

| Error text | Likely missing permission | Check command | Possible fix |
|---|---|---|---|
| cannot list resource `pods` | `list pods` | `oc auth can-i list pods -n ns --as=user` | add `view` or custom pod reader |
| cannot get resource `pods/log` | `get pods/log` | `oc auth can-i get pods/log -n ns --as=user` | custom log reader role |
| cannot create resource `pods/exec` | `create pods/exec` | `oc auth can-i create pods/exec -n ns --as=user` | custom exec role, with caution |
| cannot create deployments.apps | `create deployments` in `apps` | `oc auth can-i create deployments.apps -n ns --as=user` | add `edit` or custom role |
| cannot patch deployments/scale | `patch deployments/scale` | `oc auth can-i patch deployments/scale.apps -n ns --as=user` | scaler role |
| cannot create routes | `create routes` in `route.openshift.io` | `oc auth can-i create routes.route.openshift.io -n ns --as=user` | route manager role |
| cannot get secrets | `get secrets` | `oc auth can-i get secrets -n ns --as=user` | secret reader, with caution |
| cannot create project | `create projectrequests` | `oc auth can-i create projectrequests.project.openshift.io --as=user` | self-provisioner |
| cannot get nodes | cluster-scoped `get nodes` | `oc auth can-i get nodes --as=user` | cluster-reader or custom ClusterRoleBinding |
| unable to validate against SCC | SCC use/admission issue | `oc auth can-i use scc/<scc> --as=system:serviceaccount:ns:sa` | add SCC to SA or fix pod securityContext |
| cannot create rolebindings | manage RBAC missing | `oc auth can-i create rolebindings.rbac.authorization.k8s.io -n ns --as=user` | namespace admin or admin-created binding |

## 14. Production-grade troubleshooting procedure

Use this full procedure when working as L3/OpenShift platform admin.

### 14.1 Collect incident data

Ask or collect:

```text
Who is affected? User, group, service account, CI pipeline, operator?
Which namespace?
Which command or API call failed?
Exact Forbidden error?
Was it working earlier?
Any recent IDP, group, GitOps, or RBAC changes?
Any new Operator or namespace created?
Any project template changes?
```

### 14.2 Confirm the failing identity

```bash
oc whoami
oc whoami --show-groups
```

For pod/service account:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

### 14.3 Confirm authorization result

```bash
oc auth can-i <verb> <resource> -n <ns> --as=<subject>
```

### 14.4 List effective permissions

```bash
oc auth can-i --list -n <ns> --as=<subject>
```

Save output for comparison:

```bash
oc auth can-i --list -n demo --as=john > john-demo-permissions.txt
```

### 14.5 Find how permission is currently granted

Search RoleBindings:

```bash
oc get rolebinding -n demo -o yaml | grep -A8 -B8 john
oc get rolebinding -n demo -o yaml | grep -A8 -B8 site-users
```

Search ClusterRoleBindings:

```bash
oc get clusterrolebinding -o yaml | grep -A8 -B8 john
oc get clusterrolebinding -o yaml | grep -A8 -B8 site-users
```

### 14.6 Check groups

```bash
oc get group site-users -o yaml
oc describe group site-users
```

### 14.7 Inspect referenced roles

```bash
oc describe role <role> -n demo
oc describe clusterrole <clusterrole>
```

### 14.8 Apply minimal fix

Examples:

```bash
oc adm policy add-role-to-user view john -n demo
oc adm policy add-role-to-user edit john -n demo
oc adm policy add-role-to-group view site-users -n demo
oc adm policy add-role-to-user configmap-reader -z backend-sa -n demo
```

### 14.9 Verify after fix

```bash
oc auth can-i <verb> <resource> -n <ns> --as=<subject>
```

Then test the real operation:

```bash
oc login -u john
oc get pods -n demo
```

Or test service account behavior by restarting workload:

```bash
oc rollout restart deployment/backend -n demo
oc logs deployment/backend -n demo
```

### 14.10 Document the change

Record:

```text
Incident number
Subject receiving permission
Namespace
Role granted
Reason
Approver
Command/YAML used
Rollback command
```

Example rollback:

```bash
oc adm policy remove-role-from-user edit john -n demo
```

## 15. Preventive RBAC design

## 15.1 Use groups, not individual users

Bad:

```bash
oc adm policy add-role-to-user edit john -n app1
oc adm policy add-role-to-user edit harry -n app1
oc adm policy add-role-to-user edit susan -n app1
```

Better:

```bash
oc adm groups new app1-devs john harry susan
oc adm policy add-role-to-group edit app1-devs -n app1
```

Benefits:

```text
Cleaner access management
Easy onboarding/offboarding
Less RBAC drift
Better auditability
```

## 15.2 Prefer namespace RoleBinding over ClusterRoleBinding

Bad for normal app team:

```bash
oc adm policy add-cluster-role-to-group edit app-team
```

Better:

```bash
oc adm policy add-role-to-group edit app-team -n app1
oc adm policy add-role-to-group edit app-team -n app2
```

## 15.3 Create custom roles for automation

Do not give CI/CD tools `cluster-admin` unless truly required.

Example custom deployer role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: ci-deployer
  namespace: demo
rules:
- apiGroups: [""]
  resources: ["services", "configmaps"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
- apiGroups: ["apps"]
  resources: ["deployments", "deployments/scale"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
- apiGroups: ["route.openshift.io"]
  resources: ["routes"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
```

## 15.4 Avoid modifying default ClusterRoles

Do not manually edit default roles like:

```text
view
edit
admin
cluster-admin
self-provisioner
cluster-reader
```

Instead, create custom Roles or ClusterRoles.

## 15.5 Keep break-glass access controlled

For emergency cluster-admin access:

```text
Use named accounts, not shared accounts.
Use approval workflow.
Use MFA if available.
Log access.
Review after incident.
Remove temporary access.
```

## 15.6 Review RBAC regularly

Useful commands:

```bash
oc get clusterrolebinding -o wide
oc get rolebinding -A -o wide
oc get clusterrolebinding -o yaml | grep -B4 -A8 cluster-admin
oc get rolebinding -A -o yaml | grep -B4 -A8 cluster-admin
```

Find all role bindings in a namespace:

```bash
oc get rolebinding -n demo
```

Find all users with cluster-admin:

```bash
oc get clusterrolebinding -o jsonpath='{range .items[?(@.roleRef.name=="cluster-admin")]}{.metadata.name}{"\n"}{end}'
```

Then inspect each:

```bash
oc describe clusterrolebinding <name>
```

### Example 1

Error:

```text
Subject: john
Verb: list
Resource: pods
API group: core
Namespace: demo
```

## 18. How to avoid over-permissioning

Before granting a role, ask:

```text
Does the user need read-only or write access?
Is access needed in one namespace or all namespaces?
Is this for human user or automation?
Does the role include secrets access?
Does it include pod exec?
Does it include RBAC management?
Does it include SCC use?
Can a custom Role solve the problem?
What is the rollback command?
```

Bad escalation pattern:

```bash
oc adm policy add-cluster-role-to-user cluster-admin john
```

Better escalation pattern:

```bash
oc auth can-i create routes.route.openshift.io -n demo --as=john
oc create role route-manager --verb=get,list,watch,create,update,patch,delete --resource=routes.route.openshift.io -n demo
oc adm policy add-role-to-user route-manager john -n demo
```

## 19. Quick decision tree

```text
Forbidden error?
|
|-- Is the user logged in successfully?
|     |-- No  -> Authentication/OAuth/IDP issue
|     |-- Yes -> Continue
|
|-- Is the failing identity a service account?
|     |-- Yes -> Check pod .spec.serviceAccountName and test with --as=system:serviceaccount:ns:sa
|     |-- No  -> Check oc whoami / user / group
|
|-- Is the error about "unable to validate against any security context constraint"?
|     |-- Yes -> SCC/admission issue
|     |-- No  -> Continue RBAC
|
|-- Is the resource namespace-scoped?
|     |-- Yes -> Check RoleBindings in namespace
|     |-- No  -> Check ClusterRoleBindings / cluster-scoped roles
|
|-- Does oc auth can-i return yes?
|     |-- Yes -> Check different identity, namespace, subresource, or admission controller
|     |-- No  -> Missing RBAC permission
|
|-- Is a default role enough?
|     |-- Yes -> add view/edit/admin/cluster-reader/self-provisioner as appropriate
|     |-- No  -> create custom Role/ClusterRole
|
|-- Verify with oc auth can-i and real command
```

## 20. Interview-level explanation

An experienced OpenShift administrator should explain RBAC permission issues like this:

> In OpenShift, RBAC permission issues occur after authentication when the API server evaluates whether a user, group, or service account has an allow rule for a requested verb, resource, API group, and scope. I troubleshoot by capturing the exact Forbidden message, identifying the subject, checking the namespace and API group, validating with `oc auth can-i`, inspecting RoleBindings and ClusterRoleBindings, and then applying the least-privilege fix. I avoid assigning cluster-admin unless absolutely required. For service accounts, I test using the full `system:serviceaccount:<namespace>:<name>` identity. I also separate RBAC issues from SCC, quota, admission, and network policy problems because they can produce similar deployment failures.

## 23. Common mistakes

### Mistake 1: Granting cluster-admin for every Forbidden error

This solves the symptom but creates a security risk.

Better:

```bash
oc auth can-i <verb> <resource> -n <namespace> --as=<subject>
```

Then grant only the required permission.

### Mistake 2: Wrong API group in custom Role

Wrong:

```yaml
apiGroups: [""]
resources: ["routes"]
```

Correct:

```yaml
apiGroups: ["route.openshift.io"]
resources: ["routes"]
```

### Mistake 3: Forgetting service account namespace

Wrong subject:

```text
system:serviceaccount:backend-sa
```

Correct subject:

```text
system:serviceaccount:demo:backend-sa
```

### Mistake 4: Binding role in wrong namespace

Wrong:

```bash
oc adm policy add-role-to-user edit john -n default
```

When app is in:

```text
demo
```

Correct:

```bash
oc adm policy add-role-to-user edit john -n demo
```

### Mistake 5: Missing subresource

Role has:

```yaml
resources: ["pods"]
verbs: ["get"]
```

But logs need:

```yaml
resources: ["pods/log"]
verbs: ["get"]
```

Exec needs:

```yaml
resources: ["pods/exec"]
verbs: ["create"]
```

### Mistake 6: Confusing local admin with cluster-admin

This:

```bash
oc adm policy add-role-to-user admin john -n demo
```

is namespace-level admin.

This:

```bash
oc adm policy add-cluster-role-to-user cluster-admin john
```

is cluster-wide admin.

## 24. Summary

RBAC permission issues in OpenShift are common but very logical if you troubleshoot systematically.

Remember the core formula:

```text
Subject + Verb + Resource + API Group + Namespace/Cluster Scope = Authorization decision
```

Best troubleshooting command:

```bash
oc auth can-i <verb> <resource> -n <namespace> --as=<subject>
```

Best investigation commands:

```bash
oc get rolebinding -n <namespace> -o yaml
oc get clusterrolebinding -o yaml
oc describe role <role> -n <namespace>
oc describe clusterrole <clusterrole>
oc api-resources | grep -i <resource>
```

Best fix strategy:

```text
Use least privilege.
Use groups.
Use namespace RoleBindings where possible.
Use custom Roles for automation.
Avoid cluster-admin unless truly required.
Verify before and after using oc auth can-i.
```
