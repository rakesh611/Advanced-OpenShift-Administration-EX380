# SCC Issue Troubleshooting in Advanced OpenShift Administration

**Topic:** Security Context Constraint (SCC) issues  
**Level:** Advanced Cluster Troubleshooting / Senior OpenShift Administration  
**Audience:** OpenShift administrators, platform engineers, SREs, DevOps engineers  
**Experience target:** 10+ years Linux / Kubernetes / OpenShift operations  

---

## 1. Executive Summary

An **SCC issue** in OpenShift normally means that a workload is being rejected or constrained by the OpenShift admission layer because the pod is asking for permissions that are not allowed by the SCC available to the user or service account creating the pod.

In practical troubleshooting, SCC issues usually appear when a pod tries to do one of the following:

- Run as `root` or a fixed UID not inside the namespace UID range.
- Run as privileged.
- Use `hostPath`, `hostNetwork`, `hostPID`, `hostIPC`, or host ports.
- Add Linux capabilities such as `SYS_ADMIN`, `NET_ADMIN`, or `DAC_OVERRIDE`.
- Set `allowPrivilegeEscalation: true` when the assigned SCC requires it to be `false`.
- Use an unsupported `seccompProfile`.
- Use an invalid `fsGroup`, `supplementalGroups`, SELinux level, or volume type.
- Use the wrong service account.
- Require a specific SCC through annotation, but that SCC is not usable by the workload.

The key senior-admin rule is this:

> Do not solve every SCC problem by granting `privileged`. First identify the exact security requirement, then apply the least-permissive fix.

---

## 2. What SCC Means in OpenShift

SCC stands for **Security Context Constraints**. SCCs are OpenShift-specific admission security policies that control what a pod is allowed to do at runtime.

SCCs are conceptually similar to a combination of:

- Linux privilege controls
- Kubernetes pod security settings
- SELinux constraints
- UID/GID strategy
- volume type restrictions
- host namespace restrictions
- container capability restrictions

SCCs decide whether a pod can be admitted into the cluster and what defaults should be applied to the pod security context.

A pod can be created only if at least one SCC available to the creating user or service account can validate the pod specification.

---

## 3. Where SCC Fits in the OpenShift Request Flow

When a deployment, daemon set, job, cron job, StatefulSet, or pod is created, the following simplified flow happens:

```text
User / controller submits workload
        |
        v
Kubernetes / OpenShift API server receives request
        |
        v
Authentication: who are you?
        |
        v
Authorization / RBAC: are you allowed to create this object?
        |
        v
Admission plugins
        |
        +--> SCC admission evaluates pod securityContext
        |
        +--> Other admission controllers / webhooks
        |
        +--> Pod Security Admission warning/audit/enforce checks
        |
        v
Pod accepted or rejected
        |
        v
Scheduler schedules pod
        |
        v
Kubelet / CRI-O starts container
```

Important distinction:

- **RBAC** decides whether a subject can create or modify Kubernetes resources.
- **SCC** decides whether the resulting pod is allowed to run with the requested runtime security permissions.
- **Pod Security Admission (PSA)** can warn, audit, or enforce Kubernetes Pod Security Standards separately from SCC.

A user can have `edit` or `admin` in a project and still fail to create a pod if the pod violates SCC rules.

## 4. Common SCC Error Messages

### 4.1 Generic SCC denial

```text
Error creating: pods "app-xxxxx" is forbidden: unable to validate against any security context constraint
```

This means no SCC available to the user or service account can validate the pod.

### 4.2 Service account cannot use SCC

```text
provider "anyuid": Forbidden: not usable by user or serviceaccount
```

This does not necessarily mean the `anyuid` SCC is broken. It means the pod's subject does not have `use` permission for that SCC.

### 4.3 Root UID rejected

```text
spec.containers[0].securityContext.runAsUser: Invalid value: 0: must be in the ranges: [1000670000, 1000679999]
```

The pod requested UID `0`, but the available SCC requires the UID to be inside the namespace UID range.

### 4.4 Fixed UID rejected

```text
spec.containers[0].securityContext.runAsUser: Invalid value: 1000: must be in the ranges: [1000710000, 1000719999]
```

The application requested a fixed UID that is outside the namespace's allocated UID block.

### 4.5 Privileged container rejected

```text
spec.containers[0].securityContext.privileged: Invalid value: true: Privileged containers are not allowed
```

The workload requested `privileged: true`, but the usable SCC does not allow privileged containers.

### 4.6 HostPath rejected

```text
spec.volumes[0]: Invalid value: "hostPath": hostPath volumes are not allowed to be used
```

The pod is trying to mount a node path. Most normal application SCCs reject this.

### 4.7 Host networking rejected

```text
spec.hostNetwork: Invalid value: true: Host network is not allowed to be used
```

The pod requested the host network namespace, but the assigned SCC does not allow it.

### 4.8 Capability rejected

```text
spec.containers[0].securityContext.capabilities.add: Invalid value: "NET_ADMIN": capability may not be added
```

The pod requested a Linux capability that is not permitted by the SCC.

### 4.9 PSA warning confused with SCC issue

```text
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile
```

This is a Pod Security Admission warning. It can appear even when SCC allows the pod. Treat PSA messages separately from SCC denial messages.

## 5. Default SCCs You Must Know

The exact SCC list depends on OpenShift version and installed Operators, but these are the SCCs every senior administrator should understand.

| SCC | Purpose | Risk Level | Common Use |
|---|---|---:|---|
| `restricted-v2` | Default restrictive SCC in many OpenShift 4.11+ clusters | Low | Normal application pods |
| `restricted-v3` | More restrictive newer SCC using pod-level user namespaces in newer releases | Low | Newer hardened clusters |
| `restricted` | Older restricted SCC; common in upgraded clusters | Low | Legacy workloads |
| `nonroot` | Allows any non-root UID | Medium-low | Images that define non-root user but not namespace range |
| `nonroot-v2` | Hardened version of `nonroot` | Medium-low | Non-root workloads needing modern defaults |
| `anyuid` | Allows any UID/GID, including root | Medium-high | Legacy images requiring root or fixed UID |
| `hostnetwork` | Allows host networking and host ports | High | Ingress, networking agents, special infrastructure pods |
| `hostnetwork-v2` | Hardened hostnetwork variant | High | Modern host-network workloads |
| `hostmount-anyuid` | Allows host mounts and any UID | Very high | Trusted storage/node agents only |
| `privileged` | Allows almost all privileged/host features | Critical | Cluster/system components only |

Senior rule:

```text
restricted-v2 / restricted-v3  -> preferred
nonroot-v2                    -> acceptable for specific non-root images
anyuid                        -> exception for legacy/root workloads
hostnetwork / hostmount       -> infrastructure exception
privileged                    -> last resort only
```

## 6. SCC Selection Logic

OpenShift does not randomly assign an SCC. It evaluates SCCs available to the user or service account and selects an SCC that can validate the pod.

The selection depends on:

1. Which SCCs the subject can use.
2. SCC priority.
3. How restrictive the SCC is.
4. Whether the pod's requested security context matches the SCC.
5. Whether the workload pins an SCC using the `openshift.io/required-scc` annotation.

A pod records the selected SCC as an annotation:

```bash
oc get pod <pod-name> -n <namespace> \
  -o jsonpath='{.metadata.annotations.openshift\.io\/scc}{"\n"}'
```

Example output:

```text
restricted-v2
```

If the pod was never admitted, there is no pod annotation. In that case, check events on the ReplicaSet, Deployment, Job, or namespace events.

## 7. The Most Important Principle: Pod Uses a Service Account

Most SCC troubleshooting mistakes happen because admins check the wrong identity.

A Deployment does not usually create pods as your human user. It creates pods through a service account.

Default behavior:

```text
Namespace: app1
Deployment: web
ServiceAccount: default
Full SA identity: system:serviceaccount:app1:default
```

If the deployment has this field:

```yaml
spec:
  template:
    spec:
      serviceAccountName: web-sa
```

Then the relevant identity is:

```text
system:serviceaccount:app1:web-sa
```

Always troubleshoot SCC against the service account used by the pod template.

## 8. Fast Diagnostic Workflow

Use this flow in production and exam environments.

### Step 1: Identify the failing workload

```bash
oc get pods -n <namespace>
oc get deploy,rs,sts,ds,job,cronjob -n <namespace>
```

If the pod was never created, look at ReplicaSet or events:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc describe deploy <deployment-name> -n <namespace>
oc describe rs <replicaset-name> -n <namespace>
```

### Step 2: Read the exact SCC denial

```bash
oc describe pod <pod-name> -n <namespace>
```

If no pod exists:

```bash
oc describe rs <replicaset-name> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp | tail -30
```

### Step 3: Identify the service account

```bash
oc get deploy <deployment-name> -n <namespace> \
  -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

If output is empty, the workload uses the `default` service account.

For a running pod:

```bash
oc get pod <pod-name> -n <namespace> \
  -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

### Step 4: Check which SCC admitted a running pod

```bash
oc get pod <pod-name> -n <namespace> \
  -o jsonpath='{.metadata.annotations.openshift\.io\/scc}{"\n"}'
```

### Step 5: Check SCC access

```bash
oc auth can-i use scc/anyuid \
  --as=system:serviceaccount:<namespace>:<serviceaccount> \
  -n <namespace>
```

Examples:

```bash
oc auth can-i use scc/restricted-v2 \
  --as=system:serviceaccount:app1:default \
  -n app1

oc auth can-i use scc/anyuid \
  --as=system:serviceaccount:app1:web-sa \
  -n app1

oc auth can-i use scc/privileged \
  --as=system:serviceaccount:app1:web-sa \
  -n app1
```

### Step 6: Inspect namespace UID/GID ranges

```bash
oc get ns <namespace> -o yaml | egrep 'uid-range|supplemental-groups|mcs'
```

Typical annotations:

```yaml
openshift.io/sa.scc.uid-range: 1000710000/10000
openshift.io/sa.scc.supplemental-groups: 1000710000/10000
openshift.io/sa.scc.mcs: s0:c25,c10
```

### Step 7: Inspect pod securityContext

```bash
oc get deploy <deployment-name> -n <namespace> -o yaml | less
```

Look for:

```yaml
securityContext:
  runAsUser: 0
  runAsNonRoot: true
  fsGroup: 1000
  supplementalGroups:
  - 1000
  seccompProfile:
    type: RuntimeDefault
containers:
- securityContext:
    privileged: true
    allowPrivilegeEscalation: true
    capabilities:
      add:
      - NET_ADMIN
```

### Step 8: Compare requested permissions with SCC

```bash
oc get scc
oc describe scc restricted-v2
oc describe scc anyuid
oc describe scc nonroot-v2
oc describe scc privileged
```

## 9. Decision Tree

```text
Pod failed with SCC denial?
        |
        v
Read exact event message
        |
        +--> runAsUser invalid?
        |       |
        |       +--> Can app run random non-root UID?
        |       |       +--> Yes: remove fixed UID/root, fix image permissions
        |       |       +--> No: bind anyuid/nonroot/custom SCC to dedicated SA
        |
        +--> privileged true rejected?
        |       |
        |       +--> Is this infrastructure workload?
        |       |       +--> Yes: use dedicated SA + privileged/custom SCC
        |       |       +--> No: remove privileged requirement
        |
        +--> hostPath rejected?
        |       |
        |       +--> Replace with PVC/configMap/secret if app workload
        |       +--> If node agent, use hostmount-anyuid/custom SCC carefully
        |
        +--> hostNetwork/hostPort rejected?
        |       |
        |       +--> Use Service/Route/Ingress where possible
        |       +--> If required, use hostnetwork SCC with dedicated SA
        |
        +--> capability rejected?
        |       |
        |       +--> Remove capability or create narrow custom SCC
        |
        +--> SCC not usable by SA?
                |
                +--> Bind SCC to the service account, not random user
```

## 10. Root Cause Categories and Fixes

## 10.1 Wrong Service Account

### Symptom

The SCC is granted to one service account, but the pod uses another.

Example:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n app1
```

But the deployment uses:

```yaml
serviceAccountName: default
```

### Diagnosis

```bash
oc get deploy web -n app1 \
  -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

If the output is empty, the deployment uses `default`.

### Fix Option A: Use the intended service account

```bash
oc set serviceaccount deployment/web app-sa -n app1
oc rollout status deployment/web -n app1
```

### Fix Option B: Grant SCC to the actual service account

```bash
oc adm policy add-scc-to-user anyuid -z default -n app1
```

### Senior recommendation

Prefer a dedicated service account per exception:

```bash
oc create sa web-anyuid-sa -n app1
oc adm policy add-scc-to-user anyuid -z web-anyuid-sa -n app1
oc set serviceaccount deployment/web web-anyuid-sa -n app1
```

Do not grant risky SCCs to the namespace `default` service account unless the requirement is temporary or controlled.

---

## 10.2 Application Requests Root UID

### Symptom

```text
runAsUser: Invalid value: 0: must be in the ranges
```

### Why it happens

OpenShift allocates each namespace a UID range. The default restricted SCC strategy expects pods to run inside that allocated range. UID `0` is outside the range.

### Diagnosis

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -A10 -B5 runAsUser
oc get ns <namespace> -o yaml | grep uid-range
```

### Fix Option A: Remove explicit root UID

Patch the deployment to remove `runAsUser: 0` if the image can run with a random UID.

```bash
oc patch deploy <deployment> -n <namespace> --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/securityContext/runAsUser"}]'
```

If the field is under the container:

```bash
oc patch deploy <deployment> -n <namespace> --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/securityContext/runAsUser"}]'
```

### Fix Option B: Use `anyuid` for a legacy image

```bash
oc create sa legacy-sa -n <namespace>
oc adm policy add-scc-to-user anyuid -z legacy-sa -n <namespace>
oc set serviceaccount deployment/<deployment> legacy-sa -n <namespace>
oc rollout status deployment/<deployment> -n <namespace>
```

### Fix Option C: Rebuild the image for OpenShift random UID

Best long-term fix:

```dockerfile
FROM registry.access.redhat.com/ubi9/ubi
RUN mkdir -p /opt/app && \
    chgrp -R 0 /opt/app && \
    chmod -R g=u /opt/app
COPY . /opt/app
WORKDIR /opt/app
USER 1001
CMD ["./start.sh"]
```

For OpenShift compatibility, application paths should usually be writable by group `0`, because OpenShift commonly runs containers with a random UID that belongs to root group `0`.

---

## 10.3 Fixed Non-Root UID Outside Namespace Range

### Symptom

```text
runAsUser: Invalid value: 1001: must be in the ranges: [1000710000, 1000719999]
```

### Why it happens

The image or pod requests UID `1001`, but the restricted SCC only allows UIDs in the project range.

### Fix Options

#### Option A: Remove the fixed UID

Let SCC assign a UID from the namespace range.

#### Option B: Use `nonroot-v2` if the image must use a non-root UID

```bash
oc create sa app-nonroot-sa -n app1
oc adm policy add-scc-to-user nonroot-v2 -z app-nonroot-sa -n app1
oc set serviceaccount deployment/web app-nonroot-sa -n app1
```

#### Option C: Use custom SCC for exact UID requirement

Use this only when the application or storage truly requires a specific UID.

---

## 10.4 `anyuid` SCC Required for Legacy Root Image

### Use case

Some old images require root because they:

- Write to root-owned directories.
- Bind low ports directly.
- Change file ownership at startup.
- Start daemons assuming root.
- Install packages at runtime.
- Use init scripts requiring root.

### Production-safe approach

```bash
NAMESPACE=app1
DEPLOY=legacy-web
SA=legacy-web-anyuid

oc create sa ${SA} -n ${NAMESPACE}
oc adm policy add-scc-to-user anyuid -z ${SA} -n ${NAMESPACE}
oc set serviceaccount deployment/${DEPLOY} ${SA} -n ${NAMESPACE}
oc rollout status deployment/${DEPLOY} -n ${NAMESPACE}
```

### Verify

```bash
POD=$(oc get pod -n ${NAMESPACE} -l app=${DEPLOY} -o jsonpath='{.items[0].metadata.name}')
oc get pod ${POD} -n ${NAMESPACE} \
  -o jsonpath='{.metadata.annotations.openshift\.io\/scc}{"\n"}'
```

Expected:

```text
anyuid
```

### Security note

`anyuid` is not equal to `privileged`. It allows arbitrary UID/GID, including root, but it does not automatically allow hostPath, hostPID, hostNetwork, all capabilities, or privileged containers.

---

## 10.5 Privileged Container Rejected

### Symptom

```text
privileged containers are not allowed
```

### Diagnosis

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -A5 -B5 privileged
```

You may see:

```yaml
securityContext:
  privileged: true
```

### Common workloads that genuinely need privileged access

- Node agents
- CNI plugins
- CSI drivers
- Security scanners
- Low-level monitoring agents
- Some backup agents
- Some virtualization/storage components

### Fix for infrastructure workload

```bash
oc create sa node-agent-sa -n infra-tools
oc adm policy add-scc-to-user privileged -z node-agent-sa -n infra-tools
oc set serviceaccount daemonset/node-agent node-agent-sa -n infra-tools
```

### Fix for normal application workload

Remove privileged mode.

```bash
oc patch deploy <deployment> -n <namespace> --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/securityContext/privileged"}]'
```

### Senior warning

Do not grant `privileged` just because a vendor Helm chart asks for it. Validate why it is needed. Many Helm charts set overly broad securityContext defaults for compatibility with generic Kubernetes clusters.

---

## 10.6 HostPath Volume Rejected

### Symptom

```text
hostPath volumes are not allowed to be used
```

### Diagnosis

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -A20 hostPath
```

Example:

```yaml
volumes:
- name: host-logs
  hostPath:
    path: /var/log
```

### Normal app fix

Replace `hostPath` with one of:

- PVC
- ConfigMap
- Secret
- EmptyDir
- Projected volume

Example PVC mount:

```yaml
volumes:
- name: app-data
  persistentVolumeClaim:
    claimName: app-data-pvc
```

### Infrastructure workload fix

Use a dedicated service account and a carefully scoped SCC such as `hostmount-anyuid` or a custom SCC.

```bash
oc create sa log-agent-sa -n logging-agent
oc adm policy add-scc-to-user hostmount-anyuid -z log-agent-sa -n logging-agent
oc set serviceaccount daemonset/log-agent log-agent-sa -n logging-agent
```

### Security impact

HostPath can expose node filesystems, kubelet data, CRI-O data, secrets, certificates, or host logs. Treat it as a high-risk exception.

---

## 10.7 Host Network or Host Port Rejected

### Symptoms

```text
hostNetwork is not allowed to be used
```

```text
host ports are not allowed to be used
```

### Diagnosis

```bash
oc get deploy <deployment> -n <namespace> -o yaml | egrep -A5 'hostNetwork|hostPort'
```

### Normal app fix

Use Kubernetes networking:

```bash
oc expose deployment <deployment> --port=<port> -n <namespace>
oc expose service <service> -n <namespace>
```

or use Service/Route/Ingress instead of host networking.

### Infrastructure fix

```bash
oc create sa hostnet-sa -n infra-tools
oc adm policy add-scc-to-user hostnetwork -z hostnet-sa -n infra-tools
oc set serviceaccount daemonset/<daemonset> hostnet-sa -n infra-tools
```

### Security impact

A hostNetwork pod shares the node network namespace. On control plane nodes this can be especially dangerous because it can interact with host-level services and network paths.

---

## 10.8 Capability Rejected

### Symptom

```text
capability may not be added
```

### Diagnosis

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -A10 capabilities
```

Example:

```yaml
securityContext:
  capabilities:
    add:
    - NET_ADMIN
```

### Common capability requests

| Capability | Why app asks for it | Risk |
|---|---|---|
| `NET_ADMIN` | Change network settings, iptables, VPN | High |
| `SYS_ADMIN` | Broad kernel/admin operations | Critical |
| `CHOWN` | Change file ownership | Medium |
| `DAC_OVERRIDE` | Bypass file permissions | High |
| `NET_BIND_SERVICE` | Bind ports below 1024 | Medium-low |

### Fix Option A: Remove capability

```bash
oc patch deploy <deployment> -n <namespace> --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/securityContext/capabilities"}]'
```

### Fix Option B: Use port above 1024

Instead of binding `80` in the container, run app on `8080` and expose via Service/Route.

### Fix Option C: Custom SCC

If only one capability is needed, create a custom SCC that allows only that capability instead of granting `privileged`.

---

## 10.9 `allowPrivilegeEscalation` Rejected

### Symptom

```text
allowPrivilegeEscalation: Invalid value: true
```

### Why it happens

Modern restricted SCCs commonly require `allowPrivilegeEscalation` to be unset or `false`.

### Fix

Set it to false:

```yaml
containers:
- name: app
  securityContext:
    allowPrivilegeEscalation: false
```

Patch example:

```bash
oc patch deploy <deployment> -n <namespace> --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/securityContext/allowPrivilegeEscalation","value":false}]'
```

If the `securityContext` object does not exist, patch with a full object:

```bash
oc patch deploy <deployment> -n <namespace> --type=merge -p '
spec:
  template:
    spec:
      containers:
      - name: app
        securityContext:
          allowPrivilegeEscalation: false
'
```

Be careful with merge patch on container arrays because it matches by name only in strategic merge behavior.

---

## 10.10 Seccomp Profile Issue

### Symptom

```text
seccompProfile: Forbidden
```

or PSA warning:

```text
seccompProfile (pod or container) must be set to RuntimeDefault or Localhost
```

### Fix

For restricted workloads:

```yaml
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
```

For container-level setting:

```yaml
containers:
- name: app
  securityContext:
    seccompProfile:
      type: RuntimeDefault
```

### Senior note

If the SCC mutates empty seccomp profile to `RuntimeDefault`, your pod may run without explicitly specifying it. But for portable manifests, especially GitOps, specify it explicitly when your policy requires it.

---

## 10.11 FSGroup or Supplemental Group Rejected

### Symptoms

```text
fsGroup: Invalid value: 1000: must be in the ranges
```

```text
supplementalGroups: Invalid value
```

### Why it happens

Restricted SCCs often use namespace-allocated group ranges. If a pod requests a fixed group outside the allowed range, admission fails.

### Diagnosis

```bash
oc get ns <namespace> -o yaml | egrep 'supplemental-groups|uid-range'
oc get deploy <deployment> -n <namespace> -o yaml | egrep -A5 'fsGroup|supplementalGroups'
```

### Fix Options

1. Remove fixed `fsGroup` if not required.
2. Use storage permissions compatible with OpenShift random UID/GID model.
3. Use a custom SCC if a specific storage group is mandatory.
4. Prefer supplemental groups for shared storage access instead of forcing UID when possible.

---

## 10.12 SELinux Context Rejected

### Symptom

```text
seLinuxOptions: Invalid value
```

### Why it happens

The pod requests SELinux options not allowed by its SCC or namespace MCS allocation.

### Diagnosis

```bash
oc get ns <namespace> -o yaml | grep 'openshift.io/sa.scc.mcs'
oc get deploy <deployment> -n <namespace> -o yaml | grep -A10 seLinuxOptions
```

### Fix

For normal workloads, remove custom SELinux options from the pod. Let OpenShift assign the correct MCS label.

For trusted infrastructure workloads, use a custom SCC only after confirming the SELinux requirement.

## 10.13 Required SCC Annotation Misconfigured

### Symptom

A workload has:

```yaml
metadata:
  annotations:
    openshift.io/required-scc: my-scc
```

But pod admission fails because `my-scc` does not exist or the service account cannot use it.

### Diagnosis

```bash
oc get deploy <deployment> -n <namespace> -o yaml | grep -A5 required-scc
oc get scc my-scc
oc auth can-i use scc/my-scc \
  --as=system:serviceaccount:<namespace>:<sa> \
  -n <namespace>
```

### Fix

Either grant the required SCC:

```bash
oc create role use-my-scc \
  --verb=use \
  --resource=scc \
  --resource-name=my-scc \
  -n <namespace>

oc create rolebinding use-my-scc \
  --role=use-my-scc \
  --serviceaccount=<namespace>:<sa> \
  -n <namespace>
```

Or remove/change the annotation in the pod template, not in the live pod:

```bash
oc annotate deploy <deployment> -n <namespace> \
  openshift.io/required-scc-
```

## 10.14 Pod Security Admission vs SCC Confusion

OpenShift can use SCC and Kubernetes Pod Security Admission together.

### SCC denial example

```text
unable to validate against any security context constraint
```

This is an OpenShift SCC problem.

### PSA warning example

```text
Warning: would violate PodSecurity "restricted:latest"
```

This is a Kubernetes Pod Security Admission warning/audit/enforce message.

### How to inspect namespace PSA labels

```bash
oc get ns <namespace> --show-labels | tr ',' '\n' | grep pod-security
```

or:

```bash
oc get ns <namespace> -o yaml | grep pod-security -A5
```

### Senior rule

Do not ignore PSA warnings. Even if the pod is admitted today, future policy enforcement can reject it.

## 11. Granting SCC Access Correctly

## 11.1 Using `oc adm policy add-scc-to-user`

Most common method:

```bash
oc adm policy add-scc-to-user <scc-name> -z <serviceaccount> -n <namespace>
```

Examples:

```bash
oc adm policy add-scc-to-user anyuid -z app-sa -n app1
oc adm policy add-scc-to-user nonroot-v2 -z app-sa -n app1
oc adm policy add-scc-to-user hostnetwork -z agent-sa -n infra-tools
oc adm policy add-scc-to-user privileged -z node-agent-sa -n infra-tools
```

Full service account form:

```bash
oc adm policy add-scc-to-user anyuid \
  system:serviceaccount:app1:app-sa
```

## 11.2 Removing SCC access

```bash
oc adm policy remove-scc-from-user anyuid -z app-sa -n app1
```

or:

```bash
oc adm policy remove-scc-from-user anyuid \
  system:serviceaccount:app1:app-sa
```

## 11.3 RBAC method

Create a role that allows `use` on one SCC:

```bash
oc create role use-anyuid \
  --verb=use \
  --resource=scc \
  --resource-name=anyuid \
  -n app1
```

Bind it to the service account:

```bash
oc create rolebinding use-anyuid \
  --role=use-anyuid \
  --serviceaccount=app1:app-sa \
  -n app1
```

This method is explicit and GitOps-friendly.

## 11.4 Verify SCC access

```bash
oc auth can-i use scc/anyuid \
  --as=system:serviceaccount:app1:app-sa \
  -n app1
```

Expected:

```text
yes
```

Check who can use an SCC:

```bash
oc adm policy who-can use scc anyuid
```

Important: some commands evaluate only RBAC grants and may not show subjects added directly inside the SCC object. Always understand whether access comes from RBAC, SCC `users`, or SCC `groups` fields.

## 12. Creating a Custom SCC

Create a custom SCC only when default SCCs do not meet the requirement and a more targeted exception is safer than using a broad built-in SCC.

### Example: custom SCC allowing one fixed UID

```yaml
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata:
  name: app-fixed-uid-scc
allowPrivilegedContainer: false
allowHostDirVolumePlugin: false
allowHostIPC: false
allowHostNetwork: false
allowHostPID: false
allowHostPorts: false
readOnlyRootFilesystem: false
allowedCapabilities: []
defaultAddCapabilities: []
requiredDropCapabilities:
- ALL
runAsUser:
  type: MustRunAsRange
  uidRangeMin: 1001
  uidRangeMax: 1001
seLinuxContext:
  type: MustRunAs
fsGroup:
  type: RunAsAny
supplementalGroups:
  type: RunAsAny
seccompProfiles:
- runtime/default
volumes:
- configMap
- downwardAPI
- emptyDir
- persistentVolumeClaim
- projected
- secret
users: []
groups: []
```

Apply:

```bash
oc apply -f app-fixed-uid-scc.yaml
```

Grant to a service account:

```bash
oc create role use-app-fixed-uid-scc \
  --verb=use \
  --resource=scc \
  --resource-name=app-fixed-uid-scc \
  -n app1

oc create rolebinding use-app-fixed-uid-scc \
  --role=use-app-fixed-uid-scc \
  --serviceaccount=app1:app-sa \
  -n app1
```

Verify:

```bash
oc auth can-i use scc/app-fixed-uid-scc \
  --as=system:serviceaccount:app1:app-sa \
  -n app1
```

### Custom SCC best practices

- Do not edit default SCCs.
- Do not grant custom SCC to `system:authenticated`.
- Bind to dedicated service accounts.
- Prefer namespace-scoped RBAC bindings where possible.
- Keep `allowPrivilegedContainer: false` unless absolutely required.
- Avoid `volumes: ['*']` unless absolutely required.
- Avoid `allowedCapabilities: ['*']`.
- Avoid high SCC priority unless you fully understand SCC selection impact.
- Document who approved the exception and why.

## 13. Production Troubleshooting Playbook

Use this playbook when an application team says: "Pod is not coming up due to SCC."

### 13.1 Collect facts

```bash
NS=<namespace>
APP=<app-label-or-deployment>

oc get pods -n ${NS} -o wide
oc get events -n ${NS} --sort-by=.lastTimestamp | tail -50
oc get deploy,rs,sts,ds,job -n ${NS}
```

### 13.2 Find exact failing controller

```bash

oc describe rs <replicaset> -n ${NS}
```

### 13.3 Extract service account

```bash
oc get deploy <deployment> -n ${NS} \
  -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

If empty:

```text
default
```

### 13.4 Extract security context

```bash
oc get deploy <deployment> -n ${NS} -o yaml > /tmp/${deployment}.yaml

grep -n "securityContext\|runAsUser\|privileged\|hostNetwork\|hostPID\|hostIPC\|hostPort\|capabilities\|hostPath\|fsGroup\|supplementalGroups\|seccomp" /tmp/${deployment}.yaml
```

### 13.5 Check assigned SCC on a running pod

```bash
oc get pod <pod> -n ${NS} \
  -o jsonpath='{.metadata.annotations.openshift\.io\/scc}{"\n"}'
```

### 13.6 Check possible SCC access

```bash
SA=<serviceaccount>

for SCC in restricted-v3 restricted-v2 restricted nonroot-v2 nonroot anyuid hostnetwork hostnetwork-v2 hostmount-anyuid privileged; do
  echo -n "$SCC: "
  oc auth can-i use scc/$SCC --as=system:serviceaccount:${NS}:${SA} -n ${NS}
done
```

### 13.7 Decide minimum fix

| Error | Preferred Fix | Exception Fix |
|---|---|---|
| `runAsUser 0` | Remove root requirement / fix image | `anyuid` to dedicated SA |
| fixed UID outside range | Remove fixed UID / fix image | `nonroot-v2` or custom SCC |
| `privileged true` | Remove privileged | `privileged` to dedicated SA |
| `hostPath` | Use PVC/ConfigMap/Secret | `hostmount-anyuid` or custom SCC |
| `hostNetwork` | Use Service/Route | `hostnetwork` to dedicated SA |
| capability rejected | Remove capability | Custom SCC with specific capability |
| PSA warning | Harden manifest | Adjust PSA labels only with governance |

### 13.8 Apply and verify

```bash
oc rollout restart deploy/<deployment> -n ${NS}
oc rollout status deploy/<deployment> -n ${NS}
oc get pods -n ${NS}
oc describe pod <new-pod> -n ${NS}
oc get pod <new-pod> -n ${NS} \
  -o jsonpath='{.metadata.annotations.openshift\.io\/scc}{"\n"}'
```

## 18. Advanced: SCC and Namespace UID Allocation

OpenShift commonly assigns each namespace a UID range, for example:

```yaml
openshift.io/sa.scc.uid-range: 1000710000/10000
```

This means the namespace can use UIDs:

```text
1000710000 through 1000719999
```

If a pod does not specify a UID, the SCC can default it from this range.

If the pod specifies:

```yaml
runAsUser: 1001
```

and `1001` is outside the range, admission fails under `restricted-v2` or `restricted-v3`.

### Inspect namespace range

```bash
oc get ns app1 -o jsonpath='{.metadata.annotations.openshift\.io/sa\.scc\.uid-range}{"\n"}'
```

Alternative:

```bash
oc get ns app1 -o yaml | grep uid-range
```

### Why this matters for Linux file permissions

A container process may run as a random UID such as `1000710000`. If the image filesystem has files owned by UID `1001` and not group-writable, the app may fail with permission errors even after SCC admission succeeds.

Typical runtime error:

```text
Permission denied: '/var/lib/app/data'
```

This is not always an SCC admission issue. The SCC allowed the pod, but the image filesystem is not compatible with random UID execution.

### Image fix

```dockerfile
RUN chgrp -R 0 /var/lib/app && chmod -R g=u /var/lib/app
USER 1001
```

or for runtime-created directories:

```dockerfile
RUN mkdir -p /var/lib/app /var/log/app && \
    chgrp -R 0 /var/lib/app /var/log/app && \
    chmod -R g=u /var/lib/app /var/log/app
```

## 19. Advanced: SCC Admission vs Runtime Permission Denied

Not every permission problem is an SCC admission problem.

### SCC admission problem

The pod is not created or remains unavailable because admission rejected it.

Symptoms:

```text
pods is forbidden: unable to validate against any security context constraint
```

### Runtime Linux permission problem

The pod is created, but the process fails inside the container.

Symptoms:

```text
CrashLoopBackOff
Permission denied
cannot create directory
operation not permitted
```

### Troubleshooting difference

For admission:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc describe rs <replicaset> -n <namespace>
```

For runtime:

```bash
oc logs <pod> -n <namespace> --previous
oc rsh <pod> -n <namespace>
id
ls -ld /path
mount | grep /path
```

### Runtime fix examples

```bash
# Check runtime user
oc rsh <pod> -n <namespace> id

# Check mounted volume permissions
oc rsh <pod> -n <namespace> ls -ld /data
```

If the pod runs with a random UID and cannot write to `/data`, fix the image or storage permissions rather than blindly granting `anyuid`.

Helm charts often fail on OpenShift because charts are written for generic Kubernetes and include security settings that conflict with OpenShift SCC.

### Common Helm values causing SCC failures

```yaml
securityContext:
  runAsUser: 0
  fsGroup: 1001
containerSecurityContext:
  privileged: true
  allowPrivilegeEscalation: true

    add:
```

### Troubleshooting commands

```bash
helm get values <release> -n <namespace>

```

### Preferred fix

Override chart values:

```yaml
podSecurityContext:
  enabled: false

  enabled: false
```

```yaml
containerSecurityContext:

    drop:
    - ALL
```

Use dedicated service account with appropriate SCC:

```bash
oc create sa <release>-sa -n <namespace>
oc adm policy add-scc-to-user anyuid -z <release>-sa -n <namespace>
helm upgrade <release> <chart> -n <namespace> --set serviceAccount.name=<release>-sa
```

## 21. Operator SCC Issues

Operators may deploy operands requiring special SCCs. Examples:

- Storage operators
- Networking operators
- Security scanning operators
- Virtualization operators
- Backup/restore operators
- Monitoring/node exporters

### Symptoms

```bash
oc get csv -n <operator-namespace>
oc describe csv <csv-name> -n <operator-namespace>
oc get events -n <operand-namespace> --sort-by=.lastTimestamp
```

### Common failure

The operator creates a DaemonSet or Deployment whose service account lacks the SCC required by the operand.

### Diagnosis

```bash
oc get deploy,ds -n <operand-namespace>
oc get sa -n <operand-namespace>
oc describe rs <rs-name> -n <operand-namespace>
oc describe ds <ds-name> -n <operand-namespace>
```

### Fix approach

1. Confirm vendor documentation for required SCC.
2. Identify the exact service account used by the operand.
3. Grant the narrowest SCC required.
4. Restart/reconcile the operand.
5. Avoid manually editing operator-managed resources unless necessary.

Example:

```bash
oc adm policy add-scc-to-user privileged \
  -z <operator-operand-sa> \
  -n <operand-namespace>
```

Then restart if required:

```bash
oc rollout restart ds/<daemonset> -n <operand-namespace>
```

## 23. SCC Security Review Checklist

Before granting an SCC exception, ask these questions:

1. Which exact field is failing SCC validation?
2. Which service account is creating the pod?
3. Can the app run with `restricted-v2` or `restricted-v3` if the image is fixed?
4. Is the UID requirement real or just a bad image default?
5. Is `hostPath` truly required, or can PVC be used?
6. Is `hostNetwork` truly required, or can Service/Route be used?
7. Is `privileged` truly required, or can a specific capability work?
8. Can a custom SCC be narrower than built-in `privileged`?
9. Is the SCC grant namespace-scoped?
10. Is the grant bound to a dedicated service account?
11. Is the exception documented and approved?
12. Is the change stored in GitOps/IaC?
13. Is there a plan to remove the exception later?

## 24. Dangerous Anti-Patterns

Avoid these.

### Anti-pattern 1: Granting privileged to all authenticated users

```bash
oc adm policy add-scc-to-group privileged system:authenticated
```

This is extremely dangerous.

### Anti-pattern 2: Editing default SCCs

```bash
oc edit scc restricted-v2
```

Do not customize default SCCs. Create a custom SCC if required.

### Anti-pattern 3: Granting risky SCCs to default service account

```bash
oc adm policy add-scc-to-user privileged -z default -n app1
```

This makes every workload using the default SA in that namespace highly privileged.

### Anti-pattern 4: Using `privileged` when `anyuid` is enough

If the only issue is UID `0`, use `anyuid`, not `privileged`.

### Anti-pattern 5: Using `anyuid` when fixing the image is possible

If the image can be modified to support random UID, fix the image.

### Anti-pattern 6: Ignoring PSA warnings

Warnings today can become rejections tomorrow if policies change.

## 29. Real-World Incident Example

### Incident

A vendor application fails after migration from vanilla Kubernetes to OpenShift.

### Event

```text
Error creating: pods "vendor-app-xyz" is forbidden: unable to validate against any security context constraint:
[provider "restricted-v2": .containers[0].runAsUser: Invalid value: 0: must be in the ranges]
```

### Investigation

```bash
oc get deploy vendor-app -n vendor -o yaml | grep -A10 securityContext
```

Found:

```yaml
securityContext:
  runAsUser: 0
```

Service account:

```bash
oc get deploy vendor-app -n vendor \
  -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

Output was empty, so it used `default`.

### Bad fix

```bash
oc adm policy add-scc-to-user privileged -z default -n vendor
```

Why bad:

- Grants much more than required.
- Applies to all workloads using default SA.
- Increases blast radius.

### Better short-term fix

```bash
oc create sa vendor-app-sa -n vendor
oc adm policy add-scc-to-user anyuid -z vendor-app-sa -n vendor
oc set serviceaccount deployment/vendor-app vendor-app-sa -n vendor
```

### Best long-term fix

- Rebuild image to run as non-root/random UID.
- Remove `runAsUser: 0`.
- Use `restricted-v2` or `restricted-v3`.
- Remove `anyuid` exception.

## 30. Senior-Level Best Practices

1. **Use dedicated service accounts.** Never attach high-risk SCCs to broad/default identities.
2. **Prefer image fixes.** OpenShift-compatible images should run as arbitrary non-root UIDs.
3. **Use the least permissive SCC.** `anyuid` is better than `privileged` if only UID is the issue.
4. **Avoid editing default SCCs.** Create custom SCCs for special cases.
5. **Avoid direct users/groups in SCC YAML.** Prefer RBAC Role/RoleBinding for GitOps clarity.
6. **Audit SCC usage regularly.** Track pods using `anyuid`, `hostmount`, `hostnetwork`, and `privileged`.
7. **Treat privileged as a platform exception.** It belongs to infrastructure workloads, not normal apps.
8. **Separate PSA from SCC.** Both can affect pod security; read messages carefully.
9. **Document every exception.** Include owner, reason, risk, expiry, and mitigation plan.
10. **Validate after rollout.** Check events, pod status, and `openshift.io/scc` annotation.

```bash
# 2. Describe failing workload controller
oc describe deploy <deploy> -n <ns>
oc describe rs <rs> -n <ns>

# 3. Find service account
oc get deploy <deploy> -n <ns> -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'

# 4. If empty, SA is default
SA=<sa-or-default>

# 5. Check SCC access
oc auth can-i use scc/anyuid --as=system:serviceaccount:<ns>:${SA} -n <ns>
oc auth can-i use scc/privileged --as=system:serviceaccount:<ns>:${SA} -n <ns>

# 6. Inspect security context
oc get deploy <deploy> -n <ns> -o yaml | egrep -A8 -B8 'securityContext|runAsUser|privileged|hostPath|hostNetwork|capabilities|fsGroup|seccomp'

# 7. Apply least permissive fix
oc create sa <dedicated-sa> -n <ns>
oc adm policy add-scc-to-user <scc> -z <dedicated-sa> -n <ns>
oc set serviceaccount deployment/<deploy> <dedicated-sa> -n <ns>

# 8. Verify rollout
oc rollout status deployment/<deploy> -n <ns>

# 9. Verify selected SCC
POD=$(oc get pod -n <ns> -l app=<label> -o jsonpath='{.items[0].metadata.name}')
oc get pod $POD -n <ns> -o jsonpath='{.metadata.annotations.openshift\.io\/scc}{"\n"}'
```

## 32. Final Mental Model

Think of SCC as the OpenShift gatekeeper for pod runtime permissions.

```text
RBAC says: Can this subject create a pod object?
SCC says: Can this pod run with these Linux/container privileges?
PSA says: Does this pod comply with Kubernetes Pod Security Standards?
SELinux says: Even after admission, can the process access this file/resource at runtime?
```

A 10-year experienced OpenShift administrator does not just grant `privileged`. They identify the exact blocked field, map it to the least-permissive SCC or manifest/image change, bind it to the correct service account, verify the selected SCC annotation, and document the exception.
