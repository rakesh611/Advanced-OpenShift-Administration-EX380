# OAuth Unavailable Troubleshooting in OpenShift

**Area:** Advanced Cluster Troubleshooting  
**Role level:** Advanced OpenShift Administrator / Platform SRE / L3 Support  
**Experience target:** 10+ years Linux, Kubernetes, OpenShift, networking, identity, certificates, and production support  
**Scope:** OpenShift Container Platform 4.x self-managed clusters. Most commands also help on hosted/managed variants, but some namespaces and permissions can differ.

---

## 1. What “OAuth unavailable” means

In OpenShift, users normally authenticate through the built-in OAuth server. The OAuth server validates a user against the configured identity provider, creates an OAuth access token, and the user then presents that token to the Kubernetes/OpenShift API server.

When OAuth is unavailable, the cluster API might still be running, but **new user logins fail**. Existing `oc` sessions can continue working until their bearer tokens expire. Certificate-based admin access and some service account tokens might still work because they do not require a new interactive OAuth login.

Typical user-facing symptoms are:

- Web console login page fails or loops.
- `oc login -u <user> -p <password>` fails.
- Login returns `server is currently unable to handle the request`.
- Login returns `OAuth service is unavailable`.
- Login returns `x509: certificate signed by unknown authority`.
- Login returns `EOF`, `connection reset`, `i/o timeout`, or `503 Service Unavailable`.
- The `authentication` ClusterOperator is `Degraded=True`, `Available=False`, or `Progressing=True` for too long.
- OAuth route health checks fail, usually around the `oauth-openshift` route or `/healthz` endpoint.

The important point: **OAuth unavailable is not always an identity-provider problem.** It can be caused by OAuth pods, router/ingress, DNS, certificates, CA bundles, kube-apiserver health, API aggregation, OAuth config, LDAP/OIDC/GitHub reachability, proxy settings, or manual damage to managed resources.

## 2. OpenShift OAuth architecture

At a high level, OpenShift authentication involves these parts:

```text
User / Browser / oc CLI
        |
        | HTTPS
        v
OAuth route: oauth-openshift.apps.<cluster-domain>
        |
        v
OpenShift router / IngressController
        |
        v
Service: oauth-openshift
Namespace: openshift-authentication
        |
        v
OAuth server pods
        |
        +--> oauth.config.openshift.io/cluster
        +--> Identity provider backend: htpasswd, LDAP, OIDC, GitHub, GitLab, Keystone, request-header, etc.
        +--> API server for token/user objects
        +--> certificates, CA bundles, OAuth clients, redirect URIs
```

Core components to remember:

| Component | Namespace / Resource | Purpose |
|---|---|---|
| Cluster Authentication Operator | `openshift-authentication-operator` | Reconciles authentication stack. Reports through `clusteroperator/authentication`. |
| OAuth server | `openshift-authentication` | Handles login, authorization, token creation, IdP integration. |
| OAuth route | `route/oauth-openshift -n openshift-authentication` | External HTTPS endpoint used by web console and CLI. |
| OAuth service | `svc/oauth-openshift -n openshift-authentication` | Routes traffic to OAuth server pods. |
| OAuth config | `oauth.config.openshift.io/cluster` | Defines identity providers, token settings, templates. |
| Ingress/router | `openshift-ingress`, `openshift-ingress-operator` | Publishes the OAuth route externally. |
| Config and cert material | `openshift-config`, `openshift-config-managed` | Stores IDP secrets, CA bundles, OAuth serving cert config map, managed config. |
| OAuth API server | `openshift-oauth-apiserver` | Serves OpenShift OAuth API resources in many OCP 4.x clusters. |
| Console | `openshift-console` | Uses OAuth for browser login. Often reports OAuth issues first. |

## 3. Impact analysis

OAuth unavailable can look like a full cluster outage, but the blast radius depends on which authentication paths are affected.

### Usually impacted

- New `oc login` attempts using username/password.
- Web console login.
- OAuth authorization flows.
- New tokens for users and OAuth clients.
- Login through external IdP such as LDAP, OIDC, GitHub, or request-header proxy.

### Usually not immediately impacted

- Running workloads.
- Already authenticated `oc` sessions with unexpired tokens.
- Service account tokens already mounted into pods.
- Kubelet/node operation, unless the issue is part of wider control-plane failure.
- Certificate-based admin kubeconfigs.

### Production priority

Treat OAuth unavailable as **P1/P2 depending on business impact**:

- **P1:** Admins cannot access cluster, console unavailable, no break-glass credential, cluster update in progress, or multiple control-plane operators degraded.
- **P2:** Existing admin tokens still work and only new user logins are affected.
- **P3:** One identity provider is failing but another admin IdP still works.

## 4. Golden rule: do not destroy your break-glass access

Before changing authentication, always verify at least one working admin path:

```bash
oc whoami
oc auth can-i '*' '*' --all-namespaces
oc get co authentication
```

If you are using the `kubeadmin` account, do **not** delete the `kubeadmin` secret until another cluster-admin user has been tested successfully.

Check whether the kubeadmin secret still exists:

```bash
oc get secret kubeadmin -n kube-system
```

If the OAuth stack is unstable but you still have a valid admin token, avoid logging out from that shell. Open a second terminal for tests.

## 5. Fast triage checklist

Run this first during a real incident.

```bash
# 1. Cluster operators
oc get co
oc get co authentication -o wide
oc describe co authentication
oc get co authentication -o yaml

# 2. OAuth server components
oc get deploy,rs,pod,svc,endpoints,route -n openshift-authentication -o wide
oc describe deploy/oauth-openshift -n openshift-authentication
oc describe route/oauth-openshift -n openshift-authentication
oc get endpoints oauth-openshift -n openshift-authentication -o yaml

# 3. Authentication operator
oc get pod -n openshift-authentication-operator -o wide
oc logs -n openshift-authentication-operator deploy/authentication-operator --tail=300

# 4. OAuth server logs
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300
oc logs -n openshift-authentication deploy/oauth-openshift --previous --tail=300

# 5. Ingress/router
oc get co ingress
oc get ingresscontroller default -n openshift-ingress-operator -o wide
oc get pod -n openshift-ingress -o wide
oc logs -n openshift-ingress deploy/router-default --tail=200

# 6. OAuth configuration
oc get oauth.config.openshift.io cluster -o yaml
oc get secret,configmap -n openshift-config
oc get configmap -n openshift-config-managed | grep -i oauth

# 7. API and aggregated API health
oc get co kube-apiserver openshift-apiserver authentication ingress console
oc get --raw='/readyz?verbose'
oc get --raw='/livez?verbose'
```

For a quick route health test:

```bash
OAUTH_HOST=$(oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}')
echo "$OAUTH_HOST"
curl -vk "https://${OAUTH_HOST}/healthz"
curl -vk "https://${OAUTH_HOST}/.well-known/oauth-authorization-server"
```

If testing from inside the cluster:

```bash
oc run oauth-debug -n default --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside the pod:
curl -vk https://openshift.default.svc/.well-known/oauth-authorization-server
curl -vk https://oauth-openshift.openshift-authentication.svc/healthz
```

## 6. How to read `clusteroperator/authentication`

The `authentication` ClusterOperator status is your primary signal.

```bash
oc get co authentication
oc describe co authentication
oc get co authentication -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

Important conditions:

| Condition | Meaning |
|---|---|
| `Available=True` | Authentication stack is considered available. |
| `Available=False` | OAuth or related authentication components are not serving correctly. |
| `Degraded=True` | Operator detected a persistent error. Read `Reason` and `Message`. |
| `Progressing=True` | Rollout/config change is happening. Normal for a short time, suspicious if stuck. |
| `Upgradeable=False` | Authentication problem can block upgrade safety. |

Common condition reasons/messages:

| Message fragment | Likely area |
|---|---|
| `OAuthServerRouteEndpointAccessibleController` | OAuth route, router, DNS, TLS, route health. |
| `OAuthServerDeployment` | OAuth deployment/pods not ready. |
| `OAuthServerConfigObservation` | Invalid OAuth configuration or referenced secrets/config maps. |
| `OAuthAPIServerDeployment` / `PreconditionNotReady` | OAuth API server or aggregated API health. |
| `x509: certificate is not valid` | TLS SAN/CN mismatch, wrong custom cert, wrong route hostname. |
| `certificate signed by unknown authority` | Missing CA bundle, custom cert not trusted. |
| `no endpoints available` | OAuth service selector/pods not ready. |
| `context deadline exceeded` / `i/o timeout` | DNS, router, network, proxy, backend unreachable. |
| `connect: connection refused` | Service has no listener, router backend down, wrong target port. |

In a production incident, **copy the exact condition message** before you start remediation. It often points directly to the failing controller.

## 7. Troubleshooting flow

Use this order to avoid wasting time.

```text
1. Can I still access the API as cluster-admin?
   |
   +-- No  --> Use break-glass kubeconfig/kubeadmin/admin cert path.
   |
   +-- Yes --> Continue.

2. Is authentication ClusterOperator degraded/unavailable?
   |
   +-- No  --> Problem might be user-specific, IdP-specific, console-specific, or RBAC.
   |
   +-- Yes --> Read condition reason/message.

3. Are OAuth pods running and ready?
   |
   +-- No  --> Fix deployment/pod/scheduling/image/cert/config issue.
   |
   +-- Yes --> Continue.

4. Does OAuth service have endpoints?
   |
   +-- No  --> Fix labels/selectors/pod readiness.
   |
   +-- Yes --> Continue.

5. Does OAuth route admit and reach /healthz?
   |
   +-- No  --> Fix route, ingress, DNS, LB, router, TLS.
   |
   +-- Yes --> Continue.

6. Does OAuth fail only after credential submit?
   |
   +-- Yes --> Fix identity provider backend, CA, bind credentials, user mapping, client secret.
   |
   +-- No  --> Check OAuth clients, console redirect, API/aggregated APIs, token storage.
```

## 8. Scenario 1: OAuth pods are not running

### Symptoms

```bash
oc get pod -n openshift-authentication
```

You might see:

- `Pending`
- `CrashLoopBackOff`
- `ImagePullBackOff`
- `CreateContainerConfigError`
- `Running` but `0/1 Ready`
- Very frequent restarts

### Commands

```bash
oc get deploy/oauth-openshift -n openshift-authentication -o yaml
oc describe deploy/oauth-openshift -n openshift-authentication
oc get rs -n openshift-authentication
oc describe pod -n openshift-authentication -l app=oauth-openshift
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300
oc logs -n openshift-authentication deploy/oauth-openshift --previous --tail=300
oc get events -n openshift-authentication --sort-by=.lastTimestamp
```

### What to check

#### 8.1 Pending pods

Check scheduler and node capacity:

```bash
oc describe pod <oauth-pod> -n openshift-authentication
oc get nodes
oc describe node <node>
oc adm top nodes
oc adm top pods -n openshift-authentication
```

Look for:

- Taints not tolerated.
- No schedulable nodes.
- Control-plane nodes unavailable.
- Resource pressure: memory, disk, PID, ephemeral storage.
- MachineConfigPool updating or degraded.

Fix the real node/scheduler problem. Do not patch managed OAuth deployment scheduling unless Red Hat support directs it.

#### 8.2 CrashLoopBackOff

Check the container log and previous log:

```bash
oc logs -n openshift-authentication <pod> -c oauth-openshift --tail=300
oc logs -n openshift-authentication <pod> -c oauth-openshift --previous --tail=300
```

Common causes:

- Invalid OAuth configuration.
- Referenced IdP secret missing.
- Referenced CA config map missing or malformed.
- Bad TLS certificate/key pair.
- Failed to read mounted config.
- Bug or bad payload during upgrade.

Then inspect OAuth configuration:

```bash
oc get oauth.config.openshift.io cluster -o yaml
oc get secret -n openshift-config
oc get cm -n openshift-config
```

#### 8.3 ImagePullBackOff

Usually this means a wider image registry or pull-secret issue:

```bash
oc describe pod <oauth-pod> -n openshift-authentication
oc get secret pull-secret -n openshift-config -o yaml
oc get co image-registry marketplace authentication
oc get images.config.openshift.io cluster -o yaml
```

In disconnected clusters, verify the release image mirror and imageContentSources/imageDigestSources configuration.

## 9. Scenario 2: OAuth service has no endpoints

### Symptoms

```bash
oc get endpoints oauth-openshift -n openshift-authentication -o wide
```

Output might show no subsets/endpoints.

### Diagnosis

```bash
oc get svc oauth-openshift -n openshift-authentication -o yaml
oc get pod -n openshift-authentication --show-labels
oc get endpointslice -n openshift-authentication -l kubernetes.io/service-name=oauth-openshift -o yaml
oc describe pod -n openshift-authentication -l app=oauth-openshift
```

### Likely causes

- OAuth pods are not ready.
- Readiness probe is failing.
- Managed service selector was modified manually.
- Pods lost expected labels due to unsupported edits.
- Admission/security issue prevents pod readiness.

### Recovery

Do not manually redesign the managed service. Let the operator reconcile:

```bash
oc delete pod -n openshift-authentication -l app=oauth-openshift
```

If someone edited managed resources, compare with another healthy cluster or gather operator logs. In serious manual-damage cases, deleting the damaged managed resource can allow the operator to recreate it, but do this carefully and only when you have admin access and a rollback plan.

## 10. Scenario 3: OAuth route is not admitted or not reachable

The OAuth route is one of the most common causes of `OAuth unavailable`.

### Commands

```bash
oc get route oauth-openshift -n openshift-authentication -o wide
oc describe route oauth-openshift -n openshift-authentication
oc get route oauth-openshift -n openshift-authentication -o yaml
oc get co ingress
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc get pod -n openshift-ingress -o wide
oc logs -n openshift-ingress deploy/router-default --tail=300
```

Check the route admitted condition:

```bash
oc get route oauth-openshift -n openshift-authentication \
  -o jsonpath='{range .status.ingress[*].conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}'
```

### External health test

```bash
OAUTH_HOST=$(oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}')

# DNS resolution
getent hosts "$OAUTH_HOST"
dig +short "$OAUTH_HOST"
nslookup "$OAUTH_HOST"

# TLS and HTTP health
curl -vk "https://${OAUTH_HOST}/healthz"
openssl s_client -connect "${OAUTH_HOST}:443" -servername "${OAUTH_HOST}" -showcerts </dev/null
```

### Internal router path test

From a debug pod:

```bash
oc run net-debug -n default --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
curl -vk https://oauth-openshift.openshift-authentication.svc/healthz
curl -vk https://openshift.default.svc/.well-known/oauth-authorization-server
```

### Common causes

#### 10.1 Wildcard DNS broken

OAuth route host should resolve to the ingress VIP/load balancer.

Check:

```bash
dig +short "*.apps.<cluster-domain>"
dig +short "oauth-openshift.apps.<cluster-domain>"
```

Fix DNS to point the apps wildcard to the correct ingress VIP/load balancer.

#### 10.2 Load balancer or firewall problem

Symptoms:

- DNS resolves correctly but connection times out.
- Port 443 closed externally.
- Router pods are healthy but traffic never arrives.

Check:

```bash
curl -vk https://oauth-openshift.apps.<cluster-domain>/healthz
nc -vz oauth-openshift.apps.<cluster-domain> 443
```

If `nc` is not available in your image, use `curl -vk` or install tools in a temporary debug image.

Fix:

- Restore LB listener for 443.
- Check health checks to router nodes.
- Check security groups/firewall.
- Check bare-metal VIP/Keepalived/MetalLB/F5/HAProxy configuration.

#### 10.3 Router pods down

```bash
oc get pod -n openshift-ingress -o wide
oc describe pod -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=default
oc logs -n openshift-ingress deploy/router-default --tail=300
```

Check:

- Router deployment replicas.
- Node placement.
- HostNetwork/ports conflict.
- Router certificate issues.
- Ingress Operator degraded.

#### 10.4 Route sharding excludes OAuth namespace

If the default IngressController has a `namespaceSelector` or `routeSelector`, it can accidentally exclude the OAuth route.

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

Look for:

```yaml
spec:
  namespaceSelector: ...
  routeSelector: ...
```

If selectors were added incorrectly, restore a valid selector that includes `openshift-authentication`, or remove the selector if not required.

#### 10.5 Custom apps domain mismatch

Check cluster ingress domain:

```bash
oc get ingress.config.openshift.io cluster -o yaml
oc get dns.config.openshift.io cluster -o yaml
```

If the apps domain was changed, ensure:

- OAuth route host uses the intended domain.
- DNS wildcard points to router.
- Certificate SAN covers the hostname.
- Console OAuth redirect points to the right issuer.

## 11. Scenario 4: TLS certificate problem on OAuth route

### Symptoms

- `x509: certificate is not valid for any names`
- `x509: certificate is valid for X, not oauth-openshift.apps...`
- `certificate signed by unknown authority`
- Browser warns about invalid certificate.
- `oc login` works only with `--insecure-skip-tls-verify=true`.
- Authentication ClusterOperator reports OAuth route endpoint inaccessible.

### Inspect certificate presented by route

```bash
OAUTH_HOST=$(oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}')
openssl s_client -connect "${OAUTH_HOST}:443" -servername "${OAUTH_HOST}" -showcerts </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

### Check custom component route

OpenShift supports customizing the internal OAuth server URL with `spec.componentRoutes` in the cluster `Ingress` config.

```bash
oc get ingress.config.openshift.io cluster -o yaml
```

Look for:

```yaml
spec:
  componentRoutes:
  - name: oauth-openshift
    namespace: openshift-authentication
    hostname: <custom-hostname>
    servingCertKeyPairSecret:
      name: <secret-name>
```

Then inspect the secret:

```bash
oc get secret <secret-name> -n openshift-config -o yaml
oc extract secret/<secret-name> -n openshift-config --to=/tmp/oauth-cert --confirm
openssl x509 -in /tmp/oauth-cert/tls.crt -noout -subject -issuer -dates -ext subjectAltName
openssl rsa -in /tmp/oauth-cert/tls.key -check -noout
```

Verify:

- `tls.crt` and `tls.key` match.
- Certificate is not expired.
- SAN contains the OAuth hostname.
- Full chain is present if required.
- CA is trusted by clients.
- Secret exists in `openshift-config`, not the route namespace.

### Extract OAuth serving CA bundle

```bash
oc get cm oauth-serving-cert -n openshift-config-managed -o yaml
oc extract cm/oauth-serving-cert -n openshift-config-managed --to=/tmp/oauth-ca --confirm
ls -l /tmp/oauth-ca
```

### Recovery examples

Create a correct TLS secret:

```bash
oc create secret tls oauth-custom-cert \
  --cert=/path/to/tls.crt \
  --key=/path/to/tls.key \
  -n openshift-config
```

Patch custom component route carefully:

```bash
oc patch ingress.config.openshift.io cluster --type=merge -p '{
  "spec": {
    "componentRoutes": [
      {
        "name": "oauth-openshift",
        "namespace": "openshift-authentication",
        "hostname": "oauth-openshift.apps.example.com",
        "servingCertKeyPairSecret": {"name": "oauth-custom-cert"}
      }
    ]
  }
}'
```

If the custom route caused outage and you need to return to default generated behavior, remove the bad component route entry:

```bash
oc edit ingress.config.openshift.io cluster
```

Then remove or correct only the OAuth component route stanza. Watch rollout:

```bash
oc get co authentication -w
oc get pod -n openshift-authentication -w
```

## 12. Scenario 5: OAuth configuration is invalid

The cluster-wide OAuth config lives here:

```bash
oc get oauth.config.openshift.io cluster -o yaml
```

### Common bad changes

- Referenced secret does not exist.
- Secret exists in wrong namespace.
- ConfigMap CA reference is missing.
- Wrong key names inside secret/config map.
- Invalid LDAP bind DN/password.
- Invalid OIDC issuer URL or client secret.
- Broken request-header CA config.
- Incorrect mapping method causing identity conflict.
- YAML indentation or field name mistakes.
- Removing all valid identity providers before testing another admin login.

### Validate referenced objects

```bash
oc get oauth.config.openshift.io cluster -o jsonpath='{.spec.identityProviders}' | jq
oc get secret -n openshift-config
oc get cm -n openshift-config
```

For each identity provider, verify its referenced secrets/config maps.

Example for HTPasswd:

```bash
oc get oauth.config.openshift.io cluster -o yaml | sed -n '/identityProviders:/,$p'
oc get secret <htpasswd-secret-name> -n openshift-config -o yaml
oc extract secret/<htpasswd-secret-name> -n openshift-config --to=/tmp/htpasswd --confirm
ls -l /tmp/htpasswd
cat /tmp/htpasswd/htpasswd
```

The secret should contain a key normally named `htpasswd`.

### Watch operator reaction after changes

```bash
oc get co authentication -w
oc get pod -n openshift-authentication -w
oc logs -n openshift-authentication-operator deploy/authentication-operator -f
```

## 13. Scenario 6: HTPasswd identity provider issue

HTPasswd is common in labs and exams, so know it deeply.

### Expected objects

```bash
oc get oauth.config.openshift.io cluster -o yaml
oc get secret -n openshift-config <secret-name>
```

Example OAuth spec:

```yaml
spec:
  identityProviders:
  - name: local-htpasswd
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: local-users
```

### Create or update HTPasswd secret

```bash
htpasswd -c -B -b /tmp/htpasswd admin 'RedHat@123'
htpasswd -B -b /tmp/htpasswd user1 'Password@123'

oc create secret generic local-users \
  --from-file=htpasswd=/tmp/htpasswd \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

Patch OAuth config:

```bash
oc patch oauth.config.openshift.io cluster --type=merge -p '{
  "spec": {
    "identityProviders": [
      {
        "name": "local-htpasswd",
        "mappingMethod": "claim",
        "type": "HTPasswd",
        "htpasswd": {
          "fileData": {"name": "local-users"}
        }
      }
    ]
  }
}'
```

Watch rollout:

```bash
oc get co authentication -w
oc get pod -n openshift-authentication -w
```

### Test login safely

Use a second terminal:

```bash
oc login -u admin -p 'RedHat@123' https://api.<cluster-domain>:6443
oc whoami
```

If the user logs in but cannot do anything, that is RBAC, not OAuth availability:

```bash
oc auth can-i get pods -A
oc adm policy add-cluster-role-to-user cluster-admin admin
```

## 14. Scenario 7: LDAP identity provider issue

LDAP failures usually appear only after submitting credentials. The OAuth route and pods can be healthy, but authentication fails.

### Commands

```bash
oc get oauth.config.openshift.io cluster -o yaml
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300 | grep -i ldap
oc get secret,cm -n openshift-config
```

### Verify LDAP connectivity from cluster

```bash
oc run ldap-debug -n default --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
curl -vk ldap://ldap.example.com:389
curl -vk ldaps://ldap.example.com:636
```

If tools are available:

```bash
ldapsearch -x -H ldap://ldap.example.com:389 \
  -D 'cn=admin,dc=example,dc=com' -W \
  -b 'dc=example,dc=com' '(uid=testuser)'
```

### Check CA for LDAPS

```bash
oc get cm <ldap-ca-configmap> -n openshift-config -o yaml
oc extract cm/<ldap-ca-configmap> -n openshift-config --to=/tmp/ldap-ca --confirm
openssl x509 -in /tmp/ldap-ca/ca.crt -noout -subject -issuer -dates
```

### Common LDAP causes

- Wrong LDAP URL.
- DNS cannot resolve LDAP hostname from cluster nodes/pods.
- Firewall blocks LDAP/LDAPS port.
- Wrong bind DN or bind password.
- Wrong base DN or filter.
- LDAPS certificate chain not trusted.
- LDAP certificate SAN does not match configured hostname.
- LDAP server is slow; OAuth request times out.
- User exists but expected attribute is missing.
- Identity mapping conflict with existing user/identity object.

### Recovery

- Correct URL, bind DN, bind password secret, CA config map.
- Test LDAP from inside cluster network.
- Keep a local HTPasswd admin IdP as break-glass in enterprise clusters.

## 15. Scenario 8: OIDC identity provider issue

OIDC failures can involve external IdP availability, issuer metadata, redirect URI, client secret, token claims, or CA trust.

### Commands

```bash
oc get oauth.config.openshift.io cluster -o yaml
oc logs -n openshift-authentication deploy/oauth-openshift --tail=500 | egrep -i 'oidc|openid|oauth|token|issuer|claim|redirect|x509'
```

### Verify issuer metadata

From a debug pod:

```bash
oc run oidc-debug -n default --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi -- bash

# Inside pod:
curl -vk https://idp.example.com/.well-known/openid-configuration
```

### Check typical OIDC settings

In the external IdP, verify:

- Redirect URI exactly matches the OpenShift OAuth callback URL.
- Client ID is correct.
- Client secret is correct.
- Issuer URL matches exactly, including scheme and path.
- Required scopes are allowed.
- Username/email/name claims exist.
- IdP certificate chain is trusted.

Typical OpenShift OAuth callback pattern:

```text
https://oauth-openshift.apps.<cluster-domain>/oauth2callback/<idp-name>
```

### Common OIDC root causes

- IdP application was rotated or deleted.
- Client secret expired or rotated but OpenShift secret not updated.
- Redirect URI configured for old apps domain.
- Corporate proxy blocks outbound access from cluster.
- IdP certificate rotated and CA bundle stale.
- OIDC discovery endpoint unavailable.
- Clock skew affects token validation.

Check node time:

```bash
oc debug node/<node-name>
chroot /host timedatectl
```

## 16. Scenario 9: Request-header identity provider issue

Request-header authentication is normally used with an authenticating proxy. OAuth trusts selected headers only when they come from a trusted client certificate/CA path.

### Check config

```bash
oc get oauth.config.openshift.io cluster -o yaml
oc get cm,secret -n openshift-config
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300 | egrep -i 'request|header|x509|certificate|proxy'
```

### Common causes

- Proxy not injecting expected headers.
- Header names do not match OAuth config.
- Client CA bundle incorrect.
- Proxy certificate expired.
- Proxy route changed.
- OAuth callback/redirect through proxy misconfigured.
- Load balancer strips required headers.

### Recovery

- Validate proxy TLS chain.
- Validate header injection with a controlled test.
- Confirm OpenShift OAuth config references correct CA config map.
- Confirm the proxy is the only trusted path. Do not trust arbitrary client-supplied identity headers.

### Check important certificates

OAuth route certificate:

### Common certificate mistakes

- Secret contains only leaf cert, missing intermediate chain.
- Certificate SAN does not include route hostname.
- Wildcard cert covers `*.apps.example.com` but route is on a different domain.
- Wrong private key paired with cert.
- Self-signed cert used without distributing CA.
- External IdP changed CA, but OpenShift still has old CA bundle.
- Corporate TLS inspection proxy re-signs traffic but cluster does not trust proxy CA.

## 20. Scenario 13: OAuth unavailable after cluster upgrade

During upgrades, authentication can show `Progressing=True`. Short progressing is normal. Stuck progressing or degraded is not.

### Commands

```bash
oc get clusterversion
oc describe clusterversion

oc get pod -n openshift-authentication -o wide
oc get pod -n openshift-authentication-operator -o wide

```

### Check rollout

```bash

oc get rs -n openshift-authentication
oc describe deploy/oauth-openshift -n openshift-authentication
```

### Common causes

- Nodes unavailable during rollout.
- Old OAuth pods stuck terminating.
- PDB/topology constraints delay rollout.
- Image pull issues after update.
- Ingress operator updating simultaneously.
- Certificate or config observation failed.
- Manual change conflicts with new operator reconciliation.

### Recovery approach

1. Do not force random rollbacks.
2. Fix node/image/ingress/cert/config issue first.
3. Delete stuck OAuth pod only if deployment can recreate it.
4. Gather must-gather before destructive changes.
5. If the release payload is suspected, involve Red Hat support with exact version and operator logs.

## 23. Scenario 16: User/identity mapping conflict

Sometimes OAuth is available, but one or more users cannot log in due to identity mapping conflicts.

### Symptoms

- One user fails; others succeed.
- Logs mention identity already mapped.
- User was renamed in IdP.
- IdP name changed in OAuth config.
- `mappingMethod` changed.

### Commands

```bash
oc get users
oc get identities
oc get user <username> -o yaml
oc get identity <idp-name>:<idp-username> -o yaml
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300 | grep -i identity
```

### Understand mapping methods

| Mapping method | Behavior |
|---|---|
| `claim` | Default-like behavior; fails on conflicting identity/user claim. Safer. |
| `lookup` | Only allows login if identity already exists. Useful for controlled migrations. |
| `generate` | Generates unique user names on conflict. |
| `add` | Adds new identity to existing user if username matches. Powerful but risky. |

### Recovery

For user-specific conflicts, inspect and carefully modify `User` and `Identity` objects. Do not bulk delete users/identities during an outage.

Example:

```bash
oc get user problemuser -o yaml
oc get identity '<idp-name>:<idp-user>' -o yaml
```

If you must unlink an incorrect identity, back up first:

```bash
oc get user problemuser -o yaml > /tmp/user-problemuser.yaml
oc get identity '<idp-name>:<idp-user>' -o yaml > /tmp/identity-problemuser.yaml
```

Then use supported user/identity management commands or carefully edit references.

- `redirectURIs` exactly match application callback URLs.

## 28. Safe recovery patterns

### 28.1 Restart OAuth pods safely

Use when config is corrected and pods need to reload, or pods are stuck but deployment is healthy.

```bash
oc delete pod -n openshift-authentication -l app=oauth-openshift
oc get pod -n openshift-authentication -w
oc get co authentication -w
```

### 28.2 Restart authentication operator pod

Use only if the operator appears stuck and no rollout is happening.

```bash
oc delete pod -n openshift-authentication-operator -l app=authentication-operator
oc get pod -n openshift-authentication-operator -w
```

### 28.3 Reapply correct HTPasswd secret

```bash
oc create secret generic local-users \
  --from-file=htpasswd=/tmp/htpasswd \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

### 28.4 Add emergency local admin IdP

If enterprise IdP is down and you still have admin access, add a temporary HTPasswd IdP.

```bash
htpasswd -c -B -b /tmp/emergency.htpasswd emergency-admin 'ChangeMe-Strong-Password'

oc create secret generic emergency-htpasswd \
  --from-file=htpasswd=/tmp/emergency.htpasswd \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

Edit OAuth config and add a second identity provider rather than replacing the existing one blindly:

```bash
oc edit oauth.config.openshift.io cluster
```

Example additional entry:

```yaml
spec:
  identityProviders:
  - name: emergency-local
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: emergency-htpasswd
```

After login succeeds:

```bash
oc adm policy add-cluster-role-to-user cluster-admin emergency-admin
```

Remove the emergency IdP after the incident according to change control.

### 28.5 Fix custom OAuth route certificate

```bash
oc create secret tls oauth-custom-cert \
  --cert=/path/to/fullchain.crt \
  --key=/path/to/tls.key \
  -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
```

Then patch or edit `ingress.config.openshift.io/cluster`.

### 28.6 Restore broken route/DNS/ingress

- Fix apps wildcard DNS.
- Restore router deployment.
- Restore ingress VIP/load balancer.
- Remove accidental route/namespace selectors that exclude OAuth.
- Fix custom route certificates.

---

## 29. Unsafe actions to avoid

Avoid these during an OAuth outage:

- Deleting `kubeadmin` before a replacement admin login is tested.
- Replacing all identity providers at once without a backup.
- Deleting all `users` or `identities` objects.
- Deleting all OAuth tokens as a blind fix.
- Editing managed deployments permanently instead of fixing source config.
- Patching service selectors randomly.
- Disabling TLS verification as a permanent fix.
- Ignoring certificate SAN/chain and only checking expiry.
- Restarting all control-plane components before reading the operator condition.
- Running broad `oc delete` commands in `openshift-*` namespaces without understanding ownership.

## 31. Real-world troubleshooting examples

### Example A: `OAuthServerRouteEndpointAccessibleControllerDegraded` with x509 SAN mismatch

Condition:

```text
OAuthServerRouteEndpointAccessibleControllerDegraded:
Get "https://oauth-openshift.apps.prod.example.com/healthz":
x509: certificate is valid for *.apps.old.example.com, not oauth-openshift.apps.prod.example.com
```

Diagnosis:

```bash
oc get ingress.config.openshift.io cluster -o yaml
oc get route oauth-openshift -n openshift-authentication -o yaml
openssl s_client -connect oauth-openshift.apps.prod.example.com:443 \
  -servername oauth-openshift.apps.prod.example.com -showcerts </dev/null
```

Root cause:

- Apps domain changed, but ingress/default certificate still covers old domain.

Fix:

- Install certificate with SAN for `*.apps.prod.example.com` or correct OAuth component route cert.
- Ensure full chain exists.
- Watch authentication and ingress operators.

### Example B: OAuth route 503

Symptoms:

```bash
curl -vk https://oauth-openshift.apps.example.com/healthz
# HTTP/1.1 503 Service Unavailable
```

Diagnosis:

```bash
oc get endpoints oauth-openshift -n openshift-authentication -o yaml
oc get pod -n openshift-authentication -o wide
oc describe pod -n openshift-authentication -l app=oauth-openshift
```

Root cause possibilities:

- OAuth pods not ready.
- Service has no endpoints.
- Readiness probe failing.

Fix:

- Fix pod crash/config/cert issue.
- Delete pod only after source issue is corrected.

### Example C: OAuth works, LDAP users cannot login

Symptoms:

- `/healthz` works.
- Login page loads.
- LDAP users fail.
- Local admin IdP works.

Diagnosis:

```bash
oc logs -n openshift-authentication deploy/oauth-openshift --tail=300 | grep -i ldap
oc get oauth.config.openshift.io cluster -o yaml
```

Root cause possibilities:

- LDAP bind password changed.
- LDAPS CA expired.
- LDAP firewall blocked.
- LDAP hostname changed.

Fix:

- Update secret/CA/config.
- Test LDAP from cluster network.

### Example D: OAuth unavailable after adding route selector

Symptoms:

- Apps routes for selected workloads work.
- OAuth route no longer admitted.
- `authentication` ClusterOperator degraded.

Diagnosis:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
oc describe route oauth-openshift -n openshift-authentication
```

Root cause:

- IngressController `namespaceSelector`/`routeSelector` excludes `openshift-authentication`.

Fix:

- Remove or correct selectors.
- Confirm route admitted.

## 32. Interview-level explanation

A senior OpenShift admin should explain OAuth unavailable like this:

> In OpenShift, OAuth is the built-in token issuing layer used by the web console and `oc login`. The API server can still be healthy while OAuth is unavailable, because existing bearer tokens and certificate-based auth can continue to work. I first check `clusteroperator/authentication` because the condition message usually tells whether the failure is in route reachability, deployment readiness, config observation, OAuth API server, or certificates. Then I verify the OAuth pods in `openshift-authentication`, service endpoints, route admission, router/ingress health, TLS certificate SAN/chain, and the configured IdP backend. I avoid deleting `kubeadmin` or replacing all IdPs during the incident. If external IdP is the issue, I add or use a break-glass local IdP. If route health fails, I check DNS, LB, router, route selectors, and custom component route certs. I collect must-gather before risky changes.

## 35. Preventive controls

For mature OpenShift operations:

1. Keep at least two cluster-admin access paths:
   - Enterprise IdP group.
   - Break-glass local HTPasswd or certificate-based admin path.

2. Monitor `clusteroperator/authentication`:
   - `Available=False`
   - `Degraded=True`
   - Long `Progressing=True`

3. Monitor OAuth route health:

```bash
curl -sk https://oauth-openshift.apps.<cluster-domain>/healthz
```

4. Monitor certificate expiry:
   - Ingress default certificate.
   - OAuth custom component route cert.
   - External IdP CA/cert.
   - Proxy CA.

5. Protect managed namespaces:
   - Use RBAC/change control.
   - Avoid manual edits in `openshift-authentication` unless required.

6. Validate IdP changes in maintenance windows:
   - Add new IdP without removing old one.
   - Test login in second terminal.
   - Confirm RBAC.
   - Only then remove old IdP.

7. Keep a tested runbook:
   - OAuth route checks.
   - HTPasswd emergency admin.
   - LDAP/OIDC test commands.
   - Certificate replacement process.
   - Must-gather procedure.

## 36. Quick RCA templates

### RCA template: route/TLS

```text
Issue:
New OpenShift logins failed because OAuth route health check failed.

Impact:
Web console and new oc login sessions were unavailable. Existing sessions continued until token expiry.

Detection:
clusteroperator/authentication reported Degraded=True with OAuthServerRouteEndpointAccessibleController error.

Root cause:
OAuth route presented a certificate whose SAN did not match oauth-openshift.apps.<domain>.

Resolution:
Replaced custom OAuth/ingress certificate with a valid full-chain certificate covering the OAuth hostname and verified /healthz.

Prevention:
Added certificate expiry/SAN monitoring and change validation for ingress componentRoutes.
```

### RCA template: IdP backend

```text
Issue:
Users could reach OAuth login page but credential validation failed.

Impact:
New logins through LDAP/OIDC failed. Break-glass local admin IdP remained available.

Detection:
OAuth pod logs showed external IdP connection/certificate/bind failure.

Root cause:
External IdP certificate/client secret/bind password changed without updating OpenShift OAuth config.

Resolution:
Updated OpenShift secret/CA/config and verified login.

Prevention:
Added IdP certificate/secret rotation calendar and pre-change login validation.
```

## 37. Final mental model

When troubleshooting OAuth unavailable, think in layers:

```text
Layer 1: Admin access preserved?
Layer 2: authentication ClusterOperator condition?
Layer 3: OAuth deployment/pods ready?
Layer 4: OAuth service endpoints present?
Layer 5: OAuth route admitted and reachable?
Layer 6: TLS certificate valid and trusted?
Layer 7: OAuth config valid?
Layer 8: Identity provider reachable and accepting credentials?
Layer 9: User/identity/RBAC correct?
Layer 10: Wider API/etcd/control-plane healthy?
```

Do not jump directly to LDAP/OIDC or HTPasswd. First prove that the OAuth server and route are actually available. Then troubleshoot the identity provider.
