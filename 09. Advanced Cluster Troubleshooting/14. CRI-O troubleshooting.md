## 1. What CRI-O Is in OpenShift

CRI-O is the container runtime used by OpenShift nodes to run Kubernetes workloads. It implements the Kubernetes **Container Runtime Interface (CRI)** and works with OCI-compatible low-level runtimes such as `crun` or `runc`.

In simple terms:

```text
Kubernetes API
   ↓
Scheduler chooses node
   ↓
Kubelet receives PodSpec
   ↓
Kubelet talks to CRI-O over CRI socket
   ↓
CRI-O pulls image, creates sandbox, starts containers
   ↓
Low-level runtime starts Linux container process
```

CRI-O is not the scheduler, not the kubelet, and not the CNI plugin. It is the runtime engine responsible for container lifecycle operations on the node.

### Senior admin definition

CRI-O is the node-local runtime service that converts kubelet CRI requests into image pulls, pod sandboxes, containers, mounts, namespaces, cgroups, SELinux labels, and OCI runtime executions.

### Why CRI-O matters

If CRI-O fails, the node might still be reachable by SSH and might still have a running OS, but Kubernetes workloads can fail badly:

- New pods cannot start.
- Existing containers might continue temporarily, but lifecycle operations fail.
- `oc debug node/<node>` might fail because debug pods also require the runtime.
- Kubelet reports runtime errors.
- Node can become `NotReady`.
- MachineConfig updates can stall.
- Control plane static pods can be affected on master/control-plane nodes.

## 2. Where CRI-O Fits in the Node Stack

A practical OpenShift node stack looks like this:

```text
OpenShift API / Kubernetes API
        |
        | PodSpec, status updates
        v
+-------------------+
| kubelet.service   |
+-------------------+
        |
        | CRI gRPC over Unix socket
        v
+-------------------+
| crio.service      |
+-------------------+
        |
        +--> containers/image     image pulls, registries, auth, mirrors
        +--> containers/storage   overlay storage, image layers, writable layers
        +--> CNI plugins          pod networking setup
        +--> conmon               container monitor process
        +--> crun/runc            OCI runtime process creation
        +--> SELinux/cgroups      security and resource isolation
```

### Important paths

| Area | Common path |
|---|---|
| CRI-O service | `crio.service` |
| CRI socket | `/var/run/crio/crio.sock` |
| Main CRI-O config | `/etc/crio/crio.conf` or generated config fragments |
| Registry config | `/etc/containers/registries.conf` and drop-ins |
| Storage config | `/etc/containers/storage.conf` |
| Container storage | `/var/lib/containers/storage` |
| Runtime state | `/run/containers/storage`, `/var/run/containers` |
| Pod logs | `/var/log/pods` |
| Container log symlinks | `/var/log/containers` |
| Kubelet state | `/var/lib/kubelet` |
| CNI config | `/etc/kubernetes/cni/net.d` or platform-managed locations |

Do not assume these files should be manually edited in OpenShift. OpenShift 4 nodes are managed by the Machine Config Operator. Direct manual edits are usually temporary, unsupported, or overwritten.

## 3. Common CRI-O Failure Symptoms

### Cluster-level symptoms

```bash
oc get nodes
```

You might see:

```text
NAME       STATUS     ROLES    AGE   VERSION
worker-1   NotReady   worker   30d   v1.xx.x
worker-2   Ready      worker   30d   v1.xx.x
```

Or:

```text
Ready,SchedulingDisabled
NotReady,SchedulingDisabled
```

### Pod-level symptoms

```bash
oc get pods -A | egrep 'ContainerCreating|ImagePullBackOff|CrashLoopBackOff|CreateContainerError|RunContainerError|Unknown|Terminating'
```

Common statuses:

| Pod status | Runtime meaning |
|---|---|
| `ContainerCreating` | CRI-O might be pulling image, creating sandbox, mounting volume, or waiting on CNI/storage. |
| `CreateContainerError` | CRI-O accepted pod sandbox but failed creating a container. |
| `RunContainerError` | Runtime failed while starting container process. |
| `ImagePullBackOff` | CRI-O could not pull image or registry access failed. |
| `ErrImagePull` | Immediate image pull failure. |
| `Pod sandbox changed` | Sandbox was recreated or runtime/CNI state changed. |
| `Unknown` | Kubelet lost reliable state from runtime or node. |

### Event messages that point to CRI-O

Check events:

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Examples:

```text
Failed to create pod sandbox
Failed to create container
container create failed
rpc error: code = Unknown desc = ...
failed to mount container
error recreating the missing symlinks
can't stat lower layer
failed to reserve container name
failed to find plugin "loopback" in path
failed to setup network for sandbox
permission denied
operation not permitted
no space left on device
too many open files
context deadline exceeded
```

### Service-level symptoms

Inside node debug shell or SSH:

```bash
systemctl is-active crio
systemctl status crio.service
journalctl -b -u crio.service
```

Bad signs:

```text
inactive
failed
activating (auto-restart)
Start request repeated too quickly
Main process exited, code=exited, status=1/FAILURE
```

## 4. Production Troubleshooting Mindset

A 10-year experienced administrator does not start with destructive cleanup. The correct order is:

```text
Observe → Scope → Correlate → Stabilize → Collect Evidence → Fix → Verify → Prevent recurrence
```

### Do not immediately restart CRI-O

A restart can interrupt active lifecycle operations and hide logs. First answer:

1. Is the issue one node, one MachineConfigPool, or the whole cluster?
2. Are only new pods failing, or are existing pods also dying?
3. Is kubelet healthy?
4. Is CRI-O active?
5. Is storage full?
6. Is CNI healthy?
7. Is the image registry reachable?
8. Did MCO just apply a config?
9. Did the issue begin after upgrade, reboot, certificate change, registry mirror change, or node drain?

### Scope before action

```bash
oc get nodes -o wide
oc get mcp
oc get co
oc get pods -A --field-selector spec.nodeName=<node_name>
oc adm top nodes
```

### Golden rule

If the node is production and running real workload, **cordon and drain when possible before runtime-level repair**.

Use this checklist when someone says: “Pods are stuck on a node” or “Node is NotReady”.

### Step 1: Identify affected nodes

```bash
oc get nodes
oc get nodes -o wide
```

### Step 2: Check node conditions

```bash
oc describe node <node_name>
```

Look for:

```text
Ready=False
MemoryPressure=True
DiskPressure=True
PIDPressure=True
NetworkUnavailable=True
KubeletNotReady
container runtime is down
container runtime network not ready
```

### Step 3: Check pods on node

```bash
oc get pods -A --field-selector spec.nodeName=<node_name> -o wide
```

### Step 4: Check CRI-O service

If API works:

```bash
oc debug node/<node_name>
chroot /host
systemctl is-active crio
systemctl status crio --no-pager
```

If API does not work and SSH is available:

```bash
ssh core@<node_fqdn>
sudo systemctl is-active crio
sudo systemctl status crio --no-pager
```

### Step 5: Check CRI-O logs

```bash
oc adm node-logs <node_name> -u crio --tail=200
```

Or inside node:

```bash
journalctl -b -u crio.service --no-pager | tail -200
```

### Step 6: Check kubelet logs

```bash
oc adm node-logs <node_name> -u kubelet --tail=200
```

### Step 7: Check disk and inode pressure

Inside node:

```bash
df -h
df -ih
du -sh /var/lib/containers/storage 2>/dev/null
du -sh /var/log/pods /var/log/containers 2>/dev/null
```

### Step 8: Check runtime via `crictl`

```bash
crictl info
crictl ps -a
crictl pods
crictl images
```

### Step 9: Check recent MachineConfig activity

```bash
oc get mcp
oc describe mcp worker
oc get mc | grep -i runtime
oc get containerruntimeconfig
```

### Step 10: Stabilize

```bash
oc adm cordon <node_name>
```

Drain only if safe:

```bash
oc adm drain <node_name> --ignore-daemonsets --delete-emptydir-data
```

## 7. Checking CRI-O Service Health

### Using `oc debug`

```bash
oc debug node/<node_name>
chroot /host
systemctl is-active crio
systemctl status crio.service --no-pager
```

Expected:

```text
active
```

If not active:

```bash
journalctl -b -u crio.service --no-pager | tail -200
```

### Important systemd states

| State | Meaning | Action |
|---|---|---|
| `active (running)` | CRI-O service is running. | Move to kubelet, CNI, storage, image, or pod-specific checks. |
| `failed` | CRI-O crashed or failed startup. | Check journal, config, storage, runtime binary, disk. |
| `inactive` | Service is stopped. | Check why; do not blindly start before collecting logs. |
| `activating` | Startup hanging. | Check storage lock, image store, CNI, slow disk. |
| `auto-restart` loop | Repeated crash. | Check first failure lines in journal. |

### Get exact failure reason

```bash
systemctl status crio -l --no-pager
journalctl -b -u crio.service -o short-precise --no-pager
journalctl -b -u crio.service -p warning..alert --no-pager
```

### Typical failure patterns

#### Bad config

```text
failed to reload config
error parsing crio.conf
unknown field
invalid TOML
```

Check:

```bash
crio config --default >/tmp/default-crio.conf
crio --config /etc/crio/crio.conf --log-level debug
```

In OpenShift, fix configuration through MachineConfig/ContainerRuntimeConfig rather than permanent manual edits.

#### Storage corruption

```text
can't stat lower layer
missing symlinks
error reading name of symlink
failed to mount overlay
```

This points to containers/storage overlay state. Use the storage troubleshooting section. Do not wipe storage before collecting evidence and draining if possible.

#### Disk full

```text
no space left on device
write ... no space left on device
```

Check:

```bash
df -h
df -ih
du -xhd1 /var | sort -h
```

#### OCI runtime issue

```text
executable file not found in $PATH
runc not found
crun not found
container create failed
```

Check:

```bash
which crun runc
rpm -q crun runc cri-o
crio config | egrep 'default_runtime|runtime_path|runtime_type'
```

### Preferred method when API works

```bash
oc adm node-logs <node_name> -u crio
```

For all workers:

```bash
oc adm node-logs --role=worker -u crio
```

For all control plane nodes:

```bash

```

Recent logs:

```bash
oc adm node-logs <node_name> -u crio --since=1h
oc adm node-logs <node_name> -u crio --tail=300
```

### If API is unavailable

```bash
ssh core@<node_fqdn>
sudo journalctl -b -u crio.service --no-pager
sudo journalctl -u crio.service --since "2026-07-03 10:00:00" --no-pager
```

### Useful journal filters

```bash
journalctl -b -u crio.service -p warning..alert --no-pager
journalctl -b -u crio.service | egrep -i 'error|fail|denied|no space|timeout|overlay|runtime|pull|sandbox|cni'
```

### What to look for

| Log phrase | Likely area |
|---|---|
| `Pulling image` | Registry/image pull |
| `Trying to access` | Registry mirror/source selection |
| `unauthorized` | Pull secret/auth |
| `x509` | Registry certificate trust |
| `i/o timeout` | Network/firewall/DNS/proxy |
| `failed to create pod sandbox` | CNI, pause image, runtime, storage |
| `failed to setup network` | CNI/OVN/Multus |
| `failed to mount container` | Overlay/storage/SELinux/volume |
| `no space left on device` | Disk/inode exhaustion |
| `permission denied` | SELinux, file permissions, SCC, volume labels |
| `context deadline exceeded` | Runtime hang, image pull delay, storage/network latency |

## 9. Using `crictl` Like a Senior Admin

`crictl` talks directly to the CRI runtime. It is extremely useful because it bypasses the Kubernetes API and shows what the node runtime knows.

### Confirm endpoint

```bash
cat /etc/crictl.yaml
```

Typical endpoint:

```yaml
runtime-endpoint: unix:///var/run/crio/crio.sock
image-endpoint: unix:///var/run/crio/crio.sock
```

If needed:

```bash
crictl --runtime-endpoint unix:///var/run/crio/crio.sock info
```

### Check runtime health

```bash
crictl info
crictl version
```

If this hangs or fails while `systemctl status crio` says running, suspect:

- CRI-O internal deadlock or heavy I/O wait.
- Runtime socket issue.
- System resource exhaustion.
- Storage backend problem.
- Very high image pull/container churn.

### List pods known to runtime

```bash
crictl pods
crictl pods -a
```

### List containers

```bash
crictl ps
crictl ps -a
```

### Inspect a pod sandbox

```bash
crictl inspectp <pod_id> | jq .
```

Important fields:

```bash
crictl inspectp <pod_id> | jq '.status.metadata,.status.state,.status.network,.status.linux.namespaces'
```

### Inspect container

```bash
crictl inspect <container_id> | jq .
```

Look at:

```bash
crictl inspect <container_id> | jq '.status.exitCode,.status.reason,.status.message,.info.runtimeSpec.process,.info.config'
```

### Get container logs

```bash
crictl logs <container_id>
crictl logs --tail=100 <container_id>
```

### Remove stopped containers carefully

```bash
crictl ps -a
crictl rm <container_id>
```

Do not mass-remove production containers unless you understand the effect.

### Pull an image directly

```bash
crictl pull registry.example.com/ns/image:tag
```

This helps separate Kubernetes scheduling/RBAC issues from node runtime/registry issues.

## 10. Pod Sandbox Troubleshooting

A pod sandbox is the runtime-level infrastructure container/environment for a pod. Kubernetes creates a sandbox first, then workload containers inside it.

### Common error

```text
Failed to create pod sandbox: rpc error: code = Unknown desc = ...
```

This is not always a pure CRI-O issue. Sandbox creation touches:

- CRI-O
- CNI plugin
- pause image
- pod network namespace
- SELinux labels
- cgroups
- storage mounts
- DNS/resolv.conf generation
- kubelet pod directory

### Step-by-step

#### 1. Describe pod

```bash
oc describe pod <pod> -n <namespace>
```

#### 2. Check node

```bash
oc get pod <pod> -n <namespace> -o wide
oc describe node <node_name>
```

#### 3. Check kubelet logs

```bash
oc adm node-logs <node_name> -u kubelet --tail=300
```

#### 4. Check CRI-O logs

```bash
oc adm node-logs <node_name> -u crio --tail=300
```

#### 5. Check runtime pods

```bash
oc debug node/<node_name>
chroot /host
crictl pods -a | grep <pod_name>
```

#### 6. Inspect sandbox

```bash
crictl inspectp <pod_id> | jq .
```

### Interpret sandbox errors

| Error | Likely root cause |
|---|---|
| `failed to setup network for sandbox` | CNI/OVN/Multus issue. |
| `failed to find plugin` | CNI plugin file missing or wrong path. |
| `networkPlugin cni failed` | CNI config/plugin/runtime issue. |
| `failed to mount` | Volume/storage/overlay/SELinux. |
| `no space left on device` | Disk or inode exhaustion. |
| `context deadline exceeded` | Timeout in image pull, CNI, runtime, or storage. |
| `x509 certificate signed by unknown authority` | Registry CA trust. |
| `unauthorized` | Pull secret/auth issue. |

### Sandbox issue decision

```text
FailedCreatePodSandbox
        |
        +-- CRI-O service down? → fix crio.service
        |
        +-- CNI error? → troubleshoot OVN/Multus/CNO
        |
        +-- Image pull pause/pod image? → registry/mirror/auth/CA
        |
        +-- Mount/overlay error? → storage/SELinux/volume
        |
        +-- DiskPressure? → cleanup logs/images or add capacity
        |
        +-- Node after upgrade/reboot? → check MCO, crio, storage corruption
```

## 11. Image Pull and Registry Troubleshooting

Image pull errors are frequently reported through CRI-O because CRI-O performs the actual pull.

### Pod events

```bash
oc describe pod <pod> -n <namespace>
```

Look for:

```text
ErrImagePull
ImagePullBackOff
unauthorized: authentication required
manifest unknown
x509: certificate signed by unknown authority
dial tcp: lookup registry... no such host
i/o timeout
connection refused
```

### Runtime logs

```bash
oc adm node-logs <node_name> -u crio | egrep -i 'pull|trying to access|unauthorized|x509|manifest|timeout|registry'
```

In mirrored/disconnected environments, CRI-O logs are especially valuable because they show the actual registry location that CRI-O attempted to access.

### Test from the node

```bash
oc debug node/<node_name>
chroot /host
crictl pull <image>
podman pull <image>
```

### Check pull secret at namespace level

```bash
oc get sa default -n <namespace> -o yaml
oc get secret -n <namespace>
oc describe secret <pull_secret> -n <namespace>
```

### Check global pull secret

```bash
oc get secret/pull-secret -n openshift-config -o yaml
```

Do not print decoded production credentials into shared tickets or chat.

### Check image config resources

Depending on OpenShift version and configuration:

```bash
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
oc get image.config.openshift.io/cluster -o yaml
```

### Check registry trust

Inside node:

```bash
ls -R /etc/pki/ca-trust/source/anchors/ 2>/dev/null
ls -R /etc/containers/certs.d/ 2>/dev/null
update-ca-trust check 2>/dev/null || true
```

On OpenShift, registry CA and mirror configuration should be managed through supported cluster configuration, not random manual node edits.

### Image pull root-cause matrix

| Symptom | Check | Fix direction |
|---|---|---|
| `unauthorized` | Pull secret, service account, registry creds | Fix imagePullSecret/global pull secret. |
| `manifest unknown` | Tag/digest exists? architecture? | Correct image reference/tag/digest. |
| `x509 unknown authority` | Registry CA trust | Add trusted CA through cluster config. |
| `lookup registry no such host` | DNS | Fix DNS/CoreDNS/node resolver/proxy. |
| `connection refused` | Registry service/firewall | Fix registry endpoint/network/firewall. |
| Pull works on one node, fails on another | Node-specific config/certs/proxy | Compare node configs and MCO state. |
| Pull works with podman but not pod | Namespace pull secret/SCC/image policy | Compare credentials and admission policies. |

## 12. CRI-O Storage Troubleshooting

CRI-O uses containers/storage, usually overlay storage, under `/var/lib/containers/storage`.

### Common storage symptoms

```text
can't stat lower layer
failed to mount overlay
error recreating the missing symlinks
open /var/lib/containers/storage/overlay/.../link: no such file or directory
no space left on device
read-only file system
input/output error
```

### Check disk

```bash
df -h
df -ih
lsblk
findmnt /var
findmnt /var/lib/containers/storage
```

### Check storage usage

```bash
du -xhd1 /var/lib/containers 2>/dev/null | sort -h
du -xhd1 /var/lib/containers/storage 2>/dev/null | sort -h
```

### Check overlay mounts

```bash
mount | grep overlay | head
findmnt -t overlay
```

### Check image/container metadata

```bash
crictl images
crictl ps -a
crictl pods -a
```

### Check for filesystem errors

```bash
journalctl -b -k --no-pager | egrep -i 'xfs|ext4|nvme|scsi|blk|i/o error|read-only|filesystem|corrupt'
```

### Storage problem categories

| Category | Description | Action |
|---|---|---|
| Normal capacity pressure | Images/logs/containers consume space. | Prune safely, increase capacity, tune eviction/logging. |
| Inode exhaustion | Many small files/layers/logs. | Clean unused content, review workload churn. |
| Overlay metadata corruption | Missing lower layer/link/symlink errors. | Drain, collect logs, consider `crio wipe -f`. |
| Disk I/O errors | Hardware/cloud volume issue. | Node replacement or storage repair. |
| Read-only filesystem | Kernel remounted due to FS errors. | Reboot may not be enough; inspect disk health. |
| MCO/runtime config changed storage options | Bad `overlaySize` or generated config. | Review ContainerRuntimeConfig/MachineConfig. |

## 13. Filesystem, Inode, and Log Exhaustion

CRI-O failures are often secondary effects of node disk pressure.

### Check node condition

```bash
oc describe node <node_name> | egrep -A5 'DiskPressure|MemoryPressure|PIDPressure|Ready'
```

### Check filesystem usage

```bash
df -h
df -ih
```

### Find large directories

```bash
du -xhd1 /var | sort -h
du -xhd1 /var/log | sort -h
du -xhd1 /var/lib | sort -h
du -xhd1 /var/lib/containers | sort -h
```

### Check pod logs

```bash
du -xhd1 /var/log/pods | sort -h | tail -20
find /var/log/pods -type f -size +100M -ls
```

### Check journald

```bash
journalctl --disk-usage
```

### Emergency cleanup ideas

Use caution. Prefer platform-supported cleanup and workload fixes.

```bash
# Remove old rotated compressed logs if safe and approved
find /var/log -type f -name '*.gz' -mtime +7 -ls

# Inspect, do not blindly delete
find /var/log/pods -type f -size +500M -ls
```

### Why logs matter to CRI-O

Large container logs can fill `/var`, affecting:

- CRI-O metadata writes
- kubelet pod state writes
- image pulls
- overlay mount operations
- journald
- node readiness

### Long-term fixes

- Fix noisy application logging.
- Configure log rotation appropriately.
- Use cluster logging pipeline.
- Ensure node filesystem sizing is realistic.
- Configure eviction thresholds through supported kubelet configuration where appropriate.
- Monitor `/var`, `/var/lib/containers`, inode usage, and journald size.

## 14. Kubelet and CRI-O Interaction

Kubelet and CRI-O failures are tightly coupled. Always check both.

### Kubelet talks to CRI-O

```text
kubelet → CRI socket → CRI-O
```

If CRI-O is down, kubelet often reports:

```text
container runtime is down
PLEG is not healthy
failed to get runtime status
runtime network not ready
```

### Check kubelet

```bash
systemctl status kubelet --no-pager
journalctl -b -u kubelet.service --no-pager | tail -300
```

### Check kubelet runtime messages

```bash
journalctl -b -u kubelet.service --no-pager | egrep -i 'runtime|crio|pleg|sandbox|container|image|network'
```

### Typical kubelet messages

| Kubelet message | Meaning |
|---|---|
| `container runtime is down` | Kubelet cannot talk to CRI-O or runtime status is unhealthy. |
| `PLEG is not healthy` | Pod lifecycle event generator cannot sync runtime state in time. |
| `failed to garbage collect` | Runtime/image/container GC issue. |
| `failed to create pod sandbox` | Kubelet requested sandbox; CRI-O/CNI/storage failed. |
| `NetworkPluginNotReady` | CNI network not ready; not necessarily CRI-O. |

### Restart order

If both services must be restarted, common order:

```bash
systemctl stop kubelet
systemctl restart crio
systemctl start kubelet
```

Do this only after impact assessment. On production nodes, cordon/drain first when possible.

## 16. SELinux, SCC, and Permission-Related Runtime Failures

OpenShift strongly enforces SELinux and security context constraints. Many runtime failures are caused by permission mismatches.

### Symptoms

```text
permission denied
operation not permitted
container create failed
setresgid: invalid argument
cannot set groups
mount denied
SELinux relabel failed
```

### Check pod security context

```bash
oc get pod <pod> -n <namespace> -o yaml | egrep -A20 'securityContext|serviceAccountName|volumes'
```

### Check service account and SCC admission

```bash
oc adm policy who-can use scc anyuid
oc adm policy who-can use scc privileged
oc get pod <pod> -n <namespace> -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
```

### Check events

```bash
oc describe pod <pod> -n <namespace>
```

### Check SELinux denials on node

```bash
journalctl -b --no-pager | egrep -i 'avc|selinux|denied'
ausearch -m avc -ts recent 2>/dev/null
```

### Practical examples

#### Container expects root

Symptoms:

```text
permission denied writing /var/lib/app
```

Fix direction:

- Prefer image that supports arbitrary UID.
- Fix file ownership/permissions in image.
- Use proper SCC only when justified.

Temporary/admission-level fix for a lab or controlled workload:

```bash
oc adm policy add-scc-to-user anyuid -z <service_account> -n <namespace>
```

#### HostPath or local volume permission issue

Check:

```bash
ls -Zd <host_path>
ls -ld <host_path>
```

Fix direction:

- Use supported storage class/PVC.
- Avoid unnecessary hostPath.
- Ensure correct SELinux context and SCC.

## 21. When and How to Wipe CRI-O Storage

This is a serious operation. It clears CRI-O ephemeral container/image storage on the node. It is useful for certain overlay/storage corruption scenarios, but it is not the first troubleshooting step.

### When it may be justified

Consider `crio wipe -f` when you see:

```text
error recreating the missing symlinks
open /var/lib/containers/storage/overlay/.../link: no such file or directory
can't stat lower layer
failed to mount container
runtime storage metadata corruption
node NotReady after reboot/upgrade with CRI-O storage errors
oc debug node fails because CRI-O is broken
```

### Before wiping

1. Confirm issue is node-local.
2. Cordon node.
3. Drain node if possible.
4. Collect logs.
5. Confirm no critical local-only workload data depends on ephemeral container storage.
6. Prefer replacement for cattle-style worker nodes if easier and safer.

### Procedure

```bash
oc adm cordon <node_name>
oc adm drain <node_name> --ignore-daemonsets --delete-emptydir-data
```

SSH or console:

```bash
ssh core@<node_fqdn>
sudo -i
```

Stop kubelet:

```bash
systemctl stop kubelet
```

Remove pods known to CRI-O. First remove non-host-network pods, then all remaining pods:

```bash
for pod in $(crictl pods -q); do
  if [[ "$(crictl inspectp $pod | jq -r .status.linux.namespaces.options.network)" != "NODE" ]]; then
    crictl rmp -f $pod
  fi
done

crictl rmp -fa
```

Stop CRI-O:

```bash
systemctl stop crio
```

Wipe CRI-O ephemeral storage:

```bash
crio wipe -f
```

Start services:

```bash
systemctl start crio
systemctl start kubelet
```

Verify:

```bash
systemctl is-active crio
systemctl is-active kubelet
crictl info
```

From workstation:

```bash
oc get node <node_name>
oc adm uncordon <node_name>
```

### After wipe

Expect images to be pulled again. This can create temporary registry load and slower pod startup.

## 22. Control Plane Node CRI-O Issues

Control plane nodes run static pods for core components such as API server, controller manager, scheduler, and etcd. A CRI-O issue on a control plane node can be more dangerous than on a worker node.

### Check control plane health

```bash
oc get nodes -l node-role.kubernetes.io/master
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-apiserver -o wide
oc get co kube-apiserver etcd kube-controller-manager kube-scheduler
```

### Collect logs

```bash
oc adm node-logs --role=master -u crio
oc adm node-logs --role=master -u kubelet
```

### If API is unstable

SSH to the affected control plane node:

```bash
ssh core@<master_fqdn>
sudo journalctl -b -u crio.service --no-pager
sudo journalctl -b -u kubelet.service --no-pager
sudo crictl ps -a
sudo crictl pods -a
```

### Be careful with drain

Control plane nodes contain critical static pods and often have special scheduling behavior. Do not blindly drain or wipe runtime storage on multiple control plane nodes. Maintain etcd quorum and API availability.

### Senior admin rule

On a three-master cluster, never take down more than one control plane node at a time for runtime repair unless you have a tested recovery plan.

Disconnected clusters add more CRI-O troubleshooting complexity because image references might be rewritten by mirror configuration.

### Common disconnected failures

## 24. Upgrade-Related CRI-O Problems

Runtime problems after upgrade often involve one of these areas:

- MCO rollout incomplete.
- Node reboot failed.
- CRI-O config changed.
- Default runtime changed between `runc` and `crun` depending on version/history.
- Storage metadata corruption after reboot.
- CNI components not ready after node reboot.
- Kernel/runtime mismatch.
- Disk pressure during image repull.

### Check upgrade state

```bash

oc get co
oc get mcp
```

```bash

```

### Check CRI-O runtime

```bash

chroot /host
systemctl status crio --no-pager

crictl info
```

### Check generated MachineConfigs

```bash
oc get mc | egrep -i 'crio|runtime|containerruntime|generated'
```

### Upgrade triage pattern

```text
Upgrade issue
   |
   +-- MCP degraded? → inspect MCO and node config drift
   +-- Node NotReady? → kubelet + crio logs
   +-- CRI-O failed startup? → config/runtime/storage
   +-- Pods stuck ContainerCreating? → CNI/image/storage
   +-- Only image pulls fail? → mirror/registry/CA/pull-secret
```

## 25. Troubleshooting Decision Trees

### A. Node NotReady with runtime error

```text
Node NotReady
   |
   +-- oc describe node says container runtime down?
          |
          +-- systemctl is-active crio = inactive/failed
          |      |
          |      +-- journalctl crio shows config error → fix MCO/ContainerRuntimeConfig
          |      +-- journalctl crio shows storage error → storage troubleshooting
          |      +-- journalctl crio shows no space → cleanup/capacity
          |      +-- journalctl crio shows runtime missing → runtime/MCO/upgrade issue
          |
          +-- crio active but crictl info fails
          |      |
          |      +-- high I/O/load/disk? → resource issue
          |      +-- socket/API hang? → restart after drain
          |
          +-- crio active and crictl OK
                 |
                 +-- kubelet problem, CNI problem, or node condition issue
```

### B. Pod stuck ContainerCreating

```text
ContainerCreating
   |
   +-- oc describe pod
          |
          +-- Image pull error → registry/auth/CA/DNS/mirror
          +-- FailedCreatePodSandBox + CNI → OVN/Multus/CNI
          +-- FailedMount → storage/PV/secret/configmap/SELinux
          +-- CreateContainerError → command/user/security/runtime
          +-- no events → check kubelet and CRI-O logs
```

### C. CRI-O failed to start

```text
crio.service failed
   |
   +-- systemctl status crio
   +-- journalctl -b -u crio
          |
          +-- config parse error → generated config/MCO
          +-- storage error → overlay/storage
          +-- no space → disk/inodes
          +-- runtime binary error → crun/runc config/package
          +-- certificate/registry? → normally affects pulls, not service startup
```

### D. ImagePullBackOff

```text
ImagePullBackOff
   |
   +-- Check pod event message
   +-- crictl pull image on same node
          |
          +-- unauthorized → pull secret
          +-- x509 → CA trust
          +-- DNS no host → DNS/proxy
          +-- timeout → network/firewall/proxy
          +-- manifest unknown → wrong image/tag/digest/mirror missing
          +-- works on node but pod fails → namespace SA pull secret/admission/image policy
```

### E. Overlay corruption

```text
overlay/link/lower layer errors
   |
   +-- Collect logs
   +-- Cordon/drain
   +-- Check disk/inodes/kernel I/O errors
   +-- Restart kubelet/crio if low risk
   +-- If persistent and node-local → crio wipe -f
   +-- If repeated → replace node or investigate storage hardware/cloud volume
```

```bash
tar cvaf /tmp/crio-evidence.tar.gz /tmp/crio-evidence
```

## 28. Best Practices

### Operational best practices

- Monitor CRI-O and kubelet together.
- Monitor disk and inode usage on `/var`.
- Do not manually edit CRI-O configuration permanently on OpenShift nodes.
- Use `ContainerRuntimeConfig` for supported CRI-O parameters.
- Use `MachineConfig` for supported OS-level changes.
- Avoid leaving CRI-O debug logging enabled.
- Cordon and drain before disruptive runtime repair.
- Do not wipe CRI-O storage as a first step.
- Replace broken worker nodes when cheaper than deep repair.
- Keep registry mirror, CA, and pull secret processes documented.
- Validate MCP status after runtime-related changes.
- Keep at least one known-good debug method: `oc debug`, SSH break-glass, console access.

### Security best practices

- Do not expose pull-secret credentials in tickets.
- Avoid assigning privileged/anyuid SCC unless required.
- Prefer images that run with arbitrary UID.
- Keep SELinux enforcing.
- Do not disable security controls to “fix” runtime errors without root-cause analysis.

### Upgrade best practices

- Check `oc get mcp` before and after upgrade.
- Ensure enough free disk before upgrade.
- Watch node reboot and MCP rollout.
- Do not apply unrelated MachineConfigs during cluster upgrade.
- Test image pulls from mirrors before upgrading disconnected clusters.

### Logging best practices

- Centralize application logs.
- Detect noisy pods before they fill `/var/log/pods`.
- Use debug CRI-O logging only temporarily.
- Collect logs before restart/wipe.

## 29. Interview and Exam Style Questions

### Q1. What is CRI-O?

CRI-O is a Kubernetes-native container runtime that implements the CRI interface. Kubelet uses it to pull images, create pod sandboxes, start containers, and manage container lifecycle on each OpenShift node.

### Q2. How do you check CRI-O status on an OpenShift node?

```bash
oc debug node/<node_name>
chroot /host
systemctl is-active crio
systemctl status crio --no-pager
```

Or:

```bash
oc adm node-logs <node_name> -u crio
```

### Q3. A pod is stuck in `ContainerCreating`. Is it always CRI-O?

No. `ContainerCreating` can involve CRI-O, CNI, image pull, volumes, CSI, SELinux, SCC, kubelet, or node resource pressure. Start with `oc describe pod`, then check kubelet and CRI-O logs on the assigned node.

### Q4. What is the difference between kubelet and CRI-O?

Kubelet is the node agent that watches assigned pods and reports status to Kubernetes. CRI-O is the runtime service kubelet calls to perform container operations.

### Q5. How do you collect CRI-O logs from all worker nodes?

```bash
oc adm node-logs --role=worker -u crio
```

### Q6. When do you use `crio wipe -f`?

Use it only after careful evidence collection and node isolation, typically when CRI-O ephemeral storage is corrupted, for example missing overlay lower layers, missing symlinks, or runtime storage errors after reboot/upgrade.

### Q7. How do you change CRI-O log level in OpenShift?

Use a `ContainerRuntimeConfig` custom resource targeting the appropriate MachineConfigPool. Do not manually edit `/etc/crio/crio.conf` as a permanent fix.

### Q8. What do you check for `ImagePullBackOff`?

Check pod events, CRI-O logs, `crictl pull`, registry DNS, firewall/proxy, pull secret, global pull secret, registry CA, mirror configuration, and whether the image tag/digest exists.

### Q9. Why might `oc debug node/<node>` fail during CRI-O troubleshooting?

`oc debug node` creates a debug pod on the target node. If CRI-O cannot create containers or pod sandboxes, the debug pod itself may fail. Use SSH or console access in that case.

### Q10. What is the safest way to repair a problematic worker node?

Cordon, drain, collect logs, verify CRI-O/kubelet/storage/network, apply the minimum fix, verify node readiness, then uncordon.

## Final Senior Admin Summary

CRI-O troubleshooting is not only about restarting `crio.service`. In production OpenShift, CRI-O is connected to kubelet, CNI, container storage, registry configuration, MachineConfig, SELinux, SCCs, cgroups, image mirrors, and node filesystem health.

A strong administrator follows this order:

```text
1. Identify affected node and workload scope.
2. Read pod events.
3. Check node conditions.
4. Check kubelet and CRI-O logs together.
5. Use crictl to inspect runtime state.
6. Check disk, inodes, image pull path, CNI, SELinux, and MCO state.
7. Cordon/drain before disruptive actions.
8. Restart or wipe only when evidence supports it.
9. Verify node Ready and workload recovery.
10. Prevent recurrence through monitoring, configuration control, and capacity planning.
```

If you remember one thing: **CRI-O is where many node problems surface, but not always where they originate.**
