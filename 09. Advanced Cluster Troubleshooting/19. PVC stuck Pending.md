## 1. Executive Summary

A PersistentVolumeClaim stuck in `Pending` means OpenShift cannot bind the claim to a suitable PersistentVolume, or it has intentionally delayed binding because the StorageClass uses topology-aware provisioning such as `WaitForFirstConsumer`.

At senior level, never treat `Pending` as one issue. It is a symptom produced by several different layers:

- PVC spec mismatch
- No default StorageClass
- Wrong `storageClassName`
- StorageClass exists but provisioner is unavailable
- CSI driver is degraded
- Storage backend has no capacity
- ODF / Ceph is unhealthy
- Local PV has node-affinity mismatch
- Quota blocks PVC creation or expansion
- Static PV labels, capacity, access mode, volume mode, or reclaim state mismatch
- `WaitForFirstConsumer` is waiting for a pod
- Scheduler cannot place the pod because of taints, node selectors, affinity, topology, or resource pressure
- Cloud-provider credentials, permissions, region, zone, datastore, or API problems

The first rule:

```bash
oc describe pvc <pvc-name> -n <namespace>
```

The second rule:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

The third rule:

```bash
oc get sc,pv,pvc -A
```

The event message usually tells you which layer is failing.

## 2. What `PVC Pending` Means Internally

A PVC is a namespace-scoped request for storage. It asks for:

- Capacity, for example `10Gi`
- Access mode, for example `ReadWriteOnce` or `ReadWriteMany`
- Volume mode, for example `Filesystem` or `Block`
- Optional StorageClass
- Optional selector
- Optional explicit PV name

A PV is cluster-scoped storage already provisioned by an admin or dynamically created by a storage provisioner.

A PVC remains `Pending` when Kubernetes/OpenShift cannot complete this relationship:

```text
PVC request  --->  matching PV or dynamic provisioner  --->  Bound PV/PVC pair
```

Example:

```bash
oc get pvc -n app
```

Output:

```text
NAME       STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
data-db    Pending                                      thin-csi        12m
```

This says the claim exists, but no PV has been bound yet.

Important distinction:

| State | Meaning |
|---|---|
| `Pending` | PVC has not bound to a PV yet |
| `Bound` | PVC has a PV assigned |
| Pod `Pending` with PVC event | Pod cannot start because PVC is not bound |
| Pod `ContainerCreating` with volume event | PVC may be bound, but volume mount/attach is failing |
| PVC `Terminating` | PVC deletion is blocked, often by finalizer or active pod usage |

## 3. Storage Control Plane Architecture

OpenShift persistent storage has multiple moving parts.

```text
Developer / App Team
        |
        | creates PVC
        v
Kubernetes API Server
        |
        v
PersistentVolume Controller / Binder
        |
        | checks existing PVs or triggers dynamic provisioning
        v
StorageClass
        |
        v
CSI External Provisioner / Storage Operator
        |
        v
Backend Storage
        |
        | creates disk/share/volume
        v
PV object created and bound to PVC
        |
        v
Scheduler places Pod
        |
        v
CSI Attacher / Node Plugin / Kubelet mounts volume
```

For OpenShift troubleshooting, think in five planes:

| Plane | Objects / Components | Common Failure |
|---|---|---|
| API plane | PVC, PV, SC, events | Bad YAML, quota, missing class |
| Controller plane | PV binder, CSI provisioner | Provisioner down or cannot create PV |
| Scheduler plane | Pod, node affinity, topology | `WaitForFirstConsumer`, zone mismatch |
| Storage backend plane | ODF, vSphere, AWS, Azure, NFS, SAN | No capacity, API/auth failure |
| Node plane | kubelet, CSI node plugin, mount tools | Usually appears after PVC is bound, but can affect topology/local storage |

## 4. PVC Binding Lifecycle

### 4.1 Static provisioning

Admin creates PV manually:

```text
Admin creates PV -> User creates PVC -> Binder matches PV -> PVC Bound
```

Static binding depends on matching:

- `storageClassName`
- Capacity
- Access mode
- Volume mode
- Label selector
- `claimRef`
- PV phase
- Node affinity, for local/topology-aware volumes

### 4.2 Dynamic provisioning

Admin creates StorageClass. User creates PVC. Provisioner creates backend volume and PV.

```text
PVC -> StorageClass -> CSI provisioner -> backend volume -> PV -> Bound
```

Dynamic provisioning requires:

- Valid `StorageClass`
- Correct provisioner name
- Running CSI provisioner pods
- Working backend credentials/API
- Backend capacity
- Correct topology settings
- Sufficient namespace quota

### 4.3 Delayed binding

With `volumeBindingMode: WaitForFirstConsumer`, PVC may remain `Pending` until a pod references it.

This is normal when the event says:

```text
waiting for first consumer to be created before binding
```

or:

```text
WaitForFirstConsumer
```

The provisioner waits because it needs pod scheduling context: zone, node labels, node selectors, taints, affinity, topology, and resources.

## 5. Fast Triage Workflow

Use this sequence in real incidents.

### Step 1: Confirm PVC state

```bash
NS=<namespace>
PVC=<pvc-name>

oc get pvc $PVC -n $NS -o wide
oc describe pvc $PVC -n $NS
```

Look at:

- `Status`
- `StorageClass`
- `Volume`
- `Events`
- `Selector`
- `VolumeMode`
- Requested size
- Access modes

### Step 2: Check namespace events

```bash
oc get events -n $NS --sort-by=.lastTimestamp
```

Filter storage messages:

```bash
oc get events -n $NS --sort-by=.lastTimestamp | egrep -i 'pvc|volume|provision|storage|quota|binding|failed|waiting'
```

### Step 3: Check StorageClass

```bash
oc get sc
oc describe sc <storageclass-name>
```

Look at:

- Default annotation
- Provisioner
- `volumeBindingMode`
- Reclaim policy
- Allow volume expansion
- Parameters
- Allowed topologies

### Step 4: Check matching PVs

```bash
oc get pv
oc get pv -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,CAP:.spec.capacity.storage,ACCESS:.spec.accessModes,MODE:.spec.volumeMode,SC:.spec.storageClassName,CLAIM:.spec.claimRef.name
```

### Step 5: Check CSI / storage operator

```bash
oc get co | egrep -i 'storage|csi|odf|image|machine|cloud'
oc get pods -A | egrep -i 'csi|provisioner|attacher|snapshot|rook|ceph|odf|lvms|local-storage|topolvm'
```

### Step 6: Check pod consumer

If StorageClass uses `WaitForFirstConsumer`:

```bash
oc get pod -n $NS -o wide
oc describe pod <pod-name> -n $NS
```

Look for pod scheduling errors:

- No nodes available
- Node selector mismatch
- Taints not tolerated
- Insufficient CPU/memory
- Volume node affinity conflict
- Topology spread issues

## 7. Decision Tree

```text
PVC Pending
 |
 +-- oc describe pvc shows "waiting for first consumer"?
 |      |
 |      +-- Yes: Check pod exists and can schedule.
 |      |        Check nodeSelector, taints, affinity, topology, resources.
 |      |
 |      +-- No: Continue.
 |
 +-- PVC has storageClassName?
 |      |
 |      +-- No: Is there a default StorageClass?
 |      |        If no default, set one or specify storageClassName.
 |      |
 |      +-- Yes: Does StorageClass exist?
 |               If not, fix PVC/SC name.
 |
 +-- Static PV expected?
 |      |
 |      +-- Yes: Check matching PV: Available, capacity >= request,
 |      |        access mode, volumeMode, storageClassName, labels, claimRef.
 |      |
 |      +-- No: Dynamic provisioning expected.
 |
 +-- Dynamic provisioning expected?
 |      |
 |      +-- Check StorageClass provisioner name.
 |      +-- Check CSI provisioner pods.
 |      +-- Check storage operator health.
 |      +-- Check backend capacity/auth/API.
 |
 +-- Events show quota exceeded?
 |      |
 |      +-- Increase quota or reduce PVC size/count.
 |
 +-- ODF/CSI/local/cloud backend degraded?
        |
        +-- Fix backend/operator first, then recreate or wait for provisioning.
```

## 8. Common Root Causes and Fixes

## 8.1 No default StorageClass

### Symptom

```text
no persistent volumes available for this claim and no storage class is set
```

or PVC shows:

```text
STORAGECLASS: <none>
```

### Diagnosis

```bash
oc get sc
```

Check default annotation:

```bash
oc get sc -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.annotations.storageclass\.kubernetes\.io/is-default-class}{"\n"}{end}'
```

### Fix option 1: Specify StorageClass in PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  namespace: app
spec:
  storageClassName: thin-csi
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

### Fix option 2: Mark a default StorageClass

```bash
oc annotate storageclass thin-csi storageclass.kubernetes.io/is-default-class="true" --overwrite
```

### Senior note

Changing the default StorageClass affects future PVC behavior and can affect existing PVCs without `storageClassName`, depending on Kubernetes defaulting behavior. Do not change defaults casually in shared clusters.

---

## 8.2 Wrong `storageClassName`

### Symptom

```text
storageclass.storage.k8s.io "fast-storage" not found
```

### Diagnosis

```bash
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.storageClassName}{"\n"}'
oc get sc
```

### Fix

PVC `storageClassName` is generally immutable after creation. Usually you must recreate the PVC.

If no data exists yet:

```bash
oc delete pvc <pvc> -n <ns>
oc apply -f corrected-pvc.yaml
```

If data already exists, plan migration carefully. Do not delete a bound production PVC without backup and owner approval.

---

## 8.3 StorageClass exists but provisioner is wrong

### Symptom

PVC keeps Pending. Events show repeated provisioning failures or no provisioning activity.

### Diagnosis

```bash
oc describe sc <sc>
```

Look at:

```yaml
provisioner: example.com/wrong-driver
```

Check installed CSI drivers:

```bash
oc get csidriver
```

### Fix

Create or use a correct StorageClass with a provisioner matching the installed CSI driver.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: correct-csi
provisioner: csi.example.com
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```

---

## 8.4 No matching static PV

### Symptom

```text
no persistent volumes available for this claim and no storage class is set
```

or:

```text
no volume plugin matched
```

### Diagnosis

```bash
oc get pv
oc describe pvc <pvc> -n <ns>
```

Compare PVC and PV:

| Field | PVC | PV | Must Match? |
|---|---|---|---|
| `storageClassName` | yes | yes | yes |
| Capacity | request | capacity | PV must be >= request |
| Access mode | requested | supported | compatible |
| Volume mode | Filesystem/Block | Filesystem/Block | yes |
| Selector labels | optional | labels | if selector used |
| PV phase | - | Available | yes |
| ClaimRef | - | should not block | yes |

### Fix

Create a matching PV or correct the PVC.

## 8.5 PV is `Released`, not `Available`

### Symptom

```bash
oc get pv
```

```text
NAME      CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM
pv001     10Gi       RWO            Retain           Released   oldns/oldclaim
```

### Meaning

The old PVC was deleted, but the PV still contains old claim reference/data and is not available for automatic reuse.

### Fix approach

Production-safe method:

1. Confirm data retention requirement.
2. Backup or validate data.
3. Remove or recreate PV according to policy.
4. Rebind intentionally.

Example for lab/non-production static PV reuse:

```bash
oc patch pv pv001 --type=json -p='[{"op":"remove","path":"/spec/claimRef"}]'
```

Be careful: removing `claimRef` can expose old data to a new claim. In production, treat this as data-governance sensitive.

## 8.6 PVC requests bigger storage than any PV

### Symptom

PVC requests `100Gi`, available PVs are `50Gi`.

### Diagnosis

```bash
oc get pvc <pvc> -n <ns> -o yaml | grep -A5 requests
oc get pv
```

### Fix

Options:

- Create a bigger PV.
- Reduce PVC request if allowed and no data exists.
- Use a dynamic StorageClass that can provision required size.
- Increase backend quota/capacity.

PVC requested storage cannot normally be reduced after creation. Recreate it if no data exists.

## 8.7 Access mode mismatch

### Symptom

PVC requests RWX but only RWO PVs/storage exist.

### Diagnosis

```bash
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.accessModes}{"\n"}'
oc get pv -o custom-columns=NAME:.metadata.name,ACCESS:.spec.accessModes,SC:.spec.storageClassName,STATUS:.status.phase
```

### Fix

Use storage that supports requested access mode.

| Access Mode | Typical Backend |
|---|---|
| RWO | EBS, Azure Disk, vSphere disk, RBD/block |
| RWX | NFS, CephFS, Azure File, EFS, Manila, some NAS/CSI drivers |
| ROX | Shared read-only storage |
| RWOP | Single pod writer, CSI-supported environments |

Do not request RWX on block-only storage unless the CSI driver supports it.

## 8.8 Volume mode mismatch

### Symptom

PVC requests `Block`, PV is `Filesystem`, or reverse.

### Diagnosis

```bash
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.volumeMode}{"\n"}'
oc get pv <pv> -o jsonpath='{.spec.volumeMode}{"\n"}'
```

### Fix

Create a PV or StorageClass that supports the required `volumeMode`.

Example Filesystem PVC:

```yaml
volumeMode: Filesystem
```

Example raw Block PVC:

```yaml
volumeMode: Block
```

## 8.9 PVC selector prevents binding

### Symptom

PVC uses selector, but no PV labels match.

### Diagnosis

```bash
oc get pvc <pvc> -n <ns> -o yaml
oc get pv --show-labels
```

Example problematic PVC:

```yaml
selector:
  matchLabels:
    env: prod
    tier: gold
```

No PV has both labels.

### Fix

Either label the correct PV:

```bash
oc label pv pv001 env=prod tier=gold
```

or recreate the PVC without the restrictive selector.

Senior warning: label selectors on PVCs are powerful but often unnecessary with dynamic provisioning. A selector can disable normal dynamic behavior depending on use case and provisioner behavior.

## 8.10 Namespace quota exceeded

### Symptom

Events may show:

```text
exceeded quota
```

or PVC creation/provisioning is blocked by storage quota.

### Diagnosis

```bash
oc describe quota -n <ns>
oc get resourcequota -n <ns> -o yaml
```

Look for:

```yaml
requests.storage
persistentvolumeclaims
<storageclass>.storageclass.storage.k8s.io/requests.storage
<storageclass>.storageclass.storage.k8s.io/persistentvolumeclaims
```

### Fix

Options:

- Delete unused PVCs.
- Reduce requested size.
- Increase quota.
- Use a different namespace/project with proper quota.
- Use appropriate StorageClass-specific quota.

Example quota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: storage-quota
  namespace: app
spec:
  hard:
    requests.storage: 100Gi
    persistentvolumeclaims: "10"
```

## 8.11 `WaitForFirstConsumer` without a pod

### Symptom

```text
waiting for first consumer to be created before binding
```

PVC remains Pending, but no error.

### Diagnosis

```bash
oc describe pvc <pvc> -n <ns>
oc get pods -n <ns>
```

### Fix

Create a pod/deployment/statefulset that uses the PVC.

Example test pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pvc-consumer
  namespace: app
spec:
  containers:
    - name: test
      image: registry.access.redhat.com/ubi9/ubi
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: app-data
```

## 8.12 `WaitForFirstConsumer` with unschedulable pod

### Symptom

PVC pending and pod pending.

Pod events show:

```text
0/6 nodes are available
node(s) didn't match Pod's node affinity/selector
node(s) had untolerated taint
volume node affinity conflict
```

### Diagnosis

```bash
oc describe pod <pod> -n <ns>
oc get nodes --show-labels
oc get sc <sc> -o yaml
```

### Fix

Fix the scheduling problem first:

- Remove wrong `nodeSelector`.
- Add correct toleration.
- Fix affinity rules.
- Add capacity in the required zone.
- Correct StorageClass allowed topology.
- Avoid `nodeName` with `WaitForFirstConsumer`.

### Symptom

Events:


For ODF:

For cloud/vSphere:

- Check cloud quota.

### Fix

- Add storage capacity.
- Expand backend pool.
- Clean unused volumes safely.
- Fix quota.

## 8.14 CSI provisioner pods down

### Symptom

PVC events show external provisioner waiting or timing out.

Examples:

```text
waiting for a volume to be created, either by external provisioner ...
failed to provision volume with StorageClass ...
```

### Diagnosis

```bash
oc get pods -A | egrep -i 'csi|provisioner|attacher|resizer'
oc get co | egrep -i 'storage|csi|cloud'
oc get events -A --sort-by=.lastTimestamp | egrep -i 'csi|provision|volume'
```

Check provisioner logs:

```bash
oc logs -n <csi-namespace> deploy/<csi-controller-deployment> -c csi-provisioner
```

Container names vary by driver. Use:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.containers[*].name}{"\n"}'
```

### Fix

- Restore CSI operator.
- Fix image pull/registry issue.
- Fix secret/credentials.
- Fix node placement of CSI pods.
- Resolve backend API/auth error.
- Restart degraded controller only when root cause is understood.

### Symptom

Events/logs:

```text
UnauthorizedOperation
AccessDenied
Forbidden
failed to create volume
```

### Diagnosis

```bash
oc get co authentication cloud-controller-manager storage
oc get secret -A | egrep -i 'cloud|credential|csi|aws|azure|gcp|vsphere'
```

### Fix

- Restore cloud credentials.
- Check OpenShift cloud credential operator.

- Validate cloud API reachability from cluster.
- Confirm region, zone, resource group, subscription, project, or datastore.

## 8.16 Local PV node affinity mismatch

### Symptom

PVC may bind or stay pending depending on setup; pod often shows:

```text
volume node affinity conflict
```

or PVC waits because no local PV matches pod topology.

### Diagnosis

```bash
oc get pv <pv> -o yaml | grep -A20 nodeAffinity
oc get pod <pod> -n <ns> -o yaml | egrep -A10 'nodeSelector|affinity|tolerations'
oc get nodes --show-labels
```

### Fix

- Schedule pod to node where local PV exists.
- Correct node labels.
- Correct PV node affinity.
- Create local PV on the right node.
- Do not expect local PV to move across nodes.

## 8.17 Multiple default StorageClasses

### Symptom

PVC uses an unexpected class.

### Diagnosis

```bash
oc get sc -o custom-columns=NAME:.metadata.name,DEFAULT:.metadata.annotations.storageclass\.kubernetes\.io/is-default-class,AGE:.metadata.creationTimestamp
```

### Fix

Keep only one default unless intentionally migrating.

```bash
oc annotate storageclass old-sc storageclass.kubernetes.io/is-default-class="false" --overwrite
oc annotate storageclass new-sc storageclass.kubernetes.io/is-default-class="true" --overwrite
```

## 8.18 PVC explicitly uses `storageClassName: ""`

### Symptom

PVC does not use default StorageClass even though one exists.

### Meaning

This explicitly disables dynamic provisioning for that PVC and expects a matching static PV with empty class.

### Diagnosis

```bash
oc get pvc <pvc> -n <ns> -o yaml | grep storageClassName
```

### Fix

If dynamic provisioning is desired, recreate PVC with correct class or omit `storageClassName`.

## 9. Dynamic Provisioning Troubleshooting

Dynamic provisioning should be simple:

```text
PVC -> StorageClass -> Provisioner -> Backend volume -> PV -> Bound
```

When it fails, isolate each segment.

### 9.1 Verify PVC points to StorageClass

```bash
oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.storageClassName}{"\n"}'
oc get sc <sc>
```

### 9.2 Verify StorageClass provisioner

```bash
oc get sc <sc> -o yaml
```

Look for:

```yaml
provisioner: ebs.csi.aws.com
```

or:

```yaml
provisioner: openshift-storage.rbd.csi.ceph.com
```

or:

```yaml
provisioner: csi.vsphere.vmware.com
```

### 9.3 Verify CSI driver exists

```bash
oc get csidriver
```

## 10. Static PV Troubleshooting

Static PV troubleshooting is matching logic.

### 10.1 PV must be `Available`

```bash
oc get pv
```

Valid:

```text
pv001   10Gi   RWO   Retain   Available
```

Invalid for new binding:

```text
pv001   10Gi   RWO   Retain   Bound
pv002   10Gi   RWO   Retain   Released
pv003   10Gi   RWO   Retain   Failed
```

### 10.2 Capacity must be enough

PV can be larger than PVC request, but not smaller.

PVC:

```yaml
resources:
  requests:
    storage: 20Gi
```

PV must be `20Gi` or larger.

### 10.3 Access mode must match

PVC:

```yaml
accessModes:
  - ReadWriteMany
```

PV must include `ReadWriteMany`.

### 10.4 StorageClass must match exactly

Static PV with empty class:

```yaml
spec:
  storageClassName: ""
```

PVC must also use:

```yaml
spec:
  storageClassName: ""
```

If PV has:

```yaml
storageClassName: nfs-static
```

PVC must request:

```yaml
storageClassName: nfs-static
```

### 10.5 Selector must match labels

PVC:

```yaml
selector:
  matchLabels:
    app: db
```

PV:

```yaml
metadata:
  labels:
    app: db
```

### 10.6 `claimRef` can reserve or block

PV can be pre-bound:

```yaml
claimRef:
  namespace: app
  name: data
```

If `claimRef` points to another namespace/name, the claim will not bind.

## 11. `WaitForFirstConsumer` Deep Dive

### 11.1 Why it exists

Some storage is topology-sensitive. A disk created in one zone may only attach to nodes in that zone. Local volumes exist on one node only. vSphere datastores may map to specific failure domains. Cloud block volumes are usually zonal.

If a volume is provisioned immediately before the pod is scheduled, the volume could be created in a zone where the pod cannot run.

`WaitForFirstConsumer` delays volume creation until the scheduler knows where the pod can run.

### 11.2 Normal event

```text
Normal  WaitForFirstConsumer  persistentvolume-controller  waiting for first consumer to be created before binding
```

This is not a failure by itself.

### 11.3 Common failure with `nodeName`

Bad pod spec:

```yaml
spec:
  nodeName: worker-1
```

Why bad?

- `nodeName` bypasses normal scheduler processing.
- The scheduler cannot participate in volume binding.
- PVC can remain `Pending`.

Better:

```yaml
spec:
  nodeSelector:
    kubernetes.io/hostname: worker-1
```

### 11.4 Troubleshooting workflow

```bash
oc get sc <sc> -o yaml | grep volumeBindingMode
oc describe pvc <pvc> -n <ns>
oc get pod -n <ns> -o wide
oc describe pod <pod> -n <ns>
oc get nodes --show-labels
```

### 11.5 Fix patterns

| Problem | Fix |
|---|---|
| No pod uses PVC | Create workload that references PVC |
| Pod has `nodeName` | Replace with `nodeSelector` or affinity |
| Pod nodeSelector impossible | Correct labels or selector |
| Untolerated taint | Add toleration or use different nodes |
| No capacity in zone | Add backend capacity/nodes in same zone |
| StorageClass topology too narrow | Correct `allowedTopologies` |

## 12. StorageClass Troubleshooting

### 12.1 Inspect StorageClass

```bash
oc describe sc <sc>
oc get sc <sc> -o yaml
```

Key fields:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: <driver-name>
parameters: {}
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
allowedTopologies: []
```

### 12.2 Important fields

| Field | Why it matters |
|---|---|
| `provisioner` | Must match installed storage driver |
| `parameters` | Backend-specific; wrong values break provisioning |
| `reclaimPolicy` | Controls backend cleanup after PVC deletion |
| `volumeBindingMode` | Immediate vs delayed/topology-aware binding |
| `allowVolumeExpansion` | Required for PVC resize |
| `mountOptions` | Bad options can break provisioning or mount |
| `allowedTopologies` | Restricts volume creation to zones/nodes |

### 12.3 Default class pitfalls

No default:

```text
PVC without storageClassName will not dynamically provision.
```

Multiple defaults:

```text
PVC may use a newer default class unexpectedly.
```

Explicit empty class:

```yaml
storageClassName: ""
```

means:

```text
Do not use default dynamic provisioning.
```

## 19. Scheduler and Topology Problems

PVC Pending can be coupled with pod scheduling.

### 19.1 Pod scheduling errors

```bash

```

Common messages:


### 19.2 Immediate binding problem

With `Immediate`, PV may be created before pod placement. For zonal storage, this can create PV in zone A while pod constraints require zone B.

Fix:

- Use `WaitForFirstConsumer` for topology-constrained storage.
- Correct pod affinity/node selectors.
- Ensure nodes exist in storage topology.

## Scenario 1: PVC Pending because no default StorageClass

### Situation

Developer creates:

```yaml

  name: data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```

PVC is Pending.

### Triage

```bash
oc describe pvc data -n app
oc get sc
```

No default class.

### Fix

Either recreate PVC with class:

```yaml
storageClassName: thin-csi
```

or mark a default class:

```bash
oc annotate sc thin-csi storageclass.kubernetes.io/is-default-class="true" --overwrite
```

## Scenario 2: PVC Pending due to `WaitForFirstConsumer`

### Situation


```text
waiting for first consumer to be created before binding
```


### Fix

Deploy the workload or a test pod using the PVC. The PVC should bind after pod scheduling.

## Scenario 3: PVC Pending because pod uses `nodeName`

### Situation

StorageClass:

```yaml

```

```yaml

```

### Root cause

The scheduler is bypassed, so topology-aware volume binding cannot happen properly.

### Fix

Replace `nodeName` with:

```yaml
nodeSelector:
  kubernetes.io/hostname: worker01
```

or use node affinity.


### PVC

```yaml

```

### Result

No binding.

### Fix

Recreate PVC with:


## 23. Production-Safe Remediation Checklist

Before changing storage resources:

- Identify whether PVC is new or contains production data.
- Check if PVC is bound or still unbound.
- Check reclaim policy of any related PV.
- Confirm whether deleting PVC deletes backend volume.
- Check owner/application team approval.
- Check backup/snapshot status.
- Avoid deleting PV/PVC blindly.
- Avoid removing finalizers unless you understand the consequence.
- Avoid patching `claimRef` on production PV without data ownership approval.
- Document events and logs before remediation.

### Safe first actions

```bash
oc describe pvc <pvc> -n <ns>
oc get pvc <pvc> -n <ns> -o yaml > pvc-before.yaml
oc get events -n <ns> --sort-by=.lastTimestamp > events-before.txt
oc get sc -o yaml > storageclasses-before.yaml
oc get pv -o yaml > pvs-before.yaml
```

### Dangerous actions

| Action | Risk |
|---|---|
| `oc delete pvc` | May delete backend data if reclaim policy is Delete |
| `oc delete pv` | May delete or orphan backend volume |
| Removing finalizers | Can cause leaked resources or data loss |
| Patching `claimRef` | Can expose old data to another workload |
| Changing default StorageClass | Can affect many workloads |
| Editing StorageClass parameters | Existing PVs not changed, future provisioning affected |

## 25. Interview / Exam Notes

### 25.1 One-line answer

A PVC stuck in Pending means Kubernetes/OpenShift has not bound the claim to a PV. The reason is found in `oc describe pvc`, and common causes are missing/wrong StorageClass, no matching PV, delayed `WaitForFirstConsumer`, quota, CSI/provisioner failure, backend capacity, or topology/scheduling mismatch.

### 25.2 Commands to remember

```bash
oc describe pvc <pvc> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get sc
oc describe sc <sc>
oc get pv
oc get pods -A | grep -i csi
oc get quota -n <ns>
oc describe pod <pod> -n <ns>
```

### 25.3 Exam-style static PV checklist

For a PVC to bind to a static PV:

- PV must be `Available`.
- PV capacity must be greater than or equal to PVC request.
- Access mode must match.
- Volume mode must match.
- StorageClass must match exactly.
- Selector labels must match if used.
- `claimRef` must not point elsewhere.

### 25.4 Exam-style dynamic PVC checklist

For dynamic provisioning:

- PVC must reference an existing StorageClass or use a default one.
- StorageClass must have correct provisioner.
- CSI/operator must be healthy.
- Backend must have capacity and credentials.
- If `WaitForFirstConsumer`, a schedulable pod must consume the PVC.

### 25.5 Senior admin mindset

Do not ask first, "Why is PVC Pending?" Ask:

1. Is this static or dynamic provisioning?
2. If dynamic, which StorageClass and provisioner?
3. If static, which PV should match?
4. Is binding immediate or delayed?
5. Is the pod schedulable?
6. Are quota/admission policies blocking it?
7. Is the backend healthy?
8. Is there any risk of deleting data during remediation?

## Final Practical Summary

When PVC is stuck in Pending, follow this exact order:

```bash
oc describe pvc <pvc> -n <ns>
oc get events -n <ns> --sort-by=.lastTimestamp
oc get sc
oc describe sc <sc>
oc get pv
oc describe pod <consumer-pod> -n <ns>
oc get quota -n <ns>
oc get pods -A | egrep -i 'csi|odf|rook|ceph|lvms|topolvm|local-storage'
```

Most cases are solved by correctly identifying one of these patterns:

- No default or wrong StorageClass
- Static PV mismatch
- `WaitForFirstConsumer` waiting for a schedulable pod
- Quota exceeded
- CSI provisioner/backend failure
- ODF/Ceph capacity or health problem
- Topology/node-affinity mismatch

Always read events first. Events are the fastest path from symptom to root cause.
