## 1. Executive Summary

The **kubelet** is the node-level Kubernetes agent. In OpenShift, it is not just a background service; it is the component that makes a node useful to the cluster. If the kubelet is unhealthy, the node might become `NotReady`, pods might stop starting, logs and exec might fail, volumes might not mount, static control plane pods might not run, and the Machine Config Operator might be unable to complete updates.

In a production OpenShift cluster, kubelet troubleshooting is rarely isolated. A kubelet symptom can be caused by:

- API server reachability problems
- Expired or pending kubelet certificates
- CRI-O failures
- CNI / OVN-Kubernetes failures
- CSI mount failures
- Disk, memory, PID, or inode pressure
- MachineConfig or KubeletConfig mistakes
- DNS or node network failure
- Time drift
- RHCOS/systemd problems
- Broken image registry pull flow
- Control plane static pod problems

A senior OpenShift administrator must therefore troubleshoot kubelet by following the dependency chain:

```text
Node OS / systemd / RHCOS
        ↓
Network, DNS, time, certificates
        ↓
CRI-O + CNI + CSI
        ↓
Kubelet service
        ↓
API server registration and heartbeats
        ↓
Node Ready condition
        ↓
Pod scheduling, startup, probes, mounts, logs, exec
```

## 2. What the Kubelet Does in OpenShift

The kubelet runs on every OpenShift node and is responsible for making the node match the desired state defined by Kubernetes and OpenShift APIs.

Core responsibilities:

1. **Node registration and heartbeat**
   - Registers the node with the Kubernetes API.
   - Updates node status.
   - Maintains node lease heartbeats.
   - Reports conditions such as `Ready`, `MemoryPressure`, `DiskPressure`, and `PIDPressure`.

2. **Pod lifecycle management**
   - Watches pods assigned to the node.
   - Creates pod sandboxes through CRI-O.
   - Starts, stops, and restarts containers.
   - Runs liveness, readiness, and startup probes.

3. **Runtime integration**
   - Talks to CRI-O through the Container Runtime Interface.
   - Delegates image pull and container start operations.

4. **Networking integration**
   - Calls CNI plugins indirectly through CRI-O / network stack.
   - Depends on OVN-Kubernetes components for pod networking in default OCP deployments.

5. **Storage integration**
   - Coordinates pod volume setup.
   - Talks to CSI node plugins through kubelet volume manager.
   - Mounts projected, secret, config map, emptyDir, PVC, and CSI-backed volumes.

6. **Resource enforcement**
   - Applies pod cgroups.
   - Enforces CPU, memory, ephemeral storage, and PID constraints.
   - Evicts pods during resource pressure.

7. **Static pod management**
   - On control plane nodes, starts static pods such as API server, controller manager, scheduler, and etcd-related components depending on OpenShift architecture.

8. **Node local reporting**
   - Provides pod logs, exec, port-forward, attach, and metrics paths used by the API server and cluster tools.

## 3. OpenShift-Specific Kubelet Architecture

OpenShift differs from a manually installed Kubernetes cluster in several important ways.

### 3.1 RHCOS and Immutable Node Management

Most OpenShift 4 nodes run **Red Hat Enterprise Linux CoreOS (RHCOS)**. Administrators should not casually edit kubelet files directly on the host. In production, kubelet and host-level configuration should be managed declaratively using OpenShift APIs and Operators.

OpenShift uses the **Machine Config Operator (MCO)** to manage systemd, CRI-O, kubelet, kernel, NetworkManager, and other node-level configuration through `MachineConfig`, `KubeletConfig`, and `ContainerRuntimeConfig` resources.

### 3.2 KubeletConfig Custom Resource

OpenShift provides a `KubeletConfig` API under:

```text
machineconfiguration.openshift.io/v1
```

A `KubeletConfig` selects a `MachineConfigPool` and produces rendered machine configs. This can trigger node drain and reboot behavior depending on the change.

Example structure:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: custom-worker-kubelet
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    maxPods: 250
    evictionHard:
      memory.available: "500Mi"
      nodefs.available: "10%"
      imagefs.available: "15%"
```

Important senior-admin point:

> Do not apply random upstream kubelet parameters without checking the OpenShift release and Kubernetes version. Invalid kubelet config can make nodes fail to start kubelet or become unusable.

### 3.3 Kubelet Dependency Map

```text
kubelet.service
 ├── systemd
 ├── node network
 │   ├── default route
 │   ├── DNS
 │   ├── API VIP / load balancer
 │   └── proxy / firewall / MTU
 ├── certificates / kubeconfig
 ├── CRI-O socket
 │   └── /var/run/crio/crio.sock or runtime endpoint from service args
 ├── CNI plugins
 │   └── OVN-Kubernetes node components
 ├── CSI plugins
 │   └── /var/lib/kubelet/plugins, plugin registration
 ├── local filesystems
 │   ├── /var/lib/kubelet
 │   ├── /var/lib/containers
 │   ├── /run
 │   └── /var/log
 └── API server
     ├── node status
     ├── pod watch
     ├── secrets/configmaps/projected volumes
     └── events
```

## 4. Common Kubelet Failure Symptoms

You usually notice kubelet trouble through cluster symptoms before you see the kubelet error itself.

### 4.1 Node Symptoms

```bash
oc get nodes
```

Common outputs:

```text
NAME                    STATUS                        ROLES    AGE   VERSION
worker-1.example.com    NotReady                      worker   45d   v1.xx.x
worker-2.example.com    Ready,SchedulingDisabled      worker   45d   v1.xx.x
master-1.example.com    NotReady                      master   45d   v1.xx.x
worker-3.example.com    Ready                         worker   45d   v1.xx.x
```

Problem statuses:

- `NotReady`
- `Unknown`
- `Ready,SchedulingDisabled`
- `DiskPressure`
- `MemoryPressure`
- `PIDPressure`
- frequent node flapping between `Ready` and `NotReady`

### 4.2 Pod Symptoms

```bash
oc get pods -A -o wide | grep <node-name>
oc describe pod <pod> -n <namespace>
```

Common pod states:

- `ContainerCreating`
- `Init:CrashLoopBackOff`
- `CrashLoopBackOff`
- `ImagePullBackOff`
- `ErrImagePull`
- `CreateContainerError`
- `RunContainerError`
- `Terminating` stuck
- `Unknown`
- Pods stuck on a node after node failure

### 4.3 CLI Symptoms

```bash
oc logs <pod>
oc rsh <pod>
oc exec <pod> -- date
oc port-forward <pod> 8080:8080
```

Possible errors:

```text
Error from server: Get "https://<node>:10250/containerLogs/...": dial tcp <node>:10250: connect: connection refused
```

```text
Error from server: error dialing backend: remote error: tls: internal error
```

```text
unable to upgrade connection: pod does not exist
```

```text
container not found
```

These operations often depend on the API server contacting the kubelet endpoint on the node.

### 4.4 Machine Config Symptoms

```bash
oc get mcp
oc describe mcp worker
oc get machineconfigpool worker -o yaml
```

Problem states:

- `UPDATING=True` for too long
- `DEGRADED=True`
- Nodes stuck in `SchedulingDisabled`
- Machine Config Daemon logs showing drift or failure
- rendered config applied but kubelet never stabilizes

## 5. First 10-Minute Triage

Use this when production is down and you need fast signal.

### 5.1 Check Cluster Operators

```bash
oc get co
oc get clusterversion
```

Focus on:

- `kube-apiserver`
- `authentication`
- `machine-config`
- `network`
- `dns`
- `monitoring`
- `storage` operators

### 5.2 Check Nodes

```bash
oc get nodes -o wide
oc describe node <node-name>
```

Look at:

- Conditions
- Taints
- Events
- Capacity and allocatable
- Pod list on the node
- Kubelet version
- Container runtime version
- Internal IP

### 5.3 Check Recent Node Events

```bash
oc get events -A --sort-by=.lastTimestamp | tail -100
```

or:

```bash
oc describe node <node-name> | sed -n '/Events:/,$p'
```

### 5.4 Check Kubelet Logs from Cluster

```bash
oc adm node-logs <node-name> -u kubelet --tail=200
```

Role-wide:

```bash
oc adm node-logs --role=master -u kubelet --tail=100
oc adm node-logs --role=worker -u kubelet --tail=100
```

### 5.5 Enter Node Debug Session

```bash
oc debug node/<node-name>
chroot /host
systemctl status kubelet --no-pager
journalctl -b -u kubelet --no-pager | tail -200
journalctl -b -u crio --no-pager | tail -200
```

### 5.6 Decide the Failure Domain

Ask:

1. Is the kubelet process running?
2. Can kubelet reach the API server?
3. Can the API server reach the kubelet endpoint?
4. Is CRI-O healthy?
5. Is CNI ready?
6. Is storage mounting?
7. Is the node under resource pressure?
8. Did MCO recently apply a config?
9. Did certs rotate or expire?
10. Is only one node impacted or many?

## 6. Golden Troubleshooting Workflow

Follow this order to avoid wasting time.

### Step 1 — Identify Scope

```bash
oc get nodes
oc get pods -A -o wide | grep -E 'Pending|ContainerCreating|Unknown|CrashLoopBackOff|ImagePullBackOff'
oc get co
```

Classify:

| Scope | Meaning |
|---|---|
| One worker node | Usually local kubelet, CRI-O, disk, network, cert, or MCD issue |
| All workers | Possible MCO rollout, cluster network, registry, API, DNS, or configuration issue |
| All masters/control-plane | Critical: static pod, etcd, API server, cert, or host issue |
| New nodes only | CSR, bootstrap, Machine API, ignition, DNS, registry, or network issue |
| After config change | Suspect MachineConfig, KubeletConfig, ContainerRuntimeConfig |

### Step 2 — Read Node Conditions

```bash
oc describe node <node>
```

Important fields:

```text
Conditions:
  Type             Status  Reason
  MemoryPressure   False   KubeletHasSufficientMemory
  DiskPressure     True    KubeletHasDiskPressure
  PIDPressure      False   KubeletHasSufficientPID
  Ready            False   KubeletNotReady
```

### Step 3 — Read Events Before Logs

Events often tell you the broad category faster than logs.

```bash
oc get events -A --field-selector involvedObject.kind=Node --sort-by=.lastTimestamp
oc describe node <node> | sed -n '/Events:/,$p'
```

Examples:

```text
NodeHasDiskPressure
NodeNotReady
NodeReady
InvalidDiskCapacity
ContainerGCFailed
ImageGCFailed
FailedMount
FailedCreatePodSandBox
NetworkPluginNotReady
```

### Step 4 — Inspect Kubelet and CRI-O Together

Kubelet and CRI-O failures often appear together.

```bash
oc debug node/<node>
chroot /host
systemctl status kubelet crio --no-pager
journalctl -b -u kubelet -u crio --no-pager | tail -300
```

### Step 5 — Check Recent MCO Changes

```bash
oc get mcp
oc describe mcp worker
oc get nodes -o custom-columns=NAME:.metadata.name,MC:.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig,DESIRED:.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig,STATE:.metadata.annotations.machineconfiguration\.openshift\.io/state
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -c machine-config-daemon --tail=200
```

### Step 6 — Fix the Smallest Safe Thing First

Do not immediately reboot every node. First isolate the reason:

- Disk full? Clean logs/images safely or expand disk.
- CRI-O down? Check CRI-O logs before restart.
- Kubelet down? Read `systemctl status` and unit config first.
- Bad KubeletConfig? Revert CR and let MCO roll forward.
- CSR pending? Validate identity before approving.
- API unreachable? Fix network / load balancer / DNS first.

## 7. Node Condition Troubleshooting

OpenShift exposes node health through node conditions. The most important kubelet-related conditions are:

| Condition | Meaning | Common Causes |
|---|---|---|
| `Ready=False` | Kubelet reports node unhealthy | kubelet down, runtime down, network plugin not ready, API issue |
| `Ready=Unknown` | Control plane stopped receiving node heartbeat | network partition, node power off, kubelet hung, API reachability issue |
| `DiskPressure=True` | Node filesystem/image filesystem low | full `/var`, image bloat, logs, PVC local data, inode exhaustion |
| `MemoryPressure=True` | Node memory low | workload overuse, system daemons, leaks, no requests/limits |
| `PIDPressure=True` | Too many processes | fork bomb, high process workloads, PID limit too low |
| `NetworkUnavailable=True` | Node network not configured | CNI/OVN issue, node routing issue |

### 7.1 Ready=False

Check:

```bash
oc describe node <node>
oc adm node-logs <node> -u kubelet --tail=300
oc debug node/<node> -- chroot /host systemctl status kubelet crio --no-pager
```

Common log patterns:

```text
container runtime is down
NetworkPluginNotReady
PLEG is not healthy
failed to ensure lease exists
node "<node>" not found
Unable to update node status
failed to run Kubelet
```

Decision tree:

```text
Ready=False
 ├── kubelet service stopped? → troubleshoot systemd/kubelet config
 ├── CRI-O stopped? → troubleshoot CRI-O
 ├── NetworkPluginNotReady? → troubleshoot OVN/CNI
 ├── failed to update node status? → troubleshoot API/network/certs
 ├── disk/memory/PID pressure? → resource pressure runbook
 └── after MCO update? → inspect MCP/MCD/rendered config
```

### 7.2 Ready=Unknown

This usually means the control plane cannot hear from kubelet.

Check from cluster:

```bash
oc get node <node> -o yaml | grep -A5 -B5 'Ready'
oc get lease -n kube-node-lease | grep <node>
oc describe node <node>
```

Check node reachability:

```bash
ping <node-ip>
ssh core@<node-fqdn>   # only when required and permitted
```

From another node or bastion:

```bash
curl -k https://<node-ip>:10250/healthz
```

Possible causes:

- Node powered off
- Network isolation
- kubelet hung
- API server cannot reach node kubelet
- Firewall/security group blocks 10250
- Node DNS changed
- Certificate issue
- Severe CPU/memory starvation

### 7.3 DiskPressure=True

Check:

```bash
oc describe node <node> | grep -A10 -E 'DiskPressure|Allocated resources|Events'
oc debug node/<node>
chroot /host
df -h
df -ih
du -xh /var | sort -h | tail -30
du -xh /var/lib/containers | sort -h | tail -30
du -xh /var/log | sort -h | tail -30
journalctl --disk-usage
```

Common locations:

```text
/var/lib/containers/storage
/var/lib/kubelet
/var/log
/var/log/containers
/var/log/pods
/run
```

Do not blindly delete random kubelet directories. Prefer:

```bash
crictl images
crictl ps -a
crictl rmi --prune
journalctl --vacuum-time=2d
journalctl --vacuum-size=1G
```

Use caution with `crictl rmi --prune` on production nodes because images might need to be pulled again and disconnected clusters might not have registry reachability.

### 7.4 MemoryPressure=True

Check:

```bash
oc adm top node <node>
oc adm top pods -A --sort-by=memory | tail -30
oc debug node/<node>
chroot /host
free -m
ps aux --sort=-%mem | head -30
systemd-cgtop
```

Common causes:

- Pods without memory limits
- JVM/Elastic/DB workloads exceeding requests
- Node overcommit
- System daemon leak
- Too many pods per node
- Monitoring/logging agents under heavy load

Actions:

- Evict or reschedule noisy workloads.
- Add/adjust limits and requests.
- Reduce density or `maxPods`.
- Add nodes or increase node size.
- Investigate memory leaks.

### 7.5 PIDPressure=True

Check:

```bash
oc debug node/<node>
chroot /host
systemctl status kubelet --no-pager
ps -eLf | wc -l
ps -eLo pid,ppid,nlwp,cmd --sort=-nlwp | head -30
cat /proc/sys/kernel/pid_max
systemctl show --property DefaultTasksMax
```

Common causes:

- Application spawning many threads/processes
- Broken sidecar or logging process
- Fork bomb
- Too many pods
- Low PID limit configuration

Actions:

- Identify process-heavy pods.
- Delete or scale down bad workloads.
- Review pod PID limits and node PID reservations.
- Consider KubeletConfig tuning only after root cause is understood.

## 8. Kubelet Logs and Journald Investigation

### 8.1 From the Cluster

Single node:

```bash
oc adm node-logs <node-name> -u kubelet --tail=300
```

All workers:

```bash
oc adm node-logs --role=worker -u kubelet --tail=100
```

All control plane nodes:

```bash
oc adm node-logs --role=master -u kubelet --tail=100
```

### 8.2 From Node Debug Session

```bash
oc debug node/<node-name>
chroot /host
journalctl -b -u kubelet --no-pager
journalctl -b -u kubelet --since "1 hour ago" --no-pager
journalctl -b -f -u kubelet.service
```

With CRI-O together:

```bash
journalctl -b -u kubelet -u crio --no-pager | tail -500
```

Previous boot:

```bash
journalctl -b -1 -u kubelet --no-pager | tail -300
```

### 8.3 High-Value Log Patterns

| Log Pattern | Meaning | Next Step |
|---|---|---|
| `container runtime is down` | CRI-O not healthy | Check `crio` service and runtime socket |
| `NetworkPluginNotReady` | CNI not initialized | Check OVN node pods and CNI files |
| `failed to update node status` | API communication issue | Check API reachability, certs, kubeconfig |
| `x509: certificate has expired` | Cert problem | Check CSRs and cert validity |
| `PLEG is not healthy` | Runtime event loop issue | Check CRI-O performance/hang |
| `failed to create pod sandbox` | Runtime/CNI failure | Check CRI-O and OVN/CNI logs |
| `FailedMount` | Volume issue | Check CSI node plugin, PVC, kubelet volume manager |
| `Image garbage collection failed` | Disk/imagefs issue | Check container storage |
| `eviction manager` | Resource pressure | Check node resources and eviction thresholds |
| `node not found` | Registration/auth issue | Check node object, cert, hostname |

### 8.4 Read Logs by Time Window

When a node flaps, match time windows:

```bash
oc get events -A --sort-by=.lastTimestamp | tail -50
oc adm node-logs <node> -u kubelet --since=30m
oc adm node-logs <node> -u crio --since=30m
```

Then correlate:

```text
10:03 node NotReady
10:03 kubelet: container runtime is down
10:02 crio: storage error / overlay mount failure
10:01 MCD: reboot triggered by rendered-worker-xxxx
```

## 9. Troubleshooting Kubelet Service Failures

### 9.1 Check Service State

```bash
oc debug node/<node>
chroot /host
systemctl status kubelet --no-pager
systemctl is-enabled kubelet
systemctl cat kubelet
```

### 9.2 Start/Restart Safely

On a single worker node, after logs are captured:

```bash
systemctl restart kubelet
systemctl status kubelet --no-pager
journalctl -b -u kubelet -f
```

Production caution:

- Restarting kubelet does not normally kill running containers immediately, but it can temporarily disrupt `logs`, `exec`, probes, and pod lifecycle operations.
- On control plane nodes, be very careful. Kubelet manages static pods. Restarting it can affect control plane stability if the node already has issues.
- Always avoid restarting kubelet on multiple control plane nodes simultaneously.

### 9.3 Check Unit Files and Drop-ins

```bash
systemctl cat kubelet
systemctl show kubelet | grep -E 'FragmentPath|DropInPaths|ExecStart'
```

Look for:

- Bad ExecStart arguments
- Missing config file
- Bad kubeconfig path
- Invalid drop-in from MachineConfig
- Wrong SELinux context on files
- Broken rendered MachineConfig

### 9.4 Validate Kubelet Config on Disk

Do not assume paths. First inspect service arguments:

```bash
systemctl cat kubelet
ps -ef | grep '[k]ubelet'
```

Then check referenced files:

```bash
ls -l <path-from-kubelet-args>
cat <path-from-kubelet-args>
```

Common kubelet startup errors:

```text
failed to load Kubelet config file
unknown field "..." in kubelet config
invalid configuration
failed to run Kubelet: failed to create kubelet
```

If this started after a `KubeletConfig` change, revert the bad CR and allow MCO to render/apply a corrected config.

## 10. Kubelet and API Server Communication Issues

Kubelet must talk to the API server for:

- Node registration
- Node status updates
- Node lease updates
- Watching assigned pods
- Reading secrets/config maps for mounted volumes
- Posting events
- Certificate rotation

The API server must also talk to kubelet for:

- `oc logs`
- `oc exec`
- `oc rsh`
- `oc attach`
- `oc port-forward`
- metrics and some node-level operations

### 10.1 From Node to API

From node debug session:

```bash
oc debug node/<node>
chroot /host
curl -k https://api.<cluster-domain>:6443/readyz
curl -k https://api.<cluster-domain>:6443/livez
```

Check DNS:

```bash
getent hosts api.<cluster-domain>
getent hosts api-int.<cluster-domain>
resolvectl status || cat /etc/resolv.conf
```

Check route:

```bash
ip route
ip addr
nmcli con show
```

Check firewall/load balancer/security group externally if applicable.

### 10.2 From API / Cluster to Node Kubelet

Symptoms:

```bash
oc logs <pod>
oc exec <pod> -- date
```

Errors involving `:10250` usually mean API server cannot reach kubelet or kubelet TLS/auth is broken.

Check node IP:

```bash
oc get node <node> -o wide
oc get node <node> -o jsonpath='{.status.addresses}' | jq
```

From a privileged debug pod or another node, test:

```bash
curl -k https://<node-internal-ip>:10250/healthz
```

Expected simple response can be:

```text
ok
```

If blocked:

- Check node firewall/security groups.
- Check SDN/OVN host routing.
- Check kubelet service health.
- Check whether the node IP changed.
- Check certificates.

### 10.3 API Reachability Failure Patterns

Kubelet logs:

```text
Unable to update node status
failed to ensure lease exists
dial tcp <api-ip>:6443: i/o timeout
x509: certificate signed by unknown authority
Unauthorized
Forbidden
```

Troubleshooting map:

| Error | Likely Cause |
|---|---|
| `i/o timeout` | Network path, firewall, VIP, LB, routing |
| `no such host` | DNS failure |
| `connection refused` | API endpoint down or wrong IP/port |
| `x509 unknown authority` | CA/kubeconfig/cert issue |
| `Unauthorized` | kubelet client cert invalid/expired/not approved |
| `Forbidden` | Node identity mismatch or RBAC/node authorizer issue |

## 11. Certificate, CSR, and Node Authentication Issues

Kubelet uses certificates to authenticate to the API server. It can bootstrap and rotate certificates. Certificate problems are common when:

- A node is newly added.
- A node was powered off for a long time.
- Cluster certificates rotated while node was unavailable.
- Node hostname changed.
- Time drift caused cert validity problems.
- CSR auto-approval did not happen.

### 11.1 Check CSRs

```bash
oc get csr
oc get csr -o wide
```

Look for:

```text
Pending
Denied
Approved,Issued
```

Inspect one:

```bash
oc describe csr <csr-name>
```

Senior-admin caution:

> Never approve unknown CSRs blindly. Confirm the node identity, requester, groups, and expected hostname/IP before approval.

### 11.2 Approve Valid Node CSRs

Only after validation:

```bash
oc adm certificate approve <csr-name>
```

Bulk approval is risky. If you must use it in a lab, understand the security tradeoff:

```bash
oc get csr | awk '/Pending/ {print $1}' | xargs -r oc adm certificate approve
```

### 11.3 Check Time Drift

From node:

```bash
oc debug node/<node>
chroot /host
timedatectl
chronyc tracking
chronyc sources -v
```

Certificate validity depends on correct time. If time is wrong, kubelet can fail with TLS errors even when certs are valid.

### 11.4 Check Kubelet Client Certificate Files

Do not rely on a fixed path; inspect kubelet args first:

```bash
systemctl cat kubelet
ps -ef | grep '[k]ubelet'
```

Then check referenced kubeconfig and cert paths:

```bash
ls -l <kubeconfig-or-cert-path>
openssl x509 -in <cert-file> -noout -subject -issuer -dates
```

### 11.5 Common Certificate Errors

| Error | Meaning | Fix |
|---|---|---|
| `certificate has expired` | kubelet cert expired | check CSR, approve valid CSR, restore rotation |
| `certificate is not yet valid` | time skew | fix chrony/NTP |
| `unknown authority` | wrong CA or kubeconfig | restore correct config through MCO/rebootstrap |
| `Unauthorized` | cert invalid for node identity | check CSR, node name, kubeconfig |
| `x509: cannot validate certificate` | SAN or trust issue | check API endpoint/certs |

## 12. CRI-O and Container Runtime Issues

OpenShift 4 uses CRI-O as the container runtime. Kubelet depends on CRI-O to create pod sandboxes, pull images, start containers, stop containers, and report container state.

### 12.1 Check CRI-O Service

```bash
oc debug node/<node>
chroot /host
systemctl status crio --no-pager
journalctl -b -u crio --no-pager | tail -300
```

Check socket:

```bash
ls -l /var/run/crio/crio.sock /run/crio/crio.sock 2>/dev/null
crictl info
crictl ps -a
crictl pods
crictl images
```

### 12.2 Kubelet Logs Indicating CRI-O Problems

```text
container runtime is down
failed to connect to runtime service
PLEG is not healthy
failed to create containerd task   # less common in OCP/CRI-O, but runtime-style message
failed to create pod sandbox
context deadline exceeded
```

### 12.3 CRI-O Logs to Look For

```text
error reserving ctr name
overlay mount error
no space left on device
permission denied
failed to pull image
trying to access image registry
CNI plugin error
failed to create pod sandbox
```

### 12.4 CRI-O Recovery

After collecting logs:

```bash
systemctl restart crio
systemctl status crio --no-pager
journalctl -b -u crio -f
```

Then watch kubelet:

```bash
journalctl -b -u kubelet -f
```

Caution:

- Restarting CRI-O can disrupt running containers and pod status reporting.
- On control plane nodes, restart only with strong reason and preferably during a maintenance window unless there is an active outage.
- Do not restart CRI-O across multiple control plane nodes at once.

### 12.5 Container Storage Problems

Check:

```bash
df -h /var/lib/containers
df -ih /var/lib/containers
du -xh /var/lib/containers | sort -h | tail -30
crictl images
crictl ps -a
```

Potential fixes:

```bash
crictl rmi --prune
journalctl --vacuum-size=1G
```

If overlay storage is corrupted, do not randomly delete storage directories in production. Capture logs, isolate the node, drain if possible, and consider node reprovisioning if corruption is severe.

## 13. CNI / Pod Network Issues Affecting Kubelet

Kubelet depends on CNI readiness for pod sandbox creation. In OpenShift default networking, OVN-Kubernetes provides pod networking.

### 13.1 Symptoms

Pods stuck in `ContainerCreating` with events:

```text
FailedCreatePodSandBox
NetworkPluginNotReady
failed to setup network for sandbox
CNI plugin not initialized
```

Kubelet logs:

```text
NetworkPluginNotReady: cni plugin not initialized
failed to create pod sandbox
```

### 13.2 Check Network Operator

```bash
oc get co network
oc describe co network
oc get pods -n openshift-ovn-kubernetes -o wide
oc get pods -n openshift-network-node-identity -o wide 2>/dev/null
```

### 13.3 Check OVN Node Pod on the Affected Node

```bash
oc get pods -n openshift-ovn-kubernetes -o wide | grep <node>
oc logs -n openshift-ovn-kubernetes <ovnkube-node-pod> -c ovnkube-node --tail=200
oc logs -n openshift-ovn-kubernetes <ovnkube-node-pod> -c ovn-controller --tail=200
```

Container names can vary by version; list containers first:

```bash
oc get pod -n openshift-ovn-kubernetes <pod> -o jsonpath='{.spec.containers[*].name}'
```

### 13.4 Check Host CNI Files

```bash
oc debug node/<node>
chroot /host
ls -l /etc/cni/net.d/
ls -l /opt/cni/bin/ 2>/dev/null
ip link
ip route
```

### 13.5 Common Causes

- OVN node pod not running on node
- Network operator degraded
- Node IP changed
- MTU mismatch
- Firewall blocks Geneve/VXLAN/OVN traffic depending on topology
- Missing CNI config files
- Bad NetworkManager config
- MCO update changed network settings
- DNS failure prevents OVN components from connecting

### 13.6 Recovery

1. Confirm whether issue is single-node or cluster-wide.
2. Check network operator and OVN pods.
3. Check node routing/IP/MTU.
4. Restart affected OVN node pod only if logs indicate transient issue:

```bash
oc delete pod -n openshift-ovn-kubernetes <ovnkube-node-pod>
```

5. If node network is broken, cordon/drain and fix underlying host network.

## 14. CSI / Volume Mount Issues Affecting Kubelet

Kubelet volume manager coordinates pod volume setup. Storage problems commonly appear as kubelet errors.

### 14.1 Symptoms

Pod events:

```text

UnmountDevice failed
Multi-Attach error
```

Kubelet logs:

```text

```

### 14.2 Check Pod and PVC

```bash
oc get pvc -n <ns>

oc get pv
oc describe pv <pv>
```

### 14.3 Check CSI Components

```bash

```

- Check storage backend health.
- For stuck mounts, drain node if possible before manual unmount.
- Reboot node only after understanding storage state, especially for stateful workloads.

## 16. Eviction, DiskPressure, MemoryPressure, and PIDPressure

Kubelet eviction manager protects the node from total failure by evicting pods when thresholds are breached.

### 16.1 Hard vs Soft Eviction

Common kubelet eviction signals:

```text
memory.available
nodefs.available
nodefs.inodesFree
imagefs.available
imagefs.inodesFree
pid.available
```

Example `KubeletConfig` snippet:

```yaml
kubeletConfig:
  evictionHard:
    memory.available: "500Mi"
    nodefs.available: "10%"
    imagefs.available: "15%"
    nodefs.inodesFree: "5%"
```

Do not tune eviction thresholds just to hide pressure. Fix workload sizing and node capacity first.

### 16.2 DiskPressure Deep Dive

Check filesystems separately:

```bash
df -h
df -ih
findmnt
```

Check container image storage:

```bash
crictl images
crictl ps -a
crictl rmi --prune
```

Check logs:

```bash
journalctl --disk-usage
du -xh /var/log | sort -h | tail -20
du -xh /var/log/pods | sort -h | tail -20
du -xh /var/log/containers | sort -h | tail -20
```

### 16.3 MemoryPressure Deep Dive

```bash
oc adm top node <node>
oc adm top pods -A --sort-by=memory
oc describe node <node> | sed -n '/Allocated resources:/,/Events:/p'
```

Look for overcommit:

```text
Requests: 70% memory
Limits:   250% memory
```

If limits are too high or missing, kubelet eviction may occur before application owners understand why.

### 16.4 PIDPressure Deep Dive

```bash
ps -eLf | wc -l
ps -eLo pid,ppid,nlwp,cmd --sort=-nlwp | head -30
```

Map process to container:

```bash
crictl ps
crictl inspect <container-id> | jq '.info.pid'
```

Then correlate host PID to pod/container.

## 17. Static Pods and Control Plane Kubelet Issues

On control plane nodes, kubelet is critical because it runs static pods for core control plane components. A kubelet issue on a master can become an API, etcd, scheduler, or controller-manager issue.

### 17.1 Check Static Pod Manifests

From control plane node:

```bash
oc debug node/<master-node>
chroot /host
ls -l /etc/kubernetes/manifests
```

Common static pod manifests include components such as:

```text
kube-apiserver-pod.yaml
kube-controller-manager-pod.yaml
kube-scheduler-pod.yaml
etcd-pod.yaml
```

Names and layouts can vary by OpenShift release and topology.

### 17.2 Check Mirror Pods

```bash
oc get pods -n openshift-kube-apiserver -o wide
oc get pods -n openshift-kube-controller-manager -o wide
oc get pods -n openshift-kube-scheduler -o wide
oc get pods -n openshift-etcd -o wide
```

### 17.3 Kubelet Failure on One Master

If one master kubelet is down:

1. Check etcd quorum first.
2. Do not reboot multiple masters.
3. Collect kubelet and CRI-O logs.
4. Check static pod manifest validity.
5. Check disk pressure on `/var` and `/etc/kubernetes` related paths.
6. Restart kubelet only on the affected master after evidence collection.

### 17.4 Static Pod Crash Due to Kubelet/CRI-O

Logs may show:

```text
failed to create pod sandbox
failed to pull image
volume mount failed
manifest parse error
```

Troubleshoot like normal pods, but with higher risk because control plane pods are involved.

## 18. Machine Config Operator, KubeletConfig, and MCP Degraded Issues

### 18.1 Why MCO Matters for Kubelet

In OpenShift, MCO owns node-level configuration. A kubelet problem after a configuration rollout is often an MCO/MCD problem or a bad generated config.

Check:

```bash
oc get mcp
oc describe mcp worker
oc describe mcp master
oc get mc | tail
```

### 18.2 Check Node MachineConfig Annotations

```bash
oc get node <node> -o jsonpath='{.metadata.annotations.machineconfiguration\.openshift\.io/currentConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/desiredConfig}{"\n"}{.metadata.annotations.machineconfiguration\.openshift\.io/state}{"\n"}'
```

All nodes in a pool should eventually converge to desired config.

### 18.3 Check Machine Config Daemon Logs

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep machine-config-daemon
oc logs -n openshift-machine-config-operator <mcd-pod> -c machine-config-daemon --tail=300
```

If you need the pod on a specific node:

```bash
oc get pods -n openshift-machine-config-operator -o wide | grep <node>
```

### 18.4 MCD Drift

Configuration drift means the node no longer matches the rendered MachineConfig. This can happen if someone manually edits files on the host.

Symptoms:

```text
MachineConfigPool Degraded=True
machineconfigdaemon: content mismatch for file ...
```

Fix principle:

- Do not manually edit managed files.
- Restore expected file content/permissions or roll out corrected MachineConfig.
- If node is badly drifted, reprovisioning may be cleaner.

### 18.5 Bad KubeletConfig

Example bad situation:

```yaml
kubeletConfig:
  maxPods: "two hundred"   # invalid type
```

or unsupported upstream field for the Kubernetes version.

Symptoms:

```text
failed to load Kubelet config file
json: unknown field
invalid configuration
kubelet.service failed
```

Recovery:

1. Remove or correct the bad `KubeletConfig`.
2. Wait for MCO to render a new config.
3. If node cannot apply automatically, debug via MCD logs.
4. If kubelet cannot start and node is unreachable by `oc`, SSH may be needed as break-glass access.

### 18.6 Safe KubeletConfig Change Process

1. Test in non-production.
2. Apply to a custom MCP first, not all workers.
3. Ensure one node updates successfully.
4. Watch:

```bash
oc get mcp -w
oc get nodes -w
oc get co machine-config
```

5. Validate kubelet logs after rollout.
6. Roll out gradually.

## 19. Kubelet Verbosity and Deep Debugging

For difficult issues, increase kubelet log verbosity using OpenShift-supported configuration. Do not directly edit kubelet systemd args on the host.

### 19.1 Gather Current Logs First

```bash
oc adm node-logs --role=worker -u kubelet > worker-kubelet-before.log
oc adm node-logs --role=master -u kubelet > master-kubelet-before.log
```

### 19.2 Increase Verbosity Carefully

Depending on OpenShift release, kubelet log level can be configured through `KubeletConfig` or documented OpenShift procedures.

Example conceptual snippet:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: debug-worker-kubelet-loglevel
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  logLevel: 4
```

Caution:

- Higher verbosity can generate large logs.
- It can worsen disk pressure.
- Use temporarily and revert after investigation.

### 19.3 Capture After Increasing Verbosity

```bash
oc adm node-logs --role=worker -u kubelet --since=30m > worker-kubelet-debug.log
```

Then revert verbosity.

## 20. Node Access: `oc debug node` vs SSH

### 20.1 Preferred: `oc debug node`

```bash
oc debug node/<node>
chroot /host
```

Use it for:

- `journalctl`
- `systemctl status`
- checking filesystems
- CRI-O commands
- network commands
- kubelet unit inspection

### 20.2 Break-Glass: SSH

SSH is not the normal management path for OpenShift nodes. Use it when:

- API server is unavailable.
- kubelet is not working, so `oc debug node` cannot schedule/start.
- Node is isolated and needs host-level access.
- Red Hat Support asks for direct access steps.

Example:

```bash
ssh core@<node-fqdn>
sudo -i
journalctl -b -u kubelet --no-pager | tail -300
```

### 20.3 Do Not Make Manual Permanent Changes

Avoid:

```bash
vi /etc/kubernetes/kubelet.conf
vi /etc/systemd/system/kubelet.service
rm -rf /var/lib/kubelet
rm -rf /var/lib/containers/storage
```

Use MCO-managed resources instead.

## 21. Production Recovery Runbooks

### Runbook A — Single Worker Node `NotReady`

```bash
NODE=<node>
oc describe node $NODE
oc adm node-logs $NODE -u kubelet --tail=300
oc adm node-logs $NODE -u crio --tail=300
oc debug node/$NODE
```

Inside debug:

```bash
chroot /host
systemctl status kubelet crio --no-pager
df -h
df -ih
free -m
journalctl -b -u kubelet -u crio --no-pager | tail -500
```

Decision:

- Disk full → clean safe logs/images or expand disk.
- CRI-O down → investigate then restart CRI-O.
- Kubelet down → investigate then restart kubelet.
- Network plugin not ready → inspect OVN node pod.
- API unreachable → fix network/DNS/LB.
- Cert issue → inspect CSR/time/certs.

After fix:

```bash
oc get node $NODE -w
oc get pods -A -o wide | grep $NODE
```

### Runbook B — Many Workers `NotReady` After Change

```bash
oc get mcp
oc describe mcp worker
oc get co machine-config network kube-apiserver
oc get nodes -o wide
oc get kubeletconfig
oc get mc | tail -20
```

Check MCD logs:

```bash
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -c machine-config-daemon --tail=300
```

Likely causes:

- Bad KubeletConfig
- Bad MachineConfig
- Bad ContainerRuntimeConfig
- Network config rollout issue
- Registry/mirror config broke image pulls
- Node reboot storm

Recovery:

1. Stop the blast radius if possible.
2. Revert the bad custom resource.
3. Wait for new rendered config.
4. Recover nodes one by one.
5. Do not reboot all nodes at once.

### Runbook C — `oc logs` / `oc exec` Fails but Pods Are Running

Symptoms:

```text

```

Check:

```bash

ss -lntp | grep 10250
```

Potential causes:

- Kubelet not listening
- Firewall/security group issue
- API server cannot reach node IP
- Kubelet serving cert issue
- Node address wrong

### Runbook D — Pods Stuck in `ContainerCreating`


| `CreateContainerError` | Runtime/security/context/filesystem |

### Runbook E — Control Plane Node Kubelet Down

```bash
oc get co
oc get nodes
oc get pods -n openshift-etcd -o wide
oc get pods -n openshift-kube-apiserver -o wide
```

On affected node:


- Preserve etcd quorum.
- Do not restart multiple masters at once.

- Recover one node at a time.
- SSH only if `oc debug` cannot work.

### Scenario 5 — `oc logs` Fails but Application Is Running

Error:

```text
Error from server: Get https://10.0.1.25:10250/containerLogs/...: i/o timeout
```

Diagnosis:

```bash
oc get node worker-3 -o wide
oc adm node-logs worker-3 -u kubelet --tail=200
oc debug node/worker-3
chroot /host
ss -lntp | grep 10250
systemctl status kubelet --no-pager
```

Likely:

- API cannot reach node on 10250.
- Node IP/security group/firewall route issue.
- Kubelet not listening.
- Kubelet serving cert issue.

## 26. Interview and Exam Notes

### 26.1 How to Explain Kubelet Troubleshooting in an Interview

A strong answer:

> I start with scope: one node, many nodes, or control plane. Then I check node conditions and events using `oc describe node`. After that I collect kubelet logs with `oc adm node-logs <node> -u kubelet` and compare with CRI-O logs because kubelet depends on runtime health. If pods are stuck in `ContainerCreating`, I classify the event as CNI, CSI, image pull, or runtime. If the node is `NotReady`, I check kubelet service state, API reachability, certificates/CSR, disk/memory/PID pressure, and recent MachineConfig changes. In OpenShift I avoid manual host edits and use MCO/KubeletConfig for persistent changes.

### 26.2 Practical Exam-Style Checklist

For a bad node:

```bash
oc get nodes
oc describe node <node>
oc adm node-logs <node> -u kubelet --tail=200
oc debug node/<node>
chroot /host
systemctl status kubelet crio --no-pager
journalctl -b -u kubelet -u crio --no-pager | tail -300
```

For pods stuck:

```bash
oc describe pod <pod> -n <ns>
oc get pod <pod> -n <ns> -o wide
oc adm node-logs <node> -u kubelet --since=30m
```

For MCO issue:

```bash
oc get mcp
oc describe mcp worker
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon -c machine-config-daemon --tail=200
```

### 26.3 Common Mistakes

- Restarting kubelet before reading logs.
- Rebooting all nodes at once.
- Approving all CSRs blindly.
- Editing kubelet files manually on RHCOS.
- Ignoring CRI-O logs.
- Ignoring events and only reading pod logs.
- Treating `ContainerCreating` as an application issue when it is CNI/CSI/runtime.
- Deleting `/var/lib/kubelet` or `/var/lib/containers` without support-level reason.
- Applying upstream kubelet config without checking OpenShift compatibility.
- Forgetting that control plane kubelet manages static pods.

## Final Senior Admin Advice

Kubelet troubleshooting is about correlation, not guessing. Always correlate these five layers:

```text
1. Node condition
2. Node events
3. kubelet logs
4. CRI-O / CNI / CSI logs
5. Recent MCO or platform changes
```

A kubelet error is often the messenger, not the root cause. Treat kubelet as the center of the node control loop, then walk outward through runtime, network, storage, certificates, API reachability, and MachineConfig state.
