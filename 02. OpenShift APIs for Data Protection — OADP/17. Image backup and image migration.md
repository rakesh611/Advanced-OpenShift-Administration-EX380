## 1. What Problem Image Backup Solves

In OpenShift, application backup is not only about YAML resources and PVC data. A real production application often depends on container images that may be built inside the cluster and stored in the OpenShift internal registry.

Example:

```text
Source Code -> BuildConfig -> Build -> ImageStreamTag -> Internal Registry Image -> Deployment/DeploymentConfig
```

If you back up only Kubernetes objects such as `Deployment`, `DeploymentConfig`, `Service`, `Route`, `Secret`, and `PVC`, but you do not protect the internal image, then a restore can still fail with errors such as:

```text
ErrImagePull
ImagePullBackOff
manifest unknown
repository does not exist
unauthorized: authentication required
```

This is common in disaster recovery and migration scenarios where the target cluster does not have the old internal registry data.

### Practical production scenario

A team builds an application using OpenShift BuildConfig:

```yaml
kind: BuildConfig
spec:
  output:
    to:
      kind: ImageStreamTag
      name: payment-api:prod
```

The generated image is stored inside the OpenShift internal registry, for example:

```text
image-registry.openshift-image-registry.svc:5000/payments/payment-api@sha256:<digest>
```

The workload is deployed from an ImageStreamTag or from an internal registry pullspec. During migration to another cluster, the restored `DeploymentConfig` or `Deployment` might still point to an image digest that does not exist in the destination cluster unless the image data is migrated.

OADP image backup solves this by protecting OpenShift resources and internal images together as part of application backup and restore.

## 2. Core OpenShift Image Concepts

Before understanding OADP image backup, you must separate four different layers.

### 2.1 Container image data

The actual OCI/Docker image contains:

- Manifest
- Config
- Layers
- Digest
- Labels
- Entrypoint/CMD metadata
- Filesystem content

This is binary registry data, not only Kubernetes YAML.

### 2.2 OpenShift internal registry

OpenShift provides an integrated image registry managed by the Image Registry Operator. It runs in:

```text
openshift-image-registry
```

Common service:

```text
image-registry.openshift-image-registry.svc:5000
```

The internal registry stores image blobs/layers in configured registry storage, such as:

- Object storage
- Persistent volume
- Cloud provider storage
- OpenShift Data Foundation / NooBaa-backed storage

Important point:

```text
Image binary data != ImageStream metadata
```

The image binary data is stored in registry storage. The image metadata is exposed through OpenShift APIs such as `Image`, `ImageStream`, `ImageStreamTag`, and `ImageTag`.

### 2.3 ImageStream

An `ImageStream` is an OpenShift API object that provides a stable abstraction over one or more container image tags.

Example:

```yaml
apiVersion: image.openshift.io/v1
kind: ImageStream
metadata:
  name: payment-api
  namespace: payments
```

An ImageStream does **not** behave exactly like a Docker repository. It gives OpenShift extra capabilities:

- Tracks image tag history
- Supports rollback by tag history
- Can trigger builds or deployments
- Can point to internal or external registry images
- Can decouple workload configuration from raw registry pullspecs

### 2.4 ImageStreamTag

An `ImageStreamTag` is a tag view inside an ImageStream.

Example:

```text
payment-api:prod
payment-api:v1.0.3
payment-api:latest
```

A workload may reference the ImageStreamTag indirectly through OpenShift image change triggers, or the image trigger controller may resolve it into a concrete internal registry pullspec.

### 2.5 ImageTag

`ImageTag` is a newer OpenShift image API view that represents a single tag in an image stream and includes both spec and status information.

### 2.6 Image resource

`Image` is usually a cluster-scoped OpenShift API object representing image metadata by digest. It is not the same thing as the binary layer data in the registry.

### 2.7 External image references

Applications might use external images directly:

```yaml
image: registry.redhat.io/rhel9/httpd-24:latest
```

or:

```yaml
image: quay.io/company/payment-api:prod
```

OADP can back up the workload YAML and ImageStream metadata, but it should not be treated as a replacement for an enterprise image registry backup strategy for external registries such as Quay, Harbor, Artifactory, Nexus, or registry.redhat.io.

## 3. OADP Architecture for Images

OADP is Red Hat's OpenShift API for Data Protection. It installs and manages Velero plus OpenShift-specific plugins.

Main objects:

```text
DataProtectionApplication  -> Installs/configures Velero and plugins
BackupStorageLocation      -> Object storage target for backups
VolumeSnapshotLocation     -> Snapshot provider location, when used
Backup                     -> Request to back up selected resources
Restore                    -> Request to restore selected resources
Schedule                   -> Recurring backup request
```

### 3.1 Components involved

```text
User/Admin
   |
   | creates Backup CR
   v
Velero server in openshift-adp
   |
   | uses plugins
   v
OpenShift Velero Plugin
   |
   | processes ImageStream/ImageStreamTag/ImageTag/other OpenShift resources
   v
BackupStorageLocation object storage
```

For internal images, OADP/Velero and the OpenShift plugin coordinate to protect both:

1. API resources such as `ImageStream`, `ImageStreamTag`, `BuildConfig`, `DeploymentConfig`, `Deployment`, and related objects.
2. Internal registry image content required by those resources.

### 3.2 Why OpenShift plugin matters

Plain upstream Velero is Kubernetes-focused. It can back up standard Kubernetes resources, but OpenShift has additional resource types and behavior:

- `Route`
- `DeploymentConfig`
- `BuildConfig`
- `ImageStream`
- `ImageStreamTag`
- `ImageTag`
- OpenShift SCC-related handling
- Namespace/project-specific behavior

The OpenShift Velero plugin adds backup and restore logic for these OpenShift resources.

### 3.3 Backup storage location

OADP writes backup artifacts to object storage. Common object storage options:

- AWS S3
- Azure Blob Storage
- Google Cloud Storage
- S3-compatible object storage
- OpenShift Data Foundation Multicloud Object Gateway / NooBaa
- Ceph Object Gateway
- MinIO
- IBM Cloud Object Storage S3

For image backup and image migration, object storage is the exchange point between the source and destination clusters.

## 4. Image Backup vs Image Migration

### 4.1 Image backup

Image backup means protecting image-related objects and internal registry image data from a source OpenShift cluster into a backup location.

Goal:

```text
Source cluster -> BackupStorageLocation
```

Typical use cases:

- Disaster recovery
- Namespace rollback
- App recovery after accidental deletion
- Compliance retention
- Before application upgrade
- Before cluster upgrade
- Protection of build output images

### 4.2 Image migration

Image migration means restoring or moving image-related data to another cluster or namespace.

Goal:

```text
Source cluster -> BackupStorageLocation -> Destination cluster
```

Typical use cases:

- Moving applications from old cluster to new cluster
- Migrating between OCP versions
- Region-to-region DR
- On-premises to cloud migration
- Blue/green cluster cutover
- Rebuilding an environment from backup

### 4.3 Key difference

| Area | Image Backup | Image Migration |
|---|---|---|
| Primary goal | Preserve current internal images | Make images usable on target cluster |
| Direction | Cluster to object storage | Object storage to same/different cluster |
| Main operation | `Backup` CR | `Restore` CR |
| Registry concern | Source internal registry must be readable | Destination internal registry must be writable and usable |
| Risk | Image not included or backup partial failure | Restored workload points to wrong registry/digest/tag |
| Validation | Backup completes and image artifact exists | Pods start successfully from restored images |

## 5. What OADP Can and Cannot Protect

### 5.1 OADP can protect

OADP is designed for application backup and restore. For image scenarios, it can protect:

- Namespace-scoped application resources
- OpenShift resources such as Routes, DeploymentConfigs, BuildConfigs, and ImageStreams
- Internal images associated with OpenShift image APIs
- PVC data using CSI snapshots, Data Mover, Kopia, Restic, or provider snapshots depending on configuration
- Backup and restore schedules
- Restore with namespace mapping

### 5.2 OADP is not a full cluster backup replacement

OADP should not be used as a full etcd backup replacement. It is not intended to back up and restore the whole cluster control plane.

Do not treat OADP as the only backup for:

- etcd disaster recovery
- Cluster operators
- Cluster-wide platform configuration
- MachineConfigPool state
- Complete cluster installation state
- External image registry platforms such as Quay/Harbor themselves

For full control-plane disaster recovery, use OpenShift etcd backup and documented cluster recovery processes.

### 5.3 External image limitation

If a Deployment uses:

```yaml
image: quay.io/company/app:1.2.3
```

OADP backs up the Deployment object, but it does not magically own `quay.io`. The restored application still needs network access, credentials, and image availability in that registry.

For external registry migration, use registry tools such as:

```bash
skopeo copy
oc image mirror
podman pull/tag/push
Quay mirroring
ImageContentSourcePolicy / ImageDigestMirrorSet / ImageTagMirrorSet
```

### 5.4 Internal image backup scope

OADP internal image backup is most relevant when images are stored inside the OpenShift integrated registry, especially build output images produced by OpenShift `BuildConfig` or manually pushed to the internal registry.

## 6. Internal Image Backup Flow

High-level flow:

```text
1. Admin creates Backup CR
2. Velero starts backup
3. OpenShift plugin processes OpenShift resources
4. ImageStream/ImageStreamTag/ImageTag metadata is captured
5. Internal image content associated with those resources is copied to backup object storage
6. Backup status becomes Completed or PartiallyFailed/Failed
```

### 6.1 Example workload

Namespace:

```text
payments
```

ImageStream:

```text
payment-api:prod
```

DeploymentConfig:

```text
payment-api
```

Route:

```text
payment-api.apps.example.com
```

PVC:

```text
payment-db
```

Backup should include:

- `namespace/payments`
- `imagestream/payment-api`
- tag history and image metadata
- internal image blob/layer data
- deployment/deploymentconfig
- service
- route
- configmap
- secret
- PVC and PV data if application is stateful

### 6.2 What happens during backup

When backup includes the application namespace, Velero collects resources based on included/excluded namespaces, labels, and resource filters.

For OpenShift image resources, the OpenShift plugin handles additional logic that is not present in plain Kubernetes backup.

Backup result in object storage usually includes:

```text
backups/<backup-name>/
  <backup-name>.tar.gz
  <backup-name>-logs.gz
  <backup-name>-results.gz
  <backup-name>-csi-volumesnapshotcontents.json.gz   # if CSI used
  ...
```

Internal image data is handled by OADP/OpenShift image backup logic and stored in the configured backup location.

### 6.3 Backup status meaning

Check:

```bash
oc get backup -n openshift-adp
oc describe backup <backup-name> -n openshift-adp
```

Common phases:

```text
New
InProgress
Completed
PartiallyFailed
Failed
Deleting
```

For image backup, never accept only `Completed` at a high level. Also inspect logs for image-related warnings.

## 7. Image Migration Flow Between Clusters

Image migration uses backup plus restore.

```text
Source OCP cluster
  |
  | Backup CR
  v
Object storage / BackupStorageLocation
  |
  | Restore CR from destination cluster
  v
Destination OCP cluster
```

### 7.1 Same namespace migration

Source namespace:

```text
payments
```

Destination namespace:

```text
payments
```

Restore recreates resources into the same namespace name. This is simpler and usually less error-prone.

### 7.2 Different namespace migration

Source namespace:

```text
payments
```

Destination namespace:

```text
payments-dr
```

Use namespace mapping in the Restore CR:

```yaml
namespaceMapping:
  payments: payments-dr
```

Be careful: Some application resources may contain hardcoded namespace names, internal registry pullspecs, RoleBindings, Routes, ConfigMaps, or environment variables that still reference the old namespace.

### 7.3 Different cluster migration

For different cluster migration, both clusters must be able to use the same backup object storage location.

Production checklist:

- Source and destination DPA configured
- Same BackupStorageLocation name where practical
- Same bucket/prefix path where restore will read backup
- Destination credentials can read source backup objects
- Destination cluster has compatible OADP/Velero/OpenShift versions
- Destination internal registry is available and writable
- Destination image registry CA/trust is handled
- Network egress from Velero pod to object storage is allowed
- Required pull secrets exist
- Namespace security/RBAC is compatible

### 7.4 Why restored workloads may still fail

Even when restore completes, pods may fail if:

- Image pullspec points to old cluster internal registry route
- ImageStream triggers did not re-resolve
- Destination registry is not configured
- ImageStreamTag was restored but image blob was not restored
- Pull secret is missing
- ServiceAccount lacks `imagePullSecrets`
- Target namespace does not have access to source image
- External registry is not reachable from destination cluster
- Route hostname conflicts
- SCC/Pod Security Admission behavior differs

## 9. Example DPA Configuration

Below is a typical S3-compatible DPA pattern. Adjust provider, plugin, bucket, region, endpoint, and credentials according to your environment.

> Note: Exact fields can differ slightly by OADP release. Always check the DPA API for your installed OADP version.

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa
  namespace: openshift-adp
spec:
  backupLocations:
  - name: default
    velero:
      provider: aws
      default: true
      objectStorage:
        bucket: oadp-backups
        prefix: prod-cluster
      credential:
        name: cloud-credentials
        key: cloud
      config:
        region: us-east-1
        s3ForcePathStyle: "true"
        s3Url: https://s3.example.com
  configuration:
    velero:
      defaultPlugins:
      - openshift
      - aws
      - csi
    nodeAgent:
      enable: true
      uploaderType: kopia
```

### 9.1 Important DPA fields

| Field | Purpose |
|---|---|
| `backupLocations` | Defines object storage for backup artifacts |
| `provider` | Object storage plugin provider, such as `aws`, `azure`, `gcp`, or supported compatible plugin |
| `objectStorage.bucket` | Bucket/container name |
| `objectStorage.prefix` | Path prefix to separate clusters/environments |
| `credential` | Secret used by Velero/OADP to access storage |
| `defaultPlugins` | Plugins used by Velero, including `openshift` for OpenShift-specific resources |
| `nodeAgent.enable` | Enables file-system backup/data movement functionality where needed |
| `uploaderType` | Usually `kopia` in newer OADP versions; older environments may use Restic |

### 9.2 Azure special note for internal image backup

When using Azure, make sure object storage credentials include the storage account access key when required. In older Red Hat documentation, internal image backup was called out as not working if the credentials file contained only service principal credentials.

### 9.3 Custom CA / self-signed storage or registry

For S3-compatible endpoints, NooBaa, MinIO, or internal services using custom CA certificates, ensure the CA is configured in the BSL/DPA as required by your OADP release.

Symptoms of missing CA trust:

```text
x509: certificate signed by unknown authority
tls: failed to verify certificate
certificate verify failed
```

## 10. Image Backup YAML Examples

### 10.1 Full namespace backup including internal images

This is the safest starting point for application-level image protection.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-full-with-images
  namespace: openshift-adp
spec:
  includedNamespaces:
  - payments
  storageLocation: default
  ttl: 720h0m0s
```

Apply:

```bash
oc apply -f payments-full-with-images.yaml
```

Check:

```bash
oc get backup payments-full-with-images -n openshift-adp
oc describe backup payments-full-with-images -n openshift-adp
```

### 10.2 Backup only image-related OpenShift resources

Use this when you want to test image metadata backup separately. This does **not** replace a full application backup.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-image-metadata-only
  namespace: openshift-adp
spec:
  includedNamespaces:
  - payments
  includedResources:
  - imagestreams.image.openshift.io
  - imagestreamtags.image.openshift.io
  - imagetags.image.openshift.io
  storageLocation: default
  ttl: 168h0m0s
```

Important:

- This is useful for understanding API metadata backup.
- For real migration, include application resources too.
- If you filter too aggressively, plugin behavior or dependent resources might not be included.

### 10.3 Full application backup excluding pods

In many restore strategies, backing up pod objects is unnecessary because controllers recreate pods.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-app-no-pods
  namespace: openshift-adp
spec:
  includedNamespaces:
  - payments
  excludedResources:
  - pods
  storageLocation: default
  ttl: 720h0m0s
```

### 10.4 Label-based backup

Label your app resources:

```bash
oc label all -n payments app.kubernetes.io/part-of=payment-platform --overwrite
oc label is payment-api -n payments app.kubernetes.io/part-of=payment-platform --overwrite
```

Backup:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-label-based
  namespace: openshift-adp
spec:
  includedNamespaces:
  - payments
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payment-platform
  storageLocation: default
  ttl: 720h0m0s
```

Warning:

Label-based backup can accidentally miss resources such as ServiceAccounts, Secrets, RoleBindings, ImageStreams, or PVCs if labels are inconsistent.

### 10.5 Scheduled backup for image-producing namespace

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: payments-nightly
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
    - payments
    storageLocation: default
    ttl: 168h0m0s
```

This creates a recurring backup every day at 01:00 according to the schedule interpretation used by Velero.

## 11. Image Restore and Migration YAML Examples

### 11.1 Restore to same namespace in same cluster

Use this after accidental deletion or namespace-level recovery.

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-payments-same-ns
  namespace: openshift-adp
spec:
  backupName: payments-full-with-images
  includedNamespaces:
  - payments
```

Apply:

```bash
oc apply -f restore-payments-same-ns.yaml
```

Check:

```bash
oc get restore restore-payments-same-ns -n openshift-adp
oc describe restore restore-payments-same-ns -n openshift-adp
```

### 11.2 Restore to different namespace

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-payments-to-dr
  namespace: openshift-adp
spec:
  backupName: payments-full-with-images
  includedNamespaces:
  - payments
  namespaceMapping:
    payments: payments-dr
```

Post-restore checks:

```bash
oc get is -n payments-dr
oc get pods -n payments-dr
oc describe pod <pod-name> -n payments-dr | egrep -i "image|pull|warning|failed"
```

### 11.3 Restore on destination cluster

On source cluster:

```bash
oc apply -f payments-full-with-images.yaml
oc get backup payments-full-with-images -n openshift-adp -w
```

On destination cluster:

1. Install OADP.
2. Configure DPA/BSL to point to the same bucket and prefix.
3. Confirm the backup appears:

```bash
oc get backup -n openshift-adp
```

4. Create Restore CR:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: migrate-payments-from-prod
  namespace: openshift-adp
spec:
  backupName: payments-full-with-images
  includedNamespaces:
  - payments
```

5. Validate:

```bash
oc get ns payments
oc get is -n payments
oc get deploy,dc,sts -n payments
oc get pods -n payments
oc get events -n payments --sort-by=.lastTimestamp | tail -50
```

### 11.4 Restore only image resources

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-payments-images-only
  namespace: openshift-adp
spec:
  backupName: payments-image-metadata-only
  includedNamespaces:
  - payments
  includedResources:
  - imagestreams.image.openshift.io
  - imagestreamtags.image.openshift.io
  - imagetags.image.openshift.io
```

Use only for controlled testing. A real application restore normally requires workloads, services, routes, config, secrets, and possibly PVC data.

## 13. Advanced Production Design

### 13.1 Prefer digest-based promotion for critical workloads

Tags can move. Digests are immutable.

Risky:

```yaml
image: image-registry.openshift-image-registry.svc:5000/payments/payment-api:latest
```

Better:

```yaml
image: image-registry.openshift-image-registry.svc:5000/payments/payment-api@sha256:<digest>
```

However, during migration, hardcoded source-cluster registry pullspecs can cause problems if they reference the old cluster route. ImageStream abstraction plus proper restore testing can reduce this risk.

### 13.2 Avoid using internal registry as the only golden image source

For enterprise production, the internal registry is often best used as a build output/cache/deployment source, but the long-term image supply chain should usually include a dedicated registry platform such as Red Hat Quay.

Recommended strategy:

```text
CI build -> image signing/scanning -> Quay/enterprise registry -> OpenShift deployment
```

Use OADP image backup for application recoverability, but do not rely on it as your only image lifecycle, vulnerability scanning, retention, or promotion mechanism.

### 13.3 Separate image backup from external registry backup

If applications use Quay/Harbor/Nexus/Artifactory:

- Back up the external registry using its own supported backup method.
- Replicate or mirror critical repositories to DR site.
- Ensure pull secrets exist on destination cluster.
- Test image pull before restoring application traffic.

### 13.4 Backup namespace design

Good namespace design improves backup quality.

Bad:

```text
shared namespace contains unrelated apps, CI jobs, old images, test resources
```

Better:

```text
one application or bounded service group per namespace
consistent labels
clear ownership
separate build/test/prod image tags
```

### 13.5 Label discipline

For label-based backups, apply labels to all important resources:

```bash
oc label deploy/payment-api app.kubernetes.io/name=payment-api -n payments --overwrite
oc label svc/payment-api app.kubernetes.io/name=payment-api -n payments --overwrite
oc label route/payment-api app.kubernetes.io/name=payment-api -n payments --overwrite
oc label is/payment-api app.kubernetes.io/name=payment-api -n payments --overwrite
oc label secret/payment-api-config app.kubernetes.io/name=payment-api -n payments --overwrite
```

### 13.6 Retention policy

Image backups can grow quickly because image layers may be large.

Design retention by:

- RPO/RTO
- Number of deployments per day
- Image size
- Registry pruning policy
- Backup TTL
- Object storage lifecycle policy
- Compliance requirements

Example:

```text
Hourly backups retained 24 hours
Daily backups retained 14 days
Weekly backups retained 8 weeks
Monthly backups retained 12 months
```

### 13.7 Schedule backup after build promotion

For applications built inside OpenShift, schedule backups after production image promotion.

Example flow:

```text
Build completes -> image promoted to prod tag -> smoke test passes -> OADP backup starts
```

### 13.8 Air-gapped / disconnected clusters

In disconnected environments:

- Mirror OADP images and plugins to local registry.
- Mirror Velero/plugin images if required.
- Ensure object storage endpoint is reachable internally.
- Use trusted CA bundles.
- Mirror application base images.
- Avoid relying on public registries at restore time.

### 13.9 Multi-cluster DR pattern

Recommended DR design:

```text
Primary cluster:
  OADP Schedule -> shared object storage bucket/prefix

DR cluster:
  OADP installed
  BSL points to same bucket/prefix in read-only or controlled mode
  Restore tested regularly
```

Use read-only backup locations carefully. For DR restore, destination needs to read backup data, but you do not want two clusters accidentally writing conflicting backups to the same path.

### 13.10 Security considerations

Protect:

- Object storage credentials
- Registry credentials
- Pull secrets
- ServiceAccount tokens
- TLS private keys in Routes/Secrets
- Database passwords in Secrets

Use:

- Bucket encryption
- IAM least privilege
- Separate buckets or prefixes per cluster/environment
- Audit logging on object storage
- Network policies for OADP namespace where possible
- Secret rotation after restore if restoring to lower environments

### 13.11 Compliance considerations

Image backups may contain:

- Application binaries
- Proprietary code
- Embedded certificates
- Package manager cache
- Vulnerable libraries
- Secrets accidentally baked into images

Therefore image backup storage should be treated as sensitive production data.

## 14. Troubleshooting Image Backup and Migration

### 14.1 Backup is PartiallyFailed

Check:

```bash
oc describe backup <backup-name> -n openshift-adp
velero backup logs <backup-name> | egrep -i "error|warn|image|registry|imagestream"
```

Possible causes:

- Missing OpenShift plugin
- BSL unavailable
- Internal registry unavailable
- ImageStream references missing image
- CA trust problem
- Unauthorized registry access
- Custom BSL not reconciled by DPA
- Object storage permission issue

### 14.2 ImageStream backup plugin panic or error

Symptoms may include errors around:

```text
imagestreams.image.openshift.io
plugin panicked
registry-secret
index out of range
```

Check whether OADP created the registry secret associated with the BSL. In some scenarios where BackupStorageLocation is managed outside the DPA, the BSL must have the expected label so the OADP controller reconciles related registry secret data.

Commands:

```bash
oc get bsl -n openshift-adp --show-labels
oc get secrets -n openshift-adp | grep -i registry
```

If custom BSL is not labeled, a typical fix is:

```bash
oc label backupstoragelocation <bsl-name> \
  -n openshift-adp \
  app.kubernetes.io/component=bsl --overwrite
```

Then force or wait for DPA reconciliation and recheck secrets.

### 14.3 x509 certificate errors

Symptoms:

```text
x509: certificate signed by unknown authority
tls: failed to verify certificate
```

Check:

```bash
oc get bsl <bsl-name> -n openshift-adp -o yaml
oc logs -n openshift-adp deploy/velero -c velero | grep -i x509
```

Fix areas:

- Add CA certificate to BSL/DPA configuration.
- Ensure the CA is valid for object storage endpoint.
- Ensure system trust bundle is included if required by OADP version.
- Verify endpoint hostname matches certificate SAN.

### 14.4 Unauthorized image access after restore

Symptoms:

```text
unauthorized: authentication required
pull access denied
ImagePullBackOff
```

Check ServiceAccount image pull secrets:

```bash
oc get sa default -n payments -o yaml
oc get secret -n payments
oc describe pod <pod> -n payments | grep -i pull -A5
```

Fix:

```bash
oc secrets link default <pull-secret-name> --for=pull -n payments
```

If pulling across namespaces:

```bash
oc policy add-role-to-user system:image-puller \
  system:serviceaccount:<consumer-namespace>:default \
  -n <image-source-namespace>
```

### 14.5 Restored app points to old registry

Check image pullspecs:

```bash
oc get deploy,dc,statefulset -n payments -o yaml | grep -i "image:" -A2
```

If the image points to old route:

```text
default-route-openshift-image-registry.apps.old-cluster.example.com/payments/payment-api@sha256:...
```

Options:

1. Re-tag restored ImageStream and trigger rollout.
2. Patch Deployment image to destination internal registry.
3. Use ImageStream triggers to resolve image again.
4. Mirror images manually to destination registry and update pullspec.

Example patch:

```bash
oc set image deployment/payment-api \
  payment-api=image-registry.openshift-image-registry.svc:5000/payments/payment-api@sha256:<digest> \
  -n payments
```

### 14.6 ImageStream exists but pod cannot pull

Check ImageStream status:

```bash
oc describe is payment-api -n payments
oc get istag payment-api:prod -n payments -o yaml
```

Check registry pods:

```bash
oc get pods -n openshift-image-registry
oc logs -n openshift-image-registry deploy/image-registry --tail=100
```

Check events:

```bash
oc get events -n payments --sort-by=.lastTimestamp | tail -50
```

### 14.7 Destination backup not visible

Check BSL:

```bash
oc get bsl -n openshift-adp
oc describe bsl <bsl-name> -n openshift-adp
```

Check object storage bucket/prefix:

```text
bucket: same as source
prefix: same as source backup path
credentials: read access to source backups
region/endpoint: correct
```

Check Velero logs:

```bash
oc logs -n openshift-adp deploy/velero -c velero --tail=200
```

### 14.8 Restore completes but application still fails

Do not troubleshoot only OADP. Troubleshoot application runtime too.

Check:

```bash
oc get pods -n payments
oc describe pod <pod> -n payments
oc logs <pod> -n payments --previous
oc get cm,secret,pvc,route,svc -n payments
```

Common causes:

- Missing database data
- PVC restore incomplete
- Route hostname conflict
- Secret changed or missing
- SCC/PSA blocks pod
- NetworkPolicy blocks database
- External dependency not reachable
- Image pull problem

## 15. Interview / Exam Style Questions

### Q1. Does OADP back up external images from Quay or registry.redhat.io?

No. OADP backs up Kubernetes/OpenShift resources and can protect internal images associated with OpenShift image APIs. If a workload references external registries, the restored workload still depends on those external registries being reachable and having the image available.

### Q2. Why does an app restore fail with ImagePullBackOff even when Restore is Completed?

Because Restore completion means Kubernetes/OpenShift resources were restored according to the restore operation. It does not guarantee the runtime can pull every image. The image might be missing, credentials might be missing, the pullspec might reference the old cluster registry, or the destination internal registry might be unhealthy.

### Q3. What OpenShift image resources are important for backup?

Important resources include:

```text
ImageStream
ImageStreamTag
ImageTag
Image
BuildConfig
Build
DeploymentConfig
Deployment
ServiceAccount
Secret
```

The exact set depends on how the application builds and consumes images.

### Q4. Why is ImageStream not the same as the actual image?

ImageStream is API metadata and tag history. The actual image consists of OCI/Docker manifests and layers stored in the registry backend.

### Q5. Can OADP replace etcd backup?

No. OADP is application-focused. OpenShift control-plane recovery still needs etcd backup and documented disaster recovery procedures.

### Q6. What must match for cross-cluster migration?

At minimum:

- Destination OADP can access the backup object storage.
- BackupStorageLocation name/path/credentials are correct.
- OADP/Velero/OpenShift versions are compatible.
- Destination registry is healthy.
- Required namespaces, security, and pull secrets are valid.
- Application-specific hardcoded references are handled.

### Q7. How do you validate image migration?

A migration is successful only when:

```text
Restore CR is Completed
ImageStreams exist
Image tags resolve
Pods pull images successfully
Application readiness checks pass
Routes/services work
```

### Q8. What is the safest first backup strategy for an image-producing namespace?

Start with a full namespace backup:

```yaml
spec:
  includedNamespaces:
  - <namespace>
```

Then optimize with labels or excluded resources only after restore testing.

## 16. Quick Runbook

### 16.1 Backup runbook

```bash
# 1. Check OADP
oc get pods -n openshift-adp
oc get dpa -n openshift-adp
oc get bsl -n openshift-adp

# 2. Check registry
oc get co image-registry
oc get pods -n openshift-image-registry

# 3. Check app image resources
oc get is -n payments
oc get deploy,dc -n payments

# 4. Create backup
cat <<'EOF_BACKUP' | oc apply -f -
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-full-with-images
  namespace: openshift-adp
spec:
  includedNamespaces:
  - payments
  storageLocation: default
  ttl: 720h0m0s
EOF_BACKUP

# 5. Watch backup
oc get backup payments-full-with-images -n openshift-adp -w

# 6. Check details
oc describe backup payments-full-with-images -n openshift-adp
oc -n openshift-adp exec deploy/velero -c velero -- ./velero backup describe payments-full-with-images --details
```

### 16.2 Migration restore runbook

```bash
# On destination cluster

# 1. Check OADP and BSL
oc get pods -n openshift-adp
oc get bsl -n openshift-adp

# 2. Confirm source backup is visible
oc get backup -n openshift-adp | grep payments-full-with-images

# 3. Restore
cat <<'EOF_RESTORE' | oc apply -f -
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: migrate-payments
  namespace: openshift-adp
spec:
  backupName: payments-full-with-images
  includedNamespaces:
  - payments
EOF_RESTORE

# 4. Watch restore
oc get restore migrate-payments -n openshift-adp -w

# 5. Validate images and pods
oc get is -n payments
oc get pods -n payments
oc get events -n payments --sort-by=.lastTimestamp | tail -50
```

### 16.3 Fast failure triage

```bash
oc describe restore migrate-payments -n openshift-adp
oc -n openshift-adp exec deploy/velero -c velero -- ./velero restore logs migrate-payments
oc get pods -n payments
oc describe pod <failed-pod> -n payments
oc get is -n payments
oc describe is <imagestream> -n payments
oc logs -n openshift-image-registry deploy/image-registry --tail=100
```

## Final Senior Admin Summary

For advanced OpenShift administration, remember this mental model:

```text
OADP backs up application resources.
The OpenShift plugin adds OpenShift-specific intelligence.
Internal image backup protects internal registry images tied to ImageStreams.
Image migration is backup + restore + registry validation.
Restore success is not equal to application success.
The final proof is: restored pods pull images and serve traffic.
```

For production, always test the full cycle:

```text
Backup -> Delete/test namespace -> Restore -> Validate ImageStreams -> Validate image pull -> Validate app traffic -> Document RTO/RPO
```
