## 1. Executive Summary

`VolumeSnapshotLocation` is a Velero custom resource used by OADP to describe **where persistent volume snapshots should be created or discovered** for backup and restore operations.

In simple terms:

- `BackupStorageLocation` stores Kubernetes resource backup metadata in object storage.
- `VolumeSnapshotLocation` controls the provider-specific snapshot location for persistent volume data.
- OADP installs and manages Velero on OpenShift.
- In an OADP-managed OpenShift cluster, you usually configure VSLs through the `DataProtectionApplication` custom resource, not by manually editing the generated `VolumeSnapshotLocation` object.

A VSL does **not** usually mean an S3 bucket. It usually means a cloud or storage-provider snapshot location such as:

- AWS EBS snapshot region
- Azure managed disk snapshot resource group/subscription
- Google Persistent Disk snapshot location
- Provider-specific snapshot target
- In some architectures, snapshot handling through CSI snapshot APIs and OADP Data Mover

For an advanced administrator, the most important point is this:

> A `VolumeSnapshotLocation` is not a backup by itself. It is a configuration object that Velero uses while creating or restoring persistent volume snapshots.

## 2. Where VolumeSnapshotLocation Fits in OADP

OADP is Red Hat's OpenShift API for Data Protection. It uses Velero and OpenShift-specific plugins to back up and restore application resources, persistent volumes, and in some use cases OpenShift Virtualization workloads.

High-level architecture:

```text
+--------------------------------------------------------------+
| OpenShift Cluster                                             |
|                                                              |
|  +---------------------+                                     |
|  | OADP Operator        |                                     |
|  | namespace:           |                                     |
|  | openshift-adp        |                                     |
|  +----------+----------+                                     |
|             | reconciles                                     |
|             v                                                |
|  +-----------------------------+                             |
|  | DataProtectionApplication   |                             |
|  | apiVersion:                 |                             |
|  | oadp.openshift.io/v1alpha1  |                             |
|  +-------------+---------------+                             |
|                | creates/configures                          |
|                v                                             |
|  +-------------------------+      +-------------------------+ |
|  | BackupStorageLocation   |      | VolumeSnapshotLocation  | |
|  | velero.io/v1            |      | velero.io/v1            | |
|  +-----------+-------------+      +------------+------------+ |
|              |                                 |              |
|              v                                 v              |
|  Object Storage Bucket              Native/CSI snapshot target |
|  S3 / Azure Blob / GCS / ODF         AWS EBS / Azure Disk /    |
|                                      GCP PD / CSI backend      |
|                                                              |
|  +-------------------------+                                 |
|  | Backup / Schedule /     |                                 |
|  | Restore CRs             |                                 |
|  +-------------------------+                                 |
+--------------------------------------------------------------+
```

Main OADP/Velero resources involved:

| Resource | API Group | Purpose |
|---|---|---|
| `DataProtectionApplication` | `oadp.openshift.io/v1alpha1` | Main OADP configuration object. Defines plugins, backup locations, snapshot locations, node agent, CSI/Data Mover options, and related settings. |
| `BackupStorageLocation` | `velero.io/v1` | Object storage target for Velero backup metadata, resource manifests, logs, and sometimes file-system backup data. |
| `VolumeSnapshotLocation` | `velero.io/v1` | Provider-specific location/configuration for persistent volume snapshots. |
| `Backup` | `velero.io/v1` | One-time backup request. |
| `Schedule` | `velero.io/v1` | Scheduled backup template. |
| `Restore` | `velero.io/v1` | Restore request from an existing backup. |
| `VolumeSnapshot` | `snapshot.storage.k8s.io/v1` | Kubernetes CSI snapshot object created when using CSI snapshots. |
| `VolumeSnapshotClass` | `snapshot.storage.k8s.io/v1` | Defines CSI driver and deletion policy for snapshots. |
| `VolumeSnapshotContent` | `snapshot.storage.k8s.io/v1` | Cluster-scoped object representing the actual snapshot handle in the backend storage system. |

## 3. BackupStorageLocation vs VolumeSnapshotLocation

This is one of the most important concepts for exams, interviews, and real production troubleshooting.

### BackupStorageLocation

`BackupStorageLocation` answers:

> Where should Velero store the Kubernetes backup objects and backup metadata?

Examples:

- AWS S3 bucket
- Azure Blob container
- Google Cloud Storage bucket
- ODF NooBaa / Multicloud Object Gateway bucket
- S3-compatible object store such as MinIO or Ceph RGW

It stores data like:

- Kubernetes YAML resources
- Backup metadata
- Backup logs
- Restore logs
- Plugin metadata
- File System Backup data, depending on configuration

### VolumeSnapshotLocation

`VolumeSnapshotLocation` answers:

> Which provider-specific snapshot location/configuration should Velero use for PV snapshots?

Examples:

- AWS region for EBS snapshots
- Azure resource group/subscription for managed disk snapshots
- GCP snapshot location/project
- Portworx cloud/local snapshot type
- Provider-specific snapshot configuration

It does **not** usually contain a bucket name because native snapshots are not object-store objects. For example, an AWS EBS snapshot is an EC2/EBS snapshot resource in a region, not a file stored inside your Velero S3 bucket.

### Comparison

| Area | BackupStorageLocation | VolumeSnapshotLocation |
|---|---|---|
| Short name | BSL | VSL |
| API | `backupstoragelocations.velero.io` | `volumesnapshotlocations.velero.io` |
| Stores | Backup metadata and object resources | Provider snapshot location/config |
| Common backend | Object storage | Cloud/storage snapshot service |
| Example AWS target | S3 bucket | EBS snapshot region |
| Example Azure target | Blob container | Disk snapshot resource group/subscription |
| Example GCP target | GCS bucket | Persistent disk snapshot location |
| Required for metadata backup | Yes | No, only needed for native/provider snapshots |
| Required for File System Backup | No native snapshot VSL required in a simple single-location design | Not the actual storage target for FSB |
| Configured in OADP DPA | `spec.backupLocations` | `spec.snapshotLocations` |

## 4. Why VolumeSnapshotLocation Exists

A production OpenShift backup is normally split into two broad parts:

1. **Kubernetes/OpenShift API resources**
   - Namespaces
   - Deployments
   - StatefulSets
   - ConfigMaps
   - Secrets
   - Services
   - Routes
   - PVC definitions
   - CRDs and CRs, depending on backup scope

2. **Persistent application data**
   - Database files
   - Uploaded files
   - Message queue storage
   - Application state stored on PVCs

The first part goes to object storage through `BackupStorageLocation`.

The second part can be protected by one of these methods:

- Native cloud snapshots
- CSI snapshots
- OADP Data Mover using CSI snapshots and object storage
- File System Backup using Kopia or Restic

`VolumeSnapshotLocation` is important when Velero uses a snapshot provider to create or find volume snapshots.

### Real enterprise examples

#### Example 1: AWS OpenShift cluster

- Kubernetes objects are stored in S3.
- EBS-backed PVCs are snapshotted as EBS snapshots.
- VSL tells Velero which AWS region/profile/credentials to use for EBS snapshots.

#### Example 2: Azure OpenShift cluster

- Kubernetes objects are stored in Azure Blob.
- Managed Disk PVCs are snapshotted as Azure disk snapshots.
- VSL tells Velero which resource group/subscription/options to use.

#### Example 3: OpenShift Data Foundation with CSI snapshots

- Kubernetes objects are stored in an ODF object bucket.
- CSI snapshots are created through `VolumeSnapshot`, `VolumeSnapshotContent`, and storage-driver snapshot APIs.
- In modern OADP designs, Data Mover can copy volume snapshot data to object storage for better portability.

#### Example 4: On-premises cluster without supported snapshots

- Kubernetes objects go to S3-compatible object storage.
- PVC data is backed up using File System Backup with Kopia/Restic.
- VSL may not be needed unless a supported snapshot path is configured.

## 5. Core API Object

A basic `VolumeSnapshotLocation` looks like this:

```yaml
apiVersion: velero.io/v1
kind: VolumeSnapshotLocation
metadata:
  name: aws-default
  namespace: openshift-adp
spec:
  provider: velero.io/aws
  credential:
    name: cloud-credentials
    key: cloud
  config:
    region: us-east-1
    profile: default
```

### Important fields

#### `apiVersion`

```yaml
apiVersion: velero.io/v1
```

This is a Velero API, not an OpenShift-native API group.

#### `kind`

```yaml
kind: VolumeSnapshotLocation
```

This tells Kubernetes that the object is a Velero VSL.

#### `metadata.name`

```yaml
metadata:
  name: aws-default
```

This is the logical name used by backups and schedules when selecting a snapshot location.

#### `metadata.namespace`

```yaml
metadata:
  namespace: openshift-adp
```

In OADP installations, the OADP/Velero namespace is commonly `openshift-adp`.

In upstream Velero examples, you often see `velero`. In OpenShift OADP, use the namespace where OADP deployed Velero.

#### `spec.provider`

```yaml
spec:
  provider: velero.io/aws
```

This identifies the volume snapshotter plugin/provider.

Common examples:

| Provider | Example value |
|---|---|
| AWS | `velero.io/aws` |
| Azure | `velero.io/azure` |
| GCP | `velero.io/gcp` |
| Legacy examples | `aws`, `azure`, `gcp` |

Use the value required by your OADP and plugin version.

#### `spec.credential`

```yaml
credential:
  name: cloud-credentials
  key: cloud
```

This points to a Kubernetes secret containing the provider credentials. The secret must exist in the same namespace where Velero/OADP is running.

Important points:

- `name` is the secret name.
- `key` is the key inside the secret data.
- The content format depends on the provider.
- In OpenShift, cloud credentials might be managed through cloud credential flows, STS, workload identity, or manually created secrets depending on platform and OADP version.

#### `spec.config`

```yaml
config:
  region: us-east-1
  profile: default
```

This is a map of provider-specific string key/value pairs.

Examples:

- AWS: `region`, `profile`, `enableSharedConfig`, `ebsKmsKeyId`
- Azure: `resourceGroup`, `subscriptionId`, `apiTimeout`, `incremental`, `tags`
- GCP: `snapshotLocation`, `project`, `volumeProject`, `snapshotType`

## 6. OADP DataProtectionApplication and VSL Reconciliation

In OpenShift OADP, you should normally configure VSLs in the `DataProtectionApplication` object.

Example:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: my-oadp-backup-bucket
          prefix: prod-cluster-a
        credential:
          name: cloud-credentials
          key: cloud
        config:
          region: us-east-1
  snapshotLocations:
    - name: aws-default
      velero:
        provider: aws
        credential:
          name: cloud-credentials
          key: cloud
        config:
          region: us-east-1
          profile: default
```

The OADP Operator reconciles this and creates/updates the Velero objects.

Conceptually:

```text
DataProtectionApplication.spec.snapshotLocations[]
        |
        | OADP Operator reconciliation
        v
VolumeSnapshotLocation objects in openshift-adp namespace
```

### Why this matters

If you manually edit the generated VSL object, the OADP Operator can revert your changes during reconciliation. Treat the DPA as the source of truth.

Correct workflow:

```bash
oc edit dpa dpa-sample -n openshift-adp
```

or:

```bash
oc patch dpa dpa-sample -n openshift-adp --type merge -p '<patch>'
```

Then verify:

```bash
oc get volumesnapshotlocations.velero.io -n openshift-adp
oc describe volumesnapshotlocation aws-default -n openshift-adp
```

## 7. Provider-Specific Behavior

`VolumeSnapshotLocation` is provider-specific. Do not assume the same keys work for all cloud providers.

### AWS behavior

For AWS EBS snapshots, VSL commonly includes:

```yaml
spec:
  provider: velero.io/aws
  credential:
    name: cloud-credentials
    key: cloud
  config:
    region: us-east-1
    profile: default
```

Important AWS considerations:

- The VSL region must match where the EBS volumes exist.
- Snapshot permissions must allow creating, describing, tagging, and deleting EBS snapshots depending on backup retention lifecycle.
- If using KMS-encrypted EBS volumes, the restore path must have access to the required KMS key.
- For cross-account or cross-region DR, native EBS snapshot copy/sharing must be designed separately; a single Velero backup does not magically create snapshots in many regions.
- On ROSA/STS or AWS STS clusters, credentials and IAM role trust configuration must be correct.

Typical AWS IAM actions involved may include:

```text
ec2:CreateSnapshot
ec2:DeleteSnapshot
ec2:DescribeSnapshots
ec2:DescribeVolumes
ec2:CreateTags
ec2:DescribeTags
ec2:CreateVolume
ec2:DeleteVolume
ec2:AttachVolume
ec2:DetachVolume
kms:Decrypt
kms:Encrypt
kms:CreateGrant
kms:DescribeKey
```

Exact IAM requirements depend on plugin version, encryption, restore mode, and cluster installation type.

### Azure behavior

For Azure managed disk snapshots, VSL may look like:

```yaml
apiVersion: velero.io/v1
kind: VolumeSnapshotLocation
metadata:
  name: azure-default
  namespace: openshift-adp
spec:
  provider: velero.io/azure
  config:
    resourceGroup: my-snapshot-rg
    subscriptionId: my-subscription-id
    apiTimeout: 5m
    incremental: "true"
    tags: environment=prod,owner=platform
```

Important Azure considerations:

- `resourceGroup` can be used to store snapshots in a specific resource group.
- `subscriptionId` can be used when snapshots are stored in a different subscription, depending on plugin support and permissions.
- Incremental snapshots can reduce cost and time, but restore behavior and retention policy must be understood.
- Azure identity permissions must cover disk snapshot creation, read, delete, and disk restore operations.

### GCP behavior

For Google Persistent Disk snapshots, VSL may look like:

```yaml
apiVersion: velero.io/v1
kind: VolumeSnapshotLocation
metadata:
  name: gcp-default
  namespace: openshift-adp
spec:
  provider: velero.io/gcp
  config:
    snapshotLocation: us-central1
    project: my-gcp-project
    snapshotType: STANDARD
```

Important GCP considerations:

- `snapshotLocation` controls where snapshots are stored.
- `project` and `volumeProject` may be relevant for cross-project restore or separation of responsibilities.
- IAM permissions must cover compute snapshots and disks.

### OpenShift Data Foundation / Ceph / CSI behavior

For ODF/Ceph-based CSI snapshots:

- The storage class must support snapshots.
- A matching `VolumeSnapshotClass` must exist.
- Velero/OADP CSI plugin support must be configured.
- Snapshot data may remain in the storage backend unless OADP Data Mover is configured to copy data to object storage.

Key objects:

```bash
oc get storageclass
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

Example `VolumeSnapshotClass`:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ocs-storagecluster-rbdplugin-snapclass
  labels:
    velero.io/csi-volumesnapshot-class: "true"
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Delete
```

Important label:

```yaml
velero.io/csi-volumesnapshot-class: "true"
```

This label helps Velero identify which `VolumeSnapshotClass` to use for CSI snapshots.

## 8. CSI Snapshots vs Native Cloud Snapshots vs File System Backup

Advanced OpenShift administrators must understand this difference clearly.

### Native cloud snapshot

Native cloud snapshot means Velero talks to a provider-specific snapshotter plugin.

Example:

```text
Velero -> AWS plugin -> EBS snapshot API
Velero -> Azure plugin -> Managed disk snapshot API
Velero -> GCP plugin -> Compute snapshot API
```

VSL is very important here.

### CSI snapshot

CSI snapshot means Kubernetes snapshot APIs are used:

```text
Velero/OADP -> VolumeSnapshot CR -> CSI snapshot controller -> CSI driver -> backend snapshot
```

Objects involved:

- `VolumeSnapshot`
- `VolumeSnapshotClass`
- `VolumeSnapshotContent`
- CSI driver
- External snapshotter/controller components

In CSI-based designs, the VSL role can be less obvious because the primary location is driven by CSI driver and storage backend. However, OADP/Velero configuration and backup selection still need to match the installed plugins and feature set.

### File System Backup with Kopia/Restic

File System Backup means data is read from the mounted filesystem and copied to the backup object store.

```text
Node agent -> reads files from mounted PVC -> sends data to object storage
```

This is useful when:

- Native/CSI snapshots are not available.
- The storage backend does not support snapshots.
- You need file-level backup behavior.
- You are backing up NFS or unsupported snapshot storage.

Trade-offs:

| Method | Speed | Portability | App consistency | Storage dependency | VSL needed? |
|---|---:|---:|---:|---:|---:|
| Native cloud snapshot | Fast | Medium | Crash-consistent unless hooks used | Strong | Yes |
| CSI snapshot | Fast | Medium | Crash-consistent unless hooks used | Strong | Depends on design |
| CSI snapshot + Data Mover | Medium | Better | Crash-consistent unless hooks used | Medium | Depends on design |
| File System Backup | Slower | High | Can be improved with hooks | Lower | Usually no |

### Crash-consistent vs application-consistent

A volume snapshot is usually crash-consistent, not application-consistent.

For databases, use backup hooks or application-native backup steps:

- Quiesce writes
- Flush database buffers
- Lock tables if appropriate
- Run pre-backup hook
- Run post-backup hook
- Validate restore, not only backup success

Example PostgreSQL safer pattern:

```text
1. Run pg_start_backup or equivalent logical/native process where appropriate.
2. Snapshot or backup volume.
3. Run pg_stop_backup or complete WAL archive workflow.
4. Validate restore into a test namespace.
```

Do not treat storage snapshots as a replacement for database-consistent backup design.

## 9. End-to-End Backup Flow

### With native provider snapshot

```text
1. Admin creates/updates DPA with backupLocations and snapshotLocations.
2. OADP Operator deploys Velero and plugins.
3. OADP Operator creates BSL and VSL objects.
4. Admin creates Backup or Schedule CR.
5. Velero scans included namespaces/resources.
6. Velero exports Kubernetes/OpenShift objects to object storage using BSL.
7. For PVCs/PVs eligible for snapshots, Velero selects the matching VSL.
8. Snapshotter plugin creates provider snapshot.
9. Velero records snapshot metadata in the backup.
10. Backup phase becomes Completed or PartiallyFailed/Failed.
```

Backup object example:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-prod-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  storageLocation: default
  volumeSnapshotLocations:
    - aws-default
  ttl: 720h0m0s
```

### With CSI snapshot

```text
1. CSI driver supports snapshotting.
2. VolumeSnapshotClass exists and is usable.
3. Velero/OADP CSI plugin is installed/configured.
4. Backup starts.
5. Velero creates VolumeSnapshot objects for PVCs.
6. CSI snapshot controller binds VolumeSnapshot to VolumeSnapshotContent.
7. Backend storage creates snapshot.
8. Velero records snapshot handles and metadata.
9. Optional Data Mover copies snapshot data to object storage.
```

### With File System Backup

```text
1. Node agent runs on worker nodes.
2. Backup specifies filesystem backup behavior or defaults use FSB.
3. Node agent reads mounted PVC files.
4. Data is uploaded to object storage.
5. Backup metadata is stored in BSL.
```

## 10. End-to-End Restore Flow

### Native snapshot restore

```text
1. Admin creates Restore CR referencing a backup.
2. Velero reads backup metadata from BSL.
3. Velero recreates Kubernetes resources.
4. For PVCs/PVs backed by snapshots, Velero asks provider plugin to create volumes from snapshots.
5. PV/PVC binding occurs.
6. Workloads start with restored data.
```

Restore example:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: app-prod-restore-001
  namespace: openshift-adp
spec:
  backupName: app-prod-backup-001
  includedNamespaces:
    - app-prod
```

### CSI restore

CSI restore generally recreates PVCs from snapshot sources. Depending on the CSI driver and restore method, the restored PVC references a data source like `VolumeSnapshot`.

Important checks:

```bash
oc get pvc -n app-prod
oc describe pvc <pvc-name> -n app-prod
oc get volumesnapshot -n app-prod
oc get volumesnapshotcontent
oc describe restore app-prod-restore-001 -n openshift-adp
```

### Restore into another namespace

You can restore into a different namespace using namespace mapping:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: app-restore-to-test
  namespace: openshift-adp
spec:
  backupName: app-prod-backup-001
  namespaceMapping:
    app-prod: app-test
```

Be careful with:

- Routes and hostnames
- PVC storage class availability
- Secrets and service accounts
- NetworkPolicies
- External dependencies
- Database connection strings

```yaml
    - app-prod
  storageLocation: default
  defaultVolumesToFsBackup: true
  ttl: 168h0m0s
```

In this example, data is copied through the node agent/Kopia/Restic path to the backup object storage. A native snapshot VSL is not the storage target for the volume data.

## 14. Troubleshooting Deep Dive

### Problem 1: Backup fails with `VolumeSnapshotLocation not found`

Example error:

```text
volumesnapshotlocations.velero.io "aws-east" not found
```

Possible causes:

- Backup references wrong VSL name.
- VSL was not created by DPA reconciliation.
- VSL exists in a different namespace.
- OADP Operator failed to reconcile DPA.

Commands:

```bash
oc get volumesnapshotlocations.velero.io -n openshift-adp
oc get backup <backup-name> -n openshift-adp -o yaml | grep -A5 volumeSnapshotLocations
oc describe dpa <dpa-name> -n openshift-adp
oc logs deploy/velero -n openshift-adp | grep -i snapshot
```

Fix:

- Correct `spec.volumeSnapshotLocations` in Backup/Schedule.
- Correct `spec.snapshotLocations` in DPA.
- Wait for OADP reconciliation.
- Check OADP Operator logs.

---

### Problem 2: Backup fails because provider plugin is missing

Example symptoms:

```text
error getting volume snapshotter for provider
plugin not found
no volume snapshotter named velero.io/aws
```

Possible causes:

- AWS/Azure/GCP/CSI plugin not enabled in DPA.
- Wrong provider string in VSL.
- Velero pod did not restart after DPA change.
- Plugin image pull problem.

Commands:

```bash
oc get dpa <dpa-name> -n openshift-adp -o yaml
oc logs deploy/velero -n openshift-adp | grep -i plugin
oc get pods -n openshift-adp
oc describe pod -l deploy=velero -n openshift-adp
```

Fix:

- Add correct plugin in DPA.
- Use provider value supported by your OADP/plugin version.
- Check image pull secrets and disconnected mirror configuration.

---

### Problem 3: Snapshot region mismatch

Example symptoms:

```text
volume is in region us-east-1 but snapshot location configured for us-west-2
snapshot creation failed
```

Root cause:

The VSL is configured for a region where the provider cannot create snapshots for that volume.

For AWS/Azure, native snapshots are constrained by provider regional/location rules.

Commands:

```bash
oc get pv <pv-name> -o yaml
oc describe pv <pv-name>
oc get volumesnapshotlocation <vsl-name> -n openshift-adp -o yaml
```

AWS check:

```bash
aws ec2 describe-volumes --volume-ids <vol-id> --region <region>
```

Fix:

- Configure VSL in the same region/location as the volumes.
- Use different backups/schedules for different regions.
- For DR to another region, design a separate snapshot copy or Data Mover/object-storage strategy.

---

### Problem 4: Permission denied creating snapshots

Example symptoms:

```text
UnauthorizedOperation
AuthorizationFailed
AccessDenied
permission denied while creating snapshot
```

Possible causes:

- Missing IAM/cloud role permissions.
- Wrong secret content.
- Wrong profile in credentials file.
- Expired credentials.
- STS trust policy issue.
- KMS key permission issue.

Commands:

```bash
oc get secret cloud-credentials -n openshift-adp -o yaml
oc logs deploy/velero -n openshift-adp | grep -i -E 'denied|unauthorized|forbidden|credential|kms'
```

Fix:

- Update cloud role policy.
- Correct credential secret.
- Verify STS/workload identity binding.
- Add KMS grant/permissions where encrypted volumes are involved.

---

### Problem 5: CSI snapshot not created

Symptoms:

```text
no applicable volumesnapshotclass found
failed to create volumesnapshot
snapshot controller error
```

Possible causes:

- No `VolumeSnapshotClass` for the CSI driver.
- Missing Velero label on `VolumeSnapshotClass`.
- CSI driver does not support snapshots.
- Snapshot controller is not healthy.
- PVC uses a storage class that does not support snapshots.

Commands:

```bash
oc get volumesnapshotclass
oc describe volumesnapshotclass <class-name>
oc get volumesnapshot -A
oc get volumesnapshotcontent
oc describe pvc <pvc-name> -n <namespace>
oc get csidriver
```

Fix:

- Create or correct `VolumeSnapshotClass`.
- Add label:

```bash
oc label volumesnapshotclass <class-name> velero.io/csi-volumesnapshot-class=true
```

- Confirm CSI driver snapshot support.
- Confirm OADP CSI plugin configuration.

---

### Problem 6: Backup completes but PVC data is not restored

Possible causes:

- Backup included PVC object but did not snapshot/copy data.
- VSL not specified when multiple VSLs exist.
- Snapshot failed but backup phase is `PartiallyFailed`.
- PVC was excluded by resource filter.
- File System Backup not enabled.
- CSI snapshot was not ready.

Commands:

```bash
velero backup describe <backup-name> --details
velero backup logs <backup-name>
oc describe backup <backup-name> -n openshift-adp
oc get volumesnapshot -A
oc get podvolumebackup -A
oc get dataupload -A
```

Fix:

- Review backup details for volume snapshot section.
- Enable correct snapshot or File System Backup mechanism.
- Correct backup filters.
- Correct VSL selection.
- Test restore from a fresh backup.

---

### Problem 7: DPA configured but VSL not created

Possible causes:

- DPA YAML indentation error.
- Invalid provider configuration.
- Missing secret.
- OADP Operator reconciliation failure.
- CRD/API version mismatch.

Commands:

```bash
oc describe dpa <dpa-name> -n openshift-adp
oc get events -n openshift-adp --sort-by=.lastTimestamp
oc logs deploy/oadp-operator-controller-manager -n openshift-adp
oc get dpa <dpa-name> -n openshift-adp -o yaml
```

Fix:

- Fix DPA syntax.
- Fix `spec.snapshotLocations` structure.
- Confirm secret and plugin.
- Confirm OADP version supports your desired configuration.

---

### Problem 8: Backup references multiple VSLs incorrectly

When multiple VSLs exist for the same provider, Velero may require you to specify a valid VSL in the backup/schedule. If you have multiple VSLs, be explicit.

Example:

```yaml
spec:
  volumeSnapshotLocations:
    - aws-east-primary
```

Check:

```bash
oc get backup <backup-name> -n openshift-adp -o yaml
oc get schedule <schedule-name> -n openshift-adp -o yaml
```

Fix:

- Update Backup/Schedule template with the intended VSL.
- Avoid ambiguous naming such as `default`, `default2`, `test1` in production.

---

### Problem 9: Snapshots exist but backup deletion does not remove them

Possible causes:

- Snapshot deletion policy retains snapshots.
- Cloud permissions allow create but not delete.
- Velero backup deletion did not complete.
- CSI `VolumeSnapshotClass.deletionPolicy` is `Retain`.

Commands:

```bash
oc get deletebackuprequest -n openshift-adp
velero backup delete <backup-name>
velero backup describe <backup-name>
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

Cloud checks:

```bash
aws ec2 describe-snapshots --owner-ids self --region us-east-1
az snapshot list -g <resource-group>
gcloud compute snapshots list
```

Fix:

- Decide retention policy intentionally.
- Grant delete permissions if automated cleanup is required.
- Clean orphaned snapshots carefully after validating they are no longer needed.

---

### Problem 10: Restore fails due to KMS encryption

Symptoms:

```text
not authorized to use KMS key
access denied for encrypted snapshot
failed to create volume from snapshot
```

Root cause:

The restore identity cannot decrypt the snapshot or create an encrypted volume using the required key.

Fix:

- Add KMS permissions.
- Share/copy snapshot with appropriate encryption settings.
- Use a VSL config such as `ebsKmsKeyId` where supported and appropriate.
- Validate restore in DR account/region, not only production account.

## 15. Security and RBAC Considerations

### Kubernetes RBAC

Velero needs broad cluster access because it must read and recreate many resource types.

Check:

```bash
oc get clusterrole | grep -i velero
oc get clusterrolebinding | grep -i velero
oc get sa -n openshift-adp
```

### Cloud credentials

Cloud credentials for VSL can create and restore volume snapshots. Treat them as sensitive.

Best practices:

- Use least privilege.
- Use separate credentials for backup metadata and volume snapshots where possible.
- Rotate credentials.
- Avoid static long-lived keys where workload identity or STS is supported.
- Restrict snapshot permissions to required regions/resource groups/projects.
- Monitor snapshot creation/deletion through cloud audit logs.

### Secret handling

Do not casually print secrets:

```bash
oc get secret cloud-credentials -n openshift-adp -o yaml
```

Only decode when necessary:

```bash
oc extract secret/cloud-credentials -n openshift-adp --to=-
```

### Snapshot data sensitivity

Snapshots can contain full application data, including:

- Database records
- User uploads
- Secrets stored inside application data directories
- Logs
- Personally identifiable information

Therefore:

- Encrypt snapshots.
- Restrict snapshot sharing.
- Tag snapshots for ownership and retention.
- Monitor snapshot access.
- Include snapshots in compliance and data retention policy.

## 16. Performance and Scalability Considerations

### Snapshot speed

Native and CSI snapshots are usually faster than File System Backup because they operate at storage backend level.

However, actual time depends on:

- Storage backend snapshot implementation
- Volume size
- Change rate
- Provider API throttling
- Number of PVCs
- Snapshot controller performance
- Cloud quota limits

### Large clusters

For large OpenShift clusters:

- Avoid backing up everything in one monolithic backup unless required.
- Use namespace/application-aligned schedules.
- Stagger backup schedules.
- Separate critical workloads from low-priority workloads.
- Monitor object storage and snapshot quota usage.
- Test backup and restore under load.

### Provider throttling

Cloud providers may throttle API calls. Symptoms include:

```text
RequestLimitExceeded
TooManyRequests
rate exceeded
context deadline exceeded
```

Mitigation:

- Stagger schedules.
- Reduce concurrency if supported.
- Tune OADP/Velero timeouts if needed.
- Increase provider quotas where possible.
- Avoid mass snapshot operations during peak hours.

### Database consistency

Storage-level snapshots are fast but not always application-consistent.

Use hooks for:

- PostgreSQL
- MySQL/MariaDB
- MongoDB
- Elasticsearch/OpenSearch
- Kafka/Zookeeper/KRaft
- Redis with AOF/RDB considerations

Example Velero backup hook annotation pattern:

```yaml
metadata:
  annotations:
    pre.hook.backup.velero.io/command: '["/bin/sh", "-c", "sync"]'
    post.hook.backup.velero.io/command: '["/bin/sh", "-c", "echo backup complete"]'
```

For real databases, use database-specific safe commands rather than only `sync`.

## 17. Disaster Recovery Design Patterns

### Pattern 1: Same-cluster operational restore

Use case:

- Accidental namespace deletion
- Bad deployment
- Data corruption caught quickly

Design:

- BSL points to object storage.
- VSL points to same region/storage backend.
- Restore into same cluster or alternate namespace.

Pros:

- Simple
- Fast

Cons:

- Does not protect against full region/storage failure if snapshots remain in same backend.

### Pattern 2: Same-region cluster rebuild

Use case:

- Cluster destroyed, infrastructure still available

Design:

- Reinstall OpenShift.
- Install OADP.
- Configure same BSL and VSL.
- Restore applications.

Critical requirement:

- Cloud credentials must access existing object storage and snapshots.

### Pattern 3: Cross-region DR

Use case:

- Region outage

Design options:

1. Copy object storage backups to another region.
2. Copy native snapshots to another region using cloud-native snapshot copy.
3. Use Data Mover/File System Backup for more portable data movement to object storage.
4. Regularly test restore into DR cluster.

Important:

A VSL configured for one region does not automatically create volume snapshots in multiple regions.

### Pattern 4: Multi-provider/multi-storage cluster

Use case:

- Cluster has different storage backends.
- Some PVCs use EBS, some use Portworx, some use CSI-backed Ceph.

Design:

- Configure one VSL per provider/location as required.
- Use explicit backup selection.
- Test each storage class separately.

### Pattern 5: GitOps-managed OADP

Use case:

- Enterprise wants repeatable OADP configuration.

Design:

- Store DPA YAML in Git.
- Store SealedSecret/ExternalSecret references for credentials.
- Avoid manual edits to generated Velero objects.
- Manage Backup/Schedule CRs as GitOps resources.

## 18. Common Mistakes

### Mistake 1: Thinking VSL is an S3 bucket

Wrong assumption:

```text
VSL stores snapshots in S3.
```

Correct understanding:

```text
BSL stores backup metadata in object storage. VSL tells Velero where/how to create provider volume snapshots.
```

### Mistake 2: Editing generated VSL directly

Wrong:

```bash
oc edit volumesnapshotlocation aws-east -n openshift-adp
```

Correct:

```bash
oc edit dpa dpa-sample -n openshift-adp
```

Then let OADP reconcile.

### Mistake 3: Region mismatch

Wrong:

```yaml
snapshotLocations:
  - name: aws-west
    velero:
      config:
        region: us-west-2
```

while PVCs are backed by EBS volumes in `us-east-1`.

Correct:

Configure the VSL for the same region where the volumes exist, unless using a supported copy/migration workflow.

### Mistake 4: No restore test

A backup that has not been restored is only an assumption.

Production rule:

```text
Backup success + restore success + application validation = real protection
```

### Mistake 5: Ignoring encrypted volume restore

Encrypted snapshots require key access on restore.

Validate:

- Same account restore
- Cross-account restore
- Cross-region restore
- DR cluster restore

### Mistake 6: Backing up database PVCs without consistency plan

A crash-consistent snapshot may not be enough for business-critical databases.

Use:

- Database-native backup
- WAL/binlog/archive strategy
- Velero hooks
- Application quiescing
- Restore validation

### Mistake 7: Multiple VSLs but backup does not specify one

When multiple VSLs exist, be explicit:

```yaml
volumeSnapshotLocations:
  - aws-east-primary
```

### Mistake 8: Missing CSI `VolumeSnapshotClass`

For CSI snapshots, the storage layer must provide a usable `VolumeSnapshotClass`.

Check:

```bash
oc get volumesnapshotclass
```

## 19. Production Best Practices

### Naming standards

Use names that show provider, region, and purpose.

Good:

```text
aws-use1-prod
aws-use1-dr-creds
azure-eastus-prod
odf-rbd-prod
```

Bad:

```text
default
snapshot1
test
new-vsl
```

### Use DPA as source of truth

Manage this:

```yaml
kind: DataProtectionApplication
spec:
  snapshotLocations:
```

Do not manually manage generated objects unless you intentionally run unsupported/custom workflows.

### Separate backup and snapshot credentials

Where supported:

- BSL credentials: object storage access
- VSL credentials: volume snapshot access

This improves least privilege and auditability.

### Tag snapshots

Use provider tagging where supported.

Example Azure:

```yaml
config:
  tags: environment=prod,cluster=ocp-prod-a,owner=platform
```

For AWS, tagging support depends on plugin behavior and permissions.

### Monitor backups

Monitor:

- Backup success/failure
- Schedule execution
- Snapshot creation failure
- Velero pod restarts
- Object storage availability
- Cloud snapshot quota
- Snapshot age and cost

Useful commands:

```bash
oc get backup -n openshift-adp
oc get schedule -n openshift-adp
oc get restores -n openshift-adp
oc logs deploy/velero -n openshift-adp
```

### Define RPO and RTO

RPO: How much data can you lose?  
RTO: How fast must you restore?

Example:

| Workload | RPO | RTO | Backup method |
|---|---:|---:|---|
| Critical DB | 15 min | 1 hour | DB-native + OADP snapshots |
| App config | 24 hours | 2 hours | OADP scheduled backup |
| Dev namespace | 24 hours | Best effort | FSB or namespace backup |

### Test restores regularly

Minimum enterprise test pattern:

- Daily automated backup check
- Weekly restore into test namespace
- Monthly DR restore into separate cluster
- Quarterly full application recovery exercise

### Keep provider quotas in mind

Track:

- Number of snapshots
- Snapshot storage usage
- API rate limits
- Object storage usage
- Lifecycle policy effects

### Use lifecycle policies carefully

Cloud lifecycle policies can delete snapshots or object storage data unexpectedly.

Coordinate:

- Velero TTL
- Object storage lifecycle rules
- Cloud snapshot retention policies
- Compliance retention requirements

## 20. Interview-Level Questions and Answers

### Q1. What is `VolumeSnapshotLocation` in OADP?

`VolumeSnapshotLocation` is a Velero custom resource used by OADP to define provider-specific configuration for persistent volume snapshots. It tells Velero which snapshot provider/location/credentials/config to use when backing up PV data through snapshot mechanisms.

---

### Q2. Is `VolumeSnapshotLocation` the same as `BackupStorageLocation`?

No. `BackupStorageLocation` points to object storage for backup metadata and Kubernetes resource manifests. `VolumeSnapshotLocation` points to provider-specific snapshot configuration for persistent volume snapshots.

---

### Q3. Does `VolumeSnapshotLocation` store data in S3?

Usually no. S3/object storage is used by `BackupStorageLocation`. A VSL for AWS normally points to an AWS region for EBS snapshots. The EBS snapshot is an AWS EBS snapshot resource, not an object inside the S3 backup bucket.

---

### Q4. In OADP, should I create VSL manually?

Normally no. In OADP, configure `spec.snapshotLocations` in the `DataProtectionApplication` CR. The OADP Operator reconciles and creates the corresponding Velero `VolumeSnapshotLocation` objects.

---

### Q5. Why does my backup fail when VSL region is different from the PV region?

Because providers such as AWS and Azure restrict where volume snapshots can be created relative to the source volume. If the volume is in `us-east-1`, configuring a VSL for `us-west-2` can cause snapshot creation failure.

---

### Q6. What happens if multiple VSLs exist?

If multiple VSLs exist, especially for the same provider, you should explicitly specify the intended VSL in the Backup or Schedule. Otherwise Velero may not know which one to use or may use an unintended default.

---

### Q7. How do I check which VSL a backup used?

Use:

```bash
oc get backup <backup-name> -n openshift-adp -o yaml
velero backup describe <backup-name> --details
```

Look for:

```yaml
spec:
  volumeSnapshotLocations:
```

and backup details showing volume snapshots.

---

### Q8. What is the relationship between VSL and CSI snapshots?

CSI snapshots are Kubernetes-native snapshot objects handled by CSI drivers. VSL is a Velero snapshot-location abstraction mostly associated with provider snapshotters. In OADP environments using CSI snapshots and Data Mover, you must understand both the Velero configuration and the CSI snapshot objects because the actual snapshot may be represented by `VolumeSnapshot`, `VolumeSnapshotContent`, and storage backend handles.

---

### Q9. What do you check when VSL backup fails?

Check:

1. DPA `spec.snapshotLocations`
2. Generated VSL object
3. Provider plugin installed
4. Cloud credentials secret
5. Region/resource group/project settings
6. Cloud IAM permissions
7. Velero logs
8. Backup logs
9. PVC/PV storage backend
10. CSI snapshot objects if using CSI

Commands:

```bash
oc describe dpa <dpa-name> -n openshift-adp
oc get volumesnapshotlocation -n openshift-adp -o yaml
oc logs deploy/velero -n openshift-adp
velero backup logs <backup-name>
```

---

### Q10. Can a single Velero backup send one snapshot to multiple VSLs?

No, not as a single snapshot duplicated to multiple VSLs. For redundancy, use multiple schedules/backups with different locations, cloud-native snapshot copy, replicated object storage, or Data Mover/object storage strategies.

## Final Practical Summary

For a senior OpenShift administrator, `VolumeSnapshotLocation` is not just another YAML file. It is the bridge between OADP/Velero backup logic and the underlying storage snapshot system. When backup or restore fails, the root cause is often not the Backup CR itself, but one of these hidden dependencies:

- Wrong VSL provider
