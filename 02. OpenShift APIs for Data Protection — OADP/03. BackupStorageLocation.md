## 1. Executive Summary

`BackupStorageLocation` is the Velero custom resource that tells OADP/Velero **where backup metadata and backup artifacts are stored**.

In OpenShift APIs for Data Protection, you normally do not start by manually creating a raw Velero `BackupStorageLocation`. Instead, you configure `spec.backupLocations` inside the OADP `DataProtectionApplication` custom resource. The OADP Operator reconciles that configuration and creates or manages the Velero `BackupStorageLocation` object in the OADP namespace, usually `openshift-adp`.

At production level, a `BackupStorageLocation` is not just “an S3 bucket”. It is a complete storage contract between OpenShift, OADP, Velero, object storage, credentials, TLS trust, plugin configuration, backup synchronization behavior, and disaster recovery strategy.

A good administrator must understand:

- Which object store bucket or prefix stores backups.
- Which Velero provider plugin handles the object store.
- Which secret is used for credentials.
- Whether the location is default or non-default.
- Whether the location is writable or restore-only.
- Whether object storage is reachable from the Velero pod.
- Whether TLS certificates are trusted.
- How backups are synchronized across clusters.
- How this location relates to persistent volume snapshots, file-system backups, and CSI data movement.

Simple definition:

```text
BackupStorageLocation = object storage target used by Velero/OADP to store backup metadata, logs, resource archives, and sometimes volume data.
```

Production definition:

```text
BackupStorageLocation is the object-store endpoint, bucket/prefix, credential, provider-plugin configuration, TLS trust model, and access mode that allows OADP/Velero to persist, discover, validate, synchronize, and restore backup content across OpenShift clusters.
```

## 2. Where BackupStorageLocation Fits in OADP Architecture

OADP is Red Hat's OpenShift data protection operator built around Velero. It provides Kubernetes/OpenShift APIs for backup, restore, schedules, hooks, snapshots, and data movement.

High-level architecture:

```text
User / Admin
   |
   | creates DataProtectionApplication, Backup, Restore, Schedule
   v
OADP Operator
   |
   | reconciles Velero deployment, plugins, secrets, BSL, VSL, node-agent
   v
Velero Server Pod in openshift-adp
   |
   | talks to Kubernetes API, OpenShift APIs, object storage, snapshot APIs
   v
BackupStorageLocation  ---> Object storage bucket/prefix
VolumeSnapshotLocation ---> Cloud/native snapshot provider region/project/resource group
Node Agent / Kopia / Restic ---> File-system volume data movement to object store
```

`BackupStorageLocation` sits between Velero and object storage.

When a backup is created, Velero collects Kubernetes and OpenShift objects, runs backup item actions from plugins, captures metadata, writes logs, and uploads the backup archive to the configured object storage location.

In OpenShift, the common namespace is:

```bash
openshift-adp
```

Common resources:

```bash
oc get dpa -n openshift-adp
oc get backupstoragelocation -n openshift-adp
oc get volumesnapshotlocation -n openshift-adp
oc get backup -n openshift-adp
oc get restore -n openshift-adp
oc get schedule -n openshift-adp
oc get pods -n openshift-adp
```

Architecture with object storage:

```text
+---------------------------------------------------------------+
| OpenShift Cluster                                              |
|                                                               |
|  +---------------------+       +---------------------------+   |
|  | OADP Operator       | ----> | DataProtectionApplication |   |
|  +---------------------+       +---------------------------+   |
|             |                                                 |
|             v                                                 |
|  +---------------------+       +---------------------------+   |
|  | Velero Deployment   | ----> | BackupStorageLocation     |   |
```

## 3. BackupStorageLocation vs VolumeSnapshotLocation

Many administrators confuse `BackupStorageLocation` and `VolumeSnapshotLocation`. They are different.

| Area | BackupStorageLocation | VolumeSnapshotLocation |
|---|---|---|
| Short name | BSL | VSL |
| Main purpose | Stores backup archive and metadata in object storage | Defines where provider-native volume snapshots are created |
| Storage type | Object storage bucket/prefix | Cloud/block storage snapshot service |
| Example backend | AWS S3, MinIO, NooBaa, Ceph RGW, Azure Blob, GCS | AWS EBS snapshot region, Azure disk snapshot resource group, etc. |
| Stores Kubernetes objects | Yes | No |
| Stores OpenShift objects | Yes | No |
| Stores backup logs | Yes | No |
| Stores file-system backup data | Yes, when using FSB/Kopia/Restic | No |
| Required for OADP backups | Yes | Only needed for native snapshot-based volume backup |
| Used during restore | Yes | Sometimes, depending on PV restore method |

A backup always needs a `BackupStorageLocation` because Velero needs a place to write backup metadata.

A backup does not always need a `VolumeSnapshotLocation`. For example:

- CSI snapshots use `VolumeSnapshotClass` and CSI snapshot APIs.
- File System Backup writes volume data into object storage through the selected `BackupStorageLocation`.
- Stateless application backups need only object storage.

Important mental model:

```text
BSL = where the backup object/metadata/archive goes.
VSL = where native disk snapshots are created.
```

For a stateful application:

```text
Deployment/Service/Route/ConfigMap/Secret/PVC metadata ---> BSL
PV data by FSB/Kopia/Restic ------------------------------> BSL
PV data by CSI/native snapshots --------------------------> snapshot backend; metadata still in BSL
```

## 4. What Actually Goes into a BackupStorageLocation

The `BackupStorageLocation` stores Velero backup artifacts. Depending on plugins and backup method, this can include:

1. Kubernetes resource metadata
   - Deployments
   - StatefulSets
   - DaemonSets
   - Services
   - ConfigMaps
   - Secrets
   - PVCs
   - ServiceAccounts
   - Roles and RoleBindings
   - Custom resources

2. OpenShift-specific resources
   - Projects / namespaces
   - Routes
   - DeploymentConfigs
   - BuildConfigs
   - ImageStreams
   - SecurityContextConstraints references or related objects, depending on backup scope
   - OpenShift Virtualization objects if kubevirt plugin is enabled

3. Velero backup metadata
   - Backup object information
   - Included namespaces
   - Included/excluded resources
   - Label selectors
   - Hooks
   - Warnings and errors
   - Backup phase

4. Logs and result files
   - Backup logs
   - Restore logs
   - Backup item operation details
   - Restore item operation details

5. Persistent volume data when using File System Backup
   - Kopia or Restic repository data
   - Repository metadata
   - File-level backup data

6. Snapshot metadata when using snapshot-based backup
   - Snapshot references
   - Volume snapshot metadata
   - Persistent volume restore mapping information

A typical bucket layout may look similar to this, depending on Velero version and plugins:

```text
s3://my-oadp-bucket/velero/
  backups/
    app-backup-20260703/
      app-backup-20260703.tar.gz
      app-backup-20260703-logs.gz
      app-backup-20260703-results.gz
      app-backup-20260703-resource-list.json.gz
      velero-backup.json
  restores/
    restore-app-20260703/
      restore-app-20260703-logs.gz
      restore-app-20260703-results.gz
  kopia/
    repository data...
  restic/
    repository data...
```

The exact object names can vary by Velero/OADP version and feature set, but the concept is stable: **BSL holds backup discoverability and restore source of truth**.

## 5. OADP Resource Flow: DPA to Velero BSL

In OADP, the most common flow is:

```text
Admin creates DataProtectionApplication
      |
      v
OADP Operator reads spec.backupLocations
      |
      v
OADP Operator creates/updates Velero BackupStorageLocation
      |
      v
Velero validates the object store
      |
      v
Backups use the BSL
```

Example:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: my-oadp-bucket
          prefix: velero
        config:
          region: us-east-1
          s3ForcePathStyle: "true"
          s3Url: https://s3-openshift-storage.apps.example.com
        credential:
          name: cloud-credentials
          key: cloud
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
```

The OADP Operator reconciles this into a Velero object similar to:

```yaml
apiVersion: velero.io/v1
kind: BackupStorageLocation
metadata:
  name: default
  namespace: openshift-adp
spec:
  provider: aws
  objectStorage:
    bucket: my-oadp-bucket
    prefix: velero
  credential:
    name: cloud-credentials
    key: cloud
  config:
    region: us-east-1
    s3ForcePathStyle: "true"
    s3Url: https://s3-openshift-storage.apps.example.com
```

Important:

If a BSL is created by the `DataProtectionApplication`, treat the DPA as the source of truth. Do not manually edit the generated BSL unless you intentionally manage it outside the DPA scope.

Wrong production habit:

```bash
oc edit backupstoragelocation default -n openshift-adp
```

Better production habit:

```bash
oc edit dpa dpa-sample -n openshift-adp
```

Then verify reconciliation:

```bash
oc get backupstoragelocation default -n openshift-adp -o yaml
```

## 6. BackupStorageLocation API: Important Fields

A raw Velero `BackupStorageLocation` has fields like:

```yaml
apiVersion: velero.io/v1
kind: BackupStorageLocation
metadata:
  name: default
  namespace: openshift-adp
spec:
  provider: aws
  objectStorage:
    bucket: my-bucket
    prefix: velero
    caCert: <base64-ca-bundle>
  credential:
    name: cloud-credentials
    key: cloud
  config:
    region: us-east-1
    profile: default
    s3ForcePathStyle: "true"
    s3Url: https://s3.example.com
    insecureSkipTLSVerify: "false"
  accessMode: ReadWrite
  backupSyncPeriod: 2m0s
  validationFrequency: 1m0s
```

### 6.1 `metadata.name`

The logical name of the BSL.

Common value:

```yaml
name: default
```

This matters because backups can explicitly choose a storage location:

```yaml
spec:
  storageLocation: default
```

or with Velero CLI:

```bash
velero backup create app-backup --storage-location default
```

### 6.2 `metadata.namespace`

Usually:

```yaml
namespace: openshift-adp
```

Older upstream Velero examples often show namespace `velero`, but OpenShift OADP commonly uses `openshift-adp`.

### 6.3 `spec.provider`

The provider plugin used for object storage.

Examples:

```yaml
provider: aws
```

or depending on plugin/version:

```yaml
provider: velero.io/aws
```

In OADP DPA examples, you commonly see:

```yaml
provider: aws
```

This provider must match the installed Velero plugin. For S3-compatible object stores such as NooBaa, MinIO, Ceph RGW, or ODF MCG, the `aws` plugin is commonly used because they expose an S3-compatible API.

### 6.4 `spec.objectStorage.bucket`

The object storage bucket that stores backups.

Example:

```yaml
objectStorage:
  bucket: oadp-prod-backups
```

Production guidance:

- Use a dedicated bucket for OADP if possible.
- If the bucket is shared, use a unique prefix per cluster.
- Do not mix unrelated application objects in the same prefix.
- Apply lifecycle rules carefully.
- Enable bucket versioning or object lock if your organization requires ransomware protection.

### 6.5 `spec.objectStorage.prefix`

The subdirectory-like path inside the bucket.

Example:

```yaml
objectStorage:
  bucket: enterprise-backups
  prefix: ocp-prod-cluster-a/velero
```

Why prefix is important:

```text
Same bucket:
  enterprise-backups

Different clusters:
  ocp-prod-cluster-a/velero
  ocp-prod-cluster-b/velero
  ocp-dr-cluster/velero
```

Without a prefix, Velero assumes it owns the bucket root. That can be risky in shared buckets.

### 6.6 `spec.objectStorage.caCert`

Base64-encoded CA certificate bundle used to validate TLS connections to object storage.

Use this for:

- MinIO with private CA
- NooBaa/MCG route with custom CA
- Ceph RGW with internal CA
- ONTAP S3 or StorageGRID with enterprise CA
- Disconnected environments

Example:

```bash
base64 -w0 ca.crt
```

Then:

```yaml
objectStorage:
  bucket: oadp
  prefix: velero
  caCert: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0t...
```

Production rule:

Prefer a proper CA bundle over:

```yaml
insecureSkipTLSVerify: "true"
```

### 6.7 `spec.credential.name`

Name of the Kubernetes `Secret` containing object storage credentials.

Example:

```yaml
credential:
  name: cloud-credentials
  key: cloud
```

The secret must exist in the Velero/OADP namespace:

```bash
oc get secret cloud-credentials -n openshift-adp
```

### 6.8 `spec.credential.key`

Key inside the secret that contains the credential file.

Common value:

```yaml
key: cloud
```

The secret is commonly created like:

```bash
oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

### 6.9 `spec.config`

Provider-specific key/value configuration.

For S3-compatible storage with AWS plugin:

```yaml
config:
  region: us-east-1
  profile: default
  s3ForcePathStyle: "true"
  s3Url: https://s3.example.com
  insecureSkipTLSVerify: "false"
```

Common S3-compatible fields:

| Field | Meaning |
|---|---|
| `region` | Bucket region or placeholder region for S3-compatible systems |
| `profile` | Profile name inside credentials file |
| `s3ForcePathStyle` | Use path-style addressing, often required for MinIO/NooBaa/Ceph RGW |
| `s3Url` | Explicit S3 endpoint |
| `publicUrl` | Public URL used for generated download links |
| `insecureSkipTLSVerify` | Disable TLS verification; not recommended for production |
| `serverSideEncryption` | S3 server-side encryption setting |
| `kmsKeyId` | AWS KMS key for SSE-KMS |
| `customerKeyEncryptionFile` | SSE-C key file path mounted in Velero pod |
| `checksumAlgorithm` | S3 checksum algorithm such as `CRC32`, `CRC32C`, `SHA1`, `SHA256`, or empty string in some scenarios |

### 6.10 `spec.accessMode`

Controls whether the BSL is writable.

Valid values:

```yaml
accessMode: ReadWrite
```

or:

```yaml
accessMode: ReadOnly
```

Use `ReadOnly` when a DR cluster should restore from a bucket but not write new backups into the same prefix.

### 6.11 `spec.backupSyncPeriod`

How often Velero synchronizes backup metadata from object storage into cluster-local Velero Backup CRs.

Example:

```yaml
backupSyncPeriod: 2m0s
```

Why it matters:

- DR cluster can discover backups created by another cluster.
- Restore-only cluster can list backups from object storage.
- Frequent sync increases object store API calls.

### 6.12 `spec.validationFrequency`

How often Velero validates the BSL.

Example:

```yaml
validationFrequency: 1m0s
```

Validation checks whether the object store is reachable and usable. If validation fails, backups using that location can fail or the BSL can show an unavailable status.

## 7. DataProtectionApplication `backupLocations` Explained

In OADP, you usually configure BSL through the DPA:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: <bucket_name>
          prefix: <prefix>
        config:
          region: <region>
          s3ForcePathStyle: "true"
          s3Url: <s3_url>
        credential:
          name: cloud-credentials
          key: cloud
```

### 7.1 `backupLocations[].name`

This becomes the BSL name.

```yaml
backupLocations:
  - name: default
```

If omitted in some examples, the operator may generate or default behavior may apply depending on version, but production YAML should be explicit.

### 7.2 `backupLocations[].velero.default`

Marks this location as the default backup storage location for Velero backups.

```yaml
velero:
  default: true
```

Only one location should be default in a typical configuration.

### 7.3 `backupLocations[].velero.provider`

Object store plugin provider.

```yaml
provider: aws
```

For S3-compatible providers, `aws` is widely used in OADP examples.

### 7.4 `backupLocations[].velero.objectStorage`

Defines bucket, prefix, and optional CA bundle.

```yaml
objectStorage:
  bucket: oadp-backups
  prefix: prod/cluster-a
  caCert: <base64_encoded_cert_string>
```

### 7.5 `backupLocations[].velero.config`

Provider-specific settings.

For MinIO/NooBaa/Ceph RGW:

```yaml
config:
  region: us-east-1
  s3ForcePathStyle: "true"
  s3Url: https://minio.example.com
  insecureSkipTLSVerify: "false"
```

For AWS S3:

```yaml
config:
  region: ap-south-1
  profile: default
```

### 7.6 `backupLocations[].velero.credential`

Secret reference.

```yaml
credential:
  name: cloud-credentials
  key: cloud
```

Important OADP behavior:

The DPA requires a default secret in many installation patterns. If you do not specify a credential name, default names are used based on provider/plugin and OADP version. In production, define the secret explicitly unless you intentionally rely on the documented default.

## 8. Production YAML Examples

### 8.1 AWS S3 BackupStorageLocation Through DPA

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-prod
  namespace: openshift-adp
spec:
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: ocp-prod-oadp-backups
          prefix: cluster-a/velero
        config:
          region: ap-south-1
          profile: default
        credential:
          name: cloud-credentials
          key: cloud
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
      resourceTimeout: 10m
    nodeAgent:
      enable: true
      uploaderType: kopia
```

Credential file:

```ini
[default]
aws_access_key_id=AKIAxxxxxxxxxxxx
aws_secret_access_key=xxxxxxxxxxxxxxxxxxxxxxxx
```

Create secret:

```bash
oc create namespace openshift-adp --dry-run=client -o yaml | oc apply -f -

oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

Apply DPA:

```bash
oc apply -f dpa-prod.yaml
```

Verify:

```bash
oc get dpa -n openshift-adp
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation default -n openshift-adp
```

## 9. Credential and Secret Design

### 9.1 Standard AWS-Style Credentials File

```ini
[default]
aws_access_key_id=<ACCESS_KEY>
aws_secret_access_key=<SECRET_KEY>
```

Create secret:

```bash
oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

Verify secret exists:

```bash
oc get secret cloud-credentials -n openshift-adp
```

Do not print secrets in production terminals unless necessary:

```bash
oc extract secret/cloud-credentials -n openshift-adp --to=-
```

Use RBAC controls and audit access to this secret.

### 9.2 Multiple Profiles in One Secret

```ini
[backupStorage]
aws_access_key_id=<BACKUP_ACCESS_KEY>
aws_secret_access_key=<BACKUP_SECRET_KEY>

[volumeSnapshot]
aws_access_key_id=<SNAPSHOT_ACCESS_KEY>
aws_secret_access_key=<SNAPSHOT_SECRET_KEY>
```

DPA:

```yaml
backupLocations:
  - name: default
    velero:
      provider: aws
      default: true
      objectStorage:
        bucket: ocp-backups
        prefix: velero
      config:
        region: ap-south-1
        profile: backupStorage
      credential:
        name: cloud-credentials
        key: cloud
snapshotLocations:
  - name: default
    velero:
      provider: aws
      config:
        region: ap-south-1
        profile: volumeSnapshot
```

### 9.3 Separate Secrets for Backup and Snapshot

Use separate secrets when object storage credentials and snapshot credentials are managed by different teams or different IAM policies.

```bash
oc create secret generic backup-cloud-credentials \
  -n openshift-adp \
  --from-file cloud=backup-credentials-velero

oc create secret generic snapshot-cloud-credentials \
  -n openshift-adp \
  --from-file cloud=snapshot-credentials-velero
```

DPA backup location:

```yaml
backupLocations:
  - name: default
    velero:
      provider: aws
      default: true
      credential:
        name: backup-cloud-credentials
        key: cloud
      objectStorage:
        bucket: ocp-backups
        prefix: prod
      config:
        region: ap-south-1
```

Snapshot location:

```yaml
snapshotLocations:
  - name: default
    velero:
      provider: aws
      credential:
        name: snapshot-cloud-credentials
        key: cloud
      config:
        region: ap-south-1
```

Check exact support for explicit `credential` on snapshot locations with your OADP version and provider plugin.

### 9.4 Least Privilege IAM for S3-Compatible Backups

For an AWS S3 bucket, minimum permissions often include:

- `s3:ListBucket`
- `s3:GetObject`
- `s3:PutObject`
- `s3:DeleteObject` if backup deletion/TTL cleanup is expected
- `s3:AbortMultipartUpload`
- `s3:ListBucketMultipartUploads`
- `s3:ListMultipartUploadParts`

Example IAM-style policy skeleton:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket",
        "s3:GetBucketLocation",
        "s3:ListBucketMultipartUploads"
      ],
      "Resource": "arn:aws:s3:::ocp-prod-oadp-backups"
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": "arn:aws:s3:::ocp-prod-oadp-backups/cluster-a/velero/*"
    }
  ]
}
```

For a restore-only DR cluster, remove write/delete permissions and use `accessMode: ReadOnly`.

## 10. S3-Compatible Object Storage Design

### 10.1 AWS S3 vs S3-Compatible

AWS S3:

```yaml
config:
  region: ap-south-1
```

S3-compatible object storage:

```yaml
config:
  region: us-east-1
  s3ForcePathStyle: "true"
  s3Url: https://minio.example.com
```

The `aws` plugin can talk to many S3-compatible object stores, but compatibility is not guaranteed for every feature. Always validate:

- Authentication format
- TLS certificate trust
- Path-style vs virtual-hosted-style addressing
- Bucket region handling
- Multipart upload behavior
- Checksum behavior
- SSE/KMS behavior
- Lifecycle/retention behavior

### 10.2 Path-Style vs Virtual-Hosted-Style

Virtual-hosted-style:

```text
https://bucket-name.s3.example.com/object
```

Path-style:

```text
https://s3.example.com/bucket-name/object
```

For MinIO, NooBaa, Ceph RGW, and many private S3-compatible services, use:

```yaml
s3ForcePathStyle: "true"
```

### 10.3 Bucket and Prefix Naming Strategy

Recommended:

```text
Bucket: enterprise-oadp-backups
Prefix: prod/ocp-cluster-a/velero
Prefix: prod/ocp-cluster-b/velero
Prefix: dr/ocp-dr-cluster/velero
```

Avoid:

```text
Bucket: test
Prefix: velero
```

for all clusters, because backup objects can collide or become difficult to govern.

### 10.4 Object Lifecycle Strategy

Object store lifecycle rules should match Velero backup TTL.

Example:

```text
Velero backup TTL: 30 days
Object lifecycle expiration: 35-45 days
```

Why not expire object storage earlier?

Because Velero may still have Backup CRs referencing objects that no longer exist. Restore will fail if object storage lifecycle deletes backup content before Velero TTL cleanup.

### 10.5 Bucket Versioning and Object Lock

For ransomware-resistant backup strategy:

- Enable bucket versioning.
- Consider object lock / WORM where supported.
- Use separate IAM identity for backup writer.
- Use separate IAM identity for restore reader.
- Store credentials outside normal application namespaces.
- Audit object deletion.

Be careful: strict object lock can conflict with Velero TTL cleanup if delete operations are denied.

## 11. Default BackupStorageLocation Behavior

Velero expects at least one backup storage location. In many installations, the default location is named:

```text
default
```

A backup that does not specify `storageLocation` uses the default BSL.

Example backup without explicit BSL:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app1
```

This backup goes to the default BSL.

Backup with explicit BSL:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-backup-secondary
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app1
  storageLocation: secondary-s3
```

Production recommendation:

Always specify `storageLocation` in important schedules when multiple BSLs exist.

## 12. Multiple BackupStorageLocations

Multiple BSLs are useful for:

- Different regions
- Different object storage providers
- Different security zones
- Different applications
- Different retention policies
- DR replication
- Migration
- Restore-only cluster

Example DPA with two BSLs:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-multi-bsl
  namespace: openshift-adp
spec:
  backupLocations:
    - name: primary-s3
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: ocp-prod-backups-primary
          prefix: cluster-a
        config:
          region: ap-south-1
          profile: primary
        credential:
          name: cloud-credentials-primary
          key: cloud
    - name: secondary-s3
      velero:
        provider: aws
        default: false
        objectStorage:
          bucket: ocp-prod-backups-secondary
          prefix: cluster-a
        config:
          region: ap-south-2
          profile: secondary
        credential:
          name: cloud-credentials-secondary
          key: cloud
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
```

Create schedules targeting each location:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: app1-daily-primary
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
      - app1
    storageLocation: primary-s3
    ttl: 168h0m0s
---
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: app1-weekly-secondary
  namespace: openshift-adp
spec:
  schedule: "0 3 * * 0"
  template:
    includedNamespaces:
      - app1
    storageLocation: secondary-s3
    ttl: 720h0m0s
```

Important limitation:

A single Velero backup writes to one BSL. If you want two independent copies, create two backups or two schedules targeting two BSLs.

## 13. ReadWrite vs ReadOnly Access Mode

### 13.1 ReadWrite

Default behavior for normal backup and restore cluster.

```yaml
accessMode: ReadWrite
```

Use when the cluster should:

- Create backups
- Upload logs
- Delete backups according to TTL
- Restore backups

### 13.2 ReadOnly

Use for DR or migration clusters that should discover and restore backups but not modify the source backup location.

```yaml
accessMode: ReadOnly
```

Example scenario:

```text
Prod cluster:
  BSL: s3://prod-backups/cluster-a
  accessMode: ReadWrite

DR cluster:
  BSL: s3://prod-backups/cluster-a
  accessMode: ReadOnly
```

Benefits:

- Prevents accidental backup overwrite or deletion from DR cluster.
- Safer during migration testing.
- Useful for forensic restore.

Caution:

A restore operation may still create local Restore CRs and Kubernetes resources in the DR cluster, but it should not write new backup objects into the BSL.

## 14. Backup Sync and Validation

### 14.1 What Backup Sync Does

Backup sync scans object storage and synchronizes backup objects into the cluster's Velero API.

This matters during:

- DR cluster restore
- Cluster migration
- Reinstalling OADP and rediscovering old backups
- Reconstructing backup CRs after cluster loss

Command to see discovered backups:

```bash
oc get backup -n openshift-adp
```

If backups exist in object storage but not in the cluster, check:

```bash
oc describe backupstoragelocation <bsl-name> -n openshift-adp
oc logs deployment/velero -n openshift-adp | grep -i sync
```

### 14.2 What Validation Does

Validation checks whether Velero can connect to and use the configured object storage.

Check status:

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation default -n openshift-adp
```

You may see status such as:

```text
PHASE: Available
```

or:

```text
PHASE: Unavailable
```

Fields and condition names can vary by Velero version. Always inspect full YAML:

```bash
oc get backupstoragelocation default -n openshift-adp -o yaml
```

### 14.3 Tuning Sync and Validation

Example:

```yaml
backupSyncPeriod: 5m0s
validationFrequency: 1m0s
```

Guidance:

- Shorter periods = faster DR discovery, more object-store API calls.
- Longer periods = lower API cost, slower discovery.
- Do not disable validation in production unless there is a specific reason.

## 15. File System Backup and BackupStorageLocation

File System Backup means Velero backs up PV content at the filesystem level using the node-agent and a backup repository implementation such as Kopia or Restic.

With FSB:

```text
PV file data ---> node-agent ---> object storage under selected BSL
```

This is different from cloud snapshots:

```text
PV block snapshot ---> cloud snapshot service
Backup metadata ----> BSL
```

DPA example with Kopia:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-fsb
  namespace: openshift-adp
spec:
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: ocp-backups
          prefix: fsb/cluster-a
        config:
          region: ap-south-1
        credential:
          name: cloud-credentials
          key: cloud
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
    nodeAgent:
      enable: true
      uploaderType: kopia
```

Key admin points:

- FSB volume data consumes bucket capacity.
- Backup speed depends on node-agent resources, pod placement, storage read throughput, network throughput, and object store performance.
- Repository corruption or credential issues can break volume restores.
- `BackupStorageLocation` is now performance-critical, not just metadata storage.

## 16. CSI Snapshot Data Mover and BackupStorageLocation

CSI snapshots create snapshots through the CSI snapshot API. Data mover workflows can move snapshot data to object storage for portability and durability.

At high level:

```text
PVC -> CSI VolumeSnapshot -> Data movement -> Object storage BSL
```

Why this matters:

- Native CSI snapshots can be tied to a storage backend or cluster.
- Data movement to object storage improves restore portability.
- The BSL must have enough capacity and throughput.

Design guidance:

- For small clusters, a single BSL may be enough.
- For large stateful clusters, separate BSLs by application tier or retention class.
- Avoid using slow object storage for high-change databases without understanding RPO/RTO.
- Test restore, not only backup completion.

## 17. OpenShift Internal Images and BackupStorageLocation

OADP can back up OpenShift and Kubernetes resources as archive data on object storage. OpenShift internal images may also be part of backup workflows depending on configuration and plugin behavior.

For image-heavy clusters:

- Expect larger backup archives.
- Ensure object storage capacity is sized properly.
- Test restore into a clean namespace or DR cluster.
- Understand whether image streams reference external registries, internal registry images, or both.

Commands:

```bash
oc get imagestream -A
oc get route default-route -n openshift-image-registry
oc get configs.imageregistry.operator.openshift.io cluster -o yaml
```

Backup design question:

```text
Are you backing up only Kubernetes metadata that references images,
or are you also protecting the actual internal image content?
```

This affects object storage sizing and restore success.

## 18. Security Hardening

### 18.1 Protect the Credentials Secret

The OADP cloud credential secret can read/write backups. Treat it as sensitive.

```bash
oc get secret cloud-credentials -n openshift-adp
```

Recommended:

- Restrict access to `openshift-adp` namespace.
- Use least-privilege object storage policy.
- Rotate access keys periodically.
- Avoid long-lived root credentials.
- Use separate credentials for backup writer and restore reader.
- Audit secret access.

### 18.2 Encrypt Data in Transit

Use HTTPS for object storage:

```yaml
config:
  s3Url: https://s3.example.com
  insecureSkipTLSVerify: "false"
```

If internal CA is used:

```yaml
objectStorage:
  caCert: <base64-ca>
```

Avoid:

```yaml
insecureSkipTLSVerify: "true"
```

except temporary troubleshooting.

### 18.3 Encrypt Data at Rest

Options depend on backend:

- AWS SSE-S3
- AWS SSE-KMS
- SSE-C customer keys
- ODF/NooBaa/Ceph encryption
- StorageGRID/ONTAP object encryption

AWS plugin config examples:

```yaml
config:
  serverSideEncryption: AES256
```

SSE-KMS:

```yaml
config:
  kmsKeyId: arn:aws:kms:ap-south-1:123456789012:key/<key-id>
```

SSE-C:

```yaml
config:
  customerKeyEncryptionFile: /credentials/customer-key
```

Critical warning:

If you lose encryption keys, backups may become unrecoverable.

### 18.4 Separate Duties

Recommended identity split:

| Identity | Permission |
|---|---|
| Backup writer | Put/List/Get/Delete in backup prefix |
| Restore reader | List/Get only |
| Security admin | Manage bucket policy and encryption |
| Platform admin | Manage OADP CRs but not root object store admin |

### 18.5 Protect Against Accidental Delete

Options:

- Bucket versioning
- Object lock / retention
- MFA delete where supported
- Cross-region replication
- Separate backup account/project
- Write-only backup identity plus separate cleanup process

Balance this with Velero TTL cleanup.

## 19. Network, Proxy, DNS, TLS, and Certificate Considerations

Velero runs as a pod. The object storage endpoint must be reachable **from the Velero pod**, not only from your laptop.

### 19.1 Test DNS from Velero Pod

```bash
oc exec -n openshift-adp deployment/velero -- sh -c 'getent hosts s3.example.com'
```

If the image lacks tools, create a temporary debug pod in the same namespace:

```bash
oc run netshoot -n openshift-adp --rm -it \
  --image=nicolaka/netshoot -- bash
```

Then test:

```bash
nslookup s3.example.com
curl -vk https://s3.example.com
```

Use approved internal images in restricted environments.

### 19.2 Test TLS

```bash
openssl s_client -connect s3.example.com:443 -showcerts
```

Inside cluster:

```bash
oc debug node/<node-name>
```

or use a debug pod with openssl/curl.

### 19.3 Common TLS Error

```text
x509: certificate signed by unknown authority
```

Fix:

1. Get CA certificate.
2. Base64 encode it.
3. Add it to `objectStorage.caCert`.
4. Keep `insecureSkipTLSVerify: "false"`.
5. Restart Velero pod if needed.

### 19.4 Proxy Environments

In disconnected or proxied clusters, ensure Velero can reach object storage.

Check cluster proxy:

```bash
oc get proxy cluster -o yaml
```

Check Velero deployment environment:

```bash
oc get deployment velero -n openshift-adp -o yaml | grep -i proxy -A5 -B5
```

If object storage is internal, ensure it is in `NO_PROXY` as required.

## 22. Troubleshooting BackupStorageLocation

Troubleshooting must be systematic. Do not start by changing random YAML values.

### 22.1 Troubleshooting Decision Tree

```text
Backup failed or BSL unavailable
  |
  +-- Does BSL exist?
  |     oc get bsl -n openshift-adp
  |
  +-- Is DPA reconciled?
  |     oc describe dpa -n openshift-adp
  |
  +-- Is provider plugin installed?
  |     oc logs deployment/velero | grep -i plugin
  |
  +-- Does secret exist and key name match?
  |     oc get secret cloud-credentials -o yaml
  |
  +-- Can Velero pod resolve endpoint?
  |     DNS test from pod
  |
  +-- Can Velero pod reach endpoint?
  |     curl/nc test from pod
  |
  +-- Is TLS trusted?
  |     caCert / insecureSkipTLSVerify
  |
  +-- Does IAM allow bucket/prefix actions?
  |     S3 List/Get/Put/Delete
  |
  +-- Is bucket/prefix correct?
  |     aws s3 ls
  |
  +-- Is object storage compatible?
        s3ForcePathStyle / checksumAlgorithm / region / endpoint
```

### 22.2 BSL Does Not Exist

Symptoms:

```bash
oc get backupstoragelocation -n openshift-adp
# No resources found
```

Check DPA:

```bash
oc get dpa -n openshift-adp -o yaml
oc describe dpa <dpa-name> -n openshift-adp
```

Check operator logs:

```bash
oc logs deployment/oadp-operator-controller-manager -n openshift-adp
```

Possible causes:

- DPA not created.
- DPA YAML invalid.
- Missing required default secret.
- OADP Operator not running.
- Wrong namespace.
- CRD version mismatch.

Fix:

```bash
oc apply -f dpa.yaml
oc get events -n openshift-adp --sort-by=.lastTimestamp
```

### 22.3 BSL Is Unavailable

Check:

```bash
oc describe backupstoragelocation default -n openshift-adp
oc get backupstoragelocation default -n openshift-adp -o yaml
oc logs deployment/velero -n openshift-adp
```

Common reasons:

- Bad credentials.
- Bucket does not exist.
- Wrong region.
- Wrong endpoint URL.
- TLS error.
- Proxy blocking connection.
- DNS failure.
- Object store rejects path-style or virtual-hosted-style request.
- Plugin missing.
- Permission denied on bucket prefix.

### 22.4 Access Denied

Typical log:

```text
AccessDenied: Access Denied
status code: 403
```

Check:

```bash
oc get secret cloud-credentials -n openshift-adp
oc describe backupstoragelocation default -n openshift-adp
```

Validate with AWS CLI using same credentials:

```bash
AWS_SHARED_CREDENTIALS_FILE=./credentials-velero \
aws s3 ls s3://ocp-prod-oadp-backups/cluster-a/velero/
```

For custom endpoint:

```bash
AWS_SHARED_CREDENTIALS_FILE=./credentials-velero \
aws --endpoint-url https://minio.example.com \
  s3 ls s3://oadp/velero/
```

Fix IAM/bucket policy.

Minimum required write test:

```bash
aws s3 cp test.txt s3://bucket/prefix/test.txt
aws s3 rm s3://bucket/prefix/test.txt
```

### 22.5 No Such Bucket

Typical log:

```text
NoSuchBucket
The specified bucket does not exist
```

Check:

```bash
aws s3 ls
aws s3 ls s3://<bucket>
```

Fix:

- Create bucket.
- Correct bucket name.
- Correct region.
- Correct endpoint.
- Ensure Velero credential sees the bucket.

### 22.6 TLS Unknown Authority

Typical log:

```text
x509: certificate signed by unknown authority
```

Fix with CA:

```bash
base64 -w0 ca.crt
```

DPA:

```yaml
objectStorage:
  bucket: oadp
  prefix: velero
  caCert: <base64-ca>
config:
  insecureSkipTLSVerify: "false"
```

Temporary troubleshooting only:

```yaml
config:
  insecureSkipTLSVerify: "true"
```

### 22.7 Timeout Connecting to Object Storage

Typical log:

```text
context deadline exceeded
connect: connection timed out
```

Check:

```bash
oc exec -n openshift-adp deployment/velero -- sh -c 'getent hosts s3.example.com'
oc get networkpolicy -A
oc get egressfirewall -A 2>/dev/null
oc get proxy cluster -o yaml
```

Possible causes:

- DNS failure.
- Firewall blocks egress.
- NetworkPolicy blocks egress.
- Proxy required but not configured.
- Object storage route/service not reachable from worker nodes.
- Wrong port.

### 22.8 Signature Does Not Match

Typical log:

```text
SignatureDoesNotMatch
The request signature we calculated does not match
```

Possible causes:

- Wrong secret key.
- Wrong profile selected.
- Clock skew.
- Wrong endpoint/region combination.
- Special characters copied incorrectly.
- S3-compatible provider expects path-style.

Fix:

```yaml
config:
  region: us-east-1
  profile: default
  s3ForcePathStyle: "true"
  s3Url: https://s3.example.com
```

Check node/pod time:

```bash
date -u
oc debug node/<node> -- chroot /host date -u
```

### 22.9 Backups Do Not Appear on DR Cluster

Scenario:

- Prod cluster writes backups.
- DR cluster uses same bucket/prefix as ReadOnly.
- `oc get backup -n openshift-adp` on DR does not show backups.

Check:

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation default -n openshift-adp
oc logs deployment/velero -n openshift-adp | grep -i sync
```

Verify object storage from DR cluster credentials:

```bash
aws s3 ls s3://bucket/prefix/backups/
```

Possible causes:

- `backupSyncPeriod` disabled or long.
- BSL unavailable.
- Wrong prefix.
- DR credentials cannot list bucket.
- Backup objects were encrypted with inaccessible key.
- Backup created by incompatible Velero/OADP version.

### 22.10 Backup Succeeds But Restore Fails

Do not assume BSL is healthy just because backup completed.

Check:

```bash
oc describe restore <restore-name> -n openshift-adp
oc logs deployment/velero -n openshift-adp | grep <restore-name>
```

Possible BSL-related causes:

- Backup archive missing due to lifecycle deletion.
- Backup logs exist but tarball missing.
- Encryption key unavailable.
- Read permissions missing on restore cluster.
- Object store returns partial/corrupt object.
- Incompatible plugin set on restore cluster.

## 23. Common Failure Scenarios and Fixes

### Scenario 1: DPA Fails Because Default Secret Is Missing

Symptom:

```text
DataProtectionApplication not reconciled
secret cloud-credentials not found
```

Fix:

```bash
cat > credentials-velero <<EOF
[default]
aws_access_key_id=<ACCESS_KEY>
aws_secret_access_key=<SECRET_KEY>
EOF

oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

Then reconcile:

```bash
oc get dpa -n openshift-adp
oc describe dpa <dpa-name> -n openshift-adp
```

Usually editing/applying the DPA is enough. Restart components only when reconciliation is clearly stuck and you understand the production impact.

### Scenario 2: MinIO Endpoint Works from Laptop But Not from Velero Pod

Cause:

Your laptop can reach MinIO, but cluster egress cannot.

Fix:

- Test from inside the cluster.
- Expose MinIO through a route/service reachable from OpenShift worker nodes.
- Add a DNS entry resolvable inside the cluster.
- Update `s3Url`.
- Check network policies, egress firewalls, and proxy/no-proxy configuration.

### Scenario 3: NooBaa Fails Due to Checksum Behavior

Symptom:

Object upload fails with checksum-related errors.

Fix example:

```yaml
config:
  checksumAlgorithm: ""
```

Also validate OADP version-specific recommendations.

### Scenario 4: Backup Deleted from Object Storage Before TTL

Cause:

Object storage lifecycle deleted backup objects before Velero TTL cleanup.

Fix:

- Align bucket lifecycle with Velero TTL.
- Set object lifecycle longer than Velero TTL.
- Review bucket expiration policy.

### Scenario 5: DR Cluster Accidentally Writes Into Prod Backup Prefix

Cause:

DR cluster BSL configured as `ReadWrite` using the same bucket/prefix.

Fix:

Use:

```yaml
accessMode: ReadOnly
```

and read-only object storage credentials.

### Scenario 6: Wrong Prefix Causes “No Backups Found”

Prod:

```yaml
prefix: cluster-a/velero
```

DR accidentally configured:

```yaml
prefix: velero
```

Fix prefix exactly.

### Scenario 7: Plugin Missing

Symptom:

```text
No volume snapshotter found
No object store plugin for provider aws
```

Check DPA:

```yaml
configuration:
  velero:
    defaultPlugins:
      - openshift
      - aws
      - csi
```

Check Velero logs:

```bash
oc logs deployment/velero -n openshift-adp | grep -i plugin
```

## 24. Performance and Scale Considerations

### 24.1 Object Count

Velero backups create multiple objects per backup. At scale, object count grows quickly.

Example:

```text
100 namespaces x daily backups x 30 days = many backup archives, logs, result files, repository chunks
```

For FSB/Kopia/Restic, object count can grow much faster.

### 24.2 Object Storage Throughput

BSL performance impacts:

- Backup upload duration
- Restore download duration
- FSB backup speed
- FSB restore speed
- Backup sync time
- Object-store API cost

Measure:

```bash
oc describe backup <backup> -n openshift-adp
oc logs deployment/velero -n openshift-adp | grep -i duration
```

### 24.3 Large Cluster Backup Design

For large clusters:

- Do not back up everything with one schedule unless required.
- Group namespaces by application criticality.
- Use label selectors.
- Use separate schedules and TTLs.
- Use separate BSLs for different retention/security classes.
- Test restore per application, not only backup phase.

### 24.4 API Server Load

Backup operations read many Kubernetes resources.

Tune Velero client QPS/burst only when required and supported by your OADP version:

```yaml
configuration:
  velero:
    client-burst: 500
    client-qps: 300
```

Do not increase these values blindly. Higher QPS can create extra API server pressure on large clusters.

### 24.5 Node Agent Resource Sizing

For FSB/Kopia/Restic, node-agent resource sizing affects throughput.

Example pattern:

```yaml
configuration:
  nodeAgent:
    enable: true
    uploaderType: kopia
    podConfig:
      resourceAllocations:
        requests:
          cpu: "500m"
          memory: 512Mi
        limits:
          cpu: "2"
          memory: 2Gi
```

Exact field support can vary by OADP version. Validate against your cluster CRD:

```bash
oc explain dpa.spec.configuration.nodeAgent --recursive
```

## 25. Disaster Recovery Patterns

### 25.1 Same Cluster Restore

```text
Cluster A writes to BSL
Cluster A restores from same BSL
```

Use case:

- Accidental namespace deletion
- Failed deployment
- Application rollback

### 25.2 Cross-Cluster Restore

```text
Cluster A writes to object storage
Cluster B configures same BSL as ReadOnly
Cluster B syncs backups
Cluster B restores selected backup
```

DR cluster DPA pattern:

```yaml
backupLocations:
  - name: prod-cluster-a
    velero:
      provider: aws
      default: true
      objectStorage:
        bucket: ocp-prod-backups
        prefix: cluster-a/velero
      config:
        region: ap-south-1
      credential:
        name: restore-readonly-credentials
        key: cloud
```

Generated/direct BSL should be read-only where supported:

```yaml
accessMode: ReadOnly
```

### 25.3 Multi-Region Backup

Create separate schedules:

```text
Daily backup -> primary region bucket
Weekly backup -> secondary region bucket
```

Do not assume one backup is automatically copied to all BSLs.

### 25.4 Shared Bucket, Separate Prefix

```text
s3://enterprise-backups/ocp-prod-a/velero
s3://enterprise-backups/ocp-prod-b/velero
s3://enterprise-backups/ocp-dr/velero
```

Policy can limit each cluster to its own prefix.

### 25.5 Migration Pattern

1. Configure old cluster with BSL `ReadWrite`.
2. Run final backup.
3. Configure new cluster with same BSL `ReadOnly`.
4. Wait for backup sync.
5. Restore selected namespaces.
6. Validate applications.
7. Switch traffic.
8. Reconfigure new cluster with its own `ReadWrite` BSL.

## 26. Best Practices for 10+ Years Experience Level

### 26.1 Treat BSL as a DR Contract

Document this outside the cluster:

```text
Cluster name:
OADP version:
Velero version:
BSL name:
Provider:
Bucket:
Prefix:
Endpoint:
Region:
Secret name:
Credential owner:
Encryption method:
Retention:
Lifecycle policy:
Restore test frequency:
Last successful restore:
```

### 26.2 Never Trust Backup Without Restore

A BSL that accepts uploads is not enough.

Validate:

- Can list backups.
- Can download backup archive.
- Can restore resources.
- Can restore PV data.
- Can restore into another cluster.
- Can restore with read-only credentials.

### 26.3 Use Prefixes Intentionally

Good:

```yaml
prefix: prod/ocp-cluster-a/velero
```

Bad:

```yaml
prefix: velero
```

for every cluster.

### 26.4 Prefer CA Bundle Over Insecure TLS

Good:

```yaml
objectStorage:
  caCert: <base64-ca>
config:
  insecureSkipTLSVerify: "false"
```

Bad:

```yaml
config:
  insecureSkipTLSVerify: "true"
```

### 26.5 Separate Backup and Restore Credentials

Backup identity:

```text
List/Get/Put/Delete allowed
```

Restore identity:

```text
List/Get only
```

### 26.6 Align Velero TTL and Bucket Lifecycle

If Velero TTL is 30 days, do not configure bucket expiration at 7 days.

Recommended:

```text
Velero TTL: 30 days
Bucket lifecycle: 35-45 days
```

### 26.7 Monitor BSL Health

Check:

```bash
oc get backupstoragelocation -n openshift-adp
```

Alert on:

- BSL unavailable
- Backup failures
- No successful backup in expected window
- Restore failures
- Velero pod restart loop
- Object storage 4xx/5xx errors
- Bucket capacity threshold

### 26.8 Keep Plugin Versions Compatible

OADP ships supported Velero/plugin images. Do not randomly mix upstream plugins with supported OADP unless you understand support implications.

Check:

```bash
oc get csv -n openshift-adp
oc describe deployment velero -n openshift-adp
oc logs deployment/velero -n openshift-adp | grep -i version
```

### 26.9 Avoid Editing Generated Resources

If DPA manages BSL, edit the DPA:

```bash
oc edit dpa <dpa-name> -n openshift-adp
```

Then check generated BSL:

```bash
oc get backupstoragelocation -n openshift-adp -o yaml
```

### 26.10 Design for Cluster Loss

Store this outside the cluster:

- DPA YAML
- Secret creation process
- Bucket name/prefix
- CA cert
- Encryption key recovery process
- Restore runbook
- OADP version compatibility notes

If your only copy of backup credentials is inside the lost cluster, your DR design is incomplete.

## 27. Interview Questions and Real-World Answers

### Q1. What is BackupStorageLocation in OADP?

`BackupStorageLocation` is the Velero custom resource that defines the object storage location where backups are stored. In OADP, it is usually configured through the `DataProtectionApplication` under `spec.backupLocations`. It includes provider, bucket, prefix, credentials, endpoint, TLS settings, and access mode.

### Q2. Is BackupStorageLocation the same as VolumeSnapshotLocation?

No. BSL stores backup metadata, logs, resource archives, and file-system backup data in object storage. VSL defines where cloud/native volume snapshots are created. Every backup needs a BSL; VSL is needed only for provider-native snapshot workflows.

### Q3. What happens if a backup does not specify `storageLocation`?

It uses the default BackupStorageLocation. In production with multiple BSLs, explicitly specify `storageLocation` in backup and schedule specs to avoid ambiguity.

### Q4. Can one backup write to two BackupStorageLocations?

No. A single Velero backup writes to one BSL. For redundancy, create two schedules or two backups that target different BSLs.

### Q5. Why use a bucket prefix?

A prefix isolates Velero data within a bucket. It prevents collisions between clusters and allows shared-bucket designs with prefix-scoped IAM policies.

### Q6. What does `s3ForcePathStyle` do?

It forces S3 path-style addressing, such as `https://endpoint/bucket/object`. This is commonly required for S3-compatible stores like MinIO, NooBaa, and Ceph RGW.

### Q7. How do you troubleshoot BSL unavailable?

Check DPA, BSL status, Velero logs, provider plugin, secret name/key, bucket existence, endpoint DNS, network reachability, TLS CA, IAM permissions, region, path-style setting, and object-store compatibility.

### Q8. How do you make a DR cluster restore from prod backups safely?

Configure the same bucket and prefix on the DR cluster, use read-only object storage credentials, set BSL access mode to `ReadOnly`, wait for backup sync, then restore selected backups.

### Q9. Why should `insecureSkipTLSVerify: "true"` be avoided?

It disables TLS certificate verification and exposes backup traffic to man-in-the-middle risk. Production should use a trusted CA bundle through `objectStorage.caCert`.

### Q10. What is stored in object storage when using File System Backup?

File-system backup data is stored in the object storage associated with the selected BSL, along with backup metadata. This makes BSL capacity and throughput critical for stateful workloads.

### Q11. What secret format does S3-compatible BSL commonly use?

A credentials file stored under key `cloud`:

```ini
[default]
aws_access_key_id=<ACCESS_KEY>
aws_secret_access_key=<SECRET_KEY>
```

Secret:

```bash
oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

### Q12. What is the biggest production mistake with BackupStorageLocation?

Assuming “backup completed” means “DR is ready.” Real readiness requires restore testing, read-only DR validation, credential recovery, object lifecycle alignment, and documented restore runbooks.
