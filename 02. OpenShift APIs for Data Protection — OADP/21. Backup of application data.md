# Backup of Application Data in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, backup owners, and OpenShift/Kubernetes administrators with production experience.  
**Level:** 10+ years infrastructure / Linux / DevOps / OpenShift administration.  
**Scope:** Application-data backup using OpenShift APIs for Data Protection (OADP), Velero, BackupStorageLocation, CSI snapshots, File System Backup with Kopia/Restic, CSI Data Mover, hooks, validation, troubleshooting, and production design.

---

## 1. What “Backup of Application Data” Means in OADP

In OpenShift, an application is not only a container image or a Deployment. A real production application usually contains many moving parts:

- Kubernetes/OpenShift API objects
- Namespace metadata
- Deployments, StatefulSets, DaemonSets, Jobs, CronJobs
- Services, Routes, Ingress objects
- ConfigMaps and Secrets
- ServiceAccounts, RoleBindings, sometimes ClusterRoleBindings
- PersistentVolumeClaims and PersistentVolume metadata
- PersistentVolume data, such as database files, uploaded files, logs, reports, queues, cache data, or application state
- Internal OpenShift image registry content, if the app depends on internal ImageStreams/images
- Custom resources, if the workload depends on Operators or application-specific CRDs

**Backup of application data** means protecting the complete recoverable state of an application so that it can be restored after accidental deletion, storage corruption, namespace loss, cluster migration, disaster recovery, or ransomware-style data damage.

In OADP, this usually means protecting two major categories:

| Category | Example | Backup target |
|---|---|---|
| Application resources | Deployment, StatefulSet, Service, Route, Secret, ConfigMap, PVC, RoleBinding | Object storage through Velero backup archive |
| Application persistent data | Database files, uploaded files, block volumes, filesystem volumes | CSI snapshot, native cloud snapshot, File System Backup, or CSI Data Mover |

A senior administrator must understand that backing up only YAML is not enough for stateful applications. A Deployment can be recreated from GitOps, but a database PVC cannot be recreated unless its data is protected.

## 2. OADP Position in OpenShift Backup Strategy

OADP is used for **application-level backup and restore**. It is not a replacement for etcd backup, cluster control-plane recovery, GitOps, storage replication, database-native backup, or infrastructure disaster recovery.

### 2.1 What OADP Is Good For

OADP is strong for:

- Namespace-level application backup
- Application migration between clusters
- Stateful workload protection
- Backup of application YAML and selected cluster-scoped dependencies
- Backup of persistent volume data through snapshots or file-level copy
- Schedule-based backups
- Restore to same namespace
- Restore to different namespace
- Restore to another cluster, when storage and object-store design supports it
- Self-service backup/restore for namespace administrators in newer OADP versions

### 2.2 What OADP Is Not Meant For

OADP is **not** the correct tool for:

- Full etcd backup
- Full cluster backup including all Operators and control-plane state
- Rebuilding a broken control plane
- Replacing database-native logical backups for strict transaction consistency
- Backing up external databases that are outside Kubernetes unless the app exports data into a PVC first
- Backing up every cluster-scoped object without careful filtering
- Backing up unsupported or incompatible volume snapshots created by other tools

For full cluster control-plane recovery, use OpenShift etcd backup and disaster recovery procedures. For application recovery, use OADP.

## 3. Core Components Involved in Application Data Backup

### 3.1 OADP Operator

The OADP Operator installs and manages the data protection stack in the cluster. It normally runs in:

```bash
openshift-adp
```

The Operator creates and reconciles the `DataProtectionApplication` custom resource. That resource defines how Velero, plugins, backup locations, snapshot locations, and node agents are configured.

### 3.2 Velero

Velero is the backup and restore engine used by OADP. In an OADP environment, you usually interact with Velero by using:

```bash
oc get backups.velero.io -n openshift-adp
oc get restores.velero.io -n openshift-adp
velero backup create ...
velero backup describe ...
velero restore create ...
```

Velero stores Kubernetes/OpenShift resource definitions in object storage and coordinates persistent volume protection through snapshots, file-system backup, or Data Mover.

### 3.3 BackupStorageLocation

`BackupStorageLocation` tells Velero where backup metadata and backup archives are stored.

Common backends:

- AWS S3
- S3-compatible object storage
- OpenShift Data Foundation / NooBaa / Multicloud Object Gateway
- MinIO
- Ceph RGW
- Azure Blob
- Google Cloud Storage

In production, the backup storage should be outside the failure domain of the cluster. If the object store is inside the same OpenShift cluster and that cluster is lost, the backup might also be lost.

Check backup storage location:

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
oc describe backupstoragelocation -n openshift-adp
```

Expected state:

```text
PHASE: Available
```

### 3.4 VolumeSnapshotLocation

`VolumeSnapshotLocation` is used when Velero uses cloud-provider native snapshot APIs. CSI snapshots normally use `VolumeSnapshotClass` and do not require the same type of snapshot location configuration.

Use it when your cloud provider plugin requires it, for example native AWS/Azure/GCP snapshot integration.

### 3.5 VolumeSnapshotClass

For CSI snapshots, the cluster must have a CSI driver that supports Kubernetes snapshot APIs. The `VolumeSnapshotClass` must be labeled so Velero can discover it.

Example:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ocs-storagecluster-rbdplugin-snapclass
  labels:
    velero.io/csi-volumesnapshot-class: "true"
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Retain
```

Important fields:

| Field | Meaning |
|---|---|
| `velero.io/csi-volumesnapshot-class: "true"` | Allows Velero/OADP to use this snapshot class |
| `driver` | CSI driver name |
| `deletionPolicy: Retain` | Snapshot content is retained after VolumeSnapshot deletion |
| `deletionPolicy: Delete` | Snapshot content is deleted with VolumeSnapshot |

For migration or cross-cluster restore, be careful with default snapshot class annotations. Default snapshot classes can cause unexpected restore behavior when the target cluster has a different CSI setup.

### 3.6 Node Agent

The node agent is deployed as a DaemonSet. It is required for:

- File System Backup with Kopia or Restic
- CSI Data Mover operations
- DataUpload and DataDownload processing
- Reading volume data from nodes
- Restoring volume data back to PVCs

Check node agent:

```bash
oc get ds node-agent -n openshift-adp
oc get pods -n openshift-adp -l name=node-agent
oc logs -n openshift-adp ds/node-agent
```

If node-agent pods are not running on the nodes where application PVCs are mounted, backups can fail or remain stuck.

### 3.7 DataUpload, DataDownload, and BackupRepository

When using CSI Data Mover or newer Kopia-based data movement, OADP/Velero creates additional objects:

| Object | Purpose |
|---|---|
| `DataUpload` | Tracks upload of volume/snapshot data to object storage |
| `DataDownload` | Tracks restore/download of volume data from object storage |
| `BackupRepository` | Represents backup repository used for namespace volume data |

Commands:

```bash
oc get datauploads -A
oc get datadownloads -A
oc get backuprepositories.velero.io -A
oc describe dataupload -n openshift-adp <name>
oc describe datadownload -n openshift-adp <name>
```

## 4. Application Data Backup Methods in OADP

OADP can protect persistent application data through different mechanisms. Choosing the right one is a production design decision.

### 4.1 Method 1: Resource-Only Backup

This backs up only Kubernetes/OpenShift resources, not PV data.

Example use cases:

- Stateless applications
- Applications where data is external, such as external Oracle, PostgreSQL, S3, Kafka, or managed database
- GitOps-managed app where YAML backup is secondary
- Test workloads

Example `Backup` CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: frontend-resource-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - frontend-prod
  includedResources:
    - deployments
    - services
    - routes
    - configmaps
    - secrets
    - serviceaccounts
    - rolebindings
  excludedResources:
    - events
    - pods
    - replicasets
  storageLocation: default
  ttl: 720h0m0s
```

This is fast, but it does not protect data inside PVCs unless volume backup is separately enabled.

### 4.2 Method 2: Native Cloud Snapshot

Native cloud snapshot backup uses cloud provider snapshot APIs for persistent volumes.

Common examples:

- AWS EBS snapshots
- Azure Managed Disk snapshots
- Google Persistent Disk snapshots

Advantages:

- Fast snapshot creation
- Efficient for large volumes
- Usually crash-consistent
- Minimal application downtime

Limitations:

- Snapshot usually stays in the same cloud/storage domain
- Cross-region or cross-cluster recovery needs additional planning
- Not every storage provider supports it
- Snapshot metadata is stored in object storage, but actual snapshot data may remain in the cloud snapshot service

### 4.3 Method 3: CSI Volume Snapshots

CSI snapshots use Kubernetes `VolumeSnapshot`, `VolumeSnapshotContent`, and `VolumeSnapshotClass` APIs.

Good for:

- OpenShift Data Foundation RBD volumes
- CSI drivers that support snapshot API
- Fast rollback or local-cluster recovery
- Large stateful applications

Example flow:

1. CSI driver supports snapshots.
2. `VolumeSnapshotClass` is labeled for Velero.
3. Backup CR includes namespace/PVC resources.
4. Velero creates CSI snapshots.
5. Backup metadata is stored in object storage.

CSI snapshot alone is not always a complete disaster recovery backup if the snapshot remains in the same storage system as the production volume. For true DR, use CSI Data Mover or storage replication to move snapshot data outside the cluster/storage failure domain.

### 4.4 Method 4: File System Backup with Kopia or Restic

File System Backup copies files from mounted volumes into object storage.

It is useful when:

- Storage does not support snapshots
- Workloads use NFS, EFS, Azure Files, or other file shares
- You want data copied to an independent object store
- You need a storage-independent backup method
- You want to protect mounted volume content at file level

Example `Backup` CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-fsb-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  defaultVolumesToFsBackup: true
  storageLocation: default
  ttl: 720h0m0s
```

Important points:

- `nodeAgent.enable` must be `true` in the `DataProtectionApplication`.
- `uploaderType` must be selected during installation/configuration.
- Common uploader choices are `kopia` or `restic`.
- The uploader selection cannot usually be changed casually after repository creation.
- File System Backup reads a live filesystem unless the application is quiesced.
- FSB is usually less point-in-time consistent than CSI snapshots.
- FSB can be slower for millions of small files.

### 4.5 Method 5: CSI Snapshot Data Mover

CSI Data Mover combines snapshot consistency with off-cluster backup storage.

Basic idea:

1. Create a CSI snapshot of the PVC.
2. Read the snapshot data.
3. Upload that data to object storage using Kopia.
4. Restore later by downloading the snapshot data and recreating volume content.

Example `Backup` CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: mysql-csi-datamover-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - mysql-prod
  storageLocation: default
  ttl: 720h0m0s
  csiSnapshotTimeout: 10m0s
  itemOperationTimeout: 4h0m0s
  snapshotMoveData: true
  defaultVolumesToFsBackup: false
```

Key field:

```yaml
snapshotMoveData: true
```

This enables movement of CSI snapshot data to remote object storage.

Data Mover is usually the better enterprise choice when:

- CSI snapshots are supported
- The business needs off-cluster backup data
- You want stronger consistency than live FSB
- You want incremental backup behavior through Kopia-based repositories
- You need disaster recovery beyond the storage array itself

## 5. Production Decision Matrix

| Requirement | Best OADP approach |
|---|---|
| Stateless app | Resource-only backup or GitOps restore |
| App with PVC on CSI snapshot-capable storage | CSI snapshot |
| App with PVC and off-cluster DR requirement | CSI Data Mover |
| NFS/EFS/file-share volume | File System Backup with Kopia/Restic |
| Block-mode PVC | CSI snapshot or CSI Data Mover |
| Filesystem-mode PVC without snapshot support | File System Backup |
| Very large database | Storage snapshot plus database-aware quiescing, or database-native backup plus OADP metadata backup |
| Strict transaction consistency | Database-native backup, or carefully designed quiesce/freeze hooks plus snapshot |
| Cross-cluster migration | Object storage + compatible storage class mapping + restore testing |
| Namespace-admin delegated backup | OADP Self-Service, if supported in your OADP version |

## 6. Backup Consistency: Crash-Consistent vs Application-Consistent

This is where experienced administrators separate “backup completed” from “restore is useful.”

### 6.1 Crash-Consistent Backup

A crash-consistent backup captures data as if the server suddenly lost power.

Most CSI snapshots and live filesystem copies are crash-consistent by default.

This may be acceptable for:

- Many journaling filesystems
- Some databases with WAL/redo logs
- Applications designed to recover after crash
- Caches and non-critical state

But it may not be enough for:

- Databases with heavy writes
- Message brokers
- Distributed systems
- Multi-PVC applications
- Applications requiring ordered writes across volumes

### 6.2 Application-Consistent Backup

Application-consistent backup coordinates with the application before data is captured.

Examples:

- Flush database buffers
- Freeze filesystem
- Put application into maintenance mode
- Pause writes
- Create database-native backup into a PVC
- Snapshot after consistency point
- Unfreeze or resume writes afterward

OADP supports backup hooks to run commands before and after backup. However, hooks must be designed carefully. A hook that opens a database lock and exits immediately might release the lock before the snapshot occurs. For serious database workloads, use database-native backup procedures or validated quiesce mechanisms.

### 6.3 Senior Admin Rule

A backup is not successful because the `Backup` CR says `Completed`. It is successful only when:

1. Restore completes.
2. Application starts.
3. Data is readable.
4. Business transaction validation passes.
5. RPO and RTO are within agreed limits.

## 7. Installing and Configuring OADP for Application Data Backup

The exact installation method depends on your cloud/storage provider, but the high-level design is similar.

### 7.1 Create Namespace

```bash
oc create namespace openshift-adp
```

### 7.2 Create Object Storage Credentials

Example for S3-compatible storage:

```bash
cat > credentials-velero <<'EOF_CREDS'
[default]
aws_access_key_id=<ACCESS_KEY>
aws_secret_access_key=<SECRET_KEY>
EOF_CREDS

oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

### 7.3 Example DataProtectionApplication for S3-Compatible Storage with Kopia

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
      resourceTimeout: 10m
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: ocp-oadp-backups
          prefix: prod-cluster-a
        config:
          region: us-east-1
          s3ForcePathStyle: "true"
          s3Url: https://s3.example.com
        credential:
          name: cloud-credentials
          key: cloud
```

Check DPA status:

```bash
oc get dpa -n openshift-adp
oc describe dpa dpa-sample -n openshift-adp
oc get all -n openshift-adp
oc get backupstoragelocations.velero.io -n openshift-adp
```

Expected:

```text
DataProtectionApplication: Reconciled / Ready
BackupStorageLocation: Available
Velero pod: Running
Node-agent pods: Running, if enabled
```

### 7.4 Example DPA with CSI and Data Mover

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-csi-datamover
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
      featureFlags:
        - EnableCSI
      defaultSnapshotMoveData: true
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: ocp-oadp-backups
          prefix: prod-cluster-a
        config:
          region: us-east-1
          s3ForcePathStyle: "true"
          s3Url: https://s3.example.com
        credential:
          name: cloud-credentials
          key: cloud
```

Notes:

- Include `csi` plugin for CSI snapshots.
- Enable node agent for Data Mover.
- Use Kopia for built-in Data Mover behavior.
- Use `snapshotMoveData: true` in a Backup CR if you want to explicitly control it per backup.

## 8. Application Backup Design Before Creating the Backup CR

Before creating a backup, inspect the application properly.

### 8.1 Identify the Application Namespace

```bash
oc get ns
oc project app-prod
```

### 8.2 Identify Workload Objects

```bash
oc get deploy,sts,ds,job,cronjob -n app-prod
oc get svc,route,ingress -n app-prod
oc get cm,secret -n app-prod
oc get sa,role,rolebinding -n app-prod
```

### 8.3 Identify PVCs

```bash
oc get pvc -n app-prod
oc get pv
oc describe pvc -n app-prod
```

Important PVC details:

- StorageClass
- Access mode
- Volume mode: Filesystem or Block
- Capacity
- Bound PV
- CSI driver
- Snapshot support
- Whether the PVC is used by Deployment or StatefulSet

### 8.4 Identify StorageClass Behavior

```bash
oc get sc
oc describe sc <storageclass>
```

Check:

- Provisioner
- `volumeBindingMode`
- Reclaim policy
- Snapshot class availability
- Encryption behavior
- Whether snapshots are supported

### 8.5 Identify Application Write Behavior

Ask:

- Is it stateless or stateful?
- Is data stored in PVC or outside cluster?
- Does it use one PVC or multiple PVCs?
- Is it a database, queue, object store, or file server?
- Can writes be paused?
- Is there a database-native backup command?
- Is crash consistency acceptable?
- Is restore to another cluster required?

### 8.6 Decide Backup Type

Use this logic:

```text
Does app have PVC?
  No  -> resource-only backup may be enough.
  Yes -> Does CSI snapshot work?
           Yes -> Need off-cluster DR?
                    Yes -> CSI Data Mover.
                    No  -> CSI snapshot may be enough.
           No  -> Use File System Backup with Kopia/Restic.
```

## 11. Backup Hooks for Application Data Consistency

Backup hooks run commands in pods before or after backup processing.

Use cases:

- Flush application buffers
- Freeze a filesystem
- Stop writes briefly
- Put application into maintenance/read-only mode
- Create a logical dump into a PVC before backup
- Run post-backup cleanup

### 11.1 Generic Backup Hook Example

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-backup-with-hooks
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  defaultVolumesToFsBackup: true
  storageLocation: default
  hooks:
    resources:
      - name: quiesce-app
        includedNamespaces:
          - app-prod
        includedResources:
          - pods
        labelSelector:
          matchLabels:
            app: myapp
        pre:
          - exec:
              container: app
              command:
                - /bin/sh
                - -c
                - "echo pre-backup-hook-started && /app/bin/flush-cache"
              onError: Fail
              timeout: 60s
        post:
          - exec:
              container: app
              command:
                - /bin/sh
                - -c
                - "echo post-backup-hook-started && /app/bin/resume-writes"
              onError: Continue
              timeout: 60s
```

### 11.2 Filesystem Freeze Hook Pattern

For some workloads, `fsfreeze` can be used if the container image has the tool and the container has required privileges.

Example pattern:

```yaml
pre:
  - exec:
      container: app
      command:
        - /bin/sh
        - -c
        - "fsfreeze -f /data"
      onError: Fail
      timeout: 30s
post:
  - exec:
      container: app
      command:
        - /bin/sh
        - -c
        - "fsfreeze -u /data"
      onError: Continue
      timeout: 30s
```

Production caution:

- Validate that the application tolerates filesystem freeze.
- Keep freeze duration short.
- Monitor application latency.
- Make sure post-hook always unfreezes the filesystem.
- Never use this blindly on critical databases without vendor validation.

### 11.3 Database Backup Pattern

For databases, a better design is often:

1. Use a database-native dump or backup command.
2. Store the dump in a dedicated backup PVC or object store.
3. Use OADP to protect the PVC containing the dump and the Kubernetes resources.
4. Validate restore by importing the dump.

Examples:

- PostgreSQL: `pg_dump`, `pg_basebackup`, WAL archiving
- MySQL/MariaDB: `mysqldump`, `mysqlbackup`, binary logs
- MongoDB: `mongodump`, Ops Manager/Cloud Manager backups
- Elasticsearch/OpenSearch: snapshot repository
- Kafka: topic replication and offset backup, not simple PVC-only backup

OADP can protect the database pod and PVC, but transaction-level consistency is the database engine’s responsibility.

## 12. Scheduling Application Data Backups

For production, manual backups are not enough. Use `Schedule` CRs.

### 12.1 Daily FSB Backup Schedule

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: reports-prod-daily
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
      - reports-prod
    defaultVolumesToFsBackup: true
    storageLocation: default
    ttl: 168h0m0s
```

This means:

- Run daily at 01:00
- Keep backups for 7 days
- Use FSB for PVC data

### 12.2 Daily CSI Data Mover Schedule

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: mysql-prod-daily-datamover
  namespace: openshift-adp
spec:
  schedule: "30 1 * * *"
  template:
    includedNamespaces:
      - mysql-prod
    storageLocation: default
    ttl: 720h0m0s
    csiSnapshotTimeout: 10m0s
    itemOperationTimeout: 4h0m0s
    snapshotMoveData: true
    defaultVolumesToFsBackup: false
```

### 12.3 Retention Design

Example production retention:

| Backup type | Frequency | TTL |
|---|---:|---:|
| Critical database metadata + PVC | Every 4 hours | 48 hours |
| Daily app backup | Daily | 30 days |
| Weekly full backup | Weekly | 90 days |
| Monthly compliance backup | Monthly | 1 year or policy-based |

Be careful: all retained backups consume object storage. Retention must be aligned with storage cost, compliance, and restore requirements.

## 13. Label-Based Application Data Backup

In shared namespaces, back up only selected application resources with labels.

Example app labels:

```bash
oc label deploy payment-api app.kubernetes.io/part-of=payment -n finance-prod
oc label svc payment-api app.kubernetes.io/part-of=payment -n finance-prod
oc label route payment-api app.kubernetes.io/part-of=payment -n finance-prod
oc label secret payment-db app.kubernetes.io/part-of=payment -n finance-prod
```

Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payment-label-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - finance-prod
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payment
  defaultVolumesToFsBackup: true
  storageLocation: default
  ttl: 720h0m0s
```

Senior admin warning:

Label-based backups can accidentally exclude critical dependencies such as:

- PVCs
- Secrets
- ConfigMaps
- ServiceAccounts
- RoleBindings
- Routes
- NetworkPolicies

Always preview and inspect backup contents.

## 14. Excluding Unsafe or Noisy Resources

Do not blindly back up everything. Exclude resources that are noisy, recreated automatically, or dangerous to restore.

Common exclusions:

```yaml
excludedResources:
  - events
  - pods
  - replicasets
  - endpoints
  - endpointslices
```

For application backups, avoid backing up Operators themselves unless the documentation for that Operator explicitly supports OADP-based backup and restore.

Why?

- Operators reconcile their own resources.
- Restoring Operator-managed resources in the wrong order can break reconciliation.
- CRDs and cluster-scoped resources can conflict on restore.
- Some Operators require their own backup procedure.

Good approach:

- Back up application CRs if supported.
- Reinstall Operators through OLM/GitOps.
- Restore application namespace data after Operator is healthy.
- Follow vendor-specific backup guidance for complex Operators.

## 16. Security Considerations for Application Data Backup

Backups are high-value targets. They often contain Secrets, certificates, private keys, database files, tokens, and customer data.

### 16.1 Protect Object Storage

Use:

- Least-privilege IAM policies
- Dedicated bucket per cluster or environment
- Bucket encryption
- TLS
- Private endpoints if available
- Audit logging
- MFA/delete protection where supported by your process
- Strict access policies

### 16.2 Secret Exposure

OADP can back up Kubernetes Secrets. That is useful for restore, but it means backup storage contains sensitive material.

Controls:

- Encrypt object storage
- Restrict backup bucket access
- Rotate credentials
- Avoid sharing backup archives casually
- Separate prod/non-prod backup locations
- Audit who can create download requests or access logs

### 16.3 Repository Password

Kopia/Restic repositories use repository credentials. Losing or changing repository credentials incorrectly can make older backups unreadable.

Protect:

```bash
oc get secret -n openshift-adp velero-repo-credentials -o yaml
```

Do not rotate blindly without understanding repository impact.

### 16.4 Namespace Admin Self-Service

In newer OADP releases, namespace administrators can perform namespace-scoped backup and restore through Self-Service APIs after cluster-admin configuration.

Benefits:

- Delegates backup operations to app teams
- Restricts users to authorized namespaces
- Reduces cluster-admin dependency
- Keeps central policy control

Risks:

- Users might back up sensitive data without understanding retention
- Restore into live namespace can overwrite or conflict
- Excessive backups can consume object storage
- Download permissions must be controlled

Use RBAC, quotas, naming standards, and policy enforcement.

## 17. OADP Self-Service Concept for Application Data Backup

OADP Self-Service allows namespace admins to back up and restore their own namespace without full cluster-admin privileges, if the cluster administrator enables and configures it.

Key CRs include:

| CR | Purpose |
|---|---|
| `NonAdminBackup` | Namespace-scoped backup request |
| `NonAdminRestore` | Namespace-scoped restore request |
| `NonAdminBackupStorageLocation` | User-specific backup location |
| `NonAdminDownloadRequest` | Download logs/status information |
| `NonAdminController` | Controller that validates and translates requests |

Typical flow:

```text
Namespace admin creates NonAdminBackup
        ↓
NonAdminController validates allowed namespace and policy
        ↓
Controller creates Velero Backup object
        ↓
Velero performs backup
        ↓
Status is reflected back to namespace admin
```

Senior design recommendation:

- Enable Self-Service only after central OADP is stable.
- Use strict RBAC.
- Define allowed namespaces.
- Control BSL usage.
- Define backup TTL limits.
- Monitor backup volume and object storage consumption.
- Document restore approval process for production namespaces.

## 19. Troubleshooting Application Data Backup

### 19.1 BackupStorageLocation Is Unavailable

Symptoms:

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
```

Shows:

```text
Unavailable
```

Check:

```bash
oc describe backupstoragelocation -n openshift-adp default
oc logs -n openshift-adp deploy/velero
oc get secret cloud-credentials -n openshift-adp -o yaml
```

Common causes:

- Wrong access key or secret key
- Wrong bucket name
- Wrong region
- Wrong S3 endpoint
- Missing `s3ForcePathStyle` for S3-compatible storage
- TLS or custom CA problem
- Bucket policy denies list/put/get/delete
- Object store route/DNS not reachable from cluster
- NetworkPolicy or firewall blocking egress

Fix direction:

- Validate credentials outside OADP.
- Confirm bucket exists.
- Confirm endpoint URL.
- Confirm CA trust.
- Confirm OADP pod can resolve and reach object store.

### 19.2 Backup Completes but PVC Data Is Missing

Symptoms:

- Backup says `Completed`
- Restore recreates Deployment/StatefulSet
- PVC is empty or new
- Application starts without old data

Common causes:

- `defaultVolumesToFsBackup: true` not set for FSB
- CSI `VolumeSnapshotClass` not labeled
- DPA missing `csi` plugin
- Node agent not enabled
- Volume type unsupported
- Pod was not running/mounting the volume during FSB
- Excluded PVC/PV resources by label or resource filter

Check:

```bash
velero backup describe <backup> --details
oc get podvolumebackups -A
oc get datauploads -A
oc get volumesnapshots -A
```

### 19.3 Backup Is PartiallyFailed

Check logs:

```bash
velero backup describe <backup> --details
velero backup logs <backup>
oc logs -n openshift-adp deploy/velero
```

Common causes:

- API discovery error
- Permission problem
- CRD not available
- Hook command failed
- Snapshot timeout
- DataUpload failed
- Pod volume backup failed
- Object store write failure
- Resource excluded but dependency still referenced

Production response:

1. Read the backup details.
2. Identify failed items.
3. Decide whether failure affects restore.
4. Fix root cause.
5. Re-run backup.
6. Test restore.

Never treat `PartiallyFailed` as production-ready unless you understand every failed item.

### 19.4 DataUpload Stuck or Failed

Check:

```bash
oc get datauploads -A
oc describe dataupload -n openshift-adp <name>
oc logs -n openshift-adp ds/node-agent
oc logs -n openshift-adp deploy/velero
```

Common causes:

- Node agent not scheduled
- Node selector prevents node agent from running on needed node
- Insufficient CPU/memory
- Object storage slow/unreachable
- Snapshot not ready
- PVC provisioning delay
- XFS filesystem full, causing relabel/no-space issue
- Timeout too low
- Repository credential issue

Fix options:

- Increase `itemOperationTimeout`
- Increase node-agent resources
- Check storage and snapshot readiness
- Resize nearly full volumes
- Use cache PVC configuration where supported
- Validate object store throughput

### 19.5 FSB Is Too Slow

Causes:

- Millions of small files
- Slow NFS backend
- Low CPU/memory on node-agent
- Object storage latency
- Single-node bottleneck
- Compression/dedup overhead
- Network bandwidth limits

Actions:

```bash
oc top pods -n openshift-adp
oc top nodes
oc logs -n openshift-adp ds/node-agent
```

Improve by:

- Scheduling backups during low I/O periods
- Increasing node-agent resources
- Using CSI snapshots/Data Mover if supported
- Reducing unnecessary files
- Excluding cache/temp directories if safe
- Performing application-level logical backups for databases

### 19.6 Restore Fails Due to Existing Resources

Symptoms:

- Restore partially fails
- Resource already exists
- Immutable field errors
- PVC already bound
- Route hostname conflict

Fix options:

- Restore into a clean namespace
- Delete conflicting resources first
- Use namespace mapping
- Use restore resource modifiers if supported
- Restore in phases: storage first, then app resources
- Avoid restoring generated resources like pods/replicasets

### 19.7 Namespace UID/SCC Problems After Restore

OpenShift namespaces have security annotations such as UID ranges and SELinux MCS labels. If namespace backup/restore is incomplete, restored pods might not access data correctly.

Risk cases:

- Backup used label selector but did not include namespace object
- Restore to existing namespace with different UID/SCC annotations
- Different cluster assigns different namespace ranges
- Workload depends on SCC or custom security context

Check:

```bash
oc get ns <namespace> -o yaml
oc describe pod -n <namespace> <pod>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Fix direction:

- Include namespace metadata when needed.
- Restore into correctly prepared namespace.
- Validate SCC/ServiceAccount permissions.
- Avoid hard-coded UIDs in images unless SCC allows it.

### 19.8 Hook Failure

Symptoms:

- Backup fails at pre-hook
- Backup partially fails
- Post-hook does not run or times out

Check:

```bash
velero backup logs <backup-name>
oc logs -n <app-namespace> <pod>
oc describe backup -n openshift-adp <backup-name>
```

Fix:

- Verify command exists in container image.
- Verify container name is correct.
- Increase timeout.
- Use `onError: Continue` only where safe.
- Test commands manually with `oc rsh`.
- Keep hooks simple and deterministic.

## 21. Enterprise Design Patterns

### 21.1 GitOps + OADP Pattern

Use GitOps for desired state and OADP for runtime state.

| Data type | Source of truth |
|---|---|
| Deployment YAML | Git |
| Route/Service/ConfigMap | Git, with Secrets handled securely |
| Secrets | External Secrets/Vault/Sealed Secrets or OADP if acceptable |
| PVC data | OADP, storage snapshots, database-native backup |
| Operator installation | GitOps/OLM |

Restore sequence:

1. Rebuild cluster.
2. Install base Operators.
3. Configure storage classes.
4. Install OADP.
5. Sync GitOps app skeleton if needed.
6. Restore PVC data and runtime resources.
7. Validate application.

### 21.2 Database-Native + OADP Pattern

For important databases:

- Use database-native backup for transaction consistency.
- Store backup artifacts in object storage or PVC.
- Use OADP to back up Kubernetes metadata and optionally backup artifact PVC.
- Test restore using database-native restore command.

This gives stronger data consistency than raw PVC backup alone.

### 21.3 CSI Snapshot + Data Mover Pattern

For large stateful workloads on CSI storage:

- Use CSI snapshot for fast point-in-time capture.
- Use Data Mover to move snapshot data to object storage.
- Use Kopia-based repository for incremental behavior.
- Validate `DataUpload` and `DataDownload` status.

This is a strong OpenShift-native DR pattern.

### 21.4 Multi-Cluster Restore Pattern

For cluster migration:

- Use object storage reachable by both clusters.
- Match OADP versions as closely as possible.
- Match or map StorageClasses.
- Ensure target CSI driver supports restore.
- Prepare namespaces and SCC/RBAC carefully.
- Restore into test namespace first.
- Validate application before production cutover.

## 24. Common Mistakes Made by Administrators

### Mistake 1: Backing Up Only Deployments

A Deployment backup without PVC data is not an application-data backup.

### Mistake 2: Using Same-Cluster Object Storage Without Replication

If both the application and backup bucket are lost together, the backup design failed.

### Mistake 3: Assuming Completed Means Restorable

`Completed` means the backup operation ended successfully. It does not prove the app can be restored and used.

### Mistake 4: Ignoring Database Consistency

Live file copy of a database PVC can be unusable or require crash recovery. For critical databases, use app-aware backup.

### Mistake 5: Not Labeling VolumeSnapshotClass

Without the Velero CSI label, CSI snapshots might not be selected.

### Mistake 6: Forgetting Node Agent

FSB and Data Mover depend on node agent. If it is disabled or not scheduled, volume data backup fails.

### Mistake 7: Backing Up Operators Blindly

Operators should usually be reinstalled, not restored blindly. Follow Operator-specific backup guidance.

### Mistake 8: No Restore Drill

A backup strategy without restore drills is not production-ready.

### Mistake 9: Wrong TTL

Very long TTL can create huge storage cost. Very short TTL can violate compliance/RPO requirements.

### Mistake 10: Not Protecting Backup Credentials

Backup credentials can access sensitive data. Treat them like production secrets.

## 25. Interview and Real-World Questions

### Q1. What is the difference between resource backup and application data backup?

Resource backup protects Kubernetes/OpenShift objects such as Deployments, Services, Routes, Secrets, ConfigMaps, and PVC metadata. Application data backup also protects the actual data inside persistent volumes through snapshots, File System Backup, or Data Mover.

### Q2. When would you use File System Backup?

Use FSB when the storage backend does not support native or CSI snapshots, when using NFS-style volumes, or when you need storage-independent file-level copy to object storage.

### Q3. When is CSI Data Mover better than plain CSI snapshot?

Plain CSI snapshots can remain inside the same storage failure domain. CSI Data Mover copies snapshot data to object storage, making it better for disaster recovery and cross-cluster recovery.

### Q4. Why is object storage location important?

If object storage is inside the same failed cluster/storage system, backups might be lost with the application. Production backups should be stored outside the primary failure domain.

### Q5. What does `defaultVolumesToFsBackup: true` do?

It tells Velero/OADP to back up pod-mounted volumes using File System Backup by default for the selected backup.

### Q6. What does `snapshotMoveData: true` do?

It enables movement of CSI snapshot data to remote object storage using the Data Mover path.

### Q7. How do you verify that Data Mover completed?

Check `DataUpload` objects for backup and `DataDownload` objects for restore.

```bash
oc get datauploads -A
oc get datadownloads -A
```

### Q8. Why can a restore fail in a different namespace?

Because namespace UID ranges, SCCs, RoleBindings, Routes, PVC names, NetworkPolicies, and application configuration might reference the original namespace.

### Q9. Should you back up Operators with OADP?

Usually no. Reinstall Operators through OLM/GitOps and restore application instances according to the Operator’s supported backup process.

### Q10. What is the best proof that backup works?

A successful restore test with application-level validation.

## 26. Senior Administrator Best Practices

1. Design backup per application, not only per namespace.
2. Classify applications by RPO/RTO.
3. Use CSI Data Mover for critical CSI-backed stateful apps when off-cluster DR is required.
4. Use File System Backup for NFS or non-snapshot-capable storage.
5. Use database-native backups for strict consistency.
6. Keep OADP backup storage outside the cluster failure domain.
7. Use labels carefully and validate included resources.
8. Exclude noisy/generated resources.
9. Avoid blind Operator backups.
10. Monitor backup and restore CRs.
11. Watch DataUpload/DataDownload for Data Mover.
12. Watch PodVolumeBackup/PodVolumeRestore for FSB.
13. Protect backup credentials and repository secrets.
14. Use scheduled backups with sensible TTL.
15. Perform regular restore drills.
16. Document runbooks per application.
17. Test restore to same namespace and different namespace.
18. Test restore after OADP upgrades.
19. Test restore after OpenShift upgrades.
20. Keep backup reports for audit and compliance.

## 28. Final Mental Model

Think of OADP application data backup as four layers:

```text
Layer 1: Application identity
  Namespace, labels, ServiceAccounts, RBAC

Layer 2: Application configuration
  Deployment, StatefulSet, ConfigMap, Secret, Service, Route

Layer 3: Application persistent data
  PVC content through CSI snapshot, FSB, or Data Mover

Layer 4: Recovery proof
  Restore test, app startup, data validation, business verification
```

A junior admin asks: “Did the backup complete?”  
A senior admin asks: “Can I restore the app, prove the data is correct, meet RPO/RTO, and survive loss of the primary cluster/storage domain?”

That is the correct way to understand **Backup of Application Data in OADP**.
