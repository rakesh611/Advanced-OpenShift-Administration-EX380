# Migration Use Cases in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift Administration / senior platform engineers / 10+ years experience  
**Scope:** Application-level migration, restore, cloning, cross-cluster recovery, storage-class conversion, and migration planning with OADP/Velero on OpenShift Container Platform.  
**File purpose:** Single Markdown study note and practical runbook.

---

## 1. Executive Summary

In OpenShift APIs for Data Protection (OADP), a **migration use case** usually means using backup-and-restore mechanics to move an application state from one place to another:

- from one namespace to another namespace,
- from one cluster to another cluster,
- from one storage class to another storage class,
- from one region to another region,
- from on-premises to cloud or cloud to on-premises,
- from an older OpenShift/Kubernetes API environment to a newer compatible environment,
- from production to non-production for testing, troubleshooting, validation, or refresh.

OADP is built around **Velero** and provides OpenShift-supported APIs such as `Backup`, `Restore`, `Schedule`, `BackupStorageLocation`, and `VolumeSnapshotLocation`. It can back up Kubernetes/OpenShift resources, internal images, persistent volumes, and VM-related resources depending on the installed version, enabled plugins, and configured data-movement method.

Important senior-admin point: **OADP is not a full cluster migration tool and is not an etcd disaster recovery replacement.** It is primarily an **application data protection and application restore framework**. You can use it for migration, but the more the target environment differs from the source, the more planning you need around operators, CRDs, storage classes, UID/GID ranges, image references, routes, certificates, and API compatibility.

---

## 2. Migration Meaning in OADP

In a normal backup/restore case, the application comes back into the same logical environment. In a migration case, at least one of the restore dimensions changes.

| Migration dimension | Example | OADP mechanism |
|---|---|---|
| Namespace changes | `finance-prod` restored as `finance-uat` | `Restore.spec.namespaceMapping` |
| Cluster changes | Cluster A backup restored on Cluster B | Same BSL credentials/path, compatible APIs, OADP installed on both clusters |
| Storage class changes | `gp2` to `gp3`, `thin-csi` to `ocs-storagecluster-ceph-rbd` | Velero change-storage-class ConfigMap or restore resource modifiers |
| Storage backend changes | NFS to ODF, cloud disk to cloud disk, CSI snapshot data movement | FSB/Kopia/Restic, CSI snapshots, OADP Data Mover depending on support |
| Region changes | AWS `ap-south-1` to `ap-south-2` | Object store replication/share, FSB/Data Mover for volume content |
| Environment changes | Production clone into test | Namespace mapping, route/secret review, reduced replicas |
| API version changes | Source supports older CRD API, target prefers newer API | `EnableAPIGroupVersions`, CRD/operator planning |
| Security context changes | Different namespace UID ranges on target | Namespace/SCC annotation planning and UID/GID mitigation |

## 3. OADP vs MTC vs GitOps vs etcd Restore

A senior OpenShift administrator must decide the right tool before starting a migration.

### 3.1 Use OADP when

Use OADP when you need:

- application backup and restore,
- application-level DR,
- namespace-level restore,
- backup validation,
- restore validation,
- cross-cluster application recovery,
- stateful app clone from prod to test,
- restore to a different namespace,
- backup of Kubernetes resources plus PV data,
- scheduled backup for application namespaces,
- storage-class remapping during restore,
- CSI snapshot-based protection or file-system backup with Kopia/Restic.

### 3.2 Use Migration Toolkit for Containers when

Use MTC when your primary objective is **planned application migration between OpenShift clusters**, especially when you need migration workflows, migration plans, cutover/stage semantics, and migration-focused UX. MTC is designed specifically for container migration, while OADP is designed primarily for application backup and restore.

### 3.3 Use GitOps when

Use GitOps, for example Argo CD or OpenShift GitOps, when resources should be recreated declaratively from Git:

- Deployments
- Services
- Routes
- NetworkPolicies
- RBAC
- ConfigMaps without runtime state
- Operator subscriptions
- Custom resources whose desired state is source-controlled

OADP should protect runtime state and resources that cannot be reliably rebuilt from Git. For mature platforms, the best pattern is often:

```text
GitOps restores desired configuration
+ OADP restores application state/data
+ Operators recreate managed controllers
+ pipelines validate application health
```

### 3.4 Use etcd backup/restore when

Use etcd backup/restore only for **cluster control plane recovery** cases such as quorum loss or restoring the entire cluster state to a previous point. etcd restore is not the right method for selective application migration.

## 4. OADP Migration Architecture

A migration through OADP normally has these moving parts:

```text
Source OpenShift Cluster
  ├─ Application namespace(s)
  ├─ Application resources
  ├─ PersistentVolumeClaims
  ├─ Internal image references / ImageStreams if used
  ├─ OADP Operator / Velero
  ├─ Backup CR
  ├─ BackupStorageLocation
  └─ VolumeSnapshotLocation / FSB / Data Mover
              │
              │ writes metadata + volume data/snapshots
              ▼
Object Storage / Snapshot Store
  ├─ S3-compatible bucket / AWS / Azure / GCP / IBM / ODF NooBaa / RGW
  ├─ Velero backup tarballs
  ├─ backup logs and metadata
  ├─ Kopia/Restic repositories if FSB is used
  └─ Data Mover artifacts if CSI data movement is used
              │
              │ target cluster reads same backup location
              ▼
Target OpenShift Cluster
  ├─ OADP Operator / Velero
  ├─ same or compatible BackupStorageLocation
  ├─ required operators and CRDs preinstalled
  ├─ compatible storage classes
  ├─ namespace mapping if needed
  ├─ Restore CR
  └─ post-restore validation
```

The source cluster writes the backup. The target cluster reads the backup. For cross-cluster restores, your biggest risks are not the YAML objects themselves. The real risks are **storage movement**, **operator compatibility**, **security context mapping**, **API compatibility**, and **environment-specific configuration**.

## 5. Core OADP APIs Involved in Migration

### 5.1 `DataProtectionApplication` — DPA

The `DataProtectionApplication` custom resource controls the OADP deployment. It defines:

- backup storage locations,
- snapshot locations,
- provider plugins,
- node agent configuration,
- uploader type such as `kopia` or `restic`,
- Velero feature flags,
- resource requests and limits,
- plugin configuration.

Example DPA skeleton:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
    - velero:
        provider: aws
        default: true
        objectStorage:
          bucket: oadp-backups
          prefix: cluster-a
        config:
          region: minio
          s3Url: https://s3.example.com
          s3ForcePathStyle: "true"
        credential:
          name: cloud-credentials
          key: cloud
```

### 5.2 `BackupStorageLocation` — BSL

The BSL tells Velero where backup metadata is stored. In migration, the BSL is critical because the target cluster must be able to read the same backup objects.

Senior-admin migration rule:

```text
For cross-cluster migration, target OADP must point to the same object store bucket/prefix or to a replicated/copy-equivalent bucket/prefix.
```

Check BSL status:

```bash
oc get backupstoragelocations -n openshift-adp
oc describe backupstoragelocation <bsl_name> -n openshift-adp
```

### 5.3 `VolumeSnapshotLocation` — VSL

The VSL controls where cloud/provider snapshots are created. This matters when your migration strategy depends on CSI or provider snapshots.

Important limitation:

```text
Snapshot metadata alone is not portable across every provider, region, or storage backend.
```

For cross-provider or cross-region migration, use File System Backup or supported Data Mover rather than assuming native snapshots can be restored elsewhere.

### 5.4 `Backup`

The `Backup` CR defines what to protect.

Example namespace backup:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: finance-prod-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - finance-prod
  storageLocation: default
  ttl: 720h0m0s
  snapshotVolumes: true
```

Example backup with File System Backup:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: finance-prod-fsb-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - finance-prod
  defaultVolumesToFsBackup: true
  storageLocation: default
  ttl: 720h0m0s
```

### 5.5 `Restore`

The `Restore` CR defines how to recover or migrate the backup.

Same namespace restore:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-finance-prod
  namespace: openshift-adp
spec:
  backupName: finance-prod-backup-001
  restorePVs: true
```

Different namespace restore:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-finance-to-uat
  namespace: openshift-adp
spec:
  backupName: finance-prod-backup-001
  restorePVs: true
  namespaceMapping:
    finance-prod: finance-uat
```

## 6. Migration Use Case 1 — Restore Application to a Different Namespace

### 6.1 Business scenario

You have production application `finance-prod` and you want to restore it into `finance-uat` for:

- testing restore procedures,
- data refresh into UAT,
- troubleshooting production bugs,
- audit validation,
- migration dry run,
- developer reproduction of incidents.

### 6.2 Technical pattern

Use `Restore.spec.namespaceMapping`.

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: finance-prod-to-uat-restore
  namespace: openshift-adp
spec:
  backupName: finance-prod-backup-001
  restorePVs: true
  namespaceMapping:
    finance-prod: finance-uat
```

Apply:

```bash
oc apply -f restore-finance-prod-to-uat.yaml
```

Monitor:

```bash
oc get restore -n openshift-adp
oc describe restore finance-prod-to-uat-restore -n openshift-adp
velero restore describe finance-prod-to-uat-restore --details -n openshift-adp
velero restore logs finance-prod-to-uat-restore -n openshift-adp
```

Validate target namespace:

```bash
oc get all -n finance-uat
oc get pvc -n finance-uat
oc get route -n finance-uat
oc get events -n finance-uat --sort-by=.lastTimestamp
```

### 6.3 Senior-admin gotchas

Do not blindly expose restored routes. If source route hostnames are restored, you can conflict with production DNS or OpenShift route admission.

Review:

```bash
oc get route -n finance-uat -o wide
oc get ingress -n finance-uat
```

Scale down target workloads before exposing them if they could send emails, trigger payments, consume queues, or connect to production databases.

Example:

```bash
oc scale deploy --all --replicas=0 -n finance-uat
```

Then selectively start components:

```bash
oc scale deploy/finance-api --replicas=1 -n finance-uat
```

### 6.4 Best practice

For repeatable test refreshes, keep a post-restore patch script:

```bash
#!/usr/bin/env bash
set -euo pipefail

NS=finance-uat

# Prevent accidental production external calls
oc set env deploy/finance-api PAYMENT_GATEWAY_URL=https://mock-payments.example.com -n "$NS"
oc set env deploy/finance-api EMAIL_ENABLED=false -n "$NS"

# Use UAT route hostname
oc patch route finance-api -n "$NS" --type merge -p '{"spec":{"host":"finance-uat.apps.example.com"}}'

# Reduce replicas
oc scale deploy/finance-worker --replicas=1 -n "$NS"
```

## 7. Migration Use Case 2 — Clone Production to Test/UAT

### 7.1 Objective

Create a realistic non-production copy of production while preventing accidental external impact.

### 7.2 Recommended flow

```text
1. Freeze or quiesce application if needed.
2. Run OADP backup of production namespace.
3. Restore into mapped test namespace.
4. Patch ConfigMaps, Secrets, Routes, and external endpoints.
5. Scale controlled workloads.
6. Validate app health.
7. Mask sensitive data if required.
```

### 7.3 Backup example

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: prod-to-test-refresh-2026-07-03
  namespace: openshift-adp
spec:
  includedNamespaces:
    - finance-prod
  defaultVolumesToFsBackup: true
  storageLocation: default
  ttl: 168h0m0s
```

### 7.4 Restore example

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: prod-to-test-refresh-2026-07-03
  namespace: openshift-adp
spec:
  backupName: prod-to-test-refresh-2026-07-03
  restorePVs: true
  namespaceMapping:
    finance-prod: finance-test
```

### 7.5 Post-restore safety checklist

Run this before allowing application users into the restored environment:

```bash
NS=finance-test

oc get route -n "$NS"
oc get secret -n "$NS"
oc get configmap -n "$NS"
oc get cronjob -n "$NS"
oc get job -n "$NS"
oc get deploy,statefulset -n "$NS"
oc get networkpolicy -n "$NS"
```

Check for production endpoints:

```bash
oc get cm,secret -n finance-test -o yaml | egrep -i 'prod|production|smtp|payment|gateway|ldap|sso|kafka|mq|database|redis|api-url'
```

Disable risky CronJobs:

```bash
oc patch cronjob -n finance-test --all -p '{"spec":{"suspend":true}}'
```

### 7.6 Data privacy note

If production data includes sensitive customer information, OADP only moves/restores the data. It does not automatically anonymize or mask it. Data masking is an application/database responsibility.

## 8. Migration Use Case 3 — Same-Cluster Namespace Relocation

### 8.1 Scenario

You need to move an application from an old namespace to a new namespace in the same cluster:

```text
legacy-payment  --->  payment-prod
```

Reasons:

- namespace naming standardization,
- project ownership change,
- RBAC boundary cleanup,
- quota/limit redesign,
- migration from shared namespace to dedicated namespace.

### 8.2 Approach

1. Back up old namespace.
2. Restore into new namespace using namespace mapping.
3. Validate PVCs and routes.
4. Update DNS and external dependencies.
5. Freeze old namespace.
6. Cut over traffic.
7. Decommission old namespace after retention period.

### 8.3 Example

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: legacy-payment-to-payment-prod
  namespace: openshift-adp
spec:
  backupName: legacy-payment-backup
  restorePVs: true
  namespaceMapping:
    legacy-payment: payment-prod
```

### 8.4 Route cutover example

Before switching DNS, expose the target route with a temporary hostname:

```bash
oc patch route payment -n payment-prod --type merge \
  -p '{"spec":{"host":"payment-migration.apps.example.com"}}'
```

Validate:

```bash
curl -k https://payment-migration.apps.example.com/health
```

Then move production hostname during a change window:

```bash
oc patch route payment -n legacy-payment --type merge \
  -p '{"spec":{"host":"payment-old.apps.example.com"}}'

oc patch route payment -n payment-prod --type merge \
  -p '{"spec":{"host":"payment.apps.example.com"}}'
```

## 9. Migration Use Case 4 — Cross-Cluster Migration, Same Platform

### 9.1 Scenario

Move an application from Cluster A to Cluster B:

```text
OCP 4.18 Cluster A  --->  OCP 4.18 Cluster B
```

Both clusters use:

- same or compatible OpenShift version,
- same OADP version,
- same storage provider,
- same object storage endpoint,
- same CRDs/operators installed,
- same identity provider pattern.

This is the cleanest cross-cluster case.

### 9.2 Requirements

On both clusters:

```bash
oc get csv -n openshift-adp
oc get dpa -n openshift-adp
oc get backupstoragelocation -n openshift-adp
oc get volumesnapshotlocation -n openshift-adp
```

The target cluster must be able to read the source backup:

```bash
velero backup get -n openshift-adp
```

If no backup appears on target, check:

- bucket name,
- prefix,
- credentials,
- CA certificate,
- S3 URL,
- region,
- proxy settings,
- `BackupStorageLocation` validation status,
- whether backup sync has completed.

### 9.3 Source backup

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: crm-prod-crosscluster-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - crm-prod
  storageLocation: default
  defaultVolumesToFsBackup: true
  ttl: 720h0m0s
```

### 9.4 Target restore

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: crm-prod-crosscluster-001-restore
  namespace: openshift-adp
spec:
  backupName: crm-prod-crosscluster-001
  restorePVs: true
```

### 9.5 Validation

```bash
oc get ns crm-prod
oc get all -n crm-prod
oc get pvc,pv -n crm-prod
oc get events -n crm-prod --sort-by=.lastTimestamp
velero restore describe crm-prod-crosscluster-001-restore --details -n openshift-adp
```

### 9.6 Production cutover

During cutover:

```text
1. Freeze writes on source.
2. Take final backup.
3. Restore on target.
4. Validate database consistency.
5. Update DNS/Route/Ingress/load balancer.
6. Keep source read-only until sign-off.
7. Decommission source after retention period.
```

## 10. Migration Use Case 5 — Cross-Cluster Migration to Newer OpenShift Version

### 10.1 Scenario

```text
OCP 4.16 source  --->  OCP 4.18/4.19 target
```

This is common when teams build a fresh OpenShift cluster and migrate applications instead of upgrading in place.

### 10.2 Key concern

The target cluster must support the API versions required by restored resources.

Check source API resources:

```bash
oc api-resources > source-api-resources.txt
```

Check target API resources:

```bash
oc api-resources > target-api-resources.txt
```

Compare CRDs:

```bash
oc get crd -o name | sort > source-crds.txt
# Run on target also
oc get crd -o name | sort > target-crds.txt
```

### 10.3 Enable API group versions if needed

For environments where CRDs expose multiple API versions and compatibility matters, enable the Velero feature flag in DPA:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  configuration:
    velero:
      featureFlags:
        - EnableAPIGroupVersions
```

### 10.4 Senior-admin rule

Do not restore custom resources until the target cluster has the correct operators and CRDs installed.

Wrong order:

```text
Restore CRs first -> CRDs missing -> restore errors -> partial restore
```

Correct order:

```text
Install Operators/CRDs first -> validate API resources -> restore app CRs -> validate controllers reconcile them
```

### 10.5 Operator examples

If the app depends on operators such as:

- AMQ Streams,
- OpenShift Data Foundation,
- Red Hat Single Sign-On / Keycloak,
- Crunchy/PostgreSQL operator,
- MongoDB operator,
- OpenShift Pipelines,
- OpenShift Serverless,
- OpenShift Service Mesh,
- OpenShift Virtualization,

install compatible operators on the target before the restore.

## 11. Migration Use Case 6 — Cross-Region Migration

### 11.1 Scenario

```text
AWS Mumbai region    ---> AWS Hyderabad region
Azure Central India  ---> Azure South India
```

### 11.2 Main issue

Cloud volume snapshots are commonly regional. A snapshot created in one region might not be directly restorable in another region without provider-specific snapshot copy/replication. OADP/Velero snapshot metadata does not magically make a cloud disk snapshot portable everywhere.

### 11.3 Recommended OADP strategy

Use one of these:

1. File System Backup with Kopia/Restic.
2. OADP Data Mover for supported CSI snapshot data movement.
3. Provider-native snapshot copy, then configure matching VSL/restore behavior.
4. Application-native replication for databases, and OADP for Kubernetes resources.

### 11.4 Backup with File System Backup

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: ecommerce-prod-region-migration
  namespace: openshift-adp
spec:
  includedNamespaces:
    - ecommerce-prod
  defaultVolumesToFsBackup: true
  storageLocation: replicated-s3
```

### 11.5 Region migration runbook

```text
Preparation phase
  1. Install OADP on both clusters.
  2. Configure replicated/shared object storage.
  3. Configure FSB or Data Mover.
  4. Preinstall operators and CRDs on target.
  5. Create test restore.
  6. Measure backup/restore duration.

Cutover phase
  1. Stop writes on source application.
  2. Run final backup.
  3. Wait for backup completion.
  4. Restore on target.
  5. Validate PVC data and application readiness.
  6. Update DNS/global load balancer.
  7. Monitor error rates and latency.
```

## 12. Migration Use Case 7 — On-Premises to Cloud

### 12.1 Scenario

```text
On-prem OpenShift with ODF/NFS/vSphere storage
        --->
Managed/OpenShift cloud cluster with cloud block storage
```

Examples:

- vSphere/OpenShift to ROSA,
- bare-metal OpenShift to ARO,
- private OpenShift to self-managed AWS/OpenShift,
- ODF-backed namespace to cloud CSI-backed namespace.

### 12.2 What changes

| Area | Source | Target | Risk |
|---|---|---|---|
| Storage class | `ocs-storagecluster-ceph-rbd` | `gp3-csi` / `managed-csi` | PVC restore fails or wrong performance profile |
| Routes | `*.apps.dc1.example.com` | `*.apps.cloud.example.com` | Route conflict or wrong DNS |
| Registry | Internal registry | Different internal/external registry | Image pull failures |
| SCC/UID | Source namespace annotations | Target namespace ranges | File ownership errors |
| Identity | LDAP/OAuth source | Different IdP | RBAC/user/group mismatch |
| Operators | Installed on source | Missing/changed target operator | CRs fail to restore/reconcile |
| Network | On-prem service endpoints | Cloud network endpoints | External dependency failures |

### 12.3 Storage-class mapping example

Create this on target in `openshift-adp`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: change-storage-class-config
  namespace: openshift-adp
  labels:
    velero.io/plugin-config: ""
    velero.io/change-storage-class: RestoreItemAction
data:
  ocs-storagecluster-ceph-rbd: gp3-csi
  ocs-storagecluster-cephfs: efs-csi
```

Apply:

```bash
oc apply -f change-storage-class-config.yaml
```

Then restore:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-onprem-to-cloud
  namespace: openshift-adp
spec:
  backupName: onprem-app-backup-001
  restorePVs: true
```

### 12.4 Image migration concern

If application workloads reference the source cluster internal image registry, target pods might fail with `ImagePullBackOff`.

Check restored workloads:

```bash
oc get deploy,statefulset,daemonset -n app-prod -o yaml | grep -i image:
```

Patch images or mirror them before restore:

```bash
oc image mirror \
  source-registry.example.com/app/backend:1.0 \
  target-registry.example.com/app/backend:1.0
```

For mature production migration, use an enterprise registry independent of a single cluster.

## 13. Migration Use Case 8 — Cloud to On-Premises Repatriation

### 13.1 Scenario

Move workloads from cloud OpenShift back to on-premises OpenShift due to:

- cost optimization,
- data sovereignty,
- latency to legacy systems,
- regulatory requirement,
- cloud exit strategy.

### 13.2 Main concern

Cloud storage classes, load balancers, identity, and managed services might not exist on-premises.

Before backup, identify cloud-specific resources:

```bash
oc api-resources --namespaced=true | while read r _; do oc get "$r" -A --ignore-not-found; done
```

More practical targeted checks:

```bash
oc get svc -A | grep LoadBalancer
oc get pvc -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,SC:.spec.storageClassName,SIZE:.spec.resources.requests.storage
oc get route -A
oc get secret -A | egrep -i 'aws|azure|gcp|cloud|s3|iam|sts'
```

### 13.3 Recommended pattern

```text
1. Rebuild platform foundation on-premises.
2. Install same operators or equivalent operators.
3. Create target storage classes.
4. Configure storage-class mapping.
5. Restore application resources and data.
6. Replace cloud service bindings with on-prem equivalents.
7. Validate performance and storage IOPS.
```

## 14. Migration Use Case 9 — Storage Backend Migration

### 14.1 Scenario

Move application data from one storage backend to another:

```text
NFS storage class       ---> ODF Ceph RBD
thin-csi                ---> ocs-storagecluster-ceph-rbd
gp2                     ---> gp3
standard-csi            ---> premium-csi
```

### 14.2 Why OADP helps

OADP can back up application resources and volume data, then restore PVCs using different storage classes.

### 14.3 Options

| Option | Use when | Notes |
|---|---|---|
| Storage-class ConfigMap | Old and new storage classes are known | Simple and repeatable |
| Resource modifiers | Need JSON patch logic beyond SC mapping | Powerful but more complex |
| FSB/Kopia/Restic | Snapshot portability is not available | Slower but portable |
| App-native migration | Databases with replication/export tools | Often safer for large DBs |

### 14.4 Example ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: change-storage-class-config
  namespace: openshift-adp
  labels:
    velero.io/plugin-config: ""
    velero.io/change-storage-class: RestoreItemAction
data:
  nfs-client: ocs-storagecluster-ceph-rbd
  thin-csi: ocs-storagecluster-ceph-rbd
```

### 14.5 Validation

After restore:

```bash
oc get pvc -n app-prod -o custom-columns=NAME:.metadata.name,SC:.spec.storageClassName,STATUS:.status.phase,VOLUME:.spec.volumeName
oc describe pvc -n app-prod
oc get pods -n app-prod
```

Look for:

- PVC stuck in `Pending`,
- pod stuck in `ContainerCreating`,
- attach/mount errors,
- wrong access mode,
- storage class not found,
- volume binding mode problems,
- file permission errors.

## 15. Migration Use Case 10 — Disaster Recovery to Standby Cluster

### 15.1 Scenario

You maintain a standby OpenShift cluster for DR. OADP backups from primary are restorable on standby.

```text
Primary Cluster  ---> shared/replicated object store ---> Standby Cluster
```

### 15.2 DR architecture

```text
Primary cluster:
  - scheduled OADP backups
  - application quiesce hooks for critical stateful apps
  - object storage replication
  - monitoring backup success

Standby cluster:
  - OADP installed
  - same BSL or replicated BSL configured
  - operators preinstalled
  - storage-class mapping ready
  - restore manifests pre-approved
  - DNS cutover process tested
```

### 15.3 Scheduled backup example

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: banking-prod-hourly
  namespace: openshift-adp
spec:
  schedule: "0 * * * *"
  template:
    includedNamespaces:
      - banking-prod
    defaultVolumesToFsBackup: true
    storageLocation: dr-bucket
    ttl: 168h0m0s
```

### 15.4 DR restore manifest kept ready

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: banking-prod-dr-restore
  namespace: openshift-adp
spec:
  backupName: banking-prod-hourly-<timestamp>
  restorePVs: true
```

### 15.5 DR readiness tests

Run monthly or quarterly:

```bash
velero backup get -n openshift-adp
velero backup describe <latest_backup> --details -n openshift-adp
velero restore create dr-test-$(date +%Y%m%d) \
  --from-backup <latest_backup> \
  --namespace-mappings banking-prod:banking-dr-test \
  --wait \
  -n openshift-adp
```

Validate RTO and RPO:

```text
RPO = How much data can be lost?
RTO = How long until service is restored?
```

OADP can support a DR plan, but your actual RTO/RPO depends on backup frequency, object storage bandwidth, data size, database consistency, restore speed, operator readiness, DNS cutover, and validation automation.

## 17. Migration Use Case 12 — Operator-Managed Application Migration

### 17.1 Why this is hard

Operator-managed applications are not simple YAML plus PVC. They include:

- CRDs,
- custom resources,
- operator controllers,
- finalizers,
- admission webhooks,
- generated Secrets,
- generated ConfigMaps,
- StatefulSets/Deployments managed by the operator,
- backup logic specific to the application.

### 17.2 Rule

Do not back up the operator installation itself as part of the application namespace backup unless the vendor explicitly documents that approach.

General pattern:

```text
1. Install compatible operator on target.
2. Restore application custom resources and data.
3. Let operator reconcile.
4. Validate generated resources.
```

### 17.3 Exclude operator resources example

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-without-operators
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  excludedResources:
    - subscriptions.operators.coreos.com
    - clusterserviceversions.operators.coreos.com
    - installplans.operators.coreos.com
    - operatorgroups.operators.coreos.com
  defaultVolumesToFsBackup: true
```

| Symptom | Likely reason |
|---|---|
| CR restore fails | CRD missing on target |
| CR exists but app not created | Operator not installed or wrong channel/version |
| Webhook blocks restore | Admission webhook active but service unavailable |

## 18. Migration Use Case 13 — Stateful Database Migration

### 18.1 Scenario

Applications with PostgreSQL, MySQL, MongoDB, Redis, Kafka, Elasticsearch, or similar stateful components.

### 18.2 OADP options

| Method | Best for | Risk |
|---|---|---|
| CSI snapshot | Fast crash-consistent volume backup | App consistency depends on storage/app behavior |
| FSB/Kopia/Restic | Portable file-level backup | Slower for large databases |
| Backup hooks | Quiesce/freeze before backup | Requires correct app commands |
| App-native dump/replication | Databases needing transaction consistency | More app-specific work |

### 18.3 Backup hook concept

Use backup hooks to run pre/post commands. Example concept for a filesystem freeze pattern:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: db-backup-with-hooks
  namespace: openshift-adp
spec:
  includedNamespaces:
    - db-prod
  defaultVolumesToFsBackup: true
  hooks:
    resources:
      - name: freeze-db
        includedNamespaces:
          - db-prod
        labelSelector:
          matchLabels:
            app: postgres
        pre:
          - exec:
              container: postgres
              command:
                - /bin/bash
                - -c
                - "echo 'run database quiesce command here'"
              timeout: 30s
        post:
          - exec:
              container: postgres
              command:
                - /bin/bash
                - -c
                - "echo 'run database resume command here'"
              timeout: 30s
```

Replace placeholder commands with actual vendor-supported commands. For production databases, application-native backup or replication is often safer than raw volume capture.

### 18.4 Validation

After restore:

```bash
oc rsh -n db-prod sts/postgres
psql -c "select now();"
```

Check application-level consistency:

```bash
oc logs -n db-prod sts/postgres --tail=100
oc get pvc -n db-prod
oc get pod -n db-prod -o wide
```

## 22. Migration Design Decision Matrix

| Use case | Recommended method | Main risk | Senior recommendation |
|---|---|---|---|
| Same namespace restore | Restore CR | overwriting existing objects | use clean namespace or understand restore conflict behavior |
| Different namespace clone | `namespaceMapping` | route/secret/external endpoint conflicts | patch post-restore config |
| Same-cluster namespace move | backup + namespace mapping | UID/GID and route conflicts | restore into new namespace, validate, cut over DNS |
| Cross-cluster same version | shared BSL + restore | missing operators/storage mismatch | preinstall platform dependencies |
| Cross-cluster newer version | API compatibility | CRD version mismatch | compare `oc api-resources`, use feature flags if needed |
| Cross-region | snapshot portability | snapshots not portable | use FSB/Data Mover or provider snapshot copy |
| Cross-provider | storage and IAM differences | PV restore failure | FSB/Kopia plus storage-class mapping |
| On-prem to cloud | storage/network/registry | image pull and external endpoint failure | mirror images and patch configs |
| Cloud to on-prem | managed services missing | app dependencies unavailable | replace service bindings first |
| DR standby | backup freshness/RTO | restore too slow | regularly test restore and measure RTO |
| Stateful DB migration | consistency | crash-consistent only | use DB-native backup or hooks |
| Operator app migration | CRD/operator mismatch | reconciliation failure | install operators first, exclude operator install resources |
| VM migration | disk/guest consistency | unbootable or inconsistent VM | quiesce/stop VM where needed |

## 26. Storage Migration Deep Dive

### 26.1 Snapshot-based backup

Snapshot-based backup is efficient when source and target use compatible snapshot mechanisms. It is best for same platform/same provider/same region scenarios.

Pros:

- fast for large volumes,
- storage-efficient,
- usually lower CPU overhead.

Cons:

- less portable,
- storage-provider dependent,
- cross-region/cross-cloud limitations,
- application consistency still must be handled.

### 26.2 File System Backup — FSB

FSB backs up volume contents at the filesystem level using Kopia or Restic through the node agent.

Pros:

- more portable,
- useful for NFS and non-snapshot storage,
- useful across providers/regions,
- does not require snapshot location.

Cons:

- slower for large data,
- node-level filesystem access required,
- mounted volumes are required,
- large database files can take time,
- does not support `hostPath` backups.

### 26.3 OADP Data Mover

Data Mover is used with CSI snapshot data movement scenarios. It helps move CSI snapshot contents to object storage using Kopia in supported OADP versions/configurations.

Use it when:

- CSI snapshots are available,
- you need snapshot data moved to object storage,
- you need more portability than provider snapshot metadata alone,
- your OADP version/storage provider supports it.

### 26.4 Storage-class mapping

Use storage-class mapping when the target cluster storage class name differs from the source.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: change-storage-class-config
  namespace: openshift-adp
  labels:
    velero.io/plugin-config: ""
    velero.io/change-storage-class: RestoreItemAction
data:
  old-storage-class: new-storage-class
```

Apply before restore:

```bash
oc apply -f change-storage-class-config.yaml
```

## 27. UID/GID and SCC Migration Issues

### 27.1 Why this matters

OpenShift assigns namespace-level security metadata, including UID range, supplemental group range, and SELinux MCS label. Persistent volume files can be owned by UIDs from the source namespace range. If the target namespace receives a different UID range, pods might not be able to read/write restored data.

Common symptom:

```text
Permission denied
CrashLoopBackOff
Database cannot write to data directory
Application cannot read uploaded files
initdb: could not change permissions
```

### 27.2 Check source namespace annotations

```bash
oc get ns app-prod -o yaml | egrep 'openshift.io/sa.scc.mcs|openshift.io/sa.scc.supplemental-groups|openshift.io/sa.scc.uid-range'
```

### 27.3 Mitigation strategies

| Strategy | Use when | Caution |
|---|---|---|
| Let OADP create target namespace | Clean cross-cluster restore | Avoid pre-existing namespace with wrong annotations |
| Include namespace object in backup | Need SCC annotations preserved | Ensure selectors do not skip namespace |
| Remove pre-existing target namespace | Target namespace has wrong range | Confirm no required resources exist |
| Fix file ownership after restore | App supports chown/init container | Can be slow on large volumes |
| Run with specific SCC/UID | Legacy app needs fixed UID | Security exception; document and approve |
| Use app-native export/import | Database or app can rewrite ownership | Often cleaner |

### 27.4 Example chown init container concept

```yaml
initContainers:
  - name: fix-permissions
    image: registry.access.redhat.com/ubi9/ubi
    command: ["/bin/bash", "-c", "chown -R 1001230000:0 /data && chmod -R g=u /data"]
    securityContext:
      runAsUser: 0
    volumeMounts:
      - name: data
        mountPath: /data
```

This requires appropriate SCC permissions. Do not apply root-based fixes casually in production.

If a route with the same hostname already exists in another namespace, restore can fail or route admission can reject the hostname.

```bash
oc patch route app -n app-restore --type merge \
```

NetworkPolicies are restored exactly as objects. But target cluster namespace labels or pod labels may differ.

## 32. Troubleshooting Migration Failures

### 32.1 Backup does not complete

Check:

```bash
oc describe backup <backup_name> -n openshift-adp
velero backup logs <backup_name> -n openshift-adp
oc logs deploy/velero -n openshift-adp
oc get pods -n openshift-adp
```

Common causes:

- BSL unavailable,
- wrong cloud credentials,
- object storage TLS/CA issue,
- plugin missing,
- DPA not ready,
- node agent not running,
- insufficient CPU/memory,
- stuck volume snapshot,
- unsupported volume type.

### 32.2 Restore partially fails

Check:

```bash
velero restore describe <restore_name> --details -n openshift-adp
velero restore logs <restore_name> -n openshift-adp
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Common causes:

- CRD missing,
- operator missing,
- route hostname conflict,
- storage class missing,
- VolumeSnapshotClass conflict,
- SCC/UID mismatch,
- webhook failure,
- namespace already exists with different annotations,
- resource already exists and restore conflict policy does not update it as expected.

### 32.3 PVC stuck in Pending

```bash
oc describe pvc <pvc> -n <ns>
oc get sc
oc get pv
oc get events -n <ns> --sort-by=.lastTimestamp
```

Possible causes:

- storage class name not found,
- storage class mapping missing,
- access mode unsupported,
- topology constraints,
- WaitForFirstConsumer and no schedulable pod,
- insufficient storage capacity,
- target CSI driver not installed.

### 32.4 Pod permission denied after restore

```bash
oc logs <pod> -n <ns>
oc describe pod <pod> -n <ns>
oc get ns <ns> -o yaml | egrep 'uid-range|supplemental|mcs'
oc rsh <pod> -n <ns> id
```

Possible causes:

- source UID range differs from target,
- restored data owned by old UID,
- SCC prevents expected UID,
- rootless container cannot write restored files.

### 32.5 ImagePullBackOff

```bash
oc describe pod <pod> -n <ns> | egrep -i 'image|pull|denied|unauthorized|not found'
oc get secret -n <ns>
oc get sa default -n <ns> -o yaml
```

Possible causes:

- missing pull secret,
- image in source internal registry only,
- target cluster cannot access registry,
- image digest unavailable,
- disconnected cluster mirror missing.

## 34. Change Window Plan

### 34.1 Before change window

- OADP installed on both clusters.
- BSL validated.
- Test backup completed.
- Test restore completed.
- Operators installed on target.
- Storage mapping tested.
- Route/DNS plan approved.
- Rollback plan approved.
- Application owner signs off test restore.
- Data consistency method agreed.
- Monitoring dashboards ready.

### 34.2 During change window

```text
1. Announce freeze.
2. Stop writes or put app in maintenance mode.
3. Run final backup.
4. Confirm final backup completed without errors.
5. Restore final backup on target.
6. Apply target-specific patches.
7. Validate app health and data.
8. Switch DNS/route/load balancer.
9. Monitor logs, metrics, and user transactions.
10. Keep source available but read-only until sign-off.
```

### 34.3 Rollback

Rollback means:

```text
1. Stop target writes.
2. Move traffic back to source.
3. Investigate target restore issues.
4. Decide whether to resync data or repeat migration.
```

If target accepted writes before rollback, rollback becomes a data reconciliation problem. Plan carefully.

## 35. Production Best Practices

1. **Always perform a test restore.** A backup that has never been restored is only a hope, not a recovery plan.
2. **Do not migrate operators blindly.** Install compatible operators on the target first.
3. **Use File System Backup or Data Mover for portability.** Do not assume snapshots move across regions/providers.
4. **Keep routes disabled or changed during test restores.** Avoid production hostname collisions.
5. **Validate UID/GID ranges.** Most stateful restore surprises are permission-related.
6. **Use storage-class mapping deliberately.** Confirm access modes and performance characteristics.
7. **Use GitOps for desired state.** Use OADP for runtime state and data.
8. **Document every restore warning.** Warnings can become outages during real cutover.
9. **Measure backup and restore duration.** This defines realistic RTO.
10. **Secure backup storage.** Backup repositories can contain Secrets and application data.
11. **Encrypt and restrict backup buckets.** Treat backups as production-sensitive data.
12. **Monitor OADP.** Alert on failed schedules, unavailable BSLs, and restore failures.
13. **Keep Velero CLI compatible with OADP version.** Do not randomly use an incompatible Velero binary.
14. **Protect object storage credentials.** Anyone with access may be able to restore sensitive workloads.
15. **Have application-owner validation.** Platform restore success does not equal business application success.

## 36. Common Interview / Exam Style Questions

### Q1. Can OADP be used for migration?

Yes, but OADP is primarily for backup and restore. It can support migration scenarios such as namespace cloning, cross-cluster application restore, storage-class conversion, and DR restore. For planned large-scale application migration, MTC may be more appropriate.

### Q2. What is required for cross-cluster restore?

- OADP installed on both clusters.
- Target cluster can read the backup storage location.
- Same or compatible BSL name/path/credentials.
- Required operators and CRDs exist on target.
- Compatible OpenShift/Kubernetes API versions.
- Storage classes mapped or available.
- PV data movement method works across the environments.
- UID/GID and route/DNS concerns handled.

### Q3. Why exclude operators from backup?

Operators manage CRDs and reconcile resources. Restoring operator installation artifacts can conflict with OLM, CSVs, webhooks, or existing operator state on the target. Install operators cleanly on target, then restore application CRs/data.

### Q4. Why does a restored pod get permission denied?

The target namespace might have a different UID/GID range from the source. Restored files on PVCs may be owned by source-range UIDs, while target pods run with different UIDs.

### Q5. How do you restore to a different namespace?

Use `Restore.spec.namespaceMapping`:

```yaml
spec:
  backupName: app-backup
  restorePVs: true
  namespaceMapping:
    old-ns: new-ns
```

### Q6. How do you change storage class during restore?

Create `change-storage-class-config` ConfigMap in the Velero/OADP namespace:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: change-storage-class-config
  namespace: openshift-adp
  labels:
    velero.io/plugin-config: ""
    velero.io/change-storage-class: RestoreItemAction
data:
  old-sc: new-sc
```

### Q7. Why use FSB/Kopia/Restic in migration?

Because file-system backups are more portable than native volume snapshots, especially across regions, storage backends, and cloud providers.

### Q8. Can OADP restore to an older Kubernetes/OpenShift version?

Do not plan that. Restoring to an older Kubernetes version than the source is not supported by Velero guidance. Prefer equal or newer compatible target versions and validate API compatibility.

### Q9. What should you validate after restore?

- Backup/restore CR status,
- Velero logs,
- namespace resources,
- PVC binding,
- pod readiness,
- route/DNS,
- app health endpoint,
- database consistency,
- permissions,
- image pull status,
- external dependency connectivity.

### Q10. Is OADP a replacement for etcd backup?

No. OADP protects application resources and data. etcd backup protects cluster control-plane state.

## 38. Senior-Admin Mental Model

Think of OADP migration as four layers:

```text
Layer 1: Kubernetes/OpenShift objects
  - Namespace, Deployment, Service, Route, Secret, ConfigMap, RBAC

Layer 2: Application data
  - PVC contents, database files, uploads, queues, indexes

Layer 3: Platform dependencies
  - Operators, CRDs, SCCs, storage classes, routes, registry, identity

Layer 4: Environment integration
  - DNS, certificates, external APIs, firewalls, monitoring, SSO, business validation
```

OADP is strong at Layer 1 and Layer 2. Migration failures usually happen because Layer 3 or Layer 4 was not prepared.
