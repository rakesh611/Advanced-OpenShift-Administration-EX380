# Backup of Kubernetes Objects in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift administrators with production experience  
**Level:** Senior / 10+ years infrastructure, Linux, Kubernetes, OpenShift administration  
**Scope:** Backup of Kubernetes/OpenShift API objects using OADP/Velero, not full etcd backup and not deep persistent-volume data backup  
**Primary namespace used in examples:** `openshift-adp`

---

## 1. What “Backup of Kubernetes objects” means in OADP

In OADP, a **backup of Kubernetes objects** means exporting selected Kubernetes/OpenShift API resources from the cluster API server and storing them in an object storage backup repository through Velero.

These objects are the YAML/API definitions that describe the application and its platform dependencies, for example:

- `Namespace`
- `Deployment`
- `DeploymentConfig`
- `StatefulSet`
- `DaemonSet`
- `ReplicaSet`
- `Pod`
- `Service`
- `Route`
- `Ingress`
- `ConfigMap`
- `Secret`
- `ServiceAccount`
- `Role`
- `RoleBinding`
- `NetworkPolicy`
- `PersistentVolumeClaim`
- selected `PersistentVolume` objects related to included PVCs
- Custom Resources, such as objects created by Operators
- OpenShift-specific resources such as `BuildConfig`, `ImageStream`, `Route`, and project-scoped security/application resources

Think of it like this:

```text
Kubernetes object backup = API object definitions
Persistent volume backup = application data inside mounted storage
etcd backup = complete cluster control-plane database snapshot
```

OADP object backup is mainly used for **application recovery, migration, namespace recovery, accidental deletion recovery, and controlled disaster recovery of workloads**.

It is **not** a replacement for:

- etcd backup
- full OpenShift control-plane disaster recovery
- full Operator lifecycle backup
- full cluster rebuild automation
- storage-array-level backup
- database-native backup

A senior OpenShift administrator must clearly separate these layers. Many backup failures in production happen because teams assume that backing up YAML objects automatically protects everything required to rebuild the application. That is not always true.

## 2. OADP and Velero relationship

OADP is Red Hat’s supported OpenShift integration for application backup and restore. Internally, it installs and manages Velero and OpenShift-specific plugins.

Main components:

```text
DataProtectionApplication CR
        |
        v
OADP Operator
        |
        v
Velero deployment + plugins + backup/restore CRDs
        |
        v
BackupStorageLocation / VolumeSnapshotLocation
        |
        v
Object storage / snapshot backend / data mover backend
```

Important OADP/Velero API objects:

| API object | Purpose |
|---|---|
| `DataProtectionApplication` | OADP configuration object that deploys Velero and related components |
| `BackupStorageLocation` | Defines where object backup metadata/tarballs are stored |
| `VolumeSnapshotLocation` | Defines where volume snapshots are stored, when snapshot-based backup is used |
| `Backup` | Requests Velero/OADP to create a backup |
| `Restore` | Requests Velero/OADP to restore from a backup |
| `Schedule` | Creates recurring backup jobs |
| `PodVolumeBackup` / `PodVolumeRestore` | Used for filesystem-level volume backup/restore when enabled |
| `DataUpload` / `DataDownload` | Used by newer data mover flows for moving snapshot data, depending on version/configuration |

For Kubernetes object backup, the most important object is:

```yaml
apiVersion: velero.io/v1
kind: Backup
```

Even inside OpenShift, the `Backup` CR belongs to the Velero API group:

```text
velero.io/v1
```

OADP provides the supported OpenShift packaging, plugins, and lifecycle around this API.

## 3. What gets backed up when backing up Kubernetes objects

When a `Backup` CR is created, Velero queries the Kubernetes API server and collects eligible resources according to backup filters.

At a high level:

```text
Backup CR created
    -> Velero BackupController validates it
    -> Velero discovers API resources
    -> Velero filters by namespace/resource/label rules
    -> Velero collects object manifests
    -> Velero runs backup item actions/plugins
    -> Velero writes backup metadata and object data to BackupStorageLocation
```

Object backup usually includes:

### 3.1 Namespace-scoped resources

These resources live inside a namespace/project:

```bash
oc api-resources --namespaced=true
```

Examples:

```text
pods
services
configmaps
secrets
serviceaccounts
roles
rolebindings
deployments.apps
statefulsets.apps
daemonsets.apps
replicasets.apps
routes.route.openshift.io
networkpolicies.networking.k8s.io
persistentvolumeclaims
buildconfigs.build.openshift.io
imagestreams.image.openshift.io
```

### 3.2 Cluster-scoped resources

These resources do not live inside a namespace:

```bash
oc api-resources --namespaced=false
```

Examples:

```text
namespaces
persistentvolumes
storageclasses.storage.k8s.io
customresourcedefinitions.apiextensions.k8s.io
clusterroles.rbac.authorization.k8s.io
clusterrolebindings.rbac.authorization.k8s.io
securitycontextconstraints.security.openshift.io
apiservices.apiregistration.k8s.io
```

Cluster-scoped resources require careful handling. Including too many cluster-scoped objects can make restore dangerous because it can overwrite or conflict with target-cluster platform configuration. Including too few can make an application restore incomplete.

### 3.3 Custom resources

OADP can back up custom resources if their API is discoverable through the Kubernetes API server.

Examples:

```text
certificates.cert-manager.io
kafkas.kafka.strimzi.io
elasticsearches.logging.openshift.io
argocdapplications.argoproj.io
prometheusrules.monitoring.coreos.com
```

But restoring a custom resource requires the **CRD and its controller/operator** to exist on the restore cluster. Backing up the custom resource object is not the same as backing up the Operator installation, Operand lifecycle, webhook configuration, or external system behind it.

Senior admin rule:

```text
For Operator-managed applications, back up the application CRs, but rebuild/reinstall the Operator deliberately before restore unless the vendor explicitly supports full operator restore through OADP.
```

## 4. Object backup vs PV backup vs etcd backup

This topic is specifically about **Kubernetes object backup**.

| Backup type | Protects | Tooling | Restore target | Typical use |
|---|---|---|---|---|
| Kubernetes object backup | YAML/API objects | OADP/Velero `Backup` | Same or different cluster | App/namespace recovery |
| PV snapshot backup | Block/storage snapshot | CSI snapshot / cloud plugin | Same compatible storage backend | Fast volume recovery |
| Filesystem backup | Files inside mounted volume | Kopia/Restic/node agent | Same/different supported storage | NFS/local/non-snapshot storage |
| etcd backup | Complete OpenShift cluster state | OpenShift etcd backup | Same cluster/control-plane recovery | Cluster disaster recovery |
| DB-native backup | Logical/physical database data | PostgreSQL/MySQL/Mongo tools | App/database restore | Consistent database recovery |

For stateless applications, object backup may be enough. For stateful applications, object backup alone is usually not enough.

Example:

```text
Deployment + Service + Route + ConfigMap + Secret = application shape
PVC/PV data = application state
Database dump/WAL/archive = application consistency
```

If you restore only the Kubernetes objects of a database application, you might recreate the `StatefulSet`, `Service`, `Secret`, and `PVC` definitions, but you may not have consistent database data unless volume/data backup is also designed.

## 5. Backup CR anatomy for Kubernetes object backup

A `Backup` CR controls what Velero backs up.

Basic structure:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-object-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
  ttl: 168h0m0s
```

Important fields:

| Field | Meaning |
|---|---|
| `includedNamespaces` | Namespace/project list to include |
| `excludedNamespaces` | Namespace/project list to exclude |
| `includedResources` | Resource kinds to include |
| `excludedResources` | Resource kinds to exclude |
| `includeClusterResources` | Controls cluster-scoped resources |
| `includedClusterScopedResources` | Specific cluster-scoped resource kinds to include |
| `excludedClusterScopedResources` | Specific cluster-scoped resource kinds to exclude |
| `includedNamespaceScopedResources` | Specific namespace-scoped resource kinds to include |
| `excludedNamespaceScopedResources` | Specific namespace-scoped resource kinds to exclude |
| `labelSelector` | Select only objects matching labels |
| `orLabelSelectors` | Select objects matching at least one selector |
| `snapshotVolumes` | Whether PV snapshots should be created |
| `defaultVolumesToFsBackup` | Whether pod volumes should use filesystem backup by default |
| `storageLocation` | BackupStorageLocation name |
| `ttl` | Backup retention period |
| `hooks` | Optional pre-backup exec hooks for pods |
| `orderedResources` | Optional ordering for resources of specific kinds |
| `resourcePolicy` | Reference to reusable resource policy ConfigMap |

For pure Kubernetes object backup, use:

```yaml
snapshotVolumes: false
defaultVolumesToFsBackup: false
```

This prevents accidental volume backup behavior when your intention is only API object protection.

## 6. Prerequisites before object backup

Before creating an object backup in production, validate these points.

### 6.1 OADP namespace and pods

```bash
oc get ns openshift-adp
oc get pods -n openshift-adp
oc get deployment -n openshift-adp
oc get dpa -n openshift-adp
```

Expected:

```text
velero deployment is running
OADP operator is healthy
backup storage location is Available
```

### 6.2 BackupStorageLocation status

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
oc describe backupstoragelocation <bsl-name> -n openshift-adp
```

A healthy BSL normally shows a phase/status such as:

```text
Available
```

If BSL is unavailable, object backup may be created as a Kubernetes CR but fail when uploading data to object storage.

### 6.3 API resource discovery

```bash
oc api-resources | grep -i route
oc api-resources | grep -i deployment
oc api-resources | grep -i imagestream
oc api-resources | grep -i networkpolicy
```

For custom resources:

```bash
oc get crd | grep -i <application-or-operator-name>
oc api-resources --api-group=<group-name>
```

If the API server cannot discover a resource, Velero cannot back it up as a Kubernetes object.

### 6.4 Application labels

For label-based backup, ensure consistent labels:

```bash
oc get all -n myapp --show-labels
oc get cm,secret,route,pvc,networkpolicy -n myapp --show-labels
```

A common production issue is that `Deployment`, `Service`, and `Pod` have application labels, but `Secret`, `ConfigMap`, `Route`, `NetworkPolicy`, and PVC do not. Label-selector backups then miss critical objects.

### 6.5 Permissions

The Velero service account must have permission to list/get/watch the resources you are backing up.

Check:

```bash
oc auth can-i list deployments.apps --as=system:serviceaccount:openshift-adp:velero -n myapp
oc auth can-i list secrets --as=system:serviceaccount:openshift-adp:velero -n myapp
oc auth can-i list routes.route.openshift.io --as=system:serviceaccount:openshift-adp:velero -n myapp
oc auth can-i list crd --as=system:serviceaccount:openshift-adp:velero
```

If your cluster uses restricted RBAC for Velero, lack of permissions can cause partial backups.

## 7. Example 1 — Backup all Kubernetes objects in one namespace

This is the most common application object backup pattern.

### 7.1 YAML

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payroll-objects-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payroll
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
  ttl: 168h0m0s
```

Apply:

```bash
oc apply -f payroll-objects-backup.yaml
```

Monitor:

```bash
oc get backup payroll-objects-001 -n openshift-adp
oc describe backup payroll-objects-001 -n openshift-adp
oc logs deploy/velero -n openshift-adp --tail=200
```

Using Velero CLI:

```bash
velero backup create payroll-objects-001 \
  --namespace openshift-adp \
  --include-namespaces payroll \
  --snapshot-volumes=false \
  --default-volumes-to-fs-backup=false \
  --ttl 168h
```

### 7.2 What this protects

This protects API objects inside the `payroll` namespace, such as:

```bash
oc get deploy,svc,route,cm,secret,sa,role,rolebinding,pvc,networkpolicy -n payroll
```

### 7.3 What this does not fully protect

It does not necessarily protect:

- persistent volume data
- external database data
- external DNS records
- external load balancer configuration
- identity provider users/groups outside the cluster
- container images stored in external registries
- Operator installation itself
- etcd/control-plane recovery state

## 8. Example 2 — Backup selected resource types only

Use this when you want only Kubernetes manifests and not runtime-generated objects.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: frontend-definition-only
  namespace: openshift-adp
spec:
  includedNamespaces:
    - frontend
  includedResources:
    - deployments.apps
    - services
    - routes.route.openshift.io
    - configmaps
    - secrets
    - serviceaccounts
    - roles.rbac.authorization.k8s.io
    - rolebindings.rbac.authorization.k8s.io
    - networkpolicies.networking.k8s.io
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
  ttl: 72h0m0s
```

CLI equivalent:

```bash
velero backup create frontend-definition-only \
  --namespace openshift-adp \
  --include-namespaces frontend \
  --include-resources deployments.apps,services,routes.route.openshift.io,configmaps,secrets,serviceaccounts,roles.rbac.authorization.k8s.io,rolebindings.rbac.authorization.k8s.io,networkpolicies.networking.k8s.io \
  --snapshot-volumes=false \
  --default-volumes-to-fs-backup=false
```

Senior recommendation:

Avoid backing up short-lived objects unless you have a specific reason.

Usually exclude or avoid:

```text
events
pods
replicasets
endpoints
endpointslices
leases
controllerrevisions
```

Why?

Because controllers can recreate these runtime objects. Restoring them may create noise, conflicts, or irrelevant historical state.

## 9. Example 3 — Exclude noisy runtime resources

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-clean-object-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp
  excludedResources:
    - events
    - events.events.k8s.io
    - pods
    - replicasets.apps
    - endpoints
    - endpointslices.discovery.k8s.io
    - leases.coordination.k8s.io
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
  ttl: 168h0m0s
```

This pattern is useful for clean application recovery where controllers recreate runtime state after restore.

Be careful excluding `pods` if you rely on backup hooks that target pods. Backup hooks execute against pods, so excluding pods may not be suitable for every workflow.

## 10. Example 4 — Label-based application backup

Label-based backup is powerful but dangerous if labels are inconsistent.

### 10.1 Label objects consistently

```bash
oc label deployment/payroll-api app.kubernetes.io/part-of=payroll -n payroll
oc label service/payroll-api app.kubernetes.io/part-of=payroll -n payroll
oc label route/payroll-api app.kubernetes.io/part-of=payroll -n payroll
oc label configmap/payroll-config app.kubernetes.io/part-of=payroll -n payroll
oc label secret/payroll-secret app.kubernetes.io/part-of=payroll -n payroll
oc label pvc/payroll-data app.kubernetes.io/part-of=payroll -n payroll
oc label networkpolicy/payroll-netpol app.kubernetes.io/part-of=payroll -n payroll
```

### 10.2 Create backup with label selector

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payroll-label-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payroll
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payroll
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
  ttl: 168h0m0s
```

CLI:

```bash
velero backup create payroll-label-backup \
  --namespace openshift-adp \
  --include-namespaces payroll \
  --selector app.kubernetes.io/part-of=payroll \
  --snapshot-volumes=false \
  --default-volumes-to-fs-backup=false
```

### 10.3 Validate labels before backup

```bash
oc get all,cm,secret,route,pvc,networkpolicy,sa,role,rolebinding \
  -n payroll \
  -l app.kubernetes.io/part-of=payroll
```

If this command does not show every critical object, your backup will be incomplete.

## 11. Example 5 — Multiple label selectors using OR logic

Use `orLabelSelectors` when applications use multiple label conventions.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: mixed-labels-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app1
    - app2
  orLabelSelectors:
    - matchLabels:
        app.kubernetes.io/part-of: payments
    - matchLabels:
        application: payments
    - matchLabels:
        app: payments
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
```

Do not use `labelSelector` and `orLabelSelectors` together in the same backup request.

## 12. Example 6 — Backing up OpenShift Route, Service, Deployment, ConfigMap, Secret only

For an exam/lab or controlled app definition backup:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: route-app-object-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - route-app

    - deployments.apps

    - secrets
```

This uses newer scoped resource filters instead of generic `includedResources`.

```text

includedNamespaceScopedResources/excludedNamespaceScopedResources
includedClusterScopedResources/excludedClusterScopedResources
```

Use one filtering style deliberately.

## 13. Cluster-scoped resources: advanced handling

This is where senior-level OADP design matters.

### 13.1 Default behavior

When backing up all namespaces, cluster-scoped resources may be included by default. When namespace filtering is used, cluster-scoped resources are more limited, but related cluster-scoped objects can still be included by plugin/custom actions, such as PVs related to included PVCs.

### 13.2 Why blindly including all cluster resources is risky

Including all cluster-scoped resources can capture resources such as:

```text
ClusterRoles
ClusterRoleBindings
StorageClasses
CRDs
APIServices
SCCs
OAuth objects
Operator-related cluster objects
Machine/Infrastructure objects
```

Restoring these into another cluster can cause:

- RBAC conflicts
- API registration conflicts
- Operator lifecycle conflicts
- storage class mismatch
- SCC/security mismatch
- platform degradation
- duplicate cluster-wide objects
- unwanted privilege restoration

Senior recommendation:

```text
For application backup, include cluster-scoped resources only when they are required by the application restore plan and are safe to restore.
```

### 13.3 Include only CRDs with a namespace backup

If you are backing up custom resources and need CRD definitions available:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-with-crd-reference
  namespace: openshift-adp
spec:
  includedNamespaces:
    - my-operator-app
  includedClusterScopedResources:
    - customresourcedefinitions.apiextensions.k8s.io
  includedNamespaceScopedResources:
    - '*'
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
```

However, for production restore, prefer this process:

```text
1. Install the required Operator/CRDs on target cluster.
2. Confirm CRD API versions match backup expectations.
3. Restore namespace/application custom resources.
4. Let the Operator reconcile operands.
```

### 13.4 Include only related PVs, not all cluster resources

If backing up PVC objects and expecting PV relationship metadata:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-pvc-object-metadata
  namespace: openshift-adp
spec:
  includedNamespaces:
    - stateful-app
  includedNamespaceScopedResources:
    - persistentvolumeclaims
    - statefulsets.apps
    - services
    - secrets
    - configmaps
  includedClusterScopedResources:
    - persistentvolumes
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
```

But this still does not mean PV data is backed up. It only means the Kubernetes API objects are included.

## 14. BackupStorageLocation and object storage layout

A `BackupStorageLocation` tells Velero where to store backup files.

Example:

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
oc describe backupstoragelocation default -n openshift-adp
```

Typical object backup data stored in the bucket includes:

```text
bucket-or-prefix/
  backups/
    <backup-name>/
      <backup-name>.tar.gz
      velero-backup.json
      <backup-name>-logs.gz
      <backup-name>-results.gz
```

The tarball contains serialized Kubernetes resource definitions. The JSON metadata file records the Backup CR configuration and status information.

Senior operational point:

```text
If the Backup CR exists in Kubernetes but the tarball is missing from object storage, the backup is not usable for real restore.
```

Always validate object storage, not only the `Backup` CR.

## 15. What happens internally during object backup

Detailed flow:

```text
1. Admin creates Backup CR in openshift-adp.
2. Kubernetes API server stores the Backup object.
3. Velero BackupController watches Backup CRs.
4. BackupController validates:
   - BackupStorageLocation
   - selectors
   - resource filters
   - TTL
   - snapshot/fs backup settings
5. Velero performs API discovery.
6. Velero lists eligible resources.
7. Velero applies filters:
   - included/excluded namespaces
   - included/excluded resources
   - labels
   - cluster-scoped resource rules
   - resource policies
   - velero.io/exclude-from-backup=true label
8. Velero runs BackupItemAction plugins.
9. Velero serializes objects.
10. Velero uploads backup artifact and logs to object storage.
11. Backup status becomes Completed, PartiallyFailed, Failed, or another phase.
```

Useful command:

```bash
oc describe backup <backup-name> -n openshift-adp
```

Look for:

```text
Phase
Errors
Warnings
Start Timestamp
Completion Timestamp
Expiration
Storage Location
Included Namespaces
Excluded Namespaces
Included Resources
Excluded Resources
Label Selector
```

## 16. Backup status phases and how to interpret them

Check:

```bash
oc get backups.velero.io -n openshift-adp
oc describe backup <backup-name> -n openshift-adp
```

Common phases:

| Phase | Meaning | Action |
|---|---|---|
| `New` | Backup CR created but not processed yet | Wait/check Velero controller |
| `InProgress` | Backup is running | Monitor logs/events |
| `Completed` | Backup completed successfully | Validate contents and restore test |
| `PartiallyFailed` | Backup completed with errors | Review warnings/errors before trusting |
| `Failed` | Backup failed | Fix root cause and rerun |
| `FailedValidation` | Invalid spec or incompatible options | Correct YAML/CLI options |
| `Deleting` | Backup deletion in progress | Check finalizers/object storage |

Never treat `Completed` as enough for enterprise backup validation. A backup is trustworthy only after a restore test.

## 18. Excluding individual objects

Sometimes a resource matches the namespace or label selector but should not be backed up.

Use this label:

```bash
oc label secret temporary-token \
  velero.io/exclude-from-backup=true \
  -n myapp
```

Example use cases:

- short-lived bootstrap secrets
- temporary test configmaps
- generated secrets that should be recreated

- noisy operator-generated objects

## 19. Backup policy design for production

A production-grade Kubernetes object backup policy usually defines:

```text
What to back up
What not to back up
How often to back up
Where to store it
How long to retain it
Who can restore it
How to validate it
How to audit it
How to protect backup storage
```

### 19.1 Suggested object backup tiers

| Tier | Backup scope | Frequency | Retention | Use case |
|---|---|---|---|---|
| Critical app | Namespace + required objects + secrets | Every 1–4 hours | 7–30 days | Production app recovery |
| Standard app | Namespace objects | Daily | 7–14 days | Normal recovery |
| Platform app CRs | Selected CRs, not full operator | Daily | 14–30 days | Operator-managed workloads |
| Pre-change backup | Namespace/object snapshot before change | On demand | 1–7 days | Change rollback |
| Migration backup | App objects for movement | On demand | Until migration complete | Cluster migration |

### 19.2 Do not use one backup policy for everything

Different applications have different consistency needs.

Example:

```text
Frontend stateless app:
  Object backup may be enough.

PostgreSQL app:
  Object backup + PVC backup + pg_dump/WAL/archive strategy.

Kafka app:
  Object backup + storage strategy + broker/partition recovery plan.

Operator-managed app:
  Object backup + Operator reinstall plan + CRD/API version plan.
```

## 20. Object backup consistency

Kubernetes object backup is not a globally atomic snapshot of the cluster.

If objects are changing during backup, Velero might capture some objects before a change and other objects after a change.

Examples:

```text
Deployment updated while backup is running
Secret rotated during backup
ConfigMap changed during backup
Route modified during backup
Operator reconciles CR while backup is running
```

Senior recommendations:

- Run backup during low-change windows for critical apps.
- Use GitOps as the source of truth where possible.
- Pause high-risk automation during migration backups.
- For databases, use database-native backup hooks or coordinated quiesce steps.
- Validate backup with restore test.

## 21. Backup hooks for object backup workflows

Velero supports backup hooks for pod exec operations.

For object-only backup, hooks may still be useful to:

- flush application config
- pause write activity
- trigger app-level checkpoint
- annotate current state
- run a lightweight consistency command

Example:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-with-pre-hook
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
  hooks:
    resources:
      - name: app-pre-backup-check
        includedNamespaces:
          - myapp
        includedResources:
          - pods
        labelSelector:
          matchLabels:
            app: myapp
        pre:
          - exec:
              container: myapp
              command:
                - /bin/sh
                - -c
                - "echo pre-backup-check && date"
              onError: Continue
              timeout: 30s
```

Operational warning:

If you exclude pods from the backup, ensure hooks still work as expected in your version and configuration. Hooks target pods, so design and test carefully.

## 24. Backing up Secrets: security and operational impact

Secrets are Kubernetes objects, so object backup can include them.

This is both useful and risky.

### 24.1 Why include Secrets

Include Secrets when they are required to restore the application:

```text
TLS certificates
database passwords
pull secrets
application credentials
route certificates
OAuth client secrets
```

### 24.2 Why be careful

Backup storage now contains sensitive credentials. Anyone with access to the backup bucket may be able to extract secrets.

Senior recommendations:

- Encrypt object storage at rest.
- Restrict bucket IAM/policies.
- Separate backup admin and restore admin permissions where possible.
- Rotate credentials after major restore or suspected backup exposure.
- Avoid backing up short-lived tokens.
- Use external secret managers when possible.
- Document whether secrets are included or excluded.

### 24.3 Excluding secrets

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-without-secrets
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp
  excludedResources:
    - secrets
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
```

This is safe only if you have another way to recreate secrets during restore.

## 28. Backing up ImageStreams and internal images

OpenShift applications may depend on ImageStreams.

Object backup of an `ImageStream` backs up the ImageStream API object, but that is not always the same as backing up the actual image layers.

For internal registry/image backup, OADP has separate image backup/migration capabilities depending on version and configuration. Do not assume that object backup alone preserves all image data.

Validate image dependencies:

```bash
oc get is -n myapp
oc get istag -n myapp
oc get deployment -n myapp -o yaml | grep -i image:
oc get buildconfig -n myapp -o yaml | grep -i image
```

Senior recommendation:

For production restore, ensure images are available in:

- external registry
- mirrored registry
- OpenShift internal registry backup/migration process
- GitOps/build pipeline capable of rebuilding images

## 29. Backing up Operator-managed application objects

Operator-managed apps need special attention.

Example resources:

```text
Kafka custom resources
Argo CD Application resources
OpenShift GitOps resources
OpenShift Logging resources
OpenShift Service Mesh resources
cert-manager Certificate resources
```

Recommended restore pattern:

```text
1. Backup namespace custom resources and app-specific secrets/configmaps.
2. Document Operator channel/version/source.
3. Reinstall Operator on target cluster.
4. Confirm CRDs and API versions exist.
5. Restore custom resources.
6. Let Operator reconcile.
7. Validate operands.
```

Avoid this unless vendor-supported:

```text
Backup all operator namespaces + all cluster-scoped operator resources + restore them blindly.
```

Why?

Operators manage cluster-scoped APIs, webhooks, RBAC, finalizers, owner references, and reconciliation loops. A blind restore can cause conflicting controllers or stuck resources.

## 30. Handling ownerReferences, finalizers, and generated objects

### 30.1 OwnerReferences

Kubernetes controllers use owner references to manage dependent resources.

Example:

```text
Deployment -> ReplicaSet -> Pod
StatefulSet -> Pod
Operator CR -> Operand resources
```

Backing up generated child resources may not be necessary. Restoring both parent and child can create conflicts or redundant objects.

Senior preference:

```text
Back up declarative parent resources, not all generated runtime children, unless required.
```

### 30.2 Finalizers

Objects with finalizers can become stuck during deletion or restore scenarios.

Check:

```bash
oc get <resource> <name> -n <ns> -o jsonpath='{.metadata.finalizers}'
```

Common examples:

```text
PVC protection finalizers
operator finalizers
custom resource finalizers
service/load balancer finalizers
```

If you back up CRs with finalizers, make sure their controller exists during restore. Otherwise restored objects may become hard to delete or reconcile.

## 33. Restoring object backup: why backup design matters

Backup and restore are connected. A backup that is easy to create may be hard to restore.

Example restore:

```bash
velero restore create payroll-restore-test \
  --namespace openshift-adp \
  --from-backup payroll-objects-001 \
  --namespace-mappings payroll:payroll-restore
```

Object restore concerns:

| Concern | Why it matters |
|---|---|
| Existing resources | Velero restore is usually non-destructive by default; existing objects may be skipped |
| Namespace remapping | Some object fields still reference original namespace or hostname |
| Cluster-scoped objects | Cannot be namespace-mapped like namespaced objects |
| Secrets | May restore stale credentials |
| Routes | Hostnames may conflict |
| PVCs | Data may not exist unless volume backup is included |
| CRDs | Target cluster must support backed-up API versions |
| Operators | Controllers must exist for custom resources |

## 34. Common mistakes in Kubernetes object backup

### Mistake 1: Assuming namespace backup equals application backup

A namespace may contain only part of an application. Applications often span:

```text
frontend namespace
database namespace
monitoring namespace
shared secret namespace
operator namespace
external systems
```

### Mistake 2: Label selector misses unlabelled resources

Typical missed resources:

```text
Secrets
ConfigMaps
Routes
PVCs
NetworkPolicies
RoleBindings
ServiceAccounts
```

### Mistake 3: Backing up generated runtime objects

Backing up `Pods`, `ReplicaSets`, and `Endpoints` is often unnecessary and noisy.

### Mistake 4: Not testing restore

A backup is not proven until restore is tested.

### Mistake 5: Blindly including cluster-scoped resources

This can damage or confuse target cluster state.

### Mistake 6: Ignoring CRD/API version compatibility

If a custom resource was backed up from API version `example.com/v1beta1`, the target cluster must still serve that version during restore.

### Mistake 7: Treating OADP as etcd DR

OADP is for application backup/restore, not full control-plane recovery.

## 37. Senior-level backup architecture pattern

For a critical production application, design backup in layers:

```text
Layer 1: GitOps repository
  - Desired state YAML, Helm, Kustomize, Argo CD apps

Layer 2: OADP Kubernetes object backup
  - Runtime cluster objects, secrets, routes, RBAC, CRs

Layer 3: Persistent volume backup
  - CSI snapshot or filesystem backup

Layer 4: Application-native backup
  - Database dump, transaction logs, object store replication

Layer 5: Platform DR
  - etcd backup, install-config, ignition, cluster version, infrastructure state

Layer 6: Restore runbook
  - Tested restore sequence with RTO/RPO targets
```

Never depend on only one layer.

## 38. RTO/RPO considerations

### RPO: Recovery Point Objective

How much data/configuration can you afford to lose?

For object backup:

```text
Daily backup -> up to 24 hours of object changes lost
Hourly backup -> up to 1 hour of object changes lost
Pre-change backup -> protects against that specific change
```

### RTO: Recovery Time Objective

How quickly can you restore service?

Object restore RTO depends on:

```text
backup size
number of Kubernetes objects
API server performance
target cluster readiness
operator readiness
image availability
PVC/data restore time
DNS/route readiness
team runbook quality
```

Object backup itself is often fast. Real recovery may be slow because of dependencies outside the object backup.

## 42. OADP object backup and GitOps

OADP and GitOps solve different problems.

| GitOps | OADP object backup |
|---|---|
| Desired declarative state | Runtime API backup |
| Usually excludes generated runtime secrets | Can capture current secrets |
| Good for rebuild | Good for recovery of current state |
| Requires repo health | Requires backup storage health |
| Human-reviewed changes | Captures actual cluster state |

Best practice:

```text
Use GitOps for desired state.
Use OADP for runtime recovery and migration.
Use both for critical production applications.
```

Example:

```text
Argo CD recreates Deployment/Service/Route.
OADP restores runtime Secret/PVC metadata/NetworkPolicy/custom resources.
Database-native restore recovers data.
```

## 44. Special OpenShift considerations

### 44.1 SecurityContextConstraints

SCCs are cluster-scoped. Most applications should not require restoring SCC objects. Instead, restore namespace `ServiceAccount`, `Role`, and `RoleBinding`, and reapply SCC grants deliberately if required.

Check SCC usage:

```bash
oc adm policy who-can use scc anyuid
oc get pod -n myapp -o yaml | grep -i openshift.io/scc
```

### 44.2 Namespace annotations

OpenShift projects/namespaces may have important annotations:

```text
openshift.io/description
openshift.io/display-name
openshift.io/requester
security.openshift.io/sa.scc.uid-range
openshift.io/sa.scc.mcs
openshift.io/sa.scc.supplemental-groups
```

Be careful restoring namespace objects across clusters because UID/GID ranges and SCC annotations may differ.

### 44.3 Routes

Route restore depends on target cluster ingress domain. Same hostname can conflict if source and target are both active.

### 44.4 ImageStreams

ImageStream object backup does not guarantee actual image blob availability.

### 44.5 BuildConfigs

BuildConfig restore may require:

```text
source repository access
webhook secrets
builder images
output image stream
pull secrets
```

```yaml
    - endpointslices.discovery.k8s.io
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
  ttl: 168h0m0s
```

## 47. Interview/exam explanation

If asked to explain “Backup of Kubernetes objects in OADP,” answer like this:

> In OADP, Kubernetes object backup is performed through Velero Backup CRs. The Backup controller queries the Kubernetes API server, discovers resources, applies namespace/resource/label filters, serializes eligible API objects, and stores the backup artifact and metadata in the configured BackupStorageLocation. This protects application definitions such as Deployments, Services, Routes, ConfigMaps, Secrets, RBAC, PVC objects, NetworkPolicies, and custom resources. It does not automatically mean the application data inside persistent volumes is protected, and it is not a full etcd or OpenShift control-plane disaster recovery solution. For production, I design object backups by namespace or application labels, exclude noisy runtime resources, handle cluster-scoped resources carefully, secure Secrets in backup storage, and always validate with a restore test.

## 48. Real-world senior admin notes

1. **Backup creation is easy; restore correctness is hard.** Always design from restore backward.
2. **Do not blindly back up the whole cluster with OADP.** It is for application backup, not full cluster DR.
3. **Label strategy matters.** Bad labels produce incomplete backups.
4. **Secrets are sensitive.** Treat backup buckets as sensitive credential stores.
5. **Cluster-scoped resources are dangerous.** Include only what is required.
6. **CRDs and Operators need planning.** Custom resources are not useful if the target cluster cannot serve the API.
7. **Object backup is not data consistency.** Databases need database-aware backup.
8. **Restore tests prove backup value.** No restore test means no confidence.
9. **GitOps and OADP complement each other.** Use both.
10. **Document every backup scope.** During incidents, unclear backup scope wastes recovery time.

## 49. Minimal lab workflow

Create a sample application:

```bash
oc new-project demo-oadp-objects
oc create deployment hello --image=registry.access.redhat.com/ubi9/httpd-24
oc expose deployment hello --port=8080
oc expose service hello
oc create configmap hello-config --from-literal=ENV=demo
oc create secret generic hello-secret --from-literal=password=redhat
```

Create object-only backup:

```bash
velero backup create demo-oadp-objects-backup \
  --namespace openshift-adp \
  --include-namespaces demo-oadp-objects \
  --snapshot-volumes=false \
  --default-volumes-to-fs-backup=false
```

Verify:

```bash
velero backup describe demo-oadp-objects-backup \
  --namespace openshift-adp \
  --details
```

Restore to another namespace:

```bash
velero restore create demo-oadp-objects-restore \
  --namespace openshift-adp \
  --from-backup demo-oadp-objects-backup \
  --namespace-mappings demo-oadp-objects:demo-oadp-objects-restore
```

Check:

```bash
oc get all -n demo-oadp-objects-restore
oc get cm,secret,route -n demo-oadp-objects-restore
```

Clean up:

```bash
oc delete project demo-oadp-objects-restore
oc delete project demo-oadp-objects
```

## 50. Final summary

Backup of Kubernetes objects in OADP is the process of capturing application and platform API resources from OpenShift through Velero Backup CRs and storing them in a configured BackupStorageLocation.

For advanced administration, the key is not only knowing the command. The key is understanding backup scope, API discovery, labels, resource filters, cluster-scoped dependencies, security implications, restore compatibility, and validation.

A good Kubernetes object backup strategy answers these questions:

```text
Which namespaces are protected?
Which resources are included and excluded?
Are secrets included?
Are cluster-scoped resources required?
Are custom resources restorable on the target cluster?
Is PV/application data protected separately?
Where is backup data stored?
Who can access it?
How long is it retained?
When was the last successful restore test?
```

If you can answer these clearly, you are operating OADP like a senior OpenShift administrator.
