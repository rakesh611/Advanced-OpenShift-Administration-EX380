## 1. What is OADP?

**OADP** means **OpenShift APIs for Data Protection**. It is Red Hat's OpenShift-integrated data protection operator that installs and manages **Velero** and OpenShift-specific Velero plugins to back up and restore application workloads on OpenShift.

OADP provides Kubernetes/OpenShift APIs for:

- On-demand application backups
- Scheduled backups
- Application restores
- Persistent volume protection
- Namespace-scoped workload recovery
- Internal image backup
- Backup hooks and restore hooks
- CSI snapshot-based backup
- File-system-level backup with Restic or Kopia
- CSI snapshot data movement to object storage
- Namespace-admin self-service backup/restore in newer OADP versions

At a high level:

```text
OADP Operator + DataProtectionApplication CR
        |
        v
Velero server + OpenShift plugins + cloud/CSI plugins + node agent
        |
        +--> Kubernetes/OpenShift API objects backup
        +--> PersistentVolume backup using snapshot / filesystem backup / data mover
        +--> Object storage and snapshot storage integration
```

OADP is not just a backup command. It is an operator-managed backup architecture that introduces CRDs and controllers into the OpenShift cluster.

## 2. Important boundary: OADP is not etcd full-cluster DR

A senior OpenShift administrator must understand the boundary clearly.

### OADP protects

OADP is designed mainly for **customer applications and application-related resources**, such as:

- Namespaces/projects
- Deployments, DeploymentConfigs, StatefulSets, DaemonSets, Jobs, CronJobs
- Services, Routes, Ingresses
- ConfigMaps and Secrets
- PersistentVolumeClaims and PersistentVolumes
- Internal images used by applications
- Selected cluster-scoped resources required by applications
- OpenShift Virtualization VM resources when configured with the proper plugin

### OADP does not replace

OADP does **not** replace:

- etcd backup and restore
- OpenShift control-plane disaster recovery
- Full cluster restore
- Operator lifecycle backup strategy
- Infrastructure backup
- Storage backend replication
- Database-native backup
- GitOps repository backup
- Registry backend backup in all designs

### Why this matters

For real production disaster recovery, you normally need multiple layers:

```text
Layer 1: etcd backup                      -> cluster state recovery
Layer 2: OADP backup                      -> application workload recovery
Layer 3: Storage replication/snapshots    -> data durability
Layer 4: Database-native backups          -> application consistency
Layer 5: GitOps repository                -> desired-state rebuild
Layer 6: Image registry backup            -> image availability
```

OADP is strongest when used as an **application-centric backup and restore framework**, not as the only DR mechanism for the entire OpenShift platform.

OADP architecture can be understood in seven layers.

```text
                                      |

| Reconciles DataProtectionApplication and installs/configures Velero components  |
+--------------------------------------------------------------------------------+
                                      |
                                      v
+--------------------------------------------------------------------------------+

+--------------------------------------------------------------------------------+

+---------------------------+   +---------------------------+   +------------------+
```

## 4. Main components

### 4.1 OADP Operator

The OADP Operator is installed through Operator Lifecycle Manager.

Its job is to:

- Install OADP CRDs
- Watch `DataProtectionApplication` custom resources
- Deploy and configure Velero
- Configure plugins
- Configure backup locations
- Configure snapshot locations
- Configure node agent for file-system backup and Data Mover
- Manage generated Velero resources
- Report status through the DPA object

You do not manually deploy Velero in a normal OADP deployment. You declare the desired state using the DPA CR, and the operator reconciles the Velero deployment.

### 4.2 DataProtectionApplication CR

`DataProtectionApplication` is the main OADP configuration object.

It defines:

- Which Velero plugins are enabled
- Backup storage locations
- Snapshot locations
- Whether node agent is enabled
- Whether Kopia or Restic is used
- Resource requests and limits
- Feature flags
- Plugin-specific configuration
- Self-Service policy/enforcement in supported versions

### 4.3 Velero Deployment

Velero is the core backup/restore engine. Inside OpenShift, it usually runs as a Deployment in `openshift-adp`.

Velero watches CRs such as:

- `Backup`
- `Restore`
- `Schedule`
- `BackupStorageLocation`
- `VolumeSnapshotLocation`

Velero then performs the backup/restore operation by talking to:

- Kubernetes/OpenShift API server
- Object storage
- Snapshot APIs
- CSI snapshot APIs
- Node agent for file-system backup
- Data Mover controllers for CSI snapshot movement

### 4.4 Node Agent

The node agent runs on worker nodes, usually as a DaemonSet.

It is used for:

- File System Backup
- Restic/Kopia volume data backup
- CSI Data Mover upload/download workflows
- Reading data from mounted volumes or snapshot volumes
- Uploading volume data to object storage repositories
- Restoring data into target PVCs

Without node agent, Velero can still back up Kubernetes objects, but filesystem-level PV backup and Data Mover workflows will not work.

### 4.5 BackupStorageLocation

`BackupStorageLocation` defines where Velero stores backup metadata and, for file-system backup or Data Mover, volume data.

Common backends:

- AWS S3
- S3-compatible storage
- OpenShift Data Foundation Multicloud Object Gateway
- MinIO
- Azure Blob
- Google Cloud Storage
- IBM Cloud Object Storage S3

### 4.6 VolumeSnapshotLocation

`VolumeSnapshotLocation` defines where volume snapshots are created for native cloud snapshot plugins.

For CSI snapshots, Kubernetes `VolumeSnapshot`, `VolumeSnapshotContent`, and `VolumeSnapshotClass` objects are also involved.

### 4.7 Plugins

OADP uses Velero plugins for provider-specific and OpenShift-specific behavior.

Important plugins:

| Plugin | Purpose |
|---|---|
| `openshift` | OpenShift resource handling |
| `aws` | S3 object store and EBS snapshot integration |
| `azure` | Azure Blob and Azure disk snapshot integration |
| `gcp` | Google Cloud Storage and disk snapshot integration |
| `csi` | CSI snapshot backup and restore |
| `kubevirt` | OpenShift Virtualization backup/restore workflows |

### 4.8 Data Mover

OADP Data Mover moves CSI snapshot data to object storage, normally using Kopia.

It is used when you do not want to depend only on storage-side snapshots for long-term retention or cross-cluster recovery.

## 6. DataProtectionApplication architecture

The DPA CR is the bridge between the OpenShift Operator model and Velero runtime configuration.

### 6.1 What DPA controls

The DPA controls:

```yaml
spec:
  backupLocations:
  snapshotLocations:
  configuration:
    velero:
      defaultPlugins:
      featureFlags:
      resourceTimeout:
      defaultVolumesToFSBackup:
      defaultSnapshotMoveData:
    nodeAgent:
      enable:
      uploaderType:
```

### 6.2 Reconciliation flow

```text
Admin creates DataProtectionApplication
        |
        v
OADP Operator validates DPA
        |
        v
Operator creates/updates Velero Deployment
        |
        +--> Creates BackupStorageLocation objects
        +--> Creates VolumeSnapshotLocation objects
        +--> Creates node-agent DaemonSet if enabled
        +--> Configures plugins
        +--> Configures credentials
        +--> Updates DPA status
```

### 6.3 DPA status

The DPA status is one of the first things to check in troubleshooting:

```bash
oc get dpa -n openshift-adp
oc describe dpa <dpa-name> -n openshift-adp
oc get dpa <dpa-name> -n openshift-adp -o yaml
```

Healthy DPA means the operator has successfully deployed the required OADP/Velero components. It does not guarantee every backup will succeed, because backup success also depends on object storage, storage class, CSI driver, snapshot support, RBAC, and workload consistency.

## 7. Velero control-plane architecture inside OADP

Velero acts like a Kubernetes controller.

It watches backup-related CRs and reconciles them.

```text
Backup CR created
      |
      v
Velero backup controller sees new Backup
      |
      v
Validates BSL, VSL, plugins, namespace filters, label filters
      |
      v
Discovers Kubernetes/OpenShift resources
      |
      v
Runs pre-backup hooks if defined
      |
      v
Backs up API objects to tar archive in object storage
      |
      v
Backs up PV data using snapshot / FSB / Data Mover
      |
      v
Runs post-backup hooks
      |
      v
Updates Backup status
```

Velero is not a database backup tool by itself. It captures Kubernetes objects and PV data. Application-consistent backup for databases usually requires pre/post hooks or database-native backup integration.

## 8. Backup architecture

A backup contains two major categories of data.

### 8.1 Kubernetes/OpenShift API objects

These are exported from the Kubernetes/OpenShift API server and stored in object storage.

Examples:

- Namespace
- Deployment
- DeploymentConfig
- StatefulSet
- Service
- Route
- ConfigMap
- Secret
- PVC
- ServiceAccount
- Role and RoleBinding
- ImageStream
- Custom resources, if included

### 8.2 Persistent volume data

PV data can be protected through:

1. Native cloud snapshot
2. CSI snapshot
3. File System Backup using Restic/Kopia
4. CSI snapshot Data Mover using Kopia

### 8.3 Backup object archive

Velero stores a backup archive in the configured object storage bucket.

Conceptually:

```text
s3://bucket/velero/backups/<backup-name>/
  backup.json
  backup.tar.gz
  backup-volume-info.json
  logs.gz
  podvolumebackups/
  resource-list.json
```

The exact files can vary by version and feature, but the architectural idea is that object metadata goes into object storage, while PV data is handled by snapshot or repository mechanisms.

### 8.4 Backup filtering

OADP/Velero supports filtering by:

- Included namespaces
- Excluded namespaces
- Included resources
- Excluded resources
- Label selector
- Storage location
- Snapshot location
- TTL

Example design:

```yaml
spec:
  includedNamespaces:
  - finance-prod
  excludedResources:
  - events
  - events.events.k8s.io
  storageLocation: default
  ttl: 720h0m0s
```

## 9. Restore architecture

Restore is the reverse operation, but not a simple copy-back.

```text
Restore CR created
      |
      v
Velero reads backup metadata from BackupStorageLocation
      |
      v
Validates restore filters and target namespace mapping
      |
      v
Recreates Kubernetes/OpenShift objects
      |
      v
Restores PVs using snapshot / FSB / Data Mover
      |
      v
Runs restore hooks if configured
      |
      v
Updates Restore status
```

### 9.1 Restore complexity

Restore is often harder than backup because the target cluster may have:

- Different storage classes
- Different SCC/security policy
- Different routes/domains
- Different image registry configuration
- Different CRD versions
- Missing Operators
- Existing resources with same names
- Admission webhooks blocking object creation
- Missing `VolumeSnapshotClass`
- Different cloud provider or region

### 9.2 Namespace mapping

A common restore requirement is restoring to a different namespace.

Example:

```yaml
spec:
  backupName: app1-backup
  namespaceMapping:
    app1-prod: app1-restore-test
```

### 9.3 StorageClass mapping

When restoring across clusters with different storage classes, you might need storage class mapping.

Example scenario:

```text
Source cluster: ocs-storagecluster-ceph-rbd
Target cluster: odf-ceph-rbd
```

If you do not map the class correctly, PVCs may remain Pending or bind to the wrong storage backend.

## 10. Persistent volume backup architecture

PV backup is the most important architecture decision in OADP.

### 10.1 Decision matrix

| Method | How it works | Best for | Limitation |
|---|---|---|---|
| Native cloud snapshot | Cloud provider snapshot API | AWS EBS, Azure Disk, GCP PD | Usually provider/region-specific |
| CSI snapshot | Kubernetes VolumeSnapshot API | ODF/Ceph RBD/CephFS and CSI-backed storage | Requires CSI driver snapshot support |
| File System Backup | Node agent reads mounted filesystem and uploads to object store | NFS, unsupported snapshot backends, simple workloads | Reads live filesystem; consistency depends on app/hooks |
| CSI Data Mover | Takes CSI snapshot, mounts/reads snapshot, uploads to object store using Kopia | Long-term/cross-cluster durable PV backup | Requires CSI snapshot support and node agent/Data Mover config |

### 10.2 How to choose

Use this mental model:

```text
Is the PV backed by a CSI driver with snapshot support?
        |
        +-- Yes --> Use CSI snapshot
                    |
                    +-- Need durable/cross-cluster object storage copy?
                        |
                        +-- Yes --> Use CSI Data Mover
                        +-- No  --> Snapshot-only may be enough
        |
        +-- No --> Use File System Backup with Restic/Kopia
```

### 10.3 Application consistency

Storage snapshots are usually crash-consistent unless the application is quiesced.

For databases, consider:

- Database-native backup
- Pre-backup hooks
- Post-backup hooks
- Application flush/freeze commands
- Read-only mode during backup
- Transaction log backup
- Consistency checks after restore

For filesystem workloads, hooks might run:

```bash
fsfreeze --freeze /mount/path
fsfreeze --unfreeze /mount/path
```

But for many container images, `fsfreeze` might not be present. You may need custom images or application-specific commands.

## 11. CSI snapshot architecture

CSI snapshot backup uses Kubernetes snapshot APIs.

### 11.1 Required APIs

```bash
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

### 11.2 Required storage support

Your CSI driver must support:

- `VolumeSnapshotClass`
- `VolumeSnapshot`
- `VolumeSnapshotContent`
- Snapshot restore / volume creation from snapshot

### 11.3 CSI snapshot flow

```text
Backup CR created
      |
      v
Velero CSI plugin identifies PVCs
      |
      v
Creates VolumeSnapshot objects
      |
      v
CSI snapshot controller provisions VolumeSnapshotContent
      |
      v
Backend storage creates snapshot
      |
      v
Velero records snapshot metadata in backup
```

### 11.4 Restore from CSI snapshot

```text
Restore CR created
      |
      v
Velero reads backup metadata
      |
      v
Creates PVC/DataSource objects referencing snapshots
      |
      v
CSI provisioner creates new PV from snapshot
      |
      v
Application pods attach restored PVC
```

### 11.5 Common CSI snapshot problems

| Symptom | Likely cause |
|---|---|
| `VolumeSnapshot` stuck | CSI driver snapshot controller issue |
| Backup partially failed | PVC has no supported snapshot class |
| Restore PVC Pending | Missing storage class or snapshot class in target cluster |
| Snapshot not found | Snapshot is region/provider-bound or deleted |
| Cross-cluster restore fails | Snapshot metadata exists but backend snapshot is not available in target cluster |

## 12. File System Backup architecture: Restic and Kopia

File System Backup, often called FSB, backs up files from the filesystem level rather than using storage snapshots.

### 12.1 FSB flow

```text
Backup CR created
      |
      v
Velero selects pods/PVCs for filesystem backup
      |
      v
Node agent on the node accesses pod volume mount
      |
      v
Restic/Kopia reads files from the mounted filesystem
      |
      v
Data is uploaded to object storage repository
      |
      v
Backup status records PodVolumeBackup results
```

### 12.2 When FSB is useful

Use FSB when:

- Storage backend does not support snapshots
- NFS or file storage has no CSI snapshot capability
- You need simple object-storage-based volume backup
- You want backup portability over storage-side snapshot dependency

### 12.3 FSB limitations

- It reads live filesystem data unless the application is quiesced.
- Backup time depends on file count and data size.
- Large numbers of small files can be slow.
- It consumes node CPU, memory, and network bandwidth.
- It might require pod volume annotations or default configuration depending on version and settings.
- Block-mode PV backup is not handled the same way as filesystem-mode PV backup.

### 12.4 Restic vs Kopia

| Item | Restic | Kopia |
|---|---|---|
| Type | Backup repository tool | Backup repository tool |
| Used by | Older/default FSB paths in many environments | Modern OADP Data Mover and newer FSB workflows |
| Deduplication | Yes | Yes |
| Incremental backup | Yes | Yes |
| Data Mover | Not the main mechanism | Common uploader mechanism |

In current OADP designs, Kopia is very important because Data Mover uses Kopia to move CSI snapshot data to object storage.

## 13. OADP Data Mover architecture

OADP Data Mover solves an important problem: storage snapshots are not always enough for disaster recovery.

A snapshot might be tied to:

- One storage backend
- One cloud provider
- One region
- One cluster
- One availability zone

Data Mover moves snapshot data into object storage so the backup is more durable and portable.

### 13.1 Data Mover flow

```text
Backup CR
  |
  v
Velero CSI plugin creates CSI VolumeSnapshot
  |
  v
DataUpload CR created per volume/snapshot
  |
  v
Node agent / Data Mover reads snapshot data
  |
  v
Kopia uploads data to object storage repository
  |
  v
BackupRepository tracks repository for namespace
  |
  v
Snapshot may be cleaned up after successful movement
```

### 13.2 Restore flow with Data Mover

```text
Restore CR
  |
  v
Velero identifies backed-up volume data
  |
  v
DataDownload CR created
  |
  v
Node agent downloads data from Kopia repository
  |
  v
PVC is populated/restored
  |
  v
Application workload starts with restored data
```

### 13.3 Data Mover CRDs

| CRD | Purpose |
|---|---|
| `DataUpload` | Tracks upload of snapshot data to backup repository |
| `DataDownload` | Tracks restore/download of data from backup repository |
| `BackupRepository` | Manages per-namespace backup repository lifecycle |

### 13.4 Why Data Mover is important

Without Data Mover:

```text
Backup metadata is in object storage
PV snapshot is in storage backend
```

With Data Mover:

```text
Backup metadata is in object storage
PV data is also copied to object storage repository
```

This improves restore options when the original storage snapshot backend is not available.

## 14. BackupStorageLocation and VolumeSnapshotLocation

### 14.1 BackupStorageLocation

`BackupStorageLocation` points Velero to object storage.

It stores:

- Backup metadata
- Kubernetes/OpenShift object archive
- Logs
- File System Backup data
- Data Mover backup repository data

Example backends:

```text
AWS S3
Azure Blob
Google Cloud Storage
IBM COS S3
ODF Multicloud Object Gateway
MinIO
Other S3-compatible object storage
```

### 14.2 VolumeSnapshotLocation

`VolumeSnapshotLocation` points Velero to a snapshot backend for native provider snapshots.

For CSI snapshots, the architecture also depends on the Kubernetes `VolumeSnapshotClass` and CSI driver.

### 14.3 Important senior-level detail

In Velero architecture, a backup has:

- One `BackupStorageLocation`
- One `VolumeSnapshotLocation` per volume provider

If you want redundant backups to multiple object storage locations, create multiple schedules or backups targeting different BSLs. Do not assume one backup automatically writes to multiple object stores.

### 14.4 BSL status

Check BSL health:

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation <name> -n openshift-adp
```

Common BSL phases:

```text
Available
Unavailable
Unknown
```

If BSL is unavailable, backups will usually fail early.

## 15. OADP plugins architecture

### 15.1 Plugin categories

OADP plugins can be grouped as:

```text
Cloud object store plugins       -> aws, azure, gcp
Cloud snapshot plugins           -> aws, azure, gcp
OpenShift resource plugin        -> openshift
CSI snapshot plugin              -> csi
Virtualization plugin            -> kubevirt
Custom plugins                   -> partner/provider-specific behavior
```

### 15.2 How plugins are loaded

Plugins run as part of Velero plugin architecture. They extend Velero behavior for:

- Backup item actions
- Restore item actions
- Volume snapshotter integration
- Object store integration
- OpenShift-specific transformation
- KubeVirt/VM handling

### 15.3 Plugin selection examples

| Environment | Common plugins |
|---|---|
| AWS with EBS | `openshift`, `aws` |
| AWS with CSI snapshots | `openshift`, `aws`, `csi` |
| ODF/Ceph with S3/MCG | `openshift`, `aws`, `csi` |
| Azure | `openshift`, `azure`, `csi` if needed |
| GCP | `openshift`, `gcp`, `csi` if needed |
| OpenShift Virtualization | `openshift`, `kubevirt`, `csi` |

For S3-compatible storage such as MCG or MinIO, the `aws` plugin is commonly used because the object API is S3-compatible.

## 16. OpenShift-specific architecture considerations

### 16.1 Projects and namespaces

OpenShift projects are Kubernetes namespaces with additional OpenShift project metadata.

OADP can back up namespace-scoped application resources, but you should carefully filter what is included.

### 16.2 Operators and CRDs

Do not blindly back up and restore Operators.

A good strategy is:

1. Install required Operators on the target cluster first.
2. Verify CRDs exist and versions are compatible.
3. Restore application custom resources after the operator is ready.

Bad strategy:

```text
Backup everything including Operator namespaces, CRDs, ClusterServiceVersions, install plans, and operator-managed state.
```

This can cause restore failure, webhook conflicts, and broken operator reconciliation.

### 16.3 Internal images

OADP can back up internal images, but architecture depends on registry configuration and OADP support for internal image backup.

For critical platforms, also protect:

- Image registry storage backend
- Git repositories
- External image repositories
- Image pull secrets
- BuildConfig and ImageStream metadata

### 16.4 Routes and DNS

Restored Routes might not work immediately if:

- Target cluster has a different apps domain
- Certificates differ
- External DNS is not updated
- Load balancer is different

For cross-cluster DR, include route/DNS cutover in the DR runbook.

### 16.5 SCC and security context

SecurityContextConstraints are cluster-scoped and sensitive.

In many cases, do not restore SCCs from backup unless you have a controlled reason. Instead, recreate security policy through GitOps or platform baseline automation.

## 17. OADP Self-Service architecture

OADP Self-Service allows namespace administrators to perform backup and restore for their authorized namespaces without full cluster-admin privileges, when the cluster administrator enables and configures it.

### 17.1 Why Self-Service exists

In large enterprises, cluster administrators should not manually perform every application backup request.

Self-Service provides controlled delegation:

```text
Cluster admin owns platform policy
Namespace admin owns application backup/restore inside allowed namespace
```

### 17.2 Self-Service flow

```text
Namespace admin creates NonAdminBackup
        |
        v
NonAdminController validates request
        |
        v
Controller creates underlying Velero Backup
        |
        v
Velero performs backup
        |
        v
Status is copied back to NonAdminBackup
```

### 17.3 Self-Service CRDs

| CRD | Purpose |
|---|---|
| `NonAdminController` | Orchestrates and controls Self-Service operations |
| `NonAdminBackup` | Namespace-scoped backup request |
| `NonAdminRestore` | Namespace-scoped restore request |
| `NonAdminBackupStorageLocation` | User/namespace backup storage location |
| `NonAdminDownloadRequest` | Controlled download/log request |

### 17.4 Self-Service limitations

Self-Service is not the same as cluster-admin OADP access.

A namespace admin normally cannot:

- Back up unauthorized namespaces
- Create cluster-wide snapshot locations
- Restore cluster-scoped sensitive resources
- Perform unrestricted cross-cluster migration
- Modify global DPA policy

This is correct and desirable from a security architecture perspective.

## 18. Security architecture

### 18.1 Credentials

OADP needs credentials to access object storage and sometimes cloud snapshot APIs.

Credentials are commonly stored in a Kubernetes Secret in `openshift-adp`.

Example:

```bash
oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file=cloud=./credentials-velero
```

Security practices:

- Use least privilege IAM permissions.
- Use dedicated bucket per environment or tenant.
- Use encryption at rest on bucket and snapshots.
- Use TLS for S3 endpoints.
- Rotate credentials.
- Do not share one cloud credential across all clusters unless required.
- Prefer short-lived/STS credentials where supported.

### 18.2 Object storage hardening

Recommended controls:

- Bucket versioning
- Object lock or immutability for ransomware protection
- Server-side encryption
- Bucket lifecycle policy
- Access logging
- Deny public access
- Separate backup account/project/subscription
- Network restrictions or private endpoints

### 18.3 RBAC

Cluster-admin is usually required for installation and global operations.

For delegated operations, use Self-Service where available.

Do not give application teams direct permissions to global Velero resources unless the risk is understood.

### 18.4 Secrets in backups

Kubernetes Secrets are backed up as API objects unless excluded.

That means your backup storage becomes a sensitive security boundary.

Protect backup storage like production secrets storage.

### 18.5 Network architecture

Velero and node-agent pods must reach:

- Kubernetes API server
- Object storage endpoint
- Cloud APIs if using cloud snapshots
- CSI snapshot components if using CSI
- Internal registry if backing up internal images

In restricted/disconnected environments, verify:

- Proxy configuration
- Custom CA trust
- S3 endpoint route
- Firewall rules
- DNS resolution
- Mirrored operator catalogs
- Mirrored container images

## 19. Production design patterns

### 19.1 Namespace-level application backup

Best for:

- Individual application recovery
- Human error recovery
- Namespace migration
- Dev/test restore

Example:

```text
Backup namespace app-prod daily
Retain 30 days
Restore to app-restore-test monthly for validation
```

### 19.2 Gold/Silver/Bronze backup tiers

| Tier | RPO | Method | Retention | Restore testing |
|---|---|---|---|---|
| Gold | 1-4 hours | CSI/Data Mover + DB-native backup | 30-90 days | Monthly |
| Silver | Daily | CSI snapshot or FSB | 14-30 days | Quarterly |
| Bronze | Weekly | API objects only or FSB | 7-14 days | On demand |

### 19.3 Cross-cluster restore

Use when:

- Migrating workloads
- DR cluster testing
- Region failure planning
- Platform replacement

Checklist:

- Same or compatible OCP/OADP version
- Required Operators installed on target
- CRDs present
- Storage classes mapped
- Pull secrets available
- Image registry reachable
- Routes/DNS adjusted
- NetworkPolicies validated
- SCC/security policy ready

### 19.4 GitOps plus OADP

A mature architecture uses both:

```text
GitOps restores desired manifests
OADP restores runtime state and PV data
Database-native backup restores transactional data
```

Do not treat OADP as a replacement for GitOps.

### 19.5 Database workloads

For PostgreSQL, MySQL, MongoDB, Elasticsearch, etc.:

- Use database-native backup where possible.
- Use OADP for Kubernetes object recovery and PVC recovery.
- Use hooks only if they are tested.
- Validate restored database with application-level checks.

## 23. Common failure scenarios

### 23.1 BSL unavailable

Symptoms:

```text
BackupStorageLocation is Unavailable
Backup fails early
Velero logs show S3 access, DNS, TLS, or credential error
```

Checks:

```bash
oc describe bsl <name> -n openshift-adp
oc logs deploy/velero -n openshift-adp
oc get secret -n openshift-adp
```

Common causes:

- Wrong bucket name
- Wrong endpoint URL
- Wrong region
- Wrong access key/secret key
- Missing CA trust
- Firewall/proxy issue
- Bucket policy denies access
- S3 path-style setting mismatch

### 23.2 Backup succeeds but PV data missing

Common causes:

- PV backup method not enabled
- Node agent disabled
- PVC not selected for backup
- SnapshotClass missing
- Storage backend does not support snapshots
- `defaultVolumesToFSBackup` not set as expected
- Workload uses unsupported volume type

Checks:

```bash
oc describe backup <backup-name> -n openshift-adp
oc get podvolumebackups -A
oc get volumesnapshot -A
oc get dataupload -A
```

### 23.3 CSI snapshot stuck

Common causes:

- CSI driver snapshot controller not healthy
- Missing `VolumeSnapshotClass`
- Wrong driver name in `VolumeSnapshotClass`
- Backend storage snapshot failure
- Volume mode unsupported

Checks:

```bash
oc get volumesnapshotclass
oc get volumesnapshot -A
oc describe volumesnapshot <name> -n <namespace>
oc get volumesnapshotcontent
```

### 23.4 Restore PVC stuck Pending

Common causes:

- StorageClass missing on target cluster
- StorageClass has different name
- Snapshot restore not supported
- Insufficient storage quota
- PVC requested size mismatch or unavailable backend
- Access mode unsupported

Checks:

```bash
oc get pvc -n <namespace>
oc describe pvc <pvc-name> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### 23.5 Restore blocked by admission webhook

Common causes:

- Operator webhook exists but target operator is not ready
- CRD version mismatch
- ValidatingWebhookConfiguration blocks restored object
- Mutating webhook has unavailable service

Checks:

```bash
oc get validatingwebhookconfiguration
oc get mutatingwebhookconfiguration
oc get events -A --sort-by=.lastTimestamp
oc describe restore <restore-name> -n openshift-adp
```

### 23.6 Restored app does not work

Common causes:

- Secret restored but external dependency changed
- Route hostname changed
- Database data inconsistent
- Image pull secret missing
- NetworkPolicy blocks traffic
- SCC/security context differs
- ConfigMap contains cluster-specific endpoint

Checks:

```bash
oc get pods -n <namespace>
oc describe pod <pod> -n <namespace>
oc logs <pod> -n <namespace>
oc get route -n <namespace>
oc get networkpolicy -n <namespace>
```

## 24. Senior-admin best practices

### 24.1 Design best practices

- Do not use OADP as your only DR solution.
- Always maintain etcd backup separately.
- Use GitOps for cluster and application desired state.
- Use database-native backups for transactional applications.
- Use CSI Data Mover for durable PV backup when storage snapshots alone are not enough.
- Use object lock/immutability for ransomware protection.
- Separate backup storage from the primary cluster account/project.
- Test restore regularly.
- Document RPO and RTO per application.
- Use namespace/application labels to define backup scope.

### 24.2 Backup scope best practices

Avoid broad full-cluster style backups.

Prefer:

```text
One backup policy per application or namespace group
One schedule per criticality tier
Explicit includedNamespaces
Explicit excludedResources
Documented restore runbook
```

### 24.3 Restore test best practices

A backup is not valid until restore is tested.

Minimum restore validation:

```text
1. Restore namespace to test namespace
2. Confirm PVCs bind
3. Confirm pods start
4. Confirm route/service reachable
5. Confirm application login/API works
6. Confirm database/application consistency
7. Record restore time
8. Update runbook
```

### 24.4 Upgrade best practices

Before OADP upgrade:

- Check OADP/OCP compatibility matrix.
- Check Velero version mapping.
- Review release notes for breaking changes.
- Test backup and restore in non-production.
- Confirm existing backups are restorable with target version.
- Validate Data Mover compatibility.

### 24.5 Multi-cluster best practices

For cross-cluster restore:

- Keep OADP versions compatible.
- Keep storage classes mapped.
- Keep required Operators installed.
- Keep image registry access consistent.
- Use unique bucket prefixes per cluster.
- Avoid multiple clusters writing conflicting backups to the same prefix.

## 25. Interview-style explanation

### Question: Explain OADP architecture.

**Answer:**

OADP is the OpenShift API for Data Protection. Architecturally, it is an operator-managed Velero deployment customized for OpenShift. The OADP Operator runs in the `openshift-adp` namespace and watches the `DataProtectionApplication` custom resource. Based on that DPA, it deploys Velero, configures provider plugins, creates backup and snapshot locations, and optionally deploys a node agent for Restic/Kopia filesystem backup and CSI Data Mover.

The backup workflow starts when an administrator creates a `Backup` CR or a `Schedule` CR. Velero watches the CR, collects selected Kubernetes and OpenShift API objects, stores them in an object storage bucket through `BackupStorageLocation`, and handles persistent volume data through one of three paths: native/cloud snapshots, CSI snapshots, or filesystem backup using Restic/Kopia. In newer designs, CSI Data Mover can take CSI snapshot data and move it into object storage using Kopia, making the backup more durable and portable.

Restore happens through a `Restore` CR. Velero reads the backup metadata from object storage, recreates the selected objects, restores PVCs from snapshot or backup repository, applies namespace or storage-class mappings if configured, runs restore hooks if defined, and updates restore status.

A key point is that OADP is application-centric. It is not a replacement for etcd backup, OpenShift control-plane DR, or full cluster restore. In production, OADP should be combined with etcd backups, GitOps, storage replication, and database-native backups.

## 26. Quick revision notes

- OADP = OpenShift-integrated Velero via Operator.
- Main namespace = `openshift-adp`.
- Main config CR = `DataProtectionApplication`.
- Main operation CRs = `Backup`, `Restore`, `Schedule`.
- Object storage = `BackupStorageLocation`.
- Snapshot backend = `VolumeSnapshotLocation` or CSI snapshot APIs.
- PV backup methods = snapshot, CSI snapshot, FSB with Restic/Kopia, CSI Data Mover.
- Data Mover CRs = `DataUpload`, `DataDownload`, `BackupRepository`.
- Self-Service CRs = `NonAdminBackup`, `NonAdminRestore`, `NonAdminBackupStorageLocation`, `NonAdminDownloadRequest`.
- OADP protects apps, application resources, PVs, and internal images.
- OADP does not replace etcd backup or full-cluster DR.
- Always test restore.
- For databases, use app/database consistency controls.
- For ransomware resistance, use immutable object storage.
