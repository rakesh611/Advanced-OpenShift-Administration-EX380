# Restore Application to a Different Namespace in OpenShift APIs for Data Protection (OADP)

**Audience:** Advanced OpenShift Administration / DO380-level engineers with production experience  
**Focus:** Restoring an application backup from one namespace to another namespace using OADP and Velero  
**Example source namespace:** `prod-app`  
**Example target namespace:** `prod-app-restore`  
**OADP namespace:** `openshift-adp`

---

## 1. What “restore application to different namespace” means

In OADP, restoring an application to a different namespace means you take a backup that was created from one namespace and restore the Kubernetes objects and, optionally, persistent volume data into another namespace.

Example:

```text
Backup source namespace:  prod-app
Restore target namespace: prod-app-restore
```

You do **not** modify the original backup. Instead, you create a Velero `Restore` custom resource and define a namespace remapping:

```yaml
namespaceMapping:
  prod-app: prod-app-restore
```

This tells Velero/OADP:

```text
Any namespaced object that originally belonged to prod-app should be restored into prod-app-restore.
```

This is commonly used for:

- disaster recovery testing without overwriting production
- cloning production workloads into a test namespace
- validating backup quality
- restoring deleted application resources into a temporary namespace
- blue/green recovery testing
- forensic investigation after application corruption
- migration preparation
- application rollback testing

Important: namespace remapping changes the Kubernetes namespace metadata for restored objects. It does **not** automatically rewrite every application-level value that might contain the old namespace name inside environment variables, ConfigMaps, Secrets, scripts, URLs, database records, route hostnames, OAuth redirect URIs, or external system configuration.

---

## 2. OADP and Velero relationship

OADP is the OpenShift Operator-based data protection solution that installs and manages Velero plus OpenShift-specific plugins. Velero provides the backup and restore APIs such as:

- `Backup`
- `Restore`
- `Schedule`
- `BackupStorageLocation`
- `VolumeSnapshotLocation`

In OpenShift, these CRs usually live in:

```text
openshift-adp
```

OADP protects application resources at namespace granularity. It can back up and restore:

- Kubernetes/OpenShift resource YAML
- internal images, where applicable
- persistent volume data through snapshots or file-system backup mechanisms such as Kopia or Restic, depending on the OADP version and configuration

Do not confuse OADP application backup with OpenShift control plane backup. OADP is not a replacement for etcd backup. OADP is for customer workloads and application-level recovery, not full cluster resurrection.

## 3. High-level restore flow

A different-namespace restore follows this flow:

```text
1. Application exists in source namespace
        |
        v
2. OADP/Velero Backup CR captures namespace resources and PV data
        |
        v
3. Backup metadata and resource archive are stored in BackupStorageLocation
        |
        v
4. Restore CR is created in openshift-adp
        |
        v
5. Restore CR references backupName and namespaceMapping
        |
        v
6. Velero restore controller reads backup contents
        |
        v
7. Velero changes target namespace from source to mapped namespace
        |
        v
8. Velero recreates resources in target namespace
        |
        v
9. PV/PVC restore runs if restorePVs is true and volume backup exists
        |
        v
10. Application controllers reconcile workloads in new namespace
        |
        v
11. Admin validates pods, PVCs, services, routes, logs, app health, and data
```

---

## 4. Core concept: `namespaceMapping`

The key field is:

```yaml
spec:
  namespaceMapping:
    <source-namespace>: <target-namespace>
```

Example:

```yaml
spec:
  namespaceMapping:
    prod-app: prod-app-restore
```

Meaning:

```text
Objects backed up from prod-app will be restored into prod-app-restore.
```

Multiple namespace mappings are also possible:

```yaml
spec:
  namespaceMapping:
    frontend-prod: frontend-dr
    backend-prod: backend-dr
    database-prod: database-dr
```

Use this carefully. Multi-namespace applications often have cross-namespace references, RBAC bindings, network policies, service discovery assumptions, and route dependencies.

---

## 5. Important difference: source namespace vs target namespace

When writing restore filters, hooks, and resource modifiers, always understand whether the field expects the **original backup namespace** or the **new restore namespace**.

### 5.1 Source namespace

The source namespace is the namespace from which the backup was taken.

Example:

```text
prod-app
```

### 5.2 Target namespace

The target namespace is where you want to restore the application.

Example:

```text
prod-app-restore
```

### 5.3 Practical rule

For `namespaceMapping`, the left side is the backup/source namespace and the right side is the target namespace:

```yaml
namespaceMapping:
  prod-app: prod-app-restore
```

For restore resource modifiers, namespace conditions generally match the **original namespace in the backup**, not the new mapped namespace. Always validate this with your installed Velero/OADP version.

## 6. Why senior admins restore to a different namespace

### 6.1 DR validation without production impact

You can verify that a production backup is usable by restoring it into a temporary namespace:

```text
prod-app        -> prod-app-dr-test
```

This avoids overwriting production objects.

### 6.2 Application clone for debugging

If production has a data issue, you can restore a copy of the application into another namespace for debugging:

```text
payment-prod    -> payment-forensics
```

### 6.3 Pre-migration testing

Before moving workloads to another cluster or storage backend, restore into a separate namespace and test:

```text
legacy-app      -> legacy-app-migration-test
```

### 6.4 Ransomware/corruption recovery test

You can prove whether backups contain clean data before performing a production restore.

### 6.5 Developer test environment

A production-like environment can be created from a backup, but you must sanitize Secrets, external integrations, routes, and database endpoints.

## 7. What namespace remapping changes and does not change

### 7.1 Usually changed by Velero/OADP

When namespace mapping is configured, Velero updates the namespace for namespaced resources during restore. It also remaps namespace references that Velero understands, such as the namespace reference in PV claim references.

Examples of restored resources:

- `Deployment`
- `DeploymentConfig`
- `StatefulSet`
- `DaemonSet`
- `ReplicaSet`
- `Pod`
- `Service`
- `Route`
- `ConfigMap`
- `Secret`
- `ServiceAccount`
- `Role`
- `RoleBinding`
- `PVC`
- `NetworkPolicy`
- `ImageStream`
- application CRs, if the CRDs exist on the target cluster

### 7.2 Not automatically fixed in every case

You must manually review or patch:

- hardcoded namespace values in ConfigMaps
- hardcoded namespace values in Secrets
- application environment variables
- command-line arguments in Deployments
- route hostnames
- external DNS records
- OAuth redirect URLs
- service mesh policies
- Argo CD application labels and tracking annotations
- Helm release metadata
- image trigger annotations
- NetworkPolicy namespace selectors
- RoleBinding subjects that reference service accounts from old namespaces
- ExternalSecret or Vault path references
- database connection strings
- object storage bucket prefixes
- monitoring dashboard selectors
- alert routing labels

### 7.3 Example of a hidden old namespace reference

```yaml
env:
- name: REDIS_SERVICE
  value: redis.prod-app.svc.cluster.local
```

After restore to `prod-app-restore`, this still points to the old namespace unless patched:

```yaml
env:
- name: REDIS_SERVICE
  value: redis.prod-app-restore.svc.cluster.local
```

## 8. Prerequisites

Before restoring an application to a different namespace, verify the following.

### 8.1 Cluster access

You should have cluster-admin permissions for platform-level restore operations:

```bash
oc whoami
oc auth can-i '*' '*' --all-namespaces
```

### 8.2 OADP Operator installed

```bash
oc get csv -n openshift-adp
oc get deploy -n openshift-adp
```

Expected components might include:

```text
oadp-operator
velero
node-agent     # if file-system backup is enabled
```

### 8.3 DataProtectionApplication is ready

```bash
oc get dpa -n openshift-adp
oc describe dpa -n openshift-adp
```

Expected condition:

```text
Ready=True
```

### 8.4 BackupStorageLocation is available

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation -n openshift-adp
```

Expected:

```text
Phase: Available
```

### 8.5 Backup exists and is usable

```bash
oc get backups.velero.io -n openshift-adp
oc describe backup <backup-name> -n openshift-adp
```

Recommended Velero CLI check:

```bash
velero backup get -n openshift-adp
velero backup describe <backup-name> --details -n openshift-adp
velero backup logs <backup-name> -n openshift-adp
```

The backup should be in one of these phases:

```text
Completed
PartiallyFailed    # usable, but investigate warnings/errors carefully
```

### 8.6 Target namespace planning

Decide whether OADP should create the target namespace or whether you will create it first.

For clean DR testing, it is usually better to let OADP/Velero create the target namespace. If you pre-create the namespace, make sure required labels, annotations, quotas, limit ranges, SCC-related requirements, network labels, and pod security labels are correct.

### 8.7 Storage readiness

For stateful applications, verify:

```bash
oc get storageclass
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get pvc -n prod-app
```

Check whether the backup used:

- CSI snapshots
- cloud provider native snapshots
- Kopia file-system backup
- Restic file-system backup
- Data Mover

The restore behavior differs depending on the volume backup method.

## 10. Create a backup of the source namespace

Example Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: prod-app-backup-20260703
  namespace: openshift-adp
spec:
  includedNamespaces:
  - prod-app
  storageLocation: default
  ttl: 720h0m0s
  snapshotVolumes: true
```

Apply:

```bash
oc apply -f prod-app-backup.yaml
```

Verify:

```bash
oc get backup -n openshift-adp prod-app-backup-20260703
oc describe backup -n openshift-adp prod-app-backup-20260703
velero backup describe prod-app-backup-20260703 --details -n openshift-adp
velero backup logs prod-app-backup-20260703 -n openshift-adp
```

For file-system backup with Kopia/Restic, your actual Backup CR might include annotations on pods or default volume backup configuration in the DPA/Backup settings. Validate how your cluster is configured before assuming PV data was captured.

## 11. Basic restore to a different namespace

### 11.1 Restore CR

Create `restore-prod-app-to-new-namespace.yaml`:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-prod-app-to-prod-app-restore
  namespace: openshift-adp
spec:
  backupName: prod-app-backup-20260703
  restorePVs: true
  namespaceMapping:
    prod-app: prod-app-restore
```

Apply:

```bash
oc apply -f restore-prod-app-to-new-namespace.yaml
```

### 11.2 Verify restore object

```bash
oc get restore -n openshift-adp
oc describe restore restore-prod-app-to-prod-app-restore -n openshift-adp
```

Check phase:

```bash
oc get restore restore-prod-app-to-prod-app-restore \
  -n openshift-adp \
  -o jsonpath='{.status.phase}{"\n"}'
```

Expected:

```text
Completed
```

or possibly:

```text
PartiallyFailed
```

If `PartiallyFailed`, inspect logs and warnings.

### 11.3 Verify target namespace

```bash
oc get ns prod-app-restore
oc project prod-app-restore
oc get all
oc get pvc
oc get secret,configmap
oc get route
```

### 11.4 Velero CLI equivalent

```bash
velero restore create restore-prod-app-to-prod-app-restore \
  --from-backup prod-app-backup-20260703 \
  --namespace-mappings prod-app:prod-app-restore \
  --restore-volumes=true \
  -n openshift-adp
```

Depending on Velero version, the volume flag may appear differently. Always confirm:

```bash
velero restore create --help
```

## 12. Restore with included namespace filter

You can explicitly include the source namespace in the restore:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-prod-app-filtered
  namespace: openshift-adp
spec:
  backupName: prod-app-backup-20260703
  includedNamespaces:
  - prod-app
  restorePVs: true
  namespaceMapping:
    prod-app: prod-app-restore
```

Important: `includedNamespaces` refers to the namespace in the backup, not the final target namespace.

## 13. Restore only selected resources

Example: restore only application config objects and workloads, not events or backup metadata.

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-prod-app-selected-resources
  namespace: openshift-adp
spec:
  backupName: prod-app-backup-20260703
  includedNamespaces:
  - prod-app
  includedResources:
  - deployments
  - statefulsets
  - services
  - routes
  - persistentvolumeclaims
  - secrets
  - configmaps
  - serviceaccounts
  - roles
  - rolebindings
  excludedResources:
  - events
  - events.events.k8s.io
  - backups.velero.io
  - restores.velero.io
  restorePVs: true
  namespaceMapping:
    prod-app: prod-app-restore
```

Use this when you want tighter control over what comes back.

## 14. Restore with label selector

If backup contains many applications in a namespace and your app has labels, restore only objects matching the label.

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-payment-app-only
  namespace: openshift-adp
spec:
  backupName: prod-shared-namespace-backup
  includedNamespaces:
  - prod-app
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payment
  restorePVs: true
  namespaceMapping:
    prod-app: payment-restore
```

Be careful: label selectors can exclude dependencies such as Secrets, ServiceAccounts, PVCs, Routes, or ConfigMaps if those objects are not labeled consistently.

## 16. Persistent volume behavior during namespace remap

Stateful application restore is the most important part of this topic.

### 16.1 What `restorePVs: true` means

```yaml
restorePVs: true
```

This tells Velero/OADP to restore persistent volumes if the backup contains volume backup/snapshot information and if the provider/plugin supports the operation.

If you set:

```yaml
restorePVs: false
```

then Kubernetes resource YAML can be restored, but PV data restore from snapshots/native volume backup is disabled.

### 16.2 PVC restore flow

For a stateful workload:

```text
PVC in prod-app
     |
     v
Backup captures PVC object and volume data/snapshot
     |
     v
Restore maps namespace prod-app -> prod-app-restore
     |
     v
PVC is created in prod-app-restore
     |
     v
PV/snapshot/data restore creates or binds volume
     |
     v
StatefulSet/Deployment mounts restored PVC
```

### 16.3 PV claimRef namespace remapping

A PV can contain a claim reference like:

```yaml
spec:
  claimRef:
    namespace: prod-app
    name: mysql-data
```

During namespace remapping, Velero can change the claim reference namespace to:

```yaml
spec:
  claimRef:
    namespace: prod-app-restore
    name: mysql-data
```

This prevents the restored PV from pointing to the original PVC namespace.

### 16.4 StorageClass issues

If the target cluster or target namespace should use a different `StorageClass`, namespace mapping alone is not enough.

Example source PVC:

```yaml
spec:
  storageClassName: ocs-storagecluster-ceph-rbd
```

Target requirement:

```yaml
spec:
  storageClassName: thin-csi
```

You need a restore resource modifier or a storage-class mapping approach supported by your Velero/OADP/plugin version.

### 16.5 WaitForFirstConsumer considerations

If the StorageClass uses:

```yaml
volumeBindingMode: WaitForFirstConsumer
```

PVC binding might wait until a pod is scheduled. This is normal, but in restore scenarios it can also expose node affinity, topology, zone, or selected-node problems.

Check:

```bash
oc get sc -o custom-columns=NAME:.metadata.name,MODE:.volumeBindingMode
oc describe pvc -n prod-app-restore
oc get events -n prod-app-restore --sort-by=.lastTimestamp
```

### 16.6 Existing PVCs in target namespace

If a PVC with the same name already exists in the target namespace, Velero’s default behavior is non-destructive for existing resources. It usually skips existing resources rather than overwriting them.

For production-grade restores, avoid restoring into a dirty target namespace. Use a new namespace or delete conflicting resources only after proper approval.

## 17. Resource modifiers for target-environment changes

Namespace mapping solves namespace placement. Resource modifiers solve resource transformation during restore.

Use resource modifiers when you need to change:

- StorageClass
- route hosts
- replica counts
- image registry
- labels/annotations
- environment-specific ConfigMap values, if safe
- resource requests/limits for test restores
- Argo CD tracking labels

### 17.1 Example: change StorageClass during restore

Create `change-storageclass.yaml`:

```yaml
version: v1
resourceModifierRules:
- conditions:
    groupResource: persistentvolumeclaims
    resourceNameRegex: ".*"
    namespaces:
    - prod-app
  patches:
  - operation: replace
    path: "/spec/storageClassName"
    value: "thin-csi"
```

Create ConfigMap in OADP namespace:

```bash
oc create configmap change-storageclass \
  --from-file=change-storageclass.yaml \
  -n openshift-adp
```

Run restore with Velero CLI:

```bash
velero restore create restore-prod-app-storageclass-change \
  --from-backup prod-app-backup-20260703 \
  --namespace-mappings prod-app:prod-app-restore \
  --resource-modifier-configmap change-storageclass \
  -n openshift-adp
```

Restore CR form can be version-dependent. Validate with:

```bash
oc explain restore.spec.resourceModifier
```

Typical shape in newer Velero versions:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-prod-app-storageclass-change
  namespace: openshift-adp
spec:
  backupName: prod-app-backup-20260703
  namespaceMapping:
    prod-app: prod-app-restore
  restorePVs: true
  resourceModifier:
    kind: ConfigMap
    name: change-storageclass
```

### 17.2 Important resource modifier rule

The namespace in resource modifier conditions usually refers to the **original namespace in the backup**, not the mapped target namespace.

So use:

```yaml
namespaces:
- prod-app
```

not:

```yaml
namespaces:
- prod-app-restore
```

## 18. Restore hooks

Restore hooks run commands during or after restore for selected pods.

Types:

- `init` restore hook: adds init container before application containers start
- `exec` restore hook: runs command inside a restored container after it starts

Use cases:

- database recovery command
- permissions repair
- cache cleanup
- application re-registration
- file ownership fix
- schema validation
- post-restore smoke script

### 18.1 Example restore hook

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-prod-app-with-hook
  namespace: openshift-adp
spec:
  backupName: prod-app-backup-20260703
  namespaceMapping:
    prod-app: prod-app-restore
  restorePVs: true
  hooks:
    resources:
    - name: mysql-post-restore-check
      includedNamespaces:
      - prod-app
      includedResources:
      - pods
      labelSelector:
        matchLabels:
          app: mysql
      postHooks:
      - exec:
          container: mysql
          command:
          - /bin/bash
          - -c
          - "mysqladmin ping -uroot -p$MYSQL_ROOT_PASSWORD"
          waitTimeout: 5m
          execTimeout: 1m
          onError: Continue
```

Again, `includedNamespaces` in the hook normally refers to the namespace in the backup/source selection context. Test this in your environment.

## 19. Routes and DNS after restore

OpenShift Routes are namespaced resources. They can be restored into the new namespace, but hostnames can conflict.

Example original route:

```yaml
spec:
  host: frontend-prod.apps.example.com
```

If restored as-is into `prod-app-restore`, the same host might already be claimed by production. The router admission can reject or mark the route as not admitted.

Check:

```bash
oc get route -n prod-app-restore
oc describe route frontend -n prod-app-restore
```

Look for:

```text
Admitted: False
reason: HostAlreadyClaimed
```

### 19.1 Options

Option 1: Exclude routes from restore and create new test routes manually.

```yaml
excludedResources:
- routes.route.openshift.io
```

Option 2: Patch route hostnames after restore.

```bash
oc patch route frontend -n prod-app-restore --type=merge -p \
  '{"spec":{"host":"frontend-restore.apps.example.com"}}'
```

Option 3: Use resource modifiers to change route hostnames during restore, but be careful with JSON patch paths and route variations.

## 20. ServiceAccounts, tokens, and image pull secrets

ServiceAccounts are restored into the target namespace. However, token behavior changed across Kubernetes/OpenShift versions because modern service account tokens are projected and short-lived rather than permanently stored token secrets.

After restore, check:

```bash
oc get sa -n prod-app-restore
oc describe sa default -n prod-app-restore
oc describe sa <app-sa> -n prod-app-restore
oc get secret -n prod-app-restore
```

Validate image pull:

```bash
oc get pods -n prod-app-restore
oc describe pod <pod-name> -n prod-app-restore
```

Look for:

```text
ImagePullBackOff
ErrImagePull
unauthorized
forbidden
```

If workloads pull from private registries, ensure pull secrets exist and are linked to the right service account:

```bash
oc secrets link <serviceaccount> <pull-secret> --for=pull -n prod-app-restore
```

## 21. RBAC after namespace remap

Namespaced RBAC usually restores well if `Role` and `RoleBinding` are included.

Check:

```bash
oc get role,rolebinding -n prod-app-restore
oc describe rolebinding -n prod-app-restore
```

Pay special attention to RoleBinding subjects:

```yaml
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: prod-app
```

If the subject namespace still points to the old namespace, patch it:

```bash
oc patch rolebinding <rb-name> -n prod-app-restore --type=json -p='[
  {"op":"replace","path":"/subjects/0/namespace","value":"prod-app-restore"}
]'
```

Check access:

```bash
oc auth can-i get pods \
  --as=system:serviceaccount:prod-app-restore:app-sa \
  -n prod-app-restore
```

## 22. NetworkPolicy after namespace remap

NetworkPolicies might contain namespace selectors that still match production labels.

Example:

```yaml
namespaceSelector:
  matchLabels:
    kubernetes.io/metadata.name: prod-app
```

After restore, this might still allow traffic from or to the old namespace.

Check:

```bash
oc get networkpolicy -n prod-app-restore -o yaml
```

Search old namespace references:

```bash
oc get networkpolicy -n prod-app-restore -o yaml | grep prod-app
```

Patch as required:

```bash
oc patch networkpolicy <policy-name> -n prod-app-restore --type=json -p='[
  {"op":"replace","path":"/spec/ingress/0/from/0/namespaceSelector/matchLabels/kubernetes.io~1metadata.name","value":"prod-app-restore"}
]'
```

JSON patch paths require escaping `/` as `~1`.

## 23. ConfigMaps, Secrets, and hardcoded namespaces

Search restored resources for the original namespace:

```bash
oc get cm -n prod-app-restore -o yaml | grep prod-app
oc get secret -n prod-app-restore -o yaml | grep prod-app
oc get deploy,sts,dc -n prod-app-restore -o yaml | grep prod-app
```

Secrets are base64 encoded. Decode carefully:

```bash
oc get secret <secret-name> -n prod-app-restore -o jsonpath='{.data}'
```

For a specific key:

```bash
oc get secret <secret-name> -n prod-app-restore \
  -o jsonpath='{.data.DATABASE_URL}' | base64 -d
```

If the restored test environment must not access production systems, rotate or replace Secrets immediately.

## 24. ImageStreams and DeploymentConfig special care

OpenShift-specific objects such as `ImageStream`, `DeploymentConfig`, `BuildConfig`, and image triggers need extra validation.

Check:

```bash
oc get is,dc,bc -n prod-app-restore
oc describe dc <dc-name> -n prod-app-restore
```

Potential issues:

- image trigger points to old ImageStreamTag
- DeploymentConfig scaled down during restore flow
- disconnected restored pods remain temporarily
- post-restore hooks terminate early due to rollout triggers
- restored ImageStream uses old registry/internal reference

If using DeploymentConfig with volumes or post-restore hooks, validate whether the OADP cleanup script or manual cleanup is required for your OADP version and application pattern.

## 25. Operators and custom resources

If the application is managed by an Operator, restoring only the namespace might not be enough.

Examples:

- Crunchy PostgreSQL Operator
- AMQ Broker Operator
- OpenShift GitOps/Argo CD
- Service Mesh
- External Secrets Operator
- Cert-manager
- MongoDB/Redis operators

Before restore, verify that CRDs exist:

```bash
oc api-resources | grep -i <kind>
oc get crd | grep -i <operator-or-resource>
```

If a CRD is missing, Velero cannot restore that custom resource because the API server does not recognize it.

Check restore logs for messages like:

```text
resource not found
no matches for kind
unable to recognize
```

Do not use OADP to restore cluster operators as a substitute for proper operator lifecycle management. Install the required operator first, then restore application CRs.

## 26. Existing resource policy

Velero is non-destructive by default. If a resource already exists in the target cluster, it usually skips that resource rather than overwriting it.

This protects production, but it can surprise admins during test restores into a namespace that already contains resources.

Example default behavior:

```text
Existing target object found -> skip restore for that object
```

Newer Velero versions support an existing resource policy:

```yaml
spec:
  existingResourcePolicy: update
```

or CLI:

```bash
velero restore create restore-prod-app-update-existing \
  --from-backup prod-app-backup-20260703 \
  --namespace-mappings prod-app:prod-app-restore \
  --existing-resource-policy=update \
  -n openshift-adp
```

Use `update` carefully:

- It updates Kubernetes object specs on a best-effort basis.
- It does not mean PV data will be overwritten safely.
- It is not a replacement for a clean restore namespace.
- It can interact badly with controller-managed fields.

Senior admin recommendation: for DR tests, use a fresh namespace. Avoid update-based restores unless you have tested the behavior for each resource type.

## 27. Recommended production-grade restore procedure

### Step 1: Freeze change window

For real recovery, freeze application changes:

```text
Stop deployments, CI/CD syncs, GitOps reconciliation, user writes, and scheduled jobs if necessary.
```

For test restore, ensure test namespace cannot accidentally call production dependencies.

### Step 2: Inspect backup

```bash
velero backup describe prod-app-backup-20260703 --details -n openshift-adp
velero backup logs prod-app-backup-20260703 -n openshift-adp
```

Look for:

```text
Errors: 0
Warnings: acceptable and understood
Phase: Completed
```

### Step 3: Check source objects captured

```bash
velero backup describe prod-app-backup-20260703 --details -n openshift-adp | less
```

Validate resource counts:

- deployments
- statefulsets
- pods
- PVCs
- secrets
- configmaps
- routes
- services
- rolebindings

### Step 4: Prepare target name

Use a unique restore namespace:

```bash
export SRC_NS=prod-app
export DST_NS=prod-app-restore-20260703
export BACKUP=prod-app-backup-20260703
export RESTORE=restore-prod-app-20260703
```

### Step 5: Create Restore CR

```bash
cat <<EOF > restore.yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: ${RESTORE}
  namespace: openshift-adp
spec:
  backupName: ${BACKUP}
  includedNamespaces:
  - ${SRC_NS}
  restorePVs: true
  namespaceMapping:
    ${SRC_NS}: ${DST_NS}
EOF

oc apply -f restore.yaml
```

### Step 6: Watch restore

```bash
watch -n 5 "oc get restore ${RESTORE} -n openshift-adp -o wide"
```

### Step 7: Check logs

```bash
velero restore describe ${RESTORE} --details -n openshift-adp
velero restore logs ${RESTORE} -n openshift-adp
```

### Step 8: Validate target namespace


```bash
oc get pods -n ${DST_NS} -o wide

oc logs <pod> -n ${DST_NS} --all-containers=true
```

### Step 10: Validate application


## 29. Troubleshooting restore to a different namespace

### 29.1 Restore stuck in `InProgress`

Check:

```bash
oc describe restore <restore-name> -n openshift-adp
velero restore logs <restore-name> -n openshift-adp
oc logs deploy/velero -n openshift-adp
```

Possible causes:

- object storage access problem
- backup tarball read failure
- API server timeout
- missing CRDs
- PV restore operation waiting
- node-agent issue
- CSI snapshot restore delay

---

### 29.2 Restore is `PartiallyFailed`

Check:

```bash
velero restore describe <restore-name> --details -n openshift-adp
velero restore logs <restore-name> -n openshift-adp | egrep -i 'error|warn|fail|forbidden|denied|missing|unable'
```

Common causes:

- resource already exists
- route host already claimed
- CRD missing
- SCC/RBAC issue
- namespace quota blocks pod creation
- image pull secret missing
- PVC binding issue
- storage class missing
- webhook rejecting restored objects

---

### 29.3 Target namespace not created

Check restore logs:

```bash
velero restore logs <restore-name> -n openshift-adp | grep -i namespace
```

Check permissions:

```bash
oc auth can-i create namespaces --as=system:serviceaccount:openshift-adp:velero
```

If namespace creation is blocked by policy/admission, pre-create the namespace with required labels and retry carefully.

---

### 29.4 PVC stuck Pending

```bash
oc get pvc -n <target-ns>
oc describe pvc <pvc-name> -n <target-ns>
oc get events -n <target-ns> --sort-by=.lastTimestamp
```

Check:

```bash
oc get sc
oc get volumesnapshotclass
oc get pv | grep <target-ns>
```

Possible causes:

- StorageClass missing
- volume snapshot restore failed
- topology/zone mismatch
- WaitForFirstConsumer waiting for pod
- quota prevents PVC creation
- PV reclaim/claimRef conflict
- CSI driver unavailable

---

### 29.5 Pod stuck ContainerCreating

```bash
oc describe pod <pod> -n <target-ns>
```

Look for:

```text
MountVolume.SetUp failed
Unable to attach or mount volumes
permission denied
secret not found
configmap not found
```

Check PVC:

```bash
oc get pvc -n <target-ns>
```

---

### 29.6 Pod CrashLoopBackOff after restore

```bash
oc logs <pod> -n <target-ns> --previous
oc describe pod <pod> -n <target-ns>
```

Common causes:

- app config still points to old namespace
- DB restored but credentials mismatch
- service DNS points to production namespace
- route or external endpoint mismatch
- missing Secret key
- restored data inconsistent because app was not quiesced during backup

---

### 29.7 Route host conflict

```bash
oc describe route <route-name> -n <target-ns>
```

If host is already claimed:

```bash
oc patch route <route-name> -n <target-ns> --type=merge -p \
  '{"spec":{"host":"<new-hostname>"}}'
```

### 29.8 Missing CRD

Error example:

```text
no matches for kind "MyApp" in version "example.com/v1"
```

Fix:

```bash
oc get crd | grep -i myapp
```

Install the required Operator/CRD first, then rerun restore.

### 29.9 Old namespace references remain

Search everything:

```bash
oc api-resources --verbs=list --namespaced -o name | while read r; do
  oc get "$r" -n <target-ns> -o yaml 2>/dev/null | grep -H "prod-app" && echo "Found in $r"
done
```

For a smaller practical check:

```bash

```

Patch carefully based on object type.

## 30. Senior-admin best practices

### 30.1 Always test restores

A backup is not proven until it has been restored and validated.

Recommended schedule:

```text
Daily backup success check
Weekly namespace restore test
Monthly application functional restore test
Quarterly DR simulation
```

### 30.2 Use restore runbooks

Your runbook should include:

- backup name pattern
- source namespace
- target namespace naming convention
- restore CR template
- storage class mapping requirement
- route patch requirement
- secret sanitization steps
- app validation commands
- rollback/cleanup steps

### 30.3 Use unique target namespaces

Good:

```text
prod-app-restore-20260703
payment-drtest-20260703
```

Risky:

```text
test
restore
app-copy
```

### 30.4 Avoid restoring directly over production

Restore into a new namespace first. Validate data. Then plan controlled cutover.

### 30.5 Disable GitOps reconciliation temporarily

If Argo CD, OpenShift GitOps, Flux, or another controller manages the target namespace, it might delete or modify restored resources.

Check labels and annotations:

```bash
oc get all -n <target-ns> -o yaml | grep -i argocd
```

### 30.6 Exclude unnecessary noisy resources

Common exclusions:

```yaml
excludedResources:
- events
- events.events.k8s.io
- backups.velero.io
- restores.velero.io
- pods   # optional, if you prefer controllers to recreate pods
```

For many applications, restoring controllers such as Deployments/StatefulSets is cleaner than restoring old standalone Pods.

### 30.7 Sanitize restored secrets in non-prod

If restoring production into test:

- rotate DB passwords
- disable payment gateways
- disable mail/SMS sending
- replace external API tokens
- change S3 bucket prefixes
- block egress if required

### 30.8 Treat route exposure carefully

A restored app can become live if its route is admitted. Use temporary hostnames or exclude routes.

### 30.9 Validate data consistency

For databases, use application-aware backup hooks or database-native dump/replication strategies where needed. Crash-consistent volume snapshots are not always application-consistent.

### 30.10 Document exact OADP and Velero version

```bash
oc get csv -n openshift-adp
velero version -n openshift-adp
oc get deploy velero -n openshift-adp -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

Behavior changes across versions. Always check the version-specific documentation.

## 33. Interview-style explanation

### Question

How would you restore an OADP backup of an application from `prod-app` into `prod-app-restore`?

### Strong answer

I would first verify that OADP is healthy, the `DataProtectionApplication` is ready, the `BackupStorageLocation` is available, and the source backup is in `Completed` or acceptable `PartiallyFailed` state. Then I would create a Velero `Restore` CR in the `openshift-adp` namespace, referencing the backup name and using `spec.namespaceMapping` to map `prod-app` to `prod-app-restore`. If the application has persistent volumes, I would set `restorePVs: true` and confirm that the backup actually contains volume snapshot or file-system backup data.

After applying the restore, I would monitor the Restore CR phase, inspect Velero restore logs, and validate the target namespace resources: Deployments, StatefulSets, Services, Routes, Secrets, ConfigMaps, PVCs, and application logs. I would specifically check for old namespace references inside ConfigMaps, Secrets, RBAC subjects, NetworkPolicies, route hosts, and application environment variables, because namespace mapping does not automatically fix every app-level hardcoded value. For stateful workloads, I would verify PVC binding, StorageClass compatibility, volume data, and application consistency. I would avoid restoring over production until the restore is validated in a separate namespace.

## 34. Common mistakes

| Mistake | Result | Fix |
|---|---|---|
| Mapping target/source backward | Objects restore to unexpected namespace or fail | Use `source: target` syntax |
| Restoring into existing namespace | Resources skipped or conflict | Use a fresh namespace |
| Assuming Secrets are safe in test | Test app calls production systems | Sanitize/rotate secrets |
| Ignoring route host conflicts | Route not admitted | Patch host or exclude routes |
| Ignoring StorageClass difference | PVC Pending | Use resource modifier/storage mapping |
| Missing CRDs | Custom resources fail restore | Install operators/CRDs first |
| Not checking old namespace strings | App still talks to old services | Search and patch restored YAML |
| Assuming PV data was backed up | Empty/new PVC after restore | Validate volume backup method |
| Letting GitOps manage restored namespace | GitOps deletes restored objects | pause sync or isolate labels |
| No restore testing | Backup confidence is false | Schedule restore drills |

## 36. Final senior-level summary

Restoring an application to a different namespace in OADP is a controlled Velero restore operation using `spec.namespaceMapping`. The restore CR remains in `openshift-adp`, but the restored application objects are created in the mapped target namespace. This is one of the safest ways to test backup quality because it avoids overwriting production.

For a stateless app, the restore is usually straightforward: restore Kubernetes objects, validate pods, patch routes if needed, and test the service. For a stateful app, the real complexity is PV/PVC restore, StorageClass compatibility, volume snapshot or file-system backup behavior, application consistency, and data validation.

A 10-year-level admin should not treat namespace restore as only a YAML operation. The real work is pre-checking the backup, understanding the restore workflow, planning namespace mapping, controlling conflicts, validating storage, checking RBAC and NetworkPolicy, searching for old namespace references, sanitizing secrets, validating application health, and documenting the runbook so the restore can be repeated during an outage.
