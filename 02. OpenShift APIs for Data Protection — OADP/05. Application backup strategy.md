## 1. Executive Summary

An **application backup strategy** in OpenShift is not only about taking a Velero backup. A mature strategy answers the following questions:

- What exactly must be protected?
- What must not be protected?
- Which applications are business critical?
- What is the required RPO and RTO?
- Are persistent volumes backed up by CSI snapshot, cloud snapshot, Data Mover, or file-system backup?
- Are databases crash-consistent, file-system-consistent, or application-consistent?
- Can the backup be restored into a clean namespace, a clean cluster, or a disaster recovery cluster?
- Are backup objects encrypted, immutable, lifecycle-managed, and monitored?
- Has restore been tested recently?

OADP gives OpenShift administrators Kubernetes-native APIs for application backup and restore. It normally deploys Velero and OpenShift-specific plugins. In enterprise environments, OADP should be treated as an **application protection platform**, not a magic full-cluster recovery button.

A strong OADP backup strategy normally combines:

- **Object storage** for Kubernetes objects, OpenShift objects, internal images, metadata, and file-system backups.
- **CSI snapshots or cloud snapshots** for persistent volumes where snapshot support exists.
- **Data Mover** when snapshot data must be copied to object storage for portability or off-cluster protection.
- **File System Backup** with Kopia or Restic where snapshots are not available or not suitable.
- **Application-native backups** for databases and middleware where transaction consistency matters.
- **Backup hooks** for quiesce/unquiesce operations.
- **Schedule CRs** for repeatable backups.
- **Restore drills** for proof that the backup is useful.

The professional rule is simple:

> A backup that has never been restored is only an assumption.

## 2. What “Application Backup Strategy” Means in OpenShift

In traditional Linux administration, a backup might mean copying files from `/var/lib/app` to tape, NFS, or object storage. In OpenShift, an application is distributed across many Kubernetes and OpenShift resources:

- Namespace / Project
- Deployment, DeploymentConfig, StatefulSet, DaemonSet
- Pods and ReplicaSets generated by controllers
- Services and Routes
- ConfigMaps and Secrets
- ServiceAccounts
- Roles, RoleBindings, ClusterRoles, ClusterRoleBindings
- PersistentVolumeClaims and PersistentVolumes
- ImageStreams and internal registry images
- NetworkPolicies
- HorizontalPodAutoscalers
- PodDisruptionBudgets
- Custom resources created by Operators
- SecurityContextConstraints where custom SCCs are used
- External dependencies such as databases, DNS, identity providers, object stores, message brokers, and license servers

Therefore, an OpenShift application backup strategy has three layers:

### 2.1 Kubernetes/OpenShift Resource Layer

This protects YAML objects required to recreate the application definition:

- Deployments
- StatefulSets
- Services
- Routes
- ConfigMaps
- Secrets
- PVCs
- RBAC
- Network policies
- Application custom resources

### 2.2 Data Layer

This protects persistent data:

- PVC data
- Database files
- Uploaded files
- Message broker queues
- Stateful middleware data
- VM disks when OpenShift Virtualization is used

### 2.3 Operational Layer

This protects the ability to recover predictably:

- Backup schedules
- Restore runbooks
- Storage class mapping
- DNS cutover process
- Access control
- Monitoring
- Audit trail
- Backup validation
- DR test results

A 10-year experienced administrator does not ask only “Did the backup complete?” The correct question is:

> Can I restore the right version of the right application into the right location within the required RTO without corrupting data or breaking security?

## 3. Where OADP Fits and Where It Does Not Fit

OADP is designed mainly for **application-level backup and restore** on OpenShift. It is not a replacement for every OpenShift disaster recovery mechanism.

### 3.1 OADP Is Good For

- Backing up customer application namespaces
- Backing up application-related cluster-scoped resources
- Backing up Kubernetes and OpenShift objects
- Backing up internal images
- Backing up persistent volumes through supported mechanisms
- Restoring an application into the same namespace
- Restoring into a different namespace
- Migrating selected applications between clusters
- Supporting application-level DR workflows
- Supporting namespace-admin self-service backup models in newer OADP versions

### 3.2 OADP Is Not Good For

- Replacing etcd backup and restore
- Full OpenShift control-plane disaster recovery
- Restoring all OpenShift Operators as-is
- Blind full-cluster backup and full-cluster restore
- Backing up external systems that are outside OpenShift
- Guaranteeing database transaction consistency without app-aware handling
- Replacing storage-array replication when near-zero RPO is required

### 3.3 Why OADP Is Not a Full Cluster DR Tool

The OpenShift control plane has complex dependencies:

- etcd state
- cluster operators
- certificates
- node identities
- machine APIs
- cloud credentials
- admission webhooks
- APIService registrations
- CRDs and controllers

Trying to back up and restore the entire cluster using OADP can capture resources that should be recreated by OpenShift itself or by Operators. This can produce conflicts, stale UIDs, broken owner references, invalid webhooks, or resources managed by controllers that no longer match the restored state.

For full platform recovery, use OpenShift-supported approaches such as:

- etcd backup and restore for control-plane disaster recovery
- cluster redeployment by Infrastructure as Code
- GitOps for cluster configuration
- Operator reinstallation through OLM
- OADP for application workloads
- storage replication where required

A mature design separates:

| Layer | Recommended Protection |
|---|---|
| OpenShift control plane | etcd backup, install-config, ignition, cluster backup runbook |
| Cluster configuration | GitOps, ACM policies, manifests, IaC |
| Operators | Reinstall using OLM/GitOps, then restore application custom resources where supported |
| Applications | OADP backup/restore |
| Persistent data | CSI snapshot, Data Mover, FSB, database-native backup, storage replication |

## 4. Core OADP Building Blocks

### 4.1 OADP Operator

The OADP Operator installs and manages the data protection stack, typically including:

- Velero deployment
- Velero plugins
- Node agent for file-system backup / data movement
- BackupStorageLocation objects
- VolumeSnapshotLocation objects
- Required RBAC
- CustomResourceDefinitions

The Operator is usually installed in:

```bash
openshift-adp
```

Check installation:

```bash
oc get pods -n openshift-adp
oc get dpa -n openshift-adp
oc get all -n openshift-adp
```

---

### 4.2 DataProtectionApplication CR

The `DataProtectionApplication` or `DPA` CR is the primary OADP configuration object.

It defines:

- Which Velero plugins are enabled
- Backup storage locations
- Snapshot locations
- Node agent configuration
- Uploader type such as Kopia or Restic, depending on version
- Resource requests/limits
- Advanced options such as load concurrency in newer releases

Example conceptual DPA:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-prod
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
    - name: primary-s3
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: oadp-prod-backups
          prefix: clusters/ocp-prod-01
        config:
          region: us-east-1
          s3ForcePathStyle: "true"
          s3Url: https://s3.example.com
        credential:
          name: cloud-credentials
          key: cloud
  snapshotLocations:
    - name: aws-ebs-us-east-1
      velero:
        provider: aws
        config:
          region: us-east-1
        credential:
          name: cloud-credentials
          key: cloud
```

> Always confirm exact field support with your installed OADP version:

```bash
oc explain dpa.spec
oc explain dpa.spec.configuration
oc explain dpa.spec.configuration.nodeAgent
oc get crd dataprotectionapplications.oadp.openshift.io -o yaml
```

---

### 4.3 Velero Backup CR

The `Backup` CR tells Velero what to back up once.

It can define:

- Included namespaces
- Excluded namespaces
- Included resources
- Excluded resources
- Label selectors
- TTL
- Snapshot behavior
- File-system backup behavior
- Storage location
- Volume snapshot location
- Hooks

---

### 4.4 Velero Schedule CR

The `Schedule` CR creates repeatable backups using a cron expression.

It contains:

- A cron schedule
- A backup template
- TTL
- Included namespaces/resources
- Snapshot or FSB settings

---

### 4.5 Velero Restore CR

The `Restore` CR restores from an existing backup.

It can define:

- Backup name
- Included namespaces
- Excluded resources
- Namespace mapping
- Label selectors
- Restore hooks

---

### 4.6 BackupStorageLocation

`BackupStorageLocation` or `BSL` represents the object store location used by Velero to store backup metadata and, depending on method, data.

Object storage may be:

- AWS S3
- S3-compatible storage
- OpenShift Data Foundation / NooBaa / Multicloud Object Gateway
- MinIO
- Azure Blob Storage
- Google Cloud Storage
- Other supported providers through plugins

Check BSL:

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
oc describe backupstoragelocation -n openshift-adp
```

A healthy BSL should normally show as available.

---

### 4.7 VolumeSnapshotLocation

`VolumeSnapshotLocation` or `VSL` defines where provider snapshots are created for persistent volumes when native cloud snapshot APIs are used.

For CSI snapshots, the storage driver and `VolumeSnapshotClass` are also important.

Check VSL:

```bash
oc get volumesnapshotlocations.velero.io -n openshift-adp
oc describe volumesnapshotlocation -n openshift-adp
```

---

### 4.8 Node Agent

The node agent runs on worker nodes and is used for:

- File System Backup
- Kopia/Restic data upload
- CSI snapshot data movement in supported configurations
- Data upload and data download operations

Check node agent:

```bash
oc get ds -n openshift-adp
oc get pods -n openshift-adp -o wide
```

---

### 4.9 DataUpload and DataDownload

In modern OADP/Velero data movement workflows, you may see:

```bash
oc get datauploads -A
oc get datadownloads -A
```

These objects help track data movement into or out of backup storage.

## 5. Application Backup Strategy Design Principles

### 5.1 Start With Business Requirements

Before writing YAML, define:

| Requirement | Meaning |
|---|---|
| RPO | Maximum acceptable data loss |
| RTO | Maximum acceptable recovery time |
| Retention | How long backups must be kept |
| Legal hold | Whether backups must be immutable |
| Compliance | Encryption, audit, locality, privacy |
| Recovery target | Same namespace, new namespace, new cluster, DR region |
| Consistency | Crash, filesystem, or application consistency |

Example:

| Application | Tier | RPO | RTO | Backup Method |
|---|---:|---:|---:|---|
| Payment API | Gold | 15 min | 1 hr | DB-native + CSI/Data Mover + OADP resources |
| Internal Wiki | Silver | 4 hr | 8 hr | OADP Schedule + FSB |
| Dev namespace | Bronze | 24 hr | Best effort | Metadata backup only or weekly backup |

---

### 5.2 Back Up Applications, Not Noise

Do not blindly back up everything. Exclude:

- OpenShift system namespaces unless specifically required
- Operator namespaces during application backup
- Events
- Pods generated by controllers
- ReplicaSets where Deployments are backed up
- Completed Jobs if not required
- Build pods
- Debug pods
- Temporary ConfigMaps
- ServiceAccount token secrets that are auto-generated

Focus on resources needed to rebuild application desired state.

---

### 5.3 Restore Design Is More Important Than Backup Design

Backup strategy must be designed backward from restore.

Ask:

- Where will I restore?
- Is the StorageClass present there?
- Is the CSI driver present there?
- Are CRDs present there?
- Are Operators installed there?
- Are routes and DNS safe to restore?
- Will Secrets still be valid?
- Will external systems accept restored credentials?
- Can I avoid overwriting the running production namespace?

---

### 5.4 Separate Platform Recovery and Application Recovery

Use different mechanisms:

- Platform recovery: etcd backup, cluster install artifacts, GitOps, ACM, IaC
- Application recovery: OADP backups, DB backups, storage snapshots
- Configuration recovery: Git repositories, Helm charts, Kustomize, Argo CD

---

### 5.5 Always Test Restore

A backup strategy must include scheduled restore tests:

- Daily smoke restore for critical namespace metadata
- Weekly restore into non-production namespace
- Monthly full application restore test
- Quarterly DR exercise into separate cluster
- Restore documentation with screenshots/logs

## 7. Backup Scope Strategy

### 7.1 Namespace-Based Backup

Best for simple application ownership.

Example:

```yaml
spec:
  includedNamespaces:
    - finance-prod
```

Use when:

- One app per namespace
- Namespace is clean
- No unrelated workloads exist
- RBAC and policies are namespace-scoped

---

### 7.2 Label-Based Backup

Best for shared namespaces.

Label resources:

```bash
oc label deploy payment-api -n finance-prod app.kubernetes.io/part-of=payment
oc label svc payment-api -n finance-prod app.kubernetes.io/part-of=payment
oc label route payment-api -n finance-prod app.kubernetes.io/part-of=payment
oc label pvc payment-db -n finance-prod app.kubernetes.io/part-of=payment
```

Backup selector:

```yaml
spec:
  includedNamespaces:
    - finance-prod
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payment
```

Be careful: if you forget to label a ConfigMap, Secret, PVC, or RoleBinding, it might not be included.

---

### 7.3 Resource-Based Backup

Use when you want only selected resource kinds.

Example:

```yaml
spec:
  includedNamespaces:
    - finance-prod
  includedResources:
    - deployments.apps
    - services
    - routes.route.openshift.io
    - configmaps
    - secrets
    - persistentvolumeclaims
```

Use this carefully. Missing one required type can break restore.

---

### 7.4 Exclusion Strategy

Common exclusions:

```yaml
spec:
  excludedResources:
    - events
    - events.events.k8s.io
    - pods
    - replicasets.apps
```

You can also label individual objects:

```bash
oc label secret temporary-token -n finance-prod velero.io/exclude-from-backup=true
```

Use exclusions for:

- Temporary secrets
- Generated config
- Debug objects
- Large unnecessary resources
- Objects recreated by controllers

---

### 7.5 Cluster-Scoped Resource Strategy

Cluster-scoped resources are tricky.

Examples:

- ClusterRole
- ClusterRoleBinding
- StorageClass
- CRD
- SCC
- PriorityClass
- APIService
- MutatingWebhookConfiguration
- ValidatingWebhookConfiguration

Strategy:

| Resource | Recommendation |
|---|---|
| StorageClass | Usually recreate through platform automation; include only if needed |
| CRD | Usually installed by Operator; do not depend on app backup to restore CRDs blindly |
| Custom SCC | Include if app uses custom SCC and it is not managed elsewhere |
| ClusterRole/ClusterRoleBinding | Include only app-specific ones |
| Webhooks | Avoid restoring blindly; can break API server admission |
| APIService | Avoid unless fully understood |

A safer enterprise pattern is:

- Store cluster-scoped platform resources in GitOps.
- Use OADP for namespace resources and selected app-specific cluster resources.
- Reinstall Operators before restoring their custom resources.

## 8. Persistent Volume Backup Strategy

Persistent data is usually the most important and most difficult part.

### 8.1 Metadata-Only Backup

This backs up Kubernetes/OpenShift objects but not PV data.

Use for:

- Stateless apps
- Apps with external databases
- Apps whose data is rebuilt from another source
- CI/CD workloads

Example:

```yaml
spec:
  includedNamespaces:
    - web-prod
  snapshotVolumes: false
  defaultVolumesToFsBackup: false
```

---

### 8.2 CSI Snapshot Backup

CSI snapshot backup uses the Kubernetes CSI snapshot API.

Use when:

- Storage driver supports snapshots
- VolumeSnapshotClass exists
- Snapshot restore is supported
- Snapshot lifecycle is understood

Check:

```bash
oc get volumesnapshotclass
oc get csidriver
oc get storageclass
```

Pros:

- Fast
- Storage-efficient
- Good for large volumes
- Minimal data movement during backup

Cons:

- Snapshot may be in the same storage backend
- Cross-cluster restore may be limited
- Region/zone/provider compatibility matters
- Snapshot alone may not protect against storage backend loss

---

### 8.3 CSI Snapshot + Data Mover

Data Mover copies snapshot data to object storage.

Use when:

- You need off-cluster/off-storage protection
- You need better portability
- You want object storage as the durable backup target
- Snapshot-only backup is not enough for disaster recovery

Pros:

- Better DR posture than snapshot-only
- Object storage can have immutability and lifecycle policy
- Useful for cluster-loss scenarios

Cons:

- More network traffic
- More backup time
- More storage cost
- Requires tuning and monitoring

Check:

```bash
oc get datauploads -A
oc get datadownloads -A
oc describe dataupload -n openshift-adp <name>
```

---

### 8.4 File System Backup with Kopia or Restic

File System Backup reads mounted volume contents and uploads them to object storage.

Use when:

- CSI snapshots are not available
- NFS volumes are used
- Storage backend does not support snapshots
- You need file-level backup behavior
- Cross-cluster portability is more important than speed

Pros:

- Works in many environments
- Object-store based
- Good for NFS and unsupported snapshot environments

Cons:

- Slower for large volumes
- More node/network load
- Requires node agent
- May need careful security/SCC handling
- Consistency still requires app-aware handling

Example backup forcing FSB by default:

```yaml
spec:
  includedNamespaces:
    - legacy-app
  defaultVolumesToFsBackup: true
```

---

### 8.5 Database-Native Backup

For databases, OADP alone may not be enough.

Use database-native backups for:

- PostgreSQL
- MySQL/MariaDB
- MongoDB
- Redis with persistence
- Kafka
- Elasticsearch/OpenSearch
- DB2/Oracle

Examples:

| Database | Native Backup Approach |
|---|---|
| PostgreSQL | pg_dump, pg_basebackup, WAL archiving, operator backup CR |
| MySQL | mysqldump, xtrabackup, operator backup |
| MongoDB | mongodump, Ops Manager, operator backup |
| Redis | RDB/AOF strategy plus controlled snapshot |
| Kafka | Topic replication, MirrorMaker, storage snapshots only with careful quiescing |
| Elasticsearch | Repository snapshot API |

Best enterprise pattern:

- Use OADP to protect Kubernetes/OpenShift objects.
- Use database-native backup for transactionally consistent data.
- Optionally use CSI/Data Mover for volume-level recovery.
- Test restore from both layers.

---

### 8.6 PV Backup Decision Matrix

| Workload Type | Recommended Backup |
|---|---|
| Stateless web app | Metadata only |
| App with external DB | Metadata + external DB backup |
| Stateful app with supported CSI | OADP + CSI snapshot |
| Stateful app requiring off-cluster DR | OADP + CSI snapshot + Data Mover |
| NFS-based app | OADP + FSB |
| Critical database | DB-native backup + OADP + optional CSI/Data Mover |
| OpenShift VM | OADP with KubeVirt plugin + CSI/FSB as supported |

## 9. Application Consistency Strategy

### 9.1 Crash-Consistent Backup

A crash-consistent backup is similar to pulling power from a server and taking the disk state.

Good for:

- Stateless apps
- Some journaling filesystems
- Apps that recover cleanly after restart

Risky for:

- Databases
- Message queues
- Multi-volume applications
- Applications with in-memory state

---

### 9.2 File-System-Consistent Backup

This usually involves freezing the filesystem before snapshot and unfreezing after snapshot.

Example Velero hook annotations:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: file-app
  namespace: finance-prod
spec:
  template:
    metadata:
      annotations:
        pre.hook.backup.velero.io/container: app
        pre.hook.backup.velero.io/command: '["/bin/sh", "-c", "fsfreeze --freeze /data"]'
        pre.hook.backup.velero.io/on-error: Fail
        pre.hook.backup.velero.io/timeout: 120s
        post.hook.backup.velero.io/container: app
        post.hook.backup.velero.io/command: '["/bin/sh", "-c", "fsfreeze --unfreeze /data"]'
        post.hook.backup.velero.io/on-error: Continue
        post.hook.backup.velero.io/timeout: 120s
```

Use only when:

- The container image has `fsfreeze`
- The container has required permissions
- The filesystem supports it
- Application team approves it
- You have tested freeze/unfreeze behavior

---

### 9.3 Application-Consistent Backup

Application-consistent backup uses the application’s own mechanism to prepare data.

Examples:

- Put app in maintenance mode
- Flush buffers
- Pause writes
- Run DB checkpoint
- Run DB dump before backup
- Freeze VM filesystem using guest agent
- Use operator-native backup CRs

This is the safest approach for critical systems.

---

### 9.4 Hook Design Rules

Hooks must be:

- Idempotent
- Fast
- Safe if retried
- Logged
- Tested manually
- Version controlled
- Approved by app owner

Bad hook example:

```bash
kill -9 database
```

Good hook behavior:

- Stop accepting writes gracefully
- Flush state
- Confirm readiness
- Fail backup if quiesce fails
- Always attempt post-backup unquiesce

---

### 9.5 Hook Failure Policy

Use `on-error: Fail` when consistency is mandatory.

Use `on-error: Continue` only when:

- Hook is optional
- Backup can still be useful
- You alert on hook failure

For databases, failed pre-backup hook should normally fail the backup.

## 10. Backup Storage Strategy

### 10.1 Object Storage Requirements

Your object storage should provide:

- High durability
- Encryption at rest
- TLS in transit
- Access logging
- Lifecycle policy
- Versioning where possible
- Immutability/object lock for ransomware protection
- Cross-region replication for DR
- Monitoring and quota alerts

---

### 10.2 Bucket Layout

Recommended bucket structure:

```text
oadp-prod-backups/
  clusters/
    ocp-prod-01/
      velero/
    ocp-prod-02/
      velero/
    ocp-dr-01/
      velero/
```

Use unique prefixes per cluster.

Avoid multiple clusters writing to the same prefix unless you fully understand the consequences.

---

### 10.3 Credential Strategy

Use least privilege.

The backup identity should be able to:

- List bucket/prefix
- Put objects
- Get objects
- Delete objects only if backup deletion is allowed
- Manage snapshots only in required region/project

Avoid using admin/root cloud credentials.

Check secret:

```bash
oc get secret cloud-credentials -n openshift-adp
oc get secret cloud-credentials -n openshift-adp -o jsonpath='{.data.cloud}' | base64 -d
```

---

### 10.4 Encryption Strategy

Use:

- TLS to object storage
- Object encryption at rest
- KMS-managed keys where possible
- Separate keys per environment
- Regular key rotation policy
- Documented restore access to keys

Remember:

> If you lose encryption keys, your backups may be useless.

---

### 10.5 Immutability and Ransomware Protection

For critical production:

- Enable object lock where supported
- Use write-once retention policy
- Restrict delete permissions
- Keep backup credentials separate from application credentials
- Audit backup deletion
- Replicate to separate account/project/region

---

## 11. Schedule and Retention Strategy

### 11.1 RPO-Driven Schedule

Example policy:

| Tier | Schedule | Retention | Notes |
|---|---|---|---|
| Platinum | Every 15 min metadata + DB-native continuous | 35 days | For high-value systems |
| Gold | Every 4 hours + daily full | 30–90 days | Critical production |
| Silver | Daily | 30 days | Standard production |
| Bronze | Weekly | 14–30 days | Dev/test/non-critical |

---

### 11.2 Avoid Backup Overlap

Do not schedule backups more frequently than they can complete.

If a namespace backup usually takes 45 minutes, do not run it every 30 minutes.

Check duration:

```bash
oc get backups -n openshift-adp
oc describe backup -n openshift-adp <backup-name>
```

---

### 11.3 Stagger Backup Windows

Avoid running all backups at midnight.

Example:

| Namespace | Schedule |
|---|---|
| finance-prod | 00:15, 04:15, 08:15, 12:15, 16:15, 20:15 |
| hr-prod | 00:45, 06:45, 12:45, 18:45 |
| crm-prod | 01:15, 07:15, 13:15, 19:15 |

---

### 11.4 Retention With TTL

Velero/OADP Backup CRs support TTL-style retention.

Example:

```yaml
spec:
  ttl: 720h0m0s
```

Examples:

| Retention | TTL |
|---|---|
| 7 days | `168h0m0s` |
| 30 days | `720h0m0s` |
| 90 days | `2160h0m0s` |

Also configure object storage lifecycle carefully. Object storage lifecycle should not delete data before Velero/OADP retention expects it to exist.

---

## 12. Security, RBAC, and Tenant Strategy

### 12.1 Cluster Admin Model

Traditional OADP operations are cluster-admin driven.

Use this model when:

- Central platform team owns backups
- Compliance requires strict controls
- Backup storage is shared
- Cross-namespace restores are required

---

### 12.2 Namespace Admin / Self-Service Model

In newer OADP versions, namespace-scoped self-service workflows allow namespace admins to request backup and restore operations without full cluster-admin privileges.

Use this model when:

- Teams own their own namespaces
- Platform team wants controlled delegation
- Multi-tenant OpenShift is used
- Backup access must be namespace-limited

Design rules:

- Namespace admin must not access other tenants’ backup data
- Platform admin controls allowed backup locations
- Restore into unauthorized namespaces must be blocked
- Logs and download requests must be controlled

---

### 12.3 Secrets Strategy

Backups may contain Secrets.

This means object storage may contain:

- Database passwords
- API tokens
- TLS keys
- OAuth client secrets
- Registry credentials

Controls:

- Encrypt backup storage
- Restrict object access
- Audit downloads
- Rotate secrets after major restore when required
- Consider external secret managers
- Avoid backing up temporary auto-generated tokens when not needed

---

### 12.4 Backup Deletion Security

Backup deletion is sensitive.

Protect against:

- Accidental deletion
- Malicious deletion
- Compromised backup service account
- Ransomware deleting all backups

Controls:

- Object lock
- Separate delete permission
- Approval workflow
- Audit logs
- Separate account/project
- Backup of backup metadata

---

## 15. Restore Strategy

### 15.1 Restore Principles

Never restore blindly into production unless this is an approved incident response step.

Preferred restore flow:

1. Restore into isolated namespace.
2. Validate resources.
3. Validate PVC data.
4. Start application safely.
5. Run smoke tests.
6. Promote to production or cut over route/DNS.

---

### 15.2 Simple Restore

```yaml
apiVersion: velero.io/v1

metadata:
  name: restore-finance-prod

```

```bash
oc apply -f restore-finance-prod.yaml
```

Check:

```bash
oc get restore -n openshift-adp
oc describe restore restore-finance-prod -n openshift-adp
```

apiVersion: velero.io/v1

## 16. Application Migration and DR Strategy

OADP can be used for application movement between clusters, but strategy matters.

### 16.1 Same Cluster Restore

Use for:

- Accidental deletion
- Namespace corruption
- Bad deployment rollback
- Test restore

Risk:

- Existing resources conflict
- Production routes may be duplicated
- PVC names may collide

---

### 16.2 Same Platform, Different Cluster

Use for:

- Cluster refresh
- OpenShift upgrade migration
- Hardware migration
- DR rehearsal

Requirements:

- Same or compatible OADP/Velero versions
- Required CRDs present
- Required Operators installed
- Compatible StorageClasses
- Compatible CSI snapshot support or FSB/Data Mover
- Image pull access
- DNS strategy

---

### 16.3 Cross-Cloud Restore

More complex because:

- Snapshot APIs differ
- StorageClasses differ
- Load balancer behavior differs
- Routes/DNS differ
- Security policies differ

For cross-cloud DR, prefer:

- OADP metadata backup
- FSB/Data Mover for data portability
- Database-native backups to portable object storage
- GitOps for cluster configuration
- StorageClass mapping
- Thorough DR tests

---

### 16.4 DR Cluster Pattern

A mature DR cluster design:

1. Build DR OpenShift cluster from IaC.
2. Install required Operators using GitOps.
3. Configure OADP with read access to backup bucket.
4. Restore selected application namespaces.
5. Restore or replay database backups.
6. Validate services internally.
7. Cut over DNS/routes/load balancer.
8. Monitor application and data consistency.

---

## 17. Operator-Managed Application Strategy

### 17.1 Why Operators Are Special

Operators manage desired state. If you restore Operator-owned resources incorrectly, the Operator may:

- Recreate objects
- Delete restored objects
- Reject old CR versions
- Trigger upgrades
- Reconcile broken state
- Conflict with restored owner references

---

### 17.2 Recommended Pattern

For Operator-managed apps:

1. Back up application namespace resources carefully.
2. Do not back up the Operator installation namespace as part of the app backup.
3. Reinstall the Operator on the target cluster first.
4. Confirm CRDs and API versions exist.
5. Restore application custom resources and data.
6. Follow vendor-specific restore documentation.

---

### 17.3 Example: PostgreSQL Operator

Recommended strategy:

- Use operator-native database backup where available.
- Use OADP for Kubernetes objects.
- Restore Operator first.
- Restore DB according to Operator documentation.
- Use OADP PV restore only if supported and tested.

---

### 17.4 Example: OpenShift Data Foundation

Do not treat ODF itself as a simple application namespace backup.

For ODF-backed apps:

- Use OADP to protect application namespaces.
- Use ODF/NooBaa/MCG as backup target where appropriate.
- Understand whether PV snapshots are local to the same storage system.
- Use Data Mover or replication for stronger DR.

---

## 18. OpenShift-Specific Resources to Consider

### 18.1 Routes

Routes may expose restored applications.

Strategy:

- Exclude routes during test restore.
- Restore routes only during production recovery.
- Use namespace mapping carefully.
- Update hostnames for DR.

---

### 18.2 ImageStreams and Internal Images

OADP can protect internal images depending on configuration and plugins.

Strategy:

- Prefer external enterprise registry for important images.
- Back up ImageStreams if using OpenShift internal registry.
- Validate image pull after restore.
- Mirror images for disconnected DR.

---

### 18.3 SecurityContextConstraints

If an app uses custom SCC:

```bash
oc adm policy who-can use scc/<scc-name>
oc get scc <scc-name> -o yaml
```

Strategy:

- Manage SCC through GitOps where possible.
- Include app-specific SCC only if necessary.
- Avoid restoring default OpenShift SCCs.

---

### 18.4 RBAC

Back up app-specific:

- Roles
- RoleBindings
- ServiceAccounts

Be careful with:

- ClusterRoles
- ClusterRoleBindings

Prefer GitOps for cluster-level RBAC.

---

### 18.5 NetworkPolicy

NetworkPolicy can block restored app traffic.

Validate after restore:

```bash
oc get networkpolicy -n <namespace>
oc describe networkpolicy -n <namespace>
```

---

### 18.6 BuildConfig and DeploymentConfig

Older OpenShift applications may use:

- BuildConfig
- DeploymentConfig
- ImageStream

Include these if the app depends on OpenShift-native build/deploy workflows.

---

### 18.7 Admission Webhooks

Be very careful restoring:

- MutatingWebhookConfiguration
- ValidatingWebhookConfiguration

Broken webhooks can block API operations.

Strategy:

- Do not include cluster-wide webhooks in normal app backup.
- Recreate platform webhooks through Operator/GitOps.

## 20. Performance and Scale Strategy

### 20.1 Backup Performance Drivers

Backup duration depends on:

- Number of Kubernetes objects
- Number and size of PVCs
- Snapshot API speed
- Object storage throughput
- Network bandwidth
- Node agent CPU/memory
- File count inside volumes
- Compression/deduplication behavior
- API server responsiveness
- Backup hooks duration

---

### 20.2 Many Small Files Problem

FSB can be slow with millions of small files.

Mitigation:

- Prefer application-native backup archive
- Use CSI snapshots if possible
- Tune node agent resources
- Avoid backing up cache directories
- Exclude unnecessary paths where supported
- Re-architect app data layout if needed

---

### 20.3 Node Agent Sizing

Increase node agent resources when:

- FSB is slow
- DataUpload is slow
- Node agent is OOMKilled
- CPU throttling occurs

Check:

```bash
oc top pods -n openshift-adp
oc describe pod -n openshift-adp <node-agent-pod>
oc logs -n openshift-adp <node-agent-pod>
```

---

### 20.4 API Server Load

Large backups can stress the API server.

Mitigation:

- Split backups by namespace/tier
- Exclude noisy resources
- Stagger schedules
- Avoid full-cluster style backups
- Do not back up high-churn event resources

---

### 20.5 Snapshot Limits

Cloud and CSI providers may have:

- Snapshot rate limits
- Volume restore limits
- Regional constraints
- API throttling
- Per-volume snapshot limits

Document limits for your provider.

---

## 21. Troubleshooting Backup and Restore Failures

### 21.1 Backup Statuses

Common statuses:

| Status | Meaning |
|---|---|
| New | Backup object created |
| InProgress | Backup running |
| Completed | Backup succeeded |
| PartiallyFailed | Some resources failed |
| Failed | Backup failed |
| Deleting | Backup deletion requested |

---

### 21.2 Backup Failed

Commands:

```bash
oc describe backup -n openshift-adp <backup-name>
velero backup describe <backup-name> --details
velero backup logs <backup-name>
oc logs deploy/velero -n openshift-adp
```

Check:

- BSL available?
- Credentials valid?
- Bucket exists?
- Network route to object storage?
- CA certificate issue?
- Plugin loaded?
- CRD missing?
- Hook failed?
- Snapshot class missing?
- PVC snapshot unsupported?

---

### 21.3 Backup PartiallyFailed

Common causes:

- One resource cannot be listed
- ImageStream backup failed
- Snapshot failed for one PVC
- Hook failed for one pod
- RBAC denied access
- CRD conversion issue
- Webhook blocked object access

Action:

```bash
velero backup describe <backup-name> --details
velero backup logs <backup-name> | grep -i error
```

Do not ignore PartiallyFailed backups for production.

---

### 21.4 BSL Unavailable

Check:

```bash
oc get bsl -n openshift-adp
oc describe bsl -n openshift-adp <bsl-name>
oc get secret -n openshift-adp
oc logs deploy/velero -n openshift-adp | grep -i backupstoragelocation
```

Possible causes:

- Wrong bucket
- Wrong endpoint
- Wrong region
- Bad credentials
- TLS/CA issue
- DNS issue
- Proxy issue
- Object store down
- Clock skew causing signature errors

---

### 21.5 Snapshot Failure

Check:

```bash
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get volumesnapshotcontent -A
oc describe backup -n openshift-adp <backup-name>
oc logs deploy/velero -n openshift-adp | grep -i snapshot
```

Possible causes:

- No default VolumeSnapshotClass
- Wrong CSI driver
- SnapshotClass deletionPolicy issue
- Storage provider does not support snapshots
- PVC is not bound
- Volume mode unsupported
- Cross-zone mismatch
- Cloud API permission missing

---

### 21.6 DataUpload or DataDownload Failure

Check:

```bash
oc get datauploads -A
oc describe dataupload -n openshift-adp <name>
oc get datadownloads -A
oc describe datadownload -n openshift-adp <name>
oc logs -n openshift-adp <node-agent-pod>
```

Possible causes:

- Node agent not running on required node
- Object storage connectivity issue
- Insufficient node resources
- PVC not mounted as expected
- Permission issue on volume path
- Timeout

---

### 21.7 Restore PVC Pending

Check:

```bash
oc get pvc -n <namespace>
oc describe pvc -n <namespace> <pvc-name>
oc get storageclass
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Possible causes:

- StorageClass missing
- Different provisioner in target cluster
- Requested capacity unavailable
- AccessMode unsupported
- VolumeBindingMode issue
- Zone/topology mismatch

---

### 21.8 Restore Pods Not Ready

Check:

```bash
oc get pods -n <namespace>
oc describe pod -n <namespace> <pod>
oc logs -n <namespace> <pod>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Possible causes:

- Secret missing
- ConfigMap missing
- Image pull issue
- SCC denied
- ServiceAccount missing
- NetworkPolicy blocking
- Database corruption
- Route/Service mismatch

---

### 21.9 Admission Webhook Problems

Symptoms:

- Restore hangs or fails creating resources
- API server rejects restored objects
- Error mentions validating or mutating webhook

Mitigation:

- Reinstall required Operator first
- Temporarily exclude webhook resources
- Restore into clean namespace
- Follow vendor restore procedure

## 22. Enterprise Runbooks

### 22.1 Standard Backup Onboarding Runbook

1. Identify application owner.
2. Classify app tier.
3. Document RPO/RTO.
4. Inventory namespace resources.
5. Inventory PVCs and StorageClasses.
6. Identify Operator dependencies.
7. Identify external dependencies.
8. Choose backup method:
   - metadata only
   - CSI snapshot
   - CSI + Data Mover
   - FSB
   - app-native
9. Define schedule and retention.
10. Create Backup/Schedule CR.
11. Run manual backup.
12. Restore into test namespace.
13. Validate application.
14. Create alert rules.
15. Document runbook.
16. Get app owner sign-off.

---

### 22.2 Production Restore Runbook

1. Declare incident and severity.
2. Freeze production writes if possible.
3. Identify last known good backup.
4. Confirm backup status is Completed.
5. Confirm target namespace/cluster readiness.
6. Confirm Operators/CRDs exist if needed.
7. Confirm StorageClass/VolumeSnapshotClass exists.
8. Restore into isolated namespace where possible.
9. Validate PVCs.
10. Validate pods and logs.
11. Run application smoke test.
12. Run data validation.
13. Cut over route/DNS if required.
14. Monitor application.
15. Record incident timeline.
16. Update root-cause and prevention tasks.

---

### 22.3 DR Cluster Restore Runbook

1. Build or activate DR cluster.
2. Install required platform Operators.
3. Install OADP.
4. Configure BSL with access to production backup storage.
5. Validate BSL availability.
6. Restore cluster-scoped app prerequisites from GitOps.
7. Restore application namespace.
8. Restore or attach data.
9. Validate application.
10. Switch DNS/load balancer.
11. Notify stakeholders.
12. Continue monitoring.

---

### 22.4 Backup Deletion Runbook

1. Confirm backup name.
2. Confirm retention policy.
3. Confirm deletion approval.
4. Check whether snapshots exist.
5. Delete through Velero/OADP, not manually from object store.
6. Confirm DeleteBackupRequest completion.
7. Verify object storage cleanup.
8. Log deletion action.

## 24. Interview-Style Explanation

### Question

How would you design an application backup strategy in OpenShift using OADP?

### Senior-Level Answer

I would not start by creating a Backup CR immediately. First, I would classify the application based on business criticality, RPO, RTO, data consistency requirements, and restore target. Then I would inventory all OpenShift resources in the namespace, identify PVCs, StorageClasses, Operators, CRDs, Routes, Secrets, RBAC, and external dependencies.

For stateless applications, OADP metadata backup may be sufficient. For stateful workloads, I would choose between CSI snapshots, CSI snapshots with Data Mover, or File System Backup depending on the storage provider and DR requirement. For databases, I would not rely only on crash-consistent volume backup. I would use database-native backups or application quiesce hooks to make the backup application-consistent.

I would configure object storage as a BackupStorageLocation with encryption, lifecycle policy, immutability where required, and least-privilege credentials. If the storage supports snapshots, I would configure VolumeSnapshotLocation or CSI VolumeSnapshotClass as appropriate. For unsupported storage or NFS, I would enable nodeAgent and use Kopia/Restic-based File System Backup.

For backup scope, I would prefer namespace-based backups for clean application namespaces, label-based backups for shared namespaces, and explicit exclusions for noise such as events, pods, and generated ReplicaSets. I would avoid backing up Operators and system namespaces as part of application backup. For Operator-managed applications, I would reinstall the Operator first and restore application custom resources and data according to vendor-supported procedure.

I would create Schedule CRs based on RPO and retention, stagger schedules to avoid backup storms, monitor backup status and BSL availability, and alert on Failed or PartiallyFailed backups. Most importantly, I would run restore tests regularly into isolated namespaces or DR clusters, because a backup has no value until restore is proven.

## 26. Common Mistakes

### Mistake 1: Treating OADP as Full Cluster Backup

OADP should protect applications, not blindly restore the full OpenShift cluster.

### Mistake 2: Backing Up Operators With Applications

Operators should usually be reinstalled. Application CRs and data should be restored according to a tested process.

### Mistake 3: No Restore Testing

Completed backup status does not prove recoverability.

### Mistake 4: Ignoring PartiallyFailed

A PartiallyFailed backup can be missing the exact object or volume you need during an incident.

### Mistake 5: No Application Consistency

A crash-consistent database backup may restore but still contain logical corruption.

### Mistake 6: Overlapping Schedules

Running backups too frequently can overload API server, object storage, snapshot APIs, and node agents.

### Mistake 7: Restoring Routes Into Test Namespace

This can accidentally expose test-restored apps with production hostnames.

### Mistake 8: Missing StorageClass Mapping

Restores fail when target cluster does not have the same StorageClass or provisioner.

### Mistake 9: Weak Backup Credentials

Using overly privileged credentials increases blast radius.

### Mistake 10: No Backup Immutability

Without immutability or separate delete controls, ransomware or admin error can remove backups.

## Final Senior Admin Notes

For production OpenShift, the best OADP strategy is not a single backup YAML. It is a tested operating model:

1. Classify applications.
2. Protect only the right resources.
3. Use the right PV backup method.
4. Make stateful apps consistent.
5. Store backups securely outside the failure domain.
6. Monitor every backup.
7. Test restore regularly.
8. Keep restore runbooks ready.
9. Integrate with GitOps and platform DR.
10. Review strategy after every major OpenShift, OADP, storage, or application upgrade.

A senior OpenShift administrator should always remember:

> Backup is a technical activity, but recovery is a business outcome.
