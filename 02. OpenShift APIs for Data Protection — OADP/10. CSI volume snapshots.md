# CSI Volume Snapshots in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift / Kubernetes administrators with production experience  
**Level:** 10+ years infrastructure, OpenShift, Kubernetes, storage, backup, DR, and troubleshooting  
**Scope:** CSI volume snapshots, OADP, Velero, VolumeSnapshotClass, VolumeSnapshot, VolumeSnapshotContent, Data Mover, restore design, troubleshooting, and production runbooks

---

## 1. Executive summary

CSI volume snapshots are the Kubernetes-standard way to take point-in-time snapshots of PersistentVolumeClaim-backed storage when the underlying storage is provided through a CSI driver that supports the Kubernetes Volume Snapshot API.

In OpenShift APIs for Data Protection, OADP uses Velero plus OpenShift plugins to back up application Kubernetes resources, internal images, and persistent volume data. For persistent volumes, OADP can use:

1. **CSI volume snapshots**
2. **Native cloud provider snapshots**
3. **File System Backup, formerly Restic-based backup and later Kopia/Restic FSB**
4. **CSI Data Mover**, which takes CSI snapshots and moves the data to object storage

The most important production distinction is this:

> A plain CSI snapshot is usually a storage-backend snapshot. It is fast, efficient, and useful for same-cluster or same-storage recovery, but it is not automatically an off-cluster backup. For disaster recovery where the storage backend or cluster can be lost, use CSI Data Mover or another off-cluster backup method.

## 2. Mental model

Think of OADP CSI snapshot protection in three layers.

```text
Application layer
  └── Deployment / StatefulSet / DB / VM / PVC

Kubernetes snapshot layer
  ├── VolumeSnapshotClass       # Admin-defined snapshot policy for a CSI driver
  ├── VolumeSnapshot            # Namespace-scoped user/Velero request
  └── VolumeSnapshotContent     # Cluster-scoped binding to actual backend snapshot

OADP / Velero backup layer
  ├── Backup CR / Schedule CR
  ├── Restore CR
  ├── BackupStorageLocation     # Object storage for backup metadata/resources
  ├── DataUpload/DataDownload   # Used by CSI Data Mover
  └── BackupRepository          # Kopia repository, usually per namespace
```

A `VolumeSnapshot` is similar to a `PersistentVolumeClaim`: it is a request. A `VolumeSnapshotContent` is similar to a `PersistentVolume`: it represents the actual storage-side snapshot. A `VolumeSnapshotClass` is similar to a `StorageClass`: it tells Kubernetes which CSI driver and snapshot parameters to use.

---

## 3. What problem CSI snapshots solve

Without snapshots, backing up a PV normally means reading the filesystem contents from a running pod or node and copying those files to object storage. That works, but it can be slower, less consistent, and heavy on application I/O.

CSI snapshots solve a different problem:

- They ask the storage backend to create a point-in-time copy.
- They avoid reading every file through the pod filesystem during the snapshot operation.
- They allow fast rollback or clone-style restore when the storage backend supports it.
- They provide a standard Kubernetes API so Velero/OADP does not need a custom snapshot implementation for every storage vendor.

However, snapshots are not magic. They do not automatically make an application transaction-consistent. They also do not always protect you if the underlying storage system is lost.

## 4. Key terms

| Term | Meaning | Scope | Senior-admin note |
|---|---|---|---|
| `VolumeSnapshotClass` | Defines snapshot driver, deletion policy, and driver-specific parameters | Cluster | Must match CSI driver used by the PVC's PV |
| `VolumeSnapshot` | Request for a snapshot of a PVC | Namespace | Created manually or by Velero/OADP |
| `VolumeSnapshotContent` | Cluster object representing the actual backend snapshot | Cluster | Contains backend snapshot handle/status |
| CSI driver | Storage driver implementing CSI APIs | Cluster/node | Must support snapshot API, not only volume provisioning |
| Snapshot controller | Watches snapshot CRs and binds objects | Cluster | Provided by Kubernetes distribution/OpenShift storage stack |
| CSI external-snapshotter sidecar | Calls CSI driver snapshot operations | Storage driver pod | Usually deployed with the CSI driver |
| OADP | Red Hat operator for application backup/restore APIs | Cluster | Installs/manages Velero and plugins |
| Velero | Backup/restore engine used by OADP | Cluster | Performs backup/restore workflows |
| CSI Data Mover | Moves CSI snapshot data to object storage | Cluster | Uses Kopia through node agent/DataUpload/DataDownload |
| BackupStorageLocation | Object store for Velero backup metadata and data mover repository | Cluster | Required for OADP backups |
| VolumeSnapshotLocation | Velero snapshot location for native cloud snapshots | Cluster | Generally not required for CSI snapshots; required for native provider snapshots |

## 6. Plain CSI snapshot vs CSI Data Mover

### 6.1 Plain CSI snapshot

Plain CSI snapshot mode creates the snapshot in the storage backend and stores Kubernetes metadata in the Velero backup. It is fast and efficient, but the volume data is not copied into the Velero object store.

Use it when:

- The storage snapshot is durable enough for your recovery goal.
- You restore to the same cluster or a cluster with access to the same storage snapshot backend.
- You want fast local rollback/restore.
- You are protecting against namespace/application deletion rather than full storage disaster.

Risks:

- Backend snapshot might live in the same failure domain as the source volume.
- Cross-cluster restore can fail if the destination does not have the same CSI driver name and snapshot access.
- Snapshot metadata in object storage is not the same as data backup.

### 6.2 CSI Data Mover

CSI Data Mover creates a CSI snapshot, then reads snapshot data and writes it to object storage through a backup repository. In current OADP design, the built-in Data Mover uses Kopia as the uploader mechanism.

Use it when:

- You need off-cluster DR.
- You need to restore after accidental cluster deletion.
- You need longer retention than the storage backend snapshot policy allows.
- You need to restore into another cluster or another storage backend, subject to compatibility.
- You need incremental backup support for block and filesystem PVs.

Trade-offs:

- Slower than plain snapshots because data is copied.
- Consumes object storage capacity.
- Requires node agent, Kopia repository, credentials, and correct scheduling/resources.
- More moving parts to troubleshoot: `DataUpload`, `DataDownload`, `BackupRepository`, node-agent pods, Kopia repo, and object storage.

## 7. Snapshot consistency levels

A snapshot can be one of these consistency levels:

### 7.1 Crash-consistent

The storage captures blocks as if the node or application crashed at that instant. Most storage snapshots are crash-consistent by default.

Good for:

- Many journaling filesystems
- Applications that can recover from crash state
- Stateless or cache-like data

Risky for:

- Databases with heavy write activity
- Multi-volume applications without group snapshot consistency
- Applications with buffered writes not flushed to disk

### 7.2 Filesystem-consistent

The filesystem is frozen or flushed before snapshot and thawed afterward.

Possible with:

- Velero backup hooks
- `fsfreeze` for Linux filesystems
- Application-specific scripts

Example pre/post hook idea:

```yaml
metadata:
  annotations:
    pre.hook.backup.velero.io/command: '["/sbin/fsfreeze", "--freeze", "/var/lib/mysql"]'
    post.hook.backup.velero.io/command: '["/sbin/fsfreeze", "--unfreeze", "/var/lib/mysql"]'
```

Use carefully. Freezing a filesystem too long can cause application stalls.

### 7.3 Application-consistent

The application flushes memory, commits transactions, pauses writes, or creates its own checkpoint before the storage snapshot.

Examples:

- PostgreSQL: `pg_start_backup`/`pg_stop_backup` style workflows or proper WAL archiving strategy
- MySQL/MariaDB: `FLUSH TABLES WITH READ LOCK`, backup locks, or database-native backup tooling
- MongoDB: `fsyncLock` only with careful operational planning
- VM workloads: guest agent / freeze integration when supported

Senior rule:

> Use CSI snapshots for fast storage-level recovery, but design application consistency separately. Storage snapshots alone do not replace database backup logic.

## 9. VolumeSnapshotClass deep dive

`VolumeSnapshotClass` is one of the most important objects for OADP CSI snapshots.

Example generic class:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-snapclass
  labels:
    velero.io/csi-volumesnapshot-class: "true"
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: <csi-driver-name>
deletionPolicy: Retain
parameters: {}
```

### 9.1 `driver`

This must match the CSI driver name of the volume.

Check the PV:

```bash
oc get pv <pv-name> -o jsonpath='{.spec.csi.driver}{"\n"}'
```

Common examples:

```text
ebs.csi.aws.com
pd.csi.storage.gke.io
disk.csi.azure.com
csi.vsphere.vmware.com
openshift-storage.rbd.csi.ceph.com
openshift-storage.cephfs.csi.ceph.com
```

Always verify in your cluster. Do not copy driver names blindly.

### 9.2 `deletionPolicy`

`deletionPolicy` controls what happens to the underlying storage snapshot when the `VolumeSnapshot`/`VolumeSnapshotContent` is deleted.

| Policy | Meaning | Use case | Risk |
|---|---|---|---|
| `Delete` | Delete underlying snapshot when snapshot object is deleted | Short-lived snapshots, test/dev, automated cleanup | Accidental backup deletion can remove snapshot |
| `Retain` | Keep underlying snapshot even after Kubernetes snapshot object is deleted | Production retention, manual DR control | Orphaned snapshots can create storage cost/leak |

Production guidance:

- Use `Retain` when snapshot must survive accidental namespace or Velero cleanup.
- Use `Delete` when snapshot lifecycle is fully controlled by backup expiration and storage cost matters.
- Document storage-side cleanup for retained snapshots.

### 9.3 Velero/OADP class selection label

Velero/OADP can select a snapshot class using this label:

```yaml
metadata:
  labels:
    velero.io/csi-volumesnapshot-class: "true"
```

For each CSI driver, keep only one class with this label unless you intentionally override the class at Backup/PVC level.

### 9.4 Kubernetes default class annotation

```yaml
metadata:
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
```

Important rules:

- There should be only one default `VolumeSnapshotClass` per CSI driver.
- Multiple default classes for the same CSI driver cause snapshot creation ambiguity/failure.
- For some cross-cluster restore designs, avoid restoring a default class that conflicts with the destination cluster.

### 9.5 Per-backup snapshot class override

Use this when one backup must use a non-default class.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-backup-specific-snapclass
  namespace: openshift-adp
  annotations:
    velero.io/csi-volumesnapshot-class_ebs.csi.aws.com: gp3-retain-snapclass
spec:
  includedNamespaces:
  - app1
  storageLocation: default
  ttl: 720h0m0s
```

The annotation format is:

```text
velero.io/csi-volumesnapshot-class_<driver-name>: <VolumeSnapshotClass-name>
```

Use lowercase annotation keys.

### 9.6 Per-PVC snapshot class override

A PVC-level override has higher priority than backup-level selection.

```bash
oc annotate pvc data-postgres-0 \
  -n app1 \
  velero.io/csi-volumesnapshot-class=postgres-retain-snapclass
```

Use this when a namespace has multiple workloads requiring different snapshot classes.

## 10. OADP DPA examples

> Validate exact DPA schema with your installed OADP version using `oc explain dpa.spec --recursive` because fields evolve between OADP releases.

### 10.1 DPA with CSI snapshots and Data Mover

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  configuration:
    nodeAgent:
      enable: true
      uploaderType: kopia
    velero:
      defaultPlugins:
      - openshift
      - aws
      - csi
      featureFlags:
      - EnableCSI
      defaultSnapshotMoveData: true
      defaultVolumesToFSBackup: false
  backupLocations:
  - velero:
      provider: aws
      default: true
      credential:
        name: cloud-credentials
        key: cloud
      objectStorage:
        bucket: <bucket-name>
        prefix: velero
      config:
        region: <region>
        s3ForcePathStyle: "true"
        s3Url: <s3-compatible-url>
```

Explanation:

- `openshift` plugin backs up OpenShift-specific resources.
- `csi` plugin enables CSI snapshot integration.
- `nodeAgent.enable: true` is required for Data Mover/FSB workflows.
- `uploaderType: kopia` is preferred for modern OADP; CSI Data Mover uses Kopia even if another value exists in some versions.
- `defaultSnapshotMoveData: true` makes CSI snapshot data movement the default behavior for backups unless overridden.
- `defaultVolumesToFSBackup: false` means volumes are not defaulted to FSB; they use snapshot/Data Mover path unless annotated otherwise.

### 10.2 DPA for plain CSI snapshots only

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-csi-only
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
      - openshift
      - aws
      - csi
      featureFlags:
      - EnableCSI
  backupLocations:
  - velero:
      provider: aws
      default: true
      credential:
        name: cloud-credentials
        key: cloud
      objectStorage:
        bucket: <bucket-name>
        prefix: velero
      config:
        region: <region>
```

This creates CSI snapshots but does not move snapshot data into object storage unless backup-level or DPA-level Data Mover settings are enabled.

## 15. How OADP chooses backup method for PVCs

OADP/Velero decides how to protect a volume based on:

1. Is the PVC backed by a CSI driver?
2. Does a matching `VolumeSnapshotClass` exist?
3. Is the CSI plugin enabled?
4. Is `snapshotMoveData` enabled?
5. Is File System Backup enabled by default?
6. Are pod/PVC annotations forcing or excluding FSB?
7. Are specific snapshot class annotations present?

Typical outcomes:

| Conditions | Result |
|---|---|
| CSI plugin enabled, matching VSC exists, `snapshotMoveData: false` | Plain CSI snapshot |
| CSI plugin enabled, matching VSC exists, `snapshotMoveData: true`, node agent enabled | CSI Data Mover |
| No snapshot-capable CSI driver, FSB enabled | File System Backup |
| No snapshot-capable CSI driver, FSB disabled | PV data may not be backed up |
| Multiple default VSCs for same driver | Snapshot creation can fail |
| Wrong VSC driver | Snapshot cannot bind/create |

## 16. Backup flow — plain CSI snapshot

Detailed flow:

1. Admin creates `Backup` CR.
2. Velero processes included namespaces/resources.
3. Velero finds PVCs selected by the backup.
4. Velero checks if the PV is CSI-backed.
5. Velero selects `VolumeSnapshotClass`.
6. Velero creates `VolumeSnapshot` in the PVC namespace.
7. Snapshot controller creates `VolumeSnapshotContent`.
8. CSI external-snapshotter calls CSI driver's `CreateSnapshot`.
9. Storage backend creates snapshot and returns snapshot handle.
10. `VolumeSnapshotContent.status.snapshotHandle` is populated.
11. `VolumeSnapshot.status.readyToUse` becomes true.
12. Velero stores Kubernetes resource metadata in backup object storage.
13. Backend snapshot remains in the storage system based on lifecycle behavior.

Important:

- Object storage contains Kubernetes resource backup metadata.
- Plain CSI snapshot data remains in the storage backend.
- Backup deletion behavior depends on Velero logic and snapshot deletion policy.

---

## 17. Backup flow — CSI Data Mover

Detailed flow:

1. Admin creates `Backup` CR with `snapshotMoveData: true` or DPA has `defaultSnapshotMoveData: true`.
2. Velero creates CSI snapshot as usual.
3. OADP/Velero creates a `DataUpload` object for each snapshot.
4. Node agent/data mover pod reads snapshot data.
5. Data is written to the Kopia backup repository in object storage.
6. `BackupRepository` manages repository lifecycle, commonly per namespace.
7. DataUpload status reports progress/completion/failure.
8. Backup completes after metadata and data movement finish.
9. The temporary CSI snapshot can be cleaned up after successful data movement depending on implementation/lifecycle.

Monitor:

```bash
oc get datauploads -A
oc describe dataupload -n <namespace> <name>
oc get backuprepositories -A
oc get pods -n openshift-adp -o wide
velero backup describe <backup-name> --details
velero backup logs <backup-name>
```

## 18. Restore flow — plain CSI snapshot

Plain CSI restore requires the destination cluster/storage to access the backend snapshot.

Flow:

1. Admin creates `Restore` CR.
2. Velero restores Kubernetes objects.
3. Velero recreates `VolumeSnapshot`/`VolumeSnapshotContent` metadata as needed.
4. A restored PVC is created using the snapshot as source.
5. CSI driver provisions a new volume from snapshot.
6. Pods mount restored PVCs.

Critical requirements:

- Destination cluster must have compatible CSI driver.
- Driver name should match for cross-cluster restore.
- Snapshot handle must be valid/reachable from destination.
- StorageClass must exist or be mapped.
- AccessModes and volumeMode must be compatible.

---

## 19. Restore flow — CSI Data Mover

Data Mover restore uses object storage data instead of relying only on backend snapshot accessibility.

Flow:

1. Admin creates `Restore` CR.
2. Velero restores Kubernetes resources.
3. PVC is created on target cluster/storage.
4. OADP/Velero creates `DataDownload` object.
5. Node agent/data mover pod restores data from Kopia repository to target volume.
6. Restore completes after data and metadata are restored.
7. Application pods start or are recreated with restored PVCs.

Monitor:

```bash
oc get datadownloads -A
oc describe datadownload -n <namespace> <name>
oc get restore -n openshift-adp
velero restore describe <restore-name> --details
velero restore logs <restore-name>
```

## 20. Production design patterns

### 20.1 Same-cluster accidental deletion recovery

Use:

- Plain CSI snapshots
- `Retain` deletion policy
- Short to medium TTL
- Namespace-level backup

Good for:

- Deleted PVC
- Deleted namespace
- Failed rollout
- Accidental config deletion

Not enough for:

- Full storage backend loss
- Region loss
- Cluster destroyed with local snapshots inaccessible

### 20.2 Cluster disaster recovery

Use:

- CSI Data Mover to object storage
- Object storage replication/versioning
- Tested restore to standby cluster
- StorageClass mapping
- Application consistency hooks

Good for:

- Cluster deletion
- Storage backend failure
- Region or site failure, if object storage is remote/replicated

### 20.3 Database-heavy workloads

Use:

- App-native database backups for logical recovery
- CSI snapshots for fast restore points
- Backup hooks or DB quiesce scripts
- WAL/binlog/archive logs to object storage
- Restore drills with point-in-time recovery

Do not rely only on crash-consistent storage snapshots for high-value database recovery.

### 20.4 OpenShift Virtualization workloads

Use:

- CSI backups or CSI backups with Data Mover
- VM freeze/quiesce support where available
- Validate disk volumeMode: usually `Block`
- Validate Data Mover support for block volumes
- Avoid FSB for VM disks; it is generally not the right model for block-mode VM disks

## 22. Troubleshooting guide

### Problem 1: Backup is `PartiallyFailed`

Check:

```bash
oc describe backup <backup> -n openshift-adp
velero backup logs <backup>
oc get volumesnapshot -A
oc get datauploads -A
```

Common causes:

- Missing `VolumeSnapshotClass`
- Wrong CSI driver in VSC
- Multiple default VSCs for same driver
- CSI snapshot timeout
- DataUpload failed due to object storage/auth/network
- Application namespace contains unsupported resources/operators
- PVC uses non-CSI storage

Fix:

- Correct VSC driver/label/default annotation.
- Increase `csiSnapshotTimeout` and `itemOperationTimeout`.
- Fix BSL credentials/connectivity.
- Test manual `VolumeSnapshot`.
- Exclude resources that should not be backed up.

### Problem 2: `VolumeSnapshot` not ready

Check:

```bash
oc describe volumesnapshot <snapshot> -n <namespace>
oc describe volumesnapshotcontent <content-name>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common causes:

- CSI driver does not support snapshots.
- External snapshotter sidecar is missing/broken.
- Storage backend snapshot API failed.
- Source PVC is invalid or not bound.
- SnapshotClass has wrong parameters/secrets.

Fix:

- Validate CSI driver docs.
- Check CSI controller logs.
- Verify snapshotter secrets and RBAC.
- Try a manual snapshot outside OADP.

### Problem 3: No `VolumeSnapshotClass` found for PVC

Check the PV driver:

```bash
PV=$(oc get pvc <pvc> -n <ns> -o jsonpath='{.spec.volumeName}')
oc get pv "$PV" -o jsonpath='{.spec.csi.driver}{"\n"}'
oc get volumesnapshotclass -o yaml
```

Fix:

- Create a VSC using the exact driver name.
- Add `velero.io/csi-volumesnapshot-class: "true"` label.
- Use backup/PVC annotation override if multiple classes exist.

### Problem 4: Multiple default snapshot classes

Symptom:

- Snapshot creation fails because Kubernetes cannot choose a class.

Check:

```bash
oc get volumesnapshotclass -o json | jq -r '.items[] | select(.metadata.annotations["snapshot.storage.kubernetes.io/is-default-class"]=="true") | [.metadata.name,.driver] | @tsv'
```

Fix:

```bash
oc annotate volumesnapshotclass <wrong-default> snapshot.storage.kubernetes.io/is-default-class- --overwrite
```

Then keep only one default per CSI driver.

### Problem 5: Restore PVC stays Pending

Check:

```bash
oc describe pvc <pvc> -n <namespace>
oc get storageclass
oc get volumesnapshot -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Common causes:

- StorageClass missing on destination.
- Snapshot cannot be accessed from destination.
- CSI driver name differs between clusters.
- PVC requested smaller size than snapshot source.
- Volume mode mismatch: `Filesystem` vs `Block`.

Fix:

- Create destination StorageClass with same name or use storage class mapping.
- Use Data Mover for cross-storage restore.
- Ensure size >= source snapshot size.
- Match volumeMode and accessModes.

### Problem 6: DataUpload stuck or failed

Check:

```bash
oc get datauploads -A
oc describe dataupload -n <namespace> <name>
oc get pods -n openshift-adp -o wide
oc logs -n openshift-adp <node-agent-or-data-mover-pod>
oc describe backuprepository -n <namespace> <name>
```

Common causes:

- Node agent not enabled.
- Data mover pod cannot schedule.
- Insufficient CPU/memory.
- Object storage credentials invalid.
- S3 endpoint/TLS/CA issue.
- NetworkPolicy/firewall blocks object storage.
- Kopia repository password changed after repository creation.

Fix:

- Enable `nodeAgent` in DPA.
- Add node selectors/tolerations/resources if needed.
- Fix BSL and secret.
- Validate S3 endpoint from inside cluster.
- Avoid changing repository password after first backup unless you are intentionally creating a new repository strategy.

### Problem 7: Backup fast but restore impossible after cluster loss

Root cause:

- You used plain CSI snapshots. Snapshot data stayed in the failed storage backend or same failure domain.

Fix:

- Use CSI Data Mover or FSB for off-cluster backup.
- Replicate object storage to another site/region.
- Test full cluster-loss restore scenario.

### Problem 8: Orphaned VolumeSnapshotContent objects

Check:

```bash
oc get volumesnapshotcontent
oc describe volumesnapshotcontent <name>
```

Risk:

- Storage snapshots retained forever.
- Cost grows silently.

Fix cautiously:

```bash
oc delete volumesnapshotcontent <name>
```

Before deletion, confirm whether `deletionPolicy` is `Delete` or `Retain`. If `Delete`, deleting the object can delete the underlying storage snapshot.

## 23. Security and compliance considerations

### 23.1 RBAC

Only trusted administrators should manage:

- `VolumeSnapshotClass`
- `VolumeSnapshotContent`
- OADP DPA
- Backup/Restore CRs
- Cloud/object storage credentials

Namespace users might create `VolumeSnapshot` objects if RBAC allows it. Review permissions carefully in regulated environments.

### 23.2 Encryption

Protect these layers:

- Source PV encryption at rest
- Storage backend snapshot encryption
- Object storage encryption for Data Mover/FSB
- Kopia repository encryption/password
- TLS to S3 endpoint
- KMS secrets if using ODF encrypted volumes or cloud KMS

### 23.3 Secrets

OADP needs credentials for backup storage and sometimes snapshot/storage APIs.

Best practices:

- Use least privilege IAM.
- Separate backup and snapshot credentials when required.
- Rotate credentials with tested backup/restore validation.
- Avoid storing broad cloud admin keys.
- Protect `openshift-adp` namespace with strict RBAC.

### 23.4 Retention and legal hold

Decide retention at multiple layers:

- Velero Backup TTL
- Object storage lifecycle/versioning
- Storage snapshot lifecycle
- Kopia repository maintenance
- Compliance/legal hold policies

A Velero TTL does not always equal storage snapshot deletion if `Retain` policy or external lifecycle policies are involved.

## 24. Performance tuning

### 24.1 Snapshot creation time

Factors:

- Storage backend API performance
- Number of PVCs
- CSI driver concurrency
- Snapshot class parameters
- Application write rate
- Cloud API rate limits

Tune:

```yaml
spec:
  csiSnapshotTimeout: 20m0s
  itemOperationTimeout: 4h0m0s
```

### 24.2 Data Mover throughput

Factors:

- Node-agent resources
- Object storage bandwidth/latency
- Snapshot size and changed blocks
- Number of parallel backups
- Kopia repository performance
- NetworkPolicy/firewall/proxy

Actions:

- Schedule backups outside peak I/O periods.
- Allocate CPU/memory to node-agent/data mover pods.
- Use high-performance object storage endpoint inside/near the cluster.
- Monitor DataUpload duration and bytes transferred.
- Use incremental backup where supported.
- Avoid running many large PVC backups simultaneously without capacity planning.

### 24.3 Application performance during backup

Plain snapshots are usually lightweight, but they can still cause:

- Short storage I/O latency spikes
- Backend snapshot metadata overhead
- Copy-on-write amplification
- Database checkpoint pressure

Data Mover adds:

- Read I/O from snapshots or volumes
- Network egress to object storage
- CPU usage for compression/encryption/hashing

Plan backup windows accordingly.

| Requirement | Recommended method |
|---|---|
| Fast rollback in same cluster | Plain CSI snapshot |
| Namespace/app accidental deletion recovery | CSI snapshot + OADP metadata backup |
| Full cluster disaster recovery | CSI Data Mover or FSB to remote object storage |
| Cross-cluster migration with same CSI driver/storage access | Plain CSI snapshot may work, but validate |
| Cross-provider restore | CSI Data Mover or FSB with storage class mapping |
| NFS/EFS/non-snapshot volumes | FSB |
| OpenShift Virtualization block disks | CSI snapshot or CSI Data Mover |
| High-value database PITR | DB-native backup + WAL/binlog + optional CSI snapshot |
| Long retention/low cost | Data Mover/FSB to object storage with lifecycle policies |

## 28. Interview-style explanation

### Question: What are CSI volume snapshots in OADP?

CSI volume snapshots are Kubernetes snapshot API objects used by OADP/Velero to protect PVC-backed persistent volumes when the storage uses a CSI driver with snapshot support. OADP backs up Kubernetes metadata to object storage and asks the CSI snapshot controller/driver to create storage-side snapshots. If Data Mover is enabled, OADP also moves snapshot data to object storage using Kopia, which makes the backup more useful for disaster recovery.

### Question: What is the difference between VolumeSnapshot and VolumeSnapshotContent?

`VolumeSnapshot` is the namespace-scoped request. `VolumeSnapshotContent` is the cluster-scoped object that represents the actual storage snapshot and binds one-to-one with a `VolumeSnapshot`. The content object contains storage backend details such as the snapshot handle.

### Question: Why is VolumeSnapshotClass important?

It tells Kubernetes which CSI driver and snapshot parameters to use. OADP/Velero also uses labels/annotations on the class to select the correct snapshot class for a PVC. If the class is missing, has the wrong driver, or multiple defaults exist for the same driver, backups can fail.

### Question: Are CSI snapshots full backups?

Not always. Plain CSI snapshots are usually backend snapshots, not copies in the Velero bucket. They are excellent for fast restore but might not survive backend or cluster failure. For off-cluster backup, use CSI Data Mover or File System Backup.

### Question: How would you troubleshoot a failed CSI snapshot backup?

First check `Backup` status and Velero logs. Then check `VolumeSnapshot`, `VolumeSnapshotContent`, and events in the application namespace. Validate the PVC's PV CSI driver and ensure a matching `VolumeSnapshotClass` exists with the correct Velero label. Test a manual `VolumeSnapshot`. If using Data Mover, check `DataUpload`, `BackupRepository`, node-agent pods, object storage credentials, and network connectivity.

## 29. Common mistakes

1. Treating plain CSI snapshots as off-cluster DR backups.
2. Creating a `VolumeSnapshotClass` with the wrong CSI driver name.
3. Having multiple default VSCs for the same CSI driver.
4. Forgetting the `velero.io/csi-volumesnapshot-class: "true"` label.
5. Disabling node agent while expecting Data Mover to work.
6. Not testing manual CSI snapshots before OADP.
7. Restoring to a cluster without compatible StorageClass/CSI driver.
8. Ignoring app consistency for databases.
9. Setting `Retain` without snapshot cleanup governance.
10. Changing Kopia repository credentials after backups already exist.

## 30. Senior production recommendations

1. Always define backup goals as RPO/RTO and failure domain.
2. Use plain CSI snapshots for fast local recovery.
3. Use CSI Data Mover for off-cluster DR.
4. Use database-native backups for database correctness.
5. Perform quarterly restore drills, not just backup success checks.
6. Keep separate runbooks for same-cluster restore and full-cluster DR.
7. Monitor `Backup`, `Restore`, `DataUpload`, `DataDownload`, and object storage usage.
8. Document every snapshot class and its deletion policy.
9. Use labels/selectors to back up applications, not entire clusters blindly.
10. Never include Operators/cluster lifecycle components unless the Red Hat product documentation explicitly supports that workload backup pattern.
