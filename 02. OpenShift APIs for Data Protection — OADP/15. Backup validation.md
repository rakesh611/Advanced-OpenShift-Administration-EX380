## 1. What Backup Validation Means

Backup validation is the process of proving that an OADP backup is:

- **Created successfully** by Velero/OADP.
- **Stored correctly** in the configured backup storage location.
- **Complete** for the intended application scope.
- **Consistent** for stateful workloads.
- **Recoverable** through a restore operation.
- **Operationally useful** within the required RPO and RTO.

In production, backup validation must answer these questions:

| Question | Why It Matters |
|---|---|
| Did the backup job complete? | Confirms Velero finished the backup workflow. |
| Were there warnings or errors? | `Completed` with warnings may still hide important exclusions or hook issues. |
| Was the correct namespace selected? | Wrong namespace means the backup is useless. |
| Were PVCs/PVs protected? | Stateless backup is not enough for databases or persistent apps. |
| Was data captured by CSI snapshot or file-system backup? | The restore method depends on how the volume was protected. |
| Is the backup present in object storage? | Kubernetes CR status alone is not enough. |
| Can the backup be restored? | Restore test is the strongest validation. |
| Does the restored application actually work? | Kubernetes objects can restore successfully while the app is broken. |

### Important Principle

`Backup.status.phase=Completed` means the Velero backup workflow completed. It does **not** automatically prove:

- Application data is logically consistent.
- Database transactions were flushed.
- PVC data was captured correctly.
- External dependencies are recoverable.
- The restored application will pass business checks.

For a senior administrator, backup validation must be treated as a **multi-layer operational control**, not a single command output.

## 2. OADP Components Involved in Validation

OADP is based on Velero and uses Kubernetes custom resources to perform backup and restore operations.

Common OADP/Velero resources:

| Resource | Purpose | Validation Focus |
|---|---|---|
| `DataProtectionApplication` | Main OADP configuration | Must be reconciled and ready. |
| `BackupStorageLocation` | Object storage target for metadata and backup artifacts | Must be `Available`. |
| `VolumeSnapshotLocation` | Snapshot location for native/cloud snapshots | Must match provider and region. |
| `Backup` | One-time backup request | Must reach `Completed` or be investigated if `PartiallyFailed`/`Failed`. |
| `Schedule` | Recurring backup policy | Must create backups at expected time. |
| `Restore` | Restore request from backup | Must complete and recreate expected resources. |
| `BackupRepository` | File-system backup repository, usually Kopia/Restic backed | Must be ready for namespaces using file-system backup. |
| `PodVolumeBackup` | File-system backup operation for pod volume | Must complete for each intended pod volume. |
| `PodVolumeRestore` | File-system restore operation for pod volume | Must complete during restore. |
| `VolumeSnapshot` | CSI snapshot object | Must be `readyToUse=true`. |
| `VolumeSnapshotContent` | Backend snapshot binding | Must exist and be bound. |

### OADP Namespace

Most OADP/Velero resources are created in:

```bash
openshift-adp
```

Common commands:

```bash
oc get pods -n openshift-adp
oc get dpa -n openshift-adp
oc get backupstoragelocations.velero.io -n openshift-adp
oc get volumesnapshotlocations.velero.io -n openshift-adp
oc get backups.velero.io -n openshift-adp
oc get restores.velero.io -n openshift-adp
```

## 3. Validation Layers

A production-grade backup validation strategy has seven layers.

```text
Layer 1: OADP control-plane readiness
Layer 2: Storage location validation
Layer 3: Backup scope validation
Layer 4: Backup execution validation
Layer 5: Backup content validation
Layer 6: Persistent data validation
Layer 7: Restore and application validation
```

### Layer 1: OADP Control-Plane Readiness

Validate:

- OADP Operator is installed.
- `DataProtectionApplication` is reconciled.
- Velero deployment is running.
- Node-agent daemonset is running if file-system backup is used.
- Plugins are loaded correctly.

### Layer 2: Storage Location Validation

Validate:

- `BackupStorageLocation` is `Available`.
- `LAST VALIDATED` is recent.
- Object storage bucket is reachable.
- Credentials are correct.
- CA certificate configuration is correct for S3-compatible/self-signed endpoints.
- Bucket lifecycle policy does not delete active backups unexpectedly.

### Layer 3: Backup Scope Validation

Validate:

- Correct namespace is included.
- Correct resources are included/excluded.
- Label selectors match real objects.
- Cluster-scoped dependencies are handled.
- Operators and CRDs required by the app exist on the restore target.

### Layer 4: Backup Execution Validation

Validate:

- Backup phase.
- Errors.
- Warnings.
- Hook status.
- Item counts.
- Start and completion timestamps.
- Expiration/TTL.

### Layer 5: Backup Content Validation

Validate that expected resources were captured:

- Deployments.
- StatefulSets.
- Services.
- Routes.
- ConfigMaps.
- Secrets.
- ServiceAccounts.
- RoleBindings.
- PVCs.
- CRs used by Operators.
- NetworkPolicies.
- ImageStreams, where applicable.

### Layer 6: Persistent Data Validation

Validate:

- CSI snapshots exist and are ready.
- File-system backup objects exist and completed.
- Backup repositories are ready.
- PVCs are not skipped.
- Databases were quiesced or dumped before backup where needed.

### Layer 7: Restore and Application Validation

Validate:

- Restore completes.
- Objects are recreated.
- Pods become ready.
- PVCs bind.
- Routes work.
- Database queries succeed.
- Application health checks pass.
- Business transaction smoke test works.

## 4. Pre-Backup Validation

Pre-backup validation prevents bad backups from being created.

### 4.1 Validate OADP Operator and DPA

```bash
oc get csv -n openshift-adp
oc get dpa -n openshift-adp
oc describe dpa -n openshift-adp
```

Expected:

```text
RECONCILED=True
```

Example:

```bash
oc get dpa -n openshift-adp
```

Expected output:

```text
NAME         AGE   RECONCILED
my-dpa       20m   True
```

If DPA is not reconciled:

```bash
oc describe dpa <dpa-name> -n openshift-adp
oc get events -n openshift-adp --sort-by=.lastTimestamp
oc logs -n openshift-adp deploy/oadp-operator-controller-manager -c manager
```

Common causes:

- Wrong cloud credentials secret.
- Wrong bucket name.
- Wrong region.
- Missing plugin configuration.
- S3 endpoint/CA issue.
- Unsupported OADP/OpenShift version combination.

---

### 4.2 Validate Velero Pod

```bash
oc get deploy -n openshift-adp
oc get pods -n openshift-adp -o wide
oc logs -n openshift-adp deploy/velero
```

Expected:

```text
velero pod Running
READY 1/1
No repeated credential/storage/plugin errors
```

Useful checks:

```bash
oc describe pod -n openshift-adp -l component=velero
oc get events -n openshift-adp --sort-by=.lastTimestamp
```

Look for:

- `CrashLoopBackOff`
- `ImagePullBackOff`
- credential mount errors
- plugin init errors
- network timeouts to object storage
- CA trust errors

---

### 4.3 Validate Node-Agent for Kopia/Restic File-System Backup

OADP uses a node-level component when file-system backup is enabled. In newer OADP versions, this is commonly called **node-agent**. It handles file-system backup/restore operations for pod volumes.

```bash
oc get ds -n openshift-adp
oc get pods -n openshift-adp -o wide | grep -i node
```

Expected:

```text
node-agent pods running on worker nodes where protected workloads run
```

Check logs:

```bash
oc logs -n openshift-adp ds/node-agent
```

If node-agent is not running on the node that hosts the pod volume, file-system backup may fail or remain stuck.

---

### 4.4 Validate BackupStorageLocation

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
```

Expected:

```text
NAME            PHASE       LAST VALIDATED   AGE   DEFAULT
<name>          Available   <recent>         ...   true
```

Detailed check:

```bash
oc describe backupstoragelocation <bsl-name> -n openshift-adp
oc get backupstoragelocation <bsl-name> -n openshift-adp -o yaml
```

Validate:

- `status.phase: Available`
- `status.lastValidationTime` is recent
- correct provider
- correct bucket
- correct prefix
- correct region
- correct credential secret
- correct CA certificate configuration for custom S3

If BSL is `Unavailable`, do not trust backup success.

Common causes:

| Symptom | Possible Cause |
|---|---|
| BSL `Unavailable` | Object storage unreachable or credentials invalid. |
| TLS error | Missing custom CA or wrong S3 endpoint certificate. |
| Access denied | Wrong IAM/S3 policy. |
| Bucket not found | Wrong bucket or region. |
| Timeout | Network, proxy, firewall, DNS, or object storage endpoint issue. |

---

### 4.5 Validate VolumeSnapshotLocation

For snapshot-based PV backups:

```bash
oc get volumesnapshotlocations.velero.io -n openshift-adp
oc describe volumesnapshotlocation <vsl-name> -n openshift-adp
```

Validate:

- provider matches infrastructure
- region/zone is correct
- CSI snapshot support exists if using CSI
- snapshot class exists

Check CSI snapshot classes:

```bash
oc get volumesnapshotclass
oc describe volumesnapshotclass <class-name>
```

Validate storage classes used by PVCs:

```bash
oc get pvc -n <app-namespace>
oc get sc
```

Important: A PVC can exist and bind successfully, but backup may still skip its data if there is no supported snapshot method and file-system backup is not enabled.

### 4.6 Validate Application Inventory Before Backup

Create a resource inventory before backup. This becomes your comparison baseline for restore validation.

```bash
NS=<app-namespace>

oc get all -n $NS
oc get pvc -n $NS
oc get cm,secret,sa,role,rolebinding -n $NS
oc get route,ingress,networkpolicy -n $NS
oc get quota,limitrange -n $NS
oc get deploy,statefulset,daemonset,job,cronjob -n $NS
oc get hpa,pdb -n $NS
```

Export inventory:

```bash
mkdir -p /tmp/oadp-validation/$NS

oc get all -n $NS -o yaml > /tmp/oadp-validation/$NS/all.yaml
oc get pvc -n $NS -o yaml > /tmp/oadp-validation/$NS/pvc.yaml
oc get cm -n $NS -o yaml > /tmp/oadp-validation/$NS/configmaps.yaml
oc get secret -n $NS -o yaml > /tmp/oadp-validation/$NS/secrets.yaml
oc get route -n $NS -o yaml > /tmp/oadp-validation/$NS/routes.yaml
oc get networkpolicy -n $NS -o yaml > /tmp/oadp-validation/$NS/networkpolicy.yaml
oc get role,rolebinding -n $NS -o yaml > /tmp/oadp-validation/$NS/rbac.yaml
```

For CRD/operator-based applications:

```bash
oc api-resources --namespaced=true | grep -i <operator-or-app-name>
oc get <custom-resource-kind> -n $NS
```

Examples:

```bash
oc get postgresql -n $NS
oc get kafka -n $NS
oc get argocd -n $NS
oc get elasticsearch -n $NS
```

### 4.7 Validate Backup Scope Before Creating Backup

Example Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp
  storageLocation: default
  ttl: 720h0m0s
```

Before applying, validate namespace exists:

```bash
oc get ns myapp
```

Validate label selectors if used:

```bash
oc get all -n myapp --show-labels
oc get all -n myapp -l app=myapp
```

If your Backup CR uses:

```yaml
labelSelector:
  matchLabels:
    app: myapp
```

Then every object that must be protected must have the matching label. Many real failures happen because PVCs, Secrets, ConfigMaps, Routes, or ServiceAccounts do not carry the same application label.

## 5. Backup Execution Validation

### 5.1 Create Backup

```bash
oc apply -f backup.yaml
```

or with Velero CLI:

```bash
velero backup create app-backup-001 \
  --include-namespaces myapp \
  --storage-location default \
  --ttl 720h
```

---

### 5.2 Watch Backup Phase

```bash
oc get backups.velero.io -n openshift-adp -w
```

Check a specific backup:

```bash
oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.phase}{"\n"}'
```

Common phases:

| Phase | Meaning | Action |
|---|---|---|
| `New` | Backup object created but not yet processed | Wait or check controller. |
| `InProgress` | Backup is running | Monitor. |
| `WaitingForPluginOperations` | Waiting for async plugin operations | Check CSI/data mover operations. |
| `WaitingForPluginOperationsPartiallyFailed` | Some async operations failed | Investigate before trusting backup. |
| `Finalizing` | Velero is finalizing metadata/artifacts | Wait. |
| `FinalizingPartiallyFailed` | Finalizing but some operations failed | Investigate. |
| `Completed` | Backup completed | Continue deeper validation. |
| `PartiallyFailed` | Backup completed with some errors | Do not treat as production-valid until understood. |
| `Failed` | Backup failed | Not valid. |
| `Deleting` | Backup deletion in progress | Do not use. |

A senior administrator should treat `PartiallyFailed` as **not validated** until every warning/error is reviewed and documented.

---

### 5.3 Describe Backup

```bash
velero describe backup app-backup-001 --details -n openshift-adp
```

or:

```bash
oc describe backup app-backup-001 -n openshift-adp
```

Validate:

- Phase
- Namespaces included
- Resources included/excluded
- Label selector
- Storage location
- Snapshot volumes setting
- TTL
- Start time
- Completion time
- Expiration
- Errors
- Warnings
- Backup item count
- Volume snapshots
- File-system volume backups
- Hooks attempted/failed

Useful JSONPath commands:

```bash
oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.phase}{"\n"}'
oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.errors}{"\n"}'
oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.warnings}{"\n"}'
oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.startTimestamp}{"\n"}'
oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.completionTimestamp}{"\n"}'
oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.expiration}{"\n"}'
```

---

### 5.4 Get Backup Logs

```bash
velero backup logs app-backup-001 -n openshift-adp
```

or, depending on OADP CLI availability:

```bash
oc oadp backup logs app-backup-001 -n openshift-adp
```

Search for errors:

```bash
velero backup logs app-backup-001 -n openshift-adp | egrep -i "error|warn|failed|skip|timeout|denied|forbidden|snapshot|volume|secret|certificate|tls"
```

Important log patterns:

| Log Pattern | Meaning |
|---|---|
| `error getting backup item action` | Plugin issue. |
| `timed out waiting for snapshot` | Snapshot operation slow or broken. |
| `forbidden` | RBAC issue. |
| `access denied` | Object storage or cloud API permission issue. |
| `no volume ID returned` | Storage provider/CSI issue. |
| `pod volume backup failed` | Kopia/Restic/node-agent issue. |
| `x509: certificate signed by unknown authority` | Missing CA trust. |
| `resource not found` | Resource disappeared during backup or selector mismatch. |

---

### 5.5 Validate Backup Duration

Backup duration matters for RPO/RTO planning.

```bash
oc get backup app-backup-001 -n openshift-adp -o json | jq -r '.status.startTimestamp, .status.completionTimestamp'
```

Example manual calculation:

```bash
START=$(oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.startTimestamp}')
END=$(oc get backup app-backup-001 -n openshift-adp -o jsonpath='{.status.completionTimestamp}')
echo "Start: $START"
echo "End:   $END"
```

Validate against policy:

| Environment | Example Policy |
|---|---|
| Dev | Backup must complete within 60 minutes. |
| Staging | Backup must complete within 30 minutes. |
| Production | Backup must complete inside backup window and RPO requirement. |

## 6. Backup Content Validation

### 6.1 Validate Included Namespaces

```bash
velero describe backup app-backup-001 --details -n openshift-adp | grep -A10 "Namespaces"
```

or:

```bash
oc get backup app-backup-001 -n openshift-adp -o yaml | yq '.spec.includedNamespaces'
```

Expected:

```yaml
- myapp
```

If `includedNamespaces` is wrong, the backup is not valid for that application.

---

### 6.2 Validate Included and Excluded Resources

```bash
oc get backup app-backup-001 -n openshift-adp -o yaml | yq '.spec.includedResources'
oc get backup app-backup-001 -n openshift-adp -o yaml | yq '.spec.excludedResources'
```

Common mistake:

```yaml
excludedResources:
- secrets
```

This may break application restore because many workloads depend on Secrets for:

- database passwords
- TLS certificates
- image pull secrets
- OAuth/OIDC configuration
- application credentials

Use exclusion carefully.

---

### 6.3 Validate Label Selector Coverage

If backup uses label selectors:

```bash
oc get backup app-backup-001 -n openshift-adp -o yaml | yq '.spec.labelSelector'
```

Then test the same selector manually:

```bash
oc get all,pvc,cm,secret,sa,role,rolebinding,route,networkpolicy -n myapp -l app=myapp
```

If critical objects are missing from this output, they may be missing from backup.

Recommended approach for production:

- Prefer namespace-level backup for complete application protection.
- Use label selectors only when labels are governed and consistently applied.
- Validate selectors before every new backup policy rollout.

---

### 6.4 Validate Cluster-Scoped Dependencies

OADP is mainly used for application workload protection. Full cluster backup/restore is not the normal supported pattern. Applications may still depend on cluster-scoped objects.

Check dependencies:

```bash
oc get clusterrolebinding | grep -i myapp
oc get clusterrole | grep -i myapp
oc get crd | grep -i <app-or-operator>
oc get scc
oc get storageclass
oc get ingresscontroller -n openshift-ingress-operator
```

Cluster-scoped resources to think about:

| Dependency | Why It Matters |
|---|---|
| CRDs | Custom resources cannot restore if CRDs do not exist. |
| Operators | Operator-managed apps may need operator installed first. |
| StorageClasses | PVC restore depends on compatible storage class. |
| SCCs | Pods may fail after restore due to security restrictions. |
| ClusterRoles/ClusterRoleBindings | App service accounts may lose access. |
| IngressControllers | Routes may restore but not become reachable. |
| Image registry config | ImageStreams/internal images may need special handling. |

Validation action:

```bash
oc api-resources | grep -i <resource>
oc get crd <crd-name>
oc get operators -A
oc get csv -A
```

## 7. Persistent Volume Backup Validation

Persistent volume validation is the most important part of backup validation for stateful workloads.

OADP/Velero commonly protects volume data using:

1. **CSI snapshots / native snapshots**
2. **File-system backup using Kopia/Restic/node-agent**

The correct validation method depends on the selected data protection method.

---

### 7.1 Identify PVCs Used by the Application

```bash
NS=myapp
oc get pvc -n $NS
oc get pods -n $NS -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .spec.volumes[*]}{"  "}{.name}{" -> "}{.persistentVolumeClaim.claimName}{"\n"}{end}{end}'
```

Detailed PVC check:

```bash
oc describe pvc -n $NS
oc get pv
```

Validate:

- PVC name
- storage class
- access mode
- capacity
- bound PV
- volume mode
- app pod mount path

---

### 7.2 CSI Snapshot Validation

Check snapshot classes:

```bash
oc get volumesnapshotclass
```

Check snapshots after backup:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

Detailed snapshot validation:

```bash
oc describe volumesnapshot -n <namespace> <snapshot-name>
oc get volumesnapshot -n <namespace> <snapshot-name> -o yaml
```

Expected fields:

```yaml
status:
  readyToUse: true
  restoreSize: ...
  boundVolumeSnapshotContentName: ...
```

Validate `VolumeSnapshotContent`:

```bash
oc describe volumesnapshotcontent <content-name>
oc get volumesnapshotcontent <content-name> -o yaml
```

Expected:

- Snapshot content exists.
- It references correct snapshot handle.
- It is bound to the correct `VolumeSnapshot`.
- `readyToUse=true`.

Common CSI snapshot issues:

| Symptom | Cause | Fix |
|---|---|---|
| No `VolumeSnapshot` created | CSI snapshot not enabled or backup not configured for snapshots | Configure CSI plugin and snapshot class. |
| Snapshot stuck not ready | Storage backend problem | Check CSI controller logs. |
| Timeout waiting for snapshot | Snapshot creation is slow or backend overloaded | Increase timeout/tune storage. |
| Wrong snapshot class | Missing/default class issue | Configure correct `VolumeSnapshotClass`. |
| Restore PVC stuck Pending | Storage class mismatch or snapshot restore unsupported | Validate target cluster storage. |

---

### 7.3 File-System Backup Validation with Kopia/Restic

File-system backup protects files inside pod volumes. This is useful when:

- CSI snapshot is unavailable.
- You need file-level backup.
- Cloud/native snapshot is not supported.
- You use S3-compatible storage without backend snapshots.

Check backup repositories:

```bash
oc get backuprepositories.velero.io -n openshift-adp
oc describe backuprepository -n openshift-adp <repo-name>
```

Check PodVolumeBackup objects:

```bash
oc get podvolumebackups.velero.io -n openshift-adp
oc describe podvolumebackup -n openshift-adp <pvb-name>
```

Expected:

```text
Phase: Completed
```

Useful command:

```bash
oc get podvolumebackups.velero.io -n openshift-adp \
  -o custom-columns=NAME:.metadata.name,PHASE:.status.phase,NAMESPACE:.spec.pod.namespace,POD:.spec.pod.name,VOLUME:.spec.volume
```

If `PodVolumeBackup` is failed:

```bash
oc describe podvolumebackup <name> -n openshift-adp
oc logs -n openshift-adp ds/node-agent
oc logs -n openshift-adp deploy/velero
```

Common file-system backup issues:

| Symptom | Cause | Fix |
|---|---|---|
| No `PodVolumeBackup` objects | File-system backup not enabled or pod not annotated | Use `defaultVolumesToFsBackup: true` or pod annotations. |
| PVB stuck `InProgress` | node-agent issue | Check node-agent pod on the workload node. |
| PVB failed permission denied | Volume file permissions | Review SCC, container UID, and node-agent access. |
| Repository not ready | Kopia/Restic repository issue | Check `BackupRepository` and credentials. |
| Very slow backup | Large volume or small node-agent CPU/memory | Tune node-agent resources and concurrency. |

---

### 7.4 Validate Backup Method Used for Each PVC

For each PVC, determine whether it was protected by snapshot or file-system backup.

```bash
velero describe backup app-backup-001 --details -n openshift-adp
```

Look for sections like:

```text
Velero-Native Snapshots
CSI Snapshots
Pod Volume Backups
```

Validation checklist:

| PVC | Expected Method | Evidence | Valid? |
|---|---|---|---|
| `mysql-data` | CSI snapshot | `VolumeSnapshot readyToUse=true` | Yes/No |
| `uploads-data` | File-system backup | `PodVolumeBackup Completed` | Yes/No |
| `redis-data` | Snapshot or FSB | Evidence exists | Yes/No |

If a PVC has no snapshot and no file-system backup evidence, the backup is not valid for persistent data.

---

### 7.5 Validate PV Capacity and Restore Compatibility

Before restore, validate PV/PVC capacity:

```bash
oc get pvc -n myapp -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,SC:.spec.storageClassName,REQ:.spec.resources.requests.storage,VOLUME:.spec.volumeName
```

On target cluster, validate storage class compatibility:

```bash
oc get sc
oc describe sc <storage-class>
```

Important restore issue:

- If the target storage class cannot provision the requested PVC size, restore may create PVCs that remain `Pending`.
- If the original storage class does not exist on the target cluster, PVC restore may fail or remain unbound.
- If snapshot restore requires a `VolumeSnapshotClass`, it must exist and match the CSI driver.

## 8. Application Consistency Validation

A Kubernetes backup can be technically successful but application-inconsistent.

### 8.1 Stateless Applications

For stateless apps, validation focuses on:

- Deployments restored.
- Services restored.
- Routes restored.
- ConfigMaps/Secrets restored.
- Pods become Ready.
- Application endpoint returns expected response.

Example:

```bash
oc get deploy,svc,route,pods -n myapp
curl -k https://$(oc get route myapp -n myapp -o jsonpath='{.spec.host}')/health
```

---

### 8.2 Stateful Applications

For stateful workloads, application consistency is critical.

Examples:

| Application | Recommended Consistency Strategy |
|---|---|
| PostgreSQL | Use database dump, WAL archiving, or pre/post hooks. |
| MySQL/MariaDB | Use `mysqldump`, `FLUSH TABLES WITH READ LOCK`, or app-aware operator backup. |
| MongoDB | Use replica-set-aware backup or filesystem snapshot with quiesce. |
| Kafka | Prefer app/operator-level backup and topic/offset validation. |
| Elasticsearch | Prefer snapshot repository mechanism. |
| GitLab/Harbor | Use vendor/operator backup process where possible. |

### 8.3 Backup Hooks

Backup hooks can run commands before or after backup actions.

Example concept:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: mysql-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
  - mysql-prod
  hooks:
    resources:
    - name: mysql-quiesce
      includedNamespaces:
      - mysql-prod
      labelSelector:
        matchLabels:
          app: mysql
      pre:
      - exec:
          container: mysql
          command:
          - /bin/bash
          - -c
          - "mysql -uroot -p$MYSQL_ROOT_PASSWORD -e 'FLUSH TABLES WITH READ LOCK;'"
          onError: Fail
          timeout: 30s
      post:
      - exec:
          container: mysql
          command:
          - /bin/bash
          - -c
          - "mysql -uroot -p$MYSQL_ROOT_PASSWORD -e 'UNLOCK TABLES;'"
          onError: Continue
          timeout: 30s
```

Validation:

```bash
velero describe backup mysql-backup --details -n openshift-adp
velero backup logs mysql-backup -n openshift-adp | grep -i hook
```

Check:

- hooks attempted
- hooks failed
- timeout
- command errors
- backup phase after hook failure

Important: A hook that fails with `onError: Continue` may allow the backup to proceed but leave application consistency questionable.

## 9. Object Storage Validation

OADP backups are stored in object storage. Kubernetes CR status is not enough; validate the backend.

### 9.1 Validate Backup Exists in Object Storage

For S3-compatible storage, typical object layout includes backup metadata and artifacts under a prefix such as:

```text

```

Use your object storage CLI.

AWS S3 example:

```bash
aws s3 ls s3://<bucket>/<prefix>/backups/app-backup-001/ --recursive
```

S3-compatible endpoint example:

```bash
aws --endpoint-url https://<s3-endpoint> \
  s3 ls s3://<bucket>/<prefix>/backups/app-backup-001/ --recursive
```

Expected backup artifacts may include:

```text
backup.json
backup.tar.gz
backup-volume-snapshots.json.gz
podvolumebackups.json.gz
resource-list.json.gz
logs.gz
```

Exact files vary by Velero/OADP version and backup method.

### 9.2 Validate Object Storage Access from Cluster


Inside pod:

```bash
curl -vk https://<s3-endpoint>
```

Validate:

- DNS resolution
- TCP connectivity
- TLS handshake
- proxy configuration
- firewall rules

### 9.3 Validate Bucket Lifecycle and Retention

Check:

- Versioning settings are documented.

## 10. Schedule Backup Validation

Schedules automate recurring backups. A Schedule CR is valid only when it creates successful backup objects at the expected time.

### 10.1 Check Schedule CR

```bash
oc get schedule -n openshift-adp
oc describe schedule <schedule-name> -n openshift-adp
```

Example Schedule:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: myapp-daily
  namespace: openshift-adp
spec:
  schedule: "0 2 * * *"
  template:
    includedNamespaces:
    - myapp
    storageLocation: default
    ttl: 168h0m0s
```

Validate:

- cron expression
- timezone expectations
- included namespace
- storage location
- TTL
- snapshot/file-system settings
- last backup status

---

### 10.2 Validate Backup Created by Schedule

```bash
oc get backups.velero.io -n openshift-adp --sort-by=.metadata.creationTimestamp
```

Filter schedule backups:

```bash
oc get backups.velero.io -n openshift-adp | grep myapp-daily
```

Describe latest:

```bash
LATEST=$(oc get backups.velero.io -n openshift-adp \
  --sort-by=.metadata.creationTimestamp \
  -o jsonpath='{.items[-1:].metadata.name}')

echo $LATEST
velero describe backup $LATEST --details -n openshift-adp
```

---

### 10.3 Validate Schedule Does Not Overlap

If a backup runs longer than the schedule interval, backups may overlap or queue. This causes performance and consistency problems.

Check backup duration:

```bash
oc get backups.velero.io -n openshift-adp \
  -o custom-columns=NAME:.metadata.name,PHASE:.status.phase,START:.status.startTimestamp,END:.status.completionTimestamp
```

Policy example:

| Schedule | Expected Max Duration | Action if Exceeded |
|---|---|---|
| Every 1 hour | 30 minutes | Tune backup or reduce scope. |
| Daily 2 AM | Before 5 AM | Tune performance or split workloads. |
| Weekly full backup | Before business start | Increase node-agent resources or snapshot performance. |

## 11. Restore-Based Validation

Restore testing is the strongest validation. A backup is not fully trusted until it has been restored successfully.

### 11.1 Restore Validation Options

| Restore Type | Purpose | Frequency |
|---|---|---|
| Metadata preview/describe | Quick check of resources | Every backup. |
| Restore to test namespace | Validate object recovery | Daily/weekly. |
| Restore to isolated test cluster | Validate DR readiness | Monthly/quarterly. |
| Full application functional test | Validate business recovery | Critical apps: scheduled. |

---

### 11.2 Preview Backup and Restore Resources

Use:

```bash
velero describe backup <backup-name> --details -n openshift-adp
```

Then create a restore to a test namespace when possible.

Important: A Velero restore operation creates resources in the cluster. Do not run a restore casually in production namespaces unless planned.

---

### 11.3 Restore to Same Namespace

Example Restore CR:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-myapp-same-ns
  namespace: openshift-adp
spec:
  backupName: app-backup-001

  - myapp

```

Apply:

```bash
oc apply -f restore.yaml
```

Validate:

```bash

```

Use same-namespace restore carefully because existing resources may conflict.

### 11.4 Restore to Different Namespace

## 14. Advanced Troubleshooting

### 14.1 Backup is `Failed`

Check:

```bash
oc describe backup <backup> -n openshift-adp
velero backup logs <backup> -n openshift-adp
oc logs -n openshift-adp deploy/velero
oc get events -n openshift-adp --sort-by=.lastTimestamp
```

Common causes:

| Cause | Evidence | Fix |
|---|---|---|
| BSL unavailable | BSL status unavailable | Fix object storage endpoint/credentials. |
| Permission issue | `forbidden`, `access denied` | Fix RBAC/IAM policy. |
| Snapshot timeout | snapshot timeout logs | Check CSI backend, increase timeout if needed. |
| Plugin issue | plugin error logs | Validate plugin config and OADP version. |
| Hook failure | hook error logs | Fix command, container name, timeout, or `onError`. |

---

### 14.2 Backup is `PartiallyFailed`

Do not ignore `PartiallyFailed`.

Checklist:

```bash
velero describe backup <backup> --details -n openshift-adp
velero backup logs <backup> -n openshift-adp | egrep -i "error|failed|warn"
oc get podvolumebackups -n openshift-adp
oc get volumesnapshot -A
```

Decision:

| Failure Type | Can Backup Be Accepted? |
|---|---|
| Non-critical event object failed | Maybe, document exception. |
| PVC backup failed | No. |
| Secret missing | Usually no. |
| Hook failed for database | No unless app consistency is otherwise guaranteed. |
| Route conflict warning | Maybe if restore plan handles route patching. |
| Deprecated API warning | Maybe, but fix before future upgrades. |

---

### 14.3 BSL Unavailable

```bash
oc describe backupstoragelocation <bsl> -n openshift-adp
oc logs -n openshift-adp deploy/velero | grep -i backupstoragelocation
```

Check object storage access:

```bash
oc run curl-test -n openshift-adp --rm -it --image=registry.access.redhat.com/ubi9/ubi -- bash
curl -vk https://<s3-endpoint>
```

Common fixes:

- Correct bucket name.
- Correct region.
- Correct endpoint URL.
- Correct IAM/S3 policy.
- Add custom CA certificate.
- Fix proxy/no-proxy settings.
- Check firewall and DNS.

---

### 14.4 PVC Data Not Backed Up

Symptoms:

- Backup completes but restored PVC is empty.
- No `VolumeSnapshot` exists.
- No `PodVolumeBackup` exists.

Check:

```bash
velero describe backup <backup> --details -n openshift-adp
oc get podvolumebackups -n openshift-adp
oc get volumesnapshot -A
```

Fix options:

- Configure CSI snapshot support.
- Configure `VolumeSnapshotClass`.
- Enable file-system backup.
- Add pod annotations for FSB if opt-in mode is used.
- Use `defaultVolumesToFsBackup: true` where appropriate.

Example pod annotation for file-system backup:

```yaml
metadata:
  annotations:
    backup.velero.io/backup-volumes: data
```

---

### 14.5 Restore Completed But Pods Not Running

Check:

```bash
oc get pods -n <restore-ns>
oc describe pod -n <restore-ns> <pod>
oc get events -n <restore-ns> --sort-by=.lastTimestamp
```

Common causes:

| Symptom | Cause | Fix |
|---|---|---|
| `ImagePullBackOff` | image pull secret/internal image missing | Restore image secret or mirror image. |
| `CrashLoopBackOff` | config/data mismatch | Check logs and ConfigMaps/Secrets. |
| `CreateContainerConfigError` | missing secret/configmap | Validate backup scope. |
| `Forbidden` SCC | service account lacks SCC | Reapply SCC/RBAC. |
| PVC Pending | storage class missing | Create compatible SC or patch PVC. |
| Route conflict | same hostname exists | Patch route hostname. |

---

### 14.6 Restore Completed But App Fails

Kubernetes restore success does not equal application success.

Check:

```bash
oc logs -n <restore-ns> deploy/<app>
oc exec -n <restore-ns> <pod> -- env
oc exec -n <restore-ns> <pod> -- ls -lah /data
curl -k https://<route>/health
```

Common root causes:

- Database inconsistent.
- App expects external service not available in test namespace.
- Route hostname conflict.
- Secrets not restored.
- NetworkPolicy blocks traffic.
- SCC/RBAC changed.
- Operator not installed on target cluster.
- CRD version mismatch.

## 17. Interview and Real-World Notes

### 17.1 What Interviewers Expect

For a senior OpenShift/OADP administrator, a good answer should include:

- Backup phase validation.
- BSL validation.
- Restore test validation.
- PV/PVC data validation.
- CSI snapshot vs Kopia/Restic difference.
- Application consistency using hooks or app-native backup.
- Object storage validation.
- Warning/error review.
- RPO/RTO measurement.

### 17.2 Strong Interview Answer

> In OADP, I do not validate a backup only by checking `Backup.status.phase=Completed`. I first validate the DPA and Velero pods, then confirm the `BackupStorageLocation` is `Available`. After backup completion, I inspect `velero describe backup --details` and backup logs for warnings, errors, skipped resources, hooks, and volume backup status. For PVCs, I verify either CSI `VolumeSnapshot` objects are ready or `PodVolumeBackup` objects completed for file-system backups. Finally, I run a restore test to a different namespace or DR cluster, validate restored objects, PVC binding, pod readiness, route access, and application-level data checks. Only after restore and functional validation do I consider the backup production-valid.

### 17.3 Common Production Mistakes

| Mistake | Impact |
|---|---|
| Trusting `Completed` only | Hidden missing data or warnings. |
| Not validating PVC data | Restored app has empty volumes. |
| Not testing restore | Backup may be unusable during incident. |
| Ignoring `PartiallyFailed` | Critical objects may be missing. |
| Not checking object storage | Backup CR exists but artifacts missing or expired. |
| Using label selectors without label governance | Secrets/PVCs/Routes skipped. |
| No app consistency hooks | Database restored in corrupted or inconsistent state. |
| No DR cluster test | Restore fails due to missing storage class/CRDs/operators. |

# Final Summary

Backup validation in OADP is a complete operational process. It starts before the backup with DPA, Velero, BSL, VSL, namespace, and PVC checks. It continues during backup by validating phase, logs, warnings, errors, hooks, snapshots, and file-system backup objects. It is completed only when the backup is restored and the application passes functional and data validation.

For production, use this rule:

```text
No restore test = no proven backup.
```
