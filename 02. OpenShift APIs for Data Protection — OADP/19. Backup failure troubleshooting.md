# Backup Failure Troubleshooting in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift Administrator / OpenShift Platform Engineer / SRE with 10+ years of Linux, Kubernetes, OpenShift, storage, and operations experience.  
**Scope:** Troubleshooting failed, partially failed, stuck, incomplete, or unreliable **backup** operations in **OpenShift APIs for Data Protection (OADP)**, which is Red Hat's OpenShift operator-based distribution around Velero and OpenShift backup plugins.  
**Default namespace used in examples:** `openshift-adp`  
**Primary Velero deployment name used in examples:** `velero`

---

## 1. What “backup failure troubleshooting” means in OADP

Backup failure troubleshooting is the disciplined process of identifying **where the OADP backup pipeline broke**, proving the root cause from cluster evidence, fixing the failing layer, and validating that a new backup is restorable.

In production OpenShift, a failed backup is not always obvious. A backup can be:

- **Failed**: Velero could not complete the backup operation.
- **PartiallyFailed**: some resources or volumes failed, but the backup object was still written.
- **Completed with warnings**: backup completed, but there are warnings that might affect restore quality.
- **InProgress forever**: controller, plugin, snapshot, data mover, or repository operation got interrupted or stuck.
- **Completed but useless**: Kubernetes YAML was captured, but PV data, images, secrets, hooks, or critical CRDs were not captured correctly.
- **Schedule appears healthy but recent backups are absent**: schedule, controller, storage, or validation issue is preventing new backup creation.

A senior administrator must treat backup troubleshooting as **data-protection incident handling**, not only as `oc get backup` output checking. The real question is:

> “Can I restore this application with acceptable RPO/RTO and data consistency?”

## 2. OADP backup pipeline mental model

Before troubleshooting, understand the moving parts.

```text
User / Schedule
     |
     v
Backup CR  ---> Velero controller in openshift-adp
     |              |
     |              +--> Kubernetes API discovery and resource collection
     |              +--> OpenShift plugin actions: routes, imagestreams, internal images, SCC-related metadata, etc.
     |              +--> BackupStorageLocation plugin: S3/Azure/GCP/MCG/ODF/NooBaa/MinIO/etc.
     |              +--> Volume path decision:
     |                       - CSI snapshot
     |                       - CSI snapshot + Data Mover
     |                       - File System Backup using Restic/Kopia/node-agent
     |                       - No PV backup, metadata only
     |
     v
Object storage bucket / prefix
     |
     +--> backup metadata archive
     +--> resource JSON/YAML
     +--> logs
     +--> PV snapshot references or copied volume data
```

A backup failure usually belongs to one of these domains:

1. **OADP installation / DPA reconcile failure**
2. **Velero pod, plugin, or node-agent failure**
3. **BackupStorageLocation failure**
4. **VolumeSnapshotLocation / CSI snapshot failure**
5. **DataMover / Kopia / Restic / repository failure**
6. **Application hook failure**
7. **Kubernetes API discovery / RBAC / webhook / CRD failure**
8. **Network, DNS, proxy, TLS, or object storage endpoint failure**
9. **Cluster resource pressure: CPU, memory, ephemeral storage, quota, scheduling**
10. **Backup specification mistake: wrong namespace, labels, excluded resources, missing volume settings**

## 3. Initial triage flow

Use this order. It avoids wasting time on Velero logs when the actual failure is storage, credentials, or a missing snapshot class.

```text
1. Is OADP reconciled?
2. Are Velero and node-agent pods healthy?
3. Is BackupStorageLocation Available?
4. Is VolumeSnapshotLocation / CSI setup valid?
5. What is the Backup CR phase, errors, and warnings?
6. What do velero backup describe --details and velero backup logs say?
7. Are PodVolumeBackup/DataUpload/BackupRepository objects healthy?
8. Are storage backend, credentials, TLS, region, and prefix correct?
9. Are app hooks, webhooks, quotas, SCC, PSA, and RBAC blocking the backup?
10. Create a controlled test backup and restore validation.
```

## 4. Command setup for serious troubleshooting

### 4.1 Set variables

```bash
export OADP_NS=openshift-adp
export BACKUP_NAME=<backup-name>
export DPA_NAME=<dpa-name>
```

Find the DPA name if unknown:

```bash
oc get dpa -n ${OADP_NS}
oc get dataprotectionapplication -n ${OADP_NS}
```

### 4.2 Alias the Velero binary inside the Velero deployment

In many OpenShift environments, you do not need a local `velero` binary. Use the binary packaged in the deployment:

```bash
alias velero='oc -n openshift-adp exec deployment/velero -c velero -- ./velero'
```

Validate:

```bash
velero version
velero backup get
velero backup-location get
velero snapshot-location get
```

If `velero version` fails, check the Velero pod and container name:

```bash
oc get deploy -n ${OADP_NS}
oc get pods -n ${OADP_NS}
oc describe deploy/velero -n ${OADP_NS}
```

## 5. Golden evidence collection before changing anything

In production, collect evidence before restarting pods, editing CRs, or deleting failed backups.

```bash
mkdir -p oadp-debug-${BACKUP_NAME}
cd oadp-debug-${BACKUP_NAME}

oc get dpa -n ${OADP_NS} -o yaml > dpa.yaml
oc get pods -n ${OADP_NS} -o wide > pods.txt
oc get events -n ${OADP_NS} --sort-by=.lastTimestamp > events.txt
oc get backup -n ${OADP_NS} -o yaml > backups.yaml
oc get backup ${BACKUP_NAME} -n ${OADP_NS} -o yaml > backup-${BACKUP_NAME}.yaml
oc describe backup ${BACKUP_NAME} -n ${OADP_NS} > backup-${BACKUP_NAME}-describe.txt

oc get backupstoragelocation -n ${OADP_NS} -o yaml > bsl.yaml
oc get volumesnapshotlocation -n ${OADP_NS} -o yaml > vsl.yaml
oc get backuprepository -n ${OADP_NS} -o yaml > backuprepositories.yaml || true
oc get podvolumebackup -n ${OADP_NS} -o yaml > podvolumebackups.yaml || true
oc get dataupload -n ${OADP_NS} -o yaml > datauploads.yaml || true

oc logs deploy/velero -n ${OADP_NS} -c velero --since=24h > velero.log
velero backup describe ${BACKUP_NAME} --details > velero-backup-describe-details.txt
velero backup logs ${BACKUP_NAME} > velero-backup-logs.txt
```

Collect cluster-wide storage objects if CSI snapshot or data mover is involved:

```bash
oc get volumesnapshotclass -o yaml > volumesnapshotclasses.yaml
oc get volumesnapshot -A -o yaml > volumesnapshots.yaml || true
```

Collect must-gather when escalation or Red Hat case is possible:

```bash
oc adm must-gather
```

For OADP-specific support, use the OADP must-gather image/version recommended for your installed OADP channel and OpenShift version.

## 6. Read the Backup CR like an incident report

Start with:

```bash
oc get backup -n ${OADP_NS}
oc get backup ${BACKUP_NAME} -n ${OADP_NS} -o yaml
oc describe backup ${BACKUP_NAME} -n ${OADP_NS}
velero backup describe ${BACKUP_NAME} --details
velero backup logs ${BACKUP_NAME}
```

Focus on these fields:

```yaml
status:
  phase: PartiallyFailed
  errors: 3
  warnings: 8
  startTimestamp: "..."
  completionTimestamp: "..."
  expiration: "..."
  progress:
    itemsBackedUp: ...
    totalItems: ...
```

### Important interpretation

| Symptom | Meaning | First action |
|---|---|---|
| `Failed` | Backup did not complete | Check `velero backup describe --details` and Velero logs |
| `PartiallyFailed` | Metadata archive may exist, but some resources or volumes failed | Identify exact failed items and volume operations |
| `Completed` with warnings | Backup completed, but warnings may affect restore | Review warnings; do not ignore in production |
| `InProgress` for too long | Controller, plugin, or data operation may be stuck/interrupted | Check Velero pod restarts, DataUpload, PodVolumeBackup, snapshots |
| `WaitingForPluginOperations` | Asynchronous plugin operations are still running | Check CSI/DataMover/plugin operation resources |
| `WaitingForPluginOperationsPartiallyFailed` | Some plugin operations failed while waiting for others | Check DataUpload/VolumeSnapshot/Velero plugin logs |

Never accept `Completed` alone as proof. Confirm volume data, critical resources, and restore test.

## 7. Troubleshooting OADP installation and DPA reconciliation failures

If OADP itself is not healthy, backups will fail regardless of backup spec.

### 7.1 Check OADP operator and DPA

```bash
oc get csv -n ${OADP_NS}
oc get subscription -n ${OADP_NS}
oc get installplan -n ${OADP_NS}
oc get dpa -n ${OADP_NS}
oc describe dpa ${DPA_NAME} -n ${OADP_NS}
oc get dpa ${DPA_NAME} -n ${OADP_NS} -o yaml
```

Expected signs:

- Operator CSV is `Succeeded`.
- DPA status reports reconcile complete / reconciled condition.
- Velero deployment exists.
- Required plugins are configured.
- BackupStorageLocation CR exists.
- Node-agent is present if Restic/Kopia/File System Backup/DataMover is enabled.

### 7.2 Common DPA problems

| Problem | Evidence | Fix |
|---|---|---|
| Wrong provider plugin | Velero logs show plugin not found or unsupported provider | Correct DPA `spec.configuration.velero.defaultPlugins` or custom plugin config |
| Wrong secret name/key | DPA events or BSL unavailable | Fix DPA `backupLocations[].velero.credential` |
| Missing cloud credentials | Velero cannot validate backup location | Create or repair secret in `openshift-adp` |
| Invalid CA bundle / self-signed S3 endpoint | TLS errors in Velero logs | Add CA correctly to DPA/Velero deployment or object storage config |
| OLM install issue | CSV not `Succeeded` | Resolve CatalogSource, InstallPlan, subscription, SCC, image pull, proxy issues |
| Unsupported OADP/OCP/Velero combination | API mismatch, CSI snapshot API errors | Align OADP channel/version with OpenShift version |

### 7.3 DPA debug log level

Increase Velero log level temporarily when errors are unclear:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: <dpa-name>
  namespace: openshift-adp
spec:
  configuration:
    velero:
      logLevel: debug
```

Apply carefully:

```bash
oc edit dpa ${DPA_NAME} -n ${OADP_NS}
```

After troubleshooting, reduce log level to `info` or your operational standard.

## 8. Troubleshooting Velero pod, plugin, and node-agent failures

### 8.1 Check pods

```bash
oc get pods -n ${OADP_NS} -o wide
oc describe pod -n ${OADP_NS} -l app.kubernetes.io/name=velero
oc logs deploy/velero -n ${OADP_NS} -c velero --since=2h
oc get events -n ${OADP_NS} --sort-by=.lastTimestamp
```

If node-agent is used:

```bash
oc get ds -n ${OADP_NS}
oc get pods -n ${OADP_NS} -l name=node-agent -o wide
oc logs -n ${OADP_NS} -l name=node-agent --since=2h --all-containers=true
```

Depending on OADP/Velero version, the DaemonSet might be named `node-agent`, `restic`, or similar.

### 8.2 Pod states and likely causes

| Pod state | Common cause | Troubleshooting |
|---|---|---|
| `ImagePullBackOff` | disconnected registry, wrong image, pull secret | Check image source policy, ICSP/IDMS, pull secret, catalog mirror |
| `CrashLoopBackOff` | bad config, bad secret, memory issue, plugin crash | `oc logs --previous`, events, DPA config |
| `Pending` | node selector, taint, resource pressure, quota | `oc describe pod`, check node resources and tolerations |
| `OOMKilled` | large backup, repo maintenance, many CRDs/PVs, insufficient memory | Increase DPA pod resource limits |
| Plugin init failure | wrong plugin image or architecture | Check init containers and plugin directory |

### 8.3 Increase Velero/node-agent resources

For large clusters or large file-system backups, set explicit resources in DPA. Exact schema can vary by OADP version, but the pattern is:

```yaml
spec:
  configuration:
    velero:
      podConfig:
        resourceAllocations:
          requests:
            cpu: "500m"
            memory: "1Gi"
          limits:
            cpu: "2"
            memory: "4Gi"
    nodeAgent:
      podConfig:
        resourceAllocations:
          requests:
            cpu: "500m"
            memory: "1Gi"
          limits:
            cpu: "2"
            memory: "4Gi"
```

Use cluster monitoring to size this properly. Do not blindly set very high limits in resource-constrained clusters.

## 9. Troubleshooting BackupStorageLocation failures

BackupStorageLocation, or BSL, is the object storage target where Velero stores backup metadata, logs, and file-system/data-mover repositories.

### 9.1 Check BSL status

```bash
oc get backupstoragelocation -n ${OADP_NS}
oc describe backupstoragelocation -n ${OADP_NS}
oc get backupstoragelocation -n ${OADP_NS} -o yaml
velero backup-location get
```

A usable BSL should be `Available`. If it is `Unavailable` or `Unknown`, backups usually fail or become unreliable.

### 9.2 Common BSL failure patterns

| Error pattern | Likely cause | Fix |
|---|---|---|
| `AccessDenied` / `Forbidden` | wrong S3 IAM/access key policy | Fix bucket policy and secret |
| `NoSuchBucket` | bucket name wrong or missing | Create bucket or fix DPA BSL config |
| `SignatureDoesNotMatch` | wrong secret, wrong region, clock skew, path-style mismatch | Verify credentials, region, endpoint, NTP |
| `BucketRegionError` | region mismatch | Set correct `region` in BSL config |
| `x509: certificate signed by unknown authority` | custom/self-signed S3 endpoint CA missing | Add CA bundle to Velero/OADP config |
| `dial tcp: lookup ... no such host` | DNS issue | Check cluster DNS, proxy, endpoint spelling |
| timeout | firewall, proxy, route, object storage unavailable | Test from inside Velero pod/debug pod |
| `invalid top-level directories` | bucket/prefix contains non-Velero data | Use dedicated bucket or dedicated prefix |

### 9.3 Verify secret content without leaking it

```bash
oc get secret -n ${OADP_NS}
oc get secret <cloud-secret> -n ${OADP_NS} -o yaml
```

Do not paste decoded secrets into tickets or chat. Instead confirm keys exist.

For AWS-style credentials, typical content is under a key such as `cloud`:

```bash
oc get secret <cloud-secret> -n ${OADP_NS} -o jsonpath='{.data.cloud}' | base64 -d
```

Expected format:

```ini
[default]
aws_access_key_id=<redacted>
aws_secret_access_key=<redacted>
```

### 9.4 Test object storage reachability from inside the cluster

Run a temporary debug pod in a namespace with egress allowed:

```bash
oc run s3-debug -n ${OADP_NS} --rm -it --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi -- bash
```

Inside the pod:

```bash
curl -vk https://<s3-endpoint>
getent hosts <s3-endpoint-hostname>
```

If your cluster uses an egress firewall, NetworkPolicy, proxy, or private endpoint, prove the path from the Velero namespace, not only from your laptop.

### 9.5 Dedicated bucket/prefix best practice

For production, use either:

```text
bucket: dedicated-velero-bucket
prefix: <empty or cluster-name>
```

or:

```text
bucket: shared-platform-backup-bucket
prefix: openshift/prod-cluster-a/velero
```

Avoid writing Velero backups into the root of a bucket that already contains unrelated directories.

## 10. Troubleshooting backup CR spec mistakes

Many “OADP failures” are actually incorrect backup definitions.

### 10.1 Inspect the backup spec

```bash
oc get backup ${BACKUP_NAME} -n ${OADP_NS} -o yaml
```

Review:

```yaml
spec:
  includedNamespaces:
  excludedNamespaces:
  includedResources:
  excludedResources:
  labelSelector:
  storageLocation:
  volumeSnapshotLocations:
  defaultVolumesToFsBackup:
  ttl:
  hooks:
```

### 10.2 Common mistakes

| Mistake | Result | Fix |
|---|---|---|
| Wrong namespace | Backup completes but app missing | Correct `includedNamespaces` |
| Excluded PVC/PV resources | Workload metadata backed up, data missing | Remove bad excludes |
| Wrong label selector | Only subset captured | Verify labels with `oc get all --show-labels` |
| Wrong storage location | Backup goes to unavailable or old BSL | Set valid `storageLocation` |
| `snapshotVolumes: false` unintentionally | No snapshots created | Enable snapshots or FSB as required |
| FSB not enabled for unsupported storage | PVC metadata backed up, no volume data | Use `defaultVolumesToFsBackup` or annotations |
| TTL too short | Backup expires/deletes before DR test | Set TTL based on retention policy |

### 10.3 Example: namespace backup with FSB enabled

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app1-manual-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app1
  storageLocation: default
  defaultVolumesToFsBackup: true
  ttl: 720h0m0s
```

### 10.4 Example: namespace backup using CSI snapshots

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app1-csi-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app1
  storageLocation: default
  snapshotVolumes: true
  ttl: 720h0m0s
```

## 11. Troubleshooting CSI snapshot backup failures

CSI failures are common in OADP because three separate layers must work:

1. Kubernetes CSI snapshot API
2. Storage driver snapshot capability
3. Velero/OADP CSI plugin configuration

### 11.1 Check snapshot API objects

```bash
oc api-resources | grep -i snapshot
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

### 11.2 Check VolumeSnapshotClass labels

Velero CSI snapshot discovery often depends on the correct Velero label on `VolumeSnapshotClass`.

```bash
oc get volumesnapshotclass --show-labels
```

Typical Velero label pattern:

```yaml
labels:
  velero.io/csi-volumesnapshot-class: "true"
```

Example patch:

```bash
oc label volumesnapshotclass <class-name> velero.io/csi-volumesnapshot-class=true --overwrite
```

### 11.3 Check VolumeSnapshotLocation

```bash
oc get volumesnapshotlocation -n ${OADP_NS}
oc describe volumesnapshotlocation -n ${OADP_NS}
oc get volumesnapshotlocation -n ${OADP_NS} -o yaml
velero snapshot-location get
```

For CSI snapshots, some environments do not use cloud-native VSL the same way as AWS/GCP/Azure native snapshots, but stale or wrong VSL configuration can still mislead administrators. Validate according to your OADP and storage provider documentation.

### 11.4 Common CSI snapshot errors

| Error / symptom | Likely cause | Fix |
|---|---|---|
| Backup PartiallyFailed, no snapshot created | `VolumeSnapshotClass` label missing | Add Velero CSI label |
| `no volume snapshotter for volume snapshot location` | VSL/provider mismatch | Fix VSL or backup spec |
| `failed to get volumesnapshotclass` | missing class or RBAC issue | Create/label class; check CRDs/RBAC |
| `snapshot.storage.k8s.io` API errors | incompatible OADP/Velero/snapshot API version | Align OADP version with OCP version |
| `VolumeSnapshotContent` error | storage backend failed snapshot | Check CSI driver logs and storage array/cloud |
| Snapshot hangs | CSI controller issue or volume not ready | Check storage operator, CSI pods, PVC/PV state |
| PVC uses unsupported driver | no CSI snapshot support | Use FSB/Kopia/Restic or storage-native backup |

### 11.5 Check CSI driver and storage operator

```bash
oc get csidriver
oc get pods -A | grep -i csi
oc get co | grep -i storage
oc get sc -o yaml
oc describe pvc <pvc> -n <app-namespace>
oc describe pv <pv-name>
```

Check CSI controller logs in the relevant namespace, for example:

```bash
oc logs -n openshift-cluster-csi-drivers <csi-controller-pod> --since=2h
```

Namespace and pod names depend on storage provider.

### 11.6 StorageClass `WaitForFirstConsumer` issue

If data movement creates temporary PVCs, `WaitForFirstConsumer` storage classes can delay provisioning until a pod is scheduled. If the data mover pod cannot schedule due to node selectors, taints, topology, or resources, the PVC might remain pending.

Check:

```bash
oc get pvc -A | grep -i pending
oc describe pvc <pvc> -n <namespace>
oc describe pod <data-mover-pod> -n ${OADP_NS}
oc get nodes --show-labels
```

Fix scheduling constraints, topology, storage class availability, or data mover pod config.

## 12. Troubleshooting CSI Snapshot Data Mover / DataUpload failures

CSI Snapshot Data Mover takes a snapshot and copies the data to object storage, commonly using Kopia through Velero node-agent.

### 12.1 Check DataUpload resources

```bash
oc get dataupload -n ${OADP_NS}
oc get dataupload -n ${OADP_NS} -o wide
oc describe dataupload <dataupload-name> -n ${OADP_NS}
oc get dataupload <dataupload-name> -n ${OADP_NS} -o yaml
```

Typical phases:

```text
New / Accepted / Prepared / InProgress / Completed / Failed / Cancelled
```

Exact values can vary by Velero version.

### 12.2 Check backup repositories

```bash
oc get backuprepository -n ${OADP_NS}
oc describe backuprepository -n ${OADP_NS}
velero repo get
```

Problems with repositories cause repeated backup failures even when the BSL is available.

### 12.3 Common DataMover failures

| Symptom | Likely cause | Fix |
|---|---|---|
| `DataUpload` stuck `InProgress` | large volume, slow object storage, pod stuck | Check data mover pod logs, bandwidth, timeout |
| `DataUpload` failed quickly | credentials/repository/S3 issue | Check BSL, repo secret, endpoint, CA |
| data mover pod pending | taints/resources/node selector/storage topology | Fix node scheduling or podConfig |
| temporary PVC pending | storage class/topology issue | Fix storage class or target node constraints |
| backup waits for plugin operations | DataUpload not terminal | Describe DataUpload and node-agent logs |
| Kopia repository error | repo password mismatch, repo corruption, partial old repo | Validate `velero-repo-credentials`; avoid changing password after first backup |
| OOMKilled node-agent | large data transfer or repo maintenance | Increase node-agent resources |

### 12.4 Node-agent logs

```bash
oc get pods -n ${OADP_NS} -o wide | grep -E 'node-agent|restic|kopia'
oc logs -n ${OADP_NS} <node-agent-pod> --since=2h
oc logs -n ${OADP_NS} <node-agent-pod> --previous || true
```

### 12.5 Timeout tuning

For large PVCs or slow object storage, backup may time out before data mover completes. Review and tune OADP/Velero item operation timeouts and data mover preparation timeout according to your OADP version.

Example backup-level timeout pattern:

```yaml
spec:
  itemOperationTimeout: 8h0m0s
```

Use longer timeouts only after confirming the data transfer is actually progressing. Timeouts should not hide broken storage or networking.

## 13. Troubleshooting File System Backup using Restic/Kopia

File System Backup (FSB), historically Restic and now commonly Kopia/node-agent in newer Velero/OADP paths, reads files from mounted pod volumes and writes them to object storage.

FSB is useful when:

- Storage does not support snapshots.
- NFS/EFS/hosted file storage is used.
- You want platform-independent volume backup to object storage.
- CSI snapshots are unavailable or not portable enough.

FSB is risky when:

- Application writes heavily during backup.
- Database is not quiesced.
- Pods are not running or PVC is not mounted.
- NFS root squash blocks access.
- Node-agent cannot access host pod volume paths.

### 13.1 Check whether FSB was used

```bash
velero backup describe ${BACKUP_NAME} --details
velero backup logs ${BACKUP_NAME} | grep -i -E 'pod volume|restic|kopia|fs-backup|filesystem|node-agent'

oc get podvolumebackup -n ${OADP_NS}
oc get podvolumebackup -n ${OADP_NS} -o yaml
```

### 13.2 FSB opt-in and opt-out logic

Depending on configuration, FSB can be enabled by:

- Backup-level `defaultVolumesToFsBackup: true`
- Pod annotations for selected volumes
- DPA/node-agent configuration

Example pod annotation pattern:

```bash
oc annotate pod <pod-name> -n <app-namespace> \
  backup.velero.io/backup-volumes=<volume-name-1>,<volume-name-2> --overwrite
```

For controller-managed pods, patch the pod template in Deployment/StatefulSet/DeploymentConfig instead of annotating a single running pod.

### 13.3 Common FSB failures

| Error / symptom | Likely cause | Fix |
|---|---|---|
| no PodVolumeBackup created | FSB not enabled or no annotation | Set `defaultVolumesToFsBackup` or annotations |
| volume path not found | pod not running, volume not mounted, unsupported mount path | Ensure pod mounts PVC and is running on a node |
| permission denied | NFS root squash, SCC/privilege restrictions | Adjust export permissions or use snapshot method |
| backup partially failed | one or more volumes failed | Inspect each `PodVolumeBackup` |
| node-agent not on node | daemonset not scheduled due to taints/selectors | Fix tolerations/node selectors/resources |
| restic/kopia repo lock | interrupted operation or stale lock | Inspect repo status; avoid destructive repair without backup review |
| live DB inconsistent | no pre-backup hook/quiesce | Use app-consistent hooks or database-native backup |

### 13.4 NFS root squash issue

NFS exports with `root_squash` can prevent node-agent/Restic/Kopia from reading files as expected. Evidence usually appears as `permission denied` in PodVolumeBackup or node-agent logs.

Actions:

1. Confirm NFS export options.
2. Confirm file ownership and mode inside app pod.
3. Confirm node-agent can access host-mounted volume paths.
4. Prefer CSI snapshot or storage-native snapshot if available.
5. If policy permits, adjust NFS export and security model; do not weaken production storage security blindly.

### 13.5 FSB with databases

For MySQL, PostgreSQL, MongoDB, Redis, Elasticsearch, or similar stateful systems, FSB alone might capture a crash-consistent or inconsistent view.

Use one of these patterns:

- Pre-backup hook to flush/freeze application.
- Database-native dump to a PVC, then back up the dump.
- CSI snapshot with application quiesce.
- Operator-supported backup CRs.
- Replication-based backup from a standby replica.

Example pre-hook pattern:

```yaml
metadata:
  annotations:
    pre.hook.backup.velero.io/container: mysql
    pre.hook.backup.velero.io/command: '["/bin/bash", "-c", "mysqladmin flush-tables --single-transaction || true"]'
    pre.hook.backup.velero.io/timeout: 5m
    pre.hook.backup.velero.io/on-error: Fail
```

Treat hooks as code. Test them outside backup first.

## 14. Troubleshooting backup hooks

Hooks are powerful but frequently break backups.

### 14.1 Evidence

```bash
velero backup logs ${BACKUP_NAME} | grep -i hook
velero backup describe ${BACKUP_NAME} --details
oc logs <app-pod> -n <app-namespace> --since=1h
```

### 14.2 Common hook failures

| Problem | Evidence | Fix |
|---|---|---|
| Command not found | backup logs show exec error | Use full path or correct image tools |
| Hook timeout | backup waits then fails | Increase timeout or optimize command |
| Wrong container name | Velero cannot exec into container | Correct `pre.hook.backup.velero.io/container` |
| Hook returns non-zero | backup failed if `on-error: Fail` | Fix command or change policy intentionally |
| App has no shell | `/bin/sh` missing | Use image-specific command or helper sidecar |
| Database lock not released | application outage | Use post-hook/thaw, test manually |

### 14.3 Hook design rule

A backup hook should be:

- Idempotent
- Fast
- Observable
- Timeout-bound
- Safe on retry
- Safe if interrupted

Never put a complex long-running database dump directly inside a Velero hook unless you have tested failure and timeout behavior.

## 18. Troubleshooting scheduled backup failures

A Schedule CR may exist, but backups might not be created or might repeatedly fail.

### 18.1 Check schedules

```bash
oc get schedule -n ${OADP_NS}
oc describe schedule <schedule-name> -n ${OADP_NS}
oc get schedule <schedule-name> -n ${OADP_NS} -o yaml
velero schedule get
velero schedule describe <schedule-name>
```

### 18.2 Common schedule problems

| Problem | Evidence | Fix |
|---|---|---|
| No recent backup | wrong cron, schedule paused, controller issue | Check schedule status and Velero logs |
| Repeated PartiallyFailed backups | persistent volume or storage issue | Fix root cause before retention hides it |
| Backups expire too quickly | TTL too low | Adjust TTL according to RPO/retention |
| Too many backups | TTL too high or no lifecycle policy | Set retention and object storage lifecycle carefully |
| Overlapping backups | backup duration > schedule interval | Tune schedule, concurrency, app hooks, storage performance |

### 18.3 Production rule

If a backup schedule runs every 1 hour but each backup takes 3 hours, your schedule is not healthy. You have a throughput and consistency problem, not only a scheduling problem.

## 19. Troubleshooting stuck `InProgress` backups

### 19.1 Symptoms

```bash
oc get backup -n ${OADP_NS}
```

Example:

```text
NAME          STATUS       ERRORS   WARNINGS   CREATED
app-backup    InProgress   0        0          14h ago
```

### 19.2 First checks

```bash
oc get pod -n ${OADP_NS}
oc describe backup ${BACKUP_NAME} -n ${OADP_NS}
velero backup describe ${BACKUP_NAME} --details
velero backup logs ${BACKUP_NAME}
oc get dataupload,podvolumebackup,backuprepository -n ${OADP_NS}
oc get volumesnapshot -A
```

### 19.3 Common causes

| Cause | Evidence | Action |
|---|---|---|
| Velero pod restarted mid-backup | pod restart count, previous logs | Review cause; backup may not resume safely |
| DataUpload still running | `oc get dataupload` | Check data mover pod and object storage throughput |
| PodVolumeBackup still running | `oc get podvolumebackup` | Check node-agent logs and volume size |
| Hook hung | backup logs stop at hook | Fix hook and timeout |
| Snapshot stuck | VolumeSnapshot not ready | Check CSI driver/storage backend |
| API call hanging | discovery/webhook timeout | Fix APIService/webhook |

### 19.4 Deleting a stuck backup

Delete only after evidence collection and after confirming it is not still transferring important data:

```bash
velero backup describe ${BACKUP_NAME} --details
oc delete backup ${BACKUP_NAME} -n ${OADP_NS}
```

If deletion also hangs, check finalizers:

```bash
oc get backup ${BACKUP_NAME} -n ${OADP_NS} -o yaml
```

Do not manually remove finalizers unless you understand which cloud snapshots, object-store objects, temporary PVCs, or repository data might be orphaned.

## 20. Troubleshooting `PartiallyFailed` backups

`PartiallyFailed` is one of the most dangerous states because teams sometimes treat it as “mostly OK”. It means something failed.

### 20.1 Get exact failed items

```bash
velero backup describe ${BACKUP_NAME} --details
velero backup logs ${BACKUP_NAME} | grep -i -E 'error|failed|warn|snapshot|podvolumebackup|dataupload'
```

### 20.2 Classify the failure

| Failed item type | Risk |
|---|---|
| ConfigMap/Secret | Application may restore with wrong config or no credentials |
| PVC/PV data | Application may restore with empty/missing data |
| CRD/custom resource | Operator-managed app may not restore |
| ImageStream/internal image | App may restore but pods cannot pull image |
| Route/Service | App may restore but not be reachable |
| RoleBinding/SCC/SA | App may restore but not start due to permissions |

### 20.3 Decision rule

- If failed item is non-critical and documented, backup may be accepted with exception.
- If failed item is PVC data, Secret, CRD, or image dependency, backup should be treated as **not DR-valid** until fixed and restore-tested.

## 21. Troubleshooting object storage performance and repository maintenance

Large backups can fail even with correct credentials if object storage is slow, throttled, full, or lifecycle policies delete repository content.

### 21.1 Check object storage from Velero path

```bash
oc logs deploy/velero -n ${OADP_NS} -c velero --since=24h | grep -i -E 'timeout|throttle|slow|retry|503|500|connection reset|broken pipe'
```

### 21.2 Common object storage problems

| Problem | Evidence | Fix |
|---|---|---|
| Bucket lifecycle deletes repo content | older backups fail restore, repo errors | Exclude Velero prefix from destructive lifecycle or align retention |
| Object lock/immutability blocks deletes | backup deletion errors | Configure retention/object lock intentionally |
| Slow object storage | long DataUpload/FSB duration | Improve backend, network, concurrency, schedule |
| Proxy resets connections | intermittent upload failure | Tune proxy timeout and no_proxy settings |
| TLS inspection | x509 or EOF errors | Correct trusted CA/no TLS interception |
| Bucket full/quota | write failures | Increase quota or cleanup safely |

### 21.3 Repository password warning

For Kopia/FSB/data mover repositories, do not change repository credentials after backups already exist unless you understand the migration procedure. A password mismatch can make older repository content unreadable.

## 25. Troubleshooting application consistency failures

A backup can be technically successful but application-inconsistent.

### 25.1 Examples

| Application | Risk during live backup | Better pattern |
|---|---|---|
| MySQL/MariaDB | unflushed tables, partial transactions | DB dump, replication, pre-hook flush/lock, CSI snapshot with quiesce |
| PostgreSQL | WAL/checkpoint consistency | pg_dump/pg_basebackup, operator backup, CSI quiesce |
| MongoDB | inconsistent data files | mongodump, filesystem freeze with care, replica backup |
| Elasticsearch/OpenSearch | shard/index inconsistency | snapshot API to object store |
| Kafka | log segment consistency and offsets | MirrorMaker/cluster replication/operator backup |
| Redis | RDB/AOF timing | BGSAVE/AOF fsync policy + backup |

### 25.2 Senior rule

For stateful production systems, OADP should usually be part of the backup strategy, not the entire strategy. Combine it with application-native backups and restore testing.

## 29. Preventive controls to reduce backup failures

### 29.1 Platform controls

- Keep OADP version aligned with OpenShift version.
- Use supported object storage and supported storage snapshot drivers.
- Use a dedicated bucket or dedicated prefix per cluster.
- Monitor BSL phase and Velero backup status.
- Alert on `Failed`, `PartiallyFailed`, missing scheduled backups, and backup age.
- Monitor Velero and node-agent pod restarts/OOMKills.
- Monitor object storage capacity and lifecycle policies.
- Standardize VolumeSnapshotClass labels.
- Keep documented DPA configuration in GitOps.

### 29.2 Application controls

- Maintain per-application backup profiles.
- Define whether the app uses CSI snapshot, FSB, database-native backup, or mixed mode.
- Define backup hooks and test them.
- Document restore order for operators, CRDs, secrets, routes, PVCs, and workloads.
- Run regular restore drills in a non-production namespace or cluster.

### 29.3 Operational controls

- Keep `velero backup describe --details` output for audits.
- Keep restore validation evidence.
- Do not accept `PartiallyFailed` without exception approval.
- Do not change repository password after first backup unless following a planned migration.
- Do not manually delete object-store repository paths unless you are intentionally retiring backups.
- Review schedules so backups do not overlap continuously.

## 30. Sample backup failure runbook for production incident

### Step 1: Declare impact

```text
Application: <name>
Namespace(s): <namespaces>
Backup: <backup-name>
Schedule: <schedule-name>
Current phase: <phase>
Last successful backup: <timestamp>
RPO impact: <duration>
PV data involved: yes/no
```

### Step 2: Freeze evidence

Run evidence collection from section 5.

### Step 3: Identify failure domain

Use:

```bash
velero backup describe ${BACKUP_NAME} --details
velero backup logs ${BACKUP_NAME}
oc describe backup ${BACKUP_NAME} -n ${OADP_NS}
oc get bsl,vsl,podvolumebackup,dataupload,backuprepository -n ${OADP_NS}
```

Classify into:

```text
DPA / Velero / BSL / VSL / CSI / DataMover / FSB / Hook / API / RBAC / Network / Resource pressure / Spec issue
```

### Step 4: Fix the lowest failing layer

Examples:

- If BSL unavailable, fix object storage first.
- If VolumeSnapshotClass missing label, fix snapshot class first.
- If node-agent pending, fix scheduling/resources first.
- If hook fails, fix application hook first.

### Step 5: Create a new backup

Do not rely on the failed object becoming good.

```bash
velero backup create <new-backup-name> --include-namespaces <app-ns> --wait
velero backup describe <new-backup-name> --details
velero backup logs <new-backup-name>
```

### Step 6: Restore validation

Restore to alternate namespace or test cluster.

```bash
velero restore create <restore-name> \
  --from-backup <new-backup-name> \
  --namespace-mappings <source-ns>:<test-restore-ns>

velero restore describe <restore-name> --details
velero restore logs <restore-name>
```

Validate:

```bash
oc get all,pvc,route,secret,configmap -n <test-restore-ns>
oc get pods -n <test-restore-ns>
oc describe pod <pod> -n <test-restore-ns>
curl -k https://<restored-route>
```

For stateful apps, perform application-level validation, not only pod readiness.

### Step 7: Close incident with prevention

Record:

```text
Root cause:
Failed layer:
Evidence:
Fix:
New backup name:
Restore validation result:
Preventive action:
Monitoring/alert update:
Runbook update:
```

## 34. Key takeaways

Backup failure troubleshooting in OADP is not a single-command activity. You must follow the chain:

```text
DPA -> Velero -> Plugins -> BSL -> VSL/CSI -> DataMover/FSB -> App Hooks -> Object Storage -> Restore Validation
```

A 10-year experienced OpenShift administrator should not stop at `oc get backup`. The correct approach is to prove:

1. The backup controller was healthy.
2. The object storage target was valid.
3. Kubernetes and OpenShift resources were captured.
4. PV data was captured by the intended mechanism.
5. Application consistency was respected.
6. The backup can be restored successfully.

The final truth of any backup is not the backup phase. The final truth is a successful, validated restore.
