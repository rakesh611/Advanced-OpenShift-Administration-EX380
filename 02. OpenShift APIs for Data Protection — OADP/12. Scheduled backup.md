# Scheduled Backup in OpenShift APIs for Data Protection (OADP)

**Audience:** Advanced OpenShift / Kubernetes administrators with production experience  
**Skill level:** 10+ years Linux / Kubernetes / OpenShift administration  
**Main objects:** `Schedule`, `Backup`, `Restore`, `BackupStorageLocation`, `VolumeSnapshotLocation`, `DataProtectionApplication`, node-agent, Velero controllers  
**Namespace used by OADP by default:** `openshift-adp`

---

## 1. What is a Scheduled Backup in OADP?

A **Scheduled Backup** in OADP is an automated, recurring application backup created by a Velero `Schedule` custom resource.

Instead of manually creating a `Backup` custom resource every day or every hour, you create one `Schedule` CR. The Velero schedule controller then creates individual `Backup` CRs at the time defined by a cron expression.

In simple words:

```text
Manual backup:
  You create Backup CR every time.

Scheduled backup:
  You create Schedule CR once.
  Velero creates Backup CRs repeatedly based on cron.
```

A scheduled backup is not a separate backup engine. It is a **repeatable backup request**. The actual backup execution still happens through Velero backup controllers, OADP plugins, cloud object storage, snapshots, CSI snapshots, Kopia/Restic file-system backup, and node-agent components.

---

## 2. Why Scheduled Backups Matter in Production

In an enterprise OpenShift environment, application backup cannot depend on an administrator remembering to run a command. Scheduled backups are required for:

- Regular application protection
- Disaster recovery readiness
- RPO compliance
- Audit and compliance evidence
- Namespace-level backup automation
- Stateful application protection
- Migration preparation
- Backup standardization across teams
- GitOps-managed backup policies
- Self-service backup models

For a senior administrator, the real question is not only **how to create a schedule**, but:

- What exactly is included in every scheduled backup?
- Are persistent volumes protected by CSI snapshots, cloud snapshots, or file-system backup?
- Is the backup application-consistent or only crash-consistent?
- Does the schedule overlap with itself?
- Is the backup retained for the correct duration?
- Can the backup be restored successfully?
- Does object storage lifecycle policy conflict with Velero TTL?
- Can the schedule survive cluster upgrades and OADP upgrades?
- Are hooks needed for databases?
- Is the restore process regularly tested?

## 3. OADP Scheduled Backup Architecture

High-level architecture:

```text
+---------------------------+
| Administrator / GitOps    |
| creates Schedule CR       |
+-------------+-------------+
              |
              v
+---------------------------+
| Kubernetes API Server     |
| stores Schedule CR        |
+-------------+-------------+
              |
              v
+---------------------------+
| Velero Schedule Controller|
| watches Schedule CRs      |
+-------------+-------------+
              |
              v
+---------------------------+
| Generated Backup CR       |
| schedule-name-timestamp   |
+-------------+-------------+
              |
              v
+---------------------------+
| Velero Backup Controller  |
| collects resources        |
+-------------+-------------+
              |
              +-----------------------------+
              |                             |
              v                             v
+---------------------------+     +---------------------------+
| Object Storage / BSL      |     | PV Protection Method      |
| Kubernetes objects,       |     | CSI snapshots, cloud      |
| metadata, logs, manifests |     | snapshots, Kopia/Restic   |
+---------------------------+     +---------------------------+
```

Important point:

> A `Schedule` CR does not store backup data. It only defines when and how generated `Backup` CRs are created.

The actual backup artifacts are stored in object storage and snapshot/data-mover repositories depending on your OADP configuration.

## 4. Key OADP and Velero Resources Involved

| Resource | API group | Purpose |
|---|---|---|
| `DataProtectionApplication` | `oadp.openshift.io` | Main OADP configuration object. Installs/configures Velero, node-agent, plugins, BSL, VSL, and data movement options. |
| `BackupStorageLocation` | `velero.io/v1` | Defines where backup metadata and Kubernetes resource archives are stored, usually S3-compatible object storage. |
| `VolumeSnapshotLocation` | `velero.io/v1` | Defines provider-specific snapshot location for PV snapshots when cloud snapshot plugins are used. |
| `Schedule` | `velero.io/v1` | Defines recurring backup policy using cron and a backup template. |
| `Backup` | `velero.io/v1` | Actual backup execution object generated manually or by a schedule. |
| `Restore` | `velero.io/v1` | Restores data from a completed backup. |
| `BackupRepository` | `velero.io/v1` | Used by file-system backup/data mover repositories such as Kopia/Restic. |
| `DeleteBackupRequest` | `velero.io/v1` | Deletes backup artifacts through Velero instead of only deleting the Kubernetes object. |

## 5. Schedule CR Mental Model

A `Schedule` CR has two critical sections:

```yaml
spec:
  schedule: "0 7 * * *"
  template:
    includedNamespaces:
    - my-namespace
    storageLocation: dpa-sample-1
    ttl: 720h0m0s
```

Think of it like this:

```text
spec.schedule
  = When should backup run?

spec.template
  = What Backup spec should be used each time?
```

Every time the cron expression fires, Velero creates a new `Backup` CR using the fields under `spec.template`.

Generated backup name pattern:

```text
<schedule-name>-<timestamp>
```

Example:

```text
finance-prod-daily-20260703070031
```

## 6. Basic Scheduled Backup Example

This example backs up one namespace every day at 07:00 and keeps the generated backups for 30 days.

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: finance-prod-daily
  namespace: openshift-adp
spec:
  schedule: "0 7 * * *"
  template:
    includedNamespaces:
    - finance-prod
    storageLocation: dpa-sample-1
    ttl: 720h0m0s
    defaultVolumesToFsBackup: true
```

Apply it:

```bash
oc apply -f finance-prod-daily-schedule.yaml
```

Verify:

```bash
oc get schedules.velero.io -n openshift-adp
oc describe schedule finance-prod-daily -n openshift-adp
oc get backups.velero.io -n openshift-adp
```

Check the latest generated backup:

```bash
oc get backups.velero.io -n openshift-adp \
  -l velero.io/schedule-name=finance-prod-daily
```

## 7. Prerequisites Before Creating a Scheduled Backup

Before creating a production schedule, validate the OADP foundation.

### 7.1 OADP Operator installed

```bash
oc get operators -A | grep -i oadp
oc get csv -n openshift-adp
```

### 7.2 DataProtectionApplication ready

```bash
oc get dpa -n openshift-adp
oc describe dpa -n openshift-adp
```

Expected result:

```text
RECONCILED=True
```

or a ready/reconciled status depending on OADP version.

### 7.3 Velero pod running

```bash
oc get pods -n openshift-adp
```

Typical components:

```text
velero-...
node-agent-...
openshift-adp-controller-manager-...
```

Depending on the OADP version, node-agent might be deployed when file-system backup or data movement is enabled.

### 7.4 BackupStorageLocation available

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
```

Expected:

```text
NAME           PHASE       DEFAULT
dpa-sample-1   Available   true
```

### 7.5 Snapshot configuration validated

If you use CSI snapshots:

```bash
oc get volumesnapshotclass
```

For CSI snapshots, confirm that your storage class supports snapshots and that a correct `VolumeSnapshotClass` exists.

### 7.6 File-system backup validated

If you use Kopia/Restic file-system backup:

```bash
oc get daemonset -n openshift-adp
oc get pods -n openshift-adp -o wide | grep -E 'node-agent|restic'
```

Also check that the node-agent pods run on all relevant worker nodes.

## 8. Cron Expression in Schedule CR

OADP/Velero schedule uses standard cron format:

```text
┌───────────── minute        0 - 59
│ ┌─────────── hour          0 - 23
│ │ ┌───────── day of month  1 - 31
│ │ │ ┌─────── month         1 - 12
│ │ │ │ ┌───── day of week   0 - 6, Sunday = 0
│ │ │ │ │
* * * * *
```

Examples:

| Requirement | Cron |
|---|---|
| Every day at 07:00 | `0 7 * * *` |
| Every 6 hours | `0 */6 * * *` |
| Every 30 minutes | `*/30 * * * *` |
| Every Sunday at 01:00 | `0 1 * * 0` |
| Every Monday to Friday at 23:30 | `30 23 * * 1-5` |
| First day of every month at 02:00 | `0 2 1 * *` |

For interval schedules, quote the value:

```yaml
spec:
  schedule: "*/10 * * * *"
```

### Time zone note

Velero supports time zone specification using the `CRON_TZ=<timezone>` prefix in supported versions:

```yaml
spec:
  schedule: "CRON_TZ=Asia/Kolkata 0 2 * * *"
```

Production recommendation:

- Prefer explicit timezone if your Velero/OADP version supports it.
- Test the schedule after applying it.
- If timezone parsing fails, use UTC schedule or set the Velero container timezone according to your organization’s supported method.
- Document whether backup windows are in UTC, local data center time, or business timezone.

## 9. Full Production Schedule CR Example

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: ecommerce-prod-daily
  namespace: openshift-adp
  labels:
    backup-tier: gold
    app-owner: ecommerce
    environment: prod
spec:
  schedule: "CRON_TZ=Asia/Kolkata 0 1 * * *"
  paused: false
  useOwnerReferencesInBackup: false
  template:
    metadata:
      labels:
        backup-tier: gold
        app-owner: ecommerce
        environment: prod
    includedNamespaces:
    - ecommerce-prod
    excludedResources:
    - events
    - events.events.k8s.io
    storageLocation: dpa-sample-1
    ttl: 720h0m0s
    defaultVolumesToFsBackup: true
    hooks:
      resources:
      - name: postgres-quiesce
        includedNamespaces:
        - ecommerce-prod
        labelSelector:
          matchLabels:
            app: postgres
        pre:
        - exec:
            container: postgres
            command:
            - /bin/bash
            - -c
            - "psql -U postgres -c 'SELECT pg_start_backup(''oadp'', true);'"
            onError: Fail
            timeout: 60s
        post:
        - exec:
            container: postgres
            command:
            - /bin/bash
            - -c
            - "psql -U postgres -c 'SELECT pg_stop_backup();'"
            onError: Continue
            timeout: 60s
```

> Warning: The PostgreSQL hook above is only a pattern example. Database-specific backup hooks must be validated with the exact database version, container image, authentication method, and backup strategy. For many production databases, using database-native backup tooling together with OADP resource/PV backup is safer than relying only on volume snapshots.

## 10. Schedule CR Field-by-Field Explanation

### 10.1 `metadata.name`

```yaml
metadata:
  name: ecommerce-prod-daily
```

This is the schedule name. Generated backups use this name as prefix.

Example generated backup:

```text
ecommerce-prod-daily-20260703010012
```

Choose a name that includes:

- Application name
- Environment
- Frequency

Good examples:

```text
payments-prod-hourly
finance-prod-daily
hr-uat-weekly
openshift-gitops-daily
```

Bad examples:

```text
backup1
schedule-test
prod
```

### 10.2 `metadata.namespace`

```yaml
namespace: openshift-adp
```

The `Schedule` CR must be created in the namespace where Velero/OADP is running. In OpenShift OADP this is normally:

```text
openshift-adp
```

### 10.3 `spec.schedule`

```yaml
schedule: "0 1 * * *"
```

Defines when backups run.

Production considerations:

- Avoid peak application traffic.
- Avoid storage array maintenance windows.
- Avoid database batch job windows.
- Avoid OpenShift upgrade windows.
- Avoid running many large namespace backups at the exact same minute.
- Stagger backup schedules across applications.

Bad design:

```text
100 namespaces all scheduled at 00:00
```

Better design:

```text
critical app A: 00:30
critical app B: 01:00
critical app C: 01:30
non-critical apps: spread between 02:00 and 04:00
```

### 10.4 `spec.paused`

```yaml
paused: true
```

Pauses the schedule. No new backups should be created while paused.

Use cases:

- During maintenance
- During object storage outage
- Before major application migration
- Before changing schedule template
- During restore testing to prevent accidental new backups

Commands:

```bash
oc patch schedule ecommerce-prod-daily -n openshift-adp \
  --type merge -p '{"spec":{"paused":true}}'

oc patch schedule ecommerce-prod-daily -n openshift-adp \
  --type merge -p '{"spec":{"paused":false}}'
```

Velero CLI alternative:

```bash
velero schedule pause ecommerce-prod-daily -n openshift-adp
velero schedule unpause ecommerce-prod-daily -n openshift-adp
```

### 10.5 `spec.skipImmediately`

```yaml
skipImmediately: true
```

In Velero versions that support it, `skipImmediately` is a one-time control field used to avoid an immediate backup when a schedule is created or unpaused and the controller considers a backup due.

Use case:

```text
You apply the Schedule CR during office hours, but want the first backup only at the next defined backup window.
```

Example:

```yaml
spec:
  schedule: "0 1 * * *"
  skipImmediately: true
```

Always verify that your installed OADP/Velero CRD supports this field:

```bash
oc explain schedule.spec.skipImmediately -n openshift-adp
```

### 10.6 `spec.useOwnerReferencesInBackup`

```yaml
useOwnerReferencesInBackup: false
```

This controls whether generated `Backup` CRs get an owner reference to the `Schedule` CR.

Production recommendation:

```yaml
useOwnerReferencesInBackup: false
```

Reason:

- If owner references are enabled, deleting the `Schedule` can cause Kubernetes garbage collection to delete generated `Backup` CR objects.
- Backup data might still exist in object storage, and Velero might later sync it back.
- This can create confusing behavior for GitOps and DR operations.

Use owner references only if you fully understand your GitOps lifecycle and backup deletion behavior.

### 10.7 `spec.template.includedNamespaces`

```yaml
includedNamespaces:
- ecommerce-prod
```

Defines namespaces included in each generated backup.

Multiple namespaces:

```yaml
includedNamespaces:
- frontend-prod
- backend-prod
- database-prod
```

Full cluster backup pattern:

```yaml
includedNamespaces:
- '*'
```

Production warning:

OADP is primarily an **application backup and restore tool**. It is not a replacement for OpenShift etcd backup. Do not treat a cluster-wide OADP schedule as a complete OpenShift control plane disaster recovery solution.

### 10.8 `spec.template.excludedNamespaces`

```yaml
excludedNamespaces:
- kube-system
- openshift-monitoring
```

Useful when including many namespaces but excluding platform namespaces or temporary namespaces.

### 10.9 `spec.template.includedResources`

```yaml
includedResources:
- deployments
- services
- routes.route.openshift.io
- persistentvolumeclaims
```

Limits backup to specific resource types.

Use carefully. If you exclude required resources, restore can produce incomplete applications.

### 10.10 `spec.template.excludedResources`

```yaml
excludedResources:
- events
- events.events.k8s.io
```

Common exclusions:

```yaml
excludedResources:
- events
- events.events.k8s.io
- pods
```

Be careful with excluding `pods`. For normal Deployments, pods are recreated by controllers. For standalone pods, excluding pods means they will not restore.

### 10.11 `spec.template.labelSelector`

```yaml
labelSelector:
  matchLabels:
    app: payments
```

Backs up only resources matching all labels.

Use this when multiple applications exist in one namespace.

Production caveat:

Labels must be consistent across all required resources. If PVCs, Secrets, Routes, or ConfigMaps do not have the selected labels, they may be skipped.

### 10.12 `spec.template.orLabelSelectors`

```yaml
orLabelSelectors:
- matchLabels:
    app: frontend
- matchLabels:
    app: backend
```

Backs up resources matching any selector.

Use this for multi-component applications sharing one namespace.

### 10.13 `spec.template.storageLocation`

```yaml
storageLocation: dpa-sample-1
```

This references a `BackupStorageLocation`.

Check BSLs:

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
```

For production, use meaningful BSL names:

```text
aws-s3-primary
odf-mcg-backup
azure-backup-eastus
minio-dr-lab
```

### 10.14 `spec.template.ttl`

```yaml
ttl: 720h0m0s
```

TTL means how long generated backups remain eligible for restore before garbage collection removes them.

Examples:

| Retention | TTL |
|---|---|
| 24 hours | `24h0m0s` |
| 7 days | `168h0m0s` |
| 30 days | `720h0m0s` |
| 90 days | `2160h0m0s` |
| 1 year | `8760h0m0s` |

Important:

- TTL is Velero retention, not necessarily the same as object storage lifecycle retention.
- Object storage lifecycle policies must not delete backup data before Velero TTL.
- Immutable bucket policies must be designed carefully because Velero garbage collection needs deletion permission after TTL.
- Long TTL with frequent backups can create high S3/object storage cost.

### 10.15 `spec.template.defaultVolumesToFsBackup`

```yaml
defaultVolumesToFsBackup: true
```

This enables file-system backup by default for pod volumes when using the supported file-system backup method.

Version note:

- OADP 1.2 and later use `defaultVolumesToFsBackup`.
- Older OADP 1.1 used `defaultVolumesToRestic`.

Validate your installed CRD:

```bash
oc explain schedule.spec.template.defaultVolumesToFsBackup -n openshift-adp
oc explain backup.spec.defaultVolumesToFsBackup -n openshift-adp
```

### 10.16 `spec.template.snapshotVolumes`

```yaml
snapshotVolumes: true
```

Controls whether PV snapshots are attempted when supported by the configured provider.

Use this when you rely on CSI/cloud snapshots.

### 10.17 `spec.template.snapshotMoveData`

```yaml
snapshotMoveData: true
```

When supported, this tells Velero/OADP to move snapshot data after snapshot creation. This is useful when you do not want your backup to depend only on provider snapshot lifecycle in the source cluster/account/region.

Use cases:

- Backup to object storage independent of the source volume snapshot
- Cross-cluster restore
- Cross-region DR patterns
- Storage-provider snapshot portability limitations

### 10.18 `spec.template.csiSnapshotTimeout`

```yaml
csiSnapshotTimeout: 10m
```

Timeout for CSI snapshot readiness. Increase this for large or slow volumes.

Example:

```yaml
csiSnapshotTimeout: 30m
```

### 10.19 `spec.template.itemOperationTimeout`

```yaml
itemOperationTimeout: 4h
```

Timeout for asynchronous item operations. Large volume data movement may require tuning.

### 10.20 `spec.template.hooks`

Backup hooks run commands inside matching pods before or after backup processing.

Typical use cases:

- Flush database buffers
- Freeze filesystem
- Put application into read-only mode
- Trigger application checkpoint
- Run consistency marker command
- Resume application after backup

Example simple hook:

```yaml
hooks:
  resources:
  - name: app-flush
    includedNamespaces:
    - finance-prod
    labelSelector:
      matchLabels:
        app: finance-api
    pre:
    - exec:
        container: app
        command:
        - /bin/sh
        - -c
        - "sync"
        onError: Continue
        timeout: 30s
```

Advanced warning:

Hooks can make a backup more application-consistent, but they can also break backups if:

- Command path does not exist
- Container name is wrong
- RBAC blocks exec
- Database authentication fails
- Hook timeout is too low
- `onError: Fail` stops the entire backup
- Application does not tolerate quiesce/freeze operations

## 11. Backup Consistency Levels

Scheduled backups can provide different consistency levels depending on design.

### 11.1 Resource-consistent backup

Backs up Kubernetes/OpenShift API objects:

- Deployments
- StatefulSets
- Services
- Routes
- ConfigMaps
- Secrets
- PVC definitions
- RBAC resources

This does not guarantee application data consistency.

### 11.2 Crash-consistent volume backup

A storage snapshot or file-system backup captures volume state at a point in time without application quiescing.

This is similar to pulling power from a server and recovering from disk state.

Good for:

- Stateless apps
- Apps that tolerate crash recovery
- Databases with strong WAL/journal recovery

Risky for:

- Databases without proper journaling
- Multi-volume consistency groups
- Apps requiring external transaction consistency

### 11.3 Application-consistent backup

Uses application-aware steps such as:

- Database-native backup
- Pre/post hooks
- Filesystem freeze/unfreeze
- Write quiesce
- Transaction checkpoint

For databases, senior admins usually combine:

```text
Database-native logical/physical backup
+ OADP resource backup
+ PVC/snapshot backup where appropriate
+ restore test
```

Do not assume a scheduled OADP backup is automatically application-consistent.

## 12. Scheduled Backup Design Patterns

### 12.1 Namespace-level daily backup

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: hr-prod-daily
  namespace: openshift-adp
spec:
  schedule: "0 2 * * *"
  template:
    includedNamespaces:
    - hr-prod
    storageLocation: dpa-sample-1
    ttl: 720h0m0s
    defaultVolumesToFsBackup: true
```

Use when:

- One app per namespace
- Simple app ownership
- Namespace is the backup boundary

### 12.2 Label-based application backup in shared namespace

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: payments-prod-daily
  namespace: openshift-adp
spec:
  schedule: "30 1 * * *"
  template:
    includedNamespaces:
    - shared-prod
    labelSelector:
      matchLabels:
        app.kubernetes.io/part-of: payments
    storageLocation: dpa-sample-1
    ttl: 720h0m0s
```

Use when:

- Multiple applications share a namespace
- Labels are mature and controlled

Risk:

- Missed resources if labels are incomplete

### 12.3 Gold/Silver/Bronze backup tiers

Gold schedule:

```yaml
spec:
  schedule: "0 */4 * * *"
  template:
    ttl: 168h0m0s
```

Silver schedule:

```yaml
spec:
  schedule: "0 2 * * *"
  template:
    ttl: 720h0m0s
```

Bronze schedule:

```yaml
spec:
  schedule: "0 3 * * 0"
  template:
    ttl: 2160h0m0s
```

Use when:

- Business defines different RPO/RTO tiers
- Not every app needs the same frequency

### 12.4 Staggered backup windows

```text
00:30  identity-prod
01:00  payments-prod
01:30  ecommerce-prod
02:00  reporting-prod
02:30  non-critical-prod
```

Avoid this:

```text
00:00 all production namespaces
```

Reason:

- Object storage request spike
- CSI snapshot storm
- Storage array pressure
- Node-agent resource contention
- Backup controller queue growth
- Application latency during backup window

### 12.5 GitOps-managed schedules

Store Schedule manifests in Git:

```text
gitops-repo/
  clusters/
    prod/
      oadp/
        schedules/
          payments-prod-daily.yaml
          ecommerce-prod-daily.yaml
          identity-prod-hourly.yaml
```

Best practices:

- Use `useOwnerReferencesInBackup: false`
- Do not let pruning delete generated `Backup` CRs accidentally
- Exclude generated `Backup` objects from GitOps management
- Manage only desired `Schedule` CRs
- Use labels for ownership and audit

### 12.6 Pre-upgrade scheduled backup

Before OpenShift/OADP upgrades, create an on-demand backup from the same template:

```bash
velero backup create payments-pre-upgrade-$(date +%Y%m%d) \
  --from-schedule payments-prod-daily \
  -n openshift-adp
```

Then verify:

```bash
velero backup describe payments-pre-upgrade-YYYYMMDD --details -n openshift-adp
```

## 13. Creating a Schedule by CLI

You can create a schedule by YAML or Velero CLI.

CLI example:

```bash
velero schedule create finance-prod-daily \
  --schedule="0 7 * * *" \
  --include-namespaces finance-prod \
  --storage-location dpa-sample-1 \
  --ttl 720h0m0s \
  -n openshift-adp
```

Then export YAML for GitOps:

```bash
oc get schedule finance-prod-daily -n openshift-adp -o yaml > finance-prod-daily.yaml
```

Production preference:

```text
Use YAML/GitOps for repeatable environments.
Use CLI for testing, emergency operations, or temporary schedules.
```

## 14. Triggering an On-Demand Backup from an Existing Schedule

Useful for testing a schedule template without waiting for cron.

```bash
velero backup create finance-prod-manual-test \
  --from-schedule finance-prod-daily \
  -n openshift-adp
```

Verify:

```bash
velero backup describe finance-prod-manual-test --details -n openshift-adp
velero backup logs finance-prod-manual-test -n openshift-adp
```

This is one of the safest ways to validate a schedule template.

## 15. Verifying Scheduled Backups

### 15.1 Check schedules

```bash
oc get schedules.velero.io -n openshift-adp
```

Example:

```text
NAME                 STATUS    SCHEDULE      LAST BACKUP
finance-prod-daily   Enabled   0 7 * * *     2h ago
```

### 15.2 Check schedule details

```bash
oc describe schedule finance-prod-daily -n openshift-adp
```

Look for:

- Schedule status
- Last backup timestamp
- Validation errors
- Template fields

### 15.3 Check generated backups

```bash
oc get backups.velero.io -n openshift-adp \
  -l velero.io/schedule-name=finance-prod-daily
```

### 15.4 Check backup phase

```bash
oc get backup <backup-name> -n openshift-adp \
  -o jsonpath='{.status.phase}{"\n"}'
```

Possible backup phases include:

```text
New
InProgress
WaitingForPluginOperations
WaitingForPluginOperationsPartiallyFailed
Finalizing
Completed
PartiallyFailed
Failed
Deleting
```

Actual phases can vary by Velero/OADP version.

### 15.5 Describe backup

```bash
velero backup describe <backup-name> --details -n openshift-adp
```

Check:

- Included namespaces
- Excluded resources
- Warnings
- Errors
- PV backup method
- Snapshot count
- Pod volume backup count
- Backup storage location

### 15.6 Check backup logs

```bash
velero backup logs <backup-name> -n openshift-adp
```

## 17. Retention and Garbage Collection

Retention is controlled mainly by backup TTL:

```yaml
ttl: 720h0m0s
```

When a backup expires, Velero garbage collection removes backup resources and associated artifacts according to Velero/OADP behavior and the storage method used.

### 17.1 Retention design

Example policy:

| Tier | Frequency | TTL | Use case |
|---|---:|---:|---|
| Gold | Every 4 hours | 7 days | Critical production apps |
| Silver | Daily | 30 days | Standard production apps |
| Bronze | Weekly | 90 days | Non-critical apps |
| Pre-upgrade | Manual | 14 days | Change safety |

### 17.2 Object storage lifecycle policy

Object storage lifecycle must be aligned with Velero TTL.

Bad design:

```text
Velero TTL = 30 days
S3 lifecycle deletes after 7 days
```

Result:

```text
Backup CR may exist, but data is gone from object storage.
Restore fails.
```

Better design:

```text
Velero TTL = 30 days
S3 lifecycle expiration = 45 days or disabled for Velero prefix
```

### 17.3 Immutable object storage

Immutable buckets can protect backups against ransomware or accidental deletion, but they must be designed carefully.

If object lock prevents Velero from deleting expired backup objects, garbage collection may report delete failures.

Recommended approach:

- Define retention requirements with security/compliance team.
- Align Velero TTL with bucket retention.
- Use separate buckets/prefixes for immutable long-term retention if needed.
- Test backup deletion behavior.

## 18. Backup Frequency and Overlap Control

The most common production mistake is scheduling backups too frequently.

Example problem:

```text
Namespace backup takes 25 minutes.
Schedule runs every 15 minutes.
```

Result:

- Backup queue grows
- Storage snapshots overlap
- Object storage load increases
- Application performance may degrade
- Node-agent pods consume CPU/network for long periods
- Restore point quality becomes confusing

Rule of thumb:

```text
Backup interval >= normal backup duration + safety buffer
```

Example:

```text
Average backup duration: 10 min
Worst normal duration:   18 min
Recommended interval:    30 min or more
```

Measure backup duration:

```bash
oc get backups.velero.io -n openshift-adp \
  -o custom-columns=NAME:.metadata.name,START:.status.startTimestamp,COMPLETE:.status.completionTimestamp,PHASE:.status.phase
```

## 19. Performance Considerations

Scheduled backups can impact cluster performance.

### 19.1 API server impact

Velero queries the Kubernetes API server to collect resources.

Large cluster-wide backups can increase:

- API request volume
- etcd read load
- API server memory usage

Recommendations:

- Prefer namespace/application-scoped schedules.
- Avoid frequent full-cluster OADP backups.
- Exclude noisy resources such as events.
- Stagger large schedules.

### 19.2 Storage impact

Snapshots and file-system backups can impact:

- CSI controller load
- Storage backend load
- Volume snapshot creation time
- Node disk I/O
- Network bandwidth

Recommendations:

- Coordinate with storage team.
- Avoid snapshot storms.
- Monitor storage latency during backup windows.
- Use CSI snapshot classes designed for backup workloads.

### 19.3 Node-agent impact

File-system backup through node-agent can consume:

- CPU
- Memory
- Disk read I/O
- Network bandwidth

Recommendations:

- Set resource requests/limits for node-agent.
- Tune concurrency carefully.
- Avoid backing up huge transient directories.
- Use application-native backup for large databases where appropriate.

### 19.4 Object storage impact

Frequent backup schedules increase:

- PUT requests
- GET/LIST operations
- Storage capacity
- Lifecycle processing
- Cross-region replication cost

Recommendations:

- Use lifecycle policy carefully.
- Monitor bucket growth.
- Use separate prefixes/buckets by environment.
- Enable object storage metrics.

## 20. Parallel Backup Processing and Scheduling Strategy

Some OADP/Velero versions support parallel backup processing. Even when available, do not blindly increase concurrency.

Parallel backup is useful when:

- Multiple independent namespaces need backup at the same time
- Many small backups are blocked behind one large backup
- Backup window is too long

Parallel backup is risky when:

- All backups hit the same storage backend
- Backups contain large PVs
- Node-agent resources are limited
- API server is already under load
- Object storage throttles requests

Advanced strategy:

```text
1. Measure backup duration and bottleneck.
2. Stagger schedules first.
3. Increase concurrency only when bottleneck is controller serialization.
4. Add CPU/memory to Velero if concurrency increases.
5. Validate restore behavior after tuning.
```

## 22. Troubleshooting Scheduled Backups

### 22.1 Schedule not creating backups

Check schedule:

```bash
oc get schedule -n openshift-adp
oc describe schedule <schedule-name> -n openshift-adp
oc get schedule <schedule-name> -n openshift-adp -o yaml
```

Check Velero logs:

```bash
oc logs deploy/velero -n openshift-adp
```

Common causes:

- Invalid cron expression
- Schedule is paused
- Velero pod not running
- CRD field validation error
- OADP upgrade issue
- Schedule created in wrong namespace
- `skipImmediately` delaying first backup

### 22.2 Backup generated but stuck `InProgress`

Check backup details:

```bash
velero backup describe <backup-name> --details -n openshift-adp
velero backup logs <backup-name> -n openshift-adp
```

Check CSI snapshots:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

Check node-agent:

```bash
oc get pods -n openshift-adp -o wide | grep node-agent
oc logs -n openshift-adp <node-agent-pod>
```

Common causes:

- CSI snapshot not ready
- VolumeSnapshotClass missing or wrong
- Node-agent cannot access volume
- Large volume data movement still running
- Storage backend slow
- Object storage throttling
- Hook command hanging

### 22.3 Backup `PartiallyFailed`

```bash
velero backup describe <backup-name> --details -n openshift-adp
velero backup logs <backup-name> -n openshift-adp | grep -i error
```

Common causes:

- Some resources failed due to RBAC
- Hook failed but backup continued
- Volume backup failed for one PVC
- Unsupported resource version
- API discovery issue
- Excluded/invalid resources

Action:

```text
Treat PartiallyFailed as not fully reliable until you understand exactly what failed.
```

### 22.4 Backup `Failed`

Check:

```bash
oc describe backup <backup-name> -n openshift-adp
velero backup logs <backup-name> -n openshift-adp
oc logs deploy/velero -n openshift-adp
```

Common causes:

- BSL unavailable
- S3 credentials invalid
- Bucket permission denied
- Snapshot API failure
- Pre-hook failed with `onError: Fail`
- CRD validation error
- Velero plugin crash

### 22.5 BSL unavailable

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
oc describe backupstoragelocation <bsl-name> -n openshift-adp
```

Common causes:

- Wrong S3 endpoint
- Wrong bucket
- Invalid credentials
- Network/DNS issue
- Proxy configuration issue
- CA trust issue
- Bucket region mismatch
- IAM permission issue

### 22.6 Hook failures

Check backup logs:

```bash
velero backup logs <backup-name> -n openshift-adp | grep -i hook
```

Debug command manually:

```bash
oc exec -n <app-namespace> <pod-name> -c <container> -- <command>
```

Common causes:

- Container name mismatch
- Command missing in image
- Shell not available
- Timeout too low
- Database credentials missing
- Hook selector matches wrong pod
- Hook selector matches multiple pods unintentionally

### 22.7 PVC or PV not restored

Check backup details:

```bash
velero backup describe <backup-name> --details -n openshift-adp
```

Check restore details:

```bash
velero restore describe <restore-name> --details -n openshift-adp
```

Common causes:

- Storage class missing in target cluster
- VolumeSnapshotClass missing
- PV capacity mismatch
- Restore namespace mapping issue
- CSI driver unavailable
- FSB repository issue
- PVC excluded by label/resource filters

## 24. Security and RBAC Considerations

Scheduled backups are sensitive because they can include:

- Secrets
- ConfigMaps
- Routes
- ServiceAccount tokens depending on cluster behavior/version
- PVC data
- Database data
- Application credentials

Security best practices:

- Restrict who can create `Schedule`, `Backup`, and `Restore` CRs.
- Encrypt object storage at rest.
- Use least-privilege IAM for S3/cloud storage.
- Use TLS and trusted CA for S3-compatible endpoints.
- Protect backup bucket credentials.
- Audit backup and restore operations.
- Avoid restoring Secrets into unauthorized namespaces.
- Use separate backup locations for dev/test/prod.
- Consider object lock/immutability for ransomware protection.
- Test deletion behavior if using immutable storage.

## 25. Multi-Cluster and DR Considerations

For DR, scheduled backups must be restorable outside the source cluster.

Checklist:

- Target cluster has compatible OpenShift/Kubernetes API versions.
- Required CRDs/operators exist before restore.
- Storage classes exist or storage class mapping is configured.
- CSI drivers exist on target cluster.
- Image registry access is available.
- Routes/DNS are adjusted for target cluster.
- Secrets are restored securely.
- NetworkPolicies are compatible.
- SCCs/RBAC/ServiceAccounts are restored or pre-created.
- Backup bucket is accessible from target cluster.
- BSL may need read-only mode during restore-only DR testing.

Important:

```text
A backup that completes successfully on source cluster is not automatically a valid DR backup.
A DR backup is valid only after restore is tested on a target environment.
```

## 27. Common Production Mistakes

### Mistake 1: Backup schedule exists but no restore test

```text
Backup success is not DR readiness.
Restore success is DR readiness.
```

### Mistake 2: Scheduling too frequently

If backup takes 40 minutes, do not schedule every 30 minutes.

### Mistake 3: Backing up everything every hour

This creates API, storage, and cost pressure.

### Mistake 4: Ignoring TTL

No TTL planning causes runaway object storage growth.

### Mistake 5: S3 lifecycle deletes backups before Velero TTL

This breaks restore.

### Mistake 6: Label selector misses PVCs or Secrets

Shared namespace backup with weak labels is dangerous.

### Mistake 7: Assuming PV snapshot equals database-consistent backup

Use database-aware strategy.

### Mistake 8: Deleting Backup CR manually

Deleting only the Kubernetes object might not clean storage artifacts correctly. Use Velero delete or `DeleteBackupRequest`.

### Mistake 9: Backing up platform namespaces blindly

OADP is not an etcd backup replacement.

### Mistake 10: No documentation of RPO/RTO

Backup schedules should map to business requirements.

## 28. Interview-Level Explanation

If asked in an interview:

**Question:** What is a scheduled backup in OADP?

**Answer:**

A scheduled backup in OADP is a Velero `Schedule` custom resource created in the OADP namespace, usually `openshift-adp`. It defines a cron expression and a backup template. The Velero schedule controller watches this object and creates individual `Backup` CRs at the configured intervals. Each generated backup uses the `spec.template` from the Schedule, including namespaces, resource filters, label selectors, backup storage location, TTL, hooks, and volume backup options. The backup data is written to the configured `BackupStorageLocation`, and persistent volumes are protected through CSI/cloud snapshots, snapshot data movement, or file-system backup using node-agent/Kopia/Restic depending on OADP configuration.

For production, I would not only create the schedule. I would validate that the DPA is reconciled, BSL is available, snapshot or file-system backup is configured, the schedule does not overlap with previous runs, TTL matches retention policy, hooks are tested for stateful workloads, and restore is tested regularly. I would also monitor failed or partially failed backups, object storage capacity, Velero logs, node-agent health, and backup duration trends.

## 32. Advanced Admin Summary

A scheduled backup in OADP is easy to create but difficult to operate correctly at scale. The `Schedule` CR is only the automation wrapper. The reliability of your backup depends on the entire chain:

```text
Schedule CR
  -> generated Backup CR
  -> Velero backup controller
  -> OpenShift API discovery
  -> OADP plugins
  -> BSL object storage
  -> CSI/cloud snapshot or node-agent file-system backup
  -> TTL/garbage collection
  -> restore validation
```

For a 10-year experienced OpenShift administrator, the best practice is:

1. Design schedules from RPO/RTO requirements.
2. Scope backups by application or namespace, not blindly by cluster.
3. Use BSL/VSL/storage configuration that is validated and monitored.
4. Decide volume strategy: CSI snapshot, snapshot data movement, or file-system backup.
5. Add application hooks only when tested and necessary.
6. Avoid overlapping schedules.
7. Align TTL with object storage lifecycle and compliance.
8. Monitor failed/partial backups and backup age.
9. Test restore regularly.
10. Treat backup restore testing as part of production operations, not as an optional task.
