# Persistent Volume Backup in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift Administrator / Platform Engineer with 10+ years of Linux, storage, Kubernetes, and OpenShift operations experience.

**Scope:** This guide explains how PersistentVolume (PV) and PersistentVolumeClaim (PVC) backups work in OADP, how to choose between CSI snapshots, CSI Snapshot Data Mover, Kopia file-system backup, and legacy Restic, and how to design, operate, troubleshoot, and validate PV backup/restore in production OpenShift clusters.

**Important:** OADP is primarily an **application/workload backup** solution. It protects application resources, namespace-scoped objects, related cluster-scoped objects, PV data, and internal images depending on configuration. It is **not a replacement for etcd backup** of the OpenShift control plane.

---

## 1. What “Persistent Volume Backup” Means in OADP

In OpenShift, application backup has two different parts:

1. **Kubernetes/OpenShift object backup**
   - Namespace
   - Deployment / StatefulSet / DaemonSet
   - Service
   - Route / Ingress
   - Secret / ConfigMap
   - ServiceAccount
   - Role / RoleBinding
   - PVC object
   - Custom resources

2. **Persistent data backup**
   - Actual data stored behind the PVC
   - Database files
   - Application uploads
   - Message queue data
   - Registry data
   - Stateful application disk content

A common junior-level mistake is assuming that backing up the PVC YAML backs up the data. It does not. The PVC object only says:

```text
I need storage of size X from StorageClass Y.
```

The actual bytes live in the storage backend:

- ODF Ceph RBD
- ODF CephFS
- AWS EBS / EFS
- Azure Disk / Azure File
- GCP Persistent Disk
- vSphere CNS
- NetApp Trident
- Portworx
- NFS
- Local PV
- Other CSI-backed storage

OADP uses Velero under the hood to coordinate backup and restore. For PV data, OADP/Velero usually uses one of these methods:

| Method | Data source | Where backup data lives | Best for |
|---|---|---|---|
| CSI snapshot | Storage snapshot API | Storage backend snapshot | Fast same-storage recovery |
| CSI Snapshot Data Mover | CSI snapshot, then copied | Object storage repository | Durable DR and migration |
| File System Backup with Kopia | Mounted pod volume filesystem | Object storage repository | Non-snapshot volumes, RWX, file-level backup |
| Legacy Restic file-system backup | Mounted pod volume filesystem | Object storage repository | Older OADP environments only |
| Application-native backup | Database/application tooling | Object storage / backup system | Strong application consistency |

### 2.2 DataProtectionApplication — DPA

`DataProtectionApplication` is the main OADP custom resource. It declares:

- Which Velero plugins are enabled
- Where backups are stored
- Which credentials are used
- Whether CSI support is enabled
- Whether node-agent is enabled
- Whether Kopia or Restic is used as uploader
- Snapshot locations

Example high-level view:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
      - openshift
      - aws
      - csi
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
  - velero:
      provider: aws
      default: true
      objectStorage:
        bucket: my-oadp-bucket
        prefix: openshift/prod-cluster
      config:
        region: us-east-1
      credential:
        name: cloud-credentials
        key: cloud
  snapshotLocations:
  - velero:
      provider: aws
      config:
        region: us-east-1
```

> Adjust provider, plugin, bucket, endpoint, and credentials for your real storage platform. For S3-compatible storage such as NooBaa/MCG, MinIO, or third-party object storage, `s3Url` and `s3ForcePathStyle` are commonly required.

## 3. PV Backup Methods in Detail

---

## 3.1 Method 1 — CSI Snapshot Backup

### Concept

CSI snapshot backup uses the Kubernetes CSI snapshot API to create a point-in-time snapshot of a PVC-backed volume.

Objects involved:

```text
PVC
 └── VolumeSnapshot
      └── VolumeSnapshotContent
           └── Backend snapshot in storage platform
```

For example, with ODF RBD:

```text
PostgreSQL PVC
 └── VolumeSnapshot
      └── VolumeSnapshotContent
           └── Ceph RBD snapshot
```

### Why CSI snapshots are useful

CSI snapshots are fast because they are normally metadata operations in the storage backend. The application volume is not copied block-by-block during snapshot creation.

Good use cases:

- Fast restore in the same cluster or same storage backend
- StatefulSet backup before upgrade
- Application rollback
- Same-cloud restore
- Same-storage-class restore
- Short RPO backup schedule

### Limitations

CSI snapshots are not always full DR backups.

Important limitations:

- Snapshot may remain tied to the original storage system.
- Snapshot may not be portable across clusters, regions, clouds, or storage vendors.
- Snapshot availability depends on the CSI driver and backend.
- Application consistency is not guaranteed unless you quiesce the application.
- Snapshot metadata backup alone does not guarantee recovery after full storage loss.

### Prerequisites

Check CSI snapshot APIs:

```bash
oc api-resources | grep -i volumesnapshot
```

Expected resources:

```text
volumesnapshotclasses.snapshot.storage.k8s.io
volumesnapshotcontents.snapshot.storage.k8s.io
volumesnapshots.snapshot.storage.k8s.io
```

Check VolumeSnapshotClass:

```bash
oc get volumesnapshotclass
```

Example:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ocs-rbdplugin-snapclass
  labels:
    velero.io/csi-volumesnapshot-class: "true"
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Retain
```

Use the field supported by your installed `VolumeSnapshotClass` API schema. For the GA `snapshot.storage.k8s.io/v1` API, the field is `deletionPolicy`.

### Critical rule

For each CSI driver, configure **only one** `VolumeSnapshotClass` with:

```yaml
velero.io/csi-volumesnapshot-class: "true"
```

If you label multiple snapshot classes for the same driver, Velero may select the wrong class or fail unpredictably.

### Backup CR using CSI snapshots

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: prod-db-csi-snapshot-20260703
  namespace: openshift-adp
spec:
  includedNamespaces:
  - prod-db
  storageLocation: default
  snapshotVolumes: true
  ttl: 720h0m0s
```

Apply:

```bash
oc apply -f backup-prod-db-csi.yaml
```

Monitor:

```bash
oc get backup -n openshift-adp
oc describe backup prod-db-csi-snapshot-20260703 -n openshift-adp
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

## 3.2 Method 2 — CSI Snapshot Data Mover with Kopia

### Concept

CSI Snapshot Data Mover combines the speed and consistency advantage of CSI snapshots with the durability and portability of object storage.

Instead of keeping only the backend snapshot, OADP/Velero:

1. Creates a CSI snapshot of the PVC.
2. Creates temporary/intermediate resources to access the snapshot data.
3. Starts data mover processing through node-agent.
4. Copies the snapshot data into a Kopia-backed repository in object storage.
5. Cleans up temporary resources after completion.

High-level flow:

```text
Application PVC
   |
   | 1. CSI snapshot
   v
VolumeSnapshot / VolumeSnapshotContent
   |
   | 2. Temporary PVC/PV from snapshot
   v
Data mover pod
   |
   | 3. Upload using Kopia
   v
Object storage backup repository
```

### Why this is preferred for serious DR

CSI snapshot alone is usually storage-local. Data Mover turns the snapshot into a more portable backup by moving its data into object storage.

Good use cases:

- DR from object storage
- Cross-cluster restore
- Storage backend failure scenarios
- Long-term retention
- On-premises backup to S3-compatible target
- Hybrid cloud migration
- ODF/CSI volume protection where snapshots alone are not sufficient

### Main objects

During backup:

```text
Backup CR
VolumeSnapshot
VolumeSnapshotContent
DataUpload
BackupRepository
Temporary PVC/PV
Data mover pod
```

During restore:

```text
Restore CR
DataDownload
BackupRepository
Temporary restore PVC/PV
Data mover pod
Restored PVC
Restored workload
```

### DPA requirements

You need:

- CSI plugin enabled
- Node Agent enabled
- Kopia uploader selected
- Valid BSL
- CSI-capable storage
- Correct VolumeSnapshotClass

Example DPA concept:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
      - openshift
      - csi
      - aws
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
  - velero:
      provider: aws
      default: true
      objectStorage:
        bucket: my-oadp-bucket
        prefix: prod-cluster
      config:
        region: us-east-1
        s3Url: https://s3.example.com
        s3ForcePathStyle: "true"
      credential:
        name: cloud-credentials
        key: cloud
```

### Backup CR using CSI Snapshot Data Mover

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: prod-db-csi-datamover-20260703
  namespace: openshift-adp
spec:
  includedNamespaces:
  - prod-db
  storageLocation: default
  snapshotVolumes: true
  snapshotMoveData: true
  datamover: velero
```


Check repository:

```bash

oc describe backuprepository -n openshift-adp <repo-name>
```

### Restore CR


### Restore to a different namespace

```yaml

  name: restore-prod-db-to-test
  namespace: openshift-adp

  backupName: prod-db-csi-datamover-20260703
  namespaceMapping:
    prod-db: prod-db-restore
```

Create target namespace if needed:

```bash
oc new-project prod-db-restore
oc apply -f restore-prod-db-to-test.yaml
```

### Senior-level notes

CSI Snapshot Data Mover is usually the best general-purpose PV backup method when your storage supports CSI snapshots and you need real DR. It reduces live-volume inconsistency compared with pure file-system backup because the data mover reads from the snapshot, not from a constantly changing live volume.

However, it still does not automatically make a database transaction-consistent. For databases, use application hooks or native database backup mechanisms.

## 3.3 Method 3 — File System Backup with Kopia

### Concept

File System Backup reads files from the mounted pod volume on the node and uploads them to the backup repository.

Flow:

```text
Running pod
   |
   | mounted PVC filesystem
   v
Node filesystem path under kubelet
   |
   | node-agent reads files
   v
Kopia repository in object storage
```

This method is also called:

- File System Backup
- FSB
- Pod Volume Backup

### When to use

Use Kopia file-system backup when:

- CSI snapshot is not available
- Storage backend does not support snapshots
- You use NFS/RWX storage
- You need file-level backup behavior
- You use volumes that Velero cannot snapshot
- You need backup for pod-mounted volumes where snapshot integration is not practical

### Limitations

Important limitations:

- Reads from the live mounted filesystem.
- Backup may not represent one exact point in time for highly active workloads.
- `hostPath` volumes are not supported.
- Volume must normally be mounted by a pod.
- Orphan PVCs without a running pod might not be backed up unless mounted by a staging pod.
- Large database files may take time because deduplication scanning can be expensive.
- Massive small files increase metadata overhead.
- Restore waits for PVC/PV binding before file restore can populate data.

### Opt-in approach

Annotate the pod template with the volume name.

Example Deployment patch:

```bash
oc -n prod-db patch deployment/postgresql --type merge -p '
{
  "spec": {
    "template": {
      "metadata": {
        "annotations": {
          "backup.velero.io/backup-volumes": "postgres-data"
        }
      }
    }
  }
}'
```

Here `postgres-data` must be the **pod volume name**, not the PVC name.

Check pod volume names:

```bash
oc get pod -n prod-db <pod-name> -o jsonpath='{.spec.volumes[*].name}'
```

Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: prod-db-fsb-kopia-optin-20260703
  namespace: openshift-adp
spec:
  includedNamespaces:
  - prod-db
  storageLocation: default
  snapshotVolumes: false
  ttl: 720h0m0s
```

### Opt-out/default approach

Back up all pod volumes by default using FSB:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: prod-db-fsb-kopia-default-20260703
  namespace: openshift-adp
spec:
  includedNamespaces:
  - prod-db
  storageLocation: default
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
  ttl: 720h0m0s
```

Exclude a specific pod volume:

```bash
oc -n prod-db annotate pod/<pod-name> \
  backup.velero.io/backup-volumes-excludes=cache,tmp \
  --overwrite
```

### Verify FSB backup

```bash
oc get podvolumebackups -n openshift-adp
oc get podvolumebackups -n openshift-adp -l velero.io/backup-name=prod-db-fsb-kopia-default-20260703
oc describe podvolumebackup -n openshift-adp <name>
```

### Restore from FSB backup

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-prod-db-fsb
  namespace: openshift-adp
spec:
  backupName: prod-db-fsb-kopia-default-20260703
```

Monitor:

```bash
oc get podvolumerestores -n openshift-adp
oc describe podvolumerestore -n openshift-adp <name>
oc get pvc,pod -n prod-db
```

## 3.4 Method 4 — Legacy Restic File-System Backup

Restic was historically used by Velero/OADP for file-system backup. Modern OADP guidance is to prefer Kopia. In newer OADP/platform combinations, Restic is deprecated or removed.

### Senior guidance

For current production design:

```text
Prefer Kopia over Restic.
```

Use Restic only if:

- Your installed OADP version still supports it.
- You are maintaining an older cluster.
- You have validated restore behavior.
- You have an upgrade/migration plan to Kopia.

Do not design new OpenShift backup standards around Restic unless your enterprise support matrix explicitly requires it.

## 4. Choosing the Correct PV Backup Method

### Decision table

| Requirement | Recommended method |
|---|---|
| Fast rollback in same storage platform | CSI snapshot |
| DR after cluster loss | CSI Snapshot Data Mover |
| Cross-cluster migration | CSI Snapshot Data Mover if storage-compatible; otherwise FSB/Kopia |
| NFS/RWX without CSI snapshots | FSB/Kopia |
| Database requiring strong consistency | App-native backup + OADP metadata/PV backup |
| Large block volume | CSI Snapshot Data Mover |
| Massive small files | Test both Data Mover and FSB; tune resources |
| PVC not mounted by a pod | CSI snapshot or mount via staging pod for FSB |
| Long-term retention | Data Mover or FSB to object storage |
| Same-cloud snapshot retention only | CSI snapshot may be enough |
| Multi-region/multi-cloud DR | Data Mover to replicated object storage |

### Recommended enterprise standard

For most advanced OpenShift environments:

```text
Default for important PVCs: CSI Snapshot Data Mover with Kopia
Fallback: File System Backup with Kopia
Special case: Application-native database backup for consistency-critical systems
Avoid: New Restic designs
```

## 5. Backup Consistency: Crash-Consistent vs Application-Consistent

### Crash-consistent backup

A crash-consistent backup is equivalent to pulling power from a server and then booting it from disk.

Most CSI snapshots are crash-consistent by default.

Good enough for:

- Many stateless-plus-cache applications
- Some journaling filesystems
- Applications that recover cleanly after restart
- Non-critical file stores

Risky for:

- Databases with active writes
- Message queues
- Search indexes
- Applications with multi-volume consistency requirements

### Application-consistent backup

Application-consistent backup coordinates with the application before the snapshot or file backup.

Examples:

- PostgreSQL checkpoint or `pg_start_backup`/`pg_basebackup`
- MySQL flush tables with read lock, backup lock, or native backup tool
- MongoDB fsync lock or replica-set-aware backup
- Elasticsearch snapshot API
- Kafka topic replication and broker-aware backup design
- Redis RDB/AOF persistence coordination

### OADP backup hooks

Velero/OADP supports backup hooks that execute commands inside containers before or after backup operations.

Example concept:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: postgres-consistent-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
  - prod-db
  hooks:
    resources:
    - name: postgres-checkpoint
      includedNamespaces:
      - prod-db
      labelSelector:
        matchLabels:
          app: postgresql
      pre:
      - exec:
          container: postgresql
          command:
          - /bin/sh
          - -c
          - "psql -U postgres -c 'CHECKPOINT;'"
          timeout: 30s
          onError: Fail
  snapshotVolumes: true
  snapshotMoveData: true
  datamover: velero
  itemOperationTimeout: 8h
```

> Do not blindly copy database hook commands into production. Validate database user, permissions, replication mode, backup mode, timeout, and recovery procedure.

### Senior recommendation for databases

For serious databases, combine:

```text
Database-native backup + OADP backup of Kubernetes objects + optional PV snapshot
```

Example:

- PostgreSQL: WAL archiving + base backup + OADP for manifests and PVC snapshot
- MySQL: xtrabackup/mysqlbackup + binlogs + OADP for manifests
- MongoDB: mongodump/ops-manager/cloud-manager backup + OADP for manifests
- Elasticsearch: snapshot repository + OADP for manifests

OADP restores the platform shape. Database-native backup gives transaction consistency.

## 6. Production Backup Design Pattern

### 6.1 Backup classes

Create backup classes based on workload criticality.

| Class | Example workload | Frequency | Method | Retention |
|---|---|---:|---|---:|
| Platinum | Payment DB, identity DB | Hourly + native DB backup | Native + CSI Data Mover | 30–90 days |
| Gold | Business app DB | 4-hourly / daily | CSI Data Mover | 30 days |
| Silver | File store, reports | Daily | FSB/Kopia or Data Mover | 14–30 days |
| Bronze | Dev/test | Daily/weekly | FSB/Kopia or snapshot | 7 days |
| No backup | Cache/temp | None | Exclude | 0 |

### 6.2 Label-based backup selection

Label namespaces:

```bash
oc label namespace prod-db backup-tier=gold --overwrite
oc label namespace prod-app backup-tier=gold --overwrite
oc label namespace dev-tools backup-tier=bronze --overwrite
```

Backup CR using label selector:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: gold-namespaces-csi-datamover
  namespace: openshift-adp
spec:
  labelSelector:
    matchLabels:
      backup-tier: gold
  storageLocation: default
  snapshotVolumes: true
  snapshotMoveData: true
  datamover: velero
  ttl: 720h0m0s
```

### 6.3 Schedule CR

Daily schedule:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: gold-daily-csi-datamover
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    labelSelector:
      matchLabels:
        backup-tier: gold
    storageLocation: default
    snapshotVolumes: true
    snapshotMoveData: true
    datamover: velero
    csiSnapshotTimeout: 20m
    itemOperationTimeout: 8h
    ttl: 720h0m0s
```

Check schedules:


## 7. StorageClass and VolumeSnapshotClass Considerations

### 7.1 StorageClass check

```bash
oc get storageclass
oc describe storageclass <storageclass-name>
```

Look for:

- CSI provisioner name
- Reclaim policy
- Volume binding mode
- Expansion support
- Parameters

Example:

```bash
oc get sc -o custom-columns=NAME:.metadata.name,PROVISIONER:.provisioner,RECLAIM:.reclaimPolicy,BINDING:.volumeBindingMode
```

### 7.2 Match VolumeSnapshotClass driver to StorageClass provisioner

Example:

```bash
oc get storageclass ocs-storagecluster-ceph-rbd -o jsonpath='{.provisioner}'
```

Output:

```text
openshift-storage.rbd.csi.ceph.com
```

Your `VolumeSnapshotClass.driver` must match:

```yaml
driver: openshift-storage.rbd.csi.ceph.com
```

### 7.3 Deletion policy

For backup scenarios, `Retain` is commonly safer than `Delete` because the backend snapshot is not deleted immediately when the Kubernetes snapshot object is removed.

But you must understand the lifecycle:

- `Retain` can leave storage snapshots behind.
- `Delete` can clean up snapshots automatically but may remove recovery points if configured incorrectly.
- CSI Data Mover may clean up temporary snapshots after movement, depending on behavior and version.

Senior admin rule:

```text
Do not set snapshot deletion policy without understanding restore and cleanup behavior.
```

## 8. Restore Behavior for PVs and PVCs

Restore behavior depends on how the backup was taken.

### 8.1 Restore from storage snapshot

Velero/OADP restores PVC/PV data using the snapshot provider or CSI driver.

Typical behavior:

```text
Backup metadata -> VolumeSnapshot -> PVC datasource -> CSI driver creates new volume -> Pod mounts restored volume
```

### 8.2 Restore from CSI Snapshot Data Mover

Typical behavior:

```text
Restore CR
  -> DataDownload created
  -> Empty/new volume provisioned
  -> Data mover pod downloads data from Kopia repository
  -> PVC becomes usable
  -> Workload starts
```

### 8.3 Restore from File System Backup

Typical behavior:

```text
Restore CR
  -> PVC object restored
  -> StorageClass dynamically provisions PV
  -> Pod restore/init helper restores files into mounted volume
  -> Pod starts normally
```

### 8.4 Restore to different StorageClass

Velero can use a storage class mapping ConfigMap during restore.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: change-storage-class-config
  namespace: openshift-adp
  labels:
    velero.io/plugin-config: ""
    velero.io/change-storage-class: RestoreItemAction
data:
  ocs-storagecluster-ceph-rbd: gp3-csi
```

Use case:

```text
Source cluster: ODF RBD
Target cluster: AWS EBS gp3 CSI
```

Be careful. Storage class mapping does not magically convert incompatible volume semantics. Access mode, filesystem mode, block mode, expansion, and application expectations must be validated.

## 10. Troubleshooting PV Backup Failures

---

## 10.1 Backup stuck in `InProgress` or `WaitingForPluginOperations`

Check:

```bash
oc describe backup -n openshift-adp <backup-name>
oc logs deployment/velero -n openshift-adp
oc get datauploads -n openshift-adp
oc describe dataupload -n openshift-adp <dataupload-name>
```

Likely causes:

- DataUpload still running
- CSI snapshot not ready
- Temporary PVC pending
- Data mover pod unschedulable
- Object storage slow/unreachable
- Repository not ready
- Item operation timeout too low
- Storage backend snapshot operation slow

Fixes:

- Increase `itemOperationTimeout`
- Increase `csiSnapshotTimeout`
- Check node capacity
- Check object storage endpoint and credentials
- Check CSI driver logs
- Check VolumeSnapshotClass
- Check node-agent pods

---

## 10.2 PVC data skipped

Check backup details:

```bash
velero backup describe <backup-name> --details
```

Check logs:

```bash
oc logs deployment/velero -n openshift-adp | grep -i "skipped\|volume\|snapshot\|pvc"
```

Common causes:

- `snapshotVolumes: false`
- No FSB annotation
- `defaultVolumesToFsBackup` not enabled
- VolumeSnapshotClass missing or not labeled
- Unsupported volume type
- PVC not mounted by a pod for FSB
- CSI plugin not enabled
- Node agent disabled

---

## 10.3 No VolumeSnapshot created

Check:

```bash
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get volumesnapshotcontent
oc get backup -n openshift-adp <backup-name> -o yaml
```

Common causes:

- CSI plugin not enabled in DPA
- Wrong snapshot class driver
- Missing Velero label on VolumeSnapshotClass
- Multiple snapshot classes labeled for same driver
- PVC uses non-CSI provisioner
- Volume mode unsupported by snapshot driver

---

## 10.4 DataUpload failed

Check:

```bash
oc get datauploads -n openshift-adp
oc describe dataupload -n openshift-adp <name>
oc get pods -n openshift-adp -o wide
oc logs -n openshift-adp <data-mover-pod-name>
oc logs -n openshift-adp <node-agent-pod-name>
```

Common causes:

- Object storage credentials invalid
- S3 endpoint unreachable
- TLS/CA issue with object storage
- Temporary PVC cannot bind
- Data mover pod cannot mount snapshot volume
- Insufficient CPU/memory/ephemeral storage
- NetworkPolicy blocks egress
- Storage driver cannot create volume from snapshot

---

## 10.5 PodVolumeBackup failed

Check:

```bash
oc get podvolumebackups -n openshift-adp
oc describe podvolumebackup -n openshift-adp <name>
oc logs -n openshift-adp <node-agent-pod-name>
```

Common causes:

- Pod not running
- Volume not mounted
- Wrong volume name in annotation
- Permission issue reading files
- Massive file count causes timeout
- Node-agent not running on the same node
- HostPath not supported

---

## 10.6 Restore stuck because PVC is Pending

Check:

```bash
oc get pvc -n <restore-namespace>
oc describe pvc -n <restore-namespace> <pvc-name>
oc get events -n <restore-namespace> --sort-by=.lastTimestamp
```

Common causes:

- StorageClass missing in target cluster
- StorageClass name differs between source and target
- AccessMode unsupported
- Requested size unsupported
- VolumeBindingMode `WaitForFirstConsumer` waiting for pod scheduling
- Node topology mismatch
- Quota prevents PVC creation

Fix:

- Create storage class mapping ConfigMap
- Restore required StorageClass if appropriate
- Adjust quotas
- Ensure worker nodes satisfy topology
- Restore namespace/project permissions

---

## 10.7 Restore completes but application data missing

Check:

```bash
oc describe restore -n openshift-adp <restore-name>
oc get podvolumerestores -n openshift-adp
oc get datadownloads -n openshift-adp
oc logs deployment/velero -n openshift-adp
```

Common causes:

- Backup captured only PVC object, not PV data
- FSB annotation wrong
- Snapshot did not include the PVC
- Restore excluded PVC/PV resources
- Namespace mapping issue
- Application mounted different path/volume name
- Init container or application overwrote restored data

## 11. Performance Tuning for PV Backups

### 11.1 Factors affecting backup speed

Backup speed depends on:

- Storage backend snapshot performance
- PVC size
- Changed data size
- Number of files
- Average file size
- Object storage latency
- Network bandwidth
- Node CPU and memory
- Data mover pod scheduling
- CSI driver performance
- Deduplication overhead
- Compression/encryption overhead

### 11.2 Large database files

Large database files can be challenging for FSB/Kopia because deduplication must scan large files. CSI Snapshot Data Mover is often better, but still test actual performance.

Recommendation:

```text
For large databases, rely on database-native incremental/WAL/binlog backup for RPO and use OADP for infrastructure/application recovery.
```

### 11.3 Massive small files

Massive small files increase metadata overhead.

Examples:

- Artifact repositories
- Maven/NPM caches
- Git repositories
- Image layers
- User upload directories

Recommendations:

- Consider application-level backup/export
- Tune data mover pod resources
- Avoid backing up cache directories
- Exclude temporary volumes
- Run backup outside peak IO window

### 11.4 Concurrency

Data movement can process multiple volumes in parallel depending on node placement, data mover behavior, and node-agent configuration.

Check where operations are running:

```bash
oc get datauploads -n openshift-adp -o wide
oc get datadownloads -n openshift-adp -o wide
```

If many DataUploads queue on one node, review:

- Pod topology
- Storage topology
- Worker node capacity
- Node-agent concurrency settings supported by your OADP/Velero version
- Data mover resource configuration

### 11.5 Backup windows

Avoid running all namespace backups at the same time.

Better:

```text
01:00 critical DB namespace
01:30 app namespaces
02:00 reporting namespace
02:30 dev/test namespace
```

This reduces:

- Object storage burst load
- CSI snapshot API burst
- Worker node IO pressure
- Network bottleneck
- Repository lock contention

## 12. Security Design

### 12.1 Object storage security

Use:

- Dedicated bucket/container per cluster or environment
- Least-privilege IAM user/service account
- Bucket encryption
- TLS endpoint
- Private endpoint if available
- Object versioning
- Object lock / immutability for ransomware protection
- Lifecycle rules aligned with backup TTL
- Access logging

### 12.2 Credential security

Credentials usually live in a Kubernetes Secret in `openshift-adp`.

Check:

```bash
oc get secret -n openshift-adp
```

Do not store broad admin cloud credentials. Use a dedicated credential limited to required backup bucket and snapshot APIs.

### 12.3 RBAC

Limit who can create or restore backups.

A restore can recreate:

- Secrets
- Routes
- Workloads
- PVC data
- ServiceAccounts
- RBAC bindings

Treat restore permission as highly privileged.

### 12.4 Backup data encryption

Even if the object store encrypts data at rest, protect:

- Access keys
- Bucket policy
- Network path
- Backup repository credentials
- Restore permissions

Also validate encryption behavior of your specific OADP/Velero version and repository configuration.

## 13. Backup Exclusions

Not all volumes should be backed up.

Exclude:

- Cache directories
- Temporary files
- Build artifacts that can be regenerated
- `emptyDir` unless really needed
- Logs already shipped to logging platform
- Application scratch space

Example FSB exclude annotation:

```bash
oc -n prod-app annotate pod/<pod-name> \
  backup.velero.io/backup-volumes-excludes=cache,tmp \
  --overwrite
```

For resource exclusion, label objects:

```bash
oc label configmap temp-config velero.io/exclude-from-backup=true -n prod-app
```

## 17. Common Production Mistakes

### Mistake 1 — Backing up only PVC YAML

Symptom:

```text
Restore creates empty PVC.
```

Cause:

```text
PV data was never backed up.
```

Fix:

```text
Use snapshotVolumes, snapshotMoveData, or defaultVolumesToFsBackup/annotations.
```

---

### Mistake 2 — Missing VolumeSnapshotClass label

Symptom:

```text
No CSI snapshot is created.
```

Fix:

```yaml
metadata:
  labels:
    velero.io/csi-volumesnapshot-class: "true"
```

---

### Mistake 3 — Multiple snapshot classes labeled for same driver

Symptom:

```text
Wrong snapshot class selected or backup fails.
```

Fix:

```text
Use only one labeled VolumeSnapshotClass per CSI driver.
```

---

### Mistake 4 — Using FSB for a busy database without hooks

Symptom:

```text
Database starts with corruption or recovery issues.
```

Fix:

```text
Use DB-native backup, backup hooks, or CSI snapshot with application quiescing.
```

---

### Mistake 5 — No restore test

Symptom:

```text
Backup looked successful but restore fails during real incident.
```

Fix:

```text
Run scheduled restore drills into isolated namespaces/clusters.
```

---

### Mistake 6 — Object storage lifecycle deletes backup data too early

Symptom:

```text
Backup metadata exists but volume repository data is missing.
```

Fix:

```text
Align object storage lifecycle with Velero backup TTL and repository maintenance.
```

---

### Mistake 7 — StorageClass missing on target cluster

Symptom:

```text
PVC Pending after restore.
```

Fix:

```text
Create equivalent StorageClass or use storage class mapping.
```

## 19. Interview-Level Explanation

If asked: **How do you back up persistent volumes in OADP?**

A strong 10-year-experience answer:

> In OADP, I do not treat PVC YAML as data backup. I first classify the workload and storage backend. If the PVC is CSI-backed and the driver supports snapshots, I configure a proper VolumeSnapshotClass with the Velero CSI label and enable the CSI plugin in the DataProtectionApplication. For real DR, I prefer CSI Snapshot Data Mover with Kopia because the snapshot data is moved to object storage instead of relying only on storage-local snapshots. For non-snapshot volumes like some NFS/RWX workloads, I use File System Backup with Kopia through node-agent, either opt-in annotations or defaultVolumesToFsBackup. For databases, I combine OADP with application-native backup or Velero hooks because snapshots are usually crash-consistent, not transaction-consistent. I validate by checking Backup, DataUpload, PodVolumeBackup, BackupRepository, VolumeSnapshot, and restore into an isolated namespace. I also test StorageClass mapping, object storage lifecycle, and restore performance regularly.

## 22. Senior Design Recommendation

For enterprise OpenShift PV backup, use this model:

```text
1. CSI Snapshot Data Mover with Kopia for CSI-backed critical PVCs.
2. File System Backup with Kopia for volumes without snapshot support.
3. Application-native backup for databases and consistency-critical workloads.
4. Object storage with encryption, immutability, lifecycle controls, and replication.
5. Scheduled restore testing as part of operations, not only during incidents.
```

The real measure of backup maturity is not backup success. It is:

```text
Can you restore the correct data, to the correct namespace or cluster, within the required RTO, at the required RPO, under pressure?
```

## 24. Final Practical Summary

Persistent volume backup in OADP is not one feature; it is a design decision involving storage capability, consistency requirement, restore target, backup repository, and business RPO/RTO.

For a senior OpenShift administrator:

```text
If CSI snapshot is available and DR matters, use CSI Snapshot Data Mover with Kopia.
If snapshot is unavailable, use File System Backup with Kopia.
If the workload is a real database, add application-native backup or validated hooks.
Always test restore.
```
