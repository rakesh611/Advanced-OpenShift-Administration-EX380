## 1. Executive Summary

Velero is the upstream Kubernetes backup and restore engine used by OpenShift APIs for Data Protection, commonly called OADP. In OpenShift, OADP packages, configures, and supports Velero through the OADP Operator and adds OpenShift-specific integrations such as OpenShift resource backup plugins, internal image handling, CSI snapshot support, OpenShift Virtualization support, and DataProtectionApplication-based deployment.

For an advanced OpenShift administrator, the most important concept is this:

> **OADP protects applications and application-related resources. It is not a replacement for etcd backup, full OpenShift cluster recovery, or Operator lifecycle recovery.**

A production OADP design must answer these questions:

- Which namespaces and applications are protected?
- Which cluster-scoped objects are required for those applications?
- Where are Kubernetes object backups stored?
- How are persistent volumes protected?
- Is the backup crash-consistent or application-consistent?
- What is the RPO and RTO?
- Can the backup be restored into a new namespace, new cluster, or new storage class?
- Are backups tested regularly?
- Are object storage credentials, CA trust, retention, and immutability handled correctly?

At a high level:

- **Backup CR** tells Velero what to back up.
- **Restore CR** tells Velero what backup to restore.
- **Schedule CR** creates backups on a cron schedule.
- **BackupStorageLocation / BSL** defines object storage for metadata, logs, and backup archives.
- **VolumeSnapshotLocation / VSL** defines where cloud-provider volume snapshots are created.
- **DataProtectionApplication / DPA** is the OADP operator-managed installation and configuration object.
- **Node Agent** performs file system backup and data movement work.
- **Kopia** is commonly used as the uploader/repository mechanism for modern OADP/Velero data movement.
- **Restic** exists in older designs and legacy references, but Kopia/node-agent-based workflows are preferred in newer OADP patterns.

## 2. What OADP and Velero Are

### 2.1 Velero

Velero is an open-source Kubernetes backup, restore, and migration tool. It backs up Kubernetes API objects and can also protect persistent volume data using snapshots, CSI snapshots, file system backup, or data movement depending on configuration and storage support.

Velero is useful for:

- Application disaster recovery
- Namespace-level restore
- Migration between Kubernetes/OpenShift clusters
- Replicating production workloads into test clusters
- Recovering deleted application resources
- Restoring PVC-backed workloads
- Creating scheduled backup policies

Velero normally consists of:

- A server running inside the cluster
- CRDs such as `Backup`, `Restore`, and `Schedule`
- A local or in-cluster CLI
- Plugins for object storage and snapshot providers
- Optional node-level components for volume data operations

### 2.2 OADP

OADP is Red Hat's OpenShift-supported distribution and operator integration for Velero-based data protection.

OADP provides:

- OADP Operator
- `DataProtectionApplication` CR
- Velero deployment in `openshift-adp`
- Default plugins for providers and OpenShift resources
- CSI snapshot integration
- OpenShift-specific restore/backup behavior
- Supportable lifecycle through Red Hat Operator channels
- Integration with S3-compatible object storage
- Workload-oriented backup and restore APIs

In OpenShift, do not think of OADP as just “install Velero manually.” Think of it as:

> **Operator-managed Velero + OpenShift plugins + supported CRDs + OpenShift-specific operational model.**

## 3. What OADP Is Not

This is very important in real environments and interviews.

OADP is **not** a full cluster backup tool.

OADP does **not** replace:

- OpenShift etcd backup
- Control plane disaster recovery procedure
- Infrastructure backup
- Storage backend replication
- GitOps source of truth
- Operator lifecycle backup
- Full cluster bare-metal recovery
- Complete OpenShift upgrade rollback

### 3.1 Not an etcd backup replacement

OpenShift etcd backup protects the cluster control-plane state. OADP protects selected workload resources and persistent data. These solve different problems.

Use etcd backup for:

- Control plane disaster recovery
- Cluster-level corruption recovery
- Restoring the OpenShift cluster itself

Use OADP for:

- Application namespace restore
- Application migration
- PVC restore
- Accidental deletion recovery
- Workload-level disaster recovery

### 3.2 Not an Operator backup solution

Many Operators manage external systems or reconcile resources from their own state. Backing up an Operator namespace does not guarantee the operator-managed application will restore correctly.

Example:

- Backing up an application CR may not back up the external database it points to.
- Backing up an Operator deployment may not preserve catalog/operator lifecycle behavior.
- Backing up all Operator namespaces can restore unwanted cluster internals and cause conflicts.

Best practice:

- Reinstall Operators through GitOps/OLM.
- Back up application CRs and namespaces selectively.
- Understand each Operator's backup/restore procedure.

### 3.3 Not automatically application-consistent

A snapshot or file system backup may be crash-consistent, not application-consistent.

For databases and stateful applications, you may need:

- Database-native dump
- Pre/post Velero hooks
- Quiesce/freeze/unfreeze steps
- Storage-level consistency groups
- Operator-native backup APIs
- Application-level restore verification

## 4. Core Architecture

A typical OADP architecture looks like this:

```text
+---------------------------------------------------------------+
|                    OpenShift Cluster                          |
|                                                               |
|  +---------------------+                                      |
|  | OADP Operator        |                                      |
|  | namespace: openshift-adp                                   |
|  +----------+----------+                                      |
|             | reconciles                                      |
|             v                                                 |
|  +---------------------+        +---------------------------+  |
|  | DataProtectionApp   | -----> | Velero Deployment         |  |
|  | DPA CR              |        | Velero server/controllers |  |
|  +---------------------+        +-------------+-------------+  |
|                                              |                |
|             +--------------------------------+                |
|             |                                                 |
|             v                                                 |
|  +---------------------+        +---------------------------+  |
|  | Backup/Restore/     |        | Node Agent DaemonSet      |  |
|  | Schedule CRs        |        | Kopia/Data movement       |  |
|  +---------------------+        +-------------+-------------+  |
|                                              |                |
|                                              v                |
|                                +----------------------------+ |
|                                | PV/PVC data movement       | |
|                                | snapshots / fs backup      | |
|                                +----------------------------+ |
|                                                               |
+-------------------------+-------------------------------------+
                          |
                          v
+---------------------------------------------------------------+
| External or in-cluster S3-compatible object storage            |
| AWS S3 / ODF NooBaa / Ceph RGW / MinIO / other supported S3    |
+---------------------------------------------------------------+
```

### 4.1 Namespace

OADP is usually installed in:

```bash
openshift-adp
```

Most Velero CRs are created in this namespace:

```bash
oc get backup -n openshift-adp
oc get restore -n openshift-adp
oc get schedules -n openshift-adp
oc get backupstoragelocations -n openshift-adp
oc get volumesnapshotlocations -n openshift-adp
```

### 4.2 Object storage is mandatory

Velero needs object storage for:

- Kubernetes resource backup archive
- Backup logs
- Restore logs
- Metadata
- Some volume data backups when using file system backup or data mover

Object storage examples:

- AWS S3
- S3-compatible endpoint
- OpenShift Data Foundation NooBaa / Multicloud Object Gateway
- Ceph RADOS Gateway
- MinIO
- Azure Blob through supported plugin
- Google Cloud Storage through supported plugin

### 4.3 Snapshot storage depends on storage provider

For PV snapshots, Velero needs one of these:

- Native cloud snapshot API
- CSI driver with snapshot support
- VolumeSnapshotClass
- OADP/Velero CSI plugin
- Optional data mover to move snapshots to object storage

## 5. Main Velero and OADP Components

### 5.1 OADP Operator

The OADP Operator manages the lifecycle of the data protection stack.

It handles:

- Installing Velero
- Deploying required plugins
- Creating or reconciling default BSL/VSL objects
- Managing node-agent configuration
- Handling DPA status
- Creating supporting secrets/configuration

Check operator installation:

```bash
oc get csv -n openshift-adp
oc get subscription -n openshift-adp
oc get pods -n openshift-adp
```

### 5.2 DataProtectionApplication

`DataProtectionApplication` is the main OADP configuration CR.

It defines:

- Which Velero plugins to enable
- Backup storage locations
- Volume snapshot locations
- Node agent settings
- Uploader type such as `kopia`
- Whether default snapshot data movement is enabled
- Provider-specific settings

Example check:

```bash
oc get dpa -n openshift-adp
oc describe dpa <dpa-name> -n openshift-adp
oc get dpa <dpa-name> -n openshift-adp -o yaml
```

A healthy DPA should show reconciled/ready conditions.

### 5.3 Velero server

The Velero server is the controller process that watches Velero CRs and performs backup/restore operations.

Check it:

```bash
oc get deploy -n openshift-adp
oc get pods -n openshift-adp -l deploy=velero
oc logs -n openshift-adp deploy/velero
```

The Velero server watches CRs such as:

- `Backup`
- `Restore`
- `Schedule`
- `BackupStorageLocation`
- `VolumeSnapshotLocation`
- `DeleteBackupRequest`
- `DataUpload`
- `DataDownload`
- `PodVolumeBackup`
- `PodVolumeRestore`

### 5.4 Velero plugins

Plugins extend Velero behavior.

Common plugin categories:

- Object store plugins
- Snapshot plugins
- CSI plugin
- OpenShift plugin
- OpenShift Virtualization plugin
- Custom enterprise storage plugins

Provider plugins allow Velero to communicate with cloud/object/snapshot providers.

Examples:

- `aws`
- `azure`
- `gcp`
- `openshift`
- `csi`
- `kubevirt`

### 5.5 Node Agent

The node agent is a DaemonSet running on cluster nodes. It handles volume-level data movement for file system backup and CSI snapshot data movement.

It is important for:

- File System Backup
- Kopia-based backup/restore
- CSI Data Mover
- DataUpload/DataDownload processing
- Backup repository interaction

Check it:

```bash
oc get ds -n openshift-adp
oc get pods -n openshift-adp -l name=node-agent
oc logs -n openshift-adp ds/node-agent
```

### 5.6 Kopia

Kopia is a backup repository/uploader technology used by modern Velero/OADP workflows. It supports efficient upload/download of volume contents to object storage.

In OADP, Kopia is commonly used with:

- Node agent
- File system backup
- CSI snapshot data movement
- Backup repositories

### 5.7 Restic

Restic was used in older Velero volume backup workflows. Many older documents still mention Restic. In newer OADP/Velero versions, node-agent + Kopia is commonly preferred.

As an administrator, know both terms:

- **Restic:** legacy/common older file system backup mechanism
- **Kopia:** modern uploader/repository mechanism used in newer data movement workflows

## 7. BackupStorageLocation Concept

A `BackupStorageLocation` or BSL defines where Velero stores backup metadata and backup archives.

Think of BSL as:

> **The object storage destination for Velero backup files.**

It normally points to an S3 bucket or compatible object storage.

### 7.1 What is stored in BSL?

A BSL can store:

- Kubernetes resource manifests
- Backup metadata
- Backup logs
- Restore logs
- Plugin metadata
- Volume backup data when using file system backup/data mover
- Backup repository data depending on configuration

### 7.2 BSL health

Check BSL:

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation <bsl-name> -n openshift-adp
```

Expected phase:

```text
Available
```

Common bad phases:

- `Unavailable`
- `Unknown`
- no phase updated

### 7.3 Common BSL problems

| Problem | Symptoms | Root Cause |
|---|---|---|
| Wrong S3 endpoint | Backup fails to upload | Incorrect endpoint URL |
| Wrong bucket | BSL unavailable | Bucket missing or access denied |
| Invalid credentials | 403 / AccessDenied | Secret incorrect |
| TLS trust issue | x509 error | Missing CA certificate |
| Network issue | timeout | No route/proxy/firewall/DNS issue |
| Wrong region | AWS S3 error | Region mismatch |
| ReadOnly mode | Backup cannot write | BSL configured read-only |

### 7.4 BSL design points

For production:

- Use highly durable object storage.
- Enable versioning where possible.
- Enable object lock/immutability where required.
- Use least privilege credentials.
- Separate backup buckets per environment.
- Use prefix per cluster.
- Use lifecycle retention policies.
- Test restore from the same BSL in a separate cluster.

### 7.5 ReadOnly BSL

For migration or DR target clusters, you may configure BSL as read-only so the target cluster can discover backups without modifying source backup data.

Use case:

```text
Cluster A writes backups to S3.
Cluster B reads backups from S3 for restore/migration.
Cluster B BSL should be read-only to avoid accidental deletion or modification.
```

## 8. VolumeSnapshotLocation Concept

A `VolumeSnapshotLocation` or VSL defines where Velero creates provider-native volume snapshots.

Think of VSL as:

> **The provider snapshot location for persistent volumes.**

Examples:

- AWS EBS snapshots in a region
- Azure managed disk snapshots
- GCP persistent disk snapshots
- CSI-based snapshot integrations, depending on configuration

### 8.1 VSL vs BSL

| Area | BSL | VSL |
|---|---|---|
| Stores Kubernetes object backup | Yes | No |
| Stores logs/metadata | Yes | No |
| Stores volume data through FSB/data mover | Yes | No/indirect |
| Creates provider snapshots | No | Yes |
| Object storage bucket | Yes | No |
| Snapshot provider location | No | Yes |

### 8.2 Check VSL

```bash
oc get volumesnapshotlocation -n openshift-adp
oc describe volumesnapshotlocation <vsl-name> -n openshift-adp
```

### 8.3 VSL and CSI

With CSI snapshots, the real storage behavior depends heavily on:

- CSI driver support
- `VolumeSnapshotClass`
- Snapshot controller
- Storage backend capabilities
- Whether snapshots are local to the same cluster/storage system
- Whether data mover is enabled to copy snapshot data to object storage

## 9. DataProtectionApplication Concept

The `DataProtectionApplication` or DPA is the central OADP configuration object.

A DPA tells the OADP Operator:

- Deploy Velero
- Enable these plugins
- Use this object storage
- Use this credential
- Enable or disable node agent
- Use Kopia or another uploader type
- Configure backup and volume locations
- Configure data mover behavior

### 9.1 Minimal mental model

```text
DPA -> OADP Operator -> Velero Deployment + Plugins + BSL/VSL + Node Agent
```

### 9.2 DPA health checks

```bash
oc get dpa -n openshift-adp
oc describe dpa <name> -n openshift-adp
oc get dpa <name> -n openshift-adp -o jsonpath='{.status.conditions}' | jq
```

Look for:

- `Reconciled=True`
- successful Velero deployment
- BSL created
- pods running

### 9.3 DPA with S3-compatible storage and CSI/nodeAgent

Example pattern:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: oadp-dpa
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
      defaultSnapshotMoveData: true
    nodeAgent:
      enable: true
      uploaderType: kopia
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: oadp-backups
          prefix: cluster01
        credential:
          name: cloud-credentials
          key: cloud
        config:
          region: us-east-1
          s3Url: https://s3.example.com
          s3ForcePathStyle: "true"
  snapshotLocations:
    - name: default
      velero:
        provider: aws
        config:
          region: us-east-1
```

> Adjust fields based on your exact OADP version, provider, and Red Hat documentation. DPA schema can change across OADP versions.

## 10. Backup Concept

A `Backup` CR requests Velero to back up selected Kubernetes resources and associated volume data.

### 10.1 Backup answers these questions

- Which namespaces?
- Which resource types?
- Which labels?
- Should cluster-scoped resources be included?
- Should PVs be snapshotted/restored?
- Which BSL stores the backup?
- Which VSL stores snapshots?
- What is the TTL?
- Are hooks required?
- Should file system backup be used?
- Should CSI snapshot data be moved to object storage?

### 10.2 Simple namespace backup

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: nginx-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - nginx-prod
  storageLocation: default
  ttl: 720h0m0s
```

### 10.3 Backup with label selector

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app1-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  labelSelector:
    matchLabels:
      app: app1
  storageLocation: default
  ttl: 720h0m0s
```

### 10.4 Backup with CSI snapshot data movement

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: pg-backup-csi-datamover
  namespace: openshift-adp
spec:
  includedNamespaces:
    - postgresql
  storageLocation: default
  snapshotMoveData: true
  ttl: 720h0m0s
```

### 10.5 Backup with file system backup

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-fs-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  defaultVolumesToFsBackup: true
  storageLocation: default
  ttl: 720h0m0s
```

### 10.6 Backup phases

Common phases:

| Phase | Meaning |
|---|---|
| `New` | Backup CR created; controller has not started fully |
| `InProgress` | Backup is running |
| `WaitingForPluginOperations` | Plugin async operations are pending |
| `WaitingForPluginOperationsPartiallyFailed` | Some plugin operations failed while others continue |
| `Finalizing` | Velero is packaging and uploading final backup metadata |
| `FinalizingPartiallyFailed` | Finalizing with partial failures |
| `Completed` | Backup completed successfully |
| `PartiallyFailed` | Some resources/volumes failed |
| `Failed` | Backup failed |
| `Deleting` | Backup deletion in progress |

Check phase:

```bash
oc get backup -n openshift-adp
oc get backup <backup-name> -n openshift-adp -o jsonpath='{.status.phase}'
```

Describe:

```bash
oc describe backup <backup-name> -n openshift-adp
```

Logs:

```bash
velero backup logs <backup-name>
```

Or from in-cluster binary:

```bash
oc -n openshift-adp exec deploy/velero -- /velero backup logs <backup-name>
```

## 11. Restore Concept

A `Restore` CR tells Velero to restore resources from a backup.

### 11.1 Restore answers these questions

- Which backup should be restored?
- Restore into same namespace or mapped namespace?
- Restore all resources or selected resources?
- Restore PV data?
- Exclude problematic resources?
- Preserve NodePorts?
- What to do if resources already exist?
- Apply resource modifiers before restore?
- Run restore hooks?

### 11.2 Simple restore

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: nginx-restore
  namespace: openshift-adp
spec:
  backupName: nginx-backup
  restorePVs: true
```

### 11.3 Restore to a different namespace

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: nginx-restore-to-test
  namespace: openshift-adp
spec:
  backupName: nginx-backup
  restorePVs: true
  namespaceMapping:
    nginx-prod: nginx-test
```

### 11.4 Restore only selected resources

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-config-only
  namespace: openshift-adp
spec:
  backupName: app-prod-backup
  includedResources:
    - configmaps
    - secrets
    - services
    - routes.route.openshift.io
  restorePVs: false
```

### 11.5 Excluding resources during restore

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: app-restore-safe
  namespace: openshift-adp
spec:
  backupName: app-prod-backup
  restorePVs: true
  excludedResources:
    - nodes
    - events
    - events.events.k8s.io
    - backups.velero.io
    - restores.velero.io
    - resticrepositories.velero.io
```

### 11.6 Restore phases

Common phases:

| Phase | Meaning |
|---|---|
| `New` | Restore CR created |
| `InProgress` | Restore running |
| `WaitingForPluginOperations` | Plugin restore actions pending |
| `WaitingForPluginOperationsPartiallyFailed` | Partial plugin failures |
| `Completed` | Restore successful |
| `PartiallyFailed` | Restore completed with warnings/errors |
| `Failed` | Restore failed |

Check restore:

```bash
oc get restore -n openshift-adp
oc describe restore <restore-name> -n openshift-adp
oc -n openshift-adp exec deploy/velero -- /velero restore logs <restore-name>
```

### 11.7 Restore behavior with existing resources

By default, restores can fail or warn when a resource already exists. In production restore testing, always choose a clean namespace or use namespace mapping.

Safer test pattern:

```text
prod namespace: app-prod
restore namespace: app-prod-restore-test
```

Then verify:

```bash
oc get all -n app-prod-restore-test
oc get pvc -n app-prod-restore-test
oc get route -n app-prod-restore-test
```

## 12. Schedule Concept

A `Schedule` CR creates recurring backups using cron syntax.

### 12.1 Daily backup example

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: app-prod-daily
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
      - app-prod
    storageLocation: default
    ttl: 168h0m0s
```

This means:

```text
Run every day at 01:00 according to Velero/server timezone behavior.
Retain backup for 168 hours, i.e. 7 days.
```

### 12.2 Important scheduling rule

Do not schedule backups so frequently that a new backup starts before the previous backup completes.

Bad example:

```text
Backup takes 50 minutes, schedule runs every 30 minutes.
```

This creates:

- Queue buildup
- S3 load
- CSI snapshot pressure
- Data mover pod contention
- Increased partial failures

### 12.3 RPO mapping

| RPO Requirement | Example Schedule |
|---|---|
| 24 hours | Daily backup |
| 12 hours | Twice daily backup |
| 4 hours | Every 4 hours |
| 1 hour | Hourly backup, only if backup duration and storage can handle it |

## 13. Persistent Volume Backup Methods

Velero/OADP can protect persistent data in different ways.

### 13.1 Method comparison

| Method | What it does | Best for | Limitation |
|---|---|---|---|
| Kubernetes object backup only | Backs up PVC/PV manifests, not data | Stateless apps | No data recovery |
| Native cloud snapshot | Uses cloud snapshot API | EBS/Azure/GCP disks | Provider-specific, often same cloud/region constraints |
| CSI snapshot | Uses Kubernetes CSI snapshot API | CSI-capable storage | Snapshot may remain tied to same storage backend |
| CSI snapshot + data mover | Snapshots then copies data to object storage | DR, cross-cluster restore | More time/storage/network required |
| File System Backup | Reads mounted volume file system and uploads data | NFS/RWX/local/non-snapshot storage | Less consistent than snapshots; needs node-agent access |
| App-native backup | Uses database/app backup tools | Databases | Needs custom workflow |

### 13.2 Metadata backup vs data backup

If you back up a namespace without volume data, you may restore:

- Deployment
- Service
- Route
- ConfigMap
- Secret
- PVC object

But the PVC may not contain the original data.

For stateful apps, always validate:

```bash
oc describe backup <backup> -n openshift-adp
velero backup describe <backup> --details
velero backup logs <backup>
```

Look for:

- PV snapshot information
- PodVolumeBackup information
- DataUpload completion
- Warnings/errors for PVCs

## 14. CSI Snapshots

CSI snapshots use Kubernetes snapshot APIs and storage CSI driver support.

### 14.1 Required components

You need:

- CSI driver installed
- Snapshot controller installed by OpenShift/storage operator
- `VolumeSnapshotClass`
- PVC using a supported StorageClass
- OADP with CSI plugin enabled
- Backup configured to snapshot volumes

Check snapshot classes:

```bash
oc get volumesnapshotclass
```

Example:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ocs-storagecluster-rbdplugin-snapclass
  labels:
    velero.io/csi-volumesnapshot-class: "true"
driver: openshift-storage.rbd.csi.ceph.com
deletionPolicy: Retain
```

### 14.2 Important label

For Velero/OADP to choose the CSI snapshot class, label the correct `VolumeSnapshotClass`:

```bash
oc label volumesnapshotclass <snapshot-class-name> \
  velero.io/csi-volumesnapshot-class=true
```

### 14.3 CSI snapshot limitations

CSI snapshots are often tied to:

- Same storage backend
- Same storage cluster
- Same region/availability zone
- Same CSI driver
- Same `VolumeSnapshotClass`

This means CSI snapshot alone may not be enough for full disaster recovery if the entire storage backend is lost.

For stronger DR, use CSI snapshot data movement to object storage.

## 15. CSI Snapshot Data Movement / Data Mover

CSI Snapshot Data Movement copies snapshot data into object storage so it is not only stored as a provider-local snapshot.

### 15.1 Why Data Mover exists

Native/CSI snapshots are fast, but may be tied to the source storage system. If the storage backend is lost, the snapshot may also be lost.

Data Mover improves DR by:

- Creating a CSI snapshot
- Creating a temporary volume from the snapshot
- Launching a data mover pod
- Reading data from the temporary volume
- Uploading the data to object storage through Kopia/unified repository

During restore:

- Creates a target PVC/volume
- Launches a data mover pod
- Downloads data from object storage
- Writes data into the target volume

### 15.2 Data mover CRs

Common internal CRs:

```bash
oc get datauploads -n openshift-adp
oc get datadownloads -n openshift-adp
```

Check details:

```bash
oc describe dataupload <name> -n openshift-adp
oc describe datadownload <name> -n openshift-adp
```

### 15.3 When to use Data Mover

Use Data Mover when:

- You need cross-cluster restore.
- You need durable copy outside the storage backend.
- Storage snapshots alone are not enough for DR.
- You use OpenShift Data Foundation and want object-storage-backed backup data.
- You need VM/stateful workload protection across failure domains.

### 15.4 Trade-offs

| Benefit | Cost |
|---|---|
| Better DR portability | More object storage usage |
| Snapshot consistency plus object durability | Longer backup window |
| Can restore outside source storage backend | More network traffic |
| Useful for migration | More moving parts |

## 16. File System Backup, Node Agent, Kopia, and Restic

File System Backup backs up volume contents by reading files from the mounted volume and uploading them to backup storage.

### 16.1 When File System Backup is useful

Use it when:

- Storage does not support CSI snapshots.
- Application uses NFS/RWX volumes.
- Application uses local volumes.
- You need storage-provider-independent volume backup.
- You want data in object storage, not only snapshots.

### 16.2 Limitations

File System Backup:

- Reads live file system data.
- May not be application-consistent.
- Can be slower than snapshots.
- Needs node-agent access.
- May need privileged/root-level access depending on environment.
- Cannot fix application-level corruption.

### 16.3 Enabling file system backup in Backup CR

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: fs-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  defaultVolumesToFsBackup: true
  storageLocation: default
```

### 16.4 Pod annotation method

Instead of backing up all volumes by default, annotate specific pods/volumes.

Example annotation pattern:

```bash
oc annotate pod <pod-name> -n <namespace> \
  backup.velero.io/backup-volumes=<volume-name>
```

This is useful when only specific volumes need file-level backup.

### 16.5 Kopia vs Restic operational understanding

| Area | Kopia | Restic |
|---|---|---|
| Newer OADP direction | Yes | Legacy/common older references |
| Used by node-agent workflows | Yes | Older restic DaemonSet workflows |
| Supports unified repository direction | Yes | Older repository model |
| Seen in old docs/blogs | Less old docs | Many old docs |
| Admin action | Prefer current OADP docs | Understand for troubleshooting older clusters |

## 17. OpenShift-Specific Protection Concepts

OpenShift is Kubernetes plus many OpenShift APIs. OADP must understand resources that are not present in vanilla Kubernetes.

### 17.1 OpenShift resources often protected

Examples:

- `routes.route.openshift.io`
- `imagestreams.image.openshift.io`
- `buildconfigs.build.openshift.io`
- `deploymentconfigs.apps.openshift.io`
- `securitycontextconstraints.security.openshift.io` when application-specific
- `rolebindings.authorization.openshift.io`
- `projectrequests.project.openshift.io`
- OpenShift Virtualization resources when enabled

### 17.2 Routes

Routes can be restored, but DNS and certificates may need additional work.

Check after restore:

```bash
oc get route -n <namespace>
oc describe route <route> -n <namespace>
```

If restoring to a new cluster, verify:

- Ingress domain changed or same?
- TLS secret restored?
- External DNS points correctly?
- Certificate valid for new hostname?

### 17.3 ImageStreams

ImageStreams may reference internal registry images. OADP OpenShift plugins help with internal image backup/restore behavior, but you must verify:

```bash
oc get imagestream -n <namespace>
oc describe imagestream <name> -n <namespace>
```

Important considerations:

- Is the internal registry available?
- Are image pull secrets restored?
- Are image tags present?
- Is the target cluster allowed to pull the restored images?

### 17.4 SCCs and service accounts

If an application depends on special SCC access, backup/restore must preserve relevant service accounts and role bindings.

Check:

```bash
oc get sa -n <namespace>
oc get rolebinding -n <namespace>
oc adm policy who-can use scc/<scc-name>
```

Avoid blindly backing up all SCCs cluster-wide. Treat SCCs as platform policy managed by GitOps or cluster baseline automation.

### 17.5 Operators and CRDs

For operator-managed apps:

1. Install the Operator in the target cluster first.
2. Ensure CRDs exist before restore.
3. Restore application namespaces and CRs.
4. Let Operator reconcile.
5. Validate application-specific state.

Do not assume Velero restore alone installs the Operator correctly.

## 18. Backup Flow: What Happens Internally

When you create a `Backup` CR:

```bash
oc apply -f backup.yaml
```

Velero does roughly this:

1. Velero controller sees new `Backup` CR.
2. Validates backup spec.
3. Confirms BSL is available.
4. Discovers Kubernetes API resources.
5. Applies namespace/resource/label filters.
6. Executes backup item actions from plugins.
7. Backs up Kubernetes objects as JSON/YAML metadata.
8. Handles OpenShift-specific objects through plugins.
9. Handles PVs depending on backup method:
   - no data backup
   - native snapshot
   - CSI snapshot
   - CSI snapshot data movement
   - file system backup
10. Runs pre/post backup hooks if configured.
11. Writes backup archive and logs to object storage.
12. Updates backup status.

### 18.1 Backup object discovery

Velero queries the Kubernetes API. This means:

- API server health matters.
- RBAC matters.
- CRDs must be discoverable.
- Broken APIService objects can slow or break discovery.

Troubleshoot discovery problems:

```bash
oc get apiservice | grep False
oc api-resources
oc logs -n openshift-adp deploy/velero
```

### 18.2 Backup item actions

Plugins can add related objects.

Example:

- Backing up a PVC may include the related PV.
- OpenShift plugin may include internal image references.
- CSI plugin may create VolumeSnapshot objects.

This is why the final backup can include more resources than you explicitly selected.

### 18.3 Backup TTL and garbage collection

`ttl` defines how long a backup remains eligible before garbage collection.

Example:

```yaml
ttl: 720h0m0s
```

This means 30 days.

When backup expires, Velero can delete backup metadata and related artifacts depending on provider/plugin behavior.

## 19. Restore Flow: What Happens Internally

When you create a `Restore` CR:

```bash
oc apply -f restore.yaml
```

Velero does roughly this:

1. Velero controller sees new `Restore` CR.
2. Downloads backup metadata from BSL.
3. Applies restore filters.
4. Applies namespace mapping.
5. Applies resource modifiers if configured.
6. Restores resources in a controlled order.
7. Calls restore item actions from plugins.
8. Restores PVC/PV data if `restorePVs: true`.
9. Performs DataDownload or PodVolumeRestore if needed.
10. Runs restore hooks if configured.
11. Updates restore status.

### 19.1 Restore ordering

Restore ordering matters. Namespaces usually need to exist before namespace-scoped resources. PVCs may need to exist before pods become healthy. CRDs must exist before CRs.

For operator-managed workloads:

```text
Install Operator/CRDs -> Restore app CRs/resources -> Validate reconciliation
```

### 19.2 Namespace mapping

Namespace mapping is one of the most useful restore features.

Example:

```yaml
namespaceMapping:
  app-prod: app-restore-test
```

Use this for:

- Restore testing
- Migration validation
- Blue/green recovery
- Avoiding conflict with live production namespace

### 19.3 Resource modifiers

Resource modifiers can patch objects during restore.

Use cases:

- Change StorageClass
- Change image registry
- Remove cluster-specific annotations
- Change route hostnames
- Adjust replica count

Conceptual restore modifier pattern:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: restore-resource-modifier
  namespace: openshift-adp
data:
  resource-modifier.yaml: |
    version: v1
    resourceModifierRules:
    - conditions:
        groupResource: persistentvolumeclaims
      patches:
      - operation: replace
        path: "/spec/storageClassName"
        value: "ocs-storagecluster-ceph-rbd"
```

Then reference it in restore:

```yaml
spec:
  resourceModifier:
    kind: ConfigMap
    name: restore-resource-modifier
```

Validate schema against your installed Velero/OADP version.

## 20. Resource Filtering and Selection

Velero backups should be selective. Avoid “backup everything” as a normal production strategy.

### 20.1 Namespace filters

```yaml
includedNamespaces:
  - app-prod
excludedNamespaces:
  - kube-system
  - openshift-monitoring
```

In OpenShift, avoid backing up platform namespaces unless Red Hat documentation or a specific use case says so.

Usually exclude:

```text
openshift-*
kube-*
default
```

But do not use broad exclusions blindly if application namespaces are named similarly.

### 20.2 Resource filters

```yaml
includedResources:
  - deployments
  - services
  - routes.route.openshift.io
  - configmaps
  - secrets
  - persistentvolumeclaims
```

Exclude noisy or non-restorable resources:

```yaml
excludedResources:
  - events
  - events.events.k8s.io
  - pods
  - replicasets.apps
```

Whether to exclude pods depends on restore strategy. Velero often handles pod recreation through workload controllers, so restoring Deployments/StatefulSets is usually better than restoring standalone pods.

### 20.3 Label selectors

```yaml
labelSelector:
  matchLabels:
    backup: oadp
```

Good practice: label application resources that should be backed up.

Example:

```bash
oc label deployment/myapp -n app-prod backup=oadp
oc label service/myapp -n app-prod backup=oadp
oc label route/myapp -n app-prod backup=oadp
```

### 20.4 Cluster-scoped resources

`includeClusterResources` controls cluster-scoped resources.

Examples of cluster-scoped resources:

- PersistentVolumes
- StorageClasses
- ClusterRoles
- ClusterRoleBindings
- CRDs
- SCCs
- VolumeSnapshotClasses

Be careful. Restoring cluster-scoped resources can affect the whole cluster.

Best practice:

- Use GitOps for platform-wide objects.
- Include only application-required cluster-scoped objects.
- Avoid restoring all CRDs/operators blindly.

## 21. Hooks and Application Consistency

Hooks allow commands to run inside containers during backup or restore.

### 21.1 Why hooks matter

For stateful apps, crash-consistent backups may not be enough.

Examples:

- PostgreSQL may need `pg_dump`, checkpoint, or operator-native backup.
- MySQL may need flush/lock/unlock or backup tool.
- MongoDB may need filesystem quiesce or replica-consistent backup.
- File systems may need `fsfreeze` before snapshot.

### 21.2 Backup hook types

Backup hooks can run:

- Before backup item processing: pre hook
- After backup item processing: post hook

Example annotations:

```bash
oc annotate pod <pod-name> -n <namespace> \
  pre.hook.backup.velero.io/container=<container-name> \
  pre.hook.backup.velero.io/command='["/bin/bash", "-c", "echo pre-backup"]' \
  post.hook.backup.velero.io/container=<container-name> \
  post.hook.backup.velero.io/command='["/bin/bash", "-c", "echo post-backup"]'
```

### 21.3 fsfreeze example

```bash
oc annotate pod <pod-name> -n <namespace> \
  pre.hook.backup.velero.io/container=fsfreeze \
  pre.hook.backup.velero.io/command='["/sbin/fsfreeze", "--freeze", "/data"]' \
  post.hook.backup.velero.io/container=fsfreeze \
  post.hook.backup.velero.io/command='["/sbin/fsfreeze", "--unfreeze", "/data"]'
```

Important:

- Container must contain the command.
- Command is not automatically run through a shell unless you explicitly call shell.
- Hook failures can fail backup depending on `on-error` behavior.
- Hooks must complete within timeout.

### 21.4 Restore hooks

Restore hooks can:

- Add init containers
- Execute commands in restored pods
- Fix permissions
- Rebuild caches
- Run application recovery scripts

Use restore hooks carefully. A restore hook that fails can block application recovery.

## 22. RBAC and Multi-Tenancy

### 22.1 Cluster administrator model

Traditionally, OADP operations are cluster-admin-oriented because Velero may need to read cluster resources and manage PVs/snapshots.

Typical admin operations:

```bash
oc adm policy add-cluster-role-to-user cluster-admin <user>
```

But in production, avoid giving broad cluster-admin access for routine backup operations.

### 22.2 Tenant model

A tenant model should define:

- Who can create backups?
- Which namespaces can they protect?
- Can they restore into production?
- Can they delete backup objects?
- Can they access backup logs containing sensitive resource names?
- Can they restore Secrets?

### 22.3 Security issue: Secrets in backups

Velero backs up Kubernetes Secrets as Kubernetes objects. This means backup storage can contain sensitive data.

Protect BSL with:

- Bucket encryption
- Strict IAM
- Object lock where needed
- TLS validation
- Limited service account credentials
- Audit logging
- Backup retention controls

## 23. Security, Credentials, CA Certificates, and Encryption

### 23.1 Credential secret

OADP usually uses a secret in `openshift-adp` for object storage credentials.

Example:

```bash
oc create secret generic cloud-credentials \
  -n openshift-adp \
  --from-file cloud=credentials-velero
```

Example credentials file for S3-compatible provider:

```ini
[default]
aws_access_key_id = <ACCESS_KEY>
aws_secret_access_key = <SECRET_KEY>
```

### 23.2 TLS and CA trust

For S3-compatible object storage with a private CA, configure CA trust in DPA/BSL as supported by your OADP version.

Symptoms of CA issue:

```text
x509: certificate signed by unknown authority
certificate verify failed
```

Troubleshoot:

```bash
oc describe backupstoragelocation <bsl> -n openshift-adp
oc logs -n openshift-adp deploy/velero | grep -i x509
```

Avoid `insecureSkipTLSVerify: "true"` in production unless there is a temporary lab requirement.

### 23.3 Backup data encryption

Encryption can happen at multiple layers:

- Object storage server-side encryption
- Bucket encryption keys
- Kopia repository encryption behavior
- Storage backend encryption
- Network TLS

Enterprise design should document:

- Where encryption occurs
- Who controls keys
- Key rotation process
- Restore process if keys are rotated
- Backup of KMS policies

### 23.4 Least privilege IAM

Object storage credentials should only allow required bucket/prefix actions.

Minimum actions generally include:

- List bucket/prefix
- Get object
- Put object
- Delete object, if Velero is allowed to delete expired backups

If using immutable backup, deletion may intentionally fail until retention expires.

## 24. Designing Backup Strategy for Enterprise OpenShift

### 24.1 Define application tiers

| Tier | Example | RPO | RTO | Backup method |
|---|---|---|---|---|
| Tier 0 | Payment/database | 15 min - 1 hr | < 1 hr | App-native + snapshots + OADP metadata |
| Tier 1 | Critical business app | 4 hr | 2-4 hr | OADP scheduled + CSI data mover |
| Tier 2 | Standard app | 24 hr | 8 hr | Daily OADP backup |
| Tier 3 | Dev/test | best effort | best effort | Weekly or GitOps-only |

### 24.2 Decide backup boundary

A good backup boundary is usually an application namespace or set of namespaces.

Examples:

```text
app-prod
app-prod-db
app-prod-mq
```

For multi-namespace applications, create one backup that includes all related namespaces.

### 24.3 Decide restore target

Possible targets:

- Same namespace, same cluster
- Different namespace, same cluster
- Different cluster, same storage backend
- Different cluster, different storage backend
- DR cluster using same object storage backup repository

### 24.4 Define restore test cycle

A backup that has never been restored is not a proven backup.

Monthly restore test:

1. Select one production-like backup.
2. Restore to test namespace.
3. Validate pods become ready.
4. Validate PVC data.
5. Validate routes/services.
6. Run app smoke test.
7. Record restore duration.
8. Delete test namespace and restore CR.

### 24.5 Combine OADP with GitOps

Best enterprise pattern:

- GitOps restores desired manifests and platform baseline.
- OADP restores runtime application state and PVC data.
- Database-native backup handles transactional data where needed.
- Storage replication handles large-scale DR if required.

Do not use OADP as the only source of truth for platform configuration.

## 27. Troubleshooting Playbook

### 27.1 BackupStorageLocation unavailable

Symptoms:

```bash
oc get bsl -n openshift-adp
# PHASE: Unavailable
```

Check:

```bash
oc describe bsl <bsl> -n openshift-adp
oc logs -n openshift-adp deploy/velero | grep -i <bsl>
```

Common causes:

- Wrong endpoint
- Wrong bucket
- Wrong credentials
- Missing CA
- Network blocked
- Proxy misconfiguration
- S3 path-style vs virtual-hosted-style mismatch

Fix direction:

- Validate bucket exists.
- Validate credentials outside OpenShift.
- Check DNS from cluster.
- Check TLS chain.
- Check DPA/BSL config.
- Check firewall/proxy.

### 27.2 Backup stuck InProgress

Check:

```bash
oc describe backup <backup> -n openshift-adp
oc logs -n openshift-adp deploy/velero
oc get pod -n openshift-adp -o wide
oc get datauploads -n openshift-adp
```

Possible causes:

- DataUpload not completing
- Node-agent pod not scheduled
- CSI snapshot not ready
- API discovery stuck
- Large volume upload
- S3 slow/network slow
- Hook command hanging

### 27.3 Backup PartiallyFailed

Check details:

```bash
oc -n openshift-adp exec deploy/velero -- /velero backup describe <backup> --details
oc -n openshift-adp exec deploy/velero -- /velero backup logs <backup>
```

Look for:

- Specific resource failure
- RBAC denial
- Snapshot failure
- PodVolumeBackup failure
- DataUpload failure
- Hook failure
- Timeout

### 27.4 CSI snapshot not created

Check:

```bash
oc get volumesnapshotclass
oc get volumesnapshot -A
oc get events -A | grep -i snapshot
oc describe pvc <pvc> -n <namespace>
```

Possible causes:

- No `VolumeSnapshotClass`
- Snapshot class not labeled for Velero
- CSI driver does not support snapshots
- Snapshot controller issue
- Storage backend issue
- PVC uses unsupported StorageClass

### 27.5 DataUpload failed

Check:

```bash
oc get datauploads -n openshift-adp
oc describe dataupload <name> -n openshift-adp
oc logs -n openshift-adp ds/node-agent
oc get pods -n openshift-adp | grep data
```

Possible causes:

- Temporary PVC cannot be provisioned
- Data mover pod cannot schedule
- Insufficient CPU/memory
- Object storage upload failure
- Permission issue
- Timeout
- Storage backend slow

### 27.6 Restore completed but app not running

Check:

```bash
oc get all -n <restored-namespace>
oc get pvc -n <restored-namespace>
oc get events -n <restored-namespace> --sort-by=.lastTimestamp
oc describe pod <pod> -n <restored-namespace>
oc logs <pod> -n <restored-namespace>
```

Possible causes:

- Operator/CRDs missing
- Image pull secret missing
- Route hostname conflict
- SCC permission missing
- PVC pending
- StorageClass mismatch
- Secret/config mismatch
- Application needs post-restore recovery

### 27.7 Restore stuck waiting for PVC

Check:

```bash
oc get pvc -n <namespace>
oc describe pvc <pvc> -n <namespace>
oc get storageclass
oc get datadownloads -n openshift-adp
```

Possible causes:

- Original StorageClass does not exist on target cluster
- Requested PV size mismatch or unsupported
- Snapshot source inaccessible
- DataDownload failed
- CSI driver missing
- VolumeSnapshotClass missing

### 27.8 Velero plugin panic on OpenShift image streams

In some OADP versions/configurations, image stream backup can fail if required registry secret handling is missing when BSL is managed outside DPA scope. Prefer DPA-managed BSLs and follow Red Hat's current workaround for your OADP version.

Troubleshoot:

```bash
oc logs -n openshift-adp deploy/velero | grep -i panic
oc get secrets -n openshift-adp | grep registry
oc get bsl -n openshift-adp --show-labels
```

### 27.9 API discovery errors

Symptoms:

```text
unable to retrieve complete list of server APIs
```

Check:

```bash
oc get apiservice | grep False
oc describe apiservice <name>
oc api-resources
```

Fix broken APIService before backup if Velero cannot discover resources reliably.

## 28. Interview-Level Scenario Questions

### Q1. Can OADP back up my entire OpenShift cluster?

No. OADP is intended for customer workload/application backup and restore. It is not a full cluster or etcd backup solution. For full control-plane recovery, use OpenShift etcd backup and the official disaster recovery procedure.

### Q2. What is the difference between BSL and VSL?

BSL is object storage for backup metadata, logs, and backup archives. VSL is for provider-native volume snapshots. BSL is mandatory. VSL is only needed when using snapshot-based PV backup with a provider that needs a snapshot location.

### Q3. A backup completed but restored PVC has no data. Why?

Possible reasons:

- Backup captured PVC/PV manifests but not volume data.
- `snapshotVolumes` was false or no snapshot provider existed.
- File system backup was not enabled.
- Pod volume was not mounted or annotated.
- DataUpload failed.
- CSI snapshot failed.
- Restore used `restorePVs: false`.

### Q4. Why use CSI data mover if CSI snapshots already exist?

CSI snapshots may be local to the storage backend. Data mover copies snapshot data to object storage, improving portability and disaster recovery when the source storage system is unavailable.

### Q5. How do you restore production into a test namespace?

Use `namespaceMapping`:

```yaml
spec:
  backupName: app-prod-backup
  restorePVs: true
  namespaceMapping:
    app-prod: app-prod-restore-test
```

### Q6. How do you make database backups application-consistent?

Use one or more of:

- Database-native backup
- Operator-native backup
- Pre/post Velero hooks
- Filesystem freeze/unfreeze
- Quiesce application writes
- Validate restore with database consistency checks

### Q7. Backup is PartiallyFailed. What do you check first?

```bash
velero backup describe <backup> --details
velero backup logs <backup>
oc describe backup <backup> -n openshift-adp
oc get datauploads -n openshift-adp
oc get volumesnapshot -A
```

Focus on the exact failed resource and volume operation.

### Q8. What must exist on target cluster before restoring an operator-managed application?

- Required Operators
- Required CRDs
- Required StorageClasses
- Required VolumeSnapshotClasses or data mover config
- Required SCC/RBAC baseline
- Required image pull secrets or registry access

### Q9. How do you protect backups from ransomware?

- Use immutable object storage / object lock.
- Use separate credentials for write/delete.
- Restrict delete permissions.
- Enable versioning.
- Monitor delete operations.
- Replicate backups to another account/region.
- Test restore from immutable copy.

### Q10. How do you validate a backup is restorable?

- Restore to a test namespace/cluster.
- Verify resources, pods, PVC data, routes, and application login/API.
- Check data integrity.
- Measure RTO.
- Document issues and fix backup scope.

## 30. Quick Revision Notes

- Velero is upstream; OADP is Red Hat OpenShift-supported integration.
- OADP installs Velero and OpenShift plugins through Operator/DPA.
- Main APIs: `Backup`, `Restore`, `Schedule`, `BackupStorageLocation`, `VolumeSnapshotLocation`.
- DPA is the main OADP configuration CR.
- BSL points to object storage.
- VSL points to snapshot location.
- BSL is mandatory; VSL depends on snapshot method.
- OADP protects workloads, not full OpenShift clusters or etcd.
- Use etcd backup for control plane disaster recovery.
- Use OADP for application backup/restore/migration.
- For PVs, choose CSI snapshot, data mover, or file system backup based on storage.
- CSI snapshots may not be portable by themselves.
- Data mover copies snapshot data to object storage.
- File System Backup is storage-agnostic but may be less consistent.
- Kopia is common in newer node-agent/data movement workflows.
- Restic appears in older Velero/OADP file system backup workflows.
- Hooks help with application consistency.
- Restore tests are mandatory.
- GitOps + OADP + app-native backup is stronger than OADP alone.
