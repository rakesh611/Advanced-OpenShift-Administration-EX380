# Namespace-level backup in OpenShift APIs for Data Protection (OADP)

**Audience:** Advanced OpenShift Administration / 10+ years experience  
**Focus:** Namespace-scoped application backup and restore with OADP, Velero, Backup CR, Schedule CR, persistent volumes, internal images, production strategy, and troubleshooting.  
**Platform:** OpenShift Container Platform 4.x with OADP Operator installed in `openshift-adp`.

---

## 1. Executive summary

A **namespace-level backup** in OADP means backing up one or more application namespaces instead of attempting to back up the entire OpenShift cluster. In OpenShift, application workloads are usually grouped by namespace/project. OADP uses Velero APIs to back up Kubernetes objects, OpenShift objects, internal images, and persistent volume data at namespace granularity.

In production, namespace-level backup is the normal pattern for application disaster recovery because it lets you protect a specific application stack, restore it to the same cluster, restore it to another cluster, migrate workloads, or recover from accidental deletion without performing an etcd-level control-plane restore.

A namespace-level backup usually includes:

- Namespace/project object
- Deployments, DeploymentConfigs, StatefulSets, DaemonSets, ReplicaSets
- Pods metadata, Jobs, CronJobs
- Services, Routes, Ingresses
- ConfigMaps and Secrets
- ServiceAccounts, Roles, RoleBindings
- PVCs and, depending on configuration, PV data through CSI snapshots, native cloud snapshots, or file-system backup
- OpenShift resources such as Routes, ImageStreams, BuildConfigs, DeploymentConfigs, and internal image metadata where applicable
- Selected application-specific Custom Resources, but normally **not the Operator installation itself**

A namespace-level backup is **not** the same as full cluster backup. It does not replace etcd backup. It protects applications. etcd backup protects control-plane state.

---

## 2. Why namespace-level backup matters

In real enterprise OpenShift administration, most incidents are application-scoped, not full-cluster disasters:

- A user deletes a project accidentally.
- A bad deployment corrupts application configuration.
- A team deletes a PVC or secret.
- A namespace needs to be migrated from one cluster to another.
- A database application needs point-in-time style protection around maintenance.
- A DR test requires restoring one business application without touching the whole cluster.

For these cases, restoring etcd is too heavy and risky because etcd restore rolls the entire cluster back. Namespace-level backup gives controlled recovery for a single application boundary.

## 3. Namespace-level backup architecture

### 3.1 Main components

| Component | Purpose |
|---|---|
| OADP Operator | Installs and manages Velero and related OADP components on OpenShift. |
| `DataProtectionApplication` / DPA | Main OADP configuration object. Defines Velero plugins, backup locations, snapshot locations, node agent, and uploader type. |
| Velero deployment | Controller that processes Backup, Restore, and Schedule custom resources. |
| BackupStorageLocation / BSL | Object-storage target where Kubernetes/OpenShift resource archives and backup metadata are stored. |
| VolumeSnapshotLocation / VSL | Snapshot location for native provider snapshots, when required. CSI snapshots usually use `VolumeSnapshotClass`. |
| Node agent | DaemonSet used for file-system backup/data movement depending on OADP version and configuration. |
| Backup CR | Declarative request to back up selected namespaces/resources. |
| Restore CR | Declarative request to restore from a backup. |
| Schedule CR | Declarative recurring backup template using a Cron expression. |

### 3.2 Backup flow

For a namespace-level backup:

1. Administrator creates a `Backup` CR in `openshift-adp`.
2. The CR specifies `includedNamespaces`.
3. Velero lists and collects objects from the selected namespace(s).
4. Velero applies include/exclude resource filters and label selectors.
5. OpenShift-specific plugins handle supported OpenShift resources.
6. PV handling is decided by the backup configuration:
   - CSI snapshot
   - Native cloud snapshot
   - File-system backup with Restic/Kopia/node agent
   - Metadata-only backup if volume backup is disabled
7. Backup metadata and Kubernetes/OpenShift object manifests are written to object storage.
8. Backup status changes to `Completed`, `PartiallyFailed`, or `Failed`.

## 4. Namespace-level backup vs cluster backup vs etcd backup

| Backup type | Scope | Tool | Use case |
|---|---|---|---|
| Namespace-level backup | One or more application namespaces | OADP / Velero | Application recovery, migration, DR testing |
| Cluster-scoped resource backup | Selected cluster resources such as CRDs, ClusterRoles, StorageClasses | OADP / Velero with cluster resource filters | Support application CRs that depend on cluster-level objects |
| Full cluster application backup | Many/all namespaces, possibly cluster-scoped resources | OADP / Velero | Large migration or broad app backup, not a supported etcd replacement |
| Control-plane backup | etcd state | OpenShift etcd backup | Full cluster disaster recovery |

**Senior admin rule:** Use OADP for application recovery. Use etcd backup for control-plane disaster recovery. Do not treat OADP namespace backup as a replacement for etcd snapshots.

## 5. Prerequisites

### 5.1 Access prerequisites

You normally need cluster-admin access to configure OADP:

```bash
oc whoami
oc auth can-i '*' '*' --all-namespaces
```

Verify OADP namespace:

```bash
oc get ns openshift-adp
oc get pods -n openshift-adp
```

Expected key pods:

```text
velero-xxxxx
node-agent-xxxxx   # if node agent / file-system backup is enabled
oadp-operator-controller-manager-xxxxx
```

### 5.2 DPA readiness

```bash
oc get dpa -n openshift-adp
oc get dpa -n openshift-adp -o yaml
```

A healthy DPA should be reconciled and Velero should be running.

### 5.3 BackupStorageLocation readiness

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation -n openshift-adp
```

Expected phase:

```text
PHASE: Available
```

If BSL is not available, namespace backups will fail before they become useful.

### 5.4 Storage prerequisites for PV backup

Check PVCs in the target namespace:

```bash
NS=myapp-prod
oc get pvc -n $NS
oc get pods -n $NS -o wide
oc get storageclass
```

For CSI snapshot mode:

```bash
oc get volumesnapshotclass
oc get volumesnapshotclass -o yaml | grep -A5 -B5 'velero.io/csi-volumesnapshot-class'
```

A Velero CSI snapshot class often uses:

```yaml
metadata:
  labels:
    velero.io/csi-volumesnapshot-class: "true"
```

For each CSI driver type, avoid multiple `VolumeSnapshotClass` objects with this same Velero default label, otherwise selection can become ambiguous.

## 6. What exactly is included in a namespace-level backup?

When you set:

```yaml
spec:
  includedNamespaces:
  - myapp-prod
```

Velero includes objects from `myapp-prod` unless additional filters exclude them.

Common namespace-scoped objects:

```text
pods
deployments.apps
statefulsets.apps
daemonsets.apps
replicasets.apps
services
routes.route.openshift.io
ingresses.networking.k8s.io
configmaps
secrets
serviceaccounts
roles.rbac.authorization.k8s.io
rolebindings.rbac.authorization.k8s.io
persistentvolumeclaims
jobs.batch
cronjobs.batch
networkpolicies.networking.k8s.io
imagestreams.image.openshift.io
buildconfigs.build.openshift.io
deploymentconfigs.apps.openshift.io
```

Important cluster-scoped objects are **not automatically part of a namespace-only backup** when namespace filtering is used, unless you explicitly include cluster-scoped resources or Velero plugin actions pull specific dependent objects.

Examples of cluster-scoped resources that may matter:

```text
customresourcedefinitions.apiextensions.k8s.io
clusterroles.rbac.authorization.k8s.io
clusterrolebindings.rbac.authorization.k8s.io
storageclasses.storage.k8s.io
volumesnapshotclasses.snapshot.storage.k8s.io
securitycontextconstraints.security.openshift.io
persistentvolumes
```

Senior design point: Back up application namespace resources separately from platform/operator resources unless the application genuinely requires selected cluster-scoped objects.

## 7. Basic namespace-level Backup CR

Create a simple backup for one namespace:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-ns-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  storageLocation: default
  ttl: 720h0m0s
```

Apply it:

```bash
oc apply -f myapp-prod-ns-backup-001.yaml
```

Watch status:

```bash
watch "oc get backup -n openshift-adp myapp-prod-ns-backup-001 -o jsonpath='{.status.phase}{"\n"}'"
```

Describe:

```bash
oc describe backup -n openshift-adp myapp-prod-ns-backup-001
```

List backups:

```bash
oc get backup -n openshift-adp
```

## 8. Backup CR with snapshot-based PV protection

Use this when your storage supports CSI or native snapshots and your DPA/plugins are configured correctly.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-snapshot-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  storageLocation: default
  snapshotVolumes: true
  defaultVolumesToFsBackup: false
  csiSnapshotTimeout: 10m0s
  itemOperationTimeout: 4h0m0s
  ttl: 720h0m0s
```

Meaning:

| Field | Meaning |
|---|---|
| `includedNamespaces` | Namespaces to include in backup. |
| `storageLocation` | BSL where metadata/object archive is stored. |
| `snapshotVolumes: true` | Request snapshot backup for supported volumes. |
| `defaultVolumesToFsBackup: false` | Do not fall back to file-system backup by default. |
| `csiSnapshotTimeout` | Maximum wait for CSI snapshot operations. |
| `itemOperationTimeout` | Timeout for asynchronous backup item operations. |
| `ttl` | Retention period for backup metadata/artifacts. |

Use snapshot-based backup for large database PVCs when crash-consistent storage snapshots are acceptable and application hooks are configured if app-consistent backup is required.

## 9. Backup CR with file-system backup

Use this when:

- Storage does not support snapshots.
- Application uses NFS or another volume type without snapshot support.
- You need object-store based file-level copy.
- You enabled node agent / Restic / Kopia through DPA.

Example:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-fsbackup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  storageLocation: default
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
  ttl: 720h0m0s
```

Check node agent:

```bash
oc get ds node-agent -n openshift-adp
oc get pods -n openshift-adp -l name=node-agent -o wide
```

File-system backup is often slower than snapshots but more portable across environments.

## 10. Backup selected resources inside a namespace

Sometimes you do not want the complete namespace. Example: back up only application config and RBAC, not pods/events.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-config-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  includedResources:
  - configmaps
  - secrets
  - serviceaccounts
  - roles.rbac.authorization.k8s.io
  - rolebindings.rbac.authorization.k8s.io
  - routes.route.openshift.io
  - services
  storageLocation: default
  ttl: 168h0m0s
```

Example: exclude noisy or unnecessary resources:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-clean-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  excludedResources:
  - events
  - pods
  - replicasets.apps
  storageLocation: default
  ttl: 720h0m0s
```

Be careful excluding pods. For Deployments and StatefulSets, pods are recreated by controllers. For bare pods, excluding pods means they will not return.

## 11. Label-based namespace backup

If multiple applications share a namespace, label-based backup is useful.

Label important objects:

```bash
oc label deployment frontend app.kubernetes.io/part-of=payment -n myapp-prod
oc label service frontend app.kubernetes.io/part-of=payment -n myapp-prod
oc label route frontend app.kubernetes.io/part-of=payment -n myapp-prod
```

Backup matching objects:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payment-label-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payment
  storageLocation: default
  ttl: 720h0m0s
```

For OR style selection:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: multi-label-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  orLabelSelectors:
  - matchLabels:
      app: frontend
  - matchLabels:
      app: backend
  storageLocation: default
```

Senior warning: Label-based backup requires label discipline. If a Secret, PVC, Route, or Service is missing the selector label, it might not be backed up.

## 12. Excluding specific objects from backup

Use the Velero exclusion label:

```bash
oc label secret temporary-token velero.io/exclude-from-backup=true -n myapp-prod
oc label configmap generated-cache velero.io/exclude-from-backup=true -n myapp-prod
```

This is useful for:

- Temporary tokens
- Generated cache config
- Short-lived test objects
- Secrets that should be regenerated
- Large non-critical objects

Do not blindly exclude Secrets. Many workloads need pull secrets, application credentials, TLS secrets, and service account tokens/configuration to restore correctly.

## 13. Namespace backup with cluster-scoped dependencies

A pure namespace backup might not be enough for applications based on Operators or CRDs.

Example: your namespace has custom resources such as:

```bash
oc api-resources --namespaced=true | grep -i postgres
oc get crd | grep -i postgres
```

If restoring to a different cluster, the CRD and Operator must already exist, or the restore will fail/partially fail because the API type is unknown.

### Recommended production pattern

1. Install platform Operators and CRDs through GitOps/OLM on the target cluster.
2. Restore only application namespace objects and application custom resources.
3. Avoid backing up the Operator controller namespace unless you have a vendor-supported procedure.

### Backup with selected cluster-scoped resources

Use with caution:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-with-crd-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
  - myapp-prod
  includedClusterScopedResources:
  - customresourcedefinitions.apiextensions.k8s.io
  - clusterroles.rbac.authorization.k8s.io
  - clusterrolebindings.rbac.authorization.k8s.io
  includedNamespaceScopedResources:
  - '*'
  storageLocation: default
  ttl: 720h0m0s
```

Senior warning: Including all cluster-scoped resources can introduce conflicts, security issues, and restore ordering problems. Use explicit allowlists where possible.

## 14. Namespace backup and Operators

A common mistake is backing up both:

- Application custom resources
- Operator installation namespace

This can cause restore problems because Operators are lifecycle-managed by OLM and should usually be installed cleanly on the target cluster.

Better strategy:

| Item | Backup approach |
|---|---|
| Operator subscription/install plan/CSV | Prefer GitOps/OLM reinstall, not OADP app backup. |
| CRDs | Preinstall through Operator, or carefully back up if vendor supports it. |
| Application CRs | Include in namespace backup. |
| Operator-managed Secrets/ConfigMaps | Back up only if required and supported. |
| Operand PVCs | Protect with snapshot or file-system backup. |

Interview-ready answer:

> For Operator-based applications, I back up operand namespaces and custom resources, but I do not rely on OADP to reinstall OLM-managed Operators. I make sure the target cluster has the same Operator version/API available before restore.

## 15. Backup hooks for application consistency

Storage snapshots are often crash-consistent. Databases may require pre/post hooks for application-consistent backups.

Example pre/post hook annotations on a pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: db-pod
  namespace: myapp-prod
  annotations:
    pre.hook.backup.velero.io/command: '["/bin/sh", "-c", "pg_dumpall > /backup/pre-backup.sql"]'
    pre.hook.backup.velero.io/container: postgres
    pre.hook.backup.velero.io/timeout: 10m
    post.hook.backup.velero.io/command: '["/bin/sh", "-c", "echo backup completed"]'
    post.hook.backup.velero.io/container: postgres
spec:
  containers:
  - name: postgres
    image: postgres:latest
```

In production, hooks should be tested carefully. A failing hook can fail or delay backup. For databases, vendor-native backup tools may still be required for true transaction consistency.

## 16. Scheduled namespace backups

Use `Schedule` CR for recurring backups.

Daily backup at 01:00:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: myapp-prod-daily
  namespace: openshift-adp
spec:
  schedule: "0 1 * * *"
  template:
    includedNamespaces:
    - myapp-prod
    storageLocation: default
    snapshotVolumes: true
    defaultVolumesToFsBackup: false
    ttl: 168h0m0s
```

Weekly backup:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: myapp-prod-weekly
  namespace: openshift-adp
spec:
  schedule: "0 2 * * 0"
  template:
    includedNamespaces:
    - myapp-prod
    storageLocation: default
    snapshotVolumes: true
    ttl: 720h0m0s
```

Check schedules:

```bash
oc get schedule -n openshift-adp
oc describe schedule -n openshift-adp myapp-prod-daily
```

Manual backup from schedule:

```bash
velero backup create myapp-prod-manual-from-schedule --from-schedule myapp-prod-daily -n openshift-adp
```

Senior scheduling rule: Ensure the previous backup normally finishes before the next scheduled backup starts.

## 18. Restore namespace backup to a different namespace

This is useful for testing, cloning, migration, or blue/green recovery.

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-myapp-prod-to-dr-001
  namespace: openshift-adp
spec:
  backupName: myapp-prod-ns-backup-001
  includedNamespaces:
  - myapp-prod
  namespaceMapping:
    myapp-prod: myapp-dr
  restorePVs: true
```

After restore:

```bash
oc get all -n myapp-dr
oc get pvc -n myapp-dr
oc get route -n myapp-dr
```

Post-restore changes may be needed:

- Route hostnames may conflict.
- External DNS records may need updates.
- Secrets may point to production external systems.
- ConfigMaps may contain namespace names or URLs.
- NetworkPolicy may block traffic in the new namespace.
- ServiceAccounts and SCC bindings must be reviewed.

## 19. Restore ordering and CRDs

If the backup contains custom resources but the target cluster does not have the CRD installed, restore may fail with errors similar to:

```text
no matches for kind "ExampleApp" in version "example.com/v1"
```

Fix:

1. Install the Operator/CRDs on the target cluster.
2. Confirm API exists:

```bash
oc api-resources | grep -i example
oc get crd | grep -i example
```

3. Re-run restore.

For complex applications, restore order should be:

1. Cluster-level prerequisites: CRDs, StorageClasses, SCCs, Operators
2. Namespace creation and RBAC
3. Secrets and ConfigMaps
4. PVCs/PVs or restored volume data
5. Application controllers/custom resources
6. Routes/Ingress/DNS
7. Post-restore validation

## 20. Production backup design

### 20.1 Backup classification

| Workload type | Recommended approach |
|---|---|
| Stateless app | Namespace backup without PV snapshot may be enough. |
| App with small PVC | Snapshot or file-system backup. |
| Database | Use database-native backup plus OADP metadata/PVC backup. Add hooks if appropriate. |
| Operator-managed app | Preinstall Operator, restore operand namespace and CRs. |
| VM workload | Use OADP support path for OpenShift Virtualization, normally CSI/DataMover depending on supported version. |
| Shared namespace | Use label selectors carefully or split apps into separate namespaces. |

### 20.2 Retention example

| Backup | Frequency | TTL |
|---|---:|---:|
| Hourly config backup | Every 1 hour | 24 hours |
| Daily app backup | Daily | 7 days |
| Weekly app backup | Weekly | 30 days |
| Monthly compliance backup | Monthly | 180/365 days |

### 20.3 Naming standard

Use clear names:

```text
<app>-<env>-<scope>-<method>-<yyyymmddhhmm>
```

Examples:

```text
payment-prod-ns-csi-202607030100
payment-prod-config-202607030100
payment-dr-restore-test-20260703
```

## 22. Common problems and troubleshooting

### Problem 1: Backup stuck in `InProgress`

Check:

```bash
oc describe backup -n openshift-adp <backup-name>
oc logs deployment/velero -n openshift-adp --since=2h
oc get volumesnapshot -A
```

Possible causes:

- Volume snapshot is not ready.
- CSI driver snapshot controller issue.
- Object storage latency or credential issue.
- Hook command is hanging.
- Large file-system backup is still running.

Fix approach:

- Check VolumeSnapshot status.
- Check CSI driver pods.
- Increase `csiSnapshotTimeout` or `itemOperationTimeout` if justified.
- Fix hook timeout.
- Use smaller namespace scope or split backups.

### Problem 2: Backup `PartiallyFailed`

Check warnings/errors:

```bash
oc describe backup -n openshift-adp <backup-name>
oc get backup -n openshift-adp <backup-name> -o jsonpath='{.status.warnings}{"\n"}{.status.errors}{"\n"}'
```

Common causes:

- RBAC cannot read some resources.
- CRD exists but custom resource has conversion/webhook issue.
- A resource disappeared during backup.
- Snapshot failed for one PVC.
- Excluded/unsupported resource type.

Senior interpretation: `PartiallyFailed` is not automatically useless, but it is not production-ready until you understand exactly what failed.

### Problem 3: Restore fails because namespace already exists

Restoring into an existing namespace can conflict with existing resources.

Options:

- Delete and recreate the namespace if safe.
- Restore into a new namespace with `namespaceMapping`.
- Exclude conflicting resources.
- Use GitOps to reconcile desired state after restore.

### Problem 4: PVC restored but pod cannot mount volume

Check:

```bash
oc get pvc -n <namespace>
oc describe pvc -n <namespace> <pvc>
oc get pv
oc describe pod -n <namespace> <pod>
oc get events -n <namespace> --sort-by=.metadata.creationTimestamp | tail -50
```

Possible causes:

- StorageClass missing on target cluster.
- CSI driver missing or different.
- Snapshot restore failed.
- AccessMode mismatch.
- Zone/region topology mismatch.
- Volume binding mode issue.

### Problem 5: Route restored but application unavailable

Check:

```bash
oc get route -n <namespace>
oc describe route -n <namespace> <route>
oc get svc -n <namespace>
oc get endpoints -n <namespace>
oc get pods -n <namespace>
```

Possible causes:

- Route hostname conflict.
- Service selector mismatch.
- Pods not ready.
- TLS secret missing.
- NetworkPolicy blocking traffic.

### Problem 6: Secrets restored but app still fails

Check:

```bash
oc get secret -n <namespace>
oc describe pod -n <namespace> <pod>
oc logs -n <namespace> <pod>
```

Possible causes:

- Secret mounted but key name changed.
- External credential expired.
- Image pull secret not linked to ServiceAccount.
- SealedSecret/ExternalSecret controller not present.

### Problem 7: Custom resources did not restore

Check:

```bash
oc api-resources | grep -i <resource>
oc get crd | grep -i <resource>
oc describe restore -n openshift-adp <restore-name>
```

Fix:

- Install the CRD/Operator first.
- Match Operator version/API version.
- Restore again.

## 23. Security considerations

Namespace backups often contain sensitive data:

- Kubernetes Secrets
- TLS private keys
- Database passwords
- Pull secrets
- Service account tokens or token-related config
- OAuth/client credentials
- Application config containing endpoints and keys

Production controls:

1. Restrict access to `openshift-adp`.
2. Restrict access to object storage bucket.
3. Enable bucket encryption.
4. Use bucket versioning/object lock where appropriate, but validate compatibility with Velero backup lifecycle behavior.
5. Rotate credentials used by OADP.
6. Audit who can create Restore CRs.
7. Do not allow application teams to restore Secrets into privileged namespaces without governance.
8. Treat backup data as production-sensitive data.

RBAC check:

```bash
oc adm policy who-can create backups.velero.io -n openshift-adp
```

## 24. Performance and scale considerations

For large namespaces:

- Prefer snapshots over file-system backup for large PVCs when storage supports it.
- Split backups by application or tier.
- Avoid backing up noisy resources such as events.
- Use label selectors only if labeling is complete.
- Schedule backups outside peak I/O windows.
- Monitor object storage latency.
- Monitor Velero pod CPU/memory.
- Monitor node-agent resource usage if using file-system backup.
- Test restore time, not just backup completion.

Backup speed depends on:

| Factor | Impact |
|---|---|
| Number of API objects | More API list/watch/serialization time |
| PVC size | Major impact for file-system backup |
| Storage snapshot performance | Major impact for snapshot backup |
| Object storage throughput | Major impact for metadata and data movement |
| Hook duration | Can block backup |
| API server load | Can slow object collection |

## 25. Monitoring and alerting ideas

Useful signals:

- Backup phase is `Failed` or `PartiallyFailed`.
- No successful backup in last N hours.
- BSL phase is not `Available`.
- Velero pod restarts.
- Node-agent pod failures.
- Backup duration exceeds expected baseline.
- Restore test has not been performed in last N days.

Commands:

```bash
oc get backup -n openshift-adp --sort-by=.metadata.creationTimestamp
oc get backupstoragelocation -n openshift-adp
oc get pods -n openshift-adp
```

For mature environments, integrate OADP/Velero metrics with OpenShift monitoring and create alerts for backup failure and stale backups.

## 26. DR test procedure for namespace-level backup

A backup is only valid if restore is tested.

### Step 1: Create backup

```bash
oc apply -f myapp-prod-ns-backup-001.yaml
oc get backup -n openshift-adp myapp-prod-ns-backup-001
```

### Step 2: Restore to test namespace

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-myapp-prod-to-test-001
  namespace: openshift-adp
spec:
  backupName: myapp-prod-ns-backup-001
  namespaceMapping:
    myapp-prod: myapp-restore-test
  restorePVs: true
```

### Step 3: Validate resources

```bash
oc get all -n myapp-restore-test
oc get pvc -n myapp-restore-test
oc get route -n myapp-restore-test
oc get events -n myapp-restore-test --sort-by=.metadata.creationTimestamp | tail -50
```

### Step 4: Validate application

- Pods ready
- PVCs bound
- Service endpoints populated
- Route responds
- Logs clean
- Application login works
- Database consistency validated
- External integrations intentionally disabled or redirected in test namespace

### Step 5: Document RTO/RPO

Record:

```text
Backup start time:
Backup completion time:
Backup duration:
Restore start time:
Restore completion time:
Restore duration:
Application validation result:
Data validation result:
Issues found:
Fixes required:
```

## 27. GitOps-friendly backup manifests

Store backup policies in Git, but be careful with generated Backup CRs.

Recommended Git layout:

```text
clusters/
  prod/
    oadp/
      dpa.yaml
      schedules/
        payment-prod-daily.yaml
        payment-prod-weekly.yaml
      policies/
        payment-resource-policy.yaml
```

For Argo CD or OpenShift GitOps:

- Manage `Schedule` CRs with GitOps.
- Avoid pruning generated `Backup` CRs unintentionally.
- Avoid deleting schedules in a way that unexpectedly affects generated backup objects.
- Keep restore CRs as controlled operational manifests, not continuously synced desired state.

```yaml
metadata:
```

## 29. Interview scenario answer

**Question:** How do you perform namespace-level backup in OpenShift using OADP?

**Answer:**

I first verify that OADP is installed in `openshift-adp`, the DPA is reconciled, and the BackupStorageLocation is `Available`. Then I inspect the application namespace to understand resources, PVCs, CRDs, Operators, Routes, Secrets, and storage class behavior. For a namespace backup, I create a Velero `Backup` CR in `openshift-adp` with `spec.includedNamespaces` set to the target namespace. If the application has PVCs, I decide whether to use CSI/native snapshots or file-system backup through node agent based on storage support and RPO/RTO. For Operator-managed applications, I normally preinstall the Operator/CRDs on the target cluster and restore only operand resources. I monitor the Backup CR phase, Velero logs, BSL status, VolumeSnapshots, and backup warnings/errors. Finally, I perform a restore test, preferably to a different namespace using `namespaceMapping`, and validate pods, PVCs, Routes, Secrets, application login, and data consistency.

## 32. Key takeaways

- Namespace-level backup is the standard OADP pattern for application protection.
- `includedNamespaces` is the core field for namespace backup.
- Back up platform Operators separately from application data; do not blindly back up OLM-managed Operator namespaces.
- PVC protection must be deliberately designed: snapshot, CSI DataMover, or file-system backup.
- A backup without a tested restore is not a backup strategy.
- For production, monitor backup success, BSL health, duration, restore test frequency, and object-storage security.
- OADP application backup complements etcd backup; it does not replace control-plane disaster recovery.
