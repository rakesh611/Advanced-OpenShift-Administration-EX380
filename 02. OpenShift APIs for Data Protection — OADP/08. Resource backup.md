# Resource Backup in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and backup/DR owners with 10+ years of Linux/Kubernetes/OpenShift experience.  
**Scope:** Deep-dive into *resource backup* in OADP: what gets backed up, how Velero/OADP processes resources, how to design Backup CRs, what to include/exclude, operational commands, troubleshooting, and production best practices.  
**Assumption:** OADP is installed in the `openshift-adp` namespace, which is the common OpenShift namespace used for the OADP Operator and Velero components.

---

## 1. What “Resource Backup” Means in OADP

In OADP, **resource backup** means backing up Kubernetes and OpenShift API objects that define an application or workload.

Examples:

- `Namespace`
- `Deployment`
- `StatefulSet`
- `DaemonSet`
- `Job` / `CronJob`
- `Service`
- `Route`
- `Ingress`
- `ConfigMap`
- `Secret`
- `ServiceAccount`
- `Role` / `RoleBinding`
- `PersistentVolumeClaim`
- selected `PersistentVolume` metadata
- Custom resources such as application CRs managed by Operators
- Image-related OpenShift resources such as `ImageStream`, depending on plugin and configuration

Resource backup is different from persistent volume data backup.

| Backup area | What it protects | Example | Stored where |
|---|---|---|---|
| Resource backup | Kubernetes/OpenShift API objects | Deployment YAML, Route YAML, Secret YAML, PVC YAML | Object storage as backup archive |
| Volume snapshot backup | Persistent volume point-in-time snapshot | ODF RBD PVC snapshot, EBS snapshot | CSI/native snapshot backend, optionally moved |
| File System Backup | Files inside mounted volumes | NFS, local volume, filesystem copy | Object storage repository via node-agent/Kopia |
| Internal image backup | OpenShift internal images | ImageStream/image data | Object storage depending on plugin/configuration |

A strong OpenShift administrator must understand this distinction:

> Backing up a PVC object is not the same as backing up the data inside the volume.

A `PersistentVolumeClaim` is only the Kubernetes request/metadata. The actual application data requires either CSI/native snapshot, data mover, or File System Backup.

## 2. Why Resource Backup Matters

Resource backup protects the **desired state** of the application.

In OpenShift, most production outages are not only storage failures. They also happen due to:

- accidental namespace deletion
- wrong `oc delete` or `oc apply --prune`
- bad Helm/Operator upgrade
- broken route/service/configuration
- deleted secrets
- RBAC changes
- failed migration
- failed application upgrade
- wrong SCC/security change
- accidental deletion of application CRs
- cluster migration or DR event

For such cases, resource backup lets you restore the application definition quickly.

Example:

```text
Application = Resource definition + Runtime state + Persistent data
```

Resource backup protects the **definition** part.

## 3. OADP and Velero Relationship

OADP is Red Hat’s OpenShift data protection Operator. It deploys and manages Velero and OpenShift-specific plugins.

At a high level:

```text
User creates Backup CR
        |
        v
Kubernetes API stores Backup object
        |
        v
Velero BackupController watches Backup CR
        |
        v
Velero validates backup spec
        |
        v
Velero discovers API resources
        |
        v
Velero filters resources by namespace/resource/label
        |
        v
Plugins process OpenShift/Kubernetes objects
        |
        v
Objects are serialized into backup archive
        |
        v
Archive/logs are uploaded to BackupStorageLocation
        |
        v
Backup status becomes Completed / PartiallyFailed / Failed
```

Key OADP/Velero custom resources:

| CR | Purpose |
|---|---|
| `DataProtectionApplication` | Main OADP configuration object. Deploys Velero, node-agent, plugins, BSL/VSL definitions. |
| `BackupStorageLocation` | Object storage target for backup archives and logs. Usually S3-compatible storage. |
| `VolumeSnapshotLocation` | Cloud/native snapshot target for volume snapshots where applicable. |
| `Backup` | One-time backup request. |
| `Schedule` | Recurring backup template. |
| `Restore` | Restore request from an existing backup. |
| `PodVolumeBackup` | File System Backup operation for a pod volume. |
| `DataUpload` | Data mover upload object for snapshot/data movement workflows in newer Velero/OADP versions. |

## 4. Resource Backup Is Not Full Cluster Backup

A very important production point:

> OADP is designed mainly to protect customer applications, application-related resources, persistent volumes, and internal images. It is not a replacement for etcd backup or full OpenShift cluster recovery.

Do **not** treat OADP as your only cluster disaster recovery mechanism.

You still need:

- OpenShift etcd backup for cluster control-plane recovery
- infrastructure backup for IPI/UPI dependencies
- GitOps repository backup
- registry/object storage backup
- database-native backup for critical databases
- external secret manager backup
- storage backend replication/backup where required

Use OADP for **application-level backup and restore**, not as a full OpenShift cluster rebuild tool.

## 5. Resource Backup Workflow in Deep Detail

### 5.1 Backup CR Creation

You create a `Backup` CR in the Velero/OADP namespace:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-resource-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp-prod
  storageLocation: default
  ttl: 720h0m0s
```

Once the object is created, Velero starts processing it.

Check:

```bash
oc get backup -n openshift-adp
oc describe backup myapp-resource-backup-001 -n openshift-adp
```

### 5.2 Validation Phase

Velero checks:

- Is `BackupStorageLocation` valid?
- Is the backup spec valid?
- Are filters contradictory?
- Is the storage location available?
- Are required plugins available?
- Does the namespace exist?
- Are resource policies valid?

If validation fails, status becomes:

```text
FailedValidation
```

Useful command:

```bash
oc get backup myapp-resource-backup-001 -n openshift-adp -o yaml
```

### 5.3 Discovery Phase

Velero queries the Kubernetes API discovery endpoints to list available API groups/resources.

Examples:

```bash
oc api-resources
oc api-resources --namespaced=true
oc api-resources --namespaced=false
```

Why this matters:

- CRDs must exist to discover custom resources.
- Deprecated/removed APIs can affect backup and restore compatibility.
- Restoring to another cluster requires matching API versions or compatible CRDs.

### 5.4 Filtering Phase

Velero filters objects using the Backup spec:

- namespaces
- included resources
- excluded resources
- cluster-scoped resources
- namespace-scoped resources
- label selectors
- resource policies
- `velero.io/exclude-from-backup=true` label

Filtering is one of the most important production skills in OADP.

### 5.5 Item Processing Phase

For each selected object, Velero runs internal processing and plugins.

Examples:

- OpenShift plugin adjusts OpenShift-specific resources.
- CSI plugin handles volume snapshot related objects.
- Custom BackupItemAction plugins can add related resources.
- ServiceAccount/SCC-related plugin logic can handle OpenShift security mappings.

This is why a backup can include objects you did not explicitly list if a plugin identifies them as related dependencies.

### 5.6 Archive Creation

Velero serializes selected API objects into a backup archive.

Typical object storage layout:

```text
bucket-or-prefix/
  backups/
    myapp-resource-backup-001/
      myapp-resource-backup-001.tar.gz
      velero-backup.json
      myapp-resource-backup-001-logs.gz
      myapp-resource-backup-001-results.gz
```

Inside the tar archive, Kubernetes resources are stored as JSON/YAML-like resource documents grouped by resource type and namespace.

### 5.7 Upload to BackupStorageLocation

The archive is uploaded to the configured object store.

Examples of object storage:

- AWS S3
- Azure Blob
- Google Cloud Storage
- OpenShift Data Foundation Multicloud Object Gateway
- NooBaa
- MinIO
- IBM Cloud Object Storage
- other S3-compatible storage supported by the selected plugin/configuration

### 5.8 Status Update

Backup status phases you commonly see:

| Phase | Meaning |
|---|---|
| `New` | Backup object created but not yet processed. |
| `InProgress` | Backup is running. |
| `WaitingForPluginOperations` | Waiting for async plugin operations. |
| `Finalizing` / finalizing variants | Velero is completing metadata/results. |
| `Completed` | Backup completed successfully. |
| `PartiallyFailed` | Backup completed with warnings/errors for some items. Must investigate. |
| `Failed` | Backup failed. |
| `FailedValidation` | Spec or environment validation failed before running. |

Check phase:

```bash
oc get backups.velero.io -n openshift-adp
oc get backup myapp-resource-backup-001 -n openshift-adp -o jsonpath='{.status.phase}{"\n"}'
```

## 6. Backup CR Spec Fields — Advanced Explanation

### 6.1 `includedNamespaces`

Back up only selected namespaces.

```yaml
spec:
  includedNamespaces:
    - myapp-prod
    - myapp-config
```

Use this for application-scoped backup.

Best practice:

```text
Prefer explicit application namespaces instead of full-cluster resource backup.
```

### 6.2 `excludedNamespaces`

Exclude namespaces from a broader backup.

```yaml
spec:
  excludedNamespaces:
    - openshift-monitoring
    - openshift-logging
```

In production, avoid broad backups of all namespaces unless you have a strong reason.

### 6.3 `includedResources`

Back up only selected resource types.

```yaml
spec:
  includedResources:
    - deployments.apps
    - statefulsets.apps
    - services
    - routes.route.openshift.io
    - configmaps
    - secrets
    - persistentvolumeclaims
```

Good for configuration-only backups.

Important:

- Use fully-qualified names when possible.
- Short names like `po` work, but fully-qualified names reduce ambiguity.
- If unspecified, Velero includes all eligible resources after namespace/label filters.

### 6.4 `excludedResources`

Exclude selected resource types.

```yaml
spec:
  excludedResources:
    - events
    - events.events.k8s.io
    - pods
    - replicasets.apps
```

Common exclusions:

| Resource | Why exclude |
|---|---|
| `events` | Noisy, short-lived, not useful for restore. |
| `pods` | Usually recreated by controllers such as Deployment/StatefulSet. |
| `replicasets.apps` | Usually recreated by Deployment. Be careful with rollback needs. |
| `endpoints` / `endpointslices` | Recreated by Service/controller logic. |
| `leases.coordination.k8s.io` | Runtime leader-election/heartbeat objects. |

Do **not** blindly exclude `secrets`. Many applications require secrets to restore successfully.

### 6.5 `includeClusterResources`

Controls cluster-scoped resources.

```yaml
spec:
  includeClusterResources: true
```

Cluster-scoped examples:

- `ClusterRole`
- `ClusterRoleBinding`
- `CustomResourceDefinition`
- `StorageClass`
- `PersistentVolume`
- `SecurityContextConstraints`
- `PriorityClass`
- `APIService`

Default behavior is subtle:

- If you back up all namespaces, cluster-scoped resources are generally included by default.
- If you filter by namespace, cluster-scoped resources are generally not included except related resources such as PVs associated with included PVCs.
- If you explicitly set `includeClusterResources: false`, cluster-scoped resources are excluded.

Use case:

```yaml
spec:
  includedNamespaces:
    - myapp-prod
  includeClusterResources: true
```

This is useful when your app depends on cluster-scoped CRDs, ClusterRoles, or SCCs.

Risk:

> Restoring cluster-scoped resources to another cluster can overwrite or conflict with existing platform-level configuration.

Use with care.

### 6.6 `includedClusterScopedResources`

Newer Velero versions support explicit cluster-scoped resource filters.

```yaml
spec:
  includedNamespaces:
    - myapp-prod
  includedClusterScopedResources:
    - customresourcedefinitions.apiextensions.k8s.io
    - clusterroles.rbac.authorization.k8s.io
    - persistentvolumes
```

This is safer than `includeClusterResources: true` when you need only selected cluster resources.

### 6.7 `excludedClusterScopedResources`

```yaml
spec:
  excludedClusterScopedResources:
    - storageclasses.storage.k8s.io
    - nodes
```

Good for preventing restore of platform-owned resources.

### 6.8 `includedNamespaceScopedResources`

```yaml
spec:
  includedNamespaceScopedResources:
    - deployments.apps
    - services
    - routes.route.openshift.io
    - configmaps
    - secrets
```

Use when you want exact control over namespaced resources.

### 6.9 `excludedNamespaceScopedResources`

```yaml
spec:
  excludedNamespaceScopedResources:
    - pods
    - events
    - replicasets.apps
```

### 6.10 `labelSelector`

Back up only objects matching all labels.

```yaml
spec:
  includedNamespaces:
    - myapp-prod
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payments
```

Use this for multi-application namespaces.

Important:

> Label selection applies to objects. If your application objects are not consistently labeled, backup will be incomplete.

### 6.11 `orLabelSelectors`

Back up objects matching any one selector.

```yaml
spec:
  includedNamespaces:
    - myapp-prod
  orLabelSelectors:
    - matchLabels:
        app: frontend
    - matchLabels:
        app: backend
    - matchLabels:
        app: database
```

Do not use `labelSelector` and `orLabelSelectors` together.

### 6.12 `storageLocation`

Selects the `BackupStorageLocation`.

```yaml
spec:
  storageLocation: aws-primary
```

Check available locations:

```bash
oc get backupstoragelocations.velero.io -n openshift-adp
oc describe backupstoragelocation aws-primary -n openshift-adp
```

### 6.13 `ttl`

Defines backup retention.

```yaml
spec:
  ttl: 720h0m0s
```

Examples:

| TTL | Meaning |
|---|---|
| `24h0m0s` | 1 day |
| `168h0m0s` | 7 days |
| `720h0m0s` | 30 days |
| `2160h0m0s` | 90 days |

When a backup expires, Velero garbage collection can delete the backup CR, object storage archive, volume snapshots, and associated restore metadata.

### 6.14 `snapshotVolumes`

Controls volume snapshot behavior.

```yaml
spec:
  snapshotVolumes: false
```

For resource-only backup, set:

```yaml
snapshotVolumes: false
```

For resource + snapshot backup, set:

```yaml
snapshotVolumes: true
```

If unset, Velero decides based on configured snapshot provider/plugin support.

### 6.15 `defaultVolumesToFsBackup`

Use File System Backup for pod volumes by default.

```yaml
spec:
  defaultVolumesToFsBackup: true
```

Useful when:

- storage does not support CSI snapshots
- NFS-like storage is used
- you want file-level volume copy behavior

Important:

> File System Backup reads live mounted files. It might be less crash-consistent than storage snapshots unless you use application hooks or application-native quiescing.

### 6.16 `snapshotMoveData`

In newer OADP/Velero data mover workflows:

```yaml
spec:
  snapshotMoveData: true
```

This means:

1. create CSI snapshot
2. move snapshot data to backup storage
3. make restore less dependent on the original storage snapshot backend

Use when your DR target should not depend only on the source cluster’s snapshot backend.

### 6.17 `volumeSnapshotLocations`

```yaml
spec:
  volumeSnapshotLocations:
    - aws-primary
```

Use when multiple snapshot locations exist.

### 6.18 `hooks`

Backup hooks run commands inside containers before or after processing pod resources.

Example:

```yaml
spec:
  hooks:
    resources:
      - name: mysql-flush-hook
        includedNamespaces:
          - mysql-prod
        includedResources:
          - pods
        labelSelector:
          matchLabels:
            app: mysql
        pre:
          - exec:
              container: mysql
              command:
                - /bin/sh
                - -c
                - "mysql -uroot -p$MYSQL_ROOT_PASSWORD -e 'FLUSH TABLES WITH READ LOCK;'"
              onError: Fail
              timeout: 30s
        post:
          - exec:
              container: mysql
              command:
                - /bin/sh
                - -c
                - "mysql -uroot -p$MYSQL_ROOT_PASSWORD -e 'UNLOCK TABLES;'"
              onError: Continue
              timeout: 30s
```

Use hooks carefully. A bad hook can fail or delay backups.

### 6.19 `orderedResources`

Controls processing order for specific objects.

Example for database pods:

```yaml
spec:
  orderedResources:
    pods: mysql-prod/mysql-0,mysql-prod/mysql-1,mysql-prod/mysql-2
```

This is useful when application consistency depends on ordering.

### 6.20 `csiSnapshotTimeout`

```yaml
spec:
  csiSnapshotTimeout: 20m
```

Increase this when CSI snapshots are slow.

### 6.21 `itemOperationTimeout`

```yaml
spec:
  itemOperationTimeout: 6h
```

Useful when plugin operations or data movement take longer than default.

### 6.22 `resourcePolicy`

References a ConfigMap containing resource/volume policies.

```yaml
spec:
  resourcePolicy:
    kind: configmap
    name: resource-policy-configmap
```

Resource policies are useful for repeatable enterprise backup standards.

## 7. Production Backup Design Patterns

### Pattern 1: Resource-Only Backup for Stateless Application

Use when the application has no persistent data or persistent data is handled externally.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: frontend-resource-only-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - frontend-prod
  includedResources:
    - deployments.apps
    - services
    - routes.route.openshift.io
    - configmaps
    - secrets
    - serviceaccounts
    - roles.rbac.authorization.k8s.io
    - rolebindings.rbac.authorization.k8s.io
  excludedResources:
    - pods
    - events
    - replicasets.apps
  snapshotVolumes: false
  storageLocation: default
  ttl: 720h0m0s
```

Why this is clean:

- excludes runtime noise
- avoids unnecessary PV snapshot workflow
- focuses on reconstructing desired state

### Pattern 2: Namespace-Level Application Backup

Use when the namespace contains a single application stack.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-ns-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - payments-prod
  excludedResources:
    - events
    - events.events.k8s.io
  storageLocation: default
  ttl: 720h0m0s
```

This is simple and often effective.

Risk:

- includes more objects than needed
- may include generated or temporary resources
- may miss cluster-scoped dependencies unless configured

### Pattern 3: Label-Based Application Backup in Shared Namespace

Use when multiple apps share a namespace.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: payments-label-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - shared-prod
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: payments
  storageLocation: default
  ttl: 720h0m0s
```

Production requirement:

> Every object belonging to the application must be consistently labeled.

Check labels:

```bash
oc get all,cm,secret,route,pvc -n shared-prod --show-labels
```

### Pattern 4: Backup Application CRs Managed by Operators

Example: a custom application CR creates lower-level Kubernetes objects.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: operator-app-cr-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app-prod
  includedResources:
    - myapps.platform.example.com
    - secrets
    - configmaps
    - services
    - routes.route.openshift.io
  includedClusterScopedResources:
    - customresourcedefinitions.apiextensions.k8s.io
  storageLocation: default
  ttl: 720h0m0s
```

Warning:

> Backing up application CRs is useful, but restoring them requires the corresponding Operator and CRDs to exist on the target cluster.

### Pattern 5: Resource + PVC Metadata but No Data Backup

Use when database backup is handled by native tools such as pgBackRest, RMAN, mysqldump, MongoDB Ops Manager, etc.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: db-resource-metadata-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - db-prod
  includedResources:
    - statefulsets.apps
    - services
    - configmaps
    - secrets
    - persistentvolumeclaims
  snapshotVolumes: false
  storageLocation: default
  ttl: 720h0m0s
```

This backs up how the workload is defined, not the database data.

### Pattern 6: Resource + CSI Snapshot Backup

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: postgres-csi-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - postgres-prod
  excludedResources:
    - events
  snapshotVolumes: true
  volumeSnapshotLocations:
    - odf-primary
  storageLocation: default
  ttl: 720h0m0s
```

Use when:

- CSI snapshots are supported
- `VolumeSnapshotClass` exists
- application consistency is acceptable or handled by hooks/database logic

### Pattern 7: Resource + File System Backup

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: nfs-app-fsb-backup-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - nfs-app-prod
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
  storageLocation: default
  ttl: 720h0m0s
```

Use when:

- storage does not support snapshots
- application data is in NFS or filesystem-style volumes
- node-agent is enabled

## 8. What to Include and Exclude — Senior Admin Guidance

### 8.1 Usually Include

For application restore:

```text
namespace
serviceaccounts
roles
rolebindings
secrets
configmaps
services
routes/ingresses
deployments/statefulsets/daemonsets
jobs/cronjobs
persistentvolumeclaims
application custom resources
networkpolicies
horizontalpodautoscalers
poddisruptionbudgets
```

OpenShift-specific resources:

```text
routes.route.openshift.io
imagestreams.image.openshift.io
buildconfigs.build.openshift.io
```

Only if required:

```text
securitycontextconstraints.security.openshift.io
clusterroles
clusterrolebindings
customresourcedefinitions
storageclasses
priorityclasses
```

### 8.2 Usually Exclude

```text
events
pods, if controlled by Deployment/StatefulSet/DaemonSet
replicasets, unless rollback metadata matters
endpoints
endpointslices
leases
controllerrevisions, unless StatefulSet/DaemonSet rollback detail is needed
```

### 8.3 Be Careful With Secrets

Secrets often contain:

- database passwords
- TLS keys
- registry pull secrets
- OAuth client secrets
- application tokens

If you exclude secrets, the application may restore but fail to start.

If you include secrets, secure the backup storage:

- encrypt bucket/server-side if available
- restrict IAM/user access
- avoid broad read access
- rotate credentials after major incidents
- audit access to backup storage

### 8.4 Be Careful With Cluster-Scoped Resources

Cluster-scoped resource restore can be dangerous.

Example risks:

- restoring old `StorageClass` definitions
- overwriting `ClusterRole` objects
- restoring incompatible CRDs
- restoring SCCs that are too permissive
- conflicts across clusters

Recommended approach:

```text
Back up cluster-scoped dependencies separately and restore only after review.
```

  storageLocation: default
  ttl: 720h0m0s

## 10. Scheduling Resource Backups

A `Schedule` CR creates backups repeatedly.

Example: every day at 01:30 UTC.

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: myapp-daily-resource-backup
  namespace: openshift-adp
spec:
  schedule: "30 1 * * *"
  template:
    includedNamespaces:
      - myapp-prod
    excludedResources:
      - events
      - events.events.k8s.io
      - pods
      - replicasets.apps
    snapshotVolumes: false
    storageLocation: default
    ttl: 168h0m0s
```

Apply:

```bash
oc apply -f myapp-daily-resource-backup.yaml
```

Check:

```bash
oc get schedules.velero.io -n openshift-adp
velero schedule get
```

Manually trigger from schedule template:

```bash
velero backup create --from-schedule myapp-daily-resource-backup
```

## 11. Restore Considerations for Resource Backups

A resource backup is useful only if you regularly test restore.

Example restore:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-myapp-resource-001
  namespace: openshift-adp
spec:
  backupName: myapp-resource-backup-001
  includedNamespaces:
    - myapp-prod
```

Restore to a different namespace:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-myapp-to-test-001
  namespace: openshift-adp
spec:
  backupName: myapp-resource-backup-001
  namespaceMapping:
    myapp-prod: myapp-restore-test
```

Check restore:

```bash
oc get restore -n openshift-adp
oc describe restore restore-myapp-to-test-001 -n openshift-adp
velero restore describe restore-myapp-to-test-001 --details
velero restore logs restore-myapp-to-test-001
```

Important restore behavior:

> Velero restore is normally non-destructive. If the resource already exists, Velero skips it unless configured otherwise in supported versions/options.

Production restore plan:

1. Restore into a test namespace first.
2. Validate objects.
3. Validate pods.
4. Validate routes/services.
5. Validate secrets and config.
6. Validate PVC/data strategy separately.
7. Only then restore to production or perform cutover.

## 12. Resource Backup and GitOps

Many advanced OpenShift environments use GitOps with Argo CD or OpenShift GitOps.

Question:

> If resources are already in Git, why use OADP resource backup?

Because GitOps usually does not protect everything:

- generated secrets
- runtime-created ConfigMaps
- cert-manager issued TLS secrets
- operator-generated resources
- PVC objects
- application CR status-related dependency context
- Route host changes
- emergency hotfixes not yet committed
- tenant-created resources
- third-party operator CRs

Best practice:

```text
GitOps = source of desired config
OADP = point-in-time cluster/application recovery
Both are needed.
```

Recommended enterprise model:

| Item | Best source of recovery |
|---|---|
| Application manifests | GitOps repository |
| Runtime secrets | External secret manager + OADP fallback |
| PVC data | CSI snapshot / FSB / database-native backup |
| Application CRs | GitOps + OADP |
| Emergency config | OADP point-in-time backup |
| Cluster control plane | etcd backup |

## 13. Security Considerations

### 13.1 Backup Storage Contains Sensitive Data

OADP resource backups can include secrets.

Treat object storage as sensitive.

Secure it with:

- least privilege IAM/user permissions
- encryption at rest
- TLS in transit
- private endpoints where possible
- bucket policy restrictions
- audit logging
- retention policy
- separation between prod and non-prod backup stores
- separate credentials per cluster/environment

### 13.2 RBAC for Backup Creation

By default, backup/restore operations are normally admin-controlled.

For self-service backup models:

- create limited RBAC
- restrict namespaces
- avoid cluster-wide backup permissions
- audit backup/restore actions
- define who can restore secrets
- define who can access backup logs

### 13.3 Avoid Backing Up Unnecessary Secrets

Some secrets are short-lived or dangerous to restore:

- service account bound tokens
- temporary OAuth tokens
- generated session secrets
- certificate rotation artifacts

Use exclusions only after understanding application impact.

### 13.4 Object Lock / Immutability Caveat

If your organization requires ransomware-resistant backups, validate whether your exact OADP version and object storage configuration supports your desired immutability controls. Do not assume bucket versioning or object lock is automatically supported end-to-end by OADP.

## 14. Performance and Scale Considerations

### 14.1 Reduce Scope

The fastest backup is the backup that avoids unnecessary objects.

Good filters:

```yaml
includedNamespaces:
  - myapp-prod
excludedResources:
  - events
  - pods
  - replicasets.apps
```

### 14.2 Avoid Backing Up High-Churn Resources

High-churn resources increase API load and backup noise.

Examples:

- events
- leases
- endpoints
- endpointslices
- pods in large namespaces

### 14.3 Watch API Server Load

Large backups query many API objects.

Monitor:

```bash
oc adm top pods -n openshift-adp
oc adm top pods -n openshift-apiserver
oc adm top pods -n openshift-kube-apiserver
```

Also monitor API server request latency and etcd health in OpenShift monitoring.

### 14.4 Parallel Backup Processing

Newer OADP releases include or document parallel backup processing capabilities. Use this carefully.

Guidance:

- increase Velero CPU/memory before enabling high concurrency
- do not run multiple huge namespace backups at the same time
- avoid parallel backups of the same namespace unless your version explicitly supports your use case
- monitor object storage throttling
- monitor CSI snapshot backend limits

Check field availability:

```bash
oc explain dpa.spec.configuration.velero
oc explain dpa.spec.configuration.velero.itemBlockWorkerCount
```

Example version-dependent DPA tuning:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa
  namespace: openshift-adp
spec:
  configuration:
    velero:
      itemBlockWorkerCount: 4
```

Validate your installed OADP CRD before applying this field.

### 14.5 Object Storage Bottlenecks

Symptoms:

- backup remains `InProgress`
- log upload slow
- S3 timeout errors
- `BackupStorageLocation` intermittently unavailable
- high latency to object store

Check:

```bash
oc describe backupstoragelocation -n openshift-adp
oc logs deploy/velero -n openshift-adp
```

## 15. Troubleshooting Resource Backup

### 15.1 Backup Stuck in `New`

Possible causes:

- Velero deployment not running
- Velero controller not watching namespace
- another long backup blocking processing in sequential mode
- controller crash loop

Commands:

```bash
oc get pods -n openshift-adp
oc logs deploy/velero -n openshift-adp
oc get backup -n openshift-adp
```

### 15.2 Backup `FailedValidation`

Possible causes:

- invalid Backup spec
- missing BackupStorageLocation
- invalid resource policy
- conflicting include/exclude fields
- invalid label selector

Commands:

```bash
oc describe backup <backup-name> -n openshift-adp
oc get backup <backup-name> -n openshift-adp -o yaml
```

### 15.3 Backup `PartiallyFailed`

This is common in real environments and must not be ignored.

Possible causes:

- missing permission for a resource
- API resource unavailable
- CRD discovery issue
- plugin error
- object cannot be listed
- resource deleted during backup
- snapshot failure for one PVC

Commands:

```bash
velero backup describe <backup-name> --details
velero backup logs <backup-name> | egrep -i 'error|warn|fail|denied|forbidden'
```

### 15.4 `BackupStorageLocation` Not Available

Check:

```bash
oc get bsl -n openshift-adp
oc describe bsl <bsl-name> -n openshift-adp
oc get secret -n openshift-adp
oc logs deploy/velero -n openshift-adp
```

Common causes:

- wrong bucket name
- wrong region
- wrong credentials
- TLS/CA issue
- DNS issue
- proxy issue
- bucket policy denies access
- S3 endpoint path style/virtual host style mismatch

### 15.5 Resources Missing After Restore

Possible causes:

- resource was excluded
- namespace was excluded
- label selector did not match
- CRD missing on target cluster
- API version missing on target cluster
- restore skipped existing resource
- admission webhook blocked restore
- RBAC/SCC differences

Commands:

```bash
velero restore describe <restore-name> --details
velero restore logs <restore-name> | egrep -i 'skip|error|warn|fail|denied|forbidden'
oc api-resources | grep -i <resource>
oc get crd | grep -i <crd>
```

### 15.6 Secrets Restored but Pods Fail

Check:

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
oc describe pod <pod> -n <namespace>
oc get secret -n <namespace>
oc get sa -n <namespace>
oc adm policy who-can use scc <scc-name>
```

Common causes:

- image pull secret missing
- service account token behavior changed
- SCC/RBAC mismatch
- external secret operator not present
- TLS cert expired
- secret restored but app expected rotated credential

### 15.7 Route Restored but Application Not Reachable

Check:

```bash
oc get route -n <namespace>
oc describe route <route> -n <namespace>
oc get svc,endpoints,endpointslice -n <namespace>
oc get pods -n <namespace> -o wide
```

Common causes:

- service selector mismatch
- pods not ready
- route host conflict
- TLS secret missing
- ingress/router policy differences on target cluster

## 17. Interview-Grade Explanation

### Question: What is resource backup in OADP?

Resource backup in OADP is the process of backing up Kubernetes and OpenShift API objects that define an application. OADP uses Velero `Backup` custom resources to capture objects such as Deployments, Services, Routes, ConfigMaps, Secrets, PVCs, RBAC objects, and selected custom resources. These objects are serialized into a backup archive and stored in a configured `BackupStorageLocation`, usually S3-compatible object storage.

It is different from backing up PV data. A resource backup can capture PVC metadata, but the actual data inside the volume requires CSI snapshots, data mover, or File System Backup. For production, I design backups around namespaces, labels, and resource filters, exclude noisy runtime objects like Events, and carefully decide whether to include cluster-scoped objects such as CRDs, ClusterRoles, StorageClasses, SCCs, and PVs. I also test restore regularly because a backup that has never been restored is only an assumption.

### Question: Why should you not use OADP as full cluster backup?

OADP is primarily application-centric. It protects customer workloads and related resources. It does not replace etcd backup, infrastructure backup, GitOps repository backup, or full OpenShift control-plane disaster recovery. For cluster recovery, I still maintain OpenShift etcd backups and platform-level DR procedures. OADP is used for application restore, migration, and namespace-level recovery.

### Question: What happens when you create a Backup CR?

When a `Backup` CR is created, the Kubernetes API stores it. Velero’s BackupController sees the new object, validates it, discovers API resources, applies filters, processes items through Velero and OADP plugins, serializes selected resources into an archive, uploads the archive/logs to object storage, optionally handles PV snapshots or filesystem backups, and updates backup status to `Completed`, `PartiallyFailed`, or `Failed`.

### Question: What resources do you exclude from a backup?

I usually exclude ephemeral and noisy resources such as Events, Pods controlled by Deployments, Endpoints, EndpointSlices, Leases, and sometimes ReplicaSets. I do not blindly exclude Secrets because most applications need them during restore. I review cluster-scoped resources carefully because restoring them can conflict with target cluster configuration.

### Question: How do you validate a backup?

I validate at three levels:

1. Control plane level: `oc get backup`, `oc describe backup`, backup phase.
2. Velero level: `velero backup describe --details` and `velero backup logs`.
3. Recovery level: actual restore into a test namespace or test cluster and application validation.

## 20. Common Mistakes

| Mistake | Impact | Correct approach |
|---|---|---|
| Backing up all namespaces blindly | Huge backups, conflicts, slow restore | Use namespace/label filters |
| Assuming PVC backup means data backup | Data loss during restore | Use CSI snapshot, data mover, FSB, or DB-native backup |
| Excluding secrets blindly | App fails after restore | Include needed secrets or restore from external secret manager |
| Including all cluster-scoped resources | Target cluster conflicts | Include only required cluster resources |
| Never testing restore | False confidence | Schedule restore drills |
| Ignoring `PartiallyFailed` | Hidden restore issues | Review logs and errors |
| Backing up Operator-managed resources without Operator planning | CR restore fails | Ensure CRDs/Operators exist before restore |
| No TTL strategy | Object storage growth | Define retention by RPO/RTO/compliance |
| No security review | Secret exposure | Secure object storage and credentials |

## 21. Best Practices Summary

1. Design OADP backups at application/namespace level, not full cluster level.
2. Separate resource backup strategy from volume/data backup strategy.
3. Exclude noisy runtime resources like events, leases, endpoints, and unnecessary pods.
4. Include secrets only when required and secure object storage properly.
5. Include cluster-scoped resources only after dependency review.
6. Use labels consistently for application-level backup in shared namespaces.
7. Use backup hooks for application-consistent backups where needed.
8. Use `ttl` to control retention.
9. Monitor backup status, warnings, and object storage health.
10. Test restore regularly in another namespace or cluster.
11. Keep GitOps, OADP, etcd backup, and database-native backups aligned.
12. Document RPO, RTO, owner, schedule, and restore process.

## 24. Final Senior-Level Takeaway

For a 10+ year OpenShift administrator, OADP resource backup should be treated as an application recovery mechanism, not a blind cluster dump.

A good resource backup design answers these questions clearly:

```text
What application am I protecting?
Which namespaces contain it?
Which resource types are required to recreate it?
Which resources are runtime noise?
Which secrets are required?
Which cluster-scoped dependencies are required?
Is persistent data protected separately?
Where is the backup stored?
How long is it retained?
When was restore last tested?
```

The real value of OADP is not just creating backups. The real value is building a repeatable, secure, tested application recovery process.
